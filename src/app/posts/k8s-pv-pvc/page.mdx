<EasyIntro>
  컨테이너 안에 쓴 파일은 Pod가 사라질 때 같이 사라진다. 데이터베이스를 그렇게 띄워 두면 기계를 바꾸는 날 테이블이 통째로 없어진다. 그래서 쿠버네티스는 Pod보다 오래 사는 디스크를 따로 다루는데, 디스크가 필요하다는 요청서가 PVC이고 실제 디스크 하나가 PV이며 디스크를 찍어 내는 틀이 StorageClass다.

  호텔에 비유하면 손님이 이런 방이 필요하다고 요청서를 내면, 비어 있는 방 중 조건에 맞는 가장 작은 방이 배정되거나, 틀에 따라 새 방을 지어 준다. 클라우드 디스크는 한 구역에 묶여 있어서 그 구역 밖의 기계로는 Pod가 갈 수 없다. 그래서 Pod가 갈 기계가 정해진 뒤에 그 구역에 디스크를 만드는 방식을 쓴다.

  흔한 실수는 요청서를 지웠다가 같은 이름으로 다시 내면 옛 디스크가 돌아올 거라 믿는 것이다. 자동으로 만든 디스크는 기본으로 요청서와 함께 지워지고, 남겨 두는 설정이어도 새 요청서가 옛 디스크를 알아서 찾아가지는 않는다.
</EasyIntro>

Postgres를 Deployment 하나로 띄워 두고 잘 쓰고 있었다. 노드를 교체하는 날, Pod가 다른 노드에서 다시 떴고 테이블이 전부 사라졌다. 데이터는 컨테이너 안의 `/var/lib/postgresql/data`에 있었는데, 그 디렉터리는 Pod와 함께 지워졌다.

그래서 PersistentVolumeClaim(PVC)을 붙였다. 이번엔 다른 문제가 생긴다. 디스크가 `ap-northeast-2c`에 만들어진 뒤로 Pod가 다른 존의 노드로 가지 못하고 Pending에 머문다. 정리하려고 PVC를 지웠다 같은 이름으로 다시 만들었더니 빈 디스크가 붙는다. 이 글은 쿠버네티스가 디스크를 요청하고, 만들고, 붙이고, 돌려받는 과정을 따라가면서 이런 일이 왜 생기는지 본다.

출력은 [ConfigMap 글](/posts/k8s-configmap)과 같은 kwok 실습 클러스터(Kubernetes 1.30)에서 받았다. PV 컨트롤러, 스케줄러, 확장 컨트롤러는 진짜라서 바인딩, 대기 이벤트, 존 충돌은 실제 출력이다. 다만 kwok에는 디스크를 만드는 프로비저너가 없다. 그래서 프로비저너가 할 일(PV 만들기)은 손으로 대신했고, 클라우드 쪽에서만 볼 수 있는 출력은 예시로 표시했다.

## 컨테이너 안의 파일은 Pod와 함께 사라진다

컨테이너가 파일을 쓰는 곳은 이미지 위에 얹힌 쓰기 레이어다. 컨테이너가 지워지면 이 레이어도 지워진다. Docker에서 이 문제를 볼륨으로 푸는 과정은 [Docker 네트워크와 볼륨 글](/posts/docker-network-volume)에서 봤다. 쿠버네티스에서는 Pod가 다른 노드로 옮겨 다니니 노드의 디렉터리에 두는 것만으로는 부족하다.

쿠버네티스에서 Pod 수준으로 쓰는 볼륨은 둘을 먼저 알아 둔다. `emptyDir`은 Pod가 노드에 놓일 때 빈 디렉터리로 생기고 Pod가 지워질 때 사라진다. 컨테이너 재시작에는 살아남는다. 같은 Pod의 컨테이너끼리 파일을 나누거나 캐시를 두는 용도다.

```yaml
      volumes:
        - name: cache
          emptyDir:
            sizeLimit: 2Gi        # 넘으면 kubelet이 Pod를 쫓아낸다
        - name: shm
          emptyDir:
            medium: Memory        # tmpfs. 쓴 만큼 컨테이너 메모리로 센다
```

`medium: Memory`는 빠르지만 쓴 양이 메모리 사용량에 잡힌다. 메모리 limits를 넘으면 OOMKilled가 된다. 이 관계는 [requests와 limits 글](/posts/k8s-pod-resources)에서 본다.

`hostPath`는 노드의 디렉터리를 그대로 Pod에 붙인다. Pod가 다른 노드로 가면 다른 디렉터리를 보게 되고, 컨테이너가 노드 파일 시스템에 손댈 수 있어서 보안상 위험하다. Pod Security Standards의 baseline 수준부터 hostPath를 막는다. 노드 에이전트(로그 수집기, CNI)처럼 노드를 꼭 봐야 하는 DaemonSet이 아니면 쓰지 않는다.

Pod보다 오래 사는 데이터가 필요하면 PersistentVolume으로 간다.

## 디스크를 요청하는 쪽과 내주는 쪽

쿠버네티스는 디스크를 객체 셋으로 나눠 다룬다. 개발자는 "10Gi짜리, 한 노드에서 읽고 쓰는 디스크가 필요하다"고 PVC로 요청한다. 실제 디스크 하나를 나타내는 것은 PersistentVolume(PV)이다. StorageClass는 "이런 종류의 디스크는 이 프로비저너가 이런 설정으로 만든다"는 틀이다.

이렇게 나눈 이유는 역할이 다르기 때문이다. 앱을 배포하는 사람은 디스크가 EBS인지 Ceph인지 몰라도 된다. 같은 매니페스트를 AWS에서도 온프레미스에서도 쓰고, 어떤 디스크가 붙을지는 클러스터의 StorageClass가 정한다. PVC는 네임스페이스에 속하고, PV와 StorageClass는 클러스터 단위 객체다. PVC와 PV는 일대일로 묶이고, 한 번 묶이면 다른 PVC가 그 PV를 가져가지 못한다.

## 미리 만든 PV에 PVC가 묶이는 과정

동적 프로비저닝이 없던 시절처럼 관리자가 PV를 미리 만들어 두는 경우부터 본다. 이걸 정적 프로비저닝이라고 한다. 원리가 가장 잘 보인다.

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-orders-10g
spec:
  capacity:
    storage: 10Gi
  accessModes: ["ReadWriteOnce"]
  persistentVolumeReclaimPolicy: Retain   # PVC가 지워져도 디스크를 남긴다
  storageClassName: manual                # 같은 이름을 요청한 PVC만 묶인다
  hostPath:
    path: /mnt/data/orders                # 실습용. 운영에서는 csi, nfs 등
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: orders-data
  namespace: shop
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: manual
  resources:
    requests:
      storage: 5Gi                        # 5Gi를 요청한다
```

```bash
# PV를 만들고 상태를 본다
kubectl apply -f pv.yaml
kubectl get pv

# PVC를 만들고 둘 다 다시 본다
kubectl apply -f pvc.yaml
kubectl get pv
kubectl get pvc -n shop
```

## 접근 모드는 Pod가 아니라 노드를 센다

접근 모드는 넷이다. `ReadWriteOnce`(RWO)는 한 노드에서 읽기·쓰기로 붙일 수 있다. `ReadOnlyMany`(ROX)는 여러 노드에서 읽기만, `ReadWriteMany`(RWX)는 여러 노드에서 읽기·쓰기다. `ReadWriteOncePod`(RWOP)는 클러스터 전체에서 Pod 하나만 쓸 수 있고, 1.29부터 정식이며 CSI 드라이버에서만 된다.

RWO에서 "Once"는 노드 하나다. 같은 노드에 뜬 Pod 둘은 RWO 볼륨을 함께 쓸 수 있다. 정말 Pod 하나만 쓰게 하고 싶으면 RWOP를 쓴다. DB처럼 두 프로세스가 같은 데이터 디렉터리를 열면 망가지는 경우다.

어떤 모드를 쓸 수 있는지는 스토리지가 정한다. AWS EBS는 블록 디스크라 RWO다. 여러 노드에서 함께 쓰려면 EFS 같은 네트워크 파일 시스템(RWX)을 쓴다. PVC에 RWX를 적는다고 EBS가 공유 디스크가 되지는 않는다. 위의 `uploads`처럼 맞는 PV를 못 찾거나, 프로비저너가 거절해서 Pending에 머문다.

## StorageClass가 디스크를 만들어 준다

PV를 손으로 미리 만들어 두는 건 번거롭다. 크기가 다양한 요청을 다 맞추기도 어렵다. 그래서 운영에서는 대부분 StorageClass로 동적 프로비저닝을 한다. PVC가 들어오면 프로비저너가 디스크를 새로 만들고 PV도 만들어 묶는다.

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"   # class를 안 적은 PVC가 쓴다
provisioner: ebs.csi.aws.com           # 이 CSI 드라이버가 디스크를 만든다
parameters:
  type: gp3
  fsType: ext4
reclaimPolicy: Delete                  # 기본값. PVC를 지우면 디스크도 지운다
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
```

```bash
# StorageClass 둘(gp3, gp3-immediate)을 만들고 본다
kubectl apply -f sc.yaml
kubectl get sc

# 아까 class 없이 만든 cache-data를 다시 본다
kubectl get pvc cache-data -n shop
```

```text
storageclass.storage.k8s.io/gp3 created
storageclass.storage.k8s.io/gp3-immediate created
NAME            PROVISIONER       RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
gp3 (default)   ebs.csi.aws.com   Delete          WaitForFirstConsumer   true                   0s
gp3-immediate   ebs.csi.aws.com   Delete          Immediate              false                  0s
NAME         STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
cache-data   Pending                                      gp3            <unset>                 45s
```

StorageClass 없이 만들어 둔 `cache-data`에 기본 StorageClass `gp3`가 나중에 채워졌다. 1.28부터 정식인 기능으로, 기본 StorageClass가 생기면 class가 비어 있는 PVC에 소급해서 넣는다. 반대로 정적 PV에만 묶고 싶은 PVC라면 `storageClassName: ""`을 명시해야 기본 class로 끌려가지 않는다.

`reclaimPolicy`의 기본값은 `Delete`다. 동적으로 만든 디스크는 PVC를 지우면 디스크까지 지워진다. 뒤에서 다시 본다.

## 노드가 정해진 뒤에 디스크를 만든다

`volumeBindingMode`는 디스크를 언제 만들지 정한다. `Immediate`는 PVC가 생기자마자 만들고, `WaitForFirstConsumer`는 그 PVC를 쓰는 Pod가 노드에 배정될 때까지 기다린다. 두 PVC를 만들어 이벤트를 비교한다.

```bash
# 기본 class(gp3)의 pg-data와 gp3-immediate의 pg-data-imm을 만든다
kubectl apply -f pvc-dyn.yaml
kubectl describe pvc pg-data -n shop | sed -n '/Events/,$p'
kubectl describe pvc pg-data-imm -n shop | sed -n '/Events/,$p'
```

```text
persistentvolumeclaim/pg-data created
persistentvolumeclaim/pg-data-imm created
Events:
  Type    Reason                Age   From                         Message
  ----    ------                ----  ----                         -------
  Normal  WaitForFirstConsumer  8s    persistentvolume-controller  waiting for first consumer to be created before binding
Events:
  Type    Reason                Age   From                         Message
  ----    ------                ----  ----                         -------
  Normal  ExternalProvisioning  8s    persistentvolume-controller  Waiting for a volume to be created either by the external provisioner 'ebs.csi.aws.com' or manually by the system administrator. If volume creation is delayed, please verify that the provisioner is running and correctly registered.
```

`Immediate` 쪽은 바로 프로비저너를 기다린다. 이 메시지가 몇 분씩 이어지면 CSI 드라이버가 설치돼 있지 않거나, 드라이버의 컨트롤러 Pod가 죽었거나, 드라이버에 클라우드 권한(IAM)이 없는 것이다. EKS에서 EBS CSI 드라이버 애드온을 빼먹은 클러스터가 정확히 이 상태다.

기다리는 이유는 존 때문이다. EBS 볼륨은 가용 영역(AZ) 하나에 만들어지고 같은 AZ의 인스턴스에만 붙는다. Pod가 어느 노드에 갈지 모르는 상태에서 디스크를 먼저 만들면 엉뚱한 AZ에 만들 수 있다. `WaitForFirstConsumer`는 스케줄러가 노드를 고를 때까지 기다렸다가 그 노드의 AZ에 디스크를 만든다. 아래 그림이 그 순서다.

## 디스크가 다른 존에 있으면 Pod가 못 간다

디스크가 `ap-northeast-2c`에 생긴 뒤로 이 Pod는 그 존에만 갈 수 있다. node-2를 교체하려고 cordon하고 Pod를 지우면 어떻게 되는지 본다. 노드는 둘이고 node-1은 `ap-northeast-2a`다.

```bash
# node-2에 새 Pod가 못 오게 하고, Pod를 다시 만든다
kubectl cordon node-2
kubectl delete pod pg-0 -n shop
kubectl apply -f pg-pod.yaml
kubectl describe pod pg-0 -n shop | sed -n '/Events/,$p'
```

## PVC를 지우면 디스크는 어떻게 되나

PV의 `persistentVolumeReclaimPolicy`가 정한다. `Delete`면 PVC를 지울 때 디스크까지 지운다. `Retain`이면 디스크와 PV를 남기고 PV를 Released 상태로 둔다. 예전에 있던 `Recycle`(안을 지우고 재사용)은 쓰지 않는다. 동적으로 만든 PV는 StorageClass의 `reclaimPolicy`를 물려받으니 대부분 `Delete`다.

Retain을 쓰면 안전해 보이지만 함정이 있다. 처음의 `orders-data`(Retain PV에 묶임)를 지웠다가 같은 이름으로 다시 만들어 본다. 클러스터에는 비어 있는 `pv-spare-10g`도 하나 있다.

```bash
# PVC를 지우고 PV 상태를 본다
kubectl delete pvc orders-data -n shop
kubectl get pv pv-orders-10g

# 같은 매니페스트로 PVC를 다시 만든다
kubectl apply -f pvc.yaml
kubectl get pvc orders-data -n shop
```

```text
persistentvolumeclaim "orders-data" deleted
NAME            CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS     CLAIM              STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
pv-orders-10g   10Gi       RWO            Retain           Released   shop/orders-data   manual         <unset>                          119s
persistentvolumeclaim/orders-data created
NAME          STATUS   VOLUME         CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
orders-data   Bound    pv-spare-10g   10Gi       RWO            manual         <unset>                 5s
```

이름이 같은 PVC인데 데이터가 든 `pv-orders-10g`가 아니라 빈 `pv-spare-10g`에 묶였다. Released PV의 `claimRef`에는 지워진 PVC의 uid가 남아 있어서, 같은 이름이라도 새 PVC는 다른 객체로 본다. 맞는 빈 PV가 없었다면 Pending에 머물렀을 것이고, 기본 StorageClass가 있었다면 새 빈 디스크가 만들어졌을 것이다. 어느 쪽이든 앱은 빈 데이터 디렉터리로 뜬다. DB라면 빈 DB를 초기화하고 정상처럼 돈다.

옛 디스크를 다시 붙이려면 PV의 `claimRef`를 지워 Available로 돌리고, 새 PVC가 `volumeName`으로 그 PV를 지목하게 한다.

```bash
# 잘못 묶인 PVC를 지운 뒤, 데이터가 든 PV의 claimRef를 지운다
kubectl delete pvc orders-data -n shop
kubectl patch pv pv-orders-10g --type json -p '[{"op":"remove","path":"/spec/claimRef"}]'
kubectl get pv pv-orders-10g

# volumeName으로 그 PV를 지목한 PVC를 만든다
kubectl apply -f pvc-pin.yaml
kubectl get pvc orders-data -n shop
```

```text
persistentvolumeclaim "orders-data" deleted
persistentvolume/pv-orders-10g patched
NAME            CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM   STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
pv-orders-10g   10Gi       RWO            Retain           Available           manual         <unset>                          2m15s
persistentvolumeclaim/orders-data created
NAME          STATUS   VOLUME          CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
orders-data   Bound    pv-orders-10g   10Gi       RWO            manual         <unset>                 26s
```

`claimRef`를 지운 PV는 처음 보는 PVC 아무에게나 묶일 수 있다. 그래서 claimRef를 지우기 전에 PVC를 먼저 만들어 두거나, 다른 PVC가 끼어들지 않게 바로 이어서 만든다. 실습에서는 묶이기까지 20초쯤 걸렸다. PV 컨트롤러가 주기적으로 다시 맞추기 때문이다.

`Delete` 정책인 동적 PV는 반대 방향의 위험이 있다. 실수로 PVC 하나, 혹은 네임스페이스 하나를 지우면 그 안의 모든 디스크가 함께 지워진다. 실습 클러스터에는 디스크를 지울 CSI 드라이버가 없어서 PV가 Released로 남았지만, 실제 EKS라면 PV와 EBS 볼륨이 곧 사라진다.

<Callout kind="warning" title="중요한 PVC를 지우기 전에 PV를 Retain으로 바꾼다">
마이그레이션이나 네임스페이스 정리처럼 PVC를 지워야 할 때는 먼저 묶인 PV의 회수 정책을 바꾼다. `kubectl patch pv <PV 이름> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'`를 실행하고 `kubectl get pv`의 RECLAIM POLICY 칸이 Retain인지 확인한 뒤 지운다. 이미 Delete로 지워졌다면 쿠버네티스에서는 되돌릴 수 없고, 클라우드의 스냅샷(EBS 스냅샷 등)에서 볼륨을 복원해 PV를 정적으로 다시 만드는 수밖에 없다. 그래서 운영 데이터 볼륨은 정기 스냅샷을 따로 걸어 둔다.
</Callout>

## 쓰는 중인 PVC는 지워지지 않는다

반대로 지웠는데 안 지워지는 경우도 있다. Pod가 쓰는 중인 PVC를 지우면 Terminating에 멈춘다.

```bash
# orders-data를 쓰는 Pod가 있는 상태에서 PVC를 지운다
kubectl delete pvc orders-data -n shop --wait=false
kubectl get pvc orders-data -n shop
kubectl describe pvc orders-data -n shop | grep -E "Status|Finalizers|Used By"
```

```text
persistentvolumeclaim "orders-data" deleted
NAME          STATUS        VOLUME          CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
orders-data   Terminating   pv-orders-10g   10Gi       RWO            manual         <unset>                 113s
Status:        Terminating (lasts 0s)
Finalizers:    [kubernetes.io/pvc-protection]
Used By:       orders-worker
```

`kubernetes.io/pvc-protection` 파이널라이저가 막고 있다. 쓰는 Pod(`Used By`)가 사라지면 컨트롤러가 파이널라이저를 떼고 PVC가 지워진다. 실습에서도 `orders-worker` Pod를 지우자 PVC가 사라졌다. 데이터를 쓰는 중인 디스크가 갑자기 빠지는 것을 막는 장치이니 파이널라이저를 손으로 떼지 않는다. PV에도 같은 역할의 `kubernetes.io/pv-protection`이 있다.

## 용량 늘리기

StorageClass에 `allowVolumeExpansion: true`가 있으면 PVC의 요청 크기를 늘려 디스크를 키울 수 있다.

```bash
# 20Gi를 50Gi로 늘린다
kubectl patch pvc pg-data -n shop -p '{"spec":{"resources":{"requests":{"storage":"50Gi"}}}}'
kubectl get pvc pg-data -n shop -o jsonpath='{.spec.resources.requests.storage} {.status.capacity.storage}'; echo

# 줄여 본다
kubectl patch pvc pg-data -n shop -p '{"spec":{"resources":{"requests":{"storage":"10Gi"}}}}'

# 정적 PV에 묶인 PVC를 늘려 본다
kubectl patch pvc orders-data -n shop -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'
```

```text
persistentvolumeclaim/pg-data patched
50Gi 20Gi
The PersistentVolumeClaim "pg-data" is invalid: spec.resources.requests.storage: Forbidden: field can not be less than previous value
Error from server (Forbidden): persistentvolumeclaims "orders-data" is forbidden: only dynamically provisioned pvc can be resized and the storageclass that provisions the pvc must support resize
```

요청(spec)은 50Gi가 됐지만 실제 크기(status)는 아직 20Gi다. 확장은 CSI 드라이버의 resizer가 클라우드 디스크를 키우고, 노드에서 파일 시스템까지 늘려야 끝난다. 실습 클러스터에는 resizer가 없어서 이벤트가 `ExternalExpanding  volume_expand  waiting for an external controller to expand this PVC`에서 멈췄다. 실제 클러스터에서 이 상태가 오래가면 드라이버와 권한을 본다.

줄이는 것은 안 된다. 파일 시스템을 안전하게 줄일 방법이 없기 때문이다. 더 작은 디스크가 필요하면 새 PVC를 만들어 데이터를 옮긴다. EBS에는 한 번 크기를 바꾸면 6시간이 지나야 다시 바꿀 수 있다는 제한도 있다. 디스크가 꽉 차는 장애에서 조금만 늘리면 몇 시간 동안 더 못 늘리니, 늘릴 때는 넉넉하게 늘린다.

## StatefulSet은 Pod마다 PVC를 만든다

Deployment의 레플리카는 같은 템플릿을 공유하니, PVC를 하나 적으면 모든 Pod가 같은 PVC를 쓴다. RWO 디스크라면 다른 노드의 Pod는 붙이지 못한다. Pod마다 자기 디스크가 필요한 DB나 메시지 브로커는 StatefulSet의 `volumeClaimTemplates`를 쓴다. Deployment가 Pod를 다루는 방식은 [Deployment 글](/posts/k8s-deployment)에서 본다.

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
  namespace: shop
spec:
  serviceName: db
  replicas: 2
  selector:
    matchLabels: {app: db}
  template:
    metadata:
      labels: {app: db}
    spec:
      containers:
        - name: postgres
          image: postgres:16
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:          # Pod마다 이 틀로 PVC를 하나씩 만든다
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: gp3
        resources:
          requests:
            storage: 20Gi
```

```bash
# StatefulSet을 만들고 Pod와 PVC를 본다
kubectl apply -f sts.yaml
kubectl get pod,pvc -n shop -l app=db

# StatefulSet을 지운 뒤 PVC가 남는지 본다
kubectl delete statefulset db -n shop
kubectl get pvc data-db-0 -n shop
```

```text
statefulset.apps/db created
NAME       READY   STATUS    RESTARTS   AGE
pod/db-0   0/1     Pending   0          6s

NAME                              STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
persistentvolumeclaim/data-db-0   Pending                                      gp3            <unset>                 6s
statefulset.apps "db" deleted
NAME        STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
data-db-0   Pending                                      gp3            <unset>                 9s
```

PVC 이름은 `템플릿 이름-Pod 이름`, 즉 `data-db-0`이다. 레플리카가 2인데 `db-1`과 `data-db-1`이 없는 건 StatefulSet이 기본으로 순서대로 띄우기 때문이다. `db-0`이 Ready가 되기 전에는 `db-1`을 만들지 않는다. 실습 클러스터에는 프로비저너가 없으니 `db-0`이 계속 Pending이다.

StatefulSet을 지워도 PVC는 남는다. 같은 이름으로 다시 만들면 `db-0`은 `data-db-0`을 그대로 다시 붙여 데이터를 이어 쓴다. 규모를 줄일 때도 PVC는 남는다. 지우는 시점을 정하고 싶으면 `persistentVolumeClaimRetentionPolicy`(1.32부터 정식)의 `whenDeleted`, `whenScaled`를 `Delete`로 둔다. 기본값은 둘 다 `Retain`이다.

## 현장에서 볼륨 때문에 Pod가 안 뜰 때

볼륨 문제는 대개 Pod가 Pending이나 ContainerCreating에 머무는 모습으로 나타난다. 어느 단계에서 막혔는지에 따라 보는 곳이 다르다. PVC가 Pending이면 `kubectl describe pvc`의 이벤트를 본다. 앞에서 본 `ExternalProvisioning`이 길게 이어지면 CSI 드라이버, `no persistent volumes available`이면 StorageClass 설정이다. PVC는 Bound인데 Pod가 Pending이면 `kubectl describe pod`에서 `volume node affinity conflict`를 찾는다.

PVC도 Bound이고 노드도 정해졌는데 ContainerCreating에서 멈추는 경우가 운영에서 가장 흔하다. 대표가 Deployment 롤링 업데이트와 RWO 디스크의 조합이다.

## Pod보다 오래 사는 데이터

PVC는 "이런 디스크가 필요하다"는 요청이고, PV는 실제 디스크 하나이며, StorageClass는 디스크를 만드는 틀이다. 정적 PV는 조건이 맞는 가장 작은 것에 묶이고, 동적 프로비저닝은 `WaitForFirstConsumer`로 노드가 정해진 뒤 그 존에 디스크를 만든다. 디스크가 존에 묶이니 노드 그룹도 존을 생각해서 짜야 한다. 동적 PV의 기본 회수 정책은 Delete이고, Retain이어도 같은 이름의 새 PVC가 옛 디스크를 찾아가지 않는다. 설정과 비밀 값을 넣는 방법은 [ConfigMap](/posts/k8s-configmap)과 [Secret](/posts/k8s-secret) 글에서 봤다.

## 면접에서 나올 만한 질문

### PV, PVC, StorageClass는 각각 무엇인가요?

PVC는 사용자가 크기와 접근 모드로 디스크를 요청하는 네임스페이스 객체이고, PV는 실제 디스크 하나를 나타내는 클러스터 단위 객체다. 둘은 일대일로 묶인다. StorageClass는 어떤 프로비저너가 어떤 설정으로 디스크를 만들지 정한 틀이라, PVC가 들어오면 PV와 디스크를 자동으로 만든다. 이렇게 나눠서 앱 매니페스트가 스토리지 종류와 무관해진다.

### ReadWriteOnce는 Pod 하나만 쓸 수 있다는 뜻인가요?

아니다. 노드 하나에 붙일 수 있다는 뜻이라 같은 노드의 Pod 여럿이 함께 쓸 수 있다. 클러스터에서 Pod 하나만 쓰게 하려면 ReadWriteOncePod를 쓴다(1.29 정식, CSI 전용). 여러 노드에서 쓰려면 RWX를 지원하는 EFS나 NFS 같은 스토리지가 필요하다.

### volumeBindingMode WaitForFirstConsumer는 왜 쓰나요?

EBS 같은 블록 디스크는 존 하나에 묶이기 때문이다. Immediate면 Pod가 어디 갈지 모르는 채 디스크를 만들어 엉뚱한 존에 생길 수 있다. WaitForFirstConsumer는 스케줄러가 노드를 고른 뒤 그 노드의 존에 디스크를 만들어서 Pod가 디스크에 닿지 못하는 일을 막는다.

### PVC를 지웠다가 같은 이름으로 다시 만들면 데이터가 돌아오나요?

돌아오지 않는다. 회수 정책이 Delete면 디스크가 이미 지워졌다. Retain이어도 PV는 Released 상태이고 claimRef에 옛 PVC의 uid가 남아 있어 새 PVC와 묶이지 않는다. 새 PVC는 다른 빈 PV나 새 디스크에 묶인다. 되찾으려면 PV의 claimRef를 지우고 새 PVC에 volumeName으로 그 PV를 지정한다.

### Pod가 volume node affinity conflict로 Pending입니다. 어떻게 하나요?

PV가 묶인 존에 Pod를 받을 수 있는 노드가 없다는 뜻이다. 그 존의 노드가 cordon됐거나 자원이 모자란지 보고, 그 존에 노드를 추가한다. 오토스케일러가 존을 골라 띄울 수 있도록 노드 그룹을 존마다 나누는 것이 근본 대책이다. 존 장애를 견뎌야 하면 앱 수준 복제나 여러 존에서 붙는 스토리지를 쓴다.

### Deployment 롤링 업데이트 중 새 Pod가 Multi-Attach error로 멈춥니다. 왜 그런가요?

RWO 디스크가 옛 Pod의 노드에 붙어 있는데 새 Pod가 다른 노드에 배정됐기 때문이다. 롤링 업데이트는 새 Pod가 Ready가 돼야 옛 Pod를 내리니 서로 기다린다. 디스크 하나를 쓰는 Deployment는 strategy를 Recreate로 바꾸거나 StatefulSet으로 옮긴다.

### PVC 용량을 늘리거나 줄일 수 있나요?

StorageClass에 allowVolumeExpansion이 true이고 동적으로 만든 PVC라면 requests.storage를 늘려 키울 수 있다. CSI 드라이버가 디스크와 파일 시스템을 늘려야 status.capacity가 바뀐다. 줄이는 것은 거절되므로 새 PVC를 만들어 데이터를 옮긴다. EBS는 크기를 바꾼 뒤 6시간 동안 다시 바꿀 수 없으니 넉넉하게 늘린다.
