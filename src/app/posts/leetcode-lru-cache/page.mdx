캐시는 자리가 한정되어 있다. 가득 찼는데 새 값이 들어오면 뭔가를 버려야 한다. 가장 많이 쓰는 규칙이 "가장 오래 안 쓴 것부터 버린다"이고, 이걸 LRU(Least Recently Used)라고 부른다. 규칙은 한 줄인데, 읽기와 쓰기를 모두 O(1)에 하라는 조건이 붙으면 자료구조 두 개를 엮어야 한다.

[LeetCode 146. LRU Cache](https://leetcode.com/problems/lru-cache/)가 그 설계 문제다. 마지막 사용 시각을 적어 두고 버릴 때 훑는 풀이, 배열에 줄 세우기, 기록을 쌓아 두고 나중에 걸러 내기, 순서를 기억하는 언어 내장 맵을 빌려 쓰기, 그리고 해시맵과 이중 연결 리스트를 엮는 풀이까지 다섯 가지를 따라간다. 이중 연결 리스트의 기본 동작은 [연결 리스트](/posts/ds-linked-list) 글에서 다뤘고, 캐시에서 무엇을 언제 버리는지 같은 운영 이야기는 [캐시 개념 지도](/posts/caching-concepts-map)와 [Redis 메모리 축출 정책](/posts/redis-memory-eviction)에 있다. 이 글은 자료구조를 짜는 쪽에 집중한다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 가장 오래 안 쓴 것부터 버리는 상자

용량 `capacity`가 정해진 캐시 클래스를 만든다. 연산은 두 개다.

- `get(key)`: 키가 있으면 값을, 없으면 `-1`을 돌려준다.
- `put(key, value)`: 키가 있으면 값을 바꾸고, 없으면 새로 넣는다. 넣어서 용량을 넘으면 가장 오래 안 쓴 키를 하나 버린다.

`get`으로 읽는 것도 "쓴 것"이고, `put`으로 값을 바꾸는 것도 "쓴 것"이다. 두 연산 모두 평균 O(1)이어야 한다.

용량은 1에서 3000, 키는 0에서 10^4, 호출은 최대 2×10^5번이다. 연산마다 캐시 전체를 훑으면 3000 × 2×10^5 = 6×10^8번이라 느리다. 그리고 문제 문장이 O(1)을 요구하니, 면접에서도 이 조건을 맞추는 게 목표다.

## 용량 2짜리 캐시를 손으로 굴려 보면

이 글에서 계속 쓸 연산 순서다. 용량은 2다. 오른쪽 칸은 연산이 끝난 뒤 키를 최근에 쓴 순서로 적은 것이다. 왼쪽이 가장 최근, 오른쪽이 가장 오래된 쪽이다.

```text
연산         결과    쓴 순서 (최근 → 오래됨)
put(1, 10)           1
put(2, 20)           2  1
get(1)       10      1  2          ← 1을 읽었으니 1이 가장 최근
put(3, 30)           3  1          ← 가득 찼다. 가장 오래된 2를 버린다
get(2)       -1      3  1          ← 2는 이미 버렸다
put(1, 15)           1  3          ← 1의 값을 15로 바꾸고 맨 앞으로
put(4, 40)           4  1          ← 3을 버린다
get(3)       -1      4  1
get(1)       15      1  4
get(4)       40      4  1
```

손으로 해 보면 필요한 연산이 셋으로 정리된다.

1. 키로 값을 찾는다. `get`과 `put` 모두 이걸 먼저 한다.
2. 어떤 키를 "가장 최근"으로 옮긴다. 쓸 때마다 한다.
3. 가장 오래된 키를 찾아서 버린다. 넘칠 때만 한다.

1번은 해시맵이 O(1)에 해 준다. 어려운 건 2번과 3번을 함께 O(1)로 하는 것이다. 순서를 어딘가에 들고 있어야 하는데, 그 순서 안의 아무 키나 꺼내서 맨 앞으로 옮기는 일이 빨라야 한다. 풀이들은 이 "순서"를 어떻게 들고 있느냐가 다르다.

## 마지막으로 쓴 시각을 적어 두기

순서를 따로 들지 않고, 키마다 마지막으로 쓴 시각을 적어 둔다. 시각은 연산마다 1씩 느는 정수면 된다. 쓸 때마다 시각을 갱신하면 2번이 O(1)이 된다. 버릴 때는 전체를 훑어 시각이 가장 작은 키를 찾는다.

```js
class LRUCache {
  constructor(capacity) {
    this.cap = capacity;
    this.map = new Map(); // key → { value, used }
    this.time = 0;
  }
  get(key) {
    const e = this.map.get(key);
    if (!e) return -1;
    e.used = ++this.time;          // 쓴 시각만 갱신한다
    return e.value;
  }
  put(key, value) {
    if (this.map.has(key)) {
      const e = this.map.get(key);
      e.value = value;
      e.used = ++this.time;
      return;
    }
    if (this.map.size === this.cap) {
      // 시각이 가장 작은 키를 찾아 버린다: O(capacity)
      let oldKey, oldUsed = Infinity;
      for (const [k, e] of this.map) if (e.used < oldUsed) { oldUsed = e.used; oldKey = k; }
      this.map.delete(oldKey);
    }
    this.map.set(key, { value, used: ++this.time });
  }
}
```

`get`은 O(1), `put`도 넘치지 않으면 O(1)인데, 넘칠 때 O(capacity)다. 용량 3000에 연산 20만 번, 키를 0~10000에서 무작위로 고르게 돌려 보니 약 5초가 걸렸다. 키가 용량보다 훨씬 많아서 `put`마다 거의 매번 버리기가 일어나기 때문이다. 3번을 빠르게 하려면 시각이 가장 작은 키를 바로 알아야 한다. 순서를 들고 있어야 한다는 뜻이다.

## 쓴 순서대로 배열에 줄 세우기

키를 쓴 순서대로 배열에 줄 세운다. 맨 뒤가 가장 최근, 맨 앞이 가장 오래된 키다. 버릴 때는 맨 앞을 빼면 된다. 쓸 때는 배열에서 그 키를 찾아 빼고 맨 뒤에 다시 넣는다.

```js
class LRUCache {
  constructor(capacity) {
    this.cap = capacity;
    this.keys = [];        // 쓴 순서. 앞이 오래됨, 뒤가 최근
    this.vals = new Map();
  }
  touch(key) {
    const i = this.keys.indexOf(key); // O(capacity)로 찾는다
    this.keys.splice(i, 1);           // O(capacity)로 당긴다
    this.keys.push(key);
  }
  get(key) {
    if (!this.vals.has(key)) return -1;
    this.touch(key);
    return this.vals.get(key);
  }
  put(key, value) {
    if (this.vals.has(key)) { this.vals.set(key, value); this.touch(key); return; }
    if (this.keys.length === this.cap) this.vals.delete(this.keys.shift()); // 맨 앞을 버린다
    this.keys.push(key);
    this.vals.set(key, value);
  }
}
```

이번에는 버리기가 쉬워진 대신 쓰기가 느려졌다. `indexOf`로 찾는 데 O(capacity), `splice`로 뒤를 당기는 데 O(capacity), `shift`도 앞을 빼고 나머지를 당겨서 O(capacity)다. 같은 조건에서 약 360ms였다. 시각 풀이보다 훨씬 빠른 건 `indexOf`와 `splice`가 메모리를 붙어서 훑는 빠른 내장 연산이어서다. 그래도 연산마다 O(capacity)가 드는 건 같다.

배열의 약점은 두 가지다. 키가 배열의 어디에 있는지 모른다. 그리고 안다고 해도 중간을 빼면 뒤를 당겨야 한다. 이 두 약점을 각각 해시맵과 연결 리스트가 없앤다. 그게 마지막 풀이다. 그 전에 다른 길 두 개를 먼저 본다.

## 기록을 쌓아 두고 나중에 걸러 내기

순서 안의 키를 꺼내 옮기는 게 어렵다면, 꺼내지 않는 방법이 있다. 쓸 때마다 `(키, 시각)` 기록을 큐 뒤에 새로 붙이기만 한다. 옛 기록은 그대로 둔다. 버릴 때는 큐 앞에서 기록을 하나씩 꺼내는데, 그 기록의 시각이 그 키의 지금 시각과 같을 때만 진짜다. 다르면 그 뒤에 다시 쓴 적이 있다는 뜻이니 버리고 다음 기록을 본다.

```js
class LRUCache {
  constructor(capacity) {
    this.cap = capacity;
    this.map = new Map(); // key → { value, used }
    this.q = [];          // [key, used] 기록. 앞이 오래된 기록
    this.head = 0;        // 큐의 앞. shift 대신 인덱스로 뺀다
    this.time = 0;
  }
  get(key) {
    const e = this.map.get(key);
    if (!e) return -1;
    e.used = ++this.time;
    this.q.push([key, e.used]);       // 새 기록만 붙인다
    return e.value;
  }
  put(key, value) {
    const e = this.map.get(key);
    if (e) { e.value = value; e.used = ++this.time; this.q.push([key, e.used]); return; }
    if (this.map.size === this.cap) {
      while (true) {
        const [k, t] = this.q[this.head++];
        const cur = this.map.get(k);
        if (cur && cur.used === t) { this.map.delete(k); break; } // 최신 기록이면 진짜 가장 오래된 키
      }                                                            // 아니면 옛 기록이라 건너뛴다
    }
    const used = ++this.time;
    this.map.set(key, { value, used });
    this.q.push([key, used]);
    // 앞쪽에 버린 칸이 많아지면 배열을 잘라 메모리를 돌려받는다
    if (this.head > 1024 && this.head * 2 > this.q.length) { this.q = this.q.slice(this.head); this.head = 0; }
  }
}
```

기록 하나는 한 번 붙고 많아야 한 번 꺼내진다. 그래서 연산 하나가 오래 돌 때는 있어도, 전체로 나누면 연산당 O(1)이다. 이런 걸 상각(amortized) O(1)이라고 한다. 같은 조건에서 약 100ms였다. 대신 메모리가 키 수가 아니라 연산 수에 비례해 늘 수 있다. 같은 키를 계속 `get`하면 버리기가 일어나지 않는 동안 기록이 계속 쌓인다. 앞쪽을 잘라 내는 정리가 있어도 큐 길이는 용량보다 훨씬 클 수 있다. 문제 조건의 "O(1)"을 엄격히 연산마다로 읽으면 이 풀이는 조건을 맞추지 못한다.

## 넣은 순서를 기억하는 Map을 빌려 쓰기

자바스크립트 `Map`은 키를 넣은 순서대로 순회한다. 키를 지우고 다시 넣으면 맨 뒤로 간다. 그러니 `Map` 하나가 해시맵과 순서를 함께 들고 있는 셈이다. `map.keys().next().value`가 가장 먼저 넣은 키, 곧 가장 오래된 키다.

```js
class LRUCache {
  constructor(capacity) {
    this.cap = capacity;
    this.map = new Map(); // 넣은 순서가 곧 쓴 순서. 앞이 오래됨
  }
  get(key) {
    if (!this.map.has(key)) return -1;
    const v = this.map.get(key);
    this.map.delete(key);   // 지우고
    this.map.set(key, v);   // 다시 넣으면 맨 뒤로 간다
    return v;
  }
  put(key, value) {
    if (this.map.has(key)) this.map.delete(key);           // 순서를 갱신하려면 먼저 지운다
    else if (this.map.size === this.cap) this.map.delete(this.map.keys().next().value); // 맨 앞을 버린다
    this.map.set(key, value);
  }
}
```

코드가 가장 짧고 모든 연산이 평균 O(1)이다. 실무에서 자바스크립트로 작은 LRU가 필요하면 이걸 쓰는 경우가 많다. 다만 같은 조건에서 직접 재 보니 약 290ms로, 뒤에 나올 연결 리스트 풀이(약 50ms)보다 느렸다. 지우고 다시 넣는 일이 연산마다 일어나는 패턴이라 `Map` 내부를 정리하는 비용이 드는 것으로 보인다. 엔진 구현에 따라 다를 수 있는 숫자라 "더 느리다"보다 "공짜는 아니다" 정도로 받아들이면 된다.

`put`에서 키가 이미 있을 때 `delete`를 먼저 하는 게 중요하다. `Map.set`은 이미 있는 키의 값만 바꾸고 순서는 그대로 둔다. `new Map([[1,"a"],[2,"b"]])`에 `set(1,"c")`를 해도 순서는 `[1, 2]`다. 뒤의 "틀리는 자리"에서 이 실수를 실제로 돌려 본다.

다른 언어에도 같은 도구가 있다. Python은 `collections.OrderedDict`의 `move_to_end`와 `popitem(last=False)`를 쓴다.

```python
from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity: int):
        self.cap = capacity
        self.data = OrderedDict()
    def get(self, key: int) -> int:
        if key not in self.data:
            return -1
        self.data.move_to_end(key)             # 맨 뒤가 가장 최근
        return self.data[key]
    def put(self, key: int, value: int) -> None:
        if key in self.data:
            self.data.move_to_end(key)
        self.data[key] = value
        if len(self.data) > self.cap:
            self.data.popitem(last=False)      # 맨 앞(가장 오래된 것)을 뺀다
```

Java는 `LinkedHashMap`을 접근 순서 모드로 만들고 `removeEldestEntry`를 덮어쓴다. 생성자 세 번째 인자 `true`가 "넣은 순서" 대신 "접근한 순서"로 줄 세우라는 뜻이다.

```java
class LRUCache extends LinkedHashMap<Integer, Integer> {
    private final int cap;
    LRUCache(int capacity) {
        super(16, 0.75f, true);        // 세 번째 인자 true: 접근 순서로 줄 세운다
        cap = capacity;
    }
    public int get(int key) { return super.getOrDefault(key, -1); }
    public void put(int key, int value) { super.put(key, value); }
    @Override
    protected boolean removeEldestEntry(Map.Entry<Integer, Integer> eldest) {
        return size() > cap;           // 넣은 뒤 넘치면 가장 오래된 항목을 뺀다
    }
}
```

세 언어 모두 앞의 연산 순서에서 `[null, null, null, 10, null, -1, null, null, -1, 15, 40]`이 나왔다. 면접에서 이 답을 내면 대개 "내장 자료구조 없이 직접 만들어 보라"는 말이 돌아온다. `OrderedDict`와 `LinkedHashMap`이 안에서 바로 다음 풀이의 구조, 해시맵과 이중 연결 리스트를 쓰고 있기 때문이다.

## 해시맵이 노드를 가리키고, 노드가 줄을 선다

배열 풀이의 약점 두 개를 다시 보자. 키가 순서의 어디에 있는지 몰랐고, 중간을 빼면 뒤를 당겨야 했다. 각각을 이렇게 없앤다.

- 순서를 이중 연결 리스트로 든다. 노드 하나를 빼려면 앞 노드와 뒤 노드를 서로 이어 주기만 하면 된다. 당길 것이 없다. 단일 연결 리스트는 앞 노드를 모르니 안 되고, 앞뒤 화살표가 모두 있어야 O(1)이다.
- 해시맵의 값으로 값 대신 그 키의 노드를 둔다. 키를 받으면 노드로 바로 가니, 순서의 어디에 있는지 찾을 필요가 없다.

리스트 양 끝에는 값이 없는 보초(sentinel) 노드 `head`와 `tail`을 둔다. 진짜 노드는 언제나 두 보초 사이에 있으니, 리스트가 비었는지, 맨 앞이나 맨 뒤 노드를 빼는지를 따로 따지지 않아도 된다. `head.next`가 가장 최근, `tail.prev`가 가장 오래된 노드다. 노드에는 값과 함께 키도 넣어 둔다. 버릴 노드를 `tail.prev`로 찾은 다음 해시맵에서도 지워야 하는데, 그때 키가 필요하다.

이제 필요한 연산 셋이 모두 O(1)이다. 찾기는 해시맵, 맨 앞으로 옮기기는 "빼고 `head` 뒤에 붙이기", 버리기는 "`tail.prev`를 빼고 해시맵에서 지우기"다. 리스트 연산은 두 개만 있으면 된다.

```js
class Node {
  constructor(key, value) {
    this.key = key;      // 버릴 때 해시맵에서 지우려고 키도 둔다
    this.value = value;
    this.prev = null;
    this.next = null;
  }
}

class LRUCache {
  constructor(capacity) {
    this.cap = capacity;
    this.map = new Map();         // key → Node
    this.head = new Node(0, 0);   // head.next가 가장 최근
    this.tail = new Node(0, 0);   // tail.prev가 가장 오래됨
    this.head.next = this.tail;
    this.tail.prev = this.head;
  }
  // 노드를 리스트에서 뺀다: 앞뒤를 서로 잇는다
  remove(node) {
    node.prev.next = node.next;
    node.next.prev = node.prev;
  }
  // 노드를 head 바로 뒤(가장 최근 자리)에 붙인다
  addFront(node) {
    node.prev = this.head;
    node.next = this.head.next;
    this.head.next.prev = node;
    this.head.next = node;
  }
  get(key) {
    const node = this.map.get(key);
    if (!node) return -1;
    this.remove(node);            // 쓴 노드는 맨 앞으로
    this.addFront(node);
    return node.value;
  }
  put(key, value) {
    const node = this.map.get(key);
    if (node) {                   // 이미 있으면 값만 바꾸고 맨 앞으로
      node.value = value;
      this.remove(node);
      this.addFront(node);
      return;
    }
    if (this.map.size === this.cap) {
      const lru = this.tail.prev; // 가장 오래된 노드
      this.remove(lru);
      this.map.delete(lru.key);   // 노드에 key를 둔 이유
    }
    const fresh = new Node(key, value);
    this.addFront(fresh);
    this.map.set(key, fresh);
  }
}
```

`addFront`에서 화살표 네 개를 바꾸는 순서를 보자. 새 노드의 `prev`와 `next`를 먼저 정하고, 그다음 원래 맨 앞 노드(`head.next`)의 `prev`를 새 노드로 바꾸고, 마지막에 `head.next`를 바꾼다. `head.next`를 먼저 바꾸면 원래 맨 앞 노드를 잃는다. [Reverse Linked List](/posts/leetcode-reverse-linked-list)의 "끊기 전에 붙잡는다"와 같은 규칙이다.

아래 그림은 손으로 굴렸던 연산 순서를 이 코드로 따라간 것이다. 칸은 연산이고, 화살표 표시가 지금 연산이다. 오른쪽 칸에 `head`부터 `tail`까지 리스트를 적었다.

### Python과 Java로 쓰면

Python은 노드가 많을 때 `__slots__`를 주면 노드마다 붙는 딕셔너리가 없어져 메모리를 아낀다. 여러 대입을 한 줄에 쓰는 문법(`a, b = x, y`)은 오른쪽을 모두 계산한 뒤 왼쪽에 대입하니, 화살표 두 개를 동시에 바꿀 때 편하다.

```python
class Node:
    __slots__ = ("key", "value", "prev", "next")
    def __init__(self, key=0, value=0):
        self.key, self.value = key, value
        self.prev = self.next = None

class LRUCache:
    def __init__(self, capacity: int):
        self.cap = capacity
        self.map = {}                          # key → Node
        self.head, self.tail = Node(), Node()  # 보초: head.next가 가장 최근, tail.prev가 가장 오래됨
        self.head.next, self.tail.prev = self.tail, self.head

    def _remove(self, node):
        node.prev.next, node.next.prev = node.next, node.prev

    def _add_front(self, node):
        node.prev, node.next = self.head, self.head.next
        self.head.next.prev = node
        self.head.next = node

    def get(self, key: int) -> int:
        node = self.map.get(key)
        if node is None:
            return -1
        self._remove(node)
        self._add_front(node)                  # 쓴 노드는 맨 앞으로
        return node.value

    def put(self, key: int, value: int) -> None:
        node = self.map.get(key)
        if node:
            node.value = value
            self._remove(node)
            self._add_front(node)
            return
        if len(self.map) == self.cap:
            lru = self.tail.prev               # 가장 오래된 노드
            self._remove(lru)
            del self.map[lru.key]              # 노드에 key를 둔 이유
        node = Node(key, value)
        self._add_front(node)
        self.map[key] = node
```

Java는 노드를 `private static class`로 안에 숨긴다. 키가 `int`라 `HashMap<Integer, Node>`에서 박싱(int를 Integer 객체로 감싸기)이 일어나지만, 키 범위가 0~10^4라 `Node[] byKey = new Node[10001]` 배열로 바꾸면 박싱 없이 더 빠르다. 키 범위가 좁을 때만 쓸 수 있는 방법이다.

```java
class LRUCache {
    private static class Node {
        int key, value;
        Node prev, next;
        Node(int key, int value) { this.key = key; this.value = value; }
    }
    private final int cap;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0), tail = new Node(0, 0);  // 보초 노드

    public LRUCache(int capacity) {
        cap = capacity;
        head.next = tail;
        tail.prev = head;
    }
    private void remove(Node n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private void addFront(Node n) {
        n.prev = head; n.next = head.next;
        head.next.prev = n; head.next = n;
    }
    public int get(int key) {
        Node n = map.get(key);
        if (n == null) return -1;
        remove(n); addFront(n);
        return n.value;
    }
    public void put(int key, int value) {
        Node n = map.get(key);
        if (n != null) { n.value = value; remove(n); addFront(n); return; }
        if (map.size() == cap) {
            Node lru = tail.prev;
            remove(lru);
            map.remove(lru.key);
        }
        n = new Node(key, value);
        addFront(n);
        map.put(key, n);
    }
}
```

세 언어 모두 같은 연산 순서에서 `[null, null, null, 10, null, -1, null, null, -1, 15, 40]`이 나왔다. 다섯 풀이를 무작위 연산 6만 번(용량 1~5, 키 0~7)으로 서로 맞춰 보는 검사도 모두 통과했다.

## 캐시가 기억을 잘못하는 순간

LRU 구현의 오답은 대부분 "출력은 그럴듯한데 순서가 틀린" 경우다. 직접 돌려 본 틀린 코드 네 개다.

### 버린 노드를 Map에서 지우지 않으면

```js
if (this.map.size === this.cap) {
  const lru = this.tail.prev;
  this.remove(lru);   // 리스트에서만 뺐다. this.map.delete(lru.key)가 없다
}
```

```text
용량 2: put(1,10) put(2,20) put(3,30) get(1) get(3)
결과:   [null, null, null, null, 10, 30]     (get(1)은 -1이어야 한다)
```

리스트에서는 빠졌지만 해시맵이 아직 1의 노드를 들고 있어서 `get(1)`이 버린 값을 돌려준다. 해시맵 크기가 줄지 않으니 다음부터는 `put`마다 버리기가 일어나고, 메모리도 계속 는다. 노드에 키를 넣어 두는 이유가 이 `map.delete(lru.key)` 한 줄이다.

### 값을 바꾸고 순서를 그대로 두면

```js
if (node) { node.value = value; return; }   // 맨 앞으로 옮기지 않았다
```

```text
용량 2: put(1,10) put(2,20) put(1,11) put(3,30) get(1) get(2)
결과:   [… , -1, 20]      정답: [… , 11, -1]
```

`put(1, 11)`도 1을 쓴 것이다. 순서를 옮기지 않으면 1이 여전히 가장 오래된 키로 남아 `put(3, 30)`에서 1이 버려진다. 문제 문장에서 `put`이 사용으로 치는지 놓치기 쉽다. 자바스크립트 `Map` 풀이에서 `put`할 때 `delete`를 빼먹어도 정확히 같은 결과가 나온다. `Map.set`은 있는 키의 순서를 바꾸지 않기 때문이다.

### 키가 있는지 보기 전에 버리면

```js
put(key, value) {
  if (this.map.size === this.cap) { /* tail.prev를 버린다 */ }
  // 그다음에 key가 있는지 본다
}
```

```text
용량 2: put(1,10) put(2,20) put(2,25) get(1) get(2)
결과:   [… , -1, 25]      정답: [… , 10, 25]
```

가득 찬 상태에서 이미 있는 키 2의 값을 바꿨을 뿐인데 1이 버려졌다. 새 키가 들어오는 게 아니면 크기가 늘지 않으니 버릴 필요가 없다. 있는 키인지 먼저 보고, 새 키일 때만 넘치는지 따진다.

### 화살표를 바꾸는 순서가 틀리면

```js
addFront(node) {
  this.head.next = node;          // head.next를 먼저 바꿔 버렸다
  node.prev = this.head;
  node.next = this.head.next;     // 이미 node 자신이다
  this.head.next.prev = node;     // node.prev도 node 자신이 된다
}
```

```text
용량 3: put(1,1) put(2,2) 뒤 head부터 걸으면  →  H 2 2 2 2 2 2 2 …
```

`head.next`를 먼저 바꾸면 원래 맨 앞 노드를 잃는다. 그 뒤의 `this.head.next`는 모두 새 노드를 가리키니, 새 노드의 `next`와 `prev`가 둘 다 자기 자신이 된다. 리스트를 앞에서 걸으면 2에서 끝없이 돌고, 1은 리스트에서 사라진다. 화살표 네 개는 "새 노드의 두 화살표 → 옆 노드의 `prev` → `head.next`" 순서로 바꾼다. 헷갈리면 보초 둘만 있는 빈 리스트에 노드 하나를 넣는 그림을 그려 본다.

## 실제 캐시는 정확한 LRU를 잘 안 쓴다

### 키가 수천만 개라면

이 글의 구조는 키마다 앞뒤 포인터 두 개를 붙이고, 읽을 때마다 리스트를 고친다. 키가 수천만 개인 Redis는 그 비용이 아까워서 정확한 LRU 대신 근사 LRU를 쓴다. 키마다 마지막 접근 시각만 적어 두고, 버릴 때 키 몇 개를 무작위로 뽑아 그중 가장 오래된 것을 버린다. 이 글의 첫 풀이, "시각을 적고 버릴 때 훑기"에서 훑는 범위를 표본으로 줄인 것이다. 표본 크기와 후보 풀 이야기는 [Redis 메모리 축출 정책](/posts/redis-memory-eviction)에 있다.

### 운영체제의 페이지 교체라면

운영체제가 메모리 페이지를 내쫓을 때도 정확한 LRU는 너무 비싸다. 메모리를 읽을 때마다 리스트를 고칠 수는 없어서, 하드웨어가 페이지를 쓸 때 켜 주는 참조 비트 하나만 보고 시계 바늘처럼 돌며 비트가 꺼진 페이지를 고르는 CLOCK 계열 알고리즘을 쓴다. 리눅스는 활성·비활성 두 목록으로 이를 다듬는다. 페이지와 메모리 부족 상황은 [가상 메모리와 페이징](/posts/virtual-memory-paging)에서 다뤘다.

### 가장 적게 쓴 것을 버리라면

LeetCode 460 LFU Cache는 사용 횟수가 가장 적은 키를 버리고, 횟수가 같으면 그중 가장 오래 안 쓴 키를 버린다. 키 → 노드 해시맵에 더해 "횟수 → 그 횟수의 LRU 리스트" 해시맵을 두고, 지금 가장 작은 횟수 `minFreq`를 들고 다닌다. 쓸 때마다 노드를 횟수 f의 리스트에서 f+1의 리스트로 옮긴다. 이 글의 이중 연결 리스트가 횟수마다 하나씩 생기는 구조다.

### 여러 스레드가 함께 쓴다면

`get`도 리스트를 고치는 쓰기 연산이라, 읽기만 하는 줄 알고 잠금 없이 두면 화살표가 꼬인다. 가장 단순한 방법은 연산 전체를 잠금 하나로 감싸는 것이고, 경합이 심하면 키를 해시로 나눠 조각마다 따로 LRU와 잠금을 두는 방법을 쓴다. 이때는 조각 안에서만 LRU라서 전체로는 근사가 된다. Java라면 `Collections.synchronizedMap(new LinkedHashMap<>(…, true))`가 첫 번째 방법이다.

### 항목마다 크기나 만료 시간이 다르다면

용량을 개수가 아니라 바이트로 잡으면, 하나를 넣을 때 여러 개를 버려야 할 수 있다. `tail.prev`를 하나씩 빼며 합계가 한도 아래로 내려갈 때까지 반복한다. 만료 시간(TTL)이 있으면 `get`에서 만료를 확인해 지우는 게으른 삭제를 기본으로 하고, 만료된 항목이 메모리를 오래 차지하지 않게 주기적으로 일부를 훑는다.

## 찾기는 해시맵, 순서는 연결 리스트

LRU 캐시는 "키로 찾기", "쓴 키를 가장 최근으로 옮기기", "가장 오래된 키 버리기"를 모두 O(1)에 해야 한다. 해시맵만으로는 순서를, 배열만으로는 중간 옮기기를 빠르게 할 수 없어서 둘을 엮는다. 해시맵이 키로 노드를 가리키고, 노드들은 보초가 양 끝을 지키는 이중 연결 리스트로 줄을 선다. 쓴 노드는 빼서 `head` 뒤에 붙이고, 넘치면 `tail.prev`를 빼면서 해시맵에서도 그 키를 지운다. `put`으로 값을 바꾸는 것도 사용이라는 것, 새 키일 때만 버린다는 것을 지키면 된다.

## 면접에서 나올 만한 질문

### get과 put을 모두 O(1)로 하려면 어떤 자료구조가 필요한가요?

해시맵과 이중 연결 리스트를 함께 쓴다. 해시맵은 키에서 노드로 바로 가게 해 주고, 이중 연결 리스트는 쓴 순서를 들고 아무 노드나 O(1)에 빼고 붙이게 해 준다. 쓴 노드는 맨 앞으로 옮기고, 용량을 넘으면 맨 뒤 노드를 버린다.

### 왜 단일 연결 리스트로는 안 되나요?

노드를 빼려면 그 앞 노드의 `next`를 고쳐야 하는데, 단일 연결 리스트에서는 앞 노드를 찾으려면 머리부터 걸어야 해서 O(n)이 된다. 이중 연결 리스트는 노드가 `prev`를 들고 있어서 앞 노드로 바로 간다. 맨 뒤 노드를 버릴 때도 `tail.prev`로 바로 찾는다.

### 노드에 값뿐 아니라 키도 저장하는 이유는 무엇인가요?

버릴 때 필요하다. 가장 오래된 노드는 리스트의 `tail.prev`로 찾는데, 그 노드를 해시맵에서도 지우려면 키를 알아야 한다. 키가 없으면 해시맵에 버린 노드가 남아서 `get`이 버린 값을 돌려주고 메모리도 계속 는다.

### 보초 노드는 왜 쓰나요?

빈 리스트, 맨 앞 노드 빼기, 맨 뒤 노드 빼기 같은 경계 경우를 없애려고 쓴다. 진짜 노드는 언제나 `head`와 `tail` 사이에 있으니 `prev`와 `next`가 `null`일 일이 없다. 그래서 빼기와 붙이기를 각각 분기 없는 두세 줄로 쓸 수 있다.

### 자바스크립트 Map이나 LinkedHashMap을 쓰면 안 되나요?

실무에서는 좋은 선택이다. 자바스크립트 `Map`은 넣은 순서를 기억해서 지우고 다시 넣으면 맨 뒤로 가고, Java는 `LinkedHashMap`을 접근 순서 모드로 만들고 `removeEldestEntry`를 덮어쓰면 된다. 면접에서는 그 안의 구조를 직접 만들 수 있는지 보려는 경우가 많아서, 내장 도구를 언급한 뒤 직접 구현을 보여 주는 편이 좋다. `Map.set`이 있는 키의 순서를 바꾸지 않는다는 점은 꼭 짚는다.

### put으로 이미 있는 키의 값을 바꾸면 순서는 어떻게 되나요?

사용으로 쳐서 그 키를 가장 최근으로 옮긴다. 옮기지 않으면 방금 바꾼 키가 다음 버리기에서 사라질 수 있다. 그리고 있는 키를 바꾸는 경우는 크기가 늘지 않으니 버리기를 하지 않는다. 가득 찬 상태에서 버리기를 먼저 하면 엉뚱한 키가 사라진다.

### Redis는 왜 정확한 LRU를 쓰지 않나요?

키가 수천만 개면 키마다 앞뒤 포인터를 붙이는 메모리와, 읽을 때마다 리스트를 고치는 비용이 크다. 그래서 키마다 마지막 접근 시각만 두고, 버릴 때 몇 개를 표본으로 뽑아 그중 가장 오래된 것을 버린다. 적중률은 정확한 LRU와 거의 비슷하면서 훨씬 싸다.
