사내 문서 도우미를 만드는 팀에서 이런 요구가 올라왔다. "모델이 우리 회사 용어를 몰라요. '정산 주기'를 물으면 일반적인 회계 이야기를 하고, 'OKR 리뷰'를 물으면 다른 회사 이야기를 해요. 그리고 답 말투가 너무 영어 번역체예요. 파인튜닝을 하면 되지 않을까요?" 회의에서는 사내 위키 전체로 모델을 학습시키자는 이야기까지 나왔다.

요구를 하나씩 뜯어 보니 성격이 달랐다.

- 사내 용어의 뜻: "정산 주기"가 우리 회사에서 무엇을 뜻하는지는 사실, 곧 지식이다.
- 최신 규정: 출장비 규정은 분기마다 바뀐다. 이것도 지식이고, 자주 바뀐다.
- 답의 말투: 번역체를 피하고 사내 보고서처럼 쓰는 건 형식이다.
- 보고서 양식: 주간 보고를 정해진 다섯 칸으로 채우는 건 작업 습관이다.

이 넷을 한 가지 방법으로 다 풀려고 하면 어긋난다. 이 글은 프롬프트, RAG, 파인튜닝이 각각 모델의 어디를 바꾸는지 나누고, 무엇을 언제 고를지 신호와 숫자로 정리한다. 프롬프트 자체를 잘 쓰는 법은 [시스템 프롬프트 설계 글](/posts/system-prompt-design)에, 매 요청에 무엇을 실을지는 [컨텍스트 엔지니어링 글](/posts/context-engineering)에, RAG를 만드는 법은 [기본 RAG 글](/posts/rag-classic-pipeline)에 있다.

## 세 가지는 바꾸는 곳이 다르다

모델이 답을 만드는 과정은 "가중치 × 입력 → 다음 토큰"이다. 세 방법은 이 식의 다른 곳을 건드린다.

프롬프트는 입력을 바꾼다. 시스템 프롬프트에 역할, 규칙, 예시, 출력 틀을 적는다. 모델은 그대로이고, 요청마다 같은 글이 앞에 붙는다. 고치면 바로 반영된다.

RAG는 입력을 바꾸되, 요청마다 다르게 바꾼다. 질문과 관련된 문서를 검색해서 프롬프트에 붙인다. 모델은 그대로이고, 문서 저장소를 고치면 다음 요청부터 반영된다. 근거 문서를 함께 보여 줄 수 있다.

파인튜닝은 가중치를 바꾼다. 입력과 원하는 출력의 예시 수백~수천 개로 모델을 더 학습시켜서, 같은 입력에 원하는 쪽 출력의 확률이 높아지게 한다. 학습이 끝나면 프롬프트가 짧아도 그 행동을 한다. 고치려면 데이터를 고쳐 다시 학습해야 한다.

이렇게 놓고 보면 처음 요구의 넷 중 두 개(용어의 뜻, 최신 규정)는 입력에 넣을 일이고, 나머지 두 개(말투, 보고서 양식)는 입력으로 시도해 보고 안 되면 가중치를 건드릴 일이다. 이 구분이 이 글의 뼈대다. 다만 뒤에서 보듯 경계가 칼같지는 않다.

## 모델이 지금의 모습이 되기까지

하나는 지식이 거의 사전 학습에서 온다는 점이다. 수조 토큰을 보면서 생긴 지식에 비해, 내가 준비할 수 있는 예시 수천 개는 아주 작다. 사내 위키 몇천 쪽을 파인튜닝 데이터로 넣는다고 모델이 그 내용을 사전 학습 지식처럼 단단히 갖게 되지는 않는다.

다른 하나는 지시 튜닝과 선호 학습이 이미 "형식과 행동을 바꾸는 학습"이라는 점이다. 질문에 답하고, 지시를 따르고, 해로운 요청을 거절하는 습관이 이 단계에서 생겼다. 내 파인튜닝은 같은 종류의 일을 우리 데이터로 한 번 더 하는 것이다. 그래서 파인튜닝은 행동과 형식을 바꾸는 데 강하다.

선호 학습의 두 방식도 짚어 두자. RLHF는 사람이 고른 쌍으로 보상 모델을 먼저 만들고, 그 보상을 높이도록 강화 학습(PPO 등)으로 모델을 갱신한다. DPO(Direct Preference Optimization)는 보상 모델 없이 "고른 답의 확률은 높이고 버린 답의 확률은 낮추는" 손실을 바로 줄인다. 단계가 하나 적어 구현과 학습이 단순해서, 직접 선호 학습을 해야 할 때 많이 쓴다. 공급사 API 중에도 SFT 말고 선호 쌍(DPO 형식)으로 파인튜닝하는 기능을 주는 곳이 있다.

## 지식이 필요하면 먼저 붙여 준다

처음 요구의 "사내 용어의 뜻"과 "최신 규정"은 지식이다. 이걸 파인튜닝으로 넣으려 하면 몇 가지 벽에 부딪힌다.

첫째, 학습시켜도 잘 꺼내지 못한다. 문서 한 번을 학습 데이터로 넣으면 모델이 그 내용을 다양한 질문에서 정확히 떠올리지 못하는 경우가 많다. 같은 사실을 여러 표현의 질문-답 쌍으로 많이 만들어야 그나마 붙는다. 새로운 사실을 파인튜닝으로 넣었더니 그 사실은 느리게 배우면서 모르는 것도 아는 척하는 경향(환각)이 늘었다는 연구도 있다.

둘째, 근거를 보여 줄 수 없다. RAG는 "출장비 규정 v12, 3조"를 근거로 함께 내놓을 수 있다. 가중치에 녹은 지식은 어디서 왔는지 말해 주지 못하고, 틀렸을 때 사람이 확인할 길이 없다.

셋째, 바뀌면 다시 학습해야 한다. 규정이 분기마다 바뀌면 분기마다 데이터를 고쳐 다시 학습하고 평가해야 한다. 그 사이에는 옛 규정을 자신 있게 말한다. RAG는 문서를 바꿔 끼우면 다음 요청부터 새 규정을 쓴다.

넷째, 지울 수 없다. 개인정보나 잘못된 정보가 학습 데이터에 섞였다면 가중치에서 그것만 빼낼 방법이 사실상 없다. 다시 학습하는 수밖에 없다. 문서 저장소에서는 그 문서를 지우면 된다. 권한도 같다. RAG는 검색 단계에서 이 사용자가 볼 수 있는 문서만 고를 수 있지만, 가중치에 들어간 지식은 누구에게나 나온다.

그래서 지식은 먼저 입력으로 붙인다. 용어가 수십 개라면 시스템 프롬프트에 용어집으로 넣으면 끝이다. 수천 쪽 규정이라면 RAG로 질문에 맞는 조항만 붙인다. 이 팀의 경우 사내 용어 120개를 용어집으로 시스템 프롬프트에 넣고, 규정과 위키는 RAG로 붙이는 것으로 처음 두 요구가 정리됐다.

## 형식과 습관은 예시로 가르친다

남은 두 요구, 말투와 보고서 양식은 성격이 다르다. 모델이 모르는 사실이 아니라 우리가 원하는 방식이다. 이런 건 먼저 프롬프트로 시도한다. 말투 지침을 적고, 좋은 답 예시 두세 개를 넣고, 보고서 틀을 보여 준다. 대부분은 여기서 해결된다.

파인튜닝이 값을 하는 건 프롬프트로 안 되거나 비쌀 때다. 신호는 이런 것들이다.

- 지침과 예시를 넣어도 일관성이 안 나온다. 말투 규칙이 서른 줄이 넘어가고, 그중 몇 개는 늘 어긴다. 규칙으로 쓰기 어려운 미묘한 문체라 "이런 느낌"을 예시 수백 개로만 보여 줄 수 있다.
- 같은 일을 아주 많이 한다. 하루 수십만 건의 문의 분류나 정보 추출처럼 작업이 좁고 반복된다. 이럴 때 작은 모델을 파인튜닝하면 큰 모델에 긴 프롬프트를 쓰는 것보다 싸고 빠르다.
- 프롬프트가 너무 길다. 지침과 예시가 수천 토큰이라 요청마다 비용과 지연이 붙는다.
- 출력 형식이 복잡하고 엄격하다. 도메인 특유의 문서 구조를 매번 정확히 따라야 한다.

마지막 신호를 숫자로 보자. 말투 지침과 예시가 3천 토큰이고, 월 100만 건의 요청에 매번 싣는다. 입력 단가를 100만 토큰당 3달러로 가정했다.

```js
// cost.mjs: 말투 지침 3천 토큰을 매 요청 싣는 비용 (단가는 가정)
const req = 1_000_000, guide = 3_000, price = 3;      // 월 요청 수, 지침 토큰, 입력 100만 토큰당 3달러 가정
const tokens = req * guide;
console.log("지침 토큰/월", tokens.toLocaleString());
console.log("캐시 없이 $" + (tokens / 1e6 * price).toLocaleString());
console.log("캐시 읽기(0.1배) $" + (tokens / 1e6 * price * 0.1).toLocaleString());
```

```text
지침 토큰/월 3,000,000,000
캐시 없이 $9,000
캐시 읽기(0.1배) $900
```

캐시 없이 한 달에 9천 달러다. 하지만 지침은 요청마다 같으니 프롬프트 캐시가 맞으면 900달러로 준다(캐시 읽기 단가 배율은 공급사마다 다르다). 캐시가 있는 지금은 "프롬프트가 길어서 파인튜닝한다"는 이유가 예전보다 약해졌다. 파인튜닝한 모델은 추론 단가가 기본 모델보다 비싸게 매겨지는 공급사도 있고, 학습 비용과 다시 학습하는 비용이 따로 든다. 요청량, 캐시 적중률, 파인튜닝 모델의 단가를 넣어 직접 계산해 보고 정한다. 지연 쪽은 캐시가 있어도 긴 입력이 첫 토큰 시간에 붙으니, 지연이 중요한 서비스라면 그만큼 파인튜닝 쪽에 무게가 실린다.

## 전체 학습과 LoRA, QLoRA

파인튜닝을 하기로 했다면 다음은 "어디까지 학습시킬까"다. 모든 가중치를 갱신하는 전체 파인튜닝(full fine-tuning)과, 원래 가중치는 얼려 두고 작은 부분만 학습하는 방식(PEFT, parameter-efficient fine-tuning)이 있다. PEFT 중 가장 많이 쓰는 게 LoRA(Low-Rank Adaptation)다.

LoRA의 아이디어는 이렇다. 모델 안의 큰 행렬 W(예: 4096 × 4096)를 직접 바꾸는 대신, 바뀌는 양을 작은 행렬 두 개의 곱 B × A로 표현한다. A는 r × 4096, B는 4096 × r이고, r(랭크)은 8이나 16 같은 작은 수다. 학습은 A와 B만 하고, 추론할 때는 W + B × A를 쓴다. 파인튜닝으로 생기는 변화는 큰 행렬 전체를 바꿀 만큼 복잡하지 않고 낮은 랭크로 충분히 표현된다는 가정이다.

얼마나 작은지 7B급 모델(은닉 차원 4096, 32층)로 계산해 봤다.

```js
// lora.mjs: 7B급 모델(은닉 4096, 32층)에 LoRA를 붙일 때 학습할 파라미터 수와 메모리를 어림한다
const d = 4096, layers = 32, total = 7e9;
const lora = (r, mats) => layers * mats.reduce((s, [i, o]) => s + r * (i + o), 0);
const qv = [[d, d], [d, d]];                        // q_proj, v_proj
const all = [[d, d], [d, d], [d, d], [d, d], [d, 11008], [d, 11008], [11008, d]]; // q,k,v,o + MLP 셋
for (const [name, r, mats] of [["q,v r=8", 8, qv], ["q,v r=16", 16, qv], ["전체 선형층 r=16", 16, all]]) {
  const p = lora(r, mats);
  console.log(name.padEnd(14), (p / 1e6).toFixed(2) + "M", (p / total * 100).toFixed(3) + "%");
}
const GB = 1e9;
console.log("전체 학습(혼합 정밀도+Adam, 파라미터당 약 16바이트):", (total * 16 / GB).toFixed(0), "GB + 활성값");
console.log("LoRA, 기반 모델 16비트로 얼림:", (total * 2 / GB).toFixed(0), "GB + 어댑터·활성값");
console.log("QLoRA, 기반 모델 4비트로 얼림:", (total * 0.5 / GB).toFixed(1), "GB + 어댑터·활성값");
```

어텐션의 q, v 행렬에만 r=16으로 붙이면 학습할 파라미터는 839만 개, 전체의 0.12%다. 모든 선형층에 붙여도 0.57%다. 메모리 차이는 더 크다. 전체 학습은 가중치, 기울기, Adam 옵티마이저의 상태 두 개를 다 들고 있어야 해서 파라미터당 대략 16바이트, 7B 모델이면 112GB에 활성값까지 얹힌다. 큰 GPU 여러 장이 필요하다. LoRA는 기반 모델을 16비트로 얼려 두기만 하면 되니 14GB에 작은 어댑터만 학습한다. QLoRA는 얼린 기반 모델을 4비트로 양자화해 3.5GB까지 줄인다. 7B 모델을 GPU 한 장에서 파인튜닝할 수 있게 된 게 이 덕분이다. 위 숫자는 어림이고, 실제 메모리는 배치 크기와 문장 길이에 따른 활성값, 프레임워크 오버헤드가 더해진다.

계산을 직접 해 볼 수 있다. 층 수, 붙일 행렬들의 모양 `[입력 차원, 출력 차원]`, 랭크 r을 받아 LoRA가 학습할 파라미터 수를 돌려주면 된다. 행렬 하나에 r × (입력 + 출력)개가 붙는다.

LoRA를 고를 때의 트레이드오프도 있다. 학습할 양이 작으니 전체 학습보다 표현력이 떨어질 수 있다. 다만 형식과 말투처럼 파인튜닝이 잘하는 일에서는 차이가 작다는 보고가 많다. 어댑터가 수십 MB라 저장과 배포가 쉽고, 기반 모델 하나에 어댑터를 여러 개 바꿔 끼워 고객사별, 작업별 모델을 따로 둘 수 있다. 추론할 때 어댑터를 가중치에 미리 합쳐 두면 추가 지연도 없다. 공급사 API로 파인튜닝할 때는 이런 선택을 공급사가 대신 하고, 나는 데이터와 몇 가지 설정(에폭 수, 학습률 배율)만 정한다.

## 데이터 수백 건을 만드는 일

파인튜닝의 비용 대부분은 GPU가 아니라 데이터에서 나온다. 공급사 안내는 수십 개 예시부터 시작해 보라는 정도지만, 실무에서 형식과 말투를 안정적으로 바꾸려면 보통 수백에서 수천 건을 만든다. 형식은 대화 한 건이 한 줄인 JSONL이다.

```json
{"messages": [
  {"role": "system", "content": "사내 문서 도우미"},
  {"role": "user", "content": "이번 주 배포 장애 주간 보고 써 줘. 내용: 9/14 결제 API 타임아웃 40분, 재시도로 중복 주문 4,812건, 환불 처리 완료"},
  {"role": "assistant", "content": "[요약] 9/14 결제 API 타임아웃으로 40분간 결제 지연, 중복 주문 4,812건 발생\n[영향] ...\n[원인] ...\n[조치] ...\n[다음 할 일] ..."}
]}
```

데이터를 만들 때 지키는 것들이 있다.

- 실제 입력에서 시작한다. 지어낸 깔끔한 질문보다 로그에 있는 진짜 입력(오타, 짧은 문장, 여러 요청이 섞인 문장)이 낫다. 답은 사람이 쓰거나, 큰 모델이 쓰고 사람이 고친다.
- 양보다 질이다. 일관되지 않은 답 1천 개보다 일관된 답 300개가 낫다. 같은 종류의 입력에 서로 다른 형식의 답이 섞여 있으면 모델은 그 흔들림까지 배운다. 답을 쓰는 사람이 여럿이면 지침을 먼저 맞춘다.
- 경계와 거절도 넣는다. 범위 밖 질문, 정보가 부족한 요청에 어떻게 답하는지도 예시로 보여 준다. 잘 되는 경우만 넣으면 모든 입력에 자신 있게 답하는 모델이 된다.
- 지식은 넣지 않는다. 보고서 양식을 가르치려는 데이터에 최신 규정 내용이 섞이면, 그 규정이 바뀐 뒤에도 모델이 옛 내용을 말한다. 사실이 필요한 자리에는 RAG로 붙일 문서가 들어갈 자리를 남긴다.
- 개인정보를 지운다. 학습 데이터에 들어간 정보는 지울 수 없다고 앞에서 봤다. 로그에서 뽑았다면 이름, 연락처, 주문 번호를 바꿔 넣는다.
- 평가용을 따로 떼 둔다. 전체의 10~20%는 학습에 쓰지 않고 남겨, 학습 뒤 처음 보는 입력에서도 되는지 잰다. 학습 데이터와 거의 같은 문장이 평가용에 섞이지 않게 중복을 지운다.

그림의 검증 손실 숫자는 흐름을 보이려고 넣은 예시 값이다. 실제 곡선은 데이터와 설정마다 다르다. 볼 것은 모양이다. 2에폭에서 바닥을 찍고 3에폭에서 다시 오르면 2에폭 체크포인트를 쓴다.

직접 GPU에서 LoRA로 학습한다면 Hugging Face의 PEFT 라이브러리를 쓰는 경우가 많다. 설정의 모양은 이렇다.

```python
# PEFT LoRA 설정의 모양 (값은 흔히 쓰는 출발점이며, 데이터에 맞춰 조정한다)
from peft import LoraConfig

config = LoraConfig(
    r=16,                                   # 랭크. 클수록 표현력과 메모리가 함께 는다
    lora_alpha=32,                          # 갱신량의 배율. r의 1~2배로 두는 경우가 많다
    lora_dropout=0.05,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],   # 붙일 행렬 이름은 모델 구조마다 다르다
    task_type="CAUSAL_LM",
)
```

이 글을 쓴 환경에서는 모델을 내려받을 수 없어 이 설정으로 학습을 돌려 보지는 못했다. 그래서 설정의 모양만 보이고, 학습 결과 숫자는 싣지 않았다. 설정에서 흔히 틀리는 곳은 세 군데다. `target_modules`의 이름이 모델 구조와 맞지 않으면 어댑터가 아무 데도 붙지 않거나 오류가 난다. 학습할 파라미터 수를 찍어 보고 0이 아닌지 확인한다. 학습률은 전체 학습보다 높게(LoRA에서는 1e-4 근처에서 시작하는 경우가 많다) 잡되, 망각이 보이면 낮춘다. 그리고 학습에 쓴 채팅 템플릿(역할 표시, 특수 토큰)과 서비스에서 쓰는 템플릿이 다르면, 학습은 잘 됐는데 서비스에서는 효과가 없는 일이 생긴다.

서빙도 미리 생각한다. 공급사 API로 파인튜닝하면 새 모델 ID가 생기고 그걸 부르면 된다. 직접 띄운다면 기반 모델 하나에 어댑터를 여러 개 올려 요청마다 골라 쓰는 방식을 지원하는 추론 서버(vLLM 등)가 있어서, 고객사별 어댑터를 둬도 GPU를 그만큼 늘리지 않아도 된다. 어떤 방식이든 "어떤 데이터 버전으로, 어떤 설정으로 학습한 어댑터인지"를 모델 ID 옆에 기록한다. 석 달 뒤에 같은 모델을 다시 만들 수 있어야 한다.

## 과적합과 망각

학습을 오래 하거나 데이터가 좁으면 두 가지 문제가 생긴다.

과적합은 학습 데이터에만 맞춰지는 것이다. 학습 손실은 계속 내려가는데 따로 떼 둔 검증 손실은 어느 순간부터 올라간다. 증상으로는 학습 예시와 비슷한 입력에는 완벽하게 답하지만 조금만 다른 입력에는 엉뚱하게 답하거나, 학습 예시의 문장을 그대로 베낀 답이 나온다. 에폭 수를 줄이고, 검증 손실이 바닥일 때의 체크포인트를 쓰고, 데이터를 더 다양하게 만든다. 공급사 API도 학습 중 검증 손실을 보여 주니 그 곡선을 꼭 본다.

망각(catastrophic forgetting)은 새 일을 배우면서 원래 잘하던 일을 못하게 되는 것이다. 주간 보고 양식만 수천 번 학습시켰더니, 일반 질문에도 [요약] [영향] 칸을 채워 답하거나 원래 하던 코드 설명 능력이 떨어진다. 학습률을 낮추고, 에폭을 줄이고, 일반적인 지시-답 데이터를 조금 섞는다. LoRA는 원래 가중치를 얼려 두니 전체 학습보다 망각이 덜한 편이고, 어댑터를 빼면 원래 모델로 돌아갈 수 있다.

그래서 파인튜닝한 모델의 평가는 두 갈래로 한다. 내가 가르친 일(양식을 지키는지, 말투가 맞는지)을 떼어 둔 검증 데이터로 재고, 원래 잘하던 일(일반 질문, 범위 밖 거절, 안전한 답)이 그대로인지 기존 평가 세트로 다시 잰다. 앞쪽만 재면 망각을 모르고 배포한다.

## API에 맡길까, 직접 돌릴까

파인튜닝을 하는 길도 둘이다. 공급사의 파인튜닝 API에 데이터를 올리거나, 공개 가중치 모델을 받아 직접 학습한다.

공급사 API는 시작이 쉽다. 데이터 파일을 올리고 몇 가지 설정을 고르면 학습이 돌고, 끝나면 새 모델 ID가 생긴다. GPU를 빌릴 필요도, 학습 코드를 짤 필요도 없다. 대신 고를 수 있는 기반 모델이 공급사가 열어 준 것으로 정해지고(어떤 모델이 파인튜닝되는지는 자주 바뀌니 문서를 본다), 학습 데이터가 공급사로 간다. 학습 방식의 세부를 내가 정하지 못하고, 기반 모델이 지원 종료되면 새 기반 모델로 다시 학습해야 한다.

직접 학습은 반대다. Llama, Qwen, Gemma 같은 공개 가중치 모델 중에서 크기와 라이선스가 맞는 걸 고르고, LoRA 설정과 학습률을 내가 정한다. 데이터가 밖으로 나가지 않고, 학습한 가중치를 내가 갖는다. 대신 GPU를 구하고, 학습 파이프라인을 만들고, 학습된 모델을 서빙하는 일까지 내 몫이다. 모델 라이선스가 상업 사용과 사용자 수에 조건을 거는 경우가 있으니 고르기 전에 확인한다.

처음 해 보는 팀이라면 공급사 API로 작게 시작하는 게 낫다. 데이터 300건으로 한 번 돌려 보고, 평가 세트에서 프롬프트만 쓴 기본 모델보다 나아지는지부터 본다. 이 첫 실험의 목적은 모델을 얻는 게 아니라 "우리 데이터로 파인튜닝하면 실제로 나아지는가"를 확인하는 것이다. 나아지지 않는다면 대개 데이터가 일관되지 않거나, 애초에 프롬프트로 풀 문제였다는 뜻이다.

## 파인튜닝을 했는데 효과가 없을 때

"학습은 끝났는데 기본 모델과 별 차이가 없다"면 먼저 서비스가 정말 새 모델 ID를 부르는지 확인한다. 설정 하나 빠뜨려 옛 모델을 부르고 있는 경우가 생각보다 흔하다. 그다음 학습 데이터의 형식(시스템 프롬프트, 역할 순서)과 서비스의 요청 형식이 같은지 본다. 학습 때는 시스템 프롬프트 없이 넣었는데 서비스에서는 긴 시스템 프롬프트를 붙이면, 모델은 학습 때 보지 못한 입력을 받는 셈이다.

"학습 데이터 문장을 그대로 베껴 쓴다"면 과적합이다. 에폭을 줄이고, 비슷한 예시를 줄이고, 입력을 더 다양하게 만든다.

"엉뚱한 질문에도 보고서 양식으로 답한다"면 데이터에 그 양식만 있었던 것이다. 양식이 필요 없는 질문과 그 답을 섞어, 언제 양식을 쓰고 언제 쓰지 않는지도 가르친다.

"전보다 자신 있게 틀린 사실을 말한다"면 데이터에 사실이 섞였는지 본다. 답 예시에 들어간 날짜, 금액, 규정 내용을 모델이 외워서 다른 맥락에 가져다 쓴다. 그런 자리는 자리 표시로 바꾸거나, RAG로 붙일 문서를 함께 넣은 예시로 바꾼다.

"평가 점수는 올랐는데 사용자 불만이 늘었다"면 평가 세트가 실제 입력을 닮지 않았다. 최근 로그에서 평가 세트를 다시 뽑고, 사람이 직접 몇십 건을 읽어 본다.

## 비용, 갱신 속도, 평가를 나란히 놓으면

여기까지를 한 표로 모았다. 숫자는 이 글의 예시 기준이고, 서비스마다 다르다.

| | 프롬프트 | RAG | 파인튜닝 |
|---|---|---|---|
| 바꾸는 곳 | 요청마다 같은 입력 | 요청마다 다른 입력 | 가중치 |
| 잘 푸는 문제 | 형식, 규칙, 간단한 맥락 | 모델이 모르는 사실, 자주 바뀌는 지식 | 일관된 형식·말투, 좁고 반복되는 작업 |
| 처음 드는 비용 | 거의 없음 | 색인 파이프라인, 벡터 저장소 | 데이터 수백~수천 건, 학습 |
| 요청마다 드는 비용 | 프롬프트 길이만큼 (캐시로 줄어듦) | 검색 + 붙인 문서 토큰 | 짧은 프롬프트, 대신 모델 단가가 다를 수 있음 |
| 바꾸는 데 걸리는 시간 | 배포 한 번 | 문서 교체 즉시 | 데이터 수정 → 재학습 → 재평가 |
| 근거 보여 주기 | 프롬프트 안의 내용만 | 문서 출처를 함께 | 어려움 |
| 지우기·권한 | 쉬움 | 문서 단위로 가능 | 재학습 말고는 어려움 |
| 평가 방법 | 평가 세트 | 검색 지표 + 답 평가 | 검증 손실 + 평가 세트 + 망각 확인 |

## '지식은 RAG, 형식은 파인튜닝'의 한계

이 표어는 출발점으로 좋지만, 그대로 믿으면 놓치는 게 있다.

RAG로도 형식을 바꿀 수 있다. 검색할 때 질문과 비슷한 과거의 좋은 답을 함께 찾아 예시로 붙이면, 질문마다 맞는 퓨샷이 생긴다. 양식 종류가 많을 때는 파인튜닝보다 이게 낫기도 하다.

파인튜닝으로도 지식을 넣을 수는 있다. 잘 안 바뀌고, 출처가 필요 없고, 같은 사실을 다양하게 묻는 데이터를 충분히 만들 수 있으면 붙는다. 의료나 법률처럼 용어와 추론 방식이 일반 데이터와 크게 다른 분야에서는 도메인 데이터로 한 단계 더 학습한 모델이 RAG 문서를 더 잘 읽는다. 다만 이건 비용이 아주 큰 작업이고, 대부분의 사내 도우미에게는 과하다.

둘은 경쟁이 아니라 조합이다. 실무에서 흔한 구성은 "RAG로 사실을 붙이고, 파인튜닝으로 붙은 문서를 잘 쓰는 법을 가르친다"이다. 검색된 문서 중 관련 없는 것을 무시하고, 근거 조항을 인용하고, 문서에 없으면 모른다고 답하는 행동을 예시로 학습시키는 것이다. 검색된 문서와 질문, 좋은 답을 함께 넣은 데이터로 학습하는 방식(RAFT라는 이름으로 소개된 방법이 이런 종류다)이 그 예다. 임베딩 모델 쪽을 우리 문서로 파인튜닝해 검색 품질을 올리는 방법도 있다.

그리고 셋 중 무엇을 고르든, 먼저 해야 하는 일은 같다. 평가 세트를 만드는 것이다. 평가 세트가 없으면 프롬프트를 고쳤을 때도, RAG를 붙였을 때도, 파인튜닝을 했을 때도 좋아졌는지 모른다. 파인튜닝은 특히 되돌리기 비싸니 평가 세트 없이 시작하지 않는다.

## 큰 모델로 작은 모델 가르치기

파인튜닝의 쓰임 중 비용 면에서 가장 효과가 큰 건 증류(distillation)다. 큰 모델이 잘하는 일을 작은 모델에게 옮긴다.

순서는 이렇다. 먼저 큰 모델에 좋은 프롬프트를 써서 일을 잘하게 만든다. 실제 입력 수천 개를 큰 모델에 넣어 답을 모으고, 평가 기준으로 걸러 좋은 답만 남긴다. 이 입력-답 쌍으로 작은 모델을 파인튜닝한다. 그러면 작은 모델이 그 좁은 일에서 큰 모델에 가까운 품질을 내고, 요청당 비용과 지연은 작은 모델 수준이 된다. 하루 수십만 건의 문의 분류처럼 좁고 반복되는 작업에서 특히 효과가 크다.

주의할 점이 둘 있다. 작은 모델은 그 좁은 일만 배운다. 입력의 종류가 바뀌거나 범위가 넓어지면 큰 모델보다 빨리 무너지니, 입력 분포를 지켜보며 범위를 벗어난 입력은 큰 모델로 보내는 경로를 둔다. 그리고 약관을 확인한다. 공급사에 따라 자사 모델의 출력으로 다른 모델, 특히 경쟁 모델을 학습시키는 것을 제한하기도 한다. 같은 공급사 안에서 큰 모델의 출력으로 작은 모델을 파인튜닝하는 기능을 공식으로 제공하는 경우도 있다.

- 그 행동을 보여 주는 좋은 예시를 최소 수백 건 만들 수 있다. 수십 건이 한계라면 그 예시는 퓨샷이나 검색된 예시로 쓰는 게 낫다.

## 무엇을 모르는지가 길을 정한다

프롬프트는 요청마다 같은 입력을, RAG는 요청마다 다른 입력을, 파인튜닝은 가중치를 바꾼다. 모델이 사실을 모르면 입력으로 붙이고, 일하는 방식이 다르면 프롬프트로 시작해 안 될 때 파인튜닝으로 간다. 파인튜닝을 한다면 LoRA·QLoRA로 비용을 줄이고, 일관된 데이터 수백 건을 만들고, 가르친 일과 원래 하던 일을 함께 잰다. 셋은 경쟁이 아니라 조합이고, 무엇을 고르든 평가 세트가 먼저다.

## 면접에서 나올 만한 질문

### 파인튜닝과 RAG는 무엇이 다른가요?

RAG는 질문과 관련된 문서를 검색해 입력에 붙이고, 파인튜닝은 예시 데이터로 모델의 가중치를 바꾼다. 그래서 RAG는 문서를 바꾸면 바로 반영되고 근거를 보여 줄 수 있으며 문서 단위로 권한과 삭제를 다룰 수 있다. 파인튜닝은 재학습해야 바뀌고 근거를 보여 주기 어렵지만, 짧은 프롬프트로도 일관된 형식과 말투를 낸다. 모델이 모르는 사실은 RAG, 일하는 방식은 파인튜닝에 가깝다.

### 언제 파인튜닝을 하나요?

먼저 프롬프트와 예시로 시도하고, 평가 세트 통과율이 몇 번을 고쳐도 같은 항목에서 목표에 못 미칠 때 간다. 그 행동을 보여 주는 일관된 예시를 수백 건 이상 만들 수 있어야 하고, 가르칠 것이 자주 바뀌지 않아야 한다. 요청량이 커서 긴 프롬프트나 큰 모델의 비용이 부담이거나, 지연 때문에 작은 모델로 내려가야 할 때 특히 값을 한다. 사실을 몰라서 생긴 문제나 평가 세트가 없는 상태에서는 하지 않는다.

### 사내 지식을 모델에 넣으려고 위키 전체로 파인튜닝하면 안 되나요?

권하지 않는다. 문서를 학습시켜도 다양한 질문에서 그 내용을 정확히 꺼내지 못하는 경우가 많고, 새 사실을 파인튜닝으로 넣으면 환각이 늘었다는 연구도 있다. 근거를 보여 줄 수 없고, 규정이 바뀌면 재학습해야 하며, 개인정보나 틀린 내용을 지울 수 없고, 권한별로 다르게 보여 줄 수도 없다. 용어는 용어집으로, 문서는 RAG로 붙이는 게 맞다.

### 사전 학습, 지시 튜닝, 선호 학습은 각각 무엇을 하나요?

사전 학습은 수조 토큰으로 다음 토큰 맞히기를 해서 언어 능력과 지식 대부분을 만든다. 지시 튜닝(SFT)은 지시와 좋은 답의 쌍으로 학습해 질문에 답하고 지시를 따르는 형식을 가르친다. 선호 학습은 사람이 고른 답의 확률을 높이는데, RLHF는 보상 모델을 만든 뒤 강화 학습으로, DPO는 보상 모델 없이 선호 쌍으로 바로 학습한다. 내 파인튜닝은 그 위에 수백~수천 예시로 얇은 한 겹을 더하는 것이라 지식보다 행동을 바꾸는 데 맞다.

### LoRA는 어떻게 동작하고 왜 쓰나요?

원래 가중치 행렬은 얼려 두고, 바뀌는 양을 랭크 r의 작은 행렬 두 개의 곱으로 표현해 그것만 학습한다. 7B급 모델의 q, v 행렬에 r=16으로 붙이면 학습할 파라미터가 839만 개, 전체의 0.12%다. 옵티마이저 상태까지 전체를 들고 있는 전체 학습이 7B 기준 100GB 넘게 드는 데 비해 메모리가 크게 줄고, QLoRA는 얼린 모델을 4비트로 양자화해 GPU 한 장에서도 학습할 수 있게 한다. 어댑터가 작아 작업별로 바꿔 끼우기 쉽고, 원래 가중치를 건드리지 않아 망각도 덜하다.

### 파인튜닝한 모델이 원래 잘하던 일을 못하게 됐습니다. 왜 그렇고 어떻게 막나요?

새 일을 배우면서 기존 능력이 덮이는 망각이다. 좁은 데이터를 높은 학습률로 오래 학습할수록 심하다. 학습률과 에폭을 낮추고, 일반적인 지시-답 데이터를 조금 섞고, LoRA처럼 원래 가중치를 얼리는 방식을 쓴다. 평가는 가르친 일의 검증 데이터와 원래 하던 일의 기존 평가 세트를 함께 돌려야 망각을 배포 전에 잡는다.

### 파인튜닝 데이터는 몇 건이나, 어떻게 만드나요?

공급사 안내는 수십 건부터 시도해 보라는 정도지만, 형식과 말투를 안정적으로 바꾸려면 보통 수백에서 수천 건을 만든다. 실제 로그의 입력에서 출발하고, 같은 종류의 입력에는 같은 형식의 답을 주어 일관성을 지키며, 범위 밖 질문과 거절도 넣는다. 바뀔 수 있는 사실은 데이터에 넣지 않고, 개인정보는 지우고, 10~20%는 평가용으로 떼어 중복 없이 둔다.

### 증류는 무엇이고 언제 쓰나요?

큰 모델에 좋은 프롬프트를 써서 만든 답을 모아 작은 모델을 파인튜닝해, 좁은 작업에서 큰 모델에 가까운 품질을 작은 모델의 비용과 지연으로 얻는 방법이다. 하루 수십만 건의 분류나 추출처럼 좁고 반복되는 일에 맞다. 작은 모델은 배운 범위 밖에서 빨리 무너지니 범위를 벗어난 입력은 큰 모델로 보내는 경로를 두고, 출력으로 다른 모델을 학습시키는 걸 제한하는 공급사 약관이 있는지 확인한다.
