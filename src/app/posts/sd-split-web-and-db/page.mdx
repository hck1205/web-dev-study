이 시리즈에서 이 글의 자리: [① 서버 한 대](/posts/sd-start-single-server)에서 처음 무너진 곳을 고치는 글이다. 다음 글은 [③ 로드 밸런서와 무상태 웹](/posts/sd-load-balancer-stateless)이다. 같은 장의 글은 [④ DB 복제](/posts/sd-db-replication-intro), [⑤ 캐시와 CDN](/posts/sd-cache-and-cdn-tier), [⑥ 데이터 센터 여러 곳](/posts/sd-multi-datacenter), [⑦ 큐, 로그, 자동화](/posts/sd-queue-logging-automation), [⑧ 샤딩 입문](/posts/sd-sharding-intro)이다.

맛집 리뷰 앱이 서버 한 대로 몇 달을 버텼다. 그런데 매주 월요일 새벽, 지난주 순위를 다시 계산하는 집계 쿼리가 돌 때면 앱 전체가 굼떠진다. 어느 날은 아예 리뷰 작성이 전부 실패했다. 로그를 보니 메모리가 모자라 리눅스가 PostgreSQL 프로세스를 강제로 꺼 버렸다. 웹 앱이 사진을 줄이느라 메모리를 많이 잡은 직후였다.

웹 앱과 DB가 한 컴퓨터의 CPU, 메모리, 디스크를 나눠 쓰다 보니 한쪽의 사정이 다른 쪽을 망가뜨린다. 이 글은 가장 먼저 할 수 있는 처방, DB를 다른 서버로 옮기는 일을 다룬다. 옮기면 무엇이 좋아지는지, 무엇이 새로 비싸지는지, 옮기는 김에 DB 종류는 무엇을 골라야 하는지, 그리고 "더 큰 서버"와 "더 많은 서버"가 어떻게 다른지까지 본다.

데모는 Node.js 22와 PGlite(WASM으로 옮긴 PostgreSQL)로 돌렸다. PGlite를 PostgreSQL 통신 규약으로 열어 두고, 그 앞에 일부러 지연을 넣은 중계 프로그램을 세워 "DB가 다른 서버에 있는" 상황을 흉내 냈다.

## 같은 집에 살면 생기는 다툼

한 대에 모두 있을 때의 문제는 세 가지 자원에서 나온다.

CPU는 웹 앱이 요청을 처리하는 데도, DB가 쿼리를 계산하는 데도 쓰인다. 집계 쿼리가 코어를 잡으면 웹 앱의 응답이 늦어진다. 메모리는 더 민감하다. PostgreSQL은 자주 읽는 데이터를 메모리에 올려 두고 빠르게 답하는데, 웹 앱이 메모리를 많이 쓰면 DB가 쓸 몫이 줄어 디스크를 더 자주 읽는다. 끝내 메모리가 바닥나면 리눅스의 OOM killer(메모리 부족 때 프로세스를 골라 강제로 끄는 장치)가 개입하고, 메모리를 많이 쓰는 DB가 표적이 되기 쉽다.

디스크도 그렇다. 업로드한 사진과 로그가 디스크를 채우면 DB는 새 데이터를 쓰지 못한다.

그리고 둘은 늘려야 하는 이유도 시기도 다르다. 웹 앱은 요청이 많아지면 CPU가 더 필요하고, DB는 데이터가 쌓이면 메모리와 디스크가 더 필요하다. 한 대에 묶여 있으면 하나가 필요할 때 둘 다 함께 키워야 한다.

## 웹 계층과 데이터 계층으로 나눈다

나누면 세 가지가 좋아진다.

첫째, 서로 방해하지 않는다. DB 서버의 메모리는 온전히 DB 몫이다. 집계 쿼리가 DB의 CPU를 다 써도 웹 서버의 CPU는 멀쩡하다. 응답은 DB를 기다리느라 느려질 수 있어도, DB를 쓰지 않는 요청까지 함께 멈추지는 않는다.

둘째, 따로 키운다. 웹 서버는 CPU 위주의 기종으로, DB 서버는 메모리와 빠른 디스크 위주의 기종으로 고를 수 있다. 나중에 웹 서버를 여러 대로 늘릴 때도 DB는 그대로 둘 수 있다.

셋째, 안전해진다. DB를 인터넷에서 닿지 않는 안쪽 망(private 서브넷)에 두고, 웹 서버에서 오는 접속만 받게 한다. 웹 서버가 뚫려도 DB가 바로 노출되지는 않는다. 서브넷과 라우팅은 [VPC 서브넷 글](/posts/vpc-subnets-route-tables)에, 방화벽 규칙은 [보안 그룹과 NACL 글](/posts/security-groups-nacl)에 있다.

DB 서버 쪽에서도 두 가지를 열어야 한다. PostgreSQL은 기본 설정(`listen_addresses = 'localhost'`)에서 자기 자신의 접속만 받는다. 이 값을 사설 IP로 바꾸고, `pg_hba.conf`에 "웹 서버 대역에서 오는 matjip_app 계정은 비밀번호로 인증한다"는 줄을 넣는다. 자세한 문법은 [PostgreSQL 접속과 pg_hba 글](/posts/postgres-connections-pg-hba)에 있다.

```text
# postgresql.conf: 사설 IP에서도 접속을 받는다
listen_addresses = 'localhost,10.0.2.15'

# pg_hba.conf: 웹 서브넷(10.0.1.0/24)에서 matjip DB로 오는 matjip_app만 비밀번호(scram)로 받는다
# TYPE   DATABASE  USER        ADDRESS        METHOD
hostssl  matjip    matjip_app  10.0.1.0/24    scram-sha-256
```

옮긴 직후 가장 흔한 장애는 "연결이 안 된다"다. 웹 서버에서 `pg_isready`로 먼저 확인한다. 아래는 실습 환경에서 열린 포트와 아무도 없는 포트에 각각 물어본 결과다.

```bash
# DB가 연결을 받는지 확인한다 (실제로는 -h에 DB 서버 주소를 넣는다)
pg_isready -h 127.0.0.1 -p 55432
pg_isready -h 127.0.0.1 -p 55999; echo "exit=$?"
```

```text
127.0.0.1:55432 - accepting connections
127.0.0.1:55999 - no response
exit=2
```

`accepting connections`면 네트워크와 DB 프로세스는 괜찮고, 문제는 계정이나 비밀번호, `pg_hba.conf` 쪽이다. `no response`(종료 코드 2)면 패킷이 닿지 않는 것이다. 방화벽, `listen_addresses`, 라우팅을 본다. 이 둘을 가르는 것만으로 찾을 곳이 절반으로 준다.

## 대신 쿼리마다 길을 건넌다

나누면 공짜가 아니다. 한 대일 때 웹 앱과 DB 사이의 거리는 사실상 0이었다. 이제 쿼리 하나마다 요청이 네트워크를 건너가고 결과가 건너온다. 이 한 번 오가는 시간을 왕복 시간(RTT, Round Trip Time)이라고 한다.

같은 데이터 센터 안이라면 RTT는 보통 1ms보다 훨씬 짧고, 같은 리전의 다른 가용 영역(전원과 네트워크가 분리된 건물)이면 1~2ms 정도로 잡는다. 값은 클라우드와 위치에 따라 다르니 직접 재 보는 것이 맞다. 대략의 감은 [⑨ 지연 시간 숫자](/posts/sd-latency-numbers)에 정리돼 있다.

1ms가 작아 보이지만 쿼리를 몇 번 보내느냐에 따라 곱해진다. 맛집 목록 화면을 두 방식으로 만들어 쟀다.

- 하나씩 묻기: 식당 20곳을 가져온 뒤, 식당마다 평균 별점을 따로 묻는다. 쿼리가 1 + 20 = 21번이다. 이런 모양을 N+1 쿼리라고 부른다.
- 한 번에 묻기: 식당과 리뷰를 JOIN으로 묶어 평균까지 한 쿼리로 구한다.

같은 컴퓨터에 연결했을 때와, 한 방향마다 1ms 지연을 넣은 중계를 거쳤을 때를 비교했다. 각각 9번 재서 가운데 값을 적었다.

```bash
# 55432는 DB에 바로, 55433은 한 방향 1ms 지연 중계를 거친다
node bench.mjs
```

```text
same box (55432):    {"ping":"0.63","nPlus1":"21 queries 27.8 ms","join":"1 query 3.1 ms"}
other box (55433):   {"ping":"3.19","nPlus1":"21 queries 79.9 ms","join":"1 query 5.3 ms"}
```

`ping`은 `SELECT 1` 한 번이 왕복하는 시간이다. 지연을 넣자 0.63ms에서 3.19ms로 약 2.5ms가 늘었다. 하나씩 묻는 방식은 27.8ms에서 79.9ms로 52ms가 늘었다. 21번 × 2.5ms와 거의 같다. 한 번에 묻는 방식은 3.1ms에서 5.3ms로, 딱 한 번 치의 지연만 늘었다.

같은 서버에 있을 때는 숨어 있던 나쁜 습관이 DB를 옮기는 순간 드러난다. 그래서 DB를 나누기 전에 화면 하나가 쿼리를 몇 번 보내는지부터 센다. ORM을 쓰면 반복문 안의 지연 로딩이 N+1을 만들기 쉽다. 찾고 고치는 방법은 [N+1 쿼리 글](/posts/n-plus-one-queries)에서 다룬다.

직접 계산해 보자. 화면에 항목이 `items`개 있고, `mode`가 `"n+1"`이면 `items + 1`번, `"in"`(ID를 모아 `WHERE id IN (...)`으로 한 번 더 묻기)이면 2번, `"join"`이면 1번 왕복한다. 왕복 한 번마다 `rttMs + queryMs`가 든다. 소수 첫째 자리로 반올림해 돌려주자.

  initialCode={`function pageDbTime(items, mode, rttMs, queryMs) {
  // mode: "n+1" | "in" | "join"
  // 왕복 횟수 × (rttMs + queryMs), 소수 첫째 자리 반올림
  return 0;
}`}
  solution={`function pageDbTime(items, mode, rttMs, queryMs) {
  const trips = mode === "n+1" ? items + 1 : mode === "in" ? 2 : 1;
  return Math.round(trips * (rttMs + queryMs) * 10) / 10;
}`}
  tests={[
    { label: "같은 데이터 센터, N+1", args: [20, "n+1", 0.1, 0.5], expected: 12.6 },
    { label: "다른 가용 영역, N+1", args: [20, "n+1", 1, 0.5], expected: 31.5 },
    { label: "다른 가용 영역, IN", args: [20, "in", 1, 0.5], expected: 3 },
    { label: "다른 가용 영역, JOIN", args: [20, "join", 1, 0.5], expected: 1.5 },
    { label: "항목 100개, N+1", args: [100, "n+1", 1, 0.5], expected: 151.5 },
    { label: "DB가 다른 리전, N+1", args: [100, "n+1", 30, 0.5], expected: 3080.5 },
  ]}
/>

마지막 줄이 극단적인 경우다. DB가 다른 리전(RTT 30ms)에 있는데 N+1로 100개를 그리면 화면 하나에 3초가 넘는다. 웹 서버와 DB는 가까이 두고, 왕복 횟수는 적게 유지한다. 이 두 가지가 계층을 나눈 뒤의 기본 규칙이다.

## 연결도 이제 세어야 한다

네트워크를 건너면 연결을 맺는 비용도 커진다. PostgreSQL은 연결 하나마다 서버에 프로세스를 하나 띄우고, TLS까지 쓰면 연결을 여는 데 왕복이 여러 번 든다. 요청마다 연결을 새로 열면 그 비용을 매번 낸다.

그래서 웹 앱은 연결을 미리 몇 개 열어 두고 돌려 쓰는 커넥션 풀을 쓴다. 이때 계산이 하나 생긴다. 웹 서버가 나중에 여러 대가 되면, 서버 수 × 서버당 풀 크기가 DB의 `max_connections`(기본값 100)를 넘으면 안 된다. 웹 서버 4대가 각각 풀 30개를 잡으면 120개라서 이미 넘는다. 풀 크기를 정하는 법과 PgBouncer 같은 중간 풀은 [커넥션 풀 글](/posts/connection-pool)에서 자세히 본다.

## DB를 옮기는 김에 종류도 고른다

DB 서버를 따로 세우는 시점은 어떤 DB를 쓸지 다시 생각해 볼 좋은 때다. 크게 두 갈래가 있다.

관계형 DB(RDBMS)는 데이터를 행과 열로 된 테이블에 나눠 담고, 테이블끼리 키로 연결한다. SQL로 묻고, JOIN으로 여러 테이블을 묶는다. PostgreSQL, MySQL이 대표적이다. 맛집 앱의 데이터를 보면 이 모양이 자연스럽다.

```sql
-- 식당, 사용자, 리뷰. 리뷰는 식당과 사용자를 가리킨다
CREATE TABLE users (id int PRIMARY KEY, name text NOT NULL);
CREATE TABLE restaurants (id int PRIMARY KEY, name text NOT NULL, area text NOT NULL);
CREATE TABLE reviews (
  id serial PRIMARY KEY,
  restaurant_id int NOT NULL REFERENCES restaurants(id),  -- 없는 식당은 가리킬 수 없다
  user_id int NOT NULL REFERENCES users(id),
  stars int NOT NULL CHECK (stars BETWEEN 1 AND 5),       -- 별점은 1~5만
  body text
);
SELECT id, name, area FROM restaurants WHERE id <= 3 ORDER BY id;
```

```text
 id |    name     |  area
----+-------------+--------
  1 | 을지로 국수 | 중구
  2 | 성수 버거   | 성동구
  3 | 망원 만두   | 마포구
(3 rows)
```

식당별 평균 별점처럼 여러 테이블을 엮는 질문은 JOIN 한 번이면 된다.

```sql
-- 식당과 리뷰를 묶어 식당별 리뷰 수와 평균 별점을 구한다
SELECT r.name, r.area, count(*) AS reviews, round(avg(v.stars), 2) AS avg_stars
FROM restaurants r
JOIN reviews v ON v.restaurant_id = r.id
WHERE r.id <= 3
GROUP BY r.id, r.name, r.area
ORDER BY avg_stars DESC;
```

```text
    name     |  area  | reviews | avg_stars
-------------+--------+---------+-----------
 망원 만두   | 마포구 |     200 |      4.01
 성수 버거   | 성동구 |     200 |      3.00
 을지로 국수 | 중구   |     200 |      2.01
(3 rows)
```

관계형 DB가 기본값인 이유는 하나 더 있다. 잘못된 데이터를 DB가 막아 준다. 없는 식당에 리뷰를 달거나 별점 7을 넣으면 거절한다.

```sql
INSERT INTO reviews (restaurant_id, user_id, stars) VALUES (999, 1, 5);  -- 없는 식당
INSERT INTO reviews (restaurant_id, user_id, stars) VALUES (1, 1, 7);    -- 범위를 벗어난 별점
```

```text
ERROR:  insert or update on table "reviews" violates foreign key constraint "reviews_restaurant_id_fkey"
DETAIL:  Key (restaurant_id)=(999) is not present in table "restaurants".
ERROR:  new row for relation "reviews" violates check constraint "reviews_stars_check"
DETAIL:  Failing row contains (4002, 1, 1, 7, null).
```

두 번째 줄의 `4002`는 첫 번째 INSERT가 실패하면서도 번호 4001을 써 버렸기 때문이다. PostgreSQL의 `serial` 번호는 실패한 트랜잭션에서도 되돌아가지 않아서 중간에 빈 번호가 생긴다. 번호가 연속이라고 믿는 코드는 이 때문에 틀린다.

다른 갈래는 NoSQL, 관계형이 아닌 DB들이다. 한 가지 접근 방식에 특화해서 그것을 아주 빠르게, 아주 크게 하는 대신 JOIN이나 제약 조건 같은 것을 덜어 낸다. 대표적인 네 종류가 있다.

- 키-값 저장소(Redis, DynamoDB)는 키 하나로 값을 넣고 꺼내는 것만 한다. 대신 아주 빠르다. 세션, 캐시, 장바구니가 잘 맞는다.
- 문서 DB(MongoDB)는 JSON 같은 문서를 통째로 저장한다. 식당 하나에 메뉴와 영업시간을 함께 넣어 두고 한 번에 읽을 때 편하다.
- 와이드 컬럼 DB(Cassandra)는 엄청난 양의 쓰기를 여러 서버에 나눠 받는 데 강하다. 채팅 메시지나 활동 기록이 맞다.
- 그래프 DB(Neo4j)는 "친구의 친구가 간 식당"처럼 관계를 여러 단계 따라가는 질문에 강하다.

NoSQL을 고려할 만한 신호는 이런 것들이다. 응답이 몇 ms 안에 나와야 하고 키 하나로만 꺼낸다. 데이터에 관계가 거의 없거나 모양이 제각각이다. 데이터를 받아 그대로 저장했다가 그대로 돌려주기만 한다(JSON을 넣고 JSON을 꺼낸다). 데이터 양이 서버 한 대로는 감당이 안 될 만큼 크다.

반대로 맛집 앱처럼 식당, 사용자, 리뷰가 서로 얽혀 있고 "마포구에서 별점 4 이상인 식당의 최근 리뷰" 같은 질문을 나중에 새로 만들 일이 많다면 관계형이 맞다. 처음부터 모든 질문을 알 수는 없기 때문이다. 실무에서는 원본을 관계형 DB에 두고, 필요할 때 Redis나 검색 엔진 같은 다른 저장소를 옆에 붙이는 경우가 많다. 종류별로 더 깊이 보고 싶다면 [DB 종류 한눈에](/posts/db-types-overview)에서 시작해 [관계형 DB](/posts/db-type-relational), [키-값 DB](/posts/db-type-key-value), [MongoDB 문서 모델](/posts/mongodb-document-model)로 이어 가면 된다.

## 더 큰 서버냐, 더 많은 서버냐

DB를 나눴는데도 사용자가 계속 는다. 이제 서버를 키워야 하는데, 방법은 두 가지다.

수직 확장(scale up)은 서버를 더 좋은 것으로 바꾸는 것이다. CPU 코어를 늘리고, 메모리를 늘리고, 더 빠른 디스크를 단다. 코드를 하나도 안 고쳐도 된다. 클라우드라면 인스턴스 종류를 바꾸고 재시작하면 끝이다.

수평 확장(scale out)은 같은 서버를 여러 대 두는 것이다. 한 대가 받던 요청을 여러 대가 나눠 받는다. 대신 요청을 나눠 줄 장치가 필요하고, 서버들이 서로 같은 데이터를 보게 만드는 문제가 생긴다.

수직 확장은 단순해서 초반에 가장 먼저 쓰는 처방이다. 하지만 한계가 두 가지 있다. 하드웨어에는 끝이 있고, 큰 기종일수록 가격이 가파르게 오른다. 더 큰 문제는 아무리 커도 한 대라는 것이다. 그 한 대가 고장 나면 서비스가 멈추고, 키우려고 재시작하는 동안에도 멈춘다.

수평 확장은 끝이 없고 한 대가 빠져도 나머지가 버틴다. 다만 쉬운 곳과 어려운 곳이 있다. 웹 서버는 요청을 받아 DB에 묻고 답할 뿐 데이터를 들고 있지 않으면 똑같은 서버를 몇 대든 늘릴 수 있다. DB는 데이터를 들고 있어서 여러 대가 같은 데이터를 맞추는 문제가 따라온다. 그래서 순서가 보통 이렇다. 웹은 옆으로 늘리고, DB는 위로 키우다가, 읽기는 복제본으로 나누고, 쓰기까지 넘치면 샤딩으로 쪼갠다.

두 방식을 숫자로 비교하는 법(암달의 법칙, 늘린 만큼 빨라지지 않는 이유)은 [수평 확장과 수직 확장 글](/posts/scaling-horizontal-vertical)에 있다. 이 시리즈에서는 웹 서버를 옆으로 늘리는 일을 [③ 로드 밸런서와 무상태 웹](/posts/sd-load-balancer-stateless)에서, DB 읽기를 나누는 일을 [④ DB 복제](/posts/sd-db-replication-intro)에서, 쓰기를 쪼개는 일을 [⑧ 샤딩 입문](/posts/sd-sharding-intro)에서 한다.

## 나눈 뒤에 자주 하는 실수

DB를 나눈 뒤에 생기는 문제는 대부분 "같은 서버에 있을 때는 몰랐던 것"이다.

웹 서버와 DB를 다른 가용 영역이나 다른 리전에 둔다. 장애에 강해 보이지만 쿼리마다 RTT가 붙는다. 기본은 같은 영역에 두고, 영역 장애 대비는 DB 복제로 한다.

쿼리 타임아웃을 안 건다. 같은 서버일 때는 연결이 끊길 일이 거의 없었지만 이제 네트워크가 끊길 수 있다. 타임아웃이 없으면 응답 없는 DB를 기다리는 요청이 쌓여 웹 서버까지 멈춘다. 연결 타임아웃과 쿼리 타임아웃(`statement_timeout`)을 모두 정한다. 값을 고르는 법은 [타임아웃 글](/posts/timeouts)에 있다.

DB를 인터넷에 연다. 관리 편하자고 5432를 `0.0.0.0/0`에 열어 두면 몇 분 안에 무작위 로그인 시도가 들어온다. DB는 사설망에만 두고, 사람이 접속할 때는 배스천 서버나 VPN을 거친다.

DB 서버를 나눴으니 이제 안전하다고 생각한다. DB는 여전히 한 대다. 서버가 하나 늘었을 뿐 단일 장애 지점은 그대로다.

## 이어서 읽을 글

다음 글 [③ 로드 밸런서와 무상태 웹](/posts/sd-load-balancer-stateless)에서는 옆으로 늘리기 쉬운 웹 계층부터 여러 대로 만든다. 앞에서 요청을 나눠 주는 로드 밸런서를 붙이고, 웹 서버가 "데이터를 들고 있지 않아야" 하는 이유를 로그인 세션으로 직접 확인한다.

DB를 따로 떼면 웹과 DB가 서로의 자원을 빼앗지 않고, 각자 맞는 기종으로 따로 키울 수 있고, DB를 안쪽 망에 숨길 수 있다. 대가는 쿼리마다 건너는 네트워크다. 왕복 횟수를 줄이고, 둘을 가까이 두고, 연결과 타임아웃을 관리하는 일이 새로 생긴다.

## 면접에서 나올 만한 질문

### 웹 서버와 DB를 분리하는 이유는 무엇인가요?

같은 서버에서 CPU, 메모리, 디스크를 다투지 않게 하고 각자 따로 키우기 위해서다. 집계 쿼리가 DB CPU를 다 써도 웹 서버는 영향을 덜 받고, 메모리 부족으로 DB가 강제 종료되는 일도 줄어든다. DB를 사설망에 두고 웹 서버에서 오는 접속만 받게 해 보안도 좋아진다.

### 분리하면 무엇이 나빠지나요?

쿼리마다 네트워크 왕복 시간이 붙는다. 데모에서 왕복이 약 2.5ms 늘자 쿼리 21번짜리 화면은 52ms 느려졌고, JOIN 한 번짜리 화면은 2ms만 느려졌다. 그래서 N+1 쿼리를 없애고 웹 서버와 DB를 같은 영역에 둔다. 연결 비용도 커져서 커넥션 풀과 타임아웃을 함께 설계해야 한다.

### 관계형 DB와 NoSQL은 어떻게 고르나요?

데이터를 어떤 모양으로 꺼내는지로 고른다. 여러 엔터티가 얽혀 있고 JOIN과 트랜잭션, 제약 조건이 필요하면 관계형이 기본값이다. 키 하나로만 아주 빠르게 꺼내거나, 관계가 거의 없는 데이터를 대량으로 쓰거나, 서버 한 대를 넘는 양을 저장해야 하면 NoSQL을 고려한다. 실무에서는 원본을 관계형에 두고 캐시나 검색용 저장소를 옆에 붙이는 조합이 흔하다.

### 수직 확장과 수평 확장의 차이와 각각의 한계는요?

수직 확장은 서버를 더 좋은 것으로 바꾸는 것이라 코드 변경 없이 바로 효과가 나지만, 하드웨어에 끝이 있고 비싸지며 여전히 한 대라 장애에 약하다. 수평 확장은 서버를 여러 대로 늘려 한계가 없고 한 대가 빠져도 버티지만, 요청을 나눠 줄 장치와 서버 간 데이터 일관성 문제가 생긴다. 상태가 없는 웹 계층은 수평 확장이 쉽고, 데이터를 가진 DB는 수직 확장 후 복제와 샤딩으로 넘어가는 순서가 일반적이다.

### DB를 옮긴 뒤 웹 서버에서 DB 연결이 안 됩니다. 무엇부터 보나요?

`pg_isready`로 DB가 연결을 받는지부터 본다. `no response`면 방화벽, `listen_addresses`, 라우팅처럼 네트워크 쪽이고, `accepting connections`인데 실패하면 계정, 비밀번호, `pg_hba.conf` 규칙 쪽이다. 이렇게 네트워크 문제와 인증 문제를 먼저 나누면 찾을 범위가 크게 준다.

### 트래픽이 10배가 되면 DB 쪽에서는 무엇부터 하나요?

먼저 화면당 쿼리 수와 느린 쿼리를 줄인다. 같은 기종에서 공짜로 얻는 개선이다. 그다음 수직 확장으로 시간을 벌고, 읽기가 대부분이면 복제본으로 읽기를 나누고 캐시를 앞에 둔다. 웹 서버가 늘어나면 연결 수가 `max_connections`를 넘지 않게 풀 크기를 다시 계산한다. 쓰기까지 한 대를 넘으면 그때 샤딩을 검토한다.

### DB 서버가 죽으면 어떻게 되나요?

분리만 했다면 DB는 여전히 단일 장애 지점이라 읽기와 쓰기가 모두 멈춘다. 웹 서버는 살아 있지만 할 수 있는 일이 거의 없고, 타임아웃이 없으면 기다리는 요청이 쌓여 웹 서버까지 응답을 못 하게 된다. 해결은 복제본을 두고 주 DB가 죽으면 복제본을 승격하는 구조이고, 그 전까지는 백업에서 복원하는 것이 유일한 길이다.
