<EasyIntro>
  메모리 한도가 256MB인 곳에서 프로그램이 1GB를 달라고 했는데 성공했다. 그러고는 받은 메모리를 채워 나가다가 한도에 닿는 순간 갑자기 죽었다. 달라고 할 때는 되고 쓸 때 죽는다는 게 이상해 보이지만, 리눅스는 원래 그렇게 돌아간다.

  리눅스는 메모리를 달라는 프로그램에게 진짜 메모리가 아니라 상품권을 준다. 프로그램은 자기만의 넓은 주소 공간을 받고, 그 주소를 처음 실제로 쓰는 순간에야 커널이 끼어들어 진짜 메모리 한 조각을 연결해 준다. 어떤 주소가 어떤 실제 메모리에 연결됐는지는 페이지 테이블이라는 표에 적어 두고, CPU는 자주 쓰는 변환 결과를 작은 메모장에 외워 둬서 매번 표를 뒤지지 않는다.

  상품권은 가진 메모리보다 많이 발행할 수 있어서, 모두가 한꺼번에 쓰려 들면 커널은 돌려줄 수 없다고 말하는 대신 누군가를 죽여 자리를 만든다. 그래서 메모리 문제를 볼 때는 약속한 양이 아니라 실제로 쓰는 양, 그리고 커널이 남긴 기록을 봐야 한다.
</EasyIntro>

메모리 한도를 256MiB로 건 cgroup 안에서 C 프로그램 하나가 `malloc(1 GiB)`를 불렀다. 한도의 네 배를 달라고 했으니 실패해야 할 것 같은데 성공했다. 프로그램은 받은 메모리를 64MiB씩 채우기 시작했고, 192MiB를 채웠다는 로그를 마지막으로 소리 없이 죽었다. 종료 코드는 137이었다.

```text
malloc(1 GiB) ok
touched   64 MiB
touched  128 MiB
touched  192 MiB
/bin/bash: line 27:  4331 Killed                  bash -c "echo \$\$ > $CG/cgroup.procs; exec ./hog"
exit=137
```

할당은 성공했는데 쓰다가 죽는다. 이 순서가 이상하게 느껴진다면 리눅스가 메모리를 "주는 것"과 "실제로 내주는 것"을 따로 한다는 걸 아직 모르는 것이다. 이 글은 그 사이에서 일어나는 일을 따라간다. 프로세스마다 따로 보는 주소 공간, 그 주소를 실제 메모리로 바꾸는 페이지 테이블과 TLB, 처음 만질 때 끼어드는 page fault, 넉넉하게 약속하는 overcommit, 약속을 못 지킬 때 나서는 OOM killer까지 간다.

실습은 Ubuntu 24.04 사용자 공간에 6.18 커널이 올라간 x86-64 가상 머신(4코어, 램 16GiB, 스왑 없음)에서 했다. 22.04의 5.15 커널도 여기서 다루는 동작은 같다. C 예제는 `gcc`로, 페이지 폴트 수는 `perf stat`과 `getrusage()`로 셌다.

## 프로세스마다 따로 보는 주소

프로그램이 다루는 주소는 메모리 칩의 실제 위치가 아니다. 프로세스마다 자기만의 가상 주소 공간이 있고, 커널과 CPU가 그 주소를 그때그때 물리 메모리 위치로 바꿔 준다. 그래서 두 프로세스가 같은 주소 `0x7fff...`를 써도 서로 다른 메모리를 본다. 남의 메모리를 실수로 덮어쓸 수 없는 것도, 실행 파일을 몇 개를 띄우든 같은 주소에서 시작하는 것처럼 보이는 것도 이 덕분이다.

주소 공간이 어떻게 생겼는지는 `/proc/<PID>/maps`에 다 나온다. 코드, 전역 변수, `malloc`한 힙, `mmap`한 64MiB, 지역 변수의 주소를 찍고 멈춰 있는 프로그램을 띄워서 봤다.

```bash
# 주소를 찍고 pause()로 멈춰 있는 프로그램
gcc -O0 -o layout layout.c && ./layout &

# 그 프로세스의 주소 공간 지도 (경로는 ./layout으로 줄였다)
cat /proc/$!/maps
```

```text
code  main   0x5648604b81e9
data  g      0x5648604bb010
heap  malloc 0x5648631a52a0
mmap  64MiB  0x7fcacf400000
stack local  0x7fff8bb10c74
5648604b7000-5648604b8000 r--p 00000000 fe:00 1828804                    ./layout
5648604b8000-5648604b9000 r-xp 00001000 fe:00 1828804                    ./layout
5648604bb000-5648604bc000 rw-p 00003000 fe:00 1828804                    ./layout
5648631a5000-5648631c6000 rw-p 00000000 00:00 0                          [heap]
7fcacf400000-7fcad3400000 rw-p 00000000 00:00 0 
7fcad3428000-7fcad35b1000 r-xp 00028000 fe:00 211544                     /usr/lib/x86_64-linux-gnu/libc.so.6
7fff8baf1000-7fff8bb14000 rw-p 00000000 00:00 0                          [stack]
```

한 줄이 하나의 영역(VMA)이다. 앞은 시작과 끝 주소, 그다음 `r-xp` 같은 권한(읽기·쓰기·실행, `p`는 private), 파일 오프셋, 장치, inode, 파일 경로다. 코드 영역은 `r-x`라서 쓰려고 하면 SIGSEGV가 나고, 스택과 힙은 `rw-`라서 실행할 수 없다. 경로가 빈 영역은 파일에 매이지 않은 익명 메모리다. 64MiB짜리 `mmap`이 그렇다. 출력은 여기서 몇 줄 줄였다. 원래는 libc와 동적 로더가 영역을 다섯 개씩 갖는다.

이 영역들은 "여기를 써도 된다"는 예약일 뿐이다. 같은 프로세스를 `/proc/<PID>/status`로 보면 차이가 드러난다.

```bash
grep -E "VmSize|VmRSS|VmPTE" /proc/$!/status
```

```text
VmSize:	   68236 kB
VmRSS:	    1728 kB
VmPTE:	      40 kB
```

예약한 주소 공간(`VmSize`, `ps`의 VSZ)은 67MiB인데 물리 메모리에 올라온 양(`VmRSS`)은 1.7MiB다. 64MiB를 `mmap`했지만 아직 한 바이트도 쓰지 않았으니 커널은 실제 메모리를 하나도 주지 않았다. `VmPTE`는 이 프로세스의 페이지 테이블이 차지하는 메모리다. 이게 무엇인지가 다음 이야기다.

## 주소 하나를 네 번 나눠 찾는다

가상 주소를 물리 주소로 바꾸는 표가 페이지 테이블이다. 바이트마다 표를 두면 표가 메모리보다 커지니까, 메모리를 4KiB짜리 페이지로 잘라 페이지 단위로 짝을 적는다. 주소의 아래 12비트(2^12 = 4096)는 페이지 안의 위치라 그대로 쓰고, 나머지 위쪽 비트로 "몇 번째 페이지인가"만 찾으면 된다.

그래도 48비트 주소 공간이면 페이지가 2^36개, 680억 개다. 한 칸에 8바이트씩 평평한 표로 만들면 프로세스마다 512GiB가 필요하다. 그래서 x86-64는 표를 4단으로 쪼갠다. 위쪽 36비트를 9비트씩 네 조각으로 나누고, 조각마다 512칸(9비트)짜리 표를 하나씩 거친다. 한 표가 512칸 × 8바이트 = 4KiB라서 표 자체도 페이지 한 장에 딱 들어간다. 쓰지 않는 구역의 아래 표는 만들지 않아도 되니, 듬성듬성 쓰는 주소 공간에서도 표가 작게 유지된다. 앞에서 본 `VmPTE: 40 kB`가 그 결과다.

## 변환 결과를 기억하는 TLB

메모리 한 번 읽는 데 표를 네 번 읽어야 한다면 모든 접근이 다섯 배 느려진다. 그래서 CPU 코어마다 최근에 쓴 변환 결과(가상 페이지 번호 → 물리 프레임 번호)를 담아 두는 작은 캐시가 있다. 이게 TLB(Translation Lookaside Buffer)다. TLB에 있으면 페이지 워크 없이 바로 물리 주소가 나오고, 없으면(TLB miss) 위의 네 단계를 밟는다. 칸 수는 CPU마다 다른데 1단 TLB는 수십 칸, 2단은 천 칸 남짓이다.

1,500칸 × 4KiB면 6MiB 정도다. 그보다 넓은 범위를 무작위로 돌아다니는 프로그램은 TLB miss를 계속 낸다. 큰 해시 테이블, 그래프 탐색, 큰 힙을 훑는 GC가 그런 일을 한다. [지연 시간 숫자 글](/posts/sd-latency-numbers)에서 JavaScript 배열의 무작위 접근이 메모리 표의 100ns보다 느리게 나온 이유 중 하나가 이것이다.

문맥 교환 때도 TLB가 문제가 된다. 프로세스가 바뀌면 같은 가상 주소가 다른 물리 주소를 뜻하니 예전 변환을 버려야 한다. 요즘 CPU와 리눅스는 PCID라는 꼬리표를 붙여 프로세스별 항목을 구분하므로 전부 비우지는 않는다. 그래도 같은 코어에서 프로세스를 자주 바꾸면 캐시와 TLB가 식는 비용은 남는다.

`perf stat -e dTLB-load-misses`로 miss를 직접 세려 했지만 이 가상 머신은 하드웨어 성능 카운터를 넘겨주지 않아서 `<not supported>`가 나왔다. 물리 서버라면 이 이벤트로 바로 셀 수 있다. 대신 다음 절에서 시간으로 차이를 잰다.

## 큰 페이지로 TLB 칸을 아낀다

TLB 칸 수를 늘릴 수 없다면 칸 하나가 맡는 범위를 넓히면 된다. 페이지 워크의 PD 단계에서 멈추면 페이지 하나가 2MiB가 되고, PDPT에서 멈추면 1GiB가 된다. 2MiB 페이지 하나가 4KiB 페이지 512장을 대신하니, 같은 TLB로 512배 넓은 범위를 덮는다.

리눅스에서 큰 페이지를 쓰는 길은 두 가지다.

- hugetlbfs: 부팅 때나 `vm.nr_hugepages`로 큰 페이지를 미리 떼어 둔다. 떼어 둔 만큼은 다른 용도로 못 쓰고 스왑되지도 않는다. PostgreSQL의 `huge_pages = try`, 큰 JVM 힙의 `-XX:+UseLargePages`가 이 방식을 쓴다.
- Transparent Huge Pages(THP): 커널이 알아서 2MiB 페이지를 붙여 준다. `/sys/kernel/mm/transparent_hugepage/enabled`가 `always`면 모든 익명 메모리에, `madvise`면 프로그램이 `madvise(MADV_HUGEPAGE)`로 부탁한 영역에만 쓴다.

```bash
# THP 정책 (대괄호가 현재 값). 배포판과 커널 설정마다 기본값이 다르다
cat /sys/kernel/mm/transparent_hugepage/enabled

# 지금 THP로 잡힌 익명 메모리 총량
grep AnonHugePages /proc/meminfo
```

```text
always [madvise] never
AnonHugePages:         0 kB
```

이 머신은 `madvise`다. 1GiB 배열을 만들고 무작위 위치를 2천만 번 따라가는 C 프로그램을, 4KiB 페이지(`MADV_NOHUGEPAGE`)와 2MiB 페이지(`MADV_HUGEPAGE`)로 세 번씩 돌렸다. 한 번 읽은 값이 다음 위치를 정해서 CPU가 미리 읽어 둘 수 없게 했다.

```bash
gcc -O2 -o tlb tlb.c
for i in 1 2 3; do ./tlb; ./tlb huge; done
```

```text
4KiB pages: 235.9 ns per random read
2MiB pages: 169.3 ns per random read
4KiB pages: 268.7 ns per random read
2MiB pages: 186.1 ns per random read
4KiB pages: 235.1 ns per random read
2MiB pages: 179.4 ns per random read
```

같은 코드, 같은 데이터인데 큰 페이지 쪽이 25~30% 빠르다. 바뀐 건 주소 변환 비용뿐이다. 가상 머신에서는 게스트 페이지 테이블 위에 하이퍼바이저의 페이지 테이블(EPT)이 한 겹 더 있어 TLB miss가 더 비싸다. 물리 서버에서는 차이가 이보다 작게 나올 수 있다.

그렇다고 THP를 `always`로 켜면 끝나는 이야기는 아니다. 2MiB짜리 연속된 물리 메모리를 찾느라 커널이 메모리를 정리(compaction)하면서 할당이 수 ms씩 멈추기도 하고, 백그라운드의 `khugepaged`가 작은 페이지를 모아 합치는 일도 CPU를 쓴다. 조금만 쓰는 영역에도 2MiB를 통째로 잡으니 RSS가 불어나기도 한다. Redis가 시작할 때 THP가 켜져 있다고 경고하는 것도, fork 뒤 copy-on-write가 4KiB가 아니라 2MiB 단위로 일어나 지연과 메모리가 함께 튀기 때문이다. 큰 힙을 오래 쓰는 프로세스(JVM, DB)에는 득이 되고, 작은 할당을 자주 하고 fork하는 프로세스에는 독이 되기 쉽다. 그래서 `madvise`로 두고 원하는 프로그램만 쓰게 하는 쪽이 무난하다.

## 처음 만질 때 커널이 끼어든다

`malloc(1 GiB)`가 성공한 이유로 돌아가자. 커널은 `mmap`이나 `brk`로 주소 공간을 늘려 줄 때 VMA만 만들고 페이지 테이블 칸은 비워 둔다. 프로그램이 그 주소를 처음 읽거나 쓰는 순간, MMU는 PTE의 present 비트가 꺼져 있는 걸 보고 예외를 일으킨다. 이게 page fault다. 커널의 fault 핸들러가 깨어나 주소가 VMA 안인지 확인하고, 빈 프레임을 하나 0으로 채워 PTE에 연결한 다음, 멈췄던 명령을 다시 실행시킨다. 프로그램은 아무 일도 없었던 것처럼 이어서 돈다. 요청할 때 주지 않고 쓸 때 주는 이 방식을 demand paging이라고 한다.

VMA 밖의 주소였다면 커널은 프레임을 주지 않고 SIGSEGV를 보낸다. 권한이 맞지 않는 접근(읽기 전용 영역에 쓰기)도 같다. segmentation fault도 결국 page fault를 커널이 "이건 정당하지 않다"고 판정한 결과다.

256MiB를 `mmap`하고 절반, 전부, 그리고 한 번 더 만지며 RSS와 fault 수를 찍어 봤다.

```bash
gcc -O1 -o touch touch.c
./touch        # 4KiB 페이지
./touch huge   # MADV_HUGEPAGE
```

```text
after mmap : RSS   1404 kB, minor faults +0
half touch : RSS 132808 kB, minor faults +32781
full touch : RSS 263880 kB, minor faults +65549
touch again: minor faults +0
---
after mmap : RSS   1408 kB, minor faults +0
half touch : RSS 132812 kB, minor faults +76
full touch : RSS 263884 kB, minor faults +140
touch again: minor faults +0
AnonHugePages:    262144 kB
```

`mmap` 직후 RSS는 그대로다. 4KiB 페이지로는 256MiB / 4KiB = 65,536번 fault가 났고(여분 13번은 `printf`와 `/proc` 읽기 몫이다), RSS가 그만큼 올랐다. 이미 연결된 페이지를 다시 만지면 fault가 0이다. 큰 페이지로는 같은 양에 fault가 140번이다. 256MiB / 2MiB = 128번에 몇 번이 더해졌다. fault 한 번에 2MiB를 연결하니 fault 처리 비용도 512분의 1로 준다.

여기서 센 건 모두 minor fault다. 페이지를 디스크에서 읽어 올 필요 없이 메모리 안에서 해결된 fault라는 뜻이다. 처음 만지는 익명 메모리(0으로 채운 프레임을 붙이면 끝), 이미 페이지 캐시에 있는 파일 페이지, 아래에서 볼 copy-on-write가 여기에 들어간다.

## 디스크까지 가야 하는 major fault

첫 번째는 캐시가 비어 있었는데도 major fault가 한 번뿐이다. 커널이 순차로 읽는 걸 알아채고 뒤쪽 페이지를 미리 읽어(readahead) 두기 때문에, 나머지 fault는 이미 캐시에 들어온 페이지를 연결하는 minor fault로 끝났다. fault 한 번에 주변 페이지를 여러 장 함께 연결해서 fault 수(1,090)도 페이지 수(32,768)보다 훨씬 적다. 두 번째는 캐시가 찬 상태라 4ms다.

세 번째가 무작위 접근의 모습이다. `MADV_RANDOM`으로 미리 읽기를 끄자 페이지마다 major fault가 나서 32,768번, 1.7초가 걸렸다. 같은 128MiB인데 캐시에 있을 때보다 380배 느리다. 페이지 캐시가 무엇이고 언제 채워지고 비워지는지는 [페이지 캐시와 디스크 I/O 글](/posts/page-cache-disk-io)에서 따로 다룬다.

## fork 뒤에 쓰면 그때 복사한다

`fork()`는 부모의 주소 공간을 자식에게 그대로 복제한다. 그런데 수 GiB짜리 프로세스를 fork할 때마다 메모리를 다 복사하면 느리고 낭비다. 리눅스는 페이지 테이블만 복사하고, 양쪽 PTE를 모두 읽기 전용으로 바꿔 같은 프레임을 가리키게 둔다. 어느 쪽이든 쓰려고 하면 권한 위반 fault가 나고, 커널은 그 페이지 한 장만 복사해 쓰는 쪽에 새 프레임을 준다. copy-on-write다.

```bash
# 64MiB를 채운 부모가 fork하고, 자식이 그 메모리를 읽은 뒤 쓴다
gcc -O1 -o cow cow.c && ./cow
```

```text
child read  64MiB: minor faults +0
child write 64MiB: minor faults +16384
```

읽기만 할 때는 fault가 없다. 페이지 테이블을 복사할 때 이미 연결해 뒀기 때문이다. 쓰기를 시작하자 64MiB / 4KiB = 16,384번 fault가 나며 한 장씩 복사됐다. Redis의 `BGSAVE`가 이 원리에 기대고, 저장 중에 쓰기가 많으면 메모리가 늘어나는 이유도 같다. 그 이야기는 [Redis 영속성 글](/posts/redis-persistence-ha)에 있다.

## 커널은 약속을 넉넉하게 한다

demand paging이 있으니 커널은 실제 메모리보다 많은 주소 공간을 내줄 수 있다. 대부분의 프로그램은 받은 걸 다 쓰지 않기 때문이다. 스레드 스택은 8MiB씩 예약하지만 몇 KiB만 쓰고, 런타임은 힙을 넉넉하게 예약해 둔다. 쓰지도 않을 메모리 때문에 할당을 거절하면 멀쩡한 프로그램이 못 뜬다. 그래서 리눅스는 기본적으로 약속을 넉넉하게 한다. 이게 overcommit이다.

정책은 `vm.overcommit_memory`가 정한다.

- `0` (기본값): 휴리스틱. 한 번에 램과 스왑을 합친 것보다 큰, 누가 봐도 무리한 요청만 거절한다.
- `1`: 무조건 허락한다. 메모리를 크게 예약하고 듬성듬성 쓰는 프로그램(일부 과학 계산, Redis의 fork)에 쓴다.
- `2`: 엄격. 약속한 총량(`Committed_AS`)이 `CommitLimit` = 스왑 + 램 × `overcommit_ratio`/100(기본 50)을 넘으면 거절한다.

16GiB 램에 기본값 0인 이 머신에서 8GiB를 세 번, 20GiB를 한 번 요청했다.

```bash
cat /proc/sys/vm/overcommit_memory   # 0
./over 8 8 8 20
```

```text
malloc( 8 GiB) -> ok, RSS 1528 kB
malloc( 8 GiB) -> ok, RSS 1744 kB
malloc( 8 GiB) -> ok, RSS 1748 kB
malloc(20 GiB) -> NULL, RSS 1748 kB
CommitLimit:     8239712 kB
Committed_AS:   26482716 kB
```

8GiB 세 번은 다 받았다. 램보다 많은 24GiB를 약속했는데 RSS는 1.7MiB 그대로다. `Committed_AS`가 25GiB를 넘어 `CommitLimit`의 세 배인데도 모드 0은 이 숫자를 강제하지 않는다. 한 번에 20GiB를 달라는 요청만 "램 16GiB로는 말이 안 된다"며 거절했다. `CommitLimit` 8,239,712kB는 스왑이 없으니 `MemTotal` 16,479,424kB의 정확히 50%다. 모드 2였다면 첫 번째 8GiB부터 거절됐을 것이다.

이제 처음 장면이 설명된다. cgroup의 메모리 한도는 "할당할 때"가 아니라 "페이지를 실제로 받을 때" 검사된다. `malloc(1 GiB)`는 주소 공간만 늘렸으니 통과하고, page fault로 프레임을 받을 때마다 cgroup 사용량이 올라가다 256MiB에 닿은 순간 커널이 프로세스를 죽였다.

overcommit의 대가가 이것이다. `malloc`이 NULL을 돌려주면 프로그램이 대응할 수 있지만, 이미 받은 주소를 만지다가 메모리가 없으면 돌려줄 방법이 없다. 커널은 누군가를 죽여 자리를 만든다. 모드 2로 바꾸면 이 일이 할당 시점의 실패로 바뀌는 대신, 넉넉하게 예약하는 프로그램(JVM, 브라우저, 언어 런타임 다수)이 램이 남는데도 못 뜨는 일이 생긴다. 서버 대부분이 기본값 0으로 두고, 대신 cgroup 한도와 모니터링으로 다루는 이유다.

## 메모리가 모자라면 먼저 느려진다

OOM kill은 메모리가 부족할 때 가장 먼저 일어나는 일이 아니라 마지막에 일어나는 일이다. 램이 빠듯해지면 커널은 먼저 회수(reclaim)를 한다. 다시 읽을 수 있는 페이지부터 버린다. 디스크와 내용이 같은 깨끗한 파일 페이지(실행 파일 코드, 읽기만 한 데이터)는 그냥 버리고, 고친 파일 페이지는 디스크에 쓴 뒤 버린다. 익명 메모리는 스왑이 있어야 내보낼 수 있다. 백그라운드에서는 `kswapd`가, 급하면 할당하려던 프로세스가 직접 이 일을 한다.

문제는 버린 페이지를 곧바로 다시 쓰는 경우다. 프로그램 코드나 자주 읽는 파일이 밀려나면 다음 접근이 major fault가 되고, 읽어 오는 동안 또 다른 페이지가 밀려난다. 이게 thrashing이다. 스왑이 없어도 파일 페이지만으로 일어난다.

160MiB 한도 cgroup에서 익명 메모리 128MiB를 잡고 64MiB 파일을 미리 읽기 없이 세 번 훑어 봤다. 비교로 512MiB 한도에서도 같은 일을 했다.

```bash
# cgroup v1 메모리 컨트롤러 (v2라면 memory.max)
sudo mkdir /sys/fs/cgroup/memory/lx2thr
echo $((160<<20)) | sudo tee /sys/fs/cgroup/memory/lx2thr/memory.limit_in_bytes
bash -c 'echo $$ > /sys/fs/cgroup/memory/lx2thr/cgroup.procs; exec ./thrash f64.bin 128'
```

```text
limit 512MiB
anon 128 MiB touched
pass 1: majflt +16384, 1170 ms
pass 2: majflt +    0,    1 ms
pass 3: majflt +    0,    0 ms
limit 160MiB
anon 128 MiB touched
pass 1: majflt +16384, 1248 ms
pass 2: majflt +16384,  728 ms
pass 3: majflt +16384,  789 ms
```

512MiB에서는 첫 바퀴만 디스크를 읽고 다음부터 1ms다. 160MiB에서는 128 + 64 = 192MiB가 한도에 안 들어가니 파일 페이지가 계속 밀려나고, 매 바퀴 16,384번 major fault로 수백 ms가 든다. 프로세스는 죽지 않았다. 대신 수백 배 느려졌다. 실제 서비스에서는 이게 "OOM 나기 전 몇 분 동안 응답이 엄청 느렸다"로 나타난다.

이 상태를 숫자로 보는 곳이 PSI(Pressure Stall Information, 커널 4.20 이상)다.

```bash
# 메모리를 기다리느라 멈춘 시간의 비율. some은 일부 작업이, full은 모든 작업이 멈춘 시간
cat /proc/pressure/memory
```

```text
some avg10=0.00 avg60=0.00 avg300=0.00 total=24133
full avg10=0.00 avg60=0.00 avg300=0.00 total=23975
```

평소엔 0이다. `some avg10`이 몇 %를 넘어 계속 오르면 회수 때문에 일이 멈추고 있다는 뜻이다. systemd-oomd 같은 사용자 공간 OOM 데몬이 커널 OOM killer보다 먼저, 이 값을 보고 cgroup을 통째로 정리한다. 설치되어 켜져 있는지는 배포판과 이미지마다 달라서 `systemctl status systemd-oomd`로 확인한다.

## 누구를 죽일지 고르는 OOM killer

회수로도 자리를 못 만들면 커널은 OOM killer를 부른다. 후보마다 점수(badness)를 매긴다. 기본은 그 프로세스가 차지한 메모리, 즉 RSS와 스왑, 페이지 테이블을 합친 양이고, 여기에 `oom_score_adj`(-1000~1000)를 더해 보정한다. 가장 점수가 높은 프로세스에 SIGKILL을 보낸다. 예전 커널은 root 프로세스의 점수를 조금 깎아 주기도 했지만, 지금은 메모리 양이 거의 전부다. 지금 메모리를 가장 많이 쓰는 쪽이 죽는다.

```bash
# 프로세스별 현재 점수와 보정값
for p in 1 $(pgrep -o node) $$; do
  printf "%s %s score=%s adj=%s\n" $p "$(cat /proc/$p/comm)" $(cat /proc/$p/oom_score) $(cat /proc/$p/oom_score_adj)
done
```

```text
1 process_api score=0 adj=0
3463 node score=670 adj=0
4360 bash score=666 adj=0
```

이 커널에서 `oom_score`는 내부 점수를 0~2000 범위로 옮긴 뒤 2/3을 곱해 보여 준다. 메모리를 거의 안 쓰는 bash도 666 근처에 있는 이유다. PID 1(이 VM에서는 `process_api`)은 아예 후보가 아니라 0이다. 죽이면 안 되는 프로세스는 `oom_score_adj`를 -1000으로 두고, 먼저 죽어도 되는 일꾼은 양수로 둔다. systemd 유닛에서는 `OOMScoreAdjust=`로 정한다. 쿠버네티스는 Pod의 QoS 클래스에 따라 이 값을 다르게 매긴다. Guaranteed는 -997, BestEffort는 1000이다([requests와 limits 글](/posts/k8s-pod-resources)).

어느 OOM이었는지는 커널 로그가 알려 준다. 처음 장면의 로그다.

```bash
# 시각은 부팅 후 초다. -T를 붙이면 벽시계 시각으로 바꿔 준다
sudo dmesg | grep -E "oom-kill|Killed process"
```

```text
[ 3405.418865] oom-kill:constraint=CONSTRAINT_MEMCG,nodemask=(null),cpuset=/,mems_allowed=0,oom_memcg=/lx2oom,task_memcg=/lx2oom,task=hog,pid=4331,uid=0
[ 3405.421629] Memory cgroup out of memory: Killed process 4331 (hog) total-vm:1051280kB, anon-rss:261504kB, file-rss:1556kB, shmem-rss:0kB, UID:0 pgtables:560kB oom_score_adj:0
```

`constraint=CONSTRAINT_MEMCG`와 `oom_memcg=/lx2oom`이 "노드 전체가 아니라 이 cgroup의 한도였다"는 증거다. `total-vm` 1GiB, `anon-rss` 255MiB가 앞에서 본 예약과 실제 사용의 차이 그대로다. 노드 전체가 모자랐다면 `constraint=CONSTRAINT_NONE`과 `Out of memory:`로 시작하는 줄이 나온다. 로그의 다른 칸과 cgroup 파일(`memory.events`)을 읽는 법은 [네임스페이스와 cgroup 글](/posts/linux-namespaces-cgroups)에서 자세히 다뤘다.

## 메모리가 이상할 때 보는 숫자

"메모리가 부족한 것 같다"는 말을 들으면 아래 순서로 본다.

```bash
# 1. 진짜 모자란가: free가 아니라 available을 본다
free -m

# 2. 페이지 폴트와 회수가 일어나는가 (sysstat 패키지)
sar -B 1 3

# 3. 누가 fault를 많이 내는가: 프로세스별 누적 minor/major fault
ps -eo pid,min_flt,maj_flt,rss,comm --sort=-maj_flt | head

# 4. OOM이 있었는가, 누구 한도였는가
sudo dmesg -T | grep -iE "out of memory|oom-kill"
```

```text
               total        used        free      shared  buff/cache   available
Mem:           16093        2517        9624         172        4445       13575
Swap:              0           0           0

00:29:11     pgpgin/s pgpgout/s   fault/s  majflt/s  pgfree/s pgscank/s pgscand/s pgsteal/s    %vmeff
00:29:12         0.00  12592.00  50812.00      0.00   5004.00      0.00      0.00      0.00      0.00

```

`free`의 `free` 칸이 작다고 놀랄 필요는 없다. 리눅스는 남는 메모리를 페이지 캐시(`buff/cache`)로 쓰고, 필요하면 비워서 내준다. 새 프로그램이 실제로 받을 수 있는 양의 추정치가 `available`이다. 여기서는 16GiB 중 13GiB가 가능하다.

`sar -B`에서 볼 칸은 `majflt/s`와 `pgscank/s`(kswapd가 훑은 페이지), `pgscand/s`(할당하던 프로세스가 직접 훑은 페이지)다. `fault/s`가 초당 수만이어도 대부분 minor fault라서 괜찮다. 이 머신은 다른 빌드가 돌고 있어 5만까지 올랐지만 `majflt/s`는 1 이하, 스캔은 0이다. 메모리 압박이 없다. `pgscand/s`가 0이 아니면 프로세스가 할당하다 멈춰서 직접 회수하고 있다는 뜻이고, 이때 지연이 튄다. `vmstat 1`의 `si`/`so`(스왑 입출력)도 같은 이야기를 한다. 여러 지표를 묶어 서버 전체를 1분 안에 훑는 순서는 [리눅스 성능 점검 글](/posts/linux-performance-triage)에 정리했다.

흔한 실수 몇 가지.

- VSZ로 메모리 경보를 건다. VSZ는 예약한 주소 공간이라 실제 사용과 거의 상관이 없다. 위에서 본 node는 VSZ 730MiB, RSS 42MiB였다. 경보는 RSS(컨테이너라면 cgroup의 working set)로 건다.
- 스왑을 끄면 thrashing이 없어진다고 생각한다. 익명 메모리를 내보낼 곳이 없어질 뿐, 파일 페이지 thrashing은 그대로 일어나고 OOM은 더 갑자기 온다.
- 런타임 힙 한도를 컨테이너 한도와 같게 잡는다. 힙 밖 메모리(스레드 스택, 코드, 버퍼)도 같은 cgroup에 청구된다. 이 이야기는 [GC 글](/posts/garbage-collection)과 [JVM 메모리 글](/posts/java-jvm-memory-gc)에 실측과 함께 있다.
- `malloc`의 NULL 검사로 메모리 부족을 처리했다고 믿는다. 기본 overcommit에서는 NULL보다 SIGKILL이 먼저 온다.

## 약속과 실제 사이

가상 메모리는 프로세스에게 넓고 깨끗한 자기만의 주소 공간을 보여 주고, 실제 메모리는 쓰는 순간에 한 페이지씩 내준다. 그 사이를 페이지 테이블이 잇고, TLB가 그 변환을 빠르게 하고, page fault가 "아직 안 준 페이지"를 그때그때 채운다. 이 구조 덕에 커널은 램보다 많이 약속할 수 있지만, 약속을 못 지키는 순간에는 할당 실패가 아니라 회수와 thrashing, 그리고 OOM kill로 갚는다. 그래서 메모리 문제를 볼 때는 예약(VSZ)이 아니라 실제(RSS, PSS), 할당 실패가 아니라 major fault와 회수, 커널 로그를 본다.

## 면접에서 나올 만한 질문

### 가상 메모리를 왜 쓰나요?

프로세스마다 독립된 주소 공간을 주고, 실제 메모리 배치를 감추기 위해서다. 덕분에 한 프로세스가 다른 프로세스 메모리를 건드릴 수 없고, 프로그램은 늘 같은 모양의 주소 공간에서 시작한다. 쓸 때만 물리 메모리를 주는 demand paging, 공유 라이브러리를 한 벌만 올리는 공유, fork의 copy-on-write, 파일을 메모리처럼 다루는 `mmap`도 모두 이 간접 계층 위에서 가능해진다.

### 페이지 테이블을 왜 여러 단으로 만드나요?

평평한 표로 만들면 쓰지 않는 주소까지 칸을 만들어야 해서 프로세스마다 수백 GiB가 필요하기 때문이다. x86-64는 48비트 주소의 위쪽 36비트를 9비트씩 4단으로 나누고, 쓰는 구역의 표만 만든다. 표 하나가 512칸 × 8바이트 = 4KiB라서 페이지 한 장에 들어간다. 대가는 TLB miss 때 메모리를 네 번 더 읽어야 한다는 것이다.

### TLB miss가 많으면 어떻게 줄이나요?

칸 하나가 덮는 범위를 넓히는 huge page를 쓴다. 2MiB 페이지는 4KiB 페이지 512장을 TLB 한 칸으로 덮는다. 1GiB 배열을 무작위로 읽는 실험에서 2MiB 페이지가 25~30% 빨랐다. 큰 힙을 오래 쓰는 DB나 JVM은 hugetlbfs나 THP `madvise`로 켜고, fork가 잦거나 작은 할당이 많은 프로세스는 THP의 compaction 지연과 메모리 증가 때문에 끄는 편이다. 접근하는 데이터 범위 자체를 줄이는 것(지역성 개선)도 같은 효과를 낸다.

### minor fault와 major fault의 차이는?

디스크 I/O가 필요한지가 다르다. minor fault는 처음 만지는 익명 메모리에 0으로 채운 프레임을 붙이거나, 이미 페이지 캐시에 있는 파일 페이지를 연결하거나, copy-on-write로 복사하는 것처럼 메모리 안에서 끝난다. major fault는 페이지 내용을 디스크(파일이나 스왑)에서 읽어 와야 해서 수십 배에서 수천 배 비싸다. 성능을 볼 때는 major fault 비율이 신호다. minor fault는 초당 수만 번이어도 정상인 경우가 많다.

### malloc이 성공했는데 왜 프로세스가 OOM으로 죽나요?

리눅스 기본 overcommit(모드 0)에서는 `malloc`이 주소 공간만 예약하고, 실제 프레임은 페이지를 처음 만질 때 page fault로 받기 때문이다. 메모리 한도(노드 전체든 cgroup이든)는 그 시점에 검사된다. 그때 회수로도 자리가 안 나면 돌려줄 오류 코드가 없으니 OOM killer가 SIGKILL을 보낸다. 할당 시점에 실패시키려면 모드 2(엄격)를 쓰지만, 넉넉하게 예약하는 런타임이 램이 남는데도 못 뜨는 부작용이 있다.

### OOM killer는 누구를 고르나요? 특정 프로세스를 보호하려면?

RSS와 스왑, 페이지 테이블을 합친 메모리 사용량에 `oom_score_adj`를 더한 점수가 가장 높은 프로세스를 고른다. 보호하려면 `oom_score_adj`를 낮추고(-1000이면 제외), systemd라면 `OOMScoreAdjust=`로 정한다. cgroup 한도에 걸린 OOM은 그 cgroup 안에서만 고른다. 커널 로그의 `constraint=CONSTRAINT_MEMCG`인지 `CONSTRAINT_NONE`인지로 어느 쪽 OOM이었는지 구분한다.

### 스왑이 없는데도 서버가 OOM 직전에 매우 느려지는 이유는?

익명 메모리는 내보낼 곳이 없으니 커널이 파일 페이지(프로그램 코드, 읽던 파일)를 대신 계속 버리고, 그걸 곧바로 다시 major fault로 읽어 오기 때문이다. 160MiB cgroup 실험에서 프로세스는 죽지 않았지만 같은 파일을 훑는 시간이 1ms에서 700ms대로 늘었다. `sar -B`의 `majflt/s`와 `pgscand/s`, `/proc/pressure/memory`의 `some` 값이 오르는 걸로 알아챈다.

### fork는 큰 프로세스에서도 왜 빠른가요? 그럼 언제 메모리가 늘어나나요?

메모리를 복사하지 않고 페이지 테이블만 복사한 뒤 양쪽을 읽기 전용으로 공유하기 때문이다. 어느 쪽이든 페이지에 쓰는 순간 그 한 장만 복사된다(copy-on-write). 그래서 fork 직후에는 메모리가 거의 안 늘고, 부모가 쓰기를 많이 할수록 복사본이 쌓인다. THP가 켜져 있으면 복사 단위가 2MiB가 되어 이 증가와 지연이 커진다.
