분 단위 요청 수를 모아 두는 대시보드를 생각해 보자. "오후 2시 10분부터 3시 40분까지 요청이 몇 개였나"를 계속 묻는다. 그런데 늦게 도착한 로그가 지난 분의 숫자를 계속 고친다. [누적 합 배열](/posts/ds-array-matrix)을 만들어 두면 구간 합은 뺄셈 한 번이지만, 값 하나가 바뀔 때마다 그 뒤의 누적 합을 전부 다시 만들어야 한다. O(n)이다. 그냥 배열에서 매번 더하면 갱신은 O(1)이지만 질의가 O(n)이다.

질의와 갱신이 둘 다 많으면 둘 다 O(log n)으로 맞추는 구조가 필요하다. 세그먼트 트리(segment tree)와 펜윅 트리(Fenwick tree, Binary Indexed Tree라고도 부른다)가 그 답이다. 이 글은 원소 8개짜리 같은 배열 `[5, 3, 7, 9, 6, 4, 1, 2]` 위에서 두 구조를 단계별로 돌리고, 원소 20만 개에서 네 가지 방법을 나란히 잰다. 출력은 모두 Node 22에서 직접 돌린 것이다. 트리 모양 자체를 회전으로 고치는 구조는 [균형 탐색 트리](/posts/balanced-search-trees)에서 다뤘다. 여기서는 모양이 처음부터 고정된 트리를 쓴다.

## 값 하나가 바뀌면 누적 합을 다시 만든다

먼저 문제의 크기를 숫자로 보자. 원소 20만 개짜리 배열에 연산 20만 개를 반씩 섞었다. 절반은 "i번 값을 바꿔라", 절반은 "l부터 r까지 합을 구하라"다. 네 방법이 모두 같은 답을 내는지 확인하려고 질의 결과를 더한 checksum도 찍었다.

```text
naive loop        9401ms checksum=323248806946
prefix rebuild   69679ms checksum=323248806946
segment tree        62ms checksum=323248806946
fenwick tree       111ms checksum=323248806946
```

매번 더하는 쪽은 9.4초, 누적 합을 갱신마다 다시 만드는 쪽은 70초가 걸렸다. 누적 합은 질의가 공짜인 대신 갱신 10만 번마다 20만 칸을 다시 계산했다. 세그먼트 트리와 펜윅 트리는 0.1초 안팎이다. 100배에서 1,000배 차이다. 두 트리 사이의 차이는 의미가 없다. 같은 코드를 다시 돌리면 166ms와 132ms, 231ms와 193ms처럼 순위가 바뀐다. 둘 다 연산 하나에 O(log n), 20만이면 18걸음 남짓이다.

## 구간을 반씩 나눠 미리 더해 둔다

세그먼트 트리는 배열 전체 구간을 뿌리로 두고, 구간을 반씩 나눠 왼쪽 자식과 오른쪽 자식으로 내려가는 트리다. 잎 하나가 원소 하나이고, 안쪽 노드는 자기 구간의 합을 들고 있다. [힙](/posts/ds-heap)처럼 배열 하나에 담는다. 뿌리를 1번 칸에 두면 i번 노드의 자식은 2i와 2i + 1이다.

```js
function build(node, l, r) {
  if (l === r) {                       // 잎: 원소 하나
    tree[node] = a[l];
    return;
  }
  const m = (l + r) >> 1;
  build(2 * node, l, m);               // 왼쪽 반
  build(2 * node + 1, m + 1, r);       // 오른쪽 반
  tree[node] = tree[2 * node] + tree[2 * node + 1]; // 두 반쪽의 합
}
```

예제 배열로 만든 트리를 층별로 찍었다.

```text
tree levels:
  37
  24 13
  8 16 10 3
  5 3 7 9 6 4 1 2
```

맨 아래가 원래 배열이고, 위로 갈수록 이웃한 두 칸을 더한다. 8은 5 + 3, 24는 8 + 16, 뿌리 37은 전체 합이다. 만드는 데 노드 수만큼, O(n)이 걸린다.

## 묻는 구간을 노드 몇 개로 덮는다

구간 [2..6]의 합을 물어보자. 뿌리에서 내려가며 세 경우를 나눈다. 노드 구간이 질의 구간과 안 겹치면 0을 돌려준다. 질의 구간 안에 통째로 들어가면 그 노드의 합을 그대로 쓴다. 걸쳐 있으면 두 자식으로 나눠 내려간다.

```js
function query(node, l, r, ql, qr) {
  if (qr < l || r < ql) return 0;               // 안 겹친다
  if (ql <= l && r <= qr) return tree[node];    // 통째로 들어간다: 그대로 쓴다
  const m = (l + r) >> 1;                       // 걸쳐 있다: 나눠 내려간다
  return query(2 * node, l, m, ql, qr) + query(2 * node + 1, m + 1, r, ql, qr);
}
```

```text
  node5[2..3]=16 use
  node3[4..7] split
  node6[4..5]=10 use
  node7[6..7] split
  node14[6..6]=1 use
```

## 값 하나 고치면 뿌리까지 log n개

갱신은 더 단순하다. 바뀐 원소의 잎을 고치고, 그 잎에서 뿌리까지 올라가며 부모의 합을 다시 계산한다. 그 원소를 포함하는 구간은 층마다 하나씩, 그 길 위의 노드뿐이다. a[4]를 6에서 10으로 바꿨다.

```text
set a[4]=10: node12[4]=10, node6[4..5]=14, node3[4..7]=17, node1[0..7]=41
sum[2..6] = 31
```

노드 네 개가 바뀌었다. 잎 12번에서 6번, 3번, 뿌리 1번으로 올라갔다. 같은 질의가 이제 31을 낸다. 노드 15개 중 4개만 건드렸고, 원소가 100만 개라도 21개다.

## 배열 크기는 왜 4n인가

세그먼트 트리 코드에서 배열을 `new Array(4 * n)`으로 잡는 걸 자주 본다. 2n이면 충분할 것 같은데 왜일까. n이 2의 거듭제곱이 아니면 트리의 마지막 층이 들쭉날쭉해져서, 재귀로 만든 트리의 노드 번호가 2n을 넘는다. n을 1부터 늘려 가며 실제로 쓰는 가장 큰 번호를 봤다.

```text
n=6:max index 13 | n=10:max index 25 | n=11:max index 25 | n=12:max index 29 | n=13:max index 29 | n=14:max index 29
worst ratio max_index/n (n<=2000 all, then every 997th up to 100000): 3.976 at n= 65802
```

n이 6이면 번호 13까지 쓴다. 2n인 12칸으로 잡으면 배열 밖에 쓴다. 자바스크립트는 조용히 배열을 늘리거나 `undefined`를 더해 `NaN`을 만들고, C++이나 자바는 메모리를 깨거나 예외를 던진다. 가장 큰 번호를 n으로 나눈 값은 n = 65,802에서 3.976까지 갔다. 2의 거듭제곱보다 조금 큰 n에서 4에 가까워진다. 그래서 4n이면 안전하다. 정확히는 n 이상인 가장 작은 2의 거듭제곱의 두 배면 된다.

재귀 깊이는 걱정하지 않아도 된다. 높이가 log n이라 원소 100만 개여도 재귀는 21단계다. [이진 탐색 트리 글](/posts/ds-binary-tree-bst)에서 콜 스택이 넘친 건 트리가 기울었기 때문이고, 세그먼트 트리는 모양이 고정돼 있어 기울 일이 없다.

## 바닥부터 쌓는 반복문 세그먼트 트리

재귀 없이 쓰는 방법도 있다. 크기를 2의 거듭제곱 sz로 올림하고, 잎을 `tree[sz]`부터 `tree[sz + n - 1]`에 둔다. 그러면 배열은 2·sz칸이면 되고, 위의 실측에서 62ms를 낸 게 이 방식이다.

```js
let sz = 1;
while (sz < n) sz <<= 1;
const tree = new Float64Array(2 * sz);
for (let i = 0; i < n; i++) tree[sz + i] = a[i];                     // 잎
for (let i = sz - 1; i > 0; i--) tree[i] = tree[2 * i] + tree[2 * i + 1]; // 위로 쌓기

function update(pos, value) {
  let i = sz + pos;
  tree[i] = value;
  for (i >>= 1; i > 0; i >>= 1) tree[i] = tree[2 * i] + tree[2 * i + 1]; // 부모로 올라가며 다시 더한다
}

function query(l, r) {                 // [l, r] 닫힌 구간
  let s = 0;
  for (l += sz, r += sz + 1; l < r; l >>= 1, r >>= 1) {
    if (l & 1) s += tree[l++];         // l이 오른쪽 자식이면 그 노드를 쓰고 오른쪽으로
    if (r & 1) s += tree[--r];         // r 바로 왼쪽이 오른쪽 자식이면 그 노드를 쓴다
  }
  return s;
}
```

질의는 양 끝에서 동시에 위로 올라가며, 자기 형제가 구간 밖인 노드만 골라 더한다. 함수 호출이 없고 타입 배열을 써서 빠르다. 대신 다음에 볼 지연 전파처럼 위에서 아래로 정보를 내려보내야 하는 기능은 재귀 쪽이 훨씬 쓰기 쉽다.

## 구간 전체에 더하기: 지연 전파

이번엔 "[1..6]의 모든 값에 2를 더하라" 같은 구간 갱신이 들어온다. 원소마다 점 갱신을 하면 구간 길이 k에 O(k log n)이 든다. 지연 전파(lazy propagation)는 일을 미룬다. 구간이 통째로 덮는 노드를 만나면 그 노드의 합만 고치고 "자식들에게 2를 더할 일이 남았다"는 메모를 붙인 뒤 내려가지 않는다. 나중에 누군가 그 노드 아래로 내려갈 일이 생기면 그때 메모를 자식에게 넘긴다.

```js
function apply(node, l, r, v) {
  tree[node] += v * (r - l + 1);       // 구간 길이만큼 합이 는다
  lazy[node] += v;                     // 자식에게 넘길 일을 적어 둔다
}

function push(node, l, r) {            // 내려가기 전에 미뤄 둔 일을 자식에게 넘긴다
  if (lazy[node] === 0) return;
  const m = (l + r) >> 1;
  apply(2 * node, l, m, lazy[node]);
  apply(2 * node + 1, m + 1, r, lazy[node]);
  lazy[node] = 0;
}

function addRange(node, l, r, ql, qr, v) {
  if (qr < l || r < ql) return;
  if (ql <= l && r <= qr) return apply(node, l, r, v); // 통째로 덮으면 여기서 멈춘다
  push(node, l, r);
  const m = (l + r) >> 1;
  addRange(2 * node, l, m, ql, qr, v);
  addRange(2 * node + 1, m + 1, r, ql, qr, v);
  tree[node] = tree[2 * node] + tree[2 * node + 1];
}
```

`query`도 걸친 노드에서 나눠 내려가기 전에 `push`를 부른다. 예제 배열에서 [1..6]에 2를 더하고 세 번 물었다.

```text
add +2 to a[1..6]: nodes visited 11
pending lazy: node5:+2 node6:+2 node9:+2 node14:+2
sum[0..7] = 49  sum[2..2] = 9  sum[1..6] = 42
pending after queries: node6:+2 node9:+2 node10:+2 node11:+2 node14:+2
check 49 9 42
```

원소 여섯 개를 고치는 대신 노드 11개를 방문하고 끝났다. 메모가 붙은 노드는 넷이다. [2..3]을 맡은 5번 노드는 합만 16에서 20으로 고치고 잎 7과 9는 그대로 뒀다. 그 뒤 a[2] 하나를 묻자 5번 노드를 지나 내려가야 해서 메모가 자식 10번, 11번으로 넘어갔다. 나머지 메모는 아무도 묻지 않았으니 여전히 미뤄진 채다. 마지막 줄은 배열에 직접 더해 확인한 값이고 세 답이 모두 맞는다.

지연 전파에서 가장 흔한 버그는 `push`를 빠뜨리는 것이다. 질의는 맞는데 갱신 뒤의 갱신에서 틀리거나, 특정 순서에서만 틀린다. 작은 배열에서 무작위 연산을 만들어 그냥 배열과 답을 비교하는 테스트를 꼭 돌린다. 덧셈 대신 "값을 v로 바꿔라" 같은 대입을 섞으면 메모끼리 합치는 규칙이 바뀐다. 대입 뒤의 덧셈과 덧셈 뒤의 대입이 다르기 때문이다.

## 최하위 비트로 부모를 찾는 펜윅 트리

펜윅 트리는 구간 합 하나만 필요할 때 세그먼트 트리보다 훨씬 작고 짧다. 배열이 n + 1칸이면 되고 코드는 반복문 두 개다. 인덱스를 1부터 쓴다. `bit[i]`는 i에서 끝나는 길이 `i & -i`짜리 구간의 합을 들고 있다. `i & -i`는 i를 이진수로 썼을 때 가장 낮은 1비트만 남긴 값이다. 6은 0110이라 `6 & -6`은 2이고, `bit[6]`은 a[5..6]의 합이다.

```text
bit[1..8] = 5 8 7 24 6 10 1 37
  bit[1] i=0001 i&-i=1 covers a[1..1]
  bit[2] i=0010 i&-i=2 covers a[1..2]
  bit[3] i=0011 i&-i=1 covers a[3..3]
  bit[4] i=0100 i&-i=4 covers a[1..4]
  bit[5] i=0101 i&-i=1 covers a[5..5]
  bit[6] i=0110 i&-i=2 covers a[5..6]
  bit[7] i=0111 i&-i=1 covers a[7..7]
  bit[8] i=1000 i&-i=8 covers a[1..8]
```

홀수 칸은 자기 원소 하나, 2의 배수 칸은 둘, 4의 배수는 넷, 8은 전체를 맡는다. 세그먼트 트리의 노드 중 "왼쪽 자식"만 남기고 오른쪽 자식을 버린 모양이다. 오른쪽 자식은 부모에서 왼쪽 자식을 빼면 나오니까 따로 안 들고 있어도 된다.

앞에서부터 i까지의 합은 i에서 최하위 비트를 하나씩 지우며 내려간다. 7 = 0111에서 0110, 0100으로 가며 세 칸을 더한다. 값을 더할 때는 반대로 최하위 비트를 더하며 올라간다. 5 = 0101에서 0110, 1000으로 가며 5를 포함하는 칸을 모두 고친다.

```js
function add(i, delta) {               // a[i] += delta (1부터 센다)
  for (; i <= n; i += i & -i) bit[i] += delta;
}

function prefix(i) {                   // a[1..i]의 합
  let s = 0;
  for (; i > 0; i -= i & -i) s += bit[i];
  return s;
}

const rangeSum = (l, r) => prefix(r) - prefix(l - 1);
```

```text
prefix(7) = 35 via 7(0111)=1 + 6(0110)=10 + 4(0100)=24
add(5,+4) touches 5(0101) -> 6(0110) -> 8(1000)
sum a[3..7] = prefix(7)-prefix(2) = 31
```

## 펜윅이 못 하는 질의

펜윅의 구간 합은 prefix(r) - prefix(l - 1), 즉 뺄셈으로 만든다. 이게 되는 건 덧셈에 역연산이 있기 때문이다. 구간 최솟값이나 최댓값에는 역연산이 없다. 앞에서부터 7까지의 최솟값과 2까지의 최솟값을 알아도 3부터 7까지의 최솟값은 나오지 않는다. 그래서 임의의 구간 최솟값을 묻고 값이 커지기도 하는 갱신이 섞이면 펜윅으로는 안 되고 세그먼트 트리를 쓴다. 값이 줄어들기만 하고 늘 앞에서부터의 최솟값만 묻는 특수한 경우는 펜윅으로도 된다.

세그먼트 트리는 두 자식을 합치는 연산만 정하면 무엇이든 담는다. 합 대신 `Math.min`을 쓰면 구간 최솟값, 최대공약수를 쓰면 구간 최대공약수, "최댓값과 그 개수" 쌍을 쓰면 그것도 된다. 조건은 그 연산이 결합 법칙을 만족하는 것 하나다. 순서만 지키면 어떻게 묶어 계산해도 같은 결과여야 반으로 쪼개 미리 계산해 둘 수 있다.

앞의 반복문 세그먼트 트리에서 `+`를 `Math.min`으로, 빈 칸의 0을 `Infinity`로 바꾸기만 했다. 펜윅이 막힌 질의가 그대로 된다. a[6]의 1을 8로 키우는 갱신도 섞었다. 펜윅으로 앞에서부터의 최솟값을 들고 있었다면 이 갱신은 되돌릴 방법이 없다.

```js
for (let i = sz - 1; i > 0; i--) tree[i] = Math.min(tree[2 * i], tree[2 * i + 1]); // 합 대신 최솟값
```

```text
min[2..5] = 4  min[0..7] = 1
after a[6]=8: min[0..7] = 2  min[4..7] = 2
```

[2..5]의 7, 9, 6, 4 중 4가 나왔고, 전체 최솟값 1이 8로 바뀌자 다음으로 작은 2가 올라왔다. 바뀐 잎에서 뿌리까지 노드 세 개의 최솟값만 다시 계산했다.

펜윅도 구간 갱신을 할 수는 있다. 차이 배열에 펜윅을 얹으면 "구간에 더하기, 한 점 값 묻기"가 되고, 펜윅 두 개를 함께 쓰면 "구간에 더하기, 구간 합 묻기"까지 된다. 다만 식이 머리에 잘 안 남아서, 구간 갱신이 필요해지면 지연 전파 세그먼트 트리로 가는 경우가 많다.

## 현장에서 쓰이는 곳

순위표가 대표적이다. 점수가 0부터 10만 사이라면 점수마다 "이 점수인 사람 수"를 펜윅에 담는다. 내 순위는 내 점수보다 높은 사람 수 + 1이니, 전체 인원에서 prefix(내 점수)를 빼면 된다. 10만 명을 무작위 점수로 넣고 한 사람의 순위를 구한 뒤, 정렬 없이 전부 세는 방법과 비교했다.

```js
add(score, 1);                                   // 그 점수인 사람이 한 명 늘었다
const rank = total - prefix(myScore + 1) + 1;    // 나보다 높은 사람 수 + 1
```

```text
score 62478: rank 41361 (brute force 41361)
score 92478: rank 10004
```

점수가 바뀌면 옛 점수 칸에서 1을 빼고 새 점수 칸에 1을 더한다. 둘 다 O(log 최대 점수)다. 같은 사람이 3만 점을 더 얻자 순위가 41,361등에서 10,004등이 됐다. 점수 범위가 너무 넓거나 실수라면 실제로 나온 점수만 정렬해 번호를 다시 매기는 좌표 압축을 먼저 한다. 서비스 규모의 순위표는 보통 Redis 정렬된 셋으로 만들고, 그 구조는 [순위표 글](/posts/sd-leaderboard-sorted-set)에 있다. 이 방식은 점수 범위가 정해진 게임 서버 안이나 배치 계산에서 메모리 한 덩어리로 끝내고 싶을 때 쓴다.

시계열 롤업도 같은 모양이다. 세그먼트 트리의 노드 하나가 "1분", 그 위가 "2분", 그 위가 "4분" 같은 묶음 합이라고 보면, 모니터링 시스템이 분 단위 값을 시간, 일 단위로 미리 합쳐 두는 일과 생각이 같다. 늦게 도착한 값이 과거 칸을 고칠 때 위쪽 묶음 몇 개만 다시 계산하면 된다. 실제 시계열 DB는 디스크 블록 단위로 이 생각을 구현한다.

코딩 테스트에서는 역순 쌍 세기(inversion count)가 펜윅의 단골이다. 배열을 앞에서부터 보며 "지금까지 나온 값 중 나보다 큰 것의 수"를 펜윅으로 세면 O(n log n)이다. 이중 반복문의 O(n²)를 대신한다. 정렬이 얼마나 흐트러져 있는지 재는 지표로도 쓰인다.

```js
function countInversions(arr) {
  const sorted = [...new Set(arr)].sort((x, y) => x - y);
  const rank = new Map(sorted.map((v, i) => [v, i + 1])); // 좌표 압축: 값 → 1..m
  const m = sorted.length;
  const bit = new Array(m + 1).fill(0);
  let inv = 0;
  arr.forEach((v, seen) => {
    const r = rank.get(v);
    let notGreater = 0;                                     // 지금까지 나온 값 중 v 이하의 개수
    for (let i = r; i > 0; i -= i & -i) notGreater += bit[i];
    inv += seen - notGreater;                               // 나머지가 v보다 큰 값
    for (let i = r; i <= m; i += i & -i) bit[i]++;
  });
  return inv;
}
```

```text
[3,1,2] -> 2
[5,3,7,9,6,4,1,2] -> 19
n=100000 fenwick 2500199876 251ms | double loop 2500199876 30436ms
```

원소 10만 개에서 이중 반복문은 30초, 펜윅은 0.25초였고 답은 같다. 값이 10억까지 흩어져 있어도 좌표 압축으로 펜윅 크기를 원소 수로 줄였다. 무작위 배열의 역순 쌍은 전체 쌍 수의 절반쯤이라 25억 개다.

실수는 몇 가지가 반복된다. 펜윅을 0부터 쓰면 `0 & -0`이 0이라 `add`가 무한 반복에 빠진다. 인덱스에 1을 더해 쓰는 걸 잊지 말아야 한다. 합이 2⁵³을 넘을 수 있으면 자바스크립트 `number`는 정확도를 잃으니 `BigInt`나 `BigInt64Array`를 쓴다. 세그먼트 트리는 배열을 2n으로 잡아 범위를 넘기는 경우가 많고, 질의 구간이 닫힌 구간인지 반열린 구간인지 섞어 쓰다 한 칸씩 틀린다. 마지막으로, 갱신이 거의 없다면 이 구조가 다 필요 없다. 한 번 만든 누적 합 배열이 질의마다 뺄셈 한 번이라 가장 빠르다.

## 면접에서 나올 만한 질문

### 누적 합 배열이 있는데 세그먼트 트리가 왜 필요한가요?

누적 합 배열은 구간 합이 O(1)이지만 값 하나가 바뀌면 그 뒤를 전부 다시 계산해 O(n)이 든다. 질의와 갱신이 둘 다 많으면 둘 중 하나가 O(n)인 방법은 느리다. 원소 20만 개에 연산 20만 개를 섞자 누적 합 재계산은 70초, 매번 더하기는 9.4초, 세그먼트 트리는 0.1초 안팎이었다. 세그먼트 트리는 질의와 갱신을 둘 다 O(log n)으로 맞춘다.

### 세그먼트 트리의 질의가 O(log n)인 이유는요?

질의 구간이 노드 구간을 통째로 덮으면 그 노드 값을 바로 쓰고 아래로 내려가지 않기 때문이다. 갈라지는 건 질의 구간의 양 끝 근처뿐이라 층마다 방문하는 노드가 많아야 네 개 정도다. 높이가 log n이니 전체도 O(log n)이다. 갱신은 잎에서 뿌리까지 한 길만 고치니 정확히 높이만큼이다.

### 배열 크기를 4n으로 잡는 이유는요?

n이 2의 거듭제곱이 아니면 재귀로 만든 트리의 노드 번호가 2n을 넘는다. n이 6이면 번호 13까지 쓰고, 최악에는 4n에 가까워진다. 실측에서 n = 65,802일 때 가장 큰 번호가 n의 3.976배였다. 반복문 방식은 크기를 2의 거듭제곱 sz로 올림해 2·sz칸을 쓴다.

### 지연 전파는 무엇이고 언제 쓰나요?

구간 전체에 값을 더하거나 바꾸는 갱신이 있을 때 쓴다. 갱신 구간이 통째로 덮는 노드의 합만 고치고 "자식에게 넘길 일"을 메모로 남긴 채 내려가지 않는다. 나중에 그 노드 아래로 내려갈 때 메모를 자식에게 넘긴다. 그래서 구간 갱신도 O(log n)이다. 내려가기 전에 메모를 넘기는 처리를 빠뜨리는 버그가 가장 흔하다.

### 펜윅 트리는 어떻게 동작하나요?

`bit[i]`가 i에서 끝나는 길이 `i & -i` 구간의 합을 들고 있다. 앞에서부터 i까지의 합은 i에서 최하위 비트를 하나씩 지우며 칸을 더하고, 값을 더할 때는 최하위 비트를 더하며 올라가 그 원소를 포함하는 칸을 고친다. 둘 다 O(log n)이고 배열은 n + 1칸이다. 인덱스를 1부터 써야 하는데, 0을 넣으면 `0 & -0`이 0이라 무한 반복에 빠진다.

### 펜윅 트리로 구간 최솟값을 구할 수 있나요?

임의의 구간과 아무 갱신이 섞이면 안 된다. 펜윅의 구간 질의는 prefix(r) - prefix(l - 1)처럼 앞에서부터의 값 두 개를 빼서 만드는데, 최솟값에는 뺄셈 같은 역연산이 없다. 이럴 땐 세그먼트 트리를 쓴다. 세그먼트 트리는 결합 법칙만 만족하면 최솟값, 최대공약수 같은 어떤 합치기 연산도 담는다.

### 세그먼트 트리와 펜윅 트리 중 무엇을 고르나요?

구간 합처럼 역연산이 있는 질의와 점 갱신만 필요하면 펜윅이 메모리도 작고 코드도 짧다. 구간 최솟값처럼 역연산이 없는 질의, 구간 갱신, 여러 값을 묶은 정보가 필요하면 세그먼트 트리다. 속도는 둘 다 O(log n)이고 실측에서도 실행마다 순위가 바뀔 만큼 비슷했다. 갱신이 거의 없으면 둘 다 필요 없고 누적 합 배열이 가장 빠르다.
