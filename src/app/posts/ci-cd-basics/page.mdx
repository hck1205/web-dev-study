<EasyIntro>
  여러 사람이 함께 코드를 고치면 각자 고친 것을 합칠 때 문제가 터진다. 오래 따로 작업하다 한꺼번에 합치면 어디서 깨졌는지 찾기 어렵다. 그래서 작은 변경을 자주 합치고, 합칠 때마다 자동으로 검사를 돌리자는 습관이 생겼고 그게 지속적 통합이다.

  검사를 통과한 코드가 서비스까지 가는 길이 파이프라인이다. 공장의 검사 라인처럼 빠르고 싼 검사를 앞에, 느리고 비싼 검사를 뒤에 두고, 앞에서 떨어지면 뒤로 보내지 않는다. 중요한 약속이 하나 있는데, 시험 환경에서 확인한 바로 그 결과물을 다시 만들지 않고 그대로 실제 서비스에 옮긴다는 것이다.

  같은 코드라도 다시 만들면 재료가 조금 달라져 다른 결과물이 나올 수 있어서다. 글 처음의 금요일 사고가 바로 그 약속을 어긴 경우이고, 가끔만 실패하는 검사와 배포 속도를 재는 숫자 네 가지도 함께 다룬다.
</EasyIntro>

금요일 오후, 스테이징에서 이틀 동안 확인한 버전을 운영에 배포했다. 그런데 운영에서만 결제 금액이 이상하게 나온다. 한참 뒤에 알게 된 건, 운영 배포 잡이 스테이징에서 확인한 그 빌드를 쓰지 않고 같은 커밋을 다시 빌드했다는 사실이었다. 그 사이 의존성 하나가 `^` 범위 안에서 새 버전으로 올라가 있었다. 같은 커밋이었지만 같은 프로그램은 아니었다.

CI/CD는 이런 일을 막으려고 만든 흐름이다. "자동으로 배포해 주는 도구"로 기억하기 쉽지만, 실제로 정하는 건 변경 하나가 어떤 검사를 어떤 순서로 통과해서 어디까지 가는지다. 이 글은 그 뼈대를 다룬다. GitHub Actions 문법과 OIDC, 이미지 태그 같은 구체적인 내용은 [GitHub Actions로 이미지 빌드하고 ECR에 올리기](/posts/github-actions-docker-ecr), 쿠버네티스까지 이어지는 길은 [push에서 EKS까지 배포 파이프라인](/posts/k8s-deploy-pipeline-eks), 인프라 설정의 파이프라인은 [네트워크 설정 CI/CD](/posts/network-config-cicd)에서 다뤘다. 여기서는 그 글들이 깔고 있는 개념을 본다.

이 주제의 다른 글: [빌드 캐시로 파이프라인 줄이기](/posts/build-caching), [피처 플래그 운영](/posts/feature-flags), [롤백 전략](/posts/rollback-strategy).

실습은 Ubuntu 24.04, Node 22.22.0에서 했다. GitHub Actions 워크플로는 [act](https://github.com/nektos/act) 0.2.82로 로컬에서 실제로 돌렸다. Docker가 없는 환경이라 `-P ubuntu-latest=-self-hosted`로 잡을 호스트에서 바로 실행했다.

## 세 단어가 가리키는 범위

CI/CD 안에는 세 가지 다른 약속이 섞여 있다.

지속적 통합(Continuous Integration)은 여러 사람의 변경을 자주, 적어도 하루에 한 번 이상 main에 합치고, 합칠 때마다 빌드와 테스트를 자동으로 돌리는 습관이다. 이름에 "통합"이 들어간 이유가 있다. 브랜치에서 3주를 따로 살다가 합치면 충돌과 숨은 상호작용이 한꺼번에 터진다. 작은 변경을 자주 합치면 깨졌을 때 원인이 방금 들어온 몇 줄 안에 있다. 테스트 서버를 돌리는 건 이 습관을 버티게 하는 장치일 뿐이다. CI 서버가 있어도 브랜치를 몇 주씩 들고 있으면 CI를 하고 있는 게 아니다.

지속적 전달(Continuous Delivery)은 main에 들어간 모든 커밋이 언제든 운영에 내보낼 수 있는 상태라는 약속이다. 빌드, 테스트, 스테이징 배포까지 자동이고, 운영에 내보내는 순간만 사람이 버튼으로 정한다. 지속적 배포(Continuous Deployment)는 그 버튼마저 없앤 것이다. 검사를 다 통과한 커밋은 사람의 승인 없이 운영까지 간다.

점선은 지속적 배포다. 둘 중 무엇이 더 앞선 단계라고 할 수는 없다. 금융처럼 운영 반영에 변경 승인 기록이 필요한 곳은 지속적 전달에서 멈추는 게 맞고, 그래도 "언제든 내보낼 수 있는 상태"라는 약속은 지킬 수 있다. 지속적 배포를 하려면 테스트를 믿을 수 있어야 하고, 배포와 공개를 떼어 놓는 [피처 플래그](/posts/feature-flags)와 빠른 [롤백](/posts/rollback-strategy)이 받쳐 줘야 한다. 그게 없으면 사람이 버튼 앞에서 하던 걱정을 대신 해 줄 장치가 없다.

## 커밋 하나가 운영까지 가는 길

파이프라인은 변경 하나가 통과하는 검사들을 순서대로 늘어놓은 것이다. 순서에는 원칙이 있다. 빠르고 싸고 자주 실패하는 검사를 앞에, 느리고 비싼 검사를 뒤에 둔다. lint는 몇 초 만에 끝나고 오타 같은 흔한 실수를 잡는다. 단위 테스트는 몇십 초, 통합 테스트는 몇 분, 스테이징 배포 후 확인은 그보다 길다. 앞에서 떨어질 변경이 뒤의 비싼 단계까지 가지 않게 한다.

실제로 이 흐름을 워크플로로 짜서 돌렸다. 작은 Node 프로젝트에 lint, 테스트, 빌드, 스테이징 배포, 운영 배포 다섯 단계를 두고, 잡끼리는 `needs`로 순서를 정했다.

```yaml
# .github/workflows/ci.yml (요점만)
jobs:
  test:                       # lint와 단위 테스트
    steps:
      - uses: actions/checkout@v4
      - run: npm run lint
      - run: npm test
  build:
    needs: test               # test가 성공해야 시작한다
    steps:
      - uses: actions/checkout@v4
      - run: npm run build    # dist/price-api-<sha>.tgz와 manifest.json을 만든다
      - uses: actions/upload-artifact@v4
        with: { name: bundle, path: dist/ }
  deploy-staging:
    needs: build
    environment: staging
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v4
        with: { name: bundle, path: dist/ }
      - run: ./scripts/deploy.sh staging
  deploy-prod:
    needs: deploy-staging
    environment: production   # GitHub에서는 여기에 승인자를 걸 수 있다
    steps:                    # (download-artifact와 deploy.sh production, 위와 같다)
```

act로 로컬에서 돌리는 명령은 이렇다. act는 GitHub의 러너 대신 내 컴퓨터에서 워크플로를 해석해 실행한다. 아티팩트 저장소도 흉내 내 주기 때문에 잡 사이에 파일을 넘기는 부분까지 확인할 수 있다.

```bash
# 워크플로를 로컬에서 push 이벤트로 실행한다
# -P ...=-self-hosted : 컨테이너 대신 호스트에서 바로 실행
# --artifact-server-path : upload/download-artifact가 쓸 로컬 저장소
act push -P ubuntu-latest=-self-hosted --artifact-server-path ./artifacts
```

## 한 번만 빌드하고 승격한다

처음 이야기로 돌아가자. 환경마다 다시 빌드하면 같은 커밋에서 다른 결과물이 나올 수 있다. 의존성 범위가 열려 있거나, 베이스 이미지 태그가 `latest`이거나, 빌드 시각과 파일 수정 시각이 결과물에 들어가는 경우다. 마지막 것은 생각보다 흔하다. 내용이 같은 디렉터리를 1초 간격으로 그냥 압축해 봤다.

```bash
# 같은 내용을 두 번 압축한다. 사이에 파일 수정 시각만 바뀌었다
tar czf a1.tgz src package.json
touch src/price.js
tar czf a2.tgz src package.json
sha256sum a1.tgz a2.tgz
```

```text
61f29e9e5860a1bbc9182ca0f46d651223a030b02966703c4e1647bb98fffbe1  a1.tgz
7fe328b470de3fbc4fda433664a18447720ccb95fda249bc04a7f111f9fe5660  a2.tgz
```

tar는 파일 수정 시각과 소유자를, gzip은 압축한 시각을 헤더에 넣는다. 그래서 해시가 다르다. 빌드 스크립트는 `--sort=name --mtime=2026-01-01 --owner=0 --group=0`과 `gzip -n`으로 이런 값을 고정했다. 그 결과 위 실행에서 빌드 스크립트만 바꾼 두 커밋(`bbdc483`, `90b7537`)의 tgz 해시가 `520db2…`로 같게 나왔다. 이렇게 같은 입력에서 늘 같은 결과물이 나오는 빌드를 재현 가능한 빌드(reproducible build)라고 한다.

재현 가능하게 만들면 다시 빌드해도 된다는 뜻은 아니다. 재현성은 "이 결과물이 정말 이 소스에서 나왔는지" 확인하는 데 쓰고, 배포는 여전히 한 번 만든 것을 옮긴다. 이걸 승격(promotion)이라고 부른다. 스테이징에서 확인한 결과물에 "운영 가능" 표시를 붙여 다음 환경으로 넘기는 것이다.

위 그림의 `artifacts` 자리는 실무에서 아티팩트 저장소가 맡는다. 컨테이너 이미지는 ECR이나 GHCR 같은 레지스트리에, jar·npm 패키지·zip은 JFrog Artifactory, Sonatype Nexus Repository, SaaS인 Cloudsmith 같은 범용 저장소에 둔다. CI 서버의 "빌드 결과물 보관" 기능과 다른 점은 세 가지다.

- 버전을 바꾸지 못하게 잠근다. 릴리스 저장소에 `price-api-1.4.2.tgz`가 한 번 올라가면 같은 버전으로 덮어쓰기를 거절하도록 설정한다(Nexus의 재배포 금지, ECR의 태그 불변 설정). 덮어쓸 수 있으면 "스테이징에서 본 1.4.2"와 "운영의 1.4.2"가 다를 수 있다.
- 바깥 저장소를 대신 받아 둔다. npm 레지스트리, Maven Central, Docker Hub 앞에 프록시(원격) 저장소를 두면 한 번 받은 패키지는 캐시에서 나간다. 바깥이 느리거나 내려갔을 때, Docker Hub의 익명 요청 한도에 걸렸을 때, 작성자가 패키지를 지워 버렸을 때도 빌드가 돈다. 받는 쪽을 이 주소 하나로 모으면 어떤 외부 패키지를 쓰는지 한곳에서 보이고 막을 수도 있다.
- 지우는 규칙을 둔다. 커밋마다 올라가는 결과물은 금방 테라바이트가 된다. "스냅숏은 30일, 릴리스는 영구, 운영에 나간 적 없는 PR 빌드는 7일" 같은 보관 정책을 걸고, 운영에 배포된 버전은 정책에서 빼 둔다. 롤백하려는데 그 버전이 지워져 있으면 롤백이 아니라 재빌드가 된다.

승격도 저장소 안에서 하는 경우가 많다. `staging` 저장소에 있던 결과물을 승인 뒤 `release` 저장소로 복사하거나 표시를 붙이고, 운영 배포는 `release`에서만 받게 하면 확인하지 않은 결과물이 운영에 나갈 길이 막힌다.

환경마다 다른 것은 결과물이 아니라 설정이다. DB 주소, 외부 API 키, 기능 스위치 같은 값은 빌드에 굽지 않고 배포할 때 환경 변수나 [ConfigMap](/posts/k8s-configmap), [Secret](/posts/k8s-secret)으로 넣는다. 프런트엔드는 여기서 자주 걸린다. `NEXT_PUBLIC_*`나 `VITE_*`처럼 빌드 시점에 번들에 박히는 값이 있으면, 환경마다 빌드하거나 실행 시점에 설정 파일을 따로 받아 오는 구조로 바꿔야 한다. 이걸 모르고 스테이징 빌드를 운영에 승격하면 운영 화면이 스테이징 API를 부른다.

## 환경은 무엇을 확인하려고 두나

환경을 많이 두면 안전해 보이지만, 환경 하나마다 유지 비용과 대기 시간이 붙는다. 환경마다 답하는 질문이 달라야 둘 가치가 있다.

개발 환경은 "내 변경이 남의 것과 같이 돌아가는가"를 본다. 망가져도 된다. 스테이징은 "운영과 같은 모양에서 배포 절차 자체가 성공하는가"를 본다. 그래서 스테이징이 운영과 달라지면 쓸모를 잃는다. 버전이 다른 DB, 다른 인그레스 설정, 운영엔 있는 보안 그룹이 없는 상태라면, 스테이징을 통과해도 운영에서 어떻게 될지는 거의 알 수 없다. 스테이징 설정도 운영과 같은 IaC 코드에서 변수만 바꿔 만드는 이유다.

스테이징이 운영과 완전히 같을 수는 없다. 트래픽 양과 데이터 모양이 다르다. 그래서 운영에서만 드러나는 문제는 운영 안에서 작게 확인하는 방식으로 넘긴다. 일부 사용자에게 먼저 내보내는 [카나리 배포](/posts/canary-release), 두 벌을 띄워 놓고 전환하는 [블루-그린 배포](/posts/blue-green-deployment)가 그 방법이다. PR마다 잠깐 떠서 리뷰가 끝나면 사라지는 프리뷰 환경도 흔해졌다. 이 블로그가 쓰는 Vercel처럼 브랜치마다 프리뷰 주소를 주는 플랫폼이 그렇다.

## 합치는 주기가 파이프라인을 정한다

파이프라인이 아무리 좋아도 브랜치가 오래 살면 효과가 줄어든다. 지속적 통합이 전제하는 건 짧게 사는 브랜치다. 브랜치를 하루 이틀 안에 main에 합치는 트렁크 기반 개발이 이 전제와 가장 잘 맞는다. 브랜치 전략별 차이는 [브랜치 전략](/posts/git-branching-strategy)에서 다뤘으니 여기서는 파이프라인 쪽에서 생기는 일만 보자.

main에 하루 수십 번 합치면 문제가 하나 생긴다. PR 두 개가 각각은 테스트를 통과했는데, 합친 결과는 깨질 수 있다. A가 함수 이름을 바꾸고, B가 옛 이름으로 새 호출을 추가한 경우다. 둘 다 옛 main 기준으로는 초록불이다. 머지 큐(merge queue)는 PR을 바로 합치지 않고 줄을 세워, "지금 main + 앞 PR들 + 이 PR"을 합친 상태로 한 번 더 테스트한 뒤 통과한 것만 합친다. GitHub, GitLab 모두 기능으로 제공한다.

## 가끔 실패하는 테스트

같은 코드로 다시 돌리면 통과하는 테스트를 플레이키 테스트(flaky test)라고 한다. 파이프라인에 대한 신뢰를 가장 빨리 무너뜨리는 게 이것이다. 빨간불이 떠도 "또 그거겠지" 하고 재실행 버튼을 누르는 습관이 생기면, 진짜 실패도 같은 버튼으로 넘겨 버린다.

일부러 시간에 기대는 테스트를 하나 만들어 봤다. TTL이 50ms인 캐시에 값을 넣고, 다른 일을 하느라 0~60ms를 쓴 뒤 값이 남아 있는지 본다. 기계가 한가하면 통과하고, 바쁘면 실패한다. CI 러너는 여러 잡이 한 머신을 나눠 쓰니 바쁜 날이 있다.

```bash
# 같은 테스트를 50번 돌려 통과·실패를 센다
pass=0; fail=0
for i in $(seq 1 50); do
  if node --test flaky.test.js >/dev/null 2>&1; then pass=$((pass+1)); else fail=$((fail+1)); fi
done
echo "pass=$pass fail=$fail"
```

```text
pass=45 fail=5
```

50번 중 5번 실패했다. 코드는 한 글자도 바뀌지 않았다. 플레이키의 흔한 원인은 이렇다. 실제 시계와 `sleep`에 기대는 것, 테스트 순서에 기대는 것(앞 테스트가 남긴 DB 행), 공유 자원(같은 포트, 같은 임시 파일), 외부 네트워크 호출, 그리고 병렬 실행에서만 드러나는 경쟁 조건. 위 예는 시계를 주입받게 바꾸면 끝난다. 테스트에서는 가짜 시계로 시간을 직접 넘긴다.

비슷하지만 다른 문제로 "내 컴퓨터에선 되는데 CI에서만 실패"가 있다. 이건 플레이키가 아니라 환경 차이라서 매번 같은 결과가 나온다. 시간대가 대표적이다. 주문 시각으로 주문일을 만드는 함수를 로컬 시간대 기준으로 짜면, 한국에 있는 노트북에서는 통과하고 UTC로 도는 러너에서는 실패한다.

```bash
# 같은 테스트를 시간대만 바꿔 돌린다
TZ=Asia/Seoul node --test --test-reporter=spec tz.test.js
TZ=UTC node --test --test-reporter=spec tz.test.js
```

```text
✔ 자정 직후 주문은 그날 주문이다 (1.765179ms)
...
✖ 자정 직후 주문은 그날 주문이다 (3.499248ms)
ℹ pass 0
ℹ fail 1
```

GitHub이 주는 러너의 시간대는 UTC다. 로케일, 대소문자를 구분하는 파일 시스템(macOS 기본은 구분하지 않고 Linux는 구분한다), Node 버전도 같은 종류의 차이를 만든다. 런타임 버전은 `.nvmrc`나 `packageManager` 필드로 고정하고, CI에서도 그 값을 읽어 쓴다.

플레이키 테스트를 다루는 순서는 이렇다. 먼저 실패 기록을 모은다. 같은 커밋에서 성공과 실패가 둘 다 나온 테스트가 플레이키다. 찾으면 격리(quarantine)한다. 필수 검사에서 빼서 따로 돌리되, 결과는 계속 기록한다. 그리고 주인을 정해 기한 안에 고친다. 자동 재시도는 쓰더라도 "재시도로 통과했다"는 사실을 숨기지 않고 보고에 남긴다. 재시도로 초록불을 만들기만 하면 플레이키가 쌓이는 걸 아무도 모른다.

## 파이프라인의 속도를 재는 네 가지 숫자

"우리 배포는 괜찮은가"를 감으로 말하면 끝이 없다. DORA(DevOps Research and Assessment) 연구팀이 수년간 조사해서 정리한 네 가지 지표가 흔히 쓰인다. 흔히 DORA 지표라고 부른다.

- 배포 빈도: 운영에 얼마나 자주 배포하나.
- 변경 리드 타임: 커밋이 운영에 닿기까지 얼마나 걸리나.
- 변경 실패율: 배포 중 장애나 롤백·핫픽스로 이어진 비율.
- 복구 시간: 배포 때문에 생긴 장애에서 회복하는 데 걸린 시간. 2023년 보고서부터 "실패한 배포 복구 시간"이라는 이름으로 바뀌었다.

앞의 둘은 속도, 뒤의 둘은 안정성이다. DORA 연구에서 반복해서 나온 결과는 둘이 맞바꾸는 관계가 아니었다. 잘하는 팀은 자주 배포하면서 실패율도 낮다. 변경이 작을수록 무엇이 깨졌는지 찾기 쉽고 되돌리기도 쉬워서다. 2024년 보고서부터는 계획에 없던 배포(핫픽스 같은 재작업) 비율도 함께 보는데, 지표 정의는 해마다 조금씩 다듬어지니 인용할 때는 몇 년도 보고서인지 밝힌다.

숫자를 내는 건 어렵지 않다. 배포 기록에 "어떤 커밋이 언제 만들어졌고 언제 배포됐는지, 실패였는지, 언제 회복했는지"만 있으면 된다. 아래 함수를 채워 보자. 시각은 계산을 쉽게 하려고 시작 시점부터 흐른 시간(시간 단위)으로 준다. 리드 타임과 복구 시간은 평균 대신 중앙값을 쓴다. 한 건이 사흘 걸리면 평균이 크게 흔들리기 때문이다.

## 파이프라인이 느려지는 자리

리드 타임을 쪼개 보면 파이프라인 실행 시간은 일부일 뿐이다. 리뷰를 기다리는 시간, 승인을 기다리는 시간, 배포 창을 기다리는 시간이 대개 더 길다. 그래도 파이프라인 자체가 느리면 사람이 기다리지 않고 다른 일을 시작하고, 결과를 늦게 보고, 실패를 늦게 고친다. 커밋 후 첫 피드백(lint와 단위 테스트)은 몇 분 안에 와야 한다는 게 오래된 경험칙이다. 익스트림 프로그래밍에서 말하던 "10분 빌드"가 그 기준이다.

느려지는 이유는 대개 세 가지다. 매번 의존성을 처음부터 받는다면 캐시가 없는 것이다. 이건 [빌드 캐시](/posts/build-caching)에서 따로 다룬다. 서로 상관없는 잡을 줄줄이 묶었다면 `needs`를 정리해 병렬로 돌린다. lint와 단위 테스트, 타입 검사는 서로 기다릴 이유가 없다. 테스트 하나가 수백 개로 커졌다면 여러 러너로 나눠(sharding) 돌린다. 모노레포라면 바뀐 경로에 해당하는 것만 돌리도록 경로 필터를 건다.

act 출력에는 단계마다 걸린 시간이 붙는다. GitHub에서도 잡 화면에 같은 정보가 있다. 느리다고 느껴지면 감으로 고치지 말고 단계별 시간부터 본다. "Set up job"이 길면 러너를 기다리는 것이고, 의존성 설치가 길면 캐시 문제고, 테스트가 길면 테스트 자체 문제다.

## CI 도구는 잡이 어디서 도는지로 고른다

지금까지의 뼈대는 도구와 상관없다. 그래도 도구를 골라야 할 때 처음 갈리는 질문은 문법이 아니라 "잡을 돌리는 기계(러너, 에이전트)가 누구 것인가"다.

호스티드 러너는 CI 업체가 매번 깨끗한 VM이나 컨테이너를 내준다. 관리할 게 없고, 잡이 끝나면 기계가 사라지니 잡끼리 흔적이 섞이지 않는다. 대신 분 단위로 돈을 내고, 사내망에 있는 DB나 저장소에 닿으려면 길을 따로 열어야 하며, GPU나 큰 메모리 같은 특수 사양은 비싸거나 고를 수 없다. 셀프 호스티드 러너는 내 서버에서 에이전트가 돌며 일을 받아 간다. 사내망과 캐시를 그대로 쓰고 사양도 마음대로지만, 러너의 패치·확장·청소가 내 일이 된다. 공개 저장소에 셀프 호스티드 러너를 붙이면 누구나 PR로 내 서버에서 코드를 돌릴 수 있게 되니 특히 조심한다. 대부분의 도구가 두 방식을 다 지원하니 "기본은 호스티드, 사내망이 필요한 잡만 셀프 호스티드"로 섞는 일이 흔하다.

그 위에서 도구들은 이렇게 자리 잡고 있다.

- GitHub Actions: 코드가 GitHub에 있으면 기본 선택지다. `.github/workflows/*.yml`에 적고, 남이 만든 액션을 가져다 붙이기 쉽다. 문법과 OIDC 연동은 [GitHub Actions 워크플로](/posts/github-actions-workflows)에서 봤다.
- GitLab CI: `.gitlab-ci.yml`에 stage와 job을 적고 GitLab Runner가 실행한다. 코드 저장소, 컨테이너·패키지 레지스트리, 환경별 배포 기록까지 한 제품에 들어 있어서, GitLab 자체를 사내에 설치해 전부 내부에서 돌리려는 곳이 많이 쓴다.
- Jenkins: 서버(컨트롤러)를 직접 설치하고 에이전트를 붙인다. `Jenkinsfile`(Groovy)과 플러그인으로 거의 무엇이든 만들 수 있지만, 플러그인 버전 충돌과 보안 업데이트를 누군가 계속 챙겨야 한다. 자세한 구조는 [Jenkins 파이프라인](/posts/jenkins-pipeline-basics)에 있다.
- CircleCI: SaaS 전용으로 시작한 도구다. `.circleci/config.yml`, 재사용 설정 묶음(orb), 잡마다 고르는 실행 사양(resource class), Docker 레이어 캐시 같은 빌드 속도 기능이 강점이고 셀프 호스티드 러너도 붙일 수 있다.
- TeamCity: JetBrains 제품으로 설치형과 클라우드형이 있다. 빌드 사이의 의존 관계(빌드 체인)를 화면에서 다루기 좋고 설정을 Kotlin DSL로 코드화한다. JVM·.NET처럼 빌드가 크고 단계가 많은 프로젝트에서 자주 본다.
- Buildkite: 화면과 일정 관리는 Buildkite가 SaaS로 맡고, 잡은 전부 내 기계의 에이전트가 돌린다. 소스와 비밀 값이 사내를 벗어나지 않으면서 CI 서버 자체를 운영할 필요는 없는 중간 형태다. 파이프라인을 실행 중에 만들어 올리는 동적 파이프라인도 특징이다.

Octopus Deploy는 위 도구들과 층이 다르다. 빌드는 하지 않고, CI가 만든 패키지를 받아 "어느 환경에 어떤 순서로 내보낼지"만 맡는 배포 전용 도구다. 릴리스, 환경, 승격 규칙(라이프사이클), 운영 작업 스크립트(런북), 고객사마다 따로 배포하는 테넌트 같은 개념을 기본으로 준다. 앞에서 본 "한 번 빌드하고 승격한다"를 제품으로 만든 셈이다. 쿠버네티스에서는 같은 자리를 ArgoCD 같은 GitOps 도구가 채우고, CI와 CD를 나누는 이유는 [Jenkins와 ArgoCD의 push·pull](/posts/jenkins-argocd-push-pull)에서 다뤘다.

고를 때 현실적으로 따지는 순서는 이렇다. 코드가 어디 있는가(GitHub이면 Actions, GitLab이면 GitLab CI가 마찰이 가장 적다). 잡이 사내망에 닿아야 하는가(셀프 호스티드나 Buildkite 같은 하이브리드). 빌드 분이 얼마나 되는가(호스티드 요금이 서버 몇 대 값을 넘는 순간이 온다). 그리고 이미 쌓인 Jenkins 잡이 수백 개라면 옮기는 비용이 대부분의 장점보다 크다.

## 배포가 깨졌을 때 파이프라인에서 먼저 볼 것

증상별로 정리하면 이렇다.

로컬은 통과하는데 CI만 실패한다면 매번 실패하는지부터 본다. 매번이면 환경 차이(시간대, 로케일, 런타임 버전, 대소문자, 환경 변수 누락)이고, 가끔이면 플레이키다. CI 로그에서 런타임 버전을 찍는 줄(`node -v`)과 실패한 테스트 이름이 단서다.

CI는 초록불인데 운영에서 깨졌다면 운영에 나간 것이 정말 테스트한 그것인지 확인한다. 배포 기록의 이미지 digest나 아티팩트 해시를 빌드 로그의 값과 비교한다. 다르면 어딘가에서 다시 빌드했거나 태그가 덮어씌워진 것이다. 같다면 설정 차이(환경 변수, 시크릿, 외부 서비스 주소)를 본다.

배포가 됐는데 아무도 모른다면 알림과 기록이 없는 것이다. 배포할 때마다 커밋 SHA와 시각, 배포한 사람(또는 워크플로 실행 번호)을 남겨 두면, 장애가 났을 때 "그 시각 직전에 무엇이 나갔나"를 바로 답할 수 있다. 대시보드의 에러율 그래프에 배포 시점을 세로선으로 찍어 두는 것만으로도 원인 추적이 훨씬 빨라진다.

마지막으로, 파이프라인 정의도 코드다. 워크플로 파일을 PR로 리뷰하고, 운영 배포 잡에 쓰는 권한은 그 잡에만 준다. 아무 브랜치에서나 운영 배포 잡을 돌릴 수 있다면 리뷰를 우회하는 길이 열려 있는 셈이다. 이 부분은 [environment와 승인 설정](/posts/github-actions-docker-ecr)에서 구체적으로 다뤘다.

## 같은 커밋이 아니라 같은 파일

CI/CD에서 기억할 것은 둘이다. 변경을 작게 자주 합치고 매번 자동으로 확인한다. 그리고 확인한 바로 그 결과물을 다시 만들지 않고 환경을 따라 옮긴다. 처음의 금요일 사고는 두 번째를 어긴 것이었다. 이 위에서 배포 속도를 더 올리려면 [빌드 캐시](/posts/build-caching)로 기다리는 시간을 줄이고, 배포와 공개를 떼어 놓으려면 [피처 플래그](/posts/feature-flags)를, 잘못 나갔을 때를 대비하려면 [롤백 전략](/posts/rollback-strategy)을 본다.

## 면접에서 나올 만한 질문

### 지속적 전달과 지속적 배포는 어떻게 다른가요?

운영 반영에 사람의 결정이 남아 있느냐가 다르다. 지속적 전달은 모든 커밋을 언제든 운영에 낼 수 있는 상태로 만들고, 운영 배포만 사람이 버튼으로 정한다. 지속적 배포는 검사를 통과하면 승인 없이 운영까지 간다. 지속적 배포를 하려면 테스트 신뢰도와 피처 플래그, 빠른 롤백이 받쳐 줘야 한다.

### 지속적 통합에서 "통합"이 의미하는 건 무엇인가요?

CI 서버를 두는 게 아니라, 변경을 자주(적어도 하루에 한 번) main에 합치는 습관이다. 브랜치를 오래 들고 있으면 합칠 때 충돌과 숨은 상호작용이 한꺼번에 터지고 원인을 찾기 어렵다. 자동 빌드와 테스트는 그 잦은 합치기를 안전하게 만드는 장치다.

### 왜 환경마다 다시 빌드하면 안 되나요?

같은 커밋이라도 다시 빌드하면 다른 결과물이 나올 수 있어서다. 열려 있는 의존성 범위, `latest` 베이스 이미지, 빌드 시각이 결과물에 섞인다. 그러면 스테이징에서 확인한 것과 운영에 나간 것이 달라진다. 한 번 빌드해 digest를 기록하고 그 파일을 환경을 따라 승격하며, 환경 차이는 배포 시점의 설정으로 넣는다.

### 프런트엔드 빌드에 환경별 API 주소가 박혀 있으면 어떻게 하나요?

`NEXT_PUBLIC_*`처럼 빌드 시점에 번들에 들어가는 값이 있으면 그대로는 승격할 수 없다. 실행 시점에 설정 파일(예: `/config.json`)을 받아 오게 바꾸거나, 서버에서 렌더링할 때 값을 주입하는 구조로 바꾼다. 어쩔 수 없이 환경별로 빌드한다면, 적어도 의존성 잠금과 재현 가능한 빌드로 차이를 줄이고 운영 빌드도 스테이징을 거치게 한다.

### 플레이키 테스트는 어떻게 다루나요?

같은 커밋에서 성공과 실패가 둘 다 나온 기록으로 찾고, 필수 검사에서 격리하되 결과는 계속 모으고, 주인과 기한을 정해 고친다. 원인은 대개 실제 시계, 테스트 순서 의존, 공유 자원, 외부 네트워크, 경쟁 조건이다. 자동 재시도를 쓰더라도 재시도로 통과한 사실을 보고에 남겨야 플레이키가 쌓이는 걸 알 수 있다.

### DORA 네 가지 지표는 무엇이고 어떻게 쓰나요?

배포 빈도, 변경 리드 타임, 변경 실패율, 복구 시간이다. 앞의 둘은 속도, 뒤의 둘은 안정성인데 잘하는 팀은 둘 다 좋다는 게 연구 결과다. 배포 기록(커밋 시각, 배포 시각, 실패 여부, 회복 시각)만 있으면 계산할 수 있고, 리드 타임은 중앙값으로 본다. 팀 평가 점수로 쓰면 숫자를 조작하게 되므로 병목을 찾는 데 쓴다.

### main이 깨졌는데 고치는 데 시간이 걸린다면 어떻게 하나요?

원인 커밋을 먼저 revert해서 main을 초록불로 돌리고, 수정은 다시 PR로 올린다. 깨진 main 위에 다른 변경이 계속 쌓이면 무엇이 무엇을 깨뜨렸는지 가리기 어려워지고 모두가 막힌다. 각각은 통과한 PR 두 개가 합쳐서 깨지는 일을 막으려면 머지 큐로 합친 상태를 한 번 더 테스트한다.

### CI는 통과했는데 운영에서만 문제가 나면 무엇부터 보나요?

운영에 나간 아티팩트의 digest가 빌드 로그의 값과 같은지부터 본다. 다르면 중간에 다시 빌드했거나 태그가 덮어씌워진 것이다. 같다면 결과물이 아니라 설정 차이(환경 변수, 시크릿, 연결된 외부 서비스)를 의심하고, 배포 시각과 에러율 그래프를 겹쳐 보며 그 시각에 무엇이 바뀌었는지 좁힌다.
