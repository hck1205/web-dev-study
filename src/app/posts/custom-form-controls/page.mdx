디자인 시안에 동그란 체크박스가 있었다. 네이티브 체크박스는 네모라서, 빨리 끝내려고 `div` 하나에 클릭 핸들러를 붙이고 체크 표시를 배경 그림으로 그렸다. 마우스로 눌러 보면 잘 된다. QA에서 돌아온 내용은 이랬다. Tab 키로 가면 그 칸을 건너뛴다. 스크린리더는 "약관 동의"라는 글자만 읽고 체크 여부를 말하지 않는다. 폼을 제출하면 서버에 값이 안 간다.

```html
<div class="round-check" onclick="toggle(this)">약관 동의</div>
```

이 글은 체크박스, 라디오, 스위치, 셀렉트, 여러 줄 입력칸을 디자인대로 꾸미면서 브라우저가 공짜로 주던 기능을 잃지 않는 법을 본다. 입력 타입과 제약 검증, 오류 문구를 칸에 잇는 법은 [폼 입력과 검증](/posts/html-form-validation)에서, ARIA의 기본 규칙과 로빙 tabindex는 [ARIA와 키보드·포커스 관리](/posts/aria-keyboard-focus)에서 다뤘으니 여기서는 짧게 넘긴다. 실험은 Chromium 141(Playwright)에서 돌렸고, 다른 브라우저와 다른 곳은 따로 적는다.

## div로 만든 체크박스가 잃어버린 것

먼저 무엇을 잃었는지 재 봤다. 같은 페이지에 `div` 체크박스와 진짜 `input type="checkbox"`를 나란히 두고, 접근성 트리(브라우저가 보조 기술에 넘기는 의미 트리)를 덤프했다.

```text
generic ""
StaticText "약관 동의"
checkbox " 약관 동의" focusable=true checked="false"
```

`div`는 역할 없는 `generic`이고 글자만 남는다. 진짜 체크박스는 역할(checkbox), 이름, 상태(checked), 포커스 가능 여부를 다 갖고 있다. 스크린리더가 "약관 동의, 체크박스, 선택 안 됨"이라고 읽을 재료가 바로 이것이다.

잃은 것을 적어 보면 생각보다 길다.

- Tab 순서에 들어가는 것, 포커스 링
- Space로 토글하는 키보드 동작
- 라벨 글자를 눌러도 토글되는 것
- 역할과 체크 상태를 보조 기술에 알리는 것
- 폼을 제출할 때 `name=value`로 함께 가는 것, `required` 검증, 폼 리셋
- 고대비 모드(Windows의 forced colors)에서 시스템 색으로 다시 그려지는 것

`div`에 `role="checkbox"`, `tabindex="0"`, `aria-checked`, keydown 처리기를 붙이면 앞의 셋은 되살릴 수 있다. 폼 제출, 검증, 리셋은 숨은 input을 따로 두거나 ElementInternals로 폼 연동 커스텀 요소를 만들어야 한다. 모양 하나 때문에 이걸 다 다시 만드는 건 손해다. 그래서 방향을 바꾼다. 진짜 input은 남기고 모양만 바꾼다.

## 진짜 input을 남기고 모양만 바꾸는 세 단계

바꾸고 싶은 게 색뿐이면 `accent-color` 한 줄이면 된다. 체크박스, 라디오, range, progress의 강조색을 바꾼다. 2022년 이후의 크롬, 파이어폭스, 사파리가 모두 지원한다.

```css
input[type="checkbox"],
input[type="radio"] {
  accent-color: var(--color-accent);
}
```

브라우저가 체크 표시 색과 대비를 알아서 맞춰 준다. 모양(동그라미, 크기, 테두리 두께)은 못 바꾼다.

모양까지 바꾸려면 `appearance: none`을 쓴다. 브라우저 기본 그림을 지우고, input 자체를 빈 상자로 만들어 CSS로 다시 그린다. 요소는 그대로 input이라 역할, 키보드, 폼 동작이 다 남는다. 실험에서 `appearance: none`을 준 체크박스도 접근성 트리에 `checkbox "C appearance none"`으로 나왔고, 포커스한 뒤 Space를 누르면 `checked`가 바뀌었다.

```css
.round-check {
  appearance: none;
  inline-size: 1.25rem;
  block-size: 1.25rem;
  border: 2px solid var(--color-border-strong);
  border-radius: 50%;
  display: inline-grid;
  place-content: center;
  margin: 0;
}

.round-check::before {
  content: "";
  inline-size: 0.6rem;
  block-size: 0.6rem;
  border-radius: 50%;
  background: var(--color-on-accent);
  scale: 0;
  transition: scale 120ms ease-out;
}

.round-check:checked {
  background: var(--color-accent);
  border-color: var(--color-accent);
}

.round-check:checked::before {
  scale: 1;
}
```

input은 내용을 갖지 않는 요소(대체 요소)라 `::before`가 붙지 않을 것 같지만, `appearance: none`을 준 체크박스와 라디오에는 크롬, 파이어폭스, 사파리 모두 `::before`를 그린다. 그래도 그림이 복잡하면(아이콘, 두 겹 테두리) 세 번째 방법이 편하다.

세 번째는 input을 눈에만 안 보이게 숨기고, 옆의 형제 요소에 모양을 그리는 방법이다. 여기서 흔한 실수가 `display: none`이다. 실험 결과를 보자.

```text
after label click [ true, true, true ]
tab [ 'b', 'c', 'BODY' ]
ax "B 투명"
ax "C appearance none"
```

A는 `display: none`, B는 크기 1px에 `opacity: 0`, C는 `appearance: none`이다. 라벨을 눌러 토글하는 건 셋 다 됐다. 그래서 마우스로만 확인하면 문제가 안 보인다. 그런데 Tab 순서와 접근성 트리에서 A가 통째로 사라졌다. `display: none`과 `visibility: hidden`은 요소를 렌더링 트리와 접근성 트리에서 빼 버린다. 숨길 때는 화면 밖이 아니라 "크기만 0에 가깝게" 숨긴다.

```css
.visually-hidden-input {
  position: absolute;
  inline-size: 1px;
  block-size: 1px;
  opacity: 0;
  margin: 0;
}

/* 모양은 바로 뒤 형제에 그린다 */
.visually-hidden-input + .box { /* 기본 모양 */ }
.visually-hidden-input:checked + .box { /* 체크된 모양 */ }
.visually-hidden-input:focus-visible + .box {
  outline: 2px solid var(--color-focus);
  outline-offset: 2px;
}
.visually-hidden-input:disabled + .box { /* 비활성 모양 */ }
```

이 방법에서는 input이 실제로 눌리는 자리와 그림 자리가 다르다. input을 그림 위에 같은 크기로 겹쳐 두면(`inset: 0`) 탭 대상 크기도 맞고, 브라우저 자동화 도구가 그 좌표를 누를 때도 엇갈리지 않는다. 아래 그림은 그림 쪽을 눌렀을 때 무슨 일이 일어나는지 순서대로 보여 준다.

## 반쯤 선택된 체크박스

"전체 선택" 체크박스는 아래 항목이 일부만 선택되면 가로줄 모양이 된다. 이 세 번째 상태가 indeterminate다. HTML 속성이 아니라 자바스크립트 속성으로만 켤 수 있다.

```text
attr indeterminate -> false
matches :indeterminate true
after click [ true, false, [ true, false ] ]
```

첫 줄은 마크업에 `indeterminate`라고 써 둔 체크박스다. 아무 효과가 없다. 둘째 줄은 `el.indeterminate = true`로 켠 뒤 `:indeterminate` 선택자에 걸리는지 본 것이다. 접근성 트리에서도 `checked="mixed"`로 나왔다. 셋째 줄이 중요하다. 반쯤 상태에서 클릭하면 indeterminate는 꺼지고 checked가 켜진다. change 이벤트가 뜰 때 이미 그 상태다.

indeterminate는 보이는 모양일 뿐이다. 제출 값에는 영향이 없다. 반쯤 상태여도 checked가 false면 폼 데이터에 안 들어간다. 실험에서 `name="all"` 체크박스를 반쯤 상태로 두고 `FormData`를 찍었더니 목록에 없었다.

React에는 indeterminate prop이 없어서 ref로 넣는다.

```tsx
function ParentCheckbox({ state, onToggle }: {
  state: "checked" | "unchecked" | "mixed";
  onToggle: () => void;
}) {
  const ref = useRef<HTMLInputElement>(null);
  useEffect(() => {
    if (ref.current) ref.current.indeterminate = state === "mixed";
  }, [state]);
  return (
    <label>
      <input ref={ref} type="checkbox" checked={state === "checked"} onChange={onToggle} />
      전체 선택
    </label>
  );
}
```

부모의 상태는 저장하지 않고 자식 목록에서 계산한다. 따로 저장하면 자식을 하나 바꿀 때마다 두 곳을 맞춰야 하고, 언젠가 어긋난다. 직접 써 보자.

## 스위치는 체크박스와 언제 다른가

모양이 다른 게 아니라 약속이 다르다. 체크박스는 "고른 뒤 제출 버튼을 누르면 반영된다"이고, 스위치는 "누르는 순간 반영된다"다. 설정 화면의 "알림 받기"처럼 바로 켜지고 꺼지는 것은 스위치, 가입 폼의 "마케팅 수신 동의"처럼 제출해야 의미가 생기는 것은 체크박스다. 둘을 섞으면 사용자는 스위치를 켜고 저장 버튼을 찾거나, 체크박스를 누르고 바로 저장됐다고 믿는다.

보조 기술에도 그 차이를 알린다. ARIA의 `switch` 역할은 "켜짐/꺼짐"으로 읽힌다. 아래 조각을 하나씩 눌러 보자.

/>

버튼 대신 `input type="checkbox" role="switch"`로 만들어도 된다. 이러면 폼 제출, Space 토글을 input이 그대로 해 주고, 읽는 방식만 스위치가 된다. 사파리 17.4부터는 `input type="checkbox" switch`라는 속성으로 네이티브 스위치 모양을 그려 주는데, 다른 브라우저는 이 속성을 모르고 그냥 체크박스로 보인다. 모양을 직접 그릴 거라면 아직은 role을 쓰는 쪽이 예측하기 쉽다.

바로 반영되는 스위치에는 하나가 더 붙는다. 서버 저장이 실패하면 어떻게 하나. 누르는 순간 켜진 모양으로 바꾸고(낙관적 업데이트) 실패하면 되돌리면서 이유를 알려 준다. 되돌리기만 하고 말이 없으면 사용자는 자기가 잘못 누른 줄 안다.

## 라디오 그룹은 Tab 한 번, 방향키로 고른다

같은 `name`을 가진 라디오는 브라우저가 한 묶음으로 다룬다. 이걸 눈으로 확인해 보면 키보드 동작이 체크박스와 꽤 다르다. 실험에서 세 라디오(일반, 빠른, 새벽) 중 일반이 선택된 상태로 Tab을 돌리고 방향키를 눌렀다.

```text
tab order cb > all > sw > r1 > d2 > adb > ta > sel > BODY
after ArrowDown [ 'r2', 'r2' ]
after 2 more [ 'r1', 'r1' ]
```

Tab 순서에 라디오는 선택된 r1 하나만 나온다. 묶음 전체가 Tab 한 칸이다. 방향키는 포커스와 선택을 같이 옮긴다. 마지막에서 한 번 더 누르면 처음으로 돌아간다. 아래 그림으로 따라가 보자.

여기서 두 가지 설계가 갈린다. 첫째, 방향키만 눌러도 선택이 바뀌니 change 핸들러에서 무거운 일(요청 보내기, 화면 전체 바꾸기)을 하면 안 된다. 사용자는 세 번째 항목에 가려고 방향키를 두 번 눌렀을 뿐인데 요청이 두 번 나간다. 둘째, 라디오 모양을 카드나 버튼 모양으로 바꿔도 input은 라디오로 남겨야 이 키보드 동작이 공짜로 따라온다. 카드형 선택지를 `div role="radio"`로 새로 만들면 로빙 tabindex와 방향키를 직접 짜야 한다. 그 방법은 [ARIA와 키보드·포커스 관리](/posts/aria-keyboard-focus)에 있다.

묶음에는 `fieldset`과 `legend`로 질문을 붙인다. "배송 방법" 같은 질문이 없으면 스크린리더 사용자는 "빠른, 라디오 버튼, 3개 중 2번째"만 듣고 무엇을 고르는지 모른다.

## 셀렉트: base-select가 열어 준 문

`select`는 오랫동안 꾸밀 수 없는 컨트롤이었다. 닫힌 상자는 어느 정도 바뀌지만 펼친 목록은 운영체제가 그려서 손댈 수 없었다. 그래서 많은 팀이 버튼과 목록으로 셀렉트를 새로 만들었다. 이 비용이 꽤 크다. WAI-ARIA의 콤보박스·리스트박스 패턴을 따르려면 방향키 이동, Home·End, 글자를 치면 그 글자로 시작하는 항목으로 가는 기능, Esc로 닫고 원래 버튼으로 포커스 돌리기, `aria-activedescendant` 또는 로빙 포커스, 화면 끝에서 위로 펼치기, 스크롤 컨테이너 안에서 잘리지 않게 하기, 모바일에서 손가락으로 고르기까지 다 해야 한다. 휴대폰의 네이티브 선택 휠도 잃는다.

크로미움 135부터 들어온 customizable select가 이 문을 열었다. `appearance: base-select`를 주면 셀렉트와 펼친 목록(`::picker(select)`)을 CSS로 꾸밀 수 있고, 옵션 안에 아이콘 같은 내용도 넣을 수 있다. 실험한 크로미움 141에서는 `CSS.supports('appearance', 'base-select')`가 true였다.

```css
select,
::picker(select) {
  appearance: base-select;
}

select {
  border: 1px solid var(--color-border-strong);
  border-radius: var(--radius-md);
  padding: 0.5rem 0.75rem;
}

::picker(select) {
  border-radius: var(--radius-md);
  box-shadow: var(--shadow-lg);
}

option:checked {
  background: var(--color-accent-soft);
}
```

```html
<select name="fruit">
  <button><selectedcontent></selectedcontent></button>
  <option value="apple"><span aria-hidden="true">🍎</span> 사과</option>
  <option value="pear"><span aria-hidden="true">🍐</span> 배</option>
</select>
```

`selectedcontent`는 고른 옵션의 내용을 닫힌 상자 안에 복제해 보여 준다. 지원하지 않는 브라우저는 `appearance: base-select`를 모르는 값으로 무시하고 평범한 셀렉트를 그린다. 옵션 안의 꾸밈은 빠지고 글자만 남는다. 이렇게 점진적으로 좋아지는 방식이라 지금 써도 깨지지는 않는다. 다만 크로미움 밖에서는 이 글을 쓰는 시점에 직접 확인하지 못했으니, 쓸 때는 대상 브라우저의 지원표를 다시 본다.

판단 기준은 이렇다. 고르는 항목이 문자열 목록이면 네이티브 `select`에 base-select를 얹는다. 검색해서 거르는 목록, 여러 개 고르기에 태그가 붙는 입력, 항목을 비동기로 불러오는 자동 완성은 셀렉트가 아니라 콤보박스라 결국 직접 만들거나 검증된 헤드리스 라이브러리를 쓴다. 이 경우 라이브러리가 키보드 패턴을 맞춰 주는지 먼저 확인한다.

## 내용만큼 자라는 입력칸

댓글 칸은 처음에 한 줄이었다가 글이 길어지면 늘어나야 한다. 예전에는 input 이벤트마다 높이를 `auto`로 줄였다가 `scrollHeight`로 다시 맞추는 코드를 썼다. 이 코드는 입력할 때마다 레이아웃을 강제로 다시 계산하게 만든다.

이제는 CSS 한 줄이다. `field-sizing: content`는 입력칸 크기를 내용에 맞춘다. 실험에서 줄 높이 20px인 `textarea`에 세 줄을 쳤다.

```text
ta heights [ 20, 60 ]
```

빈 칸일 때 20px, 세 줄을 친 뒤 60px이 됐다. 끝없이 자라면 화면을 밀어내니 최소·최대 높이를 함께 준다.

```css
textarea.auto {
  field-sizing: content;
  min-block-size: 3lh;   /* 세 줄은 처음부터 보이게 */
  max-block-size: 12lh;  /* 그 뒤로는 칸 안에서 스크롤 */
}
```

`field-sizing`은 크로미움 123부터 들어갔다. 지원하지 않는 브라우저에서는 고정 높이로 남으니 그대로 써도 쓸 수는 있다. 꼭 자라야 하면 `@supports not (field-sizing: content)`일 때만 예전 스크립트를 붙인다. `input`에도 먹어서, 입력한 글자만큼 넓어지는 짧은 칸(태그 입력, 인라인 편집)에 쓸 수 있다.

## 라벨은 위에, 오류는 칸 바로 아래에

컨트롤을 꾸미다 보면 라벨과 오류 자리도 바뀐다. 몇 가지는 정해 두는 편이 낫다.

라벨은 칸 위에 둔다. 모바일 폭에서 왼쪽 라벨은 칸을 좁히고, 길어지면 줄이 바뀐다. 위에 둔 라벨은 눈이 위에서 아래로 한 줄로 내려가며 읽는다. 체크박스와 라디오만 예외로 라벨을 컨트롤 오른쪽에 둔다.

placeholder를 라벨 대신 쓰지 않는다. 입력을 시작하면 사라져서, 무엇을 적던 칸인지 확인하려면 다 지워야 한다. 대비도 대개 낮다. 칸 안의 placeholder가 위로 올라가는 floating label은 이 문제를 줄이지만, 올라간 글자가 작아지고 대비가 떨어지기 쉬워서 크기와 색을 따로 검사해야 한다.

오류는 칸 바로 아래에, 무엇이 틀렸고 어떻게 고치는지를 글자로 쓴다. 빨간 테두리만으로는 색을 구분하기 어려운 사람에게 아무 정보가 없다. 아이콘과 글자를 같이 두고, `aria-describedby`로 칸에 잇고, `aria-invalid`를 켠다. 자세한 연결 방법과 `:user-invalid`로 처음부터 빨간 칸이 되지 않게 하는 법은 [폼 입력과 검증](/posts/html-form-validation)에 있다.

필수 표시는 별표 하나로 끝내지 않는다. 별표의 뜻을 폼 위에 한 번 적거나, 라벨에 "(필수)"를 쓴다. 대부분이 필수면 반대로 "(선택)"만 붙이는 쪽이 덜 시끄럽다.

## disabled와 aria-disabled는 다르게 동작한다

"아직 누를 수 없는 버튼"을 만들 때 둘 중 무엇을 쓰느냐로 동작이 크게 갈린다. 실험한 결과다.

```text
textbox "" disabled=true
textbox "" disabled=true focusable=true
button "A" disabled=true
button "B" disabled=true focusable=true
formdata [["ship","a"],["d2","y"]]
clicks [ undefined, 1, 1 ]
```

`disabled` 속성을 준 요소(d1, A)는 접근성 트리에 비활성으로 나오고 포커스를 받지 않는다. 앞의 Tab 순서에서도 d1과 A는 빠졌다. 값은 폼 데이터에 안 들어간다. 클릭 이벤트도 뜨지 않는다.

`aria-disabled="true"`를 준 요소(d2, B)는 보조 기술에 "사용 불가"라고 알리기만 한다. 포커스를 받고, 값이 제출되고(d2=y가 들어갔다), 클릭 핸들러가 불리고, 폼 안의 버튼이면 폼까지 제출된다(마지막 숫자 1). 브라우저가 막아 주는 건 하나도 없다.

그럼 왜 aria-disabled를 쓰나. 비활성인 이유를 알려 주고 싶을 때다. `disabled` 버튼은 포커스를 받지 못하니 키보드·스크린리더 사용자는 그 버튼이 있다는 것조차 모르고 지나간다. "약관에 동의해야 결제할 수 있습니다" 같은 안내를 들려주려면 포커스가 와야 한다. 대신 막는 일은 직접 한다.

```tsx
<button
  type="submit"
  aria-disabled={!agreed}
  aria-describedby="pay-hint"
  onClick={(e) => {
    if (!agreed) e.preventDefault(); // 제출과 결제 모두 여기서 막는다
  }}
>
  결제하기
</button>
<p id="pay-hint" hidden={agreed}>약관에 동의해야 결제할 수 있다.</p>
```

규칙으로 정리하면, 화면에서 아무 의미 없는 순간(요청 중인 버튼)은 `disabled`, 왜 못 누르는지 알려야 하는 순간은 `aria-disabled`와 직접 막기다. 입력칸이라면 `disabled` 대신 `readonly`도 생각한다. 읽기 전용 칸은 포커스와 복사가 되고 값도 제출된다.

## 상태를 토큰으로 묶는다

컨트롤마다 hover, focus, checked, disabled, invalid를 따로 정하면 체크박스와 입력칸의 비활성 색이 달라지고 다크 모드에서 하나만 깨진다. 상태를 의미 토큰으로 정해 두고 모든 컨트롤이 같은 토큰을 쓴다. 토큰을 쌓는 기본 구조는 [디자인 시스템 만들기](/posts/design-system-building)에 있다.

## 꾸민 컨트롤을 점검하는 순서

리뷰나 QA에서 이 순서로 보면 대부분 걸린다.

1. 마우스를 치우고 Tab만으로 끝까지 간다. 모든 컨트롤에 포커스 링이 보이는지, 라디오 묶음이 한 칸인지 본다.
2. Space로 체크박스와 스위치를, 방향키로 라디오를 바꾼다. 바뀔 때 무거운 요청이 나가지 않는지 네트워크 탭을 같이 본다.
3. DevTools의 Elements › Accessibility 패널에서 컨트롤마다 역할, 이름, 상태(checked, mixed, disabled)를 확인한다. generic이나 이름이 빈 컨트롤이 있으면 고친다.
4. 폼을 제출하고 요청 본문에 값이 다 있는지 본다. 숨긴 input을 `display: none`으로 했다면 여기서는 멀쩡하고 1, 3번에서 걸린다.
5. 다크 모드, 200% 확대, Windows 고대비(또는 DevTools의 forced-colors 에뮬레이션)에서 체크 표시가 보이는지 본다.
6. 휴대폰에서 탭 대상이 44px 이상인지, 라벨 글자를 눌러도 토글되는지 본다.

## 진짜 부품 위에 페인트만

꾸밀 수 있는 정도는 `accent-color`, `appearance: none`, 숨긴 input 위에 그리기 순으로 넓어지고, 어느 쪽이든 상태와 키보드와 제출은 진짜 input이 맡는다. 스위치는 바로 반영된다는 약속, 라디오는 방향키 한 묶음, indeterminate는 모양뿐이라는 점, `aria-disabled`는 아무것도 막지 않는다는 점을 기억하면 꾸미는 범위를 넓혀도 기능이 새지 않는다. 셀렉트처럼 예전엔 새로 만들어야 했던 것도 base-select와 field-sizing처럼 브라우저 쪽에서 문이 열리고 있으니, 직접 만들기 전에 그 문이 열렸는지 먼저 본다.

## 면접에서 나올 만한 질문

### 체크박스 모양을 디자인대로 바꾸려면 어떻게 하나요?

진짜 input을 남기고 모양만 바꾼다. 색만 바꿀 거면 `accent-color`, 모양까지면 `appearance: none`으로 기본 그림을 지우고 CSS로 그린다. 그림이 복잡하면 input을 1px·투명으로 숨기고 형제 요소에 그리는데, 이때 `display: none`은 Tab 순서와 접근성 트리에서 빠지니 쓰지 않는다. 포커스 링은 `:focus-visible + .box`로 그림 쪽에 옮겨 그린다.

### div에 role="checkbox"를 붙이면 충분하지 않나요?

역할은 알려도 동작은 직접 만들어야 한다. `tabindex`, Space 처리, `aria-checked` 갱신을 다 붙여도 폼 제출, required 검증, 폼 리셋, 고대비 모드 대응은 여전히 없다. 그걸 채우려면 숨은 input이나 ElementInternals가 필요하니, 처음부터 input을 꾸미는 쪽이 싸다.

### indeterminate 상태는 어떻게 만들고, 제출하면 어떻게 되나요?

HTML 속성이 없어서 `el.indeterminate = true`로만 켠다. React에서는 ref와 effect로 넣는다. 모양과 접근성 트리의 `mixed` 상태만 바뀌고 제출 값은 checked를 따른다. 반쯤 상태에서 클릭하면 indeterminate는 꺼지고 checked가 켜진다. 부모 상태는 저장하지 않고 자식 목록에서 계산한다.

### 스위치와 체크박스는 언제 다르게 쓰나요?

누르는 순간 반영되면 스위치, 제출해야 반영되면 체크박스다. 스위치는 `role="switch"`와 `aria-checked`(true/false)로 켜짐·꺼짐으로 읽히게 하고, 버튼으로 만들면 `type="button"`을 꼭 준다. 바로 저장하니 실패했을 때 되돌리고 이유를 알려 주는 처리까지 함께 만든다.

### 라디오 그룹의 키보드 동작은 어떻게 되나요?

같은 name의 라디오는 Tab 순서에서 한 칸이고, 선택된 항목으로 들어온다. 방향키는 포커스와 선택을 같이 옮기고 끝에서 처음으로 돌아간다. 그래서 change 핸들러에서 요청을 보내면 방향키를 누를 때마다 요청이 나간다. 카드형으로 꾸며도 input을 라디오로 남겨야 이 동작이 공짜로 따라온다.

### disabled와 aria-disabled는 무엇이 다른가요?

`disabled`는 브라우저가 실제로 막는다. 포커스를 안 받고, 클릭이 안 되고, 값이 제출되지 않는다. `aria-disabled`는 보조 기술에 사용 불가라고 알리기만 해서 포커스, 클릭, 제출이 다 일어난다. 이유를 들려줘야 하는 버튼에는 `aria-disabled`를 쓰고 핸들러에서 직접 막는다.

### 셀렉트를 직접 만들지, 네이티브를 쓸지 어떻게 정하나요?

문자열 목록에서 하나 고르기라면 네이티브 select에 `appearance: base-select`를 얹는다. 크로미움 135부터 목록까지 꾸밀 수 있고, 모르는 브라우저는 평범한 셀렉트로 보인다. 검색해서 거르거나 여러 개를 태그로 고르는 건 콤보박스라 직접 만들거나 헤드리스 라이브러리를 쓰는데, APG의 키보드 패턴과 모바일 동작까지 비용으로 잡아야 한다.

### 폼 컨트롤의 상태 스타일은 어떻게 관리하나요?

hover, focus-visible, disabled, invalid를 의미 토큰으로 정해 모든 컨트롤이 같은 값을 쓴다. 상태가 겹칠 때 우선순위(비활성이 오류를 이긴다)를 정하고, 포커스는 `:focus-visible`, 오류는 `:user-invalid`나 `aria-invalid`로 건다. 직접 그린 모양은 forced-colors 모드에서 시스템 색으로 다시 칠해 둔다.
