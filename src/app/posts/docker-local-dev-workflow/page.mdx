Node API를 Docker로 띄우는 프로젝트에 합류했다. 로그 문구 하나를 바꾸고 결과를 보려면 `docker compose build api && docker compose up -d api`를 쳐야 했다. 의존성 캐시가 잘 잡혀 있어도 이미지를 다시 굽고 컨테이너를 갈아 끼우는 데 수십 초가 걸린다. 하루에 이걸 백 번 하면 한 시간이 사라진다. 결국 팀원 대부분은 Docker를 끄고 노트북에서 `npm run dev`로 개발했고, 노트북의 Node 버전과 이미지의 Node 버전이 달라서 생긴 버그가 운영에서 터졌다.

컨테이너는 "어디서나 같은 환경"을 주는 대신 "고친 것을 바로 보는 루프"를 느리게 만든다. 이 글은 그 루프를 다시 짧게 만드는 방법을 차례로 본다. 소스를 바인드 마운트로 꽂는 법과 그때 생기는 함정, `docker compose watch`로 바뀐 파일만 넣는 법, 개발용과 운영용 이미지를 한 Dockerfile의 target으로 나누는 법, 컨테이너 안 프로세스에 디버거를 붙이는 법, Dev Container로 편집기까지 컨테이너에 넣는 법, 테스트를 컨테이너로 돌리는 흐름이다.

기준은 Ubuntu 24.04의 Docker Engine 29와 Compose v5.6.0, Node 22다. 이 글을 쓴 환경은 Docker 데몬을 띄울 수 없어서 컨테이너를 실제로 돌리지는 못했다. 그래서 Compose 파일은 데몬 없이 도는 `docker compose config`로 검증했고, 파일 감시와 디버거는 같은 Node 22를 호스트에서 돌려 확인했다. Compose 파일 문법은 [Docker Compose 글](/posts/docker-compose), 레이어와 멀티 스테이지 빌드는 [Dockerfile과 이미지 레이어](/posts/dockerfile-image-layers)에 있다.

## 한 줄 고칠 때마다 이미지를 굽는 루프

처음 Dockerfile은 이랬다. 운영 이미지로는 흠잡을 데가 없다.

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
CMD ["node", "src/server.js"]
```

문제는 `COPY . .`다. 소스는 빌드할 때 이미지 레이어에 구워진다. 컨테이너가 보는 `src/server.js`는 내 편집기가 연 파일이 아니라 빌드 시점의 복사본이다. 그래서 파일을 저장해도 컨테이너는 모른다.

코드가 컨테이너에 닿는 길은 세 가지다. 이미지를 다시 굽는 길, 호스트 폴더를 컨테이너에 그대로 비추는 바인드 마운트, 바뀐 파일만 골라 복사하는 compose watch. 아래 그림의 점이 흐르는 방향이 코드가 이동하는 방향이다.

어느 길로 파일이 들어오든 그다음 일은 따로 있다. 파일이 바뀌었다고 이미 메모리에 올라간 Node 프로세스가 새 코드를 읽지는 않는다. 프로세스를 다시 띄우거나(`node --watch`, nodemon), 모듈만 갈아 끼우는(Vite·Next.js의 HMR) 도구가 컨테이너 안에서 돌아야 한다. 파일 전달과 다시 읽기, 이 두 단계를 나눠 생각하면 "저장했는데 안 바뀐다"를 어디서부터 볼지 정해진다.

## 소스를 바인드 마운트로 꽂으면 생기는 일

가장 흔한 방법은 프로젝트 폴더를 통째로 컨테이너의 `/app`에 비추는 것이다. 개발용 Compose 파일은 이렇게 생겼다.

```yaml
# compose.yaml (개발용)
services:
  api:
    build:
      context: .
      target: dev                 # 아래에서 볼 개발용 스테이지
    command: node --watch --inspect=0.0.0.0:9229 src/server.js
    ports:
      - "3000:3000"
      - "127.0.0.1:9229:9229"     # 디버거 포트는 내 컴퓨터에서만
    volumes:
      - ./:/app                   # 프로젝트 폴더를 그대로 비춘다
      - /app/node_modules         # 이 경로만은 컨테이너 것을 쓴다
```

짧은 문법은 Compose가 어떻게 읽었는지 눈으로 확인하는 편이 안전하다. `docker compose config`는 데몬 없이 파일을 합치고 정규화해서 보여 준다.

```bash
# 합쳐진 최종 설정을 본다 (데몬이 없어도 된다)
docker compose config
```

```text
services:
  api:
    command:
      - node
      - --watch
      - --inspect=0.0.0.0:9229
      - src/server.js
    networks:
      default: null
    volumes:
      - type: bind
        source: /home/me/api
        target: /app
        bind: {}
      - type: volume
        target: /app/node_modules
        volume: {}
```

두 줄이 다른 종류로 읽혔다. `./:/app`은 `type: bind`이고, 이름 없이 경로만 쓴 `/app/node_modules`는 `type: volume`, 즉 익명 볼륨이다. 두 번째 줄이 있는 이유는 바인드 마운트가 `/app` 아래를 통째로 가리기 때문이다. 이미지를 구울 때 `npm ci`로 만든 `/app/node_modules`가 있어도, 호스트 폴더를 덮어 씌우는 순간 컨테이너에는 호스트의 `node_modules`(없거나, 맥에서 설치한 것)가 보인다.

호스트의 `node_modules`가 보이면 순수 JS 패키지는 그럭저럭 돈다. 하지만 `bcrypt`, `sharp`처럼 네이티브 모듈이 있으면 맥이나 윈도에서 빌드한 바이너리를 리눅스 컨테이너가 읽다가 `invalid ELF header` 같은 에러로 죽는다. 익명 볼륨으로 그 경로만 따로 빼 두면 컨테이너는 이미지 안의 리눅스용 `node_modules`를 그대로 본다.

대신 익명 볼륨은 한 번 만들어지면 살아남는다. `package.json`에 패키지를 추가하고 이미지를 다시 구워도, `up`이 기존 익명 볼륨을 다시 붙이면 옛 `node_modules`가 보인다. `Cannot find module`이 뜨는데 이미지 안에는 그 패키지가 있다면 이 경우다.

```bash
# 이미지를 다시 굽고, 익명 볼륨도 새로 만들어 이미지 내용으로 채운다
docker compose up -d --build -V api     # -V = --renew-anon-volumes
```

바인드 마운트에서 하나 더 걸리는 것이 파일 소유자다. 컨테이너 안 프로세스가 root로 돌면서 `/app` 아래에 로그나 빌드 결과를 쓰면, 호스트에는 root 소유 파일이 남아 `git clean`이 권한 오류를 낸다. 리눅스 호스트에서는 개발용 스테이지에서 `USER node`로 바꾸거나 Compose의 `user: "1000:1000"`으로 내 UID를 맞춘다. 자세한 UID 이야기는 [Docker 네트워크와 볼륨](/posts/docker-network-volume)의 바인드 마운트 부분에 있다.

## 파일 감시가 컨테이너 안까지 오지 않을 때

파일이 컨테이너에 보이는 것과, 컨테이너 안의 감시 도구가 "바뀌었다"는 알림을 받는 것은 다른 이야기다. 리눅스의 감시 도구는 대부분 커널의 inotify를 쓴다. 파일이 바뀌면 커널이 이벤트를 보내 주는 방식이다. 리눅스 호스트에서 바인드 마운트를 쓰면 같은 커널이니 이벤트가 그대로 온다.

맥과 윈도는 사정이 다르다. Docker Desktop은 리눅스 VM 안에서 컨테이너를 돌리고, 호스트 폴더는 파일 공유 계층(최근 버전의 맥은 기본이 VirtioFS)을 거쳐 VM에 보인다. Docker Desktop이 호스트의 변경 이벤트를 VM 쪽으로 넘겨 주긴 하지만, 파일을 많이 읽고 쓰는 작업은 리눅스 네이티브보다 눈에 띄게 느리다. `node_modules`처럼 작은 파일 수만 개를 바인드 마운트로 읽으면 개발 서버가 뜨는 데만 한참 걸린다. 위에서 `node_modules`를 익명 볼륨으로 뺀 것은 이 속도 문제도 같이 푼다.

윈도의 WSL2에서는 위치가 중요하다. 프로젝트가 `/mnt/c/...`처럼 윈도 파일 시스템에 있으면 리눅스 쪽으로 inotify 이벤트가 오지 않아 감시 도구가 변경을 놓친다. 프로젝트를 WSL 안의 리눅스 파일 시스템(`~/projects`)에 두는 것이 가장 확실한 해결이다.

그래도 이벤트가 안 오면 감시 도구를 폴링으로 바꾼다. 일정 간격으로 파일의 수정 시각을 직접 확인하는 방식이라 CPU를 더 쓰지만 확실하다.

```yaml
services:
  web:
    environment:
      CHOKIDAR_USEPOLLING: "true"   # chokidar를 쓰는 도구(nodemon 일부 버전 등)
      WATCHPACK_POLLING: "true"     # webpack 계열 (Next.js 개발 서버)
```

Vite는 환경 변수 대신 `vite.config.ts`의 `server.watch.usePolling: true`로 켠다. 폴링은 마지막 수단으로 둔다. 감시하는 파일이 많으면 폴링 자체가 CPU를 꽤 먹는다.

리눅스 호스트에서는 반대로 감시할 수 있는 파일 수의 상한에 걸린다. 큰 모노레포에서 `ENOSPC: System limit for number of file watchers reached`가 뜨면 이 값이다.

```bash
# 사용자 하나가 걸 수 있는 inotify 감시 수
cat /proc/sys/fs/inotify/max_user_watches
```

```text
130016
```

이 값은 커널 5.11부터 메모리 크기에 따라 기본값이 정해진다. 컨테이너는 호스트 커널을 함께 쓰므로 컨테이너 안에서 바꿀 수 없고 호스트에서 올린다.

```bash
# 호스트에서 영구로 올린다
echo 'fs.inotify.max_user_watches=524288' | sudo tee /etc/sysctl.d/90-inotify.conf
sudo sysctl --system | grep inotify
```

## compose watch: 복사할 것과 다시 구울 것을 나눈다

바인드 마운트는 폴더를 통째로 비춘다. 그래서 위에서 본 `node_modules` 가리기, 파일 소유자, 맥의 파일 공유 속도 문제가 함께 따라온다. Compose의 `develop.watch`는 접근이 다르다. 호스트 쪽에서 Compose가 파일을 감시하다가, 바뀐 파일을 규칙에 따라 컨테이너로 복사하거나 이미지를 다시 굽는다. 컨테이너는 자기 파일 시스템을 그대로 쓰니 `node_modules`를 가릴 일이 없다.

```yaml
# compose.yaml
services:
  api:
    build:
      context: .
      target: dev
    ports:
      - "3000:3000"
    develop:
      watch:
        - action: sync              # 소스는 컨테이너로 복사만
          path: ./src
          target: /app/src
          ignore:
            - "**/*.test.js"
        - action: sync+restart      # 설정 파일은 복사하고 컨테이너 재시작
          path: ./config
          target: /app/config
        - action: rebuild           # 의존성이 바뀌면 이미지를 다시 굽는다
          path: package-lock.json
```

```bash
# 띄우면서 감시를 켠다. 이미 떠 있으면 docker compose watch
docker compose up --watch
```

규칙마다 무엇을 할지 고른다. 일부러 오타를 내 보면 이 버전이 받는 값이 다 나온다.

```text
validating /home/me/api/compose.yaml: services.api.develop.watch.2.action value must be one of 'rebuild', 'sync', 'restart', 'sync+restart', 'sync+exec'
```

`sync`는 파일을 복사만 한다. 컨테이너 안에서 `node --watch`나 Vite 같은 감시 도구가 돌고 있어야 새 코드가 반영된다. `sync+restart`는 복사한 뒤 컨테이너를 재시작한다. 시작할 때 한 번만 읽는 설정 파일에 맞다. `rebuild`는 이미지를 새로 굽고 컨테이너를 갈아 끼운다. lock 파일이나 Dockerfile처럼 이미지 내용을 바꾸는 파일에 건다. `sync+exec`는 복사 뒤 컨테이너 안에서 명령 하나를 실행한다.

watch에는 조건이 있다. `build`로 로컬 소스에서 이미지를 만드는 서비스만 감시한다. `image: postgres:16`처럼 받아 쓰는 이미지는 감시 대상이 아니다. 그리고 컨테이너 안에서 `target` 경로에 쓸 권한이 있어야 한다. 개발 스테이지에서 `USER node`로 바꿨다면 `/app`의 소유자도 `node`여야 복사가 실패하지 않는다.

바인드 마운트와 watch 중 무엇을 고를지는 운영체제와 프로젝트 크기로 갈린다. 리눅스 호스트에서 작은 프로젝트라면 바인드 마운트가 단순하고 빠르다. 맥·윈도에서 `node_modules`가 크거나 파일 소유자 문제로 자주 막히면 watch가 낫다. watch의 약점은 컨테이너에서 생긴 파일이 호스트로 돌아오지 않는다는 점이다. 컨테이너 안에서 `prisma generate`로 만든 타입 파일을 편집기가 봐야 한다면 그 경로만 바인드 마운트로 둔다.

## 개발용과 운영용 이미지를 target으로 나눈다

개발 컨테이너에는 운영 이미지에 없어야 하는 것이 필요하다. devDependencies, 감시 도구, 디버거, 셸 도구. 이걸 위해 `Dockerfile.dev`를 따로 만드는 팀도 있지만, 그러면 베이스 이미지 버전이나 시스템 패키지가 두 파일에서 슬금슬금 달라진다. 처음 이야기한 "노트북과 운영의 Node 버전이 달라서 생긴 버그"가 이번엔 두 Dockerfile 사이에서 생긴다.

멀티 스테이지 빌드의 스테이지에 이름을 붙이고 `target`으로 멈출 곳을 고르면 파일 하나로 둘 다 만든다.

```dockerfile
# syntax=docker/dockerfile:1
FROM node:22-alpine AS base
WORKDIR /app
COPY package*.json ./

# 개발용: devDependencies까지 설치하고 소스는 넣지 않는다 (마운트나 watch로 들어온다)
FROM base AS dev
RUN --mount=type=cache,target=/root/.npm npm ci
RUN chown -R node:node /app
USER node
CMD ["node", "--watch", "src/server.js"]

# 빌드용: 타입스크립트 컴파일 같은 일을 한다
FROM base AS build
RUN --mount=type=cache,target=/root/.npm npm ci
COPY . .
RUN npm run build

# 운영용: 런타임 의존성과 빌드 결과만
FROM base AS prod
ENV NODE_ENV=production
RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev
COPY --from=build /app/dist ./dist
USER node
CMD ["node", "dist/server.js"]
```

```bash
# 개발 이미지 (compose.yaml의 target: dev와 같다)
docker build --target dev -t api:dev .
# 운영 이미지. target을 안 주면 마지막 스테이지(prod)까지 간다
docker build -t api:prod .
```

`base` 스테이지를 함께 쓰니 Node 버전과 lock 파일이 두 이미지에서 같다. BuildKit은 target에 필요 없는 스테이지를 건너뛰어서, `--target dev`일 때는 `build`와 `prod`를 아예 실행하지 않는다.

파일을 나누는 쪽이 나을 때도 있다. 개발 환경에 브라우저, DB 클라이언트, 언어 서버까지 잔뜩 들어가서 운영 Dockerfile을 읽기 어려워지면 그때는 개발 이미지를 Dev Container 설정으로 떼어 내는 편이 깔끔하다. 이 판단 기준은 "운영 이미지의 리뷰어가 개발용 줄 때문에 헷갈리는가"다.

## 컨테이너 안 프로세스에 디버거 붙이기

`console.log`로 버티다가 결국 중단점이 필요해진다. 컨테이너 안의 Node에 디버거를 붙이려면 두 가지를 맞춘다. 인스펙터가 컨테이너의 어느 주소에서 기다리는지, 그리고 그 포트가 호스트의 어디로 나오는지.

Node의 `--inspect`는 기본으로 `127.0.0.1:9229`에서 기다린다. 컨테이너 안의 127.0.0.1은 컨테이너 자신이라, 포트를 게시해도 호스트에서 들어오는 연결이 닿지 않는다. 그래서 컨테이너 안에서는 `--inspect=0.0.0.0:9229`로 열고, 대신 호스트 쪽 게시를 `127.0.0.1:9229:9229`로 좁힌다. 인스펙터에 붙은 쪽은 그 프로세스에서 아무 코드나 실행할 수 있다. 호스트의 모든 주소로 게시하면 같은 카페 와이파이의 누구나 내 앱에서 코드를 돌릴 수 있다. 인스펙터 자체의 위험과 운영 서버에서 쓰는 법은 [Node.js 디버깅과 프로파일링](/posts/nodejs-debugging-profiling)에 있다.

`--watch`와 함께 쓰면 하나가 더 보인다. 호스트에서 같은 조합을 돌리고 파일을 한 번 고쳐 봤다.

```bash
node --watch --inspect=127.0.0.1:9229 src/server.js
```

```text

For help, see: https://nodejs.org/en/docs/inspector
listening on 3000

```

재시작하자 웹소켓 주소 끝의 UUID가 바뀌었다. 프로세스가 새로 떴으니 인스펙터도 새것이다. 예전 주소에 붙어 있던 디버거는 끊어진다. VS Code에서 `restart: true`를 주면 끊긴 뒤 같은 포트에 다시 붙는다. 그리고 소스 위치를 맞춰 줘야 중단점이 걸린다. 컨테이너 안 경로는 `/app/src/...`이고 편집기가 연 파일은 `/home/me/api/src/...`이라 서로 다른 파일로 보인다.

```json
// .vscode/launch.json
{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "node",
      "request": "attach",
      "name": "Attach to api container",
      "address": "127.0.0.1",
      "port": 9229,
      "localRoot": "${workspaceFolder}",
      "remoteRoot": "/app",
      "restart": true
    }
  ]
}
```

중단점이 회색 빈 원으로 남고 걸리지 않으면 대부분 `localRoot`와 `remoteRoot`가 어긋난 것이다. 타입스크립트라면 소스 맵이 켜져 있는지(`tsconfig`의 `sourceMap`)도 본다.

다른 언어도 원리는 같다. 디버그 서버를 컨테이너의 모든 주소에서 열고, 호스트에는 루프백으로만 게시하고, 경로를 맞춘다.

```bash
# Python: debugpy가 5678에서 기다리고, 붙을 때까지 앱 시작을 멈춘다
python -m debugpy --listen 0.0.0.0:5678 --wait-for-client -m uvicorn app:app --reload --host 0.0.0.0
```

## Dev Container: 편집기까지 컨테이너로 옮긴다

여기까지는 앱만 컨테이너에서 돌고 편집기, 린터, 언어 서버는 호스트에서 돌았다. 그러면 호스트에도 Node를 깔아야 타입 검사와 자동 완성이 제대로 된다. 결국 "호스트의 Node 버전"이 다시 등장한다.

Dev Container는 편집기의 백엔드까지 컨테이너 안으로 옮긴다. 저장소의 `.devcontainer/devcontainer.json`에 개발 환경을 적어 두면 VS Code(Dev Containers 확장), JetBrains Gateway, GitHub Codespaces가 그 컨테이너를 띄우고 그 안에서 터미널과 확장을 돌린다. 이미 쓰는 Compose 파일을 그대로 재사용할 수 있다.

```json
// .devcontainer/devcontainer.json
{
  "name": "api",
  "dockerComposeFile": ["../compose.yaml", "compose.devcontainer.yaml"],
  "service": "api",
  "workspaceFolder": "/workspace",
  "shutdownAction": "stopCompose",
  "features": {
    "ghcr.io/devcontainers/features/github-cli:1": {}
  },
  "forwardPorts": [3000],
  "postCreateCommand": "npm ci",
  "remoteUser": "node",
  "customizations": {
    "vscode": {
      "extensions": ["dbaeumer.vscode-eslint", "esbenp.prettier-vscode"]
    }
  }
}
```

```yaml
# .devcontainer/compose.devcontainer.yaml: Dev Container로 열 때만 덧붙는 설정
services:
  api:
    volumes:
      - ..:/workspace:cached
    command: sleep infinity      # 앱은 편집기 터미널에서 직접 띄운다
```

`command: sleep infinity`가 눈에 띈다. Dev Container에서는 컨테이너가 "작업 공간"이라 앱이 죽어도 컨테이너가 살아 있어야 한다. 앱은 편집기 터미널에서 `npm run dev`로 띄우고, 디버거는 같은 컨테이너 안에서 붙으니 포트 게시나 경로 맞추기가 필요 없다. `features`는 GitHub CLI 같은 도구를 설치 스크립트 대신 이름으로 끼워 넣는 기능이다.

Dev Container가 빛나는 곳은 새 사람이 들어오는 순간과 여러 프로젝트를 오가는 사람이다. 저장소를 열면 같은 도구 버전이 깔린 환경이 뜬다. 대신 편집기가 원격 모드로 돌아서 확장이 호스트와 컨테이너 중 어디서 도는지 헷갈리고, 맥에서는 결국 파일 공유 성능 문제를 다시 만난다. 큰 저장소라면 소스를 바인드 마운트 대신 볼륨에 클론하는 방식("Clone Repository in Container Volume")이 빠르다.

## 테스트도 같은 이미지로 돌린다

로컬에서 통과한 테스트가 CI에서 깨지는 흔한 이유는 둘이다. Node나 시스템 라이브러리 버전이 다르거나, 테스트가 기대하는 DB가 다르다. 컨테이너는 둘 다에 답이 있다.

첫째, 테스트를 개발 이미지 안에서 돌린다. 로컬과 CI가 같은 명령을 쓴다.

```bash
# 개발 이미지로 일회성 컨테이너를 띄워 테스트하고 지운다
docker compose run --rm api npm test
```

둘째, 테스트가 필요로 하는 DB나 브로커를 컨테이너로 띄운다. 방법은 Compose에 테스트용 서비스를 두는 쪽과, 테스트 코드가 직접 컨테이너를 띄우는 Testcontainers 쪽으로 갈린다. Testcontainers는 테스트가 시작될 때 `postgres:16-alpine` 같은 이미지를 띄우고, 준비될 때까지 기다리고, 무작위 호스트 포트를 받아 접속 주소를 넘겨준 뒤, 끝나면 지운다. 테스트 프로세스가 비정상 종료해도 Ryuk라는 작은 컨테이너가 남은 컨테이너를 정리한다. 트랜잭션 롤백, 템플릿 DB, CI 서비스 컨테이너와의 비교는 [실제 DB로 도는 통합 테스트](/posts/integration-tests-real-db)에서 자세히 다뤘다.

여기서 컨테이너 개발 특유의 문제가 하나 생긴다. 테스트 자체를 컨테이너 안에서 돌리면서 Testcontainers도 쓰면, 컨테이너 안에서 다시 컨테이너를 띄워야 한다. 흔한 방법은 호스트의 `/var/run/docker.sock`을 테스트 컨테이너에 마운트하는 것인데, 이건 그 컨테이너에 호스트 root 권한을 넘겨주는 일이다. 내 노트북에서는 감수할 만해도, 여러 팀이 쓰는 CI 러너에서는 다르다. 왜 위험한지와 대안(rootless, 별도 VM 러너)은 [Docker 호스트를 지키는 실행 옵션](/posts/docker-runtime-security)에 있다. CI에서는 보통 테스트를 러너 위에서 직접 돌리고 Testcontainers만 러너의 Docker를 쓰게 둔다.

또 하나, 컨테이너 안에서 Testcontainers가 띄운 DB에 붙으려면 주소가 `localhost`가 아니다. 띄워진 DB 컨테이너는 테스트 컨테이너의 형제라서 게이트웨이 주소나 `host.docker.internal`로 찾아가야 한다. 라이브러리가 `getHost()`로 알맞은 주소를 주니, 접속 문자열에 `localhost`를 박아 두지 않는다.

## 현장에서 개발 루프가 꼬이는 순간

"저장했는데 안 바뀐다"는 두 단계 중 어디서 끊겼는지부터 가른다. 파일이 컨테이너에 왔는지는 `docker compose exec api cat src/routes.js`로 바로 보인다. 파일은 새것인데 응답이 옛것이면 다시 읽기 단계 문제다. 감시 도구가 이벤트를 못 받는 것이니 폴링을 켜 보거나, 프로세스가 감시 모드로 떠 있는지 `docker compose exec api ps aux`로 본다. 파일이 옛것이면 전달 단계다. 바인드 마운트라면 경로 오타, watch라면 ignore와 `.dockerignore` 패턴을 의심한다.

`Cannot find module`이 이미지를 다시 구운 뒤에도 계속되면 익명 볼륨의 옛 `node_modules`다. `docker compose up -V`로 새로 만든다. `invalid ELF header`나 `Exec format error`면 호스트에서 빌드한 네이티브 바이너리가 컨테이너에 섞여 들어온 것이다. `node_modules`가 바인드 마운트에 가려졌는지 `docker compose config`의 volumes를 본다.

디버거가 `ECONNREFUSED`나 `connection reset`으로 붙지 않으면 인스펙터가 컨테이너의 127.0.0.1에서만 기다리는 경우가 가장 많다. `docker compose exec api ss -ltnp | grep 9229`로 어느 주소에서 듣는지 확인한다. 붙긴 하는데 중단점이 안 걸리면 경로 매핑이다.

맥에서 개발 서버가 뜨는 데 1분씩 걸리면 바인드 마운트로 읽는 파일 수를 의심한다. `node_modules`, `.next`, `dist`처럼 많고 자주 바뀌는 디렉터리를 볼륨으로 빼거나 watch로 바꾼다.

## 이미지는 운영처럼, 루프는 로컬처럼

컨테이너로 개발할 때 지킬 것은 하나로 모인다. 이미지는 운영과 같은 베이스에서 나오게 하고, 그 위에 개발용 구멍만 몇 개 뚫는다. 소스는 바인드 마운트나 watch로 넣고, 의존성은 이미지의 것을 쓰고, 디버거는 루프백으로만 내보내고, 테스트는 같은 이미지로 돌린다. 이 구멍들은 개발용 Compose 파일과 `target: dev`에만 있고 운영 이미지에는 하나도 남지 않는다.

## 면접에서 나올 만한 질문

### 컨테이너로 개발할 때 코드 변경을 바로 반영하려면 어떻게 하나요?

이미지를 다시 굽지 않고 소스를 컨테이너에 넣는 길을 만든다. 바인드 마운트로 프로젝트 폴더를 비추거나 Compose watch로 바뀐 파일만 복사하고, 컨테이너 안에서는 `node --watch`나 HMR 같은 감시 도구가 새 코드를 다시 읽게 한다. 파일 전달과 다시 읽기는 별개 단계라서 반영이 안 되면 둘 중 어디서 끊겼는지부터 본다.

### 바인드 마운트를 쓸 때 node_modules를 익명 볼륨으로 따로 빼는 이유는 무엇인가요?

바인드 마운트가 `/app` 아래를 통째로 가려서 이미지 안의 `node_modules` 대신 호스트의 것이 보이기 때문이다. 맥이나 윈도에서 빌드한 네이티브 모듈은 리눅스 컨테이너에서 `invalid ELF header`로 죽는다. 그 경로만 익명 볼륨으로 빼면 이미지의 리눅스용 의존성을 쓰고, 맥의 느린 파일 공유로 수만 개 파일을 읽는 일도 사라진다. 대신 익명 볼륨이 남아 옛 의존성이 보일 수 있어서 의존성을 바꾸면 `up -V`로 새로 만든다.

### compose watch의 sync와 rebuild는 언제 쓰나요?

sync는 소스 파일처럼 컨테이너 안 감시 도구가 다시 읽을 수 있는 파일에 쓰고, rebuild는 lock 파일이나 Dockerfile처럼 이미지 내용 자체를 바꾸는 파일에 쓴다. 시작할 때 한 번만 읽는 설정 파일은 sync+restart가 맞다. watch는 build로 만드는 서비스만 감시하고, 컨테이너에서 만든 파일은 호스트로 돌아오지 않는다는 점이 바인드 마운트와 다르다.

### 컨테이너 안 Node에 디버거가 붙지 않습니다. 무엇부터 보나요?

인스펙터가 어느 주소에서 기다리는지부터 본다. `--inspect`의 기본은 127.0.0.1이라 컨테이너 밖에서 닿지 않으니 컨테이너 안에서는 0.0.0.0으로 열고, 호스트 게시는 `127.0.0.1:9229:9229`로 좁힌다. 붙었는데 중단점이 안 걸리면 `localRoot`와 `remoteRoot` 경로 매핑이 어긋났거나 소스 맵이 꺼진 경우다. `--watch`로 재시작하면 인스펙터 주소가 바뀌니 디버거의 재연결 옵션도 켠다.

### 디버그 포트를 0.0.0.0으로 게시하면 왜 위험한가요?

디버거 프로토콜에는 인증이 없고, 붙은 쪽은 그 프로세스에서 임의의 코드를 실행할 수 있다. 호스트의 모든 주소로 게시하면 같은 네트워크의 누구나 환경 변수의 비밀을 읽고 명령을 실행할 수 있다. 그래서 컨테이너 안은 0.0.0.0, 호스트 게시는 루프백으로 나누고, 디버그 옵션은 개발용 설정에만 둔다.

### 개발용과 운영용 Dockerfile을 나누나요, 하나로 합치나요?

기본은 하나의 Dockerfile에 멀티 스테이지로 `dev`와 `prod` 스테이지를 두고 target으로 고르는 쪽이다. 같은 base 스테이지를 공유하니 Node 버전과 lock 파일이 두 이미지에서 어긋나지 않는다. 개발 환경에 도구가 너무 많이 붙어 운영 Dockerfile을 읽기 어려워지면 그 부분은 Dev Container 설정으로 떼어 낸다.

### Testcontainers를 컨테이너 안에서 돌릴 때 주의할 점은 무엇인가요?

컨테이너 안에서 다시 컨테이너를 띄우려면 Docker 소켓이 필요하고, 소켓을 마운트하는 것은 호스트 root를 넘기는 것과 같다. 공유 CI 러너에서는 테스트를 러너에서 직접 돌리고 Testcontainers만 러너의 Docker를 쓰게 하는 편이 안전하다. 그리고 띄운 DB는 형제 컨테이너라 `localhost`가 아니니 라이브러리가 주는 호스트와 포트를 쓴다.
