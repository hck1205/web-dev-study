새벽 3시에 세션 저장소로 쓰는 Redis 서버의 디스크 컨트롤러가 죽었다. RDB와 AOF를 다 켜 두었으니 데이터는 디스크에 남아 있다. 문제는 그 디스크가 달린 서버가 꺼져 있다는 것이다. 서버를 고쳐 다시 올리기까지 40분 동안 모든 회원이 로그인을 못 했다. 데이터를 지키는 것과 서비스를 멈추지 않는 것은 다른 문제다.

그래서 같은 데이터를 다른 서버에 실시간으로 복사해 두는 복제를 쓰고, 프라이머리가 죽었을 때 사람 대신 레플리카를 승격하는 Sentinel을 둔다. 둘 다 Redis에 기본으로 들어 있지만, 복제가 비동기라는 한 가지 성질 때문에 생각보다 많은 것이 갈린다. 레플리카에서 읽으면 옛 값이 보이고, 장애 조치 때 마지막 쓰기를 잃을 수 있고, 네트워크가 갈라지면 두 프라이머리가 동시에 쓰기를 받는다.

디스크에 남기는 RDB와 AOF는 [Redis 영속성 글](/posts/redis-persistence-ha)에서 봤다. 이 글은 복제가 처음 붙을 때와 다시 붙을 때 무엇을 주고받는지, 레플리카에서 읽을 때와 장애 조치 때 무엇을 잃는지, Sentinel이 장애를 판단하고 넘기는 순서를 따라가고, 끝에서 레플리카가 전체 동기화를 반복하는 상황을 직접 재현한다. 기준은 Ubuntu 24.04 LTS의 `redis-server` 패키지(7.0.15)이고, 예제는 [Redis 기본 글](/posts/redis-basics)의 쇼핑몰이다. 데이터를 여러 서버에 나누는 Cluster는 [Redis Cluster 글](/posts/redis-cluster)에서 이어 간다.

## 복제는 비동기다

디스크에 남겨도 서버가 죽어 있는 동안은 서비스가 멈춘다. 그래서 같은 데이터를 다른 서버에 실시간으로 복사해 둔다. 프라이머리(마스터) 하나가 쓰기를 받고, 레플리카가 그 변경을 받아 똑같이 적용한다.

```bash
# 레플리카 서버에서: 이 서버를 10.0.0.11의 레플리카로 만든다
redis-cli REPLICAOF 10.0.0.11 6379

# 재시작 후에도 유지하려면 redis.conf에
#   replicaof 10.0.0.11 6379
# 프라이머리에 비밀번호가 있으면
#   masterauth <비밀번호>

# 복제 상태
redis-cli INFO replication
```

처음 연결하면 레플리카는 아무것도 없으니 전체를 받아야 한다(full sync). 그 뒤로는 바뀐 것만 받고, 잠깐 끊겼다 다시 붙으면 놓친 부분만 받는다(partial resync). 아래 그림이 그 순서다.

전체 동기화는 비싸다. 프라이머리가 fork하고, 데이터 전체가 네트워크를 지나고, 레플리카는 받는 동안 옛 데이터로 응답하거나 잠깐 멈춘다. 그래서 backlog를 넉넉히 잡아 짧은 끊김은 부분 동기화로 넘긴다. 어림셈은 "초당 복제되는 바이트 × 견딜 끊김 시간"이다. 쓰기가 초당 2MB이고 1분 끊김을 견디고 싶으면 120MB, `repl-backlog-size 128mb` 정도다. 기본 1MB는 쓰기가 많은 서버에서 몇 초도 못 버틴다. 4.0부터는 레플리카를 재시작해도 RDB에 복제 id와 위치를 남겨 두어 부분 동기화를 시도할 수 있다.

```text
# Replication
role:master
connected_slaves:1
slave0:ip=127.0.0.1,port=6402,state=online,offset=14,lag=0
master_replid:67d5262c5701cf9688e81077c1958cea322b6d6b
master_replid2:0000000000000000000000000000000000000000
master_repl_offset:14
repl_backlog_active:1
repl_backlog_size:1048576
repl_backlog_first_byte_offset:1
repl_backlog_histlen:14
```

프라이머리 쪽 `INFO replication`이다. `slave0`의 `offset`이 `master_repl_offset`과 같으면 다 따라온 것이고, 차이가 레플리카가 밀린 양이다. `lag`는 마지막 응답 후 지난 초다. `master_replid2`는 장애 조치 때 쓰인다. 레플리카가 승격되면 옛 복제 id를 여기에 남겨서, 다른 레플리카가 옛 id로 부분 동기화를 요청해도 받아 줄 수 있다.

## 레플리카에서 읽으면 생기는 일

복제는 비동기다. 프라이머리는 쓰기를 자기 메모리에 반영하자마자 클라이언트에 `OK`를 돌려주고, 레플리카로는 그다음에 보낸다. 여기서 두 가지 문제가 생긴다.

하나는 옛 값을 읽는 것이다. 읽기를 레플리카로 나누면 프라이머리 부하는 줄지만, 방금 담은 장바구니가 레플리카에는 아직 없을 수 있다. 보통 밀리초 단위지만 전체 동기화 중이거나 네트워크가 느리면 길어진다. 레플리카는 기본으로 읽기 전용이라(`replica-read-only yes`) 실수로 쓰면 거절한다.

```text
(error) READONLY You can't write against a read only replica.
```

다른 하나는 장애 조치 때 잃는 것이다. 프라이머리가 `OK`를 준 쓰기가 레플리카로 가기 전에 죽으면, 승격된 레플리카에는 그 쓰기가 없다. 이걸 줄이는 장치가 `WAIT`다.

```bash
# 장바구니를 쓰고, 레플리카 1대가 받았다고 확인할 때까지 최대 100ms 기다린다
redis-cli SET cart:43 '[1002]'
redis-cli WAIT 1 100
```

```text
OK
(integer) 1
```

`WAIT`는 확인해 준 레플리카 수를 돌려준다. 0이 오면 아직 아무 데도 안 갔다는 뜻이니 앱이 다시 시도하거나 에러로 처리한다. 다만 `WAIT`가 Redis를 강한 일관성 저장소로 바꾸지는 않는다. 레플리카가 받았어도 디스크에 남기기 전에 같이 죽을 수 있고, 장애 조치가 그 레플리카를 고른다는 보장도 없다. 손실 확률을 줄이는 장치로 보면 된다.

프라이머리 쪽에서 막는 설정도 있다. 레플리카가 몇 대 이상 붙어 있지 않으면 쓰기를 거절하게 한다.

```text
min-replicas-to-write 1
min-replicas-max-lag 10
```

10초 안에 응답한 레플리카가 1대 미만이면 쓰기는 `NOREPLICAS Not enough good replicas to write.` 에러를 받는다. 네트워크에서 고립된 프라이머리가 혼자 쓰기를 계속 받는 시간을 10초 안팎으로 묶는다.

<Callout kind="warning" title="영속성을 끈 프라이머리를 자동 재시작하지 않는다">
프라이머리는 `save ""`, `appendonly no`이고 레플리카에만 영속성을 켠 구성이 있다. 이때 프라이머리가 죽고 systemd가 바로 다시 띄우면, 빈 상태로 뜬 프라이머리에 레플리카가 다시 붙어 전체 동기화로 빈 데이터를 받아 간다. 레플리카의 데이터까지 지워진다. 프라이머리의 영속성을 끄려면 자동 재시작을 끄거나, Sentinel처럼 프라이머리가 죽으면 레플리카를 승격하는 장치를 함께 둔다.
</Callout>

## Sentinel이 장애를 판단하고 넘기는 과정

복제만으로는 프라이머리가 죽었을 때 사람이 레플리카에 `REPLICAOF NO ONE`을 치고, 앱의 접속 주소를 바꿔야 한다. 새벽 3시에 이걸 사람이 하면 수십 분이 걸린다. Sentinel은 이걸 자동으로 한다. 별도 프로세스(기본 포트 26379)로 떠서 프라이머리와 레플리카를 감시하고, 프라이머리가 죽었다고 판단하면 레플리카 하나를 승격하고 나머지를 새 프라이머리에 붙인다.

```bash
# Ubuntu에서는 별도 패키지다
sudo apt install -y redis-sentinel

# 설정 파일
sudo nano /etc/redis/sentinel.conf
```

```text
# 이름 shop, 주소, 쿼럼 2
sentinel monitor shop 10.0.0.11 6379 2
# 5초 동안 응답이 없으면 주관적으로 다운
sentinel down-after-milliseconds shop 5000
sentinel failover-timeout shop 60000
```

`down-after-milliseconds`의 기본값은 30초인데, 예제에서는 5초로 줄였다. 쿼럼(quorum) 2는 "Sentinel 2대가 다운이라고 동의해야 진짜 다운으로 본다"는 뜻이다. Sentinel은 서로 다른 장애 영역에 최소 3대를 둔다. 한 대는 판단이 틀릴 수 있고, 두 대는 하나가 죽으면 과반을 못 만든다.

노트북에서 프라이머리 하나, 레플리카 둘, Sentinel 셋을 띄우고 프라이머리를 죽여 봤다. 아래 그림이 그때 Sentinel 로그에 남은 순서다.

```bash
# 쿼럼과 과반을 채울 수 있는지
redis-cli -p 26379 SENTINEL ckquorum shop
```

```text
OK 3 usable Sentinels. Quorum and failover authorization can be reached
```

Sentinel의 약점은 네트워크가 갈라질 때다. 프라이머리와 일부 클라이언트가 나머지와 떨어지면, 반대편에서 새 프라이머리가 뽑히는 동안 옛 프라이머리도 그쪽 클라이언트의 쓰기를 받는다. 네트워크가 돌아오면 옛 프라이머리는 레플리카로 강등되면서 그 사이 받은 쓰기를 버린다. 앞의 `min-replicas-to-write`가 이 시간을 줄여 준다.

## 현장에서 레플리카가 전체 동기화를 반복하는 순간

복제가 붙어 있는데도 레플리카 서버의 CPU와 네트워크가 주기적으로 튀고, 프라이머리 로그에 fork가 계속 찍힌다면 전체 동기화가 반복되고 있을 가능성이 크다. 잠깐 끊긴 레플리카가 부분 동기화로 돌아오지 못하고 매번 RDB 전체를 다시 받는 것이다. 노트북에서 프라이머리(6501)와 레플리카(6502)를 띄우고, 일부러 backlog를 16KB로 작게 잡아 재현했다.

```bash
# backlog를 16KB로 작게 잡은 프라이머리와 그 레플리카
redis-server --port 6501 --save "" --appendonly no --repl-backlog-size 16kb --daemonize yes --logfile p.log
redis-server --port 6502 --save "" --appendonly no --replicaof 127.0.0.1 6501 --daemonize yes --logfile r.log

# 동기화 횟수: 전체(sync_full), 부분 성공(sync_partial_ok), 부분 실패(sync_partial_err)
redis-cli -p 6501 INFO stats | grep -E "^sync_"
```

```text
sync_full:1
sync_partial_ok:0
sync_partial_err:0
```

처음 연결이라 전체 동기화가 한 번 있었다. 이제 레플리카 프로세스를 `kill -STOP`으로 잠시 멈추고, 프라이머리에서 레플리카 연결을 끊은 뒤 쓰기를 넣고, 레플리카를 다시 깨웠다. 한 번은 쓰기 세 건만, 한 번은 1KB짜리 값 200개(약 200KB, backlog의 열 배가 넘는다)를 넣었다.

```bash
# 레플리카 PID (INFO server의 process_id)
RP=$(redis-cli -p 6502 INFO server | grep process_id | cut -d: -f2 | tr -d '\r')

# 짧은 끊김: 레플리카를 멈추고, 연결을 끊고, 쓰기 세 건 뒤 다시 깨운다
kill -STOP $RP
redis-cli -p 6501 CLIENT KILL TYPE replica
for i in 1 2 3; do redis-cli -p 6501 SET cart:4$i x > /dev/null; done
kill -CONT $RP; sleep 2
redis-cli -p 6501 INFO stats | grep -E "^sync_"

# 긴 끊김: 끊긴 동안 200KB를 쓴 뒤 다시 깨운다
kill -STOP $RP
redis-cli -p 6501 CLIENT KILL TYPE replica
redis-cli -p 6501 EVAL "for i=1,200 do redis.call('SET','product:'..i, string.rep('x',1000)) end return 1" 0
kill -CONT $RP; sleep 8
redis-cli -p 6501 INFO stats | grep -E "^sync_"
```

```text
sync_full:1
sync_partial_ok:1
sync_partial_err:0

sync_full:2
sync_partial_ok:1
sync_partial_err:1
```

(출력에서 `CLIENT KILL`과 `EVAL`이 돌려준 `(integer) 1`은 뺐다.) 짧은 끊김은 `sync_partial_ok`가 1 늘어 놓친 만큼만 받았다. 긴 끊김은 `sync_partial_err`가 1 늘고 `sync_full`이 2가 됐다. 프라이머리 로그에 이유가 그대로 남는다.

```text
* Partial resynchronization request from 127.0.0.1:6502 accepted. Sending 122 bytes of backlog starting from offset 1.
* Unable to partial resync with replica 127.0.0.1:6502 for lack of backlog (Replica request was: 137).
```

레플리카가 137번 위치부터 달라고 했지만, 16KB짜리 backlog에는 그사이 쓰인 200KB 중 마지막 부분만 남아 있어서 줄 수 없었다. 레플리카 로그에는 `Full resync from master`와 키를 처음부터 다시 읽는 줄이 찍힌다. 아래 그림에서 다음을 누르면 세 번의 연결이 카운터를 어떻게 바꿨는지 따라갈 수 있다.

## 얼마나 멈춰도 되는지부터 정한다

복제는 같은 데이터를 다른 서버에 두어 프라이머리가 죽어도 데이터를 들고 있는 서버가 남게 한다. 다만 비동기라서 레플리카는 늘 조금 뒤에 있고, 장애 조치 때 프라이머리가 응답만 하고 보내지 못한 쓰기를 잃는다. `WAIT`와 `min-replicas-to-write`는 그 확률과 시간을 줄일 뿐이다. Sentinel은 프라이머리가 죽었다는 판단(쿼럼)과 장애 조치 리더 선출(과반)을 나눠서 자동으로 레플리카를 승격하고, 앱은 Sentinel에게 프라이머리 주소를 물어야 그 결과를 따라간다. 처음의 40분은 Sentinel과 레플리카가 있었다면 수 초로 줄었을 것이다.

## 면접에서 나올 만한 질문

### Redis 복제에서 데이터가 유실될 수 있는 경우는?

복제가 비동기라서다. 프라이머리는 쓰기를 반영하자마자 OK를 주고 그 뒤에 레플리카로 보내므로, 그 사이에 프라이머리가 죽고 레플리카가 승격되면 그 쓰기는 사라진다. 네트워크가 갈라졌을 때 고립된 옛 프라이머리가 받은 쓰기도 강등될 때 버려진다. WAIT과 min-replicas-to-write로 확률과 시간을 줄일 수 있지만 강한 일관성이 되지는 않는다.

### 전체 동기화와 부분 동기화는 언제 일어나나요?

레플리카가 처음 붙거나 복제 id가 맞지 않거나, 놓친 위치가 backlog에서 이미 밀려났으면 전체 동기화를 한다. 프라이머리가 fork해서 RDB를 보내므로 비싸다. 짧게 끊겼다 다시 붙어서 놓친 부분이 backlog에 남아 있으면 그만큼만 보내는 부분 동기화가 된다. 기본 backlog 1MB는 작으니 초당 복제량 × 견딜 시간으로 키운다.

### Sentinel에서 quorum은 무엇을 정하나요?

프라이머리가 진짜 다운인지(ODOWN) 판단하는 데 필요한 Sentinel 수다. 실제로 장애 조치를 시작하려면 그와 별도로 Sentinel 과반의 표를 받아 리더가 되어야 한다. 그래서 Sentinel은 서로 다른 장애 영역에 3대 이상 두고, 앱은 Redis 주소 대신 Sentinel에게 현재 프라이머리를 물어 연결해야 한다.

### 레플리카에서 읽기를 나누면 무엇을 조심해야 하나요?

복제가 비동기라서 방금 쓴 값이 레플리카에는 아직 없을 수 있다. 보통 밀리초 단위지만 전체 동기화 중이거나 네트워크가 느리면 길어진다. 장바구니를 담고 바로 목록을 다시 읽는 것처럼 "내가 쓴 것을 바로 읽어야 하는" 흐름은 프라이머리에서 읽는다. 레플리카는 기본으로 읽기 전용이라 쓰기를 보내면 `READONLY` 에러가 난다.

### WAIT 명령을 쓰면 유실이 없어지나요?

아니다. `WAIT 1 100`은 레플리카 1대가 그 쓰기를 받았다고 확인할 때까지 최대 100ms 기다리고 확인한 수를 돌려줄 뿐이다. 레플리카가 받았어도 디스크에 남기기 전에 같이 죽을 수 있고, 장애 조치가 그 레플리카를 고른다는 보장도 없다. 손실 확률을 줄이는 장치이고, 0이 돌아오면 앱이 다시 시도하거나 에러로 처리한다.

### 영속성을 끈 프라이머리를 자동 재시작하면 왜 위험한가요?

빈 상태로 뜬 프라이머리에 레플리카가 다시 붙어 전체 동기화로 빈 데이터를 받아 가기 때문이다. 레플리카에만 영속성을 켜 두었어도 그 데이터까지 지워진다. 프라이머리의 영속성을 끄려면 자동 재시작을 끄거나, Sentinel처럼 프라이머리가 죽으면 레플리카를 승격하는 장치를 함께 둔다.
