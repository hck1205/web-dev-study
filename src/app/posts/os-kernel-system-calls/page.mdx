<EasyIntro>
  컴퓨터 안의 프로그램들은 화면, 디스크, 네트워크 같은 장치를 직접 만지지 못한다. 대신 운영체제의 한가운데 있는 커널에게 부탁하고 결과를 돌려받는데, 이 부탁을 시스템 콜이라고 부른다. 은행 창구를 떠올리면 쉽다. 손님은 금고에 직접 들어갈 수 없고 창구 직원에게 "십만 원 찾아 주세요"라고 적은 종이를 내면, 직원이 신분을 확인하고 금고에 다녀와서 돈을 건넨다. 손님이 아무리 많아도 금고는 안전하고, 누가 얼마를 찾았는지 기록도 남는다.

  창구에 줄을 서고 종이를 내는 데는 시간이 들어서, 프로그램은 작은 부탁을 여러 번 하기보다 한 바구니에 모았다가 한꺼번에 내려고 한다. 커널은 창구 뒤에서 프로그램 차례 정하기, 메모리 나눠 주기, 파일 보관, 장치 다루기를 모두 맡는다. 프로그램이 이상하게 멈추면 창구에 무슨 종이를 냈는지 들여다보는 것만으로 원인을 찾는 경우가 많다.
</EasyIntro>

C로 `printf("hello\n")` 한 줄짜리 프로그램을 만들어 `strace`로 돌려 봤다. 출력은 서른 줄이 넘었다. 대부분은 라이브러리를 불러오는 줄이고, 진짜 "hello"를 찍는 건 끝에서 두 번째 줄 하나였다.

```text
fstat(1, {st_mode=S_IFIFO|0600, st_size=0, ...}) = 0
getrandom("\x91\xb4\x1e\xca\xb4\x80\x55\xb4", 8, GRND_NONBLOCK) = 8
brk(NULL)                               = 0x556bdb367000
brk(0x556bdb388000)                     = 0x556bdb388000
write(1, "hello\n", 6)                  = 6
exit_group(0)                           = ?
+++ exited with 0 +++
```

내 코드에는 `write`도 `brk`도 없다. 그런데 프로그램은 화면에 글자를 쓰려고 `write`를, 메모리를 늘리려고 `brk`를 커널에 부탁했다. 프로그램은 혼자서는 화면도 메모리도 만지지 못한다. 이 글은 그 부탁이 무엇이고, 왜 그런 벽이 있고, 벽을 넘는 데 얼마가 들고, 그 비용을 줄이려고 어떤 꾀를 쓰는지 따라간다.

실험 환경은 Ubuntu 24.04 사용자 공간, gcc 13.3, x86_64 4코어 VM이다(이 VM의 커널은 6.18이고, Ubuntu 24.04 기본 커널은 6.8이다). 시간 숫자는 VM에서 잰 값이라 절댓값보다 서로의 비율을 보면 된다. 커널이 맡는 살림 하나하나는 따로 글이 있다. 프로세스와 스레드는 [프로세스와 스레드 글](/posts/process-vs-thread), 메모리는 [가상 메모리와 페이징 글](/posts/virtual-memory-paging), CPU 차례는 [CPU 스케줄링과 인터럽트 글](/posts/cpu-scheduling-interrupts), 디스크는 [페이지 캐시와 디스크 I/O 글](/posts/page-cache-disk-io)에서 다룬다. 여기서는 그 넷을 잇는 지도를 그린다.

## 프로그램과 커널 사이에 벽이 있다

CPU에는 권한 단계가 있다. x86에서는 이걸 링(ring)이라고 부르고 0부터 3까지 있지만, 리눅스는 둘만 쓴다. 커널은 링 0, 일반 프로그램은 링 3에서 돈다. 보통 커널 모드와 사용자 모드라고 부른다.

사용자 모드에서는 할 수 없는 일이 있다. 장치 레지스터에 직접 쓰기, 인터럽트 끄기, 페이지 테이블 바꾸기, 다른 프로세스의 메모리 보기 같은 명령은 CPU가 거부한다. 시도하면 CPU가 예외를 일으키고, 커널이 그 프로그램에 시그널을 보내 끝낸다. 메모리도 나뉘어 있다. 64비트 리눅스에서 주소 공간의 위쪽 절반은 커널 몫이고, 사용자 모드에서 거기를 읽으려 하면 같은 식으로 막힌다.

이 벽이 있는 이유는 세 가지로 정리된다.

먼저 보호다. 프로그램 하나가 버그로 엉뚱한 주소에 쓰더라도 커널이나 다른 프로그램을 망가뜨리지 못한다. 브라우저 탭이 죽어도 운영체제가 멀쩡한 이유다.

다음은 추상화다. 프로그램은 "이 파일의 앞 100바이트를 달라"고만 말하면 된다. 그 파일이 NVMe SSD에 있는지 네트워크 드라이브에 있는지, 디스크 블록 몇 번에 흩어져 있는지는 커널이 알아서 한다.

마지막은 나눠 쓰기다. CPU 코어 네 개, 메모리 몇 GB, 네트워크 카드 하나를 프로세스 수백 개가 함께 쓴다. 누가 언제 얼마를 쓸지 정하는 심판이 있어야 하고, 그 심판이 커널이다.

EasyIntro의 비유로 말하면 커널은 은행 창구 뒤의 직원이다. 손님(프로그램)은 금고(하드웨어)에 들어가지 못하고, 창구에 정해진 양식(시스템 콜)으로 부탁한다.

## 창구에 부탁하는 방법: 시스템 콜

시스템 콜은 사용자 모드 프로그램이 커널에 일을 맡기는 정해진 입구다. 리눅스 x86_64에는 번호가 붙은 시스템 콜이 350개 남짓 있다. `write`는 1번, `getppid`는 110번, `clock_gettime`은 228번이다.

우리가 `printf`나 `fopen`을 부를 때 직접 시스템 콜을 하는 건 아니다. C 표준 라이브러리(리눅스에서는 보통 glibc)가 중간에 있다. `printf`는 문자열을 만들어 라이브러리 버퍼에 넣고, 버퍼를 비울 때가 되면 glibc의 `write()` 래퍼를 부른다. 래퍼는 레지스터에 번호와 인자를 채우고 `syscall` 명령 하나를 실행한다.

이 과정에서 기억할 것은 두 가지다. 시스템 콜은 함수 호출처럼 생겼지만 CPU 모드가 바뀌는 별개의 사건이다. 그리고 커널은 프로그램이 넘긴 값을 하나도 믿지 않고 다시 검사한다. 커널 버그 중 상당수가 이 검사를 빠뜨린 곳에서 나온다.

`strace`는 이 입구에 걸린 기록을 보여 주는 도구다. 프로그램이 어떤 시스템 콜을 어떤 인자로 불렀고 무엇이 돌아왔는지 한 줄씩 찍는다. 처음 장면의 `write(1, "hello\n", 6) = 6`이 바로 그림의 세 번째부터 여섯 번째 단계를 한 줄로 줄인 것이다.

```bash
# Ubuntu에는 strace가 기본으로 없을 수 있다
sudo apt install -y strace

# 프로그램을 실행하며 시스템 콜을 모두 찍는다
strace ./hello

# 어떤 시스템 콜을 몇 번 불렀는지 표로 센다 (출력은 stderr)
strace -c ./hello > /dev/null
```

```text
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
  0.00    0.000000           0         1           read
  0.00    0.000000           0         1           write
  0.00    0.000000           0         2           close
  0.00    0.000000           0         3           fstat
  0.00    0.000000           0         8           mmap
  0.00    0.000000           0         3           mprotect
...
  0.00    0.000000           0         1           execve
...
------ ----------- ----------- --------- --------- ----------------
100.00    0.000000           0        35         2 total
```

`hello` 하나 찍는 데 시스템 콜 35번이 들었다. `execve`로 프로그램을 띄우고, `openat`과 `mmap`으로 libc를 메모리에 올리고, `mprotect`로 그 영역의 권한을 정리하는 데 대부분이 쓰였다. `errors` 열의 2는 `/etc/ld.so.preload`를 찾다 없어서 난 `ENOENT` 같은, 원래 실패해도 되는 확인들이다.

## 커널로 들어오는 문은 셋이다

커널 모드로 들어가는 길은 시스템 콜만이 아니다. 들어오는 이유에 따라 셋으로 나눈다.

시스템 콜은 프로그램이 원해서 들어가는 문이다. `syscall` 명령을 실행한 바로 그 지점에서, 그 프로그램을 위해 일한다. 예측할 수 있고 동기적이다.

예외는 프로그램이 실행하던 명령 때문에 CPU가 멈춰 세우는 문이다. 0으로 나누기, 허용되지 않은 명령, 그리고 가장 흔한 페이지 폴트가 있다. 페이지 폴트는 아직 물리 메모리에 올라오지 않은 주소를 읽을 때 생기는데, 대부분은 오류가 아니라 커널이 그때 메모리를 채워 주는 정상 흐름이다. 프로그램이 원하지 않았지만 그 명령 때문에 생겼으니 역시 동기적이다. 허용되지 않은 주소였다면 커널은 `SIGSEGV`를 보낸다.

인터럽트는 프로그램과 상관없이 바깥에서 두드리는 문이다. 네트워크 카드가 패킷을 받았을 때, 디스크가 읽기를 끝냈을 때, 타이머가 정해진 시간을 알릴 때 CPU는 하던 일을 잠깐 멈추고 커널의 처리기로 뛴다. 언제 올지 모르니 비동기적이다. 리눅스는 코어마다 받은 인터럽트 수를 `/proc/interrupts`에 보여 준다.

```bash
# 코어별 인터럽트 수 중 타이머, 재스케줄, 함수 호출 인터럽트만 본다
grep -E "^ *(LOC|RES|CAL):" /proc/interrupts
```

```text
LOC:      49433      51284      47510      51945   Local timer interrupts
RES:       8115       9891      10843      10205   Rescheduling interrupts
CAL:    1086725    1078426    1101327    1034698   Function call interrupts
```

`LOC`는 코어마다 도는 타이머다. 이 타이머가 커널을 주기적으로 깨워서, 시스템 콜을 하지 않고 계산만 하는 프로그램도 차례가 되면 CPU를 내놓게 만든다. 타이머 인터럽트와 스케줄러가 어떻게 이어지는지는 [CPU 스케줄링과 인터럽트 글](/posts/cpu-scheduling-interrupts)에서 자세히 본다.

셋을 구분하는 기준은 "누가 원인인가"다. 지금 프로그램이 일부러 불렀으면 시스템 콜, 지금 프로그램의 명령이 문제를 일으켰으면 예외, 바깥 장치가 알렸으면 인터럽트다. 면접에서 이 셋을 묻는다면 동기·비동기 구분과 페이지 폴트 예시까지 말하면 충분하다.

## 모든 것은 파일이라는 말

`write(1, ...)`의 1은 무엇일까. 파일 디스크립터, 줄여서 fd다. 프로세스가 무언가를 열면 커널은 그 프로세스의 fd 표에 칸을 하나 만들고 번호를 돌려준다. 이후로 프로그램은 그 번호로만 부탁한다. 0은 표준 입력, 1은 표준 출력, 2는 표준 에러로 정해져 있고, 새로 연 것은 비어 있는 가장 작은 번호를 받는다.

`cat`이 파일 하나를 읽을 때 무엇을 부탁하는지 보자.

```bash
# 파일을 열고, 읽고, 쓰고, 닫는 시스템 콜만 골라 본다
echo web-01 > host.txt
strace -e trace=openat,read,write,close cat host.txt
```

```text
openat(AT_FDCWD, "host.txt", O_RDONLY)  = 3
read(3, "web-01\n", 131072)             = 7
write(1, "web-01\n", 7)                 = 7
read(3, "", 131072)                     = 0
close(3)                                = 0
```

(libc를 불러오는 앞부분은 뺐다.) `openat`이 3번을 돌려줬고, 이후 `read(3, ...)`로 읽는다. 0바이트가 돌아오면 파일 끝이라는 뜻이라 닫고 끝낸다.

"모든 것은 파일"이라는 말은 디스크 파일만이 아니라 터미널, 파이프, 소켓, 장치까지 같은 fd와 같은 `read`·`write`로 다룬다는 뜻이다. `/dev/urandom`에서 난수를 읽는 것도 그냥 파일 읽기다.

```bash
# 장치 파일 앞의 c는 문자 장치라는 뜻이다. 1, 9는 커널이 드라이버를 찾는 번호다
ls -l /dev/null /dev/urandom /dev/zero

# 난수 8바이트를 읽는다. 커널에는 그냥 openat과 read로 보인다
strace -e trace=openat,read -o trace.txt head -c 8 /dev/urandom | od -An -tx1
grep -A1 urandom trace.txt
```

```text
crw-rw-rw- 1 root root 1, 3 Oct 23 04:06 /dev/null
crw-rw-rw- 1 root root 1, 9 Oct 23 04:06 /dev/urandom
crw-rw-rw- 1 root root 1, 5 Oct 23 04:06 /dev/zero
 fb df 82 ef 09 2b 54 47
openat(AT_FDCWD, "/dev/urandom", O_RDONLY) = 3
read(3, "\373\337\202\357\t+TG", 8)     = 8
```

프로세스가 지금 무엇을 열고 있는지는 `/proc/PID/fd`에 심볼릭 링크로 보인다. 셸에서 `>`로 출력을 돌리면 fd 1이 그 파일을 가리키도록 바뀌는 것도 여기서 보인다.

```bash
# 백그라운드 sleep의 fd 표를 본다. 표준 출력은 pid.txt로, 표준 에러는 err.log로 돌렸다
bash -c 'sleep 30 & echo $!' > pid.txt 2> err.log
ls -l /proc/$(cat pid.txt)/fd
```

```text
lr-x------ 1 root root 64 Oct 24 04:59 0 -> /dev/null
l-wx------ 1 root root 64 Oct 24 04:59 1 -> /tmp/os2/pid.txt
l-wx------ 1 root root 64 Oct 24 04:59 2 -> /tmp/os2/err.log
```

(실험 디렉터리 경로는 줄였다.) 1번과 2번이 셸에서 돌린 파일을 그대로 가리킨다. 0번이 `/dev/null`인 건 대화형이 아닌 셸이 백그라운드 작업의 표준 입력을 막아 두기 때문이다.

이 구조 덕분에 같은 프로그램이 터미널에 쓰든 파일에 쓰든 파이프에 쓰든 코드를 바꾸지 않는다. 커널이 fd 뒤에 있는 객체 종류를 보고 알맞은 드라이버로 보낸다. 반대로 fd는 프로세스마다 개수 제한이 있다(`ulimit -n`, 흔히 기본 1024). 연결을 받기만 하고 닫지 않는 서버는 언젠가 `EMFILE (Too many open files)`를 만난다. 소켓도 fd이기 때문이다.

프로세스 관리는 프로그램을 띄우고(`fork`, `execve`), 끝내고(`exit_group`), 누가 다음에 CPU를 받을지 정한다. 리눅스는 프로세스와 스레드를 같은 `task_struct`로 표현하고, 무엇을 공유할지만 다르게 한다. 이 차이는 [프로세스와 스레드 글](/posts/process-vs-thread)에 있다.

메모리 관리는 프로세스마다 가상 주소 공간을 주고, 실제로 쓰는 순간 물리 메모리를 붙인다. `hello`가 부른 `mmap`과 `brk`가 여기로 간다. 메모리가 모자라면 OOM killer가 누군가를 끝낸다. 자세한 건 [가상 메모리와 페이징 글](/posts/virtual-memory-paging)로 넘긴다.

파일 시스템은 VFS라는 공통 층을 두고 그 아래에 ext4, xfs, tmpfs, procfs 같은 구현을 끼운다. `/proc/interrupts`를 `cat`으로 읽을 수 있는 것도 procfs가 VFS 규약을 따르기 때문이다. 읽은 내용은 메모리의 페이지 캐시에 남아서, 그림의 점선처럼 파일 시스템과 메모리 관리가 맞물린다.

장치와 네트워크는 드라이버가 맡는다. 네트워크 스택(TCP/IP)도 커널 안에 있어서, 소켓에 `send`하면 그 데이터가 커널 안에서 TCP 세그먼트로 잘리고 NIC 드라이버로 간다. 컨테이너가 쓰는 namespace와 cgroup도 이 살림들을 프로세스 묶음별로 칸막이 치는 커널 기능이다([namespace와 cgroup 글](/posts/linux-namespaces-cgroups)).

## 벽을 넘는 데 드는 값

시스템 콜이 비싸다는 말을 많이 듣는다. 얼마나 비싼지 직접 재 봤다. 같은 일을 백만 번씩 반복하고 한 번 평균을 냈다.

```c
// 평범한 함수 호출 (인라인되지 않게 막았다)
for (int i = 0; i < N; i++) s += plain(i);
// clock_gettime: glibc가 vDSO로 처리한다
for (int i = 0; i < N; i++) clock_gettime(CLOCK_MONOTONIC, &ts);
// getppid: 커널에서 할 일이 거의 없는 시스템 콜
for (int i = 0; i < N; i++) s += syscall(SYS_getppid);
// clock_gettime을 vDSO 없이 진짜 시스템 콜로
for (int i = 0; i < N; i++) syscall(SYS_clock_gettime, CLOCK_MONOTONIC, &ts);
```

```text
function call        1.2 ns
clock_gettime vDSO  19.8 ns
getppid syscall     94.1 ns
clock_gettime raw  132.9 ns
```

`getppid`는 커널에서 부모 PID 하나를 꺼내 오는 게 전부인데도 함수 호출의 수십 배가 걸렸다. 이 차이는 거의 다 벽을 넘는 값이다. 모드가 바뀔 때 CPU는 레지스터를 저장하고, 커널 스택으로 갈아타고, 돌아올 때 되돌린다. 2018년 Meltdown·Spectre 이후로는 대응책이 더 붙었다. 커널 페이지 테이블을 사용자 공간과 분리하는 KPTI가 켜진 CPU에서는 들어가고 나올 때마다 페이지 테이블을 바꿔야 하고, 분기 예측기를 비우는 처리도 들어간다. CPU 세대와 커널 설정에 따라 이 값은 수십 ns에서 수백 ns까지 달라진다.

100ns가 작아 보여도 반복되면 크다. 초당 10만 요청을 받는 서버가 요청마다 시스템 콜을 50번 한다면 초당 500만 번, 시스템 콜 진입 비용만으로 코어 하나의 절반쯤을 쓴다. 게다가 시스템 콜 뒤에 있는 실제 일(디스크, 네트워크)은 이보다 훨씬 오래 걸리고, 그동안 프로세스가 잠들면 그때는 컨텍스트 스위치가 일어난다.

### 모드 전환과 컨텍스트 스위치는 다르다

둘을 자주 헷갈린다. 모드 전환은 같은 프로세스가 사용자 모드에서 커널 모드로 들어갔다 나오는 것이다. 주소 공간도 스레드도 그대로다. `getppid`가 그렇다.

컨텍스트 스위치는 CPU가 지금 스레드를 내려놓고 다른 스레드를 올리는 것이다. 레지스터 전체를 저장하고, 다른 프로세스라면 주소 공간도 바꾼다. 그러면 TLB와 CPU 캐시에 있던 내 데이터가 쓸모없어져서 다시 데우는 비용이 따라온다. 직접 비용은 마이크로초 단위이고, 캐시를 다시 채우는 간접 비용이 더 클 때가 많다. 측정 방법과 숫자는 [프로세스와 스레드 글](/posts/process-vs-thread)에 있다.

연결 고리는 이렇다. 시스템 콜은 항상 모드 전환이지만, 컨텍스트 스위치는 그 시스템 콜이 기다려야 할 때만 생긴다. 데이터가 아직 없는 소켓에 `read`를 부르면 커널은 이 스레드를 잠재우고 다른 스레드를 올린다. 이게 블로킹 I/O의 정체다.

## 벽을 덜 넘는 꾀

비용이 벽을 넘는 횟수에 비례하니, 줄이는 방법은 대부분 "덜 넘기"다.

### 모아서 한 번에: 버퍼링

`printf`를 1000번 부르는 프로그램을 파일로 출력하면서 `write`가 몇 번 일어나는지 셌다.

```c
for (int i = 0; i < 1000; i++) printf("line %d\n", i);
```

```bash
# 출력을 파일로 돌리면 glibc는 stdout을 꽉 찬 버퍼(full buffering)로 쓴다
strace -c -e trace=write ./loop > out.txt
# stdbuf -oL로 줄 단위 버퍼링을 강제한다 (터미널에 쓸 때와 같은 방식)
strace -f -c -e trace=write stdbuf -oL ./loop > out.txt
```

```text
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
  0.00    0.000000           0         3           write
------ ----------- ----------- --------- --------- ----------------
100.00    0.000000           0         3           total
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
100.00    0.000040           0      1000           write
------ ----------- ----------- --------- --------- ----------------
100.00    0.000040           0      1000           total
```

같은 1000줄인데 `write`가 3번과 1000번이다. 전체 8890바이트를 4096바이트 버퍼로 모으니 4096, 4096, 698 세 번에 나갔다. 터미널에 찍을 때는 사람이 바로 봐야 하니 줄마다 비우고, 파일이나 파이프로 갈 때는 가득 찰 때 비운다. 이 차이 때문에 생기는 흔한 증상이 있다. `python app.py | tee log.txt`처럼 파이프로 넘기면 로그가 한참 안 보이다가 한꺼번에 나온다. 버퍼가 차기를 기다리는 것이다. 파이썬이면 `python -u`나 `PYTHONUNBUFFERED=1`, C면 `setvbuf`나 `fflush`로 푼다. 컨테이너 로그가 늦게 보일 때도 같은 원인인 경우가 많다.

버퍼 크기와 모드를 넣으면 `write`가 몇 번 일어날지 세는 함수를 만들어 보자. 실제 glibc는 버퍼보다 큰 한 덩어리를 바로 쓰는 등 세부가 더 있지만, 여기서는 단순하게 둔다. `"line"`이면 줄마다 한 번, `"full"`이면 전체 바이트를 버퍼 크기로 나눠 올림한 만큼 쓴다.

### 아예 넘지 않기: vDSO

측정 결과에서 `clock_gettime`은 20ns였다. 진짜 시스템 콜로 부르면 133ns인데 왜 다를까. `strace`로 세어 보면 답이 보인다.

```c
// clock_gettime 1000번, getppid 1000번
for (int i = 0; i < 1000; i++) clock_gettime(CLOCK_MONOTONIC, &ts);
for (int i = 0; i < 1000; i++) syscall(SYS_getppid);
```

```bash
strace -c -e trace=clock_gettime,getppid ./few
```

```text
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
100.00    0.011105          11      1000           getppid
------ ----------- ----------- --------- --------- ----------------
100.00    0.011105          11      1000           total
```

`clock_gettime`은 1000번 불렀는데 표에 아예 없다. 커널에 들어가지 않았기 때문이다. 커널은 모든 프로세스의 주소 공간에 vDSO라는 작은 공유 라이브러리를 붙여 둔다. 시간처럼 자주 읽고 비밀이 아닌 값은 커널이 공유 메모리 페이지에 계속 써 두고, vDSO의 함수가 사용자 모드에서 그 값을 읽어 계산한다. 벽을 넘지 않으니 빠르다.

```bash
# 모든 프로세스의 메모리 지도에 [vdso]가 붙어 있다
grep vdso /proc/self/maps
```

```text
7f84c065b000-7f84c065d000 r-xp 00000000 00:00 0                          [vdso]
```

x86_64 리눅스에서 vDSO로 처리되는 건 `clock_gettime`, `gettimeofday`, `time`, `getcpu` 정도다. 다만 VM에서 시계 소스가 vDSO로 읽을 수 없는 종류면 결국 시스템 콜로 떨어진다. 이 VM은 `/sys/devices/system/clocksource/clocksource0/current_clocksource`가 `tsc`라 vDSO가 동작했다. 로그마다 타임스탬프를 찍는 서버가 클라우드 VM에서 유난히 느리다면 확인해 볼 곳이다.

위 표에서 `getppid` 한 번이 11µs로 찍힌 것도 눈여겨보자. 측정 프로그램으로는 94ns였다. `strace`가 시스템 콜마다 프로세스를 멈추고 들여다보느라 100배 가까이 느려진 것이다. 이 숫자가 뒤에서 다룰 "운영 서버에서 strace를 조심하라"는 말의 근거다.

### 기다리는 방식을 바꾸기: epoll과 io_uring

연결 1만 개를 다루는 서버가 연결마다 `read`를 부르고 기다리면 스레드 1만 개가 잠들어 있어야 한다. `epoll`은 "이 fd들 중 읽을 게 생긴 것만 알려 달라"고 커널에 한 번 등록해 두고, `epoll_wait` 한 번으로 준비된 것들을 받는다. Nginx, Node.js의 libuv, Redis가 이 방식이다([Node.js 서버 런타임 글](/posts/nodejs-server-runtime)).

`io_uring`(커널 5.1부터)은 한 걸음 더 간다. 사용자 공간과 커널이 같이 보는 고리 모양 큐 두 개를 만들고, 프로그램은 제출 큐에 요청을 써 넣기만 한다. 커널은 처리 결과를 완료 큐에 쓴다. 요청 여러 개를 시스템 콜 한 번(`io_uring_enter`)으로 넘기거나, 커널 쪽 폴링 스레드를 켜면 시스템 콜 없이도 주고받을 수 있다. 대신 커널 안의 새 코드가 많아 보안 취약점이 여러 번 나왔고, 그래서 이를 끄는 환경도 있다. Docker의 기본 seccomp 프로필은 최근 버전에서 io_uring 관련 시스템 콜을 막고, 구글도 일부 제품과 서버에서 io_uring을 제한한다고 밝힌 바 있다. 쓰기 전에 배포 환경에서 허용되는지 먼저 본다. 시스템 콜을 걸러 내는 seccomp 자체는 [seccomp와 AppArmor 글](/posts/seccomp-apparmor)에 있다.

## 현장에서 strace를 꺼내는 순간

시스템 콜은 프로그램과 바깥 세상이 만나는 유일한 곳이라, 프로그램이 이상할 때 가장 먼저 들여다볼 창이 된다. 소스 코드가 없어도, 로그가 없어도 커널에 무엇을 부탁했는지는 보인다.

설정을 바꿨는데 반영이 안 될 때는 그 파일을 열기는 하는지부터 본다.

```bash
# 파일 관련 시스템 콜만 본다. 실패한 것만 보려면 -Z를 붙인다
strace -e trace=openat cat /etc/myapp/config.yaml
```

```text
openat(AT_FDCWD, "/etc/myapp/config.yaml", O_RDONLY) = -1 ENOENT (No such file or directory)
cat: /etc/myapp/config.yaml: No such file or directory
+++ exited with 1 +++
```

실제 서비스에서는 이 줄이 `/etc/myapp/config.yml`처럼 내가 생각한 것과 다른 경로를 열려 하거나, 아예 그 파일을 열지 않는 것으로 나타난다. 프로그램이 어디서 설정을 찾는지 문서를 뒤지는 것보다 빠를 때가 많다.

프로세스가 멈춘 것 같을 때는 실행 중인 프로세스에 붙어서 지금 어느 시스템 콜에 서 있는지 본다.

```bash
# 이미 떠 있는 프로세스에 붙는다. Ctrl+C로 떼면 프로세스는 계속 돈다
sudo strace -p 5209
```

```text
strace: Process 5209 attached
read(3,
```

`read(3,`에서 멈춰 있다면 fd 3에서 읽을 것을 기다리는 중이다. `ls -l /proc/5209/fd/3`으로 그 fd가 무엇인지 확인한다. 소켓이면 상대가 응답을 안 주는 것이고, 파이프면 쓰는 쪽이 멈춘 것이다. `futex(`에서 멈춰 있으면 락을 기다리는 것이고, `epoll_wait(`이면 그냥 할 일이 없어 쉬는 정상 상태다.

느린 시스템 콜을 찾을 때는 `-T`로 각 호출에 걸린 시간을, `-f`로 자식 프로세스와 스레드까지 본다.

```bash
# 시스템 콜마다 걸린 시간을 꺾쇠 안에 붙인다
strace -T -e trace=write ./hello
```

```text
write(1, "hello\n", 6)                  = 6 <0.000103>
```

<Callout kind="warning">
  strace는 시스템 콜마다 대상 프로세스를 멈추고 들여다본다. 위 측정에서 시스템 콜 하나가 94ns에서 11µs로 느려졌다. 트래픽을 받는 운영 서버에 오래 붙여 두면 그 자체가 장애가 된다. 붙일 때는 `-e trace=`로 범위를 좁히고 짧게 보고 뗀다. 오래 봐야 하면 커널 안에서 세는 `perf trace`나 bpftrace처럼 오버헤드가 작은 도구를 쓴다. 컨테이너 안에서는 ptrace 권한(`SYS_PTRACE`)이 없어 붙지 않을 수 있다.
</Callout>

bpftrace를 쓸 수 있다면 프로세스를 멈추지 않고 시스템 콜 수를 셀 수 있다. Ubuntu 24.04에서는 `sudo apt install bpftrace`로 설치한다.

```bash
# 10초 동안 프로세스 이름별 시스템 콜 횟수를 센다 (커널 안에서 집계)
sudo bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); } interval:s:10 { exit(); }'
```

시스템 콜 횟수가 비정상적으로 많은 프로세스가 보이면 `strace -c -p PID`로 짧게 붙어 어느 시스템 콜이 많은지 본다. 작은 `read`나 `write`가 수만 번이라면 버퍼링을 의심하고, `futex`가 많다면 락 경합을, `epoll_wait`가 0을 계속 돌려준다면 바쁜 폴링을 의심한다. 전체 서버가 느릴 때 CPU·메모리·디스크·네트워크 중 어디부터 볼지는 [리눅스 성능 첫 진단 글](/posts/linux-performance-triage)에 정리했다.

## 창구 앞에서 일어나는 일

프로그램은 하드웨어를 직접 만지지 못하고 커널에 시스템 콜로 부탁한다. 그 벽은 보호와 추상화와 나눠 쓰기를 위해 있고, 넘을 때마다 모드 전환 비용이 든다. 그래서 버퍼링, vDSO, epoll, io_uring은 모두 "벽을 덜 넘는" 방향으로 발전했다. 파일, 소켓, 장치가 모두 fd 하나로 보이는 덕분에 `strace` 한 줄로 프로그램이 바깥 세상과 무엇을 주고받는지 볼 수 있다. 다음으로는 그 부탁을 받은 커널이 메모리를 어떻게 나눠 주는지 [가상 메모리와 페이징 글](/posts/virtual-memory-paging)에서 이어 본다.

## 면접에서 나올 만한 질문

### 커널 모드와 사용자 모드를 왜 나누나요

하드웨어와 다른 프로세스를 보호하기 위해서다. 사용자 모드에서는 장치 접근, 페이지 테이블 변경, 인터럽트 제어 같은 특권 명령을 CPU가 거부하고, 커널 메모리도 읽을 수 없다. 덕분에 프로그램 하나의 버그가 운영체제나 다른 프로그램을 망가뜨리지 못하고, 커널이 자원을 공정하게 나눠 줄 수 있다.

### 시스템 콜은 어떻게 동작하나요

프로그램이 보통은 glibc 래퍼를 거쳐 레지스터에 시스템 콜 번호와 인자를 넣고 `syscall` 명령을 실행한다. CPU가 커널 모드로 바뀌며 커널의 정해진 입구로 뛰고, 커널은 번호로 처리 함수를 찾아 인자를 검사한 뒤 일을 한다. 결과는 레지스터로 돌려주고 사용자 모드로 돌아온다. 음수 결과는 래퍼가 errno로 바꾸고 -1을 돌려준다.

### 시스템 콜, 예외, 인터럽트는 어떻게 다른가요

셋 다 커널 모드로 들어가는 길이지만 원인이 다르다. 시스템 콜은 프로그램이 일부러 부르는 동기 진입이고, 예외는 실행 중인 명령이 문제를 일으켜 CPU가 세우는 동기 진입이다(페이지 폴트, 0으로 나누기). 인터럽트는 타이머나 NIC 같은 바깥 장치가 보내는 비동기 신호로, 지금 돌던 프로그램과 상관없이 들어온다.

### 시스템 콜은 왜 느린가요? 얼마나 느린가요

모드를 바꿀 때 레지스터 저장, 커널 스택 전환, Meltdown 이후의 KPTI 페이지 테이블 교체 같은 고정 비용이 들기 때문이다. 내가 잰 VM에서는 함수 호출이 1ns 남짓, 거의 일이 없는 `getppid`가 약 94ns였다. CPU와 완화 설정에 따라 수십에서 수백 ns로 달라진다. 개별로는 작지만 요청마다 수십 번씩 반복되면 코어를 눈에 띄게 쓴다.

### 모드 전환과 컨텍스트 스위치의 차이는 무엇인가요

모드 전환은 같은 스레드가 커널에 들어갔다 나오는 것이고 주소 공간이 그대로다. 컨텍스트 스위치는 CPU에서 다른 스레드로 갈아타는 것이라 레지스터 전체를 바꾸고, 다른 프로세스면 주소 공간도 바꿔 TLB와 캐시가 식는다. 시스템 콜은 늘 모드 전환이지만, 기다려야 하는 블로킹 호출일 때만 컨텍스트 스위치로 이어진다.

### vDSO는 무엇이고 왜 빠른가요

커널이 모든 프로세스 주소 공간에 붙여 두는 작은 공유 라이브러리다. 시간처럼 자주 읽는 값을 커널이 공유 페이지에 써 두고, `clock_gettime` 같은 함수가 사용자 모드에서 그 값을 읽어 계산하니 커널에 들어가지 않는다. 실측에서 vDSO 경로는 20ns, 같은 일을 진짜 시스템 콜로 하면 133ns였다. 시계 소스가 vDSO를 지원하지 않는 VM에서는 시스템 콜로 떨어질 수 있다.

### "모든 것은 파일"이라는 말은 무슨 뜻인가요

디스크 파일뿐 아니라 터미널, 파이프, 소켓, 장치까지 모두 파일 디스크립터라는 번호로 열고 `read`·`write`·`close`라는 같은 시스템 콜로 다룬다는 뜻이다. 커널은 fd 뒤의 객체 종류를 보고 알맞은 드라이버나 네트워크 스택으로 보낸다. 그래서 같은 코드가 파일에도 소켓에도 쓸 수 있고, 반대로 소켓도 fd 한도(`ulimit -n`)를 먹어서 닫지 않으면 `EMFILE`이 난다.

### 시스템 콜 비용을 줄이는 방법에는 무엇이 있나요

벽을 덜 넘는 게 기본이다. 사용자 공간 버퍼링으로 작은 쓰기를 모으고, `writev`로 여러 버퍼를 한 번에 쓰고, `sendfile`로 복사 없이 넘긴다. 시간 읽기처럼 vDSO로 아예 들어가지 않는 경로도 있다. 연결이 많으면 `epoll`로 기다림을 한 번에 모으고, io_uring으로 여러 요청을 공유 큐에 넣어 한 번에 넘긴다. io_uring은 보안 문제로 막힌 환경이 있어 배포 환경을 먼저 확인한다.
