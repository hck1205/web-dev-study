이탈 예측 모델이 서비스에서 몇 달째 잘 돌고 있었다. 어느 날 예측이 이상하다는 제보가 들어와서 원인을 찾으려는데, 이 모델을 다시 만들 수가 없다. 데이터 사이언티스트가 노트북에서 학습한 파일(`model.pkl`)을 서버에 복사해 올렸고, 그 노트북은 몇 번 고쳐졌고, 학습에 쓴 CSV는 그 뒤로 매일 덮어써졌다. 코드 저장소에는 서빙 코드만 있다. 지금 서버에서 도는 모델이 정확히 어떤 데이터와 어떤 설정으로 만들어졌는지 아는 사람이 없다.

일반 소프트웨어라면 이런 일은 잘 생기지 않는다. Git 커밋 하나를 찍으면 같은 바이너리가 나온다. ML 시스템은 그렇지 않다. 같은 코드라도 데이터가 바뀌면 모델이 바뀌고, 같은 데이터라도 무작위 시드 하나가 다르면 예측이 바뀐다. 그리고 코드가 하나도 안 바뀌어도 세상이 바뀌면 모델이 낡는다.

MLOps는 이 문제를 운영의 언어로 다루는 일이다. 이 글은 ML 시스템이 일반 소프트웨어와 어디가 다른지, MLOps가 지키려는 원칙, 구성 요소가 어떻게 이어지는지, 조직이 손작업에서 자동화로 넘어가는 단계를 정리한다. 각 구성 요소의 깊은 이야기는 시리즈의 다른 글로 넘긴다. 모델 학습이 안에서 무엇을 반복하는지는 [딥러닝 기초 글](/posts/deep-learning-basics), 학습한 모델을 API로 내보내는 일은 [모델 서빙 글](/posts/model-serving), 예측을 설명하고 기록하는 일은 [SHAP과 LIME 글](/posts/explainable-ai-shap-lime)에 있다.

## 같은 코드로 다른 모델이 나온다

말로만 하면 감이 잘 안 와서 직접 돌려 봤다. 고객의 방문 횟수, 이용 시간, 문의 건수로 이탈 여부를 맞히는 작은 데이터를 만들고, 랜덤 포레스트로 학습한 뒤 고객 한 명(방문 3회, 이용 40분, 문의 1건)의 이탈 확률을 찍는 스크립트다. 환경은 Python 3.13, scikit-learn 1.9다.

```python
# train.py: 데이터 경로와 시드를 받아 학습하고, 무엇으로 학습했는지 함께 찍는다
import sys, json, hashlib, platform, numpy as np, sklearn
from sklearn.ensemble import RandomForestClassifier
from sklearn.model_selection import train_test_split

path = sys.argv[1]
seed = None if sys.argv[2] == "none" else int(sys.argv[2])
d = np.loadtxt(path, delimiter=",", skiprows=1)
X, y = d[:, :3], d[:, 3]
Xtr, Xte, ytr, yte = train_test_split(X, y, test_size=0.2, random_state=0)
m = RandomForestClassifier(n_estimators=50, max_features=1, random_state=seed).fit(Xtr, ytr)

print(json.dumps({
    "data": path,
    "data_sha256": hashlib.sha256(open(path, "rb").read()).hexdigest()[:12],
    "seed": seed, "sklearn": sklearn.__version__, "python": platform.python_version(),
    "test_acc": round(m.score(Xte, yte), 4),
    "probe_churn_prob": round(float(m.predict_proba([[3, 40.0, 1]])[0, 1]), 4),
}))
```

먼저 시드를 정하지 않고 같은 데이터로 두 번 돌렸다.

```bash
python train.py churn_v1.csv none
python train.py churn_v1.csv none
```

```text
{"data": "churn_v1.csv", "data_sha256": "cc7822db7e6f", "seed": null, "sklearn": "1.9.1", "python": "3.13.16", "test_acc": 0.598, "probe_churn_prob": 0.78}
{"data": "churn_v1.csv", "data_sha256": "cc7822db7e6f", "seed": null, "sklearn": "1.9.1", "python": "3.13.16", "test_acc": 0.598, "probe_churn_prob": 0.83}
```

코드도 데이터도 같다. 시험 정확도(test_acc)도 0.598로 같다. 그런데 같은 고객의 이탈 확률이 0.78과 0.83으로 다르다. 랜덤 포레스트는 트리마다 데이터와 특징을 무작위로 뽑는데, 시드가 없으면 실행할 때마다 다르게 뽑는다. 정확도만 보고 "같은 모델"이라고 생각했다면 이 차이를 놓친다. 이탈 확률 0.8 이상인 고객에게만 쿠폰을 보낸다면, 이 고객은 어떤 날은 받고 어떤 날은 못 받는다.

시드를 고정하면 이렇다.

```bash
python train.py churn_v1.csv 42
python train.py churn_v1.csv 42
python train.py churn_v2.csv 42
```

```text
{"data": "churn_v1.csv", "data_sha256": "cc7822db7e6f", "seed": 42, "sklearn": "1.9.1", "python": "3.13.16", "test_acc": 0.594, "probe_churn_prob": 0.66}
{"data": "churn_v1.csv", "data_sha256": "cc7822db7e6f", "seed": 42, "sklearn": "1.9.1", "python": "3.13.16", "test_acc": 0.594, "probe_churn_prob": 0.66}
{"data": "churn_v2.csv", "data_sha256": "c42ec285d7d4", "seed": 42, "sklearn": "1.9.1", "python": "3.13.16", "test_acc": 0.6121, "probe_churn_prob": 0.98}
```

같은 데이터, 같은 시드면 두 번 다 0.66이다. 이제 데이터를 바꿔 본다. churn_v2.csv는 v1에 최근 고객 800명을 덧붙인 파일이다. 최근 고객은 이용 시간이 조금 길어지는 쪽으로 분포가 달라져 있다. 코드와 시드는 그대로인데 같은 고객의 이탈 확률이 0.66에서 0.98로 뛰었다. 파일 이름을 `churn.csv` 하나로 덮어쓰며 관리했다면, 이 두 모델이 다른 데이터로 만들어졌다는 걸 해시 말고는 알 방법이 없다.

이 실험에서 이미 MLOps의 출발점이 보인다. 모델 하나를 다시 만들려면 코드 커밋, 데이터의 정확한 버전(여기서는 해시), 설정과 시드, 라이브러리 버전이 전부 필요하다. 하나라도 빠지면 "비슷한 모델"은 만들 수 있어도 "그 모델"은 못 만든다.

## 코드, 데이터, 모델: 바뀌는 축이 셋이다

일반 소프트웨어의 CI/CD는 바뀌는 것이 코드 하나라고 가정한다. 코드가 바뀌면 빌드하고 테스트하고 배포한다. ML 시스템은 바뀌는 축이 셋이다.

코드는 특징을 만드는 전처리, 학습 스크립트, 서빙 코드다. 여기까지는 Git이 관리한다.

데이터는 학습에 쓴 원천 데이터와 라벨이다. 크기가 수 GB에서 수 TB라 Git에 넣을 수 없고, 매일 새로 쌓이고, 원천 시스템에서 스키마가 조용히 바뀌기도 한다. 데이터 자체가 버전 관리 대상이 된다. DVC처럼 데이터 파일의 해시만 Git에 남기고 실제 파일은 객체 저장소에 두는 도구가 있고, 레이크 테이블 포맷(Delta Lake, Iceberg)의 시간 여행(특정 시점 스냅숏 읽기)으로 "학습 시점의 테이블"을 고정하는 방법도 있다. 테이블 포맷은 [데이터 레이크 글](/posts/data-lake-hdfs)에 있다.

모델은 코드와 데이터를 학습으로 합친 결과물이다. 코드를 빌드하면 나오는 바이너리와 비슷하지만, 같은 입력으로 같은 결과물이 나온다는 보장이 약하고(위의 시드, GPU 연산의 비결정성), 결과물만 봐서는 품질을 알 수 없다. 반드시 평가 숫자와 함께 다뤄야 한다.

세 축이 따로 바뀌니 배포의 계기도 셋이다. 코드가 바뀌어서(새 특징 추가), 데이터가 바뀌어서(새 달 데이터로 재학습), 아무것도 안 바뀌었는데 세상이 바뀌어서(고객 행동이 달라져 성능이 떨어짐)다. 일반 소프트웨어에는 세 번째 계기가 거의 없다. 버그 없는 코드는 1년 뒤에도 같은 답을 낸다. 모델은 코드가 그대로여도 1년 뒤에는 틀린 답을 낼 수 있다.

## 모델 코드는 전체의 작은 상자 하나다

구글 엔지니어들이 2015년에 낸 논문 "Hidden Technical Debt in Machine Learning Systems"에 유명한 그림이 있다. 실제 ML 시스템에서 학습 코드는 한가운데 작은 상자이고, 그 주변을 데이터 수집, 특징 추출, 데이터 검증, 설정, 자원 관리, 서빙 인프라, 모니터링 같은 훨씬 큰 상자들이 둘러싸고 있다. 모델을 만드는 건 일의 일부이고, 나머지가 운영 비용을 결정한다는 이야기다.

이 논문이 꼽은 ML 특유의 기술 부채 몇 가지는 지금도 현장에서 그대로 보인다.

얽힘(entanglement)은 "무엇이든 바꾸면 모든 게 바뀐다"는 원칙으로 요약된다. 특징 하나의 분포가 바뀌면 다른 특징의 가중치까지 다 바뀐다. 일반 코드처럼 한 모듈만 고치고 나머지는 그대로라고 가정할 수 없다.

선언되지 않은 소비자도 있다. 모델의 예측을 다른 팀이 몰래 가져다 자기 시스템의 입력으로 쓰고 있으면, 모델을 고쳤을 때 엉뚱한 곳이 깨진다. API 계약처럼 예측의 소비자도 관리해야 한다.

데이터 의존성은 코드 의존성보다 다루기 어렵다. 다른 팀이 만든 테이블의 컬럼 하나가 단위가 바뀌어도(원 → 천 원) 컴파일러는 아무 말도 안 한다. 그래서 데이터 검증이 테스트의 자리를 대신한다.

파이프라인 정글과 접착 코드도 흔하다. 노트북에서 시작한 전처리가 스크립트로, 스크립트가 크론으로, 크론이 다른 스크립트를 부르는 식으로 자라서 아무도 전체 흐름을 모른다. 이 글을 시작한 장면이 그 결과다.

피드백 루프는 모델이 자기 학습 데이터를 바꾸는 현상이다. 추천 모델이 보여 준 상품만 클릭되고, 그 클릭으로 다시 학습하면 모델은 자기가 보여 준 것만 더 보여 주게 된다.

## MLOps가 지키려는 것

MLOps라는 이름은 DevOps에서 왔다. 개발과 운영을 한 흐름으로 묶고, 손작업을 자동화하고, 작게 자주 배포한다는 생각은 같다. 거기에 ML 특유의 요구가 더해진다.

재현성. 어떤 모델이든 코드 커밋, 데이터 버전, 설정, 환경으로 다시 만들 수 있어야 한다. 위 실험의 JSON 한 줄이 그 최소 형태다. 실무에서는 이 기록을 실험 추적 도구(MLflow, Weights & Biases 같은 것)가 자동으로 남긴다.

자동화. 데이터 준비, 학습, 평가, 등록, 배포를 사람이 노트북을 열어 순서대로 실행하지 않고 파이프라인이 돌린다. 사람이 할 일은 파이프라인을 고치는 것이지 파이프라인의 단계를 손으로 대신하는 게 아니다.

검증. 코드 테스트에 더해 데이터 테스트(스키마, 결측 비율, 값 범위)와 모델 테스트(이전 모델보다 나쁘지 않은지, 특정 고객군에서 무너지지 않는지)를 배포 전에 자동으로 한다.

지속 학습. 새 데이터가 쌓이거나 성능이 떨어지면 다시 학습한다. 일반 소프트웨어의 CI(지속적 통합), CD(지속적 배포)에 CT(continuous training, 지속적 학습)가 하나 더 붙는다고 말하기도 한다.

모니터링. 서버가 살아 있는지뿐 아니라 입력 분포가 학습 때와 같은지, 예측 분포가 갑자기 바뀌지 않았는지, 나중에 들어오는 정답과 비교한 실제 성능이 유지되는지를 본다.

이 원칙들은 도구 이름이 아니다. 엑셀과 셸 스크립트로도 지킬 수 있고, 비싼 플랫폼을 깔고도 못 지킬 수 있다. 판단 기준은 "지금 서버에서 도는 모델을 내일 똑같이 다시 만들 수 있나", "새 모델이 더 나쁘면 사람이 보기 전에 막히나"다.

피처 저장소(feature store)는 모델 입력이 되는 특징을 계산해 저장하고 학습과 서빙에 같은 정의로 내준다. "최근 7일 방문 횟수" 같은 특징을 학습할 때는 과거 시점 기준으로 대량으로 꺼내고(오프라인), 서빙할 때는 고객 한 명 것을 밀리초 안에 꺼낸다(온라인). 두 경로가 같은 정의를 쓰게 만드는 게 존재 이유다. 왜 이게 어려운지는 [모델 서빙 글](/posts/model-serving)에서 학습-서빙 차이로 다룬다.

학습 파이프라인은 데이터 검증, 특징 준비, 학습, 평가, 등록을 단계로 묶은 것이다. 단계 사이 의존성과 재시도는 Airflow 같은 오케스트레이터나 Kubeflow Pipelines, 클라우드의 관리형 파이프라인이 맡는다. DAG로 단계를 묶고 실패를 다시 돌리는 원리는 [Airflow 글](/posts/airflow-orchestration)과 같다.

실험 추적은 학습 한 번마다 파라미터, 지표, 데이터 버전, 코드 커밋, 결과물 위치를 남긴다. 위 실험의 JSON 한 줄을 도구가 대신 써 주고, 여러 실행을 표로 비교하게 해 준다.

모델 레지스트리는 배포할 수 있는 모델의 목록이다. 모델마다 버전 번호가 붙고, 어떤 실행에서 나왔는지 연결되고, 검토 중·운영 중·폐기 같은 상태나 별칭이 붙는다. 서빙은 "운영 중인 버전"을 레지스트리에서 꺼내 간다. 파일을 손으로 복사하지 않는다는 게 요점이다.

서빙은 모델을 실제 예측에 쓰는 곳이다. 밤마다 전체 고객을 한 번에 예측하는 배치 방식과, 요청마다 응답하는 온라인 방식이 있다.

모니터링은 서빙에서 나온 예측 로그와 나중에 들어오는 정답을 보고 이상을 잡는다. 성능이 기준 아래로 떨어지면 재학습을 부르고, 고리가 닫힌다.

작은 팀이 이걸 다 갖출 필요는 없다. 피처 저장소 없이 SQL 뷰 하나로 학습과 배치 서빙이 같은 쿼리를 쓰게 해도 되고, 레지스트리 대신 객체 저장소의 경로 규칙과 메타데이터 파일로 시작해도 된다. 중요한 건 각 화살표에서 "무엇이 어떤 버전으로 넘어갔는지"가 기록되는 것이다.

## 손작업에서 자동 재학습까지: 성숙도 0~2

구글 클라우드가 정리한 MLOps 성숙도 구분이 자주 인용된다. 수준 0, 1, 2로 나누고, 무엇이 자동화되어 있는지로 구분한다(마이크로소프트는 0~4의 다섯 단계로 나누는 등 회사마다 구분은 조금씩 다르다). 아래 그림에서 단계를 넘기면 수준마다 사람이 하던 일이 무엇으로 바뀌는지 볼 수 있다.

수준 0은 위에서 본 장면 그대로다. 모델을 만드는 사람과 운영하는 사람이 나뉘어 있고 그 사이로 파일이 오간다. 학습 코드와 서빙 코드가 따로 있으니 전처리가 두 번 구현되고, 둘이 조금씩 달라진다. 모델이 바뀌는 일이 드물어서 처음에는 괜찮아 보이지만, 세상이 바뀌어 성능이 떨어져도 아무도 모른다.

수준 1의 핵심 변화는 배포하는 대상이 바뀐다는 것이다. 수준 0에서는 모델 파일을 배포하지만, 수준 1에서는 학습 파이프라인을 배포하고 파이프라인이 모델을 만든다. 그래서 운영 환경에서 새 데이터로 재학습이 돌 수 있다. 사람이 없어도 새 모델이 나오니, 평가 단계에서 이전 모델보다 나쁘면 등록을 막는 자동 관문이 필수다. 데이터 검증도 여기서 필요해진다. 입력 데이터가 깨졌는데 그대로 학습하면 깨진 모델이 자동으로 배포된다.

수준 2는 파이프라인 자체를 일반 소프트웨어처럼 CI/CD로 다룬다. 특징 코드를 고친 PR이 올라오면 단위 테스트, 작은 데이터로 파이프라인 전체를 돌리는 통합 테스트, 학습 결과 비교가 자동으로 돌고, 머지되면 새 파이프라인이 운영에 올라간다.

어디까지 갈지는 모델이 얼마나 자주 바뀌어야 하는지로 정한다. 1년에 한 번 갱신해도 되는 모델에 수준 2를 깔면 과하다. 반대로 매주 데이터가 바뀌는 추천·광고 모델을 수준 0으로 돌리면 사람이 매주 노트북을 연다. 수준 0에서 1로 가는 신호는 보통 "재학습을 손으로 하는 게 정기 업무가 됐다"와 "운영 중인 모델을 다시 만들 수 없다"는 사고가 한 번 났을 때다.

## 다시 만들 수 있으려면 무엇을 남기나

이 글을 시작한 사고를 막는 최소 조건을 정리하면 다섯 가지다.

첫째, 코드 커밋. 학습 코드와 특징 코드가 Git에 있고, 학습은 커밋되지 않은 코드로 돌리지 않는다. 노트북은 탐색용으로 쓰고 학습은 스크립트나 파이프라인으로 돌린다.

둘째, 데이터 버전. 학습에 쓴 데이터의 정확한 스냅숏을 가리키는 식별자다. 파일이면 해시, 테이블이면 스냅숏 ID나 "이 시각까지의 데이터" 같은 조건이다. 덮어쓰는 파일 경로(`/data/churn.csv`)는 버전이 아니다.

셋째, 설정과 시드. 하이퍼파라미터, 특징 목록, 무작위 시드를 코드 밖 설정 파일에 두고 함께 기록한다. 위 실험처럼 시드 하나로 예측이 0.78과 0.83으로 갈린다.

넷째, 실행 환경. 라이브러리 버전을 잠금 파일(`requirements.txt`의 정확한 버전, `uv.lock`, `poetry.lock`)로 고정하고, 가능하면 컨테이너 이미지 다이제스트까지 남긴다. 직렬화한 모델 파일은 만든 라이브러리 버전과 다른 버전에서 열면 경고가 나거나 동작이 달라질 수 있다. scikit-learn 문서도 피클로 저장한 모델은 같은 버전에서 읽으라고 권한다.

다섯째, 결과물과 지표. 학습된 모델 파일과 평가 지표를 위 네 가지와 하나로 묶어 저장한다. 레지스트리의 모델 버전이 이 묶음을 가리킨다.

GPU 학습이면 하나 더 알아 둘 게 있다. 시드를 고정해도 GPU의 일부 연산은 병렬 합산 순서 때문에 실행마다 결과가 아주 조금 다를 수 있다. 완전한 비트 단위 재현이 필요하면 프레임워크의 결정론 옵션(PyTorch의 `torch.use_deterministic_algorithms(True)` 등)을 켜고 속도 손해를 감수한다. 대부분은 "같은 데이터와 설정이면 지표가 오차 범위 안에서 같다" 수준의 재현으로 충분하다. 그 기준을 팀이 미리 정해 둔다.

## 데이터가 깨져도 정확도는 멀쩡하다

데이터 의존성이 컴파일러에 안 잡힌다는 말을 직접 확인해 봤다. churn_v2.csv의 새 800행에서 이용 시간 컬럼이 분이 아니라 초로 들어왔다고 해 보자. 원천 시스템이 로그 형식을 바꿨는데 아무도 알려 주지 않은 상황이다. 이 파일(churn_v3_broken.csv)로 그대로 학습하면 이렇게 나온다.

```text
{"data": "churn_v3_broken.csv", "data_sha256": "180c37524dc3", "seed": 42, "sklearn": "1.9.1", "python": "3.13.16", "test_acc": 0.606, "probe_churn_prob": 0.9}
```

시험 정확도 0.606이다. 깨지지 않은 v2(0.6121)와 거의 같아서, 정확도만 보는 평가 관문은 이 모델을 통과시킨다. 시험 데이터도 같은 깨진 파일에서 나눴으니 깨진 대로 맞힌 것이다. 하지만 서빙에서는 이용 시간이 다시 분 단위로 들어올 수도 있고, 같은 고객의 이탈 확률도 0.98에서 0.9로 바뀌었다.

그래서 학습 전에 데이터 자체를 검사한다. 거창한 도구가 아니어도 된다. 컬럼 이름, 결측 비율, 값 범위, 라벨 비율을 미리 정해 두고 어기면 파이프라인을 멈추는 스크립트면 시작으로 충분하다.

```python
# validate.py: 규칙을 어기면 종료 코드 1로 파이프라인을 멈춘다
import sys, numpy as np
d = np.genfromtxt(sys.argv[1], delimiter=",", names=True)
rules = {"visits": (0, 100), "minutes": (0, 600), "tickets": (0, 50)}   # 컬럼별 허용 범위
fail = list(d.dtype.names) != ["visits", "minutes", "tickets", "churned"]
for c, (lo, hi) in rules.items():
    col = d[c]
    nan = np.isnan(col).mean()                    # 결측 비율
    out = ((col < lo) | (col > hi)).mean()        # 범위를 벗어난 비율
    ok = nan <= 0.01 and out <= 0.001
    fail |= not ok
    print(f"{'ok  ' if ok else 'FAIL'} {c:8s} null={nan:.3%} out_of_range={out:.3%} median={np.nanmedian(col):.1f}")
rate = np.nanmean(d["churned"]); ok = 0.05 <= rate <= 0.6; fail |= not ok
print(f"{'ok  ' if ok else 'FAIL'} churned  rate={rate:.3f}")
sys.exit(1 if fail else 0)
```

봐야 할 곳은 minutes 줄이다. 중앙값은 17.6에서 19.2로 조금밖에 안 움직였다. 깨진 행이 전체 5,800행 중 800행뿐이라 중앙값 같은 요약값으로는 티가 잘 안 난다. 범위를 벗어난 비율 12.103%가 먼저 잡았다. 그래서 검사는 평균·중앙값 하나보다 범위, 결측, 분포 비교를 여러 개 겹쳐 둔다. 이런 규칙을 선언형으로 관리하는 도구(Great Expectations, pandera 같은 것)도 있지만, 처음에는 이 정도 스크립트를 파이프라인 맨 앞에 두는 것만으로도 위 사고를 막는다.

## 새 모델이 운영에 들어갈 자격

자동 재학습이 돌면 사람 대신 코드가 "이 모델을 올려도 되나"를 판단해야 한다. 이 판단을 평가 관문이라고 부른다. 관문을 짤 때 흔히 쓰는 규칙은 세 가지다.

첫째, 비교 대상은 고정한다. 지금 운영 중인 모델과 후보 모델을 같은 평가 데이터에서 잰다. 평가 데이터를 매번 새로 뽑으면 숫자가 오른 게 모델 덕인지 데이터 덕인지 알 수 없다.

둘째, 허용 오차를 미리 정한다. 0.594가 0.591이 됐다고 매번 사람을 부르면 자동화한 의미가 없다. "운영 모델보다 0.01 넘게 떨어지면 거부" 같은 숫자를 정해 둔다. 이 숫자는 같은 설정으로 시드만 바꿔 여러 번 학습했을 때 지표가 얼마나 흔들리는지를 보고 정한다.

셋째, 전체 평균만 보지 않는다. 전체 정확도는 올랐는데 신규 가입자에서만 크게 떨어지는 모델이 있다. 중요한 고객군(세그먼트)마다 따로 재서 하나라도 기준을 넘게 떨어지면 거부한다. 세그먼트가 평가 결과에서 아예 빠져 있으면, 그 데이터가 사라졌다는 뜻일 수 있으니 그것도 거부한다.

아래 함수를 채워서 관문을 직접 만들어 보자. `current`와 `candidate`는 `overall`(전체 지표)과 `segments`(고객군별 지표)를 가진 객체다.

관문을 통과했다고 끝이 아니다. 평가 데이터는 과거이고 운영은 현재라, 오프라인 평가가 좋아도 운영에서 나빠질 수 있다. 그래서 관문 뒤에 카나리나 섀도 배포를 한 번 더 둔다. 오프라인 관문은 명백히 나쁜 모델을 싸게 거르고, 온라인 배포 전략은 오프라인에서 보이지 않는 문제를 작은 범위에서 겪게 한다.

## 도구 없이 시작하는 최소 구성

플랫폼을 들이기 전에도 위의 원칙은 지킬 수 있다. 객체 저장소 하나와 경로 규칙, 학습 스크립트가 남기는 메타데이터 파일이면 레지스트리의 핵심 기능(버전, 출처, 운영 중인 버전 표시)을 흉내 낼 수 있다.

```text
s3://ml-models/churn/
  v13/
    model.pkl
    manifest.json
  v14/
    model.pkl
    manifest.json
  production.txt        # 내용: v14  (서빙은 이 파일이 가리키는 버전을 읽는다)
```

manifest.json에는 위 실험에서 찍던 값을 그대로 넣는다.

```json
{
  "model": "churn",
  "version": "v14",
  "git_commit": "학습 스크립트의 커밋 해시",
  "data": "churn_v2.csv",
  "data_sha256": "c42ec285d7d4",
  "seed": 42,
  "params": { "n_estimators": 50, "max_features": 1 },
  "env": { "python": "3.13.16", "sklearn": "1.9.1" },
  "metrics": { "test_acc": 0.6121 }
}
```

배포는 `production.txt`의 내용을 바꾸는 일이 되고, 롤백은 이전 버전 이름으로 되돌리는 일이 된다. 모델 파일을 서버에 손으로 복사하지 않으니 "지금 도는 게 무엇인가"에 항상 답할 수 있다. 이 구성이 버거워지는 신호는 실행 기록을 비교하고 싶어질 때(어떤 파라미터가 좋았나), 여러 모델과 여러 팀이 같은 저장소를 쓰기 시작할 때, 승인 절차와 권한이 필요해질 때다. 그때 MLflow 같은 실험 추적·레지스트리 도구로 옮기면, 이미 남겨 둔 메타데이터를 그대로 옮겨 담으면 된다.

## DevOps를 하던 팀이 처음 겪는 것

백엔드·인프라 쪽에서 MLOps로 넘어오면 익숙한 것과 낯선 것이 섞여 있다.

익숙한 것: 컨테이너, CI/CD, 쿠버네티스, 카나리와 롤백, 지표와 알림. 서빙은 결국 HTTP API이고 파이프라인은 결국 DAG다. 이 경험이 MLOps의 절반을 이미 채운다.

낯선 것 첫째는 테스트가 "통과/실패"로 끝나지 않는다는 점이다. 새 모델의 정확도가 0.594에서 0.591로 떨어졌으면 실패인가? 데이터를 다시 섞으면 0.597이 나올 수도 있다. 기준을 숫자와 허용 오차로 미리 정해 두지 않으면 매번 사람이 판단하게 된다.

둘째는 장애가 조용하다는 점이다. 서버가 500을 내면 바로 알림이 오지만, 모델이 틀린 답을 내면 HTTP는 200이다. 입력 컬럼 단위가 바뀌어 예측이 엉망이 되어도 지연 시간과 오류율 대시보드는 정상이다. 그래서 예측 분포와 입력 분포를 따로 감시한다.

셋째는 정답이 늦게 온다는 점이다. 이탈 예측의 정답(실제로 떠났는가)은 한 달 뒤에 알 수 있다. 그 한 달 동안은 입력·예측 분포 같은 대리 지표로 버틴다.

넷째는 자원 모양이 다르다는 점이다. 학습은 GPU를 몇 시간 꽉 쓰고 끝나는 배치 작업이고, 서빙은 지연 시간 예산 안에서 계속 응답하는 서비스다. 같은 클러스터에서 둘을 돌리면 학습이 서빙의 GPU를 빼앗지 않게 큐와 우선순위를 나눠야 한다. 쿠버네티스에서 GPU를 나눠 주는 방식은 [쿠버네티스 GPU 글](/posts/k8s-gpu-dra)에 있다.

LLM을 API로 붙여 쓰는 서비스는 모델을 직접 학습하지 않으니 이 중 일부가 사라진다. 대신 프롬프트와 모델 버전이 "모델" 자리에 들어오고, 평가 세트로 회귀를 막는 일([LLM 평가 글](/posts/llm-evals))이 같은 역할을 한다. 원칙은 그대로다. 무엇이 어떤 버전으로 돌았는지 기록하고, 바꿀 때는 자동 관문을 지나게 한다.

## 플랫폼을 사기 전에 확인할 것

MLOps 도구는 많다. MLflow, Kubeflow, 클라우드 관리형 서비스(SageMaker, Vertex AI 같은 것), 피처 저장소 전용 제품(Feast 등), 실험 추적 SaaS. 하나를 골라 깔면 MLOps가 된다고 생각하기 쉽다.

도구를 고르기 전에 지금 무엇이 아픈지를 먼저 적는다. 운영 모델을 다시 못 만드는 게 문제면 실험 추적과 데이터 버전부터. 재학습을 손으로 하는 게 문제면 파이프라인부터. 학습과 서빙의 특징이 어긋나는 게 문제면 특징 정의를 한곳에 모으는 것부터. 성능이 떨어진 걸 늦게 아는 게 문제면 모니터링부터다. 아픈 곳과 상관없는 구성 요소를 먼저 깔면 운영할 시스템만 늘어난다.

흔한 실수 몇 가지도 적어 둔다. 노트북에서 학습한 모델을 "일단 이번만" 손으로 올리는 것. 이게 한 번이면 끝나지 않는다. 평가 데이터를 매번 새로 뽑아서 모델끼리 비교가 안 되는 것. 비교용 고정 평가 세트를 하나 둔다. 재학습을 자동화하면서 평가 관문을 빼는 것. 위에서 본 대로 사람이 막던 실수를 아무도 막지 못한다. 예측 로그를 남기지 않는 것. 나중에 정답과 맞춰 볼 재료가 없어서 모니터링을 시작할 수 없다.

## 세 축을 기록하고, 관문을 세우고, 고리를 닫는다

ML 시스템은 코드, 데이터, 모델이 따로 바뀌고, 아무것도 안 바뀌어도 세상이 바뀌면 낡는다. 그래서 MLOps는 세 축의 버전을 함께 기록해 어떤 모델이든 다시 만들 수 있게 하고, 데이터 준비부터 배포까지를 파이프라인으로 자동화하되 자동화한 자리마다 검증 관문을 세우고, 모니터링이 재학습을 부르게 해서 고리를 닫는다. 이어지는 글에서는 고리의 한 지점씩, 학습한 모델을 서비스에 내보내는 [모델 서빙](/posts/model-serving)부터 본다.

## 면접에서 나올 만한 질문

### MLOps는 DevOps와 무엇이 다른가

DevOps는 바뀌는 것이 코드 하나라고 보고 빌드·테스트·배포를 자동화한다. MLOps는 코드, 데이터, 모델 세 축이 따로 바뀌고, 코드가 그대로여도 세상이 바뀌면 모델이 낡는다는 점을 다룬다. 그래서 데이터와 모델의 버전 관리, 데이터·모델 검증, 지속 학습(CT), 예측 품질 모니터링이 더해진다. 컨테이너, CI/CD, 카나리 같은 DevOps 도구는 그대로 쓴다.

### ML 시스템의 숨은 기술 부채란 무엇인가

2015년 구글 논문에서 나온 말로, ML 시스템은 학습 코드보다 그 주변(데이터 수집, 특징, 설정, 서빙, 모니터링)이 훨씬 크고 거기서 운영 비용이 생긴다는 지적이다. 특징 하나가 바뀌면 전체가 바뀌는 얽힘, 몰래 예측을 가져다 쓰는 소비자, 컴파일러가 잡지 못하는 데이터 의존성, 스크립트가 엉킨 파이프라인 정글, 모델이 자기 학습 데이터를 바꾸는 피드백 루프가 대표적이다.

### 모델 재현성을 지키는 최소 조건은

코드 커밋, 데이터의 정확한 버전(해시나 스냅숏 ID), 하이퍼파라미터와 시드, 고정된 라이브러리 버전과 실행 환경, 그리고 이걸 모델 파일과 지표에 묶어 남기는 것이다. 덮어쓰는 파일 경로는 데이터 버전이 아니다. 직접 해 보면 시드만 달라도 같은 고객의 예측이 0.78과 0.83으로 갈리고, 데이터에 800행을 더하면 0.66이 0.98이 된다.

### 성숙도 수준 0, 1, 2는 무엇으로 나뉘나

자동화된 범위로 나뉜다. 수준 0은 노트북에서 손으로 학습하고 모델 파일을 넘긴다. 수준 1은 학습 과정이 파이프라인이 되어 새 데이터나 성능 저하로 자동 재학습되고, 배포 대상이 모델이 아니라 파이프라인이 된다. 수준 2는 파이프라인 코드까지 CI/CD로 테스트·배포한다. 어디까지 갈지는 모델이 얼마나 자주 바뀌어야 하는지로 정한다.

### 재학습을 자동화할 때 꼭 함께 넣어야 하는 것은

데이터 검증과 모델 평가 관문이다. 깨진 입력으로 학습한 모델이나 이전보다 나쁜 모델이 사람 확인 없이 운영에 들어가는 걸 막아야 한다. 배포는 카나리나 섀도 방식으로 작게 시작하고, 레지스트리의 이전 버전으로 바로 되돌릴 수 있게 한다.

### 모델 장애는 왜 늦게 발견되나

모델이 틀린 답을 내도 HTTP 응답은 정상이라 지연 시간·오류율 대시보드에 나타나지 않는다. 정답도 늦게 들어와서 실제 성능은 몇 주 뒤에야 알 수 있다. 그래서 입력 분포와 예측 분포를 학습 때와 비교하는 대리 지표를 따로 감시하고, 나중에 정답과 맞춰 볼 수 있게 예측 로그를 남긴다.

### 피처 저장소는 왜 필요한가

학습과 서빙이 같은 특징 정의를 쓰게 하려고 쓴다. 학습 때는 과거 시점 기준으로 대량으로, 서빙 때는 한 건을 빠르게 꺼내야 해서 경로가 둘로 갈리고, 따로 구현하면 값이 어긋난다. 작은 팀은 학습과 배치 서빙이 같은 SQL 뷰를 쓰게 하는 것만으로도 같은 효과를 낼 수 있다.
