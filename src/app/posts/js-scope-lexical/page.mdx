<EasyIntro>
  프로그램 안에서는 같은 이름의 변수가 여러 군데 있을 수 있다. 그래서 코드가 어떤 이름을 쓰면 그게 어느 변수를 가리키는지 정하는 규칙이 필요하다. 이 규칙이 없으면 안쪽에서 만든 변수와 바깥 변수가 뒤섞여서 값이 엉뚱한 곳에 들어간다.

  자바스크립트는 이름을 자기 방부터 찾고, 없으면 한 겹 바깥 방으로 나가서 찾는다. 이때 바깥 방이 어디인지는 함수를 누가 불렀느냐가 아니라 코드를 어디에 적었느냐로 정해진다. 함수는 자기가 태어난 방을 기억해 두고 어디서 불려도 그 방부터 바깥을 본다.

  그래서 안쪽에서 같은 이름으로 새 변수를 만들면 바깥 변수는 가려져서 보이지 않는다. 바깥 변수에 값을 넣고 싶었는데 새 변수를 만들어 버린 실수가 이 글의 첫 버그다.
</EasyIntro>

로그인 함수를 고치다가 이상한 버그를 만났다. 로그인은 성공했는데 화면 위쪽의 사용자 이름이 계속 비어 있다. 줄여 보면 이런 코드였다.

```js
let currentUser = null;
function login(name) {
  if (name) {
    let currentUser = { name }; // 바깥 currentUser를 가린다
    console.log("inside", currentUser.name);
  }
}
login("kim");
console.log("outside", currentUser);
```

```text
inside kim
outside null
```

안에서는 `kim`이 찍히는데 밖에서는 여전히 `null`이다. 블록 안의 `let currentUser`가 바깥 변수에 값을 넣은 게 아니라 같은 이름의 새 변수를 만들었기 때문이다. 어느 `currentUser`가 어느 것인지는 코드를 쓴 위치로 정해진다. 이 글은 자바스크립트가 이름을 어디서 찾는지, 그 규칙이 왜 "쓴 위치" 기준인지를 따라간다.

이 주제의 다른 글도 있다. `var`, `let`, `const`가 각각 어떤 범위를 만드는지는 [var, let, const 글](/posts/js-var-let-const)에서, 선언 전에 이름을 쓰면 생기는 일은 [호이스팅과 TDZ 글](/posts/js-hoisting-tdz)에서 다룬다. 이 글은 이름을 찾는 길에 집중한다.

## 이름은 안쪽부터 바깥으로 찾는다

스코프는 "이 이름이 통하는 범위"다. 자바스크립트에는 범위가 여러 겹 있다.

- 전역 범위. 페이지 전체가 공유한다.
- 모듈 범위. ES 모듈 파일 하나(그리고 Node.js의 CommonJS 파일 하나)마다 생긴다.
- 함수 범위. 함수를 호출할 때마다 새로 생긴다.
- 블록 범위. `{ }`, `if`, `for`, `try`/`catch` 블록에서 `let`, `const`, `class`를 선언하면 생긴다.

코드가 어떤 이름을 쓰면 엔진은 지금 있는 범위부터 찾고, 없으면 한 겹 바깥으로 나간다. 전역까지 나갔는데도 없으면 `ReferenceError`다. 이렇게 이어진 범위의 사슬을 스코프 체인이라고 부른다.

## 쓴 자리가 바깥을 정한다

그러면 "한 겹 바깥"은 무엇을 기준으로 정할까. 호출한 곳일까, 함수를 쓴 곳일까.

```js
const label = "global";
function show() {
  console.log(label);
}
function run() {
  const label = "run";
  show();
}
run();
```

```text
global
```

`show`는 `run` 안에서 불렸지만 `run`의 `label`을 보지 않는다. `show`를 코드에 쓴 곳이 전역이라서 `show`의 바깥은 전역이다. 이렇게 코드를 쓴 위치로 범위가 정해지는 방식을 렉시컬 스코프(lexical scope, 정적 스코프)라고 한다. lexical은 "글자로 쓰인"이라는 뜻이다. 코드를 읽기만 해도 어떤 이름이 어디로 이어지는지 알 수 있다.

반대 방식도 있다. 호출한 곳을 따라 찾는 동적 스코프다. bash의 `local` 변수가 이렇게 동작한다. 같은 구조를 bash 5.2로 돌려 봤다.

```bash
label="global"
show() { echo "$label"; }
run() { local label="run"; show; }
run   # run 안에서 부른 show
show  # 전역에서 부른 show
```

```text
run
global
```

같은 `show`인데 누가 불렀느냐에 따라 결과가 달라진다. 아래 그림에서 자바스크립트 쪽이 무엇을 보고 결정하는지 단계별로 따라가 보자. 아래 상자는 콜 스택이다.

자바스크립트에도 호출한 쪽에 따라 정해지는 것이 하나 있다. `this`다. 일반 함수의 `this`는 어떻게 불렀느냐로 정해지고, 화살표 함수는 `this`를 따로 갖지 않아서 렉시컬 스코프처럼 바깥의 `this`를 쓴다. 이 이야기는 [this 바인딩 글](/posts/js-this-binding)에 있다.

## 함수는 태어난 환경을 들고 다닌다

명세 수준에서 보면 이 규칙은 두 개의 연결로 이뤄진다.

- 모든 환경 레코드(Environment Record)는 바깥 환경을 가리키는 `[[OuterEnv]]`를 갖는다. 스코프 체인은 이 연결을 따라가는 것이다.
- 함수 객체는 만들어질 때 그 순간의 환경을 `[[Environment]]` 슬롯에 저장한다. 나중에 호출되면 새 함수 환경을 만들고 그 `[[OuterEnv]]`를 저장해 둔 `[[Environment]]`로 건다.

호출한 위치는 이 과정 어디에도 끼지 않는다. 그래서 렉시컬 스코프다.

```js
const TAX = 10;
function makePricer(rate) {
  return function price(amount) {
    const fee = 100;
    return amount + rate + TAX + fee;
  };
}
const p = makePricer(20);
console.log(p(1000));
```


`makePricer`는 이미 끝났는데 `p(1000)`은 `rate`를 읽는다. `price` 함수 객체가 `makePricer` 호출 환경을 저장해 뒀고, 그 환경이 아직 참조되고 있어서 사라지지 않았다. 이게 [클로저](/posts/js-closures)다. 클로저는 렉시컬 스코프의 결과일 뿐 별도의 규칙이 아니다. 이 연결 때문에 큰 객체가 오래 살아남는 문제는 [메모리 누수 글](/posts/js-memory-leak)에서 다룬다.

스코프 체인을 직접 흉내 내 보자. 환경 하나는 `vars`와 `outer`를 가진 객체이고, 맨 바깥의 `outer`는 `null`이다. 이름을 찾으면 그 값을, 끝까지 없으면 오류 문자열을 돌려주면 된다. 값이 `0`인 변수도 "있는" 변수이니 주의한다.

## 엔진은 실행 전에 찾을 곳을 정해 둔다

명세는 "안에서 밖으로 찾는다"고 설명하지만, 실제 엔진이 매번 이름을 문자열로 비교하며 사슬을 걷지는 않는다. 렉시컬 스코프의 큰 장점은 코드만 읽고 어디서 찾을지 미리 알 수 있다는 것이다. V8은 파싱할 때 스코프 분석을 해서 이름마다 자리를 정한다.

위의 `price` 함수를 Node 22에서 `--print-bytecode --print-bytecode-filter=price`로 찍어 보면 이렇다. 주소와 오프셋 열은 빼고 명령만 남겼다.

```text
LdaSmi [100]
Star0
LdaImmutableCurrentContextSlot [2]
Add a0, [0]
Star1
LdaImmutableContextSlot <context>, [2], [1]
ThrowReferenceErrorIfHole [0]
Add r1, [1]
Star1
Ldar r0
Add r1, [2]
Return
```

`fee`(100)는 `Star0`으로 레지스터 `r0`에 들어갔다가 `Ldar r0`으로 읽힌다. 안쪽 함수가 쓰지 않으니 힙에 둘 필요가 없다. `amount`는 매개변수라 `a0`다. `rate`는 `makePricer` 환경의 칸이라 `LdaImmutableCurrentContextSlot [2]`로 읽고, `TAX`는 한 겹 더 위 환경이라 `LdaImmutableContextSlot <context>, [2], [1]`로 읽는다. 마지막 `[1]`이 올라갈 깊이다. 그 뒤의 `ThrowReferenceErrorIfHole`은 `TAX`가 아직 초기화 전인지 확인하는 명령인데, 이게 TDZ 검사다([호이스팅과 TDZ 글](/posts/js-hoisting-tdz)).

여기서 실무에 쓸 결론이 두 가지 나온다. 첫째, 깊은 스코프의 변수를 읽는 비용 때문에 코드를 바꿀 이유는 거의 없다. 이미 칸 위치로 바뀌어 있다. 둘째, 클로저가 잡는 변수는 힙에 남는다. 함수가 오래 살면 그 Context도 같이 산다. 이 바이트코드는 V8 버전마다 이름과 모양이 조금씩 다르니 형태만 참고한다.

## 같은 이름으로 가리기

처음 버그로 돌아가자. 안쪽 범위에서 바깥과 같은 이름을 선언하면 안쪽에서는 바깥 이름이 보이지 않는다. 이걸 가리기(shadowing)라고 한다. 오류가 아니라 정상 동작이라서 엔진은 아무 말도 하지 않는다.

가리기가 늘 나쁜 건 아니다. 콜백 매개변수 이름을 `item`, `error`처럼 자주 쓰는 말로 짓다 보면 자연스럽게 생기고, 의도적으로 바깥 값을 못 쓰게 막을 때도 있다. 문제는 처음 예제처럼 "바깥 변수에 넣으려다 새 변수를 만든" 경우다. 차이는 `let` 한 단어라서 리뷰에서 놓치기 쉽다.

이런 실수는 린터가 잘 잡는다. ESLint 9에서 `no-shadow`와 `no-undef`를 켜고 처음 예제와 다음 절의 예제를 검사했다. 경로 줄은 파일 이름만 남겼다.

```text
login.js
  4:9  error  'currentUser' is already declared in the upper scope on line 1 column 5  no-shadow

setup.js
  2:3  error  'count' is not defined  no-undef

✖ 2 problems (2 errors, 0 warnings)
```

`no-shadow`는 TypeScript 프로젝트라면 `@typescript-eslint/no-shadow`를 대신 쓴다. 기본 규칙은 타입과 값의 이름이 같을 때 잘못 경고하는 경우가 있다.

## 선언 없이 대입하면 전역이 생긴다

위 검사의 `setup.js`는 이런 코드다.

```js
function setup() {
  count = 1; // 선언 없이 대입
}
setup();
console.log(globalThis.count);
```

```text
1
```

`count`를 어디서도 선언하지 않았는데 오류가 나지 않고 전역 객체에 속성이 생겼다. 스코프 체인 끝까지 이름을 못 찾았을 때, 읽기는 `ReferenceError`지만 느슨한 모드의 쓰기는 전역 객체에 새 속성을 만든다. 오타 하나가 전역 변수가 되는 셈이다.

파일 맨 위에 `"use strict";`를 붙이고 같은 코드를 돌리면 이렇게 된다. 파일 경로는 줄였다.

```text
  count = 1; // 선언 없이 대입
        ^

ReferenceError: count is not defined
    at setup (.../s4.js:3:9)
```

ES 모듈과 `class` 본문은 자동으로 엄격 모드라서 요즘 코드에서는 이 사고가 덜 난다. 그래도 번들러를 거치지 않는 레거시 스크립트, 브라우저 콘솔에 붙여 넣는 코드, 일부 설정 파일은 느슨한 모드로 돈다. 엄격 모드가 막는 다른 것들은 [strict mode 글](/posts/js-strict-mode)에 정리돼 있다.

## 매개변수 기본값에는 따로 범위가 있다

면접에서 가끔 나오는 꼬리 질문이다. 매개변수 기본값 식은 함수 본문보다 바깥의 범위에서 평가된다.

```js
let x = "outer";
function f(read = () => x) {
  let x = "inner";
  return [read(), x];
}
console.log(f());
```

```text
[ 'outer', 'inner' ]
```

기본값의 화살표 함수는 매개변수 범위에서 만들어졌고, 그 범위에는 `x`가 없으니 바깥의 `outer`를 본다. 본문의 `let x`는 그보다 안쪽 범위다. 명세에서는 기본값이 있는 함수에 매개변수용 환경과 본문용 환경을 따로 만든다. 실무에서 이걸 일부러 쓸 일은 거의 없지만, 기본값에서 본문 변수를 쓰려다 엉뚱한 값을 읽는 이유가 이것이다.

## eval과 with는 규칙을 흐린다

렉시컬 스코프는 코드만 보고 이름의 자리를 알 수 있다는 약속이다. 이걸 깨는 문법이 두 개 있다. `with (obj) { ... }`는 블록 안의 이름을 `obj`의 속성에서 먼저 찾게 해서, `obj`에 무엇이 들어오느냐에 따라 같은 줄이 다른 변수를 가리킨다. 느슨한 모드의 직접 `eval("var y = 1")`은 실행 중에 함수 범위에 새 변수를 끼워 넣는다.

엔진은 이런 함수 안에서는 이름의 자리를 미리 정하지 못하니 최적화를 포기하고 느린 방식으로 찾는다. 엄격 모드에서는 `with`가 아예 `SyntaxError`이고, `eval`은 자기만의 범위를 따로 갖는다. 새 코드에서 둘 다 쓸 이유는 없고, 레거시 코드에서 보이면 스코프를 예측하기 어려운 지점으로 표시해 둔다.

## 개발자 도구에서 스코프 체인 보기

이름이 어디서 왔는지 헷갈릴 때 가장 빠른 방법은 멈춰 놓고 보는 것이다. 크롬 개발자도구 Sources 패널에서 중단점을 걸면 오른쪽 Scope 섹션에 지금 줄의 스코프 체인이 안쪽부터 나온다. 아래 코드를 Chromium에서 열어 `debugger` 줄에 멈춘 뒤, 개발자 도구가 쓰는 것과 같은 프로토콜(CDP)로 스코프 목록을 꺼냈다.

```js
const appName = "shop";
var legacy = 1;
function makeCounter() {
  let count = 0;
  return function inc(step) {
    if (step > 0) {
      const next = count + step;
      debugger;
      count = next;
    }
    return count;
  };
}
makeCounter()(1);
```

```text
block inc | next=1
local inc | step=1
closure makeCounter | count=0
script  | appName=shop
global  |
```

패널에서는 이 목록이 Block, Local, Closure (makeCounter), Script, Global로 보인다. 조각을 눌러 각 칸이 무엇인지 확인해 보자.

Closure 칸에 "안쪽 함수가 쓰는 변수만" 보인다는 점이 실전에서 자주 헷갈린다. 중단점에서 바깥 함수의 변수를 콘솔에 쳤는데 `ReferenceError`가 나는 경우가 있다. 변수가 없어진 게 아니라 안쪽 함수가 그 변수를 쓰지 않아서 V8이 Context에 넣지 않은 것이다. 확인하고 싶다면 그 변수를 안쪽 함수에서 한 번 읽게 하거나 바깥 함수에서 멈춘다.

## React에서 컴포넌트 안에 컴포넌트를 쓰면

렉시컬 스코프는 편하다. 컴포넌트 안에서 함수를 정의하면 그 렌더의 props와 state를 인자 없이 바로 쓸 수 있다. 이 편리함 때문에 이런 코드가 나온다.

```js
function SearchPage({ keyword }) {
  const [page, setPage] = useState(1);

  // keyword와 page를 props 없이 쓰려고 안쪽에 정의했다
  function ResultList() {
    return <List keyword={keyword} page={page} />;
  }

  return <ResultList />;
}
```

동작은 한다. 하지만 `SearchPage`가 다시 렌더링될 때마다 `ResultList`는 새 함수 객체로 만들어진다. React는 컴포넌트 타입이 이전 렌더와 같은 함수인지 비교하는데, 매번 다른 함수이니 다른 컴포넌트로 보고 이전 것을 언마운트한 뒤 새로 마운트한다. `List` 안의 입력값, 스크롤 위치, 내부 state가 렌더마다 초기화된다.

고치는 방법은 `ResultList`를 파일 최상위로 옮기고 필요한 값을 props로 넘기는 것이다. 값을 가져오는 통로를 렉시컬 스코프에서 props로 바꾸는 셈이다. 렌더링 안에서 함수를 부르는 것(`{renderList()}`)은 컴포넌트 타입이 생기지 않으니 이 문제가 없다. React가 무엇을 기준으로 같은 컴포넌트로 보는지는 [React 리렌더링 글](/posts/react-rerender)의 재조정 부분에서 다룬다.

## 다시 로그인 버그로

처음 코드의 `let currentUser`는 블록 범위에 새 이름을 만들었고, 블록 안의 모든 `currentUser`는 그 새 이름을 가리켰다. 바깥 `currentUser`에 값을 넣으려면 `let`을 지우고 대입만 하면 된다. 자바스크립트는 이름을 쓴 자리에서 안쪽부터 바깥으로 찾고, 그 바깥은 호출한 곳이 아니라 코드를 쓴 곳이 정한다. 함수는 태어난 환경을 저장해 두니 어디서 불려도 같은 이름을 본다. 이 한 문장이 클로저, 가리기, 그리고 React의 오래된 값 문제를 모두 설명한다.

## 면접에서 나올 만한 질문

### 스코프란 무엇이고 자바스크립트에는 어떤 스코프가 있나요?

스코프는 이름이 통하는 범위다. 자바스크립트에는 전역, 모듈, 함수, 블록 범위가 있다. `var`는 함수 범위를, `let`, `const`, `class`는 블록 범위를 따르고, ES 모듈은 파일마다 자기 범위를 갖는다. 이름을 쓰면 안쪽 범위부터 바깥으로 찾고 전역까지 없으면 `ReferenceError`가 난다.

### 렉시컬 스코프와 동적 스코프의 차이는 무엇인가요?

렉시컬 스코프는 함수를 코드에 쓴 위치로 바깥 범위가 정해지고, 동적 스코프는 호출한 곳을 따라 찾는다. 자바스크립트는 렉시컬 스코프라서 같은 함수를 어디서 불러도 같은 변수를 본다. bash의 `local`은 동적 스코프라 누가 불렀느냐에 따라 결과가 바뀐다. 자바스크립트에서 호출 방식에 따라 정해지는 것은 스코프가 아니라 `this`다.

### 엔진은 렉시컬 스코프를 어떻게 구현하나요?

명세에서는 환경 레코드가 바깥 환경을 `[[OuterEnv]]`로 가리키고, 함수 객체가 만들어질 때 그 순간의 환경을 `[[Environment]]`에 저장한다. 호출하면 새 환경의 바깥을 저장된 환경으로 잇는다. V8은 파싱 때 스코프 분석으로 이름마다 레지스터나 Context 칸을 정해 두고, 실행 중에는 이름 비교 없이 정해진 깊이와 칸으로 바로 읽는다.

### 클로저와 렉시컬 스코프는 어떤 관계인가요?

클로저는 렉시컬 스코프의 결과다. 함수가 자기가 만들어진 환경을 기억하니, 바깥 함수가 끝난 뒤에도 그 환경이 참조되는 동안 변수가 살아 있다. 따로 추가된 규칙이 아니라 "바깥은 쓴 자리가 정한다"는 규칙을 함수가 오래 살아남는 경우에 적용한 것이다. 그래서 클로저가 잡은 변수는 힙의 Context에 남고, 함수가 오래 살면 메모리도 오래 잡힌다.

### 변수 섀도잉은 언제 문제가 되나요?

바깥 변수에 값을 넣으려다 `let`이나 `const`를 붙여 같은 이름의 새 변수를 만드는 경우다. 문법상 정상이라 오류가 없고, 바깥 값은 그대로 남아 버그를 찾기 어렵다. ESLint의 `no-shadow`(TypeScript는 `@typescript-eslint/no-shadow`)로 잡는다. 콜백 매개변수처럼 의도된 가리기는 규칙 옵션으로 허용 범위를 정한다.

### 선언하지 않은 변수에 값을 대입하면 어떻게 되나요?

느슨한 모드에서는 스코프 체인 끝까지 이름을 못 찾으면 전역 객체에 새 속성을 만든다. 오타가 조용히 전역 변수가 되는 셈이다. 엄격 모드에서는 `ReferenceError`가 난다. ES 모듈과 클래스 본문은 자동으로 엄격 모드다.

### 컴포넌트 안에 컴포넌트를 정의하면 왜 문제가 되나요?

부모가 렌더링될 때마다 안쪽 컴포넌트 함수가 새로 만들어지기 때문이다. React는 컴포넌트 타입이 같은 함수인지로 이전 것과 짝을 맞추는데, 매번 다른 함수라서 언마운트 후 다시 마운트한다. 그래서 내부 state, 입력값, 포커스가 렌더마다 사라진다. 바깥 변수를 쓰고 싶어서 생기는 실수이므로 컴포넌트를 최상위로 옮기고 props로 넘긴다.
