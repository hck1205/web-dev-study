import { getPostMetadata } from "@/features/posts";

export const metadata = getPostMetadata("http-status-codes");

프론트엔드에서 `fetch`의 결과를 `res.ok`로 판단하고 있었다. 그런데 비밀번호를 틀리게 넣어도 화면이 로그인 성공 쪽으로 넘어간다. 네트워크 탭을 열어 보니 응답이 이렇다.

```
HTTP/1.1 200 OK
Content-Type: application/json

{"success": false, "error": "INVALID_PASSWORD"}
```

서버는 실패했다고 말하고 있는데 상태 줄은 성공이라고 말한다. `res.ok`는 상태 코드만 보니 성공으로 받아들였다. 이 API를 지나가는 CDN도, 모니터링도, 재시도 로직도 모두 이 응답을 성공으로 센다. 상태 코드는 응답 본문을 열어 보지 않는 모든 중간 단계가 읽는 유일한 신호다. 그래서 대충 고르면 본문 바깥의 모든 것이 틀린 판단을 한다.

요청과 응답이 어떤 모양으로 오가는지는 [HTTP 메시지 글](/posts/http-message)에, 메서드의 안전성과 멱등성은 [HTTP 메서드 글](/posts/http-methods)에 따로 적었다. 여기서는 응답의 첫 줄, 세 자리 숫자만 본다.

## 첫 자리 숫자가 먼저다

상태 코드는 세 자리이고, 첫 자리가 응답의 큰 성격(class)을 정한다.

- 1xx: 아직 끝나지 않았다. 최종 응답 전에 오는 중간 응답이다
- 2xx: 요청을 받아들여 처리했다
- 3xx: 끝내려면 클라이언트가 더 할 일이 있다(대개 다른 주소로 가기)
- 4xx: 요청한 쪽에 문제가 있다
- 5xx: 요청은 멀쩡했을 수 있는데 서버 쪽이 처리하지 못했다

이 첫 자리가 중요한 이유는 모르는 코드를 만났을 때 드러난다. HTTP 명세(RFC 9110)는 클라이언트가 모든 코드를 알 필요는 없지만 클래스는 이해해야 한다고 정한다. 모르는 코드를 받으면 같은 클래스의 `x00`으로 취급한다. 서버가 새로 만든 `418`이나 `499`를 받은 클라이언트는 그냥 `400`이라고 보면 된다. 단, 모르는 코드의 응답은 캐시에 저장하지 않는다.

그래서 새 코드를 지어낼 때도 첫 자리만은 지켜야 한다. nginx가 클라이언트가 먼저 연결을 끊은 요청을 로그에 `499`로 남기는 것처럼, 비표준 코드가 실제로 쓰이기도 한다. 이런 코드가 바깥으로 나가더라도 클래스가 맞으면 아무것도 모르는 클라이언트가 최소한 "내 쪽 문제"인지 "서버 쪽 문제"인지는 안다.

## 최종 응답 전에 오는 1xx

1xx는 최종 응답이 아니다. 같은 요청에 1xx가 여러 번 온 다음 2xx~5xx 중 하나가 마지막에 온다. 실무에서 마주치는 건 세 개 정도다.

`100 Continue`는 큰 본문을 보내기 전에 서버의 의사를 묻는 용도다. 클라이언트가 `Expect: 100-continue` 헤더를 붙여 헤더만 먼저 보내고 기다린다. 서버가 `100`을 주면 본문을 보내고, 인증 실패나 크기 초과로 어차피 거절할 요청이면 `401`이나 `413`을 바로 준다. 수백 MB 업로드를 끝까지 보낸 다음에 거절당하는 낭비를 막는다. curl은 본문이 일정 크기를 넘으면 이 헤더를 자동으로 붙이고, 브라우저의 `fetch`는 붙이지 않는다. 프록시가 이 헤더를 제대로 처리하지 못해 요청이 1초쯤 멈췄다가 진행되는 문제가 종종 나오는데, curl이 `100`을 기다리다 일정 시간이 지나면 본문을 그냥 보내기 때문이다.

`101 Switching Protocols`는 같은 연결의 프로토콜을 바꾸는 응답이다. HTTP/1.1에서 웹소켓을 여는 요청이 대표적이다. 클라이언트가 `Upgrade: websocket`을 보내고 서버가 `101`로 답하면, 그 TCP 연결은 그 순간부터 HTTP가 아니라 웹소켓 프레임이 오간다. HTTP/2와 HTTP/3에는 이 방식의 업그레이드가 없어서 웹소켓도 다른 방법(확장 CONNECT)으로 연다.

`103 Early Hints`는 최종 응답을 만드는 동안 미리 힌트를 보내는 응답이다. 서버가 HTML을 렌더링하느라 몇백 ms가 걸린다면, 그 사이에 "어차피 이 CSS와 폰트는 필요할 것"이라고 먼저 알려 준다.

```
HTTP/1.1 103 Early Hints
Link: </app.css>; rel=preload; as=style
Link: <https://fonts.example.com>; rel=preconnect

HTTP/1.1 200 OK
Content-Type: text/html
...
```

브라우저는 `200`을 기다리는 동안 CSS를 받기 시작하고 폰트 서버와 연결을 맺어 둔다. 크롬 계열은 HTTP/2 이상의 페이지 이동 요청에서 103을 처리하고, 브라우저마다 지원하는 힌트 종류가 다르다. 103은 뒤에서 볼 HTTP/2 서버 푸시가 하던 일을 더 가볍게 대신한다.

## 성공에도 종류가 있다

2xx는 다 성공이지만 클라이언트가 해야 할 일이 다르다.

`200 OK`는 기본이다. 본문에 결과가 담겨 있다.

`201 Created`는 새 리소스를 만들었다는 뜻이고, 만든 리소스의 주소를 `Location` 헤더에 담는다. `POST /orders`가 주문을 만들었다면 `Location: /orders/42`를 준다. 클라이언트는 새 ID를 본문에서 파싱하지 않아도 어디로 가야 할지 안다. 본문에 만든 리소스를 함께 넣어 주면 한 번 더 조회하지 않아도 된다.

`202 Accepted`는 받기는 했지만 아직 처리하지 않았다는 뜻이다. 동영상 인코딩이나 대량 메일 발송처럼 오래 걸리는 작업에 쓴다. 이 응답은 성공을 약속하지 않는다. 나중에 실패할 수도 있으니 진행 상태를 볼 주소(`Location: /jobs/7`)를 함께 주고, 클라이언트는 그 주소를 확인하러 간다.

`204 No Content`는 성공했고 돌려줄 본문이 없다는 뜻이다. `DELETE`나 내용을 그대로 덮어쓰는 `PUT`에 자주 쓴다. 본문이 없다는 게 약속이라서 204에 본문을 실어 보내면 안 된다. 프론트엔드에서 204에 `res.json()`을 부르면 빈 본문을 파싱하다 예외가 나는 것도 흔한 실수다.

`206 Partial Content`는 `Range` 요청에 대한 답이다. 동영상을 중간부터 재생하거나 끊긴 다운로드를 이어 받을 때 쓴다.

```
GET /video.mp4 HTTP/1.1
Range: bytes=1048576-2097151

HTTP/1.1 206 Partial Content
Content-Range: bytes 1048576-2097151/52428800
Content-Length: 1048576
```

서버가 범위 요청을 지원하면 평소 응답에 `Accept-Ranges: bytes`를 붙여 알린다. 요청한 범위가 파일 크기를 벗어나면 `416 Range Not Satisfiable`이다. 이어 받는 사이에 파일이 바뀌면 앞뒤가 다른 파일이 섞이니, `If-Range`에 ETag를 넣어 "아직 같은 파일이면 그 범위를, 바뀌었으면 전체를 달라"고 요청한다.

## 리다이렉트는 두 가지를 정한다

3xx 중 다른 주소로 보내는 코드는 다섯 개나 된다. 헷갈리는 이유는 두 가지 질문이 섞여 있어서다. 이 이동이 영구적인가, 그리고 다시 요청할 때 메서드와 본문을 그대로 유지하는가.

| | 메서드 유지 안 됨 (POST → GET) | 메서드·본문 유지 |
|---|---|---|
| 영구 | 301 Moved Permanently | 308 Permanent Redirect |
| 임시 | 302 Found | 307 Temporary Redirect |
| 결과를 다른 곳에서 GET으로 | 303 See Other | |

301과 302는 원래 메서드를 바꾸라는 뜻이 아니었다. 그런데 초기 브라우저들이 `POST`에 301·302를 받으면 `GET`으로 바꿔서 다시 요청했고, 이게 굳어져 버렸다. 지금 명세도 이 동작을 허용하고, 브라우저의 `fetch` 표준은 301·302를 받으면 `POST`만 `GET`으로 바꾸고 본문을 버린다. 메서드를 반드시 지켜야 하는 경우를 위해 나중에 307과 308이 따로 생겼다. 그래서 API 서버에서 `POST /v1/orders`를 `/v2/orders`로 옮긴다면 301이 아니라 308을 써야 한다. 301을 쓰면 클라이언트에 따라 본문 없는 `GET /v2/orders`가 도착한다.

영구냐 임시냐는 캐시와 검색 엔진에 영향을 준다. 301과 308은 따로 `Cache-Control`이 없어도 캐시해도 되는 응답이라서, 브라우저가 한 번 받으면 원래 주소로 다시 묻지 않고 바로 새 주소로 간다. 브라우저에 따라 이 기억이 꽤 오래 남는다. 실수로 잘못된 301을 배포하면 서버에서 고쳐도 이미 방문한 사용자의 브라우저는 계속 엉뚱한 곳으로 간다. 확신이 서기 전에는 302나 307로 시험하고, 301을 낼 때도 `Cache-Control: max-age`로 기한을 정해 두는 편이 안전하다. 검색 엔진은 영구 이동을 보고 색인을 새 주소로 옮긴다.

## POST 다음에는 303

## 리다이렉트가 이어지면 왕복이 쌓인다

모바일 네트워크에서 왕복 한 번이 100~300ms라면, 이 체인은 첫 화면을 그만큼씩 늦춘다. 리다이렉트 규칙을 만드는 쪽에서 할 일은 체인을 접는 것이다. 각 규칙이 중간 주소가 아니라 최종 주소를 가리키게 하고, http에서 https로 가는 첫 단계는 HSTS로 브라우저가 아예 건너뛰게 만든다.

리다이렉트를 따라가는 횟수에는 상한이 있다. `fetch` 표준은 20번에서 멈추고 네트워크 에러로 끝낸다. 크롬의 `ERR_TOO_MANY_REDIRECTS`가 이 경우다. 흔한 원인은 프록시와 앱이 서로 다른 생각을 하는 구성이다. CDN이 https를 받아 오리진에 http로 넘기는데, 앱은 http 요청을 받으면 https로 리다이렉트한다. CDN은 그 301을 그대로 사용자에게 돌려주고, 사용자는 다시 https로 와서 같은 일을 반복한다. 앱이 `X-Forwarded-Proto` 헤더를 보고 원래 스킴을 판단하게 하면 풀린다.

보안 쪽에서 볼 것도 있다. `?next=/dashboard`처럼 이동할 주소를 쿼리로 받아 그대로 `Location`에 넣으면, 공격자가 `?next=https://evil.example`을 넣은 링크로 우리 도메인을 신뢰한 사용자를 피싱 사이트로 보낼 수 있다(오픈 리다이렉트). 이동할 주소는 허락 목록이나 같은 사이트 내부 경로로 제한한다. `fetch` 표준은 다른 출처로 리다이렉트될 때 `Authorization` 헤더를 떼어 내서, 리다이렉트 때문에 토큰이 남의 서버로 가는 사고를 막는다.

304는 이름은 3xx지만 다른 주소로 보내는 게 아니라 "가지고 있는 사본을 그대로 써라"는 뜻이다. 조건부 요청과 함께 [HTTP 캐시와 CDN 글](/posts/http-caching-cdn)에서 자세히 다뤘다.

## 4xx는 다시 보내도 같다

4xx는 요청을 고치지 않는 한 몇 번을 보내도 같은 결과가 나온다는 뜻이다. 그래서 고르는 기준은 "클라이언트가 무엇을 고쳐야 하는가"다.

### 400과 422

`400 Bad Request`는 요청 자체를 읽을 수 없을 때다. JSON 문법이 깨졌거나, 필수 헤더가 없거나, 쿼리 형식이 틀렸다. `422 Unprocessable Content`는 형식은 맞는데 내용이 규칙에 맞지 않을 때다. JSON은 멀쩡히 파싱되지만 이메일 칸에 이메일이 아닌 값이 있거나, 종료일이 시작일보다 앞서는 경우다. 422는 원래 WebDAV용이었는데 RFC 9110이 일반 코드로 들여왔다.

현실에서는 둘 다 400으로 쓰는 API도 많다. 어느 쪽이든 괜찮다. 같은 API 안에서 일관되게 쓰고, 어떤 필드가 왜 틀렸는지를 본문에 담는 게 더 중요하다.

### 401과 403

`401 Unauthorized`는 이름과 달리 인가가 아니라 인증 실패다. "누군지 모르겠다"는 뜻이라서 로그인하거나 토큰을 다시 받으면 해결될 수 있다. 명세는 401에 `WWW-Authenticate` 헤더로 어떤 방식으로 인증하라는지 알리게 한다.

```
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token", error_description="expired"
```

`403 Forbidden`은 누군지는 알지만 이 일은 허락되지 않았다는 뜻이다. 다시 로그인해도 결과가 같다. 프론트엔드에서 이 둘을 구분해야 하는 이유가 여기 있다. 401이면 리프레시 토큰으로 액세스 토큰을 다시 받고 재요청하거나 로그인 화면으로 보낸다. 403에서 같은 일을 하면 토큰을 아무리 갱신해도 끝나지 않는 루프에 빠진다.

권한이 없는 사용자에게 리소스가 있다는 사실조차 알리고 싶지 않으면 403 대신 404를 준다. GitHub이 비공개 저장소에 권한 없이 접근하면 404를 주는 게 이 경우다. 403을 주면 "그 이름의 비공개 저장소가 있다"는 정보가 샌다.

### 404와 410

`404 Not Found`는 지금 없다는 뜻이고, 언젠가 생길 수도 있다. `410 Gone`은 있었는데 일부러 영구히 지웠고 다시 생기지 않는다는 뜻이다. 탈퇴한 사용자의 프로필이나 내린 상품 페이지가 410에 맞다. 검색 엔진과 캐시에게 더 분명한 신호가 된다. 둘 다 따로 지시가 없어도 캐시할 수 있는 응답이라서, 404를 너무 오래 캐시하면 새로 만든 페이지가 한동안 안 보이는 일이 생긴다.

### 405, 409, 412, 415

`405 Method Not Allowed`는 경로는 있는데 그 메서드를 받지 않을 때다. 명세상 `Allow` 헤더로 받는 메서드 목록을 알려야 한다. `Allow: GET, HEAD`처럼. 경로 자체가 없으면 404이고, 경로는 있는데 메서드가 틀리면 405다. 라우터가 둘을 구분하지 않고 404만 주면 디버깅이 어렵다.

`409 Conflict`는 지금 리소스 상태와 충돌할 때다. 이미 있는 아이디로 가입하거나, 이미 취소된 주문을 취소하려는 경우다. 사용자가 상황을 확인하고 다시 시도할 수 있다.

`412 Precondition Failed`는 조건부 요청의 조건이 맞지 않을 때다. 두 사람이 같은 글을 동시에 고치는 상황을 막을 때 쓴다(낙관적 잠금). 글을 읽을 때 받은 ETag를 수정 요청의 `If-Match`에 넣어 보내면, 그 사이 다른 사람이 먼저 고쳐 ETag가 바뀐 경우 서버가 412로 거절한다. 덮어쓰기 대신 "다른 사람이 먼저 고쳤다"를 알려 줄 수 있다.

`415 Unsupported Media Type`은 요청 본문의 `Content-Type`을 서버가 처리하지 못할 때다. JSON만 받는 API에 폼 형식을 보내면 415다. 반대로 클라이언트가 `Accept`로 원한 형식을 서버가 만들어 줄 수 없으면 `406 Not Acceptable`이다. 415는 내가 보낸 것, 406은 내가 받고 싶은 것의 문제다.

### 429와 Retry-After

`429 Too Many Requests`는 정해진 속도를 넘겼다는 뜻이다. 보통 게이트웨이의 요청 수 제한에서 나오고, 요청을 처리하기 전에 거절한다. `Retry-After`로 언제 다시 오면 되는지 알려 준다. 값은 초(`Retry-After: 30`)나 날짜(`Retry-After: Fri, 16 Oct 2026 09:00:00 GMT`)다. 클라이언트는 이 값을 지켜야 한다. 무시하고 바로 다시 보내면 제한이 더 길어지는 서버가 많다. 제한을 어떻게 세는지는 [게이트웨이 글](/posts/gateway)에 적었다.

## 502와 504는 앱이 만들지 않는다

5xx를 볼 때는 숫자보다 먼저 "누가 이 응답을 만들었나"를 물어야 한다. 요즘 요청은 앱 서버에 바로 가지 않는다. CDN, 로드 밸런서, 리버스 프록시, 게이트웨이를 거친다. 5xx 중 일부는 앱이 만들고, 일부는 앞단의 프록시가 앱을 대신해서 만든다.

`500 Internal Server Error`는 앱이 처리하다 예상하지 못한 예외를 만났을 때다. 대개 버그다. 같은 입력이면 같은 버그를 또 밟을 가능성이 크다.

`502 Bad Gateway`는 프록시가 뒤쪽 서버에 요청을 넘겼는데 쓸 수 있는 응답을 받지 못했을 때다. 앱 프로세스가 죽어 연결이 거절됐거나, 응답 도중 연결이 끊겼거나, 앱이 HTTP가 아닌 이상한 걸 돌려준 경우다. nginx에서 `connect() failed (111: Connection refused)` 로그와 함께 502가 나오면 뒤쪽 프로세스가 그 포트에서 듣고 있지 않다는 뜻이다. 배포 중에 옛 프로세스를 내리고 새 프로세스가 뜨기 전의 틈에서 자주 보인다.

`503 Service Unavailable`은 지금은 처리할 수 없지만 일시적이라는 뜻이다. 앱이 과부하를 감지해 스스로 거절하거나, 점검 중이라고 알릴 때 쓴다. 프록시가 만들기도 한다. 로드 밸런서가 건강한 대상 서버를 하나도 찾지 못하면 503을 준다. 언제 회복될지 안다면 `Retry-After`를 붙인다.

`504 Gateway Timeout`은 프록시가 뒤쪽 서버의 응답을 기다리다 시간이 다 됐을 때다. nginx의 `proxy_read_timeout` 기본값은 60초다. 504에서 조심할 점은 앱이 요청을 못 받은 게 아니라는 것이다. 앱은 아직 그 요청을 처리하고 있을 수 있고, 처리를 끝냈는데 응답이 늦었을 수도 있다. 프록시가 포기했을 뿐이다.

그래서 장애를 볼 때 이 구분이 시간을 아낀다. 500이 늘면 앱 로그의 스택 트레이스를 본다. 502가 늘면 앱 프로세스가 살아 있는지, 배포나 재시작이 있었는지 본다. 504가 늘면 앱이나 DB가 느려진 곳을 찾는다. 앱 로그에 아무 에러가 없는데 사용자는 5xx를 받는다면 대개 502나 504이고, 범인은 앞단 로그에 있다. 게이트웨이와 프록시의 역할은 [게이트웨이 글](/posts/gateway)에 정리했다.

## access.log에서 5xx를 갈라 보기

"5xx가 늘었다"는 알람이 오면 대시보드 숫자 하나로는 앞에서 본 구분을 할 수 없다. 프록시 로그 한 줄에 "프록시가 내보낸 코드"와 "업스트림이 준 코드"가 같이 있어야 누가 만든 응답인지 바로 보인다. nginx 기본 `combined` 형식에는 업스트림 정보가 없으니 로그 형식을 하나 만들어 둔다.

```nginx
# http 블록에 둔다. $status는 클라이언트가 받은 코드, $upstream_status는 앱이 준 코드
log_format main '$remote_addr "$request" $status $body_bytes_sent '
                'rt=$request_time ups=$upstream_status urt=$upstream_response_time';
access_log /var/log/nginx/access.log main;
```

Ubuntu 24.04의 nginx 1.24 뒤에 Node.js 앱을 두고 다섯 가지 상황을 만들어 봤다. 앱이 예외를 던지는 요청, 앱 프로세스가 떠 있지 않은 포트로 가는 요청 두 번, `proxy_read_timeout 2s`인 경로에 5초 걸리는 요청, 클라이언트가 1초 만에 포기한 요청(`curl --max-time 1`), 그리고 정상 요청 두 번이다.

```text
127.0.0.1 "GET /app/boom HTTP/1.1" 500 27 rt=0.001 ups=500 urt=0.001
127.0.0.1 "GET /down/ HTTP/1.1" 502 166 rt=0.000 ups=502 urt=0.000
127.0.0.1 "GET /down/ HTTP/1.1" 502 166 rt=0.000 ups=502 urt=0.000
127.0.0.1 "GET /timeout/slow HTTP/1.1" 504 176 rt=2.002 ups=504 urt=2.002
127.0.0.1 "GET /app/slow HTTP/1.1" 499 0 rt=1.003 ups=- urt=1.002
127.0.0.1 "GET /app/ HTTP/1.1" 200 13 rt=0.001 ups=200 urt=0.001
127.0.0.1 "GET /app/ HTTP/1.1" 200 13 rt=0.001 ups=200 urt=0.001
```

줄마다 읽는 법이 다르다. 500은 `ups=500`이라 앱이 직접 만든 응답이다. 앱 로그에 스택 트레이스가 있어야 한다. 502와 504도 `ups`에 같은 숫자가 찍히지만 이건 nginx가 업스트림 몫을 대신 채운 값이다. 앱은 응답한 적이 없다. 구분하는 단서는 시간이다. 502는 `urt=0.000`으로 바로 실패했고, 504는 `urt=2.002`로 정확히 타임아웃 값만큼 기다렸다. 504의 시간이 한결같이 같은 숫자에 붙어 있으면 앱이 느린 것이고, 그 숫자는 어느 타임아웃이 먼저 터졌는지 알려 준다.

499는 nginx만 쓰는 코드다. 응답을 보내기 전에 클라이언트가 먼저 끊었다는 뜻이고, 클라이언트는 이 코드를 받지 못한다. `rt=1.003`이 클라이언트가 기다린 시간이다. 499가 몰려 있는 경로는 사용자가 기다리다 새로고침했거나, 앞단(로드 밸런서, 모바일 앱)의 타임아웃이 nginx보다 짧은 곳이다. 앱은 여전히 그 요청을 처리하고 있을 수 있다.

같은 시각의 error.log가 원인을 적어 준다. 502 두 번은 같은 줄이 두 번 남아서 하나만 옮겼다.

```text
2026/10/18 11:06:20 [error] 2176#2176: *676 connect() failed (111: Connection refused) while connecting to upstream, client: 127.0.0.1, server: , request: "GET /down/ HTTP/1.1", upstream: "http://127.0.0.1:18603/", host: "localhost:18610"
2026/10/18 11:06:22 [error] 2176#2176: *680 upstream timed out (110: Connection timed out) while reading response header from upstream, client: 127.0.0.1, server: , request: "GET /timeout/slow HTTP/1.1", upstream: "http://127.0.0.1:18601/slow", host: "localhost:18610"
2026/10/18 11:06:23 [info] 2176#2176: *682 epoll_wait() reported that client prematurely closed connection, so upstream connection is closed too while sending request to upstream, client: 127.0.0.1, server: , request: "GET /app/slow HTTP/1.1", upstream: "http://127.0.0.1:18601/slow", host: "localhost:18610"
```

`Connection refused`면 그 포트에 듣는 프로세스가 없다. `ss -ltnp | grep 18603`으로 확인하고, 배포 순서나 헬스 체크를 본다. `upstream timed out ... while reading response header`면 연결은 됐는데 첫 바이트가 안 왔다. 앱의 느린 쿼리나 외부 API 호출을 찾는다. 499에 해당하는 줄은 `[info]` 레벨이라 기본 설정에서는 안 남는다.

장애 중에는 상태 코드별 개수부터 센다. 위 로그로 돌리면 이렇다.

```bash
# 다섯 번째 칸($status)을 세어 많은 순서로 정렬한다
awk '{print $5}' /var/log/nginx/access.log | sort | uniq -c | sort -rn
```

```text
      2 502
      2 200
      1 504
      1 500
      1 499
```

502가 가장 많으면 앱 로그보다 프로세스 상태와 배포 이력을 먼저 본다. 이 판단을 놓치면 아무 에러도 없는 앱 로그를 한참 뒤지게 된다. 실제 운영 로그에서는 `grep ' 502 '`로 거른 뒤 `ups`와 `urt` 칸을 보고, 같은 업스트림 주소가 반복되면 그 서버 한 대의 문제다. 502와 504를 nginx 쪽에서 더 깊게 보는 방법은 [nginx 리버스 프록시](/posts/nginx-reverse-proxy)에, 어느 계층에서 끊겼는지 좁혀 가는 순서는 [계층별로 장애 좁히기](/posts/network-troubleshooting-by-layer)에 있다.

## 다시 보내도 되는 실패

실패한 요청을 자동으로 다시 보낼지는 두 가지로 정한다. 다시 보내면 결과가 바뀔 가능성이 있는가(상태 코드), 그리고 다시 보내도 부작용이 겹치지 않는가(메서드).

상태 코드 쪽에서 다시 보낼 만한 건 일시적인 실패다. `408 Request Timeout`(서버가 요청을 다 받기 전에 기다리기를 포기함), `429`, `502`, `503`, `504`다. 4xx 대부분은 다시 보내도 결과가 같으니 제외한다. 500도 버그일 가능성이 커서 기본으로는 제외한다. 다만 라이브러리마다 기준이 달라서 500을 재시도하는 것도 있다.

메서드 쪽은 멱등성을 본다. `GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`는 여러 번 보내도 한 번 보낸 것과 결과가 같다. `POST`와 `PATCH`는 그렇지 않다. 502나 504는 서버가 이미 처리했는지 알 수 없는 실패라서, 멱등하지 않은 요청을 다시 보내면 주문이 두 번 생길 수 있다. 반대로 408과 429는 서버가 처리를 시작하기 전에 거절했다는 뜻이라 `POST`도 다시 보낼 수 있다.

이 규칙을 함수로 옮겨 보자. 상태 코드와 메서드를 받아서 자동 재시도를 해도 되는지 돌려준다.

## 에러 본문은 Problem Details로

상태 코드는 분류일 뿐이라 "어떤 필드가 왜 틀렸는지"까지 담지는 못한다. 그건 본문의 몫이다. 문제는 API마다 에러 본문 모양이 제각각이라는 것이다. `{"error": "..."}`, `{"message": "..."}`, `{"code": 1001}`이 섞여 있으면 클라이언트는 API마다 파서를 따로 짜야 한다.

RFC 9457(Problem Details for HTTP APIs, 예전 RFC 7807을 대체)이 이 모양을 표준으로 정했다. `Content-Type`은 `application/problem+json`이다.

```
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/validation",
  "title": "입력값이 올바르지 않다",
  "status": 422,
  "detail": "endDate가 startDate보다 앞선다",
  "instance": "/bookings/7f3a",
  "errors": [{ "field": "endDate", "reason": "before_start" }]
}
```

`type`은 문제의 종류를 가리키는 URI다. 클라이언트는 이 값으로 분기한다. 사람이 읽는 `title`이나 `detail`로 분기하면 문구를 고치는 순간 깨진다. `type`을 생략하면 `about:blank`로 보는데, 이건 "상태 코드 말고는 따로 설명할 게 없다"는 뜻이다. `status`는 응답의 상태 코드를 그대로 옮긴 것이고, 프록시가 상태 코드를 바꿔도 원래 값을 알 수 있게 해 준다. `instance`는 이번 발생을 가리키는 값이라 추적 ID를 넣기 좋다. `errors`처럼 필요한 필드는 확장 멤버로 더 넣을 수 있다. Spring Boot 3의 `ProblemDetail`처럼 프레임워크가 지원하는 경우도 있다.

본문에는 내부 사정을 넣지 않는다. 스택 트레이스, SQL 문, 내부 호스트 이름은 공격자에게 지도가 된다. 자세한 원인은 서버 로그에 남기고, 본문에는 추적 ID만 줘서 둘을 이을 수 있게 한다.

## 실패를 200으로 감싸면

처음 장면으로 돌아가 보면, 실패를 200으로 감싸면 본문을 열어 보지 않는 모든 것이 틀린 판단을 한다.

CDN과 브라우저 캐시는 200을 정상 응답으로 보고 저장할 수 있다. 잠깐 DB가 흔들려서 나간 `{"success": false}`가 캐시 기간 동안 모든 사용자에게 다시 나간다. 모니터링은 상태 코드로 에러율을 세니, 에러가 쏟아져도 대시보드는 초록색이다. 재시도 로직과 서킷 브레이커도 상태 코드를 보니 일시적 장애에 반응하지 않는다. 프론트엔드에서는 `res.ok`, axios의 에러 처리, TanStack Query의 `isError`가 모두 이 실패를 놓친다.

이 방식이 나온 데는 이유가 있다. 예전에는 일부 클라이언트와 프록시가 4xx·5xx의 본문을 버리거나 자기 에러 페이지로 바꿔 버려서, 본문을 지키려고 200으로 감싸곤 했다. GraphQL도 전통적으로 요청이 실행되기만 하면 200에 `errors` 배열을 담는다. 한 요청 안에서 일부 필드만 실패할 수 있는 구조라서 그렇다. 이런 사정이 없는 REST API라면 상태 코드로 결과를 말하고, 자세한 내용은 Problem Details로 본문에 담는다. 그러면 `res.ok`가 믿을 만한 신호가 된다.

정리하면 상태 코드는 본문을 읽지 않는 중간 단계들과의 약속이다. 첫 자리로 누구의 문제인지를 말하고, 세부 코드로 클라이언트가 할 일을 알려 준다. 리다이렉트는 영구성과 메서드 유지를 따로 고르고, 5xx는 누가 만들었는지부터 보고, 재시도는 상태 코드와 메서드의 멱등성을 함께 보고 정한다.

## 면접에서 나올 만한 질문

### 상태 코드의 첫 자리는 어떤 의미가 있나요?

응답의 클래스다. 1xx는 중간 응답, 2xx는 성공, 3xx는 추가 동작 필요, 4xx는 클라이언트 문제, 5xx는 서버 문제다. 클라이언트는 모르는 코드를 받으면 같은 클래스의 x00으로 취급하게 되어 있어서, 새 코드나 비표준 코드도 첫 자리만 맞으면 최소한의 처리는 된다. 단, 모르는 코드의 응답은 캐시하지 않는다.

### 301, 302, 303, 307, 308은 어떻게 다른가요?

영구인지 임시인지, 그리고 메서드와 본문을 유지하는지로 나뉜다. 301·302는 역사적으로 브라우저가 POST를 GET으로 바꿔 버리고, 307·308은 메서드와 본문을 그대로 유지한다. 303은 결과를 다른 주소에서 GET으로 보라는 뜻이라 폼 제출 뒤 PRG 패턴에 쓴다. 301과 308은 기본으로 캐시되어 브라우저가 오래 기억하므로, 잘못 배포하면 되돌리기 어렵다.

### PRG 패턴은 무엇이고 왜 쓰나요?

POST를 처리한 뒤 HTML을 바로 주지 않고 303으로 결과 페이지에 리다이렉트해서 GET으로 받게 하는 패턴이다. 마지막 요청이 GET이 되니 사용자가 새로고침해도 POST가 다시 전송되지 않아 주문이나 결제가 중복되지 않는다. 브라우저 히스토리와 북마크도 결과 페이지 주소로 남는다.

### 401과 403의 차이는요? 403 대신 404를 주는 경우는요?

401은 인증 실패, 즉 누군지 모른다는 뜻이고 WWW-Authenticate 헤더로 인증 방법을 알린다. 403은 누군지는 알지만 권한이 없다는 뜻이라 다시 로그인해도 같다. 클라이언트는 401이면 토큰 갱신이나 로그인으로 가고, 403이면 권한 없음을 보여 준다. 리소스의 존재 자체가 정보가 되는 경우에는 403 대신 404를 줘서 존재 여부를 숨긴다.

### 400과 422는 어떻게 구분하나요?

400은 JSON 문법 오류처럼 요청을 읽을 수 없는 경우, 422는 형식은 맞지만 값이 비즈니스 규칙에 맞지 않는 경우다. 둘 다 400으로 쓰는 API도 많아서 정답이 하나는 아니다. 같은 API 안에서 일관되게 쓰고, 어떤 필드가 왜 틀렸는지를 본문에 표준 형식으로 담는 게 더 중요하다.

### 502, 503, 504는 각각 언제 나오고, 장애 분석에서 어떻게 다르게 보나요?

502는 프록시가 뒤쪽 서버에서 쓸 수 있는 응답을 받지 못했을 때로, 앱 프로세스가 죽었거나 연결이 끊긴 경우다. 503은 과부하나 점검으로 일시적으로 처리할 수 없을 때이고, 로드 밸런서에 건강한 대상이 없을 때도 나온다. 504는 프록시가 응답을 기다리다 타임아웃된 것이라 앱은 아직 처리 중이거나 이미 처리했을 수 있다. 502·504는 앱 로그에 흔적이 없을 수 있으니 앞단 로그와 앱의 생존, 지연을 먼저 본다.

### 어떤 실패를 자동으로 재시도해야 하나요?

408, 429, 502, 503, 504처럼 일시적인 실패만 재시도하고, 나머지 4xx와 대부분의 500은 다시 보내도 같으니 하지 않는다. 여기에 메서드의 멱등성을 함께 본다. 502·504는 서버가 이미 처리했을 수 있어서 POST 같은 비멱등 요청은 멱등성 키가 없으면 재시도하지 않는다. Retry-After가 있으면 따르고, 없으면 지터를 섞은 지수 백오프로 기다린다.

### 에러인데 200을 돌려주면 무엇이 문제인가요?

본문을 보지 않는 모든 계층이 성공으로 오해한다. 캐시가 에러 응답을 저장해 퍼뜨릴 수 있고, 모니터링 에러율에 잡히지 않고, 재시도와 서킷 브레이커가 동작하지 않고, 클라이언트 라이브러리의 에러 처리도 건너뛴다. 상태 코드로 결과를 알리고, 세부 내용은 RFC 9457 Problem Details 형식(application/problem+json)으로 본문에 담는 게 낫다.
