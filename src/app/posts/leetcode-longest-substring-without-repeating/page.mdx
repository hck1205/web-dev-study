로그에서 세션 ID를 뽑다가 "같은 문자가 반복되지 않는 가장 긴 구간"을 찾을 일은 거의 없다. 그런데도 이 문제는 코딩 테스트 단골이다. 가변 길이 슬라이딩 윈도의 기본 동작, 즉 오른쪽을 늘리고 조건이 깨지면 왼쪽을 당기는 흐름이 가장 깔끔하게 드러나는 문제이기 때문이다. 그리고 그 흐름에서 한 줄 차이로 틀리는 함정(`abba`)이 있어서 면접관이 좋아한다.

이 글에서는 여섯 가지 풀이를 느린 것부터 본다. 모든 부분 문자열 검사, 시작점마다 늘리기, 길이 이분 탐색, Set으로 창 줄이기, 마지막 위치로 왼쪽 끝 점프하기, 그리고 같은 생각을 배열 128칸으로 옮긴 버전이다. 문제 원문은 [LeetCode 3](https://leetcode.com/problems/longest-substring-without-repeating-characters/)에 있다. 바로 앞 문제인 [Best Time to Buy and Sell Stock](/posts/leetcode-best-time-to-buy-and-sell-stock)에서는 창의 왼쪽 끝이 "지금까지의 최저가"로 한 번에 점프했다. 이번엔 창 안의 내용 전체를 기억해야 한다. 코드는 모두 Node.js 22, Python 3.13, Java로 실제로 돌렸다.

## 중복 없는 가장 긴 조각

문자열 `s`가 주어진다. `s`의 부분 문자열(substring), 즉 이어진 구간 중에서 같은 문자가 두 번 이상 나오지 않는 것의 최대 길이를 구한다.

부분 문자열과 부분 수열(subsequence)을 헷갈리면 안 된다. 부분 문자열은 붙어 있어야 한다. `"abcbdca"`에서 `"abcd"`는 문자를 건너뛰고 고른 부분 수열이라 답이 될 수 없다.

풀이에 영향을 주는 제약은 이렇다.

- 길이는 0 이상 5만 이하다. 빈 문자열도 들어온다. 모든 부분 문자열(약 12억 5천만 개)을 하나씩 검사하면 시간 안에 못 끝난다.
- 문자는 영문자, 숫자, 기호, 공백이다. 모두 ASCII 안에 있어서 종류가 128개를 넘지 않는다. 이 사실이 공간 복잡도를 O(1)로 만들고, 배열 128칸 풀이를 가능하게 한다.

## 손으로 먼저 따라가 보기

예시는 `"abcbdca"`다. 인덱스로 쓰면 0:a, 1:b, 2:c, 3:b, 4:d, 5:c, 6:a.

왼쪽부터 조각을 늘려 본다.

```text
a        길이 1
ab       길이 2
abc      길이 3
abcb     b가 두 번. 깨졌다
```

3번 칸의 b를 넣자 1번 칸의 b와 겹쳤다. 여기서 어떻게 할지가 문제의 전부다. 겹친 b(1번)를 포함하는 조각은 3번 칸까지 늘리는 순간 무조건 깨진다. 그러니 조각의 시작을 1번 b의 다음 칸, 2번으로 옮긴다. 새 조각은 `cb`다.

```text
  cb       2번부터. 길이 2
  cbd      길이 3
  cbdc     c가 두 번. 2번 c 다음인 3번부터 다시
   bdc     길이 3
   bdca    a는 0번에 있었지만 이미 조각 밖이다. 길이 4
```

답은 4, `"bdca"`다. 마지막 줄이 중요하다. a를 전에 본 적은 있지만 그 a는 조각이 시작하는 3번보다 앞이라 지금 조각과 상관없다. "본 적이 있다"와 "지금 조각 안에 있다"는 다른 질문이다.

## 모든 조각을 다 검사하기

시작 `i`와 끝 `j`(반열린 구간 `[i, j)`)를 모두 고르고, 그 조각에 중복이 있는지 Set으로 검사한다.

```js
function lengthBrute(s) {
  // s[i..j)에 중복 문자가 없나
  const allUnique = (i, j) => {
    const seen = new Set();
    for (let k = i; k < j; k++) {
      if (seen.has(s[k])) return false;
      seen.add(s[k]);
    }
    return true;
  };
  let best = 0;
  for (let i = 0; i < s.length; i++)
    for (let j = i + 1; j <= s.length; j++)
      if (allUnique(i, j)) best = Math.max(best, j - i);
  return best;
}
```

조각이 약 n²/2개이고 하나 검사에 최대 n이 드니 O(n³)이다. 사실 중복이 없는 조각은 길이가 문자 종류 수 m(여기선 128)을 넘을 수 없어서 검사가 m 안에 끝나긴 한다. 그래도 O(n²·m)이다. 2000자 문자열에서 이미 0.8초 가까이 걸렸다. 5만 자는 어림도 없다.

낭비는 뻔하다. `[i, j)`가 중복 없다는 걸 확인해 놓고 `[i, j+1)`을 검사할 때 처음부터 다시 센다.

## 시작점마다 끝까지 늘리기

시작 `i`를 고정하고 Set에 문자를 하나씩 넣으며 오른쪽으로 늘린다. 중복이 나오는 순간 그 시작점에서는 더 늘릴 수 없으니 멈춘다.

```js
function lengthExtend(s) {
  let best = 0;
  for (let i = 0; i < s.length; i++) {
    const seen = new Set();
    let j = i;
    // 중복이 나올 때까지 오른쪽으로 늘린다
    while (j < s.length && !seen.has(s[j])) {
      seen.add(s[j]);
      j++;
    }
    best = Math.max(best, j - i);
  }
  return best;
}
```

시작점마다 많아야 m + 1칸만 늘어나니 시간은 O(n·m), 공간은 O(m)이다. m이 작으면 꽤 빠르다. 5만 자 무작위 ASCII(95종)에서 27ms 정도였다. 하지만 문자 종류가 많은 입력(유니코드)이라면 다시 O(n²)에 가까워진다.

여기서 남은 낭비는 이것이다. `i = 0`에서 `abc`까지 늘렸다가 멈췄다. `i = 1`로 가면 `bc`부터 다시 쌓는데, `bc`가 중복 없다는 건 이미 알고 있다. 앞 조각에서 맨 앞 하나만 빼면 되는 일을 매번 처음부터 한다.

## 길이를 놓고 이분 탐색하기

조금 다른 방향도 있다. "길이 L인 중복 없는 조각이 있나?"라는 질문을 생각해 보자. 길이 L인 조각이 있으면 그 안의 길이 L − 1 조각도 중복이 없다. 그러니 이 질문은 L이 작을 땐 전부 예, 어느 지점부터 전부 아니오다. 참거짓이 한 번만 바뀌는 질문이라 [이분 탐색](/posts/binary-search)으로 경계를 찾을 수 있다.

길이가 고정되면 고정 길이 창으로 O(n)에 검사한다. 창을 한 칸 밀 때 들어오는 문자의 개수를 1 늘리고 나가는 문자의 개수를 1 줄이며, "2번 이상 나온 문자의 종류 수" `dup`을 관리한다. `dup`이 0인 창이 하나라도 있으면 예다.

```js
function lengthBinary(s) {
  // 길이 len인 중복 없는 창이 있나 (고정 길이 창)
  const has = (len) => {
    const count = new Map();
    let dup = 0; // 창 안에서 2번 이상 나온 문자 종류 수
    for (let r = 0; r < s.length; r++) {
      const c = s[r];
      count.set(c, (count.get(c) || 0) + 1);
      if (count.get(c) === 2) dup++;
      if (r >= len) { // 창이 len을 넘었으니 맨 왼쪽을 뺀다
        const out = s[r - len];
        count.set(out, count.get(out) - 1);
        if (count.get(out) === 1) dup--;
      }
      if (r >= len - 1 && dup === 0) return true;
    }
    return false;
  };
  let lo = 0, hi = s.length; // 답은 [lo, hi] 안에 있다
  while (lo < hi) {
    const mid = Math.ceil((lo + hi) / 2); // lo = mid를 쓰니 올림
    if (has(mid)) lo = mid;
    else hi = mid - 1;
  }
  return lo;
}
```

검사 O(n)을 log n번 하니 O(n log n), 공간은 O(m)이다. `lo = mid`로 줄이는 쪽이 있어서 mid를 올림했다. 내림하면 두 칸 남았을 때 무한 루프가 난다. 이분 탐색 글에서 다룬 바로 그 함정이다.

실측은 50ms로 앞 풀이보다 느렸다. 이 문제에서 이분 탐색은 최선이 아니다. 그래도 "답의 단조성을 찾아 이분 탐색한다"는 생각은 다른 문제에서 자주 통하니, 면접에서 O(n²)을 넘는 첫 개선으로 꺼낼 만하다. 다음 풀이는 길이를 따로 정하지 않고 창의 크기를 상황에 맞게 늘이고 줄여서 log를 없앤다.

## 겹치면 왼쪽을 한 칸씩 당긴다

드디어 슬라이딩 윈도다. 창 `[l, r]` 안의 문자를 Set으로 들고 다닌다. 기본 틀은 [슬라이딩 윈도 패턴 글](/posts/sliding-window-pattern)에서 다뤘다.

1. `r`을 0부터 끝까지 한 칸씩 늘린다.
2. `s[r]`이 이미 창 안에 있으면, 없어질 때까지 `s[l]`을 Set에서 빼고 `l`을 한 칸 당긴다.
3. 이제 창에 중복이 없으니 `s[r]`을 넣고 길이 `r - l + 1`로 최댓값을 갱신한다.

```js
function lengthSet(s) {
  const inWindow = new Set(); // 지금 창 [l, r] 안에 있는 문자
  let l = 0, best = 0;
  for (let r = 0; r < s.length; r++) {
    // s[r]과 같은 문자가 창에서 빠질 때까지 왼쪽을 당긴다
    while (inWindow.has(s[r])) {
      inWindow.delete(s[l]);
      l++;
    }
    inWindow.add(s[r]);
    best = Math.max(best, r - l + 1);
  }
  return best;
}
```

반복문 안에 `while`이 있어서 O(n²)처럼 보이지만 아니다. 각 문자는 Set에 한 번 들어가고(`add`) 많아야 한 번 나온다(`delete`). `l`도 `r`도 뒤로 가지 않고 각각 많아야 n번 움직인다. 그래서 전체 연산은 2n 이하, 시간 O(n)이다. 공간은 창 안의 문자 수, 많아야 O(min(n, m))이다.

## 마지막으로 본 자리로 한 번에 점프한다

문자마다 "마지막으로 본 위치"를 해시맵에 적어 두면 왼쪽 끝을 한 번에 옮길 수 있다. `s[r]`을 전에 `last[s[r]]`에서 봤고 그 자리가 지금 창 안(`l` 이상)이면, 새 왼쪽 끝은 `last[s[r]] + 1`이다. 해시맵 자체는 [해시맵 글](/posts/ds-hash-map)에서 다뤘다.

```js
function lengthOfLongestSubstring(s) {
  const last = new Map(); // 문자 -> 마지막으로 본 위치
  let l = 0, best = 0;
  for (let r = 0; r < s.length; r++) {
    const c = s[r];
    // 전에 봤고, 그 자리가 지금 창 안이면 그 다음 칸으로 왼쪽 끝을 옮긴다
    if (last.has(c) && last.get(c) >= l) l = last.get(c) + 1;
    last.set(c, r);
    best = Math.max(best, r - l + 1);
  }
  return best;
}
```

조건 `last.get(c) >= l`이 앞에서 본 "본 적이 있다"와 "지금 창 안에 있다"의 차이다. 해시맵에서 문자를 지우지 않기 때문에, 창 밖으로 밀려난 오래된 위치도 맵에 그대로 남아 있다. 그 위치가 `l`보다 앞이면 무시한다.

시간 O(n)이고 이번엔 반복문 안에 `while`도 없다. 문자마다 맵 조회와 갱신이 한 번씩이다. 공간은 맵에 들어가는 문자 종류 수라 O(min(n, m))이고, ASCII로 제한되면 O(1)이라고 말해도 된다. 5만 자에서 1.4ms였다.

## 건너뛴 시작점에 답이 없는 이유

점프 풀이가 맞는지 불안할 수 있다. 3번 칸의 b에서 `l`을 0에서 2로 옮기면서 시작점 1을 한 번도 제대로 보지 않았다. 혹시 1번에서 시작하는 조각이 답이었다면?

답이 될 수 없다. 1번에서 시작해 3번 이상까지 가는 조각은 1번 b와 3번 b를 둘 다 품으니 중복이 있다. 1번에서 시작해 2번까지만 가는 조각 `"bc"`는 길이 2인데, 이미 0번에서 시작한 `"abc"`(길이 3)를 확인했다. 시작점 0도 마찬가지로 3번 이상으로는 못 늘린다. 그러니 2보다 앞에서 시작하는 조각 중 아직 안 본 더 긴 후보는 없다.

일반적으로 말하면 이렇다. `r`에서 겹침이 생겨 `l`을 `last + 1`로 옮겼다면, 그보다 앞에서 시작하는 조각은 `r`까지 늘릴 수 없다. 그 조각들의 최선은 `r - 1`에서 끝나는 것이고, 그 길이는 앞 단계에서 이미 `best`에 반영됐다. 각 `r`에서 "`r`에서 끝나는 가장 긴 중복 없는 조각"을 정확히 구하니 모든 끝점을 빠짐없이 본다. 슬라이딩 윈도가 O(n²)개의 조각 중 n개만 보고도 답을 놓치지 않는 이유가 이것이다.

실제로 5만 자 무작위 ASCII 문자열에 여섯 풀이를 20번씩 돌린 평균은 이랬다(모든 조각 검사는 2000자에서만 쟀다).

```text
모든 조각 검사 (2000자)  766 ms
시작점마다 늘리기         27.02 ms
길이 이분 탐색            50.40 ms
Set 창                    5.69 ms
마지막 위치 해시맵        1.44 ms
128칸 배열                0.15 ms
```

여섯 풀이가 같은 답을 내는지는 a~e 다섯 글자로 만든 길이 13 이하 무작위 문자열 3000개로 비교했다.

## 해시맵 대신 128칸 배열

문자가 ASCII로 제한된다는 제약을 쓰면 해시맵을 길이 128 배열로 바꿀 수 있다. 문자 코드가 곧 인덱스다. 처음 값을 -1로 두면 "본 적 없음"과 "창 밖"을 같은 비교 하나(`last[code] >= l`)로 처리할 수 있다. -1은 어떤 `l`보다도 작기 때문이다.

```js
function lengthArray(s) {
  const last = new Int32Array(128).fill(-1); // 문자 코드 -> 마지막 위치, -1은 본 적 없음
  let l = 0, best = 0;
  for (let r = 0; r < s.length; r++) {
    const code = s.charCodeAt(r);
    if (last[code] >= l) l = last[code] + 1;
    last[code] = r;
    if (r - l + 1 > best) best = r - l + 1;
  }
  return best;
}
```

복잡도는 해시맵 풀이와 같은 O(n), O(1)이다. 해시 계산이 없고 메모리가 연속이라 상수가 훨씬 작다. 같은 5만 자에서 0.15ms로, 해시맵의 약 10분의 1이었다. 대신 입력 문자 범위를 확신할 수 있을 때만 쓴다. 한글이나 이모지가 들어오면 128칸을 넘는다(아래 엣지 케이스).

## 세 언어로 쓴 최종 코드

Python은 해시맵(dict) 버전이 가장 자연스럽다.

```python
class Solution:
    def lengthOfLongestSubstring(self, s: str) -> int:
        last = {}  # 문자 -> 마지막으로 본 위치
        l = best = 0
        for r, c in enumerate(s):
            if c in last and last[c] >= l:
                l = last[c] + 1  # 창 안의 중복 바로 다음으로 왼쪽 끝을 옮긴다
            last[c] = r
            best = max(best, r - l + 1)
        return best
```

Java는 `int[128]` 배열 버전이 흔하다.

```java
import java.util.Arrays;

class Solution {
    public int lengthOfLongestSubstring(String s) {
        int[] last = new int[128];   // ASCII 문자마다 마지막으로 본 위치
        Arrays.fill(last, -1);
        int l = 0, best = 0;
        for (int r = 0; r < s.length(); r++) {
            char c = s.charAt(r);
            if (last[c] >= l) {
                l = last[c] + 1;     // 창 안에 있는 중복이면 그 다음 칸으로
            }
            last[c] = r;
            best = Math.max(best, r - l + 1);
        }
        return best;
    }
}
```

`"abcbdca"`, `""`, `" "`, `"abba"`, `"tmmzuxt"`를 넣어 세 언어 모두 4, 0, 1, 2, 5가 나오는 걸 확인했다.

언어마다 다른 점이 있다.

- Python의 `str`은 코드 포인트 단위라 `"a😀b😀"`에서 3이 나온다. 이모지를 한 글자로 센다.
- JavaScript의 `s[r]`과 Java의 `charAt`은 UTF-16 코드 단위다. 이모지 하나가 두 칸(서로게이트 쌍)으로 쪼개진다. 같은 `"a😀b😀"`에서 JS 해시맵 풀이는 4를 돌려준다. `a`, 이모지 앞 반쪽, 뒤 반쪽, `b`를 서로 다른 글자로 셌기 때문이다.
- Java의 `int[128]`에 `é`(코드 233)나 한글이 들어오면 `ArrayIndexOutOfBoundsException`이 난다. 범위를 모르면 `HashMap<Character, Integer>`나 `int[65536]`을 쓴다.
- Java는 `char`가 그대로 배열 인덱스로 쓰인다(정수로 자동 변환). JS에서는 `charCodeAt`으로 바꿔야 한다. `last[s[r]]`처럼 문자열을 인덱스로 쓰면 타입 배열에서는 조용히 `undefined`가 된다.

## 여섯 풀이 비교

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 모든 조각 검사 | O(n²·m) | O(m) | 정답 확인용 |
| 시작점마다 늘리기 | O(n·m) | O(m) | 문자 종류가 아주 적고 코드를 짧게 쓰고 싶을 때 |
| 길이 이분 탐색 | O(n log n) | O(m) | 단조성을 보여 주는 중간 단계 |
| Set 창 | O(n) | O(min(n, m)) | 창 패턴 기본형. 다른 조건으로 바꾸기 쉽다 |
| 마지막 위치 해시맵 | O(n) | O(min(n, m)) | 면접 기본 답 |
| 128칸 배열 | O(n) | O(m) = O(1) | 문자 범위가 확실할 때, 가장 빠르다 |

m은 문자 종류 수(ASCII면 128)다. Set 창은 각 문자를 두 번씩(넣고 빼고) 보고, 해시맵 점프는 한 번씩 본다. 둘 다 O(n)이지만 "중복이 몇 개 허용되나"처럼 조건이 바뀌면 Set·카운트 창 쪽이 고치기 쉽다. 점프는 "중복 0개"라는 이 문제의 조건에 딱 맞춘 최적화다.

## 왼쪽 끝이 뒤로 가는 버그

가장 흔한 실수는 창 안인지 확인하지 않고 점프하는 것이다.

```js
function wrong(s) {
  const last = new Map();
  let l = 0, best = 0;
  for (let r = 0; r < s.length; r++) {
    const c = s[r];
    if (last.has(c)) l = last.get(c) + 1; // 창 안인지 확인하지 않았다
    last.set(c, r);
    best = Math.max(best, r - l + 1);
  }
  return best;
}
wrong("abba");    // 3. 정답은 2
wrong("tmmzuxt"); // 6. 정답은 5
```

`"abba"`를 따라가 보자. 2번 칸의 b에서 `l`이 2가 된다. 3번 칸의 a는 0번에서 봤으니 `l = 0 + 1 = 1`로 바뀐다. 왼쪽 끝이 2에서 1로 뒤로 갔다. 창 `[1, 3]`은 `"bba"`인데 b가 두 개다. 길이 3이 답으로 잡힌다.

고치는 방법은 두 가지인데 같은 뜻이다. `last.get(c) >= l`일 때만 옮기거나, `l = Math.max(l, last.get(c) + 1)`로 왼쪽 끝이 절대 줄지 않게 한다. 두 번째 형태를 외워 두면 조건을 잊을 일이 없다.

다른 실수들도 있다.

- 길이를 `r - l`로 계산한다. 창이 `[l, r]` 닫힌 구간이라 `r - l + 1`이다. 한 글자짜리 문자열에서 0이 나오면 이 실수다.
- `best`를 반복문이 끝난 뒤에만 계산한다. 가장 긴 창이 중간에 있으면 놓친다. 매 `r`마다 갱신해야 한다.
- Set 창에서 `while` 대신 `if`를 쓴다. `"abcb"`에서 b가 들어올 때 a 하나만 빼고 멈추면 창에 b가 두 개 남는다. 겹친 문자가 빠질 때까지 반복해야 한다.
- 빈 문자열에서 `s[0]`을 먼저 읽는 초기화. 길이 0이 허용되는 문제라 반복문 밖에서 첫 글자를 꺼내면 안 된다.

## 조건이 바뀌면 창이 어떻게 바뀌나

### 가장 긴 조각 자체를 돌려 달라면

길이가 갱신될 때 시작 위치도 같이 기록한다.

```js
function longestUniqueSubstring(s) {
  const last = new Map();
  let l = 0, bestL = 0, best = 0;
  for (let r = 0; r < s.length; r++) {
    const c = s[r];
    if (last.has(c) && last.get(c) >= l) l = last.get(c) + 1;
    last.set(c, r);
    if (r - l + 1 > best) { best = r - l + 1; bestL = l; } // 시작 위치도 기억
  }
  return s.slice(bestL, bestL + best);
}
longestUniqueSubstring("abcbdca"); // "bdca"
longestUniqueSubstring("tmmzuxt"); // "mzuxt"
```

길이가 같은 조각이 여러 개면 `>`로 비교했으니 가장 먼저 나온 것을 돌려준다. 마지막 것을 원하면 `>=`로 바꾼다.

### 서로 다른 문자가 k종류 이하라면 (LeetCode 340, 159)

"중복이 하나도 없다" 대신 "문자 종류가 k개 이하"가 조건이 된다. 이때는 점프를 못 한다. 어느 문자를 빼야 종류가 줄어드는지 위치 하나로는 모르기 때문이다. 카운트 맵을 두고 종류 수가 k를 넘는 동안 왼쪽을 한 칸씩 당긴다. Set 창을 그대로 일반화한 모양이다.

```js
function lengthAtMostKDistinct(s, k) {
  const count = new Map(); // 창 안 문자 -> 개수
  let l = 0, best = 0;
  for (let r = 0; r < s.length; r++) {
    count.set(s[r], (count.get(s[r]) || 0) + 1);
    while (count.size > k) { // 종류가 너무 많으면 왼쪽을 뺀다
      const c = s[l];
      count.set(c, count.get(c) - 1);
      if (count.get(c) === 0) count.delete(c);
      l++;
    }
    best = Math.max(best, r - l + 1);
  }
  return best;
}
lengthAtMostKDistinct("eceba", 2);   // 3 ("ece")
lengthAtMostKDistinct("abcbdca", 2); // 3 ("bcb")
```

개수가 0이 된 문자를 맵에서 지우는 게 중요하다. 안 지우면 `count.size`가 줄지 않아 무한히 당긴다. 이 "조건이 다시 맞을 때까지 왼쪽을 당기는" 틀은 다음 문제 [Longest Repeating Character Replacement](/posts/leetcode-longest-repeating-character-replacement)와 [Minimum Window Substring](/posts/leetcode-minimum-window-substring)에서도 그대로 쓴다.

### 같은 문자를 두 번까지 허용한다면 (LeetCode 3090)

점프는 다시 쓸 수 없다. 세 번째 c가 들어왔을 때 어디로 옮길지는 "c를 두 번 전에 본 위치"라 마지막 위치 하나로는 모른다. 카운트를 두고, 방금 넣은 문자가 3개가 된 동안만 왼쪽을 뺀다. 넘칠 수 있는 문자는 방금 넣은 것뿐이라 그 문자의 개수만 보면 된다.

```js
function lengthAtMostTwice(s) {
  const count = new Map(); // 창 안 문자 -> 개수
  let l = 0, best = 0;
  for (let r = 0; r < s.length; r++) {
    const c = s[r];
    count.set(c, (count.get(c) || 0) + 1);
    while (count.get(c) > 2) { // 방금 넣은 문자가 3개가 되면 왼쪽을 뺀다
      count.set(s[l], count.get(s[l]) - 1);
      l++;
    }
    best = Math.max(best, r - l + 1);
  }
  return best;
}
lengthAtMostTwice("abcbdca"); // 7 (모든 문자가 두 번 이하)
lengthAtMostTwice("aaaa");    // 2
```

모든 조각을 세는 코드와 무작위 문자열 3000개로 비교해 같은 답이 나왔다. 허용 횟수를 1로 바꾸면 원래 문제의 Set 창과 똑같아진다.

### 문자열이 유니코드라면

JS에서는 `Array.from(s)`나 `for...of`로 코드 포인트 단위로 쪼갠 뒤 같은 알고리즘을 돌린다. `"a😀b😀"`에서 4가 아니라 3이 나온다. 결합 문자(예: 자모를 조합한 한글, 피부색이 붙은 이모지)까지 한 글자로 보려면 `Intl.Segmenter`로 자소 클러스터 단위로 쪼개야 한다. 문자 종류 수 m이 커지니 배열 풀이 대신 해시맵을 쓴다.

### 문자열이 너무 길어 스트림으로 들어온다면

해시맵 풀이는 문자열을 한 번만 앞으로 읽으니 스트림에 그대로 쓴다. 기억하는 건 `l`, `best`, 문자별 마지막 위치뿐이다. 위치는 절대 인덱스 그대로 써도 된다. 메모리는 문자 종류 수에만 비례한다. 반대로 Set 창은 `s[l]`을 다시 읽어야 해서 창 안의 문자를 따로 버퍼에 들고 있어야 한다.

### 문자 대신 숫자 배열이라면

"중복 없는 연속 구간 중 합이 가장 큰 것"이 LeetCode 1695(Maximum Erasure Value)다. 같은 창에 구간 합을 하나 더 들고 다니면 된다. 왼쪽을 당길 때 빠지는 값을 합에서 뺀다.

## 정리하며

중복 없는 가장 긴 구간은 창의 오른쪽을 늘리다가 겹치면 왼쪽을 겹친 문자의 다음 칸으로 옮기는 문제다. Set으로 한 칸씩 당기든, 마지막 위치로 한 번에 점프하든 각 포인터가 앞으로만 가서 O(n)이다. 점프할 때는 그 위치가 지금 창 안인지 확인하거나 `max`로 왼쪽 끝이 줄지 않게 해야 `"abba"`에서 틀리지 않는다. 다음 글 [Longest Repeating Character Replacement](/posts/leetcode-longest-repeating-character-replacement)는 "중복 0개"가 "바꿀 수 있는 글자 k개"로 바뀌면서, 창 안에서 가장 많은 글자 수를 세는 방법을 고민한다.

## 면접에서 나올 만한 질문

### 반복문 안에 while이 있는데 왜 O(n)인가요?

`l`과 `r`이 둘 다 앞으로만 가기 때문이다. `r`은 n번 움직이고, `l`도 전체를 통틀어 n번을 넘게 움직일 수 없다. 각 문자는 창에 한 번 들어오고 많아야 한 번 나가니 전체 연산은 2n 이하다. 반복 횟수를 반복문 구조가 아니라 포인터가 움직인 총거리로 세면 보인다.

### "abba"에서 틀리는 코드는 무엇이 문제인가요?

마지막으로 본 위치가 지금 창 안인지 확인하지 않고 왼쪽 끝을 옮긴 게 문제다. 3번 칸의 a에서 오래된 위치 0을 보고 `l`을 1로 옮기면, 이미 2였던 왼쪽 끝이 뒤로 가서 창에 b가 두 개 들어간다. `last >= l`일 때만 옮기거나 `l = max(l, last + 1)`로 고친다.

### 공간 복잡도는 O(n)인가요, O(1)인가요?

해시맵에 들어가는 건 문자 종류 수라 정확히는 O(min(n, m))이다. 이 문제는 문자가 ASCII로 제한돼 m이 128 이하이니 상수, O(1)이라고 말해도 된다. 유니코드 전체를 받는다면 m이 커지니 O(min(n, m))이라고 범위를 밝히는 게 정확하다.

### Set 창과 마지막 위치 해시맵 중 무엇을 고르나요?

이 문제만 보면 해시맵 점프가 문자를 한 번씩만 보니 조금 더 빠르다. 대신 점프는 "중복 0개"라는 조건에 맞춘 최적화라서, "종류가 k개 이하"나 "같은 문자 2개까지"처럼 조건이 바뀌면 쓸 수 없다. 그럴 땐 카운트를 두고 조건이 맞을 때까지 왼쪽을 당기는 Set·카운트 창으로 돌아간다.

### 해시맵 대신 배열을 쓰면 무엇이 좋고 무엇이 위험한가요?

문자 코드를 인덱스로 쓰니 해시 계산이 없고 메모리가 연속이라 빠르다. 같은 5만 자에서 해시맵보다 열 배쯤 빨랐다. 위험은 입력 범위다. Java의 `int[128]`에 é나 한글이 들어오면 `ArrayIndexOutOfBoundsException`이 나고, JS에서 문자열을 그대로 인덱스로 쓰면 조용히 틀린다.

### 이 문제를 이분 탐색으로도 풀 수 있나요?

풀 수 있다. 길이 L인 중복 없는 조각이 있으면 L − 1도 있으니 "길이 L이 가능한가"가 단조롭다. 길이를 이분 탐색하고 고정 길이 창으로 O(n)에 검사하면 O(n log n)이다. 가변 창이 O(n)이라 최선은 아니지만 답의 단조성을 찾아 경계를 찾는다는 생각은 다른 문제에서 자주 통한다.

### 이모지가 들어간 문자열에서는 어떻게 되나요?

JS와 Java의 문자열 인덱스는 UTF-16 코드 단위라 이모지 하나가 두 칸으로 쪼개진다. `"a😀b😀"`에서 JS 풀이는 4를 돌려주는데 실제 글자로는 3이다. `Array.from(s)`로 코드 포인트 단위로 쪼개고 해시맵 풀이를 쓰면 3이 나온다. Python의 `str`은 처음부터 코드 포인트 단위라 그대로 3이다.
