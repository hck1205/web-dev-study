장바구니 화면에서 0.1달러짜리 쿠폰 두 장을 합쳐 보여 주는데, 화면에 이상한 숫자가 찍혔다.

```js
const coupons = [0.1, 0.2];
const total = coupons.reduce((sum, c) => sum + c, 0);
console.log(total);
console.log(total === 0.3);
```

```text
0.30000000000000004
false
```

버그처럼 보이지만 자바스크립트만의 문제는 아니다. 파이썬, 자바의 `double`, C의 `double`도 같은 답을 낸다. 모두 같은 규격(IEEE 754 배정밀도)으로 숫자를 담기 때문이다. 이 글은 그 규격이 자바스크립트에서 어떤 모양으로 드러나는지 본다. `Number.EPSILON`과 `MAX_SAFE_INTEGER`가 무엇을 뜻하는지, JSON에서 큰 ID가 깨지는 사고, `toFixed`와 `parseInt`의 함정, 그리고 `BigInt`를 섞어 쓸 때의 규칙까지 간다. 아래 예제의 출력은 모두 Node 22에서 돌린 결과이고, 같은 엔진(V8)을 쓰는 크롬도 같다. 숫자 규격 자체가 명세로 정해져 있어 다른 브라우저도 결과가 같다.

## 숫자 하나는 64비트 세 칸으로 나뉜다

IEEE 754가 비트를 어떻게 나누고 반올림하는지는 언어와 상관없는 이야기라 [부동소수점](/posts/floating-point-numbers) 글에서 따로 자세히 다뤘다. 여기서는 자바스크립트에서 이 구조가 드러나는 자리만 짚는다.

자바스크립트의 `number`는 정수와 소수를 구분하지 않는다. `1`도 `0.1`도 모두 64비트 부동소수점 하나에 담긴다. 64비트는 세 칸으로 나뉜다. 부호 1비트, 지수 11비트, 가수 52비트다. 과학 표기법의 `1.6 × 10⁻¹`을 이진수로 바꿔 적는다고 보면 된다. 가수가 앞의 `1.6` 자리이고, 지수가 `10⁻¹` 자리다.

아래는 `0.1`을 실제로 비트로 풀어 본 것이다. 조각을 눌러 보면 각 칸이 무슨 값인지 나온다.

이 구조에서 두 가지가 나온다. 소수는 대부분 근삿값으로 저장된다. 그리고 정수도 가수 칸(53비트)을 넘어서면 정확히 담지 못한다. 앞의 것이 `0.1 + 0.2` 문제이고, 뒤의 것이 큰 ID 문제다. 부동소수점 자체의 원리는 이 정도로만 보고, 아래부터는 자바스크립트 코드에서 이 둘이 어떻게 사고로 이어지는지 본다.

## 0.1은 이진수로 끝나지 않는다

십진수로 `1/3`은 `0.333...`으로 끝나지 않는다. 이진수에서는 분모가 2의 거듭제곱이 아닌 분수가 모두 그렇다. `0.1`은 `1/10`이고, 10에 5가 섞여 있어 이진수로 끝나지 않는다. `0.5`(1/2), `0.25`(1/4), `0.375`(3/8)는 정확히 담긴다.

저장된 실제 값을 보려면 자릿수를 길게 출력하면 된다.

```js
console.log((0.1).toPrecision(21));
console.log((0.1 + 0.2).toPrecision(21));
console.log((0.1).toString(2));
```

```text
0.100000000000000005551
0.300000000000000044409
0.0001100110011001100110011001100110011001100110011001101
```

`0.1`은 원래보다 아주 조금 크게 저장되고, `0.2`도 그렇다. 둘을 더하면 오차가 더해져서 `0.3`에 가장 가까운 값보다 한 칸 위 값이 된다. 평소 `console.log(0.1)`이 `0.1`로 보이는 건 엔진이 "다시 읽었을 때 같은 값이 되는 가장 짧은 십진수"를 골라 보여 주기 때문이다. `0.1 + 0.2`의 결과는 `0.3`이라고 적으면 다른 값이 되니 긴 숫자가 그대로 보인다.

이런 결과는 곳곳에서 나온다.

```js
console.log(1.1 + 2.2);
console.log(0.3 - 0.1);
console.log(0.7 + 0.1);
console.log(1.15 * 100);
```

```text
3.3000000000000003
0.19999999999999998
0.7999999999999999
114.99999999999999
```

마지막 줄이 실무에서 자주 문제가 된다. 1.15달러를 센트로 바꾸려고 100을 곱했는데 115가 아니다. `Math.floor`로 자르면 114센트가 된다. 소수를 정수 단위로 바꿀 때는 `Math.round`를 써야 하는 이유다.

## 같은지 비교할 때는 오차를 허용한다

`0.1 + 0.2 === 0.3`이 `false`이니, 소수끼리는 "충분히 가까운가"로 비교한다. 이때 흔히 쓰는 값이 `Number.EPSILON`이다. 1과, 1 다음으로 표현할 수 있는 수 사이의 간격이다.

```js
console.log(Number.EPSILON);
console.log(Math.abs(0.1 + 0.2 - 0.3) < Number.EPSILON);
console.log(1000.1 + 1000.2);
console.log(Math.abs(1000.1 + 1000.2 - 2000.3) < Number.EPSILON);
```

```text
2.220446049250313e-16
true
2000.3000000000002
false
```

`0.1 + 0.2`에서는 통했는데 `1000.1 + 1000.2`에서는 실패한다. 숫자가 커지면 표현할 수 있는 수 사이의 간격도 커지기 때문이다. 1 근처에서 간격이 `2.2e-16`이면, 1024에서 2048 사이에서는 그 1024배가 된다. 고정된 `EPSILON`과 비교하는 건 1 근처에서만 맞는 방법이다.

값의 크기에 비례해서 허용 오차를 키우면 범위가 넓어진다.

```js
// 두 수 중 큰 쪽의 크기에 맞춰 허용 오차를 늘린다
const nearlyEqual = (a, b) =>
  Math.abs(a - b) <= Number.EPSILON * Math.max(1, Math.abs(a), Math.abs(b));

console.log(nearlyEqual(0.1 + 0.2, 0.3));
console.log(nearlyEqual(1000.1 + 1000.2, 2000.3));
```

```text
true
true
```

이것도 만능은 아니다. 계산을 여러 번 거치면 오차가 쌓여 몇 배로 커진다. 그래서 테스트에서는 Jest·Vitest의 `toBeCloseTo(값, 자릿수)`처럼 "소수 몇째 자리까지 같으면 된다"를 직접 정하는 편이 의도가 분명하다. 돈처럼 한 푼도 틀리면 안 되는 값은 애초에 소수로 계산하지 않는다. 아래 "돈은 정수 단위로 센다"에서 다시 본다.

## 2의 53제곱부터 정수가 건너뛴다

가수가 53비트라는 건, 정수를 빈틈없이 담을 수 있는 범위가 `2^53 - 1`까지라는 뜻이다. 이 값이 `Number.MAX_SAFE_INTEGER`다. 그 위로 가면 표현할 수 있는 정수 사이에 구멍이 생긴다.

```js
console.log(Number.MAX_SAFE_INTEGER);
console.log(2 ** 53 === 2 ** 53 + 1);
console.log(2 ** 53 + 1);
console.log(2 ** 53 + 2);
console.log(Number.isSafeInteger(2 ** 53 - 1), Number.isSafeInteger(2 ** 53));
```

```text
9007199254740991
true
9007199254740992
9007199254740994
true false
```

`2^53`을 넘으면 짝수만 담긴다. 그래서 `2^53 + 1`을 적으면 가까운 짝수로 바뀐다. 더 올라가면 4의 배수, 8의 배수만 남는다. "안전한 정수"는 이 구멍이 생기기 전까지, 즉 어떤 정수와 그 다음 정수를 구별할 수 있는 범위를 말한다.

약 9천조라 평소 계산에선 닿을 일이 없다. 문제는 사람이 세지 않는 숫자, ID다.

직접 돌려 보면 이렇다.

```js
console.log(JSON.parse('{"id": 9007199254740993}').id);
console.log(JSON.parse('{"id": 1234567890123456789}').id);
```

```text
9007199254740992
1234567890123456800
```

아래 줄은 끝 세 자리가 `789`에서 `800`으로 바뀌었다. 이 버그가 무서운 이유는 일부 ID에서만 나기 때문이다. 개발 DB의 ID는 1, 2, 3이라 아무 문제가 없다가, 운영에서 스노우플레이크 ID를 쓰는 순간 터진다.

고치는 방법은 셋이다.

가장 흔한 건 ID를 문자열로 보내는 것이다. 트위터(X) API가 `id`와 함께 `id_str`를 내려 준 것도 이 이유다. ID는 더하거나 곱하지 않으니 문자열이어도 잃는 게 없다. 서버 쪽에서 직렬화 설정 하나로 바꾸는 경우가 많다(예: 자바 Jackson의 `ToStringSerializer`). 프런트엔드 타입도 `id: string`으로 정해 둔다.

두 번째는 파싱할 때 원래 글자를 보고 `BigInt`로 바꾸는 것이다. 최근 명세에 들어간 기능으로, `JSON.parse`의 reviver 세 번째 인자 `context.source`에 원본 글자가 들어온다. Node 22와 크롬에서는 동작하지만 아직 모든 실행 환경이 지원하지는 않으니 대상 브라우저를 확인하고 쓴다.

```js
const data = JSON.parse('{"id": 9007199254740993, "n": 1}', (key, value, context) =>
  key === "id" ? BigInt(context.source) : value,
);
console.log(data);
```

```text
{ id: 9007199254740993n, n: 1 }
```

세 번째는 `json-bigint` 같은 라이브러리로 파싱하는 것이다. 기본 `JSON.parse`보다 느리고, axios나 fetch의 `res.json()`을 그대로 못 쓰고 문자열로 받아 다시 파싱해야 해서 번거롭다. 대부분은 첫 번째로 해결한다.

## 돈은 정수 단위로 센다

장바구니 합계 같은 돈 계산은 소수로 하지 않는다. 원화라면 원, 달러라면 센트처럼 가장 작은 단위의 정수로 바꿔서 계산하고, 보여 줄 때만 소수점을 찍는다. 정수는 `MAX_SAFE_INTEGER`까지 정확하니, 원 단위로 9천조 원까지는 걱정할 일이 없다.

```js
const prices = [19.99, 5.01, 0.1];
console.log(prices.reduce((a, b) => a + b, 0));

// 센트로 바꿔서 더한다. 곱한 뒤 반드시 반올림한다(1.15 * 100 = 114.999...)
const cents = prices.map((p) => Math.round(p * 100));
console.log(cents.reduce((a, b) => a + b, 0));
```

```text
25.1
2510
```

첫 줄은 운 좋게 `25.1`로 보였지만, 더하는 순서와 값에 따라 언제든 꼬리가 붙는다. 더 좋은 건 처음부터 서버가 센트 정수(`2510`)로 주는 것이다. 위처럼 클라이언트에서 `p * 100`을 하는 건, 이미 소수로 받은 값을 어쩔 수 없이 바꿀 때의 차선책이다.

화면에 찍을 때는 `Intl.NumberFormat`을 쓴다. 천 단위 구분과 통화 기호를 지역에 맞게 붙여 준다.

```js
const krw = new Intl.NumberFormat("ko-KR", { style: "currency", currency: "KRW" });
console.log(krw.format(12345));
const usd = new Intl.NumberFormat("en-US", { style: "currency", currency: "USD" });
console.log(usd.format(2510 / 100));
```

```text
₩12,345
$25.10
```

할인율 계산처럼 나눗셈이 끼면 "어디서 반올림하느냐"가 정책 문제가 된다. 품목마다 반올림한 뒤 더할지, 다 더한 뒤 한 번 반올림할지에 따라 1원이 달라진다. 서버와 클라이언트가 다른 방식으로 계산하면 "화면엔 9,900원인데 결제는 9,901원"이 된다. 금액 계산은 서버 한 곳에서 하고, 클라이언트는 받은 값을 보여 주기만 하는 게 안전하다.

## toFixed의 반올림은 보이는 숫자를 따르지 않는다

소수 둘째 자리까지 보여 주려고 `toFixed(2)`를 쓰는 경우가 많다. 그런데 결과가 학교에서 배운 반올림과 다를 때가 있다.

```js
console.log((1.005).toFixed(2));
console.log((1.255).toFixed(2));
console.log((1.45).toFixed(1));
console.log((2.5).toFixed(0), Math.round(2.5), Math.round(-2.5));
```

```text
1.00
1.25
1.4
3 3 -2
```

`1.005`는 `1.01`이 될 것 같은데 `1.00`이다. `toFixed`는 화면에 보이는 `1.005`가 아니라 실제로 저장된 값을 반올림한다. 저장된 값을 길게 찍어 보면 이유가 보인다.

```js
console.log((1.005).toPrecision(20));
console.log(1.005 * 100);
console.log(Math.round(1.005 * 100) / 100);
```

```text
1.0049999999999998934
100.49999999999999
1
```

`1.005`는 실제로 `1.00499...`라서 내림이 맞다. `Math.round(x * 100) / 100`으로 바꿔도 곱셈에서 같은 오차가 나와 `1`이 된다. 인터넷에서 자주 보이는 `Math.round((x + Number.EPSILON) * 100) / 100`은 이 값에서는 `1.01`을 주지만, 앞에서 본 대로 `EPSILON`은 1 근처에서만 의미가 있어 큰 값에서는 효과가 없다.

`Math.round`에도 따로 기억할 점이 있다. `.5`는 항상 양의 무한대 쪽으로 올린다. 그래서 `Math.round(-2.5)`는 `-3`이 아니라 `-2`다. 음수 금액(환불)을 다룰 때 부호를 떼고 반올림한 뒤 다시 붙이는 코드가 나오는 이유다.

결국 해결책은 같다. 반올림이 의미 있는 값(돈, 점수)은 정수 단위로 들고 있다가 마지막에 나누고, `toFixed`는 "대충 이 정도 자릿수로 보여 주기" 용도로만 쓴다. `toFixed`가 숫자가 아니라 문자열을 돌려준다는 것도 자주 놓친다. `(0.1).toFixed(2) + 1`은 `"0.101"`이다.

## 문자열을 숫자로 바꾸는 길은 여러 개다

입력칸의 값, 쿼리 문자열, `localStorage`에서 꺼낸 값은 모두 문자열이다. 이걸 숫자로 바꾸는 방법이 여럿인데 규칙이 다 다르다.

```js
console.log(Number("12px"), +"12px", parseInt("12px"), parseFloat("12.5px"));
console.log(Number(""), +"  42 ", parseInt(""));
console.log(Number("0x1F"), parseInt("0x1F"), parseInt("1e3"), Number("1e3"));
console.log(Number(null), Number(undefined), Number("12,000"));
```

```text
NaN NaN 12 12.5
0 42 NaN
31 31 1 1000
0 NaN NaN
```

`Number()`와 단항 `+`는 같은 변환(명세의 ToNumber)을 쓴다. 문자열 전체가 숫자여야 하고, 앞뒤 공백은 무시한다. 빈 문자열과 공백만 있는 문자열은 `0`이 된다. 입력칸을 비워 둔 걸 `0`으로 받아들이는 버그가 여기서 나온다.

`parseInt`와 `parseFloat`는 앞에서부터 읽을 수 있는 데까지만 읽고 멈춘다. `"12px"`가 `12`가 되는 건 편하지만, `"1e3"`을 `parseInt`로 읽으면 `e`에서 멈춰 `1`이 된다. 빈 문자열은 `NaN`이다.

`parseInt`는 숫자를 넣어도 먼저 문자열로 바꾼다는 점이 가장 큰 함정이다.

```js
console.log(parseInt(0.0000005));
console.log(String(0.0000005));
console.log(["1", "2", "3"].map(parseInt));
```

```text
5
5e-7
[ 1, NaN, NaN ]
```

`0.0000005`는 문자열로 바꾸면 `"5e-7"`이 되고, `parseInt`는 `5`까지 읽고 멈춘다. 숫자의 소수점을 버리고 싶다면 `Math.trunc`를 쓴다. `map(parseInt)`는 `map`이 콜백에 `(값, 인덱스)`를 넘기는데 `parseInt`의 두 번째 인자가 진법이라서 생긴다. `parseInt("2", 1)`은 1진법이라 `NaN`, `parseInt("3", 2)`는 2진법에 3이 없어 `NaN`이다. 진법은 늘 `parseInt(s, 10)`처럼 직접 적는다.

어느 걸 쓸지는 이렇게 정한다. 사용자가 입력한 값은 `Number()`로 바꾸고 `Number.isNaN`과 빈 문자열을 따로 검사한다. CSS 값처럼 단위가 붙은 문자열에서 앞의 숫자만 뽑을 때만 `parseFloat`를 쓴다. 전역 `isNaN("abc")`은 먼저 숫자로 바꿔서 `true`를 내니, 값이 `NaN` 자체인지 보려면 `Number.isNaN`을 쓴다. 비교할 때 값이 몰래 바뀌는 규칙은 [동등 비교와 형 변환 글](/posts/js-equality-coercion)에서 자세히 다룬다.

## BigInt는 다른 규칙으로 계산한다

`2^53`을 넘는 정수를 정확히 계산해야 하면 `BigInt`를 쓴다. 숫자 뒤에 `n`을 붙이거나 `BigInt()`로 만든다. 크기 제한이 사실상 없고(메모리만큼), 정수만 다룬다.

```js
console.log(10n + 20n, typeof 10n);
console.log(2n ** 64n);
console.log(BigInt("9007199254740993"), BigInt(9007199254740993));
```

```text
30n bigint
18446744073709551616n
9007199254740993n 9007199254740992n
```

마지막 줄이 중요하다. `BigInt(9007199254740993)`은 괄호 안의 숫자 리터럴이 이미 `number`로 읽히면서 반올림된 뒤에 바뀐다. 큰 값은 문자열에서 바로 만들어야 정확하다.

`number`와는 섞이지 않는다. 섞으면 조용히 틀리는 대신 바로 에러를 던진다. 에러 종류(`TypeError`, `RangeError`)가 각각 무슨 뜻인지는 [에러 처리 글](/posts/js-error-handling)에서 정리했다.

```js
const tries = [
  () => 1n + 1,
  () => Math.max(1n, 2n),
  () => +1n,
  () => BigInt(1.5),
  () => JSON.stringify({ id: 1n }),
  () => 1n >>> 0n,
];
for (const t of tries) {
  try { t(); } catch (e) { console.log(e.name + ": " + e.message); }
}
```

```text
TypeError: Cannot mix BigInt and other types, use explicit conversions
TypeError: Cannot convert a BigInt value to a number
TypeError: Cannot convert a BigInt value to a number
RangeError: The number 1.5 cannot be converted to a BigInt because it is not an integer
TypeError: Do not know how to serialize a BigInt
TypeError: BigInts have no unsigned right shift, use >> instead
```

하나씩 보면 이렇다. `1n + 1`은 어느 쪽으로 바꿔야 할지 정할 수 없어서 막는다. `number`로 바꾸면 정밀도를 잃고, `BigInt`로 바꾸면 소수를 잃기 때문이다. `Math`의 함수들은 `number`만 받는다. 단항 `+`도 `number`로 바꾸는 연산이라 에러다. 이게 asm.js 시절 코드가 `+x`를 "이건 number다"라는 표시로 써 온 것과 충돌하지 않게 하려는 설계다. `JSON.stringify`는 `BigInt`를 어떻게 적을지 정해 두지 않아서 던진다. `>>>`는 부호 없는 오른쪽 시프트인데, 크기 제한이 없는 `BigInt`에는 "부호 없는 폭"이 없으니 지원하지 않는다.

반대로 비교는 섞어도 된다.

```js
console.log(1n == 1, 1n === 1, 2n > 1, 0n ? "참" : "거짓");
console.log(7n / 2n, -7n / 2n, 7n % 2n);
console.log([10n, 2n, 1n].sort());
```

```text
true false true 거짓
3n -3n 1n
[ 1n, 10n, 2n ]
```

`==`와 크기 비교는 값을 보고, `===`는 타입이 달라 `false`다. `0n`은 falsy다. 나눗셈은 소수점 아래를 0 쪽으로 버린다(`-7n / 2n`이 `-4n`이 아니라 `-3n`). `sort()`는 비교 함수가 없으면 문자열로 바꿔 정렬하니 `BigInt`도 숫자 배열처럼 엉뚱하게 정렬된다. 이때 `(a, b) => a - b`는 결과가 `BigInt`라 `sort`가 받지 못하고 에러가 나므로, `a < b ? -1 : a > b ? 1 : 0`처럼 `number`를 돌려줘야 한다.

JSON으로 보낼 때는 직접 문자열로 바꾼다.

```js
const body = JSON.stringify({ id: 2n ** 60n }, (key, value) =>
  typeof value === "bigint" ? value.toString() : value,
);
console.log(body);
```

```text
{"id":"1152921504606846976"}
```

`BigInt`는 `number`보다 느리다. 값마다 크기가 달라 힙에 따로 저장되고, 엔진의 정수 최적화를 못 받는다. 그래서 모든 정수를 `BigInt`로 바꾸는 건 답이 아니다. 64비트 ID를 다루거나, 암호·해시 계산처럼 큰 정수 연산이 꼭 필요한 곳에만 쓴다. ID는 대개 계산할 일이 없으니 `BigInt`보다 문자열이 더 단순하다. 또 `BigInt`는 정수만 다루니 금액의 소수 계산을 대신해 주지 않는다. 금액은 센트 정수로 바꾼 뒤에야 `BigInt`로 담을 수 있다.

## 비트 연산은 32비트 정수로 접는다

`|`, `&`, `^`, `~`, `<<`, `>>`, `>>>` 같은 비트 연산자는 64비트 부동소수점을 그대로 다루지 않는다. 먼저 32비트 정수로 바꾸고 계산한 뒤, 다시 `number`로 돌려준다. `>>>`만 부호 없는 32비트로, 나머지는 부호 있는 32비트로 바꾼다.

이 성질 때문에 생긴 관용구가 있다.

```js
console.log(3.7 | 0, -3.7 | 0, ~~-3.7, Math.trunc(-3.7));
console.log(-1 >>> 0);
console.log(2 ** 31 | 0, 2 ** 32 | 0, 1 << 31, 1 << 32);
```

```text
3 -3 -3 -3
4294967295
-2147483648 0 -2147483648 1
```

`x | 0`과 `~~x`는 소수점을 버리는 빠른 방법으로 쓰였다. `>>> 0`은 음수를 부호 없는 32비트로 바꾼다. `-1 >>> 0`이 `4294967295`(`2^32 - 1`)인 건 `-1`의 비트가 32개 모두 1이기 때문이다. 해시 함수 코드에서 `hash >>> 0`을 자주 보는 이유다. 곱셈 중에 음수가 되어도 마지막에 양수 범위로 맞춘다.

문제는 32비트 범위(약 ±21억)를 넘는 값에 이 관용구를 쓸 때다. `2^31 | 0`은 음수가 되고, `2^32 | 0`은 `0`이 된다. 시프트 횟수도 32로 나눈 나머지만 써서 `1 << 32`가 `1`이다. 밀리초 타임스탬프에 쓰면 이렇게 된다.

```js
const t = Date.now();
console.log(t, t | 0);
```

```text
1792781536023 1780173591
```

타임스탬프는 이미 32비트를 한참 넘으니 `| 0`을 하면 앞자리가 잘려 나간 엉뚱한 값이 된다. 소수점을 버리려면 `Math.trunc`(0 쪽으로), `Math.floor`(아래로)를 쓴다. 지금 엔진에서는 속도 차이도 거의 없다. 비트 연산자는 플래그를 합치는 것처럼 정말 비트를 다룰 때만 쓴다.

## 다시 장바구니로

`0.30000000000000004`는 계산 실수가 아니라, 64비트에 담을 수 없는 `0.1`을 가장 가까운 값으로 반올림한 흔적이다. 같은 규격 때문에 `2^53`을 넘는 정수도 정확히 담지 못하고, JSON의 큰 ID가 조용히 바뀐다. 그래서 돈은 정수 단위로 세고 화면에 찍을 때만 나누며, ID는 문자열로 주고받고, 정말 큰 정수 계산에만 `BigInt`를 꺼낸다. `toFixed`, `parseInt`, `| 0`은 편해 보이지만 저장된 실제 값과 32비트 변환을 따른다는 걸 알고 써야 한다.

## 면접에서 나올 만한 질문

### 0.1 + 0.2가 0.3이 아닌 이유는 무엇인가요?

자바스크립트의 `number`는 IEEE 754 배정밀도(64비트) 부동소수점이고, `0.1`은 이진수로 끝나지 않는 무한 소수라 52비트 가수에서 잘려 근삿값으로 저장되기 때문이다. `0.1`과 `0.2`가 모두 조금 크게 저장되고, 더하면 오차가 합쳐져 `0.3`에 가장 가까운 값보다 한 칸 위인 `0.30000000000000004`가 된다. 자바스크립트만의 문제가 아니라 같은 규격을 쓰는 모든 언어에서 똑같다.

### 소수를 비교할 때 Number.EPSILON을 쓰면 되나요?

1 근처의 작은 값에서만 맞다. `Number.EPSILON`은 1과 그 다음 표현 가능한 수 사이의 간격이라, 값이 커지면 실제 오차가 이보다 훨씬 커진다. 실제로 `1000.1 + 1000.2`와 `2000.3`의 차이는 `EPSILON`보다 커서 비교가 실패한다. 값의 크기에 비례해 허용 오차를 키우거나, 테스트처럼 "소수 몇째 자리까지"를 직접 정하고, 돈처럼 정확해야 하는 값은 정수로 계산한다.

### MAX_SAFE_INTEGER는 무엇이고 왜 그 값인가요?

`2^53 - 1`, 즉 9007199254740991이다. 가수가 52비트에 숨은 1비트를 더해 53비트 정밀도를 가지니, 그 범위까지는 모든 정수를 빈틈없이 담는다. 그 위로 가면 이웃한 정수를 구별하지 못해 `2^53 + 1`이 `2^53`과 같아진다. `Number.isSafeInteger`로 범위 안인지 확인할 수 있다.

### 서버의 64비트 ID가 프런트엔드에서 바뀌는 문제는 어떻게 막나요?

ID를 JSON 숫자가 아니라 문자열로 내려 받는 게 가장 단순하고 확실하다. `JSON.parse`는 숫자를 모두 `number`로 만들기 때문에 `2^53`을 넘는 값은 에러 없이 반올림된다. ID는 계산하지 않으니 문자열이어도 손해가 없다. 숫자로 받아야 한다면 `JSON.parse` reviver의 `context.source`로 원본 글자를 읽어 `BigInt`로 바꾸거나 전용 파서를 쓰는데, 지원 환경과 성능을 확인해야 한다.

### 금액 계산은 어떻게 하나요? toFixed로 반올림하면 안 되나요?

원이나 센트 같은 최소 단위의 정수로 바꿔 계산하고, 보여 줄 때만 나눠서 `Intl.NumberFormat`으로 찍는다. `toFixed`는 화면에 보이는 값이 아니라 저장된 이진 값을 반올림해서 `(1.005).toFixed(2)`가 `"1.00"`이 된다. 반올림 정책(품목별인지 합계인지, 음수는 어떻게)은 서버 한 곳에서 정하고 클라이언트는 그 결과를 보여 주는 쪽이 금액 불일치를 막는다.

### BigInt와 Number를 섞어 쓰면 어떻게 되나요?

산술 연산은 `TypeError`가 난다. 어느 쪽으로 바꿔도 정밀도나 소수를 잃기 때문에 언어가 암묵 변환을 막아 두었다. `Math` 함수, 단항 `+`, `JSON.stringify`, `>>>`도 `BigInt`를 받지 않는다. 반면 `==`와 크기 비교는 섞어도 값으로 비교한다. 나눗셈은 0 쪽으로 버리고, 직렬화는 replacer로 문자열로 바꿔야 한다. 큰 값은 `BigInt(숫자)`가 아니라 `BigInt("문자열")`로 만들어야 리터럴 단계의 반올림을 피한다.

### x | 0이나 x >>> 0은 왜 쓰고, 언제 위험한가요?

비트 연산자는 피연산자를 32비트 정수로 바꾸기 때문에, `x | 0`은 소수점을 버리는 용도로, `x >>> 0`은 부호 없는 32비트로 맞추는 용도(해시 계산)로 쓰여 왔다. 32비트 범위를 넘는 값에서는 앞자리가 잘려 `2^32 | 0`이 `0`이 되고, 밀리초 타임스탬프는 엉뚱한 값이 된다. 소수점 버리기는 `Math.trunc`나 `Math.floor`로 하고, 비트 연산자는 정말 비트를 다룰 때만 쓴다.

### Number(), 단항 +, parseInt는 어떻게 다른가요?

`Number()`와 단항 `+`는 같은 변환으로, 문자열 전체가 숫자여야 하고 빈 문자열은 `0`이 된다. `parseInt`는 앞에서부터 읽을 수 있는 만큼만 읽고, 숫자를 넣어도 문자열로 먼저 바꿔서 `parseInt(0.0000005)`가 `5`가 된다. 두 번째 인자가 진법이라 `map(parseInt)`가 깨지니 진법은 항상 적는다. 사용자 입력은 `Number()`로 바꾸고 빈 값과 `Number.isNaN`을 따로 검사하는 편이 안전하다.
