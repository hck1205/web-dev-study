사내 위키와 블로그, 문서 사이트를 한 번에 검색하는 기능을 만들어야 한다고 해 보자. 검색 엔진에 넣을 페이지 목록이 있으면 좋겠는데, 그런 목록은 어디에도 없다. 있는 건 첫 화면 주소 몇 개와, 페이지마다 다른 페이지를 가리키는 링크뿐이다. 그러면 할 수 있는 일은 하나다. 첫 화면을 열고, 거기 있는 링크를 모두 적고, 적은 주소를 하나씩 열어 또 링크를 적는다. 이걸 자동으로 하는 프로그램이 웹 크롤러다. 스파이더, 봇이라고도 부른다.

면접에서 "웹 크롤러를 설계하라"는 질문이 자주 나오는 이유는 단순해 보여서다. 반복문 하나면 돌아간다. 그런데 페이지가 수억 개가 되는 순간 느린 서버, 끝없이 이어지는 링크, 같은 내용의 다른 주소, 죽은 서버가 한꺼번에 튀어나온다. 이 글은 반복문 하나짜리 크롤러에서 시작해 무엇이 깨지는지 하나씩 본다.

## 무엇을 얼마나 모을지부터 정한다

크롤러는 쓰임새에 따라 모양이 꽤 달라진다. 검색 엔진에 넣을 페이지를 모으는 크롤러, 사라지기 전에 웹 페이지를 보관하는 아카이브 크롤러, 저작권 침해나 가격 변동을 감시하는 크롤러가 있다. 이 글은 검색용 크롤러를 기준으로 하고 조건을 이렇게 정한다.

- 한 달에 웹 페이지 3억 개를 내려받는다.
- HTML만 모은다. 이미지나 PDF는 나중에 붙일 수 있게만 해 둔다.
- 새로 생긴 페이지와 바뀐 페이지를 다시 찾아간다.
- 내용이 똑같은 페이지는 한 번만 저장한다.
- 내려받은 HTML은 3년 동안 보관한다.

숫자 말고도 지켜야 할 성질이 있다. 규모가 커지면 서버를 늘려 버틸 수 있어야 하고(확장성), 깨진 HTML이나 응답하지 않는 서버를 만나도 멈추지 않아야 한다(견고성). 남의 서버에 짧은 시간에 요청을 몰아 보내지 않아야 하고(예의), 나중에 PNG나 PDF를 모으는 기능을 끼워 넣기 쉬워야 한다(확장 가능성). 예의는 다음 글에서 따로 다룬다.

웹을 그래프로 보면 설계가 쉬워진다. 페이지 하나가 점이고, 링크 하나가 한쪽 방향 화살표다. 크롤러는 몇 개의 출발점에서 화살표를 따라가며 닿는 점을 모두 찾는 그래프 탐색 프로그램이다.

## 서버 한 대, 반복문 하나로 만든 크롤러

가장 작은 크롤러를 만들어 실제로 돌려 봤다. 인터넷이 아니라 내 컴퓨터의 `127.0.0.1`에 Node로 띄운 작은 정적 사이트(페이지 9개)를 대상으로 한다. 남의 사이트에 연습용 크롤러를 돌리면 안 되기 때문이다. 핵심은 이 몇 줄이다.

```js
const frontier = [{ url: origin + "/", depth: 0 }]; // 시드 URL: 출발점
const urlSeen = new Set([origin + "/"]);           // 한 번이라도 줄 세운 URL
const contentSeen = new Map();                       // 본문 해시 → 처음 본 URL

while (frontier.length > 0) {
  const { url, depth } = frontier.shift();           // 앞에서 꺼낸다 (FIFO)
  const res = await fetch(url, { signal: AbortSignal.timeout(2000) });
  if (res.status !== 200) continue;                   // 404 같은 건 버린다
  const html = await res.text();
  const hash = sha256(html).slice(0, 8);
  if (contentSeen.has(hash)) continue;                // 내용이 같은 페이지는 한 번만
  contentSeen.set(hash, url);

  for (const [, href] of html.matchAll(/href="([^"]+)"/g)) {
    const next = new URL(href, url);                  // 상대 주소를 절대 주소로
    next.hash = "";                                   // #조각은 같은 문서다
    if (!["http:", "https:"].includes(next.protocol)) continue; // mailto: 등
    if (next.origin !== origin) continue;             // 이번엔 이 사이트만
    if (urlSeen.has(next.href)) continue;             // 이미 줄 세운 URL
    urlSeen.add(next.href);
    frontier.push({ url: next.href, depth: depth + 1 });
  }
}
```

용어 세 개만 먼저 정리한다. 시드 URL은 크롤링을 시작하는 주소다. 프런티어는 "앞으로 내려받을 URL"을 줄 세워 둔 곳이고, 여기서는 배열 하나다. URL 방문 기록(`urlSeen`)은 프런티어에 한 번이라도 넣은 URL의 목록이다. 실행 결과는 이렇다.

```text
 1 d0 /                      200 #dd7974bf +[/about, /blog, /docs] 프런티어 3
 2 d1 /about                 200 #cf0efc62 +[/team] 프런티어 3
 3 d1 /blog                  200 #2558e990 +[/blog/1, /blog/2] 프런티어 4
 4 d1 /docs                  200 #877d6ecd +[/docs/intro, /docs/intro?ref=nav] 프런티어 5
 5 d2 /team                  200 #04b6cd80 +[] 프런티어 4
 6 d2 /blog/1                200 #6c2ad88f +[/tags/js] 프런티어 4
 7 d2 /blog/2                200 #cc3a99ea +[/old-link] 프런티어 4
 8 d2 /docs/intro            200 #537c969c +[] 프런티어 3
 9 d2 /docs/intro?ref=nav    200 #537c969c 내용 중복(/docs/intro)
10 d3 /tags/js               200 #3dc93701 +[] 프런티어 1
11 d3 /old-link              404 버림
--- 내려받기 11번, 본 URL 11개, 새 내용 9개
--- 걸러 낸 링크: https://external.example/ (다른 호스트), mailto:hi@example.com (프로토콜)
```

`d0`, `d1`은 시드에서 링크를 몇 번 건넜는지(깊이)다. 몇 군데를 짚어 보자. 5번 줄에서 `/team`은 `/`로 가는 링크를 갖고 있지만 `+[]`로 아무것도 추가하지 않았다. `urlSeen`이 막았다. 9번 줄은 주소가 다른데 본문 해시가 8번 줄과 같다. 서버가 `?ref=nav`를 무시하고 같은 페이지를 줬기 때문이다. URL만 보고는 알 수 없고 내용을 봐야 알 수 있는 중복이다. `/blog/1#comments` 링크는 `#` 뒤를 지웠더니 `/blog/1`과 같아져서 따로 내려받지 않았다.

## 넓게 먼저 도는 이유

프런티어에서 앞에서 꺼내면 너비 우선 탐색(BFS)이 되고, 뒤에서 꺼내면 깊이 우선 탐색(DFS)이 된다. `shift()`를 `pop()`으로 한 글자만 바꿔 같은 사이트를 돌려 봤다.

```text
 1 d0 /                      200 #dd7974bf +[/about, /blog, /docs] 프런티어 3
 2 d1 /docs                  200 #877d6ecd +[/docs/intro, /docs/intro?ref=nav] 프런티어 4
 3 d2 /docs/intro?ref=nav    200 #537c969c +[] 프런티어 3
 4 d2 /docs/intro            200 #537c969c 내용 중복(/docs/intro?ref=nav)
 5 d1 /blog                  200 #2558e990 +[/blog/1, /blog/2] 프런티어 3
 6 d2 /blog/2                200 #cc3a99ea +[/old-link] 프런티어 3
 7 d3 /old-link              404 버림
 8 d2 /blog/1                200 #6c2ad88f +[/tags/js] 프런티어 2
 9 d3 /tags/js               200 #3dc93701 +[] 프런티어 1
10 d1 /about                 200 #cf0efc62 +[/team] 프런티어 1
11 d2 /team                  200 #04b6cd80 +[] 프런티어 0
```

페이지 9개짜리 사이트에서는 결과가 같다. 내려받은 횟수도, 얻은 내용도 같다. 차이는 순서다. DFS는 `/docs` 쪽으로 끝까지 파고든 뒤에야 `/about`으로 돌아온다. 그리고 4번 줄을 보면 중복으로 판정된 쪽이 바뀌었다. 먼저 본 주소가 "원본"이 되니, 어떤 주소를 대표로 남길지가 순서에 따라 달라진다.

실제 웹에서는 순서 차이가 결과 차이가 된다. 웹 그래프는 깊이에 끝이 없다. 날짜마다 다음 날 링크가 붙는 달력, 페이지 번호가 끝없이 늘어나는 목록 같은 곳에 DFS가 들어가면 거기서 나오지 못한다. 시드 근처의 페이지가 대체로 더 중요하다는 점도 있다. 사이트 첫 화면에서 한두 번 클릭해 닿는 페이지가 열 번 클릭해야 닿는 페이지보다 많이 읽힌다. 그래서 크롤러는 BFS를 기본으로 쓴다.

그런데 순수한 BFS에도 문제가 두 가지 있다. 첫째, 한 페이지의 링크는 대개 같은 사이트를 가리킨다. 앞의 결과에서도 내려받은 11개가 모두 같은 호스트였다. 그대로 여러 스레드로 돌리면 한 사이트에 요청이 몰린다. 둘째, BFS는 모든 URL을 똑같이 대한다. 뉴스 첫 화면과 3년 전 댓글 페이지가 같은 줄에 선다. 이 두 가지를 푸는 것이 다음 글의 주제인 예의(politeness)와 우선순위다.

## 부품으로 나눠 보기

반복문 하나에 들어 있던 일을 역할별로 떼어 내면 크롤러의 표준 구성이 된다. 하나씩 이름을 붙이면 이렇다.

- 시드 URL: 출발점. 많이 연결된 사이트 첫 화면이나 사이트맵(`sitemap.xml`), 지역이나 주제별 대표 사이트로 고른다. 시드가 한쪽에 몰려 있으면 닿지 않는 영역이 생긴다.
- URL 프런티어: 내려받을 URL을 쌓아 두는 곳. 처음에는 FIFO 큐였지만 다음 글에서 우선순위와 호스트별 줄로 바뀐다.
- HTML 다운로더: 프런티어에서 URL을 받아 페이지를 내려받는다.
- DNS 리졸버: 호스트 이름을 IP 주소로 바꾼다. 결과를 캐시해 둔다.
- 콘텐츠 파서: HTML을 읽고, 깨진 페이지는 버린다.
- 콘텐츠 중복 확인: 본문 해시를 보고 이미 저장한 내용인지 본다.
- 콘텐츠 저장소: HTML을 저장한다.
- URL 추출기: 페이지에서 링크를 뽑아 절대 주소로 바꾼다.
- URL 필터: 막힌 도메인, 원치 않는 확장자, 너무 긴 주소, `robots.txt`가 금지한 경로를 거른다.
- URL 중복 확인과 URL 저장소: 이미 프런티어에 넣었거나 내려받은 URL인지 확인한다.

## 다운로더는 느리고 이상한 서버를 만난다

내 사이트만 돌 때는 모든 서버가 착하다. 실제 웹에는 응답을 시작만 하고 끝내지 않는 서버, 끝없이 데이터를 흘려보내는 서버, HTML이라더니 이미지를 주는 서버가 있다. 다운로더가 이런 서버 하나에 붙잡히면 그 스레드는 아무 일도 못 한다. 로컬 서버에 이런 페이지들을 만들어 놓고, 시간 제한 1초와 크기 제한 1MB를 건 다운로더로 내려받아 봤다.

```js
const ctrl = new AbortController();
const timer = setTimeout(() => ctrl.abort(new Error("timeout")), 1000); // 전체 1초
const res = await fetch(url, { signal: ctrl.signal });
if (!res.ok) return `버림: 상태 ${res.status}`;
if (!res.headers.get("content-type")?.startsWith("text/html")) return "건너뜀";
const reader = res.body.getReader();          // 한 번에 다 받지 않고 조금씩 읽는다
let bytes = 0;
for (;;) {
  const { done, value } = await reader.read();
  if (done) break;
  bytes += value.length;
  if (bytes > 1_000_000) { ctrl.abort(); return "잘라냄"; } // 1MB 넘으면 끊는다
}
```

```text
(126ms) /ok        완료: 102바이트
(1013ms) /slow      실패: timeout
(78ms) /huge      잘라냄: 1,033,106바이트에서 멈춤
(8ms) /logo.png  건너뜀: content-type image/png
(2ms) /nope      버림: 상태 404
```

`/slow`는 머리만 보내고 본문을 10초 뒤에 보내도록 만들었는데, 1초에서 끊겼다. 연결 시간 제한만 걸어 두면 이 경우를 못 막는다. 연결은 금방 됐기 때문이다. 그래서 "응답 전체를 몇 초 안에"라는 제한이 필요하다. 계층마다 다른 시간 제한은 [타임아웃](/posts/timeouts)에서 자세히 다뤘다. `/huge`는 끝없이 쓰는 페이지인데 1MB를 조금 넘긴 곳에서 멈췄다. `res.text()`로 한 번에 받았다면 메모리가 찰 때까지 받았을 것이다. `/logo.png`는 머리만 보고 본문은 받지 않았다.

DNS도 다운로더를 느리게 만든다. 호스트 이름을 IP로 바꾸는 데 수십 밀리초에서 수백 밀리초가 걸리고, 크롤러는 같은 호스트를 수없이 다시 묻는다. 게다가 Node 22의 기본 `fetch`는 이름 풀이를 `dns.lookup`(운영체제의 `getaddrinfo`)에 맡기는데, 이 호출은 libuv 스레드 풀에서 돈다. 스레드 풀은 기본 4개라서 DNS 응답이 느리면 동시에 수백 개를 내려받으려 해도 이름 풀이에서 줄이 선다. 그래서 크롤러는 자체 DNS 캐시를 두고, 캐시가 없을 때는 비동기 리졸버(`dns.resolve4`처럼 스레드 풀을 쓰지 않는 쪽)로 미리 풀어 둔다. DNS의 동작 자체는 [DNS](/posts/dns) 글에 있다.

서버를 어디에 둘지도 속도에 영향을 준다. 한국 서버에서 브라질 사이트를 내려받으면 왕복만 300ms쯤 걸린다. 크롤 서버를 여러 지역에 두고 가까운 지역의 사이트를 맡기면 같은 서버 수로 더 많이 내려받는다.

## 파서와 저장소

내려받은 HTML은 파서가 읽는다. 위 예제는 정규식으로 `href`를 뽑았지만 실제로는 HTML 파서를 쓴다. 따옴표 없는 속성, 대소문자가 섞인 태그, `<base href>`처럼 상대 주소의 기준을 바꾸는 태그를 정규식으로 다 처리하기 어렵다. 파서는 별도 서버나 프로세스로 떼어 두는 편이 낫다. 일부러 이상하게 만든 HTML 하나가 파서를 멈추게 하거나 메모리를 다 먹을 수 있는데, 그게 다운로더 안에서 터지면 다운로드까지 멈춘다.

자바스크립트가 그리는 페이지도 있다. [CSR](/posts/rendering-csr-spa)로 만든 사이트는 처음 받은 HTML이 거의 비어 있고, 본문과 링크는 스크립트가 실행된 뒤에 생긴다. 이런 페이지를 읽으려면 헤드리스 브라우저로 스크립트를 실행해야 하는데, 페이지 하나에 수백 MB 메모리와 수 초가 든다. 그래서 모든 페이지를 브라우저로 열지 않는다. 먼저 HTML만 받아 보고, 본문이 비어 있는 페이지만 따로 "렌더링 줄"에 넣어 적은 수의 브라우저 서버가 천천히 처리하게 한다.

저장소는 두 가지로 나눈다. 원본 HTML은 압축해서 객체 저장소(S3 같은 곳)에 URL 해시를 키로 넣는다. 크고, 한 번 쓰고 가끔 읽기 때문이다. URL, 마지막으로 내려받은 시각, 응답 코드, 본문 해시 같은 메타데이터는 DB에 넣는다. 이건 작고 자주 읽고 고친다. 다음에 언제 다시 올지 정하는 데 이 메타데이터를 쓴다.

## 몇 대가 필요한지 계산해 보기

처음에 정한 숫자로 크기를 어림해 보자. 한 달에 3억 페이지면 초당 `3억 ÷ (30 × 24 × 3600)`으로 약 116개다. 낮과 밤의 차이를 생각해 최대치는 평균의 두 배로 잡는다. 페이지 하나를 평균 80KB로 보면 저장 공간과 대역폭도 나온다. 아래 함수의 빈 곳을 채워 직접 계산해 보자. 숫자 단위는 KB = 1,000바이트, TB = 10의 9제곱 KB로 맞췄다.

## 서버 여러 대로 나누는 기준은 호스트다

크롤 서버를 여러 대로 늘리면 URL을 어느 서버가 맡을지 정해야 한다. URL마다 무작위로 나누면 같은 사이트의 페이지가 여러 서버에 흩어진다. 그러면 서버 A와 B가 각자 "이 사이트에는 1초에 한 번만" 규칙을 지켜도, 사이트 입장에서는 1초에 두 번 맞는다. 그래서 호스트 이름을 해시해서 서버를 고른다. 같은 호스트의 URL은 늘 같은 서버로 가고, 그 서버 안에서만 속도를 지키면 된다. 서버를 더하거나 뺄 때 옮겨야 할 호스트를 줄이려면 [일관된 해싱](/posts/consistent-hashing)을 쓴다.

## 서버가 죽어도 처음부터 다시 하지 않게

크롤러는 몇 주, 몇 달씩 돈다. 그동안 서버는 반드시 죽는다. 프런티어가 메모리에만 있으면 서버 하나가 죽을 때 그 서버가 맡은 수백만 개 URL이 사라진다. 그래서 프런티어는 디스크에 둔다. 다만 URL마다 디스크를 읽고 쓰면 느리니, 앞부분 조금과 뒷부분 조금만 메모리 버퍼에 두고 가운데는 디스크 파일로 둔다. 꺼낼 때는 앞쪽 버퍼에서, 넣을 때는 뒤쪽 버퍼에 쌓았다가 한 번에 디스크로 내린다.

내려받는 중이던 URL도 문제다. 꺼낸 순간 프런티어에서 지우면, 내려받다 죽었을 때 그 URL은 영영 사라진다. [메시지 큐](/posts/message-queue-basics)에서 쓰는 방법을 그대로 쓴다. 꺼낼 때 지우지 않고 "이 URL은 지금 누가 일하는 중"이라고 표시만 하고 기한을 건다. 끝나면 지우고, 기한이 지나도 소식이 없으면 다시 줄에 세운다.

마지막에서 두 번째 단계가 중요하다. 기한 방식은 "적어도 한 번"은 처리하지만 두 번 처리할 수도 있다. 저장을 URL 해시를 키로 한 덮어쓰기로 만들어 두면 두 번 처리돼도 결과가 같다. 이런 성질을 멱등하다고 한다.

그 밖에 견고성을 위해 챙길 것은 이렇다. 다운로더와 파서의 예외는 그 페이지 하나만 실패로 기록하고 넘어간다. 같은 호스트에서 연속으로 실패하면 그 호스트를 잠깐 쉬게 한다. 서버 상태는 프런티어, URL 기록, 메타데이터 DB에 두고 크롤 서버 자체는 상태를 들고 있지 않게 만들어서, 죽은 서버 자리에 새 서버를 띄우기만 하면 일을 이어받게 한다.

## 새 형식을 끼워 넣을 자리

나중에 이미지도 모으고 싶고, 저작권 침해 페이지를 찾는 기능도 붙이고 싶어질 수 있다. 처음부터 다 만들 필요는 없고, 끼울 자리만 만들어 둔다. 파서 뒤에 "내용 처리기" 목록을 두고, 내려받은 응답의 형식에 따라 맞는 처리기에 넘긴다. HTML 처리기는 링크를 뽑고, PNG 처리기는 이미지를 저장하고, 감시 처리기는 특정 문구를 찾는다. 새 형식이 생기면 처리기 하나를 더하면 된다. 다운로더와 프런티어는 그대로다.

## 다음에 읽을 글

크롤러는 시드에서 출발해 링크를 따라가는 BFS다. 그 반복문을 프런티어, 다운로더, 파서, 중복 확인, 필터로 떼어 내고, 호스트 단위로 서버에 나누고, 꺼낸 URL에 기한을 걸어 죽어도 이어받게 만들면 큰 크롤러의 뼈대가 된다. 이 글에서 미룬 것들, 그러니까 한 사이트에 몰리지 않게 하는 호스트별 줄, 중요한 페이지를 먼저 내려받는 우선순위, `robots.txt`, 수억 개 URL의 중복 확인을 메모리 몇백 MB로 하는 법, 끝없는 링크 함정은 [㉑ 웹 크롤러 ②: 예의, 우선순위, 중복 거르기](/posts/sd-web-crawler-politeness-dedup)에서 이어진다.

## 면접에서 나올 만한 질문

### 웹 크롤러의 기본 구성 요소와 흐름을 설명해 주세요.

시드 URL을 프런티어에 넣고, 다운로더가 꺼내서 DNS를 풀고 내려받는다. 파서가 HTML을 읽고, 본문 해시로 이미 본 내용인지 확인한 뒤 새 내용이면 저장한다. URL 추출기가 링크를 뽑고, 필터가 원치 않는 URL을 거르고, URL 중복 확인을 통과한 것만 다시 프런티어에 넣는다. 프런티어가 빌 때까지 이걸 반복한다.

### 그래프 탐색으로 DFS 대신 BFS를 쓰는 이유는요?

웹은 깊이에 끝이 없어서 DFS는 달력이나 끝없는 목록 같은 곳에 빠지면 나오지 못한다. 시드 가까이 있는 페이지가 대체로 더 중요하다는 점도 BFS에 유리하다. 다만 순수한 BFS는 같은 사이트 링크가 줄줄이 붙어 한 사이트에 요청이 몰리고, 페이지의 중요도도 따지지 않는다. 그래서 실제로는 우선순위 줄과 호스트별 줄로 바꾼 BFS를 쓴다.

### URL 중복 확인과 콘텐츠 중복 확인을 둘 다 두는 이유는요?

URL 확인은 내려받기 전에 같은 주소를 거르는 것이라 싸고, 대부분의 중복을 여기서 막는다. 하지만 `?ref=nav`처럼 주소는 다른데 같은 내용을 주는 페이지는 내려받아 본문 해시를 비교해야만 알 수 있다. 두 확인이 거르는 대상이 다르니 둘 다 필요하다.

### 한 달에 3억 페이지면 규모가 어느 정도인가요?

초당 평균 약 116페이지, 최대 두 배로 232페이지다. 평균 80KB면 대역폭은 74Mbps 정도라 네트워크보다는 지연이 문제다. 페이지당 1초가 걸리면 동시에 수백 개의 요청을 서로 다른 사이트에 열어 둬야 한다. 3년 보관이면 압축 전 864TB라 객체 저장소에 둔다.

### 크롤 서버를 여러 대로 늘릴 때 URL을 어떻게 나누나요?

호스트 이름을 해시해서 담당 서버를 정한다. 같은 호스트의 URL이 한 서버로 모여야 사이트별 요청 속도를 한 곳에서 지킬 수 있기 때문이다. 다른 호스트의 링크를 찾으면 그 호스트의 담당 서버 프런티어로 묶어서 보낸다. 서버를 더하거나 뺄 때 옮길 호스트를 줄이려면 일관된 해싱을 쓴다.

### 크롤 서버 하나가 내려받는 도중에 죽으면 어떻게 되나요?

프런티어를 디스크에 두고, 꺼낸 URL은 지우지 않고 기한을 건 임대 상태로 둔다. 기한이 지나도 완료 신호가 없으면 다시 꺼낼 수 있게 되돌려 다른 서버가 처리한다. 이 방식은 같은 URL을 두 번 처리할 수 있으니 저장을 URL 해시 키 덮어쓰기처럼 멱등하게 만든다.

### 트래픽을 10배로 늘리면 어디가 먼저 막히나요?

서버를 늘리면 다운로드 자체는 따라온다. 먼저 걸리는 곳은 DNS다. 같은 호스트를 반복해 묻고, Node 같은 런타임에서는 기본 이름 풀이가 작은 스레드 풀에서 돌아서 줄이 선다. 자체 DNS 캐시와 비동기 리졸버를 둔다. 그다음은 URL 중복 확인으로, 수십억 개 URL을 그대로 들고 있으면 메모리가 모자라서 해시만 저장하거나 블룸 필터로 바꾼다.

### 자바스크립트로 그리는 페이지는 어떻게 크롤링하나요?

헤드리스 브라우저로 스크립트를 실행해야 본문과 링크가 생긴다. 하지만 페이지마다 메모리와 시간이 수십 배 들어서 모든 페이지에 쓰지 않는다. 먼저 HTML만 받아 보고 본문이 비어 있는 페이지만 렌더링 전용 줄에 넣어, 소수의 브라우저 서버가 따로 처리하게 한다.
