[Group Anagrams](https://leetcode.com/problems/group-anagrams/)는 LeetCode 49번이다. [Valid Anagram](/posts/leetcode-valid-anagram)이 단어 두 개가 애너그램인지 물었다면, 이 문제는 단어 수천 개를 애너그램끼리 묶으라고 한다. 질문이 "두 개가 같은가"에서 "같은 것끼리 모아라"로 바뀌면 필요한 도구도 바뀐다. 비교 함수 대신 같은 무리면 같은 값이 나오는 대표 키가 필요하다.

이 글은 무리를 하나씩 열어 비교하는 느린 풀이에서 시작해, 정렬한 문자열을 키로 쓰는 풀이, 글자 개수를 키로 쓰는 풀이, 개수로 정렬 문자열을 만드는 풀이까지 간다. 키를 잘못 만들면 서로 다른 무리가 섞이는 실제 입력을 보여 주고, 단어 길이에 따라 어느 키가 빠른지 재 본다. 해시맵 자체는 [해시맵 글](/posts/ds-hash-map)에 있고, 거기서도 이 문제를 짧게 다뤘다. 이 글은 그걸 풀이 여러 개와 실측으로 넓힌다. 코드는 Node.js 22, Python 3.13, Java 21에서 돌렸다.

## 같은 글자 구성끼리 묶는다

문자열 배열 `strs`가 주어진다. 글자를 재배열하면 서로 같아지는 단어끼리 묶어서 묶음들의 목록을 돌려준다. 묶음의 순서와 묶음 안의 단어 순서는 상관없다.

풀이에 영향을 주는 제약은 이렇다.

- 단어 수 n은 1 이상 10^4 이하다.
- 단어 길이 k는 0 이상 100 이하다. 빈 문자열도 들어온다.
- 글자는 영어 소문자뿐이다.

단어끼리 모든 쌍을 비교하면 쌍이 약 5천만 개이고 쌍마다 최대 100글자를 본다. 너무 많다. 단어마다 키를 한 번씩만 만들고 해시맵으로 모으면 n × (키 만드는 비용)으로 끝난다. 이 문제의 풀이들은 사실상 "키를 어떻게 만드느냐"의 차이다.

## 손으로 묶어 보기

글 끝까지 쓸 예시다.

```text
strs = ["stop", "pots", "tops", "cat", "act", "dog"]
답    = [["stop", "pots", "tops"], ["cat", "act"], ["dog"]]
```

손으로 묶는다면 "stop"을 첫 무리로 두고, "pots"를 보며 "stop이랑 같은 글자인가?"를 확인하고, "cat"을 보며 "stop 무리와 같나? 아니다, 새 무리"를 만든다. 무리가 늘면 새 단어마다 확인할 무리도 는다.

조금 지나면 요령이 생긴다. "stop"을 볼 때 머릿속으로 "o, p, s, t"를 떠올리고, "pots"를 볼 때도 같은 "o, p, s, t"가 떠오르니 같은 무리라고 판단한다. 단어를 직접 비교하는 대신 단어에서 뽑은 무언가를 비교한 것이다. 그 무언가가 이 글의 대표 키다.

좋은 키가 되려면 두 조건을 모두 지켜야 한다.

1. 애너그램이면 키가 반드시 같다.
2. 애너그램이 아니면 키가 반드시 다르다.

1번만 지키는 키는 쉽다. 예를 들어 "단어 길이"는 애너그램이면 반드시 같지만, "cat"과 "dog"도 같은 키가 되어 버린다. 2번까지 지키는 키를 고르는 게 핵심이고, 뒤에서 2번을 어기는 키가 실제로 어떻게 섞이는지 본다.

## 무리를 하나씩 열어 보는 풀이

키 없이 손으로 묶는 방식을 그대로 옮긴다. 무리마다 첫 단어를 대표로 두고, 새 단어가 오면 대표와 애너그램인지 하나씩 확인한다. 애너그램 확인은 [Valid Anagram](/posts/leetcode-valid-anagram)의 26칸 배열 풀이를 그대로 쓴다.

```js
function isAnagram(a, b) {
  if (a.length !== b.length) return false;
  const c = new Array(26).fill(0);
  for (let i = 0; i < a.length; i++) { c[a.charCodeAt(i) - 97]++; c[b.charCodeAt(i) - 97]--; }
  return c.every((x) => x === 0);
}

function groupAnagrams(strs) {
  const groups = []; // 무리 목록. 각 무리의 0번이 대표
  for (const w of strs) {
    const g = groups.find((grp) => isAnagram(grp[0], w)); // 무리를 하나씩 열어 본다
    if (g) g.push(w);
    else groups.push([w]); // 맞는 무리가 없으면 새 무리
  }
  return groups;
}

console.log(groupAnagrams(["stop", "pots", "tops", "cat", "act", "dog"]));
```

```text
[ [ 'stop', 'pots', 'tops' ], [ 'cat', 'act' ], [ 'dog' ] ]
```

시간은 무리 수를 g라 하면 O(n × g × k)다. 모든 단어가 서로 다르면 g가 n까지 커져 O(n² × k)다. 단어 1만 개, 무리 약 2천 개, 길이 100으로 재 보니 7.4초가 걸렸다. 공간은 결과를 담는 O(n × k) 말고는 26칸 배열뿐이다.

느린 이유는 Contains Duplicate 때와 같다. "맞는 무리가 있나"를 매번 처음부터 찾는다. 무리마다 이름표를 붙여 두고, 새 단어의 이름표로 무리를 바로 찾으면 된다. 이름표로 바로 찾는 구조가 해시맵이다.

## 정렬한 글자를 이름표로 쓰기

애너그램끼리는 글자를 정렬하면 같은 문자열이 된다. 애너그램이 아니면 정렬 결과가 다르다. 위의 두 조건을 다 지키니 정렬한 문자열이 곧 대표 키다.

```js
function groupAnagrams(strs) {
  const groups = new Map(); // 정렬한 글자 → 그 무리의 단어들
  for (const w of strs) {
    const key = [...w].sort().join(""); // "pots" → "opst"
    if (!groups.has(key)) groups.set(key, []);
    groups.get(key).push(w);
  }
  return [...groups.values()];
}

console.log(groupAnagrams(["stop", "pots", "tops", "cat", "act", "dog"]));
```

```text
[ [ 'stop', 'pots', 'tops' ], [ 'cat', 'act' ], [ 'dog' ] ]
```

아래 그림에서 다음을 누르면 단어를 하나씩 보며 키를 만들고, 그 키의 무리에 넣는다. 기억 칸의 각 줄이 "키: 무리"다.

단어마다 정렬 O(k log k)를 하니 시간은 O(n × k log k)다. 해시맵에 키를 넣고 찾는 것도 키 길이 k만큼 해시를 계산하니 O(n × k)가 더 붙지만 정렬보다 작다. 공간은 키와 결과 O(n × k)다. 같은 입력에서 144ms로, 무리를 하나씩 열어 보는 풀이보다 50배쯤 빨랐다.

`Map`을 쓴 덕분에 결과가 처음 나온 무리 순서대로 나온다. `Map`은 넣은 순서를 기억하기 때문이다. 문제는 순서를 상관하지 않지만, 테스트를 쓰거나 결과를 눈으로 확인할 때 편하다.

이 풀이의 한계는 정렬이다. k가 100이면 단어마다 비교 기반 정렬을 하는데, 글자 종류가 26개뿐이라는 사실을 쓰지 않는다. 개수를 세면 정렬 없이 O(k)에 키를 만들 수 있다.

## 글자 개수를 이름표로 쓰기

[Valid Anagram](/posts/leetcode-valid-anagram#26칸짜리-배열-하나면-충분하다)의 26칸 개수 배열을 키로 바꾼다. 애너그램이면 26칸이 똑같고, 아니면 어느 칸이든 다르다. 두 조건을 다 지킨다. 문제는 배열을 그대로 `Map`의 키로 쓸 수 없다는 점이다.

```js
const m = new Map();
m.set([1, 2], "x");
console.log(m.get([1, 2]));
```

```text
undefined
```

`Map`은 객체 키를 참조로 비교한다. 내용이 같아도 새로 만든 배열은 다른 키다. 그래서 개수 배열을 문자열로 바꿔서 쓴다.

```js
function groupAnagrams(strs) {
  const groups = new Map(); // "0#0#...#1#..." → 무리
  for (const w of strs) {
    const count = new Array(26).fill(0);
    for (let i = 0; i < w.length; i++) count[w.charCodeAt(i) - 97]++;
    const key = count.join("#"); // 구분자가 꼭 있어야 한다
    if (!groups.has(key)) groups.set(key, []);
    groups.get(key).push(w);
  }
  return [...groups.values()];
}

console.log(groupAnagrams(["stop", "pots", "tops", "cat", "act", "dog"]));
```

```text
[ [ 'stop', 'pots', 'tops' ], [ 'cat', 'act' ], [ 'dog' ] ]
```

"pots" 하나의 키가 만들어지는 과정을 따라가 보자. 칸 번호는 a가 0, o가 14, p가 15, s가 18, t가 19다.

## 구분자를 빼면 무리가 섞인다

위 코드의 `count.join("#")`에서 구분자를 빼고 `count.join("")`으로 쓰면 어떻게 될까. 숫자가 한 자리일 때는 문제가 없는데, 개수가 10을 넘는 순간 경계가 사라진다.

```js
function groupAnagramsNoSep(strs) {
  const groups = new Map();
  for (const w of strs) {
    const count = new Array(26).fill(0);
    for (let i = 0; i < w.length; i++) count[w.charCodeAt(i) - 97]++;
    const key = count.join(""); // 구분자 없음
    if (!groups.has(key)) groups.set(key, []);
    groups.get(key).push(w);
  }
  return [...groups.values()];
}

// a 1개 + b 11개, a 11개 + b 1개
console.log(groupAnagramsNoSep(["abbbbbbbbbbb", "aaaaaaaaaaab"]));
```

```text
[ [ 'abbbbbbbbbbb', 'aaaaaaaaaaab' ] ]
```

첫 단어의 개수는 a가 1, b가 11이라 앞부분이 "1" + "11"이고, 둘째 단어는 a가 11, b가 1이라 "11" + "1"이다. 둘 다 "111000…"이 되어 애너그램이 아닌데 한 무리로 묶였다. 앞에서 말한 두 번째 조건, "애너그램이 아니면 키가 달라야 한다"를 어긴 것이다. 단어 길이가 100까지라 개수가 두 자리, 세 자리가 될 수 있으니 실제로 나오는 입력이다.

이런 실수는 예시 몇 개로는 드러나지 않는다. 짧은 단어만 넣으면 개수가 한 자리라 다 맞기 때문이다. 키를 문자열로 이어 붙일 때는 구분자를 넣거나, 칸마다 길이를 고정하거나(`String.fromCharCode(c)`처럼 개수를 글자 하나로), 언어가 지원하면 튜플을 키로 쓴다. Java의 `Arrays.toString(count)`는 `"[0, 0, 1, ...]"`처럼 쉼표가 들어가서 안전하다.

## 합이나 해시 값 하나로 줄이면

키를 짧게 만들고 싶어서 글자 코드를 모두 더한 숫자 하나를 키로 쓰는 코드도 가끔 보인다. 순서와 상관없이 같은 글자면 같은 합이 나오니 첫 번째 조건은 지킨다. 하지만 서로 다른 구성도 합이 같을 수 있다.

```js
function groupBySum(strs) {
  const groups = new Map();
  for (const w of strs) {
    let key = 0;
    for (let i = 0; i < w.length; i++) key += w.charCodeAt(i); // 글자 코드의 합
    if (!groups.has(key)) groups.set(key, []);
    groups.get(key).push(w);
  }
  return [...groups.values()];
}
console.log(groupBySum(["ad", "bc", "da"]));
```

```text
[ [ 'ad', 'bc', 'da' ] ]
```

a(97) + d(100)와 b(98) + c(99)가 둘 다 197이라 "bc"가 "ad" 무리에 섞였다. 합은 정보를 너무 많이 버린다. 26칸 개수를 해시 함수에 넣어 숫자 하나로 줄이는 것도 같은 위험이 있다. 해시 값은 서로 다른 입력이 같은 값이 될 수 있는 게 정상이고, 해시맵은 그걸 알고 충돌한 키를 원래 키로 다시 비교해서 구분한다. 키를 직접 해시 값으로 바꿔 버리면 그 비교 단계가 사라진다. [Valid Anagram](/posts/leetcode-valid-anagram#소수를-곱하는-트릭이-위험한-이유)의 소수 곱 트릭이 틀리는 이유도 결국 같다. 키는 정보를 잃지 않는 값(정렬 문자열, 구분자가 있는 개수 문자열, 튜플)으로 두고, 숫자로 줄이는 일은 해시맵에 맡긴다.

## 개수로 정렬 문자열을 다시 만들기

정렬 키는 읽기 좋고 짧다는 장점이 있다. "opst"는 사람이 봐도 무슨 무리인지 안다. 개수 키는 빠르지만 26칸짜리라 길고 읽기 어렵다. 둘을 합치는 방법이 있다. 개수를 센 뒤 a부터 z까지 개수만큼 글자를 이어 붙이면, 비교 정렬 없이 정렬된 문자열이 나온다. 계수 정렬(counting sort)이다.

```js
function groupAnagrams(strs) {
  const groups = new Map();
  for (const w of strs) {
    const count = new Array(26).fill(0);
    for (let i = 0; i < w.length; i++) count[w.charCodeAt(i) - 97]++;
    let key = "";
    for (let k = 0; k < 26; k++) {
      if (count[k]) key += String.fromCharCode(97 + k).repeat(count[k]); // 'o' 1개, 'p' 1개, ...
    }
    if (!groups.has(key)) groups.set(key, []);
    groups.get(key).push(w);
  }
  return [...groups.values()];
}

console.log(groupAnagrams(["stop", "pots", "tops", "cat", "act", "dog"]));
```

```text
[ [ 'stop', 'pots', 'tops' ], [ 'cat', 'act' ], [ 'dog' ] ]
```

키는 정렬 키와 똑같은 "opst", "act", "dgo"다. 시간은 O(n × (k + 26))으로 개수 키와 같은 등급이다. 실제로는 61.6ms로 정렬 키(144ms)보다는 빠르고 개수 키(14.7ms)보다는 느렸다. 문자열을 조각조각 이어 붙이는 비용이 `join` 한 번보다 크기 때문이다. 키가 사람이 읽을 수 있어야 하거나(로그, 디버깅), 키 길이를 단어 길이만큼으로 줄이고 싶을 때 고를 만하다.

## Python과 Java로 옮기기

```python
from collections import defaultdict
from typing import List

class Solution:
    def groupAnagrams(self, strs: List[str]) -> List[List[str]]:
        groups = defaultdict(list)  # 없는 키를 읽으면 빈 리스트를 만들어 준다
        for w in strs:
            count = [0] * 26
            for ch in w:
                count[ord(ch) - ord("a")] += 1
            groups[tuple(count)].append(w)  # 리스트는 키가 될 수 없어 튜플로 바꾼다
        return list(groups.values())

    def groupAnagramsSorted(self, strs: List[str]) -> List[List[str]]:
        groups = defaultdict(list)
        for w in strs:
            groups["".join(sorted(w))].append(w)
        return list(groups.values())

s = Solution()
print(s.groupAnagrams(["stop", "pots", "tops", "cat", "act", "dog"]))
print(s.groupAnagramsSorted(["stop", "pots", "tops", "cat", "act", "dog"]))
```

```text
[['stop', 'pots', 'tops'], ['cat', 'act'], ['dog']]
[['stop', 'pots', 'tops'], ['cat', 'act'], ['dog']]
```

Python에서는 키로 튜플을 쓸 수 있어서 구분자 고민이 없다. 튜플은 원소 경계를 그대로 지닌 채 해시된다. 리스트를 키로 쓰면 `TypeError: unhashable type: 'list'`가 난다. 리스트는 고칠 수 있는 값이라 해시가 바뀔 수 있기 때문이다. `defaultdict(list)`는 처음 보는 키에 빈 리스트를 만들어 줘서 `if key not in groups` 확인을 없앤다. Python에서는 `sorted(w)`가 C로 구현돼 있지만 개수를 세는 `for` 반복문은 글자마다 바이트코드를 실행한다. 그래서 순위가 JavaScript와 다르게 나온다. 같은 입력으로 재 보니 길이 100에서는 개수 키 69.8ms, 정렬 키 93.4ms로 차이가 작았고, 길이 6에서는 정렬 키가 4.9ms로 개수 키 8.4ms보다 빨랐다. Python으로 풀 때는 정렬 키가 보통 충분하다.

```java
import java.util.*;

class Solution {
    public List<List<String>> groupAnagrams(String[] strs) {
        Map<String, List<String>> groups = new HashMap<>();
        for (String w : strs) {
            int[] count = new int[26];
            for (int i = 0; i < w.length(); i++) count[w.charAt(i) - 'a']++;
            String key = Arrays.toString(count); // "[0, 0, 1, ...]" 구분자가 들어간 문자열
            groups.computeIfAbsent(key, k -> new ArrayList<>()).add(w);
        }
        return new ArrayList<>(groups.values());
    }

    public List<List<String>> groupAnagramsSorted(String[] strs) {
        Map<String, List<String>> groups = new HashMap<>();
        for (String w : strs) {
            char[] cs = w.toCharArray();
            Arrays.sort(cs);
            groups.computeIfAbsent(new String(cs), k -> new ArrayList<>()).add(w);
        }
        return new ArrayList<>(groups.values());
    }
}
```

```text
[[dog], [cat, act], [stop, pots, tops]]
[[cat, act], [stop, pots, tops], [dog]]
```

같은 입력인데 두 풀이의 무리 순서가 다르다. `HashMap`은 키의 해시 순서대로 값을 꺼내서 넣은 순서를 지키지 않는다. 문제는 순서를 상관하지 않으니 둘 다 정답이다. 순서가 필요하면 `LinkedHashMap`을 쓴다.

Java에서 `int[]`를 그대로 키로 쓰면 안 된다. 배열은 `equals`와 `hashCode`가 내용이 아니라 객체 자체를 기준으로 하기 때문에, `Map<int[], String>`에 `new int[] { 1, 2 }`로 넣고 같은 내용의 새 배열로 꺼내면 `null`이 나온다. JavaScript의 `Map`에서 본 것과 같은 함정이다. `computeIfAbsent`는 키가 없을 때만 새 리스트를 만들고, 있든 없든 그 리스트를 돌려줘서 한 줄로 넣을 수 있다.

## 단어 길이에 따라 순위가 바뀐다

같은 개수(1만 개, 무리 약 2천 개)로 단어 길이만 바꿔 재 봤다. 다섯 번 돌린 가장 빠른 시간이다(하나씩 열어 보기는 한 번).

```text
k=100  무리 하나씩 열어 보기   7398.19ms
k=100  정렬 키                144.17ms
k=100  개수 키 (#)             14.73ms
k=100  개수로 만든 정렬 키      61.63ms
k=6    무리 하나씩 열어 보기   3662.42ms
k=6    정렬 키                  8.57ms
k=6    개수 키 (#)             11.82ms
k=6    개수로 만든 정렬 키      11.90ms
```

길이 100에서는 개수 키가 정렬 키보다 열 배 빨랐다. 그런데 길이 6에서는 정렬 키가 더 빨랐다. 짧은 단어를 정렬하는 비용은 아주 작고, 개수 키는 단어 길이와 상관없이 26칸 배열을 만들고 26개를 이어 붙이는 고정 비용이 든다. k log k가 26보다 작으면 정렬이 이긴다. Big O만 보고 "개수 키가 항상 빠르다"고 말하면 틀린다. 입력 크기를 함께 말하는 게 정확하다.

| 풀이 | 시간 | 키 길이 | 언제 고르나 |
|---|---|---|---|
| 무리 하나씩 열어 보기 | O(n × g × k) | 키 없음 | 출발점. 무리 수가 아주 적을 때만 |
| 정렬 키 | O(n × k log k) | k | 단어가 짧을 때, 코드를 빨리 써야 할 때 |
| 개수 키 | O(n × (k + 26)) | 26칸 | 단어가 길 때. 구분자를 꼭 넣는다 |
| 개수로 만든 정렬 키 | O(n × (k + 26)) | k | 키를 사람이 읽어야 하거나 짧게 두고 싶을 때 |

공간은 모든 풀이가 결과를 담는 O(n × k)를 쓴다. 키 저장에는 정렬 키가 O(n × k), 개수 키가 O(n × 26)이다.

면접에서는 정렬 키로 먼저 짜고, 복잡도를 말한 뒤 "글자가 26개로 정해져 있으니 정렬을 개수 세기로 바꾸면 O(n × k)가 된다"로 넘어가는 흐름이 자연스럽다. 그다음 구분자 문제를 스스로 짚으면 키 설계를 제대로 이해했다는 걸 보여 줄 수 있다. 단어가 짧으면 실제로는 정렬 키가 빠를 수 있다는 측정까지 덧붙이면, Big O와 실제 성능을 구분해서 본다는 인상을 준다.

## 비어 있거나 하나뿐인 입력

### 빈 문자열

`[""]`이면 `[[""]]`, `["", ""]`이면 `[["", ""]]`이다. 빈 문자열의 정렬 키는 `""`, 개수 키는 0 26개다. 두 키 모두 빈 문자열끼리만 같으니 따로 처리할 필요가 없다. `if (!key) continue`처럼 빈 키를 건너뛰는 코드를 넣으면 빈 문자열이 결과에서 사라진다.

### 단어 하나

`["x"]`는 `[["x"]]`다. 무리가 하나뿐이어도 2차원 배열로 돌려준다.

반대로 모든 단어가 서로 애너그램이면 무리 하나에 n개가 다 들어간다. 무리 수가 1이든 n이든 해시맵 풀이의 시간은 달라지지 않는다. 무리를 하나씩 열어 보는 풀이만 무리 수에 따라 빨라지거나 느려진다.

### 같은 단어가 여러 번 나올 때

`["ab", "ab", "ba"]`처럼 같은 단어가 반복되면 셋 다 한 무리에 그대로 들어간다. 문제는 중복을 없애라고 하지 않았으니 지우지 않는다.

### 길이만 다른 단어

`["aaa", "aa", "a"]`는 세 무리다. 글자 종류가 같아도 개수가 다르면 애너그램이 아니다. 키를 "쓰인 글자 종류"(예: `[...new Set(w)].sort().join("")`)로 만들면 셋이 한 무리가 되어 틀린다.

### 결과를 비교할 때

무리 순서와 무리 안 순서가 상관없으니, 테스트에서 결과를 비교할 때는 양쪽을 정규화해야 한다. 무리 안의 단어를 정렬하고, 무리 목록도 정렬한 뒤 비교한다. 정규화 없이 `JSON.stringify`로 비교하면 맞는 답을 틀렸다고 한다. 위 Java 출력처럼 언어마다 순서가 달라지니 특히 그렇다.

## 면접관이 조건을 바꾸면

### 유니코드가 들어오면

26칸 개수 키는 쓸 수 없다. 정렬 키로 돌아가되 코드 포인트 단위로 자른다. `[...w].sort().join("")`은 `for...of`와 같은 코드 포인트 단위라 이모지도 한 글자로 정렬된다. 화면에서 같은 글자가 다른 코드 포인트 조합일 수 있으니 `w.normalize("NFC")`를 먼저 한다. 개수 키를 쓰고 싶으면 글자별 개수 `Map`을 만든 뒤 글자 순으로 정렬해 "글자:개수" 목록으로 직렬화한다. 이 부분은 [Valid Anagram 글의 유니코드 절](/posts/leetcode-valid-anagram#유니코드가-들어오면)에 자세히 있다.

```js
function groupAnagramsUnicode(strs) {
  const groups = new Map();
  for (const w of strs) {
    const key = [...w.normalize("NFC")].sort().join(""); // 정규화 후 코드 포인트 단위 정렬
    if (!groups.has(key)) groups.set(key, []);
    groups.get(key).push(w);
  }
  return [...groups.values()];
}
console.log(groupAnagramsUnicode(["caf\u00e9", "e\u0301fac", "가나", "나가", "😀😃", "😃😀"]));
```

```text
[ [ 'café', 'éfac' ], [ '가나', '나가' ], [ '😀😃', '😃😀' ] ]
```

조합형 é로 쓴 "café"와 e + 결합 악센트로 쓴 "éfac"가 정규화 덕분에 한 무리가 됐다.

### 무리를 크기 순으로 돌려 달라면

해시맵으로 묶은 뒤 무리를 크기 순으로 정렬한다. 무리 수가 g면 O(g log g)가 더 든다. 가장 큰 무리 몇 개만 필요하면 정렬 대신 힙이나 버킷을 쓰는데, 이것이 [Top K Frequent Elements](/posts/leetcode-top-k-frequent-elements)와 같은 문제가 된다.

### 단어가 너무 많아 메모리에 다 안 들어가면

키로 나누는 방식이 그대로 분산 처리로 이어진다. 단어마다 키를 계산해 "키 → 단어" 쌍으로 내보내고, 같은 키를 같은 작업자에게 보내 거기서 모은다. MapReduce의 맵과 리듀스 단계와 같은 모양이다. 같은 키는 반드시 같은 곳으로 가니 무리가 쪼개지지 않는다.

### 단어가 하나씩 들어온다면

해시맵을 계속 들고 있으면 된다. 새 단어가 오면 키를 만들어 그 무리에 넣고, "이 단어의 애너그램이 지금까지 몇 개였나"는 무리 크기로 O(1)에 답한다. 키 계산이 O(k)라 단어 하나당 O(k)다.

### 비슷한 생각으로 푸는 문제

"같은 무리면 같은 키"를 만드는 문제는 꽤 많다. LeetCode 249. Group Shifted Strings는 글자를 모두 같은 칸만큼 밀면 같아지는 단어끼리 묶는다. 키는 이웃 글자 사이의 차이(26으로 나눈 나머지) 목록이다.

```js
function groupShifted(strs) {
  const groups = new Map();
  for (const w of strs) {
    const diffs = [];
    for (let i = 1; i < w.length; i++) {
      diffs.push((w.charCodeAt(i) - w.charCodeAt(i - 1) + 26) % 26); // z 다음은 a로 돈다
    }
    const key = diffs.join(","); // 여기서도 구분자가 필요하다
    if (!groups.has(key)) groups.set(key, []);
    groups.get(key).push(w);
  }
  return [...groups.values()];
}
console.log(groupShifted(["abc", "bcd", "xyz", "az", "ba", "a", "z"]));
```

```text
[ [ 'abc', 'bcd', 'xyz' ], [ 'az', 'ba' ], [ 'a', 'z' ] ]
```

"az"는 a에서 z로 25칸, "ba"는 b에서 a로 -1칸인데 26을 더해 나머지를 구하면 둘 다 25라 같은 무리다. 한 글자짜리는 차이가 없어 빈 키로 모인다. LeetCode 609. Find Duplicate File in System은 파일 내용을 키로 경로를 묶는다. 어느 쪽이든 키가 "같은 무리면 같고, 다른 무리면 다르다"는 두 조건을 지키는지가 정답을 가른다. [Contains Duplicate](/posts/leetcode-contains-duplicate)는 이 문제에서 키가 값 자체인 가장 단순한 경우다.

## 면접에서 나올 만한 질문

### 왜 해시맵을 썼나요?

새 단어가 들어갈 무리를 바로 찾기 위해서다. 해시맵 없이 무리를 하나씩 열어 비교하면 무리 수에 비례하는 시간이 들어 최악 O(n² × k)가 된다. 무리마다 대표 키를 정해 두면 단어마다 키를 한 번 만들고 해시 조회 한 번으로 무리를 찾으니 O(n × 키 만드는 비용)으로 줄어든다.

### 대표 키가 지켜야 할 조건은 무엇인가요?

두 가지다. 애너그램이면 키가 반드시 같아야 하고, 애너그램이 아니면 키가 반드시 달라야 한다. 정렬한 문자열과 26칸 개수 배열은 둘 다 지킨다. 단어 길이나 글자 종류 집합은 첫 번째만 지켜서 서로 다른 무리가 섞인다.

### 정렬 키와 개수 키 중 무엇이 더 빠른가요?

단어 길이에 따라 다르다. 정렬 키는 O(k log k), 개수 키는 O(k + 26)이라 긴 단어에서는 개수 키가 빠르다. 실제로 길이 100에서 열 배 빨랐다. 하지만 길이 6처럼 짧으면 개수 키의 26칸 고정 비용이 커서 정렬 키가 더 빨랐다.

### 개수 배열을 키로 쓸 때 조심할 점은요?

배열을 그대로 키로 쓰면 JavaScript `Map`과 Java `HashMap` 모두 참조로 비교해서 같은 내용의 배열을 다른 키로 본다. 문자열로 바꿔야 하는데, 구분자 없이 이어 붙이면 a 1개 + b 11개와 a 11개 + b 1개가 같은 "111…"이 되어 섞인다. 구분자를 넣거나, Python이면 튜플을 쓰거나, Java면 `Arrays.toString`을 쓴다.

### 시간 복잡도와 공간 복잡도를 말해 보세요.

개수 키 풀이는 단어마다 O(k)에 개수를 세고 O(26)에 키를 만들어 O(n × k)다. 정렬 키 풀이는 O(n × k log k)다. 공간은 결과에 모든 단어가 들어가니 O(n × k)이고, 키 저장에 정렬 키는 O(n × k), 개수 키는 O(n × 26)이 더 든다.

### 결과 순서가 실행할 때마다 달라질 수 있나요?

언어와 자료구조에 따라 다르다. JavaScript `Map`과 Python `dict`는 넣은 순서를 지켜서 처음 나온 무리 순서대로 나온다. Java `HashMap`은 해시 순서라 넣은 순서와 다르고, 같은 입력이라도 키 모양이 바뀌면 순서가 바뀐다. 문제는 순서를 상관하지 않지만, 테스트에서는 결과를 정렬해 정규화한 뒤 비교해야 한다.
