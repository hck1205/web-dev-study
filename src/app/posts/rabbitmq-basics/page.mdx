주문 취소 이벤트를 보내는 코드를 새로 붙였다. 배포 뒤 로그에는 "published" 가 잘 찍히는데 환불 담당 컨슈머는 아무것도 받지 못한다. RabbitMQ 관리 화면에서 큐를 열어 보니 메시지가 0개다. 에러는 어디에도 없다. 원인은 라우팅 키였다. 큐는 `order.created`에만 묶여 있었고, 새 코드는 `order.cancelled`로 보냈다. RabbitMQ는 갈 곳 없는 메시지를 기본으로 조용히 버린다.

RabbitMQ에서는 메시지를 큐에 넣지 않는다. 익스체인지에 보내고, 익스체인지가 규칙에 따라 큐로 나눈다. 이 한 단계를 이해하지 못하면 위 같은 일을 계속 겪는다. 이 글은 익스체인지 네 종류와 바인딩, ack와 prefetch, 발행 확인, 쿼럼 큐, 데드 레터 익스체인지를 실제로 돌린 출력과 함께 본다. Ubuntu 24.04에서 `apt`로 설치한 RabbitMQ 3.12.1(Erlang 25)이고, 클라이언트는 Node.js의 `amqplib` 0.10.4다. 지금 최신 계열은 4.x이고, 버전에 따라 다른 부분은 그때그때 밝힌다.

이 주제의 다른 글: ack, 재전달, 경쟁하는 컨슈머 같은 큐 일반의 동작은 [메시지 큐 기초](/posts/message-queue-basics)에, 한 메시지를 여러 곳에 나누는 팬아웃은 [발행·구독](/posts/pub-sub)에, 실패 메시지를 몇 번 만에 포기하고 어떻게 되돌려 보낼지는 [데드 레터 큐](/posts/dead-letter-queue)에 있다. 여기서는 RabbitMQ가 그 일들을 어떤 장치로 하는지만 본다.

```bash
# 설치하고 서버를 띄운다 (Ubuntu 24.04 저장소 기준 3.12.1)
sudo apt-get install -y rabbitmq-server

# 서버가 응답할 때까지 기다린다
sudo rabbitmqctl await_startup

# 관리 화면(15672 포트)과 rabbitmqadmin을 쓰려면 관리 플러그인을 켠다
sudo rabbitmq-plugins enable rabbitmq_management
```

## 큐가 아니라 익스체인지로 보낸다

RabbitMQ가 쓰는 AMQP 0-9-1의 모델은 이렇다. 프로듀서는 익스체인지(exchange)에 메시지와 라우팅 키를 보낸다. 익스체인지는 메시지를 저장하지 않는다. 자기에게 걸린 바인딩(binding) 목록을 보고 메시지를 복사해 큐에 넣을 뿐이다. 바인딩은 "이 익스체인지에서 이런 키로 온 메시지를 이 큐에 넣어라"라는 규칙이다. 컨슈머는 큐에서 꺼낸다.

`sendToQueue("payment", ...)`처럼 큐 이름으로 바로 보내는 코드도 있다. 이것도 실은 이름이 빈 문자열인 기본 익스체인지로 보내고, 기본 익스체인지가 라우팅 키와 이름이 같은 큐에 넣는 것이다. 모든 큐는 자기 이름으로 기본 익스체인지에 자동으로 묶여 있다.

## 익스체인지 네 종류

익스체인지마다 라우팅 키를 보는 방식이 다르다. 넷을 만들고 큐 다섯 개를 묶은 뒤 메시지 여덟 개를 보냈다.

```js
// direct: 키가 정확히 같아야 한다
await ch.bindQueue("payment", "orders.direct", "order.created");
await ch.bindQueue("email", "orders.direct", "order.created");
// topic: 점으로 나눈 단어 단위로 * 는 정확히 한 단어, # 는 0개 이상의 단어
await ch.bindQueue("kr-orders", "orders.topic", "order.*.kr");
await ch.bindQueue("audit", "orders.topic", "order.#");
// fanout: 키를 보지 않고 묶인 큐 모두에
await ch.bindQueue("audit", "orders.fanout", "");
await ch.bindQueue("email", "orders.fanout", "");
// headers: 키 대신 헤더 값으로. all이면 전부, any면 하나만 맞으면
await ch.bindQueue("vip", "orders.headers", "", { "x-match": "all", tier: "vip", region: "kr" });
```

```bash
# 익스체인지 목록 (amq.* 기본 익스체인지는 뺐다)
sudo rabbitmqctl list_exchanges name type

```

## 갈 곳 없는 메시지를 잡는 법

처음 장애로 돌아가자. 맞는 바인딩이 없는 메시지는 버려진다. 프로듀서가 이걸 알게 하려면 `mandatory` 플래그를 켜고 돌아오는 메시지를 받는다.

```js
// 갈 곳이 없으면 브로커가 basic.return으로 돌려준다
ch.on("return", (m) =>
  console.log("RETURNED", m.fields.replyCode, m.fields.replyText, m.fields.exchange, m.fields.routingKey));
ch.publish("orders.direct", "order.cancelled", body, { persistent: true, mandatory: true });
```

```text
RETURNED 312 NO_ROUTE orders.direct order.cancelled
```

`312 NO_ROUTE`가 "어느 큐로도 못 보냈다"는 뜻이다. 돌아온 메시지를 로그로 남기고 알람을 걸면 라우팅 키 오타가 배포 당일에 드러난다. 다른 방법은 익스체인지에 `alternate-exchange` 인자를 줘서, 갈 곳 없는 메시지를 따로 정한 익스체인지(와 그 뒤의 큐)로 보내는 것이다. 프로듀서 코드를 고치지 않고 운영 쪽에서 붙일 수 있다.

조심할 점이 있다. `mandatory`는 "큐까지 갔나"만 알려 준다. 큐에 들어간 메시지가 디스크에 안전하게 적혔는지는 따로 확인해야 한다.

## 브로커가 받았는지 확인하는 발행 확인

`channel.publish()`는 기본으로 응답을 기다리지 않는다. 소켓 버퍼에 넣고 끝이다. 그 순간 브로커가 죽으면 메시지는 사라지고 프로듀서는 모른다. 그래서 잃으면 안 되는 메시지는 세 가지를 같이 건다.

```js
// 1) 큐를 durable로: 브로커가 재시작해도 큐 정의가 남는다
await ch.assertQueue("payment", { durable: true, arguments: { "x-queue-type": "quorum" } });

// 2) 메시지를 persistent로: 클래식 큐에서 디스크에 적는다 (쿼럼 큐는 항상 디스크에 적는다)
// 3) 확인 채널: 브로커가 받아서 저장했다고 답할 때까지 기다린다
const ch = await conn.createConfirmChannel();
ch.publish("orders.direct", "order.created", body, { persistent: true });
await ch.waitForConfirms();   // 여기서 예외가 나면 다시 보낸다
```

발행 확인(publisher confirms)을 켜면 브로커가 메시지를 받아 처리한 뒤 `basic.ack`를 돌려준다. 쿼럼 큐라면 과반수 노드에 적힌 뒤다. 응답이 `nack`이거나 연결이 끊겨 응답을 못 받으면 프로듀서가 다시 보낸다. 다시 보내니 중복이 생길 수 있고, 그래서 메시지에 고유 ID(`messageId`)를 넣어 받는 쪽이 거른다. 어디까지가 "정확히 한 번"인지는 [메시지 전달 보장](/posts/message-delivery-semantics)에서 따로 다룬다.

확인을 한 건씩 기다리면 느리다. 수백 건을 보내고 한꺼번에 기다리거나, 비동기 콜백으로 확인을 받아 처리하는 편이 처리량이 훨씬 높다. DB에 쓴 사실을 빠짐없이 보내는 문제는 확인만으로는 풀리지 않는다. 그건 [이벤트 기반 아키텍처](/posts/event-driven-architecture)의 아웃박스가 맡는다.

## ack와 prefetch: 컨슈머가 몇 개를 쥐고 있나

큐가 컨슈머에게 메시지를 보내면 그 메시지는 `unacked` 상태가 된다. 컨슈머가 `ack`를 보내면 지워지고, `nack`(또는 `reject`)를 보내면 다시 큐로 가거나(`requeue=true`) 버려진다(데드 레터 설정이 있으면 그쪽으로). 컨슈머 연결이 끊기면 그 컨슈머가 쥐고 있던 `unacked` 메시지는 모두 큐로 돌아가 다른 컨슈머에게 간다. 이 동작의 일반론은 [메시지 큐 기초](/posts/message-queue-basics)에 있다.

RabbitMQ에서 따로 알아야 할 것은 prefetch다. 브로커는 컨슈머가 아직 ack하지 않은 메시지를 몇 개까지 미리 보낼지를 채널의 prefetch 값으로 정한다. 썸네일 작업 100개를 넣고, prefetch 10인 컨슈머 하나를 붙여서 ack하지 않고 쥐고만 있게 했다.

```bash
# prefetch 10인 컨슈머가 붙어 있을 때
sudo rabbitmqctl list_queues name messages_ready messages_unacknowledged consumers
sudo rabbitmqctl list_consumers queue_name consumer_tag ack_required prefetch_count
```

```text
name	messages_ready	messages_unacknowledged	consumers
thumbnail	90	10	1

queue_name	consumer_tag	ack_required	prefetch_count
thumbnail	worker-prefetch-10	true	10
```

컨슈머가 10개를 쥐고 90개는 큐에서 기다린다. 컨슈머 연결을 끊자 다시 `thumbnail 100 0 0`이 됐다. 같은 실험을 prefetch 0(제한 없음)으로 했다.

```text
name	messages_ready	messages_unacknowledged	consumers
thumbnail	0	100	1
```

100개가 전부 한 컨슈머에게 갔다. 이 상태에서 두 번째 컨슈머를 띄우면 받을 게 없다. 첫 컨슈머가 100개를 하나씩 처리하는 동안 둘째는 논다. 첫 컨슈머가 30번째에서 멈추면 나머지 70개는 그 연결이 끊길 때까지 아무도 처리하지 못한다. 아래 그림이 prefetch에 따라 메시지가 어떻게 나뉘는지 보여 준다.

prefetch를 몇으로 잡을지는 처리 시간과 왕복 시간으로 정한다. 하나에 수 초 걸리는 무거운 작업이면 1~5로 작게 둬서 고르게 나눈다. 하나에 수 밀리초인 가벼운 작업이면 ack를 기다리는 왕복 시간이 처리 시간보다 길어지니 수십~수백으로 늘려 컨슈머가 놀지 않게 한다. 제한 없음(0)은 거의 항상 틀린 값이다. 큐가 깊을 때 컨슈머 하나의 메모리로 메시지가 다 몰린다.

`consumer_timeout`도 기억해 둔다. 3.12의 기본값은 `1800000`ms(30분)이고, 넘기면 브로커가 `PRECONDITION_FAILED`로 채널을 닫는다. 30분이 넘는 작업을 메시지 하나로 처리하는 구조라면 이 값을 늘리기보다 작업을 나누고 진행 상황을 따로 저장하는 편이 낫다.

## 클래식 큐와 쿼럼 큐

클래식 큐는 한 노드에 있다. 그 노드가 죽으면 큐도 멈춘다. 예전에는 클래식 큐를 다른 노드에 복제하는 미러링을 썼지만 장애 상황에서 메시지를 잃거나 동기화가 멈추는 문제가 많았고, 3.8에서 쿼럼 큐가 나온 뒤 미러링은 4.0에서 아예 빠졌다.

쿼럼 큐는 Raft 합의 알고리즘으로 큐를 노드 여러 대(보통 3이나 5)에 복제한다. 리더 하나가 쓰기를 받고, 과반수 노드가 디스크에 적어야 발행 확인을 돌려준다. 리더가 죽으면 남은 노드들이 새 리더를 뽑는다.

쿼럼 큐에는 클래식 큐에 없는 장치가 있다. 메시지가 몇 번 다시 배달됐는지 `x-delivery-count` 헤더로 세고, `x-delivery-limit`을 넘으면 그 메시지를 버리거나 데드 레터로 보낸다. 처리하면 항상 죽는 독이 든 메시지가 큐 앞에서 무한히 돌지 않게 하는 장치다. `payment` 큐에 한도 3을 걸고, 받을 때마다 `nack(requeue=true)`를 하는 컨슈머를 붙였다.

```js
// 결제 API가 계속 실패한다고 치고 매번 다시 큐로 돌려보낸다
await ch.consume("payment", (m) => {
  console.log("deliver#", ++n, "redelivered=", m.fields.redelivered,
              "x-delivery-count=", m.properties.headers["x-delivery-count"]);
  ch.nack(m, false, true);
});
```

```text
deliver# 1 redelivered= false x-delivery-count= undefined
deliver# 2 redelivered= true x-delivery-count= 1
deliver# 3 redelivered= true x-delivery-count= 2
deliver# 4 redelivered= true x-delivery-count= 3
```

네 번 배달되고 멈췄다. 처음 배달에는 헤더가 없고, 다시 배달될 때마다 1씩 오른다. 3을 넘기는 순간 메시지는 `payment`에서 빠져 다음 절의 데드 레터 큐로 갔다. 버전 차이가 크니 주의한다. 3.12에서는 `x-delivery-limit`을 직접 걸지 않으면 한도가 없다. 4.0부터는 쿼럼 큐의 기본 한도가 20이라서, 데드 레터 설정 없이 쓰던 큐에서 20번 실패한 메시지가 조용히 버려진다.

쿼럼 큐가 늘 답은 아니다. 디스크에 항상 쓰고 복제하니 클래식 큐보다 느리고 메모리와 디스크를 더 쓴다. 메시지 우선순위는 4.0 전에는 지원하지 않았고, 비영속 메시지 같은 일부 기능도 다르게 동작한다. 잃어도 되는 임시 큐(응답 큐, 캐시 무효화 알림)는 클래식 큐로 둔다.

## 실패한 메시지를 보내는 데드 레터 익스체인지

큐에 `x-dead-letter-exchange`를 주면, 그 큐에서 다음 네 경우에 빠지는 메시지가 지정한 익스체인지로 다시 발행된다. 컨슈머가 `requeue=false`로 거절했을 때(`rejected`), 메시지 TTL이 지났을 때(`expired`), 큐 길이 한도를 넘어 밀려났을 때(`maxlen`), 쿼럼 큐의 배달 한도를 넘었을 때(`delivery_limit`)다.

위 실험의 `payment` 큐는 이렇게 만들었다.

```js
await ch.assertQueue("payment", {
  durable: true,
  arguments: {
    "x-queue-type": "quorum",
    "x-dead-letter-exchange": "orders.dlx",       // 빠진 메시지를 보낼 익스체인지
    "x-dead-letter-routing-key": "payment",       // 그때 쓸 라우팅 키 (없으면 원래 키)
    "x-delivery-limit": 3,                        // 3번 넘게 다시 배달되면 빠진다
  },
});
await ch.bindQueue("payment.dlq", "orders.dlx", "payment");
```

## 큐가 쌓이거나 비었을 때 보는 순서

운영에서 가장 많이 보는 명령은 `list_queues`다. 숫자 세 개의 조합으로 상황을 가른다.

```bash
# 큐마다 대기, 처리 중, 컨슈머 수
sudo rabbitmqctl list_queues name messages_ready messages_unacknowledged consumers

# 메모리나 디스크 경보가 켜졌는지
sudo rabbitmq-diagnostics alarms
```

```text
Asking node rabbit@vm to report any known resource alarms ...
Node rabbit@vm reported no alarms, local or clusterwide
```

`messages_ready`가 크고 `consumers`가 0이면 컨슈머가 다 죽었거나 다른 큐를 보고 있다. 배포한 컨슈머의 큐 이름부터 확인한다. `messages_ready`가 크고 컨슈머도 있으면 처리량이 부족한 것이니 컨슈머를 늘린다. 클래식 큐 하나는 한 노드의 한 프로세스가 처리해서 큐 하나의 처리량에도 상한이 있다.

`messages_unacknowledged`가 크고 줄지 않으면 컨슈머가 받고 ack를 안 하고 있다. prefetch가 너무 크거나, 처리 중 멈췄거나, 코드가 ack를 빼먹은 것이다. ack를 빼먹으면 연결이 끊기는 순간 전부 다시 배달되니, 재배포 때마다 처리된 메시지가 다시 오는 증상으로 나타난다.

큐가 비어 있는데 메시지가 없어졌다면 거꾸로 따라간다. 앞에서 본 `list_bindings`로 키가 맞는지, `mandatory` 반환이나 alternate exchange에 쌓였는지, DLQ에 `x-death`와 함께 가 있는지 본다.

프로듀서가 갑자기 멈추면 경보를 본다. 메모리가 `vm_memory_high_watermark`(3.12 기본 0.4, 즉 메모리의 40%. 4.0부터는 0.6)를 넘거나 남은 디스크가 `disk_free_limit`(기본 50MB) 아래로 떨어지면, 브로커는 발행하는 연결을 막는다(blocked). 프로듀서 쪽에서는 에러 없이 `publish`가 멈춘 것처럼 보인다. 쌓인 큐를 소비해서 줄이는 게 근본 해결이고, 큐 길이 한도(`x-max-length`)와 넘쳤을 때의 동작(`x-overflow`)을 미리 정해 두면 한 큐가 브로커 전체를 막지 않는다.

## Kafka와 무엇이 다른가

RabbitMQ는 메시지를 큐에 넣고, 컨슈머가 ack하면 지운다. 라우팅이 유연하고, 메시지마다 ack와 재배달, 우선순위, TTL, 데드 레터를 붙일 수 있다. 작업을 여러 워커에 나눠 주는 데 맞다. [Kafka](/posts/kafka-basics)는 메시지를 로그에 쌓고 지우지 않으며, 컨슈머 그룹마다 오프셋을 따로 둔다. 같은 이벤트를 여러 팀이 각자 다시 읽고, 대량을 오래 보관하는 데 맞다.

순서도 다르게 깨진다. RabbitMQ 큐 하나는 들어온 순서로 내보내지만, 컨슈머가 여럿이거나 `nack`로 다시 넣으면 순서가 바뀐다. 키별 순서가 필요하면 consistent hash 익스체인지 플러그인으로 키마다 큐를 나누거나, 3.9부터 있는 스트림(stream) 큐를 쓴다. 스트림은 RabbitMQ 안의 Kafka 같은 로그로, 읽어도 지워지지 않고 오프셋으로 다시 읽는다.

## 익스체인지가 정하고, ack가 지우고, 쿼럼이 지킨다

RabbitMQ에서 메시지가 사라지는 곳은 대개 셋이다. 바인딩이 없어서 익스체인지에서 버려지거나, 발행 확인 없이 보내다 브로커가 죽거나, 실패를 반복하다 한도에 걸려 버려진다. 첫째는 `mandatory`나 alternate exchange로, 둘째는 durable 큐와 persistent 메시지와 발행 확인으로, 셋째는 데드 레터 익스체인지로 막는다. prefetch는 컨슈머가 한 번에 쥘 양을 정해 일을 고르게 나누고, 쿼럼 큐는 노드 하나가 죽어도 큐가 살아 있게 한다.

## 면접에서 나올 만한 질문

### 큐로 보냈는데 큐에 메시지가 없다. 무엇부터 보나?

라우팅부터 본다. RabbitMQ는 익스체인지로 보내고 바인딩이 큐를 고르는데, 맞는 바인딩이 없으면 기본으로 조용히 버린다. `list_bindings`로 키와 바인딩이 맞는지 보고, `mandatory` 플래그를 켜서 `312 NO_ROUTE` 반환을 받거나 alternate exchange로 갈 곳 없는 메시지를 모은다. 바인딩이 맞는데도 없으면 DLQ와 `x-death` 헤더를 본다.

### direct, topic, fanout, headers 익스체인지는 어떻게 다른가?

direct는 라우팅 키가 정확히 같은 바인딩으로, topic은 점으로 나눈 단어에 `*`(한 단어)와 `#`(0개 이상)를 쓴 패턴으로, fanout은 키를 보지 않고 묶인 큐 전부로, headers는 키 대신 헤더 값으로 보낸다. 실무에서는 키 이름 규칙을 정해 두고 topic으로 대부분을 처리한다. `order.#`이 `order` 자체에도 맞는다는 걸 자주 틀린다.

### prefetch는 무엇이고 몇으로 잡나?

ack하지 않은 메시지를 컨슈머 하나에 몇 개까지 미리 보낼지 정하는 값이다. 제한이 없으면 큐의 메시지가 한 컨슈머에게 다 몰려 다른 컨슈머가 놀고, 그 컨슈머가 멈추면 쥔 메시지가 전부 묶인다. 무거운 작업은 1~5처럼 작게, 가벼운 작업은 왕복 시간을 감추도록 수십~수백으로 잡는다.

### 메시지를 잃지 않으려면 무엇을 켜야 하나?

큐를 durable로, 메시지를 persistent로 만들고, 확인 채널로 발행 확인을 받는다. 확인을 못 받으면 다시 보내니 메시지에 고유 ID를 넣어 받는 쪽이 중복을 거른다. 노드 장애까지 견디려면 쿼럼 큐로 복제한다. 컨슈머 쪽은 처리 후에 수동으로 ack한다.

### 쿼럼 큐와 클래식 큐는 언제 고르나?

잃으면 안 되는 업무 메시지는 쿼럼 큐, 잃어도 되는 임시 메시지는 클래식 큐로 둔다. 쿼럼 큐는 Raft로 과반수 노드에 적은 뒤 확인을 돌려주어 노드 하나가 죽어도 살아 있지만, 느리고 자원을 더 쓴다. 클래식 큐 미러링은 4.0에서 없어졌으니 복제가 필요하면 쿼럼 큐로 간다. 4.0부터는 쿼럼 큐에 배달 한도 20이 기본으로 걸린다.

### 같은 메시지가 계속 실패하며 큐를 막는다. 어떻게 하나?

쿼럼 큐에 `x-delivery-limit`을 걸고 `x-dead-letter-exchange`로 데드 레터 큐를 연결한다. 그러면 한도를 넘은 메시지가 `x-death` 헤더와 함께 DLQ로 빠지고 뒤의 메시지는 계속 처리된다. 실험에서는 한도 3을 걸자 네 번 배달된 뒤 `reason: delivery_limit`으로 DLQ에 갔다.

### 프로듀서가 에러 없이 멈췄다. 무엇을 의심하나?

브로커의 메모리나 디스크 경보다. 메모리가 `vm_memory_high_watermark`를 넘거나 디스크가 `disk_free_limit` 아래로 떨어지면 브로커가 발행 연결을 막아서, 프로듀서는 publish가 멈춘 것처럼 보인다. `rabbitmq-diagnostics alarms`로 확인하고, 쌓인 큐를 소비해 줄이고, 큐 길이 한도로 한 큐가 전체를 막지 않게 해 둔다.
