## 주소가 하나뿐이라 문 앞에서 막을 수 없다

REST API에서는 게이트웨이 설정 몇 줄로 꽤 많은 것을 막을 수 있었다. `/admin/*`은 운영자 역할만, `DELETE /orders/*`는 로그인한 사용자만 같은 식이다. 주소와 메서드가 곧 "무엇을 하려는지"를 말해 주기 때문이다.

GraphQL로 옮기면 이 규칙이 통째로 사라진다. 모든 요청이 `POST /graphql` 하나로 들어오고, 무엇을 하려는지는 본문 안 쿼리 문자열에 있다. 내 주문 목록을 보는 요청과 남의 주문을 꺼내는 요청이 게이트웨이 눈에는 똑같이 생겼다. 그래서 GraphQL 서버는 인가(authorization, "이 사람이 이걸 해도 되나")를 서버 안쪽에서 직접 해야 한다.

어디서 하느냐가 이 글의 질문이다. 리졸버(필드마다 값을 채우는 함수)마다 `if`를 넣을 수도 있고, 스키마에 `@auth` 같은 디렉티브를 붙일 수도 있고, 그 아래 업무 로직 계층에 둘 수도 있다. 하나씩 돌려 보면 어디가 새는지 보인다. GraphQL 자체의 동작(스키마, 리졸버, 200 속의 에러, 깊이·비용 제한)은 [GraphQL 기초](/posts/graphql-basics)에서 다뤘고, 인증과 인가의 차이와 RBAC·ABAC 같은 권한 모델은 [인증과 인가](/posts/authn-vs-authz)에 있다. 여기서는 GraphQL이라서 생기는 문제에 집중한다.

데모는 Node.js 22와 graphql-js 16.14로 만들었다. 사용자 `u1`(kim), `u2`(lee), 운영자 `a1`이 있고, 주문 `o1`과 `o3`은 kim의 것, `o2`(99만 원)는 lee의 것이다. 모든 요청은 kim으로 로그인한 상태에서 보낸다.

## 누가 묻는지는 context에 한 번 넣는다

인증, 즉 "누구냐"는 GraphQL 바깥에서 끝낸다. HTTP 미들웨어나 서버의 context 함수가 `Authorization` 헤더나 세션 쿠키를 검증하고, 결과를 요청 하나 동안 모든 리졸버가 공유하는 context 객체에 넣는다.

```ts
// Apollo Server 4·5: 요청마다 한 번 불린다
const { url } = await startStandaloneServer(server, {
  context: async ({ req }) => {
    const viewer = await verifyToken(req.headers.authorization); // 실패하면 null
    return {
      viewer,                           // 이후 모든 리졸버가 ctx.viewer로 본다
      orders: new OrderService(viewer), // 업무 계층도 이 사용자로 묶어 만든다
    };
  },
});
```

토큰이 아예 없을 때 어떻게 할지는 두 갈래다. 전부 로그인이 필요한 API라면 context 함수에서 바로 401을 내고 실행을 시작하지 않는다. 로그인 없이 볼 수 있는 필드가 섞여 있다면 `viewer`를 `null`로 두고, 로그인이 필요한 필드에서 `UNAUTHENTICATED` 코드의 에러를 낸다. 어느 쪽이든 리졸버마다 토큰을 다시 해석하지는 않는다. 토큰 검증은 한 곳, 판정은 그 결과를 읽기만 한다.

구독(subscription)은 HTTP 요청이 아니라 WebSocket 연결 위에서 돈다. 이때는 연결을 맺을 때 보내는 `connectionParams`에서 토큰을 꺼내 context를 만든다. graphql-ws라면 `useServer`의 `context` 옵션이 그 자리다. 연결은 몇 시간씩 살아 있으니 토큰이 만료되거나 권한이 빠져도 연결은 계속 이벤트를 받는다. 이 문제는 뒤에서 다시 본다.

## 리졸버에서 막았는데 다른 길로 들어왔다

가장 먼저 떠오르는 방법은 `order(id)` 리졸버 안에서 주인을 확인하는 것이다.

```js
order: ({ id }, ctx) => {
  const o = db.orders.get(fromGlobalId(id));
  if (o && o.ownerId !== ctx.viewer.id) throw new GraphQLError("FORBIDDEN");
  return o;
},
```

스키마에는 Relay 방식의 `node(id: ID!)` 필드도 있다. 화면이 어떤 객체든 ID 하나로 다시 불러올 수 있게 해 주는 관례라서 클라이언트 라이브러리(특히 Relay)가 많이 쓴다. ID는 `"Order:o2"`를 Base64로 바꾼 `T3JkZXI6bzI=`다. kim으로 로그인한 채 lee의 주문 `o2`를 두 길로 물어봤다.

```graphql
{ order(id: "T3JkZXI6bzI=") { total } }
{ node(id: "T3JkZXI6bzI=") { ... on Order { total owner { name } } } }
{ orders { total } }
```

```text
# order(id)
{"errors":[{"message":"FORBIDDEN","locations":[{"line":1,"column":3}],"path":["order"]}],"data":{"order":null}}
# node(id)
{"data":{"node":{"total":990000,"owner":{"name":"lee"}}}}
# orders
{"data":{"orders":[{"total":12000},{"total":990000},{"total":4500}]}}
```

`order`는 막혔다. 같은 주문을 `node`로 물으니 99만 원과 주인 이름까지 그대로 나온다. 전체 주문 목록 `orders`에도 남의 주문이 섞여 있다. 검사를 `order` 리졸버에만 넣었기 때문이다. 객체 ID를 바꿔 넣어 남의 객체를 꺼내는 이 취약점을 OWASP API Security Top 10은 1번(BOLA, Broken Object Level Authorization)으로 꼽는다. GraphQL에서는 `node`가 있으니 이게 특히 쉽다. 스키마의 모든 타입을 ID 하나로 꺼낼 수 있는 만능 입구라서다.

Base64는 암호화가 아니다. `T3JkZXI6bzI=`를 디코딩하면 `Order:o2`가 나오고, 숫자를 하나 바꿔 다시 인코딩하면 남의 ID가 된다. ID를 UUID로 바꾸면 추측은 어려워지지만, 목록·알림·공유 링크로 ID가 한 번 새면 똑같다. ID를 숨기는 건 방어가 아니다.

`Order`에 닿는 길은 생각보다 많다. 아래 그림에서 점이 흐르는 화살표 하나하나가 리졸버 하나다. 리졸버에 검사를 넣는 방식이라면 이 화살표마다 같은 `if`가 있어야 하고, 하나라도 빠지면 그 길로 샌다.

## 검사를 업무 계층으로 내린다

graphql.org의 공식 문서도 인가 로직을 리졸버가 아니라 업무 로직 계층(business logic layer)에 두라고 권한다. 리졸버는 "어느 함수를 부를지"만 알고, "이 사람이 이 주문을 볼 수 있나"는 주문을 꺼내는 함수 하나가 책임진다. 그러면 위 그림의 화살표가 몇 개든 모두 같은 자물쇠를 지난다.

```js
// 주문을 꺼내는 길은 이 클래스 하나뿐이다
class OrderService {
  constructor(viewer) { this.viewer = viewer; }

  async get(id) {
    const o = await db.orders.findById(id);
    if (!o || !canReadOrder(this.viewer, o)) return null; // 못 보면 없는 것처럼
    return o;
  }

  async listForUser(userId) {
    // 걸러 내기는 쿼리 안에서. 가져온 뒤에 거르지 않는다
    return db.orders.find({ ownerId: userId, visibleTo: this.viewer });
  }
}

// 리졸버는 서비스만 부른다. 여기에는 if가 없다
const resolvers = {
  Query: {
    order: (_, { id }, ctx) => ctx.orders.get(fromGlobalId(id).id),
    node:  (_, { id }, ctx) => loadNode(ctx, fromGlobalId(id)), // 타입에 맞는 서비스로 보낸다
  },
  User: { orders: (user, _, ctx) => ctx.orders.listForUser(user.id) },
};
```

같은 세 요청을 이 구조로 다시 보냈다.

```text
# order(id)
{"data":{"order":null}}
# node(id)
{"data":{"node":null}}
# orders
{"data":{"orders":[{"total":12000},{"total":4500}]}}
```

세 길이 모두 막혔다. `orders`에는 kim의 주문 두 건만 남았다. 리졸버 코드는 한 줄도 판정을 하지 않는다.

이렇게 두면 좋은 점이 하나 더 있다. 같은 업무 계층을 REST 엔드포인트, 배치 작업, 관리자 도구가 함께 쓴다. 인가 규칙이 GraphQL 스키마 안에만 있으면 REST로 같은 데이터를 내보내는 순간 규칙을 다시 짜야 하고, 둘이 조금씩 어긋난다. [헥사고날 아키텍처](/posts/hexagonal-architecture)식으로 말하면 GraphQL은 바깥 어댑터 하나일 뿐이고, 규칙은 안쪽에 있어야 한다.

판정 함수 자체는 순수 함수로 떼어 두면 테스트하기 쉽다. 운영자는 모두, 주문한 사람은 자기 것, 가게 직원(`STAFF`)은 자기 가게 주문을 볼 수 있는 규칙을 직접 써 보자.

## 필드 하나만 가려야 할 때

객체는 볼 수 있지만 필드 일부는 가려야 할 때가 있다. 다른 사용자의 이름은 보여도 이메일은 본인과 운영자만 봐야 하는 경우다. 이건 객체 단위가 아니라 필드 단위 인가다. kim이 lee를 `node`로 꺼내 이름과 이메일을 물었다.

```text
{"errors":[{"message":"FORBIDDEN","locations":[{"line":1,"column":49}],"path":["node","email"],"extensions":{"code":"FORBIDDEN"}}],"data":{"node":{"name":"lee","email":null}}}
```

`name`은 그대로 오고 `email` 자리만 `null`이 됐다. `errors`의 `path`가 `["node","email"]`이라 클라이언트는 어느 필드가 왜 비었는지 안다. GraphQL의 부분 실패 덕분이다.

여기서 스키마 설계가 중요해진다. 이 데모의 `email`은 `String`(null 가능)이다. 만약 `String!`(null 불가)으로 선언했다면 어떻게 될까. 목록 `users: [User!]!`에서 두 번째 사용자의 `email`이 막히도록 해 봤다.

```text
{"errors":[{"message":"FORBIDDEN","locations":[{"line":1,"column":16}],"path":["users",1,"email"]}],"data":null}
```

`data`가 통째로 `null`이 됐다. null이 될 수 없는 필드에서 에러가 나면 그 null이 null을 허용하는 가장 가까운 부모까지 올라가는데, `User!`, `[User!]!`가 모두 null 불가라 루트까지 올라간 것이다. 이메일 하나 때문에 kim 자신의 정보까지 사라진다. 권한에 따라 비어 있을 수 있는 필드는 null 가능으로 선언한다. 이 전파 규칙은 [GraphQL 기초](/posts/graphql-basics)의 "에러가 나도 200이 온다"에 자세히 있다.

필드 단위 판정도 업무 계층에 둘 수 있다. 서비스가 객체를 돌려줄 때 볼 수 없는 필드를 미리 지운 "보기 모델"을 만들거나, 서비스에 `canSeeEmail(viewer, user)` 같은 함수를 두고 필드 리졸버가 그걸 부른다. 리졸버에 규칙을 직접 쓰지 않는다는 원칙은 같다.

## 디렉티브로 스키마에 적으면

규칙을 스키마에서 바로 보이게 하고 싶어서 `@auth` 디렉티브를 쓰는 팀이 많다. 스키마를 훑으며 디렉티브가 붙은 필드의 리졸버를 감싸는 방식이다. graphql-tools의 `mapSchema`가 흔히 쓰이고, 원리는 아래처럼 단순하다.

```graphql
directive @auth(requires: Role = USER) on FIELD_DEFINITION | OBJECT
enum Role { USER ADMIN }

type SalesReport @auth(requires: ADMIN) { revenue: Int! }
type Query {
  order(id: ID!): Order @auth          # 로그인만 하면 된다
  report: SalesReport                  # 타입에 붙은 규칙을 따른다
  stats: SalesReport @auth(requires: ADMIN)
}
```

```js
// 서버가 뜰 때 한 번: @auth가 붙은 필드의 resolve를 감싼다
for (const field of allFields(schema)) {
  const req = authOf(field) ?? authOf(field.parentType);
  if (!req) continue;
  const inner = field.resolve ?? defaultFieldResolver;
  field.resolve = (src, args, ctx, info) => {
    if (!ctx.viewer) throw new GraphQLError("UNAUTHENTICATED", { extensions: { code: "UNAUTHENTICATED" } });
    if (rank[ctx.viewer.role] < rank[req]) throw new GraphQLError("FORBIDDEN", { extensions: { code: "FORBIDDEN" } });
    return inner(src, args, ctx, info);
  };
}
```

```text
anon order  {"errors":[{"message":"UNAUTHENTICATED","locations":[{"line":1,"column":3}],"path":["order"],"extensions":{"code":"UNAUTHENTICATED"}}],"data":{"order":null}}
user order  {"data":{"order":{"total":990000}}}
user stats  {"errors":[{"message":"FORBIDDEN","locations":[{"line":1,"column":3}],"path":["stats"],"extensions":{"code":"FORBIDDEN"}}],"data":{"stats":null}}
user report {"errors":[{"message":"FORBIDDEN","locations":[{"line":1,"column":12}],"path":["report","revenue"],"extensions":{"code":"FORBIDDEN"}}],"data":{"report":null}}
```

로그인 여부와 역할은 잘 막는다. `report`처럼 타입에 붙인 규칙은 그 타입에 닿는 모든 길에 적용되니, 필드에만 붙이는 것보다 새는 길이 적다. 그런데 둘째 줄을 보자. 일반 사용자가 남의 주문을 `order`로 꺼냈는데 99만 원이 그대로 나왔다. 디렉티브는 "이 사람이 USER 역할인가"까지만 안다. "이 주문이 이 사람 것인가"는 주문을 DB에서 꺼내 봐야 알 수 있고, 그건 디렉티브가 볼 수 없는 데이터다.

`@auth(owner: "ownerId")`처럼 디렉티브에 소유 필드 이름을 넣는 방식도 있지만, 금세 "같은 가게 직원이면", "공유받은 사람이면" 같은 조건이 붙으면서 스키마 언어로 작은 정책 언어를 다시 만드는 꼴이 된다. 그래서 디렉티브는 거친 그물(로그인 필요, 운영자 전용, 특정 스코프 필요)로 쓰고, 객체 단위 판정은 업무 계층에 둔다. 둘을 같이 쓰면 스키마만 봐도 대략의 규칙이 보이고, 세밀한 규칙은 한곳에서 테스트된다.

Federation을 쓰면 Apollo Router 같은 라우터가 `@authenticated`, `@requiresScopes` 같은 디렉티브를 읽고 하위 그래프로 보내기 전에 권한 없는 필드를 걸러 내기도 한다. 이것도 역할·스코프 같은 거친 그물이다. 하위 서비스가 객체 소유를 다시 확인해야 한다는 점은 같다. 라우터를 거치지 않고 하위 서비스에 직접 닿는 길이 있다면 더 그렇다.

## 목록과 연결에서 새는 것

단건은 막아도 목록에서 새는 경우가 많다. 목록을 먼저 잘라 온 뒤 권한 없는 것을 거르면 페이지 크기가 들쭉날쭉하고 남의 데이터 양이 드러난다. 이 부분은 [인증과 인가](/posts/authn-vs-authz)의 "목록과 검색에도 인가가 필요하다"와 같다. 인가 조건은 SQL `WHERE` 안으로 넣는다.

GraphQL에는 목록이 새는 자리가 몇 군데 더 있다.

- Relay 방식 연결(connection)의 `totalCount`. 목록은 걸렀는데 개수는 전체 테이블에서 세면 "이 가게 주문이 1,284건"이라는 정보가 샌다. 개수도 같은 조건으로 센다.
- `pageInfo.hasNextPage`와 커서. 커서 안에 내부 ID나 정렬 값이 평문으로 들어 있으면 그 값을 바꿔 다른 범위를 훑을 수 있다. 커서를 받아도 조건은 서버가 다시 붙인다.
- 같은 목록이 여러 부모 아래에 있는 경우. `me.orders`, `user(id).orders`, `shop.orders`는 같은 주문 목록을 다른 각도로 보여 주는데, 리졸버가 셋이면 필터도 셋이 된다. 서비스의 목록 함수 하나가 viewer를 받아 조건을 붙이게 한다.
- 검색과 집계. `search(text)`가 여러 타입을 섞어 돌려주는 유니온이라면 타입마다 판정이 필요하다. 매출 합계처럼 개별 행이 안 보이는 집계도 남의 값이 섞이면 새는 것이다.

## 없는 것과 못 보는 것을 같은 모양으로

남의 주문을 물었을 때 `FORBIDDEN` 에러를 줄지, 그냥 `null`을 줄지도 정해야 한다. 앞의 리졸버 방식은 `FORBIDDEN`을, 업무 계층 방식은 `null`을 돌려줬다.

`FORBIDDEN`은 친절하지만 정보를 준다. 없는 ID를 물으면 `null`, 남의 ID를 물으면 `FORBIDDEN`이 오면, 공격자는 ID를 바꿔 가며 "존재하는 주문"만 골라낼 수 있다. REST에서 남의 객체에 403 대신 404를 주는 것과 같은 이유로, 객체를 읽는 쿼리는 못 보는 것을 없는 것과 같은 모양(`null`)으로 돌려주는 편이 안전하다.

반대로 바꾸기(mutation)는 조용히 넘어가면 안 된다. 남의 주문을 `cancelOrder`로 취소하려 했는데 `null`만 오면 클라이언트는 성공인지 실패인지 모른다. 이때는 에러를 분명히 준다. 존재 여부를 숨기고 싶다면 "없음"과 "권한 없음"을 같은 `NOT_FOUND` 코드로 묶는다.

에러 메시지에도 주의한다. 개발 중에는 `"User u2 cannot read order o2 (owner u2, shop s1)"` 같은 메시지가 편하지만, 운영에서 그대로 나가면 내부 ID와 규칙이 드러난다. 클라이언트에는 `extensions.code`만 정해진 값(`UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`)으로 보내고, 자세한 이유는 서버 로그에 operationName, viewer, 대상 ID와 함께 남긴다. Apollo Server는 `formatError` 훅에서 이 정리를 한다.

## DataLoader 캐시가 권한을 넘는다

GraphQL 서버는 N+1을 막으려고 DataLoader를 거의 반드시 쓴다. 이 로더는 키별로 결과를 캐시한다. 로더를 요청마다 새로 만들어야 한다는 이야기는 [GraphQL 기초](/posts/graphql-basics)에서 했는데, 인가와 엮이면 왜 그래야 하는지가 더 분명해진다. 서버가 뜰 때 로더를 하나만 만들고, 배치 함수 안에서 "지금 요청한 사람" 기준으로 판정하도록 짠 코드를 돌려 봤다.

```js
// 잘못된 예: 전역 로더 하나, 배치 함수가 그때그때의 viewer로 판정
const globalLoader = createLoader(async (ids) =>
  ids.map((id) => (canReadOrder(currentViewer, orders[id]) ? orders[id] : null)));
```

```text
admin   -> {"id":"o2","ownerId":"u2","total":990000}
u1(전역) -> {"id":"o2","ownerId":"u2","total":990000}
u1(요청별) -> null
```

운영자가 먼저 `o2`를 읽자 결과가 로더 캐시에 남았다. 이어서 kim이 같은 키를 물으니 배치 함수는 다시 불리지 않고 캐시에 있던 99만 원짜리 주문이 그대로 나갔다. 판정이 캐시 앞이 아니라 캐시 안쪽에 있었기 때문이다. 요청마다 로더를 만들고 viewer를 묶어 두면 셋째 줄처럼 `null`이 나온다.

같은 함정이 다른 캐시에도 있다. 응답 캐시나 Redis에 리졸버 결과를 넣을 때 캐시 키에 viewer(또는 권한 범위)가 빠지면, 운영자가 본 화면이 일반 사용자에게 나간다. 공용 캐시에는 누구에게나 같은 값만 넣고, 사람마다 다른 값은 판정을 통과한 뒤에 조립한다.

## 권한 확인도 N+1이 된다

판정을 업무 계층으로 내리면 다른 비용이 생긴다. 가게 직원이 주문 50건을 볼 때, 주문마다 "이 직원이 이 가게 소속인가"를 묻는다면 판정 하나가 DB 조회 하나다. 리졸버의 N+1과 똑같은 모양이 인가 쪽에서 다시 생긴다. 직원 `st1`이 가게 세 곳에 소속돼 있고, 주문 50건이 가게 10곳에 흩어져 있는 상황을 재 봤다. 조회마다 2ms를 쉰다.

```js
// 주문마다 소속을 묻는다
await Promise.all(orders.map((o) => db.isMember(viewer.id, o.shopId)));

// 같은 틱의 가게 ID를 모아 한 번에 묻는다 (viewer에 묶인 요청별 로더)
const member = createLoader((shopIds) => db.membershipsOf(viewer.id, shopIds));
await Promise.all(orders.map((o) => member.load(o.shopId)));
```

```text
no loader : visible=15 db calls=50
loader    : visible=15 db calls=1
```

결과는 같고 조회는 50번에서 1번이 됐다. 같은 가게 ID는 로더 캐시가 합치고, 서로 다른 가게 10곳은 배치 함수 한 번으로 묻는다. 권한 판정에 필요한 데이터(소속, 공유 목록, 역할)도 데이터 로딩과 똑같이 배치로 가져와야 한다. 앞 절의 함정을 피하려고 이 로더도 viewer에 묶어 요청마다 만든다.

목록이라면 더 좋은 방법이 있다. 판정을 객체마다 하지 말고 조건으로 바꿔 쿼리에 넣는 것이다.

```sql
-- 직원이 볼 수 있는 주문만, 개수도 같은 조건으로
SELECT o.*
FROM orders o
JOIN shop_members m ON m.shop_id = o.shop_id AND m.user_id = $1
ORDER BY o.created_at DESC
LIMIT 20;
```

이렇게 하면 판정 함수 `canReadOrder`와 SQL 조건이라는 같은 규칙이 두 벌 생긴다. 둘이 어긋나지 않게, 같은 테스트 데이터로 "목록에 나온 주문은 모두 `canReadOrder`가 true"인지 확인하는 테스트를 하나 둔다. 규칙이 많아져 두 벌 관리가 버거우면 OpenFGA 같은 관계 기반 인가 서버가 "이 사람이 볼 수 있는 객체 ID 목록"을 돌려주는 기능(ListObjects)을 쓰는 방법도 있다. 관계 기반 모델 자체는 [인증과 인가](/posts/authn-vs-authz)의 "관계를 따라가는 인가"에 있다.

## 허용 목록과 introspection 끄기는 인가가 아니다

자사 앱만 쓰는 API라면 빌드 때 뽑은 쿼리만 받는 trusted documents(persisted query 허용 목록)를 많이 건다. 처음 보는 쿼리는 실행조차 안 되니 공격면이 크게 줄어든다. 그래도 인가를 대신하지는 못한다.

허용 목록에 들어 있는 쿼리 `OrderDetail($id: ID!)`는 변수만 바꿔 보낼 수 있다. 앱이 원래 쓰던 쿼리에 lee의 주문 ID를 넣으면 허용 목록은 통과한다. 막는 건 여전히 서비스의 `canReadOrder`다. introspection을 끄는 것도 마찬가지로, 스키마를 덜 보여 줄 뿐 이미 아는 필드를 묻는 요청은 막지 못한다.

그래서 이 장치들은 "이상한 쿼리"를 막는 층이고, 인가는 "정상적인 쿼리에 남의 ID를 넣은 요청"을 막는 층이다. 둘은 서로를 대신하지 않는다. 보안 점검 보고서에서 "introspection이 켜져 있다"는 지적만 고치고 끝내는 경우가 있는데, 그 아래 BOLA가 남아 있으면 실제 피해는 그대로다.

## 인가 구멍을 찾을 때

GraphQL API의 인가를 점검할 때는 스키마에서 출발한다.

1. 민감한 타입(주문, 결제, 사용자 개인 정보)마다 그 타입을 돌려주는 필드를 모두 찾는다. SDL에서 `: Order`, `[Order`를 검색하면 되고, `node`와 유니온·인터페이스도 빠뜨리지 않는다. 앞의 그림처럼 길이 몇 개인지 먼저 센다.
2. 계정 두 개(A, B)를 만들어 B의 객체 ID로 A 토큰을 써서 길마다 물어본다. Global ID라면 디코딩해서 타입과 원래 ID를 바꿔 다시 인코딩해 본다.
3. 응답에서 `data`가 비었는지만 보지 말고 `errors`의 `code`, `totalCount`, `hasNextPage` 같은 부수 정보도 본다.
4. 운영 로그는 operationName과 함께 `FORBIDDEN`, `NOT_FOUND` 비율을 본다. 한 사용자가 짧은 시간에 서로 다른 ID로 `NOT_FOUND`를 수백 번 받는다면 ID를 훑고 있는 것이다. 엔드포인트가 하나라 URL별 지표로는 이게 안 보인다.

이 점검을 CI에 넣을 수도 있다. "B의 객체를 A로 읽으면 null"이라는 통합 테스트를 타입마다 하나씩 두면, 누군가 새 필드를 붙이면서 서비스를 거치지 않고 DB를 직접 부를 때 테스트가 깨진다.

## 자물쇠는 방문에 단다

GraphQL은 주소가 하나라 문 앞(게이트웨이)에서 할 수 있는 일이 인증과 거친 제한 정도다. 같은 객체에 닿는 길이 여러 개라서 리졸버에 검사를 흩어 두면 새 길이 생길 때마다 샌다. 판정은 객체를 꺼내는 업무 계층 한곳에 두고, 디렉티브는 역할 같은 거친 그물로만 쓴다. 그다음 남는 틈은 목록의 개수, 캐시, 쓰기 입력, 오래 사는 구독이다. 쿼리 자체를 제한하는 깊이·비용 제한과 introspection 이야기는 [GraphQL 기초](/posts/graphql-basics)에, 클라이언트 쪽 캐시가 권한 경계와 엮이는 이야기는 [GraphQL 클라이언트 캐시](/posts/graphql-client-caching)에 이어진다.

## 면접에서 나올 만한 질문

### GraphQL에서는 왜 게이트웨이에서 권한을 막기 어렵나요?

모든 요청이 `POST /graphql` 하나로 들어오고, 무엇을 하려는지는 본문의 쿼리 문자열 안에 있기 때문이다. REST처럼 경로와 메서드로 "관리자 API만 막기" 같은 규칙을 걸 수 없다. 게이트웨이에서는 인증과 요청 크기·비용 같은 거친 제한만 하고, 객체와 필드 단위 인가는 서버 안쪽에서 한다.

### 인가 로직은 어디에 두는 게 좋나요?

리졸버가 아니라 업무 로직 계층에 둔다. GraphQL은 같은 타입에 닿는 길이 여러 개(`order`, `node`, `user.orders`, 검색, 뮤테이션 결과)라서 리졸버마다 검사를 넣으면 하나만 빠져도 샌다. 객체를 꺼내는 서비스 함수가 viewer를 받아 판정하면 어느 길로 오든 같은 검사를 지난다. 같은 규칙을 REST나 배치 작업이 재사용할 수 있다는 장점도 있다.

### node 인터페이스가 왜 보안상 위험한가요?

스키마의 어떤 타입이든 ID 하나로 꺼낼 수 있는 만능 입구라서다. 특정 필드에만 소유자 검사를 넣어 두면 같은 객체를 `node(id)`로 물어서 우회할 수 있고, 데모에서도 `order`는 막혔는데 `node`로는 남의 주문이 그대로 나왔다. Global ID는 보통 `"Order:o2"`를 Base64로 바꾼 것이라 디코딩해서 바꾸기도 쉽다. 그래서 `node`도 타입별 서비스로 보내 같은 판정을 받게 한다.

### @auth 같은 스키마 디렉티브만으로 충분하지 않은 이유는요?

디렉티브는 요청한 사람의 역할이나 스코프는 알지만, 대상 객체가 그 사람 것인지는 모른다. 소유 여부는 객체를 DB에서 꺼내야 알 수 있기 때문이다. 데모에서도 `@auth`가 붙은 `order`로 일반 사용자가 남의 주문을 꺼냈다. 디렉티브는 로그인 필요, 운영자 전용 같은 거친 규칙에 쓰고, 객체 단위 판정은 업무 계층에 둔다.

### 권한이 없을 때 null을 주나요, 에러를 주나요?

읽기는 보통 `null`로 없는 것과 같은 모양을 준다. `FORBIDDEN`을 주면 ID를 바꿔 가며 존재하는 객체를 골라낼 수 있기 때문이다. 쓰기는 실패를 분명히 알려야 하니 에러를 주되, 없음과 권한 없음을 같은 `NOT_FOUND` 코드로 묶을 수 있다. 권한 때문에 비어 있을 수 있는 필드는 null 가능으로 선언해야 에러가 부모로 번져 응답 전체가 `null`이 되지 않는다.

### DataLoader와 인가를 같이 쓸 때 주의할 점은요?

로더를 요청마다 새로 만들고, 판정은 캐시에서 꺼낸 뒤가 아니라 viewer에 묶인 로더나 서비스에서 한다. 전역 로더 하나를 쓰면 운영자가 먼저 읽은 객체가 캐시에 남아 다음 사용자의 요청에 판정 없이 나간다. 응답 캐시나 Redis에 결과를 넣을 때도 사람마다 다른 값이라면 캐시 키에 권한 범위를 넣어야 한다.

### 목록 필드에서는 무엇을 더 확인하나요?

필터를 가져온 뒤가 아니라 쿼리 조건에 넣고, `totalCount`와 `hasNextPage`도 같은 조건으로 계산한다. 목록은 걸렀는데 개수는 전체에서 세면 남의 데이터 양이 드러난다. 같은 목록이 `me.orders`, `user.orders`, `shop.orders`처럼 여러 부모 아래 있으면 리졸버마다 필터를 쓰지 말고 서비스의 목록 함수 하나가 조건을 붙이게 한다.

### 구독(subscription)의 인가는 어떻게 하나요?

두 번 한다. 구독을 시작할 때 그 대상을 볼 수 있는지 확인하고, 이벤트를 내보낼 때마다 받는 사람 기준으로 다시 거른다. 인증은 WebSocket 연결을 맺을 때 `connectionParams`의 토큰으로 하고, 연결이 오래 살아 있으니 토큰 만료 시각에 끊거나 재인증하게 한다. 그러지 않으면 권한이 빠진 사람도 열려 있는 연결로 계속 이벤트를 받는다.
