결제 화면에는 다섯 부품이 있다. 배송 방법 선택, 주소 입력, 쿠폰 입력, 금액 요약, 결제 버튼이다. 처음엔 단순했다. 쿠폰을 넣으면 금액 요약을 고친다. 그런데 요구가 붙을 때마다 부품끼리 서로를 부르기 시작했다. 새벽 배송은 수도권 주소에서만 되니 주소 입력이 배송 선택을 부르고, 배송비가 바뀌니 배송 선택이 금액 요약을 부르고, 금액이 0원이 되면 결제 버튼 문구가 바뀌니 금액 요약이 결제 버튼을 부른다.

```ts
declare class PriceSummary { recalc(): void }
declare class PayButton { refresh(): void }
declare class ShippingSelect { readonly method: string }

// 쿠폰 입력이 세 부품을 직접 안다
class CouponInput {
  constructor(
    private readonly summary: PriceSummary,
    private readonly pay: PayButton,
    private readonly shipping: ShippingSelect, // 새벽 배송엔 쿠폰을 못 쓴다는 규칙 때문에 추가됐다
  ) {}
  enter(code: string) {
    if (this.shipping.method === "dawn") return;
    // ... 쿠폰 검사
    this.summary.recalc();
    this.pay.refresh();
  }
}
```

이제 쿠폰 입력을 다른 화면(장바구니)에서 다시 쓰려면 금액 요약과 결제 버튼과 배송 선택을 같이 가져가야 한다. "새벽 배송이면 쿠폰 불가" 규칙은 쿠폰 입력 안에 있고, "주소가 바뀌면 새벽 배송 해제" 규칙은 주소 입력 안에 있다. 결제 화면의 규칙이 다섯 파일에 흩어진 것이다. 이번 글은 부품들이 서로를 부르지 않고 가운데 객체 하나에만 알리게 하는 중재자(Mediator) 패턴이다.

## 부품은 알리기만 한다

부품 쪽 코드는 짧아진다. 자기 값을 바꾸고 중재자에게 사건을 알린다. 다른 부품의 이름은 나오지 않는다.

```ts
type CheckoutEvent =
  | { type: "shipping:changed"; method: "standard" | "dawn" }
  | { type: "address:changed"; zip: string }
  | { type: "coupon:entered"; code: string }
  | { type: "total:changed"; total: number };

interface Mediator {
  notify(event: CheckoutEvent): void;
}

class ShippingSelect {
  method: "standard" | "dawn" = "standard";
  constructor(private readonly mediator: Mediator) {}
  choose(method: "standard" | "dawn") {
    this.method = method;
    this.mediator.notify({ type: "shipping:changed", method });
  }
  disableDawn(reason: string) {
    this.method = "standard"; // 중재자가 시킨 변경은 다시 알리지 않는다
    console.log(`  [shipping] 새벽 배송 끔 (${reason})`);
  }
}

class AddressForm {
  zip = "";
  constructor(private readonly mediator: Mediator) {}
  input(zip: string) {
    this.zip = zip;
    this.mediator.notify({ type: "address:changed", zip });
  }
}

class CouponInput {
  discount = 0;
  constructor(private readonly mediator: Mediator) {}
  enter(code: string) {
    this.mediator.notify({ type: "coupon:entered", code });
  }
  show(message: string) {
    console.log(`  [coupon] ${message}`);
  }
}

class PriceSummary {
  total = 0;
  constructor(private readonly mediator: Mediator) {}
  render(subtotal: number, shippingFee: number, discount: number) {
    const next = subtotal + shippingFee - discount;
    console.log(`  [summary] ${subtotal} + 배송 ${shippingFee} - 할인 ${discount} = ${next}`);
    if (next === this.total) return; // 바뀌지 않았으면 알리지 않는다
    this.total = next;
    this.mediator.notify({ type: "total:changed", total: next });
  }
}

class PayButton {
  enabled = false;
  setEnabled(enabled: boolean, label: string) {
    this.enabled = enabled;
    console.log(`  [pay] ${enabled ? "활성" : "비활성"} · ${label}`);
  }
}
```

## 규칙은 중재자 한 파일에

중재자는 부품을 만들고 들고 있다가, 사건이 오면 규칙에 따라 부품들을 움직인다.

```ts
const DAWN_ZIPS = /^0[0-9]|^1[0-8]/; // 새벽 배송 가능 우편번호 앞자리 (예시 규칙)

class CheckoutMediator implements Mediator {
  readonly shipping = new ShippingSelect(this);
  readonly address = new AddressForm(this);
  readonly coupon = new CouponInput(this);
  readonly summary = new PriceSummary(this);
  readonly pay = new PayButton();
  constructor(private readonly subtotal: number) {}

  notify(event: CheckoutEvent) {
    console.log(`mediator ← ${event.type}`);
    switch (event.type) {
      case "address:changed":
        if (this.shipping.method === "dawn" && !DAWN_ZIPS.test(event.zip)) this.shipping.disableDawn("지원 지역 아님");
        return this.recalc();
      case "shipping:changed":
        return this.recalc();
      case "coupon:entered": {
        const ok = event.code === "WELCOME10" && this.subtotal >= 30000;
        this.coupon.discount = ok ? Math.floor(this.subtotal * 0.1) : 0;
        this.coupon.show(ok ? "10% 할인 적용" : "쓸 수 없는 쿠폰");
        return this.recalc();
      }
      case "total:changed":
        return this.pay.setEnabled(this.address.zip !== "" && event.total > 0, `${event.total}원 결제`);
    }
  }

  private recalc() {
    const fee = this.shipping.method === "dawn" ? 4000 : this.subtotal >= 50000 ? 0 : 3000;
    this.summary.render(this.subtotal, fee, this.coupon.discount);
  }
}

const checkout = new CheckoutMediator(42000);
checkout.shipping.choose("dawn");
checkout.address.input("48058"); // 수도권이 아닌 우편번호
checkout.coupon.enter("WELCOME10");
```

## 알림이 다시 알림을 부를 때

위 코드의 `PriceSummary`에는 "값이 같으면 알리지 않는다"는 한 줄이 있다. 이 줄을 지우고, 중재자가 총액이 바뀌면 무료 배송 기준을 다시 보도록 `recalc()`를 한 번 더 부르게 바꿔 봤다. 그럴듯한 요구다.

```text
RangeError: Maximum call stack size exceeded after 2673 notify calls
```

금액 요약이 알리고, 중재자가 다시 계산하고, 금액 요약이 또 알리는 고리가 생겼다. 중재자 구조에서 가장 흔한 사고다. 모든 알림이 한곳으로 모이니 고리를 만들기도 쉽다. 아래 그림에서 마지막 단계가 고리가 끊기는 지점이다.

막는 방법은 몇 가지가 있고 보통 함께 쓴다. 값이 실제로 바뀌었을 때만 알린다. 중재자가 시킨 변경(위의 `disableDawn`)은 다시 알리지 않는다. 그래도 불안하면 중재자에 처리 중 표시를 두고, 처리 중에 들어온 사건은 큐에 쌓았다가 지금 처리가 끝난 뒤 차례로 처리한다. React도 비슷한 장치를 둔다. 같은 값으로 `setState`하면(`Object.is`로 비교한다) 다시 그리지 않고 넘어가고, 렌더링 도중 상태를 계속 바꾸는 고리는 일정 횟수에서 `Too many re-renders` 에러로 끊는다.

## 이미 쓰고 있는 중재자

HTML의 라디오 버튼이 가장 작은 예다. `name`이 같은 라디오 버튼은 서로를 모르는데, 하나를 고르면 나머지가 풀린다. 그 규칙은 브라우저가 같은 이름의 그룹을 묶어 처리한다. Java Swing은 이것을 `ButtonGroup`이라는 객체로 드러내 놓았다. 버튼들을 그룹에 넣으면 그룹이 "하나만 선택" 규칙을 맡는다.

React에서 "상태 끌어올리기"를 하면 부모 컴포넌트가 중재자가 된다. 형제 컴포넌트는 서로를 import하지 않고, `onChange` 콜백으로 부모에게 알리고 부모가 내려 준 props로 다시 그려진다. 위의 결제 화면을 React로 짜면 `CheckoutPage`가 상태와 규칙을 쥐고 다섯 자식에게 값과 콜백을 내려 주는 모양이 된다. 규칙이 커지면 `useReducer`의 리듀서 하나로 모은다. 리듀서의 `switch`가 위 `notify`의 `switch`와 거의 같다.

서버 쪽에도 있다. .NET의 MediatR은 `mediator.Send(new PlaceOrder(...))`로 요청을 보내면 그 요청을 처리할 핸들러를 찾아 연결해 준다. NestJS CQRS 모듈의 `CommandBus.execute()`도 같은 모양이다. 컨트롤러가 서비스를 직접 알지 않게 해 주지만, 이 둘은 규칙을 가진 중재자라기보다 요청을 이름으로 연결해 주는 배달부에 가깝다. 여러 서비스 사이에서는 사가의 오케스트레이터가 중재자 역할을 한다. 흐름을 중앙에서 쥘지 각 서비스가 이벤트에 반응하게 둘지는 [이벤트 기반 아키텍처 글](/posts/event-driven-architecture#흐름을-누가-쥐나)과 [사가 패턴 글](/posts/saga-pattern)에서 다뤘다.

## 이벤트 버스는 규칙 없는 중재자다

중재자를 만들 때 흔히 이렇게 짠다. 부품들이 중앙 이벤트 버스에 이벤트를 던지고, 다른 부품들이 그 버스를 구독한다. 이것도 부품끼리 서로를 모르니 그물은 사라진다. 그런데 규칙은 어디 있을까. 각 구독자 안에 흩어져 있다. "주소가 바뀌면 새벽 배송 해제"는 배송 선택의 구독 코드에, "쿠폰은 3만 원 이상"은 쿠폰 입력의 구독 코드에 있다. 처음 문제였던 "규칙이 다섯 파일에 흩어진" 상태로 돌아간다. 거기에 누가 무엇을 듣는지 코드만 봐서는 찾기 어려워진다.

[옵서버](/posts/pattern-observer)와 중재자의 차이가 여기서 갈린다. 옵서버의 주체(Subject)는 누가 듣는지, 듣고 무엇을 하는지 모르고 관심도 없다. 중재자는 부품들을 알고, 무엇이 무엇을 바꾸는지 결정한다. 그래서 둘을 함께 쓰는 경우가 많다. 부품은 옵서버 방식으로 사건을 알리고, 그 사건을 듣는 쪽은 중재자 하나뿐이며, 중재자가 규칙에 따라 부품을 부른다. 구독자가 여럿 붙기 시작하면 이름만 중재자인 이벤트 버스가 된다.

[퍼사드](/posts/pattern-facade#어댑터-중재자와-나란히-놓으면)와도 그림이 닮았는데, 퍼사드는 바깥에서 안으로 한 방향으로 흐르고 하위 시스템이 퍼사드를 모른다는 점이 다르다. 그 비교는 퍼사드 글에 정리했다.

## 중재자가 신 객체가 되는 길

중재자의 약점은 정직하다. 그물의 복잡도가 사라진 게 아니라 중재자 안으로 옮겨 왔다. 결제 화면에 규칙이 30개 붙으면 `notify`의 `switch`는 수백 줄이 되고, 모든 변경이 이 파일에서 충돌한다. 그때 쓰는 방법은 이렇다.

- 관심사별로 중재자를 나눈다. 배송 규칙과 할인 규칙이 서로 영향을 주지 않는다면 `ShippingRules`, `DiscountRules` 두 중재자로 쪼개고, 금액 요약은 둘의 결과만 받는다.
- 규칙 자체를 함수로 뺀다. 배송비 계산은 `shippingFee(method, subtotal)` 같은 순수 함수로, 결제 가능 여부는 `canPay(state)`로 둔다. 중재자는 사건을 받아 이 함수들을 순서대로 부르는 얇은 층이 된다. 순수 함수는 테스트하기도 쉽다.
- 화면에 단계가 있다면(주소 입력 → 결제 수단 → 확인) 단계별 규칙을 [상태 패턴](/posts/pattern-state)으로 나눈다.

중재자가 커지는 신호는 이렇다. `notify`에 `if (this.a.x && this.b.y && !this.c.z)` 같은 여러 부품을 동시에 보는 조건이 늘고, 사건 하나를 처리하는데 같은 부품을 두 번 부른다. 이때가 나눌 때다.

## 부품과 중재자를 따로 테스트한다

부품은 중재자 인터페이스만 알기 때문에 가짜 중재자로 테스트할 수 있다. 다른 부품을 하나도 만들지 않아도 된다.

```ts
const events: CheckoutEvent[] = [];
const fakeMediator: Mediator = { notify: (e) => events.push(e) };

const summary = new PriceSummary(fakeMediator);
summary.render(42000, 3000, 0);
summary.render(42000, 3000, 0); // 같은 값

console.assert(events.length === 1, "같은 총액이면 두 번 알리지 않는다");
console.assert(events[0].type === "total:changed");
```

중재자 테스트는 반대로 진짜 부품을 붙이고 사건 순서를 넣어 최종 상태를 본다. 위에서 돌린 시나리오 출력이 그대로 테스트의 기대값이 된다. 처음 구조에서는 쿠폰 입력 하나를 테스트하려 해도 금액 요약, 결제 버튼, 배송 선택을 모두 만들어 넣어야 했다.

## 면접에서 나올 만한 질문

### 중재자 패턴은 어떤 문제를 푸나요?

여러 객체가 서로를 직접 참조해 그물처럼 얽힌 문제를 푼다. 객체들은 중재자 하나만 알고 자기에게 일어난 일을 알리며, 누가 바뀌면 누구를 어떻게 바꿀지는 중재자가 정한다. 연결이 부품 수의 제곱에서 부품 수로 줄고, 흩어져 있던 상호작용 규칙이 한곳에 모여 부품을 다른 곳에서 다시 쓸 수 있게 된다.

### 중재자와 옵서버는 어떻게 다른가요?

옵서버의 주체는 누가 듣는지, 듣고 무엇을 하는지 모르고, 반응하는 로직은 구독자 각자에게 있다. 중재자는 참여하는 객체들을 알고 그 사이의 규칙을 직접 가진다. 실제로는 함께 쓰는 경우가 많아서, 부품은 이벤트로 알리고 그 이벤트를 듣는 쪽은 중재자 하나이며 중재자가 규칙대로 부품을 부른다.

### 이벤트 버스를 쓰면 중재자 패턴인가요?

부품끼리 서로를 모르게 한다는 점은 같지만, 버스가 규칙을 갖지 않으면 상호작용 규칙이 각 구독자 안으로 다시 흩어진다. 누가 무엇을 듣고 무엇을 바꾸는지 추적하기도 어려워진다. 규칙을 한곳에 모으고 싶다면 버스를 듣는 쪽을 중재자 하나로 두고 그 안에 규칙을 둔다.

### 중재자 패턴의 단점은 무엇이고 어떻게 다루나요?

복잡도가 사라지는 게 아니라 중재자로 옮겨 오기 때문에, 규칙이 늘면 중재자가 모든 걸 아는 신 객체가 된다. 관심사별로 중재자를 나누고, 배송비나 결제 가능 여부 같은 규칙은 순수 함수로 빼서 중재자를 얇게 유지한다. 화면에 단계가 있다면 단계별 규칙을 상태 패턴으로 나눈다.

### 중재자를 쓸 때 무한 루프는 왜 생기고 어떻게 막나요?

부품이 알리면 중재자가 다른 부품을 바꾸고, 그 부품이 또 알리는 고리가 생기기 때문이다. 실험에서는 값 비교 한 줄을 지우자 같은 총액 알림이 반복되어 2,673번 만에 호출 스택이 넘쳤다. 값이 실제로 바뀔 때만 알리고, 중재자가 시킨 변경은 다시 알리지 않으며, 필요하면 처리 중에 들어온 사건을 큐에 쌓았다가 순서대로 처리한다.

### 중재자와 퍼사드는 어떻게 다른가요?

둘 다 가운데 객체가 여럿과 연결되지만 방향이 다르다. 퍼사드는 바깥 클라이언트를 위한 단순한 입구이고, 하위 시스템은 퍼사드를 모르며 요청이 한 방향으로 흐른다. 중재자의 동료 객체들은 중재자를 알고 서로의 상호작용을 중재자를 거쳐 주고받는다.

### 실무에서 중재자를 본 예를 들어 주세요.

React에서 상태를 부모로 끌어올리면 부모 컴포넌트가 중재자가 된다. 형제는 서로를 모르고 콜백으로 부모에게 알리며 부모가 내려 준 props로 그려진다. 같은 name의 HTML 라디오 버튼과 Java Swing의 ButtonGroup은 "하나만 선택" 규칙을 맡는 중재자이고, 서비스 사이에서는 사가의 오케스트레이터가 흐름을 쥔 중재자 역할을 한다.
