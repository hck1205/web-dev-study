<EasyIntro>
  회원가입에서 이름과 이메일을 둘 다 틀렸는데 오류 메시지는 이름 것 하나만 뜨는 일이 있다. 두 검사를 그리고 기호로 이었는데, 앞 검사가 실패한 순간 뒤 검사는 아예 실행되지 않았기 때문이다. 이렇게 왼쪽만 보고 답이 정해지면 오른쪽을 건너뛰는 규칙을 단락 평가라고 부른다.

  알아 둘 점이 하나 더 있다. 이 연산자들은 참이나 거짓을 돌려주는 게 아니라 멈춘 자리에 있던 원래 값을 그대로 돌려준다. 그래서 숫자 0에서 멈추면 결과도 0이고, 그 0이 리액트 화면 구석에 그대로 찍히기도 한다.

  건너뛰는 성질은 비싼 계산이나 위험한 호출을 막는 데 일부러 쓰는 기능이지만, 꼭 실행돼야 하는 코드를 오른쪽에 두면 조용히 빠진다. 조건 자리에는 참과 거짓을 확실히 만들어 넣고, 기본값을 줄 때는 0이나 빈 문자열이 정상 값인지 먼저 생각한다.
</EasyIntro>

회원가입 폼에서 이름과 이메일을 둘 다 틀리게 넣고 제출했다. 화면에는 "이름을 입력하세요" 하나만 떴다. 이름을 고치고 다시 제출하자 그제야 이메일 오류가 나왔다. 검증 코드는 이렇게 생겼다.

```js
const errors = [];
function validateName(form) {
  if (!form.name) { errors.push("이름을 입력하세요"); return false; }
  return true;
}
function validateEmail(form) {
  if (!form.email.includes("@")) { errors.push("이메일 형식이 아닙니다"); return false; }
  return true;
}
const form = { name: "", email: "minji" };
const ok = validateName(form) && validateEmail(form);
console.log(ok, errors);

errors.length = 0;
const results = [validateName(form), validateEmail(form)];
console.log(results.every(Boolean), errors);
```

```text
false [ '이름을 입력하세요' ]
false [ '이름을 입력하세요', '이메일 형식이 아닙니다' ]
```

`&&`는 왼쪽이 `false`인 순간 오른쪽을 부르지 않는다. 결과만 놓고 보면 어차피 `false`라서 맞는 판단이다. 그런데 `validateEmail`은 값을 계산하는 함수가 아니라 오류 메시지를 쌓는 부수 효과도 가진 함수였다. 두 번째 방식처럼 모두 먼저 부르고 나서 결과를 합치면 오류가 둘 다 쌓인다.

이 글은 `&&`, `||`, `??`가 오른쪽을 언제 건너뛰는지, 그리고 결과로 무엇을 돌려주는지 따라간다. 그 두 가지를 알면 기본값 패턴, 가드, JSX의 조건부 렌더링, 훅 규칙 위반이 한 줄로 이어진다. 어떤 값이 falsy인지는 [truthy·falsy 글](/posts/js-truthy-falsy-typeof)에서, `??`와 `?.`의 자세한 규칙은 [옵셔널 체이닝 글](/posts/js-optional-chaining-nullish)에서 다뤘다. 출력은 Node 22와 React 19.3에서 실제로 돌린 결과다.

## 오른쪽은 필요할 때만 실행된다

단락 평가(short-circuit evaluation)는 왼쪽 값만으로 결과가 정해지면 오른쪽 식을 아예 평가하지 않는 규칙이다. `&&`는 왼쪽이 falsy면, `||`는 왼쪽이 truthy면, `??`는 왼쪽이 `null`도 `undefined`도 아니면 거기서 멈춘다. 전기 회로에서 전류가 짧은 길로 돌아가 버린다는 뜻의 "단락"에서 온 말이다.

이 규칙은 버그의 원인이기도 하지만 대개는 일부러 쓰는 기능이다. "로그인했으면 권한을 확인하고, 권한이 있으면 지운다"를 `isLoggedIn() && hasPermission() && remove()`로 쓰면 앞에서 실패할 때 뒤의 비싼 호출이나 위험한 호출이 일어나지 않는다. 디버그 로그도 같은 원리다.

```js
const DEBUG = false;
let stringified = 0;
const big = { rows: Array.from({ length: 3 }, (_, i) => i) };
DEBUG && console.log(JSON.stringify(big, () => { stringified++; }));
console.log("stringify 호출:", stringified);
```

```text
stringify 호출: 0
```

`DEBUG`가 꺼져 있으면 `JSON.stringify`가 한 번도 불리지 않았다. 함수 인자는 함수를 부르기 전에 모두 평가되니, `log(JSON.stringify(big))`처럼 썼다면 로그를 찍지 않더라도 직렬화 비용은 치렀을 것이다.

## 연산자가 돌려주는 것은 불리언이 아니다

두 번째 규칙이 더 자주 사람을 놀라게 한다. `&&`와 `||`는 `true`나 `false`를 돌려주지 않는다. 피연산자 중 하나를 그대로 돌려준다.

```js
console.log(0 || "기본", "" || null, "a" || "b");
console.log(1 && "둘째", 0 && "둘째", "a" && "" && "c");
console.log(null || undefined || 0);
console.log(typeof ("x" && 1), !!"x", Boolean(0));
```

```text
기본 null a
둘째 0 
0
number true false
```

`"" || null`은 `null`, `0 && "둘째"`는 `0`, `"a" && "" && "c"`는 빈 문자열이다. 둘째 줄 끝이 비어 보이는 이유다. 명세의 동작을 그대로 옮기면 이렇다. 왼쪽을 평가하고, 그 값을 ToBoolean으로 참·거짓만 판정한 다음, 멈출지 말지 정한다. 멈추면 왼쪽 값을, 안 멈추면 오른쪽을 평가해서 그 값을 돌려준다. ToBoolean은 판정에만 쓰이고 결과에는 들어가지 않는다.

## AND가 OR보다 먼저 묶인다

`&&`는 `||`보다 우선순위가 높다. 곱셈이 덧셈보다 먼저인 것과 같다. 그래서 `a || b && c`는 `a || (b && c)`다.

```js
console.log(true || false && false, (true || false) && false);
const a = "A", b = "B", c = "C";
console.log(a || b && c, (a || b) && c);
```

```text
true false
A C
```

`!`는 둘보다 더 높다. `!a && b`는 `(!a) && b`이고 `!(a && b)`와 다르다. 권한 검사에서 `!isAdmin && isOwner`를 `!(isAdmin && isOwner)`로 착각하면 반대 사람에게 버튼이 보인다. `??`는 이 둘과 괄호 없이 섞으면 아예 문법 오류다. 이유는 [옵셔널 체이닝 글](/posts/js-optional-chaining-nullish)에서 다뤘다. 실무에서는 우선순위를 외우기보다 `&&`와 `||`가 한 줄에 섞이면 괄호를 쓰는 편이 낫다. `no-mixed-operators` 린트 규칙(지금은 ESLint Stylistic 플러그인이 관리한다)이 이것을 강제한다.

## 기본값으로 쓸 때는 0을 조심한다

`||`가 첫 truthy를 돌려준다는 성질 때문에 기본값 패턴으로 오랫동안 쓰였다. `const port = process.env.PORT || 3000`은 환경 변수가 없거나 빈 문자열이면 3000을 쓴다. 이 경우에는 빈 문자열도 "없음"으로 보는 것이 맞으니 `||`가 정확하다.

반대로 `0`, `false`, `""`가 정상 값인 설정에서는 틀린다. `retries || 3`은 재시도를 끄려고 `0`을 넣은 사람의 뜻을 무시하고 3번 재시도한다. 이런 자리는 `??`로 바꾼다. 두 연산자가 어떤 값에서 갈리는지는 [옵셔널 체이닝 글](/posts/js-optional-chaining-nullish)에서 값별로 따라갔다.

논리 대입 연산자(ES2021)에도 같은 기준이 적용된다.

```js
let cfg = { retries: 0, name: "" };
cfg.retries ||= 3;
cfg.name ||= "익명";
console.log(cfg);
let user = { name: "  민지 " };
user &&= { ...user, name: user.name.trim() };
let nobody = null;
nobody &&= { ...nobody, name: "x" };
console.log(user, nobody);
```

```text
{ retries: 3, name: '익명' }
{ name: '민지' } null
```

`||=`는 `0`을 비었다고 보고 3으로 덮었다. `&&=`는 값이 있을 때만 바꿔서, `user`는 다듬어지고 `nobody`는 `null` 그대로 남았다. "있으면 손본다"를 한 줄로 쓰는 방법이다.

## 가드로 쓸 때 옵셔널 호출과 다른 점

`callback && callback()`은 옵셔널 체이닝이 생기기 전부터 쓰던 가드다. `callback?.()`과 비슷해 보이지만 판정 기준이 다르다.

```js
const onClose = 0;
console.log(onClose && onClose());
try { onClose?.(); } catch (e) { console.log(e.message); }
```

```text
0
onClose is not a function
```

`&&`는 falsy면 멈추니 `0`에서 멈추고 `0`을 돌려줬다. `?.`는 `null`과 `undefined`에서만 멈추니 `0`을 함수로 부르려다 터졌다. 콜백 prop처럼 "함수 아니면 undefined"가 보장된 값에는 `?.()`가 의도를 더 정확히 드러낸다. 결과 값을 쓰지 않는 문장 자리에서 `isValid && submit()`을 쓰면 ESLint `no-unused-expressions`가 경고한다. `allowShortCircuit` 옵션으로 허용할 수 있지만, 팀에서 읽기 쉬운 쪽은 대개 `if (isValid) submit()`이다.

## 배열 메서드도 중간에 멈춘다

`some`, `every`, `find`, `findIndex`, `includes`는 결과가 정해지는 순간 순회를 멈춘다. `some`은 `||`를, `every`는 `&&`를 배열 전체에 건 것과 같다.

```js
const seen = [];
const r = [3, 8, 12, 5].some((n) => (seen.push(n), n > 10));
console.log(r, seen);
const seen2 = [];
const r2 = [3, 8, 12, 5].every((n) => (seen2.push(n), n < 5));
console.log(r2, seen2);
```

```text
true [ 3, 8, 12 ]
false [ 3, 8 ]
```

## JSX 안에서 새어 나오는 값

React는 `{ }` 안의 값을 그대로 자식으로 받는다. `cond && <List />`가 동작하는 이유는 `cond`가 `false`면 `false`가 자식이 되고, React가 `false`, `true`, `null`, `undefined`를 그리지 않기 때문이다. 문제는 `&&`가 `false`가 아닌 다른 falsy 값을 돌려줄 때다. `react-dom/server`의 `renderToStaticMarkup`으로 몇 가지를 그려 봤다.

```js
// 각 줄은 <div>{식}</div>를 그린 결과다
items.length && <List />          // items.length가 0
title && <h2>{title}</h2>         // title이 ""
cond ? <List /> : null            // cond가 false
error || <List />                 // error가 new Error("timeout")
error?.message ?? <List />
user.name || "익명"                // user.name이 ""
```

```text
items.length && <List/>    <div>0</div>
title && <h2>              <div></div>
cond ? <List/> : null      <div></div>
error || <List/>           오류: Objects are not valid as a React child (found: [object Error]). If you meant to render a collection of children, use an array instead.
error?.message ?? ...      <div>timeout</div>
user.name || "익명"          <div>익명</div>
```

`0`이 화면에 찍히는 문제는 [truthy·falsy 글](/posts/js-truthy-falsy-typeof)에서 자세히 봤다. 빈 문자열은 그려도 보이지 않아서 넘어가지만, React Native에서는 `<Text>` 밖의 문자열이라 오류가 날 수 있다. 덜 알려진 것은 `||` 쪽이다. `error || <List />`는 오류가 있으면 Error 객체 자체를 자식으로 돌려주고, React는 객체를 그릴 수 없어 렌더링 전체가 실패한다. 오류 화면을 띄우려던 코드가 화면을 통째로 날린다.

조건부 렌더링의 기준은 단순하다. `&&`의 왼쪽은 언제나 불리언으로 만든다(`items.length > 0`, `Boolean(title)`). 둘 중 하나를 그릴 때는 삼항 연산자를 쓴다. 값을 그대로 그릴 때는 그 값이 문자열이나 숫자인지 확인한다. eslint-plugin-react의 `jsx-no-leaked-render` 규칙은 `&&` 왼쪽이 불리언이 아닐 때 경고해 준다.

## 조건 뒤에 훅을 부르면 순서가 깨진다

`&&`의 단락은 훅 규칙과 정면으로 부딪힌다. React는 훅을 이름이 아니라 호출 순서로 구분한다. 첫 번째 `useState`, 두 번째 훅, 세 번째 훅처럼 칸에 번호를 매겨 렌더링 사이에 상태를 이어 붙인다. 그런데 `isOpen && useEffect(...)`는 `isOpen`이 `false`인 렌더링에서 훅 하나를 건너뛴다. jsdom 위에서 React 19.3 개발 모드로 실제로 바꿔 그려 봤다.

```js
function Modal({ isOpen }) {
  const [title] = useState("알림");
  isOpen && useEffect(() => { console.log("열림 effect"); }, []);
  const [count] = useState(0);
  return <p>{title}{count}</p>;
}
// isOpen={false}로 한 번 그린 뒤 isOpen={true}로 다시 그린다
```

삼항 연산자, `if`, 이른 `return`도 모두 같은 문제를 일으킨다. 조건은 훅 안으로 옮긴다. `useEffect(() => { if (!isOpen) return; ... }, [isOpen])`처럼 쓴다. `eslint-plugin-react-hooks`의 `rules-of-hooks` 규칙이 이런 조건부 호출을 빌드 전에 잡는다.

## 코드 리뷰에서 단락 평가를 읽는 법

단락 평가가 얽힌 버그는 대개 오류 없이 "가끔 이상하다"로 나타난다. 증상별로 볼 곳을 정리하면 이렇다.

- 오류 메시지나 로그가 일부만 남는다. `&&`나 `every`의 오른쪽에 부수 효과가 있는 함수가 있는지 본다.
- 설정값 0이나 false가 무시된다. `||`나 `||=`로 기본값을 준 곳을 찾는다.
- 화면 구석에 `0`이 보이거나, 오류가 났을 때 화면 전체가 빈다. JSX의 `&&` 왼쪽이 숫자인지, `||`가 객체를 돌려줄 수 있는지 본다.
- 특정 조건에서만 "change in the order of Hooks" 경고가 뜬다. 훅 호출 앞에 `&&`, 삼항, `if`가 있는지 본다.
- 권한 버튼이 반대 사람에게 보인다. `!`과 `&&`, `||`가 괄호 없이 섞인 조건을 펼쳐 본다.

아래 칸에서 단락 평가를 흉내 내는 함수를 만들어 보자. `op`는 `"&&"`, `"||"`, `"??"` 중 하나이고, `values`를 왼쪽부터 그 연산자로 이었을 때의 결과와 실제로 들여다본 값의 개수를 돌려준다. 지금 코드는 불리언만 돌려주고 모든 값을 다 본다. 기대값은 모두 실제 연산자로 계산한 값이다.

## 멈추는 시점과 돌려주는 값

`&&`, `||`, `??`는 왼쪽 값으로 결과가 정해지면 오른쪽을 평가하지 않고, 결과로 불리언이 아니라 멈춘 자리의 원래 값을 돌려준다. 앞의 성질은 가드와 지연 계산을 가능하게 하지만 부수 효과와 훅 호출을 건너뛰게 만들고, 뒤의 성질은 기본값 패턴을 가능하게 하지만 JSX에 `0`이나 객체를 흘려보낸다. 조건 자리에는 불리언을, 기본값 자리에는 데이터의 의미에 맞는 연산자를 둔다. 템플릿 문자열 안에서 `&&`가 `false`를 글자로 남기는 경우는 [템플릿 리터럴 글](/posts/js-template-literals)에서 봤다.

## 면접에서 나올 만한 질문

### 단락 평가란 무엇인가

왼쪽 피연산자만으로 결과가 정해지면 오른쪽 식을 평가하지 않는 규칙이다. `&&`는 왼쪽이 falsy면, `||`는 truthy면, `??`는 `null`도 `undefined`도 아니면 멈춘다. 오른쪽에 있는 함수 호출이나 부수 효과는 일어나지 않는다. 그래서 가드나 지연 계산에 쓰고, 반대로 꼭 실행돼야 하는 코드를 오른쪽에 두면 버그가 된다.

### `0 && "x"`와 `"" || null`의 결과는

각각 `0`과 `null`이다. `&&`와 `||`는 불리언이 아니라 피연산자 중 하나를 돌려준다. 왼쪽 값을 ToBoolean으로 판정만 하고, 멈추면 왼쪽 값을, 아니면 오른쪽 값을 그대로 돌려준다. 불리언이 필요하면 `Boolean()`이나 `!!`로 바꾼다.

### `a || b && c`는 어떻게 평가되나

`&&`가 `||`보다 우선순위가 높아서 `a || (b && c)`로 묶인다. `a`가 truthy면 `b && c`는 통째로 평가되지 않는다. 의도가 `(a || b) && c`라면 괄호를 써야 한다. 두 연산자가 섞이면 괄호를 쓰는 것이 읽기에도 안전하다.

### 기본값에 `||`를 쓰면 생기는 문제는

`0`, `""`, `false` 같은 정상 값도 없는 것으로 보고 기본값으로 바꾼다. 재시도 횟수 0, 알림 끄기 false 같은 설정이 무시된다. 이런 자리는 `null`과 `undefined`만 없음으로 보는 `??`를 쓴다. 환경 변수처럼 빈 문자열도 없음으로 봐야 하는 곳은 `||`가 맞다.

### React에서 `{error || <List />}`가 위험한 이유는

`error`가 있으면 `||`가 Error 객체 자체를 돌려주고, React는 객체를 자식으로 그릴 수 없어서 "Objects are not valid as a React child"로 렌더링이 실패한다. 오류를 보여 주려던 코드가 화면 전체를 날린다. `error ? <ErrorView error={error} /> : <List />`처럼 삼항으로 나누고, 그릴 때는 `error.message` 같은 문자열을 쓴다.

### 조건부 렌더링에서 `&&` 대신 삼항을 권하는 이유는

`&&`는 왼쪽이 falsy면 그 값을 돌려주는데, `0`이나 `NaN`은 React가 그린다. 삼항은 거짓일 때 무엇을 그릴지 `null`로 명시하니 숫자가 새지 않는다. `&&`를 쓴다면 왼쪽을 `items.length > 0`처럼 불리언으로 만든다. `jsx-no-leaked-render` 규칙으로 기계적으로 막을 수도 있다.

### `isOpen && useEffect(...)`는 왜 안 되나

React는 훅을 호출 순서로 구분하는데, `&&`가 렌더링마다 훅 호출을 넣었다 뺐다 하면 뒤쪽 훅이 다른 훅의 칸을 읽는다. 개발 모드에서는 "change in the order of Hooks" 경고가 뜨고 상태가 엉키거나 렌더링이 깨진다. 조건은 effect 안으로 옮기고, `rules-of-hooks` 린트 규칙으로 막는다.

### `fn && fn()`과 `fn?.()`의 차이는

`&&`는 falsy면 멈추고, `?.`는 `null`과 `undefined`에서만 멈춘다. `fn`이 `0`이면 앞쪽은 `0`을 돌려주고 뒤쪽은 `0`을 부르려다 TypeError가 난다. 함수 아니면 `undefined`인 선택적 콜백에는 `?.()`가 의도를 더 정확히 드러낸다.
