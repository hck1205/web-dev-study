<EasyIntro>
  파일을 읽고 결과를 돌려주는 서버가 하루에 몇 번씩 죽는 일이 있다. 끝나면 불러 달라고 넘긴 함수 안에서 return 하나를 빠뜨려 응답을 두 번 보냈기 때문이다. 이렇게 나중에 불러 달라고 넘기는 함수를 콜백이라고 하는데, 콜백으로 비동기를 짜면 이런 실수가 구조적으로 잘 생긴다.

  흔히 콜백 지옥이라고 하면 오른쪽으로 밀려나는 들여쓰기를 떠올리지만, 진짜 문제는 믿음이다. 이어서 할 일을 남의 함수에 넘기는 순간 그 함수를 언제, 몇 번 부를지는 저쪽이 정한다. 게다가 콜백은 나중에 새 자리에서 실행되기 때문에 바깥에 씌운 오류 잡기가 통하지 않아, 오류를 값처럼 손으로 넘기는 배관을 단계마다 깔아야 한다.

  들여쓰기는 이름 붙은 함수로 펴면 되지만 믿음 문제는 그대로 남는다. 결과를 담은 상자를 돌려받는 쪽으로 방향을 뒤집은 것이 Promise이고, 그 이야기가 다음 글에서 이어진다.

Node.js로 만든 작은 API 서버가 하루에 몇 번씩 죽는다. 로그에는 같은 에러만 남아 있다.

```text
Error [ERR_HTTP_HEADERS_SENT]: Cannot set headers after they are sent to the client
```

문제의 핸들러는 파일을 읽어서 그대로 돌려주는 코드였다.

```js
const server = http.createServer((req, res) => {
  fs.readFile("./missing.json", "utf8", (err, text) => {
    if (err) {
      res.statusCode = 500;
      res.end("read failed");
      // return을 빠뜨렸다
    }
    res.setHeader("Content-Type", "application/json");
    res.end(text);
  });
});
```

파일이 없으면 500을 보내고 끝나야 하는데, `return`이 없어서 아래 줄까지 내려간다. 이미 응답을 보낸 뒤에 헤더를 또 쓰려다가 예외가 나고, 그 예외는 아무도 잡지 않아서 프로세스가 죽는다. 실제로 돌리면 이렇게 끝난다(경로는 `/app`으로 줄였다).

`return` 하나 빠진 실수처럼 보이지만, 콜백으로 비동기를 짜면 이런 실수가 구조적으로 잘 생긴다. 흔히 "콜백 지옥"이라고 하면 오른쪽으로 밀려나는 들여쓰기를 떠올리는데, 이 글은 그 모양보다 더 아픈 문제들을 본다. 그다음에 Promise와 async/await가 정확히 무엇을 고쳤는지 이어지는 글에서 다룬다.

이 주제의 다른 글: [Promise](/posts/js-promises) · [async/await](/posts/js-async-await) · [Promise 조합 함수](/posts/js-promise-combinators)

## 끝나면 이걸 불러 달라는 부탁

콜백은 다른 함수에 넘기는 함수다. `[1, 2, 3].map((n) => n * 2)`의 화살표 함수도 콜백이지만, 이건 `map`이 끝나기 전에 그 자리에서 불린다. 동기 콜백이다. 함수를 값으로 넘기는 이야기 자체는 [일급 함수와 콜백](/posts/js-first-class-callbacks)에서 다룬다.

여기서 보는 건 비동기 콜백이다. `fs.readFile(path, cb)`는 파일 읽기를 운영체제에 부탁하고 바로 돌아온다. 읽기가 끝나면 Node.js가 나중에 `cb`를 불러 준다. 그 사이에 콜 스택은 비어 있고, 다른 요청을 처리할 수 있다. 이 "나중에"가 어떻게 돌아가는지는 [이벤트 루프](/posts/event-loop) 글에 있다.

Node.js의 콜백 API는 모양이 정해져 있다. 콜백의 첫 번째 인자는 에러, 두 번째부터가 결과다. error-first 콜백이라고 부른다.

## 순서가 있는 일은 안으로 파고든다

회원 가입을 콜백으로 짜 보자. 이메일 중복을 확인하고, 비밀번호를 해시하고, 사용자를 저장하고, 환영 메일을 보낸다. 앞 단계의 결과가 있어야 다음 단계를 할 수 있으니 다음 단계는 앞 단계의 콜백 안에 들어간다.

```js
function signup(email, pw, done) {
  db.findUser(email, (err, existing) => {
    if (err) return done(err);
    if (existing) return done(new Error("이미 가입한 이메일"));
    hashPassword(pw, (err, hash) => {
      if (err) return done(err);
      db.insertUser({ email, hash }, (err, user) => {
        if (err) return done(err);
        sendWelcomeMail(user, (err) => {
          if (err) return done(err);
          done(null, user);
        });
      });
    });
  });
}
```

가짜 DB와 메일 함수를 붙여 세 경우를 돌린 결과다.

## 콜백을 넘기면 제어권도 넘어간다

`fs.readFile(path, cb)`를 부르는 순간, `cb`를 언제, 몇 번, 어떤 인자로 부를지는 `readFile`이 정한다. 내 코드의 나머지 흐름을 남의 함수 손에 맡긴 셈이다. 이걸 제어의 역전(inversion of control)이라고 한다.

믿어야 하는 약속은 대략 이렇다. 콜백을 정확히 한 번 부른다. 성공이든 실패든 반드시 부른다. 항상 비동기로 부른다. 에러는 던지지 않고 첫 인자로 넘긴다. 잘 만든 라이브러리는 이걸 지킨다. 하지만 내가 짠 함수, 동료가 급하게 짠 래퍼, 오래된 SDK까지 다 지킨다는 보장은 없다. 처음 본 서버가 죽은 코드도 "정확히 한 번"이 깨진 경우다. 콜백 안에서 `res.end()`를 두 번 부를 수 있게 짜 버렸다.

반대로 콜백을 한 번도 안 부르는 버그도 있다. 어느 분기에서 `done()`을 빠뜨리면 요청이 영원히 대기한다. 에러 로그도 없다. 클라이언트 쪽 타임아웃이 터져야 알게 된다. 서버에서 "가끔 응답이 30초 뒤에 504로 끝난다"는 증상이 보이면 콜백을 안 부르는 분기를 의심할 만하다.

## 바깥 try가 지나쳐 버린 예외

콜백 안에서 `throw`하면 어떻게 될까. 바깥에 `try/catch`를 씌워도 잡히지 않는다.

```js
function loadUser(id, callback) {
  setTimeout(() => {
    if (id < 0) throw new Error("bad id");
    callback(null, { id, name: "kim" });
  }, 10);
}

try {
  loadUser(-1, (err, user) => console.log(user));
} catch (e) {
  console.log("잡았다:", e.message);
}
console.log("try 블록을 벗어났다");
```

```text
                ^

    at Timeout._onTimeout (/app/cb2.js:3:23)

    at process.processTimers (node:internal/timers:523:7)

```

"잡았다"는 끝내 찍히지 않는다. 스택 트레이스를 보면 이유가 보인다. 예외가 난 자리의 호출자는 `listOnTimeout`, `processTimers` 같은 Node.js 내부 함수뿐이고 우리 `try` 블록은 없다. 아래 그림에서 콜 스택이 어떻게 바뀌는지 따라가 보자.

`try/catch`는 같은 스택 안에서만 동작한다. 비동기 콜백은 매번 새 스택에서 시작하니 에러를 인자로 넘기는 수밖에 없다. 그래서 콜백 함수 안에서 `JSON.parse`처럼 던질 수 있는 일을 하면 그 자리에서 다시 `try/catch`로 감싸 `callback(err)`로 바꿔 줘야 한다. 겹마다 이걸 반복하다 보면 코드의 절반이 에러 배관이 된다.

운영 중인 Node.js 서버라면 `process.on("uncaughtException")`으로 로그를 남길 수는 있다. 하지만 공식 문서도 이 핸들러에서 하던 일을 이어 가지 말고 정리한 뒤 종료하라고 권한다. 어디까지 실행됐는지 알 수 없는 상태이기 때문이다. 프로세스 매니저나 쿠버네티스가 다시 띄우게 두는 편이 안전하다.

## 어떤 때는 바로, 어떤 때는 나중에

캐시를 붙이다가 자주 만드는 버그가 있다. 캐시에 있으면 콜백을 바로 부르고, 없으면 네트워크를 기다렸다가 부른다.

```js
const cache = new Map();
function getPrice(id, callback) {
  if (cache.has(id)) return callback(cache.get(id)); // 캐시: 바로 부른다
  setTimeout(() => {
    cache.set(id, 1000);
    callback(1000); // 미스: 나중에 부른다
  }, 10);
}

function show(label) {
  console.log(label, "시작");
  getPrice(7, (p) => console.log(label, "가격", p));
  console.log(label, "끝");
}

show("1차");
setTimeout(() => show("2차"), 50);
```

```text
1차 시작
1차 끝
1차 가격 1000
2차 시작
2차 가격 1000
2차 끝
```

같은 함수를 같은 인자로 불렀는데 실행 순서가 다르다. 1차에서는 "끝"이 "가격"보다 먼저, 2차에서는 나중에 찍힌다. 콜백 다음 줄에서 어떤 변수를 초기화한다면, 캐시 적중 여부에 따라 콜백이 그 변수를 초기화 전에 볼 수도, 후에 볼 수도 있다. 재현도 어렵다. 처음 한 번은 늘 정상이고 두 번째부터 이상해진다.

## 동시에 시작하고 모두 끝나면

순서가 없는 일은 동시에 시작하는 게 빠르다. 화면 조각 세 개를 동시에 가져와 모두 오면 합친다고 해 보자. 콜백만으로 하려면 "몇 개 끝났나"를 직접 세야 한다.

```js
const parts = [["header", 300], ["body", 100], ["footer", 200]];
const results = [];
let done = 0;

parts.forEach(([name, ms], i) => {
  fetchPart(name, ms, (err, value) => {
    results.push(value);        // 끝난 순서대로 쌓인다
    done += 1;
    if (done === parts.length) console.log("push:", results);
  });
});

const ordered = [];
let left = parts.length;
parts.forEach(([name, ms], i) => {
  fetchPart(name, ms, (err, value) => {
    ordered[i] = value;         // 자리를 지정한다
    if (--left === 0) console.log("index:", ordered);
  });
});
```

```text
push: [ 'body', 'footer', 'header' ]
index: [ 'header', 'body', 'footer' ]
```

`push`로 모으면 끝난 순서대로 쌓여서 결과 순서가 요청 순서와 달라진다. 아래 그림처럼 응답은 빠른 것부터 온다.

## 펴는 방법 두 가지

들여쓰기 자체는 콜백을 이름 붙인 함수로 꺼내면 펴진다.

```js
function signup(email, pw, done) {
  db.findUser(email, onFound);

  function onFound(err, existing) {
    if (err) return done(err);
    if (existing) return done(new Error("이미 가입한 이메일"));
    hashPassword(pw, onHashed);
  }
  function onHashed(err, hash) {
    if (err) return done(err);
    db.insertUser({ email, hash }, onSaved);
  }
  function onSaved(err, user) {
    if (err) return done(err);
    sendWelcomeMail(user, (err) => done(err, err ? undefined : user));
  }
}
```

화살표는 사라졌지만 흐름은 여전히 함수 사이를 건너뛰며 읽어야 한다. `if (err) return done(err)`도 그대로다. 제어의 역전, 동기와 비동기가 섞이는 문제, `try/catch`가 안 되는 문제는 하나도 해결되지 않았다. 모양만 바꾼 것이다.

두 번째 방법은 콜백 API를 Promise로 감싸는 것이다. Node.js는 error-first 콜백을 Promise로 바꿔 주는 `util.promisify`를 기본으로 준다. `fs`, `dns`, `timers`처럼 자주 쓰는 모듈은 `node:fs/promises` 같은 Promise 버전을 아예 따로 낸다.

```js
const fs = require("node:fs");
const { promisify } = require("node:util");

const readFileAsync = promisify(fs.readFile);
readFileAsync("config.json", "utf8").then((text) => console.log("promisify:", text));

require("node:fs/promises").readFile("config.json", "utf8")
  .then((text) => console.log("fs/promises:", text));

readFileAsync("nope.json", "utf8").catch((err) => console.log("reject:", err.code));
```

```text
reject: ENOENT
promisify: {"port":8080}
fs/promises: {"port":8080}
```

`err`가 오면 reject, 아니면 두 번째 인자로 resolve하는 게 `promisify`가 하는 일의 전부다. 출력 순서가 호출 순서와 다른 건 파일이 없다는 사실을 더 빨리 알았기 때문이다. 앞의 회원 가입을 이렇게 감싸서 `async`/`await`로 다시 써 보자.

```js
const findUser = promisify(db.findUser);
const insertUser = promisify(db.insertUser);
const hash = promisify(hashPassword);
const mail = promisify(sendWelcomeMail);

async function signup(email, pw) {
  if (await findUser(email)) throw new Error("이미 가입한 이메일");
  const user = await insertUser({ email, hash: await hash(pw) });
  await mail(user);
  return user;
}
```

```text
fail: 이미 가입한 이메일
ok: { id: 42, email: 'new@a.com', hash: 'h:6' }
```

겹마다 있던 `if (err) return done(err)`가 사라졌다. 실패는 `throw`처럼 위로 올라가고, 호출한 쪽에서 `try/catch`나 `.catch`로 한 번에 받는다. 콜백이 두 번 불려도 Promise는 처음 한 번만 받아들이니 "정확히 한 번"도 보장된다. 메일 실패 뒤 사용자를 어떻게 할지는 여전히 직접 정해야 한다. 문법이 비즈니스 규칙까지 고쳐 주지는 않는다.

주의할 점이 하나 있다. `promisify`는 `this`를 모른다. `promisify(db.findUser)`처럼 메서드를 떼어 감싸면 안에서 `this`가 사라진다. 메서드가 `this`를 쓴다면 `promisify(db.findUser.bind(db))`로 묶어야 한다. 이유는 [this 바인딩](/posts/js-this-binding) 글에 있다.

## 콜백이 여전히 맞는 자리

콜백이 사라진 건 아니다. "한 번 끝나는 일"은 Promise가 낫지만 "여러 번 일어나는 일"은 여전히 콜백이 맞다.

- 이벤트 리스너: `button.addEventListener("click", fn)`은 클릭할 때마다 불린다. Promise는 한 번 정해지면 끝이라 이걸 표현할 수 없다.
- 스트림: `stream.on("data", fn)`은 조각이 올 때마다 불린다. 요즘은 `for await (const chunk of stream)`으로도 읽는다.
- 배열 메서드와 정렬 비교 함수: 동기 콜백이라 이 글의 문제와 상관없다.

React에서도 같은 구분이 보인다. `setCount((c) => c + 1)`의 업데이터 함수나 `onClick`에 넘기는 함수는 콜백이지만 문제 될 게 없다. 문제는 콜백 기반 브라우저 API를 `useEffect` 안에서 부를 때다.

```js
useEffect(() => {
  let ignore = false;
  navigator.geolocation.getCurrentPosition(
    (pos) => { if (!ignore) setCoords(pos.coords); },
    (err) => { if (!ignore) setError(err.message); },
  );
  return () => { ignore = true; }; // 언마운트되거나 다시 실행되면 늦게 온 콜백을 무시한다
}, []);
```

컴포넌트가 사라진 뒤에 콜백이 와도 `getCurrentPosition`은 그걸 모른다. 제어권이 저쪽에 있기 때문이다. 그래서 `ignore` 플래그로 내 쪽에서 무시한다. 개발 모드의 Strict Mode는 effect를 일부러 두 번 실행하는데, 플래그가 없으면 이런 콜백이 두 번 들어와 상태를 덮어쓴다. `fetch`라면 플래그 대신 요청 자체를 취소할 수 있다. [AbortController](/posts/abort-controller)에서 다룬다.

## 직접 만들어 보는 series

콜백만으로 "여러 작업을 차례로 실행하고, 하나라도 실패하면 멈추는" 함수를 짜 보자. 예전 `async.series`가 하던 일이다. 아래 조건을 다 지켜야 테스트를 통과한다.

- 작업은 `(cb) => …` 모양이고, `cb(err, value)`로 끝을 알린다.
- 모두 성공하면 `done(null, results)`를 부른다. 결과 순서는 작업 순서와 같다.
- 실패하면 남은 작업을 실행하지 않고 `done(err)`를 한 번만 부른다.
- 어떤 작업이 `cb`를 실수로 두 번 불러도 다음 작업은 한 번만 실행된다.

`runSeries`는 테스트를 위해 가짜 작업을 만들어 `series`를 부르는 함수다. 고치지 않는다.

## 콜백 지옥을 다시 정리하면

콜백 지옥의 본모습은 들여쓰기가 아니라 신뢰 문제다. 이어서 할 일을 남의 함수에 넘기면 몇 번, 언제, 어떻게 불릴지를 그쪽이 정하고, 비동기 경계에서는 `try/catch`가 끊긴다. 그래서 에러를 값으로 넘기는 배관을 겹마다 손으로 깔아야 했다. Promise는 결과를 담은 객체를 돌려받는 쪽으로 방향을 뒤집어서 이 문제를 푼다. 다음 글 [Promise](/posts/js-promises)에서 그 상자가 어떻게 동작하는지 본다.

## 면접에서 나올 만한 질문

### 콜백 지옥이 무엇이고 왜 문제가 되나요?

비동기 작업을 콜백으로 이어 붙이다 보면 코드가 안으로 깊게 들어가는 현상을 말한다. 하지만 더 큰 문제는 가독성보다 신뢰다. 콜백을 넘기면 그 콜백을 언제, 몇 번 부를지 상대 함수가 정하는 제어의 역전이 생기고, 에러 처리를 겹마다 직접 해야 한다. 그래서 응답을 두 번 보내거나 아예 안 보내는 버그가 쉽게 생긴다.

### Node.js의 error-first 콜백 규칙은 왜 생겼나요?

비동기 콜백 안에서 생긴 에러는 호출한 함수가 이미 끝나서 `throw`로 전달할 방법이 없기 때문이다. 그래서 에러를 값으로 넘기기로 약속하고, 빠뜨리기 어렵게 첫 번째 인자에 둔다. 콜백을 받는 쪽은 `if (err) return …`으로 먼저 확인하고 빠져나가는 게 관례다. 이 모양이 통일돼 있어서 `util.promisify`로 Promise로 자동 변환할 수 있다.

### 비동기 콜백 안에서 던진 예외는 왜 바깥 try/catch로 잡히지 않나요?

`try/catch`는 같은 콜 스택 안에서만 예외를 받는다. 비동기 콜백은 원래 함수가 끝나 스택이 빈 뒤에 이벤트 루프가 새 스택에서 부르기 때문에, 예외가 날 때 그 `try` 블록은 스택에 없다. Node.js에서는 그대로 uncaughtException이 되어 프로세스가 죽는다. 콜백 안에서 던질 수 있는 코드는 그 자리에서 감싸 에러 인자로 넘겨야 한다.

### 제어의 역전 때문에 실제로 어떤 버그가 생기나요?

콜백이 두 번 불리면 응답을 두 번 보내 `ERR_HTTP_HEADERS_SENT`가 나거나 결제 같은 후속 작업이 두 번 실행된다. 한 번도 안 불리면 요청이 응답 없이 매달려 있다가 바깥 타임아웃에 걸리고, 에러 로그도 남지 않는다. 캐시 적중 때만 동기로 부르는 식으로 호출 시점이 들쭉날쭉하면 실행 순서가 상황마다 바뀐다. 방어하려면 한 번만 받는 가드를 두거나, 한 번만 정해지는 Promise로 감싼다.

### 콜백을 어떤 때는 동기로, 어떤 때는 비동기로 부르면 왜 안 되나요?

호출한 쪽의 다음 줄과 콜백 중 무엇이 먼저 실행될지가 입력이나 캐시 상태에 따라 바뀌기 때문이다. 처음에는 잘 돌다가 캐시가 찬 뒤에만 초기화 순서가 뒤집히는 식이라 재현도 어렵다. 비동기일 수 있는 API는 항상 비동기로 부르도록 `process.nextTick`이나 `queueMicrotask`로 미룬다. Promise의 `then`은 이미 이행된 경우에도 항상 나중에 실행해서 이 문제를 원천적으로 막는다.

### 콜백 지옥은 이름 붙인 함수로 펴면 해결되지 않나요?

들여쓰기는 펴지지만 문제의 일부만 해결된다. 흐름을 여러 함수 사이를 오가며 읽어야 하고, 겹마다 에러를 넘기는 코드와 제어의 역전, `try/catch`가 끊기는 문제는 그대로 남는다. 그래서 Promise로 감싸서 결과를 객체로 돌려받고, `async`/`await`로 위에서 아래로 읽히게 쓰는 게 지금의 표준이다.

### 그러면 콜백은 이제 안 쓰나요?

한 번 끝나는 비동기 작업은 Promise가 낫지만, 여러 번 일어나는 일은 여전히 콜백이 맞다. 이벤트 리스너, 스트림의 `data` 이벤트, 타이머 반복 같은 경우다. 배열 메서드에 넘기는 동기 콜백은 이 문제와 상관이 없다. React에서는 콜백 기반 API를 effect 안에서 쓸 때 언마운트 뒤에 오는 콜백을 플래그나 취소로 무시해 줘야 한다.
