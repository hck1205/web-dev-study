<EasyIntro>
  학교 복사기는 교실마다 한 대씩 둘 필요가 없다. 비싸고 자리를 차지하니 한 대만 두고 모두가 같이 쓴다. 프로그램에도 데이터베이스 연결 묶음이나 설정처럼 딱 하나만 있어야 하는 물건이 있고, 이를 하나만 만들어 누구나 꺼내 쓰게 하는 방식이 싱글턴 패턴이다.

  그런데 하나라는 약속은 생각보다 자주 깨진다. 개발 중에 파일을 저장할 때마다 복사기가 새로 생기기도 하고, 같은 부품이 두 벌 깔려 복사기가 둘이 되기도 하며, 서버를 여러 대 띄우면 서버마다 한 대씩 생긴다. 반대로 하나뿐인 복사기에 누군가 설정을 바꿔 두면 다음 사람이 영문도 모른 채 그 설정을 떠안는다.

  알고 나면 하나만 만드는 일과 어디서든 꺼내 쓰는 일을 나눠 보게 된다. 앞의 것은 유용하지만, 뒤의 것은 테스트를 순서에 따라 깨지게 만드니 필요한 물건은 바깥에서 건네받는 쪽이 낫다.
</EasyIntro>

Next.js 개발 서버를 띄워 놓고 파일을 몇 번 저장했더니 PostgreSQL이 `FATAL: sorry, too many clients already`를 돌려준다. 코드에는 `new Pool({ max: 10 })`이 한 줄뿐이다. 그런데 저장할 때마다 모듈이 다시 평가되면서 그 한 줄이 계속 새 풀을 만들고, 이전 풀은 연결을 쥔 채 남아 있었다. 풀은 앱에 하나만 있어야 하는 물건인데 "하나"가 지켜지지 않은 것이다.

반대 방향의 사고도 있다. 기능 플래그를 싱글턴 객체에 담아 두었더니 테스트가 실행 순서에 따라 성공하기도 하고 실패하기도 한다. 앞 테스트가 켜 둔 플래그가 다음 테스트까지 살아 있어서다.

둘 다 싱글턴 패턴 이야기다. 하나만 있어야 할 것을 하나로 지키는 방법, 그리고 그 "하나"가 생각보다 자주 깨지거나 너무 오래 살아남는 이유를 차례로 본다. 디자인 패턴 전체 지도는 [디자인 패턴 개요](/posts/design-patterns-overview)에 있다.

## 하나만 만들고 모두가 같이 쓴다

GoF 책의 정의는 두 줄이다. 클래스의 인스턴스가 오직 하나임을 보장하고, 그 인스턴스에 접근하는 전역 지점을 제공한다. 이 두 가지를 위해 생성자를 막고, 인스턴스를 클래스 자신이 들고 있다가 달라는 사람에게 같은 것을 준다.

TypeScript로 쓰면 이렇다. `private constructor`가 바깥의 `new`를 컴파일 단계에서 막고, `#instance`가 실제 객체를 숨긴다.

```ts
export class AppConfig {
  static #instance: AppConfig | undefined;

  private constructor(readonly apiBaseUrl: string) {}

  static getInstance(): AppConfig {
    AppConfig.#instance ??= new AppConfig(process.env.API_BASE_URL ?? "http://localhost:3000");
    return AppConfig.#instance;
  }
}

AppConfig.getInstance() === AppConfig.getInstance(); // true
// new AppConfig("x"); // 컴파일 에러: 생성자가 private이다
```

처음 부를 때 만드는 이 방식을 지연 초기화(lazy initialization)라고 한다. 쓰지 않으면 만들지 않으니 시작이 가볍지만, 처음 쓰는 순간에 생성 비용을 치른다. 아래 그림에서 두 서비스가 차례로 설정을 달라고 할 때 무슨 일이 일어나는지 보자.

## 자바스크립트에서는 모듈이 이미 하나다

Node.js나 번들러 환경에서는 클래스를 저렇게 꾸밀 일이 드물다. 모듈은 처음 import될 때 한 번 평가되고, 그 결과가 캐시된다. 두 번째 import는 캐시된 결과를 돌려준다. 그래서 모듈 최상위에서 만든 객체는 그 자체로 싱글턴이다.

```ts
// db.ts
import { Pool } from "pg";

export const pool = new Pool({ max: 10 });
```

```ts
// 어디서 import하든 같은 pool이다
import { pool } from "./db";
```

GoF의 정의 중 "하나만 보장"은 모듈 캐시가, "전역 접근 지점"은 import가 맡는다. 클래스 버전보다 짧고, 생성자를 막을 방법을 고민할 필요도 없다. 문제는 모듈 캐시가 깨지는 순간이 생각보다 많다는 것이다.

처음 장면의 Next.js 개발 서버가 그 경우다. 개발 서버는 파일이 바뀌면 그 모듈을 다시 평가한다. 모듈 캐시가 비워지니 `new Pool()`도 다시 실행된다. 이전 풀은 누구도 참조하지 않지만 열어 둔 소켓 때문에 바로 사라지지 않는다. 그래서 Prisma 문서도 개발 환경에서는 클라이언트를 `globalThis`에 붙여 두는 방법을 권한다. 모듈은 다시 평가돼도 `globalThis`는 프로세스가 살아 있는 동안 그대로이기 때문이다.

```ts
import { Pool } from "pg";

const globalForDb = globalThis as unknown as { pool?: Pool };

export const pool = globalForDb.pool ?? new Pool({ max: 10 });

if (process.env.NODE_ENV !== "production") globalForDb.pool = pool;
```

## 같은 모듈이 두 번 로드되는 경우

모듈 캐시의 키는 모듈 이름이 아니라 해석된 파일 경로다. 같은 패키지가 `node_modules`에 두 벌 깔려 있으면 경로가 둘이고, 모듈도 두 번 평가되고, "싱글턴"도 두 개가 된다. 앱은 `config` 2.0을, 앱이 쓰는 `plugin`은 `config` 1.4를 요구해서 패키지 매니저가 두 벌을 깔아 둔 상황을 만들어 봤다. `config`는 앞의 `getInstance()` 방식 클래스다.

```js
// app.js
const Config = require("config");
const plugin = require("plugin");

Config.get().values.mode = "production";
console.log("app sees    :", Config.get().values.mode);
console.log("plugin sees :", plugin.readMode());
console.log("same class? :", Config === plugin.Config);
```

```text
app sees    : production
plugin sees : undefined
same class? : false
node_modules/config/index.js
node_modules/plugin/node_modules/config/index.js
```

마지막 두 줄은 `require.resolve`로 찍은 실제 경로다. 앱이 설정한 값을 플러그인은 보지 못한다. 에러도 나지 않고 값만 조용히 비어 있다. `instanceof` 검사도 클래스가 둘이라 실패한다.

같은 일이 다른 모양으로도 생긴다. 한 패키지가 CommonJS와 ES 모듈 진입점을 둘 다 제공할 때, 앱의 한쪽은 `require`로, 다른 쪽은 `import`로 불러 두 사본이 뜨는 경우를 Node.js 문서는 dual package hazard라고 부른다. 테스트 러너가 테스트 파일마다 모듈 레지스트리를 따로 두는 것도 같은 원리다. 마이크로 프런트엔드에서 React가 두 벌 떠서 훅이 깨지는 문제는 [마이크로 프런트엔드 글](/posts/micro-frontends)에서 자세히 다뤘다.

확인은 `npm ls config`나 `pnpm why config`로 몇 벌 깔렸는지 보는 데서 시작한다. 두 벌이 꼭 하나여야 하는 패키지라면 버전 범위를 맞추거나 `overrides`(pnpm은 `pnpm.overrides`)로 하나로 고정한다. 라이브러리를 만드는 입장이라면 상태를 모듈 변수 대신 `globalThis[Symbol.for("my-lib.registry")]`처럼 전역 심벌 키에 두어 사본끼리 공유하게 하는 방법도 쓴다. `Symbol.for`는 같은 문자열이면 어느 사본에서 불러도 같은 심벌을 준다.

## 비동기 초기화에서는 둘이 만들어진다

자바의 싱글턴 글을 찾아보면 스레드 두 개가 동시에 `getInstance()`에 들어와 객체를 두 번 만드는 문제가 꼭 나온다. 자바스크립트는 한 스레드에서 돌아가니 상관없을 것 같지만, 초기화가 비동기면 같은 일이 생긴다. `await` 하는 동안 다른 호출이 끼어들기 때문이다.

실제로 돌려 보면 차이가 그대로 나온다. 접속에 50ms가 걸린다고 치고 두 호출을 동시에 보냈다.

```js
// 1) 인스턴스를 캐시
let pool;
async function getPoolNaive() {
  if (!pool) pool = await createPool();
  return pool;
}

// 2) Promise를 캐시
let poolPromise;
function getPool() {
  poolPromise ??= createPool();
  return poolPromise;
}
```

```text
naive:   created = 2 same = false
promise: created = 1 same = true
```

결과가 아니라 "만드는 중"을 캐시하는 게 요령이다. 하나 더 챙길 것이 있다. 첫 접속이 실패하면 거부된 Promise가 캐시에 남아, 그 뒤 모든 호출이 영원히 같은 에러를 받는다. 실패하면 캐시를 비워서 다음 호출이 다시 시도하게 한다.

```ts
import { Pool } from "pg";

declare function connectWithRetry(): Promise<Pool>;

let poolPromise: Promise<Pool> | undefined;

export function getPool(): Promise<Pool> {
  poolPromise ??= connectWithRetry().catch((error: unknown) => {
    poolPromise = undefined; // 실패한 Promise를 붙잡고 있지 않는다
    throw error;
  });
  return poolPromise;
}
```

## 프로세스 하나에 하나일 뿐이다

싱글턴이 보장하는 "하나"의 범위는 프로세스다. Node.js `cluster`로 워커 두 개를 띄우고, 요청 수를 세는 객체를 워커마다 하나씩 둔 다음 여섯 번 요청했다.

```js
// 워커 안: 요청 횟수를 세는 "싱글턴" 카운터
const counter = { hits: 0 };
http.createServer((req, res) => {
  counter.hits++;
  res.end(`pid=${process.pid} hits=${counter.hits}`);
}).listen(3100);
```

```text
pid=32329 hits=1
pid=32330 hits=1
pid=32329 hits=2
pid=32330 hits=2
pid=32329 hits=3
pid=32330 hits=3
```

여섯 번 왔는데 어느 카운터도 6을 모른다. 리눅스에서 `cluster`는 기본으로 연결을 워커에 번갈아 나눠 주니 숫자가 정확히 반씩 갈렸다. 쿠버네티스 파드를 세 개 띄우면 세 개, 서버리스 함수라면 인스턴스 수만큼 생긴다.

## 요청마다 달라야 할 값을 넣으면 섞인다

서버의 싱글턴은 모든 요청이 같이 쓴다. 여기에 현재 사용자, 요청 id처럼 요청마다 다른 값을 넣으면 `await` 사이에 다른 요청이 그 값을 덮어쓴다. 남의 이름이 화면에 찍히는 사고가 이렇게 난다. 이 문제와 `AsyncLocalStorage`로 요청별 값을 흘리는 방법은 [SSR 글의 "모듈 변수는 모든 사용자가 같이 쓴다"](/posts/rendering-ssr#모듈-변수는-모든-사용자가-같이-쓴다)에서 실제로 재현해 두었다. 싱글턴에는 모든 요청이 같아도 되는 것, 즉 설정, 풀, 로거, 읽기 전용 캐시만 둔다.

## 테스트가 순서에 따라 깨진다

처음에 말한 기능 플래그 싱글턴을 그대로 테스트해 보자.

```js
test("새 결제 플래그가 켜지면 버튼 문구가 바뀐다", () => {
  flags().enable("new-checkout");
  assert.equal(checkoutButtonLabel(), "바로 결제");
});

test("기본 문구는 주문하기다", () => {
  assert.equal(checkoutButtonLabel(), "주문하기");
});
```

```bash
# Node.js 내장 테스트 러너로 실행한다
node --test --test-reporter=spec checkout.test.mjs
```

```text
✔ 새 결제 플래그가 켜지면 버튼 문구가 바뀐다 (1.041722ms)
✖ 기본 문구는 주문하기다 (1.184448ms)
ℹ tests 2
ℹ suites 0
ℹ pass 1
ℹ fail 1
```

두 번째 테스트만 따로 돌리면 통과한다. 같은 파일 안의 테스트는 모듈을 공유하니 첫 테스트가 켠 플래그가 그대로 남았다. 순서를 바꾸면 통과하고, 병렬로 돌리면 가끔 실패한다. 이런 테스트가 쌓이면 팀은 CI 재실행 버튼부터 누르게 된다.

`reset()` 메서드를 만들어 `afterEach`에서 부르는 응급처치가 있지만, 싱글턴이 늘 때마다 리셋할 목록도 는다. 근본 원인은 `checkoutButtonLabel`이 플래그를 직접 찾아간다는 데 있다. 필요한 것을 바깥에서 받게 바꾸면 테스트마다 새 객체를 넣을 수 있다.

```ts
interface Flags {
  isOn(name: string): boolean;
}

export function createCheckout(deps: { flags: Flags }) {
  return {
    buttonLabel: () => (deps.flags.isOn("new-checkout") ? "바로 결제" : "주문하기"),
  };
}

// 테스트: 매번 새 가짜를 넣는다
const fakeFlags = (on: string[]): Flags => ({ isOn: (n) => on.includes(n) });
createCheckout({ flags: fakeFlags([]) }).buttonLabel(); // "주문하기"
createCheckout({ flags: fakeFlags(["new-checkout"]) }).buttonLabel(); // "바로 결제"
```

운영에서는 앱 시작점(composition root)에서 진짜 플래그 객체를 한 번 만들어 넘긴다. 객체는 여전히 하나다. 달라진 점은 "하나만 만든다"는 결정을 클래스 자신이 아니라 조립하는 쪽이 한다는 것이다. 의존성 주입(DI)이 바로 이 생각이다.

Spring의 빈이 좋은 예다. Spring 빈의 기본 스코프는 singleton이지만, 이건 컨테이너 하나당 인스턴스 하나라는 뜻이다. 클래스는 평범한 클래스라서 테스트에서는 `new`로 따로 만들 수 있고, 컨테이너를 두 개 띄우면 인스턴스도 두 개다. 같은 "싱글턴"이라는 말이지만 GoF 싱글턴과는 하나를 지키는 주체가 다르다. NestJS의 provider도 기본은 같은 방식이다.

## 다른 언어는 어떻게 막나

멀티스레드 언어에서는 동시에 두 스레드가 들어오는 문제를 직접 막아야 한다. 자바의 이중 검사 잠금(double-checked locking)은 이렇게 생겼다.

```java
public final class Registry {
  private static volatile Registry instance;

  private Registry() {}

  public static Registry getInstance() {
    Registry local = instance;
    if (local == null) {                 // 1차 검사: 잠금 없이 빠르게
      synchronized (Registry.class) {
        local = instance;
        if (local == null) {             // 2차 검사: 잠금 안에서 다시
          instance = local = new Registry();
        }
      }
    }
    return local;
  }
}
```

`volatile`이 빠지면 다른 스레드가 생성자가 덜 끝난 객체의 참조를 볼 수 있다. 객체 생성과 참조 대입의 순서가 재배치될 수 있어서다. Java 5의 메모리 모델 개정 이후로 `volatile`을 붙이면 안전하다. 실무에서는 이보다 단순한 방법을 더 쓴다. 클래스 로딩이 스레드 안전하다는 점을 이용한 holder 관용구, 그리고 Effective Java가 권하는 원소 하나짜리 `enum`이다. `enum`은 직렬화나 리플렉션으로 두 번째 인스턴스를 만드는 것까지 막아 준다.

Go는 `sync.Once`가 "한 번만 실행"을 보장한다. Go 1.21부터는 값을 돌려주는 `sync.OnceValue`도 있다.

```go
var getClient = sync.OnceValue(func() *http.Client {
	return &http.Client{Timeout: 5 * time.Second}
})
```

Kotlin은 `object` 선언 하나로 스레드 안전한 싱글턴을 만든다. 언어마다 문법은 달라도 결국 "처음 한 번"을 언어나 런타임이 보장하게 맡기는 쪽으로 간다.

## 직접 만들어 보는 once

## 싱글턴을 써도 되는 자리

싱글턴이 안티패턴이라는 말을 자주 듣는데, 정확히는 "전역 가변 상태"가 문제다. 그 기준으로 나누면 판단이 쉬워진다.

써도 되는 것은 만들기 비싸고, 상태를 바꾸지 않거나 스스로 동시성을 관리하는 것이다. 커넥션 풀, HTTP 클라이언트(keep-alive 연결을 재사용한다), 로거, 시작할 때 읽고 다시 바뀌지 않는 설정이 여기에 든다. 이런 것도 클래스 안에서 `getInstance()`로 스스로 찾아가게 하기보다 시작점에서 만들어 넘기는 편이 테스트하기 좋다.

피해야 하는 것은 요청이나 사용자마다 달라야 하는 값, 테스트마다 초기 상태가 필요한 값, 여러 프로세스가 같이 봐야 하는 값이다. 셋 다 앞에서 실제로 깨지는 모습을 봤다.

코드 리뷰에서 볼 만한 신호도 있다. 함수 안에서 `Something.getInstance()`를 부르는데 시그니처에는 그 의존성이 드러나지 않는다면, 그 함수는 숨은 입력을 가진 셈이다. 테스트에서 `jest.resetModules()`나 `reset()` 호출이 늘어나고 있다면 싱글턴이 너무 많은 상태를 쥐고 있다는 뜻이다.

싱글턴은 "하나만 만든다"와 "어디서든 꺼내 쓴다"를 한 번에 묶은 패턴이다. 앞의 것은 대체로 유용하고, 뒤의 것이 대부분의 문제를 만든다. 하나만 만드는 일은 모듈이나 조립하는 쪽에 맡기고, 꺼내 쓰는 대신 넘겨받게 하면 장점만 남는다. 이어서 객체를 만드는 일을 누가 결정하는지 다루는 [팩토리 메서드](/posts/pattern-factory-method)를 보면 이 이야기가 이어진다.

## 면접에서 나올 만한 질문

### 싱글턴 패턴이 무엇이고 언제 쓰나요?

클래스의 인스턴스를 하나로 제한하고 그 인스턴스에 전역으로 접근하게 하는 패턴이다. 생성자를 막고 클래스가 인스턴스를 들고 있다가 같은 것을 돌려준다. 커넥션 풀, HTTP 클라이언트, 로거처럼 만들기 비싸고 여럿일 이유가 없는 자원에 쓴다.

### 싱글턴이 안티패턴이라고 불리는 이유는요?

전역 가변 상태가 되기 쉬워서다. 함수가 의존성을 시그니처로 받지 않고 몰래 꺼내 쓰니 결합이 숨고, 테스트끼리 상태가 새어 실행 순서에 따라 결과가 달라진다. 하나만 만드는 것 자체는 문제가 아니라서, 생성은 시작점에서 한 번 하고 필요한 곳에 주입하는 방식으로 장점만 남긴다.

### 자바스크립트에서 모듈 변수는 싱글턴인가요? 깨지는 경우가 있나요?

모듈은 처음 import될 때 한 번 평가되고 캐시되니 모듈 최상위 객체는 사실상 싱글턴이다. 하지만 캐시 키가 파일 경로라서 같은 패키지가 두 벌 깔리면 두 개가 된다. CommonJS와 ESM 진입점이 둘 다 로드되는 dual package hazard, 개발 서버의 모듈 재평가, 테스트 러너의 파일별 모듈 레지스트리도 같은 이유로 인스턴스를 늘린다.

### 비동기로 초기화하는 싱글턴에서 생기는 문제는요?

초기화를 await 하는 사이에 다른 호출이 들어와 인스턴스를 두 번 만든다. 결과 대신 초기화 Promise를 바로 캐시하면 뒤의 호출이 같은 Promise를 기다리게 되어 하나만 만들어진다. 실패한 Promise가 남으면 이후 호출이 모두 같은 에러를 받으니 실패하면 캐시를 비운다.

### 서버를 여러 대 띄우면 싱글턴은 어떻게 되나요?

싱글턴은 프로세스마다 하나라서 파드나 워커 수만큼 생긴다. 메모리에 둔 카운터나 요청 수 제한은 서버 수만큼 나뉘어 틀린 값을 낸다. 여러 프로세스가 공유해야 하는 상태는 Redis나 DB에 두고, 클러스터에서 한 번만 돌아야 하는 작업은 분산 락이나 리더 선출로 고른다.

### 자바에서 스레드 안전한 싱글턴은 어떻게 만드나요?

이중 검사 잠금을 쓴다면 필드에 volatile을 붙여야 덜 생성된 객체가 보이는 재배치 문제를 막는다. 더 단순하게는 클래스 로딩이 스레드 안전하다는 점을 이용한 holder 관용구나 원소 하나짜리 enum을 쓴다. enum은 직렬화와 리플렉션으로 인스턴스가 늘어나는 것까지 막는다.

### Spring 빈의 싱글턴 스코프와 GoF 싱글턴은 같은가요?

다르다. Spring의 singleton은 컨테이너 하나당 인스턴스 하나이고, 클래스 자체는 평범해서 테스트에서 직접 만들 수 있다. GoF 싱글턴은 클래스가 스스로 인스턴스 수를 제한한다. 하나를 지키는 책임이 클래스 밖으로 나갔기 때문에 Spring 방식은 테스트와 교체가 쉽다.
