쇼핑몰 주문 서비스에 "배송 전이면 취소할 수 있게 해 주세요"라는 요구가 들어왔다. `cancel()`을 열어 보니 `if (order.status === "pending")`로 시작하는 사다리가 이미 있다. 결제 전이면 그냥 취소, 결제 후면 환불하고 취소, 배송 중이면 에러. 그런데 `ship()`에도, `refund()`에도, 관리자 화면의 버튼 활성화 코드에도 같은 모양의 사다리가 있다. 상태가 하나 늘면 이 사다리를 전부 찾아다니며 한 칸씩 끼워야 한다.

이 글은 상태(State) 패턴이다. 객체의 상태에 따라 같은 메서드가 다르게 동작해야 할 때, 상태마다 동작을 묶어 객체로 꺼내는 방법이다. 시리즈 전체 지도는 [디자인 패턴 개요](/posts/design-patterns-overview)에 있고, 모양이 거의 같은 [전략 패턴](/posts/pattern-strategy)과의 차이는 뒤에서 따로 본다.

## 메서드마다 같은 switch가 반복된다

처음 코드는 대체로 이렇게 생겼다. 상태는 문자열 하나고, 메서드마다 그 문자열을 다시 검사한다.

```ts
type Status = "pending" | "paid" | "shipped" | "cancelled";

declare function refundPayment(orderId: number): void;

class Order {
  status: Status = "pending";
  trackingNo?: string;
  constructor(readonly id: number) {}

  pay() {
    if (this.status === "pending") this.status = "paid";
    else throw new Error(`${this.status} 상태에서는 결제할 수 없다`);
  }
  ship(trackingNo: string) {
    if (this.status === "paid") {
      this.trackingNo = trackingNo;
      this.status = "shipped";
    } else throw new Error(`${this.status} 상태에서는 배송할 수 없다`);
  }
  cancel() {
    switch (this.status) {
      case "pending":
        this.status = "cancelled";
        break;
      case "paid":
        refundPayment(this.id); // 결제 후 취소는 환불이 먼저다
        this.status = "cancelled";
        break;
      case "shipped":
        throw new Error("배송이 시작되어 취소할 수 없다");
      case "cancelled":
        break; // 두 번 눌러도 조용히 넘어간다
    }
  }
}
```

메서드가 셋이고 상태가 넷이라 지금은 읽힌다. 문제는 늘어나는 방향이다. "부분 배송" 상태를 넣으면 메서드마다 `case`를 하나씩 더해야 하고, 하나를 빠뜨려도 컴파일러는 모른다(`if` 사다리에서는 특히). "결제 완료 상태에서 무엇을 할 수 있나"를 알고 싶으면 파일 전체를 훑어야 한다. 한 상태의 규칙이 메서드마다 흩어져 있기 때문이다.

## 상태를 객체로 꺼내면

상태 패턴은 축을 돌린다. 메서드마다 상태를 나누던 것을, 상태마다 메서드를 모은다. 주문(Context)은 지금 상태 객체 하나를 들고 있다가 들어온 요청을 그대로 넘긴다. 상태 객체가 그 상태에서의 동작을 알고, 필요하면 다음 상태로 바꾼다.

앞의 주문을 이렇게 옮긴다. 상태 객체는 필드가 없어서 하나만 만들어 모든 주문이 같이 쓴다.

```ts
interface OrderState {
  readonly name: string;
  pay(order: Order): void;
  ship(order: Order, trackingNo: string): void;
  cancel(order: Order): void;
}

declare function refundPayment(orderId: number): void;

class Order {
  state: OrderState = Pending;
  readonly log: string[] = [];
  trackingNo?: string;
  constructor(readonly id: number) {}

  transitionTo(next: OrderState) {
    this.log.push(`${this.state.name} → ${next.name}`);
    this.state = next;
  }
  pay() { this.state.pay(this); }
  ship(trackingNo: string) { this.state.ship(this, trackingNo); }
  cancel() { this.state.cancel(this); }
}

const reject = (from: string, action: string) => () => {
  throw new Error(`${from} 상태에서는 ${action}할 수 없다`);
};

const Pending: OrderState = {
  name: "pending",
  pay: (o) => o.transitionTo(Paid),
  ship: reject("pending", "배송"),
  cancel: (o) => o.transitionTo(Cancelled),
};
const Paid: OrderState = {
  name: "paid",
  pay: reject("paid", "결제"),
  ship: (o, no) => {
    o.trackingNo = no;
    o.transitionTo(Shipped);
  },
  cancel: (o) => {
    refundPayment(o.id);
    o.transitionTo(Cancelled);
  },
};
const Shipped: OrderState = {
  name: "shipped",
  pay: reject("shipped", "결제"),
  ship: reject("shipped", "배송"),
  cancel: reject("shipped", "취소"),
};
const Cancelled: OrderState = {
  name: "cancelled",
  pay: reject("cancelled", "결제"),
  ship: reject("cancelled", "배송"),
  cancel: () => {},
};
```

`Order`에서 `if`가 모두 사라졌다. 결제 완료 상태에서 할 수 있는 일은 `Paid` 하나만 보면 된다. 새 상태를 넣을 때 `OrderState`를 구현하지 않은 메서드가 있으면 타입 검사에서 걸린다. 주문 두 개를 돌려 본 결과다.

```text
paid 상태에서는 결제할 수 없다
shipped 상태에서는 취소할 수 없다
shipped CJ-1234 [ 'pending → paid', 'paid → shipped' ]
cancelled true [ 'pending → paid', 'paid → cancelled' ]
new Order(1).state === new Order(2).state → true
```

마지막 줄이 상태 객체를 공유하고 있다는 뜻이다. 상태 객체에 필드가 없으면 주문이 백만 개여도 상태 객체는 넷이다. 상태별 데이터(예: 재시도 횟수, 대기 시작 시각)가 필요하면 그때는 전이할 때마다 `new`로 만들어 그 값을 상태 안에 둔다. 공유할지 새로 만들지는 상태가 데이터를 들고 있느냐로 정한다.

## 전이는 누가 결정하나

상태가 다음 상태를 정하면 새 상태를 넣기 쉽다. 새 클래스 하나를 만들고 들어오는 쪽 한두 곳만 고치면 된다. 대신 전체 흐름을 보려면 상태 객체를 하나씩 열어야 한다. 상태 객체들이 서로를 알게 된다는 것도 대가다. `Paid`는 `Shipped`와 `Cancelled`를 안다.

전이를 Context에 모으면 반대다. 전체 그림이 한 곳에 있지만, 상태가 늘수록 그 한 곳이 다시 처음의 `switch`를 닮아 간다. 실무에서는 대개 중간을 택한다. 동작(무엇을 하나)은 상태 객체에 두고, 전이 규칙(어디로 갈 수 있나)은 표 하나로 따로 둔다.

## 갈 수 있는 길만 그려 둔다

상태마다 다른 동작이 많지 않고 "이 상태에서 이 이벤트가 오면 저 상태로"가 대부분이라면, 클래스 대신 전이표 하나로 충분하다. 이것이 유한 상태 기계(Finite State Machine)다. 상태 패턴은 상태 기계를 객체로 짜는 방법 중 하나이고, 전이표는 데이터로 짜는 방법이다.

```ts
type State = "pending" | "paid" | "shipped" | "delivered" | "cancelled";
type Event = "pay" | "ship" | "deliver" | "cancel";

const transitions: Record<State, Partial<Record<Event, State>>> = {
  pending: { pay: "paid", cancel: "cancelled" },
  paid: { ship: "shipped", cancel: "cancelled" },
  shipped: { deliver: "delivered" },
  delivered: {},
  cancelled: {},
};

function next(state: State, event: Event): State {
  const to = transitions[state][event];
  if (!to) throw new Error(`${state}에서 ${event}는 갈 수 없는 길이다`);
  return to;
}
```

표로 두면 그림을 그리기 쉽다. 아래는 이 표를 그대로 옮긴 길이다. 다음을 누르면 이벤트가 상태 사이를 옮겨 다니고, 표에 없는 길로 가려는 이벤트는 막힌다.

### 화면 상태에도 같은 문제가 있다

```ts
type FetchState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "error"; error: Error }
  | { status: "success"; data: T };

function render(s: FetchState<string[]>): string {
  switch (s.status) {
    case "idle": return "";
    case "loading": return "불러오는 중";
    case "error": return s.error.message; // 이 갈래에서만 error가 있다
    case "success": return s.data.join(", ");
    default: {
      const never: never = s; // 갈래를 하나 더하고 여기를 안 고치면 컴파일 에러
      return never;
    }
  }
}
```

이건 클래스 없는 상태 패턴이다. 상태마다 들고 있는 데이터가 다르고(`error`는 error 갈래에만), 동작은 `switch`가 고른다. 처음 코드의 `switch`와 다른 점은 `never` 검사 덕분에 빠뜨린 갈래가 컴파일 에러로 드러난다는 것이다. TanStack Query v5가 `status`를 `'pending' | 'error' | 'success'` 하나로 두고, 가져오는 중인지는 `fetchStatus`라는 별도 축으로 나눈 것도 같은 생각이다.

## XState로 옮기면

같은 설정을 실제로 돌리면 이렇다. `pending`에서 보낸 `SHIP`과, 금액이 모자라 가드에 걸린 `PAY`는 상태를 바꾸지 못한다.

```text
after SHIP in pending: pending
after PAY 1000: pending
can CANCEL: true  can DELIVER: false
shipped { trackingNo: 'CJ-1234' }
```

라이브러리가 상태 패턴을 대신해 주는 것은 아니다. 전이 규칙은 라이브러리에 맡기고, 상태마다 다른 실제 동작(환불, 알림)은 여전히 우리 코드다. 대신 시각화 도구, 전이 테스트, 시간 제한(`after`) 같은 것을 공짜로 얻는다. 상태 다섯 개에 전이 열 개 정도라면 앞의 전이표 하나가 더 읽기 쉽다.

## 이미 매일 쓰는 상태 기계

`Promise`는 `pending`에서 `fulfilled`나 `rejected`로 한 번만 가는 상태 기계다. 한 번 정해지면 `resolve`를 다시 불러도 아무 일이 없다. 위 주문의 `Cancelled.cancel`이 조용히 넘어가는 것과 같은 규칙이다.

TCP 연결도 커널 안의 상태 기계다. `ss -tan`이 보여 주는 `ESTAB`, `TIME-WAIT`, `CLOSE-WAIT`가 상태 이름이고, 같은 패킷(FIN)을 받아도 지금 상태에 따라 다음 상태가 다르다. 그 전이는 [TCP 연결의 일생](/posts/tcp-connection-lifecycle)에서 실제 캡처로 따라갔다. 장애 대응에서 자주 보는 [서킷 브레이커](/posts/circuit-breaker)도 닫힘, 열림, 반열림 세 상태를 오가는 기계다. 같은 `call()`이 닫힘에서는 요청을 보내고, 열림에서는 바로 실패하고, 반열림에서는 몇 개만 시험 삼아 보낸다. GoF의 상태 패턴이 정확히 이 모양이다.

## 메모리 밖에서 상태가 바뀔 때

상태 패턴은 한 프로세스의 메모리 안에서 동작을 고른다. 그런데 주문 상태의 진짜 원본은 DB에 있다. 서버 두 대가 같은 주문을 동시에 불러오면 각자 자기 메모리에 `Paid` 상태를 들고 있게 된다. 배송 처리와 고객의 취소 요청이 거의 같은 순간에 들어온 상황을 흉내 내 봤다. 둘 다 DB에서 읽고, 상태를 검사하고, 행 전체를 저장한다.

```text
[ 'shipped', 'cancelled' ]
{ id: 42, status: 'shipped', trackingNo: 'CJ-1234', refunded: false }
```

두 요청이 모두 성공했다. 둘 다 읽을 때는 `paid`였으니 상태 객체 입장에서는 둘 다 정당한 전이다. 취소 쪽은 환불을 요청했을 텐데, DB에는 배송 쪽이 나중에 덮어써서 `shipped`가 남았다. 환불은 나갔는데 상품도 나간다.

메모리의 상태 객체는 "이 전이가 규칙에 맞나"만 판단할 수 있다. "읽은 뒤에 누가 바꾸지 않았나"는 DB가 판단해야 한다. 가장 간단한 방법은 기대하는 지금 상태를 `WHERE`에 넣는 조건부 UPDATE다. PostgreSQL 16에서 배송이 먼저 반영된 뒤 취소가 들어온 경우다.

```sql
-- 배송: paid일 때만 shipped로 바꾼다
UPDATE orders SET status = 'shipped' WHERE id = 42 AND status = 'paid';
-- 취소: 결제 전이나 결제 완료일 때만. 이미 shipped라 바뀌는 행이 없다
UPDATE orders SET status = 'cancelled', refunded = true
WHERE id = 42 AND status IN ('pending', 'paid')
RETURNING status;
```

```text
UPDATE 1
 status 
--------
(0 rows)

UPDATE 0
```

`UPDATE 0`이 "지는 쪽"이라는 신호다. 코드에서는 바뀐 행 수가 0이면 상태를 다시 읽어 사용자에게 "이미 배송이 시작됐다"고 알린다. 환불 같은 외부 호출은 이 UPDATE가 성공한 다음에 한다. 순서를 거꾸로 하면 위와 같은 사고가 난다. 버전 컬럼으로 같은 문제를 푸는 법은 [낙관적 잠금](/posts/optimistic-locking)에서, 재고처럼 숫자가 줄어드는 경우는 [조건부 UPDATE와 잠금](/posts/db-locking-deadlock)에서 다뤘다.

정리하면 전이표는 두 곳에 있어야 한다. 애플리케이션의 상태 객체(또는 표)는 규칙을 설명하고 빠른 에러를 내고, DB의 조건부 UPDATE는 동시에 들어온 요청 중 하나만 이기게 한다.

## 전략과 같은 모양, 다른 질문

클래스 다이어그램만 보면 상태 패턴은 [전략 패턴](/posts/pattern-strategy)과 똑같다. Context가 인터페이스 타입의 필드를 들고 일을 넘긴다. 다른 것은 누가, 언제 그 필드를 바꾸느냐다.

전략은 바깥(Client나 설정)이 골라서 넣고, 넣은 뒤에는 대개 그대로다. 전략끼리는 서로를 모른다. 상태는 객체가 일하는 도중에 스스로 바뀌고, 상태 객체들이 다음 상태를 안다. "이 필드는 사용자가 고른 옵션인가, 객체가 살아가며 지나는 단계인가"를 물어보면 갈린다. 정렬 방식이나 압축 알고리즘은 전략이고, 주문 단계나 연결 상태는 상태다.

## 상태 클래스가 필요 없는 때

상태가 둘이고 다른 동작이 한두 개라면 `boolean` 하나와 `if` 하나가 낫다. `isOpen`으로 열고 닫는 드롭다운에 `OpenState`, `ClosedState`를 만들면 읽는 사람이 파일 세 개를 오가야 한다. 처음 코드의 `switch`가 메서드 두세 곳에만 있다면 아직 버틸 만하다. 같은 `switch`가 세 곳 이상에 복사되기 시작하거나, 상태를 하나 더할 때 놓친 곳에서 버그가 난 적이 있다면 그때 꺼낸다.

반대쪽 실수는 상태마다 클래스를 만들고 나서 상태끼리 공통 동작을 상속으로 나누는 것이다. `ShippedState extends PaidState` 같은 상속이 생기면 "결제 완료에서 되던 일이 배송 중에도 되는" 사고가 숨어 들어온다. 공통 거절 동작은 앞의 `reject` 같은 작은 함수로 나누는 편이 안전하다.

테스트는 상태 패턴의 숨은 장점이다. 상태 객체 하나를 떼어 "Paid에서 cancel을 부르면 환불을 요청하고 Cancelled로 간다"를 확인하면 된다. 전이표 방식이라면 표의 모든 칸(상태 × 이벤트)을 도는 테스트 하나로 "허용되지 않은 길이 정말 막혔나"를 한꺼번에 확인할 수 있다.

## 면접에서 나올 만한 질문

### 상태 패턴은 무엇이고 언제 쓰나요?

객체의 상태에 따라 같은 메서드가 다르게 동작해야 할 때, 상태마다 동작을 객체로 묶고 Context는 지금 상태 객체에 일을 넘기게 하는 패턴이다. 메서드마다 같은 상태 `switch`가 반복되고, 상태를 하나 더할 때 여러 곳을 고쳐야 하는 냄새가 신호다. 상태가 둘뿐이고 다른 동작이 적다면 `boolean`과 `if`가 낫다.

### 상태 전이는 Context와 상태 객체 중 어디서 결정하나요?

둘 다 가능하고 트레이드오프가 있다. 상태 객체가 정하면 새 상태를 넣기 쉽지만 상태 객체들이 서로를 알게 되고 전체 흐름이 흩어진다. Context에 모으면 한눈에 보이지만 상태가 늘수록 다시 큰 `switch`가 된다. 실무에서는 동작은 상태 객체에, 허용되는 전이는 표 하나에 두는 절충을 많이 쓴다.

### 상태 패턴과 전략 패턴은 어떻게 다른가요?

구조는 같지만 필드를 바꾸는 주체와 시점이 다르다. 전략은 바깥에서 골라 넣고 보통 그대로 두며 전략끼리 서로 모른다. 상태는 객체가 일하는 도중에 스스로 바뀌고 상태 객체가 다음 상태를 안다. 사용자가 고른 옵션이면 전략, 객체가 살아가며 지나는 단계면 상태다.

### 상태 패턴과 유한 상태 기계는 같은 건가요?

유한 상태 기계는 상태, 이벤트, 전이로 이루어진 모델이고, 상태 패턴은 그걸 객체지향으로 구현하는 방법 중 하나다. 전이가 대부분이면 전이표나 XState 같은 라이브러리가 더 단순하고, 상태마다 동작이 크게 다르면 상태 객체가 낫다. 타입스크립트에서는 판별 유니온과 `never` 검사로 빠진 상태를 컴파일 시점에 잡을 수 있다.

### 상태 객체는 주문마다 새로 만들어야 하나요?

상태 객체에 필드가 없으면 하나만 만들어 모든 Context가 공유하면 된다. 주문이 많아도 상태 객체는 상태 수만큼만 있다. 재시도 횟수나 진입 시각처럼 상태별 데이터가 있으면 전이할 때마다 새로 만들어 그 값을 상태 안에 둔다.

### 서버 여러 대가 같은 주문의 상태를 바꾸면 무슨 문제가 생기나요?

각 서버가 읽은 시점의 상태로 판단하므로 둘 다 정당한 전이라고 보고 서로 덮어쓸 수 있다. 배송과 취소가 동시에 성공해 환불도 나가고 상품도 나가는 식이다. 그래서 `WHERE status = 'paid'` 같은 조건부 UPDATE나 버전 컬럼으로 DB에서 한쪽만 이기게 하고, 바뀐 행이 0이면 실패로 처리한다. 환불 같은 외부 호출은 그 UPDATE가 성공한 뒤에 한다.

### 프런트엔드에서 isLoading, isError 플래그를 따로 두면 왜 문제인가요?

플래그 세 개면 조합이 여덟 개인데 말이 되는 건 넷뿐이라, 나머지 칸이 버그가 된다. `status` 하나를 가진 판별 유니온으로 바꾸면 불가능한 조합이 타입에서 사라지고, 에러 갈래에만 `error`, 성공 갈래에만 `data`가 있게 된다. 클래스 없이 쓰는 상태 패턴이라고 볼 수 있다.
