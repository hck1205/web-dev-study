입력 종류에 따라 반환 타입이 바뀌는 `parse` 함수를 만들었다. 부르는 쪽에서는 타입이 정확히 나온다. 그런데 함수 안의 `return` 두 줄이 모두 빨간 줄이다.

```ts
type Parsed<T extends "number" | "string"> = T extends "number" ? number : string;

function parse<T extends "number" | "string">(kind: T, raw: string): Parsed<T> {
  if (kind === "number") return Number(raw);
  return raw;
}
const a = parse("number", "42");   // number
const b = parse("string", "hi");   // string
```

```text
hook.ts(4,26): error TS2322: Type 'number' is not assignable to type 'Parsed<T>'.
hook.ts(5,3): error TS2322: Type 'string' is not assignable to type 'Parsed<T>'.
```

`kind === "number"`을 확인했으니 `Number(raw)`는 맞는 값이다. 그래도 TypeScript는 받아 주지 않는다. 이 글은 이 에러가 왜 나는지에서 출발해, 조건부 타입이 언제 계산되고 언제 미뤄지는지, `infer`가 여러 자리에서 무엇을 잡는지, 템플릿 리터럴 타입과 재귀로 문자열과 경로를 다루는 법, `never`를 거름망과 검사 대상으로 쓰는 법, 그리고 이런 타입을 어디까지 써야 하는지를 본다. 출력은 TypeScript 5.9.3의 `tsc --strict`와, 에디터의 hover처럼 타입을 펼쳐 주는 작은 스크립트(컴파일러 API의 `typeToString`)로 찍었다.

이 주제의 다른 글: 조건부 타입의 기본 문법, 분배와 `[T]`로 막기, `infer`로 `ReturnType`을 만드는 법, 이벤트 이름과 라우트 매개변수를 템플릿 리터럴로 만드는 법, 재귀 깊이 한계 TS2589, `satisfies`와 타입 주석의 차이는 [유틸리티 타입과 매핑된 타입](/posts/ts-utility-mapped-types)에서 다뤘다. 이 글은 그다음 질문들, "왜 함수 안에서는 안 되나", "두 자리에서 잡으면 무엇이 나오나", "재귀 타입은 어디서 무너지나"에 답한다. 타입 매개변수와 제약 자체는 [제네릭](/posts/ts-generics)에 있다.

## 조건부 타입은 언제 계산되나

`T extends U ? X : Y`는 `T`가 무엇인지 알아야 갈래를 고를 수 있다. 부르는 자리에서는 `T`가 `"number"`로 정해지니 바로 `number`가 나온다. 함수 안에서는 다르다. `T`는 아직 "number나 string 중 무엇인가"일 뿐이라, `Parsed<T>`는 계산되지 못하고 `Parsed<T>`라는 모양 그대로 남는다. 이렇게 갈래를 정하지 못해 미뤄 둔 조건부 타입을 지연된(deferred) 조건부 타입이라고 한다.

미뤄진 타입에는 거의 아무것도 할당할 수 없다. `number`가 `Parsed<T>`에 들어가려면 어떤 `T`가 와도 들어가야 하는데, `T`가 `"string"`이면 `Parsed<T>`는 `string`이다. 그럼 `kind === "number"` 검사는 왜 소용이 없을까. 그 검사가 좁히는 건 값 `kind`의 타입이지 타입 매개변수 `T`가 아니다. `kind`가 `"number"`라는 사실에서 `T`가 `"number"`라는 결론을 끌어내려면 `T`가 유니온이 아닌 리터럴 하나라는 보장이 필요한데, `parse<"number" | "string">(...)`처럼 부르는 것도 허용되니 그 보장이 없다. 아래 그림에서 다음을 누르며 같은 `Parsed<T>`가 부르는 쪽과 함수 안에서 어떻게 다르게 다뤄지는지 따라가 보자.

조건부 타입이 미뤄지는 건 검사하는 쪽에 아직 정해지지 않은 타입 매개변수가 남아 있을 때다. 제약으로 답이 뻔해 보여도 마찬가지다. `function f<T extends string>(x: T): T extends string ? 1 : 2`에서 `return 1`을 해도 `Type '1' is not assignable to type 'T extends string ? 1 : 2'`가 난다. `T`는 반드시 `string`이니 항상 `1`일 것 같지만, 검사기는 미뤄진 조건부 타입의 갈래를 제약만 보고 미리 고르지 않는다. 그래서 함수 시그니처의 반환 타입에 타입 매개변수를 품은 조건부 타입을 쓰면 본문에서 고생한다고 기억해 두면 된다.

## 오버로드와 구현 표로 풀기

흔히 쓰는 출구는 셋이다. 첫째는 `return Number(raw) as Parsed<T>`처럼 단언하는 것이다. 동작은 하지만 검사를 끈 것이라, `"number"` 갈래에서 실수로 `raw`를 돌려줘도 아무도 모른다.

둘째는 오버로드다. 부르는 쪽에 보일 시그니처를 경우마다 따로 쓰고, 구현은 넓은 타입으로 한 번 쓴다.

```ts
function parse1(kind: "number", raw: string): number;
function parse1(kind: "string", raw: string): string;
function parse1(kind: "number" | "string", raw: string): number | string {
  return kind === "number" ? Number(raw) : raw;
}
const o1 = parse1("number", "42");   // number
declare const k: "number" | "string";
parse1(k, "1");
```

```text
fix.ts(8,8): error TS2769: No overload matches this call.
    Overload 1 of 2, '(kind: "number", raw: string): number', gave the following error.
      Argument of type '"string" | "number"' is not assignable to parameter of type '"number"'.
```

부르는 쪽 타입은 정확하다. 대신 두 가지를 알고 쓴다. 유니온 인자로는 부를 수 없다(오버로드는 시그니처 하나에 통째로 맞아야 한다). 그리고 구현 시그니처는 오버로드와 대조되지 않는다. 구현을 `kind === "number" ? raw : Number(raw)`로 거꾸로 써도 에러가 나지 않았다. 오버로드는 약속을 적는 것이고, 지키는지는 테스트가 본다.

셋째가 가장 튼튼하다. 조건부 타입 대신 "키에서 타입으로 가는 표"를 인터페이스로 두고, 구현도 같은 키를 가진 객체로 둔다.

```ts
interface ParseMap { number: number; string: string; boolean: boolean }

const parsers: { [K in keyof ParseMap]: (raw: string) => ParseMap[K] } = {
  number: Number,
  string: (raw) => raw,
  boolean: (raw) => raw === "true",
};

function parse3<K extends keyof ParseMap>(kind: K, raw: string): ParseMap[K] {
  return parsers[kind](raw);
}
const o3 = parse3("boolean", "true");   // boolean
```

에러 없이 통과한다. `parsers[kind]`의 타입이 `(raw: string) => ParseMap[K]`로 계산되고, 그 결과가 반환 타입과 같은 모양이라 검사기가 맞춰 볼 수 있다. 같은 표를 쓰면서 본문에서 분기하면 여전히 에러가 난다. 메시지가 힌트를 준다.

```ts
function parse2<K extends keyof ParseMap>(kind: K, raw: string): ParseMap[K] {
  if (kind === "number") return Number(raw);
  return raw as ParseMap[K];
}
```

```text
map.ts(3,26): error TS2322: Type 'number' is not assignable to type 'ParseMap[K]'.
    Type 'number' is not assignable to type 'never'.
```

`K`를 모를 때 `ParseMap[K]`에 값을 쓰려면 모든 갈래의 타입을 동시에 만족해야 해서 `number & string & boolean`, 즉 `never`가 된다. 분기 대신 표를 거쳐 꺼내면 이 문제가 없다. 반환 타입이 입력에 따라 바뀌는 함수는 조건부 타입보다 "인터페이스 표 + 인덱스 접근"으로 먼저 설계해 본다.

## 분배가 일어나는 자리, 일어나지 않는 자리

조건부 타입이 유니온을 멤버마다 쪼개 계산하는 분배 동작은 [유틸리티 타입 글](/posts/ts-utility-mapped-types)에서 봤다. 여기서는 그 규칙이 "검사 자리에 맨 타입 매개변수가 올 때만" 적용된다는 점을 몇 가지 모양으로 확인한다.

```ts
type ToArray<T> = T extends unknown ? T[] : never;
type ToArrayND<T> = [T] extends [unknown] ? T[] : never;
type A1 = ToArray<string | number>;
type A2 = ToArrayND<string | number>;

type IsTrue<T> = T extends true ? "yes" : "no";
type A3 = IsTrue<boolean>;

type Wrap<T> = { value: T } extends { value: string } ? "str" : "other";
type A4 = Wrap<string | number>;
```

```text
type A1 = string[] | number[]
type A2 = (string | number)[]
type A3 = "no" | "yes"
type A4 = "other"
```

`A1`과 `A2`는 결과가 다른 타입이다. `string[] | number[]`는 "전부 문자열인 배열이거나 전부 숫자인 배열"이고, `(string | number)[]`는 섞인 배열이다. API 응답 배열 타입을 만드는 헬퍼가 의도치 않게 분배되면 섞인 배열을 넣을 때 에러가 난다.

`A3`는 `boolean`이 사실 `true | false`라서 생긴 일이다. "참이면"을 물었는데 `"yes" | "no"`가 나왔다. 불리언 옵션을 받아 타입을 바꾸는 헬퍼에서 `boolean`이 들어오면 두 갈래가 합쳐진다는 걸 알아 둔다.

`A4`는 분배되지 않았다. 검사 자리가 맨 `T`가 아니라 `{ value: T }`로 감싼 모양이라서 유니온을 통째로 묻는다. `{ value: string | number }`는 `{ value: string }`에 들어가지 않으니 `"other"`다. 분배는 편리하지만 의도하지 않은 곳에서도 일어난다. 헬퍼를 만들 때 유니온을 넣어 결과를 직접 찍어 보는 것이 가장 빠른 확인법이다.

## infer가 두 자리에서 잡으면

`infer`는 조건부 타입의 `extends` 오른쪽에서 "이 자리의 타입을 이름 붙여 잡아 달라"는 표시다. 같은 이름을 두 자리에 쓰면 어떻게 될까. 자리의 성격에 따라 결과가 다르다.

```ts
type Both<T> = T extends { a: infer U; b: infer U } ? U : never;
type I1 = Both<{ a: string; b: number }>;

type Args<T> = T extends { a: (x: infer U) => void; b: (x: infer U) => void } ? U : never;
type I2 = Args<{ a: (x: { id: number }) => void; b: (x: { name: string }) => void }>;
```

```text
type I1 = string | number
type I2 = { id: number; } & { name: string; }
```

속성 값 자리처럼 "꺼내 읽는" 자리(공변 위치)에서 두 번 잡으면 후보를 유니온으로 합친다. `a`의 값도, `b`의 값도 `U`로 읽힐 수 있어야 하니 둘 중 무엇이든 될 수 있는 타입이다. 함수 매개변수처럼 "넣어 주는" 자리(반공변 위치)에서 두 번 잡으면 교집합이 된다. 두 함수에 같은 값을 넘겨야 한다면 그 값은 두 함수가 원하는 것을 모두 갖춰야 하기 때문이다.

이 성질로 유니온을 교집합으로 바꾸는 유명한 헬퍼가 나온다.

```ts
type UnionToIntersection<U> =
  (U extends unknown ? (x: U) => void : never) extends (x: infer I) => void ? I : never;
type I3 = UnionToIntersection<{ id: number } | { name: string }>;
type I4 = UnionToIntersection<string | number>;
```

```text
type I3 = { id: number; } & { name: string; }
type I4 = never
```

앞쪽의 분배가 유니온 멤버마다 함수 타입을 만들어 `((x: A) => void) | ((x: B) => void)`를 만들고, 뒤쪽에서 매개변수 자리를 `infer`로 잡으니 `A & B`가 된다. 플러그인 여러 개의 설정 타입을 하나로 합칠 때 쓴다. `string & number`처럼 함께 있을 수 없는 타입이면 `never`가 된다.

오버로드된 함수에서 잡으면 마지막 시그니처만 본다.

```ts
declare function format(x: number): string;
declare function format(x: string): number;
type I5 = ReturnType<typeof format>;
type I6 = Parameters<typeof format>;
```

```text
type I5 = number
type I6 = [x: string]
```

`format(1)`은 `string`을 돌려주는데 `ReturnType`은 `number`라고 한다. 조건부 타입은 오버로드 중 하나를 고를 방법이 없어서 마지막 것을 쓴다. 라이브러리 함수의 `ReturnType`이 이상하게 나오면 오버로드가 있는지부터 본다. 가장 넓은 시그니처를 마지막에 두는 관례도 이 때문이다.

## infer에 제약을 걸어 문자열을 숫자로

TypeScript 4.7부터 `infer`에 `extends` 제약을 붙일 수 있다. 잡은 타입이 제약에 맞을 때만 참 갈래로 간다. 4.8부터는 템플릿 리터럴 안에서 `infer N extends number`라고 쓰면 문자열 조각을 숫자 리터럴 타입으로 바꿔 준다.

```ts
type ToNum<S> = S extends `${infer N extends number}` ? N : never;
type I7 = ToNum<"42">;
type I8 = ToNum<"4.2e1">;
type I9 = ToNum<"abc">;

type First<T> = T extends [infer H extends string, ...unknown[]] ? H : never;
type K1 = First<["a", 1]>;
type K2 = First<[1, "a"]>;
```

```text
type I7 = 42
type I8 = number
type I9 = never
type K1 = "a"
type K2 = never
```

`"42"`는 `42`가 됐다. `"4.2e1"`은 숫자로 읽히긴 하지만 `42`를 다시 문자열로 쓰면 `"42"`가 되어 원래 글자와 다르니, 리터럴로 굳히지 않고 `number`로 남겼다. URL의 `/page/3`에서 `3`을 숫자 리터럴로 꺼내거나, `"v2"`에서 버전 번호를 꺼내는 타입이 이 방식으로 만들어진다. 제약이 없던 시절에는 `infer H` 뒤에 `H extends string ? ... : never`를 한 번 더 써야 했다.

## Awaited를 직접 만들어 보기

`async` 함수의 결과 타입을 꺼내려고 `Promise` 안을 여는 타입을 직접 만들면 보통 이렇게 시작한다.

```ts
type Unwrap1<T> = T extends Promise<infer U> ? U : T;
type Thenable = { then(cb: (v: { ok: true }) => void): void };
type W1 = Unwrap1<Promise<Promise<number>>>;
type W3 = Unwrap1<Thenable>;
```

```text
type W1 = Promise<number>
type W3 = { then(cb: (v: { ok: true; }) => void): void; }
```

두 군데서 틀렸다. 겹친 `Promise`를 한 겹만 벗겼고, `then` 메서드만 가진 객체(thenable)는 열지 못했다. 런타임의 `await`는 둘 다 끝까지 연다. `await`는 `Promise` 클래스를 확인하는 게 아니라 "호출할 수 있는 `then`이 있는 객체"인지 보고, 결과가 또 thenable이면 다시 연다. 이 동작을 타입으로 옮기면 TypeScript 내장 `Awaited`와 같은 모양이 된다.

```ts
type MyAwaited<T> =
  T extends null | undefined ? T :
  T extends object & { then(onfulfilled: infer F, ...args: infer _): any }
    ? F extends (value: infer V, ...args: infer _) => any
      ? MyAwaited<V>          // 꺼낸 값을 다시 연다
      : never                 // then은 있는데 콜백 자리가 함수가 아니다
    : T;                      // thenable이 아니면 그대로
type W2 = MyAwaited<Promise<Promise<number>>>;
type W4 = MyAwaited<Thenable>;
type W5 = MyAwaited<string | Promise<boolean>>;
```

```text
type W2 = number
type W4 = { ok: true; }
type W5 = string | boolean
```

`lib.es5.d.ts`의 `Awaited` 정의도 줄마다 같다. 아래 그림에서 다음을 누르면 `MyAwaited<Promise<Promise<number>>>`가 한 겹씩 열리는 과정을 볼 수 있다.

```ts
type MyReturn<T extends (...args: any) => any> = T extends (...args: any) => infer R ? R : never;
async function fetchUser(id: number) { return { id, name: "Kim" }; }
type W8 = MyAwaited<MyReturn<typeof fetchUser>>;
```


함수에서 타입을 뽑아 쓸 때의 방향 문제(구현이 정답 타입이 되어 버리는 것)는 [유틸리티 타입 글](/posts/ts-utility-mapped-types)에서 짚었다. 바깥에서 들어오는 데이터라면 계약 타입을 먼저 두고 함수를 그 타입에 맞춘다.

## 문자열을 자르고 붙이는 타입

템플릿 리터럴 타입에 `infer`를 넣으면 문자열을 패턴으로 자를 수 있고, 재귀를 더하면 반복도 된다. 이벤트 이름 만들기와 라우트 매개변수 추출은 [유틸리티 타입 글](/posts/ts-utility-mapped-types)에 있으니, 여기서는 그 재료가 되는 자르기·다듬기·잇기를 만든다.

```ts
type Split<S extends string, D extends string> =
  S extends `${infer Head}${D}${infer Tail}` ? [Head, ...Split<Tail, D>] : [S];
type TrimLeft<S extends string> = S extends ` ${infer R}` ? TrimLeft<R> : S;
type Join<T extends string[], D extends string> =
  T extends [infer F extends string, ...infer R extends string[]]
    ? R extends [] ? F : `${F}${D}${Join<R, D>}`
    : "";

type S1 = Split<"a.b.c", ".">;
type S2 = TrimLeft<"   hi">;
type S3 = Join<["user", "address", "city"], "/">;
type S4 = Split<"", ".">;
```

```text
type S1 = ["a", "b", "c"]
type S2 = "hi"
type S3 = "user/address/city"
type S4 = [""]
```

`Split`은 처음 나오는 구분자에서 앞(`Head`)과 뒤(`Tail`)로 나누고 뒤를 다시 자른다. 템플릿 리터럴의 `infer`는 왼쪽부터 가장 짧게 잡는다. 그래서 `Head`는 첫 `.` 앞까지만 잡힌다. `S4`처럼 빈 문자열은 `[""]`가 된다. 런타임의 `"".split(".")`도 `[""]`를 돌려주니 맞는 동작이다. 이런 타입은 런타임 함수와 같은 규칙을 따라야 쓸모가 있어서, 경계 사례를 런타임과 같이 확인하는 습관이 필요하다.

## 이벤트 이름과 인자를 한 표에서

조건부 타입이 실무에서 가장 쓸모 있는 곳 중 하나가 "인자가 있을 때와 없을 때"를 가르는 것이다. 이벤트 버스의 이벤트 표를 하나 두고, 거기서 `emit`의 인자 개수와 핸들러 이름을 모두 뽑아 보자.

```ts
interface Events {
  "cart/add": { id: number; qty: number };
  "cart/clear": void;
  "user/login": { userId: string };
}

declare function emit<K extends keyof Events>(
  name: K,
  ...args: Events[K] extends void ? [] : [payload: Events[K]]
): void;

emit("cart/clear");
emit("cart/add", { id: 1, qty: 2 });
emit("cart/add");
emit("cart/clear", {});
```

```text
emit.ts(14,1): error TS2554: Expected 2 arguments, but got 1.
emit.ts(15,20): error TS2554: Expected 1 arguments, but got 2.
```

나머지 매개변수 자리에 조건부 타입으로 튜플을 고르게 했다. 페이로드가 `void`면 빈 튜플이라 인자를 받지 않고, 아니면 이름 붙은 원소 하나를 받는다. `payload?:`로 선택 인자를 만드는 것보다 정확하다. 선택 인자로 두면 `emit("cart/add")`가 통과해 버린다.

같은 표에서 핸들러 객체 타입도 뽑는다. 키 이름을 바꾸는 매핑된 타입의 `as`와 위의 `Split`을 함께 쓴다.

```ts
type Handlers = {
  [K in keyof Events as `on${Capitalize<Split<K & string, "/">[1]>}`]: (payload: Events[K]) => void;
};
```

```text
type Handlers = { onAdd: (payload: { id: number; qty: number; }) => void; onClear: (payload: void) => void; onLogin: (payload: { userId: string; }) => void; }
```

`"cart/add"`가 `/`로 잘려 `"add"`, 첫 글자가 대문자가 되어 `onAdd`가 됐다. 이벤트를 하나 추가하면 `emit`의 검사와 핸들러 이름이 함께 바뀐다. 다만 `"cart/add"`와 `"wishlist/add"`가 함께 있으면 둘 다 `onAdd`가 되어 한 키로 합쳐진다. 키를 계산해 만들 때는 계산 결과가 겹칠 수 있는지 함께 본다.

## 점으로 이은 경로와 재귀의 끝

폼 라이브러리는 `register("profile.address.zip")`처럼 점으로 이은 경로 문자열을 받는다. 오타를 컴파일 시간에 잡으려면 가능한 경로를 모두 유니온으로 만드는 타입이 필요하다. 재귀 매핑된 타입으로 만든다.

```ts
type Path<T> = T extends object
  ? { [K in keyof T & string]: T[K] extends object ? K | `${K}.${Path<T[K]>}` : K }[keyof T & string]
  : never;
type PathValue<T, P extends string> =
  P extends `${infer K}.${infer Rest}`
    ? K extends keyof T ? PathValue<T[K], Rest> : never
    : P extends keyof T ? T[P] : never;

interface SignupForm {
  email: string;
  profile: { nickname: string; address: { city: string; zip: string } };
  agree: boolean;
}
type P1 = Path<SignupForm>;
type P2 = PathValue<SignupForm, "profile.address.zip">;

declare function register<P extends Path<SignupForm>>(name: P): { value: PathValue<SignupForm, P> };
register("profile.adress.zip");
```

```text
type P1 = "email" | "profile" | "agree" | "profile.address" | "profile.nickname" | "profile.address.city" | "profile.address.zip"
type P2 = string
path.ts(18,10): error TS2345: Argument of type '"profile.adress.zip"' is not assignable to parameter of type '"email" | "profile" | "agree" | "profile.address" | "profile.nickname" | "profile.address.city" | "profile.address.zip"'.
```

`{ [K in ...]: ... }[keyof T]` 모양은 "키마다 값을 계산한 객체를 만들고, 그 값들을 유니온으로 모으는" 관용구다. 오타 `adress`가 잡혔고, `PathValue`로 그 경로의 값 타입까지 꺼냈다.

이 타입은 자기 자신을 가리키는 데이터에서 무너진다. 댓글이 답글 배열을 갖는 구조에 배열 처리까지 넣어서 걸어 봤다.

```ts
type Path<T> = T extends readonly (infer E)[]
  ? `${number}` | `${number}.${Path<E>}`
  : T extends object
    ? { [K in keyof T & string]: K | `${K}.${Path<T[K]>}` }[keyof T & string]
    : never;
interface Reply { id: number; body: string; replies: Reply[] }
type R1 = Path<Reply>;
```

```text
rec.ts(7,11): error TS2615: Type of property 'replies' circularly references itself in mapped type '{ [K in "id" | "body" | "replies"]: K | `${K}.${Path<Reply[K]>}`; }'.
type R1 = any
```

경로가 끝없이 길어질 수 있으니 계산이 끝나지 않는다. 에러도 문제지만 더 위험한 건 결과가 `any`가 된다는 점이다. 에러를 `// @ts-ignore`로 덮고 쓰면 `register`가 아무 문자열이나 받아 오타를 하나도 못 잡는다. 이럴 땐 깊이를 세는 카운터를 매개변수로 넣는다.

```ts
type Prev = [never, 0, 1, 2, 3, 4];
type Path<T, D extends number = 4> = [D] extends [never]
  ? never
  : T extends readonly (infer E)[]
    ? `${number}` | `${number}.${Path<E, Prev[D]>}`
    : T extends object
      ? { [K in keyof T & string]: K | `${K}.${Path<T[K], Prev[D]>}` }[keyof T & string]
      : never;
type R1 = Path<Reply, 2>;
```

```text
type R1 = "id" | "body" | "replies" | `replies.${number}` | `replies.${number}.id` | `replies.${number}.body` | `replies.${number}.replies`
```

`Prev[D]`는 튜플에서 한 칸 앞 숫자를 꺼내 1을 빼는 효과를 낸다. 0에서 한 번 더 빼면 `never`가 되고, 첫 줄의 `[D] extends [never]`가 재귀를 멈춘다. `never`를 검사할 때 `[ ]`로 감싸야 하는 이유는 아래에서 다시 본다. 실제 폼 라이브러리들도 이런 식으로 깊이를 제한한다.

깊이를 제한해도 큰 타입에 걸면 비용이 크다. 위 `Path`를 DOM 타입 `HTMLInputElement`에 걸고 `tsc --extendedDiagnostics`로 쟀다. 기준은 `export const x = 1` 한 줄짜리 파일이다.

```text
기준 파일            Instantiations 4762     Check time 0.76s
SignupForm 경로      Instantiations 5182     Check time 0.98s
HTMLInputElement 깊이 1  Instantiations 43468    Check time 1.46s
HTMLInputElement 깊이 2  Instantiations 97696    Check time 4.27s
HTMLInputElement 깊이 3  (10분이 지나도 끝나지 않아 멈췄다)
```

깊이 하나에 검사 시간이 세 배씩 늘고, 세 단계에서는 사실상 멈췄다. 에디터라면 자동 완성과 hover가 그동안 응답하지 않는다. 경로 타입은 내가 정의한 작은 폼 타입에만 걸고, DOM 객체나 라이브러리의 거대한 타입에는 걸지 않는다. 어느 타입이 느린지 찾는 `--generateTrace` 사용법은 [tsconfig와 strict 옵션](/posts/tsconfig-strict)에 있다.

## never로 거르고, never인지 묻기

`never`는 값이 하나도 없는 타입이고, 유니온 안에서는 빈 집합이라 사라진다. 이 성질 덕분에 "조건에 안 맞으면 never"를 돌려주는 것만으로 거름망이 된다. 튜플을 거를 때와 키를 거를 때를 보자.

```ts
type Filter<T extends unknown[], U> = T extends [infer H, ...infer R]
  ? H extends U ? [H, ...Filter<R, U>] : Filter<R, U>
  : [];
type E1 = Filter<[1, "a", 2, true, 3], number>;

type KeysOfType<T, V> = { [K in keyof T]-?: T[K] extends V ? K : never }[keyof T];
interface Product { id: number; name: string; price: number; memo?: string }
type E2 = KeysOfType<Product, number>;
```

```text
type E1 = [1, 2, 3]
type E2 = "id" | "price"
```

튜플은 유니온이 아니라서 `never`를 넣으면 빈칸으로 남는다. 그래서 `Filter`는 맞지 않는 원소를 아예 펼치지 않는 식으로 건너뛴다. `KeysOfType`은 키마다 "맞으면 키, 아니면 never"를 계산한 뒤 값을 모았고, `never`가 유니온에서 빠지며 숫자 필드 이름만 남았다. `-?`를 붙인 건 선택 필드의 `undefined`가 섞여 조건이 틀어지지 않게 하려는 것이다. 정렬 가능한 컬럼만 받는 표 컴포넌트의 `sortKey` 타입 같은 데 쓴다.

거꾸로 "이 타입이 never인가"를 물을 때는 함정이 있다.

```ts
type IsNeverBad<T> = T extends never ? true : false;
type IsNever<T> = [T] extends [never] ? true : false;
type E3 = IsNeverBad<never>;
type E4 = IsNever<never>;

type IsAny<T> = 0 extends 1 & T ? true : false;
type E5 = IsAny<any>;
type E6 = IsAny<unknown>;
```

```text
type E3 = never
type E4 = true
type E5 = true
type E6 = false
```

`never`는 멤버가 0개인 유니온이라 분배하면 계산할 멤버가 없어 결과도 `never`다. `[T]`로 감싸 분배를 꺼야 `true`가 나온다. 앞의 `Path`에서 깊이 카운터가 `never`인지 물을 때 감싼 이유가 이것이다. `IsAny`는 `any`의 특이한 성질을 이용한다. `1 & T`는 보통 `1`이거나 `never`인데, `T`가 `any`면 `any`가 되어 `0`도 들어간다. 타입이 `any`로 무너졌는지 검사하는 테스트에 쓴다.

## 타입이 맞는지 타입으로 테스트한다

헬퍼 타입이 늘면 바꿀 때마다 결과가 그대로인지 확인할 방법이 필요하다. 런타임 테스트처럼 타입 테스트를 둘 수 있다. 두 타입이 정확히 같은지 보는 `Equal`과, 참이 아니면 컴파일 에러를 내는 `Expect`를 쓴다. 앞의 `Filter`, `KeysOfType`과 같은 파일에 이어서 적었다.

```ts
type Equal<A, B> =
  (<G>() => G extends A ? 1 : 2) extends (<G>() => G extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;

type test1 = Expect<Equal<E1, [1, 2, 3]>>;
type test2 = Expect<Equal<E2, "id" | "price">>;
type test3 = Expect<Equal<E2, "id">>;
```

```text
nev.ts(12,21): error TS2344: Type 'false' does not satisfy the constraint 'true'.
```

틀린 기대를 적은 `test3`만 에러가 났다. 이 파일을 `tsc --noEmit`에 포함하면 CI에서 타입 회귀를 잡는다. `Equal`이 이상하게 생긴 건 "서로 할당 가능한가"를 묻는 단순한 방식이 `any` 앞에서 무너지기 때문이다. `[A] extends [B]`를 양쪽으로 묻는 방식은 `any`와 `string`을 같다고 판정했다. 위의 `Equal`은 두 타입을 검사기 내부의 "같은 타입인가" 비교에 맡겨서 `any`와 `unknown`도 다르다고 본다. 대신 너무 엄격해서 `{ a: 1 } & { b: 2 }`와 `{ a: 1; b: 2 }`도 다르다고 한다(`false`가 나왔다). 교차 타입을 기대값과 비교할 때는 [유틸리티 타입 글](/posts/ts-utility-mapped-types)의 `Prettify`로 한 번 펼친 뒤 비교한다. Vitest의 `expectTypeOf`나 `tsd` 같은 도구가 이런 비교를 함수 모양으로 감싸 준다.

## satisfies로 계산한 타입을 검사에 건다

`satisfies`가 타입 주석과 어떻게 다른지는 [유틸리티 타입 글](/posts/ts-utility-mapped-types)에 있다. 이 글의 타입들과 엮으면 "모양은 검사하고, 리터럴은 남겨 계산에 쓰는" 조합이 된다.

```ts
type Params<P extends string> = P extends `${string}:${infer N}/${infer R}`
  ? N | Params<`/${R}`>
  : P extends `${string}:${infer N}` ? N : never;

const routes = {
  home: "/",
  user: "/users/:userId",
  post: "/users/:userId/posts/:postId",
  bad: "users",
} as const satisfies Record<string, `/${string}`>;

type S1 = Params<(typeof routes)["post"]>;
```

```text
sat.ts(9,3): error TS2322: Type '"users"' is not assignable to type '`/${string}`'.
type S1 = "userId" | "postId"
```

`/`로 시작하지 않는 경로가 검사에 걸렸고, `as const`로 남은 리터럴에서 매개변수 이름을 계산했다. 타입 주석(`: Record<string, ...>`)으로 썼다면 리터럴이 `string`으로 넓어져 `Params`가 아무것도 꺼내지 못한다.

## 런타임과 같은 규칙으로

타입은 컴파일이 끝나면 지워진다. `PathValue`가 `"profile.address.zip"`의 타입을 `string`이라고 말해 줘도, 실제로 그 값을 꺼내는 함수는 따로 있어야 하고 그 함수가 같은 규칙을 따라야 한다. 점으로 자른 키를 차례로 따라가고, 중간에 객체가 아니거나 자기 속성이 아니면 `undefined`를 돌려주는 `getByPath`를 만들어 보자. [Map, Set, WeakMap](/posts/js-map-set-weak)에서 본 것처럼 `toString` 같은 물려받은 이름에 걸리지 않게 자기 속성인지 확인한다. 빈 경로는 객체 자신을 돌려준다.

## 타입 계산을 어디까지 할까

이 글의 도구들은 강력하지만 대가가 셋이다. 첫째는 읽기다. hover에 `Path<T, Prev[D]>` 같은 미뤄진 타입이 뜨고, 에러 메시지가 수백 글자의 유니온을 늘어놓는다. 둘째는 속도다. 앞에서 깊이 하나에 검사 시간이 세 배씩 늘었다. 셋째는 무너짐이다. 순환하는 데이터에서 결과가 조용히 `any`가 되면 타입이 있는 척만 하는 코드가 된다.

그래서 쓰는 곳을 나눈다. 라이브러리나 팀 공용 유틸리티처럼 한 번 만들어 여러 곳에서 쓰는 API의 시그니처에는 조건부 타입과 `infer`가 제값을 한다. 라우터의 `params`, 폼의 필드 경로, 이벤트 버스의 인자처럼 문자열 실수를 컴파일 시간에 잡아 주는 곳이다. 이때는 타입 테스트를 함께 두고, 입력 크기를 제한하고(작은 폼 타입에만), 결과가 `any`로 무너지지 않았는지 `IsAny`로 확인한다. 반대로 화면 컴포넌트 하나에서만 쓰는 타입이라면 조건부 타입 대신 판별 유니온이나 인터페이스 표를 직접 적는다. 판별 유니온과 좁히기는 [타입 좁히기](/posts/ts-narrowing)에서 다뤘다. 같은 팀원이 hover 결과를 보고 무슨 뜻인지 바로 알 수 없다면, 그 타입은 이름 있는 인터페이스로 한 번 풀어 적을 때가 된 것이다.

## 면접에서 나올 만한 질문

### 제네릭 함수의 반환 타입을 조건부 타입으로 두면 본문에서 왜 에러가 나나요?

본문은 타입 매개변수 `T`를 모르는 상태로 한 번만 검사되는데, `T`를 모르면 조건부 타입이 갈래를 고르지 못하고 미뤄진 채 남기 때문이다. 미뤄진 타입에는 모든 가능한 `T`에 맞는 값만 들어갈 수 있어서 `number`도 `string`도 거부된다. `kind === "number"`로 값을 좁혀도 타입 매개변수 `T`는 좁혀지지 않는다. 오버로드를 쓰거나, 키에서 타입으로 가는 인터페이스 표와 구현 객체를 두고 인덱스 접근으로 꺼내면 단언 없이 풀린다.

### 분배 조건부 타입은 언제 일어나고, 어떤 결과 차이를 만드나요?

검사 자리에 맨 타입 매개변수가 오고 거기에 유니온이 들어올 때만 일어난다. `T extends unknown ? T[] : never`에 `string | number`를 넣으면 `string[] | number[]`가 되고, `[T]`로 감싸면 `(string | number)[]`가 된다. 앞은 섞인 배열을 받지 않는다. `boolean`은 `true | false`라 분배되어 두 갈래가 합쳐지고, `{ value: T }`처럼 감싼 모양은 분배되지 않는다.

### infer로 같은 이름을 두 자리에서 잡으면 무엇이 나오나요?

속성 값처럼 읽는 자리(공변 위치)에서는 후보가 유니온으로, 함수 매개변수처럼 넣는 자리(반공변 위치)에서는 교집합으로 합쳐진다. 이 성질로 유니온을 함수 매개변수 자리에 옮겼다가 다시 잡아 교집합으로 바꾸는 `UnionToIntersection`을 만든다. 오버로드된 함수에서 `ReturnType`이나 `Parameters`를 쓰면 마지막 시그니처만 본다는 것도 같은 맥락에서 알아 둔다.

### Awaited는 어떻게 구현되어 있나요? Promise extends 하나로 만들면 무엇이 틀리나요?

`T extends Promise<infer U> ? U : T`는 겹친 Promise를 한 겹만 벗기고, `then`만 있는 thenable을 열지 못한다. 런타임의 `await`는 호출 가능한 `then`이 있는 객체면 열고 결과가 또 thenable이면 다시 연다. 내장 `Awaited`는 그 동작대로, `then`의 첫 매개변수인 콜백의 첫 매개변수 타입을 `infer`로 잡아 재귀로 다시 연다. `null`과 `undefined`는 그대로 둔다.

### 재귀 타입은 어디서 문제가 되고 어떻게 막나요?

자기 자신을 가리키는 데이터(답글이 답글 배열을 갖는 구조)에 경로 타입을 걸면 계산이 끝나지 않아 TS2615 같은 순환 에러와 함께 결과가 `any`로 무너진다. 에러를 덮으면 타입이 아무 문자열이나 받아 검사가 사라진다. `Prev` 튜플로 깊이 카운터를 넘겨 일정 깊이에서 `never`로 멈추게 한다. 깊이를 제한해도 큰 타입에 걸면 느려서, `HTMLInputElement`에 깊이 2로 걸었을 때 검사 시간이 0.76초에서 4.27초가 됐고 깊이 3은 끝나지 않았다.

### never는 타입 계산에서 어떻게 쓰이나요? never인지 검사할 때 주의할 점은요?

유니온에서 빈 집합이라 사라지기 때문에 "조건에 안 맞으면 never"를 돌려주는 것만으로 거름망이 된다. 키를 값 타입으로 거르는 `KeysOfType`이나 매핑된 타입의 `as` 절이 이 성질을 쓴다. 반대로 `T extends never`로 never인지 물으면 분배할 멤버가 없어 결과가 never가 되니, `[T] extends [never]`로 감싸 묻는다.

### 타입 수준 프로그래밍을 실무에서 어디까지 쓰나요?

여러 곳에서 쓰는 API의 시그니처, 특히 문자열 실수를 컴파일 시간에 잡는 곳(라우트 매개변수, 폼 필드 경로, 이벤트 인자)에는 쓸 만하다. 그때는 `Equal`과 `Expect` 같은 타입 테스트를 함께 두고, 입력 타입의 크기를 제한하고, 결과가 `any`로 무너지지 않았는지 확인한다. 화면 한 곳에서만 쓰는 타입은 판별 유니온이나 인터페이스를 직접 적는다. hover와 에러 메시지를 팀원이 읽을 수 없거나 검사 시간이 눈에 띄게 늘면 되돌릴 신호다.
