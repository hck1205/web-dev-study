어제 저녁에 Claude Code로 쿠폰 할인 버그를 반쯤 고치다가 노트북을 덮었다. 아침에 터미널을 열고 `claude`를 쳤더니 빈 대화가 떴다. 어제 어디까지 했는지, 무엇을 시도했다 실패했는지 처음부터 다시 설명해야 하나 싶었다. 실은 `claude -c` 한 번이면 되는 일이었다.

Claude Code는 터미널 프로그램이라 처음 며칠은 옵션과 키를 모르는 데서 시간이 샌다. 이 글은 그걸 줄이려고 쓴다. 실행 옵션, 입력창에서 쓰는 키와 특수 문자, 권한 모드, 세션이 저장되는 곳과 이어 가기가 무엇을 다시 싣는지를 실제 화면과 출력으로 따라간다. 확인한 버전은 Claude Code 2.1.310(Linux)이다. 키와 명령은 버전마다 조금씩 바뀌니 다른 버전이면 `/help`로 맞춰 보자.

이 시리즈에서 이미 다룬 것은 링크로 넘긴다. 전체 그림은 [Claude Code 기본기 지도](/posts/claude-code-fundamentals-map), 설정 파일과 권한 규칙은 [프로젝트 구조](/posts/claude-code-project-structure), 압축과 되감기와 플랜 모드는 [컨텍스트 창](/posts/claude-code-context-window), 스킬과 훅은 [확장](/posts/claude-code-extensions)에 있다. 터미널 밖, 스크립트와 CI에서 돌리는 법은 [Claude Code를 스크립트와 CI에서](/posts/claude-code-headless-ci)로 이어진다.

## 켜는 방법은 네 가지다

가장 자주 쓰는 실행 형태는 넷이다.

```bash
# 1. 빈 대화로 대화형 세션을 연다
claude

# 2. 첫 프롬프트를 넣고 대화형 세션을 연다 (답을 본 뒤 계속 대화한다)
claude "쿠폰 할인 테스트가 왜 깨지는지 봐 줘"

# 3. 한 번 묻고 답만 출력한 뒤 끝낸다 (스크립트·파이프용)
claude -p "package.json의 scripts를 한 줄씩 설명해 줘"

# 4. 이 폴더의 가장 최근 대화를 이어 간다
claude -c
```

2번과 3번은 비슷해 보이지만 다르다. 2번은 대화형 화면을 열고 첫 메시지를 대신 쳐 주는 것이다. 답이 나온 뒤에도 세션이 열려 있고 권한 확인 창도 뜬다. 3번은 비대화형이라 확인 창을 띄울 수 없고, 답을 표준 출력으로 내보낸 뒤 종료한다. `cat error.log | claude -p "원인을 짐작해 줘"`처럼 파이프로 입력을 넘길 때도 3번을 쓴다. 도구를 하나도 주지 않고(`--tools ""`) 파이프로 코드만 넘겨 본 실제 출력이다.

```bash
# 파일 내용을 표준 입력으로 넘기고 답만 받는다. 도구는 쓰지 못하게 한다
cat math.js | claude -p "이 코드의 버그를 한 문장으로" --tools ""
```

```text
버그: `add` 함수가 덧셈(`+`) 대신 뺄셈(`-`)을 사용하고 있어서, `add(2, 3)`이 `5`가 아니라 `-1`을 반환합니다.
```

모델은 파일을 열지 않았다. 파이프로 들어온 내용이 프롬프트에 붙어 갔을 뿐이다. 이렇게 도구를 끄면 권한을 걱정할 일이 없어서, 로그 요약이나 diff 설명처럼 읽기만 하는 일에 편하다. 이 모드의 권한과 출력 형식은 따로 다룰 게 많아서 [다음 글](/posts/claude-code-headless-ci)로 미룬다.

세 번째 형태를 처음 쓸 때 헷갈리는 점이 하나 더 있다. `claude -p`도 대화를 세션 파일로 저장한다. 그래서 `-p`로 물은 것을 나중에 `claude -c`로 이어 대화형으로 열 수 있다. 저장이 싫으면 `--no-session-persistence`를 붙인다.

여기에 자주 붙는 옵션이 몇 개 있다. 한 줄에 다 붙여 보면 이렇다. 아래 그림의 조각을 눌러 보면 각각이 무엇을 바꾸는지 나온다.

`--add-dir`은 조금 더 설명이 필요하다. Claude Code는 시작한 폴더(작업 폴더)를 기준으로 파일 도구의 범위를 정한다. 프런트엔드 저장소에서 시작했는데 옆의 `../api`까지 봐야 하면, 이 옵션으로 폴더를 더해 준다. 세션 중에는 `/add-dir ../api`로도 된다. 더한 폴더는 접근 범위만 넓어지고 그 폴더의 `CLAUDE.md`와 설정은 기본으로 읽지 않는다. 읽게 하려면 환경 변수 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`을 켠다. 범위를 넓히는 것이니 꼭 필요한 폴더만 더한다. 홈 디렉터리 전체를 더하는 건 모든 파일을 열어 주는 것과 같다.

## 설치가 이상하면 doctor부터

키보다 먼저 알아 둘 명령이 하나 있다. 업데이트 뒤에 이상하게 동작하거나, 명령이 두 개 깔려 있는 것 같으면 `claude doctor`를 돌린다. 이 환경에서 실제로 돌린 출력이다.

"업데이트했는데 버전이 그대로"라는 증상의 흔한 원인이다. `Auto-updates`는 왜 자동 업데이트가 꺼졌는지(환경 변수)까지 보여 준다. 터미널 밖에서 도는 이 하위 명령은 설정 파일을 신뢰 확인 없이 읽기만 한다. 세션 안의 `/doctor`는 같은 점검에 더해 고치는 것까지 도와준다.

세션 안에서 지금 상태를 보는 건 `/status`다. 버전, 모델, 로그인한 계정, 작업 폴더, 연결 상태 같은 것이 나온다. "왜 이 모델로 돌지?", "어느 계정으로 과금되지?"가 궁금할 때 먼저 친다.

## 입력창에 쓰는 특수 문자 세 개

입력창 맨 앞이나 중간에 쓰는 문자 세 개가 일을 많이 줄여 준다.

`@`는 파일을 집어 넣는다. `@src/coupon.ts 여기 discount 함수 봐 줘`라고 쓰면 그 파일 내용이 메시지에 붙어서 간다. 모델이 파일을 찾느라 검색 도구를 부르는 바퀴가 줄어든다. `@`를 치고 몇 글자 쓰면 경로 자동 완성이 뜬다. 폴더를 가리키면 그 폴더의 목록이 들어간다. 연결된 MCP 서버의 리소스도 `@서버이름:...` 꼴로 가리킬 수 있다. 다만 큰 파일을 습관처럼 `@`로 붙이면 그만큼 컨텍스트를 먹는다. 필요한 파일만 붙인다.

`!`로 시작하면 셸 모드다. `! git status`라고 치면 모델을 거치지 않고 그 명령을 바로 돌린다. 출력은 대화에 남아서 다음 질문에서 모델이 볼 수 있다. "테스트 돌려서 결과 봐 줘"라고 시키면 모델이 도구를 고르고 실행하는 한 바퀴가 드는데, 내가 이미 칠 명령을 안다면 `! pnpm test coupon`이 빠르고 싸다. 모델이 보지 않았으면 하는 출력(비밀 값이 찍히는 명령)은 여기서 돌리면 안 된다. 대화에 남기 때문이다.

`/`는 명령이다. 내장 명령과 내가 만든 스킬이 같은 자리에 뜬다. 처음 쓸 때 알아 두면 좋은 내장 명령은 이 정도다.

| 명령 | 하는 일 |
|---|---|
| `/help` | 쓸 수 있는 명령과 키 목록. 버전별 차이를 맞춰 볼 때 |
| `/config` | 설정 화면(테마, 편집 모드, 알림 등)을 연다 |
| `/status` | 버전, 모델, 계정, 작업 폴더, 연결 상태 |
| `/doctor` | 설치와 설정 점검, 고칠 방법 안내 |
| `/clear` | 지금 대화를 비우고 새로 시작한다 |
| `/resume` | 지난 세션을 골라 이어 간다 |
| `/export` | 대화를 파일로 저장하거나 클립보드로 복사한다 |
| `/exit` | 세션을 끝낸다 |

`/clear`와 `/exit`의 차이는 알아 둘 만하다. `/clear`는 같은 터미널에서 새 대화를 시작한다. 이전 대화는 지워지는 게 아니라 디스크에 그대로 남아서 나중에 `/resume`으로 다시 열 수 있다. 주제가 바뀌었는데 같은 대화를 이어 쓰면 앞의 내용이 계속 컨텍스트를 차지하니, 일이 바뀌면 `/clear`가 맞다. `/export`는 대화를 사람이 읽는 텍스트로 뽑는다. PR 설명에 붙이거나, 동료에게 "이렇게 시켰더니 이렇게 하더라"를 보여 줄 때 쓴다.

## 손에 익혀 둘 키

키는 많지만 매일 쓰는 건 몇 개다.

- `Esc`: 모델이 답을 쓰거나 도구를 돌리는 중이면 멈춘다. 대화는 그대로라서 멈춘 자리에서 "그 방법 말고 이렇게 해"라고 방향을 바꾼다. 엉뚱한 파일을 고치기 시작했을 때 가장 먼저 누른다.
- `Esc` 두 번: 입력창이 비어 있으면 되감기 메뉴가 뜬다. 지난 프롬프트를 골라 코드와 대화를 그 시점으로 돌린다. 자세한 동작과 되돌릴 수 없는 것은 [컨텍스트 창](/posts/claude-code-context-window#esc-두-번으로-되돌아가기)에 정리했다.
- `Ctrl+C`: 입력 중인 글을 지우거나 진행 중인 작업을 취소한다. 한 번 더 누르면 세션을 끝낸다. `Ctrl+D`도 빈 입력창에서 종료다.
- `Ctrl+R`: 지금까지 보낸 프롬프트 기록을 거꾸로 검색한다. 셸의 `Ctrl+R`과 같은 감각이다. 어제 길게 쓴 지시문을 다시 쓸 때 편하다. `Up` 키로 직전 입력을 하나씩 불러오는 것도 된다.
- `Shift+Tab`: 권한 모드를 돌린다. 아래 절에서 따로 본다.

여러 줄 입력이 의외로 걸린다. 그냥 `Enter`는 보내기라서, 줄을 바꾸려면 다른 키가 필요하다. 어느 터미널에서나 되는 건 줄 끝에 `\`를 쓰고 `Enter`를 누르는 방법이다. `Ctrl+J`도 줄바꿈을 넣는다. `Shift+Enter`는 iTerm2, WezTerm, Ghostty, Kitty 같은 터미널에서는 바로 되고, VS Code 터미널 등 일부는 `/terminal-setup`으로 키 설정을 한 번 해 줘야 한다. macOS에서는 `Option+Enter`가 터미널 설정에 따라 된다. 긴 로그나 코드를 붙여 넣는 건 줄바꿈 키 없이 그냥 붙여 넣으면 된다.

키가 손에 안 맞으면 바꿀 수 있다. `~/.claude/keybindings.json`에 동작과 키를 짝지어 적는다. 형식은 `/help`와 공식 문서의 키 설정 항목을 참고한다.

## 권한 모드: 얼마나 맡길지 정하는 스위치

Claude Code가 파일을 고치거나 명령을 돌리기 전에 물어볼지, 그냥 할지를 정하는 것이 권한 모드다. 2.1.310의 도움말에 나오는 모드는 여섯 개다. 잘못된 값을 넣어 보면 목록이 그대로 나온다.

```bash
# 일부러 없는 모드를 넣어 허용 목록을 확인한다
claude -p "hi" --permission-mode foo
```

```text
error: option '--permission-mode <mode>' argument 'foo' is invalid. Allowed choices are acceptEdits, auto, bypassPermissions, manual, dontAsk, plan.
```

`manual`이 기본 모드다. 문서와 이전 버전에서는 `default`라고 불렀고, 이 버전에서도 `default`를 넣으면 받아들인다. 모드마다 하는 일은 이렇다.

- `manual`(기본): 파일 읽기 같은 읽기 도구는 그냥 쓰고, 파일 수정과 셸 명령은 처음 쓸 때 물어본다. "이번만 허용", "이 명령은 계속 허용" 같은 선택지가 뜬다.
- `acceptEdits`: 파일 수정은 묻지 않고 받아들인다. 셸 명령은 여전히 묻는다. 방향이 맞다고 확인된 뒤 반복 수정을 빠르게 넘길 때 쓴다.
- `plan`: 조사하고 계획만 낸다. 소스를 고치지 않는다. 승인하면 실행 모드로 넘어간다. 탐색용 명령은 돌 수 있어서 샌드박스는 아니다.
- `auto`: 모델과 별개인 분류기가 도구 호출마다 위험도를 판단해 허용하거나 막는다. 계정과 버전에 따라 쓸 수 있는지가 다르다.
- `dontAsk`: 미리 허용 규칙에 있는 것만 하고 나머지는 묻지 않고 거부한다. 비대화형 실행에서 의미가 있다.
- `bypassPermissions`: 확인을 모두 건너뛴다. 네트워크가 막힌 컨테이너 같은 버려도 되는 환경에서만 쓴다. `--dangerously-skip-permissions`가 같은 뜻이다.

세션 중에는 `Shift+Tab`을 누를 때마다 모드가 돌아간다. 기본 순서는 아래 그림처럼 `manual` → `acceptEdits` → `plan`이고, 계정에서 `auto`를 쓸 수 있으면 그 사이에 끼고, `bypassPermissions`는 `--allow-dangerously-skip-permissions`로 켜 둔 세션에서만 순환에 들어간다. 지금 모드는 입력창 아래에 표시된다. 다음을 눌러 보자.

`manual`에서 확인 창이 뜨면 대개 세 갈래 중 하나를 고른다. 이번 한 번만 허용, 이 명령(또는 이 종류의 명령)은 앞으로 묻지 않기, 거절하고 다르게 하라고 말하기. 두 번째를 고르면 그 규칙이 이 프로젝트의 로컬 설정(`.claude/settings.local.json`)에 저장된다. 저장소에 커밋되지 않는 파일이라 내 컴퓨터에서만 먹는다. 세 번째는 그냥 "아니오"보다 쓸모가 많다. "테스트 파일은 고치지 말고 구현 쪽을 고쳐"처럼 이유를 붙여 거절하면 모델이 다음 행동을 바꾼다.

이렇게 쌓인 규칙은 세션 안에서 `/permissions`로 보고 지운다. 무심코 "앞으로 묻지 않기"를 눌러 `Bash(rm:*)` 같은 넓은 규칙이 생겼다면 여기서 확인한다. 세션을 시작할 때 `--allowedTools "Bash(pnpm test:*)" Edit`처럼 이번 세션에만 허용할 도구를 넘길 수도 있다. 규칙 문법은 대화형과 비대화형이 같다.

```bash
# 이번 세션에서는 테스트 명령과 파일 수정만 묻지 않는다
claude --allowedTools "Bash(pnpm test:*)" "Edit"
```

모드는 큰 스위치이고, 세밀한 규칙은 `settings.json`의 `permissions`(allow, ask, deny)에 둔다. 예를 들어 `acceptEdits`여도 `.env` 수정은 deny 규칙으로 막을 수 있다. 저장소에 커밋한 설정으로 `bypassPermissions`를 기본값으로 만들 수 없게 막혀 있다는 점까지 [프로젝트 구조](/posts/claude-code-project-structure#허용-확인-거부)에 정리해 뒀다.

실무에서 내가 쓰는 흐름은 단순하다. 처음 보는 코드나 여러 파일에 걸친 변경은 `plan`으로 계획을 받는다. 계획이 맞으면 승인하고 `manual`로 진행하며 처음 몇 번의 수정을 직접 본다. 방향이 확인되면 `acceptEdits`로 넘겨 반복 수정을 빠르게 받는다. 셸 명령은 끝까지 묻게 둔다. 지우고, 올리고, 배포하는 건 대부분 셸에서 일어나기 때문이다.

이 글을 쓰며 이 폴더에서 연 세션 네 개다. 뒤에서 볼 이름 붙인 세션(`8a22869c…`)과 그걸 포크한 세션(`63b63a16…`)도 여기 있다. 권한이 `-rw-------`, 내 계정만 읽을 수 있다. 그래도 안에 든 건 평문이다. 한 줄이 기록 하나인 JSON Lines이고, 사용자 메시지와 모델 응답뿐 아니라 도구 호출 인자와 결과, 즉 모델이 읽은 파일 내용과 명령 출력이 들어 있다. 세션 하나에 든 기록 종류를 세어 보면 이렇다.

```bash
# 세션 파일 안의 기록 종류를 센다
grep -o '"type":"[a-z-]*"' 8a22869c-cfce-444c-9db2-9370d1285ccc.jsonl | sort | uniq -c | sort -rn | head -8
```

```text
      9 "type":"attachment"
      4 "type":"queue-operation"
      4 "type":"message"
      2 "type":"user"
      2 "type":"text"
      2 "type":"last-prompt"
      2 "type":"cost-state"
      2 "type":"assistant"
```

`user`와 `assistant`가 대화 본문이고, `attachment`는 메시지에 붙은 맥락(파일, 환경 정보 같은 것)이다. 각 기록에는 세션 ID, 작업 폴더, Claude Code 버전, 그때의 git 브랜치도 함께 적힌다. 내부 형식이라 버전마다 기록 종류는 바뀐다. 직접 파싱해서 무언가를 만들 생각이면 이 파일 대신 비대화형 모드의 JSON 출력이나 Agent SDK를 쓰는 게 안전하다.

평문이라는 점은 운영 습관으로 이어진다. 세션 중에 `.env`를 읽게 했거나 `! cat` 으로 토큰을 찍었다면 그 값이 이 파일에 남는다. 오래된 세션은 기본으로 약 30일 뒤 정리 대상이 되고 `cleanupPeriodDays` 설정으로 기간을 바꾼다. 프로젝트 하나의 기록을 지금 다 지우려면 `claude purge`가 있다. 이미 노출된 키는 파일을 지워도 노출된 것이니 키를 바꾼다.

## 어제 대화를 다시 여는 법

저장 위치가 폴더별이라는 점이 `-c`의 동작을 정한다. `-c`는 "지금 폴더의 가장 최근 세션"을 연다. 확인해 보려고 `cc-lab` 폴더에서 `math.js`에 대해 대화한 뒤, 다른 폴더(`cc-lab2`)와 원래 폴더에서 각각 `-c`로 같은 질문을 던졌다.

```bash
cd ../cc-lab2
claude -c -p "내가 직전에 물어본 파일 이름이 뭐였지? 모르면 모른다고 한 문장으로"

cd ../cc-lab
claude -c -p "내가 직전에 물어본 파일 이름이 뭐였지? 한 문장으로"
```

```text
모르겠습니다. 이 대화에는 이전에 물어보신 파일 이름이 남아 있지 않아서 확인할 수 없습니다.
math.js
```

다른 폴더에서는 이어 갈 세션이 없으니 새 대화가 됐고, 원래 폴더에서는 어제 대화를 찾았다. 처음 장면의 "새 세션이 열린다"는 대부분 이 둘 중 하나다. `-c`를 안 붙였거나, 다른 폴더(하위 폴더 포함)에서 켰다. 저장소 루트에서 시작하는 습관을 들이면 덜 헤맨다.

최근 것이 아니라 특정 세션을 열려면 `-r`이다. 값 없이 `claude -r`만 치면 이 폴더의 세션 목록이 뜨고 골라서 연다. 세션 안에서는 `/resume`이 같은 화면이다. 세션에 이름을 붙여 두면 고르기가 쉽다. 시작할 때 `-n`으로 이름을 주고, 나중에 그 이름으로 연다.

```bash
# 이름을 붙여 세션을 시작한다
claude -n coupon-fix -p "이 대화의 암호는 '귤'이다. 알았다고만 해"
# 이름으로 이어 간다
claude -r coupon-fix -p "암호가 뭐였지? 한 단어로"
```

```text
알았어요.
귤
```

이어 가면 같은 세션 ID의 파일 끝에 새 기록이 붙는다. 같은 출발점에서 다른 방향을 시험해 보고 싶으면 `--fork-session`을 함께 준다. 지난 대화를 그대로 복사한 새 세션 ID가 생기고 원래 세션은 건드리지 않는다. 같은 이름으로 포크해 본 결과, 새 ID(`63b63a16-…`)가 생기고 답은 그대로 "귤"이었다.

## 이어 가기가 다시 싣는 것과 다시 읽는 것

여기서 두 가지가 따라 나온다.

하나는 어제 읽은 파일 내용이 기록 안에 어제 버전으로 남아 있다는 점이다. 밤사이 동료가 `coupon.ts`를 고쳐 푸시했고 내가 `git pull`을 받았다면, 모델은 기록 속의 옛 내용을 기억한 채로 시작한다. 그래서 이어 간 직후 첫 지시는 "`git log -3`과 `coupon.ts`를 다시 읽고 시작해"처럼 지금 상태를 다시 보게 하는 게 안전하다.

다른 하나는 설정이 바뀌었을 때다. 2.1.x 도움말의 `--system-prompt-snapshot` 설명을 보면, 기본값에서는 시스템 프롬프트를 대화의 첫 요청 때 기록하고 이후 요청과 이어 가기에서 그 기록을 그대로 다시 보낸다(압축되기 전까지). 프롬프트 캐시를 살리려는 동작이다. 그래서 이어 간 세션에서 시스템 프롬프트에 들어가는 설정을 바꿔도 바로 반영되지 않을 수 있다. 규칙을 크게 바꿨다면 이어 가지 말고 새 세션을 여는 게 확실하다. 이 동작은 버전마다 달라질 수 있으니 쓰는 버전의 `claude --help`로 확인하자.

세션이 아주 길었다면 이어 가는 것 자체가 손해일 수도 있다. 기록 전체를 다시 싣고 시작하니 첫 요청부터 컨텍스트가 무겁다. 어제의 결론만 필요하면 어제 세션 끝에서 "지금까지 한 일과 남은 일을 정리해 줘"로 요약을 받아 두고, 오늘은 새 세션에 그 요약만 붙여 시작하는 편이 가볍다.

## CLI, 에디터 확장, 데스크톱 앱

같은 엔진을 여러 껍데기로 쓴다. 고르는 기준만 짧게 적는다.

- 터미널 CLI: 모든 기능이 가장 먼저 들어오고, 원격 서버에 SSH로 들어가서도 쓴다. 이 글의 옵션과 키가 다 여기 기준이다.
- 에디터 확장(VS Code 계열, JetBrains): 변경 사항을 에디터의 diff 화면으로 보고, 열어 둔 파일과 선택 영역이 맥락으로 들어간다. 코드를 보며 조금씩 고칠 때 편하다. 터미널의 `claude`를 에디터와 연결하는 `/ide` 명령도 있다.
- 데스크톱 앱과 웹: 여러 세션을 나란히 관리하고, 클라우드에서 도는 세션을 열거나 휴대폰에서 이어 본다. 긴 작업을 맡기고 다른 일을 할 때 맞다.

어느 껍데기든 같은 `settings.json`과 권한 규칙을 따르고, 같은 컴퓨터의 CLI와 에디터 확장은 같은 `~/.claude` 아래를 쓴다. 다만 껍데기마다 지원하는 기능과 단축키가 조금씩 다르고 자주 바뀌니, 키 이야기는 CLI 기준으로 익혀 두고 나머지는 각 화면의 도움말로 맞춘다.

## 하루 작업 하나를 이 순서로

옵션과 키를 따로 외우면 금방 잊는다. 처음의 쿠폰 버그를 하루 동안 고치는 흐름에 끼워 보면 이렇게 된다.

```bash
# 아침: 저장소 루트에서, 이름을 붙이고, 계획 모드로 시작한다
cd ~/work/shop
claude -n coupon-fix --permission-mode plan "쿠폰 할인 테스트가 깨진다. 원인과 고칠 계획만 내 줘"
```

입력창에서는 이렇게 쓴다.

```text
@src/coupon.ts @src/coupon.test.ts 이 두 파일만 먼저 보고 계획을 세워 줘
! pnpm test coupon
```

`@`로 볼 파일을 집어 주고, 실패 출력은 `!`로 직접 돌려 대화에 남긴다. 계획이 맞으면 승인하고 `manual`로 진행하며 처음 수정 몇 개를 직접 본다. 방향이 확인되면 `Shift+Tab`으로 `acceptEdits`에 맞춰 반복 수정을 넘긴다. 중간에 엉뚱한 파일을 열기 시작하면 `Esc`로 멈추고 방향을 고쳐 말한다. 아예 잘못 갔으면 `Esc` 두 번으로 그 프롬프트 직전으로 되돌린다.

점심 뒤 다른 버그를 보게 됐다면 `/clear`로 새 대화를 연다. 쿠폰 대화는 디스크에 남아 있다. 저녁에 끝내지 못했으면 "지금까지 한 일과 남은 일을 정리해 줘"로 요약을 받아 둔다. 다음 날 아침에는 같은 폴더에서 이어 간다.

```bash
# 다음 날: 이름으로 이어 가고, 첫 지시로 지금 상태를 다시 보게 한다
claude -r coupon-fix "git log -3과 src/coupon.ts를 다시 읽고, 어제 남은 일부터 이어 가자"
```

## 헤매는 순간과 볼 곳

처음 몇 주 동안 실제로 자주 막히는 장면을 증상별로 모았다.

- `claude -c`를 했는데 새 대화가 열린다: 다른 폴더(하위 폴더 포함)에서 켰다. `pwd`를 보고 저장소 루트로 가거나 `claude -r`로 목록을 본다.
- 이어 간 세션이 어제 코드 기준으로 말한다: 기록 속 파일 내용이 어제 버전이다. 파일을 다시 읽으라고 첫 지시를 준다.
- `Enter`를 눌렀더니 반쯤 쓴 지시가 가 버렸다: 줄바꿈은 `\` + `Enter`나 `Ctrl+J`, 터미널에 따라 `Shift+Enter`다. 이미 갔으면 `Esc`로 멈추고 이어서 쓴다.
- 매번 같은 명령을 허락해 달라고 묻는다: 확인 창에서 "계속 허용"을 고르거나 `settings.json`의 `permissions.allow`에 규칙을 넣는다. 모드를 `bypassPermissions`로 바꾸는 건 해결이 아니다.
- 옆 저장소의 파일을 못 읽는다고 한다: 작업 폴더 밖이다. `--add-dir`이나 `/add-dir`로 더한다.
- 업데이트 후 동작이 예전 그대로다: `claude doctor`로 실행 경로와 버전을 본다. 설치본이 두 개인 경우가 많다.
- 답 품질이 갑자기 떨어졌다: 대화가 길어 컨텍스트가 찼을 수 있다. `/status`로 상태를 보고, 일이 바뀌었으면 `/clear`, 같은 일이면 요약을 받아 새 세션으로 옮긴다.

## 면접에서 나올 만한 질문

### claude "질문"과 claude -p "질문"은 무엇이 다른가요?

앞쪽은 대화형 세션을 열고 그 문장을 첫 메시지로 넣는다. 답이 나온 뒤에도 세션이 열려 있고 권한 확인 창이 뜬다. `-p`는 비대화형이라 답을 표준 출력으로 내고 끝나며, 확인 창을 띄울 수 없으니 허용 도구와 권한 모드를 미리 정해 줘야 한다. 스크립트, 파이프, CI에서는 `-p`를 쓴다.

### 어제 하던 대화를 이어 가려면 어떻게 하나요?

같은 폴더에서 `claude -c`로 가장 최근 세션을 열거나, `claude -r`로 목록에서 고르거나, 이름이나 ID를 넘겨 연다. 세션은 작업 폴더별로 `~/.claude/projects/` 아래에 저장되므로 다른 폴더에서 `-c`를 하면 새 대화가 된다. 같은 출발점에서 다른 시도를 하려면 `--fork-session`으로 새 ID의 복사본을 만든다.

### 세션을 이어 가면 모델이 이전 내용을 기억하는 건가요?

모델이 기억하는 게 아니라 Claude Code가 저장한 대화 기록을 다음 요청에 다시 실어 보내는 것이다. 그래서 긴 세션일수록 첫 요청이 크고, 기록 속 파일 내용은 그때 버전이라 그 뒤의 변경을 모른다. 이어 간 직후에는 지금 파일과 git 상태를 다시 읽게 하거나, 요약만 들고 새 세션을 여는 게 낫다.

### 권한 모드는 어떤 게 있고 어떻게 고르나요?

기본인 manual은 수정과 셸 명령을 처음 쓸 때 묻고, acceptEdits는 수정을 묻지 않고, plan은 계획만 내고 소스를 고치지 않는다. auto는 분류기가 호출마다 판단하고, dontAsk는 허용 규칙에 없는 건 거부하고, bypassPermissions는 확인을 모두 건너뛴다. 처음 보는 코드는 plan으로 계획을 받고, 방향이 맞으면 manual로 시작해 확인 후 acceptEdits로 넘기며, bypassPermissions는 버려도 되는 격리 환경에서만 쓴다.

### 세션 파일에는 무엇이 남고 어떤 점을 조심해야 하나요?

사용자 메시지와 응답뿐 아니라 도구 호출의 인자와 결과, 즉 읽은 파일 내용과 명령 출력이 평문 JSON Lines로 남는다. 파일 권한은 내 계정 전용이지만 비밀 값을 읽게 했다면 디스크에 남는다. 보관 기간은 `cleanupPeriodDays`로 줄이고, 필요하면 `claude purge`로 지우며, 이미 노출된 키는 교체한다.

### --add-dir은 무엇이고 언제 쓰나요?

작업 폴더 밖의 폴더를 도구 접근 범위에 더한다. 프런트엔드와 API 저장소를 함께 봐야 할 때 쓴다. 더한 폴더의 CLAUDE.md와 설정은 기본으로 읽지 않아서, 그 저장소의 규칙이 적용되지 않는다는 점을 알아 둬야 한다. 범위를 넓히는 것이니 홈 디렉터리 같은 넓은 경로는 더하지 않는다.

### 업데이트했는데 버전이 그대로이거나 동작이 이상하면 어디부터 보나요?

`claude doctor`로 실제로 실행 중인 경로와 버전, 설치 방식, 자동 업데이트 상태를 본다. 네이티브 설치와 npm 전역 설치가 함께 남아 있으면 `PATH` 순서에 따라 다른 버전이 뜨는 일이 흔하다. 세션 안에서는 `/status`로 모델과 계정을, `/doctor`로 설정 문제를 확인한다.
