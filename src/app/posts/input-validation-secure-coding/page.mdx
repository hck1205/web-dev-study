결제 로그를 보다가 이상한 주문을 찾았다. 결제 금액이 마이너스였다. 추적해 보니 주문 API의 `price` 필드에 음수를 넣은 요청이었다. 화면에서는 가격을 못 바꾸게 막아 뒀는데, 누군가 브라우저를 건너뛰고 서버에 `{"productId": "...", "quantity": 2, "price": -5000}`를 직접 보냈다. 서버는 그 `price`를 그대로 믿고 합계에서 깎았다.

문제는 "가격을 왜 클라이언트가 보내게 뒀나"이기도 하지만, 더 근본은 **서버가 들어온 값을 검사 없이 믿었다**는 것이다. 입력 검증은 이 "바깥에서 온 값을 믿지 않는다"를 코드로 옮기는 일이다. 이 글은 음수 가격 같은 업무 규칙 위반부터 대량 할당·정수 오버플로·정규식 폭주(ReDoS)·유니코드 혼동·역직렬화 같은 입력발 취약점까지, 값이 들어오는 경계에서 무엇을 어떻게 거르는지 본다. 검증을 통과한 값도 **나가는 자리**에서 한 번 더 손질해야 하는데(인코딩), 그 자리별 이스케이프는 [XSS](/posts/xss)와 [SQL 주입](/posts/sql-injection)에서 깊게 다루므로 여기선 둘의 역할 분담을 분명히 하는 데 집중한다. 전체 보안 파이프라인은 [보안 테스트를 파이프라인에](/posts/security-testing-sast-dast)와 이어진다. 런타임·예제는 Node.js 22, TypeScript 5.x, zod 4 기준이다.

## 경계에서 한 번, 출력에서 한 번

입력을 다루는 작업은 이름이 섞여 쓰여 헷갈린다. 셋을 구분하자.

- **검증(validation)**: 값이 **받아들일 만한가**를 판정한다. 통과 아니면 거부. 모양(이메일 형식), 범위(1~100), 업무 규칙(재고보다 많이 못 삼). 값을 **바꾸지 않는다**.
- **정제(sanitization)**: 위험한 부분을 **떼어 내거나 바꿔** 안전하게 만든다. HTML에서 `<script>`를 제거하는 식. 값을 바꾼다.
- **인코딩/이스케이프(encoding)**: 값을 **특정 자리에 넣을 때** 그 자리에서 특별한 뜻을 갖는 기호를 평범한 글자로 바꾼다. HTML에 넣을 때 `<`를 `&lt;`로.

이 셋이 **어디에** 놓이는지가 핵심이다. 검증은 값이 **들어오는 경계**에, 인코딩은 값이 **나가는 자리**에. 둘은 다른 문제를 푼다.

왜 둘을 나눠 두나. 같은 값이라도 나가는 자리마다 위험한 기호가 다르기 때문이다. HTML에서는 `<`가, SQL에서는 `'`가, 셸에서는 `;`가 문제다. "입력 때 한 번 다 걸러 두면 되지 않나"는 함정이다. 입력 때 HTML 기준으로 정제해 버리면, 그 값을 CSV로 내보낼 때는 엉뚱하게 손질된 값이 나간다. 그래서 **원본은 검증만 해서 그대로 저장하고, 손질은 쓰는 자리에서** 한다. 이것이 "경계에서 검증, 출력에서 인코딩"이다.

## 허용 목록이 먼저다

검증에는 두 방향이 있다. **차단 목록(blacklist)**: 나쁜 걸 나열해 막는다. **허용 목록(whitelist/allowlist)**: 좋은 것만 나열해 통과시킨다. 보안에서는 거의 항상 **허용 목록이 이긴다**.

이유는 [경로 순회](/posts/path-traversal-file-upload)에서 본 것과 같다. 나쁜 것을 다 나열하는 건 지는 싸움이다. `<script>`를 막으면 `<img onerror>`가, 그걸 막으면 또 다른 게 나온다. 반면 "소문자·숫자·하이픈만 허용"처럼 좋은 모양을 정의하면, 예상 못 한 입력은 전부 자동으로 걸린다. 수량 필드라면 "정수 1~100만"이 허용 목록이고, "음수 금지, 소수 금지, …"는 차단 목록이다.

수량 검증을 허용 목록으로 짜 보자. 정수이고 1~100 범위인 것만 통과시키고, 공백은 다듬되 그 외 글자가 섞이면 거부한다.

## 스키마로 경계를 지킨다

필드 하나하나 손으로 검사하면 빠뜨린다. 요청 본문 전체의 **모양을 선언**해 두고 한 번에 검증하는 게 스키마 검증이다. TypeScript에서는 zod가, 언어 중립으로는 JSON Schema가 많이 쓰인다. zod로 주문 스키마를 만들어, 문제의 음수 가격 요청을 받아 봤다.

```text
false (root): unrecognized_keys  Unrecognized key: "price"
```

`price` 필드가 **거부**됐다. 스키마를 `strictObject`로 선언해 "정의한 필드 외에는 받지 않는다"로 뒀기 때문이다. 애초에 가격은 서버가 DB에서 읽어야 할 값이라 요청 본문에 있을 이유가 없고, 스키마가 그걸 막았다. 모양이 틀린 값도 어디가 왜 틀렸는지 알려 준다.

```text
productId: invalid_format  Invalid UUID
quantity: invalid_type     Invalid input: expected int, received number
```

그리고 정의하지 않은 필드는 조용히 떨궈 준다(일반 `object`). 이게 다음에 볼 대량 할당을 기본적으로 막는다.

```text
strip: {"name":"kim"}     ({ name, role: "admin" }에서 role이 떨어짐)
```

스키마 검증의 자리는 **신뢰 경계 바로 안쪽**이다. 요청이 들어와 핸들러가 값을 만지기 전에 통과시킨다. 통과한 뒤로는 그 값이 "모양이 보장된 타입"이라 안심하고 쓴다. TypeScript라면 스키마에서 타입을 뽑아내 컴파일 타임 타입과 런타임 검증을 하나로 묶는다.

## 입력이 만드는 고전 취약점들

경계를 안 지키면 생기는 입력발 취약점이 몇 가지 있다. 각각 작게 재현했다.

### 대량 할당(mass assignment)

클라이언트가 보낸 객체를 통째로 내부 객체에 합치면, 바꾸면 안 되는 필드까지 바뀐다. `Object.assign(user, 요청본문)`을 하면 요청에 `role: "admin"`을 끼워 넣어 권한을 올린다.

```text
mass assign: { id: 7, name: 'lee', role: 'admin' }
```

막는 법은 허용 목록이다. 받을 필드를 명시적으로 골라 할당하거나(스키마의 strip/strict), 바꿀 수 있는 필드만 따로 추린다. 요청 객체를 통째로 믿지 않는다.

### 프로토타입 오염(prototype pollution)

자바스크립트 특유의 문제다. 객체를 재귀적으로 병합하는 코드에 `{"__proto__": {"isAdmin": true}}`를 먹이면, 모든 객체가 공유하는 프로토타입이 오염돼 **엉뚱한 빈 객체까지** `isAdmin`을 갖게 된다.

```text
pollution: true   (오염 뒤 ({}).isAdmin 이 true)
```

`__proto__`·`constructor`·`prototype` 키를 걸러 내거나, `Object.create(null)`로 프로토타입 없는 객체를 쓰거나, `Map`을 쓴다. 병합 라이브러리의 안전한 버전을 쓰는 것도 방법이다.

### 정수 오버플로와 부동소수점

돈 계산을 부동소수점으로 하면 틀어진다. `0.1 * 3`은 `0.3`이 아니다.

```text
int32 wrap: -2147483648   (2147483647 + 1 | 0)
price*qty: 0.30000000000000004
```

그리고 자바스크립트의 안전 정수 한계(2의 53승)를 넘는 수는 정밀도를 잃는다. 돈은 **정수 최소 단위(원·센트)로** 다루거나 `BigInt`/고정소수점 라이브러리를 쓰고, 검증 단계에서 안전 정수 범위를 확인한다(위 playground의 `Number.isSafeInteger`).

### 정규식 폭주(ReDoS)

검증에 쓴 정규식이 특정 입력에서 **지수적으로** 느려진다. `(a+)+$` 같은 "중첩 수량자"가 대표다. `a`가 길어질수록 백트래킹이 폭발한다. 입력 길이를 늘리며 재 봤다.

```text
20자 → 56ms
24자 → 139ms
26자 → 534ms
28자 → 2751ms
```

28자에 2.7초다. 조금 더 길면 몇 분이 되고, 그동안 그 요청 스레드가 묶여 서비스 거부가 된다. 공격자가 입력 하나로 서버를 멈추는 것이다. 막는 법은 (1) 중첩 수량자를 피하는 정규식 작성, (2) 선형 시간 엔진(RE2)으로 돌리기, (3) 입력 길이 상한 두기다. 정규식 자체의 BRE·ERE·백트래킹 얘기는 [정규 표현식과 glob](/posts/regex-and-globbing)에 자세하다.

### 역직렬화

신뢰할 수 없는 바이트를 객체로 되살리는 역직렬화는, 포맷에 따라 그 과정에서 코드가 실행되거나 위 프로토타입 오염으로 이어진다. JSON은 코드 실행까지는 안 가지만(파싱만 함), 자바 직렬화·파이썬 pickle·일부 YAML 로더는 역직렬화만으로 임의 코드가 돈다. 원칙은 "신뢰할 수 없는 입력을 역직렬화하지 않기", 어쩔 수 없으면 "코드 실행이 없는 안전한 포맷(JSON)과 스키마 검증"이다.

## 눈에 안 보이는 글자: 유니코드

유니코드는 조용히 검증을 뚫는다. 세 가지가 특히 문제다.

**혼동 문자(homoglyph).** 라틴 `a`와 키릴 `а`는 눈으로 똑같지만 다른 글자다.

```text
"admin" === "аdmin"  →  false
"аdmin" 코드포인트: [430, 64, 6d, 69, 6e]   (첫 글자가 키릴 430)
```

사용자 이름·도메인 검증에서 이걸 모르면, 눈에는 `admin`인데 시스템은 다른 값으로 보는 사칭이 생긴다.

**정규화 형태 차이.** 같은 글자를 적는 바이트가 여럿이다. `é`는 한 글자로도, `e` + 결합 악센트 두 글자로도 쓴다.

```text
"é" === "é"  →  false
NFC로 정규화 후  →  true
```

**호환 문자.** 전각 문자나 합자가 정규화하면 평범한 글자로 펴진다.

```text
"ＥＸＡＭＰＬＥ".normalize("NFKC")  →  "EXAMPLE"
"ﬁle".normalize("NFKC")          →  "file"   (ﬁ 합자가 f+i로)
"ＡＤＭＩＮ".normalize("NFKC").toLowerCase()  →  "admin"
```

그래서 검증 전에 **유니코드 정규화**(보통 NFKC)를 먼저 한다. 안 그러면 `ＡＤＭＩＮ`이 금지어 `admin` 검사를 지나친 뒤 저장돼, 다른 곳에서 `admin`으로 보일 수 있다. 정규화 → (필요하면 혼동 문자 거르기) → 검증 순서다.

## 보안을 생각한 API 설계

마지막으로, 검증을 쉽게 만드는 API 설계 원칙이 있다. 애초에 위험한 값을 **받지 않게** 설계하는 게 검증보다 낫다.

- **최소 노출 응답.** 응답에 필요한 필드만 담는다. 사용자 객체를 통째로 직렬화하면 비밀번호 해시·내부 플래그까지 샌다. 명시적으로 고른 필드만 내보낸다(입력의 대량 할당과 대칭인 출력 쪽 문제다).
- **에러에 내부 정보를 숨긴다.** 스택 트레이스·SQL 에러·파일 경로를 응답에 그대로 내보내면 공격자에게 지도를 준다([SAST·DAST 글](/posts/security-testing-sast-dast)의 실험에서 따옴표 하나에 DB 에러가 샌 걸 봤다). 사용자에게는 뭉뚱그린 메시지, 로그에는 상세. 실패 메시지가 "토큰이 존재하나 만료됨"처럼 유효성을 흘리지 않게 한다.
- **권한은 서버에서 매번 재확인.** 클라이언트가 보낸 역할·소유권을 믿지 않는다. "이 사용자가 이 자원에 이 동작을 해도 되나"를 서버가 다시 묻는다([인증과 인가](/posts/authn-vs-authz)).
- **가격·합계처럼 결정이 필요한 값은 서버가 계산한다.** 클라이언트는 "무엇을 몇 개"만 보내고, 가격은 서버가 DB에서 읽어 곱한다. 음수 가격 버그가 애초에 생길 수 없게 된다.

### 검증 실패는 어떻게 응답하나

422(Unprocessable Entity)나 400(Bad Request)으로, **어느 필드가 왜 틀렸는지** 구조화해 돌려준다. 단, 사용자 입력을 그대로 에러 메시지에 되비추지 않는다(그 자체가 반사형 XSS 통로가 될 수 있다). 여러 필드가 틀렸으면 한 번에 모아서 준다. 첫 실패에서 멈추면 사용자가 고치고 또 걸리는 걸 반복한다. 그리고 실패도 로그에 남겨, 특정 IP가 검증을 반복해 두드리면 탐지한다(무차별 대입·스캔 신호).

## 들어올 때 검증하고, 나갈 때 인코딩한다

바깥에서 온 값은 믿지 않는다. 그래서 값이 들어오는 경계에서 검증하고(허용 목록으로, 정규화를 먼저 하고, 스키마로 한 번에), 값이 나가는 자리마다 그 자리에 맞게 인코딩한다. 이 둘은 다른 문제라 하나로 합치면 안 된다. 클라이언트 검증은 편의일 뿐 방어는 서버에서 다시 한다. 대량 할당·프로토타입 오염·정수 오버플로·ReDoS·유니코드 혼동·역직렬화는 모두 경계를 안 지켜 생기는 입력발 취약점이고, 스키마의 strict·허용 목록·정규화·길이 제한·안전한 포맷으로 막는다. 더 나아가, 위험한 값을 애초에 받지 않고 서버가 결정하는 API 설계가 검증보다 낫다.

## 면접에서 나올 만한 질문

### 클라이언트 검증만으로 왜 안 되나?

공격자는 브라우저가 필요 없기 때문이다. curl이나 스크립트로 서버 엔드포인트에 바로 요청을 쏘면 클라이언트 검증 코드는 실행될 일이 없다. 실제로 화면에서 가격을 못 바꾸게 막아도 서버에 직접 음수 가격을 보내면 그대로 처리된다. 클라이언트 검증은 즉각 피드백으로 UX를 높이는 편의이고, 신뢰의 근거는 반드시 서버 검증이다.

### 검증과 인코딩은 무엇이 다르고 왜 둘 다 필요한가?

검증은 값이 받아들일 만한가를 입력 경계에서 판정하고(통과/거부), 인코딩은 값을 특정 자리에 넣을 때 그 자리에서 위험한 기호를 평범한 글자로 바꾼다. 같은 값이라도 나가는 자리마다 위험한 기호가 다르기 때문에(HTML의 `<`, SQL의 `'`, 셸의 `;`) 입력 때 한 번에 걸러 둘 수 없다. 원본은 검증만 해 저장하고 손질은 쓰는 자리에서 한다.

### 검증과 이스케이프 중 무엇이 XSS를 막나?

근본적으로는 출력 인코딩(이스케이프)이 막는다. XSS는 데이터가 HTML·JS 문맥에서 코드로 해석될 때 생기므로, 그 자리에서 `<` 같은 기호를 이스케이프하면 데이터로 머문다. 입력 검증은 보조다. 허용 목록 검증이 공격 표면을 줄여 주지만, 검증만으로는 모든 문맥을 커버할 수 없어 출력 자리의 인코딩이 핵심 방어다.

### 허용 목록이 차단 목록보다 나은 이유는?

나쁜 것을 다 나열하는 차단 목록은 지는 싸움이기 때문이다. 하나 막으면 변형이 나온다. 반면 좋은 모양만 정의하는 허용 목록은 예상 못 한 입력을 전부 자동으로 거른다. 수량이면 "정수 1~100만 통과"가 허용 목록이고, "음수 금지, 소수 금지…"처럼 나쁜 경우를 쫓는 건 차단 목록이다.

### 유니코드 입력을 왜 정규화 먼저 해야 하나?

같은 글자를 적는 바이트가 여럿이고 눈에 똑같은 다른 글자가 있기 때문이다. 전각 ＡＤＭＩＮ은 NFKC 정규화하면 admin이 되고, é는 한 글자로도 두 글자로도 쓰인다. 정규화 없이 검사하면 ＡＤＭＩＮ이 금지어 검사를 지나친 뒤 다른 곳에서 admin으로 보일 수 있다. 그래서 정규화(보통 NFKC) → 필요하면 혼동 문자 거르기 → 검증 순서로 한다.

### ReDoS가 무엇이고 어떻게 막나?

검증에 쓴 정규식이 특정 입력에서 백트래킹이 폭발해 지수적으로 느려지는 서비스 거부다. (a+)+$ 같은 중첩 수량자가 대표로, 실험에서 28자 입력에 2.7초가 걸렸다. 조금 더 길면 몇 분이 되어 요청 스레드를 묶는다. 중첩 수량자를 피해 정규식을 쓰고, 선형 시간 엔진(RE2)으로 돌리고, 입력 길이에 상한을 둔다.

### 대량 할당을 어떻게 막나?

클라이언트가 보낸 객체를 통째로 내부 객체에 합치지 않는다. Object.assign으로 요청 본문을 그대로 합치면 role 같은 필드까지 끼워 넣을 수 있다. 받을 필드를 허용 목록으로 명시해 고르거나, 스키마에서 정의하지 않은 키를 떨구거나(strip) 거부하게(strict) 한다. 요청 객체를 믿지 않고 필요한 필드만 추린다.

### 검증 실패는 어떻게 응답해야 하나?

400이나 422로, 어느 필드가 왜 틀렸는지 구조화해 돌려주되 여러 필드가 틀렸으면 한 번에 모아 준다. 단 사용자 입력을 그대로 에러에 되비추지 않는다(반사형 XSS 통로). 스택 트레이스·SQL 에러 같은 내부 정보도 응답에 넣지 않고 로그에만 남긴다. 실패를 로그로 남겨 특정 IP가 반복해 두드리면 무차별 대입·스캔으로 탐지한다.
