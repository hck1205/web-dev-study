react-dom 19.3 개발 빌드에서 그대로 옮긴 코드다. `lanes & -lanes`, `& 42`. 둘 다 정수 하나를 비트의 묶음으로 쓰는 코드다. 이 글은 이런 코드를 읽고 쓸 수 있게 비트 연산을 처음부터 따라간다. 연산 다섯 개와 시프트, 플래그를 켜고 끄는 법, 가장 낮은 1 비트를 다루는 요령, XOR로 짝 없는 수 찾기, 비트마스크로 부분집합을 훑는 법과 외판원 문제의 비트마스크 DP까지 간다. 마지막으로 자바스크립트가 비트 연산에서 숫자를 32비트로 자르는 함정과 바이트 순서를 본다.

## 숫자 하나에 스위치 아홉 개

리눅스 파일 권한은 소유자, 그룹, 나머지 세 칸에 각각 읽기(r), 쓰기(w), 실행(x)이 있어 모두 아홉 개의 켜짐·꺼짐이다. 이걸 비트 아홉 개에 나란히 놓는다. 한 칸의 r, w, x는 각각 4, 2, 1의 자리다. 그래서 세 비트짜리 한 칸이 0부터 7까지의 수가 되고, 세 칸을 8진수 세 자리로 적은 것이 755다.

```bash
touch deploy.sh
chmod 755 deploy.sh              # 소유자 7, 그룹 5, 나머지 5
stat -c '%a %A %n' deploy.sh     # 8진수 권한, 기호 권한, 파일 이름
chmod g+w deploy.sh              # 그룹 칸의 쓰기 비트만 켠다
stat -c '%a %A %n' deploy.sh
chmod o-x deploy.sh              # 나머지 칸의 실행 비트만 끈다
stat -c '%a %A %n' deploy.sh
```

```text
755 -rwxr-xr-x deploy.sh
775 -rwxrwxr-x deploy.sh
774 -rwxrwxr-- deploy.sh
```

같은 일을 코드로 해 보면 비트 연산의 기본기가 전부 나온다.

```js
const R = 4, W = 2, X = 1;
const mode = 0o755;
console.log("0o755 =", mode, mode.toString(2).padStart(9, "0"));
const owner = (mode >> 6) & 7, group = (mode >> 3) & 7, other = mode & 7; // 칸을 오른쪽으로 내리고 아래 세 비트만 남긴다
console.log("owner", owner, "group", group, "other", other);
console.log("group can write?", (group & W) !== 0, " other can read?", (other & R) !== 0);
let m = mode;
m |= W << 3;   console.log("g+w ->", m.toString(8));        // 켜기
m &= ~(X << 0); console.log("o-x ->", m.toString(8));       // 끄기
m ^= R << 0;   console.log("toggle o+r ->", m.toString(8)); // 뒤집기
```

```text
0o755 = 493 111101101
owner 7 group 5 other 5
group can write? false  other can read? true
g+w -> 775
o-x -> 774
toggle o+r -> 770
```

`chmod g+w`가 하는 일이 `m |= W << 3` 한 줄이다. 쓰기 비트(2)를 그룹 칸 위치로 세 자리 올린 다음 OR로 켠다. 새로 만든 파일의 권한이 644가 되는 umask도 같은 계산이다. 파일의 기본 666에서 umask 022의 비트를 끈다(`0o666 & ~0o022`).

```bash
umask                            # 현재 umask
touch new.txt && mkdir newdir    # 새 파일과 새 디렉터리
stat -c '%a %A %n' new.txt newdir
```

```text
0022
644 -rw-r--r-- new.txt
755 drwxr-xr-x newdir
```

권한 검사 순서와 특수 비트는 [리눅스 파일 권한](/posts/linux-files-permissions)에서 다뤘다.

## 연산 다섯 개와 시프트

비트 연산은 두 수의 같은 자리끼리 계산한다. 자리 올림이 없어서 각 자리가 서로 독립이다.

```js
const show = (label, v) => console.log(label.padEnd(22), String(v).padStart(12));
show("12 & 10", 12 & 10);   // 1100 & 1010 = 1000  둘 다 1인 자리만
show("12 | 10", 12 | 10);   // 1100 | 1010 = 1110  하나라도 1이면
show("12 ^ 10", 12 ^ 10);   // 1100 ^ 1010 = 0110  서로 다르면
show("~12", ~12);           // 모든 자리를 뒤집는다
show("5 << 3", 5 << 3);     // 왼쪽으로 세 칸, 2^3을 곱한 것과 같다
show("-16 >> 2", -16 >> 2); // 부호를 유지하며 오른쪽으로
show("-16 >>> 2", -16 >>> 2); // 빈자리를 0으로 채우며 오른쪽으로
```

```text
12 & 10                           8
12 | 10                          14
12 ^ 10                           6
~12                             -13
5 << 3                           40
-16 >> 2                         -4
-16 >>> 2                1073741820
```

쓰임새로 정리하면 이렇다. AND는 원하는 자리만 남기는 거름망(마스크)이다. `x & 7`은 아래 세 비트만 남긴다. OR는 원하는 자리를 켠다. XOR는 원하는 자리를 뒤집고, 두 값이 어디서 다른지 찾는다. NOT은 마스크를 반대로 만들 때 쓴다. `x & ~mask`가 "그 자리만 끄기"다.

`~12`가 -13인 건 2의 보수 때문이다. 음수 -n은 n의 비트를 모두 뒤집고 1을 더한 값이라서, 뒤집기만 한 `~n`은 -n - 1이 된다. 시프트도 두 종류다. `>>`(산술 시프트)는 맨 위 부호 비트를 복사하며 내려서 -16이 -4가 된다. 2로 나누는 효과를 음수에서도 지킨다. `>>>`(논리 시프트)는 빈자리를 0으로 채운다. 그래서 음수를 넣으면 맨 위가 0이 되며 큰 양수가 나온다. Java에도 `>>`와 `>>>`가 똑같이 있다. C는 연산자가 `>>` 하나뿐이고, 음수를 오른쪽으로 밀 때 산술인지 논리인지는 오랫동안 구현이 정하는 동작이었다(C++20부터는 산술 시프트로 정해졌다).

## 가장 낮은 1 비트를 다루는 두 가지 요령

비트 요령의 대부분은 두 식에서 나온다. `n & (n - 1)`과 `n & -n`이다.

```js
const b = (v, w = 8) => (v >>> 0).toString(2).padStart(w, "0").slice(-w);
const n = 40;
console.log("n        ", b(n));
console.log("n - 1    ", b(n - 1));
console.log("n & (n-1)", b(n & (n - 1)));
console.log("-n       ", b(-n));
console.log("n & -n   ", b(n & -n), n & -n);
```

```text
n         00101000
n - 1     00100111
n & (n-1) 00100000
-n        11011000
n & -n    00001000 8
```

1을 빼면 가장 낮은 1이 0이 되고 그 아래가 모두 1로 바뀐다. 원래 수와 AND하면 가장 낮은 1 하나만 꺼진다. 2의 보수에서 -n은 "뒤집고 1을 더한" 값이라, 가장 낮은 1의 위쪽은 모두 원래와 반대가 되고 그 자리와 아래만 원래와 같다. AND하면 가장 낮은 1 하나만 남는다.

이 두 식으로 많은 일을 한다.

- 2의 거듭제곱인지: 1이 하나뿐인 수라서 `n > 0 && (n & (n - 1)) === 0`이다. 0과 음수를 빼는 조건을 잊는 실수가 흔하다.
- 켜진 비트 세기: 0이 될 때까지 `n &= n - 1`을 반복하고 횟수를 센다. 켜진 비트 수만큼만 돈다.
- 가장 낮은 비트 꺼내기: `n & -n`. React가 여러 lane 중 가장 급한 것을 고를 때 쓰는 식이다. 숫자가 작은 비트일수록 급한 lane으로 배치해 두었기 때문에 가장 낮은 비트가 곧 가장 급한 일이다. 펜윅 트리의 구간 이동도 이 식이다.

켜진 비트를 세는 과정을 그림으로 보자. 44는 `00101100`이다. 다음을 누를 때마다 `n &= n - 1`이 가장 낮은 1을 하나씩 지운다.

자바스크립트에는 C++의 `std::popcount`나 Java의 `Integer.bitCount` 같은 내장 함수가 없다. 대신 `Math.clz32`(맨 위에서부터 0이 몇 개인지)가 있어서 `31 - Math.clz32(n)`이 가장 높은 1의 위치다. React도 lane 위치를 이 식으로 구한다. 반복 없이 비트를 세려면 두 칸씩, 네 칸씩 묶어 더하는 SWAR 방식을 쓴다.

```js
function popcountSWAR(x) {
  x = x - ((x >>> 1) & 0x55555555);                // 2비트마다 켜진 수
  x = (x & 0x33333333) + ((x >>> 2) & 0x33333333); // 4비트마다
  x = (x + (x >>> 4)) & 0x0f0f0f0f;                // 8비트마다
  return Math.imul(x, 0x01010101) >>> 24;          // 네 바이트를 맨 위 바이트에 모은다
}
for (const x of [0, 7, 40, 255, 0xffffffff, -1]) console.log("popcount", x, popcountSWAR(x));
```

```text
popcount 0 0
popcount 7 3
popcount 40 2
popcount 255 8
popcount 4294967295 32
popcount -1 32
```

`Math.imul`은 32비트 곱셈이다. `x * 0x01010101`을 그냥 쓰면 결과가 2⁵³을 넘어 아래 비트가 뭉개질 수 있다. 32비트 정수 곱셈을 정확히 흉내 내야 할 때는 `Math.imul`을 쓴다.

## 짝이 없는 수는 XOR가 찾는다

XOR에는 세 가지 성질이 있다. 같은 수를 두 번 XOR하면 0이 된다(`a ^ a = 0`). 0과 XOR해도 그대로다(`a ^ 0 = a`). 순서를 바꿔도 결과가 같다. 그래서 모든 수가 두 번씩 나오고 하나만 한 번 나오는 배열을 전부 XOR하면, 짝이 있는 수는 서로 지워지고 하나만 남는다. 해시 집합 없이 O(1) 메모리로 푼다.

같은 생각을 조금씩 바꾸면 면접 단골 문제가 여럿 풀린다.

```js
const single = a => a.reduce((x, y) => x ^ y, 0);
console.log("single [4,1,2,1,2] =", single([4, 1, 2, 1, 2]));

// 0..n 중 빠진 수 하나: 인덱스와 값을 모두 섞으면 빠진 수만 짝이 없다
const missing = a => { let x = a.length; a.forEach((v, i) => (x ^= i ^ v)); return x; };
console.log("missing [3,0,1] =", missing([3, 0, 1]), " [9,6,4,2,3,5,7,0,1] =", missing([9, 6, 4, 2, 3, 5, 7, 0, 1]));

// 짝 없는 수가 둘: 전체 XOR의 아무 1 비트로 두 무리를 가른다
function twoSingles(a) {
  const x = a.reduce((s, v) => s ^ v, 0); // 두 수의 XOR
  const low = x & -x;                     // 두 수가 다른 자리 하나
  let r = 0;
  for (const v of a) if (v & low) r ^= v; // 그 자리가 켜진 무리만 섞는다
  return [r, x ^ r].sort((u, v) => u - v);
}
console.log("twoSingles [1,2,1,3,2,5] =", twoSingles([1, 2, 1, 3, 2, 5]));
```

```text
single [4,1,2,1,2] = 4
missing [3,0,1] = 2  [9,6,4,2,3,5,7,0,1] = 8
twoSingles [1,2,1,3,2,5] = [ 3, 5 ]
```

짝 없는 수가 둘일 때가 재미있다. 전체를 XOR하면 두 수의 XOR(3 ^ 5 = 6, `110`)이 남는다. 0이 아니니 두 수가 다른 자리가 적어도 하나 있다. 그 자리 하나(`x & -x` = 2)가 켜졌는지로 배열을 두 무리로 나누면, 두 수는 서로 다른 무리에 들어가고 짝이 있는 수는 둘이 같은 무리로 간다. 무리마다 XOR하면 각자 하나씩 남는다.

임시 변수 없이 두 값을 바꾸는 XOR 교환(`a ^= b; b ^= a; a ^= b`)도 유명하지만 쓸 일은 거의 없다. 두 변수가 같은 메모리를 가리키면 값이 0이 된다. `arr[i]`와 `arr[j]`를 바꾸는데 i와 j가 같으면 첫 줄에서 자기 자신과 XOR해 0이 되고, 그 뒤로는 0끼리 섞일 뿐이다. 요즘 컴파일러는 임시 변수를 레지스터로 처리하니 속도 이득도 없다. 구조 분해 `[a, b] = [b, a]`를 쓴다.

XOR가 "두 값이 다른 곳"을 찾는다는 성질은 실무에도 있다. RAID 5는 디스크들의 XOR를 패리티로 저장해 두었다가 디스크 하나가 죽으면 나머지와 패리티를 XOR해 되살린다. 두 해시의 비트가 몇 개 다른지(해밍 거리)는 `popcount(a ^ b)`다.

## 정수 하나로 부분집합을 센다

원소가 n개인 집합의 부분집합은 2ⁿ개이고, 각 부분집합은 "원소마다 넣었나 안 넣었나"를 적은 n비트 수 하나와 정확히 대응한다. 그래서 0부터 2ⁿ - 1까지 세기만 하면 모든 부분집합을 빠짐없이 한 번씩 훑는다.

```js
const items = ["a", "b", "c"];
for (let mask = 0; mask < 1 << items.length; mask++) {
  const picked = items.filter((_, i) => mask & (1 << i)); // i번 비트가 켜졌으면 i번 원소를 넣는다
  console.log(mask.toString(2).padStart(3, "0"), picked.join(",") || "∅");
}
```

```text
000 ∅
001 a
010 b
011 a,b
100 c
101 a,c
110 b,c
111 a,b,c
```

재귀로 넣는다·안 넣는다를 고르는 [백트래킹](/posts/recursion-backtracking)과 같은 일이지만, 상태가 정수 하나라서 배열 인덱스로 쓸 수 있다는 점이 다르다. 이게 바로 아래 비트마스크 DP의 바탕이다.

어떤 마스크의 부분집합만 훑고 싶을 때(부분 마스크 순회)는 `s = (s - 1) & m`을 반복한다. 1을 빼서 아래 자리를 하나 내리고 m에 없는 비트는 AND로 지운다.

```js
const m = 0b1011, subs = [];
for (let s = m; s; s = (s - 1) & m) subs.push(s.toString(2).padStart(4, "0"));
subs.push("0000"); // 빈 집합은 반복 조건 때문에 따로 넣는다
console.log("submasks of 1011:", subs.join(" "));
```

```text
submasks of 1011: 1011 1010 1001 1000 0011 0010 0001 0000
```

모든 마스크마다 그 부분 마스크를 다 훑으면 전체가 3ⁿ번이다. 원소마다 "바깥 마스크에 없다 / 있고 부분에도 있다 / 있는데 부분에는 없다" 세 경우라서다. n = 15면 약 1400만으로 해 볼 만하지만 n = 20이면 35억이라 어렵다.

## 외판원 문제를 비트마스크 DP로

도시 n개를 모두 한 번씩 들르고 출발지로 돌아오는 가장 짧은 길을 찾는 문제가 외판원 문제(TSP)다. 순서를 전부 따지면 (n - 1)!가지라 도시 13개면 4억 8천만 가지를 넘는다. 그런데 잘 보면 "지금까지 어느 도시들을 들렀고, 지금 어디에 있나"만 같으면 들른 순서는 앞으로의 선택과 상관이 없다. 이 두 가지를 상태로 삼는다.

dp[mask][last] = 0번에서 출발해 mask에 켜진 도시들을 모두 들르고 지금 last에 있을 때의 최소 거리. 상태 정의와 점화식을 세우는 법은 [동적 계획법](/posts/dynamic-programming) 글을 따른다. 여기서는 mask라는 정수가 집합을 대신한다는 점만 새롭다.

```js
function tsp(dist) {
  const n = dist.length, FULL = 1 << n;
  const dp = Array.from({ length: FULL }, () => new Array(n).fill(Infinity));
  dp[1][0] = 0;                                    // 0번 도시만 들르고 0번에 있다
  for (let mask = 1; mask < FULL; mask++) {
    if (!(mask & 1)) continue;                     // 출발지가 빠진 상태는 없다
    for (let last = 0; last < n; last++) {
      if (!(mask & (1 << last)) || dp[mask][last] === Infinity) continue;
      for (let nx = 0; nx < n; nx++) {
        if (mask & (1 << nx)) continue;            // 이미 들른 도시
        const nm = mask | (1 << nx);               // nx를 들른 것으로 켠다
        dp[nm][nx] = Math.min(dp[nm][nx], dp[mask][last] + dist[last][nx]);
      }
    }
  }
  let best = Infinity;
  for (let last = 1; last < n; last++) best = Math.min(best, dp[FULL - 1][last] + dist[last][0]);
  return n === 1 ? 0 : best;
}
```

mask를 작은 수부터 도는 것만으로 채우는 순서가 맞는다. 도시를 하나 더 들르면 비트가 하나 켜져 mask가 반드시 커지기 때문이다. 상태는 2ⁿ × n개, 상태마다 다음 도시 n개를 보니 시간은 O(2ⁿ · n²), 메모리는 O(2ⁿ · n)이다. 계승보다는 훨씬 작지만 여전히 지수다. 실제로 재 보면 이렇다.

```text
tsp D4 = 80
n=12 states=49152 best=170 10ms
n=16 states=1048576 best=247 85ms
n=18 states=4718592 best=163 304ms
```

첫 줄은 4개 도시 예제의 답이고, 모든 순서를 따지는 완전 탐색으로 확인한 값과 같다. 나머지는 1~100 사이 무작위 거리 표로 도시 수를 늘려 가며 잰 결과다. 18개까지는 0.3초지만 도시 하나가 늘 때마다 두 배 넘게 늘어난다. 메모리가 먼저 막힌다. n = 20이면 칸이 2000만 개를 넘어, 칸 하나가 8바이트인 `Float64Array`로 잡아도 약 170MB다. 위 코드처럼 일반 배열의 배열로 잡으면 그보다 훨씬 많다. 그래서 비트마스크 DP는 대략 n이 20 안팎까지일 때 고르는 방법이고, 그보다 크면 근사 알고리즘이나 휴리스틱으로 간다. 면접 문제에서 n ≤ 16 같은 제약이 보이면 비트마스크를 떠올리면 된다.

## 자바스크립트는 비트 연산 앞에서 32비트로 자른다

자바스크립트의 Number는 64비트 부동소수점이다. 그런데 비트 연산자를 쓰는 순간 피연산자를 32비트 부호 있는 정수로 바꾼다(명세의 ToInt32). `>>>`만 결과를 부호 없는 32비트(ToUint32)로 낸다. 이 변환이 조용히 일어나서 큰 수를 넣어도 에러 없이 엉뚱한 값이 나온다.

```js
show("1 << 31", 1 << 31);                  // 맨 위 비트가 부호 비트다
show("1 << 32", 1 << 32);                  // 시프트 횟수도 32로 나눈 나머지만 쓴다
show("(2**32 + 5) | 0", (2 ** 32 + 5) | 0); // 위쪽 비트가 잘린다
show("2**31 | 0", 2 ** 31 | 0);
show("-1 >>> 0", -1 >>> 0);                // 부호 없는 32비트로 읽기
show("(1 << 31) >>> 0", (1 << 31) >>> 0);
show("~~3.7", ~~3.7);
show("~~-3.7", ~~-3.7);
show("Math.floor(-3.7)", Math.floor(-3.7));
show("~~3e9", ~~3e9);
```

```text
1 << 31                 -2147483648
1 << 32                           1
(2**32 + 5) | 0                   5
2**31 | 0               -2147483648
-1 >>> 0                 4294967295
(1 << 31) >>> 0          2147483648
~~3.7                             3
~~-3.7                           -3
Math.floor(-3.7)                 -4
~~3e9                   -1294967296
```

현장에서 만나는 모습은 대개 이렇다.

- 31번 비트를 플래그로 쓰면 그 값이 음수로 나온다. `flags & (1 << 31)`의 결과가 -2147483648이라 `> 0`으로 검사하면 틀린다. `!== 0`으로 검사하거나 플래그를 31개까지만 쓴다. React의 lane도 31개다.
- `x | 0`이나 `~~x`로 소수점을 버리는 코드는 21억을 넘는 수에서 깨지고, 음수에서는 `Math.floor`와 방향이 다르다. `Math.trunc`를 쓴다.
- 밀리초 타임스탬프에 비트 연산을 하면 망가진다. `1761220000000 | 0`은 283408640이다. 해시를 만든다며 `Date.now() | 0`을 쓰는 코드가 이 문제를 안고 있다.
- 32비트 부호 없는 값(IPv4 주소, CRC32 체크섬)을 다룰 때는 계산 끝에 `>>> 0`을 붙여 양수로 돌려놓는다.

64비트가 필요하면 BigInt를 쓴다. BigInt의 비트 연산은 자르지 않는다. 대신 Number와 섞을 수 없고, 고정 폭이 필요하면 `BigInt.asUintN(64, x)`로 직접 자른다.

```js
show("1n << 40n", 1n << 40n);
show("BigInt.asUintN(64, -1n)", BigInt.asUintN(64, -1n));
```

```text
1n << 40n              1099511627776
BigInt.asUintN(64, -1n) 18446744073709551615
```

64비트 ID가 대표적인 경우다. 시간, 서버 번호, 순번을 비트로 이어 붙이는 스노플레이크 ID는 위쪽 비트에 타임스탬프가 들어 있어서 `id >> 22n`으로 꺼낸다. 그런데 이 ID를 JSON에서 숫자로 받으면 `JSON.parse`가 Number로 읽으며 2⁵³을 넘는 아래 자리를 잃는다. `175928847299117063`이 `175928847299117060`이 된다. 그래서 이런 API는 ID를 문자열로 내려주고, 클라이언트는 `BigInt(id)`로 바꿔 비트 연산을 한다. ID 설계 자체는 [고유 ID 생성기](/posts/sd-unique-id-generator)에 있다.

## 바이트를 놓는 순서

비트 연산은 값 위에서 일어나서 메모리에 어떻게 놓였는지 신경 쓰지 않아도 된다. 하지만 값을 바이트로 쪼개 파일이나 네트워크로 보낼 때는 순서가 문제가 된다. 0x12345678을 메모리에 놓을 때 큰 자리 바이트(12)부터 놓으면 빅 엔디언, 작은 자리(78)부터 놓으면 리틀 엔디언이다. x86과 대부분의 ARM 환경은 리틀 엔디언이고, 네트워크 프로토콜 헤더는 빅 엔디언(네트워크 바이트 순서)으로 정해져 있다.

```js
import os from "node:os";
console.log("os.endianness():", os.endianness());
const buf = new ArrayBuffer(4);
new Uint32Array(buf)[0] = 0x12345678;              // 이 기계의 순서로 저장된다
console.log("Uint32Array bytes:", [...new Uint8Array(buf)].map(x => x.toString(16)).join(" "));
const dv = new DataView(new ArrayBuffer(4));
dv.setUint32(0, 0x12345678);                       // DataView는 기본이 빅 엔디언
console.log("DataView default (big):", [...new Uint8Array(dv.buffer)].map(x => x.toString(16)).join(" "));
console.log("read as little:", dv.getUint32(0, true).toString(16));
const b = Buffer.from([0x00, 0x00, 0x01, 0xbb]);
console.log("port BE", b.readUInt16BE(2), " LE", b.readUInt16LE(2));
```

```text
os.endianness(): LE
Uint32Array bytes: 78 56 34 12
DataView default (big): 12 34 56 78
read as little: 78563412
port BE 443  LE 47873
```

`Uint32Array`는 기계의 순서를 그대로 따르고, `DataView`는 기본이 빅 엔디언이며 마지막 인자 `true`로 리틀 엔디언을 고른다. 마지막 줄이 실제로 겪는 버그다. 패킷의 포트 바이트 `01 bb`를 빅 엔디언으로 읽으면 443인데, 리틀 엔디언으로 읽으면 47873이 된다. 바이너리 형식을 파싱할 때는 그 형식의 명세가 정한 순서를 `DataView`의 인자로 명시하고, 기계 순서를 따르는 타입 배열로 바로 읽지 않는다.

## 현장에서 비트마스크를 고를 때와 피할 때

비트마스크는 작고 빠르다. 권한 32개가 정수 하나, 4바이트에 들어간다. 검사는 AND 한 번이다. [블룸 필터](/posts/bloom-filter)나 비트맵 인덱스처럼 수백만 개의 예·아니요를 담는 구조도 결국 비트 배열이다. 그래서 메모리와 속도가 중요한 곳, 집합 연산(교집합은 AND, 합집합은 OR)을 많이 하는 곳에서 고른다.

반대로 피해야 할 때도 분명하다. DB 컬럼에 권한 비트마스크를 넣으면 "쓰기 권한이 있는 사용자"를 찾는 `WHERE perms & 2 <> 0`이 일반 B-tree 인덱스를 쓰지 못해 표 전체를 훑는다. 비트 하나하나의 뜻이 코드에만 있어서 DB를 직접 보는 사람은 `perms = 37`이 무슨 뜻인지 모른다. 비트 자리를 한 번 정하면 바꾸기도 어렵다. 중간 비트의 뜻을 바꾸면 저장된 모든 값의 뜻이 바뀐다. 권한 종류가 자주 늘거나 권한으로 검색할 일이 많으면 별도 표(사용자-권한)나 불리언 컬럼이 낫다. [기능 플래그](/posts/feature-flags)처럼 운영 중에 켜고 끄는 값도 비트로 압축하기보다 이름 있는 설정으로 두는 쪽이 사고가 적다.

코드에 남길 때는 자리 값을 이름 있는 상수로 정의한다. `1 << 3`보다 `CAN_DELETE`가 읽힌다. 자바스크립트라면 31비트를 넘지 않게 하고, 더 필요하면 BigInt나 `Uint32Array` 여러 칸으로 나눈다.

도시 1개일 때를 빼먹으면 `best`가 `Infinity`로 남는다. "한 방향만 가까움" 테스트는 0→1→2→3→0 방향으로만 거리가 1이라서, 거리 표를 `dist[nx][last]`처럼 뒤집어 읽으면 틀린다.

비트 연산은 결국 정수 하나를 작은 스위치 배열로 보는 눈이다. 켜기는 OR, 끄기는 AND와 NOT, 뒤집기는 XOR, 확인은 AND다. `n & (n - 1)`과 `n & -n` 두 식이 가장 낮은 비트를 다루고, 정수가 집합을 대신하면 부분집합 순회와 비트마스크 DP가 된다. 자바스크립트에서는 이 모든 일이 32비트 안에서만 일어난다는 사실을 늘 같이 기억한다.

## 면접에서 나올 만한 질문

### 비트 연산으로 플래그를 켜고, 끄고, 뒤집고, 확인하는 방법을 설명해 주세요.

플래그 자리 값을 `1 << k`로 만든 뒤 켜기는 `x | flag`, 끄기는 `x & ~flag`, 뒤집기는 `x ^ flag`, 확인은 `(x & flag) !== 0`이다. `chmod g+w`가 그룹 쓰기 비트에 OR를 하는 것과 같다. 확인할 때 `> 0`을 쓰면 31번 비트처럼 부호 비트가 켜진 경우 결과가 음수라 틀리므로 `!== 0`으로 비교한다.

### n & (n - 1)과 n & -n은 각각 무엇을 하나요?

`n & (n - 1)`은 가장 낮은 1 비트 하나를 끈다. 1을 빼면 그 비트가 0이 되고 아래가 1로 바뀌기 때문이다. 이걸로 2의 거듭제곱 판별(결과가 0인지)과 켜진 비트 세기를 한다. `n & -n`은 2의 보수 성질 때문에 가장 낮은 1 비트 하나만 남긴다. React가 가장 급한 lane을 고르거나 펜윅 트리가 구간을 옮길 때 쓴다.

### 배열에서 한 번만 나오는 수를 O(1) 메모리로 찾으려면 어떻게 하나요?

모든 수를 XOR한다. 같은 수를 두 번 XOR하면 0이 되고 순서를 바꿔도 결과가 같아서, 짝이 있는 수는 지워지고 한 번 나온 수만 남는다. 짝 없는 수가 둘이면 전체 XOR에서 아무 1 비트 하나를 골라 그 비트로 배열을 두 무리로 나누고 무리마다 XOR한다.

### 비트마스크 DP는 언제 쓰고 한계는 무엇인가요?

상태에 "어떤 원소들을 이미 골랐나"라는 집합이 들어가고 원소 수가 20개 안팎으로 작을 때 쓴다. 집합을 정수 하나로 나타내면 배열 인덱스로 쓸 수 있어서, 외판원 문제를 (n - 1)! 대신 O(2ⁿ · n²)에 푼다. 그래도 지수라서 n이 하나 늘 때마다 두 배 넘게 늘고, n = 20이면 칸이 2000만 개를 넘어 메모리가 먼저 막힌다. 그보다 크면 근사 알고리즘으로 간다.

### 자바스크립트에서 비트 연산을 쓸 때 주의할 점은 무엇인가요?

비트 연산자는 피연산자를 32비트 부호 있는 정수로 바꾼다. 그래서 21억을 넘는 수는 위쪽 비트가 잘리고, `1 << 31`은 음수, `1 << 32`는 1이 된다. 타임스탬프나 64비트 ID에 비트 연산을 하면 조용히 틀린 값이 나온다. 부호 없는 결과가 필요하면 `>>> 0`, 64비트가 필요하면 BigInt를 쓰고, 소수점 버리기는 `| 0` 대신 `Math.trunc`를 쓴다.

### 64비트 ID를 JSON 숫자로 내려주면 무엇이 문제인가요?

자바스크립트 Number는 2⁵³까지만 정수를 정확히 담아서 `JSON.parse`가 아래 자리를 잃는다. 예를 들어 175928847299117063이 175928847299117060이 되어 다른 ID를 가리킨다. 그래서 큰 ID는 문자열로 내려주고, 비트 연산이 필요하면 클라이언트에서 BigInt로 바꾼다.

### 엔디언은 무엇이고 언제 신경 써야 하나요?

여러 바이트짜리 값을 메모리에 놓는 순서다. 큰 자리부터면 빅 엔디언, 작은 자리부터면 리틀 엔디언이고, x86과 대부분의 ARM은 리틀, 네트워크 헤더는 빅 엔디언이다. 값 위에서 하는 비트 연산에는 영향이 없지만, 바이너리 파일이나 패킷을 바이트로 읽고 쓸 때는 형식이 정한 순서를 따라야 한다. 자바스크립트에서는 `DataView`에 엔디언을 명시하고, 기계 순서를 따르는 타입 배열로 바로 읽지 않는다.

### 권한을 DB에 비트마스크 컬럼으로 저장하는 건 좋은 설계인가요?

저장 공간과 검사 속도는 좋지만 단점이 크다. `perms & 2 <> 0` 같은 조건은 일반 B-tree 인덱스를 못 써서 표 전체를 훑고, 값의 뜻이 코드에만 있어 운영 중에 읽기 어렵고, 비트 자리의 뜻을 바꾸면 저장된 모든 값이 바뀐다. 권한 종류가 자주 늘거나 권한으로 검색할 일이 많으면 사용자-권한 표나 불리언 컬럼이 낫다. 고정된 작은 플래그 묶음을 메모리 안에서 다룰 때 비트마스크가 맞다.
