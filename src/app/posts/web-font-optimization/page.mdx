글을 열면 첫 문단이 뜨고, 1초쯤 지나 글자 모양이 한 번 바뀌면서 아래 내용이 위로 훅 당겨진다. 느린 지하철 와이파이에서는 아예 글자가 없는 빈 줄만 한참 보이기도 한다. Network 패널을 열어 보면 원인은 폰트 파일 하나다. 2MB가 넘는 한글 폰트가 받아질 때까지 브라우저가 글자를 숨기거나, 다른 폰트로 그렸다가 바꿔 끼운다.

웹 폰트는 디자인에서 빼기 어렵다. 대신 언제 받기 시작하는지, 받는 동안 무엇을 보여 줄지, 얼마나 받을지는 고를 수 있다. 이 글은 한글 폰트 Pretendard를 가지고 그 세 가지를 실제로 재 본다. 측정은 Chromium 141(Playwright로 실행), 390px 화면 기준이고, 폰트 파일은 이 블로그가 쓰는 `pretendard` 1.3.9 패키지에 든 것을 그대로 썼다.

CSS 파일 자체의 렌더링 차단과 크리티컬 CSS는 [CSS 성능](/posts/css-performance)에서, CLS를 세는 규칙은 [Core Web Vitals](/posts/core-web-vitals)에서 다뤘다. 여기서는 폰트에만 집중한다.

## 한글 폰트가 무거운 이유

영문 폰트는 대소문자와 숫자, 기호를 합쳐 수백 글리프면 된다. 한글은 조합 가능한 현대 한글 음절만 11,172자다. 자주 쓰는 글자만 모은 KS X 1001 완성형도 2,350자다. 글자 수가 수십 배라 파일도 수십 배다.

fontTools로 패키지에 든 파일을 열어 글리프 수를 셌다.

```text
PretendardVariable.woff2 glyphs 14757 cmap 14336 hangul 11172 upm 2048 hhea asc/desc/gap 1950 -494 0 axes [('wght', 45.0, 930.0)]
Pretendard-Regular.woff2 glyphs 14716 cmap 14336 hangul 11172 upm 2048 hhea asc/desc/gap 1950 -494 0 axes -
Pretendard-Regular.subset.woff2 glyphs 4381 cmap 3728 hangul 2780 upm 2048 hhea asc/desc/gap 1950 -494 0 axes -
```

파일 크기는 이렇다(`ls -l`의 바이트 수).

```text
6739336  PretendardVariable.ttf          가변 폰트 원본
2057688  PretendardVariable.woff2        가변 폰트, woff2 압축
 765892  Pretendard-Regular.woff2        굵기 하나(400)
 778432  Pretendard-Medium.woff2         굵기 하나(500)
 791156  Pretendard-Bold.woff2           굵기 하나(700)
 267096  Pretendard-Regular.subset.woff2 한글 2,780자만 남긴 것
```

먼저 형식부터 정리된다. woff2는 폰트 데이터를 Brotli로 압축한 웹 전용 형식이고, 지금 쓰는 브라우저는 모두 지원한다. 같은 가변 폰트가 TTF로는 6.7MB, woff2로는 2.06MB다. 웹에 TTF나 OTF를 그대로 올릴 이유는 없다.

다음은 가변 폰트(variable font)다. 가변 폰트는 굵기 같은 축을 파일 하나에 담아서, `font-weight`를 45부터 930까지 아무 값으로나 쓸 수 있게 한다. 위 출력의 `axes [('wght', 45.0, 930.0)]`가 그 축이다. 굵기 셋(400·500·700)을 정적 파일로 받으면 2,335,480바이트이고 가변 폰트 하나는 2,057,688바이트다. 굵기를 셋 이상 쓰면 가변 폰트가 이득이고, 하나만 쓴다면 정적 파일 하나(766KB)가 훨씬 가볍다. 쓰는 굵기를 먼저 세어 보는 게 순서다.

마지막 줄이 이 글의 나머지 절반이다. 필요한 글자만 남기면(서브셋) 크기가 확 준다. 이건 뒤에서 자세히 본다.

## 폰트는 CSS를 읽은 뒤에야 발견된다

폰트 요청은 이미지보다 늦게 시작한다. 브라우저는 `@font-face`를 읽었다고 바로 받지 않는다. 그 폰트를 쓰는 요소가 실제로 화면에 있고 그 글자를 그려야 한다는 걸 스타일 계산에서 확인한 뒤에야 요청한다. 쓰지도 않을 폰트를 받지 않으려는 설계인데, 그만큼 발견이 늦다. 아래 그림에서 다음을 누르면 그 순서가 진행된다.

실제로 쟀다. CSS 응답에 300ms, 폰트 응답에 200ms가 걸리게 하고 리소스 타이밍을 꺼냈다. `disc-preload.html`은 `<head>`에 폰트 preload를 하나 더 둔 것이다.

```html
<link rel="preload" href="/f/sub-one.woff2" as="font" type="font/woff2" crossorigin />
```

```text
disc-none
   /ext.css 13→317ms
   /f/sub-one.woff2 319→531ms
disc-preload
   /f/sub-one.woff2 12→217ms
   /ext.css 13→317ms
```

preload가 폰트 요청을 CSS와 나란히 세웠다. 폰트 도착이 531ms에서 217ms로 당겨졌다. 실제 사이트라면 CSS 앞에 HTML 응답 시간과 연결 시간이 더 붙으니 차이는 더 커진다.

여기서 `crossorigin`은 빼면 안 된다. 폰트는 같은 출처에서 받더라도 CORS 모드로 요청된다. preload에 `crossorigin`이 없으면 preload는 일반 모드로 받아서, 정작 폰트를 쓸 때 모드가 안 맞아 재사용하지 못한다. 빼고 돌려 봤다.

```text
disc-preload-nocors
   /f/sub-one.woff2 11→217ms
   /ext.css 12→316ms
   /f/sub-one.woff2 318→526ms
   console: warning: A preload for 'http://localhost:18651/f/sub-one.woff2?delay=200' is found, but is not used because the request credentials mode does not match. Consider taking a look at crossorigin attribute.
   warning: The resource http://localhost:18651/f/sub-one.woff2?delay=200 was preloaded using link preload but not used within a few seconds from the window's load event. Please make sure it has an appropriate `as` value and it is preloaded intentionally.
```

같은 파일을 두 번 받았고, 두 번째 요청은 preload가 없을 때와 같은 318ms에 나갔다. preload는 효과 없이 대역폭만 썼다. 콘솔에 이 경고가 보이면 `crossorigin`부터 확인한다.

preload는 첫 화면 본문에 쓰는 폰트 한두 개에만 건다. 굵기마다, 서브셋마다 걸면 HTML·CSS·LCP 이미지와 대역폭을 다툰다. 그리고 뒤에서 볼 것처럼 크롬은 preload된 폰트를 첫 그리기 전에 잠깐 기다리기도 해서 FCP가 늦어질 수 있다.

## 받는 동안 글자를 어떻게 보여 줄까

폰트가 아직 없을 때 브라우저가 할 수 있는 일은 둘이다. 글자를 투명하게 그려 두고 기다리거나(FOIT, Flash of Invisible Text), 시스템 대체 폰트로 먼저 보여 주고 나중에 바꿔 끼우는 것(FOUT, Flash of Unstyled Text)이다. `@font-face`의 `font-display`가 이걸 고른다.

`font-display`는 두 기간으로 정의된다. 블록 기간에는 글자를 투명하게 그리고 기다린다. 그 뒤 교체 기간에는 대체 폰트로 보여 주다가 폰트가 오면 바꾼다. 교체 기간도 지나면 폰트가 와도 바꾸지 않는다. 아래 그림은 `fallback`(블록 약 100ms, 교체 약 3초)에서 폰트가 1.5초에 도착하는 경우다.

값은 네 가지(`auto` 포함 다섯)다. 기간 길이는 명세가 권장하는 값이고, 크롬과 파이어폭스는 이를 따른다. `auto`는 브라우저 기본값인데 크롬과 파이어폭스는 `block`처럼 동작한다.

| 값 | 블록 기간 | 교체 기간 | 1.5초 걸린 폰트에서 본 것 |
|---|---|---|---|
| `block` | 약 3초 | 무한 | 글자가 1.56초 동안 안 보였다 |
| `swap` | 거의 0 | 무한 | 대체 폰트로 바로 보였다가 바뀌었다 |
| `fallback` | 약 100ms | 약 3초 | 0.13초에 대체 폰트, 1.5초에 교체 |
| `optional` | 약 100ms | 없음 | 대체 폰트로 끝까지 갔다 |

표의 오른쪽 열은 실제 측정에서 왔다. 폰트 응답이 1.5초 걸리게 하고, 각 값으로 같은 글(제목과 문단 셋, 그 아래 120px 회색 상자)을 열었다. LCP는 PerformanceObserver로, CLS는 `layout-shift` 항목을 더해서, 마지막 줄은 회색 상자의 위쪽 위치다.

```text
fd-block                  font 22→1537    FCP   36  LCP [1560ms P]  CLS 0.1281  box top 662
fd-swap                   font 31→1549    FCP   64  LCP [64ms P]  CLS 0.1281  box top 662
fd-fallback               font 20→1533    FCP   40  LCP [132ms P]  CLS 0.1281  box top 662
fd-optional               font 15→1521    FCP   44  LCP [44ms P]  CLS 0  box top 798
fd-swap-fast              font 35→51      FCP   56  LCP [56ms P]  CLS 0.1281  box top 662
```

몇 가지가 눈에 띈다. `block`은 FCP가 36ms로 찍혔지만 LCP는 1,560ms다. 투명한 글자는 LCP 후보가 되지 않기 때문이다. FCP만 보고 있으면 사용자가 1.5초 동안 빈 화면을 본 걸 놓친다.

`swap`과 `fallback`은 글자를 일찍 보여 주는 대신 CLS 0.1281을 냈다. 좋음 기준 0.1을 넘는다. 대체 폰트의 한글이 더 넓어서 문단 줄 수가 많았고, 웹 폰트로 바뀌자 회색 상자가 798px에서 662px로 136px 올라갔다.

`fd-swap-fast`는 폰트가 51ms 만에 왔는데도 CLS가 똑같이 생겼다. 대체 폰트로 이미 한 번 그린 뒤에 도착했기 때문이다. "폰트가 빠르면 swap이어도 괜찮다"는 생각은 틀렸다. 빠르든 느리든 먼저 그린 뒤에 오면 밀린다.

`optional`은 CLS가 0이지만 회색 상자가 798px, 즉 끝까지 대체 폰트였다. 폰트는 받아서 캐시에 넣어 두고, 다음 페이지부터 쓴다.

## 대체 폰트를 웹 폰트 크기에 맞추기

swap을 쓰면서 밀림을 없애는 방법이 있다. 대체 폰트를 웹 폰트와 같은 크기로 보이게 조정해 두면, 바꿔 끼워도 줄 수가 같아서 아무것도 움직이지 않는다. `@font-face`의 `size-adjust`가 글리프 크기를 비율로 키우거나 줄인다.

비율은 재서 구한다. 같은 한글 문장을 16px로 두 폰트에 그려 너비를 쟀다.

```text
{
  pv: 387.640625,
  sans: 447.125,
  wqy: 449.578125,
  noto: 444,
  liberation: 447.125
}
```

`pv`가 Pretendard, `wqy`가 이 실험 환경에 깔린 한글 폰트(WenQuanYi Zen Hei)다. `sans`, `noto`, `liberation`은 각각 `sans-serif`, 설치되지 않은 Noto Sans KR, 한글이 없는 Liberation Sans를 지정한 것인데, 한글은 결국 시스템 대체 폰트로 그려져서 너비가 비슷하게 나왔다. 387.64 ÷ 449.58 = 0.862이니 대체 폰트를 86.2%로 줄이면 된다. 실제 사용자의 대체 폰트는 운영체제마다 다르다. macOS·iOS는 Apple SD Gothic Neo, 윈도는 맑은 고딕, 안드로이드는 Noto Sans CJK 계열이라 각각 재서 `local()`로 따로 정의하는 게 정확하다.

```css
/* 대체 폰트를 웹 폰트 크기에 맞춘 가짜 폰트 */
@font-face {
  font-family: "PV Fallback";
  src: local("WenQuanYi Zen Hei");
  size-adjust: 86.2%;
}
body {
  font-family: "PV", "PV Fallback", sans-serif;
}
```

```text
fd-swap-adjusted          font 13→1521    FCP   32  LCP [32ms P]  CLS 0  box top 662
```

FCP는 swap과 같이 빠르고, CLS는 0이고, 회색 상자는 처음부터 662px에 있었다. 아래 그림에서 세 경우를 비교해 보자.

이 실험은 `line-height: 1.7`처럼 줄 높이를 숫자로 고정해서 너비만 맞추면 됐다. `line-height: normal`을 쓰면 줄 높이가 폰트의 ascent·descent 값으로 정해져서, 폰트가 바뀔 때 줄 높이도 바뀐다. 그때는 `ascent-override`, `descent-override`, `line-gap-override`로 대체 폰트의 세로 치수도 맞춘다. 위 fontTools 출력에서 Pretendard는 unitsPerEm 2048에 ascent 1950, descent 494라 각각 1em의 95.2%, 24.1%다. 크롬과 파이어폭스는 이 속성들을 지원하고, 사파리는 버전에 따라 지원 범위가 달라서 사파리에서는 너비만 맞고 높이는 안 맞을 수 있다.

Next.js의 `next/font`는 이 계산을 자동으로 해서 대체 폰트용 `@font-face`를 만들어 준다. 그런데 기준이 되는 대체 폰트가 Arial이나 Times New Roman 같은 라틴 폰트다. 한글에는 그대로 통하지 않는다는 걸 직접 확인했다. Liberation Sans(Arial과 같은 치수의 폰트)에 `size-adjust: 50%`를 주고 영문과 한글의 너비를 쟀다.

```text
Latin  Hello World     plain 82.4px  size-adjust 50% 41.2px
Hangul 안녕하세요 세계        plain 116.5px  size-adjust 50% 114.2px
```

영문은 정확히 절반이 됐지만 한글은 거의 그대로다. Liberation Sans에 한글 글리프가 없어서 한글은 그다음 시스템 폰트로 넘어가고, 그 폰트에는 `size-adjust`가 걸리지 않기 때문이다. 공백 하나만 줄었다. 한글 사이트에서 밀림을 막으려면 대체용 `@font-face`의 `local()`에 한글이 있는 폰트를 넣어야 한다.

## 첫 방문은 대체 폰트로 끝내는 optional

`optional`은 다른 방향의 답이다. 블록 기간 100ms 안에 폰트가 준비되면 쓰고, 아니면 그 페이지에서는 포기한다. 교체가 없으니 밀림도 없다. 대신 첫 방문자는 대체 폰트로 읽는다. 본문 가독성이 디자인보다 중요한 블로그나 문서 사이트에 어울린다.

그런데 폰트가 빨리 와도 못 쓰는 경우가 있었다.

```text
fd-optional-fast          font 130→151    FCP  168  LCP [168ms P]  CLS 0  box top 798
fd-optional-fast-preload  font 13→19      FCP   52  LCP [52ms P]  CLS 0  box top 662
fd-swap-preload           font 10→1513    FCP  132  LCP [132ms P]  CLS 0.1281  box top 662
```

지연 없이 폰트를 주는데도 `fd-optional-fast`는 대체 폰트로 끝났다(상자 798px). 폰트 요청이 스타일 계산 뒤에야 나가고, 받은 woff2를 해석할 시간도 필요해서 첫 그리기에 맞추지 못한 것이다. 같은 페이지에 preload만 더하자 폰트가 19ms에 도착해 웹 폰트로 그려졌다. `optional`은 preload와 짝을 지어야 제 몫을 한다.

세 번째 줄은 반대쪽 비용이다. 느린 폰트를 preload하면 `swap`인데도 FCP가 64ms에서 132ms로 늦어졌다. 크롬이 preload된 폰트를 첫 그리기 전에 잠깐 기다리기 때문이다. 이 실험에서는 약 100ms였다. 이 대기 동작은 브라우저와 버전에 따라 다르니, preload를 넣은 뒤에는 FCP가 늦어지지 않았는지 꼭 다시 잰다.

영문 두 문장만 있는 페이지는 조각 1개, 38KB만 받았다. [CSS 성능](/posts/css-performance) 글의 첫 세 문단(638자)은 13개, 340KB를 받았다. 그 글 전체를 넣으면 21개, 569KB다. 통짜 파일 2.06MB에 비하면 많이 줄었지만, 문단 세 개에 340KB는 적은 양이 아니다. 자주 쓰는 글자가 여러 조각에 흩어져 있어서 짧은 글도 조각을 여럿 건드린다. 요청 수가 13개로 늘어나는 것도 비용이다. HTTP/2 이상에서는 한 연결로 나란히 받으니 큰 문제는 아니지만, 조각이 도착하는 순서대로 글자가 바뀌어서 swap일 때 여러 번 깜빡일 수 있다.

정적 서브셋은 반대 방향이다. 내 콘텐츠에 실제로 나오는 글자만 남긴다. 위 `css-performance` 글에 나오는 한글을 세어 보니 495자였고, 이 블로그의 글 585개 전체에 나오는 한글은 1,228자였다. fontTools의 `pyftsubset`으로 그 글자와 ASCII만 남겼다.

```bash
# 가변 폰트에서 one.txt에 든 글자만 남긴다
pyftsubset PretendardVariable.woff2 --text-file=one.txt --flavor=woff2 --layout-features='*' --output-file=sub-one.woff2
```

```text
126888  sub-one.woff2          가변, 한 글의 495자
 52960  sub-one-regular.woff2  Regular 하나, 같은 495자
249180  sub-all.woff2          가변, 블로그 전체 1,228자
```

블로그 전체 글자를 다 담아도 가변 폰트 249KB다. 동적 서브셋으로 긴 글 하나를 읽을 때 받은 569KB보다 작다. 대신 새 글에 처음 나오는 글자가 생기면 다시 만들어야 하고, 댓글·검색어처럼 사용자가 입력하는 글자는 미리 알 수 없다. 서브셋에 없는 글자는 대체 폰트로 그려져서 한 단어 안에서 글꼴이 섞여 보인다. 그래서 콘텐츠가 정해진 사이트(랜딩 페이지, 빌드할 때 글이 정해지는 정적 블로그)는 정적 서브셋, 사용자 입력이 많은 서비스는 동적 서브셋이나 KS X 1001 서브셋(위의 267KB 파일)이 맞다. 둘을 섞는 방법도 있다. 제목용 굵은 폰트는 제목 글자만으로 서브셋하고, 본문은 동적 서브셋을 쓴다.

브라우저가 조각을 고르는 규칙을 직접 짜 보자. 글자와 각 조각의 `unicode-range` 문자열을 받아, 받아야 할 조각의 번호를 오름차순으로 돌려준다. 범위는 `U+0000-00FF`(구간), `U+0131`(한 글자), `U+4??`(물음표 자리는 0~F 아무거나) 세 모양이 쉼표로 섞여 있다.

CDN을 계속 쓴다면 두 출처에 미리 연결을 열어 둔다.

```html
<link rel="preconnect" href="https://fonts.googleapis.com" />
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin />
```

폰트를 다른 출처에 직접 올릴 때(이미지 CDN, S3 같은 저장소)는 CORS 헤더를 빼먹기 쉽다. 폰트는 CORS 모드라서 `Access-Control-Allow-Origin` 없이 받으면 막힌다. 다른 포트의 서버에서 헤더 없이 줘 봤다.

```text
error: Failed to load resource: net::ERR_FAILED
```

이미지나 CSS는 같은 조건에서 잘 받아지니, "폰트만 안 나온다"는 증상이면 이 헤더부터 본다.

## 폰트 문제를 현장에서 좁히는 법

증상별로 확인할 곳이 다르다.

글자가 한참 안 보인다면 `font-display`가 빠져서 `auto`(블록 최대 3초)로 동작하는지 본다. 직접 쓴 `@font-face`뿐 아니라 아이콘 폰트나 외부 CSS의 `@font-face`도 확인한다. 구글 폰트는 URL에 `&display=swap`을 붙여야 `swap`이 들어간다.

로딩 중에 글이 밀린다면 Performance 패널의 Layout Shifts 줄에서 밀린 시각이 폰트 응답이 끝난 시각과 겹치는지 본다. 겹치면 대체 폰트 크기 맞추기나 `optional`을 고려한다. 한글 사이트에서 `next/font`를 쓰는데도 밀린다면 대체 폰트 기준이 라틴 폰트라 한글에는 효과가 없는 경우다.

어떤 폰트로 그려졌는지는 Elements 패널에서 요소를 고른 뒤 Computed 탭 맨 아래의 Rendered Fonts에서 볼 수 있다. 웹 폰트 이름 옆에 "Network resource", 시스템 폰트면 "Local file"로 나온다. 한 문단에 둘이 섞여 있으면 서브셋에 빠진 글자가 있다는 뜻이다.

굵은 제목이 뭉개져 보인다면 그 굵기의 파일이 없어서 브라우저가 가짜 굵게(faux bold)를 만든 것이다. 정적 폰트를 400만 받고 700을 쓰면 생긴다. 굵기 파일을 추가하거나 가변 폰트를 쓰고, 가짜 굵게를 막으려면 `font-synthesis: none`을 준다.

Network 패널의 Font 필터에서 같은 파일이 두 번 보이면 preload의 `crossorigin`을, 파일이 수십 개면 동적 서브셋을, 한 파일이 MB 단위면 woff2 변환과 서브셋을 본다.

`local()`을 웹 폰트 `src`의 첫 번째에 두는 것도 조심한다. 사용자 컴퓨터에 같은 이름의 오래된 버전이 깔려 있으면 그걸 쓰게 돼서 글자 모양이나 굵기 범위가 달라진다. `local()`은 위에서처럼 대체 폰트를 정의할 때 쓰는 게 안전하다.

## 면접에서 나올 만한 질문

### FOIT와 FOUT의 차이는? font-display는 어떻게 고르나?

FOIT는 폰트가 올 때까지 글자를 투명하게 숨기는 것이고, FOUT는 대체 폰트로 먼저 보여 주고 나중에 바꾸는 것이다. font-display는 블록 기간과 교체 기간의 길이로 둘 사이를 고른다. 본문은 빨리 읽히는 게 중요하니 swap이나 optional을 쓰고, 아이콘 폰트처럼 대체 글자가 엉뚱한 의미가 되는 경우만 block을 쓴다. 기본값 auto는 크롬·파이어폭스에서 최대 3초 블록이라 명시하는 게 좋다.

### swap을 쓰면 왜 CLS가 생기고, 어떻게 막나?

대체 폰트와 웹 폰트의 글자 폭이 다르면 바꿔 끼울 때 줄바꿈이 달라져 아래 내용이 밀린다. 실험에서 폰트가 51ms 만에 와도 이미 대체 폰트로 그린 뒤라 CLS 0.1281이 났다. 대체 폰트에 size-adjust(필요하면 ascent·descent override)를 줘서 웹 폰트와 같은 크기로 맞추면 CLS가 0이 됐다. 아니면 optional로 첫 방문에는 교체하지 않는다.

### font-display: optional의 장단점은?

블록 기간 약 100ms 안에 준비된 경우에만 웹 폰트를 쓰고 교체는 하지 않아서, FOIT도 밀림도 없다. 대신 첫 방문자는 대체 폰트로 보게 되고, 폰트는 캐시에 넣었다가 다음 페이지부터 쓴다. preload 없이 쓰면 폰트가 늦게 발견돼서 빨리 와도 놓치는 경우가 많았고, preload를 함께 걸자 첫 방문에도 웹 폰트로 그려졌다.

### 폰트 preload에 crossorigin을 꼭 붙이는 이유는?

폰트는 같은 출처에서도 CORS 모드로 요청되기 때문이다. crossorigin이 없는 preload는 다른 모드로 받아서 실제 폰트 요청이 그걸 재사용하지 못하고 한 번 더 받는다. 크롬은 "credentials mode does not match" 경고를 남긴다. 또 preload는 첫 화면 본문 폰트 한두 개에만 걸어야 다른 중요한 리소스와 대역폭을 다투지 않는다.

### 한글 웹 폰트를 가볍게 하는 방법은?

woff2로 바꾸고, 쓰는 굵기만 받고, 글자 수를 줄인다. 글자 수 줄이기는 콘텐츠의 글자만 남기는 정적 서브셋과, 폰트를 unicode-range 조각으로 나눠 필요한 조각만 받는 동적 서브셋이 있다. 정적 서브셋은 가장 작지만 새 글자나 사용자 입력을 못 담고, 동적 서브셋은 무엇이든 담지만 짧은 글에도 여러 조각과 수백 KB를 받을 수 있다. 실험에서 블로그 전체 1,228자 서브셋이 249KB, 동적 서브셋으로 긴 글 하나가 569KB였다.

### 가변 폰트는 언제 이득인가?

굵기 축을 파일 하나에 담아서 여러 굵기를 쓸 때 이득이다. Pretendard에서 정적 굵기 셋이 2.34MB, 가변 폰트 하나가 2.06MB였다. 굵기를 하나만 쓰면 정적 파일(766KB)이 훨씬 작으니 쓰는 굵기 수를 먼저 센다. 가변 폰트는 중간 굵기나 굵기 애니메이션도 쓸 수 있다.

### 구글 폰트 CDN과 직접 호스팅 중 무엇이 빠른가?

대개 직접 호스팅이다. CDN은 CSS용 출처와 파일용 출처에 새 연결을 열어야 하고 그 CSS도 렌더링을 막는다. 예전의 장점이던 사이트 간 캐시 공유는 크롬 86 이후 캐시 분할로 사라졌다. CDN을 쓴다면 두 출처에 preconnect를 걸고 display=swap을 붙인다. 직접 올릴 때 다른 출처라면 Access-Control-Allow-Origin 헤더를 빠뜨리지 않는다.
