## 실제로 도는 코드가 어느 버전인지 아무도 몰랐다

토스페이먼츠는 2020년 8월 기존 PG 사업을 인수하며 출범했다. 하태호의 [1편 "20년 레거시를 넘어 미래를 준비하는 시스템 만들기"(2025년 10월)](https://toss.tech/article/payments-legacy-1)는 인수 시점의 상태를 숨기지 않고 적었다.

소스코드는 개인 PC에만 있거나 개발 서버에만 백업돼 있었다. SVN은 협업 도구가 아니라 단순 백업 용도였고, 실제 서비스 중인 코드와 저장소의 코드가 달랐다. 지금 돌고 있는 코드가 정확히 어떤 버전인지 알 수 없었다는 뜻이다.

인프라도 비슷했다. 제조사 지원이 끝난 노후 서버가 수백 대였고, 보안 패치가 불가능한 지원 종료 OS가 돌았다. CPU가 타서 서버를 폐기한 일까지 있었다고 적었다. 사내 DNS가 없어 도메인을 hosts 파일을 손으로 고쳐 등록했고, Ansible 같은 자동화 도구 없이 수백 대 서버를 손으로 관리했다. 서버마다 라우팅 정책이 달라 새 서비스를 붙이는 데 며칠씩 걸렸다.

애플리케이션은 더 오래됐다. 1편이 정리한 레거시 현황은 이렇다. 화면은 JSP와 jQuery, 서버는 2004년 버전 Struts 1.2에 부분 적용된 iBATIS, DB 커넥션 풀을 쓰지 않고 문자열로 SQL을 조립했다. 데이터베이스는 단일 Oracle DB 하나였고, 배치는 수천 줄짜리 SQL 중심이었다. CI/CD는 없었고 보안 점검은 손으로 했다.

이런 시스템에 새 기능을 얹을 수는 있다. 문제는 고칠 때마다 무엇이 깨질지 모른다는 것이다. 1편의 표현을 빌리면 "이런 상황에서는 안정적인 서비스를 운영하는 것이 불가능해 보였다".

## 기능보다 바닥부터 다시 깐 순서

토스페이먼츠가 고른 방식은 두 갈래(Two Track)였다. 첫째 갈래는 AWS 기반 금융 클라우드를 들여 새 제품과 기능을 처음부터 모던 스택으로 만드는 것이다. 레거시 인프라를 느리고 위험하게 바꾸는 일을 줄이려는 목적이다. 둘째 갈래는 서비스를 멈추지 않고 기존 시스템을 단계적으로 고치는 것이다. 여기에는 AWS와 IDC(자체 데이터센터)의 차이를 가리는 플랫폼을 만드는 일이 들어간다.

1편은 지난 5년의 개선을 9단계로 나눴다. 순서를 보면 이 사례에서 가장 배울 만한 점이 보인다. 애플리케이션 대개편은 마지막 9단계다.

1단계는 소스코드를 찾는 일이었다. 글쓴이는 이를 "디지털 고고학"이라고 불렀다. 서버에 배포돼 실제로 동작하는 모든 `.class` 파일을 디스어셈블하고, 개인 PC·개발 서버·SVN에 흩어진 소스와 하나씩 비교해 진짜 최신 코드를 찾아냈다. 그렇게 찾은 코드를 GitHub에 올려 커밋 해시 기준으로 배포하는 체계를 만들었다.

2단계는 빌드 표준화다. Java 시스템인데도 개발자 PC마다, 서버마다 빌드 결과가 달랐다. 소스를 통째로 압축해 복사해도 같은 결과물이 나오지 않았다고 한다. Gradle 기반 통합 빌드, Docker 기반 빌드 환경, 의존성 버전 고정으로 어디서든 같은 결과가 나오게 했다. 1편은 이 단계의 결과로 "개발망에서 테스트한 것과 동일한 형상의 소프트웨어를 운영망에 배포 가능"을 꼽는다.

3단계부터 MSA 전환과 Kubernetes 도입이다. 1편은 토스페이먼츠 안의 MSA 서비스가 150개가 넘는다고 적었다. 4단계 고가용성 인프라에서는 같은 형상의 Kubernetes 클러스터 4개를 AWS의 가용 영역 4곳과 IDC 안의 서로 다른 장애 격리 영역에 나눠 두었다. 5단계는 공통 라이브러리를 최신으로 유지하려고, 문제가 되는 코드 패턴이나 라이브러리를 찾으면 자동으로 코드를 고쳐 Pull Request를 만드는 시스템이다.

6단계에 이르러서야 배포 안전장치가 나온다. 애플리케이션뿐 아니라 가상머신 클러스터와 Kubernetes 클러스터 단위로도 트래픽을 1% 단위로 조절해 보낼 수 있다. 클러스터에 작업이 필요하면 그 클러스터의 트래픽을 모두 빼고, 작업이 끝나면 1%씩 다시 넣는다.

카나리 배포는 "새 버전과 옛 버전이 무엇이 다른지 안다"는 전제 위에서만 의미가 있다. 운영 코드가 어느 버전인지 모르고, 빌드할 때마다 결과물이 다르다면 1%만 보낸 새 버전에서 문제가 생겨도 원인이 코드인지 빌드 환경인지 가를 수 없다. 토스페이먼츠가 애플리케이션을 다시 쓰기 전에 소스와 빌드부터 정리한 것은 이 설계로 보면 자연스러운 순서였을 것이다. 비율로 나눠 보내는 일반 원리는 [카나리 릴리스](/posts/canary-release) 글에 있다.

6단계에는 결제 도메인에만 있는 서버 이야기도 하나 나온다. PG와 카드사는 TCP로 "전문"을 주고받는다. 1편의 설명으로는 주고받을 데이터의 포맷을 미리 정해 두고 고정된 길이로 인코딩해 보내는 방식이다. 요청마다 연결을 새로 맺는 동기 방식과, 소수의 TCP 연결(세션)을 유지하며 비동기로 여러 요청을 섞어 보내는(multiplexing) 방식이 있다. 구현이 쉬워 동기 방식을 많이 쓰지만, 토스페이먼츠는 비동기 멀티플렉싱 어댑팅 서버를 따로 만들었다. 1편은 그 결과 결제가 몰리는 시간대에 일부 결제의 응답이 과하게 늦어지거나 실패하던 현상이 사라졌다고 썼다. 연결을 매번 맺는 비용과 연결 수 한도가 몰림 시간에 병목이 된다는 점은 HTTP의 커넥션 재사용과 같은 이야기다.

7단계와 8단계는 조회와 보안이다. 7단계에서는 가맹점의 장기간 거래 조회를 다뤘다. 몇 년 지난 결제에도 취소가 들어오기 때문에 과거 통계를 배치로 미리 만들어 두는 흔한 방법을 쓰기 어렵다고 1편은 설명한다. 수십억 건이 MSA의 여러 DB에 흩어져 있고, 과거 데이터가 바뀔 수 있으며, 거래 완료 뒤 수십 초 안에 조회돼야 한다는 조건이다. 결과로 약 1분 걸리던 쿼리가 1초 안에 응답하고, 최근 3개월만 조회되던 제약이 최대 보관 기간인 5년으로 늘었다고 썼다. 8단계에서는 모든 엔드포인트에 TLS 1.3을 지원하고, 민감한 API는 애플리케이션에서 전송 구간을 한 번 더 암호화한다고 밝혔다.

이 순서에서 하나 더 읽을 수 있다. 4단계까지는 개발자 대부분이 체감하지 못하는 바닥 공사다. 그 바닥 위에서 6단계의 1% 단위 조절이 생기고, 9단계의 결제창과 원장 전환은 모두 그 조절 장치에 기댄다. 다시 쓰기의 성패가 새 코드의 품질보다 "조금씩 보내고 바로 되돌리는 능력"에 더 크게 달려 있었다는 뜻이다.

## 2,500줄짜리 분기문과 전역 변수가 된 DTO

9단계 가운데 실시간 결제의 얼굴인 결제창을 다시 쓴 이야기는 황성우의 [2편 "가맹점은 변함없이, 결제창 시스템 전면 재작성하기"(2025년 10월)](https://toss.tech/article/payments-legacy-2)에 있다.

레거시 결제창은 하나의 Java 메서드에서 모든 분기를 처리했다. 결제수단에 따라 나누는 코드만 2,500줄이었다. 카드냐 계좌이체냐 가상계좌냐로 나누고, 그 안에서 다시 카드사마다 나누는 식이다. 공통 기능은 컴포넌트로 묶여 있지 않고 결제 방식마다 같은 코드가 다시 쓰여 있었다. 프레임워크는 20년이 넘은 Struts와 WebLogic이었다.

화면과 서버 로직도 붙어 있었다. 2편은 JSP 파일 안에서 직접 JDBC 커넥션을 얻어 쿼리를 실행하는 코드가 있었다고 썼다. 그래서 기능 하나를 추가하려면 JavaScript, JSP, Java 클래스를 모두 고쳐야 했다.

가장 까다로운 건 파라미터였다. 가맹점이 결제창을 부르는 방식은 두 가지다. 20년 전부터 있던 수백 개의 평평한(flat) 파라미터를 HTML Form으로 보내는 레거시 방식, 그리고 법인 설립 초기에 만든 JSON 기반 OpenAPI 방식이다. 레거시 파라미터 중에는 같은 값이라도 쓰는 맥락에 따라 다르게 동작하는 것이 있었다.

이 파라미터는 모두 거대한 결제요청 DTO 하나에 담겨 시스템 곳곳에서 get과 set을 당했다. 2편은 이를 "전역변수에 가깝게 취급되고 있었다"고 적었다. 어떤 값이 지금 무엇인지 알려면 값이 바뀌는 모든 지점을 쫓아가 "어느 클래스가 먼저 실행됐으니 여기서는 이 값일 것"이라고 추측해야 했다.

OpenAPI 방식도 사정이 나았던 건 아니다. 2편에 따르면 OpenAPI 파라미터는 사실 레거시 파라미터를 감싼 형태였다. 스트랭글러 패턴처럼 레거시 앞에 선 일종의 프록시로, 변환 어댑터를 거쳐 최소 수십 개의 레거시 파라미터로 바뀐 다음 결제 요청이 됐다. OpenAPI에 기능을 하나 넣으려면 대응하는 레거시 파라미터와 어댑터 로직을 함께 추가해야 했고, 시간이 지나며 어댑터에 비즈니스 로직이 녹아들었다.

여기서 짚어 둘 점이 있다. 스트랭글러 피그 패턴(새 시스템을 옛 시스템 앞에 세우고 기능을 하나씩 옮기는 방법, [마이크로서비스 글](/posts/microservices)의 "조금씩 옮기기" 절)은 앞에 세운 층이 옮겨 가는 길목일 때만 효과가 있다. 앞에 선 층이 뒤의 옛 구조로 번역만 하고 끝나면, 새 인터페이스는 옛 구조의 제약을 그대로 물려받는다. 토스페이먼츠의 첫 OpenAPI 어댑터가 그렇게 굳었다.

## 연동 방식마다 변환기 하나, 안쪽은 Feature로

새 결제창은 바깥에서 들어오는 파라미터와 안쪽 결제 로직 사이에 경계를 그었다. 2편은 파라미터를 둘로 나눴다. 가맹점 식별자·주문번호·금액처럼 값 그대로 쓰는 값 파라미터, 즉시할인 사용 여부·할부 개월 수처럼 결제 세부 기능을 켜고 끄는 기능 파라미터다. 이 기준으로 `SessionCreationRequest`라는 새 요청 객체를 만들고, 기능 파라미터는 `FeatureCashReceipt`, `FeatureCardDiscount`, `FeatureCardInstallment` 같은 Feature 객체로 추상화했다.

연동 방식마다 독립된 변환기를 두었다. `OpenAPIConverter`는 OpenAPI 스펙을 받고, `LegacyConverter`는 레거시 파라미터의 복잡한 검증, 일관되지 않은 파싱 규칙, 오래된 한글 인코딩 처리, 비즈니스 로직 곳곳에 퍼져 있던 기본값 처리를 맡는다. 두 변환기 모두 같은 `SessionCreationRequest`를 만든다. 핵심 결제 로직은 가맹점 파라미터를 직접 보지 않고 Feature만 받는다.

도메인 주도 설계에서는 이런 층을 부패 방지 계층(anti-corruption layer)이라고 부른다. 바깥 모델의 사정이 안쪽 모델로 새어 들어오지 않게 번역을 한곳에 모으는 층이다. 2편은 이 이름을 쓰지 않았지만, `LegacyConverter`가 하는 일이 정확히 그것이다. 앞 절의 첫 OpenAPI 어댑터와는 방향이 반대다. 옛 어댑터는 새 인터페이스를 옛 모델로 번역했고, 새 변환기는 옛 인터페이스를 새 모델로 번역한다.

## 화면은 배달만 한다: ENTRY, PREPARE, CONFIRM

화면과 서버를 떼어 내는 일도 해야 했다. 2편은 웹 인증을 거쳐 결제를 일으키는 여러 서비스의 통신 패턴을 관찰해 공통 3단계를 정의했다. 첫 화면을 그리는 데이터를 받는 ENTRY, 사용자가 고른 결제수단에 필요한 데이터를 받는 PREPARE, 인증을 마치고 결제 성공 페이지로 가는 CONFIRM이다.

남은 문제는 카드사·간편결제사·해외 간편결제(PayPal 등)와 브라우저에서 데이터를 주고받는 방법이었다. 2편은 이때 쓸 수 있는 표준화된 방법이 Redirect와 Form POST뿐이라고 썼다. 어디로, 어떤 방식으로 보낼지는 비즈니스 로직인데, 서버가 데이터만 JSON으로 내려 주면 그 판단이 프런트엔드로 스며든다.

그래서 서버가 도착지, 전송 방식, 전송할 데이터 세 가지를 함께 내려 주는 Bridge 인터페이스를 만들었다. 프런트엔드는 받은 데이터를 해석하지 않고, 정해진 도착지에 정해진 방식으로 그대로 전달(relay)만 한다. 아래 그림에서 다음을 누르면 사용자가 카드를 골라 결제를 마치기까지 이 흐름이 차례로 그려진다.

ENTRY 단계의 사전 요청(preflight) 이야기는 숫자까지 적혀 있다. 2편은 많은 환경에서 사전 요청이 30~50ms 안팎이고 보통 본 요청이 200~300ms라서, 비율로 보면 사전 요청이 꽤 큰 몫이라고 봤다. 모바일 결제가 많아 불안정한 무선망에서 왕복 두 번이 사용자 경험에 좋지 않다고 판단했다. 그래서 반응성이 중요한 ENTRY API만 Simple Request로 보냈다. Simple Request가 되는 조건(메서드, 헤더, Content-Type 제한)은 [CORS](/posts/cors) 글에 있다. 이 조건을 맞추려면 커스텀 헤더나 `application/json` 본문을 포기해야 하므로, 2편이 모든 API가 아니라 ENTRY 하나에만 적용한 것은 그 제약 때문이었을 것이다.

## 가맹점별, 기능별 카나리와 자동 원복

새 결제창을 다 만든 뒤 한 번에 100% 넘기면, 새 시스템의 문제가 전체 결제로 번진다. 2편은 결제 시스템의 핵심을 "서비스 연속성"이라고 부르며 이 방식을 버렸다. 대신 가맹점별, 결제 세부 기능별로 새 시스템 적용 여부를 정하고, 결제 요청 단위로 새 시스템이 처리할지를 정하는 카나리를 만들었다.

판정은 앞의 3단계 퍼널로 한다. PREPARE 대비 CONFIRM 비율이 정상 범위를 벗어나면 사용자가 결제를 끝내지 못하고 있다는 뜻이다. 이상 징후가 보이면 그 트래픽을 자동으로 레거시로 되돌린다. 2편에는 실제 그래프도 실렸다. 어느 시점에 CONFIRM 수치가 급감했고, 문제가 생긴 결제수단은 새 시스템 투입이 거의 바로 멈추고 레거시로 원복됐다.

이 판정에서 좋은 점은 지표가 사업의 결과에 붙어 있다는 것이다. 5xx 비율이나 지연 시간은 서버가 정상인데 사용자가 결제를 못 끝내는 경우(카드사로 가는 Form 값이 틀렸다든가)를 놓칠 수 있다. "PREPARE까지 온 사람 중 CONFIRM에 닿은 사람"은 그런 실패를 직접 센다. 정상 범위가 몇 %인지, 몇 분 동안 보는지는 2편에 없다.

판정 규칙은 짧아서 직접 짜 볼 수 있다. 아래 함수는 결제수단별 PREPARE·CONFIRM 건수를 받아 되돌려야 할 수단을 고른다. 기준 비율, 허용 하락 폭, 최소 표본 수는 연습용 값이고 토스페이먼츠의 실제 기준이 아니다. 표본이 너무 적은 수단을 건너뛰는 이유는 [카나리 릴리스](/posts/canary-release) 글의 "작은 비율은 증거가 적다" 절에 있다.

  // baseline: { CARD: 0.92, ... } 평소 CONFIRM / PREPARE 비율

  // 3. 들어온 순서대로 method 이름 배열을 돌려준다

  for (const s of stats) {

    const base = baseline[s.method];
    if (base === undefined) continue;

    if (ratio < base - maxDrop) out.push(s.method);
  }

세 번째 테스트에서 계좌이체는 30건 중 3건만 CONFIRM에 닿아 비율이 10%다. 그래도 원복 대상에 넣지 않는다. 30건으로는 우연인지 고장인지 가를 수 없기 때문이다. 실제 운영에서는 이렇게 건너뛴 수단을 따로 알려 사람이 보게 해야 한다.

결과도 숫자로 남았다. 새 결제창은 설계 단계부터 다계층 캐시를 넣었고, 2편 그래프에서는 평소의 20배가 넘는 피크 트래픽이 들어오는 동안 캐시 적중률이 올라 오히려 평균 응답 속도가 빨라졌다. 1편은 선착순 결제 이벤트로 트래픽이 순간 수십 배 들어오는 경우가 있고, 이때 캐시가 한꺼번에 만료되거나 한 계층이 고장 나면 저장소가 버티지 못한다는 이유를 댔다. 캐시가 동시에 만료되는 문제는 [캐시 무효화](/posts/cache-invalidation) 글에서 다룬다. 레거시에서 코드 이해조차 어려웠던 즉시할인 기능은 새 시스템에서 서버 개발자 2명, FE 개발자 1명이 1달 만에 어드민까지 다시 만들었다고 한다.

## 원장은 새 DB로, 옛 원장에 먼저 쓰고 뒤따라 쓴다

결제창이 입구라면 원장은 금고 장부다. 박순현·양권성의 [5편 "레거시 결제 원장을 확장 가능한 시스템으로"(2025년 12월)](https://toss.tech/article/payments-legacy-5)는 결제·취소·환불 내역이 기록되는 결제 원장을 옮긴 이야기다. 정산과 회계의 기초 데이터라 가장 복잡하면서도 핵심이었다고 썼다.

레거시 원장의 문제는 셋이었다. 첫째, 결제수단마다 테이블 구조가 달랐다. 카드는 전체 취소와 부분 취소를 다른 테이블에 저장했고, 계좌이체는 한 테이블에 모든 취소를 기록했다. `REFUND`라는 테이블은 이름과 달리 계좌이체 취소만 저장했다. 둘째, 결제·정산·취소·회계가 같은 원장 테이블을 공유했고 같은 컬럼이 도메인마다 다른 뜻으로 쓰였다. 컬럼 하나를 고칠 때마다 여러 팀이 영향도를 분석해야 했다. 셋째, 결제와 결제수단이 1:1로 묶여 카드와 계좌이체를 섞어 내거나 여러 사람이 나눠 내는 구조를 만들 수 없었다.

토스페이먼츠는 기존 Oracle DB에 테이블을 더하지 않고 MySQL에 새 원장을 따로 세웠다. 5편이 든 이유는 세 가지다. Oracle DB에는 여러 팀의 데이터가 섞여 있어 다른 팀의 배포나 작업이 결제 장애로 이어질 위험이 있었다. 주요 서비스가 MySQL과 JPA 중심이라 Oracle과 MyBatis XML 쿼리보다 스택을 하나로 모을 수 있었다. 오픈소스라 실험 환경을 빨리 꾸릴 수 있었다. 첫째 이유는 [마이크로서비스 글](/posts/microservices)의 "데이터베이스도 서비스마다" 절이 말하는 서비스별 데이터베이스가 실제로 어떤 장애를 막으려는 것인지 보여 준다.

새 원장의 설계는 세 갈래다. 모든 결제 승인 내역은 `approve` 공통 테이블에 저장하고 결제수단별 추가 정보는 따로 둔다. 취소할 때 행을 UPDATE하던 방식을 INSERT만 하는(INSERT-only) 원칙으로 바꿨다. 5편은 이로써 데이터 불변성을 지키고, 데드락을 막고, 과거 이력을 추적하기 쉬워졌다고 썼다. 다른 도메인은 원장 DB를 직접 조회하지 않고, 결제가 생기면 발행되는 Kafka 이벤트를 구독한다. 마지막으로 결제(수단이 정해지지 않은 상태)와 승인(실제 수단이 정해진 상태)을 나눠, 결제 하나에 여러 승인이 붙을 수 있게 했다.

INSERT-only와 결제·승인 분리가 함께 어떤 모양이 되는지 작은 예로 그려 본다. 테이블 이름 `approve`와 두 원칙은 5편에서 왔고, 행의 구성과 금액은 이해를 돕기 위해 내가 만든 예시다. 5편은 실제 컬럼 구성을 공개하지 않았다.

이 구조에서 중요한 판단은 세 번째 단계다. 새 원장 적재를 위해 결제를 느리게 만들지 않는다. 대신 "버려도 나중에 메워진다"는 보장을 배치로 만든다. 실시간 경로는 가볍게, 정확성은 배치가 책임지는 분업이다. 여러 저장소에 함께 쓰는 일이 왜 언제든 어긋나는지는 [트랜잭셔널 아웃박스](/posts/transactional-outbox) 글의 첫 절에 있다. 5편은 이 전제를 처음부터 받아들였다고 썼다. 두 저장소의 데이터는 언제든 틀어질 수 있다고 가정했다는 것이다.

실시간 적재가 안정된 뒤 과거 데이터를 옮겼다. 5편은 이를 수억 건 단위의 INSERT가 동시에 일어나는 고부하 작업이라고 불렀다. 라이브 서버와 자원을 나누지 않으려고 마이그레이션 서버를 따로 배포했고, 새 RW DB가 있는 AWS 가용 영역 하나에 마이그레이션 서버도 함께 두어 네트워크 지연을 줄였다. 단건 저장을 대량 삽입(bulk insert)이 되도록 저장 인터페이스를 다시 만들었고, 반복 조회하는 데이터는 서버 메모리에 캐시했다. IDC의 옛 DB와 AWS의 새 DB 사이 트래픽을 지켜보며 다른 서비스에 영향을 주지 않게 속도를 조절했다.

## 장애 하루가 드러낸 네 가지 어긋남

5편에서 가장 쓸모 있는 부분은 운영 중 장애 이야기다. 어느 날 관제센터에서 결제 서버 응답이 늦고 DB 부하가 비정상적으로 높다는 알림이 왔다. 대시보드에서는 MySQL의 대기 세션 수가 급증하고 있었다.

상위 쿼리 로그를 보니 특정 SELECT 하나가 계속 높은 CPU와 I/O를 쓰고 있었고, 전날 배포한 기능에서 추가된 쿼리였다. 바로 이전 버전으로 롤백했다. 5편에 따르면 토스페이먼츠는 최근 5개 배포 이미지를 늘 보관해서 다시 빌드하지 않고 즉시 재배포할 수 있었고, 롤백 뒤 DB 부하는 빠르게 정상으로 돌아왔다. 원인은 옵티마이저였다. 데이터가 쌓이면서 옵티마이저가 인덱스 대신 테이블 전체를 스캔하는 실행 계획을 골랐다. 이후 쿼리에 힌트를 넣어 의도한 인덱스를 쓰게 했다.

이 장애가 연쇄로 드러낸 문제가 넷이다. 5편의 순서대로 보면 이렇다.

첫째, 두 원장이 어긋났다. DB 부하 동안 새 원장에 일부 데이터가 들어가지 않았다. 앞 절의 5분 주기 보정 배치가 옛 원장을 기준으로 이 불일치를 해소했다. 설계 때 가정한 일이 실제로 일어났고, 가정에 맞춰 만든 장치가 일했다.

둘째, 원천사(카드사, 은행)와 어긋났다. 결제 서버가 카드사에 승인을 요청했는데 네트워크 타임아웃으로 실패하면, 카드사에서는 결제가 완료됐는데 토스페이먼츠에서는 실패로 남을 수 있다. 결제 서버는 타임아웃된 거래를 따로 저장해 두고 원천사에 취소를 보내 상태를 맞추는 망취소(network cancellation)를 돌리고 있었다. 타임아웃은 실패가 아니라 "모름"이라는 원리는 [결제 신뢰성](/posts/sd-payment-reliability) 글의 첫 절에 있다.

셋째, 가맹점이 받은 응답과 실제 결과가 어긋났다. 원인은 MSA 안에서 서버마다 다른 타임아웃이었다. 5편의 예로는, 앞단 PX 서버와 승인 서버의 타임아웃이 다르면 승인 서버가 결제를 정상 완료해도 앞단은 이미 타임아웃 실패를 돌려줄 수 있다. 승인 서버의 최대 처리 시간을 계산해 모든 상위 서버의 타임아웃을 그에 맞춰 다시 정했다. 호출 체인에서 바깥 타임아웃이 안쪽보다 짧으면 생기는 일은 [타임아웃](/posts/timeouts) 글에서 다룬다.

넷째, 결제 이벤트가 빠지고 겹쳤다. 이벤트 발행은 아웃박스 패턴으로 만들었는데도 누락이 생겼다. 5편은 이유를 솔직하게 적었다. 가맹점 결제 가용성을 더 중시하고, 외부 원천사 연동에는 롤백이 안 되는 부분이 있어서, 아웃박스 저장이 실패했다고 결제 전체를 실패 처리하지 않고 따로 처리하고 있었다. 아웃박스에 저장된 이벤트는 재발송 배치가 누락 없이 보냈다. 빠진 건 아웃박스에 들어가지도 못한 거래였다.

이 거래들은 로그로 되살렸다. 결제 서버는 거래 로그를 Elasticsearch에 쌓고, 로깅 시스템이 고장 날 때를 대비해 대체 어펜더(fallback appender)로 파드의 로컬 디스크에도 남겼다가 복구 뒤 재처리한다. 덕분에 장애 시간대 거래를 찾아 이벤트를 다시 발행했다. 그런데 이번에는 다시 발행한 이벤트가 겹쳐, 이벤트를 쌓는 서비스에서 승인이나 취소가 두 번 보였다. 이벤트 헤더에 멱등 키를 실어 받는 쪽이 같은 건을 알아보게 해서 막았다. 받는 쪽 멱등 처리의 일반 원리는 [멱등 키](/posts/idempotency-key) 글에 있다.

넷째 문제는 교과서와 현실이 갈리는 지점이다. 아웃박스 패턴의 보장은 "비즈니스 데이터와 아웃박스 행이 같은 트랜잭션에 들어간다"는 데서 나온다. 결제처럼 외부 시스템이 이미 돈을 움직인 뒤라 되돌릴 수 없는 경우, 아웃박스 저장 실패를 이유로 결제를 실패시키면 오히려 원천사와 어긋난다. 토스페이먼츠는 가용성을 고르고, 그 대가로 생기는 누락을 로그 기반 복구로 메웠다. 그리고 복구가 중복을 만든다는 것을 겪은 뒤 멱등 키를 더했다. 누락을 메우는 장치를 만들 때는 그 장치가 중복을 만든다는 것까지 함께 설계해야 한다는 교훈이다.

## 토스뱅크 코어뱅킹 전환과 나란히 놓으면

같은 토스 계열사인 토스뱅크도 비슷한 일을 먼저 공개했다. 장세경·조서희의 [은행 최초 코어뱅킹 MSA 전환기(2023년 8월)](https://toss.tech/article/slash23-corebanking)와 같은 제목의 [SLASH 23 발표](https://toss.im/slash-23/session-detail/A1-8)는, 모놀리식 코어뱅킹(계정계)에서 트래픽이 가장 많은 "지금 이자 받기"를 떼어 낸 과정이다.

검증과 전환의 모양이 닮았다. 토스뱅크는 앱에서 이자 조회가 일어나면 기존 코어뱅킹 서버와 새 이자 지급 마이크로 서버를 동시에 불러 두 값을 비교하고, 다르면 내부 모니터링 채널로 알림을 받았다. 발표 자료에 따르면 이 실시간 검증을 정기 이자 지급일까지 1개월 동안 돌렸고, 스테이징 환경에서 매일 배치로 대량 비교도 했다. 전환은 수신개발팀, 내부 팀원, 일부 고객 순으로 열고, 트래픽을 1%, 10%, 50%, 90%, 100%로 옮겼다. 발표 자료가 밝힌 결과는 평균 소요 시간 250ms에서 7ms, 최대 소요 시간 1.72초에서 11ms다.

두 사례를 겹쳐 보면 공통된 원칙이 보인다. 옛 시스템을 정답지로 두고 새 시스템을 그 옆에서 돌려 비교한다. 트래픽은 작게 시작해 늘리고, 이상하면 옛 쪽으로 돌린다. 다른 점은 비교 대상이다. 토스뱅크의 이자 조회는 같은 입력에 같은 출력이 나와야 하는 계산이라 응답 값을 그대로 비교했다. 토스페이먼츠의 결제창은 외부 카드사와 사용자를 거치는 흐름이라 두 시스템을 동시에 부를 수 없고, 대신 퍼널 비율로 판정했다. 원장은 저장된 결과를 배치로 맞춰 봤다. 무엇을 비교할 수 있느냐가 검증 방식을 정한다.

## 공개된 이야기에서 빠진 것

이 연재는 토스페이먼츠가 채용과 기술 홍보를 겸해 고른 이야기다. 실패담도 있지만(5편의 장애), 회사가 공개하기로 한 범위 안의 실패다. 결제창 전환에 걸린 기간과 가맹점 수 기준 진척, 카나리 판정의 정상 범위와 관찰 시간, 자동 원복이 몇 번 일어났는지는 나오지 않는다. 원장 이전에서 새 원장이 언제 메인 지위를 얻었는지, 옛 Oracle 원장이 지금도 남아 있는지도 글에 없다. 5편은 "신규 원장이 메인 원장의 지위를 얻기 전까지"라고만 쓴다.

숫자의 기준도 조심해야 한다. "평소의 20배가 넘는 피크"와 "응답 속도 개선"은 2편 그래프의 설명이고 절대값은 없다. 1편의 "1분 걸리던 쿼리가 1초 이내"는 대규모 조회 플랫폼 이야기인데, 어떤 저장소를 썼는지는 1편에 나오지 않는다. 연재 가운데 정산(6편), 설정 체계(8편), 하이브리드 클라우드(9편), 보안(10편)도 이 글 범위 밖이다.

토스뱅크 쪽 숫자도 기준을 확인해야 한다. 블로그 글의 성과 목록에 있는 "성능 170배 개선"은 발표 자료에서 최대 소요 시간(1.72초에서 11ms) 기준이고, 평균 소요 시간(250ms에서 7ms)으로는 약 40배라고 발표 자료가 함께 적었다. 또 앞 시스템은 MCI를 거친 시간, 새 시스템은 API 시간이라 재는 구간이 완전히 같지 않을 수 있다. 자료는 이 차이를 따로 설명하지 않는다.

## 우리 레거시를 고칠 차례가 오면

토스페이먼츠의 길이 맞는 조건은 분명하다. 시스템을 멈출 수 없고, 바깥 고객(가맹점)의 연동 방식을 바꾸라고 요구할 수 없고, 옛 시스템의 동작을 아무도 완전히 설명하지 못한다. 이 셋이 겹치면 다시 쓰기는 "새로 만들기"가 아니라 "옛것과 똑같이 동작하는 새것을 만들고 조금씩 옮기기"가 된다. 1편은 이를 위해 SLASH 24에서 소개한 테스트 자동화 플랫폼으로 회귀 테스트를 돌렸다고 썼다.

거꾸로, 옛 시스템을 잠깐 멈출 수 있거나 사용자가 내부 팀뿐이라면 이만한 장치가 필요 없을 수 있다. 가맹점별·기능별 카나리, 퍼널 기반 자동 원복, 이중 적재와 보정 배치는 각각 만들고 지키는 데 사람이 든다. 150개가 넘는 서비스, Kubernetes 클러스터 4개, 1% 단위 트래픽 조절 플랫폼은 그 비용을 감당할 규모라서 나온 답이다. 작은 팀이 이 그림을 그대로 따라 하면, 레거시를 고치기 전에 플랫폼을 만드느라 지친다.

그렇다고 "작으니까 한 번에 바꾸자"가 답인 것도 아니다. 바꾸는 범위가 작을 뿐, 옛것을 정답지로 두고 새것을 옆에서 돌려 비교하는 원칙은 규모와 상관없이 쓸 수 있다. 토스뱅크가 이자 조회 한 기능을 떼어 낼 때도 쓴 방식이다.

작은 팀이 지금 가져올 수 있는 것은 이렇다.

- 운영에서 도는 산출물과 저장소의 커밋을 1:1로 묶는다. 이미지 태그에 커밋 해시를 넣고, 토스페이먼츠처럼 최근 배포 이미지 몇 개를 지우지 않고 남겨 둔다. 다시 빌드하지 않고 되돌릴 수 있어야 롤백이 몇 분 안에 끝난다.
- 바깥 입력을 안쪽 모델로 바꾸는 변환을 한 파일에 모은다. 레거시 파라미터를 읽는 코드가 여러 곳에 흩어져 있다면, 다시 쓰기 전에 그것부터 한곳으로 몰아도 다음 작업이 쉬워진다.
- 카나리 판정 지표에 "사용자가 끝까지 갔는가"를 하나 넣는다. 결제라면 시작 대비 완료 비율, 가입이라면 폼 제출 대비 완료 비율이다. 5xx만 보면 놓치는 실패를 잡는다.
- 두 저장소에 쓰기 시작하는 날, 어긋남을 찾아 메우는 배치도 함께 만든다. 그리고 그 배치가 다시 넣은 데이터를 받는 쪽이 두 번 처리하지 않는지 확인한다.

비슷한 신호가 보이면 무엇부터 볼까. 배포 다음 날 DB 대기 세션이 늘면 상위 쿼리 로그에서 새로 생긴 쿼리를 찾고, 실행 계획이 데이터 양에 따라 바뀌었는지 본다. 가맹점이 "실패 응답을 받았는데 돈은 빠졌다"고 하면 호출 체인의 타임아웃을 바깥부터 안쪽까지 나란히 적어 바깥이 더 짧은 곳이 있는지 본다. 장애 뒤 이벤트를 다시 쐈더니 집계가 두 배가 됐다면 받는 쪽의 멱등 처리부터 확인한다.

## 면접에서 나올 만한 질문

### 레거시를 다시 쓸 때 왜 애플리케이션보다 소스 관리와 빌드를 먼저 고쳤나요?

새 버전과 옛 버전의 차이를 알아야 점진적 전환이 의미가 있기 때문이다. 토스페이먼츠는 운영 코드가 어느 버전인지 몰랐고 빌드할 때마다 결과가 달랐다. 이 상태에서는 카나리로 1%만 보내도 문제의 원인이 코드인지 빌드 환경인지 가를 수 없다. 그래서 배포된 class 파일을 디스어셈블해 최신 소스를 찾고, Gradle과 Docker로 재현 가능한 빌드를 만든 뒤에야 1% 단위 트래픽 조절과 애플리케이션 대개편으로 갔다.

### 가맹점에 연동 변경을 요구하지 않고 결제창을 어떻게 다시 썼나요?

연동 방식마다 변환기를 두고, 안쪽 결제 로직은 하나의 요청 객체만 보게 했다. LegacyConverter가 수백 개의 레거시 Form 파라미터를, OpenAPIConverter가 JSON 스펙을 각각 SessionCreationRequest로 바꾼다. 결제 세부 기능을 켜는 파라미터는 Feature 객체로 묶어 핵심 로직이 파라미터를 직접 보지 않는다. 바깥 모델이 안쪽으로 새지 않게 막는 부패 방지 계층의 실제 예다.

### 첫 OpenAPI 어댑터도 스트랭글러 패턴이었는데 왜 문제가 됐나요?

방향이 반대였기 때문이다. 첫 어댑터는 새 OpenAPI 요청을 수십 개의 레거시 파라미터로 번역해 옛 결제 로직에 넘겼다. 그러면 새 인터페이스에 기능을 넣을 때마다 레거시 파라미터와 어댑터 로직을 함께 늘려야 하고, 어댑터에 비즈니스 로직이 쌓인다. 새 구조는 옛 인터페이스를 새 모델로 번역하므로, 옛 제약이 안쪽에 남지 않는다.

### 카나리 판정에 5xx 비율 대신 PREPARE 대비 CONFIRM 비율을 쓴 이유는요?

결제는 서버가 정상 응답해도 사용자가 결제를 끝내지 못하는 실패가 있기 때문이다. 예를 들어 카드사로 가는 Form 값이 틀리면 결제창 서버에는 에러가 없지만 CONFIRM이 오지 않는다. 결제수단을 고른 사람 가운데 결제 확정까지 간 비율은 이런 실패를 직접 센다. 토스페이먼츠는 이 비율이 정상 범위를 벗어나면 그 결제수단의 트래픽을 자동으로 레거시로 되돌렸다.

### 새 원장으로 옮길 때 왜 동기 이중 쓰기 대신 비동기로 따라 쓰고 배치로 메웠나요?

새 원장 때문에 결제가 느려지거나 실패하면 안 되기 때문이다. 옛 원장을 정답으로 두고 먼저 쓴 뒤 새 원장에는 비동기로 적재했고, 스레드 풀이 차면 작업을 버렸다. 대신 읽기 전용 DB 기준 검증 배치가 5분마다 빠진 건을 다시 넣는다. 실시간 경로는 가볍게 두고 정확성은 배치가 책임지는 분업이고, 실제 DB 부하 장애 때 이 배치가 두 원장의 불일치를 해소했다.

### 아웃박스 패턴을 썼는데 이벤트가 빠진 이유와, 고친 뒤 생긴 문제는요?

아웃박스 저장이 실패해도 결제 자체를 실패시키지 않았기 때문이다. 외부 원천사가 이미 승인한 결제는 되돌릴 수 없는 부분이 있어, 가용성을 우선했다. 빠진 거래는 Elasticsearch와 로컬 디스크 대체 어펜더에 남은 로그로 찾아 이벤트를 다시 발행했는데, 그 결과 중복이 생겼다. 이벤트 헤더에 멱등 키를 넣어 받는 쪽이 같은 건을 걸러내게 해서 마무리했다.

### MSA에서 서버마다 타임아웃이 다르면 결제에서 무슨 일이 생기나요?

안쪽은 성공했는데 바깥은 실패를 돌려주는 불일치가 생긴다. 토스페이먼츠 사례에서 앞단 PX 서버의 타임아웃이 승인 서버의 처리 시간보다 짧으면, 승인 서버가 결제를 완료해도 가맹점은 실패 응답을 받았다. 승인 서버의 최대 처리 시간을 계산하고 모든 상위 서버의 타임아웃을 그보다 길게 맞춰 해결했다. 호출 체인의 타임아웃은 바깥으로 갈수록 길어야 한다.

### 우리 서비스가 서비스 열 개 정도의 작은 규모라면 같은 방식을 따라야 하나요?

장치 전부를 따라 할 필요는 없고 원칙만 가져오면 된다. 가맹점별·기능별 카나리 플랫폼이나 Kubernetes 클러스터 4개는 150개가 넘는 서비스와 수만 가맹점을 가진 규모의 답이다. 작은 팀은 커밋 해시로 산출물을 묶고 최근 이미지를 남겨 두는 것, 레거시 입력 변환을 한곳에 모으는 것, 카나리 지표에 완료 비율을 하나 넣는 것부터 시작하면 된다. 이중 적재를 한다면 보정 배치와 받는 쪽 멱등 처리를 처음부터 같이 만든다.
