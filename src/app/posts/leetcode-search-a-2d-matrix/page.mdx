[LeetCode 74. Search a 2D Matrix](https://leetcode.com/problems/search-a-2d-matrix/)는 이분 탐색을 2차원으로 넓힌 첫 문제다. 처음 보면 "행을 고르고, 그 행에서 또 찾는다"는 두 단계가 떠오르고, 그것도 맞는 풀이다. 그런데 이 행렬은 보기만 2차원이고 실제로는 1차원 정렬 배열이라는 걸 알아채면 코드가 반으로 준다.

문제를 내 말로 풀면 이렇다. m행 n열 정수 행렬이 주어진다. 각 행은 왼쪽에서 오른쪽으로 오름차순이고, 각 행의 첫 값은 바로 윗행의 마지막 값보다 크다. 이 행렬에 `target`이 있는지 `true`/`false`로 답한다.

풀이를 정하는 조건은 두 가지다.

- m, n은 1 이상 100 이하다. 빈 행렬은 오지 않고, 칸은 최대 1만 개다.
- 문제가 O(log(m × n))을 요구한다. 칸을 다 보는 O(mn)도 1만 번이라 통과는 하지만, 면접에서는 그 답으로 끝나지 않는다.

이분 탐색 구간을 어떻게 잡는지는 [LeetCode 704 글](/posts/leetcode-binary-search)에서, 이분 탐색이 "참거짓이 한 번만 바뀌는 경계 찾기"라는 일반론은 [이분 탐색 글](/posts/binary-search)에서 다뤘다. 여기서는 그 틀을 2차원에 어떻게 얹는지에 집중한다. 실행 결과는 Node.js 22, Python 3.13, OpenJDK에서 돌린 값이다.

## 행렬을 한 줄로 펴면 정렬된 배열이다

예시 하나로 끝까지 간다. 3×3 행렬에서 19를 찾는다.

```text
        열0  열1  열2
행0  [   2,   5,   8 ]
행1  [  11,  14,  19 ]
행2  [  23,  27,  30 ]
```

두 번째 조건 "행의 첫 값은 윗행의 끝 값보다 크다"가 이 문제의 전부다. 8 다음 행이 11로 시작하고, 19 다음 행이 23으로 시작한다. 그래서 행을 왼쪽 위부터 순서대로 이어 붙이면 그대로 정렬된 배열이 된다.

```text
번호 :  0   1   2   3   4   5   6   7   8
값   :  2   5   8  11  14  19  23  27  30
```

거꾸로, 번호 하나가 몇 행 몇 열인지도 계산으로 바로 나온다. 한 행에 n칸이 있으니 번호 `i`는 `i / n`(내림)행, `i % n`열이다. 번호 5는 5 / 3 = 1행, 5 % 3 = 2열, 값 19다. 번호 7은 2행 1열, 27이다.

이 변환이 되는 순간 행렬을 실제로 펼 필요가 없다. 펼친 배열에서 이분 탐색을 하면서, 칸을 읽을 때만 번호를 행과 열로 바꾸면 된다. 아래에서 다섯 가지 풀이를 차례로 보는데, 결국 이 생각에 도착하는 길이다.

## 칸을 전부 열어 본다

가장 먼저 떠오르는 건 정렬을 무시하고 모든 칸을 보는 것이다.

```js
function searchMatrix(matrix, target) {
  for (const row of matrix) {
    for (const v of row) {
      if (v === target) return true; // 찾으면 바로 끝
    }
  }
  return false; // 다 봤는데 없다
}
```

시간은 O(mn), 공간은 O(1)이다. 100×100이면 1만 칸이라 LeetCode에서는 통과한다. 그래도 이 코드는 두 가지 정렬 조건을 하나도 쓰지 않았다. 아무 행렬에나 통하는 코드라는 건, 이 문제가 준 정보를 버렸다는 뜻이다. 면접에서 이 답을 내면 바로 "정렬돼 있는 걸 어떻게 쓸 수 있나"가 돌아온다.

`matrix.flat().includes(target)`도 한 줄이지만 같은 O(mn)이고, 행렬을 복사하느라 O(mn) 공간까지 쓴다.

## 들어 있을 행부터 고른다

첫 번째로 쓸 수 있는 정보는 "행마다 범위가 겹치지 않는다"는 것이다. 행0은 2~8, 행1은 11~19, 행2는 23~30이다. 19는 행1의 범위 안에만 있을 수 있다. 그러면 위에서부터 행의 첫 값과 끝 값만 보고 들어갈 행을 고른 다음, 그 행 하나에서만 이분 탐색을 한다.

```js
function searchMatrix(matrix, target) {
  for (const row of matrix) {
    const n = row.length;
    if (row[0] <= target && target <= row[n - 1]) {
      // target이 있을 수 있는 유일한 행. 여기서만 이분 탐색한다
      let lo = 0, hi = n - 1;
      while (lo <= hi) {
        const mid = (lo + hi) >> 1;
        if (row[mid] === target) return true;
        if (row[mid] < target) lo = mid + 1;
        else hi = mid - 1;
      }
      return false; // 그 행에 없으면 어디에도 없다
    }
  }
  return false; // 어느 행의 범위에도 안 들어간다 (예: 9는 8과 11 사이)
}
```

행 하나에 들어갈지 판단하는 데 O(1), 그걸 최대 m번, 고른 행에서 O(log n)이다. 합쳐서 O(m + log n)이다. 행을 고른 뒤 다른 행은 볼 필요가 없어서 `return false`로 바로 끝내는 게 중요하다. 9처럼 행 사이 틈에 떨어지는 값은 어느 행의 범위에도 안 들어가서 루프를 다 돌고 `false`가 나온다.

한계는 행 고르기가 선형이라는 데 있다. 행이 1000개, 열이 3개처럼 세로로 긴 행렬이면 시간 대부분을 행 고르는 데 쓴다. 행의 첫 값들도 정렬돼 있으니 여기도 이분 탐색할 수 있다. 그 전에 전혀 다른 방향의 풀이를 하나 보고 가자.

## 오른쪽 위 모서리에서 계단을 내려간다

두 번째 조건(행끼리 이어진다)을 쓰지 않고 "행은 오른쪽으로, 열은 아래로 커진다"는 것만 써도 빠르게 찾을 수 있다. 오른쪽 위 칸에 서 보자. 이 칸은 자기 행에서 가장 크고, 자기 열에서 가장 작다.

- 이 칸이 target보다 크면, 같은 열 아래쪽은 더 크니 이 열 전체가 탈락이다. 왼쪽으로 한 칸 간다.
- 이 칸이 target보다 작으면, 같은 행 왼쪽은 더 작으니 이 행 전체가 탈락이다. 아래로 한 칸 간다.

한 번 비교할 때마다 행 하나나 열 하나가 통째로 사라진다. 그래서 계단을 내려가듯 왼쪽과 아래로만 움직인다.

```js
function searchMatrix(matrix, target) {
  let r = 0, c = matrix[0].length - 1; // 오른쪽 위에서 출발
  while (r < matrix.length && c >= 0) {
    const v = matrix[r][c];
    if (v === target) return true;
    if (v > target) c--; // 이 열은 아래로 갈수록 더 크다: 열 탈락
    else r++;            // 이 행은 왼쪽으로 갈수록 더 작다: 행 탈락
  }
  return false; // 행렬 밖으로 나갔다
}
```

없는 값 15를 찾을 때 어떻게 움직이는지 따라가 보자. 칸 번호는 앞에서 편 번호(행 × 3 + 열)다.

그래도 이 풀이를 알아 둘 이유가 있다. 행끼리 이어진다는 조건 없이도 통하기 때문이다. 바로 그 조건이 빠진 문제가 [LeetCode 240. Search a 2D Matrix II](https://leetcode.com/problems/search-a-2d-matrix-ii/)이고, 거기서는 이 계단이 정석이다. 아래 "면접관이 행렬을 바꿔 오면"에서 다시 본다.

왼쪽 위에서 출발하면 안 된다. 왼쪽 위 칸은 행에서도 열에서도 가장 작아서, target보다 작을 때 오른쪽으로 갈지 아래로 갈지 정할 수 없다. 오른쪽 아래도 같은 이유로 안 된다. 오른쪽 위나 왼쪽 아래처럼 "한쪽으로는 커지고 한쪽으로는 작아지는" 모서리여야 한다.

## 첫 열에서 행을, 그 행에서 열을

행 고르기 풀이로 돌아가서, 행을 선형으로 고르던 부분을 이분 탐색으로 바꾼다. 행의 첫 값만 모으면 `[2, 11, 23]`, 정렬된 배열이다. target이 들어 있을 행은 "첫 값이 target 이하인 마지막 행"이다. 19라면 첫 값이 19 이하인 행은 행0(2)과 행1(11)이고, 그중 마지막인 행1이다.

"target 이하인 마지막 자리"는 "target보다 큰 첫 자리 바로 앞"이다. 이분 탐색 글의 upper bound를 구하고 1을 빼면 된다.

```js
function searchMatrix(matrix, target) {
  const m = matrix.length, n = matrix[0].length;

  // 1단계: 첫 값이 target보다 큰 첫 행을 찾는다 (upper bound). [lo, hi) 반열린 구간
  let lo = 0, hi = m;
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    if (matrix[mid][0] <= target) lo = mid + 1; // 이 행까지는 target 이하로 시작
    else hi = mid;
  }
  const r = lo - 1;            // target 이하로 시작하는 마지막 행
  if (r < 0) return false;     // target이 2보다 작으면 들어갈 행이 없다

  // 2단계: 그 행 안에서 보통 이분 탐색
  const row = matrix[r];
  let a = 0, b = n - 1;
  while (a <= b) {
    const mid = (a + b) >> 1;
    if (row[mid] === target) return true;
    if (row[mid] < target) a = mid + 1;
    else b = mid - 1;
  }
  return false;
}
```

시간은 O(log m + log n)이고, 로그 성질로 이 값은 O(log(mn))과 같다. 요구 조건을 만족한다. 공간은 O(1)이다.

1단계의 비교를 `<=`가 아니라 `<`로 쓰면 lower bound가 되고, "첫 값이 target 이상인 첫 행"을 찾게 된다. 19를 찾으면 행2(23)가 나와서 틀린다. 첫 열 값과 정확히 같은 11은 맞게 나오니, 첫 열 값만 넣어 보는 테스트로는 이 버그가 안 잡힌다. 실제로 돌려 보면 이렇다.

```text
lower bound로 행 고르기: 19 → false (틀림), 11 → true
```

이 풀이는 맞지만 이분 탐색을 두 번 짜야 하고, 두 번 모두 경계를 맞춰야 한다. 두 탐색을 하나로 합칠 수 없을까. 처음 절에서 본 "한 줄로 펴기"가 그 방법이다.

## 번호 하나로 행과 열을 함께 찾는다

행렬을 실제로 펴지 않고, 0부터 m × n - 1까지의 번호 위에서 이분 탐색을 한다. 칸 값을 읽을 때만 번호를 `(⌊mid / n⌋, mid % n)`으로 바꾼다. 704번 코드에서 `nums[mid]` 한 줄만 바뀐다.

```js
function searchMatrix(matrix, target) {
  const m = matrix.length, n = matrix[0].length;
  let lo = 0, hi = m * n - 1; // 펼친 배열의 닫힌 구간 [lo, hi]
  while (lo <= hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    const v = matrix[Math.floor(mid / n)][mid % n]; // 번호 → (행, 열)
    if (v === target) return true;
    if (v < target) lo = mid + 1; // mid 이하는 전부 target보다 작다
    else hi = mid - 1;            // mid 이상은 전부 target보다 크다
  }
  return false;
}
```

19를 찾는 과정을 따라가 보자. 칸은 펼친 순서대로 놓았다.

시간은 O(log(mn)), 공간은 O(1)이다. 칸 1만 개면 비교는 최대 14번이다. 앞 풀이와 시간 복잡도는 같지만 이분 탐색이 하나라서 틀릴 자리가 하나뿐이다.

나누는 수가 열 개수 n이라는 것만 기억하면 된다. 번호는 행 단위로 n칸씩 묶여 있으니 n으로 나눠야 행이 나온다. 정사각 행렬로만 테스트하면 m으로 나눠도 맞게 나와서 이 실수가 숨는다. 아래 "나누는 수를 헷갈리면 틀린다"에서 실제로 틀리는 입력을 본다.

### 파이썬과 자바로 옮기면

파이썬은 `divmod`로 몫과 나머지를 한 번에 얻는다. 정수 크기 제한이 없어서 `(lo + hi) // 2`가 넘칠 걱정도 없다.

```python
from typing import List

class Solution:
    def searchMatrix(self, matrix: List[List[int]], target: int) -> bool:
        m, n = len(matrix), len(matrix[0])
        lo, hi = 0, m * n - 1
        while lo <= hi:
            mid = (lo + hi) // 2          # 파이썬 정수는 넘치지 않는다
            r, c = divmod(mid, n)          # 1차원 번호를 행과 열로
            v = matrix[r][c]
            if v == target:
                return True
            if v < target:
                lo = mid + 1
            else:
                hi = mid - 1
        return False
```

자바는 `/`가 정수끼리면 알아서 내림(양수 기준)이라 `Math.floor`가 필요 없다.

```java
class Solution {
    public boolean searchMatrix(int[][] matrix, int target) {
        int m = matrix.length, n = matrix[0].length;
        int lo = 0, hi = m * n - 1;            // m, n ≤ 100이라 int로 충분하다
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;      // (lo + hi) / 2는 큰 값에서 넘친다
            int v = matrix[mid / n][mid % n];
            if (v == target) return true;
            if (v < target) lo = mid + 1;
            else hi = mid - 1;
        }
        return false;
    }
}
```

예시 행렬에 19, 2, 30, 1, 31, 9, 23, 15를 넣어 세 언어 모두 같은 결과가 나오는 걸 확인했다.

```text
19 true / 2 true / 30 true / 1 false / 31 false / 9 false / 23 true / 15 false
```

언어별로 짚을 곳이 하나 있다. 이 문제는 칸이 1만 개라 상관없지만, 행렬이 10만 × 10만처럼 크면 `m * n`이 100억이 되어 자바 `int`(약 21억)를 넘는다. 그때는 `long lo = 0, hi = (long) m * n - 1`로 잡고, 인덱스로 쓸 때 `(int) (mid / n)`으로 다시 바꾼다. 자바스크립트는 2^53까지 정수가 정확하니 그 크기에서도 문제없다.

### 전부 훑기를 채점관으로 세운다

이분 탐색 코드는 눈으로 봐서는 경계가 맞는지 확신하기 어렵다. 그래서 틀릴 수 없는 전부 훑기 풀이를 정답으로 두고, 작은 무작위 행렬에서 다섯 풀이의 답을 비교했다. 값이 1~3씩 커지게 만들어서 행렬에 없는 값이 자연스럽게 생기고, target도 범위 밖까지 섞었다.

```js
const { brute, rowFirst, staircase, twoSearch, searchMatrix } = require("./sol.js");

function randomMatrix() {
  const m = 1 + Math.floor(Math.random() * 5);
  const n = 1 + Math.floor(Math.random() * 5);
  let cur = -10;
  const mat = [];
  for (let i = 0; i < m; i++) {
    const row = [];
    for (let j = 0; j < n; j++) {
      cur += 1 + Math.floor(Math.random() * 3); // 1~3씩 커지니 빈 값도 생긴다
      row.push(cur);
    }
    mat.push(row);
  }
  return { mat, max: cur };
}

let bad = 0;
for (let it = 0; it < 20000; it++) {
  const { mat, max } = randomMatrix();
  const t = -12 + Math.floor(Math.random() * (max + 15)); // 범위 밖 값도 섞는다
  const answers = [brute, rowFirst, staircase, twoSearch, searchMatrix].map((f) => f(mat, t));
  if (new Set(answers).size > 1) bad++;
}
console.log("mismatch", bad, "/ 20000");
```


1~5행 1~5열이면 한 줄 행렬, 한 열 행렬, 한 칸 행렬이 저절로 섞여 나온다. 앞에서 본 "m으로 나누기" 실수를 일부러 넣고 다섯 번 돌려 봤더니 매번 열다섯 번 안에 어긋나는 입력이 나왔다. 면접에서 "어떻게 검증하겠나"를 물으면 이 방식을 말로 설명하면 된다.

### 파이썬 bisect로 두 번 찾기

두 단계 풀이도 파이썬 표준 라이브러리로 짧게 쓸 수 있다. `bisect_right`가 upper bound, `bisect_left`가 lower bound다.

```python
from bisect import bisect_left, bisect_right

def searchMatrix(matrix, target):
    firsts = [row[0] for row in matrix]      # 첫 열만 모은다 (O(m) 복사)
    r = bisect_right(firsts, target) - 1     # target 이하로 시작하는 마지막 행
    if r < 0:
        return False
    row = matrix[r]
    c = bisect_left(row, target)             # 그 행에서 target 이상이 처음 나오는 자리
    return c < len(row) and row[c] == target
```

19, 11, 15, 1, 31을 넣으면 `[True, True, False, False, False]`가 나온다. 첫 열을 리스트로 따로 만드느라 O(m) 시간과 공간을 쓰는 게 흠이다. 질문이 한 번이면 이 복사가 이분 탐색보다 비싸고, 같은 행렬에 질문이 여러 번 오면 `firsts`를 한 번만 만들어 두고 재사용할 수 있어 오히려 괜찮다.

### 파이썬 bisect에 key를 넘기기

파이썬 3.10부터 `bisect_left`가 `key`를 받는다. `range(m * n)`은 실제로 리스트를 만들지 않으면서 인덱싱이 되는 객체라, 이걸 "펼친 배열"처럼 넘기고 key로 실제 값을 꺼내면 직접 이분 탐색을 짜지 않아도 된다.

```python
from bisect import bisect_left

def searchMatrix(matrix, target):
    m, n = len(matrix), len(matrix[0])
    # 번호 k의 값은 matrix[k // n][k % n]. target 이상이 처음 나오는 번호를 찾는다
    i = bisect_left(range(m * n), target, key=lambda k: matrix[k // n][k % n])
    return i < m * n and matrix[i // n][i % n] == target
```

`bisect_left`는 lower bound라서 "있다면 이 자리"를 돌려준다. 그래서 끝을 벗어나지 않았는지, 그 자리 값이 정말 target인지 두 번 확인한다. 3.10보다 오래된 파이썬(코딩 테스트 플랫폼에 따라 3.8이 남아 있기도 하다)에서는 `key`가 없어서 `TypeError`가 난다. 직접 짠 코드를 기본으로 두고 이건 알아만 두는 편이 안전하다.

## 1000×1000에서 재 본 시간

LeetCode 크기(100×100)에서는 다섯 풀이 모두 순식간이라 차이가 안 보인다. 행렬을 1000×1000(칸 100만 개)으로 키우고, 같은 무작위 질문 2000개를 다섯 풀이에 던졌다. 2000개 중 1043개가 행렬에 있는 값이었다.

```text
brute         1043 2030.5 ms
rowFirst      1043 12.6 ms
staircase     1043 7.6 ms
twoSearch     1043 2.8 ms
searchMatrix  1043 4.4 ms
```

전부 훑기는 질문 하나에 1ms씩 쓴다. 행 고르기(O(m + log n))와 계단(O(m + n))은 행이 1000개라 수백 번 비교하고, 두 이분 탐색 풀이는 20번 안팎이다.

흥미로운 건 두 번 이분 탐색(twoSearch)이 펼친 풀이보다 조금 빠르게 나왔다는 점이다. 비교 횟수는 비슷한데, 펼친 풀이는 매번 나눗셈과 나머지를 계산하고 매번 다른 행의 배열을 오간다. 두 번 탐색은 2단계에서 한 행 안에서만 움직인다. 이 정도 차이는 실행 환경에 따라 뒤집힐 수 있는 크기라 "어느 쪽이 빠르다"고 단정할 일은 아니다. 면접에서는 둘 다 O(log(mn))이고, 코드가 짧고 경계가 하나인 펼친 풀이를 먼저 내는 편이 낫다.

## 다섯 풀이를 한 줄씩 비교하면

| 풀이 | 시간 | 공간 | 쓰는 조건 | 언제 고르나 |
|---|---|---|---|---|
| 전부 훑기 | O(mn) | O(1) | 없음 | 정렬이 없는 행렬. 확인용 채점관 |
| 행 고르고 이분 탐색 | O(m + log n) | O(1) | 행 범위가 안 겹침 | 행이 적고 열이 아주 많을 때 |
| 오른쪽 위 계단 | O(m + n) | O(1) | 행·열 각각 정렬 | 240번처럼 행끼리 안 이어질 때 |
| 첫 열 + 행 이분 탐색 | O(log m + log n) | O(1) | 두 조건 모두 | 행마다 길이가 다른 변형 |
| 펼친 번호 이분 탐색 | O(log(mn)) | O(1) | 두 조건 모두 | 이 문제의 기본 답 |

"쓰는 조건" 열이 이 표에서 가장 중요하다. 행렬에 걸린 조건이 셀수록 빠른 풀이를 쓸 수 있고, 조건이 하나 빠지면 쓸 수 있는 풀이도 줄어든다. 첫 열 + 행 이분 탐색은 행마다 길이가 달라도 통하지만, 펼친 번호 풀이는 모든 행의 길이가 n으로 같아야 `mid % n` 변환이 성립한다.

## 나누는 수를 헷갈리면 틀린다

### 행 개수 m으로 나눈다

번호를 행과 열로 바꿀 때 `mid / m`, `mid % m`으로 쓰는 실수다. 정사각 행렬에서는 m과 n이 같아서 모든 테스트가 통과한다. 2행 4열로 바꾸면 바로 드러난다.

```js
const R = [[1, 3, 5, 7], [10, 11, 16, 20]];
// mid / m, mid % m으로 바꾼 코드에 여러 값을 넣어 본 결과
```

```text
16 TypeError: Cannot read properties of undefined (reading '1')
20 TypeError: Cannot read properties of undefined (reading '1')
3 true
5 false
1 true

```

m = 2로 나누면 번호 5가 2행 1열이 되는데, 2행은 존재하지 않는다. 16과 20은 그 칸을 읽다가 멈췄다. 더 무서운 건 5다. 오류 없이 조용히 `false`가 나왔다. 5는 진짜로 번호 2에 있는데, m으로 나누면 번호 2가 1행 0열(10)로 읽힌다. 탐색은 번호 2까지 제대로 좁혀 왔지만 그 칸에서 10을 보고 끝났다. 3, 1, 10은 우연히 맞았다. 테스트에 정사각이 아닌 행렬을 꼭 하나 넣자.

### 자바스크립트에서 내림을 빠뜨린다

자바나 파이썬에서 넘어오면 `mid / n`이 정수라고 착각하기 쉽다. 자바스크립트의 `/`는 실수 나눗셈이다.

```js
const mid = (lo + hi) / 2;        // (0 + 8) / 2 = 4는 정수라 운 좋게 넘어간다
const row = matrix[mid / n];      // 4 / 3 = 1.333... → matrix[1.333] = undefined
```

실제로 돌리면 첫 비교에서 `row`가 `undefined`라 `TypeError`로 멈춘다. `Math.floor(mid / n)`이나 `(mid / n) | 0`을 쓴다. 뒤쪽은 32비트 정수로 바꾸는 연산이라 21억이 넘는 번호에서는 틀리니, 크기가 커질 수 있으면 `Math.floor`가 안전하다.

### 계단을 왼쪽 위에서 시작한다

```js
let r = 0, c = 0;
while (r < m && c < n) {
  if (matrix[r][c] === target) return true;
  if (matrix[r][c] < target) c++; // 오른쪽으로만 간다
  else return false;
}
```

19를 찾으면 2, 5, 8을 지나 열 밖으로 나가서 `false`가 나온다. 19는 아래 행에 있는데 아래로 갈 이유를 만들지 못했다. 왼쪽 위 칸은 오른쪽도 아래도 더 크니, 작다는 정보만으로는 방향을 하나로 정할 수 없다.

### 행을 lower bound로 고른다

앞에서 본 대로, "첫 값이 target 이하인 마지막 행"을 구해야 하는데 "첫 값이 target 이상인 첫 행"을 구하는 실수다. 첫 열에 있는 값(2, 11, 23)으로만 테스트하면 맞게 나온다. 행 가운데나 끝에 있는 값(19)으로 테스트해야 잡힌다.

### 빈 행렬을 가정한다

이 문제는 m, n이 1 이상이라 `matrix[0].length`가 안전하다. 실무 코드나 다른 플랫폼 문제에서는 `[]`나 `[[]]`가 올 수 있다. 그때는 `if (!matrix.length || !matrix[0].length) return false`를 맨 앞에 둔다. 빠뜨리면 `[]`에서 `matrix[0]`이 `undefined`라 `.length`에서 멈추고, `[[]]`에서는 `hi = -1`이라 루프를 안 돌고 `false`가 나와 우연히 맞는다.

## 면접관이 행렬을 바꿔 오면

### 행끼리 이어지지 않는다면 (240. Search a 2D Matrix II)

조건이 "행은 오른쪽으로, 열은 아래로 정렬"만 남는다. 예를 들어 이런 행렬이다.

```text
[ 1, 4, 7 ]
[ 2, 5, 8 ]
[ 3, 6, 9 ]
```

행을 이어 붙이면 `1, 4, 7, 2, 5, 8, …`이라 정렬이 아니다. 펼친 번호 풀이에 넣어 보면 실제로 틀린다.

```text
3 flat false stair true brute true
6 flat true stair true brute true
2 flat false stair true brute true
```

3과 2는 행렬에 있는데 펼친 풀이는 `false`를 냈다. 6은 운 좋게 맞았다. 이럴 때는 오른쪽 위 계단 풀이를 쓴다. 한 번에 행이나 열 하나를 지우는 성질은 이 조건만으로 성립하기 때문이다. O(m + n)이 이 문제의 일반적인 답이고, 행마다 이분 탐색하는 O(m log n)도 성립한다. m과 n 중 한쪽이 훨씬 작으면 작은 쪽으로 돌고 큰 쪽에서 이분 탐색하는 편이 낫다.

### 있는지가 아니라 자리를 달라면

`true`/`false` 대신 `[행, 열]`을 돌려주라면 찾은 mid를 바꿔서 돌려주면 된다. "없으면 들어갈 자리"까지 달라면 lower bound로 바꾼다. `[0, m × n)` 반열린 구간에서 `v < target`이면 `lo = mid + 1`, 아니면 `hi = mid`로 돌고 끝난 `lo`를 행과 열로 바꾼다. 예시 행렬에서 돌려 본 결과다.

```text
19 → [1, 2]   15 → [1, 2]   9 → [1, 0]   31 → [3, 0]
```

15는 19 자리에 끼어들어야 하고, 9는 행1 맨 앞(11 앞)에 들어간다. 31은 `[3, 0]`, 즉 행렬 밖이라 "맨 뒤에 새 행"이라는 뜻이다. 이 자리를 쓰기 전에 범위 확인을 해야 한다. lower bound 자체는 [이분 탐색 글의 경계 절](/posts/binary-search)에서 자세히 다뤘다.

### 같은 행렬에 질문이 아주 많이 온다면

질문 하나가 O(log(mn))이라 이미 충분히 빠르다. 질문 q개면 O(q log(mn))이다. 값이 있는지만 물으면 처음에 모든 값을 `Set`에 넣어 두고 O(1)로 답할 수도 있다. 대신 O(mn) 메모리를 더 쓰고, 행렬이 바뀌면 Set도 고쳐야 한다. 정렬된 구조를 이미 갖고 있다면 이분 탐색이 메모리 면에서 낫다는 트레이드오프는 [이분 탐색 글의 마지막 질문](/posts/binary-search)과 같다.

### 행렬이 너무 커서 메모리에 다 안 올라간다면

행 단위로 파일이나 페이지에 나뉘어 있다고 하자. 펼친 번호 풀이는 mid마다 다른 행을 읽으니 디스크 읽기가 log(mn)번 흩어진다. 첫 열 + 행 이분 탐색은 행의 첫 값만 따로 모은 작은 색인을 메모리에 두고, 행 하나만 디스크에서 읽으면 된다. DB의 B-트리 인덱스가 "위쪽 노드에서 범위를 고르고, 아래 페이지 하나만 읽는" 모양인 것과 같은 생각이다. 이 경우에는 두 번 탐색이 더 실용적이다.

### 행렬에서 k번째로 작은 값 (378. Kth Smallest Element in a Sorted Matrix)

240번처럼 행·열만 정렬된 행렬에서 k번째 값을 구하는 문제다. 칸을 찾는 대신 값의 범위에서 이분 탐색한다. "x 이하인 칸이 몇 개인가"를 계단 방식으로 O(m + n)에 세고, 그 수가 k 이상이 되는 가장 작은 x를 찾는다. [Koko Eating Bananas](/posts/leetcode-koko-eating-bananas)처럼 답의 범위에서 찾는 이분 탐색에 계단 세기가 판정 함수로 들어간 모양이다.

## 두 겹 정렬은 한 겹이다

이 문제의 행렬은 행 안에서 정렬되고 행끼리도 이어져 있어서, 모양만 2차원인 1차원 정렬 배열이다. 그걸 알아채면 번호 하나 위에서 704번 이분 탐색을 그대로 돌리고, 칸을 읽을 때만 `⌊mid / n⌋`, `mid % n`으로 바꾸면 끝난다. 조건이 하나 빠진 240번에서는 이 변환이 깨지고, 오른쪽 위에서 행이나 열을 하나씩 지우는 계단이 답이 된다. 행렬에 어떤 정렬 조건이 걸려 있는지가 쓸 수 있는 풀이를 정한다.

## 면접에서 나올 만한 질문

### 이 행렬을 왜 1차원 배열처럼 다룰 수 있나요?

각 행이 정렬돼 있고, 행의 첫 값이 윗행의 끝 값보다 크기 때문이다. 이 두 조건이 있으면 행을 위에서부터 이어 붙인 수열이 전체로 정렬된다. 그래서 0부터 mn - 1까지의 번호 위에서 이분 탐색을 하고, 칸을 읽을 때만 `⌊i / n⌋`행 `i % n`열로 바꾸면 된다. 행렬을 실제로 펴서 복사할 필요는 없다.

### 번호를 행과 열로 바꿀 때 왜 열 개수로 나누나요?

펼친 번호는 한 행의 n칸이 묶음 하나라서, n칸마다 행이 하나씩 넘어가기 때문이다. 번호 i 앞에는 완전한 행이 ⌊i / n⌋개 있고, 남은 i % n이 그 행 안의 열 위치다. 행 개수 m으로 나누는 실수는 정사각 행렬에서 드러나지 않으니, 테스트에 2×4 같은 직사각 행렬을 넣어 확인한다.

### 시간 복잡도는 어떻게 되나요? O(log m + log n)과 O(log(mn))은 다른가요?

펼친 풀이는 원소 mn개 위의 이분 탐색이라 O(log(mn))이다. 로그의 성질로 log(mn) = log m + log n이라, 첫 열에서 행을 찾고 그 행에서 다시 찾는 두 단계 풀이와 복잡도가 같다. 100×100이면 둘 다 비교 14번 안팎이다. 차이는 코드에 이분 탐색이 하나냐 둘이냐, 그래서 경계 실수할 자리가 몇 개냐다.

### 오른쪽 위에서 시작하는 풀이는 언제 쓰나요?

행과 열이 각각 정렬만 돼 있고 행끼리는 이어지지 않는 행렬(240번)에서 쓴다. 오른쪽 위 칸은 자기 행에서 가장 크고 자기 열에서 가장 작아서, 비교 한 번에 행이나 열 하나를 지울 수 있다. O(m + n)이라 74번에서는 이분 탐색보다 느리지만 조건이 약해도 통한다. 왼쪽 위나 오른쪽 아래에서 시작하면 방향을 하나로 정할 수 없어서 안 된다.

### mn이 아주 커지면 무엇을 조심하나요?

자바나 C++에서 `m * n`이 `int` 범위(약 21억)를 넘을 수 있다. 번호를 `long`으로 잡고, mid도 `lo + (hi - lo) / 2`로 구해 더하기에서 넘치지 않게 한다. 자바스크립트는 2^53까지 정수가 정확해서 실제로는 문제가 안 되지만, `| 0`이나 `>> 1` 같은 비트 연산은 32비트로 잘리니 `Math.floor`를 쓴다.

### 행마다 길이가 다르다면 어느 풀이가 남나요?

펼친 번호 풀이는 모든 행이 n칸이라는 전제로 `i % n`을 쓰니 깨진다. 첫 열에서 "첫 값이 target 이하인 마지막 행"을 이분 탐색으로 고르고 그 행에서 다시 찾는 두 단계 풀이는 그대로 통한다. 행마다 시작 번호를 누적 합으로 저장해 두고 번호에서 행을 이분 탐색으로 찾는 방법도 있지만, 두 단계 풀이가 더 간단하다.

### 이 코드가 맞는지 어떻게 확인했나요?

모든 칸을 보는 O(mn) 풀이를 채점관으로 두고, 1~5행 1~5열의 무작위 행렬과 무작위 target 2만 개에서 다섯 풀이의 결과를 비교했다. 어긋난 경우는 0건이었다. 손으로 고를 때는 첫 값, 마지막 값, 행 경계 사이 값, 모든 값보다 작거나 큰 값, 한 줄과 한 열 행렬을 꼭 넣는다.
