## 카운터 한 줄이 시계열 수백 개가 된다

주문을 몇 번 조회했는지 세려고 컨트롤러에 카운터를 하나 넣었다. 어떤 주문이 많이 조회되는지도 보고 싶어서 주문 ID를 태그로 붙였다. 배포하고 나서 `/actuator/prometheus` 응답이 241줄에서 1040줄로 늘었다. 요청은 200번 보냈을 뿐이다. 실제 트래픽이라면 주문 ID 수만큼 시계열이 생기고, Prometheus 메모리가 그만큼 오른다.

스프링 부트에서 지표, trace, 로그는 Micrometer라는 계측 라이브러리 하나로 나온다. 편한 만큼 설정 한 줄이 비용을 몇 배로 바꾼다. 이 글은 Micrometer의 Observation API가 신호 셋을 어떻게 만드는지, `/actuator/prometheus`의 한 줄을 어떻게 읽는지, 태그와 히스토그램이 시계열 수를 어떻게 늘리는지, trace를 OTLP로 내보내고 로그와 지표에 trace ID를 붙이는 법을 실제로 돌려 보며 따라간다.

관측 가능성이 왜 필요한지, 세 신호가 각자 무엇에 답하는지는 [관측 가능성](/posts/observability-basics) 글에 있다. 카운터와 히스토그램 같은 지표 그릇은 [지표 타입](/posts/metrics-types), traceparent 헤더와 샘플링 원리는 [분산 추적](/posts/distributed-tracing)에서 다뤘다. 여기서는 그 개념을 스프링 부트에서 어떤 설정과 코드로 켜는지에 집중한다. 실험은 Spring Boot 4.1.1, JDK 21에서 했고 출력은 모두 실제로 돌린 결과다. Grafana와 PromQL 쿼리는 실행 결과 없이 쿼리만 적었다.

의존성은 셋이다. Boot 4에서 `spring-boot-starter-opentelemetry`가 새로 생겼다. Micrometer Tracing의 OpenTelemetry 브리지와 OTLP 내보내기를 한 번에 가져온다.

```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-opentelemetry</artifactId> <!-- tracing 브리지 + OTLP -->
</dependency>
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-registry-prometheus</artifactId>   <!-- /actuator/prometheus -->
</dependency>
```

```properties
spring.application.name=orders
server.port=19110
management.endpoints.web.exposure.include=health,prometheus,metrics
```

## 계측 한 번에 신호가 셋 나온다

예제 앱은 주문을 조회하면서 가격을 계산하고, `RestClient`로 결제 API를 부른다. 결제 API는 같은 앱 안의 다른 엔드포인트로 두어 서비스 둘을 흉내 냈다.

```java
@GetMapping("/orders/{id}")
public String order(@PathVariable String id) {
    log.info("주문 조회 시작 id={}", id);
    String price = Observation.createNotStarted("order.price", observations)
            .lowCardinalityKeyValue("currency", "KRW")    // 지표 태그와 span 속성 둘 다
            .highCardinalityKeyValue("order.id", id)      // span 속성에만
            .observe(() -> {
                sleep(30);
                return "12000";
            });
    String paid = payments.get().uri("/payments/{id}", id).retrieve().body(String.class);
    log.info("주문 조회 끝 id={} paid={}", id, paid);
    return "order " + id + " price=" + price + " paid=" + paid + "\n";
}
```

`Observation`은 "이 구간을 지켜본다"는 선언이다. 시작과 끝, 이름, 키-값만 적는다. 무엇을 만들어 낼지는 등록된 핸들러가 정한다. 지표 핸들러는 그 구간을 Timer로 재고, tracing 핸들러는 span을 열고 닫고, 로그 쪽은 MDC에 trace ID를 넣는다. 스프링 MVC의 요청 처리와 `RestClient` 호출도 프레임워크 안에서 같은 Observation으로 계측돼 있어서 코드 없이 나온다. 아래 그림에서 다음을 누르면 요청 하나가 지나가며 핸들러들이 움직이는 순서가 보인다.

이름 규칙도 볼 만하다. Micrometer 이름은 점으로 잇는다(`http.server.requests`). Prometheus 레지스트리가 점을 밑줄로 바꾸고, Timer라서 단위 `_seconds`를, 각 시계열 종류에 따라 `_count`, `_sum`, `_max`를 붙인다. 카운터는 `_total`이 붙는다. 그래서 코드에서 `orders.viewed`로 만든 카운터는 `orders_viewed_total`로 찾아야 한다.

Prometheus는 이 응답을 정해진 주기로 긁어 간다. 쿠버네티스에서 ServiceMonitor로 대상을 잡는 법은 [Prometheus 내부 구조](/posts/prometheus-basics)에 있다. 이 엔드포인트를 외부에서 닿는 포트로 열면 안 된다. [쿠버네티스 위의 스프링 부트](/posts/spring-boot-on-kubernetes)에서 본 것처럼 관리 포트를 나누고 클러스터 안에서만 긁는 게 보통이다.

## 주문 ID를 태그로 넣으면

처음 장면을 재현했다. 나쁜 예를 두 개 섞은 엔드포인트다. 카운터에 주문 ID를 태그로 넣었고, `RestClient`에 경로를 템플릿이 아니라 문자열로 이어 붙여 넘겼다.

```java
@GetMapping("/orders-bad/{id}")
public String orderBad(@PathVariable String id) {
    meters.counter("orders.viewed", "order.id", id).increment();                 // ID를 태그로
    String paid = payments.get().uri("/payments/" + id).retrieve().body(String.class); // 템플릿 없이
    return "order " + id + " paid=" + paid + "\n";
}
```

```text

```

부트는 `http.client.requests`와 `http.server.requests`의 `uri` 태그에 기본 상한 100개(`management.metrics.web.client.max-uri-tags`, `...server.max-uri-tags`)를 걸어 둔다. 넘으면 그 뒤 값은 지표로 만들지 않는다. 안전장치는 되지만 101번째 경로부터는 지표가 아예 없다는 뜻이기도 하다. 경고 메시지가 말하는 대로 `uri("/payments/{id}", id)`처럼 템플릿과 변수를 나눠 넘기면 `uri="/payments/{id}"` 한 줄로 묶인다. 직접 만든 카운터에는 이런 상한이 없다. 아래 그림에서 다음을 누르면 요청이 들어올 때마다 시계열이 어떻게 늘어나는지 보인다.

고치는 법은 값의 성격에 따라 갈린다. 주문 ID, 사용자 ID, 전체 URL처럼 값이 끝없이 늘어나는 건 지표 태그가 아니라 span 속성이나 로그 필드로 둔다. Observation이라면 `highCardinalityKeyValue`가 정확히 그 자리다. 정말 "어떤 주문이 많이 조회되나"가 궁금하다면 지표가 아니라 로그나 분석용 저장소에 물을 질문이다. 태그는 값의 개수가 미리 셀 수 있을 만큼(수십 개 이하) 작을 때만 쓴다. 시계열 DB가 왜 이 숫자에 약한지는 [시계열 DB](/posts/db-type-time-series) 글에 있다.

이미 퍼진 태그를 급히 막아야 할 때는 `MeterFilter`를 빈으로 등록한다. 배포 없이 고칠 수는 없지만 코드 여러 곳을 찾아다니지 않아도 된다.

```java
@Bean
MeterFilter dropOrderIdTag() {
    // orders.viewed에서 order.id 태그를 지운다. 같은 이름의 시계열이 하나로 합쳐진다
    return MeterFilter.ignoreTags("order.id");
}
```

## 히스토그램은 칸 수만큼 시계열을 늘린다

기본 Timer는 `_count`, `_sum`, `_max` 세 줄이다. 평균은 구할 수 있지만 p99는 못 구한다. p99를 Prometheus에서 계산하려면 히스토그램 칸(bucket)이 필요하다. 켜는 설정은 한 줄이다.

```bash
java -jar target/orders-obs.jar \
  --management.metrics.distribution.percentiles-histogram.http.server.requests=true
```

```bash
curl -s localhost:19110/actuator/prometheus > h.txt
grep '^http_server_requests_seconds_bucket' h.txt | grep -c 'uri="/orders/{id}"'
```

```text
69
```

```text
http_server_requests_seconds_bucket{...,uri="/orders/{id}",le="0.001"} 0
http_server_requests_seconds_bucket{...,uri="/orders/{id}",le="0.016777216"} 0
http_server_requests_seconds_bucket{...,uri="/orders/{id}",le="0.022369621"} 0
http_server_requests_seconds_bucket{...,uri="/orders/{id}",le="0.027962026"} 0
http_server_requests_seconds_bucket{...,uri="/orders/{id}",le="+Inf"} 4
```

(태그 일부를 `...`로 줄였다.) 태그 조합 하나에 칸 69줄이 붙는다. Micrometer는 1ms부터 30초 사이를 미리 정한 간격으로 나눠 칸을 만든다. 경계 값이 `0.016777216`처럼 어색한 이유다. 시계열이 3개에서 72개로 24배가 된다. 이 칸 수에 태그 조합 수와 Pod 수가 곱해진다. 직접 계산해 보자.

다섯 번째 테스트가 현실적인 숫자다. 엔드포인트 20개짜리 서비스 하나에 히스토그램을 켜고 30개 Pod로 돌리면 지표 하나로 43만 시계열이 된다. 그래서 히스토그램은 꼭 필요한 지표에만 켜고, 칸을 줄인다. 응답 목표가 정해져 있다면 그 경계만 칸으로 둔다.

```bash
java -jar target/orders-obs.jar --management.metrics.distribution.slo.http.server.requests=100ms,300ms,1s
```

```text
http_server_requests_seconds_bucket{...,uri="/orders/{id}",le="0.1"} 3
http_server_requests_seconds_bucket{...,uri="/orders/{id}",le="0.3"} 4
http_server_requests_seconds_bucket{...,uri="/orders/{id}",le="1.0"} 4
http_server_requests_seconds_bucket{...,uri="/orders/{id}",le="+Inf"} 4
http_server_requests_seconds_count{...,uri="/orders/{id}"} 4
http_server_requests_seconds_sum{...,uri="/orders/{id}"} 0.361595387
http_server_requests_seconds_max{...,uri="/orders/{id}"} 0.171670072
```

이번엔 칸이 4줄이다. "300ms 안에 끝난 비율"은 정확하게 나오고, p99는 칸 경계 사이를 직선으로 이어 추정하니 칸이 성글수록 부정확하다. 칸 경계가 분위수를 얼마나 틀리게 만드는지는 [지표 타입](/posts/metrics-types)에서 쟀다. SLO 비율이 목적이면 SLO 칸, 분위수 그래프가 목적이면 `percentiles-histogram`이다. `management.metrics.distribution.percentiles=0.99`처럼 앱 안에서 분위수를 계산해 내보내는 옵션도 있지만, Pod 여러 개의 값을 합칠 수 없어서 쿠버네티스에서는 잘 쓰지 않는다.

## trace를 OTLP로 내보낸다

지표는 Prometheus가 가져가고, trace는 앱이 밀어 보낸다. 표준 형식은 OTLP(OpenTelemetry Protocol)이고, 보통 OpenTelemetry Collector가 받아 Tempo나 Jaeger로 넘긴다. Collector 설정은 [OTel Collector 파이프라인](/posts/otel-collector-pipeline) 글이 다룬다. 여기서는 앱 쪽을 본다. 받는 쪽은 OTLP/HTTP 요청을 protobuf로 풀어 span을 찍기만 하는 작은 파이썬 서버로 대신했다(`opentelemetry-proto` 패키지의 정의를 썼다).

```bash
java -jar target/orders-obs.jar \
  --management.opentelemetry.tracing.export.otlp.endpoint=http://127.0.0.1:19120/v1/traces \
  --management.tracing.sampling.probability=1.0
curl -s localhost:19110/orders/7
```

```text
POST /v1/traces content-type=application/x-protobuf bytes=1519
 resource service.name=orders telemetry.sdk.language=java
  span name='http get' kind=CLIENT trace=7350f3bfe395968e0d36fdd67558da4f span=a9cd31c986945d7d parent=d4baf6254777c32d 258.4ms
     http.url=http://localhost:19110/payments/7
     uri=/payments/{id}
  span name='http get /payments/{id}' kind=SERVER trace=7350f3bfe395968e0d36fdd67558da4f span=1eb0026943bbe9fa parent=a9cd31c986945d7d 124.1ms
     http.url=/payments/7
     uri=/payments/{id}
  span name='order.price' kind=INTERNAL trace=7350f3bfe395968e0d36fdd67558da4f span=4c45745aa7e0e9ba parent=d4baf6254777c32d 60.9ms
     currency=KRW
     order.id=7
  span name='http get /orders/{id}' kind=SERVER trace=7350f3bfe395968e0d36fdd67558da4f span=d4baf6254777c32d parent=- 462.5ms
     http.url=/orders/7
     uri=/orders/{id}
```

(속성은 몇 개만 남겼고, span마다 반복되는 resource 줄은 하나로 줄였다.) span 넷이 같은 trace ID를 갖는다. `parent`를 따라가면 나무가 보인다. 맨 아래 `/orders/{id}` 서버 span이 뿌리(`parent=-`)이고, 그 아래에 `order.price`와 `http get` 클라이언트 span이 있고, 클라이언트 span 아래에 결제 쪽 서버 span이 붙었다. `order.id=7`과 `http.url=/orders/7`이 여기에는 들어 있다. 지표에서 뺀 높은 카디널리티 값이 trace에서는 찾는 열쇠가 된다.

결제 쪽이 부모를 알 수 있었던 건 `RestClient`가 요청에 `traceparent` 헤더를 넣었기 때문이다. 결제 엔드포인트가 받은 헤더를 로그로 찍었다.

```text
결제 조회 id=7 traceparent=00-7350f3bfe395968e0d36fdd67558da4f-a9cd31c986945d7d-03
```

가운데 값이 클라이언트 span ID(`a9cd31c986945d7d`)다. 그 클라이언트 span이 결제 서버 span의 부모가 됐다. 이 전파는 스프링이 만든 `RestClient.Builder`를 주입받아 쓸 때만 된다. `RestClient.create()`나 직접 만든 HTTP 클라이언트로 부르면 Observation이 붙지 않아 헤더가 빠지고, 결제 쪽 trace가 따로 떨어진다. 아래 그림에서 다음을 누르면 헤더와 span이 지나는 길이 보인다.

### 기본 샘플링은 10%다

설정에서 `sampling.probability=1.0`을 준 이유가 있다. 부트의 기본값은 `0.1`이다. 이 값을 주지 않고 띄웠을 때 결제 쪽이 받은 헤더는 끝이 `-02`였다.

```text
결제 조회 id=1 traceparent=00-812d25d8681142ce53e10f52972d18cf-3db946f4fe35e9fc-02
```

마지막 바이트는 플래그다. 맨 아래 비트가 sampled이고, 02는 그 비트가 꺼져 있다(02는 trace ID가 무작위로 만들어졌다는 표시다). 위의 1.0 실험에서는 `-03`이었다. 꺼진 trace는 내보내지 않는다. 그래서 "trace를 켰는데 Tempo에서 절반도 안 보인다"는 문의의 상당수가 이 기본값이다. 로그에는 샘플링과 상관없이 trace ID가 찍히기 때문에, 로그에서 찾은 trace ID로 Tempo를 검색했는데 없다는 증상으로 나타난다.

운영에서 1.0으로 두면 저장 비용이 요청 수에 비례한다. 흔한 구성은 앱에서는 넉넉하게(또는 1.0으로) 보내고, Collector의 꼬리 샘플링으로 오류와 느린 trace만 남기는 것이다. 이유는 [분산 추적](/posts/distributed-tracing)에서 다뤘다.

설정 이름은 4.0에서 바뀌었다. 3.x의 `management.otlp.tracing.endpoint`는 4.1.1 메타데이터에 `management.opentelemetry.tracing.export.otlp.endpoint`로 바뀌었다고(since 4.0.0, level error) 적혀 있다. 3.x 설정을 그대로 가져오면 내보내기가 조용히 꺼진 상태가 된다. 옮기는 방법은 [Boot 4 마이그레이션](/posts/spring-boot-4-migration) 글에 있다.

## 로그 한 줄에 traceId

tracing이 켜져 있으면 부트의 기본 로그 패턴에 trace ID와 span ID가 들어간다. 앞의 실험 로그다.

```text
2026-10-22T03:14:19.384Z  INFO 3724 --- [orders] [io-19110-exec-1] [7350f3bfe395968e0d36fdd67558da4f-d4baf6254777c32d] demo.OrderController : 주문 조회 시작 id=7
2026-10-22T03:14:19.613Z  INFO 3724 --- [orders] [io-19110-exec-2] [7350f3bfe395968e0d36fdd67558da4f-1eb0026943bbe9fa] demo.OrderController : 결제 조회 id=7 traceparent=00-7350f3bf…-03
```

대괄호 안이 `traceId-spanId`다. 스레드가 달라도(`exec-1`, `exec-2`) trace ID가 같으니 이 값 하나로 요청 하나의 로그를 다 모을 수 있다. 요청 밖의 로그(시작, 스케줄러)는 이 칸이 공백으로 채워진다. 형식은 `logging.pattern.correlation`으로 바꾼다.

로그 수집기가 JSON을 원하면 3.4부터 들어간 구조화 로그를 쓴다. 설정 한 줄로 ECS, Logstash, GELF 형식이 된다.

```bash
java -jar target/orders-obs.jar --logging.structured.format.console=ecs
```


(한 줄로 나온 것을 보기 좋게 폈다.) `traceId`가 따로 필드라서 Loki나 Elasticsearch에서 필드로 검색하고, Grafana에서 trace로 건너가는 링크를 걸 수 있다. 로그를 어떤 필드로 남길지, 개인정보를 어떻게 가릴지는 [구조화 로그](/posts/structured-logging)에 있다.

## 지표의 튄 점에서 trace로

히스토그램을 켜고 tracing을 함께 쓰면 칸마다 그 칸에 들어간 요청의 trace ID가 하나씩 붙는다. exemplar라고 부른다. Prometheus 기본 텍스트 형식에는 안 보이고, OpenMetrics 형식으로 요청해야 나온다.

```bash
curl -s -H 'Accept: application/openmetrics-text; version=1.0.0' localhost:19110/actuator/prometheus \
  | grep 'uri="/orders/{id}"' | grep '#'
```

```text
http_server_requests_seconds_bucket{...,uri="/orders/{id}",le="0.089478485"} 3 # {span_id="f014aaa9360527ee",trace_id="9eb91e9d080079baef5fb66b50742d04"} 0.069505166 1792638874.672
http_server_requests_seconds_bucket{...,uri="/orders/{id}",le="0.447392426"} 4 # {span_id="d4baf6254777c32d",trace_id="7350f3bfe395968e0d36fdd67558da4f"} 0.427768136 1792638859.734
```

`#` 뒤가 exemplar다. 0.43초 칸에 붙은 trace ID `7350f3bf…`는 앞에서 Collector로 보낸 바로 그 느린 요청이다. Grafana 패널에서 p99가 튄 점을 누르면 이 trace로 바로 간다. 부트는 `management.tracing.exemplars.include=sampled-traces`가 기본이라 샘플링된 trace만 exemplar로 붙인다. 샘플링이 10%면 exemplar도 그만큼 드물다. Prometheus 쪽에서는 exemplar 저장 기능을 켜야 받는다(`--enable-feature=exemplar-storage`). 패널 설정은 [Grafana 대시보드](/posts/grafana-dashboards) 글과 [Tempo 글](/posts/grafana-tempo-tracing)로 넘긴다.

## JVM 대시보드에 올릴 것

`/actuator/prometheus`에는 JVM 지표도 기본으로 나온다. 이 앱에서는 `# TYPE` 줄 기준으로 65종, 406줄이었다. 다 그릴 필요는 없다. 장애 때 실제로 보는 것만 고른 값이다.

```text
jvm_memory_used_bytes{area="heap",id="G1 Eden Space"} 1.2582912E7
jvm_memory_used_bytes{area="heap",id="G1 Old Gen"} 2.0100616E7
jvm_memory_max_bytes{area="heap",id="G1 Eden Space"} -1.0
jvm_memory_max_bytes{area="heap",id="G1 Old Gen"} 3.58612992E9
jvm_gc_pause_seconds_count{action="end of minor GC",cause="G1 Evacuation Pause",gc="G1 Young Generation"} 2
jvm_gc_pause_seconds_sum{action="end of minor GC",cause="G1 Evacuation Pause",gc="G1 Young Generation"} 0.032
jvm_gc_overhead 0.0011826729854394259
jvm_threads_live_threads 35.0
jvm_threads_states_threads{state="runnable"} 9.0
jvm_threads_states_threads{state="waiting"} 11.0
process_cpu_usage 0.6666666666666666
application_ready_time_seconds{main_application_class="demo.ObsApplication"} 24.347
```

Eden과 Survivor의 `max`가 `-1`이다. G1은 이 영역들의 최대 크기를 따로 정해 두지 않기 때문이다. 영역별 사용률을 `id`마다 `used / max`로 그리면 이 두 줄은 음수가 된다. 한도 선은 Old Gen의 `max`(3.58612992E9, 이 기계에서 JVM이 정한 최대 힙 3420MiB와 같은 값)로 긋고, 사용량은 영역을 더해서 본다. JVM 메모리 영역이 각각 무엇인지는 [JVM 메모리 글](/posts/java-jvm-memory-gc)에 있다.

패널로 옮길 때 쓰는 쿼리다(쿼리만 적었고 결과는 없다).

```text
# 힙 사용량 (영역 합) — 한도 선은 Old Gen max로
sum by (pod) (jvm_memory_used_bytes{application="orders", area="heap"})

# GC로 멈춘 시간의 비율 (1분 동안 몇 초 멈췄나)
sum by (pod) (rate(jvm_gc_pause_seconds_sum{application="orders"}[1m]))

# 엔드포인트별 p99 (percentiles-histogram을 켠 경우만)
histogram_quantile(0.99, sum by (le, uri) (rate(http_server_requests_seconds_bucket{application="orders"}[5m])))

# 5xx 비율
sum(rate(http_server_requests_seconds_count{application="orders", outcome="SERVER_ERROR"}[5m]))
  / sum(rate(http_server_requests_seconds_count{application="orders"}[5m]))
```

쿼리에 `application` 태그를 썼는데, 앞의 출력에는 이 태그가 없었다. 부트는 모든 지표에 공통 태그를 붙이는 설정을 따로 줘야 한다. 같은 Prometheus에 서비스가 여럿이면 이 태그가 서비스를 가르는 유일한 기준이 되니 처음부터 넣는다.

```properties
management.metrics.tags.application=${spring.application.name}
```

```text
jvm_threads_live_threads{application="orders"} 28.0
tomcat_threads_busy_threads{application="orders",name="http-nio-19110"} 1.0
```

같이 넣은 `server.tomcat.mbeanregistry.enabled=true`는 Tomcat 스레드 지표를 켠다. 기본은 꺼져 있어서 `tomcat_threads_busy_threads`가 없다. 요청 스레드가 다 찼는지 보려면 필요하다.

현장에서 증상과 지표를 잇는 길은 대체로 이렇다. p99가 오르는데 CPU는 낮다면 `jvm_threads_states_threads{state="waiting"}`와 `tomcat_threads_busy_threads`, 커넥션 풀 지표(`hikaricp_connections_pending`)를 본다. 스레드가 무언가를 기다리고 있다는 뜻이다. GC 멈춤 비율이 올라가면서 Old Gen 사용량이 GC 뒤에도 내려오지 않으면 누수나 힙 부족이다. 커뮤니티 대시보드(Grafana.com의 "JVM (Micrometer)" 같은 것)를 가져와 시작해도 되지만, 그 대시보드가 기대하는 태그 이름(`application`, `instance`)이 이 앱과 맞는지부터 확인한다. 패널이 비어 있으면 대개 태그 이름이 다르다.

## 1040줄을 다시 보면

처음의 1040줄은 지표에 넣지 말아야 할 값, 주문 ID와 실제 경로를 태그로 넣어서 생겼다. Observation API는 그 값을 둘 곳을 따로 준다. 낮은 카디널리티 값은 지표 태그와 span 속성 양쪽에, 높은 카디널리티 값은 span 속성에만 간다. 히스토그램은 칸 수만큼 시계열을 곱하니 필요한 지표에만 켠다. trace는 OTLP로 밀어 보내되 기본 샘플링이 10%라는 걸 기억하고, 로그와 exemplar에 붙은 trace ID로 세 신호를 오간다. 이 앱을 쿠버네티스에서 띄우는 이야기는 [쿠버네티스 위의 스프링 부트](/posts/spring-boot-on-kubernetes)에 있다.

## 면접에서 나올 만한 질문

### Micrometer의 Observation API는 무엇이고, 그냥 Timer와 무엇이 다른가요?

Observation은 코드의 한 구간을 한 번만 계측하면 등록된 핸들러들이 지표, trace, 로그 상관관계를 각각 만들어 내는 API다. Timer는 지표 하나만 만든다. 스프링 MVC 요청, `RestClient`, `WebClient` 같은 프레임워크 계측도 Observation으로 돼 있어서, 같은 이름과 키-값이 지표 태그와 span 속성으로 함께 나온다. 직접 계측할 때도 Observation을 쓰면 trace에 자식 span이 자동으로 생긴다.

### lowCardinalityKeyValue와 highCardinalityKeyValue는 어떻게 다르게 쓰이나요?

낮은 카디널리티 값은 지표 태그와 span 속성 양쪽에 들어가고, 높은 카디널리티 값은 span 속성에만 들어간다. 지표 태그는 값 하나하나가 별도 시계열이 되기 때문에 주문 ID처럼 끝없이 늘어나는 값을 넣으면 시계열이 폭증한다. 실험에서도 `order.id`는 `/actuator/prometheus`에 없었고 span에만 있었다. 값의 개수를 미리 셀 수 있으면 low, 아니면 high로 둔다.

### RestClient 호출 지표의 uri 태그가 100개에서 멈추고 경고가 나왔습니다. 왜 그런가요?

URI를 템플릿 없이 문자열로 이어 붙여서 실제 경로가 태그로 들어갔기 때문이다. 부트는 `http.client.requests`와 `http.server.requests`의 uri 태그에 기본 상한 100을 걸어 두고, 넘으면 `MaximumAllowableTagsMeterFilter`가 경고를 남기고 그 뒤 값은 지표로 만들지 않는다. `uri("/payments/{id}", id)`처럼 템플릿과 변수를 나눠 넘기면 한 줄로 묶인다. 직접 만든 카운터에는 이 상한이 없어서 더 위험하다.

### percentiles-histogram을 켜면 비용이 얼마나 늘어나나요?

Timer 하나의 태그 조합마다 `_count`, `_sum`, `_max` 3줄이던 것이 기본 칸 69줄(+Inf 포함)이 더해져 72줄이 된다. 여기에 태그 조합 수와 Pod 수가 곱해지니, 엔드포인트 20개에 Pod 30개면 지표 하나가 수십만 시계열이 될 수 있다. 그래서 필요한 지표에만 켜고, 목표 응답 시간이 정해져 있으면 `slo` 설정으로 경계 몇 개만 칸으로 둔다. 앱 안에서 분위수를 계산하는 `percentiles`는 Pod끼리 합칠 수 없어 잘 쓰지 않는다.

### 스프링 부트에서 trace를 켰는데 Tempo에서 일부만 보입니다. 무엇부터 확인하나요?

먼저 `management.tracing.sampling.probability`를 본다. 기본값이 0.1이라 열에 하나만 내보낸다. 로그에는 샘플링과 상관없이 trace ID가 찍히니 로그에서 찾은 ID가 Tempo에 없는 것도 이 때문이다. `traceparent` 헤더 끝의 플래그가 01이나 03이면 샘플링된 것이고 00이나 02면 아니다. 그다음 OTLP 엔드포인트 설정 이름(4.0에서 `management.opentelemetry.tracing.export.otlp.endpoint`로 바뀜)과 Collector 쪽 샘플링을 확인한다.

### 서비스 사이에 trace가 이어지지 않고 끊깁니다. 흔한 원인은?

호출하는 쪽이 `traceparent` 헤더를 넣지 않은 경우가 가장 흔하다. 스프링에서는 자동 설정된 `RestClient.Builder`나 `WebClient.Builder`를 주입받아야 Observation이 붙어 헤더가 들어가고, `RestClient.create()`나 직접 만든 HTTP 클라이언트는 빠진다. 비동기 실행기로 넘긴 작업에서 문맥이 전달되지 않는 경우, 중간 프록시가 헤더를 지우는 경우도 있다. 받는 쪽 로그에 `traceparent`를 찍어 보면 어디서 끊겼는지 바로 보인다.

### exemplar는 무엇이고, 스프링 부트에서 보려면 무엇이 필요한가요?

히스토그램 칸마다 그 칸에 들어간 요청 하나의 trace ID를 붙여 둔 것으로, 지표의 튄 점에서 해당 trace로 바로 건너가게 해 준다. 부트에서는 tracing과 히스토그램을 함께 켜면 붙고, 기본으로 샘플링된 trace만 exemplar가 된다. OpenMetrics 형식으로 긁어야 보이고, Prometheus는 exemplar 저장 기능을 켜야 받는다. Grafana 패널에서 exemplar를 켜고 Tempo 데이터 소스와 연결하면 점을 눌러 trace를 연다.

### 모든 지표에 서비스 이름을 붙이려면 어떻게 하나요?

`management.metrics.tags.application=${spring.application.name}`처럼 공통 태그를 준다. 기본으로는 붙지 않아서, 같은 Prometheus에 여러 서비스가 모이면 같은 이름의 JVM 지표를 구분할 수 없다. 쿠버네티스에서는 Prometheus가 `pod`, `namespace` 같은 대상 태그를 따로 붙이지만, 커뮤니티 대시보드들은 `application` 태그를 기대하는 경우가 많다. 대시보드가 비어 있으면 이 태그 이름부터 맞춘다.
