[Climbing Stairs](https://leetcode.com/problems/climbing-stairs/)는 LeetCode 70번이고 동적 계획법(DP)을 처음 배울 때 거의 항상 첫 문제로 나온다. 풀이 자체는 다섯 줄이면 끝나서, 면접에서 이 문제가 나오면 답보다 그다음 대화가 길다. "재귀로 짜면 왜 느린가", "공간을 줄일 수 있나", "n이 10^18이면?", "한 번에 1~3칸이면?", "Java에서 n이 46이면?" 같은 질문이 차례로 붙는다.

DP의 일반론(상태 정의, 메모이제이션과 타뷸레이션의 차이, 문제가 DP인지 알아보는 법)은 [동적 계획법 글](/posts/dynamic-programming)에 정리했고, 그 글에서 계단 오르기는 짧게만 다뤘다. 이 글은 이 한 문제로 일곱 가지 풀이를 놓고, 느린 것에서 빠른 것으로 넘어갈 때마다 무엇이 바뀌는지 본다. 재귀 호출과 콜 스택은 [재귀와 백트래킹 글](/posts/recursion-backtracking)에, 복잡도 표기는 [Big O 글](/posts/big-o-notation)에 있다. 문제를 푸는 전체 순서는 [LeetCode 공부 가이드](/posts/leetcode-study-guide)에 있다. 코드는 Node.js 22, Python 3, Java 21에서 직접 돌렸다.

## 한 칸 또는 두 칸씩 오르는 방법의 수

계단이 `n`칸 있다. 한 번 움직일 때 1칸이나 2칸을 오를 수 있다. 바닥에서 출발해 정확히 `n`번째 칸에 도착하는 서로 다른 방법의 수를 돌려준다. "1칸 후 2칸"과 "2칸 후 1칸"은 순서가 다르니 다른 방법으로 센다.

제약은 `n`이 1 이상 45 이하라는 것 하나다. 이 45라는 숫자가 이상하게 딱 떨어지는데, 이유가 있다. 45칸의 답은 1,836,311,903이고 46칸의 답은 2,971,215,073이다. 32비트 부호 있는 정수의 최댓값이 2,147,483,647이라서, 46부터는 Java `int`에 담기지 않는다. 문제를 만든 쪽이 `int` 반환형을 유지하려고 45에서 끊었다. 뒤에서 Java 코드를 볼 때 이 숫자를 다시 만난다.

`n`이 작으니 O(n)이면 충분하고, 지수 시간 풀이만 피하면 된다. 다만 면접에서는 "n이 엄청 크면"으로 꼭 넘어가니 O(log n) 풀이까지 알아 둔다.

## 4칸짜리 계단을 손으로 세 본다

4칸이면 방법을 모두 적을 수 있다.

```text
1 + 1 + 1 + 1
1 + 1 + 2
1 + 2 + 1
2 + 1 + 1
2 + 2
```

다섯 가지다. 이렇게 늘어놓고 보면 규칙이 하나 보인다. 마지막 걸음이 1인 줄(위의 세 줄 중 `…+1`로 끝나는 것)과 2인 줄로 나눠 보자.

- 마지막이 1로 끝나는 줄: `1+1+1+1`, `1+2+1`, `2+1+1`. 마지막 1을 떼면 3칸을 오르는 방법이 남는다. 3칸을 오르는 방법은 3가지다.
- 마지막이 2로 끝나는 줄: `1+1+2`, `2+2`. 마지막 2를 떼면 2칸을 오르는 방법이 남는다. 2가지다.

3 + 2 = 5. 4칸에 오는 방법은 "3칸에 와서 한 칸 더"와 "2칸에 와서 두 칸 더"로 빠짐없이, 겹침 없이 나뉜다. 마지막 걸음이 1이면서 동시에 2일 수는 없으니 겹치지 않고, 마지막 걸음은 1 아니면 2니까 빠지는 것도 없다. 이 "마지막 걸음으로 나누기"가 이 문제의 전부다.

말로 쓰면 이렇다. `ways(i)`를 "i번째 칸에 정확히 도착하는 방법의 수"라고 정하면

```text
ways(i) = ways(i - 1) + ways(i - 2)
ways(0) = 1   (출발점에 서 있는 방법: 아무것도 안 하기, 한 가지)
ways(1) = 1   (1칸 한 번)
```

`ways(0) = 1`이 어색하게 느껴질 수 있다. 0칸을 오르는 방법이 하나라니. 이렇게 두는 이유는 `ways(2) = ways(1) + ways(0) = 2`가 맞아떨어지게 하기 위해서다. 2칸은 "1+1"과 "2" 두 가지인데, "2" 한 걸음짜리가 바로 "0번 칸에서 두 칸 올라온 경우"다. 0번 칸에 서 있는 상태를 한 가지로 세야 이 경우가 빠지지 않는다. 빈 수열을 한 가지로 세는 것, 조합에서 0!이 1인 것과 같은 약속이다.

이 점화식은 피보나치 수열과 같다. 피보나치를 F(1) = F(2) = 1로 두면 `ways(n) = F(n + 1)`이다. 1, 2, 3, 5, 8, 13, 21… 이 수열을 알아보는 순간 풀이 대부분이 피보나치 계산법으로 바뀐다.

## 점화식 그대로 재귀로 짠다

점화식을 그대로 코드로 옮기면 이렇게 된다.

```js
function climbStairs(n) {
  if (n <= 1) return 1;                         // 0칸, 1칸은 방법이 하나
  return climbStairs(n - 1) + climbStairs(n - 2); // 마지막 걸음이 1인 경우 + 2인 경우
}
```

맞는 답을 낸다. 그런데 `n = 45`를 넣으면 한참 동안 돌아오지 않는다. 호출 수를 세서 시간과 함께 찍어 봤다.

```text
naive 20 calls 21891 0.2ms
naive 30 calls 2692537 24.1ms
naive 35 calls 29860703 266.5ms
naive 40 calls 331160281 3033.8ms
```

5칸 늘 때마다 호출이 약 11배씩 는다. 40칸에서 3초, 45칸이면 호출이 36억 번을 넘어서 30초 넘게 걸린다. 호출 수는 정확히 `2 × ways(n) - 1`이다. 답이 크면 호출도 그만큼 크다. 결국 이 함수는 답을 1씩 더해서 만들어 내는 셈이다(바닥 사례가 1을 돌려주고, 그걸 더하기만 하니까).

이 풀이의 문제는 같은 질문을 계속 다시 묻는다는 것 하나다. 서로 다른 질문은 `f(0)`부터 `f(n)`까지 n+1개밖에 없다. 그러면 답을 한 번 구할 때마다 적어 두면 된다.

## 한 번 구한 칸은 적어 둔다

재귀 구조는 그대로 두고, 답을 적어 두는 장부(메모)만 붙인다. 같은 칸을 다시 물으면 계산하지 않고 장부에서 읽는다. 이걸 메모이제이션 또는 탑다운(top-down) DP라고 부른다. 큰 문제에서 출발해 필요한 작은 문제로 내려가기 때문이다.

```js
function climbStairs(n) {
  const memo = new Map();               // i -> i번째 칸에 오는 방법의 수
  function go(i) {
    if (i <= 1) return 1;
    if (memo.has(i)) return memo.get(i); // 이미 구한 칸이면 바로 읽는다
    const v = go(i - 1) + go(i - 2);
    memo.set(i, v);                      // 처음 구한 답을 적는다
    return v;
  }
  return go(n);
}
```

이제 `go(i)`의 본문은 i마다 딱 한 번만 실행된다. 두 번째부터는 `memo.has`에서 돌아간다. 본문 실행이 n번, 각 실행이 O(1)이니 시간은 O(n)이다. 위 호출 나무로 보면 오른쪽 가지 `f(3)`과 그 아래가 통째로 잘려 나가고 왼쪽 등뼈 한 줄만 남는다.

공간은 장부 O(n)과 콜 스택 O(n)이다. 콜 스택이 n 깊이까지 내려간다는 건 실무에서 문제가 된다. 이 문제는 n이 45라 상관없지만, Python은 기본 재귀 한도가 1000이라 `n = 5000`이면 `RecursionError: maximum recursion depth exceeded`가 난다. 실제로 `lru_cache`를 붙인 재귀 함수로 `ways(5000)`을 부르니 이 에러가 났다. JavaScript도 같은 탑다운 코드를 Node.js 22 기본 설정으로 돌렸더니 n = 5000은 통과하고 n = 10000에서 `RangeError: Maximum call stack size exceeded`가 났다. 정확한 한계는 프레임 크기와 엔진 설정에 따라 다르다.

장부를 `Map` 대신 배열로 써도 된다. 키가 0부터 n까지 연속된 정수라서 배열이 더 빠르고 단순하다. `Map`을 쓴 건 "아직 안 구했다"와 "구했는데 값이 0이다"를 `has`로 구분하는 습관을 보여 주려고서다. 이 문제는 답이 0인 칸이 없어서 배열에 `0`을 "안 구함"으로 써도 되지만, 답이 0일 수 있는 문제([Coin Change](/posts/leetcode-coin-change)의 불가능 표시처럼)에서 같은 습관을 쓰면 틀린다.

재귀를 없애려면 방향을 뒤집는다.

## 바닥부터 표를 채운다

탑다운은 "n을 구하려면 n-1과 n-2가 필요하다"에서 출발했다. 거꾸로 "0과 1을 알면 2를 알고, 1과 2를 알면 3을 안다"로 아래에서 위로 채우면 재귀가 필요 없다. 이걸 타뷸레이션 또는 바텀업(bottom-up) DP라고 부른다.

```js
function climbStairs(n) {
  const dp = new Array(n + 1).fill(0); // dp[i]: i번째 칸에 오는 방법의 수
  dp[0] = 1;
  dp[1] = 1;
  for (let i = 2; i <= n; i++) {
    dp[i] = dp[i - 1] + dp[i - 2];     // 한 칸 아래에서 + 두 칸 아래에서
  }
  return dp[n];
}
```

`dp[i]`를 채우는 순간 `dp[i-1]`과 `dp[i-2]`는 이미 채워져 있다. 반복문이 작은 i부터 돌기 때문이다. 바텀업에서 가장 신경 쓸 것은 이 "채우는 순서"다. 점화식이 참조하는 칸이 항상 먼저 채워지도록 순서를 고른다. 이 문제는 앞의 두 칸만 보니 왼쪽에서 오른쪽이면 된다.

시간 O(n), 공간 O(n)이다. 탑다운과 점근적으로 같지만 함수 호출이 없고 콜 스택도 쓰지 않는다. 탑다운이 나은 경우도 있다. 모든 작은 문제가 필요하지 않을 때(일부 칸만 실제로 방문될 때) 탑다운은 방문한 칸만 계산한다. 이 문제는 0부터 n까지 모든 칸이 필요해서 그 장점이 없다.

## 손가락 두 개만 짚고 올라간다

점화식은 바로 앞 두 칸만 본다. 그러면 배열 전체를 들고 있을 이유가 없다. 변수 두 개, `prev`(두 칸 아래)와 `cur`(한 칸 아래)만 들고 한 칸씩 밀어 올린다. 이 풀이가 기본 답이다.

```js
function climbStairs(n) {
  let prev = 1; // i-2번째 칸에 오는 방법 수 (처음엔 0번 칸)
  let cur = 1;  // i-1번째 칸에 오는 방법 수 (처음엔 1번 칸)
  for (let i = 2; i <= n; i++) {
    const next = prev + cur; // i번째 칸
    prev = cur;              // 한 칸씩 위로 민다
    cur = next;
  }
  return cur;                // n = 1이면 반복문을 안 돌고 1이 나온다
}
```

6칸에서 두 변수가 움직이는 모습이다.

갱신 순서를 틀리기 쉽다. `prev = cur; cur = prev + cur;`로 쓰면 두 번째 줄의 `prev`가 이미 바뀐 값이라 `cur`가 `2 × cur`가 된다. `n = 4`에서 1 → 2 → 4 → 8로 가서 5가 아니라 8이 나온다. 임시 변수 `next`를 쓰거나, JavaScript라면 구조 분해 대입 `[prev, cur] = [cur, prev + cur]`로 오른쪽을 먼저 다 계산하게 한다. 구조 분해는 반복마다 작은 배열을 만들지만 이 크기에선 차이가 없다.

이 "바로 앞 k개만 본다면 k개만 들고 다닌다"는 공간 줄이기는 1차원 DP에서 계속 나온다. [House Robber](/posts/leetcode-house-robber)도 같은 두 변수 모양이다.

O(n)이면 이 문제의 제약에서는 충분하다. 그런데 면접관이 "n이 10^18이면?"이라고 물으면 반복문 10^18번은 끝나지 않는다.

## 행렬을 거듭제곱하면 log n번에 끝난다

피보나치 점화식은 선형이라 행렬 곱 한 번으로 쓸 수 있다.

```text
| ways(i+1) |   | 1 1 |   | ways(i)   |
| ways(i)   | = | 1 0 | × | ways(i-1) |
```

위 줄은 `ways(i+1) = ways(i) + ways(i-1)`이고, 아래 줄은 `ways(i)`를 한 칸 아래로 그대로 옮기는 것이다. 이 행렬을 M이라 하면 한 칸 오를 때마다 M을 한 번 곱한다. 그러면 n칸은 M을 n번 곱한 Mⁿ이고, 거듭제곱은 지수를 반으로 쪼개면 O(log n)번의 곱셈으로 구할 수 있다(M⁸ = ((M²)²)²). 계산해 보면 Mⁿ의 왼쪽 위 칸이 `ways(n)`이다.

```js
function mul(A, B) { // 2x2 행렬 곱
  return [
    [A[0][0] * B[0][0] + A[0][1] * B[1][0], A[0][0] * B[0][1] + A[0][1] * B[1][1]],
    [A[1][0] * B[0][0] + A[1][1] * B[1][0], A[1][0] * B[0][1] + A[1][1] * B[1][1]],
  ];
}

function climbStairs(n) {
  let result = [[1, 0], [0, 1]]; // 단위 행렬
  let base = [[1, 1], [1, 0]];   // M
  let e = n;
  while (e > 0) {
    if (e & 1) result = mul(result, base); // 지수의 이 비트가 1이면 곱한다
    base = mul(base, base);                // M, M², M⁴, M⁸ …
    e >>= 1;
  }
  return result[0][0];
}
```

`n = 6`이면 6은 이진수 110이라 M² × M⁴를 곱한다. 제곱 세 번과 결과에 곱하기 두 번, 행렬 곱이 다섯 번이다. 반복문 버전이 덧셈 다섯 번으로 끝나는 것과 비교하면 이 크기에서는 오히려 느리지만, n이 10^18이면 60번 남짓의 행렬 곱으로 끝난다. 시간 O(log n), 공간 O(1)이다. 2×2 행렬 곱 하나가 곱셈 8번이라 상수가 크다.

이 풀이가 실제로 쓸모 있으려면 답을 어떤 수로 나눈 나머지로 물어야 한다. ways(10^18)은 자릿수가 2 × 10^17개쯤 되는 수라 그대로는 어디에도 못 담는다. 그래서 "1,000,000,007로 나눈 나머지를 구하라"는 조건이 함께 붙고, 그러면 곱셈마다 나머지를 취한다. JavaScript에서는 두 수의 곱이 2^53을 넘으면 정밀도가 깨지니 `BigInt`로 곱하거나 곱셈을 쪼개야 한다. 이건 뒤의 변형 절에서 다시 짚는다.

## 공식 하나로 바로 구한다면

피보나치에는 닫힌 공식(비네 공식)이 있다.

```text
F(k) = (φ^k - ψ^k) / √5,   φ = (1 + √5) / 2,   ψ = (1 - √5) / 2
ways(n) = F(n + 1)
```

```js
function climbStairs(n) {
  const s5 = Math.sqrt(5);
  const phi = (1 + s5) / 2, psi = (1 - s5) / 2;
  return Math.round((phi ** (n + 1) - psi ** (n + 1)) / s5);
}
```

이 문제 범위(n ≤ 45)에서는 정확한 답을 낸다. 그런데 부동소수점이라 n이 커지면 틀린다. 1부터 올려 가며 `BigInt`로 계산한 정확한 값과 비교했더니 n = 70에서 처음 어긋났다.

```text
binet first wrong at 70 308061521170130 308061521170129n
```

참고로 덧셈만 하는 두 변수 풀이도 `Number`로는 n = 78에서 처음 틀린다(`14472334024676220` 대 실제 `14472334024676221`). 답이 2^53(약 9 × 10^15)을 넘기 때문이다. 공식은 그보다 먼저, φ의 거듭제곱에서 오차가 쌓이면서 무너진다.

시간은 `**` 연산이 상수 시간이라 보면 O(1)이고, 정확히는 거듭제곱 구현에 따라 O(log n)이다. 면접에서는 "닫힌 공식이 있지만 실수 오차 때문에 큰 n에서는 쓰지 않는다"까지 말하면 충분하다. 피보나치의 성질을 아는지 보여 주는 정도의 풀이다.

## 2칸 걸음을 몇 번 쓰나로 세기

DP를 전혀 안 쓰는 길도 있다. 2칸 걸음을 k번 쓴다고 정하면 1칸 걸음은 `n - 2k`번이고, 전체 걸음 수는 `n - k`번이다. 그 `n - k`개 자리 중 어디에 2칸 걸음 k개를 놓을지 고르는 경우의 수는 이항계수 C(n - k, k)다. k를 0부터 n/2까지 더하면 답이다.

4칸이면 k = 0일 때 C(4, 0) = 1(1+1+1+1), k = 1일 때 C(3, 1) = 3(2가 세 자리 중 하나), k = 2일 때 C(2, 2) = 1(2+2). 합이 5다.

```js
function climbStairs(n) {
  let total = 0;
  for (let k = 0; 2 * k <= n; k++) {   // 2칸 걸음 개수
    const m = n - k;                   // 전체 걸음 수
    let c = 1;                         // C(m, k)를 곱셈으로 쌓는다
    for (let j = 1; j <= k; j++) c = (c * (m - k + j)) / j;
    total += Math.round(c);
  }
  return total;
}
```

`c`는 j번째 곱셈 뒤에 C(m - k + j, j)가 되고 이 값은 항상 정수라서 나눗셈이 딱 떨어진다. 이항계수를 쌓는 데 O(k), 이걸 n/2번 하니 시간 O(n²), 공간 O(1)이다. 두 변수 풀이보다 느리지만, "같은 답을 조합으로도 설명할 수 있다"는 걸 보여 준다. 면접관이 "DP 말고 다른 방법은?"이라고 물을 때 꺼낼 수 있다. 걸음 종류가 1, 2로 고정일 때만 이렇게 깔끔하다.

## Python과 Java로 옮길 때

두 변수 풀이를 옮긴다.

```python
class Solution:
    def climbStairs(self, n: int) -> int:
        prev, cur = 1, 1          # 0번 칸, 1번 칸에 오는 방법 수
        for _ in range(2, n + 1):
            prev, cur = cur, prev + cur
        return cur
```

Python은 튜플 대입 `prev, cur = cur, prev + cur`의 오른쪽을 먼저 다 계산하고 나서 왼쪽에 넣는다. 그래서 임시 변수가 필요 없다. 정수는 크기 제한이 없어서 `climbStairs(100)`도 `573147844013817084101`을 정확히 낸다. 탑다운으로 쓰려면 `functools.lru_cache`(또는 3.9부터 `cache`)를 붙이는 게 가장 짧지만, 앞에서 본 재귀 한도 1000 때문에 큰 n에서는 반복문이 안전하다. `sys.setrecursionlimit`로 한도를 올릴 수는 있지만 C 스택이 먼저 터질 수 있어 근본 해결이 아니다.

```java
class Solution {
    public int climbStairs(int n) {
        int prev = 1, cur = 1;           // 0번 칸, 1번 칸에 오는 방법 수
        for (int i = 2; i <= n; i++) {
            int next = prev + cur;
            prev = cur;
            cur = next;
        }
        return cur;
    }
}
```

Java는 `int`가 32비트라서 n = 46에서 넘친다. 같은 코드에 46을 넣어 보면 이렇게 나온다.

```text
1 8 1836311903 -1323752223
2971215073
```

첫 줄의 마지막 값이 `int`로 계산한 n = 46이고, 음수가 됐다. Java는 정수 오버플로에서 예외를 던지지 않고 조용히 돌아 감는다. 두 번째 줄은 같은 계산을 `long`으로 한 값이다. 문제 제약이 45까지라 `int`로 충분하지만, 면접에서 "46이면?"을 물으면 `long`, 그 이상이면 `BigInteger`나 나머지 연산으로 바꾼다고 답한다. 넘치는 순간을 잡고 싶으면 `Math.addExact`가 `ArithmeticException`을 던진다.

JavaScript는 `Number`가 실수라 넘쳐도 음수가 되지는 않지만, 앞에서 본 대로 n = 78부터 조용히 틀린 값을 낸다. 정확해야 하면 `BigInt`로 바꾼다(`let prev = 1n, cur = 1n`). 셋 중 조용히 틀리는 방식이 언어마다 다르다는 점을 기억해 둔다.

## 일곱 풀이를 나란히 놓으면

| 풀이 | 시간 | 추가 공간 | 언제 고르나 |
|---|---|---|---|
| 점화식 그대로 재귀 | O(φⁿ) | O(n) 스택 | 점화식을 확인할 때만. 제출하면 시간 초과 |
| 탑다운 메모 | O(n) | O(n) 장부 + O(n) 스택 | 점화식에서 바로 옮기기 쉽다. 일부 칸만 필요한 문제에서 강하다 |
| 바텀업 표 | O(n) | O(n) | 표 전체가 필요할 때(경로 복원, 여러 질문) |
| 두 변수 | O(n) | O(1) | 기본 답 |
| 행렬 거듭제곱 | O(log n) | O(1) | n이 매우 크고 나머지를 물을 때 |
| 비네 공식 | O(1)~O(log n) | O(1) | 범위가 작을 때 성질을 보여 주는 용도. n ≥ 70에서 틀린다 |
| 조합으로 세기 | O(n²) | O(1) | DP 말고 다른 설명을 요구받을 때 |

면접에서는 재귀 → 메모 → 표 → 두 변수 순서로 말하며 각 단계에서 무엇을 없앴는지(중복 계산, 콜 스택, 쓰지 않는 칸)를 짚고, 시간이 남으면 행렬 거듭제곱을 언급하는 흐름이 자연스럽다.

## 틀리기 쉬운 자리

### dp[1]과 dp[2]를 바닥으로 두는 경우

`dp[0]`의 의미가 어색해서 바닥을 1칸, 2칸으로 잡는 코드가 흔하다.

```js
function climbStairs(n) {
  const dp = [];
  dp[1] = 1;
  dp[2] = 2;
  for (let i = 3; i <= n; i++) dp[i] = dp[i - 1] + dp[i - 2];
  return dp[n];
}
```

이 문제는 n ≥ 1이라 통과한다. 그런데 이 코드에 0을 넣으면 `undefined`가 나온다. 비슷한 문제에서 n = 0이 허용되면(빈 계단을 오르는 방법은 1) 바로 틀린다. 크기 `n + 1` 배열을 만들고 `dp[2] = 2`를 넣는 코드는 n = 1일 때 배열 밖에 쓰는데, JavaScript는 조용히 넘어가지만 Java와 C++에서는 `ArrayIndexOutOfBoundsException`이나 정의되지 않은 동작이 된다. `dp[0] = dp[1] = 1`로 두면 바닥이 하나로 정리되고 이런 경계 처리가 사라진다.

### 갱신 순서를 거꾸로 쓰는 경우

두 변수 풀이에서 `prev = cur; cur = prev + cur;`로 쓰면 n = 4에 8이 나온다. 앞에서 짚은 대로 오른쪽을 먼저 다 계산해야 한다.

### 조합(순서 무시)으로 세는 경우

"1+2"와 "2+1"을 같은 방법으로 세면 답이 달라진다. 이 문제는 순서가 다르면 다른 방법이다. 순서를 무시하는 문제는 [Coin Change II](/posts/leetcode-coin-change-ii)처럼 반복문의 바깥과 안쪽을 바꿔서 푼다. 계단 오르기를 "동전 1, 2로 n을 만드는 방법"으로 바꿔 생각하면, 이 문제는 순서를 세는 쪽(순열)이다.

### 재귀에 메모를 붙였는데도 느린 경우

장부를 함수 안에서 매 호출마다 새로 만들면 아무것도 기억하지 못한다.

```js
function go(i) {
  const memo = new Map();   // 호출마다 새 장부. 메모가 없는 것과 같다
  if (i <= 1) return 1;
  if (memo.has(i)) return memo.get(i);
  ...
}
```

장부는 바깥 함수(또는 클로저)에 한 번만 만든다. LeetCode에서 클래스 필드에 장부를 두면 테스트 케이스끼리 장부가 공유되는데, 이 문제는 답이 n에만 달려 있어 공유해도 맞지만 입력이 바뀌는 문제(`cost` 배열 같은)에서는 이전 케이스의 값이 섞여 틀린다.

## 면접관이 조건을 바꾸면

### 한 번에 1~3칸, 또는 1~k칸을 오를 수 있다면

마지막 걸음이 1, 2, 3 중 하나니 `ways(i) = ways(i-1) + ways(i-2) + ways(i-3)`이다(트리보나치). 1~k칸이면 앞 k칸의 합이다. 매번 k개를 더하면 O(nk)지만, 앞 k칸의 합을 창처럼 들고 다니면 O(n)이 된다. 새 칸을 더하고 k칸 전 칸을 빼는 [슬라이딩 윈도](/posts/sliding-window-pattern)다.

```js
function climbK(n, k) {
  const dp = new Array(n + 1).fill(0);
  dp[0] = 1;
  let win = 1;                         // dp[i-k] … dp[i-1]의 합
  for (let i = 1; i <= n; i++) {
    dp[i] = win;
    win += dp[i];                      // 새 칸이 창에 들어온다
    if (i - k >= 0) win -= dp[i - k];  // k칸 전 칸이 창에서 나간다
  }
  return dp[n];
}
```

```text
k3 [ 1, 2, 4, 7, 13, 24 ] k2 [ 1, 2, 3, 5, 8, 13 ]
```

k = 2일 때 원래 문제와 같은 값이 나오는 걸로 검산했다.

### 걸음 크기가 [1, 3, 5]처럼 주어진다면

마지막 걸음이 주어진 크기 중 하나니 `ways(i) = Σ ways(i - s)`(s는 걸음 크기, `i - s ≥ 0`인 것만)다. 걸음 종류가 m개면 O(nm)이다. 바깥이 칸, 안쪽이 걸음 크기인 반복문이고, 이 순서가 "순서를 세는" 반복문이다.

### 밟으면 안 되는 칸이 있다면

그 칸의 `dp`를 0으로 고정한다. 그 칸에 도착하는 방법이 없으니 그 칸을 거쳐 가는 방법도 자동으로 사라진다.

### 칸마다 비용이 있고 최소 비용을 묻는다면

LeetCode 746 Min Cost Climbing Stairs다. "방법의 수를 더한다"가 "두 갈래 중 싼 쪽을 고른다"로 바뀐다. `cost(i) = min(cost(i-1) + c[i-1], cost(i-2) + c[i-2])`. 덧셈이 min으로 바뀌었을 뿐 뼈대가 같다. `[10, 15, 20]`이면 15, `[1, 100, 1, 1, 1, 100, 1, 1, 100, 1]`이면 6이 나왔다.

### n이 10^18이고 10^9 + 7로 나눈 나머지를 묻는다면

행렬 거듭제곱에 나머지 연산을 붙인다. 걸음이 1~k칸이면 k×k 행렬이 되고 O(k³ log n)이다. JavaScript에서는 10^9 + 7 미만 두 수의 곱이 약 10^18이라 2^53을 넘으니 `BigInt`로 곱한다.

### 방법을 전부 나열하라면

개수가 아니라 목록이 필요하면 DP로는 줄일 수 없다. 답의 크기 자체가 지수라서 [백트래킹](/posts/recursion-backtracking)으로 걸음을 하나씩 붙였다 떼며 모은다. n = 4면 `1+1+1+1`, `1+1+2`, `1+2+1`, `2+1+1`, `2+2`가 나온다. 시간은 출력 크기에 비례한다.

비슷한 문제로는 Fibonacci Number(509), Min Cost Climbing Stairs(746), N-th Tribonacci Number(1137), 그리고 문자열 버전인 [Decode Ways](/posts/leetcode-decode-ways)가 있다. Decode Ways는 "한 글자 또는 두 글자씩 끊기"라서 계단 오르기에 "두 칸 걸음이 허용되는 조건"이 붙은 문제다. 집을 하나 건너뛰는 [House Robber](/posts/leetcode-house-robber)도 같은 두 변수 뼈대다.

## 면접에서 나올 만한 질문

### 이 문제가 왜 피보나치와 같은가요?

마지막 걸음이 1칸이거나 2칸이기 때문이다. n번째 칸에 오는 방법은 n-1칸에 온 뒤 1칸 오른 경우와 n-2칸에 온 뒤 2칸 오른 경우로 겹침 없이 나뉘어서 `ways(n) = ways(n-1) + ways(n-2)`가 된다. 바닥이 `ways(0) = ways(1) = 1`이라 피보나치 수열을 한 칸 민 값, 즉 F(n+1)이다.

### 단순 재귀가 왜 느린가요?

같은 칸을 여러 번 다시 계산하기 때문이다. 호출 나무의 노드 수가 `2 × ways(n) - 1`이라 답의 크기만큼, 즉 O(φⁿ)으로 늘어난다. 실제로 n = 40에서 호출이 3억 번을 넘고 3초가 걸렸다. 서로 다른 질문은 n+1개뿐이라 답을 기억하면 O(n)이 된다.

### 메모이제이션과 바텀업 중 무엇을 쓰나요?

이 문제는 바텀업, 그중에서도 두 변수 풀이를 쓴다. 0부터 n까지 모든 칸이 필요하니 탑다운의 "필요한 칸만 계산" 장점이 없고, 재귀 깊이가 n이라 큰 n에서 스택이 넘칠 위험만 남는다. 탑다운은 점화식에서 옮기기 쉽고 상태 공간 일부만 방문하는 문제에서 고른다.

### 공간을 O(1)로 줄일 수 있나요?

있다. 점화식이 바로 앞 두 칸만 보니 변수 두 개만 들고 한 칸씩 민다. 갱신할 때 새 값을 먼저 계산한 뒤 옮겨야 하고, 순서를 바꾸면 n = 4에서 8 같은 틀린 값이 나온다.

### n이 아주 크면 어떻게 하나요?

행렬 [[1,1],[1,0]]의 n제곱을 분할 정복으로 구하면 O(log n)이다. 이때 답이 너무 커서 보통 10^9 + 7로 나눈 나머지를 묻고, 곱셈마다 나머지를 취한다. 비네 공식도 있지만 부동소수점 오차로 n = 70에서 이미 틀려서 정확한 답에는 쓰지 않는다.

### Java에서 n이 46 이상이면 무엇이 문제인가요?

`int` 범위를 넘어 음수가 나온다. 46칸의 답 2,971,215,073이 `int` 최댓값 2,147,483,647보다 크고, Java는 넘쳐도 예외 없이 돌아 감아서 -1,323,752,223을 낸다. `long`은 n = 91까지 담고, 그 이상은 `BigInteger`나 나머지 연산을 쓴다. 문제 제약이 45인 이유가 이것이다.

### 한 번에 1~k칸을 오를 수 있으면 복잡도가 어떻게 되나요?

그대로 더하면 칸마다 k개를 더해 O(nk)다. 앞 k칸의 합을 슬라이딩 윈도로 유지하면 새 칸을 더하고 k칸 전을 빼는 것만으로 O(n) 시간, O(n) 공간이 된다. 창 안의 값만 원형 버퍼로 들고 있으면 공간도 O(k)로 줄어든다.
