어제까지 초록이던 CI가 오늘 아침 빨갛다. 아무도 코드를 안 고쳤다. 로그를 따라가 보니 날짜를 찍는 라이브러리가 1.5.0에서 1.5.1로 올라 있었고, `2026-10-21`이던 출력이 `10/21/2026`으로 바뀌어 있다. 수 버전만 올랐는데 왜 결과가 달라졌을까. 그리고 `package.json`에는 분명 `^1.4.2`라고 적었는데, 그건 어디까지 받아도 된다는 뜻이었을까.

버전 번호는 숫자 세 개짜리 약속이다. 이 글은 그 약속(Semantic Versioning, 줄여서 SemVer)의 규칙을 정확히 짚고, npm이 그 규칙으로 실제 설치할 버전을 어떻게 고르는지, 특히 0.x에서 캐럿 범위가 왜 한 칸 좁아지는지, 무엇이 깨지는 변경인지, 그리고 버전 번호를 사람이 고르지 않게 하는 릴리스 흐름까지 따라간다.

이 주제의 다른 글: 범위가 여러 패키지 사이에서 부딪혀 설치가 꼬이는 문제는 [의존성 지옥](/posts/dependency-hell)에서, 커밋 규칙과 Git 태그는 [브랜치 전략](/posts/git-branching-strategy#버전-번호와-태그)에서, HTTP API의 버전 관리는 [API 버전 관리](/posts/api-versioning)에서 다룬다. Helm 차트의 범위 규칙(Masterminds/semver)은 [Helm 의존성 글](/posts/helm-dependencies-oci-gitops#차트-버전과-앱-버전)에 있다. 이 글의 규칙은 npm이 쓰는 node-semver 기준이고, 둘은 사전 배포 버전을 다루는 부분이 조금 다르다.

실습은 Ubuntu 24.04, Node.js 22.22.0, npm 10.9.4, semver 7.8.5에서 했다. 패키지는 로컬에 띄운 사설 npm 레지스트리(Verdaccio 6)에 `@acme/date-fmt` 같은 이름으로 직접 올려 가며 확인했다. 출력은 모두 실제로 돌린 결과이고, 긴 작업 경로만 줄여 적었다.

## 세 숫자에 담긴 약속

SemVer 2.0.0 명세는 버전을 `MAJOR.MINOR.PATCH`로 쓰고, 어느 자리를 올리느냐로 바뀐 내용의 성격을 알린다.

- PATCH(수 버전): 공개 API는 그대로 두고 버그만 고쳤다. 받는 쪽은 아무것도 안 고쳐도 된다.
- MINOR(부 버전): 호환되는 기능을 더했다. 기존 코드는 그대로 돈다. 무언가를 deprecated로 표시하는 것도 여기다.
- MAJOR(주 버전): 호환을 깼다. 받는 쪽이 코드를 고쳐야 할 수 있다.

여기서 기준이 되는 말이 공개 API다. 명세는 "공개 API를 선언하라"고 요구한다. 문서에 적은 함수와 옵션, 타입, 기본값, 지원하는 런타임까지가 약속의 범위다. 무엇이 공개 API인지 정하지 않으면 무엇이 깨는 변경인지도 정할 수 없다.

두 가지 특별한 자리가 있다. `1.0.0`은 "이제 공개 API가 정해졌다"는 선언이다. 그 전의 `0.y.z`는 초기 개발 단계라 명세가 아무것도 약속하지 않는다. 언제든 무엇이든 바뀔 수 있다. 그리고 한 번 내보낸 버전의 내용은 절대 바꾸지 않는다. 고칠 것이 있으면 새 번호로 낸다. npm 레지스트리도 같은 버전 번호로 다시 올리는 것을 막는다(unpublish를 해도 그 번호는 다시 쓸 수 없다).

```bash
node -e 'const s=require("semver"); console.log(s.valid("01.2.3"), s.valid("1.2"), s.valid("v1.2.3"), s.valid("1.2.3-01"), s.valid("1.2.3-0a"))'
```

## 사전 배포 버전은 어떤 순서로 줄을 서나

숫자 세 자리는 왼쪽부터 숫자로 비교한다. 거기까지 같으면 사전 배포 식별자를 비교한다. 규칙은 네 개다. 식별자가 없는 쪽(정식 버전)이 더 크다. 식별자는 점으로 나눠 왼쪽부터 하나씩 비교한다. 둘 다 숫자면 숫자로, 하나라도 문자면 ASCII 순서로 비교하고, 숫자 식별자는 문자 식별자보다 항상 작다. 앞부분이 다 같으면 식별자가 더 많은 쪽이 크다.

명세의 예시를 일부러 섞어 넣고 정렬시켜 봤다.

```bash
# 인자로 받은 버전을 SemVer 순서로 정렬해 출력한다
npx semver 1.0.0 1.0.0-rc.1 1.0.0-alpha 1.0.0-alpha.1 1.0.0-alpha.beta 1.0.0-beta 1.0.0-beta.2 1.0.0-beta.11 1.0.0-rc.10 1.0.0-rc.2
```

```text
1.0.0-alpha
1.0.0-alpha.1
1.0.0-alpha.beta
1.0.0-beta
1.0.0-beta.2
1.0.0-beta.11
1.0.0-rc.1
1.0.0-rc.2
1.0.0-rc.10
1.0.0
```

`beta.11`이 `beta.2` 뒤에, `rc.10`이 `rc.2` 뒤에 왔다. 식별자를 점으로 나눠 숫자는 숫자로 읽었기 때문이다. 만약 `rc10`처럼 점 없이 붙여 썼다면 통째로 문자 식별자라 `rc10 < rc2`가 된다. 사전 배포 번호는 반드시 점으로 떼어 쓴다. 아래 그림은 두 쌍을 비교하는 과정을 한 칸씩 보여 준다.

문자 식별자의 ASCII 순서에는 함정이 하나 있다. 대문자가 소문자보다 앞이라 `1.0.0-RC.1`은 `1.0.0-beta.1`보다 작다. 팀마다 대소문자를 섞어 쓰면 RC가 베타보다 먼저인 이상한 순서가 생긴다. 식별자는 소문자로 통일하는 편이 안전하다.

빌드 메타데이터는 비교에서 빠진다. 그래서 같은 코드를 다시 빌드했다고 `+build.2`를 붙여 다시 올리는 방식은 레지스트리에서 통하지 않는다. 이미 0.4.2가 있는 패키지에 `0.4.2+build.2`를 올려 봤다.

```bash
# package.json의 version을 0.4.2+build.2로 두고 올린다
npm publish --tag old
```


npm이 빌드 메타데이터를 떼어 0.4.2로 고친 뒤 올렸고, 같은 번호가 있으니 레지스트리가 거절했다. 순서를 정할 때도 무시되어 `semver.compare("1.0.0+a", "1.0.0+b")`는 0이다. 메타데이터까지 구분해야 하면 `compareBuild`를 쓴다.

## 캐럿과 물결표가 실제로 여는 범위

`package.json`의 의존성에는 정확한 버전 대신 범위를 적는 경우가 많다. `npm install 패키지`를 하면 기본으로 `^`가 붙은 범위가 저장된다. 범위 문법은 결국 `>=`와 `<` 두 개로 풀린다. `semver.validRange`로 풀어 보면 정확한 경계가 보인다.

```bash
# 범위를 비교 연산자로 풀어 쓴 형태를 출력한다
node -e 'const s=require("semver"); for (const r of ["^1.4.2","~1.4.2","~1","1.x","1.2 - 1.4",">=1.2.0 <1.4.0 || ^2.0.0"]) console.log(r.padEnd(26), "=>", s.validRange(r))'
```

```text
^1.4.2                     => >=1.4.2 <2.0.0-0
~1.4.2                     => >=1.4.2 <1.5.0-0
~1                         => >=1.0.0 <2.0.0-0
1.x                        => >=1.0.0 <2.0.0-0
1.2 - 1.4                  => >=1.2.0 <1.5.0-0
>=1.2.0 <1.4.0 || ^2.0.0   => >=1.2.0 <1.4.0||>=2.0.0 <3.0.0-0
```

캐럿 `^1.4.2`는 "주 버전 1 안에서 1.4.2 이상 아무거나"다. 물결표 `~1.4.2`는 "1.4.x 안에서만"이다. 공백은 AND, `||`는 OR이다. 하이픈 범위 `1.2 - 1.4`는 빠진 자리를 x로 보고 끝을 포함하므로 1.4.x 전체가 들어간다.

위쪽 경계 끝의 `-0`은 무엇일까. `<2.0.0`이라고만 쓰면 `2.0.0-rc.1`은 2.0.0보다 작으니 범위 안에 든다. 주 버전 1을 원했는데 2의 후보 버전이 들어오면 안 되므로 node-semver는 가장 작은 사전 배포 버전인 `2.0.0-0`을 경계로 잡는다. 그 아래의 2.x 후보는 모두 막힌다.

실제 설치에서도 확인해 봤다. 레지스트리에 `@acme/date-fmt`의 1.4.2, 1.4.9, 1.5.0, 1.6.0-beta.1, 2.0.0을 올려 두고 `^1.4.2`로 설치했다.

```bash
# 레지스트리에 있는 버전과 태그
npm view @acme/date-fmt versions
npm view @acme/date-fmt dist-tags
# package.json에 "^1.4.2"를 적고 설치한 뒤 실제로 깔린 버전을 본다
npm install
npm ls
```

```text

{ latest: '2.0.0', next: '1.6.0-beta.1' }

app1@1.0.0 ~/v21/app1

`-- @acme/tiny@0.4.9
```

`^1.4.2`를 만족하는 버전 중 가장 높은 1.5.0이 깔렸다. `latest` 태그는 2.0.0을 가리키지만 범위 밖이라 무시됐고, 1.6.0-beta.1은 사전 배포라 후보에서 빠졌다. `npm outdated`는 이 상황을 세 칸으로 보여 준다.

```bash
# 지금 깔린 것, 범위가 허락하는 최고, 레지스트리 최신을 나란히 본다
```

Wanted가 Current와 같으면 범위 안에서는 최신이라는 뜻이다. Latest로 가려면 범위 자체를 바꿔야 하고, 그건 주 버전을 올리는 일이라 코드 수정이 따를 수 있다. 참고로 `npm outdated`는 낡은 패키지가 하나라도 있으면 종료 코드 1을 돌려준다. CI에서 알림용으로 돌릴 때 이 때문에 단계가 실패로 찍히지 않게 한다.

## 0.x에서 캐럿은 한 칸 더 좁아진다

위 출력에서 `@acme/tiny`는 `^0.4.2`였는데 0.5.0이 있어도 0.4.9에 머물렀다. 0.x 버전에서는 캐럿의 뜻이 달라지기 때문이다. 캐럿은 "가장 왼쪽의 0이 아닌 자리를 고정한다"로 정의된다. 1.4.2에서는 1이, 0.4.2에서는 4가, 0.0.3에서는 3이 고정된다.

```bash
# 0.x와 0.0.x에서 캐럿이 무엇을 허락하는지 직접 거른다
npx semver -r '^0.4.2' 0.4.1 0.4.2 0.4.9 0.5.0 1.0.0
npx semver -r '^0.0.3' 0.0.3 0.0.4 0.1.0
```

```text

0.0.3
```

명세는 0.x에서 아무것도 약속하지 않는데, npm은 왜 이렇게 정했을까. 0.x 라이브러리는 관례상 부 버전을 주 버전처럼 쓴다. 0.4에서 0.5로 가며 API를 깨는 일이 흔하다. 그래서 캐럿이 0.5.0을 자동으로 받으면 사고가 나기 쉽고, npm은 한 칸 좁혀서 받는 쪽을 보호한다.

이 보호에는 두 가지 부작용이 있다. 첫째, 0.x 패키지는 `npm update`를 아무리 돌려도 부 버전이 오르지 않는다. 몇 년째 0.x인 유명 라이브러리를 쓰면 보안 수정이 0.5.x에만 나왔는데 우리는 0.4.x에 묶여 있는 일이 생긴다. `npm outdated`의 Wanted와 Latest가 갈라져 있으면 이 경우다. 둘째, 라이브러리를 만드는 쪽은 0.x에 오래 머물수록 사용자에게 업데이트 비용을 계속 떠넘긴다. 외부 사용자가 생겼다면 1.0.0을 내고 약속을 시작하는 편이 서로 편하다. 명세의 FAQ도 운영에서 쓰이고 있다면 아마 이미 1.0.0이어야 할 것이라고 적어 둔다.

## 범위 안의 사전 배포 버전은 같은 줄에서만

사전 배포 버전에는 별도 규칙이 하나 더 있다. 범위 쪽에 사전 배포 식별자가 없으면 사전 배포 버전은 아예 후보가 되지 않는다. 범위 쪽에 있으면, 숫자 세 자리가 똑같은 사전 배포 버전만 들어온다.

```bash
# ^1.4.2는 1.5.0-beta.1을 받지 않는다 (만족하는 버전이 없으면 종료 코드 1)
npx semver -r '^1.4.2' 1.5.0-beta.1 1.4.2-beta.1; echo "exit $?"
# 범위에 사전 배포가 있으면 같은 1.5.0 줄의 후보만 들어온다
npx semver -r '^1.5.0-beta.1' 1.5.0-beta.1 1.5.0-beta.2 1.5.0 1.6.0-beta.1 1.6.0
# -p(--include-prerelease)를 주면 모든 사전 배포가 후보가 된다
npx semver -p -r '^1.4.2' 1.5.0-beta.1 1.6.0
```

```text
exit 1
1.5.0-beta.1
1.5.0-beta.2
1.5.0
1.6.0
1.5.0-beta.1
1.6.0
```

둘째 줄을 보자. `^1.5.0-beta.1`은 1.5.0-beta.2와 정식 1.5.0, 1.6.0은 받았지만 1.6.0-beta.1은 거절했다. "1.5.0의 베타를 써 보겠다"고 동의한 사람에게 다른 줄의 베타까지 떠넘기지 않겠다는 규칙이다. 이 규칙 덕분에 `^1.4.2`를 쓴 대다수 사용자는 누군가 베타를 올려도 영향을 받지 않는다.

Helm이 쓰는 Masterminds/semver는 범위에 사전 배포가 섞였을 때 판단이 다르므로, 차트를 다룰 때는 [Helm 글의 범위 검사](/posts/helm-dependencies-oci-gitops#차트-버전과-앱-버전)를 따로 본다. 아래 연습은 npm 쪽 규칙이다. 기대값은 `semver.satisfies`로 확인했다.

  // 사전 배포 version은 range에도 사전 배포가 있고

  solution={`function satisfies(version, range) {
  const parse = (v) => {
    const i = v.indexOf("-");
    const core = (i < 0 ? v : v.slice(0, i)).split(".").map(Number);
    const pre = i < 0 ? [] : v.slice(i + 1).split(".");
    return { core, pre };
  };
  const cmpCore = (a, b) => {
    for (let k = 0; k < 3; k++) if (a[k] !== b[k]) return a[k] < b[k] ? -1 : 1;
    return 0;
  };
  const isNum = (s) => /^\\d+$/.test(s);
  const cmp = (x, y) => {
    const c = cmpCore(x.core, y.core);
    if (c) return c;
    if (!x.pre.length && !y.pre.length) return 0;
    if (!x.pre.length) return 1;
    if (!y.pre.length) return -1;
    for (let k = 0; k < Math.max(x.pre.length, y.pre.length); k++) {
      const p = x.pre[k], q = y.pre[k];
      if (p === undefined) return -1;
      if (q === undefined) return 1;
      if (p === q) continue;
      if (isNum(p) && isNum(q)) return Number(p) < Number(q) ? -1 : 1;
      if (isNum(p) !== isNum(q)) return isNum(p) ? -1 : 1;
      return p < q ? -1 : 1;
    }
    return 0;
  };
  const op = range[0] === "^" || range[0] === "~" ? range[0] : "";
  const v = parse(version), b = parse(range.slice(op.length));
  if (v.pre.length && !(b.pre.length && cmpCore(v.core, b.core) === 0)) return false;
  if (cmp(v, b) < 0) return false;

  const [ma, mi, pa] = b.core;

  else if (ma > 0) upper = [ma + 1, 0, 0];
  else if (mi > 0) upper = [0, mi + 1, 0];

## npm install은 범위에서 하나를 고른다

범위는 "이 중 아무거나"이고, 실제로 깔리는 것은 하나다. npm이 그 하나를 고르는 과정을 따라가 보면 lockfile이 왜 필요한지 보인다.

```bash
# 범위로 설치하면 engines가 맞는 버전을 고른다
npm install @acme/fast-hash@^3.0.0

npm install @acme/fast-hash@3.1.0
# engine-strict를 켜면 같은 상황에서 설치를 멈춘다
npm install @acme/fast-hash@3.1.0 --engine-strict
```

범위로 설치하면 더 높은 3.1.0이 있어도 3.0.0이 깔렸다. npm은 engines가 맞는 버전을 우선한다. 그런데 Node 24를 쓰는 동료가 lockfile을 만들면 거기엔 3.1.0이 적히고, Node 22인 CI는 경고 한 줄만 찍고 3.1.0을 깐다. 경고는 로그에 묻히고, 문제는 실행할 때 낯선 문법 에러로 나타난다. 팀의 Node 버전을 `.nvmrc`나 `engines`와 `engine-strict=true`(`.npmrc`)로 묶어 두면 이 어긋남을 설치 단계에서 잡는다.

`npm install`이 범위를 어떻게 저장하는지도 알아 두자. 이름만 주면 `^최신`, `--save-exact`(`save-exact=true`)를 주면 정확한 버전이 저장된다. 태그로 설치할 때가 함정이다.

```bash
# 태그나 옵션에 따라 package.json에 저장되는 값이 달라진다
npm i @acme/date-fmt@next
npm i @acme/tiny --save-exact
cat package.json
```

```text
{"name":"app3","version":"1.0.0","private":true,"dependencies":{"@acme/date-fmt":"^1.6.0-beta.1","@acme/tiny":"0.5.0"}}
```

베타를 한 번 써 보려고 `@next`로 깔았는데 `^1.6.0-beta.1`이라는 범위가 남았다. 이 범위는 1.6.0-beta.2도, 정식 1.6.0도, 1.9.0도 받는다. 베타를 시험할 때는 정확한 버전으로 적고 끝나면 정식 범위로 돌려놓는다.

## dist-tag가 가리키는 곳

`latest`, `next` 같은 dist-tag는 버전에 붙이는 별명이다. 범위 없이 `npm install 패키지`를 하면 `latest`가 가리키는 버전이 깔린다. 별명이라 SemVer 순서와 상관없이 아무 버전이나 가리킬 수 있다는 점이 사고를 만든다.

앞의 1.5.1을 올리는 순간 그런 일이 실제로 생겼다. 2.0.0이 이미 나와 있는 상태에서 1.x 사용자를 위한 수정판을 평소처럼 `npm publish`로 올렸다.

```bash
# 1.x 수정판을 태그 지정 없이 올린 뒤 태그를 본다 (npm 10.9.4)
npm publish
npm view @acme/date-fmt dist-tags
```

```text
{ latest: '1.5.1', next: '1.6.0-beta.1' }
```

`npm publish`는 `--tag`를 주지 않으면 올린 버전에 `latest`를 붙인다. 이제 새로 `npm install @acme/date-fmt`를 하는 사람은 2.0.0이 아니라 1.5.1을 받는다. 옛 줄의 수정판은 `--tag v1-latest`처럼 다른 태그로 올리고, 이미 옮겨졌다면 태그를 되돌린다.

```bash
# latest를 원래 버전으로 되돌린다
npm dist-tag add @acme/date-fmt@2.0.0 latest
npm view @acme/date-fmt dist-tags
```

```text
+latest: @acme/date-fmt@2.0.0
{ latest: '2.0.0', next: '1.6.0-beta.1' }
```

## 무엇이 깨지는 변경인가

처음 장면의 1.5.1은 함수 이름도 인자도 그대로였다. 바뀐 건 기본 출력 형식 하나다. 레지스트리에 올라간 두 버전의 차이는 `npm diff`로 바로 볼 수 있다.

```bash
# 레지스트리에 올라간 두 버전의 실제 파일 차이를 본다
npm diff --diff=@acme/date-fmt@1.5.0 --diff=@acme/date-fmt@1.5.1
```

```text
diff --git a/index.js b/index.js
index v1.5.0..v1.5.1 100644
--- a/index.js
+++ b/index.js
@@ -1,1 +1,1 @@
-exports.format=(d)=>d.toISOString().slice(0,10);exports.version='1.5.0';
+exports.format=(d)=>d.toLocaleDateString('en-US');exports.version='1.5.1';
```

결과를 문자열로 비교하던 코드가 모두 깨진다. 시그니처만 보면 패치 같지만 공개된 동작이 바뀌었으니 주 버전 변경이다. 깨는 변경은 생각보다 범위가 넓다.

- 타입: TypeScript 타입 정의도 공개 API다. 반환 타입에 `null`을 더하거나 선택 필드를 필수로 바꾸면 런타임은 그대로여도 사용자의 빌드가 깨진다.
- 기본값과 출력 형식: 옵션을 안 준 사람이 받는 결과가 바뀌면 깨는 변경이다.
- 런타임 요구: `engines.node`를 올리거나 지원 브라우저를 줄이는 것. 많은 라이브러리가 Node 메이저 지원 중단을 주 버전 변경으로 낸다.
- 모듈 형식과 진입점: CommonJS를 빼고 ESM만 내거나, `package.json`의 `exports`를 새로 넣어 내부 파일 경로 import를 막는 것.
- peer dependency 범위를 좁히는 것: `react ^17 || ^18`을 `^18`로 줄이면 17 사용자의 설치가 막힌다([의존성 지옥](/posts/dependency-hell)의 ERESOLVE가 이것이다).

타입 쪽은 직접 보면 와닿는다. 같은 함수의 타입 정의만 바꿔서 사용자 코드를 컴파일했다.

```ts
// 1.5.0의 타입 정의
export interface FormatOptions { locale?: string }
export declare function format(d: Date, opts?: FormatOptions): string;

// 1.6.0이라고 낸 타입 정의: 반환에 null 추가, timeZone 필수
export interface FormatOptions { locale?: string; timeZone: string }
export declare function format(d: Date, opts?: FormatOptions): string | null;
```

```bash
# 사용자 코드: const label: string = format(new Date(), { locale: "ko-KR" });
npx tsc --strict --noEmit app.ts
```

```text
app.ts(2,7): error TS2322: Type 'string | null' is not assignable to type 'string'.
  Type 'null' is not assignable to type 'string'.
app.ts(2,42): error TS2345: Argument of type '{ locale: string; }' is not assignable to parameter of type 'FormatOptions'.
  Property 'timeZone' is missing in type '{ locale: string; }' but required in type 'FormatOptions'.
```

반대로 버그 수정도 누군가에겐 깨는 변경일 수 있다. 사용자가 많아지면 문서에 없는 동작까지 누군가는 의존한다(하이럼의 법칙). 그래서 "명세대로 고쳤으니 패치"가 늘 안전하지는 않다. 결과가 눈에 띄게 달라지는 수정이면 부 버전으로 올리고 변경 로그에 크게 적는 팀이 많다. 보안 수정은 예외적으로 동작을 깨더라도 수 버전으로 내는 경우가 있는데, 옛 줄에 묶인 사용자가 받을 수 있게 하려는 선택이다.

## 버전 번호를 사람이 고르지 않게

"이번엔 부 버전인가 수 버전인가"를 릴리스하는 날 기억에 의지해 정하면 틀린다. 변경을 만든 사람이 PR 단계에서 성격을 적고, 도구가 그걸 모아 번호를 정하게 한다. 방식은 크게 둘이다.

하나는 커밋 메시지에서 읽는 방식이다. [Conventional Commits](/posts/git-branching-strategy#커밋-메시지에-규칙을-둔다) 형식의 `fix:`, `feat:`, `feat!:`을 semantic-release나 release-please가 읽어 다음 번호와 변경 로그를 만든다. 별도 파일이 없어서 가볍지만, 커밋 메시지 한 줄이 곧 릴리스 결정이 된다. squash 머지라면 PR 제목이 그 한 줄이다.

다른 하나는 변경 설명 파일을 PR에 함께 넣는 Changesets다. 모노레포에서 패키지마다 다른 번호를 줘야 할 때 많이 쓴다. npm 워크스페이스로 `@acme/date-fmt`(1.5.0)와 이를 쓰는 `@acme/ui`(3.2.0)를 두고 돌려 봤다.

```bash
# changesets를 개발 의존성으로 설치하고 .changeset 폴더를 만든다
npm i -D @changesets/cli@2
npx changeset init
```

PR을 만드는 사람은 `npx changeset`으로 대화형 질문에 답하거나 아래 파일을 직접 쓴다. 어떤 패키지를 어느 자리로 올릴지와 변경 로그에 들어갈 문장이다.

```md
---
"@acme/date-fmt": minor
---

format()에 locale 옵션을 추가했다. 기본값은 그대로 ISO 형식이다.
```

```bash
# 쌓인 changeset을 보고 어떤 패키지가 얼마나 오를지 미리 본다
npx changeset status
# changeset을 소비해 package.json 버전과 CHANGELOG.md를 갱신한다
npx changeset version
```

```text
🦋  info NO packages to be bumped at patch
🦋  ---
🦋  info Packages to be bumped at minor:
🦋  info 
🦋  - @acme/date-fmt
🦋  ---
🦋  info NO packages to be bumped at major
```

`changeset version`은 changeset 파일을 지우고, date-fmt를 1.6.0으로 올리고, CHANGELOG.md를 새로 만들어 문장을 넣었다. ui는 손대지 않았다. ui가 적어 둔 `^1.5.0`이 1.6.0도 받기 때문이다. 같은 방식으로 date-fmt에 major changeset을 넣으면 결과가 달라진다.

```text
{
  "name": "@acme/ui",
  "version": "3.2.1",
  "dependencies": {
    "@acme/date-fmt": "^2.0.0"
  }
}
```

ui의 CHANGELOG에는 "Updated dependencies - @acme/date-fmt@2.0.0"이라는 Patch Changes 항목이 생겼다. 2.0.0은 `^1.5.0` 밖이라 ui의 범위가 `^2.0.0`으로 고쳐지고 ui는 수 버전만 올랐다. 여기서 사람이 판단할 몫이 남는다. ui가 date-fmt의 타입이나 함수를 그대로 다시 내보내고 있다면, ui 사용자에게도 깨는 변경이다. 그때는 ui에도 major changeset을 직접 넣어야 한다. 도구는 의존 관계를 따라 번호를 맞춰 줄 뿐, 내 공개 API가 무엇을 품고 있는지는 모른다.

실제 흐름은 CI가 이어 붙인다.

## 현장에서 버전 때문에 깨지는 순간

처음 장면으로 돌아가 보자. 코드는 그대로인데 CI가 깨졌다. 확인 순서는 이렇다.

1. lockfile이 바뀌었는지 본다. `git diff HEAD~1 -- package-lock.json`에 버전 줄이 바뀌어 있으면 누군가 `npm update`나 의존성 추가를 했다. lockfile이 그대로인데 결과가 다르면 CI가 `npm ci`가 아니라 `npm install`로 설치하고 있을 가능성이 크다([의존성 지옥](/posts/dependency-hell)에서 둘의 차이를 본다).
2. 바뀐 패키지의 출시 시각을 본다. `npm view 패키지 time --json`은 버전마다 올라간 시각을 준다. 깨지기 시작한 시각과 맞으면 거의 확정이다.
3. 실제 차이를 본다. 위의 `npm diff`로 두 버전의 파일을 비교한다. 변경 로그보다 정확하다.
4. 우선 고정하고, 그다음 고친다. 범위를 `1.5.0`으로 고정하거나, 다른 패키지가 끌고 온 경우라면 `overrides`로 버전을 박는다. 그리고 상류에 이슈를 연다. 깨는 변경이 수 버전으로 나왔다면 만든 쪽이 `npm deprecate @acme/date-fmt@1.5.1 "기본 형식이 바뀐 버그, 1.5.2로 올리세요"`로 표시하고 되돌린 1.5.2를 내는 것이 정석이다.

이걸 직접 재현하면 lockfile이 무엇을 지켜 주는지가 분명해진다. lockfile에 1.5.0이 적힌 상태에서 레지스트리에 깨진 1.5.1이 올라왔다.

```bash
# lockfile 그대로 설치하면 1.5.0이 유지된다
rm -rf node_modules && npm ci
node test.js
# 범위 안에서 최신으로 올리면 1.5.1이 들어오고 테스트가 깨진다
npm update
node test.js; echo "exit $?"
```

```text
added 2 packages in 451ms
date-fmt 1.5.0: 2026-10-21
changed 1 package in 637ms
date-fmt 1.5.1: 10/21/2026
FAIL: expected 2026-10-21
exit 1
```

범위는 "이 정도는 받아도 괜찮다"는 내 쪽의 허락이고, lockfile은 "지금 실제로 이걸 쓴다"는 기록이다. 범위만 믿으면 남의 실수가 내 배포에 그대로 들어온다. 그래서 업데이트는 Renovate나 Dependabot 같은 봇이 lockfile을 바꾸는 PR로 올리고, 그 PR에서 테스트가 돌게 한다. 봇 설정은 [의존성 지옥](/posts/dependency-hell)에서 다룬다.

## 숫자 세 개를 믿을 수 있게 만드는 것

SemVer는 숫자 자체보다 그 뒤의 약속이 본체다. 주 버전은 "고쳐야 할 수 있다", 부 버전은 "새로 생겼다", 수 버전은 "고치기만 했다"이고, 0.x는 아직 약속이 없다는 뜻이다. npm의 캐럿과 물결표는 그 약속을 믿는 정도를 적는 문법이고, 0.x에서 캐럿이 한 칸 좁아지는 것도, 사전 배포가 같은 줄에서만 들어오는 것도 받는 쪽을 보호하려는 규칙이다. 약속은 깨질 수 있으니 실제 버전은 lockfile로 고정하고, 올리는 일은 테스트가 도는 PR로 한다.

## 면접에서 나올 만한 질문

### MAJOR, MINOR, PATCH는 각각 언제 올리나요?

호환을 깨면 MAJOR, 호환되는 기능 추가면 MINOR, 호환되는 버그 수정이면 PATCH다. 기준은 공개 API이고, 여기에는 함수 시그니처뿐 아니라 타입 정의, 기본값, 지원 런타임까지 들어간다. 그래서 기본 출력 형식을 바꾸거나 `engines.node`를 올리는 것도 MAJOR로 본다.

### ^1.4.2와 ~1.4.2의 차이는 무엇인가요?

`^1.4.2`는 `>=1.4.2 <2.0.0-0`, 즉 주 버전 1 안의 모든 이후 버전이고, `~1.4.2`는 `>=1.4.2 <1.5.0-0`, 즉 1.4.x만 받는다. 위쪽 경계가 `-0`으로 끝나는 건 2.0.0-rc.1 같은 다음 주 버전의 후보가 범위에 섞이지 않게 하려는 것이다.

### ^0.4.2는 0.5.0을 받나요?

받지 않는다. 캐럿은 가장 왼쪽의 0이 아닌 자리를 고정하므로 `^0.4.2`는 `>=0.4.2 <0.5.0-0`이고, `^0.0.3`은 사실상 0.0.3 하나다. 0.x 라이브러리가 관례상 부 버전에서 API를 깨기 때문에 받는 쪽을 보호하려는 규칙이다. 대신 `npm update`로는 0.5.x의 수정을 영영 받지 못하니 `npm outdated`의 Wanted와 Latest를 보고 직접 올려야 한다.

### 1.0.0-beta.11과 1.0.0-beta.2 중 무엇이 더 높나요?

beta.11이 더 높다. 사전 배포 식별자는 점으로 나눠 왼쪽부터 비교하고, 둘 다 숫자면 숫자로 비교한다. 숫자 식별자는 문자보다 작고, 앞이 같으면 식별자가 많은 쪽이 크다. 그리고 사전 배포 버전은 같은 숫자의 정식 버전보다 항상 앞선다. 빌드 메타데이터(`+` 뒤)는 순서에 전혀 영향을 주지 않는다.

### 범위에 맞는 버전이 있는데 사전 배포 버전이 설치되지 않는 이유는요?

node-semver는 범위 쪽에 사전 배포 식별자가 없으면 사전 배포 버전을 후보로 보지 않는다. 범위에 있으면 숫자 세 자리가 같은 줄의 사전 배포만 받는다. 베타를 쓰고 싶으면 정확한 버전이나 그 줄의 사전 배포 범위를 적고, 모든 사전 배포를 허용하려면 `--include-prerelease`를 쓴다.

### 수 버전 업데이트 하나로 서비스가 깨졌습니다. 어떻게 대응하나요?

먼저 lockfile 변경과 `npm view 패키지 time`으로 어느 버전이 언제 들어왔는지 확인하고, `npm diff`로 두 버전의 실제 차이를 본다. 급한 불은 정확한 버전 고정이나 `overrides`로 끄고 상류에 알린다. 재발을 막으려면 CI는 `npm ci`로 lockfile대로만 설치하고, 업데이트는 봇이 여는 PR에서 테스트를 거쳐 들어오게 한다.

### Changesets와 semantic-release는 어떻게 다른가요?

semantic-release는 Conventional Commits 커밋 메시지를 읽어 번호와 변경 로그를 자동으로 정하고, Changesets는 PR마다 넣은 변경 설명 파일을 모아 번호를 정한다. 전자는 별도 파일이 없어 가볍지만 커밋 메시지가 곧 릴리스 결정이 된다. 후자는 모노레포에서 패키지마다 다른 번호를 주기 쉽고, "Version Packages" PR을 머지하는 시점으로 릴리스 시점을 사람이 정한다.

### dist-tag는 무엇이고 어떤 실수를 하기 쉽나요?

`latest`, `next` 같은 버전의 별명이고, 범위 없이 설치하면 `latest`가 깔린다. `npm publish`는 `--tag`가 없으면 올린 버전에 `latest`를 붙이기 때문에, 2.x가 나온 뒤 1.x 수정판을 그냥 올리면 새 사용자가 1.x를 받게 된다. 옛 줄은 별도 태그로 올리고, 잘못 옮겨졌으면 `npm dist-tag add 패키지@2.0.0 latest`로 되돌린다.
