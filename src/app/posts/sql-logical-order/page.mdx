<EasyIntro>
  월별 신청 수를 뽑았는데 세 줄이 나와야 할 자리에 아홉 줄이 나오고, 이름 하나만 바꿨더니 세 줄로 돌아오는 일이 있다. 에러는 없다. SELECT 문장을 데이터베이스가 어떤 순서로 읽는지 알아야 설명되는 일이다.

  문장은 테이블을 읽고, 행을 거르고, 묶어서 집계하고, 묶음을 거르고, 보여 줄 값과 순위 같은 창 함수를 계산하고, 겹친 행을 빼고, 정렬하고, 자르는 순서로 처리된다. 공장의 조립 라인처럼 앞 단계에서 만들지 않은 것은 뒤 단계에서만 쓸 수 있다. 그래서 보여 줄 값에 붙인 이름을 거르는 단계에서 쓰면 없다고 하고, 순위를 매긴 결과로 바로 거를 수 없다.

  아홉 줄이 나온 이유는 새로 붙인 이름이 원래 열 이름과 같아서, 묶는 단계가 원래 열을 골라 초 단위로 묶었기 때문이다. 정렬 기준이 같은 행끼리는 순서가 정해져 있지 않아 상위 몇 개를 자르면 실행마다 다른 행이 나올 수 있다는 점도 같은 순서에서 나온다. 실제 실행은 더 싼 길로 바뀌지만 결과의 뜻은 이 순서가 정한다.
</EasyIntro>

월별 수강 신청 수를 뽑으려고 이렇게 썼다.

```sql
SELECT date_trunc('month', enrolled_at) AS enrolled_at, count(*)
FROM enrollments
GROUP BY enrolled_at
ORDER BY enrolled_at;
```

석 달 치 데이터라 세 줄이 나와야 하는데 아홉 줄이 나온다. 10월이 일곱 번 찍히고 count는 전부 1이다. 에러는 없다. 별칭을 바꿔 `AS month`로 쓰고 `GROUP BY month`로 고치면 세 줄이 나온다. 이름 하나 바꿨을 뿐인데 결과가 달라진다.

이 글은 이런 일이 왜 생기는지를 PostgreSQL이 `SELECT` 한 문장을 읽는 순서로 설명한다. FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT라는 기본 순서와 `WHERE`에서 별칭이 안 되는 이유는 [SELECT와 NULL 글](/posts/sql-select-where-null)에, 집계와 `HAVING`의 기초는 [SQLD 집계 글](/posts/sqld-group-by-having)에 있다. 여기서는 그 순서 사이사이에 끼어 있는 단계(집계 계산, 윈도 함수, `DISTINCT`)와, 그 단계가 만드는 이상한 에러와 조용한 버그를 하나씩 본다. 같은 데이터로 이어지는 글이 둘 더 있다. 조건 연산자는 [WHERE 연산자 글](/posts/sql-filtering-operators), 집계 숫자가 틀리는 경우는 [집계 함정 글](/posts/sql-aggregation-pitfalls)이다.

기준은 Ubuntu 24.04의 PostgreSQL 16.15다. 아래 출력은 모두 이 환경에서 실제로 돌린 결과이고, psql에서 `\pset null '(null)'`을 켠 상태다. MySQL 8과 다른 점은 그때그때 짧게 적는다. MySQL은 직접 돌려 보지 않고 문서로 확인했다.

## 한 문장이 여덟 단계를 지난다

"완강한 강의의 평균 점수가 80점 이상인 수강생 중 상위 두 명"을 구한다. 절이 거의 다 들어간 문장이다.

```sql
SELECT s.name, round(avg(e.score), 1) AS avg_score
FROM enrollments e
JOIN students s ON s.id = e.student_id
WHERE e.status = 'completed'
GROUP BY s.name
HAVING avg(e.score) >= 80
ORDER BY avg_score DESC
LIMIT 2;
```

```text
 name | avg_score
------+-----------
 choi |      95.0
 lee  |      85.0
(2 rows)
```

PostgreSQL 문서(SELECT 명령의 Description)는 이 문장을 처리하는 순서를 이렇게 적는다. FROM의 테이블을 읽고 붙인다 → WHERE로 행을 거른다 → GROUP BY로 묶고 집계를 계산한다 → HAVING으로 묶음을 거른다 → SELECT 목록을 계산한다(윈도 함수는 여기서) → DISTINCT로 겹친 행을 뺀다 → UNION 같은 집합 연산 → ORDER BY로 정렬 → LIMIT·OFFSET으로 자른다. 기초 글의 일곱 단계 사이에 집계 계산, 윈도 함수, `DISTINCT`가 끼어 있다는 점이 이 글의 출발점이다. 아래 문장의 조각을 눌러 보면 각 절이 몇 번째인지 나온다.

## 별칭은 SELECT를 지나야 생긴다

`avg_score`는 ⑤에서 생긴다. 그러니 그보다 앞인 `WHERE`(②)와 `HAVING`(④)에서는 없다. `HAVING`에서 써 보면 `WHERE`와 같은 에러가 난다.

```sql
SELECT student_id, count(*) AS done
FROM enrollments
GROUP BY student_id
HAVING done >= 2;
```

```text
ERROR:  column "done" does not exist
LINE 1: ... done FROM enrollments GROUP BY student_id HAVING done >= 2;
                                                             ^
```

`ORDER BY`는 ⑦이니 쓸 수 있다고 배웠다. 그런데 `ORDER BY -done`처럼 식 안에 넣으면 똑같이 `column "done" does not exist`가 난다.

PostgreSQL 문서의 규칙이 이렇다. `ORDER BY`에서 출력 컬럼 이름은 그 이름 하나만 단독으로 쓸 때만 알아본다. `-done`이나 `done * 2`처럼 식 안에 들어가면 그 이름을 입력 테이블의 컬럼에서 찾고, 없으니 에러다. 식으로 정렬하려면 `ORDER BY count(*) DESC`처럼 원래 식을 쓰거나 `DESC`를 붙인다.

`GROUP BY`는 ③으로 `SELECT`보다 앞인데, 앞에서 본 것처럼 `GROUP BY month`는 됐다. 표준 SQL은 이걸 허용하지 않는다. PostgreSQL이 편의로 `GROUP BY`에서 출력 컬럼 이름과 위치 번호(`GROUP BY 1`)를 받아 주는 것이다. 순서 원칙에서 벗어난 예외라서, 다음 섹션의 함정이 여기서 생긴다.

어떤 절에서 별칭이 보이는지 그림으로 모으면 이렇다. 점선은 PostgreSQL만의 예외다.

MySQL 8은 여기서 더 너그럽다. `GROUP BY`, `HAVING`, `ORDER BY`에서 모두 별칭을 받는다(`WHERE`는 MySQL도 안 된다). 그래서 MySQL에서 돌던 `HAVING done >= 2`가 PostgreSQL로 옮기면 깨진다. 이식할 쿼리라면 `HAVING`에는 식을 그대로 적어 두는 쪽이 안전하다.

## 같은 이름이면 GROUP BY는 원래 컬럼을 고른다

이제 처음의 아홉 줄을 설명할 수 있다. 별칭을 원래 컬럼과 같은 `enrolled_at`으로 지었다. `GROUP BY enrolled_at`의 `enrolled_at`은 두 가지로 읽힌다. 테이블의 원래 컬럼(입력 컬럼)일 수도 있고, `date_trunc`로 만든 출력 컬럼일 수도 있다.

PostgreSQL 문서는 이 경우를 정해 두었다. 이름이 겹치면 `GROUP BY`는 입력 컬럼으로 읽는다. 그래서 잘리기 전의 시각, 초까지 다른 아홉 개의 값으로 묶였다. 묶음이 아홉 개니 count는 모두 1이고, 화면에는 그걸 다시 월로 자른 값이 보이니 10월이 일곱 번 찍힌다. `SELECT`의 `date_trunc('month', enrolled_at)`는 묶은 컬럼으로 계산한 식이라 문법상 문제도 없다. 에러가 나지 않는 이유다.

```text
      enrolled_at       | count
------------------------+-------
 2026-09-01 00:00:00+09 |     1
 2026-10-01 00:00:00+09 |     1
 2026-10-01 00:00:00+09 |     1
 2026-10-01 00:00:00+09 |     1
 2026-10-01 00:00:00+09 |     1
 2026-10-01 00:00:00+09 |     1
 2026-10-01 00:00:00+09 |     1
 2026-10-01 00:00:00+09 |     1
 2026-11-01 00:00:00+09 |     1
(9 rows)
```

`ORDER BY`는 반대로 고른다. 이름이 겹치면 출력 컬럼으로 읽는다. 같은 문장 안에서 같은 이름이 절마다 다른 것을 가리킬 수 있다는 뜻이다. 실제로 `SELECT name, -id AS id FROM students ORDER BY id`를 돌리면 원래 id 순서(kim부터)가 아니라 바뀐 값 기준으로 jung(-5)부터 kim(-1)까지 나온다.

고치는 방법은 셋이다. 별칭을 원래 컬럼과 다르게 짓는다(`AS month`). 위치 번호로 묶는다(`GROUP BY 1`). 식을 그대로 적는다(`GROUP BY date_trunc('month', enrolled_at)`). 위치 번호는 `SELECT` 목록이 바뀌면 조용히 다른 컬럼으로 묶이니 오래 살 쿼리에는 첫째나 셋째가 낫다.

```sql
SELECT date_trunc('month', enrolled_at) AS month, count(*)
FROM enrollments
GROUP BY month
ORDER BY month;
```

```text
         month          | count
------------------------+-------
 2026-09-01 00:00:00+09 |     1
 2026-10-01 00:00:00+09 |     7
 2026-11-01 00:00:00+09 |     1
(3 rows)
```

리포트 숫자가 "묶음마다 1"로 고르게 나오면 이 함정을 먼저 의심한다. 묶음 수가 원본 행 수와 같다는 건 아무것도 묶이지 않았다는 신호다. `SELECT count(*) FROM (원래 쿼리) t`와 원본 행 수를 나란히 놓아 보면 바로 보인다.

## 윈도 함수는 HAVING보다 늦다

수강생마다 가장 최근 수강 한 건만 보려고 `row_number()`를 붙이고 `WHERE`로 거른다.

```sql
SELECT id, student_id,
       row_number() OVER (PARTITION BY student_id ORDER BY enrolled_at DESC) AS rn
FROM enrollments
WHERE rn = 1;
```

```text
ERROR:  column "rn" does not exist
LINE 1: ...ER BY enrolled_at DESC) AS rn FROM enrollments WHERE rn = 1;
                                                                ^
```

별칭이 없다는 에러는 앞에서 본 그대로다. 그럼 식을 직접 `WHERE`에 넣으면 될까.

```sql
SELECT id, student_id
FROM enrollments
WHERE row_number() OVER (PARTITION BY student_id ORDER BY enrolled_at DESC) = 1;
```

```text
ERROR:  window functions are not allowed in WHERE
LINE 1: SELECT id, student_id FROM enrollments WHERE row_number() OV...
                                                     ^
```

윈도 함수는 ⑤에서 계산된다. `WHERE`, `GROUP BY`, `HAVING`이 모두 끝나고 남은 행을 보고 번호를 매기는 것이라, 그 앞 단계에서는 값이 존재할 수가 없다. 집계 함수를 `WHERE`에 넣으면 `aggregate functions are not allowed in WHERE`가 나오는 것과 같은 이유다. 거꾸로, 윈도 함수가 집계보다 늦으니 집계 결과에 순위를 매기는 건 된다. `GROUP BY student_id`와 함께 `rank() OVER (ORDER BY count(*) DESC)`를 쓰면 3건인 1번이 1위, 2건인 나머지 셋이 공동 2위로 나온다.

윈도 결과로 거르려면 한 단계 바깥으로 감싼다. 서브쿼리 안에서 ⑤까지 끝내 두면, 바깥 쿼리의 ①이 그 결과를 테이블처럼 읽고 ②에서 거른다. CTE(`WITH`)로 써도 같다.

```sql
SELECT id, student_id, enrolled_at
FROM (
  SELECT id, student_id, enrolled_at,
         row_number() OVER (PARTITION BY student_id ORDER BY enrolled_at DESC) AS rn
  FROM enrollments
) t
WHERE rn = 1
ORDER BY student_id;
```

```text
 id | student_id |      enrolled_at
----+------------+------------------------
  5 |          1 | 2026-10-15 08:00:00+09
  4 |          2 | 2026-10-12 09:00:00+09
  8 |          3 | 2026-10-31 23:59:30+09
  9 |          4 | 2026-11-01 00:00:00+09
(4 rows)
```

Snowflake, BigQuery, DuckDB 같은 일부 DB에는 윈도 결과를 바로 거르는 `QUALIFY` 절이 있다. PostgreSQL 16과 MySQL 8에는 없다. 윈도 함수 자체(프레임, 순위 함수의 차이)는 [PostgreSQL 윈도 함수 글](/posts/sql-window-functions-pg)에서 다룬다.

## DISTINCT는 정렬보다 먼저 겹친 걸 뺀다

최근에 수강한 순서로 수강생 번호를 중복 없이 뽑으려 했다.

```sql
SELECT DISTINCT student_id FROM enrollments ORDER BY enrolled_at DESC;
```

```text
ERROR:  for SELECT DISTINCT, ORDER BY expressions must appear in select list
LINE 1: ...ECT DISTINCT student_id FROM enrollments ORDER BY enrolled_a...
                                                             ^
```

`DISTINCT`(⑥)가 `ORDER BY`(⑦)보다 먼저다. ⑥이 끝나면 남는 건 `student_id` 하나짜리 행 네 개다. 1번 수강생은 수강 시각이 세 개였는데 그중 어느 시각으로 정렬할지 정할 수가 없다. 그래서 PostgreSQL은 `SELECT DISTINCT`에서 `ORDER BY`가 `SELECT` 목록에 있는 것만 쓰도록 막는다. MySQL 8도 이 경우를 에러로 막는다.

"어느 시각으로"를 정해 주면 풀린다. 최근 순이라면 수강생마다 가장 늦은 시각이다. `DISTINCT`가 아니라 `GROUP BY`와 `max`로 쓴다.

```sql
SELECT student_id, max(enrolled_at) AS last_at
FROM enrollments
GROUP BY student_id
ORDER BY last_at DESC;
```

```text
 student_id |        last_at
------------+------------------------
          4 | 2026-11-01 00:00:00+09
          3 | 2026-10-31 23:59:30+09
          1 | 2026-10-15 08:00:00+09
          2 | 2026-10-12 09:00:00+09
(4 rows)
```

PostgreSQL에는 `DISTINCT ON`도 있다. 이건 ⑥과 ⑦이 손을 잡는 문법이다. 먼저 `ORDER BY`로 정렬해 두고, 괄호 안 값이 같은 행 중 첫 줄만 남긴다. 그래서 `ORDER BY`의 앞부분이 `DISTINCT ON`의 식과 같아야 한다.

`DISTINCT ON (student_id)`에 `ORDER BY enrolled_at DESC`만 주면 `SELECT DISTINCT ON expressions must match initial ORDER BY expressions` 에러가 난다. `ORDER BY student_id, enrolled_at DESC`로 쓰면 앞의 윈도 함수 서브쿼리와 같은 네 줄이 나온다. 쓰는 법과 성능은 [PostgreSQL 리포트 쿼리 글](/posts/postgres-reporting-sql)에 있다. 결과를 최근 순으로 다시 보고 싶으면 이걸 서브쿼리로 감싸 바깥에서 한 번 더 정렬한다.

## LIMIT은 맨 끝이고, 동점은 정해 주지 않으면 운이다

수강 건수가 많은 수강생 두 명을 뽑는다.

```sql
SELECT student_id, count(*) AS cnt
FROM enrollments
GROUP BY student_id
ORDER BY cnt DESC
LIMIT 2;
```

```text
 student_id | cnt
------------+-----
          1 |   3
          3 |   2
(2 rows)
```

2등 자리에 3번이 나왔다. 그런데 2, 3, 4번은 모두 2건이다. 3번이 뽑힌 이유는 없다. 정렬 기준이 같은 행끼리의 순서는 SQL이 정해 주지 않고, 지금은 해시 집계가 내놓은 순서가 우연히 그랬을 뿐이다. 데이터가 바뀌거나 실행 계획이 바뀌면 2번이나 4번이 나올 수 있다. 아래 그림에서 다음을 누르면 동점이 있을 때 `LIMIT`이 무엇을 자르는지 볼 수 있다.

동점을 다루는 방법은 두 가지다. 하나는 정렬 기준 끝에 유일한 값을 붙여 순서를 완전히 정하는 것이다.

```sql
SELECT student_id, count(*) AS cnt
FROM enrollments
GROUP BY student_id
ORDER BY cnt DESC, student_id
LIMIT 2;
```

```text
 student_id | cnt
------------+-----
          1 |   3
          2 |   2
(2 rows)
```

다른 하나는 동점을 모두 받는 것이다. PostgreSQL 13부터 표준 문법 `FETCH FIRST n ROWS WITH TIES`를 쓸 수 있다. "상위 2명"이 아니라 "2등까지 모두"가 필요한 시상 같은 경우에 맞다.

```sql
SELECT student_id, count(*) AS cnt
FROM enrollments
GROUP BY student_id
ORDER BY cnt DESC
FETCH FIRST 2 ROWS WITH TIES;
```

```text
 student_id | cnt
------------+-----
          1 |   3
          3 |   2
          4 |   2
          2 |   2
(4 rows)
```

`WITH TIES`는 무엇이 동점인지 알아야 하니 `ORDER BY` 없이 쓰면 `WITH TIES cannot be specified without ORDER BY clause` 에러가 난다. MySQL 8에는 이 문법이 없어서 `RANK()`로 순위를 매긴 뒤 감싸서 거른다.

페이지를 나눌 때 이 문제가 커진다. `OFFSET`으로 페이지를 넘기면 페이지마다 쿼리를 따로 실행하니, 동점 행의 순서가 실행마다 달라지면 같은 행이 두 페이지에 나오거나 어느 페이지에도 안 나온다. 목록 API의 `ORDER BY`에는 항상 마지막에 기본 키를 붙인다. 뒤 페이지로 갈수록 느려지는 `OFFSET` 자체의 문제는 [쿼리 고쳐 쓰기 글](/posts/sql-query-rewrite)의 키셋 페이지네이션에서 다룬다.

## 집계는 CASE보다 먼저 끝난다

순서 이야기의 마지막은 "조건으로 막았는데 왜 에러가 나나"다. 점수가 0인 기록이 생기는 상황을 트랜잭션 안에서 만들고, 기록이 100건을 넘을 때만 점수 역수 합을 보려고 했다. 지금은 9건이니 `CASE`가 거짓이 되어 NULL이 나와야 한다.

```sql
BEGIN;
UPDATE enrollments SET score = 0 WHERE id = 8;
SELECT CASE WHEN count(*) > 100 THEN sum(100 / score) END AS ratio
FROM enrollments;
ROLLBACK;
```

```text
UPDATE 1
ERROR:  division by zero
```

`CASE`는 조건이 거짓이면 `THEN` 쪽을 계산하지 않는다. 그런데 `sum(100 / score)`는 `CASE`가 계산되는 ⑤보다 훨씬 앞인 ③에서, 행을 묶으면서 이미 계산된다. `CASE`가 조건을 보는 시점에는 집계가 끝나 있고, 0으로 나누는 에러는 그때 이미 났다. PostgreSQL 문서도 같은 예를 들며 `CASE`가 집계 안의 식을 막지 못한다고 적어 둔다. 0이 섞일 수 있는 나눗셈은 집계 안에서 막는다.

```sql
SELECT CASE WHEN count(*) > 100 THEN sum(100 / nullif(score, 0)) END AS ratio
FROM enrollments;   -- 위 트랜잭션 안에서 실행
```

```text
 ratio
--------
 (null)
(1 row)
```

비슷한 오해가 `WHERE`의 `AND`다. `WHERE score <> 0 AND 100 / score > 1`처럼 앞 조건으로 뒤 조건을 지키려는 코드는 프로그래밍 언어의 단락 평가를 기대한다. PostgreSQL 문서는 식의 하위 항목이 계산되는 순서를 정해 두지 않았다고 적는다. 플래너가 비용을 보고 조건 순서를 바꿀 수 있다는 뜻이다. 이 데이터에서는 에러 없이 돌았지만, 그건 보장이 아니다. 순서가 꼭 필요하면 `CASE WHEN score <> 0 THEN 100 / score > 1 END`처럼 `CASE`로 감싸거나 `nullif`를 쓴다.

## 논리 순서와 실제 실행은 다르다

여기까지의 순서는 의미를 정하는 약속이다. 실제로는 플래너가 같은 결과를 더 싸게 내는 방법을 고른다. 앞 섹션까지 쓴 9줄짜리 테이블로는 차이가 안 보이니, 같은 모양의 20만 줄짜리 `enrollments_big`을 만들어 본다.

```sql
CREATE TABLE enrollments_big AS
SELECT g AS id,
       1 + (g % 20000) AS student_id,                     -- 수강생 2만 명
       1 + (g % 5) AS course_id,
       (ARRAY['active','completed','completed','refunded'])[1 + g % 4] AS status,
       CASE WHEN g % 3 = 0 THEN NULL ELSE 40 + (g * 7) % 61 END AS score,
       timestamptz '2026-01-01 00:00+09' + g * interval '137 seconds' AS enrolled_at
FROM generate_series(1, 200000) g;
ALTER TABLE enrollments_big ADD PRIMARY KEY (id);
CREATE INDEX ON enrollments_big (enrolled_at);
CREATE INDEX ON enrollments_big (student_id);
ANALYZE enrollments_big;
SET max_parallel_workers_per_gather = 0;   -- 계획을 읽기 쉽게 병렬 실행을 끈다
```

논리 순서대로라면 `ORDER BY ... LIMIT 5`는 20만 줄을 다 정렬한 뒤 다섯 줄을 남긴다. 실제 계획은 다르다.

```sql
EXPLAIN ANALYZE
SELECT id, student_id, enrolled_at FROM enrollments_big
ORDER BY enrolled_at DESC LIMIT 5;
```

```text
                                                                               QUERY PLAN
-------------------------------------------------------------------------------------------------------------------------------------------------------------------------
 Limit  (cost=0.42..0.59 rows=5 width=16) (actual time=0.035..0.038 rows=5 loops=1)
   ->  Index Scan Backward using enrollments_big_enrolled_at_idx on enrollments_big  (cost=0.42..6807.42 rows=200000 width=16) (actual time=0.034..0.036 rows=5 loops=1)
 Planning Time: 0.394 ms
 Execution Time: 0.057 ms
(4 rows)
```

`Index Scan Backward` 줄의 `actual ... rows=5`를 본다. `enrolled_at` 인덱스는 이미 정렬돼 있으니 뒤에서부터 다섯 줄만 읽고 멈췄다. ⑦ 정렬과 ⑧ 자르기가 ① 읽기 안으로 녹아 들어간 셈이다. 인덱스가 없는 `score`로 정렬하면 이렇게 된다.

```sql
EXPLAIN ANALYZE
SELECT id, student_id, enrolled_at FROM enrollments_big
ORDER BY score DESC NULLS LAST LIMIT 5;
```

```text
                                                             QUERY PLAN
------------------------------------------------------------------------------------------------------------------------------------
 Limit  (cost=6921.93..6921.94 rows=5 width=20) (actual time=46.828..46.831 rows=5 loops=1)
   ->  Sort  (cost=6921.93..7421.93 rows=200000 width=20) (actual time=46.827..46.828 rows=5 loops=1)
         Sort Key: score DESC NULLS LAST
         Sort Method: top-N heapsort  Memory: 25kB
         ->  Seq Scan on enrollments_big  (cost=0.00..3600.00 rows=200000 width=20) (actual time=0.016..25.788 rows=200000 loops=1)
 Planning Time: 0.044 ms
 Execution Time: 46.854 ms
(7 rows)
```

이번에는 `Seq Scan`이 `rows=200000`을 다 읽었다. 그래도 전부 정렬하지는 않았다. `Sort Method: top-N heapsort`는 `LIMIT`을 알고 상위 다섯 개만 힙에 유지하며 훑었다는 뜻이고, 메모리는 25kB였다. 0.057ms와 46.8ms, 결과는 같은 다섯 줄이다.

`HAVING`도 마찬가지다. 집계가 없는 조건을 `HAVING`에 쓰면 논리적으로는 묶은 뒤에 거르지만, 플래너는 그 조건을 `WHERE`로 내려서 읽을 때부터 거른다.

```sql
EXPLAIN (COSTS OFF)
SELECT student_id, count(*) FROM enrollments_big
GROUP BY student_id
HAVING student_id <= 100;
```

```text
                           QUERY PLAN
-----------------------------------------------------------------
 HashAggregate
   Group Key: student_id
   ->  Bitmap Heap Scan on enrollments_big
         Recheck Cond: (student_id <= 100)
         ->  Bitmap Index Scan on enrollments_big_student_id_idx
               Index Cond: (student_id <= 100)
(6 rows)
```

`HAVING`에 쓴 조건이 `Index Cond`에 들어가 있다. 같은 조건을 `WHERE`에 써도 계획이 한 글자도 다르지 않았다. 그래도 사람이 읽는 쿼리로는 `WHERE`에 쓰는 게 맞다. 묶기 전에 거르는 조건과 묶은 뒤에 거르는 조건이 문장에서 구분되기 때문이다. 다른 DB가 이 최적화를 똑같이 해 준다는 보장도 없다.

## 에러 메시지에서 단계를 거꾸로 짚기

PostgreSQL이 순서 때문에 내는 에러는 몇 가지로 정해져 있다. 메시지를 보면 어느 단계에서 무엇을 찾다 실패했는지 바로 보인다.

| 메시지 | 무엇을 어디서 찾았나 | 고치는 방법 |
|---|---|---|
| `column "x" does not exist` (x가 별칭) | ②·④에서, 또는 ⑦의 식 안에서 ⑤의 이름 | 식을 다시 쓰거나 서브쿼리로 감싼다 |
| `aggregate functions are not allowed in WHERE` | ②에서 ③의 집계 | 조건을 `HAVING`으로 옮긴다 |
| `window functions are not allowed in WHERE` | ②에서 ⑤의 윈도 결과 | 서브쿼리·CTE로 감싸고 바깥에서 거른다 |
| `column "x" must appear in the GROUP BY clause ...` | ⑤에서 ③이 버린 개별 값 | 묶음 기준에 넣거나 집계로 감싼다 |
| `for SELECT DISTINCT, ORDER BY expressions must appear in select list` | ⑦에서 ⑥이 버린 컬럼 | `GROUP BY`와 `max`·`min`으로 바꾼다 |

에러가 안 나는 쪽이 더 위험하다. 묶음마다 1이 나오는 리포트(입력 컬럼과 같은 별칭), 실행할 때마다 바뀌는 상위 N개(동점), 막았다고 생각한 0으로 나누기(집계 안의 식)는 테스트 데이터가 작을 때 잘 드러나지 않는다. 리뷰할 때 별칭 이름이 원래 컬럼과 같은지, `LIMIT` 앞의 `ORDER BY`가 행 하나를 딱 가리키는지를 먼저 본다. 셋째 줄의 `GROUP BY` 규칙과 PostgreSQL이 기본 키로 묶었을 때 봐주는 경우는 [집계 함정 글](/posts/sql-aggregation-pitfalls)에서 다룬다.

## 단계를 직접 밟아 보기

## 순서를 알면 에러가 설명된다

`SELECT`는 FROM → WHERE → GROUP BY와 집계 → HAVING → SELECT와 윈도 함수 → DISTINCT → ORDER BY → LIMIT 순서로 의미가 정해진다. 어떤 이름이 어느 절에서 보이는지, 무엇이 언제 계산되는지가 모두 이 순서에서 나온다. 별칭이 `HAVING`에서 안 보이고, 윈도 함수를 `WHERE`에 못 쓰고, `DISTINCT` 뒤에 버린 컬럼으로 정렬하지 못하고, `CASE`가 집계 안의 나눗셈을 막지 못하는 것이 다 같은 이유다. 실제 실행은 플래너가 순서를 바꿔 더 싸게 하지만 결과는 바꾸지 않는다. 다음 글 [WHERE 연산자 글](/posts/sql-filtering-operators)에서는 ② 단계의 조건 하나하나가 왜 생각보다 많이 또는 적게 거르는지를 본다.

## 면접에서 나올 만한 질문

### SELECT 문은 어떤 순서로 처리되나요?

FROM과 JOIN → WHERE → GROUP BY와 집계 계산 → HAVING → SELECT 목록(윈도 함수 포함) → DISTINCT → ORDER BY → LIMIT·OFFSET 순서로 의미가 정해진다. 적는 순서와 다르다. 이 순서 때문에 `WHERE`와 `HAVING`에서는 `SELECT`의 별칭을 못 쓰고 `ORDER BY`에서는 쓸 수 있다.

### WHERE에서는 별칭을 못 쓰는데 ORDER BY에서는 되는 이유는요? 식 안에서는요?

별칭은 SELECT 단계에서 생기고, `WHERE`는 그보다 앞이고 `ORDER BY`는 뒤라서다. 다만 PostgreSQL은 `ORDER BY`에서 별칭을 이름 하나로 단독으로 쓸 때만 알아보고, `-done`처럼 식 안에 넣으면 입력 컬럼에서 찾다가 에러를 낸다. 이때는 원래 식을 쓰거나 `DESC`를 쓴다.

### 별칭을 원래 컬럼 이름과 같게 지으면 어떤 문제가 생기나요?

PostgreSQL은 이름이 겹치면 `GROUP BY`는 입력 컬럼으로, `ORDER BY`는 출력 컬럼으로 읽는다. 그래서 `date_trunc('month', enrolled_at) AS enrolled_at`으로 만들고 `GROUP BY enrolled_at`을 쓰면 월이 아니라 원래 시각으로 묶여서 묶음마다 1인 결과가 에러 없이 나온다. 별칭을 다르게 짓거나 식을 그대로 묶는다.

### 윈도 함수 결과로 행을 거르려면 어떻게 하나요?

서브쿼리나 CTE로 한 번 감싸고 바깥 쿼리의 `WHERE`에서 거른다. 윈도 함수는 `WHERE`, `GROUP BY`, `HAVING`이 끝난 뒤 SELECT 단계에서 계산되니 같은 쿼리의 `WHERE`에서는 쓸 수 없다. Snowflake나 BigQuery의 `QUALIFY`가 이걸 한 문장으로 해 주지만 PostgreSQL 16과 MySQL 8에는 없다.

### SELECT DISTINCT에서 SELECT에 없는 컬럼으로 정렬하면 왜 에러가 나나요?

`DISTINCT`가 `ORDER BY`보다 먼저 겹친 행을 합치기 때문이다. 합쳐진 한 줄에 원래 값이 여러 개였다면 어느 값으로 정렬할지 정할 수 없다. "가장 최근 값으로" 같은 기준을 `GROUP BY`와 `max`로 정해 주거나 `DISTINCT ON`을 쓴다.

### ORDER BY 없이 LIMIT을 쓰거나, 정렬 기준에 동점이 있으면 어떻게 되나요?

어느 행이 나올지 보장되지 않는다. 지금은 우연히 같은 행이 나와도 데이터나 실행 계획이 바뀌면 달라지고, `OFFSET` 페이지네이션에서는 같은 행이 두 페이지에 나오거나 빠질 수 있다. 정렬 끝에 기본 키 같은 유일한 컬럼을 붙이거나, 동점을 다 받으려면 PostgreSQL 13부터 되는 `FETCH FIRST n ROWS WITH TIES`를 쓴다.

### 논리적 처리 순서대로 DB가 실제로 실행하나요?

아니다. 순서는 결과의 의미를 정하는 약속이고, 플래너는 같은 결과를 내는 더 싼 방법을 고른다. `ORDER BY ... LIMIT`은 같은 순서의 인덱스가 있으면 정렬 없이 앞의 몇 줄만 읽고, 집계 없는 `HAVING` 조건은 `WHERE`로 내려 읽을 때부터 거른다. `EXPLAIN ANALYZE`의 `actual rows`로 확인한다.

### CASE로 조건을 걸었는데 집계 안에서 0으로 나누기 에러가 났습니다. 왜 그런가요?

집계는 SELECT 단계의 `CASE`보다 앞인 묶기 단계에서 이미 계산되기 때문이다. `CASE`가 조건을 볼 때는 `sum(100 / score)`가 끝나 있다. 집계 안에서 `nullif(score, 0)`이나 `FILTER`로 막아야 하고, `WHERE`의 `AND`도 계산 순서가 보장되지 않으니 순서가 필요하면 `CASE`로 감싼다.
