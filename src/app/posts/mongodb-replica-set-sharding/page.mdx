결제 서비스에서 이런 일이 있었다고 해 보자. 주문 API가 성공 응답을 받았고, 사용자에게 "결제 완료"를 보여 줬다. 몇 초 뒤 MongoDB 프라이머리가 죽었고 새 프라이머리가 뽑혔다. 그런데 그 주문이 DB에 없다. 로그를 뒤져 보니 옛 프라이머리의 데이터 디렉터리 아래 `rollback`이라는 폴더에 그 주문이 들어 있다.

이 장면은 쓰기 확인 수준(write concern)을 `w: 1`로 쓴 복제본 셋에서 실제로 일어날 수 있다. 이 글은 그 장면을 직접 재현하는 것에서 시작해, 선출이 어떻게 일어나는지, oplog 창이 무엇인지, read concern과 write concern을 어떻게 조합하는지, 재시도 가능한 쓰기가 막아 주는 것과 못 막는 것을 본다. 뒤쪽에서는 샤드 클러스터를 띄워 청크와 밸런서, jumbo 청크, 해시와 범위 샤드 키의 차이를 확인하고, 백업에서 흔히 하는 실수까지 짚는다.

복제본 셋과 샤딩이 무엇인지, `w: "majority"`가 어떤 흐름으로 확인되는지, 샤드 키를 고르는 기준은 [MongoDB 문서 모델](/posts/mongodb-document-model)에서 개요를 다뤘다. 여기서는 그 아래에서 실제로 벌어지는 일을 본다. 실험은 Ubuntu 24.04에서 MongoDB 8.0을 한 서버에 여러 프로세스로 띄워서 했다. 출력은 모두 실제로 돌린 것이다.

## 세 대짜리 복제본 셋 띄우기

포트만 다르게 mongod 세 개를 띄우고 하나로 묶는다. 실제 운영에서는 서버(가용 영역)를 나누지만 동작은 같다.

```bash
# 데이터 디렉터리를 만들고 같은 replSet 이름으로 세 개를 띄운다
for i in 1 2 3; do
  mkdir -p ~/rs/d$i
  mongod --replSet rs0 --port 2710$i --dbpath ~/rs/d$i --bind_ip 127.0.0.1 \
         --fork --logpath ~/rs/d$i.log
done
```

```js
// 첫 번째 멤버에 붙어서 셋을 초기화한다. 27101의 우선순위를 높게 준다
rs.initiate({
  _id: "rs0",
  members: [
    { _id: 0, host: "127.0.0.1:27101", priority: 2 },
    { _id: 1, host: "127.0.0.1:27102" },
    { _id: 2, host: "127.0.0.1:27103" },
  ],
});
```

상태를 보면 프라이머리 하나와 세컨더리 둘이다. 선출 관련 값도 같이 뽑아 봤다.

```js
const s = rs.status();
s.members.map((m) => m.name + " " + m.stateStr);
s.electionCandidateMetrics;
rs.conf().settings;
```

```text
127.0.0.1:27101 PRIMARY health=1
127.0.0.1:27102 SECONDARY health=1
127.0.0.1:27103 SECONDARY health=1
term Long('6')
{
  lastElectionReason: 'priorityTakeover',
  electionTerm: Long('6'),
  numVotesNeeded: 2,
  priorityAtElection: 2,
  electionTimeoutMillis: Long('10000')
}
{"majorityVoteCount":2,"writeMajorityCount":2,"votingMembersCount":3}
{"electionTimeoutMillis":10000,"heartbeatIntervalMillis":2000,"catchUpTimeoutMillis":-1,"chainingAllowed":true}
```

몇 가지를 읽을 수 있다. `term`은 선출이 일어날 때마다 1씩 오르는 번호다. 두 프라이머리가 동시에 자기가 프라이머리라고 믿는 순간이 있어도, 더 큰 term을 가진 쪽이 이긴다. `lastElectionReason: 'priorityTakeover'`는 우선순위가 더 높은 27101이 올라오자 기존 프라이머리를 밀어내고 자리를 가져갔다는 뜻이다. 멤버끼리는 2초(`heartbeatIntervalMillis`)마다 서로 신호를 보내고, 프라이머리에게서 10초(`electionTimeoutMillis`) 동안 소식이 없으면 세컨더리가 선거를 시작한다. 투표 멤버가 3이라 과반은 2다(`numVotesNeeded: 2`).

이 숫자 때문에 장애 조치(failover)는 보통 10초 남짓 걸린다. 그동안 쓰기는 받을 곳이 없다. 앱의 드라이버는 새 프라이머리를 찾을 때까지 기다리는데(`serverSelectionTimeoutMS` 기본 30초), 앱의 요청 타임아웃이 그보다 짧으면 장애 조치 동안 요청이 실패로 끝난다. 선출 시간을 줄이려고 `electionTimeoutMillis`를 너무 낮추면, 잠깐의 네트워크 지연에도 선거가 일어나 프라이머리가 자주 바뀐다.

## 성공 응답을 받은 주문이 사라지는 장면

이제 서론의 장면을 만든다. 세컨더리 둘이 프라이머리의 oplog를 못 가져가게 막은 뒤 쓰고, 프라이머리를 강제로 죽인다. 복제를 막는 데는 테스트용 장애 주입 지점(failpoint)을 썼다. `--setParameter enableTestCommands=1`로 띄운 서버에서만 되는 기능이라 운영에서는 쓸 일이 없다. 실제 장애에서는 네트워크가 끊기거나 세컨더리가 밀려 있을 때 같은 일이 생긴다.

```js
// 두 세컨더리에서: oplog 가져오기를 멈춘다 (테스트 전용)
db.adminCommand({ configureFailPoint: "stopReplProducer", mode: "alwaysOn" });

// 프라이머리에서: w:1로 쓴다
db.payments.insertOne({ _id: "order-1001", amount: 39000, at: new Date() }, { writeConcern: { w: 1 } });

// 프라이머리에서: w:majority로 쓴다 (3초 기다리고 포기)
db.payments.insertOne({ _id: "order-1002", amount: 52000 }, { writeConcern: { w: "majority", wtimeout: 3000 } });
```

```text
w1 -> {"acknowledged":true,"insertedId":"order-1001"}
maj ERR WriteConcernFailed waiting for replication timed out {"code":64,"codeName":"WriteConcernFailed","errmsg":"waiting for replication timed out","errInfo":{"wtimeout":true,"writeConcern":{"w":"majority","wtimeout":3000,"provenance":"clientSupplied"}}}
```

`w: 1`은 바로 성공했다. `w: "majority"`는 3초 뒤 `WriteConcernFailed`로 끝났다. 여기서 많이 오해하는 부분이 있다. 이 에러는 "쓰기가 안 됐다"가 아니라 "과반에 퍼졌는지 3초 안에 확인하지 못했다"다. 프라이머리에서 읽어 보면 두 건 다 있다.

```js
db.payments.find().readConcern("local")     // 이 멤버가 가진 최신 값
db.payments.find().readConcern("majority")  // 과반에 반영된 값만
```

```text
local read: ["order-1001","order-1002"]
majority read: []
```

`local`로 읽으면 둘 다 보이고, `majority`로 읽으면 하나도 안 보인다. 과반에 반영되지 않은 값은 나중에 사라질 수 있다는 걸 read concern이 그대로 보여 준다. 이제 프라이머리를 `kill -9`로 죽이고, 세컨더리들의 복제를 다시 풀었다. 아래 그림에서 "다음"을 누르면 그 뒤에 일어난 일이 차례로 나온다.

`w: "majority"`로 썼다면 이 일이 없었을까. 과반이 받은 쓰기는 이후 어떤 멤버가 프라이머리가 되어도 남는다. 과반이 받지 못한 `order-1002`는 결국 되돌려졌지만, 앱은 성공 응답 대신 에러를 받았으니 "완료"를 보여 주지 않았을 것이다. 5.0부터는 대부분의 구성에서 기본 write concern이 `majority`다. 위 실험 셋에서도 기본값이 그렇게 나온다.

```js
db.adminCommand({ getDefaultRWConcern: 1 });
```

```text
{"defaultReadConcern":{"level":"local"},"defaultWriteConcern":{"w":"majority","wtimeout":0},"defaultWriteConcernSource":"implicit","defaultReadConcernSource":"implicit"}
```

그러니 이 장면은 누군가 성능 때문에 `w: 1`을 명시했거나, 아래에서 볼 아비터 구성이라 기본값이 `w: 1`로 잡힌 경우에 생긴다. 운영 중인 셋의 기본값은 위 명령으로 꼭 확인해 본다.

## 아비터가 과반을 망가뜨리는 경우

데이터 노드 두 대에 투표만 하는 아비터(arbiter) 하나를 붙인 구성(PSA)이 있다. 서버 비용을 아끼려고 쓰는데, 함정이 있다. 투표 멤버가 셋이니 선출 과반은 2다. 세컨더리가 죽어도 프라이머리와 아비터 두 표로 프라이머리는 유지된다. 하지만 `w: "majority"` 쓰기는 데이터를 가진 멤버의 과반이 받아야 하는데, 데이터 노드가 프라이머리 하나만 남았으니 확인이 영영 안 된다. 쓰기는 `wtimeout`까지 기다리다 실패하거나, `wtimeout`이 없으면 끝없이 기다린다.

그래서 MongoDB는 아비터가 있어서 데이터 노드 수가 과반 이하인 구성(PSA가 여기 해당한다)에서는 기본 write concern을 `w: 1`로 잡는다. 앞 절의 롤백 위험이 기본값으로 따라온다는 뜻이다. 거기에 세컨더리가 오래 죽어 있으면 과반 커밋 지점(majority commit point)이 멈춰서, 프라이머리가 그 지점 이후의 변경 이력을 계속 메모리에 쌓아 캐시 압박이 생긴다.

어떤 구성에서 프라이머리가 서고 majority 쓰기가 되는지 직접 계산해 보면 감이 온다. 멤버 목록과 살아 있는 멤버 id를 받아 두 값을 돌려준다. 프라이머리가 되려면 살아 있는 투표 수가 과반이어야 하고, 우선순위가 0보다 큰 데이터 멤버가 하나는 살아 있어야 한다. majority 쓰기는 "투표 멤버 과반"과 "데이터를 가진 투표 멤버 수" 중 작은 값만큼 데이터 멤버가 살아 있어야 된다.

  solution={`function replicaHealth(members, up) {
  const isUp = (m) => up.includes(m.id);
  const voters = members.filter((m) => m.votes > 0);
  const majority = Math.floor(voters.length / 2) + 1;           // 선출 과반

  const hasPrimary = upVotes >= majority && electable;
  return {
    hasPrimary,
    majorityWrites: hasPrimary && dataVoters.filter(isUp).length >= writeMajority,
  };
}`}

      args: [[{ id: "a", votes: 1, priority: 1 }, { id: "b", votes: 1, priority: 1 }, { id: "arb", votes: 1, priority: 0, arbiter: true }], ["a", "b"]],
      expected: { hasPrimary: true, majorityWrites: true },
    },
    {
      label: "살아남은 둘이 모두 priority 0",
      args: [[{ id: "a", votes: 1, priority: 1 }, { id: "b", votes: 1, priority: 0 }, { id: "c", votes: 1, priority: 0 }], ["b", "c"]],
      expected: { hasPrimary: false, majorityWrites: false },
    },

      label: "투표 4 + 비투표 1에서 두 대만 남았다",

      expected: { hasPrimary: false, majorityWrites: false },
    },
  ]}
/>

PSA에서 세컨더리가 죽은 세 번째 경우가 함정이다. 프라이머리는 있으니 모니터링상 셋은 "정상"인데, majority 쓰기는 하나도 끝나지 않는다. 마지막 경우는 투표 멤버를 짝수(4)로 두면 과반이 3이 되어, 한 대를 더 늘렸는데 오히려 두 대 장애를 못 버틴다는 걸 보여 준다. 그래서 투표 멤버는 홀수로 두고(최대 7), 가능하면 아비터 대신 데이터 노드를 하나 더 둔다. 투표 멤버는 7개까지지만 비투표 멤버를 더해 50개까지 둘 수 있다. 분석용 숨김(hidden) 멤버나 일부러 1시간 늦게 따라오는 지연(delayed) 멤버는 `priority: 0`, 보통 `votes: 0`으로 둔다.

## 세컨더리가 따라올 수 있는 시간, oplog 창

세컨더리는 프라이머리의 oplog를 가져와 같은 순서로 적용한다. oplog는 고정 크기 컬렉션이라 오래된 항목부터 지워진다. 세컨더리가 점검이나 장애로 멈춰 있는 동안 프라이머리의 oplog가 한 바퀴 돌아, 세컨더리가 마지막으로 적용한 지점이 지워져 버리면 그 세컨더리는 더 이상 따라올 수 없다. 이때 상태가 RECOVERING에 머물고 로그에 "too stale"이 찍힌다. 남은 방법은 데이터를 처음부터 다시 복사하는 초기 동기화(initial sync)뿐이고, 데이터가 수 TB면 몇 시간에서 며칠이 걸린다.

그래서 oplog가 몇 시간치를 담고 있는지(oplog 창)를 안다.

```js
rs.printReplicationInfo();
```

```text
actual oplog size
'990 MB'
---
configured oplog size
'990 MB'
---
log length start to end
'20266 secs (5.63 hrs)'
---
oplog first event time
'Fri Oct 23 2026 13:12:47 GMT+0000 (Coordinated Universal Time)'
---
oplog last event time
'Fri Oct 23 2026 18:50:33 GMT+0000 (Coordinated Universal Time)'
```

`log length start to end`가 창이다. 이 실험 서버는 거의 놀고 있어서 5.63시간이지만, 쓰기가 많은 서비스에서는 같은 990MB가 몇십 분치일 수도 있다. 창이 "가장 긴 점검 시간 + 여유"보다 짧으면 oplog를 키운다. 지금은 재시작 없이 `replSetResizeOplog`로 크기를 바꿀 수 있고, 4.4부터는 크기와 별개로 최소 보존 시간(`oplogMinRetentionHours`)도 줄 수 있다.

```js
// oplog를 16GB로 늘린다 (MB 단위, 멤버마다 실행)
db.adminCommand({ replSetResizeOplog: 1, size: 16384 });
```

창은 쓰기 패턴에 따라 줄어든다. 대량 `updateMany` 한 번이 문서마다 oplog 항목을 하나씩 만들어서, 평소 하루치 창이 배치 한 번에 한 시간으로 줄어들기도 한다. 큰 배치 전후로 창과 세컨더리 지연(`rs.printSecondaryReplicationInfo()`)을 같이 본다.

## 읽기와 쓰기를 어디까지 믿을지 고르기

write concern이 "몇 대가 받았을 때 성공이라고 할지"라면, read concern은 "어떤 상태의 데이터를 읽을지"다. 둘을 따로 고르면 앞뒤가 안 맞는 조합이 생기니 같이 정한다.

- `local`(기본): 그 멤버가 가진 최신 값. 앞 실험처럼 나중에 롤백될 수 있는 값도 읽는다.
- `available`: 샤드 클러스터의 세컨더리 읽기에서 가장 빠르지만, 청크 이동 중에 남은 고아 문서까지 읽을 수 있다.
- `majority`: 과반에 반영된 값만. 롤백되지 않는다. 다만 최신 쓰기가 아직 과반에 안 퍼졌으면 조금 옛날 값을 읽는다.
- `linearizable`: 프라이머리에서만, 문서 하나 단위로, 읽기 직전까지 확인된 모든 majority 쓰기를 반영한다. 프라이머리가 정말 프라이머리인지 확인하는 왕복이 붙어서 느리고, `maxTimeMS`를 같이 줘야 한다.
- `snapshot`: 트랜잭션 안에서, 또는 5.0부터 `atClusterTime`을 준 읽기에서, 한 시점의 일관된 스냅숏을 읽는다.

실무에서 자주 쓰는 조합은 이렇다. 결제나 재고처럼 사라지면 안 되는 쓰기는 `w: "majority"`로 쓴다. "내가 방금 쓴 걸 바로 보여 줘야 하는" 화면은 인과적 일관성 세션에서 majority 읽기와 쓰기를 함께 써서, 세컨더리에서 읽더라도 내 쓰기 이후 상태를 보게 한다. 통계나 목록처럼 몇 초 늦어도 되는 읽기만 세컨더리로 보낸다(`readPreference: secondaryPreferred`). 세컨더리 읽기가 늦게 보이는 문제와 해결 방법은 [복제와 복제 지연](/posts/db-replication-sharding)에서 PostgreSQL 기준으로 자세히 다뤘는데, 원리는 같다.

```js
// 인과적 일관성 세션: 이 세션에서 쓴 것은 이 세션의 다음 읽기에서 보인다
const session = db.getMongo().startSession({ causalConsistency: true });
const orders = session.getDatabase("shop").orders;
orders.insertOne({ userId: "u42", total: 39000 }, { writeConcern: { w: "majority" } });
orders.find({ userId: "u42" }).readConcern("majority").readPref("secondary");
```

## 재시도 가능한 쓰기가 막아 주는 것

장애 조치 중에 쓰기를 보냈다면 어떻게 될까. 드라이버는 4.2 이후 기본으로 재시도 가능한 쓰기(`retryWrites=true`)를 켠다. 네트워크 오류나 "프라이머리가 아니다" 오류가 나면 새 프라이머리를 찾아 한 번 다시 보낸다. 이때 세션 id와 트랜잭션 번호를 함께 보내서, 첫 요청이 사실은 적용됐다면 서버가 같은 번호를 알아보고 두 번 적용하지 않는다. 그래서 `insertOne`, `updateOne`, `findOneAndUpdate` 같은 단건 쓰기는 장애 조치가 있어도 한 번만 적용된다. 읽기도 4.2 이후 기본으로 한 번 재시도한다(`retryReads=true`).

못 막는 것도 분명하다.

- 재시도는 한 번뿐이다. 선출이 드라이버의 서버 선택 타임아웃보다 오래 걸리면 결국 에러가 난다.
- `updateMany`, `deleteMany`처럼 여러 문서를 바꾸는 쓰기는 재시도 대상이 아니다. 중간에 끊기면 일부만 적용된 상태로 남을 수 있다.
- `w: 0`이나 `w: 1`로 쓴 뒤의 롤백은 막지 못한다. 재시도는 "응답을 못 받았을 때"의 장치지, "성공 응답 뒤에 사라지는 것"과는 상관없다.
- 앱 코드가 타임아웃 뒤 직접 다시 보내는 재시도는 드라이버가 모른다. 같은 주문이 두 번 들어갈 수 있으니, 이런 경우는 주문 번호에 유일 인덱스를 걸거나 [멱등성 키](/posts/idempotency-key)를 둔다.

## 샤드 클러스터 띄우기

이번에는 데이터를 여러 대로 나눈다. 구성은 설정 서버(config server) 복제본 셋 하나, 샤드 두 개(각각 복제본 셋), 그리고 라우터인 `mongos`다. 실험이라 셋 다 멤버 하나짜리 복제본 셋으로 띄웠다.

```bash
# 설정 서버와 샤드 두 개
mongod --configsvr --replSet cfg --port 27201 --dbpath ~/sh/cfg --fork --logpath ~/sh/cfg.log
mongod --shardsvr  --replSet shA --port 27211 --dbpath ~/sh/a   --fork --logpath ~/sh/a.log
mongod --shardsvr  --replSet shB --port 27221 --dbpath ~/sh/b   --fork --logpath ~/sh/b.log
# (각각 rs.initiate로 초기화한 뒤) 라우터를 띄운다
mongos --configdb cfg/127.0.0.1:27201 --port 27200 --fork --logpath ~/sh/mongos.log
```

```js
// mongos에 붙어서 샤드를 등록한다
sh.addShard("shA/127.0.0.1:27211");
sh.addShard("shB/127.0.0.1:27221");
```

같은 주문 4만 건을 두 컬렉션에 넣었다. 하나는 `createdAt` 범위로, 하나는 `userId` 해시로 나눈다. `createdAt`은 1초씩 늘어나는 값이다.

```js
sh.shardCollection("shop.orders_range", { createdAt: 1 });
sh.shardCollection("shop.orders_hashed", { userId: "hashed" });
// ... 4만 건을 두 컬렉션에 똑같이 넣는다

// 샤드별 문서 수와 청크 수
db.orders_range.aggregate([{ $collStats: { storageStats: {} } }, { $project: { shard: 1, count: "$storageStats.count" } }]);
```

```text
range   shA:40000
hashed  shA:20082 shB:19918
orders_range chunks: [{"_id":"shA","n":1}]
orders_hashed chunks: [{"_id":"shA","n":1},{"_id":"shB","n":1}]
```

범위 샤딩은 4만 건이 전부 shA 하나의 청크에 들어갔다. 빈 컬렉션에 범위로 샤딩하면 청크가 하나로 시작하고, 단조 증가하는 키는 새 문서가 늘 가장 큰 쪽, 즉 같은 청크로 간다. 해시 샤딩은 처음부터 해시 공간을 샤드 수만큼 나눈 청크를 만들어 두기 때문에 반반으로 나뉘었다.

## mongos가 요청을 어디로 보내는지

쿼리가 샤드 하나로 가는지, 전부에 묻는지는 mongos의 explain에서 바로 보인다.

```js
db.orders_range.find({ createdAt: { $gte: ISODate("2026-10-01T03:00:00Z"), $lt: ISODate("2026-10-01T04:00:00Z") } }).explain()
db.orders_hashed.find({ userId: "u42" }).explain()
db.orders_hashed.find({ createdAt: { $gte: ISODate("2026-10-01T03:00:00Z") } }).explain()
db.orders_hashed.find({ userId: { $in: ["u42", "u43", "u44", "u45"] } }).explain()
```

```text
range by createdAt: SINGLE_SHARD -> shA
hashed by userId:   SINGLE_SHARD -> shB
hashed by range:    SHARD_MERGE -> shB,shA
hashed by $in:      SHARD_MERGE -> shB,shA
```

`SINGLE_SHARD`는 샤드 키 조건으로 한 샤드만 골라 보낸 것이고, `SHARD_MERGE`는 여러 샤드에 보내고 결과를 mongos가 합친 것이다. 해시 샤딩은 같은 값이면 한 샤드로 가지만, 범위 조건은 해시값이 흩어져 있어서 모든 샤드에 물어야 한다. `$in`은 값마다 다른 샤드에 있을 수 있어서 해당 샤드들에 보낸다. 샤드가 2개일 땐 별 차이가 없지만, 30개가 되면 `SHARD_MERGE` 쿼리 하나가 30개 샤드를 다 깨우고 가장 느린 샤드를 기다린다.

## 밸런서가 청크를 옮기는 과정

범위 샤딩 컬렉션이 shA 한쪽에 몰려 있으니 밸런서가 옮겨 줘야 한다. 6.0부터 밸런서는 청크 개수가 아니라 샤드별 데이터 크기를 보고, 가장 많은 샤드와 가장 적은 샤드의 차이가 청크 크기의 세 배를 넘으면 옮긴다. 기본 청크 크기는 128MB(6.0 전에는 64MB)라 이 실험 데이터(약 15MB)로는 움직이지 않는다. 그래서 이 컬렉션만 청크 크기를 1MB로 낮췄다.

```js
db.adminCommand({ configureCollectionBalancing: "shop.orders_range", chunkSize: 1 });
sh.balancerCollectionStatus("shop.orders_range");
```

```text
{ chunkSize: 1, balancerCompliant: false, firstComplianceViolation: 'chunksImbalance', ok: 1 }
```

1분쯤 뒤 다시 봤다.

```text
chunks: [{"_id":"shA","n":1},{"_id":"shB","n":6}]
shB:16548 docs 6300977B | shA:40000 docs 15230879B
balancerCompliant: true
changelog: moveChunk.start 6, moveChunk.to 6, moveChunk.commit 6, moveChunk.from 6
```

청크 이동은 디스크와 네트워크를 쓰고 범위 삭제도 쓰기 부하다. 트래픽이 많은 시간을 피하려면 밸런서가 도는 시간대를 정한다.

```js
// 새벽 2시~6시에만 밸런서를 돌린다 (config 서버의 settings 컬렉션)
db.getSiblingDB("config").settings.updateOne(
  { _id: "balancer" },
  { $set: { activeWindow: { start: "02:00", stop: "06:00" } } },
  { upsert: true }
);
```

## 쪼갤 수 없는 jumbo 청크

카디널리티가 낮은 키로 샤딩하면 어떻게 되는지 `status`로 시험했다. 주문 2만 건 중 60%가 `paid`다. 청크 크기는 1MB로 낮췄다.

```js
sh.shardCollection("shop.orders_status", { status: 1 });
db.adminCommand({ configureCollectionBalancing: "shop.orders_status", chunkSize: 1 });
// 2만 건을 넣고 1분 남짓 기다린 뒤
db.getSiblingDB("config").chunks.find({ uuid: <컬렉션 UUID> }, { _id: 0, min: 1, max: 1, shard: 1, jumbo: 1 });
```

```text
[
  { min: { status: MinKey() }, max: { status: 'paid' }, shard: 'shB' },
  { min: { status: 'paid' }, max: { status: 'shipped' }, shard: 'shA', jumbo: true },
  { min: { status: 'shipped' }, max: { status: MaxKey() }, shard: 'shB', jumbo: false }
]
```

`[paid, shipped)` 청크에 `jumbo: true`가 붙었다. 이 청크에는 `status`가 `paid`인 문서만 1만 2천 건이 있는데, 청크는 샤드 키 값 사이로만 나눌 수 있으니 `paid` 하나를 둘로 쪼갤 방법이 없다. 직접 쪼개려고 해도 거절된다.

```js
db.adminCommand({ split: "shop.orders_status", middle: { status: "paid" } });
```

```text
ERR new split key { status: "paid" } is a boundary key of existing chunk [{ status: "paid" },{ status: "shipped" })
```

jumbo 청크는 밸런서가 옮기지 않는다(옮기려면 `forceJumbo` 옵션을 줘야 하고, 그동안 부하가 크다). 그 샤드만 계속 커진다. 원인이 키 자체라서 고치는 방법도 키를 바꾸는 것뿐이다. 4.4부터는 기존 키 뒤에 필드를 덧붙이는 `refineCollectionShardKey`로 `{ status: 1, _id: 1 }`처럼 쪼갤 여지를 만들 수 있고, 5.0부터는 `reshardCollection`으로 완전히 다른 키로 다시 나눌 수 있다.

```js
// 기존 키 뒤에 _id를 붙인다 (새 키 모양의 인덱스가 먼저 있어야 한다)
db.orders_status.createIndex({ status: 1, _id: 1 });
db.adminCommand({ refineCollectionShardKey: "shop.orders_status", key: { status: 1, _id: 1 } });

// 또는 아예 다른 키로 다시 나눈다 (컬렉션 전체를 새로 쓰는 무거운 작업)
db.adminCommand({ reshardCollection: "shop.orders_status", key: { userId: "hashed" } });
```

리샤딩은 컬렉션 전체를 새 키 기준으로 복사하는 동안 원래 컬렉션이 계속 읽기·쓰기를 받고, 마지막에 짧게 쓰기를 막고 바꿔치기한다. 그동안 샤드마다 컬렉션 크기만큼의 여유 디스크가 필요하고 쓰기 부하가 늘어서, 결국 처음 고를 때 신중해야 한다는 건 그대로다.

## 해시로 나눌까, 범위로 나눌까

실험에서 본 차이를 정리하면 이렇다. 해시 샤딩은 단조 증가하는 키(ObjectId, 시각)도 고르게 퍼뜨리고, 같은 값 조회는 한 샤드로 간다. 대신 범위 조회와 정렬은 모든 샤드에 묻는다. 범위 샤딩은 범위 조회가 한두 샤드에서 끝나지만, 단조 증가 키면 새 쓰기가 마지막 청크 하나에 몰린다.

주문 컬렉션이라면 "주문은 주로 회원 단위로 읽는다"는 점에서 출발한다. `{ userId: 1, createdAt: 1 }` 같은 복합 범위 키는 회원별로 퍼지면서 한 회원의 주문을 시간 순으로 한 샤드에서 읽게 해 준다. `{ userId: "hashed" }`도 쓰기 분산은 좋지만 "한 회원의 최근 주문" 정렬을 해시 키만으로는 받쳐 주지 못해서 보조 인덱스가 필요하다. 로그처럼 시간 범위로만 읽고 쓰기량이 큰 데이터는 해시나, 앞에 버킷 번호를 붙인 범위 키로 쓰기를 분산하고 범위 조회의 scatter-gather 비용을 받아들인다. 어느 쪽이든 자주 하는 쿼리 몇 개를 적어 놓고 explain에서 `SINGLE_SHARD`가 나오는지 확인하고 고른다.

그리고 샤딩은 늦게 할수록 좋다. 샤드 클러스터는 운영 요소가 몇 배로 늘고 트랜잭션과 `$lookup`이 비싸진다. 복제본 셋 하나가 디스크, 쓰기 처리량, 작업 집합(working set)이 메모리에 들어가는지 중 하나라도 한계에 닿는 신호가 보일 때, 수직 확장으로 버틸 수 있는지 먼저 따져 보고 샤딩한다.

## 백업: 덤프 한 번이 일관된 시점이 아닐 수 있다

`mongodump`는 컬렉션을 하나씩 읽어 BSON으로 내려받는 논리 백업이다. 덤프하는 몇 분 동안에도 쓰기가 계속되니, 컬렉션마다 다른 시점의 데이터가 섞인다. 복제본 셋에서는 `--oplog`를 주면 덤프하는 동안의 oplog를 함께 받아 두고, 복원할 때 `--oplogReplay`로 덤프가 끝난 시점까지 맞출 수 있다.

```bash
# 복제본 셋 전체를 덤프하면서 그동안의 oplog도 받는다
mongodump --uri "mongodb://127.0.0.1:27211/?replicaSet=shA" --oplog --gzip --out ~/dump
```

```text
done dumping `shop.orders_status` (20000 documents)
done dumping `shop.orders_hashed` (20082 documents)
done dumping `shop.orders_range` (40000 documents)
writing captured oplog to ``
	dumped 1 oplog entry
```

이 덤프에는 함정이 두 개 들어 있다. 먼저 `orders_range`가 40,000건이다. shA가 실제로 책임지는 문서는 23,452건(40,000 - 16,548)인데, 아직 지워지지 않은 고아 문서까지 같이 덤프됐다. 샤드마다 이렇게 직접 덤프해서 복원하면 문서가 중복된다. 샤드 클러스터는 mongos를 거쳐 덤프해야 고아 문서가 빠진다.

그런데 mongos를 거쳐도 문제가 남는다. 샤드마다 진행 속도가 달라서 클러스터 전체로 같은 시점이 아니고, 덤프 중에 청크가 옮겨지면 빠지거나 겹칠 수 있다. 그래서 샤드 클러스터에는 `mongodump`를 주 백업 방법으로 쓰지 않는다. 밸런서를 멈추고 샤드와 설정 서버의 파일 시스템 스냅숏을 같은 시점에 뜨거나, Atlas의 클러스터 백업이나 Ops Manager처럼 샤드 간 시점을 맞춰 주는 도구를 쓴다.

복원 쪽 옵션에도 제약이 있다. `--oplog`는 데이터베이스 하나만 고르는 덤프에서는 쓸 수 없고, `--oplogReplay`는 특정 컬렉션만 골라 복원하는 옵션과 같이 쓸 수 없다.

```text
mongodump --db shop --oplog ...           → Failed: bad option: --oplog mode only supported on full dumps
mongorestore --oplogReplay --nsInclude ... → Failed: cannot use --oplogReplay with includes specified
```

"주문 컬렉션 하나만 어제 시점으로 되돌리고 싶다"는 요청을 받으면 이 제약 때문에 막힌다. 그럴 땐 전체를 다른 서버에 복원한 뒤 필요한 컬렉션만 꺼내 오는 게 현실적인 길이다. 그래서 백업은 정기적으로 다른 서버에 실제로 복원해 보고, 걸린 시간을 재 둔다. 복원해 본 적 없는 백업은 백업이 아니다. 백업 주기와 복구 목표 시간을 정하는 방법은 [재해 복구](/posts/disaster-recovery)에서 다뤘다.

## 다시 사라진 주문 앞에서

서론의 장면으로 돌아가면, 원인은 `w: 1`이었고 결과는 rollback 파일이었다. 막는 방법은 결제 같은 쓰기를 `w: "majority"`로 쓰고, 아비터 대신 데이터 노드를 두고, 세컨더리가 따라올 수 있게 oplog 창을 넉넉히 두는 것이다. 데이터가 한 셋을 넘으면 샤드 키를 자주 하는 쿼리 기준으로 고르고, 단조 증가 키와 낮은 카디널리티 키를 피한다. 고아 문서와 청크 이동이 있다는 걸 알면 샤드에 직접 붙어 세거나 덤프하는 실수를 하지 않는다. 같은 데이터로 인덱스를 설계하는 법은 [MongoDB 인덱스와 explain](/posts/mongodb-indexes-explain), 집계가 샤드에서 어떻게 비싸지는지는 [MongoDB 집계 파이프라인](/posts/mongodb-aggregation-pipeline)에 있다.

## 면접에서 나올 만한 질문

### 복제본 셋에서 프라이머리는 어떻게 선출되나요?

멤버들은 2초마다 하트비트를 주고받고, 프라이머리에게서 10초(electionTimeoutMillis) 동안 응답이 없으면 세컨더리가 term을 올리고 투표를 요청한다. 투표 멤버의 과반을 얻은 멤버가 프라이머리가 되고, 우선순위가 더 높은 멤버가 올라오면 자리를 넘겨받기도 한다. 그래서 장애 조치는 보통 10초 남짓 걸리고 그동안 쓰기를 받을 곳이 없다. 투표 멤버는 홀수, 최대 7개로 둔다.

### w:1로 쓴 데이터가 사라지는 건 어떤 상황인가요?

프라이머리가 혼자 받고 성공을 응답한 뒤, 세컨더리에 복제되기 전에 죽으면 새 프라이머리에는 그 데이터가 없다. 옛 프라이머리가 돌아오면 공통 지점 이후의 자기 쓰기를 되돌리고 rollback 폴더에 BSON 파일로 남긴다. 자동으로 되살리지 않아서 사람이 파일을 보고 다시 넣어야 한다. `w: "majority"`로 쓰면 과반이 받은 쓰기만 성공으로 답하니 이런 일이 없다.

### w:majority 쓰기가 wtimeout으로 실패하면 쓰기가 안 된 건가요?

아니다. 과반에 퍼졌는지 정해진 시간 안에 확인하지 못했다는 뜻이고, 프라이머리에는 이미 적용돼 있다. 나중에 복제가 되면 남고, 그 전에 프라이머리가 바뀌면 롤백될 수 있다. 그래서 이 에러를 받고 그냥 다시 쓰면 중복이 생길 수 있으니 유일 키나 멱등성 키로 막는다.

### 아비터를 두면 어떤 문제가 생기나요?

PSA 구성에서 세컨더리가 죽으면 프라이머리와 아비터로 프라이머리는 유지되지만, 데이터 노드가 하나뿐이라 majority 쓰기를 확인할 수 없다. 이 때문에 PSA의 기본 write concern이 w:1로 잡혀 롤백 위험이 생기고, 과반 커밋 지점이 멈춰 캐시 압박도 생긴다. 가능하면 아비터 대신 데이터 노드를 둔다.

### oplog 창이 짧으면 무슨 일이 생기나요?

세컨더리가 멈춘 사이 oplog가 한 바퀴 돌아 마지막 적용 지점이 지워지면, 그 세컨더리는 더 따라오지 못하고 초기 동기화로 데이터를 처음부터 다시 받아야 한다. 그래서 가장 긴 점검 시간보다 창이 넉넉한지 `rs.printReplicationInfo()`로 확인하고, 필요하면 `replSetResizeOplog`로 키운다. 대량 업데이트는 창을 크게 줄이니 배치 전후로 본다.

### read concern majority와 linearizable은 어떻게 다른가요?

majority는 과반에 반영돼서 롤백되지 않을 값을 읽지만, 아직 과반에 안 퍼진 최신 쓰기는 안 보일 수 있다. linearizable은 프라이머리에서 읽기 직전까지 확인된 모든 majority 쓰기를 반영해서 가장 최신이면서 롤백되지 않는 값을 보장한다. 대신 문서 하나 단위이고 왕복이 붙어 느려서 maxTimeMS와 함께 꼭 필요한 곳에만 쓴다.

### 재시도 가능한 쓰기는 무엇을 막고 무엇을 못 막나요?

네트워크 오류나 프라이머리 교체 때 드라이버가 같은 트랜잭션 번호로 한 번 다시 보내서, 단건 쓰기가 두 번 적용되지 않으면서 성공하게 해 준다. 재시도는 한 번뿐이고, updateMany 같은 다건 쓰기는 대상이 아니며, 성공 응답 뒤의 롤백이나 앱 코드가 직접 하는 재시도는 막지 못한다.

### 샤드 키를 잘못 고르면 어떤 증상이 나타나나요?

단조 증가 키로 범위 샤딩하면 새 쓰기가 마지막 청크 하나에 몰려 샤드 하나만 바쁘다. 카디널리티가 낮은 키는 같은 값을 쪼갤 수 없어 jumbo 청크가 생기고 밸런서가 옮기지 못해 한 샤드만 커진다. 자주 하는 쿼리에 샤드 키가 없으면 모든 샤드에 묻는 SHARD_MERGE가 돼서 샤드가 늘수록 느려진다. 4.4의 refine이나 5.0의 리샤딩으로 고칠 수 있지만 무거운 작업이다.
