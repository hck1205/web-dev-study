<EasyIntro>
  기록 수집기나 네트워크 담당처럼 기계마다 꼭 하나씩 있어야 하는 프로그램이 있다. Deployment로 기계 수만큼 개수를 적어도 어떤 기계에는 둘이 가고 어떤 기계에는 하나도 안 갈 수 있고, 기계를 늘릴 때마다 숫자를 손으로 고쳐야 한다. DaemonSet은 이 일을 맡는 관리자로, 조건에 맞는 기계마다 정확히 하나씩 Pod를 띄우고 기계가 빠지면 Pod도 치운다.

  DaemonSet은 건물마다 한 명씩 배치되는 경비원과 같다. 새 건물이 생기면 경비원이 자동으로 배정되고, 건물이 없어지면 자리도 사라진다. 다만 기계에 들어오지 말라는 표시를 나중에 걸면 다음 배포 때 그 기계의 경비원이 조용히 빠져 버릴 수 있다.

  이 Pod들은 기계마다 자원을 고정으로 가져가서 앱이 쓸 자리가 그만큼 줄어든다. 업데이트는 기본으로 하나 빼고 하나 넣는 방식이고, 기계의 네트워크를 혼자 써야 하는 프로그램은 하나 더 넣고 빼는 방식을 쓸 수 없다.
</EasyIntro>

노드 열 대짜리 클러스터에 로그 수집기를 노드마다 하나씩 띄워야 한다. Deployment로 replicas 10을 주면 스케줄러가 어떤 노드에는 둘, 어떤 노드에는 하나도 놓지 않는다. 노드를 하나 더 붙이면 replicas를 손으로 11로 올려야 하고, 그래도 새 노드에 간다는 보장은 없다. 노드 로그를 읽는 에이전트가 없는 노드에서 난 장애는 로그가 남지 않는다.

DaemonSet은 "노드마다 정확히 하나"를 맡는 컨트롤러다. 노드가 붙으면 그 노드에 Pod를 띄우고, 노드가 빠지면 Pod도 치운다. 이 글은 DaemonSet이 Pod를 어느 노드에 놓을지 정하는 방식, control-plane 노드와 taint가 걸린 노드에서 생기는 일, 업데이트 전략 두 가지와 hostNetwork에서 maxSurge가 막히는 이유, 에이전트가 노드 자원을 얼마나 먹고 자리가 없을 때 무엇을 밀어내는지를 실습 클러스터에서 따라간다. 출력은 kwok로 띄운 Kubernetes 1.34.1 클러스터(control-plane 노드 하나, 워커 셋)에서 받았다. 컨트롤러와 스케줄러는 진짜이고 컨테이너는 실제로 돌지 않는다.

taint와 toleration, nodeSelector가 스케줄링에서 어떻게 걸러지는지는 [Pod 스케줄링 글](/posts/k8s-pod-scheduling)에, requests가 노드 자리를 정하는 원리는 [requests와 limits 글](/posts/k8s-pod-resources)에 있다. 같은 Workloads 묶음의 [StatefulSet 글](/posts/k8s-statefulset), [Job과 CronJob 글](/posts/k8s-job-cronjob)과 비교하며 읽으면 컨트롤러마다 무엇을 고정하는지가 보인다.

## 노드 수가 곧 replicas다

DaemonSet에는 `replicas`가 없다. 조건에 맞는 노드 수가 곧 Pod 수다. node-exporter로 만들어 봤다.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
  namespace: monitoring
spec:
  selector:
    matchLabels: {app: node-exporter}
  template:
    metadata:
      labels: {app: node-exporter}
    spec:
      hostNetwork: true            # 노드의 네트워크를 그대로 쓴다 (노드 IP:9100)
      hostPID: true                # 노드의 프로세스를 본다
      containers:
      - name: node-exporter
        image: quay.io/prometheus/node-exporter:v1.9.1
        args: ["--path.rootfs=/host"]
        ports:
        - {name: metrics, containerPort: 9100}
        resources:
          requests: {cpu: 50m, memory: 64Mi}
          limits: {memory: 128Mi}
        volumeMounts:
        - {name: root, mountPath: /host, readOnly: true}
      volumes:
      - name: root
        hostPath: {path: /}        # 노드 파일시스템을 읽기 전용으로 붙인다
```

```bash
# DaemonSet과 Pod가 어느 노드에 놓였는지 본다
kubectl -n monitoring get ds
kubectl -n monitoring get pods -o wide
```

```text

node-exporter   3         3         1       3            1           <none>          12s
NAME                  READY   STATUS    RESTARTS   AGE   IP              NODE       NOMINATED NODE   READINESS GATES
node-exporter-4fq2k   1/1     Running   0          79s   192.168.50.14   worker-3   <none>           <none>
node-exporter-n8pmt   1/1     Running   0          79s   192.168.50.13   worker-2   <none>           <none>
```

## DaemonSet Pod도 스케줄러가 놓는다

예전(1.11까지)에는 DaemonSet 컨트롤러가 Pod의 `nodeName`을 직접 채웠다. 지금은 컨트롤러가 "이 노드에만 가라"는 조건을 붙여 Pod를 만들고, 배치는 기본 스케줄러가 한다. 만들어진 Pod를 열어 보면 그 조건이 보인다.

```bash
# DaemonSet Pod에 컨트롤러가 붙인 affinity와 toleration
kubectl -n monitoring get pod node-exporter-4fq2k -o jsonpath='{.spec.affinity}{"\n"}'
kubectl -n monitoring get pod node-exporter-4fq2k \
  -o jsonpath='{range .spec.tolerations[*]}{.key}{"\t"}{.operator}{"\t"}{.effect}{"\n"}{end}'
```

```text
{"nodeAffinity":{"requiredDuringSchedulingIgnoredDuringExecution":{"nodeSelectorTerms":[{"matchFields":[{"key":"metadata.name","operator":"In","values":["worker-3"]}]}]}}}
node.kubernetes.io/not-ready	Exists	NoExecute
node.kubernetes.io/unreachable	Exists	NoExecute
node.kubernetes.io/disk-pressure	Exists	NoSchedule
node.kubernetes.io/memory-pressure	Exists	NoSchedule
node.kubernetes.io/pid-pressure	Exists	NoSchedule
node.kubernetes.io/unschedulable	Exists	NoSchedule
node.kubernetes.io/network-unavailable	Exists	NoSchedule
```

`matchFields`로 노드 이름 하나를 못 박았다. 매니페스트에 적지 않은 toleration 일곱 개도 컨트롤러가 넣었다. 이 일곱 개가 DaemonSet의 성격을 정한다.

- `not-ready`, `unreachable`에 `tolerationSeconds`가 없다. 일반 Pod는 노드가 응답하지 않으면 300초 뒤 쫓겨나지만 DaemonSet Pod는 노드가 돌아올 때까지 버틴다. 어차피 그 노드 전용이라 다른 데로 갈 곳이 없다.
- `disk-pressure`, `memory-pressure`, `pid-pressure`를 견딘다. 디스크가 꽉 찬 노드일수록 로그 수집기와 모니터링이 필요하다.
- `unschedulable`을 견딘다. cordon한 노드에도 DaemonSet Pod는 놓인다(아래에서 확인한다).
- `network-unavailable`은 `hostNetwork: true`일 때만 붙는다. CNI가 아직 준비되지 않은 노드에 CNI 에이전트 자신이 떠야 하기 때문이다.

스케줄러를 거치니 스케줄링 규칙도 똑같이 적용된다. 자리가 모자라면 Pending이 되고 FailedScheduling 이벤트가 남는다. 아래 그림이 노드 하나가 붙었을 때의 흐름이다.

## control-plane 노드에도 띄우려면

모니터링과 로그는 control-plane 노드에도 있어야 하는 경우가 많다. 그 노드의 taint를 견디는 toleration을 템플릿에 넣는다.

```bash
# control-plane taint를 견디게 한다
kubectl -n monitoring patch ds node-exporter --type json -p '[{"op":"add","path":"/spec/template/spec/tolerations","value":[{"key":"node-role.kubernetes.io/control-plane","operator":"Exists","effect":"NoSchedule"}]}]'
kubectl -n monitoring get ds
```

```text
daemonset.apps/node-exporter patched
NAME            DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR   AGE
node-exporter   4         4         4       3            4           <none>          2m10s
```

DESIRED가 4가 됐다. UP-TO-DATE가 3인 것은 템플릿이 바뀌어서 기존 세 Pod가 롤링 업데이트 중이기 때문이다. toleration 하나를 넣는 것도 템플릿 변경이라 모든 노드의 Pod가 한 번씩 다시 뜬다. 노드가 수백 대인 클러스터에서 에이전트 설정을 자주 고치면 그만큼 전체 노드에서 에이전트가 재시작된다는 뜻이다.

managed 클러스터(EKS, GKE)는 control-plane 노드를 사용자에게 보여 주지 않으니 이 toleration이 필요 없다. kubeadm으로 직접 꾸린 클러스터에서 챙긴다. 오래전에 kubeadm으로 만든 클러스터에는 1.25에서 없어진 옛 키 `node-role.kubernetes.io/master` taint가 남아 있을 수 있으니, `kubectl describe node`로 실제 taint를 보고 맞춘다.

## 라벨로 노드를 고른다

모든 노드가 아니라 일부에만 띄울 때는 `nodeSelector`나 node affinity를 쓴다. GPU 노드에만 도는 디바이스 플러그인이 대표다.

```yaml
spec:
  template:
    spec:
      nodeSelector:
        accelerator: nvidia          # 이 라벨이 있는 노드에만
      tolerations:
      - key: nvidia.com/gpu          # GPU 노드에 거는 taint를 견딘다
        operator: Exists
        effect: NoSchedule
      priorityClassName: system-node-critical
```

라벨이 붙고 떨어질 때마다 DaemonSet이 따라 움직인다.

```bash
# 처음에는 맞는 노드가 없다
kubectl -n kube-system get ds gpu-plugin
# worker-2에 라벨과 taint를 건다
kubectl label node worker-2 accelerator=nvidia
kubectl taint node worker-2 nvidia.com/gpu=present:NoSchedule
kubectl -n kube-system get ds gpu-plugin
# 라벨을 떼면
kubectl label node worker-2 accelerator-
kubectl -n kube-system get ds gpu-plugin
```

```text
NAME         DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR        AGE
gpu-plugin   0         0         0       0            0           accelerator=nvidia   3s
node/worker-2 labeled
node/worker-2 tainted
NAME         DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR        AGE
gpu-plugin   1         1         1       1            1           accelerator=nvidia   13s
node/worker-2 unlabeled
NAME         DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR        AGE
gpu-plugin   0         0         0       0            0           accelerator=nvidia   23s
```

라벨을 떼자 Pod가 지워졌다. 노드 라벨을 정리하다 실수로 지우면 그 노드의 에이전트가 조용히 사라진다는 말이기도 하다. GPU 노드를 어떻게 꾸리는지는 [GPU와 DRA 글](/posts/k8s-gpu-dra)에서 다룬다.

## taint를 나중에 걸면 에이전트가 사라진다

위 실습에서 `worker-2`에 `nvidia.com/gpu` taint를 걸었다. node-exporter는 이 taint를 견디지 않는데, 이미 돌던 Pod는 어떻게 됐을까.

```bash
# taint를 건 직후, 그리고 node-exporter를 재시작한 뒤
kubectl -n monitoring get ds node-exporter
kubectl -n monitoring rollout restart ds/node-exporter
kubectl -n monitoring get ds node-exporter
kubectl -n monitoring get pods -o wide
```


taint를 건 직후에는 DESIRED가 4 그대로였다. `NoSchedule`은 새로 놓는 것만 막고 이미 있는 Pod는 내쫓지 않으니, 컨트롤러도 "있는 건 그대로 둔다"로 셈한다. 그런데 재시작으로 Pod를 새로 만들어야 하는 순간 `worker-2`는 조건에서 빠지고, DESIRED가 3으로 줄며 `worker-2`의 모니터링이 사라졌다. 에러도 경고도 없다.

이 시차가 현장에서 문제다. taint를 건 사람과 에이전트를 배포한 사람이 다르고, 사라지는 시점은 몇 주 뒤 다음 배포다. 그래서 노드 전체를 덮어야 하는 에이전트(로그, 모니터링, CNI, CSI 노드 플러그인)는 보통 모든 taint를 견디게 둔다.

```yaml
tolerations:
- operator: Exists     # 키 없이 Exists: 어떤 taint든 견딘다
```

반대로 이 한 줄은 `NoExecute` taint도 견디니, 노드를 비우려고 거는 taint로도 에이전트가 안 빠진다. 대부분의 에이전트에는 원하는 동작이지만, 특정 노드에서 일부러 빼고 싶은 에이전트라면 nodeSelector나 affinity로 뺀다. 모니터링 쪽에서는 "노드 수와 node-exporter 타깃 수가 같은지"를 알림으로 걸어 두면 이런 구멍을 바로 잡는다. Prometheus 쿼리는 [Prometheus 기본 글](/posts/prometheus-basics)에서 이어진다.

## 업데이트: 하나 빼고 넣기, 하나 더 넣고 빼기

업데이트 전략은 두 가지다. `RollingUpdate`(기본)와 `OnDelete`. RollingUpdate는 숫자 두 개로 속도를 정한다.

- `maxUnavailable`(기본 1): 동시에 비어 있어도 되는 노드 수. 옛 Pod를 먼저 지우고 새 Pod를 띄운다. 그 사이 그 노드는 에이전트가 없다.
- `maxSurge`(기본 0, 1.25부터 정식): 노드 하나에 옛 Pod와 새 Pod가 잠깐 함께 있어도 되는 노드 수. 새 Pod가 Ready가 된 뒤 옛 Pod를 지운다. 둘 중 하나는 0이어야 한다.

## 노드 에이전트를 들여다볼 때

```bash
# Pod 스펙에 무엇이 붙었나
kubectl -n monitoring get pod node-exporter-x2qqx \
  -o jsonpath='{range .spec.ephemeralContainers[*]}{.name}  {.image}  target={.targetContainerName}{"\n"}{end}'
```

```text

debugger-4hdn2  busybox:1.36  target=node-exporter
```

임시 컨테이너는 `ephemeralcontainers` 하위 리소스로만 추가되고, 한 번 붙이면 뗄 수 없다.

```bash
# 붙인 임시 컨테이너를 빼 보려 한다
kubectl -n monitoring patch pod node-exporter-x2qqx --subresource=ephemeralcontainers \
  --type json -p '[{"op":"remove","path":"/spec/ephemeralContainers/0"}]'
```

```text
The Pod "node-exporter-x2qqx" is invalid: spec.ephemeralContainers: Forbidden: existing ephemeral containers "debugger-4hdn2" may not be removed
```

Pod가 다시 만들어질 때까지 남는다는 뜻이다. 디버깅용 이미지는 작게, 명령은 끝나는 것으로 준다. 에이전트가 아니라 노드 자체를 봐야 하면 `kubectl debug node/worker-1 --image=busybox:1.36 --profile=general`이 그 노드에 `hostPID`, `hostNetwork`, `hostIPC`가 켜지고 노드 루트가 `/host`에 붙은 Pod를 띄운다. 노드에 SSH가 막힌 managed 클러스터에서 쓸모 있지만 노드 전체 권한에 가까우니 RBAC로 쓸 사람을 좁힌다. 임시 컨테이너는 1.25부터 정식이고, 셸 없는 이미지를 다루는 순서는 [Pod 문제 해결 글](/posts/k8s-pod-troubleshooting#셸이-없는-컨테이너는-kubectl-debug로-연다), 명령 옵션은 [kubectl 필수 명령 글](/posts/kubectl-essentials)에 있다.

## 어디에 DaemonSet을 쓰나

노드마다 하나가 있어야 의미가 있는 것들이다.

- 로그 수집기: Fluent Bit, Vector, Promtail. 노드의 `/var/log/pods`를 hostPath로 읽는다. Pod마다 사이드카를 붙이는 방식보다 자원이 덜 들지만, 노드 하나의 수집기가 죽으면 그 노드의 모든 Pod 로그가 빈다.
- 노드 메트릭: node-exporter. 노드 자체를 재야 하니 hostPID, hostNetwork를 쓴다.
- 네트워크: kube-proxy, CNI 에이전트(Cilium, Calico). 노드의 iptables·eBPF 규칙을 직접 고친다. 이게 빠진 노드는 Pod 네트워크가 안 된다([CNI 글](/posts/k8s-cni-pod-network)).
- 스토리지와 장치: CSI 노드 플러그인(디스크를 노드에 붙이고 마운트한다), GPU 디바이스 플러그인.
- 보안: 런타임 감시 에이전트(Falco 같은 것).

비슷해 보이는 것이 static Pod다. kubelet이 노드의 매니페스트 디렉터리(kubeadm은 `/etc/kubernetes/manifests`)를 읽어 API 서버 없이 직접 띄운다. API 서버 자신도 이렇게 뜬다. API 서버가 없을 때도 떠야 하는 것은 static Pod, 나머지 노드 에이전트는 DaemonSet이다. 클러스터 구성 요소가 어디서 도는지는 [쿠버네티스 구조 글](/posts/k8s-architecture)에 있다.

## 노드마다 하나, 그 대가

DaemonSet은 노드 수를 replicas로 삼아, 조건에 맞는 노드마다 그 노드 전용 Pod를 만들고 배치는 스케줄러에 맡긴다. 기본 toleration 덕분에 노드가 아프거나 cordon돼도 버티지만, 나중에 건 NoSchedule taint는 다음 배포 때 조용히 에이전트를 빼 간다. 업데이트는 하나 빼고 넣는 maxUnavailable이 기본이고, 노드 자원을 혼자 쥐는 에이전트에서는 maxSurge가 막힌다. requests는 노드마다 고정 비용으로 빠지고, 높은 우선순위는 그 자리를 앱에서 빼앗는다.

## 면접에서 나올 만한 질문

### DaemonSet은 언제 쓰나요?

노드마다 정확히 하나씩 있어야 하는 에이전트에 쓴다. 로그 수집기, node-exporter, kube-proxy와 CNI 에이전트, CSI 노드 플러그인, GPU 디바이스 플러그인이 대표다. replicas 대신 조건에 맞는 노드 수가 Pod 수가 되고, 노드가 붙으면 자동으로 Pod가 생긴다.

### DaemonSet Pod는 누가 노드에 배치하나요?

지금은 기본 스케줄러가 한다. 컨트롤러가 `matchFields`로 노드 이름을 박은 node affinity를 붙여 Pod를 만들고, 스케줄러가 그 노드 하나를 후보로 놓고 평소 규칙대로 거른다. 그래서 자리가 없으면 Pending이 되고 우선순위가 높으면 선점도 한다. 1.11 이전에는 컨트롤러가 nodeName을 직접 채웠다.

### control-plane 노드에 DaemonSet Pod가 안 뜹니다.

control-plane 노드의 `node-role.kubernetes.io/control-plane:NoSchedule` taint 때문이다. 템플릿에 그 taint를 견디는 toleration을 넣으면 뜬다. 노드 전체를 덮어야 하는 에이전트는 `operator: Exists` toleration으로 모든 taint를 견디게 두는 경우가 많다. 나중에 건 NoSchedule taint 때문에 다음 배포에서 에이전트가 사라지는 일도 이걸로 막는다.

### DaemonSet 업데이트에 maxSurge를 쓰면 무엇이 좋고 무엇을 조심하나요?

새 Pod가 Ready가 된 뒤 옛 Pod를 지우니 노드에 에이전트가 비는 순간이 없다. 하지만 노드에 하나뿐인 자원을 쓰는 에이전트에는 못 쓴다. hostNetwork Pod는 hostPort가 containerPort로 채워져서 새 Pod가 포트 충돌로 Pending이 되고, 옛 Pod는 새 Pod를 기다리느라 안 지워져 롤아웃이 멈춘다. 그런 에이전트는 maxUnavailable을 쓴다.

### 노드 에이전트의 requests는 어떻게 정하나요?

노드마다 한 번씩 빠지는 고정 비용이라 작게, 그러나 실제 사용량에 맞게 잡는다. 노드 allocatable에서 DaemonSet requests 합을 뺀 것이 앱 자리이고, 작은 노드를 많이 쓸수록 비율이 커진다. 꽉 찬 노드에서도 떠야 하면 `system-node-critical` 우선순위를 주는데, 그러면 앱 Pod를 선점하니 넣기 전에 남은 자리를 계산한다. 메모리 limits는 버퍼 설정과 함께 정한다.

### drain할 때 `--ignore-daemonsets`는 왜 필요한가요?

DaemonSet Pod는 지워도 컨트롤러가 같은 노드에 바로 다시 만들기 때문에 drain이 비울 수 없다고 보고 멈춘다. 이 옵션은 DaemonSet Pod는 남기고 나머지만 내보낸다는 뜻이다. DaemonSet Pod는 unschedulable toleration이 있어 cordon한 노드에도 다시 뜨며, 노드를 끄기 직전까지 로그와 메트릭을 남긴다.

### 셸이 없는 에이전트 컨테이너는 어떻게 디버깅하나요?

`kubectl debug`로 임시 컨테이너를 붙이고 `--target`으로 대상 컨테이너의 프로세스 네임스페이스를 공유한다. 임시 컨테이너는 한 번 붙이면 뗄 수 없고 Pod가 다시 만들어질 때까지 남는다. 노드 자체를 봐야 하면 `kubectl debug node/<이름>`이 호스트 네임스페이스와 루트 파일시스템을 붙인 Pod를 띄우는데, 권한이 커서 RBAC로 좁혀 둔다.
