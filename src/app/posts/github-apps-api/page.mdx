월요일 아침, 배포 채널이 조용하다. PR이 머지되면 릴리스 노트를 만들고 Slack에 알리던 사내 봇이 금요일부터 아무 말이 없다. 로그에는 `401 Bad credentials`만 쌓여 있다. 찾아보니 봇은 2년 전 입사한 동료가 자기 계정으로 만든 개인 액세스 토큰(PAT)을 쓰고 있었고, 그 동료가 금요일에 퇴사하면서 조직에서 빠졌다. 토큰과 함께 봇의 권한도 사라졌다.

더 불편한 사실은 그다음에 보인다. 그 토큰은 `repo` 범위의 classic 토큰이라, 2년 동안 봇은 그 동료가 볼 수 있는 모든 비공개 저장소를 읽고 쓸 수 있었다. 봇 서버가 털렸다면 회사 코드 전부가 나갔다.

이 글은 이 봇을 제대로 다시 만드는 길을 따라간다. GitHub이 프로그램에게 주는 신원(PAT, OAuth App, GitHub App)이 무엇이 다른지, REST와 GraphQL API의 레이트 리밋과 페이지네이션이 어떻게 다른지, 웹훅을 받아 처리하는 흐름, 그리고 스크립트와 CI에서 `gh` CLI로 PR과 릴리스를 다루는 법을 본다. 저장소 설정(브랜치 보호, CODEOWNERS)은 [저장소 거버넌스 글](/posts/github-repo-governance)에서, 웹훅 서명 검증은 [웹훅 글](/posts/webhooks#누가-보냈는지-서명으로-확인한다)에서 다뤘다.

실습 환경에서는 GitHub API에 나가는 요청이 막혀 있어서, API 응답은 공식 문서에 나온 형식만 짧게 보이고 숫자는 문서 기준으로 적었다. 로컬에서 돌릴 수 있는 것(JWT 만들기, `gh` 도움말, 헤더 해석)은 직접 돌렸다. 레이트 리밋 숫자는 2026년 공식 문서 기준이고 GitHub이 바꿀 수 있으니 쓰기 전에 다시 확인한다.

## 프로그램에게 줄 수 있는 세 가지 신원

GitHub API를 부르려면 누군가로서 인증해야 한다. 고를 수 있는 신원이 크게 셋이다.

개인 액세스 토큰(PAT)은 사람 계정에 딸린 토큰이다. classic 토큰은 `repo`, `workflow`, `admin:org` 같은 넓은 범위(scope)를 고르고, 그 사람이 접근할 수 있는 모든 저장소에 그 범위가 걸린다. fine-grained 토큰은 한 소유자(개인이나 조직) 안에서 저장소를 골라 담고, Contents 읽기, Pull requests 쓰기처럼 권한을 항목별로 준다. 만료 기한을 두는 것이 기본이고, 조직은 fine-grained 토큰을 쓰려면 관리자 승인을 받도록 정책을 걸 수 있다. 어느 쪽이든 행동의 주체는 사람이다. 토큰으로 단 댓글은 그 사람 이름으로 달린다.

OAuth App은 "사용자 대신" 행동하는 앱이다. 사용자가 로그인 화면에서 허락하면 앱이 그 사용자의 토큰을 받는다(흐름은 [OAuth 글](/posts/oauth)과 같다). 범위는 classic PAT와 같은 넓은 scope 체계라서, `repo`를 받으면 그 사용자의 모든 비공개 저장소가 열린다. 토큰은 기본으로 만료되지 않고 사용자가 취소하거나 오래 안 쓰면 사라진다. "GitHub으로 로그인" 버튼처럼 사용자 신원이 필요한 곳에 쓰는 모델이다.

GitHub App은 그 자체가 하나의 신원이다. 조직이나 저장소에 "설치"되고, 설치할 때 관리자가 고른 저장소에만, 앱이 요청한 항목별 권한만 받는다. 댓글은 `릴리스봇[bot]` 같은 봇 이름으로 달린다. 앱을 만든 사람이 퇴사해도 앱은 조직 소유로 남는다. 짧게 사는 설치 토큰을 쓰고, 설치 수와 저장소 수에 따라 레이트 리밋도 커진다.

처음 장면의 봇을 이 셋에 대 보면 왜 GitHub App이어야 하는지가 나온다. 봇은 특정 사용자 대신 행동할 이유가 없다. 필요한 건 저장소 몇 개에 대한 좁은 권한, 사람과 무관한 수명, 그리고 이벤트를 받을 웹훅이다. GitHub App은 셋을 모두 기본으로 준다.

세 신원이 저장소에 닿는 길을 그림으로 놓으면 차이가 보인다. 사람을 거치는 길은 사람의 권한 전체를 지나고, GitHub App의 길은 설치라는 좁은 문을 지난다.

JWT는 앱 관리 API(설치 목록 보기, 설치 토큰 발급)에만 쓰고, 저장소 작업에는 쓸 수 없다. 저장소 작업은 설치 토큰으로 한다. 이렇게 나눈 덕분에 오래 사는 비밀은 개인 키 하나뿐이고, 실제로 저장소를 만지는 토큰은 한 시간이면 쓸모가 없어진다.

JWT가 어떻게 생겼는지 로컬에서 만들어 봤다. 실습용 RSA 키를 만들고, 시각은 재현할 수 있게 고정했다.

```bash
# 실습용 개인 키를 만든다 (실제 앱 키는 GitHub 앱 설정 화면에서 내려받는다)
openssl genrsa -out app.pem 2048
```

```js
// jwt.mjs: GitHub App용 JWT를 만들고 내용을 다시 읽어 본다
import { createSign, createPublicKey, createVerify } from "node:crypto";
import { readFileSync } from "node:fs";

const pem = readFileSync("app.pem", "utf8");
const b64url = (o) => Buffer.from(JSON.stringify(o)).toString("base64url");
const now = 1792800000; // 2026-10-24 00:00:00 UTC로 고정
const header = { alg: "RS256", typ: "JWT" };
// 시계 차이를 감안해 iat는 60초 앞으로, exp는 10분 한도 안으로
const payload = { iat: now - 60, exp: now + 9 * 60, iss: "Iv23liExampleClientId" };
const data = `${b64url(header)}.${b64url(payload)}`;
const sig = createSign("RSA-SHA256").update(data).sign(pem, "base64url");
const jwt = `${data}.${sig}`;

console.log(jwt.split(".").map((p) => p.length));
console.log(JSON.parse(Buffer.from(jwt.split(".")[1], "base64url")));
console.log("exp - iat =", payload.exp - payload.iat, "초");
const ok = createVerify("RSA-SHA256").update(data).verify(createPublicKey(pem), sig, "base64url");
console.log("verify:", ok);
```

```text
[ 36, 87, 342 ]
{ iat: 1792799940, exp: 1792800540, iss: 'Iv23liExampleClientId' }
exp - iat = 600 초
verify: true
```

`iat`를 60초 당겨 두는 건 GitHub 문서도 권하는 방법이다. 봇 서버의 시계가 GitHub보다 조금 빠르면 "아직 발급되지 않은 토큰"으로 거절되기 때문이다. `exp`가 10분을 넘으면 역시 거절된다. 실무에서는 이걸 직접 만들기보다 Octokit의 `@octokit/auth-app` 같은 라이브러리에 맡기는데, 라이브러리가 하는 일이 바로 이것이고 설치 토큰 캐시와 갱신까지 해 준다.

개인 키는 앱의 모든 설치에 토큰을 찍어 낼 수 있는 열쇠다. 코드 저장소에 두지 않고 비밀 관리 도구에 넣고([비밀 관리 글](/posts/secrets-management)), 앱 설정에서 키를 두 개 만들어 겹치게 둔 뒤 교체한다.

## OAuth App과 GitHub App, 사용자 대신 행동할 때

봇이 아니라 사용자가 필요한 경우도 있다. 예를 들어 사내 대시보드에서 "내가 리뷰할 PR"을 보여 주려면 그 사용자로서 API를 불러야 한다. 이때도 GitHub App을 쓸 수 있다. GitHub App은 사용자 접근 토큰(user access token)을 발급받는 OAuth 흐름을 따로 갖고 있어서, 사용자로 행동하되 앱 권한과 사용자 권한이 겹치는 범위로만 움직인다. 이 토큰은 기본으로 8시간 뒤 만료되고 리프레시 토큰으로 갱신한다.

OAuth App을 새로 만들 이유는 점점 줄고 있다. 범위가 넓고(scope가 저장소를 고르지 못한다), 토큰이 오래 살고, 조직 관리자가 승인한 앱인지 따지는 정책도 GitHub App 쪽이 더 세밀하다. 다만 오래된 도구 중에는 OAuth App만 지원하는 것이 있고, 설치 과정 없이 "로그인만" 붙이고 싶을 때는 여전히 간단하다.

정리하면 고르는 기준은 두 질문이다. 사람으로 행동해야 하나, 앱으로 행동해야 하나. 그리고 접근할 저장소를 좁혀야 하나. 사람으로 행동하고 범위가 좁으면 GitHub App의 사용자 토큰, 앱으로 행동하면 설치 토큰이다. 개인 스크립트 하나를 내 저장소에 돌리는 정도면 fine-grained PAT로 충분하다. classic PAT와 OAuth App은 그 밖의 선택지가 없을 때만 쓴다.

## REST와 GraphQL은 비용을 다르게 센다

GitHub은 REST API와 GraphQL API를 둘 다 연다. 같은 데이터를 두 길로 읽을 수 있지만 요청 수를 세는 방식이 다르다.

REST는 요청 하나가 하나로 세진다. 인증한 사용자나 PAT는 시간당 5,000번이다. GitHub App 설치 토큰은 최소 5,000번에서 시작해 설치된 저장소 수와 조직 사용자 수에 따라 늘어나며 최대 12,500번까지 간다(Enterprise Cloud 조직은 더 높다). Actions의 `GITHUB_TOKEN`은 저장소당 시간당 1,000번이고, 인증하지 않은 요청은 IP당 60번이다. 응답마다 남은 양이 헤더로 온다. 형식은 이렇다.

```text
x-ratelimit-limit: 5000
x-ratelimit-remaining: 4987
x-ratelimit-used: 13
x-ratelimit-reset: 1792803600
x-ratelimit-resource: core
```

`reset`은 한도가 다시 채워지는 유닉스 시각이다. `remaining`이 0이 되면 403이나 429가 오고, 그때는 `reset`까지 기다리거나 `retry-after` 헤더가 있으면 그만큼 기다린다. 시간당 한도와 별개로 2차 한도(secondary rate limit)도 있다. 동시 요청은 100개를 넘기지 말고, 같은 엔드포인트를 빠르게 두드리거나 콘텐츠를 만드는 요청(이슈, 댓글)을 몰아서 보내면 시간당 한도가 남아 있어도 막힌다. 그래서 봇은 쓰기 요청을 순서대로 하나씩 보내고, 막히면 지수적으로 기다린다([요청 수 제한 글](/posts/rate-limiting-in-practice)의 클라이언트 쪽 대응과 같다).

한도를 아끼는 가장 쉬운 방법은 조건부 요청이다. 응답의 `etag`를 저장해 두고 다음 요청에 `If-None-Match`로 보내면, 바뀐 게 없을 때 GitHub이 본문 없이 `304 Not Modified`를 주고 이 요청은 한도에서 빠진다. 같은 목록을 주기적으로 훑는 봇이라면 이것만으로 소비가 크게 준다. 가능하면 아예 훑지 않고 웹훅으로 바뀐 순간에만 알림을 받는 게 더 낫다.

GraphQL은 요청 수가 아니라 점수로 센다. 쿼리 하나를 실행하기 전에 GitHub이 "이 쿼리를 REST로 했다면 몇 번 불렀을까"를 바탕으로 비용을 계산하고, 시간당 5,000점(사용자 기준, 앱 설치는 REST처럼 늘어난다)에서 뺀다. 저장소 20개의 최근 PR 10개씩을 한 쿼리로 가져오면 REST로는 수십 번 부를 일을 한두 점에 끝낼 수 있다. 반대로 깊게 중첩된 연결을 크게 잡으면 한 쿼리가 수백 점을 먹는다. 비용은 쿼리 안에서 직접 물어볼 수 있다.

```graphql
query {
  repository(owner: "acme", name: "shop") {
    pullRequests(last: 10, states: MERGED) {
      nodes { number title mergedAt }
    }
  }
  # 이 쿼리의 비용과 남은 점수를 함께 받는다
  rateLimit { cost remaining resetAt }
}
```

GraphQL 쪽에는 규칙이 하나 더 있다. 목록 필드는 반드시 `first`나 `last`를 1~100 사이로 줘야 하고, 한 쿼리가 건드릴 수 있는 노드 수에도 상한이 있다. 무엇을 고를지는 이렇게 판단한다. 여러 자원을 엮어 한 화면을 만드는 읽기(대시보드)는 GraphQL이 요청 수와 응답 크기 모두에서 유리하다. 쓰기, 파일 다루기, 릴리스 자산 올리기처럼 REST에만 있거나 REST가 단순한 작업은 REST로 한다. GraphQL 자체의 개념은 [GraphQL 기초](/posts/graphql-basics)에 정리했다.

## 페이지를 넘기는 방식도 다르다

REST 목록은 한 번에 기본 30개, `per_page`로 최대 100개까지 준다. 다음 페이지 주소는 `Link` 헤더에 담겨 온다. 공식 문서에 나오는 형식은 이렇다.

```text
link: <https://api.github.com/repositories/1300192/issues?per_page=100&page=2>; rel="next", <https://api.github.com/repositories/1300192/issues?per_page=100&page=7>; rel="last"
```

여기서 흔한 실수가 `page=2, 3, 4…`를 직접 만들어 부르는 것이다. GitHub의 엔드포인트 중에는 페이지 번호 대신 `after=커서` 같은 커서로 넘기는 것도 있고, 이때는 `last`가 아예 없다. 그래서 주소를 만들지 말고 `rel="next"`가 가리키는 주소를 그대로 따라가다가 `next`가 없으면 멈춘다. 헤더 해석을 직접 짜 보자.

## 웹훅을 받는 쪽에서 할 일

GitHub App에는 웹훅 URL이 하나 붙고, 앱이 구독한 이벤트가 모든 설치에서 그 URL로 온다. 요청마다 세 헤더가 핵심이다. `X-GitHub-Event`는 이벤트 종류(`pull_request`, `push`), `X-GitHub-Delivery`는 배달마다 다른 id, `X-Hub-Signature-256`은 본문의 HMAC 서명이다.

받는 순서는 [웹훅 글](/posts/webhooks)에서 다룬 원칙 그대로다. 먼저 원문 본문으로 서명을 확인하고, `X-GitHub-Delivery`로 이미 처리한 배달인지 거른 뒤, 큐에 넣고 바로 2xx로 답한다. GitHub은 10초 안에 응답이 없으면 실패로 기록한다. 그리고 실패한 배달을 자동으로 다시 보내 주지 않는다. 봇 서버가 배포 중이라 몇 분 꺼져 있었다면 그 사이 이벤트는 앱 설정의 "Recent Deliveries"나 API로 직접 다시 보내 달라고 해야 한다. 그래서 중요한 작업은 웹훅만 믿지 않고, 주기적으로 상태를 맞춰 보는 보조 작업(예를 들어 한 시간마다 최근 머지된 PR을 조회해 놓친 게 있는지 확인)을 같이 둔다.

이벤트 본문에는 `installation.id`가 들어 있다. 앞의 흐름처럼 이 id로 그 설치의 토큰을 받아야 하니, 여러 조직에 설치된 앱이라면 설치 id별로 토큰을 캐시한다.

## 스크립트와 CI에서는 gh CLI

API를 직접 부르는 코드를 매번 짤 필요는 없다. `gh` CLI는 PR, 이슈, 릴리스, Actions를 명령으로 다루고, 인증과 페이지네이션도 처리해 준다. 실습에 쓴 버전은 2.89.0이다.

```bash
# 대화형 로그인 (내 노트북)
gh auth login
# CI에서는 환경 변수 GH_TOKEN(또는 GITHUB_TOKEN)만 있으면 로그인 없이 쓴다
export GH_TOKEN=ghs_xxx
# 현재 브랜치로 PR을 만든다. 커밋 메시지로 제목과 본문을 채운다
gh pr create --fill --base main
# 필수 검사와 리뷰가 끝나면 스쿼시로 자동 병합되게 걸어 둔다
gh pr merge --squash --auto
# 태그가 원격에 있는지 확인하고, 자동 생성한 노트와 빌드 결과물로 릴리스를 만든다
gh release create v1.4.0 --verify-tag --generate-notes dist/*.tgz
```

`gh api`는 아무 엔드포인트나 부르는 탈출구다. 도움말에서 실무에 쓸 옵션만 뽑아 봤다.

```bash
# gh api에서 페이지네이션, jq, 자리 표시자 관련 설명만 본다
gh api --help | grep -E "paginate|slurp|jq|\{owner\}|cache"
```

```text
Placeholder values `{owner}`, `{repo}`, and `{branch}` in the endpoint
- placeholder values `{owner}`, `{repo}`, and `{branch}` get populated with values
In `--paginate` mode, all pages of results will sequentially be requested until
JSON array or object. Pass `--slurp` to wrap all pages of JSON arrays or objects
      --cache duration        Cache the response, e.g. "3600s", "60m", "1h"
  -q, --jq string             Query to select values from the response using jq syntax
      --paginate              Make additional HTTP requests to fetch all pages of results
      --slurp                 Use with "--paginate" to return an array of all pages of either JSON arrays or objects
```

`--paginate`가 앞에서 짠 `Link` 헤더 따라가기를 대신 해 준다. GraphQL도 `gh api graphql`로 부르고, 쿼리에 `$endCursor` 변수와 `pageInfo`를 넣으면 `--paginate`가 커서를 넘겨 가며 끝까지 받는다. `{owner}/{repo}`는 지금 폴더의 git 원격에서 채워진다.

```bash
# 열린 PR 중 리뷰를 기다리는 것의 번호와 제목만 모든 페이지에서 뽑는다
gh api 'repos/{owner}/{repo}/pulls?state=open&per_page=100' --paginate \
  --jq '.[] | select(.draft == false) | "\(.number)\t\(.title)"'
```

GitHub Actions에서는 `gh`가 러너에 미리 깔려 있고, 워크플로의 `GITHUB_TOKEN`을 `GH_TOKEN`으로 넘기면 된다. 이 토큰은 그 저장소 하나에만, `permissions`에 적은 권한만 갖고 작업이 끝나면 만료된다. 다른 저장소를 건드려야 하거나, 봇이 만든 PR에서 다시 워크플로가 돌아야 한다면(`GITHUB_TOKEN`으로 만든 이벤트는 새 워크플로를 트리거하지 않는다) GitHub App 설치 토큰을 쓴다. `actions/create-github-app-token` 액션이 앱 ID와 개인 키로 설치 토큰을 찍어 준다.

```yaml
permissions:
  contents: write   # 릴리스를 만들려면 필요하다
jobs:
  release:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - run: gh release create "$GITHUB_REF_NAME" --verify-tag --generate-notes
        env:
          GH_TOKEN: ${{ github.token }}
```

CI에서 패키지를 배포하는 흐름과 provenance는 [npm 패키지 배포 글](/posts/npm-package-publishing#배포-직전에-보는-것과-provenance)에서 이어진다.

## 만든 앱을 남에게 줄 때: Marketplace

사내 봇이 아니라 다른 조직도 설치할 수 있는 앱을 만들면 공개 앱으로 바꾸고 GitHub Marketplace에 올릴 수 있다. Marketplace에는 GitHub App과 Actions가 올라가고, 유료 요금제를 붙이면 결제는 GitHub 청구서로 처리된다. 설치할 때 사용자는 앱이 요청한 권한 목록을 보고 저장소를 고른다. 그래서 공개 앱일수록 권한을 최소로 요청하는 게 설치율에도 직접 영향을 준다. Contents 쓰기 권한을 요구하는 린트 앱은 관리자가 설치를 망설인다.

## 현장에서 GitHub 연동이 깨지는 순간

`401 Bad credentials`는 토큰이 만료됐거나 취소됐거나 주인이 사라진 것이다. PAT라면 주인 계정과 만료일부터 본다. 설치 토큰이라면 1시간이 지나도록 캐시를 쓰고 있지 않은지 본다.

`403 Resource not accessible by integration`은 GitHub App이나 `GITHUB_TOKEN`에 그 권한이 없다는 뜻이다. 앱 설정에서 권한을 추가하면 각 설치의 관리자가 새 권한을 승인해야 적용된다는 것도 잊기 쉽다. 승인 전까지는 이전 권한으로 동작한다.

`404 Not Found`인데 저장소가 분명히 있다면 대개 권한 문제다. GitHub은 비공개 자원에 권한이 없을 때 존재 자체를 숨기려고 404를 준다. 설치할 때 그 저장소를 고르지 않았거나, fine-grained 토큰에 그 저장소를 담지 않은 경우다.

`403`에 `x-ratelimit-remaining: 0`이면 시간당 한도, `remaining`이 남았는데 403·429면 2차 한도다. 응답 본문의 메시지가 둘을 구분해 준다. 2차 한도라면 동시 요청을 줄이고 쓰기 요청 사이에 간격을 둔다.

웹훅이 안 온다면 앱 설정의 Recent Deliveries에서 응답 코드를 본다. 아예 배달 기록이 없으면 그 이벤트를 구독하지 않았거나, 앱에 그 이벤트를 볼 권한이 없는 것이다. 이벤트 구독은 권한에 묶여 있어서 Pull requests 읽기 권한이 없으면 `pull_request` 이벤트를 고를 수도 없다.

## 봇에게는 봇의 신원을

처음 장면의 봇이 멈춘 건 토큰이 사람에게 묶여 있었기 때문이고, 위험했던 건 그 사람이 가진 모든 권한을 같이 들고 있었기 때문이다. GitHub App은 이 두 문제를 구조로 푼다. 조직이 소유하고, 고른 저장소에 고른 권한만 받고, 한 시간짜리 토큰으로 일한다. API는 여러 자원을 엮는 읽기는 GraphQL, 단순한 쓰기는 REST로 나눠 쓰고, `Link` 헤더와 커서를 따라가며 한도 헤더를 본다. 반복되는 손일은 `gh`가 대신한다.

## 면접에서 나올 만한 질문

### 사내 봇은 왜 PAT가 아니라 GitHub App으로 만드나요?

PAT는 사람 계정에 묶여 있어서 그 사람이 퇴사하면 봇도 멈추고, 그 사람이 가진 모든 권한을 봇이 같이 갖는다. GitHub App은 조직 소유의 별도 신원이라 사람과 수명이 무관하고, 설치할 때 고른 저장소에 항목별 권한만 받는다. 토큰도 1시간짜리 설치 토큰이라 새어도 피해가 짧고, 레이트 리밋도 설치 규모에 따라 늘어난다.

### GitHub App의 인증 흐름을 설명해 주세요.

두 단계다. 먼저 앱의 개인 키로 RS256 JWT를 만들어 앱 자신을 증명한다. iss는 앱의 Client ID나 App ID, exp는 10분 이내다. 이 JWT로 특정 설치의 액세스 토큰을 요청하면 1시간짜리 토큰이 오고, 실제 저장소 작업은 그 토큰으로 한다. 오래 사는 비밀은 개인 키 하나뿐이다.

### OAuth App과 GitHub App은 무엇이 다른가요?

OAuth App은 항상 사용자 대신 행동하고, scope가 넓어서 저장소를 고를 수 없으며 토큰이 기본으로 만료되지 않는다. GitHub App은 앱 자신으로도, 사용자 대신으로도 행동할 수 있고, 항목별 권한과 저장소 선택, 짧은 토큰 수명을 기본으로 준다. 새로 만든다면 대부분 GitHub App이 맞고, OAuth App은 로그인만 간단히 붙이거나 오래된 도구가 요구할 때 쓴다.

### classic PAT와 fine-grained PAT는 무엇이 다른가요?

classic은 `repo` 같은 넓은 범위를 고르면 그 사람이 접근 가능한 모든 저장소에 걸린다. fine-grained는 한 소유자 안에서 저장소를 고르고 Contents, Pull requests처럼 권한을 항목별로 주며, 만료 기한을 둔다. 조직은 fine-grained 토큰에 관리자 승인을 요구할 수 있다. 둘 다 사람의 신원이라는 점은 같다.

### GitHub API에서 REST와 GraphQL의 레이트 리밋은 어떻게 다른가요?

REST는 요청 하나를 하나로 세서 인증 사용자는 시간당 5,000번이다. GraphQL은 쿼리마다 비용 점수를 계산해 시간당 5,000점에서 뺀다. 여러 자원을 엮는 읽기는 GraphQL이 훨씬 싸지만, 크게 중첩된 쿼리는 한 번에 수백 점을 먹는다. 둘 다 2차 한도가 따로 있어서 동시 요청과 몰아서 보내는 쓰기 요청을 제한한다.

### 레이트 리밋에 걸리지 않게 봇을 설계하려면요?

폴링 대신 웹훅으로 바뀐 순간에만 일한다. 폴링이 필요하면 ETag로 조건부 요청을 보내 304를 받으면 한도에서 빠진다. 응답의 `x-ratelimit-remaining`과 `reset`을 보고 속도를 조절하고, 쓰기 요청은 순서대로 보내며 403·429에는 `retry-after`나 지수 백오프로 기다린다. 여러 자원을 엮는 읽기는 GraphQL 한 번으로 합친다.

### REST 목록 API의 페이지를 넘길 때 주의할 점은요?

페이지 번호를 직접 만들지 말고 `Link` 헤더의 `rel="next"` 주소를 따라간다. 일부 엔드포인트는 커서 방식이라 페이지 번호가 없고 `last`도 없다. `next`가 없으면 끝이고, `per_page`는 최대 100이다. `gh api --paginate`나 Octokit의 paginate 기능이 이걸 대신 해 준다.

### GitHub 웹훅 처리에서 놓치기 쉬운 것은요?

GitHub은 실패한 배달을 자동으로 다시 보내지 않는다. 10초 안에 2xx를 못 주면 실패로 남고, 서버가 꺼져 있던 사이의 이벤트는 직접 재전송을 요청해야 한다. 그래서 서명 확인 후 저장하고 바로 응답하고, `X-GitHub-Delivery`로 중복을 거르며, 주기적으로 상태를 조회해 놓친 이벤트를 맞추는 보조 작업을 둔다.
