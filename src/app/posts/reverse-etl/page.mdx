영업팀장이 묻는다. "고객 화면에 최근 30일 구매액이 보였으면 좋겠어요. VIP한테 먼저 전화하게." 그 숫자는 이미 웨어하우스에 있다. [dbt](/posts/dbt-transformations)로 매일 새벽 만드는 고객 지표 테이블의 한 컬럼이다. 문제는 영업팀이 웨어하우스를 보지 않는다는 것이다. 그들은 하루 종일 CRM(고객 관리 도구) 화면에 있다. 지금은 데이터 팀이 매주 CSV를 뽑아 보내고, 영업팀 누군가가 CRM에 올린다. 지난주에는 그 사람이 휴가였다.

웨어하우스에서 만든 데이터를 CRM, 광고 플랫폼, 고객 지원 도구, 마케팅 메일 도구 같은 업무 도구로 다시 보내는 걸 리버스 ETL이라고 부른다. 보통의 ETL이 여러 원천에서 웨어하우스로 모으는 방향이라면, 이건 반대 방향이다. 모으는 쪽 이야기는 [ETL과 ELT](/posts/etl-vs-elt)에 있다. 이 글은 리버스 ETL이 실제로 풀어야 하는 문제들, 즉 무엇을 보낼지 고르는 변경분 계산, API 호출 한도와 재시도, 웨어하우스 행과 도구 쪽 레코드를 잇는 키, 삭제를 전하는 법을 작은 가짜 CRM으로 직접 돌려 본다. 이벤트를 모으는 CDP와 리버스 ETL 도구의 자리, 직접 짤지 도구를 쓸지도 정리한다.

## 반대 방향으로 흐르는 파이프

ETL과 리버스 ETL은 방향만 반대인 같은 일처럼 보이지만, 받는 쪽의 성격이 완전히 다르다.

- ETL의 받는 쪽은 웨어하우스다. 한 번에 수백만 행을 넣어도 버티고, SQL로 덮어쓰기와 병합이 된다. 틀리면 다시 넣으면 된다.
- 리버스 ETL의 받는 쪽은 SaaS 도구의 API다. 한 번에 보낼 수 있는 건수가 작고(배치당 수십~수백 건), 초당·일일 호출 한도가 있고, 레코드마다 도구 쪽 id가 따로 있다. 잘못 보낸 값은 영업 사원 화면에 바로 뜨고, 그 값으로 마케팅 메일이 나간다.

그래서 리버스 ETL의 고민은 대부분 받는 쪽 API를 어떻게 다루느냐에 있다. 웨어하우스 쪽 일은 오히려 단순하다. 보낼 모양 그대로 테이블(또는 뷰) 하나를 만들어 두면 된다. 이 글에서는 `crm_customer_metrics`라는 모델을 만들었다고 하자. 고객 id, 이메일, 최근 30일 구매액이 들어 있다.

```sql
-- 보낼 모양 그대로 만든 모델: 고객 한 명당 한 줄 (DuckDB로 실행)
select customer_id, email, purchase_30d
from crm_customer_metrics
order by customer_id;
```

## 보낼 모양은 웨어하우스에서 만든다

동기화 도구 안에서 계산하지 않는다. 받는 쪽 필드 하나에 컬럼 하나가 맞도록, 보낼 모양 그대로의 모델을 웨어하우스에 만든다. 계산 규칙이 SQL로 저장소에 남고, 테스트를 붙일 수 있고, 같은 숫자를 BI와 CRM이 함께 본다. 고객 지표 모델을 작은 예제 테이블로 만들어 DuckDB에서 돌렸다. 기준일은 10월 24일이다.

```sql
-- crm_customer_metrics: 고객 한 명당 한 줄, CRM 필드 이름에 맞춘 컬럼
select
    c.customer_id,
    lower(trim(c.email)) as email,                      -- 매칭 키는 보내기 전에 정규화한다
    coalesce(sum(o.amount) filter (
        where o.status = 'paid'
          and o.paid_at >= TIMESTAMP '2026-10-24' - interval 30 day), 0) as purchase_30d
from customers c
left join orders o using (customer_id)                 -- 주문이 없는 고객도 한 줄 남긴다
group by 1, 2
order by 1;
```

```text
┌─────────────┬─────────────────────┬──────────────┐
│ customer_id │        email        │ purchase_30d │
│    int32    │       varchar       │    int128    │
├─────────────┼─────────────────────┼──────────────┤
│         101 │ haneul@example.com  │        37000 │
│         102 │ doyoon@example.com  │        30000 │
│         103 │ seoyeon@example.com │            0 │
└─────────────┴─────────────────────┴──────────────┘
```

원본 이메일은 `' Haneul@Example.com'`, `'SEOYEON@example.com '`처럼 공백과 대문자가 섞여 있었는데 모델에서 정리됐다. 103번은 최근 30일에 환불된 주문 하나와 9월 주문 하나뿐이라 0이다. `left join`과 `coalesce`가 없으면 103번은 행이 아예 빠지거나 NULL이 된다. 행이 빠지면 동기화기는 "사라진 행"으로 보고 삭제를 보내고, NULL은 도구마다 "필드를 비운다"로도 "보내지 않는다"로도 해석한다. 0이라고 분명히 보내는 편이 받는 쪽 화면에서 오해가 적다. 이 모델에도 `customer_id`의 `unique`, `email`의 `not_null` 테스트를 건다. 키가 중복된 모델은 동기화에서 같은 레코드를 두 번 고쳐 쓰고, 어느 값이 남을지 알 수 없다.

## 매번 전부 보내지 않고 달라진 것만

가장 단순한 구현은 매번 모델 전체를 읽어 전부 보내는 것이다. 고객이 8명이면 괜찮다. 50만 명이면 매일 50만 건 API 호출이 되고, 그중 대부분은 어제와 같은 값이다. CRM의 일일 API 한도를 그것만으로 다 쓰거나, 다 보내는 데 몇 시간이 걸린다. 그래서 지난번에 보낸 상태를 기억해 두고, 이번에 달라진 행만 보낸다.

달라진 행을 찾는 방법은 몇 가지다. 모델에 `updated_at`을 두고 지난 실행 뒤에 바뀐 행만 고르는 방법은 간단하지만, 지표 테이블은 매일 통째로 다시 만들어지는 경우가 많아 모든 행의 `updated_at`이 바뀐다. 그래서 리버스 ETL 도구들은 대개 지난번에 보낸 내용의 사본(또는 행마다의 해시)을 따로 저장해 두고 이번 결과와 비교한다. 비교 결과는 세 갈래다.

- 새로 생긴 행: 지난번에 없던 키. 도구에 만든다.
- 바뀐 행: 키는 있는데 값이 다르다. 도구에서 고친다.
- 사라진 행: 지난번엔 있었는데 이번엔 없다. 도구에서 지우거나, 값을 비우거나, 그냥 둔다(아래에서 다시 본다).

## 가짜 CRM으로 돌려 본 동기화

동작을 눈으로 보려고 Python과 DuckDB로 작은 동기화기를 짰다. 가짜 CRM은 초당 3번까지만 요청을 받고 넘으면 429와 `retry_after: 1`을 돌려준다. 외부 id로 고쳐 쓰는 `upsert`와, 무조건 새로 만드는 `create` 두 API가 있다. 동기화기는 상태 테이블(`sync_state`)에 고객마다 지난번에 보낸 행의 해시를 적어 두고, 배치(2건)마다 보내고, 성공하면 그 배치의 해시를 적는다.

```python
# rsync.py 일부 (Python 3.13, duckdb 1.5)
def sync(con, crm, use_upsert=True, crash_after_batches=None, batch_size=2):
    cur = {r[0]: {"customer_id": r[0], "email": r[1], "purchase_30d": r[2]}
           for r in con.sql("select customer_id, email, purchase_30d from crm_customer_metrics").fetchall()}
    prev = dict(con.sql("select customer_id, row_hash from sync_state").fetchall())
    changed = [r for k, r in cur.items() if prev.get(k) != row_hash(r)]   # 생성 + 수정
    removed = [k for k in prev if k not in cur]                           # 삭제
    log = []
    send = crm.upsert if use_upsert else crm.create
    for i in range(0, len(changed), batch_size):
        batch = changed[i:i + batch_size]
        call(send, batch, log)                     # 429면 retry_after만큼 쉬고 다시
        if crash_after_batches is not None and i // batch_size + 1 == crash_after_batches:
            raise RuntimeError(f"batch {i // batch_size + 1} 전송 뒤 상태 저장 전에 죽음")
        for r in batch:                            # 배치가 성공하면 해시를 적는다
            con.execute("insert or replace into sync_state values (?, ?)",
                        [r["customer_id"], row_hash(r)])
    if removed:
        call(crm.delete, removed, log)
        con.execute(f"delete from sync_state where customer_id in ({','.join(map(str, removed))})")
    return {"changed": len(changed), "removed": len(removed), "retries": log.count("429")}
```

가짜 CRM 쪽은 이렇게 생겼다. 1초 안에 들어온 요청이 3개면 그다음 요청은 429로 돌려보낸다.

```python
class FakeCRM:
    def _limit(self):
        now = time.monotonic()
        self.calls = [t for t in self.calls if now - t < 1.0]
        if len(self.calls) >= 3:
            return {"status": 429, "retry_after": 1}
        self.calls.append(now); return None
    def upsert(self, batch):                 # 외부 id로 찾아서 있으면 고치고 없으면 만든다
        if (e := self._limit()): return e
        for r in batch:
            cid = self.by_ext.get(r["customer_id"])
            if cid is None:
                cid = self.next_id; self.next_id += 1; self.by_ext[r["customer_id"]] = cid
            self.contacts[cid] = r
        return {"status": 200}
    def create(self, batch):                 # 무조건 새 레코드를 만든다
        if (e := self._limit()): return e
        for r in batch:
            self.contacts[self.next_id] = r; self.next_id += 1
        return {"status": 200}

def call(fn, arg, log):                      # 429면 retry_after만큼 쉬고 같은 요청을 다시
    while True:
        res = fn(arg)
        if res["status"] == 429:
            log.append("429"); time.sleep(res["retry_after"]); continue
        return res
```

먼저 처음 동기화, 바뀐 게 없을 때, 그리고 103번 구매액 수정·107번 삭제·109번 추가를 한 뒤의 동기화다.

```bash
python3 rsync.py
```

```text
== 1. 처음 동기화와 변경분 동기화
1회차: {'changed': 8, 'removed': 0, 'retries': 1} CRM 연락처 수: 8
2회차(바뀐 것 없음): {'changed': 0, 'removed': 0, 'retries': 0}
3회차(1건 수정, 1건 삭제, 1건 추가): {'changed': 2, 'removed': 1, 'retries': 0} CRM 연락처 수: 8
```

1회차는 8건을 배치 4개로 보내다 네 번째 요청에서 초당 한도에 걸려 한 번 쉬었다(`retries: 1`). 2회차는 아무것도 보내지 않았다. 3회차는 바뀐 2건과 지운 1건만 보냈다. 같은 결과를 매일 전부 보냈다면 매번 8건, 고객이 50만 명이면 매번 50만 건이다.

## 한도에 걸리면 기다렸다가 다시

SaaS API에는 거의 다 호출 한도가 있다. 초당이나 10초당 몇 번, 하루에 몇 번 하는 식이고, 넘으면 HTTP 429(Too Many Requests)를 돌려준다. 많은 API가 `Retry-After` 헤더로 몇 초 뒤에 다시 오라고 알려 준다. 리버스 ETL에서 지켜야 할 것들이다.

- 429와 5xx는 다시 시도하고, 4xx(잘못된 이메일 형식, 없는 필드)는 다시 시도하지 않는다. 같은 요청을 백 번 보내도 400은 400이다. 이런 행은 따로 모아 "거절된 행" 목록으로 남기고, 다음 실행에서 다시 보낼지 정한다.
- `Retry-After`가 있으면 그만큼 기다리고, 없으면 지수 백오프에 무작위 흔들림(지터)을 섞는다. 여러 동기화가 같은 순간에 한꺼번에 다시 몰려드는 걸 막는다. 재시도 설계 일반은 [재시도](/posts/retries)에 있다.
- 배치 API가 있으면 쓴다. Salesforce의 Bulk API나 HubSpot의 일괄 처리 엔드포인트처럼 한 번에 여러 건을 보내는 API를 쓰면 호출 수가 수십 분의 일로 준다. 대신 배치 안에서 일부만 실패하는 응답(부분 성공)을 행 단위로 풀어 읽어야 한다. 배치 전체가 200이어도 그 안의 3건은 거절됐을 수 있다.
- 한도는 그 도구를 쓰는 모든 연동이 나눠 쓴다. 우리 동기화가 일일 한도를 다 쓰면 영업팀이 쓰는 다른 연동이 멈춘다. 동기화마다 쓸 몫을 정해 둔다.

## 동기화가 두 번 일어나면

마지막 단계의 순서에는 피할 수 없는 틈이 있다. CRM이 배치를 받았는데, 상태 테이블에 적기 전에 동기화기가 죽으면 어떻게 될까. 다음 실행은 그 배치를 아직 안 보낸 것으로 보고 다시 보낸다. 같은 데이터가 두 번 간다. 반대로 적고 나서 보내면 보내다 죽은 행이 영영 빠진다. 둘 중 하나를 골라야 한다면 "두 번 보내기"를 고르고, 두 번 받아도 괜찮게 만든다. 메시지 전달의 "최소 한 번" 보장과 같은 이야기다([메시지 전달 보장](/posts/message-delivery-semantics)).

두 번 받아도 괜찮은지는 어떤 API를 쓰느냐에 달렸다. 실험에서 두 번째 배치를 보낸 직후 죽게 하고 다시 돌려 봤다.

```text
== 2. 전송 뒤 죽고 다시 돌리기 (create)
1회차: batch 2 전송 뒤 상태 저장 전에 죽음
다시 실행: {'changed': 6, 'removed': 0, 'retries': 1}
CRM 연락처 수: 10 중복 이메일: ['jiwoo@example.com', 'seoyeon@example.com']
== 2. 전송 뒤 죽고 다시 돌리기 (upsert)
1회차: batch 2 전송 뒤 상태 저장 전에 죽음
다시 실행: {'changed': 6, 'removed': 0, 'retries': 1}
CRM 연락처 수: 8 중복 이메일: []
```

두 경우 모두 다시 실행할 때 6건을 보냈다. 첫 배치(101, 102)는 상태가 적혔고, 두 번째 배치(103, 104)는 CRM에는 갔지만 상태가 안 적혀서 다시 보낸 것이다. `create`로 보낸 쪽은 103번 서연, 104번 지우가 CRM에 두 명씩 생겼다. 영업 사원 둘이 같은 고객에게 전화하고, 한쪽 레코드에만 메모가 쌓인다. `upsert`로 보낸 쪽은 같은 외부 id를 찾아 고쳐 썼으니 8명 그대로다.

그래서 리버스 ETL은 가능하면 외부 id 기준 upsert로 보낸다. Salesforce는 객체에 외부 ID 필드를 만들어 두면 그 필드로 upsert할 수 있고, 많은 CRM과 마케팅 도구가 이메일이나 지정한 고유 속성으로 고쳐 쓰는 API를 둔다. 도구가 upsert를 주지 않으면 처음 만들 때 받은 도구 쪽 id를 상태 테이블에 함께 적어 두고, 다음부터는 그 id로 수정한다. 이 경우 "만들었는데 id를 적기 전에 죽은" 틈이 다시 생기니, 만들기 전에 이메일 같은 값으로 이미 있는지 찾아보는 단계를 둔다.

두 번 보내기가 문제가 되는 곳이 하나 더 있다. 값을 덮어쓰는 게 아니라 더하는 API다. "구매 이벤트 추가"나 "포인트 적립"처럼 호출할 때마다 쌓이는 API에 같은 배치가 두 번 가면 숫자가 두 번 늘어난다. 이런 API로 보내야 한다면 요청마다 고유한 멱등 키를 붙이고, 받는 쪽이 같은 키를 한 번만 처리하는지 확인한다. 아예 "누적값을 덮어쓰기"로 바꿀 수 있으면 그게 낫다.

## 키를 맞추는 일

웨어하우스의 `customer_id = 103`이 CRM의 어느 레코드인지 정하는 것이 키 매칭이다. 의외로 여기서 사고가 많이 난다.

- 이메일로 맞추기. 대부분의 도구가 이메일을 이미 들고 있어서 쉽다. 그런데 사람은 이메일을 바꾸고, 대소문자와 공백이 섞여 들어가고(` Seoyeon@Example.com`), 한 사람이 이메일을 여러 개 쓴다. 보내기 전에 소문자로 바꾸고 공백을 지우는 정규화를 꼭 한다. 이메일이 바뀌면 upsert가 새 레코드를 만들어 버린다.
- 외부 id로 맞추기. 도구에 `warehouse_customer_id` 같은 사용자 정의 필드를 만들고 거기에 우리 id를 넣는다. 가장 안정적이다. 처음 연결할 때 이미 도구에 있던 레코드에 이 id를 채워 넣는 작업(백필)이 한 번 필요하다.
- 도구 쪽 id로 맞추기. CRM이 만든 id를 웨어하우스로 가져와(ETL) 모델에 붙여 두고 그걸로 보낸다. 정확하지만 그 id를 가져오는 ETL이 늦으면 새 고객은 매칭되지 않는다.

매칭이 안 된 행을 어떻게 할지도 정해야 한다. "있으면 고치고 없으면 만든다"가 기본이지만, 영업 CRM처럼 사람이 직접 레코드를 관리하는 도구에는 "있을 때만 고친다(update only)"가 맞는 경우가 많다. 리버스 ETL이 CRM에 없는 고객을 마구 만들면 영업팀이 정리해 둔 레코드 사이에 출처 모를 레코드가 섞인다.

필드 소유권도 정해 둔다. 리버스 ETL이 덮어쓰는 필드(구매액, 등급)는 사람이 CRM에서 고쳐도 다음 동기화가 되돌린다. 영업 사원이 등급을 손으로 고쳤는데 다음 날 원래대로 돌아가면 신뢰가 무너진다. 동기화가 쓰는 필드는 이름에 표시를 하거나(`DW 30일 구매액`) 읽기 전용으로 잠가서, 그 필드의 주인이 웨어하우스라는 걸 화면에서 알게 한다.

## 사라진 행은 어떻게 전하나

107번 고객이 탈퇴했거나 "최근 30일 구매자" 조건에서 빠졌다. 모델에서 사라졌으니 상태 테이블에는 있고 이번 결과에는 없다. 이걸 받는 쪽에 어떻게 전할지는 도구와 용도마다 다르다.

- 레코드를 지운다. 광고 타깃 목록, 메일 세그먼트처럼 "목록에 들어 있음" 자체가 의미인 곳은 빼야 한다. 빼지 않으면 탈퇴한 사람에게 광고가 계속 나간다. 개인정보 삭제 요청이 있었던 고객이라면 법적인 문제가 된다([데이터 개인정보와 규정 준수](/posts/data-privacy-compliance)).
- 필드만 비운다. CRM 연락처처럼 레코드 자체는 영업팀 것인 경우, 레코드는 두고 우리가 채운 필드(구매액)만 비우거나 0으로 바꾼다.
- 아무것도 하지 않는다. 마지막 값을 그대로 두는 게 맞는 경우도 있다. 다만 그러면 화면의 숫자가 언제 값인지 알 수 없으니 "마지막 동기화 시각" 필드를 함께 보낸다.

어느 쪽이든 삭제는 변경분 방식에서만 알 수 있다. 매번 전체를 보내는 방식은 "이번에 없는 것"을 모르니 지워야 할 레코드가 도구에 계속 남는다. 도구 쪽 목록을 통째로 이번 결과와 똑같이 맞추는 "미러" 방식도 있지만, 도구에서 사람이 직접 넣은 레코드까지 지울 수 있으니 우리만 쓰는 목록에만 쓴다. 위의 플레이그라운드에서 본 것처럼 모델이 비었을 때 전체 삭제가 나가는 걸 막는 안전장치도 삭제 쪽에서 가장 중요하다.

## CDP와 리버스 ETL 도구의 자리

이 분야의 도구는 두 줄기에서 왔고, 지금은 서로의 영역으로 넓어지며 경계가 흐려졌다.

Segment로 대표되는 CDP(Customer Data Platform)는 이벤트 수집에서 출발했다. 웹과 앱에 SDK를 심어 `track('Order Completed')` 같은 이벤트를 모으고, 그 이벤트를 웨어하우스와 여러 도구(분석, 광고, 메일)로 동시에 흘려보낸다. 사용자마다 프로필을 만들고 여러 기기의 익명 id를 한 사람으로 묶는 신원 연결(identity resolution)도 한다. 데이터가 웨어하우스를 거치지 않고 실시간으로 도구에 가니 빠르다. 대신 계산은 CDP 안에서 정한 규칙으로만 할 수 있고, 웨어하우스에 있는 주문·결제·지원 기록 같은 다른 데이터와 섞기 어렵다.

Census, Hightouch 같은 리버스 ETL 도구는 반대로 웨어하우스에서 출발했다. 이벤트를 직접 모으지 않고, 웨어하우스에 이미 있는 모델을 읽어 도구로 보낸다. 지표 정의를 웨어하우스 한곳(dbt 모델)에 두고, 그걸 그대로 여러 도구에 보내니 숫자가 어디서나 같다. 이런 구성을 "웨어하우스가 곧 CDP"라는 뜻에서 composable CDP라고 부르기도 한다. 대신 웨어하우스 모델이 갱신되는 주기(보통 몇 분~하루)보다 빨라질 수 없다.

고르는 기준은 이렇다. 사용자가 장바구니를 버린 지 5분 안에 메시지를 보내야 한다면 이벤트를 바로 흘리는 CDP 쪽이 맞다. 고객별 매출, 이탈 위험 점수, 계약 정보처럼 여러 원천을 합쳐 계산해야 하는 값이라면 웨어하우스에서 계산해 보내는 리버스 ETL 쪽이 맞다. 둘을 같이 쓰는 회사도 많다. 이벤트는 CDP로 모아 웨어하우스에 넣고, 웨어하우스에서 계산한 값은 리버스 ETL로 내보낸다.

## 직접 짤까, 도구를 쓸까

보내는 곳이 하나이고(CRM 하나), 건수가 적고(수만 건), 하루 한 번이면 충분하면 직접 짜도 된다. 위의 동기화기 정도 코드에 Airflow 태스크 하나면 끝난다. [Airflow](/posts/airflow-orchestration)의 DAG에서 dbt 빌드가 끝난 뒤에 이 태스크를 붙이면, 모델이 갱신되지 않은 날에는 동기화도 돌지 않는다.

```python
# dags/crm_sync.py 일부: dbt 빌드가 성공해야 동기화가 돈다
@dag(schedule=CronDataIntervalTimetable("0 1 * * *", timezone="Asia/Seoul"),
     start_date=pendulum.datetime(2026, 10, 1, tz="Asia/Seoul"), catchup=False,
     max_active_runs=1)                       # 동기화 두 개가 겹쳐 돌지 않게
def crm_sync():
    build = BashOperator(task_id="dbt_build",
                         bash_command="dbt build --select +crm_customer_metrics")

    @task(retries=3, retry_delay=timedelta(minutes=5))
    def push_to_crm():
        result = sync(connect_warehouse(), CrmClient.from_env(), max_delete_ratio=0.05)
        print(result)                         # 보낸 건수, 삭제 건수, 거절된 행 수를 로그로 남긴다

    build >> push_to_crm()
```

`max_active_runs=1`이 중요하다. 동기화 하나가 한도에 걸려 길어지는 동안 다음 실행이 시작되면, 두 실행이 같은 상태 테이블을 읽고 같은 행을 동시에 보낸다. 위에서 본 "두 번 보내기"가 이번엔 동시에 일어난다. `max_delete_ratio`는 앞에서 말한 안전장치를 함수 인자로 둔 것이다.

직접 짠 동기화가 금방 커지는 지점이 있다. 보낼 곳이 다섯 개가 되면 API마다 인증, 배치 크기, 한도, 부분 실패 응답 모양, 필드 타입 규칙이 다 다르다. 도구 쪽 API가 버전을 올리면 고쳐야 한다. 마케팅 팀이 "이 세그먼트를 광고 플랫폼에도 보내 달라"고 할 때마다 데이터 팀이 코드를 짜야 한다. 동기화 실패를 누가 어떻게 보는지, 거절된 행을 어디서 확인하는지 화면도 필요해진다.

도구를 쓰면 이 부분을 산다. 커넥터, 변경분 계산, 재시도, 거절 행 기록, 필드 매핑 화면, 실행 이력이 들어 있다. 마케팅 팀이 직접 세그먼트를 만들어 보내게 할 수도 있다. 대신 비용(보통 동기화하는 행 수나 연결한 도구 수로 과금)이 들고, 고객 데이터가 바깥 서비스를 한 번 더 거친다. 개인정보가 많은 데이터라면 그 서비스가 데이터를 어디에 얼마나 두는지 확인한다.

## 동기화가 이상하다는 말을 들으면

영업팀이 "CRM 구매액이 이상하다"고 하면 이 순서로 본다.

1. 웨어하우스 모델의 값부터 본다. 그 고객의 `purchase_30d`가 웨어하우스에서도 이상하면 리버스 ETL 문제가 아니라 모델 문제다. 모델이 언제 갱신됐는지도 본다.
2. 마지막 동기화 시각과 결과를 본다. 동기화가 멈췄거나, 그 행이 거절 목록에 있지 않은지 본다. 이메일 형식 오류, 도구 쪽 필수 필드 누락이 흔하다.
3. 키 매칭을 본다. 같은 사람이 CRM에 두 명 있고 그중 다른 레코드를 보고 있지 않은지, 이메일이 바뀌어 새 레코드가 생기지 않았는지 본다.
4. 누가 값을 덮어쓰는지 본다. 같은 필드를 다른 연동이나 사람이 고치고 있으면 동기화 직후엔 맞다가 몇 시간 뒤 틀어진다. 필드 변경 이력을 본다.
5. 한도 기록을 본다. 429가 반복돼 동기화가 다 끝나지 못하고 다음 실행과 겹치고 있지 않은지 본다.

## 계산은 웨어하우스에서, 전달은 조심스럽게

리버스 ETL은 웨어하우스에서 계산한 값을 사람이 일하는 도구로 되돌려 보내는 일이다. 웨어하우스 쪽은 보낼 모양의 모델 하나면 되고, 어려운 건 받는 쪽 API다. 지난번에 보낸 상태를 기억해 달라진 것만 보내고, 한도에 걸리면 기다렸다 다시 보내고, 성공한 것만 상태에 적는다. 그러면 같은 행이 두 번 갈 수 있으니 외부 id 기준 upsert로 두 번 받아도 같게 만든다. 키 정규화, 필드 소유권, 삭제를 어떻게 전할지, 모델이 비었을 때 멈추는 안전장치를 처음부터 정해 둔다.

## 면접에서 나올 만한 질문

### ETL과 리버스 ETL의 차이는 무엇인가요

방향과 받는 쪽이 다르다. ETL은 여러 원천에서 데이터를 꺼내 웨어하우스로 모으고, 리버스 ETL은 웨어하우스에서 계산한 값을 CRM, 광고 플랫폼, 고객 지원 도구 같은 업무 도구로 내보낸다. 웨어하우스는 대량 쓰기와 덮어쓰기가 쉽지만, SaaS API는 배치 크기와 호출 한도가 작고 레코드마다 도구 쪽 id가 있어서 리버스 ETL의 어려움은 대부분 받는 쪽 API를 다루는 데 있다.

### 리버스 ETL은 어떤 문제를 풀려고 생겼나요

웨어하우스에서 정성 들여 만든 지표가 정작 일하는 사람의 화면에 없다는 문제다. 영업, 마케팅, 고객 지원 팀은 웨어하우스나 BI가 아니라 자기 업무 도구에서 일한다. CSV를 뽑아 손으로 올리던 일을 자동화하고, 지표 정의를 웨어하우스 한곳에 두어 어느 도구에서나 같은 숫자가 보이게 한다.

### 매번 전체를 보내지 않고 변경분만 보내는 방법은 무엇인가요

지난번에 보낸 행의 사본이나 해시를 상태 테이블에 저장해 두고, 이번 결과와 키로 맞춰 생성, 수정, 삭제를 가른다. 지표 모델은 매일 통째로 다시 만들어지는 경우가 많아 `updated_at`만으로는 바뀐 행을 가리기 어렵기 때문이다. 이렇게 하면 API 호출 수가 바뀐 행 수만큼으로 줄고, 지난번엔 있다가 사라진 행을 알 수 있어 삭제도 전할 수 있다.

### 동기화가 두 번 일어나면 어떤 문제가 생기고 어떻게 막나요

받는 쪽이 받은 뒤 상태를 적기 전에 동기화기가 죽으면, 다음 실행이 같은 배치를 다시 보낸다. 무조건 새로 만드는 API였다면 같은 고객이 두 명 생기고, 더하는 API였다면 숫자가 두 번 늘어난다. 실험에서 create API는 연락처가 8명에서 10명이 됐고 upsert API는 8명 그대로였다. 그래서 외부 id 기준 upsert로 보내 두 번 받아도 같은 결과가 되게 하고, 더하는 API에는 멱등 키를 붙인다.

### API 호출 한도에 걸리면 어떻게 처리하나요

429와 5xx는 `Retry-After`가 있으면 그만큼, 없으면 지수 백오프와 지터를 섞어 기다렸다 다시 보낸다. 400처럼 다시 보내도 같은 오류는 재시도하지 않고 거절 목록에 남긴다. 배치 API를 써서 호출 수를 줄이되 배치 안의 부분 실패를 행 단위로 읽고, 그 도구를 쓰는 다른 연동과 한도를 나눠 쓰니 동기화마다 쓸 몫을 정한다.

### 모델이 실수로 비어 버렸을 때 리버스 ETL이 위험한 이유는 무엇인가요

변경분 계산으로는 지난번에 있던 모든 행이 사라진 것이라 전부 삭제로 나간다. 앞단 적재 실패 하나로 CRM 필드가 다 지워지거나 광고 목록이 텅 빈다. 그래서 삭제 비율이 일정 수준을 넘으면 멈추고 사람에게 확인받거나, 보내기 전에 모델 행 수를 어제와 비교하는 검사를 둔다.

### CDP와 리버스 ETL 도구는 어떻게 다르고 언제 무엇을 쓰나요

Segment 같은 CDP는 SDK로 이벤트를 모아 웨어하우스를 거치지 않고 여러 도구로 바로 흘려보내서 빠르지만, 여러 원천을 합친 계산은 어렵다. Census, Hightouch 같은 리버스 ETL 도구는 웨어하우스 모델을 읽어 보내서 지표 정의가 한곳에 모이지만 모델 갱신 주기보다 빨라질 수 없다. 몇 분 안에 반응해야 하는 행동 기반 메시지는 CDP, 매출이나 이탈 점수처럼 여러 데이터를 합친 값은 리버스 ETL이 맞고, 둘을 함께 쓰는 경우도 많다.
