안드로이드 크롬에서 블로그를 열고 메뉴의 "홈 화면에 추가"를 눌렀다. 아이콘이 생겼고, 눌러 보니 크롬 탭이 열리면서 주소창이 그대로 보였다. 앱이 아니라 북마크였다. 아이폰 사파리에서도 공유 버튼으로 홈 화면에 올렸는데 역시 사파리 화면이 그대로 떴다.

두 경우 모두 사이트가 "나는 설치할 수 있는 앱이다"라는 신호를 주지 않아서 생긴 일이다. 이 블로그는 지금 `src/app/manifest.ts`와 `public/sw.js`를 갖춘 설치 가능한 웹 앱이다. 이 글은 그 두 파일을 따라가며 웹 앱 매니페스트가 정하는 것, 브라우저가 설치 버튼을 보여 주는 조건, 오프라인 화면을 만드는 방법, 푸시 알림이 오는 길, 그리고 브라우저마다 다른 지원 범위를 정리한다.

서비스 워커가 요청을 가로채고 캐시를 고르는 전략, 새 버전이 기다리는 이유와 `skipWaiting`의 대가는 [프런트엔드 캐시 글](/posts/frontend-browser-cache)에서 이 블로그의 `sw.js`로 자세히 다뤘다. 여기서는 설치와 오프라인 경험에 필요한 부분만 짚고 그 글로 넘긴다.

## 앱이 되려면 필요한 세 가지

PWA(Progressive Web App)는 기술 하나의 이름이 아니다. 웹 페이지가 앱처럼 설치되고, 연결이 끊겨도 열리고, 알림을 받을 수 있게 하는 조합을 부르는 말이다. 2015년 구글 크롬 팀이 붙인 이름이고, 바탕에는 네이티브 앱을 내려받게 하는 데서 생기는 이탈 문제가 있었다. 스토어에 가서, 용량을 확인하고, 내려받는 사이 사람들이 떠난다. 웹은 링크 하나로 바로 열리니, 거기에 앱의 장점만 얹자는 생각이었다.

필요한 재료는 세 가지다. 앱의 정체를 알려 주는 매니페스트, 오프라인과 푸시를 맡는 서비스 워커, 그리고 HTTPS다. 서비스 워커는 페이지의 모든 요청을 가로챌 수 있는 강한 권한이라, 중간에서 누가 바꿔치기할 수 없는 HTTPS(또는 개발용 localhost)에서만 등록된다.

"Progressive"라는 말에도 뜻이 있다. 지원하지 않는 브라우저에서는 평범한 웹사이트로 동작하고, 지원하는 곳에서만 기능이 더해진다. 이 블로그도 서비스 워커를 등록하지 못하면 그냥 넘어간다. 등록 코드가 `"serviceWorker" in navigator`를 먼저 확인하고, 실패해도 `catch`에서 아무것도 하지 않는 이유다.

필드 하나를 더 알아 둘 만하다. `id`는 이 앱이 어떤 앱인지 가리키는 이름표다. 크롬은 `id`가 없으면 `start_url`을 대신 쓴다. 그래서 나중에 분석용으로 `start_url`에 쿼리를 붙이면 브라우저 입장에서는 다른 앱이 되어 버릴 수 있다. 처음부터 `"id": "/"`처럼 고정해 두면 `start_url`을 바꿔도 같은 앱으로 남는다.

`display`가 정한 창 모양은 CSS와 자바스크립트에서도 알 수 있다. 앱 창으로 열렸을 때만 안내 문구를 숨기거나, 화면 가장자리 여백을 다르게 줄 때 쓴다.

```css
/* 설치한 앱 창으로 열렸을 때만 적용된다 */
@media (display-mode: standalone) {
  .install-hint {
    display: none;
  }
  .app-header {
    /* 노치가 있는 기기에서 상태 표시줄 아래로 내린다 */
    padding-top: env(safe-area-inset-top);
  }
}
```

```ts
// 이 블로그의 install-app.utils.ts
export const isStandalone = () =>
  window.matchMedia("(display-mode: standalone)").matches ||
  (navigator as Navigator & { standalone?: boolean }).standalone === true;
```

`navigator.standalone`은 iOS 사파리에만 있는 옛 속성이다. 요즘 iOS도 `display-mode` 미디어 쿼리를 지원하지만 둘 다 보는 편이 안전하다.

## 설치 버튼은 브라우저가 허락할 때만 뜬다

매니페스트가 있다고 바로 설치되는 건 아니다. 브라우저가 조건을 확인하고 통과해야 설치를 제안한다. 크롬 계열(크롬, 엣지, 삼성 인터넷)의 조건은 이렇다.

HTTPS로 제공되어야 하고, 매니페스트에 `name`이나 `short_name`, 192px와 512px 아이콘, `start_url`, 그리고 `display`가 `fullscreen`, `standalone`, `minimal-ui`, `window-controls-overlay` 중 하나여야 한다. `prefer_related_applications`가 `true`면 네이티브 앱을 권하는 것으로 보고 설치를 제안하지 않는다. 사용자가 페이지를 한 번 이상 누르고 일정 시간(크롬 문서 기준 30초) 머물렀다는 참여 조건도 있다. 예전에는 `fetch` 핸들러를 가진 서비스 워커도 조건이었는데, 크롬은 2022~2023년(108~112 버전)에 걸쳐 이 조건을 뺐다. 그렇다고 서비스 워커를 생략하면 오프라인에서 아이콘을 눌렀을 때 브라우저의 공룡 화면이 뜬다.

조건을 통과하면 크롬은 주소창에 설치 아이콘을 띄우고, 페이지에 `beforeinstallprompt` 이벤트를 보낸다. 이 이벤트를 잡아 두면 원하는 때에 직접 설치 창을 띄울 수 있다. 이 블로그의 푸터에 있는 설치 버튼이 그렇게 동작한다. 아래 그림에서 다음을 누르면 이벤트가 오가는 순서를 볼 수 있다.

실제 코드는 React 훅 하나다. 이벤트 객체의 타입은 TypeScript 기본 DOM 타입에 없어서 직접 선언한다.

```ts
// install-app.type.ts
export interface BeforeInstallPromptEvent extends Event {
  prompt(): Promise<void>;
  userChoice: Promise<{ outcome: "accepted" | "dismissed"; platform: string }>;
}
```

```ts
// install-app.ts (요약)
useEffect(() => {
  if (isStandalone()) return; // 이미 앱 창이면 버튼이 필요 없다
  if (isIos()) setMode("ios"); // iOS는 이벤트가 없으니 안내 문구로

  const onPrompt = (event: Event) => {
    event.preventDefault(); // 브라우저 기본 안내 대신 우리 버튼에서 띄운다
    setDeferred(event as BeforeInstallPromptEvent);
    setMode("prompt");
  };
  const onInstalled = () => {
    setDeferred(null);
    setMode("none");
  };

  window.addEventListener("beforeinstallprompt", onPrompt);
  window.addEventListener("appinstalled", onInstalled);
  return () => {
    window.removeEventListener("beforeinstallprompt", onPrompt);
    window.removeEventListener("appinstalled", onInstalled);
  };
}, []);
```

설치 버튼을 언제 보여 줄지도 설계의 일부다. 첫 화면에 들어오자마자 설치를 권하면 대부분 닫는다. 사용자가 글을 두세 편 읽었거나 즐겨찾기를 눌렀을 때처럼 이 사이트를 다시 올 이유가 생긴 순간에 권하는 편이 낫다. 이 블로그는 눈에 띄지 않게 푸터에만 둔다.

## iOS에는 설치 이벤트가 없다

iOS와 iPadOS에서는 `beforeinstallprompt`가 오지 않는다. 사용자가 공유 버튼을 누르고 "홈 화면에 추가"를 직접 골라야 한다. 그래서 iOS에서는 버튼 대신 그 방법을 알려 주는 문구를 보여 준다. 이 블로그의 `isIos()`가 그 분기다. iPadOS는 사용자 에이전트가 맥처럼 보여서 `navigator.platform === "MacIntel"`이면서 터치 지점이 있는지를 함께 본다.

iOS 16.4부터는 사파리 말고 다른 브라우저 앱에서도 공유 메뉴로 홈 화면에 추가할 수 있다. iOS에서는 모든 브라우저가 웹킷 엔진을 쓰기 때문에 설치한 웹 앱도 결국 웹킷으로 돈다. 맥에서는 사파리 17(macOS Sonoma)부터 파일 메뉴의 "Dock에 추가"로 어떤 사이트든 앱처럼 올릴 수 있다. 데스크톱 파이어폭스는 오랫동안 설치 기능이 없었고, 안드로이드 파이어폭스는 홈 화면 설치를 지원한다. 브라우저 지원은 자주 바뀌니 실제로 지원하는 기기에서 확인해야 한다.

iOS 홈 화면 앱은 처음 장면처럼 사파리로 열리는 일이 생기기도 한다. 매니페스트가 없거나 `display`가 `browser`면 북마크처럼 동작한다. 매니페스트를 고친 뒤에도 이미 추가된 아이콘은 그대로이니, 지우고 다시 추가해서 확인한다.

## 오프라인에서 열리게 하는 최소한

설치한 앱은 사용자가 "앱"으로 여긴다. 지하철에서 아이콘을 눌렀는데 브라우저의 연결 오류 화면이 뜨면 앱이 고장 났다고 느낀다. 최소한 "연결이 끊겼다"는 내 화면을 보여 줘야 한다.

방법은 서비스 워커가 설치될 때 오프라인용 페이지를 미리 캐시해 두고, 페이지 이동 요청이 네트워크에서 실패하면 그걸 꺼내 주는 것이다.

```js
// sw.js: 오프라인 폴백 페이지를 둔 최소 구성
const CACHE = "offline-v1";
const OFFLINE_URL = "/offline.html";

self.addEventListener("install", (event) => {
  // 설치가 끝나기 전에 오프라인 페이지를 받아 둔다. 실패하면 설치도 실패한다.
  event.waitUntil(caches.open(CACHE).then((cache) => cache.add(OFFLINE_URL)));
});

self.addEventListener("fetch", (event) => {
  // HTML 페이지 이동만 다룬다. 이미지·스크립트는 그대로 둔다.
  if (event.request.mode !== "navigate") return;
  event.respondWith(
    fetch(event.request).catch(() => caches.match(OFFLINE_URL)),
  );
});
```

`request.mode === "navigate"`가 페이지 이동 요청을 가리킨다. 이미지나 API 요청까지 오프라인 페이지로 바꾸면 이상한 응답이 들어가니 페이지 이동만 다룬다. `offline.html`은 스스로 완결된 파일이어야 한다. 외부 CSS나 폰트를 부르면 그것도 오프라인에서는 못 받는다. 스타일은 파일 안에 넣는다.

이 블로그의 `sw.js`는 한 걸음 더 간다. 페이지를 네트워크 우선으로 받으면서 받은 페이지를 캐시에 넣어 두고, 오프라인이면 마지막으로 본 그 페이지를, 그것도 없으면 홈을 보여 준다. 읽기용 블로그라 "전에 읽던 글이 열린다"가 더 쓸모 있기 때문이다. 캐시 우선과 네트워크 우선을 어디에 쓸지는 [프런트엔드 캐시 글](/posts/frontend-browser-cache)에서 다뤘다.

```js
// public/sw.js 중 페이지 이동 처리
if (request.mode === "navigate") {
  event.respondWith(
    fetch(request)
      .then((response) => {
        if (response.ok) caches.open(PAGE_CACHE).then((cache) => cache.put(request, response.clone()));
        return response;
      })
      .catch(() => caches.match(request).then((cached) => cached || caches.match("/"))),
  );
}
```

오프라인 상태를 화면에 알리는 것도 앱다운 경험이다. `navigator.onLine`과 `online`·`offline` 이벤트로 배너를 띄운다. 다만 `navigator.onLine`이 `true`라고 인터넷이 된다는 뜻은 아니다. 와이파이에는 붙었는데 외부로 못 나가는 경우에도 `true`다. 확실히 알려면 실제 요청의 실패로 판단한다.

## 새 버전을 알리는 방법

설치한 PWA에서 업데이트 문제가 더 자주 보인다. 브라우저 탭은 사용자가 닫지만, 홈 화면 앱은 운영체제가 메모리에 남겨 두기도 해서 옛 서비스 워커가 오래 붙어 있다. 새 서비스 워커는 옛 버전이 맡은 창이 모두 닫혀야 활성화되기 때문에 배포했는데 앱만 계속 옛 화면인 일이 생긴다. 이 대기 규칙과 `skipWaiting`을 바로 부를 때 열린 탭이 깨지는 위험은 [프런트엔드 캐시 글](/posts/frontend-browser-cache)에 있다.

앱다운 해결은 사용자에게 알리는 것이다. 새 워커가 대기 상태가 되면 "새 버전이 있다" 막대를 띄우고, 사용자가 누를 때만 `SKIP_WAITING` 메시지로 대기를 건너뛰게 한 뒤 `controllerchange`에서 한 번 다시 연다. 페이지와 `sw.js` 양쪽 코드는 그 글에 그대로 있으니 여기서는 설치한 앱에서 달라지는 점만 본다.

설치한 앱은 페이지 이동이 드물다. 한 화면에서 오래 머무는 앱이라면 브라우저가 `sw.js`를 다시 받아 볼 기회가 거의 없다. 그래서 앱이 다시 화면에 보일 때 확인을 앞당긴다.

```ts
// 앱이 백그라운드에서 돌아올 때마다 새 sw.js가 있는지 확인한다
document.addEventListener("visibilitychange", () => {
  if (document.visibilityState === "visible") registration.update();
});
```

`update()`는 받은 `sw.js`가 한 바이트도 다르지 않으면 요청 하나로 끝나서 자주 불러도 부담이 적다. 이때 브라우저는 기본값(`updateViaCache: "imports"`)으로 `sw.js` 본체는 HTTP 캐시를 거치지 않고 받는다. `importScripts`로 불러오는 파일은 캐시를 탈 수 있으니 그 파일 이름에 버전을 넣어 둔다.

매니페스트의 이름이나 아이콘을 바꾼 경우는 또 다르다. 설치된 앱의 정보는 브라우저가 정한 주기로 매니페스트를 다시 확인해서 고친다. 안드로이드 크롬은 앱을 열 때 확인하되 자주 하지는 않고, iOS는 홈 화면에 추가하던 순간의 정보를 그대로 쓴다. 아이콘을 바꿨는데 반영이 안 된다는 문의는 대부분 여기서 온다.

## 푸시 알림이 오는 길

PWA를 고르는 이유로 푸시 알림이 자주 꼽힌다. 웹 푸시에는 세 주체가 있다. 내 서버, 브라우저 회사가 운영하는 푸시 서비스, 그리고 사용자 기기의 서비스 워커다. 내 서버는 기기에 직접 연결하지 않는다. 브라우저마다 정해진 푸시 서비스에 메시지를 맡기면 그쪽이 기기까지 배달한다. 서버가 기기마다 연결을 붙잡고 있을 필요가 없게 하려는 구조다.

## 저장해 둔 것이 지워지는 순간

오프라인 앱은 Cache Storage와 IndexedDB에 데이터를 둔다. 이 저장소는 브라우저가 공간이 부족하면 지울 수 있는 "최선 노력(best-effort)" 저장소가 기본이다. 지금 얼마나 쓰고 있는지와 지워지지 않게 부탁하는 API가 있다.

```js
// 사용량과 할당량(바이트)을 본다
const { usage, quota } = await navigator.storage.estimate();
console.log(`${(usage / 1e6).toFixed(1)}MB / ${(quota / 1e6).toFixed(0)}MB`);

// 지우지 말아 달라고 부탁한다. 허락 여부는 브라우저가 정한다.
const persisted = await navigator.storage.persist();
console.log("persisted:", persisted);
```

크롬은 사이트 참여도나 설치 여부 같은 신호로 `persist()`를 조용히 허락하거나 거절하고, 파이어폭스는 사용자에게 묻는다. 사파리는 다른 규칙이 하나 더 있다. 사용자가 7일 동안 사이트와 상호작용하지 않으면 스크립트로 쓴 저장소를 지우는 정책(ITP)이 있는데, 웹킷은 홈 화면에 추가한 웹 앱은 사파리와 별개로 앱을 쓴 날을 따로 센다고 밝혔다. 앱을 꾸준히 여는 동안에는 이 규칙에 걸리지 않는다는 뜻이다. 오프라인 데이터가 중요하다면 iOS에서 설치를 권할 이유가 하나 더 생긴다. 어쨌든 브라우저 저장소는 지워질 수 있다고 보고, 서버가 원본을 갖고 다시 채울 수 있게 설계한다. 저장소별 용량과 지워지는 순서는 [브라우저 저장소 글](/posts/browser-storage)과 [프런트엔드 캐시 글](/posts/frontend-browser-cache)을 본다.

## 네이티브 앱 대신 PWA를 고를 때

PWA의 장점은 배포와 비용이다. 코드 하나로 모든 플랫폼에 닿고, 스토어 심사 없이 배포하면 다음 실행에 바로 반영된다. 링크로 공유되고 검색에 걸린다. 설치 전에도 웹으로 쓸 수 있어서 첫 사용까지의 길이 짧다.

약점은 플랫폼이 허락하는 범위다. iOS는 설치 이벤트가 없고, 백그라운드 동기화(Background Sync)나 웹 블루투스 같은 API를 지원하지 않는다. 백그라운드에서 오래 일하는 작업, 위치를 계속 추적하는 앱, 블루투스 기기 제어처럼 운영체제 깊숙이 들어가는 기능은 네이티브가 낫다. 앱 스토어 안에서 발견되어야 하는 서비스라면 그것도 고려한다. 안드로이드에서는 PWA를 TWA(Trusted Web Activity)로 감싸 플레이 스토어에 올릴 수 있고, PWABuilder 같은 도구가 이를 돕는다. 애플 앱 스토어는 웹을 감싸기만 한 앱을 심사에서 거절할 수 있다.

고르는 기준은 대개 이렇게 정리된다. 콘텐츠를 읽고, 폼을 채우고, 알림을 받는 서비스는 PWA로 충분하다. 사내 도구처럼 설치를 관리자가 안내할 수 있는 곳도 잘 맞는다. 기기 기능을 깊게 쓰거나 iOS 사용자가 대부분이고 푸시가 핵심이라면, iOS의 제약을 먼저 확인한 뒤 결정한다.

## 설치 버튼이 안 뜨고 옛 화면이 남을 때

설치 버튼이 안 뜬다는 문의가 오면 크롬 개발자 도구의 Application 패널에서 Manifest 항목을 연다. 매니페스트를 읽었는지, 아이콘이 실제로 내려받아지는지, 설치를 막는 이유가 있는지 그 화면에 나온다. 아이콘 경로가 404이거나 크기가 매니페스트에 적은 값과 다른 경우가 흔하다. 예전에는 Lighthouse에 PWA 항목이 있었지만 Lighthouse 12(2024년)에서 빠졌으니 Application 패널을 기준으로 본다. 패널 사용법은 [브라우저 DevTools 글](/posts/browser-devtools-debugging)에서 다룬다.

배포했는데 설치한 앱만 옛 화면이면 Application 패널의 Service workers 항목에서 waiting 상태인 워커가 있는지 본다. 사용자 기기라면 앱을 완전히 종료했다가 다시 여는지 물어본다. 이게 반복되면 위의 업데이트 알림을 붙인다.

오프라인에서 공룡 화면이 뜨면 서비스 워커가 등록되어 있는지, `navigate` 요청을 처리하는지, 오프라인 페이지가 실제로 캐시에 들어가 있는지를 Application 패널의 Cache storage에서 확인한다. Network 패널의 Offline 체크로 바로 재현할 수 있다.

iOS 앱 창에서 상단 상태 표시줄과 내용이 겹치면 `viewport-fit=cover`를 쓰면서 `env(safe-area-inset-top)` 여백을 빠뜨린 경우다. 반대로 상태 표시줄 색이 이상하면 `theme-color`와 `apple-mobile-web-app-status-bar-style` 메타 태그를 확인한다.

## 주소창이 보였던 이유

홈 화면에 올렸는데 주소창이 보였던 건 매니페스트가 없어서였다. 매니페스트로 앱의 이름과 창 모양을 알리면 브라우저가 설치를 허락하고, 서비스 워커가 오프라인 화면과 푸시를 맡는다. 설치 방법과 알림 지원은 브라우저마다 다르니, 특히 iOS에서는 설치를 먼저 안내해야 쓸 수 있는 기능이 있다는 걸 염두에 두고 설계한다.

## 면접에서 나올 만한 질문

### PWA는 무엇이고 어떤 문제를 풀려고 생겼나요?

웹 페이지를 앱처럼 설치하고, 오프라인에서 열고, 푸시를 받을 수 있게 하는 기술 조합이다. 매니페스트, 서비스 워커, HTTPS로 이루어진다. 네이티브 앱을 스토어에서 내려받는 과정에서 생기는 이탈을 줄이고, 링크 하나로 열리는 웹의 장점을 유지하면서 앱 경험을 더하려고 나왔다.

### 웹 앱 매니페스트에서 중요한 필드는 무엇인가요?

`name`이나 `short_name`, 아이콘, `start_url`, `display`가 설치 조건과 직결된다. `display: standalone`이면 주소창 없는 앱 창으로 열리고, `scope`는 앱이 맡는 주소 범위다. maskable 아이콘은 가운데 80% 원 안에 그림을 둬야 잘리지 않는다. `id`를 고정해 두면 `start_url`을 바꿔도 같은 앱으로 인식된다.

### beforeinstallprompt는 어떻게 쓰고 한계는 무엇인가요?

크롬 계열 브라우저가 설치 조건을 통과했을 때 보내는 이벤트다. `preventDefault`로 기본 안내를 막고 이벤트를 저장해 두었다가, 사용자가 버튼을 누를 때 `prompt()`를 부르고 `userChoice`로 결과를 받는다. 이벤트 하나로 한 번만 쓸 수 있다. 사파리와 파이어폭스에는 이 이벤트가 없어서 iOS에서는 "홈 화면에 추가" 방법을 안내해야 한다.

### 오프라인 폴백은 어떻게 만드나요?

서비스 워커의 `install` 단계에서 오프라인 페이지를 캐시에 넣어 두고, `fetch`에서 `request.mode`가 `navigate`인 요청이 네트워크에서 실패하면 그 페이지를 돌려준다. 페이지 이동만 다뤄야 이미지나 API 요청에 HTML이 들어가지 않는다. 오프라인 페이지는 외부 자원 없이 스스로 완결되어야 한다.

### 서비스 워커를 배포했는데 사용자가 계속 옛 버전을 본다면요?

새 워커는 옛 워커가 맡은 창이 모두 닫힐 때까지 waiting 상태로 기다린다. 설치한 앱은 운영체제가 창을 오래 살려 두어 더 자주 생긴다. `skipWaiting`을 무조건 부르면 열린 페이지가 옛 자원을 못 찾아 깨질 수 있어서, 대기 중인 워커를 감지해 업데이트 알림을 띄우고 사용자가 누를 때만 활성화한 뒤 `controllerchange`에서 다시 연다.

### 웹 푸시는 어떤 구조로 전달되나요?

페이지가 `pushManager.subscribe`로 브라우저의 푸시 서비스에 구독하고, 그 endpoint와 키를 내 서버에 저장한다. 서버는 VAPID로 서명하고 구독 키로 암호화한 메시지를 푸시 서비스에 보내고, 푸시 서비스가 기기의 서비스 워커를 깨워 `push` 이벤트를 준다. 서버는 404·410 응답이 오면 만료된 구독을 지워야 한다.

### iOS에서 PWA를 만들 때 주의할 점은 무엇인가요?

설치 이벤트가 없어서 사용자가 공유 메뉴로 직접 추가해야 한다. 웹 푸시는 iOS 16.4부터지만 홈 화면에 추가한 앱에서만 된다. 백그라운드 동기화 같은 일부 API가 없고, 매니페스트를 바꿔도 이미 추가된 아이콘에는 반영되지 않는다. 대신 홈 화면 앱은 사파리와 따로 사용일을 세서, 꾸준히 쓰는 동안에는 7일 저장소 삭제 규칙에 걸리지 않는다.

### PWA와 네이티브 앱은 어떻게 고르나요?

콘텐츠 소비, 폼, 알림 중심이고 빠른 배포가 중요하면 PWA가 비용 대비 낫다. 백그라운드 작업, 블루투스 같은 기기 기능, 앱 스토어 노출이 핵심이면 네이티브가 맞다. iOS 사용자 비중이 크고 푸시가 필수라면 iOS의 설치·푸시 제약을 먼저 따져 본다. 안드로이드는 TWA로 PWA를 스토어에 올리는 중간 길도 있다.
