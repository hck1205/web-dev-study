<EasyIntro>
  주 데이터베이스 서버가 죽으면 대기하던 서버가 그 일을 이어받는데, 이걸 장애 조치라고 한다. "자동으로 넘어갔다"는 말 뒤에는 몇 초 동안의 멈춤과 사라진 주문 같은 일이 숨어 있다.

  비행기의 기장과 부기장을 떠올리면 쉽다. 기장이 쓰러지면 부기장이 조종간을 잡는데, 시간의 대부분은 조종간을 넘기는 데가 아니라 "정말 쓰러진 건가"를 확인하는 데 든다. 너무 빨리 판단하면 잠깐 졸았을 뿐인 기장을 내보내게 된다. 기장이 마지막으로 받아 적은 메모가 부기장에게 아직 전해지지 않았다면 그 내용은 사라지고, 매번 부기장이 받아 적을 때까지 기다리면 잃지 않지만 일이 느려진다.

  가장 위험한 순간은 기장이 깨어나 두 사람이 동시에 조종간을 잡을 때다. 그래서 부기장이 넘겨받기 전에 기장의 손을 확실히 떼어 놓고, 관제탑과 승객에게도 이제 누가 조종하는지 빠르게 알려야 한다.
</EasyIntro>

DB 프라이머리가 죽었다. 스탠바이가 있었고, 자동 장애 조치 스크립트도 있었다. 그래서 장애 보고서에는 "자동으로 넘어감"이라고 적혔다. 그런데 고객 센터에는 "주문 완료 문자를 받았는데 주문 내역에 없다"는 문의가 하나 들어왔고, 그 10초 남짓 동안 결제 버튼은 에러를 냈다. 자동으로 넘어갔다는 말과 사용자가 겪은 일 사이에 무엇이 있었는지 숫자로 보자.

장애 조치(failover)는 죽은 주 서버의 역할을 살아 있는 대기 서버가 이어받게 하는 일이다. 이 글은 PostgreSQL 16 프라이머리와 스트리밍 스탠바이를 네트워크 네임스페이스에 띄우고, 50ms마다 주문을 넣는 클라이언트를 돌리다가 프라이머리를 죽인다. 그리고 쓰기가 멈춘 시간을 감지, 승격, 연결 전환 토막으로 나눠 재고, 응답까지 받은 주문이 사라지는 장면과, 옛 프라이머리가 살아 있을 때 클라이언트가 엉뚱한 쪽에 쓰는 장면을 본다.

이 주제의 다른 글: 사고 전체의 목표 숫자(RPO, RTO)는 [재해 복구](/posts/disaster-recovery), 대기 서버를 다른 리전에 둘 때의 지연은 [멀티 리전](/posts/multi-region)에서 다룬다. 스탠바이를 붙이는 법과 `pg_promote`는 [복제와 복제 지연](/posts/db-replication-sharding), 네트워크만 끊겼을 때 두 프라이머리가 생기는 과정은 [네트워크 분할](/posts/network-partitions), 임대와 펜싱 토큰은 [리더 선출](/posts/leader-election)에 있다. 로드 밸런서의 VIP 이중화(VRRP)는 [로드 밸런서 기본](/posts/load-balancer-basics)을 참고한다.

## 주문이 9.6초 동안 멈췄다

실험 구성은 이렇다. 프라이머리는 네임스페이스 `v18p`, 스탠바이는 `v18s`에 있고, 클라이언트는 기본 네임스페이스에서 둘 다에 닿는다. 복제 경로에는 Node로 짠 작은 지연 프록시를 끼워 한쪽 200ms씩 늦췄다. 이 컨테이너 커널에는 `tc netem`이 없어서 대신 쓴 방법이다. 복제가 0.4초 뒤처지게 만들어 비동기 복제의 손실이 눈에 보이게 하려는 것이다.

```bash
# 복제 상태: 비동기, 약 0.4초 뒤처져 있다
psql -h 10.18.1.2 -U postgres -XAc "select client_addr, state, sync_state, write_lag, replay_lag from pg_stat_replication"
```

```text
client_addr|state|sync_state|write_lag|replay_lag
10.18.2.2|streaming|async|00:00:00.403898|00:00:00.403898
(1 row)
```

클라이언트는 libpq의 다중 호스트 연결 문자열로 두 서버를 다 적고, 쓰기 가능한 쪽에만 붙게 했다(`target_session_attrs=read-write`). 장애 감지는 [네트워크 분할](/posts/network-partitions) 글의 것과 같은 순진한 스크립트다. 1초마다 묻고 세 번 연속 답이 없으면 승격한다.

```bash
# writer.sh: 50ms마다 주문 하나, 두 서버 중 쓰기 가능한 쪽에
URI="host=10.18.1.2,10.18.3.2 user=postgres connect_timeout=1 target_session_attrs=read-write"
while true; do
  out=$(psql "$URI" -XqAtc "INSERT INTO orders(amount) VALUES (1) RETURNING id, inet_server_addr()" 2>&1) \
    && echo "$(date +%T.%3N) ok $out" || echo "$(date +%T.%3N) fail"
  sleep 0.05
done

# detector.sh: 1초마다 묻고 3번 연속 실패하면 스탠바이 승격
fails=0
while true; do
  pg_isready -h 10.18.1.2 -t 1 -q && fails=0 || { fails=$((fails+1)); echo "$(date +%T.%3N) primary no answer ($fails/3)"; }
  if [ $fails -ge 3 ]; then
    echo "$(date +%T.%3N) promote standby"
    psql -h 10.18.3.2 -U postgres -XAtc "SELECT pg_promote(wait => true)"
    echo "$(date +%T.%3N) promoted"; exit
  fi
  sleep 1
done
```

두 스크립트를 띄워 두고 프라이머리 쪽 링크를 내리고 프로세스를 죽였다. 서버가 전원째 꺼진 상황이다.

```bash
echo "$(date +%T.%3N) primary host dies"
sudo ip netns exec v18p ip link set v18pc down      # 클라이언트 쪽 링크
sudo ip netns exec v18p ip link set v18ps down      # 복제 쪽 링크
sudo kill -9 $(sudo head -1 /var/tmp/v18pg/p/postmaster.pid)
```


```bash
# 옛 프라이머리에서 성공 응답을 받은 마지막 번호는 42
psql -h 10.18.3.2 -U postgres -XAc "select max(id) filter (where id <= 42) as max_old_id, count(*) filter (where id <= 42) as rows_old, pg_is_in_recovery() from orders"
```

## 감지: 빨리 알아채면 잘못 알아챈다

감지 시간을 줄이는 손잡이는 묻는 간격, 한 번 기다리는 시간, 몇 번 실패해야 죽었다고 볼지다. 다 줄이면 몇 초 안에 넘어간다. 대신 프라이머리가 잠깐 바빴던 것(체크포인트로 디스크가 밀렸거나, 네트워크가 1초 흔들렸거나)을 죽음으로 오해한다. 오해해서 넘기면 멀쩡한 프라이머리를 버리고, 그동안의 쓰기를 잃고, 경우에 따라 두 프라이머리를 만든다. [네트워크 분할](/posts/network-partitions) 글에서 보듯 "응답이 없다"는 사실만으로는 죽음과 느림과 끊김을 구별할 수 없다.

그래서 감지는 보통 이렇게 보강한다. 한 곳에서만 묻지 않고 여러 위치(다른 존의 감시자 셋)에서 물어 과반이 실패해야 죽었다고 본다. 단순 TCP 연결이 아니라 실제 쿼리나 쓰기를 해 본다. 그리고 넘긴 뒤 일정 시간은 다시 넘기지 않게 막아 왔다 갔다 하는 것(flapping)을 막는다.

토막별 시간을 더해 최악의 멈춤 시간을 계산해 보자. 감지는 "실패 횟수 × (간격 + 시간 초과)", 전환은 방식에 따라 다르다.

  const detect = p.failures * (p.intervalS + p.timeoutS);
  const sw = p.switchBy === "dns" ? p.dnsTtlS + p.retryS
    : p.switchBy === "vip" ? p.garpS
    : p.retryS;

}`}

같은 실험을 동기 복제로 다시 했다. `synchronous_standby_names = '*'`로 바꾸면 프라이머리는 스탠바이가 WAL을 디스크에 썼다는 답을 받은 뒤에야 커밋을 끝낸다.

```bash
psql -h 10.18.1.2 -U postgres -XAc "ALTER SYSTEM SET synchronous_standby_names = '*'" -c "SELECT pg_reload_conf()"
psql -h 10.18.1.2 -U postgres -XAc "select state, sync_state from pg_stat_replication"
```

```text
state|sync_state
streaming|sync
(1 row)
```

```text
# writer.sh (동기 복제)
20:39:05.975 ok 15|10.18.1.2
20:39:08.105 fail
...
20:39:15.509 ok 34|10.18.3.2

# 새 프라이머리에서: 성공 응답을 받은 마지막 번호 15까지
rows_old|max
15|15
```

이번에는 응답받은 주문이 하나도 사라지지 않았다. 대신 주문 하나에 걸리는 시간이 달라졌다. 같은 200ms 경로에서 `\timing`으로 잰 INSERT 한 건이다.

```text
INSERT 0 1
Time: 404.907 ms      -- synchronous_commit = on (기본값)
INSERT 0 1
Time: 1.174 ms        -- synchronous_commit = local
```

커밋마다 왕복 한 번(400ms)을 기다린다. 사고 전 약 5.5초 동안 비동기 실험에서는 42건, 동기 실험에서는 15건이 들어간 차이가 여기서 나왔다. 동기 복제에는 함정이 하나 더 있다. 동기 스탠바이가 하나뿐인데 그 스탠바이가 죽으면 프라이머리는 커밋을 영원히 기다린다. 쓰기가 멈춘다. 그래서 동기 복제는 스탠바이를 둘 이상 두고 `ANY 1 (s1, s2)`처럼 그중 하나만 답하면 되게 하거나, Patroni의 `synchronous_mode`처럼 동기 스탠바이가 사라지면 관리 도구가 설정을 바꿔 주게 한다. 리전 사이에 동기 복제를 걸 때의 지연은 [멀티 리전](/posts/multi-region) 글에서 잰다.

주문 번호가 42에서 67로 뛴 것도 장애 조치의 흔적이다. PostgreSQL 시퀀스는 매번 WAL을 쓰지 않으려고 32개 앞의 값을 미리 기록해 둔다. 스탠바이는 그 기록만 받았으니 승격 뒤 그 값부터 이어 간다. 번호가 비는 건 정상이고 데이터 손실이 아니다. 하지만 "주문 번호가 연속"이라고 가정한 코드나 정산 검사는 장애 조치 뒤에 거짓 경보를 낸다.

## 옛 프라이머리가 살아 있으면

실험에서는 옛 프라이머리를 확실히 죽였다. 그런데 실제 장애에서는 "죽었다고 판단한" 프라이머리가 살아 있는 경우가 많다. 이번에는 프라이머리를 그대로 둔 채 스탠바이만 승격하고 두 서버와 다중 호스트 클라이언트를 확인했다.

```bash
for h in 10.18.1.2 10.18.3.2; do
  psql -h $h -U postgres -XAtc "select inet_server_addr(), pg_is_in_recovery(), pg_walfile_name(pg_current_wal_lsn())"
done
# 다중 호스트 클라이언트는 어디에 붙나
psql "host=10.18.1.2,10.18.3.2 user=postgres target_session_attrs=read-write" -XAtc "select inet_server_addr()"
```

```text
10.18.1.2|f|000000010000000000000003
10.18.3.2|f|000000020000000000000003
10.18.1.2
```

둘 다 `pg_is_in_recovery = f`, 쓰기를 받는다. WAL 파일 이름 앞자리로 타임라인 1과 2가 갈린 게 보인다. 그리고 클라이언트는 옛 프라이머리(목록의 첫 서버)에 붙었다. `target_session_attrs=read-write`는 "쓰기 가능한 첫 서버"를 고를 뿐, 어느 쪽이 진짜인지는 모른다. 이렇게 두 프라이머리가 각자 쓰기를 받는 상태가 스플릿 브레인이다.

그래서 승격 전에 옛 프라이머리를 확실히 끊는다. 이걸 펜싱(fencing)이라고 한다. 가장 확실한 형태가 STONITH(Shoot The Other Node In The Head)다. 전원 관리 장치(IPMI)나 클라우드 API로 옛 서버를 강제로 끈다. 그보다 약한 방법으로 옛 서버의 네트워크를 끊거나(보안 그룹 변경), 스토리지 접근을 막거나, 리더 키 갱신에 실패한 노드가 스스로 내려가게 하는 방법이 있다. 스스로 내려가는 방식은 노드가 멈춰 있는 동안에는 아무것도 못 하니, Patroni는 리눅스 watchdog 장치를 써서 갱신이 멈춘 노드를 커널이 재부팅하게 할 수 있다. 저장소 쪽에서 오래된 리더의 쓰기를 거절하는 펜싱 토큰은 [리더 선출](/posts/leader-election) 글에 자세히 있다.

<Callout kind="warning">
펜싱 없이 자동 승격만 켜 두는 것이 가장 위험한 설정이다. 감지가 틀리는 순간 두 프라이머리가 생기고, 갈라진 쓰기는 PostgreSQL 복제로 합칠 방법이 없다. 이미 갈라졌다면 한쪽을 정하고, 버릴 쪽에서 갈라진 뒤 들어온 데이터를 먼저 덤프해 따로 보관한 다음 `pg_rewind`로 되감아 스탠바이로 붙인다.
</Callout>

## Patroni는 이 토막들을 어떻게 맡나

손으로 짠 감지 스크립트 대신 운영에서는 Patroni 같은 도구를 쓴다. Patroni는 DB 서버마다 옆에서 돌며 etcd나 Consul 같은 합의 저장소에 리더 키를 둔다. 리더는 키를 주기적으로 갱신하고, 갱신이 멈춰 키가 만료되면 남은 노드 중 조건을 만족하는 쪽이 키를 잡고 승격한다. 감지를 "한 감시자의 판단"이 아니라 "합의 저장소의 임대 만료"로 바꾼 것이다. 핵심 설정을 눌러 보자(값은 Patroni 기본값).

Patroni는 승격 말고도 몇 가지를 더 맡는다. 옛 프라이머리가 돌아오면 `pg_rewind`로 갈라진 부분을 되감아 스탠바이로 붙이고(`use_pg_rewind`), REST API로 각 노드의 역할을 알려 HAProxy가 프라이머리를 고르게 한다. 계획된 작업에는 장애 조치 대신 `patronictl switchover`를 쓴다. 프라이머리를 깨끗이 내리고 스탠바이가 다 따라온 뒤 넘기니 잃는 데이터가 없다. 이 전환을 정기적으로 해 보는 것이 가장 싼 장애 조치 훈련이다.

## Patroni 말고 다른 도구는 무엇이 다른가

장애 조치 도구를 비교할 때 기능 목록보다 먼저 물을 것이 둘 있다. 누가 "프라이머리는 이 서버"라고 결정하나(합의 저장소, DCS가 있나), 그리고 옛 프라이머리를 어떻게 끊나(펜싱). 앞 절들의 감지와 스플릿 브레인 문제를 각 도구가 어디서 푸는지가 여기서 갈린다.

| 도구 | 결정하는 곳 | 옛 프라이머리를 끊는 방법 |
|---|---|---|
| Patroni | etcd·Consul·ZooKeeper·쿠버네티스 API의 리더 키 | 키를 갱신 못 하면 스스로 내려간다. watchdog으로 멈춘 노드를 재부팅 |
| repmgr | DCS 없음. 각 노드의 repmgrd가 서로 확인한다 | 기본 장치가 없다. 네트워크가 갈렸을 때는 witness 서버로 다수 쪽을 가리고, 펜싱은 승격 명령에 거는 사용자 스크립트로 한다 |
| pg_auto_failover | 따로 둔 monitor 노드(PostgreSQL 하나)의 상태 기계 | 프라이머리가 monitor와 스탠바이 둘 다 못 보면 스스로 내려간다. 기본은 동기 복제라 잃는 커밋이 없다 |
| Stolon | etcd·Consul·쿠버네티스 API | 모든 클라이언트가 stolon-proxy를 거치고, proxy가 옛 프라이머리로 가는 연결을 끊는다 |

repmgr는 설치가 가볍고 오래 쓰였지만, 판단을 각 노드에 맡기는 만큼 망이 갈리는 상황을 witness 배치와 스크립트로 직접 설계해야 한다. pg_auto_failover는 노드 둘에 monitor 하나로 시작할 수 있어 가장 단순하다. 대신 monitor가 죽으면 데이터는 멀쩡해도 자동 장애 조치가 멈추니 monitor도 따로 지켜본다. Stolon은 쿠버네티스 위에서 쓰려고 만든 도구인데 2021년 릴리스 뒤로 개발이 거의 멈춰서, 지금 쿠버네티스라면 쿠버네티스 API를 DCS로 쓰는 오퍼레이터(CloudNativePG, Patroni 기반 오퍼레이터)를 먼저 본다.

관리형 서비스는 이 결정을 통째로 가져간다. RDS Multi-AZ는 다른 가용 영역의 스탠바이에 스토리지 단에서 동기로 쓰고, 장애가 나면 DNS 이름(CNAME)이 새 서버를 가리키게 바꾼다. AWS 문서 기준으로 보통 1~2분이 걸리고, Aurora는 공유 스토리지 덕분에 그보다 짧다. 펜싱도 서비스가 스토리지 쪽에서 해 주니 스플릿 브레인을 걱정할 일은 적다. 그래도 클라이언트 쪽 일은 그대로 남는다. DNS로 넘어가니 앞 절의 TTL, DNS 캐시, 풀에 남은 옛 연결 문제는 직접 챙긴다.

고를 때는 이렇게 본다. 이미 etcd나 쿠버네티스를 운영하고 있으면 Patroni나 오퍼레이터, 합의 저장소를 새로 들이기 부담스러운 작은 구성이면 pg_auto_failover, DB를 직접 운영할 이유가 없으면 관리형이다. 어느 쪽이든 "펜싱은 누가 하나"에 한 문장으로 답할 수 없으면 그 구성은 아직 자동 승격을 켜면 안 된다.

## 장애 조치가 오히려 장애가 되는 순간

"프라이머리가 하루에 몇 번씩 바뀐다"는 감지가 너무 예민하거나 합의 저장소가 불안한 경우다. etcd 디스크가 느려 리더 키 갱신이 늦으면 멀쩡한 프라이머리가 내려간다. Patroni 로그에서 갱신 실패 시각과 etcd의 지연 지표를 맞춰 보고, `ttl`을 늘리거나 etcd를 빠른 디스크로 옮긴다.

"장애 조치는 됐는데 주문 일부가 사라졌다"는 비동기 복제의 지연만큼 잃은 것이다. 사고 직전의 `pg_stat_replication.replay_lag`나 `pg_wal_lsn_diff`로 지연을 평소에 지표로 남겨 둬야 "얼마나 잃었나"에 답할 수 있다. 옛 프라이머리의 디스크가 살아 있다면 아직 넘어가지 못한 WAL을 거기서 꺼내 확인할 수 있으니 바로 지우지 않는다.

"새 프라이머리로 넘어갔는데 몇 분 동안 에러가 이어진다"는 클라이언트 쪽 문제다. DNS TTL, 앱의 DNS 캐시, 풀에 남은 옛 연결을 차례로 본다. 앱 서버 하나에서 `ss -tnp | grep 5432`로 아직 옛 IP에 붙은 연결이 있는지 보면 바로 드러난다.

"스탠바이가 승격 후보에서 빠져 아무도 승격되지 않았다"는 `maximum_lag_on_failover`에 걸린 경우다. 의도한 동작이지만, 스탠바이가 평소에도 많이 뒤처진다는 신호이니 복제 경로의 대역폭과 스탠바이의 재생 속도를 본다.

## 넘어갔다는 말의 내용

"자동으로 넘어갔다"에는 세 가지 숫자가 숨어 있다. 얼마 동안 멈췄나(실험에서는 9.584초, 그중 8.8초가 감지), 무엇을 잃었나(비동기 복제에서 응답까지 받은 42번 주문), 그리고 넘어간 뒤 정말 한 곳만 쓰고 있나(펜싱). 감지는 빠를수록 오해가 늘고, 잃지 않으려면 커밋마다 기다려야 하고, 클라이언트는 DNS·VIP·프록시·드라이버 중 하나로 데려가야 한다. 이 셋을 정한 뒤에야 장애 조치가 실제로 서비스를 지킨다.

## 면접에서 나올 만한 질문

### 장애 조치 시간은 무엇으로 이루어지나요?

감지, 승격, 클라이언트 전환 세 토막이다. 실험에서는 9.584초 중 감지가 8.8초, 승격이 0.16초, 전환이 0.54초였다. 승격 자체는 빠르고 "정말 죽었나"를 확신하는 데 대부분의 시간이 들며, DNS로 전환하면 TTL이 그 위에 더해진다.

### 감지 시간을 1초로 줄이면 안 되나요?

줄일 수는 있지만 오탐이 늘어난다. 응답이 없다는 사실만으로는 죽음, 느림, 네트워크 흔들림을 구별할 수 없어서, 체크포인트나 순간적인 지연에도 멀쩡한 프라이머리를 버리게 된다. 그래서 여러 위치에서 과반으로 판단하고, 실제 쿼리로 확인하고, 넘긴 뒤 일정 시간은 다시 넘기지 않게 막는다.

### 비동기 복제에서 장애 조치를 하면 무엇을 잃나요?

클라이언트가 성공 응답까지 받았지만 아직 스탠바이로 가지 못한 커밋을 잃는다. 비동기 복제는 프라이머리가 자기 디스크에 쓰고 바로 응답하기 때문이다. 실험에서 복제가 0.4초 뒤처진 상태로 프라이머리를 죽이자 응답받은 42번 주문이 새 프라이머리에 없었다. 동기 복제로 바꾸면 잃지 않았지만 커밋마다 왕복 시간(400ms)을 기다렸다.

### 스플릿 브레인은 왜 생기고 어떻게 막나요?

옛 프라이머리가 죽지 않았는데 죽은 것으로 판단하고 스탠바이를 승격하면 두 서버가 모두 쓰기를 받는다. 실험에서 옛 프라이머리를 살려 둔 채 승격하자 둘 다 `pg_is_in_recovery = f`였고, 다중 호스트 클라이언트는 목록의 첫 서버인 옛 프라이머리에 붙었다. 승격 전에 STONITH, 네트워크 차단, watchdog 재부팅 같은 펜싱으로 옛 프라이머리를 확실히 끊어 막는다.

### DNS, VIP, 프록시 중 클라이언트 전환은 무엇으로 하나요?

환경에 따라 고른다. DNS는 어디서나 되지만 TTL과 앱 내부 캐시만큼 늦다. VIP는 빠르지만 같은 L2 망에서만 되고 클라우드에서는 API로 IP를 옮겨야 한다. HAProxy 같은 프록시는 Patroni의 헬스 체크로 프라이머리를 고르고 앱은 주소 하나만 알면 되지만 프록시 자체를 이중화해야 한다. 어느 쪽이든 커넥션 풀의 옛 연결을 비우는 처리가 필요하다.

### Patroni의 ttl, loop_wait, retry_timeout은 어떤 관계인가요?

ttl은 리더 키의 수명이고, loop_wait는 노드가 점검하고 키를 갱신하는 주기, retry_timeout은 저장소나 DB 연결 실패를 견디는 시간이다. 리더가 일시적인 재시도 중에 키를 잃지 않도록 loop_wait + 2 × retry_timeout이 ttl 이하가 되게 잡는다. 기본값 30/10/10이면 장애 감지에 최대 수십 초가 걸리는데, 오탐을 줄이려는 선택이다.

### 장애 조치 뒤 주문 번호가 건너뛰는 건 문제인가요?

데이터 손실은 아니다. PostgreSQL 시퀀스는 WAL 기록을 줄이려고 32개 앞의 값을 미리 기록하고, 승격된 스탠바이는 그 값부터 이어 간다. 실험에서도 42 다음이 67이었다. 다만 번호가 연속이라고 가정하는 정산 검사나 코드는 거짓 경보를 내니, 시퀀스 값은 유일성만 믿는다.

### Patroni 대신 repmgr나 pg_auto_failover를 쓰면 무엇이 달라지나요?

결정을 누가 하고 펜싱을 누가 하는지가 달라진다. Patroni는 etcd 같은 합의 저장소의 리더 키로 결정하고 키를 잃은 노드가 스스로 내려간다. repmgr는 합의 저장소 없이 노드끼리 판단해서 망 분리는 witness 서버로, 펜싱은 직접 짠 스크립트로 막아야 한다. pg_auto_failover는 monitor 노드가 결정하고 동기 복제가 기본이라 단순하지만, monitor가 죽으면 자동 장애 조치가 멈춘다.
