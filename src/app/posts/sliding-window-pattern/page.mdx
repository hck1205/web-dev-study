"반복되는 글자가 없는 가장 긴 부분 문자열"을 처음 풀면 대개 시작점마다 끝까지 훑는다. 맞는 답이 나오지만 이중 반복문이다. 들여다보면 시작점을 한 칸 옮길 때마다 바로 전에 확인한 글자들을 처음부터 다시 확인하고 있다. 버린 건 맨 앞 글자 하나뿐인데도.

슬라이딩 윈도는 그 낭비를 없애는 방법이다. 연속된 구간(창)을 하나 들고, 오른쪽 끝을 한 칸 늘리거나 왼쪽 끝을 한 칸 줄일 때 바뀐 칸만큼만 상태를 고친다. 이 글은 LeetCode의 Sliding Window 묶음을 푸는 틀을 정리하는 허브다. 각 문제의 풀이는 문제 글에 있고, 여기서는 고정 창과 가변 창의 틀, 창 상태를 담는 그릇, 왜 O(n)인지, 그리고 창이 통하지 않는 입력을 본다. 전체 공부 순서는 [LeetCode 공부법](/posts/leetcode-study-guide)에 있다.

## 창이 한 칸 움직일 때 바뀌는 것

길이 3인 연속 구간의 합 중 가장 큰 값을 구해 보자. 배열은 `[2, 1, 5, 1, 3, 2]`다. 매번 세 칸을 다시 더하면 구간마다 k번 덧셈이라 O(nk)다. 그런데 창을 한 칸 밀면 바뀌는 건 들어온 칸 하나와 나간 칸 하나뿐이다.

```js
function maxSumK(a, k) {
  let sum = 0;
  for (let i = 0; i < k; i++) sum += a[i]; // 첫 창은 그냥 더한다
  let best = sum;
  for (let r = k; r < a.length; r++) {
    sum += a[r] - a[r - k];                 // 들어온 칸을 더하고 나간 칸을 뺀다
    best = Math.max(best, sum);
  }
  return best;
}
console.log(maxSumK([2, 1, 5, 1, 3, 2], 3));
```

## 길이가 정해진 창

창 길이 k가 문제에 주어지면 고정 창이다. 틀은 위와 같다. 오른쪽 끝 `r`이 한 칸 갈 때마다 `r - k` 칸이 빠진다.

상태가 합이 아닌 예로, 문자열 `s` 안에서 `p`의 애너그램(글자 구성이 같은 문자열)이 시작하는 위치를 모두 찾는 LeetCode 438번을 보자. 창 길이는 `p`의 길이로 고정이고, 창 상태는 글자별 개수다.

```js
function findAnagrams(s, p) {
  const A = 97; // 'a'의 코드
  const need = new Array(26).fill(0), win = new Array(26).fill(0);
  for (const c of p) need[c.charCodeAt(0) - A]++;
  const out = [];
  for (let r = 0; r < s.length; r++) {
    win[s.charCodeAt(r) - A]++;                                 // 들어온 글자
    if (r >= p.length) win[s.charCodeAt(r - p.length) - A]--;   // 나간 글자
    if (r >= p.length - 1 && win.every((v, i) => v === need[i])) out.push(r - p.length + 1);
  }
  return out;
}
console.log(findAnagrams("cbaebabacd", "abc"));
```

```text
[ 0, 6 ]
```

매번 26칸을 비교하니 O(26n)이고, 26은 상수라 O(n)이다. 글자 종류가 유니코드 전체처럼 크다면 비교 비용이 커지니, 일치하는 글자 종류 수를 변수 하나로 따로 세서 들어오고 나갈 때만 고치는 방식으로 바꾼다. 이 "일치 개수" 변수는 [Minimum Window Substring](/posts/leetcode-minimum-window-substring)에서 핵심 부품이 된다.

고정 창에서 자주 하는 실수는 첫 창이 다 차기 전에 답을 기록하는 것이다. 위 코드의 `r >= p.length - 1` 조건이 그걸 막는다. 이 조건을 빼면 길이가 모자란 창도 비교해서, 우연히 개수가 맞는 일은 없더라도 쓸데없는 비교를 한다. 합을 다루는 문제에서는 모자란 창의 합이 답으로 잡혀 틀린다.

## 늘렸다 줄이는 창

창 길이가 정해져 있지 않고 "조건을 만족하는 가장 긴/짧은 구간"을 물으면 가변 창이다. 오른쪽 끝은 매번 한 칸씩 늘리고, 왼쪽 끝은 조건을 보고 필요한 만큼 줄인다. 가장 긴 것과 가장 짧은 것은 줄이는 조건이 반대라서 틀이 둘이다.

```js
// 가장 긴 창: 조건이 깨지면 다시 맞을 때까지 줄이고, 줄인 뒤에 답을 잰다
function longestTemplate(a) {
  let l = 0, best = 0;
  for (let r = 0; r < a.length; r++) {
    add(a[r]);                    // 1. 오른쪽 칸을 창에 넣는다
    while (!valid()) remove(a[l++]); // 2. 깨졌으면 왼쪽을 뺀다
    best = Math.max(best, r - l + 1); // 3. 지금 창은 조건을 만족한다
  }
  return best;
}

// 가장 짧은 창: 조건을 만족하는 동안 답을 재면서 줄인다
function shortestTemplate(a) {
  let l = 0, best = Infinity;
  for (let r = 0; r < a.length; r++) {
    add(a[r]);
    while (valid()) {             // 만족하는 동안
      best = Math.min(best, r - l + 1); // 줄이기 전에 잰다
      remove(a[l++]);
    }
  }
  return best === Infinity ? 0 : best;
}
```

두 틀의 차이는 답을 재는 자리다. 가장 긴 창은 `while`을 빠져나온 뒤, 조건을 만족하는 창에서 잰다. 가장 짧은 창은 `while` 안에서, 줄이기 직전에 잰다. 이걸 바꿔 쓰면 가장 긴 문제에서 조건이 깨진 창을 답으로 잡거나, 가장 짧은 문제에서 이미 줄여 버린 창을 잰다.

예로 0과 1로 된 배열에서 0을 많아야 k개까지 1로 바꿀 때 가장 긴 1의 연속 길이(1004번)를 보자. 창 상태는 "창 안의 0 개수" 하나이고, 조건은 그게 k 이하인 것이다. 아래 그림은 `[1, 0, 1, 1, 0, 1]`, k = 1이다.

다섯 번째 단계가 이 틀의 핵심이다. 조건이 깨졌을 때 왼쪽을 한 칸만 줄이는 게 아니라, 다시 맞을 때까지 `while`로 줄인다. 앞 칸이 1이면 빼도 0 개수는 그대로라 한 칸으로는 부족하다. `while` 대신 `if`를 쓰면 이 경우를 놓친다.

## 안쪽에 while이 있어도 O(n)인 이유

가변 창 코드는 `for` 안에 `while`이 있어서 O(n²)처럼 보인다. 면접에서도 "이거 이중 반복문 아닌가요?"라는 질문을 받는다.

세는 대상을 바꾸면 답이 보인다. 반복문의 실행 횟수 대신 포인터가 움직인 거리를 센다. `r`은 0에서 n − 1까지 한 방향으로만 가니 n번 움직인다. `l`도 한 방향으로만 가고 `r`을 넘지 않으니 전체를 통틀어 많아야 n번 움직인다. `while`의 몸통은 한 번 돌 때마다 `l`을 한 칸 옮기니, 모든 `for` 반복에 걸쳐 `while` 몸통이 도는 횟수를 다 더해도 n 이하다. 원소 하나하나가 창에 한 번 들어오고 많아야 한 번 나간다고 말해도 된다.

그래서 전체는 O(n)이다. 어떤 반복에서는 `while`이 많이 돌 수 있지만 그만큼 다른 반복에서 덜 돈다. 이런 식으로 전체 합을 따지는 분석을 분할 상환 분석이라고 한다([Big O 표기법](/posts/big-o-notation)).

이 논리가 성립하려면 `l`이 절대 뒤로 가면 안 된다. [Longest Substring Without Repeating Characters](/posts/leetcode-longest-substring-without-repeating)를 해시맵으로 풀 때 "마지막으로 본 위치 + 1"로 `l`을 점프시키는데, 그 위치가 이미 창 밖(지금 `l`보다 앞)이면 `l`이 뒤로 간다. `abba`에서 마지막 `a`를 만나면 `a`의 이전 위치 0 + 1 = 1로 돌아가 창이 `bba`가 된다. 틀린 답이 나오고 O(n) 보장도 깨진다. `l = Math.max(l, last + 1)`로 막는다.

## 창 상태를 담는 그릇

창에 무엇을 들고 다닐지는 "조건을 판정하려면 무엇을 알아야 하나"로 정한다. 넣고 뺄 때 O(1)에 고칠 수 있어야 창 전체가 O(n)이 된다.

- 합이나 개수 하나면 숫자 변수 하나. 위의 0 개수, 창 합.
- 글자 구성이면 길이 26짜리 개수 배열. 영어 소문자만 나온다는 조건이 있을 때 `Map`보다 빠르고 코드도 짧다. 글자 종류가 정해져 있지 않으면 `Map`을 쓰고, 개수가 0이 되면 `delete`해서 `size`가 "서로 다른 글자 수"가 되게 한다.
- 창 안의 최댓값이나 최솟값이면 단조 덱. 최댓값은 뺄 때 다음 최댓값을 알 수 없어서 숫자 변수로는 못 들고 다닌다. 덱 안에 "앞으로 최댓값이 될 수 있는 후보"만 감소 순서로 남긴다. 원리는 [단조 스택 패턴](/posts/monotonic-stack-pattern)과 같고, 문제로는 [Sliding Window Maximum](/posts/leetcode-sliding-window-maximum)이 있다.
- 창 안의 중앙값이나 k번째 값이면 정렬된 구조가 필요하다. 힙 두 개에 지연 삭제를 붙이거나, 다른 언어의 정렬 컨테이너(Java `TreeMap`, C++ `multiset`)를 쓴다. 자바스크립트에는 기본 정렬 컨테이너가 없어서 직접 만들어야 한다. 이 경우 창은 O(n log k)가 된다.

`Map`을 쓰고 개수가 0일 때 지우지 않는 실수가 흔하다. `cnt.set(c, 0)`인 키가 남아 있으면 `cnt.size`가 실제 글자 종류보다 커서 "서로 다른 글자가 k개 이하" 같은 조건이 엉뚱하게 깨진다.

## 창이 통하지 않는 입력

가변 창이 맞는 이유를 다시 생각해 보자. 오른쪽으로 늘리면 조건이 한 방향으로만 변하고(합이 커지거나 그대로), 왼쪽을 줄이면 반대 방향으로만 변한다는 단조성이 있었다. 그래서 "깨지면 줄인다"가 안전했다. 이 단조성이 사라지면 창도 틀린다.

가장 흔한 경우가 음수다. "합이 target 이상인 가장 짧은 부분 배열"(209번)은 값이 모두 양수라는 조건이 붙어 있다. 그 조건을 빼고 음수가 섞인 배열에 같은 코드를 돌려 봤다.

```js
function minLen(target, a) {
  let l = 0, sum = 0, best = Infinity;
  for (let r = 0; r < a.length; r++) {
    sum += a[r];
    while (sum >= target) { best = Math.min(best, r - l + 1); sum -= a[l++]; }
  }
  return best === Infinity ? 0 : best;
}
console.log("window", minLen(4, [1, -5, 3, 4]), "brute", bruteMin(4, [1, -5, 3, 4]));
console.log("window", minLen(3, [1, 2, -3, 3]), "brute", bruteMin(3, [1, 2, -3, 3]));
```

```text
window 0 brute 1
window 2 brute 1
```

`bruteMin`은 모든 구간을 확인하는 이중 반복문이다. 첫 줄에서 답은 `[4]` 한 칸인데 창은 "없다"고 답한다. 창 합이 1, −4, −1, 3으로 가다가 끝까지 4에 닿지 못해서 왼쪽을 줄일 기회가 오지 않았다. 앞쪽의 1과 −5를 빼면 합이 오히려 커지는데, 창은 "합이 모자라면 늘린다"만 알아서 그 사실을 모른다. 두 번째 줄도 마지막 `[3]` 한 칸이 답인데 2를 낸다.

음수가 있으면 고르는 도구가 바뀐다.

- 합이 정확히 k인 부분 배열의 개수(560번): 누적 합과 해시맵. "지금까지의 누적 합 − k"가 앞에 몇 번 나왔는지 센다. O(n).
- 합이 k 이상인 가장 짧은 부분 배열, 음수 포함(862번): 누적 합 위에 단조 덱을 쓴다. 누적 합이 커지는 후보만 남긴다.
- 합의 최댓값(53번 Maximum Subarray): 창이 아니라 카데인 알고리즘, 곧 1차원 [동적 계획법](/posts/dynamic-programming)이다.

560번 풀이를 확인해 보면 이렇다.

```js
function subarraySum(a, k) {
  const seen = new Map([[0, 1]]); // 누적 합 0이 한 번 나왔다고 시작한다 (처음부터 잘린 구간)
  let pre = 0, count = 0;
  for (const x of a) {
    pre += x;
    count += seen.get(pre - k) ?? 0; // 앞에서 pre - k였던 지점부터 지금까지의 합이 k
    seen.set(pre, (seen.get(pre) ?? 0) + 1);
  }
  return count;
}
console.log(subarraySum([1, -1, 1, 1], 2));
```

```text
2
```

`[1, 1]`과 `[1, -1, 1, 1]` 두 개다. 문제에 "양수만", "음이 아닌 정수"라는 말이 있는지 먼저 보는 습관이 이 함정을 막는다. 면접에서 슬라이딩 윈도 풀이를 내면 "음수가 있으면요?"가 단골 꼬리 질문이다.

## 정확히 K개는 많아야 K개 둘의 차로

"서로 다른 정수가 정확히 K개인 부분 배열의 개수"(992번)는 창으로 바로 세기 어렵다. 정확히 K개인 창은 왼쪽을 줄여도 여전히 K개일 수 있어서, 언제 줄여야 하는지가 한 방향으로 정해지지 않는다.

"많아야 K개"는 단조적이다. 창을 줄이면 종류 수가 줄거나 그대로다. 그리고 오른쪽 끝이 `r`일 때 많아야 K개인 창의 왼쪽 끝은 `l`부터 `r`까지 어디든 되니, 그 개수 `r - l + 1`을 더하면 많아야 K개인 부분 배열을 전부 센다. 정확히 K개는 많아야 K개에서 많아야 K − 1개를 빼면 된다.

```js
function atMost(a, k) {
  const cnt = new Map();
  let l = 0, res = 0;
  for (let r = 0; r < a.length; r++) {
    cnt.set(a[r], (cnt.get(a[r]) ?? 0) + 1);
    while (cnt.size > k) {
      const v = a[l++];
      cnt.set(v, cnt.get(v) - 1);
      if (cnt.get(v) === 0) cnt.delete(v); // 0이 된 키는 지워야 size가 맞다
    }
    res += r - l + 1; // r에서 끝나는 창은 l..r 어디서 시작해도 된다
  }
  return res;
}
const exactly = (a, k) => atMost(a, k) - atMost(a, k - 1);
console.log(exactly([1, 2, 1, 2, 3], 2), exactly([1, 2, 1, 3, 4], 3));
```

```text
7 3
```

이 변환은 "정확히"를 단조적인 "많아야"로 바꾸는 기술이라 다른 문제에도 쓰인다. 합이 정확히 goal인 이진 부분 배열(930번), 홀수가 정확히 k개인 부분 배열(1248번)이 같은 모양이다.

## 문제 문장에서 창을 알아보는 법

문장에 "contiguous subarray", "substring"이 있으면 일단 창을 떠올린다. "subsequence"(부분 수열, 떨어져 있어도 된다)라면 창이 아니다. 연속이 아니면 창 안의 상태라는 개념이 성립하지 않아서 대개 [동적 계획법](/posts/dynamic-programming)으로 간다. 이 두 단어를 헷갈려서 시간을 버리는 경우가 꽤 많다.

그다음 무엇을 묻는지 본다. "of size k", "length k"가 있으면 고정 창이다. "longest", "at most"가 있으면 가장 긴 창, "minimum length", "smallest window"가 있으면 가장 짧은 창이다. "number of subarrays"처럼 개수를 물으면 오른쪽 끝마다 `r - l + 1`을 더하는 세기 틀이나, 위에서 본 "많아야" 두 번 빼기를 의심한다.

마지막으로 값의 범위를 본다. "positive integers", "non-negative"가 있으면 합을 다루는 창이 안전하다. 그런 말이 없고 음수가 들어올 수 있다면 누적 합 쪽을 먼저 생각한다. 이 세 단계를 거치면 창을 쓸지, 어떤 틀을 쓸지가 문제를 다 읽기 전에 거의 정해진다.

## 코드 밖에서 만나는 같은 창

슬라이딩 윈도는 알고리즘 문제에서만 쓰는 기술이 아니다. 서버에서 "최근 1분 동안 요청이 100개를 넘으면 막는다"는 처리율 제한이 바로 고정 길이(시간 기준) 창이다. 요청 시각을 큐에 넣고 1분이 지난 것을 앞에서 빼면 창 안의 개수가 곧 판정 기준이 된다. 메모리를 아끼려고 창을 칸으로 나눠 근사하는 방식까지 [처리율 제한 알고리즘](/posts/rate-limiting-algorithms)에서 다룬다.

모니터링의 "최근 5분 평균 응답 시간"도 같은 계산이다. 새 측정값을 더하고 5분 지난 값을 빼면 평균을 매번 다시 계산하지 않아도 된다. 다만 p99 같은 백분위수는 위의 "창 안의 k번째 값"처럼 넣고 빼는 것만으로는 유지가 안 돼서, 실무에서는 히스토그램으로 근사한다([백분위 지연 시간](/posts/percentile-latency)). 이름은 같지만 TCP의 슬라이딩 윈도는 "확인 응답을 받지 않고 보낼 수 있는 양"을 뜻하는 흐름 제어 개념이라 이 글의 창과는 다르다.

## 자주 틀리는 곳

### 창 길이를 r - l로 잰다

닫힌 구간 `[l, r]`의 길이는 `r - l + 1`이다. 반쯤 열린 구간 `[l, r)`로 쓰는 사람은 `r - l`이 맞다. 한 코드 안에서 두 방식을 섞으면 한 칸씩 어긋난다. 창을 항상 `[l, r]` 닫힌 구간으로 두고 `r`을 `for`의 변수로 쓰기로 정해 두면 덜 틀린다.

### 줄이는 조건에 if를 쓴다

조건을 다시 맞추는 데 한 칸으로 부족할 수 있다. 위 0 개수 예처럼 앞 칸이 조건과 상관없는 값이면 여러 칸을 빼야 한다. 줄이기는 `while`이다. 예외가 [Longest Repeating Character Replacement](/posts/leetcode-longest-repeating-character-replacement)의 "창을 줄이지 않고 미끄러뜨리는" 풀이인데, 이건 답이 커질 때만 의미가 있다는 성질을 이용한 의도적인 `if`다. 왜 그게 맞는지는 문제 글에서 따로 증명한다.

### 답을 잘못된 자리에서 잰다

가장 긴 창은 줄인 뒤에, 가장 짧은 창은 줄이기 전에 잰다. 위 템플릿 두 개를 비교해서 기억해 둔다.

### 고정 창에서 첫 창이 차기 전에 기록한다

`r >= k - 1`부터 답을 잰다. 합의 최솟값을 구하는 문제에서 이걸 빠뜨리면 길이가 모자란 창의 작은 합이 답이 된다.

## 면접에서 나올 만한 질문

### 슬라이딩 윈도는 언제 쓰나요?

연속된 부분 배열이나 부분 문자열 중 가장 긴 것, 가장 짧은 것, 개수를 물을 때 쓴다. 조건이 창을 늘리면 한 방향, 줄이면 반대 방향으로만 변해야 한다. 창 길이가 주어지면 고정 창, 조건만 주어지면 가변 창을 쓴다.

### 안에 while이 있는데 왜 O(n)인가요?

왼쪽 포인터가 한 방향으로만 움직이고 오른쪽 포인터를 넘지 않으니 전체를 통틀어 많아야 n번 움직이기 때문이다. while 몸통은 돌 때마다 왼쪽 포인터를 한 칸 옮기니 모든 반복을 합쳐도 n번 이하다. 원소마다 창에 한 번 들어오고 한 번 나간다고 보면 된다.

### 음수가 섞인 배열에서 합이 k 이상인 가장 짧은 구간을 창으로 구하면 어떻게 되나요?

틀린 답이 나온다. 음수가 있으면 왼쪽을 빼서 합이 오히려 커질 수 있어서 "모자라면 늘리고 넘치면 줄인다"는 판단의 근거인 단조성이 깨진다. 합이 정확히 k인 개수라면 누적 합과 해시맵, 가장 짧은 구간이라면 누적 합 위의 단조 덱을 쓴다.

### 가장 긴 창과 가장 짧은 창 템플릿은 무엇이 다른가요?

답을 재는 자리가 다르다. 가장 긴 창은 조건이 깨졌을 때 다시 맞을 때까지 줄인 뒤 잰다. 가장 짧은 창은 조건을 만족하는 동안 줄이면서 줄이기 직전에 잰다.

### 창 안의 최댓값을 유지하려면 어떻게 하나요?

숫자 변수 하나로는 안 된다. 최댓값이 창에서 빠질 때 다음 최댓값을 모르기 때문이다. 앞으로 최댓값이 될 수 있는 후보만 감소 순서로 담은 단조 덱을 쓰면 넣고 빼는 데 분할 상환 O(1)이라 전체가 O(n)이다.

### 서로 다른 값이 정확히 K개인 부분 배열 수는 어떻게 세나요?

정확히 K개는 창을 줄여도 그대로일 수 있어 단조적이지 않다. 그래서 단조적인 "많아야 K개"를 세는 함수를 만들고 많아야 K개에서 많아야 K − 1개를 뺀다. 많아야 K개는 오른쪽 끝마다 r − l + 1을 더하면 O(n)에 센다.

### 해시맵으로 창을 관리할 때 흔한 버그는요?

개수가 0이 된 키를 지우지 않아 size가 실제 종류 수보다 커지는 것, 그리고 마지막으로 본 위치로 왼쪽을 점프시킬 때 그 위치가 이미 창 밖이라 왼쪽이 뒤로 가는 것이다. 앞의 것은 delete로, 뒤의 것은 Math.max로 막는다.
