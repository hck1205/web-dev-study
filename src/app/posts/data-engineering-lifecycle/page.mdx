## 앱에서는 환불인데 리포트에서는 매출이다

고객센터에서 문의가 왔다. 어제 밤 11시 50분에 들어온 주문이 오늘 아침 환불됐는데, 관리자 화면에서는 환불로 보이고 아침 매출 리포트에는 매출로 잡혀 있다고 한다. 어느 쪽이 맞느냐는 질문이다.

둘 다 맞다. 관리자 화면은 운영 DB를 바로 읽으니 지금 상태를 보여 준다. 매출 리포트는 새벽 1시에 운영 DB에서 옮겨 온 사본을 읽으니 새벽 1시의 상태를 보여 준다. 환불은 그 뒤에 일어났다. 데이터가 생겨서 리포트에 닿기까지 몇 단계를 거치고, 단계마다 시간이 걸리고 모양이 바뀐다. 이 길 전체를 데이터 엔지니어링 수명 주기라고 부른다.

이 글은 처음 데이터 엔지니어링을 접하는 사람을 위한 지도다. 주문 하나를 따라 다섯 단계를 걸으면서, 단계마다 무엇을 정해야 하고 어떤 글에서 더 깊이 볼 수 있는지 이어 준다.

## 주문 하나가 지나가는 다섯 단계

조 리스(Joe Reis)와 맷 하우슬리(Matt Housley)의 책 『Fundamentals of Data Engineering』(2022)은 수명 주기를 생성, 저장, 수집, 변환, 서빙으로 나눈다. 저장은 사실 모든 단계에 걸쳐 있지만, 처음 볼 때는 순서대로 놓는 편이 이해하기 쉽다. 이 글은 생성 → 수집 → 저장 → 변환 → 서빙 순서로 따라간다.

## 데이터가 생기는 곳

생성 단계는 데이터 엔지니어가 직접 만들지 않는다. 서비스 팀이 만든 시스템에서 데이터가 생기고, 데이터 엔지니어는 그 시스템이 데이터를 어떻게 남기는지 알아야 한다. 원본마다 성격이 다르다.

운영 DB(OLTP)는 주문, 회원, 재고처럼 서비스가 돌아가는 데 필요한 현재 상태를 담는다. 행이 계속 고쳐지고 지워진다. 그래서 "어제 몇 시에 무슨 상태였나"는 운영 DB에 남지 않는다. 옮겨 오는 쪽이 그 이력을 따로 쌓아야 한다.

이벤트 로그는 "누가 언제 무엇을 했다"를 한 줄씩 덧붙인다. 클릭, 페이지 조회, 검색어, 서버 접근 로그가 여기 속한다. 고쳐지지 않고 쌓이기만 하니 이력은 남지만, 양이 운영 DB보다 몇십 배 많다.

모바일 앱은 까다롭다. 지하철에서 네트워크가 끊기면 앱은 이벤트를 기기에 모아 뒀다가 나중에 보낸다. 그래서 어제 일어난 클릭이 사흘 뒤에 도착하기도 한다. 기기 시계는 사용자가 마음대로 바꿀 수 있어 앱이 적은 시각을 그대로 믿기 어렵다. 업데이트하지 않은 옛 버전 앱이 옛 형식으로 계속 보내기 때문에 같은 이벤트에 형식이 여러 개 섞인다. 그래서 이벤트에는 기기 시각과 서버가 받은 시각, 앱 버전을 함께 남긴다.

```json
{
  "event_id": "8f1c2e4a-6b7d-4c1e-9a53-2f0d7e61b9c4",
  "event_name": "add_to_cart",
  "user_id": 42,
  "product_id": 1007,
  "client_ts": "2026-10-23T23:58:12+09:00",
  "received_at": "2026-10-26T08:03:40+09:00",
  "app_version": "5.12.0",
  "os": "android"
}
```

이 이벤트는 23일 밤에 일어났고 26일 아침에 서버에 왔다. 23일 집계를 24일 새벽에 이미 끝냈다면 이 장바구니 담기는 빠져 있다. 어느 시각으로 날짜를 셀지(일어난 시각이냐 받은 시각이냐), 며칠 늦게 온 것까지 지난 날짜에 다시 넣을지를 정해야 한다. 보통은 일어난 시각으로 세되, 지난 며칠은 매일 다시 계산해 늦게 온 것을 반영한다. `event_id`는 앱이 만든 고유 값이라 같은 이벤트가 재전송돼도 한 번만 셀 수 있게 해 준다.

IoT 기기(센서, 차량, 매장 키오스크)는 짧은 간격으로 수치를 끝없이 보낸다. 연결이 끊겼다 이어지면 순서가 뒤섞여 오고, MQTT의 QoS 1처럼 "최소 한 번" 전달을 쓰면 같은 메시지가 두 번 온다. 기기 펌웨어가 바뀌면 값의 단위가 바뀌기도 한다.

외부 SaaS(결제사, 광고 플랫폼, CRM)는 우리가 고칠 수 없는 원본이다. API 호출 횟수 제한이 있고, 형식이 예고 없이 바뀌고, 과거 데이터를 며칠 뒤에 고쳐서 다시 주기도 한다(광고비 정산이 대표적이다).

## 가져올 때 먼저 정할 것

수집은 원본에서 데이터를 꺼내 저장소로 옮기는 단계다. 도구를 고르기 전에 다섯 가지를 먼저 묻는다.

첫째는 지연이다. 몇 시간 늦어도 되는지, 몇 초 안에 와야 하는지. 아침 매출 리포트는 하루 한 번이면 되고, 이상 결제 탐지는 초 단위여야 한다. 지연 요구가 짧아질수록 비용과 운영 부담이 가파르게 는다. 실제로 필요한 것보다 짧게 잡지 않는다.

둘째는 양이다. 하루 몇 MB인지, 몇 TB인지. 하루 수백만 행이면 PostgreSQL에서 다른 PostgreSQL로 옮기는 스크립트로도 된다. 하루 수십억 이벤트면 Kafka 같은 버퍼와 분산 처리가 필요하다. 지금 양보다 1~2년 뒤의 양을 기준으로 생각하되, 10년 뒤를 위해 지금 복잡하게 만들지는 않는다.

셋째는 스키마와 그 변화다. 원본 형식이 얼마나 자주 바뀌는지, 바뀔 때 누가 알려 주는지. 형식이 바뀐 날 조용히 숫자가 틀리는 일이 가장 흔한 사고다. 이 문제는 [데이터 품질 검사](/posts/data-quality-checks)의 데이터 계약에서 다룬다.

넷째는 중복과 순서다. 네트워크가 끊겨 재시도하면 같은 데이터가 두 번 오고, 모바일·IoT 데이터는 순서가 뒤섞여 온다. 수집 단계에서 이걸 완벽히 막기는 어렵다. 대신 데이터마다 고유한 ID(이벤트 ID, 주문 ID와 버전)를 붙여 받는 쪽에서 두 번 세지 않게 한다.

아래에서 직접 해 볼 수 있다. 결제와 환불 이벤트를 받아 순매출을 구하는데, 재시도로 같은 이벤트가 두 번 올 수 있다. 같은 `eventId`는 한 번만 센다.

다섯째는 개인정보다. 이름, 전화번호, 주소, 카드 번호가 원본에 있다면 옮길지, 가려서 옮길지, 아예 빼고 옮길지를 수집할 때 정한다. 한 번 저장소에 들어가면 백업과 사본에까지 퍼져서 나중에 지우기 어렵다([개인정보와 규정](/posts/data-privacy-compliance)).

이 다섯 가지 답에 따라 방식이 갈린다. 하루 한 번 바뀐 행만 끌어오는 배치 추출과 그 함정은 [ETL과 ELT](/posts/etl-vs-elt)에서, 운영 DB의 변경 로그를 읽어 바로 흘려보내는 방법은 [CDC](/posts/cdc-change-data-capture)에서, 이벤트를 Kafka로 받아 레이크에 쌓는 스트리밍 수집은 [Kafka에서 레이크까지](/posts/kafka-to-lake-pipeline)에서 다룬다.

## 어디에 담아 두나

저장 단계의 질문은 "얼마나 오래, 얼마나 싸게, 어떤 모양으로 둘 것인가"다. 원본을 그대로 오래 두는 곳은 보통 객체 저장소(S3, GCS) 위의 데이터 레이크다. 용량당 값이 싸고 아무 형식이나 넣을 수 있다. 분석용으로 다듬은 데이터는 SQL로 빠르게 읽히는 웨어하우스나 Parquet 같은 컬럼 형식 파일에 둔다.

저장소를 고를 때 자주 놓치는 것이 "읽는 방식"이다. 운영 DB는 한 행을 빨리 찾고 고치게 행 단위로 저장하고, 분석 저장소는 한 컬럼을 수억 행 훑게 컬럼 단위로 저장한다. 같은 데이터라도 읽는 방식에 맞는 곳에 둬야 한다. 이 차이는 [컬럼형 분석 DB](/posts/db-type-columnar-olap)에서, 레이크가 파일을 블록으로 나눠 여러 서버에 저장하는 방식과 작은 파일 문제는 [데이터 레이크와 HDFS](/posts/data-lake-hdfs)에서 볼 수 있다.

얼마나 오래 둘지도 정한다. 원본은 다시 계산할 근거라 길게 두고, 오래된 것은 더 싼 저장 등급으로 옮긴다. 개인정보가 섞인 원본은 보관 기한이 법과 약관으로 정해져 있어서 기한이 지나면 지운다. "언제든 다시 계산할 수 있다"와 "필요 없는 개인정보는 지운다"가 부딪히는 지점이라, 개인정보는 수집할 때 분리해 두는 편이 낫다.

## 쓰기 좋은 모양으로 바꾸기

변환 단계에서 데이터는 원본의 모양에서 쓰는 사람의 모양으로 바뀐다. 타입을 고치고, 중복을 지우고, 시간대를 맞추고, 여러 원본의 같은 개념을 같은 키로 잇고, 회사가 합의한 정의대로 지표를 계산한다.

여기서 가장 중요한 일은 기술보다 정의다. "매출"에 환불을 빼는지, 부가세를 넣는지, 한국 시각 기준인지를 한 곳에서 정하지 않으면 팀마다 다른 숫자를 들고 회의에 온다. 원본·정제·쓰임새로 칸을 나눠 정의를 한 번만 두는 법은 [데이터 웨어하우스 설계](/posts/data-warehouse-architecture)에서, 분석 테이블을 사실과 차원으로 나누는 모델링은 [스타 스키마](/posts/olap-star-schema)에서 다룬다.

변환 도구는 데이터 크기로 고른다. 웨어하우스 안에서 SQL로 충분하면 dbt 같은 도구로 SQL을 관리한다. 웨어하우스에 넣기 전에 수 TB를 다듬어야 하거나 SQL로 쓰기 어려운 처리라면 Spark 같은 분산 처리 엔진을 쓴다([Spark 기초](/posts/spark-basics)). 이 작업들을 매일 순서대로 돌리고, 실패하면 다시 돌리고, 지난 날짜를 다시 계산하는 일은 오케스트레이터가 맡는다([Airflow](/posts/airflow-orchestration)).

## 필요한 사람에게 내주기

서빙은 다듬은 데이터를 쓰는 사람과 시스템에 내주는 단계다. 쓰는 쪽이 여럿이다.

분석가와 경영진은 대시보드와 리포트로 본다. 이쪽은 숫자의 정의가 분명하고, 기준 시각이 적혀 있고, 매일 같은 시각에 갱신되어야 한다. 데이터 사이언티스트와 머신러닝 모델은 학습 데이터와 특성(feature)으로 쓴다. 이쪽은 학습할 때와 실제 예측할 때 같은 방식으로 계산된 값을 써야 해서, 특성 계산을 한 곳에 모으는 특성 저장소(feature store)를 두기도 한다.

다듬은 데이터가 다시 운영 시스템으로 돌아가기도 한다. 웨어하우스에서 계산한 "이탈 위험 고객" 목록을 CRM이나 광고 플랫폼으로 보내는 것을 역방향 ETL(reverse ETL)이라고 부른다. 서비스 화면에 "이번 달 구매 금액" 같은 집계를 보여 주려고 API로 내주는 경우도 있다. 이렇게 데이터가 운영으로 돌아가는 순간부터는 데이터 지연과 오류가 고객 화면에 바로 보이니, 리포트용보다 더 엄격한 품질 검사와 알림이 필요하다.

## 운영 DB에 바로 리포트를 걸면

처음에는 이 모든 단계가 과해 보인다. 운영 DB에 바로 SQL을 날리면 되지 않나. 작을 때는 실제로 그렇게 시작한다. 커지면 무엇이 문제인지 PostgreSQL 16에서 주문 200만 건으로 확인했다(병렬 작업자는 끄고 쟀다).

```sql
-- 서비스가 하는 질문: 주문 하나 찾기
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE id = 123456;

-- 리포트가 하는 질문: 월별·상태별 매출
EXPLAIN (ANALYZE, BUFFERS)
SELECT date_trunc('month', created_at) AS month, status, count(*), sum(amount)
FROM orders GROUP BY 1, 2;
```

```text
-- 두 계획에서 Planning·JIT 줄은 생략했다
 Index Scan using orders_pkey on orders  (cost=0.43..8.45 rows=1 width=77) (actual time=0.153..0.154 rows=1 loops=1)
   Index Cond: (id = 123456)
   Buffers: shared hit=5 read=2
 Execution Time: 0.213 ms

 HashAggregate  (cost=198271.22..251731.80 rows=2000864 width=55) (actual time=1566.190..1566.367 rows=32 loops=1)
   Group Key: date_trunc('month'::text, created_at), status
   Buffers: shared hit=9538 read=9906 dirtied=1
   ->  Seq Scan on orders  (cost=0.00..44454.80 rows=2000864 width=21) (actual time=22.368..840.259 rows=2000000 loops=1)
         Buffers: shared hit=9538 read=9906 dirtied=1
 Execution Time: 1593.288 ms
```

`Buffers` 줄을 본다. 주문 하나 찾기는 8KB 페이지 7개를 읽고 0.2ms에 끝났다. 리포트는 `Seq Scan`으로 200만 행 전부, 페이지 1만 9천여 개(약 150MB)를 읽고 1.6초가 걸렸다. 한 번이면 괜찮다. 문제는 수억 행에서, 분석가 열 명이 아침 9시에 동시에, 대시보드가 5분마다 이걸 돌릴 때다. 그 읽기가 서비스 쿼리가 쓰던 메모리 캐시를 밀어내고 디스크와 CPU를 나눠 쓰면서 주문 API가 느려진다.

다른 문제도 있다. 운영 DB에는 지금 상태만 있어서 "지난달 말 기준 재고"처럼 과거를 묻는 질문에 답할 수 없다. 결제사, 광고 플랫폼 같은 다른 원본과 조인할 수도 없다. 그리고 리포트용 인덱스를 운영 테이블에 추가하면 모든 쓰기가 그만큼 느려진다.

그래서 첫 단계는 보통 읽기 복제본이다. 리포트를 복제본으로 보내면 주 DB의 부하는 피한다. 다만 복제본에서 긴 쿼리를 돌리면 주 DB에서 온 변경을 적용하지 못해 복제가 밀리거나, PostgreSQL이 그 쿼리를 취소하는 일이 생긴다(`max_standby_streaming_delay`, `hot_standby_feedback` 설정이 이 둘 사이의 선택이다). 복제본도 결국 행 저장이라 큰 집계는 여전히 느리다.

## 데이터 엔지니어, 분석가, 데이터 사이언티스트

이 길 위에서 일하는 사람의 역할도 나뉜다. 회사마다 경계가 다르지만 대략 이렇다.

데이터 엔지니어는 길을 만든다. 원본에서 데이터를 가져오고, 저장소를 설계하고, 변환 작업이 매일 제때 정확히 돌게 하고, 실패하면 고친다. 관심사는 파이프라인의 신뢰성, 비용, 지연이다. 소프트웨어 엔지니어링과 분산 시스템, SQL, 클라우드 인프라를 다룬다.

데이터 분석가는 길 끝에서 질문에 답한다. 다듬은 데이터로 지표를 만들고, 대시보드를 짓고, "지난달 매출이 왜 줄었나"를 파고든다. SQL과 통계, 그리고 비즈니스 이해가 핵심이다.

데이터 사이언티스트는 데이터로 예측하거나 원인을 추정한다. 추천 모델, 이탈 예측, A/B 테스트 분석이 이쪽 일이다. 통계와 머신러닝, Python을 주로 쓴다. 데이터 사이언티스트가 일하는 시간의 상당 부분이 데이터를 찾고 다듬는 데 쓰인다는 말이 흔한데, 데이터 엔지니어가 그 부분을 줄여 주는 사람이다.

둘 사이에서 변환과 지표 정의를 맡는 애널리틱스 엔지니어라는 역할도 생겼다. dbt가 퍼지면서 SQL로 정제·모델링을 맡고 테스트와 문서를 관리한다. 작은 회사에서는 한 사람이 이 모든 역할을 한다.

## 스크립트 하나로 만드는 첫 파이프라인

작은 팀의 첫 파이프라인은 대개 셸 스크립트 하나와 크론이다. 운영 DB의 `orders`를 리포트용 DB로 매일 밤 통째로 옮기는 스크립트를 Ubuntu 24.04, PostgreSQL 16에서 짜 봤다. 단순해 보여도 다섯 단계가 다 들어 있다. 운영 DB에서 생긴 데이터를(생성) 읽어 와서(수집) 리포트 DB에 담고(저장), 리포트 쿼리가 읽는다(서빙). 변환은 아직 리포트 쿼리 안에 있다.

리포트 DB에는 사본 테이블과 함께, 적재 기록을 남길 테이블을 하나 둔다. 처음 문의의 "어느 쪽이 맞나"에 답하려면 사본이 언제 기준인지 알아야 한다.

```sql
-- 리포트 DB
CREATE TABLE load_runs (
  table_name   text        NOT NULL,
  started_at   timestamptz NOT NULL,
  finished_at  timestamptz NOT NULL,
  source_as_of timestamptz NOT NULL,   -- 원본을 이 시각 기준으로 읽었다
  rows_loaded  bigint      NOT NULL
);
```

첫 판은 원본의 `\copy ... TO STDOUT`을 파이프로 리포트 DB의 `\copy ... FROM STDIN`에 바로 넘겼다. `psql -1`은 여러 `-c`를 한 트랜잭션으로 묶는다.

```bash
#!/usr/bin/env bash
set -euo pipefail
SRC=(psql -d shop   -v ON_ERROR_STOP=1)     # 운영 DB (실험에서는 접속 옵션을 더 붙였다)
DST=(psql -d report -v ON_ERROR_STOP=1)     # 리포트 DB
started=$(date -u +%FT%T.%NZ)
as_of=$("${SRC[@]}" -Atc "SELECT now()")    # 원본을 읽기 시작한 시각

"${SRC[@]}" -c "\copy (SELECT id,user_id,status,amount,created_at,updated_at FROM orders) TO STDOUT" \
| "${DST[@]}" -1 \
    -c "TRUNCATE orders_copy" \
    -c "\copy orders_copy FROM STDIN" \
    -c "INSERT INTO load_runs SELECT 'orders', '$started', clock_timestamp(), '$as_of', count(*) FROM orders_copy"
```

```text
TRUNCATE TABLE
COPY 2000000
INSERT 0 1
2026-10-24T10:18:42Z orders loaded as_of=2026-10-24 10:18:35.335572+00
```

200만 건이 7.5초에 옮겨졌다. 잘 도는 것 같으니, 원본 팀이 `amount`를 `total_amount`로 바꾼 날을 흉내 내 원본 쿼리를 일부러 틀리게 해 봤다.

```text
ERROR:  column "total_amount" does not exist
LINE 1: COPY  ( SELECT id,user_id,status,total_amount,created_at,upd...
                                         ^
TRUNCATE TABLE
COPY 0
INSERT 0 1
exit=1
```

스크립트는 종료 코드 1로 실패했다. 그런데 리포트 DB의 `orders_copy`를 세어 보니 0건이었다. 파이프의 양쪽은 동시에 돈다. 왼쪽이 실패하자 오른쪽은 빈 입력을 받았고, 빈 입력도 정상적인 입력이니 `TRUNCATE`, `COPY 0`, `INSERT`를 마치고 커밋했다. `pipefail`은 스크립트의 종료 코드만 바꿀 뿐, 이미 커밋한 오른쪽을 되돌리지 않는다. 아침 리포트는 매출 0원을 보여 준다.

고친 판은 두 가지를 바꿨다. 원본을 먼저 파일로 다 받고, 받기에 성공했을 때만 적재를 시작한다. 그리고 적재 트랜잭션 안에서 행 수가 지난번보다 10% 넘게 줄었으면 예외를 던져 되돌린다.

```bash
tmp=$(mktemp)                    # 1) 먼저 파일로 다 받는다
trap 'rm -f "$tmp"' EXIT         #    주문 데이터가 든 파일이니 끝나면 지운다
"${SRC[@]}" -c "\copy (SELECT $COLS FROM orders) TO '$tmp'"   # 실패하면 여기서 멈춘다

"${DST[@]}" -1 \
  -c "TRUNCATE orders_copy" \
  -c "\copy orders_copy FROM '$tmp'" \
  -c "DO \$\$ BEGIN
        IF (SELECT count(*) FROM orders_copy) <
           0.9 * coalesce((SELECT rows_loaded FROM load_runs WHERE table_name = 'orders'
                           ORDER BY finished_at DESC LIMIT 1), 0) THEN
          RAISE EXCEPTION 'row count dropped more than 10%%';   -- 2) 갑자기 줄면 되돌린다
        END IF;
      END \$\$" \
  -c "INSERT INTO load_runs SELECT 'orders', '$started', clock_timestamp(), '$as_of', count(*) FROM orders_copy"
```

원본 쿼리가 틀린 경우와, 원본이 절반(100만 건)만 내려온 경우를 돌렸다.

```text
ERROR:  column "total_amount" does not exist
LINE 1: COPY  ( SELECT id,user_id,status,total_amount,created_at,upd...
                                         ^
exit=1

COPY 1000000
TRUNCATE TABLE
COPY 1000000
ERROR:  row count dropped more than 10%
CONTEXT:  PL/pgSQL function inline_code_block line 5 at RAISE
exit=1
```

두 경우 모두 리포트 DB의 `orders_copy`는 직전의 200만 건 그대로였다. 첫째는 적재가 시작되지도 않았고, 둘째는 `TRUNCATE`까지 했지만 같은 트랜잭션이 롤백되면서 되돌아갔다. 트랜잭션이 끝나기 전까지 리포트를 읽는 쪽은 예전 데이터를 계속 본다. 이 작은 스크립트에 이미 [데이터 품질 검사](/posts/data-quality-checks)의 "검사하고 통과하면 넘긴다"가 들어 있다.

크론에는 이렇게 건다. `flock -n`은 이전 실행이 아직 돌고 있으면 새 실행을 건너뛰게 해서, 적재가 길어진 날 두 개가 겹쳐 도는 일을 막는다.

```bash
crontab -e   # 현재 사용자의 크론 편집
# 매일 01:05에 실행, 겹치면 건너뛰고, 출력은 로그 파일로
5 1 * * * flock -n /tmp/nightly_orders.lock /opt/etl/nightly_orders.sh >> /var/log/etl/orders.log 2>&1
```

리포트 화면에는 `load_runs`에서 기준 시각을 꺼내 함께 보여 준다. 처음 문의 같은 질문은 이 한 줄로 대부분 풀린다.

```sql
SELECT to_char(max(source_as_of) AT TIME ZONE 'Asia/Seoul', 'YYYY-MM-DD HH24:MI') || ' KST 기준' AS as_of
FROM load_runs WHERE table_name = 'orders';
```

```text
           as_of
---------------------------
 2026-10-24 19:18 KST 기준
(1 row)
```

크론의 한계(서버 시간대, 실패 알림, 여러 서버에서 중복 실행)는 [크론 잡](/posts/cron-jobs)에 정리돼 있다. 이런 스크립트가 열 개를 넘고 서로 순서가 생기기 시작하면 오케스트레이터로 옮길 때다.

## Postgres 하나에서 웨어하우스로 넘어가는 신호

작은 팀이 처음부터 레이크, 웨어하우스, Kafka, Spark, Airflow를 다 갖출 필요는 없다. 데이터가 수천만 행 이하이고 원본이 운영 DB 하나라면, 운영 DB의 읽기 복제본이나 리포트용 PostgreSQL 하나에 매일 밤 크론으로 테이블을 옮기는 것으로 충분하다.

넘어갈 때가 됐다는 신호는 이런 것들이다. 리포트 쿼리가 분 단위로 느려진다. 복제본의 긴 쿼리가 복제 지연이나 쿼리 취소를 만든다. 결제사, 광고, 앱 이벤트처럼 원본이 여러 개가 되어 함께 조인해야 한다. 과거 시점의 상태를 물어보는 질문이 늘어난다. 크론 작업이 열 개를 넘어 순서와 실패를 손으로 관리하기 힘들다.

그때 관리형 웨어하우스(BigQuery, Snowflake, Redshift)나 분석 DB(ClickHouse), 작은 규모라면 DuckDB와 Parquet 파일로 옮긴다. 크론이 많아지면 오케스트레이터를 들이고, 이벤트가 초당 수천 건을 넘거나 몇 초 지연이 필요해지면 Kafka를 들인다. 한 번에 하나씩, 지금 아픈 곳부터 바꾼다.

## 기술을 고르는 기준

데이터 도구는 종류가 많고 유행도 빨리 바뀐다. 도구 이름보다 몇 가지 질문으로 고른다.

팀이 운영할 수 있는가. 오픈소스를 직접 띄우면 라이선스 비용은 없지만 업그레이드, 장애 대응, 보안 패치를 팀이 해야 한다. 데이터 엔지니어가 한두 명이면 관리형 서비스가 대개 더 싸다. 비용이 어떻게 늘어나는가. 데이터가 열 배가 되면 비용도 열 배인지, 쿼리를 잘못 짜면 하루에 얼마가 나갈 수 있는지 미리 본다. 빠져나올 수 있는가. 데이터를 Parquet·Iceberg 같은 열린 형식으로 두면 엔진을 바꾸기 쉽다. 특정 서비스 전용 형식에 다 넣으면 나중에 옮기는 비용이 크다. 지금 필요한 지연과 규모에 맞는가. 하루 한 번이면 되는 리포트에 스트리밍 파이프라인을 짓는 것이 가장 흔한 과설계다.

## 단계 밑에 깔린 것들

앞의 책은 다섯 단계 밑에 모든 단계에 걸치는 일들을 따로 꼽는다. 보안(누가 무엇을 읽을 수 있나, 개인정보를 어떻게 가리나), 데이터 관리(데이터 목록과 계보, 품질, 정의 문서), DataOps(파이프라인도 코드처럼 버전 관리하고 테스트하고 배포한다), 오케스트레이션(작업 순서와 재시도, 백필), 그리고 소프트웨어 엔지니어링 그 자체다.

이것들이 단계마다 반복되기 때문에 데이터 엔지니어의 일은 "데이터를 옮기는 스크립트를 짜는 일"보다 넓다. 처음 문의 같은 숫자 불일치를 빨리 설명하려면 계보와 기준 시각이 있어야 하고, 형식 변경으로 조용히 틀리는 일을 막으려면 품질 검사와 계약이 있어야 한다.

## 숫자가 엇갈리면 길을 거꾸로 걷는다

데이터 엔지니어링 수명 주기는 데이터가 생기고, 모이고, 담기고, 다듬어지고, 쓰이는 길이다. 단계마다 시간이 걸리고 모양이 바뀌니, 앱과 리포트의 숫자가 다르면 서빙에서 생성까지 거꾸로 짚으며 어느 단계의 기준 시각과 정의가 달랐는지 찾는다. 작은 팀은 PostgreSQL 하나와 크론으로 시작해도 되고, 리포트가 느려지거나 원본이 늘어나는 신호가 올 때 지금 아픈 단계부터 바꾼다. 다음으로는 수집 단계의 함정을 다룬 [ETL과 ELT](/posts/etl-vs-elt)부터 읽으면 이어진다.

## 면접에서 나올 만한 질문

### 데이터 엔지니어링 수명 주기를 설명해 보라

데이터가 생기고(생성), 원본에서 가져와(수집), 담아 두고(저장), 쓰기 좋은 모양으로 바꾸고(변환), 대시보드·모델·운영 시스템에 내주는(서빙) 흐름이다. 그 밑에 보안, 데이터 관리, DataOps, 오케스트레이션이 모든 단계에 걸쳐 있다. 단계마다 지연과 모양 변화가 생기니, 숫자가 엇갈리면 단계를 거꾸로 짚으며 기준 시각과 정의를 확인한다.

### 운영 DB(OLTP)를 리포트에서 바로 조회하면 안 되는 이유는?

리포트 쿼리는 테이블 전체를 훑는 큰 읽기라 서비스 쿼리와 CPU, 디스크, 메모리 캐시를 다퉈 서비스를 느리게 한다. 운영 DB에는 현재 상태만 있어 과거 시점을 묻는 질문에 답할 수 없고, 다른 원본과 조인할 수 없으며, 리포트용 인덱스를 추가하면 쓰기가 느려진다. 읽기 복제본으로 부하는 덜 수 있지만 행 저장이라 큰 집계는 여전히 느리고, 긴 쿼리가 복제 지연이나 쿼리 취소를 만든다.

### 데이터를 수집할 때 먼저 정해야 하는 것은?

필요한 지연, 데이터 양과 증가 속도, 스키마와 그 변경 절차, 중복과 순서 뒤섞임을 어떻게 처리할지, 개인정보를 옮길지 가릴지다. 이 답에 따라 배치 추출, CDC, 스트리밍 중 방식이 갈린다. 필요한 것보다 짧은 지연을 요구하면 비용과 운영 부담이 크게 는다.

### 모바일 앱 이벤트를 수집할 때 생기는 문제는?

네트워크가 끊기면 앱이 이벤트를 모아 뒀다가 늦게 보내 며칠 늦게 도착하는 이벤트가 생긴다. 기기 시계를 믿기 어렵고, 옛 버전 앱이 옛 형식으로 계속 보낸다. 그래서 기기 시각과 서버 수신 시각, 앱 버전, 이벤트 ID를 함께 남기고, 늦게 온 데이터로 지난 날짜를 다시 계산할 수 있게 만든다.

### 데이터 엔지니어와 데이터 사이언티스트, 분석가는 무엇이 다른가?

데이터 엔지니어는 데이터가 제때 정확히 흐르게 길을 만들고 지킨다. 분석가는 다듬은 데이터로 지표와 대시보드를 만들고 비즈니스 질문에 답한다. 데이터 사이언티스트는 통계와 머신러닝으로 예측하거나 원인을 추정한다. 그 사이에서 SQL로 정제와 지표 정의를 맡는 애널리틱스 엔지니어도 있다.

### 작은 팀이 웨어하우스를 도입해야 하는 신호는?

리포트 쿼리가 분 단위로 느려지거나 복제본의 긴 쿼리가 복제 지연을 만들 때, 결제사·광고·앱 이벤트처럼 원본이 늘어 함께 조인해야 할 때, 과거 시점 질문이 늘 때다. 크론 작업이 많아져 순서와 실패를 손으로 관리하기 힘들면 오케스트레이터도 함께 들인다. 한 번에 다 바꾸지 않고 지금 아픈 단계부터 바꾼다.

### 데이터 도구를 고르는 기준은?

팀이 직접 운영할 수 있는지, 데이터가 늘 때 비용이 어떻게 느는지, 열린 형식으로 두어 나중에 빠져나올 수 있는지, 지금 필요한 지연과 규모에 맞는지를 본다. 인원이 적으면 관리형 서비스가 대개 싸고, 하루 한 번이면 되는 곳에 스트리밍을 짓는 것이 흔한 과설계다.

### 운영 DB에서 리포트 DB로 파이프(|)로 바로 옮기는 스크립트의 위험은?

파이프의 양쪽은 동시에 돌기 때문에, 원본 쪽이 실패해도 받는 쪽은 빈 입력을 정상 입력으로 받아 적재를 끝내고 커밋할 수 있다. 실제로 원본 쿼리가 실패했는데 사본 테이블이 비워진 채로 커밋됐다. 원본을 먼저 파일로 다 받고 성공했을 때만 적재하고, 적재 트랜잭션 안에서 행 수가 갑자기 줄면 예외를 던져 되돌리게 만든다.
