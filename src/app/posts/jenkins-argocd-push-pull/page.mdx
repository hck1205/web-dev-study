<EasyIntro>
  배포에는 두 가지 길이 있다. 밖에서 클러스터로 직접 밀어 넣는 길과, 클러스터 안의 도구가 저장소를 읽어 끌어오는 길이다. 개발 환경은 빠른 게 중요하니 밀어 넣고, 운영 환경은 누가 언제 무엇을 바꿨는지 설명할 수 있어야 하니 저장소를 거쳐 끌어오게 섞어 쓰는 팀이 많다.

  방 하나에 청소 당번이 둘이면 서로의 정리를 망친다. 글 처음에 급히 올린 수정이 3분 만에 사라진 것도, 운영 방에 밀어 넣는 당번과 끌어오는 당번이 동시에 있었기 때문이다. 환경 하나는 도구 하나만 바꾼다는 원칙이 이 구성의 전부다.

  같은 이미지가 개발, 시험, 운영을 차례로 지나가는 건 새로 만드는 게 아니라 다음 환경 목록에 같은 번호를 적어 주는 일이다. 되돌리는 길도 환경마다 달라서, 운영은 저장소의 기록을 되돌려야지 클러스터를 직접 건드리면 안 된다.
</EasyIntro>

운영 장애를 급히 막으려고 누군가 Jenkins의 "deploy-prod" 잡을 눌렀다. 잡은 `helm upgrade`로 고친 이미지를 올렸고 초록색으로 끝났다. 그런데 3분쯤 지나자 운영 Pod가 다시 예전 이미지로 돌아갔다. ArgoCD 화면에는 Application이 잠깐 `OutOfSync`였다가 `Synced`로 돌아온 기록만 남아 있다. 배포가 됐다가 사라진 것이다.

이 팀은 개발·스테이징은 Jenkins가 클러스터에 직접 밀어 넣고(push), 운영은 ArgoCD가 git을 읽어 끌어오는(pull) 구성을 쓰고 있었다. 두 방식을 섞는 건 흔하고 이유도 있다. 다만 어느 환경을 누가 바꿀 수 있는지가 분명하지 않으면 위처럼 두 배포 도구가 서로의 결과를 지운다.

push와 pull이 무엇인지, 클러스터 자격 증명이 어디에 있는지는 [EKS 배포 파이프라인](/posts/k8s-deploy-pipeline-eks)의 "밀어 넣는 배포와 끌어오는 배포"에서 다뤘다. ArgoCD의 동기화·selfHeal은 [ArgoCD 기본](/posts/argocd-basics), 레지스트리를 보고 git을 고치는 봇은 [ArgoCD와 Flux 비교](/posts/gitops-argocd-vs-flux)에 있다. 이 글은 그 위에서 다른 질문에 답한다. 두 방식을 환경별로 나눠 쓸 때 경계를 어디에 긋고, 이미지 태그는 누가 어떤 순서로 옮기고, 사고가 나면 환경마다 어떻게 되돌리는가. Jenkins 에이전트를 Kubernetes 위에서 돌리는 쪽은 [Kubernetes 위의 Jenkins](/posts/jenkins-on-kubernetes)에서 따로 본다.

이 글의 git 출력은 로컬에 만든 배포 저장소와 스크립트로 직접 돌린 결과다(git 2.43, 저장소 경로만 `/srv/git/...`으로 바꿔 적었다). Jenkins 콘솔과 ArgoCD, kubectl 출력은 예시다.

## 개발은 빨라야 하고 운영은 설명할 수 있어야 한다

환경마다 바라는 게 다르다. 개발 클러스터는 하루에 수십 번 바뀐다. 브랜치마다 미리보기 환경을 띄우기도 하고, 누군가 디버깅하려고 손으로 설정을 바꿔 놓아도 큰일이 아니다. 여기서 중요한 건 커밋에서 화면까지 걸리는 시간이다. 운영은 반대다. 바뀌는 횟수는 적지만, 바뀔 때마다 "누가, 언제, 무엇을, 누구의 승인으로" 바꿨는지 설명할 수 있어야 하고, 손으로 고친 흔적(drift)은 바로 드러나야 한다.

push 방식은 첫 번째에 맞는다. 파이프라인이 끝나는 순간 배포도 끝나고, 실패하면 그 잡이 빨갛게 끝난다. pull 방식은 두 번째에 맞는다. 운영 클러스터의 원본은 git이고, git 기록이 곧 배포 기록이며, CI는 운영 클러스터에 접속할 권한이 없다.

그래서 많이 쓰는 경계는 이렇다. 개발과 스테이징은 Jenkins가 `helm upgrade`나 `kubectl apply`로 직접 배포하고, 운영은 Jenkins가 배포 저장소에 태그를 올리는 커밋(또는 PR)만 만든다. 스테이징을 pull로 두는 팀도 있다. 운영과 같은 길로 배포해 봐야 그 길이 검증되기 때문이다. 어느 쪽이든 원칙은 하나다. 한 환경은 한 도구만 바꾼다.

## Jenkinsfile은 환경마다 다른 일을 한다

파이프라인 하나가 세 환경을 다 다루지만, 환경마다 하는 일의 종류가 다르다. dev와 staging에서는 배포하고, prod에서는 배포 요청을 만든다. 이 차이가 Jenkinsfile에도 그대로 보여야 한다.

```groovy
pipeline {
  agent { label 'docker' }
  options { disableConcurrentBuilds(abortPrevious: true) }   // 같은 브랜치 빌드는 하나만
  environment { IMAGE = "registry.example.com/shop/shop-api" }
  stages {
    stage('Build') {
      steps {
        script { env.TAG = env.GIT_COMMIT.take(7) }
        sh 'docker build -t "$IMAGE:$TAG" . && docker push "$IMAGE:$TAG"'
      }
    }
    stage('Deploy dev') {
      when { branch 'main' }
      steps {
        withCredentials([file(credentialsId: 'kubeconfig-dev', variable: 'KUBECONFIG')]) {
          sh 'helm upgrade --install shop-api ./chart -n shop-dev --set image.tag="$TAG" --atomic --timeout 5m'
        }
      }
    }
    stage('Deploy staging') {
      when { branch 'main' }
      steps {
        withCredentials([file(credentialsId: 'kubeconfig-staging', variable: 'KUBECONFIG')]) {
          sh 'helm upgrade --install shop-api ./chart -n shop-staging --set image.tag="$TAG" --atomic --timeout 5m'
        }
        sh './ci/smoke-test.sh https://staging.example.com'
      }
    }
    stage('Open prod PR') {
      when { branch 'main' }
      steps {
        withCredentials([string(credentialsId: 'deploy-repo-token', variable: 'GH_TOKEN')]) {
          sh './ci/open-promotion-pr.sh prod shop-api "$TAG"'
        }
      }
    }
  }
}
```

`--atomic`은 업그레이드가 제한 시간 안에 성공하지 못하면 이전 릴리스로 되돌리고 잡을 실패로 끝낸다. push 방식에서는 이게 배포 성공의 기준이 된다. Helm의 업그레이드·롤백 동작은 [Helm 업그레이드와 롤백](/posts/helm-release-lifecycle)에 자세히 있다. `disableConcurrentBuilds(abortPrevious: true)`는 main에 커밋이 연달아 들어왔을 때 앞 빌드를 끊고 최신 것만 돌린다. 앞 빌드가 늦게 끝나서 더 오래된 이미지로 dev를 덮어쓰는 일을 막는다.

dev와 staging이 같은 이미지 태그를 받는다는 것도 확인할 점이다. staging 단계에서 `docker build`를 다시 하면, 같은 커밋이라도 그사이 베이스 이미지나 의존성이 바뀌어 다른 결과물이 나올 수 있다. 한 번 빌드한 결과물을 승격하는 이유는 [CI/CD 기본](/posts/ci-cd-basics)에 정리돼 있다.

## 태그 한 줄을 고치는 단계가 깨지는 곳

pull 방식에서 Jenkins가 하는 마지막 일은 배포 저장소의 파일 한 줄을 바꾸는 것이다. Kustomize를 쓴다면 이 줄이다(파일 구조는 [Kustomize 기본](/posts/kustomize-basics)).

```yaml
# envs/prod/kustomization.yaml
images:
  - name: shop-api
    newName: registry.example.com/shop/shop-api
    newTag: 1a2b3c4
  - name: order-api
    newName: registry.example.com/shop/order-api
    newTag: 9f8e7d6
```

단순해 보이지만 서비스가 여러 개면 문제가 생긴다. 배포 저장소는 하나인데 서비스마다 Jenkins 잡이 따로 돌고, 거의 같은 시각에 같은 브랜치로 푸시한다. 아래 스크립트는 저장소를 받아서 해당 이미지의 `newTag` 줄만 바꾸고, 푸시가 거절되면 rebase한 뒤 다시 시도한다.

```bash
#!/usr/bin/env bash
# 사용법: REPO=<git url> bump-tag.sh <env> <image> <tag>
set -euo pipefail
ENV=$1 IMAGE=$2 TAG=$3
WORK=$(mktemp -d -p "$PWD" work.XXXX)
git clone -q "$REPO" "$WORK"
cd "$WORK"
FILE="envs/$ENV/kustomization.yaml"
# 이 이미지 블록의 newTag 한 줄만 바꾼다
awk -v img="$IMAGE" -v tag="$TAG" '
  $0 ~ "- name: "img"$" {hit=1}
  hit && /newTag:/ {sub(/newTag: .*/, "newTag: " tag); hit=0}
  {print}' "$FILE" > "$FILE.tmp" && mv "$FILE.tmp" "$FILE"
if git diff --quiet; then echo "no change: $ENV $IMAGE already $TAG"; exit 0; fi
git commit -qam "deploy($ENV): $IMAGE $TAG"
for i in 1 2 3; do
  if git push -q origin HEAD:main 2>push.err; then
    echo "pushed on try $i: $(git log -1 --format='%h %s')"; exit 0
  fi
  echo "push rejected on try $i:"; sed 's/^/  /' push.err
  git pull -q --rebase origin main
done
echo "giving up after 3 tries"; exit 1
```

두 잡을 거의 동시에 돌렸다. shop-api 잡이 커밋을 만든 뒤 푸시하기 전에 order-api 잡이 먼저 푸시하도록 2초 기다리게 했다.

```bash
# shop-api 잡은 커밋 후 2초 쉬었다가 푸시, order-api 잡은 바로 푸시
(PAUSE=2 ./bump-tag.sh dev shop-api 5d41402 > jobA.out 2>&1 &)
./bump-tag.sh dev order-api c4ca423 > jobB.out 2>&1
```

  To /srv/git/shop-deploy.git

  hint: the same ref. If you want to integrate the remote changes, use

첫 시도는 `(fetch first)`로 거절됐다. 원격 main이 그사이 order-api 커밋만큼 앞서 나갔기 때문이다. 두 잡은 같은 파일의 다른 줄을 고쳤으니 rebase가 충돌 없이 끝나고, 두 번째 시도에서 들어갔다. 재시도가 없는 스크립트였다면 shop-api 잡은 여기서 실패했을 것이다. 더 나쁜 경우는 누군가 이 에러를 없애려고 `git push --force`를 넣는 것이다. 그러면 order-api의 커밋이 사라지고, ArgoCD는 order-api를 예전 태그로 되돌린다.

같은 스크립트를 같은 값으로 한 번 더 돌리면 바꿀 게 없으니 커밋을 만들지 않는다. Jenkins 잡을 재시도해도 빈 커밋이 쌓이지 않는다.

```text
pushed on try 1: aeab899 deploy(staging): shop-api 5d41402
no change: staging shop-api already 5d41402
```

태그 줄을 고치는 부분을 직접 짜 보자. `sed -i 's/newTag: .*/newTag: X/'`처럼 파일 전체에서 바꾸면 다른 이미지의 태그까지 바뀐다. 이름이 정확히 같은 블록만 고쳐야 하고, 그런 블록이 없으면 `null`을 돌려 잡을 실패시키는 편이 낫다. 오타 난 이미지 이름이 조용히 무시되면 배포가 됐다고 믿게 된다.

## 운영으로 올리는 PR

운영은 직접 푸시하지 않고 PR로 올린다. staging에 실제로 떠 있는 태그를 읽어 prod에 그대로 옮기는 PR이다. 승격(promotion)은 새로 빌드하는 게 아니라 같은 결과물을 다음 환경의 목록에 적는 일이다. diff를 보면 그게 그대로 드러난다.

```bash
# staging의 shop-api 태그를 읽어 prod에 옮기는 브랜치를 만든다
git switch -c promote/shop-api-5d41402
TAG=$(awk '/- name: shop-api$/{h=1} h&&/newTag:/{print $2; exit}' envs/staging/kustomization.yaml)
echo "staging tag = $TAG"
awk -v tag="$TAG" '/- name: shop-api$/{h=1} h&&/newTag:/{sub(/newTag: .*/,"newTag: " tag);h=0} {print}' \
  envs/prod/kustomization.yaml > t && mv t envs/prod/kustomization.yaml
git commit -qam "promote(prod): shop-api $TAG (from staging)"
git diff main
```

머지까지 거친 뒤의 배포 저장소 기록이다.

## 태그 대신 digest로 승격하기

태그는 바뀔 수 있다. `5d41402`라는 태그에 누군가 다른 이미지를 다시 푸시하면 같은 이름이 다른 내용을 가리킨다. staging에서 검증한 것과 prod에 나간 것이 같다고 말하려면 이미지 digest로 적는 편이 확실하다. Kustomize의 `images`에는 `newTag` 대신 `digest`를 적을 수 있다. 레지스트리 쪽에서 태그 덮어쓰기를 막는 설정(ECR의 tag immutability 같은 것)도 함께 켠다.

이미지 참조 한 줄이 어떤 조각으로 되어 있는지 나눠 봤다. 각 조각을 누르면 설명이 나온다.

## 자격 증명이 닿는 범위를 그려 본다

이 구성을 고르는 큰 이유는 Jenkins가 뚫렸을 때 피해가 어디까지 가느냐다. Jenkins는 플러그인이 많고 사내 여러 사람이 잡을 만든다. 컨트롤러가 털렸다고 가정하고 공격자가 무엇을 할 수 있는지 하나씩 적어 본다.

- 레지스트리 push 권한으로 악성 이미지를 올릴 수 있다. 그래서 저장소 단위로 권한을 좁히고, 운영은 digest와 서명 검증으로 받는다.
- dev와 staging kubeconfig로 그 클러스터를 마음대로 할 수 있다. 이 kubeconfig의 권한은 해당 네임스페이스의 배포에 필요한 만큼만 준다. `cluster-admin`을 주면 클러스터 전체가 넘어간다.
- 배포 저장소 쓰기 토큰으로 커밋을 만들 수 있다. 여기서 운영 경로까지 직접 푸시할 수 있다면, 공격자는 PR 없이 운영을 바꾼다.

세 번째가 가장 놓치기 쉽다. GitHub의 브랜치 보호는 브랜치 단위로 걸리므로, "dev 경로는 봇이 바로 푸시하고 prod 경로는 PR만"을 한 브랜치 안에서 나누기 어렵다. 그래서 흔히 쓰는 방법은 셋이다. prod용 배포 저장소를 따로 두고 Jenkins 토큰에는 그 저장소의 PR 생성 권한만 주거나, prod Application이 보호된 별도 브랜치를 보게 하거나, 저장소 규칙(GitHub ruleset의 경로 제한처럼 플랜에 따라 쓸 수 있는 기능)으로 envs/prod 아래 변경을 막는 것이다. 어느 쪽이든 확인하는 질문은 같다. Jenkins가 가진 토큰만으로 운영을 바꿀 수 있는가.

운영 클러스터 쪽에서는 ArgoCD의 AppProject로 그 Application이 배포할 수 있는 저장소와 네임스페이스를 묶는다([ArgoCD 기본](/posts/argocd-basics)의 AppProject 부분). 배포 저장소가 바뀌어도 허락된 범위 밖의 리소스는 만들지 못한다.

<Callout kind="warning" title="Jenkins에 운영 kubeconfig를 '비상용'으로 남기지 않는다">
처음 장면의 "deploy-prod" 잡처럼 비상용 경로를 남겨 두면 그 자격 증명은 평소에도 Jenkins 안에 있다. 공격자는 비상 상황을 기다리지 않는다. 장애 때 빠르게 되돌릴 길이 필요하면 운영 담당자가 쓰는 break-glass 계정을 따로 두고, 쓰면 알림이 가고 쓴 뒤에 git을 맞추는 절차로 만든다.
</Callout>

## 되돌리는 길이 환경마다 다르다

배포 방식이 다르면 되돌리는 방법도 다르다. 장애 중에 이걸 헷갈리면 되돌렸다고 믿은 사이에 다시 나쁜 버전이 돌아온다.

dev와 staging은 push로 올렸으니 push로 되돌린다. 이전 릴리스로 `helm rollback shop-api -n shop-staging`을 하거나, 이전 커밋의 Jenkins 빌드를 다시 돌려 그 태그를 다시 올린다. 여기에는 git에 기록할 원본이 따로 없으니 클러스터 상태가 곧 정답이다.

prod는 git이 원본이라 git을 되돌린다. 승격을 머지 커밋으로 했다면 그 머지를 revert한다. 머지 커밋은 부모가 둘이라 어느 쪽 기준으로 되돌릴지 정해 줘야 한다.

```bash
# 머지 커밋을 그냥 revert하면 거절된다
git revert --no-edit 4b418c2
# -m 1: 첫 번째 부모(머지 전 main) 기준으로 되돌린다
git revert --no-edit -m 1 4b418c2
grep newTag envs/prod/kustomization.yaml
```

```text
error: commit 4b418c2e1cf714d1664e29f371c061827d1320cc is a merge but no -m option was given.
fatal: revert failed
[main 850e937] Revert "Merge PR #87: promote shop-api to prod"
 Date: Thu Oct 22 03:19:07 2026 +0000
 1 file changed, 1 insertion(+), 1 deletion(-)
    newTag: 1a2b3c4
    newTag: 9f8e7d6
```

shop-api의 prod 태그가 `1a2b3c4`로 돌아왔다. 이 커밋을 푸시하면 ArgoCD가 예전 이미지로 맞춘다. 장애 중 급하면 PR 리뷰를 생략할 수 있게 revert 전용 규칙을 미리 정해 두는 팀도 있다. 정해 두지 않으면 리뷰어를 찾는 사이에 장애가 길어진다.

prod에서 `kubectl rollout undo`나 `helm rollback`을 치면 안 되는 이유는 처음 장면과 같다. selfHeal이 켜져 있으면 몇 분 안에 git에 적힌 나쁜 태그로 다시 맞춘다. 꺼져 있으면 클러스터와 git이 다른 채로 남는다. 자동 동기화를 켠 Application에서는 ArgoCD 화면의 History and Rollback도 쓸 수 없다. 데이터베이스 마이그레이션처럼 되돌릴 수 없는 변경이 섞였을 때는 이미지만 되돌려서는 안 되는데, 그 판단은 [롤백 전략](/posts/rollback-strategy)에서 다뤘다.

## 레지스트리를 보고 태그를 고치는 봇

Jenkins가 태그 커밋을 만드는 대신, 클러스터 안의 봇이 레지스트리를 보고 새 태그를 찾아 git에 쓰게 할 수도 있다. ArgoCD 쪽 도구는 별도 프로젝트인 Argo CD Image Updater다. 이미지마다 태그를 고르는 전략(semver 범위, 가장 최근에 빌드된 것, digest 추적 등)을 정하고, 찾은 태그를 어디에 쓸지(write-back 방식)를 정한다.

write-back 방식이 중요하다. 기본값은 ArgoCD API로 Application의 파라미터를 바꾸는 방식이라 git에 아무것도 남지 않는다. git이 원본이라는 약속이 깨지는 셈이다. git 방식으로 바꾸면 봇이 배포 저장소에 커밋한다. 설정 방법은 버전에 따라 다르다. 0.x 버전은 Application의 애노테이션으로 정했고, 이후 버전에서 설정 방식이 바뀌고 있으니 쓰는 버전의 문서를 확인한다. Flux의 같은 기능과 태그 고르는 규칙은 [ArgoCD와 Flux 비교](/posts/gitops-argocd-vs-flux)에서 직접 짜 봤다.

이 봇은 dev처럼 "새 이미지가 나오면 바로 따라가면 되는" 환경에 맞는다. 운영에 쓰면 리뷰 없이 이미지가 바뀌고, 봇이 main에 푸시하려면 브랜치 보호에 예외를 줘야 한다. 운영은 앞에서 본 승격 PR이 낫다. 봇과 Jenkins가 같은 환경의 같은 줄을 동시에 고치면 앞에서 본 푸시 경쟁이 사람 몰래 일어나니, 환경마다 태그를 고치는 주체를 하나로 정한다.

## 섞어 쓸 때 보이는 증상과 확인 순서

배포가 됐다가 사라진다. 처음 장면이다. ArgoCD가 관리하는 리소스를 다른 도구가 바꿨다. Application의 이벤트와 History에서 언제 OutOfSync가 됐고 언제 selfHeal이 돌았는지 본다.

```bash
# 동기화 기록과 지금 상태를 본다
argocd app history shop-api-prod
argocd app get shop-api-prod --show-operation
```

history에서 볼 곳은 REVISION 칸이다. git 커밋은 그대로인데 같은 리비전으로 동기화 기록이 하나 더 생겼다면, git이 아니라 클러스터 쪽이 바뀌었고 selfHeal이 되돌린 것이다. 그 시각에 돈 Jenkins 잡이나 kubectl 감사 로그에서 누가 바꿨는지 찾는다.

Jenkins는 초록인데 운영에 안 나갔다. pull 방식에서는 정상이다. Jenkins가 한 일은 PR이나 커밋까지다. 머지가 됐는지, ArgoCD가 그 커밋을 읽었는지(REVISION), 동기화가 실패했는지(Degraded) 순서로 본다. 배포까지 기다려야 하는 파이프라인이라면 커밋 뒤에 `argocd app wait shop-api-staging --health --timeout 600` 같은 단계를 두는데, 이때 Jenkins에 주는 ArgoCD 토큰은 읽기 전용 역할로 만든다.

dev에서 두 도구가 싸운다. dev에도 ArgoCD Application이 있고 자동 동기화가 켜져 있는데 Jenkins가 helm upgrade까지 한다. 몇 분마다 이미지가 왔다 갔다 한다. 환경 하나에 배포 도구 하나라는 원칙으로 돌아가서, dev의 Application을 지우거나 Jenkins의 dev 배포 단계를 지운다.

배포 저장소 잡이 끝없이 돈다. 봇 커밋이 웹훅을 다시 부르고 있다. 커밋 작성자가 봇인 커밋을 건너뛰게 한다.

## 경계를 다시 그은 뒤

처음 장면의 팀은 Jenkins에서 "deploy-prod" 잡과 운영 kubeconfig를 지웠다. 장애 때 고친 이미지를 내보내는 길은 핫픽스 커밋 → 승격 PR → 머지로 하나만 남겼고, 그 길이 느리지 않게 revert와 핫픽스 PR은 승인 한 명으로 머지할 수 있게 규칙을 바꿨다. push와 pull을 섞는 구성은 각 환경을 바꾸는 주체가 하나일 때만 장점이 남는다. 개발의 속도는 push로, 운영의 기록과 최소 권한은 pull로 얻고, 그 사이를 같은 이미지 태그(가능하면 digest)를 옮기는 승격 PR이 잇는다.

## 면접에서 나올 만한 질문

### 개발·스테이징은 push, 운영은 pull로 나누는 이유는 무엇인가요?

환경마다 우선순위가 달라서다. 개발은 커밋에서 배포까지의 속도와 즉시 실패를 아는 게 중요해서 Jenkins가 바로 배포하는 push가 맞다. 운영은 누가 언제 무엇을 바꿨는지 기록이 남아야 하고, CI가 운영 클러스터 자격 증명을 갖지 않아야 하고, 손으로 고친 drift가 드러나야 해서 git을 원본으로 두는 pull이 맞다.

### pull 방식에서 Jenkins는 배포 단계에서 무엇을 하나요?

이미지를 한 번 빌드해 레지스트리에 올리고, 배포 저장소의 그 환경 파일에서 이미지 태그 한 줄을 바꾸는 커밋이나 PR을 만든다. 클러스터에는 접속하지 않는다. 그래서 Jenkins 잡이 성공해도 배포는 끝나지 않았고, 결과는 ArgoCD의 Health와 알림으로 확인한다.

### 여러 서비스의 잡이 같은 배포 저장소에 동시에 태그를 올리면 어떤 문제가 생기나요?

나중에 푸시한 잡이 fast-forward가 아니라서 거절된다. 스크립트에 `pull --rebase` 후 재시도를 넣으면 서로 다른 줄을 고친 경우 충돌 없이 들어간다. 거절을 없애려고 `--force`를 쓰면 다른 서비스의 커밋이 지워지고 ArgoCD가 그 서비스를 예전 태그로 되돌린다.

### 승격할 때 태그 대신 digest를 쓰는 이유는요?

태그는 덮어쓸 수 있어서 같은 이름이 다른 이미지를 가리킬 수 있다. digest는 이미지 내용의 해시라서 staging에서 검증한 것과 운영에 나간 것이 같다고 보장한다. 사람이 읽기 어려우니 파일에는 digest, 커밋 메시지와 PR 제목에는 태그를 적고, 레지스트리의 태그 불변 설정도 함께 켠다.

### 운영 장애 중에 kubectl rollout undo를 하면 왜 안 되나요?

ArgoCD가 관리하는 리소스라 git이 원본이기 때문이다. selfHeal이 켜져 있으면 몇 분 안에 git에 적힌 나쁜 태그로 다시 맞추고, 꺼져 있으면 클러스터와 git이 어긋난 채 남는다. 운영은 승격 커밋을 git revert(머지 커밋이면 `-m 1`)해서 되돌린다.

### Jenkins가 탈취됐다고 가정하면 이 구성에서 피해 범위는 어디까지인가요?

레지스트리 push 권한, dev·staging 클러스터 권한, 배포 저장소 쓰기 권한까지다. 운영 클러스터 자격 증명은 없으니 운영을 바꾸려면 배포 저장소를 거쳐야 한다. 그래서 Jenkins 토큰으로 운영 경로를 직접 푸시할 수 없게 저장소를 나누거나 보호 규칙을 걸고, dev kubeconfig도 네임스페이스 범위로 좁힌다.

### Argo CD Image Updater를 운영에 바로 쓰지 않는 이유는요?

새 이미지가 리뷰 없이 운영에 나가고, 봇이 main에 푸시하려면 브랜치 보호에 예외를 줘야 하기 때문이다. 기본 write-back이 ArgoCD API 방식이면 git에 기록조차 남지 않는다. 그래서 dev에 쓰고, 운영은 사람이 머지하는 승격 PR로 둔다.

### 같은 환경에 ArgoCD 자동 동기화와 Jenkins helm upgrade가 함께 걸려 있으면 어떻게 되나요?

두 도구가 서로의 결과를 덮어쓴다. Jenkins가 새 이미지를 올리면 ArgoCD가 git에 적힌 이미지로 되돌리고, 다음 Jenkins 실행 때 다시 바뀐다. 이미지가 몇 분마다 바뀌는 증상이 보이면 그 환경을 바꾸는 주체를 하나로 정리한다.
