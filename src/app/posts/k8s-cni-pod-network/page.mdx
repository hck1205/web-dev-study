  이걸 알면 기계를 넘을 때만 안 되는 장애에서 경로, 봉투용 포트, 패킷 크기 한도, 끼어든 주소 바꿈 네 가지 중 어디를 볼지 바로 나온다.

노드를 하나 새로 붙였다. `kubectl get nodes`에서는 Ready인데, 그 노드에 뜬 Pod만 다른 노드의 Pod와 통신이 안 된다. 같은 노드 안의 Pod끼리는 잘 된다. 며칠 전에는 반대로, 노드를 초기화하고 다시 붙였더니 Pod가 `ContainerCreating`에서 멈췄고 이벤트에 `"cni0" already has an IP address different from 10.244.1.1/24`가 찍혀 있었다.

둘 다 CNI 플러그인이 노드에서 하는 일을 알면 어디를 볼지 바로 나온다. 쿠버네티스 자체는 Pod에 IP를 주지도, 노드 사이에 길을 놓지도 않는다. 그 일은 노드마다 설치된 CNI 플러그인 실행 파일이 한다. 이 글은 kubelet이 플러그인을 어떻게 부르고 플러그인이 무엇을 받아 무엇을 만드는지 실제로 실행해 보고, 노드 사이를 경로로 잇는 방식과 VXLAN으로 잇는 방식을 손으로 만들어 비교한다.

Pod 안의 컨테이너들이 네트워크 네임스페이스 하나를 나눠 쓰는 구조는 [Pod 글](/posts/k8s-pod-basics)에, 컨테이너 하나를 veth와 브리지로 잇는 기본기는 [Docker 네트워크 드라이버 글](/posts/docker-network-drivers)에, VXLAN 캡슐화와 VTEP은 [SDN과 VXLAN 오버레이 글](/posts/sdn-vxlan-overlay)에 있다. 여기서는 그 조각들을 쿠버네티스가 어떻게 조립하는지를 본다.

실습은 Ubuntu 24.04 기준으로, 네트워크 네임스페이스 두 개를 노드로, 다섯 개를 Pod로 썼다. CNI 플러그인은 `go install`로 받은 공식 참조 구현(containernetworking/plugins v1.6.2의 `bridge`, `host-local`)을 직접 실행했고, 노드의 Pod 대역 할당은 kwok로 띄운 실제 controller-manager(v1.30.4)에서 봤다. kubelet 이벤트처럼 실습에서 재현할 수 없었던 출력은 예시로 표시했다.

## 쿠버네티스가 네트워크에 요구하는 세 가지

쿠버네티스 네트워크 모델은 요구 사항만 적어 두고 구현은 플러그인에 맡긴다. 요구는 세 줄이다.

- Pod마다 클러스터 전체에서 겹치지 않는 IP가 하나씩 있다.
- 모든 Pod는 NAT 없이 다른 모든 Pod와 통신한다. 받는 쪽이 보는 출발지가 보낸 Pod의 IP 그대로다.
- 노드의 에이전트(kubelet 등)는 그 노드의 모든 Pod에 닿는다.

Docker의 기본 bridge와 비교하면 이유가 보인다. Docker는 호스트마다 같은 `172.17.0.0/16`을 쓰고 바깥과는 `-p` 포트 게시와 NAT로 통신한다. 컨테이너가 수천 개로 늘고 여러 호스트에 흩어지면 포트 번호를 누가 나눠 가질지, 상대의 진짜 주소가 무엇인지가 전부 문제가 된다. 쿠버네티스는 Pod를 "IP를 가진 작은 VM"처럼 다루기로 했다. 그러면 앱은 포트 충돌 걱정 없이 늘 같은 포트로 뜨고, 서비스 발견과 방화벽 규칙은 IP 기준으로 단순해진다. 그 대가로 노드마다 겹치지 않는 Pod 대역을 나눠 주고 노드 사이에 그 대역으로 가는 길을 놓아야 한다. 이게 CNI 플러그인의 일이다.

### 참조 플러그인을 직접 실행한다

containerd가 하는 일을 손으로 해 보자. 노드 1의 네임스페이스 안에서 설정 JSON을 표준 입력으로 주고 `bridge`를 실행했다.

```bash
# 공식 참조 플러그인을 받는다 (실제 노드에는 /opt/cni/bin에 패키지로 깔려 있다)
GOBIN=$HOME/cni-bin go install github.com/containernetworking/plugins/plugins/main/bridge@v1.6.2
GOBIN=$HOME/cni-bin go install github.com/containernetworking/plugins/plugins/ipam/host-local@v1.6.2

# Pod 대신 쓸 빈 네임스페이스
sudo ip netns add n4cp1

# containerd 대신 직접 부른다: 설정은 표준 입력, 대상은 환경 변수
# (실습에서는 노드 역할을 하는 네임스페이스 n4cn1 안에서 실행했다)
sudo ip netns exec n4cn1 env CNI_COMMAND=ADD CNI_CONTAINERID=3f9a1c2b7d4e \
  CNI_NETNS=/var/run/netns/n4cp1 CNI_IFNAME=eth0 CNI_PATH=$HOME/cni-bin \
  $HOME/cni-bin/bridge < net-node1.json
```

넘긴 설정은 이렇다. `dataDir`은 실습에서 작업 디렉터리 아래로 바꿨고, 생략하면 `/var/lib/cni/networks`다. 실제 노드라면 `/etc/cni/net.d/10-mynet.conflist`의 `plugins` 배열 한 칸에 해당한다(런타임이 conflist의 `name`과 `cniVersion`을 각 칸에 붙여서 넘긴다).

```text
{
  "type": "bridge",
  "bridge": "cni0",
  "isGateway": true,
  "ipMasq": true,
  "hairpinMode": true,
  "mtu": 1500,
  "ipam": {
    "type": "host-local",
    "ranges": [[{ "subnet": "10.244.1.0/24" }]],
    "routes": [{ "dst": "0.0.0.0/0" }],
    "dataDir": "…/cni-data/node1"
  },
  "cniVersion": "1.0.0",
  "name": "k8s-pod-network"
}
```

플러그인이 표준 출력으로 돌려준 결과다.

```text
{
    "cniVersion": "1.0.0",
    "interfaces": [
        {
            "mac": "16:b6:ce:85:dd:b0",
            "name": "cni0"
        },
        {
            "mac": "5a:5c:5f:4a:85:ad",
            "name": "vethebef0116"
        },
        {
            "mac": "12:ee:ac:67:32:0e",
            "name": "eth0",
            "sandbox": "/var/run/netns/n4cp1"
        }
    ],
    "ips": [
        {
            "address": "10.244.1.2/24",
            "gateway": "10.244.1.1",
            "interface": 2
        }
    ],
    "routes": [
        {
            "dst": "0.0.0.0/0"
```

`interfaces`에 세 개가 있다. 노드의 브리지 `cni0`(없어서 새로 만들었다), 노드 쪽 veth 끝, 그리고 `sandbox` 경로가 붙은 Pod 안의 `eth0`. `ips`의 `"interface": 2`는 이 주소가 세 번째 인터페이스(`eth0`)에 붙었다는 뜻이다. `isGateway: true`라서 브리지에 `10.244.1.1`이 붙고 Pod의 게이트웨이가 됐다. 런타임은 이 JSON에서 IP를 꺼내 kubelet에 넘긴다. Pod 안을 보면 결과 그대로다.

```bash
# Pod 네임스페이스 안
sudo ip -n n4cp1 addr show eth0
sudo ip -n n4cp1 route
```

```text

    link/ether 12:ee:ac:67:32:0e brd ff:ff:ff:ff:ff:ff link-netns n4cn1

```

### IP는 파일 하나로 기억된다

같은 노드에 Pod를 하나 더 붙인 뒤 host-local의 데이터 디렉터리를 봤다.

```bash
# host-local이 쓰는 할당 기록 (기본 경로는 /var/lib/cni/networks/<네트워크 이름>, 실습은 dataDir 아래)
ls -la cni-data/node1/k8s-pod-network/
for f in cni-data/node1/k8s-pod-network/*; do echo "$f: $(cat $f | tr '\n' ' ')"; done
```

```text
total 20
drwxr-xr-x 2 root root 4096 Oct 20 14:14 .
drwxr-xr-x 3 root root 4096 Oct 20 14:14 ..
-rw------- 1 root root   18 Oct 20 14:14 10.244.1.2
-rw------- 1 root root   18 Oct 20 14:14 10.244.1.3
-rw------- 1 root root   10 Oct 20 14:14 last_reserved_ip.0
-rwxr-x--- 1 root root    0 Oct 20 14:14 lock
cni-data/node1/k8s-pod-network/10.244.1.2: 3f9a1c2b7d4e eth0
cni-data/node1/k8s-pod-network/10.244.1.3: 8b2e6f1a9c3d eth0
```

IP 이름의 파일에 컨테이너 ID와 인터페이스 이름이 적혀 있다. 이게 전부다. DEL을 부르면 파일이 지워진다. 그래서 런타임이 DEL을 못 부르고 죽거나 노드가 갑자기 꺼지면 파일이 남고, 그 IP는 계속 "사용 중"이 된다. 대역이 작은 노드에서 이런 찌꺼기가 쌓이면 새 Pod가 이렇게 실패한다. `/30` 대역으로 줄여 재현했다.

```text
{'code': 999, 'msg': 'failed to allocate for range 0: no IP addresses available in range set: 10.244.9.1-10.244.9.2'}
```

kubelet 이벤트에서는 런타임 메시지에 감싸져 이런 모양으로 보인다(예시).

```text
Warning  FailedCreatePodSandBox  8s  kubelet  Failed to create pod sandbox: rpc error: code = Unknown desc = failed to setup network for sandbox "a41f0c…": plugin type="bridge" name="k8s-pod-network" failed (add): failed to allocate for range 0: no IP addresses available in range set: 10.244.1.1-10.244.1.254
```

`plugin type="…" failed (add):` 뒤가 플러그인이 돌려준 `msg` 그대로다. CNI 문제를 볼 때는 이 부분부터 읽는다. 처음 장면의 `"cni0" already has an IP address different from …`도 같은 자리에 찍히는 bridge 플러그인의 메시지다. 실습에서 같은 노드에 다른 대역 설정으로 ADD를 부르니 똑같이 나왔다.

```text
{
    "code": 999,
    "msg": "failed to set bridge addr: \"cni0\" already has an IP address different from 10.244.9.1/30"
}
```

`kubeadm reset` 후 다시 조인하면서 노드의 Pod 대역이 바뀌었는데, 예전 대역 주소를 단 `cni0`가 남아 있을 때 난다. 노드에서 `sudo ip link delete cni0`(Flannel이면 `flannel.1`도)로 지우고 kubelet과 CNI Pod를 다시 띄우면 새 대역으로 다시 만들어진다. 지우는 순간 그 노드의 Pod 통신이 끊기니 노드를 drain한 뒤에 한다.

플러그인 실행 파일 자체가 없으면 이렇다.

```text
{
    "code": 999,
    "msg": "failed to find plugin \"host-local\" in path [/opt/cni/bin]"
}
```

CNI DaemonSet이 아직 안 떠서 `/etc/cni/net.d`가 비어 있으면, 노드가 Pod를 받기 전 단계에서 `NotReady`가 되고 이유에 `container runtime network not ready: NetworkReady=false reason:NetworkPluginNotReady message:Network plugin returns error: cni plugin not initialized`(예시)가 찍힌다. 클러스터를 막 만든 직후 모든 노드가 NotReady라면 대개 이것이다.

## 노드마다 Pod 대역을 나눠 준다

Pod IP가 클러스터 전체에서 겹치지 않으려면 노드마다 다른 대역을 써야 한다. 흔한 방법은 controller-manager가 클러스터 대역(`--cluster-cidr=10.244.0.0/16`)을 노드마다 /24로 잘라 `node.spec.podCIDR`에 적어 주는 것이다(`--allocate-node-cidrs=true`, `--node-cidr-mask-size=24`). 실습 클러스터에 대역이 비어 있는 노드 둘을 새로 붙였다.

```bash
# 새로 붙인 노드가 받은 Pod 대역
kubectl get nodes node-3 node-4 -o custom-columns=NAME:.metadata.name,PODCIDR:.spec.podCIDR

# controller-manager 로그의 할당 기록
kubectl -n kube-system logs kube-controller-manager-<노드> | grep 'Set node PodCIDR'
```

```text
NAME     PODCIDR
node-3   10.244.0.0/24
node-4   10.244.3.0/24
I1020 14:13:59.437625   21507 range_allocator.go:381] "Set node PodCIDR" logger="node-ipam-controller" node="node-3" podCIDRs=["10.244.0.0/24"]
I1020 14:14:13.120658   21507 range_allocator.go:381] "Set node PodCIDR" logger="node-ipam-controller" node="node-4" podCIDRs=["10.244.3.0/24"]
```

1번과 2번은 이미 쓰이고 있어서 node-3은 남은 첫 조각 `10.244.0.0/24`, node-4는 그다음 `10.244.3.0/24`를 받았다. /16을 /24로 자르면 노드 256대까지다. 클러스터를 처음 만들 때 고른 숫자가 나중에 노드 수의 상한이 되니, 대역 설계는 [IP 주소 글](/posts/layer-ip-addressing)에서 본 계산으로 미리 해 둔다. 사내망이나 VPC 대역과 겹치지 않게 고르는 것도 같은 이유다. 겹치면 Pod가 그 대역의 사내 서버에 닿지 못한다.

모든 CNI가 이 칸을 쓰지는 않는다. Calico와 Cilium은 자기 IPAM으로 더 작은 블록(Calico 기본 /26)을 필요할 때마다 노드에 붙여 주고, AWS VPC CNI는 VPC 서브넷의 IP를 노드의 네트워크 인터페이스(ENI)에 붙여 Pod에 그대로 준다. 앞의 두 방식은 Pod 대역이 VPC와 따로이고, 마지막 방식은 Pod가 VPC 주소를 직접 갖는다.

## 노드를 넘는 첫 번째 방법: 경로를 놓는다

이제 노드 1(`192.168.60.11`, Pod 대역 `10.244.1.0/24`)의 Pod에서 노드 2(`192.168.60.12`, `10.244.2.0/24`)의 Pod로 가 보자. 아직 아무것도 안 했으니 안 된다.

```bash
# 노드 1에서 다른 노드의 Pod 대역으로 가는 길이 있나
ip route get 10.244.2.2
```

```text
RTNETLINK answers: Network is unreachable
```

가장 단순한 해법은 각 노드에 "저 노드의 Pod 대역은 저 노드로 보내라"는 경로를 넣는 것이다. Flannel의 host-gw 모드가 이것이고, Calico는 같은 경로를 BGP로 노드와 라우터에 퍼뜨린다.

```bash
# 노드 1: 10.244.2.0/24는 노드 2로
sudo ip route add 10.244.2.0/24 via 192.168.60.12
# 노드 2: 10.244.1.0/24는 노드 1로
sudo ip route add 10.244.1.0/24 via 192.168.60.11

# Pod 1에서 Pod 3(노드 2)으로 요청하고, 지나는 홉을 본다
curl -s http://10.244.2.2:8080/
traceroute -n -q1 -w1 10.244.2.2
```

```text
hello from pod3, you are 192.168.60.11
traceroute to 10.244.2.2 (10.244.2.2), 30 hops max, 60 byte packets

 2  192.168.60.12  0.213 ms
 3  10.244.2.2  0.201 ms
```

길은 열렸다. 노드 1의 `cni0`, 노드 2, Pod 3 순서로 세 홉이다. 그런데 응답 첫 줄이 이상하다. Pod 3이 본 출발지가 Pod 1(`10.244.1.2`)이 아니라 노드 1(`192.168.60.11`)이다. 쿠버네티스 모델의 두 번째 요구를 어겼다. 노드 1의 nat 테이블에 범인이 있다.

```bash
# bridge 플러그인의 ipMasq: true가 넣은 규칙
sudo iptables -t nat -S | grep CNI-7a92
```

```text

-A CNI-7a9293d19f0c0646a514ced8 -d 10.244.1.0/24 -m comment --comment "name: \"k8s-pod-network\" id: \"3f9a1c2b7d4e\"" -j ACCEPT
-A CNI-7a9293d19f0c0646a514ced8 ! -d 224.0.0.0/4 -m comment --comment "name: \"k8s-pod-network\" id: \"3f9a1c2b7d4e\"" -j MASQUERADE
```

참조 bridge 플러그인은 자기가 아는 대역, 곧 이 노드의 `10.244.1.0/24`만 예외로 두고 나머지는 전부 MASQUERADE한다. 다른 노드의 Pod 대역도 "바깥"으로 본 것이다. 진짜 CNI 플러그인은 예외를 클러스터 전체 대역으로 잡는다. Pod 규칙을 지우고 그렇게 한 줄로 바꿨다.

```bash
# 클러스터 대역 밖으로 나갈 때만 노드 주소로 바꾼다
sudo iptables -t nat -A POSTROUTING -s 10.244.0.0/16 ! -d 10.244.0.0/16 \
  -m comment --comment "pod to outside only" -j MASQUERADE

# 노드 2의 eth0에서 본 패킷
sudo tcpdump -ni eth0 -c 2 tcp port 8080
```


## 노드를 넘는 두 번째 방법: VXLAN으로 감싼다

노드 사이 망을 건드릴 수 없으면 Pod 패킷을 노드 주소끼리의 UDP에 싸서 보낸다. Flannel의 기본 모드(VXLAN)가 하는 일을 그대로 손으로 해 봤다. 앞에서 넣은 경로는 지웠다.

```bash
# 노드 1: VNI 1, Flannel이 쓰는 포트 8472, 모르는 MAC을 배우지 않는(nolearning) VXLAN 장치
sudo ip link add flannel.1 type vxlan id 1 local 192.168.60.11 dev eth0 dstport 8472 nolearning
sudo ip addr add 10.244.1.0/32 dev flannel.1
sudo ip link set flannel.1 up

# 노드 2에 대해 세 가지를 미리 적어 둔다 (노드 2의 flannel.1 MAC = 42:a7:5b:80:48:ba)
# 1) 경로: 10.244.2.0/24는 flannel.1로, 다음 홉은 노드 2의 flannel.1 주소
sudo ip route add 10.244.2.0/24 via 10.244.2.0 dev flannel.1 onlink
# 2) 이웃: 그 다음 홉의 MAC
sudo ip neigh add 10.244.2.0 lladdr 42:a7:5b:80:48:ba dev flannel.1 nud permanent
# 3) FDB: 그 MAC은 노드 2(192.168.60.12) 뒤에 있다
sudo bridge fdb append 42:a7:5b:80:48:ba dev flannel.1 dst 192.168.60.12

# 확인
ip -d link show flannel.1
ip route
ip neigh show dev flannel.1
bridge fdb show dev flannel.1
```

```text

    link/ether de:ad:1e:7c:e4:07 brd ff:ff:ff:ff:ff:ff promiscuity 0  allmulti 0 minmtu 68 maxmtu 65535 
    vxlan id 1 fan-map local 192.168.60.11 dev eth0 srcport 0 0 dstport 8472 nolearning ttl auto ageing 300 udpcsum noudp6zerocsumtx noudp6zerocsumrx numtxqueues 1 numrxqueues 1 gso_max_size 65536 gso_max_segs 65535 tso_max_size 524280 tso_max_segs 65535 gro_max_size 65536
```

이 방식은 L2를 늘리는 게 아니라 L3 라우팅 위에 터널을 얹는다. 노드마다 `flannel.1`이 자기 대역의 `.0` 주소를 갖고, 다른 노드로 가는 경로의 다음 홉이 "상대 노드의 flannel.1"이다. 그 다음 홉의 MAC(이웃 표)과 그 MAC이 있는 노드 주소(FDB)를 미리 적어 두니, ARP도 브로드캐스트도 터널 위로 나가지 않는다. 실제 Flannel에서는 노드마다 도는 `flanneld`가 API 서버에서 다른 노드의 podCIDR과 VTEP MAC(노드 어노테이션 `flannel.alpha.coreos.com/backend-data`)을 읽어 이 세 줄을 대신 써 준다. 노드가 하나 붙을 때마다 기존 노드 모두에 세 줄이 늘어나는 셈이다.

### 감싼 만큼 MTU가 줄어든다

`flannel.1`의 MTU가 1450이다. 바깥 헤더 50바이트만큼 작다. Pod의 `eth0`는 bridge 플러그인 설정대로 1500이니, 1500짜리 패킷을 보내면 노드에서 걸린다.

```bash
# Pod 1에서 DF를 켜고 1500바이트(1472 + 28) ping
ping -c 2 -M do -s 1472 -W 1 10.244.2.2
# 1450바이트로 줄이면
ping -c 1 -M do -s 1422 -W 1 10.244.2.2
# Pod가 배운 경로 MTU
ip route get 10.244.2.2
```

```text
PING 10.244.2.2 (10.244.2.2) 1472(1500) bytes of data.
From 10.244.1.1 icmp_seq=1 Frag needed and DF set (mtu = 1450)
ping: local error: message too long, mtu=1450

--- 10.244.2.2 ping statistics ---
2 packets transmitted, 0 received, +2 errors, 100% packet loss, time 1017ms

PING 10.244.2.2 (10.244.2.2) 1422(1450) bytes of data.
1430 bytes from 10.244.2.2: icmp_seq=1 ttl=62 time=0.279 ms
10.244.2.2 via 10.244.1.1 dev eth0 src 10.244.1.2 uid 0 
    cache expires 597sec mtu 1450
```

여기서는 노드(`10.244.1.1`)가 "조각내야 하는데 DF가 켜져 있다"는 ICMP를 돌려줘서 Pod가 경로 MTU 1450을 배웠다. 두 번째 패킷부터는 Pod 커널이 알아서 줄인다. 같은 노드가 ICMP를 만드니 이번엔 됐지만, 노드 사이 망 쪽 MTU가 더 작고(VPN, 일부 클라우드) 중간 장비가 ICMP를 막으면 아무도 알려 주지 않는다. TCP 핸드셰이크와 작은 요청은 되는데 큰 응답만 멈추는 증상이 그것이다([MTU 글](/posts/layer-mtu-fragmentation)). 그래서 CNI는 Pod의 MTU 자체를 터널 MTU에 맞춰 준다. Flannel은 1450, Calico는 VXLAN이면 50, IP-in-IP면 20바이트를 빼고, Cilium도 터널 모드에서 같은 계산을 한다. 노드 NIC의 MTU가 9001인 AWS처럼 점보 프레임 망이면 이 값을 크게 올려서 처리량을 얻는다.

## 어떤 CNI를 고르나

방식은 결국 셋으로 나뉜다. 노드 사이에 경로를 놓거나(Flannel host-gw, Calico BGP), 터널로 감싸거나(Flannel VXLAN, Calico VXLAN·IP-in-IP, Cilium 터널), 클라우드 망이 Pod 주소를 직접 알게 하거나(AWS VPC CNI, Azure CNI, GKE의 VPC 기반 클러스터). 제품을 고를 때는 이런 기준을 본다.

- NetworkPolicy가 필요한가. Flannel은 정책을 집행하지 않는다. 정책이 필요하면 Calico나 Cilium을 쓰거나 Flannel 위에 Calico를 정책 전용으로 얹는다(Canal). 정책을 어떻게 집행하는지는 [NetworkPolicy 글](/posts/k8s-network-policy)에서 이어진다.
- 노드 사이 망을 내가 다룰 수 있나. 온프레미스에서 ToR 스위치와 BGP를 맺을 수 있으면 터널 없는 Calico가 빠르고 투명하다. 망을 못 건드리면 터널이다.
- 클라우드 통합이 중요한가. VPC CNI는 Pod가 VPC 주소를 가져서 보안 그룹, 흐름 로그, 다른 VPC 서비스가 Pod를 바로 본다. 대신 서브넷 IP를 Pod 수만큼 먹고 노드당 Pod 수가 인스턴스의 ENI 한도에 묶인다.
- eBPF가 필요한가. Cilium은 iptables 대신 eBPF로 경로와 정책, Service 분산까지 처리해서 kube-proxy를 대체할 수 있고, L7 정책과 흐름 관측(Hubble)을 준다. 커널 버전 요구와 다른 디버깅 도구에 익숙해지는 비용이 있다.

노드 하나에 Pod를 몇 개까지 띄울 수 있는지도 CNI가 정한다. podCIDR 방식은 대역 크기와 kubelet의 `maxPods`(기본 110) 중 작은 값이다. AWS VPC CNI는 인스턴스가 붙일 수 있는 ENI 수와 ENI당 IP 수로 정해진다. ENI마다 첫 IP는 노드 자신이 쓰니 하나씩 빼고, hostNetwork로 뜨는 Pod 두 개(aws-node, kube-proxy)를 더한다. 접두사 위임(prefix delegation)을 켜면 IP 하나 대신 /28 하나(16개)를 붙인다.

## 노드를 넘을 때만 안 되면

현장에서 Pod 네트워크 문제는 "같은 노드 안"과 "노드를 넘을 때"를 나누는 데서 시작한다. Pod를 두 노드에 하나씩, 같은 노드에 하나 더 띄워 두고 Pod IP로 직접 두드린다. Service를 끼우면 kube-proxy 문제와 섞이니 빼고 본다([Service 글](/posts/k8s-service-types)).

```bash
# 1. 문제 노드의 CNI Pod가 떠 있고 재시작이 없는가
kubectl -n kube-system get pods -o wide | grep -E 'flannel|calico|cilium|aws-node'

# 2. 노드의 CNI 설정과 실행 파일 (사전순 첫 파일이 쓰인다. 예전 CNI의 파일이 남았나)
ls -l /etc/cni/net.d/ /opt/cni/bin/

# 3. 다른 노드의 Pod 대역으로 가는 길이 있나
ip route | grep 10.244.
ip route get 10.244.2.2

# 4. 터널 방식이면 이웃·FDB 항목이 있나
ip neigh show dev flannel.1
bridge fdb show dev flannel.1

# 5. 패킷이 노드를 떠나고 상대 노드에 도착하나 (양쪽 노드에서)
sudo tcpdump -ni eth0 udp port 8472 or udp port 4789
```

2번에서 `/etc/cni/net.d`에 예전 CNI의 설정 파일이 남아 있으면, 이름이 사전순으로 앞선 쪽이 쓰여 새로 깐 CNI가 무시된다. CNI를 바꿨는데 일부 노드만 이상하면 이걸 본다. 3번에서 경로가 없으면 그 노드의 CNI 에이전트가 API 서버에서 다른 노드 정보를 못 받은 것이라 에이전트 로그를 본다. 5번에서 보내는 노드에는 보이고 받는 노드에는 안 보이면 그 사이 방화벽이나 보안 그룹이다. 받는 노드에 도착했는데 Pod에 안 닿으면 받는 노드의 FORWARD 정책(Docker가 DROP으로 바꿔 놓은 경우가 있다)과 `rp_filter`를 본다.

## 쿠버네티스는 약속만, 길은 플러그인이

쿠버네티스는 "Pod마다 고유한 IP, Pod 사이엔 NAT 없음"이라는 약속만 하고, 그 약속을 지키는 일은 노드에 깔린 CNI 실행 파일이 한다. 런타임이 Pod의 빈 네트워크 네임스페이스와 설정 JSON을 넘기면 플러그인은 veth를 꽂고 IPAM에서 주소를 받아 결과 JSON을 돌려준다. 노드 사이 길은 노드마다 나눈 Pod 대역을 경로로 알리거나, VXLAN으로 감싸 노드 주소끼리 보내거나, 클라우드 망에 직접 맡기는 셋 중 하나다. 어느 쪽이든 장애는 경로, 터널 포트, MTU, 그리고 Pod 사이에 끼어든 NAT 넷 중 하나에서 나는 경우가 많다.

## 면접에서 나올 만한 질문

### 쿠버네티스 네트워크 모델의 요구 사항은 무엇인가요?

모든 Pod가 클러스터에서 겹치지 않는 IP를 갖고, 모든 Pod가 NAT 없이 서로 통신하며, 노드의 에이전트가 그 노드의 Pod에 닿아야 한다. 쿠버네티스는 이 요구만 정하고 구현은 CNI 플러그인에 맡긴다. Pod를 IP를 가진 작은 호스트처럼 다루면 포트 충돌이 없고, 서비스 발견과 NetworkPolicy가 IP 기준으로 단순해진다.

### CNI 플러그인은 언제, 어떻게 호출되나요?

kubelet이 CRI로 Pod 샌드박스를 요청하면 containerd 같은 런타임이 네트워크 네임스페이스를 만들고 `/etc/cni/net.d`의 사전순 첫 설정 파일을 읽어 거기 적힌 type의 실행 파일을 `/opt/cni/bin`에서 실행한다. 할 일과 대상은 CNI_COMMAND, CNI_NETNS, CNI_IFNAME 같은 환경 변수로, 네트워크 설정은 표준 입력 JSON으로 준다. 플러그인은 인터페이스와 IP를 설정한 결과를 JSON으로 돌려주고, 런타임은 그 IP를 Pod IP로 보고한다. Pod를 지울 때는 DEL로 다시 부른다.

### IPAM은 무엇이고 IP가 바닥나는 경우는 언제인가요?

IPAM은 Pod에 줄 주소를 고르고 기록하는 부분이다. host-local은 노드의 Pod 대역에서 빈 IP를 고르고 IP 이름의 파일에 컨테이너 ID를 적어 둔다. 런타임이 DEL을 부르지 못하고 죽으면 파일이 남아 그 IP가 계속 쓰이는 것처럼 보이고, 작은 대역에서는 `no IP addresses available in range set`으로 새 Pod가 실패한다. 클라우드 CNI는 서브넷 IP나 ENI 한도가 바닥나는 식으로 같은 문제가 온다.

### 노드 사이 Pod 통신을 경로 방식과 VXLAN 방식으로 하면 무엇이 다른가요?

경로 방식은 각 노드가 다른 노드의 Pod 대역을 그 노드로 보내는 경로를 갖는다. 캡슐화가 없어 빠르고 tcpdump에 Pod 주소가 그대로 보이지만, 노드 사이 망이 Pod 주소를 받아 줘야 해서 같은 L2이거나 BGP로 라우터에 알려야 한다. VXLAN 방식은 Pod 패킷을 노드 주소끼리의 UDP로 감싸 노드 사이 망이 Pod 주소를 몰라도 되지만, 헤더 50바이트만큼 MTU가 줄고 UDP 포트가 열려 있어야 한다.

### 같은 노드의 Pod끼리는 되는데 다른 노드로만 안 됩니다. 어디를 보나요?

Pod IP로 직접 두드려 Service를 빼고 본다. 문제 노드에서 다른 노드의 Pod 대역으로 가는 경로가 있는지(`ip route get`), 터널 방식이면 이웃 표와 FDB 항목이 있는지 보고, 없으면 CNI 에이전트 로그를 본다. 있으면 양쪽 노드에서 tcpdump로 터널 포트(Flannel 8472, 표준 4789)를 잡아 보내는 쪽과 받는 쪽 중 어디서 사라지는지 확인한다. 보내고 못 받으면 보안 그룹이나 방화벽이다.

### Pod MTU를 잘못 잡으면 어떤 증상이 나나요?

터널 헤더만큼 줄어든 경로보다 Pod MTU가 크면, 작은 요청과 TCP 핸드셰이크는 되는데 큰 응답이나 업로드만 멈춘다. 중간에서 ICMP Frag needed가 막히면 Pod가 경로 MTU를 배우지 못해 재전송만 반복한다. 그래서 CNI는 Pod MTU를 노드 MTU에서 터널 헤더를 뺀 값(VXLAN이면 50바이트 작게)으로 설정하고, 노드 사이 망 MTU가 1500보다 작으면 그만큼 더 낮춘다.

### 'cni0 already has an IP address different from ...' 에러는 왜 나나요?

노드의 Pod 대역이 바뀌었는데 예전 대역 주소를 단 `cni0` 브리지가 남아 있을 때 bridge 플러그인이 낸다. kubeadm reset 후 다시 조인하거나 클러스터 대역을 바꿨을 때 흔하다. 노드를 drain하고 `cni0`(Flannel이면 `flannel.1`도)를 지운 뒤 CNI 에이전트와 kubelet을 다시 띄우면 새 대역으로 다시 만들어진다.

### AWS VPC CNI에서 노드의 Pod 수가 적게 잡히는 이유는요?

Pod가 VPC 서브넷의 주소를 직접 받기 때문에, 노드에 붙일 수 있는 ENI 수와 ENI당 IP 수가 Pod 수의 상한이 된다. 계산은 ENI 수 × (ENI당 IP − 1) + 2이고, m5.large는 29개, t3.medium은 17개다. 이를 넘으면 자원이 남아도 `Too many pods`로 Pending이 된다. 접두사 위임을 켜면 IP 칸마다 /28을 붙여 크게 늘릴 수 있지만 서브넷 주소도 그만큼 많이 쓴다.
