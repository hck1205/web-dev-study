관리자 화면에 "회원 목록 내려받기" 버튼이 있다. 회원 100만 명을 NDJSON(한 줄에 JSON 하나)으로 만들어 돌려주는데, 버튼을 누르면 1.5초 동안 아무것도 안 오다가 한 번에 95MB가 쏟아진다. 그동안 서버 프로세스의 메모리는 45MB에서 523MB까지 뛴다. 응답 전체를 문자열로 만든 다음 `res.end(body)`로 보냈기 때문이다. 같은 데이터를 만드는 대로 흘려보내면 첫 바이트는 0.01초에 오고 메모리는 46MB에서 움직이지 않는다.

응답을 다 만들기 전에 보내기 시작하는 것, 이것이 HTTP 스트리밍이다. LLM 답변이 한 글자씩 찍히는 화면, 배포 로그가 실시간으로 올라오는 화면, 큰 파일 내보내기가 모두 같은 장치 위에 있다. 이 글은 그 장치를 바이트부터 따라간다. 응답 본문이 어떻게 조각으로 나뉘어 날아가는지, 받는 쪽은 그 조각을 어떻게 메시지로 다시 자르는지, 중간에 끊기거나 받는 쪽이 느리면 무슨 일이 생기는지, 프록시는 그 사이에서 무엇을 하는지다. Node.js 22, Chromium 141, curl 8.5, nginx 1.24(Ubuntu 24.04)로 직접 돌렸다.

이 주제의 다른 글: [실시간 통신 네 가지 비교](/posts/realtime-communication)는 폴링·SSE·WebSocket이 어디에 서는지를, [Server-Sent Events 깊게 보기](/posts/server-sent-events)는 `EventSource`의 재연결과 연결 수 제한, 하트비트를 다룬다. 여기서는 그 둘이 깔고 있는 바닥, 끝나지 않는 HTTP 응답 자체를 본다.

## 길이를 모르는 본문은 조각으로 간다

HTTP/1.1 응답은 본문이 어디서 끝나는지 받는 쪽에 알려야 한다. 방법은 둘이다. 처음에 `Content-Length`로 전체 길이를 밝히거나, 길이를 모른다고 하고 조각마다 길이를 붙여 보내는 `Transfer-Encoding: chunked`다. 두 줄을 300ms 간격으로 쓰고 trailer 하나를 붙이는 Node 서버를 만들었다.

```js
// 길이를 미리 말하지 않고 쓰면 Node가 알아서 chunked로 보낸다
res.writeHead(200, { "content-type": "text/plain; charset=utf-8", trailer: "x-row-count" });
res.write("hello\n"); await sleep(300);
res.write("안녕\n"); await sleep(300);
res.addTrailers({ "x-row-count": "2" });   // 본문 뒤에 붙는 헤더
res.end();
```

```bash
# -N: 받는 대로 출력, -i: 헤더도 보기
curl -sN -i http://127.0.0.1:18210/chunks
```

```text
HTTP/1.1 200 OK
content-type: text/plain; charset=utf-8
trailer: x-row-count
Date: Wed, 21 Oct 2026 19:18:41 GMT
Connection: keep-alive
Keep-Alive: timeout=5
Transfer-Encoding: chunked

hello
안녕
```

curl은 조각 틀을 벗겨서 본문만 보여 준다. `--raw`를 주면 틀까지 그대로 받는다. 줄바꿈과 한글 바이트를 보려고 `od -c`로 찍었다.

```bash
# --raw: chunked 디코딩을 하지 않고 받은 바이트 그대로
curl -sN --raw http://127.0.0.1:18210/chunks | od -c
```

HTTP/2와 HTTP/3에는 chunked가 없다. 프로토콜 자체가 본문을 DATA 프레임으로 나눠 보내고, 마지막 프레임에 END_STREAM 플래그를 세운다. 명세가 `Transfer-Encoding` 헤더를 아예 금지한다. Node의 `http2` 모듈로 같은 일을 해 보면 헤더에서 그 줄이 사라진다.

```bash
# h2c(평문 HTTP/2)로 바로 붙는다
curl -sN -i --http2-prior-knowledge http://127.0.0.1:18211/
```

```text
HTTP/2 200 
content-type: application/x-ndjson
date: Wed, 21 Oct 2026 19:18:42 GMT

{"step":1}
{"step":2}
{"step":3}
```

틀은 달라도 애플리케이션이 보는 모습은 같다. 끝을 모르는 바이트 줄기가 조금씩 도착한다. 버전별 프레임 차이는 [HTTP 버전](/posts/http-versions)에 있다.

## 같은 바이트 줄기 위의 여러 형식

NDJSON(줄 단위 JSON, JSON Lines라고도 한다)은 가장 단순한 규칙이다. JSON 하나를 한 줄에 쓰고 `\n`으로 끝낸다. JSON 문자열 안의 줄바꿈은 `\n`으로 이스케이프되니 실제 줄바꿈 문자는 메시지 경계에만 나온다. 미디어 타입은 관례상 `application/x-ndjson`을 쓴다(IANA에 정식 등록된 이름은 아니다). Ollama 같은 로컬 LLM 서버, Elasticsearch의 bulk API, Docker 엔진 API의 진행 상황 스트림이 이 형식이다.

```bash
# 0.4초마다 한 줄씩 온다. 받은 시각을 앞에 붙였다
curl -sN "http://127.0.0.1:18210/ndjson?n=3&ms=400" | while IFS= read -r l; do echo "$(date +%T.%1N) $l"; done
```

```text
19:18:49.8 {"step":1,"of":3}
19:18:50.2 {"step":2,"of":3}
19:18:50.6 {"step":3,"of":3}
19:18:51.0 {"type":"done"}
```

SSE는 `text/event-stream`이라는 조금 더 많은 규칙이다. `data:`, `event:`, `id:`, `retry:` 필드를 줄로 쓰고 빈 줄로 이벤트를 끝낸다. 형식만 보면 NDJSON보다 장황한데, 그 대가로 브라우저의 `EventSource`가 재연결과 이어 받기를 공짜로 해 준다. 일부러 이벤트 두 개마다 연결을 끊는 서버에 Chromium의 `EventSource`를 붙여 봤다.

```text
6ms message id=1 tick 1
104ms message id=2 tick 2
207ms error readyState=0
712ms message id=3 tick 3
813ms message id=4 tick 4
915ms error readyState=0
1421ms message id=5 tick 5
```

```text
[ 2981ms] sse connect, Last-Event-ID: (none)
[ 3689ms] sse connect, Last-Event-ID: 2
[ 4397ms] sse connect, Last-Event-ID: 4
```

끊길 때마다 `retry: 500`에 맞춰 0.5초 뒤 다시 붙었고, 마지막으로 받은 id를 `Last-Event-ID` 헤더로 알려 줘서 서버가 3번부터 이어 보냈다. fetch로 NDJSON을 읽을 때는 이 일을 전부 직접 해야 한다. 필드 규칙과 파서는 [실시간 통신 네 가지 비교](/posts/realtime-communication)에, 브라우저가 재연결을 영영 포기하는 응답과 HTTP/1.1의 연결 6개 제한은 [Server-Sent Events 깊게 보기](/posts/server-sent-events)에 정리했다.

어느 형식을 고를지는 읽는 쪽이 정한다. 브라우저에서 GET 한 번으로 구독하고 끊기면 알아서 이어 받아야 한다면 SSE와 `EventSource`다. POST 본문과 `Authorization` 헤더가 필요하거나(LLM 호출), 브라우저가 아닌 프로그램이 읽거나, 내보내기처럼 한 번 받고 끝나는 스트림이라면 NDJSON이 단순하다. LLM API들이 형식은 SSE를 쓰면서 브라우저에서는 fetch로 읽게 하는 것도 이 때문이다.

## 조각 경계는 메시지 경계가 아니다

fetch의 응답 본문 `res.body`는 `ReadableStream`이다. `getReader()`로 리더를 얻고 `read()`를 부를 때마다 도착한 조각이 `Uint8Array`로 나온다. 이 조각이 어디서 잘려 오는지가 첫 번째 함정이다. 0.3초 간격으로 줄을 쓰는 서버와 3000줄을 한꺼번에 쓰는 서버를 Chromium에서 읽어 봤다.

```js
const reader = (await fetch("/ndjson?n=3&ms=300")).body.pipeThrough(new TextDecoderStream()).getReader();
for (;;) {
  const { value, done } = await reader.read();
  if (done) break;
  console.log(Math.round(performance.now() - t) + "ms", JSON.stringify(value));
}
```

```text
6ms "{\"step\":1,\"of\":3}\n"
305ms "{\"step\":2,\"of\":3}\n"
606ms "{\"step\":3,\"of\":3}\n"
905ms "{\"type\":\"done\"}\n"
```

3000줄(약 27만 바이트)짜리 응답에서 read()가 돌려준 조각 크기다.

```text
"sizes": [3923, 65528, 20002, 45833, 65522, 26145, 45833]
```

느린 스트림에서는 read 한 번이 줄 하나와 딱 맞는다. 로컬에서 이것만 보고 `JSON.parse(value)`를 쓰면 잘 돌아간다. 빠른 스트림에서는 조각이 64KB 안팎으로 묶여 오고 줄 중간에서 잘린다. Node.js 22의 fetch로 받은 첫 조각의 끝은 이랬다.

```text
first chunk ends with: "-01T00:00:00Z\"}\n{\"id\":732,\"email\":\"user7"
```

`user7`에서 잘렸다. 조각 크기는 TCP 세그먼트, 커널 버퍼, 프록시, 브라우저 구현이 정하는 것이고 서버의 `write()` 경계와는 상관없다. 그래서 받는 쪽은 버퍼에 이어 붙이고 줄바꿈이 나올 때마다 잘라야 한다. 아래 그림에서 조각이 들어올 때마다 버퍼가 어떻게 바뀌는지 보자.

한글이 조각 사이에서 잘리는 문제는 바이트 쪽에서 생긴다. '안'의 3바이트가 두 조각으로 나뉘어 오면 조각마다 `new TextDecoder().decode(chunk)`를 부르는 코드는 깨진 문자(U+FFFD)를 만든다. `TextDecoderStream`을 파이프에 끼우거나 `decoder.decode(chunk, { stream: true })`를 쓰면 디코더가 남은 바이트를 다음 조각까지 들고 있는다. 직접 만들어 보자. 이미 문자열로 디코딩된 조각 배열을 받아 메시지 배열을 돌려주는 함수다.

  solution={`function splitNdjson(chunks) {

## 200을 보낸 뒤에 실패하면

스트리밍 응답은 상태 코드와 헤더를 먼저 보내고 본문을 나중에 만든다. 그래서 본문을 만들다가 DB가 죽어도 상태 코드를 500으로 바꿀 방법이 없다. 이미 200이 나갔다. 세 줄을 보내고 소켓을 끊는 서버로 확인했다.

```bash
# -S: 조용히 하되 에러는 보여 준다
curl -sSN http://127.0.0.1:18210/broken; echo "exit=$?"
```

```text
{"step":1}
{"step":2}
{"step":3}
curl: (18) transfer closed with outstanding read data remaining
exit=18
```

curl은 0 조각을 못 받았으니 잘렸다고 알려 준다. fetch는 어떨까.

Node.js 22의 fetch(undici)로 읽으면 이렇다.

```text
broken status: 200 true
got {"step":1}
got {"step":2}
got {"step":3}
read threw: TypeError terminated UND_ERR_SOCKET
```

Chromium 141에서는 이렇다.

```text
"brokenStatus": 200,
"broken": "TypeError: network error after 3 reads",
```

`res.ok`는 true였다. 에러는 `read()`가 던진다. 둘 다 정상 종료와는 구분되지만, 그건 HTTP/1.1에서 서버가 연결을 비정상으로 끊은 경우다. 서버 코드가 예외를 잡아서 `res.end()`로 깔끔하게 닫아 버리면 받는 쪽에는 정상 종료와 똑같이 보인다. 반쯤 만든 내보내기 파일이 성공처럼 저장된다.

그래서 스트림 프로토콜에는 "끝났다"는 메시지를 따로 둔다. 데모의 마지막 줄 `{"type":"done"}`이 그것이다. OpenAI API는 SSE 스트림 끝에 `data: [DONE]`을, Anthropic API는 `message_stop` 이벤트를 보낸다. 중간에 실패하면 끝 메시지 대신 `{"type":"error","message":"…"}`를 쓰고 닫는다. 받는 쪽 규칙은 하나다. 끝 메시지를 받기 전에 스트림이 끝나면 성공이 아니다. 상태 코드와 헤더로 결정할 수 있는 것(권한, 입력 검증, 404)은 첫 바이트를 쓰기 전에 끝낸다. 스트리밍 SSR에서 이 문제가 어떻게 드러나는지는 [스트리밍 SSR과 Suspense](/posts/streaming-ssr-suspense)의 "상태 코드는 첫 조각과 함께 떠난다"에 있다.

## 받는 쪽이 느리면 보내는 쪽이 멈춰야 한다

처음의 내보내기 버튼으로 돌아가자. 응답을 다 만들어 보내는 방식과 만드는 대로 보내는 방식을, 서버를 새로 띄워 가며 100만 행으로 쟀다.

```text
export-buffer ttfb=1.490859s total=1.569348s size=95444459
[ 1815ms] export-buffer built 1000000 rows rss 249MB
[ 2170ms] export-buffer sent, peak rss 523MB
export?batch=1 ttfb=0.011764s total=2.676682s size=95444459
[ 3759ms] export streamed 1000000 rows, drain waits 1546 peak rss 90MB
export?batch=500 ttfb=0.010620s total=0.850302s size=95444459
[ 1398ms] export streamed 1000000 rows, drain waits 1000 peak rss 46MB
```

통째로 만들면 첫 바이트까지 1.5초, 메모리 정점 523MB다. 문자열을 만들 때 한 번, 보낼 때 Buffer로 바꾸며 또 한 번 메모리를 쓴다. 동시에 다섯 명이 누르면 컨테이너 메모리 한도를 넘는다. 스트리밍하면 첫 바이트가 0.01초다. 다만 한 행마다 `write()`를 부르면 호출이 100만 번이라 전체 시간이 2.7초로 오히려 늘었다. 500행씩 묶어 쓰자 0.85초, 46MB가 됐다. 스트리밍해도 쓰기 단위는 적당히 크게 잡는다.

`drain waits`가 배압(backpressure)이다. 서버는 받는 쪽이 가져가는 속도보다 빨리 만들 수 있다. 그때 `res.write()`가 false를 돌려주며 "내부 버퍼가 찼다"고 알린다. 이 신호를 무시하고 계속 쓰면 보낼 데이터가 서버 메모리에 쌓인다. 그래서 false가 오면 `drain` 이벤트까지 기다린다. 아래 그림에서 단계를 넘기면 이 대화가 보인다.

다섯째 단계가 실무에서 잘 터지는 곳이다. 위의 `/export`는 이렇게 짰다.

```js
// 흔한 코드: drain만 기다린다
for (let i = 1; i <= n; i++) {
  buf += row(i);
  if (i % batch) continue;
  if (!res.write(buf)) await once(res, "drain");   // 클라이언트가 떠나면 영영 안 온다
  buf = "";
  if (res.destroyed) return log("export aborted at", i);
}
```

클라이언트가 13만 바이트쯤 받고 끊게 한 뒤 서버 로그를 봤다.

```text
export: client destroyed after 135286 bytes
export2: client destroyed after 135286 bytes
[  713ms] export2 stopped at row 4000: ERR_STREAM_PREMATURE_CLOSE
```

`/export`는 아무 로그도 남기지 않았다. `once(res, "drain")`은 `error` 이벤트가 나야 실패하는데, 클라이언트가 떠나면 응답 객체는 `error`가 아니라 `close`를 낸다. 그래서 그 Promise는 영원히 대기하고, 함수가 붙잡은 DB 커서나 커넥션도 같이 남는다. 사용자가 내보내기를 열 번 누르고 취소하면 열 개가 쌓인다. `/export2`는 행을 만드는 비동기 제너레이터를 `stream.pipeline`으로 응답에 이었다.

```js
const { pipeline } = require("node:stream/promises");
const { Readable } = require("node:stream");

let made = 0;
async function* rows() {                 // 500행씩 묶어 내보낸다
  let buf = "";
  for (let i = 1; i <= n; i++) {
    buf += row(i); made = i;
    if (i % 500 === 0 || i === n) { yield buf; buf = ""; }
  }
}
try {
  await pipeline(Readable.from(rows()), res);   // 배압과 끊김을 pipeline이 처리한다
} catch (e) {
  log(`export2 stopped at row ${made}: ${e.code}`);
}
```

`pipeline`은 받는 쪽 버퍼가 차면 제너레이터를 멈추고, 연결이 끊기면 제너레이터의 `return()`을 불러 정리한 뒤 에러로 빠져나온다. 손으로 배압을 짜는 대신 이걸 쓰는 것이 안전하다. 웹 표준 쪽에서는 `ReadableStream`의 `pull()`이 같은 역할을 한다. 읽는 쪽이 `read()`를 불러야 다음 조각을 만들게 된다. 배압이 시스템 전체에서 어떻게 번지는지는 [배압](/posts/backpressure)에 있다.

```js
  res.write(JSON.stringify({ type: "token", text: tokens[i] }) + "\n");
```

실제 LLM SDK를 쓴다면 브라우저 요청의 끊김을 SDK 호출의 `AbortSignal`로 이어 준다. 화면 쪽에서 스트리밍 텍스트를 어떻게 보여 줄지는 [로딩 패턴](/posts/loading-patterns)에 있다.

반대 방향, 요청 본문을 흘려보내는 스트리밍 업로드도 있다. fetch에 `ReadableStream`을 본문으로 주고 `duplex: "half"`를 붙인다. Node.js 22의 fetch는 HTTP/1.1에서도 chunked로 잘 보낸다.

```text

[14029ms] upload chunk 2: 7B "line 2"
[14331ms] upload chunk 3: 7B "line 3"
response {"chunks":3,"bytes":21}
```

같은 코드를 Chromium에서 `http://` 주소로 돌리면 실패한다.

```text
requestfailed POST http://127.0.0.1:18210/upload net::ERR_ALPN_NEGOTIATION_FAILED
TypeError: Failed to fetch
```

크롬 계열은 요청 스트리밍을 HTTPS 위의 HTTP/2 이상에서만 허용한다. HTTP/2를 협상하는 ALPN은 TLS 안에서 일어나니 평문 HTTP에서는 협상 단계에서 막힌다. 다른 브라우저는 아직 요청 스트리밍을 지원하지 않는 경우가 많아서, 브라우저에서 큰 파일을 올릴 때는 여전히 조각을 나눠 여러 요청으로 올리는 방식이 흔하다.

## 프록시는 느린 클라이언트를 대신 받아 준다

스트리밍 응답이 "로컬에서는 바로 오는데 운영에서는 몰려서 온다"는 문제, 그리고 `proxy_buffering off`와 `X-Accel-Buffering: no`로 푸는 법은 [Server-Sent Events 깊게 보기](/posts/server-sent-events)와 [nginx 리버스 프록시](/posts/nginx-reverse-proxy)에서 재현했다. 여기서는 그 버퍼가 왜 기본으로 켜져 있는지를 본다. 같은 nginx에서 업스트림 HTTP 버전만 바꿔 NDJSON을 받아 봤다.

```nginx
location / {
  proxy_pass http://127.0.0.1:18210;
  proxy_http_version 1.1;     # 버퍼링은 기본값(on) 그대로
}
location /h10/ {
  proxy_pass http://127.0.0.1:18210/;   # proxy_http_version 기본값 1.0
}
```

```text

19:20:52.8 {"step":1,"of":3}
19:20:53.2 {"step":2,"of":3}
19:20:53.6 {"step":3,"of":3}
19:20:54.0 {"type":"done"}
== h1.0 upstream, buffering on
19:21:05.7
19:21:06.9 {"step":1,"of":3}
19:21:06.9 {"step":2,"of":3}
19:21:06.9 {"step":3,"of":3}
19:21:06.9 {"type":"done"}
```

`proxy_http_version 1.1`인 경로는 버퍼링이 켜져 있어도 줄이 제때 왔고, 기본값 1.0인 경로는 1.2초 동안 붙잡았다가 한꺼번에 내보냈다. 버전 한 줄에 따라 동작이 달라지니 이런 세부 동작에 기대지 말고 스트리밍 경로는 버퍼링 끄기를 명시하는 편이 안전하다.

그렇다고 버퍼링이 나쁜 기능은 아니다. 95MB 내보내기를 초당 20MB로만 받는 느린 클라이언트로 버퍼링 켠 경로와 끈 경로를 비교했다. 서버 로그 시각은 업스트림 앱이 마지막 바이트를 쓴 시각이다.

버퍼링이 켜져 있으면 앱은 0.9초 만에 다 쓰고 손을 뗐다. nginx가 메모리 버퍼를 넘는 부분을 임시 파일에 받아 두고 나머지 3.4초 동안 클라이언트에게 천천히 내보냈다. 버퍼링을 끄면 앱이 클라이언트 속도에 묶여 3.9초 동안 연결과 메모리를 붙잡았다. 느린 모바일 사용자가 많을수록 앱 프로세스가 그만큼 오래 묶인다. 버퍼링은 이걸 막으려고 기본으로 켜져 있다.

그래서 경로마다 고른다. 사람이 실시간으로 봐야 하는 스트림(LLM 토큰, 진행 상황, SSE)은 버퍼링을 끈다. 크기는 크지만 실시간일 필요는 없는 다운로드는 버퍼링을 켜 두고, 대신 위 경고가 자주 보이면 `proxy_max_temp_file_size`(기본 1024m)와 임시 디렉터리의 디스크 여유를 본다. 아래 그림에서 두 경로를 비교해 보자.

## 스트리밍이 안 될 때 좁혀 가는 순서

증상이 "몰려서 온다"면 경로를 한 칸씩 줄이며 `curl -sN`에 시각을 붙여 찍는다. 앱에 바로 붙어서도 몰리면 앱이 범인이다. 압축 미들웨어가 flush를 안 하거나, 응답을 모았다가 쓰는 프레임워크 설정이다. 앱 직결은 괜찮은데 프록시를 거치면 몰린다면 프록시 버퍼링이다. 응답 헤더에 `Content-Length`가 붙어 있으면 어딘가에서 본문을 다 모은 것이니, 그 헤더를 누가 붙였는지 찾는다.

"중간에 끊긴다"면 끊기는 시각을 본다. 매번 비슷한 경과 시간(60초, 100초)에 끊기면 경로 어딘가의 유휴 타임아웃이나 응답 시간 한도다. 받는 쪽 에러는 curl이면 exit 18, Node fetch면 `TypeError: terminated`, 크롬이면 `network error`이고, 개발자 도구 콘솔에는 `ERR_INCOMPLETE_CHUNKED_ENCODING`이 찍히기도 한다. 서버 로그에 아무 에러가 없는데 클라이언트만 끊겼다면 둘 사이의 장비다.

"서버 메모리가 계속 는다"면 끊긴 스트림의 핸들러가 남아 있는지 본다. 앞의 `drain` 대기처럼 끝나지 않은 Promise가 쌓이는 경우다. 진행 중인 스트림 수를 지표로 남기고, 그 수가 실제 접속 수보다 계속 커지면 정리 코드가 빠진 것이다.

## 응답을 끝내지 않는 것뿐이다

HTTP 스트리밍은 새 프로토콜이 아니라 응답을 끝내지 않고 이어 쓰는 것뿐이다. HTTP/1.1은 chunked로, HTTP/2는 DATA 프레임으로 조각을 나르고, 그 위에 NDJSON이나 SSE 같은 메시지 규칙을 얹는다. 받는 쪽은 조각을 버퍼에 이어 붙여 메시지 경계에서 자르고, 끝 메시지가 와야 성공으로 친다. 보내는 쪽은 배압을 지키고 끊김을 감지해 일을 멈춘다. 그 사이의 프록시는 실시간 경로에서만 버퍼를 끈다. 이 네 가지가 갖춰지면 내보내기도 LLM 답변도 같은 코드 모양으로 풀린다.

## 면접에서 나올 만한 질문

### HTTP 스트리밍은 어떻게 동작하나요?

응답 헤더를 먼저 보내고 본문을 다 만들기 전에 조금씩 이어 보내는 방식이다. HTTP/1.1에서는 `Content-Length` 대신 `Transfer-Encoding: chunked`로 조각마다 16진수 길이를 붙이고 길이 0인 조각으로 끝을 알린다. HTTP/2와 HTTP/3는 chunked가 없고 DATA 프레임과 END_STREAM 플래그로 같은 일을 한다. 그 위에 NDJSON이나 SSE 같은 메시지 형식을 얹어 쓴다.

### fetch로 스트림을 읽을 때 주의할 점은요?

`read()`로 받는 조각의 경계가 메시지 경계와 맞지 않는다. 느린 스트림에서는 우연히 한 줄씩 오지만, 빠른 스트림에서는 64KB 안팎으로 묶여 오고 줄 중간에서 잘린다. 그래서 버퍼에 이어 붙이고 줄바꿈이나 빈 줄에서 잘라야 하며, 여러 바이트 글자가 조각 사이에 걸릴 수 있으니 `TextDecoderStream`이나 `stream: true` 옵션으로 디코딩한다. 스트림이 끝났을 때 남은 버퍼도 처리한다.

### 스트리밍 도중 서버에서 에러가 나면 클라이언트는 어떻게 알 수 있나요?

상태 코드는 이미 200으로 나갔으니 상태 코드로는 알릴 수 없다. 연결이 비정상으로 끊기면 curl은 exit 18, fetch는 `read()`에서 에러를 던지지만, 서버가 예외를 잡고 정상 종료해 버리면 구분이 안 된다. 그래서 프로토콜에 끝 메시지(`done`, `[DONE]`)와 에러 메시지를 따로 두고, 끝 메시지 없이 끝난 스트림은 실패로 처리한다. 권한·검증처럼 미리 알 수 있는 실패는 첫 바이트를 쓰기 전에 끝낸다.

### 큰 응답을 스트리밍하면 무엇이 좋아지나요? 주의할 점은요?

첫 바이트 시간과 서버 메모리가 줄어든다. 100만 행 내보내기에서 통째로 만들면 첫 바이트 1.5초에 메모리 정점 523MB였고, 스트리밍하면 0.01초에 46MB였다. 다만 한 행마다 write하면 호출 비용 때문에 전체 시간이 오히려 늘어서, 수백 행씩 묶어 썼다. `write()`가 false를 주면 `drain`까지 기다리는 배압을 지켜야 메모리가 다시 늘지 않는다.

### 배압을 직접 구현할 때 흔한 실수는요?

`drain`만 기다리고 연결 끊김을 처리하지 않는 것이다. 클라이언트가 떠나면 응답 객체는 `error`가 아니라 `close`를 내므로 `drain`을 기다리는 Promise가 영원히 남고, 잡고 있던 DB 커서나 커넥션도 같이 남는다. `stream.pipeline`으로 생성기와 응답을 이으면 배압과 끊김을 함께 처리해 주고, 끊기면 `ERR_STREAM_PREMATURE_CLOSE`로 빠져나와 정리할 수 있다.

### LLM 답변 스트리밍에서 사용자가 중지를 누르면 서버는 무엇을 해야 하나요?

브라우저가 `AbortController`로 fetch를 끊으면 앱 서버의 응답 객체에 `close`가 오고, 앱 서버는 그걸 보고 LLM API 쪽 요청도 끊어야 한다. 이걸 빠뜨리면 아무도 보지 않는 답을 끝까지 생성하고 그 토큰 비용을 낸다. SDK를 쓴다면 요청의 `AbortSignal`을 SDK 호출에 넘기는 방식으로 잇는다.

### 프록시 버퍼링은 왜 기본으로 켜져 있고, 언제 끄나요?

느린 클라이언트로부터 앱 서버를 보호하려고 켜져 있다. 실습에서 버퍼링을 켜면 앱은 95MB를 0.9초 만에 넘기고 손을 뗐고, nginx가 임시 파일에 받아 두었다가 느린 클라이언트에게 천천히 보냈다. 끄면 앱이 3.9초 동안 클라이언트 속도에 묶였다. 그래서 LLM 토큰, 진행 상황, SSE처럼 사람이 실시간으로 보는 경로만 `proxy_buffering off`나 `X-Accel-Buffering: no`로 끈다.

### SSE, NDJSON 스트림, WebSocket 중 무엇을 고르나요?

서버에서 클라이언트로만 흐르고 브라우저가 GET으로 구독하며 재연결과 이어 받기가 필요하면 SSE와 `EventSource`가 가장 적은 코드로 된다. POST 본문이나 인증 헤더가 필요하거나, 한 번 받고 끝나는 스트림이거나, 브라우저가 아닌 프로그램이 읽는다면 fetch로 읽는 NDJSON이 단순하다. 클라이언트도 자주 짧게 말하는 채팅·게임·공동 편집이라면 WebSocket을 고른다.
