[Partition Equal Subset Sum](https://leetcode.com/problems/partition-equal-subset-sum/)은 LeetCode 416번이다. 문제는 "두 묶음으로 똑같이 나눌 수 있나"지만, 한 번만 생각을 돌리면 "합이 전체의 절반인 부분집합이 있나"가 된다. 여기서부터는 물건마다 넣을지 말지 정하는 0/1 배낭 문제(0/1 knapsack, 각 물건을 한 번만 쓸 수 있는 배낭 채우기)다. 이 글은 모든 부분집합을 대 보는 풀이에서 시작해 메모, 2차원 표, 1차원 표, 합 집합, 비트셋까지 여섯 가지를 놓는다. 1차원 표에서 반복 방향을 거꾸로 도는 이유가 이 문제의 가장 중요한 대목이다.

같은 배낭 모양이지만 동전을 몇 번이고 다시 쓸 수 있는 [Coin Change](/posts/leetcode-coin-change)와 비교하면 반복 방향 이야기가 더 선명해진다. DP의 기본은 [동적 계획법 글](/posts/dynamic-programming)에 있다. 코드는 Node.js 22, Python 3, Java 21에서 직접 돌렸다.

## 같은 합의 두 묶음으로 나눌 수 있나

양의 정수 배열 `nums`가 주어진다. 원소를 하나도 빠짐없이 두 묶음으로 나눠서 두 묶음의 합이 같게 만들 수 있으면 `true`, 아니면 `false`를 돌려준다. 원소의 순서를 지킬 필요는 없고, 각 원소는 정확히 한 묶음에 들어간다.

제약은 길이 1 이상 200 이하, 값 1 이상 100 이하다. 이 두 숫자가 풀이를 정한다. 길이 200이라 부분집합 2^200개를 다 보는 건 꿈도 못 꾼다. 대신 값이 작아서 전체 합이 많아야 200 × 100 = 20,000이고, 절반은 10,000이다. "만들 수 있는 합"을 칸으로 두면 칸이 1만 개라 넉넉하다. 원소 수가 아니라 합의 크기에 기대는 풀이가 가능한 이유다.

## 절반을 만드는 부분집합 하나만 찾으면 된다

두 묶음 A, B의 합이 같다면 각각 전체 합 `total`의 절반이다. 그러니 A의 합이 `total / 2`가 되도록 원소를 고를 수만 있으면 나머지가 B가 되고, B의 합도 자동으로 `total - total / 2 = total / 2`다. 두 묶음을 동시에 신경 쓸 필요가 없다.

여기서 바로 걸러지는 경우가 있다.

- `total`이 홀수면 절반이 정수가 아니니 무조건 `false`다.
- 가장 큰 원소가 절반보다 크면 그 원소가 든 묶음이 절반을 넘으니 `false`다. 이건 따로 검사하지 않아도 뒤의 풀이가 알아서 `false`를 낸다.
- 원소가 하나뿐이면 다른 묶음이 비어 합이 0이 된다. 값이 1 이상이라 늘 `false`다.

## 다섯 수를 손으로 나눠 본다

글 끝까지 쓸 예시다.

```text
nums   1   5   3   4   3
합     16   →  절반 8
```

8을 만드는 부분집합을 찾는다. 5 + 3 = 8이 바로 보인다. 그러면 나머지 1 + 4 + 3 = 8이다. 두 묶음 `[5, 3]`과 `[1, 4, 3]`, 답은 `true`다.

`false`가 나오는 경우도 하나 보자. `[1, 2, 5]`는 합이 8이라 절반 4를 만들어야 한다. 1, 2, 1 + 2 = 3은 되지만 4는 안 되고, 5는 혼자서 4를 넘는다. 답은 `false`다.

크게 나누는 탐욕은 통하지 않는다. 큰 수부터 합이 작은 쪽 묶음에 넣는 방법을 `[3, 3, 2, 2, 2]`에 쓰면 3, 3이 양쪽에 하나씩 가고 2, 2, 2가 3 : 2로 갈려 7 : 5가 된다. 하지만 `[3, 3]`과 `[2, 2, 2]`로 나누면 6 : 6이다. 한 번 넣은 걸 되돌릴 방법이 없는 탐욕은 이런 입력을 놓친다.

## 모든 부분집합을 대 본다

원소 n개의 부분집합을 n비트 정수로 나타내고, 합이 절반인 게 있는지 하나씩 본다.

```js
function canPartition(nums) {
  const n = nums.length;
  const total = nums.reduce((a, b) => a + b, 0);
  if (total % 2 !== 0) return false;      // 홀수면 반으로 못 나눈다
  const target = total / 2;
  for (let mask = 0; mask < (1 << n); mask++) {
    let sum = 0;
    for (let i = 0; i < n; i++) if ((mask >> i) & 1) sum += nums[i];
    if (sum === target) return true;      // 이 부분집합이 한쪽 묶음
  }
  return false;
}
```

시간은 O(2ⁿ × n), 공간은 O(1)이다. n이 20이면 약 2,000만 번이라 버틸 만하지만, 30을 넘으면 JavaScript의 32비트 비트 연산부터 깨지고 시간도 감당이 안 된다. 길이 200은 불가능하다. 그래도 길이 12 정도의 무작위 배열로 뒤의 빠른 풀이를 검증할 때 기준이 된다.

## 넣을지 말지 정하며 남은 합을 줄인다

부분집합을 한꺼번에 고르지 말고, 원소를 앞에서부터 하나씩 보며 "이걸 묶음에 넣을까, 말까"를 정한다고 생각하자. `go(i, rem)`을 "i번 원소부터 뒤를 써서 합 rem을 정확히 만들 수 있나"로 정한다.

1. `rem`이 0이면 이미 다 만들었다. `true`.
2. 원소가 다 떨어졌거나 `rem`이 음수가 되면 실패다. `false`.
3. 그 외에는 i번을 넣는 길 `go(i+1, rem - nums[i])`와 안 넣는 길 `go(i+1, rem)` 중 하나라도 되면 된다.

이대로면 여전히 2ⁿ갈래다. 하지만 `(i, rem)` 쌍은 많아야 n × (target + 1)개라, 한 번 구한 답을 적어 두면 같은 쌍을 다시 계산하지 않는다.

```js
function canPartition(nums) {
  const total = nums.reduce((a, b) => a + b, 0);
  if (total % 2 !== 0) return false;
  const target = total / 2;
  const n = nums.length;
  const memo = new Map();                    // (i, rem) → 결과
  function go(i, rem) {
    if (rem === 0) return true;              // 다 만들었다
    if (i === n || rem < 0) return false;    // 원소가 없거나 넘쳤다
    const key = i * (target + 1) + rem;      // 두 수를 하나의 키로
    if (memo.has(key)) return memo.get(key);
    const res = go(i + 1, rem - nums[i])     // i번을 넣는다
             || go(i + 1, rem);              // i번을 안 넣는다
    memo.set(key, res);
    return res;
  }
  return go(0, target);
}
```

상태가 O(n × target)개, 상태마다 O(1)이라 시간 O(n × target)이고 공간도 그만큼이다. 최악이면 200 × 10,001 ≈ 200만 개 상태가 `Map`에 들어간다. 돌아가기는 하지만 `Map`에 숫자 키 200만 개를 넣는 건 배열보다 훨씬 무겁다. 재귀 깊이는 n = 200이라 문제없다.

`||`가 앞쪽에서 `true`를 받으면 뒤쪽을 계산하지 않는다는 점도 쓸모 있다. 답을 하나 찾는 순간 위로 `true`가 올라가며 남은 갈래를 모두 건너뛴다.

여기서 "O(n × target)이면 다항 시간인가"라는 꼬리 질문이 나올 수 있다. 아니다. 이 문제의 일반형(Partition Problem)은 NP-완전이다. target은 입력의 "값"이지 "길이"가 아니라서, 값이 10^9처럼 커지면 칸 수가 폭발한다. 이런 걸 의사 다항 시간(pseudo-polynomial)이라고 부른다. 이 문제는 값이 100 이하라서 빠른 것이다.

## 원소마다 한 줄씩 만들 수 있는 합을 적는다

메모를 반복문으로 옮긴다. `dp[i][s]`를 "앞의 i개 원소 중 몇 개를 골라 합 s를 만들 수 있나"로 정한다.

```text
dp[0][0] = true                       아무것도 안 골라도 합 0은 된다
dp[i][s] = dp[i-1][s]                 i번째 원소를 안 쓴다
        또는 dp[i-1][s - x]           i번째 원소 x를 쓴다 (s ≥ x일 때)
```

```js
function canPartition(nums) {
  const total = nums.reduce((a, b) => a + b, 0);
  if (total % 2 !== 0) return false;
  const target = total / 2;
  const n = nums.length;
  const dp = Array.from({ length: n + 1 }, () => new Array(target + 1).fill(false));
  dp[0][0] = true;                                   // 합 0은 늘 만들 수 있다
  for (let i = 1; i <= n; i++) {
    const x = nums[i - 1];
    for (let s = 0; s <= target; s++) {
      dp[i][s] = dp[i - 1][s]                        // x를 안 쓴다
              || (s >= x && dp[i - 1][s - x]);       // x를 쓴다
    }
  }
  return dp[n][target];
}
```

예시에서 줄마다 참인 칸을 적으면 이렇다.

```text
i  x   만들 수 있는 합
0  -   0
1  1   0 1
2  5   0 1 5 6
3  3   0 1 3 4 5 6 8
4  4   0 1 3 4 5 6 7 8
5  3   0 1 3 4 5 6 7 8
```

세 번째 줄에서 이미 8이 생겼다. 5 + 3이다. 시간 O(n × target), 공간 O(n × target)이다. 표가 남아 있으니 마지막 줄에서 거꾸로 올라가며 어떤 원소를 골랐는지도 되짚을 수 있다(뒤의 "묶음을 실제로 꺼내라면"에서 다룬다).

이 표를 보면 i번째 줄은 바로 윗줄 하나만 본다. 그러면 줄을 하나만 두고 덮어써도 될 것 같다. 된다. 다만 덮어쓰는 방향을 틀리면 답이 틀린다.

## 한 줄로 줄이려면 큰 합부터 내려간다

`dp[s]` 한 줄만 둔다. "지금까지 본 원소로 합 s를 만들 수 있나"다. 원소 x를 하나 볼 때마다 `dp[s - x]`가 참인 s마다 `dp[s]`를 참으로 만든다.

여기서 s를 작은 쪽부터 올라가며 갱신하면 문제가 생긴다. `dp[s - x]`가 방금 이 x로 참이 된 칸일 수 있다. 그러면 x를 두 번 쓴 셈이 된다. 큰 s부터 내려가면 `dp[s - x]`는 아직 이번 x로 건드리지 않은 칸이라, 윗줄(x를 보기 전) 값 그대로다.

앞으로 가는 코드는 `[1, 2, 5]`에 `true`, `[1, 1, 4]`에도 `true`를 낸다(둘 다 답은 `false`). 같은 원소를 몇 번이고 쓸 수 있는 문제, 예를 들어 [Coin Change](/posts/leetcode-coin-change)나 [Coin Change II](/posts/leetcode-coin-change-ii)에서는 오히려 이 "앞으로" 방향이 정답이다. 한 번만 쓰면 뒤로, 여러 번 쓰면 앞으로. 반복 방향 하나가 0/1 배낭과 무한 배낭을 가른다.

```js
function canPartition(nums) {
  const total = nums.reduce((a, b) => a + b, 0);
  if (total % 2 !== 0) return false;          // 홀수면 반으로 못 나눈다
  const target = total / 2;
  const dp = new Array(target + 1).fill(false); // dp[s] = 합 s를 만들 수 있나
  dp[0] = true;                               // 아무것도 안 고르면 합 0
  for (const x of nums) {
    for (let s = target; s >= x; s--) {       // 큰 합부터: x를 한 번만 쓴다
      if (dp[s - x]) dp[s] = true;
    }
    if (dp[target]) return true;              // 절반이 생기면 더 볼 필요 없다
  }
  return dp[target];
}
```

`s >= x`에서 멈추니 x보다 작은 칸은 건드리지 않는다. x가 target보다 크면 안쪽 반복이 한 번도 안 돈다. 가장 큰 원소가 절반을 넘는 경우를 따로 거르지 않아도 되는 이유다.

시간은 O(n × target), 공간은 O(target)이다. 면접에서 기본으로 내놓을 답이 이것이다. 길이 1부터 12까지, 값 1부터 15까지 무작위 배열 2,000개로 이 글의 여섯 풀이가 모두 같은 답을 내는지 맞춰 봤다.

일찍 끝내는 `if (dp[target]) return true`는 복잡도를 바꾸지 않지만 실제 시간을 꽤 줄인다. 답이 `true`인 입력에서 앞쪽 원소 몇 개로 절반이 만들어지면 나머지를 안 본다. `false`인 입력은 끝까지 가야 하니 최악은 그대로다.

## 만들 수 있는 합만 모아 둔다

1차원 표는 만들 수 없는 합의 칸도 모두 들고 있다. 대신 "지금까지 만들 수 있는 합"만 집합에 넣어 두는 방법도 있다. 원소 x를 볼 때마다 기존 합마다 x를 더한 값을 새로 넣는다.

```js
function canPartition(nums) {
  const total = nums.reduce((a, b) => a + b, 0);
  if (total % 2 !== 0) return false;
  const target = total / 2;
  let sums = new Set([0]);                 // 지금까지 만들 수 있는 합
  for (const x of nums) {
    const next = new Set(sums);            // x를 안 쓰는 경우: 기존 합 그대로
    for (const s of sums) {
      if (s + x === target) return true;   // 절반에 닿았다
      if (s + x < target) next.add(s + x); // 절반을 넘는 합은 버린다
    }
    sums = next;
  }
  return sums.has(target);
}
```

기존 집합 `sums`를 돌면서 새 집합 `next`에 넣으니, 같은 x를 두 번 쓰는 일이 처음부터 없다. 1차원 표의 "뒤로 가기"를 집합 복사로 대신한 셈이다.

복잡도는 집합 크기가 많아야 target + 1이라 최악 O(n × target)으로 같다. 만들 수 있는 합이 적은 입력, 예를 들어 같은 값이 많이 반복되는 입력에서는 집합이 작아 빠르다. 반대로 합이 고르게 퍼지면 해시 집합의 비용이 배열보다 커서 느리다. 값의 범위는 크지만 원소 수가 적을 때 떠올리면 좋은 모양이다.

## 비트 하나를 합 하나로 쓴다

1차원 표의 `dp[s]`는 참·거짓 한 칸이다. 이걸 정수의 s번 비트로 두면 "기존 합마다 x를 더한다"가 비트를 x칸 왼쪽으로 미는 연산 하나가 된다.

```text
bits = 1                     0번 비트만 켜짐: 합 0
bits |= bits << x            켜진 비트마다 x칸 위 비트도 켠다
```

`bits << x`의 각 켜진 비트는 "기존 합 + x"다. 원래 `bits`와 OR하면 x를 안 쓴 합과 쓴 합이 한꺼번에 모인다. 한 번의 시프트가 기존 `bits`로 계산되니 같은 x를 두 번 쓰지도 않는다. JavaScript는 일반 숫자가 32비트 연산이라 1만 비트를 담으려면 `BigInt`를 쓴다.

```js
function canPartition(nums) {
  const total = nums.reduce((a, b) => a + b, 0);
  if (total % 2 !== 0) return false;
  let bits = 1n;                               // BigInt: 0번 비트 = 합 0
  for (const x of nums) bits |= bits << BigInt(x);
  return ((bits >> BigInt(total / 2)) & 1n) === 1n; // 절반 자리 비트가 켜졌나
}
```

예시에서 `true`, `[1, 2, 5]`에서 `false`가 나왔다. 시간은 이론상 O(n × total / w)다. w는 컴퓨터가 한 번에 처리하는 비트 수(보통 64)라서, 같은 일을 64칸씩 묶어 처리한다. 값 1~100 무작위 200개로 Python에서 재 보니 1차원 표가 한 번에 약 37ms, 비트 풀이가 약 0.12ms였다. 비트 연산이 C로 짜인 큰 정수 연산 안에서 돌아서 차이가 특히 크다.

이 풀이는 절반을 넘는 비트도 계속 들고 다닌다. 그래서 `total`까지의 비트가 생기는데, 길이 20,000 비트 정도라 문제는 없다. 정말 아끼려면 매번 `bits & ((1n << BigInt(target + 1)) - 1n)`로 잘라 낸다.

## Python과 Java로 쓴 1차원 표와 비트셋

```python
from typing import List

class Solution:
    def canPartition(self, nums: List[int]) -> bool:
        total = sum(nums)
        if total % 2:                       # 홀수면 반으로 못 나눈다
            return False
        target = total // 2
        dp = [False] * (target + 1)         # dp[s] = 지금까지 본 수로 합 s를 만들 수 있나
        dp[0] = True
        for x in nums:
            for s in range(target, x - 1, -1):  # 큰 합부터 내려가야 x를 한 번만 쓴다
                if dp[s - x]:
                    dp[s] = True
            if dp[target]:
                return True
        return dp[target]
```

`range(target, x - 1, -1)`은 target부터 x까지 내려간다. 끝 값은 포함하지 않으니 `x - 1`을 써야 x가 들어간다. 여기서 `range(target, x, -1)`로 쓰면 `dp[x]`를 켜지 못해 x 하나만으로 만드는 합을 놓친다. `[2, 2]`와 `[3, 3]`에서 `False`가 나온다. Python은 정수 크기 제한이 없어서 비트 풀이가 특히 깔끔하다.

```python
    def canPartitionBits(self, nums: List[int]) -> bool:
        total = sum(nums)
        if total % 2:
            return False
        bits = 1                            # 0번 비트: 합 0은 늘 만들 수 있다
        for x in nums:
            bits |= bits << x               # 기존 합마다 x를 더한 합을 한꺼번에 켠다
        return (bits >> (total // 2)) & 1 == 1
```

```java
class Solution {
    public boolean canPartition(int[] nums) {
        int total = 0;
        for (int x : nums) total += x;
        if (total % 2 != 0) return false;           // 홀수면 반으로 못 나눈다
        int target = total / 2;
        boolean[] dp = new boolean[target + 1];     // 기본값 false
        dp[0] = true;
        for (int x : nums) {
            for (int s = target; s >= x; s--) {     // 큰 합부터 내려간다
                if (dp[s - x]) dp[s] = true;
            }
            if (dp[target]) return true;
        }
        return dp[target];
    }
}
```

Java의 `boolean[]`은 만들 때 모두 `false`라 따로 채울 필요가 없다. 합은 많아야 20,000이라 `int`로 충분하다. 비트셋으로 쓰려면 `java.util.BitSet`에는 왼쪽 시프트가 없어서 `long[]`을 직접 밀거나 `BigInteger`를 쓴다. `bits = bits.or(bits.shiftLeft(x))` 후 `bits.testBit(total / 2)`로 확인하면 되고, 이 코드도 앞의 입력들에서 같은 답을 냈다. 세 언어 모두 예시에 `true`, `[1, 2, 5]`와 `[1]`에 `false`가 나왔다.

## 여섯 풀이를 칸 수로 비교하면

|---|---|---|---|
| 모든 부분집합 | O(2ⁿ × n) | O(1) | n이 20 안쪽일 때 정답 확인용 |

## 배낭을 잘못 채우는 코드

### 작은 합부터 올라가며 갱신하는 경우

```js
for (const x of nums) {
  for (let s = x; s <= target; s++) {   // 앞으로 간다
    if (dp[s - x]) dp[s] = true;
  }
}
```

그림에서 본 실수다. 같은 원소를 여러 번 쓰게 돼서 `[1, 2, 5]`에서 2 + 2 = 4를, `[1, 1, 4]`에서 1 + 1 + 1 = 3을 만들어 `true`를 낸다. 2차원 표를 1차원으로 줄일 때 "윗줄을 읽어야 하는데 이미 덮어쓴 칸을 읽고 있지 않나"를 확인하는 습관이 필요하다.

### 합이 홀수인지 안 보는 경우

`total / 2`가 소수가 된다. JavaScript에서 `new Array(4.5)`는 `RangeError`를 던지고, Java와 Python에서 정수 나눗셈을 쓰면 4가 되어 엉뚱하게 합 4를 찾는다. `[1, 2, 4]`는 합 7인데 절반을 3으로 내림하면 1 + 2 = 3을 찾아 `true`를 낸다. 홀수 검사가 맨 앞에 와야 한다.

### 탐욕으로 큰 수부터 나누는 경우

큰 수부터 합이 작은 쪽에 넣는 방법은 `[3, 3, 2, 2, 2]`에서 `false`를 낸다(답 `true`). 정렬해서 앞에서부터 절반이 될 때까지 더하는 방법도 `[3, 3, 2, 2, 2]`에서 3 + 3 = 6을 바로 찾아 맞는 것처럼 보이지만, `[1, 5, 3, 4, 3]`을 정렬한 `[1, 3, 3, 4, 5]`에서 1 + 3 + 3 = 7, 다음 4를 더하면 11이라 8을 건너뛴다. 원소를 고르는 조합이 필요한 문제라 DP나 전수 탐색이 필요하다.

### 메모 키를 문자열로 만드는 경우

`` `${i},${rem}` ``처럼 문자열 키를 쓰면 상태 200만 개마다 문자열을 만들어 느리다. 답은 맞는다. `i * (target + 1) + rem`처럼 숫자 하나로 묶거나 2차원 배열을 쓰면 된다.

## 배낭의 모양이 바뀌면

### 두 묶음을 실제로 꺼내라면

2차원 표를 남겨 두고 마지막 줄의 target에서 거꾸로 올라간다. `dp[i-1][s]`가 참이면 i번째 원소를 안 써도 되니 그냥 올라가고, 거짓이면 반드시 썼으니 그 원소를 고르고 s에서 x를 뺀다. 예시에서는 `[5, 3]`이 한쪽 묶음으로 나온다.

```js
function partitionPick(nums) {
  const total = nums.reduce((a, b) => a + b, 0);
  if (total % 2 !== 0) return null;
  const t = total / 2, n = nums.length;
  const dp = Array.from({ length: n + 1 }, () => new Array(t + 1).fill(false));
  dp[0][0] = true;
  for (let i = 1; i <= n; i++) {
    const x = nums[i - 1];
    for (let s = 0; s <= t; s++) dp[i][s] = dp[i - 1][s] || (s >= x && dp[i - 1][s - x]);
  }
  if (!dp[n][t]) return null;
  const pick = [];
  for (let i = n, s = t; i >= 1; i--) {
    if (!dp[i - 1][s]) {          // 이 원소 없이는 s를 못 만든다: 썼다
      pick.push(nums[i - 1]);
      s -= nums[i - 1];
    }
  }
  return pick.reverse();
}
```

예시에 `[5, 3]`, `[3, 3, 2, 2, 2]`에 `[3, 3]`, `[1, 2, 5]`에 `null`이 나왔다. 뒤에서부터 "안 써도 되면 안 쓴다"로 올라가니 앞쪽 원소로 이뤄진 묶음이 나온다. 1차원 표로는 어떤 원소로 칸이 켜졌는지 남지 않아서 이 되짚기를 못 한다. 칸마다 "처음 켠 원소의 번호"를 따로 적어 두면 1차원으로도 할 수 있다.

### k개의 같은 합 묶음으로 나누라면

LeetCode 698 Partition to K Equal Sum Subsets다. 절반 하나를 찾는 것으로는 부족하고 묶음 k개를 동시에 채워야 해서, 배낭 DP가 그대로 통하지 않는다. 큰 수부터 정렬해 묶음에 하나씩 넣어 보는 [백트래킹](/posts/recursion-backtracking)이나, 쓴 원소 집합을 비트마스크로 두는 O(2ⁿ × n) DP로 푼다. 이 문제는 n이 16 이하라 그게 가능하다.

### 두 묶음의 합 차이를 최소로 하라면

LeetCode 1049 Last Stone Weight II가 이 모양이다. 같은 1차원 표를 채운 뒤, 절반 이하에서 만들 수 있는 가장 큰 합 s를 찾으면 차이는 `total - 2s`다. `[1, 2, 5]`면 절반 4 이하에서 가장 큰 합이 3이라 차이는 8 - 6 = 2다.

```js
function lastStoneWeightII(stones) {
  const total = stones.reduce((a, b) => a + b, 0);
  const half = Math.floor(total / 2);          // 홀수여도 된다: 절반 이하에서 찾는다
  const dp = new Array(half + 1).fill(false);
  dp[0] = true;
  for (const x of stones) {
    for (let s = half; s >= x; s--) if (dp[s - x]) dp[s] = true; // 이 글과 같은 뒤로 가기
  }
  let s = half;
  while (!dp[s]) s--;                          // 절반 이하에서 만들 수 있는 가장 큰 합
  return total - 2 * s;                        // 두 묶음의 차이
}
```

`[1, 2, 5]`에 2, 이 글의 예시에 0, `[2, 7, 4, 1, 8, 1]`에 1이 나왔다. 차이가 0이면 이 글의 답이 `true`라는 뜻이니, 원래 문제는 이 문제의 특별한 경우다. 여기서는 합이 홀수여도 바로 끝내지 않고 절반을 내림해 찾는다는 점만 다르다.

### 각 수에 +나 -를 붙여 목표를 만들라면

[Target Sum](/posts/leetcode-target-sum)(494)이다. + 쪽 묶음의 합을 P, - 쪽을 N이라 하면 P - N = 목표, P + N = 전체 합이라 P = (전체 + 목표) / 2다. "합이 P인 부분집합의 개수"를 세는 문제로 바뀌고, 이 글의 1차원 표에서 참·거짓 대신 개수를 더하면 된다(`dp[s] += dp[s - x]`). 이때도 반복 방향은 뒤로다. `[1, 1, 1, 1, 1]`에서 목표 3이면 P = 4라 1 다섯 개 중 넷을 고르는 5가지, 이 글의 예시에서 목표 0이면 P = 8을 만드는 부분집합 4가지가 나왔다. (전체 + 목표)가 홀수이거나 목표의 절댓값이 전체보다 크면 0이다.

### 값이 아주 크거나 음수라면

값이 10^9쯤이면 칸이 너무 많아 표를 못 쓴다. 원소 수가 40 이하라면 반으로 나눠 각각 2^20개 부분집합 합을 구하고, 한쪽을 정렬해 다른 쪽에서 짝을 [이분 탐색](/posts/binary-search)하는 meet in the middle로 O(2^(n/2) × n)에 푼다. 음수가 섞이면 표의 인덱스가 음수가 되니 가장 작은 합만큼 밀어 주거나 합 집합 풀이를 쓴다.

비슷한 문제로는 [Target Sum](/posts/leetcode-target-sum), [Coin Change II](/posts/leetcode-coin-change-ii)(무한 배낭과의 대비), Partition to K Equal Sum Subsets(698), Last Stone Weight II(1049), Ones and Zeroes(474)가 있다.

## 면접에서 나올 만한 질문

### 이 문제를 어떻게 배낭 문제로 바꿨나요?

두 묶음의 합이 같으면 각각 전체의 절반이니, 합이 절반인 부분집합이 있는지만 보면 된다. 나머지는 자동으로 다른 묶음이 된다. 원소마다 넣을지 말지 한 번만 정하니 0/1 배낭이고, 합이 홀수면 바로 `false`다.

### 1차원 표에서 왜 큰 합부터 내려가나요?

`dp[s]`를 갱신할 때 읽는 `dp[s - x]`가 이번 원소를 보기 전 값이어야 하기 때문이다. 작은 쪽부터 올라가면 방금 이 원소로 켠 칸을 다시 읽어 같은 원소를 여러 번 쓴다. `[1, 2, 5]`에서 2 + 2 = 4를 만들어 틀린 `true`가 나온다. 동전처럼 여러 번 써도 되는 문제라면 반대로 앞으로 가야 맞다.

### 시간 복잡도가 다항 시간인가요?

O(n × target)이지만 target은 입력값의 크기라서 의사 다항 시간이다. 일반형인 분할 문제는 NP-완전이고, 값이 작다는 제약(1~100) 덕분에 칸 수가 1만 개로 묶여 빠른 것이다. 값이 10^9처럼 커지면 이 풀이는 쓸 수 없다.

### 더 빠르게 할 수 있나요?

참·거짓 칸을 비트로 두면 `bits |= bits << x` 한 줄로 원소 하나를 처리해 64칸씩 묶어 계산한다. 복잡도의 상수가 64분의 1쯤으로 줄고, Python에서 재 보면 1차원 표보다 수백 배 빨랐다. 합이 절반에 닿으면 일찍 끝내는 것도 `true`인 입력에서 실제 시간을 줄인다.

### 어떤 원소를 골랐는지도 알려 달라면요?

2차원 표를 남겨 두고 마지막 줄의 절반 칸에서 거꾸로 올라간다. 윗줄의 같은 칸이 거짓이면 그 원소를 반드시 썼으니 고르고 합에서 뺀다. 1차원 표로는 이 정보가 남지 않아 공간이 O(n × target)으로 늘어난다.

### 탐욕으로는 왜 안 되나요?

한 번 넣은 원소를 되돌리지 못해서다. 큰 수부터 합이 작은 쪽에 넣으면 `[3, 3, 2, 2, 2]`에서 7 : 5가 되는데, 실제로는 `[3, 3]`과 `[2, 2, 2]`로 6 : 6이 된다. 원소 조합을 따져야 해서 DP가 필요하다.
