버그를 고쳐서 배포했다. 그런데 한 사용자가 아직도 예전 화면이 보인다고 한다. 새로고침을 해도 그대로다. 개발자 도구를 열어 Network 탭을 보면 HTML 줄의 Size 칸에 `(ServiceWorker)`라고 적혀 있다. 서버까지 가지도 않고 브라우저 안에서 응답이 끝난 것이다.

반대 방향의 불만도 있다. 모바일에서 두 번째 방문인데도 첫 방문만큼 느리다는 것이다. 같은 파일을 왜 또 받는지, 받았다면 어디에 두었다가 왜 버렸는지가 궁금해진다.

두 문제 모두 "브라우저 안 어디에 무엇이 남아 있는가"의 문제다. 프런트엔드 개발자가 손댈 수 있는 캐시는 생각보다 여러 겹이고, 겹마다 규칙과 수명이 다르다. 이 글은 사용자의 브라우저를 기준으로 그 겹들을 하나씩 열어 본다.

## 요청 하나가 거치는 캐시들

페이지가 이미지 하나를 요청하면 브라우저는 응답을 찾으러 여러 곳을 차례로 들른다. 크롬 계열을 기준으로 흔히 설명하는 순서는 아래와 같다. 다른 엔진도 큰 줄기는 같지만 세부 구현은 다르다.

맨 앞의 메모리 캐시는 렌더러 프로세스 안에 있다. 같은 문서가 같은 이미지를 두 번 쓰거나, preload로 미리 받아 둔 파일을 곧 쓰는 경우처럼 지금 열린 페이지 안에서 재사용할 때 걸린다. 탭을 닫으면 사라진다. 개발자 도구 Network 탭의 Size 칸에 `(memory cache)`로 보인다.

그 뒤가 Service Worker다. 사이트가 등록해 두었다면 요청이 여기로 먼저 들어오고, Service Worker는 Cache Storage에서 꺼내 주든 네트워크로 보내든 마음대로 정한다. 여기서 응답하면 `(ServiceWorker)`로 보인다.

Service Worker가 `fetch()`로 네트워크에 보낸 요청도 HTTP 캐시를 거친다. 이 부분을 자주 놓친다. Service Worker가 있다고 HTTP 캐시가 꺼지는 게 아니다. HTTP 캐시는 디스크에 있고 탭이 닫혀도 남는다. `(disk cache)`가 여기서 온 응답이다. 크롬은 86 무렵부터 이 캐시를 최상위 사이트 단위로 나눠 저장한다. 다른 사이트에서 같은 CDN 주소의 라이브러리를 받았어도 내 사이트에서는 다시 받는다는 뜻이다. 공용 CDN에서 jQuery를 받으면 캐시를 나눠 쓴다는 옛날 이야기는 지금은 맞지 않는다.

그 너머의 CDN과 오리진 서버는 브라우저 밖이다. 그쪽 이야기는 [HTTP 캐시와 CDN](/posts/http-caching-cdn)에서 다뤘다.

## HTTP 캐시는 서버가 정한 기한을 따른다

HTTP 캐시는 응답 헤더가 시키는 대로만 움직인다. 프런트엔드 입장에서 기억할 규칙은 두 줄이다.

```
/_next/static/chunks/main-3f9c2b1e.js   Cache-Control: public, max-age=31536000, immutable
/posts/oauth                            Cache-Control: no-cache   (ETag로 재검증)
```

이름에 내용 해시가 든 정적 파일은 이름이 같으면 내용도 같으니 1년 동안 다시 묻지 않게 한다. 그 이름들을 담은 HTML은 매번 서버에 "아직 그대로인가"를 묻게 한다. 이 둘이 어긋나면 배포 뒤에 옛 화면이 남거나 흰 화면이 뜬다. 헤더 하나하나의 뜻과 재검증 과정은 앞의 글에서 자세히 썼으니 여기서는 넘어간다.

처음 장면의 "모바일에서 재방문도 느리다"는 여기부터 확인한다. 정적 파일에 `max-age`가 없거나 짧으면 재방문 때마다 재검증 왕복이 생긴다. 모바일 네트워크에서는 그 왕복 하나하나가 수백 ms다. 휴대폰의 디스크 캐시는 용량이 작아서 오래된 항목부터 밀려나기도 한다. 그래서 HTTP 캐시만 믿기 어려운 자리에 Service Worker를 둔다.

## 뒤로 가기가 즉시 뜨는 bfcache

HTTP 캐시와 전혀 다른 캐시가 하나 더 있다. 뒤로·앞으로 가기 캐시(back/forward cache, bfcache)다. 페이지를 떠날 때 페이지를 통째로, 자바스크립트 힙과 스크롤 위치까지 메모리에 얼려 둔다. 뒤로 가기를 누르면 다시 받거나 다시 실행하지 않고 녹여서 보여 준다. 그래서 거의 0ms에 뜬다.

얼렸다 녹이는 것이라 페이지 입장에서는 로드 이벤트가 다시 오지 않는다. 대신 `pageshow`가 오고 `event.persisted`가 `true`다. 장바구니 개수처럼 다른 탭에서 바뀌었을 수 있는 값은 여기서 다시 맞춘다.

```js
window.addEventListener("pageshow", (event) => {
  if (event.persisted) {
    // bfcache에서 돌아왔다. 얼어 있던 동안 바뀐 값만 다시 받는다
    refreshCartCount();
  }
});

window.addEventListener("pagehide", (event) => {
  // event.persisted가 true면 bfcache로 들어가는 중이다
  socket.close(); // 열린 연결은 여기서 닫고 pageshow에서 다시 연다
});
```

모든 페이지가 얼려지지는 않는다. 자주 걸리는 원인은 이렇다.

- `unload` 이벤트 리스너. 페이지가 "완전히 사라진다"는 가정 위에 있는 이벤트라 크롬과 파이어폭스는 이 리스너가 있으면 bfcache에 넣지 않는다. 크롬은 `unload` 자체를 단계적으로 없애는 중이다. 떠날 때 할 일은 `pagehide`나 `visibilitychange`로 옮긴다.
- 메인 문서의 `Cache-Control: no-store`. 크롬은 오랫동안 이런 페이지를 bfcache에서 뺐고, 최근 버전에서는 쿠키가 바뀌지 않는 등 조건이 맞으면 허용하는 쪽으로 바뀌고 있다. 브라우저와 버전마다 다르니 단정하지 말고 직접 테스트한다.
- 열린 연결. WebSocket, WebRTC, 끝나지 않은 IndexedDB 트랜잭션 같은 것들은 브라우저에 따라 bfcache를 막거나, 얼리는 순간 연결을 끊어 버린다. 위 코드처럼 `pagehide`에서 정리한다.

확인은 크롬 개발자 도구의 Application 패널에서 한다. Background services 아래 Back/forward cache 항목에서 "Test back/forward cache"를 누르면 다른 페이지로 갔다가 돌아와 보고, 실패하면 막은 이유를 줄줄이 보여 준다. 실제 사용자에게서 모으려면 크롬 123부터 있는 `performance.getEntriesByType("navigation")[0].notRestoredReasons`를 읽는다.

## 페이지 앞에 선 프록시, Service Worker

Service Worker는 페이지와 네트워크 사이에 끼는 작은 자바스크립트다. 페이지와 다른 스레드에서 돌고 DOM에 손댈 수 없다. 그 대신 자기 범위(scope) 안의 페이지가 보내는 모든 요청을 `fetch` 이벤트로 받아서 응답을 직접 만들어 줄 수 있다. 요청을 가로채는 프록시를 브라우저 안에 하나 세우는 셈이다. 그래서 HTTPS(또는 localhost)에서만 등록된다. 중간에서 요청을 바꿀 수 있는 코드를 아무나 심게 둘 수는 없기 때문이다.

이 프록시가 쓰는 저장소가 Cache Storage다. 요청과 응답을 짝으로 넣어 두는 곳인데, HTTP 캐시와 성격이 많이 다르다.

- HTTP 캐시는 헤더를 보고 브라우저가 알아서 넣고 뺀다. Cache Storage는 코드가 `put`한 것만 들어가고, 코드가 `delete`하기 전까지 기한 없이 남는다. `Cache-Control`을 보지 않는다.
- 키는 요청 URL과 메서드다. GET 요청만 넣을 수 있다. 쿼리 문자열이 다르면 다른 항목이다(`match`에 `ignoreSearch`를 주면 무시한다).
- 페이지에서도 `caches`로 읽고 쓸 수 있다. Service Worker 전용이 아니다.

## 설치, 활성화, 가로채기

Service Worker는 정해진 생명주기를 따른다. 이걸 알아야 "왜 새 코드가 안 돌지?"에 답할 수 있다.

1. 페이지가 `navigator.serviceWorker.register("/sw.js")`를 부르면 브라우저가 파일을 받아 `install` 이벤트를 보낸다. 여기서 앞으로 필요할 파일을 미리 캐시에 담는다. `event.waitUntil`에 넘긴 Promise가 실패하면 설치 자체가 실패하고 이 Service Worker는 버려진다.
2. 설치가 끝나면 `activate` 이벤트가 온다. 지난 버전이 쓰던 캐시를 지우는 자리다.
3. 활성화된 뒤부터 범위 안의 페이지 요청이 `fetch` 이벤트로 들어온다.

첫 방문에서 하나 헷갈리는 부분이 있다. 등록을 부른 그 페이지는 Service Worker 없이 이미 로드됐다. 그래서 활성화가 끝나도 그 페이지의 요청은 가로채지 않는다. 다음에 새로 연 페이지부터 가로챈다. 지금 열린 페이지까지 바로 맡으려면 `activate`에서 `self.clients.claim()`을 부른다.

업데이트는 브라우저가 알아서 확인한다. 범위 안의 페이지로 이동할 때마다 `sw.js`를 다시 받아 한 바이트라도 다르면 새 버전으로 보고 설치를 시작한다. 이때 `sw.js` 자체는 HTTP 캐시를 거치지 않는다(`updateViaCache`의 기본값 `"imports"`). 예전에는 `sw.js`에 긴 `max-age`를 줘서 업데이트가 하루씩 늦던 사고가 있었는데, 지금 브라우저는 이 부분을 막아 준다.

## 캐시를 먼저 볼까 네트워크를 먼저 볼까

`fetch` 이벤트에서 응답을 어디서 가져올지 정하는 방식을 전략이라고 부른다. 정답은 없고, 리소스의 성격에 맞춰 고른다.

캐시 우선(cache-first)은 캐시에 있으면 그것을 주고, 없을 때만 네트워크에 간다. 해시가 든 정적 파일, 폰트, 아이콘처럼 같은 주소의 내용이 바뀌지 않는 것에 쓴다. 가장 빠르지만, 같은 주소의 내용이 바뀌는 파일에 쓰면 영원히 옛것을 준다.

```js
async function cacheFirst(request) {
  const cached = await caches.match(request);
  if (cached) return cached;
  const response = await fetch(request);
  if (response.ok) {
    const cache = await caches.open("static");
    await cache.put(request, response.clone()); // 본문은 한 번만 읽히니 복제해서 넣는다
  }
  return response;
}
```

네트워크 우선(network-first)은 늘 네트워크에 먼저 가고, 실패할 때만 캐시를 준다. HTML처럼 최신이어야 하지만 오프라인에서도 뭔가는 보여 줘야 하는 것에 쓴다. 약점은 느린 네트워크다. 연결이 끊긴 게 아니라 느리기만 하면 응답이 올 때까지 하염없이 기다린다. 그래서 시간 제한을 걸고 넘기면 캐시로 넘어가게 만든다.

```js
async function networkFirst(request, timeoutMs = 3000) {
  const cache = await caches.open("pages");
  try {
    const response = await fetch(request, { signal: AbortSignal.timeout(timeoutMs) });
    if (response.ok) await cache.put(request, response.clone());
    return response;
  } catch {
    // 오프라인이거나 3초를 넘겼다
    return (await cache.match(request)) ?? Response.error();
  }
}
```

그 사이에 stale-while-revalidate가 있다. 캐시에 있으면 일단 그걸 바로 주고, 뒤에서 네트워크로 새 응답을 받아 캐시를 바꿔 둔다. 이번 화면은 조금 낡았을 수 있지만 다음 방문은 새것이다. 아바타 이미지, 자주 바뀌지 않는 목록 API처럼 "조금 낡아도 빠른 게 낫다"에 맞는다. 아래 그림에서 "다음"을 누르면 두 갈래가 동시에 움직이는 게 보인다.

```js
function staleWhileRevalidate(event) {
  const network = caches.open("api").then(async (cache) => {
    const response = await fetch(event.request);
    if (response.ok) await cache.put(event.request, response.clone());
    return response;
  });
  event.waitUntil(network.catch(() => {})); // 응답을 준 뒤에도 갱신이 끝날 때까지 살려 둔다
  return caches.match(event.request).then((cached) => cached ?? network);
}

self.addEventListener("fetch", (event) => {
  const url = new URL(event.request.url);
  if (url.pathname === "/api/tags") event.respondWith(staleWhileRevalidate(event));
});
```

나머지 둘은 이름 그대로다. 캐시 전용(cache-only)은 설치 때 담아 둔 것만 쓰고 네트워크에 가지 않는다. 앱 셸처럼 버전과 함께 묶여 들어온 파일에 쓴다. 네트워크 전용(network-only)은 Service Worker가 손대지 않는다. 결제, 로그인, POST 요청처럼 캐시하면 안 되는 것들이다. `fetch` 리스너에서 `respondWith`를 부르지 않고 그냥 돌아가면 그게 네트워크 전용이다.

같은 이름이 HTTP 헤더에도 있다(`Cache-Control: stale-while-revalidate=60`). 생각은 같지만 하는 쪽이 다르다. 헤더는 브라우저와 CDN이 정해진 시간 범위 안에서 해 주는 것이고, Service Worker 쪽은 내가 코드로 범위와 조건을 정한다. 서버 쪽 캐시 전략 전반은 [캐시 전략](/posts/caching-strategies)에서 따로 다룬다.

## 미리 담기와 쓰면서 담기

캐시에 무엇을 언제 넣는지도 둘로 나뉜다.

미리 담기(precaching)는 `install`에서 목록을 정해 한꺼번에 받아 두는 것이다. 오프라인 첫 화면, 앱 셸, 오프라인 안내 페이지처럼 반드시 있어야 하는 것만 넣는다. 목록 중 하나라도 실패하면 설치가 실패하니, 크고 많을수록 설치가 깨지기 쉽다. 그리고 이 다운로드는 첫 방문의 대역폭을 나눠 쓴다. 모바일 첫 방문에 수 MB를 미리 담으면 정작 지금 보는 페이지가 느려진다.

쓰면서 담기(runtime caching)는 `fetch`에서 실제로 쓰인 응답을 그때그때 넣는 것이다. 사용자가 본 것만 들어가니 낭비가 없다. 대신 한 번도 안 본 페이지는 오프라인에서 열리지 않는다. 그리고 넣기만 하고 빼지 않으면 끝없이 자란다. 개수나 나이로 오래된 항목을 지우는 규칙이 같이 있어야 한다.

## 이 블로그의 sw.js 읽기

이 블로그도 Service Worker를 쓴다. `public/sw.js` 전체가 이렇다.

```js
// Matt's Blog service worker.
// - 빌드 산출물(/_next/static), 아이콘, 폰트: 캐시 우선 (파일 이름에 해시가 있어 바뀌지 않는다)
// - 페이지: 네트워크 우선, 실패하면(오프라인) 캐시에 남은 페이지를 보여 준다
// 캐시 구조를 바꾸면 VERSION을 올린다. 이전 캐시는 activate에서 지운다.
const VERSION = "v1";
const STATIC_CACHE = `static-${VERSION}`;
const PAGE_CACHE = `pages-${VERSION}`;

self.addEventListener("install", (event) => {
  event.waitUntil(caches.open(PAGE_CACHE).then((cache) => cache.add("/")).then(() => self.skipWaiting()));
});

self.addEventListener("activate", (event) => {
  event.waitUntil(
    caches
      .keys()
      .then((keys) => Promise.all(keys.filter((key) => ![STATIC_CACHE, PAGE_CACHE].includes(key)).map((key) => caches.delete(key))))
      .then(() => self.clients.claim()),
  );
});

const isStatic = (url) =>
  url.pathname.startsWith("/_next/static/") || url.pathname.startsWith("/icons/") || /\.(woff2?|png|svg|ico)$/.test(url.pathname);

self.addEventListener("fetch", (event) => {
  const { request } = event;
  const url = new URL(request.url);
  if (request.method !== "GET" || url.origin !== self.location.origin) return;

  if (isStatic(url)) {
    event.respondWith(
      caches.match(request).then(
        (cached) =>
          cached ||
          fetch(request).then((response) => {
            if (response.ok) caches.open(STATIC_CACHE).then((cache) => cache.put(request, response.clone()));
            return response;
          }),
      ),
    );
    return;
  }

  if (request.mode === "navigate") {
    event.respondWith(
      fetch(request)
        .then((response) => {
          if (response.ok) caches.open(PAGE_CACHE).then((cache) => cache.put(request, response.clone()));
          return response;
        })
        .catch(() => caches.match(request).then((cached) => cached || caches.match("/"))),
    );
  }
});
```

앞에서 본 것들이 그대로 들어 있다. `install`은 홈(`/`) 하나만 미리 담는다. 오프라인일 때 최소한 보여 줄 페이지다. 나머지는 모두 쓰면서 담는다. `/_next/static/`, 아이콘, 폰트·이미지 확장자는 캐시 우선이고, 페이지 이동(`request.mode === "navigate"`)은 네트워크 우선이다. 다른 출처로 가는 요청과 GET이 아닌 요청은 `return`으로 그냥 보내니 네트워크 전용이다.

첫째, 캐시에 넣는 `cache.put`이 `event.waitUntil`에 묶여 있지 않다. 응답을 돌려준 뒤 브라우저가 Service Worker를 멈추면 넣기가 끝나지 않을 수 있다. 실제로는 브라우저가 놀고 있는 Service Worker를 바로 멈추지 않아서 거의 문제가 되지 않는다. 확실히 하고 싶다면 앞의 stale-while-revalidate 코드처럼 `waitUntil`로 감싼다.

둘째, Next.js App Router에서 `Link`로 이동하면 HTML 페이지 이동이 아니라 RSC 데이터를 `fetch`로 받아 온다. 이 요청은 `navigate` 모드가 아니라서 위 코드가 손대지 않는다. 그래서 이 블로그의 오프라인 대응은 주소창으로 열거나 새로고침한 페이지에만 걸린다. 오프라인에서 링크를 누르면 RSC 요청이 실패하는데, Next.js는 이때 보통 전체 페이지 이동으로 다시 시도한다. 그러면 `navigate` 요청이 되어 캐시가 받는다.

셋째, `static-v1`은 지워지지 않는다. 다음 절에서 이 이야기를 한다.

## 새 Service Worker는 기다린다

처음 장면으로 돌아가자. 새로고침해도 예전 화면이 남는 건 대부분 이 부분 때문이다.

새 `sw.js`가 설치되어도 바로 활성화되지 않는다. 옛 Service Worker가 맡고 있는 탭이 하나라도 열려 있으면 새 버전은 `waiting` 상태로 기다린다. 한 페이지를 두 버전이 나눠 맡으면 곤란하기 때문이다. HTML은 옛 버전이 줬는데, 그 HTML이 부르는 청크는 옛 캐시를 이미 지운 새 버전이 받는다면 페이지가 깨질 수 있다. 새로고침 한 번으로는 풀리지 않는다. 새로고침하는 동안에도 옛 페이지가 잠깐 겹쳐 있어서 옛 Service Worker가 계속 탭을 맡는다. 그 사이트의 탭을 모두 닫았다가 다시 열어야 바뀐다.

기다리지 않게 하는 방법이 `self.skipWaiting()`이다. 이 블로그의 `sw.js`도 `install` 끝에 부르고, `activate`에서 `clients.claim()`으로 열려 있는 탭까지 곧바로 맡는다. 배포가 사용자에게 빨리 닿는다는 장점이 크다.

대가는 열려 있던 탭이다. 그 탭은 옛 HTML과 옛 자바스크립트로 돌고 있는데, 이제부터 요청은 새 Service Worker가 받는다. 새 버전이 `activate`에서 옛 캐시를 지웠다면, 그 탭이 나중에 부르는 옛 청크는 캐시에도 없고 서버에도 없을 수 있다. 화면이 반쯤 깨지거나 청크 로드 에러가 난다. 이 블로그가 `skipWaiting`을 써도 괜찮은 건 페이지가 네트워크 우선이고, 정적 캐시 이름이 배포 때마다 바뀌지 않아 옛 청크가 남아 있기 때문이다. 오프라인 앱 셸을 캐시 전용으로 쓰는 앱이라면 이야기가 달라진다.

그래서 많이 쓰는 절충은 사용자에게 묻는 것이다. 새 버전이 대기 중이면 "새 버전이 있다. 새로고침" 같은 알림을 띄우고, 사용자가 누를 때만 `skipWaiting`을 시킨 뒤 페이지를 다시 연다.

```js
// sw.js: 페이지가 시킬 때만 대기를 건너뛴다
self.addEventListener("message", (event) => {
  if (event.data?.type === "SKIP_WAITING") self.skipWaiting();
});
```

```js
// 페이지
const registration = await navigator.serviceWorker.register("/sw.js");

function promptUpdate(worker) {
  showToast("새 버전이 있다", () => worker.postMessage({ type: "SKIP_WAITING" }));
}

if (registration.waiting) promptUpdate(registration.waiting); // 이미 대기 중인 버전
registration.addEventListener("updatefound", () => {
  const next = registration.installing;
  next?.addEventListener("statechange", () => {
    // controller가 있어야 업데이트다. 없으면 첫 설치라 물을 필요가 없다
    if (next.state === "installed" && navigator.serviceWorker.controller) promptUpdate(next);
  });
});

let reloading = false;
navigator.serviceWorker.addEventListener("controllerchange", () => {
  if (reloading) return; // 새로고침이 두 번 일어나지 않게 막는다
  reloading = true;
  location.reload();
});
```

탭을 오래 열어 두는 사용자를 위해 `registration.update()`를 주기적으로 부르기도 한다. 페이지 이동이 없으면 브라우저가 업데이트를 확인할 기회도 없기 때문이다.

<Callout kind="warning" title="Service Worker를 없애고 싶을 때">
`sw.js` 파일을 서버에서 지우기만 하면 이미 설치된 사용자에게서는 사라지지 않는다. 업데이트 확인이 404로 실패하면 브라우저는 기존 버전을 그대로 쓴다. 없앨 때는 같은 주소에 캐시를 모두 지우고 `self.registration.unregister()`를 부르는 Service Worker를 배포하고, 응답에 `Clear-Site-Data: "storage"` 헤더를 주는 방법도 함께 쓴다.
</Callout>

## Workbox를 쓰면

여기까지 손으로 짠 코드를 실제 서비스에서 다 직접 쓰지는 않는다. 구글의 Workbox가 같은 일을 모듈로 묶어 둔다.

```js
import { precacheAndRoute } from "workbox-precaching";
import { registerRoute } from "workbox-routing";
import { CacheFirst, NetworkFirst, StaleWhileRevalidate } from "workbox-strategies";
import { ExpirationPlugin } from "workbox-expiration";

precacheAndRoute(self.__WB_MANIFEST); // 빌드 도구가 해시 붙은 파일 목록을 넣어 준다

registerRoute(({ request }) => request.mode === "navigate", new NetworkFirst({ cacheName: "pages", networkTimeoutSeconds: 3 }));
registerRoute(
  ({ request }) => request.destination === "image",
  new CacheFirst({ cacheName: "images", plugins: [new ExpirationPlugin({ maxEntries: 100, maxAgeSeconds: 30 * 24 * 60 * 60 })] }),
);
registerRoute(({ url }) => url.pathname.startsWith("/api/tags"), new StaleWhileRevalidate({ cacheName: "api" }));
```

미리 담기 목록에 파일마다 해시를 붙여 바뀐 것만 다시 받고, 만료 규칙으로 쓰면서 담은 캐시가 자라는 걸 막는다. 앞에서 본 이 블로그의 두 약점, 지워지지 않는 정적 캐시와 `waitUntil` 없는 `put`을 라이브러리가 대신 처리한다. Next.js에서는 Workbox 위에 만든 Serwist 같은 플러그인으로 빌드에 붙인다. 이 블로그처럼 규칙이 두세 개뿐이면 손으로 짠 50줄이 읽기 쉽고, 규칙이 늘어나면 라이브러리로 옮긴다.

## 데이터는 어디에 저장하나

파일이 아니라 데이터를 남겨 두고 싶을 때 쓰는 저장소도 여럿이다. 고르는 기준은 동기인지, 무엇을 넣을 수 있는지, 얼마나 넣을 수 있는지다.

localStorage는 문자열 키·값 저장소다. API가 동기라서 읽고 쓰는 동안 메인 스레드가 멈춘다. 값은 문자열만 되니 객체는 `JSON.stringify`로 바꿔 넣는다. 출처당 대략 5MB를 넘기면 `QuotaExceededError`가 난다. Service Worker와 Web Worker에서는 쓸 수 없다. 테마, 닫아 둔 안내 같은 작은 설정에 맞는다. 이 블로그의 즐겨찾기와 단어 학습 기록도 여기에 있다.

sessionStorage는 API가 같고 수명만 다르다. 탭 하나에 묶여서 새로고침해도 남지만 탭을 닫으면 사라진다. 같은 사이트를 다른 탭에서 열면 각자 따로 갖는다. 작성 중인 폼처럼 이 탭에서만 의미 있는 값에 쓴다.

IndexedDB는 비동기이고, 구조화된 값(객체, 배열, `Blob`, `Date`)을 그대로 넣는다. 인덱스로 찾을 수 있고 트랜잭션이 있다. 용량도 크고 워커에서도 쓸 수 있다. 오프라인 초안, 받아 둔 목록 데이터처럼 크거나 많은 데이터는 여기다. 원래 API가 번거로워서 보통 `idb`나 `idb-keyval` 같은 얇은 래퍼로 쓴다.

```js
import { get, set } from "idb-keyval";

await set("draft:42", { title, body, savedAt: Date.now() }); // 객체를 그대로 넣는다
const draft = await get("draft:42");
```

Cache Storage는 앞에서 본 요청·응답 저장소다. 데이터를 넣을 수도 있지만 `Response`로 감싸야 하니, 응답을 그대로 다시 쓸 때만 맞는다. 화면에서 다루는 데이터를 메모리에 두고 같은 요청을 줄이는 이야기는 [화면 데이터 캐시](/posts/client-data-cache)에서 이어서 다룬다.

## 용량과 지워지는 순서

IndexedDB와 Cache Storage, Service Worker 등록은 같은 출처의 저장 공간 한도를 함께 쓴다. 한도는 브라우저마다 다르다. 크롬은 출처 하나가 디스크 전체 용량의 60%까지 쓸 수 있게 하고, 파이어폭스는 기본 모드에서 디스크의 10%와 10GiB 중 작은 값을 같은 사이트 묶음의 한도로 둔다. 사파리는 버전에 따라 정책이 여러 번 바뀌었다. 외우기보다 직접 물어보는 게 낫다.

```js
const { usage, quota } = await navigator.storage.estimate();
console.log(`${(usage / 1024 / 1024).toFixed(1)}MB / ${(quota / 1024 / 1024 / 1024).toFixed(1)}GB`);

const persisted = await navigator.storage.persist(); // true면 자동으로 지워지지 않는다
```

기본 상태의 저장소는 "최선을 다하는(best-effort)" 저장소다. 기기 디스크가 모자라면 브라우저가 오래 안 쓴 출처부터 통째로 지운다. 한 출처의 IndexedDB만 남고 Cache Storage만 지워지는 식이 아니라 함께 사라진다. `persist()`가 허락되면 사용자가 직접 지우기 전까지 남는다. 크롬은 사이트 사용 빈도, 설치 여부, 알림 권한 같은 신호로 조용히 허락 여부를 정하고, 파이어폭스는 사용자에게 묻는다.

사파리는 하나 더 있다. 추적 방지(ITP) 정책으로, 사용자가 7일 동안 그 사이트와 상호작용하지 않으면 스크립트로 만든 저장소(localStorage, IndexedDB, Service Worker와 그 캐시)를 지울 수 있다. 홈 화면에 추가한 웹 앱은 예외다. 그래서 브라우저 저장소에 넣은 데이터는 언제든 사라질 수 있다고 보고, 지워져도 서버에서 다시 받아 복구할 수 있게 짠다. 사용자의 유일한 원본을 브라우저에만 두지 않는다.

## 다음에 필요한 것을 미리 받기

지금까지는 받은 것을 남기는 이야기였다. 반대로 아직 요청하지 않은 것을 미리 받아 캐시에 넣어 두는 방법도 있다. HTML에 힌트를 적어 브라우저에게 알려 준다.

```html
<!-- 곧 쓸 다른 출처에 DNS·TCP·TLS 연결을 미리 열어 둔다 -->
<link rel="preconnect" href="https://cdn.example.com" crossorigin />
<!-- 연결까지는 아니고 DNS 조회만 미리. 오래된 브라우저용 대안으로도 쓴다 -->
<link rel="dns-prefetch" href="https://analytics.example.com" />
<!-- 이 페이지에서 곧 쓸 파일을 높은 우선순위로 지금 받는다 -->
<link rel="preload" href="/fonts/pretendard.woff2" as="font" type="font/woff2" crossorigin />
<!-- ES 모듈을 받아서 파싱까지 해 둔다 -->
<link rel="modulepreload" href="/assets/chart.js" />
<!-- 다음 페이지에서 쓸 것 같은 파일을 한가할 때 낮은 우선순위로 받는다 -->
<link rel="prefetch" href="/assets/settings-chunk.js" />
```

가장 헷갈리는 건 preload와 prefetch다. preload는 지금 페이지가 곧 쓸 것이다. 높은 우선순위로 바로 받고, `as`를 정확히 적어야 나중에 실제 요청과 짝이 맞는다. 폰트는 같은 출처여도 CORS 모드로 받기 때문에 `crossorigin`을 빼면 두 번 받는다. 받아 놓고 몇 초 안에 안 쓰면 크롬이 콘솔에 경고를 띄운다. prefetch는 다음 페이지가 쓸 것이다. 낮은 우선순위로 받아서 캐시에 넣어 두고, 지금 페이지의 로딩과 경쟁하지 않는다.

preconnect는 아낄수록 좋다. 연결 하나를 여는 데 드는 비용이 있어서, 정말 곧 쓰는 출처 두세 개에만 건다. 열어 두고 10초쯤 안 쓰면 브라우저가 닫아 버려서 헛일이 된다. LCP 이미지를 빨리 받는 방법은 [Core Web Vitals](/posts/core-web-vitals)에서, 청크를 나눠 받는 이야기는 [코드 스플리팅](/posts/code-splitting)에서 다뤘다.

한 단계 더 나간 게 Speculation Rules다. 다음 페이지를 미리 받는 데서 그치지 않고 보이지 않는 탭에서 통째로 렌더링해 둔다. 링크를 누르면 이미 다 그려진 페이지로 바꿔치기만 하니 즉시 뜬다.

```html
<script type="speculationrules">
  {
    "prerender": [{ "where": { "href_matches": "/posts/*" }, "eagerness": "moderate" }]
  }
</script>
```

`moderate`는 사용자가 링크에 포인터를 잠깐 올려 두는 정도의 신호가 있을 때 시작한다. 지금은 크롬 계열 브라우저만 지원하고, 다른 엔진은 이 스크립트를 무시하니 점진적으로 붙이기 좋다. 조심할 점은 미리 렌더링도 진짜 요청이고 진짜 실행이라는 것이다. 서버 부하와 데이터 사용량이 늘고, 분석 스크립트가 아무도 보지 않은 페이지를 조회수로 셀 수 있다. 로그아웃이나 장바구니 담기처럼 GET에 부수 효과가 있는 링크는 대상에서 빼고, 분석 코드는 `document.prerendering`을 확인해 실제로 보일 때(`prerenderingchange`)까지 미룬다.

## 개발자 도구에서 확인하기

크롬 개발자 도구의 Application 패널에 지금까지 본 저장소가 모두 모여 있다.

- Service workers: 등록된 버전과 상태(activated, waiting to activate)가 보인다. 대기 중인 버전 옆의 skipWaiting을 눌러 바로 활성화할 수 있다. 개발할 때는 Update on reload를 켜 두면 새로고침마다 새 `sw.js`를 설치하고 활성화한다. Bypass for network를 켜면 Service Worker를 거치지 않는다.
- Storage: 출처가 쓰는 용량을 종류별로 보여 준다. Clear site data로 캐시, 저장소, Service Worker 등록을 한꺼번에 지운다. 처음 방문하는 사용자의 상태를 재현할 때 쓴다.
- Cache storage, IndexedDB, Local storage, Session storage: 들어 있는 항목을 직접 열어 보고 지울 수 있다.
- Back/forward cache: 앞에서 본 bfcache 테스트다.

Network 탭의 Size 칸은 응답이 어디서 왔는지 알려 준다. `(memory cache)`, `(disk cache)`, `(ServiceWorker)`가 각각 앞의 그림의 세 겹이다. 상단의 Disable cache는 개발자 도구가 열려 있는 동안 HTTP 캐시만 끈다. Service Worker는 여전히 요청을 가로채니, "캐시를 껐는데 옛 화면이 나온다"면 Service Worker를 의심한다. Shift를 누른 채 새로고침하면 그 한 번은 Service Worker 없이 로드된다.

## 처음 장면으로 돌아가서

배포했는데 옛 화면이 남는 사용자는 대부분 새 Service Worker가 대기 중이거나, 페이지를 캐시 우선으로 받는 Service Worker를 만난 경우다. HTML은 네트워크 우선으로 받고, 대기 중인 새 버전은 사용자에게 알려서 바꾸고, 캐시 이름에 버전을 넣어 정리한다. 재방문이 느린 모바일 사용자는 반대로 정적 파일의 캐시 헤더부터 본다. 해시 파일에 긴 `max-age`와 `immutable`이 붙어 있는지, 작은 디스크 캐시에서 밀려나는 게 문제라면 Service Worker의 캐시 우선 규칙이 받쳐 주는지다. 어느 쪽이든 Network 탭의 Size 칸이 응답이 어느 겹에서 왔는지 알려 준다. 거기서 시작한다.

## 면접에서 나올 만한 질문

### 브라우저가 리소스를 찾을 때 어떤 캐시를 거치나요?

크롬 기준으로 지금 문서 안의 메모리 캐시, Service Worker와 Cache Storage, 디스크의 HTTP 캐시 순서로 보고, 없으면 네트워크로 나가 CDN과 오리진 서버까지 간다. Service Worker가 `fetch()`로 보낸 요청도 HTTP 캐시를 거친다. HTTP 캐시는 헤더를 보고 브라우저가 넣고 빼지만, Cache Storage는 코드가 넣은 것만 들어가고 코드가 지울 때까지 남는다. 개발자 도구 Network 탭의 Size 칸으로 어느 겹에서 왔는지 확인한다.

### bfcache는 무엇이고 무엇이 막나요?

뒤로·앞으로 가기를 위해 페이지를 자바스크립트 상태까지 통째로 메모리에 얼려 두는 캐시다. 돌아오면 다시 로드하지 않고 녹여서 즉시 보여 주고, `pageshow`의 `persisted`가 `true`다. `unload` 리스너, 열린 WebSocket 같은 연결이 대표적인 방해 요인이고, 메인 문서의 `Cache-Control: no-store`도 브라우저와 버전에 따라 막는다. 떠날 때의 정리는 `pagehide`로 옮기고, 개발자 도구의 bfcache 테스트로 막는 이유를 확인한다.

### Service Worker의 생명주기를 설명해 주세요.

등록하면 `install`에서 필요한 파일을 미리 담고, `activate`에서 옛 캐시를 정리한 뒤, 그 뒤 범위 안의 요청을 `fetch` 이벤트로 받는다. 등록한 첫 페이지는 이미 로드되어 있어서 `clients.claim()`을 부르지 않으면 다음 페이지부터 가로챈다. 브라우저는 페이지 이동 때 `sw.js`를 다시 받아 바이트가 다르면 새 버전을 설치하고, 새 버전은 옛 버전이 맡은 탭이 모두 닫힐 때까지 `waiting`으로 기다린다.

### 캐시 우선, 네트워크 우선, stale-while-revalidate는 각각 언제 쓰나요?

캐시 우선은 해시가 든 정적 파일, 폰트처럼 같은 주소의 내용이 바뀌지 않는 것에 쓴다. 네트워크 우선은 HTML처럼 최신이어야 하지만 오프라인에서도 무언가 보여 줘야 하는 것에 쓰고, 느린 네트워크를 대비해 시간 제한을 둔다. stale-while-revalidate는 조금 낡아도 빠른 게 나은 것, 아바타나 자주 안 바뀌는 목록에 쓴다. 결제나 로그인, POST는 네트워크 전용으로 두고 Service Worker가 손대지 않는다.

### 배포했는데 일부 사용자가 계속 옛 버전을 봅니다. Service Worker 관점에서 원인과 해결은요?

새 `sw.js`가 설치됐지만 옛 버전이 맡은 탭이 남아 있어 `waiting` 상태이거나, HTML을 캐시 우선으로 주고 있을 가능성이 크다. HTML은 네트워크 우선으로 바꾸고, 대기 중인 새 버전이 있으면 사용자에게 알려서 `skipWaiting`을 시킨 뒤 `controllerchange`에서 새로고침한다. 오래 열어 둔 탭을 위해 `registration.update()`를 주기적으로 부르기도 한다. Service Worker를 없앨 때는 파일을 지우는 게 아니라 스스로 `unregister`하는 버전을 배포한다.

### skipWaiting을 항상 쓰면 안 되나요?

배포가 빨리 닿는 대신, 옛 HTML과 자바스크립트로 돌고 있는 탭을 새 Service Worker가 맡게 된다. 새 버전이 옛 캐시를 지웠다면 그 탭이 나중에 부르는 옛 청크가 캐시에도 서버에도 없어 화면이 깨질 수 있다. 페이지를 네트워크 우선으로 받고 옛 정적 파일을 바로 지우지 않는 구조라면 비교적 안전하고, 앱 셸을 캐시 전용으로 쓰는 구조라면 사용자에게 묻고 새로고침과 함께 바꾸는 편이 낫다.

### localStorage, IndexedDB, Cache Storage는 어떻게 고르나요?

localStorage는 동기이고 문자열만, 출처당 5MB 정도라 작은 설정값에 쓴다. 메인 스레드를 막고 워커에서 못 쓰니 큰 데이터에는 맞지 않는다. IndexedDB는 비동기에 구조화된 값을 넣고 용량이 커서 오프라인 데이터, 큰 목록에 쓴다. Cache Storage는 요청·응답 쌍을 넣는 곳이라 응답을 그대로 다시 줄 때 쓴다. 어느 쪽이든 디스크가 모자라거나 사파리에서 7일간 방문이 없으면 지워질 수 있으니, 다시 받아 복구할 수 있게 짠다.

### preload와 prefetch는 어떻게 다른가요?

preload는 지금 페이지가 곧 쓸 리소스를 높은 우선순위로 바로 받는 것이고, prefetch는 다음 이동에서 쓸 리소스를 낮은 우선순위로 한가할 때 받아 두는 것이다. preload는 `as`가 맞아야 실제 요청과 짝이 맞고, 폰트는 `crossorigin`이 필요하다. 쓰지 않을 걸 preload하면 정작 중요한 리소스와 대역폭을 다툰다. 다음 페이지를 통째로 렌더링해 두려면 크롬 계열의 Speculation Rules prerender를 쓰고, 부수 효과가 있는 링크와 분석 집계를 조심한다.
