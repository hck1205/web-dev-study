<EasyIntro>
  React 컴포넌트는 화면을 바꿀 때마다 처음부터 다시 실행되는 함수라서, 그 안에 만든 변수는 매번 새로 태어났다가 사라진다. 그런데 타이머 번호나 입력칸 같은 것은 다음 번에도 기억하고 있어야 한다. useRef는 이럴 때 쓰는 이름표 붙은 상자다. 상자는 컴포넌트가 화면에 있는 동안 계속 같은 상자이고, 안에 든 것을 바꿔도 화면은 다시 그려지지 않는다. 그래서 화면에 보여 줄 값은 상자가 아니라 상태에 넣어야 한다. 상자에는 입력칸이나 버튼 같은 화면 속 진짜 요소를 넣어 둘 수도 있다. 말풍선을 버튼 바로 위에 띄우려면 버튼이 어디 있는지 먼저 재야 하는데, 화면에 그린 다음에 재면 말풍선이 엉뚱한 곳에 잠깐 보였다가 옮겨진다. useLayoutEffect는 화면에 그리기 직전에 재고 고칠 시간을 주는 도구라서 이 깜빡임을 없앤다. 대신 그 일이 오래 걸리면 화면 전체가 늦게 뜨니 꼭 필요한 곳에만 쓴다.
</EasyIntro>

버튼 위에 뜨는 툴팁을 만들었다. 버튼 위치를 재서 툴팁을 그 위에 놓는 평범한 코드다. 그런데 휴대폰에서 버튼을 누르면 툴팁이 화면 왼쪽 위 구석에 한 번 번쩍였다가 버튼 위로 옮겨 간다. 데스크톱에서는 거의 안 보이고, 느린 휴대폰에서는 매번 보인다.

```tsx
function Tooltip({ anchorRect, text }: { anchorRect: DOMRect; text: string }) {
  const tipRef = useRef<HTMLDivElement>(null);
  const [pos, setPos] = useState({ top: 0, left: 0 });

  useEffect(() => {
    const tip = tipRef.current!.getBoundingClientRect();
    setPos({ top: anchorRect.top - tip.height - 8, left: anchorRect.left });
  }, [anchorRect]);

  return (
    <div ref={tipRef} className="tooltip" style={{ top: pos.top, left: pos.left }}>
      {text}
    </div>
  );
}
```

이 짧은 코드에 이 글의 주제가 다 들어 있다. `useRef`로 DOM 요소를 붙잡는 것, 그 요소를 언제 잴 수 있는지, 잰 값을 반영하는 시점이 화면에 그리기 전인지 후인지. 깜빡임은 `useEffect`를 `useLayoutEffect`로 바꾸면 사라진다. 왜 그런지, 그리고 그 대가가 무엇인지를 따라가 본다. 그 전에 ref가 무엇인지부터 정확히 잡아 둔다.

## 렌더링이 끝나도 남는 상자

컴포넌트 함수는 렌더링할 때마다 처음부터 다시 실행된다. 함수 안의 지역 변수는 호출이 끝나면 사라지고, 다음 렌더링에서 새로 만들어진다. 그래서 이런 코드는 동작하지 않는다.

```tsx
function Stopwatch() {
  const [elapsed, setElapsed] = useState(0);
  let intervalId: number | undefined; // 렌더링마다 undefined로 다시 태어난다

  const start = () => {
    intervalId = window.setInterval(() => setElapsed((s) => s + 1), 1000);
  };
  const stop = () => clearInterval(intervalId); // 시작한 뒤 렌더링이 한 번이라도 일어났으면 undefined다

  return <button onClick={elapsed ? stop : start}>{elapsed}초</button>;
}
```

시작을 누르면 1초 뒤 `setElapsed`가 렌더링을 일으키고, 새 렌더링의 `intervalId`는 다시 `undefined`다. 정지를 눌러도 타이머는 계속 돈다. 렌더링이 바뀌어도 살아남는 자리가 필요하다.

`useRef(초깃값)`은 그 자리를 준다. `{ current: 초깃값 }` 모양의 평범한 객체를 하나 만들어 컴포넌트가 마운트되어 있는 동안 계속 같은 객체를 돌려준다. 안의 `current`는 마음대로 바꿔도 되고, 바꿔도 React는 아무것도 하지 않는다. 다시 렌더링하지 않는다.

```tsx
function Stopwatch() {
  const [elapsed, setElapsed] = useState(0);
  const intervalRef = useRef<number | null>(null); // 렌더링 사이에 같은 객체

  const start = () => {
    intervalRef.current = window.setInterval(() => setElapsed((s) => s + 1), 1000);
  };
  const stop = () => {
    if (intervalRef.current !== null) clearInterval(intervalRef.current);
    intervalRef.current = null;
  };

  useEffect(() => stop, []); // 화면을 떠날 때도 멈춘다

  return <button onClick={intervalRef.current ? stop : start}>{elapsed}초</button>;
}
```

아래 그림이 이 차이다. 렌더링마다 함수가 새로 실행되고 지역 변수와 화살표 함수도 새로 생기지만, ref 객체와 state는 React가 컴포넌트 바깥에 들고 있다가 매번 같은 것을 건네준다.

ref와 state는 둘 다 렌더링 사이에 값을 기억한다는 점에서 같다. 다른 점은 하나다. state는 바꾸면 React에 "다시 그려 달라"고 알리고, ref는 알리지 않는다. 그리고 state는 렌더링 하나 안에서 고정된 스냅숏이지만 ref는 언제 읽든 지금 들어 있는 값이 나온다.

## state로 둘까 ref로 둘까

고르는 기준은 하나로 충분하다. 그 값이 화면에 보이는가. 렌더링 결과(JSX)를 만드는 데 쓰이면 state, 이벤트 핸들러나 effect 안에서만 쓰이면 ref다.

ref가 맞는 값들은 대개 이렇다. 타이머와 `requestAnimationFrame`의 id, 진행 중인 요청을 끊을 `AbortController`, 웹소켓이나 지도 SDK 인스턴스처럼 React 바깥 객체, 이전 렌더링의 값과 비교하려고 남겨 둔 값, 드래그 중인 손가락 좌표처럼 초당 수십 번 바뀌지만 화면은 다른 방식(직접 `transform` 조작)으로 바꾸는 값. 공통점은 바뀔 때 화면을 다시 계산할 필요가 없다는 것이다.

반대로 ref에 넣으면 안 되는 값은 화면에 찍히는 값이다. 위 `Stopwatch`의 버튼은 사실 버그가 있다. `onClick={intervalRef.current ? stop : start}`는 렌더링할 때 ref를 읽는데, `start`가 `intervalRef.current`를 바꿔도 렌더링이 일어나지 않으니 버튼은 1초 뒤 `setElapsed`가 렌더링을 일으킬 때까지 여전히 `start`를 들고 있다. 그 1초 안에 두 번 누르면 interval이 두 개 생긴다. "돌고 있는지"는 화면(버튼의 동작)을 결정하니 state여야 한다.

```tsx
const [running, setRunning] = useState(false); // 화면을 결정하는 값은 state
const intervalRef = useRef<number | null>(null); // 정리할 때만 필요한 값은 ref

const start = () => {
  setRunning(true);
  intervalRef.current = window.setInterval(() => setElapsed((s) => s + 1), 1000);
};
```

두 가지가 같이 필요한 경우도 흔하다. 화면에는 state를 쓰고, 오래 사는 콜백(타이머, 구독, 이벤트 리스너)이 최신 값을 읽어야 할 때 ref에 같은 값을 복사해 두는 패턴이다. 이건 오래된 클로저 문제와 붙어 있어서 [클로저 글](/posts/js-closures)에서 `useEffectEvent`와 함께 자세히 다뤘다.

## 렌더링 중에는 ref를 만지지 않는다

몇 번 렌더링됐는지 세고 싶어서 이렇게 쓰는 사람이 많다. 나도 처음에 이렇게 셌다.

```tsx
function RenderCount() {
  const renders = useRef(0);
  renders.current += 1; // 렌더링 중에 ref를 바꾼다
  const [n, setN] = useState(0);
  return <p onClick={() => setN(n + 1)}>{renders.current}번째 렌더</p>;
}
```

React 19.2에서 이 컴포넌트를 `StrictMode` 안과 밖에 각각 띄우고 상태를 바꿔 봤다.

```text
StrictMode 안   마운트: 2번째   업데이트 1번: 4번째   업데이트 2번: 6번째
StrictMode 밖   마운트: 1번째   업데이트 1번: 2번째
```

개발 모드의 `StrictMode`는 렌더링이 순수한지 확인하려고 컴포넌트 함수를 두 번 부른다. 순수한 컴포넌트라면 두 번 불러도 결과가 같다. ref를 바꾸는 컴포넌트는 두 번 바꾸고, 숫자가 두 배로 뛴다. 이건 개발 모드만의 장난이 아니다. 동시성 렌더링에서는 React가 렌더링을 하다가 버리고 다시 시작할 수 있다. 화면에 반영되지 않은 렌더링에서도 ref는 바뀐 채로 남는다. 렌더링은 "몇 번 불려도 결과가 같은 계산"이어야 하는데 ref를 쓰면 그 약속이 깨진다.

읽기도 마찬가지다. 렌더링 중에 `ref.current`를 읽어 JSX에 쓰면, ref가 바뀌어도 React는 모르니 화면이 낡은 값으로 남는다. 앞의 `Stopwatch` 버튼이 정확히 그 버그였다. `eslint-plugin-react-hooks` 7의 `recommended` 설정은 이걸 에러로 잡는다.

```text
  5:3   error  Error: Cannot access refs during render

React refs are values that are not needed for rendering. Refs should only be accessed outside of render, such as in event handlers or effects. Accessing a ref value (the `current` property) during render can cause your component not to update as expected (https://react.dev/reference/react/useRef).

> 5 |   renders.current += 1;
    |   ^^^^^^^^^^^^^^^ Cannot update ref during render
```

이 규칙을 어긴 컴포넌트는 React Compiler도 최적화하지 않고 건너뛴다. 컴파일러가 무엇을 건너뛰는지는 [메모이제이션 훅 글](/posts/react-memoization-hooks)에서 실제 컴파일 결과로 봤다.

예외가 하나 있다. 비싼 객체를 처음 한 번만 만드는 지연 초기화다.

```tsx
function Player() {
  const playerRef = useRef<VideoPlayer | null>(null);
  if (playerRef.current === null) {
    playerRef.current = new VideoPlayer(); // 처음 한 번만. 몇 번 불려도 결과가 같다
  }
  // ...
}
```

`useRef(new VideoPlayer())`라고 쓰면 인자가 렌더링마다 평가되어 매번 플레이어를 만들고 버린다. `null`인지 확인하고 한 번만 채우는 이 모양은 몇 번 실행해도 결과가 같아서 허용된다. 같은 린트 설정으로 돌려도 에러가 나지 않는다.

렌더링 횟수를 세는 게 목적이라면 ref가 아니라 React DevTools Profiler를 쓴다. 굳이 코드로 남기려면 `useEffect` 안에서 센다. effect는 커밋된 렌더링에서만 돈다.

## DOM 요소를 붙잡는 ref

ref의 가장 흔한 쓰임은 DOM 요소다. JSX의 `ref` 속성에 ref 객체를 넘기면 React가 그 요소를 `current`에 넣어 준다.

```tsx
function SearchBox() {
  const inputRef = useRef<HTMLInputElement>(null);
  return (
    <>
      <input ref={inputRef} />
      <button onClick={() => inputRef.current?.focus()}>검색어 입력</button>
    </>
  );
}
```

언제 넣어 주는지가 중요하다. 렌더링 중에는 DOM이 아직 없거나 이전 상태라서 `current`는 비어 있다. React는 커밋 단계에서 DOM을 바꾼 직후에 ref를 채우고, 그다음 `useLayoutEffect`, 그다음 `useEffect`를 부른다. 그래서 effect 안에서는 ref를 믿고 써도 되고, 렌더링 중에는 안 된다. 요소가 사라지면 React가 `current`를 다시 `null`로 돌려놓는다.

`ref.current`가 effect에서 `null`인데 이유를 모르겠다면 셋 중 하나다. 그 요소가 조건부 렌더링이라 이번엔 그려지지 않았다. ref를 DOM 태그가 아니라 직접 만든 컴포넌트에 붙였는데 그 컴포넌트가 ref를 안쪽 요소로 넘기지 않는다. 아니면 effect의 의존성이 비어 있어서 요소가 나중에 나타나도 effect가 다시 돌지 않았다. 마지막 경우는 다음 절의 ref 콜백이 정답이다.

목록의 줄마다 ref가 필요할 때도 있다. 선택한 줄로 스크롤하는 경우다. `useRef`를 반복문 안에서 부를 수는 없으니(훅 규칙) ref 하나에 `Map`을 담고 ref 콜백으로 채운다.

```tsx
function MessageList({ messages, selectedId }: Props) {
  const nodesRef = useRef(new Map<string, HTMLLIElement>());

  useEffect(() => {
    nodesRef.current.get(selectedId)?.scrollIntoView({ block: "nearest" });
  }, [selectedId]);

  return (
    <ul>
      {messages.map((m) => (
        <li
          key={m.id}
          ref={(node) => {
            if (node) nodesRef.current.set(m.id, node);
            return () => nodesRef.current.delete(m.id); // React 19의 클린업
          }}
        >
          {m.text}
        </li>
      ))}
    </ul>
  );
}
```

## React 19에서 바뀐 두 가지

첫째, 함수 컴포넌트가 `ref`를 일반 prop으로 받는다. React 18에서는 직접 만든 `Input`에 ref를 넘기면 `forwardRef`로 감싸야 했다. 감싸지 않으면 18.3에서 이런 경고가 나오고 `current`는 `null`로 남는다.

```text
Warning: Function components cannot be given refs. Attempts to access this ref will fail. Did you mean to use React.forwardRef()?
```

React 19에서는 `ref`가 `props.ref`로 들어온다. 꺼내서 원하는 요소에 붙이면 끝이다. 19.2로 돌려 보니 `ref`를 받기만 하고 어디에도 붙이지 않은 컴포넌트는 경고 없이 `null`로 남았고, `...props`로 `input`에 펼친 컴포넌트는 `INPUT` 요소가 들어왔다. 경고가 없어진 만큼, "ref가 왜 비어 있지"는 받는 컴포넌트가 붙였는지부터 본다.

```tsx
function Input({ ref, ...rest }: ComponentProps<"input">) {
  return <input ref={ref} {...rest} />; // forwardRef 없이
}
```

`forwardRef`는 19에서도 동작하지만 앞으로 없어질 예정이라고 공식 문서에 적혀 있다. 타입을 어떻게 다는지는 [React에서 TypeScript 쓰기](/posts/typescript-in-react)에 정리해 두었다.

둘째, ref 콜백이 정리 함수를 돌려줄 수 있다. 18까지는 요소가 붙을 때 콜백을 요소와 함께, 떨어질 때 `null`과 함께 불렀다. 그래서 콜백 안에서 `if (node) ... else ...`로 두 경우를 나눠야 했다. 19에서는 effect처럼 정리 함수를 돌려주면 떨어질 때 그 함수를 부르고 `null` 호출은 하지 않는다. `ResizeObserver`나 이벤트 리스너를 요소에 붙였다 떼는 코드가 짧아진다.

다만 콜백의 참조가 렌더링마다 바뀌면 React는 렌더링마다 이전 콜백의 정리를 부르고 새 콜백을 다시 부른다. 같은 `div`에 콜백을 붙이고 두 번 렌더링한 뒤 언마운트해 봤다.

```text
useCallback으로 고정한 콜백: [ 'attach DIV', 'cleanup' ]
인라인 화살표 콜백:          [ 'attach DIV', 'cleanup', 'attach DIV', 'cleanup' ]
```

인라인 콜백은 두 번째 렌더링에서 떼었다가 다시 붙었다. 콜백 안에서 `ResizeObserver`를 만든다면 렌더링마다 관찰자를 새로 만드는 셈이다. 무거운 일을 하는 ref 콜백은 `useCallback`으로 고정하거나 컴포넌트 밖 함수로 뺀다.

TypeScript를 쓰면 하나 더 걸린다. 19의 타입은 ref 콜백이 함수 말고 다른 값을 돌려주면 에러를 낸다. `ref={(el) => (inputEl = el)}`처럼 대입식을 그대로 돌려주는 짧은 화살표가 여기 걸린다. 중괄호로 감싸 `ref={(el) => { inputEl = el; }}`로 고친다. 공식 codemod(`no-implicit-ref-callback-return`)가 이걸 바꿔 준다.

## 부모에게 손잡이만 열어 주기

ref를 prop으로 받아 안쪽 `input`에 그대로 붙이면 부모가 그 `input`의 모든 것을 만질 수 있다. 값을 바꾸고, 스타일을 고치고, 요소를 지울 수도 있다. 디자인 시스템 컴포넌트라면 너무 많이 열어 준 것이다. `useImperativeHandle`은 ref에 DOM 대신 내가 고른 메서드만 담은 객체를 넣는다.

```tsx
type ChatInputHandle = { focus: () => void; clear: () => void };

function ChatInput({ ref }: { ref?: Ref<ChatInputHandle> }) {
  const inputRef = useRef<HTMLTextAreaElement>(null);

  useImperativeHandle(ref, () => ({
    focus: () => inputRef.current?.focus(),
    clear: () => {
      if (inputRef.current) inputRef.current.value = "";
    },
  }), []);

  return <textarea ref={inputRef} />;
}

// 부모
const chatRef = useRef<ChatInputHandle>(null);
chatRef.current?.focus(); // focus와 clear만 보인다
```

이건 비상구다. 열기, 닫기, 선택 같은 대부분의 동작은 props로 표현할 수 있고 그게 React다운 방법이다. `<Modal open={open} />`이면 되는 것을 `modalRef.current.open()`으로 만들면 상태가 컴포넌트 안에 숨어서 부모가 지금 열려 있는지 모른다. 포커스, 스크롤, 텍스트 선택, 미디어 재생처럼 "상태"가 아니라 "한 번 시키는 동작"일 때만 쓴다.

## 그리기 전에 한 번 더: useLayoutEffect

이제 처음의 툴팁으로 돌아간다. 깜빡임은 순서 문제다. `useEffect`는 브라우저가 화면을 그린 뒤에 실행되는 게 보통이다. 그래서 툴팁은 `top: 0, left: 0`으로 한 번 그려지고, 그다음 effect가 크기를 재서 위치를 고치고, 다시 그려진다. 사용자는 첫 번째 그림을 본다.

`useLayoutEffect`는 React가 DOM을 바꾼 직후, 브라우저가 그리기 전에 동기로 실행된다. 여기서 state를 바꾸면 React는 화면에 그리기 전에 그 자리에서 다시 렌더링하고 커밋한다. 브라우저는 고친 위치만 그린다. 아래 그림에서 다음을 누르면 순서가 나온다.

```tsx

  const tip = tipRef.current!.getBoundingClientRect();
```

`useEffect`가 늘 그린 뒤에 도는 것은 아니다. 클릭이나 키 입력처럼 사용자의 직접적인 입력이 일으킨 렌더링이면 React 18부터는 effect도 그리기 전에 처리하는 경우가 있다. 그래서 데스크톱 클릭에서는 깜빡임이 안 보이다가, 데이터 도착이나 타이머로 툴팁이 뜰 때만 보이기도 한다. "보장"이 필요한 측정이라면 `useLayoutEffect`를 쓴다.

## 그리기를 붙잡는 값

`useLayoutEffect`는 공짜가 아니다. 이 훅이 끝날 때까지 브라우저는 화면을 그리지 못한다. 안에서 100ms가 걸리면 사용자는 100ms 동안 아무 변화도 못 본다. 깜빡임은 사라졌지만 반응이 늦어진다. 클릭에 대한 반응이라면 INP(입력부터 다음 화면이 그려지기까지의 시간)가 그대로 늘어난다.

비용의 대부분은 측정에서 나온다. `getBoundingClientRect`, `offsetHeight`, `scrollTop` 같은 값을 읽으면 브라우저는 미뤄 둔 레이아웃 계산을 그 자리에서 끝내야 한다. 이걸 강제 동기 레이아웃이라고 한다. 측정과 스타일 변경을 번갈아 하면(읽고 쓰고 읽고 쓰고) 레이아웃을 여러 번 다시 계산한다. 목록의 줄마다 `useLayoutEffect`로 높이를 재고 고치는 컴포넌트가 이 함정에 빠지기 쉽다. 브라우저가 한 프레임 안에서 무엇을 어떤 순서로 하는지는 [브라우저 렌더링 파이프라인](/posts/browser-rendering-pipeline)에서 다뤘다.

크롬 DevTools Performance 패널로 녹화하면 확인할 수 있다. 긴 작업 안에 보라색 Layout 막대가 있고, 그 위에 "Forced reflow" 경고가 붙어 있으면 자바스크립트가 레이아웃을 강제로 당긴 것이다. 그 막대를 누르면 어느 함수가 원인인지 호출 스택이 나온다.

그래서 순서를 이렇게 정한다. 먼저 CSS로 풀 수 있는지 본다. 툴팁을 버튼 기준으로 `position: absolute`로 놓으면 측정 없이 끝나는 경우가 많다. CSS Anchor Positioning은 요소를 다른 요소에 붙이고 넘치면 뒤집는 것까지 CSS로 하는데, 크롬 계열은 125부터 지원하고 다른 브라우저는 지원 범위가 아직 다르니 확인하고 쓴다. 크기 변화를 계속 따라가야 하면 `ResizeObserver`가 레이아웃이 끝난 뒤에 크기를 알려 준다. 그래도 첫 페인트 전에 재야 할 때만 `useLayoutEffect`를 쓰고, 안에서는 측정과 상태 변경 한 번으로 끝낸다.

## 서버에서는 돌지 않는다

`useLayoutEffect`도 effect라서 서버 렌더링에서는 실행되지 않는다. 서버에는 DOM도 화면도 없으니 잴 것이 없다. React 18.3에서 서버 렌더링을 하면 이런 경고가 찍혔다.

```text
Warning: useLayoutEffect does nothing on the server, because its effect cannot be encoded into the server renderer's output format. This will lead to a mismatch between the initial, non-hydrated UI and the intended UI. To avoid this, useLayoutEffect should only be used in components that render exclusively on the client.
```

같은 컴포넌트를 React 19.2의 `renderToString`으로 돌리면 아무것도 찍히지 않는다. 19에서 이 경고가 빠졌다. 경고가 없어졌을 뿐 동작은 같다. 서버 HTML의 툴팁은 여전히 `top: 0, left: 0`이고, 브라우저가 그 HTML을 먼저 그린 다음 자바스크립트가 내려받아지고 하이드레이션이 끝나야 layout effect가 돈다. 그 사이는 깜빡임이 아니라 한동안 틀린 위치로 보인다.

고르는 방법은 세 가지다. 측정이 필요한 부분은 처음부터 서버에서 그리지 않고 마운트된 뒤에만 그린다(툴팁, 팝오버는 대개 사용자 동작 뒤에 뜨니 이게 자연스럽다). 위치를 모를 때는 `visibility: hidden`으로 숨겨 두었다가 잰 뒤에 보인다. 아니면 서버에서도 맞는 위치가 나오게 CSS로 바꾼다. 서버 HTML과 첫 클라이언트 렌더링을 맞추는 문제 전반은 [하이드레이션](/posts/hydration)에서 다뤘다.

라이브러리 코드에서 `useIsomorphicLayoutEffect`라는 이름을 자주 본다. 브라우저면 `useLayoutEffect`, 서버면 `useEffect`를 쓰는 별칭이다. 18의 경고를 끄려고 생긴 우회로라 19만 지원하는 코드라면 꼭 필요하지는 않다. 서버에서 안 돈다는 사실은 이 별칭을 써도 바뀌지 않는다.

## 핸들러 안에서 바로 DOM이 필요할 때

채팅 앱에서 메시지를 보내면 목록 맨 아래로 스크롤해야 한다. 자연스러운 코드는 이렇다.

```tsx
const handleSend = (text: string) => {
  setMessages((prev) => [...prev, { id: crypto.randomUUID(), text }]);
  listRef.current!.lastElementChild?.scrollIntoView(); // 방금 추가한 메시지가 아니라 그 전 메시지로 간다
};
```

`setMessages`는 렌더링을 예약할 뿐이라, 다음 줄의 DOM에는 아직 새 메시지가 없다. 한 칸 모자라게 스크롤된다. `flushSync`로 감싸면 React가 그 업데이트를 그 자리에서 렌더링하고 커밋까지 끝낸 뒤 돌아온다.

```tsx
import { flushSync } from "react-dom";

const handleSend = (text: string) => {
  flushSync(() => {
    setMessages((prev) => [...prev, { id: crypto.randomUUID(), text }]);
  });
  listRef.current!.lastElementChild?.scrollIntoView(); // 이제 새 메시지가 DOM에 있다
};
```

항목 두 개짜리 목록에 하나를 더하고, 바로 다음 줄에서 `li` 개수를 세어 봤다.

```text
flushSync로 감싼 뒤:  li=3
그냥 setState 뒤:     li=3   (4번째를 넣었지만 아직 반영 전)
```

`flushSync`는 배칭과 동시성 렌더링을 그 자리에서 포기하는 장치다. 자주 쓰면 느려지고, 렌더링 도중이나 effect 안에서 부르면 React가 경고를 띄운다. 이 예제처럼 "핸들러에서 상태를 바꾼 직후 DOM을 읽어야 하는" 경우, 그리고 브라우저 API가 이벤트 안에서 동기로 DOM을 요구하는 경우(인쇄 직전의 `beforeprint` 같은)에만 쓴다. 대개는 메시지 목록 쪽에서 `useLayoutEffect`로 "마지막 메시지가 바뀌면 스크롤"을 거는 편이 더 단순하다.

## 증상으로 거꾸로 찾기

현장에서 ref와 layout effect 문제는 이런 모습으로 온다.

툴팁, 드롭다운, 자동 높이 텍스트 영역이 한 번 번쩍이며 제자리를 찾는다. 위치나 크기를 `useEffect`에서 재고 있다. `useLayoutEffect`로 옮기거나 CSS로 풀 수 있는지 본다. CPU를 6배 느리게 걸면 데스크톱에서도 재현된다.

화면을 열 때 첫 그림이 늦고, Performance 패널에 긴 작업과 Forced reflow가 보인다. 반대로 `useLayoutEffect`가 너무 많은 일을 한다. 목록 전체를 재는 코드라면 보이는 줄만 재거나 `ResizeObserver`로 바꾼다.

ref에 담은 값이 화면에 늦게 반영되거나 다른 동작을 해야 반영된다. 렌더링 중에 `ref.current`를 읽고 있다. state로 바꾼다. 린트의 `react-hooks/refs` 규칙이 켜져 있으면 이미 빨간 줄이 있었을 것이다.

`ref.current`가 `null`이다. 조건부 렌더링, ref를 안쪽 요소로 넘기지 않은 컴포넌트, 비어 있는 의존성 배열 순서로 확인한다. 18이라면 위의 forwardRef 경고가 콘솔에 있는지 본다.

컴포넌트를 껐다 켰더니 이벤트 리스너나 관찰자가 쌓인다. ref 콜백이 인라인이라 렌더링마다 다시 붙고 있거나, 정리를 안 하고 있다. 19라면 콜백에서 정리 함수를 돌려주고, 참조를 고정한다.

## 다시 툴팁으로

툴팁이 번쩍인 건 `useEffect`가 화면을 한 번 그린 뒤에 위치를 고쳤기 때문이다. ref는 렌더링 사이에 남는 상자이고, React는 커밋할 때 DOM 요소를 그 상자에 넣어 준다. `useLayoutEffect`는 그 직후, 그리기 전에 동기로 돌아서 잰 값을 같은 프레임에 반영한다. 대가는 그 시간만큼 그리기가 늦어진다는 것이고, 서버에서는 돌지 않는다. 화면에 보이는 값은 state, 보이지 않는 값은 ref, 첫 페인트 전에 재야 할 때만 layout effect. 이 세 줄이면 대부분의 선택이 정해진다.

## 면접에서 나올 만한 질문

### useRef와 useState는 무엇이 다른가요?

둘 다 렌더링 사이에 값을 기억하지만, state는 바꾸면 다시 렌더링을 예약하고 ref는 아무것도 알리지 않는다. state는 렌더링 하나 안에서 고정된 스냅숏이고, ref는 언제 읽든 지금 값이 나오는 바꿀 수 있는 객체다. 그래서 화면에 보이는 값은 state, 타이머 id나 외부 객체처럼 핸들러와 effect에서만 쓰는 값은 ref에 둔다.

### 렌더링 중에 ref를 읽거나 쓰면 왜 안 되나요?

렌더링은 몇 번 불려도 같은 결과를 내는 순수한 계산이어야 하는데, ref를 쓰면 호출 횟수에 따라 결과가 달라진다. StrictMode의 이중 호출이나 동시성 렌더링에서 버려진 렌더링에서도 ref는 바뀐 채 남는다. 읽기도 문제인데, ref가 바뀌어도 React는 다시 렌더링하지 않으니 화면이 낡은 값에 머문다. 처음 한 번만 채우는 지연 초기화는 예외다.

### useEffect와 useLayoutEffect의 차이는요?

`useLayoutEffect`는 DOM을 바꾼 직후 브라우저가 그리기 전에 동기로 실행되고, 그 안에서 바꾼 state도 그리기 전에 반영된다. `useEffect`는 보통 그린 뒤에 실행된다. 그래서 요소 크기를 재서 위치를 정하는 툴팁처럼 첫 프레임부터 맞아야 하는 일은 layout effect로 깜빡임을 없앤다. 대신 오래 걸리면 화면이 그만큼 늦게 뜨므로 나머지는 모두 `useEffect`에 둔다.

### useLayoutEffect를 남용하면 어떤 문제가 생기나요?

그리기를 막는 동기 작업이라 실행 시간만큼 첫 페인트와 상호작용 응답이 늦어지고 INP가 나빠진다. 안에서 `getBoundingClientRect` 같은 측정을 하면 강제 동기 레이아웃이 생기고, 측정과 변경을 번갈아 하면 레이아웃을 여러 번 다시 계산한다. CSS 배치, `ResizeObserver`로 풀 수 있는지 먼저 보고, 쓰더라도 측정 한 번과 상태 변경 한 번으로 끝낸다.

### React 19에서 ref 관련해 무엇이 바뀌었나요?

함수 컴포넌트가 `ref`를 일반 prop으로 받아서 `forwardRef`가 필요 없어졌다. ref 콜백이 정리 함수를 돌려줄 수 있게 되어, 요소가 떨어질 때 `null`로 다시 부르는 대신 그 함수를 부른다. 타입 쪽에서는 ref 콜백이 함수 말고 다른 값을 돌려주면 에러가 나서, 대입식을 돌려주는 짧은 화살표를 중괄호로 고쳐야 한다.

### 서버 렌더링에서 useLayoutEffect를 쓰면 어떻게 되나요?

서버에서는 실행되지 않는다. 18은 경고를 띄웠고 19는 경고를 없앴지만 동작은 같아서, 서버 HTML은 측정 전 모습으로 나가고 하이드레이션이 끝난 뒤에야 위치가 고쳐진다. 측정이 필요한 부분은 마운트 뒤에만 그리거나, 잴 때까지 숨기거나, CSS로 서버에서도 맞게 만든다.

### useImperativeHandle은 언제 쓰나요?

부모에게 DOM 전체 대신 고른 메서드만 열어 줄 때 쓴다. 포커스, 스크롤, 재생처럼 상태가 아닌 한 번 시키는 동작에 맞고, 열기와 닫기처럼 상태로 표현할 수 있는 건 props로 하는 게 맞다. 명령형 핸들로 상태를 바꾸면 그 상태가 자식 안에 숨어서 부모가 모르게 된다.

### flushSync는 무엇이고 언제 쓰나요?

감싼 상태 업데이트를 그 자리에서 렌더링하고 DOM 커밋까지 끝낸 뒤 돌아오게 한다. 메시지를 추가한 직후 새 메시지로 스크롤하는 것처럼 핸들러 안에서 바뀐 DOM을 바로 읽어야 할 때 쓴다. 배칭과 동시성 렌더링을 포기하는 것이라 성능 비용이 있고, 렌더링이나 effect 안에서는 부르지 않는다.
