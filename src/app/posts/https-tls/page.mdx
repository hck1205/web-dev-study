새로 띄운 API 서버를 브라우저로 열면 자물쇠가 잘 뜬다. 그런데 같은 주소를 터미널에서 `curl`로 부르면 이렇게 실패한다.

```
curl: (60) SSL certificate problem: unable to get local issuer certificate
```

Node로 부르면 `unable to verify the first certificate`가 나온다. 브라우저는 믿는데 curl과 Node는 못 믿는다는 건, 인증서를 "믿는다"는 판단이 생각보다 여러 단계로 이루어진다는 뜻이다. 이 오류를 이해하려고 HTTPS가 실제로 무엇을 지켜 주는지, TLS 1.3이 연결을 어떻게 맺는지 처음부터 정리했다. 이 장면의 답은 뒤에서 다시 나온다.

## 자물쇠가 약속하는 세 가지

HTTPS는 HTTP를 TLS라는 암호화 계층 위에 얹은 것이다. HTTP 메시지 자체는 그대로고, 그 아래에서 TLS가 세 가지를 보장한다.

첫째는 기밀성이다. 카페 와이파이를 같이 쓰는 사람이나 중간의 통신사 장비가 패킷을 떠 가도 내용을 읽을 수 없다. 둘째는 무결성이다. 중간에서 바이트 하나만 바꿔도 받는 쪽이 알아챈다. 예전에 HTTP 페이지에 통신사 광고 스크립트가 끼워 들어가던 일이 HTTPS에서는 불가능하다. 셋째는 인증이다. 지금 대화하는 상대가 정말 `shop.example.com`의 주인이라는 걸 인증서로 확인한다.

셋 중 하나라도 빠지면 나머지가 무너진다. 특히 인증이 빠지면 암호화가 아무리 강해도 소용없다. 공격자가 중간에서 서버인 척하면, 나는 공격자와 아주 안전하게 암호화된 대화를 하게 된다. 이걸 중간자 공격(MITM)이라고 한다. TLS에서 인증서 검증이 그렇게 까다로운 이유가 여기 있다.

## 암호화해도 보이는 것

TLS는 내용을 숨기지만 모든 걸 숨기지는 않는다. 같은 네트워크에 있는 사람은 여전히 내가 어느 IP에 붙었는지, 언제 얼마나 많은 데이터를 주고받았는지 안다. 경로(`/orders/42`), 쿼리 문자열, 헤더, 쿠키는 암호화된다.

애매한 건 도메인 이름이다. TLS 핸드셰이크의 첫 메시지(ClientHello)에는 SNI(Server Name Indication)라는 칸이 있고, 여기에 접속하려는 도메인이 평문으로 적힌다. IP 하나에 여러 도메인이 올라가 있는 서버가 어떤 인증서를 내밀지 고르려면 암호화 전에 이름을 알아야 하기 때문이다. 그래서 회사 방화벽이나 통신사는 HTTPS 트래픽에서도 SNI를 보고 특정 사이트를 막을 수 있다. 그 전에 일어나는 [DNS](/posts/dns) 조회도 평문 UDP라면 그대로 보인다.

이 틈을 막으려는 게 ECH(Encrypted Client Hello)다. 서버 운영자가 DNS의 HTTPS 레코드에 ECH용 공개 키를 올려 두면, 브라우저는 진짜 ClientHello를 그 키로 암호화해서 겉 ClientHello 안에 넣는다. 겉에 보이는 SNI는 CDN 같은 공용 이름이고, 진짜 도메인은 안쪽에 숨는다. 크롬과 파이어폭스는 ECH를 지원하지만 서버가 ECH를 켜 둔 경우에만 동작하고, DNS 조회가 평문이면 이름이 거기서 새니 DoH 같은 암호화된 DNS와 함께여야 의미가 있다. 그래도 IP는 숨길 수 없다. 큰 CDN 뒤에 수많은 사이트가 같은 IP를 쓸 때 그나마 효과가 커진다.

## 믿음은 루트에서 내려온다

브라우저는 `shop.example.com`의 인증서를 처음 본다. 그런데도 믿을 수 있는 건, 그 인증서에 서명한 쪽을 거슬러 올라가다 보면 이미 믿고 있는 누군가에 닿기 때문이다.

운영체제와 브라우저에는 신뢰 저장소(trust store)가 있다. 여기에 루트 CA 인증서 수백 개 남짓이 미리 들어 있다. 루트 CA는 자기 개인 키를 오프라인 금고에 넣어 두고, 평소에는 중간 CA 인증서에 서명하는 데만 꺼낸다. 실제 서버 인증서는 중간 CA가 발급한다. 중간 CA 키가 털리면 그 중간 CA만 폐기하면 되고, 브라우저마다 깔린 루트를 바꾸는 큰일은 피할 수 있다.

같은 원리로 로컬 개발용 인증서도 만든다. [mkcert](/posts/local-custom-domain)는 내 컴퓨터에만 통하는 루트를 만들어 신뢰 저장소에 넣는다. 회사 보안 장비가 HTTPS를 들여다보는 방식도 똑같다. 회사 PC에 자체 루트를 깔아 두고, 장비가 중간에서 사이트마다 인증서를 즉석 발급해 내민다. 기술적으로는 중간자 공격과 같은 구조라서, 신뢰 저장소에 무엇이 들어 있는지가 보안의 바닥이 된다.

## 브라우저가 인증서를 검사하는 순서

서버가 체인을 보내면 브라우저는 대략 이런 것들을 확인한다. 하나라도 틀리면 경고 화면을 띄우고 멈춘다.

먼저 서명이 이어지는지 본다. leaf에서 시작해 Issuer를 따라 올라가며 각 서명을 윗단 공개 키로 검증하고, 마지막이 신뢰 저장소의 루트에 닿아야 한다. 다음은 이름이다. 주소창의 호스트가 SAN 목록 중 하나와 맞는지 본다. 그다음 유효 기간이다. 지금 시각이 Not Before와 Not After 사이여야 한다. 그래서 PC 시계가 크게 틀어져 있으면 멀쩡한 사이트도 전부 인증서 오류가 난다.

폐기 여부도 확인해야 한다. 개인 키가 유출된 인증서는 만료 전이라도 CA가 폐기한다. 전통적인 방법은 두 가지였다. CA가 폐기 목록을 파일로 올려 두는 CRL, 그리고 인증서 하나하나를 CA 서버에 물어보는 OCSP다. OCSP는 매 접속마다 CA에 물어보니 느리고, 내가 어느 사이트에 가는지 CA가 알게 된다. 그래서 서버가 OCSP 응답을 미리 받아 핸드셰이크에 붙여 주는 OCSP 스테이플링이 나왔다. 그런데 응답이 늦으면 대부분의 브라우저가 그냥 통과시켜서(soft-fail) 실효성이 늘 의심받았다. 지금 흐름은 브라우저가 폐기 정보를 미리 모아 내려받는 쪽이다. 크롬은 CRLSet, 파이어폭스는 CRLite를 쓴다. Let's Encrypt는 2025년에 OCSP를 끝내고 CRL만 제공하기로 했다. 인증서 수명을 줄이는 것도 같은 맥락이다. 폐기가 잘 안 먹히면 빨리 만료되게 만드는 게 가장 확실하다.

마지막으로 Certificate Transparency(CT)를 본다. CA가 실수로든 해킹을 당해서든 엉뚱한 사람에게 `shop.example.com` 인증서를 발급하면, 위의 검사를 다 통과해 버린다. CT는 공개 CA가 발급하는 모든 인증서를 누구나 볼 수 있는 추가 전용 로그에 올리게 한다. 인증서에는 로그에 올렸다는 영수증(SCT)이 붙고, 브라우저는 영수증이 없으면 거부한다. 발급을 막지는 못하지만 몰래 발급하는 건 막는다. 도메인 주인은 crt.sh 같은 검색 도구나 모니터링 서비스로 내 도메인에 모르는 인증서가 나왔는지 볼 수 있다.

## 인증서를 자동으로 받는 방법: ACME

CA가 인증서를 내주기 전에 확인하는 건 하나다. 이 사람이 정말 그 도메인을 통제하는가. Let's Encrypt는 이 확인을 ACME라는 프로토콜로 자동화했고, 덕분에 인증서가 무료가 되고 90일마다 기계가 알아서 갱신하는 게 표준이 됐다.

확인 방법은 보통 둘 중 하나다. HTTP-01은 CA가 준 토큰을 `http://shop.example.com/.well-known/acme-challenge/{토큰}` 경로에 올려 두면 CA가 80번 포트로 가져가 확인한다. 서버가 인터넷에 열려 있어야 한다. DNS-01은 `_acme-challenge.shop.example.com`에 TXT 레코드를 넣는다. 와일드카드 인증서는 이 방식으로만 받을 수 있고, 내부망 서버처럼 밖에서 접근할 수 없는 경우에도 쓴다. 대신 DNS API 키를 자동화 도구에 줘야 해서 그 키 관리가 새 숙제가 된다.

certbot이나 쿠버네티스의 cert-manager, Caddy 같은 웹 서버가 이 과정을 대신 돌린다. 운영에서 사고가 나는 지점은 거의 갱신이다. 처음 발급은 사람이 지켜보며 하지만, 60일 뒤 갱신은 아무도 안 보는 사이에 실패한다. 방화벽을 바꿔 80번이 막혔거나, DNS API 키가 만료된 경우가 흔하다. 만료 2~3주 전에 경보가 울리게 걸어 두는 이유다.

TLS 1.3은 기능을 더한 만큼 많이 덜어 냈다. RSA 키 교환, CBC 모드, RC4, SHA-1, 압축, 재협상이 모두 빠졌다. 오래 쌓인 공격(BEAST, POODLE, CRIME, Lucky13 같은)은 대부분 이런 옵션을 노렸다. 고를 수 있는 암호 스위트도 사실상 세 개뿐이라 설정을 잘못할 여지가 줄었다.

## 키를 보내지 않고 같은 키를 만든다

핸드셰이크에서 가장 신기한 부분은 key_share다. 브라우저와 서버는 서로 공개 값만 보냈는데, 둘 다 같은 비밀 값을 얻는다. 중간에서 두 공개 값을 다 본 사람은 그 비밀을 계산하지 못한다. 이게 디피-헬먼(Diffie-Hellman) 키 교환이다.

원리는 작은 숫자로 확인할 수 있다. 모두가 아는 소수 p와 밑 g를 정한다. 브라우저는 비밀 수 a를 골라 `g^a mod p`를 보내고, 서버는 비밀 수 b를 골라 `g^b mod p`를 보낸다. 브라우저는 받은 값을 a제곱하고, 서버는 받은 값을 b제곱한다. 둘 다 `g^(ab) mod p`가 된다. 아래 코드에서 직접 계산해 보자.

  // base^exp mod mod 를 계산한다 (곱할 때마다 mod를 취해 숫자가 커지지 않게)
  let result = 1;

function diffieHellman(p, g, a, b) {
  // [브라우저가 보내는 값, 서버가 보내는 값, 브라우저가 계산한 비밀, 서버가 계산한 비밀]

  solution={`function modPow(base, exp, mod) {
  let result = 1;
  base = base % mod;
  for (let i = 0; i < exp; i++) {
    result = (result * base) % mod;
  }
  return result;
}

function diffieHellman(p, g, a, b) {
  const A = modPow(g, a, p); // 브라우저 → 서버 (공개)
  const B = modPow(g, b, p); // 서버 → 브라우저 (공개)
  const clientSecret = modPow(B, a, p);
  const serverSecret = modPow(A, b, p);
  return [A, B, clientSecret, serverSecret];
}`}

첫 번째 예에서 중간에 보이는 값은 8과 19뿐이다. 여기서 6이나 15를 알아내려면 이산 로그를 풀어야 하는데, 수가 작으니 금방 찾겠지만 실제로 쓰는 크기에서는 현실적인 시간 안에 풀 수 없다. TLS 1.3은 이 계산을 정수 대신 타원 곡선 위에서 한다(ECDHE). 같은 안전성을 훨씬 짧은 키로 얻는다. x25519의 공개 값은 32바이트다.

ECDHE의 마지막 E는 ephemeral, 즉 일회용이다. a와 b를 연결마다 새로 만들고 핸드셰이크가 끝나면 버린다. 그래서 전방향 안전성(forward secrecy)이 생긴다. 누가 오늘 내 트래픽을 전부 녹화해 두고, 1년 뒤 서버의 인증서 개인 키를 훔쳤다고 해 보자. TLS 1.2에서 흔하던 RSA 키 교환이라면 세션 키를 서버 공개 키로 암호화해 보냈으니, 개인 키 하나로 녹화본을 전부 풀 수 있다. ECDHE에서는 인증서 키가 서명에만 쓰이고 세션 키 계산에는 끼지 않는다. 그 연결의 a와 b는 이미 사라졌으니 녹화본은 계속 잠겨 있다. TLS 1.3이 RSA 키 교환을 아예 뺀 이유다.

## 본문은 대칭키로 빠르게

핸드셰이크에서 공통 비밀을 얻으면, 거기서 실제 데이터를 암호화할 대칭키를 뽑는다(HKDF라는 키 유도 함수로). 공개 키 연산은 느려서 연결을 맺을 때 한 번만 쓰고, 오가는 HTTP 데이터는 같은 키로 잠그고 여는 대칭 암호로 처리한다.

TLS 1.3의 대칭 암호는 모두 AEAD(Authenticated Encryption with Associated Data)다. 암호화와 위조 검사를 한 번에 한다는 뜻이다. 레코드마다 인증 태그가 붙고, 바이트 하나만 바뀌어도 태그가 맞지 않아 연결이 끊긴다. 앞에서 말한 무결성이 여기서 나온다. 예전 TLS는 암호화와 MAC을 따로 했고, 그 순서를 잘못 맞물린 틈을 노린 공격이 여럿 있었다.

실제로 쓰이는 건 AES-GCM과 ChaCha20-Poly1305 둘이다. 요즘 PC와 서버 CPU에는 AES 전용 명령어(AES-NI)가 있어서 AES-GCM이 가장 빠르다. AES 가속이 없는 저가형 기기에서는 소프트웨어로만 돌아도 빠른 ChaCha20-Poly1305가 유리하다. 그래서 클라이언트는 자기 기기에 맞는 쪽을 앞에 두고, 서버는 그 선호를 존중하도록 설정하는 경우가 많다.

## 다시 올 때는 0-RTT, 대신 재전송을 조심

핸드셰이크 마지막에 받은 세션 티켓을 다음 접속 때 내밀면 두 가지가 가능하다. 하나는 인증서 검증을 건너뛰는 재개(resumption)다. 다른 하나가 0-RTT다. ClientHello에 바로 HTTP 요청(early data)을 실어 보내서, 왕복 한 번도 기다리지 않고 첫 요청이 서버에 닿는다.

빠른 대신 대가가 있다. early data는 이전 세션에서 받은 키로만 암호화돼서, 이번 연결의 일회용 키가 섞이지 않는다. 그래서 그 부분은 전방향 안전성이 없고, 무엇보다 재전송(replay)을 막을 수 없다. 아래 그림에서 무슨 일이 생기는지 따라가 보자.

티켓을 한 번만 쓸 수 있게 기록해 두는 방어도 있지만, 서버가 여러 대면 그 기록을 모두 공유해야 해서 비싸다. 결국 애플리케이션이 상태를 바꾸는 요청을 [멱등하게](/posts/resilience-patterns) 만들어 두는 게 가장 튼튼하다.

## TLS를 어디서 끝낼까

여기까지는 브라우저와 서버가 직접 연결된다고 봤다. 실제 서비스에서는 그 사이에 CDN, 로드 밸런서, [게이트웨이](/posts/gateway)가 있다. 그리고 보통 그중 하나에서 TLS가 끝난다(TLS termination). 인증서와 개인 키가 그 장비에 있고, 거기서 복호화한 HTTP를 보고 경로별로 나누거나 캐시하거나 WAF로 검사한다.

로드 밸런서에서 앱 서버까지를 평문으로 둘지, 다시 암호화할지(re-encryption)는 내부망을 얼마나 믿느냐의 문제다. 예전에는 "데이터센터 안은 안전하다"고 보고 평문으로 두는 경우가 많았다. 지금은 내부망도 뚫릴 수 있다고 보고(제로 트러스트), 클라우드 내부 구간까지 암호화하는 쪽이 기본이 되어 간다. 결제나 개인정보를 다루면 규정상 필수인 경우도 있다.

흔한 실수가 두 가지 있다. 하나는 CDN에서 원본 서버로 가는 구간을 HTTP로 두는 설정이다. 브라우저 주소창에는 자물쇠가 뜨지만, CDN과 원본 사이 인터넷 구간은 평문이다. 원본까지 TLS를 쓰고 원본 인증서도 검증하게 해야 한다. 다른 하나는 리다이렉트 무한 루프다. 앱이 "HTTP로 들어왔으니 HTTPS로 보내자"고 판단하는데, 사실은 로드 밸런서가 TLS를 풀고 HTTP로 넘긴 것이었다. 앱은 원래 요청이 HTTPS였는지를 로드 밸런서가 붙여 주는 `X-Forwarded-Proto` 헤더로 판단해야 한다.

복호화하지 않고 넘기는 방법도 있다. TLS 패스스루는 로드 밸런서가 TCP 수준에서 ClientHello의 SNI만 보고 뒤 서버로 넘긴다. 개인 키를 앱 서버만 가지는 대신, 경로 기반 라우팅이나 헤더 조작 같은 HTTP 기능은 못 쓴다.

## 서버끼리도 서로 확인한다: mTLS

보통의 TLS는 한쪽만 증명한다. 서버가 인증서를 내밀고, 클라이언트는 신분을 밝히지 않는다. 사용자 인증은 그 위의 HTTP에서 쿠키나 토큰으로 한다. 그런데 서비스끼리 통신할 때는 "이 요청이 정말 주문 서비스에서 온 건가"도 확인하고 싶다. 그래서 클라이언트도 인증서를 내미는 게 mTLS(mutual TLS)다.

## 자주 마주치는 인증서 오류

처음 장면으로 돌아가자. 브라우저는 되는데 curl과 Node는 안 되는 건 거의 항상 중간 인증서 누락이다. 서버가 leaf만 보내고 중간 인증서를 빠뜨리면, 체인이 루트까지 이어지지 않는다. 그런데 브라우저는 이걸 메워 주는 장치가 있다. 크롬은 인증서의 AIA 필드에 적힌 주소에서 중간 인증서를 직접 받아 오고, 파이어폭스는 알려진 중간 인증서 목록을 미리 내장하고 있다. 예전에 다른 사이트에서 본 중간 인증서를 캐시해 두기도 한다. curl, Node, 대부분의 서버 쪽 HTTP 클라이언트와 일부 모바일 환경은 그런 걸 하지 않으니 바로 실패한다. "내 브라우저에서는 되는데"가 통하지 않는 대표적인 경우다.

확인은 openssl로 한다. `-servername`을 빼면 SNI가 안 가서 엉뚱한 기본 인증서를 받을 수 있다.

```bash
openssl s_client -connect shop.example.com:443 -servername shop.example.com -showcerts
# Certificate chain 에 0번(leaf)만 있고
# Verify return code: 21 (unable to verify the first certificate) 이면 중간 인증서 누락
```

고치는 방법은 서버에 leaf와 중간 인증서를 이어 붙인 파일을 주는 것이다. certbot이 만드는 파일로 말하면 `cert.pem`이 아니라 `fullchain.pem`을 nginx의 `ssl_certificate`에 걸어야 한다.

다른 오류들도 앞에서 본 검사 순서로 읽으면 원인이 바로 보인다. `NET::ERR_CERT_DATE_INVALID`는 유효 기간 문제다. 갱신이 실패했거나, 사용자 PC 시계가 틀렸다. `NET::ERR_CERT_COMMON_NAME_INVALID`는 이름이 SAN과 맞지 않는 경우다. `example.com`으로만 받은 인증서를 `www.example.com`에 쓰거나, 와일드카드가 두 단계를 덮을 거라고 착각했을 때 난다. `NET::ERR_CERT_AUTHORITY_INVALID`는 체인이 신뢰 저장소의 루트에 닿지 않을 때다. 자체 서명 인증서나 사내 CA가 여기에 걸린다.

인증서는 멀쩡한데 자물쇠가 깨지는 경우도 있다. 혼합 콘텐츠(mixed content)다. HTTPS 페이지가 `http://`로 스크립트나 이미지를 불러오면, 그 하나가 평문으로 오가면서 페이지 전체의 무결성이 깨진다. 스크립트 하나만 바꿔치기해도 페이지를 마음대로 조작할 수 있기 때문이다. 그래서 브라우저는 스크립트, iframe, fetch 같은 능동 콘텐츠는 막는다. 크롬 계열은 이미지·오디오·비디오를 https로 자동으로 바꿔 시도하고, 그것도 안 되면 막는다. 하드코딩된 `http://` 주소를 찾아 고치거나, CSP의 `upgrade-insecure-requests`로 한 번에 올린다.

마지막으로, HTTPS를 제대로 붙였어도 사용자가 처음에 `http://`로 들어오면 첫 요청은 평문이고, 이 순간 공격자가 HTTPS로의 리다이렉트를 가로챌 수 있다(SSL 스트리핑). 이걸 막는 게 HSTS다. HSTS가 무엇이고 프리로드 목록이 왜 필요한지는 [주소창에 google.com을 치면 일어나는 일](/posts/what-happens-google-com)에 정리했다. 실무에서는 `max-age`를 짧게 시작해서 문제가 없으면 1년(31536000초)으로 늘린다. `includeSubDomains`를 켜기 전에 HTTP로만 도는 하위 도메인이 없는지 먼저 확인해야 한다. 한 번 기억된 HSTS는 서버에서 되돌리기 어렵다.

## 자물쇠 하나에 들어 있는 것

HTTPS의 자물쇠는 암호화만이 아니라, 상대가 진짜라는 증명까지 포함한다. 그 증명은 신뢰 저장소의 루트에서 중간 CA를 거쳐 서버 인증서까지 이어지는 서명 사슬이다. TLS 1.3은 ClientHello에 키 재료를 미리 실어 왕복 한 번에 연결을 맺고, 연결마다 버리는 ECDHE 키로 전방향 안전성을 얻는다. 0-RTT는 더 빠르지만 재전송될 수 있으니 안전한 요청에만 쓴다. 운영에서 마주치는 오류 대부분은 체인, 이름, 기간 중 어디가 어긋났는지로 읽으면 풀린다.

## 면접에서 나올 만한 질문

### HTTPS는 무엇을 보장하나요?

기밀성, 무결성, 인증 세 가지다. 중간에서 내용을 읽을 수 없고, 바꾸면 알아채며, 상대가 그 도메인의 주인이라는 걸 인증서로 확인한다. 인증이 빠지면 중간자 공격에 그대로 노출되니 셋 중 가장 중요하다고 본다. 다만 접속한 IP, 트래픽 양과 시점, 그리고 ECH를 쓰지 않으면 SNI에 적힌 도메인 이름은 여전히 보인다.

### 브라우저는 처음 보는 인증서를 어떻게 믿나요?

인증서 체인을 따라 올라가며 서명을 검증한다. 서버 인증서는 중간 CA가, 중간 CA 인증서는 루트 CA가 서명했고, 루트는 OS나 브라우저의 신뢰 저장소에 미리 들어 있다. 여기에 더해 SAN이 접속한 호스트와 맞는지, 유효 기간 안인지, 폐기되지 않았는지, CT 로그에 올라갔는지(SCT)를 확인한다.

### TLS 1.3이 1.2보다 빠른 이유는요?

클라이언트가 ClientHello에 키 교환용 공개 값(key_share)을 미리 실어 보내서, 왕복 한 번 만에 핸드셰이크가 끝난다. TLS 1.2는 방식을 정하는 왕복과 키를 교환하는 왕복이 따로 있어 2-RTT였다. 재접속 때는 세션 티켓으로 0-RTT까지 가능하다. 또 ServerHello 이후 메시지를 모두 암호화해서 인증서도 더 이상 평문으로 보이지 않는다.

### 전방향 안전성(forward secrecy)이 무엇이고 어떻게 얻나요?

나중에 서버의 개인 키가 유출되더라도 과거에 녹화된 트래픽은 풀리지 않는 성질이다. 연결마다 일회용 키로 ECDHE 키 교환을 하고 끝나면 버려서 얻는다. 인증서 키는 서명에만 쓰이고 세션 키 계산에는 끼지 않는다. 그래서 TLS 1.3은 이 성질이 없는 RSA 키 교환을 없앴다.

### 0-RTT의 위험은 무엇이고 어떻게 대응하나요?

early data는 재전송 공격에 노출된다. 공격자가 암호화된 첫 패킷을 그대로 다시 보내면 서버는 정상 요청과 구별하지 못한다. 그래서 GET처럼 멱등한 요청만 0-RTT로 받고, 나머지는 `425 Too Early`로 핸드셰이크 후에 다시 보내게 한다. 상태를 바꾸는 API는 멱등성 키로 중복 처리를 막아 두는 게 근본적인 대책이다.

### 브라우저에서는 되는데 curl에서 인증서 오류가 나는 이유는요?

대부분 서버가 중간 인증서를 보내지 않아서다. 브라우저는 AIA로 중간 인증서를 받아 오거나 캐시·내장 목록으로 메우지만, curl이나 Node는 그러지 않아 체인이 끊긴다. `openssl s_client -showcerts`로 체인을 확인하고, leaf만 담긴 파일 대신 fullchain을 서버에 설정해서 고친다.

### TLS를 로드 밸런서에서 종료하면 무엇을 신경 써야 하나요?

로드 밸런서 뒤 구간이 평문인지 재암호화인지 정해야 한다. 내부망을 신뢰하지 않는다면 뒤 구간도 TLS로 다시 암호화한다. 앱은 원래 요청이 HTTPS였는지 `X-Forwarded-Proto`로 판단해야 하고, 그렇지 않으면 HTTPS 리다이렉트 무한 루프가 생긴다. 복호화하지 않고 SNI만 보고 넘기는 TLS 패스스루도 있지만, 그러면 L7 라우팅은 못 한다.

### mTLS는 언제 쓰나요?

서비스끼리 서로의 신원을 연결 단계에서 확인하고 싶을 때 쓴다. 서버가 CertificateRequest를 보내고 클라이언트도 인증서와 서명을 보낸다. 수많은 서비스의 인증서를 손으로 관리할 수 없어서 보통 서비스 메시가 짧은 수명의 인증서를 자동 발급·갱신한다. mTLS는 "누구인가"를 확인할 뿐이고, 무엇을 해도 되는지는 별도 인가 정책이 정한다.
