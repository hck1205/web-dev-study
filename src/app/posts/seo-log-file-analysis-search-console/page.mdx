## "새 글이 검색에 안 나와요"라는 문의

운영팀에서 메시지가 왔다. 지난주에 올린 글 열다섯 편이 구글에 하나도 안 나온다고 한다. 처음 떠오르는 건 짐작이다. sitemap을 안 올렸나, `noindex`가 붙었나, 구글이 원래 느린가.

짐작을 하나씩 고쳐 보는 대신 두 군데를 먼저 연다. 하나는 우리 서버의 접근 로그다. 구글봇이 그 주소를 가져가긴 했는지, 가져갔다면 무슨 상태 코드를 받았는지가 남아 있다. 다른 하나는 Google Search Console이다. 구글이 그 주소를 알고 있는지, 가져간 뒤 색인에 넣지 않았다면 어떤 이유로 분류했는지가 나온다.

로그는 "구글봇이 무엇을 요청했나"에 답하고, Search Console은 "구글이 그걸 보고 무엇을 결정했나"에 답한다. 둘 중 하나만 보면 반쪽짜리다. 이 글은 그 두 쪽을 맞춰 보는 과정을 따라간다.

크롤링·렌더링·색인의 기본 흐름, `noindex`와 `canonical`, URL 검사 도구의 실제 URL 테스트는 [SPA와 SEO](/posts/seo-for-spa)에서 다뤘다. 여기서는 그다음, 사이트 전체를 놓고 "구글봇이 실제로 무엇을 읽었나"를 재는 쪽에 집중한다.

## 접근 로그 한 줄에 남는 것

Nginx 기본 `combined` 형식에 응답 시간(`$request_time`)을 하나 덧붙인 로그를 쓴다고 하자. 응답 시간은 기본 형식에 없으니 따로 넣어야 한다.

```nginx
# /etc/nginx/nginx.conf 의 http 블록
log_format seo '$remote_addr - $remote_user [$time_local] '
               '"$request" $status $body_bytes_sent '
               '"$http_referer" "$http_user_agent" $request_time';

access_log /var/log/nginx/access.log seo;
```

칸 번호는 공백으로 잘랐을 때 기준이다. User-Agent 안에도 공백이 있어서 뒤쪽 칸 번호는 UA마다 달라진다. 그래서 응답 시간은 `$NF`(마지막 칸)로 집는다. awk의 칸 나누기와 `$NF` 같은 기본기는 [grep, awk, sed](/posts/linux-grep-awk-sed)에 정리해 두었다.

이 글의 명령과 출력은 Ubuntu 24.04의 GNU awk로 돌렸다. 로그는 글을 위해 만든 하루치 실험 로그(3,450줄)다. 실제 서비스 로그는 훨씬 크지만 명령은 같다.

## 이름표는 누구나 붙일 수 있다

먼저 구글봇이라고 밝힌 요청이 몇 개인지, 어느 IP에서 왔는지 본다.

```bash
# UA에 Googlebot이 들어간 줄 수
grep -c 'Googlebot' access.log

# 그 요청들을 IP의 앞 세 칸으로 묶어 센다
grep 'Googlebot' access.log \
  | awk '{split($1, o, "."); print o[1]"."o[2]"."o[3]".x"}' \
  | sort | uniq -c | sort -rn
```

```text
1650
   1400 66.249.66.x
    163 203.0.113.x
     87 198.51.100.x
```

1,650개 중 250개가 구글과 상관없어 보이는 대역에서 왔다. SEO 도구, 경쟁사 스크래퍼, 취약점 스캐너가 UA를 구글봇으로 바꿔 다니는 일은 흔하다. 구글봇인 척하면 봇 차단 규칙을 통과하기 쉬워서다. 이걸 걸러내지 않고 세면 "구글봇이 `/products?color=` 주소를 엄청 긁는다"는 잘못된 결론이 나온다.

진짜인지 가리는 방법은 구글이 문서로 정해 두었다. IP로 역방향 DNS를 찾아 이름이 `googlebot.com`, `google.com`, `googleusercontent.com` 중 하나로 끝나는지 보고, 그 이름으로 다시 정방향 DNS를 찾아 처음 IP가 나오는지 확인한다. 두 번 묻는 이유는 아래 그림에서 보인다.

구글 문서에 실린 예시 형식은 이렇다(이 실험 환경은 외부 DNS에 나갈 수 없어서 문서의 예를 그대로 옮긴다).

```bash
# 역방향: IP → 이름
host 66.249.66.1
# 정방향: 이름 → IP, 처음 IP와 같아야 한다
host crawl-66-249-66-1.googlebot.com
```

```text
1.66.249.66.in-addr.arpa domain name pointer crawl-66-249-66-1.googlebot.com.
crawl-66-249-66-1.googlebot.com has address 66.249.66.1
```

정방향 조회를 빼먹으면 검증이 무의미해진다. PTR 레코드는 그 IP 대역을 가진 쪽이 관리하니, 공격자가 자기 서버의 PTR에 `crawl-1-2-3-4.googlebot.com`이라고 적어 두면 역방향 조회만으로는 통과해 버린다. 반면 `googlebot.com` 존의 A 레코드는 구글만 바꿀 수 있다. DNS 조회 자체의 흐름은 [DNS 글](/posts/dns)에 있다.

빙봇도 같은 방식이다. 역방향 이름이 `search.msn.com`으로 끝나고(예: `msnbot-157-55-39-1.search.msn.com`), 정방향으로 같은 IP가 나와야 한다. 빙 웹마스터 도구에는 IP를 넣어 확인하는 "Verify Bingbot" 화면도 있다.

## 로그 수십만 줄이면 IP 목록으로 대조한다

DNS를 IP마다 두 번씩 물으면 느리고, DNS 서버에도 부담이다. 그래서 구글과 빙은 크롤러 IP 대역을 JSON으로 공개한다. 구글은 일반 크롤러용 `googlebot.json`, 특수 크롤러용 `special-crawlers.json`, 사용자가 시켜서 가져가는 요청용 `user-triggered-fetchers.json`을 나눠 두고, 빙은 `bingbot.json`을 둔다. 형식은 이런 모양이다.

```json
{
  "creationTime": "...",
  "prefixes": [
    { "ipv4Prefix": "66.249.66.0/27" },
    { "ipv6Prefix": "2001:4860:4801:10::/64" }
  ]
}
```

목록은 바뀌니 하루에 한 번쯤 내려받아 쓰고, 목록에 없는 IP만 DNS로 다시 확인하면 된다. 아래는 IPv4 주소가 CIDR 대역 목록 안에 있는지 판정하는 함수다. 직접 채워 보자.

비트 연산(`<<`, `&`)으로 짜도 되지만, 자바스크립트의 비트 연산은 부호 있는 32비트라서 `128.0.0.0` 이상에서 음수가 나온다. `>>> 0`으로 부호를 지우거나 위 풀이처럼 곱셈으로 계산한다. 실제 서비스에서는 IPv6도 함께 처리해야 하니 `ipaddr.js` 같은 검증된 라이브러리를 쓰는 편이 낫다.

검증한 IP만 남긴 파일을 만들어 두고 이후 분석은 모두 이 파일로 한다. 실험 로그에서는 구글 대역이 `66.249.66.x` 하나라 간단히 거른다.

```bash
# 검증한 구글봇 요청만 따로 저장
grep 'Googlebot' access.log | grep '^66\.249\.' > googlebot.log
wc -l < googlebot.log
```

```text
1400
```

진짜로 확인됐다고 끝이 아니다. 같은 `googlebot.com`이라도 UA를 보면 스마트폰 구글봇과 데스크톱 구글봇이 나뉜다. 구글은 모바일 우선 색인을 쓰니 요청 대부분이 스마트폰 구글봇이어야 정상이다. 반대로 `Google-InspectionTool`(URL 검사 도구), `Storebot-Google`처럼 다른 이름의 크롤러도 섞여 있다. AI 학습용 수집을 가르는 `Google-Extended`는 크롤러가 아니라 robots.txt에 쓰는 토큰이라 로그에 따로 찍히지 않는다. 봇 종류별 차단 정책은 [AI 크롤러와 봇 제어](/posts/ai-crawlers-bot-control)에서 따로 다룬다.

## 구글봇은 어디에 시간을 쓰나

검증된 요청을 경로의 첫 칸으로 묶는다. 파라미터가 붙은 주소는 물음표를 붙여 따로 센다.

```bash
# 경로 첫 칸 기준 구역별 크롤 수. 쿼리스트링이 있으면 "?"를 붙여 따로 센다
awk '{
  split($7, u, "?"); split(u[1], s, "/")
  sec = "/" s[2]; if (u[2] != "") sec = sec "?"
  n[sec]++
} END { for (k in n) printf "%6d %s\n", n[k], k }' googlebot.log | sort -rn
```

```text
   626 /products?
   366 /products
   221 /posts
   123 /search?
    64 /old
```

1,400번 중 749번(53%)이 `/products?color=...&sort=...&page=...` 같은 필터 조합과 내부 검색 결과에 갔다. 정작 검색에 나와야 할 상품 상세(`/products/123`)와 글(`/posts/...`)은 합쳐 587번이다. 구글봇이 하루에 우리 사이트에서 쓰는 요청 수는 한정되어 있는데, 그 절반을 색인할 가치가 거의 없는 주소에 쓰고 있다. 필터 조합이 크롤을 먹는 구조와 막는 방법은 [크롤 예산과 패싯 내비게이션](/posts/crawl-budget-faceted-navigation)에서 자세히 본다.

`/old`는 예전 주소다. 301을 받고 끝나니 비용은 작지만, 아직도 내부 링크나 sitemap 어딘가에 옛 주소가 남아 있다는 신호다. 리다이렉트 정리는 [리다이렉트와 사이트 이전](/posts/seo-redirects-site-migration)을 참고한다.

## 상태 코드와 응답 시간이 크롤 속도를 바꾼다

```bash
# 검증된 구글봇 요청의 상태 코드 분포
awk '{print $9}' googlebot.log | sort | uniq -c | sort -rn
```

```text
   1167 200
     73 304
     64 301
     49 404
     47 503
```

구글봇은 서버가 힘들어 보이면 스스로 덜 온다. 500, 503, 429가 늘거나 응답이 느려지면 크롤 속도를 낮추고, 상태가 좋아지면 천천히 다시 올린다. 구글 문서도 급하게 크롤을 줄이고 싶으면 이 세 코드를 잠깐 돌려주라고 안내한다. 반대로 말하면, 원인 모를 503이 며칠씩 섞여 있으면 새 페이지를 발견하는 속도도 함께 떨어진다. 503이 이틀을 넘기면 구글이 그 주소를 색인에서 빼기 시작할 수 있다는 점도 기억해 둔다.

404는 그 자체로 문제가 아니다. 없는 상품이 404를 주는 건 맞는 동작이다. 다만 404를 받는 주소가 어디서 왔는지는 본다. 사람 방문 로그의 Referer에 우리 사이트가 찍혀 있으면 깨진 내부 링크다.

304가 보이는 건 좋은 신호다. 구글봇은 `If-Modified-Since`나 `If-None-Match`를 보내 바뀌었는지 묻고, 서버가 304로 답하면 본문을 다시 받지 않는다. 정적 글처럼 잘 안 바뀌는 페이지가 304를 주면 그만큼 크롤이 다른 곳에 쓰인다. 응답 헤더의 `Last-Modified`, `ETag`가 제대로 나가는지는 `curl -I`로 확인한다.

응답 시간을 구역별로 보면 어디가 느린지 바로 나온다.

```bash
# 구역별 요청 수와 평균 응답 시간(마지막 칸 $NF)
awk '{
  split($7, u, "?"); split(u[1], s, "/")
  sec = "/" s[2]; if (u[2] != "") sec = sec "?"
  c[sec]++; t[sec] += $NF
} END { for (k in c) printf "%-12s %5d건 평균 %.3fs\n", k, c[k], t[k]/c[k] }' googlebot.log | sort -k4 -rn
```

```text
/products?     626건 평균 1.100s
/products      366건 평균 0.827s
/search?       123건 평균 0.686s
/posts         221건 평균 0.127s
/old            64건 평균 0.010s
```

필터 주소가 평균 1.1초다. 크롤을 가장 많이 먹는 구역이 가장 느리기까지 하다. 상품 상세의 평균이 높은 건 503이 3~6초씩 걸려서다. 평균은 이렇게 꼬리에 끌려가니 실제로는 구역별 95번째 백분위수도 같이 본다(정렬 후 95% 위치의 값). 서버가 느리면 구글봇이 한 번에 여는 연결 수를 줄이고, 그만큼 새 상품까지 오는 시간이 늦어진다.

## sitemap에 있는데 한 번도 안 온 주소

이제 처음 질문으로 간다. 새 글은 크롤되긴 했나. sitemap에 있는 주소 목록과 로그에 나온 주소 목록을 비교하면 된다. `comm`은 정렬된 두 파일을 비교해 한쪽에만 있는 줄을 뽑는다.

```bash
# 로그에 나온 주소(파라미터 없는 것만) 목록
awk '{print $7}' googlebot.log | grep -v '?' | sort -u > crawled.txt

# sitemap에만 있고 로그에는 없는 주소 = 한 번도 크롤되지 않은 주소
comm -23 sitemap-urls.txt crawled.txt | head -5
comm -23 sitemap-urls.txt crawled.txt | wc -l
```

```text
/posts/post-26
/posts/post-27
/posts/post-28
/posts/post-29
/posts/post-30
15
```

sitemap에 있는 70개 중 15개는 하루 동안 구글봇이 한 번도 오지 않았다. 하루치만 보면 오해할 수 있으니 실제로는 30일치 로그로 같은 비교를 한다. 그래도 안 온 주소가 있다면 이유는 대개 셋 중 하나다. 구글이 주소를 아직 모르거나, 알지만 우선순위가 낮거나, 막혀 있다.

여기서 로그만으로는 더 나아가지 못한다. 구글이 주소를 아는지는 Search Console이 알려 준다.

반대 방향도 해 본다. `comm -13`은 로그에만 있는 주소다. sitemap에도 없고 내부 링크로도 안 걸려야 할 주소가 크롤되고 있다면, 어딘가에서 새어 나간 링크(옛 메일, 외부 사이트, 자바스크립트가 만든 주소)가 있다는 뜻이다. sitemap, 크롤러가 찾은 내부 링크, 로그, Search Console 네 목록을 모두 맞대면 내부 링크가 하나도 없는 고아 페이지도 찾을 수 있다. 이건 [사이트 구조와 내부 링크](/posts/site-architecture-internal-linking)에서 이어서 본다.

## 발견됨과 크롤링됨은 다른 단계다

Search Console의 페이지 색인 생성 보고서는 색인되지 않은 주소를 이유별로 묶는다. 그중 가장 많이 헷갈리는 두 항목이 "발견됨 - 현재 색인이 생성되지 않음(Discovered - currently not indexed)"과 "크롤링됨 - 현재 색인이 생성되지 않음(Crawled - currently not indexed)"이다. 둘은 이름이 비슷하지만 막힌 단계가 다르다.

발견됨은 구글이 주소를 알지만 아직 가져가지 않았다는 뜻이다. 로그에 그 주소가 한 번도 없다면 이 상태와 맞아떨어진다. 구글 문서는 대개 "가져가려 했지만 사이트에 부담이 될 것 같아 미뤘다"고 설명한다. 그러니 원인은 페이지 내용이 아니라 사이트 전체에 있다. 앞에서 본 것처럼 필터 주소에 크롤이 몰리고, 응답이 느리고, 503이 섞여 있으면 새 주소는 대기열 뒤로 밀린다. 사이트가 작은데도 발견됨에 머문다면 그 주소로 가는 내부 링크가 너무 적어서 우선순위가 낮은 경우가 많다.

크롤링됨은 가져갔지만 색인에 넣지 않기로 했다는 뜻이다. 로그에는 200으로 남아 있다. 이번엔 페이지 쪽을 본다. 내용이 빈약하거나(상품 이름과 가격만 있는 페이지 수천 개), 다른 페이지와 거의 같거나, 렌더링 결과가 빈 화면이거나. 구글은 이 상태의 주소를 나중에 다시 보고 색인할 수도 있고, 다시 제출할 필요는 없다고 안내한다. 같은 페이지를 "색인 생성 요청"으로 계속 밀어 넣는 건 해결책이 아니다.

정리하면 로그와 보고서를 이렇게 맞춘다. 로그에 없음 + 발견됨이면 크롤 우선순위 문제다(사이트 속도, 낭비되는 주소, 내부 링크). 로그에 200 + 크롤링됨이면 내용 문제다. 로그에 없음 + 보고서에도 없음이면 구글이 주소 자체를 모른다(sitemap 제출, 링크 확인).

처음 문의의 글 열다섯 편이 로그에 없고 보고서에서 발견됨으로 나온다면, 고칠 곳은 글이 아니라 사이트다. 필터 주소가 크롤을 덜 먹게 막고, 503이 나는 원인을 찾아 고치고, 새 글로 가는 내부 링크를 늘린다. 효과는 바로 오지 않으니 몇 주에 걸쳐 크롤링 통계와 로그의 구역별 비중이 옮겨 가는지 지켜본다.

이 밖에 자주 보는 이유 몇 가지는 성격이 다르다. "리디렉션이 포함된 페이지"와 "적절한 표준 태그가 포함된 대체 페이지"는 대개 의도한 결과라 고칠 게 없다. "robots.txt에 의해 차단됨"은 크롤 자체를 막은 것이라 그 안의 `noindex`도 읽히지 않는다. 의도한 것인지 보고, 의도하지 않았다면 robots.txt부터 고친다.

## URL 검사는 한 주소를 깊게 본다

보고서가 묶음을 보여 준다면 URL 검사는 주소 하나를 판다. 주소를 넣으면 색인된 버전 기준으로 이런 값이 나온다.

- 마지막 크롤 시각과 어떤 구글봇(스마트폰, 데스크톱)으로 가져갔는지. 로그의 시각과 맞춰 보면 그날 무슨 응답을 받았는지까지 확인된다.
- 사용자가 선언한 표준 URL과 Google이 선택한 표준 URL. 둘이 다르면 내 `canonical`이 무시된 것이다.
- 크롤 허용 여부, 페이지 가져오기 결과, 색인 허용 여부.
- 이 주소를 참조한 sitemap과 참조 페이지. 참조 페이지가 비어 있으면 구글이 아는 내부 링크가 없다는 뜻이다.

"실제 URL 테스트"는 지금 이 순간의 페이지를 가져와 렌더링해 본다. 고친 내용이 반영됐는지 확인할 때 쓰고, 렌더링된 HTML과 스크린샷 보는 법은 [SPA와 SEO](/posts/seo-for-spa)에 있다. 테스트가 통과해도 색인이 보장되지는 않는다. 테스트는 "가져갈 수 있다"만 보여 준다.

## 크롤링 통계는 서버 쪽 건강검진이다

Search Console 설정 메뉴 안의 크롤링 통계 보고서는 지난 90일 동안 구글이 우리 호스트에 보낸 요청을 요약한다. 앞에서 로그로 뽑은 숫자를 구글 쪽에서 본 버전이라 생각하면 된다.

- 총 크롤링 요청 수, 총 다운로드 크기, 평균 응답 시간 그래프. 평균 응답 시간이 오르는 날 요청 수가 내려가는 모양이 자주 보인다.
- 응답별, 파일 형식별, 목적별, Googlebot 유형별 분류. 목적은 새 주소를 찾는 "발견"과 아는 주소를 다시 보는 "새로고침"으로 나뉜다. 새 글을 많이 올렸는데 발견 비율이 낮다면 새 주소가 잘 안 보인다는 뜻이다.
- 호스트 상태. robots.txt 가져오기, DNS 확인, 서버 연결 세 가지가 문제없었는지 나온다.

호스트 상태의 robots.txt 항목은 특히 본다. robots.txt가 404처럼 없으면 구글은 전부 허용으로 보고 계속 크롤한다. 하지만 robots.txt가 5xx를 주면 구글은 무엇을 막았는지 모르니 사이트 전체 크롤을 잠시 멈춘다. CDN이 robots.txt를 캐시하지 못하게 설정했거나, 앱 서버가 robots.txt까지 동적으로 만들다가 죽으면 이런 일이 생긴다. 정적 파일로 두는 게 안전하다.

로그와 크롤링 통계의 숫자가 다르게 나오는 건 자연스럽다. CDN 뒤에 있으면 캐시에서 바로 응답한 요청은 원본 서버 로그에 남지 않는다. 이 경우엔 CDN의 로그(Cloudflare Logpush, CloudFront 표준 로그 등)를 봐야 하고, Vercel처럼 로그를 오래 들고 있지 않는 플랫폼은 로그 드레인으로 외부 저장소에 흘려 두어야 30일치 분석이 가능하다.

## 화면에 안 보이는 행은 API로 꺼낸다

Search Console 화면은 표에 최대 1,000행만 보여 준다. 글이 수천 개인 사이트에서 "노출은 있는데 클릭이 0인 주소"를 다 뽑으려면 부족하다. 그래서 두 가지 길이 있다.

Search Console API의 Search Analytics 조회는 한 번에 최대 25,000행을 돌려주고, `startRow`로 다음 페이지를 이어 받는다. 데이터는 최근 16개월까지다. URL Inspection API는 URL 검사를 코드로 부르는 것인데, 속성(사이트)당 하루 2,000건, 분당 600건 한도가 있다. 배포 뒤 중요한 주소 몇백 개의 색인 상태를 매일 확인하는 정도로 쓰기 좋다.

BigQuery 대량 내보내기는 설정해 두면 매일 실적 데이터를 내 BigQuery 데이터 세트로 넣어 준다. 사이트 단위 표(`searchdata_site_impression`), URL 단위 표(`searchdata_url_impression`), 내보내기 기록(`ExportLog`)이 생긴다. 설정한 날부터 쌓이고 과거 데이터를 채워 주지는 않으니 일찍 켜 두는 게 좋다. 16개월 제한도 없어져 장기 추세를 볼 수 있고, 접근 로그를 BigQuery에 같이 올리면 "크롤 수와 노출 수"를 주소 단위로 조인할 수 있다.

```sql
-- BigQuery: 최근 28일 동안 URL별 노출·클릭 상위 10개
SELECT url, SUM(impressions) AS impressions, SUM(clicks) AS clicks
FROM `my-project.searchconsole.searchdata_url_impression`
WHERE data_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 28 DAY)
GROUP BY url
ORDER BY impressions DESC
LIMIT 10;
```

노출·클릭 숫자를 어떻게 읽고, 왜 GA4와 숫자가 다른지는 [검색 유입 재기](/posts/search-traffic-measurement)에서 따로 다룬다.

## 크롤러를 직접 돌려 사이트를 감사한다

로그는 구글이 온 곳만, Search Console은 구글이 아는 곳만 보여 준다. 우리 사이트의 링크를 처음부터 끝까지 따라가 보는 건 크롤러 도구의 몫이다. Screaming Frog SEO Spider(무료판은 500개 주소까지), Sitebulb 같은 데스크톱 크롤러가 많이 쓰인다. 홈에서 출발해 `a href`를 따라가며 주소마다 상태 코드, `title`, `canonical`, robots 메타, 클릭 깊이, 들어오는 내부 링크 수를 표로 만든다. 자바스크립트 렌더링 모드를 켜면 렌더링 전후의 차이도 비교된다.

감사할 때 순서를 정해 두면 빠진 곳이 없다.

1. 크롤 가능성: robots.txt, 4xx·5xx, 리다이렉트 체인과 루프.
2. 색인 신호: `noindex`가 붙은 주소 목록이 의도와 맞는지, `canonical`이 자기 자신 또는 맞는 대표 주소를 가리키는지.
3. 중복과 빈약함: 같은 `title`, 같은 `description`, 본문이 거의 없는 주소.
4. 구조: 클릭 깊이 분포, 내부 링크가 하나뿐인 주소, sitemap에만 있는 고아 주소.
5. 렌더링: 렌더링 전 HTML과 후 DOM의 차이.

크롤러 결과는 늘 로그와 맞대 본다. 크롤러는 "링크가 있다"를 보여 주고 로그는 "구글이 실제로 그 링크를 따라왔다"를 보여 준다. 깊이 5인 주소가 로그에 거의 안 나타난다면 구조를 바꿀 근거가 된다.

자주 하는 실수 몇 가지가 있다. 크롤러를 프로덕션에 최고 속도로 돌려 사람 트래픽까지 느려지게 만드는 것(초당 요청 수를 제한한다). 크롤러 UA를 구글봇으로 바꿔 돌린 뒤 그 기록이 다음 달 로그 분석에 "구글봇"으로 섞이는 것. 그리고 스테이징을 감사하면서 프로덕션과 robots·`noindex` 설정이 다르다는 걸 잊는 것이다.

## 짐작보다 기록을 먼저 본다

"색인이 안 된다"는 말은 너무 넓다. 로그를 열면 구글봇이 그 주소에 왔는지, 무슨 코드를 받았는지, 사이트 어디에 요청을 쓰는지가 숫자로 보인다. 그 전에 UA가 아니라 DNS 두 번이나 공개 IP 목록으로 진짜 구글봇만 남긴다. Search Console은 구글이 그 주소를 발견만 했는지, 가져가고 나서 넣지 않았는지를 알려 준다. 발견 단계에서 멈췄다면 사이트 속도와 낭비되는 주소를, 크롤 뒤에 멈췄다면 페이지 내용을 고친다.

## 면접에서 나올 만한 질문

### 로그에서 구글봇 요청을 어떻게 골라내나요?

User-Agent 문자열은 누구나 보낼 수 있어서 근거가 되지 않는다. IP로 역방향 DNS를 조회해 이름이 `googlebot.com`, `google.com`, `googleusercontent.com`으로 끝나는지 보고, 그 이름을 다시 정방향 조회해 같은 IP가 나오는지 확인한다. 로그가 크면 구글이 공개하는 크롤러 IP 대역 JSON과 대조하고, 결과는 IP별로 캐시한다.

### 역방향 DNS만 확인하면 왜 안 되나요?

PTR 레코드는 그 IP 대역을 가진 쪽이 관리해서, 공격자가 자기 IP의 PTR에 `googlebot.com` 이름을 적을 수 있다. 정방향 조회는 `googlebot.com` 존에서 답이 오고, 그 존은 구글만 고칠 수 있다. 두 방향이 같은 IP로 맞아야 위조가 아니라고 판단할 수 있다.

### "발견됨 - 현재 색인이 생성되지 않음"과 "크롤링됨 - 현재 색인이 생성되지 않음"의 차이는요?

발견됨은 주소는 알지만 아직 가져가지 않은 상태로, 대개 사이트 부담을 피하려고 크롤을 미룬 것이다. 그래서 서버 속도, 5xx, 크롤을 먹는 파라미터 주소, 내부 링크 부족처럼 사이트 쪽을 본다. 크롤링됨은 가져갔지만 넣지 않기로 한 상태라 내용이 빈약하거나 중복인지, 렌더링이 제대로 됐는지 페이지 쪽을 본다.

### 서버 응답이 느려지면 SEO에 어떤 영향이 있나요?

순위보다 먼저 크롤에 영향이 간다. 구글봇은 응답이 느려지거나 500, 503, 429가 늘면 크롤 속도를 낮춘다. 그러면 새 페이지를 발견하고 바뀐 내용을 반영하는 속도가 함께 늦어진다. 크롤링 통계 보고서에서 평균 응답 시간과 요청 수가 반대로 움직이는 모습으로 확인할 수 있다.

### 로그 분석으로 무엇을 찾을 수 있나요?

구역별 크롤 비중으로 파라미터 주소나 내부 검색 결과가 크롤을 낭비하는지 본다. 상태 코드 분포로 5xx, 불필요한 301, 깨진 링크를 찾고, 응답 시간으로 느린 구역을 찾는다. sitemap 목록과 비교해 한 번도 크롤되지 않은 중요 주소를, 반대로 로그에만 있는 주소로 새어 나간 링크를 찾는다.

### robots.txt가 5xx를 주면 어떻게 되나요?

구글은 무엇을 막았는지 알 수 없으니 사이트 전체 크롤을 잠시 멈춘다. 404처럼 파일이 없는 경우는 전부 허용으로 보는 것과 반대다. 그래서 robots.txt는 정적 파일로 두고, 크롤링 통계의 호스트 상태에서 가져오기 실패가 없는지 확인한다.

### Search Console 화면 대신 API나 BigQuery 내보내기를 쓰는 이유는요?

화면 표는 1,000행까지만 보여 주고 데이터도 16개월까지만 남는다. Search Analytics API는 요청당 25,000행씩 페이지를 넘기며 받을 수 있고, URL Inspection API는 하루 2,000건까지 색인 상태를 코드로 확인한다. BigQuery 내보내기는 설정한 날부터 매일 쌓여 장기 보관이 되고, 접근 로그와 주소 단위로 조인할 수 있다.

### CDN 뒤에 있는 사이트의 로그 분석에서 주의할 점은요?

원본 서버 로그의 IP가 CDN이나 로드 밸런서 IP로 찍히니 `X-Forwarded-For` 같은 헤더로 원래 IP를 복원해야 봇 검증이 된다. 캐시에서 바로 응답한 요청은 원본 로그에 남지 않아 크롤 수가 적게 보인다. CDN 쪽 로그를 함께 수집하고, 로그를 짧게만 보관하는 플랫폼이면 드레인으로 외부 저장소에 쌓아 둔다.
