새 버전을 스테이징에서 다 확인하고 내보냈는데 운영에서 에러율이 0.5%에서 3%로 뛰었다. 스테이징에는 없는 오래된 계정 데이터에서만 터지는 버그였다. 블루그린으로 한 번에 넘겼으니 모든 사용자가 그 3%를 겪었고, 되돌리기는 빨랐지만 이미 수천 건이 실패한 뒤였다.

운영에서만 드러나는 문제는 운영에서 확인할 수밖에 없다. 카나리 릴리스는 그 확인을 작게 한다. 새 버전에 트래픽의 5%만 보내고, 옛 버전과 지표를 나란히 비교한 다음, 괜찮으면 25%, 50%, 100%로 늘린다. 나빠 보이면 0%로 돌린다. 이름은 탄광에 먼저 들여보내 유독 가스를 알아차리던 카나리아에서 왔다. 작은 무리가 먼저 위험을 겪고, 나머지는 그 신호를 보고 움직인다.

이 주제의 다른 글: 두 벌을 띄워 한 번에 바꾸는 [블루그린 배포](/posts/blue-green-deployment), 서버를 몇 대씩 차례로 바꾸는 [롤링 배포](/posts/rolling-deployment). 기능 단위로 켜고 끄는 [피처 플래그](/posts/feature-flags)와 실험 통계를 다루는 [A/B 테스트](/posts/ab-testing)도 비율로 나눈다는 점은 같지만, 카나리는 "이 배포가 안전한가"를 묻고 A/B 테스트는 "어느 쪽이 더 나은가"를 묻는다.

출력은 Ubuntu 24.04 컨테이너의 network namespace 안에서 받았다. Node.js 백엔드 둘(stable v1은 9101, canary v2는 9102)을 띄우고 nginx 1.24 앞에서 나눴다. 일부러 나쁜 카나리는 요청의 3%에 500을 내고 35ms 걸리도록, 정상 카나리와 stable은 0.5%에 500을 내고 20ms 걸리도록 만들었다. 부하는 keep-alive 연결 50개로 쉬지 않고 요청을 보내는 Node.js 스크립트가 만든다.

## 비율로 나누는 두 가지 방법

nginx에서 비율을 나누는 방법은 크게 두 가지다. upstream의 `weight`와 `split_clients`다. 둘은 "무엇을 기준으로 나누나"가 다르다.

```nginx
# 방법 1: 가중치 라운드 로빈. 요청 20개 중 1개를 카나리로
upstream weighted {
    server 127.0.0.1:9101 weight=19;   # stable v1
    server 127.0.0.1:9102 weight=1;    # canary v2
    keepalive 16;
}

# 방법 2: 문자열을 해시해서 나눈다. 무엇을 해시하느냐가 핵심이다
split_clients "${request_id}" $by_request { 5% canary; * stable; }   # 요청마다
split_clients "${cookie_uid}" $by_user    { 5% canary; * stable; }   # 사용자마다

upstream stable { server 127.0.0.1:9101; keepalive 16; }
upstream canary { server 127.0.0.1:9102; keepalive 16; }
```

`weight`는 서버를 고르는 알고리즘의 일부다. 가중치 라운드 로빈이 어떻게 고르게 섞는지는 [로드 밸런싱 알고리즘 글](/posts/load-balancing-algorithms)에 있다. `split_clients`는 주어진 문자열을 MurmurHash2로 해시해서 그 값이 어느 구간에 떨어지는지로 변수를 정한다. 같은 문자열이면 항상 같은 쪽이다.

접근 로그에 어느 upstream이 받았는지 남겨 두면 실제 비율을 셀 수 있다.

```nginx
log_format canary '$msec $upstream_addr $status $request_time';
access_log /var/log/nginx/canary.log canary;
```

## 요청마다 나눌까, 사람마다 나눌까

5%라는 숫자가 같아도 무엇의 5%인지에 따라 사용자 경험이 다르다. 사용자 2000명이 각자 요청을 5번씩 보내게 하고, 카나리를 한 번이라도 본 사람과 두 버전을 오간 사람을 셌다.

```text
# 요청 ID로 나눈 경우 (/req)
users=2000 canary_users=449 (22.4%) users_who_saw_both=449
# 쿠키 uid로 나눈 경우 (/user)
users=2000 canary_users=89 (4.5%) users_who_saw_both=0
```

요청마다 나누면 요청의 5%는 맞지만, 사용자로 보면 22.4%가 카나리를 한 번은 봤고 그 사람들 모두 두 버전을 오갔다. 5번 중 한 번이라도 걸릴 확률이 1 − 0.95⁵ ≈ 22.6%이니 계산과 맞는다. 화면이 바뀌는 배포라면 새로고침할 때마다 버튼 위치가 바뀌는 셈이다. 새 버전이 쓴 데이터를 옛 버전이 읽는 일도 같은 사용자 안에서 일어난다.

사용자 ID나 쿠키로 나누면 4.5%가 카나리에 고정되고 오가는 사람이 없다. 대신 로그인 전 사용자처럼 ID가 없는 요청을 어떻게 할지 정해야 한다. 쿠키가 비면 해시 대상이 빈 문자열이라 모두 같은 쪽으로 간다. 처음 방문할 때 무작위 `uid` 쿠키를 심어 두는 게 흔한 해결이다.

헤더나 쿠키로 강제하는 규칙은 비율보다 앞에 둔다. 사내 사람이 `X-Canary: always`를 붙이면 0% 단계에서도 새 버전을 써 볼 수 있고, 문제가 있는 고객에게 `canary=never` 쿠키를 주면 카나리에서 빼낼 수 있다.

```nginx
# 헤더 또는 쿠키가 있으면 비율보다 먼저 적용한다
map "$http_x_canary$cookie_canary" $forced {
    default    "";
    "~^always" canary;
    "~^never"  stable;
}
map $forced $pool_user { "" $by_user; default $forced; }

location / { proxy_pass http://$pool_user; }
```

```bash
# 헤더로 카나리를 강제한다
curl -s -H 'X-Canary: always' http://127.0.0.1:8081/req
# 쿠키로 강제한다
curl -s --cookie 'canary=always' http://127.0.0.1:8081/user
# uid가 카나리 구간이어도 never가 이긴다
curl -s -H 'X-Canary: never' --cookie uid=u1 http://127.0.0.1:8081/user
```


쿠버네티스 ingress-nginx에서는 같은 일을 `canary-by-header`, `canary-by-cookie`, `canary-weight` 어노테이션이 한다. 설정 모양은 [Ingress 글](/posts/kubernetes-ingress)에, Gateway API의 가중치와 헤더 규칙은 [Gateway 글](/posts/gateway)에 있다. 서비스 사이 호출을 나눌 때는 [서비스 메시](/posts/service-mesh)의 사이드카가 같은 일을 한다.

## 지표가 다음 단계를 정한다

카나리의 단계는 대개 이렇게 생겼다. 가중치를 올리고, 일정 시간 지표를 모으고, 기준과 비교해서 다음 단계로 가거나 멈춘다. 사람이 대시보드를 보며 할 수도 있지만, 새벽 배포에서 사람은 놓친다. 그래서 규칙으로 만든다.

판단 규칙을 작게 만들어 nginx 앞에서 직접 돌려 봤다. 단계는 5, 25, 50, 100%이고 단계마다 6초씩 부하를 건다. 두 가지를 본다. 카나리 에러율이 stable보다 통계적으로 높은지(두 비율의 z 검정, z > 2.33이면 99% 수준에서 높다고 본다), 카나리 p95가 stable의 1.2배를 넘는지다.

```bash
# 가중치를 바꾸고 → 부하 → 로그 분석 → 승격/중단을 단계마다 반복한다
node rollout.js /etc/nginx
```

나쁜 카나리를 넣었을 때다.

```text
weight=  5%  canary n=632 err=2.85% p95=39ms  stable n=12007 err=0.46% p95=23ms  502=0 conn_err=0  -> ABORT (error z=7.7, p95 x1.70)
weight=  0%  rolled back to stable
```

첫 단계에서 멈췄다. 6초 동안 카나리가 받은 요청은 632건이고, 그중 2.85%가 실패했다. 전체 요청으로 보면 실패한 카나리 요청은 18건쯤이다. 블루그린으로 한 번에 넘겼다면 같은 6초 동안 요청 약 1만 2천 건의 3%, 380건쯤이 실패했을 것이다.

정상 카나리(stable과 같은 에러율과 지연)로 바꿔 다시 돌렸다.

```text
weight=  5%  canary n=586 err=0.51% p95=27ms  stable n=11183 err=0.48% p95=25ms  502=0 conn_err=0  -> promote (z=0.1)
weight= 25%  canary n=3458 err=0.32% p95=22ms  stable n=10418 err=0.58% p95=22ms  502=0 conn_err=42  -> promote (z=-1.8)
weight= 50%  canary n=6774 err=0.62% p95=22ms  stable n=6797 err=0.63% p95=22ms  502=0 conn_err=16  -> promote (z=-0.1)
weight=100%  canary n=13376 err=0.55% p95=23ms  stable n=23 err=0.00% p95=23ms  502=0 conn_err=0  -> done
```

네 단계를 다 지나 100%가 됐다. 볼 곳이 두 군데 있다. 하나는 마지막 줄의 `stable n=23`이다. 100%로 바꾼 직후에도 옛 워커가 처리하던 요청 23건은 stable이 끝냈다. 다른 하나는 `conn_err=42`, `conn_err=16`이다. 이 스크립트는 reload 직후에 새 연결 50개를 한꺼번에 여는데, 연결을 막 여는 순간이 reload와 겹치면 정리 중인 옛 워커가 받은 연결이 `ECONNRESET`으로 끊긴다. 이미 열린 연결로 계속 요청하는 동안 가중치를 바꾼 다른 실험에서는 1만 2천 건 중 0건이었다. 가중치를 단계마다 바꾸는 카나리는 reload를 여러 번 하니, 클라이언트가 멱등한 요청을 한 번 다시 보내도록 해 두거나 reload 없이 가중치를 바꾸는 프록시(Envoy의 xDS, NGINX Plus의 API, HAProxy의 런타임 API)를 쓴다.

## 작은 비율은 증거가 적다

5%에서 바로 잡힌 건 나쁜 카나리가 6배나 나빴기 때문이다. 실제 배포에서 흔한 건 "조금" 나쁜 버전이다. 에러율이 0.5%에서 1%로 두 배가 되는 정도. 이걸 작은 비율에서 잡을 수 있을까.

시뮬레이션으로 확인했다. 한 단계에 요청 1만 건이 지나가고, stable의 실제 에러율은 0.5%다. 정상 카나리(0.5%)를 잘못 중단하는 비율과 나쁜 카나리(1.0%)를 제대로 중단하는 비율을 5000번씩 돌려 셌다. 판단 규칙은 둘이다. "카나리 에러율이 stable의 2배를 넘으면 중단"하는 단순한 규칙과 위의 z 검정이다.

```bash
# 시드를 고정한 시뮬레이션. 카나리 비율과 판단 규칙별로 오판 비율을 센다
node noise.js
```

```text
share  canary_n  rule   good->abort  bad(2x)->abort
1%          100  naive         23.6%           46.2%
1%          100  z>2.33         2.5%           11.3%
5%          500  naive          8.3%           47.5%
5%          500  z>2.33         2.2%           26.1%
25%        2500  naive          1.6%           48.5%
25%        2500  z>2.33         1.3%           64.5%
```

1% 단계에서 카나리가 받는 요청은 100건이다. 에러율 0.5%면 기대값이 0.5건이니, 에러가 한 건만 나도 1%가 되어 "두 배"가 된다. 그래서 단순한 규칙은 멀쩡한 카나리를 네 번에 한 번꼴(23.6%)로 중단한다. z 검정은 그런 오판을 2.5%로 줄이지만, 나쁜 카나리를 11.3%밖에 못 잡는다. 증거가 모자라면 어느 규칙도 둘 다 잘할 수 없다.

여기서 나오는 실무 규칙이 있다. 작은 비율 단계에서는 "확실히 나쁜 것"만 잡는다고 생각한다. 크래시, 에러율 몇 배 급등, 지연 폭증 같은 것이다. 미묘한 차이는 25~50% 단계에서 충분한 요청이 쌓인 뒤에야 보인다. 그래서 단계마다 "최소 요청 수"를 두고, 그만큼 모이기 전에는 판단하지 않고 기다린다. 트래픽이 적은 서비스라면 5분이 아니라 몇 시간을 기다려야 같은 증거가 모인다.

아래 함수를 완성해 보자. 표본이 모자라면 `"wait"`, 카나리 에러율이 통계적으로 높으면 `"abort"`, 아니면 `"promote"`를 돌려준다. 첫 테스트는 위 나쁜 카나리의 실제 숫자다.

## Argo Rollouts와 Flagger가 자동으로 하는 일

쿠버네티스에서는 위 반복을 도구가 맡는다. Argo Rollouts는 Deployment 대신 `Rollout` 리소스를 쓰고, 단계와 분석을 선언한다. Flagger는 기존 Deployment를 그대로 두고 옆에 `Canary` 리소스를 붙인다. 둘 다 트래픽을 나누는 일은 ingress-nginx, Gateway API, Istio 같은 다른 장치에 시키고, 자기는 가중치를 바꾸고 지표를 묻는 일만 한다.

아래는 이 흐름을 선언한 예시다. 이 컨테이너에는 클러스터와 Prometheus가 없어 실행하지 않았다.

```yaml
# 예시: 5xx 비율이 1%를 넘는 측정이 두 번 나오면 실패로 본다
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: error-rate
spec:
  args:
    - name: service-name
  metrics:
    - name: error-rate
      interval: 1m            # 1분마다 묻는다
      count: 5                # 다섯 번 묻는다
      failureLimit: 1         # 실패가 1번을 넘으면(2번째) 중단
      successCondition: result[0] <= 0.01
      provider:
        prometheus:
          address: http://prometheus.monitoring:9090
          query: |
            sum(rate(http_requests_total{service="{{args.service-name}}",code=~"5.."}[2m]))
            /
            sum(rate(http_requests_total{service="{{args.service-name}}"}[2m]))
---
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: web
spec:
  # replicas, selector, template은 Deployment와 같다
  strategy:
    canary:
      canaryService: web-canary
      stableService: web-stable
      trafficRouting:
        nginx:
          stableIngress: web     # 이 Ingress를 본떠 카나리용 Ingress를 만든다
      analysis:
        templates:
          - templateName: error-rate
        startingStep: 1          # 첫 setWeight 뒤부터 분석을 돌린다
        args:
          - name: service-name
            value: web-canary
      steps:
        - setWeight: 5
        - pause: { duration: 10m }
        - setWeight: 25
        - pause: { duration: 10m }
        - setWeight: 50
        - pause: { duration: 10m }
```

설정에서 자주 틀리는 곳이 있다. 쿼리의 분모가 0이면(카나리에 요청이 하나도 없으면) 결과가 NaN이나 빈 값이 되고, 이게 성공인지 실패인지는 조건식이 정한다. 트래픽이 적은 새벽에 분석이 "통과"로 끝나는 건 대개 이 경우다. `rate()`의 범위를 `interval`보다 짧게 잡으면 측정 사이 구간이 빠진다. 그리고 에러율만 보면 아예 요청을 받지 못하는 카나리(라우팅이 틀려 0%)를 놓친다. 요청 수 자체도 조건에 넣는다.

Flagger는 같은 일을 `analysis` 블록 하나로 쓴다. `stepWeight: 5`, `maxWeight: 50`, `threshold: 2`처럼 "몇 %씩 올리고, 어디까지 올리고, 몇 번 실패하면 멈추나"를 숫자로 주고, 기본 지표로 요청 성공률과 지연을 쓴다. 승격하는 방식은 다르다. Flagger는 카나리의 스펙을 primary Deployment에 복사해 평소의 롤링 업데이트로 바꾸고(그 과정은 [Deployment 글](/posts/k8s-deployment)에 있다), Argo Rollouts는 ReplicaSet을 직접 다루면서 카나리 ReplicaSet을 그대로 새 stable로 삼는다.

## 카나리가 거짓말하는 순간

카나리가 통과했는데 100%에서 터지는 경우가 있다. 원인 몇 가지는 반복해서 나온다.

카나리만 쓰는 의존성이 없는 경우. 새 버전이 새 DB 쿼리를 쓰는데 5%에서는 DB가 버티다가 100%에서 커넥션 풀이 마른다. 카나리는 "이 코드가 맞나"는 잘 보지만 "이 코드가 전체 부하에서 버티나"는 보지 못한다. 공유 자원의 지표(DB CPU, 커넥션 수, 큐 길이)도 단계마다 같이 본다.

카나리 트래픽이 대표적이지 않은 경우. 사용자 ID로 나눴는데 해시 구간에 우연히 무료 사용자만 몰렸다거나, 헤더 강제로 들어온 내부 사용자 트래픽이 카나리의 대부분이라 실제 사용자 패턴이 아니다. 카나리로 간 요청의 경로·국가·클라이언트 분포가 stable과 비슷한지 본다.

지표가 카나리를 구분하지 못하는 경우. 메트릭 라벨에 버전이나 Pod 종류가 없으면 대시보드는 전체 평균만 보여 준다. 5% 카나리의 에러율이 3%여도 전체로는 0.5%에서 0.6%로 오를 뿐이라 눈에 띄지 않는다. 메트릭과 로그에 `version`이나 `track=canary` 라벨을 붙이는 게 카나리의 첫 준비다.

되돌릴 수 없는 일을 하는 경우. 카나리가 DB 스키마를 바꾸거나, 외부로 이메일을 보내거나, 새 형식으로 데이터를 쓰면 가중치를 0으로 돌려도 그 흔적은 남는다. 스키마는 넓히기와 좁히기로 나눠 배포에서 떼어 놓고([무중단 마이그레이션](/posts/zero-downtime-migrations)), 외부 효과가 있는 기능은 [피처 플래그](/posts/feature-flags)로 따로 막아 둔다. 카나리가 중단됐을 때 무엇을 더 되돌려야 하는지는 [롤백 전략](/posts/rollback-strategy)에서 다룬다.

## 작게 겪고, 증거가 쌓이면 넓힌다

카나리 릴리스는 새 버전에 운영 트래픽의 일부만 보내고, 같은 시간의 옛 버전과 지표를 비교해서 비율을 올리거나 0으로 돌리는 배포다. 나누는 기준이 요청인지 사용자인지에 따라 사용자 경험이 달라지고, 헤더·쿠키 강제 규칙은 비율보다 앞에 둔다. 작은 비율 단계는 증거가 적어 큰 문제만 잡을 수 있으니, 최소 요청 수와 통계적 기준을 함께 두고 미묘한 차이는 큰 비율에서 본다. 판단은 사람보다 규칙이 하게 만들고, 그 규칙이 카나리를 구분할 수 있도록 메트릭에 버전 라벨을 붙이는 것부터 시작한다.

## 면접에서 나올 만한 질문

### 카나리 배포가 무엇이고 블루그린과 어떻게 다른가요?

새 버전에 운영 트래픽의 일부만 보내 지표를 확인하고, 괜찮으면 비율을 단계적으로 늘리는 배포입니다. 블루그린은 확인을 전환 전에 끝내고 전체를 한 번에 옮기니 문제가 있으면 모두가 잠깐 겪고, 카나리는 일부만 겪지만 두 버전이 오래 섞입니다. 그래서 카나리는 API와 스키마가 두 버전과 모두 맞아야 하고, 비교할 지표와 자동화가 필요합니다.

### nginx에서 카나리 비율은 어떻게 나누나요?

upstream의 weight로 나누거나 split_clients로 문자열을 해시해서 나눕니다. weight는 라운드 로빈 순서로 돌려 비율이 정확하고, split_clients는 요청 ID나 사용자 쿠키 같은 값을 해시해서 같은 값은 항상 같은 쪽으로 보냅니다. 실제로 재 보니 weight 19대 1은 5.00%, 요청 ID 해시 5%는 5.17%였습니다.

### 요청 단위로 5%를 나누면 무엇이 문제인가요?

요청의 5%이지 사용자의 5%가 아닙니다. 사용자가 요청을 다섯 번 보내면 약 22%가 카나리를 한 번은 보고, 그 사람들은 두 버전을 오갑니다. 화면이 바뀌거나 버전마다 데이터 형식이 다르면 문제가 되니, 사용자 ID나 쿠키로 나눠 사람마다 고정합니다.

### 카나리를 자동으로 승격하거나 중단하는 기준은 어떻게 정하나요?

같은 시간대의 stable이나 baseline과 에러율, 지연 백분위를 비교합니다. 에러율은 두 비율의 차이가 통계적으로 의미 있는지 보고, 지연은 p95나 p99 비율로 봅니다. 단계마다 최소 요청 수를 두고 그만큼 쌓이기 전에는 판단하지 않습니다. 지난주 숫자나 절대값 하나와 비교하면 트래픽 패턴 차이가 섞입니다.

### 1% 카나리에서 에러율이 두 배로 보이면 바로 중단해야 하나요?

표본 수부터 봅니다. 1%면 요청이 100건뿐일 수 있고, 에러율 0.5%에서 에러 한 건만 나도 1%가 되어 두 배처럼 보입니다. 시뮬레이션에서 "두 배면 중단" 규칙은 멀쩡한 카나리를 23.6% 확률로 중단했습니다. 작은 단계에서는 크래시나 몇 배 급등 같은 큰 문제만 잡고, 미묘한 차이는 25~50% 단계에서 충분한 요청이 쌓인 뒤 판단합니다.

### baseline을 따로 띄우는 이유는 무엇인가요?

막 뜬 카나리와 오래 떠 있던 stable은 캐시, JIT, 커넥션 상태가 달라서 버전 말고도 차이가 납니다. 옛 버전을 카나리와 같은 시각에 같은 수로 새로 띄우면 그 차이가 양쪽에 똑같이 들어가 버전 차이만 남습니다. Spinnaker의 Kayenta가 이렇게 비교합니다.

### 카나리를 통과했는데 100%에서 장애가 났습니다. 무엇을 의심하나요?

공유 자원이 먼저입니다. 5%에서는 DB나 캐시가 버티다가 100%에서 커넥션 풀이나 CPU가 바닥나는 경우입니다. 그다음 카나리 트래픽이 대표적이었는지(내부 사용자나 특정 사용자군에 치우치지 않았는지), 메트릭에 버전 라벨이 있어 카나리 지표를 따로 볼 수 있었는지 확인합니다. 그래서 단계마다 공유 자원 지표도 함께 봅니다.

### 카나리를 0%로 되돌리면 모든 게 원래대로 돌아가나요?

트래픽만 돌아갑니다. 카나리가 바꾼 스키마, 새 형식으로 쓴 데이터, 보낸 이메일이나 결제 요청은 남습니다. 그래서 스키마 변경은 배포와 떼어 넓히기·좁히기로 하고, 외부 효과가 있는 기능은 피처 플래그로 따로 막아 둡니다.
