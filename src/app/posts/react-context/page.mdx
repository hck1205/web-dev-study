<EasyIntro>
  학교에서 교장 선생님이 전하는 말을 반장에게, 반장이 분단장에게, 분단장이 짝꿍에게 차례로 전하면 중간 사람들은 자기와 상관없는 말을 계속 옮겨야 한다. React에서도 맨 위 컴포넌트의 값을 맨 아래까지 보내려면 중간 컴포넌트들이 쓰지도 않는 값을 계속 넘겨줘야 한다. Context는 교내 방송 같은 것이다. 방송실에서 한 번 말하면 듣고 싶은 교실이 스피커로 바로 듣는다. 그런데 방송이 바뀔 때마다 스피커를 켜 둔 교실은 하던 일을 멈추고 모두 다시 귀를 기울인다. 방송 내용 중 자기 반 이야기는 한 줄뿐이어도 그렇다. 그래서 자주 바뀌는 소식과 가끔 바뀌는 소식은 채널을 나눠 방송하는 게 좋다. 그리고 방송은 말을 전하는 도구일 뿐, 말의 내용을 기억하고 고치는 일은 방송실에 있는 사람이 따로 한다.
</EasyIntro>

설정 화면에서 언어를 바꾸는 기능을 붙이고 있었다. 날짜를 "3일 전"처럼 보여 주는 `RelativeTime` 컴포넌트가 `locale`을 알아야 하는데, 이 컴포넌트는 `App → Layout → Feed → PostCard → PostMeta → RelativeTime`의 여섯 번째 층에 있다. 그 사이 네 컴포넌트는 `locale`을 쓰지도 않으면서 받아서 넘기기만 한다.

```tsx
function Feed({ posts, locale }: { posts: Post[]; locale: string }) {
  return posts.map((p) => <PostCard key={p.id} post={p} locale={locale} />);
}
function PostCard({ post, locale }: { post: Post; locale: string }) {
  return <article><h2>{post.title}</h2><PostMeta post={post} locale={locale} /></article>;
}
```

이걸 prop drilling이라고 부른다. 귀찮은 것도 문제지만 진짜 문제는 결합이다. `PostCard`의 타입에 자기와 상관없는 `locale`이 들어가고, 나중에 `timeZone`을 하나 더 넘기려면 다섯 파일을 고쳐야 한다. Context는 이 문제를 푸는 도구다. 그리고 리렌더링 문제를 만들기 쉬운 도구이기도 하다. `value` 객체를 `useMemo`로 고정하고 상태와 dispatch를 나누는 기본은 [React는 언제 다시 그리나](/posts/react-rerender)에서 짧게 봤다. 이 글은 그 아래의 동작 원리, 셀렉터가 없는 이유와 대안, 그리고 실무에서 context를 어디에 쓰고 어디에 쓰지 않을지를 본다.

## context보다 먼저 볼 것: 합성

prop drilling이 보이면 바로 context로 가기 전에 한 번 확인할 것이 있다. 중간 컴포넌트가 정말 그 자식을 직접 만들어야 하는가. 많은 경우 중간 층은 레이아웃일 뿐이라, 완성된 엘리먼트를 받아서 꽂기만 하면 된다.

```tsx
function PostCard({ title, meta }: { title: string; meta: ReactNode }) {
  return <article><h2>{title}</h2>{meta}</article>; // locale을 몰라도 된다
}

function Feed({ posts, locale }: { posts: Post[]; locale: string }) {
  return posts.map((p) => (
    <PostCard key={p.id} title={p.title} meta={<PostMeta post={p} locale={locale} />} />
  ));
}
```

`locale`을 쓰는 쪽과 가진 쪽이 한 컴포넌트 안에서 만난다. `PostCard`는 `meta` 자리에 무엇이 들어오는지 모른다. React 공식 문서도 context 전에 이 방법(`children`이나 슬롯 props)을 먼저 써 보라고 한다. 층이 두세 개면 그냥 props로 넘기는 것도 나쁘지 않다. 데이터가 어디서 오는지 코드에 다 보이기 때문이다.

context가 맞는 건 트리의 아주 많은 곳에서, 서로 멀리 떨어진 컴포넌트들이 같은 값을 읽을 때다. 테마, 로그인한 사용자, 언어, 라우터, 폼 라이브러리의 폼 상태 같은 것들이다.

## context는 전달 통로다

context를 쓰는 순서는 셋이다. `createContext`로 통로를 만들고, Provider로 값을 넣고, `useContext`(또는 19의 `use`)로 꺼낸다.

```tsx
const LocaleContext = createContext("ko-KR"); // 기본값

function App() {
  const [locale, setLocale] = useState("ko-KR"); // 상태는 여기서 산다
  return (
    <LocaleContext value={locale}>
      <Layout />
    </LocaleContext>
  );
}

function RelativeTime({ date }: { date: Date }) {
  const locale = useContext(LocaleContext); // 가장 가까운 위쪽 Provider의 값
  return <time>{formatRelative(date, locale)}</time>;
}
```

여기서 context가 하는 일을 정확히 말하면 "위에서 넣은 값을 아래에서 꺼내게 해 주는 것"뿐이다. 값을 저장하지도, 바꾸지도 않는다. `locale`을 기억하고 바꾸는 건 `App`의 `useState`다. context는 그 값을 여섯 층 아래까지 배달할 뿐이다. 그래서 "context로 상태 관리를 한다"는 말은 정확하지 않다. 상태 관리는 `useState`나 `useReducer`가 하고 context는 전달을 맡는다. 이 구분이 중요한 이유는 뒤에서 볼 성능 특성이 전부 "전달"의 성질에서 나오기 때문이다. 상태를 저장하고 일부만 구독하게 해 주는 도구는 따로 있다.

`useContext`는 자기보다 위에 있는 가장 가까운 Provider를 찾는다. 같은 context의 Provider를 중첩하면 안쪽이 이긴다. 페이지 대부분은 밝은 테마인데 사이드바만 어두운 테마로 그리고 싶으면 사이드바를 `<ThemeContext value="dark">`로 한 번 더 감싸면 된다. Portal로 다른 DOM 위치에 그린 모달도 React 트리에서는 원래 자리에 있으니 위쪽 Provider의 값을 그대로 읽는다.

### 기본값이 쓰이는 때

`createContext`에 넘긴 기본값은 위에 Provider가 하나도 없을 때만 쓰인다. Provider가 있는데 `value`를 `undefined`로 넣으면 기본값이 아니라 `undefined`가 나온다. Provider 없이 렌더링한 컴포넌트는 정말로 기본값을 받는다. `createContext({ theme: "light" })`로 만들고 Provider 없이 읽으면 `light`가 나온다.

기본값의 쓰임은 두 가지다. 하나는 Provider 없이도 말이 되는 값이 있을 때다. 테마 기본값 `light`, 언어 기본값 `ko-KR`처럼. 테스트나 스토리북에서 컴포넌트 하나만 띄울 때 Provider를 일일이 감싸지 않아도 된다.

다른 하나는 반대로, Provider 없이 쓰면 안 되는 context에서 실수를 잡는 것이다. 로그인 정보나 장바구니 같은 context는 기본값을 `null`로 두고, 꺼내는 커스텀 훅에서 바로 에러를 던진다.

```tsx
const AuthContext = createContext<AuthValue | null>(null);

export function useAuth() {
  const value = useContext(AuthContext);
  if (value === null) throw new Error("useAuth는 AuthProvider 안에서만 쓸 수 있다");
  return value;
}
```

기본값으로 그럴듯한 가짜 객체(`{ user: null, login: () => {} }`)를 넣어 두면 Provider를 빼먹어도 에러 없이 돌아간다. 로그인 버튼을 눌렀는데 아무 일도 안 일어나는 버그가 된다. 이런 context는 일찍, 크게 실패하는 쪽이 낫다.

## 값이 바뀌면 일어나는 일

Provider의 `value`가 바뀌면 React는 지난 값과 `Object.is`로 비교하고, 다르면 Provider 아래 트리에서 그 context를 읽는 컴포넌트를 찾아 렌더링을 예약한다. 여기서 중요한 건 "중간에 무엇이 있든"이다. 중간 컴포넌트가 `memo`로 감싸져 있어 렌더링을 건너뛰어도, 그 아래의 소비자는 따로 깨어난다. `memo`는 props를 비교하는 장치라서 context 변경과는 상관이 없다.

`App`이 state를 바꿔 새 값을 넘기고, 그 아래 `memo`로 감싼 `Middle`, 그 아래 context를 읽는 `Leaf`가 있는 트리에서 값을 세 번 바꿔 봤다.

```text
App: 4번   Middle: 1번   Leaf: 4번   (첫 마운트 포함)
```

`Middle`은 첫 마운트 뒤로 한 번도 렌더링되지 않았는데 `Leaf`는 매번 렌더링됐다. 아래 그림에서 다음을 누르면 이 순서를 따라간다.

## value를 매 렌더링 새로 만들 때

Provider를 가진 컴포넌트가 context와 상관없는 이유로 렌더링될 때 문제가 생긴다. 사용자 정보를 내려 주는 Provider가 1초마다 바뀌는 시계 state도 들고 있다고 하자. `memo`로 감싼 `Avatar`가 사용자 정보만 읽는다. 시계를 다섯 번 바꾸면서 `Avatar`의 렌더링을 셌다.

```text
value={{ user, now }}                  Avatar 5번 중 5번
value={{ user, setUser }}              Avatar 5번 중 5번
value={useMemo(() => ({ user, setUser }), [user])}   Avatar 5번 중 0번
```

둘째 줄이 흔한 실수다. `user`도 `setUser`도 그대로인데, 객체 리터럴은 렌더링마다 새로 만들어지니 `Object.is`에서 매번 다르다. `useMemo`로 감싸면 `user`가 바뀔 때만 새 객체가 된다. 첫째 줄은 다르다. `now`가 정말 바뀌었으니 `useMemo`로 감싸도 매초 새 값이고 `Avatar`는 매초 렌더링된다. 이건 고정의 문제가 아니라 "자주 바뀌는 값과 거의 안 바뀌는 값을 한 통로에 실은" 설계의 문제다. 시계는 시계를 쓰는 컴포넌트가 직접 들고 있어야 한다.

## 상태와 동작을 나누면

장바구니로 한 번 더 보자. 배지는 개수를 보여 주고, 상품 카드 세 개의 담기 버튼은 `add` 함수만 쓴다. 모두 `memo`로 감쌌다. 담기를 세 번 누르고 렌더링 횟수를 셌다.

```text
context 하나, value 인라인          Badge 3   AddButton 9
context 하나, value를 useMemo로     Badge 3   AddButton 9
상태 / 동작 context 분리             Badge 3   AddButton 0
```

여기서는 `useMemo`가 전혀 도움이 안 됐다. 담을 때마다 `items`가 실제로 바뀌니 `value`도 매번 새 객체가 맞다. 버튼은 `add`만 쓰는데 `items`가 바뀔 때마다 같이 깨어난다. `add`를 `useCallback`으로 고정하고 다른 context에 넣으면, 그 context의 값은 한 번도 바뀌지 않으니 버튼은 담기를 몇 번 해도 렌더링되지 않는다.

```tsx
const CartItemsContext = createContext<Item[] | null>(null);
const CartActionsContext = createContext<CartActions | null>(null);

function CartProvider({ children }: { children: ReactNode }) {
  const [items, dispatch] = useReducer(cartReducer, []);
  const actions = useMemo(() => ({
    add: (id: string) => dispatch({ type: "add", id }),
    remove: (id: string) => dispatch({ type: "remove", id }),
  }), []); // dispatch는 참조가 바뀌지 않으니 한 번만 만든다

  return (
    <CartActionsContext value={actions}>
      <CartItemsContext value={items}>{children}</CartItemsContext>
    </CartActionsContext>
  );
}

function useRequired<T>(context: Context<T | null>, name: string): T {
  const value = useContext(context);
  if (value === null) throw new Error(name + "는 CartProvider 안에서만 쓸 수 있다");
  return value;
}

export const useCartItems = () => useRequired(CartItemsContext, "useCartItems");
export const useCartActions = () => useRequired(CartActionsContext, "useCartActions");
```

`dispatch`를 그대로 넘겨도 되지만, `add`, `remove` 같은 이름 붙은 함수로 감싸 두면 소비자가 액션 객체의 모양을 몰라도 된다. 바깥에는 두 커스텀 훅만 보여 주고 context 객체 자체는 내보내지 않는다. 그러면 나중에 내부를 바꿔도 소비자 코드는 그대로다.

### 몇 개로 쪼갤까

쪼개는 기준은 두 가지다. 바뀌는 빈도(매초, 사용자 동작마다, 거의 안 바뀜)와 읽는 쪽(누가 이 값만 필요로 하나). 두 기준이 같은 값끼리 묶는다. 장바구니라면 "항목 목록"과 "동작"으로 나누면 대개 충분하다. 항목 목록 안에서 개수만 보는 배지, 합계만 보는 결제 버튼까지 각각 context로 만들기 시작하면 Provider가 열 겹으로 쌓이고, 값 사이의 일관성(개수와 목록이 같은 렌더링의 것인지)을 맞추기도 어려워진다. 그 지점이 context에서 내려와 다른 도구로 갈 신호다.

## context에 셀렉터가 없는 이유

`useContext(CartContext, (v) => v.items.length)`처럼 "이 값 중 이 부분이 바뀔 때만 깨워 달라"고 할 수 있으면 쪼갤 필요가 없다. React 팀도 이런 API를 RFC로 논의했고 실험도 했지만, 19.2 기준으로 정식 API는 없다. context는 처음부터 "값이 바뀌면 소비자를 찾아서 다시 렌더링한다"는 단순한 전달 장치로 만들어졌고, 부분 구독은 값을 저장하고 비교하는 쪽의 일이기 때문이다.

그래서 대안은 이 일을 누가 맡느냐에 따라 나뉜다.

첫째, 소비자를 얇게 만든다. context를 읽는 컴포넌트는 값을 꺼내서 필요한 한 칸만 `memo`로 감싼 무거운 자식에게 넘긴다. 소비자는 매번 렌더링되지만 그 렌더링은 싸고, 무거운 자식은 넘겨받은 값이 그대로면 건너뛴다. 테마 context에서 글자 크기만 세 번 바꿨을 때 `theme`만 받는 `HeavyChart`는 한 번도 렌더링되지 않았다(`ChartWithTheme` 3번, `HeavyChart` 0번).

```tsx
function ChartWithTheme() {
  const { theme } = useContext(SettingsContext); // 매번 렌더링되지만 싸다
  return <HeavyChart theme={theme} />;            // theme이 그대로면 건너뛴다
}
```

둘째, context에는 바뀌지 않는 저장소 객체를 넣고, 값의 변화는 저장소가 알린다. 이게 Redux의 `Provider`, Zustand를 context와 함께 쓰는 방식이 하는 일이다. context가 전달 통로라는 성질을 그대로 살린 구조다.

```tsx
function createCartStore() {
  let state: CartState = { items: [] };
  const listeners = new Set<() => void>();
  return {
    getState: () => state,
    subscribe: (fn: () => void) => { listeners.add(fn); return () => listeners.delete(fn); },
    add: (id: string) => {
      state = { ...state, items: [...state.items, id] };
      listeners.forEach((fn) => fn());
    },
  };
}

const CartStoreContext = createContext<ReturnType<typeof createCartStore> | null>(null);

function CartProvider({ children }: { children: ReactNode }) {
  const [store] = useState(createCartStore); // 한 번 만들고 다시는 바꾸지 않는다
  return <CartStoreContext value={store}>{children}</CartStoreContext>;
}

function useCart<T>(selector: (s: CartState) => T): T {
  const store = useContext(CartStoreContext);
  if (!store) throw new Error("useCart는 CartProvider 안에서만 쓸 수 있다");
  return useSyncExternalStore(store.subscribe, () => selector(store.getState()));
}
```

앞의 장바구니 실험을 이 구조로 다시 돌렸다. 배지는 `useCart((s) => s.items.length)`로 개수만, 버튼은 context에서 저장소를 꺼내 `add`만 쓴다.

```text
store를 context로 전달 + useSyncExternalStore   Badge 3   AddButton 0
```

context 값(저장소 객체)이 한 번도 바뀌지 않으니 context 때문에 깨어나는 컴포넌트는 없다. 저장소가 알리면 `useSyncExternalStore`가 셀렉터 결과를 지난번과 비교해서 달라진 컴포넌트만 렌더링한다. 셀렉터가 매번 새 배열을 돌려주면 이 비교가 무너지니 주의한다. 그 함정은 [React 안의 함수형](/posts/fp-in-react)에서 다뤘다. 이 구조를 장점으로 보면, 전역 싱글턴 저장소와 달리 Provider마다 저장소가 따로 생긴다. 테스트마다, 서버 요청마다 깨끗한 저장소를 쓸 수 있다.

셋째, 이 일을 대신하는 라이브러리를 쓴다. `use-context-selector`는 `createContext`와 `useContextSelector(Context, selector)`를 제공한다. 같은 장바구니 실험에 붙여 보니 결과가 흥미로웠다. 버튼 컴포넌트 함수는 담기마다 불렸지만(9번), 커밋된 렌더링은 0번이었다. 셀렉터 결과가 같으면 함수를 실행한 뒤 결과를 버리고 커밋하지 않는 방식이다. 커밋 비용은 아끼지만 함수 실행 비용은 남는다. 소비자의 렌더링 함수가 무거우면 효과가 생각보다 작을 수 있으니 Profiler로 확인한다.

이 지점까지 왔다면 이미 상태 관리 라이브러리가 하는 일을 직접 하고 있는 것이다. 부분 구독이 필요한 전역 상태가 여러 개라면 Zustand나 Jotai 같은 도구를 쓰는 편이 코드가 짧고 검증도 되어 있다.

## 테마, 인증, 다국어에서

세 가지 전형적인 쓰임에서 무엇을 context에 넣는지가 조금씩 다르다.

테마는 context에 가장 잘 맞는다. 거의 안 바뀌고, 바뀌면 화면 전체가 바뀌는 게 맞다. 다만 색 자체는 context보다 CSS 변수로 바꾸는 게 낫다. `html`의 `data-theme` 속성을 바꾸면 CSS가 모든 색을 바꾸고 React는 아무것도 다시 렌더링하지 않는다. context에는 "지금 테마가 무엇인지"와 "바꾸는 함수"만 두고, 그걸 읽는 건 토글 버튼처럼 테마 이름을 알아야 하는 몇 곳뿐이게 한다. 이 블로그도 그렇게 한다.

인증은 상태와 동작을 나눈다. `user`는 로그인, 로그아웃, 프로필 수정 때만 바뀌고, `login`, `logout` 함수는 바뀌지 않는다. 로그아웃할 때 앱 상태를 깨끗이 비우고 싶으면 `<AppShell key={user?.id ?? "guest"} />`처럼 사용자 id를 key로 줘서 그 아래를 통째로 새로 만드는 방법이 단순하다. 토큰처럼 자주 갱신되는 값은 context에 넣지 않는다. 토큰이 갱신될 때마다 사용자 정보를 읽는 모든 컴포넌트가 깨어난다. 토큰은 요청을 보내는 모듈(HTTP 클라이언트) 쪽이 들고 있으면 된다.

다국어는 함정이 하나 있다. 번역 함수 `t`를 Provider에서 인라인으로 만들면 렌더링마다 새 함수다. `locale`과 메시지 묶음이 바뀔 때만 새로 만들도록 `useMemo`로 고정하고, 큰 메시지 사전은 언어를 바꿀 때 동적으로 불러온다. 날짜와 숫자 형식도 같은 자리에서 만든다. 가격 2,000개를 포맷할 때 줄마다 `Intl.NumberFormat`을 새로 만들면 포매터 하나를 다시 쓸 때보다 90배 가까이 느렸다(측정은 [메모이제이션 훅 글](/posts/react-memoization-hooks)에 있다). locale마다 한 번 만들어 context 값에 함께 넣어 두면 소비자는 꺼내 쓰기만 한다.

```tsx
function LocaleProvider({ locale, messages, children }: Props) {
  const value = useMemo(() => ({
    locale,
    t: (key: string) => messages[key] ?? key,
    price: new Intl.NumberFormat(locale, { style: "currency", currency: "KRW" }),
    date: new Intl.DateTimeFormat(locale, { dateStyle: "medium" }),
  }), [locale, messages]); // 언어가 바뀔 때만 새 값

  return <LocaleContext value={value}>{children}</LocaleContext>;
}

function PriceTag({ amount }: { amount: number }) {
  const { price } = useLocale();
  return <span>{price.format(amount)}</span>;
}
```

언어를 바꾸면 이 context를 읽는 모든 컴포넌트가 다시 렌더링된다. 이건 낭비가 아니라 의도한 동작이다. 화면의 모든 글자가 바뀌어야 하니까. context가 맞는 값이란 이렇게 "바뀌면 넓게 바뀌는 게 맞는" 값이다.

## Provider를 어디에 둘까

Provider는 그 값을 읽는 컴포넌트들을 모두 덮는 가장 낮은 곳에 둔다. 장바구니 context를 앱 맨 위에 두면 결제와 상관없는 관리자 화면까지 그 아래에 들어간다. 소비자가 없으면 렌더링 비용은 없지만, 어디서든 꺼낼 수 있다는 건 어디서든 의존할 수 있다는 뜻이라 경계가 흐려진다. 상품 목록과 결제 흐름에서만 쓰는 값이면 그 라우트의 레이아웃에 둔다.

Provider 컴포넌트는 상태를 들고 `children`을 받는 모양으로 만든다. 앞의 `CartProvider`가 그렇다. 이 모양이면 Provider의 state가 바뀌어도 `children`은 위쪽에서 이미 만들어 둔 엘리먼트 그대로라 다시 렌더링되지 않고, context를 읽는 컴포넌트만 깨어난다. 반대로 상태를 가진 `App` 안에 Provider를 직접 쓰고 그 안에 화면을 그대로 적으면, 상태가 바뀔 때 `App` 아래 전체가 부모를 따라 렌더링된다. 이 차이는 [React는 언제 다시 그리나](/posts/react-rerender)의 "상태는 내리고 내용은 올린다"와 같은 원리다.

Provider가 여러 개면 하나의 컴포넌트로 묶어 둔다.

```tsx
export function AppProviders({ children }: { children: ReactNode }) {
  return (
    <ThemeProvider>
      <AuthProvider>
        <LocaleProvider>{children}</LocaleProvider>
      </AuthProvider>
    </ThemeProvider>
  );
}
```

순서는 의존 관계를 따른다. `LocaleProvider`가 사용자 설정에서 언어를 읽는다면 `AuthProvider` 안쪽에 있어야 한다. 중첩이 다섯 겹을 넘어가면 들여쓰기보다 "이게 다 정말 전역이어야 하나"를 먼저 의심한다.

## context를 쓰는 컴포넌트 테스트

context를 읽는 컴포넌트는 테스트에서도 Provider가 필요하다. 매번 감싸기 번거로우니 테스트용 래퍼를 만든다. 값을 바꿔 가며 넣을 수 있어서, 로그인한 사용자와 손님 화면을 같은 테스트 파일에서 확인할 수 있다.

```tsx
function renderWithAuth(ui: ReactElement, user: User | null = null) {
  const value = { user, login: vi.fn(), logout: vi.fn() }; // vi.fn은 Vitest의 가짜 함수
  return render(<AuthContext value={value}>{ui}</AuthContext>);
}

// 커스텀 훅만 볼 때는 renderHook의 wrapper 옵션
renderHook(() => useAuth(), { wrapper: ({ children }) => <AuthProvider>{children}</AuthProvider> });
```

기본값을 `null`로 두고 커스텀 훅에서 에러를 던지게 해 두면, 래퍼를 빼먹은 테스트는 조용히 통과하지 않고 바로 실패한다. 앞에서 본 기본값 설계가 테스트에서도 같은 역할을 한다.

## React 19에서 달라진 두 가지

첫째, context 객체 자체를 Provider로 쓴다. 이 글의 예제가 모두 `<LocaleContext value={...}>`였다. `<LocaleContext.Provider value={...}>`도 그대로 동작하지만, React 팀은 앞으로 `Context.Provider`를 지원 중단할 예정이라고 밝혔다. 19를 쓰는 새 코드는 짧은 쪽을 쓴다.

둘째, `use(Context)`로 값을 읽을 수 있다. `useContext`와 같은 값을 돌려주지만 훅이 아니라서 조건문과 반복문 안에서 부를 수 있다.

```tsx
function Price({ amount, showCurrency }: Props) {
  if (!showCurrency) return <span>{amount}</span>; // early return 뒤에서도
  const { currency } = use(LocaleContext);       // use는 부를 수 있다
  return <span>{format(amount, currency)}</span>;
}
```

`useContext`였다면 early return 뒤에서 부를 수 없다. 훅 호출 순서가 렌더링마다 바뀌기 때문이다. 이 규칙이 왜 있는지는 [훅 규칙 글](/posts/react-custom-hooks-rules)에서 본다. `use`는 Promise도 받는데, 그건 Suspense와 함께 다룰 주제다.

서버 컴포넌트에서는 context를 쓸 수 없다. Provider는 클라이언트 컴포넌트여야 하고, 서버 컴포넌트인 레이아웃은 Provider로 `children`을 감싸기만 한다. `children`은 서버에서 렌더링된 채로 Provider 안에 들어간다. 경계를 어떻게 나누는지는 [서버 컴포넌트 글](/posts/react-server-components)에 있다.

## 현장에서 context가 말썽일 때

"useAuth는 AuthProvider 안에서만 쓸 수 있다" 같은 에러가 난다. Provider가 트리의 다른 가지에 있거나, 테스트에서 컴포넌트만 띄우고 Provider로 감싸지 않았다. 앞에서 기본값을 `null`로 두고 커스텀 훅에서 던지게 한 덕분에 바로 보인다.

Provider가 분명히 있는데 소비자가 기본값을 받는다. `createContext`가 두 번 실행되어 context 객체가 두 개 생긴 경우다. 모노레포에서 같은 패키지의 다른 버전이 두 벌 설치됐거나, 라이브러리가 React나 자기 자신을 중복으로 번들했을 때 생긴다. Provider는 A 객체에 값을 넣고 소비자는 B 객체에서 꺼내니 Provider가 없는 것과 같다. `npm ls 패키지이름`이나 `pnpm why 패키지이름`으로 중복 설치를 확인한다.

값 하나를 바꿨는데 화면 전체가 버벅인다. React DevTools Profiler에서 렌더링된 컴포넌트를 눌러 이유가 "Context changed"인지 본다. 같은 context를 읽는 컴포넌트가 수백 개라면 value가 매번 새 객체인지, 자주 바뀌는 값이 섞여 있는지 확인하고, 앞의 순서대로 고정, 분리, 저장소 전달로 넘어간다.

## 처음 설정 화면으로

`locale`을 여섯 층 아래까지 넘기던 코드는 context 하나로 정리된다. 하지만 context는 값을 배달할 뿐이고, 값이 바뀌면 그 통로를 읽는 모든 컴포넌트를 깨운다. `memo`도 이걸 막지 못한다. 그래서 거의 안 바뀌고 넓게 읽히는 값(테마, 사용자, 언어)에 쓰고, 넣는 값은 고정하고, 바뀌는 빈도가 다른 값은 통로를 나눈다. 일부만 구독해야 하는 값이 많아지면 context에는 저장소만 넣고 변화는 저장소가 알리게 한다.

## 면접에서 나올 만한 질문

### Context는 왜 쓰고, prop drilling의 다른 해결책은 무엇인가요?

트리의 여러 곳에서 멀리 떨어진 컴포넌트가 같은 값을 읽을 때, 중간 컴포넌트가 쓰지도 않는 props를 넘기는 결합을 없애려고 쓴다. 그 전에 합성을 먼저 본다. 중간 컴포넌트가 `children`이나 슬롯 props로 완성된 엘리먼트를 받게 하면 값을 가진 쪽과 쓰는 쪽이 한 곳에서 만난다. 층이 얕으면 props가 오히려 데이터 흐름이 잘 보인다.

### Provider 값이 바뀌면 무엇이 다시 렌더링되나요? memo로 막을 수 있나요?

React가 새 value를 지난 값과 `Object.is`로 비교해서 다르면, 그 Provider 아래에서 해당 context를 읽는 모든 컴포넌트를 다시 렌더링한다. 중간 컴포넌트가 `memo`로 렌더링을 건너뛰어도 소비자는 따로 깨어난다. `memo`는 props만 비교하기 때문이다. 소비자가 값의 한 칸만 써도 전체가 바뀐 것으로 본다.

### Context가 상태 관리 도구가 아니라는 말은 무슨 뜻인가요?

context는 위에서 넣은 값을 아래로 전달할 뿐, 값을 저장하거나 바꾸거나 일부만 구독하게 해 주지 않는다. 상태는 Provider 컴포넌트의 `useState`나 `useReducer`가 들고 있다. 그래서 context로 전역 상태를 다루면 부분 구독이 없어 리렌더링 범위가 넓어지고, 이걸 해결하려면 저장소가 따로 필요하다.

### Provider의 value를 useMemo로 감싸면 문제가 다 해결되나요?

Provider 컴포넌트가 context와 상관없는 이유로 렌더링될 때 새 객체가 생기는 문제만 해결된다. value 안의 값이 실제로 바뀌면 여전히 모든 소비자가 깨어난다. 장바구니 항목이 바뀔 때 `add` 함수만 쓰는 버튼까지 깨어나는 건 상태와 동작을 다른 context로 나눠야 풀린다.

### context에 셀렉터가 없는데 일부만 구독하려면 어떻게 하나요?

소비자를 얇게 만들어 필요한 값만 `memo`로 감싼 자식에게 넘기는 방법, context에는 바뀌지 않는 저장소 객체만 넣고 `useSyncExternalStore`와 셀렉터로 구독하는 방법이 있다. 후자가 Redux나 Zustand가 context와 함께 동작하는 방식이다. `use-context-selector` 같은 라이브러리도 있지만 소비자 함수는 실행되고 커밋만 건너뛰는 방식이라 효과를 재 봐야 한다.

### createContext의 기본값은 언제 쓰이나요?

위에 같은 context의 Provider가 하나도 없을 때만 쓰인다. Provider에 `undefined`를 넣으면 기본값이 아니라 `undefined`가 나온다. 테마처럼 Provider 없이도 말이 되는 값은 기본값을 두고, 인증처럼 Provider가 꼭 있어야 하는 context는 `null`로 두고 커스텀 훅에서 에러를 던져 실수를 일찍 잡는다.

### React 19에서 Context 사용법이 어떻게 바뀌었나요?

`<Context value>`처럼 context 객체를 바로 Provider로 쓸 수 있고, `Context.Provider`는 앞으로 지원 중단될 예정이다. `use(Context)`로 값을 읽을 수 있는데, 훅이 아니라 조건문이나 early return 뒤에서도 부를 수 있다. 서버 컴포넌트에서는 여전히 context를 쓸 수 없어 Provider는 클라이언트 컴포넌트로 둔다.
