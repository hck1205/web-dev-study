프로필에서 닉네임을 `minji`에서 `minji_dev`로 바꿨다. 저장 버튼을 누르자 "변경되었습니다"가 뜨고 프로필 화면으로 넘어간다. 그런데 화면에는 여전히 `minji`가 있다. 새로고침하면 `minji_dev`, 한 번 더 누르면 다시 `minji`. 3초쯤 지나면 그 뒤로는 계속 `minji_dev`다.

버그 같지만 DB는 아무것도 잃지 않았다. 쓰기는 프라이머리에 들어갔고, 읽기가 아직 그 쓰기를 받지 못한 복제본으로 갔을 뿐이다. 이런 시스템을 최종 일관성(eventual consistency)을 가진 시스템이라고 부른다. 이 글은 "결국 맞춰진다"는 말이 사용자 한 명에게 무엇을 깨뜨리는지, 그걸 애플리케이션 코드에서 어떻게 다시 지켜 주는지를 PostgreSQL 16 복제본 하나를 일부러 3초 늦춰 놓고 따라간다.

이 주제의 다른 글: 일관성 모델의 사다리와 CAP·PACELC는 [CAP과 PACELC 글](/posts/db-consistency-cap)에, 스탠바이를 붙이고 복제 지연을 감시하는 법은 [복제와 복제 지연 글](/posts/db-replication-sharding)에 있다. 여기서는 그 위에서 "사용자 세션 단위의 약속"과 "여러 대가 쓰기를 받는 저장소가 결국 같아지는 장치"를 다룬다. 끊긴 회선 자체는 [네트워크 분할 글](/posts/network-partitions), 시각에 기대는 충돌 해결의 함정은 [시계 어긋남 글](/posts/clock-skew)에서 이어진다.

## 언젠가는 얼마나 걸리나

최종 일관성의 정의는 놀랄 만큼 약하다. "새 쓰기가 더 들어오지 않으면, 언젠가 모든 복제본이 마지막 값으로 같아진다." 언제 같아지는지, 같아지기 전에 읽으면 무엇이 나오는지는 약속하지 않는다. 0.1초 만에 같아져도, 사흘 뒤에 같아져도 정의는 지켜진다.

이렇게 약한 약속을 일부러 고르는 이유는 기다리지 않기 위해서다. 쓰기가 들어오면 받은 노드가 바로 성공이라고 답하고, 다른 복제본에는 뒤에서 퍼뜨린다. 그러면 세 가지를 얻는다.

- 쓰기 지연이 복제본 수나 거리와 상관없어진다. 서울에서 쓴 값을 버지니아 복제본이 확인할 때까지 기다리지 않는다.
- 복제본 일부가 죽거나 끊겨도 남은 쪽이 계속 읽기와 쓰기를 받는다.
- 읽기를 복제본 여러 대에 나눠 보내 처리량을 늘릴 수 있다.

비동기 복제를 하는 PostgreSQL의 읽기 복제본, DynamoDB의 기본 읽기, Cassandra의 `ONE`, DNS, CDN 캐시가 모두 이 자리에 있다. AWS 문서는 DynamoDB의 최종 일관성 읽기가 "보통 1초 안에" 최신 값을 반영한다고 적는다. 보통은 그렇다. 문제는 그 "보통"을 벗어난 순간과, 1초 안에 같은 사용자가 다시 읽는 순간이다.

## 복제본 하나를 일부러 3초 늦춰 보기

같은 장비 안에서는 복제가 1ms 안에 끝나서 위 증상을 눈으로 보기 어렵다. 그래서 스탠바이에 `recovery_min_apply_delay`를 걸어 커밋 반영을 3초 늦췄다. 운영에서 실수로 지운 데이터를 건지려고 "지연 복제본"을 둘 때 쓰는 설정이다. 클러스터 두 개를 비공개 포트로 만들었다.

```bash
# 실험용 프라이머리와 스탠바이 (PostgreSQL 16.15, Ubuntu 24.04)
B=/usr/lib/postgresql/16/bin; D=/var/tmp/v4pg
sudo -u postgres $B/initdb -D $D/primary -U postgres --auth=trust     # 프라이머리 클러스터 생성
# postgresql.conf: port = 55441, wal_level = replica, max_wal_senders = 5
sudo -u postgres $B/pg_ctl -D $D/primary -l $D/primary.log start      # 프라이머리 시작
sudo -u postgres $B/pg_basebackup -h 127.0.0.1 -p 55441 -U postgres \
  -D $D/standby -R -X stream                                          # 스탠바이 복사본 생성, -R은 복제 설정까지 써 준다
echo "port = 55442"                         | sudo -u postgres tee -a $D/standby/postgresql.conf
echo "recovery_min_apply_delay = '3s'"      | sudo -u postgres tee -a $D/standby/postgresql.conf  # 커밋을 3초 늦게 반영
sudo -u postgres $B/pg_ctl -D $D/standby -l $D/standby.log start      # 스탠바이 시작
```

예제 테이블은 끝까지 이 둘이다.

```sql
CREATE TABLE users (id int PRIMARY KEY, nickname text NOT NULL);
CREATE TABLE comments (id int PRIMARY KEY, user_id int REFERENCES users, body text, parent_id int);
INSERT INTO users VALUES (1, 'minji'), (2, 'junho');
INSERT INTO comments VALUES (10, 2, '첫 댓글', NULL);
```

이제 닉네임을 바꾸고, 복제본, 프라이머리, 다시 복제본 순서로 읽었다. 실제 출력이다.

```sql
-- [프라이머리] 닉네임을 바꾼다
UPDATE users SET nickname = 'minji_dev' WHERE id = 1;
-- [복제본] 바로 읽는다
SELECT id, nickname FROM users WHERE id = 1;
-- [프라이머리] 읽는다
SELECT id, nickname FROM users WHERE id = 1;
-- [복제본] 다시 읽는다. 받은 위치와 재생한 위치도 같이 본다
SELECT id, nickname, pg_last_wal_receive_lsn() AS received, pg_last_wal_replay_lsn() AS replayed
FROM users WHERE id = 1;
```

```text
 id | nickname
----+----------
  1 | minji
(1 row)

 id | nickname
----+-----------
  1 | minji_dev
(1 row)

 id | nickname | received  | replayed
----+----------+-----------+-----------
  1 | minji    | 0/3031868 | 0/3031840
(1 row)
```

두 가지가 동시에 깨졌다. 첫 번째 읽기는 내가 방금 쓴 값을 못 봤다. 세 번째 읽기는 두 번째 읽기에서 이미 본 `minji_dev`보다 옛 값을 돌려줬다. 사용자 입장에서는 시간이 거꾸로 간 것이다. 3.5초 뒤 다시 읽으니 복제본도 `minji_dev`가 됐고, 이때 `pg_stat_replication`의 `replay_lag`는 `00:00:02.988412`로 걸어 둔 지연과 맞았다.

같은 시각, 복제본은 WAL을 이미 `0/3031868`까지 받아 두고 있었다. 데이터는 도착했는데 보이지 않는다. 이 틈이 최종 일관성의 "아직"이다.

## 사용자 한 명이 기대하는 네 가지

모든 데이터가 모든 사람에게 즉시 맞을 필요는 없다. 다른 사람의 댓글이 1초 늦게 보이는 건 아무도 모른다. 하지만 한 사용자가 자기 세션 안에서 겪는 순서가 뒤집히면 바로 문의가 된다. 1994년 Bayou 프로젝트의 테리(Terry) 등은 이것을 세션 보장(session guarantees) 네 가지로 정리했다.

- 내 쓰기 읽기(read-your-writes): 내가 쓴 것은 그 뒤 내 읽기에 보인다. 위 실험의 첫 번째 읽기가 이걸 어겼다.
- 단조 읽기(monotonic reads): 한 번 본 것보다 옛 상태를 다시 보지 않는다. 세 번째 읽기가 이걸 어겼다.
- 단조 쓰기(monotonic writes): 내가 한 쓰기들은 어느 복제본에서든 내가 한 순서대로 적용된다. "비밀번호 변경 → 그 비밀번호로 API 키 발급"이 거꾸로 적용되면 안 된다.
- 쓰기가 읽기를 따른다(writes-follow-reads): 내가 무언가를 읽고 그걸 보고 쓴 것은, 내가 읽은 것보다 앞서 적용되지 않는다. 댓글을 읽고 단 답글이 원글보다 먼저 보이면 안 된다.

뒤의 두 개는 프라이머리 하나에만 쓰는 구조에서는 공짜로 지켜진다. 모든 쓰기가 한 줄로 WAL에 들어가고 그 순서대로 재생되기 때문이다. 쓰기를 여러 곳에서 받는 구조(리전마다 프라이머리가 있는 멀티 리더, 리더 없는 저장소)로 가는 순간 이 둘도 직접 챙겨야 한다. 아래 그림에서 다음을 누르면 리전이 둘인 게시판에서 답글이 원글보다 먼저 도착하는 과정이 보인다.

### 위치를 언제 읽느냐가 중요하다

토큰을 만들 때 흔히 하는 실수가 있다. 트랜잭션 안에서 `pg_current_wal_lsn()`을 읽는 것이다. ORM이 트랜잭션을 열어 두고 콜백 안에서 값을 돌려주게 짜면 자연스럽게 이렇게 된다. 결과를 보자.

```sql
-- [프라이머리] 트랜잭션 안과 밖에서 위치를 읽는다
BEGIN;
UPDATE users SET nickname = 'minji_v2' WHERE id = 1;
SELECT pg_current_wal_lsn();   -- 트랜잭션 안: 0/303F8A8
COMMIT;
SELECT pg_current_wal_lsn();   -- 커밋 뒤:     0/303F918
```

```sql
-- [복제본] 0.3초 뒤, 두 토큰으로 각각 검사한다
SELECT nickname, pg_last_wal_replay_lsn() AS replayed,
       pg_last_wal_replay_lsn() >= '0/303F8A8'::pg_lsn AS ok_inside_token,
       pg_last_wal_replay_lsn() >= '0/303F918'::pg_lsn AS ok_after_token
FROM users WHERE id = 1;
```

```text
 nickname | replayed  | ok_inside_token | ok_after_token
----------+-----------+-----------------+----------------
 minji_tx | 0/303F8F0 | t               | f
(1 row)
```

트랜잭션 안에서 읽은 토큰으로는 검사를 통과하는데, 실제로 보이는 닉네임은 바뀌기 전 값이다. 복제본은 UPDATE 기록까지는 재생했지만 커밋 기록은 아직 재생하지 않았다. 커밋 기록은 트랜잭션 안에서 읽은 위치보다 뒤에 쓰이기 때문이다. 토큰은 반드시 커밋이 끝난 뒤에 읽는다. 커밋 뒤에 다른 세션의 쓰기가 끼어들어 위치가 조금 더 커져도 상관없다. 조금 더 엄격해질 뿐 틀리지는 않는다.

### Node로 짠 라우터

토큰을 세션에 저장하고 읽을 때마다 복제본의 재생 위치와 비교하는 라우터를 `pg`(node-postgres 8)로 짰다.

```js
const session = { minLsn: "0/0" };   // 실제로는 쿠키나 서버 세션에 저장한다

async function write(sql, params) {
  await primary.query(sql, params);                                    // 자동 커밋
  const { rows } = await primary.query("SELECT pg_current_wal_lsn() AS lsn"); // 커밋 '뒤' 위치
  session.minLsn = rows[0].lsn;
}

async function read(sql, params, { waitMs = 0 } = {}) {
  const deadline = Date.now() + waitMs;
  for (;;) {
    const { rows } = await replica.query(
      "SELECT pg_last_wal_replay_lsn() >= $1::pg_lsn AS ok", [session.minLsn]);
    if (rows[0].ok) return (await replica.query(sql, params)).rows;    // 복제본이 따라왔다
    if (Date.now() >= deadline) break;
    await new Promise((r) => setTimeout(r, 100));                        // 100ms마다 다시 본다
  }
  return (await primary.query(sql, params)).rows;                       // 예산을 넘기면 프라이머리
}
```

닉네임을 바꾼 직후 기다림 예산을 0, 0.5초, 4초로 바꿔 가며 읽었다. 앞의 숫자는 시작부터 지난 시간이다.

```text
   25ms write ok, token=0/3031918
   33ms naive replica read -> [{"nickname":"minji_dev"}]
   36ms replica behind token -> primary -> [{"nickname":"minji_82"}]
  554ms replica behind token -> primary -> [{"nickname":"minji_82"}]
 3089ms replica (replayed 0/3031950) -> [{"nickname":"minji_82"}]
```

토큰 없이 복제본에서 읽은 두 번째 줄은 바로 전 닉네임 `minji_dev`를 돌려줬다. 토큰을 쓰면 세 경우 모두 방금 쓴 `minji_82`가 나온다. 차이는 어디서 읽었느냐와 얼마나 기다렸느냐다. 기다림 예산을 크게 잡으면 프라이머리 부하는 줄지만 그 사용자의 응답이 그만큼 느려진다. 예산은 평소 복제 지연의 p99보다 조금 큰 값으로 잡는다. 지연이 그 예산을 자주 넘는다면 라우팅을 손볼 게 아니라 복제본이 왜 밀리는지(긴 쿼리, 디스크, 네트워크)부터 고친다.

PostgreSQL 16에는 "이 LSN까지 재생될 때까지 기다려라"는 내장 함수가 없어서 위처럼 폴링한다. MySQL 8은 GTID를 토큰으로 쓰고 `WAIT_FOR_EXECUTED_GTID_SET(gtid_set, timeout)`으로 복제본에서 기다릴 수 있다. MongoDB는 3.6부터 인과 일관성 세션을 켜면 드라이버가 `afterClusterTime`을 알아서 붙여 같은 일을 한다.

### 단조 읽기는 토큰을 앞으로만 민다

## 여러 대가 쓰기를 받는 저장소에서는

Cassandra, DynamoDB 안쪽, Riak처럼 리더 없이 복제본 N개 중 W개가 확인하면 쓰기 성공, R개에서 읽어 가장 새 값을 고르는 저장소에서는 LSN 같은 한 줄짜리 위치가 없다. 대신 R과 W를 고른다. R + W > N이면 읽는 집합과 쓴 집합이 겹친다는 계산은 [CAP 글의 쿼럼 계산기](/posts/db-consistency-cap)에서 직접 해 봤다. 여기서 궁금한 건 그 반대편이다. R + W ≤ N으로 빠르게 가면 옛 값을 얼마나 자주, 얼마나 오래 보나.

2012년 베일리스(Bailis) 등은 이걸 PBS(Probabilistically Bounded Staleness)라는 이름으로 계산했다. 같은 생각을 Node로 돌려 봤다. 쓰기는 복제본마다 평균 20ms인 지수분포 시간 뒤에 도착하고, 클라이언트는 W번째 확인이 온 순간 성공을 받는다. 그로부터 t ms 뒤 무작위 R개 복제본에서 읽었을 때 아무도 새 값을 갖고 있지 않을 확률을 10만 번씩 셌다.

```bash
node pbs.js   # 시드 고정 난수, 조합마다 10만 번
```

```text
N W R  | t=0ms   t=10ms  t=50ms  t=100ms
3 1 1  |  66.78%  40.29%   5.37%   0.49%
3 2 1  |  33.03%  20.03%   2.69%   0.22%
3 1 2  |  33.15%  12.10%   0.24%   0.00%
3 2 2  |   0.00%   0.00%   0.00%   0.00%
5 2 2  |  29.79%  10.98%   0.19%   0.00%
5 3 3  |   0.00%   0.00%   0.00%   0.00%
```

첫 줄의 66.78%는 계산과 맞는다. W = 1이면 성공 순간 새 값을 가진 복제본은 하나뿐이고, 셋 중 무작위로 하나를 읽으면 2/3 확률로 못 본다. 볼 곳은 두 군데다. 하나는 R + W > N인 줄(3 2 2, 5 3 3)이 정말 0이라는 것, 다른 하나는 R + W ≤ N이어도 50ms만 지나면 옛 값 확률이 몇 %로 떨어진다는 것이다. 최종 일관성의 "언젠가"는 보통 아주 짧고, 위험한 건 쓰자마자 같은 사람이 다시 읽는 순간이다. 위 세션 토큰이 정확히 그 순간을 겨냥하는 이유다.

실제 시스템은 이 모델보다 거칠다. 지연이 지수분포가 아니라 긴 꼬리를 갖고, GC나 디스크 때문에 복제본 하나가 수 초씩 멈추며, 노드가 죽으면 다른 노드가 대신 받아 두는 경로가 생긴다.

### 남의 자리에 맡겨 두는 쓰기

복제본 셋 중 하나가 죽었는데 W = 2로 쓰면 나머지 둘이 확인해서 성공한다. 셋 중 둘이 죽었다면 엄격한 쿼럼은 실패를 돌려준다. Dynamo 계열은 여기서 가용성을 고를 수 있다. 원래 담당이 아닌 다른 노드가 쓰기를 대신 받아 "이건 C의 것"이라는 메모(힌트)와 함께 보관했다가, C가 돌아오면 넘겨준다. 이걸 힌트 핸드오프(hinted handoff), 이렇게 대신 받아 숫자를 채우는 쿼럼을 느슨한 쿼럼(sloppy quorum)이라고 한다.

## 결국 같아지게 만드는 장치

"언젠가 같아진다"는 저절로 일어나지 않는다. 누군가 차이를 찾아 메워야 한다. 리더 없는 저장소는 보통 세 겹으로 메운다.

읽기 복구(read repair)는 R개에서 읽었는데 값이 서로 다르면, 가장 새 값을 고르고 낡은 복제본에 그 값을 써 주는 것이다. 자주 읽는 키는 빨리 고쳐지지만 아무도 안 읽는 키는 영영 안 고쳐진다. Cassandra 4.0은 확률적으로 백그라운드 읽기 복구를 하던 `read_repair_chance` 옵션을 없앴고, 지금은 QUORUM 같은 읽기에서 불일치를 발견했을 때 응답 전에 고치는 방식만 남았다.

안티 엔트로피(anti-entropy)는 그 빈틈을 메운다. 복제본끼리 데이터 전체를 주기적으로 비교한다. 전부 주고받으면 너무 크니, 키 범위마다 해시를 트리로 쌓은 머클 트리를 주고받아 다른 범위만 내려가며 찾는다. 이 구조는 [머클 트리 글](/posts/merkle-tree)에서 따로 다룬다. Cassandra에서는 `nodetool repair`가 이 일을 하고, 운영자가 정기적으로 돌려야 한다.

여기서 흔한 사고가 하나 있다. 삭제도 쓰기다. 지운 행은 바로 사라지지 않고 "지웠음" 표시(톰스톤)로 남아 복제본에 퍼진다. 톰스톤은 `gc_grace_seconds`(기본 864000초, 10일)가 지나면 정리된다. 그런데 어느 복제본이 그 기간 내내 삭제를 못 받았다면, 톰스톤이 정리된 뒤 그 복제본의 옛 행이 안티 엔트로피로 다시 퍼진다. 지운 데이터가 살아난다. 그래서 repair 주기는 반드시 `gc_grace_seconds`보다 짧게 잡는다.

### 둘 다 새 값이라면

메우는 장치는 "어느 쪽이 새 값인가"를 알 수 있어야 동작한다. 같은 키를 두 곳에서 동시에 고쳤다면 둘 다 새 값이다. 고르는 규칙은 크게 셋이다.

- 마지막 쓰기 승리(LWW): 쓰기마다 시각을 붙여 큰 쪽을 남긴다. 단순하지만 시계가 어긋나면 실제로 나중에 한 쓰기가 사라진다. 그 장면은 [CAP 글](/posts/db-consistency-cap)에 그려 두었고, 시계가 왜 어긋나는지는 [시계 어긋남 글](/posts/clock-skew)에서 본다.
- 버전 벡터: 노드마다 카운터를 붙여 "앞뒤 관계인가, 동시인가"를 가린다. 동시라면 둘 다 남기고(siblings) 애플리케이션이 합친다.
- CRDT: 어떤 순서로 합쳐도 같은 결과가 나오게 설계한 자료형이다. 카운터, 집합, 협업 문서에 쓴다. [CRDT 글](/posts/crdt)에서 자세히 본다.

닉네임처럼 "마지막 값 하나"면 되는 데이터는 LWW로 충분한 경우가 많다. 장바구니처럼 양쪽 변경을 모두 살려야 하는 데이터는 LWW를 쓰면 안 된다.

## 화면이 먼저 덜 헷갈리게

라우팅으로 다 막지 못하는 경우도 있다. 검색 색인, 캐시, 다른 서비스가 이벤트로 받아 만든 복사본처럼, 쓰기 경로와 다른 저장소에서 읽는 화면이다. 이런 곳은 토큰을 비교할 위치가 없다.

이럴 때는 화면이 쓴 값을 직접 들고 있는다. 저장 요청의 응답에 바뀐 객체 전체를 돌려주고, 클라이언트는 그 값을 바로 그린다. 그 뒤 목록을 다시 불러올 때 서버 값의 버전(`updated_at`이나 버전 번호)이 클라이언트가 가진 것보다 낮으면 무시한다. 검색 결과처럼 몇 초 늦어도 되는 화면에는 "반영까지 몇 초 걸릴 수 있다"를 숨기지 않는다. 사용자에게 숨기는 것보다, 사용자가 이상하다고 느끼는 순간을 줄이는 쪽이 목표다.

## 가끔 옛 값이 보인다는 문의가 오면

증상은 대개 이렇게 온다. "저장했는데 반영이 안 돼요, 새로고침하면 돼요." 재현이 안 되고, 로그에는 에러가 없다. 순서대로 본다.

먼저 그 요청이 어느 노드에서 읽었는지 안다. 읽기 라우터나 커넥션 풀이 고른 노드 이름을 요청 로그에 남겨 두지 않았다면 이 단계에서 막힌다. 로그에 `db=replica-a`가 찍혀 있으면 복제 지연을 의심하고, `db=primary`인데도 옛 값이면 앞단 캐시를 의심한다.

다음으로 그 시각의 복제 지연을 본다. 시간 값과 바이트 값을 함께 본다.

```sql
-- [프라이머리] 복제본마다 재생이 얼마나 밀렸나
SELECT application_name, replay_lsn,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS gap_bytes,
       replay_lag
FROM pg_stat_replication;
```

```text
 application_name | replay_lsn | gap_bytes |   replay_lag
------------------+------------+-----------+-----------------
 walreceiver      | 0/3031868  |         0 | 00:00:02.988412
(1 row)
```

`gap_bytes`가 0인데 `replay_lag`가 3초인 이 출력은 실험의 지연 복제본이라서 그렇다. 바이트로는 다 받았고 재생만 일부러 늦췄다. 운영에서 같은 모양이 보이면 누군가 `recovery_min_apply_delay`를 걸어 둔 복제본이 읽기 풀에 섞여 있는지 확인한다. 지연 복제본은 백업 용도라 읽기 대상에서 빼야 한다.

그 밖에 자주 보는 원인은 이렇다.

- 토큰을 트랜잭션 안에서 읽었다. 위 실험처럼 검사는 통과하는데 값은 옛것이다.
- 쓰기 서비스와 읽기 서비스가 다르다. 주문 서비스가 쓰고 마이페이지 서비스가 읽는다면 토큰을 서비스 사이에도 넘겨야 한다.
- 복제본 앞의 로드밸런서가 라운드로빈이다. 같은 사용자가 요청마다 다른 복제본으로 가서 단조 읽기가 깨진다. 토큰을 쓰지 않을 거라면 사용자 ID 해시로 한 복제본에 붙인다.
- 복제본 대신 캐시가 범인이다. 쓰기 후 캐시를 지우는 순서가 꼬여 옛 값이 다시 들어간 경우다. [캐시 전략 글](/posts/caching-strategies)에 그 경쟁을 정리했다.
- 프라이머리가 장애 조치로 바뀌었다. 새 프라이머리는 옛 프라이머리의 마지막 몇 쓰기를 못 받았을 수 있다. 이건 최종 일관성이 아니라 쓰기 유실이고, [네트워크 분할 글](/posts/network-partitions)에서 이어서 본다.

## 결국이 오기 전까지를 설계한다

최종 일관성은 "언젠가 같아진다"만 약속한다. 그 언젠가는 보통 수십 ms라 대부분의 읽기에는 문제가 없고, 문제는 쓴 사람이 곧바로 다시 읽는 순간에 몰린다. 그래서 전체를 강하게 만들 필요는 없고, 사용자 세션 안의 네 가지 약속만 지켜 주면 된다. 프라이머리가 하나라면 커밋 뒤 LSN을 세션에 들고 다니고, 여러 곳이 쓰기를 받는다면 버전 벡터나 CRDT로 "무엇을 봤나"를 표현한다. 그리고 결국 같아지게 만드는 장치(힌트, 읽기 복구, 안티 엔트로피)가 정말 돌고 있는지 확인한다.

## 면접에서 나올 만한 질문

### 최종 일관성이란 무엇이고, 왜 쓰나요?

새 쓰기가 멈추면 언젠가 모든 복제본이 같은 값이 된다는 약속이다. 언제 같아지는지, 그 전에 무엇을 읽게 되는지는 약속하지 않는다. 대신 쓰기가 다른 복제본을 기다리지 않아 지연이 짧고, 일부 복제본이 죽거나 끊겨도 계속 동작하며, 읽기를 여러 복제본에 나눌 수 있다.

### 세션 보장 네 가지를 설명해 주세요.

내 쓰기 읽기는 내가 쓴 것이 내 다음 읽기에 보이는 것, 단조 읽기는 한 번 본 것보다 옛 상태를 다시 보지 않는 것이다. 단조 쓰기는 내 쓰기들이 내 순서대로 적용되는 것, 쓰기가 읽기를 따른다는 내가 읽고 나서 쓴 것이 읽은 것보다 앞서 적용되지 않는 것이다. 프라이머리 하나에만 쓰는 구조에서는 뒤의 둘이 자동으로 지켜지고, 멀티 리더나 리더 없는 구조에서는 직접 챙겨야 한다.

### 읽기 복제본을 쓰면서 read-your-writes를 지키려면 어떻게 하나요?

커밋이 끝난 뒤 프라이머리의 WAL 위치(LSN)를 세션에 저장하고, 읽을 때 그 위치 이상을 재생한 복제본에서만 읽는다. 없으면 짧게 기다리거나 프라이머리로 보낸다. 더 단순하게는 쓰기 후 몇 초간 그 사용자의 읽기를 프라이머리로 보내는 방법이 있지만, 지연이 그 시간을 넘으면 깨진다. 토큰을 트랜잭션 안에서 읽으면 커밋 기록보다 앞선 위치라 검사를 통과해도 옛 값이 보이니, 반드시 커밋 뒤에 읽는다.

### 단조 읽기는 왜 따로 챙겨야 하나요?

라운드로빈으로 복제본을 번갈아 읽으면, 앞서 따라온 복제본에서 새 값을 본 뒤 뒤처진 복제본에서 옛 값을 보게 된다. 사용자에게는 방금 본 글이 사라지는 것처럼 보인다. 읽을 때마다 본 위치로 세션 토큰을 앞으로만 밀어 주거나, 사용자를 한 복제본에 고정해 막는다. 고정은 그 복제본이 죽거나 크게 밀리면 효과가 없다는 한계가 있다.

### R + W ≤ N이면 얼마나 자주 옛 값을 읽나요?

복제 지연 분포에 따라 다르고, PBS로 계산할 수 있다. 평균 20ms 지수분포로 시뮬레이션하면 N=3, W=1, R=1에서 쓰기 직후에는 약 67% 확률로 옛 값을 읽지만, 50ms 뒤에는 약 5%, 100ms 뒤에는 0.5% 아래로 떨어진다. 그래서 대부분의 읽기는 괜찮고, 쓴 직후 같은 사용자가 다시 읽는 경우가 위험하다.

### 힌트 핸드오프와 느슨한 쿼럼은 무엇이고, 어떤 위험이 있나요?

담당 복제본이 응답하지 않을 때 다른 노드가 그 몫의 쓰기를 힌트로 받아 두었다가 돌아오면 넘겨주는 것이 힌트 핸드오프이고, 이렇게 담당이 아닌 노드로 W를 채우는 것이 느슨한 쿼럼이다. 가용성은 높아지지만, 힌트를 넘기기 전에는 R + W > N이어도 담당 노드들에서 새 값을 못 읽을 수 있다. 힌트 보관 한도(Cassandra 기본 3시간)를 넘긴 노드는 repair로 따라잡아야 한다.

### 리더 없는 저장소는 어떻게 결국 같아지나요?

쓰는 순간의 힌트 핸드오프, 읽다가 불일치를 발견하면 고치는 읽기 복구, 주기적으로 머클 트리로 범위별 해시를 비교해 차이를 메우는 안티 엔트로피를 겹쳐 쓴다. 읽기 복구는 자주 읽는 키만 고치니 안티 엔트로피가 필요하다. Cassandra에서는 repair를 톰스톤 보관 기간(`gc_grace_seconds`, 기본 10일)보다 자주 돌리지 않으면 지운 데이터가 되살아난다.
