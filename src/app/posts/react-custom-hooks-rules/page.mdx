<EasyIntro>
  React는 컴포넌트마다 기억할 것들을 사물함 한 줄에 넣어 둔다. 사물함에는 이름표가 없고 번호만 있다. 컴포넌트가 화면을 그릴 때마다 React는 "첫 번째로 부른 훅은 1번 사물함, 두 번째는 2번" 하고 순서대로 문을 연다. 그런데 어떤 때는 훅을 부르고 어떤 때는 건너뛰면, 건너뛴 다음부터는 모두 한 칸씩 밀려서 남의 사물함을 열게 된다. 이름이 들어 있어야 할 칸에서 숫자가 나오는 식이다. 그래서 훅은 늘 같은 순서로, 조건 없이 불러야 한다는 규칙이 있다. 이 규칙을 지키면서 자주 쓰는 훅 묶음을 함수 하나로 모은 것이 커스텀 훅이다. 커스텀 훅은 쓰는 방법을 나눠 주는 것이지 사물함 자체를 나눠 주는 것이 아니라서, 두 컴포넌트가 같은 훅을 써도 각자 자기 사물함을 따로 받는다.
</EasyIntro>

프로필 화면에 "수정" 모드를 붙였다. 수정할 때만 임시 이름이 필요해서 그 `useState`를 `if (edit)` 안에 넣었다. 수정 모드로 들어갔다가 저장을 누르니 화면이 하얗게 되고 에러 수집기에 이런 줄이 쌓인다.

```text
Minified React error #300; visit https://react.dev/errors/300 for the full message ...
```

개발 빌드로 띄우면 같은 에러가 이 문장으로 나온다.

```text
Rendered fewer hooks than expected. This may be caused by an accidental early return statement.
```

"훅은 조건문 안에서 부르지 마라"는 규칙은 다들 안다. 이 글은 그 규칙이 왜 있는지를 React가 훅을 저장하는 방식에서 보고, 그 위에서 커스텀 훅을 어떻게 설계할지를 따라간다. 상태를 공유하는 것처럼 보이지만 공유하지 않는다는 점, 좋은 훅과 새는 훅의 경계, 반환 모양, 브라우저 API 구독, 테스트까지 본다. `useState`와 `useEffect` 자체의 동작은 이 글에서 다시 설명하지 않는다.

## 훅은 이름이 아니라 순서로 찾는다

`useState("Kim")`을 부를 때 React에 넘기는 건 초깃값뿐이다. 이 상태가 "name"이라는 건 React가 모른다. 변수 이름은 우리 코드 안에만 있다. 그럼 다음 렌더링에서 React는 어떻게 "이 `useState`는 지난번의 그 상태"라는 걸 알까.

순서로 안다. React는 컴포넌트 인스턴스마다 훅 목록을 하나 들고 있다(내부적으로는 fiber에 달린 연결 리스트다). 첫 렌더링에서는 훅을 부를 때마다 목록 끝에 칸을 하나씩 붙이고, 그다음 렌더링부터는 훅을 부를 때마다 목록의 다음 칸을 꺼낸다. 첫 번째 `useState`는 첫 칸, 두 번째는 두 번째 칸. 그래서 훅은 렌더링마다 같은 순서로, 같은 개수만큼 불려야 한다.

처음 코드를 단순하게 줄이면 이렇다.

```tsx
function Profile({ edit }: { edit: boolean }) {
  let name = "(없음)";
  if (edit) {
    [name] = useState("Kim"); // 수정 모드에서만 부른다
  }
  const [count] = useState(0);
  const [open] = useState(false);
  console.log({ edit, name, count, open });
  return null;
}
```

React 19.2에서 `edit`을 `true`로 렌더링한 뒤 `false`로 다시 렌더링하고 로그를 받았다.

```text
{ edit: true, name: 'Kim', count: 0, open: false }
{ edit: false, name: '(없음)', count: 'Kim', open: 0 }
{ edit: false, name: '(없음)', count: 'Kim', open: 0 }
Error: Rendered fewer hooks than expected. This may be caused by an accidental early return statement.
```

에러가 나면 React가 같은 렌더링을 한 번 더 시도해 보기 때문에 두 번째 렌더링이 두 줄 찍혔다. 그 줄의 `count`가 `'Kim'`이다. 아래 그림에서 다음을 누르면 이 일이 칸 단위로 보인다. 위 칸은 React가 들고 있는 훅 목록, 아래 기억 칸은 이번 렌더링의 변수가 실제로 받은 값이다.

이름표가 아니라 번호로 찾는 방식은 일부러 고른 설계다. 이름을 붙이게 했다면 훅을 부를 때마다 고유 키를 적어야 하고, 같은 커스텀 훅을 한 컴포넌트에서 두 번 쓰면 키가 겹친다. 순서 방식은 그런 키 없이 훅을 함수처럼 자유롭게 합성하게 해 준다. 대가가 "늘 같은 순서로 불러라"는 규칙이다.

## 에러가 나는 경우와 안 나는 경우

React가 어긋남을 알아채는 건 일부뿐이다. 개수가 달라지면 알아챈다. 지난번보다 적으면 앞의 에러, 많으면 `Rendered more hooks than during the previous render.`이다. 프로덕션에서는 각각 `Minified React error #300`과 `#310`으로 찍힌다.

개수는 같은데 훅 종류가 달라지면 개발 빌드에서 이런 경고가 나온다.

```text
React has detected a change in the order of Hooks called by Mixed. This will lead to bugs and errors if not fixed. For more information, read the Rules of Hooks: https://react.dev/link/rules-of-hooks

   Previous render            Next render
   ------------------------------------------------------
1. useState                   useRef
   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
```

가장 위험한 건 개수도 종류도 같은 경우다. 아무 말도 없다.

```tsx
function Filter({ advanced }: { advanced: boolean }) {
  let label;
  if (advanced) [label] = useState("고급 필터");
  else [label] = useState("기본 필터");
  return <h2>{label}</h2>;
}
```

`advanced`를 `false`에서 `true`로 바꿔 렌더링했더니 제목은 여전히 "기본 필터"였다. 두 `useState`가 같은 칸 0을 쓰니, 두 번째 렌더링의 `useState("고급 필터")`는 초깃값을 무시하고 칸 0에 있던 "기본 필터"를 돌려준다. 에러도 경고도 없다. 코드만 보면 두 상태가 따로 있는 것 같아서 찾기도 어렵다.

같은 규칙으로 움직이는 작은 모형을 만들어 보자. 렌더링마다 부른 훅의 이름과 초깃값 목록을 받아, 각 렌더링의 변수가 실제로 받는 값을 돌려준다. 첫 렌더링에만 칸을 만들고, 그다음부터는 순서대로 칸을 꺼낸다. 지난번보다 훅이 많으면 React처럼 에러 문장을 돌려준다.

그래서 규칙은 "조건문 안에서 부르지 마라"보다 넓다. 훅은 컴포넌트나 커스텀 훅의 맨 위 층에서만 부른다. 조건문, 반복문, early return 뒤, 이벤트 핸들러 안, `useMemo`에 넘기는 함수 안, `try/catch` 블록 안에서 부르지 않는다. 조건이 필요하면 훅은 늘 부르고 조건은 그 안이나 결과에 건다.

```tsx
function Profile({ edit }: { edit: boolean }) {
  const [draft, setDraft] = useState("Kim"); // 늘 부른다
  // ...
  return edit ? <input value={draft} onChange={(e) => setDraft(e.target.value)} /> : <p>{draft}</p>;
}
```

처음 에러의 진짜 원인도 이거였다. 로딩 중이면 `if (!user) return <Spinner />`로 먼저 돌아가는 줄이 몇몇 훅보다 위에 있었다. 에러 메시지가 "accidental early return statement"를 의심하라고 한 이유다. 예외는 React 19의 `use`다. 훅이 아니라 조건문 안에서 부를 수 있다. context를 조건부로 읽는 예는 [Context 글](/posts/react-context)에서 봤다.

## 린트가 미리 잡는 것

이 규칙은 사람이 지키기 어렵다. `eslint-plugin-react-hooks`의 `rules-of-hooks` 규칙이 코드 모양만 보고 미리 잡는다. 앞의 실수들을 모아 7.1로 돌렸다.

```tsx
export function Profile({ userId, edit }) {
  if (edit) {
    const [draft, setDraft] = useState("");
  }
  const [user, setUser] = useState(null);
  useEffect(() => {
    fetch("/api/users/" + userId).then((r) => r.json()).then(setUser);
  }, []);
  return <p>{user?.name}</p>;
}

function getTheme() {
  const [theme] = useState("light");
  return theme;
}
```

```text
   5:31  error    React Hook "useState" is called conditionally. React Hooks must be called in the exact same order in every component render  react-hooks/rules-of-hooks
  10:6   warning  React Hook useEffect has a missing dependency: 'userId'. Either include it or remove the dependency array  react-hooks/exhaustive-deps
  15:19  error    React Hook "useState" is called in function "getTheme" that is neither a React function component nor a custom React Hook function. React component names must start with an uppercase letter. React Hook names must start with the word "use"  react-hooks/rules-of-hooks
```

세 번째 줄이 이름 규칙이다. 린트는 함수가 컴포넌트인지 훅인지 이름으로 판단한다. 대문자로 시작하면 컴포넌트, `use` 다음에 대문자가 오면 훅이다. 둘 다 아닌 `getTheme` 안의 `useState`는 규칙 위반이다. 이 함수가 어디서 불릴지 린트가 확인할 수 없기 때문이다. 이름을 `useTheme`으로 바꾸면 에러가 사라지고, 대신 `useTheme`을 부르는 쪽이 규칙을 지키는지 검사한다. 훅 이름이 `use`로 시작해야 하는 이유는 관례가 아니라 이 검사 때문이다.

반대 방향도 있다. 안에서 훅을 하나도 부르지 않는 함수에 `use`를 붙이지 않는다. `useFormatPrice`가 그냥 계산 함수라면 `formatPrice`가 맞다. `use`를 붙이면 린트가 그 함수를 조건문 안에서 부르지 못하게 막아서, 아무 이유 없이 쓰임새가 좁아진다. React Compiler도 같은 이름 규칙으로 훅을 알아본다. 7 버전의 `recommended` 설정에 컴파일러가 쓰는 검사가 함께 들어 있다는 이야기는 [메모이제이션 훅 글](/posts/react-memoization-hooks)에 있다.

## 커스텀 훅은 상태를 나누지 않는다

커스텀 훅은 다른 훅을 부르는 평범한 함수다. 그래서 커스텀 훅 안의 `useState`는 그 훅을 부른 컴포넌트의 훅 목록에 칸을 만든다. 두 컴포넌트가 같은 `useToggle`을 쓰면 칸도 두 벌이다.

```tsx
function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn((v) => !v), []);
  return [on, toggle] as const;
}
```

`useToggle`을 쓰는 훅 두 개를 따로 띄우고 하나만 토글했다.

```text
a: true   b: false
```

`a`만 바뀌었다. 커스텀 훅이 나눠 주는 건 "토글을 다루는 방법"이고, 토글 상태 자체는 부른 쪽마다 따로 생긴다. 이걸 모르면 `useCart()`를 헤더와 상품 카드에서 각각 불러 놓고 왜 헤더의 개수가 안 바뀌는지 헤맨다. 둘이 각자 자기 장바구니를 갖고 있다. 여러 컴포넌트가 같은 상태를 봐야 하면 상태를 공통 부모로 올리거나, context로 전달하거나, 컴포넌트 바깥의 저장소에 두고 구독해야 한다. 커스텀 훅은 그 위에 얹는 얇은 입구가 된다.

## 경계가 맞는 훅, 새는 훅

커스텀 훅으로 뽑기 좋은 것은 하나의 개념을 감추면서 바깥에 보이는 모양은 단순한 것이다. `useOnlineStatus()`는 "온라인인가"라는 불리언 하나를 돌려준다. 안에서 무슨 이벤트를 듣는지는 쓰는 쪽이 몰라도 된다. `useMediaQuery("(min-width: 768px)")`, `useDebouncedValue(value, 300)`도 그렇다.

반대로 처음엔 간단해 보이다가 쓰는 곳이 늘수록 옵션이 붙는 훅이 있다. 대표가 `useFetch`다.

```tsx
function useFetch<T>(url: string) {
  const [data, setData] = useState<T | null>(null);
  const [error, setError] = useState<unknown>(null);
  useEffect(() => {
    fetch(url).then((r) => r.json()).then(setData, setError);
  }, [url]);
  return { data, error };
}
```

검색어를 빠르게 바꾸면 이 훅은 틀린 결과를 보여 준다. `url`이 `?q=re`에서 `?q=react`로 바뀌어 요청이 두 개 나갔는데 먼저 보낸 `re`의 응답이 늦게 오면, 그 응답이 `react`의 결과를 덮어쓴다. 고치려면 정리 함수에서 이전 요청을 무시해야 한다.

```tsx
useEffect(() => {
  const controller = new AbortController();
  fetch(url, { signal: controller.signal })
    .then((r) => r.json())
    .then(setData, (e) => { if (e.name !== "AbortError") setError(e); });
  return () => controller.abort(); // url이 바뀌거나 사라지면 이전 요청을 끊는다
}, [url]);
```

여기서 끝이 아니다. 같은 `url`을 두 컴포넌트가 부르면 요청이 두 번 나간다. 화면에 다시 돌아오면 이전 데이터를 보여 줄지, 로딩부터 다시 할지 정해야 한다. 실패하면 재시도할지, 몇 번 할지. 다른 화면에서 데이터를 바꾸면 이 데이터는 언제 낡은 것으로 볼지. 응답 상태 코드가 500이어도 `fetch`는 실패로 치지 않으니 `r.ok`도 봐야 한다. 기능마다 `useFetch(url, { dedupe, retry, staleTime, enabled })`처럼 옵션이 붙으면 훅이 감추려던 복잡함이 인자로 다 새어 나온다. 쓰는 쪽은 결국 훅의 내부를 알아야 제대로 쓴다.

새는 신호는 이런 것들이다. 불리언 옵션이 셋 이상이다. 반환하는 값이 대여섯 개를 넘고, 쓰는 쪽마다 쓰는 조합이 다르다. 훅 이름이 무엇을 하는지가 아니라 언제 도는지를 말한다(`useMount`, `useEffectOnce`). React 공식 문서도 이런 생명주기 이름의 훅을 만들지 말라고 한다. effect가 무엇과 동기화하는지를 감추고 의존성 검사를 피해 가기 때문이다. 데이터 요청처럼 캐시, 중복 제거, 갱신 시점이 얽힌 문제는 그 문제를 전문으로 푸는 라이브러리에 맡기고, 커스텀 훅은 그 위에 도메인 이름을 붙이는 데 쓴다(`useProduct(id)`가 안에서 쿼리 하나를 부르는 식). 요청 캐시가 무엇을 해 주는지는 [화면 데이터 캐시](/posts/client-data-cache)에서 다뤘다.

## 배열로 돌려줄까, 객체로 돌려줄까

`useState`는 배열을 돌려준다. 쓰는 쪽이 이름을 마음대로 붙일 수 있어서다. `const [isMenuOpen, toggleMenu] = useToggle()`, `const [isMuted, toggleMute] = useToggle()`처럼 한 컴포넌트에서 여러 번 쓸 때 편하다. 값이 두 개이고 순서가 뻔할 때 배열이 맞다. TypeScript에서는 `as const`를 붙여야 `[boolean, () => void]` 튜플로 추론된다. 안 붙이면 `(boolean | (() => void))[]`가 되어 쓰는 쪽에서 타입이 흐려진다.

값이 셋 이상이거나, 쓰는 쪽마다 필요한 게 다르면 객체가 낫다. `const { data, isLoading } = useProduct(id)`처럼 필요한 것만 이름으로 꺼내고, 나중에 필드를 더해도 기존 코드가 깨지지 않는다. 배열로 다섯 개를 돌려주면 쓰는 쪽은 `const [, , , refetch] = ...`처럼 자리를 세야 한다.

어느 쪽이든 돌려주는 참조가 안정적인지 신경 쓴다. 쓰는 쪽은 훅이 돌려준 함수를 `memo`로 감싼 자식에 넘기거나 effect 의존성에 넣을 수 있다. 훅 안에서 렌더링마다 새 함수를 만들어 돌려주면, 쓰는 쪽의 `useCallback`과 `memo`가 전부 무력해진다. 위 `useToggle`이 `toggle`을 `useCallback`으로 감싼 이유다. 객체를 돌려주는 훅도 그 객체가 의존성으로 쓰일 것 같으면 `useMemo`로 감싼다. 훅을 만드는 사람이 한 번 신경 쓰면 쓰는 사람 모두가 편해진다.

## 브라우저 값을 구독하는 훅

온라인 상태나 창 크기처럼 React 바깥에서 바뀌는 값을 읽는 훅은 흔히 이렇게 시작한다.

```tsx
function useOnlineStatus() {
  const [online, setOnline] = useState(navigator.onLine);
  useEffect(() => {
    const update = () => setOnline(navigator.onLine);
    window.addEventListener("online", update);
    window.addEventListener("offline", update);
    return () => {
      window.removeEventListener("online", update);
      window.removeEventListener("offline", update);
    };
  }, []);
  return online;
}
```

대체로 동작하지만 두 가지가 어긋날 수 있다. 첫 렌더링과 effect가 구독을 시작하는 사이에 값이 바뀌면 놓친다. 그리고 동시성 렌더링에서 렌더링이 길게 나뉘어 진행되는 동안 바깥 값이 바뀌면, 같은 화면 안의 두 컴포넌트가 서로 다른 값을 보고 그려질 수 있다. 이걸 tearing(찢어짐)이라고 한다. 외부 값을 위한 정식 통로가 `useSyncExternalStore`다.

```tsx
function subscribe(onChange: () => void) {
  window.addEventListener("online", onChange);
  window.addEventListener("offline", onChange);
  return () => {
    window.removeEventListener("online", onChange);
    window.removeEventListener("offline", onChange);
  };
}

export function useOnlineStatus() {
  return useSyncExternalStore(
    subscribe,              // 바뀌면 알려 줄 구독 함수 (컴포넌트 밖에 둔다)
    () => navigator.onLine, // 지금 값
    () => true,             // 서버와 하이드레이션 때 쓸 값
  );
}
```

`getSnapshot`은 값이 그대로면 같은 값을 돌려줘야 한다. 창 크기 훅에서 흔히 하는 실수가 `() => ({ width: innerWidth, height: innerHeight })`처럼 부를 때마다 새 객체를 돌려주는 것이다. React 19.2로 돌려 보면 이런 경고가 찍힌 뒤 렌더링이 멈추지 않아 `Maximum update depth exceeded`로 끝난다.

```text
The result of getSnapshot should be cached to avoid an infinite loop
```

부를 때마다 새 객체이니 매번 "바뀌었다"고 판단해 다시 렌더링하고, 다시 새 객체를 받는다. 원시값 하나만 돌려주는 훅으로 나누는 게 가장 간단하다.

```tsx
function subscribeResize(onChange: () => void) {
  window.addEventListener("resize", onChange);
  return () => window.removeEventListener("resize", onChange);
}

export const useWindowWidth = () =>
  useSyncExternalStore(subscribeResize, () => window.innerWidth, () => 0);
```

창 너비로 레이아웃을 바꾸는 거라면 훅보다 CSS 미디어 쿼리가 먼저다. 자바스크립트가 너비를 알아야 할 때(차트 크기 계산처럼)만 이 훅을 쓰고, 특정 요소의 크기라면 `ResizeObserver`를 구독한다. 세 번째 인자인 서버 값이 하이드레이션 때 어떻게 쓰이는지는 [하이드레이션 글](/posts/hydration)에서 실제로 확인했다.

## 훅을 테스트하는 법

훅은 컴포넌트 안에서만 부를 수 있으니 테스트에도 컴포넌트가 필요하다. `@testing-library/react`의 `renderHook`이 훅 하나만 부르는 작은 컴포넌트를 대신 만들어 준다. 예전에는 `@testing-library/react-hooks`라는 별도 패키지였는데, React 18부터는 `@testing-library/react`에 들어 있는 것을 쓴다.

```tsx
import { renderHook, act } from "@testing-library/react";

test("오프라인 이벤트를 받으면 false가 된다", () => {
  let online = true;
  Object.defineProperty(window.navigator, "onLine", { get: () => online, configurable: true });

  const { result } = renderHook(() => useOnlineStatus());
  expect(result.current).toBe(true);

  act(() => {
    online = false;
    window.dispatchEvent(new Event("offline"));
  });
  expect(result.current).toBe(false);
});
```

`result.current`는 마지막 렌더링에서 훅이 돌려준 값이다. 상태를 바꾸는 코드는 `act`로 감싸야 React가 렌더링과 effect를 다 처리한 뒤 다음 줄로 넘어간다. jsdom에서 이 테스트를 돌려 `true → false → true`로 바뀌는 것을 확인했다. 인자가 바뀌는 경우는 `initialProps`와 `rerender`로 본다.

```tsx
const { result, rerender } = renderHook(({ value }) => useDoubled(value), {
  initialProps: { value: 2 },
});
expect(result.current).toBe(4);
rerender({ value: 5 });
expect(result.current).toBe(10);
```

`renderHook`이 늘 정답은 아니다. 훅이 작고 한 컴포넌트에서만 쓰인다면 그 컴포넌트를 렌더링해서 화면에 보이는 결과로 테스트하는 편이 사용자 행동에 가깝다. 여러 화면에서 쓰는 공용 훅, 시간이나 브라우저 이벤트처럼 화면으로 확인하기 번거로운 동작을 가진 훅에 `renderHook`을 쓴다. 시계와 브라우저 API를 테스트 손에 쥐여 주는 방법은 [테스트 피라미드 글](/posts/test-pyramid-unit-tests)에 있다.

## 처음 프로필 화면으로

수정 모드의 `useState`를 `if` 안에 넣었더니 화면이 하얗게 된 건, React가 훅을 이름이 아니라 부른 순서로 찾기 때문이다. 하나를 건너뛰면 뒤의 훅들이 앞 칸을 열어 엉뚱한 값을 받고, 개수가 달라지면 그제야 에러가 난다. 개수와 종류가 우연히 맞으면 에러조차 없다. 그래서 훅은 맨 위 층에서 늘 같은 순서로 부르고, 이름은 `use`로 시작해서 린트가 검사하게 한다. 커스텀 훅은 그 규칙 위에서 로직을 나누는 함수이고, 상태는 부를 때마다 따로 생긴다. 바깥에서 보이는 모양을 작게 유지하고, 돌려주는 참조를 안정적으로 만들고, 브라우저 값은 `useSyncExternalStore`로 구독한다.

## 면접에서 나올 만한 질문

### 훅을 조건문 안에서 부르면 안 되는 이유는 무엇인가요?

React는 컴포넌트마다 훅 목록을 들고 있고, 렌더링 때 훅이 불린 순서대로 다음 칸을 꺼내 준다. 이름으로 찾지 않는다. 조건 때문에 훅 하나를 건너뛰면 그 뒤 훅들이 한 칸씩 앞 칸을 받아 다른 상태 값을 읽는다. 개수가 달라지면 "Rendered fewer/more hooks" 에러가 나지만, 개수와 종류가 같으면 아무 경고 없이 값이 섞인다.

### 훅 규칙을 지키게 도와주는 도구는 무엇인가요?

`eslint-plugin-react-hooks`의 `rules-of-hooks`가 조건부 호출, 반복문 안 호출, 컴포넌트나 훅이 아닌 함수 안의 호출을 에러로 잡고, `exhaustive-deps`가 의존성 배열의 빠진 값을 경고한다. 7 버전의 `recommended`에는 React Compiler가 쓰는 검사도 들어 있다. 린트는 함수 이름으로 컴포넌트와 훅을 구분하므로 훅 이름은 `use` 다음 대문자로 시작해야 한다.

### 커스텀 훅을 두 컴포넌트에서 쓰면 상태가 공유되나요?

아니다. 커스텀 훅은 다른 훅을 부르는 함수라서, 안의 `useState`는 부른 컴포넌트의 훅 목록에 따로 칸을 만든다. 나눠지는 건 로직이고 상태는 부를 때마다 새로 생긴다. 같은 상태를 봐야 하면 공통 부모로 올리거나 context나 외부 저장소에 두고, 커스텀 훅은 그 위의 입구로 쓴다.

### 좋은 커스텀 훅과 나쁜 커스텀 훅을 어떻게 구분하나요?

좋은 훅은 개념 하나를 감추고 바깥 모양이 작다. `useOnlineStatus`처럼 값 하나를 돌려주고 내부를 몰라도 쓸 수 있다. 쓰는 곳마다 불리언 옵션이 늘고, 반환 값이 많아지고, 쓰는 쪽이 내부 동작을 알아야 하면 추상화가 새는 것이다. `useFetch`가 대표적인데, 경쟁 상태, 중복 요청, 캐시, 재시도가 얽혀서 전용 라이브러리에 맡기는 편이 낫다. `useMount` 같은 생명주기 이름도 피한다.

### 커스텀 훅은 배열과 객체 중 무엇을 돌려줘야 하나요?

값이 두 개이고 순서가 뻔하며 한 컴포넌트에서 여러 번 쓸 수 있으면 `useState`처럼 배열이 좋다. 쓰는 쪽이 이름을 붙이기 쉽다. 셋 이상이거나 쓰는 쪽마다 필요한 게 다르면 객체가 낫고, 필드를 더해도 기존 코드가 깨지지 않는다. 어느 쪽이든 돌려주는 함수는 `useCallback`으로 고정해서 쓰는 쪽의 `memo`와 의존성 배열이 깨지지 않게 한다.

### 브라우저 API 값을 읽는 훅은 왜 useSyncExternalStore로 만드나요?

`useState`와 `useEffect`로 구독하면 첫 렌더링과 구독 사이의 변화를 놓칠 수 있고, 동시성 렌더링 중 값이 바뀌면 컴포넌트끼리 다른 값을 보는 tearing이 생길 수 있다. `useSyncExternalStore`는 렌더링 중에 지금 값을 읽고, 알림이 오면 다시 읽어 달라졌을 때만 렌더링하며, 서버용 값도 따로 받는다. `getSnapshot`은 값이 그대로면 같은 값을 돌려줘야 해서 객체 대신 원시값을 돌려준다.

### 커스텀 훅은 어떻게 테스트하나요?

`@testing-library/react`의 `renderHook`으로 훅을 부르는 작은 컴포넌트를 만들고 `result.current`로 마지막 반환 값을 확인한다. 상태를 바꾸는 동작은 `act`로 감싸고, 인자 변화는 `initialProps`와 `rerender`로 본다. 한 컴포넌트에서만 쓰는 작은 훅이면 컴포넌트를 렌더링해 화면 결과로 테스트하는 편이 더 현실적이다.
