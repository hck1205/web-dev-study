이런 PR을 생각해 보자. 주문을 100건씩 묶어 배송 API로 보내는 기능이다. 리뷰 코멘트는 열네 개가 달렸다. 들여쓰기, 따옴표 종류, 변수 이름 `arr`를 `orders`로 바꾸자는 말, import 순서. 작성자는 하나씩 고치고 승인을 받아 합쳤다. 다음 날 운영에서 주문 237건 중 37건이 배송 요청에 빠졌다. 원인은 마지막 묶음을 빼먹는 반복문 조건 한 줄이었고, 그 줄에는 코멘트가 없었다.

```ts
export async function sendInBatches(orders: Order[], size = 100) {
  for (let i = 0; i + size <= orders.length; i += size) {
    await shippingApi.post("/shipments", orders.slice(i, i + size));
  }
}
```

리뷰어가 게을렀던 건 아니다. 열네 개나 달았다. 문제는 눈이 간 순서였다. 바로 보이는 것부터 지적하다 보니, 정작 시간을 써야 할 곳에 주의가 남지 않았다. 이 글은 리뷰어가 무엇을 어떤 순서로 보고, 어떻게 말하고, 무엇은 도구에 맡기는지를 다룬다. 리뷰를 강제하는 저장소 설정(브랜치 보호, CODEOWNERS, 필수 검사)은 [저장소 설정 글](/posts/github-repo-governance)에, 큰 변경을 작은 PR로 나누는 법은 [stacked PR 글](/posts/git-stacked-prs)에 있다.

## 리뷰로 얻으려는 것

리뷰를 하는 이유를 물으면 대부분 "버그를 잡으려고"라고 답한다. 틀린 말은 아니다. 그런데 Microsoft에서 리뷰를 관찰한 연구(Bacchelli와 Bird, 2013)를 보면 개발자들이 가장 기대한 것은 결함 찾기였지만, 실제로 달린 코멘트는 가독성과 구조 개선, 그리고 코드를 이해하려는 질문이 더 많았다. 리뷰는 버그 검출기이기도 하지만, 그보다 자주 팀이 서로의 코드를 알게 되는 자리로 쓰인다.

그래서 리뷰의 목표를 하나로 잡기보다 셋으로 보는 편이 실무에 맞는다.

1. 틀린 것이 들어가지 않게 한다. 정확성, 보안, 데이터 손실.
2. 코드베이스가 나빠지지 않게 한다. 설계 일관성, 쓰기 쉬운 API, 이해할 수 있는 코드.
3. 지식을 나눈다. 리뷰어가 그 코드를 알게 되고, 작성자가 팀의 관례를 배운다.

Google의 공개 리뷰 가이드(eng-practices)는 승인 기준을 "완벽한가"가 아니라 "이 변경이 코드베이스의 상태를 분명히 낫게 하는가"로 잡는다. 완벽을 기준으로 삼으면 PR이 끝없이 돌고, 작성자는 다음부터 변경을 미룬다.

피라미드의 요점은 위층에 시간을 더 쓰라는 것이다. API 모양이 틀렸다면 그 아래 구현, 테스트, 문서를 아무리 다듬어도 다시 짜야 한다. 그래서 리뷰어는 PR을 열면 diff의 첫 줄부터 읽지 않는다. 설명을 먼저 읽고, 바뀐 공개 인터페이스를 먼저 보고, 그다음 구현으로 내려간다. 맨 아래의 스타일은 사람이 보지 않도록 도구로 치운다.

## 요구사항과 API를 먼저 본다

첫 질문은 "이 PR이 해결하려던 문제를 해결하나"다. PR 설명이나 연결된 이슈를 읽고, 요구사항과 diff가 맞는지 본다. 요청은 "실패한 주문만 재전송"이었는데 PR이 모든 주문을 재전송한다면 코드가 아무리 깔끔해도 의미가 없다.

그다음은 바깥에서 보이는 모양이다. 공개 함수, HTTP 엔드포인트, 설정 키, 이벤트 스키마, 그리고 놓치기 쉬운 메트릭 이름과 로그 형식까지 포함한다. 다른 팀의 대시보드와 알림이 메트릭 이름에, 로그 파서가 로그 형식에 기대고 있을 수 있다. 이 층에서 묻는 것들이다.

- 필요한 만큼만 크고 그 이상은 아닌가. 지금 쓰는 곳이 없는 옵션을 미리 열어 두지 않았나.
- 같은 일을 하는 방법이 둘이 되지 않았나. 기존 `sendShipment`가 있는데 비슷한 `postShipment`가 생기지 않았나.
- 기존 관례와 맞나. 다른 함수는 실패를 예외로 알리는데 이것만 `null`을 돌려주지 않나.
- 내부 구현이 밖으로 새지 않나. 응답에 DB 컬럼 이름이 그대로 나가지 않나.
- 깨지는 변경(breaking change)이 아닌가. 그렇다면 버전과 이전 안내가 있나.

위의 `sendInBatches`라면 이 층에서 "한 묶음이 실패하면 어떻게 되나"를 묻는다. 지금 시그니처는 `Promise<void>`라서, 세 번째 묶음에서 예외가 나면 앞의 두 묶음은 보내졌는데 호출한 쪽은 어디까지 갔는지 모른다. 돌려줄 값을 성공·실패 목록으로 바꿀지, 실패하면 멈출지를 정하는 건 구현보다 먼저 합의할 일이다.

## 구현이 맞는가

API가 괜찮다면 그 안을 본다. 이 층이 리뷰어가 시간을 가장 많이 쓰는 곳이고, 처음 장면의 버그가 있던 곳이다. 볼 것을 범주로 나눠 두면 빼먹지 않는다.

정확성. 경계값을 대입해 본다. 빈 배열, 원소 하나, 정확히 `size`의 배수, 배수가 아닌 길이. `sendInBatches`에 237건을 넣으면 `i`가 200일 때 `200 + 100 <= 237`이 거짓이라 반복이 끝나고, 마지막 37건이 빠진다. `size`에 0이 들어오면 `i`가 늘지 않아 무한 루프다. 머릿속으로 숫자 몇 개를 넣어 보는 것만으로 잡히는 버그가 많다.

에러 처리. 실패가 어디로 가는지 따라간다. 예외를 잡아서 로그만 남기고 삼키지 않나. 재시도한다면 같은 요청을 두 번 보내도 안전한가. 배송 API가 같은 묶음을 두 번 받으면 배송이 두 번 잡힐 수 있다. 재시도와 중복 방지는 [멱등성 키 글](/posts/idempotency-key)에서 다룬 문제다.

동시성. 공유 상태를 여러 요청이 함께 고치지 않나. 읽고-계산하고-쓰는 사이에 다른 요청이 끼어들 수 있나. 위 코드처럼 `await`를 반복문 안에서 하나씩 기다리는 건 느리지만 순서가 보장되고, `Promise.all`로 바꾸면 빠르지만 상대 API에 동시에 요청이 몰린다. 어느 쪽이 맞는지는 상대 API의 제한을 알아야 정할 수 있다.

보안. 사용자 입력이 쿼리, 셸 명령, HTML, 파일 경로로 들어가지 않나. 권한 검사가 빠진 새 엔드포인트는 없나. 로그에 토큰이나 개인 정보가 찍히지 않나.

성능과 운영. 반복문 안의 쿼리(N+1), 상한 없는 목록 조회, 타임아웃 없는 외부 호출. 장애가 났을 때 이 코드가 무엇을 남기는지도 본다. 실패한 묶음의 주문 번호가 로그에 남지 않으면, 다음 날 37건을 찾느라 한참을 쓴다.

의존성. 새 라이브러리를 넣었다면 왜 필요한지, 유지보수되는지, 라이선스가 괜찮은지. 함수 하나를 쓰려고 큰 패키지를 넣지 않았는지.

이 범주를 매번 외워서 볼 수는 없으니 팀의 PR 템플릿에 짧은 체크리스트로 넣어 둔다. 다만 체크박스에 표시하는 것이 리뷰를 대신하지는 않는다. 숫자를 대입해 보는 일은 사람이 직접 해야 한다.

## 두 번째 PR: 쿠폰을 쓰는 API

구현 층의 범주가 실제 diff에서 어떻게 보이는지 하나 더 보자. 쿠폰을 한 번만 쓸 수 있게 하는 엔드포인트다. 테스트도 있고 스타일 검사도 통과했다.

```ts
app.post("/coupons/:code/redeem", async (req, res) => {
  const coupon = await db.coupon.findUnique({ where: { code: req.params.code } });
  logger.info("redeem", { code: req.params.code, auth: req.headers.authorization });
  if (!coupon || coupon.usedAt) return res.status(400).json({ error: "invalid" });
  await db.coupon.update({ where: { id: coupon.id }, data: { usedAt: new Date(), userId: req.body.userId } });
  res.json({ ok: true });
});
```

위층부터 내려가며 읽으면 코멘트가 이렇게 나온다.

```text
issue (blocking): 같은 쿠폰으로 요청 두 개가 동시에 오면 둘 다 usedAt이 비어 있는 걸 읽고
  둘 다 통과한다. 읽고 나서 쓰는 사이가 비어 있다. 조건을 붙인 update 한 번으로
  "usedAt IS NULL인 행만 바꾸고, 바뀐 행 수가 0이면 실패"로 하면 DB가 한 번만 허락한다.

issue (blocking): userId를 요청 본문에서 받는다. 로그인한 사용자가 아닌 다른 사람 이름으로
  쿠폰을 쓸 수 있다. 인증 미들웨어가 넣어 준 사용자 id를 써야 한다.

issue (blocking): authorization 헤더 전체가 로그에 남는다. 로그를 볼 수 있는 사람이면
  누구나 토큰을 재사용할 수 있다.

question: 없는 쿠폰과 이미 쓴 쿠폰이 같은 400이다. 고객 센터가 둘을 구분해야 하지 않나?
```

```ts
// 고친 뒤: 한 문장으로 확인과 사용을 묶는다
const { count } = await db.coupon.updateMany({
  where: { code: req.params.code, usedAt: null },
  data: { usedAt: new Date(), userId: req.user.id },
});
if (count === 0) return res.status(409).json({ error: "already_used_or_missing" });
```

세 개의 blocking은 모두 테스트가 통과하는 코드에 있었다. 동시 요청, 다른 사람의 id, 로그의 토큰은 한 번에 하나씩 보내는 단위 테스트로는 드러나지 않는다. 리뷰어가 "요청이 둘이면", "이 값은 누가 정하나", "이 로그를 누가 보나"를 물어야 보인다. 동시 요청이 만드는 문제는 [경쟁 상태 글](/posts/race-conditions)에서 더 다룬다.

## 테스트가 행동을 확인하나

테스트가 있는지보다 무엇을 확인하는지 본다. `sendInBatches` PR에도 테스트는 있었다. 200건을 넣고 API가 두 번 불렸는지 확인하는 테스트 하나였다. 200은 100의 배수라서 버그가 드러나지 않는다. 테스트가 통과한다는 사실이 리뷰어를 안심시켰을 수도 있다.

리뷰어가 테스트에서 묻는 것들이다.

- 경계값이 들어 있나. 빈 입력, 배수가 아닌 길이, 잘못된 인자.
- 새로 생긴 행동마다 테스트가 있나. 고친 버그라면 그 버그를 재현하는 테스트가 먼저 실패했다가 통과하나.
- 구현이 아니라 행동을 확인하나. 내부 함수 호출 순서까지 mock으로 고정하면 리팩터링할 때마다 테스트가 깨진다.
- 테스트 이름만 읽어도 무엇을 보장하는지 알 수 있나.
- 시간, 난수, 네트워크에 기대어 가끔 실패하는 테스트가 아닌가.

리뷰어 입장이 되어 보자. 아래는 PR에 올라온 묶음 나누기 함수다. 테스트를 돌려 보면 PR의 원래 테스트(배수인 경우)는 통과하지만 다른 경우는 틀린다. 고쳐서 모두 통과하게 만들어 보자. 참고로 처음 코드에 `size`로 0을 넣으면 무한 루프라서 테스트에서 뺐다.

## 문서와 이름

코드가 맞고 테스트도 있다면, 다음 사람이 읽을 수 있는지 본다.

이름은 무엇을 하는지 말해야 한다. `process`, `handle`, `data`, `tmp` 같은 이름은 읽는 사람이 본문을 다 읽게 만든다. `sendInBatches`는 괜찮은 이름이지만, 묶음 하나가 실패해도 계속 보내는지 멈추는지는 이름으로 알 수 없으니 문서 주석에 적는다.

주석은 무엇을 하는지가 아니라 왜 그렇게 했는지를 적는다. "100건씩 나눈다"는 코드가 이미 말한다. "배송 API가 한 요청에 100건까지만 받는다(2026년 10월 기준 문서)"는 코드가 말해 주지 못한다. 나중에 누군가 이 숫자를 500으로 바꾸려 할 때 막아 주는 건 이런 주석이다.

바깥에 보이는 변화가 있으면 README, 변경 기록(CHANGELOG), 설정 예시, 마이그레이션 안내가 함께 바뀌었는지 본다. 새 환경 변수를 추가했는데 `.env.example`에 없으면 다음에 배포하는 사람이 빈 값으로 띄운다.

## 스타일은 사람이 보지 않는다

처음 장면의 열네 개 코멘트 중 열한 개가 이 층이었다. 들여쓰기, 따옴표, import 순서, 줄 길이. 이런 지적은 리뷰어에게는 쉽고, 작성자에게는 사소하고, 둘 다의 주의를 갉아먹는다. 기계가 결정할 수 있는 것은 기계에게 넘긴다.

```json
// package.json
{
  "scripts": {
    "format": "prettier --write .",
    "format:check": "prettier --check .",
    "lint": "eslint ."
  }
}
```

```yaml
# .github/workflows/ci.yml 의 일부
jobs:
  style:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - run: pnpm install --frozen-lockfile
      - run: pnpm format:check    # 포맷이 다르면 실패
      - run: pnpm lint            # 린트 규칙 위반이면 실패
      - run: pnpm typecheck
```

이 job을 필수 검사로 걸면, 포맷이 어긋난 PR은 사람이 열기 전에 빨간불이 켜진다. 커밋 전에 바꾼 파일만 자동으로 고치는 훅(husky와 lint-staged 같은 조합)을 더하면 빨간불도 거의 안 켜진다. 훅은 건너뛸 수 있으니 CI 검사가 기준이고 훅은 편의다.

팀이 정할 것은 하나다. "도구가 통과시킨 스타일에는 리뷰에서 토를 달지 않는다." 마음에 안 드는 규칙이 있으면 PR 코멘트가 아니라 린트 설정을 바꾸는 PR로 논의한다. 그러면 같은 논쟁을 PR마다 반복하지 않는다.

## 코멘트에 등급을 붙인다

리뷰를 받는 사람이 가장 답답한 건 코멘트 열네 개 중 어느 것이 꼭 고쳐야 하는 것인지 모를 때다. 그래서 코멘트 앞에 등급을 붙인다. 널리 쓰는 형식 하나가 Conventional Comments다. `라벨 (꾸밈): 내용` 모양이고, 라벨은 `praise`, `nitpick`, `suggestion`, `issue`, `question`, `thought`, `todo`, `note` 같은 것을 쓴다. 꾸밈에 `blocking`이나 `non-blocking`을 붙여 합치기 전에 고쳐야 하는지를 밝힌다.

```text
issue (blocking): 237건을 넣으면 i=200에서 반복이 끝나 마지막 37건이 빠진다.
  i < orders.length 로 바꾸면 slice가 남은 만큼만 자른다.

question: 묶음 하나가 실패하면 나머지는 계속 보내야 하나, 멈춰야 하나?
  호출하는 쪽이 어디까지 갔는지 알 방법이 필요해 보인다.

suggestion (non-blocking): 실패한 묶음의 주문 번호를 로그에 남기면 재전송이 쉽다.

nitpick (non-blocking): arr 보다 orders 가 읽기 쉽다.

praise: 배송 API 한도를 상수로 뺀 것 좋다. 근거 링크까지 있어서 바꿀 때 덜 헷갈리겠다.
```

아래 그림은 리뷰어가 diff를 위에서 아래로 훑으며 코멘트를 쌓는 과정이다. 같은 diff라도 등급을 붙이면 작성자가 무엇부터 할지가 정해진다.

## 코드에 대해 말한다

같은 지적도 말투에 따라 받아들여지는 정도가 다르다. 리뷰는 글로만 오가서 말투가 실제보다 날카롭게 읽힌다.

사람이 아니라 코드를 주어로 쓴다. "왜 이렇게 짰어요?"보다 "이 조건이면 마지막 묶음이 빠지는 것 같다"가 낫다. 명령보다 이유를 붙인다. "`Promise.all`로 바꾸세요"보다 "`Promise.all`로 바꾸면 237건이 3번이 아니라 동시에 나가서 빨라진다. 다만 상대 API가 동시 요청을 몇 개까지 받는지 확인이 필요하다"가 낫다. 모르는 건 질문으로 묻는다. 작성자가 이미 고민했을 수 있다.

"그냥", "당연히", "간단히" 같은 말은 뺀다. 상대가 그걸 몰랐다면 그 말 때문에 더 묻기 어려워진다. 긴 논쟁이 세 번 넘게 오가면 글을 멈추고 10분 통화한다. 결론은 PR에 한 줄로 다시 적어 둔다. 나중에 이 PR을 찾는 사람이 결론을 볼 수 있게.

## PR 크기와 리뷰 속도

리뷰는 PR이 작을수록 잘 된다. SmartBear가 Cisco의 리뷰를 분석한 사례 연구는 한 번에 200~400줄을 넘기면 결함을 찾는 비율이 떨어지고, 한 시간에 500줄보다 빨리 읽으면 놓치는 것이 많아진다고 보고했다. 숫자는 팀과 언어마다 다르겠지만 방향은 분명하다. 1,800줄짜리 PR은 꼼꼼히 읽히지 않고 대충 승인된다.

속도는 크기만큼 중요하다. 리뷰를 기다리는 시간은 작성자의 시간을 직접 잡아먹는다. 아래 그림에서 PR 하나가 합쳐지기까지 시간이 어디서 흘러가는지 따라가 보자.

Google의 가이드는 리뷰 요청에 늦어도 근무일 하루 안에 응답하라고 권한다. 몰입한 작업을 끊고 바로 볼 필요는 없지만, 작업이 끊기는 지점(점심 뒤, 회의 뒤)에 리뷰 큐를 먼저 비우는 습관을 들이면 팀 전체의 흐름이 빨라진다. 바로 못 보면 "오늘은 어렵다, 내일 오전에 본다"라고만 답해도 작성자가 계획을 세울 수 있다.

리뷰가 늦으면 PR이 커진다. 기다리는 동안 작성자가 같은 브랜치에 다음 작업을 얹기 때문이다. 큰 PR은 다시 리뷰를 늦춘다. 이 고리를 끊으려면 작게 올리고 빨리 돌려주는 것 말고 방법이 없다.

## 작성자가 리뷰받기 좋게 만드는 법

리뷰의 질은 절반쯤 작성자에게 달려 있다.

올리기 전에 셀프 리뷰를 한다. GitHub의 Files changed 화면에서 내 diff를 리뷰어처럼 읽으면 에디터에서는 안 보이던 것이 보인다. 설명에는 왜, 무엇을, 어떻게 확인했는지, 어디를 특히 봐 달라는지를 쓴다. "API 한도 때문에 100건씩 나눴는데, 동시에 보낼지 순서대로 보낼지 의견을 듣고 싶다"는 한 줄이 리뷰어의 시간을 아낀다.

한 가지 이유로만 바꾼다. 리팩터링과 기능 변경이 섞이면 리뷰어는 이름 바꾸기 사이에서 로직 변경을 찾아야 한다. 이름 바꾸기 PR을 먼저 합치고 기능 PR을 올린다. 서로 의존하는 큰 작업은 [stacked PR](/posts/git-stacked-prs)로 쌓는다.

diff에 내가 먼저 코멘트를 단다. "이 파일은 위치만 옮겼다", "이 부분은 다음 PR에서 지운다" 같은 안내가 있으면 리뷰어가 엉뚱한 곳에서 시간을 쓰지 않는다.

모든 코멘트에 답한다. 고쳤으면 "고쳤다"와 커밋 링크를, 안 고치기로 했으면 이유를 적는다. 코멘트를 말없이 resolve하면 리뷰어는 다시 다 확인해야 한다.

## 리뷰가 잘 굴러가는지 재 본다

느낌 대신 숫자로 보면 어디가 막히는지 빨리 보인다. 자주 보는 지표는 넷이다. 첫 리뷰까지 걸린 시간, 머지까지 걸린 시간, PR의 변경 줄 수, 리뷰 왕복 횟수. GitHub CLI로 최근에 합친 PR을 JSON으로 받아 jq로 계산할 수 있다.

```bash
# 최근 합쳐진 PR 100개의 생성·머지 시각, 변경 줄 수, 리뷰 시각을 받는다
gh pr list --state merged --limit 100 \
  --json number,createdAt,mergedAt,additions,deletions,reviews > prs.json

# PR 번호, 변경 줄 수, 첫 리뷰까지 시간(h), 머지까지 시간(h)
jq -r 'def h(a; b): (((b | fromdate) - (a | fromdate)) / 360 | floor) / 10;
  .[] | [.number, (.additions + .deletions), h(.createdAt; .reviews[0].submittedAt), h(.createdAt; .mergedAt)] | @tsv' prs.json
```

아래는 같은 모양으로 만든 PR 네 개짜리 예시 파일에 jq를 돌린 결과다.

```text
412	96	0.9	4.5
413	1598	29	54.5
415	40	0.3	1.5
418	350	17.5	22
```

네 줄만 봐도 경향이 보인다. 100줄 안쪽인 412와 415는 한 시간 안에 첫 리뷰가 왔고, 1,598줄인 413은 첫 리뷰까지 29시간, 머지까지 이틀이 넘게 걸렸다. 실제 저장소에서 몇 주치를 뽑아 변경 줄 수 구간별로 중앙값을 내 보면 팀의 병목이 크기인지 응답 속도인지 나뉜다. 리뷰가 하나도 없이 합쳐진 PR은 `reviews[0]`이 없어 계산이 비니 따로 세어 본다. 그 수 자체가 규칙이 지켜지는지 보여 준다.

지표를 목표로 삼으면 망가진다. "첫 리뷰 1시간 이내"를 성과로 재면 내용 없는 승인이 빨라질 뿐이다. 숫자는 팀이 함께 보며 어디를 고칠지 고르는 데에만 쓴다.

## 의견이 갈릴 때

리뷰에서 의견이 갈리는 건 정상이다. 문제는 결론이 안 나고 PR이 멈추는 것이다. 판단의 우선순위를 미리 정해 두면 대부분 풀린다.

1. 사실과 데이터가 먼저다. 벤치마크, 재현 테스트, 공식 문서가 있으면 그것으로 정한다.
2. 팀의 스타일 가이드나 기존 관례가 그다음이다. 정해진 게 있으면 개인 취향보다 앞선다.
3. 둘 다 없고 두 방법이 비슷하게 괜찮으면 작성자의 선택을 따른다. 리뷰어가 쓰는 코드가 아니다.
4. 설계 원칙이 정말 부딪히면 글을 멈추고 대화한다. 그래도 안 되면 기술 리드나 오너 팀이 정하고, 결론을 설계 결정 기록(ADR)이나 PR에 남긴다.

리뷰어가 할 수 있는 좋은 양보는 "이건 내 취향이라 non-blocking"이라고 밝히는 것이다. 작성자가 할 수 있는 좋은 양보는 "지금 범위를 넘으니 이슈로 따로 뺀다"고 하고 실제로 이슈를 만드는 것이다.

## AI 리뷰는 어디까지 믿나

요즘은 PR을 열면 AI 리뷰어가 먼저 코멘트를 다는 팀이 많다. 써 보면 잘하는 것과 못하는 것이 꽤 분명하다.

잘하는 쪽은 피라미드의 아래 절반과 구현 층의 패턴화된 실수다. 빠진 null 검사, 닫지 않은 리소스, 경계값 실수, 오타, 테스트가 없는 분기, 흔한 보안 패턴(문자열로 이어 붙인 SQL). 위의 `i + size <= length` 같은 실수도 자주 잡는다. 사람이 지치는 반복 작업을 맡기기에 좋다.

못하는 쪽은 맥락이 필요한 판단이다. 이 PR이 요구사항을 만족하는지, 이 API가 팀의 다른 서비스와 일관된지, 이 메트릭 이름을 다른 팀의 대시보드가 쓰는지는 diff 밖에 있다. 그리고 그럴듯하지만 틀린 코멘트도 섞여 나온다. 잘못된 지적을 반박하는 데에도 시간이 든다.

그래서 AI 리뷰는 린터보다 조금 똑똑한 자동 검사로 놓는 편이 맞다. CI처럼 사람보다 먼저 돌게 하고, 결과를 작성자가 먼저 정리한 뒤 사람에게 요청한다. 승인은 사람이 한다. 문제가 생겼을 때 "AI가 통과시켰다"는 설명이 되지 않는다. 사내 코드를 외부 서비스로 보내는 도구라면 데이터가 어디에 저장되고 학습에 쓰이는지 보안 담당과 먼저 확인한다.

## 무엇을 막고 무엇을 넘기나

결국 리뷰어가 매번 내리는 결정은 이 PR을 지금 막을지다. 기준을 정리하면 이렇다.

막는다. 틀린 동작(버그, 빠진 경계값), 보안 문제, 데이터를 잃거나 망가뜨릴 수 있는 변경, 예고 없이 깨지는 API·설정·메트릭·로그 형식, 새 행동에 테스트가 없는 것, 되돌리기 어려운 마이그레이션에 되돌리는 방법이 없는 것.

넘긴다. 취향 차이, 비슷하게 좋은 다른 방법, 이번 범위 밖의 개선, 도구가 통과시킨 스타일. 넘길 것은 non-blocking으로 남기거나 후속 이슈로 만든다.

그리고 승인은 "더 할 말이 없다"가 아니라 "합쳐도 코드베이스가 나빠지지 않는다"는 뜻으로 한다. non-blocking 코멘트를 남기면서 승인하는 것이 가장 흔하고 좋은 리뷰다.

## 마지막 37건을 다시 본다면

처음 PR로 돌아가면, 리뷰어가 할 일은 열네 개를 다는 것이 아니었다. 설명을 읽고, 실패하면 어떻게 되는지 묻고, 반복문에 237을 넣어 보고, 테스트에 배수가 아닌 길이가 있는지 확인하는 것이었다. 들여쓰기는 CI가 이미 봤어야 했다. 위층부터 보고, 아래층은 도구에 넘기고, 막을 것과 넘길 것을 등급으로 밝히고, 빨리 돌려준다. 이 네 가지가 리뷰의 질을 정한다.

## 면접에서 나올 만한 질문

### 코드 리뷰에서 무엇을 가장 먼저 보나요?

PR이 해결하려던 문제를 해결하는지와 바깥에서 보이는 API 모양부터 본다. 요구사항과 어긋나거나 API가 틀리면 그 아래 구현과 테스트를 다듬어도 다시 짜야 하기 때문이다. 그다음 구현의 정확성, 에러 처리, 동시성, 보안으로 내려가고, 테스트가 행동을 확인하는지, 문서와 이름이 충분한지 본다. 포맷과 린트는 CI에 맡겨서 사람은 보지 않는다.

### 리뷰에서 무엇은 막고 무엇은 넘기나요?

틀린 동작, 보안 문제, 데이터 손실 위험, 예고 없는 깨지는 변경, 새 행동에 테스트가 없는 것은 막는다. 취향 차이, 비슷하게 좋은 대안, 범위 밖 개선은 non-blocking으로 남기거나 후속 이슈로 뺀다. 코멘트에 blocking 여부를 밝혀 두면 작성자가 무엇부터 고칠지 알고, 리뷰어도 막는 이유를 설명할 수 있는지 스스로 점검하게 된다.

### 스타일 지적이 리뷰를 채운다면 어떻게 하나요?

포맷터와 린터를 CI의 필수 검사로 걸어 사람이 보기 전에 걸러지게 한다. 커밋 전 훅으로 바꾼 파일만 자동으로 고치게 하면 더 편하지만, 훅은 건너뛸 수 있으니 기준은 CI다. 팀은 "도구가 통과시킨 스타일에는 토를 달지 않는다"고 정하고, 규칙에 불만이 있으면 PR 코멘트가 아니라 설정을 바꾸는 PR로 논의한다.

### PR 크기는 리뷰에 어떤 영향을 주나요?

크면 결함을 찾는 비율이 떨어지고 리뷰가 늦어진다. SmartBear의 Cisco 사례 연구는 한 번에 200~400줄을 넘기면 결함 검출이 떨어진다고 보고했다. 큰 PR은 누구도 한 번에 끝낼 수 없어 미뤄지고, 기다리는 동안 작성자가 작업을 더 얹어 더 커지는 악순환이 생긴다. 한 가지 이유로만 바꾸고, 리팩터링을 따로 올리고, 의존하는 작업은 stacked PR로 나눈다.

### 리뷰가 느리면 팀에 어떤 일이 생기나요?

작성자의 작업이 기다림에 묶이고, 그 사이 같은 브랜치에 일을 더 얹어서 PR이 커지고, 큰 PR은 다시 리뷰를 늦춘다. 오래 열린 PR은 main과 멀어져 충돌도 늘어난다. 근무일 하루 안에 첫 응답 같은 약속을 정하고, 작업이 끊기는 시점에 리뷰 큐를 먼저 비우고, 바로 못 보면 언제 볼지만이라도 답한다. 리뷰어가 몇 명에게 몰리면 팀 단위 자동 배정으로 나눈다.

### 리뷰 의견이 갈리면 어떻게 정하나요?

사실과 데이터, 그다음 팀의 스타일 가이드와 기존 관례 순서로 정한다. 둘 다 없고 두 방법이 비슷하게 괜찮으면 작성자의 선택을 따른다. 글로 세 번 넘게 오가면 짧게 대화하고 결론을 PR에 한 줄로 남긴다. 그래도 안 되면 오너 팀이나 기술 리드가 정하고 설계 결정 기록으로 남긴다.

### AI 코드 리뷰를 어디까지 믿나요?

빠진 null 검사, 경계값 실수, 흔한 보안 패턴처럼 diff 안에서 보이는 실수를 잡는 데는 쓸 만하다. 요구사항 충족, 다른 서비스와의 일관성, 메트릭 이름을 누가 쓰는지 같은 diff 밖 맥락은 판단하지 못하고, 그럴듯하지만 틀린 지적도 섞인다. 그래서 CI처럼 사람보다 먼저 도는 자동 검사로 두고, 승인과 책임은 사람이 진다. 외부 서비스라면 코드가 어디로 가는지 보안 측면도 먼저 확인한다.

### 작성자로서 리뷰를 잘 받으려면 무엇을 하나요?

올리기 전에 내 diff를 리뷰어 눈으로 한 번 읽고, 설명에 왜·무엇을·어떻게 확인했는지와 특히 봐 줄 곳을 쓴다. 한 가지 이유로만 바꾸고, diff에 먼저 안내 코멘트를 단다. 리뷰 중에는 강제 푸시보다 커밋을 덧붙여 바뀐 부분만 다시 보게 하고, 모든 코멘트에 고쳤는지 왜 안 고쳤는지 답한다.
