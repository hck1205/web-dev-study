오후 두 시, 메신저에 한 줄이 온다. "DB가 느려요." 주문 API의 p99가 4초를 넘었고, 대시보드의 DB CPU는 40% 언저리라 딱히 바빠 보이지도 않는다. 누군가는 재시작하자고 하고, 누군가는 인스턴스를 키우자고 한다. 둘 다 원인을 모른 채 하는 처방이고, 재시작은 증거까지 지운다.

이 글은 그 한 줄을 받고 원인이 어느 층에 있는지 10분 안에 좁히는 순서를 따라간다. DB 안(지금 무엇을 기다리나, 누가 줄 맨 앞인가, 누가 시간을 먹었나), 지나간 기록(로그), DB 밖(OS, 프로세스 하나의 시스템 콜과 CPU), 그리고 백엔드가 죽었을 때 증거를 남기는 법까지 내려간다. 찾은 쿼리를 실행 계획으로 고치는 일은 [느린 쿼리 찾기 글](/posts/sql-query-tuning), 잠금의 원리는 [재고 -1 막기 글](/posts/db-locking-deadlock), 서버 전체를 1분 안에 훑는 법은 [리눅스 성능 점검 60초 글](/posts/linux-performance-triage)에 있다. 여기서는 그 셋을 어떤 순서로 꺼내는지가 주제다.

실습 환경은 Ubuntu 24.04, PostgreSQL 16.15다. `shop` 데이터베이스에 상품 3개짜리 `products`와 주문 200만 건짜리 `orders`를 만들었다.

```sql
-- 상품 세 개. 재고를 줄이는 UPDATE가 몰리는 테이블이다
create table products(id int primary key, name text, stock int);
insert into products values (1,'keyboard',10),(2,'mouse',30),(3,'monitor',5);

-- 주문 200만 건. user_id에는 아직 인덱스가 없다
create table orders(
  id bigserial primary key,
  user_id int, product_id int, amount int,
  created_at timestamptz default now()
);
insert into orders(user_id, product_id, amount, created_at)
select (random()*10000)::int, 1+(random()*2)::int, (random()*100000)::int,
       now() - random()*interval '365 days'
from generate_series(1, 2000000);
```

중요한 건 위층부터 지우는 것이다. `pg_stat_activity`는 조회 한 번이면 끝나고 아무것도 멈추지 않는다. strace와 gdb는 프로세스를 실제로 붙잡는다. 아래층 도구부터 꺼내면 비싸고, 위층에서 끝날 일을 놓친다.

## 지금 DB 안에서 무엇을 기다리나

첫 쿼리는 세션을 상태와 대기 이벤트로 묶어 세는 것이다. 세션이 300개여도 이렇게 묶으면 몇 줄로 줄어든다.

```sql
-- 클라이언트 세션만, 상태와 대기 이벤트로 묶어 센다
select state, wait_event_type, wait_event, count(*)
from pg_stat_activity
where backend_type = 'client backend'
  and pid <> pg_backend_pid()   -- 이 조회를 하는 내 세션은 빼고
group by 1, 2, 3
order by 4 desc;
```

장애 상황을 재현해 둔 DB에서 돌린 결과다.

```text
        state        | wait_event_type |  wait_event   | count
---------------------+-----------------+---------------+-------
 active              | Lock            | tuple         |     2
 active              | Lock            | transactionid |     1
 idle in transaction | Client          | ClientRead    |     1
(3 rows)
```

읽는 법은 `wait_event_type`부터다. 자주 보는 값은 이 정도다.

- 비어 있음(NULL): 기다리지 않는다. 보통 CPU에서 계산 중이다. 다만 계측 지점이 없는 곳에서 기다리는 경우도 여기에 섞인다.
- `Lock`: 행·테이블·트랜잭션 같은 무거운 잠금을 기다린다. 누군가 먼저 쥐고 있다는 뜻이라, 다음 절의 대기열 찾기로 간다.
- `LWLock`: 공유 메모리 안의 가벼운 잠금. `BufferMapping`, `WALWrite`처럼 이름이 내부 자원을 가리킨다. 많이 보이면 동시에 같은 자원을 두드리는 쿼리가 많다는 신호다.
- `IO`: `DataFileRead`, `WALSync`처럼 디스크 읽기·쓰기를 기다린다.
- `Client`: 클라이언트를 기다린다. `ClientRead`는 "다음 명령 아직이야?" 상태다.
- `IPC`, `Timeout`, `Activity`: 병렬 워커끼리의 통신, `pg_sleep` 같은 의도된 대기, 백그라운드 프로세스의 쉬는 시간.

위 결과는 이야기가 분명하다. 세 세션이 `Lock`을 기다리고, 한 세션이 트랜잭션을 연 채로 클라이언트의 다음 명령을 기다린다(`idle in transaction`). DB CPU가 40%로 한가한데 API가 느렸던 이유다. 일을 못 하고 서 있었다.

한 번 찍은 결과는 그 순간일 뿐이다. 부하가 계속되는 상황이면 0.2초 간격으로 여러 번 찍어 모으면 "세션들이 시간을 어디에 쓰는지" 분포가 나온다. 인덱스 없는 조회를 8개 연결로 돌리면서 40번 찍었다.

```bash
# 0.2초마다 active 세션의 대기 이벤트를 찍고, 40번 모아 센다. NULL은 CPU로 표시
for i in $(seq 1 40); do
  psql -d shop -Atc "select coalesce(wait_event_type,'CPU')||':'||coalesce(wait_event,'-')
                     from pg_stat_activity
                     where state='active' and backend_type='client backend' and pid<>pg_backend_pid()"
  sleep 0.2
done | sort | uniq -c | sort -rn
```

```text
    135 CPU:-
     34 LWLock:BufferMapping
     10 IO:DataFileRead
      9 IPC:BgWorkerShutdown
      4 IPC:MessageQueueReceive
      4 IPC:BufferIO
      1 Timeout:SpinDelay
```

이번엔 대부분 CPU다. 기다리는 게 아니라 일이 많다. 같은 테이블을 여러 세션이 통째로 읽으니 버퍼를 찾는 `BufferMapping` 경합이 그다음이다. 이런 분포가 나오면 잠금이 아니라 "비싼 쿼리" 쪽으로 간다. AWS RDS의 Performance Insights나 pg_wait_sampling 확장이 하는 일이 바로 이 샘플링을 자동으로, 오래 쌓아 주는 것이다.

## 줄이 서 있으면 맨 앞을 찾는다

`Lock`이 보이면 "누가 누구를 막고 있나"를 본다. `pg_blocking_pids(pid)`는 그 세션을 막고 있는 세션들의 pid 배열을 돌려준다.

```sql
-- 막혀 있는 세션과, 그 세션을 막는 pid 목록
select pid, application_name, pg_blocking_pids(pid) as blocked_by,
       wait_event, left(query, 45) as query
from pg_stat_activity
where cardinality(pg_blocking_pids(pid)) > 0;
```

```text
  pid  | application_name |  blocked_by   |  wait_event   |                     query
-------+------------------+---------------+---------------+-----------------------------------------------
 12747 | order-api        | {12737}       | transactionid | update products set stock = stock - 1 where i
 12748 | order-api        | {12747}       | tuple         | update products set stock = stock - 1 where i
 12749 | order-api        | {12747,12748} | tuple         | update products set stock = stock - 1 where i
(3 rows)
```

여기서 흔히 실수한다. 12748을 막는 건 12747이라고 나오니 12747을 죽이고 싶어진다. 하지만 12747도 12737을 기다리는 피해자다. 대기열은 사슬이고, 풀어야 할 건 사슬의 맨 앞이다. 아래 그림에서 다음을 누르면 줄이 어떻게 생기는지 따라간다.

맨 앞을 찾는 쿼리는 "남을 막고 있는데 자기는 막혀 있지 않은 세션"이다.

```sql
-- 대기열의 뿌리: 다른 세션을 막지만, 자기는 아무도 기다리지 않는다
select a.pid, a.application_name, a.state, now() - a.xact_start as xact_age
from pg_stat_activity a
where cardinality(pg_blocking_pids(a.pid)) = 0
  and exists (select 1 from pg_stat_activity w
              where a.pid = any(pg_blocking_pids(w.pid)));
```

```text
  pid  | application_name |        state        |    xact_age
-------+------------------+---------------------+-----------------
 12737 | admin-batch      | idle in transaction | 00:00:14.906643
(1 row)
```

뿌리가 `idle in transaction`인 경우가 정말 많다. 애플리케이션이 트랜잭션 안에서 외부 API를 부르거나, 예외 경로에서 커밋도 롤백도 안 하거나, 사람이 psql에서 BEGIN을 치고 점심을 먹으러 갔거나. 쿼리 열에는 그 세션이 마지막으로 보낸 문장이 남아 있을 뿐이라, 지금 실행 중인 문장처럼 읽으면 안 된다.

같은 판단을 함수로 짜 보자. 세션 목록(각 세션의 pid와 blocked_by)을 받아 대기열의 뿌리 pid를 오름차순으로 돌려준다. 뿌리가 목록 밖에 있을 수도 있다(다른 DB의 세션을 걸러 냈다면). 서로를 기다리는 교착 상태라면 뿌리가 없다.

교착 상태에서 뿌리가 없다는 결과는 실제 동작과도 맞다. 서로를 기다리는 원은 누가 비켜 주지 않으면 영원히 안 풀리니, PostgreSQL은 `deadlock_timeout`(기본 1초)만큼 기다린 뒤 원을 찾아 한쪽을 에러로 끝낸다. 사람이 손댈 일은 원이 아니라 사슬이다.

뿌리를 찾았으면 끊는다. `pg_cancel_backend(pid)`는 지금 돌고 있는 쿼리만 취소하고, `pg_terminate_backend(pid)`는 연결을 끊어 트랜잭션을 롤백한다. `idle in transaction`은 돌고 있는 쿼리가 없으니 cancel로는 안 풀리고 terminate를 써야 한다.

```sql
select pg_terminate_backend(12737);   -- 연결을 끊고 그 트랜잭션을 롤백한다
select count(*) from pg_stat_activity where wait_event_type = 'Lock';   -- 대기가 사라졌는지 확인
```

```text
 pg_terminate_backend
----------------------
 t
(1 row)

 count
-------
     0
(1 row)
```

<Callout kind="warning">
  `pg_terminate_backend`는 그 세션의 커밋 안 된 작업을 전부 버린다. 끊기 전에 application_name, client_addr, xact_start로 누구의 무슨 작업인지 확인하고, 데이터 보정 배치라면 담당자에게 알린다. 운영 OS에서 `kill -9`로 백엔드를 죽이는 건 절대 하지 않는다. 아래 코어 덤프 절에서 보듯 PostgreSQL 전체가 재시작된다.
</Callout>

다시 같은 일이 생기지 않게 하는 설정은 세 가지다. 역할이나 데이터베이스 단위로 거는 게 안전하다.

```sql
-- 트랜잭션을 연 채 60초 넘게 놀면 서버가 연결을 끊는다
alter role app set idle_in_transaction_session_timeout = '60s';
-- 잠금을 5초 넘게 기다리면 기다리던 쪽이 에러로 끝난다(줄이 무한히 길어지지 않게)
alter role app set lock_timeout = '5s';
-- 쿼리 하나가 30초를 넘으면 취소한다
alter role app set statement_timeout = '30s';
```

## 잠금이 없어도 오래 열린 트랜잭션은 해롭다

`idle in transaction`은 잠금을 쥐지 않아도 문제다. 열려 있는 동안 그 트랜잭션이 볼 수 있는 옛 행 버전을 VACUUM이 치우지 못한다. REPEATABLE READ로 스냅샷을 잡고 가만히 있는 세션을 하나 띄운 뒤, 다른 세션에서 10만 행을 고치고 VACUUM을 돌렸다.

```sql
-- 세션 A (application_name = etl-export)
begin isolation level repeatable read;
select count(*) from products;   -- 이때 스냅샷이 잡힌다. 이후 아무것도 안 한다

-- 세션 B
update orders set amount = amount + 1 where id <= 100000;
vacuum (verbose) orders;
```

```text
tuples: 0 removed, 2099985 remain, 100000 are dead but not yet removable
removable cutoff: 798, which was 1 XIDs old when operation ended
```

10만 개의 죽은 행을 하나도 치우지 못했다. 누가 막는지는 `backend_xmin`으로 찾는다.

```sql
-- 스냅샷을 쥐고 있는 세션을 오래된 순으로
select pid, application_name, state, backend_xmin, age(backend_xmin) as xmin_age,
       now() - xact_start as xact_age
from pg_stat_activity
where backend_xmin is not null and pid <> pg_backend_pid()
order by age(backend_xmin) desc;
```

```text
 pid  | application_name |        state        | backend_xmin | xmin_age |    xact_age
------+------------------+---------------------+--------------+----------+-----------------
 4344 | etl-export       | idle in transaction |          798 |        1 | 00:00:02.332935
(1 row)
```

실습이라 2초짜리지만, 운영에서 이 세션이 반나절 열려 있으면 테이블이 부풀고 인덱스 스캔이 느려진다. "어제부터 점점 느려진다"는 제보는 잠금보다 이쪽일 때가 많다. 세션 말고도 오래된 복제 슬롯과 준비된 트랜잭션(2PC)이 같은 일을 한다. 부풀림을 재고 푸는 법은 [VACUUM과 autovacuum 글](/posts/postgres-mvcc-vacuum)에 있다.

## 기다리지 않는데 느리면 누가 시간을 먹었나

대기 이벤트가 대부분 CPU나 IO라면 잠금 문제가 아니다. 이제 쿼리별 누적 시간을 본다. `pg_stat_statements`는 `shared_preload_libraries`에 넣고 재시작해야 켜진다(확장을 만드는 것만으로는 안 된다).

```sql
-- 누적 실행 시간 상위 3개. pct는 전체 실행 시간에서의 비율
select queryid, calls,
       round(total_exec_time::numeric) as total_ms,
       round(mean_exec_time::numeric, 2) as mean_ms,
       round((100 * total_exec_time / sum(total_exec_time) over ())::numeric, 1) as pct,
       shared_blks_hit, shared_blks_read,
       left(query, 50) as query
from pg_stat_statements
where dbid = (select oid from pg_database where datname = 'shop')
order by total_exec_time desc
limit 3;
```

통계를 비우고 pgbench로 20초 동안 "사용자의 최근 주문 20건" 조회 1, 상품 조회 20의 비율로 부하를 줬다.

```text
       queryid        | calls | total_ms | mean_ms |  pct  | shared_blks_hit | shared_blks_read |                       query
----------------------+-------+----------+---------+-------+-----------------+------------------+----------------------------------------------------
  -921493459329523453 |   374 |   157430 |  420.93 | 100.0 |         5466244 |            49493 | select id, amount, created_at from orders where us
 -8095487742831459347 |  7484 |       40 |    0.01 |   0.0 |            7484 |                0 | select name, stock from products where id = $1
  5957856741738317696 |     1 |        2 |    2.01 |   0.0 |               0 |                0 | select pg_stat_statements_reset()
(3 rows)
```

호출 수로는 상품 조회가 20배 많지만, 시간은 주문 조회가 사실상 전부를 먹었다. 한 번에 420ms, 그동안 버퍼를 5백만 번 넘게 건드렸다. 200만 행을 통째로 훑는다는 뜻이다. 순위는 `calls`가 아니라 `total_exec_time`으로 정렬해야 이게 보인다. `mean_exec_time`으로만 보면 하루 한 번 도는 리포트 쿼리가 1등을 차지하고, 정작 초당 수천 번 도는 3ms짜리 쿼리를 놓친다.

PostgreSQL 14부터는 `compute_query_id`가 켜져 있으면 `pg_stat_activity.query_id`와 `pg_stat_statements.queryid`가 같은 값이라, "지금 돌고 있는 이 세션의 쿼리가 누적 순위 몇 등인가"를 조인으로 바로 볼 수 있다.

범인 쿼리의 실행 계획을 읽고 고치는 과정은 [느린 쿼리 찾기 글](/posts/sql-query-tuning)의 몫이라 결과만 적는다. `(user_id, created_at desc)` 인덱스를 운영 중에 만들고 같은 부하를 다시 줬다.

```sql
-- CONCURRENTLY: 쓰기를 막지 않고 인덱스를 만든다(대신 더 오래 걸린다)
create index concurrently orders_user_created_idx on orders(user_id, created_at desc);
```

```text
 calls | mean_ms |                    q
-------+---------+------------------------------------------
  9331 |    0.21 | select id, amount, created_at from order
(1 row)
```

평균 420.93ms가 0.21ms가 됐고, pgbench 전체 처리량은 초당 387건에서 19,795건이 됐다. 여기까지가 대부분의 "DB가 느려요"의 끝이다. 범인은 보통 DB 안에 있다.

## 이미 지나간 일은 로그에 남긴다

연락이 왔을 때는 이미 상황이 끝나 있을 때가 많다. 그때 볼 건 로그뿐이니, 평소에 남겨 둬야 한다. 처음 운영에 올릴 때 이 정도는 켜 둔다.

```ini
# postgresql.conf

log_lock_waits = on                  # deadlock_timeout(기본 1s) 넘게 잠금을 기다리면 남긴다
log_temp_files = 0                   # 정렬·해시가 디스크 임시 파일로 넘치면 크기와 함께 남긴다
log_autovacuum_min_duration = 1s     # 오래 걸린 autovacuum을 남긴다
log_checkpoints = on                 # 16에서는 기본값이 on이다
log_line_prefix = '%m [%p] %q%u@%d '  # 시각, pid, 사용자@DB. 분석기가 이 형식을 알아야 한다
```

`log_lock_waits`가 켜져 있으면 앞의 대기열이 로그에 이렇게 남는다. 누가 쥐고 있었는지까지 적힌다.

## DB가 아니라 서버가 아픈가

쿼리 순위가 평소와 같은데 전부 조금씩 느려졌다면 DB 밖을 의심한다. 같은 서버의 다른 프로세스가 디스크를 독차지하거나, 클라우드 디스크의 IOPS 한도에 걸렸거나, 메모리가 모자라 페이지 캐시가 날아갔을 수 있다. 서버 전체를 훑는 순서는 [리눅스 성능 점검 60초 글](/posts/linux-performance-triage)을 따르고, 여기서는 PostgreSQL 프로세스를 골라 보는 법만 적는다.

PostgreSQL은 연결 하나가 프로세스 하나다. 그리고 프로세스 이름에 상태를 적어 둔다. ps만으로 누가 무엇을 하는지 꽤 보인다.

```bash
# postgres 사용자의 프로세스: 상태, 커널에서 어디서 자는지(wchan), 프로세스 제목
ps -o pid,stat,wchan:16,cmd -u postgres
```

```text
  PID STAT WCHAN            CMD
 4344 Ss   ep_poll          postgres: postgres shop [local] idle in transaction
23872 Ss   ep_poll          /usr/lib/postgresql/16/bin/postgres -D /var/tmp/b25pg/data
23991 Ss   ep_poll          postgres: checkpointer
23993 Ss   ep_poll          postgres: walwriter
```

`postgres: 사용자 DB 주소 상태` 형식이다. 상태가 `idle in transaction`인 걸 OS에서도 볼 수 있다. pg_stat_activity의 pid가 곧 OS pid라서, DB에서 찾은 수상한 pid를 그대로 OS 도구에 넘기면 된다.

CPU를 많이 쓰는 백엔드 하나를 pidstat으로 1초씩 봤다. 주문 200만 건을 8번씩 불려 MD5 1,600만 개의 중복을 세는 리포트 쿼리다.

```bash
sudo apt install -y sysstat                # pidstat, iostat, sar
pidstat -u -d -p 22502 1 3                  # CPU(-u)와 디스크(-d)를 1초 간격 3번
```

```text
Average:      UID       PID    %usr %system  %guest   %wait    %CPU   CPU  Command
Average:      102     22502   95.33    3.67    0.00    0.00   99.00     -  postgres

Average:      UID       PID   kB_rd/s   kB_wr/s kB_ccwr/s iodelay  Command
Average:      102     22502      0.00  31434.67      0.00       0  postgres
```

CPU 하나를 꽉 채운다(99%). PostgreSQL 쿼리 하나는 병렬 쿼리가 아니면 코어 하나만 쓴다는 걸 기억해 두자. 8코어 서버의 CPU 평균이 12%여도 이 쿼리는 한계까지 돌고 있다. 그리고 읽기는 0인데 초당 30MB를 쓴다. 테이블을 읽는 건 페이지 캐시에서 해결되고, 정렬이 `work_mem`을 넘쳐 임시 파일로 쏟아지고 있다는 뜻이다. `log_temp_files`를 켜 두면 로그에서도 같은 사실이 보인다.

디스크를 누가 쓰는지 프로세스별로 보려면 iotop이다. Ubuntu 24.04에는 C로 다시 쓴 iotop-c가 있다.

```bash
sudo apt install -y iotop-c
sudo iotop-c -b -o -P -k -n 2 -d 1   # 배치 모드, I/O 하는 프로세스만, 스레드 대신 프로세스, KB 단위, 1초 간격 2번
```

```text
Warning: task_delayacct is 0, enable by: echo 1 > /proc/sys/kernel/task_delayacct
  Total DISK READ:    0.00 K/s |   Total DISK WRITE: 10212.18 K/s
Current DISK READ:    0.00 K/s | Current DISK WRITE: 80444.01 K/s
   PID PRIO     USER   DISK READ  DISK WRITE SWAPIN     IO COMMAND
 23993 be/4 postgres      0.00 K/s 10058.94 K/s 0.00 % 0.00 % postgres: walwriter
```

큰 테이블을 복사하는 동안이라 walwriter가 WAL을 쏟고 있다. 첫 줄 경고가 중요하다. 커널의 지연 회계(`task_delayacct`)가 꺼져 있으면 IO 열의 "I/O를 기다린 시간 비율"이 늘 0%로 나온다. 얼마나 썼는지만 보이고 얼마나 기다렸는지는 안 보이는 셈이다. 장애 중이라면 `sudo sysctl kernel.task_delayacct=1`로 잠시 켜고, 끝나면 0으로 돌려 둔다.

## 프로세스 하나의 시스템 콜을 본다

DB 안 지표로 설명이 안 되는 프로세스가 하나 남았다면 strace로 커널에 무엇을 부탁하는지 본다. 앞의 대기열에서 잠금을 기다리던 12747과 대기열 맨 앞 12737에 붙어 봤다.

```bash
sudo apt install -y strace
sudo timeout -s INT 3 strace -tt -p 12747 -o /tmp/st.txt   # 3초만 붙었다가 뗀다
cat /tmp/st.txt
```

```text
strace: Process 12747 attached
strace: Process 12747 detached
19:01:15.199087 epoll_wait(10,  <detached ...>
```

3초 동안 시스템 콜이 하나도 끝나지 않았다. `epoll_wait`에서 계속 잔다. 12737도 똑같이 `epoll_wait`에 있었다. 기다리는 백엔드는 OS에서 보면 다 비슷하게 잔다. 잠금 대기인지 클라이언트 대기인지는 OS가 모른다. 대기 이유는 DB가 안다. 그래서 순서가 위에서 아래인 것이다.

strace가 쓸모 있는 건 열심히 일하는 프로세스다. `-c`로 시스템 콜을 세면 무엇에 시간을 쓰는지 보인다. pgbench가 붙은 백엔드 하나를 4초 동안 셌다.

```bash
sudo timeout -s INT 4 strace -c -f -p 25883 -o /tmp/st3.txt   # 호출 횟수와 시간 요약
```

```text
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 32.91    0.002848           1      2421           lseek
 23.52    0.002036           2       808           sendto
 15.55    0.001346           1      1045       238 recvfrom
 11.60    0.001004           2       375        53 epoll_wait
  3.35    0.000290          10        28           fallocate
  3.05    0.000264           2       109           kill
  2.61    0.000226           8        28           openat
```

`recvfrom`과 `sendto`는 클라이언트와 주고받는 프로토콜이고, `lseek`이 많은 건 테이블 파일 크기를 확인하느라 파일 끝으로 이동하는 동작이다. `fallocate`, `openat`이 28번씩인 건 정렬용 임시 파일을 만들고 늘리는 흔적이다. 다만 여기 찍힌 시간은 커널 안에서 쓴 시간뿐이라 0.01초도 안 된다. 4초 대부분은 사용자 공간 계산이었다는 뜻이고, 그건 strace가 아니라 perf의 일이다.

운영에서 strace를 붙일 때는 조심한다. ptrace 방식이라 시스템 콜마다 프로세스를 멈췄다 풀어서, 시스템 콜이 많은 프로세스는 몇 배 느려진다. 짧게 붙고, `timeout`으로 반드시 떨어지게 하고, 이미 장애인 프로세스에만 쓴다.

## CPU를 어디에 쓰는지 본다

perf는 초당 수십~수천 번 "지금 어느 함수에 있나"를 샘플링한다. 프로세스를 멈추지 않아 strace보다 훨씬 가볍다. MD5 리포트 쿼리 백엔드를 5초 동안 초당 99번 샘플링했다.

```bash
# Ubuntu는 커널 버전에 맞는 linux-tools 패키지가 perf를 제공한다
sudo apt install -y linux-tools-$(uname -r) || sudo apt install -y linux-tools-generic
sudo perf record -F 99 -p 22502 -o /tmp/perf.data -- sleep 5
sudo perf report -i /tmp/perf.data --stdio --sort dso,symbol | grep -v '^#' | head
```

```text
     1.54%  postgres           [.] pg_md5_hash
```

문자열 비교(`memcmp`, `strcmp`)는 `count(distinct ...)`의 정렬, `libcrypto`와 `pg_md5_hash`는 md5() 계산이다. 쿼리가 하는 일과 맞아떨어진다. 그런데 1등이 `0x66360e` 같은 주소다. 배포판 바이너리에서 심볼 정보가 빠져 있어서다. 함수 이름까지 보려면 디버그 심볼 패키지(`postgresql-16-dbgsym`, Ubuntu의 ddebs 저장소)를 깔거나 debuginfod를 쓴다. 장애가 터진 다음에 깔려고 하면 늦으니, 운영 서버 이미지에 미리 넣어 두는 게 좋다.

내 실습 VM에서는 `/usr/bin/perf`가 커널 이름과 맞는 linux-tools 패키지를 못 찾아 경고만 내고 끝났고, `/usr/lib/linux-tools/6.8.0-147-generic/perf`를 직접 불러서 돌렸다. 클라우드 전용 커널에서 자주 겪는 일이다. 결과를 그림으로 펼치는 플레임 그래프는 [Node.js 디버깅과 프로파일링 글](/posts/nodejs-debugging-profiling)에서 읽는 법을 다뤘다.

## 기다린 시간을 커널에서 잰다: eBPF

perf는 CPU 위에 있는 시간을 본다. 반대로 CPU에서 내려와 무언가를 기다린 시간(off-CPU)이나, 디스크 요청 하나하나의 지연 분포는 eBPF 도구가 잘 본다. 커널 안에 작은 프로그램을 넣어 이벤트마다 값을 맵에 쌓고, 사용자 공간은 요약만 가져가니 strace처럼 프로세스를 멈추지 않는다. eBPF 자체의 구조는 [Cilium과 eBPF 글](/posts/cilium-ebpf)에 있다. DB 장애에서 자주 쓰는 건 BCC 도구 두 개다.

```bash
sudo apt install -y bpfcc-tools           # Ubuntu에서는 이름 끝에 -bpfcc가 붙는다
sudo biolatency-bpfcc -D 10 1             # 디스크별 블록 I/O 지연 히스토그램, 10초 동안 한 번
sudo offcputime-bpfcc -p 22502 10         # 그 pid가 CPU에서 내려가 기다린 시간을 스택별로 10초
```

biolatency는 지연을 2의 거듭제곱 구간(0~1us, 2~3us, … 1024~2047us)으로 나눠 막대로 그린다. 평균만 보는 `iostat`의 `await`와 달리 "대부분 0.1ms인데 일부가 50ms"인 두 봉우리 분포가 드러나서, 클라우드 디스크의 버스트 크레딧이 바닥났거나 같은 호스트의 이웃이 디스크를 두드리는 경우를 잡아낸다. offcputime은 기다린 시간을 커널·사용자 스택과 함께 모아, 그 프로세스가 `fsync`에서 기다렸는지 `futex`에서 기다렸는지를 보여 준다.

솔직히 적으면, 이 글의 실습 VM은 tracefs가 없어 트레이스포인트를 붙일 수 없었고 bpftrace도 `tracepoint not found`로 멈췄다. 컨테이너나 가벼운 가상 머신, 관리형 DB에서는 이런 일이 흔하다. RDS나 Cloud SQL이라면 OS에 들어갈 수 없으니 이 층은 Enhanced Monitoring 같은 제공 지표로 대신한다. eBPF는 직접 운영하는 서버에서, 미리 돌아가는 걸 확인해 둔 경우에만 장애 도구로 믿을 수 있다.

## 백엔드가 죽었을 때 증거를 남긴다

드물지만 백엔드 프로세스가 죽는 일이 있다. 확장 모듈의 버그, 메모리 손상, 드라이버 문제 같은 경우다. 이때 PostgreSQL이 하는 일을 직접 보려고, 연결 두 개를 띄우고 하나에 SIGSEGV를 보냈다.

```bash
# 코어 파일을 허용하고 서버를 다시 띄운다(pg_ctl -c는 ulimit -c unlimited와 같다)
sudo -u postgres /usr/lib/postgresql/16/bin/pg_ctl -D /var/tmp/b25pg/data -c restart -m fast
cat /proc/$(sudo head -1 /var/tmp/b25pg/data/postmaster.pid)/limits | grep -i core
```

```text
Max core file size        unlimited            unlimited            bytes
```

죽은 백엔드에 붙어 있던 쪽은 연결이 끊기고, 아무 상관 없던 다른 세션도 같이 끊긴다.

```text
WARNING:  terminating connection because of crash of another server process
DETAIL:  The postmaster has commanded this server process to roll back the current transaction and exit, because another server process exited abnormally and possibly corrupted shared memory.
HINT:  In a moment you should be able to reconnect to the database and repeat your command.
server closed the connection unexpectedly
```

서버 로그에는 순서대로 남는다.

```text

2026-10-23 19:05:21.695 UTC [23872] LOG:  terminating any other active server processes
2026-10-23 19:05:21.701 UTC [23872] LOG:  all server processes terminated; reinitializing
2026-10-23 19:05:22.001 UTC [23990] LOG:  database system was not properly shut down; automatic recovery in progress
2026-10-23 19:05:22.002 UTC [23990] LOG:  redo is not required
2026-10-23 19:05:22.013 UTC [23872] LOG:  database system is ready to accept connections
```

백엔드 하나가 비정상 종료하면 공유 메모리가 망가졌을 수 있다고 보고, postmaster가 모든 연결을 끊은 뒤 WAL로 복구하고 다시 받는다. 그래서 "가끔 모든 연결이 한꺼번에 끊긴다"는 증상은 백엔드 크래시를 먼저 의심한다. `kill -9`로 백엔드를 죽여도 똑같은 일이 일어난다. 앞의 경고에서 kill -9를 하지 말라고 한 이유다.

코어 파일은 `core_pattern` 설정에 따라 다른 곳에 생긴다. 이 VM은 값이 `core`라 백엔드의 작업 디렉터리인 데이터 디렉터리에 156MB짜리 `core`가 생겼다. 보통 Ubuntu 서버는 apport나 systemd-coredump가 가로채니 `cat /proc/sys/kernel/core_pattern`으로 먼저 확인하고, systemd-coredump라면 `coredumpctl list`로 찾는다. 서비스로 띄운 PostgreSQL은 유닛 파일에 `LimitCORE=infinity`가 있어야 코어가 남는다.

gdb로 코어에서 죽은 순간의 스택을 꺼낸다.

```bash
sudo apt install -y gdb
sudo gdb -batch -ex bt /usr/lib/postgresql/16/bin/postgres /var/tmp/b25pg/data/core
```


## 처음 연락이 왔을 때로 돌아가면

순서를 다시 적으면 이렇다. 먼저 `pg_stat_activity`를 상태와 대기 이벤트로 묶어 센다. Lock이 보이면 `pg_blocking_pids`로 사슬을 따라가 맨 앞을 찾는다. 대부분 CPU나 IO면 `pg_stat_statements`를 누적 시간순으로 본다. 이미 끝난 일이면 로그와 pgBadger를 본다. 쿼리 순위가 평소와 같으면 OS로 내려가 PostgreSQL pid를 골라 보고, 그래도 설명이 안 되는 프로세스 하나만 strace, perf, gdb로 들여다본다.

장애 중에 자주 하는 실수도 이 순서를 어긴 데서 나온다. 재시작부터 하면 `pg_stat_activity`도, 잠금 사슬도 사라져 다음에 또 같은 일을 겪는다. 사슬의 중간을 끊으면 다음 대기자가 그 자리를 채울 뿐이다. 서버 CPU 평균만 보고 DB가 한가하다고 판단하면 코어 하나를 꽉 채운 쿼리를 놓친다. `pg_stat_statements`를 평소에 한 번도 안 봤다면 무엇이 이상한지 비교할 기준이 없다. 그리고 바쁜 운영 백엔드에 strace를 오래 붙여 두면 장애를 키운다.

맨 처음의 "DB가 느려요"는 결국 이 순서의 두 번째 칸에서 끝났다. 재고를 고친 관리 배치가 커밋하지 않은 채 39초 동안 서 있었고, 그 뒤로 주문 요청이 줄을 섰다. 대기열의 뿌리를 끊고 `idle_in_transaction_session_timeout`을 걸면서 마무리했다.

## 면접에서 나올 만한 질문

### DB가 느리다는 연락을 받으면 무엇부터 보나요?

`pg_stat_activity`를 상태와 `wait_event_type`으로 묶어 센다. 이것만으로 DB가 일을 하느라 느린지(CPU, IO), 뭔가를 기다리느라 느린지(Lock, Client) 갈린다. 기다리는 거라면 잠금 사슬을, 일하는 거라면 `pg_stat_statements`의 누적 시간 순위를 본다. OS 도구는 그다음이다.

### 서버 CPU가 한가한데 쿼리가 느린 건 어떤 경우인가요?

대부분 잠금을 기다리는 경우다. 커밋하지 않은 `idle in transaction` 세션이 행 잠금을 쥐고 있으면 뒤의 UPDATE들이 `Lock` 대기로 서고 CPU는 놀게 된다. 또 쿼리 하나는 병렬이 아니면 코어 하나만 쓰므로, 8코어 평균 12%여도 그 쿼리의 코어는 100%일 수 있다. 그래서 서버 평균이 아니라 세션별 대기 이벤트와 프로세스별 CPU를 본다.

### 잠금 대기가 길게 늘어섰을 때 어떤 세션을 끊나요?

다른 세션을 막고 있지만 자기는 아무도 기다리지 않는 세션, 사슬의 맨 앞을 끊는다. `pg_blocking_pids`가 바로 앞의 세션만 알려 주므로 중간의 피해자를 끊는 실수가 흔하다. 맨 앞이 `idle in transaction`이면 실행 중인 쿼리가 없어 `pg_cancel_backend`로는 안 풀리고 `pg_terminate_backend`를 써야 하며, 그 트랜잭션은 롤백된다는 걸 알고 끊는다.

### 오래 열린 트랜잭션은 잠금을 안 쥐어도 왜 문제인가요?

그 트랜잭션의 스냅샷이 볼 수 있는 옛 행 버전을 VACUUM이 지우지 못하기 때문이다. 실습에서 REPEATABLE READ 세션 하나가 열려 있는 동안 10만 개의 죽은 행이 "dead but not yet removable"로 남았다. 오래 두면 테이블과 인덱스가 부풀어 전체가 서서히 느려진다. `backend_xmin` 나이로 범인을 찾고, `idle_in_transaction_session_timeout`으로 막는다.

### pg_stat_statements에서 무엇을 기준으로 정렬하나요?

`total_exec_time`이다. 서버가 실제로 쓴 시간의 비중이 보이기 때문이다. `mean_exec_time`으로 보면 가끔 도는 무거운 리포트가 위로 오고, 초당 수천 번 도는 짧은 쿼리를 놓친다. 평소에 한 번씩 스냅샷을 떠 두거나 리셋 시점을 기록해 둬야 장애 때 무엇이 늘었는지 비교할 수 있다.

### strace, perf, eBPF는 각각 언제 쓰나요?

strace는 프로세스가 커널에 무엇을 부탁하는지(파일, 소켓, 잠자기)를 보고, ptrace라 대상을 크게 느리게 하니 짧게만 붙인다. perf는 CPU 위에서 어느 함수에 시간을 쓰는지 샘플링하고 부담이 작다. eBPF 도구는 디스크 지연 분포나 CPU에서 내려와 기다린 시간처럼 커널 이벤트를 맵에 모아 요약하므로 운영에서도 비교적 안전하다. 셋 모두 DB 안의 대기 이벤트로 설명이 안 될 때 꺼낸다.

### 백엔드 하나가 죽었는데 왜 모든 연결이 끊기나요?

모든 백엔드가 공유 메모리를 함께 쓰기 때문이다. 하나가 비정상 종료하면 공유 메모리가 망가졌을 수 있으니 postmaster가 전부 끊고, 메모리를 다시 만들고, WAL로 복구한 뒤 연결을 다시 받는다. `kill -9`로 백엔드를 죽여도 같은 일이 생긴다. 원인을 찾으려면 `core_pattern`과 코어 크기 제한을 미리 설정해 코어를 남기고, gdb로 백트레이스를 뽑아 서버 로그와 함께 본다.

### 운영 서버에 미리 준비해 둘 것은 무엇인가요?

`pg_stat_statements`, `log_min_duration_statement`, `log_lock_waits`, `log_temp_files`, `log_line_prefix`처럼 사후에 볼 기록을 먼저 켠다. 역할별로 `idle_in_transaction_session_timeout`, `lock_timeout`, `statement_timeout`을 건다. OS 쪽은 sysstat, 디버그 심볼, 커널에 맞는 perf, 코어 덤프 위치를 미리 확인해 둔다. 장애가 난 뒤 설치하려 하면 늦고, 그사이 증거가 사라진다.
