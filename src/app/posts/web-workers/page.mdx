CSV 파일 하나를 올리면 표로 보여 주는 화면을 만들었다. 10만 줄짜리 파일을 넣고 "가격순 정렬"을 누르자 화면이 1초 가까이 얼어붙는다. 스피너도 멈추고, 그 사이 누른 탭 버튼은 정렬이 끝난 뒤에야 반응한다. 개발자 도구의 Performance 패널에는 빨간 빗금이 친 긴 작업 하나가 보인다.

비슷한 상황을 직접 만들어 재 봤다. 숫자 100만 개를 비교 함수로 정렬하면서 그동안 `requestAnimationFrame`이 몇 번 불리는지 셌다. 이 글의 측정은 모두 4코어 리눅스 컨테이너의 헤드리스 크로미움 141에서 했고, 절대값은 기기마다 다르니 비율만 본다.


## 메인 스레드가 혼자 하는 일

브라우저 탭 하나의 메인 스레드는 생각보다 많은 일을 한다. 자바스크립트 실행, 스타일 계산, 레이아웃, 페인트 기록, 클릭과 키 입력 처리가 모두 이 한 줄에서 차례로 돈다. 자바스크립트가 781ms 동안 놓아 주지 않으면 그 뒤에 줄 선 입력 처리와 렌더링은 기다릴 수밖에 없다.

브라우저는 50ms를 넘는 작업을 긴 작업(long task)이라고 부른다. 사용자가 버튼을 눌렀을 때 100ms 안에 반응이 보이려면, 입력이 들어온 순간 메인 스레드가 길게 잡혀 있으면 안 되기 때문이다. 상호작용부터 다음 화면까지 걸린 시간을 재는 지표가 INP이고, 긴 작업은 INP를 망치는 가장 흔한 원인이다. INP를 세 구간으로 나눠 보는 법은 [Core Web Vitals](/posts/core-web-vitals)에, 태스크와 렌더링이 끼어드는 순서는 [이벤트 루프](/posts/event-loop)에 있다.

긴 작업을 줄이는 길은 두 가지다. 작업을 잘게 쪼개 사이사이 메인 스레드를 내주거나, 작업을 아예 다른 스레드로 보내는 것이다. 이 글은 두 번째를 다룬다. 쪼개기는 끝에서 다시 비교한다.

## 워커는 자기 이벤트 루프를 가진 다른 스레드다

Web Worker는 페이지와 다른 스레드에서 자기 전역 객체와 이벤트 루프를 가지고 도는 자바스크립트 실행 환경이다. 메인 스레드와는 메모리를 나누지 않고 메시지로만 대화한다.

```ts
// sort.worker.ts
self.onmessage = (event: MessageEvent<number[]>) => {
  const sorted = event.data.slice().sort((a, b) => a - b);
  self.postMessage(sorted);
};
```

```ts
// 메인 스레드
const worker = new Worker(new URL("./sort.worker.ts", import.meta.url), { type: "module" });

worker.onmessage = (event: MessageEvent<number[]>) => renderTable(event.data);
worker.onerror = (event) => console.error("워커 오류", event.message);

worker.postMessage(prices); // 보내고 바로 다음 줄로 간다
```

앞의 정렬을 워커로 옮기고 같은 방법으로 쟀다.

```text
main:        { ms: 781, frames: 1 }
workerArray: { ms: 769, postMessageBlocked: 16, frames: 47 }
```

전체 시간은 거의 같다. 정렬이 빨라진 것이 아니다. 차이는 그동안 화면이 47번 그려졌다는 것이다. 메인 스레드는 `postMessage`를 부르는 16ms만 잡혀 있고, 나머지 시간에는 스피너를 돌리고 클릭을 받는다. 워커는 일을 빨리 끝내 주는 도구가 아니라 메인 스레드를 비워 두는 도구다.

전용 워커(Dedicated Worker)는 `new Worker()`로 만든 그 페이지에만 속한다. 페이지가 닫히면 같이 사라진다. 계산을 덜어 내는 용도는 거의 이것이다.

공유 워커(`SharedWorker`)는 같은 출처의 여러 탭과 iframe이 하나를 함께 쓴다. 각 페이지는 `worker.port`로 따로 연결되고, 워커는 `onconnect`에서 포트를 받아 관리한다. 탭마다 웹소켓을 하나씩 여는 대신 공유 워커 하나가 연결을 들고 탭들에 나눠 주는 식으로 쓴다. 다만 지원 범위가 고르지 않다. 안드로이드 크롬은 오랫동안 지원하지 않았으니 모바일이 주 사용 환경이면 쓰기 전에 지원 표를 확인하고, 없을 때 돌아갈 길(탭마다 연결, 또는 `BroadcastChannel`로 대표 탭 정하기)을 같이 만든다.

서비스 워커(Service Worker)는 성격이 다르다. 페이지가 아니라 출처와 범위(scope)에 등록되고, 페이지의 네트워크 요청을 가로채는 프록시로 동작한다. 탭이 모두 닫혀도 푸시 알림이나 백그라운드 동기화 때 깨어날 수 있고, 할 일이 없으면 브라우저가 언제든 멈춘다. 그래서 계산을 맡기거나 상태를 메모리에 오래 들고 있는 용도로는 맞지 않는다. 캐시와 오프라인 동작은 [프런트엔드 캐시](/posts/frontend-browser-cache)에서 다룬다.

## 워커 안에 없는 것

워커 안에서 쓸 수 있는 전역을 찍어 봤다.

```text
document: 'undefined',
window: 'undefined',
fetch: 'function',
indexedDB: 'object',
OffscreenCanvas: 'function',
localStorage: 'undefined',
WebSocket: 'function',
schedulerYield: 'function',
name: 'calc'
```

`document`와 `window`가 없다. DOM은 메인 스레드 전용이다. 브라우저의 DOM 구현은 여러 스레드가 동시에 고치는 상황을 전제로 만들어지지 않았고, 워커는 그 대가로 잠금 없이 안전하게 돈다. `localStorage`도 없다. 동기 API라 다른 스레드에서 열면 서로 기다리는 문제가 생기기 때문이다. 저장이 필요하면 비동기인 IndexedDB를 쓴다.

대신 `fetch`, `WebSocket`, IndexedDB, 타이머, `crypto.subtle`, `OffscreenCanvas`가 있다. 전역 객체 이름은 `self`(전용 워커에서는 `DedicatedWorkerGlobalScope`)다. `new Worker(url, { name: "calc" })`로 준 이름이 `self.name`에 들어가고, 개발자 도구의 스레드 목록에도 이 이름으로 보여 여러 워커를 구분할 때 쓸모 있다.

라이브러리를 워커에서 쓸 때 걸리는 지점이 여기다. 내부에서 `window`나 `document`를 확인 없이 건드리는 라이브러리는 워커에서 불러오는 순간 `ReferenceError`가 난다. 차트 라이브러리, 날짜 라이브러리의 로케일 감지 코드가 그런 경우가 있다. 워커로 옮길 코드는 DOM 없이 도는 순수 계산으로 잘라 낸다.

## 메시지는 복사된다

`postMessage`로 보낸 값은 참조가 아니라 복사본이 건너간다. 복사 방식은 구조화된 복제(structured clone) 알고리즘이고, JSON보다 많은 것을 담는다. `Date`, `Map`, `Set`, 정규식, `ArrayBuffer`와 타입 배열, 순환 참조가 그대로 간다. 대신 담지 못하는 것도 있다.

```text
cloneFn: "DataCloneError: Failed to execute 'postMessage' on 'Worker': () => 1 could not be cloned.",
classClone: { x: 1, isPoint: false, len: 'undefined' }
```

함수는 보낼 수 없다. 콜백을 넘겨 "끝나면 이걸 불러 줘"라고 할 수 없다는 뜻이다. 클래스 인스턴스는 보내지긴 하지만 필드만 남은 평범한 객체가 된다. `Point` 인스턴스를 복제하자 `x`는 남았는데 `instanceof Point`는 `false`, 메서드 `len`은 사라졌다. 워커에서 받은 값으로 `point.len()`을 부르면 `TypeError`가 난다. 메시지에는 데이터만 담고, 받는 쪽에서 필요하면 다시 클래스로 감싼다. 복제 규칙 자체는 [얕은 복사와 깊은 복사](/posts/js-shallow-deep-copy)에서 더 자세히 본다.

복사는 공짜가 아니다. 앞의 측정에서 100만 개 배열을 보낼 때 메인 스레드가 16ms 잡혔다. 보내는 쪽의 직렬화가 동기로 돌기 때문이다. 크기가 클수록 이 값이 커져서, 수십 MB 객체를 자주 오가면 워커로 옮긴 의미가 사라진다. 그 자리에서 다시 긴 작업이 생긴다. 숫자 덩어리라면 아래처럼 복사 자체를 없앤다.

## 큰 버퍼는 복사하지 않고 넘긴다

`ArrayBuffer`, `MessagePort`, `ImageBitmap`, `OffscreenCanvas` 같은 객체는 복사 대신 소유권을 넘길 수 있다. `postMessage`의 두 번째 인자로 넘길 목록을 주면, 메모리를 복사하지 않고 받는 쪽으로 옮긴 뒤 보낸 쪽의 버퍼는 비운다.

```ts
const buffer = new ArrayBuffer(64 * 1024 * 1024);
worker.postMessage({ buffer }, [buffer]); // 두 번째 인자: 넘길 목록
console.log(buffer.byteLength);           // 0, 이제 내 것이 아니다
```

8MB와 64MB 버퍼를 복사로 한 번, 넘기기로 한 번 보내서 워커가 답할 때까지 걸린 시간을 쟀다.

```text
clone8:     { ms: 15.8,  after: 8388608 },
transfer8:  { ms: 3.4,   after: 0 },
clone64:    { ms: 115.1, after: 67108864 },
transfer64: { ms: 2.2,   after: 0 }
```

복사는 크기에 비례해 64MB에서 115ms가 걸렸고, 넘기기는 크기와 상관없이 몇 ms다. 넘긴 뒤 보낸 쪽의 `byteLength`는 0이 된다. 버퍼가 떨어져 나간(detached) 상태라서, 그 위의 타입 배열을 읽으면 아무것도 없다. 넘긴 버퍼를 메인 스레드에서 계속 쓰려는 코드가 여기서 조용히 틀린 값을 낸다. 둘 다 계속 써야 하면 복사하거나, 아래의 공유 메모리를 쓴다.

정렬 예제를 일반 배열 대신 `Float64Array`로 바꾸고, 보낼 때와 돌려받을 때 모두 버퍼를 넘겼다.

```ts
const typed = Float64Array.from(prices);
worker.postMessage({ arr: typed }, [typed.buffer]);
// 워커: a.sort(); postMessage({ arr: a }, [a.buffer]);
```

```text
workerTyped: { ms: 138, postMessageBlocked: 0.2, inside: 137, frames: 9, sentLenAfter: 0, backLen: 1000000 }
```

메인 스레드가 잡힌 시간이 16ms에서 0.2ms로 줄었다. 전체 시간도 769ms에서 138ms로 줄었는데, 이건 넘기기 덕분만은 아니다. 타입 배열의 `sort()`는 비교 함수 없이 숫자를 직접 비교하는 내장 정렬이라 일반 배열에 비교 함수를 준 정렬보다 훨씬 빠르다. 두 효과가 겹친 숫자다. 워커와 주고받을 데이터를 처음부터 타입 배열 같은 평평한 버퍼로 설계하면, 복사 비용과 계산 비용을 함께 줄인다.

## 같은 메모리를 함께 보는 SharedArrayBuffer

넘기기는 한쪽만 쓸 수 있다. 메인 스레드와 워커, 또는 워커 여러 개가 같은 메모리를 동시에 보려면 `SharedArrayBuffer`를 쓴다. 이 버퍼를 `postMessage`로 보내면 복사도 이동도 아니고, 양쪽이 같은 메모리를 가리키게 된다.

그런데 평범한 페이지에서는 이 생성자가 아예 없다.

```text
plain { coi: false, sab: 'undefined' }
iso   { coi: true,  sab: 'function' }
```

`SharedArrayBuffer`는 페이지가 교차 출처 격리(cross-origin isolated) 상태일 때만 생긴다. 문서에 `Cross-Origin-Opener-Policy: same-origin`과 `Cross-Origin-Embedder-Policy: require-corp`(또는 `credentialless`)를 함께 보내야 한다. 공유 메모리가 있으면 워커 하나가 카운터를 계속 올리는 것만으로 아주 정밀한 타이머를 만들 수 있고, 그 타이머가 스펙터 같은 CPU 부채널 공격의 재료가 되기 때문이다. 그래서 다른 출처 자원이 동의 없이 섞이지 않은 페이지에만 허락한다. 두 헤더를 켰을 때 무엇이 깨지는지는 [웹 보안 헤더](/posts/web-security-headers)에서 직접 걸어 본다.

공유 메모리를 쓰면 동시성 문제가 바로 따라온다. 워커 네 개가 같은 `Int32Array`의 0번 칸을 각자 100만 번씩 올렸다. 한 번은 `v[0]++`로, 한 번은 `Atomics.add(v, 0, 1)`로.

```text
{ plain: 3889816, atomics: 4000000 }
```

`v[0]++`는 400만이 되어야 할 값이 3,889,816에서 멈췄다. 읽기, 더하기, 쓰기가 한 동작이 아니어서, 두 워커가 같은 값을 읽고 각자 1을 더해 쓰면 한 번이 사라진다. `Atomics.add`는 이 세 단계를 끊김 없이 한 번에 해서 정확히 400만이 됐다. 다른 언어의 스레드와 똑같은 문제고, 원리는 [스레드 안전성](/posts/thread-safety)에서 다룬다.

`Atomics.wait`로 값이 바뀔 때까지 스레드를 재울 수도 있는데, 메인 스레드에서는 막혀 있다.

```text
waitMain: 'TypeError: Atomics.wait cannot be called in this context'
```

메인 스레드를 재우면 화면이 멈추니 브라우저가 처음부터 금지한다. 워커 안에서만 쓰고, 메인 스레드에서는 Promise를 돌려주는 `Atomics.waitAsync`를 쓴다(지원 범위는 확인하고 쓴다). 실무에서 `SharedArrayBuffer`를 직접 다루는 경우는 대개 WebAssembly 스레드(영상·이미지 처리, ffmpeg.wasm 같은 것)다. 평범한 웹앱이라면 넘기기로 충분한 경우가 많고, 격리 헤더 때문에 외부 이미지와 임베드가 깨지는 비용도 크다.

## postMessage를 함수 호출처럼 감싸기

메시지를 몇 종류만 주고받을 때는 `onmessage` 안에서 `switch`로 갈라도 된다. 종류가 늘고 동시에 여러 요청이 오가면 문제가 생긴다. 정렬 요청 두 개를 연달아 보냈는데 답이 거꾸로 오면 어떤 답이 어떤 요청 것인지 모른다. 그래서 요청마다 번호를 붙이고, 답에도 그 번호를 실어 짝을 맞추는 RPC 층을 만든다.

```ts
// 쓰는 쪽은 이렇게 되기를 바란다
const sorted = await sortWorker.sort(prices);
const stats = await sortWorker.summarize(prices);
```

[Comlink](https://github.com/GoogleChromeLabs/comlink)가 이 일을 하는 작은 라이브러리다. 워커에서 `expose(api)`, 메인에서 `wrap(worker)`를 부르면 워커의 함수를 `await`로 부를 수 있다. 내부적으로는 Proxy로 메서드 호출을 가로채 메시지로 바꾸고, 번호로 답을 찾아 Promise를 풀어 준다. 편하지만 숨는 것도 있다. 호출마다 인자가 복사되니 큰 배열은 `Comlink.transfer(value, [value.buffer])`로 넘기기를 명시해야 하고, 함수를 인자로 넘기려면 `Comlink.proxy`로 감싸야 한다. 그냥 넘기면 앞에서 본 `DataCloneError`가 난다.

짝 맞추기 자체는 몇 줄이면 된다. 아래에서 직접 만들어 보자. `call`은 번호를 붙여 보내고 콜백을 기억해 둔다. `receive`는 답의 번호로 콜백을 찾아 한 번만 부르고 지운다. 모르는 번호나 이미 처리한 번호는 무시한다. 이 플레이그라운드도 Web Worker 안에서 돈다. 페이지와 다른 스레드라서 무한 루프를 짜도 화면이 멈추지 않고, 2초가 지나면 워커째 `terminate()`된다.

## 캔버스를 통째로 워커에 넘기기

그리기는 DOM이 필요하니 워커가 못 할 것 같지만, 캔버스는 예외가 있다. `canvas.transferControlToOffscreen()`으로 화면의 캔버스 제어권을 `OffscreenCanvas`로 바꿔 워커에 넘기면, 워커가 그린 결과가 화면 캔버스에 바로 나타난다.

```ts
// 메인 스레드
const offscreen = canvasRef.current!.transferControlToOffscreen();
worker.postMessage({ canvas: offscreen }, [offscreen]); // 넘길 목록에 넣는다

// 워커
self.onmessage = ({ data }) => {
  const ctx = (data.canvas as OffscreenCanvas).getContext("2d")!;
  const draw = (t: number) => {
    drawChart(ctx, t);           // 무거운 그리기도 메인 스레드와 상관없다
    requestAnimationFrame(draw); // 전용 워커에도 있다(지원 브라우저 확인)
  };
  requestAnimationFrame(draw);
};
```

데이터 점이 수만 개인 차트, 지도 타일, 게임 루프처럼 그리기 자체가 무거운 화면에서 쓴다. 메인 스레드가 React 렌더링으로 바쁜 순간에도 애니메이션이 끊기지 않는다. 지원은 크롬 계열이 가장 먼저였고 파이어폭스와 사파리는 나중에 들어왔다. 사파리에서 WebGL 컨텍스트까지 되는지는 버전을 확인하고, 없으면 메인 스레드에서 그리는 길로 돌아가게 기능 확인(`"transferControlToOffscreen" in HTMLCanvasElement.prototype`)을 둔다. 한 번 넘긴 캔버스는 메인 스레드에서 `getContext`를 부를 수 없다.

## 번들러가 워커 파일을 알아보게 하기

워커는 별도 파일로 불러와야 한다. 예전에는 워커 코드를 `public` 폴더에 두고 `new Worker("/sort.worker.js")`로 불렀는데, 그러면 TypeScript 변환도, `import`한 라이브러리 묶기도, 배포 해시도 직접 챙겨야 한다. 지금은 이 모양을 쓴다.

```ts
const worker = new Worker(new URL("./sort.worker.ts", import.meta.url), { type: "module" });
```

`new URL(상대 경로, import.meta.url)`은 "이 파일 기준으로 그 파일의 주소"라는 표준 자바스크립트다. Vite와 webpack 5는 이 모양을 보면 워커 파일을 별도 청크로 빌드하고, 해시가 붙은 최종 주소로 바꿔 준다. 경로를 변수로 만들면 번들러가 정적으로 알아보지 못하니 이 모양 그대로 쓴다.

`{ type: "module" }`은 워커 안에서 `import` 문을 쓰게 해 준다. 이걸 빼면 클래식 워커라 `importScripts()`만 쓸 수 있다. 모듈 워커는 크롬 계열이 먼저 지원했고 파이어폭스는 114부터 지원한다. 오래된 브라우저까지 받아야 한다면 번들러가 클래식 워커로 빌드하게 설정한다.

다른 방법도 있다. 이 블로그의 코드 실행 상자(위의 플레이그라운드)는 워커 코드를 문자열로 들고 있다가 `Blob`으로 만들고 `URL.createObjectURL`로 주소를 얻어 `new Worker`에 넘긴다. 파일 하나 없이 워커를 만들 수 있지만, CSP를 쓴다면 `worker-src blob:`을 허용해야 하고(`worker-src`가 없으면 `child-src`, `script-src` 순으로 따른다) 워커 코드 안에서 `import`를 쓰기 어렵다. 작은 격리 실행기에 맞는 방법이다.

React에서는 컴포넌트가 사라질 때 워커를 꼭 닫는다.

```tsx
useEffect(() => {
  const worker = new Worker(new URL("./sort.worker.ts", import.meta.url), { type: "module" });
  workerRef.current = worker;
  return () => worker.terminate(); // 안 하면 화면을 오갈 때마다 워커가 쌓인다
}, []);
```

개발 모드의 StrictMode는 effect를 두 번 실행하므로, 정리 함수가 없으면 개발 중에 워커가 두 개씩 생기는 것으로 금방 드러난다. 워커 하나는 자기 스레드와 자바스크립트 힙을 따로 가진다. 화면을 오갈 때마다 하나씩 새면 메모리가 수십 MB씩 늘어난다.

## 워커가 답이 아닐 때

워커에는 고정 비용이 있다. 이 환경에서 워커를 새로 만들어 첫 메시지를 받기까지 8~13ms가 걸렸다. 이미 떠 있는 워커와 작은 메시지를 주고받는 데는 0.1~0.3ms였다.

```text
startup: [ 9.4, 12.5, 9.3, 9.6, 7.6 ]
smallRoundTrip: [ 0.3, 0.1, 0.1, 0, 0 ]
```

그래서 버튼 클릭마다 워커를 새로 만들지 않고 한 번 띄워 재사용한다. 작업이 많으면 `navigator.hardwareConcurrency`를 참고해 워커 몇 개를 풀(pool)로 돌리되, 모바일 기기는 코어가 적고 메모리도 빠듯하니 코어 수만큼 다 띄우지 않는다.

워커로 덜어 낼 수 없는 일도 있다. 긴 작업이 DOM 조작이나 React 렌더링 자체라면 워커는 도움이 안 된다. 그때는 작업을 잘게 쪼개 메인 스레드를 중간중간 내준다.

```ts
async function processInChunks<T>(items: T[], work: (item: T) => void) {
  let last = performance.now();
  for (const item of items) {
    work(item);
    if (performance.now() - last > 40) {   // 50ms 전에 한 번씩 양보한다
      await (globalThis.scheduler?.yield?.() ?? new Promise((r) => setTimeout(r, 0)));
      last = performance.now();
    }
  }
}
```

`scheduler.yield()`는 크롬 계열에서 129부터 쓸 수 있고, 다른 브라우저는 지원 여부를 확인해야 해서 위처럼 `setTimeout`으로 물러서게 짠다. 이 환경의 크로미움 141에서는 메인 스레드와 워커 모두 `scheduler.yield`가 `function`이었다. 양보 방식의 차이와 React의 `startTransition`은 [이벤트 루프](/posts/event-loop)와 [Core Web Vitals](/posts/core-web-vitals)에서 다뤘다.

고르는 기준은 이렇다. DOM과 상관없고, 수십 ms 이상 걸리고, 입력이 크지 않거나 버퍼로 넘길 수 있으면 워커로 보낸다. 마크다운 파싱, 검색 색인 만들기, 이미지 필터, 암호화, 큰 JSON 정리 같은 것이다. DOM을 만지거나, 계산이 몇 ms뿐이거나, 주고받을 데이터가 계산보다 큰 일은 메인 스레드에서 쪼갠다.

## 워커에서 난 에러를 찾는 법

워커 안에서 잡지 않은 예외가 나면 메인 스레드의 `worker.onerror`로 `ErrorEvent`가 온다. 이걸 달아 두지 않으면 콘솔에 한 줄 찍히고 끝이라, 메인 스레드는 답을 영원히 기다린다. 앞의 RPC 층에서 남은 요청을 실패시키는 것도 이 이벤트에서 한다. 워커 안의 `async` 함수에서 난 Promise 거부는 `onerror`로 오지 않으니 워커 안에서 `self.addEventListener("unhandledrejection", ...)`로 잡아 메시지로 알린다.

`messageerror` 이벤트도 있다. 메시지가 도착했지만 받는 쪽에서 되살리지 못했을 때 온다. 보내는 쪽에서 복제할 수 없는 값은 앞에서 본 것처럼 `postMessage`가 바로 `DataCloneError`를 던지니, 이 둘을 헷갈리지 않는다.

개발자 도구에서는 Sources 패널의 스레드 목록에 워커가 이름과 함께 보이고, 워커 코드에도 중단점을 걸 수 있다. Performance 패널을 녹화하면 메인 스레드 아래에 워커 스레드가 따로 줄로 나와서, 긴 작업이 정말 메인 스레드에서 빠졌는지 눈으로 확인할 수 있다. 처음 장면의 정렬을 옮긴 뒤 이 패널을 다시 보면, 빨간 빗금은 워커 줄로 내려가고 메인 스레드에는 짧은 `postMessage`와 표를 그리는 작업만 남는다.

## 면접에서 나올 만한 질문

### Web Worker는 왜 쓰나요?

DOM과 상관없는 무거운 계산을 메인 스레드 밖으로 보내서, 그동안 입력 처리와 렌더링이 막히지 않게 하려고 쓴다. 메인 스레드는 자바스크립트, 레이아웃, 페인트, 입력 처리를 한 줄에서 하므로 50ms를 넘는 작업이 있으면 INP가 나빠진다. 워커는 계산을 빠르게 하지는 않고, 메인 스레드를 비워 둔다. 측정에서도 정렬 시간은 거의 같았지만 그동안 그려진 프레임이 1개에서 47개로 늘었다.

### 워커에서 DOM에 접근할 수 없는 이유는요?

DOM 구현이 여러 스레드가 동시에 고치는 것을 전제로 만들어지지 않았기 때문이다. 워커는 메모리를 공유하지 않고 메시지로만 대화하는 대신 잠금 없이 안전하게 돈다. 그래서 `document`, `window`, `localStorage`가 없고, `fetch`, IndexedDB, WebSocket, `OffscreenCanvas`는 있다. 화면 반영은 결과를 메시지로 받아 메인 스레드가 한다.

### postMessage로 보낸 데이터는 어떻게 전달되나요?

구조화된 복제로 복사된다. `Date`, `Map`, 타입 배열, 순환 참조까지 복사되지만 함수는 `DataCloneError`가 나고, 클래스 인스턴스는 프로토타입을 잃고 평범한 객체가 된다. 직렬화는 보내는 쪽에서 동기로 돌아서 큰 객체를 보내면 메인 스레드가 그만큼 잡힌다. 100만 개 배열에서 16ms, 64MB 버퍼 복사는 왕복 115ms가 걸렸다.

### Transferable은 무엇이고 언제 쓰나요?

`ArrayBuffer`, `MessagePort`, `OffscreenCanvas` 같은 객체를 복사하지 않고 소유권을 넘기는 방식이다. `postMessage`의 두 번째 인자에 넣으면 크기와 상관없이 몇 ms 안에 건너가고, 보낸 쪽 버퍼는 `byteLength`가 0인 떨어져 나간 상태가 된다. 이미지 픽셀, 오디오 샘플, 큰 숫자 배열처럼 한쪽만 쓰면 되는 큰 데이터에 쓴다. 넘긴 뒤 원본을 계속 쓰는 코드가 흔한 실수다.

### SharedArrayBuffer를 쓰려면 무엇이 필요한가요?

페이지가 교차 출처 격리 상태여야 한다. 문서에 `Cross-Origin-Opener-Policy: same-origin`과 `Cross-Origin-Embedder-Policy: require-corp`를 함께 보내야 생성자가 생긴다. 공유 메모리로 정밀한 타이머를 만들 수 있어 스펙터 같은 부채널 공격에 쓰일 수 있기 때문이다. 쓰게 되면 `v[0]++`처럼 나뉜 연산은 값이 사라지므로 `Atomics`로 원자적으로 고치고, `Atomics.wait`는 메인 스레드에서 쓸 수 없다.

### Dedicated, Shared, Service Worker는 어떻게 다른가요?

전용 워커는 만든 페이지에 속하고 같이 사라지며, 계산을 덜어 내는 용도다. 공유 워커는 같은 출처의 여러 탭이 포트로 함께 쓰는 하나의 워커로, 연결 하나를 여러 탭에 나눠 줄 때 쓰지만 모바일 지원을 확인해야 한다. 서비스 워커는 출처와 범위에 등록되어 네트워크 요청을 가로채는 프록시이고, 탭과 무관하게 깨어났다가 브라우저가 언제든 멈춘다. 그래서 계산이나 메모리 상태 보관에는 맞지 않는다.

### 워커를 쓰지 않고 긴 작업을 해결하는 방법은요?

작업을 50ms보다 작게 쪼개 사이사이 메인 스레드를 내준다. `scheduler.yield()`를 쓰면 양보한 뒤 이어지는 작업이 앞자리로 예약되는데, 크롬 계열 129부터라 지원하지 않는 곳에서는 `setTimeout`으로 물러선다. DOM 조작이나 React 렌더링처럼 워커로 옮길 수 없는 일, 몇 ms짜리 계산, 주고받을 데이터가 계산보다 큰 일은 쪼개기가 맞다. React에서는 급하지 않은 업데이트를 `startTransition`으로 감싼다.

### 번들러 환경에서 워커는 어떻게 만드나요?

`new Worker(new URL("./x.worker.ts", import.meta.url), { type: "module" })` 모양으로 쓴다. Vite와 webpack 5가 이 모양을 알아보고 워커를 별도 청크로 빌드해 해시가 붙은 주소로 바꿔 준다. 경로를 변수로 만들면 정적으로 분석되지 않는다. React에서는 effect 정리 함수에서 `terminate()`해서 화면을 오갈 때 워커가 쌓이지 않게 한다.
