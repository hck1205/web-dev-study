대시보드의 CPU 사용률은 40%인데 API의 p99 지연이 가끔 200ms씩 튄다. 평균 응답은 20ms로 멀쩡하다. 쿠버네티스 Pod라면 CPU limit을 2로 걸어 두었고, 노드에는 여유가 넘친다. 애플리케이션 로그에는 아무것도 없다. 코드는 아무 잘못이 없는데 요청이 "기다리고" 있다. 무엇을 기다리는 걸까.

답은 대개 CPU 차례다. 스레드가 달릴 준비가 됐는데 CPU를 못 받고 줄에 서 있거나, cgroup 한도를 다 써서 다음 주기까지 강제로 쉬고 있는 것이다. 이 글은 그 줄을 누가 어떻게 세우는지 따라간다. 먼저 운영체제가 달리던 프로그램을 끌어내릴 수 있게 해 주는 인터럽트를 보고, FCFS·SJF·라운드 로빈·우선순위·MLFQ를 같은 작업 묶음에 대어 대기 시간을 계산한다. 그다음 리눅스의 CFS와 6.6부터 들어온 EEVDF, `nice`, cgroup의 `cpu.max`를 실제로 돌려 보고, `/proc/interrupts`와 `vmstat`을 읽는 법으로 마무리한다. 환경은 Ubuntu 24.04, 리눅스 6.18 커널, 4코어 VM이다. 이 VM은 다른 작업과 같이 돌고 있어서 지연 숫자는 잡음이 섞여 있다. 크기보다 경향을 본다.

## 달리는 프로그램을 누가 끌어내리나

CPU는 명령을 하나씩 실행할 뿐이다. 무한 루프를 도는 프로그램이 스스로 멈추지 않으면, 운영체제 코드는 실행될 기회조차 없다. 그런데도 무한 루프 하나가 서버 전체를 얼리지 않는 건 인터럽트 덕분이다.

인터럽트는 CPU에게 "하던 일을 멈추고 이것부터 봐라"라고 알리는 신호다. 신호가 오면 CPU는 현재 명령을 끝낸 뒤 레지스터를 저장하고, 미리 등록된 커널의 처리기(interrupt handler)로 뛴다. 처리가 끝나면 원래 하던 곳으로 돌아오거나, 스케줄러가 다른 스레드를 고르면 그 스레드로 간다.

종류는 크게 셋이다.

- 하드웨어 인터럽트: 장치가 보낸다. 네트워크 카드에 패킷이 도착했다, 디스크 읽기가 끝났다, 키를 눌렀다 같은 것이다. 언제 올지 모르니 비동기다.
- 타이머 인터럽트: CPU마다 있는 로컬 타이머가 일정 간격으로 보낸다. 스케줄러가 "이 스레드가 너무 오래 달렸나"를 확인하는 기회가 이것이다. 이 신호가 없으면 선점(preemption)이 불가능하다.
- 예외와 트랩: CPU가 명령을 실행하다 스스로 일으킨다. 0으로 나누기, 없는 페이지 접근(page fault), 그리고 시스템 콜이 있다. 예전 리눅스는 시스템 콜을 `int 0x80`이라는 소프트웨어 인터럽트로 불렀고, 요즘 x86-64는 전용 `syscall` 명령을 쓴다.

놀이기구 줄의 비유로 말하면 타이머 인터럽트는 직원이 정해진 시간마다 울리는 종이다. 종이 울려야 직원(커널)이 끼어들어 지금 탄 사람을 내리게 할지 정할 수 있다. 아래 그림에서 다음을 누르면 무한 루프를 돌던 스레드가 종 한 번에 내려가는 과정을 볼 수 있다.

## 인터럽트 숫자 읽기

인터럽트가 실제로 얼마나 오는지 `/proc/interrupts`에서 볼 수 있다. 줄마다 인터럽트 하나, 열마다 CPU 하나다.

```bash
head -8 /proc/interrupts                         # 장치 인터럽트, CPU별 누적 횟수
grep -E 'LOC|RES|CAL|TLB' /proc/interrupts       # 타이머와 CPU 사이 인터럽트
```

```text
           CPU0       CPU1       CPU2       CPU3
 24:          1          0          0          0  IO-APIC   5-edge      ACPI:Ged
 26:          0          0          2          0  IO-APIC   4-edge      ttyS0
 32:          0        213          0          0 PCI-MSIX-0000:00:01.0   3-edge      virtio0-stats
 37:          0          0          0     153712 PCI-MSIX-0000:00:02.0   1-edge      virtio1-req.0
LOC:     347426     331453     340171     331784   Local timer interrupts
RES:     130949     115040     134996     109697   Rescheduling interrupts
CAL:     175300     164159     167371     138461   Function call interrupts
TLB:      25261      25409      28563      26423   TLB shootdowns
```

`LOC`이 로컬 타이머다. 네 코어가 고르게 받고 있다. `RES`는 다른 CPU가 "너 스케줄러 다시 돌려"라고 보낸 인터럽트다. 한 코어에서 깨운 스레드를 다른 코어에서 돌려야 할 때 생긴다. `TLB`는 한 코어가 페이지 테이블을 바꿨을 때 다른 코어의 TLB 항목을 지우라고 보내는 인터럽트다. 37번 줄 `virtio1-req.0`은 이 VM의 디스크 장치인데 15만 번이 전부 CPU3에만 몰려 있다.

이렇게 장치 인터럽트가 한 코어에 몰리는 건 실무에서 꽤 자주 만나는 병목이다. 트래픽이 많은 서버에서 `top`을 누르고 `1`을 눌러 코어별로 보면, 한 코어만 `si`(softirq) 비율이 높고 나머지는 노는 모양이 나온다. 네트워크 카드가 큐를 하나만 쓰거나 인터럽트가 한 코어로만 가는 것이다. 요즘 네트워크 카드는 큐를 여러 개 두고(RSS) 큐마다 다른 코어로 인터럽트를 보낼 수 있다. `irqbalance` 데몬이 이를 자동으로 나누고, 직접 고르려면 `/proc/irq/<번호>/smp_affinity_list`에 코어 번호를 쓴다.

장치 인터럽트 처리기는 짧아야 한다. 처리기가 도는 동안 그 코어의 다른 일이 멈추기 때문이다. 그래서 리눅스는 일을 둘로 나눈다. 처리기(top half)는 "패킷이 왔다"만 기록하고 바로 끝내고, 실제 프로토콜 처리는 softirq(bottom half)로 미룬다. softirq가 너무 많이 쌓이면 `ksoftirqd/N`이라는 커널 스레드가 일반 스레드처럼 스케줄링되어 처리한다. `top`에서 `ksoftirqd`가 CPU를 많이 쓰면 네트워크 처리가 밀리고 있다는 뜻이다.

```bash
head -6 /proc/softirqs   # softirq 종류별 CPU별 누적 횟수
```

```text
                    CPU0       CPU1       CPU2       CPU3
          HI:          0          0          0          0
       TIMER:      51221      24295      29212      23602
      NET_TX:         10         12          2          4
      NET_RX:      76769      79259      18187      14014
       BLOCK:        403       2233         16     157527
```

`NET_RX`(패킷 받기)는 CPU0·1에 몰렸고, `BLOCK`(디스크 완료)은 앞의 디스크 인터럽트를 따라 CPU3에 몰렸다. 장치 인터럽트를 받은 코어가 이어서 softirq도 처리하기 때문이다.

## 같은 작업 셋을 다섯 가지 규칙으로

이제 줄 세우는 규칙을 보자. 비교하려면 같은 작업 묶음이 필요하다. 시각 0에 작업 셋이 한꺼번에 도착한다. A는 CPU를 24ms 써야 하고, B와 C는 3ms씩이면 끝난다. 평가 기준은 대기 시간(도착해서 끝날 때까지 걸린 시간에서 실제로 CPU를 쓴 시간을 뺀 것)의 평균이다.

FCFS(First-Come First-Served)는 온 순서대로 끝까지 돌린다. A가 먼저 왔다면 A가 24ms를 다 쓰는 동안 B는 24ms, C는 27ms를 기다린다. 평균 대기는 (0 + 24 + 27) / 3 = 17ms다. 긴 작업 하나 뒤에 짧은 작업이 줄줄이 묶이는 이 모양을 호위 효과(convoy effect)라고 부른다. 마트 계산대에서 카트 가득 찬 사람 뒤에 우유 하나 든 사람이 서 있는 모습이다.

SJF(Shortest Job First)는 짧은 작업부터 돌린다. B, C, A 순서면 대기는 0, 3, 6으로 평균 3ms다. 평균 대기 시간만 보면 SJF가 이론상 최적이라는 것이 증명되어 있다. 문제는 둘이다. 운영체제는 작업이 CPU를 얼마나 쓸지 미리 모른다. 과거 사용량으로 추측할 뿐이다. 그리고 짧은 작업이 계속 들어오면 긴 작업은 영원히 못 돈다. 이것이 기아(starvation)다.

라운드 로빈(Round Robin)은 모두에게 같은 시간 조각(time quantum, 타임 슬라이스)을 주고 돌아가며 쓴다. 조각을 다 쓰면 줄 맨 뒤로 간다. 아래 그림은 조각 4ms로 세 작업을 돌린 모습이다.

평균 5.67ms로 SJF보다는 길지만 FCFS의 17ms보다 훨씬 짧다. 그리고 작업 길이를 미리 알 필요가 없고, 누구도 굶지 않는다. 대신 조각 길이가 문제다. 조각을 100ms처럼 길게 잡으면 사실상 FCFS가 된다. 1ms처럼 짧게 잡으면 응답은 빨라 보이지만, 조각마다 컨텍스트 스위칭이 일어나서 실제 일보다 갈아 끼우는 데 시간을 더 쓴다. 이 예에서 조각을 1ms로 줄여도 평균 대기는 5.67ms 그대로였다. 교환 횟수만 늘어난다.

우선순위 스케줄링은 작업마다 숫자를 주고 높은 쪽부터 돌린다. SJF도 "짧을수록 우선순위가 높다"는 우선순위 스케줄링의 한 종류다. 똑같이 기아 문제가 있고, 해법은 에이징(aging)이다. 오래 기다린 작업일수록 우선순위를 조금씩 올려 주면 언젠가는 차례가 온다.

## 직접 계산해 보기

규칙 셋을 함수 하나로 짜 보자. 작업은 `[이름, 도착 시각, 필요한 CPU 시간]`이고, 정책은 `"fcfs"`, `"sjf"`(비선점, 시간이 같으면 먼저 온 쪽), `"rr"`이다. 라운드 로빈에서 조각이 끝나는 순간 새로 도착한 작업이 있으면, 그 작업을 방금 조각을 다 쓴 작업보다 먼저 줄에 넣는다. 평균 대기 시간을 소수 둘째 자리에서 반올림해 돌려준다.

  // jobs: [["A", 0, 24], ...] 이름, 도착 시각, 필요한 CPU 시간
  // policy: "fcfs" | "sjf" | "rr", quantum: rr의 시간 조각
  // 평균 대기 시간(끝난 시각 - 도착 - 실행 시간)의 평균
  return 0;
}`}
  solution={`function avgWait(jobs, policy, quantum) {
  const list = jobs.map(([name, arrival, burst]) => ({ name, arrival, burst, left: burst }));
  const n = list.length;
  let time = 0, done = 0;
  const finish = {};
  if (policy === "rr") {
    const sorted = [...list].sort((a, b) => a.arrival - b.arrival);
    let i = 0; const queue = [];
    while (done < n) {
      while (i < n && sorted[i].arrival <= time) queue.push(sorted[i++]);
      if (queue.length === 0) { time = sorted[i].arrival; continue; }
      const job = queue.shift();
      const run = Math.min(quantum, job.left);
      time += run; job.left -= run;
      while (i < n && sorted[i].arrival <= time) queue.push(sorted[i++]);
      if (job.left > 0) queue.push(job);
      else { finish[job.name] = time; done++; }
    }
  } else {
    const pending = [...list];
    while (pending.length) {
      const ready = pending.filter((j) => j.arrival <= time);
      if (ready.length === 0) { time = Math.min(...pending.map((j) => j.arrival)); continue; }
      ready.sort((a, b) => policy === "sjf" ? a.burst - b.burst || a.arrival - b.arrival : a.arrival - b.arrival);
      const job = ready[0];
      time += job.burst; finish[job.name] = time;
      pending.splice(pending.indexOf(job), 1);
    }
  }
  const total = list.reduce((s, j) => s + (finish[j.name] - j.arrival - j.burst), 0);
  return Math.round((total / n) * 100) / 100;
}`}

## 작업의 성격을 보고 줄을 옮긴다: MLFQ

현실의 작업은 두 부류가 섞여 있다. 키 입력이나 네트워크 요청을 받고 잠깐 계산한 뒤 다시 기다리는 대화형(I/O 위주) 작업과, 한번 잡으면 계속 계산하는 CPU 위주 작업이다. 대화형 작업은 CPU를 조금만 쓰니 빨리 태워 주면 사용자가 빠르다고 느낀다. CPU 위주 작업은 조금 늦게 시작해도 상관없다. 문제는 운영체제가 어느 쪽인지 미리 모른다는 것이다.

MLFQ(Multi-Level Feedback Queue)는 행동을 보고 배운다. 우선순위가 다른 줄을 여러 개 두고, 규칙은 대략 이렇다. 새 작업은 맨 위 줄에서 시작한다. 높은 줄이 비어 있지 않으면 낮은 줄은 돌지 않는다. 받은 시간 조각을 다 쓰면 CPU 위주라고 보고 한 줄 내린다. 조각을 다 쓰기 전에 스스로 잠들면(I/O를 기다리면) 대화형이라고 보고 그 줄에 둔다. 그리고 일정 시간마다 모두를 맨 위 줄로 올린다. 마지막 규칙이 에이징이고, 이게 없으면 아래 줄의 작업이 굶는다.

MLFQ에는 고전적인 악용법이 있다. 조각이 끝나기 직전에 일부러 짧은 I/O를 부르면 계속 위 줄에 남는다. 그래서 "줄마다 쓴 시간의 총량"을 세어 내리는 식으로 보완한다. 솔라리스와 예전 윈도우, 예전 macOS의 스케줄러가 이 계열이다.

## 리눅스는 줄 대신 시간을 잰다: CFS에서 EEVDF로

리눅스는 2.6.23(2007년)부터 CFS(Completely Fair Scheduler)를 썼다. 생각이 단순하다. 줄 여러 개와 규칙 대신, 스레드마다 "지금까지 CPU를 얼마나 썼나"를 가상 실행 시간(vruntime)으로 잰다. 그리고 언제나 vruntime이 가장 작은, 즉 가장 덜 쓴 스레드를 고른다. 스레드들은 vruntime 순서로 레드-블랙 트리에 들어 있어서 가장 왼쪽을 꺼내면 된다.

잠들었다 깨어난 대화형 스레드는 잠든 동안 CPU를 안 썼으니 vruntime이 작아서 금방 차례가 온다. MLFQ처럼 성격을 추측하지 않아도 대화형 작업이 자연스럽게 빨리 돈다. 무한정 앞서지 않도록 깨어날 때 vruntime을 현재 최솟값 근처로 끌어올린다.

`nice` 값은 이 vruntime이 흐르는 속도를 바꾼다. nice 0의 가중치는 1024이고 한 단계마다 약 1.25배씩 달라진다. nice 10이면 가중치가 110이다. 가중치가 작을수록 같은 시간을 써도 vruntime이 빨리 늘어서 덜 고른다. 둘이 한 코어를 다투면 몫은 1024 : 110, 약 9.3 : 1이 된다. 실제로 그런지 한 코어에 묶어 확인했다.

```bash
taskset -c 3 ./burn &                 # nice 0, 무한 루프를 3번 코어에 묶는다
taskset -c 3 nice -n 10 ./burn &      # nice 10, 같은 코어
sleep 10
ps -o pid,ni,pcpu,time,cmd -p <첫째 PID>,<둘째 PID>
```

```text
  PID  NI %CPU     TIME CMD
 4470   0 81.1 00:00:08 ./burn
 4471  10  8.6 00:00:00 ./burn
```

81.1 : 8.6, 약 9.4 : 1로 계산과 맞는다(둘을 합쳐 90%인 건 같은 코어에 다른 작업도 있어서다). nice 10인 쪽의 스케줄러 통계도 보자.

```bash
grep -E '^(nr_switches|nr_voluntary|nr_involuntary|se.sum_exec_runtime)' /proc/<둘째 PID>/sched
```

```text
se.sum_exec_runtime                          :           877.210774
nr_switches                                  :                  580
nr_voluntary_switches                        :                    2
nr_involuntary_switches                      :                  578
```

10초 동안 실제로 CPU를 쓴 시간은 877ms이고, 교환 580번이 거의 다 빼앗긴(involuntary) 것이다. 무한 루프는 스스로 잠들지 않으니 당연하다.

여기에 우분투에서 자주 속는 함정이 있다. 데스크톱 배포판과 우분투 서버 커널은 기본으로 autogroup(`/proc/sys/kernel/sched_autogroup_enabled`가 1)이 켜져 있다. 세션(터미널) 단위로 그룹을 만들어 그룹끼리 먼저 공평하게 나누기 때문에, 다른 터미널에서 띄운 두 프로세스 사이에서는 `nice`가 생각만큼 듣지 않는다. 위 실험은 같은 셸에서 띄워서 같은 그룹이었다. systemd 서비스는 서비스마다 cgroup이 따로라 `nice`보다 `CPUWeight=`가 먼저 듣는다.

리눅스 6.6(2023년)부터 CFS의 "누구를 고를지" 부분이 EEVDF(Earliest Eligible Virtual Deadline First)로 바뀌었다. 공평하게 나눈다는 목표는 같다. 달라진 건 두 가지다. 스레드마다 받아야 할 몫과 실제로 받은 몫의 차이(lag)를 재서, 덜 받은 스레드만 "자격 있음(eligible)"으로 본다. 그리고 자격 있는 스레드 중 가상 마감 시각이 가장 이른 쪽을 고른다. 마감 시각은 요청한 시간 조각이 짧을수록 앞당겨진다. 그래서 같은 몫을 받더라도 조각을 짧게 요청한 지연에 민감한 작업이 더 자주, 더 빨리 차례를 받는다. CFS는 이런 응답성을 위해 깨어날 때 보정하는 휴리스틱을 여럿 쌓아 두었는데, EEVDF는 이를 하나의 규칙으로 정리했다. 기본 조각은 0.75ms에 CPU 수에 따른 배수를 곱한 값이고, 6.12부터는 `sched_setattr`로 스레드마다 원하는 조각을 요청할 수 있다. 우분투 24.04의 기본 커널은 6.8이라 이미 EEVDF다.

## 어느 코어에서 돌릴까: 부하 분산과 affinity

지금까지는 코어 하나의 줄만 봤다. 실제로 리눅스는 코어마다 실행 대기 줄(run queue)을 따로 둔다. 줄 하나를 모든 코어가 같이 쓰면 그 줄을 지키는 락이 병목이 되기 때문이다. 대신 줄 길이가 코어마다 달라질 수 있어서, 스케줄러가 주기적으로, 그리고 코어가 놀게 될 때 다른 코어의 줄에서 스레드를 가져온다(load balancing). 앞의 `/proc/interrupts`에서 본 `RES`(Rescheduling interrupts)가 이 과정에서 오가는 신호다.

스레드를 옮기는 데는 값이 따른다. 원래 코어의 L1·L2 캐시에 데이터가 따뜻하게 남아 있는데, 다른 코어로 가면 처음부터 다시 채워야 한다. 소켓이 둘 이상인 NUMA 서버에서 다른 소켓으로 넘어가면 메모리마저 멀어진다. 그래서 스케줄러는 웬만하면 원래 코어나 캐시를 공유하는 가까운 코어에 다시 올리려 한다.

직접 정할 수도 있다. 스레드가 돌 수 있는 코어 목록을 CPU affinity라고 한다. 이 글의 실험에서 `taskset -c 3`으로 한 코어에 묶은 것이 그것이다.

```bash
sleep 300 & P=$!
taskset -cp $P                          # 지금 돌 수 있는 코어 목록
taskset -cp 1,2 $P                      # 1, 2번 코어에서만 돌게 바꾼다
grep Cpus_allowed_list /proc/$P/status  # 커널이 기억하는 값
```

```text
pid 10787's current affinity list: 0-3
pid 10787's current affinity list: 0-3
pid 10787's new affinity list: 1,2
Cpus_allowed_list:	1-2
```

affinity로 묶으면 캐시가 따뜻하게 유지되고 다른 작업과 덜 섞이지만, 묶인 코어가 바쁘면 옆 코어가 놀아도 못 간다. 그래서 일반 서버에서는 커널에 맡기는 편이 대개 낫다. 쓸모가 있는 건 지연에 아주 민감한 작업이다. 네트워크 인터럽트는 0~1번 코어에, 애플리케이션은 2~3번 코어에 나눠 묶어 서로 방해하지 않게 하는 식이다. 쿠버네티스에서는 kubelet의 CPU 관리자를 `static` 정책으로 두면 Guaranteed QoS에 정수 CPU를 요청한 Pod에 코어를 통째로 배정한다. 이렇게 묶인 Pod는 다른 Pod와 코어를 나누지 않으니 앞에서 본 꼬리 지연이 줄어든다.

## 실시간 정책과 줄 서기의 예외

일반 스레드는 `SCHED_OTHER`(리눅스 이름은 `SCHED_NORMAL`) 정책으로 위의 공평한 스케줄러를 쓴다. 그 위에 실시간 정책이 있다. `SCHED_FIFO`는 우선순위가 높은 스레드가 스스로 내놓을 때까지 계속 돈다. `SCHED_RR`은 같은 우선순위끼리 시간 조각(`/proc/sys/kernel/sched_rr_timeslice_ms`, 기본 100ms)으로 돌아간다. 실시간 스레드가 하나라도 달릴 준비가 되면 일반 스레드는 그 코어를 받지 못한다.

```bash
cat /proc/sys/kernel/sched_rr_timeslice_ms   # SCHED_RR의 시간 조각
cat /proc/sys/kernel/sched_rt_runtime_us     # 실시간 스레드가 1초 중 쓸 수 있는 몫 (기본 950000)
chrt -p <pid>                                # 이 프로세스의 정책과 실시간 우선순위
```

무한 루프를 도는 `SCHED_FIFO` 스레드 하나가 서버를 얼리지 않게 기본값으로 1초 중 0.95초까지만 실시간 스레드에 주고, 0.05초는 일반 스레드 몫으로 남긴다. 반대쪽 끝에는 `SCHED_IDLE`(정말 아무도 안 쓸 때만)과 `SCHED_BATCH`(깨어날 때 우대하지 않음)가 있다. 백업이나 로그 압축 같은 일은 `chrt -i 0 명령`이나 `nice -n 19`로 돌리면 서비스 지연을 덜 건드린다.

## 한도를 다 쓰면 쉰다: cgroup cpu.max와 쓰로틀링

처음 상황으로 돌아가자. 컨테이너의 CPU limit은 nice와 전혀 다른 방식으로 동작한다. nice와 `cpu.weight`는 "다툴 때의 비율"이라 노드가 한가하면 얼마든지 더 쓴다. limit은 cgroup v2의 `cpu.max` 파일에 `할당량 주기` 형식으로 들어가는 절대 상한이다. 쿠버네티스에서 `limits.cpu: 2`는 `200000 100000`, 즉 100ms 주기마다 CPU 시간 200ms까지라는 뜻이다.

```bash
cat /sys/fs/cgroup/<pod 경로>/cpu.max    # "200000 100000"이면 주기 100ms에 200ms
cat /sys/fs/cgroup/<pod 경로>/cpu.stat   # nr_periods, nr_throttled, throttled_usec
```

함정은 이 200ms가 코어 수가 아니라 시간이라는 데 있다. 스레드 8개가 동시에 달리면 8개 코어에서 25ms 만에 200ms를 다 쓴다. 그러면 남은 75ms 동안 이 cgroup의 스레드는 전부 강제로 쉰다. 그 75ms 사이에 들어온 요청은 다음 주기까지 아무것도 못 한다. 1초 평균으로 보면 CPU를 2코어도 안 썼는데, 요청 하나하나는 75ms씩 얼어붙는다. 처음에 본 "사용률은 낮은데 p99가 튄다"가 이것이다. `cpu.stat`의 `nr_throttled`가 늘고 있으면 확정이다. 이 현상을 직접 재현한 것은 [requests와 limits 글](/posts/k8s-pod-resources)과 [네임스페이스와 cgroup 글](/posts/linux-namespaces-cgroups)에 있다.

손잡이는 몇 가지다. 스레드 풀 크기를 limit에 맞춘다(노드 코어 수가 아니라). limit을 올리거나 아예 빼고 requests(`cpu.weight`로 바뀐다)만으로 몫을 정하는 팀도 많다. 커널 5.14부터는 `cpu.max.burst`로 쓰지 않고 남긴 할당량을 다음 주기로 조금 넘겨 쓸 수 있다. `/proc/sys/kernel/sched_cfs_bandwidth_slice_us`(기본 5000)는 각 CPU가 전역 할당량에서 한 번에 떼어 가는 양인데, 건드릴 일은 드물다.

## 줄에서 기다린 시간이 지연이 된다

마지막으로 실제 지연을 재 봤다. 1ms 자고 일어나기를 2000번 반복하며, 정해진 1ms보다 얼마나 늦게 깨어났는지 잰다. 깨어난 스레드가 바로 CPU를 받으면 늦음은 작고, 줄에서 기다리면 커진다. 같은 코어에 무한 루프 넷을 붙여 놓고 비교했다.

```bash
taskset -c 2 ./probe alone                    # 혼자일 때
for i in 1 2 3 4; do taskset -c 2 ./burn & done
taskset -c 2 ./probe 4-hogs                   # 같은 코어에 무한 루프 넷
taskset -c 2 nice -n 10 ./probe 4hogs-n10     # 측정하는 쪽만 nice 10
pkill burn
```

```text
alone      wake delay after 1ms sleep: p50=101us p99=3459us max=14709us
4-hogs     wake delay after 1ms sleep: p50=83us p99=5593us max=28312us
4hogs-n10  wake delay after 1ms sleep: p50=101us p99=14454us max=75531us
```

중앙값은 셋 다 100마이크로초 근처다. 잠들었다 깨어난 스레드는 vruntime이 작아서(EEVDF에서는 lag가 양수라서) 무한 루프 넷을 제치고 금방 차례를 받는다. 차이는 꼬리에서 난다. 경쟁자가 생기자 p99가 3.5ms에서 5.6ms로, 최대가 15ms에서 28ms로 늘었다. 측정하는 쪽의 nice를 10으로 낮추자 p99가 14ms, 최대가 76ms로 뛰었다. 혼자일 때도 p99가 3ms를 넘는 건 이 VM을 다른 작업이 같이 쓰고 있어서다. 그래서 숫자 자체보다 셋 사이의 차이를 본다. 평균은 멀쩡한데 꼬리만 튀는 모양은 [꼬리 지연 글](/posts/tail-latency)에서 다루는 그 모양이다.

## 현장에서 CPU 차례를 의심할 때

"CPU 사용률은 낮은데 느리다"를 만나면 이 순서로 본다.

```bash
vmstat 1 5      # r: 달릴 준비가 된 스레드 수, in: 초당 인터럽트, cs: 초당 문맥 교환
```

```text
procs -----------memory---------- ---swap-- -----io---- -system-- -------cpu-------
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st gu
13  0      0 6341756 293108 5016524    0    0  2869  1961 2594   13 50  7 14 28  1  0
 9  0      0 6287776 293108 5021552    0    0   204  2116 6088 13671 69 14 14  2  2  0
 2  2      0 6259528 293112 5023996    0    0    20 22908 6459 13891 73  9 12  5  1  0
 2  0      0 6270256 294024 5073344    0    0    24  3172 7649 12566 52 12 25  8  2  0
 1  0      0 6265164 294744 5088488    0    0    60  4624 12830 28232 41 21 32  3  2  0
```

첫 줄은 부팅 뒤 평균이라 건너뛴다. `r`이 코어 수(여기서는 4)보다 꾸준히 크면 CPU 줄이 밀리고 있다. 둘째 줄의 9는 코어 4개에 스레드 9개가 달리려 한다는 뜻이다. `cs`는 초당 문맥 교환인데 1만~3만이다. 절댓값보다 평소와 비교한다. 평소의 몇 배로 뛰었다면 스레드가 너무 많거나 락 경합이다. `in`은 초당 인터럽트다. 이게 크게 뛰면서 한 코어의 `si`가 높으면 앞에서 본 장치 인터럽트 쏠림이다. `st`(steal)는 하이퍼바이저가 이 VM 대신 다른 VM에 CPU를 준 시간이라, 클라우드에서 이 값이 높으면 내 문제가 아니라 옆집 문제다.

그다음 `pidstat -w`로 어떤 프로세스가 교환을 많이 겪는지 보고, 컨테이너라면 `cpu.stat`의 `nr_throttled`를 본다. 커널 4.20부터는 `/proc/pressure/cpu`(PSI)가 "달릴 수 있는데 CPU를 못 받아 기다린 시간의 비율"을 바로 알려 준다. 이 도구들을 순서대로 쓰는 법은 [리눅스 성능 점검 글](/posts/linux-performance-triage)에 있다.

## 차례를 정하는 규칙이 지연을 정한다

스케줄러는 결국 "지금 이 코어를 누구에게 줄까"를 끝없이 다시 정하는 코드이고, 타이머 인터럽트가 그 결정을 내릴 기회를 준다. FCFS, SJF, 라운드 로빈, MLFQ는 평균 대기, 공평함, 응답성 중 무엇을 얼마나 사느냐의 차이였고, 리눅스는 실행 시간을 재서 공평하게 나누는 쪽(CFS, EEVDF)을 골랐다. 그 위에서 nice와 `cpu.weight`는 다툴 때의 비율을, `cpu.max`는 절대 상한을 정한다. 지연이 꼬리에서만 튈 때는 코드보다 먼저 이 줄을 본다.

## 면접에서 나올 만한 질문

### 선점형 스케줄링은 어떻게 가능한가요?

타이머 인터럽트 덕분이다. CPU마다 있는 타이머가 주기적으로 인터럽트를 걸면, 달리던 스레드의 의사와 상관없이 커널 처리기가 실행되고, 그 스레드가 몫을 다 썼으면 처리기에서 돌아가는 길에 스케줄러가 다른 스레드로 바꾼다. 타이머가 없으면 스레드가 스스로 시스템 콜을 부르거나 양보할 때만 바꿀 수 있는 협력형이 된다.

### 하드웨어 인터럽트 처리기는 왜 짧아야 하고, 긴 일은 어디서 하나요?

처리기가 도는 동안 그 코어의 다른 일이 멈추고, 같은 인터럽트가 다시 들어오는 것도 막히기 때문이다. 리눅스는 처리기(top half)에서는 도착 사실만 기록하고, 프로토콜 처리 같은 긴 일은 softirq(bottom half)로 미룬다. softirq가 많이 쌓이면 `ksoftirqd` 커널 스레드가 일반 스레드처럼 스케줄링되어 처리한다.

### FCFS, SJF, 라운드 로빈의 장단점은요?

FCFS는 단순하지만 긴 작업 뒤에 짧은 작업이 묶이는 호위 효과로 평균 대기가 길다. SJF는 평균 대기가 최적이지만 작업 길이를 미리 알아야 하고 긴 작업이 굶는다. 라운드 로빈은 길이를 몰라도 되고 누구도 굶지 않으며 응답성이 좋지만, 길이가 비슷한 작업끼리는 평균 대기가 FCFS보다 길어질 수 있고 조각이 짧으면 교환 비용이 커진다.

### 시간 조각(타임 슬라이스)을 짧게 하면 무엇이 좋아지고 무엇이 나빠지나요?

짧을수록 새로 깨어난 작업이 빨리 차례를 받아 응답성이 좋아진다. 대신 교환 횟수가 늘어 직접 비용과 캐시 오염이 커지고 처리량이 떨어진다. 너무 길면 사실상 FCFS가 된다. 그래서 대화형 작업은 짧게, 배치 작업은 길게 주는 식으로 작업 성격에 따라 다르게 주는 것이 MLFQ와 EEVDF가 하는 일이다.

### 기아(starvation)는 왜 생기고 어떻게 막나요?

우선순위나 SJF처럼 특정 작업을 계속 우대하는 규칙에서, 우대받는 작업이 끊이지 않으면 나머지가 영원히 못 돈다. 오래 기다린 작업의 우선순위를 조금씩 올려 주는 에이징으로 막는다. MLFQ는 주기적으로 모두를 맨 위 줄로 올리고, 리눅스 CFS·EEVDF는 실행 시간을 재서 덜 쓴 쪽을 고르니 구조적으로 기아가 생기지 않는다.

### 리눅스 CFS와 EEVDF는 무엇이 다른가요?

둘 다 스레드별 가상 실행 시간으로 CPU를 공평하게 나눈다. CFS는 vruntime이 가장 작은 스레드를 골랐고, 응답성은 깨어날 때의 보정 같은 휴리스틱으로 챙겼다. 6.6부터의 EEVDF는 받아야 할 몫보다 덜 받은 스레드 중 가상 마감 시각이 가장 이른 쪽을 고르고, 짧은 조각을 요청한 작업일수록 마감이 앞당겨져서 지연에 민감한 작업을 규칙 하나로 우대한다.

### 쿠버네티스에서 CPU 사용률이 낮은데 지연이 튀는 이유는요?

CPU limit이 cgroup `cpu.max`의 주기당 할당량으로 바뀌기 때문이다. 스레드가 많으면 100ms 주기의 할당량을 앞부분에 다 써 버리고 남은 시간 동안 cgroup 전체가 쉰다. 평균 사용률은 낮아도 그 사이에 온 요청은 수십 ms씩 멈춘다. `cpu.stat`의 `nr_throttled`로 확인하고, 스레드 풀을 limit에 맞추거나 limit을 조정한다.

### nice 값을 바꿨는데 효과가 없습니다. 왜일까요?

다른 세션이나 다른 cgroup에 있으면 nice가 거의 듣지 않는다. 우분투는 autogroup이 켜져 있어 세션 그룹끼리 먼저 공평하게 나누고, systemd 서비스와 컨테이너는 cgroup 단위로 `cpu.weight`가 먼저 적용된다. 같은 그룹 안에서 다툴 때만 nice 가중치(nice 0은 1024, nice 10은 110)대로 나뉜다. 노드가 한가하면 다툴 일이 없으니 nice는 아무 차이를 만들지 않는다.

### 스레드를 특정 코어에 묶으면 무조건 빨라지나요?

아니다. 묶으면 캐시가 따뜻하게 남고 다른 작업과 덜 섞여 지연이 안정되지만, 묶인 코어가 바쁘면 옆 코어가 놀아도 옮겨 가지 못한다. 리눅스는 코어마다 실행 대기 줄을 두고 부하를 나누면서도 가능하면 원래 코어 근처로 되돌리려 하기 때문에, 일반 서버는 커널에 맡기는 편이 낫다. 네트워크 인터럽트와 애플리케이션을 다른 코어로 나누거나, 쿠버네티스 CPU 관리자 `static` 정책으로 지연에 민감한 Pod에 코어를 통째로 줄 때 쓴다.
