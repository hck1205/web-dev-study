<EasyIntro>
  결제 서비스와 주문 서비스가 데이터베이스를 따로 쓰기 시작한 뒤, 카드에서 돈은 빠졌는데 주문 내역은 없다는 문의가 왔다. 결제 쪽 저장은 끝났고 주문 쪽 저장을 하려던 순간 프로그램이 배포로 꺼진 것이다. 데이터베이스 한 대 안에서는 "둘 다 되거나 둘 다 안 되거나"가 공짜였지만, 두 대가 되면 저장 완료 시점이 두 번이라 그 사이에 틈이 생긴다.

  2단계 커밋은 이 틈을 메우는 고전적인 방법이다. 친구 둘과 영화를 보러 가기로 할 때 한 명에게 먼저 표를 사게 하는 대신, 먼저 둘 다에게 "갈 수 있어?"를 묻고 둘 다 "응"이라고 하면 그때 "그럼 사자"고 알리는 식이다. "응"이라고 답한 친구는 그 뒤로 무슨 일이 있어도 약속을 지켜야 해서 다른 약속을 못 잡는다. 문제는 묻고 다니던 사람이 "사자"를 알리기 전에 연락이 끊기면 친구들은 가야 할지 말아야 할지 모른 채 하염없이 기다려야 한다는 것이다.

  실험에서도 결정을 못 받은 데이터베이스는 잠금을 쥔 채 재시작해도 그대로였고, 상관없는 요청까지 줄줄이 막혔다. 그래서 서비스 사이에서는 잘 쓰지 않고, 대신 단계마다 따로 저장하고 실패하면 되돌리는 방식(사가)으로 간다.
</EasyIntro>

결제 서비스와 주문 서비스가 DB를 따로 쓰기 시작한 다음 주에 고객 문의가 왔다. 카드에서 3만 2천 원이 빠졌는데 주문 내역이 없다. 로그를 보니 결제 DB 커밋은 성공했고, 바로 다음 주문 DB `INSERT`를 하려던 순간 주문 서비스 파드가 배포로 내려갔다. 코드에는 `try/catch`도 롤백도 다 있었다. 그런데 롤백할 트랜잭션이 이미 커밋된 뒤였다.

DB 한 대 안에서는 "둘 다 되거나 둘 다 안 되거나"가 공짜였다. DB가 두 대가 되면 그 약속을 누가 지키나. 이 글은 고전적인 답인 2단계 커밋(2PC, two-phase commit)이 어떻게 그 약속을 지키는지, 그리고 왜 그 대가가 커서 마이크로서비스에서는 잘 쓰지 않는지를 PostgreSQL 16 두 대로 직접 돌려 보며 본다. 실습은 Ubuntu 24.04에서 PostgreSQL 16.15 인스턴스 두 개(포트 55441, 55442)와 Node 22로 했다.

이 주제의 다른 글: 서비스를 쪼갤 때 생기는 문제 전체는 [모놀리스에서 마이크로서비스로](/posts/microservices)에서, 2PC 대신 쓰는 방법은 [사가 패턴](/posts/saga-pattern)에서, DB가 분산 트랜잭션을 대신 맡는 구조는 [분산 SQL](/posts/db-type-newsql)에서 다룬다.

## 커밋 두 번 사이에 생기는 틈

DB 한 대의 트랜잭션이 원자적인 이유는 커밋이 한 지점에서 일어나기 때문이다. PostgreSQL은 변경 내용을 WAL(먼저 쓰는 로그)에 적고, 마지막에 커밋 레코드 하나를 디스크에 쓴다. 그 레코드가 디스크에 닿기 전에 죽으면 전부 없던 일이 되고, 닿은 뒤에 죽으면 전부 살아난다. 중간은 없다.

DB가 두 대면 커밋 레코드도 두 개다. 둘을 같은 순간에 쓸 방법이 없으니 반드시 하나가 먼저 커밋되고, 그 사이에 틈이 생긴다. 처음 장면은 그 틈에 프로세스가 죽은 경우다.

순서를 바꾸거나 재시도를 붙여도 틈은 남는다. 첫 커밋이 끝난 뒤 두 번째 DB가 제약 조건 위반으로 거절하면, 이미 커밋된 첫 번째를 취소할 방법이 DB 수준에는 없다. 필요한 건 "커밋하기 전에 모두가 커밋할 수 있는지부터 확인하는 단계"다.

## 먼저 묻고, 모두 된다고 하면 그때 커밋한다

2PC는 이 확인을 별도 단계로 떼어 낸다. 전체를 진행하는 쪽을 코디네이터(조정자), 각 DB를 참여자라고 부른다.

1단계(prepare, 투표)에서 코디네이터는 참여자마다 "커밋할 준비가 됐나"를 묻는다. 참여자는 자기 몫의 변경을 끝까지 해 보고, 제약 조건 검사까지 통과하면 그 상태를 디스크에 기록한 뒤 "예"라고 답한다. 이 "예"는 무거운 약속이다. 지금부터 전원이 나가도, 프로세스가 재시작해도, 코디네이터가 커밋하라고 하면 반드시 커밋할 수 있어야 한다. 그래서 잠금도 그대로 쥐고 있는다.

2단계(commit, 결정)에서 코디네이터는 표를 모은다. 전원이 "예"면 커밋을, 하나라도 "아니오"거나 답이 없으면 롤백을 결정하고, 그 결정을 자기 디스크에 먼저 적은 다음 참여자들에게 알린다.

DB 한 대에서 커밋 레코드가 하던 역할을 2PC에서는 코디네이터의 결정 기록이 맡는다. 참여자의 "예"는 언제든 커밋할 수 있게 해 두겠다는 약속이고, 실제로 커밋할지는 그 기록 하나가 정한다.

## PostgreSQL 두 대로 직접 해 보기

PostgreSQL은 참여자 쪽 명령을 그대로 제공한다. `PREPARE TRANSACTION`, `COMMIT PREPARED`, `ROLLBACK PREPARED`다. 다만 기본값으로는 꺼져 있다. 평소 쓰던 클러스터에서 그대로 쳐 보면 이렇게 나온다.

```bash
# 기본 설정(max_prepared_transactions = 0)인 클러스터에서 시도한다
sudo -u postgres psql -X -d postgres -c 'BEGIN' -c "PREPARE TRANSACTION 't1'"
```

```text
BEGIN
ERROR:  prepared transactions are disabled
HINT:  Set max_prepared_transactions to a nonzero value.
```

`max_prepared_transactions`는 동시에 준비 상태로 둘 수 있는 트랜잭션 수이고 서버 재시작이 필요한 설정이다. 공식 문서는 쓰기로 했다면 `max_connections`만큼 잡으라고 권한다. 복제본이 있으면 복제본의 값이 프라이머리보다 작으면 안 된다. 실습용으로 두 인스턴스를 따로 만들어 10으로 켰다.

```bash
# 실습용 인스턴스 두 개를 만든다 (postgres 사용자로). 하나는 주문, 하나는 결제
/usr/lib/postgresql/16/bin/initdb -D ~/v3-lab/orders -A trust -U postgres
/usr/lib/postgresql/16/bin/initdb -D ~/v3-lab/payments -A trust -U postgres
# 포트와 준비 트랜잭션 수를 정한다 (payments는 port=55442)
printf "port=55441\nmax_prepared_transactions=10\n" >> ~/v3-lab/orders/postgresql.conf
/usr/lib/postgresql/16/bin/pg_ctl -D ~/v3-lab/orders -l ~/v3-lab/orders.log start
```

예제 테이블은 작게 둔다. 주문 DB에는 `orders`, 결제 DB에는 잔액이 음수가 될 수 없는 `wallets`와 `payments`가 있다.

```sql
-- 주문 DB (55441, shop_orders)
CREATE TABLE orders (id text PRIMARY KEY, user_id int NOT NULL, amount int NOT NULL, status text NOT NULL);

-- 결제 DB (55442, shop_payments)
CREATE TABLE wallets (user_id int PRIMARY KEY, balance int NOT NULL CHECK (balance >= 0));
CREATE TABLE payments (order_id text PRIMARY KEY, user_id int NOT NULL, amount int NOT NULL);
INSERT INTO wallets VALUES (7, 50000), (8, 3000);
```

이제 코디네이터 역할을 손으로 한다. 두 DB에서 각자 일을 하고, 커밋 대신 같은 이름(gid, 전역 트랜잭션 ID)으로 준비만 해 둔다.

```sql
-- 주문 DB
BEGIN;
INSERT INTO orders VALUES ('o-1042', 7, 32000, 'PAID');
PREPARE TRANSACTION 'o-1042';   -- 커밋 대신 준비. 이 뒤로 세션을 끊어도 된다

-- 결제 DB
BEGIN;
UPDATE wallets SET balance = balance - 32000 WHERE user_id = 7;
INSERT INTO payments VALUES ('o-1042', 7, 32000);
PREPARE TRANSACTION 'o-1042';
SELECT gid, prepared, owner, database FROM pg_prepared_xacts;  -- 준비된 트랜잭션 목록
```

```text
  gid   |           prepared            |  owner   |   database
--------+-------------------------------+----------+---------------
 o-1042 | 2026-10-20 14:18:53.502833+00 | postgres | shop_payments
(1 row)
```

psql은 이미 종료됐다. 그런데 트랜잭션은 남아 있다. 보통 트랜잭션은 세션이 끊기면 롤백되지만, 준비된 트랜잭션은 세션에서 떨어져 나와 DB가 따로 들고 있다. 이 시점에 주문 DB에서 `SELECT * FROM orders`를 하면 0행이 나온다. 아직 아무도 커밋하지 않았으니 다른 세션에는 보이지 않는다.

`pg_prepared_xacts`의 한 줄을 뜯어 보면 운영에서 무엇을 봐야 하는지가 보인다.

## 한 곳이 아니라고 답하면

이번에는 잔액이 3천 원뿐인 사용자 8이 3만 2천 원을 결제한다. 주문 DB는 준비에 성공하지만 결제 DB는 `CHECK`에 걸린다.

```sql
-- 결제 DB
BEGIN;
UPDATE wallets SET balance = balance - 32000 WHERE user_id = 8;
PREPARE TRANSACTION 'o-1043';
```

```text
BEGIN
ERROR:  new row for relation "wallets" violates check constraint "wallets_balance_check"
DETAIL:  Failing row contains (8, -29000).
ROLLBACK
```

마지막 줄을 보자. 실패한 트랜잭션에서 `PREPARE TRANSACTION`을 보내면 PostgreSQL은 에러 대신 `ROLLBACK`이라고 답하고 트랜잭션을 버린다. 이게 "아니오" 표다. 코디네이터는 명령 태그가 `PREPARE TRANSACTION`인지 `ROLLBACK`인지로 표를 읽어야 한다. 에러만 잡으면 이 경우를 놓친다.

표가 하나라도 아니오면 결정은 롤백이다. 이미 준비해 둔 주문 DB 쪽을 거둔다.

```sql
-- 주문 DB
ROLLBACK PREPARED 'o-1043';
SELECT count(*) FROM orders WHERE id = 'o-1043';
```

```text
ROLLBACK PREPARED
 count
-------
     0
(1 row)
```

## 결정 직전에 코디네이터가 죽으면

2PC의 가장 큰 약점이 여기 있다. 참여자는 "예"라고 답한 순간부터 혼자서는 아무것도 못 한다. 커밋하자니 다른 참여자가 아니오라고 했을 수 있고, 롤백하자니 코디네이터가 이미 커밋을 결정하고 다른 참여자에게는 알렸을 수 있다. 이 상태를 in-doubt(결과 미정)라고 하고, 코디네이터가 돌아올 때까지 기다리는 수밖에 없다는 뜻에서 2PC를 블로킹 프로토콜이라고 부른다.

## 결정을 먼저 적어 두는 코디네이터

블로킹을 줄이는 방법은 코디네이터를 빨리, 그리고 정확히 되살리는 것이다. 그러려면 코디네이터가 무엇을 결정했는지 디스크에 남겨야 한다. 간단한 코디네이터를 Node와 `pg`로 짰다. 표를 모으고, 결정을 파일에 적고(fsync), 그다음에 알린다. 일부러 두 지점에서 죽게 할 수 있다.

```js
// tpc.js 핵심 부분
for (const p of parts) {
  try {
    await p.c.query("BEGIN");
    for (const s of p.sql) await p.c.query(s);
    await p.c.query(`PREPARE TRANSACTION '${gid}'`);
    votes.push(true);
  } catch (e) {
    await p.c.query("ROLLBACK").catch(() => {});
    votes.push(false);
  }
}
if (crashAt === "after-prepare") process.exit(1);          // 결정 전에 죽는다
const decision = votes.every(Boolean) ? "COMMIT" : "ABORT";
appendAndFsync(LOG, { gid, decision });                    // 결정을 먼저 적는다
if (crashAt === "after-decision") process.exit(1);         // 알리기 전에 죽는다
for (const p of preparedParts) await p.c.query(`${decision === "COMMIT" ? "COMMIT" : "ROLLBACK"} PREPARED '${gid}'`);
```

복구 루틴은 시작할 때 모든 참여자의 `pg_prepared_xacts`를 훑고, 자기 기록에 결정이 있으면 그대로, 없으면 롤백한다. 결정 기록이 없다는 건 커밋을 결정한 적이 없다는 뜻이니 롤백해도 안전하다. 이 규칙을 추정 롤백(presumed abort)이라고 하고, IBM R* 시절부터 쓰던 최적화다. 롤백은 기록하지 않아도 되니 디스크 쓰기도 줄어든다.

## XA는 이 약속을 표준으로 만든 것

DB 종류가 섞여도 2PC를 하려면 참여자마다 같은 말을 알아들어야 한다. 1991년 X/Open이 정한 XA 규격이 그 공통 언어다. 트랜잭션 관리자(TM)가 리소스 관리자(RM, DB나 메시지 큐)에게 `xa_start`, `xa_end`, `xa_prepare`, `xa_commit`, `xa_rollback`, `xa_recover`를 부른다. Java의 JTA가 이 규격을 감싸고, Atomikos나 Narayana 같은 트랜잭션 관리자가 TM 역할을 한다.

MySQL은 SQL 문으로 XA를 연다. 문법만 옮겨 보면 이렇다(이 실습에서 MySQL은 돌리지 않았다).

```sql
-- MySQL 8의 XA 문법
XA START 'o-1042';
UPDATE wallets SET balance = balance - 32000 WHERE user_id = 7;
XA END 'o-1042';
XA PREPARE 'o-1042';
XA COMMIT 'o-1042';   -- 또는 XA ROLLBACK 'o-1042'
XA RECOVER;           -- 준비 상태로 남은 트랜잭션 목록. PostgreSQL의 pg_prepared_xacts에 해당한다
```

PostgreSQL에는 XA 문법이 없고, JDBC 드라이버의 `PGXADataSource`가 XA 호출을 `PREPARE TRANSACTION`과 `COMMIT PREPARED`로 바꿔 준다. PostgreSQL 문서도 이 명령들이 애플리케이션이 직접 쓰라고 만든 게 아니라 외부 트랜잭션 관리자를 위한 것이라고 적는다.

XA 운영에서 나오는 말이 하나 더 있다. 휴리스틱 결정(heuristic commit, heuristic rollback)이다. in-doubt가 너무 오래가면 DBA가 참여자 하나를 손으로 커밋하거나 롤백해 버리는 것이다. 잠금은 풀리지만, 코디네이터의 결정과 반대로 했다면 원자성이 깨진다. TM이 돌아와서 그 사실을 알면 heuristic mixed 같은 예외로 알려 줄 뿐 데이터를 맞춰 주지는 않는다.

## 3PC가 블로킹을 풀지 못하는 이유

2PC가 막히는 건 참여자가 "다른 참여자들이 다 예라고 했는지"를 모르기 때문이다. 3단계 커밋(3PC)은 1981년 스킨(Skeen)이 제안한 방식으로, 투표와 커밋 사이에 pre-commit 단계를 하나 더 넣는다. 코디네이터가 "모두 예라고 했다"를 먼저 알린 뒤에 커밋을 지시한다. 그러면 참여자는 pre-commit을 받았는지 여부로 상황을 짐작해서, 코디네이터가 죽어도 남은 참여자끼리 타임아웃 뒤에 결론을 낼 수 있다.

이 논리는 "죽은 노드는 확실히 죽은 것이고, 메시지는 정해진 시간 안에 반드시 도착한다"는 가정 위에 서 있다. 네트워크가 갈라지면 가정이 깨진다. 한쪽에서는 pre-commit을 받은 참여자들이 커밋하고, 다른 쪽에서는 pre-commit을 못 받은 참여자들이 롤백해서 결과가 갈릴 수 있다. 메시지 왕복도 하나 늘어난다. 그래서 실무에서 3PC를 쓰는 시스템은 거의 없다.

실제로 블로킹을 없앤 방법은 코디네이터와 참여자를 각각 합의 그룹으로 만드는 것이다. 그레이와 램포트의 Paxos Commit이 이 생각을 정리했고, Google Spanner는 참여자 하나하나를 Paxos로 복제된 그룹으로 두고 그 위에서 2PC를 돈다. 코디네이터 리더가 죽어도 그룹의 다른 노드가 결정 기록을 이어받는다. CockroachDB와 TiDB가 Raft 위에서 같은 일을 한다. 구간마다 어떻게 나뉘고 기록되는지는 [분산 SQL](/posts/db-type-newsql)에, 합의 그룹이 기록을 맞추는 원리는 [Raft 합의](/posts/raft-consensus)에 있다.

## 마이크로서비스가 2PC를 피하는 이유

2PC가 정확한데도 서비스 사이에서 잘 쓰지 않는 이유는 비용이 전부 가용성과 지연으로 돌아오기 때문이다.

첫째, 참여자가 모두 살아 있어야 한다. 가용성 99.9%인 서비스 셋이 2PC로 묶이면 전체는 대략 0.999³, 99.7%가 된다. 참여자가 늘수록 더 떨어진다.

둘째, 잠금이 가장 느린 참여자의 시간만큼 이어진다. 준비부터 결정까지 모든 참여자가 행 잠금을 쥐고 있으니, 한 곳이 느리면 다른 DB의 인기 있는 행까지 같이 묶인다. 앞의 지갑 잠금처럼 상관없는 요청이 줄을 선다.

셋째, 참여할 수 없는 상대가 많다. 외부 결제사의 HTTP API, 이메일 발송, 대부분의 NoSQL 저장소는 "준비만 해 두고 기다리기"를 지원하지 않는다. Kafka에도 트랜잭션이 있지만 자기 파티션들 사이의 원자성을 위한 내부 프로토콜이고 XA 참여자로 끼지는 않는다.

넷째, 서비스끼리 강하게 묶인다. 결제 서비스 DB가 주문 서비스의 트랜잭션 관리자 결정을 기다려야 하니 독립 배포와 독립 장애라는 서비스 분리의 목적과 부딪힌다.

그래서 보통은 다른 방향으로 간다.

먼저 의심할 것은 경계다. 늘 함께 바뀌어야 하는 데이터라면 같은 서비스, 같은 DB에 있어야 했을 가능성이 크다. 그다음은 DB에 쓰고 이벤트를 내보내는 아웃박스, 단계마다 로컬 트랜잭션을 커밋하고 실패하면 보상하는 [사가](/posts/saga-pattern)다. 둘 다 같은 메시지가 두 번 올 수 있다는 전제라 받는 쪽은 [멱등성 키](/posts/idempotency-key)처럼 중복을 견뎌야 한다. 2PC가 맞는 자리도 있다. 한 팀이 운영하는 DB 두세 개 사이의 짧은 트랜잭션, 금융 원장처럼 잠깐의 불일치도 허용할 수 없는 곳, 그리고 앞에서 본 분산 SQL처럼 DB가 내부에서 합의 위에 2PC를 숨겨 주는 경우다.

PostgreSQL 안에서 다른 서버의 테이블을 읽고 쓰는 `postgres_fdw`도 2PC를 쓰지 않는다. PostgreSQL 16 기준으로 원격 트랜잭션은 로컬 트랜잭션이 커밋될 때 차례로 커밋되고, 그 사이에 원격 서버가 죽으면 일부만 커밋될 수 있다.

## 준비된 채 버려진 트랜잭션을 만났을 때

운영 중에 아무도 안 건드리는 행에서 잠금 대기가 생기고, `pg_stat_activity`를 봐도 잠금을 쥔 세션이 없다면 먼저 `pg_prepared_xacts`를 본다. VACUUM이 `dead but not yet removable`을 계속 남기거나 `age(datfrozenxid)`가 계속 커질 때도 같다.

```sql
-- 1분 넘게 결정을 못 받은 준비 트랜잭션. 모니터링 쿼리로 걸어 두고 0이 아니면 알린다
SELECT gid, database, owner, now() - prepared AS waiting, age(transaction) AS xid_age
FROM pg_prepared_xacts
WHERE prepared < now() - interval '1 minute'
ORDER BY prepared;
```

찾았다면 순서가 있다. gid로 어느 트랜잭션 관리자의 것인지 알아내고, 그 관리자의 결정 기록이나 복구 기능을 먼저 쓴다. 관리자가 살아 있는데 결정을 못 보내고 있다면 그쪽 장애를 먼저 고친다. 관리자도 기록도 완전히 사라졌다면 다른 참여자들의 상태를 모두 확인해서 한 곳이라도 이미 커밋됐으면 커밋, 아무 곳도 커밋되지 않았으면 롤백으로 맞춘다.

<Callout kind="warning" title="COMMIT PREPARED와 ROLLBACK PREPARED는 되돌릴 수 없다">
손으로 끝내는 순간 그게 휴리스틱 결정이 된다. 다른 참여자와 반대로 하면 결제는 있고 주문은 없는 상태를 DB가 영구히 확정한다. 실행 전에 같은 gid를 모든 참여자 DB에서 `SELECT * FROM pg_prepared_xacts WHERE gid = '...'`로 조회하고, 이미 결정이 끝난 참여자의 데이터(주문 행이 있는지)를 확인한다. 끝낸 뒤에는 무엇을 왜 그렇게 했는지 기록하고, 반대로 끝났어야 했다는 게 밝혀지면 DB가 아니라 보상 작업(환불, 주문 재생성)으로 맞춘다.
</Callout>

흔한 실수도 몇 가지 있다. `max_prepared_transactions`만 켜 두고 감시 쿼리는 걸지 않아 버려진 트랜잭션이 몇 주씩 VACUUM을 막는다. 연결 풀러를 거치면서 `PREPARE TRANSACTION` 뒤의 `COMMIT PREPARED`를 다른 DB에 보내 `belongs to another database` 에러를 낸다. 코디네이터가 실패한 `PREPARE`의 응답 태그(`ROLLBACK`)를 성공으로 읽는다. 그리고 2PC 안에서 외부 API를 부른다. 준비 상태로 기다리는 동안 결제사가 타임아웃을 내면 그 호출은 되돌릴 방법이 없다.

## 2PC가 남기는 것

2PC는 커밋 지점을 코디네이터의 결정 기록 한 줄로 옮겨 여러 DB의 원자성을 지킨다. 그 대가로 참여자는 "예"라고 답한 순간부터 결정을 기다리며 잠금을 쥐고, 코디네이터가 죽으면 모두가 기다린다. 이 블로킹을 받아들일 수 있는 짧고 가까운 트랜잭션에는 여전히 쓸 만하고, 받아들일 수 없는 서비스 사이에서는 원자성을 조금 내려놓고 [사가](/posts/saga-pattern)로 간다. 코디네이터를 죽지 않게 만드는 쪽은 [리더 선출](/posts/leader-election)과 [Raft 합의](/posts/raft-consensus)로 이어진다.

## 면접에서 나올 만한 질문

### 2PC는 어떻게 원자성을 지키나요?

커밋 전에 모든 참여자에게 커밋할 수 있는지 먼저 묻고, 전원이 예라고 하면 그때 커밋을 결정한다. 참여자는 예라고 답하기 전에 변경과 잠금을 디스크에 남겨 나중에 반드시 커밋할 수 있게 해 둔다. 코디네이터는 결정을 자기 디스크에 먼저 적고 알리므로, 그 기록이 전체의 커밋 지점이 된다.

### 2PC가 블로킹 프로토콜이라는 건 무슨 뜻인가요?

참여자가 예라고 답한 뒤 코디네이터가 죽으면, 참여자는 커밋도 롤백도 스스로 정할 수 없어서 코디네이터가 돌아올 때까지 기다려야 한다는 뜻이다. 다른 참여자가 아니오라고 했는지, 코디네이터가 이미 커밋을 결정했는지 모르기 때문이다. 그동안 잠금을 쥐고 있어서 상관없는 요청까지 막힌다. PostgreSQL에서는 이 트랜잭션이 재시작 뒤에도 남고 VACUUM도 붙잡는다.

### 코디네이터가 재시작하면 in-doubt 트랜잭션을 어떻게 정리하나요?

모든 참여자의 준비된 트랜잭션 목록을 읽고, 자기 결정 기록에 커밋이 있으면 커밋, 없으면 롤백한다. 커밋을 결정했다면 반드시 기록이 먼저 남았을 테니 기록이 없으면 롤백해도 안전하다. 이게 추정 롤백이다. 같은 DB에 다른 관리자의 트랜잭션이 있을 수 있어서 gid 접두어로 자기 것만 고른다.

### PostgreSQL에서 준비된 트랜잭션이 오래 남으면 어떤 문제가 생기나요?

잠금이 풀리지 않아 같은 행을 건드리는 요청이 대기하고, 잠금 주인 세션이 없어서 세션을 죽여 해결할 수도 없다. 그 xid가 VACUUM의 제거 기준선을 붙잡아 죽은 행이 쌓이고, 오래가면 트랜잭션 ID 고갈 위험까지 생긴다. 그래서 `pg_prepared_xacts`의 `prepared` 시각을 감시하고 몇 분 넘게 남으면 알림을 건다.

### 3PC는 2PC의 블로킹을 해결하나요?

장애가 확실히 감지되고 메시지 지연에 상한이 있다는 가정에서만 해결한다. 네트워크 분할이 생기면 양쪽이 서로 다른 결론을 내릴 수 있고 왕복도 하나 늘어서 실무에서는 거의 쓰지 않는다. 실제로 블로킹을 줄인 방법은 코디네이터와 참여자를 Paxos나 Raft 그룹으로 복제해 결정 기록이 한 노드에만 있지 않게 하는 것이다. Spanner와 CockroachDB가 이렇게 한다.

### 마이크로서비스에서 2PC를 잘 쓰지 않는 이유는요?

모든 참여자가 살아 있어야 해서 가용성이 곱으로 떨어지고, 가장 느린 참여자만큼 잠금이 이어지며, 외부 API나 많은 NoSQL처럼 준비 단계를 지원하지 않는 상대가 많기 때문이다. 서비스들이 한 트랜잭션 관리자의 결정에 묶여 독립 배포와 장애 격리라는 분리의 목적과도 부딪힌다. 대신 아웃박스와 사가로 결과적으로 맞추고, 받는 쪽을 멱등하게 만든다.

### XA의 휴리스틱 결정이 위험한 이유는요?

in-doubt 트랜잭션을 사람이 참여자 한 곳에서 직접 커밋하거나 롤백하는 것이라, 코디네이터의 실제 결정과 반대면 원자성이 깨진 채 확정되기 때문이다. 잠금은 풀리지만 데이터 불일치는 트랜잭션 관리자가 고쳐 주지 않는다. 손으로 정리해야 한다면 모든 참여자의 상태를 먼저 확인해 이미 커밋된 곳이 있는지 보고 그 방향으로 맞춘다.
