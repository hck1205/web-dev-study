글에서 금칙어 목록에 있는 말을 모두 찾아 위치를 표시해야 한다고 해 보자. 금칙어가 서로 겹칠 수도 있다. `cats`를 찾으면 그 안의 `cat`도, 그 안의 `at`도 찾아야 한다. [LeetCode 1065. Index Pairs of a String](https://leetcode.com/problems/index-pairs-of-a-string/)(프리미엄 문제)이 이 일을 아주 작은 크기로 하는 문제다.

Easy 문제라 풀이 하나는 금방 나온다. 그런데 "단어 여러 개를 한 텍스트에서 한꺼번에 찾기"는 검색 엔진, 금칙어 필터, 바이러스 시그니처 검사가 모두 하는 일이라 꼬리 질문이 깊어지기 좋다. 이 글은 모든 부분 문자열을 집합에 묻는 풀이, 단어마다 `indexOf`로 찾는 풀이, 시작 위치마다 트라이를 내려가는 풀이, 텍스트를 한 번만 훑는 아호-코라식까지 네 가지를 본다. 트라이 자체는 [Implement Trie](/posts/leetcode-implement-trie)에서 만들었다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 텍스트 안의 단어 위치를 모두 적는다

입력은 문자열 `text`와 단어 목록 `words`다. `text[i..j]`(양 끝 포함)가 `words`에 있는 단어인 `[i, j]`를 모두 돌려준다. 답은 `i`가 작은 순서, `i`가 같으면 `j`가 작은 순서로 정렬해야 한다.

- `text` 길이는 100 이하, 단어는 20개 이하, 단어 길이는 50 이하.
- 모두 소문자이고 단어는 서로 다르다.

크기가 아주 작아서 어떤 풀이든 통과한다. 그래서 이 문제의 무게는 두 군데에 있다. 하나는 겹치는 등장을 빠짐없이 찾는 것, 다른 하나는 정렬 순서를 맞추는 것이다. 둘 다 Easy라고 방심하면 틀리는 자리다. 면접에서는 "텍스트가 100만 글자, 단어가 1만 개라면"으로 넘어간다.

이 글에서 쓸 예시다. 칸 번호를 위에 적었다.

```text
        0 1 2 3 4 5 6 7 8
text  = t h e c a t s a t
words = [cat, cats, at, the]
답    = [0,2] [3,5] [3,6] [4,5] [7,8]
```

손으로 찾아 보자. 0번에서 `the`가 2번까지. 3번에서 `cat`이 5번까지, 같은 자리에서 `cats`가 6번까지 나온다. 4번에서 `at`이 5번까지, 이건 `cat` 안에 겹쳐 있다. 7번에서 `at`이 한 번 더 나온다. `sat`은 목록에 없다.

3번에서 시작하는 단어가 두 개다. 그래서 `[3,5]`가 `[3,6]`보다 먼저 온다. 정렬 규칙의 두 번째 기준이 여기서 쓰인다.

## 모든 부분 문자열을 집합에 묻기

가능한 모든 `[i, j]`를 만들어 보고, 그 부분 문자열이 단어 집합에 있는지 묻는다.

```js
function indexPairs(text, words) {
  const dict = new Set(words);
  const res = [];
  for (let i = 0; i < text.length; i++)
    for (let j = i; j < text.length; j++)
      if (dict.has(text.slice(i, j + 1))) res.push([i, j]); // text[i..j]가 단어인가
  return res;
}
```

`i`를 바깥, `j`를 안쪽에서 키우니 답이 저절로 정렬 순서로 쌓인다. 따로 정렬할 필요가 없다.

텍스트 길이를 n이라 하면 `[i, j]`가 n²/2개이고, 부분 문자열을 만들고 해시하는 데 O(n)이라 O(n³)이다. n = 100이면 50만 번 남짓이라 아무 문제가 없다. 5,000글자로 늘리자 39초가 걸렸다.

낭비는 단어 길이가 50 이하라는 걸 쓰지 않는 데 있다. 50글자보다 긴 부분 문자열은 단어일 수 없는데도 다 만들어 본다. `j`를 `i + 49`까지만 돌게 막으면 O(n·L²)으로 줄지만(L은 단어 최대 길이), 그래도 부분 문자열을 계속 만든다.

## 단어마다 indexOf로 찾기

거꾸로 단어 쪽에서 출발할 수 있다. 단어마다 `text`에서 등장 위치를 모두 찾는다.

```js
function indexPairs(text, words) {
  const res = [];
  for (const w of words) {
    let i = text.indexOf(w);
    while (i !== -1) {
      res.push([i, i + w.length - 1]);
      i = text.indexOf(w, i + 1); // 겹치는 등장도 찾으려고 한 칸만 민다
    }
  }
  // 단어 순서대로 쌓였으니 i, 그다음 j 기준으로 정렬한다
  res.sort((a, b) => a[0] - b[0] || a[1] - b[1]);
  return res;
}
```

두 군데가 중요하다.

첫째, 다음 검색을 `i + 1`부터 한다. `i + w.length`부터 하면 겹치는 등장을 놓친다. `aaaa`에서 `aa`를 찾으면 `[0,1]`, `[1,2]`, `[2,3]` 세 개인데, 단어 길이만큼 건너뛰면 `[1,2]`가 빠진다.

```js
i = text.indexOf(w, i + w.length); // 단어 길이만큼 건너뛰면
// text = "aaaa", w = "aa" -> [[0,1],[2,3]] (정답은 [[0,1],[1,2],[2,3]])
```

둘째, 정렬 비교 함수다. 아래 "기본 정렬은 배열을 글자로 비교한다" 절에서 따로 본다.

단어 D개마다 `indexOf`가 최악 O(n·L)이라 O(D·n·L)에 정렬 O(R log R)이 더해진다(R은 답의 개수). 공간은 답 O(R)이다. `indexOf`는 엔진이 최적화한 내장 함수라 실제로는 빠르다. 단어가 많아지면 같은 텍스트를 D번 읽는다는 게 부담이 된다.

`indexOf`의 최악은 `aaaa…ab`에서 `aa…ab`를 찾는 것처럼 매번 거의 끝까지 맞다가 틀리는 입력이다. 단어마다 [KMP](/posts/string-search-algorithms#이미-맞힌-글자는-다시-보지-않는다)를 쓰면 단어 하나에 O(n + L)이 보장되어 전체 O(D·(n + L))이 된다. KMP도 한 번 맞은 뒤 실패 함수만큼만 물러나서 겹치는 등장을 놓치지 않는다. 다만 이 풀이도 텍스트를 단어 수만큼 읽는다는 점은 그대로라, 단어를 한꺼번에 찾는 다음 풀이들로 넘어간다.

## 시작 위치마다 트라이를 내려가기

단어 D개를 따로 찾지 말고 한꺼번에 찾고 싶다. 단어 목록을 트라이로 만들면 "`i`에서 시작하는 단어가 무엇무엇인가"를 한 번에 물을 수 있다.

1. 단어로 트라이를 만든다. 단어가 끝나는 노드에 끝 표시를 붙인다.
2. `text`의 시작 위치 `i`마다 뿌리에서 출발해 `text[i]`, `text[i+1]`, …을 따라 내려간다.
3. 내려간 노드에 끝 표시가 있으면 `[i, j]`를 적는다. 멈추지 않고 계속 내려간다(`cat` 다음에 `cats`가 있을 수 있다).
4. 자식이 없으면 `i`에서 시작하는 단어는 더 없다. 다음 `i`로 간다.

`i`를 왼쪽부터, `j`를 `i`부터 키우며 적으니 답이 저절로 정렬된다. 정렬이 필요 없다는 게 이 풀이의 또 다른 장점이다.

```js
function indexPairs(text, words) {
  // 1. 단어로 트라이를 만든다. end는 단어가 여기서 끝난다는 표시
  const root = {};
  for (const w of words) {
    let node = root;
    for (const ch of w) node = node[ch] ??= {};
    node.end = true;
  }
  // 2. 시작 위치마다 트라이를 내려간다
  const res = [];
  for (let i = 0; i < text.length; i++) {
    let node = root;
    for (let j = i; j < text.length; j++) {
      node = node[text[j]];
      if (!node) break;               // i에서 시작하는 단어가 더 없다
      if (node.end) res.push([i, j]); // text[i..j]가 단어다. 멈추지 않는다
    }
  }
  return res; // i, j 순서대로 쌓였으니 정렬이 필요 없다
}
```

트라이를 만드는 데 단어 글자 수 합 O(D·L), 찾는 데 시작 위치 n개 × 많아야 L칸이라 O(n·L)이다. 답을 적는 O(R)까지 더해 O(D·L + n·L + R)이다. 공간은 트라이 O(D·L)과 답이다.

[Extra Characters in a String](/posts/leetcode-extra-characters-in-a-string)의 안쪽 루프가 이것과 똑같다. 그 문제는 찾은 `[i, j]`로 DP 칸을 갱신하고, 이 문제는 그대로 적는다. 끝 표시에서 멈추지 않는 것도 같다. 반대로 [Replace Words](/posts/leetcode-replace-words)는 가장 짧은 어근만 원해서 첫 끝 표시에서 멈춘다.

### Python과 Java로 쓰면

Python은 딕셔너리 트라이에 끝 표시를 `"$"` 키로 둔다.

```python
from typing import List

class Solution:
    def indexPairs(self, text: str, words: List[str]) -> List[List[int]]:
        root = {}
        for w in words:
            node = root
            for ch in w:
                node = node.setdefault(ch, {})
            node["$"] = True  # 단어 끝 표시

        res = []
        for i in range(len(text)):
            node = root
            for j in range(i, len(text)):
                node = node.get(text[j])
                if node is None:
                    break
                if "$" in node:
                    res.append([i, j])
        return res
```

Java는 26칸 배열 노드에 결과를 `List<int[]>`로 모아 `int[][]`로 바꾼다.

```java
import java.util.*;

class Solution {
    private static class Node {
        Node[] next = new Node[26];
        boolean end;
    }

    public int[][] indexPairs(String text, String[] words) {
        Node root = new Node();
        for (String w : words) {
            Node node = root;
            for (char ch : w.toCharArray()) {
                int c = ch - 'a';
                if (node.next[c] == null) node.next[c] = new Node();
                node = node.next[c];
            }
            node.end = true;
        }
        List<int[]> res = new ArrayList<>();
        for (int i = 0; i < text.length(); i++) {
            Node node = root;
            for (int j = i; j < text.length(); j++) {
                node = node.next[text.charAt(j) - 'a'];
                if (node == null) break;
                if (node.end) res.add(new int[]{i, j});
            }
        }
        return res.toArray(new int[0][]);
    }
}
```

세 언어 모두 예시에 `[[0,2],[3,5],[3,6],[4,5],[7,8]]`을, `aaaa`와 `[a, aa]`에 일곱 쌍을 냈다. Java에서 `res.toArray(new int[0][])`는 `List<int[]>`를 2차원 배열로 바꾸는 관용구다. 결과 개수를 미리 모르니 `ArrayList`에 모았다가 바꾼다.

## 텍스트를 한 번만 훑는 아호-코라식

트라이 풀이는 시작 위치마다 뿌리로 돌아간다. `thecatsat`에서 `i = 3`에 `c, a, t, s`까지 읽고, `i = 4`에서 다시 `a, t`를 읽는다. 이미 읽은 글자를 다시 읽는 것이다. 단어가 길고 텍스트에 단어의 앞부분이 자주 나오면 이 반복이 쌓인다.

아호-코라식(Aho-Corasick)은 트라이에 "막히면 어디로 갈지"를 미리 이어 둔다. 노드 `cat`에서 다음 글자가 단어로 이어지지 않으면, 처음부터 다시 시작하는 대신 "지금까지 읽은 `cat`의 뒷부분 중 트라이에 있는 가장 긴 앞부분"인 노드 `at`으로 건너간다. 이 연결을 실패 링크라고 한다. [KMP](/posts/string-search-algorithms)의 실패 함수를 단어 여러 개로 넓힌 것이다.

1. 단어로 트라이를 만든다.
2. 뿌리에서 BFS로 내려가며 노드마다 실패 링크를 정한다. 부모의 실패 링크를 따라가며 같은 글자 자식이 있는 곳을 찾는다.
3. 노드마다 "여기서 끝나는 단어들"을 모은다. 자기 끝 표시에 실패 링크 노드의 목록을 더한다. 노드 `cat`의 목록에는 `cat`과 실패 링크 `at`의 `at`이 모두 들어간다.
4. 텍스트를 왼쪽부터 한 글자씩 읽으며 상태를 옮긴다. 자식이 없으면 실패 링크를 따라 물러난다. 상태마다 목록의 단어를 "여기서 끝난다"로 적는다.

```js
function indexPairs(text, words) {
  // 상태 번호로 트라이를 만든다. out[s]는 상태 s에서 끝나는 단어의 길이들
  const next = [new Map()], fail = [0], out = [[]];
  for (const w of words) {
    let s = 0;
    for (const ch of w) {
      if (!next[s].has(ch)) {
        next.push(new Map()); fail.push(0); out.push([]);
        next[s].set(ch, next.length - 1);
      }
      s = next[s].get(ch);
    }
    out[s].push(w.length);
  }
  // BFS로 실패 링크를 정한다. 뿌리의 자식은 실패하면 뿌리로 간다
  const queue = [...next[0].values()];
  for (let qi = 0; qi < queue.length; qi++) {
    const s = queue[qi];
    for (const [ch, t] of next[s]) {
      let f = fail[s];
      while (f && !next[f].has(ch)) f = fail[f]; // 같은 글자로 이어지는 곳까지 물러난다
      fail[t] = next[f].has(ch) && next[f].get(ch) !== t ? next[f].get(ch) : 0;
      out[t] = out[t].concat(out[fail[t]]); // 실패 링크 쪽에서 끝나는 단어도 여기서 끝난다
      queue.push(t);
    }
  }
  // 텍스트를 한 번만 훑는다
  const res = [];
  let s = 0;
  for (let j = 0; j < text.length; j++) {
    while (s && !next[s].has(text[j])) s = fail[s];
    s = next[s].get(text[j]) ?? 0;
    for (const len of out[s]) res.push([j - len + 1, j]); // j에서 끝나는 단어들
  }
  // 끝 위치 순서로 쌓였으니 시작 위치 기준으로 다시 정렬한다
  res.sort((a, b) => a[0] - b[0] || a[1] - b[1]);
  return res;
}
```

같은 예시를 아호-코라식으로 훑어 보자. 실패 링크는 `ca → a`, `cat → at`, `at → t`이고 나머지는 모두 뿌리로 간다. 노드 `cat`의 끝 목록에는 실패 링크 덕분에 `cat`과 `at`이 함께 들어 있다. 기억 칸은 지금 상태와 이번 글자에서 끝난 단어다.

5번 칸에서 `[3,5]`와 `[4,5]`가 끝 위치 순서로 함께 나온다는 점을 보자. 트라이 풀이에서는 `[4,5]`가 `i = 4`일 때 따로 나왔다. 다섯 쌍이 나오는 순서는 `[0,2]`, `[3,5]`, `[4,5]`, `[3,6]`, `[7,8]`이라 `[4,5]`와 `[3,6]`의 순서가 문제가 원하는 것과 반대다.

트라이와 실패 링크를 만드는 데 O(D·L·σ)(σ는 글자 종류, 여기서는 Map이라 실제 자식 수만큼), 텍스트를 훑는 데 O(n + R)이다. 실패 링크를 따라 물러나는 횟수는 앞으로 나아간 횟수를 넘지 않아서 전체가 선형이다. 텍스트 글자를 정확히 한 번씩만 읽는다.

대신 답이 끝 위치 순서로 나온다. `thecatsat`에서 `j = 5`에 `cat`(`[3,5]`)과 `at`(`[4,5]`)이 함께 나오고, `j = 6`에 `cats`(`[3,6]`)가 나온다. 문제는 시작 위치 순서를 원하니 정렬이 필요하다. 시작 위치마다 버킷을 두고 넣으면 비교 정렬 없이 순서를 맞출 수 있다.

```js
// res: 끝 위치 순서로 나온 [i, j] 목록, n: 텍스트 길이
const buckets = Array.from({ length: n }, () => []);
for (const [i, j] of res) buckets[i].push(j); // 시작 위치별로 모은다
const sorted = [];
for (let i = 0; i < n; i++) for (const j of buckets[i]) sorted.push([i, j]);
```

끝 위치 순서로 읽으며 넣었으니 버킷 안의 `j`는 이미 오름차순이다. 그래서 버킷 안을 다시 정렬할 필요도 없고 전체가 O(n + R)이다.

이 문제 크기에서 아호-코라식은 지나치다. 하지만 "단어 1만 개를 100만 글자 텍스트에서 찾기"라는 꼬리 질문의 답이 이것이다. 금칙어 필터와 `grep -F`에 여러 패턴을 줄 때 쓰는 방식이다. 자세한 원리는 [문자열 검색 글의 아호-코라식 절](/posts/string-search-algorithms#찾을-단어가-수천-개일-때)에 있다.

## 텍스트를 10만 글자로 늘려 재 보면

제약 안에서는 차이가 없으니 텍스트를 10만 글자로 늘리고, 길이 1~6인 무작위 단어 20개로 Node.js 22에서 재 보았다. 모든 부분 문자열 풀이는 너무 느려서 5,000글자에서만 쟀다.

```text
                      a·b 두 글자 텍스트    26글자 텍스트
모든 부분 문자열       39587ms (5,000글자)  38662ms (5,000글자)
단어마다 indexOf          109.2ms             4.3ms
트라이                     20.8ms             5.7ms
아호-코라식                36.2ms             5.4ms
찾은 쌍 수               253151               8068
```

26글자 텍스트에서는 `indexOf`가 가장 빨랐다. 단어가 20개뿐이고, 엔진의 `indexOf`는 첫 글자가 맞는 곳을 빠르게 건너뛰며 찾는다. 트라이와 아호-코라식도 비슷한 수준이다.

`a`, `b` 두 글자 텍스트에서는 순서가 바뀐다. 짧은 단어가 거의 모든 자리에서 맞아서 찾은 쌍이 25만 개가 넘는다. `indexOf` 풀이는 단어마다 찾은 뒤 25만 개를 정렬하느라 109ms가 걸렸고, 트라이는 정렬 없이 21ms에 끝났다. 아호-코라식은 텍스트를 한 번만 읽지만 역시 정렬이 필요하고, 상태마다 `out` 목록을 훑는 비용이 있어 36ms였다.

단어가 20개뿐이라 아호-코라식의 장점이 드러나지 않았다. 단어가 수천 개로 늘면 `indexOf` 풀이는 텍스트를 수천 번 읽어야 하고, 트라이는 시작 위치마다 단어 길이만큼 다시 읽는다. 아호-코라식만 단어 수와 상관없이 텍스트를 한 번 읽는다.

## 네 풀이를 나란히 세우면

n은 텍스트 길이, D는 단어 수, L은 단어 최대 길이, R은 답의 개수다.

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 모든 부분 문자열을 집합에 묻기 | O(n³) | O(D·L) | n이 100 정도로 작을 때. 정렬이 필요 없다 |
| 단어마다 indexOf | O(D·n·L + R log R) | O(R) | 단어가 적을 때. 내장 함수가 빨라 실제로 가장 빠를 때가 많다 |
| 시작 위치마다 트라이 | O(D·L + n·L + R) | O(D·L + R) | 면접 기본 답. 정렬이 필요 없다 |
| 아호-코라식 | O(D·L + n + R) | O(D·L + R) | 단어가 수천 개이거나 텍스트가 스트림일 때 |

## 기본 정렬은 배열을 글자로 비교한다

`indexOf` 풀이나 아호-코라식처럼 정렬이 필요한 풀이에서 가장 흔한 실수는 비교 함수 없이 `sort()`를 부르는 것이다.

```js
const res = [[10, 11], [2, 3], [2, 2]];
res.sort(); // 비교 함수가 없다
// -> [[10,11],[2,2],[2,3]] (정답은 [[2,2],[2,3],[10,11]])
```

JS의 기본 `sort`는 원소를 문자열로 바꿔 비교한다. `[10, 11]`은 `"10,11"`, `[2, 3]`은 `"2,3"`이 되고, 첫 글자 `1`이 `2`보다 앞이라 `[10, 11]`이 맨 앞에 온다. 이 문제의 텍스트가 100글자라 위치가 두 자리가 되는 순간 걸린다. 위치가 한 자리인 예시로만 테스트하면 통과해 버려서 찾기 어렵다.

언어마다 다르다.

- Python의 `sorted`와 `list.sort`는 리스트를 원소별로 앞에서부터 비교해서 `[[2, 2], [2, 3], [10, 11]]`이 바르게 나온다. 기본 동작이 이 문제가 원하는 순서다.
- Java는 `int[]`에 기본 순서가 없어서 비교자 없이 정렬하면 `ClassCastException`이 난다. `res.sort((a, b) -> a[0] != b[0] ? a[0] - b[0] : a[1] - b[1])`처럼 비교자를 준다. 값이 작아 뺄셈 오버플로 걱정은 없지만, 큰 값이면 `Integer.compare`를 쓴다.

트라이 풀이는 처음부터 순서대로 쌓아서 이 함정을 피한다.

## 멈추거나 건너뛰면 겹친 단어를 놓친다

정렬 말고도 겹치는 등장을 놓치는 실수가 두 가지 있다. 하나는 위에서 본 `indexOf(w, i + w.length)`다. 다른 하나는 트라이에서 끝 표시를 만나면 멈추는 것이다.

```js
for (let j = i; j < text.length; j++) {
  node = node[text[j]];
  if (!node) break;
  if (node.end) { res.push([i, j]); break; } // 첫 단어에서 멈춘다
}
// thecatsat -> [[0,2],[3,5],[4,5],[7,8]] (cats의 [3,6]이 빠진다)
```

`cat`에서 멈추면 같은 자리에서 시작하는 더 긴 `cats`를 놓친다. [Replace Words](/posts/leetcode-replace-words)에서는 이게 정답 동작이었지만 여기서는 모든 단어를 원한다.

세 번째는 트라이 풀이에서 찾은 다음 `i`를 `j + 1`로 건너뛰는 것이다. 정규식의 전역 검색이 이렇게 동작한다.

```js
// 정규식 전역 검색은 찾은 자리 뒤에서 이어 찾는다
const re = /cats|cat|at|the/g;
[..."thecatsat".matchAll(re)].map((m) => [m.index, m.index + m[0].length - 1]);
// -> [[0,2],[3,6],[7,8]] (cat의 [3,5]와 at의 [4,5]가 빠진다)
```

정규식은 한 번 맞은 자리를 소비하고 그 뒤에서 이어 찾아서 겹치는 등장을 돌려주지 않는다. 또 같은 자리에서는 대안 중 먼저 맞는 것 하나만 고른다. 정규식으로 이 문제를 풀려면 단어마다 앞보기(`(?=(cat))`)를 써서 위치를 하나씩 옮겨야 하는데, 트라이보다 나을 게 없다.

## 단어가 수천 개이거나 텍스트가 흘러들어 오면

### 단어가 수천 개, 텍스트가 100만 글자라면

`indexOf` 풀이는 텍스트를 단어 수만큼 읽어서 O(D·n·L)로 커진다. 트라이는 O(n·L)로 단어 수와 상관없지만 L이 크면 같은 글자를 L번까지 다시 읽는다. 아호-코라식은 O(n + R)에 텍스트를 한 번만 읽는다. 단어 수가 많고 길수록 아호-코라식이 낫다.

### grep으로 찾아도 겹친 단어는 안 나온다

현장에서 "로그에서 금칙어 목록의 단어가 어디 나오나"를 볼 때 가장 먼저 쓰는 건 `grep -F`다. `-F`는 패턴을 정규식이 아닌 고정 문자열로 보고, `-f`로 파일에서 여러 패턴을 읽는다. GNU grep은 고정 문자열 여러 개를 이 글의 아호-코라식 계열 알고리즘으로 한꺼번에 찾는다.

```bash
# 찾을 단어를 한 줄에 하나씩 적는다
printf 'cat\ncats\nat\nthe\n' > words.txt
# -o: 맞은 부분만, -b: 바이트 위치, -F: 고정 문자열, -f: 패턴 파일
echo thecatsat | grep -o -b -F -f words.txt
```

```text
0:the
3:cats
7:at
```

GNU grep 3.11에서 돌린 결과다. 다섯 쌍 중 세 개만 나왔다. 3번 자리에서는 가장 긴 `cats` 하나만 고르고, 고른 자리 뒤에서 이어 찾으니 그 안의 `cat`과 `at`이 빠진다. `echo aaaa | grep -o -b -F -e aa`도 `0:aa`, `2:aa` 두 개만 낸다. 정규식 전역 검색과 같은 동작이다.

그래서 grep의 `-o` 결과로 "몇 번 나왔나"를 세면 겹치는 등장이 있을 때 적게 센다. 금칙어가 서로를 품는 목록(`cat`, `cats`)이거나 같은 글자가 반복되는 단어라면 이 차이가 실제 숫자로 드러난다. 겹친 것까지 모두 필요하면 이 글의 트라이나 아호-코라식처럼 모든 끝 위치를 내보내는 코드를 따로 쓴다.

### 텍스트가 스트림으로 들어온다면

아호-코라식이 그대로 맞는다. 상태 하나만 들고 글자가 들어올 때마다 옮기고, 끝나는 단어를 바로 내보낸다. 트라이 풀이는 시작 위치마다 앞으로 L글자를 봐야 해서 최근 L글자를 버퍼로 들고 있어야 한다.

### 대소문자를 무시하라면

트라이를 만들 때와 내려갈 때 모두 소문자로 바꿔 비교한다. 위치는 원래 텍스트 기준으로 적으니 바뀌지 않는다. 다만 독일어 `ß`처럼 대소문자를 바꾸면 길이가 달라지는 글자가 있는 언어에서는 위치가 어긋나니, 글자 하나씩 비교 규칙만 바꾸는 쪽이 안전하다.

### 겹치지 않게 가장 많이, 또는 가장 길게 덮으라면

찾은 `[i, j]` 목록이 구간 목록이 된다. 겹치지 않게 가장 많이 고르는 건 끝 위치 기준 탐욕([Non-overlapping Intervals](/posts/leetcode-non-overlapping-intervals)과 같은 방식)이고, 덮이는 글자를 가장 많이 만드는 건 [Extra Characters in a String](/posts/leetcode-extra-characters-in-a-string)의 DP다.

### 찾은 단어를 굵게 표시하라면

겹치거나 붙어 있는 구간을 합쳐 `<b>` 태그를 씌우는 616번 Add Bold Tag in String(프리미엄 문제)이 이 문제의 다음 단계다. 이 글의 `[i, j]` 목록을 만들고 [Merge Intervals](/posts/leetcode-merge-intervals)처럼 합치면 된다.

## 시작 위치마다 내려가면 순서도 따라온다

단어 목록을 트라이로 만들고, 텍스트의 시작 위치마다 뿌리에서 내려가며 끝 표시를 만날 때마다 `[i, j]`를 적는다. 끝 표시에서 멈추지 않고, 찾은 뒤에 건너뛰지 않아야 겹치는 단어를 모두 잡는다. 이렇게 하면 답이 정렬 순서로 쌓여 비교 함수의 함정도 피한다. 단어가 아주 많고 텍스트가 길면 텍스트를 한 번만 읽는 아호-코라식으로 넘어간다.

## 면접에서 나올 만한 질문

### 트라이를 쓰면 무엇이 좋아지나요?

단어 D개를 따로 찾지 않고, 시작 위치마다 한 번 내려가면서 그 위치에서 시작하는 모든 단어를 한꺼번에 찾는다. 단어의 앞부분이 아니게 되는 순간 멈추니 시작 위치마다 많아야 L칸이다. 그래서 O(n·L)로 단어 수와 상관없고, 답이 처음부터 정렬 순서로 쌓인다.

### 겹치는 단어는 어떻게 빠짐없이 찾나요?

두 가지를 지킨다. 같은 시작 위치에서는 끝 표시를 만나도 멈추지 않고 내려가서 `cat`과 `cats`를 모두 찾는다. 그리고 찾은 뒤 다음 시작 위치를 `j + 1`이 아니라 `i + 1`로 잡아서 `cat` 안의 `at`도 찾는다. 정규식 전역 검색은 두 번째를 지키지 않아서 이 문제에 맞지 않는다.

### indexOf로 풀면 무엇을 조심해야 하나요?

다음 검색을 `i + w.length`가 아니라 `i + 1`부터 해야 겹치는 등장을 찾는다. 그리고 단어 순서대로 쌓인 결과를 시작 위치, 끝 위치 순으로 정렬해야 하는데, JS 기본 `sort`는 배열을 문자열로 비교해서 `[10, 11]`을 `[2, 3]`보다 앞에 둔다. 비교 함수를 꼭 준다.

### 시간과 공간 복잡도는요?

트라이 풀이는 만드는 데 O(D·L), 찾는 데 O(n·L), 답을 적는 데 O(R)이다. 공간은 트라이 노드 O(D·L)과 답 O(R)이다. 이 문제 크기에서는 몇천 번 연산이다.

### 단어가 아주 많고 텍스트가 길다면요?

아호-코라식을 쓴다. 트라이에 실패 링크를 이어 두면 막혔을 때 뿌리로 돌아가지 않고 지금까지 읽은 글자의 뒷부분으로 건너가서, 텍스트를 정확히 한 번만 읽는다. 시간은 O(n + 단어 글자 수 합 + R)이다. 답이 끝 위치 순서로 나오니 시작 위치 순으로 다시 정렬하거나 버킷에 넣는다.

### 답이 몇 개까지 나올 수 있나요?

시작 위치마다 단어가 많아야 L개(길이마다 하나)라 R은 O(n·L) 이하이고, 단어 수 D로도 막혀 O(n·min(D, L))이다. `aaaa…`에 `a`, `aa`, `aaa`처럼 같은 글자 단어를 주면 거의 모든 자리에서 모든 단어가 맞아 이 상한에 가까워진다. 그래서 어떤 풀이든 답 크기 O(R)은 피할 수 없다.

### 정규식이나 grep으로 풀면 안 되나요?

그대로는 안 된다. 정규식 전역 검색과 `grep -o`는 한 번 맞은 자리를 소비하고 그 뒤에서 이어 찾아서 겹치는 등장을 돌려주지 않는다. 같은 자리에서도 하나만 고른다. `thecatsat`에서 다섯 쌍 중 세 쌍만 나오는 이유다. 앞보기로 위치를 하나씩 옮기며 단어마다 찾을 수는 있지만, 트라이보다 복잡하고 느리다.
