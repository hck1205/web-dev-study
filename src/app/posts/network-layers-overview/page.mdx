배포 직후 장애 채널에 이런 말들이 오간다고 해 보자. "로드 밸런서 L4 헬스 체크는 통과하는데 L7에서 502가 나요." "보안 그룹은 L4라서 443만 열려 있으면 돼요." "VPN 붙은 사람만 큰 파일이 안 받아지는데, L3 쪽 MTU 같아요." 세 문장 모두 숫자 하나로 문제가 어디쯤에 있는지 말하고 있다. 이 숫자가 무슨 뜻인지 모르면 대화에 끼어들 수 없고, 알면 어디부터 봐야 할지가 바로 정해진다.

그 숫자의 출처가 네트워크 계층 모델이다. 학교에서는 OSI 7계층을 외우고 시험이 끝나면 잊어버리기 쉬운데, 현장에서는 이 번호가 공용어로 쓰인다. 이 글은 왜 통신을 층으로 나눠서 보는지, 데이터가 층을 지나며 어떻게 포장되고 풀리는지를 실제 패킷 한 장으로 확인하고, OSI 7계층과 TCP/IP 4계층이 어떻게 겹치는지, 그리고 "L4", "L7"이라는 말이 실무에서 정확히 무엇을 가리키는지까지 본다. 각 층의 자세한 이야기는 뒤에 이어지는 글들에서 하나씩 다룬다.

이 글의 출력은 Ubuntu 24.04 컨테이너 안에 network namespace로 만든 작은 망에서 직접 찍었다. 노트북 역할(`10.0.1.10`) — 라우터 두 대 — 서버 역할(`10.0.4.20`, 80번 포트에 Python HTTP 서버)로 이어진 구조다. 같은 망을 만드는 명령은 [라우팅 글](/posts/layer-ip-routing-icmp)에 있다.

## 한 덩어리로 만들면 아무것도 못 바꾼다

웹 브라우저가 서버에서 페이지 하나를 받아 오는 일을 한 프로그램이 처음부터 끝까지 다 맡는다고 생각해 보자. 그 프로그램은 랜선에 전압을 어떻게 싣는지, Wi-Fi 전파를 어떻게 쏘는지, 지구 반대편까지 어느 길로 갈지, 중간에 빠진 조각을 어떻게 다시 보낼지, 받은 바이트가 HTML인지 이미지인지까지 모두 알아야 한다. 사용자가 랜선을 뽑고 Wi-Fi로 갈아타면 브라우저를 새로 만들어야 한다.

계층 모델은 이 일을 층으로 자른다. 층마다 맡은 일이 하나씩 있고, 각 층은 바로 아래층이 제공하는 기능만 믿고 쓴다. 브라우저는 "이 바이트를 저 주소의 80번 포트로 순서대로 빠짐없이 보내 줘"라고 운영체제에 부탁할 뿐, 그 바이트가 랜선으로 가는지 Wi-Fi로 가는지 모른다. 그래서 아래층을 통째로 바꿔도 위층은 그대로 돈다. 이더넷이 Wi-Fi로 바뀌어도, IPv4가 IPv6로 바뀌어도 HTTP는 같은 모양으로 오간다. 반대로 HTTP/1.1이 HTTP/2로 바뀌어도 라우터는 아무것도 몰라도 된다.

층을 나누면 생기는 또 하나의 성질이 있다. 같은 층끼리는 같은 언어로 말한다. 내 컴퓨터의 TCP는 서버의 TCP와, 내 브라우저의 HTTP는 서버의 HTTP와 대화한다. 실제로 데이터는 아래로 내려가 선을 타고 건너간 뒤 다시 위로 올라가지만, 각 층 입장에서는 상대편의 같은 층과 직접 이야기하는 것처럼 보인다. 이 약속 하나하나를 프로토콜이라고 부른다.

## 봉투 안에 봉투

층을 지날 때 데이터에 일어나는 일은 편지를 봉투에 넣는 것과 닮았다. 이 글에서는 끝까지 이 비유로 간다. 위층이 넘겨준 내용물을 아래층이 자기 봉투에 넣고, 봉투 겉면에 자기 층에 필요한 정보만 적는다. 이걸 캡슐화(encapsulation)라고 한다. 받는 쪽은 반대로 바깥 봉투부터 하나씩 뜯는다. 이걸 역캡슐화(decapsulation)라고 한다.

봉투 겉면이 헤더다. TCP 봉투에는 포트 번호와 순서 번호를, IP 봉투에는 출발지·목적지 IP와 남은 수명(TTL)을, 이더넷 봉투에는 이번 구간에서 받을 기기의 MAC 주소를 적는다. 아래 그림에서 다음을 누르면 `GET /` 요청 한 줄이 봉투에 싸여 내려갔다가 서버에서 풀리는 과정을 따라간다. 오른쪽에 쌓이는 것이 지금 데이터가 입고 있는 봉투다. 왼쪽이 가장 바깥이다.

## 실제 프레임 한 장을 벗겨 보면

비유가 아니라 진짜 봉투를 보자. 노트북 역할의 namespace에서 서버로 `curl`을 보내면서 tcpdump로 연결의 첫 패킷(SYN)을 잡았다. `-e`는 이더넷 헤더까지 보여 주고, `-XX`는 프레임 전체를 16진수로 찍는다.

```bash
# 이더넷 헤더까지(-e), 이름 변환 없이(-nn), 자세히(-v), 프레임 전체 hex(-XX), SYN 하나만 잡는다
sudo tcpdump -i eth0 -e -nn -v -XX -c 1 'tcp[tcpflags] == tcp-syn'

# 다른 터미널에서 요청을 보낸다
curl -s -o /dev/null http://10.0.4.20/
```


74바이트가 세 겹으로 되어 있다. 맨 앞 14바이트가 이더넷 봉투다. `da5b f482 3b98`이 받는 쪽 MAC, `8ee8 858b d1aa`가 보내는 쪽 MAC, 그다음 `0800`이 "안에 든 건 IPv4"라는 표시다. 이어지는 20바이트가 IP 봉투다. 첫 바이트 `45`는 버전 4에 헤더 길이 5×4=20바이트라는 뜻이고, `40`은 TTL 64, `06`은 "안에 든 건 TCP", 마지막 8바이트 `0a00 010a`와 `0a00 0414`가 10.0.1.10과 10.0.4.20이다. 남은 40바이트가 TCP 봉투다. `a068`이 출발 포트 41064, `0050`이 목적지 포트 80이고, 뒤쪽의 `0204 05b4`는 MSS 1460을 알리는 옵션이다. SYN은 내용물 없이 봉투만 보내는 패킷이라 HTTP 바이트는 아직 없다.

`cksum ... (incorrect -> ...)`는 고장이 아니다. 요즘 리눅스는 체크섬 계산을 랜 카드(여기서는 가상 카드)에 맡겨서, 커널이 tcpdump에 넘기는 시점에는 아직 값이 비어 있다. 보내는 쪽에서 캡처하면 흔히 보이는 표시다.

각 봉투에는 "안에 무엇이 들었는지"를 알리는 칸이 하나씩 있다. 이더넷의 `0x0800`, IP의 `6`, TCP의 목적지 포트 `80`이 그 칸이다. 받는 쪽은 이 값을 보고 봉투를 뜯은 내용물을 어느 처리기로 넘길지 정한다. 계층이 서로를 모르면서도 이어지는 방법이 이것이다. 같은 연결을 `-e`만 주고 한 줄씩 보면 tcpdump가 이 세 겹을 한 줄에 펼쳐 준다. 조각을 눌러 보면 각 부분이 어느 층의 봉투에서 나왔는지 나온다.

## 층마다 데이터를 부르는 이름

봉투를 몇 겹 입었느냐에 따라 같은 데이터를 다른 이름으로 부른다. 이걸 PDU(Protocol Data Unit)라고 한다. 면접에서도, 로그를 읽을 때도 이 이름이 층을 가리키는 신호가 된다.

- L2의 단위는 프레임(frame)이다. 이더넷 헤더와 끝의 FCS까지 포함한다. "프레임 드롭"이라고 하면 랜 카드나 스위치 이야기다.
- L3의 단위는 패킷(packet)이다. IP 헤더부터 끝까지다. "패킷 로스"라는 말은 엄밀히 L3 이야기지만 실무에서는 층을 가리지 않고 쓴다.
- L4의 단위는 TCP면 세그먼트(segment), UDP면 데이터그램(datagram)이다.
- L7은 메시지(message)나 그냥 데이터라고 부른다. HTTP 요청 하나, DNS 질의 하나가 여기에 해당한다.
- L1은 단위가 아니라 비트의 흐름이다.

주소도 층마다 다르다. L2는 MAC 주소로 같은 링크 안의 기기를, L3는 IP 주소로 인터넷 전체에서 호스트를, L4는 포트로 호스트 안의 프로그램을 가리킨다. 세 주소가 왜 다 필요한지는 시리즈를 따라가면 하나씩 풀린다. MAC과 ARP는 [데이터 링크 글](/posts/layer-link-ethernet-arp), IP와 서브넷은 [IP 주소 글](/posts/layer-ip-addressing), 포트는 [포트와 소켓 글](/posts/ports-and-sockets)에서 본다.

봉투가 겹칠수록 실제 내용물에 비해 선을 타는 바이트가 늘어난다. 앞의 캡처에서 72바이트짜리 `GET` 요청은 138바이트 프레임으로 나갔다. TCP 헤더가 옵션(타임스탬프) 12바이트를 포함해 32바이트였기 때문이다. 아래 함수에 내용물 크기와 TCP 옵션 크기를 넣으면 캡처에 찍힌 프레임 길이가 나오게 만들어 보자. 테스트의 기대값은 모두 위 실습 캡처에 실제로 찍힌 `length` 값이다.

## 일곱 층과 네 층

계층을 나누는 방법으로 두 가지가 유명하다. OSI 7계층은 국제표준화기구(ISO)가 1980년대에 만든 참조 모델이다. 실제로 쓰려고 만든 OSI 프로토콜 묶음은 거의 살아남지 못했지만, 층을 부르는 번호는 공용어로 남았다. TCP/IP 4계층은 인터넷이 실제로 돌아가는 방식을 정리한 모델로, RFC 1122(1989)가 링크·인터넷·전송·응용 네 층으로 나눴다. 교과서에 따라 링크 계층을 물리와 데이터 링크로 쪼개 5계층으로 설명하기도 한다.

| OSI 7계층 | 하는 일 | TCP/IP 4계층 | 대표 프로토콜·장비 |
|---|---|---|---|
| 7 응용 | 사용자 프로그램이 쓰는 규칙 | 응용 | HTTP, DNS, SMTP, SSH |
| 6 표현 | 인코딩, 압축, 암호화 | 응용 | (TLS, UTF-8, gzip이 이 자리에 걸쳐 있다) |
| 5 세션 | 대화의 시작과 끝, 재개 | 응용 | (따로 떨어진 프로토콜은 드물다) |
| 4 전송 | 프로세스 간 전달, 신뢰성 | 전송 | TCP, UDP, QUIC |
| 3 네트워크 | 망과 망 사이의 주소와 길 찾기 | 인터넷 | IP, ICMP · 라우터 |
| 2 데이터 링크 | 같은 링크 안에서의 전달 | 링크 | 이더넷, Wi-Fi, ARP · 스위치 |
| 1 물리 | 비트를 신호로 | 링크 | 케이블, 전파, 광 |

표에서 보이듯 두 모델은 아래쪽 네 층(1~4)과 번호가 거의 그대로 맞는다. 차이는 위쪽이다. TCP/IP는 OSI의 5·6·7을 응용 계층 하나로 묶었다. 세션 관리, 인코딩, 암호화를 실제 인터넷에서는 대개 응용 프로그램이나 그 안의 라이브러리가 함께 처리했기 때문이다. 그래서 TLS가 몇 계층이냐는 질문에는 깔끔한 답이 없다. TCP 위, HTTP 아래에 있으니 OSI로 치면 5~6계층 언저리지만, TCP/IP 모델에서는 응용 계층에 속한다. 이 세 층이 어디로 갔는지는 [세션·표현·응용 계층 글](/posts/upper-layers-session-presentation-app)에서 따로 다룬다.

실무에서 "L3", "L4", "L7"이라고 할 때는 OSI 번호를 쓴다. TCP/IP 모델에는 3·7이라는 번호가 없는데도 그렇다. "L5", "L6"이라는 말은 거의 들을 일이 없다.

## L4, L7이라고 부를 때

실무에서 계층 번호는 대개 "이 장비나 서비스가 패킷의 어디까지 읽고 판단하느냐"를 말한다. 읽는 깊이가 곧 할 수 있는 일의 범위다.

- L2 스위치는 MAC 주소로 같은 망 안에서 프레임을 나른다. VLAN으로 망을 나누는 것도 여기다.
- L3 장비(라우터, L3 스위치)는 IP 주소로 망과 망 사이를 잇는다. 클라우드의 라우트 테이블, VPC 피어링이 이 층의 일이다.
- L4 장비는 IP와 포트까지 본다. "10.0.4.20의 443번으로 오는 TCP"를 기준으로 나누거나 막는다. AWS의 NLB, 보안 그룹, `iptables`의 포트 규칙이 여기에 속한다. HTTP 내용을 읽지 않으니 빠르고 프로토콜을 가리지 않지만, 경로(`/api`)나 쿠키로 나눌 수는 없다.
- L7 장비는 응용 계층 메시지를 끝까지 읽는다. HTTP의 Host, 경로, 헤더, 쿠키로 판단하고, 응답 코드를 만들어 내기도 한다. AWS ALB, Nginx 같은 리버스 프록시, API 게이트웨이, WAF가 여기다. HTTPS라면 내용을 읽기 위해 이 장비에서 TLS를 풀어야 한다.

요청 하나가 서비스에 닿기까지 지나는 장비를 층으로 표시하면 이렇게 된다. 점이 흐르는 방향이 요청의 방향이고, 노드 아래 작은 글씨가 그 장비가 읽는 깊이다.

## 현장에서 계층 번호가 쓰이는 순간

계층 모델이 가장 쓸모 있는 건 장애를 좁힐 때다. 위층은 아래층이 멀쩡하다고 믿고 돌기 때문에, 아래층이 깨지면 위층에서는 엉뚱한 증상으로 나타난다. 그래서 증상이 어느 층에서 나온 말인지 알아보는 눈이 필요하다. 실습 망에서 층마다 하나씩 일부러 고장을 내고 메시지를 받아 봤다.

```bash
# L1·L2: 링크가 살아 있는지. 스위치 쪽 포트를 내린 상태에서 확인했다
ip -br link
```

```text
lo               DOWN           00:00:00:00:00:00 <LOOPBACK>
vh1@if9          DOWN           9a:e2:a1:3d:20:1b <NO-CARRIER,BROADCAST,MULTICAST,UP>
```

`NO-CARRIER`는 케이블 건너편에서 신호가 오지 않는다는 뜻이다. 인터페이스를 켜 둔(`UP`) 상태여도 상대가 없으면 이렇게 나온다. 이 상태에서는 위층에서 무엇을 해도 소용없다. ping도 아무 메시지 없이 100% 손실로 끝났다.

```bash
# L3: 목적지로 가는 경로가 있는지. 기본 게이트웨이가 없는 호스트에서 쳤다
ping -c 1 8.8.8.8
```

```text
ping: connect: Network is unreachable
```

패킷을 하나도 내보내지 않고 내 컴퓨터 안에서 바로 실패했다. 라우팅 테이블에 그 주소로 가는 길이 없다는 L3 메시지다. 경로를 읽는 법은 [라우팅 글](/posts/layer-ip-routing-icmp)에서 본다.

```bash
# L4: 포트에서 누가 받고 있는지
nc -zv -w 2 10.0.4.20 81
```

```text
nc: connect to 10.0.4.20 port 81 (tcp) failed: Connection refused
```

```text
nc: connect to 10.0.4.20 port 81 (tcp) timed out: Operation now in progress
```

둘 다 81번 포트 연결 실패인데 뜻이 다르다. `Connection refused`는 서버까지 패킷이 갔고 서버 커널이 "그 포트에는 아무도 없다"고 RST로 바로 답한 것이다. L3 경로는 멀쩡하고, L4에서 듣는 프로그램이 없다. `timed out`은 서버에 iptables로 81번을 DROP하게 해 둔 뒤 받은 메시지다. 패킷이 중간 어딘가에서 조용히 사라졌다는 뜻이라 방화벽이나 경로를 의심한다. 응답이 바로 왔는지, 기다리다 끝났는지가 층을 가르는 단서가 된다.

```bash
# L7: 연결은 되는데 응용 계층이 거절한다
curl -s -o /dev/null -w "%{http_code}\n" http://10.0.4.20/nope
```

```text
404
```

여기까지 왔다면 L1~L4는 모두 정상이다. TCP 연결이 맺어졌고 HTTP 응답까지 받았으니, 남은 문제는 응용의 일이다. 502나 504처럼 프록시가 만들어 내는 코드는 "앞단과의 L7은 정상인데 뒤쪽과의 연결 어딘가가 문제"라는 뜻이라 다시 한 층씩 내려가며 본다. 이 내용은 [HTTP 상태 코드 글](/posts/http-status-codes)과 [Nginx 리버스 프록시 글](/posts/nginx-reverse-proxy)에 있다.

이렇게 아래층부터 하나씩 확인하면 "네트워크가 이상해요"라는 막연한 말이 "L3 경로는 있는데 L4에서 RST가 온다"처럼 구체적인 문장으로 바뀐다. 층마다 어떤 명령으로 확인하고 다음에 무엇을 볼지를 한 장의 순서로 정리한 건 [계층별 장애 좁히기 글](/posts/network-troubleshooting-by-layer), 실제 패킷을 눈으로 확인하는 법은 [tcpdump 글](/posts/packet-capture-tcpdump)에 있다.

흔한 실수도 이 그림에서 나온다. ping이 된다고 서비스가 된다고 결론 내리는 것은 L3만 보고 L4·L7을 건너뛴 것이다. 반대로 ping이 안 된다고 서버가 죽었다고 하는 것도 성급하다. ICMP만 막아 둔 서버가 많다. 실습 망에서 서버가 ICMP echo를 버리게 하자 ping은 100% 손실이었지만 `nc -zv 10.0.4.20 80`은 `succeeded!`, `curl`은 `200 OK`를 받았다.

## 층이 깔끔하게 나뉘지 않는 곳

계층 모델은 지도이지 법이 아니다. 실제 프로토콜은 여기저기서 층을 넘나든다. 면접에서 "계층이 정말 독립적이냐"는 꼬리 질문이 나오면 이런 예를 들 수 있다.

TCP의 체크섬은 TCP 헤더만이 아니라 IP 주소가 든 가짜 헤더(pseudo-header)까지 넣고 계산한다. L4가 L3의 주소를 알고 있는 셈이라, NAT 장비는 IP 주소를 바꿀 때 TCP 체크섬도 고쳐야 한다. 앞의 캡처에서 본 MSS도 그렇다. TCP가 한 번에 보낼 크기를 L2의 MTU에 맞춰 정한다. 이 경계가 어긋나면 큰 패킷만 사라지는 장애가 나는데, [MTU 글](/posts/layer-mtu-fragmentation)에서 실제로 재현해 본다.

ARP는 IP 주소로 MAC 주소를 찾는 프로토콜이라 L2와 L3 사이에 끼어 있고, ICMP는 IP 위에 실려 가지만 IP 자체의 오류를 알리는 L3 프로토콜로 친다. QUIC은 UDP(L4) 위에서 신뢰성과 암호화까지 다시 구현해서 전송 계층 역할을 응용 영역에서 한다. 로드 밸런서는 L4라고 불러도 소스 IP를 남기기 위해 PROXY protocol 같은 L7 비슷한 정보를 덧붙이기도 한다. 층 번호는 "주로 무엇을 보느냐"를 말하는 이름표로 쓰면 된다.

## 층을 나눠 보는 이유

통신을 층으로 나누면 각 층이 한 가지 일만 맡고, 바로 아래층의 기능만 믿고 쓴다. 보내는 쪽은 내려가며 헤더 봉투를 하나씩 씌우고, 받는 쪽은 바깥부터 벗기며, 중간 장비는 자기 층까지만 뜯어 본다. 스위치는 MAC, 라우터는 IP, L4 장비는 포트, L7 장비는 HTTP 내용까지 읽는다. 장애가 나면 이 순서를 뒤집어 아래층부터 확인한다. 이 그림 하나가 있으면 "L4는 되는데 L7이 안 된다"는 말이 바로 다음에 볼 곳을 알려 준다.

## 면접에서 나올 만한 질문

### 네트워크를 왜 계층으로 나누나요?

각 층이 맡은 일을 분리해서 서로 독립적으로 바꿀 수 있게 하려는 것이다. 위층은 아래층이 제공하는 기능만 쓰기 때문에 이더넷을 Wi-Fi로, IPv4를 IPv6로 바꿔도 HTTP는 그대로 동작한다. 같은 층끼리 프로토콜로 대화하니 장비와 소프트웨어를 여러 회사가 따로 만들어도 서로 통한다. 장애가 났을 때 층별로 나눠 확인할 수 있다는 것도 실무에서 큰 이점이다.

### 캡슐화와 역캡슐화를 설명해 주세요.

보내는 쪽에서 데이터가 아래층으로 내려갈 때마다 그 층의 헤더가 앞에 붙는 것이 캡슐화다. HTTP 메시지에 TCP 헤더가 붙어 세그먼트, IP 헤더가 붙어 패킷, 이더넷 헤더와 FCS가 붙어 프레임이 된다. 받는 쪽은 바깥 헤더부터 떼어 내며 올라가는데, 각 헤더의 EtherType, 프로토콜 번호, 포트 같은 칸을 보고 다음에 넘길 처리기를 고른다.

### OSI 7계층과 TCP/IP 4계층은 어떻게 다른가요?

OSI는 ISO가 만든 7층짜리 참조 모델이고, TCP/IP는 실제 인터넷 프로토콜을 기준으로 링크·인터넷·전송·응용 4층으로 정리한 모델이다. 아래쪽은 거의 일대일로 맞고, OSI의 세션·표현·응용 계층이 TCP/IP에서는 응용 계층 하나로 합쳐졌다. 실제로 돌아가는 건 TCP/IP지만 실무에서 L3, L4, L7처럼 층을 부를 때는 OSI 번호를 쓴다.

### 스위치와 라우터는 각각 몇 계층 장비이고, 패킷을 지날 때 무엇을 바꾸나요?

스위치는 L2 장비라서 이더넷 헤더의 MAC 주소만 보고 프레임을 해당 포트로 내보내며, 프레임을 고치지 않는다. 라우터는 L3 장비라서 IP 목적지를 보고 다음 구간을 고르고, TTL을 하나 줄이고, 이더넷 헤더를 다음 구간용으로 새로 단다. IP 주소와 TCP 포트는 그대로 둔다. NAT를 하는 장비는 예외로 IP와 포트까지 바꾼다.

### L4 로드 밸런서와 L7 로드 밸런서의 차이는 무엇인가요?

L4는 IP와 포트까지만 보고 TCP·UDP 연결 단위로 분배하고, L7은 HTTP 메시지를 읽어서 Host, 경로, 헤더, 쿠키로 분배한다. L4는 내용을 해석하지 않아 빠르고 어떤 프로토콜이든 넘길 수 있지만 경로 기반 라우팅이나 헤더 추가는 못 한다. L7은 기능이 많은 대신 HTTPS라면 그 장비에서 TLS를 풀어야 하고, 연결을 끊었다 새로 맺기 때문에 앱에는 로드 밸런서 IP가 보여 X-Forwarded-For 같은 헤더가 필요하다.

### TLS는 몇 계층인가요?

한 층으로 딱 떨어지지 않는다. TCP 위, HTTP 아래에서 암호화와 인증을 맡으니 OSI로 치면 표현·세션 계층에 가깝고, TCP/IP 모델에서는 응용 계층에 속한다. 실무에서는 "TLS를 어디서 종료하느냐"가 더 중요한 질문인데, L7 장비가 HTTP를 읽으려면 그 장비에서 TLS를 풀어야 하기 때문이다.

### "Connection refused"와 "timed out"은 어느 계층의 문제로 보나요?

Connection refused는 패킷이 서버까지 도착했고 서버 커널이 RST로 답한 것이라 L3 경로는 정상이고 L4에서 그 포트를 듣는 프로세스가 없다는 뜻이다. timed out은 응답이 아예 없었다는 뜻이라 중간 방화벽의 DROP, 라우팅 문제, 서버 다운처럼 더 아래층이나 경로 위를 의심한다. 그래서 refused면 서버에서 프로세스와 바인드 주소를 보고, timeout이면 방화벽 규칙과 경로부터 본다.

### 계층이 완전히 독립적이지 않은 예를 들어 보세요.

TCP 체크섬은 IP 주소가 든 가짜 헤더까지 포함해 계산하므로 NAT가 IP를 바꾸면 TCP 체크섬도 고쳐야 한다. TCP의 MSS는 아래 링크의 MTU에 맞춰 정해지고, 이게 어긋나면 큰 패킷만 사라지는 장애가 난다. ARP는 L3 주소로 L2 주소를 찾는 프로토콜이라 두 층 사이에 걸쳐 있고, QUIC은 UDP 위에서 전송 계층의 일을 다시 구현한다.
