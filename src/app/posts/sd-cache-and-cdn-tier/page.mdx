지금까지 만든 맛집 리뷰 앱은 로드 밸런서 뒤에 웹 서버 두 대, 쓰기를 받는 DB 한 대와 읽기를 나눠 받는 복제본 두 대로 돌아간다. 앱을 열면 첫 화면에 "이번 주 인기 맛집 10곳"이 뜬다. 이 목록을 만들려면 최근 7일 리뷰를 식당별로 세고 평균 별점을 구해서 정렬해야 한다.

저녁 시간에 앱을 여는 사람이 초당 2,000명이면 이 집계 쿼리도 초당 2,000번 돈다. 그런데 2,000번 모두 답이 같다. 1초 사이에 순위가 바뀔 일은 거의 없다. 복제본을 더 붙여서 버틸 수도 있지만, 같은 답을 매번 다시 계산하는 일 자체를 줄이는 편이 훨씬 싸다.

화면에는 식당 사진도 수십 장 들어간다. 사진 한 장이 300KB면 첫 화면 하나에 수 MB가 웹 서버에서 나간다. 이 바이트들은 사용자가 누구든 똑같다.

이 글은 이 두 가지 낭비를 줄이는 장치를 붙인다. 자주 읽는 데이터는 메모리에 잠깐 들고 있는 캐시 계층에, 모두에게 똑같은 파일은 사용자 가까이에 사본을 두는 CDN에 맡긴다.

## 같은 답을 초당 2,000번 계산한다

캐시(cache)는 한 번 구한 결과를 빨리 꺼낼 수 있는 곳에 잠깐 놓아 두는 저장소다. 시스템 설계에서 "캐시 계층"이라고 하면 보통 웹 서버와 DB 사이에 두는 메모리 기반 키-값 저장소를 말한다. Redis나 Memcached가 대표적이다. 키-값 저장소는 이름(키)으로 값을 넣고 꺼내는 것만 잘하는 저장소라고 생각하면 된다.

메모리에서 키 하나로 값을 꺼내는 일과, 디스크와 메모리를 오가며 수십만 줄을 세는 일은 들어가는 일의 양이 다르다. 직접 재 봤다. 리뷰 30만 줄을 넣은 PostgreSQL(브라우저와 Node에서 도는 WASM 버전인 PGlite)과 로컬 Redis 7.0을 두고, 인기 맛집 쿼리를 캐시 앞뒤로 네 번 불렀다.

```js
// cache-aside.mjs 일부. db는 PGlite, redis는 node-redis 클라이언트
const SQL = `SELECT restaurant_id, count(*) AS reviews, round(avg(rating), 2) AS avg
             FROM reviews WHERE created_at > now() - interval '7 days'
             GROUP BY restaurant_id ORDER BY reviews DESC, restaurant_id LIMIT 10`;

async function getPopular() {
  const cached = await redis.get("popular:today");        // 1. 캐시를 먼저 본다
  if (cached) return { from: "cache", rows: JSON.parse(cached) };
  const { rows } = await db.query(SQL);                   // 2. 없으면 DB에서 계산
  await redis.set("popular:today", JSON.stringify(rows), { EX: 60 }); // 3. 60초 동안 넣어 둔다
  return { from: "db", rows };
}
```

```text
request 1: from=db    105.64 ms  top=1
request 2: from=cache 0.64 ms  top=1
request 3: from=cache 0.28 ms  top=1
request 4: from=cache 0.39 ms  top=1
TTL left: 60 s
```

첫 요청은 캐시에 아무것도 없어서 DB가 계산했고 105ms가 걸렸다. 그 결과를 Redis에 넣어 둔 뒤 세 번은 1ms도 안 걸렸다. PGlite는 진짜 PostgreSQL 서버보다 느려서 105라는 숫자 자체는 의미가 크지 않다. 봐야 할 것은 두 경로가 수백 배 차이 난다는 것, 그리고 DB가 이 쿼리를 60초에 한 번만 계산하면 된다는 것이다. 초당 2,000번이던 집계가 1분에 한 번으로 줄었다.

마지막 줄의 TTL(Time To Live)은 "이 값을 몇 초 동안 믿을지"다. 60초가 지나면 Redis가 값을 지우고, 그다음 요청이 다시 DB에서 계산해 채운다. TTL은 뒤에서 따로 다룬다.

## 캐시에 없을 때와 있을 때

## 어떤 데이터를 캐시에 둘까

캐시에 두기 좋은 데이터는 자주 읽히고 드물게 바뀌는 데이터다. 인기 맛집 목록, 식당 기본 정보, 메뉴판, 카테고리 목록이 여기에 든다. 반대로 매번 정확해야 하고 자주 바뀌는 값, 예를 들어 예약 가능한 좌석 수나 포인트 잔액은 캐시에서 읽어 결정을 내리면 사고가 난다. 화면에 "대략" 보여 주는 용도로만 쓰고, 실제 차감은 DB에서 한다.

캐시가 얼마나 일하는지는 히트율(hit rate)로 본다. 읽기 요청 중 캐시에서 끝난 비율이다. 히트율이 90%면 읽기 10개 중 1개만 DB로 간다. 99%면 100개 중 1개다. 숫자 몇 개만 바꿔 보면 감이 온다.

쓰기는 캐시가 막아 주지 못한다는 점도 같이 넣어야 한다. 리뷰를 새로 쓰는 요청은 히트율과 상관없이 전부 DB(프라이머리)로 간다. 아래 함수를 완성해 보자. 초당 읽기 수, 초당 쓰기 수, 히트율을 받아 DB가 초당 받는 요청 수를 돌려준다. 소수 계산 오차를 없애려고 읽기 쪽은 반올림한다.

## 캐시는 언제까지 믿을까: TTL

캐시는 DB의 사본이다. 사본은 원본이 바뀌어도 저절로 따라 바뀌지 않는다. 식당 사장님이 영업시간을 바꿨는데 앱에는 옛 시간이 뜨는 장면을 직접 만들어 봤다. DB 대신 `Map`을 쓰고, TTL은 3초로 짧게 줬다.

```js
// stale.mjs 일부
async function read(key) {
  const hit = await redis.get(key);
  if (hit) return `cache: ${hit}`;
  const v = db.get(key); await redis.set(key, v, { EX: 3 });   // TTL 3초
  return `db   : ${v}`;
}
```

```text
0.0s db   : 영업시간 11:00-21:00
0.0s DB updated
0.0s cache: 영업시간 11:00-21:00  <- 옛 값
3.1s db   : 영업시간 11:00-23:00  <- TTL이 지나 새로 읽음
3.1s DB updated + cache key deleted
3.1s db   : 영업시간 12:00-22:00
```

세 번째 줄에서 DB는 이미 23시인데 캐시는 21시라고 답한다. TTL이 끝난 3.1초에야 새 값이 나왔다. 마지막 두 줄은 다른 방법이다. DB를 고칠 때 캐시 키를 같이 지웠더니, 바로 다음 읽기가 DB에서 새 값을 가져왔다.

그래서 TTL은 "이 데이터가 얼마나 낡아도 괜찮은가"로 정한다. 인기 순위는 몇 분 늦어도 아무도 모른다. 영업시간은 몇 분 늦으면 헛걸음하는 사람이 생긴다. 그래서 순위는 TTL 5분에 기대고, 영업시간은 고칠 때 캐시 키를 지우고 TTL은 안전망으로 길게(예: 1시간) 둔다. TTL을 아예 안 주면 지우는 코드가 한 번만 빠져도 옛 값이 영원히 남는다. 안전망으로라도 TTL은 늘 준다.

캐시와 DB를 하나의 트랜잭션으로 묶을 수는 없다. DB는 고쳤는데 캐시 삭제가 네트워크 오류로 실패할 수 있고, 지운 직후 다른 요청이 옛 값을 다시 채우는 경쟁도 생긴다. 이런 경우를 어떻게 줄이는지는 [캐시 무효화](/posts/cache-invalidation)에서 직접 재현한다. 처음 설계할 때는 "고칠 때 지우고, TTL로 한 번 더 막는다"를 기본으로 두면 된다.

TTL에는 함정이 하나 더 있다. 인기 목록처럼 모두가 읽는 키가 만료되는 순간, 그 1초 사이에 온 요청 수백 개가 모두 미스를 보고 동시에 DB로 간다. 캐시 스탬피드라고 부른다. 키 하나에 트래픽이 몰리는 핫 키 문제와 함께 [캐시 전략](/posts/caching-strategies)에서 막는 법을 다룬다.

## 메모리가 차면 무엇을 버리나

캐시는 메모리에 있어서 빠르지만, 메모리는 디스크보다 작고 비싸다. 넣고 싶은 것을 다 넣을 수는 없다. 가득 찼을 때 무엇을 버릴지 정하는 규칙을 축출 정책(eviction policy)이라고 한다.

가장 많이 쓰는 규칙은 LRU(Least Recently Used)다. 가장 오래 아무도 안 읽은 것부터 버린다. 최근에 읽힌 것은 곧 또 읽힐 가능성이 높다는 가정이다. 아래 그림은 칸이 세 개뿐인 캐시에 메뉴 네 개가 들어오는 과정이다. 기억 칸의 왼쪽이 가장 오래 안 쓰인 쪽이다.

<AlgoTrace
  caption="LRU: 칸이 셋인 캐시에 네 번째 키가 들어오면"
  cells={["SET A", "SET B", "SET C", "GET A", "SET D"]}
  memoryLabel="캐시 (왼쪽이 가장 오래됨)"
  steps={[
    { pointer: 0, memory: ["A"], caption: "A를 넣는다." },
    { pointer: 1, memory: ["A", "B"], caption: "B를 넣는다." },
    { pointer: 2, memory: ["A", "B", "C"], caption: "C까지 넣으면 칸이 다 찼다." },
    { pointer: 3, memory: ["B", "C", "A"], caption: "A를 읽으면 A는 가장 최근에 쓰인 쪽으로 옮겨진다." },
    { pointer: 4, found: [4], memory: ["C", "A", "D"], caption: "D가 들어오려면 하나를 버려야 한다. 가장 오래 안 쓰인 B가 나간다." },
  ]}
/>

Redis에서 실제로 해 봤다. 메모리 상한을 4MB로 걸고 1KB짜리 값을 1만 개 넣으면서, `menu:0`부터 `menu:9`까지 열 개는 중간중간 계속 읽었다. 정책만 바꿔 두 번 돌렸다. Redis의 LRU는 정확한 순서를 다 들고 있지 않고 표본 몇 개를 뽑아 그중 오래된 것을 버리는 근사 방식이고, 마지막 접근 시각도 대략 초 단위로만 기록한다. 그래서 몇 초 만에 끝나는 실험에서는 차이가 잘 안 보여, 1,000개마다 1초씩 쉬게 했다.

```js
// evict.mjs 일부
await redis.configSet("maxmemory", "4mb");
for (const policy of ["noeviction", "allkeys-lru"]) {
  await redis.flushAll(); await redis.configResetStat();
  await redis.configSet("maxmemory-policy", policy);
  for (let i = 0; i < 10000; i++) {
    try { await redis.set(`menu:${i}`, value); ok++; } catch (e) { err = e.message; break; }
    if (i % 1000 === 999) await sleep(1100);
    if (i > 100 && i % 200 === 0) for (let k = 0; k < 10; k++) await redis.get(`menu:${k}`);
  }
}
```

```text
noeviction  writes ok=2907 keys=2907 evicted=0 hot left=10/10 old cold left=5/5
  error: OOM command not allowed when used memory > 'maxmemory'.
allkeys-lru writes ok=10000 keys=2862 evicted=7093 hot left=10/10 old cold left=0/5
```

첫 줄의 `noeviction`은 아무것도 버리지 않는 정책이다. 2,907개째에서 메모리가 차자 그다음 쓰기부터 `OOM` 오류로 거절했다. 캐시로 쓰는 Redis가 이 상태면 캐시를 채우는 코드가 줄줄이 실패한다. 둘째 줄의 `allkeys-lru`는 1만 개를 모두 받아들이면서 7,093개를 내보냈다. 계속 읽힌 메뉴 열 개는 모두 남았고, 처음에 한 번 넣고 다시 안 읽은 `menu:10`~`menu:14`는 모두 빠졌다.

<Callout kind="warning" title="Redis를 캐시로 쓰면 maxmemory를 먼저 본다">
Redis를 처음 설치하면 `maxmemory-policy`의 기본값은 `noeviction`이다. 캐시 전용 Redis라면 `maxmemory`를 서버 메모리보다 넉넉히 작게 잡고 정책을 `allkeys-lru`나 `allkeys-lfu`로 바꾼다. 세션처럼 지워지면 안 되는 데이터와 캐시를 한 Redis에 섞으면 축출이 세션까지 지울 수 있으니 인스턴스를 나눈다. 정책별 차이는 [Redis 메모리와 축출](/posts/redis-memory-eviction)에 있다.
</Callout>

## 캐시 서버가 멈추는 날

캐시 서버가 한 대면 그 한 대가 단일 장애 지점(single point of failure, SPOF)이다. 앞에서 cache-aside로 만들었으니 서비스가 바로 멈추지는 않는다. 하지만 위 계산처럼 DB가 받는 요청이 몇 배로 뛰고, DB가 그걸 못 받으면 결국 서비스가 멈춘다. 캐시가 있던 시절에 맞춰 DB를 작게 줄여 놨다면 더 위험하다.

이 상황을 버티는 방법은 몇 가지를 겹친다.

- 캐시 서버를 여러 대로 늘리고 키를 나눠 담는다. 한 대가 죽어도 그 몫만 미스가 된다. 서버를 늘리거나 줄일 때 키가 덜 옮겨 가게 나누는 방법은 [일관된 해싱](/posts/consistent-hashing)에서 다룬다.
- 캐시마다 복제본을 두고 자동으로 넘긴다. Redis라면 [Redis 복제와 Sentinel](/posts/redis-replication-sentinel)이나 [Redis Cluster](/posts/redis-cluster)를 쓴다.
- 웹 서버의 캐시 호출에 짧은 타임아웃(수십 ms)을 건다. 캐시가 응답 없이 매달려 있을 때 기다리다 웹 서버까지 멈추는 일을 막는다.
- 캐시를 비운 채 다시 띄우면 한동안 히트율이 0에 가깝다. 인기 키를 미리 채워 두는 워밍을 하거나, 트래픽을 조금씩 돌린다.

"캐시가 있으니 DB는 이만큼만 있으면 된다"는 계산을 할 때는 캐시가 없는 순간에 DB가 얼마나 받아야 하는지도 같이 적어 둔다. 그 숫자를 못 받는다면, 캐시는 이미 성능 장치가 아니라 가용성 장치다. 그만큼 캐시 계층도 DB처럼 이중화해야 한다.

## 사진과 JS 파일은 사용자 가까이에: CDN

이제 두 번째 낭비로 넘어가자. 식당 사진, 앱의 JavaScript와 CSS 파일은 누가 요청하든 같은 바이트다. 이런 파일을 정적 파일(static file)이라고 한다. 사용자마다 달라지는 데이터(내 예약 목록 같은)는 동적 응답이다.

정적 파일을 웹 서버가 직접 내보내면 두 가지 비용이 든다. 웹 서버의 네트워크 대역폭과 CPU를 쓰고, 서버에서 먼 사용자는 왕복 시간만큼 기다린다. CDN(Content Delivery Network)은 전 세계 여러 도시에 있는 캐시 서버(엣지라고 부른다)에 정적 파일 사본을 두고, 사용자를 가까운 엣지로 보내 주는 서비스다. 원본 파일이 있는 우리 서버를 오리진(origin)이라고 부른다.

엣지는 처음부터 모든 파일을 들고 있지 않다. 누군가 처음 요청하면 오리진에서 가져와 저장해 두고, 그다음 사람에게는 저장해 둔 사본을 준다. 앞에서 본 캐시 미스, 히트와 똑같은 흐름이 도시마다 일어난다.

nginx의 `proxy_cache`로 엣지 한 대를 흉내 내 봤다. 오리진은 Node로 띄웠고, 정적 파일에는 `Cache-Control: public, max-age=31536000, immutable`을, 내 정보 API에는 `private, no-store`를 붙였다. nginx가 캐시에서 줬는지는 `X-Cache-Status` 헤더로 보이게 했다.

```bash
# 같은 JS 파일을 세 번, 내 정보 API를 두 번 엣지(8391)로 요청한다
for i in 1 2 3; do curl -s -o /dev/null -D - http://127.0.0.1:8391/static/app.3f9a1c.js | grep -i x-cache; done
for i in 1 2; do curl -s -o /dev/null -D - http://127.0.0.1:8391/api/me | grep -i x-cache; done
cat origin.log   # 오리진에 실제로 도착한 요청
```


JS 파일은 첫 요청만 오리진에 갔고 나머지 두 번은 엣지가 답했다. 내 정보 API는 두 번 모두 오리진까지 갔다. `private, no-store`를 보고 엣지가 저장하지 않았기 때문이다. 사람마다 다른 응답을 공유 캐시에 저장하면 남의 정보가 보이는 사고가 나니, 이 구분은 오리진이 헤더로 분명히 알려 줘야 한다. 엣지 설정을 더 깊게 보려면 [엣지 캐싱](/posts/edge-caching)을, 같은 IP가 여러 도시에서 답하는 원리는 [CDN 엣지와 애니캐스트](/posts/cdn-edge-anycast)를 보면 된다.

## CDN에 맡기기 전에 정할 것

CDN을 붙이는 일 자체는 설정 몇 줄이다. 정해야 할 것은 그다음이다.

먼저 비용이다. CDN은 보통 엣지에서 사용자에게 나간 데이터 양(GB)과 요청 수로 요금을 매긴다. 요금은 업체, 지역, 사용량 구간마다 다르다. 거의 아무도 안 보는 오래된 파일까지 CDN에 둘 필요는 없다. 히트율이 낮은 파일은 엣지에 있어도 매번 오리진에서 다시 가져오니 효과가 작다.

다음은 수명이다. 엣지가 사본을 얼마나 들고 있을지는 오리진이 보내는 `Cache-Control`이 정한다. 너무 짧으면 엣지가 오리진에 자주 다시 묻고, 너무 길면 파일을 고쳐도 옛 파일이 계속 나간다. 이 고민을 없애는 흔한 방법이 파일 이름에 내용의 해시를 넣는 것이다. 아래 주소와 헤더를 조각별로 눌러 보자.

마지막은 CDN이 멈췄을 때다. CDN도 장애가 난다. 위 그림의 마지막 단계처럼, 앱이나 웹 페이지가 CDN 주소에서 파일을 못 받으면 오리진 주소로 다시 시도하게 만들어 두면 느려도 화면은 뜬다. 이때 오리진은 평소 CDN이 막아 주던 트래픽을 갑자기 받으니, 앞의 캐시 장애와 같은 계산을 해 둔다.

마지막 단계가 남은 숙제다. 읽기는 캐시, CDN, 복제본으로 여러 겹 나눴지만 쓰기는 아직 한 곳으로 모인다. 그리고 이 모든 장비가 한 데이터 센터 안에 있다. 건물 하나의 전원이나 네트워크가 끊기면 캐시도 복제본도 함께 사라진다.

## 다음 글

다음 글 [⑥ 데이터 센터 여러 곳](/posts/sd-multi-datacenter)에서는 이 구조 전체를 다른 지역에 하나 더 두고, 사용자를 가까운 곳으로 보내고, 한쪽이 통째로 멈추면 다른 쪽으로 넘기는 방법을 다룬다. 캐시 패턴을 더 깊게 보고 싶다면 [캐시 전략](/posts/caching-strategies)과 [캐시 무효화](/posts/cache-invalidation), CDN 헤더를 정확히 알고 싶다면 [HTTP 캐시와 CDN](/posts/http-caching-cdn)으로 가면 된다.

한 문장으로 다시 쓰면 이렇다. 캐시는 같은 답을 다시 계산하지 않게 하고, CDN은 같은 파일을 멀리서 다시 보내지 않게 한다. 둘 다 사본이라서 언제까지 믿을지(TTL)와 어떻게 지울지를 함께 설계해야 하고, 사본이 사라진 순간 원본이 버틸 수 있는지도 계산해 둬야 한다.

## 면접에서 나올 만한 질문

### 캐시 계층은 어디에 두고 어떤 데이터를 넣나요?

웹 서버와 DB 사이에 Redis 같은 공유 메모리 저장소로 두고, 자주 읽히고 드물게 바뀌는 데이터를 넣는다. 인기 목록, 상품·식당 기본 정보, 설정값이 대표적이다. 잔액이나 재고처럼 정확해야 하는 값은 캐시에서 읽어 결정하지 않고, 화면 표시용으로만 쓴다. 웹 서버마다 따로 두지 않는 이유는 웹 계층을 무상태로 유지해 마음대로 늘리고 줄이기 위해서다.

### 캐시와 DB가 서로 다른 값을 가지면 어떻게 하나요?

기본은 DB를 고칠 때 해당 캐시 키를 지우고, 모든 키에 TTL을 줘서 지우기에 실패해도 TTL 안에는 맞춰지게 하는 것이다. 캐시와 DB는 한 트랜잭션으로 묶이지 않아서 삭제 실패나 "지운 직후 옛 값이 다시 채워지는" 경쟁이 생길 수 있다. 그래서 얼마나 어긋나도 되는지를 데이터마다 정하고 TTL을 그 기준으로 고른다. 정말 어긋나면 안 되는 값은 캐시를 거치지 않는다.

### 캐시 서버가 죽으면 어떻게 되나요?

cache-aside로 만들었다면 서비스는 DB에서 읽으며 계속 돌지만, 캐시가 막아 주던 읽기가 전부 DB로 간다. 히트율 90%였다면 DB 읽기가 약 열 배가 된다. 그래서 캐시 호출에 짧은 타임아웃을 걸고, 캐시를 여러 대로 나누고 복제본으로 자동 전환하게 한다. DB가 캐시 없이 얼마를 버티는지 미리 계산해 두는 것도 설계에 포함된다.

### 트래픽이 10배가 되면 캐시 쪽에서 무엇을 보나요?

먼저 히트율이다. 같은 히트율이어도 미스 수가 10배가 되니 DB로 가는 양이 10배다. 히트율을 몇 %p만 올려도 DB 부하가 크게 준다. 다음은 캐시 서버 자체의 메모리와 네트워크 대역폭, 그리고 특정 키 하나에 몰리는 핫 키다. 핫 키는 웹 서버 안에 아주 짧은 로컬 캐시를 하나 더 두거나 키를 복제해 나눠 읽는 식으로 푼다.

### 캐시가 가득 차면 어떻게 되나요?

축출 정책에 따라 다르다. LRU는 가장 오래 안 읽힌 키부터 버리고, 자주 읽히는 키는 남긴다. Redis 기본값인 noeviction은 아무것도 버리지 않고 새 쓰기를 OOM 오류로 거절하므로, 캐시 전용 Redis는 maxmemory와 allkeys-lru 같은 정책을 직접 설정해야 한다.

### TTL은 어떻게 정하나요?

그 데이터가 얼마나 낡아도 사용자에게 문제가 없는지로 정한다. 순위처럼 몇 분 늦어도 되는 값은 길게, 영업시간처럼 틀리면 곤란한 값은 변경 시 삭제를 기본으로 하고 TTL은 안전망으로 둔다. 많은 키가 같은 TTL로 동시에 만료되지 않게 무작위로 조금씩 흩는 것도 같이 한다.

### CDN에 올린 JS를 고쳤는데 사용자에게 옛 파일이 보입니다. 어떻게 하나요?

이름이 고정된 파일을 긴 max-age로 캐시했기 때문이다. 근본적인 방법은 파일 이름에 내용 해시를 넣어 내용이 바뀌면 주소도 바뀌게 하는 것이다. 그러면 정적 파일은 1년 동안 immutable로 캐시하고, 새 주소를 가리키는 HTML만 짧게 캐시하면 된다. 이미 퍼진 고정 이름 파일은 CDN 퍼지로 지우되, 모든 엣지에 반영되는 데 시간이 걸린다는 점을 감안한다.

### CDN이 장애 나면 어떻게 하나요?

클라이언트가 CDN에서 파일을 못 받으면 오리진 주소로 다시 시도하게 만들어 둔다. 다만 그 순간 오리진은 평소 CDN이 대신 받던 트래픽을 받게 되므로, 오리진이 얼마나 버티는지 미리 계산하고 필요하면 여러 CDN을 나눠 쓴다. 사람마다 다른 응답은 처음부터 CDN에 저장되지 않게 private로 표시해 두는 것도 함께 확인한다.
