SSR로 만든 상품 목록 페이지를 느린 휴대폰으로 연다. 0.5초 만에 목록과 "눌린 횟수 0" 버튼이 다 보인다. 버튼을 두 번 누른다. 아무 일도 없다. 1.5초쯤 지나 다시 누르니 그제야 1이 된다. 앞의 두 번은 어디로 갔을까.

서버가 보낸 HTML은 그림일 뿐이다. 버튼에 클릭 핸들러를 붙이고, 상태를 만들고, 이후 화면을 바꿀 수 있게 하는 일은 브라우저에서 React가 다시 해야 한다. 이걸 하이드레이션(hydration)이라고 한다. 이 글은 `hydrateRoot`가 실제로 무엇을 하는지, 그 비용이 얼마인지, 서버와 브라우저의 결과가 어긋나면 React가 어떻게 하는지를 React 19.3과 Chromium 141로 하나씩 재현하며 따라간다. 렌더링 방식 전체 그림은 [CSR, SSR, SSG, ISR, 스트리밍](/posts/rendering-strategies)에, 서버에서 HTML을 만드는 쪽은 [SSR](/posts/rendering-ssr)에 있다.

예제는 Node.js 서버가 `renderToString`으로 HTML을 만들고, esbuild로 묶은 클라이언트 번들이 `hydrateRoot`를 부르는 구조다. 서버는 `TZ=UTC`, 영어 로케일로 띄웠고 브라우저는 Playwright로 독일어 로케일, 서울 시간대로 열었다.

## hydrateRoot가 하는 일

브라우저에서 React 앱을 시작하는 함수는 둘이다. `createRoot(el).render(<App />)`는 빈 컨테이너에 DOM을 처음부터 만든다. `hydrateRoot(el, <App />)`는 컨테이너 안에 이미 서버가 만든 DOM이 있다고 보고, 그 DOM을 다시 쓴다.

```jsx
import { hydrateRoot } from "react-dom/client";
import { App } from "./app.jsx";

// 서버가 렌더링할 때와 똑같은 트리를 넘겨야 한다
hydrateRoot(document.getElementById("root"), <App />);
```

React는 컴포넌트를 처음부터 다시 실행한다. 서버에서 실행했던 함수들이 브라우저에서 한 번 더 돈다. 그 결과로 나온 요소를 만들 때 새 DOM 노드를 만들지 않고, 서버 HTML에서 같은 자리에 있는 노드를 짚어 자기 것으로 삼는다. 그리고 이벤트 리스너를 붙인다. 버튼마다 붙이는 게 아니라 루트 컨테이너에 이벤트 종류별로 하나씩 붙여 두고, 이벤트가 올라오면 어느 컴포넌트의 핸들러를 부를지 React가 고른다(React 17부터 이 방식이다). 마지막으로 `useEffect`가 돈다. 서버에서는 effect가 실행되지 않으니, 브라우저 첫 effect가 "이제 살아났다"는 신호다.

## 보이는데 안 눌리는 시간

처음 장면을 그대로 재현했다. JS 응답을 1.5초 늦게 주고, 버튼이 보이자마자 두 번 눌렀다.

```text
457ms: 버튼이 보여서 두 번 눌렀다 → 눌린 횟수 0
1990ms: 하이드레이션 끝 → 눌린 횟수 0
다시 누르면 → 눌린 횟수 1
```

하이드레이션 전의 클릭은 사라졌다. 그때는 페이지에 React의 리스너가 아예 없었으니 클릭은 아무도 듣지 않은 이벤트다. 끝난 뒤에 몰아서 처리해 주지도 않는다. 사용자는 "버튼이 고장 났다"고 느끼고 여러 번 누르는데, 그게 화난 클릭(rage click)으로 분석 도구에 잡히기도 한다. 링크는 예외다. `<a href>`는 JS 없이도 동작하니 하이드레이션 전에 눌러도 이동한다. 폼도 `action`이 있으면 브라우저가 기본 제출을 한다. 중요한 동작은 JS 없이도 최소한은 되게 만들어 두면 이 구간이 덜 아프다.

하이드레이션이 길면 [INP](/posts/core-web-vitals)도 나빠진다. 긴 작업 도중 들어온 입력은 그 작업이 끝날 때까지 처리되지 못해서, 첫 상호작용의 응답 지연이 수백 ms로 기록된다.

여기서 흔한 오해가 하나 있다. "SSR을 하면 JS가 줄어든다." 아니다. 서버에서 그린 컴포넌트의 코드도 하이드레이션하려면 전부 브라우저로 와서 다시 실행되어야 한다. 이 예제에서도 화면에 변하는 건 버튼 하나인데, 3,000줄 목록을 그리는 코드가 번들에 들어 있고 브라우저에서 다시 돈다. 같은 데이터도 두 번 온다. HTML로 그려진 형태로 한 번, 하이드레이션에 쓸 JSON으로 한 번. 이 비용을 줄이는 방법은 글 끝에서 본다.

## 어긋나면 React가 하는 일

하이드레이션은 "브라우저에서 다시 그린 결과가 서버 HTML과 같다"는 가정 위에 있다. 다르면 문제가 된다. 이걸 하이드레이션 불일치(hydration mismatch)라고 한다. React 19는 어긋난 종류에 따라 전혀 다르게 대응한다. 그림의 화살표를 따라 보자.

요소나 텍스트가 다르면 React는 그 부분의 서버 DOM을 버리고 브라우저에서 새로 만든다. 버리는 범위는 어긋난 지점에서 가장 가까운 `Suspense` 경계까지, 경계가 없으면 루트 전체다. 화면은 결국 맞게 나오지만 서버 렌더링의 이점을 그만큼 잃고, 큰 범위를 다시 그리는 동안 깜빡임이나 레이아웃 이동이 생길 수 있다.

속성 값만 다르면 React는 고치지 않는다. 개발 모드에서 경고만 하고 서버가 준 값을 그대로 둔다. 화면에는 서버 값이 남고, React는 자기가 브라우저 값으로 그렸다고 믿는다. 이 어긋남은 다음 업데이트 때까지 남아서 이상한 버그로 돌아온다.

실제로 재현해서 서버 노드가 교체됐는지(`isConnected`가 false가 됐는지)와 최종 DOM을 확인했다. 다음 절의 출력이 그 결과다.

## 불일치를 만드는 코드들

### 서버와 브라우저에서 갈리는 분기

```jsx
// 서버에서는 window가 없다
{typeof window !== "undefined" ? <p>모바일 할인</p> : null}
<button>장바구니</button>
```

개발 빌드 콘솔에는 이렇게 찍힌다. `+`가 브라우저, `-`가 서버다.

```text
Hydration failed because the server rendered HTML didn't match the client. As a result this tree will be regenerated on the client. This can happen if a SSR-ed Client Component used:
...
  <window>
    <main>
      <h1>
+     <p>
-     <button>
      ...

== 서버 노드가 교체됐나: true
```

브라우저는 `h1` 다음에 `p`를 기대했는데 서버 HTML에는 `button`이 있었다. 루트 전체가 다시 그려졌다. `localStorage`의 테마나 로그인 여부를 첫 렌더에서 읽는 코드도 같은 결과다.

### 로케일과 시간대

서버는 영어 로케일, 브라우저는 독일어 로케일이다. 인자 없는 `toLocaleString()`은 실행하는 환경의 로케일을 따른다.

```jsx
<p id="price">{(89000).toLocaleString()}원</p>
```

```text
Hydration failed because the server rendered text didn't match the client. ...
  <locale>
    <main>
      <p id="price">
+       89.000
        ...
== 서버 노드가 교체됐나: true
```

서버는 `89,000`, 독일어 브라우저는 `89.000`을 냈다. 날짜와 시각도 같다. 개발할 때는 서버와 브라우저가 같은 노트북이라 시간대와 로케일이 같아서 안 보이고, UTC로 도는 컨테이너에 올린 뒤에야 나타난다. 로케일과 시간대를 `toLocaleString("ko-KR", { timeZone: "Asia/Seoul" })`처럼 명시하거나, 포맷한 문자열을 서버에서 정해 데이터로 내려보낸다.

### 잘못된 HTML 중첩

```jsx
<p>가격 <div>89,000원</div></p>
```

React 입장에서는 `p` 안에 `div`가 있는 트리다. 그런데 브라우저의 HTML 파서는 `p` 안에 `div`를 허락하지 않는다. JS를 막고 서버 HTML이 파싱된 결과만 봤다.

```text
<main><p>가격 </p><div>89,000원</div><p></p></main>
```

파서가 `div`를 만나자 `p`를 닫아 버렸고, 남은 `</p>`는 빈 `p`가 됐다. 서버가 보낸 문자열은 맞았는데 DOM이 달라진 것이다. 개발 빌드는 원인을 먼저 알려 준다.

```text
In HTML, <div> cannot be a descendant of <p>.
This will cause a hydration error.
  <nesting>
    <main>
>     <p>
>       <div>
Hydration failed because the server rendered HTML didn't match the client. ...
```

`p` 안의 `div`, `a` 안의 `a`, `table` 바로 아래의 `tr`(브라우저가 `tbody`를 끼워 넣는다), `button` 안의 `button`이 흔하다. 마크다운이나 CMS의 HTML을 `p` 안에 넣을 때 자주 생긴다.

### 실행할 때마다 다른 값

```jsx
<label htmlFor={"q" + Math.random().toString(36).slice(2, 6)}>수량</label>
```

```text
A tree hydrated but some attributes of the server rendered HTML didn't match the client properties. This won't be patched up. ...
      <label
+       htmlFor="qmri1"
-       htmlFor="qc9zj"
      >
== 서버 노드가 교체됐나: false
== 최종 DOM: <main><h1>무선 이어폰</h1><label for="qc9zj">수량</label></main>
```

이번에는 속성이라 다시 그리지 않았다. 최종 DOM의 `for`는 서버 값 `qc9zj`다. React가 이 label과 짝지은 input의 `id`를 브라우저 값으로 기억하고 있다면 label을 눌러도 input에 포커스가 안 간다. 접근성 속성(`aria-labelledby`, `aria-controls`)에서 이러면 화면 읽기 프로그램만 망가져서 한참 뒤에야 발견된다. 서버와 브라우저에서 같은 값을 주는 `useId`를 쓴다. 클래스 이름도 같은 함정이다. `className={isServer ? "title" : "title dark"}`는 경고 뒤 `class="title"`로 남았다.

아래 함수는 서버 HTML과 브라우저 결과를 태그와 텍스트 조각으로 나눠 처음 어긋나는 조각을 찾는다. React가 앞에서부터 짝을 맞추다 멈추는 지점을 흉내 낸 것이다.

  // server, client: HTML 문자열
  // 태그(<...>)와 그 사이 텍스트를 조각으로 나눠 앞에서부터 비교한다
  // 반환: { index, server, client } (조각이 없으면 null), 같으면 null

  const tok = (s) => s.match(/<[^>]+>|[^<]+/g) || [];
  const a = tok(server);
  const b = tok(client);
  for (let i = 0; i < Math.max(a.length, b.length); i++) {
    if (a[i] !== b[i]) return { index: i, server: a[i] ?? null, client: b[i] ?? null };
  }
  return null;
}`}

## 확장 프로그램은 언제 끼어드느냐가 문제다

번역기, 문법 검사기, 최저가 알림 같은 브라우저 확장 프로그램은 페이지 DOM에 요소나 속성을 끼워 넣는다. 사용자 컴퓨터에서만 나는 불일치라서 재현이 어렵다. 확장 프로그램처럼 DOM을 건드리는 스크립트를 넣고, 건드리는 시점과 위치를 바꿔 가며 확인했다.

```text
하이드레이션 뒤에 main 안에 요소 추가      → 오류 없음, 요소 남음
하이드레이션 전에 main 안에 요소 추가      → Hydration failed, 다시 그림, 요소 사라짐
하이드레이션 전에 h1에 data-gramm 속성 추가 → 속성 불일치 경고 (개발 모드)
문서 전체를 하이드레이션, body 맨 앞에 추가 → 오류 없음, 요소 남음
문서 전체를 하이드레이션, head 끝에 추가    → 오류 없음, 요소 남음
```

시점이 갈랐다. 하이드레이션이 끝난 뒤의 DOM 변경은 React가 신경 쓰지 않는다. 그 전이면 불일치다. 확장 프로그램이 DOM을 건드리는 시점은 확장마다, 페이지 로딩 속도마다 다르니 같은 사용자도 어떤 날은 나고 어떤 날은 안 난다.

위치도 갈랐다. React 19는 문서 전체(`hydrateRoot(document, ...)`)를 하이드레이션할 때 `head`와 `body` 바로 아래에 끼어든 낯선 요소는 건너뛴다. Next.js App Router처럼 `<html>`부터 React가 그리는 앱이 이 경우다. 하지만 그보다 깊은 곳, 내 컴포넌트 안에 끼어든 요소는 여전히 불일치다. 운영 오류 수집에 특정 사용자에게서만 하이드레이션 오류가 반복된다면, 그 사용자의 확장 프로그램을 의심해 볼 만하다. 시크릿 창(확장이 꺼진 상태)에서 재현되는지가 첫 확인이다.

## 개발 모드와 운영 모드의 메시지는 다르다

개발 빌드는 위처럼 트리와 `+`/`-` 차이까지 보여 준다. 같은 코드를 프로덕션 빌드로 띄우면 이것만 남는다.

```text
[pageerror] Minified React error #418; visit https://react.dev/errors/418?args[]=HTML&args[]= for the full message or use the non-minified dev environment for full errors and additional helpful warnings.
```

로케일 예제는 `args[]=text`, 분기와 중첩 예제는 `args[]=HTML`이었다. 418번이 "서버 HTML과 맞지 않아 브라우저에서 다시 그렸다"는 오류다. 하이드레이션 중에 불일치가 아닌 다른 예외가 나서 React가 다시 그렸다면 423번(루트)이나 422번(Suspense 경계)이 나온다. 속성 불일치는 운영에서는 아무 흔적도 남지 않는다. 경고는 개발 빌드에만 있다.

`[pageerror]`로 찍혔다는 점도 봐 둔다. `hydrateRoot`에 아무 옵션도 주지 않으면 React는 이 오류를 `reportError`로 전역에 알린다. 그래서 `window.onerror`를 듣는 오류 수집 도구에 "잡히지 않은 오류"로 쌓인다. 화면은 멀쩡한데 오류 대시보드에 #418이 수천 건씩 찍히는 이유다. 직접 받아서 분류하려면 `onRecoverableError`를 준다.

```jsx
hydrateRoot(document.getElementById("root"), <App />, {
  onRecoverableError(error, info) {
    // 운영에서도 어느 컴포넌트 근처인지 남긴다
    logger.warn("hydration", {
      message: error.message,
      componentStack: info.componentStack,
      path: location.pathname,
      tz: Intl.DateTimeFormat().resolvedOptions().timeZone,
      locale: navigator.language,
    });
  },
});
```

이 옵션을 주면 개발 모드에서도 React가 콘솔에 차이 트리를 직접 찍지 않고 이 함수에 넘긴다. 개발 중에는 기본 동작을 두고 운영 빌드에만 주는 편이 편하다. 시간대와 로케일을 같이 남기면 "독일어 사용자에게서만 난다" 같은 패턴이 바로 보인다.

## 고치는 방법들

### 첫 렌더는 서버와 같게, 브라우저 값은 effect에서

가장 기본적인 방법이다. 첫 렌더는 서버가 그릴 수 있는 값으로 그리고, 브라우저에서만 아는 값은 `useEffect`에서 state로 바꿔 한 번 더 그린다.

```jsx
function Clock() {
  const [now, setNow] = useState(null);
  useEffect(() => setNow(new Date().toLocaleTimeString("ko-KR")), []);
  return <time>{now ?? " "}</time>; // 서버와 첫 렌더는 빈 칸
}
```

서버 HTML은 `<time> </time>`이고, 하이드레이션 뒤 시각이 채워졌다. 오류는 없다. 대가는 렌더링이 한 번 더 일어나고, 그 사이 빈 칸이 잠깐 보인다는 것이다. 빈 칸과 실제 값의 크기가 다르면 레이아웃이 밀리니 자리 크기를 맞춰 둔다.

### 외부 값은 useSyncExternalStore로

`localStorage`, `navigator.onLine`, 화면 폭처럼 React 밖에 있는 값은 `useSyncExternalStore`가 더 정확하다. 세 번째 인자 `getServerSnapshot`이 서버와 하이드레이션 때 쓸 값을 정한다.

```jsx
const theme = useSyncExternalStore(
  subscribe,                                            // 바뀌면 알려 줄 구독 함수
  () => localStorage.getItem("theme") ?? "light",       // 브라우저 값
  () => "light",                                        // 서버와 하이드레이션 때 값
);
```

브라우저 `localStorage`에 `dark`를 넣어 두고 열었다. 서버 HTML은 `테마 light`, 하이드레이션이 끝난 DOM은 `테마 dark`였고 오류는 없었다. React가 하이드레이션 동안은 서버 값으로 짝을 맞추고, 끝난 직후 브라우저 값으로 다시 그린다. 테마처럼 첫 페인트부터 맞아야 하는 값은 이것만으로는 깜빡인다. 그래서 테마는 보통 `<head>`의 작은 인라인 스크립트가 HTML 속성(`data-theme`)을 먼저 정하고, CSS가 그 속성을 따르게 만든다. 이 블로그도 그렇게 한다.

### suppressHydrationWarning은 한 단계만

정말 달라도 되는 텍스트 한 곳(렌더링한 시각 같은)이라면 그 요소에 `suppressHydrationWarning`을 붙여 경고를 끈다. 동작을 정확히 알고 써야 한다.

```text
<time suppressHydrationWarning>  서버 10:00:01 / 브라우저 10:00:03
→ 오류 없음, 최종 DOM: <time>10:00:01</time>

<p suppressHydrationWarning><span>서버 / 브라우저</span></p>
→ Hydration failed ... <p suppressHydrationWarning={true}> <span> + 브라우저
```

첫째, 경고만 끄고 값은 고치지 않는다. 화면에는 서버 값 `10:00:01`이 남았다. 둘째, 붙인 요소의 바로 안쪽 텍스트와 속성에만 듣는다. 자식 `span`의 차이는 그대로 오류가 났다. 상위 컴포넌트에 붙여 불일치를 통째로 덮는 용도로는 쓸 수 없다. `<html>`에 붙이는 건 흔한 쓰임이다. 테마 스크립트가 `html`의 속성을 바꾸니 그 한 단계만 무시하게 하는 것이다.

### 같은 값을 서버에서 정해 내려보내기

시각이나 난수가 화면에 꼭 같아야 한다면 서버에서 한 번 정해서 데이터로 넘긴다. 서버가 렌더링한 시각을 props로 넘기고 브라우저도 그 값을 쓰면 둘이 같을 수밖에 없다. 서버 컨테이너의 `TZ`를 서비스 대상 지역에 맞추는 것도 방법이지만, 사용자가 여러 시간대에 있다면 결국 브라우저 값은 effect로 반영해야 한다.

## 한꺼번에 하지 않기: 선택적 하이드레이션

하이드레이션의 또 다른 문제는 기본적으로 한 덩어리라는 것이다. 페이지 전체 JS가 와야 시작하고, 시작하면 끝날 때까지 간다. React 18부터는 `Suspense` 경계가 하이드레이션의 단위가 된다. 경계마다 따로 하이드레이션할 수 있고, 사용자가 아직 하이드레이션되지 않은 경계를 건드리면 그 경계를 먼저 처리한다. 이걸 선택적 하이드레이션(selective hydration)이라고 한다.

리뷰, 관련 상품, 장바구니 세 영역을 각각 `Suspense`로 감싸고(영역마다 1,500줄), CPU를 6배 느리게 해서 두 번 열었다. 한 번은 그냥 두고, 한 번은 `hydrateRoot` 직후 장바구니 버튼을 눌렀다.

```text
== 아무것도 안 누르면
  2012ms hydrateRoot 호출
  2418ms reviews 하이드레이션 끝
  2427ms related 하이드레이션 끝
  2430ms cart 하이드레이션 끝

== 하이드레이션 도중 cart를 누르면
  2006ms hydrateRoot 호출
  2037ms cart 클릭
  2287ms cart 하이드레이션 끝
  2625ms reviews 하이드레이션 끝
  2631ms related 하이드레이션 끝
  결과: cart 1
```

## 하이드레이션을 덜 하는 방법

선택적 하이드레이션은 순서를 바꿀 뿐 양을 줄이지는 않는다. 결국 페이지의 모든 컴포넌트 코드가 와서 한 번씩 돈다. 3,000줄 목록에서 움직이는 건 버튼 하나였는데도 그랬다. 양 자체를 줄이는 방법이 몇 가지 있다.

점진적 하이드레이션(progressive hydration)은 화면 아래쪽처럼 당장 필요 없는 영역의 하이드레이션을 보일 때나 한가할 때로 미룬다. 부분 하이드레이션(partial hydration)은 한 걸음 더 가서, 상호작용이 없는 영역은 아예 하이드레이션하지 않고 코드도 보내지 않는다. Astro의 아일랜드가 이 방식이고, Qwik은 하이드레이션 자체를 없애고 서버가 멈춘 지점에서 이어서 실행하는 재개(resumability)를 택했다. 이 둘은 [아일랜드와 재개 가능성](/posts/islands-resumability)에서 비교한다.

React 진영의 답은 [React 서버 컴포넌트](/posts/react-server-components)다. 서버 컴포넌트는 서버에서만 실행되고 결과만 보내니 코드가 번들에 없고 하이드레이션 대상도 아니다. 3,000줄 목록은 서버 컴포넌트로, 버튼만 클라이언트 컴포넌트로 두면 브라우저에서 다시 도는 건 버튼 하나뿐이다.

## 운영에서 불일치를 찾는 순서

오류 수집 도구에 #418이 쌓이기 시작했다면 이렇게 좁힌다. 먼저 `onRecoverableError`로 경로, 시간대, 로케일, 컴포넌트 스택을 모은다. 특정 시간대·로케일에 몰려 있으면 날짜·숫자 포맷이고, 특정 경로에 몰려 있으면 그 페이지의 분기나 중첩이다. 고르게 퍼져 있는데 일부 사용자에게만 반복되면 확장 프로그램을 의심한다.

다음은 재현이다. 개발 서버와 브라우저를 다른 시간대·로케일로 띄우면 대부분 바로 보인다.

```bash
# 서버를 UTC, 영어 로케일로 띄운다
TZ=UTC LANG=en_US.UTF-8 NODE_ENV=production node server.mjs
```

```js
// 브라우저는 다른 로케일·시간대로 열고 콘솔과 페이지 오류를 모은다
const ctx = await browser.newContext({ locale: "de-DE", timezoneId: "Asia/Seoul" });
const page = await ctx.newPage();
page.on("console", (m) => console.log(`[console.${m.type()}]`, m.text()));
page.on("pageerror", (e) => console.log("[pageerror]", e.message));
await page.goto("http://localhost:4401/locale?mode=dev");
```

이 글의 출력이 전부 이 방식으로 나왔다. 개발 빌드 번들로 열어야 차이 트리가 보인다. 마지막으로, 고친 뒤에는 서버 HTML(`curl`로 받은 것)과 하이드레이션 뒤 DOM을 비교해 같은지 본다. 앞의 `firstMismatch` 같은 비교를 테스트에 넣어 두면 다시 생겼을 때 배포 전에 걸린다.

## 다시 사라진 두 번의 클릭으로

처음의 두 번 클릭은 하이드레이션 전이라 React의 리스너가 없어서 사라졌다. 하이드레이션은 서버가 그린 HTML을 브라우저에서 컴포넌트를 다시 실행해 짝을 맞추고 이벤트를 붙이는 일이고, 그 비용은 화면에 보이는 모든 컴포넌트의 코드와 CPU 시간이다. 서버와 브라우저의 첫 렌더가 다르면 구조는 다시 그려지고 속성은 서버 값으로 남는다. 첫 렌더를 서버와 같게 두고, 브라우저 값은 effect나 `useSyncExternalStore`로 넘기며, `Suspense` 경계로 나눠 급한 곳부터 살린다. 하이드레이션 양 자체를 줄이는 방법은 [React 서버 컴포넌트](/posts/react-server-components)와 [아일랜드와 재개 가능성](/posts/islands-resumability)으로 이어진다.

## 면접에서 나올 만한 질문

### 하이드레이션이 무엇인가요?

서버가 만든 HTML에 브라우저에서 React가 같은 컴포넌트를 다시 실행해 기존 DOM 노드와 짝을 맞추고, 루트에 이벤트 리스너를 붙여 상호작용이 가능하게 만드는 과정이다. `createRoot`와 달리 새 DOM을 만들지 않고 서버 DOM을 재사용한다. 끝나면 첫 `useEffect`가 돌고, 그때부터 페이지가 동작한다.

### SSR을 하면 JS 양이 줄어드나요?

줄지 않는다. 서버에서 그린 컴포넌트도 하이드레이션하려면 코드가 전부 번들로 와서 브라우저에서 다시 실행된다. 데이터도 HTML과 JSON으로 두 번 온다. SSR은 첫 화면을 앞당길 뿐이고, 보이는 시점과 동작하는 시점 사이에 하이드레이션 구간이 생긴다. 코드 자체를 빼려면 서버 컴포넌트나 부분 하이드레이션이 필요하다.

### 하이드레이션 불일치는 왜 생기고, React 19는 어떻게 처리하나요?

서버와 브라우저의 첫 렌더 결과가 다를 때 생긴다. `typeof window` 분기, `Date`·`Math.random`, 로케일·시간대에 따라 바뀌는 포맷, `p` 안의 `div` 같은 잘못된 중첩, 하이드레이션 전에 DOM을 건드린 확장 프로그램이 흔한 원인이다. 요소나 텍스트가 다르면 가장 가까운 `Suspense` 경계(없으면 루트)까지 브라우저에서 다시 그리고, 속성만 다르면 개발 모드에서 경고만 하고 서버 값을 그대로 둔다.

### 운영에서 Minified React error #418이 쌓이면 어떻게 하나요?

418은 서버 HTML과 맞지 않아 브라우저에서 다시 그렸다는 오류이고, 기본값으로는 `reportError`를 거쳐 전역 오류로 수집된다. `hydrateRoot`의 `onRecoverableError`로 경로, 컴포넌트 스택, 시간대, 로케일을 함께 남겨 패턴을 찾는다. 그다음 서버를 UTC로, 브라우저를 다른 로케일과 시간대로 띄워 개발 빌드에서 재현하면 차이 트리로 원인을 찾을 수 있다.

### suppressHydrationWarning을 쓰면 되지 않나요?

붙인 요소 한 단계의 텍스트와 속성 경고만 끈다. 값은 고치지 않아서 화면에 서버 값이 남고, 자식 요소의 불일치는 그대로 오류가 난다. 렌더링 시각처럼 달라도 되는 텍스트 한 곳이나, 테마 스크립트가 속성을 바꾸는 `<html>`에만 쓴다. 나머지는 첫 렌더를 서버와 같게 하고 브라우저 값을 effect나 `useSyncExternalStore`로 반영한다.

### 선택적 하이드레이션은 무엇이고, 언제 클릭이 사라지나요?

`Suspense` 경계를 단위로 따로 하이드레이션하고, 사용자가 아직 살아나지 않은 경계를 누르면 그 경계를 먼저 하이드레이션한 뒤 클릭을 전달하는 동작이다. 루트 리스너는 `hydrateRoot`를 부를 때 붙으니 그 전, 즉 JS가 오기 전의 클릭은 사라진다. 경계의 코드가 `lazy`로 아직 도착하지 않았을 때도 당장 살릴 수 없어서 그 클릭은 버려진다.

### 하이드레이션 비용을 줄이는 방법은요?

번들과 하이드레이션 대상을 줄이는 게 먼저다. 상호작용이 없는 부분은 서버 컴포넌트로 옮겨 코드와 하이드레이션을 없애고, 남은 부분은 `Suspense`로 나눠 급한 영역부터 살린다. 프레임워크를 고를 수 있다면 상호작용 영역만 하이드레이션하는 아일랜드나 하이드레이션 없이 이어서 실행하는 재개 방식도 있다. 무거운 목록은 처음 보이는 만큼만 그리는 것도 효과가 크다.
