<EasyIntro>
  여러 프로젝트가 똑같은 도구 상자를 하나씩 복사해 쓰고 있다고 해 보자. 한 곳에서 망치를 고치면 나머지 상자는 그대로라서 금방 서로 달라진다. 그래서 도구 상자를 한 번 잘 포장해 창고에 올려 두고, 다들 거기서 받아 가게 만든다. 그게 패키지 배포다.

  포장할 때는 상자 겉에 붙이는 안내문이 중요하다. 어떤 문으로 열어야 하는지, 어떤 도구는 손님이 꺼내면 안 되는지, 상자 안에 무엇이 들었는지가 적혀 있다. 안내문이 틀리면 어떤 손님은 상자를 아예 못 연다. 포장지 안에 실수로 비밀 쪽지를 넣으면 창고에 올린 순간 모두가 읽을 수 있다.

  그래서 올리기 전에 상자를 한 번 열어 내용물을 직접 확인한다. 받아 가는 쪽도 집 전체에 하나만 둘지, 방마다 따로 둘지, 잠깐 빌려 쓰고 돌려줄지를 고른다.
</EasyIntro>

사내 프로젝트 세 개에 `formatKRW`라는 함수가 복사되어 있다. 금액을 `1,234,567원`으로 찍는 열 줄짜리다. 한 저장소에서 음수 처리 버그를 고쳤는데 나머지 둘은 그대로라, 같은 금액이 화면마다 다르게 나온다. 이제 이걸 `@acme/fmt`라는 패키지로 떼어 내 한 곳에서 고치려고 한다.

막상 해 보면 함수를 옮기는 건 5분이다. 시간을 잡아먹는 건 `package.json`이다. `main`만 적었더니 ESM 프로젝트에서 타입이 안 잡히고, `exports`를 적었더니 기존에 `dist/` 안쪽을 직접 import하던 코드가 깨지고, 배포한 tarball을 열어 보니 `.env`가 들어 있다. 이 글은 패키지 하나를 만들어 배포 직전까지 가는 길을 따라가면서 그 함정들을 직접 밟아 본다.

이 주제의 다른 글: 버전 번호와 `^`·`~` 범위는 [Semantic Versioning](/posts/semantic-versioning), 여러 패키지가 버전을 두고 부딪히는 일과 lockfile은 [의존성 지옥](/posts/dependency-hell)에서 다뤘다. ESM과 CommonJS가 런타임에서 어떻게 만나는지는 [ES 모듈 글](/posts/js-es-modules)에 있다. 이 글은 만드는 쪽, 즉 패키지 작성자 입장에서 같은 주제를 본다.

실습은 Ubuntu 24.04, Node.js 22.22.0, npm 10.9.4, TypeScript 5.9.3에서 했다. 실제 레지스트리에는 올리지 않고 `npm pack`과 `npm publish --dry-run`까지만 갔다. 출력은 실제로 돌린 결과이고 긴 작업 경로만 줄였다.

## 무엇이 tarball에 들어가는지부터 본다

패키지를 배포한다는 건 결국 폴더 하나를 `.tgz`로 묶어 레지스트리에 올리는 일이다. 받는 쪽은 그 묶음을 `node_modules/@acme/fmt`에 푼다. 그러니 가장 먼저 확인할 건 묶음 안에 무엇이 들어가느냐다.

처음 만든 `package.json`은 이름, 버전, `main` 세 줄뿐이었다. 폴더에는 빌드 결과 `dist/`, 원본 `src/`, 테스트, 그리고 로컬에서 쓰던 `.env`가 있다. `.gitignore`도 `.npmignore`도 없는 상태에서 묶음을 미리 본다.

```bash
# 실제로 만들지 않고 어떤 파일이 들어갈지만 보여 준다
npm pack --dry-run
```


첫 줄이 `.env`다. 이대로 `npm publish`를 쳤다면 비밀 값이 공개 레지스트리에 올라갔다. 한 번 올라간 버전은 지워도 이미 누군가 받아 갔을 수 있으니, 그 값은 바로 폐기해야 한다(대응 순서는 [커밋에 들어가면 안 되는 것](/posts/git-large-files-secrets)과 같다).

npm이 파일을 고르는 규칙은 이렇다. `files` 필드가 있으면 거기 적힌 것만 넣는다. 없으면 폴더 전체에서 `.npmignore`에 걸린 것을 빼고, `.npmignore`가 없으면 `.gitignore`를 대신 쓴다. 그리고 `package.json`, `README`, `LICENSE`는 어떤 설정이든 항상 들어가고 `.git`과 `node_modules`는 항상 빠진다.

빼는 목록(`.npmignore`)보다 넣는 목록(`files`)이 안전하다. 빼는 목록은 새 파일이 생길 때마다 갱신해야 하고, `.npmignore`를 만드는 순간 `.gitignore`가 무시되는 바람에 `.env`가 오히려 다시 들어가는 일도 생긴다. 넣는 목록은 모르는 파일이 생겨도 기본이 "안 들어감"이다.

```json
{
  "files": ["dist", "bin"]
}
```

같은 명령을 다시 돌리면 8개만 남는다.

```text
npm notice Tarball Contents
npm notice 6B README.md
npm notice 139B bin/acme-fmt.js
npm notice 174B dist/index.cjs
npm notice 99B dist/index.d.cts
npm notice 99B dist/index.d.mts
npm notice 99B dist/index.d.ts
npm notice 145B dist/index.mjs
npm notice 655B package.json
npm notice total files: 8
```

CI에서 배포한다면 이 목록을 매번 사람이 볼 수는 없다. `npm pack --dry-run --json`으로 파일 목록을 뽑아 "`dist/`와 `bin/` 밖의 파일이 있으면 실패"처럼 검사를 걸어 두면 실수가 배포 전에 멈춘다.

## package.json 필드 하나씩 읽기

완성한 `package.json`이다. 각 줄이 누구를 위한 것인지 아래 그림에서 하나씩 눌러 보자.

```json
{
  "name": "@acme/fmt",
  "version": "1.0.0",
  "type": "commonjs",
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "import": { "types": "./dist/index.d.mts", "default": "./dist/index.mjs" },
      "require": { "types": "./dist/index.d.cts", "default": "./dist/index.cjs" }
    },
    "./package.json": "./package.json"
  },
  "bin": { "acme-fmt": "./bin/acme-fmt.js" },
  "files": ["dist", "bin"],
  "engines": { "node": ">=20" },
  "sideEffects": false,
  "license": "MIT"
}
```

## exports는 문을 하나만 남긴다

`exports`를 넣고 나서 가장 먼저 듣는 불평은 "잘 되던 import가 깨졌다"다. 예전에는 `main`만 있었기 때문에 패키지 안의 아무 파일이나 경로로 직접 열 수 있었다.

```js
// 패키지 내부 파일을 직접 여는 코드
require("@acme/fmt/dist/index.cjs");
```

```text
Error [ERR_PACKAGE_PATH_NOT_EXPORTED]: Package subpath './dist/index.cjs' is not defined by "exports" in .../node_modules/@acme/fmt/package.json
  code: 'ERR_PACKAGE_PATH_NOT_EXPORTED'
```

이게 `exports`가 하는 일이다. 적어 둔 경로만 공개 API가 되고, 나머지는 파일이 있어도 열리지 않는다. 작성자 입장에서는 `dist/` 안의 파일 이름을 바꾸거나 쪼개도 사용자가 깨지지 않는다는 뜻이다. 반대로 `main`만 쓰던 패키지에 `exports`를 처음 넣는 건 그동안 사람들이 쓰던 경로를 닫는 일이라 주 버전을 올려야 하는 깨는 변경이다.

`"./package.json": "./package.json"`을 따로 연 이유도 같다. 일부 도구가 `require("@acme/fmt/package.json")`으로 버전을 읽는데, 이 줄이 없으면 그것마저 막힌다.

조건 객체는 위에서부터 읽는다. Node는 지금 환경에 맞는 조건(`import`나 `require`, `node`, 그리고 항상 `default`)을 들고 키를 순서대로 훑다가 처음 맞는 것을 고른다. 그래서 `default`는 맨 아래, `types`는 맨 위에 둔다. 순서를 바꾸면 조용히 다른 파일이 선택된다. 직접 규칙을 짜 보면 이 동작이 손에 잡힌다.

  solution={`function resolveExports(exp, subpath, conditions) {
  const isMap = (o) => o && typeof o === "object" && !Array.isArray(o);
  const pick = (t, star) => {
    if (typeof t === "string") return star === undefined ? t : t.split("*").join(star);
    if (t === null) return null;
    if (isMap(t)) {
      for (const key of Object.keys(t)) {
        if (key === "default" || conditions.includes(key)) {
          const r = pick(t[key], star);
          if (r !== undefined) return r;
        }
      }
    }
    return undefined;
  };
  const isSubpathMap = isMap(exp) && Object.keys(exp).some((k) => k.startsWith("."));
  const map = isSubpathMap ? exp : { ".": exp };
  if (subpath in map) {
    const r = pick(map[subpath]);
    return r === undefined ? null : r;
  }
  for (const key of Object.keys(map)) {
    const i = key.indexOf("*");
    if (i < 0) continue;
    const head = key.slice(0, i), tail = key.slice(i + 1);
    if (subpath.startsWith(head) && subpath.endsWith(tail) && subpath.length >= key.length - 1) {
      const star = subpath.slice(head.length, subpath.length - tail.length);
      const r = pick(map[key], star);
      return r === undefined ? null : r;
    }
  }
  return null;
}`}

## ESM과 CJS를 둘 다 내보낼 때 생기는 일

요즘 새 패키지는 ESM만 내는 경우가 늘었다. Node 22.12부터는 `require()`로 동기 ESM을 불러올 수 있어서(`require(esm)`, 자세한 건 [ES 모듈 글](/posts/js-es-modules#node에서-두-시스템이-만나는-자리)) CJS 사용자도 대부분 받을 수 있다. 그래도 사내에 Node 18·20 서비스나 Jest 설정이 남아 있으면 두 형식을 같이 내게 된다. 위 `exports`가 그 모양이다.

받는 쪽에서 두 방식 모두 잘 열린다.

```js
// esm.mjs
import { formatKRW } from "@acme/fmt";
console.log(formatKRW(1234567));
```

```js
// cjs.cjs
const { formatKRW } = require("@acme/fmt");
console.log(formatKRW(1234567));
console.log(require.resolve("@acme/fmt"));
```

```text
1,234,567원
1,234,567원
.../app/node_modules/@acme/fmt/dist/index.cjs
```

문제는 한 프로세스 안에서 두 길이 동시에 쓰일 때다. 내 앱은 ESM으로 import하고, 내가 쓰는 다른 라이브러리는 CJS라 require한다. 그러면 같은 패키지가 서로 다른 파일 두 개로 따로 평가된다. `@acme/fmt`에 호출 횟수를 세는 모듈 변수를 넣고 확인해 봤다.

```js
// hazard.mjs
import { createRequire } from "node:module";
import { formatKRW, callCount } from "@acme/fmt";
const require = createRequire(import.meta.url);
const cjs = require("@acme/fmt");

formatKRW(1000);      // ESM 쪽에서 한 번
cjs.formatKRW(2000);  // CJS 쪽에서 한 번
console.log("esm callCount:", callCount());
console.log("cjs callCount:", cjs.callCount());
```

```text
esm callCount: 1
cjs callCount: 1
```

두 번 불렀는데 각자 1이다. 카운터 하나쯤이면 웃고 넘기지만, 이 자리에 캐시, 설정 객체, 클래스가 있으면 이야기가 다르다. CJS 쪽에서 만든 객체를 ESM 쪽 클래스로 `instanceof` 검사하면 거짓이 나오고, 한쪽에서 바꾼 설정이 다른 쪽에 안 보인다. 이 현상을 이중 패키지 위험이라고 부르고, 싱글턴이 둘로 쪼개지는 모양은 [싱글턴 글](/posts/pattern-singleton#같은-모듈이-두-번-로드되는-경우)에서도 다뤘다.

막는 방법은 상태를 한쪽에만 두는 것이다. 많이 쓰는 방식이 "ESM 쪽을 얇은 래퍼로 만들기"다. 실제 코드는 CJS 한 벌에만 두고, `index.mjs`는 `import cjs from "./index.cjs"; export const formatKRW = cjs.formatKRW;`처럼 다시 내보내기만 한다. 그러면 어느 길로 들어와도 같은 모듈 인스턴스를 만난다. 상태가 전혀 없는 순수 함수 패키지라면 두 벌이어도 문제가 없으니, 위험은 "모듈 변수에 상태가 있나"로 판단한다.

## 타입이 안 잡히는 패키지

두 형식을 내보낼 때 가장 흔한 사고는 런타임이 아니라 타입에서 난다. 받는 쪽 `tsconfig.json`이 `"module": "nodenext"`라고 하자. 요즘 Node 프로젝트의 권장 설정이다. 먼저 위의 올바른 패키지로 일부러 틀린 코드를 검사해 봤다.

```ts
// use.mts
import { formatKRW } from "@acme/fmt";
const s: number = formatKRW(1);
```

```text
use.mts(1,46): error TS2322: Type 'string' is not assignable to type 'number'.
```

반가운 에러다. `formatKRW`가 문자열을 돌려준다는 타입을 제대로 찾았다는 뜻이다. 이번에는 `exports`에서 `types` 조건을 빼고 타입 파일을 `index.d.ts` 하나만 둔, 흔히 보는 모양으로 바꿨다.

```json
"exports": {
  ".": { "import": "./dist/index.mjs", "require": "./dist/index.cjs" }
}
```

```text
use.mts(1,27): error TS7016: Could not find a declaration file for module '@acme/fmt'. '.../node_modules/@acme/fmt/dist/index.mjs' implicitly has an 'any' type.
  There are types at '.../node_modules/@acme/fmt/dist/index.d.ts', but this result could not be resolved when respecting package.json "exports". The '@acme/fmt' library may need to update its package.json or typings.
```

메시지가 친절하게 원인을 말한다. TypeScript는 `exports`를 따라 `index.mjs`를 찾은 뒤 그 옆의 `index.d.mts`를 찾는다. `.mjs`의 짝은 `.d.mts`, `.cjs`의 짝은 `.d.cts`다. 맨 위 `types`에 적은 `index.d.ts`는 `exports`가 있으면 보지 않는다. 그래서 조건마다 `types`를 짝 맞춰 적거나, 파일 이름 짝을 맞춰 둔다.

한 벌의 `.d.ts`를 ESM과 CJS가 같이 쓰게 하는 것도 피한다. `.d.ts`는 패키지 `type`에 따라 한 형식으로만 해석되기 때문에, CJS 패키지의 `.d.ts`를 ESM 쪽이 쓰면 default import 모양이 실제 런타임과 어긋난다. 직접 검사하기 어렵다면 배포 전에 Are the Types Wrong(`npx @arethetypeswrong/cli --pack`)과 publint 같은 도구를 CI에 걸어 두면 이런 어긋남을 표로 보여 준다.

## bin: 명령어가 되는 패키지

`@acme/fmt`에는 터미널에서 바로 쓰는 명령도 하나 넣었다.

```js
#!/usr/bin/env node
// bin/acme-fmt.js
const { formatKRW } = require("../dist/index.cjs");
const n = Number(process.argv[2] ?? 0);
console.log(formatKRW(n));
```

첫 줄의 shebang이 없으면 macOS·리눅스에서 셸이 이 파일을 셸 스크립트로 실행하려다 문법 에러를 낸다. 윈도우에서는 npm이 `.cmd` 래퍼를 따로 만들어 준다. `bin` 파일 안에서는 `exports`가 아니라 상대 경로로 자기 파일을 여는 것도 볼 점이다. `exports`는 패키지 밖에서 들어올 때의 문이라, 패키지 안끼리는 상대 경로로 자유롭게 연다.

설치하면 이 파일이 어디에 걸리는지가 설치 방식에 따라 다르다. 아래 그림이 세 가지 길이다.

## 전역 설치, 로컬 설치, npx 중 무엇을 고르나

전역 설치는 npm의 prefix 아래 한 곳에 깐다. 이 머신은 Node를 `/opt/node22`에 깔았으니 그 아래 `lib/node_modules`와 `bin`이 쓰인다. 실험은 시스템을 더럽히지 않게 prefix를 따로 줬다.

```bash
# 지금 전역 prefix가 어디인지 본다
npm prefix -g
# 실습용 prefix에 전역 설치한다
npm install -g --prefix ./gprefix ./acme-fmt/acme-fmt-1.0.0.tgz
ls -l ./gprefix/bin
# 전역에 무엇이 깔렸는지 본다
npm ls -g --prefix ./gprefix
```

```text
/opt/node22
added 1 package in 467ms
lrwxrwxrwx 1 root root 45 Oct 23 19:34 acme-fmt -> ../lib/node_modules/@acme/fmt/bin/acme-fmt.js
.../gprefix/lib
`-- @acme/fmt@1.0.0
```

prefix가 `/usr` 같은 시스템 경로면 `sudo npm i -g`가 필요해지는데, 이건 남의 설치 스크립트를 root로 돌리는 일이라 피한다. nvm이나 fnm처럼 사용자 홈 아래에 Node를 까는 버전 관리자를 쓰면 전역 경로도 홈 아래가 되어 sudo가 필요 없다. 대신 Node 버전을 바꾸면 전역 패키지 목록도 버전마다 따로라서 "어제 깐 명령이 사라졌다"는 일이 생긴다.

고르는 기준은 그 도구가 프로젝트의 일부인가다. ESLint, TypeScript, 빌드 도구처럼 프로젝트마다 버전이 정해져야 하는 건 로컬 `devDependencies`로 둔다. 전역에 깔면 동료 머신과 CI의 버전이 달라져 "내 컴퓨터에선 되는데"가 시작된다. 프로젝트와 상관없이 내 손에 붙는 도구(예를 들어 패키지 이름을 빠르게 찾아보는 개인 도구)만 전역에 둔다. 한 번 쓰고 말 생성기는 npx로 실행한다.

npx는 로컬 `.bin`에 없으면 레지스트리에서 받아 캐시에 두고 실행한다.

```bash
# 프로젝트에 없는 패키지를 버전을 고정해 한 번 실행한다
npx semver@7.6.3 -r '^1.0.0' 1.4.2 2.0.0
```

```text
npm warn exec The following package was not found and will be installed: semver@7.6.3
1.4.2
```

터미널에서는 설치할지 물어보고, 입력이 없는 CI 환경에서는 경고만 찍고 진행한다. 여기서 버전을 빼고 `npx 이름`만 쓰는 건 위험하다. 이름을 한 글자 틀리면 남이 올려 둔 비슷한 이름의 패키지가 그 자리에서 실행된다. 스크립트나 문서에 npx를 적을 때는 `@버전`을 붙이고, CI에서는 `--yes`로 묻는 단계를 명시적으로 넘긴다.

## outdated와 update는 범위 안에서만 움직인다

배포한 패키지를 받는 쪽은 언젠가 업데이트를 한다. `chalk`를 `^4.0.0`, `ms`를 `~2.0.0`으로 적고 일부러 오래된 버전을 깔아 둔 프로젝트에서 확인했다.

```bash
# 범위 안의 최신(Wanted)과 레지스트리 최신(Latest)을 비교한다
npm outdated
```

```text
Package  Current  Wanted  Latest  Location            Depended by
chalk      4.0.0   4.1.2   6.0.1  node_modules/chalk  old
ms         2.0.0   2.0.0   2.1.3  node_modules/ms     old
```

세 열을 읽는 법만 알면 된다. Current는 지금 깔린 것, Wanted는 `package.json` 범위 안에서 가장 높은 것, Latest는 레지스트리의 `latest` 태그다. 오래된 게 있으면 종료 코드가 1이라 CI에서 그대로 쓰면 빌드가 깨진다는 것도 알아 둘 점이다.

```bash
# 범위 안에서만 올린다
npm update
npm outdated
```

```text
Package  Current  Wanted  Latest  Location            Depended by
chalk      4.1.2   4.1.2   6.0.1  node_modules/chalk  old
ms         2.0.0   2.0.0   2.1.3  node_modules/ms     old
```

chalk는 Wanted인 4.1.2까지 올라갔고 6.x로는 가지 않았다. ms는 `~2.0.0`이라 2.1.3이 범위 밖이니 그대로다. `npm update`가 고친 건 lockfile과 `node_modules`이고, npm 10에서는 `package.json`의 범위 문자열(`^4.0.0`)을 바꾸지 않는다. 범위를 넘어 주 버전을 올리려면 `npm install chalk@6`처럼 직접 고른다. 주 버전은 깨는 변경이 들어오는 자리라 변경 기록을 읽고 하나씩 올린다.

패키지 작성자 입장에서 이게 뜻하는 바가 있다. 사용자의 `^1.0.0`은 내가 내는 1.x를 다음 `npm update`에서 자동으로 받는다. 1.x 안에서 `exports` 경로를 닫거나 `engines`를 올리면, 사용자는 아무것도 안 했는데 깨진다. 무엇이 깨는 변경인지는 [Semantic Versioning 글](/posts/semantic-versioning#무엇이-깨지는-변경인가)에 정리해 뒀다.

## 배포 직전에 보는 것과 provenance

`npm publish --dry-run`은 로그인 없이도 어디에 어떤 태그로 올라갈지까지 보여 준다.

```bash
# 실제로 올리지 않고 배포 과정을 끝까지 흉내 낸다
npm publish --dry-run
npm publish --dry-run --access public
```

```text
npm warn This command requires you to be logged in to https://registry.npmjs.org/ (dry-run)
npm notice Publishing to https://registry.npmjs.org/ with tag latest and default access (dry-run)
+ @acme/fmt@1.0.0
npm warn This command requires you to be logged in to https://registry.npmjs.org/ (dry-run)
npm notice Publishing to https://registry.npmjs.org/ with tag latest and public access (dry-run)
+ @acme/fmt@1.0.0
```

두 줄을 본다. 레지스트리 주소가 의도한 곳인지(사내 레지스트리에 올릴 거면 `publishConfig.registry`나 `.npmrc`의 스코프 설정이 먹었는지), 그리고 access다. 스코프 패키지는 기본이 restricted라 공개 레지스트리에 처음 올릴 때 `--access public`이 없으면 유료 비공개 패키지로 올리려다 실패한다. 반대로 사내 패키지를 실수로 공개 레지스트리에 올리지 않으려면 `"publishConfig": { "registry": "사내 주소" }`를 박아 두거나 `"private": true`를 쓴다. `private`가 켜져 있으면 npm은 publish 자체를 거부한다.

`prepublishOnly` 스크립트에 빌드와 테스트를 걸어 두면 `dist/`가 낡은 채로 올라가는 일을 막는다. `prepare`는 `npm install` 때도 돌기 때문에 배포 전 검사에는 `prepublishOnly`가 맞다.

사람 노트북에서 배포하는 대신 CI에서 배포하면 provenance를 붙일 수 있다. "이 tarball은 이 저장소의 이 커밋을 이 워크플로가 빌드해서 올렸다"는 서명된 증명이다. 아래 그림이 GitHub Actions에서 그 흐름이다.

워크플로에서는 `permissions: id-token: write`를 주고 `npm publish --provenance --access public`을 쓴다. 2025년부터는 npm이 OIDC 기반 신뢰 배포(trusted publishing)도 지원해서, 레지스트리에 "이 저장소의 이 워크플로만 배포할 수 있다"고 등록해 두면 CI에 장기 npm 토큰을 넣지 않아도 된다. 최신 npm CLI(11.x대)가 필요하고 GitHub Actions와 GitLab CI 같은 지원 환경에서만 되니, 쓰기 전에 npm 공식 문서에서 현재 조건을 확인한다. 토큰을 쓴다면 쓰기 권한 토큰은 패키지 범위를 좁히고 수명을 짧게 둔다. 토큰이 새면 공격자는 내 이름으로 악성 버전을 올릴 수 있다.

## 여러 패키지를 한 저장소에서: npm workspaces

`@acme/fmt`를 쓰는 관리자 앱도 같은 저장소에 두고 싶다. 고칠 때마다 배포하고 다시 받기는 번거롭다. npm은 7부터 workspaces로 이걸 지원한다.

```json
{
  "name": "acme-monorepo",
  "private": true,
  "workspaces": ["packages/*"]
}
```

```bash
# 루트에서 한 번 설치하면 워크스페이스끼리 링크된다
npm install
ls -l node_modules/@acme
npm ls
```

```text
lrwxrwxrwx 1 root root 20 Oct 23 23:54 admin -> ../../packages/admin
lrwxrwxrwx 1 root root 18 Oct 23 23:54 fmt -> ../../packages/fmt
acme-monorepo@ .../ws
+-- @acme/admin@0.1.0 -> ./packages/admin
| `-- @acme/fmt@1.0.0 deduped -> ./packages/fmt
`-- @acme/fmt@1.0.0 -> ./packages/fmt
```

admin이 `"@acme/fmt": "^1.0.0"`을 원하고 워크스페이스 안의 fmt가 1.0.0이라 범위가 맞으니, npm은 레지스트리 대신 로컬 폴더를 링크했다. fmt를 고치면 admin이 바로 그 코드를 본다. 여기서 버전 범위가 안 맞으면 npm은 조용히 레지스트리에서 받으려 하는데, 이 차이 때문에 pnpm·Yarn은 `workspace:` 프로토콜로 "반드시 로컬"을 강제한다. 그 차이와 공용 패키지를 빌드형으로 둘지 소스형으로 둘지는 [프런트엔드 모노레포 글](/posts/frontend-monorepo)에서 길게 다뤘다.

스크립트 실행은 `-w`로 대상을 고른다.

```bash
# 모든 워크스페이스의 build를 돌린다
npm run build --workspaces
# 하나만 골라 돌린다
npm run build -w @acme/fmt
```

```text
> @acme/admin@0.1.0 build
> echo build admin
build admin
> @acme/fmt@1.0.0 build
> echo build fmt
build fmt
```

출력 순서를 보면 admin이 fmt보다 먼저 빌드됐다. npm은 워크스페이스를 의존 관계 순서가 아니라 선언(폴더 정렬) 순서대로 돈다. admin이 fmt의 `dist/`를 import한다면 깨끗한 CI에서는 admin 빌드가 실패한다. 패키지가 몇 개 안 되면 루트 스크립트에 순서를 직접 적고(`npm run build -w @acme/fmt && npm run build -w @acme/admin`), 늘어나면 의존 그래프를 보고 순서와 캐시를 관리하는 Turborepo나 Nx, 또는 `pnpm -r`처럼 위상 정렬을 해 주는 도구로 옮긴다.

## 현장에서 패키지 때문에 막히는 순간

증상에서 원인으로 거꾸로 가는 경우가 대부분이라, 자주 본 것을 증상 기준으로 적어 둔다.

`ERR_PACKAGE_PATH_NOT_EXPORTED`가 나면 받는 쪽이 `exports`에 없는 내부 경로를 열고 있다. 받는 쪽이 공개 경로로 바꾸는 게 맞고, 정말 필요한 경로라면 작성자가 `exports`에 추가한다.

`ERR_REQUIRE_ESM`이나 `Cannot use import statement outside a module`이 나면 패키지가 ESM만 내는데 받는 쪽이 CJS다. Node 22.12 이상으로 올리면 동기 ESM은 `require`로 열린다. 못 올리면 작성자가 `require` 조건을 따로 낸다.

타입이 `any`로 잡히거나 TS7016이 나면 `exports` 안 `types` 조건과 `.d.mts`·`.d.cts` 짝을 본다. 위 실험처럼 에러 메시지가 원인을 대부분 말해 준다.

설치한 명령이 `command not found`면 로컬 설치인지 전역 설치인지부터 본다. 로컬이면 `npx`나 `npm run`으로 부르고, 전역이면 `npm prefix -g`의 `bin`이 PATH에 있는지 본다. `permission denied`면 bin 파일의 실행 권한이나 shebang 줄의 줄바꿈(CRLF)을 의심한다. 윈도우에서 만든 파일이 `#!/usr/bin/env node\r`이 되면 리눅스가 `node\r`이라는 프로그램을 찾는다.

배포는 했는데 받는 쪽에 옛 코드가 보이면 `prepublishOnly` 없이 빌드를 빠뜨렸거나, 같은 버전이 아니라 다른 dist-tag를 보고 있을 수 있다. `npm view @acme/fmt dist-tags`로 태그가 가리키는 버전을 확인한다.

## 패키지는 package.json이 곧 인터페이스다

함수를 옮기는 건 쉽고, 어렵게 만드는 건 그 함수를 감싼 계약이다. 무엇이 들어가는지는 `files`가, 어떤 문으로 들어오는지는 `exports`가, 어떤 형식과 타입으로 보이는지는 조건과 `.d.mts`·`.d.cts` 짝이 정한다. 올리기 전에는 `npm pack --dry-run`으로 내용물을, `publish --dry-run`으로 목적지를 확인한다. 이 계약을 1.x 안에서 좁히면 사용자의 다음 `npm update`가 깨진다는 것까지 기억하면 된다.

## 면접에서 나올 만한 질문

### package.json의 main과 exports는 무엇이 다른가요?

`main`은 패키지 진입점 하나만 정하고 내부 파일은 경로로 다 열린다. `exports`는 공개할 경로를 명시하고, 거기 없는 경로는 `ERR_PACKAGE_PATH_NOT_EXPORTED`로 막는다. 또 `import`·`require`·`types` 같은 조건별로 다른 파일을 줄 수 있다. `exports`가 있으면 최신 Node는 `main`을 보지 않으니, `main`은 오래된 도구를 위한 대비로 남긴다.

### 기존 패키지에 exports를 처음 추가하면 마이너 버전으로 내도 되나요?

안 된다. 그동안 사용자가 쓰던 `패키지/dist/...` 같은 깊은 경로가 막히니 깨는 변경이다. 주 버전을 올리거나, 기존 경로를 `exports`에 그대로 열어 두고 다음 주 버전에서 닫는다.

### ESM과 CJS를 둘 다 내보낼 때 무엇을 조심하나요?

이중 패키지 위험이다. 한 프로세스에서 ESM 경로와 CJS 경로가 같이 쓰이면 같은 패키지가 두 번 평가되어 모듈 상태, 캐시, 클래스가 둘로 나뉜다. 상태가 있는 패키지라면 실제 구현을 한 형식에만 두고 다른 쪽은 다시 내보내기만 하는 래퍼로 만든다. 타입도 `.d.mts`와 `.d.cts`를 따로 둬서 형식마다 맞는 선언을 주고, Node 22.12 이상만 지원해도 된다면 ESM 한 벌만 내는 것도 고려한다.

### exports 조건의 순서는 왜 중요한가요?

Node와 TypeScript가 조건 객체를 위에서부터 읽다가 처음 맞는 키를 고르기 때문이다. `default`를 위에 두면 아래 조건은 절대 선택되지 않고, `types`를 아래에 두면 TypeScript가 런타임 파일을 먼저 잡는다. 그래서 `types`는 맨 위, `default`는 맨 아래에 둔다.

### npm 패키지에 원치 않는 파일이 들어가지 않게 하려면요?

`files` 필드로 넣을 것만 적는 화이트리스트를 쓴다. `.npmignore`는 빼는 방식이라 새 파일이 생길 때 놓치기 쉽고, 만드는 순간 `.gitignore`가 무시되는 함정도 있다. 배포 전에 `npm pack --dry-run`으로 내용물을 확인하고, CI에서 그 목록을 검사하면 더 안전하다.

### 전역 설치, 로컬 설치, npx는 언제 쓰나요?

프로젝트의 빌드와 검사에 쓰는 도구는 버전이 고정되도록 로컬 `devDependencies`에 두고 `npm run`이나 `npx`로 부른다. 전역 설치는 프로젝트와 상관없는 개인 도구에만 쓴다. 한 번 쓰는 생성기는 npx로 실행하되, 오타로 엉뚱한 패키지가 실행되지 않게 `@버전`을 붙인다.

### npm update를 하면 주 버전도 올라가나요?

아니다. `npm update`는 `package.json` 범위 안에서 가장 높은 버전(outdated의 Wanted)까지만 올리고 lockfile을 갱신한다. `^4.0.0`이면 4.x 안에서만 움직이고 6.x로는 가지 않는다. 주 버전은 `npm install 이름@6`으로 직접 올린다.

### provenance는 무엇을 증명하나요?

이 tarball이 어떤 저장소의 어떤 커밋에서 어떤 CI 워크플로로 빌드되었는지를 서명으로 남긴다. GitHub Actions에서는 OIDC 토큰으로 신원을 받고 Sigstore가 서명해 공개 기록에 남긴다. 배포 토큰이 털려 누가 노트북에서 악성 버전을 올리면 증명이 없거나 다른 출처가 찍히니, 받는 쪽이 `npm audit signatures`로 의심할 근거가 된다. 코드가 안전하다는 증명은 아니고 출처의 증명이다.
