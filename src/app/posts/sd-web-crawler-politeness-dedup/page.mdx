이 시리즈에서 이 글의 자리: [⑳ 웹 크롤러 ①: 시드에서 프런티어까지](/posts/sd-web-crawler-architecture)에서 크롤러의 부품과 URL 하나가 도는 길을 정했다. 이 글은 같은 장의 두 번째 글로, 그때 미뤄 둔 프런티어 안쪽(호스트별 줄과 우선순위), `robots.txt`, 같은 페이지를 두 번 저장하지 않는 법, 끝없이 이어지는 링크를 다룬다. 다음 글은 새 사례인 [㉒ 알림 시스템 ①](/posts/sd-notification-system)이다.

앞 글의 BFS 크롤러를 스레드 여러 개로 바꿔 하룻밤 돌렸다고 해 보자. 아침에 어느 쇼핑몰 운영자에게서 메일이 와 있다. 새벽 3시에 한 IP에서 초당 수십 건씩 요청이 와서 서버가 느려졌고, 그 IP는 막았다는 내용이다. 크롤러 입장에서는 링크를 순서대로 따라갔을 뿐이다. 그런데 한 페이지의 링크는 대개 같은 사이트를 가리키니, 프런티어의 앞부분이 한 사이트 주소로 꽉 차 있었다.

이 글의 절반은 남의 서버를 배려하는 이야기고, 나머지 절반은 내 자원을 아끼는 이야기다. 둘 다 프런티어 설계에서 풀린다.

## 같은 사이트에 요청이 몰리는 모습

로컬에 Node 서버 두 개를 띄워 호스트 A와 B로 삼았다. 프런티어에는 A의 URL 6개 뒤에 B의 URL 2개가 있다. 서버는 페이지 하나를 만드는 데 50ms를 쓰고, 요청이 들어온 시각을 기록한다. 먼저 워커 4개가 프런티어 앞에서부터 URL을 집어 가는 단순한 방식으로 돌렸다.

```text
[naive]
  A 요청 시각(ms): 108, 109, 110, 110, 189, 189
  A 요청 간격 최소: 0ms
  B 요청 시각(ms): 190, 190
  B 요청 간격 최소: 0ms
  전체 걸린 시간: 약 240ms
```

A는 같은 밀리초 근처에 네 번, 조금 뒤에 두 번 더 맞았다. 이 크롤러가 수백 개의 워커를 갖고 있었다면 A는 순간적으로 수백 개의 동시 요청을 받는다. 개인 블로그나 작은 쇼핑몰은 이 정도에 느려지거나 멈춘다. 운영자는 크롤러 IP를 막고, 크롤러는 그 사이트를 영영 못 읽는다.

규칙을 바꿔서 다시 돌렸다. 호스트마다 줄을 하나씩 두고, 같은 호스트에는 한 번에 하나만 보내고, 끝나면 300ms를 쉰다.

```text
[polite]
  A 요청 시각(ms): 28, 393, 746, 1102, 1455, 1810
  A 요청 간격 최소: 353ms
  B 요청 시각(ms): 28, 396
  B 요청 간격 최소: 368ms
  전체 걸린 시간: 약 1860ms
```

A로 가는 요청 사이가 늘 350ms 이상 벌어졌다(응답 50ms에 쉬는 300ms). B는 A를 기다리지 않고 처음부터 따로 진행했다. 전체 시간은 240ms에서 1,860ms로 늘었다. 한 사이트만 보면 느려진 게 맞다. 하지만 실제 크롤러는 수백만 개 사이트를 동시에 돈다. 사이트 하나하나는 천천히, 전체는 넓게 도는 것이 예의 바른 크롤러의 기본 모양이다.

## 호스트마다 줄을 하나씩 두는 구조

위 실험의 두 번째 방식을 크롤러 부품으로 옮기면 이렇게 된다. 이 줄들을 뒤쪽 큐(back queue)라고 부른다. 다운로더 바로 앞에 있어서다.

- 큐 라우터: 프런티어에 들어온 URL을 호스트별 줄로 보낸다. 한 줄에는 한 호스트의 URL만 있다.
- 매핑 테이블: 어느 호스트가 몇 번 줄인지 적어 둔 표다.
- 큐 선택기: 지금 보내도 되는 줄을 골라 워커에게 넘긴다.
- 워커: 줄 하나에서 URL을 하나씩 꺼내 내려받는다. 같은 줄의 다음 URL은 정해진 시간만큼 쉰 뒤에 꺼낸다.

줄 수는 호스트 수만큼 늘릴 수 없다. 호스트는 수억 개다. 그래서 줄 수는 워커 수의 몇 배 정도로 고정하고, 줄 하나가 비면 그 줄에 새 호스트를 배정한다. 줄마다 "다음에 보내도 되는 시각"을 들고 있고, 선택기는 이 시각이 가장 이른 줄을 꺼낸다. 최소 힙(가장 작은 값이 늘 맨 위에 오는 자료 구조)에 넣으면 이 선택이 줄 수에 상관없이 빠르다.

쉬는 시간은 고정값보다 서버 상태에 맞춰 바꾸는 편이 낫다. 흔한 방법은 직전 응답에 걸린 시간의 몇 배(예: 10배)를 쉬는 것이다. 빠른 서버에는 자주, 느린 서버에는 드물게 간다. 서버가 `429 Too Many Requests`나 `503`을 돌려주면 쉬는 시간을 크게 늘리고 `Retry-After` 헤더가 있으면 그만큼 기다린다. 서버 쪽에서 이런 응답을 어떻게 만드는지는 [요청 수 제한을 API에 붙이기](/posts/rate-limiting-in-practice)에 있고, 늘리는 간격을 고르는 법은 [지수 백오프와 지터](/posts/exponential-backoff-jitter)에 있다.

한 가지 함정이 있다. 호스트 이름은 다른데 같은 서버인 경우다. 무료 호스팅에 올라간 수천 개의 사이트가 IP 하나를 같이 쓰면, 호스트별로 예의를 지켜도 그 서버는 수천 배의 요청을 받는다. 그래서 큰 크롤러는 호스트뿐 아니라 IP 단위의 한도도 함께 둔다.

## 중요한 페이지를 먼저 꺼내는 앞쪽 큐

뒤쪽 큐는 사이트를 보호하지만 무엇을 먼저 내려받을지는 정하지 않는다. 검색용 크롤러에게 대형 포털의 첫 화면과 아무도 안 보는 오래된 게시판 페이지는 같은 무게가 아니다. 그래서 뒤쪽 큐 앞에 줄을 하나 더 둔다. 이걸 앞쪽 큐(front queue)라고 한다.

- 우선순위 계산기: URL마다 점수를 매긴다. 많은 페이지가 가리키는 페이지인지(PageRank 같은 링크 점수), 사람들이 실제로 많이 찾는지, 자주 바뀌는지, 시드에서 몇 번 건너왔는지 같은 것을 섞는다.
- 앞쪽 큐 f1~fn: 점수 구간마다 줄이 하나다. f1이 가장 높다.
- 앞쪽 선택기: 높은 줄을 더 자주 고르되 낮은 줄도 가끔 고른다. 예를 들어 f1에서 60%, f2에서 30%, f3에서 10%를 뽑는 식이다. 높은 줄만 고르면 낮은 줄은 영영 굶는다.

앞쪽은 "무엇을 먼저", 뒤쪽은 "얼마나 천천히"를 맡는다. 두 가지를 한 줄에서 처리하려고 하면 중요한 사이트의 URL이 앞에 몰려 그 사이트에 요청이 몰린다. 뒤쪽 줄이 비면 선택기가 앞쪽 큐에서 URL을 당겨 와 채운다. 이 앞뒤 두 단 구조는 Mercator라는 연구용 크롤러에서 알려진 방식이고, 면접에서 "프런티어를 어떻게 설계하나요"에 대한 표준 답이 됐다.

## robots.txt를 먼저 읽는다

사이트 운영자가 크롤러에게 "여기는 오지 마"라고 말하는 방법이 `robots.txt`다. 사이트 루트(`/robots.txt`)에 두는 텍스트 파일이고, 2022년에 RFC 9309로 표준이 됐다. 강제력은 없다. 지키는 건 크롤러의 몫이다. 로컬 서버에 아래 파일을 두고, 직접 짠 해석기로 URL마다 허용 여부를 판단했다.

```text
User-agent: *
Disallow: /private/
Disallow: /search
Allow: /private/press/
Disallow: /*.pdf$

User-agent: studybot
Disallow: /tmp/
```

```text
[anybot] 적용 규칙 4개
  /blog/1              허용  (맞는 규칙 없음)
  /private/memo        금지  (Disallow: /private/)
  /private/press/2026  허용  (Allow: /private/press/)
  /search?q=x          금지  (Disallow: /search)
  /files/a.pdf         금지  (Disallow: /*.pdf$)
  /files/a.pdf?v=2     허용  (맞는 규칙 없음)
  /tmp/x               허용  (맞는 규칙 없음)
[studybot] 적용 규칙 1개
  /blog/1              허용  (맞는 규칙 없음)
  /private/memo        허용  (맞는 규칙 없음)
  /private/press/2026  허용  (맞는 규칙 없음)
  /search?q=x          허용  (맞는 규칙 없음)
  /files/a.pdf         허용  (맞는 규칙 없음)
  /files/a.pdf?v=2     허용  (맞는 규칙 없음)
  /tmp/x               금지  (Disallow: /tmp/)
robots.txt 응답 404 → 제한 없음으로 본다
robots.txt 응답 503 → 사이트 전체 금지로 본다
```

읽는 규칙을 결과와 함께 짚어 보자. 규칙은 경로 앞부분 일치로 비교한다. `/search`는 `/search?q=x`도 막는다. 여러 규칙이 맞으면 가장 긴 규칙이 이긴다. `/private/press/2026`은 `Disallow: /private/`(9글자)와 `Allow: /private/press/`(15글자)에 다 맞지만 긴 쪽인 Allow가 이겼다. `*`는 아무 글자나, `$`는 끝을 뜻한다. 그래서 `/*.pdf$`는 `a.pdf`는 막고 `a.pdf?v=2`는 막지 못했다.

`studybot` 결과가 흔한 실수를 보여 준다. 운영자는 아마 "모든 봇에 적용되는 규칙에 더해 studybot은 `/tmp/`도 막는다"라고 생각했을 것이다. 하지만 크롤러는 자기 이름과 맞는 그룹이 있으면 그 그룹만 따르고 `*` 그룹은 보지 않는다. 그래서 studybot에게는 `/private/`가 열려 버렸다. 크롤러를 만드는 쪽이라면 표준대로 해석하면 되지만, `robots.txt`를 쓰는 쪽이라면 자기 이름 그룹에 공통 규칙을 다시 적어야 한다.

마지막 두 줄은 `robots.txt` 자체를 못 받았을 때다. 404처럼 파일이 없으면 제한이 없다고 보고, 503처럼 서버 오류면 사이트 전체를 금지로 본다. 서버가 아픈데 규칙을 모른다고 마구 내려받으면 안 되기 때문이다. RFC 9309는 받아 둔 파일을 24시간 넘게 캐시하지 말라고 권한다. 크롤러는 호스트마다 `robots.txt`를 한 번 받아 두고, URL을 프런티어에 넣기 전 필터 단계에서 확인한다.

몇 가지를 더 챙긴다. `Crawl-delay` 줄은 표준에 없다. Bing 같은 일부 크롤러는 따르지만 구글은 무시한다고 밝히고 있으니, 있으면 쉬는 시간의 하한으로 쓰는 정도가 무난하다. 페이지 안의 `<meta name="robots" content="noindex">`나 링크의 `rel="nofollow"`는 `robots.txt`와 별개로, 내려받은 뒤 저장이나 링크 추출 단계에서 지킨다. 크롤러의 User-Agent에는 이름과 연락처 URL을 넣는다. 운영자가 문제를 겪을 때 IP를 막기 전에 연락할 곳을 주는 것이다.

## 같은 페이지, 다른 주소

URL 중복 확인은 문자열이 같은지를 본다. 그런데 같은 페이지를 가리키는 주소는 생각보다 여러 모양이다. 대소문자, 기본 포트, `./`와 `../`, 끝의 `/`, 광고 추적용 매개변수, 매개변수 순서, `#` 뒤가 다 다를 수 있다. 확인하기 전에 URL을 한 가지 모양으로 맞추는 작업(canonicalization)을 한다. 아래 그림의 조각을 눌러 보면 각 부분이 어떻게 바뀌는지 볼 수 있다.

직접 만든 함수로 여러 모양을 넣어 봤다.

```js
function canonical(input) {
  const u = new URL(input);   // 스킴·호스트 소문자, 기본 포트 제거, ./ ../ 정리
  u.hash = "";                // # 뒤 제거
  const drop = (k) => k.startsWith("utm_") || k === "fbclid" || k === "gclid";
  const params = [...u.searchParams].filter(([k]) => !drop(k)).sort(([a], [b]) => a.localeCompare(b));
  u.search = new URLSearchParams(params).toString();
  if (u.pathname !== "/" && u.pathname.endsWith("/")) u.pathname = u.pathname.slice(0, -1); // 끝의 / 제거
  return u.href;
}
```

```text
http://shop.example.com/items/42             <= HTTP://Shop.Example.com:80/items/42
http://shop.example.com/items/42             <= http://shop.example.com/items/42/
http://shop.example.com/items/42             <= http://shop.example.com/items/./42#reviews
http://shop.example.com/items/42             <= http://shop.example.com/a/../items/42?utm_source=mail
http://shop.example.com/items/42?a=1&b=2     <= http://shop.example.com/items/42?b=2&a=1
http://shop.example.com/items/42?a=1&b=2     <= http://shop.example.com/items/42?a=1&b=2&fbclid=xyz
http://shop.example.com/items/%34%32         <= http://shop.example.com/items/%34%32
```

일곱 개 중 여섯 개가 두 모양으로 모였다. 마지막 줄은 못 잡았다. `%34%32`는 `42`를 퍼센트 인코딩한 것인데, 브라우저 표준 URL 파서는 이걸 풀지 않는다. RFC 3986은 숫자와 영문자처럼 인코딩할 필요가 없는 글자의 인코딩은 풀어도 된다고 하니, 크롤러는 그 부분을 직접 처리해야 한다. 끝의 `/`를 지운 것도 늘 맞지는 않는다. `/items/42`와 `/items/42/`를 다른 페이지로 주는 서버도 있다. 그래서 이 규칙들은 "같을 가능성이 높다"는 판단이고, 확실한 판단은 다음 절의 내용 비교가 한다.

사이트가 직접 알려 주는 정보도 쓴다. 페이지 안의 `<link rel="canonical" href="...">`는 "이 페이지의 대표 주소는 이것"이라는 뜻이고, `http`에서 `https`로, `example.com`에서 `www.example.com`으로 가는 301 리다이렉트도 대표 주소를 알려 준다.

## 수십억 개 URL을 봤는지 기억하기

URL 중복 확인은 모든 링크마다 한 번씩 묻는다. 페이지 하나에 링크가 수십 개니, 내려받는 양의 수십 배로 불린다. 처음에는 메모리의 Set으로 충분했다. 100만 개를 넣고 메모리를 재 봤다.

```text
n=1,000,000 p=0.01 → m=9,585,059비트(1.14MiB), k=7
Set 1,000,000개: 힙 약 141MiB
블룸 필터: 1.14MiB
넣은 URL을 "없다"고 한 수: 0
안 넣은 URL 100만 개 중 "있다"고 한 수: 9,982 (1.00%)
```

URL 문자열을 Set에 넣으면 100만 개에 약 141MiB다. 수십억 개면 수백 GB가 되니 한 서버 메모리에는 못 들어간다. 줄이는 방법은 두 갈래다.

하나는 URL 대신 64비트 해시만 저장하는 것이다. URL 하나가 8바이트가 되니 10억 개에 8GB다. 그래도 크면 디스크 기반 키-값 저장소에 넣는다. 다른 하나는 블룸 필터다. 같은 100만 개를 1.14MiB에 담았다. 대가는 질문의 1% 정도에 "봤다"고 잘못 답하는 것이다. 넣은 URL을 "없다"고 한 적은 0번이다. 비트 배열과 해시 몇 개로 이게 어떻게 되는지, 크기와 해시 개수를 어떻게 고르는지는 [블룸 필터](/posts/bloom-filter)에서 자세히 다뤘다.

크롤러에서 블룸 필터의 오답이 무슨 뜻인지 따져 봐야 한다. "봤다"는 오답이 나오면 그 URL은 프런티어에 들어가지 못한다. 처음 보는 페이지를 영영 못 내려받는다는 뜻이다. 반대로 같은 URL을 두 번 내려받는 일은 없다. 1%를 놓쳐도 되는지는 서비스가 정한다. 놓치면 안 되는 중요한 사이트라면, 블룸 필터를 앞에 두고 "봤다"고 할 때만 디스크의 정확한 기록을 한 번 더 확인한다. 대부분의 처음 보는 URL은 블룸 필터에서 바로 "없다"를 받으니 디스크를 읽는 일은 적다.

## 내용이 거의 같은 페이지

앞 글에서 본문 해시로 똑같은 페이지를 걸렀다. 문제는 "거의 같은" 페이지다. 조회수, 현재 시각, 광고 한 줄만 다른 페이지는 해시가 완전히 달라진다. 이런 페이지를 찾는 대표적인 방법이 SimHash다. 비슷한 문서는 비슷한 지문이 나오도록 만든 64비트 값이다. 만드는 방법은 이렇다. 문서를 연속한 세 단어씩 잘라(싱글, shingle) 각 조각을 64비트로 해시한다. 64개 칸마다 조각 해시의 그 비트가 1이면 +1, 0이면 -1을 더한다. 다 더한 뒤 양수인 칸은 1, 아닌 칸은 0으로 하면 지문이 된다. 조각 몇 개가 바뀌어도 다수결이 거의 그대로라 지문도 몇 비트만 바뀐다.

같은 기사에 조회수만 다른 B, 광고 한 줄을 더한 C, 전혀 다른 기사 D를 만들어 비교했다.

```text
A sha256 e39979e50113  simhash 9191d8879b1e1de7
B sha256 718aff8c7928  simhash 9091da879b1e5de7
C sha256 23967590da13  simhash b081da059b1e5de7
D sha256 72b349fe4503  simhash a5729b20c009d619
A-B 다른 비트 3/64
A-C 다른 비트 7/64
A-D 다른 비트 37/64
C-D 다른 비트 34/64
```

SHA-256은 넷 다 완전히 다르다. SimHash는 조회수만 다른 A와 B가 3비트, 광고를 더한 C가 7비트 차이고, 다른 기사 D는 37비트나 차이 난다. 무작위로 고른 두 값은 평균 32비트가 다르니, D는 남이나 다름없다. 구글이 2007년에 발표한 논문에서는 64비트 SimHash에서 3비트 이하 차이를 거의 같은 페이지로 봤다. 이 실험에서 그 기준이면 B는 거르고 C는 남긴다. 문서가 짧을수록 한 줄이 차지하는 비중이 커서 차이가 커진다. 기준값은 실제 데이터에서 잘못 거른 것과 놓친 것을 보며 맞춘다.

수십억 개 지문 중에서 3비트 이내인 것을 어떻게 빨리 찾을까. 64비트를 16비트씩 네 덩어리로 나누면, 3비트 이하로 다른 두 지문은 네 덩어리 중 적어도 하나가 완전히 같다. 다른 비트 3개가 덩어리 네 개에 다 들어갈 수 없기 때문이다. 그래서 덩어리별로 색인을 만들고, 한 덩어리가 같은 후보만 꺼내 나머지 비트를 비교한다.

## 끝없이 새 주소를 만드는 페이지

어떤 페이지는 내려받을 때마다 처음 보는 URL을 만들어 낸다. 크롤러를 붙잡아 두는 이런 구조를 스파이더 트랩(spider trap)이라고 한다. 일부러 만든 함정도 있지만 대부분은 실수다. 로컬 서버에 흔한 두 가지를 만들었다. 하나는 "다음 달" 링크가 끝없이 이어지는 달력이고, 하나는 `/docs/` 아래 페이지마다 `href="docs/"`라는 상대 링크가 있어서 `/docs/docs/docs/...`가 생기는 경우다.

```text
[규칙 없음] 내려받기 40번, 프런티어에 남은 것 2개
  마지막에 넣은 URL: /docs/docs/docs/docs/docs/docs/docs/docs/docs/docs/docs/docs/docs/docs/docs/docs/docs/docs/docs/docs/  /calendar?month=2028-06
[규칙 있음] 내려받기 10번, 프런티어에 남은 것 0개
  마지막에 넣은 URL: /calendar?month=2027-04  /calendar?month=2027-05
  막은 이유: {"같은 경로 조각 반복":1,"깊이 8 초과":1}
```

규칙이 없으면 40번에서 강제로 멈출 때까지 두 함정을 번갈아 팠고, 프런티어는 비지 않았다. URL 중복 확인은 아무 도움이 안 된다. 모든 URL이 정말로 처음 보는 주소이기 때문이다. 규칙을 넣으니 10번 만에 끝났다. 같은 경로 조각이 두 번 나오는 URL을 막아 `/docs/docs/`를 끊었고, 시드에서 8번 넘게 건너온 URL을 막아 달력을 끊었다.

이 글의 실험에서는 단순한 규칙 두 개로 충분했지만 실제로는 여러 겹을 둔다. URL 길이 상한, 경로 깊이 상한, 같은 경로에 매개변수만 다른 URL 수의 상한, 호스트마다 하루에 내려받을 페이지 예산 같은 것이다. 예산은 함정이 무엇이든 그 호스트에서 쓰는 자원에 천장을 씌운다. 그래도 새는 함정은 사람이 발견해 차단 목록에 넣는다. 호스트마다 내려받은 페이지 수와 새로 발견한 URL 수를 대시보드로 보고 있으면, 비정상적으로 URL을 쏟아 내는 호스트가 눈에 띈다.

## 바뀐 페이지만 다시 내려받기

다른 하나는 페이지마다 바뀌는 속도를 학습하는 것이다. 다시 와 봤는데 바뀌었으면 간격을 절반으로, 그대로면 두 배로 한다. 실제로 ETag를 주는 로컬 서버로 돌려 봤다. 간격은 1시간에서 일주일(168시간) 사이로 묶었다.

```text
방문 1: 200 본문 24바이트 첫 방문  간격 24h → 24h
방문 2: 304 본문  0바이트 그대로  간격 24h → 48h
방문 3: 200 본문 23바이트 바뀜  간격 48h → 24h
방문 4: 200 본문 23바이트 바뀜  간격 24h → 12h
방문 5: 304 본문  0바이트 그대로  간격 12h → 24h
방문 6: 304 본문  0바이트 그대로  간격 24h → 48h
방문 7: 304 본문  0바이트 그대로  간격 48h → 96h
```

가격이 바뀌는 동안에는 간격이 12시간까지 줄었고, 조용해지자 96시간까지 늘었다. 304로 끝난 방문은 본문이 0바이트다. 모든 서버가 ETag나 `Last-Modified`를 제대로 주지는 않으니, 그런 서버에서는 내려받은 뒤 본문 해시를 비교해 바뀌었는지 판단한다. 사이트맵의 `<lastmod>`나 RSS 피드가 있으면 그걸 먼저 보고 바뀐 페이지만 앞쪽 큐의 높은 줄에 넣는 것도 좋다. 다시 방문할 URL도 새 URL과 같은 프런티어로 들어가니, 앞쪽 큐의 점수에 "다시 볼 때가 됐는지"를 섞는다.

## 다음에 읽을 글

프런티어는 앞뒤 두 단이다. 앞쪽 큐가 중요한 페이지를 먼저 꺼내고, 뒤쪽 큐가 호스트마다 한 번에 하나씩 쉬어 가며 보낸다. 그 앞의 필터에서 `robots.txt`와 함정 규칙을 지키고, URL을 한 모양으로 맞춘 뒤 블룸 필터나 해시 저장소로 본 적 있는지 확인한다. 내려받은 뒤에는 본문 해시와 SimHash로 같은 내용과 거의 같은 내용을 거르고, 바뀌는 속도에 맞춰 다시 찾아간다. 크롤러 장은 여기까지다. 다음 글 [㉒ 알림 시스템 ①: 푸시, SMS, 이메일을 보내는 구조](/posts/sd-notification-system)에서는 반대 방향, 우리 서버가 수많은 사용자에게 메시지를 내보내는 시스템을 설계한다.

## 면접에서 나올 만한 질문

### 크롤러가 한 사이트에 부담을 주지 않게 하려면 어떻게 하나요?

프런티어 뒤에 호스트마다 줄을 하나씩 두고, 한 줄에서는 한 번에 하나만 내려받은 뒤 정해진 시간만큼 쉰다. 선택기는 쉬는 줄을 기다리지 않고 지금 보낼 수 있는 다른 줄을 고르니 전체 속도는 떨어지지 않는다. 쉬는 시간은 응답 시간에 맞춰 늘리고, 429나 503, `Retry-After`를 받으면 크게 늘린다. 여러 호스트가 한 IP를 같이 쓸 수 있으니 IP 단위 한도도 둔다.

### 우선순위와 예의를 한 줄로 처리하면 안 되나요?

중요한 사이트의 URL은 점수가 높아 줄 앞에 몰리니, 한 줄로 처리하면 그 사이트에 요청이 몰린다. 그래서 점수 구간별 앞쪽 큐가 순서를 정하고, 호스트별 뒤쪽 큐가 속도를 정하게 나눈다. 앞쪽 선택기는 높은 줄을 자주 뽑되 낮은 줄도 가끔 뽑아서 굶지 않게 한다.

### robots.txt는 어떻게 해석하나요?

자기 User-agent와 맞는 그룹이 있으면 그 그룹만 쓰고, 없으면 `*` 그룹을 쓴다. 경로 앞부분이 맞는 규칙 중 가장 긴 규칙이 이기고, 길이가 같으면 Allow가 이긴다. 파일이 404면 제한 없음, 5xx면 사이트 전체 금지로 본다. 호스트마다 받아 두되 24시간 넘게 캐시하지 않는다.

### 수십억 개 URL의 방문 여부를 어떻게 저장하나요?

URL 문자열 그대로는 100만 개에 140MiB가 넘어서 수십억 개는 메모리에 못 담는다. URL을 64비트 해시로 줄여 디스크 기반 저장소에 두거나, 블룸 필터로 1% 오답을 감수하고 수십 분의 일로 줄인다. 블룸 필터의 오답은 처음 보는 URL을 봤다고 하는 쪽이라, 그만큼 페이지를 놓친다. 놓치면 안 되면 "봤다"고 할 때만 디스크 기록을 다시 확인한다.

### 조회수만 다른 페이지를 중복으로 거르려면요?

SHA-256 같은 일반 해시는 한 글자만 달라도 완전히 다른 값이 나와서 못 거른다. SimHash처럼 비슷한 문서가 비슷한 지문을 갖는 해시를 쓰고, 64비트 중 몇 비트 이내로 다르면 거의 같은 페이지로 본다. 지문을 덩어리로 나눠 덩어리별 색인을 두면 수십억 개 중에서도 후보만 빨리 찾을 수 있다.

### 스파이더 트랩은 어떻게 막나요?

트랩은 매번 처음 보는 URL을 만들어서 URL 중복 확인으로는 못 막는다. URL 길이와 깊이 상한, 같은 경로 조각 반복 금지, 같은 경로에 매개변수만 다른 URL 수 상한을 두고, 무엇보다 호스트별 페이지 예산으로 한 사이트에 쓰는 자원에 천장을 씌운다. 호스트별로 새로 발견하는 URL 수를 지켜보고 이상한 호스트는 차단 목록에 넣는다.

### 바뀐 페이지는 어떻게 다시 찾아가나요?

ETag나 `Last-Modified`로 조건부 요청을 보내 바뀌지 않았으면 본문 없는 304를 받는다. 페이지마다 바뀌었으면 간격을 줄이고 그대로면 늘려서, 자주 바뀌는 페이지에 자원을 몰아준다. 사이트맵의 `lastmod`가 있으면 그걸 먼저 보고 바뀐 페이지만 우선순위를 높인다.

### 크롤 대상이 10배로 늘면 이 구조에서 어디를 바꾸나요?

호스트 해시로 크롤 서버를 늘리면 프런티어와 예의 규칙은 서버마다 따로 돌아서 그대로 늘어난다. 먼저 바꿀 곳은 URL 중복 확인으로, 메모리 Set에서 블룸 필터와 디스크 저장소 조합으로 옮긴다. 뒤쪽 큐 수도 워커 수에 맞춰 늘리고, `robots.txt`와 DNS 캐시는 호스트 수에 비례해 커지니 크기 상한과 만료를 둔다.
