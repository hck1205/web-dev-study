주문 상담 에이전트에 도구 여섯 개를 줬다. 로그를 보니 이상한 장면이 계속 나왔다. 고객이 주문 번호를 알려 줬는데도 모델이 `get_order` 대신 기간으로 찾는 `search_orders`를 불렀다. `search_orders`에 상태 값으로 "배송중"을 넣었다가 오류를 받고, 같은 인자로 두 번 더 불렀다. 주문 120건이 담긴 결과를 받은 다음에는 그 결과를 요약하느라 답이 늦어졌다. 그리고 이 코드를 다른 공급사 모델로 옮겨 보려 하자 도구 정의 형식부터 결과를 돌려주는 방식까지 맞지 않아 대부분을 다시 짜야 했다.

모델이 멍청해서 생긴 일이 아니다. 모델이 도구에 대해 아는 건 우리가 준 이름, 설명, 스키마, 그리고 도구가 돌려준 결과뿐이다. 이 네 가지가 모델이 읽기 좋게 쓰여 있지 않았다. 이 글은 도구를 모델이 읽는 인터페이스로 보고 설계하는 법을 다룬다. 이름과 설명, 스키마, 오류, 결과 크기, 부작용 있는 도구의 확인과 멱등성, 도구가 많아질 때를 먼저 보고, 뒤에서 공급사별 도구 호출 형식의 차이와 추상화 계층을 둘지 판단하는 법을 본다.

도구 호출 루프 한 바퀴와 서버가 실행을 맡는 이유는 [LLM API 연동 글](/posts/llm-api-integration)에 있으니 여기서는 반복하지 않는다. 도구를 다른 앱과 표준으로 나눠 쓰는 방법은 [MCP 글](/posts/mcp-protocol)에, 도구를 부르는 루프의 구조(ReAct, 계획-실행, 멈춤 조건)는 [에이전트 구조 글](/posts/agent-reasoning-patterns)에 있다. 예제 코드는 Node.js 22로 실제로 돌린 것이다.

## 모델은 도구를 이름과 설명으로만 안다

이 네 조각 중 무엇이 빠지거나 흐리면 처음 장면의 증상이 나온다. `get_order`와 `search_orders`의 설명에 서로를 언급하지 않았으니 모델은 둘 중 아무거나 골랐다. 상태 값을 자유 문자열로 열어 두었으니 "배송중"이 들어왔다.

## 이름과 설명은 고르는 기준을 담는다

이름은 짧고 구체적으로 짓는다. `동사_대상` 꼴(`search_orders`, `get_order`, `send_refund_email`)이 무난하다. 도구가 여러 시스템에 걸쳐 있으면 접두사로 묶는다(`crm_search_contacts`, `billing_get_invoice`). MCP처럼 여러 서버의 도구가 한곳에 모이면 이름이 겹치기 쉬워서 이 묶음이 더 중요하다. 공급사마다 이름에 쓸 수 있는 문자와 길이 제한이 있으니 영문 소문자, 숫자, 밑줄로만 짓는 게 안전하다.

설명은 신입 동료에게 쓰는 사용 설명서처럼 쓴다. 들어갈 것은 이렇다.

- 무엇을 하는가. 한 문장.
- 언제 쓰는가, 그리고 언제 쓰지 말고 대신 무엇을 쓰는가. 비슷한 도구가 있으면 반드시 서로를 언급한다.
- 인자의 뜻과 형식 중 스키마로 다 표현되지 않는 것. 날짜의 시간대, 금액 단위(원인지 센트인지), ID의 생김새.
- 결과의 모양과 한계. 최대 몇 건인지, 비어 있을 때 무엇이 오는지.
- 부작용. 이 도구가 무언가를 바꾸는지, 되돌릴 수 있는지.

처음 장면의 두 도구를 고쳐 쓰면 이렇게 된다.

```text
get_order
  주문 번호 하나로 주문 상세(상태, 금액, 배송지, 상품)를 가져온다.
  사용자가 "A-1234"처럼 주문 번호를 말했으면 이 도구를 쓴다.
  번호를 모르고 기간이나 상태로 찾아야 하면 search_orders를 쓴다.

search_orders
  기간과 상태로 이 고객의 주문 목록을 찾는다. 결과는 최대 20건이고 id와 status만 담긴다.
  주문 번호를 이미 알면 get_order를 쓴다. 상세가 필요하면 찾은 id로 get_order를 부른다.
  since가 없으면 오류가 난다. "지난주" 같은 말은 오늘 날짜 기준 YYYY-MM-DD로 바꿔 넣는다.
```

설명이 길어지는 걸 겁내지 않는다. 도구 고르기가 틀려서 생기는 왕복 한 번이 설명 몇 줄보다 비싸다. 다만 모든 도구 설명은 요청마다 토큰으로 실린다는 점은 기억해 둔다. 도구가 많아질 때의 이야기는 뒤에서 한다.

## 스키마는 고를 수 있는 값만 남긴다

스키마는 모델이 틀릴 여지를 줄이는 장치다. 원칙은 단순하다. 허용하는 값만 표현할 수 있게 좁힌다.

- 고정된 선택지는 `enum`으로 준다. 상태를 자유 문자열로 두면 "배송중", "shipping", "in_transit"이 섞여 들어온다.
- 꼭 필요한 인자는 `required`에 넣고, 모르는 인자는 `additionalProperties: false`로 막는다. 모델이 그럴듯한 이름의 인자(`state`)를 지어내는 걸 잡는다.
- 숫자에는 범위를 준다. `limit`에 `maximum: 20`이 없으면 모델이 1000을 넣는다.
- 구조는 얕게 둔다. 객체 안의 객체 안의 배열은 모델이 채우기도, 사람이 검사하기도 어렵다. 깊어지면 도구를 나누는 게 낫다는 신호다.
- 모델이 계산해야 하는 값을 줄인다. "지난주"를 날짜로 바꾸는 일처럼 모델이 자주 틀리는 계산은 아예 `period: "last_7_days"` 같은 선택지로 바꾸고 계산은 서버가 한다.
- 사용자 ID, 테넌트 ID처럼 권한을 정하는 값은 스키마에 넣지 않는다. 서버가 세션에서 정한다. 모델이 넣게 하면 프롬프트 주입 한 줄로 남의 주문을 조회한다.

`strict: true`를 지원하는 공급사라면 켠다. 모델이 스키마에 맞지 않는 인자를 아예 만들지 못하게 생성 단계에서 막아 준다. 대신 지원하는 스키마 키워드에 제한이 있어서 복잡한 조건(`oneOf`, 패턴)이 거절되기도 한다. 켜든 안 켜든 서버에서 다시 검사한다. 스트리밍으로 인자를 조각조각 받는 설정에서는 끝까지 못 받은 인자가 잘린 채 파싱될 수도 있기 때문이다.

## 오류는 고치는 방법까지 돌려준다

모델은 도구가 돌려준 오류를 읽고 다음 행동을 정한다. 그러니 오류 메시지는 모델에게 주는 지시문이다. `Error: 400 Bad Request`를 받은 모델은 무엇이 틀렸는지 모르니 같은 인자로 다시 부르거나 포기한다. 처음 장면에서 같은 인자로 두 번 더 부른 이유다.

인자를 검사해 고칠 방법까지 적어 돌려주는 작은 검사기를 만들어 돌려 봤다. 받은 값과 허용되는 값을 함께 적는 것이 요점이다.

```js
// 모델이 보낸 인자를 검사하고, 틀리면 모델이 고칠 수 있는 문장으로 돌려준다
function validate(schema, input) {
  const errors = [];
  for (const k of schema.required ?? []) if (!(k in input)) errors.push(`'${k}'가 빠졌다`);
  for (const [k, v] of Object.entries(input)) {
    const p = schema.properties[k];
    if (!p) { errors.push(`'${k}'는 없는 인자다. 쓸 수 있는 인자: ${Object.keys(schema.properties).join(", ")}`); continue; }
    if (p.enum && !p.enum.includes(v)) errors.push(`'${k}'는 ${p.enum.join(" | ")} 중 하나여야 한다. 받은 값: ${JSON.stringify(v)}`);
    if (p.type === "integer" && (!Number.isInteger(v) || v < p.minimum || v > p.maximum)) errors.push(`'${k}'는 ${p.minimum}~${p.maximum} 사이 정수여야 한다. 받은 값: ${JSON.stringify(v)}`);
    if (k === "since" && !/^\d{4}-\d{2}-\d{2}$/.test(v)) errors.push(`'since'는 YYYY-MM-DD 형식이어야 한다. 받은 값: ${JSON.stringify(v)}`);
  }
  return errors;
}
```

세 가지 호출을 넣었다. 하나는 맞는 인자, 하나는 처음 장면처럼 값이 틀린 인자, 하나는 이름을 지어낸 인자다.

```text
{"status":"shipped","since":"2026-10-01","limit":5} => OK
{"status":"배송중","since":"지난주","limit":50} => {"is_error":true,"content":"'status'는 paid | shipped | delivered | refunded 중 하나여야 한다. 받은 값: \"배송중\"; 'since'는 YYYY-MM-DD 형식이어야 한다. 받은 값: \"지난주\"; 'limit'는 1~20 사이 정수여야 한다. 받은 값: 50"}
{"state":"paid"} => {"is_error":true,"content":"'since'가 빠졌다; 'state'는 없는 인자다. 쓸 수 있는 인자: status, since, limit"}
```

두 번째 줄을 받은 모델은 무엇을 어떻게 고칠지 안다. 틀린 곳을 한 번에 다 알려 주는 것도 중요하다. 첫 오류만 돌려주면 모델은 고치고, 다음 오류를 받고, 또 고치느라 왕복이 세 번 생긴다. 오류는 예외로 루프를 끊지 말고 결과로 돌려준다. Anthropic API는 `tool_result`에 `is_error: true`를 붙이고, OpenAI는 별도 오류 필드 없이 결과 문자열에 오류를 담는다.

오류 메시지에 넣지 말아야 할 것도 있다. 스택 트레이스, 내부 호스트 이름, SQL 원문, 다른 사용자의 데이터다. 모델이 읽은 것은 사용자에게 그대로 전해질 수 있다고 가정한다.

## 결과는 모델이 읽을 만큼만 돌려준다

도구 결과는 다음 요청의 입력 토큰이 된다. 처음 장면의 `search_orders`는 주문 120건을 배송지와 상품 목록까지 통째로 돌려줬다. JSON으로 8,101자였다. 이걸 모델이 매 단계 다시 읽는다. 필요한 필드(id, status)만 골라 20건으로 자르니 735자가 됐다.

자를 때는 잘랐다는 사실을 알려 준다. 모델이 120건 중 20건만 봤다는 걸 모르면 "주문이 20건 있다"고 답한다. 결과에 총 건수와 다음 행동을 적는다. 아래에서 그 함수를 직접 짜 볼 수 있다.

      args: [[{ id: "A-1", status: "paid", address: "서울" }, { id: "A-2", status: "shipped", address: "부산" }, { id: "A-3", status: "paid" }, { id: "A-4", status: "paid" }], 2, ["id", "status"]],

    { label: "한도 안", args: [[{ id: "A-1", status: "paid", x: 1 }], 5, ["id", "status"]], expected: { total: 1, rows: [{ id: "A-1", status: "paid" }] } },

    { label: "없는 필드는 건너뜀", args: [[{ id: "A-1" }, { id: "A-2" }, { id: "A-3" }], 3, ["id", "status"]], expected: { total: 3, rows: [{ id: "A-1" }, { id: "A-2" }, { id: "A-3" }] } },

빈 결과도 신경 쓴다. `[]`만 돌려주면 모델은 도구가 실패했는지, 정말 없는지 헷갈려 다시 부른다. `{ "total": 0, "rows": [] }`에 "이 기간에 주문이 없다"를 더하면 반복이 준다. 큰 결과가 꼭 필요하면 페이지 단위로 나누고 커서를 돌려주거나, 결과를 파일로 저장한 뒤 경로만 돌려줘서 모델이 필요한 부분만 다시 읽게 한다.

사람이 읽는 ID를 함께 준다. 내부 UUID만 있으면 모델이 긴 문자열을 옮겨 적다가 한 글자를 틀린다. `A-1234` 같은 짧은 ID나 이름을 함께 돌려주면 다음 호출의 인자가 정확해진다.

## 도구 종류마다 조심할 곳이 다르다

같은 원칙이라도 도구가 하는 일에 따라 무게가 다르다.

웹 검색은 결과가 길고 믿을 수 없다. 제목, URL, 짧은 발췌만 돌려주고 본문은 따로 가져오게 한다. 검색 결과와 가져온 페이지는 남이 쓴 글이라 "이전 지시를 무시하고 …" 같은 문장이 섞여 들어온다. 도구 결과는 지시가 아니라 자료라고 시스템 프롬프트에 적고, 웹 결과를 읽은 뒤에는 부작용 있는 도구를 바로 쓰지 못하게 막는 정책도 고려한다. 공급사가 운영하는 서버 측 검색 도구를 쓰면 실행과 결과 정리를 공급사가 맡는다.

코드 실행은 격리가 전부다. 모델이 만든 코드는 신뢰할 수 없는 코드다. 컨테이너나 샌드박스에서 네트워크를 막거나 허용 목록으로 묶고, CPU 시간·메모리·출력 크기에 상한을 건다. 결과로는 표준 출력과 표준 오류의 끝부분, 종료 코드를 돌려준다. 출력 10만 줄을 통째로 돌려주면 그걸로 컨텍스트가 찬다.

DB 조회는 가장 위험한 편의를 경계한다. `run_sql(query)` 하나를 주면 편하지만 모델이 `DELETE`를 쓰거나, 인덱스 없는 전체 조회로 운영 DB를 멈추거나, 다른 테넌트의 행을 읽는다. 가능하면 `get_order(orderId)`처럼 목적이 정해진 도구로 쪼갠다. 자유 SQL이 꼭 필요하면(분석용 에이전트) 읽기 전용 계정과 복제본, 행 수준 보안, 문 실행 시간 제한(PostgreSQL이면 `statement_timeout`), 결과 행 수 상한을 함께 건다.

외부 API 호출은 타임아웃과 재시도를 도구 안에서 처리한다. 429나 일시적 5xx는 모델에게 보이기 전에 지수 백오프로 몇 번 다시 시도하는 게 싸다. 모델에게는 판단이 필요한 실패만 돌려준다. 임의 URL을 부르는 범용 `http_request` 도구는 SSRF(서버가 내부망 주소를 대신 부르게 되는 공격) 통로가 되니 허용할 호스트를 정해 둔다.

메시지 발송(메일, 슬랙, 문자)과 결제, 환불은 되돌릴 수 없다. 다음 절에서 따로 본다.

파일 접근은 경로를 묶는다. 작업 폴더 밖으로 나가는 `../`나 심볼릭 링크를 실제 경로로 풀어 확인하고, 비밀 값이 든 파일(`.env`, 키 파일)은 목록에서도 뺀다. 쓰기는 덮어쓰기 전에 원본을 남기거나 변경 내용을 diff로 돌려줘서 사람이 확인할 수 있게 한다.

## 되돌릴 수 없는 도구는 두 단계로 나눈다

환불 메일을 보내는 도구를 생각해 보자. 모델이 이 도구를 부르면 메일이 나간다. 그런데 모델은 같은 호출을 두 번 낼 수 있다. 응답이 늦어 루프가 재시도할 수도 있고, 모델이 앞의 호출이 성공했는지 헷갈릴 수도 있다. 사람이 확인해야 하는 경우도 있다. 그래서 부작용 있는 도구는 준비와 실행을 나누고, 실행에는 멱등성 키를 붙인다. 아래 그림에서 다음을 누르면 한 번의 발송을 따라간다.

## 도구가 많아지면 고르기가 어려워진다

도구가 다섯 개일 때 잘 고르던 모델도 오십 개가 되면 틀리기 시작한다. 이름과 설명이 비슷한 도구가 늘고, 모델이 비교해야 할 후보가 많아진다. 비용도 는다. 도구 정의는 요청마다 실리니, 설명이 넉넉한 도구 하나가 200~500토큰이라고 하면 오십 개면 요청마다 1만~2만 5천 토큰이 도구 설명으로 나간다. 프롬프트 캐시가 이 비용을 크게 줄여 주지만, 고르기가 어려워지는 문제는 남는다.

대응은 몇 가지다. 첫째, 겹치는 도구를 합친다. `get_order_status`, `get_order_items`, `get_order_address`는 `get_order` 하나에 `fields` 인자로 합칠 수 있다. 둘째, 필요한 도구만 싣는다. 요청을 먼저 분류해서 환불 문의에는 환불 관련 도구만 준다. 셋째, 도구 검색을 쓴다. Anthropic API에는 도구 대부분을 처음에는 싣지 않고(`defer_loading`) 모델이 검색 도구로 필요한 것만 찾아 불러오는 방식이 있다. 넷째, 영역별로 에이전트를 나눠 각자 작은 도구 묶음을 갖게 한다. 나눌 때의 비용은 [에이전트 구조 글](/posts/agent-reasoning-patterns)에서 본다.

도구 선택 정확도는 감으로 판단하지 않는다. "이 질문에는 이 도구가 이 인자로 불려야 한다"는 문항 50~100개를 만들어 두고, 도구 설명을 고칠 때마다 돌린다. 정답 도구가 정해져 있으니 코드로 채점할 수 있다. 채점과 회귀 테스트의 틀은 [LLM 평가 글](/posts/llm-evals)에 있다.

## 공급사마다 다른 도구 호출 형식

여기까지는 어느 공급사를 쓰든 같다. 처음 장면의 두 번째 문제, 다른 공급사로 옮기다 깨진 건 형식 차이 때문이다. 큰 개념은 같다. 도구 목록을 주고, 모델이 호출을 요청하고, 우리가 결과를 돌려준다. 하지만 모양이 다르다.

같은 정의를 네 가지 형식으로 바꾸는 어댑터를 만들어 돌려 봤다. 출력은 앞 90자만 잘라 보였다.

```js
// tool-adapters.mjs: 도구 정의 하나를 공급사별 형식으로 바꾼다
const toAnthropic = (t) => ({ name: t.name, description: t.description, input_schema: t.schema });
const toOpenAIChat = (t) => ({ type: "function", function: { name: t.name, description: t.description, parameters: t.schema } });
const toOpenAIResponses = (t) => ({ type: "function", name: t.name, description: t.description, parameters: t.schema });
const toGemini = (t) => ({ functionDeclarations: [{ name: t.name, description: t.description, parameters: t.schema }] });
```

```text
anthropic         {"name":"search_orders","description":"고객의 주문을 기간과 상태로 찾는다. 주문 번호를 이미 알면 get_order를 쓴다.","…
openai chat       {"type":"function","function":{"name":"search_orders","description":"고객의 주문을 기간과 상태로 찾는다. …
openai responses  {"type":"function","name":"search_orders","description":"고객의 주문을 기간과 상태로 찾는다. 주문 번호를 이미 알면…
gemini            {"functionDeclarations":[{"name":"search_orders","description":"고객의 주문을 기간과 상태로 찾는다. 주문 번호…
```

정의는 껍데기만 다르다. 스키마 키 이름이 `input_schema`냐 `parameters`냐, 한 겹 더 감싸느냐 정도다. 다만 스키마 안에서 받는 키워드 범위가 다르다. Gemini의 함수 선언은 OpenAPI 스키마의 부분 집합에서 출발해서 일부 JSON Schema 키워드를 받지 않던 시기가 있었고, 엄격 모드도 공급사마다 지원하는 키워드가 다르다. 정의를 바꿀 때는 각 공급사에 실제로 요청을 보내 거절되는 키워드가 없는지 확인한다.

깨지기 쉬운 곳은 정의보다 호출과 결과 쪽이다. 실제로 옮길 때 걸린 것들을 정리하면 이렇다. 공급사 API는 자주 바뀌니 2026년 10월 기준 각 문서로 다시 확인한다.

| 항목 | Anthropic Messages | OpenAI Chat Completions | OpenAI Responses | Gemini |
|---|---|---|---|---|
| 호출이 오는 곳 | `content`의 `tool_use` 블록 | `message.tool_calls[]` | 출력 항목 `function_call` | `functionCall` 파트 |
| 인자 | `input`: 객체 | `arguments`: JSON 문자열 | `arguments`: JSON 문자열 | `args`: 객체 |
| 호출 ID | `id` | `id` | `call_id` | 없거나 선택(이름으로 짝지음) |
| 결과 돌려주기 | user 메시지의 `tool_result` 블록 | `role: "tool"` 메시지 | `function_call_output` 항목 | `functionResponse` 파트 |
| 오류 표시 | `is_error: true` | 결과 문자열에 담기 | 결과 문자열에 담기 | 응답 객체에 담기 |
| 도구 강제 | `tool_choice` auto·any·tool·none | `tool_choice` auto·required·none·특정 함수 | 같은 계열 | `functionCallingConfig` mode AUTO·ANY·NONE |
| 병렬 호출 끄기 | `disable_parallel_tool_use` | `parallel_tool_calls: false` | `parallel_tool_calls: false` | 별도 설정 없음(여러 파트가 올 수 있다) |

몇 가지는 꼭 짚는다. 인자가 객체로 오는 곳과 JSON 문자열로 오는 곳이 섞여 있다. OpenAI에서는 `JSON.parse`를 빼먹으면 문자열 안의 필드를 찾다가 조용히 `undefined`가 된다. 병렬 호출 결과는 Anthropic에서 한 user 메시지에 `tool_result`를 모두 담아야 한다. 나눠 보내면 모델이 다음부터 병렬 호출을 덜 한다. 도구 강제도 같은 공급사 안에서 모델마다 다르다. Claude Opus 5.5는 `tool_choice`의 `any`와 `tool`을 400 오류로 거절하니, 특정 도구를 꼭 쓰게 하려면 `auto`에 프롬프트 지시와 `strict`를 함께 쓴다.

스트리밍에서도 다르다. 도구 인자는 한 번에 오지 않고 조각으로 온다. Anthropic은 `input_json_delta` 이벤트의 `partial_json`, OpenAI Chat Completions는 `delta.tool_calls[i].function.arguments` 조각, Responses는 `response.function_call_arguments.delta` 이벤트로 흘려보낸다. 조각을 이어 붙이고, 그 호출이 끝났다는 이벤트를 받은 뒤에 파싱한다. 중간에 파싱하면 깨진 JSON을 만나고, 끝까지 못 받은 채 잘리면 일부 필드가 빠진 인자가 된다. 그래서 스트리밍이든 아니든 실행 전에 스키마 검사를 한 번 더 한다.

## 상태를 서버에 두는 API, 두지 않는 API

또 하나의 갈림길은 대화 상태를 누가 들고 있느냐다. Anthropic Messages API와 OpenAI Chat Completions는 상태가 없다. 매 요청에 대화 전체와 도구 결과를 다시 보낸다. 무엇이 모델에게 들어가는지 우리가 다 알고, 저장도 우리 DB에 한다. 대신 기록을 들고 다니는 코드를 우리가 짠다.

OpenAI의 Assistants API는 스레드와 실행(run)을 서버에 두는 방식이었다. 대화 기록을 공급사가 들고, 우리는 스레드 ID만 들고 다녔다. OpenAI는 이 API를 Responses API로 옮기라고 공지하고 2026년 8월 종료 일정을 밝혔다. Responses API는 `previous_response_id`로 앞의 응답을 이어 가면 공급사가 저장한 기록을 이어 쓰고, 저장하지 않고 매번 보내는 방식도 고를 수 있다. Anthropic에도 에이전트 루프와 작업 환경을 서버가 맡는 Managed Agents가 베타로 있다.

상태를 서버에 두면 코드가 짧아지고, 공급사가 제공하는 도구(파일 검색, 코드 실행)를 붙이기 쉽다. 대신 기록이 공급사에 남으니 데이터 보존과 삭제 요청을 공급사 기능에 맡기게 되고, 다른 공급사로 옮길 때 기록을 꺼내 형식을 바꾸는 일이 생긴다. Assistants에서 Responses로의 이전처럼 같은 공급사 안에서도 상태 모델이 바뀌면 옮겨야 한다. 무상태 API를 쓰면 이 위험이 우리 쪽에 없다. 대화 기록을 직접 저장하고 관리하는 법은 [에이전트 메모리 글](/posts/agent-memory)에 있다.

추상화는 가장 작은 공통분모로 수렴한다. 프롬프트 캐시 위치 지정, 서버 측 도구, 생각 블록을 다음 요청에 그대로 돌려주는 규칙, 공급사 고유의 새 파라미터처럼 한 공급사에만 있는 기능은 추상화 계층이 늦게 지원하거나 아예 감춘다. 그 기능이 비용이나 품질에서 큰 차이를 만든다면, 추상화 때문에 그걸 못 쓰는 손해가 옮기기 쉬운 이득보다 크다. 공급사별 기능을 쓰는 코드는 어댑터 안에 가두고, 나머지만 공통으로 둔다.

실무 기준을 하나 두자면 이렇다. 도구 정의, 도구 실행기, 검사, 권한, 대화 기록 저장은 처음부터 내부 형식으로 둔다. 이 부분은 공급사와 상관없고, 옮길 때 가장 많이 다시 짜게 되는 곳이다. 모델 호출 자체는 지금 쓰는 공급사 SDK를 그대로 쓰되 한 모듈에 모은다. 두 번째 공급사가 실제로 필요해지면 그때 그 모듈만 어댑터로 바꾼다. 모델 교체 때 프롬프트와 품질이 바뀌는 문제는 형식과 별개라서 시험지로 다시 확인한다. 이 이야기는 [모델 고르기 글](/posts/llm-model-selection)에 있다.

## 현장에서 도구 호출이 이상할 때

"엉뚱한 도구를 부른다"는 먼저 도구 설명을 나란히 놓고 읽어 본다. 비슷한 도구가 서로를 언급하지 않거나, 설명이 "주문 관련 작업을 한다"처럼 넓으면 고르기가 갈린다. 프롬프트에 규칙을 덧붙이기 전에 설명부터 고친다.

"같은 인자로 계속 부른다"는 오류나 빈 결과가 고칠 방법을 알려 주지 않는 경우가 대부분이다. 그 도구가 돌려준 결과를 로그에서 그대로 꺼내 읽어 본다. 사람이 읽어도 다음에 뭘 해야 할지 모르겠다면 모델도 모른다.

"답이 느리고 비싸다"는 도구 결과 크기를 본다. 단계별 입력 토큰을 찍어 보면 특정 도구 결과가 실린 뒤로 입력이 확 뛰는 지점이 보인다. 필드를 줄이고, 건수를 자르고, 페이지로 나눈다.

"다른 모델로 바꿨더니 도구 호출이 깨졌다"는 위 표의 차이 중 하나다. 인자 파싱(객체와 문자열), 결과 메시지 위치, 호출 ID 짝, 거절되는 스키마 키워드나 `tool_choice` 값 순서로 확인한다.

## 도구는 모델이 읽는 API다

사람이 쓰는 API에 문서와 오류 코드를 신경 쓰듯, 모델이 쓰는 도구도 읽는 쪽을 위해 설계한다. 이름과 설명에는 언제 쓰고 언제 쓰지 말지를 담고, 스키마는 허용하는 값만 표현하게 좁히고, 오류는 고칠 방법까지 한 번에 알려 주고, 결과는 읽을 만큼만 잘라 잘랐다는 사실을 적는다. 되돌릴 수 없는 도구는 준비와 실행을 나누고 멱등성 키를 붙인다. 공급사 형식의 차이는 경계의 어댑터에 가두고, 도구 실행과 검사는 공급사를 모르게 둔다.

## 면접에서 나올 만한 질문

### 모델이 도구를 잘 고르게 하려면 도구 정의를 어떻게 쓰나요?

이름은 동사_대상 꼴로 무엇을 하는지 드러내고, 설명에는 무엇을 하는지, 언제 쓰는지, 언제 쓰지 말고 무엇을 대신 쓰는지, 결과의 모양과 부작용을 적는다. 비슷한 도구가 있으면 서로를 언급해야 모델이 갈피를 잡는다. 스키마는 enum, required, 범위, additionalProperties false로 허용 값만 남긴다. 고친 뒤에는 정답 도구가 정해진 문항으로 선택 정확도를 다시 잰다.

### 도구 오류는 모델에게 어떻게 돌려주나요?

예외로 루프를 끊지 않고 결과로 돌려주되, 받은 값과 허용되는 값, 고치는 방법을 함께 적는다. 틀린 곳은 한 번에 다 알려 줘야 왕복이 준다. Anthropic은 `is_error: true`를 붙인다. 일시적 실패는 도구 안에서 재시도하고, 스택 트레이스나 내부 정보는 담지 않는다. "400"만 돌려주면 모델이 같은 인자로 반복하는 증상이 생긴다.

### 도구 결과가 클 때는 어떻게 하나요?

결과는 다음 요청의 입력 토큰이 되고 매 단계 다시 읽히니 필요한 필드와 건수만 돌려준다. 잘랐다면 총 건수와 범위를 좁혀 다시 찾으라는 안내를 함께 넣어야 모델이 일부만 보고 전부라고 답하지 않는다. 빈 결과도 "없다"를 명시하고, 큰 결과는 페이지와 커서로 나누거나 파일로 저장해 경로만 준다.

### 메일 발송이나 환불 같은 부작용 있는 도구는 어떻게 설계하나요?

준비와 실행을 나눈다. 모델은 초안을 만드는 도구만 부르고, 실행은 승인 기록을 확인한 서버가 한다. 실행에는 초안 ID로 만든 멱등성 키를 붙여 같은 요청이 두 번 와도 한 번만 일어나게 하고, 이미 실행된 요청에는 오류가 아니라 이미 처리했다는 결과를 돌려준다. 승인 정책은 모델이 아니라 서버가 쥐고, 위험이 낮은 건 정책으로 자동 승인한다.

### 도구가 수십 개로 늘면 어떤 문제가 생기고 어떻게 대응하나요?

비슷한 도구가 늘어 선택 정확도가 떨어지고, 도구 정의가 요청마다 실려 토큰이 는다. 겹치는 도구를 인자로 합치고, 요청을 분류해 필요한 도구만 싣고, 도구 검색처럼 필요할 때만 정의를 불러오는 방식을 쓴다. 영역별로 에이전트를 나눠 도구 묶음을 작게 유지할 수도 있다. 개선 효과는 정답 도구가 정해진 문항으로 잰다.

### 공급사마다 도구 호출 형식이 어떻게 다른가요?

정의는 `input_schema`와 `parameters`처럼 껍데기만 다르지만, 호출과 결과에서 차이가 크다. Anthropic과 Gemini는 인자가 객체로 오고 OpenAI는 JSON 문자열로 와서 파싱이 필요하다. 결과는 Anthropic이 user 메시지의 `tool_result`, Chat Completions가 tool 역할 메시지, Responses가 `function_call_output` 항목이다. `tool_choice` 값과 병렬 호출 끄는 방법, 스트리밍에서 인자 조각이 오는 이벤트도 다르고, 같은 공급사 안에서도 모델마다 거절하는 설정이 있다.

### 상태를 서버에 두는 API와 무상태 API 중 무엇을 고르나요?

서버에 두면 대화 기록을 공급사가 들고 있어 코드가 짧고 공급사 도구를 붙이기 쉽지만, 보존과 삭제를 공급사에 맡기고 옮길 때 기록을 꺼내 바꿔야 한다. OpenAI가 Assistants API를 Responses API로 옮기게 한 것처럼 같은 공급사 안에서도 상태 모델이 바뀔 수 있다. 무상태 API는 기록 관리 코드를 직접 짜는 대신 무엇이 모델에 들어가는지 다 알고 데이터를 우리 쪽에 둔다. 데이터 통제와 이식성이 중요하면 무상태 쪽을 고른다.

### 여러 공급사를 위한 추상화 계층을 두면 어떤 비용이 있나요?

추상화는 공통분모로 수렴해서 프롬프트 캐시 위치, 서버 측 도구, 생각 블록 처리 같은 공급사 고유 기능을 늦게 지원하거나 감춘다. 그 기능이 비용과 품질에 큰 차이를 내면 옮기기 쉬운 이득보다 손해가 크다. 그래서 도구 정의, 실행기, 검사, 권한, 기록 저장은 처음부터 내부 형식으로 두고, 모델 호출은 한 모듈에 모아 지금 공급사 SDK를 쓰다가 두 번째 공급사가 실제로 필요할 때 어댑터로 바꾼다.
