연결 리스트를 뒤집는 함수를 짰다. 반복문 하나에 세 줄이라 간단해 보였는데, 노드 네 개를 넣고 돌리니 하나만 남았다.

```js
class ListNode { constructor(value, next = null) { this.value = value; this.next = next; } }
const fromArray = (arr) => arr.reduceRight((next, v) => new ListNode(v, next), null);
const toArray = (head) => { const out = []; for (let n = head; n; n = n.next) out.push(n.value); return out; };

function reverseBuggy(head) {
  let prev = null, curr = head;
  while (curr) {
    curr.next = prev;   // 화살표를 먼저 돌렸다
    prev = curr;
    curr = curr.next;   // 방금 prev로 바꾼 next를 따라간다
  }
  return prev;
}
console.log(toArray(reverseBuggy(fromArray([1, 2, 3, 4]))));
```

```text
[ 1 ]
```

첫 바퀴에서 1번 노드의 `next`를 `null`로 바꾼 순간, 2번 노드로 가는 길이 사라졌다. 그 뒤 `curr = curr.next`는 `null`을 따라가서 반복문이 끝난다. 2, 3, 4번 노드는 아무도 가리키지 않으니 가비지 컬렉터가 치운다. 배열이었다면 인덱스로 언제든 다시 찾아갈 수 있지만, 연결 리스트에서 노드를 찾아가는 방법은 앞 노드의 포인터 하나뿐이다. 이 한 가지 사실에서 연결 리스트의 장점과 단점, 면접 문제의 함정이 거의 다 나온다.

자료구조 시리즈의 두 번째 글이다. [배열과 행렬](/posts/ds-array-matrix)에서 본 "칸이 붙어 있다"는 성질을 버리면 무엇을 얻고 무엇을 잃는지 본다. 연결 리스트로 큐를 만드는 이야기는 [스택, 큐, 덱](/posts/ds-stack-queue-deque)에서 이어진다.

## 노드가 다음 노드의 주소를 들고 있다

연결 리스트는 값과 다음 노드를 가리키는 포인터를 묶은 노드를 줄줄이 이어 붙인 구조다. 리스트가 들고 있는 건 첫 노드(head) 하나뿐이고, 마지막 노드의 `next`는 `null`이다. 노드는 각자 따로 메모리를 잡기 때문에 서로 붙어 있을 필요가 없다. 앞뒤 포인터를 둘 다 들면 이중 연결 리스트(doubly linked list)가 된다.

| 연산 | 배열 | 단일 연결 리스트 | 이중 연결 리스트 |
|---|---|---|---|
| i번째 읽기 | O(1) | O(n), 앞에서부터 따라간다 | O(n) |
| 맨 앞에 넣기·빼기 | O(n) | O(1) | O(1) |
| 맨 뒤에 넣기 | 분할 상환 O(1) | tail을 들고 있으면 O(1) | O(1) |

| 쥐고 있는 노드 뒤에 넣기 | 해당 없음 | O(1) | O(1) |
| 쥐고 있는 노드 자체를 빼기 | 해당 없음 | O(n), 앞 노드를 찾아야 한다 | O(1) |
| 값으로 찾기 | O(n) | O(n) | O(n) |

"연결 리스트는 중간 삽입이 O(1)"이라는 말은 반만 맞다. 넣을 자리의 노드를 이미 쥐고 있을 때만 O(1)이고, 그 자리를 찾는 데는 O(n)이 든다. 인덱스 3에 넣으라는 요청이라면 세 칸을 따라가야 하니 배열과 같은 O(n)이다. 면접에서 이 꼬리 질문이 자주 나온다. 연결 리스트가 진짜 빛나는 곳은 다른 자료구조(해시맵 등)가 노드를 바로 가리켜 줄 때다. 뒤에서 볼 LRU 캐시가 그런 경우다.

단일 리스트에서 맨 뒤를 빼거나 쥔 노드를 빼는 게 O(n)인 이유도 같다. 노드를 빼려면 앞 노드의 `next`를 고쳐야 하는데, 단일 리스트에는 뒤로 가는 길이 없다. 그래서 `prev` 포인터를 더한 게 이중 연결 리스트다. 노드마다 포인터가 하나 늘어나는 대가로 양쪽 끝과 쥔 노드의 삭제가 O(1)이 된다.

## 화살표를 돌리기 전에 다음 노드를 잡아 둔다

처음의 버그로 돌아가자. 고친 코드는 한 줄 순서만 다르다. 화살표를 돌리기 전에 다음 노드를 변수에 잡아 둔다.

```js
function reverseList(head) {
  let prev = null, curr = head;
  while (curr) {
    const next = curr.next; // 1) 다음을 잃어버리기 전에 잡아 둔다
    curr.next = prev;       // 2) 화살표를 뒤로 돌린다
    prev = curr;            // 3) 한 칸씩 전진
    curr = next;
  }
  return prev;
}
console.log(toArray(reverseList(fromArray([1, 2, 3, 4]))));
```

```text
[ 4, 3, 2, 1 ]
```

```js
function reverseRec(head) {
  if (!head || !head.next) return head;
  const newHead = reverseRec(head.next);
  head.next.next = head; // 내 다음 노드가 나를 가리키게
  head.next = null;
  return newHead;
}
console.log(toArray(reverseRec(fromArray([1, 2, 3, 4]))));

  reverseRec(fromArray(Array.from({ length: 100_000 }, (_, i) => i)));

}
```

## 두 배로 달리는 포인터

연결 리스트에는 길이가 없다. 가운데 노드를 찾으려면 한 번 끝까지 세고 다시 절반을 가야 한다. 두 포인터를 다른 속도로 보내면 한 번에 된다. 느린 포인터는 한 칸, 빠른 포인터는 두 칸씩 간다. 빠른 쪽이 끝에 닿을 때 느린 쪽은 정확히 가운데에 있다.

```js
function middle(head) {
  let slow = head, fast = head;
  while (fast && fast.next) { slow = slow.next; fast = fast.next.next; }
  return slow.value;
}
console.log(middle(fromArray([1, 2, 3, 4, 5])), middle(fromArray([1, 2, 3, 4, 5, 6])));
```

```text
3 4
```

짝수 길이에서는 가운데가 둘인데, 이 코드는 뒤쪽(6개 중 4)을 돌려준다. 앞쪽을 원하면 반복 조건을 `fast.next && fast.next.next`로 바꾼다. 리스트를 반으로 나눠야 하는 병합 정렬이나 회문 확인에서는 이 차이가 경계 버그로 이어지니 짝수와 홀수를 둘 다 넣어 확인한다.

같은 아이디어로 뒤에서 n번째 노드를 지운다. 빠른 포인터를 n칸 먼저 보내 두고, 둘을 같이 움직이면 빠른 쪽이 끝에 닿을 때 느린 쪽이 지울 노드 바로 앞에 선다.

```js
function removeNthFromEnd(head, n) {
  const dummy = new ListNode(0, head); // 머리를 지우는 경우를 따로 다루지 않으려고
  let fast = dummy, slow = dummy;
  for (let i = 0; i <= n; i++) fast = fast.next;
  while (fast) { fast = fast.next; slow = slow.next; }
  slow.next = slow.next.next;
  return dummy.next;
}
console.log(toArray(removeNthFromEnd(fromArray([1, 2, 3, 4, 5]), 2)), toArray(removeNthFromEnd(fromArray([1]), 1)));
```

```text
[ 1, 2, 3, 5 ] []
```

두 번째 호출이 노드 하나짜리 리스트에서 머리를 지우는 경우다. 앞에 가짜 노드(dummy)를 하나 붙여 두면 "지울 노드가 머리인가"를 따로 검사하지 않아도 `slow.next = slow.next.next` 한 줄로 끝난다. 연결 리스트 문제에서 머리가 바뀔 수 있으면 dummy부터 만드는 습관이 실수를 가장 많이 줄인다.

## 고리가 있는지 메모리 없이 알아내기

리스트 어딘가의 `next`가 앞쪽 노드를 가리키면 고리(cycle)가 생긴다. 끝이 없으니 `while (n)` 순회는 영원히 돈다. 방문한 노드를 Set에 넣어 두면 O(n) 메모리로 찾을 수 있지만, 빠른 포인터와 느린 포인터를 쓰면 O(1) 메모리로 된다. 고리가 없으면 빠른 쪽이 먼저 `null`에 닿는다. 고리가 있으면 둘 다 고리 안에서 돌다가, 빠른 쪽이 한 바퀴마다 한 칸씩 따라잡아 언젠가 같은 노드에서 만난다. Floyd의 순환 탐지(토끼와 거북이 알고리즘)라고 부른다.

만난 다음에는 고리가 시작하는 노드도 찾을 수 있다. 한 포인터를 머리로 돌려보내고 둘 다 한 칸씩 움직이면 고리 시작점에서 만난다.

```js
function cycleStart(head) {
  let slow = head, fast = head;
  while (fast && fast.next) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) {             // 고리 안에서 만났다
      let p = head;
      while (p !== slow) { p = p.next; slow = slow.next; }
      return p.value;                // 고리가 시작하는 노드
    }
  }
  return null;                       // fast가 끝에 닿았다: 고리 없음
}
const c = fromArray([1, 2, 3, 4, 5, 6]);
let tail = c; while (tail.next) tail = tail.next;
tail.next = c.next.next; // 6 → 3 으로 고리를 만든다
console.log(cycleStart(c), cycleStart(fromArray([1, 2, 3])));
```

```text
3 null
```

왜 시작점에서 만나는지는 거리로 따지면 된다. 머리에서 고리 시작까지를 μ, 고리 길이를 λ라고 하자. 처음 만날 때 slow가 k칸을 갔다면 fast는 2k칸을 갔고, 그 차이 k는 fast가 고리를 더 돈 거리라 λ의 배수다. 위 예에서 k = 4, λ = 4다. slow는 머리에서 k칸 와 있으니, 거기서 μ칸을 더 가면 머리에서 k + μ칸이 된다. 이 자리는 고리 시작점(μ칸 지점)에서 λ의 배수만큼 더 간 곳이라 다시 고리 시작점이다. 머리에서 출발한 p도 μ칸 뒤에 시작점에 닿으니 둘이 거기서 만난다.

실무에서 이 알고리즘을 직접 짤 일은 드물다. 하지만 같은 생각은 자주 쓴다. 작업이 다음 작업을 가리키는 체인, 부모를 따라 올라가는 트리, 리다이렉트를 따라가는 크롤러처럼 "다음"을 따라가는 코드는 고리가 생기면 멈추지 않는다. 방문 표시나 최대 단계 수를 두지 않은 순회는 장애 때 CPU 100%로 드러난다. 자바 7의 `HashMap`이 동시 수정 중 버킷 리스트가 고리로 꼬여 무한 루프를 돌던 사고가 유명하다([스레드 안전성](/posts/thread-safety)).

## 정렬된 두 줄을 하나로 합치기

정렬된 두 리스트를 하나의 정렬된 리스트로 합치는 문제다. 병합 정렬의 합치기 단계와 같고, [힙](/posts/ds-heap) 글의 "k개 리스트 합치기"로 이어진다. 두 머리 중 작은 쪽을 떼어 결과 꼬리에 붙이는 일을 반복한다. 노드를 새로 만들지 않고 `next`만 다시 잇는다.

```js
function merge(a, b) {
  const dummy = new ListNode(0);
  let t = dummy;                   // 결과의 꼬리
  while (a && b) {
    if (a.value <= b.value) { t.next = a; a = a.next; }
    else { t.next = b; b = b.next; }
    t = t.next;
  }
  t.next = a ?? b;                 // 남은 쪽은 이미 정렬돼 있으니 통째로 붙인다
  return dummy.next;
}
console.log(toArray(merge(fromArray([1, 4, 7]), fromArray([2, 3, 8, 9]))));
```

## 자바스크립트에서 연결 리스트를 잘 안 쓰는 이유

이론상 장점이 있는데도 자바스크립트 코드에서 연결 리스트를 직접 만드는 일은 드물다. 같은 100만 개를 배열과 연결 리스트로 들고 메모리와 순회 시간을 쟀다. 세 번째는 노드를 만든 순서와 연결 순서를 무작위로 섞은 리스트다. 오래 돌아가는 서비스에서 넣고 빼기를 반복한 리스트는 노드가 힙 여기저기에 흩어지는데, 그 상태를 흉내 낸 것이다.

```js
// node --expose-gc llbench.js
class ListNode { constructor(value, next = null) { this.value = value; this.next = next; } }
const N = 1_000_000;

function heap(fn) {
  gc(); const before = process.memoryUsage().heapUsed;
  const keep = fn();
  gc(); const after = process.memoryUsage().heapUsed;
  return { keep, bytes: (after - before) / N };
}
const arr = heap(() => Array.from({ length: N }, (_, i) => i));
const list = heap(() => { let h = null; for (let i = N - 1; i >= 0; i--) h = new ListNode(i, h); return h; });
console.log("원소 하나당 메모리  array", arr.bytes.toFixed(1) + "B", " list", list.bytes.toFixed(1) + "B");

// 노드를 무작위 순서로 이어 붙인 리스트: 메모리 위치와 연결 순서가 어긋난다
const nodes = Array.from({ length: N }, (_, i) => new ListNode(i));
for (let i = N - 1; i > 0; i--) { const j = Math.floor(Math.random() * (i + 1)); [nodes[i], nodes[j]] = [nodes[j], nodes[i]]; }
for (let i = 0; i < N - 1; i++) nodes[i].next = nodes[i + 1];
const shuffled = nodes[0];

function time(name, fn) {
  fn();
  const t = performance.now();
  let s = 0;
  for (let k = 0; k < 10; k++) s += fn();
  console.log(name.padEnd(16), ((performance.now() - t) / 10).toFixed(2) + "ms", s / 10);
}
time("array 순회", () => { let s = 0; const a = arr.keep; for (let i = 0; i < a.length; i++) s += a[i]; return s; });
time("list 순회", () => { let s = 0; for (let n = list.keep; n; n = n.next) s += n.value; return s; });
time("섞인 list 순회", () => { let s = 0; for (let n = shuffled; n; n = n.next) s += n.value; return s; });
```

이 글을 쓴 머신(Intel Xeon 2.8GHz, Node 22.22)에서 잰 값이다. 섞인 리스트는 섞는 순서가 매번 달라서 같은 머신에서도 150~200ms 사이로 흔들렸다. 세 순회 모두 O(n)인데 배열과 섞인 리스트는 90배쯤 차이 난다.

메모리부터 보자. 배열은 칸 하나에 8바이트다. 연결 리스트 노드는 40바이트였다. V8 객체에는 값 두 개(`value`, `next`) 말고도 객체의 모양을 가리키는 맵 포인터, 속성 저장소, 원소 저장소 포인터가 붙어서다. 원소 100만 개에서 8MB와 40MB의 차이이고, 그만큼 가비지 컬렉터가 훑을 객체도 100만 개 늘어난다([가비지 컬렉션](/posts/garbage-collection)).

순회 시간은 [배열 글의 행렬 측정](/posts/ds-array-matrix)과 같은 원리다. 배열은 붙어 있는 칸을 차례로 읽으니 캐시 라인 하나로 값 여러 개를 얻는다. 연결 리스트는 다음 노드의 주소를 읽어야 다음 노드를 가져올 수 있어서 CPU가 미리 가져오기를 할 수 없다. 노드를 차례로 만든 직후에는 V8이 노드를 메모리에 나란히 놓아서 그나마 9ms였지만, 섞이면 노드마다 캐시 미스가 나서 152ms가 됐다. 이론의 O(1) 삽입이 실제로 이득이 되려면 이 상수 차이를 이길 만큼 중간 삽입·삭제가 많아야 한다.

그래서 자바스크립트에서는 보통 이렇게 고른다. 끝에서만 넣고 빼면 배열이다. 앞에서 빼는 큐가 필요하면 배열에 head 인덱스를 두거나 링 버퍼를 쓴다([스택, 큐, 덱](/posts/ds-stack-queue-deque)). 연결 리스트는 해시맵이 노드를 바로 가리켜서 찾는 비용이 없고, 쥔 노드를 O(1)에 빼야 할 때 쓴다.

## 해시맵이 노드를 가리킬 때: LRU 캐시

연결 리스트가 제자리를 찾는 대표 사례가 LRU 캐시다. 용량이 차면 가장 오래 안 쓴 항목을 버리는 캐시로, `get`과 `put`을 모두 O(1)에 해야 한다. 해시맵은 키로 노드를 바로 찾아 주고, 이중 연결 리스트는 사용 순서를 들고 있다. 맨 앞이 가장 최근, 맨 뒤가 가장 오래된 쪽이다. 읽을 때마다 그 노드를 빼서 맨 앞으로 옮기고, 넘치면 맨 뒤를 버린다. 앞뒤를 다 알아야 중간 노드를 O(1)에 빼므로 이중이어야 한다.

```js
class LRUCache {
  constructor(capacity) {
    this.capacity = capacity;
    this.map = new Map();                         // key → 노드
    this.head = { prev: null, next: null };       // 가짜 머리: 가장 최근 쪽
    this.tail = { prev: this.head, next: null };  // 가짜 꼬리: 가장 오래된 쪽
    this.head.next = this.tail;
  }
  #unlink(node) { node.prev.next = node.next; node.next.prev = node.prev; }
  #pushFront(node) {
    node.next = this.head.next; node.prev = this.head;
    this.head.next.prev = node; this.head.next = node;
  }
  get(key) {
    const node = this.map.get(key);
    if (!node) return -1;
    this.#unlink(node); this.#pushFront(node);    // 읽으면 맨 앞으로
    return node.value;
  }
  put(key, value) {
    let node = this.map.get(key);
    if (node) { node.value = value; this.#unlink(node); this.#pushFront(node); return; }
    if (this.map.size === this.capacity) {
      const old = this.tail.prev;                 // 가장 오래된 것
      this.#unlink(old); this.map.delete(old.key);
    }
    node = { key, value, prev: null, next: null };
    this.#pushFront(node); this.map.set(key, node);
  }
  keys() { const out = []; for (let n = this.head.next; n !== this.tail; n = n.next) out.push(n.key); return out; }
}
const cache = new LRUCache(2);
cache.put("a", 1);
cache.put("b", 2);
console.log(cache.get("a"), cache.keys());
cache.put("c", 3);                  // b가 밀려난다
console.log(cache.get("b"), cache.keys());
```

```text
1 [ 'a', 'b' ]
-1 [ 'c', 'a' ]
```

양 끝에 가짜 노드를 두면 "리스트가 비었나", "머리를 빼나" 같은 분기가 전부 사라진다. 앞에서 본 dummy와 같은 요령이다. 노드에 `key`를 넣어 두는 것도 빠뜨리기 쉽다. 맨 뒤 노드를 버릴 때 해시맵에서도 지워야 하는데, 노드가 자기 키를 모르면 찾을 방법이 없다. 아래 그림에서 `put("c")`가 일어날 때 둘이 어떻게 함께 움직이는지 보자.

## React 안에도 연결 리스트가 있다

React를 쓰면 연결 리스트를 직접 만들지 않아도 매일 그 위에서 일한다. 컴포넌트의 훅은 컴포넌트마다 배열이 아니라 연결 리스트로 저장된다. react-dom 19의 개발 빌드 소스에서 훅을 처음 만드는 함수를 보면 이렇다.

```js
// node_modules/react-dom/cjs/react-dom-client.development.js (19.3.1)
function mountWorkInProgressHook() {
  var hook = {
    memoizedState: null,
    baseState: null,
    baseQueue: null,
    queue: null,
    next: null
  };
  null === workInProgressHook
    ? (currentlyRenderingFiber.memoizedState = workInProgressHook = hook)
    : (workInProgressHook = workInProgressHook.next = hook);
  return workInProgressHook;
}
```

첫 훅이면 컴포넌트(Fiber)의 `memoizedState`에 달고, 아니면 앞 훅의 `next`에 붙인다. 다시 렌더링할 때는 이 리스트를 머리부터 한 칸씩 따라가며 "이번 `useState` 호출은 리스트의 몇 번째 노드"로 짝을 맞춘다. 훅에는 이름이 없고 순서만 있다. 그래서 조건문 안에서 훅을 부르면 안 된다는 규칙이 생긴다. 어떤 렌더에서 훅 하나를 건너뛰면 그 뒤의 훅이 모두 한 칸씩 밀려 엉뚱한 상태를 읽는다. 같은 소스에 `"Rendered more hooks than during the previous render."`라는 에러가 있는데, 리스트 끝을 넘어 따라가려 할 때 나는 에러다.

Fiber 트리 자체도 연결 구조다. 노드마다 `child`(첫 자식), `sibling`(다음 형제), `return`(부모) 포인터가 있고, React는 재귀 호출 대신 이 포인터를 따라 반복문으로 트리를 걷는다. 그래서 작업을 중간에 멈췄다가 그 노드부터 다시 이어 갈 수 있다. 재귀였다면 호출 스택에 상태가 묶여서 중간에 멈출 수 없다. 왜 리렌더링이 일어나는지는 [React 리렌더링 글](/posts/react-rerender)에서 다룬다.

## 연결 리스트 코드에서 자주 나는 실수

포인터를 바꾸는 순서를 틀리면 노드를 잃는다. 처음의 버그처럼 다음 노드를 잡아 두기 전에 `next`를 덮어쓰는 실수다. 그림을 그리고 화살표 하나를 바꿀 때마다 아직 닿을 수 있는 노드를 확인하면 잡힌다.

`null` 검사를 빠뜨린다. `fast.next.next`는 `fast`가 마지막 노드면 `TypeError`다. 반복 조건을 `fast && fast.next`로 두는 이유다. 빈 리스트, 노드 하나, 노드 둘은 거의 모든 연결 리스트 문제의 경계 테스트다.

머리가 바뀌는 경우를 따로 처리하다 분기가 늘어난다. dummy 노드를 앞에 붙이면 사라진다.

이중 연결 리스트에서 한쪽 포인터만 고친다. `prev`를 고치고 `next`를 안 고치면 앞으로 순회할 때와 뒤로 순회할 때 다른 리스트가 보인다. 넣기와 빼기는 각각 포인터 네 개, 두 개를 바꾸는지 세어 본다.

리스트를 다 쓴 뒤에도 노드 하나를 어딘가에 들고 있으면, 그 노드에서 닿는 나머지 노드도 전부 메모리에 남는다. 특히 이중 연결 리스트는 아무 노드 하나만 잡혀 있어도 양쪽으로 전체가 살아 있다. 캐시에서 버린 노드의 `prev`와 `next`를 `null`로 끊어 두는 게 안전하다([메모리 누수 찾기](/posts/js-memory-leak)).

배열 대신 연결 리스트를 쓰는 건 포인터 하나만 바꿔서 끼우고 빼는 능력을 사는 대신, 인덱스와 캐시 지역성을 내주는 거래다. 해시맵이 노드를 가리켜 줄 때만 그 거래가 남는다. 다음 글 [스택, 큐, 덱](/posts/ds-stack-queue-deque)에서는 넣고 빼는 위치를 끝으로 제한하면 배열로도 충분히 빠르게 만들 수 있다는 걸 본다.

## 면접에서 나올 만한 질문

### 배열과 연결 리스트의 차이를 설명해 보세요.

배열은 칸이 메모리에 붙어 있어서 인덱스 접근이 O(1)이지만 앞이나 중간에 넣고 빼면 O(n)이다. 연결 리스트는 노드가 다음 노드의 주소를 들고 흩어져 있어서 i번째에 가려면 O(n)이지만, 쥐고 있는 노드 옆에 넣고 빼는 건 O(1)이다. 실제로는 노드 객체의 메모리 비용과 캐시 미스 때문에 순회가 훨씬 느려서, 대부분의 경우 배열이 더 빠르다.

### 연결 리스트의 중간 삽입이 O(1)이라는 말은 맞나요?

넣을 자리의 노드를 이미 쥐고 있을 때만 맞다. 인덱스로 위치가 주어지면 그곳까지 따라가는 데 O(n)이 들어서 배열과 같다. 해시맵이 노드를 바로 가리켜 주는 LRU 캐시처럼 찾는 비용이 없는 구조에서만 O(1)의 장점이 산다.

### 단일 연결 리스트를 뒤집는 방법과 복잡도를 말해 보세요.

prev, curr, next 세 포인터로 한 칸씩 가며 화살표를 뒤로 돌리면 O(n) 시간, O(1) 공간이다. 다음 노드를 변수에 잡아 두고 나서 `next`를 바꿔야 나머지 노드를 잃지 않는다. 재귀로도 짤 수 있지만 노드 수만큼 호출이 쌓여 공간이 O(n)이고, Node 22에서는 노드 10만 개에서 스택이 넘쳤다.

### 리스트에 고리가 있는지 어떻게 확인하나요? 메모리를 쓰지 않는다면요?

방문한 노드를 Set에 넣으면 O(n) 공간으로 되고, 메모리 없이는 Floyd 알고리즘을 쓴다. 느린 포인터는 한 칸, 빠른 포인터는 두 칸씩 보내서 빠른 쪽이 null에 닿으면 고리가 없고, 둘이 만나면 고리가 있다. 고리 안에서는 빠른 쪽이 한 번 움직일 때마다 간격이 한 칸씩 줄어서 반드시 만난다.

### 고리의 시작점은 어떻게 찾나요?

만난 뒤 한 포인터를 머리로 보내고 둘을 한 칸씩 움직이면 고리 시작점에서 만난다. 처음 만날 때까지 느린 포인터가 간 거리 k가 고리 길이의 배수이기 때문에, 머리에서 시작점까지의 거리 μ만큼 더 가면 두 포인터 모두 시작점에 선다. 6이 3을 가리키는 예에서 k = 4, 고리 길이 4, μ = 2였다.

### LRU 캐시를 O(1)로 구현하려면 어떤 자료구조가 필요한가요?

해시맵과 이중 연결 리스트를 함께 쓴다. 해시맵은 키로 노드를 바로 찾고, 이중 연결 리스트는 사용 순서를 들고 있어서 읽은 노드를 빼서 맨 앞으로 옮기고 넘치면 맨 뒤를 버린다. 중간 노드를 O(1)에 빼려면 앞 노드를 알아야 하니 이중이어야 하고, 버린 노드를 맵에서도 지우려면 노드에 키를 넣어 둬야 한다.

### React의 훅을 조건문 안에서 부르면 안 되는 이유를 자료구조로 설명해 보세요.

훅이 컴포넌트마다 호출 순서대로 연결 리스트에 저장되고, 다시 렌더링할 때 그 리스트를 머리부터 따라가며 짝을 맞추기 때문이다. 훅에는 이름이 없어서 한 렌더에서 하나를 건너뛰면 뒤의 훅들이 한 칸씩 밀려 다른 훅의 상태를 읽는다. 개수가 달라지면 "Rendered more hooks than during the previous render." 같은 에러가 난다.

### 자바스크립트에서 연결 리스트가 배열보다 느린 이유는 무엇인가요?

노드 하나가 별도 객체라 메모리를 더 쓰고, 다음 주소를 읽어야 다음 노드를 가져올 수 있어서 캐시와 프리페치의 도움을 못 받기 때문이다. 이 글의 측정에서 노드는 40바이트, 배열 칸은 8바이트였고, 100만 개 순회는 배열 1.7ms, 노드가 흩어진 리스트 152ms였다. 객체가 많아지면 가비지 컬렉션 부담도 커진다.
