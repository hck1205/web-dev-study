Vite로 만든 사이드 프로젝트를 GitHub Pages에 올렸다. 첫 화면은 잘 뜬다. 메뉴를 눌러 `/settings`로 가는 것도 된다. 그런데 그 주소에서 새로고침을 하자 GitHub의 404 페이지가 나온다. 며칠 뒤 다른 곳으로 옮겨 새 버전을 배포했더니, 이번에는 탭을 오래 열어 둔 사용자 몇 명이 "설정 버튼을 누르면 화면이 하얘진다"고 한다.

두 증상 모두 호스팅이 무엇을 해 주고 무엇을 안 해 주는지 몰라서 생긴다. 이 글은 프런트엔드를 올리는 자리를 다섯 가지 모양으로 나누고, 각 자리에서 SPA 라우팅 폴백, 캐시, 프리뷰 배포, 콜드 스타트, 환경 변수, 도메인과 HTTPS가 어떻게 다른지 본다. 마지막에 비용과 락인을 기준으로 고르는 순서를 정리한다.

플랫폼의 기능과 요금은 자주 바뀐다. 이 글의 플랫폼 설명은 2026년 하반기에 각 서비스 공식 문서에 적힌 내용을 기준으로 했고, 요금제별 한도 숫자는 일부러 적지 않았다. 고를 때는 그 시점의 문서를 다시 본다.

## 빌드 결과물에 서버가 필요한가

호스팅을 고르기 전에 `npm run build`가 무엇을 만드는지부터 본다.

Vite나 Create React App으로 만든 SPA, Astro나 Next.js의 정적 내보내기(`output: "export"`)는 HTML, JS, CSS, 이미지 파일만 남긴다. 이건 어떤 웹 서버든 파일을 그대로 내주기만 하면 된다. 서버에서 실행되는 코드가 없다.

반대로 요청마다 서버에서 코드가 돌아야 하는 기능이 하나라도 있으면 실행 환경이 필요하다. 요청 시점에 HTML을 만드는 SSR, 일정 주기로 페이지를 다시 만드는 ISR, API 라우트나 서버 액션, 요청을 가로채는 미들웨어, 요청에 맞춰 크기를 바꾸는 이미지 최적화가 그렇다. 어떤 페이지가 정적이고 어떤 페이지가 동적인지는 [렌더링 전략](/posts/rendering-strategies) 글에서 정리했다.

이 구분이 첫 갈림길이다. 정적 파일뿐이면 거의 공짜로 어디든 올릴 수 있고 옮기기도 쉽다. 서버 코드가 있으면 그 코드를 어디서 어떤 방식으로 돌릴지가 비용과 락인을 결정한다.

## 다섯 가지 자리

프런트엔드를 올리는 자리는 대략 이렇게 나뉜다.

### 정적 호스팅: 파일을 내주기만 한다

GitHub Pages, S3와 CloudFront 조합, Cloudflare Pages의 정적 부분, Firebase Hosting 같은 것이다. 올린 파일을 그대로 내준다. 서버 코드는 돌지 않는다.

GitHub Pages는 저장소 하나로 끝나서 가장 간단하다. 대신 서버 쪽 재작성(rewrite) 규칙을 줄 수 없고, 응답 헤더도 마음대로 못 바꾼다. 문서상 사이트 크기는 1GB까지, 대역폭은 월 100GB 정도의 소프트 한도가 있다. 개인 블로그나 문서 사이트에 맞다.

S3와 CloudFront는 AWS 안에서 정적 사이트를 올리는 표준 조합이다. 버킷은 비공개로 두고 CloudFront만 읽게 한다(Origin Access Control). 헤더, 캐시 정책, 오류 응답, 경로별 동작을 다 정할 수 있다. 손이 많이 가는 대신 통제권이 크다. 버킷 쪽 설정은 [S3 실무](/posts/aws-s3-in-practice) 글에 있다.

### 엣지와 서버리스를 묶은 플랫폼

Vercel, Netlify, Cloudflare가 이 자리다. Git 저장소를 연결하면 푸시할 때마다 빌드하고, 정적 파일은 CDN에 깔고, 서버 코드는 함수로 바꿔 돌린다. 프리뷰 배포, 즉시 롤백, 자동 HTTPS가 기본으로 따라온다.

서버 코드를 돌리는 방식이 두 갈래다. 하나는 특정 리전에서 도는 서버리스 함수(Node.js 런타임)다. 일반 Node API를 다 쓸 수 있고, 데이터베이스 가까운 리전에 두면 쿼리가 빠르다. 다른 하나는 사용자 가까운 엣지에서 도는 함수다. Cloudflare Workers처럼 V8 isolate 위에서 돌아 시작이 빠르지만, 쓸 수 있는 API가 제한되고 DB가 멀면 오히려 느려진다. 요즘 Vercel 문서는 대부분의 함수를 Node.js 런타임으로 돌리길 권하고, 엣지는 리다이렉트나 인증 확인 같은 가벼운 일에 쓰는 쪽이다. 엣지가 어떻게 가까운 곳에서 답하는지는 [CDN 엣지와 애니캐스트](/posts/cdn-edge-anycast)에서 본다.

Cloudflare는 정적 사이트용으로 Pages를 먼저 냈고, 지금은 Workers에 정적 파일을 함께 올리는 방식(Workers static assets)을 새 프로젝트에 권한다. 이름이 바뀌는 중이니 문서를 볼 때 어느 쪽 설명인지 확인한다.

### 컨테이너 PaaS: 늘 떠 있는 프로세스

Render, Railway, Fly.io 같은 곳이다. Dockerfile이나 빌드 명령을 주면 컨테이너를 띄우고 계속 켜 둔다. 요청이 올 때마다 함수를 새로 띄우지 않으니 콜드 스타트가 없고(무료 요금제 제외), 웹소켓이나 긴 작업, 메모리 캐시가 자연스럽다. Next.js를 `next start`로 돌리는 것과 같아서 플랫폼 전용 기능에 덜 묶인다.

대신 CDN이 기본으로 붙지 않거나 약할 수 있다. 정적 파일까지 컨테이너가 내주면 멀리 있는 사용자는 느리다. 앞에 CDN을 따로 두는 경우가 많다. 무료 요금제는 잠들기도 한다. Render 문서는 무료 웹 서비스가 15분 동안 요청이 없으면 멈추고, 다음 요청에서 다시 뜨는 데 1분 가까이 걸릴 수 있다고 적고 있다.

### VPS와 직접 운영

EC2나 Lightsail, 국내 클라우드의 가상 서버에 Nginx와 Node를 직접 올리는 방식이다. 가장 싸고 자유롭지만, OS 패치, 인증서 갱신, 프로세스 재시작, 무중단 배포를 다 내가 한다. 플랫폼이 해 주던 일을 직접 챙기는 목록은 [Next.js 직접 운영하기](/posts/nextjs-self-hosting-deployment)에 있다. 어디까지가 내 칸인지는 [IaaS와 PaaS의 책임 경계](/posts/cloud-service-models-shared-responsibility)와 같은 이야기다.

## 새로고침하면 404가 나는 이유

처음 장면의 첫 증상이다. SPA에서 `/settings`는 브라우저 안의 라우터가 History API로 주소만 바꾼 것이다. 서버에는 `settings`라는 파일이 없다. 링크를 눌러 이동할 때는 서버에 묻지 않으니 괜찮지만, 그 주소에서 새로고침하거나 공유받은 링크로 들어오면 브라우저가 서버에 `/settings`를 달라고 한다. 파일 서버는 정직하게 404를 낸다. 이 개념은 [CSR과 SPA](/posts/rendering-csr-spa) 글에서 다뤘고, 여기서는 호스팅마다 무엇을 설정하는지를 본다.

스크래치 디렉터리에 `index.html` 하나와 해시가 붙은 JS 하나만 두고 Python의 기본 파일 서버로 띄워 확인했다(Python 3.13).

```bash
# 빌드 결과를 흉내 낸 폴더에서 파일 서버를 띄운다
python3 -m http.server 8765

# 다른 터미널: 루트, 깊은 주소, 없는 JS를 차례로 요청한다
curl -sI http://127.0.0.1:8765/
curl -sI http://127.0.0.1:8765/settings/profile
curl -sI http://127.0.0.1:8765/assets/index-old999.js
```

```text
HTTP/1.0 200 OK
Server: SimpleHTTP/0.6 Python/3.13.16
Date: Sat, 24 Oct 2026 00:11:27 GMT
Content-type: text/html
Content-Length: 82
Last-Modified: Sat, 24 Oct 2026 00:11:26 GMT

HTTP/1.0 404 File not found
Server: SimpleHTTP/0.6 Python/3.13.16
Date: Sat, 24 Oct 2026 00:11:27 GMT
Connection: close
Content-Type: text/html;charset=utf-8
Content-Length: 335

HTTP/1.0 404 File not found
...
```

GitHub Pages도 이 상태다. 해결은 "파일이 없으면 index.html을 200으로 내준다"는 폴백 규칙인데, 이 규칙을 어디에 거느냐가 플랫폼마다 다르다.

- Netlify: 배포 폴더에 `_redirects` 파일을 두고 `/*  /index.html  200` 한 줄을 쓴다. 파일이 있으면 파일이 먼저다.
- Vercel: `vercel.json`의 `rewrites`에 모든 경로를 `/index.html`로 보내는 규칙을 둔다. Next.js 프로젝트는 프레임워크가 라우팅을 처리하니 필요 없다.
- Cloudflare: Pages는 최상위에 `404.html`이 없으면 SPA로 보고 알아서 index.html을 내준다. Workers static assets는 설정에 `not_found_handling = "single-page-application"`을 준다.
- S3와 CloudFront: CloudFront 배포의 사용자 지정 오류 응답에서 403과 404를 `/index.html`, 상태 200으로 바꾼다. 버킷이 비공개면 없는 파일에 404 대신 403이 오기 때문에 둘 다 건다.
- GitHub Pages: 서버 규칙이 없다. `index.html`을 `404.html`로 복사해 두는 우회가 흔한데, 상태 코드는 여전히 404라서 검색 엔진과 모니터링에는 오류로 보인다. 해시 라우터(`/#/settings`)로 바꾸는 방법도 있다.
- Nginx: `try_files $uri $uri/ /index.html;`

여기에 함정이 하나 있다. 폴백을 모든 경로에 걸면 없는 JS 파일 요청에도 index.html이 200으로 나간다. 위 폴더에 폴백 서버 두 가지를 띄워 비교했다. 하나는 모든 경로에, 다른 하나는 확장자가 없는 경로에만 폴백을 건다.

```bash
# 8766: 없는 경로는 전부 index.html / 8767: 확장자 없는 경로만 index.html
for port in 8766 8767; do
  echo "== $port"
  for u in /settings/profile /assets/index-old999.js; do
    curl -s -o /dev/null -w "$u %{http_code} %{content_type}\n" http://127.0.0.1:$port$u
  done
done
```

```text
== 8766
/settings/profile 200 text/html
/assets/index-old999.js 200 text/html
== 8767
/settings/profile 200 text/html
/assets/index-old999.js 404 text/html;charset=utf-8
```

8766에서는 존재하지 않는 JS가 200으로 성공한다. 내용은 HTML이다. 브라우저는 이걸 모듈로 실행하려다 MIME 타입 오류를 내고, CDN은 200 응답이라 이 HTML을 JS 주소에 캐시할 수도 있다. CloudFront의 사용자 지정 오류 응답과 Netlify의 `/*` 규칙이 이 모양에 가깝다. 정적 파일 폴더(`/assets/`)는 폴백에서 빼는 게 안전하다. 플랫폼별로 쓰면 이렇다.

```nginx
# Nginx: 해시 파일 폴더는 없으면 그대로 404, 나머지만 index.html
location /assets/ {
    try_files $uri =404;
    add_header Cache-Control "public, max-age=31536000, immutable";
}
location / {
    try_files $uri $uri/ /index.html;
    add_header Cache-Control "no-cache";
}
```

```json
{
  "rewrites": [{ "source": "/((?!assets/).*)", "destination": "/index.html" }]
}
```

위는 Vercel의 `vercel.json`이다. 정규식의 부정 전방 탐색으로 `assets/`로 시작하는 경로를 규칙에서 뺀다. CloudFront라면 사용자 지정 오류 응답 대신 뷰어 요청 단계의 CloudFront Functions로 확장자 없는 요청만 바꾼다.

```js
// CloudFront Functions (viewer-request): 마지막 조각에 점이 없으면 SPA 경로로 본다
function handler(event) {
  var request = event.request;
  var last = request.uri.split("/").pop();
  if (last.indexOf(".") === -1) {
    request.uri = "/index.html";
  }
  return request;
}
```

이렇게 하면 `/settings/profile`은 index.html로, `/assets/index-old999.js`는 그대로 원본에 가서 404가 난다. 경로에 점이 들어가는 라우트(`/users/kim.lee`)가 있다면 규칙을 그 앱에 맞게 고친다.

배포한 뒤에는 세 가지를 직접 찔러 본다. 깊은 주소, 없는 JS, 그리고 해시 파일과 HTML의 캐시 헤더다.

```bash
# 깊은 주소는 200 text/html이어야 한다
curl -s -o /dev/null -w "%{http_code} %{content_type}\n" https://example.com/settings/profile
# 없는 JS는 404여야 한다. 200 text/html이면 폴백이 너무 넓다
curl -s -o /dev/null -w "%{http_code} %{content_type}\n" https://example.com/assets/nope-000.js
# 해시 파일과 HTML의 Cache-Control을 비교한다
curl -sI https://example.com/ | grep -i cache-control
```

정적 호스팅의 캐시 규칙은 두 줄로 정리된다. 내용 해시가 이름에 들어간 파일은 영원히 캐시하고, 그 파일 이름을 담고 있는 HTML은 매번 확인한다. 해시 파일에 붙이는 헤더를 조각내 보면 이렇다.

HTML에는 `Cache-Control: no-cache`(저장은 하되 쓸 때마다 서버에 확인)나 `max-age=0, must-revalidate`를 준다. HTML까지 길게 캐시하면 새 배포를 해도 사용자는 옛 HTML이 가리키는 옛 JS를 계속 받는다. 캐시 헤더와 CDN 동작의 자세한 내용은 [HTTP 캐시와 CDN](/posts/http-caching-cdn)에 있다.

플랫폼형 호스팅은 이걸 알아서 해 준다. Vercel과 Netlify는 배포마다 엣지 캐시를 새 배포 기준으로 바꾸니 무효화를 따로 하지 않는다. S3와 CloudFront는 내가 한다. 업로드할 때 파일 종류별로 헤더를 다르게 주고, 배포 뒤 HTML 경로만 무효화한다. CloudFront 무효화는 매달 처음 1,000개 경로까지 무료이고 그 뒤로 경로당 요금이 붙는다. 와일드카드 `/*`도 경로 하나로 센다.

```bash
# 해시 파일: 1년 + immutable. 옛 파일은 지우지 않는다(--delete 없음)
aws s3 sync dist/assets s3://my-site/assets \
  --cache-control "public, max-age=31536000, immutable"

# HTML은 마지막에 올린다. 새 HTML이 가리킬 JS가 이미 올라가 있어야 한다
aws s3 cp dist/index.html s3://my-site/index.html \
  --cache-control "no-cache" --content-type "text/html; charset=utf-8"

# 엣지에 남은 옛 HTML만 지운다
aws cloudfront create-invalidation --distribution-id E1234EXAMPLE --paths "/index.html" "/"
```

순서가 중요하다. HTML을 먼저 올리면 몇 초 동안 새 HTML이 아직 없는 JS를 가리킨다. 그리고 옛 해시 파일을 바로 지우지 않는 것이 다음 장애를 막는다.

대응은 세 겹이다.

첫째, 옛 파일을 한동안 남긴다. S3라면 `--delete` 없이 동기화하고, 오래된 해시 파일은 수명 주기 규칙으로 몇 주 뒤에 지운다. Vercel과 Netlify는 배포마다 고유 URL을 가진 불변 스냅숏을 남기지만, 운영 도메인은 최신 배포만 가리키므로 열린 탭의 옛 요청이 새 배포로 간다. Vercel의 Skew Protection은 클라이언트를 자기가 처음 받은 배포에 묶어 이 문제를 플랫폼에서 푼다(요금제에 따라 쓸 수 있다). 직접 운영할 때는 Next.js의 `deploymentId` 설정이 비슷한 역할을 한다.

둘째, 실패를 잡아 새로고침한다. Vite는 동적 import의 미리 불러오기가 실패하면 `window`에 `vite:preloadError` 이벤트를 보낸다. 여기서 한 번만 새로고침하게 하면 대부분 사용자는 증상을 모른다. 무한 새로고침을 막는 표시를 꼭 둔다.

```ts
// main.tsx: 청크 로드 실패 시 한 번만 새로고침한다
window.addEventListener("vite:preloadError", (event) => {
  const key = "reloaded-after-deploy";
  if (sessionStorage.getItem(key)) return; // 이미 한 번 했으면 오류를 그대로 둔다
  sessionStorage.setItem(key, "1");
  event.preventDefault();
  window.location.reload();
});
```

셋째, 오류 경계로 화면 전체가 내려가지 않게 한다. "새 버전이 나왔다, 새로고침해 달라"는 안내를 그 자리에 보여 주는 것만으로도 하얀 화면 문의가 줄어든다.

## 프리뷰 배포가 바꾸는 것

플랫폼형 호스팅의 가장 큰 장점은 PR마다 고유 주소의 프리뷰 배포가 생기는 것이다. 리뷰어가 코드 대신 화면을 보고, 디자이너와 기획자가 직접 눌러 본다. E2E 테스트를 그 주소에 돌리면 운영과 같은 빌드로 검증한다.

프리뷰에도 실수가 있다. 프리뷰가 운영 DB나 운영 결제 키를 쓰면 리뷰어의 테스트가 실제 데이터를 바꾼다. 환경 변수는 Production, Preview, Development를 나눠서 넣는다. 프리뷰 주소는 추측하기 어렵지만 비밀은 아니다. 내부 기능이 담긴 프리뷰는 플랫폼의 접근 보호를 켜고, 검색 엔진에 잡히지 않게 `X-Robots-Tag: noindex`를 준다(Vercel은 프리뷰에 기본으로 붙인다). OAuth 콜백 주소도 프리뷰 도메인마다 등록할 수 없으니, 프리뷰에서는 로그인이 안 되는 경우가 흔하다. 와일드카드 콜백을 허용하는 인증 서비스를 쓰거나 고정된 스테이징 도메인을 따로 둔다.

S3와 CloudFront로도 프리뷰를 만들 수 있다. PR 번호별로 버킷 접두사를 나누고 CI에서 올리면 된다. 다만 이걸 직접 만들고 정리하는 일이 플랫폼형 호스팅이 돈을 받는 이유 중 하나다.

## 함수가 늦게 깨어나는 순간

서버리스 함수는 요청이 없으면 실행 환경이 내려가고, 다음 요청에서 다시 띄운다. 이 시간이 콜드 스타트다. 번들이 크고, 초기화 때 DB 연결을 맺고, 무거운 SDK를 불러오면 길어진다. 원인과 줄이는 법은 [콜드 스타트](/posts/cold-starts)에, 실행 시간·크기·동시성 한도는 [서버리스의 한계](/posts/serverless-limits)에 정리했다.

프런트엔드 개발자가 자주 만나는 증상은 이렇다. 트래픽이 적은 새벽에 첫 SSR 요청만 몇 초 걸린다. 함수마다 DB 연결을 따로 맺어서 트래픽이 몰리면 DB 연결 수가 바닥난다. 함수를 엣지에 두었더니 DB가 한 리전에 있어서 쿼리 한 번에 수백 ms 왕복이 붙는다. 마지막 경우는 함수를 DB 리전으로 옮기는 것이 답이다. 엣지는 사용자 가까이 있을 뿐 데이터 가까이 있지 않다.

컨테이너 PaaS는 이 문제가 없다. 대신 요청이 없어도 인스턴스 비용이 나가고, 트래픽이 갑자기 늘면 인스턴스를 늘리는 데 분 단위가 걸린다. 들쭉날쭉한 트래픽은 함수가, 꾸준한 트래픽과 긴 연결은 컨테이너가 유리하다.

## 환경 변수가 번들에 박히는 순간

Next.js에서 `NEXT_PUBLIC_`으로 시작하는 환경 변수는 빌드할 때 그 값이 JS 번들에 문자열로 들어간다. Vite의 `VITE_`, Create React App의 `REACT_APP_`도 같다. 두 가지 사고가 여기서 난다.

하나는 비밀이 새는 것이다. 결제 서비스의 비밀 키를 급하게 쓰려고 `NEXT_PUBLIC_STRIPE_SECRET`처럼 접두사를 붙이면, 그 값은 누구나 내려받는 JS 파일에 그대로 실린다. 브라우저로 간 값은 공개된 값이다. 비밀이 필요한 호출은 서버 함수 안에서 하고, 접두사 없는 변수로 둔다. 혹시 들어갔다면 키를 즉시 폐기하고 새로 발급한다. 번들에서 지워도 이미 캐시된 파일과 사람들의 브라우저에 남는다.

다른 하나는 값이 안 바뀌는 것이다. 빌드할 때 박히니, 배포 플랫폼에서 값을 바꿔도 다시 빌드하기 전까지 화면에는 옛 값이 보인다. 같은 Docker 이미지를 스테이징과 운영에 함께 쓰려는 경우 이 방식이 맞지 않는다. 이때는 서버에서 런타임에 읽어 HTML이나 `/config.json`으로 내려 주는 방식으로 바꾼다.

## 도메인과 HTTPS

플랫폼에 커스텀 도메인을 붙일 때 막히는 곳은 거의 정해져 있다.

`www.example.com` 같은 하위 도메인은 플랫폼이 준 주소를 CNAME으로 가리키면 된다. 문제는 `example.com` 자체(apex)다. 도메인 꼭대기에는 SOA와 NS 레코드가 있어서 CNAME을 함께 둘 수 없다. 그래서 플랫폼은 고정 A 레코드를 알려 주거나, DNS 업체의 ALIAS·ANAME, Cloudflare의 CNAME 평탄화, Route 53의 별칭 레코드를 쓰라고 한다. Route 53 쪽은 [Route 53 라우팅 정책](/posts/route53-routing-policies)에 있다.

인증서는 Vercel, Netlify, GitHub Pages, Cloudflare 모두 자동으로 발급하고 갱신한다. 대개 Let's Encrypt 같은 공개 CA가 도메인 소유를 확인하는데, DNS가 아직 플랫폼을 가리키지 않으면 발급이 멈춘다. DNS에 CAA 레코드로 허용할 CA를 제한해 두었다면 플랫폼이 쓰는 CA를 추가해야 한다. CloudFront는 ACM 인증서를 쓰는데, 리전이 반드시 `us-east-1`이어야 한다. 서울 리전에서 발급한 인증서는 목록에 안 뜬다. HTTPS 자체가 무엇을 지켜 주는지는 [HTTPS와 TLS 1.3](/posts/https-tls)에 있다.

DNS를 옮길 때는 옮기기 하루 전쯤 기존 레코드의 TTL을 짧게 줄여 둔다. 그래야 문제가 생겼을 때 되돌린 값이 빨리 퍼진다.

## 비용과 락인

정적 파일만 있으면 비용 걱정은 거의 없다. 대부분의 플랫폼이 넉넉한 무료 구간을 준다. 비용이 커지는 곳은 세 군데다. 대역폭(큰 이미지와 동영상), 함수 실행 시간(무거운 SSR과 긴 응답), 이미지 최적화 같은 부가 기능의 사용량이다. 트래픽이 커지면 플랫폼의 사용량 요금이 같은 일을 하는 CDN과 컨테이너보다 비싸지는 지점이 온다. 이 계산은 [클라우드 비용 줄이기](/posts/cloud-cost-optimization)와 같은 방식으로 한다.

락인은 기능에서 생긴다. 정적 파일과 `next start`로 도는 Node 서버는 어디로든 옮길 수 있다. 반면 플랫폼의 ISR 캐시, 이미지 최적화, 엣지 미들웨어, KV 저장소, 플랫폼 전용 cron과 큐를 쓰기 시작하면 옮길 때 그만큼 다시 만들어야 한다. Next.js를 Vercel 밖으로 옮겼을 때 ISR이 파드마다 다르게 갱신되는 문제가 대표적이다([Next.js 직접 운영하기](/posts/nextjs-self-hosting-deployment)).

락인이 나쁜 것만은 아니다. 작은 팀이 프리뷰, 롤백, 인증서, CDN을 직접 만드는 비용은 생각보다 크다. 지금 쓰는 플랫폼 기능의 목록을 적어 두고, 각 기능을 다른 곳에서 무엇으로 대신할지 한 줄씩 메모해 두면 옮겨야 할 때 견적이 바로 나온다.

## 고르는 순서

정리하면 이렇게 고른다.

1. 빌드 결과에 서버 코드가 없으면 정적 호스팅이다. 개인 프로젝트는 GitHub Pages나 Cloudflare, 회사 AWS 안이면 S3와 CloudFront.
2. SSR, API 라우트, 미들웨어가 있고 팀이 작으면 플랫폼형(Vercel, Netlify, Cloudflare)이 빠르다. 프리뷰와 롤백을 공짜로 얻는다.
3. 웹소켓, 긴 작업, 메모리 상태가 필요하거나 플랫폼 전용 기능에 묶이기 싫으면 컨테이너 PaaS나 쿠버네티스로 간다. 앞에 CDN을 붙인다.
4. 비용이 커지거나 데이터 상주 같은 요구가 생기면 직접 운영을 계산해 본다.

어느 자리를 고르든 확인할 것은 같다. 깊은 주소 새로고침이 되는지, 없는 JS가 404로 오는지, 해시 파일과 HTML의 캐시 헤더가 다른지, 배포 직후 옛 탭에서 다른 화면으로 이동해 봐도 깨지지 않는지, 브라우저로 가는 환경 변수에 비밀이 없는지.

## 면접에서 나올 만한 질문

### SPA를 정적 호스팅에 올렸더니 새로고침하면 404가 납니다. 왜 그런가요?

`/settings` 같은 주소는 브라우저의 라우터가 History API로 바꾼 것이라 서버에는 그 파일이 없기 때문이다. 링크로 이동할 때는 서버에 묻지 않지만 새로고침이나 직접 진입 때는 서버에 그 경로를 요청한다. 파일이 없으면 index.html을 200으로 내주는 폴백 규칙을 호스팅에 걸면 해결된다.

### 폴백 규칙을 모든 경로에 걸면 무엇이 문제인가요?

없는 JS나 CSS 요청에도 index.html이 200으로 나간다. 브라우저는 HTML을 모듈로 실행하려다 MIME 타입 오류를 내고, CDN은 그 HTML을 JS 주소에 캐시할 수도 있다. 정적 파일 경로는 폴백에서 빼서 없는 파일은 404가 나게 하는 게 안전하다.

### 해시가 붙은 파일과 index.html의 캐시 전략을 왜 다르게 하나요?

해시 파일은 내용이 바뀌면 이름이 바뀌니 `max-age=31536000, immutable`로 영원히 캐시해도 된다. index.html은 그 파일 이름들을 담고 있어서 길게 캐시하면 새 배포가 사용자에게 닿지 않는다. 그래서 HTML은 `no-cache`로 매번 확인하고, 업로드도 JS를 먼저, HTML을 마지막에 한다.

### 배포 직후 일부 사용자에게 ChunkLoadError가 나는 이유와 대응은요?

오래 열어 둔 탭은 옛 HTML이 가리키는 옛 청크 이름을 들고 있는데, 새 배포가 그 파일을 지웠기 때문이다. 옛 해시 파일을 몇 주 남겨 두고, 청크 로드 실패를 잡아 한 번만 새로고침하고, 오류 경계로 화면 전체가 내려가지 않게 한다. Vercel의 Skew Protection처럼 클라이언트를 처음 받은 배포에 묶는 기능도 있다.

### 엣지 함수와 리전 서버리스 함수는 언제 각각 쓰나요?

DB가 필요 없는 가벼운 판단(리다이렉트, 쿠키 확인, A/B 분기)은 사용자 가까운 엣지에서 하고, DB를 읽는 SSR이나 API는 DB와 같은 리전의 함수에서 돌린다. 엣지에 두면 시작은 빠르지만 DB까지 왕복이 길어지고, 쓸 수 있는 API도 제한된다. 엣지는 사용자에 가깝지 데이터에 가깝지 않는다.

### NEXT_PUBLIC_ 환경 변수를 쓸 때 주의할 점은요?

빌드 시점에 값이 JS 번들에 문자열로 박힌다. 그래서 비밀 값을 넣으면 누구나 내려받는 파일로 새고, 배포 플랫폼에서 값을 바꿔도 다시 빌드하기 전에는 반영되지 않는다. 비밀은 서버 쪽 변수로만 쓰고, 이미 샜다면 키를 즉시 폐기한다.

### 정적 호스팅, 플랫폼형, 컨테이너 PaaS 중 무엇을 고르나요?

서버 코드가 없으면 정적 호스팅이 가장 싸고 옮기기 쉽다. SSR과 API가 있고 팀이 작으면 프리뷰·롤백·인증서를 주는 플랫폼형이 빠르고, 웹소켓이나 긴 작업, 전용 기능 락인을 피하고 싶으면 컨테이너 PaaS에 CDN을 붙인다. 트래픽이 커지면 사용량 요금과 직접 운영 비용을 다시 비교한다.

### apex 도메인을 플랫폼에 연결할 때 CNAME을 못 쓰는 이유는요?

도메인 꼭대기에는 SOA와 NS 레코드가 있어야 하는데 CNAME은 다른 레코드와 함께 둘 수 없기 때문이다. 그래서 플랫폼이 주는 A 레코드를 쓰거나 ALIAS, CNAME 평탄화, Route 53 별칭 레코드처럼 DNS 업체가 내부에서 풀어 주는 방식을 쓴다. www 같은 하위 도메인은 CNAME으로 충분하다.
