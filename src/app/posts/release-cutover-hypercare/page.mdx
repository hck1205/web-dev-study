금요일 밤 10시, 옛 주문 시스템에서 새 시스템으로 넘어가는 작업을 시작했다. 업무는 토요일 아침 6시에 다시 열린다. 리허설에서 두 시간 걸렸던 데이터 적재가 새벽 4시가 넘도록 끝나지 않는다. 지금 멈추고 되돌릴지, 조금만 더 기다릴지 누군가 정해야 한다. 그런데 되돌리는 데 얼마나 걸리는지, 몇 시까지 결정해야 하는지가 아무 데도 적혀 있지 않다.

새 시스템을 만드는 일과 그걸 운영에 올리는 일은 따로 계획해야 한다. 올리는 날의 절차가 컷오버(cutover)이고, 올린 뒤 몇 주 동안 평소보다 촘촘히 지켜보는 기간이 하이퍼케어(hypercare)다. 이 글은 컷오버 계획을 시각까지 적은 런북으로 만드는 법, 데이터 이관 리허설과 검증, 되돌릴 기준과 돌아올 수 없는 지점, 출시 전 관측 점검, 하이퍼케어 운영을 본다. 실습은 Node 22.22.0과 PostgreSQL 16으로 돌렸다.

이 주제의 다른 글: [벤더·레거시 시스템 연동](/posts/enterprise-system-integration), [새 나라에 서비스를 열 때](/posts/global-rollout-localization), [SIT와 UAT](/posts/sit-uat-testing). 평소 배포에서 되돌리는 법은 [롤백 전략](/posts/rollback-strategy)에서 다뤘다.

## 평소 배포와 컷오버는 무엇이 다른가

평소 배포는 작고 자주 한다. 문제가 생기면 이전 버전으로 돌아가고, DB는 호환되게 바꿔 두니 몇 분이면 끝난다. 컷오버는 다르다. 시스템 하나를 다른 시스템으로 바꾸거나, 대량의 데이터를 옮기거나, 새 시장을 한 번에 연다. 이런 전환은 쪼개기 어려운 순간을 하나쯤 품고 있다. 옛 시스템의 쓰기를 멈추고, 마지막 데이터를 옮기고, 새 시스템이 쓰기를 받기 시작하는 순간이다.

할 수 있다면 그 순간을 없애는 게 먼저다. 옛것과 새것을 함께 돌려 결과를 비교하는 병행 실행, 기능 단위로 조금씩 넘기는 방식은 [마이크로서비스 분해](/posts/microservices-decomposition#옛것과-새것을-함께-돌려-본다)에서 다뤘다. 스키마 변경을 잠금 없이 나누는 법은 [무중단 마이그레이션](/posts/zero-downtime-migrations)에 있다. 그래도 벤더 패키지를 교체하거나, 회계 마감 단위로 넘어가야 하거나, 옛 시스템이 증분 동기화를 지원하지 않으면 한 번에 넘어가는 밤이 남는다. 이 글은 그 밤을 다룬다.

## 되돌릴 수 있는 마지막 시각을 거꾸로 센다

되돌리는 데에도 시간이 든다. 옛 시스템의 쓰기를 다시 열고, 바꿔 둔 연동 설정을 되돌리고, 배치를 다시 켜고, 확인하는 시간이다. 이것도 리허설에서 잰다. 그러면 마지막으로 결정할 수 있는 시각이 나온다. 업무 재개 시각에서 되돌리기 시간을 뺀 값이다. 그리고 그 앞의 단계들은, 그 시각까지 남은 단계를 마칠 수 있도록 단계마다 마감을 갖는다.

```js
// runbook.mjs (줄임)
const start = new Date("2026-10-23T22:00:00+09:00");
const windowEnd = new Date("2026-10-24T06:00:00+09:00"); // 업무 재개
const rollbackMin = 90;                                    // 리허설에서 잰 되돌리기 시간
const steps = [
  { id: "S1", name: "쓰기 동결, 배치 정지", plan: 15, actual: 12 },
  { id: "S2", name: "최종 증분 추출", plan: 40, actual: 55 },
  { id: "S3", name: "적재와 인덱스", plan: 120, actual: 190 },
  { id: "S4", name: "건수·합계 대조", plan: 30, actual: 35, gate: true },
  { id: "S5", name: "트래픽 전환 (PONR)", plan: 10, actual: 10, ponr: true },
  { id: "S6", name: "스모크 테스트", plan: 30, actual: 25 },
  { id: "S7", name: "동결 해제, 개방", plan: 10, actual: 10 },
];
const lastGo = add(windowEnd, -rollbackMin);
// PONR 전 단계마다 "늦어도 이때까지 끝나야 한다"를 거꾸로 계산한다
function deadlines(steps) {
  const out = {};
  let t = lastGo;
  for (let i = ponrIdx - 1; i >= 0; i--) { out[steps[i].id] = t; t = add(t, -steps[i].plan); }
  return out;
}
```

```text
단계별 마감: S4 04:30, S3 04:00, S2 02:00, S1 01:20
창 22:00~06:00, 되돌리기 90분 -> 마지막 go/no-go 04:30
```

여기서 PONR(point of no return)은 돌아올 수 없는 지점이다. 이 예에서는 트래픽을 새 시스템으로 돌리는 S5다. 그 뒤로는 새 시스템이 실제 주문을 받기 시작하고, 그 주문은 옛 시스템에 없다. 그 뒤에 문제가 생기면 되돌리지 않고 고쳐서 앞으로 간다. 그래서 PONR 직전에 go/no-go 게이트(S4)를 두고, 그 게이트를 04:30 전에 통과해야 한다.

리허설 2회차 실측으로 돌려 보면 이렇다.

## 데이터 이관은 리허설에서 숫자를 얻는다

컷오버 리허설(모의 컷오버)은 최소 두 번 한다. 첫 번째는 절차가 맞는지, 두 번째는 시간이 맞는지 본다. 리허설은 운영과 같은 크기의 데이터로 한다. 1만 건으로 잰 시간은 2천만 건에서 쓸모가 없다. 인덱스 생성처럼 데이터 크기에 비례하지 않는 단계가 섞여 있기 때문이다.

이관 뒤에는 옮긴 데이터가 맞는지 확인한다. 건수만 세면 부족하다. 실습으로 옛 주문 테이블 20만 건을 새 테이블로 옮겼다. 새 시스템은 이메일을 필수로 바꿨고, 이관 스크립트에는 이메일이 없는 행을 조용히 거르는 조건이 들어 있다.

```sql
-- 옛 시스템: 997번째마다 이메일이 비어 있다
create table legacy_orders (ord_no int primary key, cust_email text, amount_krw bigint, ordered_at timestamp);
insert into legacy_orders
select g, case when g % 997 = 0 then null else 'c' || (g % 3000) || '@mail.kr' end,
       (g * 7919) % 5000000 + 1000, timestamp '2026-01-01' + (g || ' minutes')::interval
from generate_series(1, 200000) g;

-- 새 시스템: 이메일 필수, 시각은 timestamptz
create table orders (id int primary key, email text not null, amount bigint not null, ordered_at timestamptz not null);
insert into orders select ord_no, cust_email, amount_krw, ordered_at at time zone 'Asia/Seoul'
from legacy_orders where cust_email is not null;   -- 숨은 필터

-- 1) 건수와 합계
select 'legacy' as side, count(*), sum(amount_krw) as total from legacy_orders
union all
select 'new', count(*), sum(amount) from orders;
```

```text
--------+--------+--------------
 new    | 199800 | 499402315700
 legacy | 200000 | 499886900000
```

200건, 4억 8,458만 4,300원이 빠졌다. 건수와 합계가 어긋난 걸 알았으면 어디서 어긋났는지 좁힌다. 큰 테이블은 구간마다 체크섬을 내서 비교하면 어긋난 구간만 자세히 볼 수 있다.

```sql
-- 2) 1만 건 단위 구간별 체크섬
with l as (
  select ord_no / 10000 as bucket, md5(string_agg(ord_no || ':' || amount_krw, ',' order by ord_no)) as h from legacy_orders group by 1
), n as (
  select id / 10000 as bucket, md5(string_agg(id || ':' || amount, ',' order by id)) as h from orders group by 1
)
select count(*) filter (where l.h = n.h) as same_buckets,
       count(*) filter (where l.h is distinct from n.h) as diff_buckets
from l full join n using (bucket);

-- 3) 빠진 행 찾기
select l.ord_no, l.cust_email, l.amount_krw
from legacy_orders l left join orders o on o.id = l.ord_no
where o.id is null order by l.ord_no limit 5;
```

```text
 same_buckets | diff_buckets
--------------+--------------
            1 |           20
(1 row)

 ord_no | cust_email | amount_krw
--------+------------+------------
    997 |            |    2896243
   1994 |            |     791486
   2991 |            |    3686729
   3988 |            |    1581972
   4985 |            |    4477215
(5 rows)
```

21개 구간 중 20개가 다르다. 빠진 행이 한곳에 몰리지 않고 고르게 퍼졌다는 뜻이고, 빠진 행을 보면 공통점(이메일이 비어 있음)이 바로 보인다. 이건 이관 스크립트의 버그라기보다 업무 결정이 빠진 것이다. 이메일 없는 옛 주문을 어떻게 할지(가짜 값으로 채울지, 이메일 필수 규칙에서 옛 주문을 뺄지, 옮기지 않고 보관만 할지) 업무 담당이 정해야 한다. 리허설에서 이런 질문이 나와야 본 컷오버 밤에 나오지 않는다.

시간대도 확인한다. 옛 시스템의 `timestamp`는 서울 기준 현지 시각이었고, 새 시스템은 `timestamptz`다.

```text
    legacy_local     |        new_utc
---------------------+------------------------
 2026-01-01 00:01:00 | 2025-12-31 15:01:00+00
```

서울 0시 1분이 UTC 전날 15시 1분으로 맞게 들어갔다. `at time zone 'Asia/Seoul'`을 빼먹었다면 9시간이 밀린 채 들어가고, 건수와 합계 대조로는 잡히지 않는다. 그래서 검증 목록에 "샘플 몇 건을 양쪽 화면에서 눈으로 비교"를 넣는다. 아래 그림은 검증을 넓은 것에서 좁은 것 순서로 정리한 것이다.

마지막 항목이 자주 빠진다. 전환 직후 DNS나 앱 설정이 옛 주소를 보고 있으면, 새 시스템에는 요청이 오지 않으니 에러도 없다. 대시보드는 초록색이고 매출은 0이다.

## 하이퍼케어는 끝나는 날을 정하고 시작한다

열고 나서 2~4주쯤을 하이퍼케어 기간으로 둔다. 기간은 시스템과 업무 주기에 따라 다르다. 월말 정산이 있는 시스템이면 첫 월말을 넘길 때까지 두는 편이 낫다. 이 기간에 평소와 다르게 하는 것들이 있다.

- 만든 팀이 직접 1차 대응을 한다. 운영팀에 바로 넘기지 않는다. 새 시스템의 버그는 만든 사람이 가장 빨리 찾는다.
- 하루 한두 번 정해진 시각에 모여 새로 들어온 문제를 분류한다. 버그인지, 사용법 문의인지, 옛 시스템과 달라서 생긴 불만인지 나눈다. 같은 문의가 반복되면 안내 문서나 화면을 고친다.
- 배포 기준을 바꾼다. 하이퍼케어 버그 수정은 빨리 내보내야 하지만, 새 기능은 올리지 않는다. 바뀐 게 많을수록 원인을 찾기 어렵다.
- 옛 시스템을 바로 끄지 않는다. 읽기 전용으로 남겨 두면 "예전엔 이렇게 보였는데"라는 문의에 바로 비교할 수 있다. 끄는 날짜는 정해 둔다.

큰 문제가 터지면 하이퍼케어 중이라도 장애 대응 절차를 그대로 따른다. 분류, 지휘자, 완화가 먼저라는 순서는 [장애 대응](/posts/production-incidents)에 있다. 컷오버 자체가 계획대로 되지 않았다면, 되돌렸든 밀고 나갔든 [포스트모템](/posts/postmortems)을 쓴다. 다음 컷오버의 런북이 거기서 고쳐진다.

하이퍼케어를 끝내는 것도 기준으로 정한다. 예를 들면 이렇다. 심각도 1·2 문제가 일주일 동안 새로 나오지 않았다, SLO를 2주 연속 지켰다, 첫 월말 정산을 마쳤다, 운영팀이 런북과 알림을 넘겨받아 한 번 실제로 대응해 봤다. 끝나는 날이 없으면 만든 팀이 몇 달째 새벽 알림을 받으면서 다음 일을 못 한다.

## 컷오버가 흔들릴 때 보는 것

- 리허설보다 몇 배 느리다: 리허설 데이터가 운영보다 작았거나, 운영 DB에 그 시각 다른 작업(백업, 통계 수집)이 돈다. 인덱스를 적재 뒤에 만드는지, 제약 조건 검사를 나중으로 미뤘는지도 본다.
- 대조에서 건수는 맞는데 금액이 다르다: 단위(원과 천 원), 반올림, 할인·세금 줄을 어떻게 옮겼는지 본다.
- 전환했는데 일부 사용자만 옛 화면을 본다: DNS TTL, 브라우저·앱 캐시, 앱이 하드코딩한 주소다.
- 열었는데 에러율 0%, 주문도 0건: 요청이 새 시스템에 오지 않는다. 업무 지표와 로드 밸런서의 요청 수부터 본다.
- 하이퍼케어 문의가 줄지 않는다: 버그보다 바뀐 업무 흐름에 대한 문의가 많은지 본다. 교육과 화면 문구로 푸는 문제일 수 있다.

## 시각을 적어 두면 새벽의 결정이 쉬워진다

컷오버는 기술 작업이지만 핵심은 시간 관리다. 단계마다 리허설로 잰 시간과 담당자를 적고, 되돌리기 시간에서 거꾸로 단계별 마감을 계산하고, 돌아올 수 없는 지점 앞에 숫자로 된 게이트를 둔다. 옮긴 데이터는 건수, 합계, 구간 체크섬, 행 비교, 샘플 확인 순서로 좁혀 가며 검증한다. 연 뒤에는 업무 지표까지 보이는 관측 장치와, 끝나는 날이 정해진 하이퍼케어로 지킨다.

## 면접에서 나올 만한 질문

### 컷오버 계획에는 무엇이 들어가나요?

단계마다 계획 시각, 리허설로 잰 소요 시간, 담당자와 대기자, 끝났다는 확인 기준, 늦어도 끝나야 하는 마감 시각이 들어간다. 그리고 돌아올 수 없는 지점이 어디인지, 그 직전의 go/no-go 게이트와 되돌릴 기준을 숫자로 적는다. 되돌리는 절차와 걸리는 시간도 리허설해서 같이 적는다.

### 돌아올 수 없는 지점(PONR)은 무엇이고 왜 중요한가요?

새 시스템이 옛 시스템에 없는 데이터를 받기 시작하는 순간이다. 그 뒤에 되돌리면 새로 쌓인 데이터를 잃거나 거꾸로 옮겨야 해서, 보통은 고쳐서 앞으로 가는 길만 남는다. 그래서 그 직전에 게이트를 두고, 업무 재개 시각에서 되돌리기 시간을 뺀 시각 전에 통과하도록 계획한다.

### go/no-go를 게이트에서만 판단하면 왜 부족한가요?

앞 단계가 크게 밀리면 게이트에 도착했을 때 이미 되돌릴 시간이 없을 수 있다. 마지막 결정 시각에서 거꾸로 단계별 마감을 계산해 두면, 어느 단계에서든 마감을 넘는 순간 기다리지 않고 멈출 수 있다. 새벽에 "10분만 더"를 판단하지 않게 해 주는 장치이기도 하다.

### 데이터 이관이 맞게 됐는지 어떻게 확인하나요?

건수와 합계로 넓게 보고, 구간별 체크섬으로 어긋난 구간을 찾고, 그 구간의 행을 직접 비교해 공통점을 찾는다. 시간대 변환이나 코드의 뜻처럼 숫자로 안 잡히는 것은 샘플을 양쪽 화면에서 눈으로 비교한다. 이 검증은 운영과 같은 크기의 데이터로 하는 리허설에서 먼저 돌려 본다.

### 리허설은 왜 여러 번 하나요?

첫 번째에서는 절차의 빠진 곳과 업무 결정이 필요한 질문이 나오고, 두 번째부터는 시간이 맞는지 본다. 운영과 같은 크기의 데이터로 해야 인덱스 생성처럼 크기에 따라 달라지는 단계의 시간이 나온다. 실측이 계획과 크게 다르면 본 컷오버 전에 계획값과 마감을 고친다.

### 출시 직후 에러율이 0%인데 안심해도 되나요?

안 된다. 요청이 새 시스템에 아예 오지 않아도 에러율은 0%다. 시간당 주문 수 같은 업무 지표와 로드 밸런서의 요청 수를 함께 보고, 합성 점검으로 실제 흐름을 1분마다 흉내 내서 트래픽이 적은 시간에도 문제를 먼저 잡는다.

### 하이퍼케어는 무엇이고 언제 끝내나요?

출시 뒤 몇 주 동안 만든 팀이 직접 1차 대응을 하고, 정해진 시각마다 들어온 문제를 분류하고, 새 기능 배포를 멈추는 기간이다. 끝내는 기준은 미리 정한다. 심각한 문제가 일정 기간 새로 나오지 않음, SLO를 연속으로 지킴, 첫 월말 같은 업무 주기를 넘김, 운영팀이 넘겨받아 한 번 대응해 봄 같은 조건이다.
