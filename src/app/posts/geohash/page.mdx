배달 앱의 "내 주변 가게"를 만든다고 해 보자. 가게는 100만 곳이고, 각자 위도와 경도를 갖고 있다. 처음 떠오르는 쿼리는 이렇다.

```sql
-- 서울시청 주변 약 1km × 1km 사각형 안의 가게
SELECT id FROM places
WHERE lat BETWEEN 37.5620 AND 37.5710
  AND lon BETWEEN 126.9723 AND 126.9837;
```

`(lat, lon)`에 B-tree 인덱스를 걸면 빨라질 것 같지만, B-tree는 한 줄로 정렬된 값만 잘 찾는다. 위도 범위를 먼저 좁히고 나면 그 안에서 경도는 뒤죽박죽이다. 실제로 이 데이터에서 위도 조건만 맞는 행이 56,199개였고, 그중 경도까지 맞는 건 7,843개였다. 서울 안에서는 이 정도로 끝나지만, 전 세계 가게를 담으면 "위도 37.56~37.57"인 띠는 서울부터 리스본까지 지구를 한 바퀴 돈다.

지오해시(Geohash)는 이 문제를 2차원 좌표를 1차원 문자열로 바꿔서 푼다. 서울시청은 `wydm9qy89`가 되고, 근처 가게는 대부분 `wydm9q`로 시작한다. 그러면 "근처"를 "접두사가 같은 것"으로 바꿔 물을 수 있고, B-tree든 Redis의 정렬 집합이든 DynamoDB의 정렬 키든 한 줄짜리 인덱스면 무엇이든 쓸 수 있다.

이 글에서는 비트를 끼워 넣어 문자열을 만드는 과정, 글자 수와 칸 크기, 접두사가 가깝다는 말이 언제 거짓이 되는지, 그래서 왜 이웃 8칸을 같이 찾아야 하는지를 본다. 그다음 Redis `GEOSEARCH`가 속에서 하는 일과 PostgreSQL B-tree로 같은 일을 하는 법을 실제로 돌려 보고, 마지막에 S2와 H3를 짧게 비교한다. Redis는 Ubuntu 24.04의 Redis 7.0.15, PostgreSQL은 16.15, 계산은 Node.js 22로 했다.

이 주제의 다른 글: 데이터가 몰린 곳만 잘게 나누는 [쿼드트리](/posts/quadtree), 점이 영역 안에 있는지 판정하는 [레이 캐스팅](/posts/ray-casting).

## 지도를 반씩 접어 가며 비트를 적는다

지오해시는 이진 탐색을 두 축에 번갈아 하는 것이다. 경도 범위 -180~180을 반으로 나눠 내 점이 오른쪽(동쪽)이면 1, 왼쪽이면 0을 적는다. 다음에는 위도 -90~90을 반으로 나눠 위쪽(북쪽)이면 1, 아래면 0을 적는다. 남은 반쪽 칸에서 이걸 계속 되풀이한다. 비트가 하나 늘 때마다 칸이 절반으로 줄어든다.

여기서 "경도 비트와 위도 비트를 번갈아 적는다"가 중요하다. 이렇게 비트를 엇갈려 끼워 넣는 것을 인터리빙(interleaving)이라고 한다. 경도 비트를 다 적고 위도 비트를 뒤에 붙이면 앞자리는 경도만 말해 주니, 접두사가 같아도 위도는 어디든 될 수 있다. 번갈아 적었기 때문에 앞의 몇 비트만 보면 두 축 모두 대략적인 위치를 안다.

## 다섯 비트를 글자 하나로

비트 다섯 개는 0~31 사이 숫자이고, 이걸 32개짜리 문자표의 글자로 바꾼다. 지오해시가 쓰는 표는 `0123456789bcdefghjkmnpqrstuvwxyz`다. 숫자 10개와 소문자 22개인데, 손으로 옮겨 적을 때 헷갈리는 `a`, `i`, `l`, `o`를 뺐다. 그래서 RFC 4648의 Base32와는 글자 배열이 다르다. 라이브러리를 직접 짤 때 표준 Base32 표를 가져다 쓰면 엉뚱한 문자열이 나온다.

세로(위도 방향) 크기는 어디서나 같지만, 가로(경도 방향)는 위도가 올라갈수록 줄어든다. 경도 1도의 실제 거리가 적도에서 111km, 서울에서 88km, 위도 60도인 오슬로 근처에서는 56km이기 때문이다. 같은 6글자 칸도 적도에서는 1.2km 폭이고 서울에서는 0.97km다. "6글자면 1km 정도"라는 감은 맞지만, 정확한 반경 검색 설계는 칸 크기를 위도에 맞춰 계산해야 한다.

글자 하나가 늘 때마다 칸 넓이는 32분의 1이 된다. 길이를 고르는 기준은 "찾고 싶은 반경과 칸 크기가 비슷한 길이"다. 이유는 아래 이웃 칸 이야기에서 나온다.

function geohashEncode(lat, lon, precision) {
  let latMin = -90, latMax = 90;
  let lonMin = -180, lonMax = 180;
  let hash = "", bits = 0, count = 0, isLon = true;
  while (hash.length < precision) {
    if (isLon) {
      const mid = (lonMin + lonMax) / 2;
      if (lon >= mid) { bits = bits * 2 + 1; lonMin = mid; } else { bits = bits * 2; lonMax = mid; }

    if (++count === 5) { hash += BASE32[bits]; bits = 0; count = 0; }
  }
  return hash;
}`}

## 앞자리가 같으면 가깝다, 대체로

비트를 앞에서부터 하나씩 정하며 칸을 좁혔으니, 앞자리가 같은 두 지오해시는 같은 큰 칸 안에 있다. `wydm9q`로 시작하는 점은 모두 그 0.61km × 0.97km 칸 안에 있다. 이게 지오해시를 쓰는 이유다. 문자열을 정렬하면 같은 칸의 점들이 이웃한 줄에 모이고, "이 칸 안의 점"은 정렬된 목록에서 연속된 한 구간이 된다.

이 N자 모양이 반복되는 경로를 Z-순서 곡선(Z-order curve, 모턴 순서)이라고 한다. 칸 네 개를 N자로 훑고, 그 덩어리 네 개를 다시 같은 N자로 훑는다. 대부분 이어지는 번호가 붙어 있지만, 큰 덩어리의 경계에서는 바로 옆 칸이 번호로는 멀리 떨어진다. 위의 0011과 1001이 그런 경우다.

이 성질은 한쪽 방향으로만 성립한다. "접두사가 같으면 가깝다"는 대체로 맞지만, "가까우면 접두사가 같다"는 틀릴 수 있다.

## 10m 옆인데 접두사가 다르다

실제 좌표로 확인해 봤다. 거리는 하버사인 공식으로 계산했다.


첫 줄의 두 점은 22m 떨어져 있는데 `wyd`까지만 같다. 위도 37.6171875가 4글자 칸의 경계라서, 그 선의 남쪽과 북쪽은 세 번째 글자 다음부터 갈라진다. 셋째 줄은 더 극단적이다. 그리니치 천문대 앞마당에서 경도 0을 사이에 둔 두 점은 첫 글자부터 다르다. 경도 0은 맨 처음 자른 선이기 때문이다. 적도도 마찬가지다.

마지막 두 줄은 반대 방향의 함정이다. 서울시청과 경복궁은 1.46km인데 4글자가 같고, 아래 두 점은 6.2km나 떨어져 있는데 똑같이 4글자가 같다. 같은 4글자 칸(약 19.5km × 31km)의 양쪽 모서리에 있으면 그렇다. 공통 접두사 길이로 거리를 짐작하면 안 되는 이유다.

그래서 접두사 검색 하나로 "반경 500m 안"을 찾으면 두 종류의 실수가 생긴다. 경계 너머의 가까운 점을 놓치고, 칸 구석의 먼 점을 포함한다. 앞의 것은 이웃 칸을 같이 찾아서, 뒤의 것은 실제 거리로 다시 걸러서 해결한다.

## Redis GEOSEARCH 속에서 일어나는 일

Redis에는 위치 전용 명령이 있는데, 별도 자료구조가 아니라 정렬 집합(sorted set)이다. 점마다 52비트 지오해시를 정수로 만들어 점수(score)로 넣는다. 확인해 보자. Redis는 apt로 설치하고 다른 프로세스와 겹치지 않게 로컬 전용 포트로 띄웠다.

```bash
# Ubuntu 24.04 기본 저장소의 Redis 7.0 설치
sudo apt-get install -y redis-server
# 디스크 저장 없이, 127.0.0.1의 6391 포트로 실습용 인스턴스를 띄운다
redis-server --port 6391 --bind 127.0.0.1 --save '' --appendonly no --daemonize yes
# 경도, 위도 순서로 네 곳을 넣는다 (위도가 먼저가 아니다)
redis-cli -p 6391 GEOADD places 126.9780 37.5665 cityhall 126.9769 37.5796 gyeongbok 126.9882 37.5512 namsan 127.0276 37.4979 gangnam
# 키의 자료형과 실제로 저장된 점수를 본다
redis-cli -p 6391 TYPE places
redis-cli -p 6391 ZRANGE places 0 -1 WITHSCORES
```

`TYPE`이 `zset`이다. 점수 `4077564854911468`을 2진수로 바꾸면 정확히 52비트 `1110011111001000…`이다. 경도 26비트와 위도 26비트를 번갈아 끼운 값이고, 정렬 집합은 이 점수로 정렬되어 있으니 "이 칸 안"은 점수 범위 하나다. 그래서 `ZRANGEBYSCORE`로도 같은 키를 읽을 수 있다.

조금 다른 점이 있다. Redis는 위도를 -90~90이 아니라 -85.05112878~85.05112878 범위로 자른다. 웹 지도(EPSG:3857)가 그리는 범위다. 그래서 점수의 비트는 표준 지오해시와 열 번째 비트부터 달라지고, 극지방 좌표는 넣을 수 없다.

```bash
# 위도 86은 Redis가 다루는 범위 밖이다
redis-cli -p 6391 GEOADD places 0 86 north
# 사람이 읽는 지오해시 문자열을 달라고 하면 표준 범위로 다시 계산해서 11글자로 준다
redis-cli -p 6391 GEOHASH places cityhall gyeongbok
# 저장된 좌표를 다시 읽는다
redis-cli -p 6391 GEOPOS places cityhall
```

`GEOHASH`의 앞 9글자 `wydm9qy89`는 위에서 직접 계산한 값과 같다. 11번째 글자가 항상 `0`인 이유는 Redis 소스에 주석으로 적혀 있다. 52비트밖에 없는데 예전 API가 11글자를 내보냈기 때문에 마지막 글자는 0으로 채운다. `GEOPOS`가 돌려준 좌표는 넣은 값과 소수점 여섯째 자리부터 다르다. 26비트로 양자화하면서 생긴 오차로, 서울에서 0.2m 정도다. 그래서 바로 그 점에서 검색해도 거리가 0이 아니라 `0.0002`km로 나온다.

중요한 차이가 하나 있다. Redis는 글자(5비트) 단위가 아니라 축마다 1비트, 즉 넓이 4배 단위로 칸 크기를 고른다. 앞에서 본 "5글자는 너무 크고 6글자는 너무 작다" 문제를 거의 겪지 않는다. 내부적으로는 문자열이 아니라 정수를 쓰니 가능한 일이다.

## 후보가 많으면 Redis 전체가 멈춘다

`GEOSEARCH`의 비용이 후보 수에 비례한다는 말이 실제로 어떤 뜻인지 재 봤다. 서울 일대에 가게 100만 곳(70%는 번화가 여덟 곳 주변에 몰리게, 30%는 고르게)을 넣고 같은 명령을 200번씩 돌려 `INFO commandstats`의 호출당 평균 시간을 봤다.

```bash
# 100만 곳을 파이프라인으로 넣는다 (파일 한 줄 = GEOADD 명령 하나)
awk -F'\t' '{printf "GEOADD shops %s %s s%s\r\n",$3,$2,$1}' places.tsv | redis-cli -p 6391 --pipe
# 키 하나의 메모리 사용량(바이트)
redis-cli -p 6391 MEMORY USAGE shops
# 통계를 비우고 같은 명령을 200번 돌린 뒤 호출당 시간을 본다
redis-cli -p 6391 CONFIG RESETSTAT
for i in $(seq 200); do echo "GEOSEARCH shops FROMLONLAT 126.9780 37.5665 BYRADIUS 2 km COUNT 10 ASC"; done | redis-cli -p 6391 > /dev/null
redis-cli -p 6391 INFO commandstats | grep geosearch
```

세 번째 값 `123097`이 실행 시간(µs)이다. 이 한 번은 123ms가 걸렸다. 현장에서 "Redis 응답이 가끔 100ms씩 튄다"는 증상이 있으면 `SLOWLOG GET`에서 `GEOSEARCH`, `KEYS`, 큰 `ZRANGE` 같은 명령부터 찾는다. 위치 검색이 원인이라면 고치는 방법은 이렇다.

- 반경을 데이터 밀도에 맞게 줄인다. 번화가는 500m, 외곽은 5km처럼 단계적으로 넓혀 가며 찾는다.
- 정확한 순서가 필요 없으면 `ANY`를 쓴다. 위 표에서 2km가 84ms에서 9µs가 됐다.
- 한 키에 다 넣지 않는다. 도시나 지오해시 앞 몇 글자로 키를 나누면 키 하나의 크기와 Redis Cluster에서의 핫 슬롯이 함께 줄어든다.

## PostgreSQL에서 접두사로 찾기

PostGIS가 없는 PostgreSQL에서도 지오해시 열 하나와 B-tree로 같은 일을 할 수 있다. 위에서 Redis에 넣은 100만 곳을 PostgreSQL 16에도 넣었다. 지오해시 9글자는 Node.js로 미리 계산해 넣었다.

```sql
-- 가게 테이블: 위도, 경도, 9글자 지오해시. \copy로 100만 행을 넣었다
CREATE TABLE places (id bigint PRIMARY KEY, lat double precision NOT NULL, lon double precision NOT NULL, geohash text NOT NULL);
-- 행 예: (1, 37.509324, 127.074876, 'wydm7sm5e')
```

먼저 처음 본 사각형 쿼리를 `(lat, lon)` 인덱스로 돌린 결과다.

```sql
CREATE INDEX places_lat_lon ON places (lat, lon);
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT id FROM places
WHERE lat BETWEEN 37.5620 AND 37.5710 AND lon BETWEEN 126.9723 AND 126.9837;
```

```text

   Buffers: shared hit=5270
```

`Index Cond`에 경도 조건까지 들어 있어서 잘 쓰는 것처럼 보이지만, 인덱스는 위도 범위에 들어오는 56,199개 항목을 모두 읽고(`Buffers: shared hit=218`) 그 안에서 경도를 하나씩 검사했다. 두 번째 열은 범위를 좁히지 못하고 거르기만 한다. 서울 데이터라서 이 정도지만, 데이터가 지구 전체에 퍼져 있으면 위도 띠 하나에 걸리는 행이 훨씬 많아진다.

이제 지오해시 접두사다. `LIKE 'wydm9q%'`가 인덱스를 쓰려면 `text_pattern_ops`(또는 `COLLATE "C"`)로 만들어야 한다. 기본 정렬 규칙(collation)이 `C`가 아닌 DB에서는 일반 B-tree 인덱스로 `LIKE` 접두사 검색을 하지 못한다.

```sql
CREATE INDEX places_geohash ON places (geohash text_pattern_ops);
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT id FROM places WHERE geohash LIKE 'wydm9q%';
```

```text
 Index Scan using places_geohash on places (actual time=0.032..5.393 rows=4529 loops=1)
   Index Cond: ((geohash ~>=~ 'wydm9q'::text) AND (geohash ~<~ 'wydm9r'::text))
   Filter: (geohash ~~ 'wydm9q%'::text)
   Buffers: shared hit=4549
 Execution Time: 5.565 ms
```

`Index Cond`를 보면 PostgreSQL이 접두사를 `'wydm9q' 이상 'wydm9r' 미만`이라는 범위로 바꿨다. 지오해시 칸 하나가 B-tree의 연속 구간 하나라는 말이 그대로 보인다.

문제는 9칸이다. `geohash LIKE ANY (ARRAY['wydm9p%', 'wydm9q%', …])`로 접두사 아홉 개를 한꺼번에 주면 PostgreSQL 16은 이걸 인덱스 범위로 바꾸지 못하고 `Parallel Seq Scan`으로 간다(이 데이터에서 178ms). `OR`로 범위 조건 아홉 개를 직접 써도 되지만 쿼리가 길어진다. 더 깔끔한 방법은 접두사 길이를 정해 두고 그 길이로 자른 값에 표현식 인덱스를 거는 것이다. 그러면 `= ANY`로 9칸을 한 번에 찾는다.

```sql
-- 6글자 접두사에 대한 표현식 인덱스
CREATE INDEX places_gh6 ON places (left(geohash, 6));
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT id FROM places
WHERE left(geohash, 6) = ANY (ARRAY['wydm9p','wydm9r','wydm9x','wydm9n','wydm9q','wydm9w','wydm9j','wydm9m','wydm9t']);
```

```text

   Heap Blocks: exact=8184
   Buffers: shared hit=8239
   ->  Bitmap Index Scan on places_gh6 (actual time=2.092..2.093 rows=33582 loops=1)
         Index Cond: ("left"(geohash, 6) = ANY ('{wydm9p,wydm9r,wydm9x,wydm9n,wydm9q,wydm9w,wydm9j,wydm9m,wydm9t}'::text[]))
         Buffers: shared hit=53

```

인덱스는 53페이지만 읽었다. 그런데 테이블 쪽 `Heap Blocks: exact=8184`가 크다. 후보 33,582개가 8,184개 페이지에 흩어져 있다는 뜻이다. 행을 넣은 순서가 무작위라서, 지도에서 가까운 가게도 디스크에서는 멀리 있다.

여기서 지오해시의 다른 쓸모가 나온다. 테이블을 지오해시 순서로 다시 쓰면 지도에서 가까운 행이 같은 페이지에 모인다.

```sql
-- 테이블을 지오해시 인덱스 순서로 다시 쓴다 (ACCESS EXCLUSIVE 잠금, 운영 중에는 주의)
CLUSTER places USING places_geohash;
ANALYZE places;
```

<Callout kind="warning">
`CLUSTER`는 테이블을 통째로 새로 쓰는 동안 `ACCESS EXCLUSIVE` 잠금을 잡아 읽기까지 막고, 테이블과 인덱스 크기만큼 디스크를 더 쓴다. 운영 중인 큰 테이블이라면 `pg_repack`처럼 잠금을 짧게 잡는 도구를 쓰거나 점검 시간에 돌린다. 데이터 자체는 바뀌지 않으니 되돌릴 것은 없고, 중간에 취소하면 새로 쓰던 파일만 버려진다.
</Callout>

같은 두 쿼리를 다시 돌렸다. 바뀐 줄만 옮겼다.

```text
-- (lat, lon) 사각형

   Heap Blocks: exact=98
   Buffers: shared hit=316

-- 지오해시 9칸

   Buffers: shared hit=339

```

사각형 쿼리가 읽은 테이블 페이지가 5,052개에서 98개로 줄었다. 지오해시로 정렬했더니 `(lat, lon)` 인덱스를 쓰는 쿼리까지 빨라졌다. 지오해시는 검색 키로도 쓰지만 "비슷한 위치를 디스크에서 붙여 두는 정렬 순서"로도 쓸모가 있다. `CLUSTER`는 한 번 정렬할 뿐이고 이후 들어오는 행은 순서를 지키지 않으니, 주기적으로 다시 하거나 `pg_repack` 같은 온라인 도구를 쓴다.

마지막으로 9칸 후보를 실제 거리로 거르면 답이 나온다.

```sql
SELECT id, geohash, round(d) AS m
FROM (
  SELECT id, geohash,
         -- 하버사인 거리(미터)
         2 * 6371008.8 * asin(sqrt(
           sin(radians(lat - 37.5665) / 2) ^ 2
           + cos(radians(37.5665)) * cos(radians(lat)) * sin(radians(lon - 126.9780) / 2) ^ 2)) AS d
  FROM places
  WHERE left(geohash, 6) = ANY (ARRAY['wydm9p','wydm9r','wydm9x','wydm9n','wydm9q','wydm9w','wydm9j','wydm9m','wydm9t'])
) t
WHERE d <= 500
ORDER BY d
LIMIT 5;
```

```text
--------+-----------+----

  24186 | wydm9qy8v | 14

(5 rows)
```

후보 33,582곳 중 500m 안은 6,210곳이었다. Redis가 같은 데이터에서 6,208곳을 돌려준 것과 거의 같다. 2곳 차이는 Redis가 지구 반지름으로 6,372,797.56m를 써서 거리가 0.03% 길게 나오는 것과 좌표 양자화 오차 때문이다. 결과의 지오해시가 모두 `wydm9qy`로 시작하는 것도 눈여겨볼 만하다. 가장 가까운 것들은 실제로 접두사를 길게 공유한다.

PostgreSQL에서 위치 검색이 본업이라면 지오해시보다 GiST나 SP-GiST 인덱스(PostGIS가 있으면 `geography` 열과 `ST_DWithin`)를 쓰는 편이 낫다. 이 인덱스들은 이웃 칸 계산 없이 반경·사각형·최근접 검색을 바로 한다. 그 내부는 [쿼드트리 글](/posts/quadtree)에서 다룬다. 지오해시 열이 빛나는 곳은 한 줄짜리 키밖에 없는 저장소다. DynamoDB의 정렬 키, Cassandra의 클러스터링 키, Bigtable·HBase의 행 키, Redis 정렬 집합이 그렇다.

## 칸 모양이 다른 S2와 H3

지오해시의 약점은 세 가지로 요약된다. 칸이 위도에 따라 찌그러진다. Z-순서 곡선이 경계에서 크게 점프한다. 이웃 8칸 중 대각선 칸은 옆 칸보다 1.4배 멀어서 "이웃"의 거리가 고르지 않다. 이걸 다르게 푼 두 방식이 있다.

S2(구글)는 지구를 정육면체에 투영해 면 6개를 각각 쿼드트리로 나누고, 칸에 힐베르트 곡선 순서로 64비트 번호를 붙인다. 힐베르트 곡선은 Z-순서처럼 점프하지 않고, 번호가 이어지는 칸은 항상 붙어 있다. 레벨은 0~30이고, 서울시청이 속한 칸의 넓이를 `s2sphere` 라이브러리로 계산해 보면 레벨 12가 3.887km², 레벨 14가 0.2429km², 레벨 16이 0.0152km²다. 한 레벨에 넓이가 약 4분의 1이 된다. MongoDB의 `2dsphere` 인덱스가 S2 칸을 쓴다.

H3(우버)는 지구를 육각형으로 나눈다. 육각형은 이웃 6개가 모두 변을 맞대고 있어서 이웃까지의 거리가 거의 같다. 해상도는 0~15이고, Python `h3` 4.5.0으로 서울시청을 찍어 봤다.

```bash
# 가상 환경에 h3 라이브러리를 설치한다 (Ubuntu 24.04는 시스템 pip 설치를 막는다)
python3 -m venv venv && ./venv/bin/pip install h3
# 서울시청의 해상도 9 칸, 그 넓이, 이웃 6칸 중심까지의 거리
./venv/bin/python -c "
import h3
c = h3.latlng_to_cell(37.5665, 126.9780, 9)
print(c, round(h3.cell_area(c, 'km^2'), 4))
print([round(h3.great_circle_distance(h3.cell_to_latlng(c), h3.cell_to_latlng(n), 'm')) for n in h3.grid_disk(c, 1) if n != c])
"
```

```text
8930e1d8c0bffff 0.0725
[268, 315, 291, 268, 315, 291]
```

이웃 6칸의 중심까지 거리가 268~315m다. 정사각형 격자라면 옆 칸과 대각선 칸이 1 : 1.41로 벌어지는데, 육각형은 투영 왜곡으로 생기는 차이 정도만 남는다. 그래서 수요·공급을 칸 단위로 집계하고 주변 칸으로 번지게 하는 계산(배차, 요금 할증 지역)에 잘 맞는다. 대신 육각형 7개로 큰 육각형을 정확히 만들 수 없어서, 부모 칸이 자식 칸을 딱 맞게 덮지 않는다. 지오해시나 S2처럼 "접두사가 같으면 포함된다"는 성질이 깔끔하지 않다.

고르는 기준은 대략 이렇다. 키-값 저장소에 문자열 키 하나로 넣어야 하고 단순함이 중요하면 지오해시, 칸 크기가 고르고 영역을 칸 집합으로 정확히 덮어야 하면 S2, 이웃 관계와 칸 단위 집계가 중심이면 H3다. 셋 다 결국 "2차원을 정수 하나로 접는다"는 같은 아이디어 위에 있다.

## 현장에서 지오해시가 말썽을 부리는 순간

"근처 가게 목록에 길 건너 가게가 안 나온다"는 문의가 오면 먼저 쿼리가 접두사 하나만 보는지 확인한다. 두 가게의 지오해시를 나란히 찍어 보고 공통 접두사가 검색 길이보다 짧으면 경계 문제다. 이웃 8칸을 넣으면 해결된다.

"반경 1km로 바꿨더니 결과가 이상하게 줄었다"면 칸 크기가 반경보다 작은 상태로 9칸만 보는지 확인한다. 위 그림의 마지막 단계처럼 원이 9칸을 넘어선다. 반경이 바뀌면 길이도 다시 고르도록 코드에서 계산하게 만든다.

지오해시 앞자리를 샤드 키나 파티션 키로 쓰면 핫스팟이 생긴다. 강남역 근처 4글자 칸 하나에 시골 군 하나의 수백 배가 몰린다. 키에 앞 몇 글자만 쓰면 쓰기가 한 파티션에 쏠리니, 지오해시를 정렬 키로만 쓰고 파티션 키는 따로 고르거나 밀도에 따라 길이를 다르게 쓴다. 칸을 데이터 양에 맞춰 나누는 방식이 [쿼드트리](/posts/quadtree)다.

정확도도 착각하기 쉽다. 12글자 지오해시는 적도에서 3.7cm × 1.9cm 칸이지만, 휴대폰 GPS는 도심에서 수 미터에서 수십 미터까지 틀린다. 길이를 늘려도 저장 공간만 커진다. 반대로 지오해시를 위치 정보 노출 방지용으로 자를 때(예: 5글자만 공개)는 칸 크기 표를 보고 실제로 얼마나 숨겨지는지 확인한다. 5글자는 서울에서 4.9km × 3.9km이고, 그 칸의 경계에 사는 사람은 이웃 칸과 함께 보면 위치가 더 좁혀질 수 있다.

## 면접에서 나올 만한 질문

### 지오해시는 어떻게 만들어지나요?

경도와 위도 범위를 번갈아 반으로 나누며 점이 위쪽 반이면 1, 아래쪽이면 0을 적고, 그 비트들을 5개씩 묶어 32개 문자표의 글자로 바꾼다. 비트를 축마다 따로 적지 않고 번갈아 끼워 넣기 때문에 앞의 몇 글자만으로 두 축의 대략적 위치를 모두 안다. 글자 하나가 늘 때마다 칸 넓이는 32분의 1이 되고, 6글자면 서울에서 약 0.61km × 0.97km다.

### 왜 위도·경도 두 열에 B-tree를 거는 것보다 나은가요?

B-tree는 한 축으로 정렬되어 있어서 두 번째 열은 범위를 좁히지 못하고 거르기만 한다. 실험에서 `(lat, lon)` 인덱스는 위도 띠의 56,199개 항목을 읽어 7,843개를 찾았다. 지오해시는 2차원을 한 줄 순서로 접기 때문에 칸 하나가 인덱스의 연속 구간 하나가 되고, 한 줄짜리 키밖에 없는 Redis 정렬 집합이나 DynamoDB 정렬 키에서도 위치 검색을 할 수 있다. 다만 PostgreSQL처럼 GiST 같은 공간 인덱스가 있는 DB에서는 그쪽이 더 낫다.

### 접두사가 같은 것만 찾으면 왜 안 되나요?

가까운 점이 칸 경계 너머에 있으면 접두사가 짧게 겹치거나 아예 다르기 때문이다. 경도 0을 사이에 둔 208m 거리의 두 점은 첫 글자부터 달랐다. 그래서 가운데 칸과 둘레 8칸까지 9칸을 후보로 모으고, 실제 거리로 다시 걸러 칸 구석의 먼 점도 버린다. 실험에서 500m 안의 가게 중 53%가 가운데 칸 밖에 있었다.

### 반경에 맞는 지오해시 길이는 어떻게 고르나요?

칸의 짧은 변이 반경보다 크거나 같은 가장 긴 길이를 고른다. 그래야 9칸이 반경 원을 반드시 덮는다. 칸이 너무 크면 후보가 많아져 거리 계산 비용이 늘고, 너무 작으면 원이 9칸 밖으로 나간다. 문자열 지오해시는 글자 하나에 넓이가 32배씩 바뀌어 딱 맞는 길이가 없을 수 있어서, 작은 칸을 두 겹 이상 잡거나 Redis처럼 비트 단위로 크기를 고른다.

### Redis GEO는 내부적으로 어떻게 동작하나요?

별도 자료구조 없이 정렬 집합에 52비트 지오해시 정수를 점수로 넣는다. `GEOSEARCH`는 반경에 맞는 칸 크기를 비트 단위로 고르고, 가운데와 이웃 8칸을 점수 범위로 바꿔 후보를 꺼낸 뒤 거리를 계산해 거른다. 위도는 웹 지도 범위인 ±85.05도까지만 받는다. 비용이 후보 수에 비례해서, 밀집 지역에서 반경 2km를 `ASC`로 찾으면 한 번에 수십 ms가 걸려 단일 스레드인 Redis 전체가 그동안 멈춘다.

### GEOSEARCH에 COUNT 10을 붙였는데 왜 여전히 느린가요?

`ASC`와 함께 쓰면 가장 가까운 10개를 고르기 위해 9칸의 후보를 모두 거리 계산하고 정렬해야 하기 때문이다. 실험에서 2km 반경은 `COUNT 10 ASC`가 84ms, `COUNT 10 ANY`가 9µs였다. 정확한 순서가 필요 없으면 `ANY`를 쓰고, 필요하면 반경을 작게 시작해 결과가 모자랄 때만 넓힌다. `SLOWLOG GET`으로 실제로 느린 호출을 먼저 확인한다.

### 지오해시, S2, H3는 언제 무엇을 고르나요?

문자열 키 하나로 단순하게 저장해야 하면 지오해시가 가장 쉽다. 칸 크기가 고르고 영역을 칸 집합으로 정확히 덮어야 하면 힐베르트 곡선으로 번호를 매긴 S2가 낫다. 이웃까지의 거리가 고르고 칸 단위 집계·확산 계산이 중심이면 육각형인 H3를 고른다. H3는 부모 칸이 자식 칸을 정확히 덮지 않아서 접두사 포함 관계에 기대는 설계에는 맞지 않는다.

### 지오해시를 샤드 키로 쓰면 어떤 문제가 생기나요?

데이터가 사람 사는 곳에 몰려 있어서 번화가 칸 하나에 쓰기와 읽기가 집중되는 핫스팟이 생긴다. 고정 격자는 밀도와 상관없이 같은 크기로 나누기 때문이다. 지오해시는 정렬 키로만 쓰고 파티션 키는 다른 값으로 고르거나, 밀도에 따라 칸 크기를 다르게 나누는 쿼드트리 같은 방식을 쓴다.
