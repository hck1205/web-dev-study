이벤트가 시작되자 API 서버의 증상이 몇 가지 동시에 나왔다. 어떤 요청은 정확히 1초쯤 늦게 붙고, 뒤쪽 서버로 나가는 프록시는 CPU의 sys 비율만 치솟고, 한 대에서는 `Too many open files`가 찍혔다. 검색하면 "리눅스 네트워크 튜닝"이라는 제목으로 sysctl 스무 줄이 나온다. 그대로 붙여 넣으면 뭔가 나아질 것 같지만, 어느 줄이 지금 증상에 맞는지는 알 수 없다.

커널의 네트워크 한도는 몇 개 안 되고, 각각 넘쳤을 때 남기는 흔적이 다르다. 이 글은 그 한도들을 직접 넘겨 보는 실험이다. accept 큐, 임시 포트와 TIME_WAIT, 파일 디스크립터, conntrack 표를 차례로 넘치게 하고, 고치기 전과 후의 숫자를 나란히 놓는다. 큐와 상태가 왜 생기는지는 [TCP 연결의 일생](/posts/tcp-connection-lifecycle)과 [포트와 소켓](/posts/ports-and-sockets)에서 다뤘으니, 여기서는 "언제 닿고, 닿은 걸 어떻게 알고, 무엇을 얼마나 바꾸나"에 집중한다.

기준은 Ubuntu 24.04 LTS다. 실습 환경의 커널은 6.18이라 Ubuntu 24.04의 기본 커널(6.8)과 기본값이 다른 곳은 따로 적는다. 모든 실험은 내가 만든 네트워크 네임스페이스 안에서만 sysctl을 바꿨고, 호스트 값은 건드리지 않았다. 측정은 다른 작업이 함께 도는 공유 기계에서 했기 때문에 절대값보다 같은 조건에서의 전후 차이를 본다.

## 실험대: 네임스페이스 두 개와 작은 C 프로그램

서버와 클라이언트를 각자의 네트워크 네임스페이스에 두고 veth 한 쌍으로 이었다. 네임스페이스마다 네트워크 스택이 따로 있어서, 그 안에서 바꾼 네트워크 sysctl은 호스트에 영향을 주지 않는다. 네임스페이스 자체는 [네임스페이스와 cgroup 글](/posts/linux-namespaces-cgroups)에서 자세히 봤다.

```bash
# 서버용, 클라이언트용 네임스페이스와 그 사이의 가상 랜선
sudo ip netns add lx1-srv
sudo ip netns add lx1-cli
sudo ip link add lx1s0 netns lx1-srv type veth peer name lx1c0 netns lx1-cli
sudo ip -n lx1-srv addr add 10.78.0.1/24 dev lx1s0
sudo ip -n lx1-cli addr add 10.78.0.2/24 dev lx1c0
sudo ip -n lx1-srv link set lx1s0 up; sudo ip -n lx1-srv link set lo up
sudo ip -n lx1-cli link set lx1c0 up; sudo ip -n lx1-cli link set lo up

# 네임스페이스 안에서 본 기본값
sudo ip netns exec lx1-srv sysctl net.core.somaxconn net.ipv4.ip_local_port_range \
  net.ipv4.tcp_tw_reuse net.ipv4.tcp_max_syn_backlog net.netfilter.nf_conntrack_max
```

```text
net.core.somaxconn = 4096
net.ipv4.ip_local_port_range = 32768	60999
net.ipv4.tcp_tw_reuse = 2
net.ipv4.tcp_max_syn_backlog = 1024
net.netfilter.nf_conntrack_max = 262144
```

부하는 C로 짠 작은 프로그램 세 개로 만들었다. `srv`는 epoll로 연결을 받아 한 바이트를 읽으면 `ok`를 돌려주고, 상대가 끊으면 닫는다. 인자로 `accept()` 사이에 쉴 시간을 줄 수 있어서 일부러 느린 서버를 만들 수 있다. `cli`는 연결을 열고, 한 번 주고받고, 먼저 닫는 일을 정해진 시간 동안 반복하며 초당 횟수를 센다. `burst`는 연결 N개를 한꺼번에 열고 각각이 맺어지기까지 걸린 시간을 잰다.

네임스페이스 안이라고 모든 값을 바꿀 수 있는 건 아니다. 어떤 값은 네임스페이스마다 따로 있고, 어떤 값은 커널 전체에 하나뿐이다.

```bash
sudo ip netns exec lx1-srv ls -l /proc/sys/net/core/somaxconn /proc/sys/net/netfilter/nf_conntrack_max
sudo ip netns exec lx1-srv sysctl -w net.netfilter.nf_conntrack_max=262144
sudo ip netns exec lx1-srv sysctl net.core.netdev_max_backlog
```

```text
-rw-r--r-- 1 root root 0 Oct 22 00:50 /proc/sys/net/core/somaxconn
-r--r--r-- 1 root root 0 Oct 22 00:50 /proc/sys/net/netfilter/nf_conntrack_max
sysctl: setting key "net.netfilter.nf_conntrack_max": Operation not permitted
sysctl: cannot stat /proc/sys/net/core/netdev_max_backlog: No such file or directory
```

`somaxconn`은 네임스페이스마다 쓸 수 있고, `nf_conntrack_max`는 읽기만 되고, `netdev_max_backlog`는 아예 보이지 않는다. 쓰기를 시도할 때는 혹시 몰라 지금 값과 같은 값을 넣었다. 이 차이는 컨테이너에서 그대로 문제가 된다. Pod에도 네트워크 네임스페이스가 따로 있으니, 노드에서 `somaxconn`을 올려도 Pod 안은 기본값 그대로다. 쿠버네티스에서는 Pod의 `securityContext.sysctls`로 넣어야 하고, `net.ipv4.ip_local_port_range` 같은 일부만 "안전한 sysctl"로 기본 허용되며 `net.core.somaxconn`은 kubelet에서 따로 허락해야 한다. 반대로 `nf_conntrack_max`처럼 전체에 하나인 값은 노드에서만 바꿀 수 있다.

## 연결이 1초씩 늦게 붙는다

첫 증상부터 재현했다. 서버는 `listen(4096)`을 부르지만 실제 accept 큐 길이는 `somaxconn`과 비교해 작은 값이 된다. 커널 5.4 이전의 기본값 128을 흉내 내려고 서버 네임스페이스의 `somaxconn`을 128로 낮추고, 연결 하나를 받을 때마다 1ms씩 쉬는(초당 1000개를 받는) 서버를 띄운 뒤 연결 2000개를 한꺼번에 열었다.

```bash
# 서버 쪽 accept 큐 한도를 128로 (네임스페이스 안에서만)
sudo ip netns exec lx1-srv sysctl -w net.core.somaxconn=128
sudo ip netns exec lx1-srv ./srv 8080 4096 1000 &
sudo ip netns exec lx1-srv ss -tln

# 큐가 넘친 횟수를 전후로 보고, 그 사이에 2000개를 한꺼번에 연다
sudo ip netns exec lx1-srv nstat -saz TcpExtListenOverflows
sudo ip netns exec lx1-cli ./burst 10.78.0.1 8080 2000
sudo ip netns exec lx1-srv nstat -saz TcpExtListenOverflows
```

```text
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
LISTEN 0      128          0.0.0.0:8080      0.0.0.0:*    users:(("srv",pid=22997,fd=3))
TcpExtListenOverflows           178                0.0
connected=2000 failed=0 pending=0  p50=1047ms p99=1554ms max=1554ms  >=1s:1854
TcpExtListenOverflows           4924               0.0
```

LISTEN 줄의 `Send-Q 128`이 실제 큐 길이다. 앱은 4096을 달라고 했지만 커널이 128로 깎았다. 2000개 중 1854개가 1초 넘게 걸렸고, 중간값이 1047ms다. 큐가 찬 동안 들어온 SYN을 커널이 버렸고, 클라이언트는 1초 뒤에 SYN을 다시 보내서야 들어왔다. 그 사이 overflow 카운터가 4746 올랐다. 버린 SYN과, 큐가 차서 받아 주지 못한 마지막 ACK를 함께 센 숫자다.

`somaxconn`만 4096으로 올리고 서버를 다시 띄워 같은 부하를 줬다.

```text
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
LISTEN 0      4096         0.0.0.0:8080      0.0.0.0:*
TcpExtListenOverflows           9913               0.0
connected=2000 failed=0 pending=0  p50=26ms p99=27ms max=27ms  >=1s:0
TcpExtListenOverflows           9913               0.0
```

카운터는 그대로고, 2000개 모두 27ms 안에 붙었다. 서버가 받는 속도는 똑같이 초당 1000개인데도 그렇다. 큐가 길면 기다리는 연결이 줄 서 있을 자리가 있어서, 커널이 SYN을 버리지 않고 핸드셰이크를 끝내 둔다. 아래 그림에서 단계를 넘기면 짧은 큐에서 SYN이 버려지고 1초 뒤 다시 오는 순서를 볼 수 있다.

현장에서 "가끔 정확히 1초, 3초씩 늦다"는 말이 나오면 서버에서 overflow 카운터가 오르는지부터 본다. 올리는 값은 둘이다. 커널의 `somaxconn`과 앱이 `listen()`에 넘기는 backlog. 둘 중 작은 값이 쓰이니 한쪽만 올리면 소용없다. nginx는 `listen 443 backlog=4096;`, Node.js는 `server.listen(port, host, backlog)`, 많은 런타임이 511이나 128을 기본으로 쓴다. Ubuntu 24.04의 커널은 `somaxconn` 기본값이 이미 4096이라, 지금은 앱 쪽 backlog가 더 자주 범인이다.

다만 큐를 늘리는 건 기다릴 자리를 늘리는 것이지 처리 속도를 늘리는 게 아니다. 앱이 꾸준히 받는 속도보다 들어오는 속도가 빠르면 큐가 아무리 길어도 결국 차고, 그 전까지 연결들은 큐에서 기다린 시간만큼 늦어진다. 순간적인 몰림은 큐로 받고, 꾸준한 초과는 서버를 늘리거나 앞단에서 [요청 수를 제한](/posts/rate-limiting-in-practice)한다. 넘칠 때 SYN을 버리지 않고 RST로 바로 거절하는 `tcp_abort_on_overflow=1`도 있지만, 잠깐의 몰림까지 실패로 만들어서 거의 쓰지 않는다.

## 포트가 반쯤 차면 connect()가 느려진다

두 번째 증상은 나가는 쪽이다. 프록시가 같은 뒤쪽 서버로 짧은 연결을 계속 열고 먼저 끊으면, 끊은 쪽에 TIME_WAIT가 60초 남아 그 출발지 포트를 쥔다. [포트와 소켓 글](/posts/ports-and-sockets)에서는 이게 결국 `Cannot assign requested address`로 끝난다고 했다. 기본값 그대로 2초씩 끊어서 재 보니, 오류가 나기 한참 전에 다른 일이 먼저 일어났다.

```bash
# 클라이언트 네임스페이스: 기본 포트 범위(28232개), tcp_tw_reuse=2
for i in 1 2 3 4 5 6; do
  sudo ip netns exec lx1-cli ./cli 10.78.0.1 8080 2 | sed "s/^/t=$((i*2))s /"
done
```

```text
t=2s ok=15253 (7622/s) EADDRNOTAVAIL=0 other=0
t=4s ok=1881 (939/s) EADDRNOTAVAIL=0 other=0
t=6s ok=1752 (876/s) EADDRNOTAVAIL=0 other=0
t=8s ok=1915 (957/s) EADDRNOTAVAIL=0 other=0
t=10s ok=1685 (842/s) EADDRNOTAVAIL=0 other=0
t=12s ok=1769 (884/s) EADDRNOTAVAIL=0 other=0
```

오류는 하나도 없는데 처음 2초 뒤로 속도가 8분의 1로 떨어졌다. 어디서 시간이 가는지 `time`과 TIME_WAIT 포트의 홀짝을 봤다.

```bash
# 1.5초 돌린 직후 TIME_WAIT 포트를 짝수와 홀수로 센다
sudo ip netns exec lx1-cli ss -tanH state time-wait | \
  awk '{split($3,a,":"); if (a[2]%2) odd++; else even++} END {print "even="even, "odd="odd}'

# 그 상태에서 2초 더
sudo ip netns exec lx1-cli bash -c 'time ./cli 10.78.0.1 8080 2'
```

```text
ok=14924 (9947/s) EADDRNOTAVAIL=0 other=0
even=14116 odd=808
ok=2097 (1048/s) EADDRNOTAVAIL=0 other=0

real	0m2.003s
user	0m0.008s
sys	0m1.876s
```

짝수 포트 14116개가 모두 먼저 쓰였다. 리눅스 4.6(2016년)부터 `connect()`는 범위의 짝수 포트를 먼저 고르고, 홀수는 `bind()`가 쓰도록 남겨 둔다. 짝수가 다 차면 커널은 빈 포트를 찾아 범위를 훑기 시작하고, 쓰는 중인 포트가 늘수록 한 번 찾는 데 오래 걸린다. 2초 중 1.88초가 커널 안(sys)에서 쓰였다. 프록시의 CPU에서 sys만 치솟던 증상이 이것이다. 아래 그림이 그 순서다.

그래서 "포트 고갈"은 오류 로그보다 처리량 저하로 먼저 온다. 같은 목적지로 나가는 연결의 TIME_WAIT 수가 포트 범위의 절반을 넘으면 이미 위험하다고 본다. `ss -s`의 timewait 숫자와 범위를 비교하면 된다.

### tcp_tw_reuse가 허락하는 것

포트 범위를 1000개(40000~40999)로 줄여서 `tcp_tw_reuse` 값만 바꿔 3초씩 돌렸다. 매번 TIME_WAIT가 다 빠질 때까지 60초를 기다렸다.

```bash
sudo ip netns exec lx1-cli sysctl -w net.ipv4.ip_local_port_range="40000 40999"
echo "== tw_reuse=2"; sudo ip netns exec lx1-cli ./cli 10.78.0.1 8080 3
sleep 61    # TIME_WAIT가 모두 빠질 때까지
sudo ip netns exec lx1-cli sysctl -w net.ipv4.tcp_tw_reuse=1
echo "== tw_reuse=1"; sudo ip netns exec lx1-cli ./cli 10.78.0.1 8080 3
```

```text
net.ipv4.ip_local_port_range = 40000 40999
== tw_reuse=2
ok=1000 (333/s) EADDRNOTAVAIL=51025 other=0 first_EADDRNOTAVAIL_at=0.07s
net.ipv4.tcp_tw_reuse = 1
== tw_reuse=1
ok=3000 (1000/s) EADDRNOTAVAIL=29710 other=0 first_EADDRNOTAVAIL_at=0.07s
```

기본값 2에서는 포트 1000개를 0.07초 만에 다 쓰고 나머지 3초 동안 실패만 했다. 2는 "루프백 연결에서만 재사용"이라는 뜻이라, 네임스페이스 사이의 veth 연결은 0과 같게 취급됐다. 1로 바꾸니 3초에 정확히 3000개, 초당 1000개가 됐다. `tcp_tw_reuse`는 TIME_WAIT 포트를 아무 때나 다시 쓰게 하는 게 아니라, 그 연결의 마지막 TCP 타임스탬프가 1초 이상 지났을 때만 재사용한다. 늦게 도착한 옛 패킷은 타임스탬프가 더 작아서 새 연결이 걸러 낼 수 있기 때문이다. 이 환경의 6.18 커널에는 그 1초를 정하는 `net.ipv4.tcp_tw_reuse_delay`(기본 1000ms)가 있고, 오래된 커널은 1초로 고정이다. 포트 1000개를 1초마다 한 바퀴 돌리니 초당 1000개가 상한이 된 것이다. 이 옵션은 연결을 여는 쪽에만 효과가 있고, 양쪽 모두 TCP 타임스탬프(`tcp_timestamps=1`, 기본값)를 켜야 한다.

같은 조건에서 연결을 열지 않고 하나를 계속 썼을 때와도 비교했다.

```text
requests=324472 (108157/s) on 1 connection
```

연결 하나로 초당 10만 번 넘게 주고받았다. 연결을 맺고 끊는 비용이 빠지고 포트도 하나만 쓴다. 고치는 순서는 늘 같다. 먼저 [커넥션 풀과 keepalive](/posts/connection-pool)로 연결을 덜 만들고, 그다음 포트 범위를 넓히고 `tcp_tw_reuse=1`을 켠다. 범위와 reuse를 함께 바꾼 네임스페이스에서 기본값과 같은 12초 측정을 다시 했다.

```text
t=2s ok=32966 (16483/s) EADDRNOTAVAIL=0 other=0
t=4s ok=30750 (15375/s) EADDRNOTAVAIL=0 other=0
t=6s ok=31547 (15773/s) EADDRNOTAVAIL=0 other=0
t=8s ok=31290 (15645/s) EADDRNOTAVAIL=0 other=0
t=10s ok=31122 (15561/s) EADDRNOTAVAIL=0 other=0
t=12s ok=31464 (15732/s) EADDRNOTAVAIL=0 other=0
```

12초 내내 초당 1만 5천 개대를 유지했다. 첫 2초 숫자가 기본값 측정(7622/s)보다 높은 건 기본값 쪽이 그 2초 안에서 이미 짝수 포트를 다 쓰고 느려지기 시작했기 때문이다. 범위를 넓힐 때는 서버가 듣는 포트와 겹치지 않게 한다. 범위 안의 포트에서 듣는 서비스가 재시작하는 순간 그 포트를 나가는 연결이 먼저 잡아 `Address already in use`가 날 수 있다. 꼭 지켜야 할 포트는 `net.ipv4.ip_local_reserved_ports`에 적는다.

## Too many open files

연결 하나는 파일 디스크립터 하나다. 서버의 열린 파일 수 한도를 256으로 낮추고 연결 400개를 열어 둔 채 서버 쪽을 봤다.

```bash

sudo ip netns exec lx1-srv prlimit --nofile=256:256 ./srv 8080 4096 0 &
grep "open files" /proc/$(pgrep -x srv)/limits

# 연결 400개를 열고 4초 동안 쥐고 있는다
sudo ip netns exec lx1-cli ./burst 10.78.0.1 8080 400 4 &
sleep 2
sudo ls /proc/$(pgrep -x srv)/fd | wc -l
sudo ip netns exec lx1-srv ss -tln
```

```text
# /etc/systemd/system/api.service.d/limits.conf (drop-in)
[Service]
LimitNOFILE=65536
```

```bash
# 적용 후 실제 프로세스의 한도로 확인한다
```

```bash
cat /proc/sys/fs/nr_open
```

요즘 커널의 `fs.file-max`는 사실상 무한대라 전체 상한에 닿는 일은 드물다. 대부분은 프로세스 한도다. 그리고 한도를 올리기 전에 정말 연결이 많은 건지, 닫지 않아서 새는 건지(`ss`에서 CLOSE-WAIT가 계속 느는지)부터 본다. 새는 거라면 한도를 올려도 시간만 번다.

## conntrack 표는 연결보다 오래 남는다

방화벽 규칙에 `--ctstate`가 하나라도 있으면 커널은 모든 연결을 conntrack 표에 기록한다. 서버 네임스페이스에 그런 규칙 하나를 넣고 1초 동안 짧은 연결을 보냈다.

```bash
# 이 네임스페이스에 상태 기반 규칙 하나 (conntrack이 켜진다)
sudo ip netns exec lx1-srv iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

sudo ip netns exec lx1-cli ./cli 10.78.0.1 8080 1
sudo ip netns exec lx1-srv sysctl net.netfilter.nf_conntrack_count
sudo ip netns exec lx1-srv conntrack -L 2>/dev/null | awk '{print $4}' | sort | uniq -c
sudo ip netns exec lx1-srv conntrack -L 2>/dev/null | head -1
```


연결은 모두 끝났는데 표에는 14308줄이 남았다. conntrack도 TCP의 TIME_WAIT를 따라 하고, 그 수명(`nf_conntrack_tcp_timeout_time_wait`)이 120초라서 소켓의 TIME_WAIT(60초)보다 두 배 오래 남는다. 세 번째 칸 119가 남은 초다. 표에 동시에 있는 줄 수는 "초당 새 연결 수 × 한 줄이 남는 시간"이다. 초당 3000개면 TIME_WAIT만으로 36만 줄이고, 기본 최대치 262144를 넘는다. 그러면 [iptables 글](/posts/iptables-basics)에서 본 `nf_conntrack: table full, dropping packet`이 커널 로그에 찍히고 새 연결의 패킷이 버려진다.

이 수명은 네임스페이스마다 바꿀 수 있다. 30초로 줄이고 확인한 결과가 재밌었다.

```bash
sudo ip netns exec lx1-srv sysctl -w net.netfilter.nf_conntrack_tcp_timeout_time_wait=30
sleep 31; sudo ip netns exec lx1-srv sysctl net.netfilter.nf_conntrack_count
```

```text
net.netfilter.nf_conntrack_tcp_timeout_time_wait = 30
net.netfilter.nf_conntrack_count = 14308
```

31초 뒤에도 그대로다. 이미 들어간 줄은 들어갈 때 받은 타이머대로 흘러가서, 바꾼 값은 새 줄부터 적용된다. 옛 줄이 빠진 뒤 다시 1초 부하를 주고 31초 뒤에 보니 `conntrack -L`은 0줄을 보였는데, `nf_conntrack_count`는 14111을 가리키다 20초쯤 더 지나서 0이 됐다. 만료된 줄은 커널의 정리 작업이 돌 때 지워지고, 그때까지 카운터에 남는다. 장애 중에 수명을 줄였다면 효과가 나타나기까지 최소 옛 수명만큼은 기다려야 한다.

최대치는 앞에서 본 대로 네임스페이스에서 바꿀 수 없고 노드에서 바꾼다. 늘릴 때는 해시 버킷(`nf_conntrack_buckets`, 이 환경 읽기 전용)과 메모리를 함께 본다. 한 줄에 수백 바이트라 26만 줄이면 수십 MB 수준이다. 아예 추적할 필요가 없는 트래픽(내부 DNS, 상태가 필요 없는 UDP)은 raw 테이블의 `NOTRACK`으로 빼는 게 근본적이다. 쿠버네티스 노드에서는 kube-proxy가 시작할 때 CPU 수에 맞춰 이 값을 올리는데, [kube-proxy 모드 글](/posts/k8s-kube-proxy-modes)에 그 이야기가 있다.

## 바꾼 값은 파일로 남긴다

`sysctl -w`로 바꾼 값은 재부팅하면 사라진다. 영구로 남기려면 `/etc/sysctl.d/`에 파일을 두고, 이름 순서대로 읽히니 숫자를 앞에 붙인다. 짧은 연결이 많은 서버라면 이 정도에서 시작한다.

```text
# /etc/sysctl.d/90-net-tuning.conf
# 짧은 연결이 많은 API 서버용 (네트워크 네임스페이스 단위 값만)
net.core.somaxconn = 4096
net.ipv4.tcp_max_syn_backlog = 4096
net.ipv4.ip_local_port_range = 10240 65000
net.ipv4.tcp_tw_reuse = 1
net.netfilter.nf_conntrack_tcp_timeout_time_wait = 30
```

이 파일을 실습 네임스페이스에만 적용하고 호스트와 비교했다.

```bash
sudo ip netns exec lx1-cli sysctl -p ./90-net-tuning.conf
sysctl net.ipv4.ip_local_port_range net.ipv4.tcp_tw_reuse                          # 호스트
sudo ip netns exec lx1-cli sysctl net.ipv4.ip_local_port_range net.ipv4.tcp_tw_reuse  # 네임스페이스
```

```text
net.core.somaxconn = 4096
net.ipv4.tcp_max_syn_backlog = 4096
net.ipv4.ip_local_port_range = 10240 65000
net.ipv4.tcp_tw_reuse = 1
net.netfilter.nf_conntrack_tcp_timeout_time_wait = 30
net.ipv4.ip_local_port_range = 32768	60999
net.ipv4.tcp_tw_reuse = 2
net.ipv4.ip_local_port_range = 10240	65000
net.ipv4.tcp_tw_reuse = 1
```

호스트는 그대로고 네임스페이스만 바뀌었다. 실제 서버에서는 파일을 둔 뒤 `sudo sysctl --system`으로 `/etc/sysctl.d/`를 모두 다시 읽는다. `net.netfilter.*` 값은 conntrack 모듈이 올라온 뒤에야 존재해서, 부팅 때 sysctl이 모듈보다 먼저 돌면 `cannot stat`으로 건너뛰는 일이 있다. 재부팅 뒤 실제 값을 꼭 다시 확인한다.

<Callout kind="warning">
sysctl 튜닝 목록을 통째로 붙여 넣지 않는다. `tcp_tw_recycle`은 NAT 뒤 클라이언트의 연결을 끊는 문제로 4.12에서 지워져서 넣으면 오류가 나고, `tcp_fin_timeout`은 TIME_WAIT가 아니라 FIN-WAIT-2 시간이라 줄여도 포트가 돌아오지 않는다. 한 번에 하나씩 바꾸고, 바꾸기 전 값을 `sysctl 키`로 적어 두고, 지표가 실제로 바뀌는지 본다. 되돌릴 때는 파일을 지우고 적어 둔 값으로 `sysctl -w`를 한다. 재부팅하면 기본값으로 돌아간다는 것도 안전장치다.
</Callout>

## 한도를 하나씩 넘겨 보면

커널의 네트워크 한도는 넘칠 때 서로 다른 흔적을 남긴다. accept 큐는 overflow 카운터와 1초 지연, 임시 포트는 처리량 저하와 sys CPU, fd는 `EMFILE`과 큐에 멈춘 연결, conntrack은 `table full` 로그와 간헐적 손실이다. 각각 "동시에 쥐고 있는 수 = 들어오는 속도 × 머무는 시간"으로 크기를 어림할 수 있고, 고치는 순서는 연결을 덜 만드는 것이 먼저, 한도를 올리는 것이 나중이다. 바꾼 값은 네임스페이스마다 다를 수 있으니 컨테이너 안에서도 다시 확인한다. 큐와 상태가 생기는 원리는 [TCP 연결의 일생](/posts/tcp-connection-lifecycle)과 [포트와 소켓](/posts/ports-and-sockets)으로 돌아가서 다시 본다.

## 면접에서 나올 만한 질문

### somaxconn과 listen()의 backlog는 어떤 관계인가?

accept 큐의 실제 길이는 둘 중 작은 값이다. 앱이 `listen(4096)`을 불러도 `somaxconn`이 128이면 128이 되고, 반대로 커널 값만 올리고 앱이 511을 주면 511이다. 실습에서 128일 때 연결 2000개 중 1854개가 1초 넘게 걸렸고, 4096으로 올리자 모두 27ms 안에 붙었다. 확인은 `ss -lnt`의 LISTEN 줄 Send-Q로 한다.

### accept 큐가 넘치면 클라이언트는 무엇을 보나?

연결 거절이 아니라 지연을 본다. 리눅스는 기본적으로 큐가 찬 동안 온 SYN을 버리고, 클라이언트는 1초 뒤(그다음은 3초, 7초 쪽으로) SYN을 다시 보내서 들어온다. 그래서 "가끔 정확히 1초 늦다"는 증상이 되고, 서버의 `TcpExtListenOverflows`가 오른다. `tcp_abort_on_overflow=1`이면 RST로 거절하지만 잠깐의 몰림까지 실패로 만든다.

### 같은 목적지로 짧은 연결을 많이 열면 어떤 일이 먼저 생기나?

오류보다 처리량 저하가 먼저 온다. `connect()`는 짝수 포트를 먼저 쓰고, 짝수가 TIME_WAIT로 다 차면 빈 포트를 찾아 범위를 훑느라 커널 시간이 늘어난다. 실습에서 기본 범위로 초당 7600개를 내다가 2초 뒤 900개 수준으로 떨어졌고 sys 시간이 2초 중 1.88초였다. 끝내 다 차면 `EADDRNOTAVAIL`이 난다.

### tcp_tw_reuse는 무엇을 허락하고, 기본값 2는 무슨 뜻인가?

연결을 여는 쪽이 TIME_WAIT 포트를 다시 쓰게 하되, 마지막 타임스탬프가 1초 이상 지난 경우에만 허락한다. 타임스탬프로 옛 패킷을 걸러 낼 수 있어서 안전하다. 기본값 2는 루프백 연결에만 허락한다는 뜻이라, 다른 호스트나 다른 네임스페이스로 가는 연결에는 0과 같다. 실습에서 포트 1000개로 2일 때 3초에 1000개, 1일 때 3000개였다. 그래도 커넥션 풀이 먼저다.

### Too many open files가 나면 무엇을 확인하나?

먼저 실제 프로세스의 한도(`/proc/PID/limits`)와 지금 연 fd 수를 보고, fd가 연결 수만큼 정상적으로 많은 건지 CLOSE-WAIT로 새는 건지 구분한다. 한도에 닿으면 커널은 연결을 맺어 두지만 앱이 `accept()`를 못 해서, 클라이언트는 연결된 뒤 응답 없이 기다린다. systemd 서비스는 limits.conf가 아니라 유닛의 `LimitNOFILE=`로 올리고 재시작한 뒤 다시 `/proc`에서 확인한다.

### conntrack 표가 꽉 차는 건 어떤 서버이고, 어떻게 막나?

짧은 연결을 아주 많이 받는 서버와 NAT 게이트웨이다. 연결이 끝나도 TIME_WAIT 줄이 120초 남아서, 초당 새 연결 수 × 120이 최대치를 넘으면 `table full, dropping packet`이 난다. 대처는 최대치 올리기(메모리, 버킷 함께), TIME_WAIT 수명 줄이기, 추적이 필요 없는 트래픽을 raw 테이블에서 NOTRACK으로 빼기다. 수명을 바꾸면 새로 들어오는 줄부터 적용된다.

### 노드에서 sysctl을 올렸는데 컨테이너 안에서는 그대로인 이유는?

네트워크 sysctl 상당수가 네트워크 네임스페이스마다 따로 있기 때문이다. `somaxconn`, `ip_local_port_range`, `tcp_tw_reuse`는 Pod 안에서 기본값으로 시작하고, 쿠버네티스에서는 `securityContext.sysctls`로 넣는다(일부는 kubelet 허용이 필요하다). 반대로 `nf_conntrack_max`처럼 커널 전체에 하나인 값은 네임스페이스에서 읽기 전용이라 노드에서만 바꾼다.
