월말이 되면 "지난달 장르별 매출" 표를 뽑는다. 서점 주문 테이블에 500만 건이 있고, 쿼리는 간단하다. 기간으로 거르고, 장르로 묶고, 수량 × 가격을 더한다. PostgreSQL에서 돌리면 0.5초쯤 걸린다. 나쁘지 않아 보이지만, 같은 데이터를 DuckDB에 넣고 똑같은 SQL을 돌리면 40ms대가 나온다. 코어 하나만 쓰게 묶어 놓고도 열 배 넘게 빠르다.

SQL도 같고, 데이터도 같고, 기계도 같다. 다른 건 디스크에 데이터를 놓는 방향 하나다. 이 글은 [DB 종류 시리즈](/posts/db-types-overview)의 일곱 번째 글로, 행 대신 컬럼으로 저장하는 분석 DB가 왜 이렇게 빠른지, 그 대가로 무엇을 못 하는지, 그래서 운영 DB와 어떻게 나눠 쓰는지 정리한다.

## 주문을 받는 질문과 매출을 보는 질문

DB에 오는 질문은 크게 두 종류다.

주문 화면이 던지는 질문은 "42번 회원의 최근 주문 10건", "주문 9001번을 결제 완료로 바꿔라" 같은 것이다. 행 몇 개를 정확히 찾아 읽고 고친다. 초당 수천 번 오고, 각각 몇 ms 안에 끝나야 하고, 동시에 여러 요청이 같은 행을 고쳐도 꼬이면 안 된다. 이걸 OLTP(Online Transaction Processing, 트랜잭션 처리)라고 부른다.

월말 매출표가 던지는 질문은 다르다. "지난 1년 주문 전부를 장르와 월로 묶어 합계를 내라." 행 수백만 개를 훑지만 컬럼은 몇 개만 본다. 하루에 몇 번 오고, 몇 초 걸려도 괜찮다. 이걸 OLAP(Online Analytical Processing, 분석 처리)라고 부른다.

[관계형 DB 글](/posts/db-type-relational)에서 본 PostgreSQL과 MySQL은 OLTP에 맞춰 만든 DB다. 분석 질문도 처리할 수는 있지만, 저장 방식이 분석과 반대 방향을 향한다. 그 방향을 직접 보자.

## 실험에 쓸 주문 500만 건

서점 주문을 PostgreSQL 16에 500만 건 만든다. 분석에 쓰지 않는 배송지와 메모 컬럼도 있다. 실제 주문 테이블도 대개 이렇게 넓다.

```sql
SELECT setseed(0.17);  -- 같은 데이터를 다시 만들 수 있게 고정
CREATE TABLE orders (
  order_id    bigint      PRIMARY KEY,
  user_id     int         NOT NULL,
  book_id     int         NOT NULL,
  genre       text        NOT NULL,   -- 8가지
  status      text        NOT NULL,   -- paid, shipped, cancelled
  qty         int         NOT NULL,
  price       int         NOT NULL,
  ordered_at  timestamptz NOT NULL,   -- 2025-10-17부터 1년 사이
  ship_addr   text        NOT NULL,   -- 분석에는 안 쓰는 긴 문자열
  memo        text
);
INSERT INTO orders
SELECT i,
       1 + floor(random() * 200000)::int,
       1 + floor(random() * 50000)::int,
       (ARRAY['소설','IT','경제','과학','역사','만화','에세이','자기계발'])[1 + floor(random() * 8)::int],
       (ARRAY['paid','paid','paid','paid','shipped','shipped','cancelled'])[1 + floor(random() * 7)::int],
       1 + floor(random() * 3)::int,
       (8 + floor(random() * 30)::int) * 1000,
       timestamptz '2025-10-17' + random() * interval '365 days',
       '서울시 어딘가 ' || floor(random() * 100000)::int || '번길 ' || floor(random() * 100)::int || '-' || floor(random() * 30)::int,
       CASE WHEN random() < 0.3 THEN '문 앞에 놓아 주세요' END
FROM generate_series(1, 5000000) AS i;
```

그리고 월말 매출 쿼리다. 비교를 공정하게 하려고 병렬 처리를 끄고 코어 하나로 돌린다.

```sql
SET max_parallel_workers_per_gather = 0;

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT genre, sum(qty * price) AS revenue, count(*) AS orders
FROM orders
WHERE status <> 'cancelled'
  AND ordered_at >= '2026-09-01' AND ordered_at < '2026-10-01'
GROUP BY genre ORDER BY revenue DESC;
```

인덱스를 걸면 될 것 같지만, 이 쿼리는 1년 중 한 달, 전체의 7%를 읽는다. 인덱스로 35만 행을 하나씩 찾아가는 것보다 그냥 다 읽는 편이 빠를 때가 많고, "올해 전체"처럼 범위가 넓어지면 인덱스는 아예 쓸모가 없다. 분석 쿼리는 원래 많이 읽는 질문이다. 그러니 읽는 양 자체를 줄여야 한다.

## 행으로 저장하면 안 쓰는 컬럼도 읽는다

PostgreSQL과 MySQL(InnoDB)은 행 하나를 통째로 붙여서 저장한다. 페이지 안에 주문 1번의 모든 컬럼, 이어서 주문 2번의 모든 컬럼이 놓인다. 주문 하나를 읽고 고칠 때는 이게 최선이다. 한 번 읽으면 그 주문의 모든 값이 손에 들어온다.

## 같은 컬럼끼리 모이면 잘 눌린다

컬럼 저장의 두 번째 무기는 압축이다. genre 덩어리에는 8가지 값만 500만 번 반복된다. 이런 데이터는 거의 공짜로 줄일 수 있다.

- 사전 압축(dictionary): 서로 다른 값 8개를 표로 만들고, 본문에는 0~7 번호만 적는다. 3비트면 된다.
- 연속 길이 압축(RLE, run-length encoding): 같은 값이 이어지면 "값 × 개수"로 적는다. 정렬돼 있으면 엄청나게 줄어든다.
- 비트 패킹(bit packing): 수량 1~3은 32비트 정수가 아니라 2비트로 충분하다.
- 차이 압축(delta): 시각이나 증가하는 id는 앞 값과의 차이만 적는다.

같은 500만 건을 DuckDB 1.5에 넣고 어떤 압축이 골라졌는지 봤다. DuckDB는 데이터를 넣을 때 컬럼 조각마다 가장 잘 줄어드는 방식을 스스로 고른다.

```sql
-- DuckDB: 컬럼마다 고른 압축 방식
SELECT column_name, compression, count(*) AS segments
FROM pragma_storage_info('orders')
WHERE segment_type <> 'VALIDITY'
GROUP BY ALL ORDER BY column_name;
```

```text

├─────────────┼─────────────┼──────────┤
│ book_id     │ BitPacking  │       45 │
│ genre       │ Dictionary  │       45 │
│ memo        │ Dictionary  │       45 │
│ order_id    │ BitPacking  │       45 │
│ ordered_at  │ BitPacking  │      122 │
│ price       │ BitPacking  │       45 │
│ qty         │ BitPacking  │       45 │

│ user_id     │ BitPacking  │       75 │
└─────────────┴─────────────┴──────────┘

장르, 상태, 메모는 사전 압축, 숫자는 비트 패킹, 제각각인 주소 문자열은 FSST(자주 나오는 글자 조각을 짧은 기호로 바꾸는 문자열 압축)가 골라졌다. DB 파일 전체는 115MB, PostgreSQL 테이블은 639MB였다. 같은 데이터를 Parquet 파일로 내보내 컬럼별 크기를 보면 차이가 더 잘 보인다.

```

## 한 번에 값 하나가 아니라 묶음으로 계산한다

읽는 양만 줄어든 게 아니다. 계산 방식도 다르다. PostgreSQL 실행기는 기본적으로 행 하나를 꺼내 필터를 검사하고, 통과하면 집계에 넘기고, 다음 행을 꺼낸다. 행마다 함수 호출과 분기가 반복된다.

컬럼형 엔진은 컬럼 하나에서 값 수천 개를 배열로 꺼내 한꺼번에 처리한다(벡터화 실행, vectorized execution). DuckDB는 기본 2,048개씩 묶는다. "qty 배열 × price 배열"을 반복문 하나로 계산하면 CPU 캐시에 데이터가 연속으로 올라오고, 컴파일러가 SIMD 명령(값 여러 개를 한 명령으로 계산)으로 바꿀 수 있다. ClickHouse, DuckDB, Snowflake, BigQuery 엔진이 모두 이 방식이다.

```text
              PostgreSQL 16     DuckDB 1.5
코어 1개        약 480 ms         약 42 ms
코어 4개        214 ms (작업자 2)  13.5 ms
```

이 컨테이너(4코어)에서 같은 쿼리를 여러 번 돌려 가장 빠른 값을 적었다. 기계마다 숫자는 다르지만 차이의 크기는 비슷하게 나온다.

## 건너뛸 수 있는 덩어리는 아예 열지 않는다

세 번째 무기는 건너뛰기다. 컬럼 덩어리마다 최솟값과 최댓값을 적어 두면(zone map, min/max 통계), 조건과 겹치지 않는 덩어리는 열지 않는다. [시계열 DB 글](/posts/db-type-time-series)의 BRIN과 같은 생각이다. 그래서 데이터가 조건 컬럼 순서로 정렬돼 있을수록 효과가 크다.

DuckDB에서 주문을 `ordered_at` 순으로 정렬한 사본을 만들어 같은 쿼리를 돌려 봤다.

```sql
CREATE TABLE orders_sorted AS SELECT * FROM orders ORDER BY ordered_at;
```

```text
orders         (무작위 순서)  44.6 ms
orders_sorted  (시각 순서)     8.7 ms
```

무작위 순서에서는 모든 덩어리에 9월 주문이 조금씩 섞여 있어서 하나도 건너뛰지 못한다. 시각 순으로 정렬하면 9월이 들어 있는 덩어리 몇 개만 연다. 컬럼형 DB에서 테이블을 만들 때 정렬 키를 고르는 일이 행 저장 DB에서 인덱스를 고르는 일과 비슷한 무게를 갖는 이유다.

## 분석 DB가 잘 못 하는 것

여기까지 오면 분석 DB를 운영 DB로 쓰면 되지 않나 싶지만, 장점이 그대로 약점이 된다.

행 하나를 고치는 게 비싸다. 주문 9001번의 상태를 바꾸려면 status 컬럼 덩어리를 찾아 압축을 풀고, 고치고, 다시 압축해야 한다. 그래서 ClickHouse의 `ALTER TABLE ... UPDATE`는 파트를 통째로 다시 쓰는 무거운 백그라운드 작업(mutation)이고, 가벼운 DELETE도 지운 표시를 했다가 나중에 정리하는 방식이다. 초당 수천 건의 주문 상태 변경을 받을 구조가 아니다.

행 하나를 읽는 것도 느리다. 주문 상세 화면은 주문 하나의 모든 컬럼이 필요한데, 컬럼 저장에서는 컬럼 덩어리 10개를 각각 찾아가 조립해야 한다.

트랜잭션이 약하다. 엔진마다 다르지만, 여러 테이블을 묶는 ACID 트랜잭션이나 외래 키 같은 제약은 기대하지 않는 편이 맞다. DuckDB처럼 트랜잭션을 지원하는 엔진도 동시에 쓰는 사용자가 많은 환경을 위한 것은 아니다.

동시 요청이 많으면 버겁다. 분석 쿼리 하나가 코어를 다 쓰는 설계라, 초당 수천 개의 작은 쿼리가 몰리는 화면 API에는 맞지 않는다. ClickHouse는 이 중에서 비교적 많은 동시 쿼리를 견디는 편이지만, 그래도 운영 DB의 대체품은 아니다.

## 클라우드 데이터 웨어하우스와 DuckDB

분석 DB는 운영 방식에 따라 몇 갈래로 나뉜다.

BigQuery는 서버를 직접 띄우지 않는 구글 클라우드의 분석 DB다. 요금 방식 중 하나가 쿼리가 읽은 바이트 수만큼 내는 방식(on-demand)이라, 컬럼 저장의 성질이 바로 비용이 된다. `SELECT *`는 모든 컬럼을 읽으니 비싸고, `LIMIT 10`을 붙여도 읽는 바이트는 줄지 않는다(클러스터링되지 않은 테이블 기준). 날짜로 파티션하고 자주 거르는 컬럼으로 클러스터링하면 읽는 양이 준다.

```sql
-- BigQuery: 날짜 파티션 + 장르 클러스터링
CREATE TABLE shop.orders
PARTITION BY DATE(ordered_at)
CLUSTER BY genre
AS SELECT * FROM staging.orders;
```

Amazon Redshift는 여러 노드에 데이터를 나눠 병렬로 처리하는(MPP) 컬럼형 웨어하우스다. 어느 노드에 행을 둘지(DISTKEY), 어떤 순서로 저장할지(SORTKEY)를 테이블마다 고른다. 조인하는 두 테이블을 같은 키로 나눠 두면 노드끼리 데이터를 주고받지 않고 조인한다. Snowflake도 비슷한 자리에 있는데, 저장과 계산을 분리해서 계산 자원(웨어하우스)을 따로 늘리고 줄인다.

DuckDB는 서버가 없는 임베디드 분석 DB다. 파이썬이나 노드 프로세스 안에서 라이브러리로 돌고, Parquet이나 CSV 파일을 바로 읽는다. 노트북에서 수천만 행을 분석하거나, 배치 작업 안에서 집계할 때 쓴다. 앱 안에 들어가는 방식은 [임베디드 DB 글](/posts/db-type-embedded)의 SQLite와 같고, 저장 방향만 반대다.

## 운영 DB에서 분석 DB로 옮기는 길

그래서 실무에서는 둘을 나눈다. 주문은 PostgreSQL이 받고, 분석 DB는 복사본으로 집계한다. 옮기는 방법은 두 가지다.

하나는 배치다. 밤마다 어제 주문을 뽑아 Parquet 파일로 만들어 웨어하우스에 올린다(ETL, 또는 먼저 올리고 웨어하우스 안에서 변환하는 ELT). 단순하지만 매출표가 하루 늦다.

## 컬럼형을 고르기 전에

운영 DB에서 분석 쿼리가 몇 개뿐이고 몇 초면 끝난다면, 복제본 하나에서 돌리는 것으로 충분하다. 머티리얼라이즈드 뷰로 결과를 미리 만들어 둘 수도 있다. 새 저장소와 CDC 파이프라인을 운영하는 비용이 분석 쿼리의 불편보다 클 때가 많다.

이런 신호가 보이면 분석 DB를 검토한다. 분석 쿼리가 운영 DB의 CPU와 I/O를 눈에 띄게 먹는다, 복제본에서 긴 쿼리가 복제와 부딪혀 취소된다, 테이블이 수억 행이 넘고 대부분의 질문이 "기간 전체를 묶어서"다, 여러 서비스의 데이터를 한곳에 모아 조인해야 한다.

반대로 이런 데이터는 분석 DB에 두지 않는다. 행 단위로 자주 바뀌는 원본, 트랜잭션으로 정합성을 지켜야 하는 돈과 재고, 화면이 키로 한 건씩 찾아오는 데이터.

## 읽는 방향에 맞춰 놓는다

행 저장은 "주문 하나의 모든 것"을 빨리 읽고 고치도록, 컬럼 저장은 "모든 주문의 몇 가지"를 빨리 읽도록 데이터를 놓는다. 컬럼으로 놓으면 필요한 컬럼만 읽고, 같은 값끼리 모여 잘 눌리고, 묶음으로 계산하고, 덩어리째 건너뛸 수 있다. 그 대가로 한 행을 고치거나 한 행을 통째로 읽는 일이 비싸진다. 그래서 운영 DB와 분석 DB는 경쟁하지 않고, CDC나 배치로 이어진 두 저장소로 함께 쓴다. 다음 글은 운영 DB 쪽을 여러 대로 늘리는 [분산 SQL](/posts/db-type-newsql)이다.

## 면접에서 나올 만한 질문

### OLTP와 OLAP은 무엇이 다른가요?

OLTP는 행 몇 개를 정확히 찾아 읽고 고치는 짧은 트랜잭션이 많고, 지연 시간과 동시성, 정합성이 중요하다. OLAP은 행 수백만 개를 훑되 컬럼 몇 개만 보고 묶어서 집계하며, 처리량이 중요하고 조금 늦은 데이터여도 괜찮다. 그래서 OLTP는 행 저장, OLAP은 컬럼 저장이 맞고, 보통 저장소를 나눠 CDC나 배치로 잇는다.

### 컬럼 저장이 분석 쿼리에서 빠른 이유는 무엇인가요?

필요한 컬럼만 읽으니 I/O가 준다. 같은 컬럼 값이 모여 있어 사전, RLE, 비트 패킹 같은 압축이 잘 먹고 읽는 양이 더 준다. 값을 수천 개씩 묶어 처리하는 벡터화 실행으로 CPU 효율이 좋고, 덩어리마다 최솟값·최댓값을 적어 조건에 안 맞는 덩어리를 건너뛴다. 실험에서는 같은 쿼리가 PostgreSQL 코어 하나로 약 480ms, DuckDB로 약 42ms였다.

### 그럼 운영 DB도 컬럼형으로 쓰면 안 되나요?

행 하나를 고치려면 여러 컬럼 덩어리를 풀고 다시 압축해야 해서 갱신이 비싸다. 한 행을 통째로 읽을 때도 컬럼마다 따로 찾아가 조립해야 한다. 트랜잭션과 제약, 높은 동시 요청 처리도 행 저장 DB가 훨씬 잘한다. 그래서 주문을 받는 쪽은 관계형 DB에 두고 분석은 복사본으로 한다.

### 컬럼형 DB에서 정렬 키는 왜 중요한가요?

zone map이나 성긴 색인이 덩어리 단위로 건너뛰려면 같은 조건의 행이 몰려 있어야 하기 때문이다. 정렬하면 RLE 같은 압축도 더 잘 먹는다. 실험에서 시각 순으로 정렬한 테이블은 같은 기간 쿼리가 44.6ms에서 8.7ms가 됐다. ClickHouse의 ORDER BY는 자주 거르는 컬럼과 값 종류가 적은 컬럼을 앞에 둔다.

### ClickHouse에 데이터를 한 줄씩 넣으면 어떻게 되나요?

INSERT 하나가 파트 하나가 되므로 파트가 너무 많이 생기고, 백그라운드 병합이 따라가지 못해 'Too many parts' 에러로 쓰기가 거부될 수 있다. 수천 행 이상씩 모아서 넣거나 async_insert로 서버가 모아 넣게 한다. CDC 파이프라인에서도 Kafka 소비자가 일정 시간이나 개수만큼 묶어서 넣는다.

### 운영 DB의 데이터를 분석 DB로 옮길 때 CDC를 쓰면 무엇을 조심하나요?

PostgreSQL에서는 논리 복제 슬롯을 쓰는데, 소비자가 멈추면 슬롯이 읽지 않은 WAL이 지워지지 않고 쌓여 디스크를 채울 수 있다. 슬롯 지연을 모니터링하고 max_slot_wal_keep_size로 상한을 둔다. 같은 행의 여러 버전이 도착하니 분석 쪽에서 최신 버전만 남기는 방법(ReplacingMergeTree, MERGE)을 정해야 하고, 분석 데이터는 항상 몇 초 늦다는 걸 전제로 화면을 만든다.

### BigQuery에서 비용을 줄이려면 무엇을 하나요?

on-demand 요금은 읽은 바이트로 매겨지니 필요한 컬럼만 SELECT하고 `SELECT *`를 피한다. LIMIT은 읽는 양을 줄이지 않는다. 날짜로 파티션하고 자주 거르는 컬럼으로 클러스터링해서 조건에 맞는 부분만 읽게 하고, 자주 쓰는 집계는 미리 만들어 둔다.
