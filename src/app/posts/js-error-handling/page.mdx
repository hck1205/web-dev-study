<EasyIntro>
  프로그램이 일을 하다가 더는 할 수 없는 상황을 만나면, 하던 일을 멈추고 "문제가 생겼다"는 쪽지를 위로 던진다. 이걸 에러를 던진다고 한다.

  쪽지는 함수를 부른 쪽으로 한 칸씩 거슬러 올라간다. 중간에 쪽지를 받아 주겠다고 손을 든 곳이 있으면 거기서 멈추고, 아무도 없으면 프로그램 전체가 멈추거나 화면에 빨간 글씨가 뜬다.

  문제는 쪽지를 받아 놓고 아무것도 하지 않는 경우다. 쓰레기통에 버린 쪽지는 누구도 볼 수 없어서, 나중에 왜 고장 났는지 찾을 수가 없다. 그래서 받은 쪽지는 처리하거나, 처리할 수 없으면 다시 위로 던져야 한다.

  좋은 쪽지에는 무슨 일이 있었는지, 어디서 생겼는지, 원래 원인이 무엇이었는지가 적혀 있다. 자바스크립트에서는 Error라는 정해진 모양의 쪽지를 쓰고, 필요하면 우리만의 쪽지 종류를 만들어 쓴다.
</EasyIntro>

결제 버튼을 눌렀는데 아무 일도 일어나지 않는다는 문의가 왔다. 콘솔에는 에러가 없고, 네트워크 탭에도 결제 요청이 없다. 코드를 따라가 보니 이런 부분이 있었다.

```js
async function onPay() {
  try {
    await submitOrder(cart);
    router.push("/done");
  } catch (e) {
    // TODO: 에러 처리
  }
}
```

`submitOrder` 안에서 무슨 에러가 났는지는 이제 알 길이 없다. `catch`가 에러를 받아서 아무것도 안 하고 버렸기 때문이다. 이 글은 자바스크립트가 에러를 던지고 받는 규칙부터 시작해서, `Error` 객체에 무엇을 담아야 나중에 원인을 찾을 수 있는지, 직접 만든 에러 클래스는 어떻게 판별하는지, `finally`의 함정, 그리고 에러를 어디서 잡고 어디서 바꿔야 하는지를 본다. 출력은 Node 22에서 돌린 결과다. 서버 프로세스 전체에서 에러를 다루는 법(`uncaughtException`, 종료 코드)은 [Node.js 에러 처리 글](/posts/nodejs-error-handling)에서, 브라우저에서 놓친 에러를 수집하는 법은 [프런트엔드 에러 추적 글](/posts/frontend-error-tracking)에서 다룬다.

## 무엇이든 던질 수 있다

`throw`는 아무 값이나 던진다. 문자열도, 숫자도, 객체도, `undefined`도 된다.

```js
try {
  throw "결제 실패";
} catch (e) {
  console.log(typeof e, e instanceof Error, e.stack);
}
```

```text
string false undefined
```

던질 수는 있지만 받는 쪽은 곤란하다. 문자열에는 `stack`이 없어서 어디서 던졌는지 모른다. `e.message`를 읽는 코드는 `undefined`를 얻는다. 라이브러리가 문자열을 던지는지 `Error`를 던지는지 모르니 `catch`마다 모양을 확인해야 한다.

그래서 규칙은 하나다. 항상 `Error`나 그 자식을 던진다. ESLint의 `no-throw-literal`(TypeScript는 `@typescript-eslint/only-throw-error`)로 강제할 수 있다.

TypeScript도 이 사정을 안다. `strict` 설정에서는 `catch (e)`의 `e`가 `unknown`이다(TypeScript 4.4부터 `useUnknownInCatchVariables`). 무엇이 날아올지 모르니 쓰기 전에 좁히라는 뜻이다.

```ts
try {
  await submitOrder(cart);
} catch (e) {
  // e는 unknown이다. 바로 e.message를 쓰면 타입 에러가 난다
  const message = e instanceof Error ? e.message : String(e);
  console.error(message);
}
```

받은 값을 쓸 일이 없으면 ES2019부터 `catch { ... }`처럼 괄호를 빼도 된다. 다만 값을 안 쓴다는 건 대개 에러를 버린다는 뜻이니, 정말 버려도 되는 경우인지 한 번 더 생각한다.

## 던진 순간 함수는 거기서 멈춘다

`throw`가 실행되면 그 줄 아래는 실행되지 않는다. 엔진은 지금 함수를 빠져나가 부른 쪽으로 올라가고, 거기서도 `try`가 없으면 또 올라간다. 콜 스택을 한 칸씩 되감다가 가장 가까운 `catch`를 만나면 멈춘다. 올라가는 길에 `finally`가 있으면 그건 꼭 실행한다.

아래 코드를 보자.

```js
function validateCard(card) {
  if (!/^\d{16}$/.test(card)) throw new RangeError("카드 번호는 16자리여야 한다");
  console.log("validateCard 끝");
}
function chargeCard(card) {
  validateCard(card);
  console.log("결제 요청");
}
function submitOrder(card) {
  console.log("로딩 켜기");
  try {
    chargeCard(card);
    console.log("주문 완료");
  } finally {
    console.log("로딩 끄기");
  }
}
function onPay() {
  try {
    submitOrder("1234");
  } catch (e) {
    console.log("잡음:", e.name, e.message);
  }
}
onPay();
```

```text
로딩 켜기
로딩 끄기
잡음: RangeError 카드 번호는 16자리여야 한다
```

"validateCard 끝", "결제 요청", "주문 완료"는 한 번도 찍히지 않았다. 아래 그림에서 다음을 누르면 스택이 쌓였다가 되감기는 순서가 보인다.

`submitOrder`처럼 에러를 처리할 생각은 없지만 정리할 게 있는 함수가 `try/finally`를 쓴다. 로딩 표시 끄기, 잠금 풀기, 파일 닫기 같은 일이다. 잡지 않으니 에러는 그대로 위로 가고, 정리는 확실히 된다.

어디서도 잡히지 않은 에러는 맨 위까지 올라간다. 브라우저는 콘솔에 "Uncaught"로 시작하는 빨간 줄을 찍고 `window`에 `error` 이벤트를 보낸다. Node는 기본적으로 프로세스를 끝낸다. 그 줄을 찍은 뒤에도 페이지의 다른 코드는 계속 돈다는 점이 브라우저에서 헷갈리는 부분이다. 버튼 하나의 핸들러만 중간에 끊기고 나머지 화면은 멀쩡해 보인다.

## Error 객체가 들고 다니는 것

`new Error("메시지")`로 만든 객체에는 원인을 찾는 데 필요한 것들이 들어 있다.

`message`는 사람이 읽을 설명이다. `name`은 에러의 종류로, 기본값은 `"Error"`이고 내장 에러는 `"TypeError"`처럼 자기 이름을 갖는다. `String(e)`나 콘솔은 `name: message` 모양으로 보여 준다. `stack`은 에러가 만들어진 순간의 호출 경로다. 명세에는 아직 없지만 모든 주요 엔진이 지원해서 사실상 표준처럼 쓴다. 스택에 찍히는 위치는 `throw`한 곳이 아니라 `new Error`를 한 곳이다. 에러를 미리 만들어 두고 나중에 던지면 스택이 엉뚱한 데를 가리킨다.

`cause`는 ES2022에 들어온 옵션으로, 이 에러를 일으킨 원래 에러를 담는다.

```js
try {
  await fetch("/api/orders", { method: "POST", body });
} catch (e) {
  throw new Error("주문 저장에 실패했다", { cause: e });
}
```

이렇게 하면 위에서 받는 쪽은 "주문 저장 실패"라는 맥락과, 그 아래의 "네트워크가 끊겼다"를 함께 본다. 원래 에러를 버리고 새 메시지만 던지면 스택도 원인도 사라진다. 원인을 여러 겹 따라가며 로그를 찍는 방법은 [Node.js 에러 처리 글](/posts/nodejs-error-handling)에서 다룬다.

한 가지 함정이 있다. `message`와 `stack`은 열거되지 않는 속성이라 `JSON.stringify`가 무시한다.

```js
const e = new Error("x");
console.log(Object.keys(e), JSON.stringify(e));
```

```text
[] {}
```

에러를 서버로 보내거나 로그에 JSON으로 남길 때 `{}`만 찍히는 이유다. `name`, `message`, `stack`, `cause`를 직접 꺼내 새 객체로 만든 뒤 직렬화한다.

## 엔진이 던지는 에러 종류

직접 던지지 않아도 엔진이 던지는 에러가 있다. 종류마다 뜻이 정해져 있어서 이름만 봐도 어디를 볼지 감이 온다.

```js
const tries = [
  () => null.foo,
  () => new Array(-1),
  () => undefinedVar,
  () => JSON.parse("{bad"),
  () => decodeURIComponent("%"),
  () => (1).toFixed(101),
];
for (const t of tries) {
  try { t(); } catch (e) { console.log(e.name + " | " + e.message); }
}
```

```text
TypeError | Cannot read properties of null (reading 'foo')
RangeError | Invalid array length
ReferenceError | undefinedVar is not defined
SyntaxError | Expected property name or '}' in JSON at position 1 (line 1 column 2)
URIError | URI malformed
RangeError | toFixed() digits argument must be between 0 and 100
```

`TypeError`는 값의 종류가 맞지 않을 때다. `null`의 속성 읽기, 함수가 아닌 것 호출하기가 대표적이고, 프런트엔드에서 가장 자주 보는 에러다. `RangeError`는 값의 종류는 맞는데 범위를 벗어났을 때다. 소수를 `BigInt`로 바꾸려 할 때도 이 에러가 난다([숫자와 BigInt 글](/posts/js-numbers-bigint)). 재귀가 너무 깊어 스택이 넘칠 때도 `RangeError: Maximum call stack size exceeded`가 난다. `ReferenceError`는 없는 변수를 읽거나 TDZ에 있는 `let` 변수를 읽을 때다. `SyntaxError`는 코드 자체가 문법에 맞지 않을 때인데, 런타임에 만나는 건 대부분 `JSON.parse`다. `URIError`는 URI 인코딩 함수, `EvalError`는 지금은 거의 쓰이지 않는다.

여기에 `Promise.any`가 모두 실패했을 때 던지는 `AggregateError`가 있고, 브라우저 API는 `DOMException`을 던진다. `fetch`를 `AbortController`로 취소하면 `name`이 `"AbortError"`인 `DOMException`이 온다. 관계를 그림으로 보면 이렇다.

## 내 에러 클래스 만들기

"주문을 찾을 수 없다", "입력값이 틀렸다", "권한이 없다"는 모두 `Error`지만 화면에서 하는 일이 다르다. 404 화면, 입력칸 아래 빨간 글씨, 로그인 페이지 이동. 이걸 메시지 문자열로 구별하면 문구 하나 바꿨다가 분기가 깨진다. 종류를 클래스로 나눈다.

```js
class AppError extends Error {
  constructor(message, options) {
    super(message, options);
    this.name = new.target.name; // 자식 클래스 이름이 자동으로 들어간다
  }
}

class NotFoundError extends AppError {
  constructor(resource, id) {
    super(`${resource} ${id}을(를) 찾을 수 없다`);
    this.resource = resource;
    this.id = id;
  }
}

const nf = new NotFoundError("order", 42);
console.log(nf.name, nf instanceof NotFoundError, nf instanceof AppError, nf instanceof Error);
console.log(String(nf));
console.log(JSON.stringify(nf));
```

```text
NotFoundError true true true
NotFoundError: order 42을(를) 찾을 수 없다
{"name":"NotFoundError","resource":"order","id":42}
```

몇 가지를 짚어 보자. `super(message, options)`로 `options`를 넘겨야 `cause`가 이어진다. `this.name`을 정하지 않으면 자식 클래스도 이름이 `"Error"`로 찍혀서 로그에서 구별이 안 된다. `new.target.name`을 쓰면 자식마다 다시 적지 않아도 된다. 다만 번들러가 클래스 이름을 줄이는(minify) 설정이면 이름이 `"t"` 같은 글자로 바뀌니, 운영 로그에서 이름이 중요하면 `name`을 문자열로 직접 적거나 별도의 `code` 필드를 둔다. 마지막 줄처럼 직접 붙인 필드는 열거되어 JSON에 나오지만 `message`는 여전히 빠진다.

판별은 `instanceof`로 한다. 자식 클래스가 먼저 오게 순서를 잡는다.

```js
function toScreen(e) {
  if (e instanceof NotFoundError) return { view: "not-found" };
  if (e instanceof ValidationError) return { view: "form", fields: e.fields };
  if (e instanceof AppError) return { view: "toast", message: e.message };
  throw e; // 모르는 에러는 위로 보낸다
}
```

`instanceof`가 틀리는 경우가 두 가지 있다. 하나는 TypeScript를 `target: "ES5"`로 컴파일할 때다. ES5에는 `class`가 없어 `Error`를 상속하는 코드가 함수로 바뀌는데, 이때 프로토타입이 제대로 이어지지 않아 `nf instanceof NotFoundError`가 `false`가 된다. 생성자에서 `Object.setPrototypeOf(this, new.target.prototype)`을 부르면 고쳐지지만, 요즘은 `target`을 ES2015 이상으로 올리는 게 답이다. 다른 하나는 실행 환경(realm)이 다를 때다. iframe 안에서 만든 에러는 그 iframe의 `Error`를 상속하니 바깥 페이지의 `Error`로 `instanceof`를 하면 `false`다. 같은 라이브러리가 번들에 두 벌 들어가도 클래스가 두 개가 되어 같은 일이 생긴다. 경계를 넘는 에러는 `name`이나 `code` 필드로 판별하는 편이 튼튼하다.

## finally가 결과를 덮어쓴다

`finally`는 `try`가 정상으로 끝나든, `return`을 하든, 에러가 나든 항상 실행된다. 그런데 `finally` 안에서 `return`이나 `throw`를 하면 앞의 결과가 사라진다.

```js
function a() {
  try { return "try"; } finally { return "finally"; }
}
function b() {
  try { throw new Error("원래 에러"); } finally { return "덮음"; }
}
function c() {
  try { throw new Error("원래 에러"); } finally { throw new Error("정리 중 에러"); }
}
function d() {
  let x = 1;
  try { return x; } finally { x = 2; }
}

console.log(a());
console.log(b());
try { c(); } catch (e) { console.log(e.message); }
console.log(d());
```

```text
finally
덮음
정리 중 에러
1
```

`b`가 가장 위험하다. 에러가 났는데 `finally`의 `return`이 그 에러를 없애고 정상 값을 돌려준다. 호출한 쪽은 실패를 영영 모른다. `c`는 정리 코드가 실패하면서 원래 에러를 덮어 버린다. 로그에는 "정리 중 에러"만 남고 진짜 원인은 사라진다. `d`는 반대로 헷갈리는 경우다. `return x`가 실행되는 순간 돌려줄 값(1)이 정해지니, `finally`에서 `x`를 바꿔도 결과는 1이다. 다만 `x`가 객체라면 같은 객체를 가리키니 `finally`에서 속성을 바꾸면 그 변화는 보인다.

규칙은 간단하다. `finally`에서는 정리만 하고 `return`, `throw`, `break`, `continue`를 쓰지 않는다. ESLint의 `no-unsafe-finally`가 기본 추천 규칙으로 이걸 잡는다. 정리 코드가 실패할 수 있으면 그 안에서 따로 `try/catch`로 감싸서 원래 에러를 덮지 않게 한다.

## 삼킨 에러는 어디에도 남지 않는다

처음 결제 버튼 코드로 돌아가 보자. 빈 `catch`는 가장 흔하고 가장 비싼 실수다. 덜 노골적인 모양도 있다.

```js
// 1. 로그만 찍고 정상처럼 진행한다
try { await submitOrder(cart); } catch (e) { console.log("실패"); }
router.push("/done");

// 2. 원래 에러를 버리고 새 메시지만 던진다
try { await submitOrder(cart); } catch { throw new Error("결제 실패"); }

// 3. 기대한 에러만 잡으려다 전부 잡는다
try {
  const config = JSON.parse(text);
  applyConfig(config); // 여기서 난 TypeError도 아래로 온다
} catch (e) {
  return DEFAULT_CONFIG;
}
```

1번은 "실패"라는 글자만 남는다. 무엇이 왜 실패했는지 없고, 사용자는 완료 화면으로 넘어간다. 2번은 스택과 원인이 사라진다. `cause`로 넘기면 된다. 3번이 가장 찾기 어렵다. 깨진 JSON만 기본값으로 바꾸려 했는데, `applyConfig`의 버그도 같이 삼켜서 "설정이 가끔 적용 안 된다"는 증상만 남는다.

`catch`에서는 내가 예상한 에러인지 확인하고, 아니면 다시 던진다. `try` 블록은 실패를 예상하는 한 줄만 감싸게 좁힌다.

```js
let config;
try {
  config = JSON.parse(text);
} catch (e) {
  if (!(e instanceof SyntaxError)) throw e; // 예상한 에러가 아니면 다시 던진다
  config = DEFAULT_CONFIG;
}
applyConfig(config); // 이 버그는 숨지 않는다
```

잡아서 처리할 수 없으면 잡지 않는 게 낫다. 위에 에러를 처리할 곳(React의 에러 경계, 전역 에러 리포터)이 있으면 거기까지 올라가게 둔다. 사용자에게는 "다시 시도해 달라"를 보여 주고, 개발자에게는 스택이 남는다.

## try/catch가 닿지 않는 곳

`try/catch`는 지금 실행 중인 코드에서 동기로 던진 에러만 잡는다. 나중에 실행되는 코드에서 난 에러는 이미 `try` 블록을 빠져나간 뒤라 잡지 못한다.

```js
process.on("uncaughtException", (e) => console.log("uncaughtException:", e.message));
process.on("unhandledRejection", (e) => console.log("unhandledRejection:", e.message));

try { setTimeout(() => { throw new Error("타이머 안에서"); }, 0); } catch (e) { console.log("잡음", e.message); }
try { Promise.reject(new Error("await 없는 reject")); } catch (e) { console.log("잡음", e.message); }

async function load() { throw new Error("async 함수 안"); }
try { load(); } catch (e) { console.log("잡음", e.message); }
try { await load(); } catch (e) { console.log("await로 잡음:", e.message); }
```

```text
await로 잡음: async 함수 안
unhandledRejection: await 없는 reject
unhandledRejection: async 함수 안
uncaughtException: 타이머 안에서
```

"잡음"은 한 번도 찍히지 않았다. `setTimeout`의 콜백은 `try`가 끝난 뒤 이벤트 루프가 따로 부른다. `Promise.reject`와 `await` 없이 부른 `async` 함수는 에러를 던지지 않고 거부된 Promise를 돌려줄 뿐이라, `try`에서 볼 때는 정상으로 끝났다. 마지막 줄처럼 `await`를 붙여야 거부가 그 자리에서 던진 에러로 바뀐다.

브라우저에서도 같다. 이벤트 리스너, 타이머 콜백 안의 에러는 그 콜백 안에서 잡아야 하고, 놓친 동기 에러는 `window`의 `error` 이벤트, 놓친 Promise 거부는 `unhandledrejection` 이벤트로 간다. React 컴포넌트가 렌더링하다 던진 에러는 에러 경계가 잡지만, 이벤트 핸들러와 비동기 코드의 에러는 에러 경계도 못 잡는다. 이 차이는 [Suspense와 에러 경계 글](/posts/react-suspense-error-boundary)에서 자세히 본다. `try` 안에서 `return promise`와 `return await promise`가 다르게 동작하는 문제는 [async/await 글](/posts/js-async-await)에 있다.

## 경계에서 한 번 바꾼다

```ts
class HttpError extends AppError {
  constructor(readonly status: number, readonly code: string, options?: ErrorOptions) {
    super(`HTTP ${status} ${code}`, options);
  }
}
class NetworkError extends AppError {}

async function request<T>(url: string, init?: RequestInit): Promise<T> {
  let res: Response;
  try {
    res = await fetch(url, init);
  } catch (e) {
    // 사용자가 취소한 건 실패가 아니다. 그대로 올려 보낸다
    if (e instanceof DOMException && e.name === "AbortError") throw e;
    throw new NetworkError("서버에 닿지 못했다", { cause: e });
  }
  if (!res.ok) {
    const body = await res.json().catch(() => ({}));
    throw new HttpError(res.status, body.code ?? "UNKNOWN");
  }
  return res.json() as Promise<T>;
}
```

## 예외 대신 값으로 돌려주기

예외는 "여기서는 처리 못 하니 위로 보낸다"를 공짜로 해 준다. 대신 함수 시그니처에 실패가 드러나지 않는다. `parseConfig(text): Config`만 보고는 무엇을 던지는지 알 수 없고, TypeScript도 던지는 타입을 검사하지 않는다.

다른 방법은 실패를 값으로 돌려주는 것이다. `{ ok: true, value }` 또는 `{ ok: false, error }`를 돌려주면 받는 쪽은 `ok`를 확인하지 않고는 값을 쓸 수 없다. TypeScript가 그 검사를 강제한다. Go의 `value, err`, Rust의 `Result`가 같은 생각이다.

둘 중 하나만 쓰는 건 아니다. 입력 검증처럼 실패가 흔하고 예상되는 일, 호출한 쪽이 바로 분기해야 하는 일은 값으로 돌려준다. 버그나 "여기서는 어쩔 수 없는" 실패는 예외로 던진다. 값 방식은 모든 호출 단계에서 `if (!r.ok) return r`를 써야 해서 깊은 호출에서는 장황해진다. `map`, `flatMap`으로 이 반복을 줄이는 방법은 [펑터와 모나드 글](/posts/fp-functors-monads-js)에서 다룬다.

아래는 JSON 설정 문자열을 받아 결과를 값으로 돌려주는 함수다. 깨진 JSON은 `INVALID_JSON`, `port`가 없으면 `MISSING_PORT`, 정수가 아니거나 1~65535 밖이면 `INVALID_PORT`다. 성공하면 `port`만 담아 돌려준다. `JSON.parse`가 던지는 `SyntaxError`만 값으로 바꾸고, 다른 에러는 그대로 던지게 써 보자.

`"null"`이 까다롭다. `JSON.parse("null")`은 에러 없이 `null`을 주고, `typeof null`은 `"object"`라서 `null` 검사를 따로 해야 `"port" in null`의 `TypeError`를 피한다. 이 `TypeError`를 `catch`로 같이 잡아 `INVALID_JSON`으로 돌려줬다면, 앞에서 본 "전부 잡는" 실수가 된다.

## 다시 결제 버튼으로

처음 코드의 빈 `catch`를 고치면 이렇게 된다. 예상한 실패(품절, 네트워크)는 화면에서 처리하고, 모르는 에러는 다시 던져 에러 경계와 에러 리포터까지 보낸다. 던지는 쪽은 `Error` 계열만 던지고 `cause`로 원인을 이어 붙인다. `finally`에서는 정리만 한다. 그리고 바깥 세계의 에러는 경계에서 한 번만 내 에러 종류로 바꾼다. 이 네 가지만 지켜도 "아무 일도 안 일어난다"는 문의가 오면 적어도 어디서 멈췄는지는 로그에 남는다.

## 면접에서 나올 만한 질문

### throw로 문자열을 던지면 안 되나요?

던질 수는 있지만 쓰지 않는다. 문자열에는 `stack`이 없어서 어디서 던졌는지 알 수 없고, `message`, `name`, `cause`도 없어 받는 쪽마다 모양을 확인해야 한다. 항상 `Error`나 그 자식을 던지고, ESLint의 `no-throw-literal`로 강제한다. TypeScript가 `catch` 변수를 `unknown`으로 두는 것도 무엇이든 던질 수 있기 때문이다.

### 에러가 던져지면 실행은 어떻게 흘러가나요?

`throw` 아래 줄은 실행되지 않고, 엔진이 콜 스택을 한 칸씩 되감으며 가장 가까운 `catch`를 찾는다. 올라가는 길에 있는 `finally`는 모두 실행된다. 끝까지 `catch`가 없으면 브라우저는 콘솔에 Uncaught 에러를 찍고 `window`의 `error` 이벤트를 보내며, Node는 기본적으로 프로세스를 끝낸다. 브라우저에서는 그 핸들러만 끊기고 페이지의 나머지는 계속 돈다.

### finally 안에서 return하면 어떻게 되나요?

`try`의 반환값이나 던져진 에러가 모두 사라지고 `finally`의 `return` 값이 결과가 된다. 에러가 났는데 정상 값이 돌아가니 호출한 쪽은 실패를 모른다. `finally`에서 `throw`하면 원래 에러가 새 에러로 덮인다. 그래서 `finally`에서는 정리만 하고 제어 흐름 문장을 쓰지 않으며, `no-unsafe-finally` 규칙이 이걸 잡는다.

### 사용자 정의 에러 클래스는 어떻게 만들고 판별하나요?

`Error`를 상속하고 `super(message, options)`로 `cause`까지 넘기며, `this.name`을 클래스 이름으로 정한다. 판별은 `instanceof`로 하고 자식 클래스부터 확인한다. 다만 TypeScript를 ES5로 컴파일하거나, iframe처럼 실행 환경이 다르거나, 라이브러리가 번들에 두 벌 들어가면 `instanceof`가 틀린다. 경계를 넘나드는 에러는 `code` 같은 필드로 판별하는 편이 튼튼하다.

### try/catch로 잡지 못하는 에러는 어떤 게 있나요?

`setTimeout`이나 이벤트 리스너 같은 콜백 안의 에러, 그리고 `await` 없이 부른 Promise의 거부다. 콜백은 `try`가 끝난 뒤 따로 실행되고, Promise 거부는 던진 게 아니라 거부된 값을 돌려준 것이기 때문이다. `await`를 붙이거나 `.catch`를 달아야 하고, 놓친 것은 `window`의 `error`, `unhandledrejection` 이벤트로 수집한다. React 에러 경계도 이벤트 핸들러와 비동기 에러는 못 잡는다.

### 에러를 잡았을 때 어떻게 처리하는 게 좋나요?

예상한 에러인지 확인하고, 처리할 수 있는 것만 처리하고 나머지는 다시 던진다. `try` 블록은 실패를 예상하는 코드만 감싸게 좁혀서 버그가 같이 삼켜지지 않게 한다. 새 에러로 감쌀 때는 `cause`로 원래 에러를 남긴다. 빈 `catch`나 로그만 찍고 정상처럼 진행하는 코드는 원인을 영영 지운다.

### fetch는 404에서 에러를 던지나요? 에러 처리는 어디에 두나요?

던지지 않는다. `fetch`는 응답을 받기만 하면 상태 코드와 상관없이 이행되고, 네트워크 실패나 취소일 때만 거부된다. 그래서 `res.ok`를 직접 확인해야 한다. 이런 바깥 세계의 차이는 API 클라이언트 같은 경계에서 한 번만 내 에러 종류(`HttpError`, `NetworkError`)로 바꾸고, 화면은 그 종류만 보고 분기하게 한다. 취소(`AbortError`)는 실패가 아니니 따로 통과시킨다.

### 예외 대신 Result 같은 값을 돌려주는 방식은 언제 쓰나요?

실패가 흔하고 예상되며 호출한 쪽이 바로 분기해야 할 때, 예를 들어 입력 검증이나 설정 파싱에 쓴다. 실패가 반환 타입에 드러나서 TypeScript가 확인을 강제한다는 게 장점이다. 대신 모든 단계에서 실패를 전달하는 코드가 늘어난다. 버그나 그 자리에서 처리할 수 없는 실패는 예외로 던지고, 경계에서 예외를 값으로 바꾸는 식으로 둘을 섞어 쓴다.
