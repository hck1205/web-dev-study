서점 서비스를 처음으로 실제 운영 서버에 올리기로 했다. 개발할 때는 `apt install postgresql` 한 번이면 충분했다. 그런데 운영 전날이 되니 질문이 쏟아진다. 램 32GB 서버에 `shared_buffers`는 얼마로 하지. `max_connections`는 앱 서버 개수만큼 올려야 하나. 누가 실수로 `DELETE`를 WHERE 없이 치면 어디까지 되돌릴 수 있지. 1년 뒤 PostgreSQL 17이나 18로 올릴 때 서비스를 얼마나 멈춰야 하지.

이 글은 그 질문들에 차례로 답한다. 설정을 바꾸고 적용하는 법, 메모리와 연결 수를 정하는 계산, 매일 볼 숫자, 백업 세 가지(pg_dump, pg_basebackup, WAL 보관)와 실제 시점 복구(PITR), 버전 업그레이드까지다. 기준은 Ubuntu 24.04 LTS의 PostgreSQL 16.15이고, 설정을 바꾸고 재시작하고 일부러 데이터를 지우는 실험은 전부 따로 만든 클러스터(`16/pg3`, 포트 5453)와 거기서 복원한 클러스터(`16/pg3r`, 포트 5454)에서 했다. 이 시리즈의 [내부 구조 글](/posts/postgres-architecture)과 [VACUUM 글](/posts/postgres-mvcc-vacuum)을 읽었다고 가정한다.

예제 DB는 서점 `shop`이다. 이번에는 백업이 의미 있도록 데이터를 넉넉히 넣었다.

```sql
-- users 1만, books 1만, orders 100만, order_items 200만
SELECT relname, n_live_tup FROM pg_stat_user_tables ORDER BY relname;
SELECT pg_size_pretty(pg_database_size(current_database()));
```

```text
   relname   | n_live_tup
-------------+------------
 books       |      10000
 order_items |    2000000
 orders      |    1000000
 users       |      10000
(4 rows)

 pg_size_pretty
----------------
 307 MB
(1 row)
```

## 설정은 어디에 쓰고 언제 적용되나

설정을 바꾸는 방법은 두 가지다. `/etc/postgresql/16/main/postgresql.conf`를 직접 고치거나(Ubuntu 기준, RHEL 계열은 보통 데이터 디렉터리 안), SQL로 `ALTER SYSTEM`을 친다. `ALTER SYSTEM`은 데이터 디렉터리의 `postgresql.auto.conf`에 값을 쓰고, 이 파일은 `postgresql.conf`보다 나중에 읽혀서 이긴다. 그래서 두 곳에 같은 설정이 있으면 `auto.conf` 쪽이 적용된다. 이걸 모르면 `postgresql.conf`를 아무리 고쳐도 안 바뀐다.

언제 적용되는지는 설정마다 다르고, `pg_settings.context`에 적혀 있다.

```sql
SELECT name, setting, unit, context FROM pg_settings
WHERE name IN ('shared_buffers', 'max_connections', 'wal_level', 'archive_mode',
               'shared_preload_libraries', 'huge_pages', 'archive_command', 'max_wal_size',
               'log_min_duration_statement', 'work_mem', 'maintenance_work_mem',
               'effective_cache_size', 'random_page_cost', 'effective_io_concurrency')
ORDER BY context, name;
```

```text
            name            |  setting   | unit |  context
----------------------------+------------+------+------------
 archive_mode               | off        |      | postmaster
 huge_pages                 | try        |      | postmaster
 max_connections            | 100        |      | postmaster
 shared_buffers             | 16384      | 8kB  | postmaster
 shared_preload_libraries   |            |      | postmaster
 wal_level                  | replica    |      | postmaster
 archive_command            | (disabled) |      | sighup
 max_wal_size               | 1024       | MB   | sighup
 log_min_duration_statement | -1         | ms   | superuser
 effective_cache_size       | 524288     | 8kB  | user
 effective_io_concurrency   | 1          |      | user
 maintenance_work_mem       | 65536      | kB   | user
 random_page_cost           | 4          |      | user
 work_mem                   | 4096       | kB   | user
(14 rows)
```

`postmaster`는 서버를 재시작해야 바뀐다. 공유 메모리 크기나 프로세스 구성이 걸린 설정이다. `sighup`은 설정 파일을 다시 읽으면(`SELECT pg_reload_conf()` 또는 `systemctl reload`) 바로 바뀐다. `superuser`와 `user`는 다시 읽어도 되고, 세션에서 `SET`으로 그 연결만 바꿀 수도 있다(`superuser`는 슈퍼유저만). 운영 전에 `postmaster` 설정을 먼저 정해 두는 이유가 이것이다. 나중에 바꾸려면 서비스를 멈춰야 한다.

실제로 세 개를 바꾸고 다시 읽어 봤다.

```sql
ALTER SYSTEM SET work_mem = '16MB';           -- user
ALTER SYSTEM SET shared_buffers = '256MB';    -- postmaster
ALTER SYSTEM SET random_page_cost = 1.1;      -- user
SELECT pg_reload_conf();

-- 적용됐는지, 재시작을 기다리는지
SELECT name, setting, unit, pending_restart FROM pg_settings
WHERE name IN ('work_mem', 'shared_buffers', 'random_page_cost');
```

```text
       name       | setting | unit | pending_restart
------------------+---------+------+-----------------
 random_page_cost | 1.1     |      | f
 shared_buffers   | 16384   | 8kB  | t
 work_mem         | 16384   | kB   | f
(3 rows)
```

```text
LOG:  parameter "work_mem" changed to "16MB"
LOG:  parameter "shared_buffers" cannot be changed without restarting the server
LOG:  parameter "random_page_cost" changed to "1.1"
LOG:  configuration file "/var/lib/postgresql/16/pg3/postgresql.auto.conf" contains errors; unaffected changes were applied
```

`shared_buffers`는 여전히 16384 × 8kB = 128MB이고 `pending_restart`가 `t`다. 서버 로그에도 그렇게 남는다. 마지막 줄의 "contains errors"는 무서워 보이지만 재시작 대기를 그렇게 부르는 것이다. 어느 파일 몇 번째 줄이 이겼는지는 `pg_file_settings`가 보여 준다.

```sql
SELECT sourcefile, sourceline, name, setting, applied, error
FROM pg_file_settings WHERE name IN ('work_mem', 'shared_buffers', 'random_page_cost');
```

```text
                   sourcefile                    | sourceline |       name       | setting | applied |            error
-------------------------------------------------+------------+------------------+---------+---------+------------------------------
 /etc/postgresql/16/pg3/postgresql.conf          |        130 | shared_buffers   | 128MB   | f       |
 /var/lib/postgresql/16/pg3/postgresql.auto.conf |          5 | work_mem         | 16MB    | t       |
 /var/lib/postgresql/16/pg3/postgresql.auto.conf |          6 | shared_buffers   | 256MB   | f       | setting could not be applied
 /var/lib/postgresql/16/pg3/postgresql.auto.conf |          7 | random_page_cost | 1.1     | t       |
(4 rows)
```

되돌릴 때는 `ALTER SYSTEM RESET shared_buffers`로 `auto.conf`에서 그 줄을 지운다. 바꾸기 전에 `SHOW`로 지금 값을 적어 두고, 바꾼 뒤 `pg_settings`로 확인하고, 재시작이 필요한 설정은 점검 시간에 모아서 재시작하는 순서를 지킨다.

<Callout kind="warning" title="여러 값을 한 문자열로 넣으면 서버가 안 뜬다">
`ALTER SYSTEM SET shared_preload_libraries = 'auto_explain,pg_stat_statements'`처럼 따옴표 하나로 묶으면, PostgreSQL은 이름이 `auto_explain,pg_stat_statements`인 라이브러리 하나로 저장한다(`auto.conf`에 `'"auto_explain,pg_stat_statements"'`로 쓰인다). 다시 읽을 때는 문제가 없다가, 재시작하는 순간 `FATAL:  could not access file "auto_explain,pg_stat_statements": No such file or directory`로 서버가 뜨지 않는다. 실제로 해 보고 그대로 멈췄다. 목록은 `= auto_explain, pg_stat_statements`처럼 따옴표 없이 쉼표로 나열한다. 이미 멈췄다면 `postgresql.auto.conf`에서 그 줄을 직접 고치고(서버가 꺼져 있을 때만) 다시 시작한다. 재시작 전에 `pg_file_settings`의 `error` 열을 확인하는 습관이 이런 사고를 막는다.
</Callout>

## 메모리 설정 정하기

[내부 구조 글](/posts/postgres-architecture)에서 본 대로, 메모리는 모두가 함께 쓰는 `shared_buffers`, 연결과 작업마다 따로 잡는 `work_mem`과 `maintenance_work_mem`, 그리고 PostgreSQL 밖의 OS 페이지 캐시로 나뉜다. 램 32GB짜리 DB 전용 서버라면 출발점은 이렇다.

```ini
# /etc/postgresql/16/main/conf.d/tuning.conf  (Ubuntu는 conf.d의 .conf 파일을 자동으로 읽는다)
shared_buffers = 8GB            # 램의 25% 안팎. 재시작 필요
effective_cache_size = 24GB     # 램의 50~75%. 플래너에게 주는 힌트일 뿐 메모리를 잡지 않는다
work_mem = 16MB                 # 정렬·해시 작업 하나당. 아래 계산으로 정한다
maintenance_work_mem = 1GB      # CREATE INDEX, VACUUM용. 동시에 몇 개만 돈다
huge_pages = try                # shared_buffers가 크면 리눅스 huge pages 설정을 함께
```

`shared_buffers`를 25%보다 크게 잡아서 얻는 건 생각보다 적다. 나머지 램은 OS 페이지 캐시가 쓰고, 그 캐시도 PostgreSQL 데이터를 들고 있다. 너무 키우면 `work_mem`과 OS 캐시 몫이 줄어든다. 이 숫자들은 출발점이고, 아래 "매일 보는 숫자"의 캐시 적중률과 임시 파일을 보며 조정한다. 웹 도구 PGTune도 비슷한 공식으로 값을 계산해 준다.

## work_mem은 곱하기로 계산한다

`work_mem`이 위험한 이유는 한도가 연결 하나도, 쿼리 하나도 아니고 실행 계획의 정렬·해시 노드 하나라서다. 해시 조인과 해시 집계는 거기에 `hash_mem_multiplier`(13부터, 기본값 2)를 곱한 만큼까지 쓴다. 병렬 쿼리면 worker마다 또 따로 잡는다. 주문과 주문 항목을 조인해 사용자별 구매액을 구하는 쿼리로 확인했다.

```sql
SET work_mem = '4MB';     -- 기본값
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.user_id, sum(i.qty * i.price) AS spent
FROM orders o JOIN order_items i USING (order_id)
GROUP BY o.user_id ORDER BY spent DESC LIMIT 3;

SET work_mem = '32MB';
-- 같은 쿼리
```

```text
-- work_mem = 4MB
   Buffers: shared hit=489 read=19612, temp read=12658 written=12728
                                 ->  Parallel Hash  (cost=11519.67..11519.67 rows=416667 width=16) (actual time=85.212..85.213 rows=333333 loops=3)
                                       Buckets: 262144  Batches: 8  Memory Usage: 7968kB
 Execution Time: 596.298 ms

-- work_mem = 32MB
   Buffers: shared hit=681 read=19420
                                       Buckets: 1048576  Batches: 1  Memory Usage: 55168kB
 Execution Time: 709.127 ms
```

4MB에서는 해시 테이블을 8조각(`Batches: 8`)으로 나눠 임시 파일(`temp written`)을 쓰며 처리했다. 해시 메모리 한도가 4MB × 2 = 8MB라 `Memory Usage: 7968kB`에서 멈춘 것이다. 32MB에서는 임시 파일 없이 한 번에 했는데, 해시 테이블 하나가 55MB를 썼다. `work_mem` 32MB보다 크다. 병렬 해시는 프로세스 3개(본인 + worker 2)가 하나의 해시 테이블을 나눠 쓰고, 한도도 32MB × 2 × 3 = 192MB까지 커지기 때문이다.

그리고 이 경우엔 오히려 느려졌다. 두 번씩 돌려도 596ms와 620ms, 709ms와 683ms였다. 임시 파일이 OS 페이지 캐시에 머물러 디스크까지 안 갔고, 큰 해시 테이블은 CPU 캐시를 덜 탄다. `work_mem`을 올린다고 늘 빨라지지 않는다. 확실한 건 메모리를 더 쓴다는 것뿐이다. 그래서 전역값은 보수적으로 두고, 큰 리포트 쿼리처럼 필요한 곳에서만 `SET LOCAL work_mem = '256MB'`로 올리는 편이 안전하다.

최악의 경우 메모리를 얼마나 쓸 수 있는지 계산해 보자. 연결 수 × (1 + 병렬 worker 수) × work_mem × (정렬 노드 수 + 해시 노드 수 × hash_mem_multiplier)다. 실제로 모든 연결이 동시에 이런 쿼리를 돌리는 일은 드물지만, 이 값이 램을 훌쩍 넘으면 언젠가 OOM killer를 만난다. 마지막 테스트가 위 실험의 192MB다.

## SSD라면 random_page_cost를 낮춘다

플래너는 페이지 하나를 순서대로 읽는 비용(`seq_page_cost`)을 1, 아무 데나 골라 읽는 비용(`random_page_cost`)을 4로 본다. 회전 디스크 시절의 비율이다. SSD나 클라우드 블록 스토리지에서는 무작위 읽기가 그렇게 비싸지 않으니 1.1~2 정도로 낮추는 게 보통이고, 그러면 인덱스를 더 잘 쓴다. 사용자 한 명의 주문 항목을 가져오는 조인으로 비교했다(둘 다 데이터가 메모리에 있는 상태).

```sql
SET random_page_cost = 4;
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.order_id, i.book_id
FROM orders o JOIN order_items i USING (order_id) WHERE o.user_id = 77;

SET random_page_cost = 1.1;
-- 같은 쿼리
```

```text
-- random_page_cost = 4
 Nested Loop  (cost=5.63..819.71 rows=200 width=16) (actual time=0.110..2.289 rows=200 loops=1)
   ->  Bitmap Heap Scan on orders o  (cost=5.20..371.46 rows=100 width=8) (actual time=0.092..1.009 rows=100 loops=1)
         ->  Bitmap Index Scan on orders_user_id_idx  (cost=0.00..5.17 rows=100 width=0) (actual time=0.072..0.073 rows=100 loops=1)
   ->  Index Only Scan using order_items_pkey on order_items i  (cost=0.43..4.46 rows=2 width=16) (actual time=0.012..0.012 rows=2 loops=100)
 Execution Time: 2.399 ms

-- random_page_cost = 1.1
 Nested Loop  (cost=0.85..271.51 rows=200 width=16) (actual time=0.020..0.698 rows=200 loops=1)
   ->  Index Scan using orders_user_id_idx on orders o  (cost=0.42..113.26 rows=100 width=8) (actual time=0.010..0.246 rows=100 loops=1)
   ->  Index Only Scan using order_items_pkey on order_items i  (cost=0.43..1.56 rows=2 width=16) (actual time=0.004..0.004 rows=2 loops=100)
 Execution Time: 0.719 ms
```

`orders`를 읽는 방법이 Bitmap Heap Scan에서 Index Scan으로 바뀌었고, 전체 `cost`가 819에서 271로 내려가며 2.4ms가 0.72ms가 됐다. 작은 차이 같지만 초당 수천 번 도는 쿼리라면 크다. 반대로 데이터가 대부분 디스크에 있는 느린 스토리지라면 4가 맞을 수 있으니, 바꾼 뒤 주요 쿼리의 실행 계획을 확인한다. SSD라면 `effective_io_concurrency`(비트맵 힙 스캔의 미리 읽기 개수, 16 기본값 1)도 200 정도로 올리는 게 흔하다. 실행 계획 읽는 법은 [쿼리 튜닝 글](/posts/sql-query-tuning)에 있다.

## max_connections를 올리는 대신 연결 풀

앱 서버가 10대이고 각자 풀 크기가 20이면 연결이 200개 필요하다. 그렇다고 `max_connections`를 500, 1000으로 올리면 안 된다. 연결마다 프로세스가 하나씩 생기고, 위에서 계산한 `work_mem` 예산이 연결 수에 비례하며, 동시에 실행 중인 쿼리가 CPU 코어 수를 크게 넘으면 처리량은 오히려 떨어진다. 실제로 DB가 동시에 돌릴 수 있는 일은 코어 수의 몇 배 정도다.

그래서 앱 서버와 DB 사이에 PgBouncer 같은 연결 풀러를 둔다. 앱은 PgBouncer에 수백, 수천 개를 연결하고, PgBouncer는 PostgreSQL에 수십 개만 연결해 돌려 쓴다. 아래 그림의 점이 요청이 흐르는 방향이다.

PgBouncer의 풀 모드가 중요하다. `session` 모드는 클라이언트가 연결을 끊을 때까지 DB 연결 하나를 내준다. 안전하지만 풀링 효과가 적다. `transaction` 모드는 트랜잭션 하나가 끝나면 DB 연결을 바로 돌려받아 다른 클라이언트에게 준다. 효과가 크지만, 같은 클라이언트의 다음 트랜잭션이 다른 backend로 갈 수 있으니 세션에 붙는 상태가 깨진다.

- 세션 단위 `SET`(예: `SET search_path`, `SET statement_timeout`)이 다른 클라이언트에게 새거나 사라진다. 트랜잭션 안에서 `SET LOCAL`을 쓰거나, 역할(`ALTER ROLE ... SET`)에 기본값을 건다.
- 이름 붙은 prepared statement는 PgBouncer 1.21부터 `max_prepared_statements` 설정으로 지원한다. 그 이전 버전이면 드라이버의 서버 측 prepare를 꺼야 한다.
- 세션 단위 advisory lock, `LISTEN`, 임시 테이블, `WITH HOLD` 커서는 쓰지 않는다. 이런 기능이 필요한 연결(마이그레이션 도구, 리스너)은 PgBouncer를 거치지 않고 DB에 직접 붙인다.

```ini
; /etc/pgbouncer/pgbouncer.ini 의 핵심 줄 (예시)
[databases]
shop = host=127.0.0.1 port=5432 dbname=shop

[pgbouncer]
pool_mode = transaction
max_client_conn = 1000        ; 앱이 PgBouncer에 붙을 수 있는 수
default_pool_size = 40        ; DB 하나·사용자 하나당 PostgreSQL 연결 수
max_prepared_statements = 100 ; 1.21+
```

`default_pool_size`는 코어 수의 2~4배에서 시작해 대기 시간(PgBouncer의 `SHOW POOLS`에서 `cl_waiting`)을 보며 조정한다. `max_connections`는 풀 크기 합에 관리용 여유(직접 붙는 관리자, 복제, 모니터링)를 더한 정도면 된다. 풀 크기 이야기와 N+1 같은 앱 쪽 문제는 [쿼리 튜닝 글](/posts/sql-query-tuning)에 있다.

## 매일 보는 숫자들

모니터링 도구(Prometheus의 postgres_exporter, 클라우드 콘솔)가 무엇이든, 결국 보는 건 몇 개의 시스템 뷰다. 첫째는 DB 단위 통계 `pg_stat_database`다.

```sql
SELECT datname, blks_hit, blks_read,
       round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 2) AS hit_pct,
       xact_commit, xact_rollback, deadlocks, temp_files,
       pg_size_pretty(temp_bytes) AS temp
FROM pg_stat_database WHERE datname = current_database();
```

```text
 datname | blks_hit | blks_read | hit_pct | xact_commit | xact_rollback | deadlocks | temp_files |  temp
---------+----------+-----------+---------+-------------+---------------+-----------+------------+--------
 pg3_ops | 44365449 |    180743 |   99.59 |         309 |             0 |         0 |        142 | 377 MB
(1 row)
```

`hit_pct`는 `shared_buffers`에서 찾은 비율이다. OLTP 서비스는 보통 99% 이상이 나온다. 이 값이 서서히 떨어지면 자주 쓰는 데이터가 `shared_buffers`보다 커졌다는 신호다. 다만 [내부 구조 글](/posts/postgres-architecture)에서 봤듯 `blks_read`는 OS 캐시에서 온 것일 수도 있어서, 디스크 I/O 지표(iostat의 `r/s`, `await`)와 같이 본다. `temp_files`와 `temp`가 계속 늘면 `work_mem`이 부족한 쿼리가 있다. `xact_rollback`이 갑자기 늘면 앱 에러, `deadlocks`가 0이 아니면 [교착 상태](/posts/db-transaction-isolation)를 찾는다. 이 값들은 누적이라 시간당 증가량으로 봐야 한다.

둘째는 지금 무슨 일이 일어나는지 보여 주는 `pg_stat_activity`다. 부하 테스트 중에 상태별로 묶어 봤다.

```sql
SELECT datname, usename, state, wait_event_type, count(*)
FROM pg_stat_activity WHERE backend_type = 'client backend'
GROUP BY 1, 2, 3, 4 ORDER BY count(*) DESC;
```

```text
  datname  | usename  |        state        | wait_event_type | count
-----------+----------+---------------------+-----------------+-------
 pg3_bench | postgres | active              | LWLock          |     2
 pg3_bench | postgres | active              | IO              |     1
 pg3_bench | postgres | active              | Lock            |     1
 pg3_bench | postgres | active              |                 |     1
 pg3_bench | postgres | idle in transaction |                 |     1
 pg3_ops   | postgres | active              |                 |     1
(6 rows)
```

`active` 수가 코어 수를 꾸준히 넘으면 CPU나 I/O가 밀리고 있다. `wait_event_type`이 `Lock`이면 행이나 테이블 잠금을 기다리는 중이고, `pg_blocking_pids(pid)`로 누가 막는지 찾는다. `IO`는 디스크, `LWLock`은 내부 공유 메모리 경합이다. `idle in transaction`이 오래 남아 있으면 VACUUM을 막는다([VACUUM 글](/posts/postgres-mvcc-vacuum)). 셋째는 테이블 단위의 `pg_stat_user_tables`로, `seq_scan`이 큰 테이블에서 계속 늘면 인덱스가 빠진 쿼리가 있고, `n_dead_tup`과 `last_autovacuum`으로 VACUUM 상태를 본다. 그리고 DB 나이 `age(datfrozenxid)`, 복제 지연, 디스크 사용량(데이터와 `pg_wal`)을 알림에 건다.

## 느린 쿼리를 로그로 잡기

어떤 쿼리가 느린지 알려면 로그가 가장 확실하다. `log_min_duration_statement`를 걸면 그보다 오래 걸린 쿼리가 실행 시간과 함께 남는다. 실행 계획까지 남기고 싶으면 `auto_explain` 확장을 미리 적재한다(`shared_preload_libraries`는 재시작이 필요하다).

```sql
ALTER SYSTEM SET log_min_duration_statement = '200ms';
ALTER SYSTEM SET shared_preload_libraries = auto_explain, pg_stat_statements;   -- 따옴표 없이 나열
-- 재시작 후에 auto_explain 설정이 인식된다
ALTER SYSTEM SET auto_explain.log_min_duration = '500ms';
ALTER SYSTEM SET auto_explain.log_analyze = on;   -- 실제 행 수와 시간까지 (오버헤드가 있다)
ALTER SYSTEM SET auto_explain.log_buffers = on;
SELECT pg_reload_conf();
```

`auto_explain.*` 설정은 라이브러리를 적재하기 전에 `ALTER SYSTEM`으로 넣으려 하면 `ERROR:  unrecognized configuration parameter "auto_explain.log_min_duration"`으로 거부된다. 그래서 재시작한 뒤에 넣었다. 앞의 구매액 쿼리를 돌리자 로그에 이렇게 남았다(일부).


첫 줄이 `auto_explain`이 남긴 실제 실행 계획이고, 마지막 줄이 `log_min_duration_statement`가 남긴 쿼리와 시간이다. 운영에서 문제가 된 그 순간의 계획을 그대로 볼 수 있다는 게 가장 큰 장점이다. 다음 날 손으로 `EXPLAIN`을 치면 통계와 캐시가 달라 다른 계획이 나오기도 한다. `log_analyze = on`은 모든 쿼리에 시간을 재는 비용이 붙으니, 부담되면 `auto_explain.sample_rate`로 일부만 잰다. 어떤 쿼리가 누적으로 시간을 가장 많이 쓰는지는 로그보다 `pg_stat_statements`가 낫다([쿼리 튜닝 글](/posts/sql-query-tuning)). 잠금 대기는 `log_lock_waits = on`을 켜면 `deadlock_timeout`(1초)보다 오래 기다린 잠금이 로그에 남는다.

## 논리 백업과 복원

백업은 두 종류다. 논리 백업은 데이터를 SQL이나 그에 준하는 형태로 꺼낸다. `pg_dump`가 하는 일이다. 물리 백업은 데이터 디렉터리의 파일을 그대로 복사한다. 먼저 `pg_dump`다. 형식이 네 가지인데 운영에서는 `-Fc`(custom)나 `-Fd`(directory)를 쓴다.

```bash
# 백업 디렉터리 (postgres 사용자 소유)
sudo -u postgres mkdir -p /var/lib/postgresql/backup && cd /var/lib/postgresql/backup

# time 출력은 실제 걸린 초만 보이게
TIMEFORMAT='%R s'

# 일반 SQL 텍스트 (psql로 복원)
time sudo -u postgres pg_dump -p 5453 -Fp -f shop.sql pg3_ops
# custom 형식: 압축, pg_restore로 골라서·병렬로 복원 가능
time sudo -u postgres pg_dump -p 5453 -Fc -f shop.dump pg3_ops
# directory 형식: 테이블마다 파일, 백업도 병렬(-j)로
time sudo -u postgres pg_dump -p 5453 -Fd -j 4 -f shop.dir pg3_ops

ls -lh; du -sh shop.dir; ls shop.dir
```

```bash
sudo -u postgres createdb -p 5453 pg3_restore1
```

백업은 1.4~2.2초였는데 복원은 6.6초다. 데이터를 넣고, 인덱스와 제약 조건을 다시 만들고, 외래 키를 검사하기 때문이다. `-j 4`로 인덱스를 동시에 만들자 4.4초로 줄었다. 데이터가 수백 GB면 이 차이가 몇 시간이다. 특정 테이블만 살리려면 `pg_restore -t order_items`처럼 고르거나, `-l`로 목차를 파일로 뽑아 고친 뒤 `-L`로 넘긴다.

역할도 챙겨야 한다. 덤프에는 `GRANT SELECT ... TO shop_app` 같은 권한이 들어 있는데, 새 서버에 `shop_app` 역할이 없으면 그 줄들이 `role "shop_app" does not exist` 에러로 실패한다. 그래서 `globals.sql`을 먼저 `psql -f`로 넣는다. 받아 둔 `globals.sql`에는 비밀번호가 SCRAM 해시로 들어 있다(`PASSWORD 'SCRAM-SHA-256$4096:...'`). 평문은 아니지만 유출되면 오프라인 대입 공격의 재료가 되니 백업 파일 권한과 저장 위치를 지킨다. 16.10 이후의 `pg_dump`와 `pg_dumpall`은 출력 맨 앞과 끝에 `\restrict` 줄을 붙인다. 덤프에 악성 psql 명령이 끼어드는 것을 막는 보안 수정이고, 그래서 복원할 때 쓰는 `psql`도 같은 마이너 이상으로 맞춘다.

논리 백업은 버전과 무관하게 옮길 수 있고(새 버전의 `pg_dump`로 옛 서버를 뜬다), 일부만 꺼낼 수 있다는 장점이 있다. 대신 "백업한 그 순간"으로만 돌아갈 수 있고, 큰 DB는 복원이 느리다.

## 물리 백업과 WAL 보관

물리 백업은 데이터 디렉터리를 파일째 복사한다. 그냥 `cp`하면 복사하는 동안 파일이 바뀌어 깨진 복사본이 된다. `pg_basebackup`은 체크포인트를 하나 찍고, 그 지점부터 복사가 끝날 때까지의 WAL을 함께 받아서, 복원할 때 WAL을 재생해 일관된 상태로 맞춘다. [내부 구조 글](/posts/postgres-architecture)의 크래시 복구와 같은 원리다.

그런데 백업 시점 이후의 WAL까지 계속 모아 두면 어떨까. 백업에 그 WAL을 이어서 재생하면 백업 이후 아무 시점으로나 갈 수 있다. 이게 시점 복구(PITR, Point-In-Time Recovery)다. WAL 세그먼트가 다 찰 때마다 `archive_command`로 다른 곳에 복사하게 설정한다.

```bash
# 보관 장소 (실제로는 다른 서버나 객체 스토리지)
sudo -u postgres mkdir -p /var/lib/postgresql/pg3_archive

# archive_mode는 재시작 필요, archive_command는 reload로 바뀐다
sudo -u postgres psql -p 5453 <<'SQL'
ALTER SYSTEM SET archive_mode = on;
ALTER SYSTEM SET archive_command = 'test ! -f /var/lib/postgresql/pg3_archive/%f && cp %p /var/lib/postgresql/pg3_archive/%f';
ALTER SYSTEM SET archive_timeout = '60s';   -- 쓰기가 적어도 60초마다 세그먼트를 넘긴다
SQL
sudo pg_ctlcluster 16 pg3 restart

# 동작 확인: 세그먼트를 강제로 넘기고 보관 통계를 본다
sudo -u postgres psql -p 5453 -c "SELECT pg_switch_wal()"
sudo -u postgres psql -p 5453 -c "SELECT archived_count, last_archived_wal, failed_count FROM pg_stat_archiver"
```

```text
 archived_count |    last_archived_wal     | failed_count
----------------+--------------------------+--------------
             33 | 00000001000000010000001A |            0
(1 row)
```

`%p`는 보관할 WAL 파일 경로, `%f`는 파일 이름이다. 앞의 `test ! -f`는 같은 이름 파일이 이미 있으면 덮어쓰지 않고 실패하게 하는 안전장치다. `archive_command`가 실패하면 PostgreSQL은 그 세그먼트를 지우지 않고 계속 재시도한다. 보관 장소가 꽉 차서 실패가 이어지면 `pg_wal`이 차올라 결국 DB 디스크가 가득 찬다. `failed_count`와 `pg_wal` 크기를 반드시 알림에 건다. 실제 운영에서는 `cp`보다 아래에서 볼 pgBackRest나 WAL-G 같은 도구를 `archive_command`에 쓴다. 15부터는 셸 명령 대신 `archive_library`로 모듈을 지정하는 방법도 있다.

이제 베이스 백업을 뜬다.

```bash
# 빠른 체크포인트(-c fast), 백업 중 WAL을 함께 스트리밍(-Xstream), 진행률(-P)
sudo -u postgres pg_basebackup -p 5453 -D /var/lib/postgresql/pg3_base \
  -Fp -Xstream -c fast -P -v --label=pitr-demo
```

## WHERE 없는 DELETE 3초 전으로

이제 사고를 낸다. 베이스 백업을 뜬 뒤 정상 주문이 하나 들어왔고, 몇 초 뒤 누군가 `order_items`를 WHERE 없이 지웠다.

```sql
-- 백업 뒤에 들어온 정상 주문

INSERT INTO order_items VALUES (currval('orders_order_id_seq'), 7, 1, 28000);
SELECT now() AS good_time;
-- 실수
DELETE FROM order_items;
SELECT now() AS accident_time;
SELECT pg_switch_wal();       -- 마지막 WAL까지 보관되게
```

```text
DELETE 2000001
```

```bash

sudo cp -a /var/lib/postgresql/pg3_base /var/lib/postgresql/16/pg3r

# 2. Ubuntu 클러스터 설정을 복사해 포트와 경로만 바꾼다
sudo cp -a /etc/postgresql/16/pg3 /etc/postgresql/16/pg3r
sudo sed -i -e "s#/var/lib/postgresql/16/pg3'#/var/lib/postgresql/16/pg3r'#" \
  -e "s#/etc/postgresql/16/pg3/#/etc/postgresql/16/pg3r/#g" -e "s#^port = 5453#port = 5454#" \
  -e "s#16-pg3.pid#16-pg3r.pid#" -e "s#^cluster_name = '16/pg3'#cluster_name = '16/pg3r'#" \
  /etc/postgresql/16/pg3r/postgresql.conf

# 3. 복구 설정: 보관된 WAL을 가져오는 법, 멈출 시점. 복원본은 보관을 끈다
sudo -u postgres tee -a /var/lib/postgresql/16/pg3r/postgresql.auto.conf <<'EOF'

EOF

# 4. 이 파일이 있으면 복구 모드로 시작한다
sudo -u postgres touch /var/lib/postgresql/16/pg3r/recovery.signal
sudo pg_ctlcluster 16 pg3r start
```

복원본의 `archive_mode`를 끄는 이유가 있다. 백업에 들어 있던 `postgresql.auto.conf`는 원본의 `archive_command`를 그대로 가지고 있어서, 켜 둔 채로 띄우면 복원본의 WAL이 원본의 보관 장소에 섞여 들어간다. 로그를 보자.

## 백업은 복원해 봐야 백업이다

백업 파일이 있다는 것과 복원할 수 있다는 것은 다르다. `archive_command`가 몇 주째 조용히 실패하고 있었거나, 백업 스크립트가 빈 파일을 만들고 있었거나, 복원 절차를 아무도 몰라서 사고 당일 몇 시간을 헤맬 수 있다. 그래서 정기적으로 실제 복원을 해 본다.

- 매일: 백업 작업 성공 여부, `pg_stat_archiver.failed_count`, 마지막 보관 시각(`last_archived_time`)이 `archive_timeout`보다 오래되지 않았는지를 알림으로 받는다.
- 매주: 최신 베이스 백업에 `pg_verifybackup`을 돌리고, 별도 서버에서 최신 시점까지 복원해 띄운 뒤 주요 테이블의 행 수와 최근 데이터를 확인한다. 걸린 시간을 기록한다.
- 분기마다: 위의 PITR 실습처럼 특정 시점 복원을 사람이 직접 해 본다. 문서대로 했을 때 되는지가 핵심이다.

목표 숫자도 미리 정한다. 얼마만큼의 데이터를 잃어도 되는가(RPO)는 WAL 보관 주기와 복제로, 얼마 안에 복구해야 하는가(RTO)는 베이스 백업 주기, 복원 속도, 대기 복제본으로 정해진다. WAL 보관만으로는 마지막 세그먼트가 보관되기 전 몇 초~`archive_timeout`분의 데이터를 잃을 수 있다. 이 틈을 좁히려면 `pg_receivewal`로 WAL을 실시간으로 받아 두거나 [스트리밍 복제](/posts/db-replication-sharding)를 함께 쓴다. 복제는 백업을 대신하지 않는다. `DELETE`도 복제본에 그대로 복제된다.

## 백업 도구와 PostgreSQL 17의 증분 백업

위 실습은 원리를 보려고 `cp`와 `pg_basebackup`으로 했다. 운영에서는 보통 전용 도구를 쓴다. pgBackRest는 전체·차등·증분 백업, 병렬 압축, S3 같은 객체 스토리지, 보관 기간 관리, 복원 명령 하나로 PITR까지 해 준다. Barman은 백업 서버를 따로 두고 여러 DB 서버의 백업과 WAL을 모으는 방식이다. 클라우드에서는 WAL-G도 많이 쓴다. 어느 쪽이든 원리는 같다. 베이스 백업 + 보관된 WAL이다.

PostgreSQL 17부터는 기본 도구에도 증분 백업이 들어왔다. `summarize_wal = on`으로 WAL 요약을 켜 두면, `pg_basebackup --incremental=<이전 백업의 backup_manifest>`가 이전 백업 이후 바뀐 블록만 뜬다. 복원할 때는 `pg_combinebackup`으로 전체 백업과 증분 백업들을 합쳐 완전한 데이터 디렉터리를 만든다. 16에서는 이 기능이 없으니 증분이 필요하면 pgBackRest 같은 도구를 쓴다.

## 메이저 버전 올리기

PostgreSQL은 해마다 메이저 버전(16, 17, 18)이 나오고 각각 5년 동안 지원한다. 16은 2028년 11월에 지원이 끝난다. 메이저 버전은 데이터 파일 형식이 바뀔 수 있어서, 새 바이너리로 옛 데이터 디렉터리를 그대로 열 수 없다. 방법은 셋이다.

첫째, `pg_dump`/`pg_restore`. 새 버전 서버를 만들고 새 버전의 `pg_dump`로 옛 서버를 떠서 넣는다. 가장 단순하고 확실하지만, 덤프와 복원이 끝날 때까지 쓰기를 멈춰야 한다. 위 실험의 속도로 보면 수십 GB 이하일 때 현실적이다.

둘째, `pg_upgrade`. 데이터 파일은 그대로 두고 시스템 카탈로그만 새 형식으로 옮긴다. 기본은 파일을 복사(`--copy`)해서 데이터 크기에 비례해 걸리지만, `--link`를 주면 하드 링크를 만들어 수백 GB도 몇 분 안에 끝난다. 대신 `--link`로 새 서버를 한 번 띄우면 옛 서버는 다시 쓸 수 없으니, 그 전에 백업이 있어야 한다. Ubuntu에서는 PGDG 저장소로 새 버전을 설치한 뒤 `pg_upgradecluster`가 이 과정을 감싸 준다. 이 컨테이너에는 16만 설치되어 있어 실제로 돌리지는 못했고, 흐름은 이렇다.

```bash
# 예: 16 → 17 (PGDG 저장소에서 postgresql-17을 설치한 뒤). 실제 실행 결과는 싣지 않았다
sudo pg_dropcluster 17 main --stop        # 설치 때 자동으로 생긴 빈 17 클러스터 제거
sudo pg_upgradecluster -m link 16 main    # 내부에서 pg_upgrade --link 실행, 포트도 넘겨받는다

# pg_upgrade를 직접 쓸 때는 먼저 --check로 호환성만 검사한다
sudo -u postgres /usr/lib/postgresql/17/bin/pg_upgrade --check \
  -b /usr/lib/postgresql/16/bin -B /usr/lib/postgresql/17/bin \
  -d /var/lib/postgresql/16/main -D /var/lib/postgresql/17/main \
  -o "-c config_file=/etc/postgresql/16/main/postgresql.conf" \
  -O "-c config_file=/etc/postgresql/17/main/postgresql.conf"

# 업그레이드 뒤 통계 다시 모으기 (pg_upgrade는 17까지 플래너 통계를 옮기지 않는다)
sudo -u postgres vacuumdb --all --analyze-in-stages
```

업그레이드 직후 통계가 비어 있으면 플래너가 엉뚱한 계획을 고른다. `--analyze-in-stages`는 표본을 작게 해서 빨리 한 번, 점점 크게 다시 모아 서비스를 빨리 정상 계획으로 돌려놓는다. 18부터는 `pg_upgrade`가 통계를 옮겨 준다고 하니 쓰는 버전의 노트에서 확인한다. 확장(PostGIS, pg_repack 등)은 새 버전용 패키지가 먼저 설치되어 있어야 한다.

셋째, 논리 복제. 새 버전 서버를 만들고 옛 서버를 발행자(`CREATE PUBLICATION`), 새 서버를 구독자(`CREATE SUBSCRIPTION`)로 묶어 데이터를 따라오게 한 뒤, 거의 따라왔을 때 쓰기를 잠깐 멈추고 앱을 새 서버로 돌린다. 중단 시간이 몇 초~몇 분이다. 대신 `wal_level = logical`(재시작 필요)이어야 하고, 스키마 변경(DDL)과 시퀀스 값은 복제되지 않아 따로 맞추며, 기본 키가 없는 테이블은 `UPDATE`/`DELETE`를 복제하려면 `REPLICA IDENTITY`를 정해야 한다. 준비할 게 가장 많은 방법이다.

## 마이너 업데이트

16.14에서 16.15 같은 마이너 업데이트는 버그와 보안 수정만 들어 있고 데이터 형식이 같다. 패키지를 올리고 재시작하면 끝이다. 미룰 이유가 거의 없다.

```bash
# 지금 버전 확인 → 업데이트 → 재시작 → 확인
sudo -u postgres psql -c "SELECT version();"
sudo apt update && sudo apt install --only-upgrade postgresql-16
sudo systemctl restart postgresql@16-main
sudo -u postgres psql -c "SELECT version();"
```

재시작이 끊김을 만드니 점검 시간에 하고, 복제본이 있으면 복제본부터 올린 뒤 전환(switchover)하는 순서로 끊김을 줄인다. 릴리스 노트는 꼭 읽는다. 가끔 "이 버그의 영향을 받은 인덱스는 다시 만들라"는 안내가 들어 있다.

## 관리형 서비스를 쓴다면

Amazon RDS·Aurora, Google Cloud SQL, Azure Database for PostgreSQL을 쓰면 이 글의 많은 부분을 서비스가 대신한다. 자동 백업과 PITR은 콘솔에서 시각을 고르면 새 인스턴스로 복원되고, 마이너 업데이트는 점검 시간에 자동으로, 장애 조치는 대기 인스턴스로 몇십 초~몇 분 안에 넘어간다. 대신 슈퍼유저가 없어 일부 확장과 설정을 못 쓰고, 설정은 `ALTER SYSTEM`이 아니라 파라미터 그룹(플래그)으로 바꾸며, 데이터 디렉터리와 OS에 접근할 수 없어 장애 원인을 깊이 보기 어렵고, 같은 사양의 직접 운영보다 비용이 높다. 그래도 메모리·연결 수 계산, 모니터링, VACUUM과 XID 나이, 업그레이드 전략, 복원 연습은 관리형에서도 그대로 사람이 할 일이다.

## 운영에 올리기 전 점검

처음 질문으로 돌아가 운영 전날 할 일을 순서대로 적으면 이렇다. 먼저 재시작이 필요한 설정을 정한다. `shared_buffers`는 램의 25%(32GB면 8GB), `max_connections`는 풀 크기 합에 여유를 더한 정도, `wal_level`은 복제와 PITR을 생각해 `replica` 이상, `archive_mode = on`, 확장은 `shared_preload_libraries = auto_explain, pg_stat_statements`. 재시작해서 한 번에 적용하고 `pending_restart`가 없는지 본다. 다음으로 `work_mem`은 위 계산으로 최악 예산이 램을 넘지 않게, `random_page_cost`는 SSD면 1.1로, `effective_cache_size`는 램의 70% 정도로, autovacuum은 큰 테이블에 테이블별 기준을 건다. 앱 앞에 연결 풀을 두고 역할에 `statement_timeout`과 `idle_in_transaction_session_timeout`을 건다. 로그에는 `log_min_duration_statement`, `log_lock_waits`, `log_autovacuum_min_duration`, 그리고 기본으로 켜진 `log_checkpoints`가 남게 한다. 모니터링에는 캐시 적중률, 활성 연결과 대기 이벤트, 임시 파일, `n_dead_tup`, `age(datfrozenxid)`, 복제 지연, 디스크와 `pg_wal` 크기, `pg_stat_archiver.failed_count`를 건다. 백업은 베이스 백업 + WAL 보관을 다른 장소에 두고, 오픈 전에 한 번은 실제로 다른 서버에 시점 복원을 해 본다. 마지막으로 업그레이드 계획을 적어 둔다. 지금 버전의 지원 종료일, 쓸 방법(`pg_upgrade --link`인지 논리 복제인지), 그리고 그 방법을 연습할 스테이징 서버다.

PostgreSQL 운영은 결국 이 시리즈에서 본 구조를 숫자로 지켜보는 일이다. 연결은 프로세스이니 풀로 묶고, 메모리는 곱하기로 예산을 잡고, WAL은 복구와 백업의 재료이니 보관하고, 죽은 행과 XID 나이는 VACUUM이 따라가는지 본다. 그리고 백업은 복원해 본 것만 믿는다.

## 면접에서 나올 만한 질문

### 설정을 바꿨는데 반영이 안 된다. 무엇을 확인하나

먼저 `pg_settings`에서 그 설정의 `context`와 `pending_restart`를 본다. `postmaster`면 재시작해야 하고, `sighup`이면 `pg_reload_conf()`가 필요하다. 그다음 `pg_file_settings`로 어느 파일의 몇 번째 줄이 적용됐는지 본다. `ALTER SYSTEM`이 쓴 `postgresql.auto.conf`가 `postgresql.conf`보다 우선이라, 거기에 남은 옛 값이 이기고 있는 경우가 흔하다.

### shared_buffers, work_mem, max_connections를 어떻게 정하나

`shared_buffers`는 OS 페이지 캐시와 나눠 쓰는 설계라 램의 25% 안팎에서 시작한다. `work_mem`은 정렬·해시 노드 하나당 한도이고 병렬 worker와 `hash_mem_multiplier`까지 곱해지니, 연결 수와 곱한 최악 예산이 램을 넘지 않게 정하고 큰 쿼리에만 `SET LOCAL`로 올린다. `max_connections`는 크게 올리지 않고 연결 풀로 묶은 뒤, 풀 크기 합에 관리용 여유를 더한 만큼만 둔다.

### PgBouncer transaction 모드에서 조심할 점은

트랜잭션이 끝나면 DB 연결이 다른 클라이언트에게 가니, 세션에 붙는 상태가 깨진다. 세션 단위 `SET`, 임시 테이블, `LISTEN`, 세션 advisory lock, `WITH HOLD` 커서를 쓰면 안 된다. prepared statement는 PgBouncer 1.21 이상에서 `max_prepared_statements`를 켜야 한다. 이런 기능이 필요한 연결은 PgBouncer를 거치지 않게 따로 둔다.

### pg_dump와 pg_basebackup의 차이는

`pg_dump`는 DB 하나를 논리적으로 꺼내는 백업이라 다른 버전으로 옮기거나 테이블 하나만 복원할 수 있지만, 백업한 순간으로만 돌아가고 큰 DB는 복원이 느리다. 역할은 `pg_dumpall --globals-only`로 따로 받아야 한다. `pg_basebackup`은 클러스터 전체 파일을 복사하는 물리 백업이라 같은 메이저 버전에서만 쓸 수 있지만, 보관된 WAL과 합치면 백업 이후 아무 시점으로나 복원할 수 있다.

### PITR은 어떻게 동작하나

베이스 백업을 새 디렉터리에 풀고 `recovery.signal`과 `restore_command`, `recovery_target_time`을 둔 뒤 띄우면, 백업의 체크포인트부터 보관된 WAL을 차례로 재생한다. 목표 시각 이후의 첫 커밋 앞에서 멈추고(기본 pause), 확인한 뒤 `pg_wal_replay_resume()`으로 승격하면 새 타임라인으로 갈라진다. 실습에서는 WHERE 없는 `DELETE` 커밋 직전에 멈춰 200만 행을 되살렸다. 운영 서버를 덮어쓰지 말고 옆에서 복원해 필요한 데이터만 옮기는 게 안전하다.

### WAL 보관이 실패하면 어떤 일이 생기나

PostgreSQL은 보관에 성공하지 못한 세그먼트를 지우지 않고 계속 재시도한다. 그래서 `pg_wal`이 계속 커지고, 결국 디스크가 가득 차면 DB가 멈춘다. PITR도 끊긴 지점 이후로는 불가능해진다. `pg_stat_archiver`의 `failed_count`와 `last_archived_time`, `pg_wal` 크기를 알림에 걸어 둬야 한다.

### 메이저 버전 업그레이드 방법은 무엇이 있고 어떻게 고르나

데이터가 작고 중단 시간을 감당할 수 있으면 `pg_dump`/`pg_restore`가 가장 단순하다. 큰 DB에서 몇 분 정도 멈출 수 있으면 `pg_upgrade --link`가 빠르지만, 새 서버를 띄운 뒤에는 옛 서버로 못 돌아가니 백업이 먼저다. 중단을 몇 초로 줄여야 하면 논리 복제로 새 서버를 따라오게 한 뒤 전환하는데, DDL과 시퀀스를 따로 맞추고 `REPLICA IDENTITY`를 챙겨야 한다. 어느 방법이든 업그레이드 뒤 `vacuumdb --analyze-in-stages`로 통계를 다시 모은다(17까지).

### 백업이 잘 되고 있는지 어떻게 보장하나

백업 작업의 성공 여부와 WAL 보관 실패를 매일 알림으로 받고, 정기적으로 다른 서버에 실제로 복원해 띄워 데이터를 확인하고 걸린 시간을 잰다. `pg_verifybackup`은 파일이 빠지거나 깨졌는지만 검사하니 복원 연습을 대신하지 못한다. 복제본은 실수로 지운 데이터도 그대로 복제하므로 백업이 아니다.
