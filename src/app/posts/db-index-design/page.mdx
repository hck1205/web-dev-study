관리자 화면에 결제 대기 주문 목록이 생겼다. `status`에 인덱스를 만들어 뒀는데 목록 한 번에 8ms가 걸리고, 실행 계획을 보면 힙을 6천 페이지 넘게 읽는다. 인덱스는 탔는데 왜 이렇게 많이 읽을까. 같은 날 로그인 쪽에서는 `email`에 인덱스가 있는데도 테이블 전체를 읽는다는 보고가 올라온다.

인덱스를 하나 만드는 것만으로는 부족하고, 쿼리 모양에 맞는 인덱스를 골라야 한다. 인덱스가 B-tree로 어떻게 찾는지, 실행 계획을 어떻게 읽는지는 [인덱스 글](/posts/db-index)에서 봤다. 이 글은 그다음, 여러 컬럼을 묶는 순서, 힙까지 가지 않는 인덱스, 일부 행만 담는 인덱스, 함수 결과로 만드는 인덱스, 그리고 B-tree가 아닌 인덱스를 고르는 법을 다룬다. 찾아보기 비유는 앞 글과 같다. 기준은 Ubuntu 24.04의 PostgreSQL 16(16.15)이고, 실행 계획은 모두 이 환경에서 실제로 돌린 출력이다.

## 앞 글의 주문 100만 건 그대로

같은 쇼핑몰을 쓴다. 처음부터 따라 하려면 아래로 테이블을 만들고 회원 10만 명, 상품 1,000개, 주문 100만 건을 채운 뒤, 앞 글에서 만든 `user_id` 인덱스를 만들어 둔다.

```sql
-- 회원
CREATE TABLE users (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- 1, 2, 3 ... 자동 증가
  email      text NOT NULL,
  name       text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

-- 상품
CREATE TABLE products (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  text NOT NULL,
  price integer NOT NULL
);

-- 주문: 누가(user_id) 무엇을(product_id) 얼마에(amount) 샀나
CREATE TABLE orders (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    bigint NOT NULL REFERENCES users (id),
  product_id bigint NOT NULL REFERENCES products (id),
  status     text NOT NULL,          -- pending, paid, delivered, cancelled
  amount     integer NOT NULL,
  created_at timestamptz NOT NULL
);

INSERT INTO users (email, name, created_at) VALUES
  ('kim@example.com',  'kim',  '2025-10-01 09:00+09'),
  ('lee@example.com',  'lee',  '2025-10-02 10:30+09'),
  ('park@example.com', 'park', '2025-10-03 14:10+09');

INSERT INTO products (name, price) VALUES
  ('무선 이어폰', 39000),
  ('충전 케이스', 15000),
  ('이어팁', 5000);

INSERT INTO orders (user_id, product_id, status, amount, created_at) VALUES
  (1, 1, 'delivered', 39000, '2025-10-27 11:00+09'),
  (1, 3, 'delivered',  5000, '2025-10-27 11:00+09'),
  (2, 2, 'paid',      15000, '2025-10-28 20:15+09'),
  (3, 1, 'cancelled', 39000, '2025-10-29 08:40+09'),
  (1, 2, 'pending',   15000, '2025-10-30 23:05+09');

SELECT setseed(0.42);  -- random() 결과를 매번 같게 고정한다

-- 회원 4번 ~ 100000번
INSERT INTO users (email, name, created_at)
SELECT 'user' || i || '@example.com',
       'user' || i,
       timestamptz '2025-10-04 00:00+09' + i * interval '1 minute'
FROM generate_series(4, 100000) AS i;

-- 상품 4번 ~ 1000번
INSERT INTO products (name, price)
SELECT '상품 ' || i, (1 + floor(random() * 100)::int) * 1000
FROM generate_series(4, 1000) AS i;

-- 주문 6번 ~ 1000000번: 30초마다 한 건, 회원과 상품은 무작위
INSERT INTO orders (user_id, product_id, status, amount, created_at)
SELECT 1 + floor(random() * 100000)::bigint,
       1 + floor(random() * 1000)::bigint,
       CASE WHEN r < 0.80 THEN 'delivered'   -- 80%
            WHEN r < 0.94 THEN 'paid'        -- 14%
            WHEN r < 0.99 THEN 'cancelled'   -- 5%
            ELSE 'pending' END,              -- 1%
       (1 + floor(random() * 100)::int) * 1000,
       timestamptz '2025-10-31 00:00+09' + i * interval '30 seconds'
FROM (SELECT i, random() AS r FROM generate_series(6, 1000000) AS i) AS s;

VACUUM ANALYZE;  -- 통계를 모으고 정리한다

CREATE INDEX orders_user_id_idx ON orders (user_id);  -- 앞 글에서 만든 인덱스
```

주문 상태는 배송 완료가 80%, 결제 완료 14%, 취소 5%, 결제 대기 1%로 들어 있다. 주문은 2025년 10월 말부터 2026년 10월 13일까지 30초마다 한 건씩 시간 순서대로 쌓여 있다.

## 여러 컬럼 인덱스는 순서가 결과를 바꾼다

관리자 화면에 "결제 대기 중인 주문을 최근 순으로 20건" 보여 주는 목록이 생겼다. 대기 주문(`pending`)은 전체의 1%다.

```sql
SELECT id, user_id, amount, created_at FROM orders
WHERE status = 'pending' AND created_at >= '2026-10-06'
ORDER BY created_at DESC
LIMIT 20;
```

`status`에만 인덱스를 만들면 이렇게 나온다.

```sql
CREATE INDEX orders_status_idx ON orders (status);
```

```text
                                                                   QUERY PLAN
------------------------------------------------------------------------------------------------------------------------------------------------
 Limit  (cost=10077.97..10078.02 rows=20 width=28) (actual time=8.226..8.231 rows=20 loops=1)
   Buffers: shared hit=6226 read=11
   ->  Sort  (cost=10077.97..10078.51 rows=215 width=28) (actual time=8.224..8.227 rows=20 loops=1)
         Sort Key: created_at DESC
         Sort Method: top-N heapsort  Memory: 27kB
         Buffers: shared hit=6226 read=11
         ->  Bitmap Heap Scan on orders  (cost=119.98..10072.25 rows=215 width=28) (actual time=8.018..8.173 rows=213 loops=1)
               Recheck Cond: (status = 'pending'::text)
               Filter: (created_at >= '2026-10-06 00:00:00+09'::timestamp with time zone)
               Rows Removed by Filter: 9809

 Execution Time: 8.259 ms
(19 rows)
```

안쪽부터 읽는다. 인덱스로 대기 주문 10,022건을 찾고(`rows=10022`), 힙 6,223페이지를 읽어 날짜 조건으로 9,809건을 버린다(`Rows Removed by Filter`). 남은 213건을 정렬(`Sort`)해서 20건만 남긴다. 인덱스가 날짜를 모르니 날짜 거르기와 정렬을 모두 힙에서 한다.

두 컬럼을 묶은 복합 인덱스를 만든다. 순서는 `(status, created_at)`이다.

```sql
DROP INDEX orders_status_idx;
CREATE INDEX orders_status_created_idx ON orders (status, created_at);
```

```text
                                                                      QUERY PLAN
-------------------------------------------------------------------------------------------------------------------------------------------------------
 Limit  (cost=0.42..61.05 rows=20 width=28) (actual time=0.026..0.042 rows=20 loops=1)
   Buffers: shared hit=9 read=3
   ->  Index Scan Backward using orders_status_created_idx on orders  (cost=0.42..652.17 rows=215 width=28) (actual time=0.026..0.039 rows=20 loops=1)
         Index Cond: ((status = 'pending'::text) AND (created_at >= '2026-10-06 00:00:00+09'::timestamp with time zone))
         Buffers: shared hit=9 read=3
 Planning:
   Buffers: shared hit=19 read=1
 Planning Time: 0.209 ms
 Execution Time: 0.055 ms
(9 rows)
```

6,237페이지가 12페이지가 됐다. `Sort`도 사라졌다. 두 조건이 모두 `Index Cond`에 들어갔고, `Index Scan Backward`로 인덱스를 뒤에서부터 읽으며 20건을 채우자마자 멈췄다.

복합 인덱스는 첫 번째 컬럼으로 정렬하고, 첫 번째 값이 같은 것끼리는 두 번째 컬럼으로 정렬한다. 찾아보기로 치면 단어를 가나다순으로 늘어놓고, 같은 단어 안에서는 쪽수 순으로 적어 둔 것이다. 그래서 `pending`이면서 10월 6일 이후인 주문은 인덱스 안에서 한 덩어리로 붙어 있다. 아래 그림의 칸은 `(status, 날짜)`로 정렬된 인덱스의 잎 일부를 줄여 그린 것이다.

실제로 재 보면 차이가 숫자로 나온다. 기간을 한 달로 늘려 대기 주문 수를 센다. 두 인덱스를 하나씩 만들어 같은 쿼리를 돌렸다.

```sql
-- 최근 한 달 동안 들어온 결제 대기 주문 수 (결과 869건)
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders
WHERE status = 'pending' AND created_at >= '2026-09-13';
```

```text
-- (created_at, status) 인덱스
   ->  Index Only Scan using orders_created_status_idx on orders  (cost=0.42..2561.01 rows=928 width=0) (actual time=0.044..4.199 rows=869 loops=1)
         Index Cond: ((created_at >= '2026-09-13 00:00:00+09'::timestamp with time zone) AND (status = 'pending'::text))
         Heap Fetches: 0
         Buffers: shared hit=1 read=417

-- (status, created_at) 인덱스
   ->  Index Only Scan using orders_status_created_idx on orders  (cost=0.42..38.98 rows=928 width=0) (actual time=0.040..0.152 rows=869 loops=1)
         Index Cond: ((status = 'pending'::text) AND (created_at >= '2026-09-13 00:00:00+09'::timestamp with time zone))
         Heap Fetches: 0
         Buffers: shared hit=1 read=7
```

둘 다 `Index Cond`에 두 조건이 다 들어가 있어서 겉으로는 비슷해 보인다. 그런데 앞의 것은 한 달 치 주문 8만 7천 건의 인덱스 항목을 다 훑느라 418페이지를 읽었고, 뒤의 것은 8페이지를 읽었다. `Index Cond`에 조건이 들어갔다고 안심하지 말고 `Buffers`를 봐야 하는 이유다.

여기서 복합 인덱스의 규칙이 나온다. 같다(`=`)로 비교하는 컬럼을 앞에, 범위(`>=`, `BETWEEN`, `<`)로 비교하는 컬럼을 뒤에 둔다. 범위 조건이 걸린 컬럼 다음에 오는 컬럼은 인덱스 안에서 정렬 순서가 끊겨서 범위를 좁히는 데 못 쓴다. `ORDER BY`도 같은 원리라서 `WHERE status = ? ORDER BY created_at`은 `(status, created_at)` 인덱스가 정렬까지 해결한다.

반대 방향도 있다. 인덱스는 왼쪽 컬럼부터 차례로만 쓸 수 있다(leftmost prefix). `(status, created_at)` 인덱스는 `status`만 있는 조건에도 쓰이지만, `created_at`만 있는 조건에는 쓰이지 않는다. 찾아보기에서 단어를 모르고 쪽수만으로 찾을 수는 없는 것과 같다.

```sql
-- status 조건 없이 날짜만으로 찾는다
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders WHERE created_at >= '2026-10-12';
```

```text
                                                              QUERY PLAN
---------------------------------------------------------------------------------------------------------------------------------------
 Finalize Aggregate  (cost=15558.14..15558.15 rows=1 width=8) (actual time=40.249..45.426 rows=1 loops=1)
   Buffers: shared hit=9346
   ->  Gather  (cost=15557.92..15558.13 rows=2 width=8) (actual time=40.171..45.420 rows=3 loops=1)
         Workers Planned: 2
         Workers Launched: 2
         Buffers: shared hit=9346
         ->  Partial Aggregate  (cost=14557.92..14557.93 rows=1 width=8) (actual time=35.334..35.335 rows=1 loops=3)
               Buffers: shared hit=9346
               ->  Parallel Seq Scan on orders  (cost=0.00..14554.33 rows=1436 width=0) (actual time=35.142..35.267 rows=1174 loops=3)
                     Filter: (created_at >= '2026-10-12 00:00:00+09'::timestamp with time zone)
                     Rows Removed by Filter: 332160
                     Buffers: shared hit=9346
 Planning Time: 0.027 ms
 Execution Time: 45.445 ms
(14 rows)
```

다시 테이블 전체(9,346페이지)를 읽었다. 첫 컬럼의 값 종류가 적으면 각 값마다 건너뛰며 찾는 skip scan이라는 방법이 있는데, PostgreSQL은 18부터 B-tree에 들어갔고 16에는 없다. MySQL은 8.0.13부터 있다. 그래도 skip scan은 특수한 경우를 구제하는 장치라서, 자주 쓰는 조건이면 그 컬럼이 앞에 오는 인덱스를 따로 둔다.

복합 인덱스가 생기면 앞부분이 겹치는 단일 인덱스는 지워도 된다. `(status, created_at)`이 있으면 `(status)` 인덱스가 하던 일을 다 한다. 둘 다 두면 쓰기 비용만 두 번 낸다.

## 표까지 가지 않는 커버링 인덱스

이번에는 같은 조건에서 날짜와 금액을 가져온다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT created_at, amount FROM orders
WHERE status = 'pending' AND created_at >= '2026-09-13';
```

```text
                                                                QUERY PLAN
------------------------------------------------------------------------------------------------------------------------------------------
 Index Scan using orders_status_created_idx on orders  (cost=0.42..2692.58 rows=928 width=12) (actual time=0.008..0.681 rows=869 loops=1)
   Index Cond: ((status = 'pending'::text) AND (created_at >= '2026-09-13 00:00:00+09'::timestamp with time zone))
   Buffers: shared hit=545
 Planning:
   Buffers: shared hit=3
 Planning Time: 0.079 ms
 Execution Time: 0.732 ms
(7 rows)
```

`count(*)`일 때는 8페이지였는데 545페이지가 됐다. `amount`가 인덱스에 없어서 869건마다 힙을 찾아갔기 때문이다. 이럴 때 `INCLUDE`로 `amount`를 인덱스 잎에 같이 담는다.

```sql
-- 검색 키는 (status, created_at), 잎에는 amount도 함께 적어 둔다
CREATE INDEX orders_status_created_incl_idx
  ON orders (status, created_at) INCLUDE (amount);
```

```text
                                                                    QUERY PLAN
--------------------------------------------------------------------------------------------------------------------------------------------------
 Index Only Scan using orders_status_created_incl_idx on orders  (cost=0.42..42.98 rows=928 width=12) (actual time=0.163..0.342 rows=869 loops=1)
   Index Cond: ((status = 'pending'::text) AND (created_at >= '2026-09-13 00:00:00+09'::timestamp with time zone))
   Heap Fetches: 0
   Buffers: shared hit=1 read=7
 Planning:
   Buffers: shared hit=21 read=1
 Planning Time: 0.218 ms
 Execution Time: 0.405 ms
(8 rows)
```

545페이지가 8페이지로 줄었다. 쿼리에 필요한 컬럼을 모두 가진 인덱스를 커버링 인덱스라고 한다. 찾아보기에 쪽수만 적지 않고 짧은 설명까지 적어 두면 본문을 펼칠 필요가 없는 것과 같다. 위 출력은 새 인덱스를 처음 읽는 순간이라 `read=7`로 디스크에서 가져왔고, 그래서 시간은 오히려 조금 길게 나왔다. 같은 조건에서 비교하려면 이번에도 `Buffers`를 본다.

아래 그림에서 두 길을 비교해 보면 차이가 어디서 나는지 보인다. 왼쪽은 인덱스가 날짜까지만 알아서 금액을 가지러 힙에 869번 다녀오고, 오른쪽은 인덱스 잎에 금액이 함께 적혀 있어서 힙에 가지 않는다.

`INCLUDE` 컬럼은 잎에만 저장되고 정렬 기준에 들어가지 않는다. `(status, created_at, amount)`로 만들어도 Index Only Scan은 되지만, `amount`까지 정렬 키가 되면 중간 페이지에도 실려서 인덱스가 커진다. 정렬이나 검색에 쓰지 않는 컬럼은 `INCLUDE`가 맞다. 대가는 크기다.

```sql
SELECT indexrelname, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes WHERE relname = 'orders';
```

```text
          indexrelname          |  size
--------------------------------+---------
 orders_pkey                    | 21 MB
 orders_user_id_idx             | 9088 kB
 orders_status_created_idx      | 37 MB
 orders_status_created_incl_idx | 46 MB
(4 rows)
```

37MB가 46MB가 됐다. 컬럼을 계속 넣으면 인덱스가 테이블만큼 커진다. 자주 돌고 느린 쿼리 몇 개에만 쓴다. 비교가 끝났으니 `orders_status_created_incl_idx`는 지운다.

## 일부 줄만 담는 부분 인덱스

관리자 화면이 찾는 건 늘 `pending`뿐이다. 그런데 `(status, created_at)` 인덱스는 배송 완료된 주문 80만 건까지 다 담고 있다. 이럴 때 조건에 맞는 행만 담는 부분 인덱스(partial index)를 만든다.

```sql
-- status = 'pending'인 행만 담는다
CREATE INDEX orders_pending_created_idx
  ON orders (created_at) WHERE status = 'pending';

SELECT pg_size_pretty(pg_relation_size('orders_pending_created_idx'));
```

```text
 pg_size_pretty
----------------
 240 kB
(1 row)
```

37MB 대신 240kB다. 같은 쿼리는 이 인덱스를 탄다.

```text
 Aggregate  (cost=30.85..30.86 rows=1 width=8) (actual time=0.200..0.201 rows=1 loops=1)
   Buffers: shared hit=1 read=4
   ->  Index Only Scan using orders_pending_created_idx on orders  (cost=0.29..28.53 rows=928 width=0) (actual time=0.035..0.113 rows=869 loops=1)
         Index Cond: (created_at >= '2026-09-13 00:00:00+09'::timestamp with time zone)
         Heap Fetches: 0
         Buffers: shared hit=1 read=4
```

`Index Cond`에 status가 없다. 인덱스 자체가 이미 `pending`만 담고 있어서다. 인덱스가 작으니 다른 데이터와 함께 메모리에 머물기도 쉽고, `delivered` 주문이 들어오거나 바뀔 때는 이 인덱스를 고칠 필요도 없다.

조건이 쿼리와 맞아야만 쓰인다는 게 단점이다. `WHERE status = 'paid'`는 이 인덱스로 못 찾는다. 응용 코드가 `status = $1`처럼 값을 파라미터로 넘기면, 플래너가 값을 모르는 일반 계획에서는 부분 인덱스를 쓸지 판단하지 못할 수 있다. 부분 인덱스를 쓸 쿼리는 조건을 SQL에 그대로 적는 편이 안전하다. 비슷한 쓰임으로 `WHERE deleted_at IS NULL`(지우지 않은 행만)이나 "같은 회원의 대기 주문은 하나만" 같은 조건부 유니크 제약이 있다.

```sql
-- 회원마다 결제 대기 주문은 하나만 허용한다
CREATE UNIQUE INDEX orders_one_pending_per_user
  ON orders (user_id) WHERE status = 'pending';
```

```text
ERROR:  could not create unique index "orders_one_pending_per_user"
DETAIL:  Key (user_id)=(70593) is duplicated.
```

예제 데이터는 무작위로 만들어서 대기 주문이 두 건 이상인 회원이 483명 있다. 그래서 실패했다. 실제 서비스에서 이런 규칙을 걸 때도 기존 데이터가 규칙을 지키는지 먼저 확인한다. 비교가 끝났으니 `orders_pending_created_idx`도 지운다.

## 함수를 씌운 컬럼과 유니크 인덱스

로그인할 때 이메일을 대소문자 구분 없이 찾는다. `users.email`에 인덱스가 있는데도 이렇게 나온다.

```sql
CREATE INDEX users_email_idx ON users (email);

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, name FROM users WHERE lower(email) = 'kim@example.com';
```

```text
                                              QUERY PLAN
------------------------------------------------------------------------------------------------------
 Seq Scan on users  (cost=0.00..2435.00 rows=500 width=17) (actual time=0.225..28.330 rows=1 loops=1)
   Filter: (lower(email) = 'kim@example.com'::text)
   Rows Removed by Filter: 99999
   Buffers: shared hit=935
 Planning:
   Buffers: shared hit=34 read=1
 Planning Time: 0.166 ms
 Execution Time: 28.372 ms
(8 rows)
```

인덱스는 `email` 원래 값으로 정렬돼 있다. `lower(email)`의 결과는 인덱스에 없으니, 행마다 `lower()`를 계산해서 비교할 수밖에 없다. 찾아보기는 "Kim"으로 정리돼 있는데 "kim"으로 찾으려는 것과 같다. 예상 행 수 `rows=500`은 플래너가 함수 결과의 통계를 몰라서 넣은 기본값(전체의 0.5%)이다.

해결은 함수 결과 자체로 인덱스를 만드는 식 인덱스(expression index)다. 대소문자만 다른 이메일로 두 번 가입하는 것도 막아야 하니 유니크로 만든다.

```sql
DROP INDEX users_email_idx;

-- lower(email) 값으로 정렬하고, 같은 값이 두 번 들어오지 못하게 한다
CREATE UNIQUE INDEX users_email_lower_key ON users (lower(email));
```

```text
                                                          QUERY PLAN
------------------------------------------------------------------------------------------------------------------------------
 Index Scan using users_email_lower_key on users  (cost=0.42..8.44 rows=1 width=17) (actual time=0.023..0.024 rows=1 loops=1)
   Index Cond: (lower(email) = 'kim@example.com'::text)
   Buffers: shared hit=1 read=3
 Planning:
   Buffers: shared hit=19 read=1
 Planning Time: 0.188 ms
 Execution Time: 0.041 ms
(7 rows)
```

```sql
-- 대소문자만 다른 이메일로 가입해 본다
INSERT INTO users (email, name) VALUES ('Kim@Example.com', 'kim2');
```

```text
ERROR:  duplicate key value violates unique constraint "users_email_lower_key"
DETAIL:  Key (lower(email))=(kim@example.com) already exists.
```

식 인덱스는 쿼리의 식이 인덱스의 식과 글자 그대로 같아야 쓰인다. `lower(email)`로 만들었으면 `upper(email)`이나 `lower(trim(email))`로는 못 찾는다. 식 인덱스를 만들면 `ANALYZE`가 그 식의 결과로도 통계를 모아서, 예상 행 수도 정확해진다.

유니크 인덱스는 값이 겹치지 않는다는 보장을 준다. `UNIQUE` 제약을 걸면 PostgreSQL이 내부적으로 유니크 인덱스를 만들고, 기본 키도 마찬가지다. 플래너는 "많아야 1행"이라는 사실을 알고 계획을 세운다. 하나 조심할 것은 NULL이다. 기본 동작에서 NULL끼리는 서로 다른 값으로 보기 때문에 NULL은 여러 개 들어간다. PostgreSQL 15부터는 `UNIQUE NULLS NOT DISTINCT`로 NULL도 하나만 허용할 수 있다.

## B-tree가 아닌 인덱스들

B-tree가 거의 모든 경우를 맡지만, 데이터 모양에 따라 더 맞는 인덱스가 있다.

해시 인덱스는 값의 해시만 저장해서 `=` 비교만 한다. 범위와 정렬은 못 하고, 유니크와 여러 컬럼도 안 된다. PostgreSQL 10부터 장애 복구에 안전해졌지만, 아주 긴 문자열을 같다로만 찾을 때 크기가 작다는 정도 말고는 B-tree보다 나은 경우가 드물다.

GIN은 값 하나가 여러 조각을 가진 데이터에 쓴다. 배열의 원소, `jsonb`의 키, 문서의 단어, 그리고 문자열을 세 글자씩 자른 조각(trigram)이다. B-tree가 못 하는 `'%kim%'` 같은 중간 일치 검색이 이걸로 된다. B-tree가 왜 못 하는지는 [인덱스가 안 타는 이유 글](/posts/db-index-pitfalls)에 있다.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

-- lower(email)을 세 글자 조각으로 잘라 색인한다
CREATE INDEX users_email_trgm_idx ON users USING gin (lower(email) gin_trgm_ops);

EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM users WHERE lower(email) LIKE '%kim%';
```

```text
                                                          QUERY PLAN
-------------------------------------------------------------------------------------------------------------------------------
 Bitmap Heap Scan on users  (cost=12.86..49.91 rows=10 width=8) (actual time=0.030..0.031 rows=1 loops=1)
   Recheck Cond: (lower(email) ~~ '%kim%'::text)
   Heap Blocks: exact=1
   Buffers: shared hit=4
   ->  Bitmap Index Scan on users_email_trgm_idx  (cost=0.00..12.86 rows=10 width=0) (actual time=0.020..0.020 rows=1 loops=1)
         Index Cond: (lower(email) ~~ '%kim%'::text)
         Buffers: shared hit=3
```

GIN 인덱스가 없을 때는 같은 쿼리가 Seq Scan으로 935페이지를 다 읽고 35ms가 걸렸다. GIN은 행 하나에 조각이 여러 개라 쓰기가 B-tree보다 무겁다. 검색이 중심인 컬럼에 쓴다.

BRIN은 반대로 아주 작은 인덱스다. 페이지 묶음(기본 128페이지)마다 최솟값과 최댓값만 적어 둔다. `orders.created_at`처럼 행이 들어온 순서와 값의 순서가 같은 컬럼에서 잘 맞는다.

```sql
CREATE INDEX orders_created_btree ON orders (created_at);
CREATE INDEX orders_created_brin  ON orders USING brin (created_at);

SELECT pg_size_pretty(pg_relation_size('orders_created_btree')) AS btree,
       pg_size_pretty(pg_relation_size('orders_created_brin'))  AS brin;
```

```text
 btree | brin
-------+-------
 21 MB | 24 kB
(1 row)
```

```sql
-- B-tree는 지우고 BRIN만 남긴 상태에서 하루 치 주문을 센다
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders
WHERE created_at >= '2026-10-12' AND created_at < '2026-10-13';
```

```text
 Aggregate  (cost=10039.92..10039.93 rows=1 width=8) (actual time=1.622..1.623 rows=1 loops=1)
   Buffers: shared hit=133
   ->  Bitmap Heap Scan on orders  (cost=12.71..10033.11 rows=2722 width=0) (actual time=1.011..1.458 rows=2880 loops=1)
         Recheck Cond: ((created_at >= '2026-10-12 00:00:00+09'::timestamp with time zone) AND (created_at < '2026-10-13 00:00:00+09'::timestamp with time zone))
         Rows Removed by Index Recheck: 10816
         Heap Blocks: lossy=128
         Buffers: shared hit=133
         ->  Bitmap Index Scan on orders_created_brin  (cost=0.00..12.03 rows=13514 width=0) (actual time=0.027..0.028 rows=1280 loops=1)
               Index Cond: ((created_at >= '2026-10-12 00:00:00+09'::timestamp with time zone) AND (created_at < '2026-10-13 00:00:00+09'::timestamp with time zone))
               Buffers: shared hit=5
```

`Heap Blocks: lossy=128`은 "이 128페이지 안에 있을 수도 있다"는 덩어리 하나를 통째로 읽었다는 뜻이다. 그래서 `Rows Removed by Index Recheck`로 1만 행을 다시 걸러 냈다. 정확하진 않지만 9,346페이지 대신 133페이지를 읽었고, 인덱스는 B-tree의 1천분의 1 크기다. 로그나 이벤트처럼 쌓이기만 하는 큰 테이블의 시간 컬럼에 맞다. 값이 들어온 순서와 상관없이 흩어진 컬럼(`user_id` 같은)에서는 모든 묶음의 범위가 넓어져 쓸모가 없다. 이 정렬 정도는 `pg_stats.correlation`으로 볼 수 있고, `created_at`은 1, `user_id`는 0.01이었다.

이 밖에 위치나 범위 겹침을 찾는 GiST와 SP-GiST가 있다. 지도 좌표, 예약 시간 겹침 같은 곳에 쓴다.

## 인덱스를 하나 더 만들자는 리뷰를 받았을 때

현장에서 인덱스는 대개 "이 쿼리가 느리니 인덱스를 추가하겠다"는 마이그레이션 리뷰로 들어온다. 그때 확인하는 순서가 있다.

먼저 이미 있는 인덱스로 해결되는지 본다. 테이블이 오래되면 누가 왜 만들었는지 모르는 인덱스가 쌓이고, 그중에는 다른 인덱스의 앞부분과 겹쳐서 할 일이 없는 것도 있다. 앞에서 본 것처럼 `(status, created_at)`이 있으면 `(status)`는 필요 없다. 시스템 카탈로그에서 이런 쌍을 찾을 수 있다. 아래는 `orders_status_idx`와 `orders_status_created_idx`를 둘 다 만들어 둔 상태에서 돌린 결과다.

```sql
-- 다른 인덱스의 앞부분과 컬럼이 똑같은 인덱스 (유니크, 부분, 식 인덱스는 뺀다)
SELECT a.indrelid::regclass AS table_name,
       a.indexrelid::regclass AS covered_index,
       b.indexrelid::regclass AS by_index,
       pg_size_pretty(pg_relation_size(a.indexrelid)) AS covered_size
FROM pg_index a
JOIN pg_index b
  ON a.indrelid = b.indrelid
 AND a.indexrelid <> b.indexrelid
 AND a.indnatts < b.indnatts
 AND (b.indkey::int2[])[0:a.indnatts - 1] = (a.indkey::int2[])[0:a.indnatts - 1]
WHERE NOT a.indisunique
  AND a.indpred IS NULL AND b.indpred IS NULL
  AND a.indexprs IS NULL AND b.indexprs IS NULL;
```

```text
 table_name |   covered_index   |         by_index          | covered_size
------------+-------------------+---------------------------+--------------
 orders     | orders_status_idx | orders_status_created_idx | 6888 kB
(1 row)
```

유니크 인덱스를 뺀 이유는 겹쳐도 제약 역할을 하기 때문이다. 겹치는 인덱스를 지우는 것만으로 쓰기 비용이 줄어든다.

다음은 컬럼의 값 분포다. 부분 인덱스를 쓸지, 복합 인덱스의 어느 자리에 둘지가 여기서 갈린다. `ANALYZE`가 모아 둔 통계를 보면 테이블을 세지 않고도 알 수 있다.

```sql
SELECT attname, n_distinct, most_common_vals, most_common_freqs, correlation
FROM pg_stats
WHERE tablename = 'orders' AND attname IN ('status', 'user_id', 'created_at')
ORDER BY attname;
```

```text
  attname   | n_distinct |          most_common_vals          |            most_common_freqs            | correlation
------------+------------+------------------------------------+-----------------------------------------+--------------
 created_at |         -1 |                                    |                                         |            1
 status     |          4 | {delivered,paid,cancelled,pending} | {0.7995,0.1417,0.048433334,0.010366667} |      0.66407
 user_id    |      90921 |                                    |                                         | -0.003412799
(3 rows)
```

`status`는 값이 4개뿐이고 `pending`이 1%다. 자주 찾는 값이 드물다면 그 값만 담는 부분 인덱스가 맞다. `n_distinct`가 `-1`인 `created_at`은 거의 모든 값이 다르다는 뜻이고(음수는 행 수에 대한 비율), `correlation`이 1이라 BRIN이 잘 맞는다. `user_id`는 상관관계가 0에 가까워서 BRIN은 쓸모가 없다. 통계는 표본으로 모으기 때문에 `ANALYZE`를 돌릴 때마다 이 값들이 조금씩 달라진다. 위 BRIN 절에서 `user_id`가 0.01로 나온 것도 그래서다.

마지막으로 그 쿼리가 얼마나 자주 도는지 본다. 하루 몇 번 도는 관리자 리포트를 위해 수정이 잦은 컬럼에 인덱스를 거는 건 손해일 수 있다. 인덱스를 만든 뒤에는 같은 쿼리의 `Buffers`가 실제로 줄었는지 확인하고, 몇 주 뒤 `pg_stat_user_indexes.idx_scan`으로 정말 쓰이는지 다시 본다. 인덱스가 쓰기에 매기는 값과 운영 중에 안전하게 만드는 방법은 [인덱스가 안 타는 이유 글](/posts/db-index-pitfalls)에 있다.

## 쿼리 모양에 맞춰 고른다

인덱스는 쿼리 모양에 맞을 때만 일한다. 같다로 비교하는 컬럼을 앞에, 범위와 정렬 컬럼을 뒤에 두면 찾는 행이 한 덩어리로 붙는다. 필요한 컬럼이 모두 인덱스에 있으면 힙을 건너뛰고, 자주 찾는 행이 일부뿐이면 그 행만 담아 작게 만든다. 컬럼에 함수를 씌워 찾는다면 그 함수 결과로 인덱스를 만든다. 값이 여러 조각으로 이루어졌으면 GIN, 들어온 순서대로 값이 커지면 BRIN이 B-tree보다 맞다. 어느 것이든 만든 뒤 `Buffers`가 줄었는지로 확인한다.

## 면접에서 나올 만한 질문

### 복합 인덱스의 컬럼 순서는 어떻게 정하나요?

같다로 비교하는 컬럼을 앞에, 범위로 비교하거나 정렬하는 컬럼을 뒤에 둔다. 복합 인덱스는 앞 컬럼 순으로 정렬되고 같은 값 안에서 다음 컬럼 순으로 정렬돼서, 이 순서여야 찾는 행이 한 덩어리로 붙는다. 예제에서 `(status, created_at)`은 8페이지, `(created_at, status)`는 418페이지를 읽었다. 그리고 왼쪽 컬럼부터만 쓸 수 있어서 `(status, created_at)`은 `created_at`만 있는 조건에는 쓰이지 않는다.

### 커버링 인덱스는 무엇이고, 언제 쓰나요?

쿼리에 필요한 컬럼이 전부 인덱스 안에 있어서 테이블(힙)을 읽지 않아도 되는 인덱스다. PostgreSQL에서는 `INCLUDE`로 검색 키가 아닌 컬럼을 잎에 담고, 실행 계획에 Index Only Scan으로 나온다. 다만 가시성 맵이 켜진 페이지만 힙을 건너뛰니 VACUUM이 잘 돌아야 하고, `Heap Fetches`로 확인한다. 인덱스가 커지니 자주 돌고 느린 쿼리에만 쓴다.

### 부분 인덱스는 언제 쓰나요?

자주 찾는 행이 테이블의 일부일 때 쓴다. 결제 대기 주문(전체의 1%)만 찾는다면 `WHERE status = 'pending'`인 행만 담아서, 예제에서 37MB 대신 240kB가 됐다. 인덱스가 작아 메모리에 머물기 쉽고, 조건에 맞지 않는 행이 바뀔 때는 고칠 필요도 없다. 대신 쿼리의 조건이 인덱스 조건과 맞아야만 쓰이고, 값을 파라미터로 넘기면 일반 계획에서 못 쓸 수 있다. 조건부 유니크 제약을 걸 때도 쓴다.

### lower(email)로 찾는 쿼리는 어떻게 빠르게 하나요?

`email` 인덱스는 원래 값으로 정렬돼 있어서 `lower(email)` 결과로는 찾을 수 없고, 행마다 함수를 계산하는 Seq Scan이 된다. 함수 결과 자체로 식 인덱스를 만든다(`CREATE UNIQUE INDEX ... ON users (lower(email))`). 유니크로 만들면 대소문자만 다른 이메일로 두 번 가입하는 것도 막는다. 쿼리의 식이 인덱스의 식과 글자 그대로 같아야 쓰인다.

### GIN과 BRIN은 언제 B-tree 대신 쓰나요?

GIN은 값 하나가 여러 조각으로 이루어진 데이터에 쓴다. 배열 원소, `jsonb` 키, 문서의 단어, `pg_trgm`의 세 글자 조각이 그렇고, `LIKE '%kim%'` 같은 중간 일치 검색이 된다. 대신 쓰기가 무겁다. BRIN은 페이지 묶음마다 최솟값과 최댓값만 적어서 아주 작다. 로그의 시간 컬럼처럼 들어온 순서와 값의 순서가 같을 때(`pg_stats.correlation`이 1에 가까울 때) 맞고, 값이 흩어진 컬럼에는 쓸모가 없다.
