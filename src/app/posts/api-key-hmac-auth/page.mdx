파트너사가 우리 주문 API를 직접 부르고 싶다고 연락이 왔다. 사람이 로그인하는 화면이 있는 게 아니라 파트너사의 배치 서버가 밤마다 주문을 밀어 넣는다. 로그인 페이지도, 리다이렉트도, 쿠키도 없다. 남은 질문은 하나다. 우리 서버는 들어온 요청이 정말 그 파트너가 보낸 것인지 무엇으로 확인할까.

선택지는 생각보다 여러 개다. 아이디·비밀번호를 헤더에 넣는 Basic 인증, 긴 무작위 문자열 하나를 주는 API 키, 요청 내용에 서명하게 하는 HMAC, 클라이언트 인증서를 쓰는 mTLS, 그리고 [OAuth](/posts/oauth)의 클라이언트 자격 증명 흐름. 이 글은 앞의 셋을 직접 만들어 보면서 각각 무엇을 막고 무엇을 못 막는지 확인하고, 마지막에 mTLS·OAuth와 나란히 놓고 고른다. 실험은 이 컨테이너(Node 22)에서 돌린 서버와 curl 출력이다.

## Basic 인증이 아직 남아 있는 자리

가장 오래된 방법부터 보자. Basic 인증은 `아이디:비밀번호`를 Base64로 바꿔 `Authorization` 헤더에 넣는다. curl의 `-u` 옵션이 그대로 해 준다.

```bash
# -u로 아이디와 비밀번호를 주면 curl이 Authorization 헤더를 만든다
curl -s -u partner-a:s3cret localhost:3001/basic

# 같은 값을 직접 만들어 보면
echo -n "partner-a:s3cret" | base64
```

```text
got: Basic cGFydG5lci1hOnMzY3JldA==
cGFydG5lci1hOnMzY3JldA==
```

Base64는 암호화가 아니라 글자를 바꿔 적는 방법일 뿐이다. 헤더를 본 사람은 누구나 되돌린다. 그래서 Basic 인증은 HTTPS 위에서만 쓴다. 그 조건만 지키면 생각보다 쓸 만한 자리가 있다. 사내 도구, 메트릭 수집 엔드포인트, 프록시가 붙여 주는 간단한 보호, 오래된 SOAP 연동이 그렇다. 표준이라 모든 HTTP 클라이언트가 지원하고 서버 구현도 몇 줄이면 된다.

약점은 구조에 있다. 매 요청마다 진짜 비밀번호가 그대로 간다. 로그를 남기는 프록시나 디버깅용 미들웨어가 헤더를 찍으면 비밀번호가 평문으로 남는다. 비밀번호가 사람이 외우는 값이면 [비밀번호 공격](/posts/password-attacks-credential-stuffing)의 대상이 되고, 서버는 매 요청마다 느린 해시로 검증해야 해서 비싸다. 브라우저에서 쓰면 로그아웃이 없다는 문제도 있는데, 서버 간 호출에서는 상관없다. 서버 간에는 사람이 외우는 비밀번호 대신 서버가 만든 긴 무작위 값을 주는 쪽이 낫고, 그게 API 키다.

## API 키 한 줄에 담는 것

API 키는 서버가 만들어 건네는 긴 무작위 문자열이다. 그냥 32바이트 무작위 값을 hex로 줘도 동작은 한다. 그런데 실무에서 쓰는 키는 보통 앞에 무언가 붙어 있다. 우리 주문 API 키를 이렇게 만들어 봤다.

```js
import { randomInt, createHash } from "node:crypto";
const B62 = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz";
const b62 = (n) => Array.from({ length: n }, () => B62[randomInt(62)]).join("");

function issueKey(env) {
  const id = b62(8);       // 찾기용 ID. 비밀이 아니다
  const secret = b62(32);  // 진짜 비밀
  return `ord_${env}_${id}_${secret}`;
}
```

```text
ord_live_bGHLRfYs_vlouxHASVF4RcmhOD5eBY0hmuS032M6J
entropy bits: 190.5
```

맨 앞의 `ord_`는 사람이 봐도, 기계가 봐도 "이건 우리 서비스 키"라고 알 수 있게 하는 접두사다. 이게 있으면 코드 저장소나 채팅에 키가 실수로 올라갔을 때 정규식 하나로 찾아낼 수 있다. GitHub 같은 코드 호스팅의 비밀 스캐닝도 서비스마다 정해진 접두사 패턴으로 유출된 키를 잡는다. 접두사 없는 hex 64자는 커밋 해시, 파일 체크섬과 구분이 안 된다.

길이는 비밀 부분으로 128비트 이상을 잡는다. 62진수 22자면 약 131비트, 32자면 약 190비트다. 무작위 값은 반드시 `crypto.randomBytes`나 `randomInt` 같은 암호학적 난수에서 뽑는다. `Math.random()`은 내부 상태가 출력에서 추측될 수 있어서 키 생성에 쓰면 안 된다.

## 평문으로 저장하지 않고 앞자리로 찾는다

키를 DB에 그대로 넣으면 DB 백업 하나, 읽기 전용 계정 하나만 새도 모든 파트너의 키가 한꺼번에 샌다. 공격자는 그 키로 바로 파트너인 척 요청한다. 비밀번호와 같은 이유로 키도 해시로 저장한다. 사용자에게는 발급 순간 딱 한 번 보여 주고, 그 뒤로는 우리도 원래 값을 모른다.

다른 점은 해시 종류다. 비밀번호는 사람이 고른 짧은 값이라 사전 대입이 되니 일부러 느린 해시(scrypt·bcrypt·Argon2id)를 쓴다. API 키의 비밀 부분은 190비트 무작위 값이라 사전이 없다. SHA-256 하나로 해시해 둬도 원래 값을 찾으려면 2의 190승 가지를 다 넣어 봐야 한다. 그리고 API 키는 요청마다 검증하니, 요청마다 100ms씩 쓰는 느린 해시는 처리량을 그대로 깎는다. 빠른 해시가 맞는 자리다. 해시 종류를 고르는 이유는 [해시와 비밀번호 저장](/posts/hash-hmac-password-hashing)에 더 자세히 있다.

```js
{
  key_id: 'bGHLRfYs',
  secret_sha256: '30bd8ebdfa19714d75031346c63c84f8b91506a3e0b21d05b59e4d5669eea475',
  last4: '2M6J'
}
```

찾는 방법이 문제다. 해시만 저장하면 "이 키가 누구 것인지"를 찾기 위해 들어온 키를 해시해서 인덱스로 조회해야 한다. 그래도 되지만, 키 ID를 따로 두면 조회가 더 깔끔하다. 키 ID로 한 줄을 찾고, 그 줄의 해시와 들어온 비밀의 해시를 [상수 시간 비교](/posts/hash-hmac-password-hashing)로 맞춰 본다. 키 ID로 찾았는데 없으면 바로 401이다.

```sql
-- API 키 테이블. 비밀은 해시로만 둔다
CREATE TABLE api_keys (
  key_id         text PRIMARY KEY,          -- 'bGHLRfYs'. 키 문자열 안의 공개 부분
  partner_id     bigint NOT NULL,
  secret_sha256  bytea  NOT NULL,           -- sha256(secret)
  last4          text   NOT NULL,           -- 관리 화면에 '…2M6J'로 보여 줄 값
  scopes         text[] NOT NULL,           -- '{orders:write}'
  created_at     timestamptz NOT NULL DEFAULT now(),
  expires_at     timestamptz,
  last_used_at   timestamptz,
  revoked_at     timestamptz
);
```

검증 함수는 이렇게 생긴다. 형식 검사 → 환경 확인 → 키 ID로 행 찾기 → 해시 비교 → 폐기 여부 순서다. 행이 없을 때도 가짜 해시와 비교해서, 키 ID가 있는지 없는지가 응답 시간으로 새지 않게 한다.

```js
const sha = (s) => createHash("sha256").update(s).digest();
const DUMMY = sha("dummy");

function verifyApiKey(raw) {
  const m = /^ord_(live|test)_([0-9A-Za-z]{8})_([0-9A-Za-z]{32})$/.exec(raw ?? "");
  if (!m) return { ok: false, error: "malformed_key" };
  const [, env, id, secret] = m;
  if (env !== ENV) return { ok: false, error: "wrong_environment" };
  const row = rows.get(id);                       // 실제로는 key_id로 DB 조회
  const match = timingSafeEqual(sha(secret), row?.hash ?? DUMMY);
  if (!row || !match || row.revokedAt) return { ok: false, error: "invalid_key" };
  return { ok: true, partner: row.partner, scopes: row.scopes };
}
```

맞는 키, 끝 글자 하나 틀린 키, 폐기된 키, 테스트 키, 엉뚱한 값을 넣어 봤다.

```text
ord_live_bGHLRfYs_vlou  {"ok":true,"partner":42,"scopes":["orders:write"]}
ord_live_bGHLRfYs_vlou  {"ok":false,"error":"invalid_key"}
ord_live_Q7hT2mXa_oldo  {"ok":false,"error":"invalid_key"}
ord_test_bGHLRfYs_vlou  {"ok":false,"error":"wrong_environment"}
Bearer abc              {"ok":false,"error":"malformed_key"}
```

틀린 키와 폐기된 키는 같은 `invalid_key`로 묶었다. 폐기됐다고 따로 알려 주면 공격자에게 "이 키는 한때 진짜였다"는 정보를 준다. 반면 환경이 틀렸다는 건 비밀과 무관한 정보라 자세히 알려 주는 편이 연동하는 사람에게 낫다.

`last4`는 관리 화면에서 "어느 키가 어느 키인지" 구분하는 용도다. 파트너가 "끝이 2M6J인 키를 끄고 싶다"고 말할 수 있게 한다. 앞의 `key_id`도 비슷한 역할을 하지만, 사용자는 끝자리로 기억하는 경우가 많다.

DB 유출에 더 대비하고 싶으면 SHA-256 대신 서버만 아는 키로 HMAC을 계산해 저장하기도 한다. DB만 털리고 서버 설정은 안 털렸다면 해시를 봐도 맞춰 볼 방법이 없다. 이 키는 [비밀 관리](/posts/secrets-management) 저장소에 둔다.

## 키마다 할 수 있는 일을 따로 정한다

키 하나에 모든 권한을 주면 키 하나가 새는 순간 모든 게 열린다. 키를 발급할 때 범위(scope)를 정한다. 주문을 넣는 배치 서버에는 `orders:write`만, 정산 대시보드에는 `settlements:read`만 준다. 서버는 인증이 끝난 뒤 그 요청이 키의 범위 안인지 한 번 더 본다. 인증이 통과해도 범위 밖이면 401이 아니라 403이다(누군지는 알지만 이 일은 못 한다).

키마다 따로 세는 것도 몇 가지 있다.

- 요청 수 한도. 파트너 하나가 실수로 무한 루프를 돌려도 다른 파트너가 영향을 받지 않게 키 ID를 한도의 키로 쓴다([요청 수 제한을 API에 붙이기](/posts/rate-limiting-in-practice)).
- 마지막 사용 시각. 90일 동안 한 번도 안 쓴 키는 꺼도 되는지 파트너에게 묻는다. 요청마다 DB에 쓰면 부하가 되니 몇 분에 한 번 모아서 쓴다.
- 허용 IP 대역. 파트너 배치 서버의 고정 IP를 받아 두면 키가 새도 다른 곳에서는 못 쓴다. 다만 파트너가 클라우드에서 IP가 바뀌는 환경이면 운영 부담이 크다.

로그에는 키 ID만 남긴다. 키 전체를 남기면 로그 시스템이 비밀 저장소가 된다. 요청 로깅 미들웨어가 `Authorization` 헤더를 찍지 않게 미리 막아 두는 것이 가장 흔하게 놓치는 부분이다.

## 키를 바꾸고 끊는 순서

키는 언젠가 바뀐다. 파트너 담당자가 퇴사하거나, 키가 저장소에 올라갔거나, 그냥 정해 둔 교체 주기가 와서다. 키가 하나뿐이면 교체하는 순간 파트너 서버가 멈춘다. 그래서 키를 계정당 두 개 이상 둘 수 있게 만든다.

교체는 겹치게 한다. 새 키를 발급하고, 파트너가 새 키로 배포하고, 우리 쪽에서 옛 키의 `last_used_at`이 멈춘 걸 확인한 다음, 옛 키를 폐기한다. 폐기는 행을 지우지 않고 `revoked_at`을 채운다. 나중에 "이 키로 무엇이 들어왔나"를 감사할 때 행이 남아 있어야 한다. [JWT 서명 키 교체](/posts/jwt-key-rotation)에서 게시·전환·퇴역으로 키를 겹쳐 두는 것과 같은 생각이다.

유출이면 겹칠 시간이 없다. 바로 폐기하고 새 키를 발급한다. 폐기가 즉시 효과를 내려면 키 검증 결과를 오래 캐시하지 않는다. 게이트웨이가 키 검증 결과를 10분 캐시하면 폐기해도 10분 동안 그 키가 통한다. 캐시를 쓴다면 폐기 이벤트로 캐시를 지우는 길을 함께 만든다.

## 키는 요청과 묶이지 않는다

API 키도 결국 Basic 인증과 같은 종류다. 요청마다 같은 비밀을 들고 간다. 누군가 그 값을 한 번 보면, 그 사람은 어떤 요청이든 마음대로 만들어 보낼 수 있다. 이런 값을 가진 사람이 곧 주인이 되는 증표를 bearer 자격 증명이라고 한다.

TLS가 전송 구간을 지켜 주니 보통은 충분하다. 그런데 TLS가 끝나는 지점이 생각보다 많다. 로드 밸런서, API 게이트웨이, 사내 프록시, 요청을 기록하는 APM 에이전트가 모두 헤더를 평문으로 본다. 그중 하나가 헤더를 로그에 남기면 키가 샌다. 그리고 요청 본문은 키와 아무 관계가 없어서, 중간에서 본문을 바꿔도 키는 여전히 유효하다.

이걸 바꾸는 방법이 요청 자체에 서명하는 것이다. 비밀은 보내지 않고, 비밀로 계산한 서명만 보낸다. 서명은 그 요청의 메서드·경로·본문·시각에 묶여 있어서, 서명을 훔쳐도 다른 요청에는 못 쓴다.

## 요청에 서명하기

HMAC 서명 요청의 생각은 단순하다. 보내는 쪽과 받는 쪽이 비밀 하나를 나눠 갖는다. 보내는 쪽은 요청에서 중요한 부분을 정해진 순서로 이어 붙인 문자열(정규 문자열)을 만들고, 그걸 비밀로 HMAC-SHA256 해서 헤더에 붙인다. 받는 쪽은 받은 요청으로 같은 문자열을 다시 만들고 같은 계산을 해서 맞춰 본다. HMAC이 무엇이고 왜 `sha256(key + msg)`가 아니라 HMAC이어야 하는지는 [해시와 HMAC](/posts/hash-hmac-password-hashing)에 있다.

이 실험에서 쓴 정규 문자열은 여섯 줄이다.

```text
POST
/v1/orders
channel=web&dry=false
1792760034
n-001
5d2fc70f93576c3347f25b51541151a9acfb5f1879400da4217bd0bb66e822e8
```

메서드, 경로, 정렬한 쿼리, 유닉스 시각(초), 요청마다 새로 만드는 무작위 값(nonce), 본문의 SHA-256이다. 본문을 통째로 넣지 않고 해시를 넣는 이유는 본문이 크거나 바이너리일 수 있어서다. 서명은 이렇게 보낸다.

```text
Authorization: HMAC-SHA256 KeyId=partner-a, Signature=<64자리 hex>
X-Timestamp: 1792760034
X-Nonce: n-001
```

받는 쪽은 순서가 중요하다. 싼 검사부터 하고 비싼 검사를 뒤에 둔다.

```js
// 1) 헤더 모양 확인 → 2) 키 ID로 비밀 찾기 → 3) 시각 범위 → 4) 서명 비교 → 5) nonce 중복
const secret = SECRETS.get(keyId);
if (!secret) return fail("invalid_signature");
if (Math.abs(Date.now() - ts * 1000) > 300_000) return fail("stale_timestamp");
const expected = createHmac("sha256", secret)
  .update(canonical(req.method, url.pathname, url.search, ts, nonce, body))
  .digest();
if (!timingSafeEqual(expected, Buffer.from(sig, "hex"))) return fail("invalid_signature");
if (seen.has(`${keyId}:${nonce}`)) return fail("replayed_nonce");
seen.set(`${keyId}:${nonce}`, Date.now() + 300_000);
```

서명을 만들어 주는 작은 스크립트로 요청을 다섯 번 보내 봤다.

```bash
# 정상 요청
curl -s -X POST 'localhost:3001/v1/orders?dry=false&channel=web' $H -d '{"sku":"A-100","qty":2}'
# 같은 헤더 그대로 한 번 더 (재전송)
# 서명은 qty:2로 만들고 본문은 qty:200으로 바꿔서 (변조)
# 10분 전 시각으로 서명해서 (오래된 요청)
# 쿼리 순서를 바꿔 서명해서 (정규화 확인)
```

```text
== valid
{"ok":true,"body":{"sku":"A-100","qty":2}}
== replay
{"error":"replayed_nonce"}
== tampered
{"error":"invalid_signature"}
== stale
{"error":"stale_timestamp"}
== query reorder
{"ok":true,"body":{"sku":"A-100","qty":2}}
```

본문에서 수량 하나를 바꾸자 서명이 맞지 않았다. 본문 해시가 서명 안에 들어 있기 때문이다. API 키였다면 이 요청은 통과했다. 아래 그림은 같은 흐름을 한 단계씩 보여 준다. 마지막 단계에서 공격자가 가로챈 요청을 그대로 다시 보낸다.

## 같은 요청을 다시 보내는 공격

서명만 있으면 변조는 막지만 재전송은 못 막는다. 공격자가 정상 요청 하나를 통째로 복사해 다시 보내면 서명도 그대로 맞는다. 주문 API라면 같은 주문이 두 번 들어간다.

시각과 nonce가 이걸 막는다. 시각은 서명 안에 들어 있어서 바꿀 수 없고, 서버는 지금과 5분 이상 차이 나면 거절한다. 그러면 재전송할 수 있는 시간이 5분으로 줄어든다. 그 5분 안의 재전송은 nonce로 막는다. 서버는 본 nonce를 5분 동안 기억하고 같은 값이 다시 오면 거절한다. 5분이 지난 nonce는 지워도 된다. 그 시각의 요청은 어차피 시각 검사에서 걸리기 때문이다. 두 검사가 서로 빈자리를 메운다.

서버가 여러 대면 nonce 저장소를 공유해야 한다. 서버마다 따로 기억하면 공격자가 다른 서버로 보내 통과한다. 보통 Redis에 `SET key 1 NX EX 300`으로 넣고, 이미 있으면 재전송으로 본다.

시각 범위를 너무 좁히면 시계가 어긋난 파트너 서버의 정상 요청이 거절된다. NTP가 멈춘 서버는 하루에 몇 초씩 밀리기도 한다. 5분 범위가 흔한 이유가 이것이고, 시계 차이로 401이 날 때 보는 법은 [시계 차이](/posts/clock-skew) 글에 있다. 재전송 방지가 있어도 네트워크 오류로 파트너가 새 nonce로 같은 주문을 다시 보내는 건 정상 재시도라서 막을 수 없다. 그건 인증이 아니라 [멱등성 키](/posts/idempotency-key)가 할 일이다.

웹훅 서명도 같은 구조다. 방향만 반대다. 우리가 보내는 쪽이 되고 파트너가 받는 쪽이 된다([웹훅](/posts/webhooks)).

## 정규화가 틀리면 맞는 서명도 틀린다

HMAC 서명 연동에서 가장 시간을 많이 잡아먹는 건 암호가 아니라 정규화다. 보내는 쪽과 받는 쪽이 한 글자라도 다르게 문자열을 만들면 서명이 맞지 않고, 서버는 그냥 401만 준다. 흔히 어긋나는 자리는 이렇다.

- 쿼리 순서. 보내는 쪽은 `dry=false&channel=web`, 받는 쪽 프레임워크는 `channel=web&dry=false`로 다시 조립한다. 그래서 키 이름으로 정렬해서 서명한다. 위 실험의 마지막 요청이 순서를 바꿔 보내도 통과한 이유다.
- 인코딩. 공백을 `%20`으로 할지 `+`로 할지, `/`를 인코딩할지, 대문자 hex(`%2F`)인지 소문자(`%2f`)인지.
- 본문. JSON을 서명한 뒤 HTTP 클라이언트가 다시 직렬화하면 공백과 키 순서가 바뀐다. 서명은 실제로 보낼 바이트로 한다.
- 경로. 끝 슬래시, 프록시가 붙이는 경로 접두사(`/api`), 대소문자.

정렬과 인코딩을 직접 짜 보자. 객체로 받은 쿼리를 키 이름으로 정렬하고, 키와 값을 `encodeURIComponent`로 인코딩해 `&`로 잇는다. 기대값은 node로 확인했다.

`sort()`는 UTF-16 코드 순서라 대문자가 소문자보다 앞에 온다. 양쪽이 같은 규칙만 쓰면 어느 쪽이든 상관없지만, 규칙을 문서에 정확히 적어야 한다. 그리고 `encodeURIComponent`는 `!'()*`를 인코딩하지 않는다. AWS SigV4처럼 RFC 3986 규칙대로 이 글자들까지 인코딩하라는 규격도 있어서, 남의 규격에 맞출 때는 이런 글자가 든 값으로 꼭 시험해 본다.

연동이 안 맞을 때는 서버가 만든 정규 문자열을 디버그 로그(운영이 아닌 곳)에 찍어서 파트너가 만든 것과 줄 단위로 비교하는 게 가장 빠르다. 서명값끼리 비교해서는 어디가 다른지 알 수 없다.

## AWS SigV4는 무엇을 더했나

AWS API의 서명 방식(Signature Version 4)도 같은 뼈대 위에 있다. 메서드·경로·쿼리·서명할 헤더 목록·본문 해시로 정규 요청을 만들고, 그 해시와 날짜·리전·서비스를 묶은 "서명할 문자열"을 HMAC-SHA256 한다. 여기에 두 가지가 더 있다.

하나는 서명할 헤더를 요청이 스스로 밝힌다는 것이다(`SignedHeaders=host;x-amz-date`). 프록시가 헤더를 더 붙여도 서명에 들어간 헤더만 보고 검증한다. 다른 하나는 비밀 키를 그대로 쓰지 않고 날짜·리전·서비스로 한 단계씩 HMAC을 거듭해 서명용 키를 뽑는다는 것이다.

```text
kDate    = HMAC("AWS4" + 비밀 키, "20150830")
kRegion  = HMAC(kDate, "us-east-1")
kService = HMAC(kRegion, "iam")
kSigning = HMAC(kService, "aws4_request")
```

AWS 문서의 예시 비밀 키(`wJalrXUtnFEMI/K7MDENG+bPxRfiCYEXAMPLEKEY`)로 이 연쇄를 node에서 계산하면 `c4afb1cc5771d871763a393e44b703571b55cc28424d1a5e86da6ed3c154a4b9`가 나온다. 이렇게 뽑은 키는 그날 그 리전 그 서비스에만 쓸 수 있다. 서명 키 하나가 새도 피해 범위가 좁고, 검증하는 쪽(예: 리전별 서비스)에 진짜 비밀 키 대신 파생 키만 내려 줄 수 있다.

직접 만드는 API라면 이 정도까지 갈 필요는 없다. 하지만 "서명할 헤더 목록을 명시한다"와 "비밀 키를 범위별로 파생한다"는 가져다 쓸 만한 생각이다. AWS에 요청을 보낼 때는 직접 구현하지 말고 SDK를 쓴다.

## 대가: 서버가 비밀 원본을 들고 있어야 한다

HMAC에는 API 키에 없는 비용이 하나 있다. 서버가 서명을 다시 계산하려면 비밀의 원래 값이 필요하다. API 키처럼 해시만 저장해 둘 수 없다. 서명을 검증하는 모든 서버가 모든 파트너의 비밀 원본을 읽을 수 있어야 하니, DB가 털리면 공격자가 파트너인 척 서명할 수 있다.

그래서 HMAC 비밀은 평문 컬럼이 아니라 KMS로 암호화해서 저장하고, 검증하는 서비스만 복호화 권한을 갖게 한다. 이 비대칭이 싫으면 공개 키 서명으로 간다. 파트너가 개인 키로 요청에 서명하고(Ed25519, ECDSA), 서버는 공개 키만 저장한다. 서버 DB가 털려도 서명을 만들 수 없다. 대신 파트너가 키 쌍을 관리해야 해서 연동 난도가 올라간다.

## mTLS, OAuth 클라이언트 자격 증명과 나란히 놓기

남은 두 선택지를 함께 놓고 보자.

mTLS는 TLS 연결을 맺을 때 클라이언트도 인증서를 내게 한다. 인증이 HTTP보다 아래, 연결 단계에서 끝난다. 비밀(개인 키)이 네트워크를 지나가지 않고, 연결 자체가 그 클라이언트에 묶인다. 대신 인증서 발급·갱신·폐기를 운영해야 하고, TLS를 중간에서 끊는 로드 밸런서가 있으면 클라이언트 인증서 정보를 헤더로 전달하는 설정이 필요하다. 금융권 연동이나 사내 서비스 사이에서 많이 쓴다. 구성과 인증서 교체는 [전송 구간 암호화](/posts/encryption-in-transit)에 있다.

OAuth 2.0 클라이언트 자격 증명 흐름은 파트너가 `client_id`와 `client_secret`으로 인가 서버에서 짧게 사는 액세스 토큰을 받아, 그 토큰으로 API를 부른다. API 키와 달리 매 요청에 들고 다니는 값이 몇 분~한 시간 뒤에 죽는다. 비밀은 토큰 발급 때만 지나가고, 권한 범위(scope)와 만료가 표준으로 정해져 있다. 인가 서버를 이미 운영하고 있거나 파트너가 많아 표준 도구로 붙이게 하고 싶을 때 맞다. 다만 토큰을 받는 왕복이 하나 더 생기고, 액세스 토큰도 결국 bearer라 요청 본문을 묶지는 못한다.

정리하면 이렇게 고른다. 파트너가 적고 빨리 열어야 하면 API 키로 시작한다. 해시 저장, 범위, 키별 한도, 교체 절차만 지켜도 대부분의 서비스에 충분하다. 결제나 정산처럼 요청 내용이 바뀌면 큰일 나는 API, TLS가 여러 번 끊기는 경로를 지나는 API라면 HMAC 서명을 더한다. 파트너가 많아지고 사용자 위임까지 생기면 OAuth로 옮기고, 망 단위로 신뢰를 묶고 싶으면 mTLS를 쓴다. 여럿을 겹쳐 쓰는 것도 흔하다. mTLS로 연결을 묶고 그 위에서 API 키로 파트너를 구분하는 식이다.

## 401이 나면 어디부터 보나

연동 첫날 파트너가 "401만 나와요"라고 하면 대개 아래 중 하나다.

1. 키 앞자리부터 본다. `ord_test_`로 운영 서버를 부르고 있지 않은지. 접두사로 환경을 나눠 두면 서버가 `wrong_environment`처럼 다른 에러를 줄 수 있다(키가 유효한지는 알려 주지 않는다).
2. 헤더가 도착했는지 본다. 프록시나 게이트웨이가 `Authorization` 헤더를 지우거나, 리다이렉트를 따라가는 HTTP 클라이언트가 다른 호스트로 갈 때 헤더를 버리는 경우가 있다.
3. 서명이면 시각을 본다. 파트너 서버의 `date -u`와 우리 서버의 시각을 맞춰 본다. `stale_timestamp`를 따로 돌려주면 이 단계가 바로 끝난다.
4. 정규 문자열을 줄 단위로 비교한다. 쿼리 순서, 인코딩, 본문 재직렬화, 경로 접두사가 가장 흔한 범인이다.
5. 범위를 본다. 인증은 통과하고 범위 밖이면 403이어야 한다. 401과 403을 섞어 쓰면 이 단계를 찾기 어렵다.

에러를 얼마나 자세히 돌려줄지는 저울질이다. 위 실험처럼 `stale_timestamp`와 `replayed_nonce`를 구분해 주면 연동이 훨씬 쉽다. 반면 "이 키 ID는 없다"와 "서명이 틀렸다"를 구분해 주면 공격자에게 키 ID가 유효한지 알려 준다. 시각·형식처럼 비밀과 상관없는 실패는 자세히, 키와 서명의 실패는 하나로 묶는 것이 무난하다.

## 마무리

서버 간 인증은 "요청마다 무엇을 들고 오게 하나"의 문제다. Basic 인증과 API 키는 비밀 자체를 들고 와서 간단하지만, 한 번 보면 누구나 쓸 수 있다. 그래서 API 키는 접두사와 충분한 길이로 만들고, 해시로 저장하고, 범위와 한도를 키마다 두고, 겹쳐서 교체한다. 요청 내용까지 지켜야 하면 비밀 대신 서명을 들고 오게 하는 HMAC으로 가고, 시각과 nonce로 재전송을 막고, 정규화 규칙을 양쪽이 똑같이 맞춘다. 그 대가로 서버가 비밀 원본을 지켜야 한다는 것까지 알고 고르면 된다.

## 면접에서 나올 만한 질문

### API 키를 왜 평문으로 저장하면 안 되나요?

DB 백업이나 읽기 권한 하나만 새도 모든 파트너의 키가 한꺼번에 새고, 공격자는 그 키로 바로 파트너인 척 요청할 수 있다. 그래서 발급할 때 한 번만 보여 주고 해시만 저장한다. 키 ID를 공개 부분으로 따로 두면 그 ID로 행을 찾고 해시를 상수 시간 비교로 맞춰 볼 수 있다.

### API 키는 bcrypt가 아니라 SHA-256으로 해시해도 되나요?

된다. 비밀번호는 사람이 고른 짧은 값이라 사전 대입을 늦추려고 느린 해시를 쓰지만, API 키는 128비트 이상의 무작위 값이라 사전이 없고 전수 탐색도 불가능하다. 그리고 요청마다 검증하니 느린 해시는 처리량을 그대로 깎는다. DB만 새는 상황까지 대비하려면 서버 비밀로 HMAC을 계산해 저장하는 방법도 있다.

### API 키 앞에 접두사를 붙이는 이유는 무엇인가요?

사람과 기계가 키의 출처와 환경을 바로 알아보게 하려는 것이다. 코드 저장소나 로그에 키가 올라갔을 때 정규식 하나로 찾을 수 있고, 비밀 스캐닝 도구도 접두사 패턴으로 유출을 잡는다. live와 test를 접두사로 나누면 운영 서버에 테스트 키를 넣는 실수를 서버가 바로 거절할 수 있다.

### HMAC 서명 요청은 API 키보다 무엇을 더 막나요?

API 키는 요청과 무관한 같은 값을 매번 보내서, 한 번 본 사람은 어떤 요청이든 만들 수 있고 본문을 바꿔도 키는 유효하다. HMAC은 비밀 대신 메서드·경로·쿼리·본문 해시·시각으로 만든 서명을 보내서, 서명을 훔쳐도 다른 요청에 쓸 수 없고 본문을 바꾸면 검증이 실패한다. 여기에 시각 범위와 nonce를 더해 재전송까지 막는다.

### 재전송 공격은 타임스탬프와 nonce로 어떻게 막나요?

시각은 서명 안에 있어 바꿀 수 없고, 서버는 지금과 5분 이상 차이 나면 거절해 재전송 가능한 시간을 5분으로 줄인다. 그 5분 안의 재전송은 nonce를 5분 동안 기억했다가 같은 값이 오면 거절해서 막는다. 5분이 지난 nonce는 시각 검사가 대신 막으니 지워도 된다. 서버가 여러 대면 nonce 저장소를 Redis처럼 공유해야 한다.

### HMAC 방식의 단점은 무엇인가요?

서버가 서명을 다시 계산하려면 비밀 원본이 필요해서 API 키처럼 해시로만 저장할 수 없다. 그래서 KMS로 암호화해 두고 검증 서비스만 복호화하게 한다. 그리고 정규화 규칙이 한 글자만 어긋나도 401이 나서 연동이 까다롭다. 서버에 비밀을 두기 싫으면 파트너가 개인 키로 서명하고 서버는 공개 키만 갖는 방식으로 간다.

### API 키와 OAuth 클라이언트 자격 증명은 언제 다르게 쓰나요?

API 키는 발급 하나로 바로 쓸 수 있어 파트너가 적고 빨리 열어야 할 때 맞다. 클라이언트 자격 증명은 client_secret으로 짧게 사는 액세스 토큰을 받아 쓰므로, 매 요청에 실리는 값이 금방 만료되고 범위와 만료가 표준으로 정해진다. 인가 서버를 이미 운영하거나 파트너가 많아 표준 도구로 붙이게 하고 싶을 때 고른다. 둘 다 bearer라 요청 본문을 묶지는 못한다.

### mTLS는 API 키나 HMAC과 무엇이 다른가요?

인증이 HTTP 헤더가 아니라 TLS 연결을 맺는 단계에서 끝나고, 개인 키는 네트워크를 지나가지 않는다. 연결이 그 클라이언트에 묶여서 헤더를 훔치는 공격이 통하지 않는다. 대신 인증서 발급·갱신·폐기 운영이 필요하고, TLS를 중간에서 끊는 로드 밸런서가 있으면 인증서 정보를 뒤로 전달하는 설정이 필요하다. 그래서 mTLS로 연결을 묶고 API 키로 파트너를 구분하는 식으로 겹쳐 쓰기도 한다.
