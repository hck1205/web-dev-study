아침에 보니 shop 네임스페이스의 Deployment `web`이 없다. `kubectl get events`는 한 시간이면 사라지고, 남은 이벤트에는 ReplicaSet과 Pod가 지워졌다는 말뿐이다. 누가 언제 어디서 지웠는지는 쿠버네티스 오브젝트 어디에도 남지 않는다. 그 답은 API 서버의 감사 로그(audit log)에만 있다. 감사 로그를 켜 두지 않았다면 답이 없다.

이 글은 감사 로그가 무엇을 어떤 단위로 남기는지, 정책의 네 가지 수준과 단계, 규칙이 고르는 순서, 파일과 웹훅 두 가지 백엔드를 보고, 실제 로그에서 jq로 "누가 지웠나"를 찾는다. 감사 로그가 Secret 값을 그대로 적어 버리는 실수와, 아무것도 안 해도 하루에 쌓이는 양도 직접 잰다.

출력은 [kwok 실습 클러스터](/posts/local-k8s-kind-minikube)(Kubernetes 1.37.0) 두 개에서 받았다. 하나는 실무형 정책, 하나는 모든 것을 RequestResponse로 남기는 정책이다. kwokctl의 `--kube-audit-policy`와 `--extra-args`로 API 서버에 감사 옵션을 넣었다.

이 주제의 다른 글: 감사 로그에 남는 인가 판단(`authorization.k8s.io/reason`)은 [RBAC 글](/posts/k8s-rbac)에서, 어드미션 정책이 감사 로그에 남기는 흔적의 출처는 [어드미션 컨트롤 글](/posts/k8s-admission-control)에서 다룬다. 앱 로그를 JSON으로 남기는 일반론은 [구조화 로깅 글](/posts/structured-logging)에 있다.

## 위에서부터 처음 맞는 규칙 하나

감사 정책은 규칙 목록이고, 요청마다 위에서부터 훑어 처음 맞는 규칙 하나의 수준을 쓴다. 맞는 규칙이 없으면 None이다. 실무형 정책으로 이렇게 썼다.

```yaml
apiVersion: audit.k8s.io/v1
kind: Policy
omitStages:
  - RequestReceived
rules:
  # 노이즈: 리더 선출 Lease, 헬스 체크는 남기지 않는다
  - level: None
    resources:
      - group: coordination.k8s.io
        resources: ["leases"]
  - level: None
    nonResourceURLs: ["/healthz*", "/livez*", "/readyz*", "/version"]
  # Secret·ConfigMap은 값이 남지 않게 Metadata까지만
  - level: Metadata
    resources:
      - group: ""
        resources: ["secrets", "configmaps"]
  # 읽기는 Metadata
  - level: Metadata
    verbs: ["get", "list", "watch"]
  # 나머지 쓰기는 요청 본문까지
  - level: Request
```

규칙의 순서가 결과를 바꾼다. Secret 규칙이 "나머지 쓰기는 Request"보다 위에 있어야 Secret 생성 본문이 남지 않는다. 아래 그림은 개발자가 Secret을 만드는 요청이 규칙을 하나씩 지나는 모습이다.

하위 리소스는 따로 맞춘다. `resources: ["pods"]`는 Pod 자체에만 맞고 `pods/exec`, `pods/log`에는 맞지 않는다. 일부러 `pods`를 RequestResponse, `*/log`를 Request, 나머지를 Metadata로 둔 정책으로 API 서버를 다시 띄우고 확인했다.

```bash
# Pod 조회, exec, logs를 한 번씩 보낸다 (kwok이라 exec와 logs는 실패한다)
kubectl get pod -n policy policy-webhook-5d8dfff77d-7s5ds
kubectl exec -n policy policy-webhook-5d8dfff77d-7s5ds -- ls
kubectl logs -n policy policy-webhook-5d8dfff77d-7s5ds

# 동사, 리소스, 하위 리소스별로 어떤 수준이 남았는지 센다
jq -r 'select(.objectRef.namespace=="policy" and .objectRef.resource=="pods")
  | [.verb, .objectRef.resource, (.objectRef.subresource // "-"), .level] | @tsv' audit.log | sort | uniq -c
```

```text
      2 create	pods	exec	Metadata
      2 get	pods	-	RequestResponse
      2 get	pods	exec	Metadata
      2 get	pods	log	Request
```

`pods` 규칙은 exec를 잡지 못했고, exec는 catch-all의 Metadata로 내려갔다. `*/log`는 `pods/log`에 맞았다. exec 요청은 `get`과 `create` 두 동사로 남는 것도 보인다. kubectl이 웹소켓 업그레이드를 먼저 시도하고 실패하면 다른 방식으로 다시 보내기 때문이다. "누가 운영 Pod에 exec했나"를 찾으려면 `subresource=="exec"`로 찾고, 동사는 거르지 않는다.

아래에서 이 매칭 규칙을 직접 짜 볼 수 있다. 규칙의 `users`, `userGroups`, `verbs`, `namespaces`, `resources`(그룹과 리소스, `*`, `*/하위`, `리소스/*`), `nonResourceURLs`(끝의 `*`는 접두사)를 지원한다. 리소스 조건이 있는 규칙은 경로 요청에 맞지 않고, 반대도 마찬가지다.

<CodePlayground
  caption="감사 정책: 이 요청은 어떤 수준으로 남나"
  functionName="auditLevel"
  initialCode={`function auditLevel(rules, req) {
  // rules: [{ level, users?, userGroups?, verbs?, namespaces?, resources?: [{ group, resources? }], nonResourceURLs? }]
  // req: 리소스 요청이면 { user, groups?, verb, group, resource, subresource?, namespace? }
  //      경로 요청이면 { user, verb, path }
  // 위에서부터 처음 맞는 규칙의 level, 없으면 "None"
  return "None";
}`}
  solution={`function auditLevel(rules, req) {
  const has = (list, v) => list.includes(v);
  const matchPath = (path, spec) =>
    spec === "*" || spec === path || (spec.endsWith("*") && path.startsWith(spec.slice(0, -1)));
  const matchResource = (r) => {
    if (!req.resource) return false;
    if (r.namespaces && !has(r.namespaces, req.namespace ?? "")) return false;
    if (!r.resources) return true;
    const combined = req.subresource ? req.resource + "/" + req.subresource : req.resource;
    return r.resources.some((gr) => gr.group === (req.group ?? "") && (!gr.resources || gr.resources.some((res) =>
      res === combined || res === "*" ||
      (req.subresource && res === "*/" + req.subresource) ||
      (res.endsWith("/*") && res.slice(0, -2) === req.resource))));
  };
  for (const r of rules) {
    if (r.users && !has(r.users, req.user)) continue;
    if (r.userGroups && !(req.groups || []).some((g) => has(r.userGroups, g))) continue;
    if (r.verbs && !has(r.verbs, req.verb)) continue;
    if (r.namespaces || r.resources) { if (matchResource(r)) return r.level; continue; }
    if (r.nonResourceURLs) {
      if (!req.resource && r.nonResourceURLs.some((s) => matchPath(req.path, s))) return r.level;
      continue;
    }
    return r.level;
  }
  return "None";

## Secret을 RequestResponse로 남기면

"일단 다 남기자"며 모든 요청을 RequestResponse로 남기는 정책을 걸면 어떻게 되는지 확인했다. 비밀번호가 든 Secret을 만들고 한 번 읽었다.

```bash
# DB 비밀번호 Secret을 만들고 읽는다
kubectl create secret generic pg-cred -n pay --from-literal=password='Tr0ub4dor&3'
kubectl get secret pg-cred -n pay -o yaml > /dev/null

# 비밀번호의 base64를 감사 로그에서 찾는다
echo -n 'Tr0ub4dor&3' | base64
jq -c 'select(.objectRef.name=="pg-cred") | {verb, level, req: .requestObject.data, resp: .responseObject.data}' audit.log
```

```text
VHIwdWI0ZG9yJjM=
{"verb":"create","level":"RequestResponse","req":{"password":"VHIwdWI0ZG9yJjM="},"resp":{"password":"VHIwdWI0ZG9yJjM="}}
{"verb":"get","level":"RequestResponse","req":null,"resp":{"password":"VHIwdWI0ZG9yJjM="}}
```

비밀번호가 요청 본문과 응답 본문에 두 번, 읽을 때 또 한 번 적혔다. base64는 암호가 아니니([Secret 글](/posts/k8s-secret) 참고) 평문이 남은 것과 같다. 이 클러스터는 웹훅 백엔드도 켜 두었다. Secret을 하나 더 만들고 수집기가 받은 이벤트를 파일로 저장해 보니 그 값도 그대로 들어 있었다. 외부 시스템으로도 나간 것이다.

이 로그는 Secret보다 훨씬 넓게 퍼진다. 감사 로그는 로그 수집 시스템으로 보내고, 보안 팀과 SRE가 검색하고, 오래 보관한다. etcd의 Secret을 [저장 시 암호화](/posts/encryption-at-rest)로 잠가 두고 RBAC으로 읽을 사람을 줄여도, 감사 로그를 볼 수 있는 사람은 그 모든 값을 본다. 한 번 새면 로그 보관 기간 동안 회수할 수 없으니 값을 교체하는 수밖에 없다.

그래서 실무형 정책의 앞부분은 늘 이렇다. `secrets`, `configmaps`(비밀이 섞여 들어오는 일이 잦다), `tokenreviews`와 `serviceaccounts/token`(토큰이 본문에 있다)은 Metadata로 먼저 잡는다. 실무형 정책 클러스터에서 같은 요청은 이렇게 남았다. 값이 없다.

```text
{"verb":"create","stage":"ResponseComplete","level":"Metadata","user":"kwok-admin","requestURI":"/api/v1/namespaces/pay/secrets?fieldManager=kubectl-create&fieldValidation=Strict","has_req":false,"code":201}
{"verb":"get","stage":"ResponseComplete","level":"Metadata","user":"kwok-admin","requestURI":"/api/v1/namespaces/pay/secrets/pg-cred","has_req":false,"code":200}
```

CRD로 비밀을 다루는 도구(External Secrets의 일부 리소스, cert-manager의 일부 리소스처럼 본문에 키가 들어가는 것)도 같은 이유로 확인한다. 로그 파일 자체의 권한도 본다. kwok이 만든 파일은 `-rw-r-----`(소유자 root)였다. 노드에 로그인할 수 있는 사람이 누구인지가 곧 감사 로그를 읽을 수 있는 사람이다.

## 아무것도 안 해도 쌓이는 로그

사람이 아무 요청도 보내지 않는 1분 동안 두 클러스터의 로그가 얼마나 늘어나는지 쟀다. 노드도 Pod도 거의 없는 kwok 클러스터다.

```bash
# 60초 동안 로그 크기와 줄 수가 얼마나 늘어나는지 잰다
a1=$(stat -c %s audit.log); l1=$(wc -l < audit.log); sleep 60
a2=$(stat -c %s audit.log); l2=$(wc -l < audit.log); echo "$((a2-a1)) bytes $((l2-l1)) events"
```

```text
실무형 정책:          56820 bytes 65 events
RequestResponse 정책: 386708 bytes 196 events
```

RequestResponse 정책 쪽에서 무엇이 쌓였는지 세 보니 대부분이 Lease 갱신이었다.

```text
     60 update	leases	ResponseComplete	kwok-admin
     60 update	leases	RequestReceived	kwok-admin
     12 get	/openapi/v3	ResponseComplete	system:apiserver
     12 get	/openapi/v3	RequestReceived	system:apiserver
```

컨트롤러 매니저와 스케줄러가 리더 자리를 지키려고 2초마다 Lease를 갱신한다. 1분에 60번, 단계 두 개씩이다. 실무형 정책은 Lease를 None으로, RequestReceived를 omitStages로 빼서 같은 시간에 7분의 1 정도만 남았다. 진짜 클러스터는 여기에 노드마다 10초에 한 번씩 노드 Lease 갱신이 더해지고, kube-proxy와 CNI, 모니터링 도구의 watch와 list가 붙는다. 노드 100대짜리 클러스터라면 노드 Lease만 1분에 600번이다.

로그 파일 백엔드는 회전(rotation) 옵션을 같이 정한다. 기본값을 1.37.0 도움말에서 확인했다.

```text
--audit-log-maxage int        ... Setting a value of 0 means old audit log files are not removed based on age. (default 366)
--audit-log-maxbackup int     The maximum number of old audit log files to retain. ... (default 100)
--audit-log-maxsize int       The maximum size in megabytes of the audit log file before it gets rotated. ... (default 100)
--audit-log-mode string       ... Known modes are batch,blocking,blocking-strict. (default "blocking")
```

기본값 그대로면 100MB 파일 100개, 10GB까지 컨트롤 플레인 노드 디스크에 쌓인다. 컨트롤 플레인 디스크가 차면 etcd가 먼저 멈춘다. 감사 로그 경로를 etcd 데이터와 다른 디스크(또는 별도 파티션)에 두거나, `maxbackup`을 줄이고 수집기로 빨리 내보낸다. `blocking` 모드는 이벤트를 다 쓴 뒤에 응답한다. 디스크가 느리면 API 요청 전체가 느려진다.

## 파일로 남길까, 웹훅으로 보낼까

백엔드는 두 가지다. 로그 백엔드(`--audit-log-path`)는 API 서버가 있는 노드의 파일에 쓰고, 웹훅 백엔드(`--audit-webhook-config-file`)는 kubeconfig 형식으로 적은 주소로 이벤트 묶음을 POST한다. 둘을 같이 켤 수 있다. 실습에서는 둘 다 켜고 `127.0.0.1:19644`에 수집기를 띄웠다.

```yaml
# 웹훅 백엔드 설정 (kubeconfig 형식)
apiVersion: v1
kind: Config
clusters:
  - name: audit-sink
    cluster:
      server: http://127.0.0.1:19644/audit
contexts:
  - name: default
    context:
      cluster: audit-sink
      user: ""
current-context: default
users: []
```

```bash
# kwok 클러스터를 감사 정책과 웹훅 백엔드를 켜고 만든다
kwokctl create cluster --name r9-aud --runtime binary \
  --kube-audit-policy ./naive-policy.yaml \
  --extra-args kube-apiserver=audit-webhook-config-file=$PWD/webhook-kubeconfig.yaml \
  --extra-args kube-apiserver=audit-webhook-batch-max-wait=5s
```

수집기는 받은 묶음의 크기만 기록했다. 클러스터가 뜨는 순간에는 400개씩 꽉 찬 묶음이 오고, 조용해지면 5초마다 작은 묶음이 온다. 400은 `--audit-webhook-batch-max-size`의 기본값이다.

## 지운 사람을 jq로 찾기

이제 처음 질문으로 돌아간다. 실무형 정책 클러스터에서 `dev` 그룹 인증서를 가진 `minsu`가 `web`을 지웠고, 관리자가 `--as=jiwoo`로 jiwoo 행세를 하며 ConfigMap 하나를 지웠다.

```bash
# web Deployment를 지운 요청을 찾는다
jq -c 'select(.verb=="delete" and .objectRef.resource=="deployments" and .objectRef.name=="web")
  | {time: .requestReceivedTimestamp, user: .user.username, groups: .user.groups, ip: .sourceIPs, ua: .userAgent, code: .responseStatus.code}' audit.log
```

```text
{"time":"2026-10-21T01:23:08.918894Z","user":"minsu","groups":["dev","system:authenticated"],"ip":["127.0.0.1"],"ua":"kubectl/v1.37.0 (linux/amd64) kubernetes/f54c212","code":200}
```

한 줄로 답이 나왔다. 같은 이벤트의 어노테이션에는 왜 지울 수 있었는지도 있다.

```text
"authorization.k8s.io/reason": "RBAC: allowed by RoleBinding \"dev-edit/shop\" of ClusterRole \"edit\" to Group \"dev\""
```

다음 할 일이 바로 보인다. dev 그룹 전체에 edit를 준 RoleBinding이 원인이니 그 바인딩을 좁힌다. 네임스페이스 하나에서 일어난 삭제를 시간순으로 보면 그림이 더 분명해진다.

```bash
# shop 네임스페이스의 삭제를 시간순으로 본다. 행세한 사용자도 함께
jq -r 'select(.verb=="delete" and .objectRef.namespace=="shop")
  | [.stageTimestamp, .user.username, (.impersonatedUser.username // "-"), .objectRef.resource, .objectRef.name, .responseStatus.code] | @tsv' audit.log
```

```text
2026-10-21T01:23:08.923152Z	minsu	-	deployments	web	200
2026-10-21T01:23:08.944125Z	kwok-admin	-	replicasets	web-5997c7558c	200
2026-10-21T01:23:08.962972Z	kwok-admin	-	pods	web-5997c7558c-58w8g	200
2026-10-21T01:23:08.965938Z	kwok-admin	-	pods	web-5997c7558c-wpzcv	200
2026-10-21T01:23:08.968645Z	kwok-admin	-	pods	web-5997c7558c-drnpv	200
2026-10-21T01:23:09.106930Z	kwok-admin	jiwoo	configmaps	feature-flags	200
```

두 가지를 읽어 낸다. 첫째, minsu의 삭제 하나 뒤에 ReplicaSet과 Pod 삭제가 줄줄이 따라왔다. 가비지 컬렉터가 소유 관계를 따라 지운 것이다. kwok은 컨트롤러 매니저가 관리자 인증서로 돌아서 `kwok-admin`으로 찍혔지만, 보통 클러스터에서는 `system:serviceaccount:kube-system:generic-garbage-collector`로 남는다. 범인을 찾을 때는 시스템 계정의 삭제를 걸러 내고 사람의 첫 삭제를 찾는다.

둘째, 마지막 줄은 `user`가 관리자, `impersonatedUser`가 jiwoo다. `kubectl --as`로 행세한 요청은 실제 인증된 사람과 행세한 사람이 둘 다 남는다. 인가는 jiwoo의 권한으로 했지만 책임은 관리자에게 있다. 행세 권한(`impersonate` 동사)을 가진 사람이 누구인지 함께 점검한다.

자주 쓰는 질문 몇 개를 더 적어 둔다.

```bash
# 거절된 요청: 누가 무엇을 하려다 막혔나
jq -r 'select(.responseStatus.code==403)
  | [.user.username, .verb, .objectRef.resource, .objectRef.namespace, .annotations["authorization.k8s.io/decision"]] | @tsv' audit.log

# 이 네임스페이스에 exec한 사람 (동사는 get, create 둘 다 나온다)
jq -r 'select(.objectRef.subresource=="exec" and .objectRef.namespace=="policy" and .stage=="ResponseComplete")
  | [.requestReceivedTimestamp, .user.username, .verb, .objectRef.name, .responseStatus.code] | @tsv' audit.log

# 사람이 Secret을 읽은 기록 (시스템 계정 제외)
jq -r 'select(.objectRef.resource=="secrets" and (.verb=="get" or .verb=="list")
  and (.user.username | startswith("system:") | not))
  | [.requestReceivedTimestamp, .user.username, .objectRef.namespace, .objectRef.name // "(list)"] | @tsv' audit.log
```

## 어드미션과 지연도 어노테이션으로 남는다

감사 이벤트의 `annotations`에는 인가 말고도 여러 구성 요소가 메모를 남긴다. 실습 로그에 나온 키를 모두 셌다.


## 관리형 클러스터에서 감사 로그를 켜는 곳

EKS, GKE, AKS에서는 API 서버 플래그를 직접 못 건드린다. 감사 정책도 클라우드가 정해 둔 것을 쓰고, 사용자는 내보낼지 말지를 고른다. EKS는 컨트롤 플레인 로깅에서 `audit` 로그 종류를 켜야 CloudWatch Logs로 나가고 기본은 꺼져 있다. GKE는 Cloud Audit Logs의 관리자 활동 로그가 기본으로 남고, 데이터 접근 로그는 따로 켠다. AKS는 진단 설정에서 `kube-audit` 또는 `kube-audit-admin` 범주를 고른다. 세부 이름과 기본값은 서비스마다 자주 바뀌니 쓰는 클라우드의 문서로 확인한다. 공통으로 기억할 것은 둘이다. 켜지 않으면 사고가 난 뒤에는 되돌려 볼 방법이 없고, 켜면 로그 저장 비용이 꽤 나온다. 쓰기만 남기는 범주(`kube-audit-admin`처럼)가 있으면 그것부터 켠다.

## 사고가 나기 전에 켜 두는 기록

감사 로그는 API 서버에 들어온 요청마다 누가, 언제, 어디서, 무엇을, 왜 허용됐는지를 남긴다. 정책은 위에서부터 처음 맞는 규칙 하나를 쓰므로 None으로 노이즈를 먼저 빼고, Secret처럼 값이 위험한 리소스를 Metadata로 잡은 다음, 읽기는 Metadata, 쓰기는 Request, 마지막에 catch-all을 둔다. RequestResponse는 응답 본문까지 적어서 비밀 값이 새고 로그 양이 폭발한다. 백엔드는 노드 파일과 웹훅을 함께 두고, `apiserver_audit_error_total`로 구멍을 감시한다. 이렇게 켜 둔 기록이 있으면 "누가 지웠나"는 jq 한 줄이다.

## 면접에서 나올 만한 질문

### 쿠버네티스 감사 로그는 무엇을 남기나

API 서버에 들어온 요청마다 사용자와 그룹, 동사, 대상 오브젝트, 출발 IP, user agent, 응답 코드, 인가 판단의 이유를 JSON 이벤트로 남긴다. 사람과 컨트롤러의 요청을 구분하지 않고 모두 남긴다. 정책 수준에 따라 요청 본문과 응답 본문이 더해진다. 쿠버네티스 Event는 금방 사라지고 행위자를 남기지 않으니, 누가 무엇을 했는지는 감사 로그로만 답한다.

### 네 가지 수준을 어떻게 나눠 쓰나

None은 노이즈(Lease 갱신, 헬스 체크)에, Metadata는 읽기와 Secret·ConfigMap·토큰 관련 리소스에, Request는 일반 쓰기에, RequestResponse는 결과까지 남겨야 하는 좁은 범위에 쓴다. 실습에서 ConfigMap 100개 목록 하나가 Metadata로는 837바이트, RequestResponse로는 14만 바이트였다. 읽기를 RequestResponse로 남기면 로그가 데이터보다 빨리 늘어난다.

### 감사 정책에서 규칙 순서가 왜 중요한가

요청마다 위에서부터 처음 맞는 규칙 하나만 쓰기 때문이다. Secret을 Metadata로 잡는 규칙이 '나머지 쓰기는 Request'보다 아래에 있으면 Secret 본문이 로그에 남는다. 맞는 규칙이 없으면 None이라 끝에 catch-all을 둔다. `pods` 규칙이 `pods/exec`에 맞지 않는 것처럼 하위 리소스도 따로 적어야 한다.

### omitStages에 RequestReceived를 넣는 이유는

RequestReceived는 처리 전에 남기는 단계라 결과가 없고, 같은 요청의 ResponseComplete가 그 내용을 모두 포함하기 때문이다. 빼면 짧은 요청의 이벤트가 두 개에서 하나로 줄어 로그 양이 절반 가까이 준다. watch나 exec 같은 long-running 요청은 ResponseStarted가 연결이 열렸다는 기록을 따로 남긴다.

### 로그 백엔드와 웹훅 백엔드는 어떻게 다르고, 왜 둘 다 켜나

로그 백엔드는 API 서버가 있는 노드의 파일에 쓰고 기본이 blocking이다. 웹훅 백엔드는 외부 수집기로 묶음을 POST하고 기본이 batch라 요청을 막지 않지만, 수집기가 죽으면 재시도 끝에 이벤트를 버리고 `apiserver_audit_error_total`만 남는다. API 서버가 여러 대면 파일이 노드마다 나뉘니 수집기로 모으고, 수집기 장애 동안의 기록은 파일로 메우려고 둘을 함께 켠다.

### 감사 로그에 Secret 값이 남았다. 어떻게 하나

먼저 값을 교체한다. 로그는 수집 시스템과 백업으로 퍼져 있어서 회수할 수 없다고 본다. 그다음 정책에서 secrets, configmaps, tokenreviews 같은 리소스를 Metadata로 잡는 규칙을 쓰기 규칙보다 위에 둔다. 감사 로그 자체에 접근할 수 있는 사람도 Secret을 읽을 수 있는 사람으로 보고 권한을 관리한다.

### 감사 로그에서 Deployment를 누가 지웠는지 어떻게 찾나

`verb=="delete"`와 objectRef의 리소스·네임스페이스·이름으로 이벤트를 찾아 `user`, `impersonatedUser`, `sourceIPs`, 시각을 본다. 같은 시각에 따라오는 ReplicaSet과 Pod 삭제는 가비지 컬렉터의 것이니 걸러 낸다. `kubectl --as`로 행세한 경우에는 실제 사람이 `user`에 남는다. `authorization.k8s.io/reason`에서 어떤 바인딩 덕분에 지울 수 있었는지도 보고 권한을 좁힌다.
