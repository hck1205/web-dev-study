  데이터를 매일 정리하는 프로그램도 이 두 가지 방식으로 나뉜다. 에어플로와 프리펙트는 할 일 목록 쪽에 가깝고, 대그스터는 결과 목록 쪽에 가깝다. 클라우드 회사가 대신 돌려 주는 서비스도 있는데, 편한 대신 그 회사 방식에 묶이고 쓴 만큼 돈을 낸다.

[Airflow 글](/posts/airflow-orchestration)에서 하루치 클릭을 광고별 비용으로 집계하는 DAG를 만들었다. 센서로 원본을 기다리고, 실패하면 재시도하고, 데이터 구간으로 날짜를 고르고, 백필로 지난주를 다시 돌렸다. 그 글을 읽고 팀 회의에 가져갔더니 질문이 나왔다. "우리 팀은 파이썬 함수 몇 개면 되는데 Airflow는 너무 무겁지 않나", "Dagster는 자산 중심이라던데 그게 뭐가 다른가", "그냥 AWS Glue 쓰면 안 되나".

이 글은 같은 파이프라인을 Prefect 3.9와 Dagster 1.13으로 다시 짜서 직접 돌려 보고, 오래된 Luigi 3.8도 잠깐 돌려 본다. 그다음 태스크 중심과 자산 중심이 백필을 어떻게 다르게 만드는지, 그리고 AWS Glue·Azure Data Factory·GCP Dataflow 같은 관리형 서비스가 어디까지 맡아 주는지를 비교한다. 실험은 Python 3.13 가상 환경에서 했고, 원본은 `raw/dt=2026-10-19`부터 `dt=2026-10-21`까지 날짜별 CSV 세 개, 결과는 DuckDB 파일에 쓴다.

DAG, 데이터 구간, 센서 모드, 재시도의 기본 개념은 Airflow 글에 있으니 여기서는 반복하지 않는다. 오케스트레이터가 순서를 잡아 주는 변환 작업 자체(ETL과 ELT 중 어디서 변환하나)는 [ETL과 ELT](/posts/etl-vs-elt)에, SQL 변환을 모델 단위로 관리하는 도구는 [dbt로 SQL 변환 관리하기](/posts/dbt-transformations)에 있다.

## 크론으로 충분하지 않은 순간

먼저 오케스트레이터가 왜 필요한지 한 번만 짚고 간다. 크론은 "이 시각에 이 명령을 실행한다"만 안다. 그래서 크론 위에 파이프라인을 올리면 다음을 직접 만들어야 한다.

- 앞 작업이 끝났는지 확인하고 시작하기(의존 관계)
- 실패한 단계만 다시 돌리기(재시도, 부분 재실행)
- 어느 날짜 작업이 성공했고 어느 날짜가 비었는지 보기(실행 이력)
- 지난 날짜를 범위로 다시 돌리기(백필)
- 실패하면 사람에게 알리기

이 중 두세 개가 필요해지면 셸 스크립트가 점점 오케스트레이터를 닮아 간다. 오케스트레이터는 이걸 표준 방식으로 제공하는 도구고, 도구마다 "파이프라인을 무엇으로 표현하나"가 다르다. 크론 자체의 함정(시간대, 겹치는 실행)은 [크론 잡](/posts/cron-jobs)에 따로 정리했다.

## Prefect: 파이썬 함수에 장식만 붙인다

Prefect는 "이미 있는 파이썬 코드를 거의 그대로 파이프라인으로"를 내세운다. 함수에 `@task`, 그 함수들을 부르는 함수에 `@flow`를 붙이면 끝이다. DAG를 따로 선언하지 않는다. 플로 함수가 실행되면서 태스크를 부르는 순서가 곧 의존 관계다.

```python
# prefect_flow.py
import csv, os, duckdb
from datetime import date, timedelta
from prefect import flow, task, get_run_logger
from prefect.runtime import task_run

BASE = os.path.dirname(os.path.abspath(__file__))

@task(retries=2, retry_delay_seconds=2)
def aggregate(day: str) -> dict:
    cost = {}
    with open(f"{BASE}/raw/dt={day}/clicks.csv") as f:
        for row in csv.DictReader(f):
            cost[row["ad_id"]] = cost.get(row["ad_id"], 0) + int(row["cost"])
    con = duckdb.connect(f"{BASE}/warehouse.duckdb")
    con.execute("CREATE TABLE IF NOT EXISTS ad_cost_daily (dt DATE, ad_id VARCHAR, cost BIGINT)")
    con.execute("DELETE FROM ad_cost_daily WHERE dt = ?", [day])   # 같은 날짜를 지우고 다시 쓴다
    con.executemany("INSERT INTO ad_cost_daily VALUES (?, ?, ?)",
                    [(day, k, v) for k, v in cost.items()])
    con.close()
    return {"dt": day, "ads": len(cost), "cost": sum(cost.values())}

@task(retries=2, retry_delay_seconds=2)
def report(summary: dict):
    if task_run.run_count == 1:              # 알림 API가 첫 시도에 시간 초과로 실패했다고 치자
        raise TimeoutError("notify API timed out")
    get_run_logger().info(f"report try={task_run.run_count} summary={summary}")

@flow(log_prints=True)
def clicks_daily(day: str | None = None):
    day = day or (date.today() - timedelta(days=1)).isoformat()
    s = aggregate(day)
    report(s)

if __name__ == "__main__":
    import sys
    clicks_daily(sys.argv[1] if len(sys.argv) > 1 else None)
```

이 구조가 Prefect의 특징이다. 코드는 내가 고른 곳(로컬, 컨테이너, 쿠버네티스 잡)에서 돌고, 서버는 상태와 일정만 관리한다. 일정을 붙이려면 플로에 `serve`나 `deploy`를 쓴다.

```python
# 매일 01:00(UTC)에 어제 날짜로 돌리는 배포를 띄운다. 이 프로세스가 살아 있는 동안 일정이 돈다
if __name__ == "__main__":
    clicks_daily.serve(name="daily", cron="0 1 * * *")
```

여기서 Airflow와 큰 차이가 하나 보인다. Prefect에는 Airflow의 데이터 구간처럼 "이 실행이 맡은 기간"이 기본 개념으로 묶여 있지 않다. 위 코드는 `date.today()`로 어제를 골랐다. 이러면 1시에 돌아야 할 실행이 서버 장애로 다음 날 돌면 엉뚱한 날짜를 처리한다. 예약된 시각은 `prefect.runtime.flow_run.scheduled_start_time`으로 읽을 수 있으니, 날짜는 그 값이나 명시적인 파라미터로 정하는 규칙을 팀이 직접 세워야 한다. 백필도 마찬가지로 "날짜 파라미터를 바꿔 실행을 여러 번 만든다"를 직접 한다.

대신 동적인 흐름은 쉽다. 플로가 그냥 파이썬이라 `if`로 분기하고, 실행 중에 받은 목록만큼 `for`로 태스크를 부를 수 있다. 파일 수가 날마다 다른 수집 작업, API 응답에 따라 갈라지는 작업처럼 실행 전에 모양을 정하기 어려운 파이프라인에서 Prefect가 편하다.

## Dagster: 만들 결과물을 먼저 적는다

Dagster는 질문을 바꾼다. "어떤 작업을 어떤 순서로 돌리나" 대신 "어떤 데이터가 있어야 하고, 그건 무엇으로 만드나"를 적는다. 이 데이터 하나하나를 자산(asset)이라 부르고, Dagster는 이걸 소프트웨어 정의 자산이라고 소개한다. 테이블, 파일, 모델처럼 오래 남는 결과물이 자산이다.

같은 파이프라인을 자산으로 쓰면 이렇다.

```python
# dagster_defs.py
import csv, os, duckdb
import dagster as dg

BASE = os.path.dirname(os.path.abspath(__file__))
daily = dg.DailyPartitionsDefinition(start_date="2026-10-19", end_date="2026-10-22")

@dg.asset(partitions_def=daily)
def raw_clicks(context: dg.AssetExecutionContext) -> list[dict]:
    day = context.partition_key                      # "2026-10-21" 같은 파티션 키
    with open(f"{BASE}/raw/dt={day}/clicks.csv") as f:
        return list(csv.DictReader(f))

@dg.asset(partitions_def=daily)
def ad_cost_daily(context: dg.AssetExecutionContext, raw_clicks: list[dict]) -> dg.MaterializeResult:
    day = context.partition_key
    cost = {}
    for row in raw_clicks:
        cost[row["ad_id"]] = cost.get(row["ad_id"], 0) + int(row["cost"])
    con = duckdb.connect(f"{BASE}/dagster_wh.duckdb")
    con.execute("CREATE TABLE IF NOT EXISTS ad_cost_daily (dt DATE, ad_id VARCHAR, cost BIGINT)")
    con.execute("DELETE FROM ad_cost_daily WHERE dt = ?", [day])
    con.executemany("INSERT INTO ad_cost_daily VALUES (?, ?, ?)",
                    [(day, k, v) for k, v in cost.items()])
    con.close()
    return dg.MaterializeResult(metadata={"ads": len(cost), "cost": sum(cost.values())})

@dg.asset_check(asset=ad_cost_daily)
def cost_not_negative() -> dg.AssetCheckResult:
    con = duckdb.connect(f"{BASE}/dagster_wh.duckdb", read_only=True)
    bad = con.execute("SELECT count(*) FROM ad_cost_daily WHERE cost < 0").fetchone()[0]
    return dg.AssetCheckResult(passed=bad == 0, metadata={"negative_rows": bad})

defs = dg.Definitions(assets=[raw_clicks, ad_cost_daily], asset_checks=[cost_not_negative])
```

의존 관계를 따로 적지 않았다. `ad_cost_daily` 함수의 인자 이름이 `raw_clicks`라서, Dagster는 "이 자산은 raw_clicks 자산으로 만든다"고 읽는다. 날짜는 파티션 키로 들어온다. 파티션 정의가 자산에 붙어 있으니, 자산 하나는 "날짜마다 한 칸씩 있는 표"처럼 관리된다. 이 칸 하나를 만드는 일을 머티리얼라이즈(materialize)라고 한다.

처음에 `ad_cost_daily`의 21일 칸만 만들어 봤다.

```bash
export DAGSTER_HOME=$PWD/.dagster
dagster asset materialize -f dagster_defs.py --select ad_cost_daily --partition 2026-10-21
```

로그 앞의 시각과 실행 id는 줄였다. 실패한 이유가 흥미롭다. `raw_clicks`가 반환한 값은 Dagster의 IO 매니저가 저장소(기본은 `DAGSTER_HOME/storage` 아래 피클 파일)에 저장하고, 다음 자산은 거기서 읽는다. 위쪽 자산의 21일 칸이 아직 없으니 읽을 게 없다. 자산끼리 값을 넘기는 방식은 Airflow의 XCom보다 자연스럽지만, 큰 데이터를 반환값으로 넘기면 그만큼 저장소에 쌓인다는 뜻이기도 하다. 실무에서는 큰 테이블을 반환하지 않고 웨어하우스에 직접 쓴 뒤 위치만 넘기거나, 웨어하우스용 IO 매니저를 쓴다.

## 자산 중심이면 백필이 빈칸 채우기가 된다

이제 이 글에서 가장 중요한 차이를 본다. 21일만 만든 상태에서 Dagster 인스턴스에 "어느 칸이 비었나"를 물었다.

```python
# status.py: 자산마다 만들어진 파티션과 빈 파티션을 센다
import dagster as dg
from dagster_defs import daily
inst = dg.DagsterInstance.get()
for key in ["raw_clicks", "ad_cost_daily"]:
    done = inst.get_materialized_partitions(dg.AssetKey(key))
    allp = daily.get_partition_keys()
    print(f"{key:14} done={sorted(done)} missing={[p for p in allp if p not in done]}")
```

```text
raw_clicks     done=['2026-10-21'] missing=['2026-10-19', '2026-10-20']
ad_cost_daily  done=['2026-10-21'] missing=['2026-10-19', '2026-10-20']
```

Dagster는 실행 기록이 아니라 자산의 칸을 기준으로 상태를 안다. 그래서 백필은 "비어 있는 칸을 채워라"가 된다. UI에서는 파티션 표에서 빈칸만 골라 백필을 띄울 수 있고, CLI로는 파티션마다 실행했다.

```bash
# 빈 파티션 두 개를 채운다
for p in 2026-10-19 2026-10-20; do
```

## Luigi가 먼저 했던 것

Dagster의 생각이 완전히 새로운 건 아니다. Spotify가 2012년에 공개한 Luigi는 태스크마다 `output()`으로 결과 파일을 정하고, 그 파일이 있으면 그 태스크는 끝난 것으로 봤다. 같은 집계를 Luigi 3.8로 짜서 두 번 돌려 봤다.

```python
# luigi_tasks.py
import csv, json, luigi

class RawClicks(luigi.ExternalTask):
    day = luigi.DateParameter()
    def output(self):
        return luigi.LocalTarget(f"raw/dt={self.day}/_SUCCESS")

class AdCostDaily(luigi.Task):
    day = luigi.DateParameter()
    def requires(self):
        return RawClicks(self.day)
    def output(self):                       # 결과 파일이 있으면 "이미 끝난 일"로 본다
        return luigi.LocalTarget(f"out/ad_cost/dt={self.day}.json")
    def run(self):
        cost = {}
        with open(f"raw/dt={self.day}/clicks.csv") as f:
            for row in csv.DictReader(f):
                cost[row["ad_id"]] = cost.get(row["ad_id"], 0) + int(row["cost"])
        with self.output().open("w") as f:   # 임시 파일에 쓰고 끝나면 이름을 바꾼다
            json.dump(cost, f)
```

```bash
python -m luigi --module luigi_tasks AdCostDaily --day 2026-10-21 --local-scheduler
```

두 번째는 결과 파일이 있으니 아무것도 돌리지 않았다. 결과물이 있으면 건너뛴다는 생각이 여기 있다. 그런데 Luigi는 "파일이 있나"만 본다. 원본이 고쳐져도 결과 파일이 있으면 다시 돌지 않으니, 다시 만들려면 사람이 파일을 지워야 한다. 그리고 Luigi에는 스케줄러가 없다. 중앙 스케줄러(`luigid`)는 같은 태스크가 두 번 돌지 않게 막고 진행을 보여 줄 뿐이고, 언제 시작할지는 결국 크론이 정한다. 실행 이력도 길게 남지 않는다. 그래서 새로 시작하는 팀이 Luigi를 고르는 경우는 드물고, 오래된 시스템에서 만나는 정도다.

Luigi가 남긴 것은 두 가지다. 결과물로 완료를 판단하면 재실행이 안전해진다는 것, 그리고 그걸 하려면 결과물의 "신선도"까지 알아야 한다는 숙제. Dagster의 파티션 상태와 오래된 칸 판정이 그 숙제에 대한 답이다.

## 같은 일을 네 도구로 해 보니

세 도구를 직접 돌려 본 감각을 정리하면 이렇다. 차이가 여러 축이라 표로 둔다.

| | Airflow | Prefect | Dagster | Luigi |
|---|---|---|---|---|
| 파이프라인 단위 | DAG와 태스크 | 플로와 태스크(파이썬 함수) | 자산과 파티션 | 태스크와 결과 파일 |
| 실행 전에 모양이 정해지나 | 파싱 시점에 정해진다(동적 태스크 매핑은 있음) | 실행하며 정해진다 | 자산 그래프는 정해진다 | 실행하며 의존을 따라간다 |
| 날짜 개념 | 데이터 구간이 기본 | 파라미터로 직접 | 파티션 키 | 파라미터로 직접 |
| 백필 | 날짜 범위로 실행 재생성 | 실행을 직접 여러 번 | 빈칸·오래된 칸 채우기 | 결과 파일을 지우고 다시 |
| 스케줄러 | 내장 | 서버·serve | 데몬(스케줄, 센서, 자동화) | 없음(크론 필요) |
| 생태계 | 가장 넓다(프로바이더 수백 개) | 중간 | dbt 등과 자산 단위 통합이 강하다 | 정체 |

고르는 기준은 대략 이렇다. 이미 Airflow가 있고 운영 노하우가 쌓였다면 바꿀 이유가 약하다. Airflow 3도 데이터셋을 이은 "에셋" 기반 스케줄링(앞 DAG가 테이블을 갱신하면 뒤 DAG를 깨우는 방식)을 갖추고 있다. 다만 Dagster처럼 파티션별 상태를 중심에 두지는 않는다. 파이썬 스크립트 몇 개를 빨리 묶어야 하고 흐름이 동적이면 Prefect가 가볍다. 테이블이 수백 개고 dbt 모델과 ML 피처, 대시보드까지 "무엇이 오래됐나"를 한 그래프로 보고 싶다면 Dagster의 자산 모델이 맞다. 데이터 계보를 오케스트레이터가 바로 알게 되는 것도 장점인데, 계보 자체를 관리하는 방법은 [메타데이터와 데이터 계보](/posts/data-catalog-lineage)에서 다룬다.

AWS Glue는 서버리스 Spark다. Spark 작업 코드를 올리면 클러스터를 띄우고 끄는 일을 AWS가 한다. 테이블 메타데이터를 담는 Glue Data Catalog, S3를 훑어 스키마를 추정하는 크롤러, 북마크(이미 처리한 파일을 기억하는 증분 처리)가 함께 온다. Glue에도 워크플로와 트리거가 있지만 복잡한 의존 관계나 Glue 밖의 작업을 묶기에는 약해서, 보통 Airflow(MWAA)나 Step Functions가 Glue 작업을 부르는 구조가 된다. 요금은 DPU(작업 단위 계산 자원)를 쓴 시간으로 매기고, 글 쓰는 시점 미국 동부 기준 DPU 시간당 0.44달러이며 Glue 2.0 이후 작업은 초 단위로 청구되고 최소 1분이다(리전·작업 종류에 따라 다르다).

Azure Data Factory(ADF)는 두 칸에 걸쳐 있다. 파이프라인 안에 활동(activity)을 이어 붙이는 오케스트레이터이면서, 수십 종의 원본에서 데이터를 옮기는 복사 활동이 강점이다. 변환은 Databricks나 SQL로 넘기거나, 내부적으로 Spark에서 도는 매핑 데이터 흐름을 쓴다. 화면에서 끌어다 놓는 방식이라 코드 리뷰와 테스트가 어렵다는 불만이 흔하고, 파이프라인 정의는 JSON으로 Git에 연결해 관리할 수 있다. 요금은 활동 실행 횟수와 데이터 이동 단위 시간으로 나뉘어 매겨진다.

GCP Dataflow는 Apache Beam 코드를 실행하는 관리형 엔진이다. 같은 Beam 코드로 배치와 스트리밍을 모두 돌리고, 작업자 수를 자동으로 늘리고 줄인다. 오케스트레이터가 아니라 처리 엔진이라, 매일 언제 무엇을 돌릴지는 Cloud Composer(관리형 Airflow)나 Workflows가 정한다. 배치와 스트리밍을 한 코드로 다루는 설계 이야기는 [람다와 카파 아키텍처](/posts/lambda-kappa-architecture)와 이어진다.

관리형 Airflow(AWS MWAA, GCP Cloud Composer)와 Dagster+, Prefect Cloud, Astronomer 같은 회사 서비스는 오케스트레이터 자체를 대신 운영해 준다. 메타데이터 DB 백업, 스케줄러 이중화, 버전 업그레이드를 맡기는 대가로 돈을 낸다.

## 관리형으로 갈 때 잃는 것

관리형 서비스는 "운영할 사람이 없는 팀"에게는 거의 항상 이득이다. 그래도 고르기 전에 확인할 것이 있다.

비용은 작업이 많아질수록 직선으로 늘어난다. 작은 작업 수백 개가 각각 Glue 작업으로 돌면 작업마다 최소 청구와 기동 시간이 붙는다. 이럴 때는 작은 작업을 하나로 묶거나, 아주 가벼운 작업은 Glue의 Python shell 작업이나 컨테이너로 돌린다. 관리형 Airflow도 환경 크기별로 시간당 요금이 붙어서, DAG가 몇 개뿐인 팀에게는 비싼 경우가 있다.

종속은 코드보다 주변에서 생긴다. Spark 코드 자체는 옮길 수 있어도, Glue의 북마크, DynamicFrame API, 크롤러가 만든 카탈로그에 기대기 시작하면 다른 곳으로 옮기기 어렵다. ADF의 화면 정의는 다른 도구로 옮길 방법이 거의 없다. 처리 엔진은 표준(Spark, Beam, SQL)을 쓰고 클라우드 고유 API는 얇게 감싸 두는 편이 나중에 덜 아프다.

로컬에서 재현하기 어렵다. 관리형 서비스에서만 나는 실패(권한, 네트워크, 할당량)는 개발 PC에서 재현되지 않는다. 그래서 변환 로직을 순수 함수나 SQL로 떼어 내 로컬에서 테스트하고, 관리형 서비스는 그걸 부르는 얇은 층으로 두는 구조가 좋다. 위 실험에서 집계 로직이 Prefect, Dagster, Luigi 어디로든 거의 그대로 옮겨 갔던 것도 로직이 도구와 분리돼 있었기 때문이다.

## 도구를 바꿔도 남는 규칙

네 도구로 같은 파이프라인을 짜 보면, 도구보다 오래가는 규칙이 몇 개 보인다. 태스크든 자산이든 같은 날짜를 다시 돌리면 같은 결과가 나와야 한다(날짜 범위를 지우고 다시 쓰기). 날짜는 "지금"이 아니라 실행이 맡은 구간이나 파티션 키로 고른다. 변환 로직은 오케스트레이터 코드와 떼어 둔다. 이 세 가지가 지켜지면 도구를 바꾸는 일은 생각보다 작다. 차이는 그 위에서 무엇을 기본으로 주느냐다. Airflow는 데이터 구간과 넓은 생태계를, Prefect는 파이썬 그대로의 유연함을, Dagster는 결과물의 상태와 신선도를 기본으로 준다.

## 면접에서 나올 만한 질문

### 오케스트레이터와 크론은 무엇이 다른가?

크론은 정해진 시각에 명령을 실행하는 것만 한다. 오케스트레이터는 작업 사이의 의존 관계, 실패한 단계의 재시도와 부분 재실행, 날짜별 실행 이력, 과거 날짜의 백필, 알림을 제공한다. 그래서 앞 작업이 늦게 끝나면 기다리고, 실패한 날짜만 골라 다시 돌릴 수 있다.

### 태스크 중심 모델과 데이터 자산 중심 모델의 차이는?

태스크 중심(Airflow, Prefect)은 "어떤 작업을 어떤 순서로 돌리나"를 적고 실행 기록으로 상태를 안다. 자산 중심(Dagster)은 "어떤 테이블·파일이 있어야 하고 무엇으로 만드나"를 적고, 자산의 파티션마다 언제 만들어졌는지로 상태를 안다. 그래서 자산 중심은 계보와 신선도를 바로 알고, 어떤 칸이 비었거나 오래됐는지 계산할 수 있다.

### 자산 중심 모델이 백필을 어떻게 바꾸나?

태스크 중심 백필은 날짜 범위를 주고 실행을 다시 만드는 일이라, 이미 성공한 날짜도 다시 돌고 원본이 바뀌었을 때 영향받는 하위 작업은 사람이 찾는다. 자산 중심은 파티션 표에서 빈칸만 고르고, 위쪽 자산이 아래쪽보다 최근에 바뀐 칸을 오래된 칸으로 판정해 그것만 다시 만든다. 날짜마다 실행할지 한 실행에 범위를 묶을지는 처리 엔진에 맞게 고른다.

### Prefect를 쓸 때 날짜 처리에서 주의할 점은?

Prefect에는 Airflow의 데이터 구간 같은 "이 실행이 맡은 기간" 개념이 기본으로 묶여 있지 않다. date.today() 같은 현재 시각으로 날짜를 고르면 실행이 밀렸을 때 다른 날짜를 처리한다. 예약 시각(scheduled_start_time)이나 명시적인 날짜 파라미터로 범위를 정하고, 백필은 그 파라미터를 바꿔 실행을 여러 번 만든다.

### Luigi는 왜 요즘 새 프로젝트에서 잘 쓰이지 않나?

결과 파일이 있으면 완료로 보는 생각은 좋았지만, 파일 존재만 보고 신선도는 모르니 원본이 바뀌어도 다시 돌지 않는다. 내장 스케줄러가 없어 시작은 크론에 맡겨야 하고, 실행 이력과 UI도 약하다. 이 완료 판정 아이디어는 Dagster의 자산과 파티션 상태로 발전했다.

### AWS Glue를 오케스트레이터로 써도 되나?

Glue는 기본적으로 서버리스 Spark 처리 엔진이고, 워크플로와 트리거가 있지만 복잡한 의존 관계나 Glue 밖 작업을 묶기에는 약하다. 보통 Airflow(MWAA)나 Step Functions가 Glue 작업을 부르는 구조로 쓴다. 작은 작업이 많으면 작업마다 최소 청구와 기동 시간이 붙어 비싸지니 묶거나 가벼운 실행 방식을 쓴다.

### 관리형 ETL 서비스의 종속을 줄이려면?

처리 로직은 Spark, Beam, SQL 같은 표준으로 쓰고, 북마크나 DynamicFrame 같은 클라우드 고유 기능은 얇은 층에만 둔다. 변환 로직을 오케스트레이터와 떼어 순수 함수나 SQL로 만들어 로컬에서 테스트한다. 그러면 도구를 바꿀 때 부르는 층만 다시 쓰면 된다.
