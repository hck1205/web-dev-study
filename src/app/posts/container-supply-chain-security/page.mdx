  컨테이너 이미지가 서버에 닿기까지는 식품이 공장에서 마트 진열대까지 가는 길과 비슷하다. 상자에 붙은 이름표는 언제든 다른 상자에 옮겨 붙일 수 있어서, 내용물로 만든 지문 번호로 상자를 가리켜야 바꿔치기를 막는다. 상자에는 성분표를 붙여 무엇이 들었는지 적고, 성분 중 알려진 문제가 있는지 검사하고, 만든 곳의 봉인 스티커로 공장에서 나온 그대로인지 확인한다. 마지막으로 클러스터 입구에서 이 확인을 통과한 상자만 들인다.

  흔한 구멍은 입구 검사가 허술한 경우다. 허용한 저장소 이름을 앞부분만 비교하면 비슷하게 지은 가짜 주소가 통과하고, 검사 서버가 죽었을 때 모두 통과시키도록 두면 그 서버만 멈추면 문이 열린다.

어제 서명을 확인하고 배포한 `app:1.0`을 오늘 다시 받았더니 다른 프로그램이 나온다.

```bash
docker run --rm localhost:19330/demo/app:1.0
```

```text
v2-evil
```

레지스트리는 해킹당하지 않았다. 누군가 같은 태그로 새 이미지를 올렸을 뿐이다. 태그는 덮어쓸 수 있는 이름표라서, 태그로 받는 쪽은 그 이름표가 지금 무엇을 가리키는지만 안다. 이미지를 만든 사람, 그 안에 든 패키지, 그 사이에 손댄 사람이 있는지는 따로 확인해야 한다.

컨테이너 공급망 보안은 이 확인을 단계마다 거는 일이다. 이미지에 무엇이 들었나(SBOM), 그중 알려진 취약점은 무엇인가(스캔), 누가 만들었고 그 뒤로 바뀌지 않았나(서명), 클러스터는 그걸 확인한 이미지만 받나(어드미션). 실습은 Ubuntu 24.04 호스트에서 Trivy 0.70.0, Syft 1.36.0, cosign 3.0.2를 받아 돌렸고, 로컬 레지스트리(`registry:3`, 포트 19330)와 kwok으로 띄운 쿠버네티스 1.33 API 서버를 썼다.

이미지를 작게 만드는 Dockerfile 쪽 이야기와 Trivy를 처음 돌려 보는 법은 [Dockerfile과 이미지 레이어](/posts/dockerfile-image-layers)에, 한 번 빌드한 결과를 digest로 승격하는 파이프라인은 [CI/CD 기초](/posts/ci-cd-basics#한-번만-빌드하고-승격한다)에, npm 쪽 공급망은 [의존성 지옥](/posts/dependency-hell#설치는-남의-코드를-실행하는-일이다)에 있다. 서명 자체의 원리는 [전자 서명과 인증서](/posts/digital-signatures-certificates)가 다룬다. CKS 시리즈의 다른 글은 [CIS 벤치마크와 kube-bench](/posts/cis-benchmark-kube-bench), [seccomp와 AppArmor 프로필](/posts/seccomp-apparmor), [Falco 런타임 탐지](/posts/falco-runtime-security)다.

```bash
docker push localhost:19330/demo/app:1.0          # 첫 번째 이미지
# ... Dockerfile을 바꿔 다시 빌드하고 같은 태그로

docker run --rm localhost:19330/demo/app:1.0
```

그래서 운영 매니페스트에는 digest를 적는다. 사람이 읽기 좋게 `api:1.4.2@sha256:...`처럼 둘을 같이 적어도 되고, 그때 런타임은 digest로 받는다. digest를 손으로 관리하기는 힘드니 CI가 빌드 결과의 digest를 매니페스트에 써 넣거나, Renovate 같은 봇이 베이스 이미지 digest를 갱신하는 PR을 올리게 한다. Dockerfile의 `FROM`도 같다. `FROM node:22-alpine`은 빌드할 때마다 다른 베이스를 받을 수 있다.

  solution={`function parseImage(ref) {
  let digest = null;
  const at = ref.indexOf("@");
  if (at >= 0) { digest = ref.slice(at + 1); ref = ref.slice(0, at); }
  let registry = "docker.io";
  const slash = ref.indexOf("/");
  if (slash >= 0) {
    const first = ref.slice(0, slash);
    if (first.includes(".") || first.includes(":") || first === "localhost") {
      registry = first;
      ref = ref.slice(slash + 1);
    }

  if (registry === "docker.io" && !ref.includes("/")) ref = "library/" + ref;
  if (!tag && !digest) tag = "latest";
  return { registry, repository: ref, tag, digest };
}`}

## 이미지에 무엇이 들었나: SBOM

SBOM(Software Bill of Materials)은 소프트웨어의 부품 목록이다. 이미지 안의 OS 패키지, 언어 패키지, 바이너리를 이름과 버전, 패키지 주소(purl)로 적는다. 형식은 CycloneDX와 SPDX 두 가지가 널리 쓰인다. Syft로 `node:22-alpine`의 SBOM을 뽑았다.

```bash
# 표로 하나, CycloneDX JSON으로 하나
syft docker:node:22-alpine -q -o cyclonedx-json=sbom.cdx.json -o table=sbom.txt
awk 'NR>1{print $NF}' sbom.txt | sort | uniq -c
grep -E '^(libssl3|musl|busybox|npm) ' sbom.txt
jq '{bomFormat, specVersion, components: (.components|length)}' sbom.cdx.json
```

```text
     18 apk
      1 binary
      7 duplicate)
      2 duplicates)
    178 npm
busybox                             1.37.0-r31   apk                      
libssl3                             3.5.8-r0     apk                      
musl                                1.2.6-r2     apk                      
npm                                 10.9.9       npm                      
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.6",
  "components": 498
}
```

Node.js 실행 이미지인데 패키지 대부분이 npm 패키지(178개)다. 이미지에 같이 들어 있는 npm CLI 자신의 의존성이다. 앱은 런타임에 npm을 쓰지 않는다. CycloneDX의 components 498개에는 파일 항목(280개)까지 들어 있다.

SBOM이 쓸모 있는 순간은 새 취약점이 발표된 날이다. "우리 이미지 중 libssl3 3.5.8을 쓰는 게 몇 개인가"를 이미지를 다시 받아 풀지 않고 SBOM만 뒤져서 답할 수 있다. 스캐너도 SBOM을 입력으로 받는다.

```bash
# 이미지 대신 SBOM 파일을 스캔한다
trivy sbom --quiet --format json -o sbom-scan.json sbom.cdx.json
jq -r '[.Results[]?.Vulnerabilities[]?.Severity] | group_by(.) | map("\(.[0])=\(length)") | join(" ")' sbom-scan.json
```

```text
HIGH=11 LOW=1 MEDIUM=10 UNKNOWN=1
```

이미지를 직접 스캔한 결과(`HIGH=11 LOW=1 MEDIUM=10 UNKNOWN=2`)와 거의 같다. 한 건 차이는 SBOM을 만든 도구(Syft)와 읽는 도구(Trivy)가 패키지를 알아보는 방식이 조금 달라서 생긴다. 한 도구로 만든 SBOM을 다른 도구로 읽으면 이런 차이가 늘 생길 수 있다는 점은 알아 둔다.

## 알려진 취약점 걸러 내기

Trivy로 호스트에 있던 이미지 여섯 개를 스캔했다. 취약점 DB(약 130MB)는 처음 한 번 받는다.

```bash
for i in node:22-slim node:22-alpine gcr.io/distroless/nodejs22-debian12:latest python:3.12-slim nginx:1.27-alpine alpine:3.20; do
  f="r-$(echo $i | tr '/:' '__').json"
  trivy image --quiet --scanners vuln --format json -o "$f" $i
  printf '%-45s %s\n' "$i" "$(jq -r '[.Results[]?.Vulnerabilities[]?.Severity] | group_by(.) | map("\(.[0])=\(length)") | join(" ")' $f) os=$(jq -r '.Metadata.OS.Family + " " + .Metadata.OS.Name' $f)"
done
```

그런데 distroless 이미지도 CRITICAL 1, HIGH 6이 나왔다. OS가 `debian 12.13`으로, 다른 Debian 이미지(12.15)보다 오래됐다. 이 VM에 예전에 받아 둔 `latest`라서다. 생성 시각으로 나이를 가늠하려 해도 안 된다.

재현 가능한 빌드를 위해 생성 시각을 0으로 고정해 두었다. 이미지 나이는 레지스트리의 digest 이력으로 확인해야 한다. 셸이 없다는 것도 보인다. 공격자가 앱 취약점으로 명령 실행을 얻어도 쓸 셸과 도구가 없다. 대신 운영자도 `kubectl exec`로 들어가 볼 수 없으니, 디버깅은 `kubectl debug`의 임시 컨테이너로 한다.

CI에서는 결과를 기준으로 빌드를 멈춘다.

```bash

trivy image --quiet --scanners vuln --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 --format json -o /dev/null node:22-alpine; echo "exit=$?"
```

```text

exit=1
```

`--ignore-unfixed`는 고친 버전이 아직 없는 취약점을 빼서, 지금 손쓸 수 있는 것만 실패로 만든다. 여기서는 고칠 수 있는 HIGH가 남아 있어서 둘 다 1이다. 실무에서는 이렇게 문턱을 정하고, 예외는 `.trivyignore`에 CVE 번호와 이유, 만료일을 적어 관리한다. 스캔은 빌드할 때 한 번으로 끝나지 않는다. 어제 깨끗했던 이미지도 오늘 새 CVE가 발표되면 취약해지므로, 레지스트리에 있는 이미지와 돌고 있는 이미지를 주기적으로 다시 스캔한다. 이때 SBOM을 저장해 두면 이미지를 다시 받지 않고 다시 스캔할 수 있다.

## 누가 만들었나: 서명

스캔과 SBOM은 "이 이미지에 무엇이 들었나"를 말한다. "이 이미지를 우리 CI가 만들었고 그 뒤로 바뀌지 않았나"는 서명이 말한다. Sigstore 프로젝트의 cosign이 컨테이너 서명에서 가장 널리 쓰인다. 방식은 두 가지다.

키 방식은 키 쌍을 만들어 개인 키로 서명하고, 검증하는 쪽에 공개 키를 나눠 준다. 로컬 레지스트리에서 해 봤다. 이 VM에서는 Sigstore의 공개 서비스(TUF 저장소, 투명성 로그 Rekor)에 닿지 않아서 투명성 로그 기록을 끄고, 신뢰 루트 파일은 GitHub의 `sigstore/root-signing` 저장소에서 받아 썼다.

```bash
COSIGN_PASSWORD=demo cosign generate-key-pair      # cosign.key, cosign.pub
IMG=localhost:19330/demo/app@sha256:6aa698b4fffd0a2a2055ecbaa3405521d1720ca3ec61553c7380149fd13d5e95
# 태그가 아니라 digest에 서명한다
COSIGN_PASSWORD=demo cosign sign --yes --key cosign.key --tlog-upload=false --use-signing-config=false $IMG
cosign verify --key cosign.pub --insecure-ignore-tlog=true --trusted-root trusted_root.json $IMG
```

서명 옆에 SBOM이나 빌드 정보를 붙이는 것을 증명(attestation)이라고 한다. in-toto 형식의 문장에 "이 digest의 SBOM은 이것"을 담아 서명한다.

```bash

  --type cyclonedx --predicate app.cdx.json $IMG
cosign verify-attestation --key cosign.pub --insecure-ignore-tlog=true --trusted-root trusted_root.json --type cyclonedx $IMG 2>/dev/null \
  | jq -r '.payload' | base64 -d | jq '{_type, predicateType, subject, components: (.predicate.components|length)}'
```

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: image-digest-and-registry
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - apiGroups: [""]
      apiVersions: ["v1"]
      operations: ["CREATE", "UPDATE"]
      resources: ["pods"]
  variables:
  - name: images
    expression: "object.spec.containers.map(c, c.image) + (has(object.spec.initContainers) ? object.spec.initContainers.map(c, c.image) : [])"
  validations:
  - expression: "variables.images.all(i, i.startsWith('registry.example.com/'))"
    message: "이미지는 registry.example.com에서만 받는다"
  - expression: "variables.images.all(i, i.contains('@sha256:'))"
    message: "이미지는 태그가 아니라 digest로 고정한다"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: image-digest-and-registry
spec:
  policyName: image-digest-and-registry
  validationActions: ["Deny"]
  matchResources:
    namespaceSelector:
      matchLabels:
        supply-chain: enforced
```

ImagePolicyWebhook은 CKS에서 자주 나오는 내장 어드미션 플러그인이다. API 서버가 Pod의 이미지 목록을 `ImageReview`로 외부 HTTPS 서버에 보내고, 서버가 허용 여부를 답한다. 실습에서는 digest 없는 이미지를 거절하는 30줄짜리 Node 서버를 127.0.0.1:19340에 띄우고 API 서버에 연결했다.

```yaml
# admission.yaml: --admission-control-config-file로 넘기고 --enable-admission-plugins에 ImagePolicyWebhook을 넣는다
apiVersion: apiserver.config.k8s.io/v1
kind: AdmissionConfiguration
plugins:
- name: ImagePolicyWebhook
  configuration:
    imagePolicy:
      kubeConfigFile: /etc/kubernetes/ipw/kubeconfig.yaml   # 서버 주소와 CA, API 서버의 클라이언트 인증서
      allowTTL: 50        # 허용 결과를 50초 캐시
      denyTTL: 50         # 거절 결과를 50초 캐시
      retryBackoff: 500   # 재시도 간격(ms)
      defaultAllow: true  # 서버에 닿지 못할 때의 동작 (아래에서 확인)
```

```bash
kubectl run t1 --image=nginx:1.27-alpine
```

`defaultAllow: true`는 서버가 죽으면 모두 허용하는 설정이다. 공격자 입장에서는 정책 서버만 멈추면 문이 열린다. `false`로 바꾸고 다시 띄운 API 서버에서는 같은 상황에서 이렇게 나온다.

```text
Error from server (Forbidden): pods "t5" is forbidden: Post "https://127.0.0.1:19340/review?timeout=30s": dial tcp 127.0.0.1:19340: connect: connection refused
```

이번에는 닫혔다. 대신 정책 서버가 죽으면 CoreDNS나 정책 서버 자기 자신을 포함해 아무 Pod도 새로 못 뜬다. 정책 서버를 여러 개 띄우고, 장애 때 쓸 절차(설정 파일에서 플러그인을 빼고 API 서버를 다시 띄우기)를 미리 적어 둔다. 이 플러그인은 네임스페이스를 가려 적용하는 기능이 없다는 점도 같이 기억해 둔다.

서명을 실제로 검증하는 건 Kyverno의 `verifyImages`나 Sigstore의 policy-controller 같은 웹훅이 맡는다. 아래는 Kyverno 정책의 모양이다(예시, 이 환경에서 Kyverno를 돌리지 않았고 필드 위치는 버전마다 조금씩 옮겨 가고 있다).

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-shop-images
spec:
  validationFailureAction: Enforce
  webhookTimeoutSeconds: 30
  rules:
  - name: cosign-key
    match:
      any:
      - resources:
          kinds: ["Pod"]
    verifyImages:
    - imageReferences: ["registry.example.com/shop/*"]
      mutateDigest: true      # 태그로 와도 검증한 digest로 바꿔 넣는다
      verifyDigest: true
      required: true
      attestors:
      - entries:
        - keys:
            publicKeys: |-
              -----BEGIN PUBLIC KEY-----
              (cosign.pub 내용)
              -----END PUBLIC KEY-----
```

`mutateDigest`가 쓸모 있다. 개발자가 태그로 매니페스트를 써도, 정책이 서명을 확인한 그 digest로 Pod 스펙을 고쳐 넣는다. 확인한 것과 실행하는 것이 같아진다.

## 어디서부터 거나

한 번에 다 켜려다 배포가 멈추는 것보다, 순서를 정해 하나씩 거는 편이 낫다. 작은 팀이라면 먼저 CI에 Trivy를 `--exit-code 1 --ignore-unfixed`로 걸고, 실행 이미지를 멀티 스테이지와 작은 베이스로 줄이고, 매니페스트에 digest를 적는다. 그다음 허용 레지스트리와 digest 규칙을 ValidatingAdmissionPolicy로 경고(`Warn`)부터 걸어 위반을 모은 뒤 `Deny`로 올린다. 레지스트리가 여러 팀에 열려 있거나 외부 기여가 많아지면 CI에서 키리스 서명을 붙이고, 클러스터에서 서명 검증 웹훅을 건다. SBOM은 처음부터 빌드마다 만들어 저장해 두면, 새 CVE가 나온 날 영향 범위를 바로 답할 수 있다.

장애 대응에서 자주 보는 증상도 정리해 둔다. 배포가 갑자기 멈췄는데 Deployment는 만들어졌다면 ReplicaSet 이벤트에서 어드미션 거절을 찾는다. 서명한 이미지가 검증에서 "no signatures found"를 내면 태그로 확인하고 있지 않은지, 서명을 저장한 방식과 검증 도구의 버전이 맞는지 본다. 스캐너가 갑자기 CI를 무더기로 실패시키면 대개 코드가 아니라 취약점 DB가 갱신된 것이다.

## 면접에서 나올 만한 질문

### 이미지 태그 대신 digest로 배포해야 하는 이유는요?

태그는 레지스트리에서 언제든 다른 이미지를 가리키게 바꿀 수 있는 이름표이고, digest는 매니페스트 내용의 해시라 바뀌지 않는다. 같은 태그로 다른 이미지가 올라오면 태그로 받는 쪽은 모르고 새 이미지를 실행한다. 서명도 digest에 붙으므로, 확인한 것과 실행하는 것을 같게 하려면 digest로 고정한다. 관리는 CI가 빌드 결과 digest를 매니페스트에 써 넣거나 봇이 갱신하게 한다.

### SBOM은 무엇이고 언제 쓸모가 있나요?

이미지 안의 OS 패키지, 언어 패키지, 바이너리를 이름, 버전, purl로 적은 부품 목록이다. CycloneDX와 SPDX 형식이 많이 쓰인다. 새 취약점이 발표됐을 때 이미지를 다시 받지 않고 SBOM만 뒤져 영향받는 이미지를 찾을 수 있고, 스캐너에 SBOM을 넣어 다시 스캔할 수도 있다. 서명한 증명으로 이미지에 붙이면 SBOM 자체도 위조되지 않았음을 확인할 수 있다.

### Trivy 결과가 수백 건입니다. 어떻게 줄이나요?

어디서 나왔는지부터 나눈다. 대부분 베이스 이미지의 OS 패키지나 이미지에 딸려 온 도구(npm CLI 같은)에서 나온다. 멀티 스테이지 빌드로 실행 단계에 필요한 것만 남기고, distroless나 Alpine 같은 작은 베이스를 최신 digest로 쓰면 크게 준다. 남은 것은 `--ignore-unfixed`로 지금 고칠 수 있는 것부터 보고, 예외는 이유와 만료일을 적어 관리한다.

### cosign의 키 방식과 키리스 방식은 어떻게 다른가요?

키 방식은 오래 쓰는 키 쌍으로 서명하고 공개 키로 검증한다. 키 관리와 유출 시 교체가 부담이다. 키리스 방식은 CI의 OIDC 토큰으로 Fulcio에서 10분짜리 인증서를 받아 임시 키로 서명하고, Rekor 투명성 로그에 남긴다. 검증할 때는 인증서의 신원(워크플로 경로)과 발급자를 조건으로 건다. 이 조건을 느슨하게 걸면 아무나의 서명도 통과한다.

### ImagePolicyWebhook의 defaultAllow는 무엇을 정하나요?

정책 서버에 닿지 못할 때의 동작이다. true면 모두 허용(fail-open)이라 정책 서버만 멈추면 검사가 사라진다. false면 모두 거절(fail-closed)이라 정책 서버 장애가 곧 Pod 생성 장애가 된다. 보안 쪽에서는 false가 맞고, 그러려면 정책 서버를 이중화하고 장애 때 플러그인을 빼는 절차를 준비한다. 판정 결과는 allowTTL·denyTTL 동안 캐시된다.

### 허용 레지스트리 정책을 짤 때 흔한 실수는요?

접두사 비교에서 끝의 `/`를 빼서 `registry.example.com.evil.io`를 통과시키는 것, initContainers와 ephemeralContainers를 빼먹는 것, `nginx`처럼 레지스트리를 생략한 이름이 docker.io라는 걸 잊는 것이다. 그리고 Pod만 검사하면 Deployment는 만들어지고 ReplicaSet 이벤트에만 거절이 남아서, 배포 도구가 성공으로 착각할 수 있다.

### 서명했는데 검증에서 "no signatures found"가 나옵니다. 무엇을 보나요?

먼저 태그로 확인하고 있지 않은지 본다. 태그가 다른 digest로 옮겨 갔으면 그 digest에는 서명이 없다. 다음으로 서명 저장 방식과 도구 버전을 본다. cosign 3은 새 번들 형식을 OCI referrers로 저장하는데, 옛 방식의 태그를 찾는 도구는 서명을 못 찾을 수 있다. 레지스트리가 referrers API를 지원하는지도 확인한다.
