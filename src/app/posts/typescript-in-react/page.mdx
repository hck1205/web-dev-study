<EasyIntro>
  사용자 정보를 보여 주는 React 화면을 TypeScript로 옮겼더니, 코드는 그대로인데 오류가 났다. 처음에 비어 있던 상태를 보고 TypeScript가 이 자리는 영원히 비어 있다고 정해 버렸기 때문이다.

  TypeScript는 사물함에 처음 넣은 물건을 보고 그 칸의 이름표를 쓴다. 처음 물건이 진짜 모양을 다 보여 주면 그냥 맡기면 되지만, 빈 칸이나 빈 목록으로 시작하면 나중에 들어올 물건을 이름표에 미리 적어 줘야 한다. 화면 요소를 붙잡아 두는 칸도 처음엔 비어 있다가 화면이 그려진 뒤에 채워지니, 쓰기 전에 비었는지 확인한다. 함께 와야 하는 설정값은 종류별로 묶어 두면, 하나를 빠뜨리거나 섞어 넣었을 때 검사기가 알려 준다.

  흔한 실수는 빈 칸을 억지로 사용자라고 우겨서 오류를 지우는 것이다. 그러면 첫 화면에서 엉뚱한 곳이 터지니, 아직 없는 상태도 이름표에 그대로 드러내는 편이 맞다.

사용자 정보를 불러오는 컴포넌트를 자바스크립트에서 TypeScript로 옮겼다. 로직은 한 줄도 안 바꿨는데 에러가 두 개 났다.

```tsx
import { useEffect, useState } from "react";

interface User { id: number; name: string }
declare function fetchUser(): Promise<User>;

export function Profile() {
  const [user, setUser] = useState(null);
  useEffect(() => {
    fetchUser().then((data) => setUser(data));
  }, []);
  return <p>{user?.name}</p>;
}
```

```text
state.tsx(9,40): error TS2345: Argument of type 'User' is not assignable to parameter of type 'SetStateAction<null>'.
  Type 'User' provides no match for the signature '(prevState: null): null'.
state.tsx(11,20): error TS2339: Property 'name' does not exist on type 'never'.
```

`useState(null)`이라고 쓰면 TypeScript는 초기값 `null`을 보고 상태 타입을 `null`로 추론한다. 그 상태에는 `null` 말고 아무것도 넣을 수 없다. 그리고 `user?.name`의 `?.`가 `null`을 걸러 내고 나면 남는 타입이 없어 `never`가 된다. 자바스크립트에서는 "나중에 사용자가 들어올 자리"였던 것이 타입으로는 "영원히 null인 자리"로 읽힌 셈이다.

이 글은 React 컴포넌트를 TypeScript로 쓸 때 매번 만나는 자리를 차례로 본다. 상태, props, children, 이벤트, ref, 래퍼 컴포넌트, 서로 배타적인 props, 제네릭 컴포넌트, Context와 커스텀 훅이다. 검사는 TypeScript 5.9.3과 `@types/react` 19.3.0으로 했다. 타입 정의는 React 버전보다 `@types/react` 버전을 따르니, 18을 쓰는 프로젝트라면 몇 군데가 다르다(본문에서 짚는다).

이 주제의 다른 글: 제네릭 자체는 [제네릭](/posts/ts-generics)에서, 판별 유니온을 좁히는 원리는 [타입 좁히기](/posts/ts-narrowing)에서, `ComponentProps`와 `Omit`을 조합하는 도구는 [유틸리티 타입과 매핑된 타입](/posts/ts-utility-mapped-types)에서 다룬다. 렌더링이 언제 일어나는지는 [리렌더링](/posts/react-rerender) 글에 있다.

## 초기값이 타입을 정한다

`useState`의 타입 선언은 대략 `useState<S>(initial: S | (() => S)): [S, Dispatch<SetStateAction<S>>]`다. 타입 인자를 주지 않으면 `S`를 초기값에서 추론한다. 초기값이 실제 값의 모양을 다 보여 줄 때는 추론에 맡기고, 그렇지 않을 때만 적는다.

```tsx
const [count, setCount] = useState(0);                       // number. 적을 필요 없다
const [user, setUser] = useState<User | null>(null);          // 나중에 채워질 값
const [items, setItems] = useState([]);                       // never[]가 된다
setItems([{ id: 1 }]);
const [tags, setTags] = useState<string[]>([]);               // 빈 배열은 타입을 적는다
setTags((prev) => [...prev, "ts"]);
```

```text
state2.tsx(6,13): error TS2322: Type '{ id: number; }' is not assignable to type 'never'.
```

빈 배열에서는 원소 타입을 알 수 없어 `never[]`가 된다. 추론이 이렇게 동작하는 이유는 [타입 시스템 기초](/posts/ts-type-system-basics)에서 다뤘다. React 쪽에서 기억할 규칙은 짧다. `null`, 빈 배열, 빈 객체(`{}`)가 초기값이면 타입을 적는다.

`useState<User>(null as any)`나 `useState({} as User)`처럼 단언으로 에러를 지우는 코드도 자주 보인다. 그러면 첫 렌더링에서 `user`는 실제로 `null`이거나 빈 객체인데 타입은 `User`라고 말한다. `user.name`은 앞쪽에서는 TypeError로 터지고, 뒤쪽에서는 `undefined`가 `string`인 척 흘러간다. "아직 없음"이 실제로 있는 상태라면 타입에도 `| null`로 드러내고, 화면에서 그 경우를 그려 주는 편이 맞다.

## props 타입을 적는 자리

함수 컴포넌트는 props 객체 하나를 받는 함수다. 그 매개변수에 타입을 적는다.

```tsx
type ButtonProps = {
  label: string;
  size?: "sm" | "md";
  onClick: () => void;
};

function Button({ label, size = "md", onClick }: ButtonProps) {
  return <button data-size={size} onClick={onClick}>{label}</button>;
}
```

기본값은 구조 분해에서 준다. 예전 클래스 컴포넌트의 `defaultProps`는 함수 컴포넌트에서 React 19부터 지원하지 않는다. `type`과 `interface` 어느 쪽으로 써도 되는데, 차이는 [타입 시스템 기초](/posts/ts-type-system-basics)에서 다룬다. 팀에서 하나로 정해 두는 게 낫다.

`React.FC<Props>`로 적는 방식도 있다. `@types/react` 18부터는 `FC`가 `children`을 몰래 넣어 주지 않아서, 예전에 쓰던 이유가 많이 사라졌다.

```tsx
type CardProps = { title: string };
const Card: FC<CardProps> = ({ title }) => <section><h2>{title}</h2></section>;

<Card title="a">본문</Card>
```

```text
children.tsx(20,8): error TS2322: Type '{ children: string; title: string; }' is not assignable to type 'IntrinsicAttributes & CardProps'.
  Property 'children' does not exist on type 'IntrinsicAttributes & CardProps'.
```

`FC`를 쓰든 안 쓰든 받을 props는 직접 적어야 한다. 함수 선언으로 쓰면 제네릭 컴포넌트를 만들기 쉽고 호이스팅도 되니, 요즘은 그냥 함수에 props 타입을 적는 쪽이 흔하다.

반환 타입은 보통 적지 않는다. TypeScript 5.1부터 JSX 컴포넌트의 반환 타입 검사가 라이브러리 정의를 따르게 바뀌어서, 지금의 `@types/react`에서는 컴포넌트가 문자열, 숫자 배열, `null`, 서버 컴포넌트의 Promise까지 돌려줄 수 있다. 객체를 돌려주면 그때 막힌다.

```tsx
function Name() { return "kim"; }
function Nums() { return [1, 2]; }
async function Server() { return <p>서버</p>; }
function Bad() { return { a: 1 }; }
export const x = <><Name /><Nums /><Server /><Bad /></>;
```

```text
ret.tsx(5,47): error TS2786: 'Bad' cannot be used as a JSX component.
  Its type '() => { a: number; }' is not a valid JSX element type.
    Type '() => { a: number; }' is not assignable to type '(props: any) => ReactNode | Promise<ReactNode>'.
      Type '{ a: number; }' is not assignable to type 'ReactNode | Promise<ReactNode>'.
```

첫 번째 에러는 런타임에서 React가 내는 에러를 컴파일 시점에 미리 본 것이다. 같은 걸 React 19.3에서 렌더링하면 이렇게 나온다.

`ReactElement`로 좁히는 건 자식을 `cloneElement`로 고치거나 자식의 props를 읽는 컴포넌트처럼 "JSX 하나"가 꼭 필요할 때만이다. 그런데 `ReactElement`로 적어도 어떤 컴포넌트의 엘리먼트인지까지는 막지 못한다. `<Tabs>` 안에 `<Tab>`만 오게 하는 건 타입으로 안 되고, 런타임 검사나 설계(배열 props로 받기)로 푼다. `children`만 받는 단순한 래퍼라면 `PropsWithChildren<Props>`가 `children?: ReactNode`를 붙여 준다.

자식에게 값을 넘겨야 하면 children 자리에 함수를 받는다(render prop). 이때 타입은 `(item: T) => ReactNode`다.

## 이벤트 객체의 타입은 어디서 오나

JSX 속성에 바로 쓴 화살표 함수는 타입을 적지 않아도 된다. `onChange` 자리가 기대하는 타입에서 `e`의 타입이 정해진다(문맥적 타이핑). 핸들러를 따로 빼면 그 문맥이 사라진다.

```tsx
function handleChange(e) {                                  // 문맥이 없다
  setQ(e.target.value);
}
function handleTyped(e: ChangeEvent<HTMLInputElement>) {    // 직접 적는다
  setQ(e.target.value);
}
function handleClick(e: MouseEvent<HTMLButtonElement>) {
  console.log(e.target.value);
  console.log(e.currentTarget.value);
}

<input value={q} onChange={(e) => setQ(e.target.value)} />  // 추론된다
<input value={q} onChange={handleTyped} />
<button value="go" onClick={handleClick}>찾기</button>
<button onClick={handleTyped}>틀림</button>
```

`ChangeEvent`만 예외다. `@types/react` 19.3의 정의는 `target: EventTarget & CurrentTarget`이라서 `e.target.value`가 바로 된다. 정의 옆 주석에는 이게 정확하지 않지만 React 20까지 호환을 위해 둔다고 적혀 있다. 다른 이벤트에서는 `currentTarget`을 쓰는 습관을 들이는 게 안전하다. 이벤트가 퍼지는 순서 자체는 [이벤트 전파](/posts/event-propagation) 글에서 다룬다.

핸들러 타입을 외우기 싫으면 속성의 타입을 그대로 꺼내 쓴다.

```tsx
const handleSubmit: ComponentProps<"form">["onSubmit"] = (e) => {
  e.preventDefault();
};
```

이러면 버전에 따라 이름이 바뀌는 것도 피한다. 실제로 `@types/react` 19.3에서 form의 `onSubmit`은 `SubmitEventHandler`로 선언되어 있고, 예전 버전은 `FormEventHandler`였다.

## ref는 처음엔 비어 있다

```tsx
const inputRef = useRef<HTMLInputElement>(null);
const timer = useRef<number>();
const count = useRef(0);
useEffect(() => {
  inputRef.current.focus();
  inputRef.current?.focus();
  count.current += 1;
}, []);
```

```text
refs.tsx(9,17): error TS2554: Expected 1 arguments, but got 0.
refs.tsx(12,5): error TS18047: 'inputRef.current' is possibly 'null'.
```

변수에 붙는 타입을 펼쳐 보면 이렇다.

```text
const inputRef: RefObject<HTMLInputElement | null>
const count: RefObject<number>
const timer: RefObject<number | undefined>
```

DOM 요소를 담는 ref는 `null`로 시작해서 커밋 단계에 요소가 붙는다. 그래서 `current`가 `HTMLInputElement | null`이고, 쓰기 전에 확인해야 한다. 아래 그림은 그 시간 순서를 보여 준다.

`@types/react` 19부터 `useRef`에는 인자가 꼭 필요하다(위의 TS2554). 18까지는 인자 없는 `useRef<number>()`가 됐고, `useRef<T>(null)`이 읽기 전용 `current`를 돌려주는 등 오버로드가 헷갈렸다. 19에서는 `useRef`가 늘 바꿀 수 있는 `RefObject`를 돌려주고, 들어갈 수 있는 값을 인자 타입이 그대로 드러낸다. 18 프로젝트에서 업그레이드하면 이 부분에서 에러가 꽤 난다.

React 19에서는 함수 컴포넌트가 `ref`를 일반 prop으로 받는다. 그래서 감싼 `input`에 ref를 넘기는 데 `forwardRef`가 필요 없다.

```tsx
function TextField({ label, ...rest }: { label: string } & ComponentProps<"input">) {
  return <label>{label}<input {...rest} /></label>;
}

<TextField label="이메일" ref={inputRef} type="email" />   // 19에서는 에러 없음
```

`ComponentProps<"input">`에 `ref`가 들어 있어서 `rest`와 함께 `input`으로 넘어간다. React 18에서는 함수 컴포넌트가 `ref`를 props로 받지 못하므로 `forwardRef<HTMLInputElement, Props>((props, ref) => ...)`로 감싸야 한다. `forwardRef`는 제네릭 컴포넌트와 잘 맞지 않는다는 문제도 있었는데, 19의 방식은 그 문제가 없다.

```tsx
type ButtonProps = Omit<ComponentProps<"button">, "type"> & {
  variant: "primary" | "ghost";
  type?: "button" | "submit";
};

  return <button type={type} className={cx("btn", variant, className)} {...rest} />;
}
```

`Omit`을 빼먹으면 어떻게 되는지는 시그니처를 바꾸는 경우에 잘 보인다. `input`을 감싸면서 `onChange`가 이벤트 대신 문자열을 받게 하고 싶다고 하자.

```tsx
type Bad = ComponentProps<"input"> & { onChange: (value: string) => void };
type Good = Omit<ComponentProps<"input">, "onChange"> & { onChange: (value: string) => void };

<BadField onChange={(value: string) => console.log(value.trim())} />
<GoodField onChange={(value) => console.log(value.trim())} />
```

```text

  Type '(value: string) => void' is not assignable to type 'ChangeEventHandler<HTMLInputElement, HTMLInputElement>'.
    Types of parameters 'value' and 'event' are incompatible.
```

`Bad`의 `onChange`는 이벤트 핸들러이면서 동시에 문자열 핸들러여야 해서, 문자열만 받는 함수를 넣을 수 없다. 빼고 더한 `Good`은 의도대로 동작한다.

`...rest`를 펼치는 위치도 정해야 한다. `{...rest}`를 마지막에 두면 사용하는 쪽이 `type`이나 `onClick`을 덮을 수 있고, 처음에 두면 컴포넌트가 정한 값이 이긴다. 덮어도 되는 것과 안 되는 것을 정하고 그에 맞게 둔다. 남이 만든 컴포넌트의 props가 필요하면 `ComponentProps<typeof Button>`으로 꺼낸다. 라이브러리가 props 타입을 export하지 않아도 쓸 수 있다.

`as` prop으로 렌더링할 요소를 바꾸는 다형성(polymorphic) 컴포넌트도 있지만, 타입이 금방 복잡해지고 검사도 느려진다. 링크와 버튼 정도라면 아래처럼 판별 props로 나누는 편이 읽기 쉽다.

## 같이 와야 하는 props, 같이 오면 안 되는 props

확인 대화상자를 선택 props로만 만들면 이렇게 된다.

```tsx
type LoosenProps = {
  kind?: "alert" | "confirm";
  message: string;
  onConfirm?: () => void;
  confirmText?: string;
};
<LooseDialog kind="confirm" message="삭제할까요?" />   // 통과. 확인을 눌러도 아무 일이 없다
```

`kind`가 `"confirm"`이면 `onConfirm`이 꼭 있어야 하는데, 각 필드를 따로 선택으로 두면 그 관계를 표현할 수 없다. 경우마다 타입을 나누고 `kind`로 구분하는 유니온으로 바꾼다.

```tsx
type DialogProps =
  | { kind: "alert"; message: string }
  | { kind: "confirm"; message: string; onConfirm: () => void; confirmText?: string };

function Dialog(props: DialogProps) {
  if (props.kind === "confirm") {
    return <button onClick={props.onConfirm}>{props.confirmText ?? "확인"}</button>;
  }
  return <p>{props.message}</p>;
}

<Dialog kind="confirm" message="삭제할까요?" />
<Dialog kind="alert" message="저장했다" onConfirm={() => {}} />
<Dialog kind="confirm" message="삭제할까요?" onConfirm={() => {}} />
```

```text
disc.tsx(30,8): error TS2322: Type '{ kind: "confirm"; message: string; }' is not assignable to type 'IntrinsicAttributes & DialogProps'.
  Property 'onConfirm' is missing in type '{ kind: "confirm"; message: string; }' but required in type '{ kind: "confirm"; message: string; onConfirm: () => void; confirmText?: string | undefined; }'.
disc.tsx(31,43): error TS2322: Type '{ kind: "alert"; message: string; onConfirm: () => void; }' is not assignable to type 'IntrinsicAttributes & DialogProps'.
  Property 'onConfirm' does not exist on type 'IntrinsicAttributes & { kind: "alert"; message: string; }'.
```

빠진 것도, 섞인 것도 잡혔다. 컴포넌트 안에서는 `props.kind`를 확인하면 그 분기에서 `onConfirm`을 쓸 수 있다.

조심할 곳은 구조 분해다. 나머지(`...rest`)로 받으면 좁히기가 끊긴다.

```tsx
function Dialog2({ kind, message, ...rest }: DialogProps) {
  if (kind === "confirm") return <button onClick={rest.onConfirm}>{message}</button>;
  return <p>{message}</p>;
}
```

```text
disc.tsx(22,56): error TS2339: Property 'onConfirm' does not exist on type '{} | { onConfirm: () => void; confirmText?: string | undefined; }'.
  Property 'onConfirm' does not exist on type '{}'.
```

`kind`와 `rest`가 서로 다른 변수가 되면서 "kind가 confirm이면 rest에 onConfirm이 있다"는 연결이 사라졌다. 판별 유니온 props는 `props`를 통째로 받아 좁힌 뒤 분기 안에서 꺼내 쓰는 게 안전하다. 좁히기가 어떤 조건에서 유지되고 끊기는지는 [타입 좁히기](/posts/ts-narrowing)에서 자세히 본다.

## 어떤 값이든 받는 목록 컴포넌트

셀렉트 박스나 목록처럼 "무슨 항목이든 받되, 받은 항목 타입을 콜백에 그대로 돌려주는" 컴포넌트는 제네릭으로 만든다.

```tsx
type SelectProps<T> = {
  options: T[];
  value: T;
  getLabel: (option: T) => string;
  onChange: (option: T) => void;
};
function Select<T>({ options, value, getLabel, onChange }: SelectProps<T>) {
  return (
    <select value={options.indexOf(value)} onChange={(e) => onChange(options[Number(e.target.value)])}>
      {options.map((o, i) => <option key={i} value={i}>{getLabel(o)}</option>)}
    </select>
  );
}

// .tsx에서 화살표 함수 제네릭은 <T,>로 쓴다
const List = <T,>({ items, render }: { items: T[]; render: (item: T) => ReactNode }) => (
  <ul>{items.map((it, i) => <li key={i}>{render(it)}</li>)}</ul>
);

<Select options={fruits} value={fruit} getLabel={(f) => f.name} onChange={(f) => setFruit(f)} />
<Select options={fruits} value={fruit} getLabel={(f) => f.label} onChange={setFruit} />
```

```text
generic.tsx(53,65): error TS2339: Property 'label' does not exist on type 'Fruit'.
```

`options`에 `Fruit[]`를 넘기는 순간 `T`가 `Fruit`로 정해지고, `getLabel`과 `onChange`의 `f`도 `Fruit`가 된다. 사용하는 쪽은 타입 인자를 적지 않아도 되고, `onChange`에서 받은 값을 `as Fruit`로 단언할 필요도 없다. `.tsx`에서 화살표 함수에 `<T,>`를 쓰는 이유와 제네릭 훅, 추론이 실패하는 경우는 [제네릭](/posts/ts-generics) 글에서 다룬다.

## Context와 커스텀 훅이 돌려주는 타입

Context는 Provider 바깥에서 쓰이면 기본값을 돌려준다. 그럴듯한 기본값이 없으면 `null`로 두고, 확인하는 훅을 하나 만들어 그것만 쓰게 한다.

```tsx
type Theme = { mode: "light" | "dark"; toggle: () => void };
const ThemeContext = createContext<Theme | null>(null);

function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("useTheme은 ThemeProvider 안에서만 쓸 수 있다");
  return ctx;   // Theme
}

const raw = useContext(ThemeContext);
<p>{raw.mode}</p>
```

```text
generic.tsx(57,11): error TS18047: 'raw' is possibly 'null'.
```

`useTheme`은 확인을 한 곳에 모으고 돌려주는 값을 `Theme`으로 좁힌다. 기본값으로 `{} as Theme`을 넣는 코드도 흔한데, Provider를 빠뜨렸을 때 `toggle is not a function`이 엉뚱한 곳에서 나서 원인을 찾기 어렵다. 위처럼 빨리 실패하게 하면 에러 메시지가 원인을 말해 준다.

커스텀 훅에서 배열을 돌려줄 때는 튜플로 고정해야 한다.

```tsx
function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = () => setOn((v) => !v);
  return [on, toggle];             // (boolean | (() => void))[]
}
function useToggle2(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = () => setOn((v) => !v);
  return [on, toggle] as const;    // readonly [boolean, () => void]
}

const [open, toggleOpen] = useToggle();
<button onClick={toggleOpen}>{String(open)}</button>
```

```text
generic.tsx(55,15): error TS2322: Type 'boolean | (() => void)' is not assignable to type 'MouseEventHandler<HTMLButtonElement> | undefined'.
  Type 'boolean' is not assignable to type 'MouseEventHandler<HTMLButtonElement>'.
```

배열 리터럴은 기본으로 "원소 타입들의 유니온 배열"로 추론된다. 위치마다 타입이 다르다는 정보를 남기려면 `as const`나 반환 타입 `[boolean, () => void]`를 적는다. 돌려줄 것이 셋 이상이면 이름 있는 객체로 돌려주는 편이 쓰는 쪽에서 헷갈리지 않는다.

## 연습: 조건부 클래스 이름을 합치는 cx

`useReducer`의 액션을 판별 유니온으로 만들고 `dispatch`에서 잘못된 액션을 잡는 방법은 [타입 좁히기](/posts/ts-narrowing) 글에서 실제 에러와 함께 다뤘으니 여기서는 넘어간다. 대신 앞의 `Button`에서 쓴 `cx`를 직접 만들어 보자. 래퍼 컴포넌트가 받은 `className`과 자기 클래스를 합칠 때 매번 쓰는 함수다(`clsx`, `classnames` 같은 라이브러리가 하는 일). 인자 타입은 자기 자신을 품는 재귀 타입이다.

```ts
type ClassDict = Record<string, boolean | null | undefined>;
type ClassValue = string | number | bigint | boolean | null | undefined | ClassDict | ClassValue[];
```

규칙은 이렇다. 거짓 같은 값(`false`, `null`, `undefined`, `0`, 빈 문자열)은 건너뛴다. 그래서 `isActive && "active"`처럼 써도 된다. 문자열과 숫자는 그대로 넣고, 배열은 안쪽을 같은 규칙으로 펼치고, 객체는 값이 참인 키만 넣는다. `true` 자체는 클래스 이름이 아니니 건너뛴다. 아래 그림은 인자 하나하나가 결과에 들어가는지를 보여 준다.

## 다시 null로 시작한 상태로

처음 에러는 TypeScript가 초기값만 보고 상태의 모양을 정했기 때문에 났다. React에서 TypeScript를 쓸 때 대부분의 타입은 추론에 맡기고, 추론이 실제 의도보다 좁아지는 자리에서만 적으면 된다. 비어서 시작하는 상태(`null`, 빈 배열), 따로 뺀 이벤트 핸들러, `null`로 시작하는 ref, 튜플을 돌려주는 훅이 그런 자리다. props는 함께 와야 하는 것을 판별 유니온으로 묶고, 기본 요소를 감쌀 때는 `ComponentProps`에서 빼고 더한다. `@types/react`의 버전에 따라 `useRef`, `ref` prop, 이벤트 타입이 달라지니 업그레이드할 때는 그 부분부터 본다. 전체 학습 순서는 [TypeScript 로드맵](/posts/typescript-roadmap)에 정리했다.

## 면접에서 나올 만한 질문

### useState(null)로 시작한 상태에 값을 넣으면 왜 에러가 나나요?

타입 인자를 주지 않으면 `useState`가 초기값에서 상태 타입을 추론하는데, `null`에서는 `null` 타입만 나오기 때문이다. 그래서 `setUser(user)`가 `SetStateAction<null>`에 맞지 않는다는 에러가 난다. `useState<User | null>(null)`처럼 들어올 값을 적고, 쓸 때 null인지 확인한다. 빈 배열도 같은 이유로 `never[]`가 되니 원소 타입을 적는다.

### children의 타입은 무엇으로 하나요?

대부분 `ReactNode`로 한다. JSX 엘리먼트, 문자열, 숫자, null, boolean, 배열 등 React가 그릴 수 있는 것 전부를 포함하고, 일반 객체는 빠져서 "Objects are not valid as a React child" 런타임 에러를 컴파일 단계에서 막는다. JSX 하나만 받아야 할 때는 `ReactElement`로 좁히지만, 특정 컴포넌트의 엘리먼트만 받게 하는 건 타입으로 할 수 없다.

### React.FC를 쓰지 않는 이유는 무엇인가요?

쓰면 안 되는 건 아니지만 예전만큼 쓸 이유가 없다. `@types/react` 18부터 `FC`가 `children`을 자동으로 넣지 않아 props를 어차피 직접 적어야 하고, 화살표 함수에 타입을 붙이는 형태라 제네릭 컴포넌트를 만들기 불편하다. 함수 선언에 props 타입을 적으면 같은 효과에 제네릭과 호이스팅까지 자연스럽다.

### 이벤트 핸들러에서 e.target과 e.currentTarget의 타입이 다른 이유는요?

`target`은 이벤트가 실제로 일어난 요소라 버튼 안의 아이콘처럼 어떤 요소일지 알 수 없고, `currentTarget`은 핸들러를 단 요소라 타입을 확정할 수 있기 때문이다. 그래서 `MouseEvent<HTMLButtonElement>`에서 `currentTarget`만 `HTMLButtonElement`이고 `target`은 `EventTarget`이다. `ChangeEvent`만 호환성 때문에 `target`도 요소 타입으로 정의되어 있다.

### `useRef<HTMLInputElement>(null)`의 current는 왜 null일 수 있나요?

ref는 렌더링 중에는 비어 있다가 커밋 단계에서 DOM 요소가 들어오고, 언마운트되면 다시 null이 되기 때문이다. 조건부 렌더링으로 요소가 빠질 수도 있어서 effect 안에서도 null 확인이 필요하다. `@types/react` 19에서는 `RefObject<HTMLInputElement | null>`로 이 사실이 타입에 드러나고, `useRef`에 인자가 꼭 필요하다.

### 서로 배타적인 props는 어떻게 타입으로 표현하나요?

공통 판별 필드(`kind`, `variant` 등)를 둔 유니온으로 경우마다 타입을 나눈다. 그러면 confirm인데 `onConfirm`이 빠지거나 alert에 `onConfirm`이 섞이는 것을 컴파일 에러로 잡는다. 컴포넌트 안에서는 `props.kind`로 좁혀 쓰고, `...rest`로 구조 분해하면 좁히기가 끊기니 props를 통째로 받아 분기 안에서 꺼낸다.

### 기본 button을 감싸는 컴포넌트의 props는 어떻게 만드나요?

`ComponentProps<"button">`으로 기본 속성을 모두 받고, 다르게 정할 속성은 `Omit`으로 뺀 뒤 `&`로 우리 props를 더한다. 빼지 않고 더하면 덮어쓰는 게 아니라 교차되어, `onChange`처럼 시그니처를 바꾼 속성에는 맞는 함수가 없어진다. React 19에서는 `ref`도 일반 prop이라 그대로 넘어가고, 18에서는 `forwardRef`가 필요하다. `...rest`를 펼치는 위치로 사용하는 쪽이 덮어쓸 수 있는 범위를 정한다.
