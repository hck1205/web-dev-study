`Math.pow`나 `**` 한 줄이면 끝나는 일을 왜 직접 짤까. 거듭제곱을 빠르게 하는 방법(빠른 거듭제곱, exponentiation by squaring)은 RSA 암호의 모듈러 거듭제곱, 행렬 거듭제곱으로 피보나치 수 구하기, 큰 수의 나머지 계산에 그대로 쓰인다. 라이브러리 함수가 실수에서는 해 주지만, 나머지 연산이 끼거나 행렬이 되면 직접 짜야 한다. [Pow(x, n)](https://leetcode.com/problems/powx-n/)은 그 기법을 가장 단순한 형태로 연습하는 문제다. 그리고 지수가 -2^31일 때 터지는 정수 함정이 하나 숨어 있다.

이 글은 풀이 다섯 개를 놓는다. n번 곱하는 반복, 한 번씩 줄이는 재귀, 반으로 나누는 재귀, 지수의 비트를 읽는 반복, 그리고 로그와 지수 함수다. 분할 정복이라는 큰 틀은 [분할 정복 글](/posts/divide-and-conquer)에서, 비트를 읽는 연산은 [비트 연산 글](/posts/bit-manipulation)에서 다뤘다. 코드는 모두 Node.js 22, Python 3, Java 21에서 직접 돌렸다.

## x를 n번 곱한 값을 구한다

실수 `x`와 정수 `n`이 주어진다. x의 n제곱을 돌려준다. 라이브러리 거듭제곱 함수는 쓰지 않는다는 게 문제의 취지다.

- `x`는 -100보다 크고 100보다 작은 실수다.
- `n`은 32비트 정수 전체 범위(-2^31 이상 2^31 - 1 이하)다. 음수일 수 있다.
- x가 0이 아니거나 n이 양수라고 약속한다. 0의 음수 제곱(0으로 나누기)은 들어오지 않는다.
- 답의 절댓값은 10^4 이하다.

두 번째 제약이 이 문제의 전부다. n이 최대 약 21억이라 n번 곱하는 방법은 너무 느리고, 음수 쪽 끝인 -2^31은 부호를 바꾸면 양수 쪽 끝 2^31 - 1을 넘는다. 네 번째 제약은 결과가 엄청 커지거나 작아지는 경우를 상당히 걸러 준다. 다만 2의 -2^31제곱처럼 0에 아주 가까워서 0으로 처리되는 답은 들어올 수 있다.

## 3의 13제곱을 손으로 줄여 보기

3을 13번 곱하면 1,594,323이다. 곱셈은 12번 한다. 이걸 줄이는 관찰은 두 가지다.

첫째, 제곱하면 지수가 두 배가 된다. 3² = 9, 9² = 81 = 3⁴, 81² = 6561 = 3⁸이다. 곱셈 세 번으로 3⁸까지 왔다.

둘째, 지수는 더해진다. 3^13 = 3^(8 + 4 + 1) = 3⁸ × 3⁴ × 3¹이다. 13을 8 + 4 + 1로 나누는 건 13을 2진수로 쓰는 것과 같다. 13은 2진수로 `1101`이고, 1인 자리가 1, 4, 8이다.

```text
13 = 1101(2) = 8 + 4 + 1
3^13 = 3^8 × 3^4 × 3^1 = 6561 × 81 × 3 = 1,594,323
```

3, 3², 3⁴, 3⁸을 만드는 데 제곱 세 번, 그중 필요한 것 셋을 곱하는 데 곱셈 두 번이다. 열두 번이 다섯 번이 됐다. n이 21억이면 차이가 훨씬 크다. 21억은 2진수로 31자리라서 제곱 31번과 곱셈 많아야 31번이면 된다.

## n번 곱하기

가장 먼저 쓰는 코드는 정의 그대로다. 음수 지수는 x를 1/x로 바꾸고 양수로 만든다. x^(-n) = (1/x)^n이기 때문이다.

```js
function myPow(x, n) {
  let N = n;
  if (N < 0) { x = 1 / x; N = -N; }   // 음수 지수는 역수의 양수 지수로
  let r = 1;
  for (let i = 0; i < N; i++) r *= x;
  return r;
}
```

시간은 O(|n|), 공간은 O(1)이다. 1억 번에 내 컴퓨터에서 156ms, n = 2^31 - 1이면 3.06초가 걸렸다. 테스트 하나에 3초면 LeetCode에서 시간 초과다.

JavaScript에서는 `-N`이 문제를 일으키지 않는다. 숫자가 모두 64비트 실수라 2^31도 정확히 표현된다. Java와 C++에서는 바로 이 줄이 터지는데, 뒤에서 따로 본다.

## 한 번씩 줄이는 재귀

재귀로 쓰면 x^n = x × x^(n-1)이다. 반복문과 하는 일은 같지만 이 실수를 한 번은 짚을 만하다.

```js
function myPow(x, n) {
  if (n === 0) return 1;
  if (n < 0) return 1 / myPow(x, -n);
  return x * myPow(x, n - 1);          // 지수를 1씩 줄인다
}
console.log(myPow(2, 10));    // 1024
myPow(2, 20000);              // RangeError: Maximum call stack size exceeded
```

시간 O(n)에 더해 호출 스택이 n단계로 쌓인다. Node.js 기본 설정에서 지수 2만에서 스택이 넘쳤다. 반복문보다 나쁜 풀이지만, 다음 풀이가 여기서 한 글자만 바꾼 것이라 출발점으로 둔다. `n - 1` 대신 `n / 2`로 줄이면 된다.

## 반으로 나누는 재귀

x^n을 x^(n/2)로 만든다.

- n이 짝수면 x^n = x^(n/2) × x^(n/2)
- n이 홀수면 x^n = x^(n/2) × x^(n/2) × x (n/2는 내림)

같은 값 x^(n/2)를 두 번 쓰니 한 번만 계산해 변수에 담는다.

```js
function myPow(x, n) {
  if (n < 0) return myPow(1 / x, -n);   // 음수 지수는 역수로
  if (n === 0) return 1;
  const half = myPow(x, Math.floor(n / 2)); // 반만 구한다
  return n % 2 === 0 ? half * half : half * half * x;
}
```

3^13을 넣으면 13, 6, 3, 1, 0으로 지수가 반씩 줄며 내려갔다가, 돌아오면서 제곱한다. 아래 그림에서 왼쪽이 내려가는 호출, 오른쪽이 돌아오는 값이다. 점이 화살표를 따라 바닥까지 내려갔다가 다시 올라온다.

지수가 매번 반이 되니 호출 깊이는 log₂n + 1이다. n = 2^31 - 1이어도 32단계라 스택 걱정이 없다. 호출마다 곱셈이 한두 번이라 시간 O(log n), 스택 공간 O(log n)이다.

음수 처리를 `myPow(1 / x, -n)`으로 바꾼 데도 이유가 있다. 앞 풀이처럼 `1 / myPow(x, -n)`으로 해도 수학적으로는 같지만, x^|n|이 실수 범위를 넘는 경우 차이가 난다. 예를 들어 0.5^(-2000)은 무한대지만 문제는 그런 입력을 주지 않는다. 반대로 2^(-2000)은 0에 가까운 작은 수인데, `1 / myPow(2, 2000)`은 2^2000이 무한대(`Infinity`)가 된 뒤 1을 나눠 0을 내고, 역수부터 곱하는 쪽은 0.5를 거듭 곱해 0에 수렴한다. 이 경우는 둘 다 0이지만, 큰 수를 먼저 만들어 나누는 방식은 중간값이 넘칠 위험이 있다는 걸 알아 둔다.

### 반을 두 번 구하면 다시 느려진다

`half` 변수 없이 `myPow(x, n / 2) * myPow(x, n / 2)`로 쓰면 어떻게 될까. 호출이 매번 두 갈래로 갈라진다. 깊이는 log n인데 갈래가 두 배씩 늘어서, 호출 수가 2^(log n) = n에 비례한다. 직접 세어 보니 n = 1023에서 2,047번, n = 100만에서 2,097,151번 호출됐다. 반으로 나눴는데도 O(n)이다. 같은 값을 두 번 계산하지 않는 것, 즉 겹치는 부분 문제를 한 번만 푸는 것이 이 풀이의 속도를 만든다.

## 지수의 비트를 오른쪽부터 읽는다

재귀를 반복문으로 바꾸면 스택도 필요 없다. 앞에서 손으로 한 계산 그대로다. 지수를 2진수로 보고 가장 낮은 비트부터 읽는다.

- `x`는 차례로 x, x², x⁴, x⁸, ...이 된다. 매 단계 제곱한다.
- 지금 읽는 비트가 1이면 그때의 `x`를 결과에 곱한다.
- 지수를 2로 나눠(오른쪽으로 한 칸 밀어) 다음 비트로 간다.

```js
function myPow(x, n) {
  let N = n;
  if (N < 0) { x = 1 / x; N = -N; }   // 음수 지수는 역수의 양수 지수로
  let result = 1;
  while (N > 0) {
    if (N % 2 === 1) result *= x;     // 이번 비트가 1이면 지금의 x를 곱한다
    x *= x;                           // x, x², x⁴, x⁸ ...
    N = Math.floor(N / 2);            // 다음 비트로
  }
  return result;
}
```

3^13을 이 코드로 돌리며 단계마다 값을 찍어 옮겼다. 칸은 13의 비트를 낮은 자리부터 놓은 것이다.

마지막 단계의 `x *= x`는 쓸데없는 곱셈이다. 43,046,721(3^16)은 아무 데도 쓰이지 않는다. 지우려면 `if (N > 1)` 같은 조건을 붙여야 하는데, 곱셈 한 번 아끼자고 분기를 늘릴 이유는 없다. 다만 모듈러 거듭제곱에서 x가 큰 정수라면 이 마지막 제곱이 넘침을 일으킬 수 있어서, 그때는 신경 쓴다.

곱셈 횟수는 비트 수만큼 제곱하고, 1인 비트 수만큼 결과에 곱한다. 13에서 7번, 2^31 - 1(1이 31개)에서 62번이다. 시간 O(log n), 공간 O(1)이다. 이 풀이를 기본 답으로 삼는다.

`N % 2`와 `Math.floor(N / 2)` 대신 `N & 1`과 `N >>= 1`을 쓰고 싶어진다. Python과 Java(`long`)에서는 그게 자연스럽지만 JavaScript에서는 위험하다. 실수 절에서 출력과 함께 본다.

### 몇 번 곱하나

지수별로 제곱 횟수와 결과에 곱한 횟수를 세어 봤다.

```text
n                제곱   결과에 곱하기   n번 곱하기라면
13               4      3              13
1,000            10     6              1,000
1,000,000        20     7              1,000,000
2,147,483,647    31     31             2,147,483,647
2,147,483,648    32     1              2,147,483,648
```

제곱 횟수는 비트 수, 곱하기 횟수는 1인 비트 수다. 2^31 - 1은 31비트가 모두 1이라 곱셈이 가장 많은 경우고, 바로 다음 수 2^31은 1이 하나뿐이라 곱하기가 한 번이다. 마지막 줄의 2^31이 바로 n = -2^31의 부호를 바꾼 값이다.

### 왼쪽 비트부터 읽어도 된다

비트를 높은 자리부터 읽는 방법도 있다. 결과를 제곱하면 지금까지 만든 지수가 두 배가 되고(2진수로 한 칸 왼쪽으로 밀기), 비트가 1이면 x를 곱해 지수에 1을 더한다.

```js
function myPow(x, n) {
  let N = n;
  if (N < 0) { x = 1 / x; N = -N; }
  const bits = N.toString(2);       // 높은 비트부터 읽는다
  let result = 1;
  for (const b of bits) {
    result *= result;               // 지금까지의 지수를 두 배로
    if (b === "1") result *= x;     // 비트가 1이면 지수에 1을 더한다
  }
  return result;
}
// 13 = "1101": 지수가 1 → 3 → 6 → 13, 값이 3 → 27 → 729 → 1594323
```

곱셈 횟수는 오른쪽부터 읽는 방법과 같다. 차이는 곱하는 값이다. 왼쪽부터 읽으면 결과에 늘 원래의 x를 곱하고, 오른쪽부터 읽으면 x², x⁴처럼 계속 바뀌는 값을 곱한다. x가 작은 수이고 곱셈 비용이 값의 크기에 따라 달라지는 경우(큰 정수 연산)에는 왼쪽부터가 유리하다. 대신 비트를 미리 알아야 해서 문자열로 바꾸거나 가장 높은 비트 위치를 먼저 구해야 한다. 면접에서는 오른쪽부터 읽는 쪽이 코드가 짧아 더 흔하다.

## 로그와 지수 함수로 계산하기

수학적으로 x^n = e^(n × ln x)다. 한 줄로 끝난다.

```js
const pow = (x, n) => Math.exp(n * Math.log(x));
console.log(pow(1.0001, 100000)); // 22015.456048527933
console.log(pow(-2, 3));          // NaN
```

시간 O(1)이지만 두 가지가 걸린다. 음수 x의 로그는 실수에서 정의되지 않아 `NaN`이 나온다. -2의 세제곱은 -8인데 말이다. 부호를 따로 처리해야 한다(n이 홀수면 음수). 또 `Math.log`와 `Math.exp`가 각각 반올림 오차를 내고, n × ln x에서 오차가 n배로 커진다. 면접에서 이걸 답으로 내면 "라이브러리 함수를 쓰지 말라"는 취지와도 맞지 않는다. 라이브러리의 `Math.pow`가 실제로 이 방식을 그대로 쓰는 것도 아니다. 구현마다 오차를 줄이는 별도 처리를 한다.

## 빠르다고 더 정확하지는 않다

곱셈을 덜 하니 반올림 오차도 덜 쌓일 것 같다. 직접 재 봤다. 1.0001의 10만 제곱을 50자리 정밀도의 십진 연산으로 구한 기준값과 비교했다.

```text
기준값 (50자리)       22015.456048527954540...
Math.pow             22015.456048527954
n번 곱하기             22015.45604852786
비트 읽기 (빠른 거듭제곱) 22015.456048481854
```

`Math.pow`가 가장 정확했고, 놀랍게도 n번 곱하기가 빠른 거듭제곱보다 기준값에 가까웠다. 빠른 거듭제곱은 x를 계속 제곱하는데, 제곱할 때마다 그때까지의 상대 오차도 두 배가 된다. 오차가 적은 횟수로 생기지만 생긴 오차가 크게 불어나는 셈이다. n번 곱하기는 오차가 매번 조금씩 생기지만 서로 상쇄되기도 해서 결과적으로 덜 틀렸다. 실수 연산의 오차가 왜 이렇게 움직이는지는 [부동소수점 글](/posts/floating-point-numbers)에 있다.

여기서 빠른 거듭제곱의 차이는 열두 번째 유효숫자부터라 이 문제의 답에는 영향이 없지만, 정확도가 중요한 계산이라면 직접 짠 거듭제곱보다 라이브러리 함수가 낫다. 빠른 거듭제곱이 진짜 빛나는 곳은 정수 나머지 연산처럼 오차가 없는 세계다.

## Python과 Java로 옮기기

```python
class Solution:
    def myPow(self, x: float, n: int) -> float:
        if n < 0:                    # 음수 지수는 역수의 양수 지수로
            x, n = 1 / x, -n
        result = 1.0
        while n > 0:
            if n & 1:                # 이번 비트가 1이면 지금의 x를 곱한다
                result *= x
            x *= x                   # x, x², x⁴, x⁸ ...
            n >>= 1                  # 다음 비트로
        return result

    def myPowRec(self, x: float, n: int) -> float:
        if n < 0:
            return self.myPowRec(1 / x, -n)
        if n == 0:
            return 1.0
        half = self.myPowRec(x, n // 2)
        return half * half if n % 2 == 0 else half * half * x

s = Solution()
print(s.myPow(2.0, 10), s.myPow(2.0, -2), s.myPow(2.1, 3), s.myPow(1.0, -2147483648))
print(s.myPowRec(3.0, 13), s.myPowRec(-1.0, -2147483647))
```

```text
1024.0 0.25 9.261000000000001 1.0
1594323.0 -1.0
```

Python 정수는 크기 제한이 없어서 `-n`도, `n & 1`과 `n >>= 1`도 어떤 크기에서나 안전하다. `n // 2`는 음수에서 내림이라 -3 // 2가 -2가 되지만, 위 코드는 음수를 먼저 양수로 바꾸니 상관없다. 재귀 깊이도 32단계라 기본 한도 1000에 한참 못 미친다.

실수가 넘칠 때 Python은 두 얼굴을 보인다. `2.0 ** 1100`은 `OverflowError`를 던지지만, 같은 값을 `*=`로 1100번 곱하면 `inf`가 된다. 직접 짠 거듭제곱은 예외 없이 `inf`를 돌려준다는 걸 알아 둔다.

```java
class Solution {
    public double myPow(double x, int n) {
        long N = n;                  // int로 -n을 하면 -2^31에서 넘친다
        if (N < 0) {
            x = 1 / x;
            N = -N;
        }
        double result = 1.0;
        while (N > 0) {
            if ((N & 1) == 1) result *= x;  // 이번 비트가 1이면 곱한다
            x *= x;
            N >>= 1;
        }
        return result;
    }

    public static void main(String[] args) {
        Solution s = new Solution();
        System.out.println(s.myPow(2.0, 10) + " " + s.myPow(2.0, -2) + " " + s.myPow(2.1, 3));
        System.out.println(s.myPow(1.0, Integer.MIN_VALUE) + " " + s.myPow(2.0, Integer.MIN_VALUE));
        int n = Integer.MIN_VALUE;
        System.out.println(-n + " " + Math.abs(n));
    }
}
```

```text
1024.0 0.25 9.261000000000001
1.0 0.0
-2147483648 -2147483648
```

마지막 줄이 이 문제의 함정이다. `int`의 범위는 -2^31부터 2^31 - 1까지라서, -2^31의 부호를 바꾼 2^31은 들어갈 자리가 없다. Java는 예외 없이 값을 감아서 -n이 다시 -2^31이 된다. `Math.abs`도 마찬가지로 음수를 돌려준다. 그래서 지수를 `long`에 먼저 옮긴 뒤 부호를 바꾼다.

| 풀이 | 시간 | 추가 공간 | 언제 고르나 |
|---|---|---|---|
| n번 곱하기 | O(n) | O(1) | 정의 확인용. n이 수천 이하일 때만 |
| 한 번씩 줄이는 재귀 | O(n) | O(n) 스택 | 쓰지 않는다. 다음 풀이의 출발점 |
| 반으로 나누는 재귀 | O(log n) | O(log n) 스택 | 점화식으로 설명하기 쉽다. 행렬·다항식 거듭제곱에도 그대로 |
| 비트 읽는 반복 | O(log n) | O(1) | 기본 답. 모듈러 거듭제곱의 표준 모양 |
| 로그와 지수 함수 | O(1) | O(1) | 실수 근사가 괜찮고 x가 양수일 때. 이 문제의 취지와는 맞지 않는다 |

## 거듭제곱에서 자주 틀리는 곳

### Java에서 int 지수의 부호를 바로 바꾼다

```java
if (n < 0) { x = 1 / x; n = -n; }   // n이 -2^31이면 -n도 -2^31
while (n > 0) { /* ... */ }          // 한 번도 돌지 않는다
// myPow(2.0, Integer.MIN_VALUE) → 1.0 (정답은 0.0)
```

-n이 여전히 음수라 반복이 한 번도 돌지 않고 1.0을 돌려준다. `x = 1.0`인 테스트에서는 정답도 1.0이라 우연히 통과해서 더 찾기 어렵다. LeetCode 테스트에 `n = -2147483648`이 실제로 있다. `long N = n`으로 옮기는 게 정석이다. C++도 같다.

### JavaScript에서 비트 연산으로 지수를 나눈다

```js
let N = 2147483648;   // n = -2^31의 부호를 바꾼 값
console.log(N >> 1);  // -1073741824
console.log(N >>> 1); // 1073741824
```

JavaScript의 `>>`, `&`는 피연산자를 32비트 부호 있는 정수로 바꾼 뒤 계산한다. 2^31은 32비트 부호 있는 범위를 벗어나 -2^31로 읽히고, 한 칸 밀면 음수가 된다. 비트 연산으로 쓴 반복은 첫 바퀴 뒤 `N`이 음수가 돼서 멈추고, `myPow(2, -2147483648)`이 0이 아니라 1을 돌려준다. 부호 없는 밀기 `>>>`는 이 값에서는 맞지만 2^32 이상에서 또 깨진다. 이 문제에서는 `N % 2`와 `Math.floor(N / 2)`가 안전하다.

### 2로 나눌 때 내림을 빼먹는다

`N = N / 2`로 쓰면 13이 6.5, 3.25로 소수가 되고, `N % 2 === 1`이 거의 참이 되지 않는다. 그동안 x는 계속 제곱되다 무한대가 된다. 실제로 3^13이 1,594,323이 아니라 3이 나왔다. 정수 나눗셈이 없는 JavaScript에서 거듭제곱 코드가 엉뚱한 값을 내면 이것부터 본다.

### 반을 변수에 담지 않는다

앞에서 본 대로 `myPow(x, n/2) * myPow(x, n/2)`는 호출이 두 갈래로 갈라져 O(n)이 된다. 답은 맞으니 작은 테스트로는 모른다. 큰 n에서 시간 초과로만 드러난다.

### 0과 음수 x를 잊는다

x = 0, n > 0이면 0이고, n = 0이면 x가 무엇이든 1이다. 코드는 둘 다 자연스럽게 처리한다. 음수 x는 n이 짝수면 양수, 홀수면 음수여야 한다. 비트 풀이는 x를 그대로 곱하니 부호가 저절로 맞지만, 로그 풀이는 `NaN`을 낸다. x = -1과 n = -2147483647(홀수)로 -1이 나오는지 확인한다.

## 같은 뼈대로 푸는 문제들

### 나머지를 구하라면 (모듈러 거듭제곱)

x^n mod m은 비트 풀이에서 곱할 때마다 `% m`을 하면 된다. 나머지 연산은 곱셈과 순서를 바꿔도 되기 때문이다. 정수라 오차가 없다. 3^200 mod 1,000,000,007처럼 결과가 수십 자리를 넘는 계산도 곱셈 몇백 번이면 끝난다. JavaScript에서는 두 수의 곱이 2^53을 넘으면 정밀도가 깨지니 `BigInt`를 쓰고, Java는 `long`으로 곱한 뒤 나눈다. 이유는 [JS 숫자와 BigInt 글](/posts/js-numbers-bigint)에 있다. 372. Super Pow가 이 문제다.

```js
function modPow(base, exp, mod) {
  let result = 1n, b = BigInt(base) % BigInt(mod), e = BigInt(exp);
  const m = BigInt(mod);
  while (e > 0n) {
    if (e & 1n) result = (result * b) % m;  // BigInt의 비트 연산은 크기 제한이 없다
    b = (b * b) % m;
    e >>= 1n;
  }
  return result;
}
console.log(modPow(3, 200, 1000000007)); // 3^200을 1e9+7로 나눈 나머지
```

```text
136318165n
```

`BigInt`에서는 `&`와 `>>`가 32비트로 잘리지 않아 안전하다. 앞의 실수와 대조된다.

실무 코드라면 직접 짜기 전에 언어가 주는 것부터 쓴다. Python의 내장 `pow`는 세 번째 인자로 나머지를 받고, Java는 `BigInteger.modPow`가 있다. 둘 다 안에서 같은 빠른 거듭제곱을 한다.

```python
print(pow(3, 200, 1_000_000_007))   # 3^200 mod (1e9+7)
print(pow(3, -1, 1_000_000_007))    # 3의 곱셈 역원 (Python 3.8+)
```

```text
136318165
333333336
```

```java
BigInteger p = BigInteger.valueOf(1_000_000_007L);
System.out.println(BigInteger.valueOf(3).modPow(BigInteger.valueOf(200), p)); // 136318165
```

세 방법 모두 같은 값을 냈다. Python 3.8부터는 지수에 -1을 주면 곱셈 역원을 구해 준다. 3 × 333,333,336을 1e9+7로 나눈 나머지가 1이다. 나머지가 소수일 때 역원은 페르마의 소정리로 x^(p-2) mod p이기도 해서, 결국 이것도 빠른 거듭제곱이다.

### 행렬을 거듭제곱하라면

곱셈만 정의되면 같은 코드가 통한다. 피보나치 수는 2 × 2 행렬 `[[1,1],[1,0]]`의 n제곱에서 나온다. 행렬 곱셈 한 번이 O(1)(크기 2 고정)이라 n번째 피보나치 수를 O(log n)에 구한다. 509. Fibonacci Number나 [70. Climbing Stairs](/posts/leetcode-climbing-stairs)를 이 방법으로 풀 수 있다. 결과 초깃값 1은 단위 행렬로 바뀐다.

```js
function matMul(a, b) {
  return [
    [a[0][0] * b[0][0] + a[0][1] * b[1][0], a[0][0] * b[0][1] + a[0][1] * b[1][1]],
    [a[1][0] * b[0][0] + a[1][1] * b[1][0], a[1][0] * b[0][1] + a[1][1] * b[1][1]],
  ];
}
function fib(n) {
  let result = [[1, 0], [0, 1]];    // 단위 행렬 (숫자의 1에 해당)
  let m = [[1, 1], [1, 0]];
  while (n > 0) {                   // myPow와 똑같은 뼈대
    if (n % 2 === 1) result = matMul(result, m);
    m = matMul(m, m);
    n = Math.floor(n / 2);
  }
  return result[0][1];              // m^n = [[F(n+1), F(n)], [F(n), F(n-1)]]
}
console.log([0, 1, 2, 3, 10, 50, 78].map(fib).join(" "));
```

```text
0 1 1 2 55 12586269025 8944394323791464
```

F(78)은 8,944,394,323,791,464로 2^53(약 9.007×10^15) 바로 아래다. F(79)부터는 `Number`로 정확히 담을 수 없으니 `BigInt`로 바꾸거나 나머지를 취한다.

## 면접에서 나올 만한 질문

### 왜 O(log n)인가요?

지수를 매 단계 반으로 줄이기 때문이다. 지수를 2진수로 보면 비트 수가 log₂n + 1개고, 비트마다 제곱 한 번과 많아야 곱셈 한 번을 한다. n = 2^31 - 1이어도 곱셈은 62번이다.

### 재귀에서 반을 변수에 담지 않으면 어떻게 되나요?

`pow(x, n/2) * pow(x, n/2)`는 호출이 두 갈래로 갈라져서, 깊이는 log n이지만 호출 수가 n에 비례한다. n = 1023에서 2,047번 호출됐다. 같은 부분 문제를 한 번만 풀어야 O(log n)이 된다.

### 음수 지수는 어떻게 처리하나요?

x^(-n) = (1/x)^n이니 x를 역수로 바꾸고 지수를 양수로 만든다. 큰 값을 먼저 만든 뒤 1을 나누는 방식보다 역수부터 곱하는 쪽이 중간값이 넘칠 위험이 적다. x가 0이고 n이 음수인 경우는 0으로 나누기라 문제에서 막아 두었다.

### n이 -2^31이면 무엇을 조심해야 하나요?

32비트 정수에서 -2^31의 부호를 바꾸면 2^31인데, `int` 최댓값이 2^31 - 1이라 넘쳐서 다시 -2^31이 된다. Java에서는 반복이 한 번도 돌지 않아 1.0이 나온다. 지수를 `long`에 옮긴 뒤 부호를 바꾼다. JavaScript는 숫자가 64비트 실수라 부호는 괜찮지만, 비트 연산 `>>`가 32비트로 잘라서 같은 값에서 틀린다.

### 반복 풀이에서 x를 계속 제곱하는데 넘치지 않나요?

이 문제는 답이 10^4 이하라고 약속해서 결과는 넘치지 않지만, 마지막 단계의 쓰지 않는 제곱은 커질 수 있다. 실수라면 무한대가 될 뿐 결과에 쓰이지 않아 문제없다. 정수 모듈러 거듭제곱이라면 곱할 때마다 나머지를 취하고, 곱셈 결과가 자료형을 넘지 않는지(JavaScript는 2^53, Java는 `long`) 확인한다.

### 빠른 거듭제곱이 n번 곱하기보다 더 정확한가요?

꼭 그렇지 않다. 실제로 1.0001의 10만 제곱에서 n번 곱하기가 빠른 거듭제곱보다 정확했다. 제곱을 거듭하면 그때까지의 상대 오차도 두 배씩 커지기 때문이다. 정확도가 중요하면 라이브러리 함수를 쓰고, 빠른 거듭제곱은 오차가 없는 정수 나머지 연산에서 쓰는 게 제자리다.

### 이 기법을 어디에 쓰나요?

RSA 같은 공개 키 암호의 모듈러 거듭제곱, 행렬 거듭제곱으로 선형 점화식(피보나치 등)을 O(log n)에 푸는 것, 큰 수의 나머지 계산이다. 곱셈이 결합 법칙을 만족하는 연산이면 숫자가 아니어도 된다. 그래프의 인접 행렬을 거듭제곱해 길이 k인 경로 수를 세는 것도 같은 코드다.
