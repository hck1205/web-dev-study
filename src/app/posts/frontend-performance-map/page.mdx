상품 페이지를 개발자 노트북에서 열면 첫 사진이 260ms 만에 뜬다. 느리다고 할 사람이 없다. 같은 페이지를 느린 망과 느린 CPU를 흉내 낸 조건에서 열면 4,212ms가 걸린다. 사용자 리뷰에 "페이지가 안 열려요"가 올라오는 쪽은 두 번째 숫자다.

프런트엔드 성능 작업은 손댈 곳이 너무 많아서 길을 잃기 쉽다. 번들, 이미지, 폰트, CSS, 렌더링, 하이드레이션, 데이터 요청, 캐시. 각각에 글이 하나씩 있을 만큼 깊다. 이 글은 그 글들을 한 장의 지도로 묶는다. 무엇부터 재고, 숫자를 보고 어느 손잡이를 돌릴지, 그리고 그 손잡이를 자세히 다룬 글이 어디 있는지를 따라간다.

측정은 [지연 로딩 전략](/posts/lazy-loading-strategies)에서 만든 상품 페이지 두 벌로 했다. 모든 것을 즉시 받는 버전과 시점별로 미룬 버전이다. Playwright로 Chromium 141을 띄우고, 망 제한(왕복 150ms, 내려받기 1.6Mbps)과 CPU 4배 느리게를 따로따로 켜고 꺼 가며 다섯 번씩 잰 가운데 값이다.

## 노트북에서는 아무도 느리다고 하지 않는다

## 고치기 전에 재는 것

성능 작업은 측정으로 시작한다. 숫자 없이 고치면 체감은 바뀌지 않는데 코드만 복잡해지기 쉽다. 측정에는 두 갈래가 있다.

실험실 측정(lab)은 위처럼 정해진 조건에서 같은 페이지를 열어 재는 것이다. 매번 같은 조건이라 고치기 전과 후를 비교하기 좋고, 원인을 추적할 트레이스가 남는다. 대신 실제 사용자의 기기, 망, 캐시 상태, 행동을 모른다. 실사용자 측정(RUM, Real User Monitoring)은 사용자 브라우저에서 `PerformanceObserver`로 지표를 모아 서버로 보내는 것이다. 진짜 숫자지만 흩어져 있고 원인을 바로 알려 주지 않는다.

둘은 역할이 다르다. 실사용자 측정으로 어느 페이지, 어느 기기층이 나쁜지 찾고, 실험실 측정으로 그 조건을 재현해 원인을 찾고 고친 뒤 다시 실사용자 숫자로 확인한다. 실사용자 숫자는 평균이 아니라 75번째 백분위수(p75)로 본다. 평균은 빠른 다수가 느린 소수를 가린다.

자세한 내용은 세 글로 나눠 두었다.

- [Core Web Vitals](/posts/core-web-vitals): LCP, INP, CLS가 무엇을 재고, 각각을 어떤 조각으로 나눠 원인을 찾는지.
- [성능 지표 측정](/posts/performance-metrics-measurement): TTFB, FCP, LCP, Speed Index, TBT, INP, CLS를 브라우저가 어떻게 재고, 직접 모으려면 어떤 API를 쓰는지.
- [Lighthouse 읽기](/posts/lighthouse-explained): Lighthouse 점수가 어떻게 나오고, 점수와 실사용자 숫자가 왜 다른지.

## 덜 보내기

첫 방문에서 가장 큰 효과는 대개 바이트를 줄이는 데서 나온다. 무엇이 큰지는 종류별로 본다.

JS는 받는 것보다 실행이 비싸다. 같은 100KB라도 이미지는 디코딩하면 끝이지만 JS는 파싱, 컴파일, 실행을 거치고 그동안 메인 스레드를 쓴다. 번들러가 무엇을 하는지는 [번들러 기초](/posts/bundler-basics), 번들을 나누고 안 쓰는 코드를 덜어 내는 법은 [번들 쪼개기](/posts/code-splitting), 나눈 조각을 언제 받을지는 [지연 로딩 전략](/posts/lazy-loading-strategies)에 있다.

이미지는 바이트로는 가장 큰 경우가 많고 LCP 요소인 경우도 많다. 포맷, 반응형 크기, 지연 로딩과 우선순위는 [이미지 최적화](/posts/image-optimization)에서 다룬다. 한글 웹폰트는 글자 수 때문에 파일이 유난히 크다. 서브셋과 `font-display`는 [웹폰트 최적화](/posts/web-font-optimization)에, 안 쓰는 CSS와 CSS-in-JS의 런타임 비용은 [CSS 성능](/posts/css-performance)에 있다.

데이터도 바이트다. 목록 화면이 상세 필드까지 받으면 압축해도 열 배 넘게 크다. 필드 고르기와 압축 단계 선택은 [데이터 요청 최적화](/posts/data-fetching-optimization)에서 쟀다.

리소스 힌트(`preload`, `preconnect`, `fetchpriority`)는 [리소스 힌트](/posts/resource-hints-loading)에서, HTML을 어디서 만들지(CSR, SSR, SSG, 스트리밍)는 [렌더링 전략 비교](/posts/rendering-strategies)와 [스트리밍 SSR](/posts/streaming-ssr-suspense)에서, 데이터 요청의 계단은 [데이터 요청 최적화](/posts/data-fetching-optimization)에서, 연결 수와 프로토콜 차이는 [HTTP 버전](/posts/http-versions)에서 다룬다.

일찍 보내기에는 대가가 있다. 모든 것을 앞당기면 결국 모두가 같은 회선을 다툰다. `preload`를 열 개 붙이면 진짜 급한 LCP 이미지가 그 사이에 끼어 늦어진다. 앞당기는 건 늦게 발견되는 핵심 리소스 몇 개뿐이다.

## 덜 그리기

바이트가 다 와도 브라우저는 스타일을 계산하고, 배치하고, 칠하고, 합성해야 화면을 만든다. DOM이 크거나, 스크롤하거나 애니메이션할 때마다 배치를 다시 하게 만들면 이 단계가 프레임 예산 16.7ms를 넘긴다. 단계 하나하나와 각 단계를 깨우는 원인은 [브라우저 렌더링 파이프라인](/posts/browser-rendering-pipeline)에, 그걸 바탕으로 한 최적화(레이아웃 스래싱 피하기, `content-visibility`, 긴 목록 가상화)는 [렌더링 성능 최적화](/posts/rendering-performance-optimization)에 있다.

움직이는 것은 합성 단계에서 끝나게 만든다. `transform`과 `opacity`만 바꾸는 애니메이션은 레이아웃과 페인트를 건너뛴다. 이 부분은 [애니메이션 성능](/posts/animation-performance)에서 트레이스로 쟀다. React 화면에서는 브라우저가 그리기 전에 React가 다시 렌더링하는 양부터 줄인다. 그건 [React는 언제 다시 그리나](/posts/react-rerender)에서 다룬다.

## 덜 실행하기

메인 스레드는 하나다. JS 실행, 스타일과 레이아웃, 입력 처리가 모두 그 위에서 줄을 선다. 50ms를 넘는 긴 작업이 있으면 그동안 눌러도 반응하지 않고, 이게 INP를 나쁘게 만든다. 이벤트 루프가 일을 어떻게 고르는지는 [이벤트 루프](/posts/event-loop)에, 긴 작업을 쪼개서 입력에 양보하는 법은 [Core Web Vitals의 INP 부분](/posts/core-web-vitals)에 있다.

서버에서 HTML을 그려 보내는 페이지는 하이드레이션이 큰 몫을 차지한다. 비용과 불일치는 [하이드레이션](/posts/hydration)에, 필요한 곳만 살리는 방식은 [아일랜드와 재개 가능성](/posts/islands-resumability)에 있다. 지연 로딩 글에서 쟀듯이 하이드레이션을 미루면 JS 실행은 줄지만 큰 DOM의 비용은 남는다. 손잡이 하나로 모든 게 풀리지 않는 예다.

입력마다 무거운 일을 하는 코드는 횟수를 줄인다([디바운스와 스로틀](/posts/debounce-throttle)). 오래 쓰는 화면이 점점 느려진다면 메모리 누수를 의심한다([메모리 누수](/posts/js-memory-leak)).

## 좋아진 숫자가 되돌아가지 않게

성능은 고친 날보다 그다음 몇 달이 어렵다. 기능이 붙을 때마다 라이브러리가 하나씩 들어오고, 누구도 그 하나 때문에 느려졌다고 느끼지 못한다. 그래서 숫자로 한도를 정해 둔다. 이걸 성능 예산(performance budget)이라고 한다. "첫 로드 JS는 압축해서 170KB 이하", "LCP p75는 2.5초 이하" 같은 식이다.

예산은 CI에서 검사해야 효과가 있다. 빌드 결과의 파일 크기를 재서 넘으면 실패시키고, 실험실 측정을 같은 조건으로 돌려 지표가 크게 나빠지면 경고한다. 실사용자 숫자는 배포 버전별로 나눠 봐서 어느 배포부터 나빠졌는지 찾는다.

## 페이지 하나를 점검할 때 보는 목록

새 페이지를 내보내기 전이나 느리다는 이야기를 들었을 때 위에서부터 훑는다. 항목마다 자세한 글을 붙였다.

1. 느린 기기 조건으로 재고, 실사용자 p75와 비교한다. [성능 지표 측정](/posts/performance-metrics-measurement), [Core Web Vitals](/posts/core-web-vitals)
2. 해시 붙은 정적 파일에 긴 캐시를 주고 있나. [프런트엔드 캐시](/posts/frontend-browser-cache), [HTTP 캐시와 CDN](/posts/http-caching-cdn)
3. 첫 로드 JS에 첫 화면이 안 쓰는 코드가 있나. Coverage 탭으로 본다. [번들 쪼개기](/posts/code-splitting), [지연 로딩 전략](/posts/lazy-loading-strategies)
4. LCP 요소가 HTML에 있고, lazy가 없고, 적당한 크기와 포맷인가. [이미지 최적화](/posts/image-optimization), [리소스 힌트](/posts/resource-hints-loading)
5. 폰트가 글자를 오래 숨기거나 화면을 밀지 않나. [웹폰트 최적화](/posts/web-font-optimization)
6. 첫 페인트를 막는 CSS가 크지 않나. [CSS 성능](/posts/css-performance)
7. 데이터 요청이 계단을 이루거나 중복되지 않나. [데이터 요청 최적화](/posts/data-fetching-optimization)
8. 서드파티 스크립트와 임베드가 첫 로드에 끼어 있지 않나. [지연 로딩 전략](/posts/lazy-loading-strategies)
9. 누른 순간 긴 작업이 돌지 않나. 하이드레이션이 얼마나 걸리나. [하이드레이션](/posts/hydration), [이벤트 루프](/posts/event-loop)
10. 스크롤과 애니메이션이 레이아웃을 깨우지 않나. [렌더링 성능 최적화](/posts/rendering-performance-optimization), [애니메이션 성능](/posts/animation-performance)

번호는 대략 효과가 넓은 순서다. 1번에서 어느 지표가 나쁜지 정했다면 그 지표에 묶인 항목부터 본다. 앞의 측정처럼 LCP가 망에 묶여 있으면 2~8번이, 긴 작업이 CPU에 묶여 있으면 3번과 9번이 먼저다.

## 다시 4.2초로

노트북의 260ms와 휴대폰의 4,212ms는 같은 코드에서 나왔다. 조건을 하나씩 켜 보면 LCP는 망에, 긴 작업은 CPU에 묶여 있었고, 첫 로드에서 덜 보내는 손잡이 하나가 두 숫자를 함께 내렸다. 성능 작업은 기법 목록을 하나씩 적용하는 일이 아니라, 사용자 조건에서 재고, 나쁜 지표가 무엇에 묶였는지 보고, 그 지표에 닿는 손잡이부터 돌린 뒤 다시 재는 반복이다.

## 면접에서 나올 만한 질문

### 프런트엔드 성능을 개선하라고 하면 무엇부터 하나요?

재는 것부터 한다. 실사용자 측정으로 어느 페이지와 기기층의 어떤 지표가 나쁜지 찾고, 그 조건을 실험실에서 재현해 원인을 본다. 고친 뒤에는 같은 조건으로 다시 재고, 실사용자 p75로 확인한다. 측정 없이 기법부터 적용하면 체감은 그대로인데 코드만 복잡해지기 쉽다.

### 실험실 측정과 실사용자 측정은 어떻게 다르고, 왜 둘 다 필요한가요?

실험실 측정은 정해진 조건에서 재서 비교와 원인 추적이 쉽지만 실제 사용자의 기기와 망을 모른다. 실사용자 측정은 진짜 분포를 보여 주지만 흩어져 있고 원인을 바로 말해 주지 않는다. 실사용자 숫자로 문제를 찾고 실험실에서 원인을 고친 뒤 다시 실사용자 숫자로 확인하는 식으로 같이 쓴다.

### 실사용자 지표를 평균이 아니라 p75로 보는 이유는?

평균은 빠른 다수가 느린 소수를 가리기 때문이다. 고성능 기기 사용자가 많으면 평균은 좋아 보여도 하위 사용자는 여전히 느리다. p75는 사용자 넷 중 셋이 그보다 빠르다는 뜻이라 느린 쪽을 놓치지 않으면서 극단값에 흔들리지 않는다. Core Web Vitals의 기준도 p75로 판정한다.

### 성능 최적화 기법들을 어떤 순서로 보나요?

다시 보내지 않기, 덜 보내기, 일찍 보내기, 덜 그리기, 덜 실행하기 순서로 본다. 위쪽일수록 효과가 아래로 번진다. 보내지 않은 바이트는 파싱하고 실행할 필요도 없어서, 예제에서 덜 보내기 하나로 LCP와 긴 작업이 함께 줄었다. 다만 INP처럼 상호작용 중의 문제는 메인 스레드 쪽에서만 풀린다.

### 어떤 지표가 망에 묶였는지 CPU에 묶였는지 어떻게 아나요?

망 제한과 CPU 제한을 하나씩 따로 켜서 잰다. 예제에서 망만 느리게 하자 LCP가 260ms에서 3912ms로, CPU만 느리게 하자 긴 작업이 53ms에서 483ms로 뛰었다. 망에 묶인 지표는 바이트와 요청 순서를, CPU에 묶인 지표는 실행량을 줄여야 움직인다.

### 성능 예산은 왜 두고 어떻게 지키나요?

기능이 붙을 때마다 조금씩 느려지는 것을 막으려고 둔다. 하나하나는 티가 안 나서 아무도 눈치채지 못하기 때문이다. 종류별 바이트나 지표 기준을 숫자로 정하고, CI에서 빌드 결과 크기와 실험실 측정을 검사해 넘으면 실패시킨다. 실사용자 숫자는 배포 버전별로 나눠 보면 어느 배포부터 나빠졌는지 찾을 수 있다.
