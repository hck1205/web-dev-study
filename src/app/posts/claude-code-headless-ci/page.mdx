  이 글은 이 도우미를 사람 없이 스크립트와 자동 검사 기계 안에서 돌리는 방법을 다룬다.

PR이 열릴 때마다 Claude Code로 자동 리뷰를 돌려 보고 싶었다. 로컬에서는 잘 되던 명령을 CI에 그대로 옮겼더니 작업이 끝나지 않았다. 대화형 화면이 떠서 "이 명령을 실행해도 될까요?"를 묻고 있었고, CI에는 그 질문에 답할 사람이 없다.

사람 없이 돌리려면 세 가지를 미리 정해야 한다. 어떻게 실행하고 결과를 어떤 모양으로 받을지, 무엇을 허락할지, 언제 멈출지다. 이 글은 `claude -p`를 중심으로 그 셋을 실제 출력으로 확인하고, PR 리뷰 스크립트와 GitHub Actions 작업으로 묶는다. 확인한 버전은 Claude Code 2.1.310(Linux)이고, 출력의 필드 이름은 버전에 따라 늘거나 바뀔 수 있다.

대화형으로 쓰는 옵션과 키, 세션 이어 가기는 [Claude Code 손에 익히기](/posts/claude-code-cli-and-sessions)에서 봤다. 권한 규칙 문법과 설정 파일의 층은 [프로젝트 구조](/posts/claude-code-project-structure)에, 훅은 [확장](/posts/claude-code-extensions)에 있다. 일반적인 워크플로 문법은 [GitHub Actions 워크플로](/posts/github-actions-workflows)를 참고하자.

## -p는 한 번 묻고 끝나는 실행이다

`-p`(`--print`)를 붙이면 Claude Code는 대화형 화면 없이 프롬프트 하나를 처리하고, 결과를 표준 출력에 쓰고, 종료한다. 그 사이에 모델은 평소처럼 도구를 부르며 여러 바퀴를 돈다. 다른 점은 사람에게 물을 수 없다는 것 하나다.

```bash
# 파일을 읽고 버그를 말하게 한다. 결과는 표준 출력으로
claude -p "math.js의 add 함수 버그를 한 문장으로" --model haiku
```

```text
Warning: no stdin data received in 3s, proceeding without it. If piping from a slow command, redirect stdin explicitly: < /dev/null to skip, or wait longer.
`add`가 덧셈이 아니라 뺄셈을 합니다: `math.js` 1행의 `return a - b;`가 `a + b`여야 합니다.
```

첫 줄의 경고가 CI에서 처음 만나는 함정이다. `-p`는 표준 입력이 파이프로 들어올 수 있어서 잠깐 기다린다. 터미널이 아닌 곳(CI, cron, 다른 프로그램의 자식 프로세스)에서는 표준 입력이 열린 채 비어 있는 경우가 많아 3초를 기다린 뒤 경고를 남기고 진행한다. 입력을 넘길 게 없으면 `< /dev/null`을 붙여 기다림과 경고를 없앤다. 반대로 `git diff | claude -p "..."`처럼 넘길 게 있으면 파이프로 준다.

`-p` 실행도 기본으로 세션 파일을 남긴다. CI에서는 남겨 봐야 볼 사람이 없고 러너가 사라지면 같이 사라지니 `--no-session-persistence`를 붙인다. 그리고 도움말에 적혀 있듯 `-p`는 작업 폴더 신뢰 확인 창을 건너뛴다. 이 한 줄이 뒤에서 볼 보안 이야기의 출발점이다.

## 결과를 받는 모양 세 가지

`--output-format`은 `text`(기본), `json`, `stream-json` 중 하나다. 사람이 읽을 거면 `text`, 다른 프로그램이 읽을 거면 나머지 둘이다.

`json`은 실행이 끝난 뒤 JSON 객체 하나를 낸다. 답 본문은 `result`에 있고, 그 옆에 실행 결과를 판단할 필드들이 붙는다. 파일 수정까지 시킨 실행의 결과를 `jq`로 몇 개만 골라 봤다.

```bash
# 파일을 고치게 하고, 결과 JSON에서 판단에 필요한 필드만 본다
claude -p "math.js의 add 버그를 고쳐 줘. 고친 뒤 node로 확인은 하지 마." \
  --output-format json --allowedTools "Read" "Edit" --model haiku \
  --no-session-persistence < /dev/null > r-allow.json
jq '{type, subtype, is_error, num_turns, duration_ms, total_cost_usd, terminal_reason}' r-allow.json
```

```text

  "subtype": "success",

  "num_turns": 6,
  "duration_ms": 11372,
  "total_cost_usd": 0.004798210000000001,
  "terminal_reason": "completed"
}
```

`stream-json`은 한 줄에 이벤트 하나씩, 실행하는 동안 계속 낸다. 긴 작업의 진행 상황을 보여 주거나, 도구 호출을 실시간으로 기록하거나, 다른 프로그램이 중간에 끼어들 때 쓴다. 처음 붙여 보면 이렇게 거절당한다.

```text
Error: When using --print, --output-format=stream-json requires --verbose
```

`--verbose`를 함께 주고 같은 수정 작업을 돌린 뒤, 줄마다 이벤트 종류와 담긴 내용만 뽑아 봤다.

```bash
claude -p "math.js의 add 버그를 고쳐 줘" --output-format stream-json --verbose \
  --allowedTools "Read" "Edit" --model haiku --no-session-persistence < /dev/null > r-stream.jsonl
jq -r '[.type, (.subtype // ""), ((.message.content // []) | map(.type + (if .name then ":" + .name else "" end)) | join(","))] | join(" ")' r-stream.jsonl
```


## 권한은 출발 전에 정한다

대화형에서는 위험한 호출마다 사람이 답한다. `-p`에는 그 사람이 없으니 무엇을 허락할지 미리 정해야 한다. 정하지 않으면 어떻게 될까. 아무 허용 규칙 없이 "고쳐 줘"를 시켜 봤다.

```bash
claude -p "math.js의 add 버그를 고쳐 줘" --output-format json --model haiku \
  --no-session-persistence < /dev/null > r-deny.json
echo "exit=$?"
jq -c '{subtype, is_error, num_turns, denied: [.permission_denials[].tool_name]}' r-deny.json
jq -r .result r-deny.json | head -2
```

```text
exit=0
{"subtype":"success","is_error":false,"num_turns":7,"denied":["Bash","Edit","Bash"]}
`math.js`의 `add` 버그는 `-` 연산자를 쓴 것입니다. 하지만 아직 파일을 수정하지 못했습니다. 편집 권한이 승인되지 않았고, 확인용 `node` 실행도 승인이 필요해서 막혔습니다.
```

이 출력에서 가장 중요한 건 `exit=0`과 `success`다. 파일은 그대로인데 실행은 성공으로 끝났다. 물어볼 사람이 없으니 확인이 필요한 호출(`Edit`, `Bash`)은 거부됐고, 모델은 할 수 있는 만큼 하고 "못 고쳤다"고 말로 보고했다. 종료 코드만 보는 CI라면 초록 불이 켜진다. 그래서 `permission_denials`가 비어 있지 않으면 실패로 다루거나 적어도 경고를 남겨야 한다.

허락은 두 단계로 준다. `--allowedTools`는 묻지 않고 허용할 도구와 규칙이다. 규칙 문법은 설정 파일과 같아서 `Read`, `Edit`처럼 도구 이름만 쓰거나 `Bash(pnpm test:*)`처럼 명령 앞부분으로 좁힌다. 같은 작업에 `Read`와 `Edit`을 허락하자 파일이 고쳐졌고, 결과의 `denied`에는 여전히 `Bash` 두 번이 남았다. 모델이 셸로 파일을 찾아보려다 막힌 것이다. 막혀도 다른 길로 일을 끝냈다.

`--permission-mode`는 규칙 밖의 호출을 어떻게 할지 정한다. 비대화형에서 주로 고르는 건 셋이다.

- `dontAsk`: 허용 규칙에 없는 건 묻지 않고 거부한다. 무엇이 허용되는지 명시적이라 CI의 기본값으로 맞다. 같은 작업에 `--permission-mode dontAsk --allowedTools Read`만 줬더니 `Bash`와 `Edit`이 거부됐다.
- `acceptEdits`: 파일 수정은 허용하고 나머지는 규칙대로 한다. 코드를 고쳐 PR을 올리는 작업이면 이쪽이다.
- `bypassPermissions`: 모든 확인을 건너뛴다. 네트워크가 막히고 비밀 값이 없는 일회용 컨테이너에서만 쓴다. CI 러너는 보통 저장소 쓰기 토큰과 비밀 값을 들고 있으니 여기에 해당하지 않는다.

꼭 막아야 할 것은 `--disallowedTools`로 따로 적는다. 거부 규칙은 허용 규칙보다 먼저 평가된다. 예를 들어 리뷰 작업에 `--disallowedTools "Bash(git push:*)" "Bash(curl:*)"`를 붙여 두면 다른 규칙을 잘못 넓혀도 그 둘은 막힌다. 아예 도구 목록 자체를 줄이려면 `--tools "Read,Grep,Glob"`처럼 쓸 도구만 남긴다. 목록에 없는 도구는 모델이 존재조차 모른다.

## 멈출 자리를 정한다: 바퀴 수와 비용 상한

사람이 지켜보지 않는 실행에는 상한이 필요하다. 모델이 헤매며 같은 시도를 반복하면 시간과 돈이 계속 나간다. 둘을 일부러 아주 작게 걸어 봤다.

```bash
# 바퀴 수 상한 1
claude -p "math.js의 add 버그를 고쳐 줘" --output-format json --allowedTools "Read" "Edit" \
  --max-turns 1 --model haiku --no-session-persistence < /dev/null > r-turns.json; echo "exit=$?"
# 비용 상한 0.0005달러
claude -p "math.js의 add 버그를 고쳐 줘" --output-format json --allowedTools "Read" "Edit" \
  --max-budget-usd 0.0005 --model haiku --no-session-persistence < /dev/null > r-budget.json; echo "exit=$?"
jq -c '{subtype, is_error, num_turns, total_cost_usd, terminal_reason, errors}' r-turns.json r-budget.json
```

```text
exit=1
exit=1
{"subtype":"error_max_turns","is_error":true,"num_turns":2,"total_cost_usd":0.00197335,"terminal_reason":"max_turns","errors":["Reached maximum number of turns (1)"]}
{"subtype":"error_max_budget_usd","is_error":true,"num_turns":1,"total_cost_usd":0.0021062500000000005,"terminal_reason":"budget_exhausted","errors":["Reached maximum budget ($0.0005)"]}
```

이번에는 종료 코드가 1이고 `is_error`가 `true`다. 권한 거부와 달리 상한에 걸리면 실패로 끝난다. `result`는 `null`이라 답 본문도 없다. 파일도 고쳐지지 않았다. `text` 형식이면 `Error: Reached max turns (1)`을 출력하고 역시 1로 끝난다.

비용 숫자를 보자. 상한은 0.0005달러였는데 실제로는 0.0021달러를 썼다. 상한은 모델 호출 도중에 끊는 게 아니라 호출이 끝난 뒤 누적 비용을 확인하고 다음으로 넘어가지 않는 방식으로 동작한 것이다. 그러니 상한은 "이 금액에서 멈춘다"가 아니라 "이 금액을 넘으면 더 진행하지 않는다"로 읽어야 하고, 호출 한 번이 클 수 있는 큰 모델일수록 여유를 두고 잡는다. 바퀴 수 상한은 작업 크기에 맞춘다. 리뷰처럼 읽기만 하는 작업은 10번 안팎, 고치고 테스트까지 돌리는 작업은 30번 이상이 필요하기도 하다. 처음에는 넉넉히 잡고, 결과의 `num_turns` 분포를 보고 줄인다.

CI 쪽에도 상한을 따로 둔다. 작업에 `timeout-minutes`를 걸어 두지 않으면 네트워크 문제로 멈춘 실행이 러너를 몇 시간씩 잡고 있는다.

## 답의 모양을 JSON Schema로 고정한다

리뷰 결과를 PR 댓글로 달려면 모델의 자유로운 문장보다 정해진 모양이 편하다. `--json-schema`에 JSON Schema를 넘기면 결과의 `structured_output`에 그 모양에 맞는 값이 들어온다.

```bash
claude -p "math.js를 리뷰해. 파일은 고치지 마." --output-format json --allowedTools Read \
  --model haiku --no-session-persistence --json-schema '{
  "type": "object",
  "properties": {
    "verdict": { "type": "string", "enum": ["approve", "request_changes"] },
    "issues": { "type": "array", "items": { "type": "object",
      "properties": { "line": { "type": "integer" }, "message": { "type": "string" } },
      "required": ["line", "message"] } }
  },
  "required": ["verdict", "issues"]
}' < /dev/null > r-schema.json
jq -c .structured_output r-schema.json
```

```text
{"verdict":"request_changes","issues":[{"line":1,"message":"add(a, b)가 a - b를 반환함. 덧셈이어야 하므로 return a + b; 로 수정 필요."}]}
```

`verdict`가 열거값 둘 중 하나로 왔다. 이제 `jq -r .structured_output.verdict`로 분기하면 된다. 모양은 고정되지만 내용이 맞다는 보장은 아니다. 줄 번호가 틀리거나 없는 문제를 지어낼 수 있다. 사람이 읽는 댓글로 쓰고, 이 값으로 PR을 자동으로 막거나 합치지는 않는 편이 안전하다. 구조화 출력이 API 수준에서 어떻게 검증되는지는 [LLM API를 서비스에 붙이기](/posts/llm-api-integration)에서 다뤘다.

## 리뷰 스크립트 하나로 묶기

지금까지의 옵션을 스크립트 하나로 묶었다. diff를 표준 입력으로 넘기고, 읽기 도구만 허락하고, 상한을 걸고, 결과를 마크다운으로 바꾼다. CI와 로컬에서 같은 스크립트를 쓰려고 파일로 뺐다.

```bash
#!/usr/bin/env bash
# scripts/review.sh — PR 리뷰를 비대화형으로 돌리고 마크다운 댓글 본문을 만든다
set -euo pipefail
BASE="${BASE:-main}"
SCHEMA='{"type":"object","properties":{"verdict":{"type":"string","enum":["approve","request_changes"]},"issues":{"type":"array","items":{"type":"object","properties":{"file":{"type":"string"},"line":{"type":"integer"},"severity":{"type":"string","enum":["high","medium","low"]},"message":{"type":"string"}},"required":["file","line","severity","message"]}}},"required":["verdict","issues"]}'

set +e
git diff "$BASE"...HEAD | claude -p \
  "표준 입력은 이 PR의 diff다. 버그와 보안 문제만 찾아라. 스타일 지적은 하지 마라. 필요하면 파일을 읽어도 되지만 고치지 마라." \
  --output-format json \
  --json-schema "$SCHEMA" \
  --permission-mode dontAsk \
  --allowedTools "Read" "Grep" "Glob" \
  --max-turns 8 \
  --max-budget-usd 0.50 \
  --no-session-persistence > review.json
code=$?
set -e

echo "exit=$code subtype=$(jq -r .subtype review.json) turns=$(jq -r .num_turns review.json) cost=$(jq -r '.total_cost_usd*10000|round/10000' review.json)"
if [ "$code" -ne 0 ]; then
  echo "리뷰 실패: $(jq -r '.errors // [] | join("; ")' review.json)" >&2
  exit "$code"
fi
jq -r '.structured_output | "**판정: \(.verdict)**\n" + (.issues | map("- `\(.file):\(.line)` [\(.severity)] \(.message)") | join("\n"))' review.json
```

실험용 저장소에 쿠폰 함수를 고친 브랜치를 만들었다. 퍼센트 입력도 받겠다며 `rate > 1`이면 100으로 나누는 줄을 넣었는데, 실수로 계산식에 `* 100`을 붙였다.

```diff
 export function applyCoupon(price, rate) {
   // rate는 0~1
-  return Math.round(price * (1 - rate));
+  if (rate > 1) rate = rate / 100;
+  return Math.round(price * (1 - rate * 100));
 }
```

이 브랜치에서 스크립트를 돌린 실제 출력이다. 모델은 따로 지정하지 않아 기본 모델로 돌았다.

```text
exit=0 subtype=success turns=2 cost=0.1678
**판정: request_changes**
- `coupon.js:4` [high] `rate * 100`이 잘못 들어갔다. 계산식이 `price * (1 - rate*100)`이 되어 정상 입력(0~1)에서도 결과가 틀린다. 예: price=10000, rate=0.2이면 1-20=-19라서 -190000이 나온다. 모든 할인 금액이 음수가 된다. 결제 금액이 음수가 되면 환불이나 포인트 적립 같은 금전 피해로 이어질 수 있다. `price * (1 - rate)`로 되돌려야 한다.
- `coupon.js:3` [medium] `rate > 1`이면 퍼센트로 보고 100으로 나누는 휴리스틱에 모호함이 있다. rate=1은 100% 할인(기존 계약)으로 처리되지만 퍼센트 입력 1(1%)과 구분할 수 없다. 1%를 뜻하는 호출은 조용히 100% 할인이 되어 가격이 0원이 된다. 입력 단위를 하나로 고정해야 한다.
- `coupon.js:3` [medium] rate 범위 검증과 clamp가 없다. rate가 100을 넘으면(예: 150 → 1.5) 1-rate가 음수여서 가격이 음수가 된다. 음수 rate는 가격을 올리고, NaN이나 문자열이면 NaN을 반환한다. 사용자나 클라이언트가 rate를 조작할 수 있으면 쿠폰 악용 경로가 된다. 서버에서 0<=rate<=1(finite)을 검증하고 결과는 Math.max(0, ...)로 제한해야 한다.
```

심어 둔 버그(`rate * 100`)를 첫 줄에 high로 잡았고, 계산 예시(10000원에 0.2면 -190,000원)도 맞다. 둘째 지적인 "1이 100%인지 1%인지 모호하다"는 내가 의도하지 않았지만 맞는 지적이다. 바퀴는 2번, 비용은 약 0.17달러였다. diff를 입력으로 줬으니 파일을 따로 찾을 필요가 적었다. PR이 하루 50개면 하루 8달러 남짓이다. 리뷰처럼 정해진 일은 `--model`로 작은 모델을 골라 비용을 더 줄일 수 있다. 모델별 비용 차이는 [Claude Code 모델과 비용](/posts/claude-code-models-and-cost)에 있다. 큰 PR일수록 diff와 읽는 파일이 늘어 비용이 커지니, 작업 로그에 `cost`를 남겨 두고 가끔 분포를 본다.

## GitHub Actions에서 돌리기

이제 CI에 올린다. 저장소 설정의 Actions secrets에 `ANTHROPIC_API_KEY`를 넣고, 아래 워크플로를 둔다. 이 작업은 이 글에서 실제 GitHub에 돌려 보지는 못했다. 위의 스크립트를 그대로 부르는 구조라 스크립트 부분은 로컬 실행과 같다.

```yaml
# .github/workflows/claude-review.yml
name: claude-review
on:
  pull_request:
    types: [opened, synchronize]

permissions:
  contents: read
  pull-requests: write

concurrency:
  group: claude-review-${{ github.event.pull_request.number }}
  cancel-in-progress: true   # 새 커밋이 오면 이전 리뷰를 취소한다

jobs:
  review:
    runs-on: ubuntu-24.04
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0       # base와의 diff를 만들려면 이력이 필요하다
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm install -g @anthropic-ai/claude-code
      - name: review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          BASE: origin/${{ github.base_ref }}
        run: ./scripts/review.sh > review.md
      - name: comment
        env:
          GH_TOKEN: ${{ github.token }}
          PR: ${{ github.event.pull_request.number }}
        run: gh pr comment "$PR" --body-file review.md
```

몇 가지를 덧붙인다. 커밋을 올릴 때마다 댓글이 새로 쌓이면 PR이 지저분해진다. `gh pr comment`의 `--edit-last`로 마지막 댓글을 고쳐 쓰거나, 댓글에 표식을 넣어 찾아 바꾸는 식으로 하나만 유지한다. `permissions`는 필요한 것만 준다. 리뷰 작업은 코드를 푸시할 일이 없으니 `contents: read`면 된다.

직접 스크립트를 짜는 대신 Anthropic의 공식 액션 `anthropics/claude-code-action`을 쓸 수도 있다. v1 기준으로 `anthropic_api_key`, `prompt`, 그리고 위에서 본 CLI 옵션을 문자열로 넘기는 `claude_args` 같은 입력을 받는다. PR 댓글에서 멘션해 작업을 시키는 흐름, 진행 상황 댓글 같은 것이 이미 들어 있어 편하다. 대신 안에서 무엇을 하는지 한 겹 가려지니, 권한과 상한 옵션은 `claude_args`로 명시적으로 넘겨 위의 규칙표를 그대로 유지한다. 입력 이름은 버전마다 바뀌므로 액션 저장소의 README를 기준으로 한다.

## 남의 PR 브랜치에서 돌릴 때

여기가 이 글에서 가장 조심할 부분이다. 앞에서 `-p`가 작업 폴더 신뢰 확인을 건너뛴다고 했다. 대화형에서는 처음 여는 저장소에 "이 폴더를 믿나요?"를 묻고, 믿기 전에는 그 저장소의 훅이나 `.mcp.json`의 서버를 실행하지 않는다. `-p`에는 물을 사람이 없으니 그 확인이 없다. 즉 체크아웃한 저장소의 `.claude/settings.json`에 적힌 훅과 `.mcp.json`의 MCP 서버가 그대로 적용된다.

내 저장소의 내 브랜치라면 괜찮다. 문제는 외부 기여자의 PR이다. 공격자가 PR에 `.claude/settings.json`을 추가하고 `PreToolUse` 훅에 `curl`로 환경 변수를 보내는 명령을 넣었다고 하자. 그 브랜치를 체크아웃하고 `claude -p`를 돌리는 순간 훅이 러너에서 실행되고, 그 러너가 들고 있는 `ANTHROPIC_API_KEY`나 저장소 토큰이 나간다. 모델이 프롬프트 주입에 넘어가는지와 상관없이 일어나는 일이다. 훅은 모델이 아니라 클라이언트가 실행하기 때문이다. 신뢰 확인이 원래 무엇을 막는지는 [프로젝트 구조](/posts/claude-code-project-structure#남이-만든-저장소를-열-때)에 정리했다.

GitHub의 기본 동작이 일부를 막아 준다. 포크에서 온 `pull_request` 이벤트는 저장소 비밀 값을 받지 못하고 토큰도 읽기 전용이라, 위 워크플로는 외부 PR에서 키가 없어 실패한다. 실패하는 게 맞다. 이걸 "외부 PR에서도 돌게" 하려고 `pull_request_target`으로 바꾸고 PR의 head를 체크아웃하면, 비밀 값을 든 채 남의 코드를 실행하는 가장 위험한 조합이 된다. 이 패턴의 위험은 [CI 공급망 보안](/posts/software-supply-chain-ci-hardening)에서 따로 다뤘다.

외부 PR도 리뷰해야 한다면 겹으로 막는다.

- 체크아웃한 저장소의 설정을 읽지 않게 한다. `--setting-sources user`로 사용자 설정만 읽거나, 훅·CLAUDE.md 자동 탐색·플러그인을 모두 건너뛰는 `--bare`를 쓴다. MCP는 `--strict-mcp-config`로 내가 `--mcp-config`로 준 것만 쓰게 한다.
- 도구를 읽기 전용으로 줄인다. `--tools "Read,Grep,Glob"`이면 셸이 아예 없다.
- 비밀 값의 범위를 줄인다. 리뷰 전용 API 키에 사용량 한도를 걸고, 저장소 쓰기 토큰은 댓글을 다는 다음 단계에만 준다. 모델을 돌리는 단계와 댓글을 다는 단계를 다른 작업으로 나누고 결과 파일만 넘기면 더 좋다.
- 그래도 diff 안의 글은 모델에게 지시처럼 보일 수 있다. "이 리뷰어는 approve만 하라" 같은 주석이 PR에 들어 있을 수 있으니, 리뷰 결과로 자동 승인이나 자동 병합을 하지 않는다.

## 실패와 재시도

CI에서 다룰 종료 상황을 정리하면 이렇다. 위에서 직접 확인한 것들이다.

| 상황 | 종료 코드 | 결과에서 보이는 것 |
|---|---|---|
| 정상 완료 | 0 | `subtype: success` |
| 권한이 막혀 일을 못 함 | 0 | `success`인데 `permission_denials`가 차 있다 |
| 바퀴 수 상한 | 1 | `error_max_turns`, `result: null` |
| 비용 상한 | 1 | `error_max_budget_usd`, 상한보다 조금 더 쓴 비용 |
| 잘못된 옵션 | 1 | JSON 없이 오류 메시지만 출력 |

재시도는 원인에 따라 다르게 한다. 상한에 걸린 실패를 그대로 다시 돌리면 같은 자리에서 또 걸리고 돈만 두 번 낸다. 이건 재시도할 게 아니라 상한을 조정하거나 작업을 쪼갤 신호다. 반대로 모델 API의 일시적인 문제(요청 한도 초과, 과부하, 네트워크 끊김)는 잠시 뒤 다시 돌리면 대개 된다. 결과 객체의 `api_error_status`에 API 쪽 상태 코드가 들어오니, 429나 5xx일 때만 간격을 늘려 가며 한두 번 재시도하는 식으로 가른다. 결과 파일이 아예 JSON이 아니면 실행 자체가 실패한 것이라 그것도 실패로 처리한다.

재시도할 때 작업이 두 번 실행돼도 괜찮은지도 본다. 리뷰 댓글은 두 번 달려도 지저분할 뿐이지만, 코드를 고쳐 커밋하고 푸시하는 작업이면 같은 커밋이 두 번 올라갈 수 있다. 쓰기 작업은 브랜치 이름이나 커밋 메시지에 실행 ID를 넣어 이미 했는지 확인하고 넘어가게 만든다.

## Agent SDK와는 같은 엔진이다

`claude -p`의 옵션들은 Claude Agent SDK의 옵션과 거의 일대일로 맞는다. `--allowedTools`는 `allowedTools`, `--max-turns`는 `maxTurns`, `--max-budget-usd`는 `maxBudgetUsd`, `--permission-mode`는 `permissionMode`, `--no-session-persistence`는 `persistSession: false`다. `stream-json`으로 나오는 이벤트도 SDK가 비동기 반복자로 내주는 메시지와 같은 모양이다. SDK는 같은 엔진을 라이브러리로 쓰는 방법이기 때문이다.

그래서 고르는 기준은 단순하다. 셸 스크립트와 CI 단계 한두 개로 끝나면 `claude -p`와 `jq`가 가장 가볍다. 결과에 따라 분기가 많거나, 도구 호출마다 내 코드로 허락 여부를 판단해야 하거나(`canUseTool` 콜백), 다른 서비스 안에 넣어야 하면 SDK로 옮긴다. SDK로 같은 수정 작업을 돌린 예는 [에이전트 프레임워크 비교](/posts/agent-frameworks-comparison)에 있다.

## 면접에서 나올 만한 질문

### Claude Code를 CI에서 돌리려면 무엇을 바꿔야 하나요?

`-p`로 비대화형 실행을 하고, 물을 사람이 없으니 권한과 상한을 미리 정한다. `--permission-mode dontAsk`와 `--allowedTools`로 허용 범위를, `--max-turns`와 `--max-budget-usd`로 멈출 자리를 정한다. 결과는 `--output-format json`으로 받아 종료 코드와 함께 판단하고, 표준 입력이 없으면 `< /dev/null`을 붙이고 세션 저장은 끈다.

### 종료 코드가 0이면 작업이 성공한 건가요?

아니다. 권한이 막혀 파일을 하나도 못 고쳐도 `subtype: success`, 종료 코드 0으로 끝난다. 모델은 못 했다고 말로만 보고한다. 결과의 `permission_denials`를 함께 보고, 고쳐야 하는 작업이면 실제 diff가 생겼는지도 확인한다. 상한에 걸렸을 때는 1로 끝난다.

### json과 stream-json은 언제 무엇을 쓰나요?

끝난 뒤 결과 하나만 필요하면 json이다. 답 본문, 성공 여부, 바퀴 수, 비용, 거부된 호출이 한 객체에 있다. 긴 작업의 진행을 보여 주거나 도구 호출을 실시간으로 기록해야 하면 stream-json이고, `-p`에서는 `--verbose`가 필요하다. 이벤트 종류가 버전마다 늘어나니 모르는 type은 무시하게 파싱한다.

### --max-budget-usd를 걸면 그 금액을 넘지 않나요?

넘을 수 있다. 실험에서 0.0005달러 상한에 0.0021달러를 썼다. 호출 도중에 끊는 게 아니라 호출이 끝난 뒤 누적 비용을 보고 더 진행하지 않는 방식이라, 마지막 호출만큼 넘친다. 상한은 여유를 두고 잡고, 정확한 비용 통제는 API 키의 사용량 한도로 한 겹 더 건다.

### 외부 기여자의 PR에 자동 리뷰를 돌릴 때 위험은 무엇인가요?

`-p`는 작업 폴더 신뢰 확인을 건너뛰어서, PR이 넣은 `.claude/settings.json`의 훅이나 `.mcp.json`의 서버가 러너에서 실행될 수 있다. 러너가 비밀 값을 들고 있으면 그대로 빠져나간다. `pull_request_target`으로 PR head를 체크아웃해 돌리는 구성은 피하고, `--bare`나 `--setting-sources user`, `--strict-mcp-config`로 저장소 설정을 무시하고, 도구를 읽기 전용으로 줄이고, 키 범위와 한도를 좁힌다.

### 실패했을 때 재시도는 어떻게 하나요?

원인으로 가른다. 바퀴 수나 비용 상한에 걸린 실패는 다시 돌려도 같은 자리에서 걸리니 재시도하지 않고 상한이나 작업 크기를 조정한다. 모델 API의 429나 5xx 같은 일시적인 오류는 간격을 늘려 한두 번 재시도한다. 쓰기 작업은 실행 ID로 이미 했는지 확인하게 만들어 두 번 실행돼도 안전하게 한다.

### claude -p와 Claude Agent SDK는 어떤 관계인가요?

같은 엔진을 쓰는 두 방법이다. 옵션이 거의 일대일로 대응하고, stream-json 이벤트와 SDK가 내주는 메시지 모양도 같다. 셸 스크립트와 CI 몇 단계면 `-p`가 가볍고, 결과에 따른 분기가 많거나 도구 호출마다 코드로 허락을 판단하거나 서비스 안에 넣어야 하면 SDK가 맞다.
