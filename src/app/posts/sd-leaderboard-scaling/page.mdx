<EasyIntro>
  게임 사용자가 열 배로 늘면 점수순 목록 하나가 서버 한 대에 담기 버거워진다. 서버를 여러 대로 묶는 기능을 써도 목록 하나는 통째로 한 서버에 남기 때문에, 목록을 여러 조각으로 쪼개는 일은 직접 해야 한다.

  쪼개는 방법은 둘이다. 반 아이들을 키 순서대로 몇 줄로 세우듯 점수대별로 조각을 나누면, 1등은 맨 위 조각만 보면 되고 내 순위도 빨리 구한다. 대신 점수가 오르면 다른 조각으로 옮겨야 하고, 매달 초에는 모두 0점이라 한 조각에 몰린다. 사용자 번호로 나누면 사람이 고르게 퍼지지만, 1등을 찾을 때마다 모든 조각에 물어보고 결과를 합쳐야 한다.

  같은 점수면 먼저 도달한 사람을 위에 두고 싶을 때는 점수 숫자 하나에 이긴 횟수와 시각을 함께 넣는다. 이때 숫자가 너무 커지면 컴퓨터가 끝자리를 반올림해 버려서, 아무 경고 없이 순서가 틀어진다.
</EasyIntro>

이 시리즈에서 이 글의 자리: 앞 글 [게임 리더보드 설계 ①: Redis 정렬된 셋으로 상위 10명과 내 순위 구하기](/posts/sd-leaderboard-sorted-set)에서 순위표 하나를 Redis 한 대에 올렸다. 이 글은 같은 장의 두 번째 글로, 그 한 대가 버거워졌을 때 순위표를 여러 대로 나누는 두 방법, 동점을 깨는 점수 설계, 다 잃었을 때 다시 만드는 일을 다룬다. 다음 글은 새 장인 [결제 시스템 설계 ①](/posts/sd-payment-flow)이다.

게임이 해외에 출시되면서 사용자가 열 배가 됐다. 하루 활성 사용자 3,000만 명, 한 달 1억 5천만 명이다. 앞 글 끝의 계산대로라면 이번 달 순위표 하나가 15GiB를 넘고, 저녁 피크에는 초당 1만 4천 번 가까이 점수가 오른다. 그런데 운영 쪽에서 먼저 연락이 온다. 새벽에 스냅숏을 뜨는 순간 Redis 메모리가 30GiB 가까이 치솟아 알림이 울렸고, 복제본 하나가 재시작한 뒤 따라잡는 데 한참 걸렸다고 한다.

이 글의 실험은 로컬에 Redis 7.0을 다섯 대 띄워서 했다. 한 대는 정답을 확인하는 기준용, 네 대는 샤드다. 데이터는 앞 글과 같은 분포로 만든 100만 명이고, 앞 글의 측정 중에 더해진 점수 없이 새로 넣었다. 그래서 같은 사용자의 순위가 앞 글과 조금 다르다.

## 키 하나는 나눠지지 않는다

먼저 짚을 것이 있다. Redis Cluster를 쓰면 데이터가 자동으로 여러 노드에 나뉜다고 생각하기 쉽다. Cluster가 나누는 단위는 키다. 키 이름을 해시해서 16,384개 슬롯 중 하나에 넣고, 슬롯을 노드에 나눠 준다. 자세한 동작은 [Redis Cluster](/posts/redis-cluster)에 있다.

순위표는 `lb:2026-10`이라는 키 하나다. 키 하나는 슬롯 하나, 슬롯 하나는 노드 하나에 산다. 노드를 열 대로 늘려도 이 정렬된 셋은 한 노드에 통째로 있고, 쓰기 1만 4천 번도 그 노드 하나가 다 받는다. 결국 순위표를 여러 키로 쪼개는 일은 애플리케이션이 직접 해야 한다. 쪼개는 기준은 두 가지다. 점수 구간으로 나누거나, 사용자 ID로 나눈다.

## 점수 구간으로 나누기

첫 번째는 점수대별로 샤드를 두는 것이다. 0~10점은 1번 샤드, 11~26점은 2번 샤드, 이런 식이다. 경계를 어떻게 정하느냐가 먼저다. 점수 폭을 똑같이 100점씩 나누면 이렇게 된다.

```text
equal-width ranges [0,100) [100,200) [200,300) [300,inf): 917900 / 75274 / 6274 / 552
```

100만 명 중 91만 명이 첫 샤드에 몰렸다. 판 수 점수는 대부분이 낮고 소수만 높아서 폭을 같게 자르면 이렇게 기운다. 그래서 경계는 점수가 아니라 사람 수를 기준으로 고른다. 전체를 점수순으로 세워 25%, 50%, 75% 지점의 점수를 경계로 삼았다.

```text
quantile ranges [0,11) [11,27) [27,55) [55,inf): 241350 / 250482 / 256146 / 252022
```

네 샤드에 25만 명씩 고르게 나뉘었다. 같은 점수인 사람은 같은 샤드에 가야 하니 정확히 25%씩은 아니다. 이 배치에서 두 가지 질문에 답하는 법을 보자.

실제로 돌려서 기준 서버 한 대의 결과와 비교했다.

```text

```

상위 10명은 샤드 하나만 보고도 한 대일 때와 같았고, 순위도 정확히 맞았다. 앞 글의 공동 순위가 필요하면 내 샤드 안에서 `ZCOUNT`를 쓰고 위 샤드의 `ZCARD`를 더하면 된다. 질문 하나에 많아야 샤드 수만큼, 그것도 동시에 보낼 수 있는 가벼운 명령이다.

## 점수가 경계를 넘을 때

점수 구간 샤드의 대가는 사용자가 움직인다는 것이다. 54점인 사용자가 한 판 이기면 55점이 되어 샤드 3으로 옮겨야 한다. 두 샤드는 다른 서버라 한 트랜잭션으로 묶을 수 없다. 순서를 정해야 한다.

```text
user:0999924 score=54 lives in shard 2 [27,55)
total members: 1000000
ZINCRBY -> 55, belongs to shard 3 now
after ZADD to shard 3: total members 1000001 (counted twice for a moment)
after ZREM from shard 2: total members 1000000
rank = ZREVRANK in shard 3: 245781
```

먼저 넣고 나중에 빼면 잠깐 두 번 세어질 뿐 사라지지는 않는다. 그 사이에 서버가 죽으면 두 샤드에 남는데, 사용자별 현재 점수를 원본으로 두고 "점수에 맞지 않는 샤드에 있는 멤버"를 주기적으로 지우는 청소로 메운다. 이 청소가 없으면 한 사람이 순위표에 두 번 나오는 문의를 받게 된다.

더 큰 문제는 경계가 시간에 따라 낡는다는 것이다. 월간 토너먼트는 매달 1일에 모두 0점에서 시작한다. 1일 아침에는 전원이 샤드 0에 있고, 한 달 동안 사람들이 위쪽 샤드로 서서히 올라간다. 위의 25% 경계는 이 달 말의 분포에서 뽑은 숫자라 월초에는 전혀 맞지 않는다. 그래서 실제로는 지난달 같은 날짜의 분포로 경계를 정하거나, 하루 한 번 분포를 다시 재서 경계를 옮기고 사용자들을 백그라운드로 옮긴다. 경계를 옮기는 동안의 순위 계산까지 생각하면 운영이 꽤 복잡하다.

## 사용자 ID로 나누기

두 번째는 사용자 ID를 해시해서 샤드를 고르는 것이다. 점수와 상관없이 사람이 고르게 퍼지고, 점수가 올라도 샤드를 옮기지 않는다.

```text
hash shards: 249957 / 249300 / 250040 / 250703
```

대신 상위 10명이 어느 샤드에 있는지 모른다. 모든 샤드에 "너희 상위 10명"을 물어 모은 뒤 합쳐서 다시 10명을 고른다. 여러 곳에 흩뿌려 묻고 답을 모으는 이 방식을 스캐터-개더(scatter-gather)라고 부른다.

실제 결과도 기준 서버와 같았고, 공동 순위도 정확했다.

```text
top10 hash   : same
hash shards ZCOUNT (41 +inf: [87283, 86902, 87300, 87920] sum=349405 (single node: 349405)
```

해시 샤드에서는 순위를 구하기 어렵다는 말을 자주 듣는데, 공동 순위라면 이렇게 `ZCOUNT`를 샤드 수만큼 더하면 된다. 샤드마다 O(log N)이니 비용은 왕복 수에서 나온다. 어려워지는 건 동점까지 하나하나 다른 순위를 매기거나, 아래에서 볼 깊은 페이지를 줄 때다.

## 나눈 대가를 재 본다

같은 로컬 환경에서 상위 10명 조회를 3,000번씩 돌려 평균 왕복 시간을 쟀다.

```text
top10 single node                           66 µs
top10 range shards (top shard only)        113 µs
top10 hash shards, one by one              294 µs
top10 hash shards, in parallel             191 µs
```

점수 구간 샤드는 한 곳만 물으니 한 대일 때와 같은 급이다. 113µs로 더 나왔지만, 두 가지만 다시 번갈아 재 보니 한 대가 89~91µs, 점수 구간 샤드가 69~83µs로 순서가 뒤집혔다. 이 정도 차이는 같은 컴퓨터에서 재는 잡음이다. 해시 샤드는 네 곳을 하나씩 물으면 네 배 가까이, 동시에 물어도 세 배쯤 걸렸다. 같은 컴퓨터 안이라 µs 단위지만, 샤드가 다른 서버에 있으면 왕복마다 수백 µs가 붙고, 샤드 중 하나만 느려도 전체가 그만큼 기다린다. 샤드가 많을수록 그중 하나가 느릴 확률도 커진다.

차이가 크게 벌어지는 건 깊은 페이지다. "10만 등부터 10명"을 보여 달라고 하면, 한 대나 점수 구간 샤드는 그 위치부터 10명만 꺼낸다. 해시 샤드는 10만 등이 어느 샤드의 몇 번째인지 모르니 샤드마다 앞에서 100,010명을 받아 합쳐야 한다. 서버 안에서 걸린 시간을 `INFO commandstats`로 봤다.

```text
server time ZREVRANGE single  : 22 µs
server time ZREVRANGE per hash shard: 37758 µs, 30435 µs, 35522 µs, 34339 µs
```

22µs와 샤드마다 30~38ms다. 1,500배가 넘고, 그동안 각 샤드는 앞 글에서 본 것처럼 다른 요청을 받지 못한다. 거기에 40만 명분의 응답이 네트워크를 탄다. 해시 샤드를 고른다면 깊은 페이지 기능은 빼거나, 주변 순위처럼 "내 점수 근처"만 각 샤드에 `ZREVRANGEBYSCORE`로 물어 합치는 식으로 바꿔야 한다.

두 방식을 나란히 놓으면 이렇다.

| | 점수 구간 샤드 | 사용자 ID 해시 샤드 |
|---|---|---|
| 상위 10명 | 맨 위 샤드 하나 | 모든 샤드에 묻고 병합 |
| 내 순위 | 내 샤드 순위 + 위 샤드 인원 | 모든 샤드의 `ZCOUNT` 합 |
| 점수가 오를 때 | 경계를 넘으면 샤드 이동 | 이동 없음 |
| 깊은 페이지 | 위치로 바로 감 | 샤드마다 앞부분을 다 받음 |
| 운영 부담 | 경계 관리, 월초 쏠림 | 샤드가 늘수록 읽기 비용 증가 |

읽기가 많고 순위와 페이지가 중요한 리더보드라면 점수 구간 샤드가 유리하다. 경계 관리가 부담스럽고 화면이 상위 10명 정도라면 해시 샤드가 단순하다. 다만 둘 다 1억 명 규모에서 고민할 일이고, 앞 글의 계산처럼 수백만 명까지는 한 대와 복제본으로 충분하다. 나누는 일 자체의 일반론은 [샤딩 입문](/posts/sd-sharding-intro)에서 다뤘다.

## 먼저 도달한 사람이 위에 서게

앞 글에서 동점은 이름순으로 갈린다고 했다. "같은 점수면 그 점수에 먼저 도달한 사람이 위"라는 규칙을 원하면, 점수 하나에 승수와 시각을 함께 담는다. Redis 점수는 배정밀도 실수라 2의 53제곱(약 9×10^15)까지만 정수를 정확히 담는다. 그 안에 두 값을 나눠 넣는다.

이 점수는 `ZINCRBY`로 올릴 수 없다. 이길 때마다 승수는 하나 늘고 시각 부분은 지금으로 바뀌어야 하니, 현재 점수를 읽어 승수를 꺼내고 새 점수를 계산해 다시 넣어야 한다. 읽고 쓰는 사이에 다른 요청이 끼지 않도록 Lua 스크립트로 묶는다.

```lua
-- win.lua: KEYS[1] 순위표, ARGV[1] 사용자, ARGV[2] 올릴 승수, ARGV[3] 이번 달 시작부터 지난 초
local cur = redis.call('ZSCORE', KEYS[1], ARGV[1])
local wins = 0
if cur then wins = math.floor(tonumber(cur) / 4194304) end
wins = wins + tonumber(ARGV[2])
local score = wins * 4194304 + (4194303 - tonumber(ARGV[3]))
redis.call('ZADD', KEYS[1], score, ARGV[1])
return {wins, score}
```

amy는 1시간째, bob은 2시간째에 30승이 됐다. cat은 시작 직후 29승을 했다가 10,000초째에 30승이 됐다.

```text

1) (integer) 30
2) (integer) 130019823
127.0.0.1:17121> EVALSHA <sha> 1 lb:tie bob 30 7200
1) (integer) 30
2) (integer) 130016223
127.0.0.1:17121> EVALSHA <sha> 1 lb:tie cat 29 100
1) (integer) 29
2) (integer) 125829019
127.0.0.1:17121> EVALSHA <sha> 1 lb:tie cat 1 10000
1) (integer) 30
2) (integer) 130013423
127.0.0.1:17121> ZREVRANGE lb:tie 0 -1 WITHSCORES

2) "130019823"
3) "bob"
4) "130016223"
5) "cat"
6) "130013423"
```

셋 다 30승이지만 30승에 먼저 도달한 순서대로 섰다. 화면에 보일 승수는 점수를 4,194,304로 나눈 몫이다. 130,019,823 ÷ 4,194,304의 몫은 30이고, 나머지로 3,600초를 되살릴 수 있다.

여기서 욕심을 내 시각을 밀리초 단위 유닉스 시간으로 넣으면 깨진다. 2026년의 밀리초 시각은 41비트가 필요해서 승수에 남는 자리가 12비트(4,096)뿐이고, 승수가 5,000이면 점수가 2의 53제곱을 넘는다. 1ms 먼저 도달한 amy와 나중인 bob을 넣어 봤다.

```text
127.0.0.1:17121> ZADD lb:bad 10995522641415552 amy 10995522641415551 bob
(integer) 2
127.0.0.1:17121> ZREVRANGE lb:bad 0 -1 WITHSCORES
1) "bob"
2) "10995522641415552"
3) "amy"
4) "10995522641415550"
```

bob의 점수가 반올림되어 amy와 같아졌고, 동점이니 이름순으로 bob이 위에 섰다. 오류도 경고도 없다. 그래서 시각의 단위와 범위를 먼저 정하고, 승수의 최댓값까지 곱해 2의 53제곱 안인지 계산해 둔다. 같은 함정이 [뉴스 피드 설계 ②](/posts/sd-news-feed-retrieval)에서 64비트 ID를 점수에 넣을 때도 나왔다.

이 Lua 스크립트를 Redis Cluster에서 쓸 때는 앞 글의 판 ID 기록 키처럼 함께 다루는 키들이 같은 슬롯에 있어야 한다. 키 이름에 `{2026-10}`처럼 중괄호 해시 태그를 넣으면 중괄호 안만 해시해서 같은 슬롯에 모인다.

## Redis 없이 NoSQL로 만든다면

리더보드를 꼭 Redis로 만들 필요는 없다. 쓰기가 많고 한 파티션 안에서 정렬 키로 정렬해 주는 NoSQL(DynamoDB, Cassandra 같은)로도 만든다. DynamoDB식으로 테이블을 그리면 파티션 키와 정렬 키를 이렇게 둔다.

파티션 키를 달 하나(`2026-10`)로만 두면 이번 달 쓰기가 전부 한 파티션에 몰린다. 그래서 `2026-10#p3`처럼 뒤에 `user_id % N`을 붙여 쓰기를 N개로 흩는다(쓰기 샤딩). 그러면 상위 10명은 위에서 본 해시 샤드와 똑같이 N개 파티션에 묻고 합쳐야 한다. N을 키우면 쓰기는 편해지고 읽기는 무거워진다. 적당한 N은 부하 테스트로 정한다.

이 구조의 약점은 정확한 순위다. 파티션 안에서 내 앞에 몇 개가 있는지 세 주는 기능이 Redis처럼 O(log N)이 아니다. 그래서 정확한 순위 대신 "상위 몇 %"를 보여 주는 타협을 한다. 주기적으로 점수 분포를 훑어 구간 경계를 계산해 두고, 내 점수가 어느 구간인지만 본다. 100만 명 데이터로 경계를 계산하면 이렇다.

```text
top 1%: 184
top 5%: 119
top 10%: 92
top 25%: 55
top 50%: 27
```

41점이면 "상위 50% 안", 92점이면 "상위 10%"다. 1억 명이 각자 정확한 등수를 알아야 하는 게임은 드물고, 상위권에게만 정확한 순위를 보여 주는 경우가 많다. 이 경계표는 [점수 구간 샤드](#점수-구간으로-나누기)의 경계를 고를 때도 그대로 쓸 수 있다.

## 다 잃었을 때 다시 만들기

복제본까지 잃었거나, 버그로 점수가 틀어졌다면 원본에서 다시 만든다. 앞 글에서 원본은 DB의 판 기록이라고 했다. 실험에서는 PostgreSQL의 100만 명 점수를 `COPY`로 흘려 읽고 1,000명씩 `ZADD`로 넣었다.

```js
// rebuild.mjs 일부: 새 키에 채운 뒤 이름을 바꿔 한 번에 교체한다
const p = spawn("su", ["postgres", "-c", "psql -X -d c12_lb -c \"COPY (SELECT user_id, score FROM leaderboard WHERE month = '2026-10-01') TO STDOUT\""]);
for await (const line of rl) { /* 1,000명씩 ZADD lb:2026-10:rebuild */ }
await r.cmd("RENAME", "lb:2026-10:rebuild", "lb:2026-10:restored");
```

```text
rebuilt 1000000 members from PostgreSQL in 3.1 s
```

100만 명에 3.1초다. 연결 하나로 이 속도라면 1억 5천만 명은 단순 계산으로 8분쯤이고, 샤드별로 동시에 채우면 줄어든다. 판 기록에서 사용자별 합계를 구하는 집계 쿼리가 추가로 들고, 그 쿼리는 운영 DB가 아니라 복제본에서 돌린다.

다시 만드는 동안 지금 키를 직접 고치지 않는다. 새 키에 다 채운 뒤 `RENAME`으로 바꾸면 사용자는 옛 순위표나 새 순위표 중 하나만 본다. 반쯤 채운 순위표가 보이는 일이 없다. 다시 만드는 사이에 들어온 판 결과는 판 기록에 쌓여 있으니, 교체한 뒤 그 시각 이후의 판만 한 번 더 반영한다. 앞 글에서 판 ID로 중복을 거르게 해 둔 덕분에 겹쳐 반영해도 안전하다.

## 나눈 뒤에 생기는 문의

- 같은 사람이 순위표에 두 번 나온다. 점수 구간 샤드에서 이동 중에 죽은 흔적이다. 사용자별 현재 점수와 맞지 않는 샤드에 있는 멤버를 찾는 청소 작업이 도는지 본다.
- 월초에 리더보드가 유난히 느리다. 점수 구간 샤드의 경계가 지난달 말 분포에 맞춰져 있어 모두가 샤드 0에 몰렸는지 본다. 샤드별 `ZCARD`와 명령 수를 비교한다.
- 해시 샤드로 바꾼 뒤 상위 10명 조회의 p99만 튀었다. 평균이 아니라 가장 느린 샤드 하나가 전체를 정한다. 샤드별 지연을 따로 보고, 그 샤드에서 큰 범위 조회가 도는지 `SLOWLOG`를 본다.
- 동점인데 순서가 매번 다르다. 합성 점수가 2의 53제곱을 넘어 반올림되고 있는지 본다. 승수 최댓값과 시각 단위로 최대 점수를 계산해 본다.

## 샤드 결과를 직접 합쳐 보기

해시 샤드의 상위 k명 병합을 짜 보자. `shards`는 샤드별 목록의 배열이고, 각 목록은 `[이름, 점수]` 쌍이 점수 내림차순(같은 점수는 이름 오름차순)으로 정렬돼 있다. 전체에서 점수 내림차순, 같은 점수는 이름 오름차순으로 앞 `k`명을 돌려준다. 샤드가 비어 있을 수도 있다.

## 다음에 읽을 글

순위표 키 하나는 Redis Cluster가 나눠 주지 않으니 직접 쪼갠다. 점수 구간으로 나누면 상위 10명과 순위가 빠르지만 사용자가 샤드를 옮기고 경계가 낡는다. 사용자 ID로 나누면 고르게 퍼지지만 읽을 때마다 모든 샤드를 모으고, 깊은 페이지는 사실상 못 준다. 동점은 승수와 시각을 2의 53제곱 안에 나눠 담은 합성 점수로 깨고, 다 잃으면 원본에서 새 키에 채워 `RENAME`으로 바꾼다.

리더보드 두 편은 여기까지다. 다음 장은 [결제 시스템 설계 ①](/posts/sd-payment-flow)이다. 리더보드는 점수가 한 번 더 올라가도 사과로 끝나지만, 결제는 한 번 더 청구되면 그대로 사고다. 같은 "두 번 처리"를 훨씬 엄격하게 다룬다.

## 면접에서 나올 만한 질문

### Redis Cluster를 쓰면 리더보드가 자동으로 나뉘지 않나요?

나뉘지 않는다. Cluster는 키 단위로 슬롯에 나누는데, 순위표는 정렬된 셋 키 하나라 통째로 한 노드에 있다. 노드를 늘려도 그 키의 메모리와 쓰기는 한 노드가 다 받는다. 그래서 점수 구간이나 사용자 ID 기준으로 키를 여러 개로 나누는 일은 애플리케이션이 한다.

### 점수 구간 샤딩과 해시 샤딩은 무엇이 다른가요?

점수 구간 샤딩은 상위 10명이 맨 위 샤드에 모여 있어 한 곳만 묻고, 순위도 내 샤드 순위에 위 샤드 인원을 더해 빨리 구한다. 대신 점수가 경계를 넘으면 샤드를 옮겨야 하고, 분포가 바뀌면 경계를 다시 정해야 한다. 해시 샤딩은 사람이 고르게 퍼지고 이동이 없지만, 상위 10명과 순위를 구할 때 모든 샤드에 묻고 합치는 스캐터-개더가 필요하다.

### 해시 샤드에서 특정 사용자의 순위는 어떻게 구하나요?

공동 순위라면 내 점수를 알아낸 뒤 모든 샤드에 `ZCOUNT key (점수 +inf`를 동시에 보내 더하고 1을 더한다. 샤드마다 O(log N)이라 비용은 샤드 수만큼의 왕복이다. 동점까지 서로 다른 순위를 매기거나 깊은 위치의 목록을 보여 주는 일은 샤드마다 많은 데이터를 받아야 해서 비싸다.

### 월간 토너먼트에서 점수 구간 샤딩의 함정은요?

매달 1일에 모두 0점에서 시작해서 월초에는 전원이 가장 낮은 구간 샤드에 몰린다. 지난달 말 분포로 정한 경계는 월초에 맞지 않는다. 지난달 같은 시점의 분포로 경계를 정하거나, 주기적으로 분포를 다시 재 경계를 옮기고 사용자를 백그라운드로 이동한다.

### 같은 점수일 때 먼저 도달한 사람을 위에 두려면요?

점수 하나에 승수와 시각을 함께 담는다. 승수에 2의 22제곱을 곱하고, 한 달 안의 경과 초를 최댓값에서 뺀 값을 더하면 먼저 도달한 사람이 큰 점수를 갖는다. 이길 때마다 시각 부분이 바뀌니 `ZINCRBY` 대신 읽고 계산해 넣는 Lua 스크립트를 쓴다. Redis 점수는 배정밀도 실수라 최대 점수가 2의 53제곱 안인지 반드시 계산해 둔다.

### Redis 데이터를 다 잃으면 어떻게 복구하나요?

원본인 DB의 판 기록을 사용자별로 합쳐 새 키에 채우고, 다 채운 뒤 `RENAME`으로 한 번에 바꾼다. 100만 명을 3.1초에 채웠으니 1억 5천만 명은 한 연결로 수 분, 샤드별 병렬이면 더 짧다. 재구성 중에 들어온 판은 교체 후 다시 반영하는데, 판 ID로 중복을 거르게 해 두었기 때문에 겹쳐도 안전하다.

### Redis 대신 NoSQL로 만들면 무엇을 포기하나요?

정확한 순위다. 쓰기를 여러 파티션으로 흩어야 하니 상위 10명은 스캐터-개더로 구할 수 있지만, 내 앞에 몇 명이 있는지 빨리 세 주는 연산이 없다. 그래서 점수 분포로 구간 경계를 주기적으로 계산해 "상위 몇 %"를 보여 주는 식으로 타협하고, 정확한 순위는 상위권에게만 준다.
