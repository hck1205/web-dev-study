금요일 오후, 설정 파일 하나에 오타가 있었다. 고친 사람은 PR을 열지 않고 main에 바로 푸시했다. 한 줄짜리라 괜찮을 거라 생각했고, 저장소는 아무것도 막지 않았다. 배포 파이프라인은 main에 커밋이 들어오자마자 돌았고 10분 뒤 결제 API가 500을 냈다. 사후 회의에서 "리뷰를 받았어야 했다"는 말이 나왔지만, 그 말은 이미 팀 문서에 적혀 있었다.

사람에게 약속을 지키라고 하는 대신 저장소가 지키게 만드는 것이 이 글의 주제다. 브랜치 보호와 ruleset, 승인과 새 커밋의 관계, 필수 상태 검사, CODEOWNERS, 저장소 권한, 템플릿과 이슈 관리, 그리고 GitHub이 제공하는 보안 기능을 차례로 본다. 브랜치 전략을 어떻게 고를지는 [브랜치 전략 글](/posts/git-branching-strategy)에서, 리뷰어가 PR을 어떤 순서로 읽는지는 [코드 리뷰 글](/posts/code-review-practices)에서 다룬다. 기준은 2026년 하반기 github.com의 화면과 REST API다. GitHub은 설정 이름과 메뉴 위치를 자주 바꾸니, 화면이 조금 다르면 이름으로 찾으면 된다.

## 규칙은 사람보다 서버가 지킨다

Git 자체에는 "이 브랜치에는 리뷰를 받은 커밋만 들어온다" 같은 개념이 없다. 쓰기 권한이 있으면 누구나 `git push origin main`을 할 수 있다. 로컬의 pre-push 훅으로 막을 수도 있지만 훅은 각자의 컴퓨터에 있어서 `--no-verify` 하나로 건너뛴다. 막는 일은 푸시를 받는 서버가 해야 한다.

GitHub에서 그 역할을 하는 것이 브랜치 보호 규칙(branch protection rule)과 그 후속인 ruleset이다. 둘 다 "이 브랜치에 무엇이 들어올 수 있는가"를 정한다. 흔히 거는 조건은 이렇다.

- PR을 거치지 않은 직접 푸시 금지
- 승인 리뷰 최소 개수
- 필수 상태 검사(CI) 통과
- 강제 푸시와 브랜치 삭제 금지
- 코드 오너 승인, 리뷰 대화 해결, 선형 히스토리, 서명된 커밋

규칙을 걸면 그 금요일의 푸시는 이렇게 거절된다. 메시지 형식은 GitHub이 바꿀 수 있지만 대략 이 모양이다.

```text
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote: - Changes must be made through a pull request.
```

## 브랜치 보호 규칙과 ruleset

예전부터 있던 브랜치 보호 규칙은 저장소 설정의 Branches 메뉴에서 브랜치 패턴 하나에 규칙 묶음 하나를 건다. 2023년에 정식으로 나온 ruleset은 같은 일을 더 유연하게 한다. 새로 설정한다면 ruleset을 쓰는 편이 낫다. 차이는 네 가지 정도다.

첫째, 겹쳐서 건다. 한 브랜치에 ruleset 여러 개가 걸리면 규칙이 모두 합쳐지고, 같은 규칙이면 가장 엄격한 값이 이긴다. "모든 브랜치에 강제 푸시 금지"와 "main에는 승인 2개"를 따로 만들 수 있다. 기존 브랜치 보호 규칙과도 함께 적용된다.

둘째, 우회할 수 있는 대상(bypass list)을 명시한다. 저장소 관리자, 특정 팀, 배포용 GitHub App을 지정하고, 항상 우회할지 PR을 통해서만 우회할지도 고른다. 브랜치 보호 규칙의 "관리자에게도 적용" 체크 하나보다 세밀하다.

셋째, 읽기 권한만 있어도 규칙을 볼 수 있다. 브랜치 보호 규칙은 관리자만 설정 화면을 볼 수 있어서 "왜 머지가 안 되지"를 일반 개발자가 확인하기 어려웠다. ruleset은 CLI로도 바로 볼 수 있다.

```bash
gh ruleset list                 # 이 저장소에 걸린 ruleset 목록
gh ruleset check main           # main 브랜치에 실제로 적용되는 규칙 모음
gh ruleset view --web           # 브라우저에서 자세히 보기
```

넷째, 조직 단위로 건다. 조직 설정에서 "이름이 `prod-`로 시작하는 모든 저장소의 기본 브랜치"처럼 저장소를 골라 한 번에 걸 수 있다(조직 ruleset은 요금제에 따라 쓸 수 있는 범위가 다르다).

설정은 화면에서 해도 되지만 저장소가 많으면 API로 같은 규칙을 찍어 내는 편이 낫다. 아래는 기본 브랜치에 거는 ruleset 하나다. 규칙 이름과 필드는 REST API 문서의 형식을 따랐다.

```bash
# 기본 브랜치에 ruleset을 만든다 (OWNER/REPO는 바꿔 쓴다)
gh api -X POST repos/OWNER/REPO/rulesets --input main-ruleset.json
```

```json
{
  "name": "protect-main",
  "target": "branch",
  "enforcement": "active",
  "conditions": {
    "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] }
  },
  "bypass_actors": [
    { "actor_id": 5, "actor_type": "RepositoryRole", "bypass_mode": "pull_request" }
  ],
  "rules": [
    { "type": "deletion" },
    { "type": "non_fast_forward" },
    { "type": "required_linear_history" },
    {
      "type": "pull_request",
      "parameters": {
        "required_approving_review_count": 1,
        "dismiss_stale_reviews_on_push": true,
        "require_code_owner_review": true,
        "require_last_push_approval": true,
        "required_review_thread_resolution": true
      }
    },
    {
      "type": "required_status_checks",
      "parameters": {
        "strict_required_status_checks_policy": false,
        "required_status_checks": [{ "context": "test" }, { "context": "build" }]
      }
    }
  ]
}
```

`~DEFAULT_BRANCH`는 기본 브랜치 이름이 main이든 master든 따라간다. `non_fast_forward`가 강제 푸시 금지이고, `bypass_actors`의 역할 id 5는 저장소 관리자다. `bypass_mode`를 `pull_request`로 두면 관리자도 PR을 열어야 하고, 급할 때 그 PR에서만 규칙을 건너뛸 수 있다. 우회 기록이 PR에 남는다는 점이 직접 푸시를 허용하는 것과 다르다.

한 가지는 미리 알아 둔다. 비공개 저장소에서 브랜치 보호와 ruleset을 쓰려면 Free가 아닌 요금제(Pro, Team, Enterprise)가 필요하다. 공개 저장소는 Free에서도 된다. 개인 비공개 저장소에서 설정 화면이 보이는데 적용이 안 된다면 요금제부터 확인한다.

## 승인 뒤에 커밋이 또 올라오면

승인을 받은 뒤 작성자가 커밋을 하나 더 올렸다. 그 승인은 아직 유효해야 할까. 유효하다면 승인받은 뒤 아무 코드나 끼워 넣고 합칠 수 있다. 무효라면 오타 하나 고칠 때마다 다시 리뷰어를 찾아야 한다.

GitHub은 이 사이에 손잡이를 두 개 둔다.

- dismiss stale approvals: 새 커밋이 올라오면 기존 승인을 무효로 돌린다. 리뷰어가 본 것과 합쳐지는 것이 같다는 걸 보장한다.
- require approval of the most recent reviewable push: 마지막으로 푸시한 사람이 아닌 누군가가 마지막 푸시를 승인해야 한다. A가 승인한 PR에 B가 몰래 커밋을 올리고 자기가 합치는 일을 막는다.

둘 다 켜면 가장 안전하지만 리뷰가 느려진다. 실무에서 고르는 기준은 이렇다. 배포가 바로 일어나는 브랜치나 결제·인증처럼 사고 비용이 큰 저장소라면 둘 다 켠다. 이때 리뷰어가 다시 볼 부분이 적도록 강제 푸시 대신 커밋을 덧붙이고, 다시 쌓았다면 [stacked PR 글](/posts/git-stacked-prs)에서 본 `git range-diff`로 바뀐 부분만 보여 준다. 사내 도구처럼 위험이 낮은 저장소라면 stale 무효화는 끄고 최근 푸시 승인만 켜는 절충도 있다. 무엇을 고르든 팀이 이유를 알고 고르는 게 중요하다. 그냥 기본값으로 두면 대개 둘 다 꺼져 있다.

## 필수 상태 검사가 영원히 기다리는 이유

필수 상태 검사는 이름으로 건다. 위 ruleset의 `test`, `build`가 그 이름이다. GitHub Actions라면 job의 이름(job id, 또는 `name:`을 줬다면 그 값)이 검사 이름이 된다. 여기서 두 가지 사고가 자주 난다.

첫째, 이름이 바뀐다. 워크플로에서 job 이름을 `test`에서 `unit-test`로 바꾸거나 matrix를 추가해 `test (20)`, `test (22)`가 되면, 규칙은 여전히 `test`라는 이름을 기다린다. 그 이름의 결과는 영원히 오지 않으니 PR에는 "Expected — Waiting for status to be reported"가 남고 머지 버튼이 잠긴다. matrix를 쓴다면 모든 matrix job이 끝난 뒤 도는 요약 job 하나를 두고 그 이름을 필수로 거는 방법이 흔하다.

```yaml
# .github/workflows/ci.yml
jobs:
  test:
    strategy:
      matrix:
        node: [20, 22]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pnpm install --frozen-lockfile && pnpm test
  ci-ok:                       # 필수 검사로는 이 이름 하나만 건다
    if: always()
    needs: [test]
    runs-on: ubuntu-latest
    steps:
      - run: test "${{ needs.test.result }}" = "success"
```

`if: always()`가 없으면 test가 실패했을 때 ci-ok가 건너뛰어지고, 건너뛴 job은 성공으로 보고된다. 실패한 PR이 통과하는 셈이라 꼭 붙인다.

둘째, 경로 필터. `on.pull_request.paths: ["src/**"]`처럼 걸어 두면 문서만 바꾼 PR에서는 워크플로가 아예 시작하지 않는다. GitHub 문서도 이렇게 경로·브랜치 필터로 건너뛴 워크플로의 검사는 Pending으로 남아 필수 검사를 막는다고 적고 있다. 반면 job 단위의 `if:` 조건으로 건너뛴 것은 성공으로 보고된다. 그래서 필수 검사가 걸린 워크플로에는 트리거 단계의 경로 필터를 쓰지 않고, 워크플로는 항상 돌게 둔 채 job 안에서 바뀐 경로를 보고 건너뛴다.

"머지 전에 최신 main을 반영하라"(strict)도 생각할 거리다. 켜면 main과 합친 결과로 검사받은 PR만 합쳐져서, 각자는 통과했는데 합치니 깨지는 일이 줄어든다. 대신 누군가 먼저 합칠 때마다 다른 PR이 모두 다시 업데이트하고 CI를 다시 돌려야 한다. PR이 많은 저장소에서는 이 줄 서기가 병목이 되는데, 그때 쓰는 것이 머지 큐(merge queue)다. 합치려는 PR을 큐에 넣으면 GitHub이 앞의 PR들과 합친 임시 브랜치를 만들어 검사하고 통과한 순서대로 합친다. 머지 큐를 쓰려면 워크플로가 `merge_group` 이벤트에도 반응해야 한다. 이걸 빼먹으면 큐에 들어간 PR의 검사가 시작되지 않는다.

```yaml
on:
  pull_request:
  merge_group:        # 머지 큐가 만든 임시 브랜치에서도 돈다
```

## CODEOWNERS는 마지막 줄이 이긴다

CODEOWNERS는 경로별 담당자 목록이다. 저장소의 `.github/`, 루트, `docs/` 중 한 곳에 `CODEOWNERS`라는 이름으로 두면, PR이 그 경로를 건드릴 때 담당자에게 자동으로 리뷰를 요청한다. ruleset에서 코드 오너 승인을 필수로 걸면 그 담당자 중 한 명의 승인이 있어야 합쳐진다.

```text
# .github/CODEOWNERS
# 기본 담당
* @acme/platform
*.md @acme/docs
/apps/web/ @acme/frontend
payments/ @acme/payments @kim
/apps/web/package.json
```

규칙은 `.gitignore`와 비슷한 패턴에 하나가 다르다. 위에서부터 맞춰 보되, 맞는 줄이 여러 개면 마지막에 맞은 줄이 이긴다. 그래서 넓은 규칙을 위에, 좁은 규칙을 아래에 둔다. 아래 그림은 `apps/web/src/payments/api.ts`가 어느 팀에게 가는지 한 줄씩 따라간다.

마지막 줄처럼 담당자 없이 패턴만 쓰면 "이 파일은 담당자 없음"이 된다. 위에서 프런트엔드 팀이 맡았던 `apps/web/package.json`의 담당자를 지우는 효과가 있다. 반대로 실수하기 쉬운 것도 이 규칙이다. `/apps/web/` 아래의 문서는 `*.md`보다 아래에 있는 `/apps/web/` 줄이 이겨서 문서 팀이 아니라 프런트엔드 팀에게 간다. 문서 팀이 모든 md를 보게 하고 싶다면 `*.md` 줄을 맨 아래로 내려야 한다.

몇 가지 규칙이 더 있다.

- 담당자로 적은 사람이나 팀은 그 저장소에 쓰기 권한이 있어야 한다. 권한이 없는 팀을 적으면 GitHub이 그 줄을 오류로 표시하고 리뷰 요청을 보내지 않는다. 저장소의 CODEOWNERS 파일 화면에서 오류가 있는 줄을 보여 주니 바꾼 뒤에 한 번 열어 본다.
- 사람보다 팀을 적는다. 사람이 퇴사하거나 팀을 옮겨도 파일을 고칠 필요가 없고, 팀 설정의 자동 배정(라운드 로빈, 부하 분산)으로 팀원 중 한 명에게만 요청이 가게 할 수 있다.
- `.gitignore`와 달리 `!`로 시작하는 제외 패턴과 `[a-z]` 같은 범위는 쓸 수 없다.
- 초안(draft) PR에는 코드 오너 리뷰 요청이 가지 않는다. Ready for review로 바꿀 때 요청된다.
- CODEOWNERS 파일 자체에도 담당자를 둔다. `/.github/CODEOWNERS @acme/platform`을 두지 않으면 누구든 자기를 결제 코드의 오너로 적는 PR을 올려 스스로 승인 조건을 풀 수 있다.

## 누가 무엇을 할 수 있나

규칙을 아무리 걸어도 관리자 권한을 모두가 갖고 있으면 의미가 없다. 권한 구조는 계정 종류에 따라 다르다.

개인 계정의 저장소는 단순하다. 소유자와 협업자(collaborator)뿐이고, 협업자는 푸시와 머지를 할 수 있지만 설정은 못 바꾼다. 세밀하게 나눌 방법이 없으니 팀이 쓰는 저장소는 처음부터 조직(organization)에 둔다.

조직의 저장소는 역할 다섯 단계로 나눈다.

- Read: 코드를 보고 이슈와 PR에 댓글을 단다.
- Triage: 코드는 못 바꾸지만 이슈와 PR에 라벨을 붙이고 닫고 담당자를 지정한다. 이슈를 정리하는 사람에게 준다.
- Write: 브랜치에 푸시하고 PR을 합친다. 대부분의 개발자.
- Maintain: 저장소 설정 일부(토픽, 위키, 머지 방식)를 바꾸지만 삭제나 공개 범위 변경 같은 위험한 일은 못 한다.
- Admin: 모든 설정, 규칙, 삭제, 공개 범위 변경.

사람마다 역할을 주지 않고 팀에 준다. 조직 안에 `frontend`, `payments` 같은 팀을 만들고, 팀에 저장소별 역할을 주고, 사람은 팀에 넣는다. 하위 팀은 상위 팀의 권한을 물려받는다. 조직 전체 기본 권한(base permission)은 Read나 없음으로 두고 필요한 만큼만 팀으로 올린다. 외부 협력사 직원은 조직 구성원이 아니라 외부 협업자(outside collaborator)로 특정 저장소에만 넣는다.

## 공개 저장소와 비공개 저장소

공개 범위는 코드를 누가 보는지만 정하는 게 아니다. 외부 기여가 들어오는 방식과 CI의 보안이 함께 바뀐다.

공개 저장소에 외부 사람이 PR을 보내면 그 사람의 fork에서 온다. 이때 `pull_request` 이벤트로 도는 워크플로는 읽기 전용 토큰을 받고, 저장소의 시크릿을 받지 못한다. 모르는 사람이 워크플로 파일을 고쳐 시크릿을 빼 가는 걸 막는 장치다. 처음 기여하는 사람의 워크플로는 관리자가 승인해야 실행되게 하는 설정도 있다.

이걸 피하려고 `pull_request_target`을 쓰면 위험해진다. 이 이벤트는 base 저장소의 권한과 시크릿으로 돈다. 여기서 PR의 코드를 체크아웃해서 빌드하거나 테스트하면, 외부인이 쓴 코드가 시크릿을 들고 실행된다. 라벨 붙이기나 댓글 달기처럼 PR 코드를 실행하지 않는 일에만 쓴다.

비공개 저장소를 공개로 바꿀 때는 지금 파일이 아니라 히스토리 전체가 공개된다는 걸 기억한다. 몇 년 전에 지운 `.env`도 커밋 안에 그대로 있다. 바꾸기 전에 비밀 값 검사를 히스토리 전체에 돌리고, 나온 값은 빼는 것보다 먼저 폐기한다. 빼는 방법은 [커밋에 들어가면 안 되는 것 글](/posts/git-large-files-secrets)에 있다.

## PR이 리뷰받기 좋은 모양

규칙이 PR을 강제하면 PR의 질이 리뷰 속도를 정한다. 리뷰어가 가장 먼저 부딪히는 것은 크기와 설명이다.

크기는 줄 수보다 "한 가지 이유로 바뀌었나"로 본다. 리팩터링과 기능 추가가 섞이면 리뷰어는 이름 바꾸기 200줄 사이에서 실제 로직 변경 20줄을 찾아야 한다. 이름 바꾸기 PR을 먼저 합치고, 기능 PR을 그다음에 올린다. 서로 의존하는 큰 작업은 [stacked PR](/posts/git-stacked-prs)로 쌓는다.

설명에는 리뷰어가 코드를 보기 전에 알아야 할 것을 쓴다. 왜 바꾸는지, 무엇을 바꿨는지, 어떻게 확인했는지, 어디를 특히 봐 달라는지. 화면이 바뀌면 전후 스크린샷을 붙인다. 아직 의견만 받고 싶으면 draft PR로 연다. draft에는 코드 오너 요청이 가지 않아서 담당 팀을 귀찮게 하지 않는다.

리뷰어가 무엇을 어떤 순서로 보는지, 코멘트를 어떻게 다는지는 [코드 리뷰 글](/posts/code-review-practices)에서 따로 다룬다. 이 글에서는 그 과정을 저장소가 어떻게 받쳐 주는지만 본다.

## 템플릿과 CONTRIBUTING이 대신 묻는 것

PR 템플릿은 위의 질문을 매번 본문에 미리 채워 둔다. `.github/pull_request_template.md`에 두면 모든 PR이 이 내용으로 시작한다.

```md
<!-- .github/pull_request_template.md -->
## 왜
<!-- 이 변경이 필요한 이유. 이슈가 있으면 Fixes #번호 -->

## 무엇을
<!-- 바뀐 동작. 리팩터링만 있으면 그렇다고 쓴다 -->

## 어떻게 확인했나
- [ ] 단위 테스트
- [ ] 로컬에서 직접 실행
- [ ] 스크린샷 (화면 변경 시)

## 리뷰어에게
<!-- 특히 봐 줬으면 하는 곳, 고민한 대안 -->
```

`Fixes #123`처럼 본문에 닫기 키워드(close, fix, resolve와 그 변형)를 쓰면 PR이 기본 브랜치에 합쳐질 때 그 이슈가 자동으로 닫힌다. 기본 브랜치가 아닌 곳으로 합치면 닫히지 않는다. 템플릿이 여러 개 필요하면 `.github/PULL_REQUEST_TEMPLATE/` 디렉터리에 파일을 여러 개 두고 PR 주소에 `?template=hotfix.md`를 붙여 고르게 한다. CLI라면 `gh pr create --template hotfix.md`다.

이슈는 자유 서식 대신 이슈 폼(issue form)으로 받는다. YAML로 칸을 정하면 필수 항목을 빼먹은 버그 신고가 줄어든다.

```yaml
# .github/ISSUE_TEMPLATE/bug.yml
name: 버그 신고
description: 기대와 다르게 동작하는 것
labels: ["bug", "triage"]
body:
  - type: textarea
    id: what
    attributes:
      label: 무슨 일이 있었나
      description: 기대한 동작과 실제 동작
    validations:
      required: true
  - type: input
    id: version
    attributes:
      label: 버전
      placeholder: "1.4.2"
  - type: dropdown
    id: env
    attributes:
      label: 환경
      options: ["production", "staging", "local"]
```

```yaml
# .github/ISSUE_TEMPLATE/config.yml
blank_issues_enabled: false          # 템플릿 없는 빈 이슈를 막는다
contact_links:
  - name: 보안 취약점 신고
    url: https://github.com/acme/web/security/advisories/new
    about: 공개 이슈 대신 비공개로 알려 주세요
```

`CONTRIBUTING.md`는 기여 방법을 적는 문서다. 브랜치 이름 규칙, 커밋 메시지 규칙, 로컬에서 테스트 돌리는 법, 리뷰를 언제쯤 받을 수 있는지를 적는다. 루트, `docs/`, `.github/` 중 한 곳에 두면 이슈나 PR을 열 때 GitHub이 링크를 보여 준다. 보안 취약점을 어디로 알릴지는 `SECURITY.md`에 따로 쓴다. 조직이라면 `.github`라는 이름의 공개 저장소에 이런 파일을 두면 파일이 없는 저장소 전체의 기본값이 된다. 단, CODEOWNERS는 이 방식으로 물려줄 수 없고 저장소마다 둬야 한다.

README는 저장소의 첫 화면이다. 이 저장소가 무엇인지, 어떻게 띄우는지, 어디에 배포되는지, 누구에게 물어보는지만 있어도 새로 온 사람이 첫날 덜 헤맨다. 길고 자주 바뀌는 설계 문서는 위키나 `docs/` 디렉터리로 뺀다. 위키는 PR 리뷰를 거치지 않으니, 리뷰가 필요한 문서는 `docs/`에 코드와 함께 두는 편이 낫다. 질문과 토론처럼 할 일이 아닌 대화는 이슈 대신 Discussions로 옮긴다.

## 라벨, 이슈, Projects 보드로 흐름을 본다

이슈가 수백 개 쌓이면 라벨이 없으면 아무것도 못 찾는다. 새 저장소에는 `bug`, `documentation`, `duplicate`, `enhancement`, `good first issue`, `help wanted`, `invalid`, `question`, `wontfix`가 기본으로 있다. 여기에 접두어로 축을 나눈 라벨을 더하면 필터가 쉬워진다.

```bash
# 종류, 우선순위, 영역을 접두어로 나눈다
gh label create "type: bug" --color d73a4a --description "기대와 다르게 동작"
gh label create "priority: p1" --color b60205 --description "이번 주 안에"
gh label create "area: payments" --color 0e8a16
gh label create "triage" --color fbca04 --description "아직 분류 전"

# 다른 저장소의 라벨을 그대로 복사
gh label clone acme/web --repo acme/pay-api
```

새 이슈는 폼에서 `triage` 라벨을 달고 들어오고, 정해진 사람이 주기적으로 `label:triage`를 보며 종류, 우선순위, 담당을 정하고 `triage`를 뗀다. 이 일에 Triage 역할이 맞는다. 같은 답을 자주 쓴다면 저장된 답변(saved replies)에 넣어 둔다. 개인 설정이라 팀 전체가 공유하지는 않는다.

할 일의 흐름은 Projects로 본다. 지금의 Projects는 여러 저장소의 이슈와 PR을 한 표에 모으고, 같은 데이터를 표(table), 보드(board), 로드맵(roadmap) 세 화면으로 보여 준다. 상태, 우선순위, 스프린트(iteration) 같은 칸을 직접 만든다. 기본 제공 자동화로 "이슈가 닫히면 상태를 Done으로", "PR이 합쳐지면 Done으로", "이 저장소에 새 이슈가 생기면 보드에 추가" 정도를 켜 두면 손으로 옮길 일이 크게 준다. 칸반 보드의 열은 할 일, 진행 중, 리뷰 중, 완료 정도로 짧게 둔다. 열이 많으면 아무도 옮기지 않는다.

`@사용자`나 `@조직/팀`을 쓰면 알림이 간다. 팀을 멘션하면 팀원 전체에게 가니, 질문은 사람 하나에게 하고 팀 멘션은 팀 전체가 알아야 할 때만 쓴다. "저도 같은 문제가 있어요" 같은 댓글은 이모지 반응으로 대신하면 이슈를 구독한 사람 모두에게 가는 알림이 준다.

## 저장소가 대신 봐 주는 보안

GitHub은 저장소 안의 위험을 찾아 주는 기능 세 가지를 준다. 설정의 보안 메뉴에서 켠다.

Dependabot은 의존성의 알려진 취약점을 본다. 저장소의 lockfile로 의존성 그래프를 만들고 GitHub Advisory Database와 맞춰 보다가 해당하는 버전이 있으면 알림을 띄운다. 보안 업데이트를 켜면 고친 버전으로 올리는 PR까지 열어 준다. 취약점과 상관없이 버전을 꾸준히 올리게 하려면 설정 파일을 둔다.

```yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 5
    groups:
      dev-tools:                 # 개발 도구는 PR 하나로 묶는다
        dependency-type: "development"
        update-types: ["minor", "patch"]
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "monthly"
```

묶지 않으면 주마다 PR이 수십 개 쌓이고, 결국 아무도 안 보는 PR 더미가 된다. 묶음과 주기를 정하고, 자동 머지는 테스트가 충분한 patch 업데이트에만 거는 정도가 무난하다. 업데이트 봇의 운영 전략은 [의존성 지옥 글](/posts/dependency-hell)에서 더 다룬다.

secret scanning은 커밋 안의 API 키, 토큰 같은 비밀 값을 패턴으로 찾는다. 공개 저장소에서는 무료이고, 비공개 저장소는 유료 기능(GitHub Secret Protection)이다. push protection을 켜면 비밀 값이 든 커밋은 푸시 단계에서 거절된다. 알림이 떴다면 값을 히스토리에서 지우는 것보다 그 값을 폐기하고 새로 발급하는 것이 먼저다. 푸시된 순간 이미 누군가 받아 갔을 수 있다.

code scanning은 코드를 정적 분석해 SQL 인젝션, 경로 조작 같은 취약한 흐름을 찾는다. CodeQL의 기본 설정(default setup)을 켜면 워크플로 파일 없이 지원 언어를 알아서 분석하고, 결과가 PR에 주석으로 달린다. 다른 분석 도구의 결과도 SARIF 형식으로 올리면 같은 화면에 모인다. ruleset에 "code scanning 결과 필수" 규칙을 걸면 심각도가 높은 경고가 있는 PR은 합치지 못하게 할 수 있다. 공개 저장소는 무료, 비공개는 유료(GitHub Code Security)다.

<Callout kind="warning">
비밀 값 알림을 받고 그 커밋을 지우거나 강제 푸시로 덮는 것으로 끝내면 안 된다. fork, 다른 사람의 로컬 clone, CI 캐시, GitHub이 보관하는 PR 참조에 값이 남는다. 순서는 폐기와 재발급, 그 값으로 접근한 기록 확인, 그다음 히스토리 정리다.
</Callout>

## 리뷰가 병목이 될 때

규칙을 다 켜면 이번엔 PR이 리뷰를 기다리며 쌓인다. 규칙을 다시 끄는 대신 기다림이 어디서 생기는지 본다.

리뷰어가 몇 명에게 몰린다면 CODEOWNERS가 너무 넓거나 사람 이름으로 적혀 있는 경우가 많다. 사람 대신 팀을 적고, 팀 설정의 코드 리뷰 자동 배정으로 팀원에게 고르게 나눈다. 경로를 잘게 나눠 아무 상관 없는 팀이 오너로 걸리지 않게 한다.

PR이 크면 리뷰가 늦다. 누가 열어 봐도 한 번에 끝나지 않을 것 같으면 다들 미룬다. 작게 나누고, 리팩터링은 따로 올린다.

검사와 머지의 줄 서기가 길다면 strict 요구를 끄고 머지 큐로 옮긴다. 각자 main을 따라잡느라 CI를 다시 돌리는 시간이 사라진다.

시간이 문제라면 팀이 약속을 정한다. 예를 들어 "리뷰 요청은 근무 시간 기준 하루 안에 첫 응답"처럼. 첫 응답이 승인일 필요는 없다. "오늘은 못 보니 다른 사람에게 넘긴다"도 응답이다. 리뷰가 어떻게 생산성에 영향을 주는지는 [코드 리뷰 글](/posts/code-review-practices)에서 더 본다.

## 그 금요일의 푸시를 다시 막는다면

ruleset이 main으로의 직접 푸시를 거절하고, PR을 열면 CODEOWNERS가 설정 파일의 담당 팀을 리뷰어로 부른다. 필수 검사가 설정 파일 문법을 확인하고, 승인 뒤에 커밋이 또 오면 다시 승인을 받는다. 관리자도 급할 때는 PR 안에서만 우회하고 그 기록이 남는다. 저장소 권한은 팀 단위로 최소한만 주고, Dependabot과 secret scanning이 사람이 놓치는 것을 본다. 약속을 문서에 적는 대신 저장소에 적어 둔 것이다.

## 면접에서 나올 만한 질문

### 브랜치 보호 규칙은 왜 필요한가요? 팀 규칙으로 정하면 안 되나요?

Git은 쓰기 권한만 있으면 누구나 아무 브랜치에 푸시할 수 있어서, 문서로 정한 규칙은 급할 때 건너뛰게 된다. 로컬 훅도 `--no-verify`로 넘어간다. 그래서 푸시를 받는 서버가 PR 필수, 승인 수, 필수 검사, 강제 푸시 금지를 강제한다. 관리자 우회도 PR 안에서만 허용해 기록이 남게 한다.

### 브랜치 보호 규칙과 ruleset은 무엇이 다른가요?

ruleset은 여러 개를 겹쳐 걸 수 있고 같은 규칙이면 가장 엄격한 값이 적용된다. 우회 대상을 역할, 팀, 앱 단위로 정하고 PR을 통해서만 우회하게 할 수 있다. 읽기 권한만 있어도 걸린 규칙을 볼 수 있어서 개발자가 머지가 막힌 이유를 직접 확인한다. 조직 단위로 여러 저장소에 한 번에 걸 수도 있다. 새로 설정한다면 ruleset을 쓰고, 기존 브랜치 보호 규칙과는 함께 적용된다.

### 승인을 받은 뒤 새 커밋을 푸시하면 승인을 무효로 해야 하나요?

사고 비용이 큰 브랜치라면 무효로 하는 편이 맞다. 그렇지 않으면 승인받은 뒤 리뷰받지 않은 코드를 끼워 넣을 수 있다. 여기에 마지막 푸시를 푸시한 사람이 아닌 사람이 승인하게 하는 옵션을 더하면 남의 승인에 올라타는 것도 막는다. 대신 재승인 때문에 리뷰가 느려지니, 강제 푸시 대신 커밋을 덧붙이거나 range-diff로 바뀐 부분만 보여 줘 재리뷰 비용을 줄인다. 위험이 낮은 저장소라면 최근 푸시 승인만 켜는 절충도 있다.

### 필수 상태 검사가 계속 Expected 상태로 남아 머지가 안 됩니다. 원인은?

필수 검사는 이름으로 걸리기 때문에 그 이름의 결과가 오지 않으면 영원히 기다린다. job 이름을 바꿨거나 matrix를 추가해 이름이 `test (20)`처럼 바뀐 경우, 그리고 워크플로 트리거의 경로·브랜치 필터 때문에 워크플로가 아예 시작하지 않은 경우가 흔하다. 요약 job 하나를 `if: always()`로 두고 그 이름만 필수로 걸고, 경로 판단은 워크플로 안의 job 조건으로 옮긴다. 머지 큐를 쓴다면 `merge_group` 이벤트를 빼먹지 않았는지도 본다.

### CODEOWNERS에서 여러 줄이 한 파일에 맞으면 누가 오너가 되나요?

마지막에 맞은 줄의 담당자가 오너가 된다. 그래서 `*` 같은 넓은 규칙을 위에, 좁은 경로를 아래에 둔다. 담당자 없이 패턴만 적은 줄은 앞에서 정한 오너를 지운다. 오너로 적은 사람이나 팀에게 쓰기 권한이 없으면 그 줄은 오류로 무시되고, CODEOWNERS 파일 자체에도 오너를 둬야 누군가 자기를 오너로 바꾸는 PR로 조건을 푸는 일을 막는다.

### 외부 fork에서 온 PR에서 CI가 시크릿을 못 읽습니다. pull_request_target으로 바꾸면 되나요?

바꾸면 시크릿은 읽히지만 그 상태로 PR 코드를 체크아웃해 실행하면 외부인이 쓴 코드가 시크릿과 쓰기 토큰을 들고 돈다. `pull_request`가 fork PR에 읽기 전용 토큰만 주는 건 의도된 보호다. 시크릿이 필요 없는 검사는 `pull_request`에서 돌리고, 배포 미리보기처럼 시크릿이 필요한 일은 관리자가 확인한 뒤 라벨 등으로 수동 실행하게 한다. `pull_request_target`은 라벨 붙이기처럼 PR 코드를 실행하지 않는 일에만 쓴다.

### 리뷰가 병목이 되면 무엇부터 보나요?

기다림이 어디서 생기는지부터 나눈다. 리뷰어 몇 명에게 몰리면 CODEOWNERS를 팀 단위로 바꾸고 자동 배정으로 나누고, PR이 커서 미뤄지면 작게 나누고 리팩터링을 따로 올린다. CI 재실행 줄 서기가 길면 최신 main 반영 요구를 머지 큐로 바꾼다. 마지막으로 첫 응답 시간 같은 팀 약속을 정한다. 규칙을 끄는 건 원인을 다 본 뒤의 일이다.

### Dependabot, secret scanning, code scanning은 각각 무엇을 막나요?

Dependabot은 내가 쓰는 의존성 버전에 알려진 취약점이 있는지 보고 고친 버전으로 올리는 PR을 연다. secret scanning은 커밋에 들어간 키와 토큰을 찾고, push protection을 켜면 푸시 단계에서 막는다. code scanning은 내 코드의 취약한 흐름을 정적 분석으로 찾아 PR에 표시한다. 비밀 값이 이미 올라갔다면 히스토리 정리보다 폐기와 재발급이 먼저다.
