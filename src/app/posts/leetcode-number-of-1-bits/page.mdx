[Number of 1 Bits](https://leetcode.com/problems/number-of-1-bits/)는 LeetCode 191번이다. 정수 하나를 이진수로 썼을 때 1이 몇 개인지 센다. 이 개수를 해밍 가중치(Hamming weight) 또는 팝카운트(popcount)라고 부른다. 문제 자체는 반복문 하나면 끝나지만, 면접에서는 "더 빠르게", "여러 번 불리면", "음수가 들어오면"으로 이어지기 좋아서 비트 연산 기본기를 보는 문제로 자주 나온다.

`n & (n - 1)`이 가장 낮은 1을 끈다는 것과 SWAR 방식의 원리는 [비트 연산 글](/posts/bit-manipulation#가장-낮은-1-비트를-다루는-두-가지-요령)에서 봤다. 이 글에서는 이 문제 하나를 놓고 문자열 변환부터 SWAR까지 여섯 가지로 풀어 실제로 재 보고, 음수 입력에서 무한 루프가 나는 이유와 언어별 내장 함수까지 정리한다. 코드는 Node.js 22, Python 3.13, Java 21에서 직접 돌렸다.

## 이진수로 쓰면 1이 몇 개인가

양의 정수 `n`이 주어진다. `n`을 이진수로 썼을 때 1인 자리의 개수를 돌려준다.

- 지금 문제는 `n`이 1 이상 2^31 - 1 이하라고 정해 둔다. 31비트 안에 든다.
- 예전 버전은 입력을 32비트 부호 없는 정수로 주었다. 그래서 Java처럼 부호 없는 정수가 없는 언어에서는 맨 위 비트가 켜진 입력이 음수로 들어왔다. 지금 풀어도 이 경우를 생각해 두는 편이 좋다. 실제 코드에서는 음수가 들어올 수 있기 때문이다.
- 후속 질문으로 "이 함수가 아주 여러 번 불린다면 어떻게 최적화하나"가 붙어 있다.

입력이 32비트로 정해져 있으니 어떤 풀이든 최대 32번 안에 끝난다. 그래서 이 문제에서 O 표기는 대부분 O(1)이 된다. 비교할 때는 "비트 폭 w만큼 도나, 켜진 비트 수 k만큼 도나, 상수 번에 끝나나"로 나눠 보는 게 더 쓸모 있다.

## 90을 손으로 세어 보면

예시 하나를 정해 두고 끝까지 쓴다. 90은 이진수로 `1011010`이다. 8칸에 맞추면 이렇다.

```text
자리값  128  64  32  16   8   4   2   1
비트      0   1   0   1   1   0   1   0
```

64 + 16 + 8 + 2 = 90이고, 1은 네 개다. 손으로 세면 왼쪽부터 훑으며 1을 짚는다. 컴퓨터도 같은 일을 하되, 어느 쪽에서 어떻게 훑느냐가 풀이를 가른다. 글자로 바꿔 세면 문자열 풀이, 맨 아래 칸을 보고 한 칸씩 밀면 시프트 풀이, 켜진 칸만 골라 지우면 Kernighan 풀이, 여러 칸을 한꺼번에 세면 표나 SWAR 풀이다.

## 이진 문자열로 바꿔 세기

가장 먼저 떠오르는 건 언어가 이미 해 주는 일을 쓰는 것이다. JavaScript의 `toString(2)`는 수를 이진 문자열로 바꿔 준다. 그 문자열에서 `"1"`을 센다.

```js
function hammingWeight(n) {
  let count = 0;
  for (const ch of n.toString(2)) {
    if (ch === "1") count++; // 글자 하나하나가 비트 하나다
  }
  return count;
}

console.log(hammingWeight(90), hammingWeight(1), hammingWeight(2147483647), hammingWeight(128));
```

```text
4 1 31 1
```

시간은 비트 폭만큼, 공간도 문자열 길이만큼 든다. 읽기는 쉽지만 숫자를 문자열로 바꾸는 데 메모리를 새로 잡고, 글자 단위로 비교하니 느리다. 뒤의 측정에서 200만 번 부르는 데 1초가 넘게 걸렸다. 가장 빠른 풀이보다 100배 넘게 느리다.

함정이 하나 더 있다. 음수를 넣으면 `(-3).toString(2)`가 `"-11"`이 된다. 2의 보수가 아니라 부호와 절댓값이다. 그래서 32비트로 보면 1이 31개인 -3에서 2가 나온다. 음수를 32비트 그대로 보려면 `(-3 >>> 0).toString(2)`처럼 먼저 부호 없는 값으로 바꿔야 한다. 이 문제처럼 비트를 다루는 문제에서 문자열 변환을 피하는 이유다.

## 맨 아래 칸을 보고 한 칸씩 민다

문자열 없이 비트를 직접 읽는 방법이다. `n & 1`은 맨 아래 비트 하나만 남긴다. 그 값을 개수에 더하고, `n`을 오른쪽으로 한 칸 밀어 다음 비트를 맨 아래로 가져온다. `n`이 0이 되면 남은 1이 없으니 멈춘다.

```js
function hammingWeight(n) {
  let count = 0;
  while (n !== 0) {
    count += n & 1; // 맨 아래 비트가 1이면 1을 더한다
    n >>>= 1;       // 부호 없이 오른쪽으로 한 칸 민다
  }
  return count;
}

console.log(hammingWeight(90), hammingWeight(1), hammingWeight(2147483647), hammingWeight(-3));
```

```text
4 1 31 31
```

아래 그림에서 다음을 누르면 오른쪽 끝 칸부터 한 칸씩 읽어 간다. 0인 칸도 빠짐없이 들른다.

반복 횟수는 가장 높은 1의 위치만큼이다. 90은 7번 돈다. 32비트 전체로 보면 최대 32번이고, 시간은 O(w), 공간은 O(1)이다.

`>>>`와 `>>`의 차이가 이 풀이의 성패를 가른다. `>>>`는 빈 왼쪽 칸을 0으로 채우고, `>>`는 부호 비트로 채운다. 음수에서 `>>`를 쓰면 왼쪽에 1이 끝없이 들어와 `n`이 -1에서 멈추고 영원히 0이 되지 않는다. 뒤의 "틀리기 쉬운 곳"에서 실제로 돌려 본다.

### 마스크를 옮기는 같은 풀이

`n`을 밀지 않고, 1을 왼쪽으로 밀어 만든 마스크를 32자리에 차례로 대 보는 방법도 있다.

```js
function hammingWeight(n) {
  let count = 0;
  for (let i = 0; i < 32; i++) {
    if ((n & (1 << i)) !== 0) count++; // i번 자리가 켜져 있나
  }
  return count;
}
```

입력을 바꾸지 않아서 음수에도 안전하고, 항상 32번 돈다. 조건을 `!== 0`으로 쓴 데 이유가 있다. `1 << 31`은 JavaScript에서 -2147483648이라 31번 자리가 켜진 수와 AND하면 결과가 음수다. `> 0`으로 쓰면 그 자리를 놓친다. 실제로 `> 0`으로 쓴 코드에 -1을 넣으면 31이 나온다(답은 32).

이 두 풀이의 한계는 0인 칸도 똑같이 들른다는 데 있다. 1이 두 개뿐인 수라도 가장 높은 1까지는 전부 훑는다. 켜진 칸만 골라 갈 수 있으면 더 적게 돈다.

## 켜진 비트만 골라 지운다

`n & (n - 1)`은 `n`에서 가장 낮은 1 하나를 끈다. 1을 빼면 가장 낮은 1이 0이 되고 그 아래 0들이 모두 1로 바뀌는데, 원래 수와 AND하면 바뀐 부분이 모두 0이 되기 때문이다. 이걸 `n`이 0이 될 때까지 반복하면 반복 횟수가 곧 1의 개수다. Brian Kernighan이 C 언어 책에서 소개해 그의 이름으로 부른다.

```js
function hammingWeight(n) {
  let count = 0;
  while (n !== 0) {
    n &= n - 1; // 가장 낮은 1 하나를 끈다
    count++;    // 끈 만큼 센다
  }
  return count;
}

console.log(hammingWeight(90), hammingWeight(1), hammingWeight(2147483647), hammingWeight(-3));
```

```text
4 1 31 31
```

90에서는 네 번만 돈다. 아래 그림에서 다음을 누르면 오른쪽에 있는 1부터 하나씩 꺼진다.

반복 횟수는 켜진 비트 수 k다. 시간은 O(k), 공간은 O(1)이다. 1이 적은 수일수록 빠르고, 최악(-1처럼 32개가 다 켜진 수)에서도 시프트 풀이와 같은 32번이다.

음수도 그대로 된다. -3은 32비트로 `11111111111111111111111111111101`이고, 1을 빼고 AND하는 건 부호와 상관없는 비트 계산이다. 31번 지우면 0이 된다. 시프트를 쓰지 않으니 `>>`와 `>>>`를 헷갈릴 일도 없다. 그래서 면접에서 이 문제의 기본 답으로 이 풀이를 낸다.

### Python과 Java

```python
class Solution:
    def hammingWeight(self, n: int) -> int:
        count = 0
        while n:
            n &= n - 1   # 가장 낮은 1 하나를 끈다
            count += 1
        return count

s = Solution()
print(s.hammingWeight(90), s.hammingWeight(1), s.hammingWeight(2147483647))
print((90).bit_count(), bin(90), bin(90).count("1"))
print(bin(-3), (-3).bit_count(), (-3 & 0xFFFFFFFF).bit_count())
```

```text
4 1 31
4 0b1011010 4
-0b11 2 31
```

Python은 정수 크기에 제한이 없어서 음수를 "32비트 2의 보수"로 보지 않는다. 음수에 Kernighan 반복을 그대로 쓰면 `n`이 0에 닿지 않아 끝나지 않는다. -3 & -4 = -4, -4 & -5 = -8처럼 계속 더 작은 음수가 된다. 32비트로 보고 싶으면 `n & 0xFFFFFFFF`로 먼저 잘라 양수로 만든다. 위 출력의 마지막 줄이 그 차이다. `bin(-3)`은 `-0b11`이고 `bit_count()`도 절댓값의 1을 세서 2가 나온다. 자르고 나면 31이다.

Python 3.10부터는 `int.bit_count()`가 있다. 실제 코딩 테스트에서는 이것 하나면 된다. 그 전 버전이면 `bin(n).count("1")`을 쓴다.

```java
class Solution {
    public int hammingWeight(int n) {
        int count = 0;
        while (n != 0) {      // n > 0으로 쓰면 음수 입력에서 바로 0을 돌려준다
            n &= n - 1;       // 가장 낮은 1 하나를 끈다
            count++;
        }
        return count;
    }

    public static void main(String[] args) {
        Solution s = new Solution();
        System.out.println(s.hammingWeight(90) + " " + s.hammingWeight(1) + " " + s.hammingWeight(2147483647) + " " + s.hammingWeight(-3));
        System.out.println(Integer.bitCount(90) + " " + Integer.bitCount(-3) + " " + Integer.toBinaryString(-3));
    }
}
```

```text
4 1 31 31
4 31 11111111111111111111111111111101
```

Java의 `int`는 32비트 2의 보수라서 Kernighan 반복이 음수에서도 31번 만에 0이 된다. 조건만 `n != 0`으로 쓰면 된다. `n > 0`으로 쓰면 음수 입력이 반복에 들어가지도 못하고 0을 돌려준다. 예전 버전 문제에서 맨 위 비트가 켜진 입력에 오답이 나던 흔한 원인이다.

Java에는 `Integer.bitCount`와 `Long.bitCount`가 있다. JIT 컴파일러는 CPU가 지원하면 이 호출을 `POPCNT` 같은 하드웨어 명령 하나로 바꾼다. `Integer.toBinaryString(-3)`은 32자리 2의 보수 문자열을 주니 JavaScript의 `toString(2)`와 다르다는 점도 기억해 둔다.

### -3에는 왜 1이 31개나 있나

음수 입력의 답이 낯설어 보이면 2의 보수를 한 번 떠올리면 된다. 컴퓨터는 -x를 "x의 비트를 모두 뒤집고 1을 더한 값"으로 저장한다. 3과 -3을 32칸으로 나란히 찍어 보면 이렇다.

```text
3   00000000000000000000000000000011
~3  11111111111111111111111111111100   모두 뒤집으면 -4
-3  11111111111111111111111111111101   거기에 1을 더한 값
```

3의 1 두 개를 뒤집으면 1이 30개인 `~3`이 되고, 1을 더하면 맨 아래가 켜져 31개가 된다. 그래서 작은 음수일수록 1이 많다. -1은 32개가 다 켜진 수다. 음수를 왜 이렇게 저장하는지(덧셈기 하나로 뺄셈까지 하려고)는 [논리 게이트와 ALU](/posts/logic-gates-alu)에서 다룬다.

### 내장 함수는 얼마나 빠른가

언어가 주는 함수와 손으로 짠 Kernighan을 같은 무작위 31비트 수로 비교했다. Java는 200만 개를 세 번 돌린 뒤 마지막 회차를 쟀고, Python은 20만 개를 다섯 번 돌려 가장 빠른 시간을 골랐다.

```text
Java     kernighan   29.48ms
Java     bitCount     1.38ms
Python   kernighan  234.97ms
Python   bin.count   50.43ms
Python   bit_count    5.28ms
```

Java의 `Integer.bitCount`는 Kernighan보다 20배쯤 빠르다. JIT가 이 호출을 CPU 명령 하나로 바꾸기 때문이다. Python 차이는 더 크다. 반복문은 칸마다 바이트코드를 실행하지만 `bit_count`는 C 함수 한 번이다. `bin(n).count("1")`도 문자열을 만들긴 하지만 반복이 C 안에서 돌아서 파이썬 반복문보다 빠르다. 면접에서는 Kernighan을 직접 짜서 원리를 보여 주고, "실제 코드라면 내장 함수를 쓴다"고 덧붙이는 게 좋다.

## 여러 번 불린다면 표를 만든다

문제의 후속 질문이 이것이다. 같은 함수를 수백만 번 부른다면 미리 계산해 둔 것을 쓴다. 32비트 전체를 표로 만들 수는 없으니(40억 칸) 8비트 단위로 끊는다. 0부터 255까지 각 수의 1 개수를 표에 적어 두면, 32비트 수 하나는 네 바이트를 표에서 찾아 더하면 된다.

표는 이렇게 채운다. `i`의 1 개수는 `i >> 1`(맨 아래 비트를 뺀 수)의 1 개수에 맨 아래 비트를 더한 값이다. `i >> 1`은 `i`보다 작으니 이미 채워져 있다. 이 점화식이 [Counting Bits](/posts/leetcode-counting-bits)의 풀이 그 자체다.

```js
const TABLE = new Uint8Array(256);
for (let i = 1; i < 256; i++) TABLE[i] = TABLE[i >> 1] + (i & 1); // 앞에서 구한 값에 맨 아래 비트를 더한다

function hammingWeight(n) {
  return TABLE[n & 0xff]           // 맨 아래 바이트
       + TABLE[(n >>> 8) & 0xff]   // 둘째 바이트
       + TABLE[(n >>> 16) & 0xff]  // 셋째 바이트
       + TABLE[n >>> 24];          // 맨 위 바이트 (>>>라서 음수도 0..255)
}

console.log(TABLE.slice(0, 16).join(","));
console.log(hammingWeight(90), hammingWeight(2147483647), hammingWeight(-1));
```

```text
0,1,1,2,1,2,2,3,1,2,2,3,2,3,3,4
4 31 32
```

출력 첫 줄은 0부터 15까지의 1 개수다. 8은 `1000`이라 1, 15는 `1111`이라 4다. 짝수 2k는 k를 한 칸 민 것이라 개수가 같고(6과 3이 둘 다 2), 홀수 2k + 1은 거기에 1이 하나 더 붙는다(7은 3). 점화식이 표 안에서 그대로 보인다.

표는 256바이트이고 한 번만 만든다. 그 뒤 호출마다 표 조회 네 번과 시프트·AND 몇 번이면 끝난다. 반복도 분기도 없다. 표를 16비트로 키우면 조회가 두 번으로 줄지만 표가 64KB가 되어 CPU 캐시에 덜 맞는다. 8비트 표가 보통 적당하다.

## 표 없이 한꺼번에 세는 SWAR

표도 없이 상수 번 연산으로 끝내는 방법이 있다. 32비트를 작은 칸으로 나눠, 칸마다 1의 개수를 동시에 더한다. 레지스터 하나 안에서 여러 칸을 병렬로 계산한다고 해서 SWAR(SIMD Within A Register)라고 부른다.

```js
function hammingWeight(x) {
  x = x - ((x >>> 1) & 0x55555555);                // 2비트 칸마다 1의 개수 (0~2)
  x = (x & 0x33333333) + ((x >>> 2) & 0x33333333); // 4비트 칸마다 (0~4)
  x = (x + (x >>> 4)) & 0x0f0f0f0f;                // 8비트 칸마다 (0~8)
  return Math.imul(x, 0x01010101) >>> 24;          // 네 바이트를 맨 위 바이트에 모은다
}

console.log(hammingWeight(90), hammingWeight(2147483647), hammingWeight(-1));
```

```text
4 31 32
```

90의 아래 8비트로 각 단계를 찍어 보면 칸이 커지며 개수가 모이는 게 보인다.

```text
원래        01 01 10 10      두 칸씩 끊어 본다
2비트 칸    01 01 01 01      각 칸에 1이 하나씩: 1, 1, 1, 1
4비트 칸    0010 0010        네 칸씩: 2, 2
8비트 칸    00000100         여덟 칸: 4
```

첫 줄이 가장 헷갈린다. 2비트 칸 `ab`의 값은 2a + b이고, 1의 개수는 a + b다. 칸 값에서 a(한 칸 민 값의 아래 비트)를 빼면 2a + b - a = a + b가 된다. `0x55555555`(`0101...`)는 각 칸의 아래 비트만 남겨 옆 칸에서 넘어온 비트를 지운다. 둘째 줄부터는 이웃한 칸끼리 더하는 게 전부다. 마지막 줄은 `0x01010101`을 곱해 네 바이트의 합을 맨 위 바이트에 모으고 `>>> 24`로 꺼낸다. 곱셈 결과가 2^53을 넘어 정밀도를 잃지 않도록 32비트 곱셈인 `Math.imul`을 쓴다. 이 부분은 [비트 연산 글](/posts/bit-manipulation#가장-낮은-1-비트를-다루는-두-가지-요령)에서 같은 코드로 한 번 봤다.

연산은 항상 12번 남짓이고 반복도 분기도 없다. 시간 O(1), 공간 O(1)이다. 대신 처음 보는 사람이 읽기 어렵다. 실무에서는 언어가 내장 함수를 주면 그것을 쓰고, 없을 때 이 코드를 주석과 함께 쓴다.

## 틀리기 쉬운 곳

### 부호 있는 시프트로 무한 루프

```js
function bad(n) {
  let c = 0, steps = 0;
  while (n !== 0 && steps < 40) { // 무한 루프를 끊으려고 40번에서 멈춘다
    c += n & 1;
    n >>= 1; // 부호 비트를 복사하며 민다
    steps++;
  }
  return [n, c, steps];
}
console.log(bad(-3));
```

```text
[ -1, 39, 40 ]
```

`>>`는 왼쪽 빈칸을 부호 비트로 채운다. -3에서 출발하면 몇 번 밀고 나서 모든 비트가 1인 -1이 되고, -1을 밀어도 -1이다. `n !== 0`이 영원히 참이라 반복이 끝나지 않는다. 40번에서 강제로 끊었더니 개수가 39로 불어나 있었다. Java의 `>>`도 똑같다. 부호 없이 밀려면 JavaScript와 Java 모두 `>>>`를 쓴다. 그래서 시프트로 풀 때는 처음부터 `>>>`를 쓰거나, 아예 시프트가 없는 Kernighan을 쓴다.

### 조건을 `> 0`으로 쓰기

앞에서 본 것처럼 반복 조건을 `n > 0`으로 쓰면 음수는 반복에 들어가지 못하고, 마스크 비교를 `> 0`으로 쓰면 31번 자리를 놓친다. 비트 연산 결과는 "0인가 아닌가"로만 본다.

### Python에서 음수를 그대로 넣기

Python의 음수는 왼쪽으로 1이 끝없이 이어진 것처럼 동작한다. `while n:` 반복에 음수를 넣으면 `n &= n - 1`이 계속 더 작은 음수를 만들 뿐 0에 닿지 않는다. 32비트로 정해진 문제라면 `n &= 0xFFFFFFFF`를 먼저 한다.

### 표 조회에서 맨 위 바이트를 `>>`로 꺼내기

```js
const bad = (n) => TABLE[n & 0xff] + TABLE[(n >> 8) & 0xff] + TABLE[(n >> 16) & 0xff] + TABLE[n >> 24];
console.log(-1 >> 24, TABLE[-1 >> 24], bad(-1));
```

```text
-1 undefined NaN
```

아래 세 바이트는 `& 0xff`로 잘라서 괜찮지만, 맨 위 바이트를 `>> 24`로만 꺼내면 음수에서 부호가 따라와 -1이 된다. 타입 배열에 음수 인덱스를 넣으면 `undefined`이고, 더하면 `NaN`이다. 에러 없이 조용히 틀린다. `>>> 24`로 꺼내거나 `(n >> 24) & 0xff`처럼 마지막에도 마스크를 씌운다.

### 32비트를 넘는 수를 JavaScript 비트 연산에 넣기

JavaScript 비트 연산은 피연산자를 32비트로 자른다. `2 ** 32 + 5`를 넣으면 위쪽 비트가 사라져 5의 1 개수 2가 나온다. 64비트 값이 필요하면 BigInt로 같은 Kernighan 반복을 돌린다(`n &= n - 1n`). 자르는 규칙은 [비트 연산 글](/posts/bit-manipulation#자바스크립트는-비트-연산-앞에서-32비트로-자른다)에 있다.

## 면접관이 이어서 묻는 것

### 64비트 정수라면

Java는 `long`에 같은 Kernighan 반복을 쓰거나 `Long.bitCount`를 부른다. SWAR는 마스크를 64비트로 늘리고(`0x5555555555555555L` 등) 마지막 곱셈을 `0x0101010101010101L`, 시프트를 56으로 바꾼다. JavaScript는 BigInt로 반복을 돌린다. BigInt는 느리니 성능이 중요하면 64비트를 위아래 32비트 두 개로 나눠 각각 세어 더한다.

JavaScript로 64비트를 세는 코드는 이렇다. `BigInt.asUintN(64, n)`이 음수를 64비트 2의 보수로 바꿔 주니, 반복이 끝나지 않는 Python의 음수 문제를 여기서는 피한다.

```js
function popcount64(n) {           // n은 BigInt
  n = BigInt.asUintN(64, n);       // 음수를 64비트 2의 보수로 본다
  let c = 0;
  while (n !== 0n) { n &= n - 1n; c++; }
  return c;
}
console.log(popcount64(2n ** 40n + 5n), popcount64(-1n), popcount64(175928847299117063n));
```

```text
3 64 18
```

### 1의 개수가 아니라 비트 길이를 묻는다면

"이 수를 이진수로 쓰면 몇 자리인가"는 다른 질문이다. 가장 높은 1의 위치를 찾으면 된다. JavaScript에는 맨 위부터 0이 몇 개인지 세는 `Math.clz32`가 있어서 `32 - Math.clz32(n)`이 비트 길이다. 90은 7, 2^31 - 1은 31이고, 맨 위 비트가 켜진 음수는 32다. Java는 `32 - Integer.numberOfLeadingZeros(n)`, Python은 `n.bit_length()`다. 1의 개수와 헷갈려 `bit_length`를 쓰는 실수가 실제로 나오니 이름을 정확히 기억해 둔다.

### 두 수의 비트가 몇 자리 다른가

LeetCode 461. Hamming Distance다. 두 수를 XOR하면 다른 자리만 1이 되니, 그 결과의 1 개수가 답이다. `hammingWeight(x ^ y)` 한 줄이다. 배열 전체에서 모든 쌍의 해밍 거리 합을 구하는 477. Total Hamming Distance는 쌍마다 세면 O(n²)라서, 자리마다 1인 수 c개와 0인 수 n - c개를 세어 c × (n - c)를 더하는 식으로 O(32n)에 푼다.

```js
const hammingDistance = (x, y) => {
  let n = x ^ y, c = 0;      // 다른 자리만 1
  while (n !== 0) { n &= n - 1; c++; }
  return c;
};
console.log(hammingDistance(1, 4), hammingDistance(90, 91));
```

```text
2 1
```

### 0부터 n까지 전부 세라면

[Counting Bits](/posts/leetcode-counting-bits)다. 수마다 이 문제를 풀면 O(n log n)이지만, 앞의 표를 채운 점화식 `bits[i] = bits[i >> 1] + (i & 1)`을 쓰면 O(n)에 끝난다.

### 2의 거듭제곱인가

1이 정확히 하나인 수다. 1을 다 세지 않아도 `n > 0 && (n & (n - 1)) === 0`이면 된다. Kernighan 한 번 만에 0이 되는지 보는 셈이다. [Power of Two](/posts/leetcode-power-of-two)에서 자세히 다룬다.

### 이 연산이 실제로 쓰이는 곳

비트맵에 사용자 집합을 담아 두면 "두 조건을 모두 만족하는 사용자 수"가 AND 뒤의 팝카운트다. Redis에서는 `BITOP AND`로 두 비트맵을 합친 뒤 `BITCOUNT`로 센다. 체스 엔진은 말의 위치를 64비트 비트보드로 들고 다니며 남은 말 수를 팝카운트로 센다. 해시 두 개가 얼마나 비슷한지를 해밍 거리로 재는 유사 이미지 검색도 같은 연산을 쓴다. 이런 곳에서는 한 번에 수억 번 부르니 앞의 측정처럼 풀이에 따라 수십 배 차이가 난다.

같은 패턴의 다른 문제로 [Single Number](/posts/leetcode-single-number), [Reverse Bits](/posts/leetcode-reverse-bits), [Sum of Two Integers](/posts/leetcode-sum-of-two-integers)가 있다.

정리하면, 1을 세는 방법은 "모든 칸을 본다", "켜진 칸만 본다", "칸을 묶어 한꺼번에 센다" 세 단계로 빨라진다. 면접에서는 Kernighan을 기본으로 내고, 음수에서 `>>`가 왜 위험한지와 여러 번 불릴 때 표나 내장 함수로 바꾼다는 이야기까지 하면 된다.

## 면접에서 나올 만한 질문

### `n & (n - 1)`은 왜 가장 낮은 1을 끄나요?

1을 빼면 가장 낮은 1이 0이 되고 그 아래 0들이 모두 1로 바뀐다. 그보다 위쪽 비트는 그대로다. 원래 수와 AND하면 바뀐 부분은 원래와 반대라서 모두 0이 되고, 위쪽은 같아서 그대로 남는다. 결과적으로 가장 낮은 1 하나만 꺼진다.

### Kernighan 풀이와 시프트 풀이의 차이는 무엇인가요?

시프트 풀이는 가장 높은 1까지 모든 칸을 들러서 최대 32번 돈다. Kernighan은 켜진 비트 수만큼만 돈다. 1이 적은 수에서 차이가 크고, 1이 32개 다 켜진 최악에서는 같다. 시프트가 없어서 음수에서 `>>` 때문에 무한 루프가 날 위험도 없다.

### Kernighan 풀이의 시간 복잡도를 O(1)이라고 해도 되나요?

입력이 32비트로 정해져 있으니 최대 32번이라 형식상 O(1)이 맞다. 하지만 그렇게만 말하면 시프트 풀이와 차이가 안 보인다. 켜진 비트 수 k에 비례하는 O(k)라고 말하고, 시프트 풀이는 비트 폭 w에 비례하는 O(w), SWAR와 표는 입력과 상관없는 상수 번이라고 나눠 설명하는 편이 정확하다.

### 음수가 들어오면 어떻게 되나요?

32비트 2의 보수로 보고 센다. -3이면 31이다. JavaScript와 Java는 시프트를 `>>>`로 쓰거나 Kernighan을 쓰면 되고, 반복 조건은 `n !== 0`이어야 한다. Python은 정수에 폭이 없어서 `n & 0xFFFFFFFF`로 먼저 잘라야 반복이 끝난다.

### 이 함수가 아주 여러 번 불린다면 어떻게 최적화하나요?

먼저 언어의 내장 함수를 쓴다. Java의 `Integer.bitCount`는 JIT가 CPU의 팝카운트 명령으로 바꿔 준다. 내장 함수가 없으면 0~255의 1 개수를 담은 256바이트 표를 한 번 만들어 바이트 네 개를 조회해 더하거나, SWAR로 반복 없이 상수 번 연산에 끝낸다. 측정에서 표와 SWAR가 Kernighan보다 4~7배 빨랐다.

### 두 정수의 해밍 거리는 어떻게 구하나요?

두 수를 XOR하면 서로 다른 자리만 1이 된다. 그 결과의 1 개수가 해밍 거리다. 배열의 모든 쌍에 대한 합이라면 자리마다 1인 수와 0인 수를 세어 곱해 더하면 O(32n)이다.
