팀 저장소 다섯 개에 같은 `review-checklist` 스킬과 `log-digger` 서브에이전트, 편집 뒤 포맷 훅이 복사돼 있다. 누군가 체크리스트에 "하드코딩된 URL 찾기"를 추가했는데 두 저장소에만 들어갔다. 새로 온 사람은 어느 저장소 것이 최신인지 모른다. 개인 컴퓨터의 `~/.claude/skills/`에 둔 것까지 치면 판이 더 많다.

이걸 하나로 묶는 단위가 플러그인이다. 스킬, 서브에이전트, 훅, MCP 서버를 한 폴더에 넣고 버전을 붙여 마켓플레이스에서 설치하고 업데이트한다. 이 글은 실험용 플러그인과 마켓플레이스를 직접 만들어 설치·업데이트해 보고, 플러그인 형태로 들어오는 다른 확장 세 가지를 함께 본다. 언어 서버로 코드를 찾는 코드 인텔리전스, Claude의 말투와 응답 틀을 바꾸는 출력 스타일, 화면 아래 한 줄을 내 것으로 바꾸는 상태 줄, 그리고 메신저나 웹훅에서 열린 세션으로 메시지를 밀어 넣는 채널이다.

스킬, 서브에이전트, 훅 하나하나를 만드는 법은 [Claude Code 확장 글](/posts/claude-code-extensions)과 [훅 깊이 보기](/posts/claude-code-hooks-deep-dive)에 있다. 여기서는 그것들을 묶고 나눠 주는 쪽을 본다. 기준은 Claude Code 2.1.310(Ubuntu 24.04)과 2026년 10월의 [플러그인 문서](https://code.claude.com/docs/en/plugins)다. 채널은 아직 연구 미리보기(research preview)라 플래그와 규약이 바뀔 수 있다고 문서가 적는다.

## 플러그인 한 개를 뜯어보면

플러그인은 구성 요소를 담은 폴더와, 그 이름을 정하는 매니페스트 `.claude-plugin/plugin.json`이다. 실험용으로 `team-kit`을 만들었다.

```text
team-kit/
├── .claude-plugin/
│   └── plugin.json          # 이름, 버전, 설명
├── skills/
│   └── review-checklist/
│       └── SKILL.md          # /team-kit:review-checklist
├── agents/
│   └── log-digger.md         # team-kit:log-digger 서브에이전트
└── hooks/
    ├── hooks.json            # 편집 뒤 PostToolUse 훅
    └── format.sh
```

```json
{
  "name": "team-kit",
  "version": "1.0.0",
  "description": "팀 공용 리뷰 체크리스트, 로그 요약 에이전트, 편집 후 포맷 훅"
}
```

훅은 `settings.json`이 아니라 플러그인 안의 `hooks/hooks.json`에 같은 모양으로 쓴다. 스크립트 경로는 플러그인이 설치된 위치를 가리키는 `${CLAUDE_PLUGIN_ROOT}`로 적는다. 설치하면 플러그인 폴더가 캐시로 복사되거나 다른 곳에서 읽히기 때문에, 상대 경로나 내 컴퓨터의 절대 경로를 쓰면 다른 사람 컴퓨터에서 깨진다.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "\"${CLAUDE_PLUGIN_ROOT}\"/hooks/format.sh" }
        ]
      }
    ]
  }
}
```

플러그인을 켜면 각 파일이 세션의 어디에 붙는지가 정해진다. 그림으로 보면 이렇다.

이름 앞붙이가 중요하다. 플러그인의 스킬은 `/review-checklist`가 아니라 `/team-kit:review-checklist`로 불린다. 다른 플러그인이나 내 개인 스킬과 이름이 겹쳐도 충돌하지 않게 하려는 장치다. 서브에이전트도 `team-kit:log-digger`가 된다. 그리고 문서가 짚는 보안상 예외가 있다. 플러그인이 주는 서브에이전트는 앞머리의 `hooks`, `mcpServers`, `permissionMode` 필드를 무시한다. 플러그인 하나가 서브에이전트를 핑계로 권한 모드를 바꾸지 못하게 막은 것이다. 훅과 MCP 서버가 필요하면 플러그인 수준의 `hooks/hooks.json`과 `.mcp.json`에 둔다.

## 마켓플레이스에서 설치하고 업데이트하기

마켓플레이스는 가게가 아니라 목록이다. `.claude-plugin/marketplace.json`에 플러그인 이름과 가져올 위치를 적은 저장소나 폴더면 된다. 팀 저장소 하나에 두고 각자 등록하면 된다.

```json
{
  "name": "team-market",
  "description": "우리 팀 플러그인",
  "owner": { "name": "Platform Team" },
  "plugins": [
    { "name": "team-kit", "source": "./plugins/team-kit", "description": "리뷰 체크리스트와 로그 요약" }
  ]
}
```

`source`는 `.claude-plugin/`이 아니라 마켓플레이스 루트(그 폴더를 담은 곳)에서 시작하는 경로다. 먼저 검사한다.

```bash
# 플러그인과 마켓플레이스 형식을 검사한다
claude plugin validate ./team-market
```

```text
‼ Found 1 warning:

  > plugins[0] plugin.json → author: No author information provided. Consider adding author details for plugin attribution

√ Validation passed with warnings
```

플러그인 폴더만 따로 검사하면 Anthropic 디렉터리에 낼 때의 기준도 함께 본다. README와 LICENSE가 없다고 "디렉터리가 받지 않는 문제 2개"를 알려 줬다. 팀 안에서만 쓰는 마켓플레이스라면 막지는 않지만, README는 남이 플러그인을 고를 때 처음 읽는 글이라 쓰는 편이 낫다.

등록하고 설치한다. 실험은 내 설정을 건드리지 않게 `CLAUDE_CONFIG_DIR`로 빈 설정 폴더를 가리킨 채 돌렸다.

```bash
# 마켓플레이스를 등록하고, 플러그인이름@마켓플레이스이름으로 설치한다
claude plugin marketplace add ./team-market
claude plugin install team-kit@team-market
claude plugin details team-kit
```

```text
Adding marketplace…√ Successfully added marketplace: team-market (declared in user settings)
Installing plugin "team-kit@team-market"...√ Successfully installed plugin: team-kit@team-market (scope: user)

team-kit 1.0.0
  Description: 리뷰 체크리스트와 로그 요약
  Source: team-kit@team-market

Component inventory
  Skills (1)  review-checklist
  Agents (1)  log-digger
  Hooks (1)  PostToolUse  (harness-only — no model context cost)
  MCP servers (0)
  LSP servers (0)

Projected token cost
  Always-on:   ~119 tok   added to every session

Per-component (rounded)
  component         always-on  on-invoke
  review-checklist        ~80       ~110
  log-digger              ~40        ~70
```

`details`의 아래쪽이 이 글에서 가장 쓸모 있는 출력이다. 스킬과 서브에이전트는 이름과 설명이 매 세션 컨텍스트에 실려 "always-on" 비용이 생기고, 불릴 때 본문만큼 더 든다. 훅은 Claude Code가 실행만 하고 모델에 아무것도 싣지 않으니 컨텍스트 비용이 0이다. 이 플러그인은 작아서 119토큰이지만, 스킬 서른 개짜리 플러그인이나 도구가 많은 MCP 서버를 묶은 플러그인은 숫자가 다르다. 설치하기 전에는 `/plugin`의 Marketplaces 탭에서 공식 마켓플레이스 플러그인의 Context cost 추정을 볼 수 있다.

설치 범위(scope)는 셋이다. user는 이 컴퓨터의 모든 프로젝트, project는 커밋되는 `.claude/settings.json`에 적혀 저장소의 모든 사람, local은 이 저장소의 나만이다. project 범위로 켜도 각자 자기 컴퓨터에 설치는 해야 한다. 설정에는 이렇게 남는다.

```json
{
  "extraKnownMarketplaces": {
    "team-market": {
      "source": { "source": "directory", "path": "/…/team-market" }
    }
  },
  "enabledPlugins": {
    "team-kit@team-market": true
  }
}
```

업데이트는 마켓플레이스 목록을 새로 받은 뒤 플러그인을 올린다. 버전을 1.1.0으로 올리고 돌렸다.

```bash
# 목록을 새로 받고, 플러그인을 새 버전으로 올린다
claude plugin marketplace update team-market
claude plugin update team-kit@team-market
```

```text
Updating marketplace: team-market...Validating local marketplace
√ Successfully updated marketplace: team-market
Checking for updates for plugin "team-kit@team-market"…
√ Plugin "team-kit" updated from 1.0.0 to 1.1.0 for scope user. Restart to apply changes.
```

마지막 줄의 "Restart to apply changes"를 놓치기 쉽다. 업데이트는 다음 세션부터 적용된다. 대화형 세션에서는 `/reload-plugins`로 다시 읽을 수 있다. 개발하는 동안에는 마켓플레이스 없이 `claude --plugin-dir ./team-kit`으로 폴더를 바로 실어 시험한다. 그렇게 띄운 세션에서 `/context`를 보니 서브에이전트가 `team-kit:log-digger | Plugin | 54`, 스킬이 `team-kit:review-checklist | Plugin (team-kit) | ~30`으로 잡혔다. 파일을 하나 쓰게 하자 훅이 돌아 플러그인 데이터 폴더(`${CLAUDE_PLUGIN_DATA}`, 이 실행에서는 `~/.claude/plugins/data/team-kit-inline/`)의 로그에 `formatted: …/hello.txt`가 남았다. 플러그인이 상태를 남길 곳은 플러그인 폴더가 아니라 이 데이터 폴더다. 업데이트하면 플러그인 폴더는 새로 바뀌기 때문이다.

## 코드 인텔리전스: grep 대신 언어 서버로 찾기

큰 TypeScript 저장소에서 "`createSession`을 쓰는 곳을 모두 고쳐 줘"라고 하면 Claude는 보통 grep으로 그 글자를 찾는다. 같은 이름의 다른 함수, 주석, 문자열까지 걸리고, 후보 파일을 하나씩 열어 진짜인지 확인한다. 파일을 읽을 때마다 컨텍스트가 찬다.

코드 인텔리전스 플러그인은 에디터가 쓰는 언어 서버(LSP)를 Claude Code에 붙인다. 플러그인은 "어느 확장자를 어떤 명령으로 띄운 서버가 맡는지"만 적고, 서버 바이너리는 따로 설치한다. TypeScript는 `typescript-lsp` 플러그인과 `typescript-language-server`, Python은 `pyright-lsp`와 `pyright-langserver`, Go는 `gopls-lsp`와 `gopls` 식이다.

```bash
# 1. 언어 서버 바이너리를 설치하고 PATH에 있는지 확인한다
npm install -g typescript-language-server typescript
which typescript-language-server
# 2. Claude Code 안에서 공식 마켓플레이스의 플러그인을 설치한다
#    /plugin install typescript-lsp@claude-plugins-official
```

붙이면 두 가지가 생긴다. 하나는 편집 뒤 진단이다. Claude가 파일을 고칠 때마다 서버가 찾은 타입 오류, 빠진 import가 바로 돌아오고, 대화에 `Found N new diagnostic issues in M files` 줄이 뜬다. 컴파일을 돌리지 않아도 방금 낸 실수를 안다. 다른 하나는 읽기 전용 `LSP` 도구다. 정의로 가기, 참조 찾기를 글자가 아니라 기호(symbol)로 한다. 아래 그림은 같은 질문을 두 방식이 처리하는 길이다.

/>

그림의 숫자(23곳, 9개)는 흐름을 보여 주려고 넣은 예시다. 실제 차이는 저장소에 따라 다르다. 문서는 "정의로 가기" 한 번이 grep 한 번과 후보 파일 여러 개 읽기를 대신해서 불필요한 파일 읽기를 줄인다고 적는다. 타입이 있는 언어, 같은 이름이 흔한 큰 저장소일수록 이득이 크다. 작은 스크립트 저장소라면 grep으로 충분하다.

알아 둘 제약도 있다. 언어 서버는 Claude가 그 확장자의 파일을 처음 편집할 때 뜨고, 메모리를 쓴다. 클라우드 세션에서는 플러그인 언어 서버를 띄우지 않는다. 진단 줄이 안 뜨면 `/plugin`의 Errors 탭에서 `Executable not found in $PATH` 같은 줄을 찾는다. 바이너리를 설치했는데 `claude`를 띄운 셸의 PATH에 없으면 생기는 일이다. 언어 서버 바이너리가 이미 PATH에 있고 플러그인이 없으면 Claude Code가 세션당 한 번 "LSP plugin recommendation" 창으로 설치를 권한다.

## 출력 스타일: 말투와 응답의 틀을 바꾸기

"설명은 짧게, 결과부터"를 매 프롬프트에 붙이고 있다면 출력 스타일이 맞다. 출력 스타일은 세션 내내 Claude의 역할, 말투, 응답 형식을 정하는 지시문이다. 기본(Default) 말고 네 가지가 들어 있다.

- Proactive: 일상적인 결정은 묻지 않고 합리적으로 가정해 바로 일을 시작한다. 권한 모드는 바꾸지 않는다.
- Concise: 첫 문장에 결과를 쓰고 서두와 과정 설명, 끝 요약을 뺀다. 오류 보고, 실패한 테스트 출력, 보안 경고는 그대로 다 쓴다(2.1.237 이상).
- Explanatory: 작업은 그대로 하고 왜 그렇게 했는지 짧은 `Insight` 블록을 붙인다. 낯선 코드베이스를 익힐 때 좋다.
- Learning: Explanatory에 더해, 설계 판단이 필요한 작은 조각은 `TODO(human)`으로 남기고 내가 쓰게 한다.

`/output-style concise`로 바꾸고, 고른 값은 `.claude/settings.local.json`의 `outputStyle`에 저장된다. 설정 파일에 직접 쓸 때는 대소문자를 맞춘다. `"explanatory"`라고 쓰면 맞는 스타일이 없어 조용히 Default가 된다. 명령은 대소문자를 무시하지만 설정 값은 구분한다.

직접 만들 수도 있다. `~/.claude/output-styles/`나 `.claude/output-styles/`에 마크다운 파일을 둔다.

```markdown
---
name: Review notes
description: 변경마다 리뷰어가 볼 위험과 확인 방법을 붙인다
keep-coding-instructions: true
---

코드를 바꾼 응답 끝에는 "리뷰어에게" 절을 붙인다.
이 변경이 깨뜨릴 수 있는 것, 그것을 확인하는 명령이나 테스트를 두세 줄로 적는다.
위험이 없으면 "없음" 한 줄만 쓴다.
```

`keep-coding-instructions: true`가 핵심 필드다. 출력 스타일은 Claude Code의 기본 시스템 프롬프트 중 소프트웨어 엔지니어링 지시 부분을 바꿔 끼운다. 이 필드를 빼면 그 지시가 빠져서, 코딩과 상관없는 비서나 글쓰기 도우미를 만들 때 쓴다. 코딩은 그대로 하고 말하는 방식만 바꾸려면 `true`로 둔다. 스타일 파일은 시작할 때 읽으니 세션 중에 고치면 재시작해야 반영된다. 반면 세션 중에 스타일을 바꾸는 것은 대화 메시지로 새 지시를 덧붙이는 방식이라 프롬프트 캐시를 깨지 않는다(2.1.251 이상).

출력 스타일과 CLAUDE.md는 하는 일이 다르다. CLAUDE.md는 프로젝트에서 알아야 할 사실(빌드 명령, 폴더 구조)이고, 출력 스타일은 나와 일하는 방식(말투, 응답 틀)이다. 그리고 둘 다 지시일 뿐이라, 매번 꼭 일어나야 하는 일(편집 뒤 포맷, 명령 차단)은 훅에 둔다. 플러그인도 `output-styles/` 폴더로 스타일을 줄 수 있고, `force-for-plugin: true`면 플러그인을 켜는 것만으로 사용자 설정을 덮고 적용된다. 남의 플러그인이 이걸 켜 두면 내 말투가 바뀐 이유를 한참 찾게 된다.

## 상태 줄을 내 계기판으로

화면 아래 한 줄(상태 줄)은 내가 짠 스크립트의 출력으로 바꿀 수 있다. Claude Code가 세션 정보를 JSON으로 stdin에 넣고, 스크립트가 찍은 글을 보여 준다. 로컬에서만 돌고 API 토큰을 쓰지 않는다. [비용 글](/posts/claude-code-models-and-cost)에서 본 숫자들(모델, effort, 컨텍스트 사용률, 추정 비용, 5시간 창 사용률)을 늘 보이게 하는 데 쓴다.

```bash
#!/usr/bin/env bash
# ~/.claude/statusline.sh
# 모델·effort, 컨텍스트 %, 세션 추정 비용, 5시간 창 사용률을 한 줄로 보여 준다
input=$(cat)
model=$(jq -r '.model.display_name // "?"' <<<"$input")
effort=$(jq -r '.effort.level // "-"' <<<"$input")
ctx=$(jq -r '.context_window.used_percentage // 0 | floor' <<<"$input")
cost=$(jq -r '.cost.total_cost_usd // 0' <<<"$input")
five=$(jq -r '.rate_limits.five_hour.used_percentage // empty' <<<"$input")
warn=""
[ "$ctx" -ge 70 ] && warn=" ⚠"
printf '%s·%s  ctx %s%%%s  $%.2f' "$model" "$effort" "$ctx" "$warn" "$cost"
[ -n "$five" ] && printf '  5h %s%%' "$five"
echo
```

```json
{
  "statusLine": { "type": "command", "command": "~/.claude/statusline.sh" }
}
```

문서의 필드 이름대로 만든 JSON을 넣어 확인했다.

```bash
# 구독 세션처럼 rate_limits가 있는 입력과, API 세션처럼 없는 입력을 넣어 본다
echo '{"model":{"display_name":"Opus"},"effort":{"level":"medium"},"context_window":{"used_percentage":12.4},"cost":{"total_cost_usd":0.4213},"rate_limits":{"five_hour":{"used_percentage":38}}}' | ./statusline.sh
echo '{"model":{"display_name":"Sonnet"},"effort":{"level":"high"},"context_window":{"used_percentage":81.9},"cost":{"total_cost_usd":3.1}}' | ./statusline.sh
echo '{"model":{"display_name":"Haiku"}}' | ./statusline.sh
```

```text
Opus·medium  ctx 12%  $0.42  5h 38%
Sonnet·high  ctx 81% ⚠  $3.10
Haiku·-  ctx 0%  $0.00
```

세 번째 줄처럼 필드가 비어 있는 경우를 꼭 견뎌야 한다. 세션 첫 요청 전에는 `context_window.current_usage`가 `null`이고 압축 직후에도 잠깐 그렇다. `effort`는 effort를 받지 않는 모델에서 빠지고, `rate_limits`는 구독 세션에서만 온다. `// 0`, `// empty` 같은 jq 기본값이 그 처리다.

언제 다시 그리는지도 알아 둔다. 세션 시작, 새 응답 도착, `/compact` 완료, 권한 모드 변경 때 돌고, 300ms 디바운스로 몰아서 한 번 돈다. 이전 실행이 안 끝났는데 새 갱신이 오면 이전 것을 취소한다. 그래서 스크립트 안에서 `git fetch`나 원격 API 호출을 하면 갱신이 계속 취소돼 줄이 비어 보인다. 위 스크립트는 jq를 다섯 번 불러도 한 번에 약 27ms였다(20번 도는 데 0.54초). 느린 정보는 따로 캐시 파일에 써 두고 상태 줄은 그 파일만 읽는다. 시계처럼 시간에 따라 바뀌는 값은 `refreshInterval`(초)로 주기 갱신을 건다. 터미널 폭은 `tput cols`로 못 읽고 `COLUMNS` 환경 변수로 받는다.

같은 로직을 자바스크립트로 옮겨 보면 빈 필드 처리가 손에 익는다.

## 채널: 밖에서 열린 세션으로 메시지 밀어 넣기

밤에 CI가 깨지면 아침에 내가 로그를 복사해 세션에 붙여 넣는다. 그 사이 Claude는 아무것도 모른다. 채널은 이 방향을 뒤집는다. 채널은 열린 Claude Code 세션으로 이벤트를 밀어 넣는 MCP 서버다. 일반 MCP 서버는 Claude가 필요할 때 부르는 도구고, 채널은 밖에서 먼저 말을 건다.

미리보기 단계에서 공식 채널은 Telegram, Discord, iMessage 플러그인이고, 브라우저로 시험하는 fakechat 데모가 있다. 모두 Bun 스크립트라 Bun이 필요하다. 설치한 뒤 `--channels`로 그 세션에 켠다.

```bash
# 공식 마켓플레이스의 텔레그램 채널을 이 세션에 켠다
claude --channels plugin:telegram@claude-plugins-official
```

직접 만든 채널은 아직 허용 목록에 없어서 개발 플래그로 띄운다. 문서의 웹훅 예제는 `claude/channel` 기능을 선언한 MCP 서버가 127.0.0.1:8788로 POST를 받아 `notifications/claude/channel` 알림으로 넘기는 구조다.

```bash
# 개발 중인 채널 서버를 이 세션에만 싣는다. 처음엔 경고 창과 .mcp.json 승인 창이 뜬다
claude --dangerously-load-development-channels server:webhook
# 다른 터미널에서 CI가 보내는 것처럼 POST를 날린다
curl -X POST localhost:8788 -d "build failed on main: https://ci.example.com/run/1234"
```

Claude의 컨텍스트에는 이런 태그로 들어간다고 문서가 보여 준다(이 부분은 대화형 승인 창이 필요해 직접 돌리지 않았다). 터미널에는 `← webhook: build failed on main: …` 한 줄로 표시된다.

```text
<channel source="webhook" path="/" method="POST">
build failed on main: https://ci.example.com/run/1234
</channel>
```

열린 세션으로 들어온다는 점이 비슷한 기능들과의 차이다. 클라우드 세션과 Slack의 Claude는 매번 새 샌드박스에서 시작하고, Remote Control은 내가 폰이나 브라우저로 내 로컬 세션을 직접 조종하는 것이다. 채널은 사람이 아닌 출처(CI, 오류 추적기, 메신저 봇)가 내 로컬 세션을 깨운다. 메신저 채널은 양방향이라 텔레그램으로 물으면 Claude가 내 컴퓨터의 진짜 파일로 일하고 같은 대화방으로 답한다. 다만 터미널에는 Claude의 답 본문이 아니라 도구 호출과 "sent" 확인만 보인다.

보안 장치가 몇 겹 있다. 채널마다 보낸 사람 허용 목록이 있어서, 텔레그램과 디스코드는 봇에 메시지를 보내 받은 페어링 코드를 세션에서 승인해야 목록에 들어간다. 목록 밖의 메시지는 조용히 버려진다. 세션마다 `--channels`로 켜야 하고, Team·Enterprise는 관리자가 `channelsEnabled`를 켜기 전에는 막혀 있다. 채널이 권한 중계(permission relay)를 선언하면 그 채널로 답할 수 있는 사람이 내 세션의 도구 실행을 승인할 수 있다. 허용 목록에 넣는 사람은 내 컴퓨터에서 명령을 승인할 권한을 받는 셈이다. 그리고 채널은 세션이 열려 있을 때만 받는다. 늘 받으려면 세션을 백그라운드 프로세스로 띄워 둬야 한다.

## 확장을 붙일수록 늘어나는 것

플러그인 하나를 켜면 그 플러그인은 쓰지 않는 세션에도 들어온다. 문서가 적는 비용은 셋이다.

첫째는 컨텍스트다. Claude가 스스로 부를 수 있는 스킬, 서브에이전트, 명령은 이름과 설명이 매 턴 실린다. `claude plugin details`의 always-on 숫자가 그것이다. 플러그인 열 개에 스킬이 열 개씩이면 설명만으로 수천 토큰이 질문 전에 깔리고, 그만큼 Claude가 엉뚱한 스킬을 고를 가능성도 커진다. 훅은 컨텍스트를 먹지 않지만 사건마다 실행 시간을 더한다.

둘째는 프로세스다. 플러그인의 MCP 서버와 언어 서버는 켜진 세션마다 옆에서 돈다. 플러그인을 세션 중에 켜고 끄는 것도 비용이 다르다. 스킬, 에이전트, 훅만 있는 플러그인은 캐시를 깨지 않고 끝에 덧붙지만, MCP 서버를 주는 플러그인을 켜고 끄면 도구 목록이 바뀌어 캐시 전체를 다시 쓴다.

셋째는 권한이다. 플러그인이 실행하는 것은 내 권한으로 돈다. 공식(`claude-plugins-official`), 커뮤니티, 서드파티로 등급이 나뉘지만, 문서도 등급과 상관없이 설치한 플러그인은 내 사용자 권한으로 코드를 실행할 수 있다고 적는다. 동료가 만든 팀 마켓플레이스도 서드파티다.

그래서 남의 플러그인을 고를 때는 이 순서로 본다. `hooks/hooks.json`과 거기서 부르는 스크립트를 읽는다(무엇을 언제 실행하나). `.mcp.json`을 읽는다(어떤 프로세스가 뜨고 어디로 연결하나). 스킬 앞머리의 `allowed-tools`를 본다(묻지 않고 실행할 수 있는 도구를 넓히나). 출력 스타일의 `force-for-plugin`을 본다. 버전이 붙어 있고 변경 이력이 있는지, 마지막 업데이트가 언제인지 본다. 설치한 뒤에는 `/plugin`의 Installed 탭에서 "Not used recently" 묶음을 보고 끈다. 지우지 않고 끄기만 하려면 `claude plugin disable`이다.

정리하면 플러그인은 "같은 설정을 여러 곳에 맞춰 두는 문제"를 푸는 포장이고, 코드 인텔리전스·출력 스타일·상태 줄·채널은 그 포장에 담기는 확장들이다. 포장이 편할수록 무엇이 딸려 들어오는지 보기 어려워지니, `details`의 숫자와 `hooks.json` 한 장은 꼭 열어 보고 설치한다.

## 면접에서 나올 만한 질문

### 플러그인은 스킬이나 훅을 그냥 두는 것과 무엇이 다른가?

기능은 같고 묶음과 배포 방식이 다르다. 스킬, 서브에이전트, 훅, MCP 서버를 한 폴더에 담아 이름과 버전을 붙이고, 마켓플레이스에서 이름으로 설치하고 업데이트한다. 여러 저장소와 여러 사람에게 같은 설정을 맞춰 줄 때 쓰고, 혼자 한 프로젝트에서 쓰는 스킬 하나면 플러그인까지 만들 필요가 없다.

### 마켓플레이스는 무엇이고 설치 범위는 어떻게 고르나?

`.claude-plugin/marketplace.json`에 플러그인 이름과 가져올 위치를 적은 목록이고, 호스팅되는 가게가 아니다. 범위는 내 모든 프로젝트의 user, 커밋되는 설정으로 저장소 사람 모두에게 켜는 project, 이 저장소의 나만인 local이 있다. project로 켜도 각자 설치는 해야 하고, 업데이트는 다음 세션부터 적용된다.

### 플러그인 서브에이전트에 hooks나 permissionMode를 넣으면?

무시된다. 플러그인 하나가 서브에이전트를 거쳐 권한 모드를 바꾸거나 MCP 서버를 몰래 띄우지 못하게 막은 보안 장치다. 훅과 MCP 서버가 필요하면 플러그인 수준의 `hooks/hooks.json`과 `.mcp.json`에 두고, 그러면 플러그인이 켜진 동안 늘 적용된다.

### 코드 인텔리전스 플러그인이 grep 탐색보다 나은 점은?

글자가 아니라 기호로 정의와 참조를 찾아서 이름만 같은 다른 함수나 주석이 걸리지 않고, 후보 파일을 하나씩 열어 볼 필요가 줄어 컨텍스트를 덜 쓴다. 편집할 때마다 언어 서버가 타입 오류를 바로 알려 줘 빌드 전에 실수를 잡는다. 대신 언어 서버 바이너리를 따로 설치해야 하고 메모리를 쓰며, 클라우드 세션에서는 돌지 않는다.

### 출력 스타일과 CLAUDE.md, 훅은 어떻게 나눠 쓰나?

CLAUDE.md는 프로젝트에 대한 사실, 출력 스타일은 말투와 응답 틀 같은 일하는 방식, 훅은 매번 반드시 일어나야 하는 동작이다. 출력 스타일도 지시일 뿐이라 강제되지 않는다. 커스텀 스타일에서 `keep-coding-instructions`를 빼면 기본 코딩 지시가 빠지니, 코딩은 그대로 하고 말투만 바꿀 때는 `true`로 둔다.

### 상태 줄 스크립트를 만들 때 흔한 실수는?

없는 필드를 처리하지 않는 것이다. 첫 요청 전과 압축 직후에는 사용량이 `null`이고, effort와 rate_limits는 모델과 요금제에 따라 빠진다. 또 갱신이 300ms 디바운스로 몰리고 새 갱신이 이전 실행을 취소하니, 스크립트 안에서 네트워크 호출을 하면 줄이 자주 비어 보인다. 느린 값은 캐시 파일로 빼고 0과 없음을 구분한다.

### 채널은 일반 MCP 서버, Remote Control과 무엇이 다른가?

일반 MCP 서버는 Claude가 필요할 때 부르는 도구고, 채널은 밖에서 열린 세션으로 이벤트를 먼저 밀어 넣는다. Remote Control은 사람이 폰으로 로컬 세션을 조종하는 것이고, 채널은 CI나 메신저 봇 같은 사람 아닌 출처가 세션을 깨운다. 새 세션이 아니라 이미 열린 세션이라 하던 작업의 맥락과 파일을 그대로 쓴다.

### 커뮤니티 플러그인을 설치하기 전에 무엇을 확인하나?

`hooks/hooks.json`과 거기서 부르는 스크립트, `.mcp.json`이 띄우는 프로세스와 연결 대상, 스킬의 `allowed-tools`, 출력 스타일의 `force-for-plugin`을 읽는다. 설치한 플러그인은 등급과 상관없이 내 권한으로 실행되기 때문이다. `claude plugin details`로 매 세션 깔리는 토큰을 보고, 쓰지 않으면 끈다. MCP 서버가 든 플러그인을 세션 중에 켜고 끄면 캐시도 깨진다.
