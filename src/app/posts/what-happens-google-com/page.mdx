"브라우저 주소창에 google.com을 입력하고 엔터를 치면 무슨 일이 일어나나요?" 면접에서 워낙 자주 나와서 오히려 대충 외우고 넘어가기 쉬운 질문이다. 그런데 하나씩 풀어 보면 네트워크, 보안, 브라우저가 한 번에 다 들어 있다. 엔터를 누른 순간부터 화면에 검색창이 뜰 때까지를 순서대로 따라가 본다.

큰 흐름은 이렇다. 브라우저가 입력을 주소로 해석하고, DNS로 서버의 IP를 알아내고, 그 서버와 TCP 연결을 맺고, TLS로 암호화 채널을 만들고, HTTP로 페이지를 요청하고, 받은 HTML을 화면에 그린다. 사이사이에 캐시가 끼어들어 단계를 건너뛰게 해 준다.

## 검색어인가, 주소인가

주소창은 검색창이기도 하다. 브라우저는 먼저 입력이 주소처럼 생겼는지 본다. `google.com`은 점이 있고 알려진 최상위 도메인(`.com`)으로 끝나니 주소로 판단한다. `구글`처럼 주소 같지 않으면 기본 검색 엔진으로 검색어를 보낸다.

다음은 `https://`를 붙일지 `http://`를 붙일지다. 입력에는 스킴이 없다. 크롬 같은 최신 브라우저는 직접 입력한 주소에 기본으로 HTTPS를 먼저 시도한다. 여기에 HSTS가 더해진다. 서버가 `Strict-Transport-Security` 응답 헤더를 보내면 브라우저는 "이 도메인은 앞으로 HTTPS로만 접속한다"고 기억해 두고, 그 뒤로는 HTTP 요청을 아예 보내지 않는다. 첫 접속 전부터 이 규칙을 적용하고 싶은 도메인을 위해, 브라우저에 미리 내장해 두는 HSTS 프리로드 목록도 있다.

결국 브라우저가 만든 주소는 이런 모양이다. 조각을 눌러 보면 각각의 역할이 나온다.

## 서버와 연결 맺기: TCP와 TLS

IP를 알았으니 서버에 연결한다. HTTP/1.1과 HTTP/2는 TCP 위에서 동작하고, HTTPS라면 그 위에 TLS를 한 겹 더 얹는다. TCP는 "데이터가 빠짐없이 순서대로 도착하게" 해 주고, TLS는 "중간에서 아무도 못 읽고 못 바꾸게" 해 준다. 각각 시작할 때 서로 확인하는 절차(핸드셰이크)가 있다.

구글처럼 HTTP/3를 지원하는 서버라면 다음 접속부터는 이 그림이 달라진다. HTTP/3는 TCP 대신 UDP 위의 QUIC을 쓰고, QUIC은 연결 설정과 TLS 1.3 핸드셰이크를 하나로 합쳐 왕복 한 번에 끝낸다. 브라우저는 첫 응답의 `Alt-Svc` 헤더를 보고 HTTP/3를 쓸 수 있다는 걸 알게 된다.

HTTP/2의 멀티플렉싱에도 약점이 하나 있다. 요청은 여러 개가 동시에 오가지만 아래의 TCP 연결은 하나다. 패킷 하나가 유실되면 TCP는 그게 다시 올 때까지 뒤의 데이터를 전부 붙잡고 기다리는데, 그 사이 상관없는 다른 요청들까지 멈춘다(TCP 수준의 head-of-line blocking). HTTP/3가 TCP를 버리고 QUIC으로 간 가장 큰 이유가 이거다. QUIC은 요청마다 흐름을 따로 관리해서, 한 요청의 유실이 다른 요청을 막지 않는다.

HTML은 DOM이라는 트리가 되고, CSS는 CSSOM이라는 트리가 된다. 둘을 합친 게 렌더 트리다. 여기에는 화면에 실제로 보이는 것만 들어간다. `display: none`인 요소나 `<head>`는 빠진다. 그다음 레이아웃 단계에서 각 요소의 정확한 위치와 크기를 계산하고, 페인트 단계에서 글자·색·그림자를 픽셀로 채운다. 마지막으로 여러 레이어를 합성해 화면에 내보낸다.

이 순서를 알면 성능 이야기가 쉬워진다. 요소의 크기나 위치를 바꾸면 레이아웃부터 다시 해야 한다(리플로우). 색만 바꾸면 페인트부터 다시 한다(리페인트). `transform`과 `opacity`만 바꾸는 애니메이션은 합성 단계에서 처리할 수 있어서 가장 가볍다.

중간에 끼어드는 것들도 있다. CSS는 렌더링을 막는다. CSSOM이 완성되기 전에 그리면 스타일 없는 화면이 번쩍 보이니, 브라우저는 CSS를 다 받을 때까지 그리지 않는다. 자바스크립트는 파싱을 막는다. 평범한 `<script>`를 만나면 HTML 파싱을 멈추고 스크립트를 받아 실행한 뒤에 이어 간다. 스크립트가 DOM을 바꿀 수 있기 때문이다. 이걸 피하려고 `defer`(받는 건 병렬로, 실행은 파싱이 끝난 뒤 순서대로)나 `async`(받는 건 병렬로, 받는 즉시 실행)를 붙인다. 이 단계들이 어느 스레드에서 무엇을 기다리며 도는지는 [브라우저 렌더링 파이프라인](/posts/browser-rendering-pipeline)에서 트레이스로 따라간다.

## 캐시가 단계를 건너뛰게 해 준다

두 번째 방문부터는 이 과정의 상당 부분이 생략된다. DNS 답은 TTL 동안 브라우저와 OS, 리졸버에 남아 있다. 서버와의 연결도 잠깐 유지되어 다시 쓸 수 있다. TLS는 세션 재개로 핸드셰이크를 줄이고, HTTP/3의 0-RTT는 첫 패킷부터 요청을 실어 보낸다(재전송 공격 위험 때문에 안전한 요청에만 쓴다). 정적 파일은 HTTP 캐시에서 바로 꺼내 쓴다. 우리가 "두 번째는 빠르다"고 느끼는 건 이 캐시들이 겹겹이 작동한 결과다.

## 페이지가 안 뜰 때 몇 번째 단계인지 고르기

이 흐름을 외워 두면 장애 신고를 받았을 때 바로 쓸모가 있다. "사이트가 안 열린다"는 말은 DNS, TCP, TLS, HTTP, 렌더링 중 어디서든 나올 수 있는데, 에러 문구가 이미 단계를 알려 주는 경우가 많다. 크롬의 에러 화면 코드와 curl의 종료 코드를 단계에 맞춰 보면 이렇다.

| 단계 | 크롬 에러 화면 | curl |
|---|---|---|
| DNS | `ERR_NAME_NOT_RESOLVED` | `(6) Could not resolve host` |
| TCP | `ERR_CONNECTION_REFUSED`, `ERR_CONNECTION_TIMED_OUT` | `(7) Failed to connect`, `(28) ... timed out` |
| TLS | `NET::ERR_CERT_AUTHORITY_INVALID` 같은 `ERR_CERT_*` | `(60) SSL certificate problem` |
| HTTP | 에러 화면 없이 서버가 준 404·502 페이지 | 종료 코드 0, 상태 코드만 다르다 |

curl 쪽은 Ubuntu 24.04의 curl 8.5에서 단계마다 일부러 실패를 만들어 확인했다. 실습용 nginx를 `localhost:18613`에 자체 서명 인증서로 띄웠고, 18603번에는 아무것도 띄우지 않았다.

```bash
# DNS: 존재할 수 없는 이름 (.invalid 는 예약된 최상위 도메인이다)
curl -sS -o /dev/null https://no-such-host.invalid/

# TCP: 아무도 듣지 않는 포트
curl -sS -o /dev/null https://127.0.0.1:18603/

# TLS: 내 컴퓨터가 믿지 않는 인증서
curl -sS -o /dev/null https://localhost:18613/

# HTTP: 연결은 다 됐고 서버가 404를 준다 (인증서를 --cacert로 믿게 했다)
curl -sS -o /dev/null --cacert cert.pem -w '%{http_code}\n' https://localhost:18613/nope
```

```text
curl: (6) Could not resolve host: no-such-host.invalid
curl: (7) Failed to connect to 127.0.0.1 port 18603 after 0 ms: Couldn't connect to server
curl: (60) SSL certificate problem: self-signed certificate
404
```

(60) 뒤에 붙는 안내 문단은 줄였다. 마지막 줄이 중요하다. 404나 502는 앞의 네 단계가 모두 성공했다는 뜻이다. 네트워크나 인증서를 볼 필요가 없고, 서버의 라우팅과 그 뒤를 보면 된다. 반대로 `(6)`이 나왔는데 서버 로그를 뒤지면 시간만 쓴다. 요청은 서버에 닿지도 않았다.

"안 열린다"가 아니라 "느리다"면 단계별 시간을 잰다. curl `-w`의 시간 값은 각 단계가 끝난 시각을 요청 시작부터 누적해서 적는다.

```bash
curl -s -o /dev/null --cacert cert.pem \
  -w 'dns:   %{time_namelookup}\ntcp:   %{time_connect}\ntls:   %{time_appconnect}\nttfb:  %{time_starttransfer}\ntotal: %{time_total}\n' \
  https://localhost:18613/
```

```text
dns:   0.000021
tcp:   0.000121
tls:   0.003846
ttfb:  0.004262
total: 0.004303
```

로컬이라 전부 몇 밀리초지만 읽는 법은 같다. 앞 값과의 차이가 그 단계에 든 시간이다. 여기서는 TLS가 3.7ms로 가장 컸다. 실제 사이트에서 `dns`만 수백 밀리초라면 리졸버를, `tcp`와 `tls`의 차이가 크면 서버까지의 거리(RTT)나 TLS 설정을, `ttfb`에서 크게 뛰면 서버가 응답을 만드는 데 오래 걸린 것이다. 브라우저에서는 Network 탭에서 요청을 고르고 Timing 탭을 열면 같은 구간이 DNS Lookup, Initial connection, SSL, Waiting for server response, Content Download로 나뉘어 나온다. 연결을 재사용한 요청에는 앞의 세 구간이 없다. 캐시 이야기에서 본 "두 번째는 빠르다"가 이 탭에서 눈에 보인다.

여기서 단계를 골랐으면 그 단계부터 더 아래로 내려가 확인한다. 층마다 무슨 명령으로 보는지는 [계층별로 장애 좁히기](/posts/network-troubleshooting-by-layer)에, 이 단계들을 OSI 계층에 맞춰 현장에서 쓰는 법은 [OSI 7계층을 알면 현장에서 무엇이 달라지나](/posts/osi-in-practice)에 정리했다.

## 정리

엔터 한 번에 브라우저는 입력을 HTTPS 주소로 만들고, DNS로 여러 단계를 거쳐 IP를 찾고, TCP와 TLS 핸드셰이크로 안전한 연결을 맺는다. 그다음 HTTP로 리다이렉트를 따라가 HTML을 받고, DOM과 CSSOM을 만들어 레이아웃·페인트·합성 순서로 화면을 그린다. 단계마다 캐시가 있어 다시 방문할 때는 대부분을 건너뛴다. 면접에서는 전체 흐름을 먼저 한 문단으로 말하고, 면접관이 파고드는 단계에서 깊게 들어가면 된다.

## 면접에서 나올 만한 질문

### 주소창에 google.com을 입력하면 무슨 일이 일어나나요?

브라우저가 입력을 주소로 해석하고 HTTPS 우선 정책과 HSTS에 따라 https 주소로 만든다. 캐시를 확인한 뒤 DNS로 IP를 얻고, TCP 3-way handshake와 TLS 핸드셰이크로 암호화된 연결을 맺는다. HTTP 요청을 보내 301 리다이렉트를 따라 www.google.com의 HTML을 받고, DOM·CSSOM·렌더 트리를 만들어 레이아웃, 페인트, 합성 순서로 화면을 그린다. 이후 CSS·JS 같은 하위 자원을 같은 연결로 받아 페이지를 완성한다.

### DNS는 어떻게 동작하나요? 재귀 질의와 반복 질의의 차이는요?

브라우저와 OS 캐시에 없으면 리졸버에게 묻는다. 내 컴퓨터와 리졸버 사이는 "최종 답을 달라"는 재귀 질의이고, 리졸버는 루트 → TLD(.com) → 권한 있는 네임서버 순서로 직접 한 단계씩 묻는 반복 질의를 한다. 받은 답은 TTL 동안 각 단계에 캐시된다.

### TCP는 왜 3-way handshake를 하나요? 2번이면 안 되나요?

양쪽이 서로의 시작 시퀀스 번호를 주고받고, 상대가 그걸 받았는지 확인해야 하기 때문이다. SYN으로 내 번호를 보내고, SYN+ACK로 상대가 내 번호를 받았다는 확인과 자기 번호를 보내고, 마지막 ACK로 상대 번호를 받았다고 확인한다. 두 번으로 끝내면 서버는 자기 번호가 클라이언트에게 갔는지 알 수 없고, 지연된 옛 SYN이 도착했을 때 잘못된 연결을 열 수 있다.

### TLS 핸드셰이크에서는 무슨 일이 일어나고, 인증서는 어떻게 검증하나요?

클라이언트가 지원하는 암호 방식과 키 교환 값을 보내고, 서버가 방식을 골라 자기 키 교환 값과 인증서, 서명을 보낸다. 양쪽이 같은 세션 키를 계산해서 이후 통신을 대칭키로 암호화한다. 인증서는 신뢰하는 루트 CA까지 서명 체인이 이어지는지, 도메인이 맞는지, 유효 기간과 폐기 여부를 검증한다. TLS 1.3은 이 과정을 왕복 한 번에 끝낸다.

### HTTP/1.1, HTTP/2, HTTP/3의 차이는요?

HTTP/1.1은 한 연결에서 요청을 하나씩 처리해서 브라우저가 연결을 여러 개 연다. HTTP/2는 연결 하나에서 여러 요청을 동시에 주고받는 멀티플렉싱과 헤더 압축을 지원하지만, TCP 위라서 패킷 하나가 유실되면 모든 요청이 기다린다. HTTP/3는 UDP 기반 QUIC 위에서 요청별로 흐름을 나눠 이 문제를 없애고, 연결과 TLS 설정을 합쳐 더 빨리 시작한다.

### 301과 302는 어떻게 다르고, HSTS는 무엇인가요?

301은 영구 이동이라 브라우저와 검색 엔진이 새 주소를 기억하고, 302는 임시 이동이라 다음에도 원래 주소로 요청한다. HSTS는 서버가 "앞으로 이 도메인은 HTTPS로만 접속하라"고 알려 주는 헤더다. 브라우저가 이를 기억해 HTTP 요청 자체를 보내지 않게 하고, 프리로드 목록에 오른 도메인은 첫 접속부터 적용된다.

### 브라우저는 HTML을 어떻게 화면에 그리나요? 리플로우와 리페인트는요?

HTML로 DOM, CSS로 CSSOM을 만들고 합쳐서 화면에 보이는 요소만 담은 렌더 트리를 만든다. 레이아웃에서 위치와 크기를 계산하고, 페인트에서 픽셀을 채우고, 합성에서 레이어를 합친다. 크기·위치가 바뀌면 레이아웃부터 다시 하는 리플로우가, 색처럼 모양만 바뀌면 리페인트가 일어난다. transform과 opacity는 합성만 다시 하면 돼서 애니메이션에 유리하다.

### script 태그의 async와 defer는 어떻게 다른가요?

일반 script는 HTML 파싱을 멈추고 받아서 실행한다. async는 파싱과 병렬로 받고 받는 즉시 실행해서, 실행 순서가 보장되지 않는다. defer는 병렬로 받고 파싱이 끝난 뒤 문서에 적힌 순서대로 실행한다. 다른 스크립트나 DOM에 의존하면 defer, 독립적인 분석 스크립트 같은 건 async가 맞다.
