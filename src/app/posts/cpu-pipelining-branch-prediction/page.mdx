<EasyIntro>
  똑같은 배열을 더하는 코드인데, 배열을 정렬해 두기만 하면 다섯 배 넘게 빨라지는 일이 있다. 계산량은 하나도 안 변했는데 빨라진 이유를 따라가면 CPU가 명령을 처리하는 방식이 보인다.

  CPU는 빨래를 하듯 일한다. 세탁기가 도는 동안 건조기에 앞 빨래를 넣는 것처럼, 한 명령을 끝까지 기다리지 않고 다음 명령을 겹쳐서 처리한다. 그런데 "만약 ~이면"이라는 갈림길을 만나면 어느 쪽으로 갈지 결과가 나올 때까지 다음 빨래를 넣을 수 없다. 그래서 CPU는 기다리지 않고 지난번에 간 쪽으로 가겠다고 짐작한 뒤 미리 달린다.

  짐작이 맞으면 거의 공짜지만, 틀리면 미리 해 둔 일을 전부 버리고 처음부터 다시 한다. 정렬된 배열은 갈림길 방향이 한동안 같아서 짐작이 잘 맞고, 뒤섞인 배열은 절반쯤 틀려서 느려진다.
</EasyIntro>

바이트 배열에서 128 이상인 값만 더하는 C 함수가 있다. 같은 배열을 정렬한 뒤 다시 돌리면 다섯 배 넘게 빨라진다. 더하는 값도, 비교 횟수도 그대로다.

```c
long count_big(const unsigned char *d, int n) {
  long s = 0;
  for (int i = 0; i < n; i++) { if (d[i] >= 128) s += d[i]; }
  return s;
}
```

```text
random   1.556 s  (4.75 ns/elem)  sum=31493160000
sorted   0.288 s  (0.88 ns/elem)  sum=31493160000
```

이 차이는 CPU가 `if`의 결과를 알기도 전에 다음 명령을 실행하고 있어서 생긴다. 이 글은 명령어를 한 줄로 세워 겹쳐 처리하는 파이프라인, 그 흐름을 끊는 해저드, 분기 방향을 미리 맞히는 분기 예측, 순서를 바꿔 실행하는 비순차 실행, 그 추측이 남긴 흔적을 노린 Spectre, 명령 하나로 값 여러 개를 처리하는 SIMD까지 직접 잰 숫자로 따라간다.

실습은 Ubuntu 24.04, gcc 13.3, Node 22, Xeon 4코어 KVM 가상 머신에서 했다. 다른 작업과 함께 쓰는 머신이라 숫자는 실행마다 조금씩 다르다. 명령어 하나가 실행되는 기본 순서는 [CPU 명령어 사이클](/posts/cpu-instruction-cycle)에서, 메모리를 기다리는 시간은 [CPU 캐시](/posts/cpu-cache-hierarchy)에서 다뤘다.

## 다섯 단계를 겹쳐서 돌린다

명령어 하나는 가져오기, 풀기, 실행, 메모리 접근, 결과 쓰기를 거친다. 교과서에서 흔히 쓰는 5단계 RISC 파이프라인으로 이름을 붙이면 IF, ID, EX, MEM, WB다. 한 명령이 다섯 단계를 다 끝낸 뒤에 다음 명령을 시작하면, 단계마다 회로의 4/5는 늘 놀고 있다.

파이프라인은 이 단계들을 겹친다. 첫 명령이 풀기 단계로 넘어가면 비어 있는 가져오기 단계에 다음 명령을 넣는다. 세탁기가 돌 때 건조기에 앞 빨래를 넣는 것과 같다. 아래 그림에서 다음을 누르면 한 사이클씩 진행된다. 실행 단계(EX)에 있는 명령이 강조된다.

명령 하나가 끝나는 데 걸리는 시간(지연)은 여전히 다섯 사이클이다. 달라진 건 처리량이다. 파이프가 차면 매 사이클 명령 하나가 끝난다. 단계를 더 잘게 쪼개면 한 단계가 짧아져 클럭을 높일 수 있어서, 2000년대 초반 펜티엄 4는 파이프라인을 20단계 넘게 늘렸다. 요즘 x86 코어도 10단계 중후반에서 20단계 안팎이다. 단계가 길수록 흐름이 끊길 때 버리는 일이 많아진다. 이 글의 나머지가 그 끊김에 대한 이야기다.

## 흐름이 끊기는 세 가지 경우

파이프라인이 매 사이클 명령 하나를 끝내려면 다음 명령이 바로 출발할 수 있어야 한다. 그렇지 못한 상황을 해저드(hazard)라고 하고 세 가지로 나눈다.

데이터 해저드는 앞 명령의 결과가 필요한데 아직 안 나온 경우다. `add rax, rbx` 바로 뒤에 `sub rcx, rax`가 오면 `sub`는 `rax`를 기다려야 한다. CPU는 결과를 레지스터에 쓰기 전에 실행 단계 출구에서 다음 명령의 입구로 바로 넘겨주는 전달(forwarding) 회로로 대부분을 메운다. 메모리에서 읽은 값을 바로 쓰는 경우처럼 전달로도 메울 수 없으면 한두 사이클을 비워 두고(stall) 기다린다.

구조 해저드는 두 명령이 같은 회로를 동시에 쓰려는 경우다. 곱셈기가 하나뿐인데 곱셈 두 개가 연달아 오면 하나는 기다린다. CPU는 실행 장치를 여러 벌 두어 줄인다.

제어 해저드는 분기다. `jne`의 결과는 실행 단계에서야 나오는데, 그때까지 가져오기 단계는 무엇을 가져와야 할지 모른다. 기다리면 단계 수만큼 사이클을 날린다. 그래서 CPU는 기다리지 않고 짐작한다.

[앞 글](/posts/cpu-instruction-cycle)에서 곱셈 결과를 다음 곱셈이 기다리게 만들면 한 번에 세 사이클이 걸렸다. 데이터 해저드가 사라지지 않는 대표적인 경우가 이런 의존 사슬이다. 사슬을 끊으면 CPU가 알아서 겹친다. 실수 배열의 합을 누산기 하나로 구하는 것과 넷으로 나눠 구하는 것을 비교했다. SIMD를 끄고(`-fno-tree-vectorize`) 스칼라 덧셈만 쓰게 했다.

```c
double sum1(const double *x, int n) { double s = 0; for (int i = 0; i < n; i++) s += x[i]; return s; }
double sum4(const double *x, int n) {
  double s0 = 0, s1 = 0, s2 = 0, s3 = 0;
  for (int i = 0; i < n; i += 4) { s0 += x[i]; s1 += x[i+1]; s2 += x[i+2]; s3 += x[i+3]; }
  return (s0 + s1) + (s2 + s3);
}
```

```text
1 accumulator  0.74 ns/add   4 accumulators  0.19 ns/add   (8.38656e+11)
1 accumulator  0.71 ns/add   4 accumulators  0.20 ns/add   (8.38656e+11)
```

같은 덧셈 4,096번인데 3.7배 빨라졌다. 누산기가 하나면 매번 앞의 `s`를 기다리고, 넷이면 서로 상관없는 덧셈 네 줄이 동시에 흐른다. 컴파일러가 이걸 알아서 해 주지 않는 이유는 부동소수점 덧셈의 순서를 바꾸면 반올림 결과가 달라질 수 있어서다. `-ffast-math`를 주면 바꿔도 된다고 허락하는 셈이지만 결과가 마지막 자리에서 달라질 수 있다.

## 분기 결과를 미리 맞힌다

분기 예측기는 분기 명령마다 과거에 어느 쪽으로 갔는지를 기록해 두고, 다음에 그 분기를 만나면 결과가 나오기 전에 갈 쪽을 고른다. 고른 쪽의 명령을 가져와 계속 실행하다가, 실제 결과가 나왔을 때 맞았으면 그대로 진행하고 틀렸으면 그 뒤로 실행한 것을 모두 버리고 맞는 쪽부터 다시 가져온다.

가장 단순한 예측기는 분기마다 2비트 카운터 하나를 둔다. 0과 1이면 "안 간다", 2와 3이면 "간다"로 예측하고, 실제로 갔으면 1 올리고(3에서 멈춤) 안 갔으면 1 내린다(0에서 멈춤). 한 번 어긋났다고 바로 예측을 뒤집지 않는 게 요점이다. 세 번 돌고 빠져나오는 루프의 분기를 따라가 보자. 칸은 분기가 실제로 간 방향(T: 간다, N: 안 간다)이고, 기억 칸은 카운터 값과 예측 결과다.

실제 CPU의 예측기는 이보다 훨씬 똑똑하다. 최근 몇십~몇백 개 분기의 결과(전역 이력)와 분기 주소를 섞어 표를 찾고, 이력 길이가 다른 표 여러 개 중 가장 잘 맞는 것을 고른다(TAGE 계열). 그래서 규칙이 있는 패턴은 꽤 길어도 배운다. 앞의 함수를 `if` 변환을 끈 채로 컴파일해 데이터 모양만 바꿔 봤다.

```text
always taken           0.35 ns/elem
alternate T F          1.11 ns/elem
period 3: T T F        0.93 ns/elem
random, 90% taken      1.73 ns/elem
random, 50% taken      4.67 ns/elem
```

"간다, 안 간다"가 번갈아 나오거나 세 개 주기로 반복되는 패턴은 2비트 카운터라면 자주 틀렸을 텐데, 무작위 50%보다 네 배 넘게 빠르다. 예측기가 규칙을 배운 것이다. 늘 같은 쪽으로 가는 경우보다 느린 이유는 이 글의 측정만으로는 가르기 어렵다(더하기를 하는 횟수와 분기 모양이 함께 바뀌었다). 무작위가 섞이면 규칙이 없으니 예측이 틀리는 비율만큼 느려진다. 90%가 한쪽이어도 10%는 틀린다.

## 틀리면 버리고 다시 가져온다

글 처음의 결과를 다시 보자. 무작위 배열에서 128 이상은 절반이고 규칙이 없으니 분기 예측이 절반쯤 틀린다. 정렬하면 앞쪽 절반은 늘 "안 간다", 뒤쪽 절반은 늘 "간다"라서 경계 한 번 말고는 다 맞힌다. 두 시간의 차이를 틀린 횟수로 나누면 한 번 틀릴 때의 손해를 어림할 수 있다.

- 원소 하나당 차이: 4.75 - 0.88 = 3.87ns
- 무작위에서는 원소 두 개에 한 번꼴로 틀린다: 3.87 × 2 = 7.7ns
- 이 VM이 2.7GHz 안팎으로 돈다면 약 21사이클

## 분기를 없애는 방법

예측을 잘하게 만들 수 없으면 분기를 없애는 방법이 있다. 앞의 함수는 `-O2`로 그냥 컴파일하면 gcc가 알아서 분기를 없앤다.

```text
random   0.328 s  (1.00 ns/elem)  sum=31493160000
sorted   0.325 s  (0.99 ns/elem)  sum=31493160000
```

정렬 여부와 상관없이 1ns다. 어셈블리를 보면 조건 점프 대신 `cmovs`가 있다.

```text
    13e0:	movzx  eax,BYTE PTR [rdi]
    13e3:	mov    rcx,rax
    13e6:	add    rax,rdx
    13e9:	test   cl,cl
    13eb:	cmovs  rdx,rax
    13ef:	add    rdi,0x1
    13f3:	cmp    rsi,rdi
    13f6:	jne    13e0 <count_big+0x10>
```

루프 안의 조건 점프는 끝의 `jne` 하나뿐이고, 이건 루프를 도는 동안 늘 같은 쪽이라 쉽게 맞힌다. 일단 `s + d[i]`를 계산해 두고, 부호 비트(128 이상)가 켜져 있을 때만 그 값을 `s`에 옮긴다. 조건부 이동(cmov)은 점프가 아니라 데이터 흐름이라 예측할 것이 없다. 대신 양쪽을 다 계산하니 늘 1ns를 낸다. 정렬된 배열에서는 분기 쪽(0.88ns)이 오히려 조금 빨랐다. 예측이 잘 맞는 분기는 공짜에 가깝고, 무작위 분기는 비싸다. 어느 쪽이 나을지는 데이터가 정한다. 그래서 컴파일러가 늘 cmov를 고르지는 않고, 프로파일 기반 최적화(PGO)가 실제 분기 확률을 알려 주면 판단이 나아진다.

자바스크립트에서도 같은 현상이 보인다. 같은 함수를 Node 22에서 돌렸다. 워밍업으로 최적화 컴파일이 끝나기를 기다린 뒤 쟀다.

```js
function countBig(d) {
  let s = 0;
  for (let i = 0; i < d.length; i++) if (d[i] >= 128) s += d[i];
  return s;
}
```

```text
random  476 ms  (2.91 ns/elem)  sum=16095570000
sorted  183 ms  (1.12 ns/elem)  sum=16095570000
```

2.6배 차이다. V8의 최적화 컴파일러(TurboFan)가 여기서는 분기를 남겼다는 뜻이다. 무작위 순서의 데이터를 조건으로 거르는 핫 루프라면, 미리 정렬하거나 분기 없는 식(`s += d[i] & -(d[i] >> 7)` 같은)으로 바꿔 볼 만하다. 다만 이런 손질은 측정으로 효과를 확인한 핫 루프에만 한다. 나머지 코드에서는 읽기 쉬운 `if`가 낫다.

## 기다리는 동안 다른 일을 먼저 한다

파이프라인이 겹쳐 처리한다면, 비순차 실행(out-of-order execution)은 순서를 바꿔 처리한다. 앞 명령이 캐시 놓침으로 수백 사이클을 기다리는 동안, 그 결과와 상관없는 뒤의 명령을 먼저 실행한다. 요즘 고성능 코어는 수백 개의 명령을 동시에 들고 있다가 재료가 준비된 것부터 실행 장치로 보낸다.

순서를 바꿔도 프로그램이 다르게 동작하면 안 되니 두 가지 장치가 있다. 레지스터 이름 바꾸기(renaming)는 같은 `rax`를 쓰지만 사실은 상관없는 두 명령이 서로를 기다리지 않게, 실제로는 수백 개 있는 물리 레지스터에 따로 배정한다. 완료 대기열(ROB, reorder buffer)은 실행은 아무 순서로 하더라도 결과 확정(retire)은 원래 순서대로 하게 한다. 그래서 예측이 틀렸거나 예외가 나면 그 뒤의 결과를 아무 일 없었던 것처럼 버릴 수 있다. 아래 그림은 캐시를 놓친 load 뒤에서 상관없는 명령이 먼저 끝나는 모습이다.

## 추측이 남긴 흔적을 읽는 공격, Spectre

추측 실행은 틀리면 결과를 버리니 안전해 보였다. 2018년에 공개된 Spectre는 "결과는 버려도 캐시에 남은 흔적은 남는다"는 점을 이용했다. 가장 기본형(변종 1, 경계 검사 우회)은 이런 코드를 노린다.

```c
if (x < array1_size) {
  y = array2[array1[x] * 4096];
}
```

공격자는 먼저 범위 안의 `x`를 여러 번 넣어 분기 예측기가 "조건은 참"으로 배우게 만든다. 그다음 범위를 한참 벗어난 `x`를 넣으면, CPU는 `array1_size`를 메모리에서 읽어 오는 동안 예측대로 안쪽을 추측 실행한다. `array1[x]`로 비밀 바이트를 읽고, 그 값에 따라 `array2`의 서로 다른 줄을 캐시에 올린다. 예측이 틀린 걸 알고 결과를 버리지만 캐시에 올라온 줄은 그대로다. 마지막으로 `array2`의 줄마다 읽는 시간을 재서 빠른 줄을 찾으면 비밀 값을 알 수 있다.

완화책은 공짜가 아니다. 시스템 호출이나 문맥 전환이 잦은 워크로드는 완화책 때문에 눈에 띄게 느려질 수 있다. 그래서 커널 부팅 옵션 `mitigations=off`로 다 끄는 이야기가 가끔 나오는데, 남의 코드를 함께 돌리는 서버(클라우드, 브라우저, 다중 테넌트)에서는 쓰면 안 된다. 브라우저는 같은 이유로 `SharedArrayBuffer`처럼 정밀한 시계를 만들 수 있는 기능을 교차 출처 격리(COOP·COEP 헤더)가 된 페이지에서만 쓸 수 있게 막았다. 사이트마다 프로세스를 나누는 사이트 격리도 이 공격 이후 크롬 계열에서 기본이 됐다.

## 명령 하나로 값 여러 개를 계산한다

파이프라인과 비순차 실행이 명령 여러 개를 동시에 처리한다면, SIMD는 명령 하나가 값 여러 개를 처리한다. x86의 AVX2 레지스터(ymm)는 256비트라서 바이트 32개나 `int32` 8개를 한 번에 더한다. AVX-512는 그 두 배다. 앞의 함수를 분기 없는 식으로 쓰고, 벡터화를 끈 경우와 `-O3 -march=native`로 이 CPU의 SIMD를 다 쓰게 한 경우를 비교했다.

```c
unsigned count_big(const unsigned char *d, int n) {
  unsigned s = 0;
  for (int i = 0; i < n; i++) s += d[i] >= 128 ? d[i] : 0;
  return s;
}
```

```bash
gcc -O2 -fno-tree-vectorize -o simd_scalar simd.c   # 스칼라만
gcc -O3 -march=native -o simd_avx simd.c            # 이 CPU의 SIMD까지
```

```text
== simd_scalar
random  0.331 s  (1.009 ns/elem)  sum=31493160000
== simd_avx
random  0.047 s  (0.145 ns/elem)  sum=31493160000
```

일곱 배 빨라졌다. 어셈블리에는 32바이트를 한 번에 읽는 `vmovdqu8`, 32개를 동시에 비교하는 `vpcmpltb`, 여덟 개씩 더하는 `vpaddd`가 나온다. 비교 결과를 분기가 아니라 마스크 레지스터(`k1`)에 담아서, 조건에 맞지 않는 칸은 0으로 만든 채 더한다.

```text
    1358:	vmovdqu8 ymm2,YMMWORD PTR [rax]
    1362:	vpcmpltb k1,ymm2,ymm5
    1369:	vpmovzxbw ymm1,xmm2
    1379:	vpmovzxwd ymm2{k1}{z},xmm1
    13a9:	vpaddd ymm2,ymm2,ymm4
```

컴파일러가 루프를 벡터화하려면 조건이 있다. 반복끼리 의존이 없어야 하고(앞의 누산기 하나짜리 실수 합은 순서 문제로 막힌다), 분기가 없거나 마스크로 바꿀 수 있어야 하고, 포인터가 서로 겹치지 않는다고 확신할 수 있어야 한다. `gcc -fopt-info-vec-missed`를 주면 어느 루프가 왜 벡터화되지 않았는지 알려 준다. `-march=native`로 만든 바이너리는 빌드한 머신의 명령어를 쓰니, 더 오래된 CPU에서 돌리면 `Illegal instruction`으로 죽는다. 배포용이면 `-march=x86-64-v3`처럼 목표 세대를 정해 둔다. 자바스크립트에서는 엔진이 이런 벡터화를 거의 하지 않아서, 이런 계산이 정말 무겁다면 WebAssembly SIMD를 쓴다.

## 현장에서 이 지식이 쓰이는 곳

이 내용을 매일 쓰지는 않는다. 그래도 몇 가지 증상은 이 지식으로만 설명된다.

같은 코드인데 입력 데이터에 따라 처리 시간이 몇 배씩 다르면, 데이터의 정렬 상태나 분포가 바뀌어 분기 예측이 틀리기 시작했는지 본다. 하드웨어 카운터가 열린 환경이면 `perf stat -e branches,branch-misses`로 틀린 비율을 바로 볼 수 있다. 카운터가 막힌 VM이라면 이 글처럼 데이터를 정렬한 경우와 비교해 본다.

정확도가 중요한 계산에서 `-ffast-math`나 SIMD 버전이 결과를 바꾼 것처럼 보이면, 부동소수점 덧셈의 순서가 바뀐 탓인지 먼저 의심한다. 버그가 아니라 반올림 순서 차이일 수 있다.

클라우드 인스턴스 세대를 바꿨는데 시스템 호출이 많은 서비스만 느려졌다면 CPU 취약점 완화책의 차이를 본다. `/sys/devices/system/cpu/vulnerabilities/`를 두 인스턴스에서 비교하면 된다.

빌드 서버에서 `-march=native`로 만든 바이너리가 운영 서버에서 `Illegal instruction`으로 죽으면 두 머신의 `lscpu` 플래그(`avx2`, `avx512f` 등)를 비교한다.

## 기다리지 않으려고 짐작한다

CPU는 명령을 한 줄로 세워 겹쳐 처리하고(파이프라인), 결과를 기다려야 할 때는 상관없는 명령을 먼저 하고(비순차 실행), 분기 결과는 짐작해서 미리 달린다(분기 예측과 추측 실행). 짐작이 맞으면 거의 공짜이고, 틀리면 십수 사이클을 버린다. 그래서 무작위 분기는 비싸고, 분기를 cmov나 SIMD 마스크로 바꾸면 데이터와 상관없이 일정해진다. 그 짐작이 캐시에 흔적을 남긴다는 점이 Spectre였다. 의존 사슬을 끊고, 예측하기 쉬운 데이터 흐름을 만들고, 측정으로 확인하는 것이 이 지식을 코드에 옮기는 방법이다.

## 면접에서 나올 만한 질문

### 파이프라이닝이 무엇이고 무엇이 좋아지나요?

명령어 처리를 가져오기, 풀기, 실행, 메모리, 쓰기 같은 단계로 나누고, 여러 명령을 서로 다른 단계에 겹쳐 처리하는 방식이다. 명령 하나의 지연은 그대로지만 파이프가 차면 매 사이클 명령 하나가 끝나서 처리량이 단계 수만큼 늘어난다. 단계를 잘게 나누면 클럭을 높일 수 있지만, 분기 예측이 틀릴 때 버리는 일이 많아진다.

### 파이프라인 해저드의 종류와 해결책을 설명해 주세요.

앞 결과를 기다려야 하는 데이터 해저드는 실행 결과를 다음 명령에 바로 넘기는 전달 회로와 짧은 stall로, 같은 회로를 두 명령이 쓰려는 구조 해저드는 실행 장치를 여러 벌 두어서 줄인다. 분기 결과를 몰라 다음 명령을 못 가져오는 제어 해저드는 분기 예측과 추측 실행으로 메운다. 코드 쪽에서는 의존 사슬을 끊어 주면 CPU가 더 많이 겹친다. 이 글에서 실수 합의 누산기를 넷으로 나누니 3.7배 빨라졌다.

### 정렬된 배열을 처리하는 것이 왜 더 빠를 수 있나요?

데이터에 따라 갈리는 분기가 있으면 정렬된 배열에서는 분기 방향이 한동안 같아 예측이 거의 맞고, 무작위 배열에서는 절반쯤 틀리기 때문이다. 틀릴 때마다 추측으로 실행한 명령을 버리고 다시 가져와야 해서 이 머신에서 한 번에 약 20사이클을 잃었다. 측정으로는 원소당 4.75ns와 0.88ns, 다섯 배 넘는 차이였다. 컴파일러가 분기를 cmov로 바꾸면 이 차이는 사라진다.

### 분기 예측기는 어떻게 동작하나요?

가장 단순한 형태는 분기마다 2비트 포화 카운터를 두고, 실제 결과에 따라 올리고 내리며 2 이상이면 '간다'로 예측한다. 한 번 어긋나도 바로 뒤집지 않아서 루프 끝에서 한 번만 틀린다. 실제 CPU는 최근 분기들의 결과 이력과 분기 주소를 섞어 여러 표를 찾는 방식(TAGE 계열 등)을 써서 번갈아 나오는 패턴이나 주기적인 패턴도 배운다. 간접 분기와 함수 복귀 주소는 따로 예측하는 구조가 있다.

### 비순차 실행에서 순서를 바꿔도 결과가 같은 이유는 무엇인가요?

실행은 재료가 준비된 순서로 하지만, 결과 확정(retire)은 완료 대기열(ROB)에서 원래 프로그램 순서대로 하기 때문이다. 레지스터 이름 바꾸기로 이름만 같은 레지스터 사이의 가짜 의존을 없애고, 확정 전에는 결과가 바깥에 보이지 않으니 예측이 틀리거나 예외가 나면 그 뒤를 버릴 수 있다. 다만 여러 코어 사이에서 메모리 쓰기가 보이는 순서는 별개 문제로, 메모리 모델과 배리어가 정한다.

### Spectre는 어떤 원리의 공격인가요?

추측 실행의 결과는 버려지지만 그 과정에서 캐시에 올라온 줄은 남는다는 점을 이용한다. 변종 1은 경계 검사 분기를 '참'으로 학습시킨 뒤 범위 밖 인덱스로 비밀을 추측 실행으로 읽게 하고, 그 값에 따라 캐시에 올라온 줄을 시간 측정으로 찾아낸다. 설계에서 나온 문제라 커널의 추측 장벽과 인덱스 가리기, 간접 분기 예측 제한, 브라우저의 사이트 격리와 정밀 타이머 제한처럼 여러 층에서 막는다. 리눅스에서는 `/sys/devices/system/cpu/vulnerabilities/`로 상태를 본다.

### SIMD는 무엇이고 언제 효과가 큰가요?

명령 하나로 레지스터에 담긴 값 여러 개를 동시에 처리하는 방식으로, AVX2는 256비트라 바이트 32개나 int32 8개를 한 번에 다룬다. 반복끼리 의존이 없고 분기가 없거나 마스크로 바꿀 수 있는 배열 루프에서 효과가 크다. 이 글의 측정에서 같은 함수가 일곱 배 빨라졌다. `-march=native` 바이너리는 다른 CPU에서 Illegal instruction으로 죽을 수 있으니 배포용은 목표 세대를 정해 빌드한다.

### 분기를 없애는 것이 언제나 좋은가요?

그렇지 않다. cmov나 마스크는 양쪽을 다 계산해서 늘 일정한 비용을 내고, 예측이 잘 맞는 분기는 거의 공짜라서 정렬된 데이터에서는 분기 버전이 더 빨랐다(0.88ns 대 1.00ns). 또 cmov는 두 값에 데이터 의존을 만들어 의존 사슬을 길게 할 수 있다. 데이터 분포를 보고 측정으로 고르고, 가능하면 프로파일 기반 최적화로 컴파일러에 실제 분기 확률을 알려 준다.
