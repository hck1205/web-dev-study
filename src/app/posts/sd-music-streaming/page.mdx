이 시리즈에서 이 글의 자리: 시리즈 본편 60편에는 없는 덤 사례다. 같은 미디어 계열인 [㉛ 동영상 ① 올리기와 트랜스코딩](/posts/sd-video-upload-transcoding)과 [㉜ 동영상 ② 스트리밍과 비용](/posts/sd-video-streaming-cost)을 먼저 읽으면 편하고, 전체 순서는 [시스템 설계 공부 순서](/posts/system-design-study-path)에 있다. 이 글은 영상 글에서 만든 부품을 음악에 맞게 다시 고르는 연습이다.

출근길 지하철에서 재생 버튼을 누른다. 1초 안에 소리가 나와야 하고, 터널에 들어가 신호가 끊겨도 노래는 계속 나와야 한다. 내가 그 곡을 끝까지 들었다는 기록은 나중에 가수에게 돈으로 돌아간다. 음악 스트리밍 서비스를 설계한다는 건 이 세 가지를 동시에 만족시키는 일이다.

인터넷에 "Spotify System Design"이라는 그림이 많이 돌아다닌다. 앱, 인증 서비스, 로드 밸런서, 웹 서버, 캐시, 600TB짜리 음원 저장소, 70GB짜리 메타데이터 SQL(리더와 팔로워), 검색 서비스, CDN, 그리고 큐 뒤의 분석 파이프라인이 그려져 있다. 면접에서 "음악 스트리밍을 설계해 보라"는 질문에 답하는 뼈대로는 좋다. 다만 이건 면접용 개요이지 Spotify의 실제 구조가 아니다. 실제 회사가 무엇을 쓰는지는 공개 발표 몇 개로만 엿볼 수 있고 계속 바뀐다. 이 글은 그 그림을 목차로만 쓰고, 숫자와 결정은 직접 계산해서 채운다.

## 노래 파일을 서버 한 대에 올려 두면

가장 작은 버전부터 만들자. 서버 한 대에 mp3 파일을 폴더째 넣고, 같은 서버의 PostgreSQL에 곡 제목과 파일 경로를 적는다. 앱은 `GET /songs/201`로 정보를 받고 `GET /files/201.mp3`로 파일을 받아 튼다.

친구 몇 명이 쓸 때는 잘 돈다. 사용자가 늘면 이 순서로 터진다.

1. 디스크가 먼저 찬다. 곡이 6MB라면 1만 곡에 60GB, 100만 곡이면 6TB다. 한 대의 디스크로는 감당이 안 된다.
2. 그다음은 회선이다. 동시에 1만 명이 160kbps로 들으면 1.6Gbps가 필요하다. 서버 한 대의 네트워크 카드가 먼저 막힌다.
3. 곡 정보 조회와 파일 전송이 같은 서버에서 경쟁한다. 큰 파일을 보내느라 바쁜 동안 "다음 곡 정보"를 묻는 작은 요청이 줄을 선다.
4. 재생 수를 `UPDATE songs SET plays = plays + 1`로 세면 인기곡 한 행에 쓰기가 몰려 잠금 경합이 생긴다.

이 네 가지가 앞으로의 설계 순서다. 파일과 정보를 떼어 놓고, 파일은 사용자 가까이로 보내고, 정보는 복제와 캐시로 읽기를 나누고, 재생 기록은 큐로 빼서 따로 센다.

## 만들 것과 만들지 않을 것

면접에서는 범위부터 좁힌다. 여기서는 이렇게 잡는다.

- 곡을 검색하고, 고르고, 재생한다. 재생은 1초 안에 시작한다.
- 재생목록을 만들고 곡을 넣고 뺀다.
- 유료 사용자는 곡을 기기에 내려받아 오프라인으로 듣는다.
- 재생 수를 정확하게 세서 권리자 정산에 쓴다.
- 들은 기록으로 추천 목록을 만든다.

빼는 것도 적어 둔다. 팟캐스트, 가사, 소셜 기능, 아티스트가 곡을 올리는 화면은 다루지 않는다. 음원은 음반사나 유통사가 대량으로 보내 준다고 가정한다. 올리는 쪽은 [동영상 ① 올리기와 트랜스코딩](/posts/sd-video-upload-transcoding)의 구조를 그대로 쓰면 된다. 원본 무손실 파일을 받아 여러 비트레이트로 인코딩하는 작업 그래프다.

비기능 요구도 정한다. 읽기가 압도적으로 많다. 곡은 한 번 올라가면 거의 안 바뀌고, 하루에 수억 번 재생된다. 재생은 끊기면 안 되지만 "방금 추가한 곡이 재생목록에 1초 늦게 보이는" 정도는 참을 수 있다. 반대로 재생 수는 늦게 나와도 되지만 틀리면 안 된다. 요구마다 무엇을 양보할 수 있는지가 다르다는 것이 이 설계의 출발점이다.

## 600TB와 70GB는 어디서 나왔나

그림에는 음원 600TB, 메타데이터 70GB라는 숫자가 적혀 있다. 근거는 없으니 직접 거꾸로 맞춰 본다. 가정은 이렇다.

- 곡 수 1억. Spotify는 1억 곡이 넘는다고 알려져 있지만 여기서는 계산하기 쉬운 가정값이다.
- 곡당 파일 크기 6MB. 5분짜리 곡을 160kbps로 한 벌 저장하면 `160,000 × 300 ÷ 8 = 6,000,000`바이트다. 평균 3분 30초 곡이라면 약 230kbps일 때 6MB가 된다.
- 곡당 메타데이터 700바이트. 제목, 아티스트 id, 앨범 id, 길이, 장르, 발매일, 파일 위치 정도다.

이 가정에서 음원은 `1억 × 6MB = 600TB`, 메타데이터는 `1억 × 700B = 70GB`다. node로 확인했다.

```js
// estimate.mjs: 곡 수와 비트레이트로 음원 저장량과 메타데이터 크기를 어림한다
const TB = 1e12, GB = 1e9;
function storage(songs, seconds, kbpsList, metaBytes) {
  const perSong = kbpsList.reduce((s, kbps) => s + (kbps * 1000 * seconds) / 8, 0);
  return { perSongMB: +(perSong / 1e6).toFixed(2), audioTB: Math.round((songs * perSong) / TB), metaGB: Math.round((songs * metaBytes) / GB) };
}
console.log("1억 곡, 5분, 160kbps 한 벌, 곡당 700B:", storage(1e8, 300, [160], 700));
console.log("1억 곡, 3분 30초, 96/160/320kbps 세 벌:", storage(1e8, 210, [96, 160, 320], 700));
```

```text
1억 곡, 5분, 160kbps 한 벌, 곡당 700B: { perSongMB: 6, audioTB: 600, metaGB: 70 }
1억 곡, 3분 30초, 96/160/320kbps 세 벌: { perSongMB: 15.12, audioTB: 1512, metaGB: 70 }
```

실제 서비스는 곡을 한 벌만 두지 않는다. 앱 설정에 음질 단계가 여러 개 있는 걸 보면 알 수 있듯이, 같은 곡을 여러 비트레이트로 인코딩해 둔다. 96, 160, 320kbps 세 벌이면 같은 1억 곡이 1.5PB가 된다. 여기에 저장소 자체의 복제나 이레이저 코딩 여유가 붙는다. 그래도 결론은 같다. 음원과 메타데이터는 크기가 만 배 가까이 차이 난다. 70GB는 서버 한 대의 메모리에 거의 다 올라가는 크기고, 600TB는 어떤 단일 서버에도 안 들어간다. 그러니 둘은 처음부터 다른 저장소에 둔다.

듣는 쪽 숫자도 잡아 둔다. 하루 사용자 1억 명이 평균 60분씩 160kbps로 듣는다고 가정했다.

```text
{
  perUserMB: 72,
  dailyPB: 7.2,
  concurrent: 4166667,
  avgGbps: 667,
  playsPerDay: 1714285714,
  playsPerSec: 19841
}
```

한 사람이 하루 72MB, 전체로는 하루 7.2PB를 내보낸다. 평균 동시 청취자는 약 417만 명이고 평균 대역폭은 667Gbps다. 저녁 시간대는 이 두세 배로 잡는다. 곡 하나를 3분 30초로 보면 하루 재생은 약 17억 회, 초당 약 2만 건의 재생 이벤트가 들어온다. 이 숫자들이 각각 CDN, 큐, 집계 파이프라인의 크기를 정한다. 어림셈 방법 자체는 [용량 어림하기](/posts/sd-capacity-estimation)에서 자세히 봤다.

직접 바꿔 보자. 곡 수, 곡 길이(초), 비트레이트 목록(kbps), 곡당 메타데이터 바이트를 받아 `[음원 TB, 메타데이터 GB]`를 반올림한 정수로 돌려준다. 1TB = 10^12바이트, 1GB = 10^9바이트다.

## 음원은 객체 저장소에, 가까운 곳은 CDN에

600TB를 담는 곳은 객체 저장소다. 파일을 키 하나로 넣고 꺼내는 저장소로, 용량을 거의 무한히 늘릴 수 있고 여러 디스크와 데이터센터에 나눠 담아 잘 잃어버리지 않는다. 데이터와 메타데이터를 어떻게 나누는지는 [객체 저장소 ① 구조](/posts/sd-object-storage-architecture)에서, 복제와 이레이저 코딩으로 얼마나 안전한지는 [객체 저장소 ② 내구성](/posts/sd-object-storage-durability)에서 봤다. 음원 키는 `audio/201/160.ogg`처럼 곡 id와 음질로 짓고, 한 번 쓴 파일은 고치지 않는다. 음원을 다시 인코딩하면 새 키로 쓴다.

객체 저장소는 튼튼하지만 사용자와 멀고, 내보내는 트래픽 값이 비싸다. 그래서 앞에 CDN을 둔다. CDN은 사용자와 가까운 도시마다 서버(엣지)를 두고 자주 받는 파일을 들고 있는 캐시망이다. 음원은 안 바뀌니 엣지에 오래 둬도 된다. 엣지가 어떻게 가까운 사용자를 받는지는 [CDN과 캐시 계층](/posts/sd-cache-and-cdn-tier)에 있다.

## 재생 버튼부터 첫 소리까지

그 주소는 서명된 URL이다. 아무나 CDN 주소를 알아내 음원을 받아 가면 안 되니, 웹 서버가 경로와 만료 시각에 비밀 키로 서명을 붙인다. 엣지는 같은 키로 서명을 다시 계산해 맞을 때만 파일을 준다. 아래 주소는 `demo-secret`이라는 연습용 키로 `HMAC-SHA256("/audio/201/160.ogg:1792832400")`을 실제로 계산해 만든 것이다. 실제 CDN마다 매개변수 이름과 서명 방식은 다르다.

## 곡을 조각으로 받는다

음원 하나는 6MB 정도라 동영상보다 훨씬 작다. 그래도 통째로 받지 않고 HTTP `Range` 요청으로 나눠 받는다. 중간으로 건너뛸 때 그 부분부터 받을 수 있고, 듣다가 넘기면 나머지를 안 받아도 되기 때문이다. 작은 node 서버에 6,000,000바이트짜리 파일을 두고 엣지처럼 잘라 주게 했다.

```js
// range-server.mjs 일부: Range 헤더가 있으면 그 구간만 206으로 돌려준다
const m = /^bytes=(\d+)-(\d*)$/.exec(req.headers.range ?? "");
const start = Number(m[1]);
const end = m[2] ? Math.min(Number(m[2]), size - 1) : size - 1;
if (start >= size) {
  res.writeHead(416, { "Content-Range": `bytes */${size}` });
  return res.end();
}
res.writeHead(206, {
  "Content-Range": `bytes ${start}-${end}/${size}`,
  "Content-Length": end - start + 1,
  "Cache-Control": "public, max-age=31536000, immutable",
});
```

```bash
# 첫 512KB, 끝부분, 파일보다 뒤를 차례로 요청해 응답 헤더만 본다
curl -s -o /dev/null -D - -r 0-524287 http://127.0.0.1:8091/track-160.ogg
curl -s -o /dev/null -D - -r 5767168- http://127.0.0.1:8091/track-160.ogg | head -3
curl -s -o /dev/null -D - -r 7000000- http://127.0.0.1:8091/track-160.ogg | head -2
```

```text
HTTP/1.1 206 Partial Content
Content-Type: audio/ogg
Content-Range: bytes 0-524287/6000000
Content-Length: 524288
Accept-Ranges: bytes
Cache-Control: public, max-age=31536000, immutable
Date: Wed, 21 Oct 2026 19:16:25 GMT
Connection: keep-alive
Keep-Alive: timeout=5

HTTP/1.1 206 Partial Content
Content-Type: audio/ogg
Content-Range: bytes 5767168-5999999/6000000
HTTP/1.1 416 Range Not Satisfiable
Content-Range: bytes */6000000
```

볼 곳은 `Content-Range`다. `bytes 0-524287/6000000`은 전체 6,000,000바이트 중 앞 524,288바이트를 줬다는 뜻이다. 끝부분을 열린 범위(`5767168-`)로 달라고 하면 서버가 파일 끝인 5,999,999까지 잘라 준다. 파일보다 뒤를 달라고 하면 416이다. 플레이어가 파일 크기를 잘못 알고 있을 때 이 응답이 로그에 쌓인다.

건너뛰기는 바이트 위치 계산이다. 고정 비트레이트(CBR) 160kbps면 1초가 20,000바이트이니 2분 30초 지점은 3,000,000바이트 근처다. 실제로 `-r 3000000-3524287`을 요청하면 206과 함께 524,288바이트가 왔다. 다만 Ogg Vorbis나 AAC를 가변 비트레이트(VBR)로 인코딩하면 시간과 바이트가 비례하지 않는다. 그래서 컨테이너의 색인(MP4의 `moov`, Ogg의 페이지 정보)을 먼저 읽거나 앞뒤를 몇 번 찔러 위치를 찾는다.

회선이 나빠지면 음질을 낮춘다. 동영상처럼 HLS나 DASH로 몇 초짜리 세그먼트를 만들어 조각마다 음질을 고르는 방법도 있고, 곡 단위로 "다음 곡은 낮은 음질로 받는다"처럼 단순하게 가는 방법도 있다. 음원은 작고 짧아서 곡 단위 전환으로도 충분할 때가 많다. 브라우저에서 HLS와 DASH의 목록 구조, 플레이어가 화질을 고르는 원리는 [동영상 ② 스트리밍과 비용](/posts/sd-video-streaming-cost)에서 이미 다뤘다. 이 글에서는 반복하지 않는다.

비용도 영상과 같은 공식이다. 전송량은 재생 수 × 듣는 시간 × 비트레이트다. 음원은 파일이 작아서 같은 엣지 디스크에 영상보다 훨씬 많은 곡을 담을 수 있다. 반대로 거의 안 듣는 꼬리 쪽 곡이 아주 많아서, 1억 곡 대부분은 엣지에 둘 필요가 없다. 인기 상위 몇 %만 엣지에 오래 두고 나머지는 요청이 올 때만 가져오게 한다.

## 곡 정보와 재생목록은 SQL에 둔다

메타데이터는 관계가 분명하다. 아티스트가 앨범을 내고, 앨범에 곡이 있고, 재생목록이 곡을 순서대로 가리킨다. 조인이 많고, 재생목록 순서를 바꾸는 쓰기는 트랜잭션이 필요하다. 70GB라면 관계형 DB 한 대로 시작해도 된다. PostgreSQL 16에서 뼈대를 만들어 봤다.

```sql
CREATE TABLE artists (id bigint PRIMARY KEY, name text NOT NULL);
CREATE TABLE albums  (id bigint PRIMARY KEY, artist_id bigint NOT NULL REFERENCES artists,
                      title text NOT NULL, released date);
CREATE TABLE tracks (
  id          bigint PRIMARY KEY,
  album_id    bigint NOT NULL REFERENCES albums,
  title       text   NOT NULL,
  duration_ms integer NOT NULL,
  audio_key   text   NOT NULL          -- 객체 저장소의 키. 파일 자체는 DB에 없다
);
CREATE TABLE playlists (id bigint PRIMARY KEY, owner_id bigint NOT NULL, name text NOT NULL);
CREATE TABLE playlist_tracks (
  playlist_id bigint REFERENCES playlists,
  position    integer,
  track_id    bigint NOT NULL REFERENCES tracks,
  PRIMARY KEY (playlist_id, position)
);

-- 재생목록 7번을 순서대로, 아티스트 이름까지 붙여 읽는다
SELECT pt.position, t.title, ar.name AS artist, t.duration_ms / 1000 AS sec, t.audio_key
FROM playlist_tracks pt
JOIN tracks t   ON t.id = pt.track_id
JOIN albums al  ON al.id = t.album_id
JOIN artists ar ON ar.id = al.artist_id
WHERE pt.playlist_id = 7
ORDER BY pt.position;
```

```text
 position |    title    |  artist  | sec | audio_key
----------+-------------+----------+-----+------------
        1 | Glow        | Lumen    | 201 | audio/201/
        2 | 첫차를 타고 | 새벽밴드 | 214 | audio/101/
        3 | 정류장      | 새벽밴드 | 187 | audio/102/
```

`audio_key`에는 파일이 아니라 저장소 안의 위치만 있다. 음질별 파일은 그 접두사 아래에 `96.ogg`, `160.ogg`처럼 붙는다. 곡 정보 70GB와 음원 600TB가 따로 노는 이유가 이 한 컬럼에 다 들어 있다.

읽기는 쓰기보다 훨씬 많다. 곡 정보는 거의 안 바뀌고, 재생목록도 보는 횟수가 고치는 횟수보다 수십 배 많다. 그래서 그림처럼 리더 한 대가 쓰기를 받고, 팔로워(복제본) 여러 대가 리더의 변경 기록을 따라 쓰며 읽기를 나눠 받는다. 복제가 어떻게 따라오는지, 리더가 죽으면 누가 이어받는지는 [DB 복제 입문](/posts/sd-db-replication-intro)에 있다.

70GB가 몇 TB로 커지거나, 재생목록 쓰기가 리더 한 대로 버거워지면 사용자 id로 재생목록 테이블을 나누는 샤딩을 고려한다. 곡 정보는 모두가 읽는 공유 데이터라 샤딩보다 캐시가 먼저다. 샤딩 키 고르는 법은 [샤딩 입문](/posts/sd-sharding-intro)에 있다.

## 검색은 따로 만든 색인에 묻는다

"glow"를 치면 곡 Glow, 앨범 Glow, Glow라는 단어가 들어간 재생목록이 함께 나와야 한다. 오타("glwo")도 어느 정도 받아 줘야 하고, 인기 있는 것이 위로 와야 한다. `WHERE title LIKE '%glow%'`로는 안 된다. 앞에 와일드카드가 붙으면 B-tree 인덱스를 못 쓰고, 순위도 매길 수 없다.

그래서 검색 전용 저장소에 역색인을 만든다. 단어마다 그 단어가 나오는 곡 id 목록을 미리 적어 두는 구조다. 역색인과 순위 계산은 [Elasticsearch 역색인](/posts/elasticsearch-inverted-index)에서 자세히 봤다. 검색창에 글자를 칠 때마다 후보를 보여 주는 자동 완성은 [자동 완성 ① 트라이](/posts/sd-autocomplete-trie)와 [자동 완성 ② 데이터 파이프라인](/posts/sd-autocomplete-data-pipeline)의 구조를 그대로 쓴다.

이 색인의 원본은 메타 DB다. 곡이 새로 들어오거나 제목이 고쳐지면 그 변경을 큐에 흘려 검색 색인이 따라 쓰게 한다. 그래서 새 곡이 검색에 나오기까지 몇 초에서 몇 분의 지연이 있다. 신곡 발매 시각에 맞춰 검색에 떠야 한다면, 발매 전에 색인에 넣어 두고 "공개 시각" 필드로 거르는 쪽이 안전하다.

## 많이 듣는 곡은 캐시에 둔다

음악 재생은 아주 한쪽으로 쏠린다. 차트 상위 곡, 큰 공식 재생목록, 신곡이 대부분의 요청을 받는다. 그 곡들의 정보를 매번 DB에서 읽을 필요가 없다. 웹 서버는 먼저 Redis 같은 캐시를 보고, 없으면 팔로워에서 읽어 캐시에 담는 cache-aside 방식을 쓴다. 캐시를 어디에 두고 언제 비우는지는 [CDN과 캐시 계층](/posts/sd-cache-and-cdn-tier)에서 봤다.

캐시에 둘 것은 성격에 따라 수명을 다르게 준다.

- 곡 정보와 앨범 정보: 거의 안 바뀐다. 몇 시간 수명을 주고, 고칠 때 키를 지운다.
- 공식 재생목록(차트, 장르별 목록): 하루 몇 번 바뀐다. 바뀌는 시점에 새로 계산해 덮어쓴다.
- 내 재생목록: 나만 본다. 캐시 이득이 작으니 팔로워에서 바로 읽어도 된다.

신곡이 0시에 공개되는 순간이 가장 위험하다. 수백만 명이 같은 곡 정보를 동시에 찾는데 캐시는 비어 있다. 이때 캐시 미스가 한꺼번에 DB로 몰리지 않게 공개 몇 분 전에 미리 채워 두고, 같은 키의 미스는 한 요청만 DB에 가게 묶는다. 음원 파일도 같은 이유로 발매 전에 엣지에 밀어 둔다.

## 지하철에서도 들리게: 내려받기와 DRM

유료 사용자는 곡을 기기에 내려받는다. 내려받은 파일이 그냥 ogg 파일이면 복사해서 남에게 줄 수 있으니, 음반사와의 계약상 암호화해 저장하는 것이 보통이다. 이렇게 재생 권한을 기술로 묶는 것을 DRM(디지털 권리 관리)이라고 한다. 아래는 일반적인 흐름이다. 실제 서비스의 키 관리 방식은 공개되지 않은 부분이 많아서, 구조만 보는 예로 읽어야 한다.

마지막 단계의 한도는 서비스마다 다르다. Spotify의 지원 문서는 오프라인 곡을 유지하려면 적어도 30일에 한 번 온라인에 접속해야 한다고 안내해 왔는데, 정책은 바뀔 수 있다. 설계 면접에서는 숫자보다 "키에 만료를 붙이고 주기적으로 갱신한다"는 구조를 말하면 된다.

DRM이 완벽하지는 않다. 재생하는 순간 소리는 결국 스피커로 나가고, 기기를 장악한 사람은 복호화된 데이터를 가로챌 수 있다. DRM은 복사를 불가능하게 만드는 게 아니라 손쉬운 복사를 막는 장치다. 브라우저 쪽에서는 EME(Encrypted Media Extensions)와 Widevine, FairPlay 같은 플랫폼 DRM을 쓰는데, 어느 것을 쓸 수 있는지는 브라우저와 운영체제에 따라 다르다.

기기에 쌓아 둔 재생 기록이 다음 절과 이어진다. 오프라인에서 들은 곡도 정산 대상이라, 나중에 몰아서 올라온 기록을 중복 없이 세야 한다.

## 재생 한 번이 정산서의 한 줄이 되기까지

곡 재생은 권리자에게 돈으로 돌아간다. 그래서 재생 수는 틀리면 안 되는 숫자다. 처음 설계처럼 `plays = plays + 1`을 DB에 바로 쓰면 초당 2만 건이 인기곡 몇 행에 몰린다. 재생 기록은 큐(메시지를 쌓아 두는 줄)에 넣고, 뒤에서 여러 소비자가 나눠 읽어 집계한다. 큐의 동작은 [Kafka 기초](/posts/kafka-basics)에서 봤다.

같은 이벤트가 세 갈래로 간다. 실시간 집계는 몇 초 늦게라도 대략 맞으면 된다. 차트나 아티스트 대시보드에 쓴다. 원본 로그는 모든 이벤트를 그대로 객체 저장소에 쌓는다. 정산은 하루가 끝난 뒤 이 원본 로그를 처음부터 다시 세서 만든다. 빠른 숫자와 정확한 숫자를 다른 길로 만드는 것이다.

정확하게 세려면 두 가지를 걸러야 한다. 하나는 중복이다. 앱이 이벤트를 보냈는데 응답을 못 받으면 다시 보내고, 소비자가 처리 후 오프셋을 저장하기 전에 죽으면 같은 이벤트를 다시 받는다. 큐는 보통 "적어도 한 번" 전달하기 때문이다. 다른 하나는 재생으로 치지 않는 짧은 재생이다. 업계에서는 30초 이상 들어야 한 번으로 센다는 기준이 널리 알려져 있다. 실제 정산 규칙은 계약마다 다르니 여기서는 가정이다.

그래서 앱이 재생마다 고유한 `playId`를 만들어 붙인다. 소비자는 이미 센 `playId`를 기억해 두고 다시 오면 건너뛴다. node로 흉내 냈다.

```js
// plays.mjs: 재생 이벤트가 큐에서 두 번 오더라도 곡별 재생 수를 한 번씩만 센다
const delivered = [
  { playId: "p1", track: "t42", ms: 183000 },
  { playId: "p2", track: "t42", ms: 12000 },   // 12초만 듣고 넘김
  { playId: "p3", track: "t7",  ms: 95000 },
  { playId: "p1", track: "t42", ms: 183000 },  // 앱이 응답을 못 받아 다시 보냄
  { playId: "p4", track: "t42", ms: 30000 },   // 딱 30초
  { playId: "p3", track: "t7",  ms: 95000 },   // 소비자가 커밋 전에 죽어 다시 받음
  { playId: "p5", track: "t7",  ms: 29999 },
];
const naive = {}, exact = {}, seen = new Set();
for (const e of delivered) {
  naive[e.track] = (naive[e.track] ?? 0) + 1;
  if (e.ms < 30000) continue;          // 30초 미만은 재생으로 치지 않는다
  if (seen.has(e.playId)) continue;    // 이미 센 재생
  seen.add(e.playId);
  exact[e.track] = (exact[e.track] ?? 0) + 1;
}
console.log("받은 이벤트:", delivered.length);
console.log("그냥 센 값 :", naive);
console.log("걸러 센 값 :", exact);
```

```text
받은 이벤트: 7
그냥 센 값 : { t42: 4, t7: 3 }
걸러 센 값 : { t42: 2, t7: 1 }
```

받은 이벤트 7건을 그냥 세면 7회, 거르면 3회다. 정산서에 7이 찍히면 권리자에게 두 배 넘게 지급한다. 같은 과정을 한 칸씩 따라가 보자.

실제로는 "이미 센 번호" 집합이 메모리에 무한히 쌓일 수 없다. 그래서 하루 단위로 끊고, 결과와 처리 위치(오프셋)를 같은 트랜잭션에 저장해 재시작해도 두 번 더하지 않게 만든다. 하루가 끝나면 원본 로그로 다시 세어 실시간 숫자와 맞춰 본다. 오프셋을 언제 저장하는지, 결과와 책갈피를 어떻게 한곳에 두는지, 대조는 어떻게 하는지는 [광고 클릭 집계 ② 정확히 한 번](/posts/sd-ad-click-exactly-once)에 같은 문제로 자세히 있다. 음악 재생 정산은 그 글의 클릭을 재생으로 바꾸면 거의 그대로다.

오프라인 재생 기록은 며칠 늦게 몰려온다. 이벤트에는 서버가 받은 시각이 아니라 기기에서 들은 시각을 적고, 정산 마감을 며칠 늦게 잡거나 늦게 온 기록을 다음 정산에 보정으로 넣는다. 기기 시계를 조작한 기록이나 같은 계정이 사람이 들을 수 없는 속도로 쌓는 재생은 부정 재생으로 걸러야 하는데, 이건 규칙과 모델이 계속 바뀌는 영역이라 여기서는 이름만 적어 둔다.

## 추천은 밤사이 만들어 둔다

원본 로그에는 누가 무엇을 언제 끝까지 들었는지, 어디서 넘겼는지가 다 있다. 추천은 이 로그로 만든다. 비슷한 곡을 들은 사람끼리 묶는 협업 필터링, 곡의 소리 특징이나 장르로 묶는 방법을 섞는 것이 일반적이다.

설계에서 중요한 건 언제 계산하느냐다. 매주 바뀌는 개인 추천 재생목록 같은 것은 밤사이 배치로 모든 사용자 몫을 계산해 키-값 저장소에 넣어 두고, 앱이 열면 읽기만 한다. "방금 들은 곡과 비슷한 다음 곡"처럼 바로 반응해야 하는 것은 미리 계산해 둔 곡별 이웃 목록에서 고른다. 요청할 때마다 모델을 돌리지 않으니 읽기 경로는 캐시처럼 빠르다. 곡을 벡터로 바꿔 가까운 곡을 찾는 방식은 [벡터 DB](/posts/vector-db)과 이어진다.

## 어디부터 터지나

설계를 다 그린 뒤 면접관이 묻는 장애를 미리 짚어 본다.

CDN 한 곳이 느려지면 재생 시작이 늦어진다. 앱은 첫 조각 응답 시간과 끊김 횟수를 지표로 올리고, 서버는 그 지표로 다른 CDN이나 다른 엣지로 보낸다. 여러 CDN을 섞어 쓰는 이유다.

메타 DB 리더가 죽으면 재생목록 수정만 멈추고 재생은 계속된다. 팔로워를 승격하는 동안의 쓰기 실패는 앱이 재시도하게 둔다.

큐가 밀리면 실시간 차트가 늦어진다. 재생에는 영향이 없다. 큐 길이(소비자 지연)를 지표로 보고 소비자를 늘린다. 정산은 원본 로그에서 다시 세니 결과는 틀리지 않는다.

검색 색인이 망가지면 메타 DB에서 다시 만든다. 원본이 DB이고 색인은 복사본이라서 가능하다. 이것도 다시 만드는 데 몇 시간이 걸릴 수 있으니 색인을 두 벌 두고 바꿔 끼운다.

## 면접에서 나올 만한 질문

### 음원 파일과 곡 정보를 왜 다른 곳에 저장하나요?

크기와 접근 방식이 완전히 달라서다. 1억 곡이면 음원은 수백 TB에서 PB 단위지만 곡 정보는 수십 GB다. 음원은 키로 통째로 읽는 큰 파일이라 객체 저장소와 CDN이 맞고, 곡 정보는 조인과 트랜잭션이 필요한 작은 행이라 관계형 DB가 맞다. DB에는 파일 위치만 둔다.

### 1억 곡의 저장 용량을 어림해 보세요.

곡당 크기는 비트레이트 × 길이 ÷ 8이다. 160kbps로 5분이면 6MB라서 한 벌에 600TB, 96/160/320kbps 세 벌을 3분 30초 기준으로 두면 약 1.5PB다. 여기에 저장소의 복제나 이레이저 코딩 여유를 곱한다. 메타데이터는 곡당 1KB 안쪽이라 100GB 안팎이다.

### 재생을 누르고 1초 안에 소리가 나게 하려면요?

웹 서버는 권한 확인과 서명된 URL 발급만 하고, 소리는 가까운 CDN 엣지에서 받는다. 파일 전체가 아니라 `Range`로 앞부분 수백 KB만 먼저 받아 바로 재생한다. 인기곡은 엣지에 미리 두고, 재생목록의 다음 곡 첫 조각은 미리 받아 둔다.

### 재생 중 중간으로 건너뛰면 어떻게 동작하나요?

그 시각에 해당하는 바이트 위치부터 `Range` 요청을 보낸다. 고정 비트레이트면 시간 × 초당 바이트로 바로 계산되고, 가변 비트레이트면 컨테이너의 색인을 보거나 몇 번 찔러 위치를 찾는다. 서버는 206 Partial Content와 `Content-Range`로 답하고, 범위가 파일 밖이면 416을 준다.

### 재생 수를 DB의 카운터 컬럼으로 바로 올리면 안 되나요?

초당 수만 건이 인기곡 몇 행에 몰려 잠금 경합이 생기고, 재시도로 생긴 중복도 걸러지지 않는다. 재생 이벤트를 큐에 넣고 소비자가 나눠 집계한다. 실시간 숫자는 대략으로 두고, 정산용 숫자는 원본 로그를 다시 세서 만든다.

### 정산용 재생 수를 정확하게 세려면 무엇을 하나요?

재생마다 앱이 고유한 id를 붙이고, 소비자는 이미 센 id를 건너뛴다. 집계 결과와 큐 오프셋을 같은 트랜잭션에 저장해 재시작해도 두 번 더하지 않는다. 30초 미만 재생처럼 규칙에 안 맞는 것은 거르고, 하루가 끝나면 원본으로 다시 세어 대조한다.

### 신곡이 0시에 공개되면서 트래픽이 10배로 뛰면요?

음원은 공개 전에 엣지에 밀어 두고, 곡 정보는 캐시를 미리 채워 둔다. 같은 키의 캐시 미스는 하나로 묶어 DB에 한 번만 가게 한다. 재생 이벤트는 큐가 받아 주니 집계가 늦어질 뿐 재생은 영향받지 않는다.

### 오프라인 재생에서 구독이 끝난 사용자는 어떻게 막나요?

파일은 암호화해 저장하고, 기기에 묶인 키에 만료를 붙인다. 앱이 주기적으로 온라인에서 키를 갱신하게 하고, 그때 구독이 끝났으면 키를 무효로 만든다. 그래서 오프라인으로 버틸 수 있는 기간에 한도를 둔다. DRM은 복사를 완전히 막지 못하고 손쉬운 복사를 막을 뿐이니, 그 한계도 같이 말한다.
