관리자 화면에 "이번 달 결제 완료 주문, 금액 큰 순 20개"라는 목록이 하나 생겼다. 주문 테이블과 주문 상품 테이블을 조인해서 금액을 더하고, 정렬해서 위에서 20개를 자르는 쿼리다. 주문이 20만 건쯤 되자 이 목록 하나가 1초 가까이 걸린다. 마이페이지의 "내 주문" 목록도 비슷한 조인을 하고, 그 화면을 위해 주문 엔티티에 `itemCount`, `firstItemName`, `displayStatus` 같은 필드가 하나씩 붙어 갔다. 주문을 바꾸는 코드가 화면 때문에 점점 무거워진다.

이 글은 이 문제를 "바꾸는 모델과 읽는 모델을 나눠서" 푸는 CQRS(Command Query Responsibility Segregation)를 본다. 왜 나누는지, 얼마나 멀리 나눌지, 읽기 모델을 채우는 프로젝터를 어떻게 짜는지, 그리고 나누는 순간 생기는 "방금 바꾼 게 안 보인다"를 어떻게 받아 내는지가 순서다. 예제는 Node 22와 PGlite 0.2.17(PostgreSQL 16.4를 WebAssembly로 빌드한 것)에서 돌린 실제 출력이다.

이 주제의 다른 글: 상태 대신 사건을 저장하는 방식은 [이벤트 소싱](/posts/event-sourcing), 바뀐 사실을 브로커로 빠짐없이 내보내는 방법은 [트랜잭셔널 아웃박스](/posts/transactional-outbox), 서비스 사이에서 이벤트를 주고받는 큰 그림은 [이벤트 기반 아키텍처](/posts/event-driven-architecture)에 있다. 여기서는 한 서비스 안에서 쓰기와 읽기를 가르는 일만 본다.

## 주문 목록 하나가 870ms 걸린다

예제의 쓰기 모델은 평범한 정규화 테이블이다. 주문(`orders`) 20만 건, 주문 상품(`order_items`) 60만 건, 상품(`products`) 500개다.

```sql
CREATE TABLE products (id int PRIMARY KEY, name text NOT NULL, price int NOT NULL);
CREATE TABLE orders (
  id bigserial PRIMARY KEY, user_id int NOT NULL, status text NOT NULL,
  version int NOT NULL DEFAULT 1, created_at timestamptz NOT NULL);
CREATE TABLE order_items (
  order_id bigint NOT NULL REFERENCES orders(id), product_id int NOT NULL REFERENCES products(id),
  qty int NOT NULL, price int NOT NULL);
CREATE INDEX ON order_items (order_id);
CREATE INDEX ON orders (user_id, created_at DESC);
```

관리자 목록 쿼리와 실행 계획이다.

```sql
EXPLAIN (ANALYZE, COSTS OFF)
SELECT o.id, o.user_id, sum(i.qty * i.price) AS total, count(*) AS lines
FROM orders o JOIN order_items i ON i.order_id = o.id
WHERE o.status = 'paid' AND o.created_at >= timestamptz '2026-10-01'
GROUP BY o.id
ORDER BY total DESC   -- 합계로 정렬하니 모든 후보 주문의 합계를 먼저 구해야 한다
LIMIT 20;
```

볼 줄은 둘이다. `order_items`를 60만 행 전부 읽었고(`rows=600000`), 그 위에서 주문 24,615개의 합계를 만든 뒤(`HashAggregate ... rows=24615`) 20개만 남겼다. 정렬 기준인 `total`이 테이블 어디에도 저장돼 있지 않으니, 위에서 20개를 고르려면 후보 전부의 합계를 먼저 계산할 수밖에 없다. 인덱스를 더 붙여도 "합계 순서"를 담은 인덱스는 만들 수 없다.

쓰기 쪽에서 보면 이 테이블들은 잘 설계됐다. 주문 상품의 가격은 한 곳에만 있고, 주문을 취소하면 `orders` 한 행만 바뀐다. 문제는 읽기가 원하는 모양(주문당 한 줄, 합계 포함, 합계 순)과 쓰기가 지키려는 모양(중복 없는 정규화)이 다르다는 데 있다.

## 바꾸는 길과 읽는 길을 나눈다

출발점은 버트런드 마이어가 정리한 CQS(Command Query Separation)다. 메서드는 상태를 바꾸는 명령이거나 값을 돌려주는 조회 중 하나여야 하고, 둘을 섞지 않는다. 그렉 영이 2010년 무렵 이 생각을 메서드가 아니라 모델 단위로 넓힌 게 CQRS다. 상태를 바꾸는 요청(명령)은 쓰기 모델이 받고, 화면을 그리는 요청(조회)은 따로 만든 읽기 모델이 받는다.

- 명령(command)은 "주문해 줘", "이 주문을 취소해 줘" 같은 의도다. 업무 규칙을 검사하고 거절할 수 있다. 돌려주는 건 성공 여부와 새로 생긴 ID, 버전 정도다.
- 조회(query)는 상태를 바꾸지 않는다. 화면 하나가 원하는 모양을 그대로 돌려준다. 업무 규칙이 없다.

명령 쪽은 업무 규칙을 지키는 데만 집중하고, 조회 쪽은 화면이 원하는 모양을 미리 만들어 두는 데만 집중한다. 쓰기 모델에서 `itemCount` 같은 화면용 필드를 걷어 낼 수 있고, 읽기 모델은 화면마다 하나씩 따로 둘 수 있다. 관리자 목록용, 마이페이지용, 검색용 읽기 모델이 서로 다른 저장소에 있어도 된다.

나누면 읽기와 쓰기를 따로 키울 수도 있다. 대부분의 서비스는 읽기가 쓰기보다 훨씬 많으니 읽기 모델만 복제본이나 캐시, 검색 엔진으로 늘린다. [읽기 복제본](/posts/db-replication-sharding)을 붙이는 것과 비슷해 보이지만 다르다. 복제본은 같은 테이블의 사본이고, 읽기 모델은 모양부터 다른 테이블이다.

첫 단계는 코드만 나누는 것이다. 같은 DB, 같은 테이블을 쓰지만 명령 처리기와 조회 처리기를 따로 두고, 조회는 ORM 엔티티 대신 화면용 DTO를 SQL로 바로 만든다. 데이터는 하나라 지연이 없다. 이것만으로도 엔티티에 화면용 필드가 붙는 일은 멈춘다. 앞의 870ms는 그대로다.

두 번째는 같은 DB 안에 읽기용 테이블을 두고 명령과 같은 트랜잭션에서 함께 고치는 것이다. 읽기 모델이 항상 최신이고, 성능 문제도 풀린다. 대신 명령 처리기가 읽기 모델을 알아야 하고, 읽기 모델이 늘수록 명령 하나가 고칠 테이블이 늘어 쓰기가 느려진다. PostgreSQL의 머티리얼라이즈드 뷰를 주기적으로 갱신하는 것도 이 단계에 가깝다(`REFRESH MATERIALIZED VIEW CONCURRENTLY`, 갱신하는 동안 읽기를 막지 않으려면 유일 인덱스가 필요하다. [PostgreSQL다운 SQL](/posts/postgres-advanced-sql) 참고). 다만 갱신이 뷰 전체를 다시 계산해서 데이터가 크면 무겁다.

세 번째는 이 글의 예제다. 명령은 쓰기 모델과 "무엇이 바뀌었나"라는 사건만 남기고, 따로 도는 프로젝터가 그 사건을 읽어 읽기 모델을 고친다. 명령 처리기는 읽기 모델을 전혀 모른다. 읽기 모델을 다른 DB나 Elasticsearch, Redis에 둘 수 있다. 대가는 지연이다. 명령이 끝난 순간과 읽기 모델에 보이는 순간 사이에 틈이 생긴다.

네 번째는 쓰기 모델 자체를 사건의 목록으로 저장하는 [이벤트 소싱](/posts/event-sourcing)과 합치는 것이다. 이때는 상태 테이블이 아예 없으니 조회는 반드시 읽기 모델에서 해야 한다. CQRS가 이벤트 소싱을 요구하지는 않지만, 이벤트 소싱은 사실상 CQRS를 요구한다.

대부분은 첫 단계면 충분하다. 두 번째, 세 번째로 넘어가는 신호는 숫자로 잡는다. 조회 쿼리가 인덱스로 풀리지 않는 집계·정렬을 하고 p95가 목표를 넘는다, 읽기 트래픽이 쓰기의 수십 배라 같은 DB에서 서로 방해한다, 같은 데이터를 전혀 다른 모양(전문 검색, 통계)으로 읽어야 한다. 이 중 하나가 보일 때 나눈다.

## 명령 처리기는 사실을 남기고 끝난다

세 번째 단계를 직접 짜 보자. 명령 처리기는 주문을 쓰고, 같은 트랜잭션에서 `order_events`에 사건을 하나 남긴다.

```sql
-- 상태를 바꾼 사실. 명령 처리와 같은 트랜잭션에 쌓인다
CREATE TABLE order_events (
  position bigserial PRIMARY KEY,           -- 프로젝터가 어디까지 읽었는지 가리킬 번호
  order_id bigint NOT NULL,
  version  int    NOT NULL,                 -- 이 주문의 몇 번째 변경인지
  type     text   NOT NULL,
  data     jsonb  NOT NULL,
  UNIQUE (order_id, version)
);
```

```js
async function cancelOrder(orderId, expectedVersion) {
  return db.transaction(async (tx) => {
    // 업무 규칙: 결제 완료 상태이고, 내가 본 버전 그대로일 때만 취소한다
    const r = await tx.query(
      `UPDATE orders SET status = 'cancelled', version = version + 1
       WHERE id = $1 AND version = $2 AND status = 'paid' RETURNING version`,
      [orderId, expectedVersion]);
    if (r.rows.length === 0)
      throw new Error(`order ${orderId}: version ${expectedVersion} is stale or not cancellable`);
    // 바뀐 사실을 같은 트랜잭션에 남긴다
    const { rows: [e] } = await tx.query(
      `INSERT INTO order_events (order_id, version, type, data)
       VALUES ($1, $2, 'OrderCancelled', '{}') RETURNING position`,
      [orderId, r.rows[0].version]);
    return { orderId, position: Number(e.position) };   // 읽기 쪽을 기다릴 때 쓸 번호
  });
}
```

명령이 돌려주는 값은 화면 데이터가 아니라 `position`이다. 이 번호가 나중에 "읽기 모델이 내 명령까지 따라왔나"를 확인하는 기준이 된다. `expectedVersion`은 사용자가 화면에서 본 버전이다. 그 사이 누가 먼저 바꿨으면 `UPDATE`가 0행이 되어 명령이 거절된다. [낙관적 잠금](/posts/optimistic-locking)과 같은 원리다.

명령 하나에 실리는 값을 조각으로 나눠 보면 각자 맡은 일이 있다. 조각을 눌러 보자.

## 프로젝터가 읽기 모델을 채운다

읽기 모델은 관리자 목록이 원하는 모양 그대로다. 주문당 한 줄, 합계와 상품 수와 대표 상품명이 미리 계산돼 있고, 정렬 순서대로 인덱스가 있다.

```sql
CREATE TABLE order_summaries (
  order_id bigint PRIMARY KEY, user_id int NOT NULL, status text NOT NULL,
  total int NOT NULL, item_count int NOT NULL, first_item text NOT NULL,
  created_at timestamptz NOT NULL,
  version int NOT NULL                       -- 마지막으로 반영한 주문 버전
);
CREATE INDEX ON order_summaries (status, total DESC);   -- 관리자 목록용
CREATE INDEX ON order_summaries (user_id, created_at DESC); -- 마이페이지용
CREATE TABLE projector_checkpoints (name text PRIMARY KEY, position bigint NOT NULL);
```

프로젝터는 체크포인트 뒤의 사건을 순서대로 읽어 요약 행을 고치고, 마지막으로 읽은 위치를 저장한다. 여기서는 읽기 모델이 같은 DB에 있어서 요약 행 수정과 체크포인트 저장을 한 트랜잭션으로 묶었다.

```js
async function projectOnce(batch = 100) {
  return db.transaction(async (tx) => {
    const { rows: [cp] } = await tx.query(
      "SELECT position FROM projector_checkpoints WHERE name = 'order_summaries' FOR UPDATE");
    const { rows } = await tx.query(
      "SELECT * FROM order_events WHERE position > $1 ORDER BY position LIMIT $2", [cp.position, batch]);
    for (const e of rows) {
      if (e.type === "OrderCancelled") {
        // 이미 더 새로운 버전을 반영했으면 아무것도 하지 않는다
        await tx.query(
          "UPDATE order_summaries SET status = 'cancelled', version = $2 WHERE order_id = $1 AND version < $2",
          [e.order_id, e.version]);
      }
      // OrderPlaced는 INSERT ... ON CONFLICT DO UPDATE ... WHERE version < EXCLUDED.version
    }
    if (rows.length)
      await tx.query("UPDATE projector_checkpoints SET position = $1 WHERE name = 'order_summaries'",
        [rows.at(-1).position]);
    return rows.length;
  });
}
```

주문을 하나 넣고, 프로젝터가 돌기 전과 후에 조회해 봤다.

## 같은 쿼리, 읽기 모델에서

처음의 관리자 목록을 읽기 모델에 다시 던졌다.

869.7ms가 0.86ms가 됐다. 조인도 집계도 정렬도 없다. `(status, total DESC)` 인덱스를 큰 금액부터 따라가다가 날짜 조건에 맞는 20개를 찾으면 멈춘다. 10월 이전 주문 212개를 건너뛰었다는 `Rows Removed by Filter: 212`가 이 쿼리가 하는 일의 전부다. 결과도 같은 금액(116408원)의 주문들이 나온다.

같은 금액끼리 순서가 다른 건 두 쿼리 모두 동점 처리 기준이 없어서다. 화면에 페이지가 있다면 `ORDER BY total DESC, order_id`처럼 끝에 유일한 열을 붙이고 인덱스도 맞춘다.

대가도 숫자로 보인다. 읽기 모델은 쓰기 모델의 일부를 한 번 더 저장하니 디스크를 더 쓰고, 인덱스 두 개만큼 프로젝터의 쓰기가 무거워진다. 주문 상품 이름이 바뀌면 `first_item`을 가진 요약 행을 모두 고쳐야 한다. 읽기 모델은 "자주 읽고 드물게 바뀌는 것"을 미리 계산해 두는 장치라서, 원본이 자주 바뀌는 값을 담을수록 손해다.

## 방금 취소했는데 목록엔 결제 완료

세 번째 단계에서는 명령과 조회 사이에 틈이 있다. 관리자가 주문을 취소하고 목록으로 돌아왔는데 그 주문이 여전히 "결제 완료"로 보이면, 취소가 안 된 줄 알고 다시 누른다. 두 번째 취소는 버전이 맞지 않아 거절된다.

```text
command  : { orderId: 200001, position: 2 }
again    : order 200001: version 1 is stale or not cancellable
```

이 틈을 받아 내는 방법은 여러 가지다. 서버에서 기다리는 방법은 명령이 돌려준 `position`을 들고, 읽기 모델의 체크포인트가 그 위치를 넘을 때까지 짧게 기다렸다가 조회하는 것이다. 예제에서는 프로젝터가 50ms 뒤에 돌게 하고 기다려 봤다.

```js
async function waitForPosition(position, timeoutMs = 2000) {
  const start = Date.now();
  while (Date.now() - start < timeoutMs) {
    const { rows: [cp] } = await db.query(
      "SELECT position FROM projector_checkpoints WHERE name = 'order_summaries'");
    if (Number(cp.position) >= position) return true;   // 내 명령까지 반영됐다
    await new Promise((r) => setTimeout(r, 20));
  }
  return false;   // 시간 안에 못 따라왔다. 화면에 '반영 중'을 보여 준다
}

setTimeout(() => projectOnce(), 50);
const t0 = Date.now();
console.log("waited   :", await waitForPosition(c.position), `${Date.now() - t0}ms`);
console.log("query    :", await findSummary(placed.orderId));
```


기다리는 방법은 프로젝터가 멈추면 모든 명령이 타임아웃까지 기다린다는 약점이 있다. 그래서 타임아웃을 짧게 두고, 넘기면 기다리지 않고 "반영 중"을 보여 준다. 다른 방법도 있다.

- 명령의 응답에 바뀐 결과를 실어 보내고, 화면이 그걸 먼저 반영한다.
- 방금 명령을 보낸 사용자의 조회만 쓰기 모델로 보낸다. 몇 초 동안만 그렇게 하고 다시 읽기 모델로 돌린다.
- 화면이 아예 "처리 중" 상태를 정식으로 보여 준다. 송금이나 환불처럼 원래 시간이 걸리는 일에 맞다.

이 문제는 데이터베이스 복제본에서 생기는 "방금 쓴 걸 못 본다"와 같은 종류다. 사용자 한 명에게 무엇을 보장할지는 [최종 일관성과 세션 보장](/posts/eventual-consistency)에서 더 자세히 다룬다.

React 쪽 코드에도 같은 구분이 이미 있다. TanStack Query의 `useMutation`은 명령이고 `useQuery`는 조회다. 취소 버튼의 `onSuccess`에서 목록 쿼리를 `invalidateQueries`로 무효화하면, 서버의 읽기 모델이 아직 따라오지 못했을 때 옛 목록을 다시 받아 오는 일이 생긴다. 그래서 명령 응답으로 받은 상태를 `setQueryData`로 캐시에 먼저 넣고, 무효화는 조금 뒤에 하거나 서버가 `position`을 기다린 뒤 응답하게 맞춘다. 캐시를 갱신하는 방법들은 [클라이언트 데이터 캐시](/posts/client-data-cache)에 있다.

## 두 번 반영되는 프로젝션

예제처럼 읽기 모델과 체크포인트가 같은 DB에 있으면 둘을 한 트랜잭션으로 묶을 수 있다. 읽기 모델이 Elasticsearch나 Redis처럼 다른 저장소에 있으면 그럴 수 없다. 반영한 뒤 체크포인트를 저장하기 전에 프로젝터가 죽으면, 다시 뜬 프로젝터는 같은 사건을 또 읽는다.

일별 매출 읽기 모델을 따로 띄운 PGlite에 두고 실험했다. 2번 사건을 반영한 직후 죽게 하고 다시 돌렸다. 하나는 `total = total + 금액`으로 더하고, 하나는 행마다 마지막으로 반영한 position을 적어 두고 그보다 큰 사건만 더한다.

```sql
-- 더하기만 하는 프로젝션
INSERT INTO daily_sales (day, total) VALUES ($1, $2)
ON CONFLICT (day) DO UPDATE SET total = daily_sales.total + EXCLUDED.total;

-- 반영한 위치를 함께 적는 프로젝션
INSERT INTO daily_sales VALUES ($1, $2, $3)
ON CONFLICT (day) DO UPDATE
  SET total = daily_sales.total + EXCLUDED.total, last_position = EXCLUDED.last_position
  WHERE daily_sales.last_position < EXCLUDED.last_position;  -- 이미 본 사건이면 건너뛴다
```

```text
naive attempt 1: crashed before checkpoint
naive { day: '2026-10-21', total: 39636 }
guarded attempt 1: crashed before checkpoint
guarded { day: '2026-10-21', total: 19818 }
expected total: 19818
```

더하기만 한 쪽은 39636원이다. 체크포인트가 0에 머물러 있으니 두 번째 시도에서 1번과 2번 사건을 모두 다시 더했다. 위치를 적어 둔 쪽은 다시 읽어도 이미 본 사건을 건너뛰어 맞는 값이 나온다. 이 방법은 한 행에 사건이 position 순서대로 들어온다는 전제가 있어서, 프로젝터를 여러 개 띄워 나눠 처리하면 깨진다. 여러 개로 늘릴 때는 주문 ID로 사건을 나눠 한 주문은 늘 같은 프로젝터가 맡게 한다.

그래서 프로젝션은 "같은 사건을 다시 받아도 결과가 같게" 짠다. 덮어쓰기(`status = 'cancelled'`)는 원래 그렇고, 더하기·빼기처럼 누적하는 값은 반영한 위치나 버전을 함께 저장한다. 사건 전달이 왜 "적어도 한 번"인지는 [메시지 전달 보장](/posts/message-delivery-semantics)에서 다룬다.

직접 짜 보자. 사건 목록을 받아 주문별 요약을 만드는 프로젝터다. 사건은 순서가 섞여 올 수 있고, 이미 반영한 사건(체크포인트 이하)이 다시 올 수도 있다. 넘겨받은 상태는 고치지 말고 새 상태를 돌려준다.

## 읽기 모델은 언제든 버리고 다시 만든다

읽기 모델은 원본이 아니다. 원본은 쓰기 모델과 사건이고, 읽기 모델은 거기서 계산한 결과다. 그래서 프로젝터에 버그가 있었거나 화면이 새 열을 원하면 읽기 모델을 고치는 대신 다시 만든다.

다시 만들 때 쓰는 순서는 이렇다. 새 테이블 `order_summaries_v2`를 만들고, 새 프로젝터를 체크포인트 0에서 돌린다. 사건이 처음부터 남아 있지 않다면 예제의 첫 적재처럼 쓰기 모델에서 한 번에 채운 뒤 그 시점의 position부터 이어 간다. v2가 현재 position을 따라잡으면 조회를 v2로 돌리고, 문제가 없으면 v1과 옛 프로젝터를 지운다. 배포에서 블루·그린을 하는 것과 같은 모양이고, 그동안 v1이 계속 서비스한다.

여기서 흔한 실수 둘이 있다. 하나는 사건을 오래 보관하지 않는 것이다. 사건 테이블을 일주일 뒤 지운다면 다시 만들 때 쓰기 모델에서 채우는 길을 꼭 남겨 둔다. 다른 하나는 프로젝터가 사건 밖의 현재 값을 읽는 것이다. 예제의 프로젝터는 상품 이름을 `products` 테이블에서 읽는다. 다시 만들 때는 그 시점의 이름이 아니라 오늘의 이름이 들어간다. 이름이 바뀔 수 있고 과거 이름이 중요하다면 사건에 이름을 담는다.

## 나누지 않는 편이 나은 경우

화면이 테이블 모양과 거의 같은 CRUD 서비스에는 CQRS가 짐이다. 관리 도구, 설정 화면, 작은 사내 서비스가 그렇다. 테이블이 둘이 되고, 프로젝터라는 움직이는 부품이 생기고, 지연을 화면이 감당해야 한다.

쓰기 직후 반드시 최신 값을 읽어야 하는 흐름도 맞지 않는다. 재고를 확인하고 바로 차감하는 일은 읽기 모델을 보고 결정하면 안 된다. 명령 처리기는 판단에 필요한 값을 항상 쓰기 모델에서 읽는다. 읽기 모델은 사람이 보는 화면용이다.

그리고 시스템 전체에 거는 패턴이 아니다. 같은 서비스 안에서도 느린 목록 화면 하나만 읽기 모델로 빼고, 나머지는 평범한 테이블 조회로 둔다. 한 서비스 전체를 CQRS로 짜고 나서 대부분의 읽기 모델이 테이블과 똑같은 모양인 걸 발견하는 일이 흔하다.

## 읽기 화면이 이상할 때 보는 순서

"취소했는데 목록에 그대로다", "합계가 실제보다 크다" 같은 문의가 오면 이 순서로 본다.

먼저 프로젝터가 얼마나 밀렸는지 본다. 사건의 마지막 위치와 체크포인트의 차이가 지연이다.

```sql
-- 쌓인 사건과 읽기 모델이 반영한 위치의 차이
SELECT (SELECT max(position) FROM order_events) - position AS lag_events
FROM projector_checkpoints WHERE name = 'order_summaries';
```

차이가 계속 커지면 프로젝터가 멈췄거나 느리다. 같은 사건에서 계속 실패하고 있다면 그 사건의 데이터가 프로젝터가 예상하지 못한 모양인 것이다. 이 숫자를 지표로 내보내고 몇 초 이상이면 알림을 건다.

차이가 0인데 값이 틀리면 프로젝션 코드나 중복 반영을 의심한다. 그 주문의 사건을 쓰기 쪽에서 처음부터 다시 접어 본 값과 읽기 모델의 값을 비교한다. 다르면 앞 절의 "두 번 반영"이나 사건 밖의 값을 읽는 문제다. 고친 뒤에는 그 행만 손으로 고치지 말고 읽기 모델을 다시 만든다. 손으로 고친 행은 다음 재생성 때 또 틀어진다.

마지막으로 명령이 실제로 성공했는지 본다. 쓰기 모델에 버전이 올라갔는지, 사건이 남았는지 확인한다. 명령 처리기가 쓰기 모델만 고치고 사건을 빠뜨리는 버그가 있으면, 읽기 모델은 영원히 그 변경을 모른다. 쓰기와 사건을 한 트랜잭션에 두는 이유가 이것이다.

## 명령과 조회가 다른 질문에 답할 때

CQRS는 "쓰기가 지키려는 모양과 읽기가 원하는 모양이 다르다"는 사실을 인정하는 구조다. 쓰기 모델은 규칙과 불변식을 지키고 사건을 남긴다. 읽기 모델은 화면 하나를 위해 미리 계산된 테이블이고, 언제든 버리고 다시 만든다. 그 사이의 지연은 position과 체크포인트로 재고, 화면에서 받아 낸다. 다음 글인 [이벤트 소싱](/posts/event-sourcing)은 쓰기 모델까지 사건으로 바꿨을 때 무엇이 달라지는지 본다.

## 면접에서 나올 만한 질문

### CQRS가 무엇이고 왜 쓰나요?

상태를 바꾸는 명령과 데이터를 읽는 조회를 서로 다른 모델로 처리하는 구조다. 쓰기는 정규화된 모델에서 업무 규칙과 불변식을 지키는 데 집중하고, 읽기는 화면이 원하는 모양으로 미리 계산해 둔 모델에서 조인 없이 읽는다. 조회가 인덱스로 풀리지 않는 집계와 정렬을 하거나 읽기가 쓰기보다 훨씬 많을 때 효과가 크다. 예제에서는 870ms 걸리던 관리자 목록이 읽기 모델에서 0.86ms가 됐다.

### CQS와 CQRS는 무엇이 다른가요?

CQS는 메서드 단위의 원칙이고 CQRS는 그걸 모델과 저장소 단위로 넓힌 것이다. CQS는 한 메서드가 상태를 바꾸면서 값을 돌려주지 말라는 규칙이다. CQRS는 명령을 처리하는 모델과 조회를 처리하는 모델 자체를 나누고, 필요하면 저장소도 나눈다.

### CQRS를 하려면 이벤트 소싱도 해야 하나요?

아니다. 같은 DB에서 코드 경로만 나누거나, 읽기용 테이블을 같은 트랜잭션에서 함께 고치는 것도 CQRS다. 반대로 이벤트 소싱은 상태 테이블이 없어서 조회용 읽기 모델이 사실상 필요하니 CQRS와 거의 항상 같이 간다.

### 읽기 모델이 늦게 반영되는 문제는 어떻게 다루나요?

명령이 사건의 위치나 버전을 돌려주고, 그 값으로 지연을 다룬다. 서버가 읽기 모델의 체크포인트가 그 위치를 넘을 때까지 짧게 기다렸다가 응답하거나, 명령 응답에 바뀐 결과를 실어 화면이 먼저 반영하게 한다. 방금 쓴 사용자의 조회만 잠시 쓰기 모델로 보내는 방법도 있다. 기다리는 방식은 프로젝터가 멈추면 모두 기다리게 되니 타임아웃을 짧게 두고 넘기면 "반영 중"을 보여 준다.

### 프로젝터가 같은 이벤트를 두 번 처리하면 어떻게 되나요?

덮어쓰는 프로젝션은 결과가 같지만, 누적하는 프로젝션은 값이 두 번 더해진다. 읽기 모델이 다른 저장소에 있어 반영과 체크포인트 저장을 한 트랜잭션으로 묶을 수 없으면 이 일이 생긴다. 행마다 마지막으로 반영한 위치나 버전을 함께 저장하고 그보다 작거나 같은 사건은 건너뛰게 해서 막는다. 같은 대상의 사건은 한 프로젝터가 순서대로 처리해야 이 방법이 통한다.

### 읽기 모델에 버그가 있었다면 어떻게 고치나요?

행을 손으로 고치지 않고 읽기 모델을 다시 만든다. 새 테이블을 만들고 새 프로젝터를 처음부터 돌려 현재 위치까지 따라잡게 한 뒤, 조회를 새 테이블로 돌리고 옛것을 지운다. 그러려면 사건을 충분히 오래 보관하거나 쓰기 모델에서 한 번에 채우는 길이 있어야 하고, 프로젝터가 사건 밖의 현재 값을 읽지 않아야 다시 만든 결과가 같다.

### 명령 처리기가 판단할 때 읽기 모델을 봐도 되나요?

안 된다. 읽기 모델은 늦을 수 있어서, 재고나 잔액처럼 결정에 쓰는 값을 거기서 읽으면 이미 바뀐 값으로 판단하게 된다. 명령 처리기는 쓰기 모델에서 읽고, 버전을 비교하는 낙관적 잠금이나 트랜잭션 안의 조건부 UPDATE로 동시 변경을 막는다.

### CQRS를 쓰지 말아야 할 때는 언제인가요?

화면이 테이블 모양과 거의 같은 CRUD 서비스, 쓰기 직후 항상 최신 값을 봐야 하는 흐름, 팀이 지연과 재생성을 운영할 여력이 없는 경우다. 읽기 모델과 프로젝터라는 부품이 생기고 데이터가 두 벌이 되니, 느린 화면 하나처럼 효과가 분명한 곳에만 부분적으로 거는 게 보통이다.
