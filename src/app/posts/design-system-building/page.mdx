## 버튼이 일곱 종류가 된 회사

서비스가 셋인 회사의 코드를 검색해 본다. `Button`이라는 이름의 컴포넌트가 일곱 개 나온다. 파란색이 `#2563eb`, `#2463EB`, `#1d4ed8` 세 가지로 쓰이고, 모서리는 4px, 6px, 8px이 섞여 있다. 어떤 버튼은 키보드 Tab으로 갔을 때 테두리가 보이지 않는다. 브랜드 색을 바꾸자는 결정이 나자 세 팀이 각자 몇백 군데를 고치는 데 두 달이 걸렸다.

디자인 시스템은 이걸 한 번에 고치려는 시도다. 그리고 시니어 프런트엔드 면접에서 자주 나오는 주제다. "디자인 시스템을 만들어 본 적이 있나", "토큰은 어떻게 나눴나", "컴포넌트 API를 어떻게 설계했나", "깨지는 변경은 어떻게 배포했나" 같은 질문은 결국 여러 팀이 같이 쓰는 코드를 어떻게 설계하고 운영하느냐를 묻는다.

이 글은 토큰부터 배포와 도입까지 순서대로 간다. 스타일링 도구 자체를 고르는 이야기는 [CSS 스타일링 방식 고르기](/posts/css-styling-approaches)에 따로 썼다. Compound component나 render props 같은 React 합성 패턴은 별도 주제라 여기서는 API 설계에 필요한 만큼만 쓴다.

## 컴포넌트 묶음보다 큰 것

디자인 시스템이라고 하면 버튼, 입력칸, 모달 같은 컴포넌트 패키지를 먼저 떠올린다. 실제로는 그보다 넓다.

- 토큰: 색, 간격, 글자, 모서리, 그림자, 움직임 같은 디자인 결정을 이름 붙인 값.
- 컴포넌트: 토큰으로 만든 재사용 부품. 접근성과 상호작용이 들어 있다.
- 문서와 규칙: 언제 어떤 컴포넌트를 쓰는지, 쓰지 말아야 하는 경우, 글쓰기 톤.
- 운영: 버전 정책, 변경 공지, 기여 절차, 피드백 창구.

디자이너의 Figma 라이브러리와 개발자의 코드 패키지가 같은 이름의 토큰과 컴포넌트를 쓰는 게 이상적이다. 둘이 따로 놀면 디자이너는 `Primary/Large`라고 부르고 코드는 `variant="solid" size="lg"`라고 불러서 시안을 옮길 때마다 번역이 필요하다.

### 디자인 시스템, 컴포넌트 라이브러리, UI 킷, 패턴

이 말들이 자주 섞여 쓰여서 회의에서 서로 다른 것을 가리키곤 한다. 층으로 나눠 두면 덜 헷갈린다.

UI 킷은 디자이너가 쓰는 Figma 같은 도구 안의 부품 모음이다. 그림으로서의 버튼과 입력칸이 있고, 코드나 사용 규칙은 없다. 컴포넌트 라이브러리는 그 부품을 코드로 만든 패키지다. `npm install`로 받아 쓰고, 상호작용과 접근성이 들어 있다. 디자인 시스템은 이 둘을 같은 토큰 위에 올리고, 언제 무엇을 쓰는지 정한 규칙과 운영 방식까지 묶은 것이다. 그래서 "컴포넌트 라이브러리를 만들었다"와 "디자인 시스템을 만들었다"는 다른 말이다. 앞의 것은 코드가 있다는 뜻이고, 뒤의 것은 여러 팀이 같은 결정을 따른다는 뜻이다.

패턴은 컴포넌트보다 한 단계 위의 단위다. 버튼과 입력칸이 부품이라면, 로그인 흐름, 빈 상태, 폼 오류를 보여 주는 방식, 삭제 확인처럼 "이 과업은 이렇게 푼다"는 해법이 패턴이다. 패턴에는 어떤 컴포넌트를 어떤 순서로 놓는지와 함께 문구, 오류가 났을 때의 동작이 들어간다. 패턴은 코드 하나로 만들기보다 문서와 예제로 남기는 경우가 많다.

공개된 예로는 구글의 Material Design, IBM의 Carbon, Shopify의 Polaris, GitHub의 Primer가 자주 거론된다. 넷 다 토큰, 컴포넌트, 사용 규칙, 패턴을 함께 공개하고 있어서 처음 구조를 잡을 때 참고하기 좋다. 반대로 제품이 하나이고 팀이 작으면 이 전부가 필요하지 않다. 서비스와 팀이 늘어서 같은 버튼을 여러 번 만드는 비용이 보이기 시작할 때가 들일 때다.

### 원자에서 페이지까지: Atomic Design

컴포넌트를 어떤 크기로 나눌지 이야기할 때 많이 쓰는 틀이 Brad Frost의 Atomic Design이다. 화면을 다섯 단계로 본다.

- 원자(atom): 더 쪼개면 의미가 없는 것. 라벨, 입력칸, 버튼, 아이콘.
- 분자(molecule): 원자 몇 개가 한 가지 일을 하는 묶음. 라벨과 입력칸과 버튼을 합친 검색 폼.
- 유기체(organism): 분자와 원자가 모인 화면의 한 구역. 로고, 메뉴, 검색 폼이 든 헤더.
- 템플릿(template): 유기체를 배치한 페이지의 뼈대. 내용 자리는 비워 둔다.
- 페이지(page): 템플릿에 실제 내용을 채운 것. 긴 제목, 빈 목록 같은 실제 데이터로 뼈대가 버티는지 여기서 확인한다.

디자인 시스템이 맡는 건 대개 원자와 분자, 일부 유기체까지다. 템플릿과 페이지는 각 제품 팀의 몫이다. 이 틀은 말을 맞추는 데 좋지만, 폴더 구조로 그대로 옮기면 "이건 분자인가 유기체인가"로 시간이 간다. 검색 폼에 자동 완성 목록이 붙으면 어디로 가야 할지 정답이 없다. 그래서 많은 팀이 단계 이름을 어휘로만 쓰고, 코드는 컴포넌트 이름별 폴더로 둔다.

### 있는 화면부터 센다

이미 서비스가 돌아가는 회사라면 토큰을 정하기 전에 지금 무엇이 쓰이고 있는지부터 센다. 주요 화면을 캡처해 버튼끼리, 색끼리 모아 붙이는 시각 감사와, 소스에서 hex 색과 px 값을 뽑아 세는 일이다. 첫 장면의 파란색 세 가지와 모서리 세 가지도 이렇게 찾은 숫자다. 명령과 실제 출력, 그 숫자로 토큰 후보를 고르는 방법은 [디자인 시스템 운영 글](/posts/design-system-adoption-governance)에 있다. 많이 쓰인 값이 원시 토큰 후보가 되고, 한 자리만 다른 값(`#2563eb`과 `#2463EB`)은 오타로 보고 합친다.

## 토큰을 세 층으로 쌓는다

가장 흔한 실수는 색을 바로 쓰는 것이다. 버튼 배경에 `blue-600`, 링크 글자에도 `blue-600`, 선택된 탭 밑줄에도 `blue-600`을 쓴다. 나중에 "링크만 조금 더 진하게"라는 요청이 오면 `blue-600`을 찾아서 그중 어느 것이 링크인지 하나하나 골라야 한다.

그래서 토큰을 층으로 나눈다.

원시 토큰(primitive)은 쓸 수 있는 값의 목록이다. `blue.600 = #2563eb`, `gray.900 = #1a1a1a`, `space.4 = 16px`처럼 값 자체에 이름을 붙인다. 의미가 없다. 팔레트라고 생각하면 된다.

의미 토큰(semantic)은 용도에 이름을 붙이고 원시 토큰을 가리킨다. `color.action.primary → blue.600`, `color.text.default → gray.900`, `color.border.focus → blue.500`. 컴포넌트는 여기서부터 쓴다. 링크만 진하게 바꾸고 싶으면 `color.text.link`가 가리키는 값만 바꾼다.

컴포넌트 토큰(component)은 특정 부품의 자리에 이름을 붙이고 의미 토큰을 가리킨다. `button.primary.bg → color.action.primary`. 브랜드마다 버튼만 다르게 하고 싶을 때 이 층이 쓸모 있다. 모든 시스템에 필요한 층은 아니다. 컴포넌트가 수십 개인 시스템에서 컴포넌트마다 토큰 수십 개를 만들면 토큰이 수천 개가 되어 아무도 관리하지 못한다. 작게 시작하면 원시와 의미 두 층으로 충분하고, 테마나 브랜드별 덮어쓰기가 필요한 컴포넌트만 세 번째 층을 둔다.

토큰의 원천은 코드나 CSS가 아니라 플랫폼 중립적인 데이터로 두는 게 좋다. W3C 디자인 토큰 커뮤니티 그룹(DTCG)이 정한 JSON 형식이 있고, 2025년에 첫 안정 버전이 나왔다. Figma 플러그인과 변환 도구들이 이 형식을 읽는다.

```json
{
  "color": {
    "blue": {
      "600": { "$type": "color", "$value": "#2563eb" },
      "400": { "$type": "color", "$value": "#7aa2ff" }
    },
    "action": {
      "primary": { "$type": "color", "$value": "{color.blue.600}" }
    }
  }
}
```

`{color.blue.600}`은 다른 토큰을 가리키는 별칭이다. Style Dictionary 같은 변환 도구가 이 파일을 읽어 웹용 CSS 변수, 타입스크립트 상수, iOS·안드로이드용 값을 함께 만든다. 웹 앱 하나뿐이라면 처음부터 CSS 변수와 TS 객체로 시작해도 되지만, 앱이 늘어날 계획이라면 원천을 하나로 두는 비용이 가장 싸다.

```css
/* 변환 결과: 의미 토큰이 원시 토큰 변수를 가리키게 남겨 두면 테마 전환이 쉽다 */
:root {
  --blue-600: #2563eb;
  --blue-400: #7aa2ff;
  --color-action-primary: var(--blue-600);
  --button-primary-bg: var(--color-action-primary);
}
```

### 성공, 경고, 오류는 기능 색으로 따로 둔다

브랜드 색과 별도로, 상태를 알리는 기능 색(functional color)을 의미 토큰으로 둔다. 보통 `success`, `warning`, `danger`(또는 `error`), `info` 네 가지이고, 각각 글자·배경·테두리 자리를 나눈다. 같은 빨강이라도 오류 문구의 글자색과 오류 알림 상자의 옅은 배경은 다른 값이어야 하기 때문이다.

```css
:root {
  --color-danger-text: var(--red-700);    /* #b91c1c, 흰 배경 6.47:1 */
  --color-danger-bg: var(--red-50);       /* #fef2f2, 알림 상자 배경 */
  --color-danger-border: var(--red-600);
  --color-warning-text: var(--amber-700); /* #b45309, 흰 배경 5.02:1 */
  --color-warning-bg: var(--amber-50);
  --color-success-text: var(--green-700); /* #15803d, 흰 배경 5.02:1 */
  --color-success-bg: var(--green-50);
}
```

기능 색은 대비에서 자주 걸린다. 경고에 흔히 쓰는 노랑 `#f59e0b`는 흰 배경 위 대비가 2.15:1이고, 초록 `#16a34a`도 3.30:1이라 본문 글자로는 쓸 수 없다. 그래서 아이콘이나 테두리에는 밝은 원색을 쓰더라도 글자색 토큰은 한두 단계 진한 값(`#b45309`, `#15803d`)으로 따로 둔다. 다크에서는 반대로 `#dc2626`이 `#121212` 위에서 3.88:1로 모자라서 더 밝은 `#f87171`(6.77:1)로 바꾼다.

색 사용 가이드에는 이런 규칙을 함께 적는다. 기능 색은 상태를 알릴 때만 쓰고 장식에 쓰지 않는다(빨간 버튼이 많으면 진짜 오류가 묻힌다). 상태를 색만으로 알리지 않고 아이콘이나 문구를 같이 붙인다(WCAG 1.4.1, 색각이 다른 사람은 빨강과 초록을 구분하지 못할 수 있다). 브랜드 색이 빨강 계열이면 `danger`와 헷갈리지 않게 색상이나 밝기를 떨어뜨린다. 색 공간과 단계 색을 고르는 방법은 [CSS 색과 배경 글](/posts/css-color-background)에서 다룬다.

## 다크 모드는 의미 층에서 갈라진다

다크 모드를 처음 만들 때 원시 토큰을 뒤집는 경우가 있다. `gray.100`과 `gray.900`의 값을 서로 바꾸는 식이다. 그러면 `gray.900`이라는 이름이 다크 모드에서는 밝은 색이 되어 이름이 거짓말을 한다. 무엇보다 모든 색이 정확히 대칭으로 뒤집히지 않는다.

원시 토큰은 그대로 두고, 의미 토큰이 테마마다 다른 원시 토큰을 가리키게 한다. 아래 그림은 같은 `Button`의 배경색이 라이트와 다크에서 어떤 길을 따라 정해지는지 보여 준다.

## 대비는 토큰을 만들 때 검사한다

색 대비는 컴포넌트마다 검사하기보다 토큰 단계에서 막는 게 싸다. 글자색 토큰과 배경색 토큰의 짝은 정해져 있으니, 토큰 파일이 바뀔 때마다 모든 짝의 대비를 계산해 기준을 못 넘으면 CI를 실패시킨다.

WCAG 2의 대비율은 두 색의 상대 휘도(relative luminance)로 계산한다. 각 채널을 0~1로 나누고, 화면의 감마를 되돌려 빛의 양에 비례하는 값으로 바꾼 뒤, 사람 눈이 초록에 가장 민감하다는 가중치로 더한다. 밝은 쪽을 L1, 어두운 쪽을 L2라 하면 대비율은 (L1 + 0.05) ÷ (L2 + 0.05)다. 기준은 본문 글자 4.5:1, 큰 글자(대략 24px 이상, 굵으면 18.66px 이상) 3:1, 버튼 테두리나 아이콘 같은 UI 요소 3:1이다(WCAG 2.2 AA).

```ts
// 채널 하나(0~255)를 빛의 양에 비례하는 값으로 바꾼다
const linear = (c: number) => {
  const s = c / 255;
  return s <= 0.04045 ? s / 12.92 : ((s + 0.055) / 1.055) ** 2.4;
};
// 상대 휘도: 초록 가중치가 가장 크다
const luminance = (r: number, g: number, b: number) =>
  0.2126 * linear(r) + 0.7152 * linear(g) + 0.0722 * linear(b);
```

직접 만들어 보자. `#rrggbb` 두 개를 받아 대비율을 소수점 둘째 자리로 반올림해 돌려준다. 순서와 상관없이 밝은 쪽이 분자에 와야 한다.

## 동작과 모양을 나눈다

드롭다운 메뉴 하나를 제대로 만들려면 생각보다 많은 일이 필요하다. 버튼을 누르면 열리고, 화살표 키로 항목을 오가고, 글자를 치면 그 글자로 시작하는 항목으로 가고, Esc로 닫히고, 닫히면 포커스가 버튼으로 돌아오고, 바깥을 누르면 닫히고, 화면 끝에 닿으면 반대쪽으로 펼쳐지고, 스크린 리더에는 "메뉴, 항목 5개"라고 읽혀야 한다. WAI-ARIA Authoring Practices에 컴포넌트 종류별로 이런 규칙이 정리되어 있다.

이 동작은 회사마다 다를 이유가 없다. 다른 건 모양이다. 그래서 요즘 디자인 시스템은 동작과 접근성만 담고 스타일은 하나도 없는 헤드리스(headless) 컴포넌트 위에 자기 스타일을 입힌다. Radix Primitives, React Aria(Adobe), Headless UI, Ark UI, Base UI가 이런 라이브러리다. 복사해서 쓰는 컴포넌트 모음으로 유명한 shadcn/ui도 안쪽은 Radix 같은 헤드리스 라이브러리다.

```tsx
// Radix의 DropdownMenu에 우리 토큰으로 모양만 입힌다
import * as Menu from "@radix-ui/react-dropdown-menu";
import styles from "./menu.module.css";

export function ActionMenu({ onEdit, onDelete }: ActionMenuProps) {
  return (
    <Menu.Root>
      <Menu.Trigger className={styles.trigger}>더보기</Menu.Trigger>
      <Menu.Portal>
        {/* 키보드 탐색, 포커스 복귀, 바깥 클릭, 위치 계산은 Radix가 한다 */}
        <Menu.Content className={styles.content} sideOffset={4}>
          <Menu.Item className={styles.item} onSelect={onEdit}>수정</Menu.Item>
          <Menu.Item className={styles.item} data-tone="danger" onSelect={onDelete}>삭제</Menu.Item>
        </Menu.Content>
      </Menu.Portal>
    </Menu.Root>
  );
}
```

```css
/* 상태는 라이브러리가 data 속성으로 알려 준다. 스타일은 그걸 읽기만 한다 */
.item[data-highlighted] { background: var(--color-bg-hover); }
.item[data-disabled] { color: var(--color-text-disabled); }
.content[data-state="open"] { animation: fade-in 150ms var(--easing-out); }
```

React Aria는 같은 일을 훅으로도 제공한다. `useButton`, `useComboBox` 같은 훅이 요소에 붙일 props(이벤트 핸들러, `aria-*` 속성)를 돌려주고, 마크업은 내가 직접 쓴다. 더 많이 제어할 수 있는 대신 써야 할 코드가 늘어난다. 처음에는 컴포넌트 형태가 빠르고, 아주 특수한 위젯을 만들 때 훅으로 내려간다.

직접 다 만들지 않는 이유는 비용 때문이다. 콤보박스 하나를 스크린 리더 여러 개(VoiceOver, NVDA, TalkBack)와 브라우저 조합에서 제대로 동작하게 만드는 일은 컴포넌트 하나에 몇 주가 들 수 있다. 헤드리스 라이브러리를 쓰면 그 시간을 토큰, 문서, 도입에 쓸 수 있다. 대신 라이브러리의 DOM 구조와 data 속성에 스타일이 묶이므로, 라이브러리의 메이저 업데이트가 우리 시스템의 깨지는 변경이 될 수 있다는 점은 감안한다.

변형은 boolean 여러 개보다 하나의 유니언으로 둔다. `primary`, `secondary`, `outline`을 각각 boolean으로 받으면 `<Button primary outline>`이 무엇인지 아무도 모른다. 서로 독립인 축(모양, 의미 색, 크기)만 별도 prop으로 나눈다.

요소를 바꾸는 방법은 두 가지가 있다. `as` prop은 `<Button as="a" href="...">`처럼 그릴 태그를 받는다. 편하지만 타입이 복잡하다. `as`에 따라 받을 수 있는 props가 바뀌어야 하고(`a`면 `href`, `button`이면 `type`), 이걸 제네릭으로 정확히 표현하면 타입 검사가 느려지고 오류 메시지가 읽기 어려워진다. Radix가 퍼뜨린 `asChild`는 반대로 자식 요소를 그대로 받고, 내 props와 이벤트 핸들러, `ref`를 자식에 합쳐 준다. 타입이 단순하고 Next.js의 `Link` 같은 라우터 컴포넌트와도 잘 맞는다. 대신 자식이 정확히 하나여야 하고, 자식 컴포넌트가 props를 DOM까지 전달하고 `ref`를 받아야 한다.

```tsx
// asChild의 핵심: 자식 하나를 복제하며 props를 합친다 (Radix Slot의 단순화)
import { cloneElement, isValidElement } from "react";

function Slot({ children, ...props }: SlotProps) {
  if (!isValidElement(children)) return null;
  const childProps = children.props as Record<string, unknown>;
  return cloneElement(children, {
    ...props,
    ...childProps,
    // 클래스는 이어 붙인다. 실제로는 핸들러와 ref, style도 합쳐야 한다
    className: [props.className, childProps.className].filter(Boolean).join(" "),
  });
}
```

실제 구현은 이벤트 핸들러를 둘 다 호출하고 `ref`를 합치고 `style`을 병합하는 등 처리가 더 많다. 직접 만들기보다 `@radix-ui/react-slot`을 가져다 쓰는 게 낫다.

props가 많아지면 합성으로 나눈다. `Card`에 `title`, `subtitle`, `image`, `footer`, `actions`, `badge`를 다 props로 받다 보면, 누군가 제목 옆에 아이콘을 넣고 싶을 때 `titleIcon`이 또 생긴다. `Card.Header`, `Card.Body`, `Card.Footer`처럼 조각을 내보내고 쓰는 쪽이 조립하게 하면 API가 커지지 않는다. 반대로 버튼처럼 작고 모양이 일정한 부품은 props가 더 안전하다. 조립할 자유가 크면 모양이 흩어진다.

React 19부터 함수 컴포넌트가 `ref`를 일반 prop으로 받으므로 `forwardRef` 없이 `ref`를 전달할 수 있다. 공용 컴포넌트는 처음부터 `ref`를 받아 DOM 요소에 넘겨야 쓰는 쪽에서 포커스를 옮기거나 위치를 잴 수 있다.

## 접근성을 기본값으로 넣는다

디자인 시스템이 접근성에서 가장 큰 힘을 내는 이유는 한 번 고치면 모든 곳이 고쳐지기 때문이다. 반대로 시스템이 놓치면 모든 곳이 같이 틀린다.

포커스 표시는 시스템이 책임진다. 마우스 클릭 때 테두리가 보기 싫다고 `outline: none`을 주는 일이 흔한데, 키보드 사용자는 지금 어디에 있는지 알 수 없게 된다. `:focus-visible`은 브라우저가 키보드 탐색처럼 표시가 필요하다고 판단할 때만 켜지니 이걸로 모양을 정한다.

```css
.button:focus-visible {
  outline: 2px solid var(--color-border-focus);
  outline-offset: 2px; /* 배경색과 겹치지 않게 띄운다 */
}
```

아이콘만 있는 버튼은 이름을 필수로 만든다. 타입으로 강제하면 리뷰에서 잡을 필요가 없다.

```tsx
// 아이콘 버튼은 aria-label 없이 컴파일되지 않는다
type IconButtonProps = React.ComponentPropsWithoutRef<"button"> & {
  icon: React.ReactNode;
  "aria-label": string;
};
```

입력칸은 `label`과 오류 메시지 연결을 컴포넌트 안에서 처리한다. `TextField`가 `useId()`로 id를 만들어 `label`의 `htmlFor`, 오류 문구의 `id`, 입력칸의 `aria-describedby`와 `aria-invalid`를 이어 주면 쓰는 쪽은 `label="이메일" error="형식이 틀렸다"`만 넘기면 된다.

모달은 열릴 때 포커스를 안으로 옮기고, 바깥 내용은 탭으로 갈 수 없게 막고, 닫히면 연 버튼으로 포커스를 돌려줘야 한다. 네이티브 `<dialog>` 요소를 `showModal()`로 열면 바깥 내용을 비활성(inert)으로 만들고 Esc 닫기를 브라우저가 해 준다. 헤드리스 라이브러리를 쓰면 이 부분이 이미 들어 있다.

움직임은 `prefers-reduced-motion`을 존중한다. 토큰에 `motion.duration`을 두고, 움직임 줄이기 설정에서 그 값을 0에 가깝게 바꾸면 컴포넌트마다 따로 처리할 필요가 없다.

검사는 자동과 손을 섞는다. axe-core 같은 자동 도구는 대비, 이름 없는 버튼, 잘못된 ARIA 속성처럼 기계가 판단할 수 있는 것을 잡는다. 하지만 "포커스 순서가 화면 흐름과 맞는가", "스크린 리더로 들었을 때 이해되는가"는 사람이 키보드와 스크린 리더로 직접 써 봐야 안다. 자동 도구는 접근성 문제의 일부만 찾는다고 보고, 새 컴포넌트를 낼 때 키보드만으로 한 번, VoiceOver나 NVDA로 한 번 써 본다.

## Storybook을 문서이자 작업대로

컴포넌트를 만드는 사람은 앱 전체를 띄우지 않고 부품 하나를 여러 상태로 보고 싶다. 쓰는 사람은 어떤 변형이 있고 어떻게 쓰는지 알고 싶다. Storybook은 이 둘을 한 곳에서 한다. 컴포넌트의 상태 하나하나를 "스토리"로 적으면, 그게 개발용 작업대가 되고, 문서가 되고, 뒤에서 볼 시각 테스트의 대상이 된다.

```tsx
// button.stories.tsx (Storybook 8~9의 CSF3 형식)
import type { Meta, StoryObj } from "@storybook/react";
import { expect, userEvent, within } from "storybook/test"; // 8에서는 "@storybook/test"
import { Button } from "./button";

const meta = {
  component: Button,
  tags: ["autodocs"], // props 표와 예제로 문서 페이지를 자동으로 만든다
  args: { children: "저장" },
  argTypes: { variant: { control: "inline-radio" } },
} satisfies Meta<typeof Button>;
export default meta;

type Story = StoryObj<typeof meta>;

export const Solid: Story = { args: { variant: "solid" } };
export const DangerOutline: Story = { args: { variant: "outline", tone: "danger" } };
export const Disabled: Story = { args: { disabled: true } };

// 상호작용까지 스토리로 적으면 테스트가 된다
export const KeyboardFocus: Story = {
  play: async ({ canvasElement }) => {
    const canvas = within(canvasElement);
    await userEvent.tab();
    await expect(canvas.getByRole("button", { name: "저장" })).toHaveFocus();
  },
};
```

`@storybook/addon-a11y`를 켜면 스토리마다 axe-core 검사 결과가 패널에 뜬다. 다크 테마, 좁은 화면, 긴 텍스트(번역하면 독일어가 두 배로 길어진다), 오류 상태처럼 화면에서 잘 안 보는 상태를 스토리로 남겨 두는 게 중요하다. 그 상태들이 깨지는 걸 사람이 매번 확인하지 않아도 되게 하는 게 다음 단계다.

문서에는 props 표보다 "언제 쓰지 말아야 하는지"가 더 쓸모 있다. "페이지 이동에는 Button이 아니라 Link를 쓴다", "한 화면에 solid 버튼은 하나만" 같은 규칙이다. props는 타입이 알려 주지만 판단 기준은 문서만 알려 준다.

## 눈으로 보던 회귀를 기계가 본다

토큰 하나를 바꾸면 어디가 달라지는지 사람이 다 볼 수 없다. `space.3`을 12px에서 14px로 바꾸면 그걸 쓰는 컴포넌트 수십 개의 모양이 바뀐다. 단위 테스트는 "버튼에 클래스가 붙는가"를 볼 뿐 "버튼이 2px 커졌다"는 모른다.

시각 회귀 테스트(visual regression test)는 스토리마다 스크린샷을 찍어 승인된 기준 이미지와 픽셀 단위로 비교한다. 다르면 차이를 강조한 이미지를 보여 주고, 사람이 의도한 변경이면 승인해서 새 기준으로 삼고, 아니면 고친다. Chromatic은 Storybook 스토리를 그대로 찍는 서비스이고, Playwright의 `toHaveScreenshot()`으로 직접 구성할 수도 있다.

```ts
// visual.spec.ts: Storybook을 정적으로 빌드해 띄운 뒤 스토리마다 찍는다
import { test, expect } from "@playwright/test";

const stories = ["button--solid", "button--danger-outline", "button--disabled"];

for (const id of stories) {
  test(id, async ({ page }) => {
    await page.goto(`/iframe.html?id=${id}&viewMode=story`);
    await expect(page).toHaveScreenshot(`${id}.png`, {
      animations: "disabled",   // 움직이는 중간 프레임을 찍지 않는다
      maxDiffPixelRatio: 0.001, // 안티앨리어싱 차이 정도는 허용한다
    });
  });
}
```

```bash
# 처음 한 번, 또는 의도한 변경을 승인할 때 기준 이미지를 다시 만든다
npx playwright test visual.spec.ts --update-snapshots
# 평소에는 비교만 한다. 다르면 실패하고 차이 이미지를 남긴다
npx playwright test visual.spec.ts
```

이 테스트가 흔들리는 원인은 거의 정해져 있다. 폰트가 늦게 로드되어 대체 폰트로 찍힘, 애니메이션 중간 프레임, 현재 시각이나 무작위 데이터, 운영체제마다 다른 글꼴 렌더링이다. 마지막 것은 개발자 맥북에서 만든 기준 이미지를 리눅스 CI와 비교하면 모든 글자 가장자리가 달라서 전부 실패하는 형태로 나타난다. 기준 이미지는 항상 같은 도커 이미지 안에서 만들고 비교한다. 흔들리는 테스트를 방치하면 사람들이 차이를 보지 않고 승인 버튼부터 누르게 되어 테스트가 의미를 잃는다.

## 깨지는 변경을 알리고 옮겨 준다

디자인 시스템 패키지를 쓰는 앱이 열 개라면, 버전 번호는 그 앱들과의 약속이다. 버전 규칙 자체는 [Semantic Versioning](/posts/semantic-versioning)에 정리했다. 디자인 시스템에서 까다로운 건 무엇이 깨지는 변경(major)인지가 코드보다 넓다는 점이다.

- prop 이름 변경이나 삭제, 값 목록에서 하나를 빼는 것은 당연히 major다.
- 기본값 변경도 major다. `size`의 기본값을 `md`에서 `sm`으로 바꾸면 아무 코드도 안 고친 앱의 화면이 바뀐다.
- 토큰 이름 변경이나 삭제는 major다. 앱이 CSS 변수를 직접 읽고 있을 수 있다.
- DOM 구조 변경은 회색 지대다. 공식 API는 아니지만 쓰는 쪽 테스트가 `getByRole`이 아니라 클래스 선택자로 요소를 찾고 있거나, 스타일을 선택자로 덮고 있으면 깨진다. 문서에 "DOM 구조와 내부 클래스는 공개 API가 아니다"라고 밝혀 두고, 그래도 큰 변경은 major로 낸다.
- 시각적 변화는 합의로 정한다. 모서리 6px에서 8px처럼 의도한 디자인 개선은 보통 minor로 내고 변경 기록에 스크린샷을 붙인다.

major를 자주 내면 앱들이 따라오지 않는다. 그래서 깨지는 변경은 한 번에 터뜨리지 않고 단계를 밟는다. 새 API를 minor로 먼저 추가하고, 옛 API는 개발 모드에서 콘솔 경고를 띄우는 deprecated 상태로 한동안 둔다. 다음 major에서 지운다. 기계적으로 바꿀 수 있는 변경(prop 이름 바꾸기, import 경로 바꾸기)은 jscodeshift 같은 도구로 코드모드(codemod)를 만들어 함께 배포하면 앱 팀이 명령 한 줄로 옮긴다.

```tsx
// 개발 모드에서만 경고하고, 옛 값은 새 값으로 바꿔 계속 동작하게 둔다
if (process.env.NODE_ENV !== "production" && variant === "primary") {
  console.warn('[ds] Button variant="primary"는 v5에서 사라진다. variant="solid"를 쓴다.');
}
const resolved = variant === "primary" ? "solid" : variant;
```

## 모노레포에서 패키지로 내보내기

토큰, 아이콘, 컴포넌트, 문서 사이트는 보통 한 저장소에 패키지로 나눠 둔다. `@acme/tokens`가 바뀌면 `@acme/ui`가 그걸 쓰고, 문서 사이트는 둘 다 쓴다. 패키지 사이를 잇는 pnpm 워크스페이스 설정, 빌드형과 소스형 패키지의 차이, `exports` 경계, React가 두 벌 들어가는 사고와 Changesets로 버전을 전파하는 실습은 [프런트엔드 모노레포](/posts/frontend-monorepo)에 있다. 디자인 시스템 패키지에서 특히 챙길 것만 적는다.

React와 React DOM은 `dependencies`가 아니라 `peerDependencies`에 둔다. 쓰는 앱의 React를 함께 쓰라는 뜻이다. `dependencies`에 두면 앱에 React가 두 벌 깔려 훅이 깨진다. 헤드리스 라이브러리처럼 공유되어야 하는 상태가 없는 의존성은 `dependencies`에 둬도 된다.

CSS를 어떻게 내보낼지 정한다. 컴포넌트가 CSS 파일을 `import`하는 방식은 쓰는 앱의 번들러가 CSS import를 처리해야 한다. 런타임 CSS-in-JS로 만든 패키지는 쓰는 앱도 같은 라이브러리와 서버 렌더링 설정을 갖춰야 하고 서버 컴포넌트에서 막힌다. 여러 앱이 다른 프레임워크와 번들러를 쓴다면 결과물이 평범한 CSS인 방식(CSS Modules, 제로 런타임, 미리 빌드한 CSS 파일 하나)이 가장 덜 묶인다. 패키지의 CSS는 `@layer ds`처럼 레이어 안에 넣어 두면 앱이 자기 스타일로 덮을 때 명시도 싸움이 없다.

`package.json`의 `sideEffects`도 적어 둔다. `"sideEffects": ["*.css"]`라고 써 두면 번들러가 안 쓰는 컴포넌트의 자바스크립트는 지우되 CSS import는 지우지 않는다. `false`로만 두면 CSS까지 사라지는 사고가 난다.

## 만들어도 안 쓰이는 디자인 시스템

디자인 시스템 프로젝트가 실패하는 가장 흔한 모습은 기술이 아니다. 잘 만든 패키지가 있는데 아무도 안 쓰고, 각 팀은 여전히 자기 버튼을 만든다.

흔한 이유가 몇 가지 있다. 시스템 팀이 반년 동안 혼자 완벽한 컴포넌트 50개를 만들고 나서 공개했는데, 실제 제품에 필요한 건 그중 일부였고 정작 필요한 테이블과 날짜 선택기는 없다. 컴포넌트가 너무 닫혀 있어서 제품의 작은 요구(버튼 안에 배지 하나)를 못 받아 주니 팀들이 복사해서 고친다. 버그를 고쳐 달라고 해도 2주가 걸리니 팀들이 기다리지 않는다. 그리고 쓰라고 강제했지만 옮기는 비용은 각 팀이 떠안는다.

잘 퍼지는 시스템은 반대로 간다. 가장 많이 쓰이는 몇 개(버튼, 입력칸, 모달, 토스트)부터 실제 제품 한 곳과 같이 만들어 그 제품에 먼저 들어간다. 한 번 실사용에서 다듬어진 컴포넌트를 다른 팀에 권한다. 시스템 팀만 코드를 쓰는 게 아니라 제품 팀이 기여할 수 있는 절차(제안, 리뷰 기준, 누가 유지하는지)를 열어 둔다. 탈출구를 문서화해 두되, 탈출구를 쓴 곳을 모아 다음에 시스템에 넣을 후보로 본다.

도입 정도는 숫자로 본다. 저장소마다 시스템 컴포넌트를 import한 횟수와, 같은 역할을 하는 자체 컴포넌트(이름에 `Button`이 들어간 로컬 컴포넌트)의 수를 스크립트로 세어 주기적으로 본다. 하드코딩된 hex 색의 개수를 세는 린트 규칙도 같은 역할을 한다. 숫자가 늘지 않는 팀이 있으면 그 팀에 무엇이 모자란지 직접 묻는 게 가장 빠르다.

## 재료부터 약속까지

디자인 시스템은 토큰이라는 재료, 동작과 접근성이 든 부품, 그 부품을 언제 쓰는지 알려 주는 문서, 그리고 바꿀 때 지키는 약속으로 이루어진다. 토큰은 원시와 의미를 나눠 테마가 의미 층에서 갈라지게 하고, 동작은 헤드리스 라이브러리에 맡겨 모양에 집중하고, API는 좁고 예측 가능하게 열고, 변경은 시각 테스트와 단계적인 폐기로 안전하게 퍼뜨린다. 그리고 그 모든 걸 실제 제품 한 곳과 함께 만들어야 쓰인다.

## 면접에서 나올 만한 질문

### 디자인 토큰을 왜 여러 층으로 나누나?

값과 용도를 분리하려고 나눈다. 원시 토큰은 `blue.600` 같은 팔레트이고, 의미 토큰은 `action.primary`처럼 용도에 이름을 붙여 원시 토큰을 가리킨다. 컴포넌트가 의미 토큰만 쓰면 링크 색만 바꾸거나 다크 모드에서 다른 값을 쓰는 일을 한 곳에서 한다. 컴포넌트 토큰은 브랜드별 덮어쓰기가 필요할 때만 두는데, 모든 컴포넌트에 만들면 토큰이 수천 개로 늘어 관리가 안 된다.

### 다크 모드는 토큰 구조에서 어떻게 구현하나?

원시 토큰은 그대로 두고 의미 토큰이 테마마다 다른 원시 토큰을 가리키게 한다. `data-theme` 속성에 따라 CSS 변수 묶음을 바꾸면 컴포넌트 코드는 그대로다. 라이트 값을 기계적으로 뒤집지 않고 다크용 값을 따로 정해 대비를 다시 검사한다. 예를 들어 `blue.600`은 흰 배경에서 충분하지만 `#121212` 위에서는 3.62:1이라 글자로 쓰기에 모자라다. `color-scheme: dark`로 브라우저 기본 UI도 함께 바꾼다.

### 헤드리스 컴포넌트를 쓰는 이유는?

드롭다운, 콤보박스, 모달 같은 위젯의 키보드 탐색, 포커스 관리, ARIA 속성은 회사마다 다를 이유가 없고 제대로 만들기 어렵기 때문이다. Radix나 React Aria 같은 헤드리스 라이브러리는 동작과 접근성만 주고 스타일은 비워 두니, 우리는 토큰으로 모양만 입힌다. 상태는 data 속성으로 알려 주니 CSS가 그걸 읽는다. 대신 라이브러리의 DOM 구조에 스타일이 묶이므로 라이브러리의 메이저 업데이트가 우리의 깨지는 변경이 될 수 있다.

### as prop과 asChild는 무엇이 다른가?

둘 다 컴포넌트를 다른 요소로 그리게 하는 방법이다. `as`는 태그나 컴포넌트를 받아 그걸로 렌더링하는데, `as` 값에 따라 받을 props가 달라져서 정확한 타입을 만들면 복잡하고 검사가 느려진다. `asChild`는 자식 요소를 그대로 그리면서 내 클래스, 핸들러, `ref`를 합쳐 준다. 타입이 단순하고 라우터의 `Link`와 잘 맞지만, 자식이 하나여야 하고 그 자식이 props와 `ref`를 DOM까지 전달해야 한다.

### 디자인 시스템에서 깨지는 변경은 무엇이고 어떻게 배포하나?

prop이나 토큰의 이름 변경·삭제, 허용 값 제거, 기본값 변경이 major다. 기본값은 코드를 안 고친 앱의 화면도 바꾸니 특히 조심한다. DOM 구조는 공개 API가 아니라고 문서로 밝히되 큰 변경은 major로 낸다. 배포는 새 API를 minor로 먼저 추가하고 옛 API는 개발 모드 경고와 함께 남겨 두었다가 다음 major에서 지운다. 기계적인 변경은 코드모드를 함께 내서 앱 팀의 이전 비용을 줄인다.

### 시각 회귀 테스트는 어떻게 운영하나?

스토리마다 스크린샷을 찍어 승인된 기준 이미지와 비교하고, 차이가 나면 사람이 의도한 변경인지 판단해 승인하거나 고친다. Chromatic이나 Playwright의 `toHaveScreenshot()`을 쓴다. 흔들림의 원인인 폰트 로딩, 애니메이션, 시각·무작위 데이터를 고정하고, 운영체제마다 글꼴 렌더링이 다르니 기준 이미지는 항상 같은 도커 이미지에서 만든다. 흔들리는 테스트를 방치하면 차이를 안 보고 승인하게 되어 의미가 없어진다.

### 디자인 시스템 패키지에서 React를 peerDependencies에 두는 이유는?

쓰는 앱의 React 인스턴스를 함께 써야 하기 때문이다. `dependencies`에 두면 버전이 어긋날 때 React가 두 벌 설치되고, 훅이 다른 React의 디스패처를 찾아 "Invalid hook call" 같은 오류가 난다. peer로 두면 앱이 설치한 React 하나를 공유한다. 같은 이유로 컨텍스트를 공유해야 하는 라이브러리도 peer로 둔다.

### 디자인 시스템이 조직에서 안 쓰이는 이유와 해결책은?

실제 제품의 요구와 떨어져 만들어졌거나, 너무 닫혀 있어서 작은 요구를 못 받아 주거나, 고쳐 달라는 요청이 느리게 처리되기 때문인 경우가 많다. 가장 많이 쓰는 컴포넌트 몇 개부터 실제 제품 한 곳과 같이 만들어 먼저 넣고, 제품 팀이 기여할 수 있는 절차와 문서화된 탈출구를 둔다. import 횟수와 로컬 중복 컴포넌트 수, 하드코딩된 색의 개수를 세어 도입 정도를 숫자로 보고, 늘지 않는 팀에 이유를 직접 묻는다.
