글 목록 줄마다 삭제 버튼이 있고, 페이지가 뜰 때 버튼마다 클릭 리스너를 단다. 그리고 "더 보기"를 누르면 글을 몇 개 더 붙인다.

  btn.addEventListener("click", e => console.log("delete", e.currentTarget.closest("li").dataset.id))

more.addEventListener("click", () => {
  const li = document.createElement("li");

"더 보기"를 누르고, 새로 생긴 3번 글의 삭제 버튼을 누르고, 처음부터 있던 1번 글의 삭제 버튼을 눌렀다. Playwright로 띄운 Chromium 141의 로그다.

```text
appended li 3
delete 1
```

3번 글의 삭제 버튼은 아무 반응이 없다. 리스너를 다는 코드는 페이지가 뜰 때 한 번 돌았고, 그때 3번 버튼은 없었다. 새 버튼에도 리스너를 달려면 줄을 붙일 때마다 다는 코드를 다시 불러야 하고, 지울 때는 떼야 한다. 줄이 1만 개면 리스너도 1만 개다.

이 글은 이 문제를 리스너 하나로 푸는 이벤트 위임(event delegation)을 다룬다. 어떻게 동작하는지, 어디서 틀리기 쉬운지, 위임이 통하지 않는 이벤트, 그리고 React가 이미 내부에서 위임을 하고 있다는 사실까지 따라간다. 출력은 모두 Chromium 141(헤드리스)에서 실제로 돌린 결과다.

이 주제의 다른 글: 위임이 기대는 버블링 규칙은 [이벤트 전파](/posts/event-propagation)에서, 위임 핸들러가 쓰는 `closest`와 DOM 트리는 [DOM 기초](/posts/dom-basics)에서 봤다. 여기서는 그 설명을 반복하지 않는다.

## 리스너를 부모 하나에 단다

클릭은 눌린 요소에서 끝나지 않고 조상을 따라 올라간다. 그러니 버튼마다 듣지 말고 목록(`ul`) 하나에서 들으면 된다. 리스너 안에서 `e.target`을 보고 "어느 줄의 어느 버튼이 눌렸나"를 알아낸다. 나중에 붙은 줄도 같은 `ul` 안에 있으니 따로 할 일이 없다.

```js
list.addEventListener("click", e => {
  const btn = e.target.closest("[data-action]");
  if (!btn || !list.contains(btn)) return;     // 동작 버튼이 아니거나 목록 밖이면 무시
  const id = btn.closest("li").dataset.id;
  if (btn.dataset.action === "delete") remove(id);
});
```

아래 그림은 새로 붙은 3번 줄의 삭제 버튼, 그 안의 아이콘을 눌렀을 때다. 다음을 누르며 클릭이 어디서 처리되는지 보자.

## target이 버튼이 아니라 아이콘일 때

위임 코드에서 가장 흔한 버그는 `e.target`이 늘 버튼이라고 믿는 것이다. 버튼 안에 아이콘이나 `span`이 있으면 사용자가 정확히 어디를 눌렀느냐에 따라 `target`이 바뀐다. 아이콘을 누를 때와 버튼 글자 바깥 여백을 누를 때를 비교했다.

```js
list.addEventListener("click", e => {
  console.log("target:", e.target.nodeName.toLowerCase(),
    "| matches(button):", e.target.matches("button"),
    "| closest:", e.target.closest("[data-action]")?.dataset.action ?? null);
});
```

```text
target: svg | matches(button): false | closest: delete
target: button | matches(button): true | closest: delete
```

`e.target.matches("button")`이나 `e.target.tagName === "BUTTON"`으로 검사하면 아이콘을 눌렀을 때 아무 일도 일어나지 않는다. 데스크톱에서 버튼 가운데를 누르며 테스트하면 잘 되고, 손가락이 큰 모바일에서 "가끔 안 눌린다"는 제보가 온다. `closest`는 자기 자신부터 검사하니 버튼을 직접 눌러도, 안쪽을 눌러도 같은 결과를 준다.

위임 핸들러의 핵심은 결국 아래 한 줄이다. 조각을 하나씩 눌러 보자.

마지막 단계가 두 번째로 흔한 버그다. `closest`는 리스너가 달린 요소에서 멈추지 않고 문서 끝까지 올라간다. 목록이 `data-action="close-panel"`을 가진 패널 안에 있으면, 목록의 빈 곳을 눌렀을 때 패널의 동작이 잡힌다. 실제로 돌려 봤다.

```js
list2.addEventListener("click", e => {
  const btn = e.target.closest("[data-action]");
  console.log("naive closest:", btn?.dataset.action ?? null, "| inside list2:", btn ? list2.contains(btn) : null);
});
```

```text

```

## 실제로 얼마나 줄어드나

줄 1만 개, 줄마다 삭제 버튼이 있는 목록으로 비교했다. 버튼마다 리스너를 다는 경우와 `ul`에 하나만 다는 경우다. 리스너를 달기 전후로 Chrome DevTools Protocol로 GC를 돌린 뒤 힙 사용량(`Runtime.getHeapUsage`)을 쟀고, 리스너 수는 `DOMDebugger.getEventListeners`로 셌다. 두 번 돌린 값이 같았다.

```text
perItem   setup ms 7.9 heap +KB 657 listeners on 1st button 1 on ul 0
delegated setup ms 0.0 heap +KB 26 listeners on 1st button 0 on ul 1
```

버튼마다 달면 리스너를 다는 데 약 8ms, 힙이 657KB 늘었다. 리스너마다 함수 객체와 클로저, 등록 정보가 생기기 때문이다. 위임은 1ms도 안 걸리고 26KB다. 숫자는 이 기기의 헤드리스 크롬에서 잰 값이라 환경마다 다르다. 크기를 보는 감은 이렇다. 1만 줄에 수백 KB와 몇 ms는 데스크톱에서는 큰 문제가 아니지만, 저사양 모바일에서 첫 화면이 뜨는 시점에 메인 스레드를 쓰는 일이고, 목록이 바뀔 때마다 떼고 다는 코드까지 더하면 빠뜨린 리스너가 [메모리 누수](/posts/js-memory-leak)가 된다.

위임의 진짜 이득은 숫자보다 코드 쪽에 있다.

- 나중에 붙은 요소가 저절로 동작한다. 처음 버그가 사라진다.
- 줄을 지울 때 리스너를 뗄 필요가 없다. 뗄 게 없으니 빠뜨릴 수도 없다.
- 동작 목록이 한곳에 모인다. 아래처럼 `data-action` 이름과 처리 함수를 짝지은 객체 하나로 화면의 버튼들을 관리할 수 있다.

```js
const actions = {
  delete: id => remove(id),
  pin: id => pin(id),
  share: id => openShare(id),
};
list.addEventListener("click", e => {
  const btn = e.target.closest("[data-action]");
  if (!btn || !list.contains(btn)) return;
  const run = actions[btn.dataset.action];
  if (run) run(btn.closest("li").dataset.id);
});
```

`actions[btn.dataset.action]`처럼 DOM 값으로 함수를 고를 때는 객체에 등록한 이름만 통하게 한다. `window[btn.dataset.action]()`처럼 전역에서 찾으면 HTML에 값을 넣을 수 있는 사람이 아무 함수나 부를 수 있다. 위 `actions`도 일반 객체라서 `data-action="toString"`이면 프로토타입의 함수가 잡힌다. 엄격히 하려면 `Object.hasOwn(actions, name)`으로 확인하거나 `Map`을 쓴다.

비용도 있다. 목록 안의 아무 곳을 눌러도 리스너가 한 번 돈다. 빈 곳을 눌러도 `closest`가 몇 칸 올라간다. 이 정도는 무시할 만하지만, `document` 하나에 모든 화면의 동작을 몰아넣고 클릭마다 수십 개의 선택자를 검사하면 이야기가 다르다. 위임은 가까운 공통 부모, 예를 들어 목록이나 표, 툴바에 단다.

## 위임이 통하지 않는 이벤트

위임은 버블링에 기대니 올라가지 않는 이벤트에는 그대로 쓸 수 없다. 대표적으로 `focus`, `blur`, `mouseenter`, `mouseleave`다. 같은 일을 하는 올라가는 이벤트로 바꾼다. 실제로 부모에 리스너를 달고 자식에서 이벤트를 일으켰을 때 부모까지 온 것은 이것뿐이었다.

```text
G reached parent: mouseover, focusin, focusout
```

폼의 입력칸마다 포커스가 들어올 때 도움말을 바꾸려면 `form`에서 `focusin`을 듣는다. 줄에 마우스를 올리면 강조하는 기능은 `mouseover`로 위임할 수 있는데, 하나 더 신경 써야 한다. `mouseover`는 줄 안의 자식 요소를 옮겨 다닐 때마다 다시 일어난다. `e.relatedTarget`(마우스가 떠나온 요소)이 같은 줄 안이면 무시한다.

```js
list.addEventListener("mouseover", e => {
  raw++;
  const li = e.target.closest("li");
  if (!li || li.contains(e.relatedTarget)) return;  // 같은 li 안에서 움직인 것은 무시
  entered.push(li.dataset.id);
});
```

`b`, `i`, `span`이 든 줄 두 개 위로 마우스를 천천히 옮겼다.

```text
mouseover 10 row entered 1,2
```

`mouseover`는 열 번 일어났지만 줄에 들어간 건 두 번이다. 걸러 내지 않으면 강조 애니메이션이 열 번 다시 시작된다. 사실 단순한 강조는 CSS `li:hover`가 리스너 없이 해 주니, 자바스크립트로 할 일이 있을 때만 이 코드를 쓴다.

버블링되는 이벤트인데도 위임 핸들러에 안 오는 경우도 있다.

- 길 중간의 코드가 `stopPropagation()`을 부른다. 서드파티 위젯이나 모달 라이브러리에서 자주 나온다. [이벤트 전파](/posts/event-propagation)에서 본 대로 이건 위에서 막을 방법이 없다. 캡처 단계로 위임하면(`addEventListener("click", fn, true)`) 버블 단계에서 막는 코드보다 먼저 받는다.
- `disabled` 버튼은 클릭 이벤트 자체가 없다. 안쪽의 `span`을 눌러도 마찬가지였다. 반대로 `aria-disabled="true"`로 모양만 비활성으로 만든 버튼은 클릭이 그대로 오니, 위임 핸들러에서 직접 걸러야 한다.
- 위임할 부모 자체를 다시 그리는 코드가 있다. `list.innerHTML = ...`로 목록을 통째로 바꾸면 `ul`은 그대로라 괜찮지만, `ul`을 감싼 영역을 바꾸면 `ul`이 새 요소가 되고 리스너가 사라진다. 위임은 오래 사는 요소에 단다.

## React는 이미 위임하고 있다

React에서 `onClick`을 1만 개 줄에 달아도 DOM 리스너는 1만 개가 생기지 않는다. React 17부터는 `createRoot`에 넘긴 루트 요소에 이벤트 종류마다 리스너를 하나씩 달고, 거기서 받은 네이티브 이벤트의 `target`부터 컴포넌트 트리를 따라 올라가며 `onClick`을 찾아 부른다. 이 글에서 손으로 만든 구조를 프레임워크 전체가 쓰는 셈이다. 그 순서가 네이티브 리스너와 섞일 때 생기는 일은 [이벤트 전파](/posts/event-propagation)의 React 절에 실제 출력과 함께 있다.

그러니 React에서 리스너 수를 줄이려고 위임을 직접 할 필요는 거의 없다. 1만 줄 목록이 느리다면 원인은 리스너가 아니라 1만 개의 컴포넌트를 렌더링하는 비용이고, 답은 화면에 보이는 줄만 그리는 가상화나 [리렌더링](/posts/react-rerender) 줄이기다. 대신 이런 경우에는 React 안에서도 위임 모양이 쓸모 있다.

- 줄마다 `onClick={() => remove(item.id)}`처럼 새 함수를 만들어 `memo`한 줄 컴포넌트가 매번 다시 그려진다면, 부모에 핸들러 하나를 두고 `data-id`를 읽게 바꾸면 줄에 넘기는 props가 바뀌지 않는다.
- 마크다운처럼 `dangerouslySetInnerHTML`로 넣은 HTML 안의 링크나 버튼은 React가 모르는 요소다. 감싼 요소에 `onClick` 하나를 달고 `e.target.closest("a")`로 위임한다.

## 위임 코드를 볼 때 확인하는 것

위임 핸들러에서 생기는 문제는 대부분 증상만 봐도 어디인지 좁혀진다.

1. 가끔 안 눌린다: `e.target`을 직접 검사하고 있는지 본다. 아이콘이나 글자 `span`을 눌렀을 때 `target`이 바뀐다. `closest`로 바꾼다.
2. 엉뚱한 동작이 실행된다: `closest`가 컨테이너 밖까지 올라갔다. `contains` 검사를 넣는다. 중첩된 목록이면 가장 가까운 것이 이기니, 안쪽 목록의 동작이 바깥 목록에서도 한 번 더 처리되지 않는지 본다.
3. 한 번 눌렀는데 두 번 처리된다: 버튼에 직접 단 리스너와 위임 리스너가 함께 있다. 개발자 도구 Elements 패널의 Event Listeners 탭에서 버튼과 조상을 같이 본다. 위임 리스너를 화면이 다시 그려질 때마다 또 달고 있는 경우도 많다. 콘솔의 `getEventListeners(list).click.length`가 1보다 크면 그렇다.
4. 아예 안 온다: 위에서 본 `stopPropagation`, `disabled`, 부모 교체를 차례로 의심한다. `document`에 캡처 리스너를 달아 클릭이 어디까지 오는지 찍어 보면 빠르다.

클릭이 아니라 스크롤이나 입력처럼 자주 오는 이벤트를 위임할 때는 핸들러 하나가 모든 이벤트를 받으니 무거운 일을 바로 하지 않는다. 그 처리 횟수를 줄이는 방법은 [디바운스와 스로틀](/posts/debounce-throttle)에서 이어진다.

## 직접 만들어 보는 위임 판정

위임 핸들러가 하는 판단만 떼어 내서 함수로 만들어 보자. `path`는 클릭된 요소부터 위로 올라가는 노드 배열이고, 각 노드는 `{ tag, id, action, inactive }` 중 필요한 것만 가진다. `inactive: true`는 `aria-disabled`로 비활성 모양만 낸 요소다. `findAction(path, containerId)`는 가장 가까운 `action`을 돌려주되, 컨테이너 밖의 것은 보지 않고, 찾은 요소가 비활성이면 `null`을 돌려준다. 테스트의 기대값은 같은 구조의 DOM을 Chromium에서 만들고 `closest`와 `contains`로 판정한 결과와 맞춰 봤다.

## 다시 3번 글의 삭제 버튼으로

새로 붙은 버튼이 반응하지 않은 건 리스너가 요소에 붙어 있었고, 그 요소가 리스너를 달 때 없었기 때문이다. 리스너를 오래 사는 부모로 옮기고, 클릭이 올라오면 `closest`로 누가 눌렸는지 찾고 `contains`로 내 영역인지 확인하면 된다. 올라가지 않는 이벤트는 올라가는 짝으로 바꾸고, React를 쓴다면 이 일은 이미 루트에서 일어나고 있다.

## 면접에서 나올 만한 질문

### 이벤트 위임이 무엇인가요?

자식마다 리스너를 다는 대신 공통 부모에 하나만 달고, 버블링으로 올라온 이벤트의 `target`을 보고 어느 자식에서 났는지 판단하는 방법이다. 나중에 추가된 자식도 따로 리스너를 달지 않아도 동작하고, 지울 때 뗄 필요도 없다.

### 위임 핸들러에서 e.target 대신 closest를 쓰는 이유는 무엇인가요?

`target`은 실제로 눌린 가장 안쪽 요소라서 버튼 안의 아이콘이나 `span`이 될 수 있다. `e.target.matches("button")`으로 검사하면 아이콘을 눌렀을 때 실패한다. `closest`는 자기 자신부터 조상으로 올라가며 찾으니 어디를 눌러도 같은 버튼을 돌려준다.

### closest 뒤에 contains로 한 번 더 확인하는 이유는 무엇인가요?

`closest`는 리스너가 달린 요소에서 멈추지 않고 문서 끝까지 올라간다. 목록 바깥의 조상이 같은 선택자에 맞으면 그 요소를 돌려주기 때문에, 찾은 요소가 내 컨테이너 안에 있는지 `container.contains(found)`로 확인한다.

### 위임을 쓸 수 없는 이벤트는 어떻게 처리하나요?

`focus`, `blur`, `mouseenter`, `mouseleave`처럼 버블링되지 않는 이벤트는 부모에 오지 않는다. 버블링되는 짝인 `focusin`, `focusout`, `mouseover`, `mouseout`으로 바꾸거나 캡처 단계로 등록한다. `mouseover`는 자식 사이를 옮길 때마다 다시 일어나니 `relatedTarget`이 같은 줄 안이면 무시한다.

### 위임의 단점이나 주의할 점은 무엇인가요?

컨테이너 안 어디를 눌러도 핸들러가 돌고, 중간에서 `stopPropagation`을 부르는 코드가 있으면 이벤트가 오지 않는다. `document` 하나에 모든 동작을 몰아넣으면 클릭마다 검사할 선택자가 늘어 입력 반응이 느려진다. 가까운 공통 부모에 달고, 그 부모가 다시 그려져 교체되지 않는지 확인한다.

### 버튼 1만 개에 리스너를 다는 것과 위임은 실제로 얼마나 차이 나나요?

크롬에서 재 보면 버튼마다 달 때 약 8ms와 힙 650KB 정도가 들었고, 위임은 1ms 미만에 26KB였다. 기기마다 숫자는 다르지만 리스너 수만큼 함수와 등록 정보가 생긴다는 점은 같다. 더 큰 이득은 새 요소 처리와 리스너 해제를 신경 쓰지 않아도 된다는 코드 쪽에 있다.

### React에서도 이벤트 위임을 직접 해야 하나요?

대부분 필요 없다. React 17부터 루트 요소에 이벤트 종류별 리스너를 하나씩 달고 거기서 컴포넌트의 핸들러를 찾아 부르니, 이미 위임 구조다. 긴 목록이 느리면 리스너가 아니라 렌더링 비용을 봐야 하고, 직접 위임이 쓸모 있는 건 `dangerouslySetInnerHTML`로 넣은 HTML처럼 React가 모르는 요소를 다룰 때다.
