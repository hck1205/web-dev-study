서비스가 서울 리전 하나에서 돌고 있다. 리전 장애에 대비하고, 일본 사용자도 빠르게 하려고 도쿄 리전을 하나 더 열기로 했다. 회의에서 "그냥 양쪽에 똑같이 띄우고 DB는 복제하면 되지 않나"라는 말이 나온다. 그런데 막상 해 보면 도쿄 사용자의 주문 버튼이 오히려 느려지고, 가끔 재고가 한 개씩 어긋나고, 개인정보를 어느 나라에 저장하는지 묻는 메일이 법무팀에서 온다.

멀티 리전은 서비스를 지리적으로 떨어진 데이터 센터 묶음(리전) 두 곳 이상에서 돌리는 구성이다. 이 글은 먼저 거리가 정하는 지연을 계산하고, 리전 사이에 동기 복제를 걸면 커밋 하나가 얼마나 느려지는지 PostgreSQL 16으로 직접 잰다. 그다음 쓰기를 한 리전에만 받는 액티브-패시브와 양쪽에서 받는 액티브-액티브를 비교하고, 양쪽 쓰기가 부딪칠 때의 충돌, 사용자를 가까운 리전으로 보내는 라우팅, 데이터 거주 요건, 그리고 리전 안에서 피해 범위를 줄이는 셀 구조까지 본다.

이 주제의 다른 글: 사고 때 목표 숫자와 DR 단계는 [재해 복구](/posts/disaster-recovery), 대기 서버로 넘기는 과정과 펜싱은 [장애 조치](/posts/failover), 백업 사본의 위치는 [백업 전략](/posts/backup-strategy)에서 다룬다. 결국 같아지게 만드는 장치는 [최종 일관성](/posts/eventual-consistency), 순서와 상관없이 합쳐지는 자료형은 [CRDT](/posts/crdt), 같은 IP가 가까운 곳에서 답하는 원리는 [CDN 엣지와 애니캐스트](/posts/cdn-edge-anycast)에 있다.

## 빛이 정하는 바닥

리전 사이의 지연은 줄일 수 없는 바닥이 있다. 광섬유 안에서 빛은 진공의 약 2/3, 초당 20만 km쯤으로 간다. 1ms에 200km다. 서울과 도쿄는 직선으로 약 1,150km라서 왕복(RTT) 바닥이 11.5ms, 서울과 미국 동부(버지니아)는 약 11,000km라서 110ms다. 실제 케이블은 직선으로 깔려 있지 않고 중간에 장비를 거치니 측정값은 이보다 크다. 서울-도쿄는 보통 30ms 안팎, 서울-미국 동부는 180ms 안팎이 나온다. 회선과 경로에 따라 다르니 자기 환경에서 `ping`이나 `mtr`로 재 본다.

이 숫자가 무서운 이유는 곱해지기 때문이다. 요청 하나가 리전을 한 번 건너는 게 아니라, TCP 연결과 TLS 협상에 왕복이 몇 번, DB 쿼리가 순서대로 몇 번이면 그만큼 곱해진다. [지연과 대역폭](/posts/latency-bandwidth-throughput) 글의 왕복 계산을 리전 단위로 해 보자.

## 커밋 하나가 바다를 건너면

리전 장애에 데이터를 하나도 잃지 않으려면 커밋이 다른 리전의 기록을 기다려야 한다. 동기 복제다. 그 비용을 직접 쟀다. 프라이머리와 스탠바이를 서로 다른 네트워크 네임스페이스에 띄우고, 복제 경로에 Node로 짠 지연 프록시를 끼워 한쪽 16ms(왕복 약 32ms, 서울-도쿄 정도)와 65ms(왕복 약 130ms, 서울-미국 서부 정도)를 넣었다. 이 컨테이너에는 `tc netem`이 없어서 쓴 방법이다.

```bash
# 프록시: 받은 바이트를 양쪽 모두 DELAY ms 뒤에 넘긴다 (TCP_NODELAY를 켜야 지연이 쌓이지 않는다)
sudo ip netns exec v18p node delay-proxy.js 10.18.2.2 6432 10.18.2.2 5432 16 &

# 스탠바이는 프록시를 거쳐 복제받고, 프라이머리는 그 스탠바이를 동기로 기다린다
psql -h 10.18.1.2 -U postgres -c "ALTER SYSTEM SET synchronous_standby_names = '*'" -c "SELECT pg_reload_conf()"

# INSERT 한 줄짜리 부하를 5초 동안, 연결 1개
echo "INSERT INTO orders(amount) VALUES (1);" > ins.sql
echo "== one-way 16ms ($(psql -h 10.18.1.2 -U postgres -XAtc 'select sync_state from pg_stat_replication'))"
for m in local on remote_apply; do
  printf "%-13s " $m
  PGOPTIONS="-c synchronous_commit=$m" pgbench -h 10.18.1.2 -U postgres -n -c 1 -T 5 -f ins.sql postgres | grep "latency average"
done
# 연결 8개로 동시에
echo "8 clients, on:"
PGOPTIONS="-c synchronous_commit=on" pgbench -h 10.18.1.2 -U postgres -n -c 8 -T 5 -f ins.sql postgres | grep -E "latency average|^tps"
# 프록시 지연을 65로 바꿔 같은 측정을 한 번 더
```

```text
== one-way 16ms (sync)
local         latency average = 0.653 ms
on            latency average = 34.779 ms
remote_apply  latency average = 36.007 ms
8 clients, on:
latency average = 34.747 ms
tps = 230.237913 (without initial connection time)

== one-way 65ms (sync)
local         latency average = 0.296 ms
on            latency average = 136.322 ms
remote_apply  latency average = 132.996 ms
8 clients, on:
latency average = 133.355 ms
tps = 59.990110 (without initial connection time)
```

`synchronous_commit = local`(다른 리전을 기다리지 않음)은 0.3~0.7ms, `on`(스탠바이가 디스크에 썼다는 답을 기다림)은 왕복 시간과 거의 같은 35ms와 136ms다. 커밋 하나에 왕복 한 번이 그대로 붙는다. 연결 하나로는 초당 7~28건밖에 못 쓰는 셈이다. 연결 8개로 늘리자 처리량은 연결 수만큼 늘어 230건, 60건이 됐다. 각 커밋이 따로 왕복을 기다릴 뿐 서로를 막지는 않아서다. 그래도 커밋 하나의 지연은 35ms, 133ms 그대로라 사용자 한 명이 기다리는 시간은 줄지 않는다.

그래서 리전 사이의 동기 복제는 골라서 쓴다. PostgreSQL은 트랜잭션마다 `synchronous_commit`을 바꿀 수 있다. 결제 확정처럼 절대 잃으면 안 되는 쓰기만 `SET LOCAL synchronous_commit = on`으로 기다리게 하고, 조회 기록 같은 쓰기는 `local`로 둔다. 리전 하나가 사라질 때 잃는 것은 그 비동기 쓰기 몇 초어치다.

## 쓰기는 한 리전에서: 액티브-패시브

가장 흔한 멀티 리전은 쓰기를 한 리전(주 리전)만 받는 구성이다. 다른 리전은 읽기 복제본으로 읽기만 처리하고, 쓰기는 주 리전으로 보낸다. 주 리전이 사라지면 다른 리전의 복제본을 승격한다. 아래 그림에서 다음을 누르면 도쿄 사용자의 읽기와 쓰기가 가는 길이 보인다.

이 구성의 장점은 충돌이 없다는 것이다. 쓰기가 한 곳에서만 일어나니 순서가 하나다. 대신 먼 사용자의 쓰기는 느리고, 복제 지연 때문에 "방금 쓴 게 안 보인다"가 생긴다. 이건 [최종 일관성](/posts/eventual-consistency) 글의 세션 보장(내 쓰기 읽기)으로 푼다. 주 리전 장애 때의 전환은 [장애 조치](/posts/failover)와 같지만, 리전 단위라 판단을 사람이 하는 경우가 많다. 리전 하나가 30초 흔들렸다고 리전 전체를 넘기면 그 비용이 더 크기 때문이다.

## 양쪽에서 쓰면 부딪친다: 액티브-액티브

두 리전 모두 쓰기를 받으면 먼 사용자의 쓰기도 빨라지고, 리전 하나가 사라져도 다른 쪽이 바로 받는다. 대가는 같은 데이터를 양쪽에서 동시에 바꾸는 충돌이다. 가장 단순한 해결 규칙인 "나중에 쓴 쪽이 이긴다(LWW, Last Write Wins)"를 Node로 흉내 내 보자. 버지니아 서버의 시계가 200ms 늦은 상태에서 두 리전이 같은 행을 고치고, 복제가 도착하면 타임스탬프가 큰 쪽이 행 전체를 가져간다.

```bash
# 두 리전이 같은 행을 각자 고친 뒤 LWW로 합치는 흉내 (lww.js)
node lww.js
```

```text
1000ms seoul    write {"stock":9} ts=1000
1000ms virginia write {"stock":9} ts=800
1100ms seoul    write {"nickname":"kim-seoul"} ts=1100
1150ms virginia write {"nickname":"kim-virginia"} ts=950
merged: {"stock":9,"nickname":"kim-seoul","ts":1100}
expected by real time: stock 8, nickname kim-virginia
```

두 가지가 틀렸다. 재고는 양쪽에서 하나씩 팔렸으니 8이어야 하는데 9가 됐다. 둘 다 10을 읽고 9를 썼고, 합치면서 한쪽 쓰기가 사라졌다. 닉네임은 버지니아가 50ms 더 늦게 바꿨는데 서울 값이 남았다. 버지니아의 시계가 늦어서 타임스탬프가 작게 찍혔다. 에러는 어디에도 없다. 아래 그림에서 다음을 누르면 두 쓰기가 어디서 사라지는지 보인다.

충돌을 다루는 방법은 크게 세 가지다.

첫째, 충돌이 나지 않게 쓰기의 주인을 나눈다. 사용자마다 홈 리전을 정하고 그 사용자의 데이터는 홈 리전에서만 쓴다. 한국 사용자는 서울, 미국 사용자는 버지니아가 주인이다. 테이블 전체로 보면 액티브-액티브지만 행 하나로 보면 액티브-패시브다. 실무에서 가장 많이 쓰는 방법이다. 사용자가 이사하면 홈 리전을 옮기는 절차가 필요하고, 두 사용자 사이의 거래처럼 주인이 둘인 데이터는 따로 설계한다.

둘째, 합치는 규칙이 순서와 상관없는 자료형을 쓴다. 재고를 "값 9"로 쓰지 않고 "리전별로 몇 개 뺐다"로 쓰면 합칠 때 더하기만 하면 된다. 이게 [CRDT](/posts/crdt)의 카운터다. 다만 재고처럼 "0 아래로 내려가면 안 된다"는 조건은 CRDT만으로는 지킬 수 없다. 양쪽이 동시에 마지막 하나를 팔 수 있기 때문이다. 이런 조건은 리전마다 재고를 미리 나눠 주거나(서울 6개, 버지니아 4개), 그 결정만 한 리전에서 하게 한다.

셋째, LWW를 쓰되 잃어도 되는 데이터에만 쓴다. 마지막 접속 시각, 화면 설정처럼 하나가 덮여도 문제없는 값이다. 시계에 기대니 [시계 차이](/posts/clock-skew)를 줄이고, 가능하면 서버 시각 대신 하이브리드 논리 시계처럼 인과를 반영한 값을 쓴다. DynamoDB 글로벌 테이블이나 Cassandra의 다중 데이터센터 쓰기는 기본이 LWW 계열이라, 이 성질을 알고 써야 한다.

## 두 리전이 같은 번호를 만들지 않게

액티브-액티브에서 충돌보다 먼저 터지는 게 ID다. 두 리전이 각자 `bigserial`로 주문 번호를 매기면 서울의 1001번과 도쿄의 1001번이 따로 생기고, 복제가 만나는 순간 기본 키가 부딪친다. 가장 간단한 해결은 리전마다 번호 공간을 나누는 것이다.

```sql
-- 리전마다 시퀀스를 따로: 서울은 홀수, 도쿄는 짝수
CREATE SEQUENCE order_id_seoul START 1 INCREMENT 2;
CREATE SEQUENCE order_id_tokyo START 2 INCREMENT 2;
SELECT nextval('order_id_seoul') AS seoul, nextval('order_id_tokyo') AS tokyo FROM generate_series(1,3);
```

```text
 seoul | tokyo
-------+-------
     1 |     2
     3 |     4
     5 |     6
(3 rows)
```

간단하지만 리전을 셋으로 늘리면 증가 폭을 다시 정해야 하고, 번호 순서가 생성 시각 순서와 어긋난다. 그래서 요즘은 리전과 상관없이 겹치지 않는 ID를 쓰는 경우가 많다. 시각이 앞자리에 들어가 정렬도 되는 UUIDv7이나, 시각·리전·순번을 비트로 나눠 담는 Snowflake 방식이다. PostgreSQL 16에는 무작위 UUID(`gen_random_uuid()`, v4)만 있고 `uuidv7()`은 18부터 들어왔다. 16에서는 앱에서 만들어 넣는다. ID 설계 자체는 [샤딩](/posts/db-sharding) 글의 전역 ID 부분에 자세히 있다.

ID만 나눠서는 안 되는 것도 있다. 이메일 같은 유일 제약은 두 리전이 동시에 같은 값을 받으면 각자 성공하고 나중에 부딪친다. 이런 제약은 홈 리전 하나에서만 검사하게 하거나, 값을 해시해 주인 리전을 정해 그쪽에 먼저 등록하게 한다.

## 사용자를 가까운 리전으로

사용자를 어느 리전으로 보낼지는 보통 DNS나 애니캐스트가 정한다. ```sql

```text
pg_is_in_recovery|pg_last_wal_receive_lsn|pg_last_wal_replay_lsn

(1 row)
```

## 데이터가 국경을 넘으면

멀티 리전을 하면 데이터가 나라를 넘는다. 복제본, 백업 사본, 로그, 분석용 사본이 다 그렇다. 어떤 데이터는 특정 국가 안에 있어야 하거나, 밖으로 옮길 때 동의나 계약 같은 조건이 붙는다. EU의 GDPR은 유럽 경제 지역 밖으로 개인정보를 옮길 때 적정성 결정이나 표준 계약 조항 같은 근거를 요구하고, 한국 개인정보 보호법도 국외 이전에 고지와 동의 같은 요건을 둔다. 금융, 공공, 의료는 업종별 규정이 더 있다. 구체적인 판단은 법무팀의 몫이고, 엔지니어가 할 일은 "어떤 데이터가 어디에 있는지"를 답할 수 있게 만드는 것이다.

설계로 옮기면 이렇다. 개인정보는 사용자의 홈 리전에만 저장하고, 다른 리전에는 식별자만 둔다. 전역 검색이나 통계가 필요하면 가명 처리한 값만 모은다. 그리고 데이터 경로를 빠짐없이 센다. 흔히 놓치는 것이 백업이다. DB는 서울에만 두었는데 백업 사본을 재해 대비로 미국 리전에 복사하고 있었다면 그것도 국외 이전이다. 로그 수집 서비스, 오류 추적 SaaS, 고객 지원 도구로 흘러가는 개인정보도 같다.

## 셀 기반 구조: 리전 안에서도 쪼갠다

리전을 둘로 늘려도 남는 위험이 있다. 잘못된 배포나 설정 하나가 모든 리전에 동시에 퍼지면 리전이 몇 개든 함께 죽는다. 그리고 리전 하나의 규모가 너무 커지면 그 안의 장애가 사용자 전부에게 닿는다. 셀 기반 구조(cell-based architecture)는 서비스 전체를 작은 복사본(셀) 여러 개로 나누고, 사용자를 셀 하나에 고정한다. 셀은 앱, 캐시, DB까지 자기 것을 따로 가진다.

셀이 열 개면 셀 하나가 죽어도 사용자의 10%만 영향을 받는다. 배포는 셀 하나에 먼저 내고 문제가 없으면 다음 셀로 넘긴다. 리전은 여러 셀을 담는 그릇이 되고, 셀 하나가 리전 둘에 걸쳐 액티브-패시브로 있을 수도 있다. 셀 라우터는 가능한 한 단순하게 만든다. 라우터가 죽으면 모든 셀에 못 가니, 라우팅 표를 각 진입점에 캐시해 두고 라우터 장애 때도 마지막 표로 보낼 수 있게 한다. 대가도 있다. 셀을 넘는 조회(전체 사용자 통계, 셀이 다른 두 사용자의 거래)는 따로 모아야 하고, 셀을 늘릴 때 사용자를 옮기는 작업이 생긴다. 사용자를 셀에 나누는 계산은 [일관된 해싱](/posts/consistent-hashing)이나 명시적인 매핑 표를 쓴다.

## 멀티 리전이 아픈 순간

"리전을 하나 더 열었더니 p99가 두 배가 됐다"는 리전을 넘는 호출이 숨어 있는 경우다. 도쿄 앱이 세션 확인은 서울 Redis에서, 설정 조회는 서울 API에서 하고 있었다. 분산 추적에서 한 요청 안의 구간을 리전별로 칠해 보면 바로 보인다. 앱이 부르는 것들의 엔드포인트를 리전별로 나눠 같은 리전 것만 부르게 고친다.

"대기 리전의 복제본이 몇 시간째 뒤처져 있었다"는 평소에 아무도 안 보는 쪽에서 생긴다. 리전 사이 대역폭은 리전 안보다 훨씬 좁고 비싸서, 대량 배치 하나가 복제를 몇 시간 밀어 놓는다. 대기 리전의 복제 지연(`pg_stat_replication.replay_lag`)에 알림을 건다. 장애 때 잃는 양이 곧 이 값이다.

"클라우드 요금에서 데이터 전송비가 갑자기 늘었다"는 리전 간 전송이 공짜가 아니어서다. 리전 사이 트래픽은 보통 GB당 몇 센트가 붙고, 복제, 백업 복사, 리전을 넘는 API 호출이 모두 여기에 들어간다. 복제와 백업은 압축하고, 리전을 넘는 호출은 위에서처럼 없앤다.

"재고나 잔액이 가끔 한두 개씩 맞지 않는다"는 액티브-액티브의 LWW가 조용히 쓰기를 덮은 경우다. 에러가 없어서 정산에서야 드러난다. 충돌이 나면 안 되는 데이터에 LWW가 걸려 있지 않은지 테이블별로 확인하고, 홈 리전이나 CRDT로 옮긴다.

## 거리와 충돌을 먼저 정한다

멀티 리전에서 먼저 정할 것은 서버 대수가 아니라 두 가지다. 리전을 건너는 왕복을 어디에 쓸지, 그리고 양쪽에서 쓴 것이 부딪칠 때 누가 이길지다. 실험에서 리전 사이 동기 커밋은 왕복 시간 그대로(35ms, 136ms) 늦어졌고, LWW 병합은 에러 없이 재고 하나와 닉네임 하나를 잃었다. 대부분의 서비스는 쓰기의 주인을 한 리전(또는 사용자의 홈 리전)으로 정하고, 읽기를 가까이 두고, 리전 안에서는 셀로 피해 범위를 줄이는 쪽으로 간다.

## 면접에서 나올 만한 질문

### 액티브-패시브와 액티브-액티브의 차이는 무엇인가요?

액티브-패시브는 쓰기를 한 리전만 받고 다른 리전은 읽기와 대기를 맡는다. 쓰기 순서가 하나라 충돌이 없지만 먼 사용자의 쓰기가 느리고, 주 리전 장애 때 승격과 전환이 필요하다. 액티브-액티브는 양쪽이 쓰기를 받아 빠르고 장애에 강하지만, 같은 데이터를 동시에 바꾸는 충돌을 해결해야 하고 각 리전이 상대 몫까지 받을 용량을 가져야 한다.

### 리전 사이에 동기 복제를 걸면 어떻게 되나요?

커밋마다 리전 간 왕복 시간이 그대로 붙는다. 실험에서 왕복 약 32ms에서는 커밋이 35ms, 약 130ms에서는 136ms가 걸렸고, 같은 조건의 로컬 커밋은 1ms도 안 됐다. 연결을 늘리면 처리량은 늘지만 사용자 한 명의 대기 시간은 줄지 않는다. 그래서 잃으면 안 되는 쓰기만 트랜잭션 단위로 동기로 기다리게 한다.

### Last Write Wins의 문제는 무엇인가요?

동시에 들어온 쓰기 중 하나를 에러 없이 버린다. 실험에서 두 리전이 재고 10에서 하나씩 팔았는데 병합 결과가 8이 아니라 9였다. 또 서버 시계에 기대므로 시계가 늦은 리전의 더 나중 쓰기가 진다. 덮여도 되는 값에만 쓰고, 카운터는 CRDT로, 중요한 데이터는 홈 리전으로 주인을 정한다.

### 액티브-액티브에서 충돌을 피하는 실용적인 방법은 무엇인가요?

사용자마다 홈 리전을 정해 그 사용자의 데이터는 그 리전에서만 쓰게 하는 것이다. 테이블 전체로는 양쪽에서 쓰지만 행 하나로는 주인이 하나라 충돌이 없다. 다른 리전으로 들어온 요청은 홈 리전으로 넘기고, 두 사용자에 걸친 데이터나 이사 같은 경우는 따로 설계한다.

### 사용자를 가까운 리전으로 보내는 방법은 무엇인가요?

DNS 기반 라우팅과 애니캐스트가 대표적이다. DNS는 리졸버 위치나 측정 지연으로 가까운 리전의 IP를 주고 헬스 체크로 죽은 리전을 뺀다. 대신 TTL만큼 전환이 늦다. 애니캐스트는 같은 IP를 여러 곳에서 광고하고 BGP 경로가 고르게 해서 전환이 빠르지만, 경로가 바뀌면 진행 중인 TCP 연결이 끊길 수 있다.

### 데이터 거주 요건은 설계에 어떤 영향을 주나요?

개인정보를 어느 나라에 저장하는지 답할 수 있게 데이터 경로를 설계해야 한다. 보통 개인정보는 사용자의 홈 리전에만 두고 다른 리전에는 식별자나 가명 처리한 값만 둔다. 복제본뿐 아니라 백업 사본, 로그, 외부 SaaS로 가는 데이터도 국외 이전이 될 수 있어 함께 센다.

### 셀 기반 구조는 무엇이고 왜 쓰나요?

서비스 전체를 앱, 캐시, DB까지 갖춘 작은 복사본 여러 개로 나누고 사용자를 하나에 고정하는 구조다. 셀 하나의 장애나 잘못된 배포가 그 셀의 사용자에게만 닿아 피해 범위가 줄고, 배포를 셀 단위로 나눠 낼 수 있다. 대신 셀을 넘는 조회와 사용자 이동이 복잡해지고, 셀 라우터가 단일 장애점이 되지 않게 단순하게 만들어야 한다.
