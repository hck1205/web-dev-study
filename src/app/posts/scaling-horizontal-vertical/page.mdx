<EasyIntro>
  서버 한 대가 꽉 찼을 때 선택지는 둘이다. 더 좋은 서버로 바꾸거나(수직 확장), 같은 서버를 한 대 더 두고 요청을 나누거나(수평 확장). 그런데 CPU를 두 배로 키웠는데 처리량이 그대로이거나, 두 대로 늘렸더니 사용자가 자꾸 로그아웃되는 일이 생긴다.

  마트 계산대로 생각하면 된다. 수직 확장은 계산원을 더 빠른 사람으로 바꾸는 것이고, 수평 확장은 계산대를 늘리는 것이다. 계산원을 바꿔도 가게 프로그램이 한 사람만 쓰게 되어 있으면 소용이 없고, 계산대를 늘려도 손님 정보를 1번 계산대 수첩에만 적어 두면 2번 계산대는 그 손님을 모른다. 그래서 계산대를 늘리려면 수첩(세션, 파일, 캐시, 예약 작업)을 모두가 보는 곳으로 옮겨야 한다.

  계산대를 네 배로 늘려도 네 배 빨라지지는 않는다. 모든 손님이 거쳐야 하는 재고 확인 창구 하나가 남아 있으면 거기서 줄이 서고, 계산대끼리 서로 맞춰야 하는 일이 많으면 늘릴수록 오히려 느려지기도 한다. 그래서 확장의 실제 일은 서버를 늘리는 것보다 그 한 줄로 서는 구간을 줄이는 쪽에 있다.
</EasyIntro>

API 서버 한 대가 CPU 90%를 넘나든다. vCPU 4개짜리다. 선택지는 둘이다. 8개짜리로 바꾸거나, 같은 서버를 하나 더 띄워 로드 밸런서 뒤에 두거나. 앞쪽은 재시작 한 번이면 끝나니 쉬워 보였다. 그런데 8코어로 바꿨는데도 처리량이 거의 그대로였다. 그래서 두 대로 늘렸더니 이번에는 사용자들이 "자꾸 로그아웃된다"고 한다.

두 증상 모두 확장 방식의 전제를 몰라서 생겼다. 서버를 키우는 수직 확장(scale up)은 앱이 늘어난 자원을 쓸 수 있어야 의미가 있고, 서버를 늘리는 수평 확장(scale out)은 앱이 상태를 서버 밖에 두어야 성립한다. 이 글은 두 방식의 한계와 조건을 실제로 재 보고, 서버를 늘려도 그만큼 빨라지지 않는 이유를 암달의 법칙과 보편 확장성 법칙(USL)으로 계산한 뒤, 언제 무엇을 고를지 정리한다. 실습은 Ubuntu 컨테이너(vCPU 4개)에서 Node 22와 Go 1.24, Redis로 했다.

이 주제의 다른 글: 대수를 자동으로 늘리고 줄이는 쪽은 [오토스케일링](/posts/autoscaling)에서, DB를 늘리는 방법은 [DB 복제](/posts/db-replication-sharding)와 [샤딩](/posts/db-sharding)에서 다룬다.

수직 확장의 장점은 코드를 바꾸지 않는다는 것이다. 트랜잭션, 메모리 캐시, 로컬 파일, 프로세스 안의 락이 모두 그대로 동작한다. 수평 확장의 장점은 천장이 사실상 없고, 한 대가 죽어도 나머지가 받는다는 것이다. 대신 앱이 그 구조에 맞게 바뀌어야 한다.

## 키워도 쓰지 못하는 자원

처음 장면의 "8코어로 바꿨는데 그대로"를 재현해 봤다. CPU를 5ms 쓰는 핸들러를 가진 Node 서버를 프로세스 1개, 2개, 3개로 띄우고 동시 16개로 6초씩 두드렸다.

```bash
# cluster 모듈로 워커 프로세스 수만 바꿔 처리량을 잰다
WORKERS=1 node cores.js
WORKERS=2 node cores.js
WORKERS=3 node cores.js
```

```text
workers=1 req/s=194
workers=2 req/s=377
workers=3 req/s=466
```

프로세스 하나는 초당 194건에서 멈춘다. 요청 하나에 CPU 5ms면 한 코어로는 초당 200건이 최대이고, Node의 JS 코드는 한 스레드에서 돌기 때문이다. 코어가 4개든 64개든 이 숫자는 같다. 프로세스를 늘리자 처리량이 따라 올라갔다(3개에서 덜 오른 건 부하 발생기도 같은 기계의 CPU를 쓰고 있어서다). 수직 확장은 앱이 늘어난 코어를 쓸 수 있을 때만 효과가 있다. Node는 cluster나 PM2로 코어 수만큼 프로세스를 띄우고, 파이썬은 Gunicorn 워커 수를 늘린다. 이렇게 하면 한 기계 안에서 이미 "여러 대"를 운영하는 셈이라, 다음 절의 수평 확장 조건이 똑같이 적용된다.

운영 중인 서버에서 이 상태인지는 쉽게 확인된다. 프로세스 하나가 코어 하나만큼 쓰고 있는지 보면 된다. 위 서버를 프로세스 하나로 띄우고 부하를 거는 동안 찍었다.

```bash
# 코어 수
nproc
# 부하 중인 node 프로세스의 CPU 사용률 (100% = 코어 하나)
top -b -n 1 -p "$(pgrep -f one.js)" | tail -2
```

```text
4
  PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
24066 root      20   0 1015000  58588  45528 R  80.0   0.4   0:02.85 node
```

`top`의 프로세스 %CPU는 코어 하나를 100%로 센다. 코어가 4개인데 node 하나가 80~100% 근처에 붙어 있고 응답이 밀린다면, 기계 전체로는 4분의 1밖에 안 쓰는 상태다. 이 상태에서 코어를 늘리는 수직 확장은 돈만 쓴다. 대시보드의 "인스턴스 CPU 25%"만 보고 "여유가 있다"고 판단하는 실수도 여기서 나온다.

메모리도 비슷하다. 메모리를 64GB로 키워도 Node의 기본 힙 한도나 JVM의 `-Xmx`가 그대로면 앱은 늘어난 메모리를 못 쓴다. 이 이야기는 [가비지 컬렉션](/posts/garbage-collection) 글에 있다.

수직 확장에는 바깥쪽 한계도 있다.

- **천장**: 클라우드에서 고를 수 있는 가장 큰 인스턴스가 끝이다. 그 위로는 길이 없다.
- **비용 곡선**: 같은 계열 안에서는 크기가 두 배면 값도 대략 두 배로 선형이다. 비선형은 끝에서 온다. 메모리 특화나 최신 세대 대형 인스턴스는 단위 자원당 값이 비싸고, 코어 수로 라이선스를 매기는 상용 DB는 코어를 늘릴 때마다 라이선스가 붙는다.
- **바꾸는 동안의 중단**: 대부분 인스턴스 타입을 바꾸려면 멈췄다 다시 켜야 한다. 관리형 DB도 인스턴스 등급을 바꾸면 장애 조치나 재시작 시간이 생긴다.
- **단일 장애점**: 아무리 커도 한 대다. 그 한 대가 죽으면 전부 죽는다. 가용성을 위해 결국 두 대가 필요하고, 그러면 이미 수평 확장의 문제를 풀어야 한다.

## 늘리려면 상태를 밖으로 빼야 한다

두 대로 늘렸더니 로그아웃이 되는 이유를 직접 만들었다. 같은 앱 두 개(8081, 8082)를 띄우고 그 앞에 라운드 로빈으로 번갈아 보내는 작은 프록시를 뒀다. 앱은 로그인하면 세션을 자기 메모리의 `Map`에 저장한다.

```bash
# 쿠키를 저장하며 로그인하고, 같은 쿠키로 세 번 내 정보를 요청한다
curl -s -c jar localhost:8080/login
curl -s -b jar -w '%{http_code}\n' localhost:8080/me
curl -s -b jar -w '%{http_code}\n' localhost:8080/me
curl -s -b jar -w '%{http_code}\n' localhost:8080/me
```

```text
[app-2] logged in
[app-1] who are you?
401
[app-2] hello kim
200
[app-1] who are you?
401
```

로그인은 app-2가 받았고 세션도 app-2의 메모리에만 있다. 다음 요청이 app-1로 가면 모르는 세션이라 401이다. 같은 앱의 세션 저장소만 Redis로 바꿔 다시 돌렸다.

```text
[app-1] logged in
[app-2] hello kim
200
[app-1] hello kim
200
[app-2] hello kim
200
```

```bash
# 세션이 어디에 있는지 확인한다
redis-cli -p 6399 --scan --pattern 'sess:*'
```

```text

```

이제 어느 서버로 가도 같은 세션을 읽는다. 서버가 요청 사이에 기억할 것을 자기 안에 두지 않는 상태, 즉 무상태(stateless)가 되어야 수평 확장이 된다.

로드 밸런서의 스티키 세션(같은 사용자를 같은 서버로 보내기)으로도 증상은 사라진다. 하지만 그 서버가 죽거나 배포로 내려가면 세션이 같이 사라지고, 오래 붙어 있는 사용자 때문에 서버 간 부하가 기운다. 임시방편으로 쓰고, 세션은 공유 저장소나 서명된 토큰으로 옮긴다. 세션과 토큰의 차이는 [쿠키와 세션 로그인](/posts/cookie-session-login) 글에 있다.

세션 말고도 서버 안에 숨어 있는 상태가 많다. 수평 확장 전에 하나씩 확인한다.

- **업로드한 파일**: 로컬 디스크에 저장하면 다른 서버에서는 404다. 객체 저장소(S3 같은)로 옮긴다.
- **메모리 캐시**: 서버마다 캐시가 따로라서 한 서버에서 지운 값이 다른 서버에는 남는다. 짧은 TTL로 허용하거나 Redis 같은 공유 캐시를 쓴다. [캐시 전략](/posts/caching-strategies) 글 참고.
- **예약 작업**: 서버마다 같은 cron이 돌면 메일이 대수만큼 나간다(아래 그림).
- **웹소켓 연결**: 사용자 A와 B가 다른 서버에 붙어 있으면 서로의 메시지를 전하려면 pub/sub 같은 중계가 필요하다.
- **프로세스 안의 락이나 카운터**: 한 대일 때는 지켜지던 "한 번만"이 대수만큼 깨진다.

## 늘린 만큼 빨라지지 않는다: 암달의 법칙

상태를 다 빼고 서버를 네 배로 늘리면 네 배 빨라질까. 일 중에 나눌 수 없는 부분이 있으면 아니다. 전체 작업 중 병렬로 나눌 수 있는 비율을 p라고 하면, N개로 나눴을 때 빨라지는 배수는 이렇다.

```text
speedup(N) = 1 / ((1 - p) + p / N)
```

p가 0.9면 나눌 수 없는 10%가 남는다. N을 무한히 늘려도 그 10%는 그대로라서 최대 10배가 끝이다. Go로 직접 쟀다. 전체 계산의 10%는 한 고루틴에서만 하고 나머지 90%를 N개로 나눴다.

```bash
# 일의 10%는 직렬, 90%는 N개로 나눈다 (GOMAXPROCS = N)
./am amdahl
```

```text
workers=1 time=1.04s
workers=2 time=631ms
workers=3 time=522ms
workers=4 time=486ms
```

이론값은 2개일 때 1.82배(0.57초), 3개일 때 2.5배(0.42초), 4개일 때 3.08배(0.34초)다. 실제는 1.65배, 1.99배, 2.14배로 이론보다 더 낮았다. 이 컨테이너가 다른 작업과 CPU 4개를 나눠 쓰고 있었고(측정 때 load average가 5 안팎), 고루틴끼리 끝나기를 기다리는 비용도 있다. 현실은 암달의 법칙보다 나쁘다. 그 차이를 설명하는 것이 다음 절이다.

서버 수준으로 옮기면 직렬 부분은 모든 요청이 지나는 한 곳이다. DB 한 대, 전역 락 하나, 순서를 지켜야 하는 큐 하나. 앱 서버를 100대로 늘려도 모든 요청이 같은 DB 행을 갱신하면 그 행의 락이 직렬 구간이 된다.

## 맞추는 비용까지 세면: 보편 확장성 법칙

닐 건서(Neil Gunther)의 보편 확장성 법칙(USL)은 암달의 법칙에 한 항을 더한다. 노드끼리 서로 상태를 맞추는 비용(일관성 비용)이다. 노드가 N개면 짝이 N(N−1)개라서 이 비용은 N의 제곱으로 자란다.

```text
C(N) = N / (1 + α(N - 1) + βN(N - 1))
```

α는 줄을 서는 비용(경합), β는 서로 맞추는 비용(일관성)이다. β가 0이면 암달의 법칙과 같다(α = 1 − p). β가 0보다 크면 처리량이 어느 지점에서 꺾여 내려간다. 꼭짓점은 N = √((1 − α) / β)다.

## 층마다 늘리기 쉬운 정도가 다르다

시스템 전체를 한 가지 방식으로 확장하지는 않는다. 층마다 사정이 다르다.

앱 서버는 상태만 빼면 수평 확장이 가장 쉽다. 로드 밸런서 뒤에 같은 서버를 붙이면 된다. 로드 밸런서가 요청을 어떻게 나누는지는 [로드 밸런서 기초](/posts/load-balancer-basics) 글에 있다.

캐시는 키를 나눠 담으면 늘릴 수 있다. 노드를 추가할 때 키가 대부분 다른 노드로 옮겨 가면 캐시가 한꺼번에 비어 DB가 맞는다. 그래서 [일관된 해싱](/posts/consistent-hashing)을 쓴다.

DB는 가장 어렵다. 쓰기는 한 곳에서 순서를 정해야 하니 직렬 구간 그 자체다. 그래서 DB는 수직 확장으로 오래 버티는 게 보통이고, 읽기가 많으면 읽기 복제본으로 읽기만 수평으로 나누고, 쓰기와 데이터가 한 대를 넘을 때 샤딩으로 간다. 순서와 신호는 [DB 복제](/posts/db-replication-sharding) 글의 "언제 다음 단계로 넘어가나"에 정리돼 있다.

## 언제 무엇을 고르나

처음에는 수직 확장으로 시작하는 게 대개 맞다. 코드가 단순하고, 지금 쓰는 인스턴스의 몇 배까지는 버튼 하나로 간다. 다만 앱이 늘어난 자원을 쓰는지(프로세스 수, 힙 한도, 스레드 풀 크기)를 먼저 확인한다.

수평 확장으로 넘어가야 하는 신호는 이렇다.

- 가용성이 필요하다. 한 대가 죽거나 배포로 내려가는 동안에도 서비스가 돌아야 한다면 최소 두 대는 이미 필요하다.
- 가장 큰 인스턴스가 보이기 시작한다. 지금 크기에서 두세 단계밖에 안 남았다면 천장에 닿기 전에 구조를 바꿔야 한다.
- 부하가 출렁인다. 낮에는 10대, 밤에는 2대가 필요하다면 큰 한 대를 계속 켜 두는 것보다 작은 여러 대를 [오토스케일링](/posts/autoscaling)하는 게 싸다.

반대로 수평 확장을 미뤄도 되는 경우도 있다. 상태가 많은 레거시 앱, 강한 일관성이 필요한 단일 DB, 아직 서버 한 대 비용이 작은 초기 서비스. 이럴 때 무리하게 나누면 분산 시스템의 복잡도(네트워크 분할, 일관성, 분산 트랜잭션)를 미리 사들이는 셈이다.

현장에서 자주 보는 실수 몇 가지. 서버를 늘렸는데 처리량이 안 오르면 직렬 구간부터 찾는다. DB CPU, 커넥션 풀 대기, 핫 로우 락 대기를 본다. 두 대로 늘린 직후 "로그인이 풀린다", "업로드한 이미지가 가끔 안 보인다", "메일이 두 통씩 간다"는 신고가 오면 서버 안에 남은 상태다. 그리고 8코어로 키웠는데 CPU 사용률이 12.5%(8분의 1)에 머물면 앱이 한 코어만 쓰고 있다.

## 더 큰 서버의 끝, 더 많은 서버의 조건

수직 확장은 쉽지만 천장과 단일 장애점이 있고, 앱이 늘어난 자원을 쓸 수 있어야 효과가 있다. 수평 확장은 천장이 멀지만 상태를 서버 밖으로 빼야 성립하고, 나눌 수 없는 부분(α)과 서로 맞추는 비용(β) 때문에 늘린 만큼 빨라지지 않는다. 그래서 확장 설계의 실제 일은 서버를 늘리는 것보다 직렬 구간과 공유 상태를 줄이는 쪽에 있다.

## 면접에서 나올 만한 질문

### 수평 확장과 수직 확장의 차이와 장단점은요?

수직 확장은 한 대의 자원을 키우는 것이라 코드 변경 없이 바로 효과를 볼 수 있지만, 가장 큰 인스턴스라는 천장과 단일 장애점이 있고 바꿀 때 재시작이 필요하다. 수평 확장은 같은 서버를 여러 대 두는 것이라 천장이 멀고 한 대가 죽어도 버티지만, 앱이 무상태여야 하고 로드 밸런서와 공유 저장소가 필요하다. 보통 수직으로 시작하고, 가용성이나 천장 문제가 보이면 수평으로 간다.

### 서버를 두 대로 늘렸더니 로그인이 자꾸 풀립니다. 왜 그런가요?

세션이 각 서버의 메모리에 있어서다. 로그인한 서버와 다음 요청을 받은 서버가 다르면 세션을 찾지 못한다. 세션을 Redis 같은 공유 저장소로 옮기거나 서명된 토큰을 쓰면 해결된다. 스티키 세션은 증상을 숨길 뿐 서버가 내려가면 세션이 같이 사라진다.

### 무상태 서버로 만들려면 무엇을 확인해야 하나요?

서버가 요청 사이에 기억하는 것을 모두 찾는다. 세션, 로컬 디스크에 저장한 업로드 파일, 서버별 메모리 캐시, 서버마다 도는 예약 작업, 웹소켓 연결, 프로세스 안의 락과 카운터가 대표적이다. 각각 공유 저장소, 객체 저장소, 공유 캐시, 단일 워커나 분산 락, pub/sub로 옮긴다.

### 코어를 두 배로 늘렸는데 처리량이 그대로인 이유는요?

앱이 늘어난 코어를 쓰지 못해서다. Node처럼 JS 코드를 한 스레드에서 돌리는 런타임은 프로세스 하나가 코어 하나만 쓴다. 실습에서 프로세스 하나는 초당 194건에서 멈췄고 프로세스를 늘리자 처리량이 올랐다. 그 외에 DB 커넥션 수, 전역 락처럼 코어와 상관없는 직렬 구간이 병목일 수도 있다.

### 암달의 법칙을 설명해 주세요.

전체 작업 중 병렬로 나눌 수 있는 비율이 p일 때 N개로 나누면 빨라지는 배수는 1 / ((1 − p) + p/N)이다. 나눌 수 없는 부분 때문에 최대 배수는 1 / (1 − p)로 제한된다. 직렬 부분이 10%면 아무리 늘려도 10배가 끝이다. 그래서 확장성을 높이려면 노드를 늘리기보다 직렬 구간을 줄여야 한다.

### 서버를 늘렸는데 오히려 처리량이 떨어질 수 있나요?

있다. 보편 확장성 법칙은 노드끼리 상태를 맞추는 비용(β)이 노드 수의 제곱으로 자란다고 보고, 이 비용이 있으면 처리량이 꼭짓점을 지나 내려간다. 공유 카운터 하나를 여러 고루틴이 두드리는 실험에서 일꾼을 1개에서 4개로 늘리자 처리량이 절반 가까이로 떨어졌다. 같은 캐시 키 무효화, 핫 로우 갱신, 노드 간 동기화가 분산 시스템에서 β를 키운다.

### DB는 왜 수평 확장이 어렵나요?

쓰기는 한 곳에서 순서를 정해야 해서 직렬 구간 그 자체이기 때문이다. 그래서 DB는 수직 확장으로 오래 버티고, 읽기가 많으면 읽기 복제본으로 읽기만 나누며, 쓰기와 데이터가 한 대를 넘으면 샤딩한다. 샤딩은 샤드를 넘는 쿼리와 트랜잭션이 비싸져서 마지막 카드로 쓴다.
