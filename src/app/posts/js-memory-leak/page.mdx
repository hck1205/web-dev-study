관리자 대시보드를 SPA로 만들었다고 하자. 목록 페이지와 차트 페이지를 오가며 쓰는 화면이다. 막 열었을 때는 빠른데, 하루 종일 켜 두고 페이지를 수십 번 오가면 스크롤이 버벅이고 클릭 반응이 늦어진다. 크롬 작업 관리자(Shift + Esc)를 열어 보면 그 탭의 메모리 수치가 처음 120MB에서 800MB까지 올라가 있다. 새로 고침하면 다시 120MB로 돌아온다.

자바스크립트는 메모리를 알아서 치워 주는 언어다. `free()`를 부를 일도 없다. 그런데 왜 메모리가 계속 차오를까. 답을 찾으려면 먼저 가비지 컬렉션이 무엇을 쓰레기로 보는지부터 알아야 한다.

## 쓰레기의 기준은 닿을 수 있느냐다

가비지 컬렉터(GC)는 "이 객체를 앞으로 쓸까"를 판단하지 못한다. 그건 프로그램의 의도라서 알 방법이 없다. 대신 더 단순한 질문을 한다. "루트에서 참조를 따라가서 이 객체에 닿을 수 있나?"

루트는 GC가 무조건 살아 있다고 보는 출발점이다. 전역 객체(`window`, `globalThis`), 지금 실행 중인 함수들의 지역 변수(콜 스택), 문서에 붙어 있는 DOM 트리, 엔진 내부 핸들 같은 것들이다. 루트에서 참조를 한 번이라도 따라가 닿는 객체는 살아 있고, 닿지 않는 객체는 쓰레기다.

## 루트에서 출발해 표시하고 치운다

이 방식의 약점은 표시하는 동안 프로그램이 객체 그래프를 바꾸면 안 된다는 데 있다. 가장 단순한 구현은 자바스크립트 실행을 멈추고(stop-the-world) GC를 돌린다. 힙이 수백 MB면 이 멈춤이 수십~수백 ms까지 길어질 수 있다. 그래서 V8은 표시를 잘게 나눠 자바스크립트 실행 사이사이에 하거나(incremental), 다른 스레드에서 동시에 한다(concurrent). 그 사이에 프로그램이 참조를 바꾸면 쓰기 장벽(write barrier)이라는 장치가 그 변경을 GC에게 알려 준다.

## 대부분의 객체는 금방 죽는다

함수 안에서 만든 임시 배열, `map`이 돌려준 중간 결과, 템플릿 문자열 같은 객체는 만들어지고 몇 ms 안에 쓸모가 없어진다. 이렇게 객체 대부분이 젊어서 죽는다는 관찰을 세대 가설(generational hypothesis)이라고 한다. V8은 힙을 두 세대로 나눠 이 성질을 이용한다.

새 객체는 작은 young generation(새 공간)에 들어간다. 여기는 자주, 빠르게 치운다(minor GC, Scavenge). 살아 있는 객체만 다른 반쪽 공간으로 복사하고 원래 반쪽은 통째로 비운다. 죽은 객체가 대부분이니 복사할 게 적어서 빠르다. 두 번의 minor GC에서 살아남은 객체는 old generation으로 옮겨진다(승격). old generation은 크고 덜 자주, 앞에서 본 mark-and-sweep에 압축(compact, 살아남은 객체를 한쪽으로 모아 빈틈을 없애기)을 더해 치운다(major GC).

누수와 연결하면 이렇다. 실수로 붙잡아 둔 객체는 minor GC를 계속 살아남아 old generation으로 간다. old generation이 커질수록 major GC가 할 일이 늘어나 멈춤이 길어지고 자주 일어난다. 누수가 메모리만 먹는 게 아니라 버벅임까지 만드는 이유다.

## 누수는 잊어버린 참조다

이제 누수를 정확히 말할 수 있다. GC가 있는 언어에서 메모리 누수는 "더 이상 쓰지 않는데 아직 루트에서 닿는 객체"다. GC는 닿는 객체를 절대 지우지 않는다. 그러니 누수는 GC의 버그가 아니라, 어딘가에 참조를 하나 남겨 둔 내 코드의 문제다.

정상인 앱의 메모리 그래프는 톱니 모양이다. 객체를 만들면서 올라가다가 GC가 돌면 뚝 떨어진다. 중요한 건 떨어진 바닥의 높이다. 아래 그림에서 다음을 누르면 정상 앱과 누수가 있는 앱의 그래프가 바뀐다.

같은 함수 참조라는 게 함정이다. `addEventListener("resize", () => draw())`처럼 화살표 함수를 바로 넘기면, 나중에 똑같이 생긴 화살표 함수로 `removeEventListener`를 불러도 다른 함수라서 떼지지 않는다. 여러 리스너를 한 번에 떼려면 `AbortController`가 편하다.

```js
const controller = new AbortController();
window.addEventListener("resize", onResize, { signal: controller.signal });
document.addEventListener("keydown", onKey, { signal: controller.signal });

// 정리할 때 한 줄로 전부 뗀다
controller.abort();
```

`setInterval`도 같은 구조다. 브라우저의 타이머 목록이 콜백을 잡고 있으니 `clearInterval`을 부르기 전까지 콜백과 콜백이 닿는 모든 것이 산다. `IntersectionObserver`, `ResizeObserver`의 `disconnect`, 웹소켓이나 이벤트 버스의 구독 해제도 마찬가지다.

React에서는 이 정리를 `useEffect`가 돌려주는 함수에서 한다.

```jsx
useEffect(() => {
  const controller = new AbortController();
  window.addEventListener("resize", onResize, { signal: controller.signal });
  const id = setInterval(poll, 5000);
  fetch("/api/rows", { signal: controller.signal }).then(/* ... */);

  return () => {
    controller.abort(); // 리스너 해제 + 진행 중인 요청 취소
    clearInterval(id);
  };
}, []);
```

개발 모드의 Strict Mode가 이펙트를 일부러 한 번 마운트, 언마운트, 다시 마운트하는 이유가 이것이다. 정리 함수를 빠뜨렸으면 개발 중에 리스너가 두 번 붙는 증상으로 바로 드러난다. 진행 중인 `fetch`를 취소하지 않는 것도 작은 누수다. 응답이 올 때까지 콜백이 컴포넌트의 상태와 클로저를 붙잡는다. React 18부터는 언마운트된 컴포넌트에 `setState`해도 경고가 나오지 않으니, 경고가 없다고 정리가 잘 됐다고 볼 수는 없다.

## 문서에서 떨어진 DOM

앞의 그림에 나온 detached DOM은 리스너 없이도 생긴다. DOM 요소를 자바스크립트 변수, 배열, `Map`에 담아 두고 요소만 문서에서 지우면 된다.

```js
const rowsById = new Map();
function renderRow(item) {
  const tr = document.createElement("tr");
  rowsById.set(item.id, tr); // 빨리 찾으려고 담아 둔다
  tbody.append(tr);
}

tbody.replaceChildren(); // 화면에서는 사라지지만 rowsById는 그대로다
```

DOM 요소 하나를 잡으면 그 요소의 부모와 자식으로 이어진 트리 전체가 함께 살아남는다. 테이블 행 하나를 잡았을 뿐인데 떨어져 나간 테이블 전체가 남는 식이다. 요소를 다 지울 때 담아 둔 자료구조도 같이 비우거나, 아래에서 볼 `WeakMap`처럼 요소가 사라지면 같이 사라지는 자료구조를 쓴다.

## 클로저는 생각보다 많이 잡는다

클로저는 바깥 함수의 변수를 잡는다. 여기까지는 다들 안다. 덜 알려진 사실이 있다. V8에서는 한 함수 안의 클로저들이 바깥 변수를 담은 상자(context)를 같이 쓴다.

```js
function setup() {
  const big = new Array(1_000_000).fill(1); // 약 8MB
  const report = () => console.log(big.length); // big을 쓰는 클로저
  return () => {}; // big을 안 쓰는 클로저를 돌려준다
}
const handlers = [];
for (let i = 0; i < 20; i++) handlers.push(setup());
```

돌려준 함수는 `big`을 쓰지 않는다. 그런데 같은 스코프의 `report`가 `big`을 쓰기 때문에 `big`은 공유 context에 들어가고, 돌려준 함수도 그 context를 잡는다. Node.js 22에서 `--expose-gc`로 GC를 돌린 뒤 `heapUsed`를 재 보면 이 코드는 약 150MB가 늘어난다. `report` 줄을 지우면 늘어난 양이 1MB도 안 된다. 쓰지 않는 클로저도 큰 객체를 잡을 수 있다는 뜻이다. 큰 데이터는 필요한 값만 꺼내 지역 변수에 담거나, 다 쓴 뒤 `big = null`로 끊는다.

## 끝없이 자라는 캐시

캐시는 일부러 참조를 남겨 두는 장치라서, 비우는 규칙이 없으면 정의상 누수다. 검색어별 결과를 `Map`에 쌓는 코드는 사용자가 검색할 때마다 커진다. 모듈 최상위에 둔 배열에 로그를 계속 `push`하는 코드, 엄격 모드가 아닌 스크립트에서 `var` 없이 대입해 생긴 전역 변수도 같은 부류다. 전역은 루트라서 거기 붙은 것은 영원히 산다.

해결은 크기 제한이다. 가장 흔한 방식이 LRU(Least Recently Used), 가장 오래 쓰지 않은 항목부터 버리는 캐시다. 자바스크립트 `Map`은 넣은 순서를 기억하니까, 조회할 때 지웠다가 다시 넣으면 맨 뒤(가장 최근)로 간다. 그러면 맨 앞이 가장 오래 쓰지 않은 항목이다. 아래 함수는 용량과 연산 목록을 받아, 연산이 끝난 뒤 캐시에 남은 키를 오래된 것부터 돌려준다. 테스트 기대값은 풀이를 Node.js에서 돌려 확인했다.

## 약하게 잡아 두는 방법

캐시의 키가 객체라면 다른 길이 있다. `WeakMap`은 키를 약하게 잡는다. 키 객체에 닿는 다른 참조가 모두 사라지면, `WeakMap`에 들어 있다는 사실은 그 객체를 살려 두지 못한다. 키가 치워지면 그 항목의 값도 같이 치워진다.

```js
const sizeCache = new WeakMap();
function measure(el) {
  if (!sizeCache.has(el)) sizeCache.set(el, el.getBoundingClientRect());
  return sizeCache.get(el);
}
// el이 DOM에서 지워지고 다른 참조가 없으면 캐시 항목도 함께 사라진다
```

앞의 `rowsById`처럼 DOM 요소에 데이터를 붙여 두는 용도에 딱 맞는다. 대가도 있다. 키는 객체(또는 등록되지 않은 심볼)만 된다. 언제 항목이 사라질지 GC가 정하니 `size`도 없고 순회도 못 한다. 그래서 문자열 키로 찾는 캐시, 개수를 세야 하는 캐시에는 쓸 수 없고 앞의 LRU가 맞다. `WeakSet`은 같은 성질의 집합이다.

`WeakRef`는 객체 하나를 약하게 가리키는 상자다. `ref.deref()`는 객체가 아직 살아 있으면 그 객체를, 치워졌으면 `undefined`를 돌려준다. `FinalizationRegistry`는 등록한 객체가 치워진 뒤 콜백을 불러 준다. 둘 다 쓸 일이 드물다. GC가 언제 돌지, 아니 돌기는 할지조차 보장되지 않기 때문에 콜백이 늦게 오거나 끝내 안 올 수 있다. 파일 닫기나 구독 해제처럼 반드시 해야 하는 정리를 여기에 맡기면 안 된다. 정리는 명시적으로 하고, 이 API들은 큰 캐시를 메모리 압박에 맞춰 줄이는 보조 장치 정도로 쓴다.

<Callout kind="warning" title="WeakMap은 누수를 고치는 도구가 아니다">
`WeakMap`은 키가 사라질 때 값을 따라 치워 줄 뿐이다. 키 객체를 리스너나 전역 배열이 여전히 잡고 있다면 값도 계속 산다. 누수를 찾았으면 먼저 그 참조를 누가 잡고 있는지 확인하고 끊는다.
</Callout>

## 크롬 개발자 도구로 범인 찾기

코드를 읽어서 찾을 수 있으면 좋겠지만, 실제로는 측정부터 한다. 순서는 이렇다.

먼저 누수가 있는지 확인한다. 개발자 도구의 More tools에서 Performance monitor를 열면 JS heap size, DOM Nodes, JS event listeners가 실시간 그래프로 나온다. 의심되는 동작(차트 페이지에 갔다가 목록으로 돌아오기)을 열 번쯤 반복한다. Memory 패널의 휴지통 버튼(Collect garbage)으로 GC를 돌린 뒤에도 세 숫자가 반복 횟수에 비례해 오르면 누수다. DOM Nodes만 오르면 detached DOM, event listeners가 오르면 떼지 않은 리스너부터 본다.

다음은 힙 스냅샷 비교다. Memory 패널에서 Heap snapshot을 고르고 아래처럼 찍는다. 스냅샷을 찍을 때는 항상 GC가 먼저 돌기 때문에 스냅샷에는 살아 있는 객체만 담긴다.

1. 페이지를 열고 한 번 워밍업(차트 페이지를 한 번 오가기)한 뒤 스냅샷 1
2. 같은 동작을 5번 반복하고 스냅샷 2
3. 다시 5번 반복하고 스냅샷 3

스냅샷 3을 선택하고 보기를 Summary로 둔 채 "Objects allocated between Snapshot 1 and Snapshot 2"를 고르면, 스냅샷 1과 2 사이에 생겨서 스냅샷 3까지 살아남은 객체만 남는다. 워밍업에서 생긴 정상적인 캐시는 걸러지고, 반복할 때마다 새로 생겨 안 죽는 것만 보인다. 개수가 5의 배수로 늘어난 클래스가 있으면 거의 범인이다. 두 스냅샷을 놓고 Comparison 보기로 바꾸면 클래스별 `# New`, `# Deleted`, `# Delta`, `Size Delta`를 볼 수 있다.

detached DOM은 Summary의 클래스 필터에 `Detached`를 입력하면 바로 나온다. 문서에서 떨어졌는데 살아 있는 DOM 요소가 `Detached`가 붙은 이름으로 모여 있다.

목록에서 객체를 하나 고르면 아래 Retainers 패널에 그 객체를 붙잡고 있는 경로가 나온다. 누수 원인은 거의 이 경로 안에 있다. 앞의 차트 예시라면 경로를 루트 쪽부터 다시 이어 붙였을 때 이렇게 된다. 조각을 눌러 보자.

## Node.js 서버가 점점 무거워질 때

서버의 누수는 더 늦게 드러난다. 배포 직후에는 멀쩡하다가 며칠 지나 메모리 경보가 울리거나, `FATAL ERROR: ... JavaScript heap out of memory`로 프로세스가 죽고 재시작된다. 컨테이너라면 메모리 한도를 넘어 OOM으로 죽는다. 재시작하면 한동안 괜찮아지니 원인을 미루기 쉽다.

먼저 숫자를 본다. `process.memoryUsage()`는 이런 값을 돌려준다(빈 Node.js 22 프로세스에서 찍은 값, 단위는 바이트).

```js
{
  rss: 43606016,       // 프로세스가 실제로 차지한 물리 메모리 전체
  heapTotal: 5345280,  // V8이 확보해 둔 힙
  heapUsed: 3774992,   // 그중 실제로 쓰는 힙
  external: 1302304,   // V8 밖 C++ 메모리 (Buffer 등)
  arrayBuffers: 10511  // external 중 ArrayBuffer·Buffer 몫
}
```

이 값을 주기적으로 지표로 보내고, 요청량이 비슷한 시간대끼리 GC 직후의 `heapUsed`를 비교한다. 브라우저의 톱니 그림과 똑같이 바닥이 계속 오르면 자바스크립트 힙 누수다. `heapUsed`는 평평한데 `rss`만 오르면 힙 밖이다. 해제하지 않은 `Buffer`, 네이티브 모듈의 누수, 메모리 단편화를 의심한다. 둘을 나눠 보지 않으면 힙 스냅샷을 아무리 뒤져도 안 나오는 문제에 시간을 쓴다.

서버에서 흔한 누수 자리도 브라우저와 닮았다. 요청이나 사용자 ID를 키로 모듈 최상위 `Map`에 쌓는 캐시, 요청마다 공유 `EventEmitter`에 `on`으로 붙이고 떼지 않는 리스너가 대표적이다. 후자는 같은 이벤트에 리스너가 10개를 넘으면 Node.js가 `MaxListenersExceededWarning`을 찍어 주니 이 경고를 무시하지 않는다. `setMaxListeners`로 경고만 끄는 건 증상을 숨기는 일이다.

원인은 힙 스냅샷으로 찾는다. 로컬이나 스테이징이라면 `node --inspect server.js`로 띄우고 크롬에서 `chrome://inspect`를 열어 해당 프로세스의 개발자 도구를 띄운다. 그다음은 브라우저와 똑같다. 부하 도구로 요청을 일정량 보내고 스냅샷, 또 보내고 스냅샷을 찍어 비교한다.

운영 중인 프로세스에서는 코드로 찍는다.

```js
// node --heapsnapshot-signal=SIGUSR2 server.js 로 띄우면
// kill -USR2 <pid> 로도 찍을 수 있다
import v8 from "node:v8";
const file = v8.writeHeapSnapshot(); // 현재 디렉터리에 .heapsnapshot 파일을 쓴다
```

`.heapsnapshot` 파일은 크롬 Memory 패널에서 Load로 열면 된다. 주의할 게 있다. 스냅샷을 쓰는 동안 이벤트 루프가 완전히 멈추고, 힙 크기 정도의 메모리를 추가로 쓴다. 이미 한도 근처인 프로세스에서 찍으면 그 자체로 OOM이 날 수 있다. 로드밸런서에서 뺀 인스턴스 하나에서 찍거나, `--heapsnapshot-near-heap-limit=1` 옵션으로 힙 한도에 닿기 직전에 자동으로 한 장 남기게 한다.

`--max-old-space-size`로 힙 한도를 늘리는 건 처방이 아니다. 누수라면 죽는 시점이 늦춰질 뿐이고, 컨테이너 메모리 한도보다 크게 잡으면 V8이 GC로 버티기 전에 컨테이너가 먼저 죽는다. 원래 데이터가 큰 서비스라 한도를 올려야 한다면, 컨테이너 한도보다 여유 있게 작게 잡는다.

## 다시 느려지는 탭으로

처음의 대시보드가 800MB까지 올라간 건 GC가 일을 안 해서가 아니다. 페이지를 오갈 때마다 어딘가(리스너, 타이머, `Map`, 클로저)에 참조가 하나씩 남았고, GC는 루트에서 닿는 객체를 지우지 않는다는 규칙대로 움직였을 뿐이다. 찾을 때는 반복 동작 뒤 GC 직후의 바닥을 보고, 스냅샷 비교로 반복 횟수만큼 늘어나는 객체를 고르고, Retainers 경로에서 그 객체를 붙잡은 참조를 찾아 끊는다.

## 면접에서 나올 만한 질문

### 자바스크립트의 가비지 컬렉터는 무엇을 기준으로 메모리를 회수하나요?

도달 가능성이다. 전역 객체, 콜 스택의 지역 변수 같은 루트에서 참조를 따라가 닿을 수 있는 객체는 살리고 나머지를 회수한다. 기본 알고리즘은 루트부터 표시하고 표시 없는 객체를 치우는 mark-and-sweep이다. 그래서 서로를 참조하는 순환 구조도 루트에서 끊기면 회수된다.

### V8의 세대별 GC는 왜 나눠서 하나요?

대부분의 객체가 만들어지고 금방 죽는다는 관찰 때문이다. 새 객체는 작은 young generation에 두고 살아 있는 것만 복사하는 Scavenge로 자주 빠르게 치운다. 두 번 살아남으면 old generation으로 승격하고, 거기는 mark-sweep-compact로 드물게 치운다. 표시 작업은 incremental, concurrent로 나눠 메인 스레드 멈춤을 줄인다.

### GC가 있는데 메모리 누수가 어떻게 생기나요?

GC는 닿을 수 있는 객체를 지우지 않기 때문이다. 더 쓰지 않는데 어딘가에 참조가 남아 있으면 GC 입장에서는 살아 있는 객체다. SPA에서는 떼지 않은 window 리스너, 해제하지 않은 `setInterval`, 문서에서 지웠지만 변수에 남은 DOM, 크기 제한 없는 캐시, 정리 함수 없는 `useEffect`가 흔한 원인이다.

### Map 대신 WeakMap을 쓰면 무엇이 달라지나요?

`WeakMap`은 키를 약하게 잡아서, 키 객체에 다른 참조가 없으면 항목이 키와 함께 회수된다. DOM 요소나 객체에 부가 데이터를 붙일 때 정리 코드 없이도 새지 않는다. 대신 키는 객체만 되고, `size`와 순회가 없다. 문자열 키 캐시나 개수 제한이 필요한 캐시는 LRU 같은 명시적 정책이 맞다.

### WeakRef와 FinalizationRegistry로 리소스 정리를 하면 안 되나요?

안 된다. GC가 언제 돌지, 돌지조차 보장되지 않아서 콜백이 늦거나 아예 오지 않을 수 있다. 엔진마다 동작도 다를 수 있다. 파일, 소켓, 구독 같은 정리는 명시적으로 하고, 이 API들은 메모리 압박에 따라 줄어들어도 되는 캐시 같은 보조 용도로만 쓴다.

### 크롬 개발자 도구로 누수를 어떻게 찾나요?

Performance monitor에서 같은 동작을 반복하며 GC 후에도 JS heap, DOM Nodes, 리스너 수가 계속 오르는지 본다. 그다음 워밍업 후 스냅샷 1, 반복 후 스냅샷 2, 또 반복 후 스냅샷 3을 찍고, 스냅샷 1과 2 사이에 할당돼 3까지 살아남은 객체를 본다. 반복 횟수에 비례해 늘어난 객체를 골라 Retainers 경로에서 붙잡은 참조를 찾는다. detached DOM은 `Detached` 필터로 바로 걸러진다.

### Shallow size와 Retained size의 차이는 무엇인가요?

Shallow size는 객체 자신이 차지하는 크기이고, Retained size는 그 객체가 회수되면 함께 풀려나는 전체 크기다. 배열이나 클로저 context처럼 자신은 작아도 큰 객체를 혼자 붙잡고 있으면 Retained size가 크다. 누수 원인을 찾을 때는 Retained size로 정렬한다.

### Node.js 서버의 메모리가 계속 오르면 어떻게 접근하나요?

먼저 `process.memoryUsage()`를 지표로 보고 GC 직후 `heapUsed`가 오르는지, `heapUsed`는 평평한데 `rss`만 오르는지 나눈다. 앞이면 자바스크립트 힙 누수라서 `--inspect`나 `v8.writeHeapSnapshot()`, `--heapsnapshot-signal`로 스냅샷을 찍어 비교한다. 뒤면 Buffer, 네이티브 모듈, 단편화를 본다. 스냅샷은 이벤트 루프를 멈추고 메모리를 더 쓰니 트래픽에서 뺀 인스턴스에서 찍고, `--max-old-space-size`를 올리는 건 해결이 아니라 지연이다.
