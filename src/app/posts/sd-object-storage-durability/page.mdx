디스크 1만 장으로 객체 저장소를 운영한다고 하자. 하드디스크는 1년에 대략 1~2%가 고장 난다(Backblaze 같은 곳이 매년 공개하는 통계가 대체로 이 범위다. 모델과 연식에 따라 크게 다르다). 1%로만 잡아도 1년에 100장, 일주일에 두 장꼴이다. 디스크 고장은 사고가 아니라 일과다. 그래서 질문이 바뀐다. "디스크가 죽으면 어떡하나"가 아니라 "디스크가 매주 죽어도 데이터를 잃지 않으려면 몇 벌을 어디에 두고, 얼마나 빨리 다시 만들어야 하나"다.

## 세 벌을 두면 몇 개의 9가 나오나

내구성(durability)은 저장한 데이터를 1년 동안 잃지 않을 확률이다. 99.9999%처럼 9의 개수로 말한다. 9가 여섯 개면 객체 100만 개 중 1년에 하나쯤 잃는다는 뜻이다. 가용성(availability)과 헷갈리기 쉽다. 가용성은 지금 요청에 응답하느냐이고, 내구성은 데이터가 아직 존재하느냐다. 서버가 한 시간 멈추면 가용성은 떨어지지만 데이터는 멀쩡할 수 있다.

같은 객체를 서로 다른 디스크 세 장에 두면 세 장이 모두 고장 나야 잃는다. 고장이 서로 독립이라고 치고, 디스크 연간 고장률(AFR)을 1%로 잡아 두 경우를 계산해 봤다. 하나는 고장 난 디스크를 다시 채우지 않는 경우, 다른 하나는 고장 나면 정해진 시간 안에 다른 디스크에 다시 복제하는 경우다.

```js
// durability.mjs: 디스크가 독립적으로 고장 난다고 가정한 대략의 손실 확률
const C = (n, r) => { let v = 1; for (let i = 1; i <= r; i++) v = (v * (n - r + i)) / i; return v; };
const nines = (loss) => (-Math.log10(loss)).toFixed(1);
const afr = 0.01;                 // 디스크 연간 고장률 1%
// (가) 고치지 않는다: 1년 안에 n개 중 m+1개 이상이 고장 나면 잃는다
function noRepair(n, m) {
  let s = 0;
  for (let j = m + 1; j <= n; j++) s += C(n, j) * afr ** j * (1 - afr) ** (n - j);
  return s;
}
// (나) 고장 나면 repairHours 안에 다시 만든다: 첫 고장 뒤 그 시간 안에 m개가 더 고장 나야 잃는다
function withRepair(n, m, repairHours) {
  const q = afr * repairHours / (365 * 24);   // 한 디스크가 수리 시간 안에 고장 날 확률(근사)
  return n * afr * C(n - 1, m) * q ** m;
}
for (const [name, n, m] of [["3 replicas", 3, 2], ["4+2", 6, 2], ["8+4", 12, 4]]) {
  const a = noRepair(n, m), b = withRepair(n, m, 24), c = withRepair(n, m, 168);
  console.log(`${name.padEnd(10)} no-repair ${a.toExponential(1)} (${nines(a)} nines) | repair 24h ${b.toExponential(1)} (${nines(b)}) | repair 7d ${c.toExponential(1)} (${nines(c)})`);
}
```


첫 줄만 먼저 보자. 4+2, 8+4는 아래에서 설명한다. 세 벌을 두고 아무것도 안 하면 0.01³ = 10⁻⁶, 9가 여섯 개다. 그런데 고장 난 사본을 24시간 안에 다시 만들면 10.6개로 뛴다. 같은 세 벌인데 수리 속도만으로 9가 네 개 넘게 늘었다. 데이터를 잃으려면 첫 디스크가 죽은 뒤 수리가 끝나기 전, 그 짧은 틈에 나머지 두 장이 연달아 죽어야 하기 때문이다. 수리가 7일로 늘어지면 9.0개로 내려간다. 내구성은 사본 수만큼 수리 속도가 정한다.

이 계산을 그대로 믿으면 안 된다. 독립 고장이라는 가정이 실제로는 가장 먼저 깨진다. 같은 날 같은 공장에서 나온 디스크는 비슷한 시기에 같이 죽고, 랙 전원 하나가 나가면 그 랙의 디스크가 동시에 사라진다. 소프트웨어 버그 하나가 모든 사본을 똑같이 지울 수도 있다. 위 숫자는 "수리를 빨리 하면 얼마나 좋아지는지" 같은 상대 비교에만 쓰고, 실제 내구성은 고장을 서로 떨어뜨려 놓는 배치가 정한다.

## 몇 벌이 확인해야 성공인가

## 세 벌은 비싸다

복제는 단순하고 읽기도 빠르다. 사본 아무거나 하나만 읽으면 된다. 문제는 값이다. 100TB를 저장하려면 300TB의 디스크가 필요하다. 원본 외에 200%를 더 쓰는 셈이다. 데이터가 50PB면 100PB를 순전히 사본에 쓴다.

이레이저 코딩(erasure coding)은 다른 방법으로 같은 목표에 간다. 객체를 k개의 데이터 조각으로 자르고, 그 조각들로 계산한 패리티 조각 m개를 더 만든다. k + m개를 서로 다른 노드에 두면, 그중 아무 m개를 잃어도 남은 k개로 원본을 되살린다. "4+2"는 데이터 4조각, 패리티 2조각이라는 뜻이다.

가장 쉬운 패리티는 XOR이다. XOR은 두 비트가 다르면 1, 같으면 0을 내는 연산이다. 같은 값을 두 번 XOR하면 사라진다(a ^ b ^ b = a). 그래서 P = D0 ^ D1 ^ D2 ^ D3를 저장해 두면, 데이터 조각 하나를 잃었을 때 나머지 셋과 P를 XOR해서 잃은 조각을 다시 만든다. 16바이트 객체 `OBJECT-STORAGE!!`를 4바이트씩 넷으로 자르고 첫 바이트만 따라가 보자.

4+1은 데이터 4에 패리티 1이라 저장 공간이 원본의 1.25배다. 세 벌의 3배와 비교하면 훨씬 싸다. 대신 한 조각만 잃을 수 있다.

## 둘을 잃어도 되살리려면

조각 둘을 잃으면 XOR 하나로는 안 된다. P에서 아는 건 "잃은 둘을 XOR한 값"뿐이라 두 값을 가를 수 없다. 패리티를 하나 더 두되, 이번엔 조각마다 다른 계수를 곱해서 더한다. Q = 1·D0 ^ 2·D1 ^ 4·D2 ^ 8·D3 같은 식이다. 그러면 모르는 값 둘에 식 둘이 생겨 풀린다.

여기서 곱셈은 보통 곱셈이 아니라 GF(2⁸)라는 유한체의 곱셈이다. 0~255 바이트끼리 곱하고 나눠도 결과가 다시 0~255 안에 머물고, 0이 아닌 값으로 나눌 수 있도록 정의한 연산이다. 덧셈은 XOR이다. RAID 6가 이 방식(P와 Q 두 패리티)을 쓰고, 이것을 일반화해 m개의 패리티를 만드는 것이 리드-솔로몬 부호다. 곱셈표를 만들어 4+2를 직접 구현했다.

```js
// erasure.mjs (발췌): GF(2^8) 곱셈표 (다항식 0x11d, 생성원 2)
const EXP = new Uint8Array(512), LOG = new Uint8Array(256);
for (let i = 0, x = 1; i < 255; i++) {
  EXP[i] = x; LOG[x] = i;
  x <<= 1; if (x & 0x100) x ^= 0x11d;
}
for (let i = 255; i < 512; i++) EXP[i] = EXP[i - 255];
const mul = (a, b) => (a && b ? EXP[LOG[a] + LOG[b]] : 0);
const div = (a, b) => (a ? EXP[LOG[a] + 255 - LOG[b]] : 0);
const g = (i) => EXP[i];                                 // 2^i

const D = [0, 1, 2, 3].map((i) => Uint8Array.from(obj.subarray(i * 4, i * 4 + 4)));
const P = xor(...D);                                     // P = D0 ^ D1 ^ D2 ^ D3
const Q = D.reduce((acc, d, i) => acc.map((v, j) => v ^ mul(g(i), d[j])), new Uint8Array(4));

// D_x, D_y를 잃었을 때: 남은 조각을 빼면
//   Pxy = Dx ^ Dy,  Qxy = g^x·Dx ^ g^y·Dy  -> 두 식을 풀어
//   Dx = (Qxy ^ g^y·Pxy) / (g^x ^ g^y),  Dy = Pxy ^ Dx
```


```text
8+4        raw 24 bytes for 16 -> overhead 50%
```

4+1은 둘을 잃자 `D1^D2`라는 값 하나만 남기고 멈췄다. 4+2는 D1과 D2를 동시에 잃어도 P와 Q로 둘 다 되살려 원본 `OBJECT-STORAGE!!`를 다시 만들었다. 데이터 하나와 P를 잃은 경우도 Q로 데이터를 푼 다음 P를 다시 계산했다. 저장 공간은 4+2가 1.5배로, 세 벌의 절반이다. 그러면서 견디는 고장 수는 둘로 같다.

실제 시스템은 이 계산을 SIMD 명령으로 빠르게 돌리는 라이브러리(Intel ISA-L 같은 것)를 쓴다. HDFS는 RS-6-3(데이터 6, 패리티 3)을 기본 정책 중 하나로 제공하고, Backblaze는 17+3으로 20대의 서버에 나눈다고 공개했다. Ceph와 MinIO도 k와 m을 설정으로 고른다.

## 무엇을 고를지 숫자로 비교한다

앞의 내구성 계산을 다시 보자. 4+2는 세 벌과 똑같이 둘을 견디는데 9의 개수는 오히려 적다(수리 24시간 기준 9.3 대 10.6). 디스크가 3장에서 6장으로 늘어서 그중 셋이 겹쳐 죽을 경우의 수가 많아졌기 때문이다. 8+4는 넷까지 견디니 16.7로 압도적이다. 저장 공간은 4+2와 8+4가 1.5배로 같다. 같은 1.5배라면 k와 m을 함께 키울수록 내구성이 좋아지지만, 읽을 때와 수리할 때 거쳐야 할 노드도 늘어난다.

| 방식 | 디스크 사용 | 견디는 고장 | 읽기에 필요한 노드 | 조각 하나 수리에 읽는 양 |
|---|---|---|---|---|
| 세 벌 복제 | 3배 | 2 | 1 | 사본 1개 |
| 4+2 | 1.5배 | 2 | 4 | 조각 4개 |
| 8+4 | 1.5배 | 4 | 8 | 조각 8개 |

그래서 실무에서는 섞어 쓴다. 갓 올라와 자주 읽히는 객체와 작은 객체는 복제로 두고, 시간이 지나 덜 읽히는 큰 데이터는 이레이저 코딩으로 옮긴다. 작은 객체를 바로 8조각으로 자르면 4KiB 객체가 512바이트 조각 12개가 되어, ①편에서 본 블록 낭비와 IOPS 문제가 12배로 커진다. 그래서 작은 객체는 먼저 볼륨 파일로 모은 다음, 수 GB짜리 볼륨 단위로 이레이저 코딩을 거는 방법을 쓴다.

직접 계산해 보자. 원본 크기와 k, m을 받아 필요한 원시 디스크 용량, 추가로 쓰는 비율, 견디는 고장 수, 읽기에 필요한 노드 수를 돌려준다. 세 벌 복제는 k=1, m=2로 넣으면 같은 공식에 들어간다.

## 디스크가 조용히 틀린 값을 줄 때

디스크가 통째로 죽으면 오히려 쉽다. 노드가 하트비트를 못 보내니 바로 안다. 더 무서운 건 디스크가 정상인 척하면서 틀린 바이트를 돌려줄 때다. 자기장이 약해진 섹터, 펌웨어 버그, 메모리나 케이블에서 생긴 오류로 비트가 뒤집힌다. 이렇게 저장된 데이터가 시간이 지나며 조용히 망가지는 현상을 비트 부패(bit rot)라고 한다. 운영체제는 읽기 오류를 보고받지 못하니 그대로 앱에 넘긴다.

막는 방법은 체크섬이다. 객체를 쓸 때 내용으로 짧은 지문(CRC32나 해시)을 계산해 위치표에 같이 적고, 읽을 때마다 다시 계산해 비교한다. 다르면 이 사본은 믿지 않고 다른 사본에서 읽은 뒤, 좋은 사본으로 망가진 쪽을 덮어 고친다. 메모 객체 `pay 100 to bob`의 비트 하나를 일부러 뒤집어 봤다.

```js
// bitrot.mjs (발췌): 체크섬 없이 읽기 vs 체크섬으로 잡고 복제본에서 고치기
mapping.push({ name, offset: off, size: buf.length, crc: zlib.crc32(buf) });   // 쓸 때 기록

// 디스크의 비트 하나가 뒤집힌다: "100"의 '1'(0x31)이 '9'(0x39)로 (비트 3)
one[0] ^= 0b00001000; fs.writeSync(fd, one, 0, 1, pos);

function verifiedRead(m) {
  const a = read("nodeA", m);
  const got = zlib.crc32(a);
  if (got === m.crc) return a.toString();
  console.log(`  nodeA crc ${hex(got)} != 기록 ${hex(m.crc)} -> 손상, nodeB에서 읽는다`);
  const b = read("nodeB", m);
  if (zlib.crc32(b) !== m.crc) throw new Error("두 복제본 모두 손상");
  const w = fs.openSync("./rot/nodeA/vol-0001.dat", "r+");
  fs.writeSync(w, b, 0, b.length, m.offset); fs.closeSync(w);   // 좋은 사본으로 덮어 고친다
  return b.toString();
}
```

```text
체크섬 없이 읽기 : pay 900 to bob
  nodeA crc 0600960d != 기록 15d7d6f9 -> 손상, nodeB에서 읽는다
체크섬으로 읽기  : pay 100 to bob
다시 읽기        : pay 100 to bob (이번엔 경고 없음)
스크럽 결과      : 3 개 검사, 0 개 손상
```

체크섬 없이 읽으면 `pay 900 to bob`이 아무 경고 없이 나온다. 비트 하나에 100원이 900원이 됐다. 체크섬을 확인하면 값이 다르다는 걸 알고 다른 노드에서 올바른 값을 읽었고, 망가진 사본도 고쳐서 다음 읽기부터는 경고가 없다.

마지막 줄의 스크럽(scrub)도 필요하다. 체크섬은 읽을 때만 확인되는데, 몇 년 동안 아무도 안 읽는 백업 객체가 대부분이다. 그사이 사본 셋이 하나씩 차례로 썩으면 정작 필요할 때 좋은 사본이 없다. 그래서 백그라운드에서 모든 객체를 주기적으로(예: 몇 주에 한 바퀴) 훑어 체크섬을 확인한다. 스크럽이 디스크를 너무 바쁘게 하면 사용자 요청이 느려지니 속도를 제한해서 돌린다.

이레이저 코딩에서는 조각마다 체크섬을 둔다. 8+4라면 읽은 조각 여덟 개를 각각 확인하고, 하나가 틀리면 그 조각을 버리고 패리티로 되살린다. 객체 전체의 체크섬과 볼륨 파일 전체의 체크섬을 함께 두면, 객체 하나를 읽을 때와 볼륨을 통째로 옮길 때 모두 검사할 수 있다.

## 어떤 체크섬을 쓰나

체크섬은 읽기마다 계산하니 속도가 중요하다. 256MiB를 종류별로 계산해 봤다.

```js
// hashspeed.mjs: 256MiB를 체크섬 종류별로 계산하는 데 걸리는 시간
const buf = crypto.randomBytes(256 * 1024 * 1024);
t("crc32", (b) => zlib.crc32(b));
t("md5", (b) => crypto.createHash("md5").update(b).digest());
t("sha256", (b) => crypto.createHash("sha256").update(b).digest());
```

```text
crc32      98 ms   2617 MiB/s
md5       478 ms    536 MiB/s
sha256    203 ms   1262 MiB/s
```

이 컨테이너(Xeon 2.1GHz, Node 22.22) 기준으로 CRC32가 SHA-256보다 두 배, MD5보다 다섯 배쯤 빠르다. SHA-256이 MD5보다 빠르게 나온 건 이 CPU에 SHA 전용 명령(`sha_ni`)이 있어서로 보인다. 기계마다 순위가 바뀔 수 있다. 우연한 비트 오류를 잡는 데는 CRC면 충분하다. 누군가 일부러 같은 체크섬을 갖는 다른 내용을 만들어 끼워 넣는 공격까지 막으려면 SHA-256 같은 암호 해시를 쓴다. [파일 동기화 설계 ①](/posts/sd-file-sync-block-upload)에서 블록 이름으로 SHA-256을 쓴 것도 같은 내용이면 같은 블록으로 합치려면 충돌이 사실상 없어야 해서다.

체크섬은 디스크 안에서만 쓰는 게 아니다. 클라이언트에서 네트워크, API 서비스, 데이터 노드까지 오는 길에도 비트가 뒤집힐 수 있다. 그래서 클라이언트가 올릴 때 체크섬을 함께 보내고, 서버가 받은 내용으로 다시 계산해 다르면 거절한다. 처음부터 끝까지 같은 값을 들고 가니 종단 간 체크섬이라고 부른다. 아래 요청의 헤더를 눌러 보자. 값은 `pay 100 to bob` 14바이트로 직접 계산했다.

AWS SDK는 2024년 말 무렵 나온 버전부터 올리기 요청에 CRC 계열 체크섬을 기본으로 붙인다(언어별 SDK마다 시작 버전이 다르다). 오래된 SDK나 직접 만든 클라이언트는 따로 켜야 한다. 체크섬을 암호화 전에 계산할지 후에 계산할지도 정해야 한다. 디스크에는 암호문이 놓이니 디스크 쪽 체크섬은 암호문으로, 사용자에게 약속하는 체크섬은 평문으로 계산하는 게 자연스럽다. 저장 시 암호화와 키 관리는 [저장 데이터 암호화](/posts/encryption-at-rest)에 정리했다.

## 현장에서 내구성이 깨지는 순간

설계만큼 운영이 내구성을 정한다. 지켜볼 지표는 이렇다. 복제 수나 조각 수가 모자란 객체의 수(degraded objects), 수리 대기열의 길이, 수리 속도(초당 몇 GB를 되살리는가), 스크럽이 찾은 체크섬 불일치 수. 디스크 하나가 죽은 뒤 수리 대기열이 줄지 않고 계속 쌓이면, 앞의 계산에서 본 "수리 7일" 쪽으로 가고 있다는 신호다. 이때 사용자 트래픽 때문에 수리를 너무 느리게 제한해 두지 않았는지 본다.

흔한 실수도 있다. 사본 셋을 같은 랙 서버에 두고 "세 벌이니 안전하다"고 믿는 것, 체크섬은 있는데 스크럽이 꺼져 있는 것, 그리고 복제나 패리티를 백업으로 착각하는 것이다. 복제는 디스크 고장을 막지만 실수로 지운 객체도 세 벌 모두에서 지운다. 랜섬웨어가 덮어쓴 객체도 충실히 세 벌로 복제된다. 사람의 실수와 공격에는 버전 관리와 지울 수 없는 사본이 필요하다. 버전 관리는 다음 글에서 만들고, 보관 기간 동안 아무도 지우지 못하게 잠그는 Object Lock은 [백업 전략](/posts/backup-strategy)에서 다뤘다.

## 다음에 읽을 글

사본 셋을 장애 도메인에 나눠 두고, 수리를 빨리 하는 것이 내구성을 올린다는 걸 계산으로 봤다. 같은 내구성을 절반 가격에 얻으려면 이레이저 코딩을 쓰고, 그 대가로 읽기와 수리에 노드를 여럿 거친다. 비트 부패는 체크섬과 스크럽으로 잡는다. 다음 글 [객체 저장소 설계 ③: 버전, 멀티파트 업로드, 가비지 컬렉션](/posts/sd-object-storage-versioning-multipart)에서는 사람이 실수로 덮어쓴 객체를 되돌리는 버전 관리, 큰 파일을 조각으로 올리는 멀티파트 업로드, 그리고 그 과정에서 생긴 쓰레기를 치우는 일을 만든다.

같은 키를 N대에 복제하고 몇 대의 확인을 기다릴지 정하는 쿼럼 이야기는 [키-값 저장소 설계 ①](/posts/sd-kv-store-partition-replication)에, 복제본끼리 다른 부분을 해시 트리로 빠르게 찾는 방법은 [머클 트리](/posts/merkle-tree)에 있다.

## 면접에서 나올 만한 질문

### 내구성과 가용성은 어떻게 다른가요?

내구성은 데이터가 사라지지 않을 확률이고, 가용성은 지금 요청에 응답할 확률이다. AZ 하나가 한 시간 멈추면 그곳에만 있는 객체는 그동안 못 읽지만(가용성 하락) 디스크가 멀쩡하면 잃지는 않는다(내구성 유지). 객체 저장소는 보통 내구성을 훨씬 높게 잡는다. 잃은 데이터는 되돌릴 수 없어서다.

### 세 벌 복제로 몇 개의 9가 나오나요?

디스크 고장률 1%에 고장이 독립이라면 수리하지 않을 때 0.01³ = 10⁻⁶, 9가 여섯 개다. 고장 난 사본을 24시간 안에 다시 만들면 10개가 넘는다. 수리 전 틈에 나머지 둘이 연달아 죽어야만 잃기 때문이다. 다만 실제로는 같은 랙이나 같은 배치의 디스크가 함께 죽는 상관 고장이 지배적이라, 사본을 서로 다른 장애 도메인에 두는 것이 숫자보다 중요하다.

### 이레이저 코딩은 어떻게 동작하나요?

객체를 k개 데이터 조각으로 자르고 그 조각으로 m개 패리티를 계산해 k + m개를 다른 노드에 둔다. 아무 m개를 잃어도 남은 k개로 되살린다. 패리티 하나면 XOR로 충분하고, 둘 이상이면 GF(2⁸) 위에서 조각마다 다른 계수를 곱한 리드-솔로몬 부호를 쓴다. 4+2로 조각 둘을 지우고 P, Q로 원본을 되살리는 것을 직접 확인했다.

### 복제와 이레이저 코딩은 언제 무엇을 고르나요?

자주 읽고 지연에 민감하거나 작은 객체는 복제, 덜 읽히는 큰 데이터는 이레이저 코딩이다. 8+4는 1.5배 공간으로 넷을 견뎌 세 벌(3배)보다 싸고 내구성도 높다. 대신 평소 읽기도 노드 여덟을 거쳐 꼬리 지연이 길어지고, 조각 하나를 수리할 때 여덟 조각을 읽어야 해서 수리 트래픽이 크다. 그래서 새 객체는 복제로 받고, 시간이 지나면 볼륨 단위로 이레이저 코딩으로 옮기는 방식을 많이 쓴다.

### 4+2와 세 벌 복제는 둘 다 고장 둘을 견디는데 내구성이 같나요?

아니다. 4+2는 디스크 여섯 장에 걸쳐 있어서 셋이 겹쳐 죽는 경우의 수가 세 벌보다 많다. 같은 고장률과 24시간 수리로 계산하면 세 벌이 10.6개, 4+2가 9.3개의 9였다. 내구성을 올리려면 m을 키워야 하고, 공간을 같게 유지하려면 k도 같이 키운다. 8+4가 16개가 넘게 나온 이유다.

### 디스크가 고장 나지 않았는데 데이터가 틀리면 어떻게 아나요?

체크섬이다. 쓸 때 객체와 조각마다 CRC나 해시를 계산해 저장하고, 읽을 때 다시 계산해 비교한다. 다르면 다른 사본이나 패리티로 읽고 망가진 쪽을 고친다. 아무도 읽지 않는 객체를 위해 백그라운드 스크럽으로 주기적으로 전체를 검사한다. 클라이언트도 올릴 때 체크섬을 보내 네트워크 구간의 오류까지 잡는다.

### 디스크가 하나 죽으면 무슨 일이 일어나나요?

하트비트가 끊기면 배치 서비스가 그 디스크를 배치도에서 빼고, 그 디스크에 있던 사본이나 조각 목록을 수리 대기열에 넣는다. 복제는 남은 사본에서 복사하고, 이레이저 코딩은 남은 k개 조각을 읽어 계산한다. 수리 속도가 곧 내구성이라 수리 대기열 길이와 속도를 지표로 본다. 너무 느리면 사용자 트래픽 제한보다 수리를 우선한다.

### 데이터가 10배로 늘면 무엇이 달라지나요?

디스크 수가 10배라 고장도 10배, 수리 트래픽도 10배다. 복제로 버티던 비용이 감당되지 않으면 차가운 데이터부터 이레이저 코딩으로 옮겨 디스크를 절반으로 줄인다. 이때 k + m이 커지면 읽기와 수리에 거치는 노드가 늘어나니, 장애 도메인 수(AZ, 랙)가 조각 배치를 감당하는지도 함께 확인한다.
