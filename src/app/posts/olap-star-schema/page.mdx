4월 초에 뽑아 둔 "3월 지역별 매출" 보고서가 있다. 5월에 같은 쿼리로 3월을 다시 뽑았더니 서울 매출이 줄고 부산 매출이 늘었다. 3월 주문은 하나도 바뀌지 않았다. 바뀐 건 회원 정보다. 4월에 서울에서 부산으로 이사한 회원의 주소를 회원 테이블에서 고쳤고, 보고서는 주문을 회원 테이블에 조인해 지역을 가져온다. 그 회원이 3월에 서울에서 산 책이 지금은 부산 매출로 잡힌다.

운영 DB의 테이블을 분석 DB로 그대로 옮겨 놓으면 이런 일이 생긴다. 운영 DB는 "지금 이 회원은 어디 사나"를 정확히 답하도록 설계됐고, 분석은 "그때 이 매출은 어디서 났나"를 묻는다. 이 글은 분석 DB에 데이터를 어떤 모양으로 넣는지, 그중 가장 흔한 스타 스키마를 다룬다.

같은 주제의 다른 글과 나눠 맡는다. 컬럼 저장이 왜 분석에 빠른지(압축, 벡터화, 건너뛰기)와 ClickHouse, BigQuery 같은 엔진의 쓰임새는 [컬럼형 분석 DB](/posts/db-type-columnar-olap)에 있다. 운영 DB의 변경을 분석 DB로 옮기는 방법은 [CDC 글](/posts/cdc-change-data-capture)에 있다. 이 글은 그 사이, 옮겨 온 데이터를 무슨 테이블로 짜는지를 본다. 숫자는 DuckDB 2.0.0(4스레드)과 PostgreSQL 16.15에서 직접 돌려 얻었다.

## 사건은 가운데, 설명은 둘레에

스타 스키마는 테이블을 두 종류로 나눈다.

가운데에는 일어난 일을 한 줄씩 쌓는 사실 테이블(fact table)이 있다. 서점이라면 "언제, 어느 회원이, 어떤 책을, 몇 권, 얼마에 샀다"가 한 줄이다. 줄 수가 가장 많고 계속 늘어난다. 컬럼은 대부분 숫자다. 더할 수 있는 측정값(수량, 금액)과, 둘레 테이블을 가리키는 키다.

둘레에는 그 사건을 설명하는 차원 테이블(dimension table)이 있다. 날짜 차원은 그 날이 몇 월인지, 주말인지를 들고 있다. 책 차원은 장르와 출판사를, 회원 차원은 지역과 등급을 들고 있다. 줄 수가 적고, 사람이 읽는 글자가 많다. 보고서의 `GROUP BY`와 `WHERE`에 들어가는 말은 거의 다 차원에서 온다.

그림으로 그리면 사실 테이블을 차원들이 별처럼 둘러싼다. 그래서 이름이 스타 스키마다.

실험용 데이터는 이렇게 만들었다. 1년치 날짜 365줄, 책 5만 권, 회원 20만 명, 판매 줄 500만 개다.

```sql
-- DuckDB
CREATE TABLE dim_date AS
SELECT CAST(strftime(d, '%Y%m%d') AS INTEGER) AS date_key,   -- 20260915 같은 정수 키
       CAST(d AS DATE) AS full_date, year(d) AS year, month(d) AS month,
       strftime(d, '%Y-%m') AS year_month, isodow(d) IN (6, 7) AS is_weekend
FROM range(DATE '2025-10-01', DATE '2026-10-01', INTERVAL 1 DAY) t(d);

CREATE TABLE fact_sales AS
SELECT i AS line_id,
       CAST(strftime(DATE '2025-10-01' + CAST(floor(random() * 365) AS INTEGER), '%Y%m%d') AS INTEGER) AS date_key,
       1 + CAST(floor(random() * 50000) AS INTEGER)  AS book_key,
       1 + CAST(floor(random() * 200000) AS INTEGER) AS customer_key,
       1 + CAST(floor(random() * 3) AS INTEGER)      AS qty,
       (8 + CAST(floor(random() * 30) AS INTEGER)) * 1000 AS price
FROM range(1, 5000001) t(i);
-- dim_book(book_key, isbn, genre, publisher, list_price),
-- dim_customer(customer_key, customer_id, region, tier)도 같은 식으로 만든다
```

날짜를 차원 테이블로 따로 두는 게 어색해 보일 수 있다. `date_trunc`로 계산하면 되지 않나. 그런데 회사마다 "회계 연도는 4월부터", "명절 연휴", "프로모션 주간" 같은 달력이 따로 있다. 이걸 날짜 차원의 컬럼으로 한 번 만들어 두면 모든 보고서가 같은 달력을 쓴다. 쿼리마다 계산하면 사람마다 다르게 계산한다.

## 한 줄이 무엇인지부터 정한다

스타 스키마를 설계할 때 가장 먼저 정하는 것은 사실 테이블 한 줄의 단위, 입도(grain)다. "주문 하나가 한 줄"인지 "주문 안의 책 한 권이 한 줄"인지에 따라 넣을 수 있는 측정값이 달라진다. 이걸 섞으면 숫자가 부풀어도 아무 에러가 나지 않는다.

운영 DB에는 보통 주문 머리(`orders`)와 주문 줄(`order_lines`)이 따로 있다. 배송비는 주문 하나에 한 번 붙으니 머리에 있다. 이 둘을 조인해 "9월 상품 금액과 배송비 합계"를 냈다. PostgreSQL 16이다.

```sql
CREATE TABLE orders (order_id int PRIMARY KEY, order_date date NOT NULL, shipping_fee int NOT NULL);
CREATE TABLE order_lines (order_id int REFERENCES orders, line_no int, book text, amount int,
                          PRIMARY KEY (order_id, line_no));
INSERT INTO orders VALUES (9001, '2026-09-03', 3000), (9002, '2026-09-03', 0), (9003, '2026-09-04', 3000);
INSERT INTO order_lines VALUES
  (9001, 1, '소설 A', 15000), (9001, 2, '만화 B', 8000), (9001, 3, 'IT C', 32000),
  (9002, 1, '경제 D', 21000),
  (9003, 1, '역사 E', 12000), (9003, 2, '소설 F', 14000);

-- 줄 단위로 조인한 뒤 배송비를 더하면
SELECT sum(l.amount) AS goods, sum(o.shipping_fee) AS shipping
FROM orders o JOIN order_lines l USING (order_id);

-- 실제 배송비 합계
SELECT sum(shipping_fee) AS shipping FROM orders;
```

```text
 goods  | shipping
--------+----------
 102000 |    15000
(1 row)

 shipping
----------
     6000
(1 row)
```

배송비가 6,000원인데 15,000원으로 나왔다. 조인이 주문 머리 한 줄을 주문 줄 수만큼 복제했기 때문이다. 9001번 주문의 배송비 3,000원이 세 번 더해졌다.

해결은 둘 중 하나다. 입도가 다른 측정값은 사실 테이블을 따로 둔다(주문 단위 사실 테이블과 주문 줄 단위 사실 테이블). 아니면 주문 단위 값을 줄 단위로 나눠 내린다. 첫 줄에 몰아 주거나, 금액 비율로 나눈다.

```sql
-- 첫 줄에 배송비를 몰아 준 줄 단위 사실 테이블과 같은 계산
SELECT sum(l.amount) AS goods,
       sum(CASE WHEN l.line_no = 1 THEN o.shipping_fee ELSE 0 END) AS shipping
FROM orders o JOIN order_lines l USING (order_id);
```

```text
 goods  | shipping
--------+----------
 102000 |     6000
(1 row)
```

몰아 주기는 합계는 맞지만 "장르별 배송비"처럼 줄 속성으로 나누면 첫 줄의 장르에 다 붙는다. 금액 비율로 나누면 장르별로도 그럴듯하지만 원 단위 반올림 오차를 마지막 줄에서 맞춰야 한다. 어느 쪽이든 사실 테이블을 만들 때 한 번 정하고 문서에 적어 둔다. 보고서를 쓰는 사람이 매번 정하게 두면 사람마다 숫자가 달라진다.

## 조인이 넷인데 왜 느리지 않나

정규화를 배울 때 조인은 비싸다고 배운다. 스타 스키마의 보고서는 거의 항상 사실 테이블 하나에 차원 서넛을 조인한다. "서울 회원의 7월 이후 장르별 월 매출"을 DuckDB로 돌렸다.

```sql
SELECT b.genre, dd.year_month, sum(f.qty * f.price) AS revenue
FROM fact_sales f
JOIN dim_book b      ON b.book_key = f.book_key
JOIN dim_date dd     ON dd.date_key = f.date_key
JOIN dim_customer c  ON c.customer_key = f.customer_key
WHERE c.region = '서울' AND dd.year_month >= '2026-07'
GROUP BY b.genre, dd.year_month
ORDER BY b.genre, dd.year_month;
```

이 최적화의 이름과 모양은 엔진마다 다르다. 런타임 필터, 조인 필터 밀어 넣기, 스타 조인 최적화 같은 이름으로 불린다. 엔진이 해 주지 않으면 차원을 먼저 거른 결과를 `IN` 목록이나 세미 조인으로 쓰는 식으로 직접 비슷하게 만든다. 컬럼 저장이 읽는 양을 줄이는 원리는 [컬럼형 분석 DB](/posts/db-type-columnar-olap)에 있다.

## 다 펼쳐 놓은 넓은 테이블과 비교하면

조인이 싫으면 차원 컬럼을 사실 테이블에 다 붙여 하나의 넓은 테이블로 만들 수도 있다. OBT(One Big Table)라고 부른다. 같은 500만 줄을 장르, 출판사, 지역, 등급까지 붙인 13개 컬럼의 넓은 테이블로 만들어 비교했다. 각각 따로 DuckDB 파일에 담아 크기를 쟀다.

```text
star file MB 46.9  obt file MB 78.9

star median  25.1 ms
obt  median  18.0 ms
```

넓은 테이블이 1.7배 크고, 쿼리는 조금 빠르다. 행 저장이었다면 "서울"이나 "출판사123" 같은 문자열이 500만 번 반복돼 크기가 훨씬 컸겠지만, 컬럼 저장은 같은 값이 반복되는 컬럼을 사전 인코딩으로 잘 누른다. 그래서 컬럼형 엔진에서는 넓은 테이블의 저장 비용이 생각보다 작다. 같은 스크립트를 한 번 더 돌렸을 때는 43ms와 38ms가 나왔다. 공유 실험 환경이라 절대값은 흔들리고, 둘의 차이는 매번 몇 ms 수준이었다.

차이는 차원이 바뀔 때 크게 드러난다. 장르 이름 "IT"를 "컴퓨터"로 바꿨다.

```sql
UPDATE dim_book SET genre = '컴퓨터' WHERE genre = 'IT';   -- 스타 스키마
UPDATE obt_sales SET genre = '컴퓨터' WHERE genre = 'IT';  -- 넓은 테이블
```

```text
star updated   6,195 rows in    80.0 ms
obt  updated 619,367 rows in   372.0 ms
```

스타 스키마는 책 6,195권을 고치면 끝이다. 넓은 테이블은 그 책들이 팔린 61만 줄을 다 고쳐야 한다. 이 데이터는 작아서 0.4초지만, 수십억 줄짜리 웨어하우스에서는 몇 시간짜리 작업이 되고, 컬럼 저장은 행 단위 수정에 약하다. 그래서 보통은 스타 스키마를 원본으로 두고, 대시보드 하나가 자주 쓰는 모양만 넓은 테이블이나 요약 테이블로 만들어 둔다. 넓은 테이블은 언제든 스타 스키마에서 다시 만들 수 있으니 버려도 되는 사본으로 다룬다.

## 회원이 이사하면 지난 매출은 어느 지역 것인가

처음 장면으로 돌아가자. 회원의 지역처럼 천천히 바뀌는 차원 속성을 어떻게 다룰지가 SCD(Slowly Changing Dimension) 문제다. 흔히 쓰는 방식은 번호로 부른다.

- 1형은 덮어쓴다. 과거 매출도 새 지역으로 잡힌다. 처음 장면이 이거다. 오타 수정처럼 "원래 틀린 값"을 고칠 때 맞다.
- 2형은 버전을 새로 만든다. 이사 전 회원과 이사 후 회원을 차원에서 서로 다른 줄로 두고, 사실 테이블은 판매 당시의 줄을 가리킨다.
- 3형은 "이전 지역" 컬럼을 하나 더 둔다. 직전 값 하나만 비교할 때 쓰고, 두 번 이사하면 처음 값은 사라진다.

2형을 PostgreSQL 16으로 만들었다. 회원 7이 4월 1일에 서울에서 부산으로 이사한다.

```sql
CREATE TABLE dim_customer (
  customer_key serial PRIMARY KEY,         -- 대리 키: 버전마다 새 번호
  customer_id  bigint NOT NULL,            -- 운영 DB의 회원 번호
  region       text   NOT NULL,
  valid_from   date   NOT NULL,
  valid_to     date   NOT NULL DEFAULT '9999-12-31',
  is_current   boolean NOT NULL DEFAULT true
);
INSERT INTO dim_customer (customer_id, region, valid_from) VALUES
  (7, '서울', '2025-01-01'), (8, '부산', '2025-01-01');

CREATE TABLE fact_sales (
  sale_date    date    NOT NULL,
  customer_key int     NOT NULL REFERENCES dim_customer,
  amount       integer NOT NULL
);
-- 3월 주문: 회원 7(그때 서울, 키 1)이 두 번, 회원 8(키 2)이 한 번
INSERT INTO fact_sales VALUES ('2026-03-10', 1, 41000), ('2026-03-22', 1, 15000), ('2026-03-15', 2, 9000);

-- 4월 1일 이사: 지금 버전을 닫고 새 버전을 연다. 한 트랜잭션으로
BEGIN;
UPDATE dim_customer SET valid_to = '2026-04-01', is_current = false
WHERE customer_id = 7 AND is_current;
INSERT INTO dim_customer (customer_id, region, valid_from) VALUES (7, '부산', '2026-04-01');
COMMIT;

-- 4월 주문을 적재할 때는 판매 날짜에 유효했던 버전의 대리 키를 찾는다
INSERT INTO fact_sales (sale_date, customer_key, amount)
SELECT s.sale_date, c.customer_key, s.amount
FROM (VALUES (DATE '2026-04-05', 7, 22000), (DATE '2026-04-09', 8, 12000))
     AS s(sale_date, customer_id, amount)
JOIN dim_customer c
  ON c.customer_id = s.customer_id
 AND s.sale_date >= c.valid_from AND s.sale_date < c.valid_to;

SELECT * FROM dim_customer ORDER BY customer_key;
```

```text
 customer_key | customer_id | region | valid_from |  valid_to  | is_current
--------------+-------------+--------+------------+------------+------------
            1 |           7 | 서울   | 2025-01-01 | 2026-04-01 | f
            2 |           8 | 부산   | 2025-01-01 | 9999-12-31 | t
            3 |           7 | 부산   | 2026-04-01 | 9999-12-31 | t
(3 rows)
```

회원 7이 두 줄이 됐다. 키 1은 3월 31일까지의 서울 회원, 키 3은 4월부터의 부산 회원이다. `valid_to`를 다음 버전의 `valid_from`과 같게 두고 "이상, 미만"으로 비교하면 날짜 하나가 두 버전에 걸리지 않는다. 이제 같은 사실 테이블로 질문 두 개에 다 답할 수 있다.

```sql
-- 1) 판매 당시 지역으로: 대리 키로 조인
SELECT c.region, to_char(f.sale_date, 'YYYY-MM') AS month, sum(f.amount) AS revenue
FROM fact_sales f JOIN dim_customer c USING (customer_key)
GROUP BY 1, 2 ORDER BY 2, 1;

-- 2) 지금 사는 지역으로: 같은 회원의 현재 버전에 다시 조인
SELECT cur.region, to_char(f.sale_date, 'YYYY-MM') AS month, sum(f.amount) AS revenue
FROM fact_sales f
JOIN dim_customer c   ON c.customer_key = f.customer_key
JOIN dim_customer cur ON cur.customer_id = c.customer_id AND cur.is_current
GROUP BY 1, 2 ORDER BY 2, 1;
```

```text
 region |  month  | revenue
--------+---------+---------
 부산   | 2026-03 |    9000
 서울   | 2026-03 |   56000
 부산   | 2026-04 |   34000
(3 rows)

 region |  month  | revenue
--------+---------+---------
 부산   | 2026-03 |   65000

(2 rows)
```

## 미리 묶어 둔 요약 테이블

같은 보고서를 하루에 수백 번 연다면 매번 500만 줄을 읽을 이유가 없다. 날짜, 장르, 지역별로 미리 묶은 요약 테이블을 만들었다.

```sql
CREATE TABLE agg_daily AS
SELECT f.date_key, b.genre, c.region,
       sum(f.qty * f.price) AS revenue, sum(f.qty) AS qty, count(*) AS lines,
       count(DISTINCT f.customer_key) AS buyers
FROM fact_sales f
JOIN dim_book b USING (book_key)
JOIN dim_customer c USING (customer_key)
GROUP BY ALL;
```

```text
star median  25.1 ms
obt  median  18.0 ms
agg  median   2.8 ms
same result: True | agg_daily rows: 20440
```

500만 줄이 365일 × 8장르 × 7지역 = 20,440줄로 줄었고, 같은 보고서가 2.8ms에 같은 답을 냈다. 매출, 수량, 줄 수처럼 더할 수 있는 값은 이렇게 미리 묶어도 월 단위, 분기 단위로 다시 더하면 맞는다.

맞지 않는 값이 있다. 요약 테이블에 하루 구매자 수(`buyers`)도 넣어 뒀다. 9월 서울 IT 구매자 수를 원본에서 센 값과, 하루 구매자 수를 더한 값을 비교했다.

```text
2026-09 서울 IT buyers: true distinct = 6478 | sum of daily distinct = 7298
```

실제로는 6,478명인데 더하면 7,298명이다. 9월에 두 번 산 사람이 두 날에 한 번씩 세어졌다. 서로 다른 사람 수, 비율, 평균처럼 더할 수 없는 값은 요약에서 다시 더하면 틀린다. 평균은 합계와 건수를 따로 두고 나중에 나누면 되고, 구매자 수는 원본에서 세거나, 합칠 수 있는 근사 구조([HyperLogLog](/posts/hyperloglog))를 요약 칸마다 넣어 둔다.

요약 테이블은 원본이 바뀌면 다시 만들어야 한다. 어제 하루치만 다시 계산해 덮어쓰는 식으로 칸 단위로 고치면 싸다. PostgreSQL의 머티리얼라이즈드 뷰, ClickHouse의 머티리얼라이즈드 뷰처럼 엔진이 대신 관리하는 기능도 있다. 동작 방식이 엔진마다 다르다(PostgreSQL은 통째로 다시 계산하고, ClickHouse는 들어오는 줄마다 더한다). PostgreSQL 쪽은 [뷰와 머티리얼라이즈드 뷰](/posts/sql-views-materialized)에 있다.

## 차원을 더 쪼갤지, 아예 다른 모델로 갈지

책 차원의 출판사에도 "출판사 그룹", "국가" 같은 속성이 붙으면, 출판사를 따로 차원 테이블로 빼고 책 차원이 그걸 가리키게 만들 수 있다. 차원을 정규화한 이 모양을 눈송이(snowflake) 스키마라고 부른다(같은 이름의 클라우드 웨어하우스와는 관계없다). 저장 공간과 수정 범위는 줄지만 조인이 하나 늘고, 보고서를 쓰는 사람이 테이블 관계를 더 알아야 한다. 분석 쪽에서는 차원 하나를 넓게 펴 두는 스타 쪽을 기본으로 두는 경우가 많다. 차원은 작아서 중복 비용이 크지 않기 때문이다.

여러 원천 시스템을 모아 이력 전체를 보관하는 층이 따로 필요한 큰 조직에서는 데이터 볼트(Data Vault) 같은 모델을 원천 보관층에 두고, 보고서용으로는 그 위에 스타 스키마를 다시 만드는 구성도 쓴다. 작은 팀이라면 원천 테이블을 그대로 쌓는 층 하나와 스타 스키마 층 하나로 시작하면 충분하다. 이 변환을 SQL 파일로 관리하고 의존 순서대로 돌려 주는 도구(dbt 같은)를 흔히 쓴다.

## 분석 숫자가 안 맞는다는 문의가 오면

"대시보드 매출이 정산 시스템보다 크다"는 문의가 오면, 먼저 쿼리가 조인하는 테이블의 입도를 본다. 입도가 다른 테이블을 조인했는지 확인하는 가장 빠른 방법은 조인 전후의 줄 수를 세는 것이다.

```sql
-- 조인 전후 줄 수가 다르면 무언가가 복제되고 있다
SELECT count(*) FROM orders;                                  -- 3
SELECT count(*) FROM orders o JOIN order_lines l USING (order_id);  -- 6
```

과거 달의 숫자가 다시 뽑을 때마다 바뀐다면 1형으로 덮어쓰는 차원이 있는지 본다. 어떤 속성을 1형으로, 어떤 속성을 2형으로 다룰지 차원마다 정해 문서에 적어 둔다. 등급처럼 실적 평가에 쓰는 속성은 대개 2형이다.

최근 며칠의 숫자가 조금씩 늘어난다면 늦게 도착한 사실이나, 예약 키(-1)로 들어갔다가 나중에 고쳐진 줄이다. 예약 키가 붙은 줄 수를 지표로 지켜보면, 원천에서 회원 정보가 늦게 오는 날을 바로 알 수 있다.

```sql
SELECT count(*) FROM fact_sales WHERE customer_key = -1;   -- "알 수 없음"으로 들어간 판매
```

## 질문의 모양대로 쌓는다

스타 스키마는 분석 질문의 모양을 그대로 테이블로 만든 것이다. 가운데 사실 테이블은 정해 둔 입도로 사건을 쌓고, 둘레 차원은 그 사건을 묶고 거르는 말을 들고 있다. 입도를 섞으면 숫자가 소리 없이 부풀고, 차원을 덮어쓰면 과거가 바뀐다. 2형 차원은 버전마다 대리 키를 주고 사실 테이블이 판매 당시의 키를 가리키게 해서, 그때의 답과 지금 기준의 답을 둘 다 남긴다. 자주 보는 모양은 넓은 테이블이나 요약 테이블로 만들어 두되, 언제든 다시 만들 수 있는 사본으로 다룬다. 이 테이블들을 채우는 변경 흐름은 [CDC](/posts/cdc-change-data-capture)와 [스트림 처리](/posts/stream-processing)에서 이어진다.

## 면접에서 나올 만한 질문

### 사실 테이블과 차원 테이블은 무엇이 다른가요?

사실 테이블은 판매 한 줄처럼 일어난 일을 정해 둔 입도로 쌓고, 측정값과 차원 키로 이뤄진다. 줄 수가 가장 많고 계속 늘어난다. 차원 테이블은 날짜, 상품, 고객처럼 그 사건을 설명하는 속성을 담고, 작고 글자가 많다. 보고서의 묶기와 거르기는 대부분 차원 속성으로 한다.

### 입도(grain)를 먼저 정해야 하는 이유는요?

입도가 다른 값을 한 사실 테이블에 섞거나 조인하면, 큰 단위의 값이 작은 단위의 줄 수만큼 복제되어 합계가 부푼다. 실험에서 주문당 배송비 6,000원이 주문 줄과 조인하자 15,000원이 됐고 에러는 없었다. 입도마다 사실 테이블을 따로 두거나, 큰 단위 값을 작은 단위로 나눠 내리는 규칙을 한 번 정해 둔다.

### 조인이 많은 스타 스키마가 분석에서 느리지 않은 이유는요?

차원은 작고 사실 테이블만 크다. 엔진은 차원을 먼저 거르고, 작은 차원으로 해시 표를 만든 뒤 큰 사실 테이블을 한 번 훑으며 찔러 본다. 실험한 DuckDB는 차원에서 걸러 낸 키를 사실 테이블 스캔에 미리 적용해 500만 줄을 18만 줄로 줄였고, 조인 셋짜리 쿼리가 25ms였다.

### 넓은 테이블 하나(OBT)로 다 펼치면 안 되나요?

조회는 조금 빠르고, 컬럼 저장에서는 크기도 생각만큼 커지지 않는다. 실험에서 1.7배였다. 문제는 차원 속성이 바뀔 때다. 장르 이름 하나를 바꾸는 데 스타 스키마는 6천 줄, 넓은 테이블은 61만 줄을 고쳐야 했다. 그래서 스타 스키마를 원본으로 두고 넓은 테이블은 필요한 곳에만 다시 만들 수 있는 사본으로 둔다.

### 고객이 이사하면 과거 매출의 지역은 어떻게 처리하나요?

SCD 2형으로 고객 차원에 버전을 만든다. 이전 버전의 유효 기간을 닫고 새 대리 키로 새 버전을 열며, 사실 테이블은 판매 당시 유효했던 버전의 키를 가리킨다. 그러면 판매 당시 지역 기준과 현재 지역 기준을 둘 다 계산할 수 있다. 덮어쓰는 1형은 오타 수정처럼 과거도 함께 바뀌어야 맞는 속성에만 쓴다.

### 왜 운영 DB의 고객 번호를 그대로 쓰지 않고 대리 키를 따로 두나요?

2형에서는 같은 고객이 여러 버전을 가지니 고객 번호만으로는 어느 버전인지 가리킬 수 없다. 대리 키는 버전마다 다른 번호라 사실 테이블이 정확히 한 버전을 가리킨다. 여러 원천 시스템의 번호 체계가 달라도 분석 쪽 키를 하나로 맞출 수 있고, 아직 도착하지 않은 고객을 예약 키로 표시할 수도 있다.

### 요약 테이블에서 월간 구매자 수를 일별 구매자 수의 합으로 구하면 안 되는 이유는요?

서로 다른 사람 수는 더할 수 없는 값이라, 한 달에 두 번 산 사람이 두 번 세어진다. 실험에서 실제 6,478명이 일별 합으로는 7,298명이 됐다. 합계와 건수처럼 더할 수 있는 값만 요약해 다시 더하고, 고유 수는 원본에서 세거나 HyperLogLog 같은 합칠 수 있는 근사 구조를 둔다.
