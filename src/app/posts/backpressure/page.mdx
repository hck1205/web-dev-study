S3에 있는 큰 CSV를 받아 사용자에게 그대로 내려 주는 다운로드 API가 있다. 사내망에서 테스트할 때는 멀쩡했다. 그런데 출시 후 지하철에서 내려받는 모바일 사용자가 몇 명 붙자 서버 메모리가 GB 단위로 치솟고 Pod가 재시작됐다. 코드는 S3 응답의 `data` 이벤트마다 `res.write(chunk)`를 부르는 몇 줄이었다. S3는 초당 수백 MB로 주는데 사용자는 초당 수백 KB로 받는다. 그 차이가 전부 서버 메모리에 쌓였다.

빠른 쪽과 느린 쪽이 이어지면 차이는 어딘가에 쌓인다. 받는 쪽이 "천천히 보내 달라"고 거꾸로 신호를 보내 보내는 쪽을 늦추는 장치를 백프레셔(backpressure)라고 한다. 이 글은 Node 스트림의 `write()`와 `drain`, `pipeline()`으로 그 신호를 직접 보고, 같은 원리가 TCP 소켓과 서비스 사이 큐, Reactive Streams의 `request(n)`에서 어떻게 반복되는지 따라간다. 실습은 Ubuntu 컨테이너의 Node 22.22로 했다.

쌓기는 짧은 폭주를 흡수하는 데 좋지만, 차이가 계속되면 버퍼는 (P − C) × 시간만큼 자라서 언젠가 넘친다. 버리기는 시스템을 지키지만 데이터나 요청을 잃는다. 소비자를 늘리는 건 근본적인 해결이지만 [오토스케일링](/posts/autoscaling) 글에서 보듯 몇 분이 걸린다. 늦추기는 잃는 것 없이 전체 속도를 가장 느린 구간에 맞춘다. 실제 시스템은 이 넷을 섞는다. 작은 버퍼로 순간 폭주를 받고, 버퍼가 차면 생산자를 늦추고, 늦출 수 없는 입구(사용자 요청)에서는 버린다.

## 버퍼만 두면 시간 문제다

"큐를 두면 되지 않나"라는 생각은 순간 폭주에는 맞고 지속되는 차이에는 틀리다. 간단히 시뮬레이션해 보자. 매 틱마다 `arrivals[i]`개가 오고, 소비자는 틱마다 `perTick`개를 처리하며, 큐에는 `maxQueue`개까지만 들어간다. 넘치는 것은 버린다.

## Node 스트림의 신호: write()가 false를 돌려준다

Node의 `Writable` 스트림은 안에 버퍼를 하나 들고 있고, 버퍼에 쌓인 양이 `highWaterMark`에 닿으면 `write()`가 `false`를 돌려준다. 이것이 "그만 보내라"는 신호다. 버퍼가 비면 `drain` 이벤트로 "다시 보내도 된다"고 알린다. 강제는 아니다. `false`를 받고도 계속 쓰면 스트림은 거절하지 않고 그냥 다 받아 둔다.

```bash
cat > drain.js <<'EOF'
// 1ms에 청크 하나씩만 처리하는 느린 소비자
const { Writable } = require("stream");
const slow = new Writable({
  highWaterMark: 64 * 1024,
  write(chunk, enc, cb) { setTimeout(cb, 1); },
});
const chunk = Buffer.alloc(16 * 1024);
let i = 0;
function produce() {
  while (i < 12) {
    const ok = slow.write(chunk);
    i++;
    console.log(`write #${i} -> ${ok}  writableLength=${slow.writableLength}`);
    if (!ok) { slow.once("drain", () => { console.log("drain  writableLength=" + slow.writableLength); produce(); }); return; }
  }
  slow.end();
}
produce();
EOF
# false가 오면 멈추고 drain을 기다리는 생산자
node drain.js
```

```text
write #1 -> true  writableLength=16384
write #2 -> true  writableLength=32768
write #3 -> true  writableLength=49152
write #4 -> false  writableLength=65536
drain  writableLength=0
write #5 -> true  writableLength=16384
write #6 -> true  writableLength=32768
write #7 -> true  writableLength=49152
write #8 -> false  writableLength=65536

...
```

## 신호를 무시하면 얼마나 쌓이나

16KiB 청크 2만 개(약 312MiB)를 느린 소비자에게 보내는 코드를 세 가지로 짰다. `false`를 무시하고 계속 쓰기, `false`면 `drain`을 기다리기, `pipeline()`에 맡기기.

```text
ignore   writableLength after loop=313MiB
ignore   time=478ms peakRSS=380MiB
respect  time=218ms peakRSS=70MiB
pipeline time=255ms peakRSS=67MiB
```

무시한 쪽은 루프가 끝난 순간 스트림 버퍼에 313MiB가 쌓여 있었고 RSS가 380MiB까지 올랐다. 신호를 지킨 쪽은 70MiB 근처에서 끝났다. 시간도 무시한 쪽이 두 배 걸렸다. 큰 버퍼를 할당하고 GC가 그걸 훑는 비용이 더해졌기 때문이다. 처음 이야기한 다운로드 API가 정확히 ignore 모드였다. 느린 사용자 한 명당 파일 크기만큼 메모리를 들고 있었던 셈이다.

## pipeline()이 대신 해 주는 것

신호를 손으로 지키는 코드는 길고 틀리기 쉽다. 그래서 스트림을 이을 때는 `pipeline()`을 쓴다. 읽는 쪽에서 쓰는 쪽으로 흐르는 동안 `write()`가 `false`면 읽는 쪽을 멈추고(pause), `drain`이 오면 다시 흘린다.

```js
const { pipeline } = require("node:stream/promises");
const zlib = require("node:zlib");

app.get("/export.csv.gz", async (req, res) => {
  const src = await s3.getObject(params);            // 읽기 스트림
  res.setHeader("Content-Encoding", "gzip");
  try {
    // 백프레셔 + 에러 전파 + 끝나면 모두 정리
    await pipeline(src.Body, zlib.createGzip(), res);
  } catch (err) {
    // 클라이언트가 끊으면 여기로 온다(ERR_STREAM_PREMATURE_CLOSE). S3 스트림도 이미 닫혔다
    req.log.warn({ err }, "export aborted");
  }
});
```

`a.pipe(b)`도 백프레셔는 지킨다. 차이는 에러 처리다. `pipe()`는 중간 스트림에서 에러가 나도 나머지를 닫아 주지 않아서, 클라이언트가 다운로드를 취소하면 S3 연결과 파일 핸들이 열린 채 남는다. `pipeline()`은 한 곳에서 에러가 나면 모두 `destroy()`하고 콜백이나 Promise로 알려 준다.

`for await`로 읽는 코드도 자연스럽게 백프레셔를 지킨다. 반복 한 번이 끝나야 다음 청크를 읽기 때문이다. 반대로 `readable.on("data", async (chunk) => { await db.insert(chunk) })`처럼 `data` 이벤트에 비동기 함수를 걸면 await가 읽기를 멈추지 못한다. 이벤트는 계속 오고 insert만 쌓인다.

## 소켓 아래에서는 TCP가 같은 일을 한다

`res.write()`의 신호는 결국 TCP 소켓에서 온다. TCP에도 백프레셔가 있다. 받는 쪽 커널이 "내 수신 버퍼에 이만큼 남았다"는 수신 창(window)을 ACK마다 알리고, 0이 되면 보내는 쪽은 멈춘다. [TCP의 흐름 제어](/posts/tcp-reliability-congestion)다. 서버가 소켓을 읽지 않게(`pause()`) 해 두고 클라이언트가 1ms마다 64KiB씩 2초 동안 쓰게 했다.

```bash
# 서버는 읽지 않는다. 클라이언트는 계속 쓴다. 2초 뒤 버퍼 상태를 본다
node tcpbp.js
# 그동안 다른 터미널에서 수신 창이 0이 되는 순간을 잡는다
sudo tcpdump -i lo -nn 'tcp port 9409' | grep "win 0"
```

이 구조 덕분에 백프레셔는 서비스 경계를 넘어서도 전파된다. 앞 절의 다운로드 API에서 폰이 느리면 폰의 수신 창이 닫히고, 서버 응답 소켓이 `false`를 내고, `pipeline()`이 S3 응답 읽기를 멈추고, 서버의 수신 창이 닫혀 S3가 보내기를 멈춘다. 각 층이 자기 한도만 지키면 끝에서 끝까지 늦춰진다.

## 서비스 사이에서는 큐 길이로 말한다

HTTP API 앞단에서는 사정이 다르다. 사용자 요청은 늦출 수가 없다. 사용자는 "천천히 보내 달라"는 신호를 받지 않고 그냥 기다리거나 새로 고침을 누른다. 그래서 서비스의 입구에서는 큐 길이에 상한을 두고 넘치면 빠르게 거절하는 부하 차단(load shedding)이 백프레셔 역할을 한다.

동시에 4개, 한 건에 20ms 걸리는 서버(초당 약 200건)에 초당 400건을 5초 동안 보냈다. 대기열에 상한이 없을 때와 20개로 묶고 넘치면 503을 줄 때를 비교했다.

```text
MAXQ=Infinity sent=1924 ok=1924 503=0 maxQueue=959 ok.p50=2517ms ok.p99=5008ms ok.max=5055ms
MAXQ=20 sent=1912 ok=982 503=930 maxQueue=20 ok.p50=120ms ok.p99=137ms ok.max=142ms
```

상한이 없으면 모두 성공했지만 대기열이 959개까지 자랐고 중간값이 2.5초, p99가 5초다. 실제 서비스라면 클라이언트 타임아웃(보통 몇 초)이 먼저 터져서, 서버는 이미 포기한 요청을 열심히 처리하고 있었을 것이다. 상한을 두면 절반을 즉시 503으로 돌려보내는 대신 받아들인 요청은 140ms 안에 끝났다. 처리한 양은 어차피 소비자 속도로 정해진다. 앞의 시뮬레이션과 같은 이야기다.

상한은 "기다려도 되는 시간 × 처리 속도"로 정한다. 대기 시간 = 대기열 길이 ÷ 처리량(리틀의 법칙)이라서, 0.1초까지 기다리게 하고 초당 200건을 처리한다면 20개다. 거절 응답은 429와 503 중에 고른다. 특정 클라이언트가 한도를 넘었으면 429, 서버 전체가 바쁘면 503이 맞다. 클라이언트별 한도를 거는 쪽은 [요청 수 제한을 API에 붙이기](/posts/rate-limiting-in-practice) 글에 있다.

거절은 재시도를 부른다는 것도 같이 봐야 한다. 503을 받은 클라이언트가 바로 다시 보내면 부하는 줄지 않는다. Retry-After를 지키고 지터를 섞는 클라이언트, 그리고 [재시도 예산](/posts/retries)이 있어야 부하 차단이 의미가 있다.

메시지 큐는 소비자가 당겨 가는 구조라서 백프레셔가 자연스럽다. 워커는 자기가 처리할 수 있을 만큼만 꺼낸다(RabbitMQ의 prefetch, Kafka의 `max.poll.records`). 대신 쌓이는 곳이 큐로 옮겨 갈 뿐이라서, 큐 깊이가 계속 오르면 소비자를 늘리거나 생산을 줄여야 한다는 신호로 읽는다. [메시지 큐 기초](/posts/message-queue-basics)에서 큐 깊이 그래프를 읽는 법을 다룬다.

## 당겨 가는 쪽이 양을 정한다: request(n)

자바 진영의 Reactive Streams(Project Reactor, RxJava, Akka Streams가 따르는 규약)는 백프레셔를 규약 자체에 넣었다. 구독자가 `request(n)`으로 "n개까지 받을 수 있다"고 말하기 전에는 발행자가 보내지 못한다. 신호를 무시할 방법이 없다는 점이 Node 스트림의 `false`와 다르다.

## 백프레셔가 빠진 시스템의 증상

현장에서 백프레셔가 빠져 있으면 대개 이런 모습으로 나타난다.

느린 클라이언트나 느린 하위 서비스가 있을 때만 메모리가 오른다. 평소에는 멀쩡하다가 특정 고객사, 특정 시간대에만 RSS가 튄다. Node라면 `res.writableLength`나 `socket.writableLength`를 로그에 찍어 보고, 커널 쪽은 `ss -tnm`으로 Send-Q가 꽉 찬 연결이 있는지 본다. 고치는 방법은 `pipeline()`이나 `for await`로 바꾸는 것이다.

처리량은 그대로인데 지연만 초 단위로 늘어난다. 앞의 상한 없는 대기열 실험이 그 모양이다. 서버 안 어딘가(스레드 풀 큐, 커넥션 풀 대기열, 워커의 메모리 배열)에 상한 없는 줄이 있다. 줄 길이를 지표로 내보내고 상한과 빠른 거절을 둔다. [커넥션 풀](/posts/connection-pool)의 획득 대기 타임아웃도 같은 장치다.

배치 작업이 시작하자마자 하위 DB나 API를 쓰러뜨린다. `Promise.all(ids.map(fetchOne))`처럼 10만 건을 한꺼번에 시작하는 코드가 흔한 원인이다. 동시 실행 수를 정한 작업 풀(p-limit 같은 라이브러리, 또는 워커 N개가 큐에서 꺼내는 구조)로 바꾼다.

흔한 실수도 있다. `highWaterMark`를 수백 MB로 키워 "버퍼가 넉넉하니 안전하다"고 여기는 것은 연결 수만큼 메모리를 곱해 놓는 일이다. 컨슈머 쪽 처리를 메모리 큐에 넣고 바로 ack하는 코드는 브로커의 백프레셔를 우회한다. 프로세스가 죽으면 그 큐의 내용도 같이 사라진다.

## 가장 느린 곳이 속도를 정하게 둔다

백프레셔는 느린 쪽의 사정을 빠른 쪽에 전하는 신호다. 스트림에서는 `write()`의 `false`와 `drain`, TCP에서는 수신 창, 리액티브 스트림에서는 `request(n)`, 서비스 입구에서는 꽉 찬 대기열과 503이다. 형태는 달라도 원칙은 같다. 모든 버퍼에 상한을 두고, 상한에 닿으면 앞쪽을 늦추거나 거절한다. 버퍼를 키우는 것은 문제가 터지는 시점을 늦출 뿐이다.

## 면접에서 나올 만한 질문

### 백프레셔가 무엇이고 왜 필요한가요?

받는 쪽이 처리 속도를 보내는 쪽에 거꾸로 알려 생산 속도를 늦추는 장치다. 생산자가 소비자보다 빠르면 차이만큼 어딘가에 쌓이고, 상한 없는 버퍼는 결국 메모리를 다 쓰거나 지연을 끝없이 늘린다. 백프레셔가 있으면 전체 속도가 가장 느린 구간에 맞춰지고 메모리는 버퍼 상한 안에 머문다.

### Node에서 write()가 false를 돌려주면 어떻게 해야 하나요?

더 쓰지 말고 `drain` 이벤트를 기다렸다가 다시 쓴다. `false`는 내부 버퍼가 `highWaterMark`에 닿았다는 신호일 뿐 쓰기를 거절하지는 않아서, 무시하면 데이터가 전부 메모리에 쌓인다. 실습에서 신호를 무시하자 RSS가 380MiB까지 올랐고, 지킨 쪽은 70MiB에서 끝났다. 손으로 다루기보다 `pipeline()`을 쓰는 게 안전하다.

### pipe()와 pipeline()의 차이는요?

둘 다 백프레셔는 지키지만 에러 처리가 다르다. `pipe()`는 중간 스트림에서 에러가 나도 다른 스트림을 닫지 않아서 파일 핸들이나 업스트림 연결이 새기 쉽다. `pipeline()`은 한 곳에서 에러가 나거나 클라이언트가 끊으면 모든 스트림을 정리하고 콜백이나 Promise로 에러를 넘겨준다.

### TCP의 흐름 제어와 애플리케이션의 백프레셔는 어떤 관계인가요?

TCP 흐름 제어는 커널 사이의 백프레셔다. 받는 쪽이 수신 창 크기를 ACK에 실어 보내고 0이면 보내는 쪽 커널이 멈춘다. 커널 버퍼는 크기가 정해져 있어 넘치지 않지만, 앱이 소켓 쓰기의 신호를 무시하면 그 위의 사용자 공간 버퍼에 쌓인다. 각 층이 자기 한도를 지켜야 끝에서 끝까지 늦춰진다.

### 사용자 요청처럼 늦출 수 없는 입력에는 어떻게 백프레셔를 거나요?

대기열에 상한을 두고 넘치면 일을 시작하기 전에 503이나 429로 빠르게 거절한다. 상한은 허용할 대기 시간에 처리량을 곱해 정한다. 실습에서 상한이 없으면 p99가 5초까지 늘었고, 20개로 묶자 절반을 거절하는 대신 받은 요청은 137ms에 끝났다. 거절이 재시도 폭풍이 되지 않도록 Retry-After와 재시도 예산을 함께 둔다.

### 큐를 크게 잡으면 문제가 해결되지 않나요?

순간적인 폭주는 흡수하지만 지속되는 속도 차이는 해결하지 못한다. 소비자 처리량이 그대로라서 처리하는 양은 같고, 큰 큐는 대기 시간과 쌓인 일만 늘린다. 그 사이 클라이언트는 타임아웃으로 떠나고 서버는 아무도 기다리지 않는 요청을 처리하게 된다.

### Reactive Streams의 request(n)은 무엇을 해결하나요?

구독자가 받을 수 있는 수를 먼저 말해야 발행자가 보낼 수 있게 만든 규약이다. Node 스트림처럼 신호를 무시하고 계속 보낼 방법이 없어서 백프레셔가 강제된다. 발행자 쪽에서 넘치는 데이터는 버릴지, 버퍼에 담을지, 최신 것만 남길지를 연산자로 명시적으로 고른다.
