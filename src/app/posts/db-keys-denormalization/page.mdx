주문 테이블을 정규화해서 회원, 주문, 주문 상품, 상품 넷으로 나눴다. 이제 남은 선택이 있다. 회원의 기본키는 이메일로 할까, 번호로 할까, 요즘 많이 쓴다는 UUID로 할까. 주문 목록 화면은 주문마다 합계를 보여 줘야 하는데, 매번 주문 상품을 묶어 더하자니 초당 수천 번이다. 상품 가격을 주문 상품에도 적어 두는 건 중복이 아닌가. 상품 속성은 카테고리마다 다른데 열을 수십 개 만들어야 하나.

테이블을 어떻게 나누는지는 [정규화 글](/posts/db-modeling-normalization)에서 함수 종속을 따라 1NF부터 BCNF까지 봤다. 이 글은 그다음, 나눈 테이블을 실제로 쓰면서 고르는 것들이다. 키를 무엇으로 할지, 중복처럼 보이지만 중복이 아닌 값, 일부러 다시 합치는 반정규화와 원본과 맞추는 방법, `jsonb` 열을 어디까지 쓸지, 그리고 자주 보는 설계 실수다. SQL은 PostgreSQL 16 기준이고 출력은 PostgreSQL 16.15에서 실제로 실행한 결과다.

## 정규화를 마친 네 테이블

앞 글 끝의 테이블을 그대로 쓴다. 처음부터 따라 하려면 아래를 돌린다. 데이터는 김민지(1번)의 주문 셋과 이도윤(2번)의 주문 하나, 그리고 아직 주문이 없는 박서준(3번)이다.

```sql
CREATE TABLE users (
  user_id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- 대리 키
  email      text NOT NULL UNIQUE,                             -- 자연 키는 대체키로
  name       text NOT NULL,
  phone      text,                                             -- 없을 수 있다
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE products (
  product_id bigint  PRIMARY KEY,                   -- 1001, 1002처럼 정해 둔 번호
  name       text    NOT NULL,
  price      integer NOT NULL CHECK (price >= 0)    -- 지금 판매가. 음수는 막는다
);

CREATE TABLE orders (
  order_id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    bigint NOT NULL REFERENCES users (user_id) ON DELETE RESTRICT,
  status     text NOT NULL DEFAULT 'pending'
             CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled')),
  ordered_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
  order_id   bigint  NOT NULL REFERENCES orders (order_id) ON DELETE CASCADE,
  product_id bigint  NOT NULL REFERENCES products (product_id),
  unit_price integer NOT NULL CHECK (unit_price >= 0),  -- 주문 당시 가격
  quantity   integer NOT NULL CHECK (quantity > 0),     -- 0개 주문은 말이 안 된다
  PRIMARY KEY (order_id, product_id)                    -- 한 주문에 같은 상품 줄은 하나
);

CREATE INDEX orders_user_id_idx ON orders (user_id);
CREATE INDEX order_items_product_id_idx ON order_items (product_id);

INSERT INTO users (email, name, phone) VALUES
  ('kim@example.com',  '김민지', '010-1111-2222'),
  ('lee@example.com',  '이도윤', '010-3333-4444'),
  ('park@example.com', '박서준', NULL);

INSERT INTO products VALUES
  (1001, '무선 이어폰', 39000), (1002, '충전 케이스', 15000), (1003, '이어팁', 5000);

INSERT INTO orders (user_id, ordered_at) VALUES
  (1, '2026-10-01'), (2, '2026-10-03'), (1, '2026-10-05'), (1, '2026-10-09');

INSERT INTO order_items VALUES
  (1, 1001, 39000, 1), (1, 1003, 5000, 2),
  (2, 1002, 15000, 1), (3, 1002, 15000, 1), (4, 1003, 5000, 1);
```

## 자연 키와 대리 키, 그리고 UUID

기본키를 고를 때 가장 먼저 부딪히는 선택이 자연 키냐 대리 키냐다. 자연 키는 업무에 원래 있는 값(이메일, 주민등록번호, 상품 코드)이고, 대리 키(surrogate key)는 행을 구분하려고 DB가 붙이는 의미 없는 번호다.

이메일을 회원의 기본키로 쓰면 처음 장면과 같은 문제가 키에서 다시 생긴다. 이메일은 바뀐다. 기본키가 바뀌면 그걸 외래키로 들고 있는 주문 300줄도 같이 바뀌어야 한다. `ON UPDATE CASCADE`로 DB가 대신 고쳐 줄 수는 있지만, 키가 바뀌는 순간 그 키를 캐시나 로그, 다른 서비스에 들고 있던 곳은 아무도 고쳐 주지 않는다. 주민등록번호 같은 값은 바뀌지 않아도 개인정보라 키로 여기저기 복사되면 안 된다.

그래서 보통은 대리 키를 기본키로 두고, 자연 키에는 `UNIQUE`를 건다. 키는 절대 안 바뀌고, 업무상 중복 방지도 그대로 지킨다. 대리 키를 쓰면서 `UNIQUE`를 빠뜨리면 같은 이메일로 회원이 둘 생기니, 이 둘은 짝으로 다닌다고 생각하면 된다.

대리 키를 만드는 방법은 크게 두 가지다. 1씩 늘어나는 정수(`bigint` identity)와 무작위에 가까운 UUID다.

```sql
-- PostgreSQL 10+: SQL 표준 identity 열. serial보다 이걸 쓴다
user_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY

-- PostgreSQL 13+: 무작위 UUID(v4)를 내장 함수로 만든다
user_id uuid DEFAULT gen_random_uuid() PRIMARY KEY
```

```sql
-- MySQL 8
user_id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
-- MySQL의 UUID()는 시간 기반 v1이다. BINARY(16)에 넣고, 두 번째 인자 1로 시간 부분을 앞으로 옮겨 정렬되게 한다
user_id BINARY(16) DEFAULT (UUID_TO_BIN(UUID(), 1)) PRIMARY KEY
```

UUID의 장점은 DB에 묻지 않고 어디서든 만들 수 있다는 것이다. 앱 서버나 모바일 앱이 먼저 ID를 정해서 보낼 수 있고, 여러 DB를 합쳐도 겹치지 않는다. 번호가 1, 2, 3으로 이어지지 않으니 URL의 `/orders/1042`를 `/orders/1043`으로 바꿔서 남의 주문을 찾아보는 시도도 어려워진다. 다만 이건 권한 검사를 대신하지 못한다. 추측이 어려워질 뿐이다.

단점은 크기와 순서다. `bigint`는 8바이트, UUID는 16바이트다. 문자열(`char(36)`)로 저장하면 36바이트를 넘는다. 기본키는 인덱스에 들어가고 외래키로 다른 테이블에도 복사되니 크기가 여러 번 곱해진다. 더 큰 문제는 v4 UUID가 무작위라는 데 있다. B-tree 인덱스는 값 순서대로 정렬돼 있어서, 1씩 늘어나는 키는 항상 오른쪽 끝 페이지에만 추가된다. 무작위 키는 인덱스 전체 아무 곳에나 끼어든다. 꽉 찬 페이지에 끼어들면 페이지를 반으로 쪼개고(page split), 쪼개진 페이지는 한동안 반쯤 빈 채로 남는다.

직접 100만 줄씩 넣어서 기본키 인덱스를 비교해 봤다. UUIDv7은 앞 48비트가 밀리초 단위 시각이라 시간 순으로 정렬되는 UUID다. PostgreSQL 16에는 만드는 함수가 없어서, 시각을 앞에 붙이는 SQL 함수를 만들어 흉내 냈다.

```sql
CREATE EXTENSION IF NOT EXISTS pgstattuple;  -- 인덱스 내부 통계를 보는 확장

CREATE TABLE t_bigint (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, v int);
CREATE TABLE t_uuid4  (id uuid DEFAULT gen_random_uuid() PRIMARY KEY, v int);
CREATE TABLE t_uuid7  (id uuid DEFAULT uuid7() PRIMARY KEY, v int);  -- uuid7()은 직접 만든 함수

INSERT INTO t_bigint (v) SELECT g FROM generate_series(1, 1000000) g;
-- t_uuid4, t_uuid7에도 같은 방법으로 100만 줄

-- 리프 페이지 수와 평균 채움률
SELECT 't_bigint_pkey' AS idx, leaf_pages, avg_leaf_density FROM pgstatindex('t_bigint_pkey')
UNION ALL SELECT 't_uuid4_pkey', leaf_pages, avg_leaf_density FROM pgstatindex('t_uuid4_pkey')
UNION ALL SELECT 't_uuid7_pkey', leaf_pages, avg_leaf_density FROM pgstatindex('t_uuid7_pkey');
```

```text
      idx      | leaf_pages | avg_leaf_density
---------------+------------+------------------
 t_bigint_pkey |       2733 |            90.06
 t_uuid4_pkey  |       4931 |            70.05
 t_uuid7_pkey  |       4477 |            77.11
(3 rows)
```

`avg_leaf_density`가 리프 페이지가 평균 몇 % 차 있는지다. 순서대로 들어간 `bigint`는 90%로 꽉 차 있다(PostgreSQL B-tree의 기본 fillfactor가 90이다). 무작위 v4는 페이지 분할 때문에 70%로 떨어졌고, 키가 두 배 크기까지 겹쳐 리프 페이지 수가 1.8배가 됐다. 인덱스 크기로는 21MB 대 39MB였다. 같은 줄 수를 담는 데 메모리와 디스크를 거의 두 배 쓴다는 뜻이다.

세 키가 같은 100만 줄을 담는 데 쓴 잎 페이지를 나란히 놓으면 이렇다. 점이 흐르는 방향이 새 키가 들어가는 곳이다.

직접 만든 v7이 77%에 그친 건 시각을 밀리초까지만 넣고 나머지를 무작위로 채웠기 때문이다. 같은 밀리초 안에 들어온 수백 줄은 여전히 무작위 순서다. PostgreSQL 18에 들어간 내장 `uuidv7()`은 밀리초 아래 정밀도까지 써서 한 세션 안에서 순서가 유지되게 만든다.

이 실험은 인덱스가 메모리(shared_buffers 128MB)에 다 들어가는 크기라 차이가 작게 나온 편이다. 인덱스가 메모리보다 커지면 무작위 키는 삽입할 때마다 디스크에서 다른 페이지를 읽어 와야 한다. 순서대로 들어가는 키는 늘 같은 오른쪽 끝 페이지만 건드리니 이 비용이 거의 없다.

MySQL InnoDB에서는 차이가 더 크다. InnoDB는 테이블 자체를 기본키 순서로 저장한다(클러스터드 인덱스). 기본키가 무작위면 인덱스뿐 아니라 행 데이터가 들어갈 자리도 무작위가 된다. 그리고 보조 인덱스가 행 위치 대신 기본키 값을 들고 있어서, 기본키가 16바이트면 모든 보조 인덱스가 같이 커진다.

고르는 기준은 이렇다. 한 DB 안에서 번호를 매기면 충분하면 `bigint` identity가 가장 작고 빠르다. 여러 곳에서 ID를 미리 만들어야 하거나 외부에 노출되는 ID를 추측하기 어렵게 하고 싶으면 UUID를 쓰되, v4 대신 시간 순으로 정렬되는 v7을 쓴다. 둘을 섞는 방법도 흔하다. 내부 조인은 `bigint`로 하고, 외부에 보여 주는 ID만 UUID 열로 따로 두고 `UNIQUE`를 건다.

## 주문 당시 가격은 중복이 아니다

`order_items.unit_price`와 `products.price`는 둘 다 가격이라 중복처럼 보인다. 정규화를 처음 배우면 `unit_price`를 지우고 조인해서 가격을 가져오고 싶어진다. 그러면 가격을 올리는 순간 과거 주문 금액이 전부 바뀐다.

```sql
UPDATE products SET price = 42000 WHERE product_id = 1001;  -- 이어폰 가격 인상

SELECT oi.order_id, p.name, oi.unit_price, p.price AS current_price
FROM order_items oi JOIN products p USING (product_id)
WHERE product_id = 1001;
```

```text
UPDATE 1
 order_id |    name     | unit_price | current_price
----------+-------------+------------+---------------
        1 | 무선 이어폰 |      39000 |         42000
(1 row)
```

1번 주문은 39,000원에 팔렸다. 이건 지금 가격과 다른 사실이다. `unit_price`는 "이 주문에서 이 상품을 얼마에 팔았나"를 기록한 값이고, 주문과 상품 둘 다에 완전 종속이다. [정규화 글](/posts/db-modeling-normalization)의 함수 종속 플레이그라운드에서 `상품 → 가격`이 깨진 게 바로 이 이유였다. 중복이 아니라 다른 사실이니 정규화를 어긴 게 아니다.

배송지 주소, 주문 당시 상품명, 적용된 할인율, 환율도 같다. 원본이 나중에 바뀌어도 그 시점의 값을 유지해야 하면 스냅숏으로 따로 저장하는 게 올바른 모델링이다. 반대로 "회원의 현재 등급"처럼 늘 최신 값을 봐야 하는 걸 주문에 복사해 두면 그건 중복이다. 구분하는 질문은 하나다. 원본이 바뀌었을 때 이 값도 따라 바뀌어야 하는가.

## 일부러 다시 합칠 때 (반정규화)

정규화된 테이블은 쓰기와 일관성에 강하지만, 읽을 때는 조인과 집계가 필요하다. 주문 목록 화면에 주문마다 합계 금액을 보여 주려면 매번 `order_items`를 묶어서 더해야 한다. 이게 초당 수천 번 불리고, 주문 한 건에 상품이 수십 줄이면 부담이 된다. 이럴 때 계산 결과를 미리 저장해 두는 게 반정규화(denormalization)다. 성능을 위해 일부러 중복을 들이는 것이다.

반정규화 전에 먼저 해 볼 것이 있다. 느린 이유가 조인이 아니라 인덱스가 없어서인 경우가 많다. `EXPLAIN ANALYZE`로 실행 계획을 보고 인덱스부터 확인한다. 집계 결과를 잠깐 들고 있으면 되는 거라면 캐시나 머티리얼라이즈드 뷰로 원본을 건드리지 않고 해결할 수 있다. 반정규화는 그다음이다.

그래도 필요하면 비용을 알고 들인다. 쓰기가 늘어난다. 주문 상품 한 줄이 바뀔 때마다 주문 합계도 고쳐야 한다. 일관성이 깨질 수 있다. 고치는 경로 하나만 빠져도 합계가 틀린다. 그리고 경합이 생긴다. 상품 리뷰 수를 `products.review_count`에 들고 있으면, 인기 상품에 리뷰가 몰릴 때 모든 리뷰 작성이 그 한 줄의 락을 차례로 기다린다.

`orders.total_amount`를 추가하고 트리거로 맞춰 보자. 트리거는 테이블에 변화가 생길 때 DB가 자동으로 실행하는 함수다.

```sql
ALTER TABLE orders ADD COLUMN total_amount integer NOT NULL DEFAULT 0;

-- 이미 있는 주문은 한 번 계산해서 채운다
UPDATE orders o SET total_amount = coalesce(
  (SELECT sum(unit_price * quantity) FROM order_items WHERE order_id = o.order_id), 0);

CREATE FUNCTION sync_order_total() RETURNS trigger AS $$
BEGIN
  -- INSERT·UPDATE면 NEW, DELETE면 OLD에 바뀐 줄이 들어 있다
  UPDATE orders
     SET total_amount = coalesce((
           SELECT sum(unit_price * quantity) FROM order_items
            WHERE order_id = coalesce(NEW.order_id, OLD.order_id)), 0)
   WHERE order_id = coalesce(NEW.order_id, OLD.order_id);
  RETURN NULL;  -- AFTER 트리거라 반환값은 쓰이지 않는다
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER order_items_sync_total
AFTER INSERT OR UPDATE OR DELETE ON order_items
FOR EACH ROW EXECUTE FUNCTION sync_order_total();
```

트리거의 장점은 어느 경로로 데이터를 바꿔도 빠짐없이 맞춰진다는 것이다. 단점은 보이지 않는다는 것이다. 앱 코드만 읽는 사람은 `INSERT` 하나가 다른 테이블을 고친다는 걸 모른다. 대량으로 넣을 때 줄마다 불려서 느려지고, 이 예제는 `order_id`를 바꾸는 `UPDATE`가 오면 옛 주문 쪽 합계를 다시 계산하지 않는다(그것까지 하려면 `OLD.order_id` 쪽도 따로 계산해야 한다). 트리거를 쓰면 이런 경계 조건을 다 챙겨야 한다.

다른 방법은 두 가지다. 앱에서 같은 트랜잭션 안에 두 테이블을 함께 고치는 방법은 코드에서 흐름이 보이지만, 그 코드를 안 거치는 경로(관리자 SQL, 다른 서비스)에서는 어긋난다. 배치로 주기적으로 다시 계산하는 방법은 실시간성을 포기하는 대신 가장 단순하다. PostgreSQL의 머티리얼라이즈드 뷰가 이 방식이다.

```sql
CREATE MATERIALIZED VIEW daily_sales AS
SELECT (o.ordered_at AT TIME ZONE 'Asia/Seoul')::date AS day,
       sum(oi.unit_price * oi.quantity) AS revenue,
       count(DISTINCT o.order_id) AS orders
FROM orders o JOIN order_items oi USING (order_id)
GROUP BY 1;

-- CONCURRENTLY로 갱신하면 갱신 중에도 읽기가 막히지 않는다. 대신 UNIQUE 인덱스가 있어야 한다
CREATE UNIQUE INDEX ON daily_sales (day);
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales;   -- cron 같은 걸로 주기적으로 돌린다
```

MySQL에는 머티리얼라이즈드 뷰가 없어서 집계 테이블을 만들고 이벤트 스케줄러나 외부 배치로 채운다. 트리거는 MySQL도 `FOR EACH ROW`로 지원한다.

어떤 방법을 쓰든 원본과 사본이 맞는지 확인하는 쿼리를 하나 만들어 두고 주기적으로 돌린다. 결과가 0줄이어야 정상이다.

```sql
-- 저장된 합계와 실제 합계가 다른 주문
SELECT o.order_id, o.total_amount, coalesce(sum(oi.unit_price * oi.quantity), 0) AS actual
FROM orders o LEFT JOIN order_items oi USING (order_id)
GROUP BY o.order_id
HAVING o.total_amount <> coalesce(sum(oi.unit_price * oi.quantity), 0);
```

```text
 order_id | total_amount | actual
----------+--------------+--------
(0 rows)
```

## JSONB 열은 어디까지 괜찮나

PostgreSQL의 `jsonb`는 JSON을 파싱한 이진 형태로 저장하는 타입이다. 테이블 안에 스키마 없는 칸을 하나 둘 수 있으니, 정규화가 귀찮을 때 다 여기에 넣고 싶어진다.

잘 맞는 경우는 상품마다 속성이 제각각인 경우다. 이어폰에는 블루투스 버전과 노이즈 캔슬링, 케이스에는 무선 충전 여부, 이어팁에는 사이즈 목록이 있다. 이걸 열로 만들면 대부분 비어 있는 열이 수십 개 생긴다.

```sql
ALTER TABLE products ADD COLUMN attrs jsonb NOT NULL DEFAULT '{}';

UPDATE products SET attrs = '{"color": "white", "bluetooth": "5.3", "anc": true}' WHERE product_id = 1001;
UPDATE products SET attrs = '{"color": "white", "wireless_charging": true}'      WHERE product_id = 1002;
UPDATE products SET attrs = '{"sizes": ["S", "M", "L"]}'                         WHERE product_id = 1003;

-- @> (포함) 검색을 빠르게 하는 GIN 인덱스. jsonb_path_ops는 @>만 지원하는 대신 더 작다
CREATE INDEX products_attrs_idx ON products USING gin (attrs jsonb_path_ops);

SELECT product_id, attrs FROM products WHERE attrs @> '{"anc": true}';
```

```text
 product_id |                        attrs
------------+-----------------------------------------------------
       1001 | {"anc": true, "color": "white", "bluetooth": "5.3"}
(1 row)
```

넣은 순서와 키 순서가 다르다. `jsonb`는 저장할 때 키를 정렬하고(짧은 키가 먼저) 중복 키는 마지막 것만 남긴다. 원문 그대로가 필요하면 `json` 타입을 쓴다. 외부 API 응답 원본, 사용자별 화면 설정, 로그 부가 정보처럼 DB가 내용을 해석할 일이 적은 데이터도 `jsonb`가 잘 맞는다.

안티 패턴이 되는 경우는 분명하다. JSON 안의 값이 다른 테이블을 가리키면(`{"user_id": 42}`) 외래키를 걸 수 없어서, 지워진 회원 번호가 그대로 남는다. 자주 필터링하고 정렬하고 집계하는 값을 JSON에 넣으면 플래너가 통계를 제대로 못 써서 실행 계획이 나빠지고, 필요한 경로마다 식 인덱스를 따로 만들어야 한다. 타입 검사와 `NOT NULL`도 안 된다. 그리고 `jsonb` 안의 값 하나를 바꿔도 PostgreSQL은 값 전체를 새로 쓴다. 큰 문서의 카운터 하나를 자주 올리면 매번 문서 전체를 다시 쓴다.

기준은 이렇다. 모든 행에 있고, 조건이나 조인에 쓰고, 다른 테이블과 관계가 있는 값은 열로 뺀다. 행마다 다르고, 통째로 읽고 쓰고, 가끔 포함 검색만 하는 값은 `jsonb`에 둔다. MySQL 8의 `JSON` 타입도 이진 형식으로 저장한다. 인덱스는 생성 열(generated column)을 만들어 걸거나 8.0.13부터 식 인덱스로 걸고, 배열 안의 값은 8.0.17부터 다중 값 인덱스(multi-valued index)로 찾는다.

## 자주 보는 설계 실수

EAV(Entity-Attribute-Value)는 속성을 행으로 저장하는 방식이다. `(entity_id, attribute, value)` 테이블 하나에 모든 속성을 넣는다. 유연해 보이지만 `value`가 전부 문자열이라 타입도 제약도 없고, 상품 하나를 화면에 그리려면 속성 수만큼 셀프 조인하거나 피벗해야 한다. 속성이 정말 제각각이라면 위의 `jsonb`가 같은 문제를 더 잘 푼다.

쉼표로 이은 목록은 [정규화 글](/posts/db-modeling-normalization)의 1NF에서 본 문제가 검색에서 더 교묘하게 나타난다.

```sql
CREATE TEMP TABLE carts (cart_id int, product_ids text);
INSERT INTO carts VALUES (1, '1001,1003'), (2, '10030');

SELECT cart_id FROM carts WHERE product_ids LIKE '%1003%';   -- 1003번 상품이 담긴 장바구니?
```

```text
 cart_id
---------
       1
       2
(2 rows)
```

10030번 상품만 담긴 2번 장바구니까지 걸렸다. 앞뒤에 쉼표를 붙여 비교하는 식으로 땜질할 수는 있지만, 인덱스를 못 쓰고 외래키도 못 건다. `cart_items(cart_id, product_id)` 테이블로 나누는 게 답이다.

"성능 때문에 외래키를 안 건다"는 말도 자주 듣는다. 외래키 검사 비용은 실제로 있다. 자식을 넣을 때 부모 인덱스를 한 번 찾고, 부모를 지울 때 자식을 찾는다. 하지만 인덱스가 있으면 이건 인덱스 조회 한 번이다. 외래키를 빼면 고아 데이터(없는 회원의 주문)가 쌓이고, 그걸 찾아 지우는 정리 배치와 버그 추적에 드는 비용이 훨씬 크다. 느리다면 대부분 PostgreSQL에서 외래키 열 인덱스를 빠뜨린 경우다. 샤딩으로 테이블이 서로 다른 DB에 흩어져서 외래키를 걸 수 없는 경우는 예외인데, 그때는 앱과 정합성 검사 배치가 그 역할을 대신해야 한다.

소프트 삭제(soft delete)는 행을 지우지 않고 `deleted_at`에 시각을 적어 지운 것으로 치는 방식이다. 복구가 쉽고 기록이 남지만 함정이 있다. 탈퇴한 회원의 이메일로 다시 가입하려고 하면 `UNIQUE`가 막는다.

```sql
ALTER TABLE users ADD COLUMN deleted_at timestamptz;
UPDATE users SET deleted_at = now() WHERE user_id = 3;          -- 박서준 탈퇴
INSERT INTO users (email, name) VALUES ('park@example.com', '박서준');  -- 같은 이메일로 재가입
```

```text
ERROR:  duplicate key value violates unique constraint "users_email_key"
DETAIL:  Key (email)=(park@example.com) already exists.
```

PostgreSQL에서는 부분 유니크 인덱스로 "살아 있는 회원끼리만 이메일이 유일"하게 바꾼다.

```sql
ALTER TABLE users DROP CONSTRAINT users_email_key;
CREATE UNIQUE INDEX users_email_active_key ON users (email) WHERE deleted_at IS NULL;

INSERT INTO users (email, name) VALUES ('park@example.com', '박서준');  -- 재가입 성공
INSERT INTO users (email, name) VALUES ('park@example.com', '박서준');  -- 살아 있는 중복은 여전히 막는다
```

```text
INSERT 0 1
ERROR:  duplicate key value violates unique constraint "users_email_active_key"
DETAIL:  Key (email)=(park@example.com) already exists.
```

MySQL에는 부분 인덱스가 없다. `active_email VARCHAR(255) AS (IF(deleted_at IS NULL, email, NULL))` 같은 생성 열을 만들고 거기에 `UNIQUE`를 건다. `UNIQUE`는 `NULL`끼리는 중복으로 보지 않으니, 지운 행은 몇 개든 들어간다.

<Callout kind="warning" title="소프트 삭제는 모든 쿼리에 조건을 붙여야 한다">
`deleted_at IS NULL`을 빠뜨린 쿼리 하나가 탈퇴한 회원에게 마케팅 메일을 보낸다. 외래키도 소프트 삭제를 모르기 때문에, 지운 회원의 주문이 여전히 정상 참조로 남는다. 개인정보 보관 기한이 있으면 결국 진짜로 지우는 배치가 필요하다. 복구와 감사 기록이 목적이라면, 원본은 지우고 지운 행을 별도의 보관 테이블로 옮기는 방식이 조회 쿼리를 덜 오염시킨다.
</Callout>

이름도 설계의 일부다. PostgreSQL은 따옴표 없는 이름을 소문자로 바꾸니 `snake_case`로 쓴다. `"OrderItems"`처럼 따옴표로 대문자를 넣으면 그 뒤로 모든 쿼리에 따옴표를 붙여야 한다. 테이블 이름을 복수형(`users`)으로 할지 단수형(`user`)으로 할지는 팀마다 다르지만 섞지만 않으면 된다. 그런데 단수형을 고르면 바로 부딪히는 게 있다.

```sql
CREATE TABLE user (id int);
CREATE TABLE order (id int);
```

```text
ERROR:  syntax error at or near "user"
LINE 1: CREATE TABLE user (id int);
                     ^
ERROR:  syntax error at or near "order"
LINE 1: CREATE TABLE order (id int);
                     ^
```

`order`는 PostgreSQL과 MySQL 모두 예약어(`ORDER BY`)이고, `user`는 PostgreSQL에서 예약어(현재 사용자를 돌려주는 `SELECT user;`)다. 이 글이 처음부터 `users`, `orders`를 쓴 이유다. 외래키 열은 `user_id`처럼 가리키는 테이블 이름을 따라 짓고, 시각은 `_at`(`created_at`), 참거짓은 `is_`(`is_active`) 같은 규칙을 정해 두면 스키마만 보고 뜻을 알 수 있다.

## SQLD에서 묻는 식별자와 반정규화

SQLD 1과목에서 반정규화와 슈퍼타입·서브타입 변환은 2024년 개정 이후 출제 기준에서 비중이 달라졌으니, 응시하는 회차의 공식 출제 기준을 한 번 확인한다. 기출에서 자주 본 것들을 시험 말로 묶으면 이렇다.

식별자는 본질식별자(업무에 원래 있는 값, 이 글의 자연 키)와 인조식별자(일부러 만든 번호, 대리 키)로 구분한다. 인조식별자는 키가 단순해지고 바뀌지 않는 대신, 본질식별자에 `UNIQUE`를 따로 걸지 않으면 중복 데이터가 생기고 불필요한 인덱스가 하나 더 늘어난다는 단점이 짝으로 나온다.

반정규화는 정규화된 모델에서 성능을 위해 중복을 허용하는 것이고, 기법은 세 부류로 외운다.

- 테이블 반정규화: 병합(1:1 관계, 1:M 관계, 슈퍼타입·서브타입 병합), 분할(수직 분할은 자주 쓰는 열과 아닌 열을 나누고, 수평 분할은 행을 기간 등으로 나눈다. 파티셔닝이 수평 분할이다), 추가(중복 테이블, 통계 테이블, 이력 테이블, 부분 테이블)
- 컬럼 반정규화: 중복 컬럼 추가(조인을 줄이려고 부모 열을 자식에 복사), 파생 컬럼 추가(계산 결과를 저장. 이 글의 `total_amount`), 이력 테이블에 컬럼 추가(최신 여부, 시작·종료일), PK에 의한 컬럼 추가(복합 PK의 일부를 일반 열로도 둠), 응용 시스템 오작동을 위한 컬럼 추가(이전 값 보관)
- 관계 반정규화: 중복 관계 추가(여러 단계를 거쳐 조인하던 경로에 직접 관계를 하나 더 둔다)

반정규화 절차는 대상 조사(범위, 대량 처리, 통계, 자주 쓰는 조회) → 다른 방법 검토 → 반정규화 적용 순서다. 다른 방법으로는 뷰, 클러스터링, 인덱스 조정, 응용 프로그램 처리, 파티셔닝이 나온다. 반정규화가 첫 번째 선택이 아니라는 게 시험의 일관된 입장이다.

슈퍼타입·서브타입을 테이블로 바꾸는 방법도 같이 나온다. 하나로 합치는 Single Type(All in One), 서브타입마다 슈퍼타입 열을 넣는 Plus Type(Super+Sub), 각각 테이블로 두고 1:1로 잇는 One to One Type이다. 데이터가 적고 조회가 한 번에 일어나면 Single, 서브타입별로 따로 처리하면 Plus, 전체와 개별 처리가 고르게 섞이면 One to One을 고른다.

## 중복을 어디에 둘지 고르는 일

기본키는 바뀌지 않는 대리 키로 두고 자연 키에는 `UNIQUE`를 건다. 여러 곳에서 ID를 만들어야 하면 UUID를 쓰되 시간 순으로 정렬되는 v7을 고른다. 주문 당시 가격처럼 시점이 다른 사실은 중복이 아니니 스냅숏으로 저장한다. 반정규화는 인덱스와 캐시, 머티리얼라이즈드 뷰로 안 될 때 들이고, 원본과 사본을 맞추는 방법(트리거, 같은 트랜잭션, 배치)과 어긋남을 찾는 쿼리를 함께 둔다. `jsonb`는 행마다 다르고 통째로 읽는 값에만 쓴다. 나눈 테이블을 동시에 여러 요청이 고칠 때의 문제는 [트랜잭션과 격리 수준 글](/posts/db-transaction-isolation)에서 이어서 본다.

## 면접에서 나올 만한 질문

### 기본키로 자연 키와 대리 키 중 무엇을 쓰나요?

보통 대리 키를 기본키로 쓰고 자연 키에는 UNIQUE를 건다. 이메일 같은 자연 키는 바뀔 수 있고, 기본키가 바뀌면 외래키로 복사된 모든 곳과 캐시, 외부 시스템이 같이 바뀌어야 한다. 대리 키만 두고 UNIQUE를 빠뜨리면 업무상 중복이 생기니 둘은 같이 쓴다.

### UUID를 기본키로 쓰면 어떤 문제가 있나요?

크기와 삽입 위치가 문제다. bigint의 두 배인 16바이트라 인덱스와 외래키가 모두 커지고, v4는 무작위라 B-tree의 아무 페이지에나 끼어들어 페이지 분할이 잦다. 100만 줄로 실험하면 bigint 인덱스는 리프 채움률 90%, v4는 70%로 크기가 거의 두 배였다. InnoDB는 테이블 자체가 기본키 순서로 저장돼서 영향이 더 크다. 분산 생성이나 ID 노출 때문에 UUID가 필요하면 시간 순으로 정렬되는 UUIDv7을 쓰거나, 내부 키는 bigint로 두고 외부 노출용 UUID 열을 따로 둔다.

### 반정규화는 언제 하나요?

인덱스, 쿼리 수정, 캐시, 머티리얼라이즈드 뷰로도 읽기 성능이 안 나올 때 한다. 주문 합계나 리뷰 수처럼 자주 읽고 계산 비용이 큰 집계가 대표적이다. 들일 때는 원본과 사본을 맞추는 방법(트리거, 같은 트랜잭션에서 함께 갱신, 배치 재계산)을 정하고, 어긋남을 찾는 검사 쿼리를 함께 둔다. 카운터 같은 값은 한 행에 쓰기가 몰려 락 경합이 생길 수 있다는 것도 고려한다.

### 주문 테이블에 상품 가격을 저장하는 건 반정규화인가요?

아니다. 주문 상품의 가격은 "이 주문에서 얼마에 팔았나"라는 별개의 사실이라 주문과 상품 둘 다에 완전 종속이다. 상품 테이블의 가격은 지금 판매가다. 가격을 올렸을 때 과거 주문 금액이 바뀌면 안 되니 스냅숏으로 저장하는 게 올바른 모델링이다. 반대로 늘 최신 값이어야 하는 회원 등급을 주문에 복사하면 그건 중복이다.

### 외래키를 성능 때문에 안 거는 건 괜찮나요?

대부분은 손해다. 외래키 검사는 인덱스 조회 한 번이라 비용이 작고, 없으면 고아 데이터가 쌓여 정리 배치와 버그 추적 비용이 더 커진다. 외래키 때문에 느리다면 PostgreSQL에서 자식 쪽 외래키 열에 인덱스를 안 만든 경우가 많다. 샤딩으로 테이블이 다른 DB에 흩어져 걸 수 없을 때만 앱 검증과 정합성 배치로 대신한다.
