면접관이 "검색창 자동완성을 설계해 보세요"라고 말한다. 백엔드 면접이었다면 트라이를 그리고, 검색 기록을 모으는 파이프라인과 캐시 계층을 그리면 된다. 그 길은 [검색어 자동완성 설계 ①](/posts/sd-autocomplete-trie)에 정리했다. 그런데 이번 자리는 프런트엔드 면접이다. 서버 상자를 그리기 시작하면 면접관은 곧 이렇게 끊는다. "서버는 이미 있다고 치고요, 사용자가 '리액트'를 칠 때 브라우저에서는 무슨 일이 일어나나요?"

프런트엔드 시스템 디자인은 같은 기능을 반대쪽 끝에서 본다. 컴포넌트를 어떻게 나누고, 상태를 어디에 두고, API 응답을 어떤 모양으로 받고, 느린 네트워크와 낡은 기기에서 어떻게 버티고, 키보드와 화면 낭독기로도 쓸 수 있는지, 그리고 배포한 뒤 그게 잘 돌고 있는지 어떻게 아는지를 묻는다. 이 글은 그 질문들을 45분 안에 다루는 순서를 자동완성 하나로 끝까지 따라간다.

이 주제의 다른 글은 각도가 다르다. 상태를 종류별로 어디에 둘지는 [프런트엔드 상태 구조](/posts/frontend-state-architecture), 브라우저를 네트워크 끝의 노드로 보는 관점은 [분산 시스템으로서의 프런트엔드](/posts/frontend-as-distributed-system), 이 글의 순서를 큰 문제에 적용한 사례는 [뉴스 피드 화면 설계](/posts/fe-sd-news-feed)에 있다. 예제는 Node 22로 띄운 작은 서버와 React 19 앱을 Chromium 141(Playwright, 헤드리스)에서 돌렸고, 출력은 찍힌 그대로다.

## 같은 기능을 반대쪽 끝에서 본다

백엔드 설계 면접과 프런트엔드 설계 면접은 다루는 시스템이 같아도 확대하는 곳이 다르다. 백엔드 쪽은 초당 요청 수, 저장 공간, 샤딩과 복제처럼 서버 여러 대가 함께 버티는 법을 묻는다. 프런트엔드 쪽은 사용자 한 명의 기기 안을 묻는다. 그 기기는 CPU가 느릴 수 있고, 네트워크가 끊길 수 있고, 같은 앱이 탭 세 개에 떠 있을 수 있다.

## 45분 안에 무엇을 언제 말하나

흔히 RADIO라고 부르는 틀이 있다. 요구 사항(Requirements), 구조(Architecture), 데이터 모델(Data model), 인터페이스(Interface, 컴포넌트 API와 서버 API), 최적화와 깊이 파기(Optimizations)의 앞 글자다. 이름은 몰라도 된다. 순서가 중요하다. 이 글에서는 여기에 접근성과 관측을 따로 떼어 챙긴다. 면접에서 자주 빠지면서도 꼬리 질문으로 자주 돌아오는 두 가지라서다.

시간은 대략 이렇게 쓴다. 요구 사항에 5분, 컴포넌트 구조에 10분, 데이터와 API에 10분, 성능·접근성 깊이 파기에 15분, 관측과 약점 정리에 5분. 면접관이 특정 부분을 파고들면 그쪽으로 시간을 옮긴다. 정해진 시간표를 지키는 것보다 면접관이 궁금해하는 걸 따라가는 편이 낫다.

첫 5분에 물을 것은 기능보다 환경이다. 자동완성이라면 이런 질문이 답을 바꾼다.

- 주 사용 기기가 모바일인가. 그렇다면 화면 키보드가 목록을 가리고, 터치 대상 크기와 느린 CPU를 신경 써야 한다.
- 결과에 무엇이 나오나. 글자만인지, 썸네일과 카테고리가 붙는지에 따라 응답 크기와 렌더링 비용이 달라진다.
- 한국어 입력을 지원하나. 지원한다면 조합 중인 글자를 어떻게 다룰지 정해야 한다. 아래에서 실제로 잰다.
- 검색 결과 페이지가 검색 엔진에 잡혀야 하나. 자동완성 목록 자체는 상관없지만 결과 페이지의 렌더링 방식은 바뀐다.

질문이 끝나면 화면을 먼저 그린다. 입력창 하나, 그 아래 목록 하나, 목록의 한 줄에 무엇이 들어가는지. 상자와 화살표보다 화면 스케치가 먼저 나오는 게 프런트엔드 면접의 첫 신호다.

## 컴포넌트를 나누고 요청이 지나는 길을 긋는다

화면이 정해지면 컴포넌트로 나눈다. 자동완성은 크게 세 조각이다. 입력을 받는 `SearchInput`, 목록을 그리는 `SuggestionList`, 그 둘이 공유하는 상태와 요청 로직을 담은 훅(`useSuggestions`)이다. 목록 한 줄은 `SuggestionItem`으로 따로 둔다. 강조 표시나 썸네일 같은 변화가 생기면 이 한 조각만 바뀐다.

컴포넌트 API도 이때 정한다. 재사용할 컴포넌트라면 props가 곧 인터페이스다.

```ts
interface TypeaheadProps {
  fetchSuggestions: (q: string, signal: AbortSignal) => Promise<string[]>; // 데이터 출처를 바깥에서 주입
  debounceMs?: number;        // 기본 250
  minLength?: number;         // 이 글자 수부터 요청
  renderItem?: (item: string, query: string) => React.ReactNode; // 줄 모양을 바꿀 자리
  onSelect: (item: string) => void;
}
```

`fetchSuggestions`를 바깥에서 받으면 같은 컴포넌트로 상품 검색과 주소 검색을 모두 만들 수 있고, 테스트에서는 가짜 함수를 넣을 수 있다. `signal`을 넘기는 건 취소를 계약에 넣었다는 뜻이다.

응답 쪽에서는 세 가지를 정해 둔다. 첫째, 응답에 요청한 검색어(`q`)를 그대로 돌려받는다. 늦게 온 응답이 어느 검색어의 것인지 알아야 버릴 수 있다. 둘째, 캐시 기간을 정한다. 추천어는 몇 분 낡아도 괜찮으니 `Cache-Control: max-age=300` 정도로 CDN과 브라우저가 함께 쓰게 할 수 있다. 셋째, 에러 모양을 정한다. 자동완성이 실패했다고 빨간 경고를 띄우면 검색 자체를 방해한다. 조용히 목록을 닫고 사용자가 엔터로 검색할 수 있게 둔다.

여러 API를 조합해야 하는 화면이라면 화면 전용 API(BFF, Backend for Frontend)를 두는 선택도 여기서 나온다. 자동완성 하나로는 과하지만, 뒤에서 볼 뉴스 피드처럼 글·작성자·좋아요 수를 한 번에 그려야 하는 화면에서는 요청 수를 줄이는 큰 수단이 된다. 페이지를 넘기는 방식(오프셋과 커서)은 [페이지와 정렬](/posts/api-pagination-sorting)에서 다뤘다.

## 키를 누를 때마다 요청하면 생기는 일

가장 단순한 구현부터 만들어 재 봤다. 입력이 바뀔 때마다 effect에서 요청하고, 응답이 오면 목록을 바꾼다.

```jsx
// 첫 구현: 키 입력마다 요청
useEffect(() => {
  if (!q) return setItems([]);
  fetch(`/search?q=${encodeURIComponent(q)}`)
    .then((r) => r.json())
    .then((d) => setItems(d.items));
}, [q]);
```

실험 서버는 검색어가 짧을수록 늦게 답하게 했다. 실제로도 "r" 하나로 찾으면 후보가 많아 서버가 오래 걸리는 경우가 흔하다. 응답 지연은 `900 - 글자 수 × 110`ms(최소 60ms)다. Playwright로 "react ho"를 키 사이 90ms 간격으로 쳤다.

```text
== naive
요청 7번: "r" "re" "rea" "reac" "react" "react h" "react ho"
화면에 반영된 순서: react h(827ms) | react(859ms) | reac(873ms) | react ho(888ms) | rea(890ms) | re(897ms) | r(911ms)
입력값 "react ho", 마지막 목록: ["react","react query","react router","react hooks","redux"]
```

요청이 일곱 번 나갔다. 공백까지 친 "react "는 앞뒤를 자르면 "react"와 같아서 요청이 하나 줄었다. 문제는 둘째 줄이다. 응답이 보낸 순서와 거의 반대로 왔고, 마지막에 도착한 건 가장 먼저 보낸 "r"의 응답이었다. 입력창에는 "react ho"가 있는데 목록에는 "redux"까지 나온다. 아래 그림은 도착 순서대로 화면이 어떻게 바뀌었는지 다시 보여 준다.

이 버그는 개발자 컴퓨터에서는 잘 안 보인다. 로컬 서버는 모든 검색어에 비슷하게 빨리 답하니 순서가 뒤집힐 일이 적다. 사용자 휴대폰의 흔들리는 네트워크에서만 가끔 생기고, "검색창이 가끔 엉뚱한 걸 보여 준다"는 재현 안 되는 문의로 돌아온다. 같은 종류의 문제를 백엔드에서는 [경쟁 상태](/posts/race-conditions)라고 부른다.

## 줄이고, 끊고, 기억한다

고친 구현은 세 가지를 더했다. 입력이 250ms 멈춘 뒤에만 요청하고, 다음 입력이 오면 앞 요청을 `AbortController`로 취소하고, 받은 결과는 검색어를 키로 기억한다.

```jsx
// 고친 구현: 디바운스 + 취소 + 캐시
useEffect(() => {
  if (!q) return setItems([]);
  if (cache.current.has(q)) return setItems(cache.current.get(q));
  const ac = new AbortController();
  const t = setTimeout(() => {
    fetch(`/search?q=${encodeURIComponent(q)}`, { signal: ac.signal })
      .then((r) => r.json())
      .then((d) => { cache.current.set(q, d.items); setItems(d.items); })
      .catch((e) => { if (e.name !== "AbortError") throw e; });
  }, 250);
  return () => { clearTimeout(t); ac.abort(); }; // 다음 입력이 오면 예약도, 요청도 끊는다
}, [q]);
```

같은 입력을 다시 넣었다. 이어서 글자 세 개를 지웠다가 다시 쳤다.

```text
== tuned
요청 1번: "react ho"
화면에 반영된 순서: react ho <- react ho
입력값 "react ho", 마지막 목록: ["react hooks"]
지웠다 다시 친 뒤 요청 누계 2번, 반영: react <- react | react ho <- cache
```

요청이 한 번으로 줄었고 목록도 맞다. "react"까지 지웠을 때 한 번 더 요청했고, 다시 "react ho"를 치자 캐시에서 바로 꺼냈다. 세 장치는 하는 일이 서로 다르다. 디바운스는 요청 수를 줄이지만 순서를 보장하지 않는다. 사용자가 300ms쯤 멈췄다가 다시 치면 요청 두 개가 겹칠 수 있다. 그 겹침을 끊는 게 취소다. 캐시는 같은 질문을 두 번 하지 않게 한다. 디바운스의 세부 규칙과 React에서 디바운스가 망가지는 이유는 [디바운스와 스로틀](/posts/debounce-throttle)에, `AbortController`의 동작은 [fetch 제대로 쓰기](/posts/browser-fetch)에 있다.

취소 대신 쓸 수 있는 방법도 있다. 요청마다 번호를 붙이고, 응답이 오면 지금까지 화면에 반영한 번호보다 작으면 버린다. 취소는 서버가 이미 받은 요청을 되돌리지 못한다. 브라우저가 응답을 기다리지 않을 뿐이라 서버는 계산을 끝까지 한다. 번호 비교는 요청을 끊지는 않지만 어떤 데이터 계층에서도 쓸 수 있다. 실무에서는 TanStack Query 같은 라이브러리가 쿼리 키 단위로 이 일을 대신해 준다. [화면 데이터 캐시](/posts/client-data-cache)에 정리했다.

이 캐시를 그대로 두면 안 되는 점도 면접에서 짚어야 한다. `Map`은 계속 커진다. 하루 종일 켜 두는 관리자 화면이라면 오래된 항목부터 버리는 LRU로 크기를 묶는다. 추천어가 바뀌는 서비스라면 몇 분 지난 항목은 다시 받는다.

직접 해 보자. 응답이 도착한 순서대로 요청 번호가 주어진다. 지금까지 반영한 번호보다 큰 응답만 화면에 반영할 때, 반영되는 번호 목록을 돌려주는 함수다. 위 실험의 도착 순서를 그대로 테스트에 넣었다.

## 한글은 한 글자에 입력 이벤트가 여러 번 온다

요구 사항 단계에서 물었던 한국어 입력을 재 봤다. Chromium의 개발자 도구 프로토콜(`Input.imeSetComposition`)로 한글 입력기가 "리액트"를 조합하는 과정을 흉내 내고, 입력창에서 일어난 이벤트와 서버가 받은 요청을 찍었다. 운영체제 입력기를 직접 쓴 것은 아니어서 이벤트 수는 입력기와 브라우저에 따라 다를 수 있다.

```text
compositionstart()
input("ㄹ", isComposing=true)
input("리", isComposing=true)
input("리ㅇ", isComposing=true)
input("리애", isComposing=true)
input("리액", isComposing=true)
input("리액ㅌ", isComposing=true)
input("리액트", isComposing=true)
input("리액트", isComposing=true)
compositionend(리액트)
== naive 요청 7번: "ㄹ" "리" "리ㅇ" "리애" "리액" "리액ㅌ" "리액트"
== tuned 요청 1번: "리액트"
```

세 글자를 치는 동안 `input` 이벤트가 여덟 번 왔고, 키마다 요청하는 구현은 "ㄹ", "리ㅇ", "리액ㅌ" 같은 조합 중간 글자로 서버에 일곱 번 물었다. 영어 "react"보다 요청이 많고, 중간 글자로는 쓸모 있는 추천어도 거의 없다. 디바운스를 건 구현은 조합이 끝난 "리액트"로 한 번만 물었다.

조합 중에는 엔터 키도 조심해야 한다. 한글을 치다가 엔터를 누르면 조합을 끝내는 엔터와 검색을 실행하는 엔터가 겹친다. 크롬 계열에서는 조합을 끝내는 키 입력이 `keydown`으로도 전달되고 그때 `isComposing`이 `true`라서, 이 값을 확인하지 않으면 검색이 두 번 실행되거나 마지막 글자가 빠진 채 실행된다는 보고가 많다. 브라우저와 운영체제마다 동작이 달라서, 엔터 처리에서는 `event.nativeEvent.isComposing`(React)이나 `event.isComposing`을 먼저 확인하는 습관을 들인다.

## 키보드와 화면 낭독기로도 고를 수 있어야 한다

자동완성은 접근성 질문이 가장 많이 나오는 컴포넌트다. 마우스로 고르는 목록은 누구나 만들지만, 화면 낭독기 사용자는 목록이 열렸는지, 지금 몇 번째가 선택됐는지 들을 수 없다. W3C의 ARIA 작성 가이드(APG)에 콤보박스 패턴이 정리돼 있다. 입력창에 `role="combobox"`와 `aria-expanded`, `aria-controls`를 주고, 목록은 `role="listbox"`, 각 줄은 `role="option"`으로 둔다. 방향키로 움직일 때 포커스는 입력창에 그대로 두고 `aria-activedescendant`로 지금 고른 줄을 알린다. 포커스를 목록으로 옮기면 사용자가 계속 타자를 칠 수 없다.

위 실험 앱에서 아래 방향키를 한 번 누른 뒤 Playwright의 접근성 트리 스냅숏을 찍었다. 화면 낭독기가 받는 정보와 거의 같은 모양이다.

```text
- text: 검색
- combobox "검색" [expanded]: react ho
- listbox "추천 검색어":
  - option "react hooks" [selected]
```

입력창이 이름("검색")과 열린 상태를 갖고, 목록에 이름이 있고, 첫 줄이 선택된 상태로 읽힌다. `aria-*` 속성을 하나라도 빠뜨리면 이 트리에서 바로 티가 난다. 접근성을 말로만 하지 말고 이렇게 확인하는 방법까지 말하면 면접에서 설득력이 생긴다.

그 밖에 챙길 것은 짧게 말한다. 결과 개수가 바뀌면 `aria-live` 영역으로 "추천 검색어 5개"처럼 알린다. Esc로 목록을 닫는다. 모바일에서는 목록 한 줄의 높이를 44px 이상으로 둔다. 강조 표시를 색으로만 하지 않고 굵기도 바꾼다. 다국어라면 오른쪽에서 왼쪽으로 쓰는 언어에서 목록 정렬과 화살표 방향이 뒤집히는지 본다.

## 빠르다는 걸 숫자로 말한다

깊이 파기 단계에서 성능을 말할 때는 사용자가 느끼는 순간에 숫자를 붙인다. 자동완성에서 사용자가 느끼는 건 두 가지다. 키를 눌렀을 때 글자가 바로 찍히는가, 멈췄을 때 목록이 금방 뜨는가.

앞의 것은 INP(Interaction to Next Paint)로 잰다. 키 입력마다 무거운 목록을 다시 그리면 입력 자체가 늦어진다. React라면 입력값 상태와 목록 상태를 나누고, 목록 쪽을 `useDeferredValue`로 늦춰 입력이 먼저 그려지게 할 수 있다. 원리는 [React는 언제 다시 그리나](/posts/react-rerender)에 있다. 지표의 정의와 기준값은 [Core Web Vitals](/posts/core-web-vitals)에 있다.

뒤의 것은 "멈춘 뒤 목록이 뜨기까지"다. 디바운스 250ms에 왕복 시간이 더해진다. 디바운스를 너무 길게 잡으면 요청은 줄지만 느려 보인다. 첫 글자부터 캐시에 남은 인기 검색어를 바로 보여 주고 서버 결과로 바꾸는 방법, 입력창에 포커스가 가는 순간 인기 검색어 목록을 미리 받아 두는 방법이 있다. 자동완성 코드 자체를 처음 화면 번들에 넣을지도 정한다. 검색창이 첫 화면의 주인공이 아니라면 포커스할 때 불러와도 된다. [코드 스플리팅](/posts/code-splitting)에서 다룬 동적 import가 그 자리다.

## 배포한 뒤에 잘 도는지 어떻게 아나

마지막 5분에는 관측을 말한다. 프런트엔드 코드는 사용자 기기에서 돌아서, 서버 로그에는 브라우저에서 일어난 일이 거의 남지 않는다. 자동완성이라면 이런 숫자를 모은다.

- 입력이 멈춘 뒤 목록이 뜨기까지 걸린 시간의 p75와 p95. 기기 등급과 네트워크 종류로 나눠 본다.
- 목록을 연 횟수 대비 고른 횟수. 추천이 쓸모 있는지를 보여 준다.
- 요청 실패율과 취소율. 취소율이 지나치게 높으면 디바운스가 짧다는 뜻일 수 있다.
- 자바스크립트 에러. 소스맵으로 원래 줄을 찾는다.

사용자 기기에서 지표를 모아 묶는 방법은 [성능 지표는 어떻게 재나](/posts/performance-metrics-measurement)에, 에러를 모으고 되돌리는 방법은 [프런트엔드 에러 추적](/posts/frontend-error-tracking)에 있다. 면접에서는 도구 이름보다 "무엇을 재고 어떤 숫자가 나빠지면 무엇을 고칠지"를 말하는 편이 낫다.

마무리할 때 약점을 먼저 꺼낸다. 이 설계라면 캐시가 무한히 커질 수 있다는 점, 취소해도 서버는 계산을 끝낸다는 점, 오프라인일 때 아무것도 보여 주지 못한다는 점을 들 수 있다. 각각 LRU, 서버 쪽 요청 수 제한과 CDN 캐시, 최근 검색어를 기기에 저장해 두는 방법으로 이어 말하면 된다.

## 면접관이 자주 끼어드는 자리

같은 자동완성 문제라도 면접관이 끼어드는 지점은 대개 정해져 있다. 준비할 때 이 지점마다 한두 문장짜리 답을 미리 만들어 두면 좋다.

"서버 렌더링을 할 건가요?"는 자동완성보다 그 페이지 전체의 질문이다. 검색 결과 페이지가 검색 엔진에 잡혀야 하면 서버에서 그리고, 자동완성은 어차피 사용자 입력 뒤에 생기니 클라이언트에서 그린다. 렌더링 방식 고르기는 [CSR, SSR, SSG, ISR, 스트리밍](/posts/rendering-strategies)에 정리했다.

"상태 관리 라이브러리를 쓸 건가요?"에는 상태의 종류부터 나눈다. 입력값은 그 컴포넌트에만 있는 상태고, 추천 결과는 서버에서 빌려 온 상태고, 검색 결과 페이지의 검색어는 주소에 있어야 하는 상태다. 셋이 사는 곳이 다르니 전역 저장소 하나로 묶을 이유가 없다. 이 구분은 [프런트엔드 상태 구조](/posts/frontend-state-architecture)에서 이어 간다.

"요청이 실패하면요? 느리면요?"에는 기다리는 화면과 실패한 화면을 따로 말한다. 느릴 때는 이전 목록을 흐리게 유지하고 작은 표시만 붙인다. 목록이 깜빡이며 비었다 채워지는 게 더 느려 보인다. 기다리는 화면을 고르는 기준은 [로딩 패턴](/posts/loading-patterns)에 있다.

자동완성 하나로 요구 사항, 컴포넌트, API, 상태, 성능, 접근성, 관측을 모두 지나왔다. 면접에서 큰 화면을 받아도 순서는 같다. 화면부터 그리고, 요청이 지나는 길을 긋고, 그 길에서 실제로 깨지는 곳을 숫자로 말한다.

## 면접에서 나올 만한 질문

### 프런트엔드 시스템 디자인은 백엔드 시스템 디자인과 무엇이 다른가요?

같은 기능이라도 사용자 기기 안을 확대해서 본다. 서버 대수나 샤딩 대신 컴포넌트 구조, 상태를 둘 곳, API 응답 모양, 느린 네트워크와 기기에서의 성능, 접근성, 배포 후 관측을 묻는다. 어림하는 숫자도 초당 요청 수가 아니라 입력 반응 시간, 번들 크기, DOM 노드 수 같은 것이다. 다만 클라이언트 결정이 서버 비용을 바꾸니 백엔드 숫자와도 이어서 말할 수 있어야 한다.

### 45분 동안 어떤 순서로 진행하나요?

요구 사항과 환경 질문으로 5분, 화면 스케치와 컴포넌트 구조로 10분, 데이터 모델과 API로 10분, 성능·접근성 같은 깊이 파기로 15분, 관측과 약점 정리로 5분 정도를 쓴다. 흔히 RADIO라고 부르는 순서와 같다. 면접관이 특정 부분을 파고들면 시간표보다 그쪽을 따라간다. 첫 질문을 건너뛰면 나머지 시간을 잘못된 문제에 쓰게 된다.

### 자동완성에서 키 입력마다 요청하면 무엇이 문제인가요?

요청 수가 글자 수만큼 늘어 서버 비용이 커지고, 더 큰 문제는 응답이 뒤죽박죽으로 온다는 점이다. 실험에서는 가장 먼저 보낸 "r"의 응답이 마지막에 도착해 입력값과 다른 목록이 화면에 남았다. 디바운스로 요청을 줄이고, 다음 입력이 오면 앞 요청을 취소하거나 요청 번호로 낡은 응답을 버리고, 결과를 캐시해 같은 질문을 반복하지 않는다.

### 디바운스만 걸면 응답 순서 문제가 해결되나요?

해결되지 않는다. 디바운스는 요청 수를 줄일 뿐이라, 사용자가 디바운스 시간보다 조금 길게 멈췄다가 다시 치면 요청 두 개가 겹치고 순서가 뒤집힐 수 있다. 겹침은 AbortController로 앞 요청을 끊거나, 응답의 검색어나 요청 번호를 지금 값과 비교해 버리는 방식으로 막는다. 취소는 브라우저가 기다리지 않을 뿐이고 서버는 계산을 끝까지 한다는 점도 함께 말한다.

### 한국어 입력에서 따로 신경 쓸 점은 무엇인가요?

한글은 조합 중에도 input 이벤트가 계속 오고 값이 "ㄹ", "리ㅇ"처럼 중간 글자로 바뀐다. 실험에서는 "리액트" 세 글자에 이벤트가 여덟 번 왔고, 키마다 요청하는 구현은 일곱 번 요청했다. 디바운스로 조합이 끝난 값만 보내고, 엔터 처리에서는 isComposing을 확인해 조합을 끝내는 엔터가 검색을 실행하지 않게 한다. 이 동작은 브라우저와 입력기마다 다를 수 있어 실제 기기에서 확인한다.

### 자동완성의 접근성은 어떻게 만들고 어떻게 확인하나요?

ARIA 작성 가이드의 콤보박스 패턴을 따른다. 입력창에 combobox 역할과 aria-expanded, aria-controls를 주고, 목록은 listbox, 각 줄은 option으로 두며, 포커스는 입력창에 둔 채 aria-activedescendant로 선택된 줄을 알린다. 확인은 접근성 트리를 직접 본다. 개발자 도구의 접근성 패널이나 Playwright의 aria 스냅숏으로 이름, 열린 상태, 선택된 줄이 읽히는지 본다.

### 결과 캐시는 어디까지 키워도 되나요?

그냥 Map에 넣으면 앱을 오래 켜 둘수록 계속 커진다. 크기 상한을 두고 오래 안 쓴 항목부터 버리는 LRU로 묶고, 추천어가 바뀌는 서비스라면 몇 분 지난 항목은 다시 받는다. 서버 응답에 Cache-Control을 주면 브라우저 HTTP 캐시와 CDN도 같은 일을 나눠 맡는다. TanStack Query를 쓰면 staleTime과 gcTime이 같은 역할을 한다.

### 배포한 뒤 자동완성이 잘 동작하는지는 어떻게 아나요?

사용자 기기에서 숫자를 모은다. 입력이 멈춘 뒤 목록이 뜨기까지의 p75·p95를 기기와 네트워크별로 나눠 보고, 목록을 연 횟수 대비 고른 비율, 요청 실패율과 취소율, 자바스크립트 에러를 함께 본다. 서버 로그는 브라우저에서 생긴 지연과 에러를 보여 주지 못하니 RUM과 에러 추적이 따로 필요하다. 숫자마다 나빠지면 무엇을 고칠지까지 정해 두는 게 관측의 목적이다.
