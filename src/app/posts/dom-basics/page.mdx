## HTML 문자열이 객체 트리가 된다

브라우저는 받은 HTML 텍스트를 읽어(파싱) 객체로 바꾼다. 태그 하나가 객체 하나가 되고, 태그 안에 들어 있던 것은 그 객체의 자식이 된다. 이렇게 만든 객체 트리가 DOM(Document Object Model)이다. 자바스크립트는 HTML 문자열이 아니라 이 트리를 만진다. `document`가 트리의 뿌리이고, 그 아래 `html`, 다시 그 아래 `head`와 `body`가 있다.

트리에는 태그만 있는 게 아니다. 태그 사이의 줄바꿈과 공백도 텍스트 노드로 들어간다. 위 목록에서 `ul`의 자식을 세어 보면 바로 보인다.

```js
const list = document.getElementById("list");
console.log(list.childNodes.length, list.children.length);
console.log([...list.childNodes].map(n => n.nodeName).join(", "));
console.log(list.firstChild.nodeType, JSON.stringify(list.firstChild.textContent), list.firstElementChild.nodeType);
console.log(document.documentElement.nodeName, document.head.nodeName, document.body.nodeName, document.nodeType);
```

`li`를 두 개만 둔 목록에서 돌린 결과다.

```text
5 2
#text, LI, #text, LI, #text
3 "\n  " 1
HTML HEAD BODY 9
```

`childNodes`는 다섯 개, `children`은 두 개다. `childNodes`는 텍스트 노드까지 모든 노드를 담고, `children`은 요소만 담는다. `nodeType`이 1이면 요소, 3이면 텍스트, 9면 문서다. `firstChild`로 첫 항목을 잡으려다 줄바꿈 텍스트를 잡는 실수가 여기서 나온다. 요소만 원하면 `firstElementChild`, `nextElementSibling`처럼 이름에 Element가 붙은 쪽을 쓴다.

요소 객체는 여러 층의 프로토타입을 물려받는다. `input` 하나의 체인을 찍어 보면 이렇다.

```js
const chain = [];
for (let o = Object.getPrototypeOf(document.createElement("input")); o; o = Object.getPrototypeOf(o)) {
  chain.push(o.constructor.name);
}
console.log(chain.join(" -> "));
```

```text
HTMLInputElement -> HTMLElement -> Element -> Node -> EventTarget -> Object
```

맨 아래 `EventTarget`이 `addEventListener`를 주고, `Node`가 `appendChild`·`childNodes`·`textContent` 같은 트리 기능을, `Element`가 `querySelector`·`classList`·`getAttribute`를, `HTMLElement`가 `hidden`·`dataset`·`click()`을, 마지막 `HTMLInputElement`가 `value`·`checked`를 준다. 텍스트 노드는 `Element`를 거치지 않고 `CharacterData`를 거쳐 `Node`로 간다. 그래서 텍스트 노드에는 `querySelector`가 없다. 체인을 따라 메서드를 찾는 원리는 [프로토타입 체인](/posts/js-prototype-chain)과 같다.

`element.querySelectorAll()`은 그 요소의 자손만 본다. 요소 자신은 선택자에 맞아도 결과에 들어가지 않는다. 아래 CodePlayground에서 직접 만들어 보면 이 차이가 손에 잡힌다.

찾는 게 없을 때의 반응도 다르다. `querySelector(".nope")`는 `null`, `querySelectorAll(".nope")`는 길이 0인 목록을 준다. 그래서 `null` 검사를 빼먹고 바로 속성을 쓰면 에러가 나는 쪽은 `querySelector`다.

## 찾는 방법마다 돌려주는 것이 다르다

처음 버그로 돌아가자. 같은 "요소 목록"이라도 무엇으로 찾았느냐에 따라 살아 있는 목록(live)과 찍어 둔 목록(static)으로 갈린다.

```js
const live = document.getElementsByTagName("li");
const snap = document.querySelectorAll("li");
const liveNodes = list.childNodes;
list.append(document.createElement("li"));
console.log(live.length, snap.length, liveNodes.length);
console.log(Object.prototype.toString.call(live), Object.prototype.toString.call(snap));
console.log(typeof snap.forEach, typeof live.forEach);
```

```text
3 2 6
[object HTMLCollection] [object NodeList]
function undefined
```

`li`를 하나 붙였더니 `getElementsByTagName`의 결과는 3이 되고, `querySelectorAll`의 결과는 2 그대로다. `childNodes`도 살아 있는 목록이라 6이 됐다. 그리고 `HTMLCollection`에는 `forEach`가 없다. `[...live]`나 `Array.from(live)`로 배열로 바꿔 써야 한다.

| 찾는 방법 | 돌려주는 것 | DOM이 바뀌면 |
| --- | --- | --- |
| `getElementById` | 요소 하나 또는 `null` | 해당 없음 |
| `querySelector` | 요소 하나 또는 `null` | 해당 없음 |
| `querySelectorAll` | `NodeList` | 그대로(static) |
| `getElementsByClassName`, `getElementsByTagName` | `HTMLCollection` | 따라 바뀜(live) |
| `children` | `HTMLCollection` | 따라 바뀜(live) |
| `childNodes` | `NodeList` | 따라 바뀜(live) |

`NodeList`라는 이름만 보고 static이라고 외우면 틀린다. `childNodes`는 `NodeList`지만 살아 있다. 확실한 기준은 "`querySelectorAll`이 돌려준 것만 찍어 둔 목록"이다.

처음 코드가 두 개만 지운 과정을 한 칸씩 따라가 보자. 칸은 문서에 있는 네 `li`이고, 아래 상자는 그 순간의 `items` 내용이다.

고치는 방법은 셋이다. `querySelectorAll`로 찍어 둔 목록을 돌거나, `[...items]`로 배열을 만든 뒤 돌거나, 뒤에서부터 돈다(`for (let i = items.length - 1; i >= 0; i--)`). 앞의 둘이 읽기 쉽다. 살아 있는 목록이 쓸모없는 건 아니다. 한 번 잡아 두고 여러 번 `length`만 볼 때는 다시 찾을 필요가 없다. 다만 반복문 안에서 목록에 영향을 주는 변경을 하면 위와 같은 일이 난다.

브라우저의 선택자 엔진은 보통 오른쪽 끝 조각부터 본다. 후보 요소가 맨 오른쪽 조건(`a[href^="/posts"]`)에 맞는지 먼저 확인하고, 맞을 때만 조상 쪽으로 올라가며 나머지 조건을 확인한다. 대부분의 요소가 오른쪽 끝 조건에서 걸러지니 조상을 훑는 비용을 아낀다. 그래서 `.list *`처럼 오른쪽 끝이 넓은 선택자는 모든 요소를 후보로 만든다. 다만 실제 페이지에서 선택자 하나의 속도가 병목이 되는 일은 드물다. 그보다 아래에서 볼 레이아웃 비용이 훨씬 크다.

자주 쓰는 도구가 두 개 더 있다. `el.matches(selector)`는 이 요소가 선택자에 맞는지 참·거짓으로 답하고, `el.closest(selector)`는 자기 자신부터 시작해 조상으로 올라가며 처음 맞는 요소를 돌려준다. 클릭한 곳에서 가장 가까운 카드나 행을 찾을 때 쓰고, [이벤트 위임](/posts/event-delegation)의 핵심 도구가 된다.

## 속성과 프로퍼티는 다른 값이다

DOM에서 "값"이라는 말은 두 군데를 가리킨다. HTML에 적힌 속성(attribute)과 자바스크립트 객체의 프로퍼티(property)다. 처음에는 프로퍼티가 속성에서 값을 가져오지만, 그 뒤로는 따로 움직이는 경우가 있다. 입력창이 대표적이다.

```html
<input id="name" value="kim">
<input id="agree" type="checkbox">
<a id="link" href="/posts/dom">글</a>
```

Playwright로 입력창을 비우고 `lee`를 친 뒤 값을 읽었다.

```js
const name = document.getElementById("name");
console.log(name.getAttribute("value"), name.value, name.defaultValue);
name.setAttribute("value", "park");
console.log(name.getAttribute("value"), name.value);
const agree = document.getElementById("agree");
agree.checked = true;
console.log(agree.hasAttribute("checked"), agree.checked);
const link = document.getElementById("link");
console.log(link.getAttribute("href"), link.href);
```

```text
kim lee kim
park lee
false true
/posts/dom https://blog.test/posts/dom
```

`value` 속성은 처음 값(`defaultValue`)이고, `value` 프로퍼티는 지금 화면에 있는 값이다. 사용자가 한 번 입력하면 그 뒤로 속성을 `park`로 바꿔도 화면 값은 `lee`에서 움직이지 않는다. 체크박스도 같다. `checked` 프로퍼티를 켜도 HTML의 `checked` 속성은 생기지 않는다. `href`는 프로퍼티가 절대 주소로 풀어 준다.

그래서 폼 값을 읽을 때는 `getAttribute("value")`가 아니라 `.value`를 읽는다. 반대로 "초기화 버튼을 누르면 처음 값으로 돌아간다"는 동작은 속성에 남은 처음 값을 쓰는 것이다. React에서 `defaultValue`(비제어)와 `value`(제어)가 나뉘는 것도 이 구분을 그대로 옮긴 것이다.

`data-*` 속성은 `dataset`으로 읽고 쓴다. 하이픈 이름이 camelCase로 바뀐다.

```js
name.dataset.userId = "42";
console.log(name.outerHTML);
```

```text
<input id="name" value="park" data-user-id="42">
```

## textContent와 innerText, innerHTML

글자를 넣고 뺄 때도 세 가지가 섞여 쓰인다.

```html
<p id="p">보이는 글 <span style="display:none">숨긴 글</span> <b>굵은 글</b></p>
```

```js
console.log(JSON.stringify(p.textContent));
console.log(JSON.stringify(p.innerText));
```

```text
"보이는 글 숨긴 글 굵은 글"
"보이는 글 굵은 글"
```

`textContent`는 트리에 있는 텍스트 노드를 그대로 이어 붙인다. CSS를 보지 않는다. `innerText`는 화면에 보이는 대로의 글자를 준다. 숨긴 요소는 빠지고 줄바꿈도 렌더링 결과를 따른다. 화면을 알아야 하니 `innerText`를 읽으면 브라우저가 스타일과 레이아웃을 최신으로 맞춰야 한다. 반복문 안에서 읽으면 아래에서 볼 강제 레이아웃이 그대로 생긴다. 특별한 이유가 없으면 `textContent`를 쓴다.

`innerHTML`은 문자열을 HTML로 해석해서 넣는다. 사용자 입력을 그대로 넣으면 `<img src=x onerror=...>` 같은 문자열이 코드로 실행된다. 이건 [XSS](/posts/xss)에서 따로 다룬다. 글자만 넣을 거면 `textContent`, 요소를 만들 거면 `createElement`나 `append`를 쓴다.

## DOM을 바꾸면 화면은 나중에 바뀐다

`el.style.width = "120px"`를 실행하는 순간 화면이 바로 바뀌지는 않는다. 브라우저는 "스타일을 다시 계산해야 한다", "배치(레이아웃)를 다시 해야 한다"는 표시만 해 두고, 스크립트가 끝난 뒤 다음 프레임을 그릴 때 한꺼번에 처리한다. 스타일 계산 → 레이아웃 → 페인트 → 합성으로 이어지는 이 과정은 [이벤트 루프](/posts/event-loop)에서 본 것처럼 태스크 사이에서만 돈다.

문제는 그 사이에 크기나 위치를 읽을 때다. `offsetWidth`, `offsetHeight`, `getBoundingClientRect()`, `scrollTop`, `getComputedStyle()`, 그리고 앞에서 본 `innerText`가 그런 값이다. 브라우저는 정확한 값을 주려고 미뤄 둔 레이아웃을 그 자리에서 해 버린다. 이걸 강제 동기 레이아웃(forced synchronous layout), 흔히 강제 리플로라고 한다.

아래 그림은 상자 200개의 폭을 1px씩 늘리는 두 가지 방법이다. 다음을 누르면 레이아웃이 몇 번 일어나는지 보인다.

실제로 재 봤다. Chrome DevTools Protocol의 `Performance.getMetrics`가 주는 `LayoutCount`를 함수 실행 전후로 비교했다.

```js
// 읽고 바로 쓰기
for (const b of boxes) {
  b.style.width = (b.offsetWidth + 1) + "px";
}

// 먼저 다 읽고, 한 번에 쓰기
const widths = boxes.map(b => b.offsetWidth);
boxes.forEach((b, i) => { b.style.width = (widths[i] + 1) + "px"; });
```

```text
interleaved     ms 24.8 layout during JS 200 layout incl. frame 200 style 200
batched         ms 0.3 layout during JS 1 layout incl. frame 1 style 1
appendMany      ms 2.3 layout during JS 1 layout incl. frame 1 style 1
appendFragment  ms 1.8 layout during JS 1 layout incl. frame 1 style 1
appendManyRead  ms 899.6 layout during JS 1000 layout incl. frame 1000 style 1000
```

시간은 이 기기에서 한 번 돈 값이라 기기마다 다르다. 봐야 할 것은 레이아웃 횟수다. 번갈아 하면 200번, 모아서 하면 1번이다.

아래 세 줄이 흔한 오해를 풀어 준다. `appendMany`는 반복문에서 `div` 1,000개를 하나씩 `append`했다. 그래도 레이아웃은 1번이다. 쓰기만 하면 브라우저가 알아서 모아 둔다. `DocumentFragment`에 모았다가 한 번에 넣은 `appendFragment`도 1번이다. 시간 차이는 크지 않다. "DOM에 하나씩 넣으면 그때마다 리플로가 일어난다"는 설명은 반만 맞다. 리플로를 부르는 건 넣는 행위가 아니라 넣은 뒤에 크기를 읽는 행위다. `appendManyRead`처럼 매번 `wrap.offsetHeight`를 읽으면 1,000번 레이아웃을 하고 900ms 가까이 걸린다. 요소가 늘수록 한 번의 레이아웃도 비싸져서 시간이 횟수보다 빠르게 늘어난다.

`DocumentFragment`나 `append(...nodes)`, `replaceChildren()`이 쓸모없다는 뜻은 아니다. 코드가 "준비하고 한 번에 넣는다"는 모양이 되니 실수로 중간에 읽는 코드가 끼어들 틈이 줄어든다. 애니메이션처럼 매 프레임 바꾸는 경우의 비용은 [애니메이션 성능](/posts/animation-performance)에, 레이아웃 스래싱이 INP를 어떻게 키우는지는 [Core Web Vitals](/posts/core-web-vitals)에 있다.

## 현장에서 이 구조를 만나는 순간

가장 흔한 첫 만남은 이 에러다.

```text
TypeError: Cannot set properties of null (setting 'textContent')
```

`<head>` 안의 스크립트가 아직 파싱되지 않은 `#app`을 찾으면 `querySelector`가 `null`을 준다. 파서는 위에서 아래로 읽으면서 트리를 만들고, 스크립트를 만나면 멈춰서 실행한다. 그 시점에는 아래쪽 요소가 트리에 없다. 아래는 같은 페이지에서 순서대로 찍힌 로그다.

```html
<head>
  <script>console.log("D1", document.querySelector("#app"));</script>
  <script>document.addEventListener("DOMContentLoaded", () => console.log("D3", document.querySelector("#app").nodeName));</script>
</head>
<body><div id="app"></div>
  <script>console.log("D4", document.readyState);</script>
</body>
```

```text
D1 null
D4 loading
D3 DIV
```

해결은 `<script defer>`(또는 `type="module"`, 기본이 defer처럼 동작한다)로 파싱이 끝난 뒤 실행하거나, 스크립트를 `</body>` 앞으로 옮기거나, `DOMContentLoaded`를 기다리는 것이다.

느려진 화면은 개발자 도구 Performance 패널에서 보라색 Layout 막대를 찾는다. 스크립트 안에서 강제로 일어난 레이아웃에는 경고 삼각형이 붙고, 누가 불렀는지 호출 스택이 나온다. Console의 Verbose 수준을 켜 두면 이런 줄도 남는다. 위 `appendManyRead`를 돌릴 때 CDP 로그로 받은 실제 문구다.

```text
Forced reflow while executing JavaScript took 190ms
```

그 밖에 자주 만나는 증상들이다.

- 목록의 일부만 바뀐다: 살아 있는 컬렉션을 돌면서 그 컬렉션을 바꾸고 있는지 본다.
- 첫 자식이 이상한 값이다: `firstChild`가 줄바꿈 텍스트 노드를 잡았다. `firstElementChild`로 바꾼다.
- 탭이 점점 무거워진다: 지운 요소를 변수나 배열이 계속 잡고 있으면 문서에서 떨어진 채 메모리에 남는다. 찾는 방법은 [메모리 누수](/posts/js-memory-leak)의 detached 요소 항목에 있다. 콘솔에서는 Elements 패널에서 고른 요소를 `$0`으로 바로 만질 수 있어 확인이 빠르다.
- 입력값을 읽었는데 처음 값이 나온다: `getAttribute("value")`를 읽고 있다.

## React를 쓰면 DOM을 덜 만질 뿐이다

React를 쓰면 `querySelector`를 쓸 일이 거의 없다. 상태를 바꾸면 React가 이전 결과와 비교해 바뀐 부분만 DOM에 반영한다. 이 비교와 반영 과정은 [리렌더링](/posts/react-rerender)에서 다뤘다. 그래도 DOM이 사라진 건 아니라서 위의 규칙이 그대로 살아 있다.

- React가 관리하는 노드를 `innerHTML`이나 `remove()`로 직접 바꾸면 React가 기억하는 트리와 실제 트리가 어긋난다. 직접 만져야 하면 `ref`로 잡은 노드 중 React가 자식을 그리지 않는 곳(차트, 지도 라이브러리가 들어갈 빈 `div`)만 만진다.
- 크기를 재서 위치를 정하는 툴팁은 `useLayoutEffect`에서 잰다. 브라우저가 그리기 전에 실행되어 깜빡임이 없다. 다만 여기서 읽는 `getBoundingClientRect()`도 강제 레이아웃이다. 여러 컴포넌트가 각자 읽고 쓰면 위의 번갈아 하기가 그대로 생긴다.
- 제어 컴포넌트의 `value`는 앞에서 본 프로퍼티 쪽이고, `defaultValue`는 속성 쪽이다.

## 직접 만들어 보는 querySelectorAll

## 다시 할 일 목록으로

`todo`가 두 개 남은 이유는 `getElementsByClassName`이 돌려준 목록이 DOM을 따라 살아 움직였기 때문이다. DOM은 HTML 문자열이 아니라 객체 트리이고, 찾는 방법마다 돌려주는 것의 성질이 다르다. 그리고 그 트리를 바꾸는 것보다 바꾼 직후에 크기를 읽는 것이 비싸다. 이 트리 위에서 클릭이 어떻게 오르내리는지는 [이벤트 전파](/posts/event-propagation)에서 이어진다.

## 면접에서 나올 만한 질문

### DOM이 무엇인가요?

브라우저가 HTML을 파싱해서 만든 객체 트리이고, 자바스크립트가 문서를 읽고 바꾸는 인터페이스다. 태그는 요소 노드가 되고, 태그 사이 글자와 공백은 텍스트 노드가 된다. 그래서 `childNodes`에는 줄바꿈 텍스트가 섞이고, 요소만 보려면 `children`을 쓴다.

### querySelectorAll과 getElementsByClassName의 차이는 무엇인가요?

`querySelectorAll`은 호출한 순간의 결과를 찍어 둔 static `NodeList`를 주고, `getElementsByClassName`은 DOM이 바뀌면 따라 바뀌는 live `HTMLCollection`을 준다. 살아 있는 목록을 돌면서 그 목록에서 빠지게 만드는 변경을 하면 인덱스가 밀려 항목을 건너뛴다. `HTMLCollection`에는 `forEach`도 없어 배열로 바꿔 쓴다.

### NodeList는 항상 static인가요?

아니다. `querySelectorAll`이 주는 `NodeList`만 static이고, `childNodes`가 주는 `NodeList`는 live다. 타입 이름보다 어디서 얻었는지가 기준이다.

### 속성(attribute)과 프로퍼티(property)는 어떻게 다른가요?

속성은 HTML에 적힌 값이고 프로퍼티는 DOM 객체의 현재 값이다. 입력창의 `value` 속성은 처음 값(`defaultValue`)으로 남고, 사용자가 입력한 값은 `value` 프로퍼티에만 있다. 그래서 폼 값은 `.value`로 읽는다. `href` 프로퍼티는 절대 주소로 풀린 값을 준다.

### 리플로(레이아웃)는 언제 일어나고 어떻게 줄이나요?

DOM이나 스타일을 바꾸면 브라우저는 다시 계산할 필요만 표시해 두고 다음 프레임에 한 번 처리한다. 그 전에 `offsetWidth`, `getBoundingClientRect()`, `innerText` 같은 값을 읽으면 그 자리에서 레이아웃을 강제로 한다. 읽기와 쓰기를 번갈아 하지 말고 먼저 다 읽은 뒤 한꺼번에 쓴다. 실제로 재 보면 상자 200개를 번갈아 처리할 때 레이아웃 200번, 모아서 처리하면 1번이었다.

### DOM에 요소를 하나씩 추가하면 매번 리플로가 일어나나요?

크기를 읽지 않으면 일어나지 않는다. 브라우저가 쓰기를 모아 두기 때문에 반복문에서 1,000개를 `append`해도 레이아웃은 한 번이었다. 중간에 `offsetHeight`를 읽으면 1,000번이 된다. `DocumentFragment`는 리플로 횟수보다는 준비하고 한 번에 넣는 코드 모양을 강제한다는 점에서 쓸모가 있다.

### innerHTML, textContent, innerText는 언제 쓰나요?

글자만 넣고 뺄 때는 `textContent`를 쓴다. CSS를 보지 않아 빠르고 HTML로 해석하지도 않는다. `innerText`는 보이는 글자만 주지만 레이아웃을 강제한다. `innerHTML`은 문자열을 HTML로 해석하므로 사용자 입력을 넣으면 XSS가 된다.

### head의 스크립트에서 요소가 null로 나오는 이유는 무엇인가요?

파서가 위에서부터 트리를 만들다 스크립트를 만나면 멈추고 실행하는데, 그 시점에는 아래 요소가 아직 트리에 없다. `defer`나 `type="module"`로 파싱이 끝난 뒤 실행하거나, `DOMContentLoaded`를 기다리거나, 스크립트를 `body` 끝으로 옮긴다.
