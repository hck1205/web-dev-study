## 새 글이 몇 주째 색인되지 않는다

블로그에 글을 올린 지 3주가 지났는데 구글에 나오지 않는다. sitemap에도 있고 `noindex`도 없다. Search Console의 페이지 색인 보고서에서는 "발견됨 - 현재 색인이 생성되지 않음"으로 남아 있다. 구글이 주소는 알지만 가져갈 만큼 중요하다고 보지 않는다는 뜻이다(이 상태를 로그와 맞춰 읽는 법은 [접근 로그와 Search Console](/posts/seo-log-file-analysis-search-console)에 있다).

홈에서 그 글까지 직접 눌러 가 보니 이상한 게 보였다. 홈 → 블로그 목록 → "다음" → "다음" → "다음" → "다음" → "다음" → 글. 일곱 번을 눌러야 했다. 목록은 한 쪽에 10개씩 최신순이고, 쪽 사이에는 "다음" 링크 하나만 있었다. 그 글은 날짜가 예전으로 잡혀 6쪽까지 밀려 있었다.

구글봇도 사람처럼 링크를 따라 주소를 찾는다. 링크를 여러 번 건너야 닿는 주소는 늦게 발견되고, 구글이 그 주소를 덜 중요하게 보는 근거가 된다. 이 글은 사이트의 구조를 개발자 손으로 고칠 수 있는 것들, 즉 URL 설계, 클릭 깊이, 내부 링크와 앵커 텍스트, 빵부스러기, 토픽 클러스터를 차례로 본다. 크롤링·색인의 기본과 `canonical`은 [SPA와 SEO](/posts/seo-for-spa)에서 다뤘다.

## URL의 깊이와 클릭 깊이는 다르다

먼저 헷갈리기 쉬운 두 깊이를 나눈다. URL의 깊이는 주소에 슬래시가 몇 개인지다. `/blog/seo/site-architecture`는 세 단계다. 클릭 깊이는 홈에서 링크를 몇 번 눌러야 그 페이지에 닿는지다.

검색 엔진이 신경 쓰는 건 클릭 깊이다. `/posts/p1`처럼 짧은 주소라도 일곱 번 눌러야 닿으면 깊은 페이지이고, `/shop/women/coats/wool/grey-coat`처럼 긴 주소라도 홈의 기획전 배너에서 바로 링크되면 얕은 페이지다. 구글 쪽 담당자들도 여러 번 같은 설명을 해 왔다. 주소의 슬래시 수는 순위 요소가 아니고, 홈에서 가까운 페이지를 더 중요하게 보는 경향이 있다는 것이다.

그렇다고 URL 구조가 아무 의미 없는 건 아니다. 폴더는 사람과 구글 모두에게 사이트의 구역을 알려 준다. 구글 문서도 같은 주제의 페이지를 디렉터리로 묶으면 구역마다 얼마나 자주 크롤할지 판단하는 데 도움이 된다고 설명한다. Search Console에서 `/products/`만 걸러 보거나, 로그에서 구역별 크롤 비중을 세거나, 리다이렉트 규칙을 구역 단위로 거는 일도 폴더가 있으면 쉬워진다.

## 슬러그를 정하는 규칙

슬러그는 주소의 마지막 칸, 사람이 읽는 이름이다. 몇 가지는 정해 두고 지키면 나중에 중복 주소가 생기지 않는다.

소문자로 쓴다. 주소의 경로는 대소문자를 가린다. `/Posts/SEO`와 `/posts/seo`는 서버에 따라 같은 파일을 줄 수도 있지만, 검색 엔진에게는 다른 주소다. 대문자가 섞인 링크가 한 군데만 있어도 같은 페이지의 사본이 생긴다. 서버에서 대문자 주소를 소문자로 301 처리해 두면 실수가 들어와도 하나로 모인다.

단어 사이는 하이픈으로 잇는다. 구글은 밑줄 대신 하이픈을 쓰라고 권한다. 밑줄은 단어를 붙인 것으로 읽힐 수 있다. 공백은 `%20`이 되어 보기 싫고 복사할 때 깨지기 쉽다.

짧고 뜻이 드러나게 쓴다. `the`, `a` 같은 말이나 날짜는 빼도 된다. 날짜를 주소에 넣으면 글을 고쳐 다시 내보낼 때 주소가 거짓말이 된다.

한글 슬러그는 쓸 수 있다. 다만 실제로 오가는 주소는 UTF-8로 퍼센트 인코딩된 문자열이다. Node.js로 바꿔 보면 이렇다.

```js
encodeURIComponent("검색-엔진-최적화");
new URL("https://example.com/posts/검색-엔진").href;
```

```text
%EA%B2%80%EC%83%89-%EC%97%94%EC%A7%84-%EC%B5%9C%EC%A0%81%ED%99%94
https://example.com/posts/%EA%B2%80%EC%83%89-%EC%97%94%EC%A7%84
```

브라우저 주소창과 검색 결과에는 한글로 보이니 읽기는 좋다. 하지만 메신저나 문서에 복사하면 인코딩된 긴 문자열로 붙는 경우가 많고, 로그와 분석 도구에서도 인코딩된 채로 찍힌다. 더 까다로운 함정은 유니코드 정규화다. 같은 "검"도 조합형(NFC)과 분해형(NFD)이 있는데, macOS 파일 이름은 분해형으로 저장되는 경우가 있다. 파일 이름에서 슬러그를 만드는 정적 사이트라면 같은 글자가 전혀 다른 바이트가 된다.

```js
encodeURIComponent("검");                  // NFC
encodeURIComponent("검".normalize("NFD")); // NFD
```

```text
%EA%B2%80
%E1%84%80%E1%85%A5%E1%86%B7
```

눈에는 똑같은데 주소는 다르다. 한쪽으로 링크하고 다른 쪽으로 파일이 만들어지면 404가 나거나 사본이 생긴다. 한글 슬러그를 쓰기로 했다면 슬러그를 만들 때 `normalize("NFC")`를 꼭 거친다. 이 블로그처럼 영문 kebab-case 슬러그로 정하는 것도 흔한 선택이다.

주소를 바꾸는 건 비싸다. 슬러그를 다듬고 싶어졌다면 옛 주소에서 새 주소로 301을 걸고 내부 링크와 sitemap까지 새 주소로 바꿔야 한다. 그 과정과 실수는 [리다이렉트와 사이트 이전](/posts/seo-redirects-site-migration)에 정리했다.

## 홈에서 몇 번 눌러야 닿나

실제로 정적 HTML 67개짜리 사이트를 만들어 `python3 -m http.server`로 띄우고, 홈에서 `a href`만 따라가는 작은 크롤러를 돌렸다.

```js
// crawl.mjs: 홈에서 출발해 a href만 따라가며 클릭 깊이를 잰다 (같은 호스트만)
const origin = process.argv[2];
const depth = new Map([["/", 0]]);
const queue = ["/"];
while (queue.length) {
  const path = queue.shift();
  const html = await (await fetch(origin + path)).text();
  for (const [, href] of html.matchAll(/<a\s[^>]*href="([^"#]+)"/g)) {
    const url = new URL(href, origin + path);
    if (url.origin !== origin || depth.has(url.pathname)) continue;
    depth.set(url.pathname, depth.get(path) + 1);
    queue.push(url.pathname);
  }
}
```

```bash
# 실험용 정적 사이트를 띄우고 크롤러를 돌린다
cd site && python3 -m http.server 4317 &
node crawl.mjs http://localhost:4317
```


깊이 분포가 2부터 7까지 10개씩 고르게 퍼졌다. 글이 늘면 꼬리는 계속 길어진다. 글이 600개면 가장 오래된 글은 깊이 61이다. 실제 사이트에서는 Screaming Frog 같은 크롤러의 "Crawl Depth" 보고서가 같은 숫자를 보여 준다.

마지막 두 줄은 다음 섹션에서 본다.

## 링크가 하나도 없는 페이지

크롤 결과의 마지막 두 줄로 돌아가자. `/about.html`과 `/posts/p61.html`은 크롤러가 찾지 못했다.

`p61`은 sitemap에만 있고 어느 페이지도 링크하지 않는 고아 페이지다. 캠페인용으로 만든 페이지, 목록 정렬 버그로 빠진 글, 분류를 개편하면서 끊긴 페이지가 흔히 이렇게 된다. 구글은 sitemap으로 주소를 알 수는 있지만, 사이트 안에서 아무도 가리키지 않는 페이지를 중요하다고 볼 이유가 없다. 고아 페이지는 크롤러 결과와 sitemap, Search Console, 접근 로그를 맞대서 "크롤러는 못 찾았는데 다른 목록에는 있는 주소"로 찾는다.

`/about.html`은 링크가 있는데도 못 찾았다. 홈의 그 링크가 이렇게 생겼기 때문이다.

```html
<span onclick="location.href='/about.html'">소개</span>
```

구글은 `href` 속성이 있는 `<a>` 요소만 링크로 따라간다고 문서에 못 박아 두었다. 클릭 핸들러로 이동하는 `span`, `button`, `href` 없는 `a`, `href="javascript:void(0)"`은 사람에게는 링크지만 크롤러에게는 그냥 글자다. 렌더링 뒤의 DOM을 보더라도 결과는 같다. 구글봇은 버튼을 누르지 않는다.

React에서는 이런 코드가 같은 문제를 만든다.

```tsx
// 크롤러가 따라가지 못한다: 렌더링 결과에 href가 없다
<div onClick={() => router.push(`/posts/${post.slug}`)}>{post.title}</div>

// 따라간다: Next.js Link는 a href를 렌더링한다
<Link href={`/posts/${post.slug}`}>{post.title}</Link>
```

카드 전체를 누를 수 있게 하고 싶어서 `div`에 `onClick`을 거는 경우가 많다. 그럴 때는 제목을 `<a href>`로 두고 그 링크의 클릭 영역을 카드 전체로 넓히는 편이 크롤러와 접근성 모두에 맞다. 클라이언트 라우팅에서 링크가 어떻게 동작하는지는 [클라이언트 라우팅](/posts/react-client-routing)에 있다. `#` 뒤만 바뀌는 해시 링크도 주소가 같은 것으로 취급되니 별도 페이지로 발견되지 않는다.

## 목록을 고치면 깊이가 줄어든다

깊이 7을 줄이는 방법은 여러 가지다. 같은 글 60개로 세 가지 구조를 만들어 위의 BFS 함수로 쟀다. 줄마다 구조 이름, 깊이별 글 수, 가장 오래된 글(p1)의 깊이, 가장 깊은 글의 깊이다.

```text
next {"2":10,"3":10,"4":10,"5":10,"6":10,"7":10} p1 depth 7 max 7
numbers {"2":10,"3":50} p1 depth 3 max 3
hub {"2":60} p1 depth 2 max 2
```

`next`는 처음 구조다. `numbers`는 목록마다 1쪽부터 6쪽까지 번호 링크를 모두 둔 것이다. 1쪽에서 모든 쪽이 한 번에 닿으니 어느 글이든 깊이 3 안에 들어온다. 쪽이 수백 개라면 전부 걸 수는 없으니 "1, 2, 3 … 10, 20, 50, 100"처럼 건너뛰는 번호를 섞는다. `hub`는 홈에 주제 페이지 6개를 걸고 주제마다 글 10개를 모두 나열한 것이다. 모든 글이 깊이 2가 된다.

숫자보다 중요한 건 방향이다. 글이 늘어도 깊이가 함께 늘지 않는 구조를 고른다. 날짜순 목록 하나에만 기대면 오래된 글은 계속 밀려나고, 주제별 허브와 글끼리의 링크가 있으면 오래된 글도 몇 번 안에 닿는다.

페이지네이션에서 흔한 오해도 하나 짚는다. 예전에는 `rel="prev"`, `rel="next"`로 쪽 사이 관계를 알렸지만, 구글은 2019년에 이 신호를 오래전부터 쓰지 않았다고 밝혔다. 각 쪽이 크롤 가능한 별도 주소(`?page=2`)를 갖고 `a href`로 이어져 있으면 된다. 2쪽 이후의 `canonical`을 1쪽으로 몰면 그 쪽에만 있는 글로 가는 길을 구글이 무시할 수 있으니 각 쪽은 자기 자신을 가리킨다. 무한 스크롤도 같다. 스크롤로 불러오는 내용마다 `?page=N` 주소와 링크가 있어야 크롤러가 끝까지 닿는다.

## 모바일 화면에 없는 링크

구글은 모바일 우선 색인을 쓴다. 스마트폰 구글봇이 본 페이지가 색인의 기준이라는 뜻이다. 그래서 데스크톱에만 있는 링크는 구조에서 빠진 것과 비슷하게 된다.

흔한 경우가 메뉴다. 데스크톱에서는 분류 메뉴를 다 펼쳐 보여 주고, 모바일에서는 햄버거 버튼을 눌렀을 때 API로 메뉴를 불러와 그린다. 스마트폰 구글봇은 버튼을 누르지 않으니 모바일 HTML에는 분류 링크가 하나도 없다. 데스크톱 사이드바의 "인기 글", "관련 글"을 모바일에서 아예 렌더링하지 않는 것도 같다.

```tsx
// 모바일에서 링크가 사라진다: 화면 폭을 보고 아예 그리지 않는다
{isDesktop && <CategoryMenu />}

// 링크는 남는다: 마크업은 늘 있고 CSS로 접었다 편다
<nav className="category-menu" data-open={open}>
  <CategoryLinks />
</nav>
```

접힌 메뉴, 탭 안의 내용, 아코디언처럼 CSS로 감춘 링크는 HTML에 있으니 크롤러가 따라간다. 문제는 "그리지 않은" 링크다. 반응형 화면을 만들 때 모바일에서 무언가를 빼기로 했다면 그 안에 다른 길이 없는 링크가 있는지 같이 확인한다.

## 앵커 텍스트는 링크된 페이지의 설명이다

링크의 글자, 즉 앵커 텍스트는 구글이 링크된 페이지가 무엇에 관한 것인지 짐작하는 단서다. "여기", "자세히 보기", "더보기"만 가득하면 그 단서가 없다. 사람도 마찬가지다. 스크린 리더 사용자는 링크만 모아 듣는 경우가 많은데 "더보기"가 열 번 나오면 어디로 가는지 모른다.

```html
<!-- 무엇으로 가는지 모른다 -->
<a href="/posts/crawl-budget">여기</a>를 보면 자세히 나온다.

<!-- 링크된 페이지를 설명한다 -->
필터 주소가 크롤을 먹는 문제는 <a href="/posts/crawl-budget">크롤 예산 글</a>에 정리했다.
```

반대 방향의 실수도 있다. 모든 내부 링크를 "강남 피부과 추천" 같은 똑같은 검색어로 맞추는 것이다. 외부 링크에서 같은 앵커를 대량으로 맞추면 링크 조작으로 보일 수 있고, 내부 링크라도 문장에 어색하게 박힌 키워드는 사람에게 읽기 나쁘다. 링크된 페이지 제목이나 그 페이지가 답하는 질문을 자연스러운 문장 안에 넣으면 충분하다.

이미지 링크라면 `alt`가 앵커 텍스트 역할을 한다. 로고 이미지에 `alt="홈"` 정도는 적어 둔다.

내부 링크에 `rel="nofollow"`를 붙여 중요한 페이지로 신호를 몰아주려는 시도도 아직 보인다. 이른바 PageRank 조각하기다. 구글은 2009년 무렵부터 nofollow 링크도 신호를 나눠 가지는 몫으로 셈한다고 설명해 왔다. 그러니 신호가 다른 링크로 옮겨 가지 않고 그냥 사라진다. 로그인, 장바구니처럼 색인할 필요가 없는 페이지는 링크에 nofollow를 다는 대신 그 페이지에 `noindex`를 주거나 그냥 둔다. 링크가 신호를 나르는 원리는 [검색 순위와 PageRank](/posts/search-engine-ranking-pagerank)에서 다룬다.

## 빵부스러기는 위치를 알려 주는 링크 줄이다

빵부스러기(breadcrumb)는 "홈 › 여성 › 코트 › 회색 울 코트"처럼 지금 페이지의 위치를 위 단계부터 보여 주는 링크 줄이다. 구조 면에서 하는 일이 둘 있다.

하나는 위쪽으로 가는 내부 링크다. 상세 페이지마다 분류와 구역으로 가는 링크가 생기니 분류 페이지가 많은 링크를 받는다. 다른 하나는 구조를 구조화 데이터로 알려 주는 것이다. `BreadcrumbList`를 넣으면 구글이 경로를 이해하는 데 쓰고, 데스크톱 검색 결과에서는 주소 대신 그 경로가 표시되기도 한다. 2025년 초에 구글은 모바일 검색 결과에서 이 경로 표시를 빼고 도메인만 보이게 바꿨다고 밝혔다. 그래도 화면 안의 링크 줄은 여전히 쓸모가 있다. 마크업 방법은 [구조화 데이터와 JSON-LD](/posts/structured-data-json-ld)에 있다.

```tsx
// 화면의 링크 줄. nav와 aria-label로 이 줄이 무엇인지 알린다
<nav aria-label="현재 위치">
  <ol>
    <li><a href="/">홈</a></li>
    <li><a href="/women">여성</a></li>
    <li><a href="/women/coats">코트</a></li>
    <li aria-current="page">회색 울 코트</li>
  </ol>
</nav>
```

상품이 여러 분류에 속하면 빵부스러기도 여러 개가 될 수 있다. 화면에는 하나만 보여 주는 게 보통이고, 대표 분류를 데이터에 정해 둔다. 사용자가 들어온 경로마다 빵부스러기를 바꾸면 같은 페이지의 링크 구조가 요청마다 달라져 구조를 읽기 어려워진다.

## 허브와 토픽 클러스터

글이 수십 개를 넘으면 날짜순 목록만으로는 구조가 안 보인다. 그래서 주제를 단위로 묶는다. 한 주제를 넓게 소개하는 허브 페이지(필러 페이지라고도 한다)를 두고, 그 주제의 세부 글들이 허브와 서로 링크한다. 이 묶음을 토픽 클러스터라고 부른다.

점선은 옆 글끼리의 링크다. 본문에서 자연스럽게 이어지는 곳에만 건다. 모든 글 아래에 같은 주제 글 스무 개를 기계적으로 붙이면 링크가 너무 많아져 어떤 게 중요한지 흐려진다. 예전에는 "한 페이지에 링크 100개 이하"라는 구글 가이드라인이 있었지만 지금은 숫자 기준을 두지 않는다. 다만 메가 메뉴와 푸터에 링크 수백 개가 모든 페이지에 똑같이 박혀 있으면, 그 링크들은 페이지마다 같아서 어느 페이지가 중요한지 알려 주는 게 거의 없다.

허브는 목록 페이지와 다르다. 제목과 링크만 늘어놓은 페이지는 빈약한 페이지로 보일 수 있다. 주제를 처음 보는 사람이 무엇부터 읽으면 되는지, 세부 글이 각각 어떤 질문에 답하는지를 문장으로 적는다. 이 블로그의 토픽 페이지와 로드맵이 그런 역할을 한다.

쇼핑몰이라면 분류 페이지가 허브다. 분류 페이지에 상품 목록만 있는 게 아니라 하위 분류 링크와 짧은 설명이 있으면 같은 역할을 한다. 필터 조합 페이지를 허브처럼 쓰고 싶은 유혹이 들 때가 있는데, 대부분은 색인할 가치가 없는 주소를 늘리는 결과가 된다. 어느 조합을 색인 대상으로 올릴지는 [크롤 예산과 패싯 내비게이션](/posts/crawl-budget-faceted-navigation)에서 다룬다.

## 사이트링크는 고를 수 없다

브랜드 이름으로 검색하면 첫 결과 아래에 "로그인", "요금제", "고객센터" 같은 하위 링크가 붙는 경우가 있다. 사이트링크다. 이건 구글이 자동으로 만들고 사이트 운영자가 직접 지정할 수 없다. Search Console에 있던 사이트링크 강등 기능도 2016년에 없어졌다.

구글이 밝힌 건 사이트 구조가 사이트링크를 만드는 데 쓰인다는 정도다. 그러니 할 수 있는 건 앞에서 본 것들이다. 중요한 구역을 홈과 메뉴에서 직접 링크하고, 내부 링크의 앵커 텍스트와 페이지 `title`을 짧고 분명하게 쓴다. 사이트링크에 나오면 안 되는 페이지(예전 이벤트, 내부용 페이지)가 뜬다면 그 페이지를 정리하거나 `noindex`를 준다.

## 링크 구조를 코드로 지킨다

구조는 한 번 고쳐 놓아도 기능이 붙으면서 다시 무너진다. 새 목록 화면이 `onClick` 카드로 만들어지고, 분류 개편으로 어떤 글이 어느 허브에도 안 걸린다. 사람이 매번 크롤러를 돌리기는 어려우니 배포 파이프라인에 넣는다.

가장 단순한 형태는 앞의 크롤러를 미리보기 배포에 돌려 두 가지를 검사하는 것이다. sitemap의 모든 주소가 크롤 결과에 있는지(고아 페이지 없음), 그리고 정해 둔 깊이 안에 있는지다.

```js
// check-depth.mjs: 미리보기 배포를 크롤한 결과(depth Map)와 sitemap 주소를 비교한다
const MAX_DEPTH = 4;
const missing = sitemapPaths.filter((p) => !depth.has(p));
const tooDeep = sitemapPaths.filter((p) => depth.get(p) > MAX_DEPTH);

if (missing.length || tooDeep.length) {
  console.error("고아 페이지:", missing);
  console.error(`깊이 ${MAX_DEPTH} 초과:`, tooDeep);
  process.exit(1);
}
```

정적 사이트라면 크롤 없이 빌드 단계에서 같은 검사를 할 수도 있다. 글 목록, 허브 목록, 본문의 링크를 한 데이터에서 만들면 "어느 허브에도 속하지 않은 글"을 빌드 때 바로 찾을 수 있다. 이 블로그도 글마다 토픽 하나와 로드맵 자리 하나를 정하게 하고, 빠진 글이 있으면 빌드를 멈춘다. 같은 원리로 허브 페이지는 데이터에서 자동으로 만든다.

```tsx
// app/topics/[topic]/page.tsx: 허브는 글 데이터에서 만든다. 손으로 목록을 고치지 않는다
export default async function TopicPage({ params }: { params: Promise<{ topic: string }> }) {
  const { topic } = await params;
  const posts = getPostsByTopic(topic); // 같은 레지스트리에서 sitemap도 만든다
  return (
    <ul>
      {posts.map((post) => (
        <li key={post.slug}>
          <Link href={`/posts/${post.slug}`}>{post.title}</Link>
          <p>{post.summary}</p>
        </li>
      ))}
    </ul>
  );
}
```

sitemap, 허브, 목록이 같은 데이터에서 나오면 "sitemap에는 있는데 링크가 없다"는 상황 자체가 잘 생기지 않는다. 손으로 관리하는 메뉴와 자동으로 만든 sitemap이 따로 놀 때 고아 페이지가 생긴다.

관련 글 목록도 같은 데이터로 만든다. 태그가 겹치는 글, 같은 토픽의 앞뒤 글을 자동으로 고르면 손이 덜 가지만 품질은 확인한다. 태그 하나만 겹치는 글을 기계적으로 걸면 앵커 텍스트는 좋아도 독자가 실제로 이어 읽을 링크가 아니다. 본문 안 링크는 사람이 고르고, 글 아래 목록은 데이터로 채우는 식으로 나눠 두면 둘의 장점을 함께 얻는다.

마지막으로, 링크가 첫 HTML에 있는지도 본다. 구글은 렌더링한 DOM의 링크도 따라가지만, 렌더링은 나중에 일어나고 다른 크롤러는 렌더링하지 않는다. 관련 글이나 허브 목록을 클라이언트에서 API로 불러와 그리면 첫 HTML에는 링크가 없다. `curl -s 주소 | grep -o 'href="/posts/[^"]*"' | wc -l` 한 줄로 첫 HTML에 글 링크가 몇 개 있는지 바로 알 수 있다.

## 구조를 고칠 때 순서

구조 개편은 한 번에 크게 하면 무엇이 효과였는지 알 수 없다. 이렇게 나눠서 한다.

1. 지금 상태를 잰다. 크롤러로 클릭 깊이 분포와 들어오는 내부 링크 수를 뽑고, sitemap·로그·Search Console과 맞대 고아 페이지를 찾는다.
2. 링크를 `a href`로 바꾼다. `onClick` 이동, `href` 없는 링크, 해시 링크를 찾아 고친다. 렌더링 전 HTML에도 링크가 있으면 더 좋다.
3. 목록과 허브를 고친다. 번호 페이지네이션, 주제 허브, 분류 페이지 설명, 빵부스러기.
4. 본문 링크를 손본다. 앵커 텍스트를 설명형으로, 관련 글끼리 자연스럽게.
5. 주소 자체를 바꾸는 건 마지막에, 꼭 필요할 때만 301과 함께 한다.
6. 몇 주 뒤 다시 잰다. 깊이 분포, 로그의 구역별 크롤 비중, 페이지 색인 보고서의 발견됨 수가 함께 움직이는지 본다.

## 처음 그 글은 깊이 7이었다

글이 색인되지 않은 이유는 내용이 아니라 길이었다. 날짜순 목록의 "다음" 링크만 따라가야 닿는 구조라 글이 오래될수록 깊어졌다. 클릭 깊이는 URL의 슬래시 수가 아니라 홈에서 누르는 횟수이고, 크롤러는 `a href`만 따라간다. 번호 페이지네이션과 주제 허브로 깊이를 낮추고, 링크 글자에는 그 페이지가 무엇인지 적고, 빵부스러기로 위 단계를 잇는다. 고친 뒤에는 다시 크롤해서 깊이 분포가 줄었는지 숫자로 확인한다.

## 면접에서 나올 만한 질문

### 클릭 깊이와 URL 깊이는 어떻게 다른가요?

URL 깊이는 주소의 슬래시 수이고, 클릭 깊이는 홈에서 링크를 몇 번 눌러야 닿는지다. 검색 엔진이 중요도를 짐작할 때 신경 쓰는 건 클릭 깊이다. 짧은 주소도 링크로 멀면 깊은 페이지이고, 긴 주소도 홈에서 바로 링크되면 얕다. 폴더 구조는 구역을 알리고 관리하기 쉽게 만드는 용도다.

### 클릭 깊이는 어떻게 재나요?

홈에서 출발해 `a href`를 따라가는 너비 우선 탐색으로 잰다. BFS는 가까운 페이지부터 넓혀 가니 처음 닿은 깊이가 최소 클릭 수가 된다. 실무에서는 Screaming Frog 같은 크롤러의 깊이 보고서를 쓰고, 그 결과를 sitemap, 로그와 맞대 고아 페이지와 깊은 페이지를 찾는다.

### 자바스크립트 onClick으로 이동하는 링크는 왜 문제인가요?

구글은 `href`가 있는 `<a>` 요소만 링크로 따라간다. `div`나 `button`에 클릭 핸들러로 이동을 걸면 렌더링한 DOM에도 주소가 없어서 크롤러가 그 페이지를 발견하지 못한다. 구글봇은 클릭하지 않는다. Next.js의 `Link`처럼 `a href`를 렌더링하는 컴포넌트를 쓰고, 카드 전체 클릭은 링크의 클릭 영역을 넓혀서 만든다.

### 고아 페이지는 무엇이고 어떻게 찾나요?

사이트 안의 어떤 페이지도 링크하지 않는 페이지다. sitemap으로 주소는 알려질 수 있지만 내부 링크가 없으니 중요하지 않은 페이지로 보이고 크롤도 드물다. 크롤러가 찾은 주소 목록과 sitemap, Search Console, 접근 로그의 주소 목록을 비교해서 크롤러만 못 찾은 주소를 뽑는다.

### 글이 늘어날 때 페이지네이션은 어떻게 설계하나요?

"다음" 링크만 있으면 쪽 수만큼 깊이가 늘어난다. 번호 링크를 두고 쪽이 많으면 건너뛰는 번호를 섞어 깊이를 묶어 두고, 주제 허브나 분류 페이지로 다른 길을 만든다. 각 쪽은 크롤 가능한 별도 주소를 갖고 자기 자신을 `canonical`로 둔다. 구글은 `rel=prev/next`를 쓰지 않으니 그것에 기대지 않는다.

### 내부 링크에 nofollow를 달아 중요한 페이지에 신호를 몰 수 있나요?

안 된다. nofollow 링크도 신호를 나눠 가지는 몫으로 셈해지고 그 몫은 다른 링크로 옮겨 가지 않고 사라진다는 게 구글의 설명이다. 색인할 필요가 없는 페이지는 그 페이지에 `noindex`를 주고, 중요한 페이지는 허브와 본문에서 링크를 더 받게 구조를 바꾼다.

### 한글 슬러그를 쓸 때 주의할 점은요?

실제 주소는 UTF-8로 퍼센트 인코딩되어 오가니 복사나 로그에서는 긴 문자열로 보인다. 더 큰 함정은 유니코드 정규화로, 같은 글자도 NFC와 NFD의 바이트가 달라 다른 주소가 된다. 슬러그를 만들 때 NFC로 정규화하고, 대소문자·공백 규칙을 정해 한 페이지에 한 주소만 생기게 한다.

### 사이트링크를 원하는 대로 바꿀 수 있나요?

직접 지정할 수 없다. 구글이 사이트 구조를 보고 자동으로 만들고, Search Console의 강등 기능도 2016년에 없어졌다. 중요한 구역을 홈과 메뉴에서 직접 링크하고 `title`과 앵커 텍스트를 분명하게 쓰는 게 할 수 있는 일이고, 나오면 안 되는 페이지는 정리하거나 `noindex`를 준다.
