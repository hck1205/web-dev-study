상품 상세 API(`GET /products/1001`)에 Redis 캐시를 붙였다고 하자. DB에서 상품과 옵션, 리뷰 요약을 모아 오는 데 30ms가 걸리던 응답이 1ms 안쪽으로 줄고, DB 읽기 부하는 몇 분의 일로 떨어진다. 여기까지는 쉽다.

그다음에 문제가 생긴다. 운영자가 1001번 무선 이어폰의 가격을 39,000원에서 35,000원으로 내렸는데, 어떤 사용자에게는 몇 분 동안 옛 가격이 보인다. 매일 자정에 배치로 캐시를 한꺼번에 채웠더니, 그 캐시들이 같은 시각에 만료되면서 DB CPU가 튄다. 누군가 없는 상품 번호를 초당 수천 번 요청하자 캐시는 아무 일도 못 하고 요청이 전부 DB로 간다.

셋 다 캐시를 "넣는" 문제가 아니라 "언제 채우고 언제 지우나"의 문제다. 이 글은 그 결정을 패턴별로 정리한다. 예제는 처음부터 끝까지 상품 1001번과 그 캐시 키 `cache:product:1001`을 쓴다. Redis 자체가 처음이라면 [Redis 기본 글](/posts/redis-basics)을 먼저 보면 좋다.

## 캐시를 먼저 보고 없으면 DB에서: cache-aside

가장 흔한 패턴이다. 응용 코드가 캐시와 DB 사이에서 직접 일한다. 읽을 때는 캐시를 먼저 보고, 없으면(미스) DB에서 읽어 캐시에 넣은 뒤 돌려준다. 필요한 순간에 채운다고 해서 lazy loading이라고도 한다. 쓸 때는 DB를 고치고 캐시 키를 지운다.

코드로 쓰면 이렇다. Node.js의 `redis` 패키지(v4 이상) 기준이고, `db.query`는 쓰는 DB 드라이버로 바꿔 읽으면 된다.

```js
import { createClient } from "redis";

const redis = createClient({ url: process.env.REDIS_URL });
await redis.connect();

const TTL_SECONDS = 300;

async function getProduct(id) {
  const key = `cache:product:${id}`;

  const cached = await redis.get(key);          // 1) 캐시를 본다. 없으면 null
  if (cached !== null) return JSON.parse(cached); //    히트면 여기서 끝

  const product = await db.query(                // 2) 미스면 DB에서 읽는다
    "SELECT id, name, price FROM products WHERE id = $1", [id]);

  if (product) {                                 // 3) 읽은 값을 TTL과 함께 넣는다
    await redis.set(key, JSON.stringify(product), { EX: TTL_SECONDS });
  }
  return product;
}

async function updatePrice(id, price) {
  await db.query("UPDATE products SET price = $1 WHERE id = $2", [price, id]); // DB 먼저
  await redis.del(`cache:product:${id}`);                                      // 그다음 삭제
}
```

cache-aside의 좋은 점은 실제로 요청된 데이터만 캐시에 들어간다는 것과, Redis가 죽어도 DB로 읽으면 서비스는 돈다는 것이다. 단, 두 번째 장점을 살리려면 Redis 호출에 짧은 타임아웃(수십 ms)을 걸고, 실패하면 캐시를 건너뛰게 짜야 한다. 타임아웃 없이 Redis를 기다리면 캐시가 장애의 원인이 된다. 이 부분은 [장애 대응 패턴 글](/posts/resilience-patterns)의 타임아웃 이야기와 같다.

약점은 첫 요청이 늘 느리다는 것(콜드 스타트), 캐시를 지우기 전까지는 옛 값이 보일 수 있다는 것, 그리고 이 로직이 응용 코드 곳곳에 퍼진다는 것이다.

## 캐시가 대신 읽어 오는 read-through

read-through는 데이터 흐름은 cache-aside와 같은데, DB에서 읽어 채우는 일을 캐시 층이 맡는다. 응용 코드는 `cache.get(key)`만 부르고, 캐시에 없으면 캐시가 미리 등록된 로더(loader) 함수로 DB를 읽어 채운 뒤 돌려준다. 자바의 Caffeine `LoadingCache`나 캐시 라이브러리들이 이 방식이다.

Redis 서버 자체는 DB를 읽어 오지 않는다. 그래서 Redis로 read-through를 하려면 응용 쪽에 이런 래퍼를 둔다. 차이는 "누가 미스를 처리하나"뿐이지만 실무에서는 꽤 크다. 로딩 로직이 한곳에 모이니 TTL, 직렬화, 뒤에서 볼 스탬피드 방어를 한 번만 짜면 된다. Caffeine은 같은 키를 동시에 요청하면 로더를 한 번만 부른다.

## 쓰기는 어디로 먼저 보내나

읽기 쪽 이야기를 했으니 쓰기 쪽이다. 쓸 때 캐시와 DB 중 어디에, 어떤 순서로 쓰느냐에 따라 이름이 나뉜다.

write-through는 쓰기를 캐시와 DB 양쪽에 동기로 반영한다. 보통 캐시 층이 DB 쓰기까지 마치고 나서 성공을 돌려준다. 캐시가 늘 최신이라 쓰고 바로 읽어도 히트가 난다. 대신 쓰기마다 두 곳을 거치니 쓰기 지연이 늘고, 한 번도 안 읽힐 데이터까지 캐시에 들어가 메모리를 쓴다. 두 쓰기 중 하나만 성공하는 경우도 처리해야 한다.

write-behind(write-back)는 캐시에만 쓰고 바로 성공을 돌려준 뒤, DB에는 나중에 모아서 쓴다. 상품 조회수가 좋은 예다. 조회마다 DB에 `UPDATE`를 하면 행 하나에 쓰기가 몰리는데, Redis에서 `INCR product:1001:views`로 세고 1분마다 모인 값을 DB에 한 번 쓰면 DB 쓰기가 수천 분의 일로 준다. 대가는 유실이다. DB에 옮기기 전에 Redis가 죽으면 그 사이 쓰기는 사라진다. 그래서 잃어도 되는 숫자(조회수, 좋아요 집계)에 쓰고, 주문이나 결제에는 쓰지 않는다.

write-around는 쓰기를 DB에만 하고 캐시는 건드리지 않는다(또는 지우기만 한다). 캐시는 다음 읽기 때 cache-aside로 채워진다. 위의 `updatePrice`가 이 방식이다. 쓰고 한동안 안 읽히는 데이터(로그, 대량 입력)로 캐시를 채우지 않는다는 장점이 있고, 쓴 직후 첫 읽기는 미스다.

| 방식 | 쓰기 경로 | 잘 맞는 곳 | 조심할 것 |
|---|---|---|---|
| write-through | 캐시와 DB에 동기로 | 쓰고 곧바로 자주 읽는 데이터 | 쓰기 지연, 안 읽힐 데이터도 캐시에 |
| write-behind | 캐시에 쓰고 DB는 나중에 | 조회수처럼 쓰기가 몰리고 잃어도 되는 값 | 캐시 장애 시 유실, 순서 |
| write-around | DB에만, 캐시는 삭제 | 대부분의 일반 CRUD (cache-aside와 짝) | 쓴 직후 첫 읽기는 미스 |

실무에서 가장 많이 보는 조합은 cache-aside 읽기에 write-around(쓰고 나서 삭제)다. 이 글의 나머지도 이 조합을 기준으로 한다.

## TTL은 얼마나 낡아도 되는지로 정한다

쓸 때마다 캐시를 지운다면 TTL이 왜 필요할까. 삭제는 실패할 수 있기 때문이다. Redis가 잠깐 응답을 못 했거나, 코드 경로 하나가 삭제를 빠뜨렸거나, 관리자가 DB를 직접 고쳤을 수 있다. TTL은 그런 경우에 옛 값이 남아 있을 수 있는 최대 시간이다. 그래서 TTL은 "이 데이터가 최악의 경우 얼마나 낡아도 괜찮은가"로 정한다.

- 상품 가격과 재고 표시: 쓸 때 지우고, TTL은 수 분. 결제 단계에서는 캐시가 아니라 DB 값을 다시 확인한다.
- 인기 상품 순위: 지우지 않고 TTL 30~60초에 맡긴다. 1분 늦은 순위는 아무도 모른다.
- 사이트 설정, 카테고리 목록: 잘 안 바뀌니 TTL을 길게(수십 분~수 시간) 두고 바꿀 때 지운다.

TTL을 너무 짧게 잡으면 미스가 늘어 캐시가 하는 일이 줄고, 너무 길게 잡으면 메모리를 오래 차지하고 삭제가 실패했을 때 피해가 길어진다.

여기에 지터(jitter)를 섞는다. 같은 시각에 채운 키들이 같은 TTL을 가지면 같은 시각에 만료된다. 처음 장면의 자정 배치가 그렇다. TTL에 무작위로 ±10% 정도를 더하면 300초짜리 키들이 270~330초 사이에 흩어져 만료된다.

```js
// base 300, ratio 0.1이면 270~330초 사이 정수
function ttlWithJitter(base, ratio = 0.1) {
  const spread = base * ratio;
  return Math.round(base - spread + Math.random() * spread * 2);
}

await redis.set(key, value, { EX: ttlWithJitter(300) });
```

## 고칠 때 캐시를 지울까, 같이 고칠까

가격을 바꿨을 때 캐시에 새 가격을 바로 써 넣으면(`SET`) 다음 읽기가 미스 없이 새 값을 받는다. 그런데 대부분 지우는(`DEL`) 쪽을 고른다. 이유가 몇 가지 있다.

동시에 두 번 고치면 순서가 꼬인다. 요청 A가 가격을 35,000원으로, 요청 B가 33,000원으로 거의 동시에 바꾼다고 하자. DB에는 A, B 순서로 커밋돼 33,000원이 남았는데, 캐시 쓰기는 네트워크 사정으로 B, A 순서로 도착하면 캐시에는 35,000원이 남는다. DB와 캐시가 다른 값을 들고 TTL까지 간다. 지우기는 몇 번을 어떤 순서로 해도 결과가 같다(멱등).

캐시 값이 DB 행 하나와 딱 맞지 않는 경우가 많다. 상품 상세 캐시에는 옵션, 리뷰 요약, 할인율이 함께 들어간다. 가격 하나 바꿀 때 그 JSON 전체를 다시 계산하는 코드를 쓰기 경로마다 넣느니, 지우고 읽기 경로 한곳에서 만들게 하는 편이 단순하다. 안 읽힐 수도 있는 값을 미리 계산하는 낭비도 없다.

지우기의 대가는 쓰기 직후의 미스 한 번이다. 아주 뜨거운 키라면 그 미스가 뒤에서 볼 스탬피드로 이어지니 그때는 따로 대비한다.

키 자체를 바꾸는 방법도 있다. 버전을 키에 넣는 것이다. 캐시하는 JSON 모양을 바꿔 배포할 때 특히 쓸모 있다. 옛 코드와 새 코드가 섞여 도는 배포 중에 같은 키를 쓰면, 새 코드가 옛 모양의 JSON을 읽다가 오류를 낸다. 키에 스키마 버전을 넣어 두면 새 코드는 새 키만 보고, 옛 키는 아무도 안 읽다가 TTL로 사라진다. 아래 키를 조각별로 눌러 보자.

      title: "A가 들고 있던 옛 값을 넣는다",
      detail: "삭제보다 늦게 도착한 쓰기다. 캐시에는 39,000원이 들어간다.",
      payload: "SET cache:product:1001 '{\"price\":39000}' EX 300",
    },
    {
      from: "redis",
      to: "redis",
      label: "300초간 옛 값",
      title: "TTL이 끝날 때까지 틀린 값이 나간다",
      detail: "DB는 35,000원인데 캐시는 39,000원이다. 다음 쓰기나 만료 전까지 아무도 이걸 고치지 않는다.",
    },
  ]}

이 일이 일어나려면 A의 DB 읽기가 B의 커밋보다 먼저 시작하고, A의 캐시 쓰기가 B의 삭제보다 늦게 끝나야 한다. 보통 DB 읽기는 쓰기보다 빨라서 창이 좁지만, 트래픽이 많으면 결국 일어난다. 특히 A가 복제 지연이 있는 읽기 전용 복제본(replica)에서 읽는다면 창이 복제 지연만큼 넓어진다. B가 프라이머리에 커밋하고 캐시를 지운 뒤에도, A는 레플리카에서 몇백 ms 전의 값을 읽어 다시 채울 수 있다.

순서를 반대로(캐시 삭제 먼저, DB 수정 나중) 하면 더 나빠진다. 삭제와 커밋 사이에 들어온 모든 읽기가 미스를 내고 DB의 옛 값을 읽어 채운다. 그래서 순서는 DB 먼저, 삭제 나중이다.

그래도 남는 창은 이렇게 줄인다.

- TTL을 안전망으로 둔다. 틀린 값이 남아도 TTL이 지나면 사라진다. 결국 피해의 상한은 TTL이다.
- 지연 이중 삭제(delayed double delete): 커밋 후 한 번 지우고, 잠시 뒤(복제 지연과 읽기 시간보다 넉넉하게, 예를 들어 500ms~1초) 한 번 더 지운다. 두 번째 삭제가 A가 늦게 넣은 옛 값을 치운다. `setTimeout`으로 하면 그 사이 프로세스가 죽을 때 빠지므로, 지연 큐에 넣어 처리하는 편이 확실하다.
- 캐시를 채우는 읽기는 프라이머리에서 한다. 복제 지연으로 생기는 창이 없어진다. 프라이머리 부하와 맞바꾸는 셈이다.
- 변경 데이터 캡처(CDC): Debezium 같은 도구가 DB의 변경 로그(MySQL binlog, PostgreSQL WAL)를 읽어 커밋된 변경마다 캐시를 지운다. 응용 코드에서 삭제를 빠뜨려도, 관리자가 DB를 직접 고쳐도 지워진다. 운영할 구성 요소가 하나 늘어난다.

삭제 자체가 실패하는 경우도 챙긴다. `redis.del`이 타임아웃 나면 그 키는 TTL까지 옛 값이다. 재시도 큐에 넣거나, DB 트랜잭션과 함께 "지워야 할 키"를 기록하는 아웃박스 테이블을 두고 별도 작업자가 지우게 한다. 어떤 방법을 써도 DB와 캐시를 완전히 동시에 맞출 수는 없다. 캐시를 쓴다는 건 짧은 불일치를 받아들인다는 뜻이고, 결제 금액처럼 그게 안 되는 값은 캐시를 거치지 않고 DB에서 읽는다.

## 만료 순간 같은 키로 몰리는 요청

1001번이 타임세일 상품이라 초당 2,000번 요청된다고 하자. 캐시 키가 만료되는 순간, DB 조회가 끝나 캐시가 다시 채워지기까지 30ms가 걸린다. 그 30ms 동안 들어온 60개 요청이 모두 미스를 보고 똑같은 쿼리를 DB에 보낸다. 조회가 2초 걸리는 무거운 집계라면 4,000개다. DB가 느려지면 채우는 시간이 더 길어지고, 그 사이 미스가 더 쌓인다. 이게 캐시 스탬피드(thundering herd)다. CDN 층에서 같은 일이 생기는 모습과 대책은 [HTTP 캐시와 CDN 글](/posts/http-caching-cdn)에서 다뤘고, 여기서는 응용 서버와 Redis 사이에서 막는 방법을 본다.

첫 번째는 락이다. 미스를 본 요청 중 하나만 DB를 읽게 한다. 아래 그림에서 다음을 누르면 요청 둘이 동시에 미스를 본다.

락에서 조심할 건 두 가지다. 락 만료 시간은 채우는 시간보다 길어야 한다. 짧으면 A가 채우는 도중에 락이 풀려 다른 요청이 또 DB에 간다. 반대로 A가 락을 잡은 채 죽으면 만료될 때까지 아무도 못 채우니 너무 길어도 안 된다. 그리고 기다리는 요청들은 그만큼 응답이 늦어진다. 그래서 값을 지우지 말고 옛 값을 함께 보관해 두는 방법을 섞는다. 값 안에 "논리적 만료 시각"을 넣고, Redis TTL은 그보다 길게 준다. 논리적 만료가 지났으면 락을 잡은 하나만 다시 채우고, 나머지는 기다리지 않고 옛 값을 바로 받는다. HTTP의 `stale-while-revalidate`와 같은 생각이다.

두 번째는 요청 합치기(request coalescing)다. 같은 서버 프로세스 안에서 같은 키를 동시에 읽으려는 요청들이 하나의 Promise를 함께 기다리게 한다. Go의 `singleflight`가 이 방식이다.

```js
const inflight = new Map(); // 키 → 진행 중인 로딩 Promise

function loadOnce(key, loader) {
  if (inflight.has(key)) return inflight.get(key); // 이미 누가 읽는 중이면 그걸 같이 기다린다
  const promise = loader().finally(() => inflight.delete(key));
  inflight.set(key, promise);
  return promise;
}
```

락과 달리 Redis 왕복이 없고 기다리는 요청이 결과를 바로 받는다. 대신 합쳐지는 범위가 프로세스 하나다. 응용 서버가 20대면 DB 조회도 20번이다. 그래서 서버 안에서는 합치고, 서버 사이에서는 락을 거는 식으로 같이 쓴다.

세 번째는 확률적 조기 갱신이다. 만료되기 전에, 요청 중 소수가 확률적으로 미리 다시 채운다. 만료가 가까울수록 확률이 높아진다. 논문에서 XFetch라고 부르는 방식으로, 요청마다 이 조건을 본다.

```js
// delta: 지난번 다시 채우는 데 걸린 시간(초), expiry: 만료 시각(초), beta: 보통 1
const shouldRefresh = now - delta * beta * Math.log(Math.random()) >= expiry;
```

`Math.log(Math.random())`은 0 이하라서 빼면 더해지는 값이 된다. 만료까지 남은 시간이 t초일 때 한 요청이 갱신에 걸릴 확률은 e^(−t/delta)다. 채우는 데 50ms가 걸리는 키라면 만료 0.5초 전에는 요청 하나당 약 0.0045%, 0.2초 전에는 약 1.8%, 0.1초 전에는 약 13.5%다. 초당 2,000번 요청되는 키는 대개 만료 0.2~0.3초 전쯤 요청 하나가 갱신을 시작하고, 나머지는 그동안 기존 값을 받는다. 채우는 시간이 긴 키일수록 더 일찍 갱신이 시작된다. 키마다 `delta`를 값과 함께 저장해야 한다는 번거로움이 있다.

## 키 하나에만 몰리는 트래픽

스탬피드가 "만료 순간"의 문제라면, 핫 키는 평소에도 키 하나에 요청이 몰리는 문제다. 메인 배너, 타임세일 상품, 유명인의 프로필 같은 키다. Redis Cluster로 노드를 열 대 두어도 키 하나는 노드 하나에 있다. 그 노드의 한 스레드와 네트워크 카드가 그 키를 혼자 감당한다.

값 크기도 계산에 넣는다. 100KB짜리 상품 상세 JSON을 초당 1만 번 읽으면 1GB/s, 즉 8Gbps다. 명령 처리보다 네트워크가 먼저 찬다.

찾는 방법은 몇 가지 있다. `redis-cli --hotkeys`는 접근 빈도를 보는데, 축출 정책이 LFU(`allkeys-lfu` 등)일 때만 동작한다. `redis-cli --bigkeys`는 큰 키를 찾는다. 둘 다 `SCAN`으로 돌아서 서버를 멈추지는 않는다. 모든 명령을 실시간으로 찍는 `MONITOR`는 그 자체가 부하라 운영 서버에서는 잠깐만 쓴다. 가장 쓸 만한 건 응용 쪽에서 키 접두사별 호출 수를 지표로 남기는 것이다.

막는 방법은 키를 덜 부르게 하거나 여러 곳으로 나누는 것이다.

- 응용 서버 메모리에 로컬 캐시를 둔다. TTL을 1~5초만 줘도 서버 한 대당 Redis 호출이 초당 1번 이하로 준다. 다음 절에서 자세히 본다.
- 키를 복제한다. `cache:product:1001#0`부터 `#7`까지 같은 값을 여덟 개 두고, 읽을 때는 그중 하나를 무작위로 고른다. Cluster에서는 이름이 다르니 다른 노드로 흩어진다. 지우거나 고칠 때는 여덟 개를 다 처리해야 한다.
- 레플리카에서 읽는다. 읽기를 여러 노드로 나누지만 복제 지연만큼 옛 값이 섞인다.
- 값을 줄인다. 화면에 필요한 필드만 담고, 큰 값은 압축하거나 해시로 쪼개 필요한 필드만 읽는다.

## 없는 데이터를 계속 물어볼 때

cache-aside 코드를 다시 보면 DB에 상품이 없을 때는 캐시에 아무것도 넣지 않는다. 그래서 없는 상품 번호(`/products/99999999`)로 들어오는 요청은 매번 미스이고 매번 DB에 간다. 크롤러나 공격자가 무작위 번호를 초당 수천 번 넣으면 캐시가 있으나 마나다. 이걸 캐시 관통(cache penetration)이라고 한다.

가장 간단한 대책은 "없음"도 캐시하는 것이다(negative caching). 상품이 없으면 빈 표시값을 짧은 TTL로 넣는다.

```js
const NOT_FOUND = "__none__";

const cached = await redis.get(key);
if (cached === NOT_FOUND) return null;          // 없다는 것도 캐시에서 답한다
if (cached !== null) return JSON.parse(cached);

const product = await db.query(/* ... */);
if (product) {
  await redis.set(key, JSON.stringify(product), { EX: ttlWithJitter(300) });
} else {
  await redis.set(key, NOT_FOUND, { EX: 60 });   // 없음은 짧게. 새 상품이 생기면 지운다
}
```

없음의 TTL은 짧게 둔다. 그 번호로 상품이 새로 등록되면 등록할 때 키를 지워 준다. 그런데 공격자가 매번 다른 번호를 넣으면 없음 표시가 번호마다 쌓여 메모리를 먹는다.

그때 쓰는 게 블룸 필터(Bloom filter)다. 비트 배열 하나와 해시 함수 몇 개로 "이 값이 집합에 있는가"를 답하는 구조인데, "없다"는 답은 항상 맞고 "있다"는 답은 가끔 틀린다(거짓 양성). 존재하는 상품 번호를 모두 블룸 필터에 넣어 두고, 필터가 없다고 하면 캐시도 DB도 보지 않고 바로 404를 준다. 거짓 양성 1%를 목표로 하면 원소 하나에 약 9.6비트가 들고 해시 함수는 7개 정도면 된다. 상품 1억 개라도 약 120MB다. 기본 블룸 필터는 원소를 지울 수 없어서, 삭제가 잦으면 주기적으로 다시 만들거나 카운팅 블룸 필터, 쿠쿠 필터를 쓴다. Redis에서는 RedisBloom 모듈의 `BF.ADD`, `BF.EXISTS`로 쓸 수 있다(Redis Stack에 들어 있고 Redis 8에는 기본 포함, Ubuntu 24.04의 7.0 패키지에는 없다).

그리고 애초에 말이 안 되는 입력(음수, 범위를 벗어난 번호)은 캐시 앞에서 걸러 내고, 같은 IP의 요청 수를 제한한다.

## 여러 키가 한꺼번에 만료될 때

스탬피드가 키 하나에 요청이 몰리는 문제라면, 캐시 눈사태(cache avalanche)는 많은 키가 동시에 사라지는 문제다. 처음 장면의 자정 배치처럼 같은 시각에 같은 TTL로 채운 키들이 한꺼번에 만료되거나, Redis가 재시작돼서 캐시가 통째로 비었을 때 생긴다. 평소 히트율 95%로 DB가 5%만 받다가 갑자기 100%를 받으면 DB 부하가 스무 배가 된다.

- TTL에 지터를 섞는다. 앞에서 본 `ttlWithJitter`다.
- 캐시를 미리 채울 때는 한꺼번에 하지 않고 속도를 제한해 나눠 채운다. 새 Redis로 옮길 때는 트래픽을 넘기기 전에 인기 키부터 채워 둔다.
- Redis가 통째로 비지 않게 한다. 레플리카와 자동 장애 조치(Sentinel, Cluster)를 두고, 재시작해도 데이터가 남게 RDB나 AOF를 켠다. 이건 [영속성과 고가용성 글](/posts/redis-persistence-ha)에서 다룬다.
- 그래도 비었을 때 DB가 쓰러지지 않게 한다. DB로 가는 동시 요청 수를 제한하고(벌크헤드), 넘치면 기본값이나 옛 값을 주거나 빠르게 실패한다. [장애 대응 패턴 글](/posts/resilience-patterns)의 서킷 브레이커와 폴백이 여기서 쓰인다.

"캐시가 이상하니 한 번 비우자"며 운영 Redis에 `FLUSHALL`을 치면, 그 순간부터 모든 요청이 DB로 간다. 캐시를 믿고 줄여 둔 DB라면 그대로 쓰러진다. 문제 있는 키만 `SCAN`과 `UNLINK`로 지우거나, 키 버전을 올려 새 키로 천천히 넘어간다.
</Callout>

## 로컬 캐시와 Redis를 겹쳐 쓰기

Redis도 결국 네트워크 너머에 있다. 왕복이 0.3ms라도 요청 하나에 캐시 조회가 스무 번이면 6ms다. 그래서 응용 서버 프로세스 메모리에 작은 캐시(로컬 캐시, in-process cache)를 하나 더 둔다. 자바라면 Caffeine, Node.js라면 `lru-cache` 같은 라이브러리다. 네트워크가 없으니 조회가 µs 아래로 끝난다.

대책은 이렇다. 로컬 캐시 TTL을 아주 짧게(수 초) 둬서 불일치를 그 시간 안에 가둔다. 값을 바꿀 때 Redis Pub/Sub으로 "1001번을 지워라"를 모든 서버에 알린다. Pub/Sub은 끊겨 있던 서버가 메시지를 놓치므로, 짧은 TTL을 안전망으로 같이 둔다. Redis 6부터는 서버가 도와주는 클라이언트 쪽 캐시(`CLIENT TRACKING`)도 있다. 클라이언트가 읽은 키를 Redis가 기억해 두었다가, 그 키가 바뀌면 무효화 메시지를 보내 준다. 클라이언트 라이브러리가 지원해야 쓸 수 있다.

어느 층에 무엇을 둘지는 데이터 성격으로 정한다. 카테고리 목록이나 설정처럼 거의 안 바뀌고 모두에게 같은 값은 로컬 캐시에 잘 맞는다. 사용자가 방금 고친 자기 프로필처럼 고친 직후 바로 보여야 하는 값은 로컬 캐시에 두지 않는다. 로컬 캐시는 서버 메모리를 쓰고(자바라면 힙과 GC 부담), 서버가 새로 뜰 때마다 비어 있다는 것도 계산에 넣는다.

## LRU 캐시를 직접 짜 보기

로컬 캐시는 메모리가 한정돼 있어서, 꽉 차면 무언가를 내보내야 한다. 가장 흔한 기준이 LRU(Least Recently Used), 가장 오래 안 쓴 것부터 내보내기다. 자바스크립트의 `Map`은 넣은 순서를 기억하므로, 읽을 때마다 지웠다가 다시 넣으면 맨 뒤가 가장 최근, 맨 앞이 가장 오래 안 쓴 키가 된다.

아래 함수는 용량 `capacity`인 LRU에 `ops`를 차례로 적용하고, `get` 결과만 순서대로 돌려준다. 없으면 `null`이다. `put`으로 이미 있는 키를 고쳐도 최근에 쓴 것으로 친다.

  solution={`function runLru(capacity, ops) {
  const cache = new Map();
  const out = [];
  for (const [op, key, value] of ops) {
    if (op === "get") {
      if (!cache.has(key)) {
        out.push(null);
        continue;
      }
      const v = cache.get(key);
      cache.delete(key); // 지웠다가
      cache.set(key, v); // 다시 넣으면 맨 뒤(가장 최근)로 간다
      out.push(v);
    } else {
      if (cache.has(key)) cache.delete(key);
      cache.set(key, value);
      if (cache.size > capacity) {
        const oldest = cache.keys().next().value; // 맨 앞이 가장 오래 안 쓴 키
        cache.delete(oldest);
      }
    }
  }
  return out;
}`}

`Map`의 `delete`와 `set`, 첫 키 꺼내기는 모두 상수 시간이라 `get`과 `put`이 O(1)이다. 언어에 순서를 기억하는 맵이 없다면 해시맵과 이중 연결 리스트를 함께 써서 같은 일을 한다. 면접에서 LRU를 짜 보라고 하면 보통 이 구조를 묻는 것이다. 실제 라이브러리는 여기에 항목별 TTL과 크기 기준 상한을 더한다. Redis가 메모리가 찼을 때 쓰는 LRU는 이렇게 정확한 순서를 유지하지 않고 표본을 뽑아 근사하는데, 그 이야기는 [메모리와 축출 정책 글](/posts/redis-memory-eviction)에서 다룬다.

## 캐시가 일하는지 숫자로 본다

캐시를 넣었으면 제 몫을 하는지 숫자로 확인한다. 가장 먼저 보는 건 히트율이다. Redis가 서버 전체 기준으로 세어 둔 값이 있다.

```bash
# 키를 찾은 횟수, 못 찾은 횟수, 만료로 지운 수, 메모리가 차서 쫓아낸 수
redis-cli INFO stats | grep -E '^(keyspace_hits|keyspace_misses|expired_keys|evicted_keys)'
```

```text
expired_keys:0
evicted_keys:0
keyspace_hits:9412
keyspace_misses:588
```

히트율은 hits ÷ (hits + misses)라서 9412 ÷ 10000 = 94.12%다. 이 숫자를 읽을 때 조심할 게 있다. 이 값은 서버가 시작된 뒤(또는 `CONFIG RESETSTAT` 뒤) 누적값이라, 지금 상태를 보려면 1분 간격으로 두 번 읽어 차이를 봐야 한다. 그리고 서버 전체 합계다. 락 확인용 `SET NX` 전의 `GET`이나 없음 확인처럼 캐시가 아닌 조회까지 섞여서, 상품 캐시의 히트율이 따로 보이지 않는다. 그래서 실무에서는 응용 코드에서 키 종류별로 히트와 미스를 지표로 남긴다.

히트율 몇 %의 차이가 생각보다 크다. 초당 1만 요청에 히트율 95%면 DB에 500개, 99%면 100개가 간다. 겨우 4%p 차이인데 DB 부하는 다섯 배다. 응답 시간으로 보면, 히트가 1ms이고 미스가 50ms일 때 평균은 95%에서 0.95 × 1 + 0.05 × 50 = 3.45ms, 99%에서 1.49ms다. 그리고 히트율이 95%면 느린 쪽 5% 안에 미스가 다 들어가니, p99 응답 시간은 미스 경로의 시간 그대로다. 평균만 보면 캐시가 다 해결한 것 같지만 꼬리 지연은 DB가 정한다.

같이 보는 숫자가 몇 개 더 있다.

- `evicted_keys`가 늘고 있다면 메모리가 모자라 아직 쓸 키를 쫓아내는 중이다. 히트율이 떨어지는 흔한 원인이다.
- `used_memory`와 `maxmemory`의 비율. 축출이 시작될 시점을 미리 본다.
- Redis 응답 시간(`redis-cli --latency`, 응용 쪽 p99)과 `SLOWLOG`. 캐시가 느려지면 빠른 층이 아니다.
- 캐시 뒤에 있는 DB의 초당 쿼리 수. 캐시가 일을 잘하면 트래픽이 늘어도 이 숫자는 덜 는다. 히트율이 그대로인데 이게 튄다면 스탬피드나 눈사태를 의심한다.

## 캐시는 지우는 일까지가 설계다

캐시를 넣는 코드는 열 줄이면 된다. 어려운 건 그 뒤다. 읽을 때 채우고(cache-aside), 쓸 때는 DB를 먼저 고친 뒤 캐시를 지우고, 지우기가 실패하거나 경쟁에 져도 TTL이 피해를 가둔다. 만료 순간의 몰림은 락과 요청 합치기, 조기 갱신으로, 키 하나의 몰림은 로컬 캐시와 키 복제로, 없는 키 공격은 없음 캐시와 블룸 필터로, 한꺼번에 사라지는 일은 지터와 고가용성으로 막는다. 그리고 이 모든 게 맞게 돌고 있는지는 키 종류별 히트율과 DB 쪽 숫자로 확인한다.

## 면접에서 나올 만한 질문

### cache-aside 패턴을 설명하고 장단점을 말해 주세요.

응용이 캐시를 먼저 보고, 없으면 DB에서 읽어 TTL과 함께 캐시에 넣고 돌려준다. 쓸 때는 DB를 고친 뒤 캐시 키를 지운다. 실제로 요청된 데이터만 캐시에 들어가고, 캐시가 죽어도 DB로 서비스할 수 있다. 대신 첫 요청은 느리고, 삭제 전이나 경쟁 상황에서는 옛 값이 보일 수 있으며, 로직이 응용 코드에 흩어진다.

### write-through와 write-behind는 언제 쓰나요?

write-through는 캐시와 DB에 동기로 함께 써서 캐시가 늘 최신이고, 쓰고 바로 자주 읽는 데이터에 맞다. 대신 쓰기가 느려지고 안 읽힐 데이터도 캐시에 들어간다. write-behind는 캐시에만 쓰고 DB에는 모아서 나중에 써서 쓰기 폭주를 흡수한다. 캐시가 죽으면 옮기기 전 데이터를 잃으니 조회수처럼 잃어도 되는 값에만 쓴다.

### 데이터를 수정할 때 캐시를 갱신하지 않고 삭제하는 이유는요?

동시에 두 번 수정하면 캐시 쓰기 순서가 DB 커밋 순서와 달라져 틀린 값이 남을 수 있는데, 삭제는 몇 번을 어떤 순서로 해도 결과가 같다. 캐시 값이 여러 테이블을 조합한 경우가 많아 쓰기 경로마다 다시 계산하는 것보다 읽기 경로 한곳에서 만드는 게 단순하다. 대가는 쓰기 직후 미스 한 번이고, 아주 뜨거운 키는 스탬피드 대비를 같이 한다.

### DB 수정과 캐시 삭제는 어떤 순서로 하고, 그래도 불일치가 생기는 경우는요?

DB를 먼저 커밋하고 캐시를 지운다. 반대로 하면 그 사이 읽기가 옛 값을 다시 채운다. 그래도 미스를 본 읽기가 커밋 전 값을 읽어 들고 있다가 삭제 뒤에 넣으면 옛 값이 남는다. 레플리카에서 읽으면 이 창이 복제 지연만큼 넓어진다. 짧은 TTL을 안전망으로 두고, 지연 이중 삭제나 CDC 기반 삭제, 프라이머리에서 채우기로 창을 줄인다.

### 캐시 스탬피드는 어떻게 막나요?

인기 키가 만료되는 순간 미스가 몰려 같은 쿼리가 DB에 쏟아지는 현상이다. `SET NX PX`로 채우기 락을 잡아 한 요청만 DB에 가게 하고, 나머지는 잠깐 기다리거나 논리적 만료가 지난 옛 값을 받게 한다. 프로세스 안에서는 같은 키의 로딩을 Promise 하나로 합치고, 만료 직전에 확률적으로 미리 갱신하는 방법도 쓴다. 여러 키가 동시에 만료되지 않게 TTL 지터도 섞는다.

### 캐시 관통과 캐시 눈사태는 무엇이 다른가요?

관통은 DB에도 없는 키를 계속 물어서 매번 캐시를 뚫고 DB에 가는 문제다. 없음을 짧은 TTL로 캐시하고, 키가 무작위로 바뀌는 공격에는 블룸 필터로 없는 키를 앞에서 거른다. 눈사태는 많은 키가 동시에 만료되거나 캐시 서버가 통째로 비어서 DB로 트래픽이 한꺼번에 가는 문제다. TTL 지터, 나눠 채우기, Redis 고가용성, DB 앞의 동시성 제한과 서킷 브레이커로 막는다.

### 핫 키 문제는 어떻게 해결하나요?

키 하나는 클러스터에서도 노드 하나에 있어서 그 노드의 CPU와 네트워크가 먼저 찬다. 응용 서버에 수 초짜리 로컬 캐시를 둬서 Redis 호출을 줄이거나, 같은 값을 여러 키로 복제해 무작위로 읽게 해서 노드를 나눈다. 레플리카 읽기와 값 크기 줄이기도 쓴다. 찾을 때는 `--hotkeys`나 `--bigkeys`, 응용 쪽 키별 지표를 본다.

### 로컬 캐시와 Redis를 같이 쓸 때 일관성은 어떻게 맞추나요?

로컬 캐시는 서버마다 따로 있어서 Redis 삭제 한 번으로는 안 지워진다. 로컬 TTL을 수 초로 짧게 둬서 불일치를 그 안에 가두고, 수정 시 Pub/Sub으로 모든 서버에 무효화를 알린다. Pub/Sub은 메시지를 놓칠 수 있어 TTL을 같이 둔다. Redis 6의 `CLIENT TRACKING`처럼 서버가 무효화를 보내 주는 방법도 있고, 고친 직후 바로 보여야 하는 데이터는 로컬 캐시에 두지 않는다.
