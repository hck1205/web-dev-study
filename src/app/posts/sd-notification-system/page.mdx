이 시리즈에서 이 글의 자리: [㉑ 웹 크롤러 ②: 예의, 우선순위, 중복 거르기](/posts/sd-web-crawler-politeness-dedup)로 크롤러 장을 마쳤다. 이 글은 알림 시스템 장의 첫 글로, 푸시·SMS·이메일이 어떤 업체를 거쳐 사용자에게 닿는지와, 그걸 보내는 우리 쪽 부품을 설계한다. 같은 장의 다음 글 [㉓ 알림 시스템 ②: 잃지 않고 두 번 보내지 않기](/posts/sd-notification-reliability)에서 재시도, 중복 제거, 수신 설정, 모니터링을 다룬다. 그다음은 [㉔ 뉴스 피드 ①](/posts/sd-news-feed-publishing)이다.

쇼핑몰의 주문 API에 기능을 하나 더한다고 해 보자. 주문이 끝나면 "배송이 시작됐다"는 푸시를 휴대폰마다 보내고, 문자와 메일도 한 통씩 보낸다. 가장 빠른 구현은 주문 API의 마지막 줄에 업체 API 호출 세 개를 붙이는 것이다. 테스트에서는 잘 돈다. 그런데 문자 업체가 잠깐 장애를 내자 주문이 실패하기 시작했고, 실패한 주문의 고객에게는 이미 "배송이 시작됐다"는 푸시가 가 있었다.

면접 단골 질문 "알림 시스템을 설계하라"는 바로 이 상황을 일반화한 것이다. 이 글은 알림 한 통이 사용자 휴대폰에 닿기까지 누구를 거치는지부터 보고, 그 위에 우리 시스템을 하나씩 쌓는다.

## 주문 API 안에서 바로 보내 보기

로컬에 가짜 업체 서버를 띄웠다. 푸시는 80ms, 문자는 400ms, 메일은 250ms가 걸리게 했다. 실제 업체가 아니라 응답 시간만 흉내 낸 Node 서버다. 주문 API가 이 업체들을 차례로 부르게 하고, 사용자 한 명(휴대폰 두 대)에게 보냈다.

```js
async function placeOrderSync(user) {
  const c = contacts[user];
  for (const t of c.push) await send("push", t, "배송이 시작됐다"); // 기기마다
  await send("sms", c.sms, "배송이 시작됐다");
  await send("email", c.email, "배송이 시작됐다");
}
```

```text
[바로 보내기] 주문 응답까지 903ms
[바로 보내기, SMS 장애] 570ms 뒤 주문 실패: sms 503 / 그때까지 나간 것 push:ios:tok-a, push:android:tok-b
```

문제가 세 가지 보인다. 주문 응답이 0.9초 늦어졌다. 업체 응답 시간이 그대로 고객이 기다리는 시간에 더해졌다. 두 번째 줄은 더 나쁘다. 문자 업체가 503을 돌려주자 주문 자체가 실패했는데, 푸시 두 개는 이미 나간 뒤다. 고객이 주문을 다시 누르면 푸시를 또 받는다. 마지막으로, 알림을 보내는 곳이 주문 API만이 아니다. 결제, 배송, 쿠폰, 마케팅 팀이 다 비슷한 코드를 각자 붙이면 업체 키와 재시도 로직이 서비스마다 흩어진다.

해결의 방향은 분명하다. 주문 API는 "이 사람에게 이런 알림을 보내 달라"고 맡기기만 하고 바로 응답한다. 실제로 보내는 일은 다른 곳이 한다. 그 다른 곳을 설계하는 것이 이 글이다.

## 알림 한 통이 거치는 바깥 업체

우리 서버는 사용자 휴대폰에 직접 푸시를 보낼 수 없다. 휴대폰은 앱마다 서버와 연결을 열어 두지 않는다. 배터리가 버티지 못하기 때문이다. 대신 운영체제가 자기 회사 서버 하나와 연결을 유지하고, 모든 앱의 알림이 그 연결 하나로 들어온다. 그래서 채널마다 거쳐야 하는 업체가 정해져 있다.

- iOS 푸시: 애플의 APNs(Apple Push Notification service). 우리 서버가 HTTP/2로 APNs에 보내면 APNs가 기기에 전달한다.
- 안드로이드 푸시: 구글의 FCM(Firebase Cloud Messaging). HTTP v1 API로 보낸다. FCM은 iOS 기기(APNs를 대신 거쳐서)와 웹 브라우저로도 보낼 수 있어서, 푸시를 FCM 하나로 모으는 서비스도 많다.
- SMS: 통신사와 연결된 문자 발송 업체. 건당 비용이 있다. 한국에서는 보내는 번호를 미리 등록해야 한다(발신번호 사전등록제).
- 이메일: 대량 메일 발송 업체나 직접 운영하는 메일 서버. 스팸함에 빠지지 않게 하는 설정(SPF, DKIM, DMARC)은 [이메일 프로토콜 글](/posts/sd-email-protocols)에서 다룬다.

푸시를 받으려면 먼저 기기가 자기 주소를 알려 줘야 한다. 이 주소를 디바이스 토큰이라고 한다. 앱이 설치되고 사용자가 알림을 허용하면, 운영체제가 APNs나 FCM에서 토큰을 받아 앱에 준다. 앱은 그 토큰을 우리 서버에 올린다. 아래 그림에서 다음을 누르면 토큰이 생기는 순간부터 알림이 닿는 순간까지 따라간다.

## 연락처를 어디에 두나

보낼 곳은 채널마다 다르다. 이메일과 전화번호는 사용자 한 명에 하나씩이니 사용자 테이블에 둔다. 디바이스 토큰은 다르다. 한 사람이 휴대폰, 태블릿, 웹 브라우저를 쓸 수 있으니 따로 테이블을 둔다. PostgreSQL 16으로 만들어 봤다.

```sql
CREATE TABLE users (
  id         bigint PRIMARY KEY,
  email      text,                       -- 이메일 알림용
  phone      text,                       -- SMS용 (E.164 형식)
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE devices (
  id           bigserial PRIMARY KEY,
  user_id      bigint NOT NULL REFERENCES users(id),
  platform     text NOT NULL CHECK (platform IN ('ios', 'android', 'web')),
  token        text NOT NULL UNIQUE,     -- 같은 토큰이 두 줄로 생기지 않게
  app_version  text,
  last_seen_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON devices (user_id);       -- "이 사용자의 기기들"을 빨리 찾는다
```

사용자 1은 아이폰과 안드로이드 폰을, 사용자 2는 웹 브라우저를 등록했다고 하자. 그런데 사용자 1이 안드로이드 폰을 사용자 2에게 넘겼고, 사용자 2가 그 폰에서 로그인했다. 앱은 켜질 때마다 토큰을 올리니 같은 토큰이 다른 사용자 번호로 올라온다.

```sql
-- 앱이 켜질 때마다 토큰을 올린다. 같은 토큰이면 주인과 시각만 고친다
INSERT INTO devices (user_id, platform, token, app_version)
VALUES (2, 'android', 'cK3x...Qz', '5.2.0')
ON CONFLICT (token) DO UPDATE
  SET user_id = EXCLUDED.user_id, app_version = EXCLUDED.app_version, last_seen_at = now();

-- 사용자별로 보낼 기기
SELECT u.id, d.platform, d.token, d.app_version
FROM users u JOIN devices d ON d.user_id = u.id
ORDER BY u.id, d.platform;
```

```text
 id | platform |                   token                   | app_version 
----+----------+-------------------------------------------+-------------
  1 | ios      | a1f0...e9                                 | 5.2.0
  2 | android  | cK3x...Qz                                 | 5.2.0
  2 | web      | https://fcm.googleapis.com/fcm/send/dR... | 
(3 rows)
```

안드로이드 폰이 사용자 2 밑으로 옮겨 갔다. `token`에 `UNIQUE`가 없었다면 같은 토큰이 두 사용자에게 걸려서, 사용자 1의 주문 알림이 사용자 2의 폰에 뜬다. 개인정보가 새는 사고다. 로그아웃할 때 그 기기의 토큰 줄을 지우는 것도 같은 이유로 챙긴다. 웹 푸시는 토큰이 브라우저 업체 주소 모양이다. 크롬 계열은 위처럼 FCM 주소가 나온다.

토큰은 조용히 죽기도 한다. 앱을 지우면 그 토큰은 쓸모가 없어지는데, 우리 서버는 알 길이 없다. 보내 봤을 때 APNs가 410(`Unregistered`)을, FCM이 `UNREGISTERED`를 돌려주면 그때 지운다. 이 처리는 [㉓ 알림 시스템 ②](/posts/sd-notification-reliability)에서 다시 본다. `last_seen_at`이 몇 달씩 갱신되지 않은 토큰도 정리 대상이다.

## 얼마나 보내야 하나

이 글에서는 이런 조건을 잡는다. 푸시는 하루 2천만 건, 문자는 50만 건, 메일은 300만 건이다. iOS, 안드로이드, 웹을 모두 지원한다. 알림은 몇 초 안에 가면 되고, 사용자는 채널별로 알림을 끌 수 있다.

하루 2천만 건이면 평균 초당 약 231건이다. 문자는 초당 6건, 메일은 35건 정도다. 평균만 보면 서버 한 대로 충분해 보인다. 알림은 평균이 의미가 없다. 마케팅 팀이 "오후 7시에 전체 회원 1천만 명에게 쿠폰 알림"을 예약하면, 10분 안에 보내야 한다고 할 때 초당 약 16,700건이 된다. 평균의 70배가 넘는다. 이 몰림을 받아 주는 구조가 필요하다. 규모 어림하는 법은 [⑩ 규모 추정](/posts/sd-capacity-estimation)에서 연습했다.

## 첫 설계: 알림 서버 하나

주문 API에서 떼어 낸 일을 알림 서버 하나에 모은다. 알림을 보내고 싶은 서비스(주문, 결제, 배송, 마케팅 예약 작업 같은 것을 통틀어 트리거 서비스라고 부른다)는 알림 서버의 API를 부르기만 한다. 알림 서버는 요청을 확인하고, 연락처를 찾고, 본문을 만들고, 업체에 보낸다. 업체 키와 보내는 코드가 한곳에 모였으니 처음보다는 낫다. 하지만 아래 그림처럼 금방 한계가 온다.

채널마다 큐를 나눈 덕분에 장애가 한 채널에 갇혔다. 큐 하나에 다 넣으면 문자 몫이 앞을 막고 있는 동안 뒤의 푸시도 못 나간다. 채널 말고도 나눌 기준이 있다. 인증 번호처럼 늦으면 쓸모없는 알림과 마케팅 알림을 같은 큐에 넣으면, 1천만 건짜리 쿠폰 발송 뒤에 인증 번호가 줄을 선다. 그래서 같은 채널 안에서도 급한 큐와 느긋한 큐를 나눈다.

## 알림 서버가 요청 하나에 하는 일

알림 서버의 API는 대략 이런 모양이다. 트리거 서비스는 본문을 직접 만들지 않고 템플릿 이름과 값만 넘긴다.

```http
POST /v1/notifications
{
  "request_id": "order-1001-shipped",
  "user_id": 1,
  "template": "order_shipped",
  "params": { "order_id": 1001, "eta": "10월 23일" },
  "channels": ["push", "sms", "email"]
}
```

받은 뒤 하는 일은 이렇다. 먼저 누가 보냈는지 확인한다. 이 API는 사내 서비스만 부를 수 있어야 하니, 서비스마다 발급한 키(앱 키와 비밀 값)나 서비스 간 인증서(mTLS)로 확인한다. 아무나 부를 수 있으면 우리 이름으로 스팸을 보내는 통로가 된다. 그다음 요청을 검사한다. 템플릿이 있는지, 필요한 값이 다 왔는지, 전화번호와 메일 주소 모양이 맞는지 본다. 연락처와 사용자 설정을 캐시에서 찾고, 사용자가 끈 채널은 뺀다. 템플릿에 값을 채워 본문을 만들고, 보낼 곳마다 하나씩 작업을 만들어 채널별 큐에 넣는다. `request_id`는 같은 요청이 두 번 와도 한 번만 처리하려고 받는다. 이 부분과 템플릿, 설정은 다음 글에서 자세히 본다.

보낼 곳을 고르는 부분을 직접 짜 보자. 사용자 정보와 요청 채널을 받아 실제로 보낼 대상 목록을 만든다. iOS는 APNs로, 나머지 기기(안드로이드와 웹)는 FCM으로 보낸다고 하자.

## 워커는 업체와 씨름한다

워커는 큐에서 작업을 꺼내 업체를 부르고, 응답에 따라 셋 중 하나를 한다. 성공하면 보냈다고 기록하고 큐에서 지운다. 잠깐의 실패(타임아웃, 429, 5xx)면 조금 뒤에 다시 시도한다. 고칠 수 없는 실패(죽은 토큰, 잘못된 번호)면 다시 보내지 않고, 원인이 된 데이터를 고친다. 이 셋을 가르는 기준과 재시도 간격은 다음 글의 주제다.

워커를 채널마다 따로 두는 데는 이유가 하나 더 있다. 업체마다 보내는 방법이 다르다. APNs는 HTTP/2 연결 하나에 요청 여러 개를 동시에 실어 보낼 수 있어서, 연결을 오래 열어 두고 재사용해야 빠르다. 요청마다 연결을 새로 맺으면 TLS 핸드셰이크만으로 시간이 다 간다. 문자 업체는 초당 보낼 수 있는 건수를 계약으로 정해 두는 경우가 많아서, 워커가 그 속도를 넘지 않게 맞춰야 한다. 메일은 받는 쪽(지메일, 네이버 메일 같은 곳)이 한 발신자에게서 갑자기 많은 메일이 오면 스팸으로 의심하니, 새 발신 주소는 천천히 양을 늘린다.

워커는 상태를 들고 있지 않으니 늘리기 쉽다. 큐 깊이와 "큐에 들어가서 나오기까지 걸린 시간"을 보고 워커 수를 조절한다. 다만 워커를 늘린다고 업체가 더 빨리 받아 주지는 않는다. 업체 한도에 닿은 뒤에는 워커를 늘려도 429만 늘어난다. 그때는 큐에 쌓이는 걸 받아들이고, 급한 알림이 먼저 나가게 큐를 나눠 두는 것이 답이다.

## 다음에 읽을 글

알림 시스템은 받는 쪽(알림 서버)과 보내는 쪽(워커) 사이에 채널별 큐를 둔 구조다. 트리거 서비스는 템플릿과 값만 넘기고 바로 돌아가고, 알림 서버는 인증, 검사, 연락처 조회, 본문 만들기를 하고 큐에 넣는다. 워커는 APNs, FCM, 문자, 메일 업체와 각자의 방식으로 씨름한다. 이 구조 위에서 알림을 하나도 잃지 않고, 두 번 보내지 않고, 사용자가 원치 않는 알림은 보내지 않는 법은 [㉓ 알림 시스템 ②: 잃지 않고 두 번 보내지 않기](/posts/sd-notification-reliability)에서 이어진다.

## 면접에서 나올 만한 질문

### 알림 시스템의 전체 구조를 설명해 주세요.

트리거 서비스가 알림 서버 API를 부르면, 알림 서버가 인증과 검사를 하고 연락처와 수신 설정을 조회해 본문을 만든다. 보낼 곳마다 작업을 만들어 채널별 메시지 큐에 넣고 바로 응답한다. 채널별 워커가 큐에서 꺼내 APNs, FCM, 문자 업체, 메일 업체에 보낸다. 알림 서버와 워커는 상태가 없어서 여러 대로 늘리고, 연락처와 설정은 DB와 캐시에 둔다.

### 우리 서버가 휴대폰에 직접 푸시를 보내면 안 되나요?

앱마다 서버와 연결을 유지하면 배터리가 버티지 못해서 운영체제가 허락하지 않는다. iOS는 APNs, 안드로이드는 FCM과의 연결 하나로 모든 앱의 알림을 받는다. 그래서 우리 서버는 디바이스 토큰을 주소로 써서 이 업체들에 보내고, 업체가 기기에 전달한다.

### 디바이스 토큰은 어떻게 관리하나요?

한 사용자가 여러 기기를 쓰니 사용자 테이블과 따로 기기 테이블을 두고, 토큰에 유니크 제약을 건다. 앱이 켜질 때마다 토큰을 올려 바뀐 토큰을 따라가고, 같은 토큰이 다른 사용자로 올라오면 주인을 바꾼다. 업체가 410이나 `UNREGISTERED`를 돌려주면 지우고, 오래 갱신되지 않은 토큰도 정리한다. 유니크 제약이 없으면 넘겨준 폰에 이전 주인의 알림이 뜨는 사고가 난다.

### 왜 메시지 큐를 두나요? 알림 서버가 바로 보내면 안 되나요?

업체 응답 시간과 장애가 요청한 서비스로 번지지 않게 하려는 것이다. 큐가 있으면 알림 서버는 넣고 바로 응답하고, 예약 발송처럼 한꺼번에 몰리는 양도 큐가 받아 워커가 업체 속도에 맞춰 빼낸다. 업체가 죽어 있는 동안 작업은 큐에 남아 있다가 복구되면 나간다.

### 큐를 채널마다 나누는 이유는요?

한 채널의 업체 장애나 느림이 다른 채널을 막지 않게 하려는 것이다. 큐 하나에 다 넣으면 문자 몫이 앞을 막는 동안 푸시도 못 나간다. 같은 이유로 인증 번호 같은 급한 알림과 마케팅 알림도 큐를 나눠서, 대량 발송 뒤에 급한 알림이 줄 서지 않게 한다.

### 마케팅 발송으로 트래픽이 평소의 70배가 되면요?

알림 서버는 큐에 넣기만 하니 몇 대만 늘려도 버티고, 쌓이는 건 큐가 받는다. 워커는 큐 깊이를 보고 늘리되, 업체 한도에 닿으면 더 늘려도 429만 늘어난다. 그래서 대량 발송은 느긋한 큐로 보내 급한 알림과 섞이지 않게 하고, 예약 시각을 몇 분에 걸쳐 나눠 업체 한도 안에서 흘려보낸다.

### 알림 서버 하나가 요청을 받다가 죽으면요?

알림 서버는 상태가 없어서 로드 밸런서가 다른 서버로 보낸다. 큐에 넣기 전에 죽었다면 트리거 서비스는 응답을 못 받았으니 다시 보내고, `request_id`로 이미 처리한 요청인지 확인해 두 번 보내지 않는다. 큐에 넣은 뒤라면 작업은 큐에 남아 있다.

### APNs가 200을 주면 사용자가 알림을 본 건가요?

아니다. 200은 APNs가 맡았다는 뜻일 뿐이다. 기기가 꺼져 있으면 APNs는 앱마다 마지막 알림 하나만 보관하고, 사용자가 알림을 꺼 두었을 수도 있다. 그래서 중요한 정보는 알림에만 의존하지 않고 앱을 열 때 서버에서 다시 받아 오게 하며, 실제로 열었는지는 앱이 따로 보고하는 이벤트로 잰다.
