## 디자인 시스템을 누가 쓰는지 아무도 모른다

디자인 시스템 팀이 생긴 지 1년이 됐다. 버튼, 입력칸, 모달, 토스트, 테이블까지 서른 개 남짓한 컴포넌트를 만들었고 문서 사이트도 있다. 분기 리뷰에서 임원이 묻는다. "그래서 몇 팀이 쓰고 있죠? 1년 동안 무엇이 나아졌나요?" 팀은 답을 못 한다. 슬랙에서 질문이 많이 오니 꽤 쓰는 것 같다는 느낌만 있다.

같은 주에 한 제품 팀이 결제 화면에 자체 버튼을 새로 만들었다는 걸 코드 리뷰에서 우연히 알게 된다. 이유를 물으니 "디자인 시스템 버튼에는 아이콘 오른쪽 배치가 없어서"였다. 그 요청은 석 달 전에 이슈로 올라와 있었고 아무도 답하지 않았다.

디자인 시스템을 어떻게 만드는지(토큰 층, 헤드리스 컴포넌트, Storybook, 버전과 배포)는 [디자인 시스템 만들기](/posts/design-system-building)에 정리했다. 컴포넌트 API를 어떻게 좁고 예측 가능하게 설계하는지는 [핵심 컴포넌트 API 설계](/posts/core-component-api-design)에 있다. 이 글은 만든 다음의 일을 다룬다. 얼마나 쓰이는지 재고, 잘못 쓰이면 알려 주고, 누가 무엇을 결정하는지 정하고, 오래된 것을 정해진 날에 치우는 일이다.

## 처음부터 만들지, 있는 화면에서 걷어 낼지

측정 이야기 전에 출발점을 짚는다. 디자인 시스템은 두 방향에서 시작한다.

있는 화면에서 걷어 내는 방식은 이미 서비스가 돌아가는 회사에 맞다. 먼저 시각 감사(visual audit)를 한다. 주요 화면을 캡처해서 버튼끼리, 입력칸끼리, 색끼리 한 판에 모아 붙인다. 버튼이 일곱 종류, 파란색이 다섯 가지라는 사실이 눈에 보이면 설득이 쉬워진다. 캡처와 함께 코드에서도 센다.

```bash
# 소스에 직접 쓴 hex 색을 소문자로 맞춰 세기
grep -rhoE '#[0-9a-fA-F]{6}\b' src | tr 'A-F' 'a-f' | sort | uniq -c | sort -rn

# px로 직접 쓴 글자 크기 세기
grep -rhoE 'font-size: *[0-9.]+px' src | sort | uniq -c | sort -rn
```

작은 예제 저장소에서 돌린 결과다.

```text
      3 #2563eb
      3 #111827
      1 #2564eb
      1 #1f2937
      2 font-size: 14px
      2 font-size: 13px
      1 font-size: 18px
      1 font-size: 17px
      1 font-size: 15px
      1 font-size: 12px
```

`#2563eb`와 `#2564eb`는 눈으로는 구분이 안 되는 같은 파랑이다. 누군가 색을 손으로 옮겨 적다 한 자리가 틀렸을 것이다. 글자 크기는 12, 13, 14, 15, 17, 18px 여섯 가지인데, 단계로 정리하면 셋이나 넷이면 된다. 이 숫자가 토큰을 정할 때의 재료가 된다. 간격과 글자 크기를 숫자 체계로 묶는 방법은 [간격과 크기, 글자 단계를 숫자 체계로](/posts/spacing-sizing-type-scale)에서 이어서 다룬다.

화면만 보지 말고 일하는 방식도 본다. 디자이너가 Figma에서 컴포넌트를 어떻게 관리하는지, 개발자가 디자인을 어디서 받아 가는지, 리뷰는 누가 하는지. 디자인 파일에는 버튼이 세 종류인데 코드에는 일곱 종류라면, 문제는 컴포넌트가 아니라 디자인과 코드 사이의 전달 과정에 있다.

처음부터 만드는 방식은 새 제품이나 전면 개편 때 맞다. 걷어 낼 과거가 없으니 원칙과 토큰부터 정할 수 있다. 대신 실제 화면의 요구를 모른 채 만들게 되니, 아래에서 다룰 파일럿 제품이 더 중요해진다.

## import를 세는 것에서 시작한다

"몇 팀이 쓰나"에 답하는 가장 직접적인 방법은 코드를 훑는 것이다. 정규식으로 `import { Button }`을 찾으면 주석이나 별칭 import, 여러 줄 import를 놓친다. 그래서 코드를 구문 트리(AST)로 파싱해서 JSX 요소를 센다. react-scanner가 이 일을 하는 도구다.

```js
// scanner.config.js: @acme/ui에서 가져온 컴포넌트와 props만 센다
module.exports = {
  crawlFrom: "./app/src",
  includeSubComponents: true, // Table.Row 같은 하위 컴포넌트도 센다
  importedFrom: "@acme/ui",
  processors: ["count-components-and-props"],
};
```

```bash
npx react-scanner -c scanner.config.js
```

파일 세 개짜리 예제 앱에서 실제로 돌린 출력이다.

```text
Scanned 3 files in 0.518711937 seconds
{
  "Button": {
    "instances": 3,
    "props": {
      "variant": 2,
      "kind": 1,
      "size": 1
    }
  },
  "Modal": {
    "instances": 1,
    "props": {
      "open": 1
    }
  },
  "TextField": {
    "instances": 1,
    "props": {
      "label": 1
    }
  }
}
```

컴포넌트 수만이 아니라 props 쓰임도 나온다. 여기서 `kind`가 눈에 띈다. `Button`의 공식 prop은 `variant`인데, 누군가 옛 버전 문서를 보고 `kind`를 썼다. 타입 검사가 느슨하게 설정된 앱이었다면 이 prop은 조용히 무시되고 기본 모양으로 그려진다. props 통계는 이렇게 오용을 찾는 데도 쓰고, 거의 안 쓰이는 prop을 지울 근거로도 쓴다. 전체 5천 곳 중 2곳에서만 쓰는 prop이라면 유지할 이유를 다시 따져 본다.

## 복제본까지 세야 도입률이 된다

시스템 컴포넌트가 몇 번 쓰였는지만으로는 부족하다. 1,000번 쓰였어도 같은 역할의 자체 컴포넌트가 3,000번 쓰였다면 도입률은 25%다. 그래서 출처를 가리지 않고 모든 JSX 요소를 센 다음, 시스템 컴포넌트와 같은 역할을 하는 것을 짝지어 비교한다.

```js
// all.config.js: 출처와 상관없이 모든 JSX 요소를 센다
module.exports = {
  crawlFrom: "./app/src",
  processors: ["count-components"],
};
```

```text
Scanned 3 files in 0.437724917 seconds
{
  "Button": 3,
  "button": 2,
  "Modal": 1,
  "MyButton": 1,
  "TextField": 1,
  "form": 1
}
```

`button`(맨 HTML 버튼)이 2번, `MyButton`(팀이 만든 버튼)이 1번 나온다. 둘 다 시스템 `Button`이 할 일을 대신하고 있다. 도입률은 "시스템 컴포넌트 사용 수 ÷ (시스템 컴포넌트 + 같은 역할의 대체물)"로 계산한다. 버튼만 보면 3 ÷ (3 + 3) = 50%다.

짝짓기는 사람이 정한다. `MyButton`, `LegacyButton`, `PrimaryBtn`처럼 이름에 단서가 있는 건 이름 규칙으로 찾고, `button`, `input`, `select` 같은 맨 HTML 요소는 시스템에 대응하는 컴포넌트가 있을 때만 대체물로 친다. 다만 이 예제에서 `MyButton` 안에도 `button`이 하나 들어 있어서 같은 버튼이 두 번 잡혔다. 로컬 컴포넌트를 정의하는 파일은 맨 요소 집계에서 빼는 식으로 보정한다. 숫자를 완벽하게 만들기보다 같은 규칙으로 매달 재서 방향을 보는 게 목적이다.

아래 함수는 집계 결과와 시스템 컴포넌트 목록, 대체물 짝을 받아 컴포넌트별 도입률과 전체 도입률을 계산한다.

  // equivalents: 대체물 → 시스템 컴포넌트 { button: "Button", MyButton: "Button" }

  solution={`function adoption(counts, dsNames, equivalents) {
  const pct = (a, b) => (b === 0 ? null : Math.round((a / b) * 1000) / 10);
  const byComponent = {};
  let dsTotal = 0;
  let localTotal = 0;
  for (const name of dsNames) {
    const ds = counts[name] ?? 0;
    let local = 0;
    for (const [other, target] of Object.entries(equivalents)) {
      if (target === name) local += counts[other] ?? 0;
    }
    byComponent[name] = pct(ds, ds + local);
    dsTotal += ds;
    localTotal += local;
  }
  return { overall: pct(dsTotal, dsTotal + localTotal), byComponent };
}`}

두 번째 예처럼 컴포넌트별로 나눠 보면 할 일이 보인다. 버튼은 다 옮겨 왔는데 `Select`는 0%다. 시스템 `Select`가 검색이나 여러 개 고르기를 못 해서 다들 `LegacySelect`를 쓰고 있을 가능성이 크다. 이건 홍보할 문제가 아니라 컴포넌트를 고칠 문제다. 저장소별, 팀별로 같은 계산을 하면 어느 팀에 먼저 가서 물어볼지도 정해진다.

색과 간격도 같은 방식으로 잰다. 앞의 grep처럼 하드코딩된 hex 수를 매달 세거나, stylelint 규칙으로 토큰이 아닌 색을 경고하고 그 경고 수를 지표로 삼는다. 컴포넌트 도입률은 높은데 하드코딩 색이 늘고 있다면, 시스템 컴포넌트를 쓰면서 겉모양을 덮어쓰고 있다는 신호다.

앱들이 어떤 버전을 쓰는지도 같이 모은다. 저장소마다 lockfile에서 `@acme/ui` 버전을 읽어 두면 "최신 major를 쓰는 앱 4/10" 같은 숫자가 나온다. 도입률이 높아도 절반이 두 major 전에 멈춰 있으면 고친 버그와 접근성 개선이 그 앱에는 닿지 않는다.

## 문서 사이트도 지표를 남긴다

코드 스캔은 "이미 쓴 것"을 보여 주고, 문서 사이트는 "쓰려고 찾아본 것"을 보여 준다. 문서 사이트나 Storybook에 일반 웹 분석을 붙여 두면 읽을 거리가 생긴다. Storybook은 `preview-head.html`, `manager-head.html`에 스크립트를 넣을 수 있다.

가장 쓸모 있는 건 결과가 없는 검색어다. "날짜 범위", "스테퍼", "칩"을 검색하고 아무것도 못 찾은 기록이 쌓이면 다음에 만들 컴포넌트 목록이 된다. 코드 복사 버튼을 누른 횟수는 실제로 가져다 쓰려는 의도에 가깝다. 반대로 어떤 컴포넌트 문서는 조회가 많은데 코드 스캔 숫자는 늘지 않는다면, 사람들이 찾아와서 읽고는 쓰지 않기로 했다는 뜻이다. 문서가 불친절하거나 컴포넌트가 요구를 못 받거나 둘 중 하나다.

문서 사이트 지표는 [제품 지표를 재는 법](/posts/product-analytics-funnels)에서 다룬 방식 그대로다. 이벤트 이름을 정하고(`Docs Searched`, `Code Copied`), 속성으로 컴포넌트 이름과 검색어를 남긴다. 사내 도구라도 검색어에 고객 정보가 섞여 들어갈 수 있으니 길이를 자르고 보관 기간을 정한다.

## 건강 지표는 팀이 얼마나 빨리 답하는지다

도입률이 결과라면, 그 결과를 만드는 원인은 대개 시스템 팀의 응답 속도다. 처음 사례에서 결제 팀이 자체 버튼을 만든 이유도 석 달 동안 답이 없던 이슈였다. 그래서 서비스 지표를 따로 본다.

- 이슈 첫 응답까지 걸린 시간. 해결이 아니라 "봤고, 언제쯤 된다"는 첫 답이다. 제품 팀이 기다릴지 직접 만들지는 이 답으로 정한다.
- 버그를 고쳐 배포하기까지 걸린 시간의 중앙값과 90번째 백분위. 평균은 오래 묵은 이슈 몇 개에 끌려간다.
- 릴리스 주기. 고친 것이 실제로 패키지로 나가는 간격이다. 고쳐 놓고 한 달 동안 배포하지 않으면 고친 게 아니다.
- 시스템 저장소의 CI 시간과 시각 회귀 테스트 통과율. 기여하려는 사람이 PR 하나에 40분씩 기다리면 기여가 끊긴다.
- 컴포넌트별 번들 크기. `DatePicker` 하나 import했는데 날짜 라이브러리 전체가 따라오면 성능에 민감한 팀은 쓰지 않는다.

이 숫자들은 분기마다 같은 표로 공개한다. 도입률과 나란히 놓으면 "응답이 빨라진 분기에 도입률이 올랐다" 같은 이야기를 근거로 할 수 있고, 처음의 임원 질문에도 답이 된다.

## 잘못 쓰면 개발 중에 알려 준다

스캔은 한 달에 한 번이지만, 오용은 개발자가 코드를 쓰는 그 순간에 알려 주는 게 가장 싸다. 타입이 1차 방어선이다. `variant`를 문자열 리터럴 유니온으로 두면 `kind="primary"`나 `variant="primery"`는 컴파일에서 막힌다. 타입으로 표현하기 어려운 규칙은 개발 모드 경고로 잡는다.

```ts
// dev-warning.ts: 개발 모드에서만, 같은 경고는 한 번만 띄운다
const warned = new Set<string>();

export function devWarnOnce(key: string, message: string) {
  if (process.env.NODE_ENV === "production") return; // 프로덕션 번들에서는 지워진다
  if (warned.has(key)) return;
  warned.add(key);
  console.warn(`[@acme/ui] ${message}`);
}
```

```tsx
export function IconButton({ icon, "aria-label": label, ...rest }: IconButtonProps) {
  if (!label) {
    // 글자 없는 버튼은 스크린리더가 "버튼"이라고만 읽는다
    devWarnOnce("IconButton:label", "IconButton에는 aria-label이 필요하다. 예: aria-label=\"닫기\"");
  }
  return <button type="button" aria-label={label} {...rest}>{icon}</button>;
}
```

`process.env.NODE_ENV === "production"` 비교는 번들러가 빌드 때 상수로 바꿔서, 프로덕션 번들에서는 경고 코드가 통째로 빠진다. 같은 경고를 한 번만 띄우는 이유는 목록 100줄에서 같은 경고가 100번 찍히면 개발자가 콘솔을 아예 안 보게 되기 때문이다. 폐기 예정 prop도 이 함수로 알린다. "`kind`는 다음 major에서 사라진다, `variant`를 쓴다"처럼 무엇으로 바꾸면 되는지를 같이 적는다.

프로덕션에서는 경고 대신 오류를 모은다. React 19의 `createRoot`는 `onCaughtError`(에러 바운더리가 잡은 오류)와 `onUncaughtError` 옵션을 받고, 두 번째 인자로 `componentStack`을 준다. 이 스택에 시스템 컴포넌트 이름이 있으면 오류 수집 도구에 태그를 붙인다.

```tsx
createRoot(container, {
  onCaughtError(error, errorInfo) {
    const fromDs = /\bat (Button|Modal|Select|DatePicker)\b/.test(errorInfo.componentStack ?? "");
    reportError(error, { tags: { designSystem: fromDs ? "yes" : "no" } }); // 수집 도구로 보낸다
  },
}).render(<App />);
```

이름으로 찾는 방식은 프로덕션 번들이 컴포넌트 이름을 줄여 버리면 동작하지 않는다. 시스템 패키지가 `displayName`을 명시해 두면 덜 흔들린다. 완벽하지 않아도, 시스템 컴포넌트에서 나는 오류가 어느 버전부터 늘었는지 볼 수 있으면 충분하다.

## v1 전에 파일럿 제품에 먼저 넣는다

시스템 팀이 혼자 반년 동안 컴포넌트 50개를 만들고 공개하면, 실제 제품에 필요한 건 그중 일부이고 정작 필요한 것은 빠져 있기 쉽다. 그래서 1.0을 내기 전에 파일럿 제품 하나를 정해 같이 만든다.

파일럿은 너무 쉽지도 너무 어렵지도 않은 곳을 고른다. 정적인 마케팅 페이지는 폼과 테이블이 없어서 검증이 안 된다. 반대로 레거시가 가장 깊은 핵심 결제 화면은 일정 압박이 커서 시스템 문제가 바로 제품 장애가 된다. 폼, 목록, 모달이 고루 있고, 팀이 협조적이며, 몇 주 늦어져도 버틸 수 있는 신규 기능이 좋다.

파일럿 기간에 시스템 팀은 그 제품 팀 옆에 붙는다. 0.x 버전으로 내서 깨지는 변경을 허용하고, 파일럿 팀이 막힌 곳을 매주 모은다. 파일럿을 끝낼 때 확인하는 질문은 "이 컴포넌트로 실제 화면을 끝까지 만들 수 있었나", "탈출구(시스템 밖 코드)를 몇 군데 썼고 왜 썼나"다. 탈출구 목록이 다음 작업 목록이 된다. 두 번째 제품에서도 같은 컴포넌트가 큰 수정 없이 들어가면 그때 1.0으로 API를 굳힌다.

## 폐기 날짜를 지키게 하는 codemod

옛 API를 지우겠다고 공지해도, 옮기는 일이 각 팀 몫이면 날짜는 계속 밀린다. 그래서 기계적으로 바꿀 수 있는 변경은 시스템 팀이 변환 스크립트(codemod)를 만들어 함께 준다. 앞에서 스캔으로 찾은 `kind`를 `variant`로 바꾸는 jscodeshift 변환이다.

```js
// kind-to-variant.js: @acme/ui의 Button에 붙은 kind prop만 variant로 바꾼다
module.exports = function transformer(file, api) {
  const j = api.jscodeshift;
  const root = j(file.source);
  const local = new Set();
  // import { Button as Btn } 처럼 별칭으로 가져와도 찾는다
  root.find(j.ImportDeclaration, { source: { value: "@acme/ui" } })
    .find(j.ImportSpecifier, { imported: { name: "Button" } })
    .forEach((p) => local.add(p.node.local.name));
  if (local.size === 0) return null; // 이 파일은 건드리지 않는다
  let changed = 0;
  root.find(j.JSXOpeningElement)
    .filter((p) => p.node.name.type === "JSXIdentifier" && local.has(p.node.name.name))
    .find(j.JSXAttribute, { name: { name: "kind" } })
    .forEach((p) => { p.node.name.name = "variant"; changed++; });
  return changed ? root.toSource() : null;
};
```

```bash
npx jscodeshift -t kind-to-variant.js --parser=tsx --extensions=tsx app/src
```

`MyButton`이나 맨 `button`에 붙은 `kind`가 있었더라도 바뀌지 않는다. 이름이 아니라 import 출처로 대상을 찾기 때문이다. 정규식 치환으로 하면 바로 이 부분에서 엉뚱한 코드를 고친다. 결과의 `skipped`는 변환이 `null`을 돌려준 파일, 즉 `@acme/ui` Button이 없거나 바꿀 것이 없던 파일이다.

폐기는 이런 순서로 간다. 새 API를 minor로 추가하고, 옛 API에 개발 모드 경고를 붙이고, codemod를 같이 배포하고, 스캔으로 옛 API 사용 수를 매달 공개한다. 사용 수가 0에 가까워지면 major에서 지운다. 숫자가 줄지 않는 팀이 있으면 그 팀의 코드에 codemod가 못 바꾸는 패턴이 있는지 직접 본다. 버전 규칙과 무엇이 깨지는 변경인지는 [디자인 시스템 만들기](/posts/design-system-building#깨지는-변경을-알리고-옮겨-준다)에 정리했다.

## 다시 분기 리뷰로

처음 질문으로 돌아가면, 이제는 숫자로 답할 수 있다. 저장소 열 곳의 버튼 도입률이 50%에서 80%로 올랐고, `Select`는 0%라 다음 분기 우선순위로 올렸고, 이슈 첫 응답 중앙값은 9일에서 2일로 줄었다는 식이다. 디자인 시스템도 하나의 제품이다. 쓰는 사람(제품 팀)이 있고, 그 사람들이 왜 안 쓰는지 재고, 답하는 속도를 관리하고, 결정을 기록하고, 낡은 것을 치우는 일까지가 만드는 일에 포함된다.

## 면접에서 나올 만한 질문

### 디자인 시스템 도입률은 어떻게 재나요?

코드를 AST로 파싱해 시스템 컴포넌트 사용 수를 세고, 같은 역할을 하는 로컬 컴포넌트와 맨 HTML 요소도 함께 세서 "시스템 ÷ (시스템 + 대체물)"로 계산한다. 정규식은 별칭 import나 여러 줄 import를 놓쳐서 react-scanner 같은 AST 도구를 쓴다. 컴포넌트별, 팀별로 나눠 보면 어느 컴포넌트가 요구를 못 받는지와 어느 팀에 먼저 물어볼지가 보인다.

### 사용 수만 세면 안 되는 이유는요?

사용 수는 늘어도 같은 역할의 자체 컴포넌트가 더 빨리 늘면 실제 도입은 줄고 있을 수 있다. 그래서 대체물을 분모에 넣은 비율로 보고, 하드코딩 색 수나 덮어쓴 스타일 수처럼 겉모양을 우회한 흔적도 같이 본다. 앱별로 쓰는 버전 분포도 봐야 고친 내용이 실제로 닿았는지 안다.

### 컴포넌트 오용을 어떻게 잡나요?

먼저 타입으로 막는다. variant를 리터럴 유니온으로 두면 오타와 옛 prop은 컴파일에서 걸린다. 타입으로 표현 못 하는 규칙(아이콘 버튼의 aria-label)은 개발 모드에서만 한 번씩 뜨는 경고로 알리고, 프로덕션 빌드에서는 상수 치환으로 경고 코드가 빠지게 한다. 이미 퍼진 오용은 스캔의 props 통계로 찾는다.

### 중앙형과 연합형 거버넌스의 차이와 고르는 기준은요?

중앙형은 전담 팀이 만들고 결정해서 일관성이 높지만 요청이 몰리면 병목이 된다. 연합형은 제품 팀들이 함께 만들어 현장 요구가 빨리 들어오지만 책임이 흐려지기 쉽다. 보통은 작은 코어 팀이 리뷰와 릴리스, 품질 기준을 맡고 제품 팀이 기여하는 혼합형으로 가며, 누가 머지하고 누가 버그를 받는지를 이름으로 정해 두는 게 핵심이다.

### 1.0을 내기 전에 파일럿 제품이 필요한 이유는요?

실제 화면의 요구를 모른 채 만든 컴포넌트는 필요 없는 기능이 많고 필요한 기능이 빠지기 쉽다. 폼, 목록, 모달이 고루 있는 신규 기능 하나와 같이 만들면서 0.x로 API를 바꿔 가고, 탈출구를 쓴 곳을 모아 다음 작업으로 삼는다. 두 번째 제품에서도 큰 수정 없이 들어갈 때 API를 1.0으로 굳힌다.

### 기여 절차에 RFC를 두는 이유는요?

새 컴포넌트나 깨지는 변경을 코드부터 올리면 리뷰에서 API를 처음부터 다시 다투게 된다. RFC로 문제, 제안 API, 키보드 동작, 대안을 먼저 합의하면 구현 뒤 다시 짜는 일이 줄고, 결정과 거절의 이유가 기록으로 남아 같은 제안이 반복될 때 답이 빨라진다. 작은 버그 수정까지 RFC를 요구하면 기여가 끊기니 변경 규모별로 길을 나눈다.

### 폐기 일정이 계속 밀릴 때 어떻게 하나요?

옮기는 비용을 각 팀에 떠넘기지 않는다. 새 API를 minor로 먼저 내고, 옛 API에 개발 모드 경고를 붙이고, import 출처로 대상을 찾는 codemod를 함께 배포한다. 스캔으로 옛 API 사용 수를 매달 공개하고, 0에 가까워지면 major에서 지운다. 줄지 않는 팀은 codemod가 못 바꾸는 패턴이 있는지 직접 본다.

### codemod를 정규식 치환 대신 AST로 짜는 이유는요?

정규식은 이름만 보고 바꾸니 다른 패키지의 같은 이름 컴포넌트, 문자열 안의 텍스트, 별칭 import를 구분하지 못한다. AST 변환은 import 출처를 확인해 그 컴포넌트에 붙은 prop만 바꾸고, 바꿀 게 없는 파일은 건드리지 않는다. 그래서 수백 개 저장소에 돌려도 리뷰할 diff가 의도한 변경만 담는다.
