사내 위키 검색에 벡터 검색을 붙이면서 처음 고른 모델은 `all-MiniLM-L6-v2`였다. Sentence Transformers 문서의 첫 예제에 나오고, 작고 빠르고, 384차원이라 저장도 가볍다. 영어 문서로 시험할 때는 잘 됐다. 그런데 한국어 위키에서 "휴가 신청은 어디서 해요?"를 검색하자 1등이 "서버 증설 요청 절차"였고, 정작 "연차 사용 안내"는 10위 밖이었다. 다른 질문도 비슷했다. 결과를 보면 질문과 상관없이 늘 비슷한 문서 몇 개가 위에 올라왔다.

원인은 모델 카드에 적혀 있었다. 이 모델은 영어 문장 쌍으로 학습됐다. 한국어 문장은 토크나이저가 아주 잘게 쪼개고, 학습 때 한국어 문장끼리 뜻이 가깝다는 신호를 거의 받지 못했으니 뜻이 다른 한국어 문장도 비슷한 자리에 찍힌다. 모델이 고장 난 게 아니라 일에 맞지 않는 모델을 고른 것이다.

임베딩과 코사인 유사도, 벡터 DB가 가까운 점을 빨리 찾는 방법은 [벡터 DB 글](/posts/vector-db)에 있고, 임베딩을 검색에 써서 답을 만드는 흐름은 [기본 RAG 글](/posts/rag-classic-pipeline)에 있다. 이 글은 그 앞 단계, 어떤 임베딩 모델을 어떤 설정으로 쓸지와, 같은 벡터로 검색 말고 무엇을 할 수 있는지를 다룬다. 실제 모델의 벡터는 수백에서 수천 차원이라, 계산 원리를 보일 때는 손으로 만든 작은 벡터를 쓴다.

## 모델을 고를 때 먼저 보는 다섯 가지

임베딩 모델 비교표를 보면 숫자가 많다. 그중 실제로 선택을 가르는 건 다섯 가지 정도다.

언어가 첫째다. 모델이 어떤 언어 데이터로 학습됐는지 모델 카드에서 확인한다. "multilingual"이라고 적혀 있어도 언어마다 품질이 다르다. 한국어 문서를 다룬다면 학습 데이터에 한국어가 충분히 들어간 모델인지, 한국어 평가 결과가 공개돼 있는지 본다. 질문은 한국어인데 문서는 영어인 경우(교차 언어 검색)도 있다면 그것까지 되는 모델이어야 한다.

최대 입력 길이가 둘째다. 모델마다 한 번에 받는 토큰 수가 정해져 있고, 넘는 부분은 대개 조용히 잘린다. 오류가 나지 않으니 모르고 지나치기 쉽다. 512토큰짜리 모델에 2천 토큰짜리 청크를 넣으면 앞 4분의 1만 벡터에 반영된다. 청크 크기는 모델의 최대 길이 안에서 정한다. 이 한도는 글자가 아니라 토큰 기준이라, 같은 글자 수라도 한국어는 영어보다 토큰을 많이 쓴다는 점도 계산에 넣는다.

차원이 셋째다. 차원이 크면 담을 수 있는 정보가 많지만, 저장 공간과 검색 시간이 그만큼 는다. 아래 계산은 문서 100만 개를 저장할 때의 크기다.

```js
// emb.mjs: 임베딩 저장 용량과 재색인 비용을 계산한다
const docs = 1_000_000, tokensPerDoc = 500;
for (const [name, dims] of [["3-small 1536", 1536], ["3-large 3072", 3072], ["3-large 256으로", 256], ["1024 차원", 1024]]) {
  const f32 = docs * dims * 4 / 1e9, i8 = docs * dims / 1e9;
  console.log(name.padEnd(16), "float32", f32.toFixed(2), "GB   int8", i8.toFixed(2), "GB");
}
const tok = docs * tokensPerDoc;
console.log("재색인 토큰", tok.toLocaleString());
for (const [name, price] of [["3-small $0.02/1M", 0.02], ["3-large $0.13/1M", 0.13]]) console.log(name, "$" + (tok / 1e6 * price).toFixed(2));
```

```text
3-small 1536     float32 6.14 GB   int8 1.54 GB
3-large 3072     float32 12.29 GB   int8 3.07 GB
3-large 256으로    float32 1.02 GB   int8 0.26 GB
1024 차원          float32 4.10 GB   int8 1.02 GB
재색인 토큰 500,000,000
3-small $0.02/1M $10.00
3-large $0.13/1M $65.00
```

벡터만의 크기이고, HNSW 같은 인덱스는 이웃 연결 정보를 더 쓰며 대개 메모리에 올려야 빠르다. 3072차원 float32로 1,200만 개면 벡터만 150GB 가까이 된다. 차원을 줄이는 방법은 뒤에서 본다.

평가 점수가 넷째다. 임베딩 모델을 비교하는 공개 벤치마크로 MTEB(Massive Text Embedding Benchmark)가 가장 널리 쓰인다. 검색, 분류, 군집, 문장 유사도 같은 과제를 여러 데이터셋에서 재서 순위를 매긴다. 다국어로 넓힌 MMTEB도 있다. 출발점으로는 좋지만 그대로 믿지 않는다. 총점은 여러 과제의 평균이라, 내가 할 일(한국어 검색)의 점수와 다를 수 있다. 공개 데이터셋이 학습에 섞였을 가능성도 있다. 순위는 후보를 세 개쯤으로 줄이는 데 쓰고, 결정은 내 데이터로 한다.

비용과 운영이 다섯째다. API로 쓰면 토큰당 요금을 내고, 직접 띄우면 서버를 낸다. 위 계산처럼 문서 100만 개(평균 500토큰)를 한 번 색인하는 요금은 OpenAI의 `text-embedding-3-small` 단가로 10달러, `text-embedding-3-large`로 65달러다(100만 토큰당 0.02달러, 0.13달러로 알려진 공개 단가로 계산했다. 단가는 바뀔 수 있으니 계산 전에 가격표를 확인한다). 생각보다 싸다. 비싼 건 요금보다 저장소와 검색 인프라, 그리고 모델을 바꿀 때 전부 다시 하는 일이다.

## API로 쓰는 모델과 직접 띄우는 모델

임베딩 모델을 쓰는 방법은 크게 둘이다. 공급사 API를 부르거나, 공개된 모델을 내려받아 직접 띄운다.

API형으로는 OpenAI(`text-embedding-3-small` 1536차원, `text-embedding-3-large` 3072차원), Google Gemini(`gemini-embedding-001`), Cohere(Embed 계열), Jina(jina-embeddings 계열), Voyage 같은 곳이 있다. 서버를 운영할 필요가 없고, 큰 모델의 품질을 바로 쓸 수 있다. 대신 문서와 질문이 모두 바깥으로 나가고, 요청마다 네트워크 지연이 붙고, 공급사가 모델을 내리면 따라 옮겨야 한다.

직접 띄우는 쪽은 Hugging Face에 공개된 모델을 Sentence Transformers 같은 라이브러리로 돌린다. 다국어 검색용으로는 BGE-M3, multilingual-e5 계열 같은 모델이 자주 쓰이고, 한국어 데이터로 더 학습시킨 공개 모델도 있다. 데이터가 밖으로 나가지 않고, 쓴 만큼 요금이 붙지 않고, 모델 버전을 내가 고정할 수 있다. 대신 GPU나 넉넉한 CPU 서버를 운영해야 하고, 처리량과 지연을 내가 책임진다.

```python
# 직접 띄우는 모델은 대략 이런 모양으로 쓴다 (Sentence Transformers)
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("intfloat/multilingual-e5-large")    # 처음 한 번 내려받는다
docs = ["passage: 연차는 인사 시스템의 휴가 메뉴에서 신청한다.",
        "passage: 서버 증설은 인프라 팀에 티켓으로 요청한다."]
q = ["query: 휴가 신청은 어디서 해요?"]

doc_vecs = model.encode(docs, normalize_embeddings=True)       # 길이 1로 맞춘다
q_vec = model.encode(q, normalize_embeddings=True)
print(doc_vecs.shape)                                           # (2, 1024)
print(q_vec @ doc_vecs.T)                                       # 정규화했으니 내적 = 코사인
```

이 예제는 이 글을 쓴 환경에서 모델을 내려받을 수 없어 돌려 보지 못했다. 사용법의 모양만 보이려고 넣었고, 실제 점수는 직접 돌려서 확인해야 한다. 코드에서 볼 곳은 세 군데다. 문장 앞의 `query:`, `passage:` 접두어, `normalize_embeddings=True`, 그리고 정규화한 벡터끼리는 내적이 곧 코사인이라는 사실이다. 셋 다 다음 절의 주제다.

어느 쪽을 고를지는 데이터 정책이 먼저 정한다. 문서를 외부로 보낼 수 없으면 직접 띄운다. 보낼 수 있다면 처음엔 API로 빠르게 시작하고, 호출량이 커져 요금이 서버 비용을 넘거나 지연이 문제가 될 때 직접 띄우는 쪽을 따져 보는 순서가 흔하다.

## 질문과 문서는 다르게 넣는다

검색에서 질문과 문서는 생김새가 다르다. 질문은 "휴가 신청은 어디서 해요?"처럼 짧고, 문서는 "연차는 인사 시스템의 휴가 메뉴에서 신청한다. 반차는…"처럼 길다. 같은 방식으로 벡터를 만들면 짧은 질문과 비슷하게 짧은 문서가 유리해지는 식으로 어긋날 수 있다. 그래서 많은 모델이 질문용과 문서용을 나눠서 받는다.

나누는 방법은 모델마다 다르다. E5 계열은 문장 앞에 `query: `와 `passage: `를 붙이도록 학습됐다. 붙이지 않아도 돌아가지만 성능이 떨어진다. Cohere는 `input_type`(`search_query`, `search_document`, `classification`, `clustering`)을, Gemini는 `task_type`(`RETRIEVAL_QUERY`, `RETRIEVAL_DOCUMENT`, `CLASSIFICATION` 등)을 요청에 넣는다. Jina v3는 과제별 어댑터를 `task`로 고른다. OpenAI의 `text-embedding-3` 계열은 이런 구분 없이 같은 방식으로 넣는다.

## 정규화와 거리 재기

임베딩 벡터끼리의 가까움은 보통 코사인 유사도로 잰다. 두 벡터가 가리키는 방향이 얼마나 같은지만 보고, 길이는 무시한다. 내적(dot product)은 방향과 길이를 함께 본다. 둘은 벡터 길이가 모두 1일 때만 같다.

이게 왜 중요한지 정규화하지 않은 벡터로 계산해 봤다. 질문 `[1, 0.2]`에 대해, 방향은 거의 같지만 짧은 문서와 방향은 덜 맞지만 긴 문서를 비교했다.

```js
// norm.mjs: 정규화하지 않은 벡터에서 내적과 코사인이 순위를 다르게 매기는 장면
const dot = (a, b) => a.reduce((s, x, i) => s + x * b[i], 0);
const len = (a) => Math.sqrt(dot(a, a));
const cos = (a, b) => dot(a, b) / (len(a) * len(b));
const q = [1, 0.2];
const docs = { "짧은 정답 문서": [0.9, 0.25], "긴 엉뚱한 문서": [2.0, 1.8] };
for (const [k, v] of Object.entries(docs))
  console.log(k.padEnd(10), "길이", len(v).toFixed(3), " 내적", dot(q, v).toFixed(3), " 코사인", cos(q, v).toFixed(3));
```

```text
짧은 정답 문서   길이 0.934  내적 0.950  코사인 0.997
긴 엉뚱한 문서   길이 2.691  내적 2.360  코사인 0.860
```

코사인으로는 짧은 정답 문서가 0.997로 1등인데, 내적으로는 긴 엉뚱한 문서가 2.360으로 1등이다. 길이가 순위를 뒤집었다. OpenAI 임베딩처럼 API가 처음부터 길이 1로 정규화해 돌려주면 이런 일이 없지만, 직접 띄운 모델이나 차원을 잘라 받은 벡터는 정규화돼 있지 않을 수 있다.

그래서 규칙을 정해 둔다. 저장하기 전에 모든 벡터를 길이 1로 정규화하고, 벡터 DB의 거리 함수는 그에 맞게 고른다. pgvector라면 코사인 거리(`<=>`)를 쓰거나, 정규화를 보장한 뒤 내적(`<#>`, 음수 내적을 돌려준다)을 써서 계산을 아낀다. 정규화한 벡터에서는 유클리드 거리로 매긴 순위도 코사인과 같다. 무엇을 쓰든 색인할 때와 검색할 때 같은 거리를 쓰는 게 먼저다. 인덱스를 코사인용 연산자 클래스로 만들어 놓고 검색은 내적으로 하면 인덱스를 타지 않는다.

## 차원을 줄여도 쓸 만한 벡터

앞의 용량 계산에서 3072차원은 부담스럽다. 그런데 최근 모델 다수는 벡터를 앞에서부터 잘라 써도 품질이 크게 떨어지지 않게 학습돼 있다. 이걸 마트료시카 표현 학습(Matryoshka Representation Learning)이라고 부른다. 큰 인형 안에 작은 인형이 들어 있듯, 3072차원 벡터의 앞 256개만 떼어도 그 자체로 쓸 만한 벡터가 되도록 학습 단계에서 여러 길이의 손실을 함께 줄인다.

OpenAI `text-embedding-3` 계열은 `dimensions` 파라미터로, Gemini는 `outputDimensionality`로 줄인 벡터를 받는다. Jina v3, 일부 공개 모델도 같은 방식을 지원한다. 지원하지 않는 모델의 벡터를 앞에서 자르면 품질이 크게 떨어지니, 모델 카드에서 Matryoshka 지원 여부를 먼저 확인한다.

줄일 때 지킬 것이 있다. 잘라 낸 벡터는 길이가 1이 아니니 다시 정규화한다(앞 절의 함정). 얼마나 줄일지는 내 평가 세트로 정한다. 3072, 1024, 512, 256차원으로 같은 질문을 돌려 recall@k가 어디서 꺾이는지 보고, 꺾이기 직전을 고른다. 차원을 줄이는 대신 값의 정밀도를 줄이는 방법도 있다. float32를 int8로 바꾸면 앞의 표처럼 4분의 1이 되고, 벡터 DB에 따라 이진 양자화(차원당 1비트)까지 지원한다. 둘을 함께 쓰는 경우도 많다. 작게 줄인 벡터로 후보를 넉넉히 뽑고, 원래 벡터로 다시 줄 세우는 방식이다.

## 내 데이터로 시험지를 만든다

후보 모델을 세 개로 줄였다면 내 데이터로 비교한다. 처음 사고는 모델 카드를 읽지 않은 탓도 있지만, 영어 시험만 보고 고른 탓이 더 컸다.

시험지는 실제 질문으로 만든다. 검색 로그가 있으면 거기서 50~100개를 고르고, 없으면 문서를 읽고 사람이 물을 법한 질문을 쓴다. 질문마다 정답 문서를 표시해 둔다. 쉬운 질문만 고르지 말고, 문서와 다른 단어를 쓴 질문("휴가" ↔ "연차"), 짧은 질문, 영어 약어가 섞인 질문, 오타가 있는 질문을 섞는다.

각 모델로 문서를 색인하고 질문을 돌려 recall@k와 MRR 같은 지표를 계산한다. 지표를 계산하는 법과 검색 품질 실험은 [RAG 검색 품질 글](/posts/rag-retrieval-quality)에서 숫자로 다뤘으니 같은 방법을 쓰면 된다. 점수 말고도 같이 잰다. 문서 1만 개를 색인하는 데 걸린 시간, 질문 하나의 임베딩 지연, 차원별 저장 크기다.

비교할 때는 한 번에 하나만 바꾼다. 모델을 바꾸면서 청크 크기도 바꾸면 무엇 때문에 좋아졌는지 모른다. 그리고 모델 하나를 고르고 끝내지 말고, 이 시험지를 저장소에 남겨 둔다. 모델을 바꿀 때, 청크 규칙을 바꿀 때, 문서가 크게 늘었을 때 다시 돌린다.

예시가 수백 개 이상 쌓이면 임베딩을 입력으로 로지스틱 회귀 같은 작은 분류기를 학습시키는 쪽이 대개 더 정확하고 빠르다. 임베딩 모델은 그대로 두고 그 위에 가벼운 모델만 얹는 방식이라 학습도 몇 초면 끝난다. LLM에게 분류를 맡기는 것과 비교하면 요청당 비용과 지연이 훨씬 작고, 같은 입력에 늘 같은 답이 나온다. 대신 라벨 정의가 바뀌면 예시를 다시 모아야 한다. 라벨이 자주 바뀌고 문의량이 적다면 LLM 분류가, 라벨이 안정적이고 양이 많다면 임베딩 분류가 맞다.

라벨 없이 묶는 군집(clustering)도 같은 벡터로 한다. 지난달 문의 1만 건을 k-means나 HDBSCAN 같은 알고리즘으로 묶으면, 미리 정하지 않은 문의 유형이 무리로 드러난다. 무리마다 대표 문장 몇 개를 뽑아 사람이 이름을 붙이면 새 라벨 후보가 된다.

## 무리에서 먼 점을 찾는다

그림의 '결제창 해킹?'처럼 어느 무리와도 먼 점은 처음 보는 종류의 입력일 가능성이 높다. 이상 탐지에 쓸 수 있다. 가장 단순한 점수는 "가장 가까운 이웃 k개와의 평균 유사도"를 1에서 뺀 값이다. 클수록 외딴 점이다.

```js
// anomaly.mjs: 가장 가까운 이웃 k개와의 평균 코사인으로 이상 점수를 매긴다
const dot = (a, b) => a.reduce((s, x, i) => s + x * b[i], 0);
const cos = (a, b) => dot(a, b) / Math.sqrt(dot(a, a) * dot(b, b));
const logs = {
  "배송 지연 1": [0.9, 0.1, 0.0], "배송 지연 2": [0.8, 0.3, 0.1], "배송 지연 3": [0.85, 0.2, 0.05],
  "환불 문의 1": [0.2, 0.9, 0.1], "환불 문의 2": [0.1, 0.8, 0.3], "환불 문의 3": [0.15, 0.85, 0.2],
  "새로운 문의": [0.1, 0.1, 0.95],
};
const K = 2;
for (const [name, v] of Object.entries(logs)) {
  const sims = Object.entries(logs).filter(([n]) => n !== name).map(([, u]) => cos(v, u)).sort((a, b) => b - a);
  const score = 1 - sims.slice(0, K).reduce((a, b) => a + b, 0) / K;   // 클수록 이상
  console.log(name.padEnd(8), "score", score.toFixed(3));
}
```

```text
배송 지연 1  score 0.023
배송 지연 2  score 0.024
배송 지연 3  score 0.009
환불 문의 1  score 0.021
환불 문의 2  score 0.022
환불 문의 3  score 0.009
새로운 문의   score 0.603
```

무리 안의 점은 0.01~0.02대인데 새로운 문의는 0.603이다. 실제로는 이렇게 깔끔하게 갈리지 않는다. 임베딩 공간에서 유사도 값의 분포는 모델마다 달라서, 어떤 모델은 상관없는 문장끼리도 코사인이 0.7을 넘는다. 그래서 고정된 임계값을 쓰지 말고, 평소 데이터의 점수 분포를 재서 상위 1%처럼 분위수로 임계값을 정한다.

쓰임은 여럿이다. 고객 문의에서 새로운 장애 유형이 생기는 걸 일찍 알아채거나, 로그 메시지 중 처음 보는 패턴을 골라내거나, RAG에 들어온 질문 중 문서 어디와도 먼 질문(답할 근거가 없는 질문)을 걸러 "모른다"로 보내는 데 쓴다. 마지막 쓰임은 특히 실용적이다. 검색 1등의 유사도가 평소 분포보다 낮으면 답을 지어내게 두지 말고 범위 밖으로 처리한다.

한계도 알아 둔다. 임베딩은 뜻의 가까움을 잴 뿐, 숫자나 형식의 이상(금액이 평소의 100배, 같은 IP에서 1초에 500건)은 잡지 못한다. 그런 건 기존의 수치 기반 탐지가 맞다. 임베딩 이상 탐지는 "글의 내용이 처음 보는 종류인가"에만 쓴다.

## 좋아한 것의 근처를 추천한다

추천도 같은 원리다. 사용자가 읽은 글들의 벡터를 평균 내면 그 사용자의 관심이 어느 방향인지 나타내는 벡터가 된다. 아직 안 읽은 글 중 그 벡터와 가까운 것을 고른다.

```js
// rec.mjs: 읽은 글 벡터의 평균으로 사용자 벡터를 만들고 안 읽은 글을 줄 세운다
const dot = (a, b) => a.reduce((s, x, i) => s + x * b[i], 0);
const norm = (a) => { const l = Math.sqrt(dot(a, a)); return a.map((x) => x / l); };
const items = {
  "Redis 캐시": [0.9, 0.1, 0.1], "CDN 캐시": [0.8, 0.2, 0.3], "DB 인덱스": [0.3, 0.9, 0.1],
  "쿼리 튜닝": [0.2, 0.8, 0.2], "CSS 그리드": [0.1, 0.1, 0.9],
};
const read = ["Redis 캐시", "DB 인덱스"];
const user = norm(read.map((k) => norm(items[k])).reduce((a, v) => a.map((x, i) => x + v[i])).map((x) => x / read.length));
console.log("user", user.map((x) => x.toFixed(3)).join(", "));
Object.entries(items).filter(([k]) => !read.includes(k))
  .map(([k, v]) => [k, dot(user, norm(v))]).sort((a, b) => b[1] - a[1])
  .forEach(([k, s]) => console.log(k.padEnd(8), s.toFixed(3)));
```

```text
user 0.771, 0.624, 0.127
CDN 캐시   0.889
쿼리 튜닝    0.800
CSS 그리드  0.279
```

캐시 글과 인덱스 글을 읽은 사용자에게 CDN 캐시(0.889)와 쿼리 튜닝(0.800)이 위로, CSS 그리드(0.279)가 아래로 간다. 클릭 기록이 하나도 없는 새 글도 내용만으로 벡터가 생기니 바로 추천 후보가 된다. 협업 필터링(비슷한 사용자가 본 것을 추천)이 약한 콜드 스타트를 내용 기반 추천이 메워 주는 지점이다.

평균 벡터의 약점도 이 결과에 보인다. 관심사가 둘(캐시, DB)인 사용자의 평균은 둘 사이 어딘가를 가리켜서, 관심이 셋, 넷으로 갈라지면 어느 쪽에도 가깝지 않은 방향이 된다. 그래서 실제로는 최근에 읽은 글마다 따로 이웃을 찾아 합치거나, 사용자 벡터를 관심사별로 여러 개 두거나, 오래된 기록의 가중치를 줄인다. 그리고 내용이 비슷한 것만 계속 추천하면 같은 주제만 맴돈다. 임베딩 유사도는 후보를 뽑는 단계에 쓰고, 최종 순위는 클릭과 체류 시간 같은 행동 신호를 더해 정하는 구성이 흔하다.

## 모델을 바꾸면 모든 벡터를 다시 만든다

임베딩 모델을 바꿀 때 가장 크게 놀라는 부분이 이것이다. 모델 A의 벡터와 모델 B의 벡터는 서로 비교할 수 없다. 차원이 같아도 각 축이 뜻하는 바가 다르다. 같은 회사의 다음 버전 모델도 마찬가지다. 그래서 모델을 바꾸면 문서 전체를 새 모델로 다시 임베딩하고 인덱스를 새로 만들어야 한다. 질문만 새 모델로 바꾸고 문서는 옛 벡터 그대로 두면, 오류 없이 엉터리 결과가 나온다.

재색인 비용은 앞에서 계산한 요금보다 시간과 운영이 크다. 문서 100만 개를 API로 다시 임베딩하면 요금은 수십 달러지만, 공급사의 분당 요청 한도 안에서 나눠 보내야 하니 몇 시간에서 며칠이 걸릴 수 있다. 그동안 검색 서비스는 계속 돌아야 한다. 이럴 때 쓰는 순서가 있다.

1. 벡터마다 만든 모델 이름, 버전, 차원, 과제 설정을 함께 저장해 둔다. 처음부터 해 둬야 나중에 섞이지 않는다.
2. 새 모델로 새 인덱스를 따로 만든다. 그동안 들어오는 새 문서와 수정된 문서는 옛 인덱스와 새 인덱스 둘 다에 쓴다.
3. 새 인덱스가 다 차면 평가 세트를 돌려 옛 모델보다 나은지 확인한다. 일부 트래픽만 새 인덱스로 보내 실제 지표도 비교한다.
4. 검색을 새 인덱스로 바꾸고, 문제가 없으면 옛 인덱스를 지운다. 바로 지우지 말고 되돌릴 시간을 둔다.

벡터 DB를 고르는 단계에서도 이걸 염두에 둔다. 인덱스를 두 벌 동시에 둘 저장 공간이 있는지, 인덱스를 이름으로 바꿔 끼울 수 있는지(별칭 같은 기능), 대량 적재가 얼마나 빠른지가 모델 교체의 난이도를 정한다. API형 모델은 공급사가 옛 모델의 지원 종료를 발표하면 내 일정과 상관없이 이 작업을 해야 한다는 점도 비용에 넣는다.

## 벡터 옆에 모델 이름을 적어 두는 테이블

위 순서의 1번을 PostgreSQL 16과 pgvector(여기서는 0.6.0)로 해 봤다. 문서 테이블과 벡터 테이블을 나누고, 벡터 테이블의 기본 키를 `(doc_id, model)`로 잡아 한 문서에 모델별 벡터가 따로 들어가게 했다. 교체 기간에 옛 벡터와 새 벡터가 한 테이블에 함께 산다.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE docs (
  id    bigint PRIMARY KEY,
  title text NOT NULL
);

CREATE TABLE doc_embeddings (
  doc_id    bigint NOT NULL REFERENCES docs(id),
  model     text   NOT NULL,              -- 벡터를 만든 모델과 버전
  task      text   NOT NULL,              -- 접두어·과제 설정 (passage, RETRIEVAL_DOCUMENT 등)
  dims      int    NOT NULL,
  embedding vector NOT NULL,              -- 차원을 고정하지 않아 여러 모델을 한 테이블에 둔다
  PRIMARY KEY (doc_id, model),
  CHECK (vector_dims(embedding) = dims)   -- 적어 둔 차원과 실제 차원이 다르면 거절
);
```

문서 세 개에 옛 모델(`m-old`)과 새 모델(`m-new`)의 벡터를 넣었다. 설명용 3차원 벡터이고, 두 모델은 같은 문서를 전혀 다른 방향에 찍는다. 그리고 새 모델로 만든 질문 벡터로 검색했다. 첫 번째는 모델을 거르지 않은 쿼리, 두 번째는 같은 모델만 고른 쿼리다.

```sql
-- (1) 모델을 거르지 않고 찾으면
SELECT d.title, e.model, round((e.embedding <=> '[0.90, 0.33, 0.28]')::numeric, 3) AS cos_dist
FROM doc_embeddings e JOIN docs d ON d.id = e.doc_id
ORDER BY e.embedding <=> '[0.90, 0.33, 0.28]' LIMIT 3;

-- (2) 같은 모델의 벡터만 찾으면
SELECT d.title, round((e.embedding <=> '[0.90, 0.33, 0.28]')::numeric, 3) AS cos_dist
FROM doc_embeddings e JOIN docs d ON d.id = e.doc_id
WHERE e.model = 'm-new'
ORDER BY e.embedding <=> '[0.90, 0.33, 0.28]' LIMIT 3;
```

```text
        title        | model | cos_dist 
---------------------+-------+----------
 연차 사용 안내      | m-new |    0.001
 서버 증설 요청 절차 | m-old |    0.011
 출장비 정산         | m-old |    0.344
(3 rows)

        title        | cos_dist 
---------------------+----------
 연차 사용 안내      |    0.001
 출장비 정산         |    0.439
 서버 증설 요청 절차 |    0.602
(3 rows)
```

첫 결과의 2등을 보자. 옛 모델의 "서버 증설 요청 절차" 벡터가 거리 0.011로 붙었다. 새 모델 기준으로는 0.602나 떨어진 문서다. 두 모델의 좌표를 한 공간에 놓고 잰 값이라 숫자 자체에 뜻이 없다. 오류도 나지 않는다. 그래서 모든 검색 쿼리에 `WHERE model = ...`이 빠지지 않게 하고, 차원을 잘못 넣는 실수는 `CHECK` 제약이 막는다. 2차원 벡터를 넣어 보면 `violates check constraint "doc_embeddings_check"`로 거절된다.

인덱스는 모델마다 따로 만든다. 차원을 고정하지 않은 `vector` 열에는 HNSW 인덱스를 바로 만들 수 없어서, 차원을 정한 식(`embedding::vector(3)`)과 모델 조건을 붙인 부분 인덱스로 만든다. 실제로는 3 대신 그 모델의 차원을 쓴다.

```sql
CREATE INDEX doc_emb_new_hnsw ON doc_embeddings
  USING hnsw ((embedding::vector(3)) vector_cosine_ops)
  WHERE model = 'm-new';
```

이 인덱스를 타려면 쿼리도 같은 식으로 써야 한다. 행이 여섯 개뿐이라 순차 스캔을 끄고(`SET enable_seqscan = off`) 두 쿼리의 계획을 비교했다.

```text
-- ORDER BY embedding <=> '[0.90, 0.33, 0.28]'
 Limit
   ->  Sort
         Sort Key: ((embedding <=> '[0.9,0.33,0.28]'::vector))
         ->  Index Scan using doc_embeddings_pkey on doc_embeddings
               Index Cond: (model = 'm-new'::text)

-- ORDER BY embedding::vector(3) <=> '[0.90, 0.33, 0.28]'
 Limit
   ->  Index Scan using doc_emb_new_hnsw on doc_embeddings
         Order By: ((embedding)::vector(3) <=> '[0.9,0.33,0.28]'::vector)
```

캐스팅이 없는 첫 쿼리는 기본 키 인덱스로 모델만 거른 뒤 모든 행의 거리를 계산해 정렬(`Sort`)한다. 문서가 100만 개면 100만 번 계산이다. 캐스팅을 맞춘 두 번째 쿼리는 HNSW 인덱스가 거리 순서대로 바로 꺼내 준다(`Order By`가 인덱스 스캔 안에 있다). 인덱스를 만들어 두고도 느리다면 계획에 `Sort`가 있는지부터 본다.

## 검색이 이상할 때 먼저 의심할 곳

"상관없는 문서가 늘 위에 온다"면 언어와 모델 카드부터 본다. 처음 사고처럼 영어 모델에 한국어를 넣고 있을 수 있다. 질문 몇 개를 넣고 1등 유사도 값을 보면, 상관없는 문서와의 유사도가 정답 문서와 거의 같은 값으로 붙어 있는 경우가 많다.

"긴 문서의 뒷부분 내용으로는 검색이 안 된다"면 최대 입력 길이를 넘어 잘린 것이다. 청크 크기를 토큰으로 세어 모델 한도와 비교한다.

"어제까지 잘 되다가 갑자기 엉망이 됐다"면 질문과 문서의 모델이나 설정이 어긋났는지 본다. 검색 서버의 모델 설정만 바뀌었거나, 접두어나 과제 종류가 한쪽만 바뀌었거나, 차원을 줄여 받으면서 정규화를 빼먹은 경우다. 벡터 옆에 저장한 모델 이름과 지금 검색 서버의 설정을 비교한다.

"정확한 이름이나 코드 번호로 찾으면 안 나온다"면 임베딩의 한계다. 임베딩은 뜻을 잡는 데 강하고 정확한 문자열 일치에는 약하다. 오류 코드, 제품 번호, 사람 이름이 중요한 검색이라면 키워드 검색(BM25)을 함께 쓰는 하이브리드 검색으로 보완한다.

## 지도를 고르는 일

임베딩 모델을 고르는 일은 내 글이 찍힐 지도를 고르는 일이다. 언어, 최대 입력 길이, 차원, 공개 점수, 비용을 보고 후보를 줄인 뒤, 내 질문과 문서로 만든 시험지로 정한다. 질문과 문서에는 모델이 요구하는 접두어나 과제 설정을 지키고, 저장 전에 정규화하고, 필요하면 Matryoshka로 차원을 줄인다. 그렇게 만든 지도는 검색 말고도 분류, 군집, 이상 탐지, 추천에 그대로 쓰인다. 그리고 지도를 바꾸면 모든 점을 다시 찍어야 하니, 벡터마다 어느 지도의 좌표인지 처음부터 적어 둔다.

## 면접에서 나올 만한 질문

### 임베딩 모델은 무엇을 기준으로 고르나요?

내 데이터의 언어를 학습했는지, 최대 입력 길이가 청크 크기를 감당하는지, 차원에 따른 저장·검색 비용, MTEB 같은 공개 점수, API 요금이나 서버 비용을 본다. 공개 점수는 여러 과제의 평균이라 내 과제와 다를 수 있으니 후보를 줄이는 데만 쓰고, 실제 질문 50~100개와 정답 문서로 만든 시험지에서 recall@k를 재서 정한다. 데이터를 외부로 보낼 수 없다면 직접 띄우는 모델로 범위가 먼저 좁혀진다.

### 영어로 학습된 임베딩 모델을 한국어 문서에 쓰면 어떻게 되나요?

오류 없이 돌지만 결과가 나빠진다. 토크나이저가 한국어를 잘게 쪼개고, 학습 때 한국어 문장끼리 뜻이 가깝다는 신호를 거의 받지 못해서 뜻이 다른 문장도 비슷한 자리에 찍힌다. 그래서 질문과 상관없이 같은 문서들이 늘 위에 오는 증상이 보인다. 모델 카드에서 학습 언어를 확인하고 다국어나 한국어 평가가 있는 모델을 고른다.

### 질문과 문서에 다른 접두어나 input_type을 쓰는 이유는?

검색에서 질문은 짧고 문서는 길어 생김새가 다르기 때문에, 많은 모델이 둘을 다르게 인코딩하도록 학습됐다. E5는 query와 passage 접두어, Cohere는 input_type, Gemini는 task_type으로 구분한다. 설정을 틀려도 결과가 완전히 망가지지는 않아 눈치채기 어렵고, 색인 쪽과 검색 쪽이 따로 있으면 한쪽만 바뀌기 쉬우니 설정 한곳에서 관리하고 평가 세트로 확인한다.

### 코사인 유사도와 내적은 언제 같고, 왜 정규화하나요?

벡터 길이가 모두 1일 때 둘은 같다. 정규화하지 않으면 내적은 길이가 긴 벡터를 유리하게 만들어, 계산해 보니 방향이 거의 같은 문서(코사인 0.997)보다 길이만 긴 문서(코사인 0.860)가 내적으로 1등이 됐다. 저장 전에 모두 정규화해 두면 계산이 싼 내적을 써도 코사인과 같은 순위가 나온다. 색인과 검색에 같은 거리 함수를 쓰는 것도 지켜야 인덱스를 탄다.

### 차원을 줄이고 싶을 때 어떻게 하나요?

Matryoshka 방식으로 학습된 모델은 벡터를 앞에서부터 잘라도 쓸 만하다. OpenAI의 dimensions, Gemini의 outputDimensionality처럼 API에서 줄인 벡터를 바로 받을 수 있다. 자른 벡터는 다시 정규화하고, 몇 차원까지 줄일지는 평가 세트의 recall@k가 꺾이는 지점으로 정한다. 지원하지 않는 모델을 자르면 품질이 크게 떨어진다. 정밀도를 int8이나 이진으로 낮추는 양자화와 함께 쓰기도 한다.

### 임베딩으로 분류를 할 때 LLM 분류와 비교하면 어떤가요?

라벨이 붙은 예시를 임베딩해 kNN이나 작은 분류기를 얹으면, 요청당 비용과 지연이 LLM보다 훨씬 작고 같은 입력에 늘 같은 답이 나온다. 대신 라벨 정의가 바뀌면 예시를 다시 모아야 한다. kNN은 라벨별 예시 수가 다르면 k가 클수록 많은 라벨로 쏠리니 예시 수를 맞추거나 중심점 방식을 쓴다. 라벨이 자주 바뀌고 양이 적으면 LLM, 안정적이고 양이 많으면 임베딩이 맞다.

### 임베딩으로 이상 탐지나 추천을 한다면 어떻게 하나요?

이상 탐지는 가장 가까운 이웃들과의 평균 유사도가 낮은 점을 찾는다. 유사도 분포가 모델마다 다르니 고정 임계값 대신 평소 데이터의 분위수로 정하고, 숫자나 빈도의 이상은 기존 수치 탐지에 맡긴다. 추천은 읽은 글 벡터의 평균과 가까운 안 읽은 글을 고르는 내용 기반 방식이라 새 글의 콜드 스타트에 강하다. 관심사가 여러 갈래면 평균이 흐려지니 최근 글별로 이웃을 찾거나 벡터를 여러 개 두고, 최종 순위는 행동 신호와 섞는다.

### 임베딩 모델을 교체하면 무엇을 해야 하나요?

모델이 다르면 차원이 같아도 벡터를 비교할 수 없어서 문서 전체를 새 모델로 다시 임베딩해야 한다. 질문만 바꾸면 오류 없이 엉터리 결과가 나온다. 벡터마다 모델 이름과 버전, 차원, 과제 설정을 저장해 두고, 새 인덱스를 따로 만들며 그동안의 변경은 양쪽에 쓴다. 평가 세트와 일부 트래픽으로 확인한 뒤 바꿔 끼우고, 옛 인덱스는 되돌릴 시간을 둔 뒤 지운다.
