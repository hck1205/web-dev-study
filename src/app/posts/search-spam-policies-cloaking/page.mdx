## 봇에게만 다른 HTML을 주면 클로킹일까

SPA로 만든 쇼핑몰이 검색에 잘 안 나와서, 크롤러에게만 미리 렌더링한 HTML을 주는 동적 렌더링을 붙이자는 이야기가 나왔다. 요청의 User-Agent를 보고 구글봇이면 프리렌더 서버의 HTML을, 사람이면 원래의 빈 HTML과 자바스크립트를 준다. 회의에서 누군가 묻는다. "그거 클로킹 아니에요? 구글이 벌 준다던데."

결론부터 말하면, 내용이 같으면 클로킹이 아니다. 구글 문서도 동적 렌더링이 사람과 봇에게 비슷한 내용을 주는 한 클로킹으로 보지 않는다고 적는다. 클로킹은 "검색 엔진과 사람에게 다른 내용을 보여 주어 순위를 조작하는 것"이다. 기준은 기술이 아니라 내용과 의도다. 다만 같은 문서에서 구글은 동적 렌더링을 임시 해결책으로 부르고 장기적으로 권하지 않는다. SSR이나 SSG로 사람과 봇에게 같은 HTML을 주는 편이 낫다는 것이다. 렌더링 방식 고르는 법은 [SPA와 SEO](/posts/seo-for-spa)에 있다.

문제는 의도하지 않은 차이다. 프리렌더 캐시가 오래돼 봇은 지난주 가격을 보고 사람은 오늘 가격을 본다. 프리렌더 서버가 타임아웃이 나서 봇에게만 빈 페이지나 오류 페이지가 간다. 봇용 HTML에만 "SEO용 설명 문단"을 몰래 덧붙인다. 앞의 둘은 품질 문제이고, 마지막 하나는 정말 클로킹이다.

이 글은 이런 경계선을 개발자 관점에서 정리한다. 구글의 스팸 정책 중 개발자가 실수로 밟기 쉬운 것, 해킹으로 남이 내 사이트에 심는 스팸, 대량 생성 콘텐츠와 평판 악용 같은 최근 정책, 그리고 벌을 받았을 때 수동 조치와 알고리즘 하락을 구분해 회복하는 법까지 간다.

## 동적 렌더링을 붙인다면 지킬 것

그래도 당장 SSR로 옮길 수 없어 동적 렌더링을 붙인다면, 클로킹처럼 보이는 차이가 생기지 않게 몇 가지를 지킨다. Next.js의 미들웨어(16에서는 `proxy.ts`)나 Nginx에서 봇 요청만 프리렌더 서버로 보내는 구조를 예로 든다.

```ts
// proxy.ts (Next.js 16. 15 이하는 middleware.ts): 봇 요청만 프리렌더 서버로 넘긴다
import { NextResponse, type NextRequest } from "next/server";

const BOT_UA = /googlebot|bingbot|yeti|slurp|duckduckbot|facebookexternalhit|twitterbot|slackbot/i;

export function proxy(request: NextRequest) {
  const ua = request.headers.get("user-agent") ?? "";
  if (!BOT_UA.test(ua)) return NextResponse.next();

  const target = new URL(`https://prerender.internal${request.nextUrl.pathname}${request.nextUrl.search}`);
  const res = NextResponse.rewrite(target);
  res.headers.set("Vary", "User-Agent"); // 캐시가 봇용 응답을 사람에게 주지 않게
  return res;
}
```

첫째, `Vary: User-Agent`를 단다. 이게 없으면 CDN이 봇에게 준 프리렌더 HTML을 같은 주소로 들어온 사람에게, 혹은 사람용 빈 HTML을 봇에게 캐시로 줄 수 있다. 어느 쪽이든 사람과 봇이 보는 게 엉킨다. UA마다 캐시가 갈리면 캐시 효율이 떨어지니, CDN에서 UA를 "봇/사람" 두 값으로 정규화해 캐시 키로 쓰는 방법도 있다.

둘째, 프리렌더 결과의 신선도를 정한다. 가격과 재고가 바뀌는 페이지라면 캐시 시간을 짧게 두거나 상품이 바뀔 때 프리렌더 캐시를 지운다.

셋째, 프리렌더가 실패했을 때 봇에게 무엇을 줄지 정한다. 타임아웃이 나면 빈 페이지 200을 주지 말고 원래 사람용 HTML을 주거나 503으로 다음에 다시 오게 한다. 빈 200은 소프트 404나 빈약한 페이지로 색인된다.

넷째, 봇용 HTML에만 들어가는 내용을 만들지 않는다. "SEO용 문단"을 봇에게만 덧붙이는 순간 동적 렌더링은 클로킹이 된다. 리뷰에서 봇 분기 코드는 따로 보고, 봇용과 사람용 렌더링 결과의 본문 텍스트를 정기적으로 비교한다. 비교 방법은 아래 해킹 확인과 같다.

## 스팸 정책이 겨냥하는 것

구글은 검색 결과에 나오기 위한 기본 요건을 "Google 검색 필수사항(Search Essentials)"으로 정리하고, 그 안에 스팸 정책 목록을 둔다. 목록은 이렇다. 클로킹, 도어웨이, 만료 도메인 악용, 해킹된 콘텐츠, 숨겨진 텍스트와 링크, 키워드 반복, 링크 스팸, 자동 생성 트래픽, 멀웨어와 악성 행동, 오해를 일으키는 기능, 대량 생성 콘텐츠 악용, 스크래핑, 몰래 리다이렉트, 사이트 평판 악용, 빈약한 제휴 페이지, 사용자 생성 스팸. 법적 삭제 요청이나 개인 정보 삭제, 사기 같은 항목도 함께 있다.

정책마다 공통으로 묻는 건 하나다. 이 페이지가 사람에게 도움이 되려고 있는가, 아니면 검색 순위를 얻으려고 있는가. 같은 기술이 어느 쪽에 쓰였느냐로 판정이 갈린다. 텍스트를 감추는 CSS도 아코디언에 쓰면 정상이고 키워드 목록을 숨기는 데 쓰면 스팸이다.

정책 위반은 두 가지 방식으로 처리된다. 하나는 사람이 검토해서 내리는 수동 조치다. Search Console에 알림이 오고 이유가 적혀 있다. 다른 하나는 알고리즘이다. 구글은 SpamBrain이라는 머신러닝 기반 스팸 탐지 시스템을 쓰고, 이 시스템과 순위 시스템이 스팸으로 판단한 페이지나 링크의 효과를 낮춘다. 이쪽은 알림이 없다. 둘의 차이와 회복 방법은 뒤에서 다시 본다.

## 사람과 봇이 같은 것을 보는가

클로킹 의심을 받는 개발 상황을 모아 보면 대부분 "요청을 보고 다른 응답을 주는" 코드다. 하나씩 경계를 짚는다.

동적 렌더링과 프리렌더. 앞에서 본 대로 같은 내용이면 괜찮다. 대신 프리렌더 결과를 정기적으로 사람 화면과 비교한다. 캐시가 낡으면 봇은 품절 상품을 재고 있음으로 보고, 구조화 데이터의 가격과 화면 가격이 달라져 리치 결과 자격도 잃는다.

지역과 언어. 구글봇은 주로 미국 IP에서 크롤한다. IP로 국가를 판단해 미국 사용자에게 미국 페이지를 주는 사이트라면, 구글봇이 미국 페이지를 받는 건 클로킹이 아니다. 미국 사람과 같은 대우이기 때문이다. 반대로 "구글봇이면 한국 페이지를 준다"처럼 봇만 따로 대우하는 규칙을 만들면 그때부터 봇과 사람이 다른 것을 보는 상황이 된다. 언어별 페이지는 IP로 바꾸지 말고 주소를 나누고 `hreflang`으로 연결하는 게 정석이다.

페이월. 유료 기사 본문을 봇에게는 전부, 사람에게는 앞부분만 주면 겉보기로는 클로킹이다. 구글은 이 경우를 위해 구조화 데이터로 유료 영역을 표시하는 방법을 둔다. `isAccessibleForFree`를 `false`로 두고 `hasPart`의 `cssSelector`로 유료 부분을 가리키면, 구글이 의도된 페이월로 알아본다. 형식은 [구조화 데이터와 JSON-LD](/posts/structured-data-json-ld)에 있다.

로그인과 개인화. 로그인한 사람에게 추천 상품을 더 보여 주는 건 문제가 없다. 구글봇은 늘 비로그인 첫 방문자로 오니, 비로그인 사용자가 보는 화면이 색인된다. 비로그인 사용자에게 보여 주지 않는 내용을 봇에게만 열어 주는 것이 문제다.

A/B 테스트. 사람마다 다른 버전을 주는 실험은 괜찮다. 구글봇을 특정 버전에 고정하거나 실험에서 빼는 코드는 넣지 않는다. 버전마다 주소가 다르면 원본을 가리키는 `canonical`을 두고, 리다이렉트로 나눈다면 302 같은 임시 리다이렉트를 쓴다. 실험이 끝나면 바로 정리한다. 실험 설계 자체는 [A/B 테스트](/posts/ab-testing)에서 다룬다.

코드 리뷰에서 눈여겨볼 모양은 이런 것이다.

```tsx
// 위험: 봇일 때만 보이는 내용. 의도와 상관없이 클로킹이다
export default function ProductPage({ product, isBot }: Props) {
  return (
    <main>
      <h1>{product.name}</h1>
      {isBot && <p>{product.seoKeywords.join(" ")}</p>}
    </main>
  );
}
```

`isBot` 같은 값이 렌더링 분기에 들어가 있으면 그 자체로 경고 신호다. 봇 여부는 프리렌더로 보낼지, 로그를 어떻게 남길지 같은 인프라 결정에만 쓰고, 화면에 무엇을 그릴지는 사람과 같은 규칙으로 정한다.

정리하면 질문은 늘 같다. 구글봇과, 같은 조건(같은 나라, 비로그인, 첫 방문)의 사람이 같은 내용을 보는가.

## 해킹된 사이트는 봇에게만 스팸을 보여 준다

내가 의도하지 않은 클로킹도 있다. 사이트가 해킹당해 공격자가 코드를 심는 경우다. 흔한 형태는 이렇다. 공격자는 사람에게는 원래 페이지를 그대로 보여 주고, 구글봇에게만 스팸 키워드와 스팸 사이트 링크를 보여 준다. 운영자는 아무 이상을 못 느끼는데 검색 결과에는 "정품 시계 최저가 레플리카" 같은 제목이 뜬다. 공격자는 남의 사이트가 쌓아 둔 신뢰를 빌려 스팸 사이트 순위를 올린다.

작게 흉내 내 보면 확인하는 방법도 보인다. UA에 Googlebot이 있으면 다른 HTML을 주는 서버를 로컬에 띄우고 `curl`의 `-A`로 UA를 바꿔 요청했다.

```bash
# 사람처럼 요청
curl -s http://localhost:4318/products/42 | grep -o '<title>[^<]*</title>'
# 구글봇 UA로 요청
curl -s -A 'Mozilla/5.0 (compatible; Googlebot/2.1; +http://www.google.com/bot.html)' \
  http://localhost:4318/products/42 | grep -o '<title>[^<]*</title>'
```

```text
<title>회색 울 코트 | Shop</title>
<title>정품 시계 최저가 레플리카</title>
```

이 방법은 UA만 보는 단순한 코드만 잡아낸다. 정교한 코드는 IP가 구글 대역인지까지 확인해서, 내 노트북에서 UA만 바꾼 요청에는 정상 페이지를 준다. 그래서 진짜 확인은 구글에게 맡긴다. Search Console의 URL 검사에서 실제 URL 테스트를 돌리면 구글의 크롤러가 구글 IP에서 가져간 HTML이 보인다. 거기에 내가 쓰지 않은 제목과 링크가 있으면 해킹이다.

다른 단서도 있다. `site:내도메인 레플리카`처럼 우리와 상관없는 단어로 검색해 보면 이상한 주소가 색인돼 있는 게 보인다. 일본어 키워드 해킹이라 불리는 유형은 일본어 스팸 페이지 수천 개를 새 주소로 만들어 내고, 공격자가 자기 Search Console 계정을 소유자로 추가해 sitemap을 제출하기도 한다. Search Console의 사용자 및 권한 목록에 모르는 계정이 있는지, 페이지 색인 보고서에 갑자기 새 주소가 수천 개 늘지 않았는지 본다. 접근 로그에서 구글봇에게만 다른 크기의 응답이 나가는 주소를 찾는 것도 방법이다(로그 분석은 [접근 로그와 Search Console](/posts/seo-log-file-analysis-search-console)에 있다).

서버에 직접 접근할 수 있다면 파일 쪽에서도 흔적을 찾는다. 아래는 Ubuntu 24.04에서 PHP 사이트를 흉내 낸 실험 디렉터리(여기서는 `/var/www/shop`)에 심어 둔 파일을 찾는 명령이다. 업로드 디렉터리에는 PHP 파일이 있을 이유가 없고, 해킹 코드는 대개 최근에 바뀐 파일이며, `base64_decode`나 UA 검사 같은 문자열을 품고 있다.

```bash
cd /var/www/shop
# 최근 일주일 사이에 바뀐 PHP 파일을 수정 시각과 함께 본다
find . -name '*.php' -newermt '2026-10-12' -printf '%TY-%Tm-%Td %TH:%TM  %p\n' | sort

# 업로드 디렉터리 안의 PHP 파일 (있으면 안 된다)
find ./wp-content/uploads -name '*.php'

# 흔한 해킹 코드 문자열이 든 파일
grep -rlE 'base64_decode|HTTP_USER_AGENT' --include='*.php' .
```

```text
2026-10-19 03:12  ./wp-content/uploads/2026/10/cache.php
2026-10-19 03:13  ./wp-includes/load.php
./wp-content/uploads/2026/10/cache.php
./wp-content/uploads/2026/10/cache.php
./wp-includes/load.php
```

새벽 3시 12분에 업로드 폴더에 PHP 파일이 생기고 1분 뒤 코어 파일이 바뀌었다. 첫 파일이 원격 명령을 받는 뒷문이고, 두 번째가 구글봇일 때만 스팸을 끼워 넣는 코드다. 수정 시각을 접근 로그와 맞추면 그 직전에 어떤 요청이 들어왔는지, 즉 침입 경로가 보인다. 정상 파일에도 `base64_decode`가 쓰이니 grep 결과는 후보일 뿐이고, 코어 파일은 배포본과 해시를 비교하는 게 확실하다. 컨테이너로 배포하는 사이트라면 실행 중인 파일 시스템을 읽기 전용으로 두는 것만으로도 이런 변조 대부분을 막는다.

모니터링을 자동화하고 싶다면, 같은 주소를 사람 조건과 봇 조건으로 가져와 본문 텍스트가 얼마나 겹치는지 재는 방법이 있다. 아래는 두 텍스트의 단어 집합이 겹치는 비율(자카드 유사도)을 구하는 함수다. 1이면 같고 0이면 하나도 겹치지 않는다.

## 숨긴 텍스트와 몰래 리다이렉트

숨긴 텍스트 정책은 사람에게는 안 보이고 검색 엔진에게만 읽히도록 텍스트나 링크를 숨기는 것을 막는다. 흰 바탕에 흰 글자, 화면 밖으로 밀어낸 키워드 목록, 글자 크기 0, 1픽셀 이미지에 걸린 링크가 고전적인 예다.

개발자가 걱정할 일은 반대 방향이다. 정상적으로 감춘 내용까지 스팸이 될까 봐서다. 구글 문서는 아코디언, 탭, 슬라이드처럼 사용자가 열어 볼 수 있게 감춘 내용은 정상이라고 설명한다. 모바일 우선 색인 이후로 탭 안의 내용도 색인된다. 스크린 리더용으로 화면에서만 감춘 텍스트(`sr-only` 같은 클래스)도 접근성을 위한 정상 패턴이다. 기준은 같다. 사람에게 도움이 되려고 감췄나, 검색 엔진을 속이려고 감췄나. 스크린 리더용 텍스트에 키워드 스무 개를 넣으면 같은 클래스라도 후자가 된다.

```html
<!-- 정상: 아이콘 버튼의 이름을 스크린 리더에게만 알려 준다 -->
<button type="button">
  <svg aria-hidden="true">...</svg>
  <span class="sr-only">장바구니에 담기</span>
</button>

<!-- 위반: 같은 클래스로 키워드를 숨긴다 -->
<span class="sr-only">코트 울코트 겨울코트 여성코트 코트추천 코트최저가</span>
```

두 코드의 CSS는 똑같다. 첫째는 화면을 볼 수 없는 사람에게 버튼이 무엇인지 알려 주고, 둘째는 아무에게도 도움이 되지 않는다. 검색 엔진은 이런 차이를 문맥으로 판단하고, 판단이 애매하면 숨긴 텍스트의 가치를 낮게 본다. 키워드를 숨겨서 얻는 건 거의 없고 잃을 건 있다.

몰래 리다이렉트는 검색 엔진에 보여 준 것과 다른 곳으로 사람을 보내는 것이다. 개발자가 실수로 만드는 경우는 드물지만, 남이 넣은 코드로 생기는 경우는 꽤 있다. 광고 스크립트나 서드파티 위젯이 모바일 사용자만 이상한 사이트로 보내는 일이 실제로 보고된다. 검색 결과에서 들어온 사람만(Referer가 구글인 경우만) 리다이렉트하는 해킹 코드도 흔하다. 운영자가 주소를 직접 쳐서 들어가면 멀쩡하니 발견이 늦다.

```bash
# 검색에서 들어온 사람인 척: Referer를 구글로, UA를 아이폰으로 바꿔 리다이렉트를 확인한다
curl -sI -e 'https://www.google.com/' \
  -A 'Mozilla/5.0 (iPhone; CPU iPhone OS 18_6 like Mac OS X) AppleWebKit/605.1.15' \
  https://shop.example.com/products/42 | grep -iE '^(HTTP|location)'
```

자바스크립트로 하는 리다이렉트는 `curl`로 보이지 않으니 실제 모바일 브라우저로 검색 결과에서 눌러 들어가 보는 것도 해야 한다. 정상적인 리다이렉트, 예를 들어 주소를 옮긴 301이나 로그인 페이지로 보내는 302는 이 정책과 상관없다. 리다이렉트를 올바르게 쓰는 법은 [리다이렉트와 사이트 이전](/posts/seo-redirects-site-migration)에 있다.

## 오해를 일으키는 기능과 멀웨어

오해를 일으키는 기능은 사이트가 할 수 없는 일을 할 수 있다고 속이는 것이다. 누르면 광고로 가는 가짜 "다운로드" 버튼, 작동하지 않는 "무료 변환기" 같은 것이다. 멀웨어 정책은 사용자 기기에 해를 끼치는 코드나 원치 않는 소프트웨어를 다룬다. 개발자에게 현실적인 위험은 공급망이다. 서드파티 스크립트나 npm 패키지가 탈취되어 방문자에게 악성 코드를 내려보내면, 구글 세이프 브라우징이 사이트를 위험하다고 표시하고 크롬이 경고 화면을 띄운다. Search Console 보안 문제 보고서에 그 내용이 나온다. 외부 스크립트에 SRI(`integrity` 속성)를 걸고 CSP로 스크립트 출처를 제한해 두면 이런 사고의 범위를 줄일 수 있다.

## 내 사이트에 남이 쓰는 스팸

댓글, 포럼, 사용자 프로필, 리뷰처럼 사용자가 내용을 쓰는 곳은 스패머의 좋은 표적이다. 프로필 소개란에 스팸 링크를 넣은 계정이 하루 수천 개씩 만들어지기도 한다. 이런 페이지가 많아지면 구글은 "사용자 생성 스팸" 수동 조치를 내릴 수 있다. 사이트 운영자가 직접 쓰지 않았어도 사이트의 책임이다.

막는 방법은 여러 겹이다.

- 사용자가 쓴 링크에는 `rel="ugc"`를 붙인다. 구글에 이 링크가 운영자가 보증한 게 아니라고 알린다. `nofollow`도 함께 써도 된다.
- 새 계정의 프로필 페이지는 일정 조건(활동 기간, 게시물 수)을 넘기 전까지 `noindex`로 둔다. 스팸 계정 대부분은 그 조건을 넘지 못한다.
- 가입과 글쓰기에 봇 차단(CAPTCHA, 속도 제한)을 둔다. 링크가 들어간 첫 글은 검토 대기로 보낸다.
- 스팸 단어와 스팸 도메인 목록으로 자동 걸러 낸다. Search Console 실적의 쿼리에 우리와 상관없는 단어가 늘면 경보로 쓴다.

링크 스팸 정책은 반대 방향, 내가 남의 사이트에 링크를 사거나 심는 쪽이다. 순위를 위해 돈을 주고 링크를 사는 것, 과도한 상호 링크 교환, 위젯이나 테마에 숨겨 배포하는 링크, 자동화된 링크 생성이 대상이다. 광고나 협찬 링크 자체는 괜찮다. `rel="sponsored"`를 붙이면 된다. 구글은 2016년 무렵부터 부자연스러운 링크를 대부분 사이트 전체를 벌주기보다 그 링크의 효과를 무시하는 쪽으로 처리한다고 설명해 왔다. 그래서 누군가 내 사이트로 스팸 링크를 잔뜩 걸어도 대개는 무시된다. 링크 거부(disavow) 도구는 아직 있지만 수동 조치를 받았거나 대량으로 링크를 산 기록이 있는 경우가 아니면 쓸 일이 드물다. 링크가 순위 신호가 되는 원리는 [검색 순위와 PageRank](/posts/search-engine-ranking-pagerank)에서 다룬다.

## 해킹 알림을 받은 날의 순서

보안 문제 알림이 오거나 검색 결과에 낯선 제목이 보이면 당황해서 파일부터 지우기 쉽다. 순서를 정해 두면 같은 일을 두 번 겪지 않는다.

1. 증거를 남긴다. 지우기 전에 서버 파일 시스템 스냅샷이나 이미지, 접근 로그, 데이터베이스 덤프를 따로 보관한다. 침입 경로를 찾으려면 바뀐 파일의 시각과 로그가 필요하다.
2. 계정을 정리한다. 관리자, 배포, DB, Search Console 소유자 목록에서 모르는 계정을 지우고 남은 계정의 비밀번호와 API 키를 바꾼다.
3. 침입 경로를 막는다. 변경 시각 직전의 요청을 로그에서 찾아 취약한 플러그인이나 업로드 기능을 확인하고, 업데이트하거나 끈다.
4. 깨끗한 상태로 되돌린다. 심긴 파일을 하나씩 지우기보다 신뢰할 수 있는 배포본이나 백업에서 다시 배포한다. WordPress라면 `wp core verify-checksums`처럼 배포본 해시와 비교하는 도구로 코어 변조를 확인한다.
5. 생성된 스팸 주소를 처리한다. 404나 410으로 응답하게 하고, 급하면 Search Console 삭제 도구로 검색 결과에서 잠시 숨긴다. 삭제 도구는 약 6개월 동안 숨길 뿐 색인에서 지우는 게 아니니 410 응답과 함께 쓴다.
6. 검토를 요청한다. 보안 문제 보고서에서 무엇을 고쳤는지 적어 요청한다.
7. 재발을 지켜본다. 몇 주 동안 사람·봇 응답 비교와 `site:` 검색, 페이지 색인 보고서의 새 주소 수를 매일 본다.

## 키워드 반복과 남의 글 가져오기

키워드 반복은 순위를 위해 같은 단어를 부자연스럽게 채우는 것이다. 사람이 손으로 쓰는 글보다 템플릿이 만드는 경우가 더 많다. 상품 템플릿이 `title`에 "코트 | 울코트 | 겨울코트 | 여성코트 | 코트 추천"을 붙이거나, 이미지 `alt`마다 상품 이름과 분류 이름을 열 번씩 넣거나, 푸터에 지역 이름 수백 개를 나열하는 식이다. 이런 건 정책 이전에 구글이 제목을 바꿔 보여 주는 이유가 되고, 스크린 리더 사용자에게는 소음이다. `alt`는 이미지를 설명하고 `title`은 페이지를 설명하면 충분하다.

스크래핑 정책은 남의 콘텐츠를 가져와 가치를 더하지 않고 올리는 것을 겨냥한다. 개발자가 자주 만드는 경계 사례는 상품 피드다. 제조사나 다른 쇼핑몰의 상품 설명을 그대로 가져와 수천 개 페이지를 채우면, 같은 문장이 웹에 수백 곳 있으니 우리 페이지를 고를 이유가 없다. 빈약한 제휴 페이지 정책도 비슷하다. 제휴 링크로 수익을 얻는 것 자체는 괜찮지만, 판매처의 설명을 복사하고 링크만 붙인 페이지는 대상이 된다. 우리만의 정보(실측 사이즈, 직접 찍은 사진, 실제 후기, 비교)를 더하는 게 해결책이고, 그게 어려운 페이지는 `noindex`로 두는 편이 사이트 전체에 낫다.

## 대량 생성, 만료 도메인, 평판 악용

2024년 3월 구글은 스팸 정책에 세 가지를 새로 넣거나 크게 고쳤다. 셋 다 "순위를 얻을 목적으로 무언가를 대량으로, 혹은 남의 신뢰를 빌려" 하는 것을 겨냥한다.

대량 생성 콘텐츠 악용은 사용자에게 도움이 되기보다 순위를 얻으려고 페이지를 대량으로 만드는 것이다. 구글은 만드는 방법은 상관없다고 명시한다. 생성형 AI로 만들든, 사람을 고용해 만들든, 둘을 섞든 판단 기준은 목적과 가치다. 개발자가 자주 만나는 형태는 프로그래매틱 SEO다. "지역 × 서비스" 조합으로 `/seoul/gangnam/aircon-cleaning` 같은 페이지를 수천 개 만들고, 지역 이름만 바꾼 같은 문단을 채운다. 지역마다 실제로 다른 정보(가격, 가능한 업체, 후기, 영업시간)가 있으면 유용한 페이지이고, 이름만 바꾼 껍데기라면 이 정책에 걸릴 수 있다. 같은 페이지 묶음이 특정 지역 검색을 받아 한 페이지로 몰아 보내는 구조라면 도어웨이 정책에도 걸린다.

만료 도메인 악용은 기간이 끝난 도메인을 사서, 그 도메인이 원래 쌓아 둔 평판을 이용해 상관없는 저품질 콘텐츠를 올리는 것이다. 문 닫은 지역 병원의 도메인을 사서 카지노 리뷰를 올리는 식이다. 도메인을 사서 원래 주제와 이어지는 사이트를 새로 만드는 것은 해당하지 않는다.

사이트 평판 악용은 신뢰받는 사이트에 그 사이트와 상관없는 제3자 콘텐츠를 올려 그 사이트의 순위 신호를 빌리는 것이다. "기생 SEO"라고도 부른다. 뉴스 사이트 하위 폴더에 외부 업체가 만든 쿠폰 할인 코드 페이지가 수백 개 있는 경우가 대표적이다. 구글은 2024년 5월부터 이 정책으로 수동 조치를 시작했고, 같은 해 11월에는 사이트 운영자가 관여하거나 감독했더라도 제3자 콘텐츠로 순위 신호를 악용하면 위반이라고 정책 설명을 고쳤다. 외부 콘텐츠를 사이트에 들일 때는 그 콘텐츠가 사이트의 주제와 독자에게 맞는지 보고, 맞지 않으면 `noindex`로 두거나 별도 도메인에 둔다.

## 구조화 데이터로 속이는 것

구조화 데이터에도 별도의 수동 조치가 있다. 리치 결과(별점, 가격, FAQ 같은 꾸밈)를 얻으려고 화면에 없는 내용을 마크업하면 구조화 데이터 문제로 조치를 받을 수 있다. 이 조치는 순위가 아니라 리치 결과 자격을 잃게 하는 경우가 많다.

개발자가 실수하기 쉬운 경우가 몇 가지 있다. 리뷰를 화면에 보여 주지 않으면서 `aggregateRating`만 넣는 것, 모든 페이지 템플릿에 같은 회사 별점을 넣는 것, 자기 회사나 자기 서비스에 대한 리뷰를 스스로 마크업하는 것이다. 마지막 것은 구글이 2019년부터 리치 결과 대상에서 뺐다. 구조화 데이터의 가격과 재고가 화면 값과 다른 것도 같은 문제가 된다. 앞의 프리렌더 캐시가 낡는 문제가 여기서 다시 나온다.

원칙은 클로킹과 같다. 마크업은 사람이 화면에서 볼 수 있는 내용을 기계가 읽기 쉽게 다시 적은 것이어야 한다. 화면과 마크업을 같은 데이터에서 만들면 둘이 어긋날 일이 줄어든다. 마크업 방법과 검증 도구는 [구조화 데이터와 JSON-LD](/posts/structured-data-json-ld)에서 다룬다.

## 생성형 AI로 만든 글은 스팸인가

상품 1만 개의 설명을 LLM으로 만들자는 이야기도 자주 나온다. 구글의 입장은 2023년 초부터 같다. 콘텐츠를 어떻게 만들었는지가 아니라 사람에게 도움이 되는지를 본다. AI로 만들었다는 이유만으로 스팸이 되지 않고, 사람이 썼다는 이유만으로 괜찮아지지도 않는다. 위반이 되는 건 순위를 얻을 목적으로 가치 없는 페이지를 대량으로 찍어 낼 때이고, 그게 앞의 대량 생성 콘텐츠 악용이다.

그래서 실무의 질문은 "AI를 써도 되나"가 아니라 "이 페이지에 다른 곳에 없는 정보가 있나"다. 상품 속성(소재, 실측, 세탁 방법)을 데이터에서 가져와 문장으로 다듬는 건 사람에게 도움이 된다. 상품 이름만 넣고 "이 코트는 겨울에 따뜻하고 스타일리시합니다" 같은 문장을 1만 번 만드는 건 아니다. 생성 결과를 표본으로 사람이 검토하고, 사실과 다른 내용(없는 소재, 틀린 치수)이 들어가지 않게 데이터와 대조하는 단계를 파이프라인에 넣는다. 틀린 정보가 많으면 정책 이전에 반품과 신뢰 문제가 먼저 온다.

## 경쟁사의 스팸을 신고하면

경쟁 사이트가 숨긴 텍스트나 산 링크로 위에 있는 것 같을 때, 구글의 스팸 신고 양식으로 알릴 수 있다. 다만 구글은 신고를 개별 수동 조치로 바로 이어 가기보다 스팸 탐지 시스템을 개선하는 데 주로 쓴다고 설명한다. 신고했다고 경쟁사가 곧 내려가지는 않는다는 뜻이다. 내 사이트의 개선에 쓰는 시간이 대개 더 남는다.

## 벌을 받았다: 수동 조치와 알고리즘 하락

어느 날 검색 유입이 반으로 줄었다. 먼저 가를 것은 이게 사람의 판단인지 시스템의 판단인지다. 둘은 확인하는 곳도, 회복하는 법도 다르다.

수동 조치는 Search Console의 "보안 및 직접 조치 › 직접 조치" 보고서에 나온다. 조치의 종류(사용자 생성 스팸, 부자연스러운 링크, 빈약한 콘텐츠 등)와 범위가 적혀 있다. 범위는 사이트 전체에 걸린 조치와 일부 주소에만 걸린 조치로 나뉘고, 예시 주소가 몇 개 함께 나온다. 이 보고서가 비어 있으면 수동 조치는 없는 것이다.

수동 조치를 풀려면 예시 주소만이 아니라 같은 문제가 있는 모든 페이지를 고친다. 그다음 같은 보고서에서 재검토 요청을 보낸다. 요청에는 무엇이 문제였는지, 무엇을 고쳤는지, 다시 생기지 않게 무엇을 바꿨는지를 구체적으로 적는다. 링크 문제라면 삭제를 요청한 링크와 그 결과를 문서로 남긴다. 검토는 며칠에서 몇 주가 걸리고 결과는 메시지로 온다. 고친 게 부족하면 거절되고, 다시 고쳐 요청할 수 있다. 조치가 풀린다고 순위가 예전 그대로 돌아온다는 보장은 없다. 조작으로 얻었던 효과는 처음부터 없었던 것이 되기 때문이다.

재검토 요청은 짧은 사과문이 아니라 작업 보고서처럼 쓴다. 검토하는 사람이 고친 범위를 확인할 수 있어야 한다.

```text
문제: 사용자 프로필 페이지(/users/*)에 스팸 링크가 담긴 계정이 대량 생성됨 (약 4만 개)
원인: 가입에 봇 차단이 없었고, 새 프로필이 즉시 색인 가능했음
조치:
- 스팸 계정과 프로필 페이지 삭제, 해당 주소는 410 응답
- 사용자 작성 링크에 rel="ugc nofollow" 적용
- 활동 30일 미만 프로필은 noindex
- 가입에 CAPTCHA와 IP별 속도 제한 추가, 링크 포함 첫 글은 검토 대기
확인: 삭제한 주소 목록과 변경 배포 날짜를 첨부 문서에 정리함
```

링크 문제로 받은 조치라면 링크 거부 파일도 함께 준비한다. 형식은 한 줄에 주소 하나, 또는 `domain:`으로 도메인 전체를 적는 텍스트 파일이다. 먼저 상대 사이트에 삭제를 요청하고, 지워지지 않은 것만 넣는다.

```text
# 2026-10 링크 판매 업체에서 산 링크. 삭제 요청했으나 응답 없음
domain:links-for-sale.example
https://blog.example.net/sponsored-post-123
```

알고리즘 하락은 알림이 없다. 구글의 Search Status Dashboard에 그 시기에 스팸 업데이트나 핵심 업데이트가 있었는지 먼저 본다. 스팸 업데이트는 SpamBrain 같은 스팸 시스템을 개선하는 업데이트이고, 핵심 업데이트는 순위 시스템 전반을 다시 조정하는 업데이트다. 날짜가 맞는다면 사이트 전체의 품질과 스팸 문제를 정리하고 기다린다. 구글은 스팸 업데이트로 떨어진 사이트가 정책을 고치면 자동 시스템이 몇 달에 걸쳐 그 개선을 알아본다고 설명한다. 핵심 업데이트는 "고칠 특정 문제가 있는 게 아닐 수 있다"고 말하고, 콘텐츠를 개선한 효과가 다음 핵심 업데이트 때 드러나기도 한다고 한다.

어느 쪽이든 하지 말아야 할 일이 있다. 떨어진 날 사이트 구조를 한꺼번에 뜯어고치는 것이다. 원인을 모른 채 여러 개를 바꾸면 무엇이 효과였는지 알 수 없고, 리다이렉트 실수 같은 새 문제를 얹을 수 있다. 숫자를 좁혀 가는 순서는 [검색 유입 재기](/posts/search-traffic-measurement)에 정리했다.

## 유용한 콘텐츠 시스템과 E-E-A-T가 아닌 것

스팸 정책 이야기를 하면 꼭 따라 나오는 두 이름이 있다. 둘 다 오해가 많다.

유용한 콘텐츠 시스템(helpful content system)은 2022년 8월에 처음 나왔다. 검색 순위를 얻으려고 만든, 사람에게 별 도움이 안 되는 콘텐츠가 많은 사이트를 낮추는 사이트 단위 신호로 소개됐다. 2024년 3월 핵심 업데이트에서 구글은 이 시스템을 별도 시스템이 아니라 핵심 순위 시스템의 일부로 합쳤다고 밝혔다. 그래서 지금은 "유용한 콘텐츠 업데이트"가 따로 나오지 않고, 그 판단은 핵심 업데이트 안에서 일어난다. 스팸 정책 위반과는 다르다. 정책을 어기지 않았어도 도움이 덜 되는 콘텐츠는 순위가 낮을 수 있고, 이건 수동 조치나 재검토 요청의 대상이 아니다.

E-E-A-T는 경험(Experience), 전문성(Expertise), 권위(Authoritativeness), 신뢰(Trust)의 머리글자다. 원래 구글이 검색 결과 품질을 평가하는 사람들(품질 평가자)에게 주는 가이드라인의 개념이고, 2022년 12월에 경험이 더해졌다. 가이드라인은 네 가지 중 신뢰를 가장 중요하게 둔다. 여기서 흔한 오해가 둘이다.

E-E-A-T는 점수가 매겨지는 순위 요소가 아니다. 구글은 E-E-A-T 자체가 특정 순위 요소는 아니라고 설명한다. 순위 시스템은 여러 신호를 섞어 쓰고, 그 신호들이 E-E-A-T가 좋은 콘텐츠를 알아보는 방향으로 설계되어 있다는 뜻에 가깝다. "저자 소개 박스를 달면 E-E-A-T 점수가 오른다"는 식의 접근은 근거가 없다.

품질 평가자의 평가는 개별 사이트 순위를 직접 바꾸지 않는다. 평가자들은 실험 중인 순위 변경이 결과를 좋게 만드는지 판단하는 데이터를 낸다. 평가자가 내 사이트를 낮게 평가했다고 내 순위가 떨어지는 구조가 아니다.

그래도 개념은 쓸모가 있다. 건강, 돈, 안전처럼 잘못된 정보가 사람에게 해를 끼칠 수 있는 주제(가이드라인에서는 YMYL이라 부른다)일수록 누가 썼는지, 어떤 경험과 근거가 있는지가 중요하다. 개발자가 할 수 있는 건 그 정보가 페이지에 드러나게 만드는 일이다. 저자 페이지와 연락처, 고친 날짜, 출처 링크를 템플릿에 자리 잡게 하고, 구조화 데이터로 저자와 조직을 표시한다. 점수를 올리는 장치가 아니라, 사람과 시스템이 신뢰를 판단할 재료를 주는 일이다.

## 배포 전에 확인할 것

스팸 정책은 대부분 의도의 문제지만, 개발자의 코드가 의도와 상관없이 위반처럼 보이게 만드는 경우가 있다. 배포 전후로 이것들을 본다.

- 요청에 따라 응답을 바꾸는 코드가 있다면, 구글봇과 같은 조건의 사람이 같은 내용을 받는지. UA나 IP로 분기하는 코드는 리뷰에서 따로 표시한다.
- 프리렌더나 캐시된 봇용 HTML이 사람 화면과 얼마나 다른지. 가격, 재고, 구조화 데이터를 비교한다.

```bash
# 같은 주소를 사람 UA와 구글봇 UA로 받아 본문 차이만 본다 (프리렌더 비교용)
diff <(curl -s https://shop.example.com/products/42) \
     <(curl -s -A 'Mozilla/5.0 (compatible; Googlebot/2.1; +http://www.google.com/bot.html)' \
       https://shop.example.com/products/42) | head -20
```

- 위 비교는 프리렌더처럼 내가 만든 분기를 확인하는 용도다. 구글 IP까지 확인하는 해킹 코드는 이걸로 안 보이니 URL 검사의 실제 URL 테스트로 따로 본다.
- 서드파티 스크립트(광고, 위젯, 채팅)가 리다이렉트나 숨긴 링크를 넣지 않는지. 새로 붙인 스크립트는 모바일에서 검색 결과로 들어가 확인한다.
- 사용자가 쓰는 곳의 링크에 `rel="ugc"`가 붙는지, 새 프로필이 `noindex`인지.
- 지역·조합 페이지를 대량으로 만든다면, 페이지마다 실제로 다른 정보가 있는지.
- Search Console의 직접 조치와 보안 문제 보고서, 사용자 및 권한 목록을 정기적으로 본다. 알림 메일이 개인 메일함에서 묻히지 않게 팀 주소를 소유자로 둔다.

## 다시 동적 렌더링으로

처음 질문의 답은 이렇다. 봇에게 미리 렌더링한 HTML을 주는 것 자체는 클로킹이 아니다. 클로킹은 검색 엔진과 사람에게 다른 내용을 보여 주어 순위를 조작하는 것이고, 판정은 기술이 아니라 내용과 의도로 한다. 다만 프리렌더가 낡거나 깨지면 의도하지 않은 차이가 생기고, 해킹은 내가 모르는 사이에 진짜 클로킹을 만든다. 그래서 사람과 봇이 같은 것을 보는지 정기적으로 비교하고, 유입이 떨어지면 수동 조치 보고서부터 열어 사람의 판단인지 시스템의 판단인지 가른다. E-E-A-T와 유용한 콘텐츠 판단은 고쳐서 신청하는 대상이 아니라 사이트를 더 쓸모 있게 만드는 방향이다.

## 면접에서 나올 만한 질문

### 클로킹이란 무엇이고 동적 렌더링은 클로킹인가요?

클로킹은 검색 엔진과 사람에게 다른 내용을 보여 주어 검색 순위를 조작하는 것이다. 동적 렌더링은 봇에게 미리 렌더링한 HTML을 주지만 내용이 사람이 보는 것과 같으면 클로킹이 아니라고 구글 문서에 나온다. 다만 구글은 동적 렌더링을 임시 해결책으로 보고 권하지 않으며, 프리렌더 캐시가 낡거나 봇용 HTML에만 내용을 더하면 차이가 생기니 SSR이나 SSG가 낫다.

### 사이트가 해킹돼 구글봇에게만 스팸을 보여 주는지 어떻게 확인하나요?

`curl -A`로 UA를 바꿔 비교할 수 있지만, 정교한 코드는 IP까지 확인해서 이것만으로는 부족하다. Search Console URL 검사의 실제 URL 테스트로 구글 IP에서 가져간 HTML을 보고, `site:` 검색으로 상관없는 단어의 페이지가 색인됐는지, Search Console 소유자 목록에 모르는 계정이 있는지 본다. 발견하면 침입 경로를 먼저 막고, 심긴 코드와 페이지를 지운 뒤 보안 문제 검토를 요청한다.

### 사용자 생성 스팸은 어떻게 막나요?

사용자가 쓴 링크에 `rel="ugc"`를 붙이고, 새 계정의 프로필은 조건을 넘기 전까지 `noindex`로 두며, 가입과 글쓰기에 봇 차단과 속도 제한을 둔다. 링크가 들어간 첫 글은 검토 대기로 보낸다. 운영자가 쓰지 않았어도 사이트에 쌓인 스팸은 수동 조치 대상이 될 수 있다.

### 프로그래매틱 SEO로 지역별 페이지를 수천 개 만들면 문제가 되나요?

만드는 방법이 아니라 목적과 가치로 판단한다. 지역마다 실제로 다른 가격, 업체, 후기 같은 정보가 있으면 유용한 페이지이고, 지역 이름만 바꾼 같은 문단이면 대량 생성 콘텐츠 악용에 걸릴 수 있다. 지역 검색을 받아 한 페이지로 몰아 보내는 구조라면 도어웨이 정책에도 해당한다.

### 수동 조치와 알고리즘 하락은 어떻게 구분하고 각각 어떻게 회복하나요?

수동 조치는 Search Console 직접 조치 보고서에 종류와 범위가 나온다. 모든 해당 페이지를 고치고 무엇을 고쳤는지 구체적으로 적어 재검토를 요청하면 사람이 다시 본다. 알고리즘 하락은 알림이 없으니 Search Status Dashboard의 업데이트 날짜와 맞춰 보고, 사이트를 개선한 뒤 시스템이 다시 평가하기를 기다린다. 몇 달이 걸리거나 다음 핵심 업데이트에 반영되기도 한다.

### E-E-A-T는 순위 요소인가요?

직접적인 순위 요소가 아니다. 구글 품질 평가자 가이드라인의 개념이고, 평가자의 평가는 개별 사이트 순위를 바꾸지 않고 순위 변경 실험을 판단하는 데 쓰인다. 순위 시스템이 여러 신호로 경험, 전문성, 권위, 신뢰가 좋은 콘텐츠를 알아보도록 설계되었다는 뜻에 가깝다. 개발자는 저자 정보, 고친 날짜, 출처, 연락처가 페이지에 드러나게 만드는 정도로 기여한다.

### 동적 렌더링을 붙일 때 주의할 점은 무엇인가요?

봇용과 사람용 응답이 캐시에서 섞이지 않게 `Vary: User-Agent`를 달거나 CDN 캐시 키에 봇 여부를 넣는다. 프리렌더 캐시가 가격·재고보다 낡지 않게 신선도를 정하고, 프리렌더가 실패하면 빈 200 대신 원래 HTML이나 503을 준다. 봇용 HTML에만 내용을 더하지 않고, 두 응답의 본문을 정기적으로 비교한다.

### 광고 링크와 사용자 링크에는 어떤 rel을 붙이나요?

돈을 받고 건 광고·협찬 링크에는 `rel="sponsored"`, 댓글·포럼·프로필처럼 사용자가 쓴 링크에는 `rel="ugc"`를 붙인다. 둘 다 `nofollow`와 함께 써도 된다. 돈을 받은 링크를 표시 없이 걸면 링크 스팸 정책에 걸리고, 사용자 링크를 그냥 두면 스패머의 표적이 되어 사용자 생성 스팸 수동 조치로 이어질 수 있다.
