`shop` 네임스페이스를 정리하던 사람이 `kubectl delete ns shop`을 쳤다. Deployment와 Service는 Git에 있으니 다시 적용하면 된다. 그런데 운영 중에 손으로 만든 Secret 두 개, 오퍼레이터가 만든 인증서, 그리고 PVC에 들어 있던 업로드 파일은 Git에 없다. 네임스페이스를 지우면 PVC도 지워지고, StorageClass의 reclaimPolicy가 Delete라면 디스크까지 사라진다.

[etcd 스냅숏](/posts/k8s-etcd-backup)이 있다면 클러스터 전체를 어젯밤으로 되돌릴 수는 있다. 하지만 그러면 다른 네임스페이스의 오늘 변경도 모두 사라지고, 스냅숏에는 디스크 안의 파일이 없다. EKS라면 애초에 etcd 스냅숏을 뜰 수도 없다. 이런 사고를 위해 쓰는 것이 Velero다. API 서버를 거쳐 원하는 네임스페이스나 리소스만 떠 두고, 볼륨 데이터까지 함께 챙기며, 다른 이름의 네임스페이스나 다른 클러스터로 되살린다.

이 글은 Velero가 etcd 스냅숏과 무엇이 다른지, BackupStorageLocation과 스케줄, 백업 훅, 볼륨을 백업하는 세 가지 방법(클라우드 스냅숏, CSI 스냅숏과 데이터 이동, 파일 시스템 백업), 네임스페이스를 바꿔 복원하는 법을 본다.

Velero는 1.18.0 CLI를 썼다. `velero install --dry-run`이 만드는 매니페스트, `-o yaml`로 뽑은 Backup·Schedule·Restore 객체, kwok 클러스터(Kubernetes 1.37.0)에 CRD를 올리고 만든 객체의 `get`·`describe` 출력은 실제로 받았다. 이 클러스터에는 Velero 서버가 돌지 않으니(컨테이너가 실제로 뜨지 않는다) 백업이 끝까지 진행된 뒤의 출력은 형식을 맞춘 예시로 따로 표시한다.

이 주제의 다른 글: 백업을 몇 벌 어디에 둘지는 [백업 전략](/posts/backup-strategy), 얼마나 잃고 얼마나 멈출지는 [재해 복구](/posts/disaster-recovery), CSI 볼륨 스냅숏 자체는 [StorageClass와 볼륨 스냅숏](/posts/k8s-storageclass-snapshots)에서 다룬다.

etcd 스냅숏은 저장소의 바이트를 그대로 뜬다. 같은 etcd 버전, 같은 클러스터 구성으로만 되돌릴 수 있고, 되돌리면 전부 되돌아간다. Velero는 API 서버에 "shop 네임스페이스의 객체를 다 달라"고 물어서 받은 JSON을 묶어 둔다. 그래서 일부만 뜨고 일부만 되살릴 수 있고, 다른 클러스터에 그 JSON을 다시 만들 수 있다.

대신 잃는 것도 있다. Velero는 API 서버가 정한 그 리소스의 preferred version으로 객체를 받아 두고, 복원할 때 같은 그룹·버전이 대상 클러스터에 있어야 한다. 문서는 백업을 뜬 클러스터보다 낮은 쿠버네티스 버전으로의 복원을 지원하지 않는다고 적는다. 클러스터 전체의 "한 순간"을 뜨는 것도 아니다. 객체를 차례로 읽으니 백업 도중에 바뀐 객체는 앞뒤가 섞일 수 있다.

둘은 대신하는 관계가 아니다. 자체 관리 클러스터라면 컨트롤 플레인이 통째로 죽는 사고에는 etcd 스냅숏을, 네임스페이스 단위 사고와 클러스터 이전에는 Velero를 쓴다. 관리형 클러스터에서는 Velero(와 GitOps)가 거의 유일한 선택지다.

## 설치하면 생기는 것들

`velero install`에 `--dry-run -o yaml`을 주면 클러스터에 만들 객체를 출력만 한다. AWS 플러그인과 노드 에이전트를 켜서 뽑아 보고 종류만 추렸다.

# 클러스터에 적용하지 않고 설치 매니페스트만 만든다

  --plugins velero/velero-plugin-for-aws:v1.14.4 \

## 백업이 쌓이는 곳, BackupStorageLocation

BackupStorageLocation(BSL)은 "백업 파일을 어느 버킷의 어느 경로에 둘지"를 적은 객체다. 하나의 버킷을 여러 클러스터가 쓸 때는 prefix로 나눈다.

```bash
# 운영 클러스터용 BSL. prod-cluster 경로 아래에 쌓는다
velero backup-location create default --provider aws --bucket velero-backups \
  --prefix prod-cluster --config region=ap-northeast-2 --default
velero backup-location get
```

```text
NAME      PROVIDER   BUCKET/PREFIX                 PHASE     LAST VALIDATED   ACCESS MODE   DEFAULT
default   aws        velero-backups/prod-cluster   Unknown   Unknown          ReadWrite     true
```

PHASE가 `Unknown`인 것은 실습 클러스터에 서버가 없어 아무도 버킷을 확인하지 않았기 때문이다. 서버가 돌면 주기적으로 버킷에 접근해 보고 `Available`이나 `Unavailable`로 바꾼다. 운영에서 이 칸이 `Unavailable`이면 그 뒤의 백업은 모두 실패한다. 자격 증명 만료, 버킷 정책 변경, IRSA 설정 실수가 흔한 원인이다.

Velero에서 기억해 둘 성질이 하나 있다. 문서는 버킷을 "진실의 원천"이라고 부른다. 버킷에 올바른 형식의 백업 파일이 있는데 클러스터에 Backup 객체가 없으면 서버가 객체를 만들어 준다(object storage sync). 반대로 클러스터에 Completed 백업 객체가 있는데 버킷에 파일이 없으면 그 객체를 지운다. 그래서 새 클러스터에 Velero를 깔고 같은 버킷을 BSL로 붙이기만 하면 옛 클러스터의 백업 목록이 보인다. 클러스터 이전과 재해 복구가 이 성질 위에서 돈다.

같은 이유로 복원하는 쪽 클러스터의 BSL은 읽기 전용으로 붙인다.

```bash
# DR 클러스터에서는 운영 백업을 읽기만 한다
velero backup-location create dr-readonly --provider aws --bucket velero-backups \
  --prefix prod-cluster --access-mode ReadOnly --config region=ap-northeast-2 -o yaml
```

```text
apiVersion: velero.io/v1
kind: BackupStorageLocation
metadata:
  creationTimestamp: null
  name: dr-readonly
  namespace: velero
spec:
  accessMode: ReadOnly
  config:
    region: ap-northeast-2
  objectStorage:
    bucket: velero-backups
    prefix: prod-cluster
  provider: aws
status: {}
```

ReadWrite로 붙이면 DR 클러스터의 Velero가 TTL이 지난 백업을 지우거나, 운영 클러스터의 백업과 같은 이름으로 새 백업을 써 버릴 수 있다. 백업 버킷 자체는 [백업 전략](/posts/backup-strategy)에서 다룬 것처럼 다른 계정에 두고 Object Lock을 건다. velero의 자격 증명이 털려도 지울 수 없게 하려는 것이다.

## 백업 하나, 그리고 매일 밤의 스케줄

백업은 범위를 정해서 만든다. 네임스페이스(`--include-namespaces`), 리소스 종류(`--include-resources`), 라벨(`--selector`)로 고르고, 보관 기간을 `--ttl`로 준다. `-o yaml`을 주면 만들지 않고 객체만 보여 준다.

```bash
# shop 네임스페이스를 30일 동안 보관하는 백업
velero backup create shop-20261021 --include-namespaces shop --snapshot-move-data --ttl 720h -o yaml
```

```text
apiVersion: velero.io/v1
kind: Backup
metadata:
  creationTimestamp: null
  name: shop-20261021
  namespace: velero
spec:
  csiSnapshotTimeout: 0s
  hooks: {}
  includedNamespaces:
  - shop
  itemOperationTimeout: 0s
  metadata: {}
  snapshotMoveData: true
  ttl: 720h0m0s
status: {}
```

`-o yaml` 없이 실제로 만들고 목록을 보면, 서버가 없는 실습 클러스터에서는 이렇게 멈춰 있다.

```bash
velero backup create shop-20261021 --include-namespaces shop --ttl 720h
velero backup get
velero backup describe shop-20261021 | grep -E 'Phase|Storage Location|Data Mover'
```

```text
Backup request "shop-20261021" submitted successfully.
Run `velero backup describe shop-20261021` or `velero backup logs shop-20261021` for more details.
NAME            STATUS   ERRORS   WARNINGS   CREATED   EXPIRES   STORAGE LOCATION   QUEUE POSITION   SELECTOR
shop-20261021   New      0        0          <nil>     29d                                           <none>
Phase:  New
Storage Location:  
Data Mover:                  velero
```

"submitted successfully"는 백업이 됐다는 뜻이 아니다. Backup 객체가 만들어졌다는 뜻이다. STATUS가 `New`에서 움직이지 않으면 velero 서버 Pod가 죽어 있거나 다른 Velero 설치(다른 네임스페이스)가 이 객체를 보고 있지 않은 것이다. `kubectl -n velero get pods`와 `kubectl -n velero logs deploy/velero`부터 본다. 서버가 정상이라면 `InProgress`를 거쳐 이렇게 끝난다(예시, 형식은 실제와 같다).

```text
NAME            STATUS      ERRORS   WARNINGS   CREATED                         EXPIRES   STORAGE LOCATION   QUEUE POSITION   SELECTOR
shop-20261021   Completed   0        0          2026-10-21 10:12:03 +0900 KST   29d       default                             <none>
```

`PartiallyFailed`도 자주 본다. 객체 대부분은 들어갔지만 일부 볼륨이나 훅이 실패한 상태다. 완료로 착각하기 쉬우니 모니터링은 `Completed`만 성공으로 센다. 실패한 이유는 `velero backup describe --details`와 `velero backup logs`에 있다.

매일 뜨려면 Schedule을 만든다. 스케줄은 백업 템플릿 하나와 cron 식이다.

```bash
# 매일 03:00(한국 시각)에 shop을 뜨고 14일 보관한다
velero schedule create shop-nightly --schedule="0 18 * * *" --include-namespaces shop \
  --default-volumes-to-fs-backup --ttl 336h -o yaml
```

```text
apiVersion: velero.io/v1
kind: Schedule
metadata:
  creationTimestamp: null
  name: shop-nightly
  namespace: velero
spec:
  schedule: 0 18 * * *
  template:
    csiSnapshotTimeout: 0s
    defaultVolumesToFsBackup: true
    hooks: {}
    includedNamespaces:
    - shop
    itemOperationTimeout: 0s
    metadata: {}
    ttl: 336h0m0s
  useOwnerReferencesInBackup: false
status: {}
```

`--schedule` 도움말은 "using UTC time"이라고 적는다. 18시 UTC가 한국 시각 03시다. 헷갈리면 `--schedule="CRON_TZ=Asia/Seoul 0 3 * * *"`처럼 시간대를 앞에 붙일 수 있다. TTL을 주지 않으면 기본 30일이고, 만료된 백업은 바로 지워지지 않고 1시간마다 도는 정리 루프에서 버킷의 파일과 스냅숏까지 함께 지워진다.

스케줄을 고를 때 볼 것은 [재해 복구](/posts/disaster-recovery)의 RPO다. 하루 한 번이면 최악의 경우 하루치를 잃는다. 주문 DB처럼 그걸 못 견디는 데이터는 Velero가 아니라 DB 자체의 백업(WAL 보관, PITR)이 맡아야 한다. Velero의 볼륨 백업은 DB 파일을 통째로 복사하는 것이라 시점 복구가 안 된다.

## 백업 순간을 맞추는 훅

DB가 쓰고 있는 볼륨을 그대로 스냅숏으로 뜨면, 전원을 뽑은 순간의 디스크와 같은 상태(crash-consistent)가 된다. 대부분의 DB는 이걸 복구하지만, 버퍼에 있던 쓰기가 반쯤 반영된 파일을 쓰는 앱은 깨질 수 있다. 백업 훅은 Pod를 백업하기 직전과 직후에 컨테이너 안에서 명령을 실행한다. Pod 어노테이션으로 거는 것이 가장 흔하다.

```bash
# 백업 직전에 디스크 쓰기를 멈추고(fsfreeze), 백업이 끝나면 푼다
kubectl -n shop annotate pod -l app=uploads \
  pre.hook.backup.velero.io/container=fsfreeze \
  pre.hook.backup.velero.io/command='["/sbin/fsfreeze", "--freeze", "/var/uploads"]' \
  pre.hook.backup.velero.io/timeout=30s \
  post.hook.backup.velero.io/container=fsfreeze \
  post.hook.backup.velero.io/command='["/sbin/fsfreeze", "--unfreeze", "/var/uploads"]'
```

명령은 셸 없이 실행된다. 파이프나 `&&`가 필요하면 `["/bin/sh", "-c", "..."]`로 감싼다. 기본 `on-error`는 `Fail`이라 pre 훅이 실패하면 그 Pod의 백업이 실패로 기록된다. 타임아웃 기본값은 30초다. 1.15부터는 함께 백업해야 하는 항목들(예: 같은 RWX 볼륨을 쓰는 Pod들)을 ItemBlock으로 묶어서, 묶음 안의 모든 Pod에 pre 훅을 실행한 뒤 함께 백업하고 post 훅을 실행한다.

fsfreeze는 위험한 도구이기도 하다. post 훅이 실행되지 않으면(Velero 서버가 중간에 죽으면) 파일 시스템이 얼어붙은 채로 남아 앱이 쓰기에서 멈춘다. 그래서 freeze를 하는 사이드카를 따로 두고, 문서 예제도 그렇게 한다. DB라면 fsfreeze보다 DB가 제공하는 방법을 쓴다. PostgreSQL이면 pre 훅에서 `CHECKPOINT`를 실행해 두는 정도가 부담이 적고, 제대로 된 시점 백업은 DB 도구로 한다.

복원에도 훅이 있다. 복원된 Pod에 init 컨테이너를 넣어 데이터를 준비하거나(`init.hook.restore.velero.io/...`), 컨테이너가 뜬 뒤 명령을 실행한다(`post.hook.restore.velero.io/...`). 복원 후 캐시를 비우거나 외부 시스템에 재등록하는 데 쓴다.

## 볼륨을 백업하는 세 가지 길

객체는 JSON으로 쉽게 뜬다. 어려운 것은 PVC 안의 데이터다. Velero는 볼륨마다 세 가지 중 하나를 쓴다. 같은 볼륨에 둘을 함께 쓰지는 않는다. 파일 시스템 백업을 고른 볼륨은 스냅숏을 건너뛴다.

첫째, 클라우드 디스크 스냅숏(VSL). AWS 플러그인이 EBS 스냅숏 API를 직접 부른다. 빠르고 일관되지만 스냅숏이 EBS 쪽에 남으니 같은 리전·계정에 묶인다. 리전 장애나 계정 침해에는 함께 잃는다.

둘째, CSI 스냅숏과 데이터 이동. 클러스터의 CSI 드라이버로 VolumeSnapshot을 만들고([StorageClass와 볼륨 스냅숏](/posts/k8s-storageclass-snapshots)), `--snapshot-move-data`를 주면 그 스냅숏을 임시 볼륨으로 붙여 데이터를 BSL 버킷으로 옮긴 뒤 스냅숏은 지운다. 스냅숏의 일관성과 버킷의 독립성을 함께 얻는다. 기본 데이터 이동기는 파일 시스템을 읽어 kopia로 올리고, 최신 문서에는 블록 단위로 바뀐 블록만 읽는 이동기(CSI Changed Block Tracking 연동)도 소개돼 있다.

셋째, 파일 시스템 백업(FSB). 스냅숏 기능이 없는 볼륨(NFS, EFS, emptyDir, local)도 뜰 수 있다. node-agent가 살아 있는 파일 시스템을 그대로 읽으니 한 시점이 아니다. 백업 도중 바뀐 파일은 앞뒤가 섞인다. 볼륨마다 `backup.velero.io/backup-volumes` 어노테이션으로 고르거나 `--default-volumes-to-fs-backup`으로 전부 고른다. hostPath 볼륨은 지원하지 않는다.

FSB의 엔진은 오래 restic이었다가 kopia로 바뀌었다. 1.15부터 restic 경로가 폐기 절차에 들어갔고 1.17에서 restic으로 새 백업을 만드는 기능이 빠졌다. 옛 restic 백업에서 복원하는 것은 한동안 남아 있다. 설치 출력의 `--uploader-type=kopia`가 그 결과다. 블로그나 사내 문서에 `--use-restic`, `restic` DaemonSet이 나오면 옛 버전 이야기다.

kopia 저장소에는 비밀번호가 있다. Velero는 설치할 때 `velero-repo-credentials` Secret에 기본 비밀번호를 만들어 둔다. 첫 백업 전에 바꾸지 않으면 버킷만 손에 넣은 사람도 기본값으로 저장소를 열 수 있다. 그리고 그 비밀번호를 잃으면 DR 클러스터에서 볼륨 데이터를 풀지 못하니 Velero 밖에도 보관한다.

## 다른 이름으로 되살리기

글 처음의 사고로 돌아가자. `shop` 네임스페이스를 백업에서 되살린다. 다만 바로 원래 이름으로 복원하기보다 다른 이름으로 먼저 복원해 내용을 확인하는 편이 안전하다. `--namespace-mappings`가 그 일을 한다.

```bash
# shop의 백업을 shop-restore-test라는 이름으로 되살린다. 운영 도메인을 가로채지 않게 Ingress는 뺀다
velero restore create shop-to-staging --from-backup shop-20261021 \
  --namespace-mappings shop:shop-restore-test --exclude-resources ingresses.networking.k8s.io -o yaml
```

```text
apiVersion: velero.io/v1
kind: Restore
metadata:
  creationTimestamp: null
  name: shop-to-staging
  namespace: velero
spec:
  backupName: shop-20261021
  excludedResources:
  - ingresses.networking.k8s.io
  hooks: {}
  includedNamespaces:
  - '*'
  itemOperationTimeout: 0s
  namespaceMapping:
    shop: shop-restore-test
  uploaderConfig: {}
status: {}
```

이 그림에서 가장 자주 빠뜨리는 것이 볼륨이다. EBS 스냅숏은 리전과 계정에 묶이므로, 다른 리전에서 되살리려면 데이터 이동이나 FSB로 버킷에 데이터를 올려 두어야 한다. 그리고 버킷 자체가 리전 장애에 같이 죽지 않도록 S3 복제로 다른 리전에 사본을 둔다.

DR 훈련을 하면 대개 이런 것들이 막힌다. 복원한 Pod가 운영 리전의 ECR 이미지를 가리킨다(Velero에는 복원 시 이미지 이름을 바꾸는 ConfigMap 설정이 있다). StorageClass 이름이 DR 클러스터에 없다(같은 방식의 StorageClass 매핑 설정이 있다). 오퍼레이터의 CRD 버전이 다르다. 그리고 [재해 복구](/posts/disaster-recovery)에서 말한 것처럼, 복원 순서를 문서로만 갖고 있던 팀은 거의 예외 없이 첫 훈련에서 한 번은 막힌다.

## 백업이 조용히 실패하는 자리

Velero 운영에서 실제로 문제가 되는 곳을 증상과 함께 적어 둔다.

- 백업이 `New`에서 안 움직인다: velero 서버 Pod가 없거나 CrashLoop이다. `kubectl -n velero logs deploy/velero`를 본다.
- `PartiallyFailed`가 매일 쌓인다: 대개 FSB의 특정 볼륨이나 훅 타임아웃이다. `velero backup describe <이름> --details`의 볼륨 목록과 `velero backup logs`에서 `error`를 찾는다. Completed만 성공으로 세는 알림이 없으면 몇 달 동안 아무도 모른다.
- BSL이 `Unavailable`이다: 자격 증명이나 버킷 정책이다. 이 상태에서는 백업이 올라가지 않는다.
- 복원했는데 아무것도 안 바뀌었다: 객체가 이미 있어 기본 정책 none으로 건너뛰었다. 복원 결과의 Warnings에 "already exists"가 찍힌다.
- 복원한 PVC가 Pending이다: 대상 클러스터에 같은 StorageClass가 없거나, CSI 스냅숏을 쓰는데 VolumeSnapshotClass가 없다.
- 백업 용량이 계속 늘어난다: TTL이 없는 수동 백업이 쌓였거나, kopia 저장소 정리(유지 보수 작업)가 실패하고 있다.

이 중 대부분은 복원해 보지 않으면 드러나지 않는다. 한 달에 한 번 최근 백업 하나를 `--namespace-mappings`로 다른 이름에 되살리고, Pod가 Ready가 되고 데이터가 맞는지 확인한 뒤 지우는 작업을 일정에 넣는다. 그게 이 글에서 가장 실무적인 한 줄이다.

## API로 뜨고 API로 되살린다

Velero는 etcd를 직접 뜨는 대신 API 서버에 객체를 물어 묶어 두고, 볼륨은 클라우드 스냅숏, CSI 스냅숏과 데이터 이동, 파일 시스템 백업 중 하나로 챙긴다. 그래서 네임스페이스나 라벨 단위로 뜨고, 이름을 바꿔 되살리고, 다른 클러스터로 옮길 수 있다. 버킷이 진실의 원천이라 같은 버킷을 붙이면 다른 클러스터에서 백업이 보이고, 그래서 복원하는 쪽은 ReadOnly로 붙인다. 클러스터 전체의 한 순간을 뜨는 etcd 스냅숏과는 맡는 사고가 다르다.

## 면접에서 나올 만한 질문

### Velero와 etcd 스냅숏은 무엇이 다른가요?

etcd 스냅숏은 저장소의 키공간 전체를 바이트 그대로 뜨고, 되돌리면 클러스터 전체가 그 시점으로 간다. Velero는 API 서버에 객체를 물어 JSON으로 묶어 두므로 네임스페이스·라벨 단위로 뜨고 되살릴 수 있고, 다른 클러스터로 옮길 수 있다. 대신 클러스터 전체의 한 순간이 아니고, 대상 클러스터에 같은 API 버전이 있어야 하며 더 낮은 쿠버네티스 버전으로는 복원하지 못한다. 관리형 클러스터에서는 etcd에 접근할 수 없어 Velero 쪽을 쓴다.

### BackupStorageLocation과 VolumeSnapshotLocation은 각각 무엇인가요?

BSL은 객체 묶음과 메타데이터, 파일 시스템 백업 데이터가 올라가는 오브젝트 스토리지의 버킷과 경로다. VSL은 클라우드 디스크 스냅숏을 만들 위치(공급자와 리전)다. BSL은 Velero가 진실의 원천으로 삼아, 버킷에 있는 백업을 클러스터 객체로 동기화한다. 그래서 다른 클러스터에서 같은 버킷을 ReadOnly로 붙이면 백업 목록이 보인다.

### 파일 시스템 백업과 CSI 스냅숏 데이터 이동은 어떻게 고르나요?

CSI 스냅숏을 지원하는 볼륨이면 데이터 이동이 낫다. 스냅숏으로 한 시점을 잡은 뒤 그 데이터를 버킷으로 옮기니 일관되고 리전·계정에서 독립적이다. 스냅숏이 없는 NFS, EFS, emptyDir 같은 볼륨은 파일 시스템 백업을 쓰는데, 살아 있는 파일을 읽어 한 시점이 아니라는 약점이 있다. 엔진은 kopia이고 restic 경로는 1.17에서 새 백업이 막혔다.

### 백업 훅은 언제 쓰고, 무엇을 조심하나요?

백업 순간에 앱의 디스크 상태를 맞추고 싶을 때 쓴다. Pod 어노테이션으로 pre·post 명령을 걸어 fsfreeze로 쓰기를 멈추거나 DB 체크포인트를 실행한다. 명령은 셸 없이 실행되고, 기본 on-error는 Fail, 타임아웃은 30초다. post 훅이 실행되지 않으면 freeze가 풀리지 않을 수 있어 사이드카로 분리하고, DB의 시점 복구는 Velero가 아니라 DB 도구로 한다.

### 네임스페이스를 바꿔 복원할 때 주의할 점은 무엇인가요?

`--namespace-mappings`는 객체의 namespace 필드만 바꾼다. ConfigMap 안의 서비스 주소, ClusterRoleBinding의 subjects, Ingress 호스트처럼 값 안에 박힌 이름은 그대로라 테스트 복원이 운영 리소스를 건드릴 수 있다. PV가 이미 있으면 velero-clone- 이름으로 새로 만든다. 그리고 이미 있는 객체는 기본 정책 none으로 건너뛰니, 덮어써야 하면 `--existing-resource-policy update`를 준다.

### 백업이 Completed가 아니라 PartiallyFailed로 끝나면 어떻게 하나요?

일부 항목이나 볼륨이 실패했다는 뜻이니 성공으로 세면 안 된다. `velero backup describe --details`로 어느 볼륨이 실패했는지, `velero backup logs`에서 오류 줄을 찾는다. 흔한 원인은 FSB 대상 볼륨의 권한, 훅 타임아웃, node-agent가 없는 노드다. 모니터링은 Completed만 성공으로 집계하고 그 외 상태에 알림을 건다.

### Velero 백업이 정말 쓸 만한지 어떻게 확인하나요?

정기적으로 복원해 본다. 최근 백업을 다른 네임스페이스 이름으로 되살려 PVC가 Bound되고 Pod가 Ready가 되며 데이터가 맞는지 확인하고 지운다. BSL이 Available인지, 백업 상태가 Completed인지, 마지막 성공 시각이 스케줄대로 갱신되는지도 지표로 본다. 복원 테스트 없이 쌓인 백업은 사고 날 처음 열어 보는 상자와 같다.
