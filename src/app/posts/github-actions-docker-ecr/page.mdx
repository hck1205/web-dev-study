저장소 Settings의 Secrets에 `AWS_ACCESS_KEY_ID`가 하나 들어 있다. 언제 누가 넣었는지 아무도 모르고, IAM 콘솔을 보면 그 키의 마지막 교체일이 2년 전이다. 같은 주에 운영에서 장애가 났는데 떠 있는 이미지 태그가 `latest`라서 어떤 커밋이 배포됐는지 바로 답하지 못했다.

두 문제 모두 GitHub Actions에서 이미지를 만들어 ECR에 올리는 워크플로를 처음 짤 때 정해진다. 이 글은 그 워크플로 한 장을 위에서부터 읽는다. 이벤트와 잡, 스텝의 뼈대, 오래 사는 키 대신 OIDC로 AWS 역할을 잠깐 빌리는 법, 커밋 SHA로 태그를 붙이는 이유, buildx 캐시를 Actions 캐시에 두는 법, 이미지 검사, 같은 브랜치 배포가 겹칠 때의 concurrency, environment로 운영 배포 앞에 문을 다는 법까지 간다.

Dockerfile 자체를 빠르고 작게 만드는 법은 [Dockerfile과 이미지 레이어](/posts/dockerfile-image-layers)에서, 이 이미지가 EKS까지 가는 전체 흐름은 [push에서 EKS까지 배포 파이프라인](/posts/k8s-deploy-pipeline-eks)에서 이어진다. 워크플로 검사는 actionlint 1.7.12로 직접 돌린 출력이다. 이 실습 환경에는 AWS 계정과 GitHub 러너가 없어서, AWS CLI와 Actions 로그는 실제 형식을 따른 예시이고 그때마다 예시라고 적는다. 액션 버전(`@v4`, `@v6`)은 글을 쓰는 시점의 메이저 버전이다.

## 워크플로 파일 한 장의 뼈대

워크플로는 `.github/workflows/` 아래의 YAML 파일 하나다. 큰 칸은 셋이다. `on`은 언제 돌지, `jobs`는 무엇을 할지, 각 잡의 `steps`는 그 일을 어떤 순서로 할지 적는다.

잡은 각자 깨끗한 러너(가상 머신) 하나에서 돈다. 같은 워크플로의 잡이라도 파일 시스템을 공유하지 않는다. 그래서 `test` 잡에서 만든 파일을 `build-push` 잡이 그냥 읽을 수 없다. 넘겨야 할 값은 `outputs`로, 파일은 아티팩트로 넘긴다. 잡 사이의 순서는 `needs`가 정한다. `needs`가 없으면 잡은 동시에 출발한다.

이 글에서 계속 볼 파일은 아래와 같다. 테스트, 이미지 빌드와 푸시, 배포 세 잡으로 되어 있다.

```yaml
name: ci-cd

on:
  push:
    branches: [main]
    paths:
      - "app/**"
      - "k8s/**"
      - ".github/workflows/ci-cd.yml"
  pull_request:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: ci-cd-${{ github.ref }}
  cancel-in-progress: true

env:
  AWS_REGION: ap-northeast-2
  ECR_REPOSITORY: shop-api

jobs:
  test:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"
          cache: maven
      - name: Unit test
        working-directory: app
        run: ./mvnw -B test

  build-push:
    needs: test
    if: github.event_name == 'push'
    runs-on: ubuntu-24.04
    permissions:
      contents: read
      id-token: write
    outputs:
      image: ${{ steps.meta.outputs.image }}
    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials (OIDC)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-ecr-push
          aws-region: ${{ env.AWS_REGION }}

      - name: Login to ECR
        id: ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: Image name
        id: meta
        run: echo "image=${{ steps.ecr.outputs.registry }}/${{ env.ECR_REPOSITORY }}:${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"

      - uses: docker/setup-buildx-action@v3

      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          context: app
          push: true
          tags: ${{ steps.meta.outputs.image }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

스텝은 두 종류다. `uses`는 남이 만든 액션을 가져다 쓰고, `run`은 셸 명령을 직접 친다. 스텝끼리는 같은 러너 안이라 파일과 환경을 공유한다. 한 스텝이 다음 스텝에 값을 넘길 때는 `$GITHUB_OUTPUT` 파일에 `이름=값`을 한 줄 쓰고, 뒤에서 `steps.<id>.outputs.<이름>`으로 읽는다. 잡 밖으로 내보내려면 잡의 `outputs`에 한 번 더 옮겨 적는다. `deploy` 잡이 `needs.build-push.outputs.image`로 이미지 이름을 받는 길이 이것이다.

`${{ }}`는 GitHub이 러너에 명령을 넘기기 전에 문자열을 치환하는 식이다. `$GITHUB_SHA`는 러너 안에서 셸이 읽는 환경 변수다. 같은 값이라도 언제 풀리는지가 다르고, 이 차이가 뒤에 나오는 스크립트 주입 문제로 이어진다.

## 언제 돌지는 이벤트와 경로가 정한다

`on.push.branches`는 어느 브랜치에 푸시될 때, `paths`는 어떤 파일이 바뀌었을 때만 돌지 정한다. README 한 줄 고쳤는데 이미지를 다시 굽고 배포까지 하면 시간과 돈이 샌다. 대신 경로를 너무 좁히면 워크플로 파일 자체를 고친 커밋이 안 돌아서 고친 게 맞는지 확인을 못 한다. 그래서 워크플로 파일 경로를 목록에 함께 넣었다.

`pull_request`에서는 테스트만 돌리고 이미지는 굽지 않는다. `build-push`의 `if: github.event_name == 'push'`가 그 일을 한다. PR 단계에서 이미지를 올리지 않는 이유가 하나 더 있다. 포크에서 온 PR은 저장소의 secrets를 받지 못하고, OIDC 토큰도 발급받지 못한다. 남의 코드가 내 클라우드 권한으로 도는 것을 막는 장치다. 아래 그림에서 두 실행이 같은 워크플로를 타도 어디서 갈리는지 본다.

이걸 피하려고 `pull_request_target`으로 바꾸고 PR의 코드를 체크아웃하면, 포크의 코드가 secrets를 들고 도는 구멍이 그대로 열린다.

브랜치를 어떻게 나누느냐에 따라 이 트리거도 달라진다. main 하나에 바로 합치는 흐름이면 main 푸시가 곧 배포고, release 브랜치를 두는 흐름이면 태그 푸시(`on.push.tags`)에 배포를 거는 편이 많다. 브랜치 전략은 [브랜치 전략](/posts/git-branching-strategy)에서 비교했다.

## 푸시하기 전에 actionlint로 걸러 낸다

워크플로 YAML은 문법이 틀려도 푸시해 보기 전까지 모른다. 그리고 틀린 키는 에러가 아니라 무시되는 경우가 많다. `branches`를 `branch`로 쓰면 브랜치 조건이 통째로 빠져서 모든 브랜치 푸시에 돈다. actionlint는 이런 실수를 로컬에서 잡는 정적 검사기다. 키 이름, 식 안의 프로퍼티, `needs`가 가리키는 잡, `run` 스크립트(shellcheck가 설치돼 있으면 함께 돌린다)까지 본다.

```bash
# Go로 설치한다 (Go 1.24 이상)
go install github.com/rhysd/actionlint/cmd/actionlint@latest
# shellcheck가 있으면 run 스크립트도 검사한다
sudo apt install -y shellcheck
# 저장소 루트에서 .github/workflows 아래를 모두 검사한다
actionlint
```

일부러 틀린 곳을 여섯 군데 넣은 파일을 검사했다.

## 오래 사는 키 대신 OIDC로 역할을 잠깐 빌린다

처음 질문으로 돌아간다. 저장소 secrets에 IAM 사용자의 액세스 키를 넣는 방식은 키가 만료되지 않는다는 게 문제다. 워크플로 로그나 의존성 하나에서 새면 누군가 그 키로 몇 달이고 계정을 쓴다. 교체하려면 IAM과 GitHub 양쪽을 손으로 바꿔야 해서 미루게 된다.

OIDC(OpenID Connect) 방식은 저장할 키가 없다. 잡이 돌 때마다 GitHub이 "이 잡은 acme/shop 저장소의 main 브랜치에서 돌고 있다"는 서명된 토큰(JWT)을 발급하고, AWS STS가 그 토큰을 확인한 뒤 한 시간짜리 임시 자격 증명을 내준다. 아래 그림에서 다음을 누르면 토큰과 자격 증명이 오가는 순서가 보인다.

AWS 쪽 준비는 두 가지다. 계정에 GitHub을 OIDC 공급자로 한 번 등록하고, 워크플로가 빌릴 역할을 만든다. 공급자 등록은 계정당 한 번이다.

```bash
# GitHub Actions를 OIDC 공급자로 등록한다 (계정당 한 번)
aws iam create-open-id-connect-provider \
  --url https://token.actions.githubusercontent.com \
  --client-id-list sts.amazonaws.com
```

공급자를 만들 때 예전에는 인증서 지문(thumbprint)을 꼭 넣어야 했지만, 지금 AWS는 GitHub 같은 주요 공급자에 대해서는 자체 신뢰 루트로 확인한다고 안내한다. Terraform이나 오래된 문서에 지문 값이 보이면 그 흔적이다.

## 신뢰 정책의 sub 조건이 문을 정한다

역할에는 정책이 두 장 붙는다. 권한 정책은 "이 역할로 무엇을 할 수 있나", 신뢰 정책은 "누가 이 역할을 빌릴 수 있나"를 적는다. OIDC에서 문지기는 신뢰 정책이다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
        },
        "StringLike": {
          "token.actions.githubusercontent.com:sub": "repo:acme/shop:ref:refs/heads/main"
        }
      }
    }
  ]
}
```

`sub` 조건이 빠지면 GitHub에 있는 아무 저장소나, 즉 남의 계정의 워크플로도 이 역할을 빌릴 수 있다. 공급자는 GitHub 전체에 하나라서 aud만으로는 내 저장소인지 가려지지 않는다. 그래서 sub는 반드시 적고, 와일드카드는 좁게 쓴다.

`sub`의 모양은 잡이 어떤 맥락에서 돌았느냐에 따라 바뀐다.

## ECR에 로그인하고 올리기

ECR은 AWS의 컨테이너 레지스트리다. Docker Hub처럼 `docker push`로 올리지만, 비밀번호 대신 IAM으로 인증한다. 저장소(repository)는 이미지 이름 하나에 해당하고, 미리 만들어 둬야 푸시가 된다.

```bash
# 저장소를 만든다. 태그 덮어쓰기를 막고 푸시할 때 검사한다
aws ecr create-repository \
  --repository-name shop-api \
  --image-tag-mutability IMMUTABLE \
  --image-scanning-configuration scanOnPush=true
```

```text
{
    "repository": {
        "repositoryArn": "arn:aws:ecr:ap-northeast-2:123456789012:repository/shop-api",
        "registryId": "123456789012",
        "repositoryName": "shop-api",
        "repositoryUri": "123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/shop-api",
        "createdAt": "2026-10-21T10:02:11.512000+09:00",
        "imageTagMutability": "IMMUTABLE",
        "imageScanningConfiguration": {
            "scanOnPush": true
        },
        "encryptionConfiguration": {
            "encryptionType": "AES256"
        }
    }
}
```

위 출력은 예시다. 볼 곳은 `repositoryUri`다. 이 주소가 이미지 이름의 앞부분이 된다. 로그인은 `amazon-ecr-login` 액션이 대신하지만, 안에서 하는 일은 손으로 치는 명령과 같다.

aws ecr get-login-password --region ap-northeast-2 \
  | docker login --username AWS --password-stdin 123456789012.dkr.ecr.ap-northeast-2.amazonaws.com

## 태그는 커밋 SHA로 붙인다

`latest` 하나로 배포하면 처음의 장애 상황이 된다. 지금 떠 있는 게 어느 커밋인지 레지스트리를 뒤져야 알고, 되돌리려면 "어제의 latest"를 찾아야 하는데 그런 이름은 없다. 쿠버네티스에서는 문제가 하나 더 있다. 매니페스트의 이미지 문자열이 `shop-api:latest`로 그대로면 템플릿이 바뀌지 않으니 롤링 업데이트가 일어나지 않는다. 노드마다 언제 받았느냐에 따라 다른 이미지가 돌기도 한다.

커밋 SHA로 태그를 붙이면 이미지와 코드가 일대일로 묶인다. 워크플로의 `${GITHUB_SHA::7}`은 bash의 문자열 자르기다. 로컬에서 같은 식을 돌려 보면 이렇게 나온다.

```bash
# 러너가 넣어 주는 GITHUB_SHA를 흉내 내고, 앞 7자리로 이미지 이름을 만든다
GITHUB_SHA=$(git rev-parse HEAD) bash -c 'echo "image=123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/shop-api:${GITHUB_SHA::7}"'
```

```text
image=123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/shop-api:5cf44af
```

정리하면 태그 규칙은 이렇게 잡는다. 배포에 쓰는 태그는 SHA, 릴리스에는 `v1.4.0` 같은 버전 태그를 하나 더, `latest`는 사람이 로컬에서 받아 볼 때만 쓴다. 저장소를 IMMUTABLE로 두면 같은 태그를 다른 이미지로 덮어쓰려 할 때 푸시가 막힌다. 그런 저장소에 `latest`를 매번 다시 올리면 두 번째부터 이렇게 실패한다(예시).

```text
tag invalid: The image tag 'latest' already exists in the 'shop-api' repository and cannot be overwritten because the repository is immutable.
```

더 단단하게 하려면 매니페스트에 태그 대신 다이제스트(`shop-api@sha256:...`)를 적는다. 태그는 사람이 읽기 좋고, 다이제스트는 누가 태그를 옮겨도 같은 내용을 보장한다. ArgoCD 같은 GitOps 도구와 이미지 서명 검사는 다이제스트를 기준으로 움직인다.

SHA 태그는 금방 쌓인다. 하루에 스무 번 배포하면 한 달에 600개다. ECR 수명 주기 정책으로 "태그 없는 이미지는 7일 뒤 삭제, SHA 태그는 최근 200개만" 같은 규칙을 걸어 둔다. 되돌릴 수 있는 범위가 그 숫자만큼이라는 점은 정해 두고 쓴다.

## buildx 캐시를 Actions 캐시에 둔다

GitHub이 주는 러너는 잡마다 새 머신이다. 로컬에서는 두 번째 빌드부터 레이어 캐시가 먹지만, 러너에서는 매번 처음부터 빌드한다. Maven 의존성 받는 데만 몇 분이 걸린다.

`docker/build-push-action`은 BuildKit(buildx)으로 빌드하고, 캐시를 바깥에 내보냈다가 다음 빌드에서 가져오는 기능이 있다. `cache-to: type=gha`는 그 캐시를 GitHub Actions 캐시 저장소에 둔다. `mode=max`는 최종 이미지에 남지 않는 빌드 스테이지의 레이어까지 저장한다. 멀티 스테이지 Dockerfile에서 의존성을 받는 빌드 스테이지가 캐시돼야 효과가 크므로 max를 쓴다. 기본값인 `min`은 최종 이미지의 레이어만 남긴다.

Actions 캐시에는 저장소마다 용량 한도(기본 10GB)가 있고, 넘치면 오래 안 쓴 것부터 지워진다. 오래 안 쓴 항목은 일주일쯤 지나면 사라진다. 그래서 첫 빌드나 오랜만의 빌드는 느린 게 정상이다. 2025년에 Actions 캐시 서비스가 새 버전으로 바뀌면서 오래된 buildx와 액션 버전의 gha 캐시가 동작하지 않게 됐다. 캐시가 계속 안 먹으면 `setup-buildx-action`과 `build-push-action`이 최신 메이저인지부터 본다. 캐시를 ECR에 두는 방법(`type=registry,ref=.../shop-api:buildcache`)도 있다. 용량 한도가 없고 여러 워크플로가 같이 쓰기 좋지만, ECR 저장 비용이 들고 캐시용 태그가 IMMUTABLE 설정과 부딪히므로 캐시 전용 저장소를 따로 둔다.

## 올린 이미지를 검사한다

`scanOnPush=true`로 만든 저장소는 푸시될 때마다 기본 스캔을 돈다. 베이스 이미지의 OS 패키지에 알려진 취약점(CVE)이 있는지 본다. Amazon Inspector를 켜는 확장 스캔은 Java, Python 같은 언어 패키지까지 보고, 새 CVE가 나오면 이미 올라간 이미지도 다시 검사한다. 결과는 CLI로 확인한다.

```bash
# 특정 태그의 스캔 결과를 심각도별 개수로 본다
aws ecr describe-image-scan-findings \
  --repository-name shop-api --image-id imageTag=5cf44af \
  --query 'imageScanFindings.findingSeverityCounts'
```

```text
{
    "HIGH": 2,
    "MEDIUM": 7,
    "LOW": 15
}
```

위 출력은 예시다. ECR 스캔은 푸시가 끝난 뒤에 돌기 때문에 워크플로를 멈추지 못한다. 취약한 이미지가 배포되는 것을 막고 싶으면 파이프라인 안에서 검사한다. 빌드한 이미지를 Trivy 같은 도구로 검사하고 CRITICAL이 있으면 실패시키는 스텝을 푸시 앞에 둔다. 처음부터 엄격하게 걸면 베이스 이미지의 고칠 수 없는 CVE 때문에 배포가 전부 멈춘다. 고칠 수 있는 것만(`--ignore-unfixed`) 막는 데서 시작하는 팀이 많다.

## 같은 브랜치 배포가 겹칠 때 concurrency

main에 3분 간격으로 두 번 합쳤다. 워크플로가 둘 돈다. 늦게 시작한 쪽의 빌드가 먼저 끝나서 새 이미지를 배포하고, 그 뒤에 먼저 시작한 쪽이 옛 이미지를 배포하면 운영에 옛 버전이 남는다.

`concurrency.group`은 같은 이름의 실행이 동시에 하나만 돌게 한다. 같은 그룹에는 도는 것 하나, 기다리는 것 하나만 있을 수 있고, 새로 들어온 실행이 기다리던 실행을 밀어낸다. `cancel-in-progress: true`면 도는 것까지 취소한다. 아래 그림에서 커밋 세 개가 연달아 들어올 때 무엇이 살아남는지 본다.

    { pointer: 0, memory: ["A 도는 중"], caption: "A가 들어와 바로 돈다." },
    { pointer: 1, memory: ["A 취소", "B 도는 중"], caption: "cancel-in-progress가 true라서 B가 들어오면 A가 취소되고 B가 돈다." },
    { pointer: 2, found: [2], memory: ["B 취소", "C 도는 중"], caption: "C가 들어오면 B도 취소된다. 마지막 커밋만 끝까지 간다." },

테스트와 빌드에는 이게 좋다. 어차피 버려질 결과에 러너를 쓰지 않는다. 배포 잡에는 위험하다. `kubectl apply` 도중에 취소되면 리소스 절반만 바뀐 상태로 남는다. 그래서 배포 잡에는 따로 그룹을 걸고 취소하지 않게 한다.

```yaml
  deploy:
    needs: build-push
    concurrency:
      group: deploy-production
      cancel-in-progress: false
```

이러면 배포는 차례로 하나씩 돈다. 기다리던 배포가 새 배포에 밀려 취소되는 것은 그대로라서, 결국 마지막 이미지가 배포된다. 그룹 이름에 `github.ref`를 넣으면 브랜치마다, `deploy-production`처럼 고정하면 저장소 전체에서 하나씩이다. PR마다 따로 돌려야 하는 미리보기 환경이면 `github.head_ref`를 넣는다.

## secrets와 environment로 운영 배포 앞에 문을 단다

secrets는 저장소, 조직, environment 세 단계에 둘 수 있다. 로그에 값이 그대로 찍히면 GitHub이 `***`로 가린다. 다만 값을 base64로 바꾸거나 한 글자씩 자르면 가려지지 않는다. 가림은 사고를 줄이는 장치이지 막는 장치가 아니다.

environment는 "운영" 같은 배포 대상에 규칙을 붙이는 단위다. 잡에 `environment: production`을 적으면 그 잡은 다음을 거친다.

- 지정한 사람의 승인을 받아야 시작한다(required reviewers). 저장소 요금제에 따라 쓸 수 있는 범위가 다르다.
- 정해진 브랜치나 태그에서만 배포된다(deployment branches). feature 브랜치의 워크플로가 운영에 배포하는 것을 막는다.
- 그 environment에만 둔 secrets를 그 잡만 읽는다. 운영 DB 비밀번호가 PR 테스트 잡에 보이지 않는다.

OIDC와 같이 쓰면 sub가 `environment:production`이 되므로, 운영 역할의 신뢰 정책을 이 sub에 묶는다. 그러면 승인 없이 운영 역할을 빌리는 길이 없어진다. 앞에서 본 sub 사고는 거꾸로 이 성질 때문에 생긴 것이다.

```yaml
  deploy:
    needs: build-push
    runs-on: ubuntu-24.04
    environment: production
    permissions:
      contents: read
      id-token: write
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-eks-deploy
          aws-region: ${{ env.AWS_REGION }}
      - name: Deploy
        env:
          IMAGE: ${{ needs.build-push.outputs.image }}
        run: ./scripts/deploy.sh "$IMAGE"
```

워크플로 맨 위의 `permissions: contents: read`도 같은 생각이다. `permissions`를 한 줄이라도 적으면 적지 않은 나머지 권한은 모두 없음이 된다. 그래서 OIDC가 필요한 잡에만 `id-token: write`를 따로 준다. 2023년 이후 새로 만든 저장소와 조직은 `GITHUB_TOKEN` 기본 권한이 읽기 전용이지만, 오래된 저장소는 쓰기가 기본인 경우가 있어 명시해 두는 편이 낫다.

## matrix로 여러 조합을 한 번에 돌린다

라이브러리를 Java 17과 21에서 모두 테스트해야 하거나, 서비스 셋을 같은 방식으로 빌드해야 할 때 잡을 복사하지 않고 matrix를 쓴다. 조합마다 잡이 하나씩 생겨 동시에 돈다.

```yaml
  test:
    runs-on: ubuntu-24.04
    strategy:
      fail-fast: false
      matrix:
        java: ["17", "21"]
        db: [postgres]
        include:
          - java: "21"
            db: mysql
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: ${{ matrix.java }}
      - run: ./mvnw -B test -Ddb=${{ matrix.db }}
        working-directory: app
```

이 설정은 (17, postgres), (21, postgres), (21, mysql) 세 잡을 만든다. `include`는 조합을 하나 더하고, `exclude`는 뺀다. `fail-fast`는 기본이 true라서 하나가 실패하면 나머지를 취소한다. 어느 조합이 왜 깨지는지 한 번에 보고 싶으면 false로 둔다. 한 워크플로 실행에서 matrix가 만들 수 있는 잡은 256개까지다.

이미지 빌드에 matrix를 쓸 때는 조심한다. 서비스마다 다른 이미지를 굽는 건 괜찮지만, 같은 이미지를 아키텍처별로 matrix로 나눠 구우면 태그 하나에 여러 아키텍처를 묶는 매니페스트를 따로 만들어야 한다. 그때는 build-push-action의 `platforms: linux/amd64,linux/arm64` 한 줄이 더 단순하다.

## 실패한 잡 로그에서 먼저 볼 줄

빨간 X가 뜨면 실패한 스텝을 펼쳐 맨 아래 `Error:` 줄부터 본다. 자주 만나는 것들은 이렇게 갈린다(로그는 예시).

`Credentials could not be loaded, please check your action inputs: Could not load credentials from any providers`가 나오고 그 위에 id-token 권한을 설정하려던 것 아니냐는 안내가 있으면 `permissions`에 `id-token: write`가 빠졌다. 워크플로 맨 위에만 적고 잡 단위 `permissions`를 따로 적었다면, 잡 단위 설정이 위를 덮어써서 빠진 것이다.

`Not authorized to perform sts:AssumeRoleWithWebIdentity`는 신뢰 정책이다. 저장소 이름의 대소문자, environment가 붙어 바뀐 sub, aud 값을 차례로 맞춰 본다. AWS CloudTrail의 `AssumeRoleWithWebIdentity` 실패 이벤트에 들어온 sub가 남는다.

`denied: User: arn:aws:sts::123456789012:assumed-role/gha-ecr-push/... is not authorized to perform: ecr:InitiateLayerUpload`처럼 역할 이름이 보이면 역할은 빌렸고 권한 정책이 모자란 것이다. 저장소 ARN이 정책의 Resource와 맞는지 본다.

`name unknown: The repository with name 'shop-api' does not exist`는 ECR 저장소를 안 만들었거나 리전이 다르다. `aws-region`과 저장소를 만든 리전이 같은지 본다.

빌드가 매번 처음부터 돈다면 로그의 `importing cache manifest from gha:` 줄 다음에 캐시를 찾지 못했다는 메시지가 있는지 본다. 브랜치마다 캐시 범위가 나뉘어 있어서, 새 브랜치의 첫 빌드는 기본 브랜치의 캐시만 읽을 수 있다.

## 키를 저장하지 않는 파이프라인

처음의 두 문제는 이렇게 풀린다. 저장소 secrets에서 AWS 키를 지우고, 잡마다 OIDC로 한 시간짜리 자격 증명을 빌린다. 누가 빌릴 수 있는지는 신뢰 정책의 sub가 정하고, environment를 붙이면 운영 역할은 승인을 거친 잡만 빌린다. 이미지는 커밋 SHA로 태그를 붙여 어떤 코드가 떠 있는지 바로 답하고, IMMUTABLE 저장소로 태그가 옮겨지지 않게 한다. 이 이미지를 클러스터에 올리는 매니페스트를 저장소 어디에 어떻게 두는지는 [쿠버네티스 프로젝트 폴더 구조](/posts/k8s-project-structure)에서 이어 본다.

## 면접에서 나올 만한 질문

### GitHub Actions에서 AWS에 접근할 때 액세스 키 대신 OIDC를 쓰는 이유는?

저장해 둘 장기 키가 없어지기 때문이다. 잡마다 GitHub이 서명한 토큰을 받아 STS에서 한 시간짜리 자격 증명으로 바꾸므로, 새더라도 금방 만료되고 교체할 키도 없다. 누가 역할을 빌릴 수 있는지를 저장소, 브랜치, environment 단위로 신뢰 정책에 적을 수 있다는 것도 장점이다.

### 신뢰 정책에서 sub 조건을 빼면 어떻게 되나?

GitHub의 아무 저장소에서나 그 역할을 빌릴 수 있게 된다. OIDC 공급자는 GitHub 전체에 하나이고 aud는 보통 `sts.amazonaws.com`으로 같기 때문에, 내 저장소인지 가르는 건 sub뿐이다. 그래서 sub는 반드시 저장소와 ref, 또는 environment까지 좁혀 적고 `repo:acme*`처럼 슬래시 앞에서 끝나는 와일드카드는 피한다.

### 잘 되던 OIDC 인증이 environment를 붙인 뒤로 실패한다. 왜인가?

잡에 environment가 붙으면 토큰의 sub가 `repo:org/repo:ref:refs/heads/main`에서 `repo:org/repo:environment:production`으로 바뀐다. 신뢰 정책이 ref 모양으로 맞춰져 있으면 `Not authorized to perform sts:AssumeRoleWithWebIdentity`가 난다. 운영 배포 역할은 environment sub에 묶는 게 오히려 맞는 설계라서, 정책을 그 sub로 고친다.

### 이미지 태그를 latest 대신 커밋 SHA로 붙이는 이유는?

떠 있는 이미지가 어느 코드인지 바로 알고, 그 태그로 되돌릴 수 있기 때문이다. 쿠버네티스에서는 이미지 문자열이 바뀌어야 Pod 템플릿이 바뀌어 롤링 업데이트가 일어나는데, latest는 문자열이 그대로라 배포가 안 된다. 저장소를 IMMUTABLE로 두면 태그가 다른 이미지로 옮겨지는 것도 막는다. 더 엄격하게는 다이제스트로 고정한다.

### buildx 캐시의 mode=max와 min은 무엇이 다른가?

min은 최종 이미지에 들어간 레이어만 캐시로 내보내고, max는 중간 빌드 스테이지의 레이어까지 내보낸다. 멀티 스테이지 빌드에서 의존성을 받는 단계는 최종 이미지에 남지 않으므로 min이면 매번 다시 받는다. 대신 max는 캐시 용량을 더 써서, 저장소당 용량 한도가 있는 gha 캐시에서는 오래된 항목이 더 빨리 밀려난다.

### concurrency의 cancel-in-progress를 배포 잡에 켜면 무엇이 위험한가?

배포가 도중에 취소되면 리소스 일부만 바뀐 상태로 남는다. 테스트나 빌드는 취소해도 결과를 버리면 그만이지만, `kubectl apply`나 `terraform apply`는 중간에 끊기면 사람이 정리해야 한다. 배포 잡은 고정된 그룹에 cancel-in-progress를 false로 두어 차례로 돌게 하고, 기다리던 실행만 새 실행에 밀려나게 한다.

### 포크에서 온 PR에서는 왜 이미지를 올리지 못하나?

`pull_request` 이벤트로 도는 포크 PR에는 저장소 secrets가 전달되지 않고 OIDC 토큰도 발급되지 않는다. 남이 고친 코드가 내 클라우드 권한으로 도는 것을 막기 위해서다. 이를 피하려고 `pull_request_target`에서 PR 코드를 체크아웃해 빌드하면 바로 그 구멍이 열리므로, PR에서는 테스트만 돌리고 이미지는 합친 뒤 main에서 굽는다.

### 워크플로의 run에 `${{ github.event.head_commit.message }}`를 바로 쓰면 무엇이 문제인가?

스크립트 주입이 된다. `${{ }}`는 셸이 실행하기 전에 문자열로 치환되므로 메시지에 따옴표와 명령을 넣으면 그대로 실행된다. 외부에서 들어오는 값은 `env:`로 환경 변수에 넣고 셸에서 `"$MSG"`로 읽는다. actionlint가 이런 사용을 경고로 잡아 준다.
