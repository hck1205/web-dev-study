`curl https://...`로 12바이트짜리 HTML 하나를 받았다. 요청 헤더가 82바이트, 응답 헤더가 186바이트다. 다 합쳐도 300바이트가 안 되는 대화인데, 같은 순간 랜 카드를 지나간 프레임을 세어 보니 17개, 3393바이트였다. 내용물보다 열 배 넘는 바이트가 선을 탄 셈이다. 나머지 3100바이트는 어디서 왔을까.

이 글은 HTTPS 요청 하나가 선 위에서 어떤 모양인지 바이트 단위로 뜯어 본다. 층마다 붙는 헤더가 몇 바이트이고 왜 그 크기인지, TLS가 얹는 몫, 큰 파일을 받을 때 내용물 대비 선을 타는 바이트의 비율, 터널이 한 겹 더 씌울 때의 비용, 그리고 tcpdump에 MTU보다 큰 "패킷"이 찍히는 이유까지 실제 캡처로 본다.

캡슐화라는 개념 자체와 층마다 데이터를 부르는 이름, 평문 HTTP의 SYN 한 장을 16진수로 읽는 법은 [OSI 7계층 글](/posts/network-layers-overview)에서 다뤘다. 여기서는 그 다음 질문, "그래서 실제로 몇 바이트가 드나" 와 "TLS를 얹으면 무엇이 달라지나"에 답한다. tcpdump 옵션과 필터는 [tcpdump 글](/posts/packet-capture-tcpdump)을 참고한다. 기준 OS는 Ubuntu 24.04, 실습은 네트워크 네임스페이스 두 개(클라이언트 `10.0.1.10`, 서버 `10.0.1.20`)를 veth로 이은 망이다. 서버는 파이썬 `http.server`에 TLS 1.3 인증서를 물렸고, 클라이언트는 curl 8.5다. 출력은 모두 실제 캡처다.

## 요청 하나가 만든 17개의 프레임

캡처를 걸고 HTTPS 요청을 한 번 보냈다.

```bash
# 클라이언트 쪽: 443 포트 트래픽을 파일로 남긴다
sudo tcpdump -i eth0 -nn -w small.pcap tcp port 443
# 다른 터미널: HTTP/1.1로 작은 파일 하나를 받는다. 요청·응답 헤더 크기도 찍는다
curl -s --http1.1 --cacert cert.pem -o /dev/null \
  -w 'http=%{http_code} size=%{size_download} req=%{size_request} hdr=%{size_header}\n' \
  https://10.0.1.20/index.html
```

```text
http=200 size=12 req=82 hdr=186
```

```text
* SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384 / X25519 / id-ecPublicKey
```

캡처 파일의 프레임마다 헤더 크기와 그 안에 든 TLS 레코드를 세는 짧은 파이썬 스크립트를 돌렸다(pcap을 읽어 IP 헤더 길이, TCP 데이터 오프셋, TLS 레코드 헤더 5바이트를 차례로 따라가는 30줄짜리다).

순서대로 읽으면 대화가 보인다.

- 1~3: TCP 3-way handshake. 내용물이 없는 프레임 세 장이다. SYN과 SYN-ACK의 TCP 헤더가 40바이트인 건 MSS, SACK, 타임스탬프, 윈도 스케일 옵션 20바이트가 붙어서다.
- 4: ClientHello 517바이트. 지원하는 암호 목록과 키 교환용 공개 키가 들어 있다. 도메인으로 접속하면 접속할 이름(SNI)도 여기에 평문으로 실린다. 이 실습은 IP로 접속해서 SNI가 없다.
- 6: 서버의 답 778바이트. ServerHello(122)만 평문이고, 그 뒤 인증서(437), 서명(96), Finished(69)는 이미 암호화되어 ApplicationData로 포장돼 있다. TLS 1.3은 핸드셰이크 도중부터 암호화한다.
- 8: 클라이언트 Finished.
- 9: 드디어 HTTP 요청. 평문 82바이트가 TLS 레코드 104바이트가 됐다.
- 10, 12의 첫 레코드: 서버가 보낸 세션 티켓 두 장(다음 연결을 빨리 맺기 위한 것).
- 12의 둘째·셋째 레코드: HTTP 응답 헤더 186바이트(203)와 본문 12바이트(29).
- 14: 연결을 닫는다는 TLS 알림(close_notify). 15~17은 TCP 종료.

쓸모 있는 바이트는 요청 82 + 응답 198, 280바이트다. 선을 탄 프레임은 3393바이트이고, 이더넷이 프레임마다 앞뒤로 붙이는 24바이트(뒤에서 본다)까지 넣으면 3801바이트다. 7.4%만 내용물이다. 작은 요청에서 바이트를 먹는 건 헤더보다 연결을 맺고 끊는 비용, 특히 인증서다. 연결 재사용(keep-alive)과 HTTP/2의 다중화, TLS 세션 재개가 왜 중요한지가 숫자로 보인다. TLS 핸드셰이크의 각 메시지가 무엇을 하는지는 [HTTPS와 TLS 글](/posts/https-tls)에 있다.

## 요청 프레임 한 장을 바이트로 뜯기

9번 프레임, HTTP 요청이 든 170바이트를 16진수로 찍었다.

```bash
# 저장한 파일에서 요청이 든 프레임만 골라 MAC(-e), 자세히(-v), 전체 hex(-XX)로 본다
tcpdump -nn -e -v -XX -r small.pcap 'tcp[((tcp[12]>>4)*4)]=0x17 and len==170'
```

내용물 82바이트에 TLS가 22바이트(헤더 5, 종류 1, 태그 16), TCP가 32바이트, IP가 20바이트, 이더넷이 14바이트를 얹었다. 그런데 이게 끝이 아니다. 캡처에 안 보이는 바이트가 더 있다.

## 캡처에 찍히지 않는 24바이트

tcpdump가 보여 주는 `length 170`은 이더넷 헤더부터 내용 끝까지다. 실제 선 위에는 그 앞뒤에 더 있다.

- 프리앰블과 SFD 8바이트: 받는 쪽 랜 카드가 클럭을 맞추라고 보내는 `10101010...` 패턴과 "여기서부터 프레임"이라는 표시
- FCS 4바이트: 프레임 끝의 CRC32 오류 검사값. 랜 카드가 붙이고 떼서 캡처에는 보통 안 남는다
- IFG(프레임 사이 간격) 12바이트: 프레임 사이에 반드시 비워 두는 시간. 바이트로 치면 12바이트만큼 선을 못 쓴다

합쳐서 프레임마다 24바이트다. 이더넷에는 최소 크기도 있다. FCS를 뺀 프레임이 60바이트보다 작으면 0으로 채워(padding) 보낸다. TCP 타임스탬프가 붙은 빈 ACK는 66바이트라 패딩이 필요 없지만, 옵션 없는 빈 ACK(54바이트)는 60바이트로 늘어난다.

## 큰 파일은 얼마나 효율적인가

작은 요청은 헤더가 내용물보다 크다. 큰 파일은 어떨까. 1MiB(1,048,576바이트) 파일을 같은 방식으로 받으며 서버 쪽에서 찍었다. 이때 서버의 TSO와 GSO를 껐다(이유는 다음 절에서 본다).

```bash
# 서버: 세그먼트 분할을 랜 카드(여기선 veth)에 맡기지 않게 한다
sudo ethtool -K eth0 tso off gso off
# 서버에서 보낸 세그먼트의 TCP 내용 길이 분포
tcpdump -nn -r big.pcap 'src port 443' | awk '{for(i=1;i<=NF;i++) if($i=="length") print $(i+1)}' | sort -n | uniq -c | sort -rn | head -4
```

```text
    709 1448
     46 478
      3 0
      1 961
```

세그먼트 대부분이 1448바이트다. MTU 1500에서 IP 20, TCP 20, 타임스탬프 12를 빼면 1448이다. SYN에서 알린 MSS는 1460이지만, 옵션이 매번 붙으니 실제로 싣는 건 1448이다. 478바이트짜리 46개는 TLS 레코드 경계에서 남은 조각이다.

같은 캡처를 스크립트로 합산했다.

```text
{'S': 1101800, 'C': 14260} {'S': 762, 'C': 205} {'S': 1051500, 'C': 722}
records 73 [(16401, 64), (250, 2), (122, 1), (1, 1), (23, 1)]
```

서버는 프레임 762장, 1,101,800바이트를 보냈다. TCP가 실은 내용은 1,051,500바이트, 그중 TLS 레코드는 16,401바이트짜리가 64개다. TLS 1.3 레코드의 평문 최대 크기가 16,384(2^14)바이트라 큰 응답은 이 크기로 잘려 각각 17바이트(종류 1 + 태그 16)와 헤더 5바이트를 단다. 레코드당 22바이트, 0.13%라서 TLS가 큰 전송에 얹는 몫은 작다.

선 위의 24바이트까지 넣으면 1,101,800 + 762 × 24 = 1,120,088바이트다. 파일 1,048,576바이트를 받는 데 93.6%의 효율이다. 한 세그먼트로 보면 1448바이트를 싣는 데 1538바이트(1514 프레임 + 24)를 쓰니 94.1%가 상한이다. 1Gbps 링크에서 파일 전송이 940Mbps 근처에서 멈추는 이유다. 거기에 클라이언트가 돌려보낸 ACK 205장(14,260바이트)이 반대 방향을 쓴다.

내용물 크기, MSS, TCP 옵션 크기로 선 위의 바이트를 계산하는 함수를 짜 보자. 프레임 최소 크기 60바이트(FCS 제외)도 지켜야 한다.

## tcpdump에 MTU보다 큰 패킷이 찍힐 때

앞의 실험을 처음에는 TSO를 켠 채로 했다. 그때 서버 쪽 캡처는 이랬다.

## 한 겹 더 씌우면 줄어드는 자리

봉투는 더 늘어날 수 있다. VPN이나 오버레이 망은 원래 패킷 전체를 새 헤더로 한 번 더 싼다. 그만큼 안쪽 패킷이 쓸 수 있는 자리가 준다. 많이 쓰는 것들의 추가 바이트다.

| 감싸는 것 | 추가 바이트 | 구성 |
|---|---|---|
| 802.1Q VLAN 태그 | 4 | 프레임 안에 끼우므로 IP MTU는 그대로, 프레임이 1522로 커진다 |
| PPPoE | 8 | PPPoE 6 + PPP 2. 가정용 회선 MTU가 1492인 이유 |
| GRE (IPv4) | 24 | 바깥 IP 20 + GRE 4 |
| VXLAN (IPv4) | 50 | 바깥 이더넷 14 + IP 20 + UDP 8 + VXLAN 8 |
| WireGuard (IPv4) | 60 | 바깥 IP 20 + UDP 8 + WG 헤더 16 + 태그 16. 안쪽 패킷을 16의 배수로 채우는 몇 바이트가 더 붙을 수 있다 |
| IPsec ESP 터널 | 약 50~70 | 바깥 IP, ESP 헤더, IV, 패딩, 무결성 값. 암호 방식과 패딩에 따라 달라진다 |

바깥 선의 MTU가 1500이면 VXLAN 안쪽은 1450, WireGuard 안쪽은 1420이 된다. WireGuard 기본 MTU가 1420인 이유다. 안쪽 TCP가 이걸 모르고 1460짜리 MSS로 보내면 큰 패킷만 사라지는 장애가 난다. 그 증상과 MSS 클램핑은 [MTU와 단편화 글](/posts/layer-mtu-fragmentation)에서 자세히 다뤘다. VXLAN 자체는 [VXLAN 오버레이 글](/posts/sdn-vxlan-overlay)에, WireGuard는 [VPN 글](/posts/vpn-ipsec-wireguard)에 있다.

## 프로토콜을 바꾸면 달라지는 몫

같은 요청도 프로토콜에 따라 헤더 몫이 다르다. 실습은 HTTP/1.1 over TLS 1.3 over IPv4였다. 다른 조합에서 바뀌는 부분만 짚는다.

- IPv6: IP 헤더가 20에서 40바이트로 늘어난다. 꽉 찬 세그먼트의 내용이 1448에서 1428로 준다. 대신 라우터가 체크섬을 다시 계산하지 않아도 된다(IPv6 헤더에는 체크섬이 없다). 자세한 건 [IPv6 글](/posts/ipv6-basics).
- HTTP/2: TLS 레코드 안에서 다시 프레임으로 나눈다. 프레임마다 9바이트 헤더가 붙지만 헤더 압축(HPACK)으로 반복되는 요청 헤더가 몇 바이트로 줄어서, 요청이 많을수록 오히려 바이트가 준다. 연결 하나에 요청 여러 개를 섞어 보내니 핸드셰이크 비용도 한 번만 낸다.
- HTTP/3(QUIC): TCP 대신 UDP 8바이트에 QUIC 헤더와 태그를 붙인다. 짧은 헤더는 플래그 1바이트, 연결 ID(0~20바이트), 패킷 번호(1~4바이트)로 되어 있고, 인증 태그 16바이트는 TLS처럼 붙는다. 대신 TCP 타임스탬프 12바이트가 없고, 연결과 TLS 핸드셰이크를 한 번에 해서 왕복이 준다. [UDP와 QUIC 글](/posts/udp-and-quic)에 있다.

수치보다 중요한 건 비율이다. 큰 전송에서 헤더 몫은 몇 퍼센트로 고정되고, 작은 요청에서는 핸드셰이크와 헤더가 대부분을 차지한다. 그래서 작은 요청이 많은 API는 연결 재사용, HTTP/2, 헤더 크기(쿠키!)를 먼저 보고, 큰 전송은 MTU와 오프로드, 혼잡 제어를 먼저 본다.

## 현장에서 바이트를 세야 할 때

몇 바이트가 붙는지 알면 숫자가 이상할 때 바로 의심할 곳이 생긴다.

"1Gbps 회선인데 파일 전송이 940Mbps밖에 안 나온다"는 정상이다. 위에서 계산한 94%가 헤더와 프레임 간격의 몫이다. 반대로 "VPN을 붙였더니 큰 파일만 멈춘다"는 정상이 아니다. 터널의 60바이트를 MTU에서 빼지 않아 큰 패킷이 버려지는 경우가 대부분이다.

```bash
# 경로 MTU를 확인한다: DF를 걸고 크기를 줄여 가며 ping (1472 = 1500 - IP 20 - ICMP 8)
ping -M do -s 1472 -c 1 10.0.1.20

ip link show eth0
ethtool -k eth0 | grep -E 'segmentation|receive-offload|checksumming'
```

```text
PING 10.0.1.20 (10.0.1.20) 1472(1500) bytes of data.
1480 bytes from 10.0.1.20: icmp_seq=1 ttl=64 time=0.037 ms
```

`1472(1500)`은 ICMP 내용 1472바이트가 IP 패킷 1500바이트가 된다는 뜻이다. 1바이트만 늘려 1473으로 보내면 내 쪽에서 바로 거절된다.

```text
PING 10.0.1.20 (10.0.1.20) 1473(1501) bytes of data.
ping: local error: message too long, mtu=1500
```

WireGuard 터널(MTU 1420) 너머로 같은 시험을 한다면 1472는 막히고 1392(1420 − 28) 이하만 통과해야 맞다. 크기를 줄여 가며 처음 통과하는 값이 경로의 진짜 MTU를 알려 준다.

대역폭을 계획할 때도 쓴다. 작은 메시지를 아주 많이 보내는 서비스(IoT, 게임, 메트릭 수집)는 내용물보다 헤더가 더 많은 바이트를 먹는다. 100바이트 메시지라면 TCP와 TLS를 거쳐 선 위에서 두 배 넘게 커진다. 메시지를 모아 보내거나(배치), 연결을 재사용하거나, 바이너리 포맷으로 바꾸는 게 효과가 큰 이유다.

캡처를 볼 때는 세 가지를 기억한다. 보내는 쪽 캡처의 큰 length와 `cksum incorrect`는 오프로드 착시다. `length`는 FCS와 프리앰블을 뺀 값이다. 그리고 TLS 안은 보이지 않아도 길이는 보인다. 레코드 길이에서 22를 빼면 평문 크기가 나오니, 암호화돼 있어도 "요청이 82바이트였다"는 건 알 수 있다. 민감한 서비스에서 응답 크기로 내용을 추측하는 공격을 막으려고 TLS 1.3이 레코드 패딩을 허용하는 이유다.

## 3393바이트의 내역

처음의 질문으로 돌아가면, 280바이트짜리 대화가 3393바이트가 된 건 TCP 연결과 종료 프레임, ClientHello와 인증서, 세션 티켓, 그리고 모든 프레임에 붙는 66바이트(이더넷 14, IP 20, TCP 32)와 TLS 레코드마다 붙는 22바이트 때문이다. 큰 파일에서는 이 몫이 6% 남짓으로 줄어든다. 바이트를 아끼려면 작은 요청은 연결을 다시 쓰고, 큰 전송은 MTU를 터널에 맞춘다. 이 지식이 쓰이는 전체 그림은 [네트워크 필수 개념 지도](/posts/networking-essentials-map)에 정리했다.

## 면접에서 나올 만한 질문

### HTTPS 요청 하나가 선 위에서 어떤 헤더를 입나요?

바깥부터 이더넷 14바이트, IPv4 20바이트, TCP 20바이트와 옵션(타임스탬프면 12바이트), TLS 레코드 헤더 5바이트가 붙고, 안에 암호화된 HTTP 요청과 GCM 인증 태그 16바이트가 있다. TLS 1.3은 진짜 레코드 종류 1바이트를 암호문 안에 숨긴다. 실습에서 82바이트 요청은 TLS 104, TCP 136, IP 156, 이더넷 170바이트가 됐고, 선 위에서는 FCS와 프리앰블, 프레임 간격 24바이트가 더 든다.

### 1Gbps 링크에서 TCP 처리량이 1Gbps가 나오지 않는 이유는요?

헤더와 이더넷 프레임 사이 비용 때문에 내용물이 차지할 수 있는 비율에 상한이 있다. 타임스탬프를 쓰는 TCP는 세그먼트당 1448바이트를 싣는 데 1538바이트어치 선을 쓰니 약 94%다. 그래서 940Mbps 근처가 정상이고, 실습의 1MiB HTTPS 전송도 선 위 바이트 대비 93.6%였다. 이보다 훨씬 낮다면 혼잡 제어, 창 크기, 손실 같은 다른 원인을 봐야 한다.

### TLS가 붙이는 오버헤드는 얼마나 되나요?

데이터 전송 단계에서는 레코드마다 헤더 5, 숨긴 종류 1, 인증 태그 16으로 22바이트다. 레코드 평문 최대가 16KB라 큰 전송에서는 0.13% 정도로 작다. 무거운 건 핸드셰이크다. ClientHello와 인증서 체인이 수 KB를 쓰고 왕복이 필요해서, 작은 요청이 많을 때는 연결 재사용과 세션 재개가 효과가 크다.

### tcpdump에서 MTU보다 큰 패킷이 보이는데 문제인가요?

대개 문제가 아니라 TSO나 GSO 같은 세그먼트 오프로드 때문이다. 커널이 큰 덩어리를 랜 카드에 넘기고 랜 카드가 MSS 크기로 자르는데, tcpdump는 자르기 전 덩어리를 본다. 받는 쪽에서는 GRO가 합친 덩어리가 보인다. 같은 이유로 보내는 쪽 캡처의 체크섬 오류 표시도 착시다. 선 위의 모양을 봐야 하면 상대 쪽에서 찍거나 잠깐 `ethtool -K`로 오프로드를 끈다.

### VPN 터널을 쓰면 MTU를 왜 줄여야 하나요?

터널이 원래 패킷 전체를 새 헤더로 다시 싸기 때문이다. WireGuard는 IPv4에서 60바이트, VXLAN은 50바이트를 더 쓰니 바깥 MTU가 1500이면 안쪽은 1420, 1450이 된다. 안쪽 TCP가 이걸 모르고 큰 세그먼트를 보내면 터널 앞에서 버려지거나 쪼개지고, ICMP가 막혀 있으면 큰 패킷만 사라진다. 터널 인터페이스 MTU를 낮추거나 MSS 클램핑으로 맞춘다.

### TLS로 암호화하면 패킷 크기로부터 아무것도 알 수 없나요?

아니다. AES-GCM 같은 방식은 평문 길이를 바꾸지 않아서 레코드 길이에서 22바이트를 빼면 평문 크기가 나온다. 실습에서 99바이트 레코드를 보고 82바이트 요청임을 알 수 있었다. 응답 크기와 타이밍으로 어떤 페이지를 봤는지 추측하는 공격이 있어서, TLS 1.3은 레코드 패딩을 허용하고 민감한 서비스는 응답 크기를 일정하게 맞추기도 한다.
