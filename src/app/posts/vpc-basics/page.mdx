EC2 인스턴스를 하나 띄워 nginx를 올렸다. 브라우저에서 `http://54.180.x.x`로 접속하면 페이지가 잘 뜬다. 그런데 서버에 SSH로 들어가 `ip addr`을 쳐 보면 그 공인 IP가 어디에도 없다. 랜카드에 붙은 주소는 `10.0.1.10` 하나뿐이다. 같은 날 DB 서버를 "외부에서 못 들어오게" 다른 서브넷에 만들었더니, 이번에는 그 서버에서 `apt update`가 멈춘다.

두 장면 모두 VPC(Virtual Private Cloud)가 어떻게 생겼는지 알면 바로 설명된다. 이 글은 VPC가 왜 생겼는지, 어떤 부품으로 이루어지는지, 패킷이 그 부품들을 어떤 순서로 지나는지를 본다. 실제 AWS 계정 대신 Ubuntu 24.04의 네트워크 네임스페이스로 VPC 하나를 흉내 내서 패킷이 지나는 모습을 직접 확인한다. 서브넷과 라우트 테이블은 [다음 글](/posts/vpc-subnets-route-tables)에서, VPC끼리 잇는 법은 [피어링·Transit Gateway·PrivateLink 글](/posts/vpc-peering-transit-privatelink)에서, 방화벽은 [보안 그룹과 NACL 글](/posts/security-groups-nacl)에서 더 깊게 판다.

AWS 용어로 설명하지만 GCP와 Azure도 뼈대는 같다. 차이가 나는 곳은 그때그때 적는다.

## 남의 건물 안에 내 층을 하나 빌린다

클라우드 초기의 EC2(EC2-Classic)는 모든 고객의 인스턴스가 하나의 거대한 평면 네트워크에 섞여 있었다. 주소는 AWS가 아무거나 줬고, 내 서버 옆자리에 누가 있는지 알 수 없었다. 회사 데이터센터에서 하던 일, 그러니까 "우리 대역은 `10.0.0.0/16`, DB는 밖에서 못 들어오는 망에, 웹만 인터넷에 노출" 같은 설계를 그대로 옮길 방법이 없었다.

VPC는 이 문제를 풀려고 2009년에 나왔다. 클라우드 사업자의 거대한 물리망 위에, 고객마다 논리적으로 분리된 사설망을 하나씩 만들어 준다. 이 글에서는 VPC를 "남의 건물 안에 빌린 내 층"으로 생각하겠다. 층 안의 방 배치(서브넷), 복도 안내판(라우트 테이블), 건물 정문(인터넷 게이트웨이), 방문마다 선 경비(보안 그룹)를 내가 정한다. 다른 층 사람과 같은 방 번호(같은 IP 대역)를 써도 서로 섞이지 않는다.

이 격리가 소프트웨어로 된다는 점이 물리망과 다르다. 실제로는 호스트의 하이퍼바이저와 네트워크 카드(AWS는 Nitro 카드)가 모든 패킷에 "이건 어느 VPC의 패킷인가"를 붙여 캡슐화해서 물리망으로 보낸다. 그래서 스위치를 사거나 케이블을 꽂지 않고 API 호출 한 번으로 망을 만들고 지운다. 이런 오버레이의 원리는 [VXLAN 오버레이 글](/posts/sdn-vxlan-overlay)에서 따로 본다.

2013년 12월 이후에 만든 AWS 계정은 처음부터 VPC만 쓸 수 있었고, EC2-Classic은 2023년에 완전히 종료됐다. 지금 AWS에서 인스턴스를 띄운다는 건 항상 어떤 VPC의 어떤 서브넷에 띄운다는 뜻이다.

- VPC는 리전 하나에 속하고, 그 리전의 모든 가용 영역(AZ, 같은 리전 안에서 전원과 네트워크가 분리된 데이터센터 묶음)에 걸친다.
- 서브넷은 AZ 하나에만 속한다. 서브넷 하나를 두 AZ에 걸칠 수 없다. 그래서 고가용성 설계는 "AZ마다 서브넷 하나씩"으로 시작한다.
- 인스턴스는 서브넷에 직접 붙지 않고 ENI(Elastic Network Interface, 가상 랜카드)를 꽂아서 붙는다. 사설 IP, 보안 그룹, MAC 주소는 모두 ENI의 속성이다. ENI를 떼어 다른 인스턴스에 붙이면 IP도 따라간다.

GCP는 여기서 다르다. GCP의 VPC 네트워크는 전역(global) 자원이고 서브넷이 리전 단위다. 그래서 서울과 도쿄 서브넷이 피어링 없이 한 VPC 안에서 바로 통한다. Azure의 VNet은 AWS처럼 리전 단위다.

## VPC를 이루는 부품

VPC 하나를 만들면 기본으로 따라오는 것과 내가 붙여야 하는 것이 있다.

- CIDR 블록: VPC가 쓸 사설 대역. AWS는 `/16`(65,536개)부터 `/28`(16개)까지 허용한다. 나중에 보조 CIDR을 붙일 수는 있지만(기본 할당량 5개) 처음 대역은 바꿀 수 없다.
- 서브넷: CIDR을 잘게 나눈 조각. AZ 하나에 속한다.
- 라우트 테이블: 서브넷에서 나가는 패킷을 어디로 보낼지 적은 표. 모든 테이블에 VPC 대역 전체를 가리키는 `local` 경로가 들어 있고 지울 수 없다. 그래서 같은 VPC 안의 서브넷끼리는 따로 설정하지 않아도 통한다.
- 인터넷 게이트웨이(IGW): VPC와 인터넷 사이의 문. VPC당 하나만 붙는다. 사업자가 알아서 이중화하고 늘려 주는 논리적인 장치라 대역폭 제한이 따로 없다.
- NAT 게이트웨이: 프라이빗 서브넷이 밖으로 나갈 때만 쓰는 출구. 들어오는 연결은 받지 않는다.
- 보안 그룹과 네트워크 ACL: ENI 단위의 상태 기억 방화벽과, 서브넷 경계의 상태 없는 방화벽.

목록에 "VPC 라우터"라는 장비는 없다. 서브넷마다 `.1` 주소에 라우터가 있는 것처럼 동작하지만 실제 상자는 없다. 각 호스트의 가상화 계층이 라우트 테이블을 읽고 바로 목적지로 보낸다. 그래서 VPC 안에서 traceroute를 쳐 보면 보통 VPC 라우터가 홉으로 잡히지 않고 목적지가 바로 나온다. 뒤에서 만들 리눅스 모형은 라우터가 진짜 네임스페이스라 홉이 보이는데, 이 점이 실제 클라우드와 다르다.

## 공인 IP는 인스턴스 안에 없다

처음 장면으로 돌아가자. 인스턴스 안에 공인 IP가 없는 이유는 인터넷 게이트웨이가 1:1 NAT를 하기 때문이다. 인스턴스에 공인 IPv4(자동 할당 또는 탄력적 IP)를 주면, AWS는 "공인 `54.180.x.x` ↔ 사설 `10.0.1.10`" 짝을 기억해 두고 IGW를 지나는 패킷의 주소를 바꿔 쓴다. 운영체제는 이 변환을 모른다. 자기 주소는 사설 IP뿐이다.

이 구조에서 실무에 바로 쓰이는 사실 몇 가지가 나온다.

- 앱이 자기 공인 IP를 알아야 하면 운영체제가 아니라 인스턴스 메타데이터(`169.254.169.254`)에 물어야 한다.
- 인스턴스를 멈췄다 켜면 자동 할당 공인 IP는 바뀐다. 고정이 필요하면 탄력적 IP(EIP)를 붙인다.
- 2024년 2월부터 AWS는 공인 IPv4 주소 하나에 시간당 0.005달러를 받는다. 쓰지 않는 EIP뿐 아니라 붙어 있는 공인 IP도 과금된다. 서버마다 공인 IP를 주는 설계가 비용 면에서도 불리해졌다.
- IGW가 바꿔 주는 건 공인 IP가 있는 ENI뿐이다. 공인 IP가 없는 인스턴스의 패킷이 IGW에 가면 그냥 버려진다. 프라이빗 서브넷의 라우트 테이블을 IGW로 바꿔도 인터넷이 되지 않는 이유다.

## 리눅스 네임스페이스로 VPC 하나 만들기

개념만으로는 감이 덜 온다. Ubuntu 24.04 한 대에서 네트워크 네임스페이스(격리된 네트워크 스택)를 여섯 개 만들어 VPC를 흉내 내 보자. 실제 AWS가 이렇게 구현된 건 아니고, 패킷이 지나는 순서와 결정 지점을 똑같이 재현한 모형이다.

- `vc-vr`: VPC 라우터. 서브넷마다 브리지 하나(`brpub`, `brpriv`)를 두고, 서브넷별 라우트 테이블을 정책 라우팅(`ip rule`)으로 고른다.
- `vc-web`(`10.0.1.10`), `vc-natgw`(`10.0.1.20`): 퍼블릭 서브넷의 서버와 NAT 게이트웨이.
- `vc-app`(`10.0.2.10`): 프라이빗 서브넷의 서버.
- `vc-igw`: 인터넷 게이트웨이. 공인 IP와 사설 IP를 1:1로 바꾼다.
- `vc-inet`(`198.51.100.80`): 인터넷 저편의 서버.

```bash
# 네임스페이스 여섯 개를 만든다
for n in vr web natgw app igw inet; do sudo ip netns add vc-$n; done

# VPC 라우터 안에 서브넷 두 개를 브리지로 만든다 (.1이 라우터 주소)
sudo ip netns exec vc-vr ip link add brpub type bridge
sudo ip netns exec vc-vr ip addr add 10.0.1.1/24 dev brpub
sudo ip netns exec vc-vr ip link add brpriv type bridge
sudo ip netns exec vc-vr ip addr add 10.0.2.1/24 dev brpriv

# 서버를 브리지에 꽂는다 (veth 한쪽은 라우터의 브리지, 다른 쪽은 서버의 eth0)
sudo ip link add vcweb type veth peer name eth0 netns vc-web
sudo ip link set vcweb netns vc-vr
sudo ip netns exec vc-vr ip link set vcweb master brpub up
sudo ip netns exec vc-web ip addr add 10.0.1.10/24 dev eth0
sudo ip netns exec vc-web ip link set eth0 up
sudo ip netns exec vc-web ip route add default via 10.0.1.1   # 기본 게이트웨이 = 서브넷의 .1

# IGW: 공인 IP ↔ 사설 IP 1:1 변환 (공인 IP가 있는 서버만)
sudo ip netns exec vc-igw iptables -t nat -A PREROUTING -d 203.0.113.10 -j DNAT --to-destination 10.0.1.10
sudo ip netns exec vc-igw iptables -t nat -A POSTROUTING -s 10.0.1.10 -o vcigw-net -j SNAT --to-source 203.0.113.10
# 공인 IP 짝이 없는 사설 주소는 버린다
sudo ip netns exec vc-igw iptables -A FORWARD -i vcigw-vr -j DROP
```

전체 스크립트는 길어서 핵심만 옮겼다. NAT 게이트웨이와 서브넷별 라우트 테이블 부분은 [서브넷과 라우트 테이블 글](/posts/vpc-subnets-route-tables)에서 이어서 본다. 다 만든 뒤 웹 서버 안에서 주소를 보면 처음 장면이 그대로 나온다.

```bash
# 웹 서버 네임스페이스에서 주소와 경로 확인
sudo ip netns exec vc-web ip -br addr
sudo ip netns exec vc-web ip route
```

```text
lo               UNKNOWN        127.0.0.1/8 
eth0@if5         UP             10.0.1.10/24 
default via 10.0.1.1 dev eth0 
10.0.1.0/24 dev eth0 proto kernel scope link src 10.0.1.10 
```

공인 IP `203.0.113.10`은 어디에도 없다. 그 주소는 IGW 네임스페이스가 들고 있다. 이제 바깥 서버에서 공인 IP로 접속하고, 거꾸로 웹 서버에서 바깥으로 나가 본다. 바깥 서버에는 `python3 -m http.server`를 띄워 접속 로그를 남겼다.

```bash
# 인터넷 쪽에서 공인 IP로 접속
sudo ip netns exec vc-inet curl -s -o /dev/null -w '%{http_code}\n' http://203.0.113.10/
# 웹 서버에서 바깥으로 나가기
sudo ip netns exec vc-web curl -s -o /dev/null -w '%{http_code}\n' http://198.51.100.80/
```

```text
200
200
```

양쪽 로그에 찍힌 출발지 주소가 이 구조를 그대로 보여 준다.

```text
# 웹 서버(10.0.1.10)의 접속 로그
198.51.100.80 - - [20/Oct/2026 13:17:31] "GET / HTTP/1.1" 200 -
# 바깥 서버(198.51.100.80)의 접속 로그
203.0.113.10 - - [20/Oct/2026 13:17:12] "GET / HTTP/1.1" 200 -
```

웹 서버는 사용자의 진짜 IP를 보고, 바깥 서버는 웹 서버의 사설 IP가 아니라 공인 IP를 본다. IGW의 conntrack 표에 그 변환이 남아 있다. 첫 줄은 웹 서버가 밖으로 나간 연결, 둘째 줄은 밖에서 들어온 연결이다.

```bash
# IGW 네임스페이스의 연결 추적 표에서 TCP 항목만 보기
sudo ip netns exec vc-igw conntrack -L -p tcp
```

```text
tcp      6 82 TIME_WAIT src=10.0.1.10 dst=198.51.100.80 sport=42514 dport=80 src=198.51.100.80 dst=203.0.113.10 sport=80 dport=42514 [ASSURED] mark=0 use=1
tcp      6 94 TIME_WAIT src=198.51.100.80 dst=203.0.113.10 sport=44988 dport=80 src=10.0.1.10 dst=198.51.100.80 sport=80 dport=44988 [ASSURED] mark=0 use=1
```

각 줄의 앞쪽 `src= dst=`는 처음 들어온 모습, 뒤쪽은 응답이 돌아올 때 기대하는 모습이다. 첫 줄에서 응답의 목적지가 `203.0.113.10`인 것을 보면 나갈 때 출발지가 바뀌었다는 걸 알 수 있다. conntrack 표를 읽는 법은 [iptables NAT 글](/posts/iptables-nat)에 자세히 있다.

## VPC 안의 DNS와 메타데이터

VPC를 만들면 DNS 리졸버와 메타데이터 서비스가 함께 따라온다. 둘 다 링크 로컬 주소(`169.254.0.0/16`, 망 밖으로 나가지 않는 주소)에 있다.

- Route 53 Resolver: VPC 대역 +2 주소와 `169.254.169.253`. 인스턴스는 DHCP 옵션으로 이 주소를 DNS 서버로 받는다(Ubuntu는 systemd-resolved가 이 주소로 넘긴다). VPC 속성 `enableDnsSupport`가 꺼져 있으면 동작하지 않는다.
- 사설 DNS 이름: `enableDnsHostnames`를 켜야 인스턴스가 `ip-10-0-1-10.ap-northeast-2.compute.internal` 같은 이름을 받는다. 기본 VPC는 켜져 있고, 직접 만든 VPC는 꺼진 채로 시작한다. 인터페이스 엔드포인트의 사설 DNS도 이 두 속성이 모두 켜져 있어야 한다.
- 인스턴스 메타데이터(IMDS): `169.254.169.254`. 공인 IP, IAM 역할의 임시 자격 증명 같은 것을 돌려준다.

메타데이터 서비스는 보안 사고와 자주 엮인다. 웹 앱에 SSRF(서버가 공격자가 준 주소로 대신 요청하게 만드는 취약점)가 있으면, 공격자가 `http://169.254.169.254/latest/meta-data/iam/security-credentials/...`를 요청하게 해서 자격 증명을 빼 간다. IMDSv2는 먼저 `PUT`으로 토큰을 받고 그 토큰을 헤더에 실어야 응답하게 바꿔서 이런 단순한 GET 공격을 막는다. 새로 띄우는 인스턴스는 IMDSv2만 허용(`HttpTokens=required`)으로 두는 게 기본이다.

```bash
# IMDSv2: 토큰을 먼저 받고 (TTL 6시간)
TOKEN=$(curl -s -X PUT http://169.254.169.254/latest/api/token \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
# 토큰을 실어서 자기 공인 IP를 묻는다
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/public-ipv4
```

```text
203.0.113.10
```

(예시 출력이다. 실제로는 인스턴스에 붙은 공인 IP가 나온다.)

## 기본 VPC를 그대로 쓰면 생기는 일

계정을 처음 만들면 리전마다 기본 VPC가 하나씩 있다. 대역은 `172.31.0.0/16`이고, AZ마다 `/20` 서브넷이 하나씩 있으며, 모든 서브넷이 IGW로 가는 경로를 가진 퍼블릭 서브넷이다. 서브넷 설정에 "공인 IP 자동 할당"도 켜져 있다. 실습용으로는 편하지만 운영에 그대로 쓰면 이런 일이 생긴다.

- DB든 배치 서버든 띄우는 즉시 공인 IP를 받는다. 보안 그룹 하나만 잘못 열면 바로 인터넷에 노출된다.
- 모든 계정의 기본 VPC가 같은 대역이라, 나중에 계정끼리 잇거나 사내망과 VPN으로 이으려 할 때 겹친다.
- 퍼블릭/프라이빗 구분이 없으니 "DB는 밖에서 경로 자체가 없다"는 이중 방어선이 없다.

운영 환경은 VPC를 따로 설계해서 만들고, 기본 VPC는 지우거나 쓰지 않는 게 보통이다. 손으로 콘솔에서 만들면 환경마다 조금씩 달라지니 Terraform 같은 코드로 남긴다. 이 부분은 [Terraform으로 네트워크 만들기 글](/posts/terraform-network-iac)에서 다룬다.

## 현장에서 VPC 때문에 막히는 순간

"연결이 안 된다"는 말을 들으면 증상부터 구분한다. 증상이 어느 부품을 의심할지 알려 준다.

- 바로 `Connection refused`: 패킷이 서버까지 갔다. 서버에 그 포트를 듣는 프로세스가 없다. VPC 문제가 아니다.
- `Connection timed out`: 패킷이 어딘가에서 조용히 버려졌다. 경로(라우트 테이블, IGW, NAT), 보안 그룹, NACL 중 하나다. 보안 그룹과 NACL은 거절 응답을 보내지 않고 그냥 버린다.
- VPC 안끼리는 되는데 밖으로만 안 된다: 서브넷의 라우트 테이블과 NAT 게이트웨이, 공인 IP 유무를 본다.
- 밖에서 공인 IP로만 안 된다: 서브넷이 정말 퍼블릭(기본 경로가 IGW)인지, 인스턴스에 공인 IP가 있는지, 보안 그룹 인바운드를 본다.

확인 순서는 바깥쪽 설정부터 안쪽으로 간다. 인스턴스가 어느 서브넷에 있는지, 그 서브넷이 어느 라우트 테이블을 쓰는지부터 확인한다.

```bash
# 인스턴스의 VPC, 서브넷, 사설·공인 IP 확인
aws ec2 describe-instances --instance-ids i-0123456789abcdef0 \
  --query 'Reservations[].Instances[].{Vpc:VpcId,Subnet:SubnetId,Private:PrivateIpAddress,Public:PublicIpAddress}'
```

```text
[
    {
        "Vpc": "vpc-0a1b2c3d4e5f67890",
        "Subnet": "subnet-0aa11bb22cc33dd44",
        "Private": "10.0.2.10",
        "Public": null
    }
]
```

(예시 출력이다. 형식은 AWS CLI v2 기본 JSON 출력과 같다.) `Public`이 `null`이면 이 인스턴스는 IGW로 직접 나갈 수 없다. 나가려면 NAT가 필요하다. 다음 단계인 라우트 테이블 확인은 [다음 글](/posts/vpc-subnets-route-tables)에서 이어 간다.

설정을 하나하나 읽는 대신 AWS의 Reachability Analyzer에 출발지와 목적지를 주면 경로를 계산해서 어느 부품에서 막히는지 알려 준다. 실제 패킷을 보내는 게 아니라 설정을 분석하는 도구라서 운영 중인 서버에도 부담이 없다. 실제로 어떤 패킷이 거부됐는지 보려면 [VPC 흐름 로그](/posts/network-flow-logs)를 켠다.

## VPC를 몇 개로 나눌까

처음에는 VPC 하나에 서브넷을 나눠 dev와 prod를 함께 두기 쉽다. 그러면 `local` 경로 때문에 dev 서버에서 prod DB에 경로가 열려 있다. 막는 건 보안 그룹 하나뿐이다. 그래서 규모가 조금만 커져도 환경마다 VPC를 나누고, 더 커지면 계정까지 나눈다(AWS Organizations로 계정 여러 개를 묶는다).

VPC를 나누면 격리는 쉬워지지만 연결이 일이 된다. 공용 서비스(로그 수집, CI, 사내 인증)에 여러 VPC가 닿아야 하고, 대역이 겹치지 않게 관리해야 한다. VPC가 서너 개면 피어링으로 충분하고, 수십 개가 되면 Transit Gateway로 허브를 만든다. 이 선택은 [피어링·Transit Gateway·PrivateLink 글](/posts/vpc-peering-transit-privatelink)에서 숫자와 함께 다룬다.

## 다시 처음 장면으로

`ip addr`에 공인 IP가 없는 건 IGW가 밖에서 주소를 바꿔 주기 때문이고, 운영체제는 그 사실을 모른다. 프라이빗 서브넷에서 `apt update`가 멈춘 건 그 서브넷의 라우트 테이블에 밖으로 나가는 경로(NAT 게이트웨이)가 없었기 때문이다. VPC는 남의 건물 안에 빌린 내 층이고, 방 배치와 안내판과 문을 내가 정한다. 다음 글에서는 그 안내판, 라우트 테이블을 서브넷 단위로 자세히 읽는다.

## 면접에서 나올 만한 질문

### VPC가 무엇이고 왜 필요한가요?

클라우드 사업자의 물리망 위에 고객마다 논리적으로 격리된 사설망을 만들어 주는 기능이다. 내 IP 대역을 정하고, 서브넷과 라우트 테이블로 어느 서버가 인터넷에 노출될지 정하고, 방화벽을 붙일 수 있다. 예전 EC2-Classic처럼 모든 고객이 한 평면에 섞여 있으면 데이터센터에서 하던 망 분리 설계를 옮길 수 없어서 생겼다.

### 인스턴스 안에서 공인 IP가 보이지 않는 이유는요?

인터넷 게이트웨이가 공인 IP와 사설 IP를 1:1로 바꿔 주기 때문이다. 운영체제의 랜카드에는 사설 IP만 붙어 있고, 들어오는 패킷은 IGW에서 목적지가 사설 IP로, 나가는 패킷은 출발지가 공인 IP로 바뀐다. 그래서 자기 공인 IP가 필요하면 인스턴스 메타데이터에 물어야 한다.

### 퍼블릭 서브넷과 프라이빗 서브넷은 무엇으로 갈리나요?

서브넷 설정에 그런 이름의 옵션은 없고, 연결된 라우트 테이블에 IGW로 가는 기본 경로가 있으면 퍼블릭이다. 다만 퍼블릭 서브넷에 있어도 인스턴스에 공인 IP가 없으면 인터넷과 통하지 못한다. 프라이빗 서브넷은 기본 경로가 NAT 게이트웨이를 가리키거나 아예 없어서 바깥에서 들어오는 길이 없다.

### 서로 다른 VPC가 같은 CIDR을 써도 되나요? 문제는 언제 생기나요?

서로 연결하지 않는 한 문제없다. 패킷이 VPC 단위로 캡슐화되어 격리되기 때문이다. 문제는 두 VPC를 피어링이나 Transit Gateway로 잇거나 사내망과 VPN으로 이을 때 생긴다. 라우트 테이블에서 같은 대역이 이미 내 것이라 저쪽으로 보낼 경로를 둘 수 없어서, 처음부터 회사 전체에서 대역을 겹치지 않게 나눠 둔다.

### 서브넷 /24에서 쓸 수 있는 IP가 251개인 이유는요?

AWS가 서브넷마다 다섯 개를 예약한다. 망 주소, VPC 라우터(.1), DNS(.2), 예비(.3), 브로드캐스트(마지막 주소)다. EKS처럼 Pod마다 VPC IP를 쓰는 구성에서는 이 수가 노드와 Pod 수의 상한이 되니 서브넷을 넉넉히 잡는다.

### 인스턴스 메타데이터 서비스가 보안에서 문제가 되는 이유와 대책은요?

`169.254.169.254`가 IAM 역할의 임시 자격 증명까지 돌려주기 때문에, SSRF 취약점이 있으면 공격자가 서버를 시켜 자격 증명을 빼 갈 수 있다. IMDSv2는 PUT으로 받은 토큰을 헤더에 실어야 응답하게 해서 단순한 GET 기반 SSRF를 막는다. 인스턴스를 IMDSv2만 허용으로 두고, 컨테이너에서는 홉 제한(hop limit)을 1로 두어 컨테이너가 메타데이터에 닿지 못하게 하는 설정도 함께 쓴다.

### 연결이 안 된다는 문의가 오면 VPC에서 무엇부터 보나요?

먼저 refused인지 timeout인지 본다. refused면 패킷은 서버까지 갔으니 앱과 포트를 보고, timeout이면 경로나 방화벽에서 버려진 것이다. 그다음 인스턴스의 서브넷과 공인 IP 유무, 그 서브넷의 라우트 테이블, 보안 그룹, NACL 순서로 확인하고, Reachability Analyzer나 흐름 로그로 어디서 막혔는지 확인한다.
