알림이 울렸다. "ProductsErrorRate > 5% for 10s". 상품 API 대시보드를 열었더니 서버가 낸 5xx는 0건이다. 헬스 체크도 200을 돌려준다. 서버 쪽 숫자는 전부 멀쩡한데 사용자 쪽 프로브는 요청 100%가 실패한다고 말한다. 무엇을 먼저 해야 할까. 원인을 찾을까, 일단 사용자부터 살릴까, 누구에게 알릴까.

이 글은 그 순간부터 끝날 때까지의 순서를 다룬다. 장애 대응(incident response)은 기술 문제이기 전에 조직 문제다. 누가 지휘하는지, 무엇을 먼저 하는지, 얼마나 자주 알리는지가 정해져 있지 않으면 똑똑한 사람이 여럿 모여도 서로 같은 로그를 보며 시간을 쓴다.

이 주제의 다른 글: 장애를 일부러 미리 겪어 보는 [카오스 엔지니어링](/posts/chaos-engineering), 알림을 받는 사람의 구조인 [온콜](/posts/on-call), 끝난 뒤 배우는 [포스트모템](/posts/postmortems). 알림 자체를 설계하는 법은 [알림 설계](/posts/alerting)에 있다.

글 속 장애는 실습 환경에서 실제로 재현했다. Ubuntu 24.04 컨테이너의 네트워크 네임스페이스 두 개에 Node.js 22로 만든 상품 API, 재고 서비스, 부하 생성기를 띄우고, 재고 서비스 앞의 Toxiproxy 2.12.0으로 "배포 뒤 1.5초씩 느려진 재고 서비스"를 만들었다. 로그와 시각은 모두 그 실행에서 나온 것이다. 다만 대응하는 사람의 행동은 스크립트로 돌려서, 실제 장애보다 시간이 훨씬 짧다. 사람이 하면 몇 분씩 걸릴 일이 몇 초로 줄어 있다.

## 장애 하나가 지나가는 네 단계

장애는 대개 같은 길을 지난다. 알아채고(detect), 무엇이 얼마나 나쁜지 가르고(triage), 피해를 멈추고(mitigate), 원래대로 되돌리고 원인을 고친다(resolve). 그 뒤에 배우는 단계(포스트모템)가 붙는다.

장애 대응 지표도 이 단계에 붙는다. 영향이 시작된 뒤 알아채기까지(MTTD), 알림을 받고 사람이 응답하기까지(MTTA), 피해가 멈추기까지(MTTM), 완전히 끝나기까지(MTTR). 앞 글자 M은 평균(mean)이다. 팀마다 MTTR의 R을 복구(recover)로 보기도 하고 해결(resolve)로 보기도 해서, 숫자를 비교할 때는 정의부터 맞춘다.

꼭 갈라 둘 것은 완화와 해결이다. 둘은 다른 단계다. 완화는 원인을 몰라도 할 수 있다. 롤백, 기능 끄기, 트래픽 옮기기, 서버 늘리기. 해결은 원인을 알아야 한다. 장애 중에는 완화가 먼저다.

## 분류: 얼마나 나쁜지 정하고 지휘자를 세운다

알림을 받은 사람이 가장 먼저 할 일은 고치는 게 아니다. 영향을 확인하고, 등급을 정하고, 혼자 감당할 일인지 판단하는 것이다. 실습에서 응답자가 처음 친 명령 네 개와 결과다.

```bash
# 헬스 체크는 어떤가
curl -s -o /dev/null -w 'healthz %{http_code} %{time_total}s\n' http://10.19.0.2:7000/healthz
# 사용자가 부르는 엔드포인트는 어떤가 (3초 제한)
curl -s -o /dev/null -m 3 -w 'products %{http_code} %{time_total}s\n' http://10.19.0.2:7000/products
# 재고 서비스(8003)로 열린 연결 수
sudo ip netns exec v19s ss -tn state established '( dport = :8003 )' | tail -n +2 | wc -l
# 최근에 바뀐 것
tail -n 3 deploy.log
```

```text
healthz 200 0.000691s
products 000 3.002418s
8
2026-10-21T00:15:52.593Z deploy inventory v2.4.0 (author=ci, change=stock query rewrite)
```

네 줄이 이야기를 다 한다. 헬스 체크는 거짓말을 하고 있다. 실제 엔드포인트는 3초 안에 응답이 없다(`000`은 curl이 상태 코드를 받지 못했다는 뜻이다). 재고로 가는 연결이 한도인 8개에 붙어 있다. 그리고 장애가 시작되기 몇 초 전에 재고 서비스가 배포됐다. "최근에 바뀐 것"은 분류 단계에서 반드시 묻는 질문이다. 장애의 상당수는 배포나 설정 변경 직후에 난다.

등급은 영향으로 정한다. 회사마다 이름과 숫자는 다르지만 대개 이런 모양이다.

| 등급 | 영향 | 대응 |
|---|---|---|
| SEV1 | 핵심 기능이 대부분의 사용자에게 안 된다, 데이터 유실, 보안 사고 | 즉시 지휘자 지정, 관련 팀 호출, 외부 공지 |
| SEV2 | 핵심 기능이 일부 사용자에게 안 되거나 크게 느리다 | 지휘자 지정, 정해진 간격으로 내부 공유 |
| SEV3 | 부가 기능 장애, 우회 방법이 있다 | 담당 팀이 업무 시간에 처리 |
| SEV4 | 사용자 영향이 거의 없다 | 티켓 |

상품 목록이 100% 실패하니 이 장애는 SEV1이나 SEV2다. 등급이 애매하면 높게 잡는다. 높게 잡았다가 내리는 비용은 회의 몇 분이지만, 낮게 잡았다가 올리는 비용은 늦어진 대응 전체다. 장애를 선언하는 일 자체를 가볍게 만드는 것도 중요하다. "이게 장애인가?"를 10분 동안 고민하는 팀보다, 일단 선언하고 아니면 닫는 팀이 빠르다.

## 역할을 나누면 손이 덜 겹친다

장애가 커지면 사람이 늘어난다. 사람이 늘면 모두가 같은 대시보드를 보고, 서로 다른 걸 동시에 바꾸고, 아무도 바깥에 알리지 않는 일이 생긴다. 그래서 역할을 나눈다. 미국 소방의 현장 지휘 체계(ICS)를 빌려 와서 IT 장애에 맞게 줄인 방식이 널리 쓰인다.

지휘자(incident commander)는 직접 고치지 않는다. 지금 무엇을 하고 있는지, 누가 하는지, 다음 결정이 무엇인지를 쥔다. 조작 담당(ops lead, 또는 해당 시스템 전문가)은 명령을 치고 변경을 한다. 변경은 지휘자에게 말하고 한다. 소통 담당(communications lead)은 정해진 간격으로 내부 채널과 상태 페이지에 상황을 올린다. 기록 담당(scribe)은 시각과 함께 무엇을 봤고 무엇을 했는지 적는다. 이 기록이 나중에 포스트모템의 타임라인이 된다.

작은 팀에서는 한 사람이 여러 역할을 겸한다. 다만 지휘자와 조작 담당은 가능하면 나눈다. 명령을 치면서 전체를 보기는 어렵다. 장애가 길어지면 지휘자도 교대한다. 넘길 때는 "지금 상태, 시도한 것, 다음에 할 것"을 말로 넘기고 채널에 "지휘자가 누구에서 누구로 바뀜"을 적는다.

## 원인보다 완화가 먼저다

분류에서 재고 배포가 의심스럽다는 것까지 알았다. 여기서 흔히 빠지는 함정이 "왜 느려졌는지"를 파고드는 것이다. 새 쿼리가 무엇을 바꿨는지, 인덱스를 탔는지. 흥미로운 질문이지만 그동안 사용자는 계속 실패한다.

완화 수단은 원인과 상관없이 쓸 수 있는 것들이다. 직전 변경을 롤백한다. 문제 기능을 플래그로 끈다. 트래픽을 다른 리전이나 다른 인스턴스로 옮긴다. 서버를 늘린다. 들어오는 양을 줄인다(부하 차단). 어느 것을 고를지는 되돌리기 쉬운 것, 빨리 효과가 보이는 것부터다.

## 해결과 종료 선언

롤백 뒤 재고 서비스를 직접 불러 확인하고, 플래그를 끄고, 사용자 지표가 평소로 돌아온 채로 버티는지 지켜본 뒤 종료를 선언했다.

```bash
# 재고 서비스를 직접 부른다
curl -s -o /dev/null -w 'inventory direct %{http_code} %{time_total}s\n' http://10.19.0.2:8003/stock
# 기능 줄이기를 끈다
curl -s -X POST http://10.19.0.2:7000/admin/degrade/off
```

```text
inventory direct 200 0.012128s
degrade=false
2026-10-21T00:17:02.691Z user: req=198 fail=0 (0.0%) p99=24ms
2026-10-21T00:17:22.691Z user: req=198 fail=0 (0.0%) p99=22ms
```

플래그를 끄는 것도 변경이다. 완화로 켠 것들을 하나씩 거둘 때마다 지표를 보고, 한꺼번에 다 되돌리지 않는다. 종료 선언 기준은 미리 정해 둔다. "사용자 지표가 SLO 안으로 돌아와 15분 동안 유지" 같은 식이다. 실습에서는 시간을 줄여 25초를 지켜봤다.

해결이 원인 제거까지 뜻하지는 않는다. 롤백으로 재고 서비스는 옛 버전이 됐지만 v2.4.0의 쿼리가 왜 느렸는지는 아직 모른다. 그건 장애가 끝난 뒤 담당 팀이 차분히 볼 일이다. 상품 API에 타임아웃이 없었던 문제도 마찬가지다. 이런 것들은 포스트모템의 후속 조치가 된다.

## 상황 공유는 정해진 간격으로, 다음 시각을 적어서

장애 중 가장 많이 받는 질문은 "지금 어떻게 돼 가요?"다. 이 질문에 매번 답하다 보면 대응할 시간이 없다. 그래서 공유 간격을 정해 둔다. 흔히 SEV1은 내부에 15~30분마다, 상태 페이지에 30분마다, SEV2는 30~60분마다로 잡는다. 할 말이 없어도 간격이 되면 "변화 없음, 다음 공유 HH:MM"을 올린다. 다음 공유 시각이 있으면 사람들은 기다린다.

내부 공유 한 번의 모양은 늘 같게 한다.

```text
[SEV2] 상품 목록 조회 실패 - 업데이트 #2 (00:16:35 UTC)
영향: 00:15:52부터 상품 목록 요청 대부분이 실패했다. 00:16:30부터 재고 수량 없이 목록만 보인다.
조치: 기능 줄이기 플래그를 켰다(00:16:25). 재고 서비스 v2.4.0 롤백을 재고 팀과 진행 중.
다음: 롤백 후 재고 수량 표시 복구.
지휘자: @kim  소통: @lee
다음 업데이트: 00:46 UTC 또는 상태가 바뀔 때
```

외부 상태 페이지에는 기술 세부를 빼고 사용자가 겪는 증상, 우회 방법, 다음 업데이트 시각만 쓴다. "DB 커넥션 풀이 고갈되어" 같은 말은 사용자에게 도움이 되지 않고, 확정되지 않은 원인을 외부에 적으면 나중에 정정해야 한다.

## 장애 대응에서 흔히 하는 실수

원인을 찾느라 완화를 미루는 것. 앞에서 봤다. 원인이 분명해 보여도 되돌릴 수 있는 완화가 있으면 먼저 한다.

여러 사람이 동시에 다른 걸 바꾸는 것. 한 사람은 서버를 늘리고, 다른 사람은 설정을 고치고, 또 한 사람은 캐시를 비운다. 지표가 좋아져도 무엇이 효과였는지 모르고, 나빠지면 무엇을 되돌려야 할지 모른다. 변경은 지휘자를 거쳐 한 번에 하나씩 한다.

헬스 체크와 서버 지표를 믿는 것. 실습에서 `/healthz`는 0.7ms에 200을 줬고 `err5xx`는 0이었다. 의존성을 부르지 않는 얕은 헬스 체크와, 끝난 요청만 세는 서버 지표는 "줄 서 있는" 장애를 못 본다. 사용자 쪽에서 재는 프로브를 함께 둔다([헬스 체크 설계](/posts/health-checks)).

알림이 풀리자마자 끝났다고 보는 것. 안쪽에 남은 줄, 재시도로 쌓인 큐, 완화로 켜 둔 플래그가 남아 있다. 하나씩 거두고 지표를 확인한 뒤 종료한다.

기록을 남기지 않는 것. 장애 중에는 다 기억할 것 같지만 이틀 뒤에는 "플래그를 먼저 켰나, 롤백을 먼저 했나"도 헷갈린다. 채널에 시각과 함께 적는 사람이 있어야 한다.

## 타임라인에서 숫자 뽑기

아래 함수는 장애 이벤트 목록을 받아, 영향 시작(`impact_start`)부터 감지(`detected`), 응답(`acked`), 완화(`mitigated`), 종료(`resolved`)까지 각각 몇 초 걸렸는지 소수 첫째 자리로 반올림해 돌려준다. 이벤트는 순서가 섞여 들어올 수 있고, 아직 없는 단계는 `null`이다. 시각은 ISO 8601 문자열이다.

<CodePlayground
  caption="장애 지표 계산"
  functionName="incidentMetrics"
  initialCode={`function incidentMetrics(events) {
  // events: [{ t: "2026-10-21T00:15:52.593Z", type: "impact_start" }, ...]
  return { ttd: null, tta: null, ttm: null, ttr: null };
}`}
  solution={`function incidentMetrics(events) {
  const at = (type) => {
    const e = events.find((x) => x.type === type);
    return e ? Date.parse(e.t) : null;
  };
  const start = at("impact_start");
  const sec = (type) => {
    const t = at(type);

## 서버 숫자가 멀쩡하던 그 알림으로

처음 장면의 답은 이렇다. 서버의 5xx가 0이어도 사용자 쪽 프로브를 믿는다. 영향을 확인하고 등급을 정하고 지휘자를 세운다. "최근에 바뀐 것"을 묻는다. 원인을 다 알기 전에 되돌릴 수 있는 완화부터 한다. 정해진 간격으로 다음 공유 시각을 적어 알린다. 알림이 풀려도 안쪽 찌꺼기와 켜 둔 완화를 거두고 지표가 유지되는 걸 본 뒤 끝낸다. 그리고 그동안 남긴 기록으로 [포스트모템](/posts/postmortems)을 쓴다.

## 면접에서 나올 만한 질문

### 장애가 났을 때 가장 먼저 무엇을 하나요?

고치기 전에 영향을 확인하고 등급을 정한다. 사용자 쪽 지표로 누가 얼마나 영향을 받는지 보고, 혼자 감당할 규모가 아니면 장애를 선언해 지휘자를 세우고 필요한 사람을 부른다. 그다음 "최근에 바뀐 것"을 확인하고 되돌릴 수 있는 완화부터 한다.

### 원인을 먼저 찾지 않고 완화부터 하는 이유는요?

원인을 찾는 동안에도 사용자는 계속 실패하기 때문이다. 롤백, 플래그 끄기, 트래픽 옮기기는 원인을 몰라도 피해를 멈출 수 있다. 원인은 피해가 멈춘 뒤 증거를 보존한 채로 차분히 찾는다. 다만 롤백이 DB 스키마 변경처럼 되돌릴 수 없는 걸 건드리면 완화 수단을 다르게 고른다.

### 서버 5xx는 0인데 사용자는 다 실패한다고 합니다. 어떻게 된 걸까요?

요청이 실패하지 않고 줄을 서 있는 경우다. 실습에서는 재고 서비스가 느려지자 연결 8개가 모두 묶이고 요청이 1000건 넘게 대기했다. 사용자는 2초에 떠났지만 서버는 그 요청을 끝내지 못했으니 5xx도 없고, 끝난 요청만 세는 p99는 한참 뒤에야 오른다. 처리량 급감과 대기 줄 길이, 그리고 사용자 쪽 프로브를 함께 본다.

### 지휘자는 무엇을 하고 왜 직접 고치지 않나요?

지휘자는 전체 그림과 결정을 쥔다. 누가 무엇을 하는지 배정하고, 변경을 한 번에 하나씩 승인하고, 소통 담당에게 요약을 넘긴다. 명령을 치면서 전체를 보기는 어려워서, 직접 손을 대면 다른 사람의 변경과 겹치거나 공유가 끊긴다. 작은 팀이라도 지휘와 조작은 가능하면 나눈다.

### 장애 등급은 무엇으로 정하고, 애매하면 어떻게 하나요?

사용자 영향의 범위와 크기로 정한다. 핵심 기능이 대부분에게 안 되면 SEV1, 일부에게 안 되거나 크게 느리면 SEV2 같은 식이다. 애매하면 높게 잡는다. 내리는 비용은 작지만 늦게 올리는 비용은 늦어진 대응 전체이기 때문이다.

### 장애 중 상황 공유는 어떻게 하나요?

정해진 간격으로, 같은 형식으로, 다음 공유 시각을 적어서 한다. 영향, 지금까지 한 조치, 다음 조치, 담당자, 다음 업데이트 시각을 넣는다. 외부 상태 페이지에는 기술 세부와 확정되지 않은 원인을 빼고 증상과 우회 방법만 쓴다.

### 알림이 풀렸는데 바로 종료하면 안 되는 이유는요?

사용자 쪽 증상이 멈춰도 안쪽에 찌꺼기가 남아 있을 수 있다. 실습에서는 플래그를 켠 뒤에도 1101건이 대기 줄에 있었고, 롤백한 뒤에야 빠졌다. 완화로 켠 플래그나 늘린 서버도 하나씩 거둬야 한다. 미리 정한 종료 기준(SLO 안에서 일정 시간 유지)을 채운 뒤 끝낸다.

### MTTR을 줄이려면 어디부터 보나요?

MTTR을 감지, 응답, 완화, 해결로 나눠 어느 구간이 긴지부터 본다. 감지가 길면 사용자 쪽 지표에 알림을 건다. 응답이 길면 온콜 구조와 호출 경로를 본다. 완화가 길면 롤백과 플래그처럼 원인과 무관하게 쓸 수 있는 수단을 미리 준비해 둔다. 평균 하나만 보면 어디를 고칠지 알 수 없다.
