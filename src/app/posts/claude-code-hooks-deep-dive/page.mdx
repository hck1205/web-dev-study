새 터미널에서 세션을 열 때마다 `export DEPLOY_TARGET=staging`, `nvm use 20`을 치고, "지금 브랜치는 feat/auth고 이슈는 #4211이다"를 붙여 넣었다. 한 번 빼먹으면 Claude가 운영 주소로 요청을 보내는 스크립트를 만든다. 사람이 매번 기억해야 하는 일은 결국 빠진다.

이 일은 SessionStart 훅이 대신한다. 세션이 열릴 때 스크립트가 돌아 환경 변수를 심고, 브랜치 정보를 Claude의 컨텍스트에 넣는다. 만들고 나면 다음 질문이 따라온다. 훅은 어떤 순서로 불리나, stdin으로 무엇이 들어오나, 무엇을 돌려주면 무엇이 바뀌나, 셸 명령 대신 모델에게 판단을 맡기는 훅은 언제 쓰나, 훅이 느리거나 끝나지 않으면 어떻게 되나.

이 글은 그 질문을 실험용 저장소에 훅을 직접 걸고 `claude -p`로 돌린 결과로 답한다. 종료 코드 0, 2, 그 밖의 뜻, Bash 명령을 검사하는 `validate-bash.sh`, 매처를 읽는 규칙은 [Claude Code 확장 글](/posts/claude-code-extensions)에서 다뤘으니 여기서는 짧게만 짚는다. 훅이 놓이는 `settings.json`의 위치와 우선순위는 [프로젝트 구조 글](/posts/claude-code-project-structure)에 있다.

기준은 Claude Code 2.1.310, Ubuntu 24.04, bash 5.2, jq 1.7이고, 문서는 2026년 10월의 [훅 레퍼런스](https://code.claude.com/docs/en/hooks)다. 사건 종류만 서른 개가 넘고 버전마다 필드가 늘어 왔다. 버전이 붙은 동작은 문서에 적힌 범위로 쓴다.

## 손으로 넣던 환경 변수를 SessionStart로

SessionStart 훅은 `CLAUDE_ENV_FILE`이라는 환경 변수를 받는다. 이 경로의 파일에 `export` 줄을 쓰면, 그 세션에서 Claude가 실행하는 모든 Bash 명령 앞에 그 내용이 먼저 실행된다. 셸 설정 파일을 고치지 않고 세션 단위로 변수를 심는 방법이다.

```bash
#!/usr/bin/env bash
# .claude/hooks/session-start.sh
# SessionStart: 셸 환경 변수를 남기고, 브랜치 정보를 Claude에게 알린다
input=$(cat)
if [ -n "$CLAUDE_ENV_FILE" ]; then
  # 다른 훅이 쓴 줄을 지우지 않게 >>로 덧붙인다
  echo 'export DEPLOY_TARGET=staging' >> "$CLAUDE_ENV_FILE"
  echo 'export API_BASE_URL=http://localhost:8080' >> "$CLAUDE_ENV_FILE"
fi
branch=$(git -C "$CLAUDE_PROJECT_DIR" branch --show-current 2>/dev/null)
jq -nc --arg b "${branch:-none}" --arg s "$(jq -r .source <<<"$input")" \
  '{hookSpecificOutput: {hookEventName: "SessionStart",
    additionalContext: ("Current git branch: " + $b + ". Session source: " + $s + ".")}}'
```

```json
{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/session-start.sh" }
        ]
      }
    ]
  }
}
```

`chmod +x`를 하고 세션을 띄워 `printenv`를 시켰다.

```bash
# 훅이 심은 변수가 Claude의 Bash에 보이는지 확인한다
claude -p 'Run exactly this Bash command: printenv DEPLOY_TARGET API_BASE_URL' \
  --model haiku --allowedTools "Bash(printenv:*)"
```

PostToolUse 훅으로 그때 Bash 도구가 돌려준 결과를 받아 두었다.

```json
{
  "tool_name": "Bash",
  "tool_response": {
    "stdout": "staging\nhttp://localhost:8080",
    "stderr": "",
    "interrupted": false,
    "isImage": false,
    "noOutputExpected": false
  },
  "duration_ms": 110
}
```

변수가 들어갔고, Claude는 답에서 "SessionStart 훅이 브랜치가 master라고 알려 줬다"고 말했다. `additionalContext`는 대화 맨 앞, 첫 프롬프트 전에 시스템 알림(system reminder)으로 들어간다. 화면에 메시지로 보이지는 않는다.

몇 가지를 알아 두면 덜 헤맨다. SessionStart의 매처는 도구 이름이 아니라 세션이 열린 방식이다. `startup`(새 세션), `resume`(`--resume`, `--continue`, `/resume`), `clear`(`/clear`), `compact`(압축 직후), `fork`(갈라진 세션)가 있다. 매처를 비우면 다섯 경우 모두 돈다. 압축 뒤에 다시 넣어야 할 정보가 있으면 `compact`를 일부러 포함한다. 또 SessionStart는 `command`와 `mcp_tool` 타입만 받는다. HTTP, 프롬프트, 에이전트 훅은 걸 수 없다.

대화형 세션에서 SessionStart 훅은 뒤에서 돌아서 바로 타이핑할 수 있지만, Claude의 첫 응답은 훅이 끝날 때까지 기다린다. 이 훅은 모든 세션에서 돌기 때문에 느린 작업(패키지 설치, 큰 API 조회)을 넣으면 세션을 열 때마다 그만큼 기다린다. 늘 같은 내용이면 스크립트 대신 CLAUDE.md에 적는 것이 맞다. 훅은 브랜치, 열린 이슈, 배포 대상처럼 그때그때 바뀌는 사실을 넣을 때 쓴다.

## 사건은 이 순서로 온다

훅이 언제 불리는지 직접 보려고, 받은 JSON의 키만 한 줄씩 남기는 기록기를 만들어 여섯 사건에 모두 걸었다.

```bash
#!/usr/bin/env bash
# .claude/hooks/log.sh: 사건 이름, 시각, 받은 JSON의 키를 남긴다
input=$(cat)
ev=$(jq -r '.hook_event_name' <<<"$input")
printf '%s %-17s %s\n' "$(date +%H:%M:%S.%3N)" "$ev" "$(jq -c 'keys' <<<"$input")" \
  >> "$CLAUDE_PROJECT_DIR/events.log"
printf '%s\n' "$input" > "$CLAUDE_PROJECT_DIR/last-$ev.json"   # 마지막 입력 전체도 남긴다
exit 0
```

위의 `printenv` 실행 한 번이 남긴 기록이다.

기록을 몇 번 더 남기다 보면 그림에 없는 경우가 보인다. 처음에는 `--allowedTools` 없이 돌렸는데, 그때 기록은 SessionStart, UserPromptSubmit, PreToolUse, Stop, SessionEnd였다. PostToolUse가 없다. PreToolUse는 권한 확인보다 먼저 돌기 때문에 불렸지만, 명령이 권한에서 막혀 실행되지 않았으니 "성공한 뒤"가 오지 않았다. 실행된 도구가 실패하면 PostToolUseFailure, auto 모드가 호출을 거부하면 PermissionDenied라는 별도 사건이 온다. "PreToolUse 수와 PostToolUse 수가 같다"고 가정한 집계 스크립트는 여기서 틀린다.

그 밖에도 사건이 많다. 권한 확인 창이 뜨기 직전의 PermissionRequest, 병렬 도구 호출 한 묶음이 끝난 뒤의 PostToolBatch, 서브에이전트의 SubagentStart·SubagentStop, 압축 앞뒤의 PreCompact·PostCompact, 모델을 바꾸기 전의 PreModelSwitch, CLAUDE.md가 읽힐 때의 InstructionsLoaded, 작업 폴더가 바뀔 때의 CwdChanged 등이다. 처음에는 위의 여섯 개로 충분하다.

UserPromptSubmit은 내가 친 프롬프트에만 불리지 않는다는 점도 기억한다. `/loop` 반복, 백그라운드 서브에이전트가 결과를 보고할 때, 다른 세션이 보낸 메시지가 도착할 때도 돈다. 이 훅에 "프롬프트마다 슬랙에 알림"을 걸면 루프가 돌 때마다 알림이 간다.

## stdin으로 들어오는 JSON

모든 사건에 공통으로 들어오는 필드가 있다. `session_id`, `transcript_path`(대화 기록 파일 경로), `cwd`, `hook_event_name`, 그리고 대부분의 사건에 `permission_mode`와 `prompt_id`가 붙는다. 기록에서 보이듯 도구 사건과 Stop에는 `effort`(지금 적용된 effort 단계)도 온다. 서브에이전트 안에서 불린 훅에는 `agent_id`와 `agent_type`이 붙는다. 그 위에 사건마다 고유한 필드가 더해진다.

Stop 훅의 `last_assistant_message`는 방금 끝난 답의 본문이다. 대화 기록 파일(`transcript_path`)은 비동기로 써져서 Stop 시점에 마지막 답이 아직 없을 수 있으니, 방금 답을 읽어야 하는 훅은 파일 대신 이 필드를 쓴다. `background_tasks`와 `session_crons`는 아직 도는 백그라운드 작업과 예약된 깨우기 목록이다. 비어 있지 않으면 세션이 "끝났다"기보다 "기다리는 중"이다.

## stdout으로 돌려주는 JSON

답하는 방법은 둘이다. 종료 코드만 쓰거나, 0으로 끝내고 stdout에 JSON을 하나 찍는다. 하나만 고른다. 2로 끝내면서 JSON을 같이 찍으면 2의 막는 효과가 그대로 남는다. 그리고 stdout에는 JSON만 있어야 한다. 셸 설정 파일이 시작할 때 찍는 인사말 한 줄만 섞여도 JSON으로 읽히지 않는다.

JSON 필드는 세 갈래다.

모든 사건이 받는 공통 필드가 있다. `continue: false`는 훅이 돈 뒤 Claude를 완전히 멈추고 `stopReason`을 사용자에게 보여 준다. 사건별 판정보다 앞선다. `systemMessage`는 사용자에게 보이는 경고다. 문서가 짚는 함정 하나는 `suppressOutput`이다. 받기는 하지만 아무 효과가 없다. 성공한 훅의 stdout은 원래 대화에 표시되지 않고 디버그 로그에만 남는다.

막거나 돌려보낼 때는 최상위 `decision: "block"`과 `reason`을 쓰는 사건이 많다. UserPromptSubmit, PostToolUse, Stop, SubagentStop, PreCompact 등이다. `decision`에 올 수 있는 값은 `"block"` 하나뿐이고, 허용하려면 필드를 빼면 된다.

더 세밀한 제어는 `hookSpecificOutput` 안에 `hookEventName`과 함께 쓴다. PreToolUse의 `permissionDecision`(allow, deny, ask, defer)과 `updatedInput`, PostToolUse의 `updatedToolOutput`, 여러 사건의 `additionalContext`가 여기 있다. 사건마다 무엇을 바꿀 수 있는지가 다르다.

| 사건 | 막기 | 바꾸기 | 덧붙이기 |
| :- | :- | :- | :- |
| SessionStart | 못 한다 | 세션 제목, 처음 메시지(`-p`) | `additionalContext`, 일반 stdout |
| UserPromptSubmit | `decision: "block"` | 프롬프트는 못 바꾼다 | `additionalContext`, 일반 stdout |
| PreToolUse | `permissionDecision: "deny"` | `updatedInput`으로 인자 | `additionalContext` |
| PostToolUse | 이미 실행됐다. block은 피드백이 된다 | `updatedToolOutput`으로 결과 | `additionalContext` |
| Stop | `decision: "block"`이면 계속 일한다 | 없다 | `additionalContext`(오류 표시 없이 계속) |
| SessionEnd | 못 한다 | 없다 | 없다. JSON이 버려진다 |

비밀값을 가리는 일은 이 표에서 자리가 정해진다. 밖으로 나가는 도구 인자는 PreToolUse의 `updatedInput`, 안으로 들어오는 결과는 PostToolUse의 `updatedToolOutput`이다. UserPromptSubmit으로 프롬프트 속 비밀값을 지우려는 시도는 안 된다. 바꿀 수 없고, 막아도 프롬프트 글은 대화 기록 파일과 입력 기록에 남는다고 문서가 적는다.

`additionalContext`를 쓸 때 문서가 권하는 요령도 있다. "배포 대상은 staging이다"처럼 사실을 서술한다. "시스템 지시: 반드시 ~하라" 같은 명령조는 프롬프트 인젝션 방어에 걸려 Claude가 오히려 그 글을 사용자에게 보여 주며 의심할 수 있다. 문자열은 필드마다 1만 자가 상한이고, 넘으면 파일로 빠지고 앞 2,000자 미리보기만 들어간다. 또 이어 연 세션에서는 지난 턴의 UserPromptSubmit·PostToolUse 출력이 다시 실행되지 않고 저장된 글 그대로 재생된다. 커밋 해시나 시각 같은 값은 낡는다. 매번 새로 넣어야 하는 값은 이어 열 때 다시 도는 SessionStart에 둔다.

## 느린 훅은 세션을 멈춘다

훅은 기본으로 끝날 때까지 Claude를 기다리게 한다. 그래서 시간 제한이 있고, 사건과 타입마다 기본값이 다르다.

| 대상 | 기본 시간 제한 |
| :- | :- |
| command, http, mcp_tool (대부분 사건) | 600초 |
| UserPromptSubmit, PreModelSwitch 등의 command, http, mcp_tool | 30초 |
| prompt 훅 | 30초 |
| agent 훅 | 60초 |
| SessionEnd 전체 | 1.5초 |

UserPromptSubmit이 30초로 짧은 이유는 이 훅이 모든 프롬프트 앞에서 모델 처리를 막기 때문이다. 시간을 넘기면 어떻게 되는지 확인하려고, 외부 조회를 흉내 내어 몇 초 잠든 뒤 "이번 주 당번은 Mina다"를 덧붙이는 훅에 `timeout: 3`을 걸었다.

```bash
#!/usr/bin/env bash
# UserPromptSubmit: 느린 외부 조회를 흉내 낸 뒤 컨텍스트를 붙인다
cat > /dev/null
sleep "${SLOW_SECONDS:-0}"
jq -nc '{hookSpecificOutput: {hookEventName: "UserPromptSubmit",
  additionalContext: "The on-call engineer this week is Mina."}}'
```

```text
sleep=0  wall=8.0s   answer=Mina
sleep=5  wall=11.4s  answer=UNKNOWN
```

5초 잠든 쪽은 3초에서 잘렸고, 출력이 통째로 버려져 Claude는 당번을 몰랐다. 프롬프트 자체는 그대로 갔다. 훅이 시간을 넘기면 막지 않고 통과시키는 쪽(fail open)이 기본이다. 컨텍스트 주입이 늦어서 빠지는 것은 괜찮지만, 정책 검사 훅이 이렇게 빠지면 검사 없이 통과한다. 그런 훅에는 2.1.295부터 `onFailure: "block"`을 주어 실패나 시간 초과 때 막게 한다. 그리고 벽시계 시간이 3.4초 늘었다. 프롬프트마다 3초씩 붙는 셈이다.

기다릴 필요가 없는 일은 `async: true`로 뒤에서 돌린다. 파일을 고칠 때마다 테스트를 돌리는 PostToolUse 훅이 예다. 이렇게 돌린 훅은 막거나 판정할 수 없고, 끝나면 `additionalContext`와 `systemMessage`가 다음 턴에 Claude에게 전달된다. 실패했을 때만 Claude를 깨우고 싶으면 `asyncRewake: true`를 쓴다. 이 훅이 2로 끝나면 그 stderr가 Claude에게 알림으로 간다. `claude -p`에서는 세션이 끝날 때 아직 돌던 async 훅을 죽인다. 세션보다 오래 살아야 하는 일은 완전히 분리된 프로세스로 띄운다.

SessionEnd의 1.5초는 특히 자주 걸린다. 세션 통계를 원격으로 보내는 훅이 네트워크가 느린 날 조용히 잘린다. 그 훅에 `timeout`을 따로 주면 전체 예산이 가장 큰 값까지(최대 60초) 늘고, `CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS`로 직접 정할 수도 있다. 종료 이유는 `reason`에 `clear`, `resume`, `logout`, `prompt_input_exit`, `other`로 온다. `-p` 실행이 끝났을 때는 `other`였다.

## Stop 훅이 끝나지 않을 때

Stop 훅의 `decision: "block"`은 "아직 끝내지 마라"는 뜻이다. `reason`이 Claude의 다음 지시가 되어 같은 턴이 이어진다. 답의 마지막 줄에 VERIFIED가 없으면 한 번 돌려보내는 훅을 만들었다.

```bash
#!/usr/bin/env bash
# Stop 훅: 답의 마지막 줄에 VERIFIED가 없으면 한 번 돌려보낸다
input=$(cat)
# 이미 Stop 훅 때문에 이어서 일하는 중이면 다시 막지 않는다
if [[ $(jq -r '.stop_hook_active' <<<"$input") == "true" ]]; then
  exit 0
fi
if jq -r '.last_assistant_message' <<<"$input" | tail -n 1 | grep -q 'VERIFIED'; then
  exit 0
fi
jq -n '{decision: "block", reason: "Finish your answer with a final line that says VERIFIED."}'
```

"2+2는?"을 물었더니 Stop이 두 번 불렸다. 첫 번째는 `stop_hook_active=false`에 답이 "4"라 막혔고, 두 번째는 `stop_hook_active=true`라 통과했다. 마지막 답은 VERIFIED로 끝났다. 정상이다.

그다음 `stop_hook_active` 검사를 빼고 늘 막게 바꿨다. 고칠 수 없는 테스트 실패를 만난 Stop 훅이 이렇게 된다. Claude Code에는 연속 8번 이어 붙이면 다음 block을 무시하고 턴을 끝내는 상한이 있다. 그래서 Stop이 9번 불리고 끝날 줄 알았다. 실제 기록은 이랬다(같은 줄이 이어지는 곳은 줄이고 화살표로 설명을 붙였다).

## command, prompt, agent 훅

훅 핸들러의 `type`은 다섯 가지다. 셸 명령을 돌리는 `command`, JSON을 POST로 보내는 `http`, MCP 서버의 도구를 부르는 `mcp_tool`, 모델에게 한 번 묻는 `prompt`, 도구를 쓰는 서브에이전트를 띄우는 `agent`다. 앞의 셋은 정해진 규칙을 코드로 검사하고, 뒤의 둘은 판단을 모델에게 맡긴다.

프롬프트 훅을 PreToolUse에 걸어 봤다. ".env 파일의 내용을 읽거나 출력하거나 복사하거나 보내는 명령은 막고 나머지는 허용하라"는 규칙 하나를 글로 썼다. `$ARGUMENTS` 자리에 훅 입력 JSON이 들어간다.

```json
{
  "matcher": "Bash",
  "hooks": [
    {
      "type": "prompt",
      "prompt": "You review one Bash command before it runs. Block it if it reads, prints, copies or sends the contents of any .env file. Otherwise allow. Hook input: $ARGUMENTS",
      "continueOnBlock": true
    }
  ]
}
```

명령 세 개를 시킨 결과를 모으면 이렇다.

```text
cat .env    → 막힘. "A PreToolUse hook blocked it ... doesn't allow commands that print .env file contents"
wc -l .env  → 허용. ".env has 1 line."
ls -la      → 허용
훅 판단 비용(claude-haiku-5-5): 0.000157 / 0.000219 / 0.000098 달러
```

프롬프트 훅은 따로 모델을 정하지 않으면 Claude Code가 백그라운드 일에 쓰는 모델로 판단한다. 이 실행에서는 Haiku 5.5였고, 한 번에 0.0001~0.0002달러였다. 디버그 로그에서 판단 하나에 약 1.1초가 걸렸다(명령 훅은 40~110ms). 응답은 `ok`, `reason`, 그리고 Stop에서만 쓰는 `impossible`이다. `impossible: true`는 "이 조건은 절대 못 맞춘다"는 뜻이라 Stop 훅이 끝없이 돌려보내는 문제를 모델 쪽에서 끊는다. PreToolUse에서 `ok: false`의 기본 동작은 턴을 끝내는 것이고, `continueOnBlock: true`를 주면 이유를 도구 오류로 Claude에게 돌려주어 다른 방법을 찾게 한다.

`wc -l .env`가 통과한 데서 프롬프트 훅의 성격이 보인다. 이 명령은 파일을 열어 읽지만 내용은 출력하지 않는다. 모델은 규칙의 의도를 읽고 허용했다. 정규식이라면 `.env`가 들어간 모든 명령을 막았을 것이다. 의도를 읽는 판단은 유연하지만 같은 입력에 늘 같은 답을 낸다는 보장이 없다. 그래서 반드시 지켜야 하는 경계는 권한의 deny 규칙과 command 훅에 두고, 프롬프트 훅은 "커밋 메시지가 규칙에 맞나", "모든 할 일이 끝났나"처럼 글을 읽고 판단해야 하는 곳에 쓴다.

에이전트 훅은 프롬프트 훅에 도구를 준 것이다. 서브에이전트가 Read, Grep, Glob으로 파일을 직접 확인하고 최대 50턴 뒤 `ok`를 돌려준다. "단위 테스트가 모두 통과하는지 확인하라"를 Stop에 거는 식이다. 기본 시간 제한은 60초이고, 문서는 아직 실험 기능이라 운영에는 command 훅을 권한다. 판단 한 번이 서브에이전트 하나라서 프롬프트 훅보다 훨씬 비싸고 느리다.

모든 사건이 다섯 타입을 다 받지는 않는다. 프롬프트와 에이전트 훅은 PreToolUse, PostToolUse, Stop, SubagentStop, UserPromptSubmit 같은 판단이 필요한 사건에서만 쓸 수 있다. SessionStart는 command와 mcp_tool만, SessionEnd와 Notification은 prompt와 agent를 받지 않는다. 한 사건에 걸린 훅은 동시에 돌고, 프롬프트·에이전트 훅은 12개까지만 한꺼번에 돈다.

## 훅이 안 먹을 때 보는 순서

먼저 `/hooks` 메뉴에서 훅이 실제로 등록됐는지 본다. 설정 파일에 썼다고 등록된 것이 아니다. JSON 문법이 틀렸거나, 신뢰하지 않은 폴더라 대화형 세션이 프로젝트 훅을 읽지 않았을 수 있다.

다음은 디버그 로그다. `claude --debug-file ./debug.txt`로 띄우면 훅마다 끝난 시각과 걸린 시간이 남는다.

```bash
# 훅 실행 줄만 골라 본다
grep -E 'Hooks: [A-Za-z]+(:[a-z]+)? \[|prompt hook' debug.txt
```

```text
2026-10-24T05:42:57.762Z [DEBUG] Hooks: SessionStart:startup ["$CLAUDE_PROJECT_DIR"/.claude/hooks/session-start.sh] finished with status 0 (113ms)
2026-10-24T05:42:58.123Z [DEBUG] Hooks: UserPromptSubmit ["$CLAUDE_PROJECT_DIR"/.claude/hooks/log.sh] finished with status 0 (45ms)
2026-10-24T05:42:59.382Z [DEBUG] Hooks: Processing prompt hook with prompt: You review one Bash command before it runs. Block it if it reads, prints, copies or sends the contents of any .env file. Oth
2026-10-24T05:43:00.487Z [DEBUG] Hooks: Prompt hook condition was met: The command is just 'ls' listing files in the current directory. It does not read, print, copy, or send the contents of any .env 
2026-10-24T05:43:03.773Z [DEBUG] Hooks: Stop ["$CLAUDE_PROJECT_DIR"/.claude/hooks/log.sh] finished with status 0 (42ms)
```

`finished with status` 뒤의 종료 코드와 괄호 안의 시간을 본다. 세션이 굼뜨면 여기서 가장 느린 훅을 찾는다. JSON이 무시되는 것 같으면 같은 로그에서 `Hook output does not start with {, treating as plain text`를 찾는다. stdout 앞에 다른 글이 섞였다는 뜻이다. 훅 하나를 따로 시험할 때는 기록기가 남긴 `last-사건.json`을 그대로 stdin으로 넣어 돌려 본다.

신뢰와 관련해 실험 중에 본 것도 하나 있다. 신뢰 확인을 한 번도 하지 않은 폴더에서 `claude -p`를 돌렸더니 stderr에 이런 줄이 떴다.

```text
Ignoring 1 permissions.allow entry from .claude/settings.json: this workspace has not been trusted. Run Claude Code interactively here once and accept the trust dialog, ...
```

같은 파일의 허용 규칙은 무시됐는데, 같은 파일의 훅은 모두 돌았다. 허용 규칙은 권한을 넓히니 신뢰 전에는 버리고, 훅은 `-p`가 신뢰한 것으로 치고 돌린다. 남의 저장소에 `claude -p`를 돌리기 전에 `.claude/settings.json`의 `hooks`를 먼저 읽어야 하는 이유다. 확장 쪽 보안은 [확장 글의 해당 절](/posts/claude-code-extensions)에 모아 두었다.

정리하면 훅은 "언제(사건과 매처), 무엇을 받고(stdin JSON), 무엇을 돌려주나(종료 코드나 JSON)"의 세 줄로 읽힌다. 거기에 얼마나 오래 걸리고 실패하면 어느 쪽으로 넘어지는지(시간 제한, `onFailure`)를 더하면, 새 사건을 만나도 문서의 그 사건 절만 보면 된다.

## 면접에서 나올 만한 질문

### Claude Code 훅 사건은 어떤 순서로 불리나?

세션에 한 번 SessionStart, 턴마다 UserPromptSubmit, 도구 호출마다 PreToolUse와 PostToolUse, 응답 끝에 Stop, 세션이 닫힐 때 SessionEnd다. PreToolUse는 권한 확인보다 먼저 돌기 때문에 권한에서 막힌 명령은 PreToolUse만 있고 PostToolUse가 없다. 실패한 도구는 PostToolUseFailure로 간다.

### 세션마다 환경 변수를 넣으려면 어떻게 하나?

SessionStart 훅에서 `CLAUDE_ENV_FILE` 경로의 파일에 `export` 줄을 덧붙인다. 그 세션에서 Claude가 실행하는 Bash 명령마다 그 내용이 먼저 실행된다. 다른 훅의 줄을 지우지 않게 `>>`로 쓰고, 늘 같은 정보라면 훅보다 CLAUDE.md가 낫다.

### 훅이 Claude에게 정보를 넘기는 방법은? 주의할 점은?

`hookSpecificOutput.additionalContext`나 일부 사건의 일반 stdout으로 넘기고, 시스템 알림으로 그 사건이 일어난 자리에 들어간다. 명령조보다 사실 서술로 써야 인젝션 방어에 걸리지 않는다. 필드마다 1만 자가 상한이고, 이어 연 세션에서는 지난 턴의 출력이 다시 실행되지 않고 저장된 글로 재생되니 바뀌는 값은 SessionStart에 둔다.

### UserPromptSubmit 훅으로 프롬프트 속 비밀값을 지울 수 있나?

없다. UserPromptSubmit은 막거나 컨텍스트를 덧붙일 수만 있고 프롬프트를 바꿀 수 없다. 막아도 프롬프트 글은 대화 기록 파일과 입력 기록에 남는다. 도구로 나가는 값은 PreToolUse의 `updatedInput`, 도구 결과는 PostToolUse의 `updatedToolOutput`으로 가린다.

### 훅이 시간 제한을 넘기면 어떻게 되나?

기본으로 그 훅의 출력이 버려지고 동작은 그대로 진행된다. 실험에서 3초 제한을 넘긴 UserPromptSubmit 훅의 컨텍스트가 빠져 Claude가 답을 몰랐고 프롬프트는 그대로 갔다. 정책 검사 훅은 `onFailure: "block"`으로 실패 시 막게 하고, 기다릴 필요 없는 일은 `async`로 뒤에서 돌린다.

### Stop 훅이 무한히 Claude를 돌려보내는 것을 어떻게 막나?

입력의 `stop_hook_active`가 true면 막지 않고, 백그라운드 작업이 도는 중이면 막지 않는다. Claude Code도 연속 8번이면 강제로 끝내지만 도구를 부를 때마다 횟수가 초기화되어, 실험에서는 Stop이 18번 불리고 1분 넘게 돌았다. 안내만 할 때는 block 대신 `additionalContext`를 쓴다.

### command 훅과 prompt 훅, agent 훅은 언제 고르나?

규칙을 코드로 쓸 수 있으면 command 훅이다. 빠르고 같은 입력에 늘 같은 답을 낸다. 글을 읽고 의도를 판단해야 하면 prompt 훅으로 모델에 한 번 묻고, 파일을 직접 확인해야 하면 agent 훅을 쓴다. 뒤의 둘은 호출마다 모델 비용과 지연이 붙고 판단이 흔들릴 수 있어서, 반드시 지킬 경계는 권한 규칙과 command 훅에 둔다.

### 훅이 등록됐는데 동작하지 않는 것 같다. 어디부터 보나?

`/hooks`에서 등록을 확인하고, `--debug-file`로 띄워 그 훅의 종료 코드와 걸린 시간을 본다. JSON이 무시되면 stdout 앞에 셸 인사말 같은 다른 글이 섞였는지 찾는다. 훅 하나는 저장해 둔 입력 JSON을 stdin으로 넣어 따로 돌려 보고, 대화형 세션이라면 그 폴더를 신뢰했는지도 확인한다.
