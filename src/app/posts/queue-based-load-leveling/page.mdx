한정판 판매가 오전 10시 정각에 열렸다. 평소 초당 200건이던 주문 API에 10초 동안 초당 2,000건이 들어왔다. 주문 하나는 재고 차감, 결제 승인 요청, 주문 저장까지 DB 쓰기 여러 번을 하고, DB는 초당 500건 정도가 한계다. 3초 만에 커넥션 풀이 바닥났고, 대기하던 요청들이 타임아웃으로 떨어졌다. 클라이언트는 실패를 보고 재시도했고, 10초가 지나 원래 트래픽으로 돌아왔는데도 DB는 몇 분 동안 회복하지 못했다.

이 서비스는 처리 능력이 모자란 게 아니다. 10초 동안 몰린 2만 건을 1분에 나눠 처리할 수 있었다면 DB는 한 번도 한계를 넘지 않았다. 문제는 모든 요청을 들어온 그 순간에 처리하려 한 데 있다. 이 글은 요청과 처리 사이에 큐를 두어 급증을 받아 내는 부하 평준화, 바로 답하지 않고 접수증을 주는 비동기 요청-응답, 여러 워커가 같은 큐를 나눠 처리하는 경쟁 소비자, 급한 일을 먼저 처리하는 우선순위 큐를 한 흐름으로 따라간다. 실습은 Node 22, Redis 7, PostgreSQL 16으로 했다.

이 주제의 다른 글: 큐 자체의 ack와 가시성 타임아웃, 재전달은 [메시지 큐 기초](/posts/message-queue-basics)에서, 받는 쪽이 느릴 때 보내는 쪽을 늦추는 원리는 [백프레셔](/posts/backpressure)에서, 계속 실패하는 메시지를 빼 두는 법은 [데드 레터 큐](/posts/dead-letter-queue)에서 다룬다. 요청 스레드에서 무거운 일을 하는 다른 모양들은 [성능 안티패턴](/posts/performance-antipatterns)에 있다.

## 10시 정각에 DB가 넘어지는 과정

요청이 들어오는 즉시 DB까지 가는 구조에서는 DB가 들어오는 속도를 그대로 받아야 한다. 초당 2,000건이 오면 DB도 초당 2,000건을 처리하거나, 처리하지 못한 만큼이 어딘가에 쌓여야 한다. 그 어딘가가 커넥션 풀 대기열과 앱 서버의 메모리, 그리고 사용자의 타임아웃이다.

이 대기열들은 기다리는 용도로 만든 게 아니다. 커넥션 풀 대기열은 보통 몇 초짜리 타임아웃이 있고, 사용자는 5초쯤 지나면 새로고침을 누르고, 앱 서버의 HTTP 타임아웃은 30초다. 어느 하나가 넘치면 요청은 실패하고, 실패한 요청의 일부는 재시도로 돌아와 들어오는 속도를 더 올린다. 이런 증폭은 [재시도](/posts/retries) 글에서 숫자로 재 봤다.

여기서 바꿀 수 있는 것은 "언제 처리하느냐"다. 주문을 받는 일과 주문을 처리하는 일을 떼어 놓고, 그 사이에 기다리는 일이 본업인 큐를 둔다.

## 큐가 급증을 받아 낸다

API는 요청을 검증하고 큐에 넣은 뒤 바로 답한다. 워커는 큐에서 DB가 감당할 속도로 꺼내 처리한다. 들어오는 속도와 처리하는 속도가 달라도, 그 차이는 큐에 쌓였다가 나중에 빠진다. 이걸 부하 평준화(queue-based load leveling)라고 부른다.

그림에서 보이듯 큐는 처리 능력을 늘려 주지 않는다. 시간을 늘려 줄 뿐이다. 그래서 조건이 하나 붙는다. 긴 시간으로 평균을 냈을 때 들어오는 양이 처리량보다 작아야 한다. 하루 종일 초당 600건이 들어오는데 처리량이 500건이면 큐는 끝없이 길어진다.

얼마나 쌓이고 얼마나 기다리게 되는지는 간단한 계산으로 미리 볼 수 있다. 처음 장면처럼 10초 동안 초당 2,000건이 오고 이후 초당 200건으로 돌아가면, 큐는 1만 5천 건까지 쌓이고 마지막 주문은 약 30초를 기다리며, 큐가 다 비는 건 60초째다.

처리량은 워커 수가 아니라 가장 느린 의존성이 정한다. 워커를 100개로 늘려도 DB가 초당 500건이면 처리량은 500건이다. 오히려 워커가 DB를 다시 한계 너머로 밀어붙이면 큐를 둔 의미가 사라진다. 그래서 워커의 동시 처리 수에는 DB가 버티는 값으로 상한을 둔다.

## 바로 답하지 않고 접수증을 준다

큐를 두면 API는 처리 결과를 모른 채 답해야 한다. 이때 쓰는 HTTP 약속이 202 Accepted다. "요청은 받았고 아직 처리하지 않았다"는 뜻이다. 202와 함께 작업 상태를 볼 수 있는 주소를 `Location` 헤더로 주고, 언제 다시 물어보면 좋을지 `Retry-After`로 알려 준다. 이 흐름을 비동기 요청-응답이라고 부른다.

작은 Node 서버로 이 흐름을 만들어 curl로 따라가 봤다. 작업은 0.5초 뒤 running, 2.5초 뒤 succeeded가 되게 했다.

```bash
# 1) 내보내기 요청: 202와 상태 URL을 받는다
curl -si -X POST localhost:58080/exports

# 2) 1초 뒤 상태 확인
curl -si localhost:58080/exports/jobs/bd8c2893

# 3) 2초 더 지나 다시 확인
curl -si localhost:58080/exports/jobs/bd8c2893
```

```text
HTTP/1.1 202 Accepted
Location: /exports/jobs/bd8c2893
Retry-After: 2
Content-Type: application/json

{"jobId":"bd8c2893","status":"queued"}

HTTP/1.1 200 OK
Retry-After: 2
Content-Type: application/json

{"status":"running"}

HTTP/1.1 303 See Other
Location: /exports/bd8c2893/file
```

(`Date`, `Connection` 같은 공통 헤더는 줄였다.) 상태 URL을 만들 때 정할 것이 몇 가지 있다.

- 상태 값은 `queued`, `running`, `succeeded`, `failed` 정도로 짧게 두고, 실패면 이유와 다시 시도해도 되는지를 함께 준다. `failed`도 200으로 돌려주는 게 보통이다. 상태 조회 자체는 성공했기 때문이다.
- 작업 기록에는 수명을 둔다. 끝난 작업 기록은 며칠 뒤 지우고, 그 뒤의 조회에는 404나 410을 준다.
- 상태 URL도 권한을 확인한다. 작업 id를 추측해 남의 내보내기 파일을 받아 가지 못하게, 작업을 만든 사용자(또는 테넌트)만 볼 수 있게 한다.
- "작업 기록 저장"과 "큐에 넣기"는 서로 다른 저장소라 하나만 성공할 수 있다. 기록은 있는데 메시지가 없으면 작업이 영원히 queued로 남는다. 같은 DB 트랜잭션에 아웃박스 행을 함께 쓰고 릴레이가 큐로 옮기게 하면 이 틈이 없어진다. 운영 방법은 [아웃박스 릴레이 운영](/posts/transactional-outbox)에 있다.

이 규칙들을 API 쪽 코드로 옮기면 이런 모양이 된다. 작업 기록과 아웃박스 행을 한 트랜잭션에 쓰고, 그 뒤에 202를 돌려준다.

```ts
// POST /exports: 작업을 접수하고 202를 돌려준다
app.post("/exports", async (req, res) => {
  const userId = req.user.id;                         // 인증 미들웨어가 넣어 준 값
  const key = req.get("Idempotency-Key") ?? crypto.randomUUID();

  const job = await db.tx(async (t) => {
    // 같은 키로 다시 오면 기존 작업을 돌려준다
    const existing = await t.oneOrNone("SELECT id, status FROM export_jobs WHERE user_id = $1 AND idem_key = $2", [userId, key]);
    if (existing) return existing;
    const created = await t.one(
      "INSERT INTO export_jobs (user_id, idem_key, status) VALUES ($1, $2, 'queued') RETURNING id, status",
      [userId, key],
    );
    // 큐로 보낼 메시지를 같은 트랜잭션의 아웃박스에 쓴다. 릴레이가 큐로 옮긴다
    await t.none("INSERT INTO outbox (topic, payload) VALUES ('exports', $1)", [{ jobId: created.id, userId, key }]);
    return created;
  });

  res.status(202).set({ Location: `/exports/jobs/${job.id}`, "Retry-After": "2" }).json({ jobId: job.id, status: job.status });
});
```

같은 키로 두 번 와도 작업이 하나만 생기게 `(user_id, idem_key)`에 유일 제약을 걸어 둔다. 동시에 두 요청이 들어와 둘 다 `existing`이 없다고 보는 경우는 그 제약이 막는다.

## 결과를 돌려주는 세 가지 길

202를 받은 클라이언트는 결과를 언제 알게 될까. 길은 크게 셋이다.

폴링은 위에서 본 방식이다. 클라이언트가 상태 URL을 주기적으로 묻는다. 가장 단순하고 방화벽이나 프록시와 부딪칠 일이 없다. 대신 묻는 간격만큼 늦게 알고, 사용자가 많으면 상태 조회만으로 요청이 꽤 된다. 서버가 `Retry-After`로 간격을 정해 주고, 클라이언트는 오래 걸릴수록 간격을 늘린다. 서버가 응답을 붙잡고 있다가 바뀌면 답하는 롱 폴링도 있다. 그 비용은 [롱 폴링](/posts/long-polling)에서 다룬다.

브라우저 쪽 폴링은 서버가 준 간격을 따르고, 상한과 중지를 함께 둔다.

```ts
async function waitForJob(statusUrl: string, signal: AbortSignal): Promise<string> {
  let delayMs = 1000;
  const deadline = Date.now() + 10 * 60_000;            // 10분이 지나면 포기하고 안내한다
  while (Date.now() < deadline) {
    const res = await fetch(statusUrl, { redirect: "manual", signal });
    if (res.type === "opaqueredirect" || res.status === 303) return statusUrl + "/result";
    const body = await res.json();
    if (body.status === "failed") throw new Error(body.reason ?? "export failed");
    const retryAfter = Number(res.headers.get("Retry-After"));
    delayMs = retryAfter > 0 ? retryAfter * 1000 : Math.min(delayMs * 2, 15_000);
    await new Promise((r) => setTimeout(r, delayMs));
  }
  throw new Error("timed out");
}
```

브라우저의 `fetch`는 303을 만나면 기본으로 따라가서 결과 주소의 응답을 돌려준다. 위 코드처럼 `redirect: "manual"`을 주면 따라가지 않는 대신 응답 내용을 읽을 수 없는 `opaqueredirect`로 받는다. 결과 파일을 바로 받을 거라면 기본값대로 따라가게 두고, 응답의 `res.redirected`로 끝났는지 판단해도 된다.

웹훅은 서버 대 서버에서 쓴다. 요청할 때 콜백 주소를 받아 두었다가, 작업이 끝나면 워커가 그 주소로 결과를 보낸다. 받는 쪽은 폴링 없이 바로 알지만, 보내는 쪽은 받는 서버가 죽어 있을 때의 재시도, 서명, 중복 전달을 다 책임져야 한다. 클라이언트도 웹훅이 끝내 안 올 때를 대비해 상태 URL을 함께 쓰는 편이 안전하다. 자세한 건 [웹훅](/posts/webhooks)에 있다.

브라우저라면 서버가 먼저 말하게 할 수 있다. 화면이 열려 있는 동안 SSE나 WebSocket 연결로 진행률과 완료를 밀어 준다. 연결을 붙잡는 서버 자원이 들고, 연결이 끊기면 상태 URL로 돌아와야 한다. [Server-Sent Events](/posts/server-sent-events) 글에서 재연결과 프록시 버퍼링을 다룬다.

화면을 닫을 수 있는 긴 작업(몇 분짜리 리포트)은 이메일이나 앱 알림으로 끝을 알리고 결과 페이지를 링크하는 것도 흔하다. 어느 길을 고르든 상태 URL은 기본으로 둔다. 다른 길이 실패했을 때 돌아올 곳이다.

## 여러 워커가 같은 큐를 나눠 처리한다

워커 하나로 처리량이 모자라면 같은 큐를 읽는 워커를 여러 개 띄운다. 메시지 하나는 워커 하나만 가져가고, 빨리 끝낸 워커가 다음 것을 가져간다. 워커들이 일감을 놓고 경쟁하는 모양이라 경쟁 소비자(competing consumers) 패턴이라고 부른다. ack와 가시성 타임아웃이 이 경쟁을 안전하게 만드는 장치이고, 그 원리는 [메시지 큐 기초](/posts/message-queue-basics)에 있다.

워커가 몇 개 필요한지는 리틀의 법칙으로 어림한다. 동시에 처리 중인 작업 수 = 처리량 × 작업 하나의 처리 시간. 초당 500건을 처리해야 하고 하나에 100ms가 걸리면 동시에 50개를 처리해야 한다. 워커 하나가 동시에 10개씩 처리하면 5개가 필요하다. 거꾸로 DB가 초당 500건까지만 버틴다면 동시 처리 수 50이 상한이고, 워커를 더 띄워도 그 이상 가져가지 못하게 막는다.

워커 프로세스 하나 안에서도 동시 처리 수를 정해 둔다. Redis 리스트를 큐로 쓴다면, 꺼낸 메시지를 처리 중 목록으로 옮기는 `BLMOVE`와 동시 처리 한도를 함께 쓴다.

```ts
import { createClient } from "redis";

const CONCURRENCY = 10;                       // 이 프로세스가 동시에 처리할 최대 개수
const redis = createClient({ url: process.env.REDIS_URL });
await redis.connect();

async function loop(slot: number) {
  const conn = redis.duplicate();             // 블로킹 명령은 연결을 붙잡으니 슬롯마다 따로
  await conn.connect();
  while (true) {
    // 큐 맨 앞에서 꺼내 처리 중 목록으로 옮긴다. 5초 동안 없으면 null
    const raw = await conn.blMove("orders:queue", "orders:processing", "LEFT", "RIGHT", 5);
    if (!raw) continue;
    try {
      await handleOrder(JSON.parse(raw));      // 멱등하게 만든 처리
      await conn.lRem("orders:processing", 1, raw); // 끝났으면 처리 중 목록에서 지운다(ack)
    } catch (e) {
      console.error({ slot, err: String(e) });  // 남겨 두면 회수 작업이 다시 큐로 돌린다
    }
  }
}

for (let i = 0; i < CONCURRENCY; i++) void loop(i);
```

처리 중 목록에 오래 남은 메시지를 다시 큐로 돌리는 회수 작업이 따로 있어야 이 구조가 완성된다. 그 부분과 가시성 타임아웃의 원리는 [메시지 큐 기초](/posts/message-queue-basics)에서 같은 명령으로 다룬다. 이걸 직접 다 짜기보다 [BullMQ](/posts/bullmq-job-queue) 같은 라이브러리가 동시 처리 수, 재시도, 멈춘 작업 회수를 대신해 준다.

워커 수를 큐 길이에 맞춰 자동으로 조절하고 싶을 때 쿠버네티스에서는 KEDA를 많이 쓴다. KEDA는 큐 길이 같은 외부 지표를 읽어 HPA에 넘겨 주고, 할 일이 없을 때 워커를 0개까지 줄일 수 있다. Redis 리스트를 큐로 쓴다면 이렇게 적는다.

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: order-worker
spec:
  scaleTargetRef:
    name: order-worker        # 늘리고 줄일 Deployment
  minReplicaCount: 0          # 큐가 비면 0개까지
  maxReplicaCount: 10         # DB가 버티는 동시 처리 수로 상한을 정한다
  pollingInterval: 15         # 큐 길이를 몇 초마다 볼지 (기본 30)
  cooldownPeriod: 300         # 마지막 활동 뒤 0개로 줄이기까지 기다릴 초 (기본 300)
  triggers:
    - type: redis
      metadata:
        addressFromEnv: REDIS_ADDRESS
        listName: orders:queue
        listLength: "100"         # Pod 하나당 감당할 대기 메시지 수
        activationListLength: "1" # 0개에서 깨어나는 기준
```

여기서 가장 중요한 줄은 `maxReplicaCount`다. 큐가 10만 건 쌓였다고 워커를 200개로 늘리면, 그 워커들이 한꺼번에 DB로 달려가 처음 장면을 그대로 재현한다. 오토스케일링에서 늘어나는 속도와 관찰 간격을 정하는 법은 [오토스케일링](/posts/autoscaling)과 [HPA](/posts/k8s-hpa)에서 다룬다. 0개에서 깨어나는 동안 첫 메시지가 기다리는 시간도 감안한다. 큐 지연 목표가 수 초라면 최소 1개는 남겨 둔다.

## 급한 일을 먼저 꺼내기

큐가 쌓이면 모든 작업이 같이 늦어진다. 그런데 작업마다 급한 정도가 다르다. 유료 사용자의 주문 확인 메일과 무료 사용자의 월간 리포트가 같은 줄에 서 있으면, 리포트 1만 건 뒤에 메일이 기다린다. 이때 우선순위 큐를 쓴다.

가장 단순한 방법은 우선순위마다 큐를 따로 두는 것이다. Redis의 `BLPOP`은 여러 리스트를 주면 왼쪽에 적은 리스트부터 확인해서 비어 있지 않은 첫 리스트에서 꺼낸다. 이 성질로 우선순위를 만들 수 있다.

```bash
# 무료 작업 셋, 유료 작업 하나를 넣는다
redis-cli rpush jobs:free f1 f2 f3
redis-cli rpush jobs:paid p1

# 워커는 항상 paid를 먼저 본다
redis-cli blpop jobs:paid jobs:free 0
redis-cli blpop jobs:paid jobs:free 0
redis-cli blpop jobs:paid jobs:free 0
```

```text
3
1
jobs:paid
p1
jobs:free
f1
jobs:free
f2
```

나중에 넣은 `p1`이 먼저 나오고, 그다음부터 무료 작업이 순서대로 나온다. RabbitMQ는 큐를 만들 때 `x-max-priority` 인자를 주면 큐 하나 안에서 메시지 우선순위를 지원한다. SQS 표준 큐에는 우선순위가 없어서 큐를 나눠야 한다. 큐 하나 안에서 가장 작은 것을 꺼내는 자료구조 자체는 [힙과 우선순위 큐](/posts/ds-heap)에 있다.

엄격한 우선순위에는 함정이 있다. 유료 작업이 끊이지 않고 들어오면 무료 작업은 영원히 나오지 않는다. 이걸 기아(starvation)라고 한다. 막는 방법은 둘이다. 하나는 가중치를 두어 꺼내는 것이다. 유료에서 4번 꺼내면 무료에서 1번 꺼내는 식이다. 다른 하나는 우선순위마다 워커 풀을 따로 두는 것이다. 유료 워커 8개, 무료 워커 2개로 나누면 무료도 느리지만 꾸준히 처리되고, 무료 쪽 폭주가 유료 쪽 처리량을 빼앗지도 못한다. 고객사 단위로 공정하게 나누는 문제는 [멀티 테넌시](/posts/multi-tenancy-isolation)의 공정 몫과 같은 이야기다.

## 큐가 끝없이 쌓일 때 정하는 기준

큐는 급증을 받아 주지만, 받아 준 작업이 사용자가 기다리는 시간 안에 끝나지 않으면 받은 의미가 없다. 주문 확인이 3시간 뒤에 오면 사용자는 이미 고객센터에 전화했다. 그래서 큐에도 목표가 필요하다.

목표는 큐 길이가 아니라 큐 지연 시간으로 정한다. "주문 처리 작업의 99%가 큐에 들어간 지 60초 안에 꺼내진다" 같은 식이다. 큐 길이 1만 건은 처리량이 초당 1만 건인 시스템에는 1초이고, 초당 10건인 시스템에는 17분이다. 같은 숫자가 전혀 다른 뜻이 된다.

지연 시간을 재려면 메시지에 넣은 시각을 적어 둔다. 맨 앞 메시지의 나이가 지금 가장 오래 기다린 작업의 대기 시간이다.

```bash
# 메시지에 넣은 시각(ms)을 함께 담는다
redis-cli rpush orders:queue '{"orderId":"o-1","enqueuedAt":1792784010906}'

# 맨 앞 메시지를 지우지 않고 본다. 지금 시각에서 enqueuedAt을 빼면 가장 오래된 대기 시간이다
redis-cli lindex orders:queue 0
```

SQS라면 CloudWatch의 `ApproximateAgeOfOldestMessage`, Kafka라면 소비자 그룹의 랙(lag)이 같은 역할을 한다. 경보는 이 나이가 목표의 절반쯤을 넘을 때 건다.

목표를 넘기 시작하면 무엇을 할지도 미리 정해 둔다.

- 처리량을 늘린다. 워커를 늘릴 여유가 DB에 있다면 가장 먼저다.
- 덜 급한 일을 미룬다. 우선순위가 낮은 작업의 워커를 잠깐 멈추고 급한 쪽에 몰아준다.
- 들어오는 쪽에서 거절한다. 지금 넣어도 목표 안에 못 끝낼 작업이라면 큐에 넣지 않고 503이나 429로 바로 거절한다. 받아 놓고 3시간 뒤에 처리하는 것보다 지금 "나중에 다시"라고 말하는 편이 정직하다.
- 상한을 둔다. 큐 길이 상한이나 메시지 수명(TTL)을 두어 너무 오래된 작업은 버리거나 따로 빼 둔다. 수명이 지난 "10시 판매 시작" 알림은 보내지 않는 게 낫다.

## 순서가 필요한 작업

경쟁 소비자는 순서를 깬다. 같은 주문에 대한 "생성"과 "취소" 메시지가 큐에 차례로 있어도, 워커 둘이 하나씩 가져가면 취소가 먼저 끝날 수 있다. 전체 순서를 지키려면 워커가 하나여야 하는데 그러면 처리량을 늘릴 수 없다.

실무에서는 전체 순서 대신 키별 순서를 지킨다. 같은 주문의 메시지는 같은 줄에 넣고, 그 줄은 한 번에 한 워커만 처리한다. Kafka는 메시지 키로 파티션을 고르고 파티션 하나는 소비자 그룹에서 소비자 하나만 읽는다. SQS FIFO 큐는 `MessageGroupId`가 같은 메시지를 순서대로 하나씩 내준다. 대가는 핫 키다. 주문 하나에 메시지가 몰리면 그 줄만 밀린다. 파티션 쪽 이야기는 [Kafka 기초](/posts/kafka-basics)에 있다.

순서 자체를 덜 필요하게 만드는 방법도 있다. 메시지에 버전 번호를 넣고, 처리할 때 저장된 버전보다 오래된 메시지는 무시한다. 그러면 순서가 뒤집혀 와도 최종 상태는 맞는다.

## 두 번 처리되어도 괜찮게

대부분의 큐는 최소 한 번 전달을 보장한다. 워커가 처리를 마치고 ack를 보내기 직전에 죽으면, 메시지는 다른 워커에게 다시 간다. 그래서 같은 주문이 두 번 처리될 수 있다는 가정에서 출발한다. 각 전달 보장이 어디까지인지는 [메시지 전달 보장](/posts/message-delivery-semantics)에서 다룬다.

가장 흔한 장치는 처리한 메시지를 기록하는 표다. 클라이언트가 보낸 `Idempotency-Key`를 메시지에 실어 두고, 워커는 처리 트랜잭션 안에서 그 키를 먼저 넣어 본다.

```sql
CREATE TABLE processed_messages (
  idempotency_key text PRIMARY KEY,
  processed_at    timestamptz NOT NULL DEFAULT now()
);

-- 워커가 같은 메시지를 두 번 받았다
INSERT INTO processed_messages (idempotency_key) VALUES ('ord-7f3a')
ON CONFLICT DO NOTHING RETURNING idempotency_key;

INSERT INTO processed_messages (idempotency_key) VALUES ('ord-7f3a')
ON CONFLICT DO NOTHING RETURNING idempotency_key;
```

```text
 idempotency_key
-----------------
 ord-7f3a
(1 row)

INSERT 0 1

 idempotency_key
-----------------
(0 rows)

INSERT 0 0
```

첫 번째는 한 줄이 돌아오니 처리를 계속하고, 두 번째는 0줄이니 이미 처리된 메시지로 보고 ack만 한다. 이 `INSERT`와 실제 주문 처리가 같은 트랜잭션에 있어야 한다. 따로 커밋하면 키만 남고 처리는 안 된 상태가 생긴다. 결제처럼 외부 API를 부르는 처리라면 그쪽에도 같은 키를 넘긴다. 동시에 같은 키가 두 번 들어오는 경우까지 다루는 구현은 [멱등성 키 구현](/posts/idempotency-key)에 있다.

계속 실패하는 메시지도 정해 둔다. 잘못된 데이터 때문에 매번 실패하는 메시지가 재시도로 큐 앞을 계속 차지하면 뒤의 정상 메시지까지 늦어진다. 재시도 횟수에 상한을 두고, 넘으면 [데드 레터 큐](/posts/dead-letter-queue)로 빼 둔다.

## 큐를 두지 않는 편이 나을 때

큐는 공짜가 아니다. 사용자는 결과를 바로 보지 못하고, 화면은 "처리 중" 상태를 다뤄야 하고, 운영할 시스템이 하나 늘고, 장애 지점도 하나 는다. 이런 경우에는 다시 생각한다.

- 사용자가 결과를 바로 봐야 하는 짧은 요청. 로그인, 장바구니 담기, 검색처럼 수십 ms에 끝나는 일을 큐로 보내면 지연만 늘어난다.
- 급증이 아니라 평소 처리량이 모자랄 때. 평균 도착량이 처리량보다 크면 큐는 시간만 벌 뿐 결국 넘친다. 처리 자체를 빠르게 하거나 늘려야 한다.
- 결과를 동기적으로 확정해야 하는 단계. 재고를 확정했는지 사용자에게 바로 말해야 한다면, 그 단계만 동기로 두고 나머지(메일, 포인트 적립, 분석 이벤트)를 큐로 보내는 식으로 나눈다.

처음 장면의 주문도 전부 큐로 보낼 필요는 없었다. 재고 예약은 Redis 같은 빠른 저장소에서 동기로 하고, "주문 접수됨"을 202로 돌려준 뒤 결제 확정, 주문 저장, 메일 발송을 큐 뒤의 워커가 DB 속도에 맞춰 처리하면 된다.

## 현장에서 큐 문제를 만났을 때

"주문 확인 메일이 안 온다"는 제보가 오면 이 순서로 본다. 가장 오래된 메시지의 나이가 늘고 있는지 본다. 늘고 있다면 워커 수와 워커의 처리 속도를 보고, 워커는 충분한데 느리다면 워커가 기다리는 의존성(DB, 외부 API)을 본다. 나이가 늘지 않는데 메일이 안 간다면 메시지가 아예 안 들어오고 있는 것이니 생산 쪽(아웃박스 릴레이, enqueue 에러 로그)을 본다. 데드 레터 큐에 메시지가 쌓이고 있다면 같은 이유로 실패하는 메시지를 몇 개 꺼내 본다.

큐 지연이 갑자기 튀었다가 내려가기를 반복하면 오토스케일러가 늦게 반응하는지, 워커가 0개까지 줄었다 깨어나는지를 본다. 워커를 늘렸더니 오히려 처리량이 줄었다면 워커들이 DB나 외부 API를 한계 너머로 밀고 있는 것이다. 동시 처리 수 상한을 낮춘다.

## 급증은 줄로 받고, 줄은 시간으로 잰다

큐는 들어오는 속도와 처리하는 속도를 떼어 놓아, 급증을 DB가 버티는 속도로 고르게 펴 준다. 그 대가로 API는 결과 대신 202와 상태 URL을 주고, 결과는 폴링이나 웹훅이나 서버 푸시로 돌려준다. 워커는 같은 큐를 나눠 처리하되 가장 느린 의존성이 정한 상한을 넘지 않게 늘리고, 급한 일은 따로 줄을 세운다. 그리고 큐의 건강은 길이가 아니라 가장 오래 기다린 작업의 나이로 잰다.

## 면접에서 나올 만한 질문

### 큐 기반 부하 평준화는 어떤 문제를 푸나요?

들어오는 요청이 순간적으로 처리 능력을 넘을 때, 넘친 몫을 큐에 쌓았다가 처리할 수 있는 속도로 꺼내게 해서 뒤쪽 시스템이 한계를 넘지 않게 한다. 처리 능력을 늘려 주는 게 아니라 시간을 벌어 주는 것이라, 긴 시간 평균으로 보면 도착량이 처리량보다 작아야 한다. 10초 동안 초당 2,000건이 오고 처리량이 500건이면 큐는 1만 5천 건까지 쌓이고 마지막 작업은 약 30초를 기다린다.

### 202 Accepted는 언제 쓰고, 응답에 무엇을 담나요?

요청은 받았지만 아직 처리하지 않았을 때 쓴다. 작업 상태를 볼 수 있는 URL을 `Location` 헤더에, 다시 물어볼 간격을 `Retry-After`에 담고, 본문에는 작업 id와 현재 상태를 넣는다. 202는 큐가 메시지를 확실히 받은 뒤에 돌려줘야 하고, 작업이 끝나면 상태 URL이 303으로 결과 주소를 안내하는 방식이 흔하다.

### 비동기 작업의 결과는 어떻게 돌려주나요?

폴링, 웹훅, 서버 푸시(SSE나 WebSocket) 세 가지가 있다. 폴링은 단순하지만 간격만큼 늦고 조회 요청이 늘며, 웹훅은 서버 대 서버에서 바로 알릴 수 있지만 재시도와 서명과 중복을 책임져야 하고, 서버 푸시는 화면이 열린 동안 진행률까지 보낼 수 있지만 연결 자원이 든다. 어느 쪽을 써도 상태 URL은 기본으로 두어, 다른 길이 실패했을 때 돌아올 곳으로 삼는다.

### 경쟁 소비자에서 워커 수는 어떻게 정하나요?

리틀의 법칙으로 필요한 동시 처리 수를 어림한다. 초당 500건을 100ms씩 처리해야 하면 동시에 50개가 필요하다. 다만 상한은 워커가 아니라 가장 느린 의존성이 정하므로, DB가 버티는 동시 처리 수를 넘지 않게 `maxReplicaCount`나 동시 처리 한도를 둔다. 큐 길이로 워커를 늘리는 KEDA 같은 도구를 쓸 때도 이 상한이 가장 중요한 설정이다.

### 큐가 계속 쌓이면 어떤 기준으로 대응하나요?

큐 길이가 아니라 가장 오래 기다린 메시지의 나이로 목표를 정한다. 같은 1만 건도 처리량에 따라 1초일 수도 17분일 수도 있기 때문이다. 목표를 넘기 시작하면 의존성에 여유가 있는 만큼 워커를 늘리고, 덜 급한 작업을 미루고, 목표 안에 못 끝낼 새 작업은 입구에서 503이나 429로 거절하고, 수명이 지난 메시지는 버린다.

### 우선순위 큐에서 낮은 우선순위 작업이 굶는 문제는 어떻게 막나요?

엄격한 우선순위는 높은 작업이 끊이지 않으면 낮은 작업을 영원히 미룬다. 높은 쪽에서 4번 꺼내면 낮은 쪽에서 1번 꺼내는 식으로 가중치를 두거나, 우선순위마다 워커 풀을 따로 두어 낮은 쪽도 꾸준히 처리되게 한다. 워커 풀을 나누면 낮은 쪽 폭주가 높은 쪽 처리량을 빼앗지 못하는 효과도 있다.

### 경쟁 소비자를 쓰면 순서가 깨지는데, 순서가 필요한 작업은 어떻게 하나요?

전체 순서 대신 키별 순서를 지킨다. 같은 주문의 메시지는 같은 파티션이나 같은 메시지 그룹에 넣어 한 번에 한 소비자만 처리하게 한다. Kafka는 메시지 키로 파티션을 고르고, SQS FIFO는 `MessageGroupId`로 묶는다. 순서 자체를 덜 필요하게 하려면 메시지에 버전을 넣어 오래된 메시지를 무시하게 만든다.

### 같은 메시지가 두 번 처리되는 건 어떻게 막나요?

대부분의 큐가 최소 한 번 전달이라 중복은 정상으로 보고 처리를 멱등하게 만든다. 요청의 멱등성 키를 메시지에 실어 두고, 워커는 처리 트랜잭션 안에서 처리 기록 표에 그 키를 `ON CONFLICT DO NOTHING`으로 넣어 본 뒤 0줄이면 이미 처리된 것으로 보고 ack만 한다. 키 기록과 실제 처리가 같은 트랜잭션에 있어야 하고, 외부 API에도 같은 키를 넘긴다.
