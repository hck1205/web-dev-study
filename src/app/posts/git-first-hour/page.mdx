## 최종_진짜최종_v3.zip

내 문서 폴더에 이런 파일들이 있었다.

```text
보고서.docx
보고서_수정.docx
보고서_최종.docx
보고서_최종_진짜.docx
보고서_최종_진짜_v3.zip
```

어느 게 마지막인지는 파일 날짜로 겨우 짐작한다. 두 번째와 세 번째 사이에 무엇이 바뀌었는지는 둘을 열어 놓고 눈으로 비교해야 안다. 동료가 `보고서_최종.docx`를 받아 고쳐 보내면, 그사이 내가 고친 것과 합치는 일도 손으로 한다.

버전 관리 시스템(VCS)은 이 일을 대신 하는 프로그램이다. 파일 이름은 하나로 두고, 원하는 순간의 상태를 메모와 함께 기록한다. 언제든 그 기록을 다시 꺼내 보고, 무엇이 바뀌었는지 줄 단위로 비교하고, 여러 사람의 변경을 합친다. Git은 그중 지금 가장 널리 쓰는 도구다.

이 글은 Git을 처음 깔고 한 시간 안에 첫 커밋을 만들어 GitHub에 올리기까지를 따라간다. 실행 결과는 Ubuntu 24.04의 Git 2.43.0에서 직접 돌린 것이고, GitHub에 붙는 부분은 실제 GitHub 대신 로컬에 만든 원격 저장소로 같은 동작을 재현했고, 출력에 나오는 원격 주소만 GitHub 주소로 바꿔 적었다. 각 단계의 속 사정은 끝에 링크한 글들에서 더 깊이 본다.

## Git과 GitHub는 다른 것이다

처음에 가장 많이 헷갈리는 게 이 둘이다. Git은 내 컴퓨터에 까는 프로그램이다. 인터넷 없이도 돌고, 기록은 프로젝트 폴더 안의 `.git` 폴더에 저장된다. GitHub는 Git 저장소를 인터넷에 올려 두고 여러 사람이 함께 쓰게 해 주는 서비스다. 저장소를 보관하는 일 말고도 코드 리뷰(PR), 이슈, CI 같은 협업 기능을 얹었다. GitLab, Bitbucket도 같은 자리에 있는 서비스다.

Git이 "분산" 버전 관리라는 말도 여기서 나온다. 예전에 많이 쓰던 SVN 같은 중앙 집중형은 기록 전체가 서버 하나에만 있고, 각자의 컴퓨터에는 지금 작업 중인 파일만 있었다. 커밋하려면 서버에 접속해야 했고, 서버가 멈추면 아무도 기록을 남기지 못했다. Git은 저장소를 받는 순간 모든 기록이 통째로 내 컴퓨터에 복사된다. 커밋, 기록 보기, 비교가 전부 내 컴퓨터 안에서 끝나고, 서버와는 주고받을 때만 연결한다.

## 설치하고 나를 소개하기

Ubuntu에서는 apt로 깐다.

```bash
# 패키지 목록을 갱신하고 git을 설치한다
sudo apt update
sudo apt install -y git

# 설치된 버전을 확인한다
git --version
```

```text
git version 2.43.0
```

macOS는 터미널에서 `git --version`을 처음 치면 Xcode 명령줄 도구를 설치하겠느냐고 묻는다. 그걸 받거나 Homebrew로 `brew install git`을 한다. Windows는 Git for Windows를 설치하면 Git Bash라는 터미널이 함께 온다. 이 글의 명령은 셋 모두에서 똑같이 동작한다.

설치하고 나서 바로 커밋하면 이런 오류를 만난다. 일부러 아무 설정 없이 해 봤다.

```bash
mkdir report && cd report
echo "# 월간 보고서" > README.md
git init
git add README.md
git commit -m "첫 보고서"
```

```text
Author identity unknown

*** Please tell me who you are.

Run

  git config --global user.email "you@example.com"
  git config --global user.name "Your Name"

to set your account's default identity.
Omit --global to set the identity only in this repository.

fatal: unable to auto-detect email address (got 'root@vm.(none)')
```

커밋마다 "누가 만들었는지"가 들어가는데 Git이 그걸 모른다는 뜻이다. 오류가 시키는 대로 이름과 이메일을 정한다. 이메일은 GitHub 계정에 등록한 주소로 맞춰야 GitHub가 커밋을 내 계정과 연결해 프로필에 보여 준다. 이메일을 공개하기 싫으면 GitHub 설정에 있는 `숫자+아이디@users.noreply.github.com` 주소를 쓴다.

```bash
# 이 컴퓨터의 모든 저장소에 쓸 이름과 이메일
git config --global user.name "Kim Dev"
git config --global user.email "kimdev@example.com"

# 새 저장소의 첫 브랜치 이름을 main으로 한다
git config --global init.defaultBranch main

# 설정이 잘 들어갔는지 본다
git config --global --list
```

```text
user.name=Kim Dev
user.email=kimdev@example.com
init.defaultbranch=main
```

`--global` 설정은 홈 폴더의 `~/.gitconfig` 파일에 그대로 적힌다. 열어 보면 이렇다.

```text
[user]
	name = Kim Dev
	email = kimdev@example.com
[init]
	defaultBranch = main
```

`init.defaultBranch`를 정하지 않으면 `git init`할 때마다 "Using 'master' as the name for the initial branch"라는 긴 안내가 나오고 첫 브랜치가 `master`가 된다. GitHub가 새 저장소의 기본 브랜치를 `main`으로 만들기 때문에 처음부터 맞춰 두면 올릴 때 덜 헷갈린다.

회사 저장소에서만 회사 이메일을 쓰고 싶으면 그 저장소 안에서 `--global` 없이 `git config user.email ...`을 친다. 그 저장소의 `.git/config`에 적혀서 전역 설정보다 우선한다.

## 사진을 찍기 전에 고르는 단계

이제 첫 커밋을 만든다. 폴더를 저장소로 만드는 게 `git init`이다.

```bash
# 이 폴더를 Git 저장소로 만든다 (.git 폴더가 생긴다)
git init

# 지금 상태를 본다
git status
```

```text
Initialized empty Git repository in /home/kim/report/.git/
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md
	report.md

nothing added to commit but untracked files present (use "git add" to track)
```

`Untracked files`는 Git이 아직 관리하지 않는 파일이다. 폴더에 있다고 다 기록되는 게 아니다. 어떤 파일을 다음 기록에 넣을지 `git add`로 고른다. 고른 파일이 올라가는 곳을 스테이징 영역이라고 부른다. 사진을 찍기 전에 찍을 물건을 상 위에 올려 두는 단계라고 생각하면 된다.

```bash
# 두 파일을 다음 커밋에 넣는다
git add README.md report.md
git status
```

```text
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   README.md
	new file:   report.md
```

`Changes to be committed`에 두 파일이 올라왔다. 이제 사진을 찍는다. `-m` 뒤에 무엇을 했는지 한 줄 메모를 쓴다.

```bash
# 스테이징 영역에 올린 그대로를 기록한다
git commit -m "첫 보고서 추가"
```

```text
[main (root-commit) 1b8cf4d] 첫 보고서 추가
 2 files changed, 2 insertions(+)
 create mode 100644 README.md
 create mode 100644 report.md
```

`1b8cf4d`가 이 커밋의 이름(해시의 앞 7자리)이다. `root-commit`은 부모가 없는 첫 커밋이라는 표시다.

파일을 한 번 고쳐 보자. `report.md`의 숫자를 바꾸고 다시 상태를 본다.

```bash
echo "매출 120" > report.md
git status

# 무엇이 바뀌었는지 줄 단위로 본다
git diff
```

```text
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   report.md

no changes added to commit (use "git add" and/or "git commit -a")
diff --git a/report.md b/report.md
index 9412818..c5b631f 100644
--- a/report.md
+++ b/report.md
@@ -1 +1 @@
-매출 100
+매출 120
```

`-`로 시작하는 줄이 지워진 것, `+`가 새로 들어간 것이다. "보고서_수정.docx와 보고서_최종.docx 사이에 무엇이 바뀌었지"를 눈으로 비교하던 일을 이 한 명령이 한다. 마음에 안 들면 안내문대로 `git restore report.md`로 마지막 커밋 상태로 되돌린다. 이번엔 기록한다.

```bash
# 이미 관리 중인 파일의 변경을 add와 commit을 한 번에 한다
git commit -am "3월 매출 수정"

# 기록을 본다
git log
git log --oneline
```

```text
commit 8055186cac9bf6f791757d411491a3c57e9248c7
Author: Kim Dev <kimdev@example.com>
Date:   Sat Oct 24 04:57:51 2026 +0000

    3월 매출 수정

commit 1b8cf4d36b6046a8e2ab82bc00eaae0d5230e375
Author: Kim Dev <kimdev@example.com>
Date:   Sat Oct 24 04:57:51 2026 +0000

    첫 보고서 추가
8055186 3월 매출 수정
1b8cf4d 첫 보고서 추가
```

`-a`는 이미 한 번 add한 파일만 대상으로 한다. 새로 만든 파일은 여전히 `git add`가 필요하다. 왜 add와 commit이 두 단계로 나뉘어 있는지, add한 뒤에 또 고치면 어떻게 되는지는 [스테이징 영역 글](/posts/git-staging-area)에서 자세히 본다.

커밋 메시지는 나중의 나와 동료가 읽는다. "수정", "ㅇㅇ" 대신 무엇을 왜 바꿨는지 한 줄로 쓴다. 첫 줄은 50자 안팎으로 짧게, 필요하면 한 줄 비우고 아래에 자세히 쓰는 게 관례다.

### 넣지 말아야 할 파일 미리 빼기

비밀번호가 든 `.env`, 수백 MB짜리 `node_modules/`, 빌드 결과물은 저장소에 넣지 않는다. `.gitignore` 파일에 적어 두면 `git status`에 나오지도 않고 `git add .`에도 안 들어간다.

```bash
# 무시할 파일 목록을 만든다
printf ".env\nnode_modules/\n" > .gitignore

# 비밀 값 파일을 하나 만들어 본다
echo "API_KEY=x" > .env
git status -s
```

```text
?? .gitignore
```

`.env`가 목록에 없다. `??`는 아직 관리하지 않는 새 파일이라는 표시다. `.gitignore` 자체는 커밋해서 팀이 같은 규칙을 쓰게 한다. 이미 커밋해 버린 파일은 `.gitignore`에 적어도 빠지지 않는다는 점, 비밀 값을 실수로 올렸을 때 해야 할 일은 [.gitignore 글](/posts/git-ignore-config)과 [큰 파일·비밀 값 글](/posts/git-large-files-secrets)에 있다.

## GitHub에 저장소 만들고 인증하기

여기까지는 전부 내 컴퓨터 안의 일이다. 이제 GitHub에 같은 저장소를 하나 만들어 올린다. GitHub 웹에서 New repository를 누르고 이름을 `report`로 정한다. 이미 로컬에 커밋이 있으니 README나 .gitignore를 추가하는 체크박스는 끈다. 켜면 GitHub 쪽에 첫 커밋이 따로 생겨서 처음 push부터 거절당한다(뒤에서 본다).

올리기 전에 인증부터 해야 한다. 처음 해 보는 사람이 가장 많이 막히는 곳이다. GitHub는 2021년 8월 13일부터 Git 작업에 계정 비밀번호를 받지 않는다. HTTPS 주소로 push할 때 비밀번호를 넣으면 이런 형식의 메시지와 함께 실패한다.

```text
remote: Support for password authentication was removed on August 13, 2021.
fatal: Authentication failed for 'https://github.com/kimdev/report.git/'
```

방법은 둘 중 하나다.

첫째, GitHub CLI(`gh`)로 로그인한다. 가장 쉽다. `gh auth login`을 치면 브라우저가 열리고, 로그인하면 토큰이 운영체제의 자격 증명 저장소에 저장된다. 이후 HTTPS 주소로 하는 push에 그 토큰이 쓰인다.

```bash
# Ubuntu에서 gh 설치 (공식 apt 저장소 등록은 GitHub CLI 문서를 따른다)
sudo apt install -y gh

# 브라우저로 로그인하고, Git이 이 인증을 쓰도록 설정한다
gh auth login

# 로그인 상태를 확인한다
gh auth status
```

둘째, SSH 키를 만들어 GitHub에 등록한다. 서버나 여러 대의 컴퓨터에서 쓴다면 이쪽이 편하다.

```bash
# ed25519 방식의 키 쌍을 만든다 (-C는 키에 붙이는 메모)
ssh-keygen -t ed25519 -C "kimdev@example.com"
```

```text
Generating public/private ed25519 key pair.
Your identification has been saved in /home/kim/.ssh/id_ed25519
Your public key has been saved in /home/kim/.ssh/id_ed25519.pub
The key fingerprint is:
SHA256:YKk1fIE/PWOkXsqQMalqQV78+6uyE2pv3VxneYtWdRI kimdev@example.com
```

파일이 두 개 생겼다. `id_ed25519`는 개인 키라 절대 남에게 주지 않는다. 권한이 `-rw-------`(나만 읽기)인지 확인한다. `.pub`이 붙은 공개 키(`ssh-ed25519 AAAAC3NzaC1lZDI1NT...`로 시작하는 한 줄)를 GitHub 설정의 SSH and GPG keys에 붙여 넣는다. 그다음 `ssh -T git@github.com`으로 붙어 보면, GitHub 문서에 나온 대로 "Hi 아이디! You've successfully authenticated, but GitHub does not provide shell access." 같은 인사가 나와야 성공이다.

인증 방식에 따라 저장소 주소도 다르다. HTTPS는 `https://github.com/kimdev/report.git`, SSH는 `git@github.com:kimdev/report.git`이다. SSH 키를 등록해 놓고 HTTPS 주소를 쓰면 여전히 비밀번호를 묻는다. 토큰과 자격 증명 도우미, 회사 계정과 개인 계정을 나눠 쓰는 법은 [원격 저장소 글](/posts/git-remote-collaboration)에서 다룬다.

## 처음으로 push하기

로컬 저장소에 원격 주소를 등록하고 올린다. 보통 원격의 이름은 `origin`으로 짓는다.

```bash
# GitHub 저장소 주소를 origin이라는 이름으로 등록한다
git remote add origin git@github.com:kimdev/report.git
git remote -v

# 그냥 push해 본다
git push
```

```text
origin	git@github.com:kimdev/report.git (fetch)
origin	git@github.com:kimdev/report.git (push)
fatal: The current branch main has no upstream branch.
To push the current branch and set the remote as upstream, use

    git push --set-upstream origin main

To have this happen automatically for branches without a tracking
upstream, see 'push.autoSetupRemote' in 'git help config'.
```

처음 push할 때는 "내 main을 원격의 어느 브랜치와 짝지을지"를 한 번 알려 줘야 한다. 안내대로 `-u`(`--set-upstream`의 짧은 이름)를 붙인다.

```bash
# 내 main을 origin의 main으로 올리고, 둘을 짝지어 둔다
git push -u origin main
git status
```

```text
To github.com:kimdev/report.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
On branch main
Your branch is up to date with 'origin/main'.
```

`[new branch]`가 원격에 main 브랜치가 새로 생겼다는 뜻이다. 한 번 짝지어 두면 다음부터는 `git push`만 쳐도 된다. GitHub 페이지를 새로고침하면 커밋 두 개와 파일이 보인다.

## 동료가 먼저 올렸을 때

혼자 쓰는 저장소라면 여기까지로 충분하다. 동료와 함께 쓰면 곧 이런 장면을 만난다. 동료가 비용 항목을 추가해 먼저 push했고, 나는 그걸 모른 채 메모 파일을 커밋해 push했다.

```bash
git add notes.md
git commit -m "메모 추가"
git push; echo "exit=$?"
```

```text
To github.com:kimdev/report.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com:kimdev/report.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.
exit=1
```

`rejected`는 실패가 아니라 보호다. 원격에는 내가 모르는 커밋(동료의 "비용 추가")이 있다. 내 커밋으로 그대로 덮어쓰면 동료의 커밋이 사라지니 Git이 막았다. 이미 원격 상태를 한 번 받아 본 뒤라면 같은 상황이 `(non-fast-forward)`로 표시된다. 둘 다 "먼저 받아서 합쳐라"는 뜻이다.

여기서 `git push --force`로 밀어붙이는 게 처음 하는 사람이 가장 많이 하는 사고다. 동료의 커밋이 원격에서 지워진다. 안내대로 먼저 받는다. 그런데 그냥 `git pull`을 치면 요즘 Git은 이렇게 멈춘다.

```text
hint: You have divergent branches and need to specify how to reconcile them.
hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint:
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
...
fatal: Need to specify how to reconcile divergent branches.
```

내 커밋과 동료의 커밋이 갈라졌으니 어떻게 합칠지 정하라는 것이다. 처음에는 `--rebase`를 고르면 기록이 한 줄로 깔끔하게 남는다. 내 커밋을 동료 커밋 뒤로 옮겨 붙이는 방식이다.

```bash
# 원격 커밋을 받고, 내 커밋을 그 뒤로 옮겨 붙인다
git pull --rebase

# 기록을 그래프로 본다
git log --oneline --graph

# 이제 다시 올린다
git push
```

```text
Successfully rebased and updated refs/heads/main.
* cee51d4 메모 추가
* 11ecac7 비용 추가
* 8055186 3월 매출 수정
* 1b8cf4d 첫 보고서 추가
To github.com:kimdev/report.git
   11ecac7..cee51d4  main -> main
```

동료의 "비용 추가" 뒤에 내 "메모 추가"가 붙었고, push가 통과했다. 매번 옵션을 붙이기 귀찮으면 `git config --global pull.rebase true`로 기본값을 정한다. 둘이 같은 줄을 고쳤다면 이 단계에서 충돌이 나는데, 그 해결은 [머지 충돌 글](/posts/git-merge-conflict)에서 본다. merge와 rebase 중 무엇을 고를지는 [rebase 글](/posts/git-rebase)에 있다.

GitHub에서 저장소를 만들 때 README 체크박스를 켰다면 첫 push부터 바로 이 거절을 만난다. GitHub 쪽에 내가 모르는 첫 커밋이 이미 있기 때문이다. 이때 두 기록은 공통 조상이 없어서 `git pull --rebase origin main`으로 합치거나, 처음부터 체크박스를 끄고 만드는 게 간단하다.

## 처음 한 시간에 만나는 오류 정리

`Author identity unknown`은 이름과 이메일을 정하지 않은 것이다. `git config --global user.name`, `user.email`을 설정한다.

`fatal: not a git repository`는 저장소가 아닌 폴더에서 Git 명령을 쳤다는 뜻이다. `pwd`로 지금 위치를 보고, 저장소 폴더로 `cd`한다.

`Support for password authentication was removed`는 HTTPS에 계정 비밀번호를 넣은 것이다. `gh auth login`이나 SSH 키를 쓴다.

`Permission denied (publickey)`는 SSH 키가 GitHub에 등록되지 않았거나, 다른 키를 쓰고 있는 것이다. `ssh -T git@github.com`으로 먼저 확인한다.

`no upstream branch`는 첫 push에서 짝을 정하지 않은 것이다. `git push -u origin main`을 한 번 한다.

`rejected ... (fetch first)`, `(non-fast-forward)`는 원격에 내가 모르는 커밋이 있다는 뜻이다. `git pull --rebase` 후 다시 push한다. `--force`는 쓰지 않는다.

이 밖에 저장소가 명령을 거부하는 더 다양한 상황은 [Git 트러블슈팅 글](/posts/git-troubleshooting)에 모아 두었다.

## 첫 한 시간 다음에 볼 것

이 한 시간 동안 쓴 명령은 열 개 남짓이다. `config`로 나를 소개하고, `init`으로 폴더를 저장소로 만들고, `status`로 상태를 보고, `add`로 고르고, `commit`으로 기록하고, `log`와 `diff`로 돌아보고, `remote`와 `push`로 GitHub에 올리고, `pull`로 동료의 변경을 받는다. "최종_진짜최종" 파일들이 하던 일을 커밋 기록이 대신 한다.

다음으로는 브랜치를 만들어 작업을 나누는 법([브랜치와 머지 글](/posts/git-branch-merge))과, GitHub에서 PR로 함께 일하는 흐름([PR 협업 글](/posts/github-pull-request-flow))을 보면 된다. 실수로 커밋한 걸 되돌리는 법은 [되돌리기 글](/posts/git-undo)에 있다.

## 면접에서 나올 만한 질문

### Git과 GitHub의 차이는 무엇인가요?

Git은 내 컴퓨터에서 도는 버전 관리 프로그램이고, 기록은 저장소의 `.git` 폴더에 저장된다. GitHub는 Git 저장소를 원격에 호스팅하고 PR, 이슈, CI 같은 협업 기능을 얹은 서비스다. Git은 GitHub 없이도 완전히 동작하고, GitLab이나 Bitbucket처럼 같은 역할의 다른 서비스도 있다.

### 분산 버전 관리와 중앙 집중형 버전 관리는 어떻게 다른가요?

중앙 집중형(SVN 등)은 기록 전체가 서버에만 있어서 커밋하거나 기록을 보려면 서버에 접속해야 하고, 서버가 멈추면 모두 멈춘다. 분산형(Git)은 clone할 때 전체 기록이 각자의 컴퓨터로 복사되어 커밋, 기록 조회, 비교, 브랜치가 모두 로컬에서 끝난다. 서버와는 push와 pull로 주고받을 때만 연결하고, 어느 복사본으로든 저장소를 되살릴 수 있다.

### git add와 git commit을 왜 나눠 두었나요?

add로 다음 커밋에 넣을 변경을 고르고, commit으로 고른 것만 기록하게 하려는 것이다. 작업 폴더에 여러 변경이 섞여 있어도 의미 있는 단위로 나눠 커밋할 수 있다. 고른 내용이 모이는 곳이 스테이징 영역(인덱스)이고, add한 뒤 또 고친 내용은 다시 add하기 전까지 커밋에 들어가지 않는다.

### git config --global과 저장소별 설정은 어떻게 적용되나요?

`--global`은 홈 폴더의 `~/.gitconfig`에, 옵션 없이 저장소 안에서 설정하면 그 저장소의 `.git/config`에 적힌다. 저장소 설정이 전역보다 우선해서, 회사 저장소에서만 회사 이메일을 쓰는 식으로 나눌 수 있다. 커밋에 남는 이름과 이메일이 GitHub 계정의 이메일과 맞아야 커밋이 계정에 연결된다.

### push가 rejected될 때 왜 그렇고, 어떻게 해결하나요?

원격 브랜치에 내 로컬에 없는 커밋이 있어서, 그대로 올리면 그 커밋을 덮어쓰게 되기 때문에 Git이 막는 것이다. `git pull --rebase`(또는 merge)로 원격 커밋을 먼저 받아 합친 뒤 다시 push한다. `--force`로 밀면 동료의 커밋이 원격에서 사라지므로 공유 브랜치에서는 쓰지 않는다.

### GitHub에 HTTPS로 push할 때 비밀번호가 거부되는 이유는?

GitHub는 2021년 8월부터 Git 작업에 계정 비밀번호 인증을 받지 않는다. HTTPS를 쓰려면 개인 액세스 토큰이나 `gh auth login`으로 받은 토큰을 자격 증명 도우미에 저장해 쓰고, 아니면 SSH 키를 등록해 SSH 주소로 쓴다. 비밀번호보다 범위와 만료를 정할 수 있는 토큰이나 키가 유출됐을 때 피해가 작다.
