## 첫 이슈를 받은 날

팀에 들어와 처음 받은 일은 이슈 #12였다. "결제 화면에 쿠폰 코드를 넣을 수 있게 해 주세요." 코드는 고칠 수 있을 것 같은데, 그다음이 막막했다. 브랜치 이름은 뭐로 짓지, PR은 언제 열지, 리뷰 코멘트가 열 개 달리면 어떻게 반영하지, 반영한 뒤에 커밋을 정리해도 되나, 머지 버튼 옆의 화살표는 뭘 고르지.

이 글은 이슈 하나가 PR이 되어 리뷰를 거쳐 main에 들어가기까지의 하루를 따라간다. 기본 명령(`clone`, `push`, `pull`)은 [Git 첫 한 시간 글](/posts/git-first-hour)에서, fetch와 강제 푸시의 속 사정은 [원격 저장소 글](/posts/git-remote-collaboration)에서 다뤘다. 여기서는 그 위에서 GitHub가 얹은 협업 장치를 본다. 이슈와 PR을 잇는 방법, draft PR, 리뷰 반영과 suggestion, 리뷰 중의 강제 푸시 예절, 세 가지 머지 방식이 히스토리에 남기는 모양, 그리고 권한이 없는 저장소에 fork로 기여하는 흐름이다.

머지 방식별 히스토리는 Git 2.43으로 같은 상황을 로컬에서 재현해 실제 출력을 실었다. GitHub 화면과 `gh` 명령의 출력은 계정과 저장소마다 달라서 명령만 적는다.

## 이슈에서 브랜치를 딴다

이슈는 할 일의 기록이고, PR은 그 일을 한 코드다. 둘을 이어 두면 PR이 머지될 때 이슈가 저절로 닫히고, 나중에 이슈에서 "이걸 고친 코드가 뭐였지"를 바로 찾는다.

먼저 최신 main에서 브랜치를 만든다. 이름은 팀 규칙을 따르되, 보통 종류와 이슈 번호, 짧은 설명을 넣는다.

```bash
# 최신 main을 받는다
git switch main
git pull

# 이슈 번호가 들어간 브랜치를 만든다
git switch -c feature/12-coupon-code
```

`gh`를 쓰면 이슈와 연결된 브랜치를 바로 만들 수 있다. 이렇게 만든 브랜치는 이슈 화면의 Development 칸에 연결되어 표시된다.

```bash
# 이슈 #12에 연결된 브랜치를 만들고 바로 체크아웃한다
gh issue develop 12 --checkout
```

PR과 이슈를 잇는 가장 흔한 방법은 PR 설명(또는 커밋 메시지)에 닫는 키워드를 쓰는 것이다.

```text
쿠폰 코드 입력란과 검증 API 호출을 추가한다.

Closes #12
```

`close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved` 아홉 단어가 이렇게 동작한다. 대소문자는 가리지 않는다. 다른 저장소의 이슈는 `Fixes acme/shop#12`처럼 쓴다. 이슈 여러 개를 닫으려면 `Closes #12, closes #15`처럼 이슈마다 키워드를 붙인다.

여기서 처음에 많이 당하는 함정이 하나 있다. 이 키워드는 PR이 저장소의 기본 브랜치(보통 main)로 머지될 때만 이슈를 닫는다. `develop` 브랜치를 쓰는 팀에서 `develop`으로 머지하면 PR에는 연결이 보이는데 이슈는 열린 채로 남는다. 그런 팀은 릴리스 PR이 main에 들어갈 때 닫히게 하거나, 이슈를 손으로 닫는 규칙을 둔다. 그냥 참조만 하고 닫고 싶지 않으면 `Refs #12`나 `#12`만 쓴다.

## 덜 됐을 때 여는 draft PR

PR은 다 끝났을 때만 여는 게 아니다. 방향이 맞는지 일찍 확인받고 싶으면 draft로 연다. draft PR은 머지 버튼이 막혀 있고, CODEOWNERS로 지정된 리뷰어에게 리뷰 요청이 가지 않는다. "아직 보지 마세요, 하지만 보고 싶으면 보세요" 상태다.

```bash
# 첫 커밋을 올린다
git push -u origin feature/12-coupon-code

# draft PR을 연다. 제목과 본문은 편집기에서 쓴다
gh pr create --draft --base main

# 준비가 끝나면 리뷰 가능 상태로 바꾼다
gh pr ready

# 리뷰어를 지정한다
gh pr edit --add-reviewer minji
```

draft라도 CI는 돈다. 그래서 "CI가 내 환경과 다르게 깨지는지"를 일찍 알 수 있다. 다만 무거운 E2E 테스트를 draft에서는 건너뛰게 워크플로를 짜 두는 팀도 있다. GitHub Actions에서는 `github.event.pull_request.draft` 값으로 조건을 건다.

PR 설명은 리뷰어가 코드를 열기 전에 읽는 글이다. 무엇을 바꿨는지는 diff가 보여 주니, 왜 바꿨는지와 어떻게 확인했는지를 쓴다. 화면이 바뀌면 전후 스크린샷을 붙이고, 일부러 하지 않은 것(이번 PR 범위 밖)도 적어 둔다. 그래야 "이건 왜 안 했어요?"라는 코멘트가 줄어든다. 저장소에 PR 템플릿을 두면 이 칸이 미리 채워져 나온다. 템플릿을 두는 법은 [저장소 설정 글](/posts/github-repo-governance)에 있다.

이슈 #12의 PR 설명은 이렇게 썼다.

```text
## 왜
결제 화면에서 쿠폰을 쓸 방법이 없어 CS 문의가 늘었다. (#12)

## 무엇을
- 결제 화면에 쿠폰 코드 입력란을 추가한다
- 서버의 쿠폰 검증 API를 호출하고, 실패 사유를 입력란 아래에 보여 준다

## 확인한 방법
- 유효한 코드, 만료된 코드, 없는 코드로 각각 결제 화면에서 확인
- 검증 API 응답이 3초를 넘으면 입력란이 다시 활성화되는지 확인

## 이번에 하지 않은 것
- 쿠폰 여러 장 동시 적용 (#15에서 따로 한다)

Closes #12
```

"하지 않은 것"에 이슈 번호를 적어 두면 리뷰어가 범위 밖 요청을 하지 않고, 남은 일도 이슈로 추적된다.

리뷰어가 코드를 직접 제안하고 싶을 때는 코멘트 안에 `suggestion` 코드 블록을 쓴다. 고르는 줄을 이 내용으로 바꾸자는 뜻이다.

````text
만료일도 같이 보면 좋겠어요.

```suggestion
if (!coupon || coupon.expiresAt < now) {
```
````

작성자 화면에는 이 코멘트 아래 "Commit suggestion" 버튼이 생긴다. 누르면 그 변경이 바로 브랜치에 커밋되고, 커밋 메시지에 제안한 사람이 `Co-authored-by`로 들어간다. 여러 suggestion을 "Add suggestion to batch"로 모아 한 커밋으로 넣을 수도 있다. 버튼으로 반영한 커밋은 GitHub 서버에서 만들어진 것이라, 로컬에서 이어 작업하기 전에 꼭 `git pull`로 받아 와야 한다. 받지 않고 로컬에서 커밋해 push하면 앞 글에서 본 `rejected`를 만난다.

나머지 코멘트는 로컬에서 고쳐 커밋을 더한다. 이때 커밋 메시지를 "리뷰 반영"으로만 쓰지 말고 무엇을 고쳤는지 적는다. squash로 머지할 거라도 리뷰어는 이 커밋 단위로 변경을 확인한다.

코멘트마다 답을 남기는 게 좋다. 고쳤으면 "반영했습니다" 한 줄과 커밋 해시, 고치지 않기로 했으면 이유를 쓴다. 대화가 끝난 스레드는 Resolve conversation으로 접는다. 저장소가 "모든 대화가 해결되어야 머지 가능"을 켜 두었다면 이 버튼이 머지 조건이다. 어떤 의견을 꼭 따라야 하고 어떤 건 취향인지 구분하는 법은 [코드 리뷰 글](/posts/code-review-practices)에서 다룬다.

### 내가 리뷰어가 되었을 때

반대로 리뷰를 요청받았을 때 GitHub에서 하는 동작도 알아 두면 좋다. 줄마다 코멘트를 달 때 "Add single comment"를 누르면 코멘트 하나마다 알림이 바로 간다. "Start a review"로 모아 두었다가 마지막에 한 번에 제출하면 작성자는 알림 한 번으로 전체 의견을 받는다. 대부분은 모아서 제출하는 쪽이 작성자에게 편하다.

제출할 때 결론을 셋 중 하나로 고른다. Comment는 의견만 남기고 승인 여부는 말하지 않는다. Approve는 머지해도 된다는 뜻이다. Request changes는 고치기 전에는 머지하면 안 된다는 뜻이고, 브랜치 보호 규칙이 있으면 이 리뷰어가 다시 승인하거나 리뷰를 철회하기 전까지 머지가 막힌다. 사소한 의견만 있으면 Approve와 함께 코멘트를 남겨 작성자가 고치고 바로 머지하게 하는 편이 흐름을 덜 끊는다.

```bash
# 리뷰 요청받은 PR 목록을 본다
gh pr list --search "review-requested:@me"

# PR 브랜치를 내 로컬로 받아 직접 돌려 본다
gh pr checkout 12

# 결론을 제출한다
gh pr review 12 --approve
gh pr review 12 --request-changes --body "만료된 쿠폰이 통과됩니다. 재현 방법은 코멘트에 적었어요."
```

화면에서 diff만 읽기보다 `gh pr checkout`으로 받아 직접 실행해 보면 빠르게 확인되는 게 많다. 특히 UI 변경이나 마이그레이션이 들어간 PR이 그렇다.

## 리뷰 중에는 히스토리를 다시 쓰지 않는다

리뷰를 반영하다 보면 커밋이 지저분해진다. "오타", "다시 수정", "진짜 수정". 이걸 rebase로 정리하고 강제 푸시하고 싶어진다. 리뷰가 진행 중이라면 참는 게 낫다.

PR 화면에는 "지난번 리뷰 이후 바뀐 것만 보기"가 있다. 리뷰어는 이걸로 반영한 부분만 확인한다. 강제 푸시로 커밋을 바꾸면 GitHub가 비교할 기준 커밋이 사라져서, 리뷰어는 바뀐 부분을 가려 보지 못하고 처음부터 다시 읽어야 한다. 줄에 달려 있던 코멘트도 그 줄이 사라진 것으로 보여 "Outdated"로 접힌다. 함께 같은 브랜치를 만지던 동료가 있었다면 그의 로컬 브랜치도 엇갈린다.

그래서 보통 이렇게 한다.

- 리뷰 중에는 커밋을 더하기만 한다.
- 정리가 필요하면 squash 머지에 맡긴다. 저장소가 squash를 허용한다면 PR 안의 커밋은 지저분해도 main에는 하나로 들어간다.
- 커밋 단위가 의미 있어서 꼭 정리해야 한다면 `git commit --fixup <커밋>`으로 고칠 대상을 표시해 두고, 승인을 받은 뒤 `git rebase -i --autosquash`로 한 번에 접는다. 그리고 리뷰어에게 "커밋만 정리했고 내용은 같다"고 알린다.

강제 푸시를 해야 할 때(main이 앞서 나가서 rebase했을 때 등)는 `--force` 대신 `--force-with-lease`를 쓴다. 내가 마지막으로 본 뒤에 원격 브랜치에 누가 커밋을 올렸다면 거절해 주기 때문에, 방금 버튼으로 반영한 suggestion 커밋을 날려 버리는 사고를 막는다. 이 옵션이 정확히 무엇을 비교하는지는 [원격 저장소 글](/posts/git-remote-collaboration)에서 실제 출력으로 봤다. GitHub는 강제 푸시가 일어나면 PR 타임라인에 "force-pushed"와 함께 전후 비교 링크를 남기니, 리뷰어는 그 링크로 무엇이 바뀌었는지 확인할 수 있다.

## 머지 버튼의 세 가지 선택지

승인을 받고 CI가 초록이면 머지 버튼이 열린다. 버튼 옆 화살표를 누르면 세 가지가 나온다. Create a merge commit, Squash and merge, Rebase and merge. 셋 다 코드는 같은 결과가 되지만 main에 남는 히스토리 모양이 다르다.

같은 상황을 로컬에서 재현했다. 내 PR 브랜치에는 커밋 세 개(쿠폰 모델 추가, 쿠폰 검증 추가, 리뷰 반영)가 있고, 그사이 다른 PR 하나가 main에 먼저 들어갔다.

```bash
# 1. merge commit: 브랜치를 그대로 두고 합친 커밋을 하나 더 만든다
git merge --no-ff feature/coupon -m "Merge pull request #12 from kimdev/feature/coupon"
git log --oneline --graph
```

```text
*   38cb9cd Merge pull request #12 from kimdev/feature/coupon
|\
| * 638cf05 리뷰 반영: 만료일 검사
| * 24dea81 쿠폰 검증 추가
| * 12f4dd2 쿠폰 모델 추가
* | 7174c6b 다른 PR이 먼저 머지됨
|/
* 29a33c9 초기 커밋
```

```bash
# 2. squash: 브랜치의 변경을 모두 합쳐 main 위에 새 커밋 하나로 만든다
git merge --squash feature/coupon
git commit -m "쿠폰 적용 기능 (#12)"
git log --oneline --graph
```

```text
* c3098cc 쿠폰 적용 기능 (#12)
* 7174c6b 다른 PR이 먼저 머지됨
* 29a33c9 초기 커밋
```

```bash
# 3. rebase: 커밋을 하나씩 main 끝으로 옮겨 붙인다
git switch feature/coupon && git rebase main
git switch main && git merge --ff-only feature/coupon
git log --oneline --graph
```

```text
* c4ace15 리뷰 반영: 만료일 검사
* 5f63c46 쿠폰 검증 추가
* 52f0a3b 쿠폰 모델 추가
* 7174c6b 다른 PR이 먼저 머지됨
* 29a33c9 초기 커밋
```

merge commit은 PR이 하나의 단위였다는 사실을 머지 커밋으로 남긴다. `git log --first-parent main`으로 보면 PR 단위로만 한 줄씩 보이고, 되돌릴 때 `git revert -m 1 38cb9cd` 하나로 PR 전체를 뺀다. 대신 "오타 수정" 같은 중간 커밋까지 모두 main에 남고, 그래프가 복잡해진다.

squash는 main을 PR 하나당 커밋 하나로 깔끔하게 만든다. GitHub는 제목 끝에 `(#12)`처럼 PR 번호를 붙여 주어 커밋에서 PR로 바로 찾아간다. 되돌리기도 커밋 하나다. 대신 PR 안의 커밋 단위 정보가 main에서 사라진다. 그리고 다음 절에서 볼 문제가 생긴다.

rebase는 머지 커밋 없이 한 줄 히스토리를 만들면서도 커밋 단위를 살린다. 커밋 하나하나가 의미 있는 단위로 잘 나뉜 PR에 맞는다. 다만 해시가 모두 바뀐다(`12f4dd2`가 `52f0a3b`가 됐다). 로컬 브랜치의 커밋과 main의 커밋이 다른 해시라서 Git은 둘이 같은 커밋인지 모른다. GitHub의 Rebase and merge는 커밋마다 커미터 정보를 새로 쓰기 때문에 서명된 커밋의 서명도 유지되지 않는다.

어느 것이 정답은 아니다. 많은 팀이 squash만 허용해서 main을 단순하게 유지하고, 커밋 단위가 중요한 라이브러리나 큰 저장소는 merge commit이나 rebase를 쓴다. 저장소 설정에서 허용할 방식을 고르고 나머지는 꺼 두면 사람마다 다르게 고르는 혼란이 없다. 브랜치 전략과의 관계는 [브랜치 전략 글](/posts/git-branching-strategy)에서 다룬다.

## squash 뒤에 같은 브랜치로 이어 가면

squash로 머지한 직후, 같은 브랜치에서 작업을 이어 갔다. 쿠폰 사용 내역 기능을 커밋 하나 더 하고, 최신 main을 받으려고 합쳤다.

```bash
# squash 머지 뒤에도 같은 브랜치에서 계속 작업한다
git switch feature/coupon
git commit -am "쿠폰 사용 내역 추가"

# 최신 main을 합친다
git merge main
```

```text
Auto-merging coupon.txt
CONFLICT (add/add): Merge conflict in coupon.txt
Automatic merge failed; fix conflicts and then commit the result.
```

내가 쓴 코드끼리 충돌이 났다. main에 있는 squash 커밋은 내 세 커밋과 내용은 같지만 전혀 다른 커밋이다. Git이 보기에 내 브랜치의 세 커밋은 아직 main에 들어가지 않았다. 실제로 main에 없는 커밋을 세어 보면 네 개가 다 나온다.

```bash
# main에 없는 내 브랜치 커밋을 본다
git log --oneline main..feature/coupon
```

```text
f402d62 쿠폰 사용 내역 추가
638cf05 리뷰 반영: 만료일 검사
24dea81 쿠폰 검증 추가
12f4dd2 쿠폰 모델 추가
```

같은 이유로 squash 머지가 끝난 브랜치를 `git branch -d`로 지우려 하면 거절당한다.

```text
error: the branch 'feature/coupon' is not fully merged.
If you are sure you want to delete it, run 'git branch -D feature/coupon'
```

처음에는 Git이 고장 난 줄 안다. 규칙은 간단하다. squash로 머지된 브랜치는 끝난 것으로 보고 버린다. 이어서 할 일이 있으면 최신 main에서 새 브랜치를 따고, 머지 뒤에 만든 커밋만 옮긴다.

```bash
# 최신 main에서 새 브랜치를 따고, 새로 만든 커밋만 가져온다
git switch -c feature/coupon-history main
git cherry-pick f402d62
git log --oneline
```

```text
3937a38 쿠폰 사용 내역 추가
c3098cc 쿠폰 적용 기능 (#12)
7174c6b 다른 PR이 먼저 머지됨
29a33c9 초기 커밋
```

squash 머지된 브랜치는 `-D`로 지워도 안전하다. 내용은 이미 main에 있다. GitHub 저장소 설정의 "Automatically delete head branches"를 켜 두면 원격 브랜치는 머지할 때 지워진다. PR 여러 개를 쌓아서 올리다가 아래 PR이 squash로 들어가는 경우는 더 복잡한데, 그건 [stacked PR 글](/posts/git-stacked-prs)에서 다룬다.

## 권한이 없는 저장소에는 fork로 기여한다

오픈소스 프로젝트에서 버그를 고치고 싶은데 그 저장소에 push 권한이 없다. 이때는 저장소를 내 계정으로 복사한 fork에 브랜치를 올리고, 원본 저장소로 PR을 연다. 원본을 `upstream`, 내 fork를 `origin`으로 두는 원격 구성과 동기화 명령은 [원격 저장소 글](/posts/git-remote-collaboration)에 실제 출력과 함께 있으니, 여기서는 같은 저장소 안의 PR과 무엇이 다른지에 집중한다.

```bash
# 원본을 fork하고 내 컴퓨터로 받는다 (upstream 원격도 함께 등록된다)
gh repo fork acme/shop --clone
cd shop

# 작업 브랜치에서 고치고 내 fork로 올린다
git switch -c fix/coupon-rounding
git push -u origin fix/coupon-rounding

# 원본 저장소의 main을 대상으로 PR을 연다
gh pr create --repo acme/shop --base main
```

- 비밀 값: fork에서 온 PR로 도는 GitHub Actions에는 원본 저장소의 Secrets가 전달되지 않고, `GITHUB_TOKEN`도 읽기 권한만 받는다. 누구나 PR을 열 수 있으니, 아무 코드나 실행해 배포 키를 빼 가지 못하게 막은 것이다. 그래서 fork PR에서는 배포 미리보기나 외부 서비스 호출 단계가 실패하거나 건너뛰어지는 게 정상이다.
- 워크플로 승인: 공개 저장소는 설정에 따라(기본값은 처음 기여하는 사람 중 일부에게 적용된다) 처음 기여하는 사람의 PR에서 워크플로를 바로 돌리지 않고 메인테이너의 승인을 기다린다. PR 화면에 "Approve and run" 버튼이 보이면 그 상태다. 내 PR의 CI가 시작되지 않는다고 다시 푸시할 필요는 없다.
- 메인테이너의 수정: PR을 열 때 "Allow edits by maintainers"가 켜져 있으면 원본 메인테이너가 내 fork 브랜치에 직접 커밋을 올릴 수 있다. 사소한 수정은 메인테이너가 바로 고치고 머지할 수 있어서 기여가 빨라진다. 그러니 내 fork 브랜치에서 강제 푸시하기 전에 원격에 새 커밋이 있는지 확인한다.
- 리뷰와 머지: 나는 원본 저장소에서 승인하거나 머지할 권한이 없다. 할 수 있는 건 PR을 고쳐 올리고 대화하는 일이다.

fork PR을 위해 비밀 값이 필요한 검사를 돌리려고 `pull_request_target` 이벤트를 쓰는 저장소가 있는데, 이건 원본 저장소 권한으로 돌아서 잘못 쓰면 fork의 코드가 비밀 값에 닿는다. 메인테이너 쪽의 이 함정은 [저장소 설정 글](/posts/github-repo-governance)에서 다룬다.

오픈소스에 처음 PR을 보낸다면 먼저 그 저장소의 `CONTRIBUTING.md`를 읽는다. 이슈를 먼저 열어 방향을 합의하라는 프로젝트, 커밋 서명(DCO의 `Signed-off-by`)을 요구하는 프로젝트, 커밋 메시지 형식을 정한 프로젝트가 많다. 큰 변경을 이슈 합의 없이 PR로 바로 보내면 오래 방치되거나 닫히기 쉽다.

## 현장에서 PR이 막히는 순간

머지 버튼이 회색이고 "Required statuses must pass"가 뜨는데 검사 하나가 영원히 "Expected — Waiting for status to be reported"라면, 필수 검사로 등록된 이름과 실제 워크플로 job 이름이 다르거나 그 워크플로가 이 PR의 변경 경로에서 돌지 않게 걸러진 것이다. 내 코드 문제가 아니라 저장소 설정 문제라 관리자에게 알린다.

승인을 받았는데 새 커밋을 올리자 승인이 사라졌다면 저장소가 "새 커밋이 올라오면 승인 무효"를 켜 둔 것이다. 리뷰어에게 다시 요청한다.

"This branch is out-of-date with the base branch"가 뜨면 main이 앞서 나간 것이다. Update branch 버튼은 기본으로 main을 내 브랜치에 merge한다. 저장소가 한 줄 히스토리를 요구하면 화살표에서 rebase로 바꾸거나 로컬에서 `git pull --rebase origin main` 후 `--force-with-lease`로 민다.

PR이 머지됐는데 이슈가 열려 있다면 기본 브랜치가 아닌 곳으로 머지했거나, 키워드를 PR 제목에만 쓰고 본문에 쓰지 않은 것이다. 닫는 키워드는 PR 본문이나 커밋 메시지에 있어야 한다.

## 이슈 #12가 닫히기까지

이슈 #12는 브랜치 하나와 draft PR로 시작했다. 리뷰어의 suggestion 두 개는 버튼으로, 나머지 코멘트는 커밋을 더해 반영했고, 리뷰가 끝날 때까지 히스토리를 다시 쓰지 않았다. 팀이 squash를 쓰기로 했으니 main에는 `쿠폰 적용 기능 (#12)` 커밋 하나가 남았고, 본문의 `Closes #12` 덕분에 이슈는 저절로 닫혔다. 끝난 브랜치는 버리고, 다음 일은 최신 main에서 새 브랜치로 시작한다. 이 흐름을 몸에 익히면 회사 저장소든 오픈소스든 PR을 올리는 방식은 거의 같다.

## 면접에서 나올 만한 질문

### PR(Pull Request)은 Git의 기능인가요?

아니다. GitHub, GitLab 같은 호스팅 서비스의 기능이다. Git이 제공하는 건 브랜치와 병합이고, PR은 "이 브랜치를 저 브랜치에 합쳐 달라"는 요청에 리뷰, 코멘트, CI 결과, 승인 규칙을 붙인 협업 장치다. GitLab에서는 같은 것을 Merge Request라고 부른다.

### merge commit, squash, rebase 머지는 각각 언제 쓰나요?

merge commit은 브랜치 커밋을 그대로 두고 머지 커밋을 남겨서 PR 단위로 되돌리기 쉽고 이력이 정확하지만 그래프가 복잡해진다. squash는 PR 하나를 커밋 하나로 만들어 main이 단순해지지만 PR 안의 커밋 단위가 사라진다. rebase는 머지 커밋 없이 한 줄로 쌓으면서 커밋 단위를 살리지만 해시가 모두 바뀐다. 커밋이 잘 나뉜 팀은 rebase나 merge commit을, 커밋이 지저분해도 main을 단순하게 두고 싶은 팀은 squash를 고른다.

### squash 머지 후 같은 브랜치에서 계속 작업하면 무슨 문제가 생기나요?

main의 squash 커밋은 내 커밋들과 내용만 같은 다른 커밋이라, Git은 내 커밋이 아직 main에 없다고 본다. 그래서 main을 합치면 내가 쓴 코드끼리 충돌하고, `git branch -d`도 "not fully merged"로 거절한다. squash로 머지된 브랜치는 버리고 최신 main에서 새 브랜치를 따서 머지 뒤에 만든 커밋만 cherry-pick한다.

### 리뷰 중에 rebase하고 강제 푸시하면 왜 안 좋나요?

리뷰어가 쓰는 "지난번 이후 바뀐 것만 보기"의 기준 커밋이 사라져 처음부터 다시 읽어야 하고, 줄 코멘트가 Outdated로 접힌다. 버튼으로 반영한 suggestion 커밋처럼 원격에만 있는 커밋을 지울 위험도 있다. 리뷰 중에는 커밋을 더하고, 정리는 승인 뒤나 squash 머지에 맡기며, 꼭 강제 푸시해야 하면 `--force-with-lease`를 쓴다.

### PR로 이슈를 자동으로 닫으려면 어떻게 하나요?

PR 본문이나 커밋 메시지에 `Closes #12`, `Fixes #12` 같은 닫는 키워드를 쓴다. 이 키워드는 PR이 저장소의 기본 브랜치로 머지될 때만 동작해서, develop 같은 다른 브랜치로 머지하면 이슈가 열린 채로 남는다. 닫지 않고 참조만 하려면 `Refs #12`처럼 쓴다.

### draft PR은 왜 쓰나요?

방향을 일찍 확인받거나 CI 결과를 먼저 보고 싶을 때 쓴다. draft는 머지할 수 없고 CODEOWNERS 리뷰어에게 리뷰 요청이 가지 않아서, 아직 덜 됐다는 신호를 분명히 준다. 준비가 끝나면 Ready for review로 바꿔 정식 리뷰를 받는다.

### fork에서 연 PR은 같은 저장소의 PR과 무엇이 다른가요?

fork PR로 도는 GitHub Actions에는 원본 저장소의 Secrets가 전달되지 않고 `GITHUB_TOKEN`도 읽기 전용이라, 비밀 값이 필요한 단계는 돌지 않는다. 공개 저장소는 처음 기여하는 사람의 워크플로 실행에 메인테이너 승인을 요구하기도 한다. 기여자는 원본에 승인·머지 권한이 없고, "Allow edits by maintainers"를 켜 두면 메인테이너가 기여자의 fork 브랜치에 직접 커밋할 수 있다.
