<EasyIntro>
  Instagram은 문을 연 첫날 2만 5천 명이 가입했다. 사진 정보를 담은 데이터베이스는 곧 가장 큰 서버의 메모리보다 커졌고, 엔지니어는 몇 명뿐이었다.

  Instagram은 데이터를 서버 여러 대로 나누면서 한 가지 꾀를 냈다. 처음부터 서버 수보다 훨씬 많은 상자 수천 개를 만들어 두고, 상자 여러 개를 서버 한 대에 담는 것이다. 서버가 모자라면 상자 몇 개를 새 서버로 옮기기만 하면 된다. 사용자가 어느 상자에 들어갈지는 사용자 번호를 상자 수로 나눈 나머지로 정해 두었으니 바뀌지 않는다.

  상자를 나누면 사진 번호도 문제가 된다. 상자마다 1번부터 세면 번호가 겹친다. 그래서 번호 안에 "언제 만들었는지, 몇 번 상자에서 만들었는지, 그 순간 몇 번째인지"를 칸으로 나눠 넣었다. 이 계산은 데이터베이스 안의 작은 함수가 한다.

  이 방법은 별도의 번호표 서버가 필요 없다는 장점이 있다. 대신 상자를 처음에 몇 개로 정할지, 번호 칸을 몇 자리로 할지를 처음에 잘 정해야 나중에 바꾸지 않아도 된다.
</EasyIntro>

이 글은 실제 서비스 사례 시리즈의 하나다. 분산 ID의 일반 원리는 [고유 ID 생성기 설계](/posts/sd-unique-id-generator)에서, 샤드 키와 리샤딩의 일반론은 [DB 샤딩](/posts/db-sharding)과 [샤딩 입문](/posts/sd-sharding-intro)에서 다뤘다. 여기서는 Instagram이 2012년에 직접 발표한 내용을 따라, PostgreSQL을 어떻게 나눴고 ID를 어떻게 만들었고 무엇을 감수했는지 본다.

자료는 Instagram 공동 창업자 Mike Krieger가 2012년 4월에 발표한 슬라이드 두 벌이다. 하나는 샌프란시스코 PostgreSQL 사용자 모임(SFPUG)에서 발표한 ["Sharding @ Instagram"](https://media.postgresql.org/sfpug/instagram_sfpug.pdf)으로, PostgreSQL 프로젝트 사이트에 올라가 있다. 다른 하나는 Airbnb 테크 토크에서 발표한 ["Scaling Instagram"](https://speakerdeck.com/mikeyk/scaling-instagram)이다(Speaker Deck 게시일 2012년 4월 12일). 같은 내용을 Instagram Engineering 블로그의 2012년 글 "Sharding & IDs at Instagram"이 더 자세히 설명한 것으로 알려져 있지만, 그 블로그가 있는 사이트가 자동 접근을 막아 열지 못했다. 그래서 이 글은 두 슬라이드에 적힌 것만 근거로 삼는다. 슬라이드는 발표 원고가 아니라서, 말로 덧붙였을 설명은 빠져 있다.

## 첫날 2만 5천 명, 서버는 LA의 한 대

슬라이드의 처음은 출발점이다. 제품을 만든 두 사람은 백엔드 경험이 거의 없었다. 초기 구성은 PostgreSQL, Redis, Memcached였는데 모두 LA 어딘가의 서버 한 대에 있었고, 그 서버는 "내 맥북 프로보다 약했다." 출시 첫날 2만 5천 명이 가입했고 부하가 치솟았다. 첫 주 금요일에도 줄지 않자 EC2로 옮겼다. PostgreSQL은 9.0으로 올렸다. 발표 시점에 사용자는 "2년이 안 돼 3천만 명 이상"이었고, 백엔드 엔지니어는 2010년 2명, 2011년 3명, 2012년 5명이었다.

왜 PostgreSQL이었나에 대한 답은 짧다. "처음에는 PostGIS." 위치 기능 때문이었다. 처음에는 Django ORM으로 모든 것을 했고(`./manage.py syncdb`), 슬라이드는 "ORM 덕분에 기본 키를 제대로 생각하지 않고 넘어가기 너무 쉬웠다"고 적었다. 이 문장이 나중의 ID 이야기로 이어진다.

출시 후에는 DB를 별도 서버로 옮겼고, 그때 가장 큰 테이블은 사진 메타데이터였다. 처음부터 스트리밍 복제로 마스터-슬레이브를 돌렸고, 백업은 복제본을 멈추고 `xfs_freeze`로 디스크를 얼린 뒤 EBS 스냅숏을 찍는 방식이었다. 초기에 부딪힌 문제로는 설정(`work_mem`, `shared_buffers`, vacuum `cost_delay`), Django가 남기는 `idle in transaction` 연결, 연결 풀링(PgBouncer)을 들었다. 지금 PostgreSQL을 처음 운영하는 팀이 만나는 문제와 거의 같다. 연결과 프로세스 모델은 [PostgreSQL 아키텍처](/posts/postgres-architecture)에서 다뤘다.

## 수직 분할로 한 번, 그다음은 나눌 수밖에

사진이 계속 늘었고, 당시 EC2에서 가장 큰 서버의 메모리는 68GB였다. 첫 대응은 수직 분할이었다. Django DB 라우터로 사진 앱의 모델만 다른 DB(`photodb`)로 보냈다. 슬라이드는 "외래 키 관계를 다 풀고 나면 쉽다"고 적었다. 쉽다는 말 앞에 조건이 붙어 있다. 읽기 경합을 줄일 곳에는 스트리밍 복제본을 읽기용으로 썼다.

몇 달 뒤 `photosdb`가 60GB를 넘었다. 슬라이드는 "클라우드 하드웨어라서 앞당겨졌지만, 어차피 언젠가 닿았을 한계"라고 했다. 남은 길은 수평 분할, 즉 샤딩이었다. 이 대목의 슬라이드 한 장이 솔직하다. "샤딩이 필요해지기 전에 경험 있는 사람을 뽑아 두겠지" 다음 장이 "확장에 관해서는 한 번도 맞은 적이 없다"다.

검토한 대안도 나온다. NoSQL 대안들, Skype의 샤딩 프록시, 범위·날짜 기반 분할을 봤고, "당시에는 어느 것도 주 데이터베이스를 맡을 수준이 아니었다"고 판단해 PostgreSQL 안에서 직접 하기로 했다. 요구는 세 가지였다. 운영과 코드의 복잡도가 낮을 것, 용량을 쉽게 늘릴 것, 애플리케이션 성능에 주는 영향이 작을 것.

Airbnb 발표에는 범위 기반 분할을 버린 이유가 하나 더 있다. MongoDB 같은 범위 방식은 샤드가 커지면 쪼갠다(A-H, I-Z를 A-D, E-H, I-P, Q-Z로). 그런데 쪼갤 때 데이터를 옮기는 디스크 IO가 크고, EC2에서는 특히 그렇다. 그래서 반대로 했다. 미리 잘게 쪼개 둔다.

## 논리 샤드 수천 개를 물리 서버 몇 대에

슬라이드의 표현으로는 "아주 아주 아주 많은(수천 개의) 논리 샤드를, 그보다 적은 물리 샤드에 대응시킨다." 슬라이드의 예는 논리 샤드 8개, 서버 2대다.

```text
// 8 logical shards on 2 machines
user_id % 8 = logical shard
logical shards -> physical shard map
{
        0: A, 1: A,
        2: A, 3: A,
        4: B, 5: B,
        6: B, 7: B
}
```

서버를 4대로 늘리면 지도만 바뀐다. `user_id % 8`은 그대로다.

```text
// 8 logical shards on 2 4 machines
{
        0: A, 1: A,
        2: C, 3: C,
        4: B, 5: B,
        6: D, 7: D
}
```

이것이 [샤딩 입문](/posts/sd-sharding-intro)에서 본 논리 샤드다. 키를 샤드로 바꾸는 함수(나머지 연산)는 처음에 정한 논리 샤드 수로 고정하고, 서버가 늘면 논리 샤드를 통째로 옮긴다. 키가 어느 논리 샤드에 있는지는 절대 바뀌지 않으니 행 단위로 데이터를 다시 나눌 일이 없다. 대가는 처음에 정한 논리 샤드 수가 사실상 서버 수의 상한이 된다는 점이다. 슬라이드도 "논리 샤드가 물리 샤드보다 많은 동안은 이렇게 할 수 있다"고 조건을 달았다.

논리 샤드를 무엇으로 구현했는지가 이 사례의 PostgreSQL다운 부분이다. 논리 샤드 하나가 PostgreSQL 스키마(schema) 하나다. 슬라이드는 "2년 동안 대충 넘겨 온 그 `public`"을 짚으며 계층을 적었다. 데이터베이스 안에 스키마, 스키마 안에 테이블, 테이블 안에 열. 서버마다 스키마 수천 개를 fabric 같은 병렬 작업 도구로 만들었고, 스키마마다 같은 테이블(`photos_by_user` 등)이 있다.

```text
machineA:            machineB:
  shard0               shard4
    photos_by_user       photos_by_user
  shard1               shard5
    photos_by_user       photos_by_user
  ...                  ...
```

애플리케이션 쪽은 단순하다. `SHARD_TO_DB`라는 사전이 논리 샤드 번호를 DB 번호로 바꾼다. Django ORM 대신 `select(fields, table_name, shard_key, where_statement, where_parameters)` 같은 아주 단순한 DB 추상화 층을 직접 썼고, 그 안에서 `shard_key % num_logical_shards = shard_id`로 샤드를 고른다. 샤드 키는 "대부분의 경우 user_id"다. 샤딩된 DB를 만들고 지우는 Django 테스트 러너도 따로 만들었다.

여러 샤드에 걸친 조회도 다뤘다. 대부분의 질의는 서버 한두 대에 있는 샤드 몇 개만 본다. 같은 DB 서버 안의 여러 스키마에 걸치면 `UNION ALL`로 합친다. 클라이언트가 `((shard_key, id), (shard_key, id), ...)`처럼 넘기면 라이브러리가 샤드별·서버별 하위 질의로 나누고, 적어도 서버 안에서는 병렬로 실행한다. 슬라이드에는 그 `UNION ALL`의 실행 계획 일부가 있다. `Append` 아래에 스키마마다 `Limit` → `Index Scan`이 붙고, 느린 쪽은 160ms, 빠른 쪽은 0.018ms가 걸렸다. 한 서버 안의 scatter-gather인 셈이고, 서버를 넘는 병렬화는 "언젠가 하면 좋겠다"로 남겨 두었다.

## 사진 번호를 DB 안에서 만든다

샤드를 나누자 다음 과제가 왔다. 슬라이드의 제목은 "next challenge: unique IDs"다. 요구는 세 가지였다.

1. 조회 없이 시간 순으로 정렬할 수 있을 것
2. 64비트일 것
3. 운영 복잡도가 낮을 것

검토한 선택지는 티켓 서버, UUID, Twitter Snowflake, MongoDB 같은 애플리케이션 수준 ID였다. 각각 왜 버렸는지는 슬라이드에 없다. 요구와 맞대 보면, UUID는 128비트이고 정렬되지 않으며(2012년에는 시간 순서가 있는 UUIDv7이 없었다), 티켓 서버와 Snowflake는 별도 서버를 운영해야 한다. 이 셋의 일반적인 장단점은 [고유 ID 생성기 설계](/posts/sd-unique-id-generator)에 있고, Snowflake 원본은 [Twitter 사례](/posts/rw-twitter-snowflake-timeline)에서 읽었다. 슬라이드가 고른 답은 한 줄이다. "데이터베이스는 이미 시퀀스 증가를 꽤 잘한다."

비트 구성은 이렇다.

```text
[ 41 bits of time in millis ]
[ 13 bits for shard ID ]
[ 10 bits sequence ID ]
```

그리고 그 ID를 만드는 PL/pgSQL 함수가 슬라이드에 그대로 있다. 논리 샤드(스키마) `insta5`의 함수다. PostgreSQL 16.15(Ubuntu 24.04)에 그대로 옮겨, 테이블의 기본값으로 걸고 행 세 개를 넣어 봤다.

```sql
-- 논리 샤드 하나 = 스키마 하나. 슬라이드의 insta5를 만든다
CREATE SCHEMA insta5;
CREATE SEQUENCE insta5.table_id_seq;

-- 슬라이드의 함수를 그대로 옮겼다
CREATE OR REPLACE FUNCTION insta5.next_id(OUT result bigint) AS $$
DECLARE
    our_epoch bigint := 1314220021721;   -- 기준 시점(밀리초)
    seq_id bigint;
    now_millis bigint;
    shard_id int := 5;                    -- 이 스키마의 논리 샤드 번호
BEGIN
    SELECT nextval('insta5.table_id_seq') % 1024 INTO seq_id;      -- 시퀀스의 아래 10비트
    SELECT FLOOR(EXTRACT(EPOCH FROM clock_timestamp()) * 1000) INTO now_millis;
    result := (now_millis - our_epoch) << 23;   -- 시각을 23비트(13 + 10) 위로
    result := result | (shard_id << 10);        -- 샤드 번호를 10비트 위로
    result := result | (seq_id);                -- 맨 아래 10비트는 순번
END;
$$ LANGUAGE PLPGSQL;

-- ID를 기본값으로 쓰는 테이블. 애플리케이션은 ID를 몰라도 된다
CREATE TABLE insta5.photos_by_user (
  id bigint NOT NULL DEFAULT insta5.next_id() PRIMARY KEY,
  user_id bigint NOT NULL,
  caption text
);
INSERT INTO insta5.photos_by_user (user_id, caption)
VALUES (8197, 'first'), (8197, 'second'), (16389, 'third');

-- 만든 ID를 칸별로 다시 나눈다
SELECT id,
       id >> 23                AS ms_since_epoch,
       to_timestamp(((id >> 23) + 1314220021721) / 1000.0) AT TIME ZONE 'UTC' AS created_utc,
       (id >> 10) & 8191       AS shard_id,   -- 13비트 마스크
       id & 1023               AS seq_id      -- 10비트 마스크
FROM insta5.photos_by_user ORDER BY id;
```

```text
         id          | ms_since_epoch |       created_utc       | shard_id | seq_id 
---------------------+----------------+-------------------------+----------+--------
 4015545164431889409 |   478690286211 | 2026-10-25 06:38:27.932 |        5 |      1
 4015545164440278018 |   478690286212 | 2026-10-25 06:38:27.933 |        5 |      2
 4015545164440278019 |   478690286212 | 2026-10-25 06:38:27.933 |        5 |      3
(3 rows)
```

볼 열은 `shard_id`와 `seq_id`다. 세 ID 모두 샤드 5에서 나왔고, 순번은 시퀀스 값 1, 2, 3이다. 두 번째와 세 번째는 같은 밀리초(…933)에 만들어져 시각 칸이 같고 순번만 다르다. 시각은 이 글을 쓰는 순간의 시계다. 사용자 8197과 16389는 둘 다 `% 8192`가 5라서 같은 샤드에 들어간다는 설정으로 넣었다(13비트 샤드 칸이면 논리 샤드를 최대 8,192개 둘 수 있다).

첫 ID를 비트 칸으로 나눠 보자. 조각을 누르면 칸마다 무엇이 들었는지 나온다.

41비트 칸의 수명도 계산해 둔다. 기준 시점 1314220021721에 2^41ms를 더하면 2081-04-30T12:54:37.273Z다. 다만 ID가 부호 있는 `bigint`에 들어가니, 앞의 설명처럼 시각 칸의 맨 위 비트가 1이 되는 순간(기준 시점에서 2^40ms, 약 34.8년 뒤인 2046년 6월) 음수 ID가 나온다. 슬라이드는 이 부분을 다루지 않는다. 부호 비트를 비워 두는 [Snowflake 구성](/posts/rw-twitter-snowflake-timeline)과 갈리는 지점이다.

아래 플레이그라운드에서 이 구성으로 ID를 칸별로 풀어 볼 수 있다. 기대값은 같은 함수를 node로 돌려 얻었고, 세 번째 테스트는 위 PostgreSQL 출력의 첫 행이다.

## 슬라이드의 두 줄 디코드 식

슬라이드에는 ID에서 값을 꺼내는 식도 두 줄 있다.

```text
# pulling shard ID from ID:
shard_id = id ^ ((id >> 23) << 23)
timestamp = EPOCH + id >> 23
```

이걸 글자 그대로 계산하면 기대와 다른 값이 나온다. 위의 첫 ID로 node에서 돌렸다.

```js
// slide.mjs: 슬라이드의 식을 글자 그대로 옮겼다
const EPOCH = 1314220021721n;
const id = 4015545164431889409n;
const slideShard = id ^ ((id >> 23n) << 23n);
const slideTs = EPOCH + id >> 23n;            // 자바스크립트도 파이썬도 + 가 >> 보다 먼저다
console.log("slide shard_id =", slideShard.toString(), " slide timestamp =", slideTs.toString());
console.log("lower23 >> 10 =", slideShard >> 10n, " lower23 & 1023 =", slideShard & 1023n);
```

```text
slide shard_id = 5121  slide timestamp = 478690442878
lower23 >> 10 = 5n  lower23 & 1023 = 1n
```

첫 식은 아래 23비트, 즉 샤드와 순번을 합친 값(5 × 1024 + 1 = 5121)을 낸다. 샤드만 얻으려면 10비트를 더 밀어야 한다. 둘째 식은 연산자 우선순위 때문에 `(EPOCH + id) >> 23`으로 계산된다. 의도는 `EPOCH + (id >> 23)`이었을 것이다. 발표 슬라이드의 줄임 표기로 보이지만, 비트 칸 ID를 다루는 코드를 옮겨 적을 때 흔히 나는 실수 두 가지(마스크 빠뜨리기, 우선순위)가 한 장에 다 있다. 디코드 함수는 위 플레이그라운드처럼 칸마다 시프트와 마스크를 명시하고, 알려진 ID로 테스트를 걸어 둔다.

## 이 방식이 얻은 것과 감수한 것

슬라이드는 장단점을 한 줄씩 적었다. 장점은 "64비트 안에서 고유성이 보장되고 CPU 부담이 크지 않다", 단점은 "처음부터 ID가 크다." 그리고 "이 방식으로 수억 개의 ID를 만들었고 문제가 없었다"고 했다. 정수 자동 증가를 쓰다 바꾸면 ID 자릿수가 갑자기 19자리로 늘어나는데, 그 정도는 감수할 만하다는 판단이다.

슬라이드가 말하지 않는 약점도 구조에서 보인다. 아래는 내 해석이다.

첫째, 순번이 넘치면 기다리지 않는다. Snowflake는 같은 밀리초에 4,096개를 다 쓰면 다음 밀리초까지 기다린다. 이 함수는 `nextval % 1024`라서, 한 논리 샤드가 같은 밀리초에 1,025번째 ID를 만들면 순번이 한 바퀴 돌아 첫 번째와 같은 값이 될 수 있다. 시퀀스 값이 1,024 차이 나는 두 호출이 같은 밀리초에 떨어지는 경우다. 논리 샤드가 사용자 단위로 잘게 나뉘어 있으니 한 샤드에 그만큼 몰릴 일은 드물었을 것이고, 기본 키 제약이 중복을 거절해 조용히 덮어쓰지는 않는다. 그래도 "보장"의 범위는 샤드당 밀리초당 1,024개까지다.

둘째, 시계는 DB 서버의 것이다. `clock_timestamp()`를 쓰니 서버마다 시계가 다르면 ID의 시간 순서도 그만큼 어긋난다. 같은 서버 안에서도 시계가 뒤로 가면 시각 칸이 작아진다. 순번 칸이 있어 바로 겹치지는 않지만 시간 순서가 뒤집힌다. 슬라이드의 첫 요구가 "조회 없이 시간 순 정렬"이었으니, 이것은 서로 다른 샤드에서 만든 ID 사이의 "대략적인" 순서로 읽어야 한다. [시계 차이](/posts/clock-skew)의 일반론이 그대로 적용된다.

셋째, 장점이 큰 쪽도 있다. ID에 논리 샤드 번호가 들어 있으니 사진 ID만 받아도 어느 샤드를 볼지 안다. 별도의 ID → 샤드 조회 테이블이 필요 없다. 그리고 ID를 만드는 데 네트워크 호출이 없다. 행을 넣는 바로 그 DB가 기본값으로 만든다. 같은 아이디어(ID 안에 샤드 번호)를 다른 비트 배치로 쓴 [Pinterest 사례](/posts/rw-pinterest-mysql-sharding)와 나란히 보면 좋다.

## 리샤딩은 복제본을 세우고 지도를 바꾼다

물리 서버를 늘리는 방법도 슬라이드에 있다. 먼저 쓴 수단은 `pg_reorg`였다. 테이블을 인덱스 순서로 다시 써서 짧은 잠금으로 테이블 이름만 바꾸는 도구로, 일부 DB에서 20GB 넘게 공간을 아꼈다고 했다. 특히 EC2에서 쓸모 있었다고 한다.

마지막 단계가 스키마를 논리 샤드로 고른 이유 중 하나다. 슬라이드는 "스키마의 아름다움은 물리적으로 다른 파일이라는 것"이라며 "지울 때 IO 부담이 없고 '스위스 치즈'가 없다"고 적었다. 한 테이블에서 절반의 행을 `DELETE`로 지우면 테이블 파일에 죽은 행이 남아 VACUUM이 치워야 하지만([PostgreSQL MVCC와 VACUUM](/posts/postgres-mvcc-vacuum)), 스키마를 통째로 지우면 그 파일들이 사라진다.

한계도 함께 적혀 있다. 매핑을 바꿀 때 약 30초의 점검이 필요하다(일부 DB에 "읽기 전용" 모드를 두면 풀 수 있다고 했다). 여러 샤드에 걸친 범위 스캔에는 맞지 않는다. 사용자 ID로 나눴으니 "전체 사진을 시간순으로" 같은 질의는 모든 샤드를 봐야 한다.

## 피드와 팔로우 그래프는 어디에 두었나

같은 슬라이드에 PostgreSQL 밖의 이야기도 있다. 출시 때 메인 피드는 Redis였다. 사용자가 사진을 올리면 팔로워 목록을 꺼내 팔로워마다 `LPUSH feed:<user_id> <media_id>`로 넣고, 피드를 읽을 때 `LRANGE feed:4 0 20`으로 ID만 꺼낸 뒤 Memcached에서 내용을 채운다. 정리하면 "정본 데이터는 PG, 피드·목록·집합은 Redis, 객체 캐시는 memcache"였다. 사진을 올리는 흐름은 사용자의 미디어 DB에 동기로 쓰고, 위치 태그가 있으면 비동기 작업이 Solr에 넣고, 팔로워 배달은 큐로 넘긴다. Airbnb 발표는 Redis가 특히 쓸모 있는 순간으로 "Taylor Swift가 CMA 시상식에서 생중계로 올릴 때"를 꼽았다. 같은 해 Twitter가 QCon에서 설명한 쓰기 시점 팬아웃([Twitter 사례](/posts/rw-twitter-snowflake-timeline))과 같은 구조다. 일반론은 [뉴스 피드 ①](/posts/sd-news-feed-publishing)에 있다.

팔로우 그래프는 실패담이다. 처음에는 `(source_id, target_id, status)` 테이블 하나였다. DB가 바빠서 Redis에 같은 데이터를 병렬로 두기 시작했고, 슬라이드는 그 결과를 "불일치, 추가 로직, 정말 많은 추가 로직, 지원팀에게 캐시 무효화라는 개념을 알려 줘야 하는 상황"이라고 적었다. 재설계에서는 "PG는 초당 수만 요청을 처리할 수 있으니, 아주 가벼운 memcached 캐시만" 두는 쪽으로 돌아갔다. Airbnb 발표의 교훈은 두 줄이다. 핵심 저장소를 보완하는 다용도 도구(Redis 같은)를 하나 두고, 같은 일을 하는 도구 둘을 두지 말 것. 이중 저장의 일반적인 문제는 [캐시 무효화](/posts/cache-invalidation)에 있다.

## 2012년 슬라이드가 말하지 않는 것

두 슬라이드 모두 회사가 고른 성공담이고, 발표 원고가 아니라 장표다. 논리 샤드를 실제로 몇 개 만들었는지("수천 개" 외의 숫자), 샤드 수를 어떻게 정했는지, 리샤딩을 몇 번 했는지, 그 30초 점검이 사용자에게 어떻게 보였는지는 나오지 않는다. 순번 넘침이나 시계 문제를 겪었는지도 말하지 않는다. "수억 개의 ID를 만들었고 문제가 없었다"는 문장이 전부다. 그 뒤의 변화도 이 두 자료로는 알 수 없다. 단서 하나는 2018년 USENIX LISA의 Instagram 발표 [초록](https://www.usenix.org/conference/lisa18/presentation/xiao)이다. 초록은 Facebook이 미국과 유럽에 데이터 센터를 두고 있지만 Instagram 인프라는 아직 미국에만 있다고 했고, Instagram이 많이 쓰는 DB 중 하나로 Cassandra를 들며 대서양을 건너는 쿼럼 요청이 느려 데이터셋을 미국과 유럽 파티션으로 나눴다고 적었다. 2012년의 "PostgreSQL이 중심"에서 저장소가 늘었다는 뜻이다. 하지만 PostgreSQL 샤딩과 이 ID 방식이 지금도 그대로인지는 이번에 찾은 1차 자료로 확인하지 못했다.

## 논리 샤드와 DB 안의 ID를 내 서비스에

이 설계가 맞는 조건은 슬라이드의 세 요구 그대로다. 엔지니어가 몇 명뿐이라 운영할 부품을 늘릴 수 없고, PostgreSQL을 이미 쓰고 있고, 대부분의 질의가 사용자 하나를 중심으로 돈다(사용자의 사진, 사용자의 피드). 이때 "스키마 = 논리 샤드, 나머지 연산 + 지도로 라우팅, ID는 DB 함수로"는 새 서버 종류 없이 샤딩을 가능하게 한다. 반대로 질의가 사용자를 가로지르거나(전체 검색, 랭킹), 샤드를 넘는 트랜잭션이 많다면 사용자 ID 샤딩이 맞지 않는다. 지금이라면 Citus 같은 PostgreSQL 확장이나 관리형 분산 SQL이 이 라우팅을 대신해 주는 선택지도 있다. 같은 PostgreSQL 샤딩을 다른 시대에 한 [Notion 사례](/posts/rw-notion-postgres-sharding)와 비교해 보면 좋다.

처음부터 따라 하면 드는 비용도 슬라이드에 보인다. ORM을 버리고 직접 만든 DB 추상화 층으로 갈아타야 했고, 외래 키 관계를 풀어야 했고, 샤딩된 DB용 테스트 러너를 만들어야 했다. 서버마다 스키마 수천 개를 만들고 관리하는 도구도 필요하다. PostgreSQL 카탈로그는 스키마·테이블 수만큼 커지고, 스키마 변경(열 추가)을 수천 번 반복해야 한다. 데이터가 서버 한 대와 복제본으로 버틴다면 이 비용을 낼 이유가 없다. Instagram도 수직 분할과 읽기 복제본을 먼저 썼다.

작은 팀이 지금 바로 가져올 만한 것은 둘이다. 하나는 외부에 보이는 ID를 처음부터 "나중에 샤드를 알 수 있는" 모양으로 두는 것이다. 지금 샤딩할 생각이 없어도, 시간 순서가 있는 64비트 ID나 UUIDv7을 쓰면 나중에 자동 증가 키를 걷어 내는 일을 피한다. 슬라이드의 "ORM 덕분에 기본 키를 생각하지 않고 넘어가기 쉬웠다"가 그 경고다. 다른 하나는 샤딩을 하게 되면 서버 수보다 훨씬 많은 논리 샤드로 시작하는 것이다. 키를 샤드로 바꾸는 함수는 한 번 정하면 바꾸기 가장 어려운 부분이고, 지도는 쉽게 바꿀 수 있다.

비슷한 신호가 보이면 먼저 볼 것도 정해 둔다. 가장 큰 테이블이 서버 메모리를 넘기 시작하면 샤딩보다 먼저 그 테이블만 다른 DB로 떼어 낼 수 있는지(수직 분할), 읽기를 복제본으로 돌릴 수 있는지 본다. DB 안에서 ID를 만든다면 서버 시계를 NTP로 맞추고 시계 역행을 감시한다. 한 샤드에서 밀리초당 생성량이 순번 칸(여기서는 1,024)에 가까워지는지도 지표로 둔다. 캐시 저장소에 정본과 같은 데이터를 병렬로 쓰기 시작했다면 Instagram의 팔로우 그래프처럼 "추가 로직"이 늘기 전에 멈추고, 정본 DB에 가벼운 캐시만 얹는 쪽을 먼저 검토한다.

## 면접에서 나올 만한 질문

### Instagram은 PostgreSQL을 어떻게 샤딩했나요?

논리 샤드 수천 개를 PostgreSQL 스키마로 만들고, 그보다 적은 물리 서버에 나눠 담았다. 애플리케이션이 `user_id % 논리 샤드 수`로 논리 샤드를 고르고, `SHARD_TO_DB` 지도로 서버를 찾는다. 서버를 늘릴 때는 나머지 연산을 바꾸지 않고 지도만 바꿔 논리 샤드를 통째로 옮긴다. 2012년 슬라이드 기준이다.

### 왜 논리 샤드를 물리 서버보다 훨씬 많이 만들었나요?

샤드를 쪼갤 때 행 단위로 데이터를 다시 나누지 않기 위해서다. 범위 방식은 커진 샤드를 쪼개며 데이터를 옮기는 IO가 크고, EC2에서 특히 그랬다고 Airbnb 발표가 적었다. 미리 잘게 쪼개 두면 키의 논리 샤드는 영원히 같고, 논리 샤드 단위로 서버만 옮기면 된다. 대가로 처음 정한 논리 샤드 수가 서버 수의 상한이 된다.

### Instagram의 ID 비트 구성은 무엇이고, Snowflake와 무엇이 다른가요?

41비트 밀리초 시각, 13비트 논리 샤드 번호, 10비트 순번이다. 별도 ID 서버 없이 각 샤드 스키마의 PL/pgSQL 함수가 시퀀스의 `nextval % 1024`와 `clock_timestamp()`로 만들어 테이블 기본값으로 쓴다. Snowflake는 기계 번호 10비트와 순번 12비트를 쓰고 부호 비트를 비우며, 순번이 넘치면 다음 밀리초까지 기다린다. Instagram 방식은 ID에 샤드 번호가 들어 있어 ID만 보고 샤드를 찾는다.

### 왜 UUID나 Snowflake 대신 DB 함수로 ID를 만들었나요?

요구가 시간 순 정렬, 64비트, 낮은 운영 복잡도였기 때문이다. UUID는 128비트이고 당시에는 시간 순서가 없었으며, 티켓 서버나 Snowflake는 새 서버를 운영해야 한다. 슬라이드의 답은 "DB는 이미 시퀀스 증가를 잘한다"였다. 대가로 ID가 처음부터 19자리로 크고, 시각은 DB 서버의 시계를 믿는다.

### 이 ID 방식에서 같은 ID가 나올 수 있나요?

구조상 드물게 가능하다. 순번이 `nextval % 1024`라서 한 논리 샤드가 같은 밀리초에 1,024개를 넘게 만들면 순번이 한 바퀴 돌아 같은 값이 될 수 있고, 시계가 뒤로 가도 시각 칸이 겹칠 수 있다. 슬라이드는 이 경우를 다루지 않았고 수억 개를 문제없이 만들었다고만 적었다. 기본 키 제약이 중복을 거절하니 조용히 덮어쓰지는 않지만, 샤드당 생성 속도와 시계를 감시해야 한다.

### 논리 샤드를 스키마로 구현하면 무엇이 좋나요?

옮기고 지우기가 깔끔하다. 서버를 복제본으로 통째로 세운 뒤 지도를 바꾸고, 각 서버에서 맡지 않는 스키마를 `DROP SCHEMA`로 지우면 된다. 스키마는 물리적으로 다른 파일이라 지울 때 IO 부담이 없고, 행을 `DELETE`할 때처럼 테이블에 죽은 행이 남지 않는다. 대신 매핑을 바꿀 때 약 30초의 점검이 필요했고, 샤드를 넘는 범위 스캔에는 맞지 않았다.

### 우리 서비스가 2012년 Instagram의 10분의 1 규모라면 같은 샤딩을 하나요?

대개 아직 하지 않는다. Instagram도 수직 분할과 읽기 복제본을 먼저 썼고, 사진 DB가 서버 메모리를 넘은 뒤에 샤딩했다. 슬라이드의 마무리도 "필요할 때까지 샤딩하지 말라, 다만 얼마나 어려운지 과대평가하지도 말라"다. 지금 가져올 것은 시간 순서가 있는 64비트 ID나 UUIDv7을 처음부터 쓰는 습관, 그리고 샤딩하게 되면 논리 샤드를 넉넉히 만드는 원칙이다.

### Instagram이 팔로우 그래프를 Redis에 병렬로 두었다가 되돌린 이유는요?

같은 데이터를 두 저장소가 따로 들고 있으니 불일치와 그걸 맞추는 로직이 계속 늘었기 때문이다. 슬라이드는 결과를 "불일치, 추가 로직, 정말 많은 추가 로직, 지원팀에게 캐시 무효화를 알려 줘야 하는 상황"이라고 적었다. 재설계에서는 PostgreSQL이 초당 수만 요청을 감당한다고 보고 아주 가벼운 memcached 캐시만 얹었다. 교훈은 같은 일을 하는 도구 둘을 두지 말라는 것이다.
