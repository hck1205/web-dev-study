[Design Twitter](https://leetcode.com/problems/design-twitter/)는 LeetCode 355번이고 난이도는 Medium이다. 트윗 쓰기, 팔로우, 언팔로우, 그리고 "내 피드의 최신 트윗 10개"를 돌려주는 작은 트위터를 만든다. 자료구조 설계 문제처럼 보이지만, 피드를 만드는 부분은 결국 "시간순으로 정렬된 목록 여러 개를 합쳐 앞의 10개만 꺼내기"다. 그래서 힙 패턴에 들어 있다.

이 문제는 면접에서 시스템 설계로 이어지기 쉽다. "유명인이 팔로워 1억 명이면?" 같은 질문이다. 이 글은 전체 트윗을 한 줄에 쌓고 거르기, 사람별로 모아 정렬하기, 사람마다 최근 10개만 두기, 힙으로 합치기, 쓸 때 팔로워 피드에 미리 넣기까지 다섯 설계를 코드로 비교하고, 각각이 어느 입력에서 이기는지 직접 재 본다. 정렬된 목록 여러 개를 힙으로 합치는 기본 그림은 [힙 글](/posts/ds-heap#k개의-줄을-하나로-합치기)과 [Merge k Sorted Lists](/posts/leetcode-merge-k-sorted-lists)에 있다. 코드는 Node.js 22, Python 3.13, Java 21에서 돌렸다.

## 트윗 쓰기, 팔로우, 최신 10개 보기

`Twitter` 클래스에 메서드 네 개를 만든다.

- `postTweet(userId, tweetId)`: 사용자가 트윗을 하나 쓴다. 트윗 id는 모두 다르다.
- `getNewsFeed(userId)`: 그 사용자와, 그 사용자가 팔로우하는 사람들이 쓴 트윗 중 가장 최근 것부터 최대 10개의 id를 돌려준다.
- `follow(followerId, followeeId)`: 팔로우한다.
- `unfollow(followerId, followeeId)`: 팔로우를 끊는다.

풀이를 고를 때 볼 제약은 이렇다.

- 사용자 id는 1 이상 500 이하다. 한 사람이 팔로우하는 사람도 많아야 499명이다.
- 트윗 id는 0 이상 10^4 이하이고, 쓴 순서와 아무 관계가 없다. 나중에 쓴 트윗의 id가 더 작을 수 있다.
- 네 메서드를 합쳐 최대 3 × 10^4번 부른다.

두 번째 줄이 가장 많이 틀리는 곳이다. "최근"은 쓴 순서이지 id의 크기가 아니다. 그래서 트윗마다 시각을 따로 붙여야 한다. 실제 시계를 쓸 필요는 없고, 트윗을 쓸 때마다 1씩 늘어나는 정수 하나면 충분하다. 같은 밀리초에 두 트윗이 들어와도 순서가 갈린다.

## 타임라인 하나를 손으로 만들어 본다

이 글 내내 쓰는 예시다. 사용자 1부터 4까지 열 개의 트윗을 이 순서로 쓴다. `t0`부터 `t9`가 붙인 시각이다.

```text
시각  쓴 사람  트윗 id
t0    1        7
t1    2        15
t2    3        9
t3    4        50
t4    2        3
t5    1        42
t6    3        31
t7    2        28
t8    4        1
t9    3        12
```

그다음 사용자 1이 2와 3을 팔로우하고 피드를 연다. 피드에 들어갈 사람은 1, 2, 3이고 4는 빠진다. 시각이 큰 것부터 4의 트윗(t8, t3)을 건너뛰며 읽으면 이렇다.

```text
t9 12, t7 28, t6 31, t5 42, t4 3, t2 9, t1 15, t0 7
```

답은 `[12, 28, 31, 42, 3, 9, 15, 7]`이다. id만 보면 순서가 엉망이라는 게 보인다. id로 정렬했다면 42가 맨 앞에 왔을 것이다.

이어서 1이 3을 언팔로우하고 다시 피드를 열면 3의 트윗이 빠져 `[28, 42, 3, 15, 7]`이 된다. 손으로 하면서 한 일은 두 가지였다. 피드에 들어갈 사람을 정하기, 그리고 그 사람들의 트윗을 시각순으로 합쳐 앞에서 10개 자르기. 다섯 설계는 이 두 일을 언제, 얼마나 미리 해 두느냐가 다르다.

## 모든 트윗을 한 줄에 쌓고 뒤에서 거른다

가장 단순한 설계다. 트윗을 쓴 순서대로 배열 하나에 쌓는다. 배열의 순서가 곧 시각이라 시각을 따로 붙일 필요도 없다. 피드는 배열 끝에서부터 거꾸로 읽으며, 쓴 사람이 나이거나 내가 팔로우하는 사람이면 담고, 10개가 차면 멈춘다.

```js
class Twitter {
  constructor() {
    this.all = [];                 // [쓴 사람, 트윗 id]를 쓴 순서대로
    this.follows = new Map();      // 사용자 -> 팔로우하는 사람 Set
  }
  fol(u) {
    if (!this.follows.has(u)) this.follows.set(u, new Set());
    return this.follows.get(u);
  }
  postTweet(u, id) { this.all.push([u, id]); }
  getNewsFeed(u) {
    const fs = this.fol(u), out = [];
    for (let i = this.all.length - 1; i >= 0 && out.length < 10; i--) {
      const [a, id] = this.all[i];
      if (a === u || fs.has(a)) out.push(id); // 나와 팔로우한 사람만 담는다
    }
    return out;
  }
  follow(a, b) { if (a !== b) this.fol(a).add(b); }
  unfollow(a, b) { this.fol(a).delete(b); }
}
```

쓰기, 팔로우, 언팔로우는 모두 O(1)이다. 피드는 최악에 전체 트윗 수 T만큼 읽어서 O(T)다.

이 설계의 성적은 입력에 따라 극단적으로 갈린다. 모두가 모두를 팔로우하면 배열 끝의 10개가 바로 답이라 거의 공짜다. 실제로 500명이 서로 다 팔로우하고 트윗 2만 개를 쓴 뒤 피드를 1만 번 열었더니 31ms로 다섯 설계 중 가장 빨랐다. 반대로 사용자 1이 맨 처음에 한 번만 쓰고 조용해진 사용자 2만 팔로우하면, 피드를 열 때마다 다른 사람들의 트윗 2만 개를 끝까지 훑는다. 같은 1만 번이 2.2초였다. 피드 비용이 "내가 팔로우하지 않는 사람들의 활동량"에 끌려다닌다는 게 문제다.

## 사람별로 나눠 담고 모아서 정렬한다

그래서 트윗을 쓴 사람별 목록에 나눠 담는다. 이제는 배열 순서만으로는 사람 사이의 선후를 알 수 없으니, 트윗마다 시각 `time`을 붙인다. 피드는 나와 팔로우한 사람들의 목록을 모두 모아 시각의 역순으로 정렬하고 앞의 10개를 자른다.

```js
class Twitter {
  constructor() {
    this.time = 0;                 // 트윗마다 1씩 늘리는 시각
    this.tweets = new Map();       // 사용자 -> [[시각, 트윗 id], ...] 오래된 순
    this.follows = new Map();
  }
  fol(u) {
    if (!this.follows.has(u)) this.follows.set(u, new Set());
    return this.follows.get(u);
  }
  postTweet(u, id) {
    if (!this.tweets.has(u)) this.tweets.set(u, []);
    this.tweets.get(u).push([this.time++, id]);
  }
  getNewsFeed(u) {
    const c = [];
    for (const v of [u, ...this.fol(u)])
      for (const t of this.tweets.get(v) || []) c.push(t);   // 관련된 트윗을 전부 모은다
    c.sort((x, y) => y[0] - x[0]);                            // 시각이 큰 것부터
    return c.slice(0, 10).map((t) => t[1]);
  }
  follow(a, b) { if (a !== b) this.fol(a).add(b); }
  unfollow(a, b) { this.fol(a).delete(b); }
}
```

이제 피드는 팔로우하지 않는 사람의 활동과 무관하다. 앞의 "조용한 사람만 팔로우" 입력이 8.7ms로 줄었다. 대신 팔로우한 사람들의 트윗을 몽땅 모아 정렬해서, 관련 트윗이 N개면 O(N log N)이다. 모두가 모두를 팔로우하는 입력에서는 피드를 열 때마다 2만 개를 정렬해서 27초가 걸렸다. 필요한 건 10개뿐인데 전부 정렬하는 게 낭비다.

## 사람마다 최근 10개만 들고 있는다

피드가 10개만 보여 준다면, 한 사람의 트윗 중 피드에 나올 수 있는 것도 그 사람의 최근 10개뿐이다. 11번째로 오래된 트윗은 그 사람 혼자서도 10개에 밀리니 다른 사람과 섞이면 더 밀린다. 그래서 사람별 목록을 길이 10으로 자른다.

```js
postTweet(u, id) {
  if (!this.tweets.has(u)) this.tweets.set(u, []);
  const l = this.tweets.get(u);
  l.push([this.time++, id]);
  if (l.length > 10) l.shift();    // 가장 오래된 것을 버린다
}
```

나머지는 앞 설계와 같다. 피드에서 모으는 트윗이 많아야 10 × (팔로우 수 + 1)개로 묶인다. 모두가 모두를 팔로우하는 입력이 27초에서 7.4초로 줄었다. 그래도 팔로우가 499명이면 5000개를 매번 정렬한다. 메모리도 사람당 10개로 줄었지만, 이건 문제가 "최근 10개"만 묻기 때문에 성립하는 지름길이다. 피드를 아래로 더 내려 보는 기능이 생기면 버린 트윗이 필요해진다.

## 사람별 목록의 끝을 힙으로 합친다

사람별 목록은 이미 시각순으로 정렬되어 있다. 쓴 순서대로 붙였으니까. 정렬된 목록 여러 개에서 가장 큰 것부터 차례로 꺼내는 일은 k개 정렬 리스트 합치기와 똑같다. 목록마다 맨 끝(가장 최근) 트윗을 하나씩 최대 힙에 넣고, 시작한다.

1. 나와 팔로우한 사람마다 가장 최근 트윗 하나를 힙에 넣는다. 원소는 `[시각, 트윗 id, 쓴 사람, 그 사람 목록에서의 위치]`다.
2. 힙에서 시각이 가장 큰 원소를 꺼내 답에 붙인다.
3. 꺼낸 트윗을 쓴 사람의 목록에서 바로 앞 트윗이 있으면 그걸 힙에 넣는다.
4. 답이 10개가 되거나 힙이 빌 때까지 2와 3을 되풀이한다.

```js
class MaxHeap {
  constructor() { this.a = []; }   // 원소의 0번(시각)이 클수록 위로
  get size() { return this.a.length; }
  push(x) {
    const a = this.a;
    a.push(x);
    let i = a.length - 1;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (a[p][0] >= a[i][0]) break;
      [a[p], a[i]] = [a[i], a[p]];
      i = p;
    }
  }
  pop() {
    const a = this.a, top = a[0], last = a.pop();
    if (a.length) {
      a[0] = last;
      let i = 0;
      for (;;) {
        const l = 2 * i + 1, r = l + 1;
        let m = i;
        if (l < a.length && a[l][0] > a[m][0]) m = l;
        if (r < a.length && a[r][0] > a[m][0]) m = r;
        if (m === i) break;
        [a[m], a[i]] = [a[i], a[m]];
        i = m;
      }
    }
    return top;
  }
}

class Twitter {
  constructor() {
    this.time = 0;
    this.tweets = new Map();       // 사용자 -> [[시각, 트윗 id], ...] 오래된 순
    this.follows = new Map();
  }
  fol(u) {
    if (!this.follows.has(u)) this.follows.set(u, new Set());
    return this.follows.get(u);
  }
  postTweet(u, id) {
    if (!this.tweets.has(u)) this.tweets.set(u, []);
    this.tweets.get(u).push([this.time++, id]);
  }
  getNewsFeed(u) {
    const h = new MaxHeap();
    for (const v of [u, ...this.fol(u)]) {     // 1. 사람마다 가장 최근 트윗 하나
      const l = this.tweets.get(v);
      if (l && l.length) {
        const i = l.length - 1;
        h.push([l[i][0], l[i][1], v, i]);
      }
    }
    const out = [];
    while (h.size && out.length < 10) {
      const [, id, v, i] = h.pop();            // 2. 가장 최근 것을 꺼낸다
      out.push(id);
      if (i > 0) {                             // 3. 같은 사람의 바로 앞 트윗을 넣는다
        const p = this.tweets.get(v)[i - 1];
        h.push([p[0], p[1], v, i - 1]);
      }
    }
    return out;
  }
  follow(a, b) { if (a !== b) this.fol(a).add(b); }
  unfollow(a, b) { this.fol(a).delete(b); }
}
```

복잡도를 따져 본다. 팔로우한 사람이 F명이면 1단계에서 힙에 F + 1개를 넣어 O(F log F)다. 한꺼번에 힙으로 만들면 O(F)다. 그 뒤 꺼내기와 넣기를 10번만 하니 O(10 log F)다. 합쳐서 피드 한 번이 O(F + 10 log F)이고, 전체 트윗 수와 무관하다. 쓰기, 팔로우, 언팔로우는 O(1)이다. 공간은 트윗과 팔로우 관계를 저장하는 O(T + 팔로우 수)다.

측정에서도 힙은 어느 입력에서나 버텼다. LeetCode 크기의 무작위 연산 3만 번이 76ms, 모두가 모두를 팔로우하는 입력이 776ms, 조용한 사람만 팔로우하는 입력이 7.5ms였다. 한 줄 설계만큼 빠른 입력은 없지만 무너지는 입력도 없다. 면접에서 기대하는 답이 이것이다.

### 왜 사람마다 하나씩만 힙에 넣나

관련 트윗을 전부 힙에 넣고 10번 꺼내도 답은 같다. 하지만 넣는 데만 O(N log N)이 들어 정렬과 다를 게 없다. 사람마다 하나씩만 넣어도 되는 이유는 각 사람의 목록이 이미 정렬되어 있어서다. 어떤 사람의 두 번째로 최근 트윗은 그 사람의 가장 최근 트윗보다 먼저 나올 수 없다. 그러니 가장 최근 트윗이 꺼내지기 전까지 두 번째 것은 후보조차 아니다. 후보만 힙에 두는 것, 그게 k개 리스트 합치기의 원리다.

## 쓸 때 팔로워 피드에 미리 꽂아 둔다

지금까지는 피드를 열 때 합쳤다. 이걸 읽기 시점에 모은다고 해서 pull 방식이라 부른다. 반대로 트윗을 쓰는 순간 팔로워 모두의 피드 목록에 미리 넣어 두면, 피드를 열 때는 끝에서 10개를 읽기만 하면 된다. 쓰기 시점에 퍼뜨린다고 해서 push 방식이다.

```js
class Twitter {
  constructor() {
    this.time = 0;
    this.tweets = new Map();   // 사용자 -> 자기가 쓴 트윗
    this.follows = new Map();  // 사용자 -> 팔로우하는 사람
    this.fans = new Map();     // 사용자 -> 나를 팔로우하는 사람
    this.feed = new Map();     // 사용자 -> 미리 만들어 둔 피드, 오래된 순
  }
  get(m, u, mk) { if (!m.has(u)) m.set(u, mk()); return m.get(u); }
  postTweet(u, id) {
    const t = [this.time++, id, u];
    this.get(this.tweets, u, () => []).push(t);
    this.get(this.feed, u, () => []).push(t);                // 내 피드에
    for (const fan of this.get(this.fans, u, () => new Set()))
      this.get(this.feed, fan, () => []).push(t);            // 팔로워 피드마다
  }
  getNewsFeed(u) {
    const l = this.feed.get(u) || [], out = [];
    for (let i = l.length - 1; i >= 0 && out.length < 10; i--) out.push(l[i][1]);
    return out;
  }
  follow(a, b) {
    if (a === b) return;
    const fs = this.get(this.follows, a, () => new Set());
    if (fs.has(b)) return;
    fs.add(b);
    this.get(this.fans, b, () => new Set()).add(a);
    const mine = this.get(this.feed, a, () => []), theirs = this.tweets.get(b) || [];
    const m = [];
    let i = 0, j = 0;
    while (i < mine.length || j < theirs.length) {          // b의 지난 트윗을 시각순으로 섞어 넣는다
      if (j >= theirs.length || (i < mine.length && mine[i][0] < theirs[j][0])) m.push(mine[i++]);
      else m.push(theirs[j++]);
    }
    this.feed.set(a, m);
  }
  unfollow(a, b) {
    const fs = this.follows.get(a);
    if (!fs || !fs.has(b)) return;
    fs.delete(b);
    this.fans.get(b).delete(a);
    this.feed.set(a, (this.feed.get(a) || []).filter((t) => t[2] !== b)); // b의 트윗을 걷어 낸다
  }
}
```

피드는 O(10)이다. 대가는 다른 곳에서 치른다. 트윗 하나를 쓰면 팔로워 수 P만큼 피드에 넣어 O(P)이고, 피드마다 같은 트윗을 가리키니 공간도 팔로워 수만큼 불어난다. 팔로우하면 상대의 지난 트윗을 내 피드에 섞어 넣느라 O(내 피드 + 상대 트윗), 언팔로우하면 내 피드에서 상대 트윗을 걸러 내느라 O(내 피드)다.

모두가 모두를 팔로우하는 입력에서 1.3초로 힙의 776ms보다 느렸다. 트윗 하나가 500개 피드에 들어가서, 트윗 2만 개가 피드 쓰기 1000만 번이 되기 때문이다. 대신 피드 열기는 가장 빠르다. 실제 서비스는 읽기가 쓰기보다 훨씬 많아서 이 방식이 매력적이다. 문제는 팔로워가 수천만 명인 계정이다. 글 하나에 수천만 번 쓰기가 생긴다. 그래서 큰 서비스는 보통 계정에 따라 두 방식을 섞는다. 이 이야기는 [뉴스 피드 설계 ①](/posts/sd-news-feed-publishing)에서 자세히 다룬다.

LeetCode에서는 다섯 설계 모두 통과한다. 이 설계는 면접에서 "피드를 더 빨리 열 수 없나요"를 물었을 때 꺼낼 답이다.

## 읽기가 많나 쓰기가 많나에 따라 갈린다

| 설계 | 쓰기 | 피드 | 팔로우·언팔로우 | 언제 고르나 |
|---|---|---|---|---|
| 한 줄에 쌓고 거르기 | O(1) | O(T) | O(1) | 모두가 서로 팔로우하는 작은 그룹 |
| 사람별로 모아 정렬 | O(1) | O(N log N) | O(1) | 관련 트윗이 적을 때. 코드가 가장 읽기 쉽다 |
| 사람마다 최근 10개 | O(1) | O(10F log(10F)) | O(1) | 피드 길이가 고정일 때 |
| 사람별 목록을 힙으로 합치기 | O(1) | O(F + 10 log F) | O(1) | 어떤 입력에서도 무너지지 않는 기본값 |
| 쓸 때 팔로워 피드에 넣기 | O(P) | O(10) | O(피드 크기) | 읽기가 압도적으로 많고 팔로워 수가 고를 때 |

T는 전체 트윗 수, N은 피드에 관련된 트윗 수, F는 팔로우 수, P는 팔로워 수다.

같은 Node.js에서 세 입력을 돌렸다.

```text
입력                                  한 줄    모아 정렬   최근 10개   힙       push
LeetCode 크기 무작위 3만 번            155ms    194ms      133ms      76ms     68ms
500명이 서로 팔로우, 피드 1만 번       31ms     27403ms    7450ms     776ms    1310ms
조용한 사람만 팔로우, 피드 1만 번      2187ms   8.7ms      3.1ms      7.5ms    2.9ms
```

한 줄 설계는 두 번째 입력에서 가장 빠르고 세 번째에서 가장 느리다. push 방식은 첫째와 셋째에서 가장 빠르지만 둘째에서 쓰기 비용이 드러난다. 힙은 한 번도 1등을 못 했지만 꼴찌도 없었다. 설계를 고를 때 "평균"보다 "어떤 입력이 오면 무너지나"를 먼저 묻게 되는 이유다.

## heapq의 튜플과 Java의 int 배열 원소

힙 합치기 설계를 옮긴다.

```python
import heapq
from collections import defaultdict

class Twitter:
    def __init__(self):
        self.time = 0
        self.tweets = defaultdict(list)    # 사용자 -> [(시각, 트윗 id), ...] 오래된 순
        self.follows = defaultdict(set)    # 사용자 -> 팔로우하는 사람들

    def postTweet(self, userId: int, tweetId: int) -> None:
        self.tweets[userId].append((self.time, tweetId))
        self.time += 1

    def getNewsFeed(self, userId: int) -> list[int]:
        h = []
        for u in self.follows[userId] | {userId}:
            if self.tweets[u]:
                i = len(self.tweets[u]) - 1
                t, tid = self.tweets[u][i]
                h.append((-t, tid, u, i))  # 시각에 -를 붙여 최신이 맨 위로
        heapq.heapify(h)
        out = []
        while h and len(out) < 10:
            _, tid, u, i = heapq.heappop(h)
            out.append(tid)
            if i > 0:
                t, nid = self.tweets[u][i - 1]
                heapq.heappush(h, (-t, nid, u, i - 1))
        return out

    def follow(self, followerId: int, followeeId: int) -> None:
        if followerId != followeeId:
            self.follows[followerId].add(followeeId)

    def unfollow(self, followerId: int, followeeId: int) -> None:
        self.follows[followerId].discard(followeeId)   # 없으면 조용히 넘어간다
```

```text
[12, 28, 31, 42, 3, 9, 15, 7]
[28, 42, 3, 15, 7]
[]
```

예시대로 쓰고 팔로우한 뒤의 피드, 3과 팔로우한 적 없는 9를 언팔로우한 뒤의 피드, 아무 활동도 없는 사용자 77의 피드다.

Python에서 짚을 곳이 셋 있다. 첫째, 튜플은 앞 원소부터 비교한다. 시각이 모두 달라서 첫 원소에서 순서가 정해지지만, 시각이 같을 수 있는 설계라면 다음 원소로 넘어가 비교한다. 거기에 비교할 수 없는 객체가 있으면 `TypeError`가 난다. 둘째, `unfollow`에서 `remove` 대신 `discard`를 썼다. `remove`는 없는 값을 지우면 `KeyError`를 낸다. 팔로우한 적 없는 사람을 언팔로우하는 호출이 들어와도 조용히 넘어가야 한다. 셋째, `defaultdict`는 읽기만 해도 빈 항목을 만든다. 사용자 77의 피드를 열면 `self.follows[77]`과 `self.tweets[77]`이 생긴다. 이 문제에서는 무해하지만 메모리를 세는 면접 질문에서는 짚을 만하다.

```java
import java.util.*;

class Twitter {
    private int time = 0;
    private final Map<Integer, List<int[]>> tweets = new HashMap<>();  // 사용자 -> [시각, 트윗 id] 오래된 순
    private final Map<Integer, Set<Integer>> follows = new HashMap<>();

    public void postTweet(int userId, int tweetId) {
        tweets.computeIfAbsent(userId, k -> new ArrayList<>()).add(new int[]{time++, tweetId});
    }

    public List<Integer> getNewsFeed(int userId) {
        // 원소: {시각, 트윗 id, 사용자, 그 사용자 목록에서의 위치}. 시각이 큰 것이 맨 위
        PriorityQueue<int[]> h = new PriorityQueue<>((a, b) -> Integer.compare(b[0], a[0]));
        Set<Integer> users = new HashSet<>(follows.getOrDefault(userId, Set.of()));
        users.add(userId);
        for (int u : users) {
            List<int[]> l = tweets.get(u);
            if (l != null && !l.isEmpty()) {
                int i = l.size() - 1;
                h.offer(new int[]{l.get(i)[0], l.get(i)[1], u, i});
            }
        }
        List<Integer> out = new ArrayList<>();
        while (!h.isEmpty() && out.size() < 10) {
            int[] e = h.poll();
            out.add(e[1]);
            if (e[3] > 0) {
                int[] p = tweets.get(e[2]).get(e[3] - 1);
                h.offer(new int[]{p[0], p[1], e[2], e[3] - 1});
            }
        }
        return out;
    }

    public void follow(int followerId, int followeeId) {
        if (followerId != followeeId) follows.computeIfAbsent(followerId, k -> new HashSet<>()).add(followeeId);
    }

    public void unfollow(int followerId, int followeeId) {
        Set<Integer> s = follows.get(followerId);
        if (s != null) s.remove(followeeId);
    }
}
```

```text
[12, 28, 31, 42, 3, 9, 15, 7]
[28, 42, 3, 15, 7]
[]
```

Java에서는 `int[]`가 비교할 수 있는 타입이 아니라서 `PriorityQueue`에 비교자를 꼭 줘야 한다. 빼먹으면 Java 21에서는 첫 원소를 넣는 순간 `ClassCastException`이 난다. 컴파일은 통과하니 실행해 봐야 안다. 비교자 안에서도 `b[0] - a[0]` 같은 뺄셈 대신 `Integer.compare`를 쓴다. 시각이 작은 정수라 이 문제에서는 넘칠 일이 없지만, 시각 자리에 실제 밀리초 시각을 `long`으로 넣는 순간 뺄셈 비교는 위험해진다.

팔로우 목록을 `Set`이 아니라 `List<Integer>`로 두면 다른 함정이 생긴다. `list.remove(followeeId)`는 `int`를 넘기면 그 값이 아니라 그 인덱스를 지운다. `[5, 1000, 7]`에서 `remove(1)`을 부르니 1이 아니라 인덱스 1의 1000이 지워져 `[5, 7]`이 되었다. 값을 지우려면 `remove(Integer.valueOf(followeeId))`라고 써야 한다. `Set`을 쓰면 이 문제도, 중복 팔로우도 함께 사라진다.

## 시각 대신 트윗 id로 정렬하면 틀린다

### id가 클수록 최근이라고 가정한다

시각을 붙이지 않고 트윗 id로 정렬하는 실수가 가장 흔하다. 예시를 id 역순으로 정렬하면 `[42, 31, 28, 15, 12, 9, 7, 3]`이 나온다. 정답 `[12, 28, 31, 42, 3, 9, 15, 7]`과 첫 칸부터 다르다. LeetCode의 기본 예시는 우연히 id가 쓴 순서대로 커져서 통과해 버린다. 실무에서도 같은 일이 있다. 여러 서버가 따로 id를 만들면 id의 크기와 생성 순서가 어긋난다. 시간순 정렬이 필요한 id는 Snowflake처럼 앞자리에 시각을 넣어 설계한다.

### 자기 자신을 팔로우 목록에 넣어 둔다

"내 트윗도 피드에 나와야 하니" 사용자를 만들 때 팔로우 Set에 자기 자신을 넣어 두는 설계가 있다. 그러면 `unfollow(1, 1)`이 들어오면 자기 자신이 빠져서 내 트윗이 피드에서 사라진다. 예시에서 그렇게 해 보니 피드가 `[12, 28, 31, 3, 9, 15]`가 되어 내 트윗 42와 7이 없어졌다. 자기 자신은 팔로우 목록 밖에서 따로 넣고, 자기 자신에 대한 팔로우와 언팔로우는 무시한다.

### 자기 자신을 팔로우하면 트윗이 두 번 나온다

`follow(a, b)`에서 `a === b`를 막지 않고, 피드에서 `[u, ...팔로우 목록]`을 모으면 내가 두 번 들어간다. 예시에서 `follow(1, 1)`을 부르고 모아 정렬하는 설계로 피드를 열었더니 `[12, 28, 31, 42, 42, 3, 9, 15, 7, 7]`이 나왔다. 42와 7이 두 번씩이다. 힙 설계에서도 같은 사람이 힙에 두 번 올라가 똑같이 겹친다. 막는 곳은 `follow` 한 곳이면 된다.

### 피드가 10개를 넘는지 확인하지 않는다

반복 조건에서 `out.length < 10`을 빼면 관련 트윗을 전부 돌려준다. 트윗이 10개 이하인 예시에서는 차이가 없어서 놓치기 쉽다. 플레이그라운드의 테스트에 트윗 12개짜리를 넣어 두었다.

## 진짜 서비스라면 어떻게 바뀌나

### 팔로워가 1억 명인 계정이 있다면

push 방식으로는 그 계정의 글 하나가 1억 번의 쓰기가 된다. 그래서 팔로워가 많은 계정만 pull로 빼고, 나머지는 push로 미리 만든다. 피드를 열 때 미리 만든 피드와 "내가 팔로우하는 유명 계정들의 최근 글"을 힙으로 합친다. 이 글의 힙 설계가 그 합치는 부분이다.

### 피드를 계속 아래로 내려 본다면

"다음 10개"를 달라는 요청이 오면 마지막으로 보여 준 트윗의 시각을 커서로 받는다. 각 사람의 목록에서 그 시각보다 앞선 위치를 [이분 탐색](/posts/binary-search)으로 찾아 힙을 다시 채우면 같은 방식으로 이어진다. 사람마다 최근 10개만 두는 설계는 여기서 쓸 수 없다. 커서를 쓰는 페이지 넘기기는 [뉴스 피드 설계 ②](/posts/sd-news-feed-retrieval)에서 다룬다.

### 트윗을 지우는 기능이 생긴다면

사람별 목록에서 그 트윗을 찾아 지우면 된다. 트윗 id에서 위치로 가는 해시맵을 두면 찾기가 O(1)이다. 배열 가운데를 지우면 뒤가 밀리니, 지웠다는 표시만 남기고 피드를 만들 때 건너뛰는 방법이 더 흔하다. push 방식이라면 팔로워들의 피드에 퍼진 사본까지 지워야 해서 훨씬 비싸다.

### 피드를 최신 10개가 아니라 k개로 바꾼다면

힙 설계는 꺼내는 횟수만 k로 바꾸면 된다. O(F + k log F)다. 사람마다 최근 10개만 두는 설계는 k가 바뀔 때마다 저장 규칙을 바꿔야 한다.

비슷하게 정렬된 목록 여러 개를 합치는 문제로는 [Merge k Sorted Lists](/posts/leetcode-merge-k-sorted-lists)가 있다. 힙에 넣는 원소에 "어느 목록의 몇 번째인가"를 같이 담는 요령도 같다. 크기를 k로 묶어 두는 다른 쓰임은 [Kth Largest Element in a Stream](/posts/leetcode-kth-largest-element-in-a-stream)에서 본다. 클래스 하나에 해시맵과 다른 자료구조를 엮는 설계 문제로는 [LRU Cache](/posts/leetcode-lru-cache)가 있다.

  constructor() { this.a = []; }

    const a = this.a;

    let i = a.length - 1;

      if (a[p][0] >= a[i][0]) break;
      [a[p], a[i]] = [a[i], a[p]];
      i = p;
    }
  }
  pop() {

    if (a.length) {
      a[0] = last;

      for (;;) {

        if (m === i) break;

      }
    }

## 면접에서 나올 만한 질문

### 피드는 어떤 자료구조로 만드나요?

사람별로 트윗을 시각순 목록에 담고, 피드를 열 때 나와 팔로우한 사람마다 가장 최근 트윗 하나씩을 최대 힙에 넣는다. 맨 위를 꺼내 답에 붙이고 그 사람의 바로 앞 트윗을 넣는 일을 10번 한다. 정렬된 목록 여러 개를 합치는 k개 리스트 합치기와 같은 방식이다. 팔로우 관계는 사용자에서 Set으로 가는 해시맵에 둔다.

### 피드 한 번의 시간 복잡도는 어떻게 되나요?

팔로우한 사람이 F명이면 힙을 만드는 데 O(F), 꺼내고 넣기를 10번 하는 데 O(10 log F)다. 전체 트윗 수와 관계가 없다는 게 장점이다. 관련 트윗을 전부 모아 정렬하면 O(N log N)이라, 500명이 서로 팔로우한 입력에서 27초와 0.8초로 갈렸다.

### 트윗 id로 정렬하면 안 되나요?

안 된다. 문제에서 트윗 id는 쓴 순서와 관계가 없어서, 나중에 쓴 트윗의 id가 더 작을 수 있다. 쓸 때마다 1씩 늘어나는 시각을 따로 붙여야 한다. 실무에서도 여러 서버가 만든 id는 순서를 보장하지 않아서, 시간순이 필요하면 시각을 앞자리에 넣은 id를 설계한다.

### 자기 자신을 팔로우하거나 언팔로우하면 어떻게 하나요?

둘 다 무시한다. 자기 자신은 팔로우 목록과 별개로 피드에 늘 넣는다. 팔로우 목록에 자기 자신을 넣어 두는 설계는 `unfollow(1, 1)` 한 번에 내 트윗이 피드에서 사라지고, 반대로 막지 않으면 같은 트윗이 두 번 나온다.

### 피드를 더 빨리 열 수는 없나요?

트윗을 쓰는 순간 팔로워마다의 피드 목록에 미리 넣어 두면 피드 열기는 O(10)이 된다. 대신 쓰기가 팔로워 수만큼 비싸지고, 같은 트윗의 참조가 팔로워 수만큼 저장되며, 팔로우와 언팔로우 때 피드를 다시 섞거나 걸러 내야 한다. 읽기가 쓰기보다 훨씬 많은 서비스에서 고른다.

### 팔로워가 아주 많은 계정은 어떻게 처리하나요?

그 계정에 push 방식을 쓰면 글 하나가 팔로워 수만큼의 쓰기가 된다. 그래서 팔로워가 많은 계정만 pull로 빼고, 피드를 열 때 미리 만들어 둔 피드와 그 계정들의 최근 글을 힙으로 합친다. 두 방식을 섞는 기준은 팔로워 수나 계정의 활동량으로 정한다.

### 사람마다 최근 10개만 저장하면 안 되나요?

이 문제에서는 맞는 답이 나온다. 한 사람의 11번째 트윗은 그 사람 혼자서도 10개에 밀려서 피드에 나올 수 없기 때문이다. 하지만 피드를 더 내려 보는 기능이나 k가 바뀌는 요구가 생기면 버린 트윗이 필요해진다. 저장을 문제의 숫자에 맞춰 줄이는 건 요구가 고정일 때만 쓰는 지름길이다.
