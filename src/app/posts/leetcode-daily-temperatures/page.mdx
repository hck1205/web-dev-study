날씨 앱에 "며칠 뒤에 오늘보다 따뜻해진다"는 문구를 넣자는 이야기가 나왔다. 일별 기온 예보 배열을 받아서 날마다 그 숫자를 계산하면 된다. 처음 짠 코드는 날마다 뒤쪽 날짜를 하나씩 훑었다. 몇 주치 데이터로는 문제가 없었는데, 수십 년치 관측 기록에 같은 계산을 돌리자 몇 초씩 걸렸다.

[LeetCode 739. Daily Temperatures](https://leetcode.com/problems/daily-temperatures/)가 이 계산이다. "오른쪽에서 처음으로 나보다 큰 값까지의 거리"를 묻는 문제로, 단조 스택(monotonic stack)의 가장 대표적인 연습 문제다. 이 글은 이중 반복문에서 시작해 기온 범위를 이용한 풀이, 구간 최댓값 표, 단조 스택 두 방향, 답 배열을 건너뛰는 풀이까지 여섯 가지를 비교한다. 단조 스택 패턴 전체는 [단조 스택 패턴 글](/posts/monotonic-stack-pattern)에, 스택 자료구조는 [스택·큐·덱 글](/posts/ds-stack-queue-deque)에 있다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 며칠을 기다려야 더 따뜻해지나

정수 배열 `temperatures`가 주어진다. `i`번째 값은 `i`일의 기온이다. 같은 길이의 배열 `answer`를 돌려주는데, `answer[i]`는 `i`일 뒤로 처음 `i`일보다 기온이 높은 날까지 며칠 걸리는지다. 그런 날이 없으면 0이다. "높은" 날이라서 같은 기온은 따뜻해진 것으로 치지 않는다.

제약 조건에서 풀이 선택에 영향을 주는 건 두 가지다. 배열 길이가 최대 10^5이라 O(n²)은 최악에 50억 번 가까이 비교하게 된다. 그리고 기온이 30 이상 100 이하라서 서로 다른 기온이 71가지뿐이다. 두 번째 조건은 뒤에서 한 풀이에 쓴다.

이 글에서 계속 쓸 예시다.

```text
day      0   1   2   3   4   5   6   7
temp    65  70  62  61  68  72  60  64
answer   1   4   2   1   1   0   1   0
```

손으로 몇 개만 확인해 보자. 0일은 65도이고 바로 다음 날이 70도라서 1이다. 1일은 70도인데 62, 61, 68은 모두 낮고 5일의 72도에서 처음 높아진다. 5 - 1 = 4다. 5일의 72도는 뒤에 더 높은 날이 없어서 0이고, 마지막 날은 뒤에 날이 없으니 당연히 0이다.

1일을 손으로 찾을 때 62, 61, 68을 하나씩 확인했다. 그런데 2일, 3일, 4일의 답을 구할 때도 이 날들을 또 본다. 같은 비교가 여러 번 반복된다는 느낌이 들면, 그 비교 결과를 어딘가에 남겨 둘 방법이 있는지 생각해 볼 때다.

## 날마다 앞으로 하나씩 세어 보면

문제를 그대로 옮기면 이중 반복문이다. 날마다 그 뒤를 차례로 보다가 처음 더 높은 날을 만나면 멈춘다.

```js
function dailyTemperatures(temperatures) {
  const n = temperatures.length;
  const answer = new Array(n).fill(0);
  for (let i = 0; i < n; i++) {
    for (let j = i + 1; j < n; j++) {
      if (temperatures[j] > temperatures[i]) {
        answer[i] = j - i; // 처음 만난 더 따뜻한 날
        break;
      }
    }
  }
  return answer;
}
```

공간은 답 배열을 빼면 O(1)이다. 시간은 최악 O(n²)이다. 기온이 계속 내려가거나 그대로인 입력에서는 날마다 끝까지 훑어도 더 높은 날이 없어서 `break`가 한 번도 걸리지 않는다. 길이 10^5으로 재 봤다.

```text
입력                          이중 반복문
무작위 기온 10^5개              67 ms
내려가거나 같은 기온 10^5개    4879 ms
```

무작위 입력은 대개 금방 더 높은 날을 만나서 빠르지만, 나쁜 입력 하나에 5초 가까이 걸린다. LeetCode에서 시간 초과가 난다. 이 풀이가 느린 이유는 앞 절에서 본 그대로다. 1일을 볼 때 확인한 "62, 61, 68은 70보다 낮다"는 정보를 버리고, 2일을 볼 때 61, 68을 다시 본다.

## 기온 범위가 좁다는 걸 이용하면

기온이 30부터 100까지 71가지뿐이라는 조건을 쓰면 다른 길이 열린다. 배열을 오른쪽에서 왼쪽으로 훑으면서, 기온마다 "이 기온이 지금까지 가장 가깝게 나온 날"을 표에 적어 둔다. `i`일에 도착하면 `temperatures[i] + 1`부터 100까지 표를 보고 그중 가장 이른 날을 고른다.

```js
function dailyTemperatures(temperatures) {
  const n = temperatures.length;
  const answer = new Array(n).fill(0);
  // next[t] = 지금 보는 날보다 뒤에서 기온 t가 처음 나오는 날
  const next = new Array(101).fill(Infinity);
  for (let i = n - 1; i >= 0; i--) {
    let warmer = Infinity;
    for (let t = temperatures[i] + 1; t <= 100; t++) {
      if (next[t] < warmer) warmer = next[t]; // 더 높은 기온 중 가장 가까운 날
    }
    if (warmer !== Infinity) answer[i] = warmer - i;
    next[temperatures[i]] = i; // 이제 i일이 이 기온의 가장 가까운 날이다
  }
  return answer;
}
```

날마다 최대 70칸을 보니 시간은 O(n·W)다. W는 기온 범위 71이다. 앞의 나쁜 입력에서 4879ms가 9ms로 줄었다. 공간은 표 크기 O(W)다.

빠르긴 한데 기온 범위라는 문제 밖의 조건에 기댄다. 기온 대신 주가나 응답 시간처럼 값의 범위가 넓은 데이터라면 표를 만들 수 없다. 범위와 상관없이 O(n)이 나오는 풀이가 필요하다.

## 구간 최댓값 표로 크게 건너뛰기

값의 범위에 기대지 않으면서 이중 반복문보다 빠르게 가는 중간 단계도 있다. `i`일의 답을 찾을 때 한 칸씩 걷지 말고, "이 구간 안에 `i`일보다 높은 날이 하나라도 있나"를 한 번에 물어 큰 걸음으로 건너뛰는 것이다. 구간 안에 높은 날이 없으면 통째로 건너뛰고, 있으면 걸음을 반으로 줄인다.

"구간에 높은 날이 있나"는 "구간의 최댓값이 `i`일보다 높은가"와 같다. 2의 거듭제곱 길이 구간의 최댓값을 미리 표로 만들어 두면(sparse table) 이 질문에 O(1)로 답할 수 있다. `sp[k][i]`는 `i`부터 2^k칸의 최댓값이고, 길이 2^k 구간은 길이 2^(k-1) 구간 둘로 나뉘니 앞 줄에서 바로 만든다.

```js
function dailyTemperatures(temperatures) {
  const n = temperatures.length;
  // sp[k][i] = i부터 2^k칸(i ~ i + 2^k - 1)의 최댓값
  const sp = [temperatures.slice()];
  for (let k = 1; (1 << k) <= n; k++) {
    const prev = sp[k - 1], cur = new Array(n - (1 << k) + 1);
    for (let i = 0; i < cur.length; i++) cur[i] = Math.max(prev[i], prev[i + (1 << (k - 1))]);
    sp.push(cur);
  }
  const answer = new Array(n).fill(0);
  for (let i = 0; i < n; i++) {
    // i + 1부터 2^k칸씩 크게 건너뛰되, 그 구간에 더 높은 날이 없을 때만 건너뛴다
    let pos = i + 1;
    for (let k = sp.length - 1; k >= 0; k--) {
      if (pos + (1 << k) <= n && sp[k][pos] <= temperatures[i]) pos += 1 << k;
    }
    if (pos < n) answer[i] = pos - i; // pos가 처음으로 더 높은 날
  }
  return answer;
}
```

큰 걸음부터 시도하는 방식은 이진수로 거리를 한 자리씩 정하는 것과 같다. 첫 번째 더 높은 날까지의 거리를 2^16, 2^15, ... 순서로 "더해도 되나"를 물어 채워 간다. 표를 만드는 데 O(n log n), 날마다 log n번 물으니 전체 O(n log n)이고 공간도 O(n log n)이다. 나쁜 입력에서 35ms로, 이중 반복문의 4.9초와는 비교가 안 되지만 단조 스택보다는 열 배쯤 느리다.

이 문제만 놓고 보면 과한 도구다. 그래도 알아 둘 가치가 있는 건, 질문이 "모든 날의 답"이 아니라 "임의의 날 `i` 이후로 `x`도 이상인 첫날은?"처럼 매번 기준값이 바뀌는 질의로 바뀌면 단조 스택은 쓸 수 없고 이 표는 그대로 쓸 수 있기 때문이다. 단조 스택은 기준값이 그 날의 기온일 때만 성립한다.

## 아직 답을 못 찾은 날을 쌓아 두는 스택

다시 손으로 푼 장면으로 돌아가자. 2일(62도), 3일(61도)은 4일(68도)이 올 때까지 답을 기다리고 있었다. 그리고 1일(70도)도 아직 기다리는 중이다. 기다리는 날들을 늘어놓으면 `70, 62, 61`처럼 기온이 내려가는 순서다. 우연이 아니다. 만약 기다리는 날 뒤에 그보다 높은 날이 있었다면, 그날이 바로 답이라서 기다림이 이미 끝났을 것이다. 그래서 아직 기다리는 날들은 늘 왼쪽에서 오른쪽으로 갈수록 기온이 낮거나 같다.

이 줄을 스택으로 들고 다닌다. 스택 안의 값이 한 방향으로 정렬된 상태를 유지하는 스택을 단조 스택이라고 한다.

- 새 날 `i`가 오면 스택 맨 위 날의 기온과 비교한다.
- `i`일이 더 높으면, 맨 위 날은 드디어 더 따뜻한 날을 만났다. 꺼내고 답을 `i - 그날`로 적는다. 다음 맨 위와 또 비교한다.
- 더 높지 않으면 멈추고 `i`일을 스택에 넣는다. 이제 `i`일도 기다리는 날이다.
- 끝까지 남은 날은 답이 0이다. 답 배열을 0으로 채워 두었으니 따로 할 일이 없다.

스택에는 기온이 아니라 날짜(인덱스)를 넣는다. 답이 "며칠 뒤"라서 거리를 계산하려면 날짜가 필요하고, 기온은 날짜만 있으면 배열에서 읽을 수 있다.

4일의 장면을 다시 보자. 68도가 들어오면서 61과 62를 꺼내고 70 앞에서 멈췄다. 70보다 아래 칸은 볼 필요가 없다. 스택이 내려가는 순서라서 70 아래는 전부 70 이상이고, 68이 70을 못 넘으면 그 아래도 못 넘는다. 이게 단조 스택이 비교를 아끼는 방식이다.

```js
function dailyTemperatures(temperatures) {
  const n = temperatures.length;
  const answer = new Array(n).fill(0); // 끝까지 못 찾은 날은 0
  const stack = []; // 아직 더 따뜻한 날을 못 만난 날의 인덱스. 기온이 내려가는 순서

  for (let i = 0; i < n; i++) {
    // 오늘이 맨 위 날보다 따뜻하면, 맨 위 날의 기다림이 끝났다
    while (stack.length && temperatures[stack[stack.length - 1]] < temperatures[i]) {
      const j = stack.pop();
      answer[j] = i - j;
    }
    stack.push(i); // 오늘도 더 따뜻한 날을 기다리기 시작한다
  }
  return answer;
}
```

### 반복문이 두 겹인데 왜 O(n)인가

`for` 안에 `while`이 있어서 O(n²)처럼 보인다. 하지만 `while`이 한 번 돌 때마다 스택에서 날 하나가 빠진다. 날마다 스택에 정확히 한 번 들어가고 많아야 한 번 빠지니, 전체 실행에서 `while`이 도는 횟수를 다 더해도 n을 넘지 않는다. 어떤 날에 `while`이 많이 돌면 그만큼 다른 날에는 덜 돈다. 이렇게 한 번의 연산이 아니라 전체 합으로 세는 걸 분할 상환 분석이라고 한다([Big O 글](/posts/big-o-notation)).

그래서 시간은 O(n), 공간은 스택 O(n)이다. 기온이 계속 내려가는 입력이면 모든 날이 스택에 쌓인다. 앞의 나쁜 입력에서 4.5ms, 무작위 입력에서 2.2ms였다.

### 끝까지 스택에 남는 날들

예시를 다 돌리고 나면 스택에는 `5:72, 7:64`가 남는다. 이 날들은 뒤에 더 따뜻한 날이 없어서 답이 0인 날이다. 오른쪽 끝에서 왼쪽을 바라보면, 7일의 64도가 첫 기록이고 5일의 72도가 그 기록을 깬 날이다. 남은 스택은 "오른쪽에서 볼 때 최고 기온 기록을 세운 날들"이고, 그래서 바닥부터 기온이 내려가는 순서다.

반복문의 어느 시점에 멈춰도 같은 말이 성립한다. `i`일까지 처리한 순간의 스택은 "0일부터 `i`일까지만 놓고 볼 때 오른쪽에서 기록을 세운 날들"이다. 이 불변식이 단조 스택 풀이가 맞는 이유다. 새 날이 오면 그보다 낮은 기록들은 더는 기록이 아니게 되니 빠지고, 빠지는 순간 그 날에게 처음으로 더 높은 날이 나타난 것이다. 면접에서 "왜 맞는지 설명해 보라"고 하면 이 불변식으로 답한다.

### Python과 Java로 쓰면

Python은 리스트를 스택으로 쓰고 `stack[-1]`로 맨 위를 본다.

```python
from typing import List

def daily_temperatures(temperatures: List[int]) -> List[int]:
    n = len(temperatures)
    answer = [0] * n
    stack = []  # 아직 더 따뜻한 날을 못 만난 날의 인덱스
    for i, t in enumerate(temperatures):
        while stack and temperatures[stack[-1]] < t:
            j = stack.pop()
            answer[j] = i - j
        stack.append(i)
    return answer
```

Java는 `Deque<Integer>`를 써도 되지만, 인덱스는 0부터 n - 1까지라서 `int[]` 배열과 높이 변수 하나로 스택을 만들면 박싱이 없어 더 빠르다. 스택 크기는 n을 넘지 않으니 배열 크기를 n으로 잡으면 넘치지 않는다. `new int[n]`은 0으로 초기화되므로 답 배열을 따로 채울 필요도 없다.

```java
class Solution {
    public int[] dailyTemperatures(int[] temperatures) {
        int n = temperatures.length;
        int[] answer = new int[n];     // 0으로 초기화되어 있다
        int[] stack = new int[n];      // 인덱스를 담는 배열 스택
        int top = 0;                   // 스택 높이
        for (int i = 0; i < n; i++) {
            while (top > 0 && temperatures[stack[top - 1]] < temperatures[i]) {
                int j = stack[--top];
                answer[j] = i - j;
            }
            stack[top++] = i;
        }
        return answer;
    }
}
```

세 언어 모두 예시에서 `[1, 4, 2, 1, 1, 0, 1, 0]`을 낸다.

## 오른쪽에서 왼쪽으로 후보만 남기기

같은 단조 스택을 반대 방향으로 돌릴 수도 있다. 오른쪽 끝에서 왼쪽으로 가면서, 스택에는 "앞으로 볼 날들에게 답이 될 수 있는 후보"만 남긴다.

`i`일에 도착하면 스택 맨 위의 날 중 `i`일보다 낮거나 같은 날을 전부 버린다. 그 날들은 `i`일에게도 답이 아니고, `i`보다 왼쪽 날들에게도 답이 될 수 없다. 왼쪽 날에게는 `i`일이 더 가깝고 더 따뜻하거나 같기 때문이다. 버리고 나면 맨 위가 `i`일보다 따뜻한 가장 가까운 날이다.

```js
function dailyTemperatures(temperatures) {
  const n = temperatures.length;
  const answer = new Array(n).fill(0);
  const stack = []; // 오른쪽에서 답이 될 수 있는 후보들. 위로 갈수록 가깝고 낮다
  for (let i = n - 1; i >= 0; i--) {
    // 오늘보다 낮거나 같은 후보는 누구에게도 답이 될 수 없다
    while (stack.length && temperatures[stack[stack.length - 1]] <= temperatures[i]) {
      stack.pop();
    }
    if (stack.length) answer[i] = stack[stack.length - 1] - i;
    stack.push(i); // 오늘은 왼쪽 날들의 후보가 된다
  }
  return answer;
}
```

예시를 오른쪽부터 돌리면 스택이 이렇게 바뀐다. 각 줄은 그날을 처리하고 넣은 뒤의 스택이다.

```text
7일 64도  버림: -        답 0   스택: 7:64
6일 60도  버림: -        답 1   스택: 7:64 6:60
5일 72도  버림: 60, 64   답 0   스택: 5:72
4일 68도  버림: -        답 1   스택: 5:72 4:68
3일 61도  버림: -        답 1   스택: 5:72 4:68 3:61
2일 62도  버림: 61       답 2   스택: 5:72 4:68 2:62
1일 70도  버림: 62, 68   답 4   스택: 5:72 1:70
0일 65도  버림: -        답 1   스택: 5:72 1:70 0:65
```

1일(70도)에 도착했을 때 스택은 바닥부터 `5:72, 4:68, 2:62`이다. 62와 68을 버리면 맨 위 72가 답이 되어 5 - 1 = 4가 나온다. 5일의 72도는 들어오면서 60과 64를 모두 버렸다. 이보다 왼쪽 날들에게는 72도가 60, 64보다 가깝고 더 따뜻하니, 60과 64는 다시 쓰일 일이 없다.

복잡도는 똑같이 O(n), O(n)이다. 차이는 답이 정해지는 시점이다. 왼쪽에서 오른쪽 방향은 "꺼낼 때" 꺼낸 날의 답이 정해지고, 오른쪽에서 왼쪽 방향은 "넣기 직전에" 지금 날의 답이 정해진다. 이번 문제에서는 같지만, 데이터가 실시간으로 들어오는 상황이라면 미래를 알 수 없으니 왼쪽에서 오른쪽 방향만 쓸 수 있다. 반대로 "날마다 오른쪽에서 더 큰 값이 무엇인지"를 각 날을 처리하는 순간 알아야 하는 경우라면 오른쪽에서 왼쪽 방향이 편하다.

비교 연산자가 `<=`로 바뀐 것도 눈여겨볼 점이다. 같은 기온의 후보는 따뜻한 날이 아니니 버려야 한다. 이 차이는 뒤에서 다시 본다.

## 답 배열을 건너뛰며 따라가기

스택 없이 답 배열 자체를 지도로 쓰는 풀이도 있다. 오른쪽에서 왼쪽으로 가면서, `i`일의 답을 찾을 때 `j = i + 1`부터 본다. `j`일이 더 따뜻하면 답이다. 아니라면 `j`일보다 따뜻한 날은 이미 `answer[j]`에 적혀 있다. `j`일과 그 사이의 날들은 `j`일 이하이니 `i`일보다도 따뜻할 수 없고, 바로 `j + answer[j]`로 건너뛴다. `answer[j]`가 0이면 `j`보다 따뜻한 날이 없다는 뜻이고, `j`도 `i` 이하이니 `i`의 답도 0이다.

```js
function dailyTemperatures(temperatures) {
  const n = temperatures.length;
  const answer = new Array(n).fill(0);
  for (let i = n - 2; i >= 0; i--) {
    let j = i + 1;
    while (temperatures[j] <= temperatures[i]) {
      if (answer[j] === 0) { j = -1; break; } // j보다 따뜻한 날이 없다 → i도 없다
      j += answer[j]; // j보다 따뜻한 첫날로 건너뛴다
    }
    if (j !== -1) answer[i] = j - i;
  }
  return answer;
}
```

1일(70도)이 어떻게 건너뛰는지 그림으로 보자. 오른쪽 날들의 답은 이미 구해져 있다.

Python으로 옮기면 이렇다. `while`의 조건과 탈출이 같으니 언어가 바뀌어도 구조는 그대로다.

```python
def daily_temperatures(temperatures):
    n = len(temperatures)
    answer = [0] * n
    for i in range(n - 2, -1, -1):
        j = i + 1
        while temperatures[j] <= temperatures[i]:
            if answer[j] == 0:   # j보다 따뜻한 날이 없다 → i도 없다
                j = -1
                break
            j += answer[j]       # j보다 따뜻한 첫날로 건너뛴다
        if j != -1:
            answer[i] = j - i
    return answer
```

예시에서 `[1, 4, 2, 1, 1, 0, 1, 0]`, `[70, 70, 75]`에서 `[2, 1, 0]`, 길이 1에서 `[0]`이 나온다. `answer[j] == 0`일 때 바로 멈추는 줄이 빠지면 `j += 0`이 되어 같은 자리에서 영원히 돈다. 이 풀이에서 가장 조심할 곳이다.

"추가 공간을 O(1)로 할 수 있나"라는 꼬리 질문에 이 풀이를 꺼낸다. 다만 처음 보는 사람이 코드만 보고 이해하기는 어렵고, 답 배열이 거리여야만 성립하는 방식이라 "더 큰 값 자체"를 묻는 변형에는 바로 옮기기 어렵다(인덱스를 함께 적어 두면 된다).

|---|---|---|---|
| 이중 반복문 | O(n²) | O(1) | n이 작을 때, 정답 확인용 |

| 구간 최댓값 표 | O(n log n) | O(n log n) | 기준값이 질의마다 바뀌는 변형일 때 |

## 같은 기온은 따뜻해진 게 아니다

이 문제에서 가장 흔한 실수는 왼쪽에서 오른쪽 풀이의 비교를 `<=`로 쓰는 것이다.

```js
// 같은 기온도 꺼내 버린다
while (stack.length && temperatures[stack[stack.length - 1]] <= temperatures[i]) {
  const j = stack.pop();
  answer[j] = i - j;
}
```

`[70, 70, 75]`를 넣으면 정답은 `[2, 1, 0]`인데 이 코드는 `[1, 1, 0]`을 낸다. 1일의 70도가 0일의 70도를 꺼내면서 "1일 뒤에 따뜻해진다"고 적어 버렸다. 같은 기온은 따뜻해진 게 아니다. 본문 예시처럼 같은 값이 없는 입력에서는 두 코드의 답이 똑같아서, 같은 값이 연속으로 나오는 테스트를 넣지 않으면 발견하지 못한다. 기온을 30~37도로 좁혀 무작위 5000세트를 이중 반복문과 비교했더니 이 버전만 3569세트에서 답이 달랐다.

같은 기온이 이어지는 `[71, 69, 69, 72, 68, 75]`에서 두 코드의 스택을 한 줄씩 찍어 보면 어디서 갈라지는지 보인다.

```text
<  로 비교 (맞는 코드)
0일 71도  꺼냄: -                              스택: 0:71
1일 69도  꺼냄: -                              스택: 0:71 1:69
2일 69도  꺼냄: -                              스택: 0:71 1:69 2:69
3일 72도  꺼냄: 2일 답 1, 1일 답 2, 0일 답 3    스택: 3:72
4일 68도  꺼냄: -                              스택: 3:72 4:68
5일 75도  꺼냄: 4일 답 1, 3일 답 2              스택: 5:75
→ [3, 2, 1, 2, 1, 0]

<= 로 비교 (틀린 코드)
2일 69도  꺼냄: 1일 답 1                       스택: 0:71 2:69
3일 72도  꺼냄: 2일 답 1, 0일 답 3              스택: 3:72
→ [3, 1, 1, 2, 1, 0]
```

맞는 코드에서는 2일에 같은 69도가 두 칸 나란히 쌓인다. 스택이 "엄격하게 내려가는" 게 아니라 "내려가거나 같은" 순서라는 뜻이다. 3일의 72도가 오면 같은 69도 두 칸이 차례로 풀린다. 틀린 코드는 2일에 1일을 미리 꺼내 버려 1일의 답이 1이 됐다.

헷갈리면 이렇게 정리한다. 왼쪽에서 오른쪽 방향은 "꺼내는 조건 = 답이 되는 조건"이라 문제의 "더 높은"을 그대로 쓴 `<`다. 오른쪽에서 왼쪽 방향은 "버리는 조건 = 답이 될 수 없는 조건"이라 그 반대인 `<=`다. 문제가 "높거나 같은 날"을 물었다면 둘 다 하나씩 바뀐다.

스택에 기온을 넣는 실수도 있다. 기온만 들고 있으면 꺼낼 때 그날이 며칠이었는지 알 수 없어서 거리를 계산하지 못한다. 인덱스를 넣고 기온은 배열에서 읽는다.

길이 1인 입력은 반복문이 바로 끝나고 `[0]`이 나온다. 마지막 날은 어느 풀이에서든 항상 0이다. 답 배열 건너뛰기 풀이는 `i = n - 2`부터 시작하니 길이 1이면 반복문을 돌지 않는다. 처음부터 `j = i + 1`을 보므로 `n - 1`에서 시작하면 범위를 벗어난다.

## 면접관이 조건을 바꾸면

### 배열이 원형이라면

마지막 날 다음에 다시 첫날이 온다고 보는 변형이 LeetCode 503 Next Greater Element II다. 거리 대신 더 큰 값 자체를 묻고, 없으면 -1이다. 배열을 두 번 이어 붙인 것처럼 2n번 돌면 된다. 두 번째 바퀴에서는 답만 찾고 새로 넣지 않는다.

```js
function nextGreaterCircular(nums) {
  const n = nums.length;
  const res = new Array(n).fill(-1);
  const stack = [];
  for (let k = 0; k < 2 * n; k++) {
    const i = k % n;
    while (stack.length && nums[stack[stack.length - 1]] < nums[i]) res[stack.pop()] = nums[i];
    if (k < n) stack.push(i); // 두 번째 바퀴에서는 답만 찾고 넣지 않는다
  }
  return res;
}
// [3, 8, 4, 1, 2] → [8, -1, 8, 2, 3]
```

마지막 원소 2의 답 3은 한 바퀴 돌아 첫 원소에서 찾은 것이다. 8은 가장 크니 끝까지 -1이다. 여전히 O(n)이다.

### 기온이 하루씩 실시간으로 들어온다면

왼쪽에서 오른쪽 풀이는 미래를 보지 않으니 그대로 온라인 알고리즘이 된다. 새 기온이 들어올 때마다 스택에서 풀리는 날들을 꺼내 "며칠 걸렸다"를 알려 주면 된다.

```js
class WarmWatcher {
  constructor() { this.stack = []; this.day = 0; } // [날짜, 기온]
  add(t) {
    const done = [];
    while (this.stack.length && this.stack[this.stack.length - 1][1] < t) {
      const [d] = this.stack.pop();
      done.push([d, this.day - d]); // d일이 이제야 따뜻한 날을 만났다
    }
    this.stack.push([this.day, t]);
    this.day++;
    return done;
  }
}
// 65 → [], 70 → [[0,1]], 62 → [], 61 → [], 68 → [[3,1],[2,2]]
```

메모리가 걱정이라면 스택에 남은 날 수가 문제다. 기온이 계속 내려가면 끝없이 쌓인다. 실무라면 "30일 넘게 기다리면 포기한다"처럼 상한을 두고 스택 바닥(가장 오래된 날)부터 버린다. 바닥을 버려야 하니 그때는 덱이 필요하다.

### 왼쪽으로 가장 가까운 더 따뜻한 날이라면

방향만 바꾸면 된다. 오른쪽에서 왼쪽으로 꺼내며 답을 적거나, 왼쪽에서 오른쪽으로 후보를 남기는 방식이다. 주가에서 "오늘 가격 이하였던 날이 며칠 연속인가"를 묻는 LeetCode 901 Online Stock Span이 이 형태다. 스택에 `[가격, 묶인 날 수]`를 쌓아 두고, 오늘 가격 이하인 칸을 꺼내며 날 수를 더한다. `100, 80, 60, 70, 60, 75, 85`를 넣으면 `1, 1, 1, 2, 1, 4, 6`이 나온다.

### 다른 배열의 값마다 다음 큰 값을 묻는다면

LeetCode 496 Next Greater Element I은 `nums2`에 단조 스택을 한 번 돌려 "값 → 다음 큰 값"을 해시맵에 담고, `nums1`의 값마다 맵에서 읽는다. O(n + m)이다. 해시맵은 [해시맵 글](/posts/ds-hash-map)에 있다.

### 양쪽으로 처음 작은 값을 찾는다면

"오른쪽에서 처음 나보다 작은 값"과 "왼쪽에서 처음 나보다 작은 값"을 동시에 구하면, 그 사이가 내가 가장 낮은 구간이 된다. 이 구간의 넓이를 묻는 게 [Largest Rectangle in Histogram](/posts/leetcode-largest-rectangle-in-histogram)이고, 이 문제의 단조 스택을 방향만 바꿔 그대로 쓴다. 양쪽 벽 사이에 고이는 물을 묻는 [Trapping Rain Water](/posts/leetcode-trapping-rain-water)도 단조 스택으로 풀 수 있다.

## 기다리는 날들은 늘 기온이 내려가는 순서다

이중 반복문은 같은 날들을 여러 번 비교해서 느리다. 아직 답을 못 찾은 날들은 기온이 내려가는 순서로 줄을 서게 되고, 새 날이 오면 그보다 낮은 날들만 줄 끝에서 빠지며 답을 얻는다. 날마다 한 번 들어가고 한 번 빠지니 이중 반복문 모양이어도 O(n)이다. 꺼내는 조건은 문제의 "더 높은"을 그대로 쓴 `<`이고, 같은 값이 이어지는 입력으로 확인한다.

## 면접에서 나올 만한 질문

### 단조 스택이 무엇이고 이 문제에서 왜 쓰나요?

스택 안의 값이 한 방향으로 정렬된 상태를 유지하도록, 새 값이 들어오기 전에 규칙을 깨는 값들을 꺼내는 스택이다. 이 문제에서 아직 더 따뜻한 날을 못 만난 날들은 기온이 내려가는 순서일 수밖에 없다. 그래서 새 날이 맨 위보다 따뜻하면 맨 위의 답이 바로 정해지고, 반복 비교 없이 O(n)에 끝난다.

### 반복문이 두 겹인데 왜 O(n)인가요?

`while`이 한 번 돌 때마다 스택에서 원소가 하나 빠지는데, 원소마다 한 번 들어가고 많아야 한 번 빠진다. 그래서 전체 실행에서 `while`이 도는 횟수의 합이 n을 넘지 않는다. 한 번에 많이 돌 수는 있지만 전체 합이 n으로 묶이는 분할 상환 O(n)이다.

### 스택에 왜 기온이 아니라 인덱스를 넣나요?

답이 "며칠 뒤"라는 거리라서 꺼낼 때 그날의 위치가 필요하다. 인덱스만 있으면 기온은 배열에서 다시 읽을 수 있으니 인덱스 하나로 둘 다 얻는다. 기온만 넣으면 거리를 계산할 수 없다.

### 비교를 `<=`로 쓰면 어떻게 되나요?

같은 기온을 따뜻해진 것으로 쳐서 답이 틀린다. `[70, 70, 75]`에서 정답 `[2, 1, 0]` 대신 `[1, 1, 0]`이 나온다. 꺼내는 조건이 곧 답이 되는 조건이라 문제의 "더 높은"을 그대로 쓴 `<`가 맞다. 오른쪽에서 왼쪽으로 후보를 버리는 방식에서는 반대로 `<=`가 맞다.

### 추가 공간을 O(1)로 줄일 수 있나요?

오른쪽에서 왼쪽으로 가면서 이미 구한 답 배열을 따라 건너뛰면 된다. `j`일이 `i`일보다 따뜻하지 않으면 `j + answer[j]`로 건너뛰고, `answer[j]`가 0이면 `i`의 답도 0이다. 건너뛰는 경로가 단조 스택의 후보와 같아서 시간도 분할 상환 O(n)이다.

### 날마다 기준 온도가 다르면 어떻게 하나요?

"i일 뒤로 x도 이상인 첫날"처럼 기준값이 질의마다 바뀌면 단조 스택은 쓸 수 없다. 스택이 "그날 기온보다 높은 날"이라는 고정된 기준으로 정리된 구조이기 때문이다. 구간 최댓값을 담은 sparse table이나 세그먼트 트리를 만들어 두고, 큰 걸음부터 건너뛰거나 이분 탐색으로 첫 위치를 찾으면 질의마다 O(log n)이다.

### 데이터가 실시간으로 들어오면 어느 풀이를 쓰나요?

왼쪽에서 오른쪽 단조 스택이다. 미래 데이터를 보지 않고, 새 기온이 올 때마다 스택에서 풀리는 날들을 바로 알려 줄 수 있다. 기온이 계속 내려가면 스택이 끝없이 커지니, 대기 기간에 상한을 두고 오래된 날을 버리려면 덱으로 바꾼다.
