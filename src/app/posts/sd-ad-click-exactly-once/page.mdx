이 시리즈에서 이 글의 자리: 앞 글 [㊹ 광고 클릭 집계 ①: 이벤트 시간과 윈도](/posts/sd-ad-click-stream-windows)에서 클릭을 1분 칸으로 세는 구조와 늦게 온 클릭을 다루는 법을 정했다. 이 글은 같은 장의 두 번째 글로, 같은 클릭을 두 번 세지도 빠뜨리지도 않는 법과 하루치를 다시 세어 맞추는 대사, 한 광고에 클릭이 몰리는 핫스팟을 다룬다. 다음 글은 새 사례인 [㊻ 호텔 예약: 이중 예약 막기](/posts/sd-hotel-double-booking)다.

새벽에 집계 노드 하나가 메모리 부족으로 재시작됐다고 하자. 다음 날 광고주가 묻는다. "12시 00분 클릭이 11번으로 찍혀 있는데, 우리 쪽 로그로는 8번이다." 노드가 다시 뜨면서 이미 센 구간을 한 번 더 읽어 센 것이다. 반대로 어떤 날은 숫자가 모자란다. 이 글은 이 두 방향의 오차가 어디서 생기는지 하나씩 재현하고 막는다.

메시지가 몇 번 전달되는지에 대한 일반론, 즉 최대 한 번, 최소 한 번, 정확히 한 번의 뜻과 Kafka의 멱등 프로듀서·트랜잭션은 [메시지 전달 보장](/posts/message-delivery-semantics)에서 다뤘다. 요청 하나를 한 번만 처리하는 API 쪽 방법은 [멱등성 키](/posts/idempotency-key)에 있다. 여기서는 그 원리를 광고 집계라는 한 시스템에 끝까지 적용해 본다.

## 노드 하나가 죽었다 살아나면

가장 작은 버전부터 보자. 소비자 하나가 Kafka에서 클릭을 4개씩 읽어 광고별로 더하고, 결과를 DB에 더한 뒤, 어디까지 읽었는지(오프셋)를 Kafka에 커밋한다. 오프셋은 "다음에 읽을 번호"를 적어 두는 책갈피다. 소비자가 죽었다 살아나면 마지막으로 커밋한 오프셋부터 다시 읽는다. 책갈피의 자세한 동작은 [Kafka 기초](/posts/kafka-basics)에 있다.

이 구조에서 두 가지를 저장한다. 센 결과와 책갈피다. 둘을 따로 저장하는 한, 둘 사이에서 죽는 순간이 반드시 생긴다. 결과는 썼는데 책갈피는 못 옮겼거나, 책갈피는 옮겼는데 결과는 못 썼거나. 앞의 경우는 다시 읽어 두 번 세고, 뒤의 경우는 건너뛰어 빠뜨린다. 이 글의 절반은 이 틈을 없애는 이야기다.

## 같은 클릭이 두 번 오는 길은 둘이다

중복은 출처가 둘이고, 막는 법도 다르다.

하나는 보내는 쪽의 재전송이다. 앱이 클릭을 보냈는데 응답을 못 받으면 다시 보낸다. 서버는 이미 받았으니 같은 클릭이 원본 큐에 두 번 들어간다. 원본 큐 안에서 이미 두 줄이 된 것이라, 큐를 아무리 정확히 한 번 읽어도 두 번 센다.

다른 하나는 처리하는 쪽의 재처리다. 원본 큐에는 한 번만 있는데, 집계 노드가 죽었다 살아나며 같은 구간을 다시 읽어 센다. 위의 새벽 장애가 이쪽이다.

앞의 것은 클릭마다 고유 번호를 붙여 걸러야 하고, 뒤의 것은 결과와 책갈피를 함께 저장해야 한다. 하나만 막아서는 숫자가 맞지 않는다. 일부러 같은 클릭을 반복해 보내는 부정 클릭은 또 다른 문제다. 이건 행동 패턴으로 판단하는 별도의 위험 탐지 시스템이 맡는다.

## 클릭마다 번호를 붙여 거른다

보내는 쪽 재전송을 막으려면 클릭이 만들어지는 순간 고유 번호(`click_id`)를 붙인다. 앱이 재전송할 때도 같은 번호를 쓴다. 집계 노드는 최근에 본 번호를 기억해 두고, 이미 본 번호면 세지 않는다.

모든 번호를 영원히 기억할 수는 없다. 그래서 기억하는 기간을 정한다. 10분 동안 기억하도록 만들어 돌려 봤다.

```js
// dedupe.js: click_id를 10분 동안 기억한다
const TTL = 600;
const seen = new Map();                   // click_id -> 처음 본 시각
function accept(clickId, now) {
  for (const [id, t] of seen) { if (t <= now - TTL) seen.delete(id); else break; }  // 오래된 것부터 지운다
  if (seen.has(clickId)) return "duplicate";
  seen.set(clickId, now); return "counted";
}
```

```text
t=  0s c-101 -> counted  (remembering 1)
t=  2s c-102 -> counted  (remembering 2)
t=  3s c-101 -> duplicate  (remembering 2)
t= 30s c-103 -> counted  (remembering 3)
t=400s c-102 -> duplicate  (remembering 3)
t=700s c-101 -> counted  (remembering 1)
ids to remember at 5x peak: 34,722,222, at ~64 B each: 2222 MB
```

3초 뒤의 재전송과 400초 뒤의 재전송은 걸렀다. 그런데 오프라인 큐에 남아 있다가 700초 뒤에 온 c-101은 이미 잊은 뒤라 한 번 더 셌다. 기억하는 기간보다 늦게 오는 중복은 이 방식으로 못 막는다. 기간을 늘리면 메모리가 는다. 하루 10억 클릭이 평균의 5배로 몰릴 때 10분 동안 기억할 번호는 약 3,470만 개다. 번호 하나에 64바이트를 잡으면 2.2GB다. 집계 노드가 광고 번호로 나뉘어 있으니 노드마다 자기 몫만 기억하면 된다. 메모리를 더 줄여야 하면 "없다"는 답만 확실한 [블룸 필터](/posts/bloom-filter)로 1차 판별을 하고, "있을지도 모른다"일 때만 정확한 저장소에 묻는다.

기억하는 기간보다 늦게 온 중복과 다른 노드로 흩어진 중복은 결국 하루치 대사가 잡는다. 이 글 뒤쪽에서 다룬다.

## 오프셋을 언제 저장하나

이제 처리하는 쪽의 재처리다. 클릭 12개(ad001이 8개, ad002가 4개)를 4개씩 세 묶음으로 처리하는 소비자를 Node 22로 만들고, 두 번째 묶음에서 실제로 `process.exit(1)`로 프로세스를 죽였다. 결과는 SQLite 파일에, 책갈피는 따로 파일에 저장한다. 책갈피 파일이 Kafka 브로커에 커밋한 오프셋 역할을 한다. 죽은 뒤 같은 프로그램을 다시 띄워 끝까지 돌린다.

```js
// eo.js 일부: 세 가지 순서
if (strategy === "commit-first") {         // 책갈피 먼저, 결과 나중
  commitKafka(end); crash("after-commit"); writeResults();
} else if (strategy === "write-first") {   // 결과 먼저, 책갈피 나중
  writeResults(); crash("after-write"); commitKafka(end);
} else {                                   // 결과와 책갈피를 같은 DB, 같은 트랜잭션에
  db.exec("BEGIN");
  writeResults();
  db.prepare("INSERT INTO offsets (topic, part, next) VALUES ('clicks', 0, ?) ON CONFLICT (topic, part) DO UPDATE SET next = excluded.next").run(end);
  crash("before-commit");
  db.exec("COMMIT");
}
```

```text
truth: ad001=8 ad002=4
== commit-first
  [commit-first] start from offset 0
  [commit-first] crash after-commit (batch 4-7)
  [commit-first] start from offset 8
  [commit-first] done
  result: ad001=5 ad002=3
== write-first
  [write-first] start from offset 0
  [write-first] crash after-write (batch 4-7)
  [write-first] start from offset 4
  [write-first] done
  result: ad001=11 ad002=5
== atomic
  [atomic] start from offset 0
  [atomic] crash before-commit (batch 4-7)
  [atomic] start from offset 4
  [atomic] done
  result: ad001=8 ad002=4
```

책갈피를 먼저 옮기면 4~7번 묶음의 결과를 쓰기 전에 죽었고, 살아난 소비자는 8번부터 읽었다. 4개를 빠뜨려 ad001=5, ad002=3이 됐다. 이게 최대 한 번이다. 결과를 먼저 쓰면 4~7번을 이미 더한 뒤 책갈피를 못 옮기고 죽었고, 살아난 소비자는 4번부터 다시 읽어 그 묶음을 한 번 더 더했다. ad001=11, 새벽 장애의 그 숫자다. 이게 최소 한 번이다.

세 번째는 결과와 책갈피를 같은 DB의 한 트랜잭션에 넣었다. 커밋 직전에 죽자 SQLite가 트랜잭션을 통째로 되돌렸다. 결과도 책갈피도 4번 이전 그대로다. 살아난 소비자는 책갈피를 Kafka가 아니라 DB에서 읽어 4번부터 다시 했고, 숫자는 정확히 8과 4가 됐다. 둘이 함께 저장되거나 함께 버려지니 사이의 틈이 없다. 아래 그림은 결과를 먼저 쓰는 경우에 두 번 세는 순서다.

## 결과와 책갈피를 한 곳에 둔다

정리하면 방법은 이렇다. 결과를 쓰는 곳에 책갈피도 함께 쓰고, 둘을 한 트랜잭션으로 묶는다. 다시 시작할 때는 그 저장소에서 책갈피를 읽는다. Kafka에 따로 커밋한 오프셋은 참고용일 뿐이다.

그런데 결과와 책갈피를 같은 곳에 둘 수 없는 구조가 있다. 앞 글의 큰 그림에서 집계 서비스는 결과를 DB가 아니라 두 번째 큐로 보냈다. 이유가 여기 있다. 결과도 Kafka 토픽이고 원본도 Kafka 토픽이면, Kafka 트랜잭션 하나에 "결과 토픽에 쓰기"와 "원본 토픽의 오프셋 커밋"을 함께 담을 수 있다. 읽고, 처리하고, 쓰는 일이 Kafka 안에서 한 번에 확정된다. 이 기능의 동작과 한계는 [메시지 전달 보장](/posts/message-delivery-semantics)의 트랜잭션 부분에 있다.

그다음 구간, 즉 결과 큐에서 집계 DB로 옮기는 쪽은 다시 같은 문제가 생긴다. 여기서는 두 가지 중 하나를 쓴다. DB에 결과와 함께 결과 큐의 책갈피를 한 트랜잭션으로 쓰거나, 쓰기를 여러 번 해도 결과가 같은 덮어쓰기로 바꾸거나다. 아래 그림에서 다음을 누르면 클릭이 두 구간을 지나며 어떻게 한 번만 반영되는지 보인다.

결국 "정확히 한 번"은 구간마다 받는 쪽이 중복을 알아보게 만들어 이어 붙인 결과다. 한 구간이라도 빠지면 그 자리에서 두 번 세거나 빠뜨린다. 면접에서 "정확히 한 번을 보장한다"고 말하면 "어디서 어디까지요?"가 바로 따라온다. 구간을 나눠 각각 어떻게 지키는지 말할 수 있어야 한다.

## 더하지 말고 덮어쓰면

DB 구간에는 트랜잭션 없이 푸는 더 간단한 길이 있다. 앞의 실험에서 두 번 센 이유는 결과를 "3을 더하라"로 썼기 때문이다. 같은 지시를 두 번 받으면 6이 더해진다. 결과를 "12:00 칸의 ad001은 8이다"처럼 값 자체로 쓰면, 몇 번을 다시 써도 8이다. 여러 번 해도 결과가 같은 성질을 멱등성이라고 한다.

이렇게 하려면 집계 노드가 칸의 누적값을 들고 있다가 매번 칸 전체의 값을 내보내야 한다. 앞 글에서 본 "닫은 칸을 고쳐 다시 내기"와도 잘 맞는다. 늦은 이벤트로 8이 9가 되면 9를 다시 쓰면 된다. 다만 순서가 뒤바뀌어 9가 먼저, 8이 나중에 도착하면 8로 되돌아간다. 그래서 값마다 칸의 버전(몇 번째로 고친 결과인지)을 붙이고, DB는 더 큰 버전일 때만 덮어쓴다.

```sql
-- PostgreSQL: 더 새로운 버전일 때만 덮어쓴다
INSERT INTO ad_minute_counts (ad_id, minute, filter_id, cnt, version)
VALUES ('ad001', '2026-10-22 12:00', 'all', 9, 2)
ON CONFLICT (ad_id, minute, filter_id) DO UPDATE
  SET cnt = EXCLUDED.cnt, version = EXCLUDED.version
  WHERE ad_minute_counts.version < EXCLUDED.version;
```

덮어쓰기가 되면 DB 구간은 최소 한 번으로 보내도 결과가 정확하다. 실무에서는 트랜잭션을 쓰는 것보다 이쪽이 단순하고 빠른 경우가 많다. 대신 집계 노드가 칸의 상태를 잃지 않아야 한다. 그 이야기가 다음이다.

## 메모리에 있던 칸은 스냅샷으로 지킨다

집계 노드는 1분 칸, 최근 3분 상위 N개, 최근에 본 `click_id` 같은 상태를 메모리에 들고 있다. 노드가 죽으면 이 상태가 사라진다. 책갈피만 되돌려 다시 읽으면 될 것 같지만, 상위 N개처럼 몇 분치 입력이 쌓여야 만들어지는 상태는 처음부터 다시 쌓으려면 오래 걸린다.

그래서 주기적으로 상태를 통째로 떠서 영구 저장소에 둔다. 이게 스냅샷이다. 이때 스냅샷에 그 순간의 책갈피를 꼭 함께 적는다. "오프셋 4000까지 반영한 상태가 이것"이라는 짝이 맞아야, 복구할 때 스냅샷을 불러오고 4000부터 다시 읽으면 정확히 이어진다. 짝이 어긋나면 그 사이 구간을 두 번 세거나 빠뜨린다. 앞에서 결과와 책갈피를 한 트랜잭션에 둔 것과 같은 원리를 상태에 적용한 것이다. Flink의 체크포인트가 이 일을 한다.

## 하루가 끝나면 원본으로 다시 센다

여기까지 해도 실시간 숫자가 틀릴 수 있는 길이 남는다. 허용 지연보다 늦게 온 클릭, 기억 기간보다 늦게 온 중복, 집계 코드의 버그다. 그래서 하루가 끝나면 원본 저장소에 쌓아 둔 클릭으로 같은 칸을 다시 세고, 실시간 결과와 맞춰 본다. 이걸 대사(reconciliation)라고 한다. 은행이 장부와 실제 잔고를 맞춰 보는 일과 같은 이름이다.

대사는 배치 작업이다. 원본을 `click_id`로 한 번 거른 뒤 (광고, 분)마다 세고, 집계 DB의 값과 칸마다 비교해 다른 칸을 뽑는다. 일부러 세 가지 오류를 섞어 돌려 봤다. 늦게 온 c3를 놓친 칸, 재처리 때 중복으로 센 칸, 실시간 쪽이 아예 내지 못한 칸이다.

```text
ad     minute expected actual
ad001  12:00         3      2  diff -1
ad002  12:00         1      2  diff +1
ad003  12:02         1      0  diff -1
```

세 칸이 모두 잡혔다. 원본 쪽에 같은 클릭 c6이 두 번 남아 있었지만 `click_id`로 걸러 1로 셌다. 원본도 중복을 품고 있을 수 있으니 대사에서도 거른다. 직접 만들어 보자. 원본은 `[광고, 분, click_id]`, 실시간 결과는 `[광고, 분, 수]`로 들어온다.

  //       한쪽에만 있는 칸은 없는 쪽을 0으로 본다

  solution={`function reconcile(raw, agg) {
  const seen = new Set(), expected = new Map();
  for (const [ad, minute, clickId] of raw) {
    if (seen.has(clickId)) continue;               // 원본의 중복도 거른다
    seen.add(clickId);
    const k = ad + "|" + minute;
    expected.set(k, (expected.get(k) || 0) + 1);
  }
  const actual = new Map(agg.map(([ad, minute, c]) => [ad + "|" + minute, c]));
  const out = [];
  for (const k of new Set([...expected.keys(), ...actual.keys()])) {
    const e = expected.get(k) || 0, a = actual.get(k) || 0;
    if (e !== a) { const [ad, minute] = k.split("|"); out.push([ad, minute, e, a]); }
  }
  return out.sort((x, y) => (x[0] < y[0] ? -1 : x[0] > y[0] ? 1 : x[1] < y[1] ? -1 : x[1] > y[1] ? 1 : 0));
}`}

다른 칸이 나오면 원본으로 센 값을 확정값으로 삼아 집계 DB를 고친다. 앞에서 본 덮어쓰기가 여기서도 쓰인다. 고친 칸 수와 차이의 합은 그 자체로 중요한 지표다. 평소 0.1% 안팎이던 차이가 어느 날 2%가 되면 실시간 경로 어딘가가 고장 난 것이다. 대사는 오류를 고치는 장치이면서 실시간 경로의 건강을 재는 장치다. 큰 배치를 나눠 돌리고 실패한 부분만 다시 하는 법은 [배치 처리](/posts/batch-processing)에 있다.

## 다시 계산하는 길을 하나로 둔다

대사나 버그 수정으로 지난 기간을 다시 계산할 일이 생긴다. 이때 실시간 경로와 별도로 배치 전용 코드를 두는 구조를 람다 아키텍처라고 부른다. 빠른 스트림 경로와 정확한 배치 경로가 나란히 돌고, 둘의 결과를 합쳐 보여 준다. 문제는 같은 집계 규칙을 두 벌의 코드로 유지해야 한다는 점이다. 스트림 쪽 버그를 고쳤는데 배치 쪽을 안 고치면 두 결과가 영영 안 맞는다.

카파 아키텍처는 길을 하나로 둔다. 다시 계산할 때도 원본을 같은 스트림 집계 코드에 다시 흘려 넣는다. 원본 저장소에서 지난 기간의 클릭을 읽어 다시 계산 전용 집계 노드에 넣고, 결과는 같은 결과 큐로 보내 덮어쓴다. 실시간 집계 노드와 자원을 나눠 쓰지 않게 다시 계산용 노드는 따로 띄운다.

카파 쪽의 비용은 다시 계산이 느릴 수 있다는 것이다. 스트림 엔진이 하루치를 다시 흘리는 데는 배치 엔진보다 시간이 더 들 수 있다. 그래도 규칙이 한 벌이라는 장점이 커서, 이 문제에서는 카파 쪽이 자주 선택된다. 대사 자체는 비교만 하는 단순한 배치라서 따로 두어도 규칙 중복 문제가 작다.

## 광고 하나에 클릭이 몰리면

앞 글에서 클릭을 광고 번호로 나눠 집계 노드에 보냈다. 같은 광고는 한 노드가 혼자 센다. 그런데 큰 행사 광고 하나가 전체 클릭의 40%를 받으면 어떻게 될까. 1분 동안 클릭 10만 개, 그중 40%가 ad007인 경우를 노드 4대로 나눠 봤다.

```js
// hotspot.js 일부: 몰리는 광고만 키를 4개로 쪼갠다
run("key = ad_id", (c) => c.ad);
run("hot key split x4", (c) => (HOT.has(c.ad) ? `${c.ad}#${h(c.id) % SPLIT}` : c.ad));
```

```text
key = ad_id        node load 14188 / 15178 / 56016 / 14618  max/avg 2.24  ad007 total 40705
hot key split x4   node load 24463 / 25322 / 25484 / 24731  max/avg 1.02  ad007 total 40705
```

광고 번호로만 나누면 ad007을 맡은 노드 하나가 5만 6천 개를 받는다. 평균의 2.24배다. 노드를 아무리 더해도 ad007은 한 노드에만 가니 소용이 없다. 몰리는 광고만 키 뒤에 0~3을 붙여(`ad007#0`~`ad007#3`) 네 노드에 흩으면 노드마다 2만 5천 개 안팎으로 고르게 된다. 각 노드는 자기 몫의 ad007만 세고, 그다음 단계에서 네 조각을 더해 ad007의 1분 값을 만든다. 더한 값은 40,705로 쪼개기 전과 같다. 이번에는 네 조각의 해시가 서로 다른 노드에 떨어졌지만, 조각끼리 같은 노드에 겹칠 수도 있다. 그래서 조각 수를 노드 수보다 넉넉히 두거나, 몰리는 키의 조각은 노드에 직접 나눠 배정한다.

이 방법은 더하기처럼 쪼개서 계산한 뒤 합칠 수 있는 집계에만 통한다. 합계, 건수, 최댓값은 된다. 서로 다른 사용자 수처럼 조각끼리 겹칠 수 있는 값은 그냥 더하면 틀린다. 그런 값은 조각마다 [HyperLogLog](/posts/hyperloglog) 같은 합칠 수 있는 근사 구조를 만들어 합치거나, 쪼개는 기준을 사용자 번호로 바꿔 겹치지 않게 한다. 어떤 광고가 몰리는지 미리 알 수 없다면, 단계 하나를 더 둬서 모든 키를 노드 안에서 먼저 조금 합치고(지역 집계) 그 결과만 다음 단계로 보내는(전역 집계) 방식이 자동으로 몰림을 줄인다.

## 집계가 맞는지 지켜보는 숫자

돈이 걸린 집계는 빠른 것만큼 맞는 게 중요하다. 그래서 일반 서비스 지표에 더해 정확성을 재는 숫자를 지켜본다.

클릭이 일어난 시각에서 결과가 DB에 쓰인 시각까지의 지연을 단계별로 찍어 둔다. 어느 단계에서 늘었는지 바로 보인다. 원본 큐와 결과 큐의 컨슈머 랙은 처리량이 모자란지 알려 준다. Kafka는 메시지를 지우지 않고 쌓아 두는 로그라서 "큐에 몇 개 남았나"보다 랙을 본다.

정확성 쪽으로는 늦어서 따로 뺀 클릭 수, `click_id`로 걸러 낸 중복 수, 대사에서 고친 칸 수와 차이의 합을 본다. 셋 다 평소의 범위가 있다. 중복 수가 갑자기 열 배가 되면 앱 쪽 재전송 로직이 고장 났거나 부정 클릭이 시작된 것이다. 대사 차이가 커지면 실시간 경로의 버그다.

흔한 실수 하나를 적어 둔다. 정확히 한 번을 Kafka 설정 하나로 얻을 수 있다고 믿고 DB 구간을 그냥 더하기로 두는 경우다. Kafka 트랜잭션은 Kafka 안에서만 지켜진다. DB에 쓰는 순간부터는 결과와 책갈피를 함께 쓰거나 덮어쓰기로 바꾸지 않으면, 이 글 맨 앞의 11이 다시 나온다.

## 다음에 읽을 글

같은 클릭이 두 번 들어오는 길은 보내는 쪽의 재전송과 처리하는 쪽의 재처리, 둘이다. 앞의 것은 `click_id`를 일정 기간 기억해 거르고, 뒤의 것은 결과와 책갈피를 한 트랜잭션에 쓰거나 결과를 덮어쓰기로 바꿔 막는다. 메모리의 칸은 책갈피와 짝지은 스냅샷으로 지킨다. 그래도 남는 오차는 하루치 원본으로 다시 센 대사가 잡고, 다시 계산은 같은 집계 코드를 지나게 한다. 몰리는 광고는 키를 쪼개 나눠 센 뒤 더한다.

이걸로 광고 클릭 집계 장을 마친다. 다음 글 [㊻ 호텔 예약: 이중 예약 막기](/posts/sd-hotel-double-booking)에서는 "한 번만"이 다른 모양으로 나온다. 같은 방을 두 사람이 동시에 잡으려 할 때 하나만 성공시키는 문제다. 돈이 오가는 흐름에서 같은 원리를 더 엄격하게 쓰는 사례는 [결제 신뢰성](/posts/sd-payment-reliability)에 있다.

## 면접에서 나올 만한 질문

### 광고 클릭 집계에서 최소 한 번이면 안 되나요?

청구에 쓰이는 숫자라 안 된다. 최소 한 번은 장애 때 같은 구간을 다시 처리해 부풀린다. 실험에서 묶음 하나를 다시 읽자 ad001이 8에서 11이 됐다. 하루 수십억 클릭에서 몇 퍼센트만 부풀어도 청구 금액이 크게 어긋나니, 구간마다 중복을 막아 정확히 한 번으로 만든다.

### 같은 클릭이 두 번 들어오는 원인은 뭔가요?

보내는 쪽 재전송과 처리하는 쪽 재처리 두 가지다. 앱이 응답을 못 받아 다시 보내면 원본 큐에 두 줄이 생기고, 집계 노드가 죽었다 살아나며 같은 구간을 다시 읽으면 결과에 두 번 더해진다. 앞의 것은 `click_id`로 거르고, 뒤의 것은 결과와 책갈피를 함께 저장해 막는다. 하나만 막으면 숫자가 맞지 않는다.

### 오프셋을 결과보다 먼저 커밋하면 어떻게 되나요?

결과를 쓰기 전에 죽으면 그 묶음을 건너뛰어 빠뜨린다. 실험에서 4개를 잃어 ad001이 8에서 5가 됐다. 반대로 결과를 먼저 쓰면 두 번 센다. 둘을 따로 저장하는 한 그 사이에서 죽는 순간이 생기니, 같은 저장소의 한 트랜잭션에 쓰고 재시작할 때 그 저장소에서 책갈피를 읽는다.

### 집계 결과를 왜 DB에 바로 쓰지 않고 큐에 한 번 더 넣나요?

결과도 Kafka 토픽이면 결과 쓰기와 원본 오프셋 커밋을 Kafka 트랜잭션 하나로 묶을 수 있다. 집계 구간이 Kafka 안에서 한 번에 확정된다. 그 뒤 DB 구간은 결과 큐의 책갈피를 DB에 함께 쓰거나, 버전을 붙인 덮어쓰기로 만들어 따로 지킨다. DB가 느려도 집계가 멈추지 않는 장점도 있다.

### 분산 트랜잭션 없이 정확히 한 번을 만들 수 있나요?

받는 쪽 쓰기를 멱등하게 만들면 된다. "3을 더하라" 대신 "이 칸은 8이다"처럼 값 자체를 쓰고, 칸마다 버전을 붙여 더 새 버전일 때만 덮어쓰게 한다. 그러면 같은 결과를 몇 번 받아도 값이 같아서 최소 한 번으로 보내도 정확하다. 대신 집계 노드가 칸의 누적값을 잃지 않게 스냅샷으로 지켜야 한다.

### 집계 노드가 죽으면 메모리의 상태는 어떻게 복구하나요?

주기적으로 상태를 스냅샷으로 떠서 영구 저장소에 두고, 그 순간의 책갈피를 함께 적는다. 새 노드는 스냅샷을 불러오고 그 책갈피부터 다시 읽는다. 상태와 책갈피의 짝이 맞아야 그 사이 구간을 한 번만 반영한다. 스냅샷 간격은 복구 때 다시 읽을 양과 평소 부하 사이의 맞바꿈이다.

### 실시간 결과가 맞는지 어떻게 확인하나요?

하루가 끝나면 원본 저장소의 클릭을 `click_id`로 거른 뒤 다시 세고, 칸마다 실시간 결과와 비교하는 대사를 돌린다. 다른 칸은 원본 값으로 덮어써 확정한다. 고친 칸 수와 차이의 합을 지표로 두면, 평소보다 커졌을 때 실시간 경로의 고장을 알아챌 수 있다.

### 광고 하나에 클릭이 몰리면요?

광고 번호로 나누면 그 광고를 맡은 노드 하나가 몰린 양을 다 받는다. 실험에서 40%를 받는 광고 때문에 한 노드가 평균의 2.24배를 받았다. 몰리는 광고의 키를 여러 조각으로 쪼개 여러 노드가 나눠 세고 다음 단계에서 더하면 1.02배로 고르게 된다. 더할 수 있는 집계에만 통하고, 고유 사용자 수 같은 값은 HyperLogLog처럼 합칠 수 있는 구조를 쓴다.
