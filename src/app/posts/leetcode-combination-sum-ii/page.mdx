카드 명세서에 4만 원 환불이 한 줄 들어왔는데, 어느 주문을 취소한 환불인지 적혀 있지 않았다. 그날 주문은 3만, 1만, 3만, 2만, 1만 원 다섯 건이었다. 주문 몇 건을 골라 합이 정확히 4만 원이 되는 경우를 모두 찾으면 후보가 좁혀진다. 주문은 한 번씩만 취소할 수 있고, 금액이 같은 주문은 여러 건 있을 수 있다. 화면에는 "1만 + 3만"을 한 번만 보여 줘야 한다. 1만 원짜리가 두 건이라고 같은 조합을 두 번 보여 주면 헷갈린다.

[LeetCode 40. Combination Sum II](https://leetcode.com/problems/combination-sum-ii/)가 이 계산이다. 같은 수를 여러 번 쓸 수 있었던 [Combination Sum](/posts/leetcode-combination-sum)과 달리 후보 하나는 한 번만 쓰고, 후보에 같은 값이 섞여 있다. 같은 값 때문에 생기는 겹침을 막는 조건은 [Subsets II](/posts/leetcode-subsets-ii)에서 자세히 봤다. 이 글은 그 조건에 "합이 넘치면 멈춘다"를 더할 때 무엇이 달라지는지, 후보가 100개일 때 왜 거르는 방식이 무너지는지를 본다. 백트래킹의 기본 틀은 [재귀와 백트래킹 글](/posts/recursion-backtracking)에 있다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 한 장씩만 쓸 수 있는 후보로 합을 맞춘다

정수 배열 `candidates`와 정수 `target`이 주어진다. 후보 중 몇 개를 골라 합이 정확히 `target`이 되는 조합을 모두 돌려준다. 후보 하나는 조합 안에서 한 번만 쓴다. 후보에 같은 값이 여러 개 있을 수 있는데, 같은 조합(값의 개수가 같은 조합)은 한 번만 넣는다. 답의 순서는 상관없다.

풀이를 정하는 제약은 이렇다.

- 후보는 최대 100개다. 부분집합을 전부 보면 2^100이라 절대 끝나지 않는다.
- 후보 값은 1 이상 50 이하, `target`은 30 이하다. 값이 모두 양수라 합이 넘치면 그 갈래를 버릴 수 있고, 조합의 길이도 30을 넘지 못한다.

두 번째 제약이 이 문제를 풀 수 있게 만든다. 후보는 100개라도 합이 30을 넘는 순간 멈출 수 있으니, 실제로 보는 갈래는 아주 적다. 대신 같은 값이 많으면 겹친 답이 폭발적으로 늘어나는 함정이 있다. 뒤에서 1이 100개인 입력으로 확인한다.

## [3, 1, 3, 2, 1]에서 4를 맞춰 보면

먼저 정렬하면 `[1, 1, 2, 3, 3]`이다. 두 1을 `1`, `1'`, 두 3을 `3`, `3'`으로 구분해서 합 4를 만드는 경우를 다 적어 보자.

```text
1 + 1' + 2 = 4
1 + 3      = 4
1 + 3'     = 4
1' + 3     = 4
1' + 3'    = 4
```

다섯 가지가 나오지만 따옴표를 지우면 `[1,1,2]`와 `[1,3]` 두 가지다. `[1,3]` 하나가 네 번 나왔다. 1을 고르는 방법 2가지와 3을 고르는 방법 2가지를 곱한 만큼 겹쳤다. 같은 값이 k개씩 있는 수를 여러 개 쓰는 조합은 그 곱만큼 겹친다는 뜻이다.

[Subsets II](/posts/leetcode-subsets-ii)에서 정한 약속을 그대로 쓰면 된다. 같은 값 중에서는 늘 앞의 것부터 쓴다. 1을 하나만 쓸 때는 언제나 `1`이고 `1'`은 쓰지 않는다. 그러면 `[1,3]`은 `1 + 3` 하나만 남는다. 여기에 이 문제만의 관찰이 하나 더 있다. 정렬했으니 남은 합보다 큰 후보를 만나면 그 뒤도 모두 크다. `1 + 2`까지 온 상태에서 남은 합은 1인데 다음 후보가 3이면 거기서 멈춘다.

## 겹치는 답은 Set으로 지우면 될까

[Combination Sum](/posts/leetcode-combination-sum)의 틀에서 `go(i)`를 `go(i + 1)`로 바꿔 한 번씩만 쓰게 하고, 겹치는 답은 문자열 키로 거른다. 정렬해 뒀으니 넘치면 멈추는 가지치기도 넣는다.

```js
function combinationSum2(candidates, target) {
  const a = [...candidates].sort((x, y) => x - y);
  const seen = new Set();
  const res = [];
  const path = [];

  function go(start, remain) {
    if (remain === 0) {
      const key = path.join(",");   // 정렬돼 있으니 같은 조합은 같은 키
      if (!seen.has(key)) {
        seen.add(key);
        res.push([...path]);
      }
      return;
    }
    for (let i = start; i < a.length; i++) {
      if (a[i] > remain) break;      // 뒤는 더 크니 볼 필요가 없다
      path.push(a[i]);
      go(i + 1, remain - a[i]);      // 한 번씩만 쓴다
      path.pop();
    }
  }

  go(0, target);
  return res;
}
```

`[3, 1, 3, 2, 1]`, 4에서 `[[1,1,2],[1,3]]`이 나온다. 호출은 14번이었다. 같은 입력을 다음 풀이는 8번 호출로 끝낸다.

작은 입력에서는 문제없어 보이지만 같은 값이 많으면 무너진다. 1만 n개 있고 `target`이 10이면 답은 `[1,1,…,1]`(1이 10개) 하나다. 그런데 이 코드는 n개 중 10개를 고르는 모든 방법을 다 만든 뒤에 하나만 남긴다.

```text
1이 20개, target 10:   호출   616,666번     62ms
1이 24개, target 10:   호출 4,540,386번    552ms
1이 28개, target 10:   호출 24,821,333번  3565ms
```

후보 4개를 늘릴 때마다 일곱 배 가까이 느려진다. 제약의 최대인 1이 100개, `target` 30이면 C(100, 30) ≈ 2.94 × 10^25가지를 만들어야 한다. LeetCode에서 이 풀이가 시간 초과가 나는 이유다. 가지치기는 "합이 넘치는 갈래"만 자르고, "이미 본 것과 같은 갈래"는 자르지 못한다. 겹침은 거르는 게 아니라 만들지 않아야 한다.

## 정렬하고, 같은 자리의 같은 값은 건너뛰고, 넘치면 멈춘다

for문 한 번은 "path의 다음 자리에 어떤 후보를 놓을까"를 정한다. 같은 자리에 같은 값을 두 번 놓으면 그 아래로 펼쳐지는 조합이 똑같다. 그래서 같은 for문 안에서 앞과 같은 값이면 건너뛴다. [Subsets II](/posts/leetcode-subsets-ii)와 같은 한 줄이다.

```js
if (i > start && a[i] === a[i - 1]) continue;
```

`i > start`는 "이번 for문의 첫 후보가 아니다"라는 뜻이다. 첫 후보는 앞 값과 같아도 고른다. `[1]` 다음 자리에서 첫 후보는 `1'`이고, 이걸 고르는 건 1을 하나 더 쓰는 정당한 선택이다. 그래야 `[1,1,2]`가 나온다.

여기에 Combination Sum에서 쓰던 가지치기를 붙이면 최종 코드다.

```js
function combinationSum2(candidates, target) {
  const a = [...candidates].sort((x, y) => x - y); // 같은 값을 붙이고, 작은 값부터
  const res = [];
  const path = [];

  function go(start, remain) {
    if (remain === 0) {             // 합을 정확히 맞췄다
      res.push([...path]);
      return;
    }
    for (let i = start; i < a.length; i++) {
      if (i > start && a[i] === a[i - 1]) continue; // 같은 자리에 같은 값은 한 번만
      if (a[i] > remain) break;     // 정렬돼 있으니 뒤는 모두 넘친다
      path.push(a[i]);
      go(i + 1, remain - a[i]);     // i + 1: 같은 후보를 다시 쓰지 않는다
      path.pop();
    }
  }

  go(0, target);
  return res;
}
```

정렬된 `[1, 1, 2, 3, 3]`에서 4를 찾는 과정을 따라가 보자. 초록 칸이 지금 `path`에 들어 있는 후보다.

결과는 `[[1,1,2],[1,3]]`이고 호출은 8번이다. 문제의 1이 100개짜리 입력에서는 답이 1개, 호출이 31번이었다. 첫 for문에서 1을 넣고 들어가면, 다음 단계도 첫 후보 1을 넣고, 같은 자리의 나머지 1은 전부 건너뛴다. 30번 들어가면 합이 맞는다. 거르는 풀이가 10^25가지를 만들던 입력이다.

### 두 조건의 순서와 break

for문 안에 조건이 두 개 있다. 같은 값 건너뛰기를 먼저 두든 break를 먼저 두든 답은 같다. 정렬돼 있어서 건너뛸 후보가 넘치는 후보라면 그 뒤도 넘치기 때문이다. 눈여겨볼 곳은 넘칠 때 `continue`가 아니라 `break`를 쓴 것이다. 1부터 50까지 두 번씩 있는 후보 100개에서 30을 맞추면 답은 1225개로 같은데, for문을 돈 횟수는 break가 19,777번, continue가 484,651번이었다. 24배 차이다. break가 맞으려면 반드시 오름차순으로 정렬돼 있어야 한다. 이 조건이 무너지는 경우를 뒤에서 본다.

### 복잡도를 어떻게 말하나

최악은 O(2^n · n)이라고 말할 수 있다. 부분집합을 다 볼 수 있다는 상한이고, 답 하나를 복사하는 데 길이만큼 든다. 하지만 이 문제에서는 상한이 너무 느슨하다. 값이 1 이상이라 조합 길이가 `target` 이하이고, 같은 값 건너뛰기 덕에 같은 갈래를 두 번 가지 않는다. 그래서 서로 다른 값의 개수를 d, `target`을 T라고 하면 탐색 마디는 "서로 다른 값으로 T 이하의 합을 만드는 조합 수" 정도로 묶인다. 면접에서는 "최악은 2^n이지만 양수와 작은 target 덕에 실제로는 그보다 훨씬 작고, 겹치는 갈래는 아예 가지 않는다"고 설명하면 된다. 추가 공간은 재귀 깊이와 `path`로 O(T)다.

### Python과 Java에서는

Python은 `sorted`가 새 리스트를 만든다. 재귀 깊이는 많아야 T + 1 = 31이라 기본 한도 1000을 걱정할 필요가 없다.

```python
from typing import List

def combination_sum2(candidates: List[int], target: int) -> List[List[int]]:
    cands = sorted(candidates)       # 같은 값을 붙이고, 작은 값부터 본다
    res, path = [], []

    def go(start: int, remain: int) -> None:
        if remain == 0:
            res.append(path[:])
            return
        for i in range(start, len(cands)):
            if i > start and cands[i] == cands[i - 1]:
                continue             # 같은 자리에 같은 값은 한 번만
            if cands[i] > remain:
                break                # 뒤는 더 크니 볼 필요가 없다
            path.append(cands[i])
            go(i + 1, remain - cands[i])   # 한 번씩만 쓰니 i + 1
            path.pop()

    go(0, target)
    return res
```

Java는 `Arrays.sort`가 넘겨받은 배열을 그대로 정렬한다. `int[]`는 숫자 오름차순이라 비교자가 필요 없다. 합은 30 이하라 오버플로 걱정도 없다.

```java
import java.util.*;

class Solution {
    public List<List<Integer>> combinationSum2(int[] candidates, int target) {
        Arrays.sort(candidates); // 같은 값을 붙이고 작은 값부터 본다
        List<List<Integer>> res = new ArrayList<>();
        go(candidates, 0, target, new ArrayList<>(), res);
        return res;
    }

    private void go(int[] c, int start, int remain, List<Integer> path, List<List<Integer>> res) {
        if (remain == 0) {
            res.add(new ArrayList<>(path));
            return;
        }
        for (int i = start; i < c.length; i++) {
            if (i > start && c[i] == c[i - 1]) continue; // 같은 자리에 같은 값은 한 번만
            if (c[i] > remain) break;                    // 뒤는 더 크다
            path.add(c[i]);
            go(c, i + 1, remain - c[i], path, res);
            path.remove(path.size() - 1);
        }
    }
}
```

세 언어 모두 `[3, 1, 3, 2, 1]`, 4에서 `[[1, 1, 2], [1, 3]]`을, `[2]`, 1에서 빈 목록을, 1이 100개인 입력과 30에서 답 1개를 냈다.

## 넣거나, 같은 값을 통째로 건너뛰거나

후보마다 "넣는다/안 넣는다"로 나누는 이진 트리로도 풀 수 있다. 겹침은 같은 값 중 앞의 것을 안 넣고 뒤의 것을 넣을 때 생긴다. 그러니 어떤 값을 안 넣기로 했으면 같은 값을 통째로 건너뛰고 다음 값으로 간다.

```js
function combinationSum2(candidates, target) {
  const a = [...candidates].sort((x, y) => x - y);
  const res = [];
  const path = [];

  function go(i, remain) {
    if (remain === 0) {
      res.push([...path]);
      return;
    }
    if (i === a.length || a[i] > remain) return; // 후보가 없거나, 이 값부터 다 넘친다

    path.push(a[i]);                 // a[i]를 넣는다
    go(i + 1, remain - a[i]);
    path.pop();

    let j = i + 1;                   // 안 넣기로 했으면 같은 값을 모두 건너뛴다
    while (j < a.length && a[j] === a[i]) j++;
    go(j, remain);
  }

  go(0, target);
  return res;
}
```

같은 입력에서 같은 두 답이 나온다. `a[i] > remain`이면 그 아래 갈래를 둘 다 버리는 게 break와 같은 역할이다.

이 모양은 [Subsets II](/posts/leetcode-subsets-ii)의 "안 넣으면 다 건너뛰기"에 합 조건을 더한 것이다. 원소마다 결정에 조건을 하나씩 붙이기 쉬워서, 배낭 문제처럼 무게와 가치를 함께 들고 다닐 때 이 모양이 편하다. 시작 위치 풀이와 비교하면 같은 일을 다른 트리 모양으로 하는 것뿐이라 속도도 비슷했다.

## 금액마다 몇 장을 낼지 고르기

같은 값이 여러 개 있다는 건 "값과 개수"로 바꿔 생각할 수 있다는 뜻이다. `[3, 1, 3, 2, 1]`은 1이 2개, 2가 1개, 3이 2개다. 값마다 0개부터 그 개수까지, 그리고 남은 합을 넘지 않는 만큼 고르면 된다. 같은 값 중 "어느 것"을 고를지는 처음부터 질문에 없어서 겹침이 생길 수 없다.

```js
function combinationSum2(candidates, target) {
  const count = new Map();                          // 값 → 개수
  for (const x of candidates) count.set(x, (count.get(x) || 0) + 1);
  const vals = [...count.keys()].sort((x, y) => x - y);
  const res = [];
  const path = [];

  function go(k, remain) {
    if (remain === 0) {
      res.push([...path]);
      return;
    }
    if (k === vals.length || vals[k] > remain) return;
    const v = vals[k];
    const c = count.get(v);
    let used = 0;
    for (let t = 1; t <= c && t * v <= remain; t++) { // v를 t개 낸다
      path.push(v);
      used++;
      go(k + 1, remain - t * v);
    }
    for (let t = 0; t < used; t++) path.pop();        // 낸 만큼 되돌린다
    go(k + 1, remain);                                // v를 하나도 안 낸다
  }

  go(0, target);
  return res;
}
```

결과 순서만 `[[1,3],[1,1,2]]`로 다르다. 1을 하나 낸 갈래를 먼저 끝까지 가기 때문이다.

이 문제는 값이 1~50뿐이라 후보가 많으면 같은 값이 많을 수밖에 없다. 후보가 100개면 적어도 50개는 앞의 값과 겹친다. 그래서 값 단위로 보면 트리의 깊이가 후보 수가 아니라 서로 다른 값의 수로 줄어든다. 처음 이야기처럼 데이터가 원래 "금액별 건수"로 정리돼 있다면 펼쳐서 정렬하지 않고 이 모양으로 바로 탐색하는 게 자연스럽다. `t * v <= remain` 조건이 값마다 낼 수 있는 최대 개수를 정해 주는 것도 편하다.

## 작은 합의 목록을 이어 붙여 큰 합을 만든다

`target`이 30 이하로 작으니 [동적 계획법](/posts/dynamic-programming)으로 목록을 쌓을 수도 있다. `dp[s]`를 "지금까지 본 값들로 합 s를 만드는 조합 목록"으로 둔다. 처음엔 `dp[0] = [[]]`이고 나머지는 비어 있다. 서로 다른 값 v를 하나씩 들이면서, v를 k개(1 ≤ k ≤ 개수) 붙여 `dp[s - k·v]`의 조합들로 `dp[s]`를 늘린다.

값 단위로 들이기 때문에 같은 조합이 두 번 생기지 않는다. 다만 v를 들일 때는 들이기 전의 `dp`만 읽어야 한다. 방금 v를 붙여 만든 목록을 다시 읽으면 v를 개수보다 많이 쓰게 된다. 그래서 새 배열 `next`에 쓴다.

```js
function combinationSum2(candidates, target) {
  const count = new Map();
  for (const x of candidates) count.set(x, (count.get(x) || 0) + 1);
  const vals = [...count.keys()].sort((x, y) => x - y);

  let dp = Array.from({ length: target + 1 }, () => []);
  dp[0] = [[]];                                    // 합 0은 빈 조합 하나
  for (const v of vals) {
    const c = count.get(v);
    const next = dp.map((list) => [...list]);      // v를 하나도 안 쓴 경우는 그대로
    for (let s = 1; s <= target; s++) {
      for (let k = 1; k <= c && k * v <= s; k++) { // v를 k개 붙인다
        for (const comb of dp[s - k * v]) {        // 들이기 전의 목록만 읽는다
          next[s].push([...comb, ...Array(k).fill(v)]);
        }
      }
    }
    dp = next;
  }
  return dp[target];
}
```

`[3, 1, 3, 2, 1]`, 4에서 `dp`가 채워지는 모습이다. 칸은 합 0~4이고, 초록 칸이 조합이 하나라도 있는 합이다.

## 답이 사라지는 네 가지 실수

### `i > start` 대신 `i > 0`

```js
if (i > 0 && a[i] === a[i - 1]) continue;
```

`[3, 1, 3, 2, 1]`, 4에서 `[[1,3]]` 하나만 나왔다. `[1,1,2]`가 사라졌다. `[1]` 다음 자리의 첫 후보 `1'`까지 "앞과 같은 값"으로 막았기 때문이다. 같은 값을 여러 개 쓰는 조합은 늘 이 조건에서 사라진다.

### 같은 값을 다음 칸과 비교하기

"같은 값 중 마지막 것만 쓰자"는 생각으로 이렇게 쓰기도 한다.

```js
if (i + 1 < a.length && a[i] === a[i + 1]) continue; // 다음 칸과 같으면 건너뛴다
```

이것도 `[[1,3]]`만 냈다. 같은 값 중 마지막 것만 쓰게 되니 1을 두 개 쓰는 길이 처음부터 없다. "앞의 것부터 쓴다"는 약속은 같은 값을 여러 개 쓰는 길을 열어 두지만, "마지막 것만 쓴다"는 하나만 쓰게 만든다.

### 비교자 없는 `sort()`

[Subsets II](/posts/leetcode-subsets-ii)에서는 비교자를 빼도 답이 맞았다. 같은 값만 붙어 있으면 됐으니까. 이 문제는 break 때문에 "작은 값부터"라는 성질이 꼭 필요하다.

```js
[10, 1, 2, 7, 6, 1, 5].sort(); // [1, 1, 10, 2, 5, 6, 7] 문자열 순서
```

이 배열로 target 8을 찾으면 답이 4개(`[1,1,6]`, `[1,2,5]`, `[1,7]`, `[2,6]`)여야 하는데 빈 목록이 나왔다. 첫 for문에서 1, 1 다음에 10을 만나 "넘친다, 뒤도 다 넘친다"며 break하고, 빈 path에서도 1 다음 10에서 break한다. 2, 5, 6, 7은 한 번도 보지 못한다. 에러 없이 답만 조용히 사라지는 버그라 숫자 정렬에는 반드시 `(x, y) => x - y`를 넘긴다.

### `go(i + 1)` 대신 `go(i)`

[Combination Sum](/posts/leetcode-combination-sum)에서 코드를 가져오다 흔히 남는 실수다. 같은 후보를 다시 쓸 수 있게 돼서 `[3, 1, 3, 2, 1]`, 4에서 `[[1,1,1,1],[1,1,2],[1,3],[2,2]]`가 나왔다. 1은 두 개뿐인데 네 번 썼고, 2는 하나뿐인데 두 번 썼다. 두 문제의 차이는 사실상 이 인자 하나와 건너뛰기 한 줄이다.

## 조건이 달라지면

### 조합의 개수만 달라면

목록이 필요 없으면 dp 풀이에서 목록 대신 개수를 더한다. 값 단위로 들이니 겹침 걱정이 없다.

```js
function countCombinations(candidates, target) {
  const count = new Map();
  for (const x of candidates) count.set(x, (count.get(x) || 0) + 1);
  let dp = new Array(target + 1).fill(0);
  dp[0] = 1;
  for (const [v, c] of count) {
    const next = dp.slice();                        // v를 안 쓴 경우
    for (let s = 1; s <= target; s++) {
      for (let k = 1; k <= c && k * v <= s; k++) next[s] += dp[s - k * v];
    }
    dp = next;
  }
  return dp[target];
}
```

`[3, 1, 3, 2, 1]`, 4에서 2, 1~50이 두 번씩인 100개와 30에서 1225가 나왔다. 백트래킹으로 센 개수와 같다. 서로 다른 값 d개, target T, 값마다 최대 개수 c면 O(d · T · c)이고 정렬도 필요 없다. 개수가 수십억으로 커지면 Java는 `long`, JavaScript는 2^53을 넘는지 확인해야 한다.

### 같은 수를 여러 번 써도 되면

[Combination Sum](/posts/leetcode-combination-sum)이다. `go(i)`를 넘기고, 후보가 서로 다르니 건너뛰기 조건이 필요 없다. 후보에 같은 값이 섞인 채로 여러 번 써도 된다면, 먼저 중복을 지운 뒤 Combination Sum으로 푼다. 어차피 몇 번이든 쓸 수 있으니 같은 값이 여러 개 있는 의미가 없다.

### 1~9를 k개만 써서 n을 맞추라면

LeetCode 216 Combination Sum III다. 후보가 1~9로 서로 다르고 한 번씩만 쓰니 건너뛰기 조건이 없고, `path.length === k`일 때만 합을 확인한다. k = 3, n = 7이면 `[1,2,4]` 하나다.

### 음수가 섞여 있다면

break가 틀린 가지치기가 된다. 지금 넘쳐도 뒤에 음수가 있으면 다시 맞출 수 있기 때문이다. 같은 값 건너뛰기는 그대로 쓸 수 있지만 합으로 자르는 가지치기는 버려야 해서 최악 2^n을 다 본다. 개수만 필요하면 합의 범위를 음수 쪽으로 밀어(offset) dp를 쓴다. [Target Sum](/posts/leetcode-target-sum)이 그 계산이다.

### 하나만 찾으면 된다면

재귀 함수가 찾았는지를 돌려주게 해서 처음 찾은 순간 끝까지 빠져나온다. 존재 여부만 묻는 것이면 개수 dp를 불리언으로 바꾼 부분합 문제다. [Partition Equal Subset Sum](/posts/leetcode-partition-equal-subset-sum)이 이 계산을 쓴다.

### 비슷한 문제

[Subsets II](/posts/leetcode-subsets-ii)는 합 조건이 없는 같은 틀이다. [Combination Sum](/posts/leetcode-combination-sum)은 같은 수를 여러 번 쓰는 버전이다. LeetCode 47 Permutations II는 같은 값 처리를 순열에 옮긴 것이고 [Permutations](/posts/leetcode-permutations)에 코드가 있다. [Coin Change II](/posts/leetcode-coin-change-ii)는 같은 금액을 여러 번 쓰는 조합의 개수를 dp로 센다.

## 환불 금액 맞추기에 쓰면

처음의 주문 금액 `[3, 1, 3, 2, 1]`(만 원 단위)과 환불 4만 원을 넣으면 `[1,1,2]`와 `[1,3]`이 나온다. "1만 원 두 건과 2만 원 한 건" 또는 "1만 원 한 건과 3만 원 한 건"이다. 화면에는 이 두 줄을 보여 주고, 어느 주문인지는 같은 금액의 주문 목록을 함께 보여 주면 된다.

실무에서 이걸 그대로 쓰기 전에 두 가지를 확인한다. 금액은 원 단위 정수로 다룬다. 3.3만 원 같은 소수를 부동소수점으로 더하면 `0.1 + 0.2 !== 0.3` 문제로 `remain === 0`이 영원히 참이 되지 않는다. 그리고 후보 수와 금액 범위를 본다. 주문이 수백 건이고 금액이 제각각이면 같은 값 건너뛰기가 거의 효과가 없고, 합으로 자르는 가지치기만 남는다. 그때는 답이 수천, 수만 개가 될 수 있으니 목록 전체 대신 "몇 가지인지"를 먼저 세고, 너무 많으면 날짜 같은 다른 조건으로 후보를 줄이는 게 낫다.

## 같은 값은 앞의 것부터, 넘치면 그 자리에서

후보에 같은 값이 섞이면 같은 조합이 여러 번 만들어지고, 같은 값이 많을수록 그 수가 조합 수만큼 폭발한다. 그래서 결과를 거르는 방식은 1이 100개인 입력에서 끝나지 않는다. 정렬해서 같은 값을 붙이고, 같은 for문 안에서 `i > start && a[i] === a[i - 1]`이면 건너뛰면 겹치는 갈래를 아예 가지 않는다. 정렬은 같은 값을 붙여 주는 동시에 "넘치면 뒤도 넘친다"는 break를 가능하게 한다. 두 효과 모두 숫자 오름차순일 때만 성립한다.

## 면접에서 나올 만한 질문

### Combination Sum과 무엇이 다른가요?

후보 하나를 한 번만 쓰니 재귀에 `i` 대신 `i + 1`을 넘긴다. 후보에 같은 값이 섞여 있어서 같은 조합이 여러 번 나올 수 있으니, 정렬한 뒤 같은 for문 안에서 앞과 같은 값을 건너뛴다. 넘치면 break하는 가지치기는 그대로다.

### 결과를 Set으로 걸러도 되지 않나요?

작은 입력에서는 답이 맞지만 시간 초과가 난다. 1이 100개이고 target이 30이면 답은 하나인데, 거르는 방식은 100개 중 30개를 고르는 약 2.94 × 10^25가지를 다 만든다. 겹침은 만든 뒤 지우는 게 아니라 만들지 않아야 한다. 건너뛰기 조건을 쓰면 같은 입력이 31번 호출로 끝난다.

### 왜 `i > start`인가요? `i > 0`이면 안 되나요?

막아야 하는 건 같은 자리에 같은 값을 두 번 놓는 것뿐이다. `i > 0`이면 더 깊은 단계의 첫 후보까지 막아서 같은 값을 여러 개 쓰는 조합이 사라진다. `[3, 1, 3, 2, 1]`, 4에서 `[1,1,2]`가 빠지고 `[1,3]`만 남는다.

### 정렬은 무엇을 해 주나요?

두 가지다. 같은 값을 나란히 붙여 바로 앞 칸과 비교해서 겹침을 막게 해 주고, 작은 값부터 보게 해서 넘치는 후보를 만나면 뒤를 다 버리는 break를 가능하게 한다. JavaScript에서 비교자를 빼면 문자열 순서가 돼서 break가 엉뚱한 곳에서 걸리고 답이 사라진다.

### `break` 대신 `continue`를 쓰면 어떻게 되나요?

답은 같지만 느려진다. 넘치는 후보 뒤도 다 넘치는데 끝까지 하나씩 확인하기 때문이다. 1~50이 두 번씩인 후보 100개에서 for문 반복이 19,777번에서 484,651번으로 늘었다. 반대로 정렬하지 않은 상태에서 break를 쓰면 답이 빠진다.

### 시간 복잡도는 어떻게 되나요?

상한은 O(2^n · n)이지만 이 문제에서는 너무 느슨하다. 값이 모두 양수라 조합 길이가 target 이하로 묶이고, 넘치면 끊고, 겹치는 갈래는 가지 않는다. 실제 탐색량은 서로 다른 값으로 target 이하의 합을 만드는 조합 수에 가깝다. 추가 공간은 재귀 깊이 O(target)이다.

### 개수만 필요하면 어떻게 하나요?

값마다 개수를 세고, `dp[s]`를 합 s를 만드는 조합 수로 둔 다음 값 단위로 들이며 k개씩 붙인다. 들이기 전의 dp만 읽어야 개수 제한을 지킨다. 서로 다른 값 d개, target T, 최대 개수 c면 O(d · T · c)이고 정렬도 필요 없다.
