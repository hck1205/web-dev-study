무선 이어폰 재고가 1개 남았을 때 두 사람이 동시에 사서 재고가 -1이 됐다. 주문 코드는 재고를 `SELECT`로 읽고, 0보다 크면 `UPDATE`로 1을 뺐다. 트랜잭션도 썼다. 그런데 두 요청이 같은 "재고 1"을 읽고 둘 다 통과했다. 고치려고 잠금을 걸었더니 이번에는 바쁜 시간에 `deadlock detected` 에러가 가끔 찍힌다.

왜 트랜잭션을 써도 이런 일이 생기는지, 격리 수준이 무엇을 막고 무엇을 안 막는지는 [트랜잭션과 격리 수준 글](/posts/db-transaction-isolation)에서 두 세션으로 재현했다. 이 글은 그 틈을 실제로 막는 방법을 고른다. 조건부 `UPDATE`, 비관적 잠금, 낙관적 잠금, 격리 수준 올리기를 같은 장면에서 비교하고, 잠금이 만드는 교착 상태와 오래 열린 트랜잭션, 서비스 여러 개에 걸친 작업까지 본다. SQL은 PostgreSQL 16 기준이고, 출력은 PostgreSQL 16.15에 psql 두 개를 붙여 실제로 실행한 결과다.

## 계좌, 상품, 주문 세 테이블

앞 글과 같은 테이블이다. 계좌 `accounts`(1번 kim 100,000원, 2번 lee 50,000원), 상품 `products`(1001번 무선 이어폰 재고 1개, 1002번 충전 케이스 30개, 1003번 이어팁 120개), 주문 `orders`다.

```sql
CREATE TABLE accounts (
  account_id bigint PRIMARY KEY,
  owner      text   NOT NULL,
  balance    bigint NOT NULL CHECK (balance >= 0)   -- 잔액은 음수가 될 수 없다
);

CREATE TABLE products (
  product_id bigint  PRIMARY KEY,
  name       text    NOT NULL,
  stock      integer NOT NULL,                      -- 일부러 CHECK를 안 걸었다
  version    integer NOT NULL DEFAULT 1             -- 낙관적 잠금에서 쓴다
);

CREATE TABLE orders (
  order_id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    bigint NOT NULL,
  product_id bigint NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

INSERT INTO accounts VALUES (1, 'kim', 100000), (2, 'lee', 50000);
INSERT INTO products VALUES (1001, '무선 이어폰', 1), (1002, '충전 케이스', 30), (1003, '이어팁', 120);
```

## 재고가 음수가 되지 않게 막는 방법들

처음 장면의 원인은 "읽고, 앱에서 판단하고, 쓰는" 사이에 다른 트랜잭션이 끼어든 것이었다. 고치는 방법은 그 틈을 없애거나, 틈에 끼어든 걸 알아채는 것이다.

가장 좋은 방법은 판단을 `UPDATE` 안으로 넣는 것이다. 조건과 계산을 한 문장에 쓰면 읽기와 쓰기 사이에 틈이 없다.

```sql
-- [1] A
BEGIN;
UPDATE products SET stock = stock - 1
WHERE product_id = 1001 AND stock > 0      -- 재고가 있을 때만
RETURNING stock;                           -- 바뀐 값을 바로 돌려받는다

-- [2] B
BEGIN;
UPDATE products SET stock = stock - 1
WHERE product_id = 1001 AND stock > 0
RETURNING stock;                           -- A의 잠금을 기다린다

-- [3] A
COMMIT;
```

```text
-- [1] A
 stock
-------
     0
(1 row)

UPDATE 1

-- [3] 이후 B
 stock
-------
(0 rows)

UPDATE 0
```

B는 A의 커밋을 기다렸다가, `READ COMMITTED`의 규칙대로 행의 최신 버전(재고 0)에 `WHERE` 조건을 다시 검사했다. `stock > 0`이 거짓이니 고친 행이 없다(`UPDATE 0`). 앱은 영향받은 행 수가 0이면 품절로 처리하면 된다. 격리 수준을 올릴 필요도, 재시도도 필요 없다. MySQL에서도 같은 방식으로 동작한다.

여기에 `CHECK (stock >= 0)`을 걸어 두면 실수로 조건을 빠뜨린 코드가 있어도 마지막에 DB가 막는다.

```sql
ALTER TABLE products ADD CHECK (stock >= 0);
UPDATE products SET stock = stock - 1 WHERE product_id = 1001;   -- 재고 1 → 0
UPDATE products SET stock = stock - 1 WHERE product_id = 1001;   -- 0 → -1 시도
```

```text
UPDATE 1
ERROR:  new row for relation "products" violates check constraint "products_stock_check"
DETAIL:  Failing row contains (1001, 무선 이어폰, -1, 1).
```

한 문장으로 표현할 수 없는 판단이면(재고 확인 후 쿠폰 확인, 결제 한도 확인 등 여러 단계) 읽을 때부터 잠그는 비관적 잠금(pessimistic locking)을 쓴다. `SELECT ... FOR UPDATE`는 읽은 행에 잠금을 걸어, 커밋할 때까지 다른 트랜잭션이 그 행을 고치거나 `FOR UPDATE`로 읽지 못하게 한다.

```sql
-- [1] A
BEGIN;
SELECT stock FROM products WHERE product_id = 1002 FOR UPDATE;   -- 30, 행을 잠근다

-- [2] B
BEGIN;
SELECT stock FROM products WHERE product_id = 1002 FOR UPDATE;   -- 읽기부터 기다린다

-- [3] A
UPDATE products SET stock = 29 WHERE product_id = 1002;
COMMIT;            -- B의 SELECT가 풀린다
```

```text
-- [3] 이후 B
 stock
-------
    29
(1 row)
```

B는 A가 끝난 뒤의 값 29를 읽었다. [앞 글](/posts/db-transaction-isolation)의 갱신 손실 때와 달리 B가 낡은 값을 볼 틈이 없다. 기다리지 않고 바로 실패하고 싶으면 `NOWAIT`를 붙인다.

```text
ERROR:  could not obtain lock on row in relation "products"
```

충돌이 드물다면 잠그지 않고, 쓸 때 "내가 읽은 뒤로 바뀐 게 없나"만 확인하는 낙관적 잠금(optimistic locking)이 낫다. `version` 열을 두고, 고칠 때 읽었던 버전을 조건으로 건다.

```sql
-- [1] A, B 둘 다 읽는다 (트랜잭션 없이)
SELECT stock, version FROM products WHERE product_id = 1003;   -- 120, 1

-- [2] A
UPDATE products SET stock = 119, version = version + 1
WHERE product_id = 1003 AND version = 1;     -- UPDATE 1

-- [3] B  (B도 버전 1을 읽었다)
UPDATE products SET stock = 119, version = version + 1
WHERE product_id = 1003 AND version = 1;     -- UPDATE 0: 그새 누가 바꿨다

-- [4] B  다시 읽고 다시 시도
SELECT stock, version FROM products WHERE product_id = 1003;   -- 119, 2
UPDATE products SET stock = 118, version = version + 1
WHERE product_id = 1003 AND version = 2;     -- UPDATE 1
```

B의 첫 `UPDATE`는 0행을 고쳤다. 에러가 아니라 조건에 맞는 행이 없는 것이다. 앱은 0행이면 다시 읽고 다시 계산한다. 잠금을 오래 잡지 않으니 사용자가 수정 화면을 몇 분씩 열어 두는 경우(관리자 상품 편집 같은 것)에 잘 맞는다. 충돌이 잦으면 재시도가 계속 실패해서 오히려 느려진다. JPA의 `@Version`이 이 방식이다.

작업 큐처럼 여러 워커가 "아직 안 한 일 하나"를 집어 가는 경우에는 `SKIP LOCKED`가 있다. 남이 잠근 행은 기다리지 않고 건너뛴다. 영수증 메일 발송 작업 세 개가 있는 `jobs` 테이블로 해 봤다.

```sql
-- [1] A
BEGIN;
SELECT job_id FROM jobs WHERE status = 'ready'
ORDER BY job_id LIMIT 1 FOR UPDATE SKIP LOCKED;   -- 1

-- [2] B
BEGIN;
SELECT job_id FROM jobs WHERE status = 'ready'
ORDER BY job_id LIMIT 1 FOR UPDATE SKIP LOCKED;   -- 2. 1번은 A가 잡고 있어 건너뛴다

-- [3] A, B 각자
UPDATE jobs SET status = 'done' WHERE job_id = 1;  -- A
UPDATE jobs SET status = 'done' WHERE job_id = 2;  -- B
COMMIT;
```

두 워커가 기다림 없이 서로 다른 작업을 가져갔다. `SKIP LOCKED`가 없으면 B는 A가 끝날 때까지 1번 행에서 기다렸다가, 1번이 이미 처리된 걸 보고 다시 찾아야 한다. MySQL도 8.0부터 `SKIP LOCKED`와 `NOWAIT`를 지원한다.

`SERIALIZABLE`로 올리는 것도 방법이다. 이 경우 40001(그리고 뒤에서 볼 교착 상태 40P01)을 받으면 트랜잭션 전체를 다시 실행하는 코드가 반드시 있어야 한다.

```ts
// SQLSTATE로 재시도 대상인지 판단한다 (node-postgres는 err.code에 들어 있다)
const RETRYABLE = new Set(["40001", "40P01"]);

async function withRetry<T>(run: () => Promise<T>, maxAttempts = 3): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    try {
      return await run(); // run 안에서 BEGIN ... COMMIT 전체를 실행한다
    } catch (err: any) {
      if (!RETRYABLE.has(err.code) || attempt >= maxAttempts) throw err;
      await new Promise((r) => setTimeout(r, 20 * 2 ** attempt * Math.random())); // 지터 섞인 백오프
    }
  }
}
```

재시도할 때는 트랜잭션 안의 쿼리만이 아니라 판단 로직까지 처음부터 다시 실행해야 한다. 이전 시도에서 읽은 값을 재사용하면 재시도하는 의미가 없다. 그리고 트랜잭션 안에서 결제 API 호출이나 메일 발송 같은 외부 작업을 하면 재시도할 때 두 번 실행된다. 외부 작업은 커밋 뒤로 뺀다.

## 서로 기다리다 멈추는 교착 상태

kim이 lee에게 10,000원을, 동시에 lee가 kim에게 5,000원을 보낸다. 송금 코드는 "보내는 사람 출금 → 받는 사람 입금" 순서다. 같은 일이 DB 밖, 애플리케이션의 뮤텍스나 커넥션 풀에서 생기는 경우는 [데드락 글](/posts/deadlocks)에서 다룬다.

```sql
-- [1] A: kim → lee
BEGIN;
UPDATE accounts SET balance = balance - 10000 WHERE account_id = 1;   -- 1번 행 잠금

-- [2] B: lee → kim
BEGIN;
UPDATE accounts SET balance = balance - 5000 WHERE account_id = 2;    -- 2번 행 잠금

-- [3] A
UPDATE accounts SET balance = balance + 10000 WHERE account_id = 2;   -- B의 2번을 기다린다

-- [4] B
UPDATE accounts SET balance = balance + 5000 WHERE account_id = 1;    -- A의 1번을 기다린다
```

```text
ERROR:  deadlock detected
DETAIL:  Process 3374 waits for ShareLock on transaction 1184; blocked by process 3371.
Process 3371 waits for ShareLock on transaction 1185; blocked by process 3374.
HINT:  See server log for query details.
CONTEXT:  while updating tuple (0,5) in relation "accounts"
```

A는 B가 잡은 2번 행을, B는 A가 잡은 1번 행을 기다린다. 둘 다 상대가 끝나야 진행할 수 있으니 영원히 끝나지 않는다. 이게 교착 상태(deadlock)다. 아래 그림의 화살표가 "누가 무엇을 잡고, 무엇을 기다리나"다. 화살표를 따라가면 원을 그리며 제자리로 돌아온다.

PostgreSQL은 잠금을 `deadlock_timeout`(기본 1초) 동안 기다린 트랜잭션이 생기면 대기 관계를 따라가 원이 있는지 검사한다. 원을 찾으면 검사한 쪽을 에러로 끝내서 원을 끊는다. 이 실험에서는 A가 먼저 기다리기 시작했지만, A의 1초가 지날 때는 B가 아직 기다리기 전이라 원이 없었다. 나중에 기다린 B의 검사에서 원이 발견돼 B가 끝났다. 그러면 A는 잠금을 얻어 커밋하고, B는 통째로 롤백된다. 실제로 이 실험의 최종 잔액은 kim 90,000원, lee 60,000원으로 A의 송금만 반영됐다. 에러 메시지를 조각내 보면 읽는 법이 보인다.

교착 상태를 없애는 가장 확실한 방법은 잠그는 순서를 정하는 것이다. 송금이라면 보내는 쪽, 받는 쪽 순서가 아니라 계좌 번호가 작은 쪽부터 잠근다. 그러면 A와 B가 모두 1번을 먼저 잡으려 하고, 늦은 쪽은 1번에서 기다릴 뿐 2번을 쥐고 있지 않으니 원이 생기지 않는다.

```sql
-- 계좌 번호 순서로 먼저 잠근 뒤 고친다
BEGIN;
SELECT account_id FROM accounts WHERE account_id IN (1, 2) ORDER BY account_id FOR UPDATE;
UPDATE accounts SET balance = balance - 10000 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 10000 WHERE account_id = 2;
COMMIT;
```

트랜잭션을 짧게 유지하는 것도 도움이 된다. 잠금을 쥔 시간이 짧을수록 엇갈릴 확률이 줄어든다. 그래도 완전히 없앨 수는 없으니, 교착 상태 에러(SQLSTATE 40P01)도 앞의 재시도 대상에 넣는다. MySQL InnoDB는 기다리기 시작하는 순간 바로 검사해서(`innodb_deadlock_detect = ON`) 고친 행이 적은 쪽을 롤백하고, 에러는 이렇게 나온다.

```text
ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
```

대기 관계에서 원을 찾는 건 그래프에서 사이클을 찾는 문제다. 아래 `detectDeadlock`은 "트랜잭션 → 그 트랜잭션이 기다리는 트랜잭션 목록"을 받아서 원을 이루는 트랜잭션들을 돌려준다. 원이 없으면 빈 배열이다. 원에 끼지 않고 그냥 기다리기만 하는 트랜잭션은 결과에 넣지 않는다. 그걸 끝내 봐야 원은 그대로이기 때문이다.

  const state = {}; // 없음: 아직 안 봄, 1: 지금 따라가는 경로에 있음, 2: 다 봄
  const path = [];

  function visit(tx) {
    state[tx] = 1;
    path.push(tx);
    for (const next of waitsFor[tx] || []) {
      // 지금 경로에 있는 트랜잭션으로 돌아왔다 → 그 지점부터가 원이다
      if (state[next] === 1) return path.slice(path.indexOf(next));
      if (state[next] === undefined) {
        const cycle = visit(next);
        if (cycle) return cycle;
      }
    }
    path.pop();
    state[tx] = 2;
    return null;
  }

  for (const tx of Object.keys(waitsFor)) {
    if (state[tx] === undefined) {
      const cycle = visit(tx);
      if (cycle) return cycle;
    }
  }
  return [];
}`}

## 오래 열린 트랜잭션이 남기는 것

교착 상태는 DB가 알아서 끊어 주지만, 그냥 오래 기다리는 건 끊어 주지 않는다. A가 행을 잠근 채 아무것도 안 하고 있으면 B는 끝없이 기다린다. 지금 누가 누구를 막고 있는지는 `pg_stat_activity`와 `pg_blocking_pids`로 본다.

```sql
-- 세 번째 세션에서 실행. A가 1003번을 UPDATE한 채 멈춰 있고, B가 같은 행을 기다리는 중
SELECT pid, pg_blocking_pids(pid) AS blocked_by, state, wait_event_type, wait_event,
       left(query, 30) AS query
FROM pg_stat_activity
WHERE datname = 'shop_tx' AND pid <> pg_backend_pid()
ORDER BY pid;
```

```text
 pid  | blocked_by |        state        | wait_event_type |  wait_event   |             query
------+------------+---------------------+-----------------+---------------+--------------------------------
 3535 | {}         | idle in transaction | Client          | ClientRead    | UPDATE products SET stock = st
 3539 | {3535}     | active              | Lock            | transactionid | UPDATE products SET stock = st
(2 rows)
```

두 줄을 보면 된다. 3539(B)는 `active`인데 `wait_event_type`이 `Lock`이고 `blocked_by`가 3535다. 3535(A)는 `idle in transaction`이다. 트랜잭션을 연 채 클라이언트의 다음 명령을 기다리고 있다(`ClientRead`). `query`는 그 세션이 마지막으로 실행한 쿼리라, A가 지금 `UPDATE`를 실행 중이라는 뜻이 아니다. 앱이 트랜잭션을 열고 외부 API 응답을 기다리거나, 예외가 나서 커밋도 롤백도 안 하고 연결을 풀에 돌려준 경우에 이렇게 된다.

막힌 쪽을 무한정 기다리지 않게 하는 설정이 `lock_timeout`이다. 잠금을 이 시간 이상 기다리면 그 문장을 취소한다.

```sql
SET lock_timeout = '1s';
UPDATE products SET stock = stock - 1 WHERE product_id = 1003;   -- A가 잡고 있는 행
```

```text
ERROR:  canceling statement due to lock timeout
CONTEXT:  while updating tuple (0,21) in relation "products"
```

비슷한 설정이 셋 더 있다. `statement_timeout`은 문장 하나의 실행 시간 상한이다(`ERROR:  canceling statement due to statement timeout`). `idle_in_transaction_session_timeout`은 트랜잭션을 연 채 놀고 있는 세션을 끊는다. 기본값이 0(끄기)이라 직접 켜야 한다. 트랜잭션 하나가 열려 있는 전체 시간을 제한하는 `transaction_timeout`은 PostgreSQL 17에 새로 생겼다. 16에서는 위 설정들을 조합하고, 나머지는 앱에서 관리한다.

```sql
-- 앱이 쓰는 DB 사용자에 기본값으로 걸어 둔다 (새 연결부터 적용)
ALTER ROLE app_user SET lock_timeout = '3s';
ALTER ROLE app_user SET statement_timeout = '30s';
ALTER ROLE app_user SET idle_in_transaction_session_timeout = '60s';

-- 지금 오래 열려 있는 트랜잭션 찾기
SELECT pid, state, now() - xact_start AS xact_age, left(query, 40) AS query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_start;
```

```text
 pid  |        state        |    xact_age     |                  query
------+---------------------+-----------------+------------------------------------------
 3460 | idle in transaction | 00:00:04.202683 | SELECT * FROM accounts WHERE account_id
(1 row)
```

`xact_age`가 트랜잭션이 열린 지 얼마나 됐는지다. 몇 분, 몇 시간짜리가 보이면 그 앱 코드를 찾아야 한다. 급하면 `SELECT pg_terminate_backend(3460);`으로 그 연결을 끊을 수 있다. 끊긴 쪽의 트랜잭션은 롤백된다.

<Callout kind="warning" title="트랜잭션 안에서 외부를 기다리지 않는다">
트랜잭션을 열고 결제 API, 메일 발송, 다른 서비스 HTTP 호출을 기다리면 그 시간 내내 행 잠금을 쥐고, VACUUM이 옛 버전을 치우지 못한다. 외부 호출이 30초 타임아웃에 걸리면 같은 상품을 사려는 모든 요청이 30초씩 줄을 선다. 외부 호출은 트랜잭션 밖으로 빼고, DB 안의 상태 변경만 짧게 묶는다. 외부 호출이 실패했을 때 되돌리는 처리는 다음 절의 방식으로 따로 만든다.
</Callout>

## 서비스 여러 개에 걸친 트랜잭션

주문 서비스와 결제 서비스가 DB를 따로 쓰면, 한 DB의 트랜잭션으로는 둘을 함께 묶을 수 없다. 교과서적인 답은 2단계 커밋(2PC, two-phase commit)이다. 조정자가 모든 참여자에게 "커밋할 준비가 됐나"를 묻고(prepare), 모두 준비됐다고 하면 "커밋하라"고 알린다. PostgreSQL도 `PREPARE TRANSACTION`으로 지원한다(기본값 `max_prepared_transactions = 0`이라 켜야 쓸 수 있다).

실무에서 2PC를 피하는 이유는 준비 단계와 커밋 단계 사이에 조정자가 죽으면 참여자들이 잠금을 쥔 채 결정을 기다려야 하기 때문이다. 가장 느린 참여자가 전체 속도를 정하고, 참여자 하나만 응답이 없어도 모두가 멈춘다. 메시지 브로커나 외부 API는 아예 2PC에 참여하지 못한다.

그래서 보통은 두 가지를 조합한다. 트랜잭셔널 아웃박스(transactional outbox)는 "DB를 바꾸고 이벤트를 보낸다"를 원자적으로 만드는 방법이다. 이벤트를 브로커로 바로 보내지 않고, 같은 DB의 `outbox` 테이블에 같은 트랜잭션으로 적는다. 별도 프로세스가 `outbox`를 읽어 브로커로 보낸다.

```sql
BEGIN;
UPDATE products SET stock = stock - 1 WHERE product_id = 1001 AND stock > 0;
INSERT INTO orders (user_id, product_id) VALUES (1, 1001);
INSERT INTO outbox (topic, payload)                       -- 보낼 이벤트도 같은 트랜잭션에
VALUES ('order.created', '{"order_id": 3, "product_id": 1001}');
COMMIT;
-- 릴레이 프로세스가 outbox를 FOR UPDATE SKIP LOCKED로 집어 브로커에 보내고 표시한다
```

주문이 커밋되면 이벤트도 반드시 남고, 롤백되면 이벤트도 없다. 브로커로 보내는 쪽은 실패하면 다시 보내니 같은 이벤트가 두 번 갈 수 있어서, 받는 쪽은 이벤트 ID로 중복을 걸러야 한다.

사가(saga)는 긴 작업을 각 서비스의 짧은 로컬 트랜잭션 여러 개로 나누고, 중간에 실패하면 이미 끝난 단계를 되돌리는 보상 트랜잭션을 실행하는 방식이다. 결제가 실패하면 주문 서비스가 "주문 취소, 재고 복구"를 실행한다. 격리가 없다는 점은 알고 써야 한다. 보상 전까지 다른 요청이 중간 상태(주문은 있는데 결제는 실패)를 볼 수 있으니, `pending` 같은 상태 값으로 아직 확정이 아님을 드러낸다. 서비스를 나누는 기준과 사가의 두 방식(코레오그래피, 오케스트레이션)은 [마이크로서비스 글](/posts/microservices)에서 더 다룬다.

## SQLD에서 묻는 잠금과 교착 상태

SQLD에서 동시성 제어와 잠금은 기출 범위와 회차에 따라 비중이 다르다. 응시 회차의 공식 출제 기준을 확인하고, 자주 보이던 내용을 시험 말로 다시 묶으면 이렇다.

동시성 제어는 두 갈래다. 비관적 동시성 제어는 충돌이 날 것이라 보고 읽을 때부터 잠근다(`SELECT ... FOR UPDATE`). 낙관적 동시성 제어는 충돌이 드물다고 보고 잠그지 않고 진행하다가 커밋 시점에 충돌을 검사한다(버전 열). 잠금 종류는 공유 잠금(S, 읽기)과 배타 잠금(X, 쓰기)이고, S끼리만 함께 걸 수 있다. S와 X, X와 X는 함께 못 건다. 잠금 단위(행, 페이지, 테이블, DB)가 작을수록 동시성은 높고 관리 비용은 크다.

2단계 잠금(2PL, Two-Phase Locking)은 트랜잭션이 잠금을 얻기만 하는 확장 단계와 풀기만 하는 수축 단계로 나뉘는 규약이다. 한 번이라도 풀기 시작하면 새 잠금을 얻을 수 없다. 이 규약을 지키면 직렬 가능성(serializability)이 보장되지만, 교착 상태는 막지 못한다. 이 조합이 보기로 자주 나온다.

교착 상태가 생기는 네 조건은 상호 배제(한 자원을 한 트랜잭션만 쓴다), 점유와 대기(잡은 채 다른 걸 기다린다), 비선점(남이 잡은 걸 빼앗을 수 없다), 환형 대기(기다림이 원을 이룬다)다. 넷이 모두 성립해야 교착 상태가 생기니, 하나만 깨면 예방된다. 잠금 순서를 정하는 건 환형 대기를 깨는 방법이다.

## 틈을 없애거나, 틈을 알아채거나

트랜잭션은 동시에 실행되는 트랜잭션끼리의 문제를 격리 수준만큼만 막는다. 그래서 재고 -1과 갱신 손실은 앱이 막아야 한다. 고치는 방법은 읽기와 쓰기 사이의 틈을 없애거나(조건부 `UPDATE`, `FOR UPDATE`), 틈에 누가 끼어들었는지 알아채는 것(버전 열, `REPEATABLE READ`, `SERIALIZABLE`과 재시도)이다. 잠금을 쓰면 교착 상태가 따라오니 잠금 순서를 정하고, 40P01과 40001은 재시도한다. 어느 쪽이든 트랜잭션은 짧게, 외부 호출은 트랜잭션 밖으로 둔다.

## 면접에서 나올 만한 질문

### 재고 차감에서 동시성 문제를 어떻게 막나요?

가장 먼저 조건과 계산을 한 문장에 넣는다. `UPDATE products SET stock = stock - 1 WHERE product_id = ? AND stock > 0`을 실행하고 영향받은 행이 0이면 품절로 처리한다. 읽기와 쓰기 사이에 틈이 없어서 격리 수준을 올리지 않아도 된다. 여러 단계 판단이 필요하면 SELECT ... FOR UPDATE로 먼저 잠그고, 충돌이 드문 편집 화면이면 버전 열로 낙관적 잠금을 쓴다. 마지막 안전장치로 CHECK (stock >= 0)을 건다.

### 낙관적 잠금과 비관적 잠금은 언제 각각 쓰나요?

충돌이 잦고 실패 비용이 크면 비관적 잠금, 충돌이 드물고 대기 시간이 길면 낙관적 잠금이다. 비관적 잠금은 읽을 때부터 행을 잠가서 확실하지만 잠금 대기와 교착 상태가 생길 수 있다. 낙관적 잠금은 버전 열을 조건에 넣고 UPDATE 결과가 0행이면 다시 시도한다. 사용자가 수정 화면을 몇 분씩 열어 두는 경우에는 그동안 잠금을 쥘 수 없으니 낙관적 잠금이 맞다.

### 교착 상태는 왜 생기고 어떻게 줄이나요?

두 트랜잭션이 서로가 잡은 잠금을 기다려 대기가 원을 이룰 때 생긴다. PostgreSQL은 deadlock_timeout(기본 1초) 뒤에 대기 그래프를 검사해서 한쪽을 에러로 끝낸다. 줄이려면 잠금 순서를 정한다. 송금이라면 계좌 번호가 작은 쪽부터 잠근다. 트랜잭션을 짧게 유지하고, 그래도 생기는 교착 상태는 재시도로 처리한다.

### 여러 서비스에 걸친 작업은 어떻게 일관성을 맞추나요?

2PC는 조정자 장애 시 참여자가 잠금을 쥔 채 멈추고 가장 느린 참여자에 묶여서 잘 쓰지 않는다. 대신 각 서비스가 로컬 트랜잭션으로 상태를 바꾸면서 같은 트랜잭션에 아웃박스 테이블로 이벤트를 남기고, 릴레이가 그 이벤트를 전달한다. 실패하면 사가 패턴으로 이미 끝난 단계를 보상 트랜잭션으로 되돌린다. 이벤트는 두 번 갈 수 있으니 받는 쪽은 멱등하게 처리하고, 중간 상태는 pending 같은 상태 값으로 드러낸다.

### 오래 열린 트랜잭션은 어떤 문제를 만드나요?

그 트랜잭션이 쥔 행 잠금 때문에 같은 행을 고치려는 요청이 줄줄이 기다리고, 그 트랜잭션의 스냅숏이 볼 수 있는 옛 버전은 VACUUM이 치우지 못해 테이블과 인덱스가 부푼다. `pg_stat_activity`에서 `idle in transaction`과 오래된 `xact_start`로 찾고, `idle_in_transaction_session_timeout`으로 한도를 건다. 근본적으로는 결제 API나 메일 발송처럼 DB 밖을 기다리는 일을 트랜잭션 밖으로 뺀다.
