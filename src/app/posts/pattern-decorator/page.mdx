import { getPostMetadata } from "@/features/posts";

API를 부르는 `fetchJson`이라는 함수가 있다. 처음에는 `fetch`를 부르고 JSON을 돌려주는 다섯 줄이었다. 그러다 결제 API가 가끔 503을 내서 재시도 옵션이 붙었다. 장애 분석 때문에 로그 옵션이 붙었고, 응답이 멈추는 일이 있어 타임아웃이 붙었고, 상품 목록은 캐시하자고 해서 캐시 옵션이 붙었다. 지금 호출부는 이렇게 생겼다.

```ts
fetchJson("/api/payments/42", { retry: 3, log: true, timeoutMs: 2000, cache: false });
```

함수 안은 `if (options.retry)`, `if (options.log)`가 서로 얽혀 있다. 재시도할 때 로그를 매번 남겨야 하는지, 캐시에서 꺼낸 응답도 로그에 찍어야 하는지는 코드를 끝까지 읽어야 알 수 있다. 다음 요구사항은 "인증 토큰이 만료되면 갱신하고 한 번 더"다. 옵션이 또 하나 붙는다.

이번 글은 이 기능들을 하나씩 떼어 각각을 같은 모양의 겉옷으로 만드는 데코레이터(Decorator) 패턴이다. 상속으로 기능을 조합하면 클래스가 곱으로 는다는 이야기는 [디자인 패턴 개요](/posts/design-patterns-overview)에서 다뤘으니, 여기서는 감싸는 방법과 감싸는 순서, 그리고 감쌌을 때 생기는 부작용을 본다.

## 같은 모양으로 감싸고 앞뒤에 일을 더한다

데코레이터의 규칙은 둘이다. 감싸는 객체는 감싸인 객체와 같은 인터페이스를 구현한다. 그리고 호출을 받으면 안쪽 객체에 넘기면서 그 앞이나 뒤에 자기 일을 한다. 같은 인터페이스라서 감싼 것을 또 감쌀 수 있고, 부르는 쪽은 몇 겹인지 모른다.

GoF 그림에서는 FetchClient가 ConcreteComponent, RetryClient 같은 것이 ConcreteDecorator다. 공통 부모 Decorator 클래스를 두기도 하지만 TypeScript에서는 인터페이스 하나로 충분하다. 처음의 옵션들을 하나씩 클래스로 떼면 이렇다.

```ts
interface HttpClient {
  get(url: string): Promise<string>;
}

class FetchClient implements HttpClient {
  async get(url: string) {
    const res = await fetch(url);
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return res.text();
  }
}

// 감싼 객체와 같은 인터페이스를 구현하고, 호출을 넘기면서 앞뒤에 일을 더한다
class LoggingClient implements HttpClient {
  constructor(private readonly inner: HttpClient, private readonly log: (line: string) => void = console.log) {}

  async get(url: string) {
    const started = Date.now();
    try {
      const body = await this.inner.get(url);
      this.log(`GET ${url} ok ${Date.now() - started}ms`);
      return body;
    } catch (error) {
      this.log(`GET ${url} fail ${(error as Error).message}`);
      throw error;
    }
  }
}

class RetryClient implements HttpClient {
  constructor(private readonly inner: HttpClient, private readonly attempts = 3) {}

  async get(url: string) {
    let lastError: unknown;
    for (let i = 1; i <= this.attempts; i++) {
      try {
        return await this.inner.get(url);
      } catch (error) {
        lastError = error;
      }
    }
    throw lastError;
  }
}

class TimeoutClient implements HttpClient {
  constructor(private readonly inner: HttpClient, private readonly ms: number) {}

  get(url: string) {
    return Promise.race([
      this.inner.get(url),
      new Promise<never>((_, reject) => setTimeout(() => reject(new Error(`timeout ${this.ms}ms`)), this.ms)),
    ]);
  }
}

// 조립은 한 곳에서. 필요한 기능만 골라 겹친다
export const api: HttpClient = new LoggingClient(new RetryClient(new TimeoutClient(new FetchClient(), 2000), 3));
```

클래스마다 하는 일이 하나다. 재시도 클래스는 로그를 모르고, 로그 클래스는 재시도를 모른다. 캐시가 필요한 상품 API에는 `CacheClient`를 하나 더 끼우고, 내부 관리 API에는 로그만 붙인다. `fetchJson` 안의 `if`가 하던 일을 이제 조립하는 한 줄이 한다. 기존 클래스를 고치지 않고 기능을 더하니 개방 폐쇄 원칙을 그대로 따르는 모양이다.

## 감싸는 순서가 결과를 바꾼다

마지막 단계에서 로그가 한 줄이었다. 겹의 순서를 바꾸면 어떻게 될까. 처음 두 번은 503을 내는 가짜 서버로 두 순서를 직접 돌려 봤다.

```ts
const outer = new LoggingClient(new RetryClient(flaky(2), 3), log);
await outer.get("/orders");

const inner = new RetryClient(new LoggingClient(flaky(2), log), 3);
await inner.get("/orders");
```

```text
log(retry(x)): 1 줄
  GET /orders ok 0ms
retry(log(x)): 3 줄
  GET /orders fail HTTP 503
  GET /orders fail HTTP 503
  GET /orders ok 0ms
```

같은 두 겹인데 결과가 다르다. 어느 쪽이 맞는지는 무엇을 알고 싶은지에 달렸다. "사용자 요청이 결국 성공했나"를 보려면 로그를 바깥에, "업스트림이 얼마나 자주 실패하나"를 보려면 안에 둔다. 둘 다 필요하면 두 겹을 다 끼운다. 아래 그림은 바깥 로그 순서에서 호출이 겹을 드나드는 모습이다.

이 실험에는 함정이 하나 더 있다. `Promise.race`는 기다리기만 그만둘 뿐 진행 중인 요청을 취소하지 않는다. 멈춘 연결은 계속 열려 있고, 서버가 늦게 처리를 끝내면 그 결과는 버려진다. 실제 `TimeoutClient`는 `AbortSignal.timeout(ms)`를 만들어 안쪽 `fetch`에 넘겨야 연결까지 끊긴다. 이러려면 인터페이스에 `signal`을 받는 자리가 있어야 한다. 데코레이터가 할 수 있는 일은 인터페이스가 열어 준 만큼이다.

재시도를 감쌀 때는 무엇을 감싸는지도 봐야 한다. `get`이 아니라 결제 승인 같은 `POST`를 `RetryClient`로 감싸면, 첫 요청이 서버에서는 성공했는데 응답만 늦은 경우 결제가 두 번 된다. 재시도는 같은 요청을 여러 번 보내도 결과가 같은 요청에만 붙이거나, [멱등성 키](/posts/idempotency-key)를 함께 보낸다. 재시도 간격과 횟수는 [재시도 글](/posts/retries)에서 따로 다뤘다.

캐시 겹도 위치에 따라 의미가 바뀐다. `Cache(Logging(x))`면 캐시 적중은 로그에 남지 않고, `Logging(Cache(x))`면 모든 호출이 남는다. 캐시를 `Retry` 안쪽에 두면 실패한 응답을 캐시하지 않도록 따로 신경 써야 한다. 겹을 추가할 때마다 "이 겹은 무엇을 보고 무엇을 못 보나"를 한 번씩 따져 보면 된다.

## 클래스 대신 함수를 감싸도 된다

인터페이스에 메서드가 하나뿐이라면 클래스까지 갈 필요가 없다. 함수를 받아 같은 모양의 함수를 돌려주는 고차 함수가 곧 데코레이터다.

```ts
type Get = (url: string) => Promise<string>;
type Wrap = (next: Get) => Get;

const withRetry = (attempts: number): Wrap => (next) => async (url) => {
  let lastError: unknown;
  for (let i = 0; i < attempts; i++) {
    try {
      return await next(url);
    } catch (error) {
      lastError = error;
    }
  }
  throw lastError;
};

const withLog = (log: (line: string) => void): Wrap => (next) => async (url) => {
  const body = await next(url);
  log(`GET ${url} ok`);
  return body;
};

// 배열에 적은 순서가 바깥 → 안쪽 순서가 되게 접는다
const wrap = (...wraps: Wrap[]) => (base: Get): Get => wraps.reduceRight((acc, w) => w(acc), base);

const get = wrap(withLog(console.log), withRetry(3))(async (url) => (await fetch(url)).text());
```

`wrap(withLog, withRetry)`처럼 목록으로 쓰면 괄호가 깊어지지 않고 순서도 위에서 아래로 읽힌다. 메서드가 여럿이거나 감싸는 쪽이 상태(캐시 맵, 회로 차단기의 실패 수)를 오래 들고 있어야 한다면 클래스가 더 읽기 쉽다. 메서드가 하나 늘어날 때 TypeScript가 `implements`로 "이 겹은 새 메서드를 넘기지 않았다"고 알려 주는 것도 클래스 쪽의 이점이다.

## 메서드 위의 @는 데코레이터 패턴인가

TypeScript 5.0부터 TC39 표준 데코레이터가 들어왔다. `experimentalDecorators` 없이 메서드 위에 `@logged`를 붙이면 그 메서드를 감싼 새 함수로 바꿔 끼운다.

```ts
function logged<This, Args extends unknown[], R>(
  target: (this: This, ...args: Args) => R,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => R>,
) {
  const name = String(context.name);
  return function (this: This, ...args: Args): R {
    console.log(`→ ${name}(${args.join(", ")})`);
    const result = target.call(this, ...args);
    console.log(`← ${name} = ${String(result)}`);
    return result;
  };
}

class PriceCalculator {
  constructor(private readonly taxRate: number) {}

  @logged
  withTax(price: number) {
    return Math.round(price * (1 + this.taxRate));
  }
}

new PriceCalculator(0.1).withTax(20_000);
```

```text
→ withTax(20000)
← withTax = 22000
```

감싸서 앞뒤에 일을 더한다는 생각은 같다. 다른 점은 시점과 단위다. `@logged`는 클래스를 정의하는 순간 그 클래스의 모든 인스턴스에 고정으로 붙는다. GoF의 데코레이터는 실행 중에 객체 하나를 감싼다. 같은 `FetchClient`라도 결제 API용 인스턴스에는 재시도를, 관리 API용에는 로그만 붙이는 식으로 객체마다 다르게 고를 수 있다. 그러니 `@` 문법은 데코레이터 패턴을 구현하는 도구 중 하나이지 같은 것은 아니다. Python의 `@functools.cache`도 정의 시점에 함수를 감싸는 같은 계열이다.

참고로 NestJS나 TypeORM의 `@Controller`, `@Column`은 대부분 감싸는 게 아니라 메타데이터를 붙이는 용도라서 패턴 이름과는 더 멀다. 아직 많은 프로젝트가 `experimentalDecorators`(옛 문법)를 쓰는데, 표준 데코레이터와는 함수 시그니처가 달라서 섞어 쓸 수 없다.

## 매일 감싸고 있는 것들

자바의 입출력 스트림이 교과서 예제다. `new BufferedReader(new InputStreamReader(new FileInputStream("a.txt"), UTF_8))`에서 바깥 두 겹은 각각 버퍼링과 문자 디코딩을 더한다. 모두 같은 `Reader`/`InputStream` 계열이라 어떤 순서로든 겹칠 수 있다.

Go 표준 라이브러리에서는 `func(http.Handler) http.Handler` 모양이 그대로 데코레이터다. `http.TimeoutHandler`, `http.StripPrefix`, `http.MaxBytesHandler`가 모두 핸들러를 받아 같은 인터페이스의 핸들러를 돌려준다. Go 1.24에서 로그 겹을 직접 씌워 돌렸다.

```go
func withLogging(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		next.ServeHTTP(w, r)
		log.Printf("%s %s %s", r.Method, r.URL.Path, time.Since(start).Round(time.Millisecond))
	})
}

h := withLogging(http.TimeoutHandler(hello, 2*time.Second, "timeout"))
```

```text
2026/10/20 14:24:03 GET /hi 0s
200 hello
```

React의 고차 컴포넌트(HOC)도 같은 생각이다. react-redux의 `connect(mapState)(Component)`는 컴포넌트를 받아 스토어 값을 props로 넣어 주는 컴포넌트를 돌려준다. `React.memo(Component)`도 같은 props 계약을 지키면서 "props가 같으면 다시 그리지 않는다"를 더한다([리렌더링 글](/posts/react-rerender) 참고). 요즘은 상태를 끌어오는 HOC 대부분을 훅이 대신한다. 감싸는 겹이 컴포넌트 트리에 쌓이지 않고, props 이름이 겹칠 걱정도 없어서다. Redux의 `applyMiddleware`는 스토어의 `dispatch`를 미들웨어 수만큼 감싼다.

## 감쌌더니 달라진 것들

감싼 객체는 원래 객체가 아니다. 이 단순한 사실이 몇 가지 문제를 낳는다.

```ts
const base = new FetchClient();
const api: HttpClient = new LoggingClient(base);

api === base;                 // false
api instanceof FetchClient;   // false
```

어딘가에서 `instanceof FetchClient`로 분기하거나, `Set`에 원래 객체를 넣고 감싼 객체로 찾으면 조용히 틀린다. 데코레이터를 쓰기로 했다면 구체 클래스가 아니라 인터페이스로만 다루는 습관이 필요하다.

인터페이스가 넓으면 넘겨야 할 메서드도 많다. `HttpClient`에 `post`, `put`, `delete`가 있다면 로그 겹은 네 메서드를 모두 구현해야 하고, 그중 셋은 그냥 넘기기만 한다. TypeScript에서는 `implements` 덕분에 빠뜨리면 컴파일이 안 되지만, 자바스크립트에서 클래스 상속으로 "나머지는 부모가 알아서" 처리하게 하면 새로 생긴 메서드가 겹을 건너뛰어 버린다. 인터페이스를 좁게 유지하는 것이 데코레이터를 쓰기 쉬운 조건이다.

디버깅할 때는 스택 트레이스가 겹 수만큼 길어진다. 겹이 다섯 개면 에러 위치를 찾기 전에 `LoggingClient.get`, `RetryClient.get`… 을 지나야 한다. 반대로 테스트는 쉬워진다. 겹마다 가짜 안쪽 객체(앞의 `flaky(2)`처럼)를 넣어 혼자 검증할 수 있다. 처음의 `fetchJson`이었다면 재시도 로직 하나를 테스트하려고 로그와 캐시 옵션까지 신경 써야 했다.

## 프록시, 어댑터와 갈리는 지점

감싸는 패턴끼리의 비교표는 [어댑터 글](/posts/pattern-adapter#비슷한-구조-패턴과-헷갈릴-때)에 정리해 두었다. 데코레이터 입장에서 한 번 더 짚으면, 어댑터는 인터페이스를 바꾸고 데코레이터는 그대로 둔다. [프록시](/posts/pattern-proxy)는 데코레이터와 코드 모양까지 같아서 의도로 가른다. 프록시는 진짜 객체로 가는 접근을 통제(지연 생성, 권한 확인, 원격 호출)하고 보통 진짜 객체를 스스로 만들거나 관리한다. 데코레이터는 이미 있는 객체를 바깥에서 받아 기능을 더하고, 여러 겹 쌓는 것이 전제다. Spring의 `@Transactional`은 이름과 달리 AOP 프록시로 구현된다.

[책임 연쇄](/posts/pattern-chain-of-responsibility)와도 닮았다. 미들웨어 체인도 다음 처리기를 부르니까. 차이는 끊을 수 있느냐다. 책임 연쇄의 처리기는 요청을 처리하고 사슬을 끝낼 수 있다. 데코레이터는 원칙적으로 항상 안쪽을 부르고 결과에 무언가를 더한다. Koa의 미들웨어처럼 `await next()` 앞뒤에 코드를 쓰는 양파 모양은 둘을 섞은 것이다. 하나만 감싸는 데코레이터와 여러 자식을 모으는 [컴포지트](/posts/pattern-composite)의 차이는 그 글에서 다뤘다.

## 직접 겹쳐 보는 재시도와 로그

`withRetry`와 `withLog`를 완성해 보자. `withRetry(fn, times)`는 `fn`이 던지면 최대 `times`번까지 다시 부르고, 끝내 실패하면 마지막 에러를 던진다. `withLog(fn, logs)`는 성공하면 `"ok"`, 실패하면 `"fail " + 메시지`를 `logs`에 넣고 결과나 에러를 그대로 넘긴다. `scenario`는 두 겹을 어떤 순서로 쌓았는지에 따라 무엇이 달라지는지 보여 준다.

데코레이터는 "같은 모양으로 감싸서 앞뒤에 일을 더한다"가 전부다. 기능마다 겹 하나를 만들고 조립하는 곳에서 필요한 것만 고르니, 옵션이 얽힌 함수 하나보다 각 기능이 단순해진다. 대신 겹의 순서가 곧 동작이 되니, 조립하는 한 줄을 코드 리뷰에서 가장 꼼꼼히 봐야 한다.

## 면접에서 나올 만한 질문

### 데코레이터 패턴은 무엇이고 왜 쓰나요?

객체를 같은 인터페이스의 다른 객체로 감싸서, 호출을 넘기는 앞뒤에 기능을 더하는 패턴이다. 원래 클래스를 고치거나 상속하지 않고 런타임에 필요한 기능만 골라 겹칠 수 있다. 상속으로 기능을 조합하면 하위 클래스가 곱으로 늘어나는데, 데코레이터는 기능 수만큼만 클래스가 는다.

### 데코레이터를 감싸는 순서가 왜 중요한가요?

바깥 겹은 안쪽에서 일어난 일을 결과로만 보기 때문이다. 로그를 재시도 바깥에 두면 요청당 한 줄, 안쪽에 두면 시도마다 한 줄이 남는다. 타임아웃을 재시도 바깥에 두면 전체 예산이 되어 첫 시도가 멈추면 재시도할 기회가 없고, 안쪽에 두면 시도별 예산이 된다. 그래서 보통 시도별 타임아웃과 전체 마감 시간을 둘 다 둔다.

### TypeScript의 @데코레이터 문법과 GoF 데코레이터 패턴은 같은가요?

같은 생각에서 나왔지만 같지 않다. @ 문법은 클래스를 정의할 때 메서드나 클래스를 감싼 것으로 바꿔 끼우니 모든 인스턴스에 고정으로 적용된다. GoF 데코레이터는 실행 중에 객체 하나하나를 감싸서 인스턴스마다 다른 조합을 고를 수 있다. TypeScript 5.0부터 TC39 표준 데코레이터를 지원하고, 옛 experimentalDecorators와는 시그니처가 다르다.

### 데코레이터와 프록시는 어떻게 구분하나요?

둘 다 같은 인터페이스로 감싸서 코드 모양만으로는 구분이 안 되고 의도로 가른다. 데코레이터는 기능을 더하는 게 목적이고 바깥에서 받은 객체를 여러 겹 쌓는 것이 전제다. 프록시는 진짜 객체로 가는 접근을 통제하는 게 목적이라 지연 생성, 권한 확인, 원격 호출을 하고 진짜 객체의 생성을 직접 관리하는 경우가 많다.

### 데코레이터를 쓸 때 생기는 문제는 무엇인가요?

감싼 객체는 원래 객체와 다른 객체라서 동등성 비교나 instanceof 분기가 깨진다. 인터페이스가 넓으면 넘기기만 하는 메서드를 겹마다 다 구현해야 하고, 빠뜨리면 그 메서드는 겹을 건너뛴다. 겹이 많아지면 스택 트레이스가 길어지고 조립 순서를 이해하기 어려워진다. 그래서 인터페이스를 좁게 두고 조립은 한 곳에서 한다.

### 재시도 데코레이터를 아무 요청에나 붙여도 되나요?

안 된다. 서버는 처리했는데 응답만 늦은 경우 재시도가 같은 일을 한 번 더 한다. 조회처럼 여러 번 보내도 결과가 같은 요청에만 붙이거나, 결제 같은 요청에는 멱등성 키를 함께 보내 서버가 중복을 알아보게 한다. Promise.race로 만든 타임아웃은 요청을 취소하지 않으니 AbortSignal을 넘겨 연결까지 끊어야 한다.

### 실무에서 데코레이터 패턴을 본 예를 들어 주세요.

자바의 BufferedReader가 InputStreamReader를 감싸고 그게 FileInputStream을 감싸는 입출력 스트림이 대표적이다. Go에서는 http.Handler를 받아 http.Handler를 돌려주는 미들웨어, 표준 라이브러리의 http.TimeoutHandler와 http.StripPrefix가 그렇다. React의 고차 컴포넌트와 React.memo, Redux의 applyMiddleware가 dispatch를 감싸는 것도 같은 구조다.
