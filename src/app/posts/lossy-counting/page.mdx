<EasyIntro>
  실시간 인기 검색어를 만들 때 모든 검색어의 횟수를 정확히 적으면, 한 번만 나온 오타나 무작위 글자까지 영원히 자리를 차지해 메모리가 계속 늘어난다. 우리가 알고 싶은 건 자주 나온 몇 개뿐인데 나머지 수만 개를 세느라 공간을 쓰는 셈이다.

  Lossy Counting은 칠판에 검색어와 횟수를 적다가 정해진 건수마다 한 번씩 대청소를 하는 방법이다. 청소 때는 지금까지 거의 안 나온 검색어를 지운다. 지운 검색어가 나중에 다시 오면 처음부터 세되, "지워지기 전에 이만큼 놓쳤을 수도 있다"는 최대치를 옆에 함께 적어 둔다. 그래서 놓친 양은 정해 둔 작은 비율을 넘지 않고, 정말 자주 나온 검색어는 하나도 빠지지 않는다.

  조금 덜 세는 대신 칠판 크기는 검색어 종류가 아니라 허락한 오차에 맞춰 작게 유지된다. 트렌드를 볼 때는 시간대마다 칠판을 새로 쓰고 이전 시간대와 비교해야, 늘 많은 검색어 대신 갑자기 뜬 검색어가 보인다.
</EasyIntro>

"실시간 인기 검색어"를 만든다고 해 보자. 제일 쉬운 방법은 검색이 들어올 때마다 Redis `ZINCRBY trend 1 "검색어"`를 하고, 순위는 `ZREVRANGE`로 꺼내는 것이다. 처음엔 잘 돈다. 몇 주 뒤 Redis 메모리 그래프가 계단처럼 올라가 있다. 오타, 한 번만 검색된 긴 문장, 봇이 던진 무작위 문자열까지 모든 검색어가 한 번씩은 들어와 영원히 자리를 차지한다. 순위 10위 안에 들 일이 없는 것들이다.

숫자로 보면 이렇다. 검색어 10만 종류에서 Zipf 분포(지수 1.0)로 검색 100만 건을 만들어 그대로 `ZINCRBY`했다. 실제 서비스 로그가 아니라 분포를 가정한 데이터다.

```text
127.0.0.1:6731> ZCARD trend:all
(integer) 80742
127.0.0.1:6731> ZCOUNT trend:all 1 10
(integer) 72544
127.0.0.1:6731> MEMORY USAGE trend:all
(integer) 8283859
```

검색어 80,742개를 세느라 8MB를 썼는데, 그중 72,544개(90%)는 열 번 이하로 나온 꼬리다. 상위 1% 이상을 차지하는 검색어는 여덟 개뿐이다. 우리가 알고 싶은 건 그 여덟 개인데, 그걸 찾으려고 나머지 8만 개를 모두 정확히 세고 있다.

Lossy Counting은 이 낭비를 없앤다. "전체의 s 이상 나온 것"을 빠짐없이 찾되, 개수는 최대 εN만큼 덜 셀 수 있다고 허락하면, 메모리를 원소 종류 수가 아니라 1/ε에 비례하게 줄일 수 있다. 같은 데이터에서 항목 723개만 들고 상위 검색어를 모두 정확히 찾았다. 이 글은 Manku와 Motwani가 2002년에 낸 이 알고리즘이 어떻게 돌아가는지, 보장이 왜 성립하는지, ε와 s를 어떻게 고르는지, 실시간 트렌드에 어떻게 쓰는지를 본다. 측정은 모두 Node.js 22로 직접 돌린 결과이고, Redis는 7.0.15다.

이 주제의 다른 글: 아무 키의 횟수를 고정 메모리로 답하는 [Count-Min Sketch](/posts/count-min-sketch)는 같은 문제를 다른 방향에서 푼다. 두 방법을 같은 데이터로 비교한 내용은 그 글에 있다.

## 버킷마다 한 번 대청소를 한다

알고리즘은 스트림을 폭 w = ⌈1/ε⌉짜리 버킷으로 자른다. ε = 0.001이면 1,000건마다 버킷 하나다. 현재 버킷 번호를 b(1부터)라고 하자. 표에는 항목마다 세 값을 둔다.

규칙은 두 개다.

1. 원소 x가 오면 표에 있으면 f를 1 올리고, 없으면 (x, f=1, Δ=b−1)로 새 줄을 만든다.
2. 버킷이 끝날 때마다(w건마다) f + Δ ≤ b인 줄을 모두 지운다. 그리고 b를 1 올린다.

질문이 오면 f ≥ (s − ε)N인 줄을 내놓는다. N은 지금까지 본 건수다.

## 왜 εN보다 더 틀리지 않나

보장은 네 가지다.

- 덜 세는 양은 εN 이하다. f ≤ 진짜 횟수 ≤ f + εN.
- 진짜로 sN 이상 나온 원소는 반드시 결과에 들어간다(거짓 음성 없음).
- 진짜 횟수가 (s − ε)N보다 작은 원소는 결과에 들어가지 않는다.
- 표의 줄 수는 최대 (1/ε)·log(εN)이다.

첫 번째가 나머지의 바탕이라 이것만 따라가 보자. 버킷 b가 끝날 때 줄이 지워지는 조건은 f + Δ ≤ b다. 그 줄이 생기기 전 이 원소의 진짜 횟수는 Δ 이하였고, 생긴 뒤로는 f번 왔으니, 지워지는 순간 진짜 횟수는 f + Δ ≤ b 이하다. 그리고 버킷 번호 b는 지금까지 본 건수를 버킷 폭으로 나눈 값이라 b ≤ εN이다. 정리하면 이 원소가 잃어버린 횟수는 항상 εN 이하다. 다시 들어올 때는 Δ = b − 1로 그 불확실성을 기록하니, f + Δ는 항상 진짜 횟수의 상한이 된다.

그러면 두 번째 보장이 따라 나온다. 진짜 횟수가 sN 이상인 원소의 f는 최소 sN − εN = (s − ε)N이니 문턱을 넘는다. 대신 진짜 횟수가 (s − ε)N과 sN 사이인 원소는 결과에 들어올 수도 있다. 이건 거짓 양성이 아니라 허락된 오차 범위다.

공간 상한 (1/ε)·log(εN)은 직관적으로 이렇다. 매 버킷마다 한 번만 나온 원소는 바로 지워지고, 오래 살아남으려면 버킷당 평균 한 번 넘게 와야 한다. 그런 원소는 많아야 1/ε종류 언저리다. 로그는 최악의 순서에서 아직 지워지기 전인 줄들 몫이다. 원소 종류가 백만이든 십억이든 상관없다.

## 같은 데이터로 재 보기

앞의 검색 100만 건(검색어 80,742종류)에 ε를 바꿔 가며 돌렸다.

```text
eps     w      최대 항목  bound(1/e·ln(eN))  최대 과소추정  εN
0.01    100       101          921          9283     10000
0.001   1000       723         6908           928     1000
0.0001  10000      4871        46052            96     100
```

ε = 0.001에서 표가 가장 컸을 때도 723줄이었다. 정확히 세면 80,742줄이다. 100분의 1도 안 된다. 덜 센 양의 최댓값은 928로 εN = 1,000 안이고, 다른 ε에서도 모두 εN 안이었다. 실제 표 크기는 이론 상한(이 표에선 자연로그로 계산)보다 한참 작다. 상한은 최악의 순서를 가정한 값이고, 실제 데이터는 그렇게 짓궂지 않다.

이제 s = 0.01(전체의 1% 이상), ε = 0.001로 결과를 뽑았다.

```text
s=0.01 eps=0.001: output 9, true heavy 8, missed 0
q0 true 82886 est 82886 delta 0
q1 true 41673 est 41673 delta 0
q2 true 27790 est 27790 delta 0
...
q7 true 10343 est 10343 delta 0
q8 true 9291 est 9291 delta 0 (below s)
```

진짜로 1% 이상인 검색어 여덟 개를 하나도 빠짐없이 찾았다. 아홉 번째 q8은 9,291번으로 1%(10,000)에 못 미치지만 (s − ε)N = 9,000을 넘어서 결과에 들어왔다. 보장이 허락한 범위다. 인기 검색어들은 Δ가 0이고 f가 정확했다. 처음부터 자주 나와서 한 번도 지워지지 않았기 때문이다. 이건 데이터 성질이지 보장이 아니다. 나중에 뜬 원소는 Δ가 크다.

ε는 보통 s의 10분의 1로 잡는다. 논문도 그 정도를 예로 든다. ε를 줄이면 문턱 근처의 애매한 원소가 줄고 덜 세는 양도 준다. 대신 표가 1/ε에 비례해 커진다. 위 표에서 ε를 10배 줄일 때마다 표는 약 7배 커졌다.

직접 구현해 보자. `lossyCount`가 결과 원소를 f가 큰 순서(같으면 이름순)로 돌려주면 된다. 첫 두 테스트는 위 그림과 같은 스트림이고, 기대값은 Node.js에서 돌려 확인했다.

// f >= (s - eps) * N 인 원소를 f 내림차순(같으면 이름 오름차순)으로 돌려준다
function lossyCount(stream, eps, s) {
  const w = Math.ceil(1 / eps);     // 버킷 폭
  const table = new Map();          // 원소 → { f, d }
  let bucket = 1;                   // 현재 버킷 번호

    // 1. 있으면 f++, 없으면 { f: 1, d: bucket - 1 }
    // 2. (i + 1)이 w의 배수면 f + d <= bucket 인 줄을 지우고 bucket++

  solution={`function lossyCount(stream, eps, s) {
  const w = Math.ceil(1 / eps);
  const table = new Map();
  let bucket = 1;
  stream.forEach((x, i) => {
    const e = table.get(x);
    if (e) e.f++; else table.set(x, { f: 1, d: bucket - 1 });
    if ((i + 1) % w === 0) {
      for (const [k, v] of table) if (v.f + v.d <= bucket) table.delete(k);
      bucket++;
    }
  });
  const N = stream.length;
  return [...table]
    .filter(([, v]) => v.f >= (s - eps) * N)
    .sort((a, b) => b[1].f - a[1].f || (a[0] < b[0] ? -1 : 1))
    .map(([k]) => k);
}`}

## 인기 검색어는 "지금" 많은 것이다

전체 기간 누적으로 세면 어제 1위가 오늘도 1위다. 트렌드는 "최근 몇 분 동안 갑자기 많아진 것"이다. 그래서 실무에서는 스트림을 시간 창(window)으로 자르고, 창마다 Lossy Counting을 새로 돌려 상위 원소를 뽑은 뒤 이전 창과 비교한다.

같은 100만 건을 10만 건씩 창 10개로 나누고, 마지막 두 창에서만 검색의 3%를 새 검색어 `q_new`로 바꿨다. 창마다 s = 0.01, ε = 0.001로 돌렸다.

```text
window 1: heavy 9 top3 q0:8197 q1:4079 q2:2727
window 2: heavy 9 top3 q0:8455 q1:4136 q2:2794
(창 3~7도 상위 셋이 q0, q1, q2로 같다)
window 8: heavy 9 top3 q0:8396 q1:4135 q2:2725
window 9: heavy 10 top3 q0:7979 q1:4067 q_new:3046   rising: q_new 0→3046
window 10: heavy 9 top3 q0:8127 q1:3952 q_new:2961
```

9번 창에서 `q_new`가 처음 나타나 3위가 됐고, 이전 창에는 없던 원소라 "급상승"으로 잡혔다. 10번 창에서는 이미 상위권이니 급상승이 아니다. q0처럼 늘 많은 검색어는 순위는 높아도 트렌드가 아니다. 그래서 트렌드 점수는 보통 "이번 창의 횟수 / 이전 창들의 평균 횟수"처럼 비율로 만들고, 횟수가 너무 작은 원소는 문턱으로 거른다(1번에서 3번으로 늘어난 것도 3배다). 창을 딱 끊는 대신 오래된 횟수에 감쇠를 곱하는 방식도 있다.

## 정확한 답은 나중에 배치로 낸다

스트리밍으로 근사하는 이유는 "지금" 답해야 해서다. 하루 뒤에 정확한 순위가 필요하면 로그를 DB에 넣고 세면 된다. 같은 검색 100만 건을 PostgreSQL 16에 넣고 1% 이상인 검색어를 정확히 셌다.

```sql
-- 검색 로그 100만 줄: (id, term)
CREATE TABLE searches (id bigint, term text);
-- (COPY로 적재한 뒤)
ANALYZE searches;

-- 전체의 1%(10,000번) 이상 나온 검색어
EXPLAIN (ANALYZE, COSTS OFF)
SELECT term, count(*) FROM searches
GROUP BY term HAVING count(*) >= 10000
ORDER BY 2 DESC;
```

## 다른 방법들과 비교

자주 나온 원소를 찾는 스트리밍 알고리즘은 여러 개다. 고르는 기준은 "보장이 결정적인가", "아무 원소의 횟수를 물을 수 있는가", "합칠 수 있는가"다.

- Sticky Sampling: 같은 논문에 나온 확률적 버전이다. 원소를 점점 낮은 확률로 표에 넣는다. 공간 상한이 원소 수 N과 무관하게 (2/ε)·log(1/(sδ))로 나오지만 확률 δ로 틀릴 수 있다. 논문의 실험에서는 Lossy Counting이 실제로 공간을 덜 썼다.
- Misra–Gries: 카운터를 k개만 둔다. 새 원소가 오면 빈 칸에 넣고, 칸이 없으면 모든 카운터를 1씩 깎는다. 1982년 알고리즘이고 덜 세는 양이 N/(k+1) 이하다. Spark의 `DataFrame.stat.freqItems`가 이 계열(Karp, Schenker, Papadimitriou의 방법)을 쓴다고 문서에 적혀 있다. 그래서 결과에 거짓 양성이 섞일 수 있다고도 적혀 있다.
- Space-Saving: 카운터 k개가 꽉 차면 가장 작은 카운터를 새 원소에게 넘기고 그 값 + 1로 시작한다. 덜 세는 대신 더 센다. 구현이 단순하고 실무 정확도가 좋아 많이 쓴다.
- Count-Min Sketch: 원소를 저장하지 않고 고정 크기 카운터 표에 해시로 더한다. 어떤 원소의 횟수든 물을 수 있고 표끼리 더해서 합칠 수 있다. 대신 항상 더 세고, 상위 목록을 얻으려면 힙을 따로 둔다. [다음 글](/posts/count-min-sketch)에서 같은 데이터로 비교한다.

Lossy Counting은 결정적 보장(확률 없이 항상 εN 이하)과 단순함이 장점이다. 원소를 직접 들고 있으니 결과에 원소 이름이 바로 나온다. 약점은 표 크기가 데이터 순서에 따라 출렁이고(상한은 있지만 고정이 아니다), 표에 없는 원소의 횟수를 물으면 "εN 이하"라는 것밖에 모른다는 것이다.

결국 칸이 넉넉하면 무엇을 써도 상위 목록은 비슷하게 나오고, 차이는 칸이 빠듯할 때 드러난다. Lossy Counting은 표 크기가 데이터에 따라 출렁이는 대신 ε 하나로 보장을 말할 수 있고, Space-Saving은 칸 수를 정확히 고정하고 싶을 때 편하다.

## 현장에서 틀어지는 지점

결과에 원소가 너무 많이 나온다. 문턱 근처의 애매한 원소들이다. (s − ε)N과 sN 사이는 보장이 허락한 범위라 버그가 아니다. 결과가 깔끔해야 하면 ε를 줄이거나, 결과로 받은 몇십 개만 다음 창에서 정확히 다시 세서 확인한다. 후보를 줄인 뒤 정확히 세는 두 단계 방식이 흔하다.

나중에 뜬 원소의 숫자가 작게 나온다. 창 중간에 갑자기 뜬 원소는 들어올 때 Δ가 크고, 그 전의 횟수는 이미 버려졌다. f만 보여 주면 실제보다 작다. 그 원소가 처음부터 표에 있던 원소보다 늦게 집계되는 건 정상이고, 순위를 매길 때 f + Δ(상한)를 함께 보면 판단이 덜 틀린다.

정규화를 안 했다. "Docker", "docker", "docker "가 세 줄로 나뉘면 각자 문턱을 못 넘는다. 알고리즘보다 앞단의 키 정규화가 결과를 더 크게 바꾼다.

봇이 표를 흔든다. 무작위 문자열을 대량으로 보내도 보장은 깨지지 않고 표 크기도 상한 안에 있다. 하지만 같은 문자열을 반복해서 보내면 정말로 "자주 나온 원소"가 된다. 알고리즘은 횟수만 볼 뿐이다. 사용자나 IP당 한 번만 세는 중복 제거, 레이트 리밋을 앞에 둬야 트렌드가 조작되지 않는다.

ZSET에 다 쓰고 나중에 잘라 낸다. 처음 장면처럼 `ZINCRBY`로 모든 검색어를 쌓고 주기적으로 `ZREMRANGEBYRANK`로 하위를 지우는 방식도 있다. 이건 지운 원소의 횟수를 잊으면서 Δ를 기록하지 않으니 보장이 없다. 꾸준히 조금씩 오는 원소가 매번 지워져서 영영 위로 못 올라온다. 지울 거라면 Lossy Counting처럼 "지워질 때까지의 상한"을 같이 기록해야 한다.

## 조금 덜 세는 대신 빠짐없이

Lossy Counting은 스트림을 1/ε건짜리 버킷으로 자르고, 버킷이 끝날 때마다 f + Δ가 버킷 번호 이하인 줄을 지운다. 지울 때 잃은 횟수는 εN을 넘지 않고, 다시 들어올 때 Δ로 그 불확실성을 적어 두기 때문에, sN 이상 나온 원소는 빠짐없이 찾고 개수는 εN 안에서 덜 센다. 메모리는 원소 종류가 아니라 1/ε에 비례한다. 트렌드처럼 "지금" 많은 것을 찾을 때는 창마다 새로 돌리고 이전 창과 비율로 비교하며, 여러 워커로 나눌 때는 원소를 키로 파티션한다.

이 주제의 다른 글: 아무 원소의 횟수를 묻고 표끼리 합쳐야 한다면 [Count-Min Sketch](/posts/count-min-sketch)가 맞다. 서로 다른 원소가 몇 개인지만 궁금하다면 [HyperLogLog](/posts/hyperloglog)를 본다.

## 면접에서 나올 만한 질문

### Lossy Counting은 무엇을 보장하나?

전체 N건 중 sN 이상 나온 원소는 반드시 결과에 들어가고, 각 원소의 횟수는 최대 εN만큼만 덜 센다. 진짜 횟수가 (s − ε)N보다 작은 원소는 결과에 들어가지 않는다. 확률이 아니라 항상 성립하는 결정적 보장이다. 표의 크기는 최대 (1/ε)·log(εN)줄이다.

### Δ는 왜 필요한가?

원소가 지워졌다가 다시 들어오면 그 전 횟수를 모르기 때문이다. 지워지는 조건이 f + Δ ≤ b라서, 지금 버킷이 b일 때 새로 들어온 원소의 과거 횟수는 b − 1을 넘을 수 없다. 그 값을 Δ로 적어 두면 f + Δ가 항상 진짜 횟수의 상한이 되고, 이게 다음 삭제 판단과 εN 보장의 근거가 된다.

### 덜 세는 양이 εN을 넘지 않는 이유는?

어떤 원소가 버킷 b 끝에서 지워질 때 진짜 횟수는 f + Δ ≤ b 이하였다. 버킷 번호 b는 본 건수를 버킷 폭 1/ε로 나눈 값이라 εN 이하다. 그래서 지우면서 잃는 횟수는 εN을 넘지 않고, 표에 남아 있는 동안은 정확히 센다.

### ε와 s는 어떻게 고르나?

s는 알고 싶은 문턱(예: 전체의 1%)이고, ε는 보통 s의 10분의 1로 잡는다. ε가 작을수록 문턱 근처의 애매한 결과와 덜 세는 양이 줄지만 표가 1/ε에 비례해 커진다. 실측에서 ε를 10배 줄일 때 표는 약 7배 커졌다.

### 인기 검색어처럼 최근 트렌드를 잡으려면?

누적으로 세면 늘 많은 원소가 계속 1위라 트렌드가 안 보인다. 스트림을 시간 창으로 자르고 창마다 Lossy Counting으로 상위 후보를 뽑아, 이전 창들과 비교한 증가 비율로 순위를 매긴다. 횟수가 너무 작은 원소는 문턱으로 거르고, 봇 반복을 막으려면 사용자당 중복 제거를 앞에 둔다.

### 워커 여러 대로 나눠서 세려면 무엇을 주의하나?

같은 원소가 항상 같은 워커로 가도록 원소를 키로 파티션해야 한다. 무작위로 나누면 인기 원소의 횟수가 흩어져 어느 워커에서도 문턱을 못 넘을 수 있고, Lossy Counting 표는 지운 시점이 달라 단순히 더해 합칠 수 없다. 합치기가 꼭 필요하면 더해서 합칠 수 있는 Count-Min Sketch를 쓴다.

### Lossy Counting과 Count-Min Sketch는 언제 각각 쓰나?

상위 원소 목록이 필요하고 결정적 보장을 원하면 Lossy Counting이다. 원소 이름을 들고 있어 결과가 바로 나온다. 아무 원소의 횟수를 물어야 하거나, 여러 서버의 결과를 더해서 합쳐야 하거나, 메모리를 정확히 고정해야 하면 Count-Min Sketch가 낫다. 대신 그쪽은 항상 더 세고 상위 목록을 위해 힙을 따로 둔다.
