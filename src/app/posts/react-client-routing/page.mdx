쇼핑몰 SPA에서 상품 상세 주소 `/products/42`를 북마크했다가 다시 열었더니 404가 난다. 목록에서 눌러 들어가면 잘 나오던 페이지다. 그걸 고치고 나니 다른 문제가 보인다. 상품 페이지에 들어갈 때마다 스피너가 세 번 연달아 돈다. 상단 사용자 메뉴가 뜨고, 그다음 카테고리 사이드바가, 마지막으로 상품 정보가 뜬다. 하나씩 차례로.

새로고침 404는 서버가 `/products/42`라는 파일을 모르기 때문에 난다. 서버가 모든 앱 주소에 `index.html`을 주게 하는 SPA 폴백으로 고치는데, 그 원리와 함정은 [CSR과 SPA](/posts/rendering-csr-spa)에서 다뤘다. 이 글은 그다음 이야기다. 브라우저 안에서 주소를 화면으로 바꾸는 라우터가 무엇을 하는지, 스피너 세 개가 왜 줄지어 도는지, 주소를 데이터와 코드와 상태의 중심에 두면 무엇이 달라지는지를 React Router 8.5(7에서 정한 API가 거의 그대로다)와 TanStack Router 1.170으로 확인한다.

## 주소 하나가 화면 세 겹이 된다

`/products/42`라는 주소는 사실 화면 하나가 아니다. 사이트 전체 틀(헤더, 사용자 메뉴), 상품 영역의 틀(카테고리 사이드바), 그리고 상품 42번의 상세가 겹쳐 있다. 주소를 `/products/43`으로 바꾸면 안쪽 한 겹만 바뀌고 바깥 두 겹은 그대로 남아야 한다. 이걸 중첩 라우트라고 부른다.

React Router의 데이터 모드에서는 라우트를 트리로 적는다.

```tsx
// main.tsx
import { createBrowserRouter } from "react-router";
import { RouterProvider } from "react-router/dom";
import { createRoot } from "react-dom/client";

const router = createBrowserRouter([
  {
    path: "/",
    Component: RootLayout,          // 헤더, 사용자 메뉴
    children: [
      { index: true, Component: Home },
      {
        path: "products",
        Component: ProductsLayout,  // 카테고리 사이드바
        children: [
          { index: true, Component: ProductList },
          { path: ":productId", Component: ProductDetail },
        ],
      },
    ],
  },
]);

createRoot(document.getElementById("root")!).render(<RouterProvider router={router} />);
```

부모 컴포넌트는 자식이 들어갈 자리를 `<Outlet />`으로 비워 둔다.

```tsx
import { Outlet, NavLink } from "react-router";

function ProductsLayout() {
  return (
    <div className="products">
      <aside>
        <NavLink to="/products?category=shoes">신발</NavLink>
      </aside>
      <main>
        <Outlet /> {/* 여기에 ProductList 또는 ProductDetail이 들어간다 */}
      </main>
    </div>
  );
}
```

아래 그림에서 점이 흐르는 방향이 주소가 화면으로 풀리는 순서다. `/products/42`는 루트에서 출발해 `products`를 지나 `:productId`까지 세 라우트에 걸리고, 각 라우트의 컴포넌트가 부모의 `Outlet` 자리에 하나씩 끼워진다.

동적 세그먼트 `:productId`의 값은 `useParams()`로 읽는다. 값은 항상 문자열이다. `/products/042`와 `/products/42`는 다른 주소지만 `Number()`로 바꾸면 같은 상품이 된다. 이런 주소가 섞이면 검색 엔진에는 중복 페이지로 보이니, 정규화하지 않은 주소는 정식 주소로 리다이렉트한다.

## 어떤 라우트가 이기나

라우트가 많아지면 주소 하나에 여러 패턴이 맞는 경우가 생긴다. `/products/new`는 `/products/new`에도, `/products/:id`에도, `/products/*`에도 맞는다. 예전 React Router(v5)는 위에서부터 처음 맞는 것을 골랐고, 그래서 라우트 순서를 바꾸다 "상품 등록 페이지가 상세 페이지로 뜬다"는 버그가 흔했다. v6부터는 순서가 아니라 점수로 고른다. 설치된 패키지의 `computeScore`를 열어 보면 규칙이 짧다.

```text
조각 수만큼 기본 점수 + 정적 조각 10 + 동적 조각(:id) 3 + 빈 조각 1, 스플랫(*)이 있으면 -2
점수가 같으면 먼저 적은 라우트
```

React Router의 `matchRoutes`로 실제 결과를 확인했다. 라우트 배열은 일부러 `/products/:id`를 맨 앞에 뒀다.

```text
/products/new          → /products/new {}
/products/42           → /products/:id {"id":"42"}
/products/42/reviews   → /products/* {"*":"42/reviews"}
/ko/products/42        → /:lang/products/:id {"lang":"ko","id":"42"}
```

적은 순서와 상관없이 가장 구체적인 패턴이 이겼다. 직접 짜 보면 규칙이 손에 익는다. 아래 `matchRoute`는 패턴 목록과 경로를 받아 이긴 패턴과 파라미터를 돌려준다. 테스트의 기댓값은 모두 React Router의 `matchRoutes` 결과와 같은지 대조해 둔 값이다.

  solution={`function matchRoute(patterns, pathname) {
  const score = (pattern) => {
    const segs = pattern.split("/");
    let s = segs.length + (segs.includes("*") ? -2 : 0);
    for (const seg of segs) {
      if (seg === "*") continue;
      s += seg.startsWith(":") ? 3 : seg === "" ? 1 : 10;
    }
    return s;
  };
  const ranked = patterns
    .map((p, i) => ({ p, i, s: score(p) }))
    .sort((a, b) => b.s - a.s || a.i - b.i);

  const url = pathname.split("/").filter(Boolean);
  for (const { p } of ranked) {
    const segs = p.split("/").filter(Boolean);
    const params = {};
    let ok = true;
    for (let k = 0; k < segs.length && ok; k++) {
      const seg = segs[k];
      if (seg === "*") { params["*"] = url.slice(k).join("/"); break; }
      if (k >= url.length) ok = false;
      else if (seg.startsWith(":")) params[seg.slice(1)] = decodeURIComponent(url[k]);
      else if (seg.toLowerCase() !== url[k].toLowerCase()) ok = false;

    if (ok) return { path: p, params };
  }
  return null;

## 컴포넌트가 데이터를 부르면 폭포가 된다

처음 장면의 스피너 세 개로 돌아가자. 세 레이아웃이 각자 `useEffect`로 데이터를 불렀다.

```tsx
function RootLayout() {
  const [user, setUser] = useState<User | null>(null);
  useEffect(() => { fetchUser().then(setUser); }, []);
  if (!user) return <Spinner />;          // 사용자 정보가 올 때까지 Outlet을 안 그린다
  return <Shell user={user}><Outlet /></Shell>;
}
// ProductsLayout, ProductDetail도 같은 모양
```

부모가 데이터를 받기 전에는 `Outlet`을 그리지 않으니 자식 컴포넌트는 마운트조차 안 된다. 자식의 `useEffect`는 부모가 끝난 뒤에야 출발한다. 요청 하나가 300ms라면 세 겹이 차례로 900ms를 쓴다. 렌더링해야 데이터를 부르는 이 방식을 fetch-on-render라고 부른다. 부모에서 스피너를 안 그리고 바로 `Outlet`을 그려도 문제가 남는다. 상세 페이지 코드가 별도 청크라면 청크를 받은 뒤에야 컴포넌트가 실행되고 그제야 요청이 출발한다.

그런데 라우터는 주소를 읽는 순간 이미 세 라우트가 걸린다는 걸 안다. 라우트마다 데이터를 부르는 함수를 붙여 두면 렌더링 전에 셋을 한꺼번에 출발시킬 수 있다. 이것이 loader다.

정말 동시에 도는지 확인했다. 브라우저 없이 Node에서 `createMemoryRouter`로 같은 트리를 만들고, loader마다 300ms를 기다리게 했다.

```tsx
const routes = [{
  path: "/", loader: () => wait(300, "root(user)"),
  children: [{
    path: "products", loader: () => wait(300, "products(categories)"),
    children: [{ path: ":productId", loader: ({ params }) => wait(300, `product(${params.productId})`) }],
  }],
}];
const router = createMemoryRouter(routes, { initialEntries: ["/products/42"] });
```

```text
  42ms root(user) start
  43ms products(categories) start
  43ms product(42) start
 344ms root(user) end
 344ms products(categories) end
 344ms product(42) end
 346ms initialized: / > products > :productId
```

세 loader가 1ms 안에 함께 출발했고 300ms 뒤에 함께 끝났다. 900ms가 300ms가 됐다. 대신 자식 loader는 부모 loader의 결과를 받을 수 없다. 상품 요청에 사용자 정보가 꼭 필요하다면 API 쪽에서 해결하거나(토큰은 쿠키나 헤더로 어차피 같이 간다) 그 의존을 한 loader 안에서 직접 기다린다.

## loader와 action: 데이터를 주소에 붙인다

loader는 `params`와 `request`를 받아 값을 돌려주는 평범한 함수다. 컴포넌트는 `useLoaderData()`로 꺼낸다.

```tsx
import { useLoaderData, type LoaderFunctionArgs } from "react-router";

export async function productLoader({ params, request }: LoaderFunctionArgs) {
  const res = await fetch(`/api/products/${params.productId}`, { signal: request.signal });
  if (res.status === 404) throw new Response("상품 없음", { status: 404 });
  return res.json() as Promise<Product>;
}

function ProductDetail() {
  const product = useLoaderData() as Product;
  return <h1>{product.name}</h1>;
}
```

`request.signal`을 넘기는 것이 작은 차이를 만든다. 사용자가 상품 42를 누르고 로딩 중에 43을 누르면 라우터가 앞 내비게이션을 취소하고 그 signal을 중단시킨다. 넘기지 않으면 버려진 요청이 끝까지 돌고, 응답이 늦게 도착한 쪽이 화면을 덮는 경쟁 조건을 걱정하게 된다. 라우터는 마지막 내비게이션의 결과만 반영하니 그 걱정은 라우터가 대신 한다.

loader에서 던진 `Response`나 에러는 가장 가까운 라우트의 `ErrorBoundary`(또는 `errorElement`)가 받는다. 상세 라우트에 경계를 두면 상품 하나가 없어도 헤더와 사이드바는 멀쩡히 남는다. 경계의 원리는 [Suspense와 에러 경계](/posts/react-suspense-error-boundary)에서 다뤘다.

데이터를 바꾸는 쪽은 action이다. `<Form method="post">`로 제출하면 라우터가 그 라우트의 action을 부르고, 끝나면 화면에 걸린 loader들을 다시 부른다(재검증). 장바구니에 담은 뒤 헤더의 장바구니 개수를 손으로 갱신하지 않아도 된다는 뜻이다.

```tsx
import { Form, redirect, useNavigation, type ActionFunctionArgs } from "react-router";

export async function addToCartAction({ request, params }: ActionFunctionArgs) {
  const form = await request.formData();
  await fetch("/api/cart", { method: "POST", body: JSON.stringify({ id: params.productId, qty: form.get("qty") }) });
  return redirect("/cart");
}

function AddToCart() {
  const navigation = useNavigation();
  const busy = navigation.state === "submitting";
  return (
    <Form method="post">
      <input name="qty" type="number" defaultValue={1} />
      <button disabled={busy}>{busy ? "담는 중" : "장바구니 담기"}</button>
    </Form>
  );
}
```

주소를 바꾸지 않는 작은 변경(좋아요 버튼, 목록 안의 체크박스)은 `useFetcher()`의 `fetcher.Form`을 쓴다. 내비게이션 없이 action을 부르고 재검증만 한다. 재검증이 너무 잦다면 라우트에 `shouldRevalidate`를 둬서 "검색 파라미터만 바뀌었을 때는 사이드바 loader를 다시 부르지 않는다" 같은 조건을 건다. 폼과 낙관적 업데이트 자체는 [React 폼](/posts/react-forms-actions)에 있다.

loader가 있다고 데이터 캐시 라이브러리가 필요 없어지는 건 아니다. React Router의 loader는 내비게이션마다 다시 불리고 결과를 오래 들고 있지 않는다. 같은 데이터를 여러 화면에서 쓰거나 백그라운드 갱신이 필요하면 loader 안에서 TanStack Query의 `queryClient.ensureQueryData`를 부르는 식으로 캐시를 끼운다. loader는 "언제 출발할지"를, 캐시는 "얼마나 들고 있을지"를 맡는다. 캐시 쪽 이야기는 [클라이언트 데이터 캐시](/posts/client-data-cache)에 있다.

## 라우트 단위로 코드를 자른다

라우트는 코드를 자르기 가장 좋은 경계다. 사용자는 한 번에 한 주소에 있으니까. 데이터 모드에서는 `lazy`로 라우트의 컴포넌트와 loader를 나중에 받는다.

```tsx
{
  path: ":productId",
  lazy: async () => {
    // 컴포넌트와 loader를 동시에 받는다
    const [{ default: Component }, { productLoader: loader }] = await Promise.all([
      import("./product-detail"),
      import("./product-loader"),
    ]);
    return { Component, loader };
  },
}
```

loader를 컴포넌트 파일과 같은 청크에 두면 다시 폭포가 생긴다. 청크를 내려받아야 loader를 알 수 있고, 그다음에야 데이터 요청이 출발한다. 문서 예제가 굳이 `product-loader`를 따로 import하는 이유다. loader 파일은 작으니 금방 오고, 무거운 컴포넌트 청크와 데이터 요청이 나란히 진행된다. 더 나아가 loader를 lazy 밖, 처음 번들에 두면 청크와 데이터가 완전히 동시에 출발한다. 청크를 어떻게 나누고 언제 미리 받을지는 [번들 쪼개기](/posts/code-splitting)의 "라우트로 자를까, 컴포넌트로 자를까"를 참고한다.

## 검색 파라미터를 상태로 쓰기

상품 목록의 카테고리, 정렬, 페이지 번호를 `useState`에 두면 새로고침하거나 링크를 공유할 때 사라진다. 뒤로 가기를 눌러도 이전 필터로 돌아가지 않는다. 이 값들은 주소에 둬야 한다. 주소가 곧 상태다.

```tsx
import { useSearchParams } from "react-router";

function ProductList() {
  const [params, setParams] = useSearchParams();
  const page = Number(params.get("page") ?? "1");   // 항상 문자열이라 직접 바꾼다
  const sort = params.get("sort") === "price" ? "price" : "new";

  const goPage = (p: number) =>
    setParams((prev) => { prev.set("page", String(p)); return prev; });

  const changeSort = (s: string) =>
    setParams((prev) => { prev.set("sort", s); prev.delete("page"); return prev; }, { replace: true });
  // ...
}
```

`useSearchParams`는 브라우저의 `URLSearchParams`를 그대로 준다. 값은 모두 문자열이고, 없을 수도 있고, 사용자가 주소창에 `?page=abc`를 쳐 넣을 수도 있다. 그래서 읽을 때마다 검증하고 기본값을 정한다. 페이지 이동은 히스토리에 남기는 게 자연스럽지만, 검색어 입력처럼 글자마다 바뀌는 값은 `replace: true`로 덮어써야 뒤로 가기 한 번에 한 글자씩 지워지는 일이 없다. 정렬을 바꿀 때 페이지를 지우는 것도 흔히 빠뜨린다. 5페이지에서 정렬을 바꾸면 새 정렬의 5페이지가 나와 버린다.

검색 파라미터를 바꾸면 내비게이션이 일어나 loader도 다시 불린다. loader에서 `new URL(request.url).searchParams`로 읽으면 필터가 데이터 요청에 그대로 이어진다.

## 들어가기 전에 막는 자리

로그인하지 않은 사용자가 `/orders`에 들어오면 로그인 화면으로 보내고, 로그인 뒤에는 원래 가려던 주소로 돌려보내야 한다. 컴포넌트 안에서 `useEffect`로 검사해 `navigate`하면 보호된 화면이 한 번 그려졌다가 튕긴다. 라우터에는 렌더링 전에 끼어드는 자리가 있다.

React Router에서는 loader에서 `redirect`를 던지는 것이 가장 단순하다. 여러 라우트를 한꺼번에 막으려면 부모 라우트에 미들웨어를 둔다. 미들웨어는 v8에서 플래그 없이 항상 켜져 있고, 자식 loader가 돌기 전에 위에서부터 차례로 실행된다.

```tsx
import { redirect, createContext } from "react-router";

const userContext = createContext<User>();

async function authMiddleware({ request, context }) {
  const user = await getSessionUser();
  if (!user) {
    const from = new URL(request.url).pathname;
    throw redirect(`/login?redirect=${encodeURIComponent(from)}`);
  }
  context.set(userContext, user);   // 아래 loader들이 context.get(userContext)로 꺼낸다
}

createBrowserRouter([
  { path: "/login", Component: Login },
  { path: "/", middleware: [authMiddleware], Component: AppLayout, children: [/* 보호된 라우트 */] },
]);
```

`redirect` 쿼리를 그대로 `navigate`에 넣으면 `?redirect=https://evil.example` 같은 주소로 외부 사이트에 보내는 오픈 리다이렉트가 된다. `/`로 시작하고 `//`로 시작하지 않는 경로만 받는다.

하나 분명히 해 둘 것이 있다. 클라이언트 라우트 가드는 보안 장치가 아니라 사용자 경험 장치다. 번들 안의 코드는 누구나 읽고 고칠 수 있으니, 주문 목록 API가 서버에서 토큰을 검사하지 않으면 가드는 아무것도 막지 못한다. 토큰을 어디에 두고 어떻게 갱신하는지는 [SPA 인증 토큰 저장](/posts/spa-auth-token-storage)에서 다뤘다.

## 뒤로 가기를 눌렀을 때 스크롤

긴 상품 목록을 내려 보다 하나를 눌러 상세로 갔다가 뒤로 가기를 누른다. 목록 맨 위로 돌아가 있으면 사용자는 짜증이 난다. 문서를 통째로 다시 받던 시절에는 브라우저가 스크롤을 기억했다. SPA에서는 브라우저가 복원하려는 시점에 아직 목록이 그려지지 않았거나 데이터가 오는 중이라 복원이 어긋난다.

React Router는 루트 레이아웃에 `<ScrollRestoration />`을 한 번 두면 위치마다 스크롤을 `sessionStorage`에 저장했다가, 뒤로 가기로 돌아왔을 때 loader가 끝나고 화면이 그려진 뒤에 복원한다. 새 주소로 갈 때는 맨 위로 올린다. 기본 키는 히스토리 항목마다 달라서, 같은 목록 주소라도 링크를 눌러 새로 들어오면 맨 위에서 시작한다. 탭 전환처럼 검색 파라미터만 바뀔 때 위치를 유지하고 싶다면 `getKey`로 경로 이름을 키로 쓴다.

```tsx
<ScrollRestoration getKey={(location) => location.pathname} />
```

복원이 잘 안 되는 흔한 원인은 데이터를 loader가 아니라 컴포넌트의 `useEffect`에서 받는 경우다. 라우터 입장에서는 렌더링이 끝났는데 목록은 아직 비어 있어서 복원할 높이가 없다. 여기서도 loader가 답이 된다.

## React Router의 세 가지 모드

지금까지 본 `createBrowserRouter`는 React Router가 말하는 데이터 모드다. React Router는 쓰는 최상위 API에 따라 모드가 셋으로 나뉜다.

선언 모드는 `<BrowserRouter>` 안에 `<Routes>`와 `<Route>`를 JSX로 적는 예전 방식이다. 주소와 컴포넌트를 잇고 `Link`, `useNavigate`, `useParams`를 쓰는 데까지다. loader, action, `useFetcher`는 없다. 데이터 모드는 라우트 설정을 렌더링 밖으로 꺼내서 loader, action, 대기 상태, 미들웨어를 더한다. 프레임워크 모드는 데이터 모드를 Vite 플러그인으로 감싼 것이다. v7에서 Remix를 흡수하면서 생겼다.

```ts
// app/routes.ts
import { type RouteConfig, index, route, layout } from "@react-router/dev/routes";

export default [
  index("./routes/home.tsx"),
  layout("./routes/products-layout.tsx", [
    route("products/:productId", "./routes/product.tsx"),
  ]),
] satisfies RouteConfig;
```

```tsx
// app/routes/product.tsx
import type { Route } from "./+types/product";

export async function loader({ params }: Route.LoaderArgs) {
  return { product: await getProduct(params.productId) };  // params.productId가 타입으로 보장된다
}

export default function Product({ loaderData }: Route.ComponentProps) {
  return <h1>{loaderData.product.name}</h1>;
}
```

라우트 파일마다 `./+types/...` 타입이 생성돼 `params`와 `loaderData`의 타입이 라우트 설정에서 바로 나온다. 라우트 모듈 단위로 코드가 자동으로 잘리고, 설정 파일의 `ssr`과 `prerender`로 SSR, 정적 생성, SPA 중에서 고른다. 서버에서 도는 `loader`와 브라우저에서 도는 `clientLoader`를 나눠 쓸 수 있다.

v8은 7에서 예고했던 것을 정리한 판이다. `react-router-dom` 패키지가 없어져서 `RouterProvider`는 `react-router/dom`에서, 나머지는 모두 `react-router`에서 가져온다. 패키지가 ESM 전용이 됐고, 미들웨어가 플래그 없이 항상 켜지며, Node 22.22와 React 19.2.7 이상을 요구한다. v6 코드에서 `react-router-dom` import가 보이면 v8 업그레이드의 첫 작업은 import 경로 정리다.

## TanStack Router: 타입이 주소를 안다

React Router 데이터 모드의 `Link to`는 그냥 문자열이다. `/prodcts`라고 오타를 내도 컴파일은 통과하고, 누르면 404가 난다. TanStack Router는 라우트 트리 전체를 타입으로 만들어서 이걸 컴파일 때 잡는다.

```tsx
import { createRootRoute, createRoute, createRouter, Link, Outlet, redirect } from "@tanstack/react-router";

const rootRoute = createRootRoute({ component: () => <Outlet /> });

type ProductSearch = { page: number; sort: "price" | "new" };

const productsRoute = createRoute({
  getParentRoute: () => rootRoute,
  path: "/products",
  // 주소의 검색 파라미터를 검증해 타입 있는 값으로 바꾼다
  validateSearch: (search: Record<string, unknown>): ProductSearch => ({
    page: Number(search.page ?? 1),
    sort: search.sort === "price" ? "price" : "new",
  }),
});

const productRoute = createRoute({
  getParentRoute: () => rootRoute,
  path: "/products/$productId",
  beforeLoad: ({ location }) => {
    if (!isLoggedIn()) throw redirect({ to: "/login", search: { redirect: location.href } });
  },
  loader: ({ params }) => fetchProduct(params.productId),
});

// loginRoute(/login, redirect 검색 파라미터)는 같은 모양이라 생략
const routeTree = rootRoute.addChildren([productsRoute, productRoute, loginRoute]);
export const router = createRouter({ routeTree, defaultPreload: "intent", scrollRestoration: true });

declare module "@tanstack/react-router" {
  interface Register { router: typeof router }   // 이 한 줄로 앱 전체의 Link가 이 트리를 안다
}
```

동적 세그먼트를 `:id` 대신 `$productId`로 쓴다. 일부러 틀린 링크 세 개를 넣고 `tsc`를 돌렸다.

```tsx
<Link to="/products/$productId" params={{ id: "42" }}>wrong param</Link>
<Link to="/prodcts">typo</Link>
<Link to="/products" search={{ page: 2, sort: "cheap" }}>bad search</Link>
```

```text
ts-router.tsx(49,49): error TS2353: Object literal may only specify known properties, and 'id' does not exist in type '{ productId: string; } | ParamsReducerFn<...>'.
ts-router.tsx(50,13): error TS2820: Type '"/prodcts"' is not assignable to type '"/" | "/products" | "/products/$productId" | "/login" | "." | ".."'. Did you mean '"/products"'?
ts-router.tsx(51,47): error TS2322: Type '"cheap"' is not assignable to type '"price" | "new"'.
```

파라미터 이름, 경로 오타, 검색 파라미터 값이 모두 컴파일 에러가 됐다. 라우트 이름을 바꾸면 그 주소로 가는 모든 링크가 빨갛게 표시되니 리팩터링이 겁나지 않다. 검색 파라미터를 상태로 쓰는 일에서 특히 강하다. `validateSearch`를 한 번 통과한 값이라 `Route.useSearch()`가 주는 `page`는 이미 숫자다. React Router에서 매번 하던 문자열 파싱과 기본값 처리를 라우트 정의 한 곳으로 모은 셈이다. 검증에는 Zod 같은 스키마 라이브러리를 그대로 꽂을 수 있다.

실행 순서도 구분해 둔다. `beforeLoad`는 부모부터 자식으로 차례로 돌고, 그 결과를 아래로 컨텍스트로 넘길 수 있다. 가드와 인증 정보 주입이 여기 들어간다. `loader`는 그다음에 매칭된 라우트 모두에서 동시에 돈다. React Router의 미들웨어와 loader의 관계와 같은 그림이다. TanStack Router의 loader 결과는 라우터가 캐시한다. 기본 `staleTime`이 0이라 같은 주소로 돌아오면 캐시된 값을 먼저 보여 주고 뒤에서 다시 부르며(stale-while-revalidate), `staleTime`을 늘리면 그 시간 안에는 다시 부르지 않는다. `defaultPreload: "intent"`는 링크에 마우스를 올리거나 터치를 시작하는 순간 그 라우트의 코드와 loader를 미리 부른다.

실무에서는 `createRoute`를 손으로 엮기보다 파일 기반 라우팅을 쓴다. Vite 플러그인이 `src/routes/products.$productId.tsx` 같은 파일 이름에서 라우트 트리와 타입을 생성하고, `autoCodeSplitting`을 켜면 라우트 컴포넌트를 자동으로 별도 청크로 뺀다. 설치된 플러그인의 기본 분할 묶음을 열어 보면 `component`, `errorComponent`, `notFoundComponent`만 있고 `loader`는 빠져 있다. 앞 절의 폭포를 피하려고 loader는 처음 번들에 남기는 것이다. 생성된 `routeTree.gen.ts`는 커밋하고 손으로 고치지 않는다.

## 무엇을 고를까

셋 다 중첩 라우트, 라우트 단위 데이터 로딩, 코드 분할을 한다. 갈리는 지점은 "서버를 얼마나 쓰느냐"와 "타입을 얼마나 원하느냐"다.

로그인 뒤에만 쓰는 관리 도구나 대시보드처럼 검색 노출이 필요 없고 정적 호스팅으로 충분한 SPA라면 클라이언트 라우터가 맞다. 그중 검색 파라미터가 복잡한 화면(필터 열 개짜리 목록, 대시보드 조건)이 많으면 TanStack Router의 타입 있는 검색 파라미터가 큰 차이를 만든다. 이미 React Router를 쓰는 코드가 많거나 팀이 익숙하다면 데이터 모드로 올려서 loader부터 들이는 편이 이전 비용이 적다.

첫 HTML에 내용이 있어야 하는 서비스(상품 페이지, 블로그)라면 서버 렌더링이 되는 쪽으로 간다. React Router 프레임워크 모드, TanStack Router 위에 서버를 얹은 TanStack Start, Next.js App Router가 후보다. Next.js는 파일 시스템이 곧 라우트이고 기본이 서버 컴포넌트라, 데이터를 서버에서 읽어 HTML과 함께 보내는 쪽에 가장 깊이 들어가 있다. 대신 서버를 운영해야 하고 캐시 규칙을 따로 익혀야 한다. 그 부담은 [Next.js 직접 운영하기](/posts/nextjs-self-hosting-deployment)와 [Next.js App Router는 언제 정적이고 언제 동적인가](/posts/nextjs-static-dynamic-rendering)에 정리했다. 서버 컴포넌트 자체는 [React 서버 컴포넌트](/posts/react-server-components)에 있다.

어느 쪽이든 판단 기준은 같다. 주소를 읽는 순간 데이터와 코드가 함께 출발하는가. 상태가 주소에 있어서 새로고침과 공유와 뒤로 가기를 견디는가. 이 두 질문에 예라고 답하게 해 주는 도구면 된다.

## 다시 스피너 세 개로

새로고침 404는 서버의 SPA 폴백으로 고친다. 스피너 세 개는 데이터를 컴포넌트가 아니라 라우트에 붙여서 고친다. 라우터는 주소를 읽는 순간 어떤 라우트들이 걸리는지 알기 때문에, 그 loader들을 렌더링 전에 함께 출발시켜 900ms를 300ms로 만든다. 같은 이유로 코드 청크와 loader는 따로 두고, 필터와 페이지는 주소에 두고, 가드는 렌더링 전 자리에 두되 진짜 검사는 서버에 맡긴다. 주소를 앱의 중심에 두는 것이 클라이언트 라우팅의 거의 전부다.

## 면접에서 나올 만한 질문

### 클라이언트 라우팅은 어떻게 동작하나

History API의 `pushState`로 주소만 바꾸고 문서는 다시 받지 않는다. 라우터는 주소가 바뀌면 라우트 설정과 대조해 걸리는 라우트들을 고르고, 바깥 레이아웃부터 안쪽 페이지까지 `Outlet` 자리에 컴포넌트를 끼워 그린다. 주소 바깥 레이아웃은 그대로 남고 바뀐 겹만 다시 그린다. 서버는 앱 주소 전부에 같은 `index.html`을 줘야 새로고침 404가 나지 않는다.

### 주소 하나에 여러 라우트가 맞으면 무엇이 이기나

React Router v6 이후는 적은 순서가 아니라 점수로 고른다. 조각 수에 정적 조각 10, 동적 조각 3, 빈 조각 1을 더하고 스플랫이 있으면 2를 빼서, 가장 구체적인 패턴이 이긴다. 그래서 `/products/new`는 `/products/:id`보다 앞에 적지 않아도 이긴다. 점수가 같을 때만 먼저 적은 라우트가 이긴다.

### fetch-on-render가 왜 느리고 loader는 무엇이 다른가

컴포넌트가 렌더링된 뒤 `useEffect`로 데이터를 부르면, 부모가 데이터를 받아 자식을 그릴 때까지 자식의 요청이 출발하지 못해 중첩 깊이만큼 요청이 줄을 선다. loader는 라우터가 주소를 매칭한 직후 렌더링 전에 걸린 라우트 모두의 loader를 동시에 부른다. 실험에서 300ms짜리 세 겹이 900ms에서 300ms로 줄었다. 대신 자식 loader는 부모 loader 결과를 기다리지 않으니 의존이 있으면 따로 처리한다.

### lazy 라우트에서 loader를 컴포넌트와 같은 파일에 두면 무엇이 문제인가

청크를 내려받아야 loader를 알 수 있어서 "청크 다운로드 → 데이터 요청"의 폭포가 다시 생긴다. loader를 작은 별도 모듈로 나눠 `Promise.all`로 함께 import하거나, loader를 처음 번들에 두면 청크와 데이터 요청이 나란히 진행된다. TanStack Router의 자동 코드 분할이 컴포넌트만 떼어 내고 loader는 남기는 것도 같은 이유다.

### 필터와 페이지 번호를 왜 검색 파라미터에 두나

새로고침, 링크 공유, 뒤로 가기를 견디는 상태가 되기 때문이다. `useState`에 두면 셋 다 깨진다. 대신 값이 항상 문자열이고 사용자가 아무 값이나 넣을 수 있으니 읽을 때 검증하고 기본값을 정해야 한다. 글자마다 바뀌는 값은 `replace`로 히스토리를 덮고, 정렬이 바뀌면 페이지를 초기화한다.

### 클라이언트 라우트 가드만으로 페이지를 보호할 수 있나

없다. 가드는 렌더링 전에 로그인 화면으로 보내 깜빡임을 없애는 사용자 경험 장치다. 번들 코드는 누구나 고칠 수 있으니 실제 보호는 API 서버가 요청마다 권한을 검사해서 한다. 가드를 만들 때는 `redirect` 쿼리에 외부 주소가 들어와 오픈 리다이렉트가 되지 않게 내부 경로만 받는다.

### TanStack Router의 타입 안전 라우팅은 무엇을 막아 주나

라우트 트리를 타입으로 등록해서 `Link`의 경로 오타, 없는 파라미터 이름, 검색 파라미터의 잘못된 값을 컴파일 에러로 만든다. `validateSearch`를 통과한 검색 파라미터는 이미 숫자나 유니온 타입이라 컴포넌트마다 파싱할 필요가 없다. 라우트 이름을 바꾸면 영향받는 링크가 모두 드러나 리팩터링이 안전해진다.

### React Router, TanStack Router, Next.js 중 무엇을 고르나

검색 노출이 필요 없고 정적 호스팅이면 충분한 SPA라면 클라이언트 라우터를 쓴다. 검색 파라미터가 복잡하고 타입 안정성을 중시하면 TanStack Router, 기존 코드와 팀 경험이 React Router 쪽이면 데이터 모드로 올린다. 첫 HTML에 내용이 있어야 하면 React Router 프레임워크 모드, TanStack Start, Next.js App Router 같은 서버 렌더링 쪽으로 가고, 그만큼 서버 운영과 캐시 규칙의 부담을 진다.
