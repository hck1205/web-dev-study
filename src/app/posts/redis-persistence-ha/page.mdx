<EasyIntro>
  새벽에 서버를 껐다 켰더니 로그인 정보를 담아 둔 Redis가 텅 비어 있었고, 아침에 사용자들이 줄줄이 로그아웃됐다. Redis는 데이터를 메모리에 두기 때문에, 디스크에 따로 남기지 않으면 꺼지는 순간 다 사라진다.

커널 보안 패치 때문에 새벽에 서버를 재부팅했다. 아침에 고객센터로 "자꾸 로그아웃된다"는 문의가 몰린다. 로그인 세션을 Redis에 두고 있었는데, 재부팅 뒤 올라온 Redis가 텅 비어 있었다. 설정을 열어 보니 캐시 서버용 설정을 그대로 복사해 와서 `save ""`, `appendonly no`였다. 디스크에 아무것도 남기지 않는 설정이다.

캐시라면 비어도 DB에서 다시 채우면 된다. 세션은 다르다. 원본이 Redis뿐이라 날아가면 그걸로 끝이다. Redis는 메모리에 데이터를 두지만 디스크에 남기는 방법이 두 가지 있다. 특정 순간의 사진을 찍는 RDB와, 쓰기 명령을 한 줄씩 적는 AOF다. 이 글은 각각이 무엇을 지켜 주고 무엇은 못 지키는지를 직접 돌려 보며 정리하고, 남긴 파일로 정말 복원되는지 확인하는 법까지 본다. 서버 한 대가 죽어도 서비스를 이어 가는 복제와 Sentinel은 [복제와 Sentinel 글](/posts/redis-replication-sentinel)에서, 데이터를 여러 서버에 나누는 Cluster는 [Redis Cluster 글](/posts/redis-cluster)에서 이어 간다.

기준은 Ubuntu 24.04 LTS의 `redis-server` 패키지(7.0.15)다. 예제는 [Redis 기본 글](/posts/redis-basics)의 쇼핑몰이다. 세션 `session:42`, 장바구니 `cart:42`, 재고 카운터 `stock:1001`, 그리고 상품 캐시 20만 개를 합쳐 키 25만 개, 메모리 130MB 정도가 들어 있다. 메모리가 가득 찰 때의 이야기는 [메모리와 축출 정책 글](/posts/redis-memory-eviction)에 따로 있다.

## 재시작하면 무엇을 읽어 오나

Redis는 시작할 때 디스크에서 데이터를 읽어 메모리를 채운다. 규칙은 단순하다. `appendonly yes`면 AOF 파일만 읽는다. 아니면 RDB 파일(`dump.rdb`)을 읽는다. 둘 다 없으면 빈 상태로 시작한다. 세션이 날아간 서버는 마지막 경우였다.

Ubuntu 패키지의 기본 설정은 이렇다.

```bash
# 저장 규칙과 AOF 설정 확인
redis-cli CONFIG GET save
redis-cli CONFIG GET appendonly

# 데이터 파일이 쌓이는 디렉터리
redis-cli CONFIG GET dir
```

```text
1) "save"
2) "3600 1 300 100 60 10000"
1) "appendonly"
2) "no"
1) "dir"
2) "/var/lib/redis"
```

기본은 RDB만 켜져 있다. `/etc/redis/redis.conf`에서 `save` 줄이 주석으로 막혀 있어도 Redis 7.0의 내장 기본값 `3600 1 300 100 60 10000`이 적용된다. 그래서 설치 직후 그대로 쓰면 재부팅해도 대부분 남는다. 데이터를 잃는 건 누군가 `save ""`로 끈 경우, 또는 마지막 스냅샷 이후의 쓰기다.

모니터링에 걸어 둘 줄은 두 개다. `rdb_last_bgsave_status`가 `ok`가 아니면 저장이 실패하고 있는 것이고, `rdb_changes_since_last_save`가 계속 커지면 지금 죽을 경우 그만큼을 잃는다. `rdb_last_cow_size`는 다음 절에서 본다.

RDB의 장점은 파일이 작고 읽기가 빠르다는 것이다. 메모리 130MB인 데이터가 32MB짜리 `dump.rdb`가 됐고, 재시작할 때 키 25만 개를 0.6초에 읽었다. 백업으로 옮기기도 좋다. 단점은 사진과 사진 사이의 변경을 잃는다는 것이다.

## fork와 copy-on-write

`BGSAVE`는 `fork()`로 자식 프로세스를 만든다. 자식은 fork한 순간의 메모리를 그대로 보고 파일에 쓴다. 메모리를 통째로 복사하는 건 아니다. 리눅스는 부모와 자식이 같은 물리 페이지를 공유하게 해 두고, 어느 쪽이든 페이지를 고치려 할 때 그 페이지만 복사한다(copy-on-write). 아래 그림에서 다음을 누르면 저장 중에 쓰기가 들어올 때 일어나는 일이 차례로 보인다.

쓰기가 거의 없을 때 저장하면 로그에 `Fork CoW for RDB: current 1 MB`가 찍혔다. 같은 130MB 데이터를 쓰기가 계속 쏟아지는 중에 저장하니 76MB가 됐다. 저장하는 1초 남짓 동안 데이터의 절반 넘는 페이지가 고쳐진 것이다. 쓰기가 많은 서버일수록 저장 중에 메모리가 데이터 크기만큼까지 더 필요할 수 있다. `maxmemory`를 물리 메모리보다 넉넉히 작게 잡는 이유다.

fork가 실패하는 경우도 있다. 커널의 `vm.overcommit_memory`가 기본값 0이면, 메모리가 빠듯할 때 커널이 fork를 거절할 수 있다. 그러면 로그에 `Can't save in background: fork: Cannot allocate memory`가 남고, 기본 설정(`stop-writes-on-bgsave-error yes`)에서는 쓰기 명령이 전부 이렇게 막힌다.

```text
(error) MISCONF Redis is configured to save RDB snapshots, but it's currently unable to persist to disk. Commands that may modify the data set are disabled, because this instance is configured to report errors during writes if RDB snapshotting fails (stop-writes-on-bgsave-error option). Please check the Redis logs for details about the RDB error.
```

저장에 실패하는데 조용히 쓰기를 받으면 나중에 재시작했을 때 크게 잃을 수 있으니 일부러 막는 것이다. 디스크가 가득 찼을 때도 같은 에러가 난다. 해결은 원인(디스크, 권한, 메모리)을 고치는 것이고, Redis 로그가 먼저 알려 준다. `vm.overcommit_memory=1` 설정 방법은 [메모리 글](/posts/redis-memory-eviction)에 있다.

## AOF는 쓰기 명령을 한 줄씩 적는다

AOF(Append Only File)는 사진 대신 일기다. 데이터를 바꾸는 명령을 받을 때마다 그 명령을 파일 끝에 덧붙인다. 재시작할 때는 일기를 처음부터 다시 실행해 데이터를 만든다. 실행 중인 서버에서 켜 보자.

```bash
# 실행 중에 AOF를 켠다 (현재 데이터로 기준 파일을 먼저 만든다)
redis-cli CONFIG SET appendonly yes

# 기준 파일 생성이 끝났는지 (0이면 끝)
redis-cli INFO persistence | grep aof_rewrite_in_progress

# 설정 파일에도 남긴다
redis-cli CONFIG REWRITE

# 쓰기 두 번
redis-cli SET cart:42 '[1001,1003]'
redis-cli INCR stock:1001

# AOF 디렉터리 확인
sudo ls -l /var/lib/redis/appendonlydir
```

```text
OK
aof_rewrite_in_progress:0
OK
OK
(integer) 1
-rw-rw---- 1 redis redis 32036030 Oct 16 21:21 appendonly.aof.1.base.rdb
-rw-rw---- 1 redis redis       98 Oct 16 21:21 appendonly.aof.1.incr.aof
-rw-rw---- 1 redis redis       88 Oct 16 21:21 appendonly.aof.manifest
```

Redis 7.0부터 AOF는 파일 하나가 아니라 디렉터리다(multi-part AOF). `base`는 켜는 순간의 전체 데이터이고, 기본 설정(`aof-use-rdb-preamble yes`)에서는 RDB 형식이라 크기가 앞의 `dump.rdb`와 같다. `incr`가 그 뒤로 들어온 쓰기 명령의 일기다. `manifest`는 어느 파일을 어떤 순서로 읽을지 적은 목차다.

```bash
# 목차와, 일기 파일의 실제 내용
sudo cat /var/lib/redis/appendonlydir/appendonly.aof.manifest
sudo cat /var/lib/redis/appendonlydir/appendonly.aof.1.incr.aof
```

```text
file appendonly.aof.1.base.rdb seq 1 type b
file appendonly.aof.1.incr.aof seq 1 type i
*2
$6
SELECT
$1
0
*3
$3
SET
$7
cart:42
$11
[1001,1003]
*2
$4
INCR
$10
stock:1001
```

일기는 클라이언트가 보내는 것과 같은 RESP 형식이다. `*3`은 인자 3개, `$7`은 다음 값이 7바이트라는 뜻이다. 사람이 읽을 수 있어서, 실수로 `FLUSHALL`을 쳤을 때 AOF 재작성이 일어나기 전이라면 서버를 멈추고 파일 끝의 `FLUSHALL`을 지운 뒤 다시 띄워 살리는 방법도 있다.

<Callout kind="warning" title="redis.conf에서 appendonly만 yes로 바꾸고 재시작하지 않는다">
데이터가 `dump.rdb`에만 있는 서버에서 설정 파일의 `appendonly`를 `yes`로 고치고 재시작하면, Redis는 AOF만 읽으려 하고 AOF가 없으니 빈 AOF를 새로 만들어 빈 상태로 시작한다. 직접 해 보니 키 25만 개짜리 `dump.rdb`를 옆에 두고도 `DBSIZE`가 0이었다. 그대로 두면 다음 저장 때 빈 데이터가 `dump.rdb`까지 덮는다. 위처럼 실행 중에 `CONFIG SET appendonly yes`로 켜고, `aof_rewrite_in_progress:0`을 확인한 뒤 `CONFIG REWRITE`로 설정 파일에 남긴다. 이미 빈 상태로 떴다면 바로 멈추고 `dump.rdb`를 백업한 다음 `appendonly no`로 되돌려 다시 시작한다.
</Callout>

일기를 파일에 쓴다고 바로 디스크에 닿는 건 아니다. `write()`는 운영체제의 페이지 캐시에 넣을 뿐이고, 디스크에 확실히 내리는 건 `fsync()`다. 이 빈도를 `appendfsync`가 정한다.

- `always`: 명령마다 fsync한다. 잃는 쓰기가 거의 없지만 디스크 속도가 곧 쓰기 속도가 되어 크게 느려진다.
- `everysec`: 기본값. 1초마다 백그라운드 스레드가 fsync한다. 서버나 전원이 죽으면 최대 1초 남짓을 잃는다. 디스크가 느려 이전 fsync가 끝나지 않으면 Redis가 쓰기를 최대 2초까지 미루므로, 최악은 2초 정도다.
- `no`: fsync를 운영체제에 맡긴다. 리눅스는 보통 수십 초 단위로 내리니 그만큼 잃을 수 있다.

Redis 프로세스만 죽고 서버는 살아 있다면 페이지 캐시에 들어간 내용은 운영체제가 결국 디스크에 쓴다. fsync 정책이 문제가 되는 건 서버 자체가 꺼질 때다.

## AOF가 커지면 다시 쓴다

일기는 계속 길어진다. `INCR stock:1001`을 100만 번 하면 일기는 100만 줄인데, 데이터는 숫자 하나다. 그래서 Redis는 주기적으로 AOF를 다시 쓴다(rewrite). 일기를 줄이는 게 아니라, 지금 메모리 상태로 새 `base`를 만들고 그 뒤부터 새 `incr`를 시작한다.

```bash
# 자동 재작성 조건: 마지막 재작성 때보다 100% 커지고, 64MB 이상일 때
redis-cli CONFIG GET auto-aof-rewrite-*

# 손으로 재작성
redis-cli BGREWRITEAOF
```

```text
1) "auto-aof-rewrite-min-size"
2) "67108864"
3) "auto-aof-rewrite-percentage"
4) "100"
Background append only file rewriting started
```

재작성도 fork로 한다. 7.0 이전에는 자식이 새 파일을 쓰는 동안 부모가 그 사이 들어온 쓰기를 메모리 버퍼에 따로 모아 두었다가 마지막에 붙였는데, 이 버퍼가 메모리를 먹고 같은 데이터를 두 번 쓰게 했다. 7.0의 multi-part AOF는 재작성을 시작할 때 부모가 새 `incr` 파일을 열어 거기에 바로 쓰고, 자식이 새 `base`를 다 쓰면 `manifest`만 바꿔서 옛 파일들을 버린다.

서버가 AOF를 쓰는 도중에 꺼지면 마지막 명령이 반만 적힐 수 있다. 기본 설정(`aof-load-truncated yes`)은 시작할 때 끝의 잘린 부분을 버리고 로그를 남긴 채 뜬다. 파일 중간이 깨졌다면 `redis-check-aof --fix`로 고친다. 고치면 깨진 지점 이후가 잘려 나가니 원본을 먼저 복사해 둔다.

```bash
# AOF 검사 (manifest를 가리킨다). --fix는 원본을 복사해 둔 뒤에
sudo redis-check-aof /var/lib/redis/appendonlydir/appendonly.aof.manifest
```

AOF를 켠 서버를 재시작하면 로그에 읽는 과정이 그대로 남는다.

```text
* RDB is base AOF
* Done loading RDB, keys loaded: 250001, keys expired: 0.
* DB loaded from base file appendonly.aof.1.base.rdb: 0.637 seconds
* DB loaded from incr file appendonly.aof.1.incr.aof: 0.000 seconds
* DB loaded from append only file: 0.637 seconds
```

`base`(RDB 형식)를 빠르게 읽고, 그 뒤의 짧은 일기만 다시 실행한다. 일기가 길면 명령을 하나씩 실행하느라 재시작이 느려지는데, 재작성이 그 길이를 짧게 유지한다.

## RDB와 AOF를 함께 켜면

둘은 같이 켤 수 있고, 주 저장소에 가까운 용도라면 그게 흔한 선택이다. 시작할 때는 AOF만 읽고, RDB는 다른 서버로 옮기기 쉬운 백업 파일 역할을 한다. 아래 그림은 5분 간격 RDB와 `everysec` AOF를 같이 켠 서버가 10시 6분에 전원이 나갔을 때, 재시작 후 무엇이 남는지 따라간 것이다.

마지막 장면이 두 방식의 차이다. RDB만 켜면 마지막 스냅샷 이후 몇 분을 통째로 잃는다. AOF `everysec`는 1초 남짓만 잃는다. 대신 AOF는 쓰기마다 디스크 쓰기가 붙고, 파일이 크고, 재시작이 조금 느리다.

어떻게 고를지는 데이터를 잃었을 때의 비용으로 정한다.

순수 캐시라면 둘 다 꺼도 된다(`save ""`). 재시작하면 비지만, 대신 fork도 디스크 쓰기도 없다. 다만 재시작 직후 모든 요청이 DB로 몰린다. 그게 감당이 안 되면 RDB만 켜서 재시작 후 웬만큼 채워진 상태로 뜨게 한다.

세션, 장바구니처럼 잃으면 불편하지만 치명적이지 않은 데이터는 RDB와 AOF `everysec`를 함께 켠다. 세션이 날아간 서버가 이 경우였다.

결제나 잔액처럼 한 건도 잃으면 안 되는 데이터는 Redis를 원본으로 쓰지 않는 편이 낫다. `appendfsync always`로도 디스크 한 대를 믿는 것이고, 서버를 늘리는 복제는 비동기라서 장애 조치 때 잃을 수 있다. 그 이야기는 [복제와 Sentinel 글](/posts/redis-replication-sentinel)에 있다.

## 백업은 복원해 봐야 백업이다

RDB 파일은 백업하기 좋다. Redis는 새 스냅샷을 임시 파일에 다 쓴 뒤 이름을 바꾸므로, `dump.rdb`는 언제 복사해도 완성된 파일이다. 서버가 돌고 있는 중에 그냥 복사하면 된다. AOF를 켠 7.0 서버라면 `appendonlydir` 디렉터리를 통째로 복사한다.

```bash
# 스냅샷을 새로 찍고, 끝났는지 확인한 뒤
redis-cli BGSAVE
redis-cli INFO persistence | grep -E "rdb_bgsave_in_progress|rdb_last_bgsave_status"

# 날짜를 붙여 복사하고 다른 서버(또는 오브젝트 스토리지)로 보낸다
sudo cp /var/lib/redis/dump.rdb /backup/redis/dump-$(date +%Y%m%d-%H%M).rdb
```

같은 서버의 디스크에만 두면 서버와 함께 사라진다. 다른 서버나 오브젝트 스토리지로 보내고, 시간별·일별로 몇 세대를 남긴다.

그리고 실제로 복원해 본다. 파일이 있다는 것과 그 파일로 데이터가 살아난다는 것은 다르다. 먼저 파일을 검사한다.

```bash
# RDB 파일 검사
redis-check-rdb /backup/redis/dump-20261016-2120.rdb
```

`Checksum OK`와 키 개수를 본다. 그다음 다른 포트로 띄워서 데이터를 읽어 본다.

```bash
# 복원 연습용 디렉터리에 복사해 다른 포트로 띄운다 (AOF는 꺼서 RDB를 읽게 한다)
mkdir -p /tmp/restore && cp /backup/redis/dump-20261016-2120.rdb /tmp/restore/dump.rdb
redis-server --port 6390 --dir /tmp/restore --appendonly no --daemonize yes

# 키 개수와 중요한 키 확인
redis-cli -p 6390 DBSIZE
redis-cli -p 6390 GET cart:42

# 연습이 끝나면 저장하지 않고 내린다
redis-cli -p 6390 SHUTDOWN NOSAVE

```

TTL이 걸린 키는 백업 시점 이후 시간이 지났으면 복원하자마자 만료된다. 세션 백업을 하루 뒤에 복원하면 30분짜리 세션은 다 사라져 있다. 복원에 걸린 시간도 재 둔다. 데이터가 커지면 RDB를 읽는 데만 몇 분이 걸리고, 그 시간이 장애 시간이 된다.

## 무엇을 잃어도 되는지부터 정한다

Redis의 영속성은 "얼마나 잃어도 되는가"라는 질문에 대한 답이다. RDB는 몇 분 간격의 사진이라 작고 빠르지만 그 사이를 잃고, AOF `everysec`는 1초 남짓만 잃는 대신 디스크를 더 쓴다. 둘 다 fork에 기대니 메모리 여유와 overcommit 설정이 따라와야 하고, 백업은 다른 곳에 두고 실제로 복원해 봐야 의미가 있다. 세션처럼 원본이 Redis뿐인 데이터를 두기 전에, 그 데이터가 사라지면 어떻게 되는지를 먼저 정해야 설정이 따라 정해진다. "얼마나 멈춰도 되는가"라는 다른 질문은 [복제와 Sentinel 글](/posts/redis-replication-sentinel)에서 다룬다.

## 면접에서 나올 만한 질문

### RDB와 AOF는 어떻게 다른가요?

RDB는 특정 시점의 데이터 전체를 바이너리 파일로 찍는 스냅샷이고, AOF는 쓰기 명령을 받을 때마다 파일 끝에 덧붙이는 기록이다. RDB는 파일이 작고 재시작이 빠르지만 스냅샷 사이의 변경을 잃는다. AOF는 everysec 기준 1초 남짓만 잃지만 파일이 커서 주기적으로 재작성해야 한다. 같이 켜면 시작할 때는 AOF를 읽는다.

### BGSAVE 중에 메모리가 늘어나는 이유는 무엇인가요?

BGSAVE는 fork로 자식 프로세스를 만들고, 자식은 copy-on-write로 부모와 메모리 페이지를 공유한다. 저장하는 동안 부모가 쓰기를 처리해 페이지를 고치면 그 페이지가 복사되므로, 쓰기가 많을수록 최대 데이터 크기만큼 메모리가 더 든다. 그래서 maxmemory를 물리 메모리보다 넉넉히 작게 잡고, vm.overcommit_memory=1로 fork 실패를 막는다.

### appendfsync 옵션별로 잃을 수 있는 데이터는 얼마인가요?

always는 명령마다 fsync해서 거의 잃지 않지만 디스크 속도가 쓰기 속도를 정해 느리다. 기본값 everysec는 1초마다 fsync해서 서버가 꺼지면 1초 남짓, fsync가 밀리면 최대 2초 정도를 잃을 수 있다. no는 운영체제에 맡겨서 수십 초를 잃을 수 있다. Redis 프로세스만 죽고 OS가 살아 있으면 페이지 캐시의 내용은 디스크에 내려간다.

### Redis가 MISCONF 에러를 내며 쓰기를 거부합니다. 왜 그런가요?

RDB 저장(BGSAVE)이 실패하고 있는데 `stop-writes-on-bgsave-error yes`(기본값)라서 일부러 쓰기를 막은 것이다. 저장에 실패하면서 조용히 쓰기를 받으면 재시작할 때 크게 잃기 때문이다. 원인은 보통 fork 실패(`vm.overcommit_memory`가 0인데 메모리가 빠듯할 때), 디스크 가득 참, 디렉터리 권한이고, Redis 로그의 `Can't save in background` 줄이 먼저 알려 준다. 원인을 고치는 것이 해결이다.

### RDB만 쓰던 서버에서 AOF를 켜려면 어떻게 하나요?

실행 중에 `CONFIG SET appendonly yes`로 켜고, `INFO persistence`의 `aof_rewrite_in_progress:0`으로 기준 파일이 다 만들어진 걸 확인한 뒤 `CONFIG REWRITE`로 설정 파일에 남긴다. 설정 파일만 고치고 재시작하면 Redis는 AOF만 읽으려 하는데 AOF가 없으니 빈 상태로 뜨고, 다음 저장 때 빈 데이터가 `dump.rdb`까지 덮는다.

### Redis 백업은 어떻게 하고, 무엇을 확인하나요?

`BGSAVE` 후 `rdb_last_bgsave_status:ok`를 확인하고 `dump.rdb`(AOF를 켠 7.0이면 `appendonlydir` 전체)를 다른 서버나 오브젝트 스토리지로 복사해 몇 세대를 남긴다. Redis는 임시 파일에 다 쓴 뒤 이름을 바꾸므로 언제 복사해도 완성된 파일이다. 그다음 `redis-check-rdb`로 체크섬과 키 개수를 보고, 다른 포트로 띄워 실제로 데이터를 읽어 본다. TTL이 지난 키는 복원하자마자 사라지고, 복원에 걸리는 시간이 곧 장애 시간이라는 것도 재 둔다.
