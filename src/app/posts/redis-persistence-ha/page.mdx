커널 보안 패치 때문에 새벽에 서버를 재부팅했다. 아침에 고객센터로 "자꾸 로그아웃된다"는 문의가 몰린다. 로그인 세션을 Redis에 두고 있었는데, 재부팅 뒤 올라온 Redis가 텅 비어 있었다. 설정을 열어 보니 캐시 서버용 설정을 그대로 복사해 와서 `save ""`, `appendonly no`였다. 디스크에 아무것도 남기지 않는 설정이다.

캐시라면 비어도 DB에서 다시 채우면 된다. 세션은 다르다. 원본이 Redis뿐이라 날아가면 그걸로 끝이다. Redis는 메모리에 데이터를 두지만, 디스크에 남기는 방법이 두 가지(RDB, AOF) 있고, 서버 한 대가 죽어도 서비스를 이어 가는 방법이 세 단계(복제, Sentinel, Cluster) 있다. 이 글은 각각이 무엇을 지켜 주고 무엇은 못 지키는지를 직접 돌려 보며 정리한다.

기준은 Ubuntu 24.04 LTS의 `redis-server` 패키지(7.0.15)다. 예제는 [Redis 기본 글](/posts/redis-basics)의 쇼핑몰이다. 세션 `session:42`, 장바구니 `cart:42`, 재고 카운터 `stock:1001`, 그리고 상품 캐시 20만 개를 합쳐 키 25만 개, 메모리 130MB 정도가 들어 있다. 메모리가 가득 찰 때의 이야기는 [메모리와 축출 정책 글](/posts/redis-memory-eviction)에 따로 있다.

## 재시작하면 무엇을 읽어 오나

Redis는 시작할 때 디스크에서 데이터를 읽어 메모리를 채운다. 규칙은 단순하다. `appendonly yes`면 AOF 파일만 읽는다. 아니면 RDB 파일(`dump.rdb`)을 읽는다. 둘 다 없으면 빈 상태로 시작한다. 세션이 날아간 서버는 마지막 경우였다.

Ubuntu 패키지의 기본 설정은 이렇다.

```bash
# 저장 규칙과 AOF 설정 확인
redis-cli CONFIG GET save
redis-cli CONFIG GET appendonly

# 데이터 파일이 쌓이는 디렉터리
redis-cli CONFIG GET dir
```

```text
1) "save"
2) "3600 1 300 100 60 10000"
1) "appendonly"
2) "no"
1) "dir"
2) "/var/lib/redis"
```

기본은 RDB만 켜져 있다. `/etc/redis/redis.conf`에서 `save` 줄이 주석으로 막혀 있어도 Redis 7.0의 내장 기본값 `3600 1 300 100 60 10000`이 적용된다. 그래서 설치 직후 그대로 쓰면 재부팅해도 대부분 남는다. 데이터를 잃는 건 누군가 `save ""`로 끈 경우, 또는 마지막 스냅샷 이후의 쓰기다.

RDB의 장점은 파일이 작고 읽기가 빠르다는 것이다. 메모리 130MB인 데이터가 32MB짜리 `dump.rdb`가 됐고, 재시작할 때 키 25만 개를 0.6초에 읽었다. 백업으로 옮기기도 좋다. 단점은 사진과 사진 사이의 변경을 잃는다는 것이다.

## fork와 copy-on-write

`BGSAVE`는 `fork()`로 자식 프로세스를 만든다. 자식은 fork한 순간의 메모리를 그대로 보고 파일에 쓴다. 메모리를 통째로 복사하는 건 아니다. 리눅스는 부모와 자식이 같은 물리 페이지를 공유하게 해 두고, 어느 쪽이든 페이지를 고치려 할 때 그 페이지만 복사한다(copy-on-write). 아래 그림에서 다음을 누르면 저장 중에 쓰기가 들어올 때 일어나는 일이 차례로 보인다.

쓰기가 거의 없을 때 저장하면 로그에 `Fork CoW for RDB: current 1 MB`가 찍혔다. 같은 130MB 데이터를 쓰기가 계속 쏟아지는 중에 저장하니 76MB가 됐다. 저장하는 1초 남짓 동안 데이터의 절반 넘는 페이지가 고쳐진 것이다. 쓰기가 많은 서버일수록 저장 중에 메모리가 데이터 크기만큼까지 더 필요할 수 있다. `maxmemory`를 물리 메모리보다 넉넉히 작게 잡는 이유다.

fork가 실패하는 경우도 있다. 커널의 `vm.overcommit_memory`가 기본값 0이면, 메모리가 빠듯할 때 커널이 fork를 거절할 수 있다. 그러면 로그에 `Can't save in background: fork: Cannot allocate memory`가 남고, 기본 설정(`stop-writes-on-bgsave-error yes`)에서는 쓰기 명령이 전부 이렇게 막힌다.

```text
(error) MISCONF Redis is configured to save RDB snapshots, but it's currently unable to persist to disk. Commands that may modify the data set are disabled, because this instance is configured to report errors during writes if RDB snapshotting fails (stop-writes-on-bgsave-error option). Please check the Redis logs for details about the RDB error.
```

저장에 실패하는데 조용히 쓰기를 받으면 나중에 재시작했을 때 크게 잃을 수 있으니 일부러 막는 것이다. 디스크가 가득 찼을 때도 같은 에러가 난다. 해결은 원인(디스크, 권한, 메모리)을 고치는 것이고, Redis 로그가 먼저 알려 준다. `vm.overcommit_memory=1` 설정 방법은 [메모리 글](/posts/redis-memory-eviction)에 있다.

## AOF는 쓰기 명령을 한 줄씩 적는다

AOF(Append Only File)는 사진 대신 일기다. 데이터를 바꾸는 명령을 받을 때마다 그 명령을 파일 끝에 덧붙인다. 재시작할 때는 일기를 처음부터 다시 실행해 데이터를 만든다. 실행 중인 서버에서 켜 보자.

```bash
# 실행 중에 AOF를 켠다 (현재 데이터로 기준 파일을 먼저 만든다)
redis-cli CONFIG SET appendonly yes

# 기준 파일 생성이 끝났는지 (0이면 끝)
redis-cli INFO persistence | grep aof_rewrite_in_progress

# 설정 파일에도 남긴다
redis-cli CONFIG REWRITE

# 쓰기 두 번
redis-cli SET cart:42 '[1001,1003]'
redis-cli INCR stock:1001

# AOF 디렉터리 확인
sudo ls -l /var/lib/redis/appendonlydir
```

```text
OK
aof_rewrite_in_progress:0
OK
OK
(integer) 1
-rw-rw---- 1 redis redis 32036030 Oct 16 21:21 appendonly.aof.1.base.rdb
-rw-rw---- 1 redis redis       98 Oct 16 21:21 appendonly.aof.1.incr.aof
-rw-rw---- 1 redis redis       88 Oct 16 21:21 appendonly.aof.manifest
```

Redis 7.0부터 AOF는 파일 하나가 아니라 디렉터리다(multi-part AOF). `base`는 켜는 순간의 전체 데이터이고, 기본 설정(`aof-use-rdb-preamble yes`)에서는 RDB 형식이라 크기가 앞의 `dump.rdb`와 같다. `incr`가 그 뒤로 들어온 쓰기 명령의 일기다. `manifest`는 어느 파일을 어떤 순서로 읽을지 적은 목차다.

```bash
# 목차와, 일기 파일의 실제 내용
sudo cat /var/lib/redis/appendonlydir/appendonly.aof.manifest
sudo cat /var/lib/redis/appendonlydir/appendonly.aof.1.incr.aof
```

```text
file appendonly.aof.1.base.rdb seq 1 type b
file appendonly.aof.1.incr.aof seq 1 type i
*2
$6
SELECT
$1
0
*3
$3
SET
$7
cart:42
$11
[1001,1003]
*2
$4
INCR
$10
stock:1001
```

일기는 클라이언트가 보내는 것과 같은 RESP 형식이다. `*3`은 인자 3개, `$7`은 다음 값이 7바이트라는 뜻이다. 사람이 읽을 수 있어서, 실수로 `FLUSHALL`을 쳤을 때 AOF 재작성이 일어나기 전이라면 서버를 멈추고 파일 끝의 `FLUSHALL`을 지운 뒤 다시 띄워 살리는 방법도 있다.

<Callout kind="warning" title="redis.conf에서 appendonly만 yes로 바꾸고 재시작하지 않는다">
데이터가 `dump.rdb`에만 있는 서버에서 설정 파일의 `appendonly`를 `yes`로 고치고 재시작하면, Redis는 AOF만 읽으려 하고 AOF가 없으니 빈 AOF를 새로 만들어 빈 상태로 시작한다. 직접 해 보니 키 25만 개짜리 `dump.rdb`를 옆에 두고도 `DBSIZE`가 0이었다. 그대로 두면 다음 저장 때 빈 데이터가 `dump.rdb`까지 덮는다. 위처럼 실행 중에 `CONFIG SET appendonly yes`로 켜고, `aof_rewrite_in_progress:0`을 확인한 뒤 `CONFIG REWRITE`로 설정 파일에 남긴다. 이미 빈 상태로 떴다면 바로 멈추고 `dump.rdb`를 백업한 다음 `appendonly no`로 되돌려 다시 시작한다.
</Callout>

일기를 파일에 쓴다고 바로 디스크에 닿는 건 아니다. `write()`는 운영체제의 페이지 캐시에 넣을 뿐이고, 디스크에 확실히 내리는 건 `fsync()`다. 이 빈도를 `appendfsync`가 정한다.

- `always`: 명령마다 fsync한다. 잃는 쓰기가 거의 없지만 디스크 속도가 곧 쓰기 속도가 되어 크게 느려진다.
- `everysec`: 기본값. 1초마다 백그라운드 스레드가 fsync한다. 서버나 전원이 죽으면 최대 1초 남짓을 잃는다. 디스크가 느려 이전 fsync가 끝나지 않으면 Redis가 쓰기를 최대 2초까지 미루므로, 최악은 2초 정도다.
- `no`: fsync를 운영체제에 맡긴다. 리눅스는 보통 수십 초 단위로 내리니 그만큼 잃을 수 있다.

Redis 프로세스만 죽고 서버는 살아 있다면 페이지 캐시에 들어간 내용은 운영체제가 결국 디스크에 쓴다. fsync 정책이 문제가 되는 건 서버 자체가 꺼질 때다.

## AOF가 커지면 다시 쓴다

일기는 계속 길어진다. `INCR stock:1001`을 100만 번 하면 일기는 100만 줄인데, 데이터는 숫자 하나다. 그래서 Redis는 주기적으로 AOF를 다시 쓴다(rewrite). 일기를 줄이는 게 아니라, 지금 메모리 상태로 새 `base`를 만들고 그 뒤부터 새 `incr`를 시작한다.

```bash
# 자동 재작성 조건: 마지막 재작성 때보다 100% 커지고, 64MB 이상일 때
redis-cli CONFIG GET auto-aof-rewrite-*

# 손으로 재작성
redis-cli BGREWRITEAOF
```

```text
1) "auto-aof-rewrite-min-size"
2) "67108864"
3) "auto-aof-rewrite-percentage"
4) "100"
Background append only file rewriting started
```

재작성도 fork로 한다. 7.0 이전에는 자식이 새 파일을 쓰는 동안 부모가 그 사이 들어온 쓰기를 메모리 버퍼에 따로 모아 두었다가 마지막에 붙였는데, 이 버퍼가 메모리를 먹고 같은 데이터를 두 번 쓰게 했다. 7.0의 multi-part AOF는 재작성을 시작할 때 부모가 새 `incr` 파일을 열어 거기에 바로 쓰고, 자식이 새 `base`를 다 쓰면 `manifest`만 바꿔서 옛 파일들을 버린다.

서버가 AOF를 쓰는 도중에 꺼지면 마지막 명령이 반만 적힐 수 있다. 기본 설정(`aof-load-truncated yes`)은 시작할 때 끝의 잘린 부분을 버리고 로그를 남긴 채 뜬다. 파일 중간이 깨졌다면 `redis-check-aof --fix`로 고친다. 고치면 깨진 지점 이후가 잘려 나가니 원본을 먼저 복사해 둔다.

```bash
# AOF 검사 (manifest를 가리킨다). --fix는 원본을 복사해 둔 뒤에
sudo redis-check-aof /var/lib/redis/appendonlydir/appendonly.aof.manifest
```

AOF를 켠 서버를 재시작하면 로그에 읽는 과정이 그대로 남는다.

```text
* RDB is base AOF
* Done loading RDB, keys loaded: 250001, keys expired: 0.
* DB loaded from base file appendonly.aof.1.base.rdb: 0.637 seconds
* DB loaded from incr file appendonly.aof.1.incr.aof: 0.000 seconds
* DB loaded from append only file: 0.637 seconds
```

`base`(RDB 형식)를 빠르게 읽고, 그 뒤의 짧은 일기만 다시 실행한다. 일기가 길면 명령을 하나씩 실행하느라 재시작이 느려지는데, 재작성이 그 길이를 짧게 유지한다.

## RDB와 AOF를 함께 켜면

둘은 같이 켤 수 있고, 주 저장소에 가까운 용도라면 그게 흔한 선택이다. 시작할 때는 AOF만 읽고, RDB는 다른 서버로 옮기기 쉬운 백업 파일 역할을 한다. 아래 그림은 5분 간격 RDB와 `everysec` AOF를 같이 켠 서버가 10시 6분에 전원이 나갔을 때, 재시작 후 무엇이 남는지 따라간 것이다.

마지막 장면이 두 방식의 차이다. RDB만 켜면 마지막 스냅샷 이후 몇 분을 통째로 잃는다. AOF `everysec`는 1초 남짓만 잃는다. 대신 AOF는 쓰기마다 디스크 쓰기가 붙고, 파일이 크고, 재시작이 조금 느리다.

어떻게 고를지는 데이터를 잃었을 때의 비용으로 정한다.

순수 캐시라면 둘 다 꺼도 된다(`save ""`). 재시작하면 비지만, 대신 fork도 디스크 쓰기도 없다. 다만 재시작 직후 모든 요청이 DB로 몰린다. 그게 감당이 안 되면 RDB만 켜서 재시작 후 웬만큼 채워진 상태로 뜨게 한다.

세션, 장바구니처럼 잃으면 불편하지만 치명적이지 않은 데이터는 RDB와 AOF `everysec`를 함께 켠다. 세션이 날아간 서버가 이 경우였다.

결제나 잔액처럼 한 건도 잃으면 안 되는 데이터는 Redis를 원본으로 쓰지 않는 편이 낫다. `appendfsync always`로도 디스크 한 대를 믿는 것이고, 뒤에서 볼 복제는 비동기라서 장애 조치 때 잃을 수 있다.

## 복제는 비동기다

디스크에 남겨도 서버가 죽어 있는 동안은 서비스가 멈춘다. 그래서 같은 데이터를 다른 서버에 실시간으로 복사해 둔다. 프라이머리(마스터) 하나가 쓰기를 받고, 레플리카가 그 변경을 받아 똑같이 적용한다.

```bash
# 레플리카 서버에서: 이 서버를 10.0.0.11의 레플리카로 만든다
redis-cli REPLICAOF 10.0.0.11 6379

# 재시작 후에도 유지하려면 redis.conf에
#   replicaof 10.0.0.11 6379
# 프라이머리에 비밀번호가 있으면
#   masterauth <비밀번호>

# 복제 상태
redis-cli INFO replication
```

처음 연결하면 레플리카는 아무것도 없으니 전체를 받아야 한다(full sync). 그 뒤로는 바뀐 것만 받고, 잠깐 끊겼다 다시 붙으면 놓친 부분만 받는다(partial resync). 아래 그림이 그 순서다.

전체 동기화는 비싸다. 프라이머리가 fork하고, 데이터 전체가 네트워크를 지나고, 레플리카는 받는 동안 옛 데이터로 응답하거나 잠깐 멈춘다. 그래서 backlog를 넉넉히 잡아 짧은 끊김은 부분 동기화로 넘긴다. 어림셈은 "초당 복제되는 바이트 × 견딜 끊김 시간"이다. 쓰기가 초당 2MB이고 1분 끊김을 견디고 싶으면 120MB, `repl-backlog-size 128mb` 정도다. 기본 1MB는 쓰기가 많은 서버에서 몇 초도 못 버틴다. 4.0부터는 레플리카를 재시작해도 RDB에 복제 id와 위치를 남겨 두어 부분 동기화를 시도할 수 있다.

```text
# Replication
role:master

master_replid2:0000000000000000000000000000000000000000
master_repl_offset:14
repl_backlog_active:1
repl_backlog_size:1048576
repl_backlog_first_byte_offset:1
repl_backlog_histlen:14
```

프라이머리 쪽 `INFO replication`이다. `slave0`의 `offset`이 `master_repl_offset`과 같으면 다 따라온 것이고, 차이가 레플리카가 밀린 양이다. `lag`는 마지막 응답 후 지난 초다. `master_replid2`는 장애 조치 때 쓰인다. 레플리카가 승격되면 옛 복제 id를 여기에 남겨서, 다른 레플리카가 옛 id로 부분 동기화를 요청해도 받아 줄 수 있다.

## 레플리카에서 읽으면 생기는 일

복제는 비동기다. 프라이머리는 쓰기를 자기 메모리에 반영하자마자 클라이언트에 `OK`를 돌려주고, 레플리카로는 그다음에 보낸다. 여기서 두 가지 문제가 생긴다.

하나는 옛 값을 읽는 것이다. 읽기를 레플리카로 나누면 프라이머리 부하는 줄지만, 방금 담은 장바구니가 레플리카에는 아직 없을 수 있다. 보통 밀리초 단위지만 전체 동기화 중이거나 네트워크가 느리면 길어진다. 레플리카는 기본으로 읽기 전용이라(`replica-read-only yes`) 실수로 쓰면 거절한다.

```text
(error) READONLY You can't write against a read only replica.
```

다른 하나는 장애 조치 때 잃는 것이다. 프라이머리가 `OK`를 준 쓰기가 레플리카로 가기 전에 죽으면, 승격된 레플리카에는 그 쓰기가 없다. 이걸 줄이는 장치가 `WAIT`다.

```bash
# 장바구니를 쓰고, 레플리카 1대가 받았다고 확인할 때까지 최대 100ms 기다린다
redis-cli SET cart:43 '[1002]'
redis-cli WAIT 1 100
```

```text
OK
(integer) 1
```

`WAIT`는 확인해 준 레플리카 수를 돌려준다. 0이 오면 아직 아무 데도 안 갔다는 뜻이니 앱이 다시 시도하거나 에러로 처리한다. 다만 `WAIT`가 Redis를 강한 일관성 저장소로 바꾸지는 않는다. 레플리카가 받았어도 디스크에 남기기 전에 같이 죽을 수 있고, 장애 조치가 그 레플리카를 고른다는 보장도 없다. 손실 확률을 줄이는 장치로 보면 된다.

프라이머리 쪽에서 막는 설정도 있다. 레플리카가 몇 대 이상 붙어 있지 않으면 쓰기를 거절하게 한다.

```text
min-replicas-to-write 1
min-replicas-max-lag 10
```

10초 안에 응답한 레플리카가 1대 미만이면 쓰기는 `NOREPLICAS Not enough good replicas to write.` 에러를 받는다. 네트워크에서 고립된 프라이머리가 혼자 쓰기를 계속 받는 시간을 10초 안팎으로 묶는다.

<Callout kind="warning" title="영속성을 끈 프라이머리를 자동 재시작하지 않는다">
프라이머리는 `save ""`, `appendonly no`이고 레플리카에만 영속성을 켠 구성이 있다. 이때 프라이머리가 죽고 systemd가 바로 다시 띄우면, 빈 상태로 뜬 프라이머리에 레플리카가 다시 붙어 전체 동기화로 빈 데이터를 받아 간다. 레플리카의 데이터까지 지워진다. 프라이머리의 영속성을 끄려면 자동 재시작을 끄거나, Sentinel처럼 프라이머리가 죽으면 레플리카를 승격하는 장치를 함께 둔다.
</Callout>

## Sentinel이 장애를 판단하고 넘기는 과정

복제만으로는 프라이머리가 죽었을 때 사람이 레플리카에 `REPLICAOF NO ONE`을 치고, 앱의 접속 주소를 바꿔야 한다. 새벽 3시에 이걸 사람이 하면 수십 분이 걸린다. Sentinel은 이걸 자동으로 한다. 별도 프로세스(기본 포트 26379)로 떠서 프라이머리와 레플리카를 감시하고, 프라이머리가 죽었다고 판단하면 레플리카 하나를 승격하고 나머지를 새 프라이머리에 붙인다.

```bash
# Ubuntu에서는 별도 패키지다
sudo apt install -y redis-sentinel

# 설정 파일
sudo nano /etc/redis/sentinel.conf
```

```text
# 이름 shop, 주소, 쿼럼 2
sentinel monitor shop 10.0.0.11 6379 2
# 5초 동안 응답이 없으면 주관적으로 다운
sentinel down-after-milliseconds shop 5000
sentinel failover-timeout shop 60000
```

`down-after-milliseconds`의 기본값은 30초인데, 예제에서는 5초로 줄였다. 쿼럼(quorum) 2는 "Sentinel 2대가 다운이라고 동의해야 진짜 다운으로 본다"는 뜻이다. Sentinel은 서로 다른 장애 영역에 최소 3대를 둔다. 한 대는 판단이 틀릴 수 있고, 두 대는 하나가 죽으면 과반을 못 만든다.

앱이 Redis 주소를 직접 적어 두면 Sentinel이 아무리 빨리 승격해도 앱은 죽은 서버를 계속 찾는다. 클라이언트 라이브러리의 Sentinel 모드(ioredis의 `sentinels` 옵션, Lettuce·Jedis의 Sentinel 연결 등)를 써야 장애 조치가 완성된다. 설정이 맞는지는 Sentinel에게 물어볼 수 있다.

```bash
# 쿼럼과 과반을 채울 수 있는지
redis-cli -p 26379 SENTINEL ckquorum shop
```

```text
OK 3 usable Sentinels. Quorum and failover authorization can be reached
```

Sentinel의 약점은 네트워크가 갈라질 때다. 프라이머리와 일부 클라이언트가 나머지와 떨어지면, 반대편에서 새 프라이머리가 뽑히는 동안 옛 프라이머리도 그쪽 클라이언트의 쓰기를 받는다. 네트워크가 돌아오면 옛 프라이머리는 레플리카로 강등되면서 그 사이 받은 쓰기를 버린다. 앞의 `min-replicas-to-write`가 이 시간을 줄여 준다.

## Cluster는 키를 16384개 슬롯으로 나눈다

Sentinel 구성은 결국 프라이머리 한 대가 모든 쓰기와 모든 데이터를 감당한다. 데이터가 한 서버 메모리를 넘거나 쓰기가 한 대로 모자라면 Redis Cluster로 데이터를 나눈다.

Cluster는 키 공간을 16384개의 해시 슬롯으로 나누고, 슬롯 범위를 프라이머리들에 나눠 준다. 키가 어느 슬롯에 갈지는 `CRC16(키) mod 16384`로 정해진다. 프라이머리 3대로 만들면 슬롯은 이렇게 나뉜다.

```bash
# 클러스터 모드로 띄운 서버 3대를 묶는다 (실제로는 --cluster-replicas 1로 레플리카도 붙인다)
redis-cli --cluster create 10.0.0.11:6379 10.0.0.12:6379 10.0.0.13:6379
```

```text
>>> Performing hash slots allocation on 3 nodes...
Master[0] -> Slots 0 - 5460
Master[1] -> Slots 5461 - 10922
Master[2] -> Slots 10923 - 16383
```

`MSET`, `MGET`, `SUNION` 같은 여러 키 명령, `MULTI`/`EXEC` 트랜잭션, Lua 스크립트는 모든 키가 같은 슬롯일 때만 된다. 같은 슬롯에 모으는 장치가 해시 태그다. 키에 `{...}`가 있으면 중괄호 안만 해시한다.

```bash
redis-cli CLUSTER KEYSLOT user:42
redis-cli CLUSTER KEYSLOT '{user:42}:cart'
```

`{user:42}:cart`와 `{user:42}:profile`은 둘 다 `user:42`만 해시해서 같은 슬롯이다. 이렇게 지은 키끼리는 트랜잭션도 된다. 규칙에는 세부가 있다. 첫 `{` 뒤에 처음 나오는 `}`까지가 태그이고, 그 사이가 비어 있으면(`{}foo`) 키 전체를 해시한다. `foo{}{bar}`도 첫 태그가 비었으니 전체를 해시한다. 해시 태그를 남용하면 위험하다. 모든 키를 `{shop}`으로 묶으면 전부 한 슬롯, 한 노드로 가서 클러스터를 쓰는 의미가 없어진다. 회원 id처럼 값이 고르게 퍼지는 것으로 태그를 단다.

Cluster에는 Sentinel이 필요 없다. 프라이머리들이 서로를 감시하다가, 한 프라이머리가 `cluster-node-timeout`(기본 15초) 넘게 응답이 없고 프라이머리 과반이 동의하면 그 레플리카를 승격한다. 프라이머리는 최소 3대, 각자 레플리카를 하나씩 둔 6대 구성이 기본이다. 복제가 비동기라는 성질은 그대로라서 장애 조치 때 잃는 쓰기가 있을 수 있다는 것도 같다. 또 Cluster에서는 DB 번호가 0 하나뿐이라 `SELECT 1`을 쓸 수 없다.

## MOVED와 ASK

앱이 키의 슬롯이 어느 노드에 있는지 모르고 아무 노드에나 물으면 어떻게 될까. 노드가 프록시처럼 대신 전달해 주지는 않는다. 그 키는 저쪽 노드에 있다고 알려 줄 뿐이다.

```bash
# 노드 A(7001)에 cart:42를 물으면
redis-cli -p 7001 GET cart:42

# -c를 주면 redis-cli가 안내를 따라간다
redis-cli -c -p 7001 GET cart:42
```

```text
(error) MOVED 15749 127.0.0.1:7003
"[1001,1003]"
```

`MOVED 15749 127.0.0.1:7003`은 "슬롯 15749는 이제 7003 담당이니 앞으로 거기로 가라"는 뜻이다. 클러스터를 지원하는 클라이언트는 시작할 때 `CLUSTER SLOTS`(7.0부터는 `CLUSTER SHARDS`도)로 슬롯 지도를 받아 두고 처음부터 맞는 노드로 보낸다. `MOVED`를 받으면 지도를 새로 고친다.

## 단일 서버부터 관리형 서비스까지

구성은 작은 것부터 시작해, 넘어가야 할 신호가 보일 때 올린다.

단일 서버와 레플리카. 데이터가 한 서버 메모리에 넉넉히 들어가고, 장애 때 몇 분 멈춰도 되는 서비스다. 레플리카는 백업과 수동 장애 조치용이다. 운영 부담이 가장 적다.

Sentinel. 데이터는 한 대에 들어가지만 프라이머리가 죽었을 때 사람을 기다릴 수 없는 서비스다. 세션 저장소가 대표적이다. 프라이머리 1, 레플리카 1~2, Sentinel 3이 흔한 구성이고, 클라이언트가 Sentinel 모드를 지원해야 한다.

Cluster. 데이터가 한 서버의 메모리를 넘거나(예를 들어 수십 GB를 넘어가며 fork와 전체 동기화가 부담스러워질 때), 쓰기가 한 대의 CPU 하나로 모자랄 때다. 대신 여러 키 명령에 해시 태그가 필요하고, 클라이언트가 클러스터를 지원해야 하고, 운영할 노드 수가 늘어난다. 데이터는 작은데 읽기만 많다면 Cluster보다 레플리카를 늘려 읽기를 나누는 게 먼저다.

관리형 서비스. 이 모든 걸 직접 운영하지 않는 방법이다. AWS ElastiCache(Redis OSS·Valkey 엔진, Cluster 모드를 켜거나 끌 수 있다), Azure Cache for Redis, Google Cloud Memorystore가 있다. 장애 조치, 패치, 백업 스냅샷을 대신 해 주지만 복제가 비동기라는 성질은 그대로인 경우가 많으니 서비스 문서에서 장애 조치 때의 유실 가능성을 확인한다. AWS MemoryDB는 쓰기를 여러 가용 영역에 걸친 트랜잭션 로그에 남긴 뒤 응답한다고 설명하는, 주 저장소 용도를 겨냥한 서비스다. 그만큼 쓰기 지연이 더 크다. 어느 쪽이든 엔진 버전, 사용할 수 없는 명령, 가격 구조가 서비스마다 다르니 고를 때 그 시점의 문서를 확인한다.

## 백업은 복원해 봐야 백업이다

RDB 파일은 백업하기 좋다. Redis는 새 스냅샷을 임시 파일에 다 쓴 뒤 이름을 바꾸므로, `dump.rdb`는 언제 복사해도 완성된 파일이다. 서버가 돌고 있는 중에 그냥 복사하면 된다. AOF를 켠 7.0 서버라면 `appendonlydir` 디렉터리를 통째로 복사한다.

```bash
# 스냅샷을 새로 찍고, 끝났는지 확인한 뒤
redis-cli BGSAVE
redis-cli INFO persistence | grep -E "rdb_bgsave_in_progress|rdb_last_bgsave_status"

# 날짜를 붙여 복사하고 다른 서버(또는 오브젝트 스토리지)로 보낸다
sudo cp /var/lib/redis/dump.rdb /backup/redis/dump-$(date +%Y%m%d-%H%M).rdb
```

같은 서버의 디스크에만 두면 서버와 함께 사라진다. 다른 서버나 오브젝트 스토리지로 보내고, 시간별·일별로 몇 세대를 남긴다.

그리고 실제로 복원해 본다. 파일이 있다는 것과 그 파일로 데이터가 살아난다는 것은 다르다. 먼저 파일을 검사한다.

```bash
# RDB 파일 검사
redis-check-rdb /backup/redis/dump-20261016-2120.rdb
```


`Checksum OK`와 키 개수를 본다. 그다음 다른 포트로 띄워서 데이터를 읽어 본다.

```bash
# 복원 연습용 디렉터리에 복사해 다른 포트로 띄운다 (AOF는 꺼서 RDB를 읽게 한다)
mkdir -p /tmp/restore && cp /backup/redis/dump-20261016-2120.rdb /tmp/restore/dump.rdb
redis-server --port 6390 --dir /tmp/restore --appendonly no --daemonize yes

# 키 개수와 중요한 키 확인
redis-cli -p 6390 DBSIZE
redis-cli -p 6390 GET cart:42

# 연습이 끝나면 저장하지 않고 내린다
redis-cli -p 6390 SHUTDOWN NOSAVE
```

```text

```

TTL이 걸린 키는 백업 시점 이후 시간이 지났으면 복원하자마자 만료된다. 세션 백업을 하루 뒤에 복원하면 30분짜리 세션은 다 사라져 있다. 복원에 걸린 시간도 재 둔다. 데이터가 커지면 RDB를 읽는 데만 몇 분이 걸리고, 그 시간이 장애 시간이 된다.

## 무엇을 잃어도 되는지부터 정한다

Redis의 영속성과 고가용성은 "얼마나 잃어도 되는가"와 "얼마나 멈춰도 되는가"라는 두 질문에 대한 답이다. RDB는 몇 분 간격의 사진이라 작고 빠르지만 그 사이를 잃고, AOF `everysec`는 1초 남짓만 잃는 대신 디스크를 더 쓴다. 둘 다 fork에 기대니 메모리 여유와 overcommit 설정이 따라와야 한다. 복제는 비동기라 장애 조치 때 마지막 쓰기를 잃을 수 있고, Sentinel은 그 장애 조치를 자동으로 해 주며, Cluster는 슬롯으로 데이터를 나눠 한 대의 한계를 넘는다. 세션처럼 원본이 Redis뿐인 데이터를 두기 전에, 그 데이터가 사라지면 어떻게 되는지를 먼저 정해야 설정이 따라 정해진다.

## 면접에서 나올 만한 질문

### RDB와 AOF는 어떻게 다른가요?

RDB는 특정 시점의 데이터 전체를 바이너리 파일로 찍는 스냅샷이고, AOF는 쓰기 명령을 받을 때마다 파일 끝에 덧붙이는 기록이다. RDB는 파일이 작고 재시작이 빠르지만 스냅샷 사이의 변경을 잃는다. AOF는 everysec 기준 1초 남짓만 잃지만 파일이 커서 주기적으로 재작성해야 한다. 같이 켜면 시작할 때는 AOF를 읽는다.

### BGSAVE 중에 메모리가 늘어나는 이유는 무엇인가요?

BGSAVE는 fork로 자식 프로세스를 만들고, 자식은 copy-on-write로 부모와 메모리 페이지를 공유한다. 저장하는 동안 부모가 쓰기를 처리해 페이지를 고치면 그 페이지가 복사되므로, 쓰기가 많을수록 최대 데이터 크기만큼 메모리가 더 든다. 그래서 maxmemory를 물리 메모리보다 넉넉히 작게 잡고, vm.overcommit_memory=1로 fork 실패를 막는다.

### appendfsync 옵션별로 잃을 수 있는 데이터는 얼마인가요?

always는 명령마다 fsync해서 거의 잃지 않지만 디스크 속도가 쓰기 속도를 정해 느리다. 기본값 everysec는 1초마다 fsync해서 서버가 꺼지면 1초 남짓, fsync가 밀리면 최대 2초 정도를 잃을 수 있다. no는 운영체제에 맡겨서 수십 초를 잃을 수 있다. Redis 프로세스만 죽고 OS가 살아 있으면 페이지 캐시의 내용은 디스크에 내려간다.

### Redis 복제에서 데이터가 유실될 수 있는 경우는?

복제가 비동기라서다. 프라이머리는 쓰기를 반영하자마자 OK를 주고 그 뒤에 레플리카로 보내므로, 그 사이에 프라이머리가 죽고 레플리카가 승격되면 그 쓰기는 사라진다. 네트워크가 갈라졌을 때 고립된 옛 프라이머리가 받은 쓰기도 강등될 때 버려진다. WAIT과 min-replicas-to-write로 확률과 시간을 줄일 수 있지만 강한 일관성이 되지는 않는다.

### 전체 동기화와 부분 동기화는 언제 일어나나요?

레플리카가 처음 붙거나 복제 id가 맞지 않거나, 놓친 위치가 backlog에서 이미 밀려났으면 전체 동기화를 한다. 프라이머리가 fork해서 RDB를 보내므로 비싸다. 짧게 끊겼다 다시 붙어서 놓친 부분이 backlog에 남아 있으면 그만큼만 보내는 부분 동기화가 된다. 기본 backlog 1MB는 작으니 초당 복제량 × 견딜 시간으로 키운다.

### Sentinel에서 quorum은 무엇을 정하나요?

프라이머리가 진짜 다운인지(ODOWN) 판단하는 데 필요한 Sentinel 수다. 실제로 장애 조치를 시작하려면 그와 별도로 Sentinel 과반의 표를 받아 리더가 되어야 한다. 그래서 Sentinel은 서로 다른 장애 영역에 3대 이상 두고, 앱은 Redis 주소 대신 Sentinel에게 현재 프라이머리를 물어 연결해야 한다.

### Redis Cluster에서 MGET이나 트랜잭션을 쓰려면 어떻게 하나요?

Cluster는 CRC16(키) mod 16384로 슬롯을 정하고 슬롯을 노드에 나누므로, 여러 키 명령과 MULTI, Lua 스크립트는 모든 키가 같은 슬롯일 때만 된다. 다르면 CROSSSLOT 에러가 난다. 키에 `{user:42}`처럼 해시 태그를 넣으면 중괄호 안만 해시해서 같은 슬롯에 모인다. 태그를 하나로 몰면 한 노드에 쏠리니 고르게 퍼지는 값으로 단다.

### MOVED와 ASK의 차이는 무엇인가요?

MOVED는 그 슬롯의 담당 노드가 바뀌었다는 영구적인 안내라서 클라이언트가 슬롯 지도를 고친다. ASK는 슬롯을 옮기는 중에 그 키가 이미 새 노드로 갔다는 일시적인 안내라서, 지도는 그대로 두고 이번 요청만 ASKING을 붙여 새 노드로 보낸다. 슬롯 이동이 끝나면 옛 노드는 MOVED를 돌려준다.
