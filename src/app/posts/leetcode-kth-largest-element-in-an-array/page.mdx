[Kth Largest Element in an Array](https://leetcode.com/problems/kth-largest-element-in-an-array/)는 LeetCode 215번이다. 배열에서 k번째로 큰 값을 구한다. 문제 끝에 "정렬하지 않고 풀 수 있나"라는 말이 붙어 있어서, 정렬로 한 줄에 끝내면 면접에서는 그다음 질문이 바로 나온다.

실무에서도 같은 모양을 자주 만난다. 응답 시간 10만 개에서 상위 1%에 해당하는 값(p99)을 구하거나, 점수 순위에서 커트라인 점수를 구하는 일이 모두 "k번째 값 하나"를 찾는 일이다. 이 글은 정렬, 최대 힙, 크기 k인 최소 힙, 퀵셀렉트 두 가지, 값 세기까지 여섯 풀이를 느린 것부터 본다. 힙의 기본 동작은 [힙 글](/posts/ds-heap)에, 무작위 기준값이 왜 평균을 지켜 주는지는 [무작위 알고리즘 글](/posts/randomized-algorithms)에 있으니 여기서는 이 문제에 필요한 만큼만 다룬다. 코드는 Node.js 22, Python 3.13, Java 21에서 돌렸다.

## k번째로 큰 값 하나만 필요하다

정수 배열 `nums`와 정수 `k`가 주어진다. 배열을 내림차순으로 줄 세웠을 때 k번째에 오는 값을 돌려준다. "서로 다른 값 중 k번째"가 아니다. `[4, 4, 4, 1]`에서 두 번째로 큰 값은 1이 아니라 4다. 같은 값도 각자 한 자리를 차지한다.

풀이를 고르는 데 영향을 주는 제약은 이렇다.

- k는 1 이상 n 이하이고, n은 최대 10^5다. 그래서 O(n²)은 100억 번이라 안 된다.
- 값은 -10^4 이상 10^4 이하다. 범위가 2만 1개로 좁다는 사실이 뒤에서 풀이 하나를 만든다.
- 값이 겹칠 수 있다. 실제로 LeetCode에는 같은 값이 잔뜩 들어 있는 입력이 있어서, 퀵셀렉트를 대충 짜면 시간 초과가 난다.

## 손으로 먼저 찾아 본다

이 글 내내 쓰는 예시다.

```text
nums = [5, 2, 8, 1, 9, 3, 7],  k = 3
```

큰 순서로 늘어놓으면 9, 8, 7, 5, 3, 2, 1이다. 세 번째는 7이다. 오름차순으로 보면 1, 2, 3, 5, 7, 8, 9에서 인덱스 4다. 이 "오름차순 인덱스 n - k"라는 숫자가 퀵셀렉트에서 계속 쓰인다. n = 7, k = 3이라 7 - 3 = 4다.

손으로 찾을 때 머릿속에서 일어나는 일을 들여다보면, 나는 "9, 8은 7보다 크고 나머지는 7보다 작다"를 확인하고 있었다. 1, 2, 3, 5 사이의 순서는 전혀 신경 쓰지 않았다. k번째 값을 찾는 데 필요한 건 그 값보다 큰 것이 정확히 k - 1개라는 사실뿐이다. 이 관찰이 정렬을 넘어서는 모든 풀이의 출발점이다.

## 다 줄 세우고 k번째를 읽는다

가장 먼저 떠오르는 답이다. 내림차순으로 정렬하고 인덱스 k - 1을 읽는다.

```js
function findKthLargest(nums, k) {
  const a = [...nums].sort((x, y) => y - x); // 내림차순. 입력을 바꾸지 않게 복사한다
  return a[k - 1];
}

console.log(findKthLargest([5, 2, 8, 1, 9, 3, 7], 3)); // 7
```

시간은 O(n log n)이다. JavaScript의 `sort`는 V8에서 TimSort라 이미 정렬된 입력이나 같은 값만 있는 입력에서는 거의 O(n)으로 끝난다. 공간은 복사본 O(n)이고, TimSort가 병합에 쓰는 임시 공간도 최대 O(n)이다.

이 풀이가 틀린 건 아니다. 면접에서 첫 답으로 내놓고 "k번째 하나를 위해 n개 전부의 순서를 정하고 있다"는 낭비를 스스로 짚으면 좋다. 위에서 본 것처럼 우리는 1, 2, 3, 5의 순서를 알 필요가 없었다.

비교 함수를 빼먹는 실수는 뒤의 "흔한 실수"에서 실제로 틀리는 입력과 함께 본다.

## 전부 힙에 넣고 k번 꺼낸다

정렬 대신 최대 힙(max-heap, 가장 큰 값이 항상 맨 위에 있는 자료구조)을 쓰면 "필요한 만큼만 순서를 정한다"를 할 수 있다. 배열 전체를 한 번에 힙으로 만드는 heapify는 O(n)이다. 그다음 맨 위를 k - 1번 버리면 맨 위에 k번째로 큰 값이 남는다.

```js
function findKthLargest(nums, k) {
  const a = [...nums], n = a.length;
  const down = (i, size) => {           // i번 칸을 자식 중 큰 쪽과 바꾸며 내린다
    for (;;) {
      const l = 2 * i + 1, r = l + 1;
      let m = i;
      if (l < size && a[l] > a[m]) m = l;
      if (r < size && a[r] > a[m]) m = r;
      if (m === i) return;
      [a[m], a[i]] = [a[i], a[m]];
      i = m;
    }
  };
  for (let i = (n >> 1) - 1; i >= 0; i--) down(i, n); // 아래 층부터 올라오며 heapify
  let size = n;
  for (let t = 0; t < k - 1; t++) {
    a[0] = a[--size];                   // 맨 위를 버리고 마지막 칸을 올린다
    down(0, size);
  }
  return a[0];
}
```

시간은 O(n + k log n)이다. heapify가 O(n)인 이유(아래 층 노드는 많지만 내려갈 거리가 짧다)는 [힙 글의 heapify 부분](/posts/ds-heap#한꺼번에-만들면-on이다)에 있다. k가 작으면 사실상 O(n)이고, k가 n/2쯤이면 O(n log n)이 된다. 공간은 복사본 O(n)이다. 입력을 바꿔도 되면 복사 없이 O(1)이다.

한계는 k가 클 때다. 10만 개에서 k = 5만이면 꺼내기를 5만 번 한다. 그리고 n개를 모두 메모리에 올려야 시작할 수 있다. 데이터가 한 줄씩 흘러 들어오면 이 방법은 못 쓴다.

## 크기 k인 바구니에 큰 것만 남긴다

방향을 뒤집는다. 최소 힙을 크기 k로 유지하면서 값을 하나씩 넣고, 크기가 k를 넘으면 맨 위(가장 작은 값)를 버린다. 그러면 힙에는 언제나 "지금까지 본 값 중 큰 것 k개"가 남고, 그중 맨 위가 k번째로 크다. 최대 힙이 아니라 최소 힙인 이유는 버려야 할 것이 "큰 것 k개 중 꼴찌"이기 때문이다. 꼴찌를 O(1)에 보려면 작은 것이 위에 있어야 한다. 같은 기법을 빈도에 적용한 것이 [Top K Frequent Elements](/posts/leetcode-top-k-frequent-elements)다.

JavaScript에는 힙이 없으니 작게 직접 만든다.

```js
class MinHeap {
  constructor() { this.a = []; }
  get size() { return this.a.length; }
  peek() { return this.a[0]; }
  push(x) {
    const a = this.a;
    a.push(x);
    let i = a.length - 1;
    while (i > 0) {                       // 부모보다 작으면 위로 올린다
      const p = (i - 1) >> 1;
      if (a[p] <= a[i]) break;
      [a[p], a[i]] = [a[i], a[p]];
      i = p;
    }
  }
  pop() {
    const a = this.a, top = a[0], last = a.pop();
    if (a.length) {
      a[0] = last;
      let i = 0;
      for (;;) {                          // 자식 중 작은 쪽과 바꾸며 내려간다
        const l = 2 * i + 1, r = l + 1;
        let m = i;
        if (l < a.length && a[l] < a[m]) m = l;
        if (r < a.length && a[r] < a[m]) m = r;
        if (m === i) break;
        [a[m], a[i]] = [a[i], a[m]];
        i = m;
      }
    }
    return top;
  }
}

function findKthLargest(nums, k) {
  const heap = new MinHeap();
  for (const x of nums) {
    heap.push(x);
    if (heap.size > k) heap.pop(); // 큰 것 k개에 못 드는 값을 버린다
  }
  return heap.peek();
}
```

예시를 넣고 값마다 힙 배열을 찍어 봤다. 힙 배열의 맨 앞이 맨 위다.

```text
8 [2,5,8]

```

## 기준값 하나로 반씩 버린다

손으로 풀 때의 관찰로 돌아간다. 답은 "자기보다 큰 값이 k - 1개인 값"이다. 아무 값 하나를 기준값(pivot)으로 정하고, 배열을 기준값보다 작은 것과 큰 것으로 나눠 보면 기준값이 오름차순에서 몇 번째 자리인지 바로 알 수 있다. 그 자리가 n - k면 기준값이 답이다. 아니면 답이 있는 쪽만 남기고 반대쪽은 버린다.

이게 퀵셀렉트(quickselect)다. 퀵 정렬과 나누는 방법이 같지만, 퀵 정렬은 양쪽을 다 다시 나누고 퀵셀렉트는 한쪽만 들어간다. 이 차이 덕분에 평균 시간이 n + n/2 + n/4 + … = 2n, 즉 O(n)이 된다.

가장 흔히 보는 Lomuto 방식부터 짠다. 기준값을 맨 끝으로 보내고, 기준값보다 작은 것을 앞쪽에 차례로 모은다.

```js
function findKthLargest(nums, k) {
  const a = [...nums];
  const target = a.length - k;       // 오름차순에서 답이 놓일 자리
  let lo = 0, hi = a.length - 1;
  while (true) {
    const r = lo + Math.floor(Math.random() * (hi - lo + 1)); // 무작위 기준값
    [a[r], a[hi]] = [a[hi], a[r]];
    const pivot = a[hi];
    let store = lo;                  // 여기 앞쪽은 모두 pivot보다 작다
    for (let i = lo; i < hi; i++) {
      if (a[i] < pivot) {
        [a[i], a[store]] = [a[store], a[i]];
        store++;
      }
    }
    [a[store], a[hi]] = [a[hi], a[store]]; // 기준값을 제자리에 놓는다
    if (store === target) return a[store];
    if (store < target) lo = store + 1;
    else hi = store - 1;
  }
}
```

기준값을 무작위로 고르는 이유는 매번 끝값을 고르면 정렬된 입력에서 한 번에 하나씩만 줄어 O(n²)이 되기 때문이다. 무작위면 어떤 입력을 줘도 "평균적으로" 반씩 줄어든다. 입력을 만든 사람이 내 기준값을 예측할 수 없다는 게 요점이다.

그런데 이 코드는 LeetCode에서 시간 초과가 난다. 같은 값만 10만 개 있는 배열을 넣어 보면 알 수 있다. 모든 값이 기준값과 같아서 `a[i] < pivot`이 한 번도 참이 아니고, store는 늘 lo에 머문다. 기준값이 맨 앞에 놓이고 범위는 하나만 줄어든다. 무작위로 골라도 모두 같은 값이라 소용이 없다. 실제로 `Array(100000).fill(1)`에 k = 1을 넣었더니 6.4초가 걸렸다. 같은 입력에 정렬은 2.4ms였다.

## 같은 값은 한가운데에 모은다

고치는 방법은 배열을 둘이 아니라 셋으로 나누는 것이다. 기준값보다 작은 것, 같은 것, 큰 것. 네덜란드 국기 문제(Dutch National Flag)라고 부르는 3-way 분할이다. 포인터 세 개를 쓴다.

- `lt` 앞쪽은 모두 기준값보다 작다.
- `lt`부터 `i` 앞까지는 기준값과 같다.
- `gt` 뒤쪽은 모두 기준값보다 크다.
- `i`부터 `gt`까지가 아직 안 본 칸이다.

`a[i]`가 작으면 `lt` 칸과 바꾸고 둘 다 한 칸 간다. 크면 `gt` 칸과 바꾸고 `gt`만 줄인다. 이때 `i`를 움직이지 않는 이유는 뒤에서 가져온 값을 아직 안 봤기 때문이다. 같으면 `i`만 간다.

나누고 나면 기준값과 같은 값들이 `lt`부터 `gt`까지 한 덩어리로 모인다. 목표 자리 n - k가 그 덩어리 안에 있으면 답은 기준값이다. 같은 값이 10만 개인 입력은 첫 분할에서 덩어리가 배열 전체가 되어 바로 끝난다.

```js
function findKthLargest(nums, k) {
  const a = [...nums];
  const target = a.length - k;
  let lo = 0, hi = a.length - 1;
  while (lo < hi) {
    const pivot = a[lo + Math.floor(Math.random() * (hi - lo + 1))];
    let lt = lo, i = lo, gt = hi;
    while (i <= gt) {
      if (a[i] < pivot) {                 // 작은 쪽으로 보낸다
        [a[lt], a[i]] = [a[i], a[lt]];
        lt++; i++;
      } else if (a[i] > pivot) {          // 큰 쪽으로 보낸다. 가져온 값은 아직 안 봤다
        [a[i], a[gt]] = [a[gt], a[i]];
        gt--;
      } else {
        i++;                              // 같으면 가운데에 둔다
      }
    }
    if (target < lt) hi = lt - 1;         // 답이 작은 쪽에 있다
    else if (target > gt) lo = gt + 1;    // 답이 큰 쪽에 있다
    else return pivot;                    // 같은 값 덩어리 안이다
  }
  return a[lo];
}
```

첫 회차에서 기준값 2는 운 나쁘게 두 번째로 작은 값이었다. 그래도 한 번에 두 칸을 버렸다. 운이 좋으면 반을, 나빠도 몇 칸은 버린다. 평균을 내면 매번 일정 비율이 줄어 전체가 O(n)이 된다.

시간은 평균 O(n), 최악 O(n²)이다. 최악은 기준값이 매번 범위의 최솟값이나 최댓값으로 뽑히는 경우인데, 무작위라 그럴 확률이 매우 낮다. 공간은 복사본 O(n)이고, 입력을 바꿔도 되면 O(1)이다. 재귀 대신 반복문으로 써서 콜 스택도 쓰지 않는다.

최악을 보장하고 싶으면 기준값을 "다섯 개씩 묶은 중앙값들의 중앙값"으로 고르는 median of medians를 쓴다. 기준값이 항상 범위의 30%와 70% 사이에 떨어지는 게 증명돼 최악도 O(n)이지만, 상수가 커서 무작위 퀵셀렉트보다 실제로는 느리다. GCC의 C++ 표준 라이브러리에 있는 `std::nth_element`는 퀵셀렉트로 돌다가 재귀가 너무 깊어지면 다른 방법으로 바꾸는 introselect를 쓴다. 면접에서는 "이론상 최악 O(n)도 가능하고, 실무 라이브러리는 섞어서 쓴다"까지만 말할 수 있으면 충분하다.

퀵셀렉트의 단점은 입력 배열을 뒤섞는다는 것이다. 복사하지 않으면 호출한 쪽의 배열 순서가 바뀐다. 그리고 데이터가 한꺼번에 메모리에 있어야 한다.

## 값의 범위가 좁으면 세기만 한다

제약을 다시 보면 값은 -10^4 이상 10^4 이하다. 가능한 값이 20001가지뿐이다. 그러면 비교할 필요 없이 값마다 몇 번 나왔는지 센 뒤, 큰 값부터 개수를 빼 가며 k가 0 이하가 되는 순간의 값을 돌려주면 된다. 계수 정렬(counting sort)에서 정렬된 배열을 만들기 직전에 멈추는 셈이다.

```js
function findKthLargest(nums, k) {
  let min = Infinity, max = -Infinity;
  for (const x of nums) {
    if (x < min) min = x;
    if (x > max) max = x;
  }
  const cnt = new Int32Array(max - min + 1); // cnt[v - min] = v가 나온 횟수
  for (const x of nums) cnt[x - min]++;
  for (let v = cnt.length - 1; v >= 0; v--) { // 큰 값부터
    k -= cnt[v];
    if (k <= 0) return v + min;              // 여기서 k개를 다 셌다
  }
}
```

`[4, 4, 4, 1, 4]`, k = 2면 4가 네 번이라 첫 칸에서 k가 2 - 4 = -2가 되고 4를 돌려준다. 같은 값이 여러 자리를 차지한다는 규칙이 개수 빼기로 자연스럽게 들어간다. 음수는 `x - min`으로 옮겨서 칸 번호를 0부터 시작하게 했다.

시간은 O(n + R)이고 R은 값의 범위(max - min + 1)다. 공간은 O(R)이다. 이 문제에서는 R이 2만 정도라 사실상 O(n)이고, 재 보면 가장 빠르다. 하지만 값이 64비트 정수나 실수면 칸을 만들 수 없다. 이 풀이는 제약을 읽고 골라야 나오는 답이고, 범위가 없으면 퀵셀렉트로 돌아간다.

## Python과 Java로 옮기기

면접에서 가장 많이 쓰는 두 가지를 옮긴다. 범위가 정해지지 않은 일반 답인 3-way 퀵셀렉트와, 짧고 안전한 크기 k 힙이다.

```python
import heapq
import random
from typing import List

class Solution:
    def findKthLargest(self, nums: List[int], k: int) -> int:
        a = nums[:]                      # 입력을 건드리지 않게 복사
        target = len(a) - k              # 오름차순에서 답이 놓일 자리
        lo, hi = 0, len(a) - 1
        while lo < hi:
            pivot = a[random.randint(lo, hi)]
            lt, i, gt = lo, lo, hi
            while i <= gt:               # 작은 것 | 같은 것 | 큰 것 으로 나눈다
                if a[i] < pivot:
                    a[lt], a[i] = a[i], a[lt]
                    lt += 1
                    i += 1
                elif a[i] > pivot:
                    a[i], a[gt] = a[gt], a[i]
                    gt -= 1
                else:
                    i += 1
            if target < lt:
                hi = lt - 1
            elif target > gt:
                lo = gt + 1
            else:
                return pivot
        return a[lo]

    def findKthLargestHeap(self, nums: List[int], k: int) -> int:
        heap = nums[:k]
        heapq.heapify(heap)              # 처음 k개로 최소 힙을 만든다
        for x in nums[k:]:
            if x > heap[0]:
                heapq.heapreplace(heap, x)  # 맨 위를 꺼내고 x를 넣는 걸 한 번에
        return heap[0]

s = Solution()
for nums, k in [([5, 2, 8, 1, 9, 3, 7], 3), ([4, 4, 4, 1, 4], 2), ([-3, -1, -2], 1), ([7], 1)]:
    print(s.findKthLargest(nums, k), s.findKthLargestHeap(nums, k), heapq.nlargest(k, nums)[-1])
```

```text
4 4 4
-1 -1 -1
7 7 7
```

`random.randint(lo, hi)`는 양 끝을 모두 포함한다. JavaScript의 `Math.random`과 달리 `+ 1`을 붙이지 않는다. Python의 `heapq`는 최소 힙만 있어서 크기 k 힙과 잘 맞는다. 최대 힙이 필요하면 값에 `-`를 붙여 넣는 게 관용구다. 한 줄로 끝내려면 `heapq.nlargest(k, nums)[-1]`을 쓴다. 내부에서 크기 k 힙을 쓰니 O(n log k)다. Python은 반복문이 느려서 직접 짠 퀵셀렉트가 생각만큼 빠르지 않다. 무작위 값 10만 개에서 재 보니 퀵셀렉트가 21~35ms, C로 구현된 `sorted(nums)[-k]`가 18ms였다. k = 1이면 `heapq.nlargest`가 1ms로 가장 빨랐고, k = 5만이면 86ms로 가장 느렸다. 언어가 바뀌면 순위도 바뀐다.

```java
import java.util.*;
import java.util.concurrent.ThreadLocalRandom;

class Solution {
    public int findKthLargest(int[] nums, int k) {
        int[] a = nums.clone();
        int target = a.length - k;
        int lo = 0, hi = a.length - 1;
        while (lo < hi) {
            int pivot = a[ThreadLocalRandom.current().nextInt(lo, hi + 1)]; // hi + 1은 포함하지 않는다
            int lt = lo, i = lo, gt = hi;
            while (i <= gt) {
                if (a[i] < pivot) swap(a, lt++, i++);
                else if (a[i] > pivot) swap(a, i, gt--);
                else i++;
            }
            if (target < lt) hi = lt - 1;
            else if (target > gt) lo = gt + 1;
            else return pivot;
        }
        return a[lo];
    }

    public int findKthLargestHeap(int[] nums, int k) {
        PriorityQueue<Integer> heap = new PriorityQueue<>(); // 기본이 최소 힙
        for (int x : nums) {
            heap.offer(x);
            if (heap.size() > k) heap.poll();
        }
        return heap.peek();
    }

    private static void swap(int[] a, int i, int j) { int t = a[i]; a[i] = a[j]; a[j] = t; }
}
```

```text
7 7
4 4
-1 -1
7 7
```

`main`에서 Python과 같은 네 입력을 넣은 결과다.

Java의 `PriorityQueue`는 기본이 최소 힙이다. 최대 힙이 필요하면 `Collections.reverseOrder()`를 넘긴다. `(a, b) -> b - a`도 흔히 쓰는데, 이 문제는 값이 작아 괜찮지만 `int` 범위 끝의 값끼리 빼면 넘쳐서 부호가 뒤집힌다. `Integer.compare(b, a)`가 안전하다. `PriorityQueue<Integer>`는 값을 박싱해 담아서 `int[]`에서 직접 도는 퀵셀렉트보다 메모리를 많이 쓴다. `Arrays.sort(int[])`는 원시 타입이라 Dual-Pivot 퀵 정렬을 쓰고, 이 문제에서는 생각보다 빠르다.

## 틀리기 쉬운 자리

### 비교 함수 없이 정렬한다

```js
const a = [10, 9, 2, 1];
console.log(a.sort());                // [ 1, 10, 2, 9 ]
console.log(a[a.length - 2]);         // 2. 두 번째로 큰 값은 9인데 틀렸다
```

JavaScript의 `sort`는 비교 함수가 없으면 값을 문자열로 바꿔 사전 순으로 정렬한다. "10"이 "2"보다 앞이다. 한 자리 수만 있는 예시로 테스트하면 통과해 버려서 더 위험하다. 숫자 정렬에는 항상 `(x, y) => x - y`를 넘긴다.

### k - 1과 n - k를 헷갈린다

내림차순이면 인덱스 k - 1, 오름차순이면 n - k다. 퀵셀렉트를 오름차순으로 나누면서 목표를 k - 1로 두면 k번째로 작은 값이 나온다. 위 예시에서 k = 3이면 3이 나온다. 정렬 방향과 목표 인덱스를 한 쌍으로 기억한다.

### 큰 쪽으로 보낸 뒤 i를 움직인다

3-way 분할에서 `a[i] > pivot`일 때 `gt`와 바꾸고 `i++`까지 하면, 뒤에서 가져온 값을 보지 않고 지나친다. 그 값이 기준값보다 작았다면 큰 쪽 무리에 섞여 답이 틀린다. 작은 쪽으로 보낼 때는 `lt` 자리 값이 이미 본 "같은 값"이라 `i++`해도 되지만, 큰 쪽은 아니다.

### 서로 다른 값으로 착각한다

`new Set(nums)`로 중복을 지우고 k번째를 구하면 `[4, 4, 4, 1]`, k = 2에서 1이 나온다. 정답은 4다. 문제는 "정렬했을 때 k번째"를 묻는다. 서로 다른 값 기준으로 묻는 건 LeetCode 414번 Third Maximum Number 같은 다른 문제다.

### 원소가 하나뿐이다

n = 1, k = 1이면 3-way 퀵셀렉트의 `while (lo < hi)`가 한 번도 돌지 않는다. 그래서 반복문 뒤의 `return a[lo]`가 꼭 있어야 한다. 이 줄을 빼면 `undefined`가 나온다. 범위가 줄어들다 한 칸만 남는 경우도 같은 줄로 빠져나오니, 원소 하나짜리 테스트는 이 줄을 확인하는 테스트이기도 하다.

## 면접관이 조건을 바꾸면

### 값이 계속 들어오고 매번 k번째를 물으면

크기 k인 최소 힙을 계속 들고 있는다. 값이 오면 넣고, k를 넘으면 맨 위를 버리고, 맨 위를 답한다. 한 번에 O(log k)다. 퀵셀렉트는 값이 올 때마다 전체를 다시 나눠야 해서 맞지 않는다. 이 변형이 그대로 [Kth Largest Element in a Stream](/posts/leetcode-kth-largest-element-in-a-stream)이다.

### k번째가 아니라 가운데 값을 계속 물으면

k가 고정이 아니라 "전체 개수의 절반"으로 움직인다. 크기 k 힙 하나로는 안 되고, 작은 절반을 담는 최대 힙과 큰 절반을 담는 최소 힙 두 개를 쓴다. [Find Median from Data Stream](/posts/leetcode-find-median-from-data-stream)에서 자세히 본다.

### 배열 두 개가 이미 정렬돼 있으면

합쳐서 k번째를 구하는 문제가 된다. 합치지 않고 양쪽에서 k/2씩 비교해 버리면 O(log k)다. [Median of Two Sorted Arrays](/posts/leetcode-median-of-two-sorted-arrays)가 이 생각을 쓴다.

### 데이터가 메모리에 다 안 들어가면

크기 k 힙으로 한 번 훑는다. k마저 크면 값의 범위를 구간으로 나눠 구간마다 개수를 세는 방법이 있다. 첫 번째 훑기에서 구간별 개수로 답이 들어 있는 구간을 찾고, 두 번째 훑기에서는 그 구간의 값만 모아 퀵셀렉트한다. 여러 서버에 나뉜 데이터의 p99를 구할 때는 정확한 값 대신 t-digest 같은 근사 구조를 서버마다 만들어 합치는 게 실무의 보통 방법이다.

### k개를 모두 돌려 달라면

퀵셀렉트가 끝나면 목표 자리 오른쪽에 큰 값 k - 1개가 모여 있다. 순서는 안 맞지만 "상위 k개"는 그대로 잘라 쓰면 된다. 순서까지 필요하면 그 k개만 정렬해 O(n + k log k)다. 점 사이 거리로 같은 일을 하는 문제가 [K Closest Points to Origin](/posts/leetcode-k-closest-points-to-origin)이다.

## 면접에서 나올 만한 질문

### 정렬하지 않고 풀 수 있나요?

퀵셀렉트로 평균 O(n)에 풀 수 있다. 기준값으로 배열을 나누면 기준값이 오름차순에서 몇 번째인지 알 수 있고, 답이 있는 쪽만 남겨 다시 나눈다. 한쪽만 들어가니 n + n/2 + … 해서 평균 2n번 비교한다. 정렬은 모든 원소의 순서를 정하지만 이 문제는 k번째 하나만 정하면 된다.

### 퀵셀렉트의 최악 시간은 얼마이고 어떻게 피하나요?

O(n²)이다. 기준값이 매번 범위의 끝값이면 한 칸씩만 줄어든다. 기준값을 무작위로 골라 특정 입력이 최악을 만들지 못하게 하고, 같은 값이 많은 입력은 3-way 분할로 같은 값을 한 덩어리로 묶어 처리한다. 최악까지 O(n)을 보장해야 하면 median of medians를 쓰지만 상수가 커서 실무에서는 잘 쓰지 않는다.

### 같은 값이 많으면 왜 느려지나요?

두 갈래로 나누는 Lomuto 분할은 기준값과 같은 값을 한쪽으로 몰아서, 모두 같은 값이면 범위가 한 칸씩만 줄어든다. 실제로 1을 10만 개 채운 배열에 6초 넘게 걸렸다. 작은 것, 같은 것, 큰 것 세 갈래로 나누면 목표 자리가 같은 값 덩어리 안에 들어가는 순간 끝나서 한 번 만에 답이 나온다.

### 힙 풀이와 퀵셀렉트 중 무엇을 고르나요?

데이터가 한 번에 다 있고 k가 크면 퀵셀렉트가 빠르다. 데이터가 흘러 들어오거나, 메모리에 다 못 올리거나, 입력 배열을 건드리면 안 되면 크기 k 힙을 고른다. 힙은 O(n log k)라 k가 작으면 사실상 선형이고, 최악이 없다는 점도 장점이다.

### 최소 힙인데 왜 k번째로 큰 값이 나오나요?

힙에 큰 값 k개만 남기기 때문이다. 크기가 k를 넘을 때마다 가장 작은 값을 버리면, 남은 k개 중 가장 작은 값이 전체에서 k번째로 크다. 그 값이 최소 힙의 맨 위라 O(1)에 읽는다.

### 값의 범위를 알면 더 빠르게 할 수 있나요?

값이 좁은 범위의 정수면 값마다 개수를 세고 큰 값부터 개수를 빼서 O(n + R)에 끝난다. 이 문제는 R이 2만 정도라 재 보면 가장 빠르다. 범위가 없거나 값이 실수면 쓸 수 없어서, 제약을 보고 고르는 풀이다.
