배포한 컨테이너가 응답을 안 한다는 연락을 받았다. 서버에 들어가 `docker ps`를 치니 STATUS가 `Up Less than a second`다. 방금 떴으니 괜찮은 걸까. 몇 초 뒤 다시 치면 `Restarting (1) 3 seconds ago`로 바뀌어 있다. `docker logs`를 보니 같은 에러가 네 번 찍혀 있고, 다른 컨테이너는 로그가 아예 비어 있다.

Docker 명령은 자주 쓰는 것만 추리면 열 개쯤이다. `build`, `images`, `run`, `ps`, `logs`, `exec`, `stop`, `rm`, `push`, `pull`. 하나하나는 쉬운데, 각 명령이 실제로 무엇을 건드리는지 모르면 위 같은 상황에서 엉뚱한 곳을 본다. 이 글은 열 개를 따로 외우지 않고, 프로젝트 폴더에서 이미지로, 이미지에서 컨테이너로, 이미지에서 레지스트리로 갔다가 돌아오는 한 바퀴로 묶어서 본다. 명령마다 사람들이 자주 걸려 넘어지는 지점을 직접 재현했다.

이 주제의 다른 글과 나눈 몫은 이렇다. 컨테이너가 무엇이고 `docker run` 옵션이 무슨 뜻인지는 [컨테이너 기초](/posts/docker-container-basics)에, Dockerfile과 캐시는 [Dockerfile과 이미지 레이어](/posts/dockerfile-image-layers)에, 네트워크와 볼륨은 [Docker 네트워크와 볼륨](/posts/docker-network-volume)에 있다. 여기서는 같은 설명을 되풀이하지 않고 링크로 넘긴다.

기준은 Ubuntu 24.04 LTS의 Docker Engine 29다. 출력은 Docker Engine 29.8.2(containerd 이미지 저장소 사용)에서 직접 돌린 것이고, 예제 앱은 요청마다 `GET / 200` 같은 줄을 표준 출력에 찍는 Node 22 HTTP 서버다.

```js
// app.js
const http = require("node:http");
const host = process.env.HOST ?? "0.0.0.0";
const port = Number(process.env.PORT ?? 8080);
const server = http.createServer((req, res) => {
  console.log(`${req.method} ${req.url} 200`);
  res.end("ok\n");
});
server.listen(port, host, () => console.log(`listening on ${host}:${port}`));
if (process.env.GRACEFUL === "1") {
  process.on("SIGTERM", () => {
    console.log("SIGTERM received, closing");
    server.close(() => process.exit(0));
  });
}
```

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY app.js .
CMD ["node", "app.js"]
```

이렇게 놓고 보면 헷갈리던 것들이 정리된다. `rm`은 컨테이너를 지우고 이미지는 건드리지 않는다. 이미지를 지우는 건 `rmi`다. `stop`한 컨테이너는 사라진 게 아니라 Containers 칸에 멈춘 채 남아 있다. `push`는 이미지 저장소에서 바로 레지스트리로 가니, 프로젝트 폴더를 고친 뒤 `build` 없이 `push`하면 옛 이미지가 올라간다.

## build: 이름표는 옮겨 가고 내용은 다이제스트가 지킨다

`docker build`에서 가장 먼저 걸리는 건 컨텍스트다. 마지막 인자 `.`이 빌드 컨텍스트이고, CLI는 이 폴더를 BuildKit에 보낸다. BuildKit은 Dockerfile이 참조하는 파일만 가져가서, `COPY app.js .`처럼 파일을 콕 집으면 폴더에 큰 파일이 있어도 상관없다. 문제는 `COPY . .`다. 200MB짜리 로그 파일을 폴더에 두고 `COPY . .`로 빌드한 뒤, `.dockerignore`로 빼고 다시 빌드했다.

```bash
# 컨텍스트 전송 줄만 본다
docker build --progress=plain -f Dockerfile.all -t me/app:all . 2>&1 | grep 'transferring context'
```

```text
#5 transferring context: 200.05MB 3.2s done
#4 transferring context: 92B 0.2s done
```

첫 빌드는 16초 걸렸고 그 파일이 이미지 안에도 들어갔다. `.dockerignore` 쓰는 법은 [Dockerfile 글](/posts/dockerfile-image-layers)에 있다. 여기서는 transferring context 숫자를 보는 습관만 챙긴다. 보낸 컨텍스트는 빌드 캐시에도 남아서 나중에 `docker system df`의 Build Cache 줄을 불린다.

두 번째로 걸리는 건 이름이다. 빌드 로그 끝에 이런 줄이 있다.

```text
#8 exporting manifest list sha256:c86e0e304a90ac41c2eb04cd0fbb2b72a130f58d07968158e34b40a155829720 done
#8 naming to docker.io/me/app:1.0 done
```

`-t me/app:1.0`이라고만 줬는데 `docker.io/me/app:1.0`으로 이름이 붙었다. 레지스트리를 안 쓰면 Docker Hub로 채워진다. 그리고 그 위의 `sha256:c86e0e…`가 이 빌드 결과의 다이제스트다. 태그는 이 다이제스트를 가리키는 이름표일 뿐이다. 같은 태그로 다시 빌드하면 이름표만 새 결과로 옮겨 간다. 앱을 한 글자 고쳐 다시 빌드하니 `me/app:1.0`의 ID가 `c86e0e304a90`에서 `7352a668730b`로 바뀌었다.

containerd 이미지 저장소에서는 `docker images`의 IMAGE ID가 이 다이제스트의 앞 12자리다. 예전 저장소(`overlay2` 그래프 드라이버)에서는 IMAGE ID가 이미지 설정(config)의 해시라서, 레지스트리가 알려 주는 다이제스트와 값이 다르다. 업그레이드한 서버에서 "로컬 ID와 레지스트리 다이제스트가 왜 다르냐"는 질문이 나오는 이유다. 둘을 비교하려면 `docker image inspect --format '{{json .RepoDigests}}'`를 본다.

## images: 같은 태그로 다시 빌드하면 옛 이미지는 어디로 가나

이름표가 옮겨 가면 원래 이미지는 이름 없이 남는다. 이걸 dangling 이미지라고 부른다. containerd 이미지 저장소를 끈 데몬(그래프 드라이버 방식)에서 같은 태그로 두 번 빌드하고 `docker images -a`를 쳤다.

```text
IMAGE         ID             DISK USAGE   CONTENT SIZE   EXTRA
alpine:3.20   bf8527eb54c3        7.8MB             0B
me/app:1.0    cb0fbc4c710a        7.8MB             0B
<untagged>    99fd10b26ba2        7.8MB             0B
```

`-a` 없이 친 기본 목록에는 세 번째 줄이 없었다. Docker 29의 기본 `docker images`는 이름 없는 이미지를 숨긴다. 예전 버전처럼 `<none>:<none>`이 줄줄이 보이지 않으니 디스크가 왜 찼는지 모르고 넘어가기 쉽다. `-a`나 `-f dangling=true`로 봐야 나온다. 같은 실험을 containerd 이미지 저장소 쪽에서 하면 목록에 untagged 이미지가 남지 않았고, 대신 옛 레이어가 빌드 캐시 쪽에 남아 있었다. 어느 쪽이든 디스크 사용량은 한곳에서 본다.

```bash
# 종류별 사용량과 지울 수 있는 양
docker system df
```

```text
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          13        2         1.204GB   280.9MB (23%)
Containers      2         2         24.58kB   0B (0%)
Local Volumes   1         1         60.72MB   0B (0%)
Build Cache     62        0         1.232GB   461.3MB
```

이 서버에서는 이미지보다 빌드 캐시가 더 컸다. 앞에서 200MB 컨텍스트를 두 번 보낸 흔적이 여기 들어 있다. 빌드를 자주 하는 CI 러너나 개발 서버에서 디스크가 차면 Images 줄보다 Build Cache 줄을 먼저 본다. `docker builder prune --filter until=168h`처럼 오래된 캐시부터 지운다. prune 명령의 범위와 위험은 [컨테이너 기초의 자원과 디스크 절](/posts/docker-container-basics#자원과-디스크-들여다보기)에 정리해 두었다.

## run과 ps: 떠 있는 것과 떠 있었던 것

`docker run`의 옵션 뜻은 [컨테이너 기초](/posts/docker-container-basics#docker-run-옵션-뜯어보기)에서 봤다. 이 글에서 볼 것은 `run`이 끝난 뒤 남는 흔적이다. 웹 서버, 한 번 돌고 끝나는 마이그레이션, 환경 변수가 없어서 바로 죽는 앱 셋을 띄웠다.

```bash
# 웹 서버: 백그라운드, 포트 게시, 이름
docker run -d --name app -p 18250:8080 me/app:1.0

# 한 번 돌고 끝나는 작업
docker run --name once me/app:1.0 node -e 'console.log("migrate done")'

# 설정이 없어 바로 죽는 앱. 실패하면 3번까지 다시 띄운다
docker run -d --name crashy --restart on-failure:3 me/app:1.0 \
  node -e 'console.error("DATABASE_URL is not set"); process.exit(1)'

docker ps -a
```

```text
CONTAINER ID   IMAGE        COMMAND                  CREATED          STATUS                      PORTS                     NAMES
f6ed12f856d0   me/app:1.0   "docker-entrypoint.s…"   13 seconds ago   Exited (0) 12 seconds ago                             once
c6688f85dbda   me/app:1.0   "docker-entrypoint.s…"   13 seconds ago   Exited (1) 10 seconds ago                             crashy
26e75217d197   me/app:1.0   "docker-entrypoint.s…"   30 seconds ago   Up 29 seconds               0.0.0.0:18250->8080/tcp   app
```

`-a` 없이 `docker ps`만 치면 `app` 한 줄만 나와서 `crashy`는 없는 것처럼 보인다. 죽은 컨테이너는 지워지지 않고 Exited 상태로 남아 있고 `-a`를 붙여야 보인다. 이걸 모르고 "컨테이너가 사라졌다"고 다시 `run`하면 `Conflict. The container name "/crashy" is already in use`를 만난다. 한 번 쓰고 버릴 컨테이너는 `--rm`으로 띄워 끝날 때 지워지게 한다. 몇 번 다시 떴는지는 STATUS에 안 나온다. `inspect`로 본다.

```bash
# 재시작 횟수, 상태, 마지막 종료 코드
docker inspect -f '{{.RestartCount}} {{.State.Status}} {{.State.ExitCode}}' crashy
```

```text
3 exited 1
```

정책을 `--restart always`로 바꾸면 더 헷갈린다. 2초 간격으로 `docker ps`를 찍어 봤다.

```text
Up Less than a second
Restarting (1) 3 seconds ago
Restarting (1) 6 seconds ago
Restarting (1) 1 second ago
```

첫 줄만 봤다면 방금 떴으니 괜찮다고 생각했을 것이다. 컨테이너가 `Up`인 순간을 잡은 것뿐이고, 25초 사이에 8번 다시 떴다. `Restarting (1)`의 1은 마지막 종료 코드다. 재시작 간격은 100ms부터 두 배씩 늘어나서 시간이 갈수록 `Restarting` 상태인 시간이 길어진다. 컨테이너 하나가 지나온 상태를 차례로 놓으면 이렇다. 상태마다 무엇이 남아 있는지 오른쪽을 본다.

## logs: stdout으로 낸 것만 남는다

`docker logs`는 컨테이너 안에 들어가 파일을 읽는 명령이 아니다. 컨테이너 PID 1의 stdout과 stderr를 데몬이 받아 호스트 파일에 적어 둔 것을 읽는다. 기본 로그 드라이버 json-file이면 그 파일은 여기 있다.

```bash
# 로그 파일 경로를 찾아 앞부분을 그대로 본다
sudo head -c 300 "$(docker inspect -f '{{.LogPath}}' app)"
```

따라가며 볼 때는 `docker logs -f --tail 100 app`처럼 `--tail`을 같이 쓴다. `--tail` 없이 `-f`만 주면 처음부터 다 쏟아내서, 몇 달 돈 컨테이너에서는 터미널이 한참 멈춘다. `-f`에서 Ctrl+C로 빠져도 컨테이너는 계속 돈다.

앱이 로그를 파일에 쓰면 `docker logs`에는 아무것도 없다. stdout이 아니니 데몬이 받을 게 없어서다.

```bash
# 로그를 컨테이너 안 /tmp/app.log에만 쓰는 앱
docker run -d --name filelog me/app:1.0 node -e \
  'const fs=require("fs"); setInterval(()=>fs.appendFileSync("/tmp/app.log","GET / 200\n"),200)'

docker logs filelog | wc -l
docker exec filelog tail -n 2 /tmp/app.log
```

```text
0
GET / 200
GET / 200
```

로그는 컨테이너 쓰기 레이어 안에 있다. 컨테이너를 지우면 같이 사라지고, 디스크는 컨테이너 크기로 조용히 불어난다. 컨테이너용 앱이 stdout으로 로그를 내는 이유가 여기 있다. 그래야 데몬이 크기를 관리하고, 수집기가 한 경로에서 모든 컨테이너 로그를 읽는다. 로그를 어떤 모양으로 낼지는 [구조화된 로그](/posts/structured-logging) 글에서 다룬다.

반대로 stdout으로 냈더니 이번엔 호스트 디스크가 찬다. json-file은 기본으로 크기 제한이 없다. 데몬 전체 기본값을 바꾸는 `daemon.json` 설정은 [컨테이너 기초](/posts/docker-container-basics#띄우고-들여다보고-멈추고-지우기)에 있고, 컨테이너 하나에만 걸 때는 `--log-opt`를 쓴다. 정말 잘리는지 1KB짜리 파일 2개로 작게 걸어 확인했다.

```bash
# 5ms마다 한 줄씩 찍는 컨테이너. 로그 파일은 1KB, 2개까지
docker run -d --name chatty --log-opt max-size=1k --log-opt max-file=2 me/app:1.0 \
  node -e 'let i=0; setInterval(()=>console.log("line "+(i++)+" "+"x".repeat(40)),5)'

sleep 4
sudo ls -l "$(dirname "$(docker inspect -f '{{.LogPath}}' chatty)")" | grep json
docker logs chatty | head -n 1
```

```text
-rw-r----- 1 root root  120 Oct 21 19:15 74f9e265a8d4746f5c4640665ae13e121a0573b307618bb8526a342118c355ba-json.log
-rw-r----- 1 root root 1079 Oct 21 19:15 74f9e265a8d4746f5c4640665ae13e121a0573b307618bb8526a342118c355ba-json.log.1
line 720 xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

파일이 `.log`와 `.log.1` 두 개로 돌고, `docker logs`가 보여 주는 첫 줄이 0번이 아니라 720번이다. 앞 줄은 지워졌다. 운영에서는 10MB씩 3개 정도로 건다. 장애 시점 로그가 회전되어 사라지기 전에 수집기가 가져가야 하니, 로그를 오래 남기는 일은 [중앙 로그 파이프라인](/posts/centralized-logging-pipeline)에 맡긴다. 처음부터 회전과 압축이 켜진 `local` 드라이버를 쓰는 방법도 있다. 다른 드라이버(syslog, fluentd 등)를 쓰면 `docker logs`가 안 되던 시절이 있었는데, Docker 20.10부터는 로컬에 사본을 함께 남겨서(dual logging) 대부분 그대로 읽힌다.

## exec와 attach는 다른 문으로 들어간다

컨테이너 안을 보고 싶을 때 손이 가는 명령이 둘이다. `exec`는 새 프로세스를 하나 더 띄우고, `attach`는 이미 도는 PID 1의 표준 입출력에 내 터미널을 붙인다. 이 차이는 빠져나올 때 드러난다.

```bash
# exec로 띄운 셸이 종료 코드 3으로 끝나도
docker exec app sh -c 'exit 3'; echo "exec exit=$?"
docker ps --filter name=app --format '{{.Names}} {{.Status}}'
```

```text
exec exit=3
app Up 11 minutes
```

exec로 띄운 셸이 끝나도 PID 1은 그대로다. attach는 다르다. attach한 터미널에서 Ctrl+C를 누르면 CLI가 그 SIGINT를 컨테이너 PID 1에 그대로 넘긴다(`--sig-proxy` 기본값이 true다). attach 중인 CLI 프로세스에 SIGINT를 보내서 Ctrl+C를 흉내 냈다.

```bash
# --init으로 띄운 컨테이너에 attach하고, attach 프로세스에 SIGINT를 보낸다
docker run -d --init --name att me/app:1.0
docker attach att &
kill -INT $!
docker ps -a --filter name=att --format '{{.Names}} {{.Status}}'
```

```text
att Exited (130) 2 seconds ago
```

로그를 보려고 attach했다가 Ctrl+C로 나오는 순간 서버가 꺼진다. 130은 128 + 2(SIGINT)다. 같은 실험을 `--init` 없이 하면 컨테이너는 `Up`으로 남았다. node가 PID 1이라 SIGINT를 무시했기 때문인데, 이건 다음 절의 stop 이야기와 같은 원리다. attach에서 컨테이너를 살려 두고 빠지려면 Ctrl+P, Ctrl+Q를 차례로 누른다. 로그를 볼 때는 attach 대신 `docker logs -f`를 쓰는 편이 안전하다.

### 셸이 없는 이미지

distroless 같은 작은 이미지에는 셸이 없다. 같은 앱을 `gcr.io/distroless/nodejs22-debian12` 위에 올리고 들어가 보려 하면 이렇게 된다.

```text
$ docker exec slim sh; echo "exit=$?"
OCI runtime exec failed: exec failed: unable to start container process: exec: "sh": executable file not found in $PATH
exit=127
```

exec는 그 이미지 안의 실행 파일만 돌릴 수 있다. 이미지를 디버그용으로 다시 빌드하지 않고 안을 보는 길은 둘이다. 하나는 호스트 도구를 컨테이너의 namespace에 들어가서 쓰는 `nsenter`다. 호스트 root 권한이 필요하다.

```bash
# 컨테이너 PID 1의 호스트 PID
PID=$(docker inspect -f '{{.State.Pid}}' slim)

# 그 프로세스의 네트워크 namespace에서 호스트의 ss를 실행한다
sudo nsenter -t "$PID" -n ss -ltnp
```

```text
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
LISTEN 0      511          0.0.0.0:8080      0.0.0.0:*    users:(("node",pid=7605,fd=18))
```

`-n`은 네트워크 namespace만 바꾸고 파일 시스템은 호스트 것을 쓴다는 뜻이다. 그래서 컨테이너에 없는 `ss`가 돈다. 다른 하나는 도구가 든 컨테이너를 옆에 띄워 namespace를 함께 쓰는 방법이다.

```bash
# slim의 PID namespace와 네트워크를 함께 쓰는 alpine 컨테이너
docker run --rm --pid container:slim --network container:slim alpine:3.20 \
  sh -c 'ps; ls /proc/1/root/app'
```

```text
PID   USER     TIME  COMMAND
    1 root      0:00 /nodejs/bin/node app.js
   13 root      0:00 sh -c ps; ls /proc/1/root/app
   19 root      0:00 ps
app.js
```

alpine 안에서 PID 1이 distroless의 node로 보이고, `/proc/1/root`로 그 파일 시스템까지 읽힌다. 네트워크도 같이 쓰니 이 안에서 `netstat -ltn`을 치면 node가 여는 포트가 보인다. 쿠버네티스의 `kubectl debug`가 하는 일도 이것과 같은 생각이다([Pod 트러블슈팅](/posts/k8s-pod-troubleshooting#셸이-없는-컨테이너는-kubectl-debug로-연다)). Docker Desktop에는 이 과정을 묶은 `docker debug` 명령이 있는데, Desktop 버전과 요금제에 따라 쓸 수 있는 범위가 달라 왔다. 이 글에서 쓴 Linux용 Docker CLI 29.8.2에는 그 명령이 없었다.

## stop: SIGTERM을 보내고 10초를 센다

`docker stop`은 PID 1에게 끝내 달라는 SIGTERM을 보내고, 기본 10초를 기다린 뒤에도 살아 있으면 SIGKILL로 끊는다. 리눅스 시그널 자체는 [프로세스와 시그널](/posts/linux-processes-signals)에서, 셸이 PID 1일 때 10초가 걸리는 현상은 [컨테이너 기초](/posts/docker-container-basics#재시작-정책과-pid-1)에서 봤다. 여기서는 셸이 아니라 node가 직접 PID 1인 경우를 본다. `CMD ["node", "app.js"]`처럼 exec 형식으로 잘 써도 문제가 남는다는 게 요점이다.


## rm과 prune: 지우면 무엇이 같이 사라지나

`docker rm`은 멈춘 컨테이너만 지운다. 돌고 있으면 `cannot remove container "app": container is running`으로 거절한다. `-f`를 붙이면 SIGKILL로 바로 끊고 지운다. stop의 10초 유예도 없으니 운영 컨테이너에는 쓰지 않는다.

지울 때 놓치기 쉬운 게 익명 볼륨이다. `-v /data`처럼 이름 없이 볼륨을 붙이거나, 이미지 Dockerfile에 `VOLUME /data`가 있으면(postgres, redis 공식 이미지가 그렇다) Docker가 해시 이름의 볼륨을 만든다. 이건 `rm`으로 지워지지 않는다.

```bash
# 익명 볼륨을 붙인 컨테이너 둘
docker run -d --name v1 -v /data me/app:1.0
docker run -d --name v2 -v /data me/app:1.0
docker volume ls

# v1은 그냥, v2는 -v를 붙여 지운다
docker rm -f v1
docker rm -f -v v2
docker volume ls
```


지우기 전에는 둘이었는데 하나가 남았다. `-v` 없이 지운 v1의 볼륨이 주인 없이 남은 것이다. 테스트용 postgres를 띄웠다 지웠다 반복한 서버에서 `docker volume ls`를 치면 이런 해시 이름이 수십 개 나온다. 남은 볼륨은 `docker volume prune`으로 정리한다.

이름 붙인 볼륨 `keepme`를 하나 만들어 두고 `docker volume prune -f`를 쳤더니 해시 이름 볼륨만 `Deleted Volumes`에 나왔고 `keepme`는 남았다. Docker 23부터 `volume prune`은 기본으로 익명 볼륨만 지운다. 이름 붙인 볼륨까지 지우려면 `-a`를 붙인다. 예전 블로그 글의 "prune은 안 쓰는 볼륨을 다 지운다"는 설명은 그 이전 버전 기준이다. 남길 데이터는 이름 붙인 볼륨에 두는 게 그래서 더 안전하다. 볼륨 종류와 백업은 [Docker 네트워크와 볼륨](/posts/docker-network-volume#볼륨을-tar로-백업하고-되살리기)에 있다.

## push와 pull: 레지스트리는 태그를 옮길 수 있다

이미지 이름이 어디까지 레지스트리이고 어디부터 저장소인지 헷갈리면 push가 엉뚱한 곳으로 간다. `docker push me/app:1.0`은 Docker Hub의 `me` 계정으로 가려 하고, 그 계정에 권한이 없으면 앞 그림의 `push access denied`가 난다. 이름 조각의 뜻은 [컨테이너 기초의 이미지 이름 절](/posts/docker-container-basics#이미지-이름은-레지스트리부터-다이제스트까지)에서 봤으니, 그 규칙을 직접 코드로 짜 보자. 첫 조각에 `.`이나 `:`이 있거나 `localhost`면 레지스트리이고, Docker Hub의 한 단어짜리 이름에는 `library/`가 붙고, 태그도 다이제스트도 없으면 `latest`다.

pull 쪽의 함정은 Docker Hub의 횟수 제한이다. 로그인하지 않은 pull은 요청한 IP 기준으로 센다. 남은 횟수는 응답 헤더로 확인할 수 있다. Docker가 안내하는 확인용 저장소(`ratelimitpreview/test`)에 HEAD 요청을 보내면 pull 횟수를 쓰지 않고 헤더만 받는다.

```bash
# 익명 토큰을 받아 HEAD 요청으로 제한 헤더만 본다
TOKEN=$(curl -s "https://auth.docker.io/token?service=registry.docker.io&scope=repository:ratelimitpreview/test:pull" | jq -r .token)
curl -s --head -H "Authorization: Bearer $TOKEN" \
  https://registry-1.docker.io/v2/ratelimitpreview/test/manifests/latest | grep -i '^ratelimit'
```

```text
ratelimit-limit: 100;w=3600
ratelimit-remaining: 43;w=3600
```

이 글을 쓰는 시점에 익명 요청은 3600초(1시간) 창에 100번이었고, 같은 출구 IP를 쓰는 다른 작업이 이미 57번을 쓴 상태였다. 이 숫자는 Docker가 여러 번 바꿔 왔으니 지금 값은 직접 헤더로 확인한다. NAT 뒤의 CI 러너 여러 대가 같은 IP로 나가면 금방 바닥나고 `429 Too Many Requests`가 난다. `docker login`으로 계정 한도를 쓰거나, 클라우드 레지스트리의 pull-through 캐시나 사내 미러를 둔다.

## 계속 재시작하거나 포트가 대답하지 않을 때

처음 상황으로 돌아가자. 증상은 대개 둘 중 하나다. 컨테이너가 계속 다시 뜨거나, 떠 있는데 포트가 대답하지 않는다. 앞에서 본 명령을 이 순서로 친다.

계속 재시작하는 쪽은 "왜 죽었나"를 종료 코드와 마지막 로그로 좁힌다. 메모리를 계속 늘리는 앱을 64MiB 한도와 `--restart on-failure:2`로 띄워 재현했다.

```bash
# 50ms마다 8MB씩 버퍼를 늘리는 앱. 스왑 없이 64MiB 한도
docker run -d --name hungry --restart on-failure:2 --memory 64m --memory-swap 64m me/app:1.0 \
  node -e 'const a=[]; setInterval(()=>a.push(Buffer.alloc(8e6,1)),50)'

# 1. 지금 상태와 지나온 횟수, 종료 코드, OOM 여부
docker ps -a --filter name=hungry --format '{{.Names}} {{.Status}}'
docker inspect -f 'restarts={{.RestartCount}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}}' hungry
# 2. 죽기 직전 로그 (여러 번 뜬 로그가 이어 붙어 있다)
docker logs --tail 50 hungry
# 3. 데몬이 본 사건 순서
docker events --since 5m --until 0s --filter container=hungry --format '{{.Action}} {{index .Actor.Attributes "exitCode"}}'
```

```text
hungry Exited (137) 12 seconds ago
restarts=2 exit=137 oom=true
```

```text
create
start
oom
die 137
```

이 뒤로 start, oom, die 137이 두 번 더 반복됐다.

2번의 `docker logs`는 비어 있었다. OOM으로 죽는 앱은 마지막 말을 남길 틈이 없다. 로그가 비었다고 앱이 아무 일도 안 했다고 판단하면 안 되고, `oom=true`와 이벤트의 `oom` 줄을 본다. 반대로 종료 코드가 1이면 앱이 스스로 에러를 내고 나간 것이니 로그에 이유가 있다. 앞의 `crashy`처럼 `DATABASE_URL is not set`이 여러 번 찍혀 있을 것이다. 137인데 `oom=false`면 누군가 stop이나 kill을 했거나 stop 타임아웃에 걸린 것이다.

포트가 대답하지 않는 쪽은 바깥에서 안으로 한 칸씩 들어간다. 앱이 `HOST=127.0.0.1`로 컨테이너 안의 루프백에만 묶인 경우를 재현했다. 개발 서버 기본값이 localhost인 프레임워크에서 흔히 생긴다. 아래 그림에서 다음을 누르면 요청이 어디서 끊기는지 나온다.

```text
LISTEN 0      511        127.0.0.1:8080      0.0.0.0:*
```

1번의 에러 모양에서 이미 절반이 보인다. reset은 "어딘가 받아 줬다가 끊었다"는 뜻이고, 같은 실험에서 `-p 8080:18254`처럼 앞뒤를 뒤집어 쓴 컨테이너에 18254로 치면 `curl: (7) Failed to connect to localhost port 18254 after 0 ms: Couldn't connect to server`가 났다. 호스트에서 그 포트를 듣는 게 아예 없다는 뜻이다. `-p`는 `호스트:컨테이너` 순서다. 4~6번에서 `127.0.0.1:8080`이 보이면 앱 설정 문제다. Express라면 `app.listen(8080, "0.0.0.0")`, Vite 개발 서버라면 `--host`, Flask라면 `--host=0.0.0.0`처럼 프레임워크마다 바꾸는 곳이 다르다. 컨테이너 안의 localhost가 왜 컨테이너 자신인지는 [Docker 네트워크와 볼륨](/posts/docker-network-volume#컨테이너-안의-localhost는-컨테이너-자신이다)에서 다뤘다. 여기까지 다 정상인데 다른 서버에서만 안 되면 방화벽과 경로 문제다. 그때는 [계층별로 장애 좁히기](/posts/network-troubleshooting-by-layer)의 순서로 넘어간다.

## 한 바퀴를 다시 그려 보면

열 개의 명령은 네 곳을 오간다. `build`는 폴더를 이미지로 만들고 이름표를 붙인다. `push`와 `pull`은 그 이미지를 레지스트리와 주고받는데, 이름표는 옮겨 갈 수 있고 내용을 지키는 건 다이제스트다. `run`은 이미지 위에 컨테이너를 띄우고, 컨테이너는 죽어도 `rm`하기 전까지 설정과 로그를 들고 남는다. `logs`는 stdout만 보고, `exec`는 이미지에 있는 것만 실행하고, `stop`은 PID 1이 SIGTERM을 받아 줘야 10초를 기다리지 않는다. 장애 때는 이 그림을 머릿속에 놓고 바깥에서 안으로 한 칸씩 들어가면 된다. 여러 컨테이너를 파일 하나로 묶어 띄우는 건 [Docker Compose](/posts/docker-compose)에서, 같은 일을 쿠버네티스에서 하는 법은 [Pod 트러블슈팅](/posts/k8s-pod-troubleshooting)에서 이어진다.

## 면접에서 나올 만한 질문

### docker stop과 docker kill은 어떻게 다른가요?

stop은 PID 1에 SIGTERM을 보내고 기본 10초를 기다린 뒤에도 살아 있으면 SIGKILL을 보내고, kill은 기본으로 바로 SIGKILL을 보낸다. 그래서 stop은 앱이 처리 중인 요청을 끝내고 연결을 닫을 기회를 준다. 종료 코드는 SIGTERM으로 죽으면 143, SIGKILL이면 137이고, 앱이 핸들러로 정리하고 나가면 0이다.

### docker stop이 항상 10초 걸리고 종료 코드가 137입니다. exec 형식 CMD로 node를 띄웠는데도요.

node가 PID 1이라서다. 커널은 PID 1에게 시그널의 기본 동작을 적용하지 않아서, SIGTERM 핸들러가 없는 node는 그 시그널을 그냥 무시하고 10초 뒤 SIGKILL을 맞는다. 앱에 SIGTERM 핸들러를 넣어 정리 후 스스로 종료하게 하는 게 근본 해결이다. `--init`으로 tini를 PID 1에 두면 시그널은 전달되지만, 핸들러가 없으면 143으로 바로 죽을 뿐 정리는 안 된다.

### 컨테이너가 계속 재시작합니다. 무엇부터 보나요?

종료 코드와 OOMKilled, 재시작 횟수를 `docker inspect`로 보고, `docker logs --tail`로 죽기 직전 로그를 본다. 종료 코드 1처럼 앱이 스스로 나간 경우는 로그에 이유가 있고, 137에 OOMKilled가 true면 메모리 한도라서 로그가 비어 있는 경우가 많다. `docker events`로 die와 oom 사건의 순서를 보면 확실해진다. `docker ps`의 Up 표시는 재시작 사이의 한순간일 수 있어서 믿지 않는다.

### docker logs에 아무것도 안 나옵니다. 왜 그럴까요?

docker logs는 PID 1의 stdout과 stderr만 보여 주기 때문이다. 앱이 로그를 파일에 쓰거나, 셸 스크립트가 PID 1이고 앱 출력을 다른 곳으로 돌리고 있으면 비어 있다. 로그를 stdout으로 내도록 바꾸는 게 원칙이고, nginx 공식 이미지처럼 로그 파일을 /dev/stdout에 링크하는 방법도 있다. OOM처럼 앱이 출력할 틈 없이 죽은 경우에도 비어 있으니 종료 상태를 함께 본다.

### exec와 attach는 무엇이 다른가요?

exec는 컨테이너의 namespace 안에서 새 프로세스를 하나 더 실행하고, attach는 이미 돌고 있는 PID 1의 표준 입출력에 터미널을 붙인다. exec로 띄운 셸은 끝나도 컨테이너에 영향이 없지만, attach 중 Ctrl+C는 SIGINT로 PID 1에 전달돼서 서버를 끌 수 있다. 붙은 채로 빠지려면 Ctrl+P, Ctrl+Q를 쓰고, 로그를 볼 목적이면 docker logs -f를 쓴다.

### 셸이 없는 distroless 이미지는 어떻게 디버깅하나요?

exec는 이미지 안의 실행 파일만 돌릴 수 있으니, 도구를 바깥에서 가져와 같은 namespace에 넣는다. 호스트에서 `nsenter -t PID -n`으로 네트워크 namespace에 들어가 호스트의 ss나 curl을 쓰거나, `--pid container:이름 --network container:이름`으로 도구가 든 컨테이너를 옆에 띄운다. 후자는 `/proc/1/root`로 대상 컨테이너의 파일도 읽을 수 있다. 쿠버네티스에서는 kubectl debug의 임시 컨테이너가 같은 역할을 한다.

### 운영 배포에 태그 대신 다이제스트를 쓰는 이유는 무엇인가요?

태그는 같은 이름으로 다시 push하면 다른 이미지를 가리키도록 옮겨 가는 이름표고, 다이제스트는 매니페스트 내용의 해시라 바뀌지 않는다. 그래서 태그로 배포하면 언제 pull했느냐에 따라 서버마다 다른 코드가 돌 수 있고, 롤백할 대상도 흐려진다. 다이제스트로 고정하면 재현이 보장되는 대신 보안 패치를 자동으로 받지 않으니, 갱신은 도구로 다이제스트를 올리는 변경을 받아서 한다.

### -p로 포트를 열었는데 접속하면 Connection reset by peer가 납니다.

호스트 쪽 포트 게시는 됐지만 컨테이너 안에서 그 포트를 0.0.0.0으로 듣는 프로세스가 없는 경우다. 흔한 원인은 앱이 127.0.0.1에 묶여 있어서 컨테이너 자기 루프백으로 온 연결만 받는 것이다. `docker exec`로 안에서 localhost를 쳐서 되는지, nsenter로 듣는 주소가 무엇인지 확인하고 앱을 0.0.0.0에 묶는다. 아예 연결 거부(Couldn't connect)가 나면 -p를 빠뜨렸거나 호스트와 컨테이너 포트 순서를 뒤집은 것이다.
