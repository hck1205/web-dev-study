관리자 화면에서 상품 가격을 89,000원에서 99,000원으로 바꿨다. 저장은 성공했고 DB에도 99,000원이 들어갔다. 그런데 상품 페이지는 계속 89,000원이다. 누군가는 새로고침하니 바뀌었다고 하고, 누군가는 아직이라고 한다.

Next.js App Router에는 이런 일이 생길 수 있는 곳이 네 군데 있다. 같은 요청 안에서 같은 조회를 한 번만 하게 하는 요청 메모이제이션, 요청을 넘어 fetch 결과를 저장하는 데이터 캐시, 렌더링한 HTML과 RSC payload를 저장하는 전체 라우트 캐시, 브라우저 메모리에 RSC payload를 두는 클라이언트 캐시(예전 문서의 라우터 캐시)다. 이 글은 Next.js 16.4.1 앱과 가짜 가격 API를 만들어 각 층이 언제 값을 들고 있다가 언제 놓는지를 재 본다. 빌드 때 fetch가 한 번 불려 값이 굳는 문제는 [정적·동적 렌더링](/posts/nextjs-static-dynamic-rendering)에, ISR의 시간 기반·요청 기반 재생성은 [SSG와 ISR](/posts/rendering-ssg-isr)에 실측이 있다. 여기서는 네 층을 한 그림에 놓고 "어디부터 의심하나"와 "바꾼 뒤 무엇을 부르나"에 답한다.

## 요청 하나 안에서만 쓰는 메모

상품 페이지를 이렇게 짜는 일은 흔하다. `generateMetadata`는 제목에 가격을 넣으려고, 레이아웃은 배너에 쓰려고, 페이지는 본문에 쓰려고 각자 같은 API를 부른다. 셋 다 `cache: "no-store"`를 줬다. 가짜 API 서버가 받은 요청을 찍게 해 두고 페이지를 두 번 요청했다.

```tsx
// app/memo/layout.js 와 page.js, generateMetadata 모두 같은 줄이 있다
const p = await (await fetch(`${API}/price?k=memo`, { cache: "no-store" })).json();
// page.js에만 주소가 다른 줄이 하나 더 있다
const p2 = await (await fetch(`${API}/price?k=memo&v=2`, { cache: "no-store" })).json();
```

```text
-- 첫 번째 요청
18:57:52 GET /price?k=memo
18:57:52 GET /price?k=memo&v=2
-- 두 번째 요청
18:57:52 GET /price?k=memo
18:57:52 GET /price?k=memo&v=2
```

같은 주소를 세 곳에서 불렀는데 요청 하나에 API 호출은 한 번이다. 주소가 다른 `v=2`는 따로 나갔다. 두 번째 요청에서는 둘 다 다시 나갔다. 이게 요청 메모이제이션이다. 같은 렌더링 안에서 URL과 옵션이 같은 GET `fetch`를 하나로 합치고, 요청이 끝나면 잊는다. `no-store`와 상관없이 동작한다. `no-store`는 요청 사이에 저장하지 말라는 뜻이지 요청 안에서 두 번 부르라는 뜻이 아니기 때문이다.

그래서 App Router에서는 데이터를 위에서 받아 props로 내려 주지 않고, 필요한 컴포넌트가 각자 부르는 방식이 권장된다. 부르는 곳이 늘어도 비용이 늘지 않는다.

`fetch`가 아닌 DB 조회에는 이게 적용되지 않는다. React의 `cache`로 감싸야 같은 효과가 난다. 레이아웃, 페이지, 메타데이터가 각자 `getUser()`를 부르게 하고, 감싼 버전과 안 감싼 버전을 비교했다.

```js
// app/lib/data.js
import { cache } from "react";
let dbCalls = 0;
export async function getUserRaw() {
  dbCalls++;
  console.log("db call", dbCalls);
  return { name: "kim" };
}
export const getUser = cache(getUserRaw);
```

```text
-- getUser(cache로 감쌈)를 세 곳에서, 요청 두 번
db call 1
db call 2
-- getUserRaw(그대로)를 세 곳에서, 빌드 때 한 번
db call 1
db call 2
db call 3
```

감싼 쪽은 요청마다 한 번, 안 감싼 쪽은 부른 만큼 실행됐다. 로그인한 사용자를 읽는 `getCurrentUser()`처럼 한 요청에서 여러 컴포넌트가 묻는 함수가 대표적인 쓰임새다.

몇 가지를 기억해 둔다. 메모이제이션은 서버 컴포넌트 트리 안에서만 일어난다. Route Handler는 React 트리 밖이라 같은 `fetch`를 두 번 부르면 두 번 나간다. POST 같은 GET 아닌 `fetch`도 합치지 않는다. `cache`는 인자를 `Object.is`로 비교하므로 매번 새 객체를 넘기면 매번 실행된다. id 같은 원시값을 넘긴다. 그리고 `cache`로 감싼 함수는 모듈 최상단에서 한 번 만든다. 컴포넌트 안에서 `cache(...)`를 부르면 렌더링마다 새 메모가 생겨 의미가 없다.

## 요청을 넘어 남는 응답, 데이터 캐시

메모이제이션은 요청이 끝나면 사라진다. 여러 사용자가 같은 가격을 물을 때 API를 한 번만 부르려면 응답을 요청 밖에 저장해야 한다. 이게 데이터 캐시다. `fetch`에 옵션을 주면 쓴다.

```js
fetch(url, { cache: "force-cache" });               // 무기한 저장
fetch(url, { next: { revalidate: 60 } });           // 60초 뒤 다시 확인
fetch(url, { next: { tags: ["price"] } });          // 태그를 붙여 두고 나중에 태그로 지운다
fetch(url, { cache: "no-store" });                  // 저장하지 않는다
```

Next 14까지는 옵션 없는 `fetch`가 `force-cache`처럼 동작했다. 15부터 기본값이 저장하지 않는 쪽으로 바뀌었다. 14 시절 코드를 옮기면 갑자기 API 호출이 늘어나는 이유다. 반대로 옵션이 없어도 빌드 때 한 번 불려 HTML에 값이 굳는 경우가 있는데, 그건 데이터 캐시가 아니라 라우트를 미리 렌더링한 결과다. 둘을 구분하는 방법은 [정적·동적 렌더링 글](/posts/nextjs-static-dynamic-rendering)에 있다.

DB 조회처럼 `fetch`가 아닌 함수는 `unstable_cache`로 감싸 데이터 캐시에 넣는다. 이름에 `unstable_`이 붙어 있지만 Cache Components를 켜지 않은 앱에서는 여전히 이 방법을 쓴다.

```js
import { unstable_cache } from "next/cache";
export const getPrice = unstable_cache(
  async (id) => db.price.find(id),
  ["price"],                              // 캐시 키 앞부분
  { tags: ["price"], revalidate: 3600 },
);
```

데이터 캐시는 자체 호스팅이면 `.next/cache` 아래 디스크에 쌓인다. 문서에 따르면 `fetch` 캐시와 `unstable_cache`는 배포가 바뀌어도 남는다. 이건 장점이면서 함정이다. 응답 모양이 바뀐 새 배포가 옛 모양의 캐시를 읽을 수 있다. 응답 구조를 바꾸는 배포라면 태그나 키를 바꾼다.

## 렌더링 결과를 통째로, 전체 라우트 캐시

정적 라우트는 빌드 때 HTML과 RSC payload를 만들어 둔다. 요청이 오면 렌더링 없이 이 파일을 준다. 이게 전체 라우트 캐시다. 동적 라우트(`ƒ`)는 이 층을 거치지 않는다. 응답 헤더 `x-nextjs-cache`로 이 층의 결과를 밖에서 볼 수 있다.

```bash
# 정적 페이지의 캐시 상태를 헤더로 본다
curl -sI localhost:3922/tagged | grep -i x-nextjs-cache
```

```text
x-nextjs-cache: HIT
```

`HIT`은 저장된 걸 그대로 줬다는 뜻, `STALE`은 오래된 걸 주면서 뒤에서 다시 만들기 시작했다는 뜻, `MISS`는 저장된 게 없어 지금 렌더링했다는 뜻이다. 이 헤더가 아예 없으면 동적 라우트다.

데이터 캐시와 라우트 캐시는 따로 노는 것처럼 보이지만 무효화로 연결되어 있다. 태그 `price`를 무효화하면 그 태그가 붙은 fetch를 쓴 정적 페이지도 다시 만들어진다. 실험에서 `revalidateTag("price", "max")`를 부르자 다음 요청이 `STALE`로 옛 가격을 받고 API를 한 번 불렀고, 그다음 요청이 `HIT`으로 새 가격을 받았다. 같은 실험의 자세한 시간표는 [SSG와 ISR](/posts/rendering-ssg-isr)에 있다.

`revalidatePath`도 같은 장치를 쓴다. Next는 라우트마다 경로에서 만든 "보이지 않는 태그"를 자동으로 붙인다. 문서에서는 soft tag라고 부르고 `_N_T_` 접두사가 붙는다. `/blog/hello`라면 `_N_T_/layout`, `_N_T_/blog/layout`, `_N_T_/blog/hello/layout`, `_N_T_/blog/hello`가 붙는다. `revalidatePath("/blog/hello")`는 이 태그들을 무효화하는 것이다. 그래서 `revalidatePath("/", "layout")`처럼 루트 레이아웃을 무효화하면 사이트 전체가 다시 만들어진다. 편하지만 비싸다. 문서도 가능하면 경로보다 태그로 정확히 지우라고 권한다.

## 브라우저 메모리의 사본, 클라이언트 캐시

서버를 다 고쳐도 남는 층이 하나 있다. `Link`로 이동하면 라우터가 받은 RSC payload를 브라우저 메모리에 둔다. 어떤 이동에서 다시 서버에 묻는지 재 보려고, 동적 페이지 `/memo`를 오가며 가짜 API가 받은 호출 수를 셌다. `/memo` 한 번 렌더링에 API 호출이 2번(위의 `k=memo`와 `v=2`) 생긴다.

```text
-- 기본 설정
open /feed                 API hits so far: 1
Link -> /memo              API hits so far: 3
Link -> /feed              API hits so far: 3
Link -> /memo again        API hits so far: 5
browser back -> /feed      API hits so far: 5
browser forward -> /memo   API hits so far: 5
router.refresh()           API hits so far: 7
```

`/feed`를 열자마자 1이 된 건 화면에 보이는 `/memo` 링크를 미리 받으면서 서버가 그 라우트의 일부(본문 위쪽의 레이아웃이나 메타데이터)를 렌더링했기 때문이다. 본문만 부르는 `v=2`는 이때 나가지 않았다. 링크로 다시 들어가자 2가 늘었다. 동적 페이지는 기본으로 클라이언트에 저장되지 않는다는 뜻이다. Next 15에서 `staleTimes.dynamic` 기본값이 30초에서 0초로 바뀐 결과다. 반대로 브라우저의 뒤로·앞으로 가기는 서버에 묻지 않았다. 스크롤 위치와 화면이 흔들리지 않게 하려고 이 이동에서는 받아 둔 것을 그대로 쓴다. `router.refresh()`는 현재 라우트를 서버에서 다시 받는다.

같은 실험을 `next.config.mjs`에 `experimental.staleTimes.dynamic: 30`을 주고 다시 했다.

```text
-- staleTimes.dynamic = 30
open /feed                 API hits so far: 1
Link -> /memo              API hits so far: 3
Link -> /feed              API hits so far: 3
Link -> /memo again        API hits so far: 3
browser back -> /feed      API hits so far: 3
browser forward -> /memo   API hits so far: 3
router.refresh()           API hits so far: 5
```

이번에는 30초 안에 링크로 다시 들어가도 서버에 묻지 않았다. 처음 장면에서 "새로고침하니 바뀌었다"는 사람이 이 경우다. 서버는 이미 99,000원을 주는데 그 사람의 탭에는 89,000원짜리 payload가 남아 있었다. 새로고침은 이 층을 비운다.

정적 페이지는 `staleTimes.static`(기본 5분) 동안 재사용된다. 이 값은 실험 기능이라 이름 앞에 `experimental`이 붙는다. Cache Components를 켜면 `cacheLife`의 `stale` 값으로 라우트마다 정하는 방법이 권장되고, 이때 클라이언트는 최소 30초를 지킨다.

이 층을 비우는 방법은 `router.refresh()`, 서버 액션 안에서 부르는 `revalidatePath`·`revalidateTag`·`updateTag`, 서버 액션 안의 `cookies().set`·`delete`, 그리고 새로고침이다. Route Handler에서 `revalidateTag`를 불러도 다른 사용자 브라우저에 있는 사본은 지워지지 않는다. 그 사본은 그 탭이 다시 묻거나 시간이 지나야 바뀐다.

## 값이 안 바뀔 때 어디부터 의심하나

위 실험들을 합치면 바깥에서 안쪽으로 하나씩 지워 가는 순서가 나온다.

먼저 브라우저를 뺀다. 같은 주소를 `curl`로 요청해서 새 값이 오면 서버는 이미 맞고, 남은 건 그 사용자의 클라이언트 캐시다. 새로고침으로 바뀌면 확정이다. 사용자 행동 뒤에 바로 보여야 하는 값이면 그 행동을 서버 액션으로 처리하고 액션 안에서 재검증한다.

```bash
# 응답 상태와 캐시 헤더, 본문의 가격을 한 번에 본다
curl -s -D - -o body.html localhost:3922/products/1 | grep -i -E '^HTTP|x-nextjs-cache|cache-control'
grep -o '[0-9,]*원' body.html | head -1
```

`curl`도 옛 값이면 헤더를 본다. `x-nextjs-cache: HIT`이면 라우트 캐시가 옛 HTML을 들고 있다. 그 페이지가 쓰는 fetch에 태그를 붙여 두었는지, 가격을 저장하는 코드가 그 태그를 무효화하는지 본다. 헤더가 없으면 동적 라우트인데, 그래도 옛 값이면 데이터 캐시다. 페이지가 부르는 `fetch`에 `force-cache`나 `revalidate`가 있는지, `unstable_cache`로 감싼 함수가 있는지 찾는다.

여기까지 맞는데 사람마다 다르면 서버가 여러 대인지, 앞에 CDN이 있는지 본다. 이건 아래 "실패하거나 서버가 여러 대일 때"에서 다룬다.

개발 서버로 재현하지 않는다. `next dev`는 페이지를 항상 새로 렌더링해서 위 층 대부분이 동작하지 않는다. `next build && next start`로 재현하고, 캐시 판단을 더 자세히 보고 싶으면 `NEXT_PRIVATE_DEBUG_CACHE=1 next start`로 로그를 켠다.

## Cache Components를 켜면 무엇이 바뀌나

Next 16에는 캐시를 다루는 두 번째 방식이 있다. `next.config`에 `cacheComponents: true`를 주면 켜진다. 문서는 이걸 기본 모델로, 위에서 본 fetch 옵션 중심의 방식을 "이전 모델"로 부른다.

켜면 판단의 출발점이 바뀐다. 이전 모델은 "기본으로 정적, 요청 시점 값을 쓰면 동적"이었다. Cache Components는 "기본으로 요청 때 실행, 캐시하고 싶은 것에 표시"다. 표시는 `"use cache"` 지시어로 한다. 함수, 컴포넌트, 파일 단위에 붙일 수 있다.

```tsx
import { cacheLife, cacheTag } from "next/cache";

export async function getPrice(id: string) {
  "use cache";
  cacheLife("hours"); // 얼마나 저장할지
  cacheTag(`price-${id}`); // 나중에 무엇으로 지울지
  return db.price.find(id);
}
```

캐시 키는 직접 정하지 않는다. 빌드 ID, 함수의 위치로 만든 ID, 직렬화한 인자, 그리고 함수가 바깥에서 붙잡은 변수가 합쳐진다. 그래서 `userId`를 클로저로 붙잡은 캐시 함수는 사용자마다 다른 항목이 된다. 대신 `"use cache"` 안에서는 `cookies()`, `headers()`, `searchParams`를 읽을 수 없다. 읽으면 `next-request-in-use-cache` 에러다. 요청 값은 바깥에서 읽어 인자로 넘긴다. 키에 빌드 ID가 들어가므로 새로 배포하면 `"use cache"` 항목은 모두 새로 시작한다. 배포를 넘어 남던 `fetch` 캐시와 다른 점이다.

`cacheLife`는 세 값을 정한다. `stale`은 브라우저가 서버에 묻지 않고 쓰는 시간, `revalidate`는 서버가 다시 만들기 시작하는 시간, `expire`는 옛 값을 더는 주지 않는 시간이다. 미리 정해 둔 프로필은 이렇다.

```text
Profile   stale  revalidate  expire
default   5m     15m         never
seconds   30s    1s          60s
minutes   5m     1m          1h
hours     5m     1h          1d
days      5m     1d          1w
weeks     5m     1w          30d
max       5m     30d         1y
```

항목이 만들어진 지 몇 초 지났는지에 따라 같은 탭에서 다시 볼 때 무슨 일이 생기는지 함수로 짜 보면 세 값의 역할이 갈린다. 브라우저는 `stale`(최소 30초) 안이면 서버에 묻지 않는다. 서버는 `revalidate` 전이면 그대로 주고, `expire` 전이면 옛 값을 주며 뒤에서 다시 만들고, 그 뒤면 새로 만들 때까지 기다리게 한다. 단순하게 하려고 브라우저와 서버의 사본이 같은 순간에 만들어졌다고 가정한다.

어디에 저장되는지도 다르다. 기본 핸들러는 인스턴스 메모리의 LRU다. 서버 한 대를 오래 띄우는 자체 호스팅이면 잘 맞고, 요청마다 다른 인스턴스가 뜰 수 있는 서버리스에서는 런타임 항목이 거의 재사용되지 않는다. 여러 인스턴스가 함께 쓰려면 `"use cache: remote"`로 플랫폼이 제공하는 원격 핸들러(Redis 같은 것)에 둔다. 네트워크를 한 번 더 타므로 적중률이 높을 때만 이득이다.

이미 돌아가는 앱이라면 서두를 필요는 없다. 켜는 순간 `fetch` 옵션 대신 `"use cache"`로 생각하는 방식이 바뀌고, 요청 시점 값을 Suspense 밖에서 읽는 코드는 빌드 에러가 난다. 새 앱이거나, 한 페이지 안에서 정적인 부분과 사용자별 부분이 섞여 있어 페이지 전체를 동적으로 돌리던 앱이라면 얻는 게 크다.

가격을 저장한 직후에 부를 수 있는 함수가 여럿이다. 무엇이 다른지는 "누가 언제 새 값을 보나"로 갈린다.

`updateTag(tag)`는 서버 액션에서만 부를 수 있다. 태그를 즉시 만료시키고, 액션 응답에 현재 페이지를 새 데이터로 다시 렌더링한 결과를 같이 실어 보낸다. 가격을 바꾼 관리자가 저장 버튼을 누른 그 화면에서 바로 99,000원을 봐야 할 때 쓴다. 자기가 쓴 값을 자기가 바로 읽는다고 해서 read-your-own-writes라고 부른다.

`revalidateTag(tag, "max")`는 서버 액션과 Route Handler 둘 다에서 부를 수 있다. 태그를 오래된 것으로 표시만 하고, 다음에 읽는 사람이 옛 값을 받는 사이 뒤에서 새로 만든다. 서버 액션에서 불러도 그 응답에 새 화면을 싣지 않는다. 그래서 관리자 화면에서 이걸 쓰면 저장했는데 화면은 옛 가격인 장면이 나온다. CMS 웹훅처럼 화면 없이 "언젠가 바뀌면 되는" 갱신에 맞다. 16부터 두 번째 인자를 빼면 타입 에러이고, 옛 값을 바로 버리려면 `{ expire: 0 }`을 준다.

`revalidatePath(path)`는 태그를 몰라도 경로로 무효화한다. 앞에서 본 soft tag를 지우는 것이라 그 경로의 레이아웃 데이터까지 같이 다시 만든다. 범위가 넓어지기 쉽다.

`refresh()`(서버 액션 안, `next/cache`)와 `router.refresh()`(클라이언트)는 캐시를 지우지 않는다. 현재 라우트를 서버에서 다시 받아 그릴 뿐이다. 캐시 밖의 값, 예를 들어 `no-store`로 읽는 알림 개수를 바꾼 뒤에 쓴다. 데이터 캐시에 옛 가격이 있으면 `router.refresh()`를 아무리 불러도 옛 가격이 온다. "refresh를 불렀는데 안 바뀐다"는 문의의 대부분이 이 경우다.

```ts
"use server";
import { updateTag } from "next/cache";
import { redirect } from "next/navigation";

export async function savePrice(id: string, won: number) {
  // 권한 확인과 입력 검증은 생략. 실제로는 여기서 먼저 한다
  await db.price.update(id, won);
  updateTag(`price-${id}`); // 이 화면에서 바로 새 값
  redirect(`/admin/products/${id}`); // redirect는 예외를 던지므로 재검증을 먼저 부른다
}
```

서버 액션을 공개 엔드포인트로 보고 지키는 일은 [서버 액션과 민감 데이터](/posts/nextjs-server-actions-security)에, 웹훅을 받는 Route Handler를 만드는 법은 [Route Handler와 Proxy](/posts/nextjs-route-handlers-proxy)에 있다.

## 실패하거나 서버가 여러 대일 때

다시 만들다 실패하면 Next는 마지막으로 성공한 결과를 계속 준다. ISR 페이지(`revalidate = 5`)가 부르는 가격 API를 500으로 바꿔 두고 요청해 봤다.

```text
18:59:22 GET /isr -> 200 isr 109000 at 18:59:21  x-nextjs-cache: HIT
-- API를 500으로
18:59:29 GET /isr -> 200 isr 109000 at 18:59:21  x-nextjs-cache: STALE
18:59:30 GET /isr -> 200 isr 109000 at 18:59:21  x-nextjs-cache: HIT
18:59:36 GET /isr -> 200 isr 109000 at 18:59:21  x-nextjs-cache: STALE
```

서버 로그에는 `Error: price api 500`과 digest가 찍혔지만 사용자는 200과 마지막 정상 페이지를 받았다. 이 성질은 페이지가 예외를 던질 때만 지켜진다. 조회 실패를 `try/catch`로 삼키고 "가격 정보 없음"을 그리면 그 화면이 정상 결과로 저장된다. [SSG와 ISR](/posts/rendering-ssg-isr#다시-만들다-실패하면)에 같은 현상을 더 길게 잰 기록이 있다.

서버가 여러 대면 무효화가 그 요청을 받은 인스턴스에만 일어난다. `revalidateTag`가 A 인스턴스에서 불리면 B는 계속 옛 값을 준다. 로드 밸런서가 번갈아 보내면 새로고침할 때마다 가격이 바뀐다. 문서의 해법은 캐시 핸들러(`cacheHandlers`)를 직접 두는 것이다. 핸들러의 `updateTags()`는 무효화 사건을 Redis 같은 공유 저장소에 쓰고, `refreshTags()`는 요청을 시작하기 전에 그 저장소를 읽어 자기 상태를 맞춘다. `refreshTags()`가 예외를 던지면 요청 자체가 실패하므로, 저장소가 죽었을 때는 잡아서 마지막 상태로 계속 가게 짠다.

CDN이 앞에 있으면 HTML과 RSC payload를 같은 수명과 같은 무효화 규칙으로 캐시해야 한다. 둘이 엇갈리면 새로고침한 화면과 링크로 들어간 화면이 다른 가격을 보여 준다. Next가 보내는 `Vary` 헤더를 CDN이 존중하게 설정한다. 배포 중에 옛 빌드의 브라우저가 새 빌드 서버를 만나는 문제는 `deploymentId`를 설정해 두면 브라우저가 감지하고 전체 새로고침으로 맞춘다.

## 다시 99,000원으로

처음 장면을 층별로 풀면 이렇다. 관리자가 저장한 뒤 `revalidateTag("price", "max")`를 불렀다면 첫 손님은 `STALE`로 옛 가격을 받는다. 그 손님 이후로는 서버가 새 가격을 주지만, 그 전에 페이지를 링크로 봐 둔 손님의 탭에는 클라이언트 캐시가 남아 있다. 서버가 두 대라면 한 대는 아직 무효화를 모른다. 요청 메모이제이션은 요청 하나 안의 이야기라 이 장면과 관계없다. 값을 바꾸는 쪽에서는 "누가 언제 새 값을 봐야 하나"를 먼저 정하고, 그에 맞게 `updateTag`, `revalidateTag`, `revalidatePath`, `refresh`를 고른다. 값이 안 바뀌는 쪽에서는 `curl`로 브라우저를 빼고, `x-nextjs-cache`로 라우트 캐시를 보고, fetch 옵션으로 데이터 캐시를 본다.

## 면접에서 나올 만한 질문

### Next.js App Router의 캐시 층을 설명해 주세요.

요청 하나 안에서 같은 GET fetch를 합치는 요청 메모이제이션, 요청을 넘어 fetch 결과를 저장하는 데이터 캐시, 정적 라우트의 HTML과 RSC payload를 저장하는 전체 라우트 캐시, 브라우저 메모리에 RSC payload를 두는 클라이언트 캐시가 있다. 앞의 셋은 서버, 마지막은 브라우저 탭에 있다. 범위와 수명이 달라서 값이 안 바뀔 때 어느 층인지 바깥부터 하나씩 확인한다.

### 요청 메모이제이션과 데이터 캐시는 무엇이 다른가요?

메모이제이션은 렌더링 한 번 안에서만 살아서, 같은 URL과 옵션의 GET fetch를 layout, page, generateMetadata가 각자 불러도 한 번만 나가게 한다. `no-store`여도 동작하고 요청이 끝나면 잊는다. 데이터 캐시는 `force-cache`나 `revalidate`를 준 fetch의 응답을 요청 사이에 저장해 여러 사용자가 나눠 쓴다. DB 조회는 메모이제이션에 React `cache`, 데이터 캐시에 `unstable_cache`나 `"use cache"`를 쓴다.

### 값을 바꿨는데 화면이 그대로입니다. 어디부터 보나요?

`curl`로 같은 주소를 요청해 브라우저를 뺀다. 새 값이 오면 클라이언트 캐시가 원인이고, 새로고침이나 서버 액션 안의 재검증으로 풀린다. 옛 값이면 `x-nextjs-cache` 헤더로 라우트 캐시를 보고, 동적 라우트인데도 옛 값이면 fetch 옵션과 `unstable_cache`로 데이터 캐시를 찾는다. 사람마다 다르면 인스턴스 여러 대나 CDN을 의심한다.

### revalidateTag와 updateTag는 언제 나눠 쓰나요?

`updateTag`는 서버 액션 전용으로 태그를 즉시 만료하고 액션 응답에 새 화면을 실어서, 저장한 사람이 바로 자기 변경을 본다. `revalidateTag(tag, "max")`는 옛 값을 주면서 뒤에서 갱신하는 방식이라 Route Handler 웹훅처럼 약간 늦어도 되는 갱신에 쓴다. 서버 액션에서 `revalidateTag`를 쓰면 응답에 새 화면이 실리지 않아 저장 직후 옛 값이 보일 수 있다.

### router.refresh()를 불렀는데도 옛 값이 나오는 이유는요?

`router.refresh()`는 캐시를 무효화하지 않고 현재 라우트를 서버에서 다시 렌더링해 받을 뿐이다. 서버의 데이터 캐시나 라우트 캐시가 옛 값을 들고 있으면 다시 받아도 옛 값이다. 서버 쪽 사본을 지우려면 `revalidateTag`, `updateTag`, `revalidatePath` 중 하나를 먼저 불러야 한다.

### 클라이언트 캐시는 언제 서버에 다시 묻나요?

Next 15부터 동적 페이지는 `staleTimes.dynamic`이 0이라 링크로 다시 들어가면 매번 서버에 묻는다. 정적 페이지는 기본 5분 동안 재사용한다. 브라우저 뒤로·앞으로 가기는 스크롤과 화면을 지키려고 받아 둔 것을 그대로 쓴다. 새로고침, `router.refresh()`, 서버 액션의 재검증과 쿠키 변경이 이 층을 비운다.

### "use cache"는 기존 fetch 캐시와 무엇이 다른가요?

Cache Components를 켜야 쓰며, 함수나 컴포넌트에 표시해 그 결과를 캐시한다. 키는 빌드 ID, 함수 ID, 인자, 클로저 변수로 자동으로 만들어지고, 안에서 cookies나 headers를 읽을 수 없어 요청 값은 인자로 넘긴다. 키에 빌드 ID가 들어가 배포마다 새로 시작하는 반면, fetch 캐시와 `unstable_cache`는 배포를 넘어 남는다. 기본 저장소는 인스턴스 메모리라 서버리스에서는 `"use cache: remote"`를 고려한다.

### 서버가 여러 대일 때 재검증은 어떻게 맞추나요?

기본으로는 `revalidateTag`를 받은 인스턴스만 무효화되어 다른 인스턴스가 옛 값을 계속 준다. 캐시 핸들러를 두고 `updateTags()`에서 무효화 사건을 Redis 같은 공유 저장소에 쓰고, `refreshTags()`에서 요청 전에 읽어 맞춘다. 저장소 장애 때 `refreshTags()`가 예외를 던지면 요청이 실패하니 잡아서 마지막 상태로 계속 간다. 앞에 CDN이 있으면 HTML과 RSC payload를 같은 규칙으로 캐시한다.
