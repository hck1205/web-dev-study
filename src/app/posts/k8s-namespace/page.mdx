`kubectl apply -f k8s/`가 깔끔하게 끝났다. 그런데 바로 `kubectl get pods`를 치면 이렇게 나온다.

```text
No resources found in default namespace.
```

Pod는 떠 있다. 매니페스트에 `namespace: shop-prod`가 적혀 있었고, kubectl은 `default`를 보고 있었을 뿐이다. 쿠버네티스를 처음 만지면 한 번씩 겪는 일이다. 반대 방향도 있다. 개발 환경을 지운다고 `kubectl delete -f`를 쳤는데 컨텍스트가 운영 네임스페이스를 가리키고 있었다면 웃을 일이 아니다.

네임스페이스는 클러스터 안의 객체를 칸으로 나누는 장치다. 이 글은 그 칸이 무엇을 나누고 무엇을 나누지 않는지, 이름과 DNS, 권한, 한도, 보안 수준이 네임스페이스에 어떻게 걸리는지, 그리고 지운 네임스페이스가 Terminating에서 멈추는 이유를 본다. `kubectl` 출력은 [Pod 글들](/posts/k8s-pod-basics)처럼 kwok로 띄운 실습 클러스터(Kubernetes 1.30)에서 받았다. API 서버, 컨트롤러, 인가, 어드미션은 진짜이고 노드와 컨테이너만 흉내 낸다. 그래서 Pod IP와 Service IP가 둘 다 `10.0.0.x`처럼 보이고, 실제 DNS 조회 결과는 예시로 적었다.

## 이름을 나누는 칸, 벽은 아니다

네임스페이스가 가장 먼저 하는 일은 이름을 나누는 것이다. 같은 클러스터에 `api`라는 Deployment가 두 개 있어도 네임스페이스가 다르면 부딪히지 않는다.

```bash
# 네임스페이스 두 개를 만들고, 같은 이름의 Deployment를 각각 띄운다
kubectl create namespace shop-dev
kubectl create namespace shop-prod
kubectl create deployment api --image=nginx:1.27 --replicas=2 -n shop-dev
kubectl create deployment api --image=nginx:1.27 --replicas=3 -n shop-prod

# 네임스페이스를 안 주면 default만 본다
kubectl get pods

# 모든 네임스페이스를 한 번에 본다
kubectl get deploy -A
```

```text
namespace/shop-dev created
namespace/shop-prod created
deployment.apps/api created
deployment.apps/api created
No resources found in default namespace.
NAMESPACE   NAME   READY   UP-TO-DATE   AVAILABLE   AGE
shop-dev    api    2/2     2            2           8s
shop-prod   api    2/3     3            2           8s
```

`-A`(`--all-namespaces`)로 보면 NAMESPACE 칸이 앞에 붙는다. 객체의 진짜 이름은 `shop-prod/api`처럼 네임스페이스와 이름의 짝이다. etcd에도 `/registry/deployments/shop-prod/api` 같은 키로 들어간다.

여기서 오해가 하나 생긴다. 칸을 나눴으니 서로 못 건드릴 거라는 생각이다. 네임스페이스는 기본으로는 이름만 나눈다. shop-dev의 Pod가 shop-prod의 Pod로 패킷을 보내면 그대로 닿는다. 같은 노드에 섞여 뜨고, CPU도 같이 쓴다. 칸 사이에 벽을 세우는 것은 따로 거는 정책들이다. 네트워크는 NetworkPolicy, API 권한은 RBAC, 자원 총량은 ResourceQuota, 컨테이너 보안 수준은 Pod Security Admission이 맡는다. 이 정책들이 "네임스페이스 단위로" 걸리기 때문에 네임스페이스가 격리의 단위처럼 보이는 것이다.

## 처음부터 있는 네 개

클러스터를 막 만들면 네임스페이스가 넷 있다.

```bash
# 네임스페이스 목록과 라벨을 본다
kubectl get namespaces --show-labels
```

```text
NAME              STATUS   AGE   LABELS
default           Active   35s   kubernetes.io/metadata.name=default
kube-node-lease   Active   35s   kubernetes.io/metadata.name=kube-node-lease
kube-public       Active   35s   kubernetes.io/metadata.name=kube-public
kube-system       Active   35s   kubernetes.io/metadata.name=kube-system
shop-dev          Active   8s    kubernetes.io/metadata.name=shop-dev
shop-prod         Active   8s    kubernetes.io/metadata.name=shop-prod
```

`default`는 네임스페이스를 안 적었을 때 들어가는 곳이다. 운영 워크로드를 여기 두면 나중에 권한과 한도를 나누기가 어렵다. `kube-system`은 CoreDNS, kube-proxy, CNI 같은 클러스터 부품이 사는 곳이라 손대지 않는다. `kube-public`은 인증 없이도 읽을 수 있는 공개 정보(클러스터 부트스트랩용 ConfigMap 정도)를 두는 곳이고, `kube-node-lease`에는 노드마다 Lease 객체가 하나씩 있다. kubelet이 이 Lease를 주기적으로 갱신해 "살아 있다"는 신호를 보내는데, 노드 상태 전체를 고쳐 쓰는 것보다 훨씬 가볍다.

LABELS 칸의 `kubernetes.io/metadata.name`은 API 서버가 모든 네임스페이스에 자동으로 붙인다(1.21부터). 라벨로 네임스페이스를 고르는 NetworkPolicy의 `namespaceSelector`가 이 라벨 덕분에 "이름이 shop-prod인 네임스페이스"를 따로 라벨을 달지 않고도 가리킬 수 있다.

`default`와 `kube-system`은 지울 수도 없다.

```bash
# 시스템 네임스페이스를 지워 본다
kubectl delete ns default
kubectl delete ns kube-system
```

```text
Error from server (Forbidden): namespaces "default" is forbidden: this namespace may not be deleted
Error from server (Forbidden): namespaces "kube-system" is forbidden: this namespace may not be deleted
```

참조에도 경계가 있다. Ingress의 backend Service도 같은 네임스페이스에 있어야 한다.

## 이름을 지을 때 걸리는 규칙

네임스페이스 이름은 DNS 이름의 한 조각으로 쓰인다. 그래서 규칙이 DNS 라벨(RFC 1123)과 같다. 소문자, 숫자, 하이픈만 쓰고, 처음과 끝은 영숫자이고, 63자 이하다. 실제로 어긋나게 만들어 보면 API 서버가 정규식까지 알려 준다.

```bash
# 대문자, 점, 64자 이름을 차례로 넣어 본다
kubectl create ns Shop-Prod
kubectl create ns shop.prod
kubectl create ns $(printf 'a%.0s' {1..64})
```

```text
The Namespace "Shop-Prod" is invalid: metadata.name: Invalid value: "Shop-Prod": a lowercase RFC 1123 label must consist of lower case alphanumeric characters or '-', and must start and end with an alphanumeric character (e.g. 'my-name',  or '123-abc', regex used for validation is '[a-z0-9]([-a-z0-9]*[a-z0-9])?')
The Namespace "shop.prod" is invalid: metadata.name: Invalid value: "shop.prod": must not contain dots
The Namespace "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa" is invalid:
* metadata.name: Invalid value: "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa": must be no more than 63 characters
* metadata.labels: Invalid value: "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa": must be no more than 63 characters
```

마지막 출력에 오류가 두 줄인 게 재미있다. 앞에서 본 `kubernetes.io/metadata.name` 라벨 값에도 이름이 그대로 들어가니 라벨 값 길이 제한(63자)에도 같이 걸렸다. 점이 안 되는 이유는 Service의 DNS 이름이 `서비스.네임스페이스.svc...`로 이어지기 때문이다. 이름에 점이 있으면 어디까지가 네임스페이스인지 알 수 없다.

`kube-`로 시작하는 이름은 만들 수는 있지만 시스템용으로 남겨 두는 관례가 있다. 아래에서 규칙을 직접 코드로 옮겨 볼 수 있다.

## kubectl이 어느 칸을 보고 있나

처음 이야기로 돌아가 보자. kubectl은 `-n`을 안 주면 kubeconfig의 현재 컨텍스트에 적힌 네임스페이스를 쓰고, 거기도 없으면 `default`를 쓴다. 매번 `-n`을 붙이기 귀찮으면 컨텍스트의 기본값을 바꾼다.

```bash
# 현재 컨텍스트의 기본 네임스페이스를 shop-dev로 바꾼다
kubectl config set-context --current --namespace=shop-dev

# 이제 -n 없이도 shop-dev를 본다
kubectl get pods

# 지금 기본 네임스페이스가 무엇인지 확인한다
kubectl config view --minify -o jsonpath='{..namespace}{"\n"}'
```

```text
Context "kwok-wl-lab" modified.
NAME                  READY   STATUS    RESTARTS   AGE
api-59cfb66bb-dpspq   1/1     Running   0          16s
api-59cfb66bb-qv8q7   1/1     Running   0          16s
shop-dev
```

편하지만 위험도 같이 커진다. 컨텍스트에 숨은 기본값은 화면에 안 보인다. 운영 클러스터에서 지우는 명령을 칠 때는 습관처럼 `-n`을 명시하고, 셸 프롬프트에 현재 컨텍스트와 네임스페이스를 띄워 두는 사람이 많다(kube-ps1 같은 도구). `kubens`는 이 전환을 짧게 해 주는 도구다.

헷갈리게 만드는 동작이 하나 더 있다. 오타 난 네임스페이스로 조회하면 에러가 아니라 "없다"고 답한다.

```bash
# shop-prod를 shop-prd로 잘못 쳤다
kubectl get pods -n shop-prd

# 같은 오타로 만들려고 하면 그때서야 없다고 한다
kubectl apply -n shop-prd -f configmap.yaml

# 파일 안의 namespace와 -n이 다르면 kubectl이 막는다
kubectl apply -n shop-prod -f configmap-dev.yaml
```

```text
No resources found in shop-prd namespace.
Error from server (NotFound): error when creating "configmap.yaml": namespaces "shop-prd" not found
error: the namespace from the provided object "shop-dev" does not match the namespace "shop-prod". You must pass '--namespace=shop-dev' to perform this operation.
```

조회가 비어 있으면 Pod가 사라졌다고 놀라기 전에 네임스페이스 이름부터 다시 본다. `kubectl get ns`로 정확한 이름을 확인하는 게 가장 빠르다. 매니페스트에 `namespace:`를 적어 두면 세 번째처럼 엉뚱한 곳에 적용되는 걸 막아 주지만, 같은 매니페스트를 여러 환경에 쓰려면 적지 않고 `-n`이나 Kustomize의 `namespace:`로 넣는다. 둘 중 하나로 팀 규칙을 정해 둔다. 매니페스트를 폴더로 어떻게 나누는지는 [쿠버네티스 프로젝트 구조](/posts/k8s-project-structure)에서 다룬다.

## 네트워크는 기본으로 열려 있다

권한부터 보자. Role과 RoleBinding은 네임스페이스 안의 객체라서 그 네임스페이스에만 효력이 있다. 내장 ClusterRole `edit`를 RoleBinding으로 묶으면 "이 네임스페이스에서만 edit"가 된다. 권한 묶음은 클러스터에 하나 두고, 어디에 적용할지는 RoleBinding이 정하는 방식이다.

```bash
# shop-dev에 배포용 ServiceAccount를 만들고, 그 네임스페이스에서만 edit 권한을 준다
kubectl create serviceaccount deployer -n shop-dev
kubectl create rolebinding deployer-edit --clusterrole=edit \
  --serviceaccount=shop-dev:deployer -n shop-dev

# 네임스페이스마다 권한을 확인한다
kubectl auth can-i update deployments -n shop-dev  --as=system:serviceaccount:shop-dev:deployer
kubectl auth can-i update deployments -n shop-prod --as=system:serviceaccount:shop-dev:deployer
kubectl get pods -n shop-prod --as=system:serviceaccount:shop-dev:deployer
```

```text

yes
no
Error from server (Forbidden): pods is forbidden: User "system:serviceaccount:shop-dev:deployer" cannot list resource "pods" in API group "" in the namespace "shop-prod"
```

CI가 환경마다 다른 ServiceAccount로 배포하게 해 두면, 개발 파이프라인의 토큰이 새도 운영은 못 건드린다. 거꾸로 CI 토큰 하나에 ClusterRoleBinding으로 `cluster-admin`을 주면 네임스페이스를 아무리 나눠도 소용없다.

한도는 ResourceQuota가 건다. CPU·메모리 합계를 거는 법과 Pod가 Pending조차 안 되고 ReplicaSet 이벤트에만 FailedCreate가 남는 함정은 [requests와 limits](/posts/k8s-pod-resources) 글에서 실제로 재현했다. 여기서는 개수 한도만 보자. `count/<리소스>.<그룹>` 형식으로 거의 모든 객체의 개수를 묶을 수 있다.

```bash
# shop-dev에 Deployment 2개, Service 1개, Pod 10개 한도를 건다
kubectl create quota objects -n shop-dev --hard=count/deployments.apps=2,services=1,pods=10
kubectl create deployment worker --image=busybox:1.36 -n shop-dev -- sleep 3600
kubectl create deployment cron --image=busybox:1.36 -n shop-dev -- sleep 3600
kubectl get quota -n shop-dev
```

```text
resourcequota/objects created
deployment.apps/worker created
error: failed to create deployment: deployments.apps "cron" is forbidden: exceeded quota: objects, requested: count/deployments.apps=1, used: count/deployments.apps=2, limited: count/deployments.apps=2
NAME      AGE   REQUEST                                                  LIMIT
objects   0s    count/deployments.apps: 2/2, pods: 3/10, services: 0/1
```

이미 있던 `api`와 새 `worker`로 2개가 찼고, 세 번째는 만드는 순간 거절됐다. 테스트용 네임스페이스에서 LoadBalancer Service(`services.loadbalancers`)를 0으로 막아 두면 실수로 클라우드 로드 밸런서 비용이 나가는 일을 막을 수 있다.

보안 수준은 Pod Security Admission이 네임스페이스 라벨을 읽어서 건다. 1.25에 GA가 됐고 그전의 PodSecurityPolicy를 대신한다. `privileged`, `baseline`, `restricted` 세 단계가 있고, 모드는 `enforce`(거절), `audit`(감사 로그), `warn`(경고)이다. 운영 네임스페이스에 `restricted`를 걸어 봤다.

```bash
# shop-prod에 restricted를 강제한다
kubectl label ns shop-prod pod-security.kubernetes.io/enforce=restricted --overwrite

# 보안 설정이 없는 Pod를 띄워 본다
kubectl run debug --image=busybox:1.36 -n shop-prod -- sleep 3600
```

```text

namespace/shop-prod labeled
```

첫 경고가 중요하다. 라벨을 거는 순간 이미 떠 있는 `api` Pod 셋이 규칙을 어기고 있다고 알려 주지만, 그 Pod들을 죽이지는 않는다. 함정은 다음 배포다.

```bash

kubectl -n shop-prod rollout restart deploy/api
kubectl -n shop-prod get rs
```


경고는 길어서 뒷부분을 줄였다. 새 ReplicaSet은 DESIRED 1, CURRENT 0이다. Pod를 만들 때마다 거절당하고 있다. 옛 Pod가 살아 있어 서비스는 멀쩡하니 아무도 모르고 지나가다가, 노드 교체로 옛 Pod가 사라지는 날 장애가 된다. 그래서 순서를 지킨다. 먼저 `warn`과 `audit`만 걸어 두고 경고가 사라질 때까지 매니페스트를 고친 다음 `enforce`로 올린다. `kubectl label --dry-run=server`로 미리 걸어 보면 위 경고만 받고 실제로는 바뀌지 않는다.

멈추는 자리는 대부분 둘이다. 하나는 주인 없는 finalizer다. 오퍼레이터를 먼저 지우고 그 오퍼레이터가 관리하던 CR이 남은 네임스페이스를 지우면, finalizer를 떼어 줄 주인이 없다. 실습에서는 ConfigMap에 아무도 처리하지 않는 finalizer를 달아 재현했다.



`NamespaceFinalizersRemaining`이 범인과 finalizer 이름까지 알려 준다. 그 finalizer의 주인(오퍼레이터)을 되살려 정리하게 하는 게 정석이고, 주인이 영영 없다면 정리할 외부 자원(클라우드 디스크, DNS 레코드 등)이 없는지 확인한 뒤 그 객체의 finalizer만 뗀다.

```bash
# 남은 객체와 finalizer를 확인하고, 그 객체에서만 뗀다
kubectl get configmap -n old-feature -o custom-columns=NAME:.metadata.name,FINALIZERS:.metadata.finalizers
kubectl patch configmap flags -n old-feature --type=merge -p '{"metadata":{"finalizers":null}}'
kubectl get ns old-feature
```

```text
NAME    FINALIZERS
flags   [example.com/cleanup]
configmap/flags patched
Error from server (NotFound): namespaces "old-feature" not found
```

다른 하나는 응답하지 않는 API 그룹이다. 지워진 prometheus-adapter의 APIService 등록만 남아 있는 상황을 만들고 네임스페이스를 지워 봤다.

```bash
# 사용할 수 없는 APIService가 있는지, 네임스페이스 조건이 무엇인지 본다
kubectl get apiservice | grep -v Local
kubectl get ns load-test -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}: {.message}{"\n"}{end}'
```

```text

v1beta1.custom.metrics.k8s.io          monitoring/prometheus-adapter   False (ServiceNotFound)   10s
v1beta1.metrics.k8s.io                 kube-system/metrics-server      True                      95s
NamespaceDeletionDiscoveryFailure=True DiscoveryFailed: Discovery failed for some groups, 1 failing: unable to retrieve the complete list of server APIs: custom.metrics.k8s.io/v1beta1: stale GroupVersion discovery: custom.metrics.k8s.io/v1beta1
NamespaceDeletionGroupVersionParsingFailure=False ParsedGroupVersions: All legacy kube types successfully parsed
NamespaceDeletionContentFailure=False ContentDeleted: All content successfully deleted, may be waiting on finalization

```

내용물은 다 지웠는데도 멈췄다. 컨트롤러는 custom.metrics.k8s.io 그룹 안에 이 네임스페이스의 객체가 있는지 확인할 수 없으니 끝내지 못한다. 이 네임스페이스와 아무 관계 없는 APIService 하나가 클러스터 전체의 네임스페이스 삭제를 막는 셈이다. 망가진 APIService를 고치거나 지우면 1초 만에 끝났다.

```bash
# 쓰지 않는 APIService 등록을 지운다
kubectl delete apiservice v1beta1.custom.metrics.k8s.io
```

<Callout kind="warning" title="네임스페이스의 finalize를 강제로 비우지 않는다">
검색하면 `kubectl get ns X -o json`에서 `spec.finalizers`를 비운 뒤 `kubectl replace --raw /api/v1/namespaces/X/finalize -f -`로 밀어 넣는 방법이 나온다. 네임스페이스는 사라지지만 안에 남은 객체는 etcd에 그대로 남고, 같은 이름의 네임스페이스를 다시 만들면 되살아난다. 외부 자원도 정리되지 않는다. 먼저 위의 conditions로 원인을 찾고, 남은 객체 단위로 finalizer를 다룬다. 이미 강제로 지웠다면 같은 이름으로 네임스페이스를 다시 만들어 남은 객체를 확인하고 정상적으로 지운다.
</Callout>

## 네임스페이스를 어떻게 나누나

정답은 없지만 흔한 방식은 셋이다. 팀마다 하나(`team-payments`), 환경마다 하나(`shop-dev`, `shop-stage`, `shop-prod`), 앱과 환경을 곱해서(`payments-prod`). 기준은 "권한과 한도를 누구 단위로 줄 것인가"다. 같은 사람들이 같이 배포하고 같은 한도를 나눠 쓰는 묶음이 한 네임스페이스가 된다.

개발과 운영을 한 클러스터의 네임스페이스로만 나누는 건 조심한다. 앞에서 봤듯 노드, CRD, 웹훅, 클러스터 버전은 공유된다. 개발에서 시험하던 오퍼레이터의 웹훅이 운영 Pod 생성을 막을 수 있고, 클러스터 업그레이드는 모든 환경에 한 번에 온다. 그래서 운영만큼은 클러스터를 따로 두는 곳이 많다. 클러스터를 새로 만드는 비용은 [EKS 클러스터 기본](/posts/eks-cluster-basics)에서 볼 수 있다. 서로 믿지 못하는 고객별로 나눠야 하는 멀티테넌시라면 네임스페이스만으로는 부족하다. 커널을 공유하기 때문이다. 노드를 나누거나(taint와 전용 노드 풀), vCluster처럼 네임스페이스 안에 가상 컨트롤 플레인을 두거나, 클러스터를 나눈다.

네임스페이스를 새로 만들 때 함께 넣을 기본 세트도 정해 두면 좋다. RoleBinding, ResourceQuota와 LimitRange, 기본 거부 NetworkPolicy, Pod Security 라벨이다. 손으로 하면 한두 개씩 빠지니 Helm 차트나 Terraform 모듈 하나로 찍어 낸다.

## 칸을 나누는 것과 벽을 세우는 것

네임스페이스는 이름을 나누는 칸이고, 권한(RoleBinding), 한도(ResourceQuota), 보안 수준(Pod Security 라벨), 네트워크(NetworkPolicy)를 거는 단위다. 칸만 만들고 정책을 안 걸면 이름만 다를 뿐 모두 섞여 있다. 노드, CRD, 웹훅처럼 클러스터 단위 객체는 칸을 넘어 영향을 준다. 지울 때는 안의 모든 것이 사라지고, 멈추면 conditions가 이유를 알려 준다. 다음 글에서는 이 네임스페이스 안에서 가장 많이 만드는 객체인 [Deployment](/posts/k8s-deployment)를 본다.

## 면접에서 나올 만한 질문

### 네임스페이스는 무엇을 격리하나요?

기본으로는 이름만 나눈다. 같은 이름의 객체를 네임스페이스별로 둘 수 있고, RBAC, ResourceQuota, LimitRange, Pod Security, NetworkPolicy 같은 정책을 네임스페이스 단위로 걸 수 있을 뿐이다. 정책을 안 걸면 다른 네임스페이스의 Pod와 네트워크로 통신할 수 있고, 같은 노드와 커널을 공유한다.

### 네임스페이스에 속하지 않는 리소스에는 무엇이 있나요?

Node, PersistentVolume, StorageClass, ClusterRole과 ClusterRoleBinding, CRD, 웹훅 설정, IngressClass, PriorityClass, Namespace 자신이 클러스터 단위다. `kubectl api-resources --namespaced=false`로 확인한다. 네임스페이스 관리자 권한만으로는 이것들을 만들 수 없어서, CRD를 설치하는 차트는 클러스터 권한이 필요하다.

### 다른 네임스페이스의 Service는 어떻게 호출하나요?

`서비스.네임스페이스`나 전체 이름 `서비스.네임스페이스.svc.cluster.local`로 부른다. Pod의 resolv.conf search 목록에 자기 네임스페이스가 먼저 들어가 있어서 짧은 이름 `api`는 같은 네임스페이스의 Service로 풀린다. 네임스페이스는 DNS 조회도 연결도 막지 않으니, 막으려면 NetworkPolicy를 쓴다.

### NetworkPolicy를 만들었는데 트래픽이 막히지 않습니다. 왜 그럴까요?

먼저 CNI가 NetworkPolicy를 지원하는지 본다. flannel처럼 지원하지 않는 CNI에서는 객체만 만들어지고 아무 효과가 없으며 에러도 나지 않는다. 지원한다면 podSelector와 namespaceSelector가 의도한 Pod를 고르는지, policyTypes에 방향이 들어갔는지 확인한다.

### 네임스페이스가 Terminating에서 끝나지 않습니다. 어떻게 보나요?

`kubectl get ns X -o yaml`의 status.conditions를 본다. NamespaceFinalizersRemaining이면 finalizer가 남은 객체가 있으니 그 주인 컨트롤러를 살려 정리하게 하거나, 정리할 외부 자원이 없는 걸 확인한 뒤 그 객체의 finalizer를 뗀다. NamespaceDeletionDiscoveryFailure면 응답하지 않는 APIService가 있으니 `kubectl get apiservice`에서 False인 것을 고치거나 지운다. 네임스페이스의 finalize를 강제로 비우면 객체가 etcd에 남으니 피한다.

### 개발과 운영을 같은 클러스터의 다른 네임스페이스로 나눠도 되나요?

작은 규모에서는 된다. 다만 노드, CRD, 웹훅, 클러스터 버전과 컨트롤 플레인을 공유하므로 개발에서 한 실수가 운영에 번질 수 있다. 그래서 운영은 별도 클러스터로 두고, 개발과 스테이징은 네임스페이스로 나누는 경우가 많다. 서로 믿지 못하는 테넌트라면 네임스페이스만으로는 부족하고 노드나 클러스터를 나눈다.

### Pod Security를 restricted로 바꿨는데 서비스가 멀쩡합니다. 끝난 건가요?

아니다. enforce 라벨은 이미 떠 있는 Pod를 죽이지 않고 새로 만드는 Pod만 거절한다. 다음 배포나 노드 교체 때 새 Pod가 만들어지지 못해 ReplicaSet 이벤트에 FailedCreate만 쌓인다. 그래서 warn과 audit로 먼저 걸어 위반을 고친 뒤 enforce로 올리고, `--dry-run=server`로 미리 확인한다.
