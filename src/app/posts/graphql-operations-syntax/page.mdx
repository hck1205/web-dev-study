검색 화면에서 "15인치 노트북"은 잘 나오는데 `15" 노트북`을 치면 아무것도 안 나온다. 응답을 보니 검색 결과 대신 문법 에러가 와 있다. 클라이언트 코드는 이랬다.

```js
// 사용자 입력을 쿼리 문자열에 그대로 이어 붙였다
const query = `{ search(text: "${input}") { name } }`;
```

```text
{"errors":[{"message":"Syntax Error: Unexpected character: U+B178.","locations":[{"line":1,"column":21}]}]}
```

입력의 큰따옴표가 GraphQL 문자열을 닫아 버렸고, 그 뒤의 "노"(U+B178)는 문법에 맞지 않는 글자가 됐다. 따옴표가 하나라서 에러로 끝났을 뿐이다. 입력이 이렇다면 이야기가 달라진다.

```text
input: a") { name } users { email } x: search(text: "b

{"data":{"search":[...],"users":[{"email":"admin@ex.com"}],"x":[...]}}
```

검색어 하나로 쿼리 구조가 바뀌어 `users` 필드가 끼어들었다. SQL 인젝션과 같은 모양이다. 서버가 필드마다 권한을 검사한다면 이 필드는 막히겠지만, 그 검사가 하나라도 빠져 있으면 그대로 새어 나간다.

이 글은 이런 실수를 막는 변수에서 시작해, GraphQL 쿼리 문서에 쓰는 문법(인자, 변수, 별칭, 프래그먼트, 디렉티브, 작업 이름)을 실제 요청으로 하나씩 확인한다. 데모는 Node.js 22와 graphql-js 16.14로 돌렸다. 타입 쪽 이야기는 [GraphQL 스키마 설계](/posts/graphql-schema-type-system)에, 요청이 HTTP로 어떻게 실리는지는 [GraphQL 기초](/posts/graphql-basics)의 "요청 한 번을 뜯어보면"에 있다.

## 값은 변수로 떼어 보낸다

쿼리 문서에는 구조만 쓰고 바뀌는 값은 변수로 보낸다. 작업 이름 옆에 변수와 타입을 선언하고, 필드 인자 자리에 `$이름`을 쓴다.

```graphql
query Search($text: String!, $first: Int = 1) {
  search(text: $text, first: $first) { name }
}
```

```json
{ "query": "query Search($text: String!, $first: Int = 1) { ... }", "variables": { "text": "15\" 노트북" } }
```

```text
  search text="15\" 노트북" first=1
{"data":{"search":[{"name":"연필"}]}}
```

따옴표가 섞인 입력이 리졸버에 그대로 도착했다. 변수 값은 JSON으로 따로 오니 쿼리 문법과 섞일 일이 없다. 문서가 항상 같은 문자열이라는 점도 크다. 서버는 파싱과 검증 결과를 문서 단위로 캐시할 수 있고, persisted query처럼 문서를 해시로 바꿔 보내는 방식도 이게 전제다.

변수는 선언한 타입으로 실행 전에 검사된다. 선언에 `!`가 있는데 값을 안 보내면 거절되고, 선언 타입이 쓰이는 자리의 타입보다 느슨해도 거절된다.

```text
query Search($text: String!) { ... }   variables: {}
Variable "$text" of required type "String!" was not provided.

query Search($text: String) { search(text: $text) { name } }
Variable "$text" of type "String" used in position expecting type "String!".
```

둘째 에러는 값이 들어 있어도 난다. 검증은 값이 아니라 문서를 보기 때문이다. `search(text:)`가 `String!`을 요구하니, 그 자리에 오는 변수도 null이 될 수 없다고 선언해야 한다. 예외가 하나 있다. 인자 자체에 기본값이 있거나 변수에 기본값이 있으면 nullable 변수를 non-null 자리에 쓸 수 있다.

기본값은 변수를 아예 안 보냈을 때만 쓰인다. `"first": null`을 명시적으로 보내면 기본값 1이 아니라 null이 들어간다. "안 보냄"과 "null을 보냄"을 구분하는 규칙인데, 수정 뮤테이션에서 "이 필드는 건드리지 마"와 "이 필드를 지워"를 나누는 데 쓰인다.

변수로 바꿀 수 없는 것도 있다. 필드 이름, 타입 이름, 프래그먼트 이름은 변수가 될 수 없다. 변수는 값 자리에만 온다. "사용자가 고른 필드만 받기"를 하고 싶다면 문자열을 조립하지 말고 `@include` 디렉티브로 필드마다 켜고 끈다. 뒤에서 본다.

## 인자는 어느 필드에나 붙는다

REST에서 쿼리 스트링은 URL 하나에 한 벌이다. GraphQL에서는 필드마다 인자를 받을 수 있어서, 깊은 곳의 목록도 각자 다른 조건으로 자른다.

```graphql
query ProductPage($id: ID!) {
  product(id: $id) {
    name
    reviews(first: 3, orderBy: HELPFUL) { body }
    seller {
      name
      products(first: 5, excludeId: $id) { name }
    }
  }
}
```

`reviews`의 `first: 3`과 `seller.products`의 `first: 5`는 서로 상관없다. 같은 변수 `$id`를 두 군데에 쓸 수도 있다. 인자 값으로는 리터럴(`3`, `HELPFUL`, `"문자열"`, `[1, 2]`, `{ name: "펜" }`)이나 변수를 쓰고, 입력 객체 안의 필드 하나만 변수로 둘 수도 있다(`input: { name: $name, price: 1000 }`).

인자 이름은 순서와 상관없고, 스키마에 없는 인자를 넘기면 검증에서 막힌다. 열거형 값은 따옴표 없이 쓴다는 것, 목록 자리에 값 하나를 주면 원소 하나짜리 목록이 된다는 것 같은 값 해석 규칙은 [GraphQL 스키마 설계](/posts/graphql-schema-type-system)의 스칼라 부분에 있다.

## 같은 필드를 두 번 받을 때는 별칭을 붙인다

상품 비교 화면에서 두 상품을 한 번에 받고 싶다. `product`를 두 번 쓰면 이렇게 된다.

```graphql
{ product(id: 1) { name } product(id: 2) { name } }
```

```text
Fields "product" conflict because they have differing arguments. Use different aliases on the fields to fetch both if this was intentional.
```

응답 JSON의 키는 필드 이름이라 `product` 키 하나에 두 결과를 담을 수 없다. 별칭(alias)을 붙이면 응답 키가 바뀐다.

```graphql
{ cheap: product(id: 3) { name price } premium: product(id: 2) { name price } }
```

```text
{"data":{"cheap":{"name":"지우개","price":300},"premium":{"name":"공책","price":2000}}}
```

반대로 같은 필드를 같은 인자로 두 번 쓰면 에러가 아니라 합쳐진다.

```graphql
{ product(id: 1) { name } product(id: 1) { price } }
```

```text
{"data":{"product":{"name":"연필","price":500}}}
```

이 합치기 규칙(명세의 field merging)이 실무에서 가장 자주 부딪히는 검증 에러를 만든다. 컴포넌트 둘이 각자 프래그먼트로 `avatar(size: 40)`과 `avatar(size: 80)`을 고르고, 그 둘이 한 쿼리에 모이면 위의 conflict 에러가 난다. 각자 보기에는 문제없는 프래그먼트가 합쳐지는 순간 깨지는 것이다. 이럴 때는 한쪽에 `largeAvatar: avatar(size: 80)`처럼 별칭을 붙인다.

별칭은 응답 키를 화면 코드에 맞추는 데도 쓴다. 서버 필드는 `displayName`인데 컴포넌트 props가 `title`이라면 `title: displayName`으로 받는다. 다만 별칭은 서버 입장에서 같은 리졸버를 여러 번 부르는 방법이기도 하다. `a1: product(id: 1) … a500: product(id: 500)`처럼 별칭 수백 개를 붙인 쿼리는 깊이가 1이라 깊이 제한을 그냥 지나간다. 비용 계산에 별칭 수를 넣어야 하는 이유다([GraphQL 기초](/posts/graphql-basics)의 깊이·비용 제한).

## 프래그먼트로 선택을 나눠 갖는다

상품 카드가 목록, 검색 결과, 장바구니 세 화면에 나온다. 카드에 필요한 필드를 세 쿼리에 각각 적으면, 카드에 필드 하나를 더할 때 세 곳을 다 고쳐야 한다. 이름 있는 프래그먼트로 한 번만 쓴다.

```graphql
query Compare {
  a: product(id: 1) { ...ProductCard }
  b: product(id: 3) { ...ProductCard }
}

fragment ProductCard on Product {
  id
  name
  price
  seller { name }
}
```

```text
{"data":{"a":{"id":"1","name":"연필","price":500,"seller":{"name":"문구점"}},"b":{"id":"3","name":"지우개","price":300,"seller":{"name":"다이소"}}}}
```

`on Product`는 타입 조건이다. 이 프래그먼트는 `Product` 타입 자리에서만 펼칠 수 있다. 서버는 프래그먼트를 그 자리에 펼친 것과 똑같이 실행한다. 프래그먼트는 문서를 정리하는 도구일 뿐 성능에는 영향이 없다.

검증 규칙이 프래그먼트를 깐깐하게 본다. 쓰지 않는 프래그먼트가 문서에 있으면 거절되고, 자기 자신을 펼치는 고리도 거절된다. 고리를 허용하면 펼치는 일이 끝나지 않기 때문이다.

```text
{ product(id: 1) { name } } fragment Card on Product { id }
Fragment "Card" is never used.

{ product(id: 1) { ...A } } fragment A on Product { seller { name } ...A }
Cannot spread fragment "A" within itself.
```

첫째 규칙 때문에 클라이언트에서 프래그먼트 문자열을 공용 파일 하나에 모아 두고 모든 쿼리에 붙이는 방식은 곧 막힌다. 쓰는 쿼리에만 붙여야 한다.

인라인 프래그먼트는 이름 없이 그 자리에서 쓰는 프래그먼트다. 두 가지 용도가 있다. 하나는 인터페이스나 유니언 자리에서 타입마다 필드를 고르는 것이다(`... on Product { price }`). 다른 하나는 타입 조건 없이 여러 필드에 디렉티브를 한 번에 거는 것이다.

```graphql
query Product($id: ID!, $admin: Boolean!) {
  product(id: $id) {
    name
    ... @include(if: $admin) { costPrice stockCount supplier { name } }
  }
}
```

프래그먼트가 펼쳐지고 같은 필드가 합쳐지는 과정을 그림으로 보자. 실행기는 선택 집합을 위에서부터 훑으며 응답 키 목록을 만든다.

### 컴포넌트마다 프래그먼트를 붙여 두는 방식

React 앱에서 프래그먼트가 진짜 쓸모를 보이는 곳은 프래그먼트 colocation이다. 컴포넌트 파일 옆에 그 컴포넌트가 쓰는 필드를 프래그먼트로 적고, 페이지 쿼리는 자식 컴포넌트의 프래그먼트를 펼치기만 한다.

```tsx
// product-card.tsx: 이 컴포넌트가 쓰는 필드는 여기에만 적는다
export const ProductCardFragment = graphql(`
  fragment ProductCard on Product { id name price seller { name } }
`);

// product-list-page.tsx: 페이지는 자식이 무엇을 쓰는지 모른다
const ProductListQuery = graphql(`
  query ProductList { products(first: 20) { ...ProductCard } }
`);
```

카드에 `rating`을 더하면 카드 파일만 고치면 된다. 페이지 쿼리는 그대로다. Relay는 여기서 더 나아가 컴포넌트가 자기 프래그먼트에 적힌 필드만 읽게 막는다(data masking). Apollo Client와 GraphQL Code Generator의 client preset도 비슷한 방식을 지원한다. 정확히 어디까지 막아 주는지는 도구와 버전마다 다르니 쓰는 도구의 문서를 확인한다. 이렇게 하면 부모가 자식 데이터에 몰래 기대는 일이 없어져, 필드를 지워도 어디가 깨질지 프래그먼트만 보면 안다.

## 디렉티브로 실행을 바꾼다

디렉티브는 `@이름(인자)`로 문서나 스키마의 어떤 위치에 붙어 동작을 바꾸는 표시다. graphql-js 16.14에 기본으로 들어 있는 것은 `@include`, `@skip`, `@deprecated`, `@specifiedBy`, 그리고 입력 객체의 필드 중 정확히 하나만 받게 하는 `@oneOf`다. 앞의 넷을 먼저 본다. 느린 필드를 나중에 보내는 `@defer`·`@stream`은 아직 명세 초안이라 [GraphQL 실시간](/posts/graphql-subscriptions-defer)에서 따로 다룬다.

`@include(if:)`와 `@skip(if:)`는 쿼리에 붙는다. 조건이 맞지 않으면 그 필드는 실행도 안 되고 응답에 키도 없다. null로 오는 것이 아니라 키가 아예 빠진다는 점을 화면 코드에서 챙긴다.

```graphql
query($withSeller: Boolean!) {
  product(id: 1) { name seller @include(if: $withSeller) { name } price @skip(if: $withSeller) }
}
```

```text
withSeller=false  {"data":{"product":{"name":"연필","price":500}}}
withSeller=true   {"data":{"product":{"name":"연필","seller":{"name":"문구점"}}}}
```

같은 문서 하나로 두 가지 모양을 받았다. 문서가 바뀌지 않으니 persisted query로 등록한 문서 하나가 여러 화면 상태를 처리한다. 문자열 조립을 피해야 하는 이유가 하나 더 생긴 셈이다.

`@deprecated(reason:)`은 스키마에 붙는다. 필드를 지우기 전에 "곧 없어진다"고 알리는 표시다. 붙여도 그 필드는 그대로 동작하고, introspection으로 표시가 보인다. 2021년판 명세부터는 인자와 입력 필드에도 붙일 수 있다.

```text
{ product(id: 1) { oldPrice } }
{"data":{"product":{"oldPrice":null}}}

{ __type(name: "Product") { fields(includeDeprecated: true) { name isDeprecated deprecationReason } } }
... {"name":"oldPrice","isDeprecated":true,"deprecationReason":"price를 쓴다"} ...
```

IDE와 코드 생성기가 이 표시를 읽어 취소선을 긋거나 경고를 띄운다. `@specifiedBy(url:)`은 커스텀 스칼라의 형식 명세를 가리키는 표시로, [GraphQL 스키마 설계](/posts/graphql-schema-type-system)에서 다뤘다.

### 직접 만드는 디렉티브

디렉티브는 직접 만들 수 있다. 붙는 위치에 따라 두 종류다. 쿼리 문서에 붙는 실행 디렉티브(`on FIELD`, `on FRAGMENT_SPREAD` 등)와 스키마에 붙는 타입 시스템 디렉티브(`on FIELD_DEFINITION`, `on OBJECT` 등)다. 가격을 원화 표기로 바꿔 주는 실행 디렉티브를 만들어 봤다.

```graphql
directive @won(withUnit: Boolean = true) on FIELD
```

```js
// 리졸버가 자기 필드에 붙은 디렉티브를 읽는다
label: (args, ctx, info) => {
  const d = getDirectiveValues(schema.getDirective("won"), info.fieldNodes[0]);
  if (!d) return "1500";
  return d.withUnit ? "1,500원" : "1,500";
},
```

```text
{ product { plain: label withUnit: label @won noUnit: label @won(withUnit: false) } }
{"data":{"product":{"plain":"1500","withUnit":"1,500원","noUnit":"1,500"}}}
```

세 필드에 별칭을 붙인 이유는 앞에서 본 합치기 규칙 때문이다. 별칭 없이 `label`을 디렉티브만 다르게 세 번 쓰면, graphql-js 16은 이걸 한 필드로 합친다(디렉티브는 충돌 검사 대상이 아니다). 그러면 `info.fieldNodes`에 노드가 셋 들어오는데 위 코드는 첫 노드만 보니 결과가 꼬인다.

graphql-js는 스키마에 선언한 디렉티브를 검증만 할 뿐 실행에 반영하지 않는다. 동작은 리졸버나 스키마 변환 코드가 직접 구현해야 한다. 선언하지 않은 디렉티브를 쓰면 검증에서 막힌다.

```text
{ product(id: 1) @cached { name } }
Unknown directive "@cached".
```

실무에서는 실행 디렉티브보다 스키마 디렉티브를 훨씬 많이 쓴다. `@auth(requires: ADMIN)`으로 권한 검사를, `@cacheControl(maxAge: 60)`으로 캐시 힌트를 다는 식이다(Apollo Server의 cacheControl처럼 서버 라이브러리가 해석한다). 표시가 스키마에 남아 리뷰할 때 보이는 것이 장점이다. 반면 표시만 있고 그걸 해석하는 코드가 빠지면 권한 검사가 조용히 사라진다. 권한처럼 빠지면 안 되는 것은 디렉티브가 붙은 필드를 테스트에서 따로 확인한다.

## 문서에 작업이 여럿일 때

문서 하나에 작업(operation)을 여러 개 넣을 수 있다. 개발 도구에서 쿼리를 모아 둘 때 흔하다. 그러면 어떤 작업을 실행할지 `operationName`으로 골라야 한다.

```text
query A { product(id: 1) { name } } query B { product(id: 2) { name } }
(operationName 없음)  Must provide operation name if query contains multiple operations.
(operationName "B")   {"data":{"product":{"name":"공책"}}}

{ product(id: 1) { name } } query B { product(id: 2) { name } }
This anonymous operation must be the only defined operation.
```

이름 없는 작업(중괄호로 바로 시작하는 쿼리)은 문서에 그것 하나뿐일 때만 허용된다.

작업이 하나뿐이어도 이름을 붙이는 편이 낫다. GraphQL은 URL이 모두 `/graphql`이라 접근 로그, APM, 에러 추적 도구에서 요청을 나눌 기준이 작업 이름밖에 없다. 이름 없는 쿼리가 많으면 "어떤 화면이 느린가"에 답할 수 없다. 이름은 `ProductPage`, `AddToCart`처럼 화면이나 동작을 드러내고 서비스 안에서 겹치지 않게 짓는다. 클라이언트 린트 규칙(예: graphql-eslint의 이름 강제 규칙)으로 이름 없는 작업을 막아 두면 이 문제가 처음부터 생기지 않는다.

## 뮤테이션의 필드는 적힌 순서대로 하나씩 돈다

쿼리와 뮤테이션은 문법이 거의 같지만 최상위 필드를 실행하는 방식이 다르다. 각 필드가 20ms, 50ms 걸리는 쿼리를 돌리면 이렇다.

```text
{ a: slow(ms: 50) b: slow(ms: 20) }
  +  6ms start slow 50
  +  9ms start slow 20
  + 29ms end slow 20
  + 59ms end slow 50
```

`b`가 `a`를 기다리지 않고 시작해 먼저 끝났다. 쿼리 필드는 읽기만 하니 순서가 상관없어서, 명세는 병렬로 실행해도 된다고 정한다. 뮤테이션은 다르다.

```text
mutation { first: addToCart(productId: 1) second: addToCart(productId: 2) clear: clearCart }
  start add 1
  end add 1 cart= 1
  start add 2
  end add 2 cart= 2
  start clear
  end clear
{"data":{"first":1,"second":2,"clear":0}}
```

`addToCart`의 Promise가 끝난 뒤에야 다음 필드가 시작한다. 쓰기 순서가 섞이면 결과가 실행할 때마다 달라질 수 있으니, 최상위 뮤테이션 필드는 순서대로 하나씩 실행한다. 이 규칙은 최상위에만 적용된다. 각 뮤테이션이 돌려준 객체 아래의 선택 집합은 쿼리처럼 평소대로 실행된다.

순서대로 돈다고 트랜잭션은 아니다. 중간 필드가 실패하면 앞 필드의 쓰기는 이미 끝나 있다. 그리고 실패 이후가 어떻게 되는지는 반환 타입의 느낌표에 달렸다. 세 번 담기 중 두 번째가 실패하도록 해 봤다.

```text
add: Int!   (non-null)
  start add 1 / end add 1 / start add -1
{"errors":[{"message":"음수는 담을 수 없다","path":["b"]}],"data":null}

add: Int    (nullable)
  start add 1 / end add 1 / start add -1 / start add 2 / end add 2
{"errors":[{"message":"음수는 담을 수 없다","path":["b"]}],"data":{"a":1,"b":null,"c":3}}
```

반환 타입이 non-null이면 `b`의 null이 `data`까지 올라가고, 그 뒤의 `c`는 실행조차 되지 않았다. 그런데 `a`는 이미 장바구니에 담겼다. 응답은 `data: null`이라 클라이언트는 아무것도 안 된 줄 알지만 서버 상태는 바뀌어 있다. nullable이면 `c`까지 실행되고 각 결과가 따로 온다. 아래 그림에서 두 경우를 단계별로 따라가 보자.

## 쿼리 문서를 코드에서 다루는 법

여기까지의 문법을 알고 나면 클라이언트 코드에서 지킬 것이 몇 가지 나온다.

쿼리 문서는 정적인 문자열로 둔다. 템플릿 리터럴 안에 `${}`로 값을 끼우지 않는다. 값은 변수로, 필드의 유무는 `@include`로, 반복되는 선택은 프래그먼트로 처리하면 문서를 조립할 일이 거의 없다. 문서가 정적이면 빌드할 때 모든 문서를 뽑아 서버 허용 목록(trusted documents)에 올릴 수 있고, 코드 생성기가 문서마다 결과 타입을 만든다.

코드 생성은 이 글의 문법을 그대로 따라간다. 별칭을 붙이면 결과 타입의 키도 별칭이 되고, `@include`가 붙은 필드는 선택적 속성(`seller?:`)이 된다. 디렉티브로 빠진 키는 null이 아니라 없는 키라는 차이가 타입에도 드러난다.

"Fields conflict" 에러가 나면 문서 하나가 아니라 합쳐진 결과를 본다. 같은 객체 아래에서 서로 다른 프래그먼트가 같은 응답 키를 다른 인자나 다른 타입으로 고르고 있다. 에러의 `locations`가 두 군데를 가리키니, 그 두 곳 중 한쪽에 별칭을 붙인다.

운영 로그에서는 작업 이름과 변수를 함께 남기되 변수는 조심한다. 변수에는 비밀번호, 토큰, 개인 정보가 들어갈 수 있다. 작업 이름과 문서 해시는 남기고 변수는 남기지 않거나 민감한 키를 가린다.

## 구조는 문서에, 값은 변수에

GraphQL 쿼리 문서는 받을 모양을 적는 구조이고, 바뀌는 값은 변수로 떼어 보낸다. 같은 필드를 다른 인자로 두 번 받으려면 별칭으로 응답 키를 나누고, 반복되는 선택은 프래그먼트로 묶어 컴포넌트 옆에 둔다. 디렉티브는 같은 문서로 여러 모양을 받게 해 주고, 작업 이름은 엔드포인트가 하나인 GraphQL에서 운영의 기준이 된다. 그리고 뮤테이션의 최상위 필드는 순서대로 하나씩 실행되지만 트랜잭션은 아니고, non-null 반환 타입에서 실패하면 뒤의 필드는 실행되지 않는다. 실행기가 이 문서를 받아 어떤 단계를 거쳐 응답을 만드는지는 [GraphQL 실행 엔진 안쪽](/posts/graphql-execution-validation)에서 이어진다.

## 면접에서 나올 만한 질문

### GraphQL에서 변수를 써야 하는 이유는 무엇인가요?

사용자 입력을 쿼리 문자열에 이어 붙이면 따옴표 하나로 문법이 깨지고, 악의적인 입력이 다른 필드를 끼워 넣어 쿼리 구조를 바꿀 수 있다. 변수는 값을 JSON으로 따로 보내므로 구조와 값이 섞이지 않고, 선언한 타입으로 실행 전에 검사된다. 문서가 항상 같은 문자열이라 서버가 파싱·검증 결과를 캐시하고, persisted query나 허용 목록으로 등록하기도 쉽다. 필드 이름처럼 구조에 해당하는 것은 변수로 바꿀 수 없고 `@include` 같은 디렉티브로 처리한다.

### 변수에 기본값이 있을 때 null을 보내면 어떻게 되나요?

기본값은 변수를 아예 보내지 않았을 때만 쓰이고, null을 명시적으로 보내면 null이 들어간다. 이 구분 덕분에 수정 뮤테이션에서 "건드리지 않음"과 "null로 지우기"를 나눌 수 있다. 또 nullable 변수를 non-null 인자 자리에 쓰면 원래는 검증 에러지만, 변수나 인자에 기본값이 있으면 허용된다.

### 별칭은 언제 쓰나요?

같은 필드를 다른 인자로 두 번 이상 받을 때 쓴다. 응답 키가 필드 이름이라 별칭 없이 `product(id: 1)`과 `product(id: 2)`를 함께 쓰면 conflict 에러가 난다. 응답 키를 화면 코드의 이름에 맞출 때도 쓴다. 반대로 별칭은 같은 리졸버를 수백 번 부르는 수단이 될 수 있어서, 서버의 비용 계산에 별칭 수를 넣어야 한다.

### 프래그먼트는 왜 쓰고, 성능에 영향이 있나요?

여러 쿼리나 여러 위치에서 같은 선택 집합을 반복하지 않으려고 쓴다. 서버는 프래그먼트를 그 자리에 펼친 것과 똑같이 실행하므로 성능에는 영향이 없다. React 앱에서는 컴포넌트 옆에 그 컴포넌트가 쓰는 필드를 프래그먼트로 두고 페이지 쿼리가 펼치게 하는 colocation이 핵심 용도다. 쓰지 않는 프래그먼트와 자기 자신을 펼치는 고리는 검증에서 거절된다.

### 인라인 프래그먼트는 언제 쓰나요?

인터페이스나 유니언 자리에서 실제 타입마다 다른 필드를 고를 때 `... on Product { price }`처럼 쓴다. 타입 조건 없이 여러 필드에 `@include`나 `@skip`을 한 번에 걸 때도 쓴다. 유니언에서는 공통 필드를 약속하지 않으니 인라인 프래그먼트 없이 필드를 고를 수 없다.

### `@include`로 빠진 필드는 응답에서 어떻게 보이나요?

null이 아니라 키 자체가 응답에 없다. 리졸버도 실행되지 않는다. 그래서 화면 코드는 그 키가 없을 수 있다고 가정해야 하고, 코드 생성기도 이 필드를 선택적 속성으로 만든다. 같은 문서 하나로 여러 모양을 받을 수 있어서 문서를 조립하지 않아도 된다.

### 커스텀 디렉티브는 어떻게 동작하나요?

스키마에 `directive @이름 on 위치`로 선언하면 검증기가 쓸 수 있는 위치와 인자를 검사하지만, graphql-js 같은 실행기는 그 의미를 모른다. 동작은 리졸버가 `info`에서 디렉티브를 읽거나, 스키마를 변환하는 코드가 디렉티브가 붙은 필드의 리졸버를 감싸서 구현한다. 실무에서는 `@auth`, `@cacheControl` 같은 스키마 디렉티브를 많이 쓰는데, 해석하는 코드가 빠지면 표시만 남고 동작이 사라지니 테스트로 확인해야 한다.

### 뮤테이션 하나에 필드를 여러 개 넣으면 어떻게 실행되나요?

최상위 뮤테이션 필드는 적힌 순서대로 하나씩, 앞 필드가 끝난 뒤에 실행된다. 쿼리 필드는 병렬로 실행될 수 있는 것과 다르다. 하지만 트랜잭션은 아니어서 중간 필드가 실패해도 앞의 쓰기는 남는다. 반환 타입이 non-null이면 실패한 null이 data까지 올라가 뒤 필드는 실행되지 않으니, 함께 성공해야 하는 쓰기는 뮤테이션 하나로 만들고 그 안에서 트랜잭션을 연다.
