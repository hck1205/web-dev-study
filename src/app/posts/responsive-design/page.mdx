## 휴대폰에서 옆으로 밀리는 페이지

데스크톱에서 다 만든 페이지를 휴대폰으로 연다. 세로로 스크롤하는데 엄지가 조금만 비껴가도 화면 전체가 오른쪽으로 20px쯤 미끄러진다. 오른쪽 끝에 하얀 띠가 보이고, 헤더는 그 띠만큼 짧아 보인다. 페이지 어딘가에 화면 폭보다 넓은 요소가 하나 있다는 뜻이다.

반응형 디자인은 이런 일을 막는 기술의 묶음이다. 한 벌의 HTML과 CSS가 360px 휴대폰부터 2560px 모니터까지 읽기 좋게 모양을 바꾸게 만든다. 미디어 쿼리 몇 줄이 전부처럼 보이지만, 실제로는 브라우저가 화면 폭을 어떻게 정하는지, 픽셀이 무엇을 뜻하는지, 휴대폰의 주소창과 노치가 공간을 어떻게 빼앗는지까지 알아야 버그를 잡을 수 있다.

이 글은 그 순서대로 간다. 레이아웃 도구(flex, grid)와 박스 크기 계산은 따로 다룰 주제라 여기서는 반응형에 필요한 만큼만 언급한다. 반응형 이미지는 [이미지 최적화](/posts/image-optimization)에 자세히 있다.

## 뷰포트 메타 태그가 없으면 980px로 그린다

스마트폰이 처음 나왔을 때 웹은 데스크톱 폭에 맞춰 만들어져 있었다. 320px 화면에 그대로 그리면 다 깨진다. 그래서 iOS 사파리는 꾀를 냈다. 페이지를 980px 폭인 척하는 가상의 화면에 그린 다음, 그걸 통째로 축소해 휴대폰 화면에 맞춘다. 안드로이드 크롬도 같은 방식을 따랐다. 메타 태그가 없는 페이지가 휴대폰에서 개미 글씨로 보이는 이유다.

이때 뷰포트가 두 개라는 점을 알아 두면 이후 버그가 덜 헷갈린다. 레이아웃 뷰포트(layout viewport)는 CSS가 폭을 계산하는 기준 상자다. `width: 100%`나 미디어 쿼리의 `width`가 이걸 본다. 비주얼 뷰포트(visual viewport)는 지금 실제로 눈에 보이는 영역이다. 사용자가 핀치 줌을 하면 비주얼 뷰포트만 작아지고 레이아웃 뷰포트는 그대로다.

```html
<!-- 반응형 페이지라면 head에 반드시 넣는다 -->
<meta name="viewport" content="width=device-width, initial-scale=1" />
```

`width=device-width`는 "레이아웃 뷰포트 폭을 이 기기의 CSS 픽셀 폭으로 맞춰라"는 뜻이다. iPhone 15라면 393px, 갤럭시 S23이면 360px가 된다. 그제야 `min-width: 768px` 같은 쿼리가 휴대폰에서 꺼진다. Next.js App Router는 이 태그를 기본으로 넣어 주고, `viewport` export로 바꿀 수 있다.

## CSS 픽셀과 기기 픽셀은 다르다

iPhone 15 화면의 실제 발광 소자는 가로 1179개다. 그런데 CSS에서는 393px로 보인다. 이 비율이 기기 픽셀 비율(DPR, device pixel ratio)이다. 1179 ÷ 393 = 3이다.

CSS 픽셀은 "팔 길이만큼 떨어져서 봤을 때 비슷한 크기로 보이는 단위"로 정해져 있다. 그래서 DPR이 3인 휴대폰에서 `width: 100px` 상자는 기기 픽셀 300개로 그려지고, 눈에는 DPR 1 모니터의 100px와 비슷한 크기로 보인다. 반응형 레이아웃은 CSS 픽셀만 생각하면 된다. 기기 픽셀이 문제가 되는 건 이미지(작은 이미지를 늘려 그리면 흐려진다)와 1px 선(DPR 3에서 0.33px 선을 그리고 싶을 때) 정도다.

```js
// 브라우저 콘솔에서 지금 기기의 값을 본다
window.devicePixelRatio;          // 휴대폰에서 2~3, 일반 모니터 1, 맥북 2
document.documentElement.clientWidth; // 레이아웃 뷰포트 폭(스크롤바 제외), CSS 픽셀
window.innerWidth;                // 스크롤바를 포함한 폭
window.visualViewport.width;      // 핀치 줌을 반영한 실제 보이는 폭
```

데스크톱 브라우저에서 Ctrl + 를 눌러 200%로 확대하면 `devicePixelRatio`가 두 배가 되고 CSS 픽셀 폭은 절반이 된다. 1280px 창이 640px처럼 동작하니 태블릿 레이아웃이 켜진다. 반응형으로 잘 만든 페이지는 확대에도 강하다는 말이 여기서 나온다. 고정 폭으로 만든 페이지는 확대하면 가로 스크롤이 생긴다.

## 단위마다 기준이 다르다

반응형 버그의 꽤 많은 부분은 단위가 무엇을 기준으로 계산되는지 헷갈려서 생긴다.

| 단위 | 기준 | 주로 쓰는 곳 |
|---|---|---|
| `px` | CSS 픽셀 | 테두리, 그림자, 작은 고정값 |
| `%` | 부모의 같은 축 크기(속성마다 다르다) | 폭, 레이아웃 비율 |
| `em` | 그 요소의 `font-size` | 버튼 안쪽 여백처럼 글자 크기를 따라가야 할 때 |
| `rem` | 루트(`html`)의 `font-size` | 글자 크기, 간격 |
| `vw` · `vh` | 뷰포트 폭·높이의 1% | 전체 화면 섹션, 유동 타이포 |
| `dvh` · `svh` · `lvh` | 주소창 상태에 따라 달라지는 뷰포트 높이의 1% | 모바일 전체 화면 |
| `cqi` · `cqw` | 가장 가까운 컨테이너 폭의 1% | 컨테이너 쿼리 안의 크기 |

`%`는 속성마다 기준이 다르다는 점이 함정이다. `width: 50%`는 부모 폭의 절반이지만, `padding-top: 50%`도 부모의 높이가 아니라 폭을 기준으로 한다. `height: 50%`는 부모 높이가 정해져 있지 않으면 아무 효과가 없다.

글자 크기를 `rem`으로 쓰는 이유는 사용자 설정 때문이다. 브라우저 설정에서 기본 글꼴 크기를 20px로 바꾼 사람에게 `1rem`은 20px다. `16px`로 박아 두면 그 설정을 무시한다. `html { font-size: 62.5% }`로 1rem을 10px로 만드는 오래된 기법은 계산은 편하지만, 루트 글자 크기를 바꿔 둔 걸 잊고 라이브러리가 `rem`을 가정한 크기로 작게 그려지는 문제를 만든다. 요즘은 루트를 건드리지 않고 그냥 `1rem = 16px`로 생각하는 쪽이 많다.

`em`은 겹치면 곱해진다. 부모가 `1.2em`, 자식도 `1.2em`이면 자식 글자는 1.44배가 된다. 중첩 목록에서 글자가 점점 커지는 버그의 흔한 원인이다. 대신 버튼 패딩을 `0.5em 1em`으로 주면 버튼 글자 크기만 바꿔도 모양이 같은 비율로 커져서 크기 변형(size)을 만들기 좋다.

미디어 쿼리 안의 `em`과 `rem`은 조금 특별하다. 쿼리는 문서 스타일보다 먼저 판정되기 때문에 `html`의 `font-size`가 아니라 브라우저 기본 글꼴 크기(보통 16px)를 기준으로 한다. 그래서 `@media (min-width: 48em)`은 기본 설정에서 768px와 같지만, 기본 글꼴을 20px로 키운 사용자에게는 960px에서 켜진다. 글자를 키운 사람에게 더 넓은 화면이 되어야 넓은 레이아웃을 주는 셈이라 의도에 맞을 때가 많다. 이 블로그처럼 px로 쿼리를 쓰는 프로젝트도 흔하고, 어느 쪽이든 팀 안에서 하나로 맞추는 게 중요하다.

## 100vh가 휴대폰에서 넘치는 이유

첫 화면을 꽉 채우는 섹션을 `height: 100vh`로 만들었다. 데스크톱에서는 완벽하다. 휴대폰에서 열면 아래쪽 버튼이 하단 주소창 뒤에 가려져 있다. 스크롤을 조금 내리면 주소창이 접히면서 그제야 버튼이 보인다.

모바일 브라우저는 스크롤할 때 주소창과 툴바를 접었다 폈다 한다. 그 순간마다 뷰포트 높이가 바뀌는데, 이 값에 맞춰 `vh`를 계속 바꾸면 스크롤 중에 레이아웃이 들썩인다. 그래서 브라우저들은 `vh`를 주소창이 접힌 상태, 즉 가장 큰 높이로 고정하기로 했다. 주소창이 펴져 있을 때는 `100vh`가 실제 보이는 높이보다 크다.

이걸 풀려고 세 가지 단위가 생겼다. 크롬 108, 사파리 15.4, 파이어폭스 101부터 쓸 수 있다.

- `svh`(small): 주소창이 다 펴져 있을 때의 높이. 가장 작다. 언제나 다 보인다.
- `lvh`(large): 주소창이 다 접혔을 때의 높이. 지금의 `vh`와 같다.
- `dvh`(dynamic): 지금 상태에 맞춰 바뀐다. 스크롤하면 값이 따라 변한다.

```css
.hero {
  /* 지원하지 않는 브라우저를 위한 대비. 뒤의 선언이 이해되면 그걸 쓴다 */
  min-height: 100vh;
  /* 주소창이 펴진 상태에서도 아래 버튼이 가려지지 않는다 */
  min-height: 100svh;
}

.fullscreen-modal {
  /* 지금 보이는 높이에 딱 맞춘다. 스크롤이 없는 고정 요소라 들썩임이 없다 */
  height: 100dvh;
}
```

어떤 걸 고를지는 요소가 스크롤과 함께 움직이는지로 정한다. 스크롤되는 문서 안의 큰 섹션에 `dvh`를 쓰면 주소창이 접힐 때마다 섹션 높이가 바뀌고 그 아래 내용이 밀린다. 그래서 문서 흐름 안에서는 `svh`가 안전하다. 화면에 고정된 모달, 채팅 입력창처럼 스크롤과 무관하게 화면을 채워야 하는 것에는 `dvh`가 맞다.

키보드는 또 다르다. 입력칸을 눌러 가상 키보드가 올라오면 iOS 사파리는 레이아웃 뷰포트를 줄이지 않고 비주얼 뷰포트만 줄인다. `dvh`도 키보드를 반영하지 않는다. 채팅 앱에서 입력창을 키보드 바로 위에 붙이려면 `window.visualViewport`의 `resize` 이벤트로 높이를 읽어야 한다. 크롬 계열은 `<meta name="viewport" content="..., interactive-widget=resizes-content">`로 키보드가 레이아웃 뷰포트를 줄이게 바꿀 수 있지만, 사파리는 이 값을 지원하지 않는다.

## 모바일부터 쓰고 min-width로 넓힌다

미디어 쿼리를 쓰는 방향은 둘이다. 데스크톱을 기본으로 쓰고 `max-width`로 좁은 화면을 고치는 데스크톱 우선(desktop-first), 모바일을 기본으로 쓰고 `min-width`로 넓은 화면을 더하는 모바일 우선(mobile-first)이다.

```css
/* desktop-first: 넓은 화면을 기본으로 두고 좁아지면 되돌린다 */
.list { display: grid; grid-template-columns: repeat(3, 1fr); gap: 2rem; }
@media (max-width: 1023px) { .list { grid-template-columns: repeat(2, 1fr); } }
@media (max-width: 767px)  { .list { grid-template-columns: 1fr; gap: 1rem; } }

/* mobile-first: 한 줄을 기본으로 두고 넓어지면 칸을 더한다 */
.list { display: grid; gap: 1rem; }
@media (min-width: 768px)  { .list { grid-template-columns: repeat(2, 1fr); gap: 2rem; } }
@media (min-width: 1024px) { .list { grid-template-columns: repeat(3, 1fr); } }
```

결과 화면은 같지만 모바일 우선이 나은 이유가 몇 가지 있다. 모바일 화면은 대부분 한 줄로 쌓이는 단순한 배치라, 그걸 기본으로 두면 쿼리 안에는 "더하는" 규칙만 들어간다. 데스크톱 우선은 넓은 화면의 복잡한 배치를 좁은 화면에서 하나하나 "취소"해야 한다. 취소를 빠뜨린 속성이 휴대폰에서 버그로 남는다. 그리고 쿼리를 이해하지 못하는 아주 오래된 환경이나 쿼리 경계에 걸린 이상한 폭에서도 기본 스타일, 즉 한 줄 배치가 나온다. 깨져도 읽을 수는 있다.

두 방식을 섞으면 경계에서 사고가 난다. `max-width: 768px`와 `min-width: 768px`를 같이 쓰면 정확히 768px에서 둘 다 켜진다. 소수점 폭(확대 배율 때문에 767.5px가 될 수 있다)에서는 반대로 둘 다 꺼지는 틈이 생긴다. 미디어 쿼리 범위 문법(크롬 104, 사파리 16.4, 파이어폭스 63부터)을 쓰면 이 틈이 없어진다.

```css
/* 768px 이상, 1024px 미만. 경계가 겹치지도 비지도 않는다 */
@media (768px <= width < 1024px) { ... }
```

브레이크포인트 숫자는 기기 목록에서 고르기보다 내용이 깨지는 지점에서 고른다. 창을 천천히 넓혀 가면서 한 줄이 너무 길어지거나 카드가 너무 넓어 보이는 폭을 찾는다. 그래도 팀에서 숫자를 공유해야 하니 보통 768px(태블릿 세로)과 1024px(태블릿 가로·작은 노트북) 두세 개로 맞추고, 하드코딩하지 않게 상수로 모은다.

```ts
// breakpoints.ts: 쿼리 문자열을 한곳에서 만든다
export const media = {
  tablet: "@media (min-width: 768px)",
  desktop: "@media (min-width: 1024px)",
} as const;
```

미디어 쿼리는 폭 말고도 쓸모가 있다. `(hover: hover) and (pointer: fine)`은 마우스가 있는 환경에서만 호버 효과를 켠다. 터치 기기에서 호버 스타일이 탭한 뒤에 붙어 남는 문제를 막는다. `(prefers-reduced-motion: reduce)`, `(prefers-color-scheme: dark)`도 같은 문법이다.

## 화면 대신 자리를 보는 컨테이너 쿼리

상품 카드를 만들었다. 넓으면 사진을 왼쪽, 글을 오른쪽에 두고, 좁으면 위아래로 쌓는다. 미디어 쿼리로 `min-width: 768px`이면 가로 배치로 했다. 그런데 이 카드를 데스크톱 화면의 좁은 사이드바에 넣으니 사이드바 폭이 280px인데도 가로 배치가 켜져 글이 세로로 길게 찌그러진다. 화면이 넓은 건 맞지만 카드가 놓인 자리는 좁다.

미디어 쿼리는 뷰포트만 본다. 컴포넌트는 자기가 어디에 놓일지 모른다. 컨테이너 쿼리(container query)는 이 질문을 "화면이 얼마나 넓나"에서 "내가 놓인 상자가 얼마나 넓나"로 바꾼다. 크롬 105, 사파리 16, 파이어폭스 110부터 지원하고, 2023년부터 주요 브라우저 모두에서 쓸 수 있다.

```css
/* 1. 부모를 컨테이너로 선언한다. 폭(inline 방향)만 질문할 수 있게 한다 */
.card-slot {
  container-type: inline-size;
  container-name: card;
}

/* 2. 기본은 세로 배치 (모바일 우선과 같은 방향) */
.card { display: grid; gap: 0.75rem; }

/* 3. 카드가 놓인 상자가 420px 이상일 때만 가로 배치 */
@container card (min-width: 420px) {
  .card { grid-template-columns: 160px 1fr; }
  .card-title { font-size: clamp(1rem, 4cqi, 1.25rem); }
}
```

이제 같은 카드가 메인 영역에서는 가로로, 사이드바에서는 세로로 그려진다. 카드 코드는 바뀌지 않았다. 디자인 시스템 컴포넌트처럼 여러 곳에 들어가는 부품은 미디어 쿼리보다 컨테이너 쿼리로 만드는 쪽이 맞다. 미디어 쿼리는 페이지 전체 골격(사이드바를 보일지, 열을 몇 개로 할지)에 남긴다.

`cqi`는 컨테이너 inline 크기의 1%다. 위 예에서 카드 제목이 컨테이너 폭을 따라 커진다.

컨테이너 쿼리를 쓰다 처음 밟는 함정은 두 가지다.

하나는 요소가 자기 자신을 질문할 수 없다는 점이다. `.card`에 `container-type`을 주고 `.card`의 `grid-template-columns`를 바꾸려고 하면 동작하지 않는다. 쿼리는 가장 가까운 "조상" 컨테이너를 본다. 그래서 감싸는 요소가 하나 더 필요하다.

다른 하나는 컨테이너가 쪼그라드는 문제다. `container-type: inline-size`는 크기 격리(size containment)를 건다. 컨테이너의 폭이 자식 내용에 따라 정해지지 않는다는 약속이다. 그래야 "자식이 폭을 바꾸고, 그 폭으로 쿼리가 다시 바뀌는" 순환이 생기지 않는다. 그런데 폭이 내용으로 정해지는 자리, 예를 들어 `display: inline-block`이나 `width: fit-content`, 줄어드는 flex 아이템에 컨테이너를 두면 내용이 없는 것으로 계산되어 폭이 0이 된다. 화면에서 카드가 사라지면 컨테이너가 놓인 자리를 먼저 본다. `container-type: size`는 높이까지 격리해서, 높이를 따로 주지 않으면 높이가 0이 된다. 대부분은 `inline-size`로 충분하다.

크기 말고 CSS 변수 값을 묻는 스타일 쿼리(`@container style(--variant: compact)`)도 있다. 크롬 111, 사파리 18부터 되지만 모든 브라우저에서 되지는 않으니 지원 범위를 확인하고, 안 될 때도 기본 모양이 괜찮게 짠다.

## 글자 크기를 clamp로 부드럽게

제목 크기를 모바일 28px, 태블릿 36px, 데스크톱 48px로 정해 쿼리 두 개로 나눴다. 창을 넓혀 보면 767px에서 768px로 넘어가는 순간 제목이 툭 커진다. 그 사이 폭에서는 제목이 화면에 비해 너무 크거나 작다.

`clamp(최소, 선호, 최대)`는 선호값을 계산하되 최소와 최대 사이에 가둔다. 선호값에 `vw`를 섞으면 화면 폭을 따라 연속으로 커지는 글자를 쿼리 없이 만들 수 있다. 이걸 유동 타이포그래피(fluid typography)라고 한다.

390px에서 28px, 1280px에서 48px가 되게 하려면 두 점을 지나는 직선을 구하면 된다. 기울기는 (48 − 28) ÷ (1280 − 390) = 0.02247이다. 폭 1px당 글자가 0.02247px 커진다는 뜻이고, `vw`로 바꾸면 100을 곱해 2.2472vw다. y절편은 28 − 0.02247 × 390 = 19.235px, 즉 1.2022rem이다.

```css
h1 {
  /* 390px 이하에서 28px, 1280px 이상에서 48px, 그 사이는 직선으로 */
  font-size: clamp(1.75rem, 1.2022rem + 2.2472vw, 3rem);
}
```

820px 태블릿에서 계산해 보면 19.235 + 0.022472 × 820 = 37.66px다. 쿼리 경계에서 튀는 일 없이 폭에 비례해 자란다.

선호값에 `rem`을 꼭 섞는 이유가 있다. `font-size: 5vw`처럼 `vw`만 쓰면 사용자가 브라우저를 확대해도 글자가 커지지 않는다. 확대하면 CSS 픽셀 기준 뷰포트가 좁아지고, `vw` 값도 그만큼 줄어서 상쇄되기 때문이다. 200%까지 확대해 글자를 키울 수 있어야 한다는 WCAG 1.4.4를 어기게 된다. `rem` 부분은 확대와 사용자 글꼴 설정을 따라가니, 기울기를 너무 크게 잡지 않으면 확대가 살아 있다. 최대값을 `rem`으로 두는 것도 같은 이유다.

아래에서 직접 만들어 보자. 최소·최대 글자 크기(px)와 그 크기가 적용될 뷰포트 폭(px)을 받아 `clamp()` 문자열을 돌려준다. 숫자는 소수점 넷째 자리까지 반올림하고, 1rem은 16px로 본다.

<CodePlayground

  // 2. y절편: 폭이 0일 때의 글자 크기(px)
  // 3. clamp(최소rem, 절편rem + 기울기*100 vw, 최대rem) 문자열을 만든다

본문은 기울기를 작게(16→20px처럼), 큰 제목은 크게 잡는 게 보통이다. 본문 글자가 화면 폭에 따라 많이 변하면 한 줄 길이가 들쭉날쭉해져 오히려 읽기 불편하다. 글 폭은 `max-width: 65ch`처럼 글자 수 단위로 막아 한 줄을 대략 45~75자 사이에 두는 게 흔한 기준이다.

`clamp()`는 글자에만 쓰는 게 아니다. `padding: clamp(1rem, 4vw, 3rem)`처럼 여백에 쓰면 화면 가장자리 여백이 폭에 따라 자연스럽게 늘어난다. `width: min(100% - 2rem, 72rem)`은 "화면 폭에서 양쪽 1rem씩 뺀 값과 72rem 중 작은 것"이라 컨테이너 하나를 쿼리 없이 만든다.

## 이미지와 동영상이 상자를 넘지 않게

가로 스크롤 버그의 단골은 이미지다. `<img>`는 기본적으로 원본 크기로 그려지니, 1200px 사진은 390px 화면을 그대로 뚫고 나간다.

```css
img, video, svg, canvas {
  max-width: 100%;  /* 부모보다 넓어지지 않는다 */
  height: auto;     /* 폭이 줄면 비율에 맞춰 높이도 준다 */
}

.thumb {
  aspect-ratio: 4 / 3;  /* 이미지가 오기 전에도 자리를 잡는다 */
  object-fit: cover;    /* 비율이 다른 사진은 잘라서 채운다 */
  width: 100%;
}
```

크기만 줄이면 휴대폰이 데스크톱용 큰 파일을 받는 문제는 그대로다. 화면 폭과 DPR에 맞는 파일을 브라우저가 고르게 하는 `srcset`·`sizes`, 화면마다 다른 구도를 주는 `<picture>`, 자리를 미리 잡아 레이아웃이 밀리지 않게 하는 `width`·`height` 속성은 [이미지 최적화](/posts/image-optimization)에서 실제 측정과 함께 다뤘다.

`<iframe>`으로 넣은 동영상은 `max-width`만으로 높이가 따라오지 않는다. `width: 100%; aspect-ratio: 16 / 9;`를 함께 준다.

## 손가락이 누를 수 있는 크기

마우스 커서는 1px 점이지만 손가락 끝은 화면에서 대략 1cm 가까운 면적을 덮는다. 24px짜리 아이콘 버튼 두 개를 붙여 두면 엉뚱한 쪽이 눌린다.

기준은 몇 가지가 있다. WCAG 2.2의 2.5.8(AA)은 누를 수 있는 대상이 최소 24×24 CSS 픽셀이거나, 그보다 작으면 주변에 다른 대상과 겹치지 않는 24px 지름의 여유가 있어야 한다고 한다. 2.5.5(AAA)는 44×44px다. 애플 가이드라인은 44pt, 머티리얼 디자인은 48dp를 권한다. 실무에서는 44px를 바닥으로 잡는 팀이 많다. 이 블로그도 링크와 버튼을 44px 이상으로 맞춘다.

아이콘 자체를 키울 필요는 없다. 보이는 크기는 그대로 두고 누르는 면적만 넓힌다.

```css
.icon-button {
  /* 아이콘은 20px지만 누르는 상자는 44px */
  display: inline-grid;
  place-items: center;
  min-width: 44px;
  min-height: 44px;
}

/* 글 속 작은 링크는 높이를 늘리기 어렵다. 줄 간격과 여백으로 띄운다 */
.tag-list a {
  display: inline-flex;
  align-items: center;
  min-height: 44px;
  padding-inline: 0.5rem;
}
```

간격도 크기만큼 중요하다. 44px 버튼 두 개를 0px로 붙여 두면 경계 근처 탭이 반반으로 갈린다. 자주 쓰는 동작과 삭제처럼 되돌리기 어려운 동작은 떨어뜨려 둔다.

## 노치와 홈 바를 피해 가장자리 비우기

`viewport-fit=cover`를 넣으면 페이지가 화면의 둥근 모서리, 노치, 아래쪽 홈 바 밑까지 그려진다. 꽉 찬 배경을 원할 때 쓰는데, 그대로 두면 하단 고정 버튼이 홈 바에 겹치고 가로 모드에서 메뉴 글자가 노치에 잘린다.

브라우저는 가려지는 영역의 크기를 환경 변수로 알려 준다. `env(safe-area-inset-top)`, `right`, `bottom`, `left`다. 노치가 없는 기기와 데스크톱에서는 0이다.

```css
.bottom-bar {
  position: fixed;
  inset-inline: 0;
  bottom: 0;
  /* 기본 여백 0.75rem에 홈 바 높이를 더한다. env()의 두 번째 값은 대비값이다 */
  padding-bottom: calc(0.75rem + env(safe-area-inset-bottom, 0px));
}

.site-header {
  /* 가로 모드에서 노치가 왼쪽이나 오른쪽으로 온다 */
  padding-inline: max(1rem, env(safe-area-inset-left)) max(1rem, env(safe-area-inset-right));
}
```

`max()`를 쓴 이유는 노치 없는 기기에서도 최소 1rem은 비우되, 노치가 그보다 크면 노치만큼 비우기 위해서다. `calc()`로 더하면 노치가 있는 기기에서 여백이 필요 이상으로 커진다. 하단 바처럼 내용이 항상 가장자리에 붙는 곳은 더하고, 좌우 여백처럼 이미 충분한 곳은 `max()`로 고른다.

`viewport-fit=cover`가 없으면 iOS는 페이지를 안전한 영역 안에만 그리고 `env()` 값은 0이다. 값이 0으로만 나와 이상하면 메타 태그부터 본다.

## 가로 스크롤 범인 찾기

다시 처음 장면이다. 휴대폰에서 페이지가 옆으로 20px 밀린다. 범인을 찾는 순서는 늘 비슷하다.

먼저 정말 넘치는지 숫자로 확인한다. 개발자 도구 기기 모드로 390px를 맞추고 콘솔에서 문서 폭을 비교한다. `scrollWidth`가 `clientWidth`보다 크면 넘친다.

```js
// 문서 전체가 뷰포트보다 넓은지 본다
const root = document.documentElement;
console.log(root.scrollWidth, root.clientWidth); // 두 값이 다르면 가로 스크롤이 있다
```

다음은 오른쪽 끝이 뷰포트를 넘는 요소를 전부 찾는다. 문서 순서대로 훑으면 바깥 요소가 먼저 걸리고, 가장 안쪽에서 걸린 요소가 대개 원인이다.

```js
// 오른쪽 끝이 뷰포트 밖으로 나간 요소를 모두 출력한다
const vw = document.documentElement.clientWidth;
for (const el of document.querySelectorAll("body *")) {
  const r = el.getBoundingClientRect();
  if (r.right > vw + 0.5 || r.left < -0.5) console.log(Math.round(r.right), el);
}
```

아래 그림은 이 스크립트가 한 페이지를 훑으며 넘치는 요소를 좁혀 가는 모습이다. 각 칸은 문서 순서의 요소이고, 오른쪽에는 지금까지 찾은 넘치는 요소가 쌓인다.

눈으로 찾고 싶으면 모든 요소에 외곽선을 그린다. `outline`은 박스 크기에 영향을 주지 않아 레이아웃을 흔들지 않는다.

```css
/* 디버깅용. 넘치는 상자가 화면 오른쪽 밖으로 삐져나온 선으로 보인다 */
* { outline: 1px solid rgb(255 0 0 / 0.4); }
```

파이어폭스 개발자 도구는 이 일을 대신 해 준다. Inspector에서 넘침을 만든 요소 옆에 `overflow` 배지를, 스크롤이 생긴 컨테이너 옆에 `scroll` 배지를 붙인다.

범인은 대개 아래 중 하나다.

- 고정 폭: `width: 400px`, `min-width`가 큰 요소. `max-width: 100%`로 바꾼다.
- `width: 100vw`: 데스크톱 윈도우처럼 스크롤바가 자리를 차지하는 환경에서 `100vw`는 스크롤바 폭까지 포함해 문서보다 넓다. 대부분 `width: 100%`면 된다.
- 끊기지 않는 긴 문자열: URL, 이메일, 해시 값. `overflow-wrap: anywhere`를 준다.
- 줄어들지 않는 flex·grid 아이템: flex 아이템은 기본 `min-width: auto`라 안의 내용(긴 단어, 넓은 표)보다 작아지지 않는다. 아이템에 `min-width: 0`을 준다. grid에서 `1fr`도 같은 이유로 넘치니 `minmax(0, 1fr)`로 쓴다.
- 넓은 표와 코드 블록: 감싸는 상자에 `overflow-x: auto`를 주고, 그 상자 안에서만 스크롤되게 한다.
- 음수 여백: 화면 끝까지 배경을 늘리려고 `margin-inline: -1rem`을 준 요소가 부모 패딩보다 넓게 나간 경우.
- 화면 밖에 숨겨 둔 요소: `transform: translateX(100%)`로 오른쪽에 숨긴 메뉴 패널도 문서 폭을 늘린다.

가장 흔한 미봉책은 `body { overflow-x: hidden }`이다. 스크롤은 사라지지만 범인은 그대로 잘려 있다. 게다가 `overflow: hidden`은 그 요소를 스크롤 컨테이너로 만들어서 안쪽의 `position: sticky`가 동작하지 않게 될 수 있다. 정말 잘라야 한다면 스크롤 컨테이너를 만들지 않는 `overflow-x: clip`(크롬 90, 사파리 16, 파이어폭스 81부터)을 쓰고, 그래도 원인은 찾아서 고친다. iOS 사파리는 `body`의 `overflow-x: hidden`만으로는 가로 스크롤을 막지 못하는 경우가 있어 `html`에도 같이 줘야 했다는 점도 이 방법이 불안한 이유다.

마지막으로 기기 모드만 믿지 않는다. 개발자 도구의 기기 모드는 폭과 DPR은 흉내 내지만 주소창이 접히는 동작, 홈 바, 가상 키보드, iOS의 입력칸 확대는 재현하지 않는다. 출시 전에 실제 아이폰 사파리와 안드로이드 크롬에서 한 번씩 열어 본다. 아이폰이 없다면 맥의 Xcode 시뮬레이터가 그나마 가깝다.

## 작은 화면부터 쌓아 올리기

반응형은 미디어 쿼리 문법이 아니라 "화면 폭을 모르는 상태에서 부품을 만드는 습관"이다. 메타 태그로 레이아웃 뷰포트를 기기 폭에 맞추고, 모바일 한 줄 배치를 기본으로 둔 뒤 `min-width`로 넓히고, 여러 자리에 들어가는 부품은 컨테이너 쿼리로 자기 자리를 보게 한다. 높이는 `svh`·`dvh`, 글자는 `clamp()`, 가장자리는 `env(safe-area-inset-*)`. 그리고 가로 스크롤이 보이면 `overflow-x: hidden`을 덮기 전에 가장 안쪽에서 넘친 요소를 찾는다.

## 면접에서 나올 만한 질문

### viewport 메타 태그는 왜 필요한가?

없으면 모바일 브라우저가 페이지를 데스크톱용으로 보고 980px 정도의 가상 화면에 그린 뒤 통째로 축소한다. 그러면 글자가 작아지고 미디어 쿼리도 980px 기준으로 판정되어 모바일 스타일이 켜지지 않는다. `width=device-width, initial-scale=1`을 넣으면 레이아웃 뷰포트가 기기의 CSS 픽셀 폭이 된다. 확대를 막는 `maximum-scale=1`은 접근성 위반이라 넣지 않는다.

### CSS 픽셀과 기기 픽셀은 어떻게 다른가?

CSS 픽셀은 눈에 비슷한 크기로 보이게 정한 논리 단위이고, 기기 픽셀은 실제 발광 소자다. 둘의 비율이 devicePixelRatio이고, iPhone 15는 1179개의 기기 픽셀을 393 CSS 픽셀로 쓰니 3이다. 레이아웃은 CSS 픽셀로만 생각하면 되고, DPR은 이미지 해상도를 고를 때 중요하다. 브라우저 확대도 DPR을 바꾸는 방식이라 확대하면 CSS 폭이 줄어든다.

### 모바일에서 100vh가 문제가 되는 이유와 해결책은?

모바일 브라우저는 스크롤에 따라 주소창을 접었다 펴는데, `vh`는 들썩임을 막으려고 주소창이 접힌 가장 큰 높이로 고정되어 있다. 그래서 주소창이 펴진 처음 화면에서 `100vh` 요소의 아래쪽이 가려진다. 문서 흐름 안의 섹션은 항상 다 보이는 `svh`를, 화면에 고정된 모달처럼 지금 높이에 맞춰야 하는 요소는 `dvh`를 쓴다. 가상 키보드는 `dvh`에도 반영되지 않으니 필요하면 `visualViewport`를 읽는다.

### mobile-first가 desktop-first보다 나은 이유는?

모바일은 한 줄로 쌓이는 단순한 배치라 이걸 기본으로 두면 쿼리 안에 넓은 화면을 위해 더하는 규칙만 들어간다. 데스크톱 우선은 복잡한 배치를 좁은 화면에서 하나하나 취소해야 하고, 빠뜨린 취소가 휴대폰 버그가 된다. 쿼리가 적용되지 않는 상황에서도 기본인 한 줄 배치가 나와 읽을 수는 있다. 두 방향을 섞으면 경계 폭에서 둘 다 켜지거나 둘 다 꺼지는 틈이 생기니 한쪽으로 통일하거나 범위 문법을 쓴다.

### 미디어 쿼리 대신 컨테이너 쿼리를 쓰는 경우는?

컴포넌트가 화면 폭이 아니라 자기가 놓인 자리 폭에 반응해야 할 때다. 같은 카드가 메인 영역과 좁은 사이드바에 함께 들어가면 미디어 쿼리로는 사이드바 안에서도 넓은 배치가 켜진다. 부모에 `container-type: inline-size`를 주고 `@container`로 묻는다. 요소는 자기 자신을 질문할 수 없고, 크기 격리 때문에 폭이 내용으로 정해지는 자리에 컨테이너를 두면 폭이 0이 되는 점을 조심한다.

### clamp()로 글자 크기를 만들 때 vw만 쓰면 안 되는 이유는?

`vw`만 쓰면 브라우저를 확대해도 글자가 커지지 않는다. 확대하면 CSS 기준 뷰포트가 좁아지면서 `vw` 값도 줄어 확대 효과를 상쇄하기 때문이다. 텍스트를 200%까지 키울 수 있어야 한다는 WCAG 1.4.4를 어긴다. 그래서 선호값을 `1.2rem + 2.2vw`처럼 `rem`과 섞고, 최소·최대도 `rem`으로 둔다.

### 모바일에서 가로 스크롤이 생기면 어떻게 찾나?

먼저 `documentElement`의 `scrollWidth`와 `clientWidth`를 비교해 실제로 넘치는지 본다. 그다음 모든 요소의 `getBoundingClientRect().right`가 뷰포트 폭을 넘는지 훑어서 가장 안쪽에서 걸린 요소를 찾는다. 흔한 원인은 고정 폭, `100vw`, 끊기지 않는 긴 문자열, `min-width: auto`로 줄지 않는 flex 아이템, 넓은 표와 코드 블록이다. `overflow-x: hidden`은 원인을 숨기고 sticky를 깨뜨릴 수 있어 마지막 수단으로 두고, 써야 한다면 `overflow-x: clip`을 쓴다.

### 터치 대상 크기는 얼마로 잡고, 아이콘이 작으면 어떻게 하나?

WCAG 2.2 AA는 24×24px 이상이나 그만한 여유 간격을 요구하고, AAA와 애플 가이드라인은 44px, 머티리얼은 48dp다. 실무에서는 44px를 바닥으로 잡는 경우가 많다. 아이콘을 키울 필요는 없고 버튼의 `min-width`·`min-height`나 패딩으로 누르는 면적만 넓힌다. 되돌리기 어려운 동작은 자주 쓰는 버튼과 떨어뜨려 잘못 누르지 않게 한다.
