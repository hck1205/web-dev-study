Git 오류는 대부분 영어 몇 줄과 hint 몇 줄로 나온다. 처음 보면 겁이 나지만, 읽어 보면 무엇이 문제인지와 어떻게 하라는지가 거의 다 적혀 있다. 문제는 그 hint가 늘 상황에 맞는 답은 아니라는 것이다. `git pull` 하라는 말을 따랐다가 머지 커밋이 생기고, 검색해서 찾은 `--force`로 동료 커밋을 지우는 일이 여기서 생긴다.

이 글은 실무에서 자주 만나는 Git 문제를 증상별로 모았다. 각 문제마다 실제로 재현한 오류 메시지를 먼저 보이고, 왜 그런지, 어떤 명령으로 고치는지, 다음에 안 겪으려면 무엇을 해 두면 되는지를 적었다. 기준은 Ubuntu 24.04의 Git 2.43이고 출력은 모두 그 버전에서 직접 재현한 결과다. 원격 주소와 경로만 읽기 쉽게 바꿨다.

되돌리기(reset, revert, restore)의 원리는 [Git 되돌리기 글](/posts/git-undo)에, rebase가 커밋을 다시 만드는 과정은 [rebase 글](/posts/git-rebase)에 자세히 있다. 여기서는 증상에서 해결까지 가는 길에 집중한다.

## 문제가 어디서 났는지부터 가른다

Git 문제는 거의 다 네 곳 중 한 곳에서 난다. 내가 파일을 고치는 작업 폴더, 다음 커밋에 들어갈 내용을 모아 두는 스테이징 영역(index), 커밋과 브랜치가 쌓이는 로컬 저장소, 그리고 원격 저장소다. 오류 메시지가 어느 곳을 말하는지 알면 고칠 명령도 좁혀진다. 아래 그림에서 화살표가 각 명령이 데이터를 옮기는 방향이다.

무엇을 하든 먼저 칠 명령은 `git status`다. 지금 어느 브랜치에 있는지, rebase나 merge가 진행 중인지, 무엇이 충돌했는지를 알려 주고, 다음에 칠 명령까지 괄호 안에 적어 준다. 이 글의 절반은 `git status`를 읽는 법이라고 봐도 된다.

```bash
# 지금 상태: 브랜치, 진행 중인 작업, 충돌 파일, 다음에 할 명령
git status

# 내가 최근에 한 일 (HEAD가 움직인 기록). 뭔가 잃어버렸을 때 여기서 찾는다
git reflog -10

# 위험한 작업 전에 지금 위치에 이름표를 붙여 둔다 (실패하면 여기로 돌아온다)
git branch backup/before-fix
```

## 푸시가 fetch first로 거절된다

원인은 내가 마지막으로 받은 뒤에 누군가 같은 브랜치에 푸시했다는 것이다. 원격 브랜치는 앞으로만 움직이므로, 원격 커밋을 조상으로 갖지 않은 내 커밋으로는 옮겨 주지 않는다.

```bash
# 원격 커밋을 받아서 내 커밋을 그 위로 옮긴다 (아직 안 민 내 커밋이니 rebase해도 된다)
git pull --rebase

# 충돌이 나면 고치고 이어 간다
git add <파일>
git rebase --continue

# 다시 민다
git push
```

`(non-fast-forward)`로 거절되면서 hint가 "the tip of your current branch is behind its remote counterpart"라고 하면, 대개 이미 푸시한 커밋을 amend하거나 rebase한 경우다. 이때 `git pull`을 하면 같은 내용의 커밋이 두 벌 생긴다. 혼자 쓰는 브랜치라면 아래 "이미 푸시한 커밋 메시지" 항목처럼 `--force-with-lease`로 민다. 막으려면 `git config --global pull.rebase true`를 켜 두고, 푸시 전에 `git status -sb`로 behind가 0인지 본다. 원격 협업의 흐름 전체는 [원격 협업 글](/posts/git-remote-collaboration)에 있다.

## pull이 divergent branches라며 멈춘다

```text
hint: You have divergent branches and need to specify how to reconcile them.
hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint: 
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
...
fatal: Need to specify how to reconcile divergent branches.
```

오류가 아니라 질문이다. 내 브랜치와 원격 브랜치가 각자 다른 커밋을 쌓아 갈라졌는데, 합치는 방식을 정해 두지 않았으니 골라 달라는 것이다. 예전 Git은 묻지 않고 merge했다.

```bash
# 이번 한 번만 rebase로
git pull --rebase

# 앞으로 계속 rebase로 (가장 흔한 선택)
git config --global pull.rebase true

# 또는 갈라지면 항상 멈추고 직접 고르게
git config --global pull.ff only
```

설정 하나만 해 두면 다시 안 본다. 어느 쪽을 고를지는 [원격 협업 글](/posts/git-remote-collaboration)에서 비교했다.

## refusing to merge unrelated histories

GitHub에서 저장소를 만들 때 README나 LICENSE를 넣고, 로컬에서는 따로 `git init`으로 시작한 프로젝트를 그 저장소에 연결하면 생긴다.

```bash
# 로컬 프로젝트를 새 원격에 연결하고 밀어 본다
git remote add origin git@github.com:matt/shop.git
git push -u origin main

# 거절되니 받아서 합치려 한다
git pull --no-rebase origin main
```

```text
From github.com:matt/shop
 * branch            main       -> FETCH_HEAD
fatal: refusing to merge unrelated histories
```

원인은 두 히스토리에 공통 조상이 없다는 것이다. 원격의 "Initial commit"과 내 첫 커밋은 각자 따로 시작한 뿌리다. Git 2.9부터는 이런 머지를 기본으로 막는다. 엉뚱한 저장소끼리 실수로 합치는 걸 막으려는 것이다.

정말 합치려는 게 맞으면 옵션으로 허락한다.

```bash
# 공통 조상이 없어도 합친다
git pull --no-rebase --allow-unrelated-histories origin main
git log --oneline --graph
git push -u origin main
```

```text
Merge made by the 'ort' strategy.
 LICENSE   | 1 +
 README.md | 1 +
 2 files changed, 2 insertions(+)
 create mode 100644 LICENSE
 create mode 100644 README.md
*   0b2555b Merge branch 'main' of github.com:matt/shop
|\  
| * badf1a3 Initial commit
* 736d5c3 feat: app
```

원격에 있던 게 자동 생성된 README뿐이고 필요 없다면, 합치지 않고 `git push --force-with-lease -u origin main`으로 덮어쓰는 방법도 있다. 새 저장소라 지울 게 없을 때만 그렇게 한다. 막으려면 이미 로컬 프로젝트가 있을 때는 GitHub에서 저장소를 만들 때 README, .gitignore, LICENSE를 넣지 말고 빈 저장소로 만든다.

## 바꾼 파일이 덮어써진다며 브랜치를 못 바꾼다

```text
error: Your local changes to the following files would be overwritten by checkout:
	app.js
Please commit your changes or stash them before you switch branches.
Aborting
```

merge나 pull에서는 끝이 `by merge:`로 바뀌어 나온다. 아직 커밋하지 않은 `app.js`의 변경이 있는데, 옮겨 가려는 브랜치에서도 `app.js`가 다르게 생겼다. 그대로 바꾸면 내 변경이 사라지니 Git이 멈춘 것이다. 변경한 파일이 대상 브랜치와 같은 내용이면 이 오류 없이 변경을 들고 넘어간다.

```bash
# 방법 1: 하던 일을 잠깐 치워 두고 바꾼다
git stash push -m "wip: app tweak"
git switch feature/x
git stash pop

# 방법 2: 지금 상태를 임시 커밋으로 남긴다 (나중에 amend나 reset --soft로 정리)
git commit -am "wip"

# 방법 3: 브랜치를 바꾸지 않고 다른 폴더에 그 브랜치를 꺼낸다
git worktree add ../shop-feature-x feature/x
```

추적하지 않는 새 파일도 같은 일을 일으킨다.

```text
error: The following untracked working tree files would be overwritten by merge:
	new.txt
Please move or remove them before you merge.
Aborting
```

합쳐 올 쪽에 같은 이름의 파일이 커밋되어 있어서다. 내 `new.txt`가 필요하면 다른 이름으로 옮겨 두고, 필요 없으면 지운다. `git stash push -u`는 추적하지 않는 파일까지 치워 준다. 급한 작업이 자주 끼어든다면 방법 3의 worktree가 가장 편하다. [Git 고급 기능 글](/posts/git-tips-advanced)에서 자세히 본다.

## stash pop에서 충돌이 났다

치워 둔 변경을 다른 브랜치에서 꺼냈더니 같은 줄이 서로 달랐다.

```text
Auto-merging app.js
CONFLICT (content): Merge conflict in app.js
On branch feature/x
Unmerged paths:
  (use "git restore --staged <file>..." to unstage)
  (use "git add <file>..." to mark resolution)
	both modified:   app.js

no changes added to commit (use "git add" and/or "git commit -a")
The stash entry is kept in case you need it again.
```

마지막 줄을 봐 둔다. 충돌이 나면 stash는 지워지지 않고 남아 있다. 그래서 잘못 풀어도 다시 꺼낼 수 있다. 파일에는 충돌 표시가 들어가 있다.

```text
<<<<<<< Updated upstream
feature
=======
local edit
>>>>>>> Stashed changes
```

`Updated upstream`이 지금 브랜치의 내용, `Stashed changes`가 꺼낸 내 변경이다.

```bash
# 표시를 지우고 원하는 내용으로 고친 뒤, 해결했다고 표시
git add app.js

# stash pop은 원래 변경을 스테이징하지 않으니, 스테이징만 풀어 같은 상태로 만든다
git restore --staged app.js

# 남아 있는 stash를 직접 지운다
git stash drop
```

```text
Dropped refs/stash@{0} (504e9b3e7fe17f775e8fc90b7fdd72890257ebea)
```

꼬였으면 `git checkout -- app.js`로 파일을 되돌리고 `git stash pop`을 다시 하면 된다. stash가 아직 남아 있으니까. 실수로 drop했어도 출력에 찍힌 해시(`504e9b3...`)로 `git stash apply 504e9b3`를 하면 돌아온다. stash를 오래 쌓아 두면 무엇이었는지 잊는다. 하루를 넘길 변경이면 브랜치에 커밋하는 편이 낫다.

## detached HEAD에서 만든 커밋이 사라졌다

옛 커밋을 확인하려고 해시로 checkout했다가, 그 상태에서 고치고 커밋까지 했다.

```text
Note: switching to 'badf1a3'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.
...
HEAD is now at badf1a3 Initial commit
```

detached HEAD는 HEAD가 브랜치가 아니라 커밋을 직접 가리키는 상태다. 이 상태에서 커밋하면 아무 브랜치도 그 커밋을 가리키지 않는다. 다른 브랜치로 옮기는 순간 Git이 경고한다.

```text
Warning: you are leaving 1 commit behind, not connected to
any of your branches:

  1a8a12d feat: experiment

If you want to keep it by creating a new branch, this may be a good time
to do so with:

 git branch <new-branch-name> 1a8a12d

Switched to branch 'main'
```

이 경고를 놓쳤어도 커밋은 아직 저장소에 있다. 이름표가 없어서 안 보일 뿐이다. HEAD가 움직인 기록인 reflog에서 찾는다. 아래 그림은 reflog를 위에서부터 훑어 잃어버린 커밋을 찾는 과정이다.

```text
1a8a12d feat: experiment
```

`HEAD@{1}`은 셸에 따라 중괄호를 다르게 해석할 수 있으니 zsh 등에서는 따옴표로 감싸 `'HEAD@{1}'`로 쓴다. reflog는 로컬에만 있고, 브랜치에 연결되지 않은 기록은 기본 90일(도달할 수 없는 커밋은 30일)이 지나면 `git gc`가 지운다. 그 전에 찾으면 된다. 막으려면 옛 커밋을 살펴볼 때부터 `git switch -c try/old badf1a3`처럼 브랜치를 만들어서 들어가거나, 보기만 할 거면 `git switch --detach`로 의도를 분명히 하고 커밋하지 않는다.

## 브랜치를 실수로 지웠다

머지되지 않은 브랜치를 `-d`로 지우려 하면 Git이 막는다. 그래서 `-D`로 지웠는데, 알고 보니 필요한 브랜치였다.

```text
error: the branch 'feature/payment' is not fully merged.
If you are sure you want to delete it, run 'git branch -D feature/payment'
Deleted branch feature/payment (was 0f4ab09).
```

지울 때 출력의 `(was 0f4ab09)`가 그 브랜치의 마지막 커밋이다. 브랜치는 커밋을 가리키는 이름표일 뿐이라, 이름표만 지워졌고 커밋은 남아 있다.

```bash
# 출력에 찍힌 해시로 바로 되살린다
git branch feature/payment 0f4ab09

# 터미널을 닫아 해시를 모르면 reflog에서 그 브랜치에서 한 일을 찾는다
git reflog -3
```

```text
9e773d1 HEAD@{0}: checkout: moving from feature/payment to main
0f4ab09 HEAD@{1}: commit: feat(payment): add card form
9e773d1 HEAD@{2}: checkout: moving from main to feature/payment
```

브랜치 자체의 reflog는 브랜치와 함께 지워지지만, HEAD의 reflog에는 "moving from feature/payment"처럼 그 브랜치를 오간 기록이 남는다. 원격에 밀어 둔 브랜치였다면 `git switch feature/payment`만으로 `origin/feature/payment`에서 다시 만들어진다. 원격 브랜치까지 지웠다면 GitHub의 PR 화면에 남은 "Restore branch" 버튼을 쓸 수 있다. 막으려면 `-D`를 칠 때 한 번 멈추고, 지우기 전에 `git log main..feature/payment`로 main에 없는 커밋이 있는지 본다.

## 이미 푸시한 커밋 메시지가 틀렸다

```bash
# 마지막 커밋 메시지 고치기
git commit --amend -m "feat: add z"

# 그냥 밀면 거절된다
git push
```

```text
To github.com:matt/shop.git
 ! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs to 'github.com:matt/shop.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart. If you want to integrate the remote changes,
hint: use 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.
```

amend는 커밋을 고치는 게 아니라 새 커밋을 만든다. 메시지가 커밋 해시 계산에 들어가니 해시가 바뀌고, 원격 입장에서는 원래 커밋을 버리라는 요청이 된다. 여기서 hint대로 `git pull`을 하면 옛 커밋과 새 커밋이 머지되어 같은 변경이 두 번 보이는 이상한 히스토리가 된다.

혼자 쓰는 기능 브랜치라면 lease를 걸고 덮어쓴다.

```bash
# 내가 알고 있는 원격 상태일 때만 덮어쓴다
git push --force-with-lease --force-if-includes
```

```text
To github.com:matt/shop.git
 + ff87eb9...f022ed4 main -> main (forced update)
```

<Callout kind="warning" title="공유 브랜치의 히스토리는 고치지 않는다">
main처럼 여러 사람이 받아 가는 브랜치에서 이미 푸시한 커밋을 amend나 rebase로 바꾸고 강제 푸시하면, 그 커밋을 받은 모든 사람의 저장소와 어긋난다. 그들이 다음에 pull하면 옛 커밋이 머지로 되살아난다. 메시지 오타 정도면 그냥 두고, 내용이 틀렸으면 `git revert`로 되돌리는 새 커밋을 만든다. 실수로 덮어썼다면 출력의 왼쪽 해시(`ff87eb9`)로 `git push --force-with-lease origin ff87eb9:main`을 해서 원래대로 돌린다.
</Callout>

더 오래된 커밋의 메시지를 고치려면 `git rebase -i`에서 `reword`를 쓴다. 이 역시 그 뒤의 커밋 해시를 모두 바꾸므로 같은 조건이 붙는다. 자세한 방법은 [rebase 글](/posts/git-rebase)과 [되돌리기 글](/posts/git-undo)에 있다.

## rebase가 끝나지 않은 채로 남아 있다

충돌이 난 rebase를 두고 다른 일을 하다 돌아오면, 브랜치를 바꾸려 할 때 이렇게 막힌다.

```text
fatal: cannot switch branch while rebasing
Consider "git rebase --quit" or "git worktree add".
```

`git branch`를 치면 브랜치 이름 자리에 `* (no branch, rebasing feature)`가 보인다. `git status`가 지금 상황과 할 일을 정확히 알려 준다.

```text
interactive rebase in progress; onto b22552d
Last command done (1 command done):
   pick 7145ee8 feat: change f
No commands remaining.
You are currently rebasing branch 'feature' on 'b22552d'.
  (fix conflicts and then run "git rebase --continue")
  (use "git rebase --skip" to skip this patch)
  (use "git rebase --abort" to check out the original branch)

Unmerged paths:
  (use "git restore --staged <file>..." to unstage)
  (use "git add <file>..." to mark resolution)
	both modified:   f.txt
```

선택지는 셋이다.

```bash
# 1. 이어서 끝낸다: 충돌을 고치고 표시한 뒤 계속
git add f.txt
git rebase --continue

# 2. 없던 일로 한다: rebase 시작 전 상태로 브랜치를 되돌린다
git rebase --abort

# 3. 이 커밋만 버리고 다음으로 (그 커밋의 변경이 정말 필요 없을 때만)
git rebase --skip
```

`--quit`은 rebase 진행 정보만 지우고 지금 상태(HEAD)를 그대로 둔다. 무엇을 하는지 정확히 알 때가 아니면 `--abort`가 안전하다. merge 도중이면 `git merge --abort`, cherry-pick 도중이면 `git cherry-pick --abort`로 같은 일을 한다. 막으려면 프롬프트에 브랜치와 진행 중인 작업을 띄워 둔다. Ubuntu의 bash는 `/usr/lib/git-core/git-sh-prompt`를 불러와 `PS1`에 `__git_ps1`을 넣으면 `(feature|REBASE 1/1)`처럼 보여 준다.

## pnpm-lock.yaml에서 충돌이 났다

두 브랜치가 각자 의존성을 올리면 락파일이 충돌한다.

```text
Auto-merging pnpm-lock.yaml
CONFLICT (content): Merge conflict in pnpm-lock.yaml
Automatic merge failed; fix conflicts and then commit the result.
```

락파일은 패키지 관리자가 `package.json`을 보고 만든 결과물이다. 수천 줄의 해시와 의존성 트리를 손으로 섞으면 존재하지 않는 조합이 만들어지기 쉽다. 손으로 고치지 말고 다시 만든다.

```bash
# 1. package.json에 충돌이 있으면 그것부터 손으로 푼다 (원하는 버전을 고른다)
git status

# 2. 락파일은 한쪽 것을 그대로 가져온다 (merge 중: --ours는 지금 브랜치, --theirs는 합쳐 오는 브랜치)
git checkout --theirs pnpm-lock.yaml

# 3. 패키지 관리자가 package.json에 맞게 락파일을 다시 계산한다
pnpm install

# 4. 결과를 확인하고 머지를 마무리한다
git add package.json pnpm-lock.yaml
git commit
```

```text
Updated 1 path from the index
```

pnpm은 충돌 표시가 남은 `pnpm-lock.yaml`을 `pnpm install`이 알아서 풀어 준다고 공식 문서에 적어 두었다. npm도 `package-lock.json` 충돌을 `npm install`로 해결하도록 안내한다. 어느 쪽이든 결과 락파일은 사람이 아니라 도구가 만든 것이어야 한다.

헷갈리는 함정이 하나 있다. rebase 도중에는 ours와 theirs가 반대다. rebase는 상대 브랜치 위에 내 커밋을 하나씩 다시 얹는 작업이라, 그 순간의 "ours"는 상대 브랜치(얹히는 바닥)이고 "theirs"가 내 커밋이다. 막으려면 CI에서 `pnpm install --frozen-lockfile`(CI 환경에서는 기본값)로 락파일과 `package.json`이 맞지 않으면 실패하게 하고, 의존성 업데이트는 Renovate나 Dependabot처럼 한 PR에 하나씩 들어오게 한다.

## 큰 파일을 커밋해서 푸시가 안 된다

DB 덤프 파일 하나를 실수로 커밋하고 그 위에 커밋을 더 쌓았다. GitHub는 파일 하나가 100MB를 넘으면 `GH001: Large files detected`로 시작하는 오류와 함께 푸시 전체를 거절한다(50MB를 넘으면 경고만 한다). 먼저 무엇이 큰지 찾는다.

```bash
# 저장소 크기
git count-objects -vH

# 히스토리 전체에서 큰 blob 찾기 (크기 순)
git rev-list --objects --all \
  | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' \
  | sort -k3 -n -r | head -3

# 그 파일이 들어간 커밋
git log --oneline --all -- dump.sql
```

```text
count: 9
size: 114.51 MiB
in-pack: 0
packs: 0
size-pack: 0 bytes
prune-packable: 0
garbage: 0
size-garbage: 0 bytes
```

```text
blob eba910ce310f9972ee1898208bff7113df4ce468 120000000 dump.sql
commit dbe3b61b60ef45c6198dce94f991efb08944b1cc 213 
commit 241d01db8874a3d7588146eebbf1536694ea3f49 205 
```

```text
dbe3b61 chore: add db dump
```

나중 커밋에서 파일을 지워도 소용없다. 푸시는 히스토리 전체를 보내니, 그 파일이 들어간 커밋이 하나라도 있으면 거절된다. 히스토리에서 빼야 한다.

마지막 커밋에만 들어갔고 아직 푸시 전이라면 간단하다.

```bash
# 파일은 디스크에 두고 Git 추적만 뺀 뒤 마지막 커밋을 다시 만든다
git rm --cached dump.sql
echo "dump.sql" >> .gitignore
git add .gitignore
git commit --amend --no-edit
```

여러 커밋 전에 들어갔다면 히스토리를 다시 쓰는 도구를 쓴다. Git 공식 문서도 옛 `git filter-branch` 대신 권하는 git-filter-repo다. Ubuntu 22.04 이후는 `sudo apt install git-filter-repo`로 설치한다.

```bash
# 다시 쓰기 전에 백업 (filter-repo는 되돌릴 수 없다)
git clone --mirror git@github.com:matt/shop.git shop-backup.git

# 히스토리 전체에서 dump.sql을 뺀다
git filter-repo --path dump.sql --invert-paths
```

```text
Aborting: Refusing to destructively overwrite repo history since
this does not look like a fresh clone.
  (expected at most one entry in the reflog for HEAD)
Note: when cloning local repositories, you need to pass
      --no-local to git clone to avoid this issue.
Please operate on a fresh clone instead.  If you want to proceed
anyway, use --force.
```

filter-repo는 작업하던 저장소에서 실수로 돌리지 않도록 새로 clone한 저장소에서만 돈다. 새로 clone해서 돌리거나, 백업을 해 뒀다면 `--force`를 붙인다.

```text
NOTICE: Removing 'origin' remote; see 'Why is my origin removed?'
        in the manual if you want to push back there.
        (was git@github.com:matt/shop.git)
Parsed 3 commits
HEAD is now at d8a4138 feat: more

New history written in 0.02 seconds; now repacking/cleaning...
Repacking your repo and cleaning out old unneeded objects
Completely finished after 0.10 seconds.
```

```bash
# 결과 확인: 커밋 해시가 모두 바뀌고 저장소가 작아졌다
git log --oneline
git count-objects -vH | grep size-pack

# origin이 지워졌으니 다시 붙이고, 모든 브랜치와 태그를 덮어쓴다
git remote add origin git@github.com:matt/shop.git
git push --force --all origin
git push --force --tags origin
```

```text
d8a4138 feat: more
840ed4d feat: app
size-pack: 1.61 KiB
```

115MB였던 저장소가 1.61KiB가 됐다. 대신 모든 커밋 해시가 바뀌었으니 팀원들은 기존 clone을 버리고 새로 받아야 한다. 옛 clone에서 pull하면 큰 파일이 다시 섞여 들어온다. 큰 파일을 정말 버전 관리해야 한다면 Git LFS(`git lfs track "*.sql"`)를 쓴다. 막으려면 `.gitignore`에 덤프와 빌드 산출물을 미리 넣고, pre-commit 훅으로 일정 크기 이상 파일을 막는다.

## 비밀 값이 든 .env를 커밋했다

푸시까지 했다면 순서를 지킨다. 히스토리를 고치는 것보다 키를 바꾸는 게 먼저다.

<Callout kind="note" title="먼저 키를 폐기한다">
공개 저장소에 올라간 비밀 값은 몇 분 안에 자동 수집기에 긁혀 간다고 보고 대응한다. 히스토리에서 지워도 이미 clone한 사람, 포크, CI 캐시, GitHub의 PR 화면에는 남는다. 그래서 첫 번째 일은 그 키를 발급한 곳에서 폐기하고 새 키를 발급하는 것이다. 히스토리 정리는 그다음이다.
</Callout>

```bash
# 그 값이 히스토리 어디에 있는지 찾는다 (-S는 그 문자열이 생기거나 사라진 커밋)
git log --all --oneline -S "sk_live"

# 앞으로는 추적하지 않게 한다 (디스크의 파일은 남는다)
echo ".env" >> .gitignore
git rm --cached .env
git commit -m "chore: stop tracking .env"

# 히스토리에서도 지운다: 파일 통째로, 또는 값만 치환
git filter-repo --path .env --invert-paths
printf 'sk_live_123==>REMOVED\n' > ../replacements.txt
git filter-repo --replace-text ../replacements.txt
```

```text
9e773d1 chore: stop tracking .env
f8f3fc7 feat: app
```

`-S`로 찾으면 그 값이 처음 들어간 커밋(`f8f3fc7`)과 빠진 커밋(`9e773d1`)이 나온다. 그 사이 모든 커밋에 값이 있었다는 뜻이다. GitHub의 push protection(secret scanning)이 켜진 저장소라면 알려진 형식의 토큰은 푸시 단계에서 막히기도 한다. 막으려면 처음부터 `.env`를 `.gitignore`에 넣고 `.env.example`에 키 이름만 적어 커밋한다. gitleaks 같은 도구를 pre-commit 훅이나 CI에 걸어 둔다.

## .gitignore에 적었는데 계속 추적된다

`.env`를 `.gitignore`에 넣었는데 고치면 여전히 `git status`에 나온다.

```bash
git status --short

# 무시 규칙에 걸리는지, 어느 파일 몇 번째 줄 때문인지 확인
git check-ignore -v .env
git check-ignore -v --no-index .env
```

```text
 M .env
.gitignore:1:.env	.env
```

`M`은 추적 중인 파일이 바뀌었다는 표시다. `.gitignore`는 아직 추적하지 않는 파일에만 효과가 있다. 한 번 커밋된 파일은 규칙과 상관없이 계속 추적된다. 그래서 첫 `check-ignore -v`는 아무것도 출력하지 않고(추적 중이라 무시 대상이 아니다) 종료 코드 1로 끝나고, 추적 여부를 무시하는 `--no-index`를 붙여야 규칙이 맞는다는 게 보인다.

```bash
# 추적에서 빼기 (디스크의 파일은 그대로 남는다)
git rm --cached .env
git commit -m "chore: stop tracking .env"

# 폴더째 빼려면 -r
git rm -r --cached dist/
```

```text
rm '.env'
```

이 커밋을 받은 팀원의 디스크에서는 그 파일이 지워진다는 데 주의한다. Git 입장에서는 파일 삭제 커밋이기 때문이다. 설정 파일이라면 미리 알리거나 백업하게 한다. 규칙 자체가 안 먹는다면 경로를 의심한다. `/build`는 저장소 루트의 build만, `build/`는 어디에 있든 build라는 폴더만, `build`는 같은 이름의 파일과 폴더 모두에 맞는다. 내 컴퓨터에만 해당하는 것(`.idea/`, `.DS_Store`)은 저장소의 `.gitignore`보다 전역 설정(`git config --global core.excludesFile ~/.gitignore_global`)에 둔다.

## 줄바꿈 때문에 파일 전체가 바뀌었다고 나온다

한 글자도 안 고쳤는데 diff에 파일 전체가 지워졌다 다시 생긴 것으로 나온다. 윈도우와 리눅스·맥을 같이 쓰는 팀에서 자주 본다.

```bash
# 줄바꿈 차이를 눈에 보이게 출력 (^M이 CR 문자다)
git diff | cat -A | head -12

# 인덱스(i/)와 작업 폴더(w/)의 줄바꿈, 적용된 속성(attr/) 보기
git ls-files --eol
```

```text
diff --git a/win.txt b/win.txt$
index b5eff57..de98044 100644$
--- a/win.txt$
+++ b/win.txt$
@@ -1,3 +1,3 @@$
-a^M$
-b^M$
-c^M$
+a$
+b$
+c$
```

```text
i/lf    w/lf    attr/                 	unix.txt
i/crlf  w/crlf  attr/                 	win.txt
```

줄바꿈 문자가 저장소에 어떻게 저장되는지는 [Git 내부 구조 글](/posts/git-internals-basics)에서 다뤘다. 여기서는 증상에서 해결까지만 본다. 윈도우는 줄 끝을 CR LF(`\r\n`) 두 글자로, 리눅스와 맥은 LF(`\n`) 한 글자로 쓴다. 누군가의 에디터가 줄바꿈을 바꿔 저장하면 모든 줄이 바뀐 것이 된다. `^M`이 지워진 줄과 없는 줄이 짝을 이루면 줄바꿈 문제다. `git diff --ignore-cr-at-eol`로 보면 아무 차이도 나오지 않는다.

예전에는 각자 `core.autocrlf`를 맞추라고 했다. 윈도우는 `true`(커밋할 때 LF로, 꺼낼 때 CRLF로), 리눅스·맥은 `input`(커밋할 때만 LF로)이다. `true`인 상태에서 LF 파일을 add하면 이런 경고가 나온다.

```text
warning: in the working copy of 'unix.txt', LF will be replaced by CRLF the next time Git touches it
```

개인 설정은 사람마다 빠뜨리기 쉽다. 저장소에 `.gitattributes`를 두면 모두에게 같은 규칙이 적용되고 개인의 `core.autocrlf`보다 우선한다.

```bash
# 저장소 규칙: 텍스트는 LF로 저장, 바이너리는 건드리지 않음, .bat는 CRLF
cat > .gitattributes <<'EOF'
* text=auto eol=lf
*.png binary
*.bat text eol=crlf
EOF

# 이미 커밋된 파일에도 규칙을 다시 적용한다
git add .gitattributes
git add --renormalize .
git status --short
git commit -m "chore: normalize line endings"
```

```text
A  .gitattributes
M  win.txt
i/lf    w/lf    attr/text=auto eol=lf 	.gitattributes
i/lf    w/lf    attr/text=auto eol=lf 	unix.txt
i/lf    w/crlf  attr/text=auto eol=lf 	win.txt
```

`--renormalize` 뒤 `ls-files --eol`을 보면 저장소(i/) 쪽이 모두 lf가 됐다. 작업 폴더(w/)의 `win.txt`는 아직 crlf인데, 파일을 다시 꺼낼 때(`git checkout -- win.txt`나 다음 checkout) 규칙대로 바뀐다. 정규화 커밋은 기능 변경과 섞지 말고 따로 만든다. 그래야 리뷰도, `git blame`에서 이 커밋을 건너뛰는 설정도 쉽다.

## 권한만 바뀐 파일이 diff에 나온다

내용은 그대로인데 이런 diff가 나온다.

```text
diff --git a/unix.txt b/unix.txt
old mode 100644
new mode 100755
```

실행 권한(x 비트)이 바뀌었다. 압축을 풀거나, 윈도우·WSL·도커 볼륨처럼 권한을 다르게 다루는 파일 시스템을 오가면 생긴다. Git은 파일 권한 중 실행 비트 하나만 기록한다. 100644는 일반 파일, 100755는 실행 파일이다.

```bash
# 이 저장소에서 권한 변경을 무시한다
git config core.fileMode false

# 권한을 일부러 바꾸고 싶을 때는 파일 시스템과 상관없이 인덱스에 직접 기록한다
git update-index --chmod=+x deploy.sh
git status --short
```

```text
M  deploy.sh
```

`core.fileMode false`는 무시할 뿐 고치지는 않는다. 셸 스크립트처럼 실행 권한이 의미 있는 파일은 `update-index --chmod`로 저장소에 정확히 기록해 둬야, 리눅스 서버에서 clone했을 때 `Permission denied` 없이 실행된다. 이 설정을 전역(`--global`)으로 켜면 진짜 권한 변경까지 못 보게 되니 문제가 있는 저장소에만 켠다.

## 대소문자만 바꾼 파일 이름이 반영되지 않는다

맥에서 `Button.tsx`를 `button.tsx`로 이름만 바꿨는데 `git status`에 아무것도 안 나온다. 그대로 두면 리눅스에서 도는 CI가 `./button`을 찾지 못해 빌드가 깨진다.

macOS(APFS 기본 설정)와 윈도우의 파일 시스템은 대소문자를 구분하지 않는다. 그래서 Git도 그런 곳에서는 `core.ignorecase=true`로 저장소를 만들고, 대소문자만 다른 이름을 같은 파일로 본다. 리눅스는 구분한다.

```bash
# Git에게 이름 변경을 직접 알린다
git mv Button.tsx button.tsx
git status --short

# 파일 시스템이 거부하면 다른 이름을 한 번 거친다
git mv Button.tsx tmp.tsx && git mv tmp.tsx button.tsx

git commit -m "refactor: lowercase file name"
```

```text
R  Button.tsx -> button.tsx
```

`R`이 이름 변경으로 기록됐다는 표시다. 이미 두 이름이 모두 커밋되어 버렸다면 `git ls-files | grep -i button`으로 확인하고 하나를 `git rm --cached`로 뺀다. 막으려면 파일 이름 규칙을 정하고(이 블로그는 kebab-case), 린터의 import 대소문자 검사 규칙을 켠다.

## cannot lock ref 오류가 난다

브랜치를 만들 때 이렇게 나온다.

```bash
# feature라는 브랜치가 있는 상태에서 feature/login을 만들려고 하면
git branch feature/login
```

```text
fatal: cannot lock ref 'refs/heads/feature/login': 'refs/heads/feature' exists; cannot create 'refs/heads/feature/login'
```

브랜치 이름은 `.git/refs/heads/` 아래 파일 경로로 저장된다. `feature`가 이미 파일이니 같은 이름의 폴더 `feature/`를 만들 수 없다. `feature`와 `feature/login`은 동시에 있을 수 없다는 뜻이다. 하나를 다른 이름으로 바꾸거나 지운다(`git branch -m feature feature/base`).

fetch에서 같은 오류를 만나는 경우가 더 많다. 아래 그림의 순서로 생긴다.

## index.lock 파일이 있다며 아무것도 안 된다

```text
fatal: Unable to create '/home/matt/shop/.git/index.lock': File exists.

Another git process seems to be running in this repository, e.g.
an editor opened by 'git commit'. Please make sure all processes
are terminated then try again. If it still fails, a git process
may have crashed in this repository earlier:
remove the file manually to continue.
```

Git은 인덱스를 고치는 동안 다른 프로세스가 동시에 고치지 못하게 `index.lock` 파일을 만들고, 끝나면 지운다. 이 파일이 남아 있으면 다른 Git 명령이 돌고 있거나, 앞선 명령이 강제 종료되면서 못 지운 것이다.

```bash
# 정말 돌고 있는 git이 없는지 먼저 본다 (IDE의 Git 연동, 커밋 메시지 편집기 등)
pgrep -a git

# 없으면 남은 잠금 파일을 지운다
rm -f .git/index.lock
```

돌고 있는 프로세스가 있는데 지우면 두 프로세스가 동시에 인덱스를 써서 망가질 수 있다. 꼭 먼저 확인한다.

## index file corrupt

```text
error: bad signature 0x62726167
fatal: index file corrupt
```

인덱스 파일(`.git/index`)이 깨졌다. 디스크 오류, 동기화 프로그램(Dropbox, iCloud 등)이 `.git` 폴더를 건드린 경우, 쓰는 도중 전원이 나간 경우에 생긴다. 인덱스는 "다음 커밋에 들어갈 내용"의 목록일 뿐이라 커밋과 작업 폴더의 파일은 안전하다. 지우고 HEAD에서 다시 만든다.

```bash
# 깨진 인덱스를 치우고 (만약을 위해 지우지 않고 옮겨 둔다)
mv .git/index .git/index.broken

# HEAD 커밋을 기준으로 인덱스를 다시 만든다 (작업 폴더 파일은 안 건드린다)
git reset

git status
```

```text
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean
```

`git reset`은 기본이 `--mixed`라 인덱스만 HEAD에 맞추고 작업 폴더는 그대로 둔다. 스테이징해 둔 내용은 사라지니 다시 `git add` 한다. 다른 데이터도 의심된다면 `git fsck`로 저장소 전체를 검사한다. 저장소를 클라우드 동기화 폴더 안에 두지 않는 게 가장 좋은 예방이다.

## not a git repository

```text
fatal: not a git repository (or any of the parent directories): .git
```

지금 폴더와 그 위 어느 폴더에도 `.git`이 없다. 대개 엉뚱한 폴더에서 명령을 쳤거나, clone이 만든 하위 폴더로 들어가지 않은 경우다.

```bash
# 지금 위치와 저장소 루트 확인
pwd
git rev-parse --show-toplevel

# clone은 저장소 이름으로 폴더를 만든다. 그 안으로 들어가야 한다
git clone git@github.com:matt/shop.git && cd shop
```

비슷하게 생겼지만 원인이 다른 오류가 있다. Git 2.35.2부터는 다른 사용자가 소유한 저장소에서 명령을 거부한다. 도커 컨테이너에 마운트한 소스나 `sudo`로 만든 폴더에서 자주 본다.

```text
fatal: detected dubious ownership in repository at '/srv/shop'
To add an exception for this directory, call:

	git config --global --add safe.directory /srv/shop
```

남이 만든 저장소의 `.git/config`에 심어 둔 설정(예: 훅 경로)이 내 권한으로 실행되는 것을 막는 보안 장치다. 믿을 수 있는 저장소면 안내대로 예외를 추가하거나, 소유자를 맞춘다(`sudo chown -R $USER /srv/shop`). `safe.directory '*'`로 모든 곳을 풀어 버리는 건 장치를 끄는 것과 같으니 피한다.

## 서브모듈 폴더가 비어 있다

clone한 프로젝트의 `vendor/lib` 폴더가 비어 있어서 빌드가 실패한다.

```bash
# 서브모듈 상태: 맨 앞이 -면 아직 초기화하지 않은 것
git submodule status

# 초기화하고 기록된 커밋으로 받는다 (서브모듈 안의 서브모듈까지)
git submodule update --init --recursive
git submodule status
```

```text
-c34eceea6b8effd5cafac03bcb0c87469f960d6f vendor/lib
```

```text
Submodule 'vendor/lib' (git@github.com:acme/lib.git) registered for path 'vendor/lib'
Cloning into '/home/matt/shop/vendor/lib'...
done.
Submodule path 'vendor/lib': checked out 'c34eceea6b8effd5cafac03bcb0c87469f960d6f'
 c34eceea6b8effd5cafac03bcb0c87469f960d6f vendor/lib (heads/main)
```

서브모듈은 "이 경로에는 저 저장소의 이 커밋을 꺼내 둔다"는 기록만 부모 저장소에 남긴다. 그냥 clone하면 그 기록만 받고 내용은 받지 않는다. 처음부터 `git clone --recurse-submodules`로 받거나, `git config --global submodule.recurse true`를 켜 두면 pull과 checkout 때도 서브모듈을 따라 움직인다. 서브모듈 안에 들어가면 브랜치가 아니라 detached HEAD 상태인 것도 정상이다. 부모가 정한 커밋을 그대로 꺼냈기 때문이다. 서브모듈과 subtree의 차이는 [Git 고급 기능 글](/posts/git-tips-advanced)에서 다룬다.

## Author identity unknown

새 서버나 새 컨테이너에서 처음 커밋하면 나온다.

```text
Author identity unknown

*** Please tell me who you are.

Run

  git config --global user.email "you@example.com"
  git config --global user.name "Your Name"

to set your account's default identity.
Omit --global to set the identity only in this repository.

fatal: unable to auto-detect email address (got 'root@vm.(none)')
```

커밋에는 작성자 이름과 이메일이 꼭 들어가야 하는데 설정이 없고, 호스트 이름으로 추측한 값도 쓸 수 없는 모양이라 멈췄다.

```bash
# 전역 설정 (이 사용자의 모든 저장소)
git config --global user.name "Matt"
git config --global user.email "matt@example.com"

# 회사 저장소만 다른 이메일을 쓰려면 그 저장소 안에서 --global 없이
git config user.email "matt@company.example"

# 지금 적용되는 값과 어느 파일에서 왔는지 확인
git config --show-origin user.email
```

이메일은 GitHub 계정에 등록한 주소여야 커밋이 내 프로필과 연결된다. 이메일을 공개하기 싫으면 GitHub가 주는 `아이디@users.noreply.github.com` 주소를 쓴다. 이미 틀린 이메일로 커밋했다면 `git commit --amend --reset-author --no-edit`로 마지막 커밋의 작성자를 지금 설정으로 바꾼다. 회사와 개인 저장소를 폴더로 나눈다면 `includeIf "gitdir:~/work/"`로 폴더마다 다른 설정 파일을 자동으로 불러오게 할 수 있다.

## 오류를 만났을 때의 순서

오류가 나면 먼저 메시지의 `fatal:`·`error:` 줄과 `!` 줄을 읽고, `git status`로 지금 진행 중인 작업이 있는지 본다. 고치는 명령을 치기 전에 `git branch backup/...`으로 이름표를 하나 붙여 두면, 무엇을 하든 돌아올 곳이 생긴다. 커밋한 것은 reflog에 거의 다 남아 있으니 커밋까지 간 작업은 쉽게 잃어버리지 않는다. 정말 조심할 것은 두 가지, 공유 브랜치의 강제 푸시와 커밋하지 않은 변경을 지우는 명령(`reset --hard`, `checkout -- .`, `clean -fd`)이다.

## 면접에서 나올 만한 질문

### push가 거절됐을 때 git pull을 하면 항상 해결되나요?

fetch first처럼 동료가 먼저 푸시한 경우는 pull(가능하면 `--rebase`)로 합친 뒤 다시 밀면 된다. 하지만 내가 이미 푸시한 커밋을 amend나 rebase해서 생긴 non-fast-forward라면, pull은 옛 커밋과 새 커밋을 머지해 같은 변경이 두 번 들어간 히스토리를 만든다. 이때는 혼자 쓰는 브랜치일 때만 `--force-with-lease`로 덮어쓴다. 그래서 거절 이유 괄호 안의 문구를 먼저 읽는다.

### 커밋을 잃어버렸을 때 어떻게 찾나요?

reflog를 본다. HEAD와 각 브랜치가 움직인 기록이 로컬에 남아 있어서, detached HEAD에서 만든 커밋이나 `-D`로 지운 브랜치의 커밋도 해시를 찾을 수 있다. 찾은 해시에 `git branch`로 이름표를 붙이면 복구된다. reflog는 기본으로 90일(도달할 수 없는 항목은 30일) 보관되고 그 뒤 gc가 정리하며, 원격에는 없는 로컬 기록이다.

### .gitignore에 추가했는데 파일이 계속 추적되는 이유는 무엇인가요?

.gitignore는 아직 추적하지 않는 파일에만 적용되기 때문이다. 이미 커밋된 파일은 `git rm --cached`로 추적을 끊고 커밋해야 한다. 이 커밋을 받은 다른 사람의 디스크에서는 파일이 삭제되므로 설정 파일이라면 미리 알린다. 규칙이 맞는지는 `git check-ignore -v --no-index`로 확인한다.

### 비밀 키를 커밋해서 푸시했습니다. 무엇부터 하나요?

키를 발급한 곳에서 즉시 폐기하고 새로 발급하는 것이 먼저다. 히스토리를 지워도 이미 clone한 사람, 포크, CI 캐시, 호스팅 서비스의 PR 화면 등에 남아 있을 수 있어서 키가 안전해지지 않는다. 그다음 git-filter-repo로 히스토리에서 파일이나 값을 지우고 강제 푸시하고, 팀원들에게 다시 clone하게 한다. 재발 방지로 .gitignore, .env.example, gitleaks 같은 검사를 둔다.

### 히스토리에 들어간 큰 파일은 왜 나중에 지워도 푸시가 안 되나요?

푸시는 브랜치 끝의 상태만이 아니라 원격에 없는 커밋 전체를 보내고, 그중 한 커밋에라도 그 파일이 들어 있으면 blob도 함께 가기 때문이다. 아직 푸시 전이고 마지막 커밋이면 `git rm --cached` 후 amend로, 여러 커밋 전이면 git-filter-repo로 히스토리에서 빼야 한다. 히스토리를 다시 쓰면 해시가 모두 바뀌므로 강제 푸시와 팀원의 재clone이 필요하다. 꼭 필요한 큰 파일은 Git LFS로 관리한다.

### 락파일 충돌은 어떻게 푸나요?

손으로 섞지 않는다. package.json 충돌을 먼저 풀고, 락파일은 한쪽 것을 가져온 뒤 `pnpm install`이나 `npm install`로 다시 계산해서 커밋한다. 수천 줄의 해시를 손으로 합치면 실제로 존재하지 않는 의존성 조합이 생기기 쉽다. CI에서는 frozen lockfile 옵션으로 락파일과 package.json이 어긋나면 실패하게 한다.

### 줄바꿈 때문에 파일 전체가 diff에 나오면 어떻게 하나요?

CRLF와 LF가 섞인 것이다. `git diff | cat -A`에서 `^M`으로 확인하고, 사람마다 다른 `core.autocrlf` 대신 저장소에 `.gitattributes`(`* text=auto eol=lf`)를 두어 규칙을 통일한다. 이미 커밋된 파일은 `git add --renormalize .`로 한 번에 정규화하는데, 이 커밋은 기능 변경과 섞지 않고 따로 만든다.

### rebase나 merge 도중 꼬였을 때 가장 안전하게 빠져나오는 방법은 무엇인가요?

`git rebase --abort`나 `git merge --abort`다. 작업을 시작하기 전 상태로 브랜치를 그대로 돌려놓는다. `git status`가 지금 어떤 작업이 진행 중인지와 continue, skip, abort 중 무엇을 할 수 있는지를 알려 주니 먼저 그걸 읽는다. 시작하기 전에 백업 브랜치를 만들어 두면 abort 뒤에도 안심할 수 있다.
