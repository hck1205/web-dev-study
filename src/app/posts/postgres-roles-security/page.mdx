서점 API 서버의 접속 문자열을 열어 보면 `postgresql://matt:...@db/shop`이다. [설치 글](/posts/postgres-getting-started)에서 만든 개인 역할을 그대로 앱에 넣어 둔 것이다. 이 역할로 무엇을 할 수 있는지 시험해 본다.

```sql
SELECT current_user;
BEGIN;
DROP TABLE order_items;      -- 주문 상세 테이블을 통째로 지운다
TRUNCATE orders CASCADE;     -- 주문을 전부 비운다
ROLLBACK;                    -- 실험이니 되돌린다
```

```text
 current_user
--------------
 matt
(1 row)

BEGIN
DROP TABLE
TRUNCATE TABLE
ROLLBACK
```

둘 다 성공했다. 앱 서버에 SQL 인젝션 구멍이 하나만 있거나, 누가 실수로 마이그레이션 스크립트를 운영 DB에 돌리면 테이블이 사라진다. `matt`는 슈퍼유저도 아닌데 왜 이게 될까. 테이블의 주인(owner)이라서다. PostgreSQL에서 주인은 `GRANT`로 준 권한과 상관없이 자기 객체를 바꾸고 지울 수 있다. 앱이 주인 계정으로 붙는 순간 권한 설계는 의미가 없어진다.

이 글은 역할(role)과 권한을 처음부터 짚고, 서점 DB를 주인 / 마이그레이션 / 읽기·쓰기 / 읽기 전용 역할로 나눈다. 그다음 비밀번호 저장 방식, `pg_hba.conf`와 TLS로 접속 경로를 좁히고, 행 단위 보안(RLS)으로 서점마다 자기 주문만 보게 만든다. 기준은 Ubuntu 24.04의 PostgreSQL 16(16.15)이고 출력은 모두 실제로 돌린 결과다. 실습은 쓰던 서버와 따로 띄운 클러스터(포트 5491)에서 했다.

## 역할 하나가 사용자이자 그룹이다

PostgreSQL에는 "사용자"와 "그룹"이 따로 없다. 둘 다 역할이다. 로그인할 수 있는 역할이 사용자처럼 쓰이고, 다른 역할을 멤버로 품은 역할이 그룹처럼 쓰인다. `CREATE USER`는 `CREATE ROLE ... LOGIN`의 다른 이름일 뿐이다. 역할은 클러스터 전체에 하나씩 있어서 모든 데이터베이스에서 같은 이름으로 보인다.

역할에는 속성(attribute)이 붙는다. 권한(privilege)과 다르게 객체가 아니라 역할 자체에 붙는 능력이다.

- `LOGIN`: 접속할 수 있다. 없으면 그룹 역할이다.
- `SUPERUSER`: 모든 권한 검사를 건너뛴다. RLS도 무시한다. 설치할 때 만든 `postgres` 하나로 충분하다.
- `CREATEDB`: 데이터베이스를 만들 수 있다.
- `CREATEROLE`: 역할을 만들 수 있다. PostgreSQL 16부터는 자기가 만든 역할(정확히는 `ADMIN OPTION`을 가진 역할)만 고칠 수 있게 좁혀졌다. 15까지는 슈퍼유저가 아닌 거의 모든 역할을 고칠 수 있어서 사실상 슈퍼유저에 가까웠다.
- `REPLICATION`: 복제 접속을 할 수 있다.
- `BYPASSRLS`: 행 단위 보안 정책을 건너뛴다. 뒤에서 다시 본다.
- `CONNECTION LIMIT n`, `VALID UNTIL '시각'`: 동시 접속 수와 비밀번호 만료 시각.

앱 계정에는 `LOGIN` 말고는 아무것도 주지 않는다. 앱이 DB나 역할을 만들 일은 없다.

### 멤버십과 SET ROLE

`GRANT app_rw TO api`라고 하면 `api`가 `app_rw`의 멤버가 된다. 멤버는 두 가지 방법으로 그룹의 권한을 쓴다. 기본은 상속(INHERIT)이다. 따로 아무것도 안 해도 그룹 권한이 내 권한처럼 적용된다. 다른 하나는 `SET ROLE app_rw`로 잠시 그 역할이 되는 것이다. 리눅스의 `sudo -u`와 비슷하다.

PostgreSQL 16부터는 멤버십마다 이 둘을 따로 켜고 끈다. 평소에는 권한이 없다가, 필요할 때만 `SET ROLE`로 주인 역할이 되게 하려면 상속을 끈다.

```sql
CREATE ROLE dba_kim LOGIN PASSWORD 'kim-2026';
GRANT shop_owner TO dba_kim WITH INHERIT FALSE;   -- 상속은 끄고, SET ROLE만 허용
```

```sql
-- dba_kim으로 접속해서
SELECT count(*) FROM books;                         -- 상속이 없으니 권한도 없다
SET ROLE shop_owner;                                -- 명시적으로 주인 역할이 된다
SELECT session_user, current_user, count(*) FROM books;
RESET ROLE;
```

```text
ERROR:  relation "books" does not exist
LINE 1: SELECT count(*) FROM books
                             ^
SET
 session_user | current_user | count
--------------+--------------+-------
 dba_kim      | shop_owner   |     4
(1 row)
```

첫 에러가 "권한 없음"이 아니라 "없는 테이블"이라는 점을 기억해 둔다. 스키마에 `USAGE` 권한이 없으면 그 안의 이름을 찾지도 못해서 이렇게 나온다. 테이블이 분명히 있는데 `does not exist`가 나오면 스키마 권한을 의심한다. `session_user`는 처음 로그인한 역할, `current_user`는 지금 권한 검사에 쓰이는 역할이다. 로그에는 둘 다 남길 수 있어서 누가 주인 역할로 무엇을 했는지 추적된다. 멤버십 목록은 `\drg`(16부터)로 본다.

```text
                 List of role grants
   Role name   | Member of  |   Options    | Grantor
---------------+------------+--------------+----------
 analyst       | app_ro     | INHERIT, SET | postgres
 api           | app_rw     | INHERIT, SET | postgres
 dba_kim       | shop_owner | SET          | postgres
 shop_migrator | shop_owner | INHERIT, SET | postgres
(4 rows)
```

이 순서대로 권한을 하나씩 준다. 권한은 객체 종류마다 다르다.

- 데이터베이스: `CONNECT`(접속), `CREATE`(스키마 생성), `TEMP`(임시 테이블).
- 스키마: `USAGE`(안의 객체 이름을 찾기), `CREATE`(객체 만들기).
- 테이블: `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`(외래 키로 참조), `TRIGGER`. 컬럼 단위로도 줄 수 있다(`GRANT SELECT (id, name) ON users TO ...`).
- 시퀀스: `USAGE`(nextval), `SELECT`(currval), `UPDATE`(setval).
- 함수와 프로시저: `EXECUTE`.

`DROP`과 `ALTER`는 이 목록에 없다. 이건 권한이 아니라 주인만 할 수 있는 일이다. 주인의 멤버(상속 포함)도 주인처럼 할 수 있다. 처음 장면에서 `matt`가 테이블을 지울 수 있었던 이유가 이것이다.

## 주인, 마이그레이션, 앱, 분석 역할로 나누기

이제 서점 DB의 역할을 나눈다. 원칙은 단순하다. 테이블의 주인은 로그인할 수 없는 역할로 두고, 사람과 프로그램은 필요한 만큼만 받은 역할로 붙는다.

그룹(`app_rw`, `app_ro`)을 두는 이유는 권한을 사람이나 서비스마다 따로 관리하지 않기 위해서다. 새 서비스가 생기면 로그인 역할을 하나 만들어 그룹에 넣기만 하면 된다. 슈퍼유저(`postgres`)로 아래를 실행한다.

```sql
-- 역할 만들기
CREATE ROLE shop_owner NOLOGIN;                       -- 주인: 아무도 직접 로그인하지 않는다
CREATE ROLE app_rw NOLOGIN;                           -- 권한 묶음
CREATE ROLE app_ro NOLOGIN;
CREATE ROLE shop_migrator LOGIN PASSWORD 'migrate-2026';
CREATE ROLE api LOGIN PASSWORD 'api-2026' CONNECTION LIMIT 50;
CREATE ROLE analyst LOGIN PASSWORD 'analyst-2026';

GRANT shop_owner TO shop_migrator;                    -- 마이그레이션은 주인 권한으로
GRANT app_rw TO api;
GRANT app_ro TO analyst;

-- 주인 바꾸기: DB와 테이블, 타입을 shop_owner에게
ALTER DATABASE shop OWNER TO shop_owner;
ALTER TABLE users OWNER TO shop_owner;
ALTER TABLE books OWNER TO shop_owner;
ALTER TABLE orders OWNER TO shop_owner;
ALTER TABLE order_items OWNER TO shop_owner;
ALTER TYPE order_status OWNER TO shop_owner;

-- 아무나(PUBLIC) 접속하고 스키마를 보던 기본 권한을 회수
REVOKE ALL ON DATABASE shop FROM PUBLIC;
GRANT CONNECT ON DATABASE shop TO app_rw, app_ro, shop_migrator;
REVOKE ALL ON SCHEMA public FROM PUBLIC;
GRANT USAGE ON SCHEMA public TO app_rw, app_ro;

-- 지금 있는 테이블과 시퀀스에 권한 주기
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_rw;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO app_rw;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_ro;
```

`REVOKE ... FROM PUBLIC`이 빠지기 쉬운 부분이다. 새 데이터베이스는 기본으로 모든 역할(`PUBLIC`)에 `CONNECT`와 `TEMP`를 준다. 회수하지 않으면 같은 클러스터의 다른 서비스 계정도 이 DB에 접속한다. 테이블 권한이 없으니 데이터는 못 읽지만, 카탈로그를 뒤져 테이블 구조를 보거나 함수를 실행할 수는 있다. 결과를 확인한다.

```text
--------+-------+-------+-------------------------------+-------------------+----------

        |       |       | app_rw=arwd/shop_owner       +|                   |
        |       |       | app_ro=r/shop_owner           |                   |
(1 row)
```

```sql
SELECT count(*) FROM books;

DROP TABLE order_items;
```

읽기와 쓰기는 되고, 지우기·비우기·구조 바꾸기·새 테이블 만들기는 막혔다. 에러 문구가 둘로 나뉜다. `must be owner`는 주인만 할 수 있는 일(DROP, ALTER), `permission denied`는 GRANT로 받을 수 있는데 안 받은 일(TRUNCATE, 스키마 CREATE)이다. `analyst`는 읽기만 된다. 그리고 `matt`는 이제 이 DB에 들어오지도 못한다.

```text
ERROR:  permission denied for table users
psql: error: connection to server at "localhost" (127.0.0.1), port 5491 failed: FATAL:  permission denied for database "shop"
DETAIL:  User does not have CONNECT privilege.
```

`users`의 id는 identity 컬럼인데 `api`가 `INSERT`할 수 있었다. identity 컬럼의 자동 번호는 테이블 `INSERT` 권한만 있으면 된다. 실제로 시퀀스 권한을 빼고 해 봐도 `INSERT`는 되고, `SELECT nextval('users_id_seq')`처럼 시퀀스를 직접 부를 때만 `permission denied for sequence`가 난다. `serial` 컬럼은 기본값이 `nextval()` 호출이라 시퀀스 `USAGE`가 꼭 필요하다. 시퀀스 권한을 빠뜨려 `serial` 테이블 INSERT가 막히는 일이 흔해서 위 스크립트에도 넣어 두었다.

### 새로 만든 테이블에는 권한이 없다

며칠 뒤 마이그레이션으로 `coupons` 테이블을 추가했다. 그런데 분석 담당이 읽지 못한다.

```sql
-- shop_migrator로 접속해서
CREATE TABLE coupons (code text PRIMARY KEY, discount integer NOT NULL);
\dt coupons
```

```text
            List of relations
 Schema |  Name   | Type  |     Owner
--------+---------+-------+---------------
 public | coupons | table | shop_migrator
(1 row)
```

```sql
-- analyst로 접속해서
SELECT * FROM coupons;
```

```text
ERROR:  permission denied for table coupons
```

`GRANT ... ON ALL TABLES IN SCHEMA`는 그 순간 있던 테이블에만 권한을 준다. 앞으로 생길 테이블에는 적용되지 않는다. 가장 흔한 실수다. 앞으로 만들 객체의 권한은 `ALTER DEFAULT PRIVILEGES`로 정한다.

```sql
-- shop_owner가 public 스키마에 만드는 테이블과 시퀀스에 자동으로 붙일 권한
ALTER DEFAULT PRIVILEGES FOR ROLE shop_owner IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_rw;
ALTER DEFAULT PRIVILEGES FOR ROLE shop_owner IN SCHEMA public
  GRANT USAGE, SELECT ON SEQUENCES TO app_rw;
ALTER DEFAULT PRIVILEGES FOR ROLE shop_owner IN SCHEMA public
  GRANT SELECT ON TABLES TO app_ro;

\ddp
```

```text
                Default access privileges
   Owner    | Schema |   Type   |   Access privileges
------------+--------+----------+------------------------
 shop_owner | public | sequence | app_rw=rU/shop_owner
 shop_owner | public | table    | app_rw=arwd/shop_owner+
            |        |          | app_ro=r/shop_owner
(2 rows)
```

이걸 걸고 나서 `shop_migrator`가 다시 `coupons`를 만들어도 여전히 `permission denied`다. 두 번째 함정이다. 기본 권한은 `FOR ROLE`에 적은 역할이 직접 만든 객체에만 붙는다. 위 `\dt` 출력에서 주인이 `shop_migrator`였다. 상속으로 주인 권한을 쓰고 있어도, 만든 객체의 주인은 로그인한 역할이 된다. 마이그레이션은 주인 역할로 바꾼 뒤에 해야 한다.

```sql
-- shop_migrator로 접속해서
DROP TABLE coupons;
SET ROLE shop_owner;                 -- 주인 역할로 바꾸고
CREATE TABLE coupons (code text PRIMARY KEY, discount integer NOT NULL);
\dp coupons
```

```text
                                    Access privileges
 Schema |  Name   | Type  |       Access privileges       | Column privileges | Policies
--------+---------+-------+-------------------------------+-------------------+----------
 public | coupons | table | shop_owner=arwdDxt/shop_owner+|                   |
        |         |       | app_rw=arwd/shop_owner       +|                   |
        |         |       | app_ro=r/shop_owner           |                   |
(1 row)
```

이제 주인이 `shop_owner`이고 기본 권한이 붙었다. 매번 `SET ROLE`을 잊지 않도록 역할 설정으로 고정해 두면 편하다. `ALTER ROLE shop_migrator SET role = 'shop_owner'`를 하면 이 역할로 접속할 때마다 자동으로 `shop_owner`가 된다(`session_user`는 `shop_migrator`, `current_user`는 `shop_owner`로 나온다).

### 미리 정의된 역할

PostgreSQL에는 자주 쓰는 권한 묶음이 `pg_`로 시작하는 역할로 들어 있다. 운영 계정에 슈퍼유저를 주지 않고 이걸 준다.

- `pg_read_all_data`, `pg_write_all_data`(14부터): 모든 DB의 모든 테이블을 읽기, 쓰기. 앞으로 생길 테이블도 포함한다. 백업 도구나 전사 분석 계정에 쓴다. 다만 RLS 정책은 그대로 적용된다.
- `pg_monitor`: `pg_stat_activity`의 다른 사용자 쿼리, 각종 통계 뷰를 읽는다. 모니터링 에이전트용이다.
- `pg_signal_backend`: 다른 세션의 쿼리를 취소하거나 끊는다(`pg_cancel_backend`, `pg_terminate_backend`). 슈퍼유저 세션은 제외다.
- `pg_read_server_files`, `pg_write_server_files`, `pg_execute_server_program`: 서버 파일 읽기·쓰기, 서버에서 프로그램 실행. 사실상 슈퍼유저와 같아서 주지 않는다.
- `pg_checkpoint`(15부터), `pg_maintain`(17부터, VACUUM·ANALYZE·REINDEX 등).

함수에도 기본 권한 함정이 하나 있다. 새로 만든 함수의 `EXECUTE`는 기본으로 `PUBLIC`에게 열려 있다. 실습에서 `shop_owner`가 `books`의 재고를 0으로 만드는 함수를 만들자 `analyst`도 그 함수를 호출할 수 있었다. 함수 안의 `UPDATE`가 `permission denied for table books`로 막힌 건 함수가 호출한 사람 권한으로 도는(`SECURITY INVOKER`, 기본값) 덕이다. 만든 사람 권한으로 도는 `SECURITY DEFINER` 함수였다면 그대로 실행됐다. 그래서 `ALTER DEFAULT PRIVILEGES FOR ROLE shop_owner REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC`으로 막고 필요한 역할에만 준다. `SECURITY DEFINER` 함수에는 `SET search_path = pg_catalog, public`처럼 경로를 고정한다. 경로가 열려 있으면 호출한 쪽이 같은 이름의 함수나 테이블을 먼저 찾히게 만들어 주인 권한으로 실행시킬 수 있다. 함수와 트리거는 [다음다음 글](/posts/postgres-functions-triggers)에서 자세히 본다.

## 비밀번호는 SCRAM으로 저장한다

역할의 비밀번호는 `pg_authid`에 해시로 저장된다. 어떤 방식으로 저장할지는 `password_encryption`이 정하고, PostgreSQL 14부터 기본값이 `scram-sha-256`이다. 예전 방식 `md5`와 나란히 놓고 보면 차이가 보인다.

```sql
SET password_encryption = 'md5';                      -- 비교용으로 옛 방식
CREATE ROLE old_app LOGIN PASSWORD 'old-2026';
RESET password_encryption;
SELECT rolname, rolpassword FROM pg_authid WHERE rolname IN ('old_app', 'api');
```

```text
 rolname |                                                              rolpassword
---------+---------------------------------------------------------------------------------------------------------------------------------------
 api     | SCRAM-SHA-256$4096:WpBfQ0+Og1WPCpNeSqrBRA==$yTiD/PNcz1u3d+X2cn+hSoE8957S621BwQ2JfsQ/fz4=:E0YTyVg2H2e37rSudX72hW0+RcwcH9CLMa3FFD6vIUk=
 old_app | md5b114b1c8396959cc98d37c893170248d
```

md5 값은 `md5(비밀번호 + 역할 이름)` 하나다. 솔트가 역할 이름이라 다른 서버에서 같은 이름과 비밀번호를 쓰면 해시도 같고, 무엇보다 md5 인증은 이 해시만 알면 비밀번호를 몰라도 로그인할 수 있다. 해시가 사실상 비밀번호다. SCRAM은 무작위 솔트(`WpBf...`)와 4096번 반복으로 만든 키를 저장하고, 로그인할 때도 비밀번호나 저장된 값을 보내지 않고 서로 증명만 주고받는다. 서버가 유출돼도 저장된 값으로 바로 로그인하지 못한다.

md5로 저장된 역할을 옮기려면 `password_encryption`이 `scram-sha-256`인 상태에서 비밀번호를 다시 설정하면 된다. `pg_hba.conf`에 `md5`라고 적힌 줄은 저장된 값이 SCRAM이면 SCRAM으로 인증하니, 비밀번호를 모두 바꾼 다음 줄을 `scram-sha-256`으로 바꾼다. 최신 버전에서 md5 비밀번호가 어떻게 취급되는지는 버전 노트에서 확인한다(제거 예정으로 안내되고 있다).

비밀번호를 SQL로 바꿀 때 조심할 점이 하나 있다. `log_statement = 'ddl'`이 켜진 서버에서 `ALTER ROLE ... PASSWORD`를 치면 로그에 평문이 남는다.

```text
2026-10-17 16:26:46.006 UTC [11357] postgres@shop LOG:  statement: ALTER ROLE old_app PASSWORD 'new-secret-2026'
```

psql의 `\password old_app`은 클라이언트에서 SCRAM 값을 만들어 해시만 보내서 이 문제가 없다. 셸 기록(`~/.bash_history`)과 psql 기록(`~/.psql_history`)에도 남지 않는다.

## pg_hba.conf와 TLS로 들어오는 길 좁히기

권한은 들어온 다음의 이야기이고, 들어오는 길 자체는 `pg_hba.conf`가 정한다. 읽는 방법은 [접속 글](/posts/postgres-connections-pg-hba)에서 봤다. 위에서부터 첫 번째로 맞는 줄 하나가 결정한다. 서점의 운영용 명부는 이렇게 쓸 수 있다. 앱 서버는 `10.0.1.0/24`, 배포 서버는 `10.0.2.10` 한 대, 복제 서버는 `10.0.3.0/24`다.

```text
# TYPE    DATABASE        USER            ADDRESS          METHOD
local     all             postgres                         peer
hostssl   shop            api,analyst     10.0.1.0/24      scram-sha-256
hostssl   shop            shop_migrator   10.0.2.10/32     scram-sha-256
hostssl   replication     replicator      10.0.3.0/24      scram-sha-256
host      all             all             0.0.0.0/0        reject
host      all             all             ::/0             reject
```

줄마다 DB와 역할과 주소를 좁혔다. 마이그레이션 역할은 배포 서버 한 대에서만 들어온다. 앱 서버가 털려도 그 서버에서 `shop_migrator`로는 못 붙는다. 외부 접속은 모두 `hostssl`이라 평문 접속은 어느 허용 줄에도 맞지 않고, 마지막 `reject`가 나머지를 명시적으로 거절한다. 슈퍼유저는 서버 안에서 `peer`로만 들어온다. reload한 뒤 `pg_hba_file_rules`로 서버가 읽은 내용과 `error` 칸을 확인한다. 이 명부에서는 `localhost`로 들어오는 TCP 접속도 마지막 줄에 걸린다.

```text
psql: error: connection to server at "localhost" (127.0.0.1), port 5491 failed: FATAL:  pg_hba.conf rejects connection for host "127.0.0.1", user "api", database "shop", SSL encryption
```

<Callout kind="warning" title="trust는 비밀번호 없이 누구든 그 역할로 들여보낸다">
`trust`는 "그 줄에 맞으면 확인 없이 통과"다. 비밀번호를 잊었다고 `host all all 127.0.0.1/32 trust`를 맨 위에 넣고 reload하면, 실습에서 그랬듯 `psql -h localhost -U postgres`가 비밀번호 없이 슈퍼유저로 들어온다. 그 서버에 접속할 수 있는 모든 프로세스(웹 서버, 컨테이너 안의 앱)가 슈퍼유저가 된다. 비밀번호를 다시 정해야 하면 `sudo -u postgres psql`(peer)로 들어가 `\password`를 쓴다. 이미 `trust`를 넣었다면 그 줄을 지우고 바로 `reload`한 뒤, 그 사이의 접속을 `log_connections` 로그에서 확인한다.
</Callout>

### sslmode는 verify-full로

`hostssl`로 TLS를 강제해도 클라이언트가 서버 인증서를 검증하지 않으면 반쪽이다. 클라이언트의 기본값 `sslmode=prefer`와 흔히 쓰는 `require`는 암호화만 하고 상대가 진짜 내 DB인지는 확인하지 않는다. 중간에서 가짜 서버가 끼어들면 그대로 비밀번호 증명과 데이터를 주고받는다. `verify-ca`는 인증서가 믿는 CA가 서명한 것인지, `verify-full`은 거기에 더해 인증서의 이름이 접속한 호스트 이름과 맞는지까지 본다.

서버 쪽은 `ssl = on`과 인증서·키 파일 경로다. Ubuntu 패키지는 설치할 때 만든 자체 서명 인증서를 쓴다.

```sql
SHOW ssl_cert_file;               -- /etc/ssl/certs/ssl-cert-snakeoil.pem
SHOW ssl_min_protocol_version;    -- TLSv1.2 (13부터 기본값)
```

운영에서는 사내 CA나 공인 CA가 발급한 인증서로 바꾸고, 클라이언트에 그 CA 인증서를 준다. `verify-full`로 접속하는 세 가지 경우를 보자.

```bash
# CA 인증서를 안 줬다
psql "host=localhost dbname=shop user=api sslmode=verify-full"

# CA 인증서를 줬다 (여기서는 자체 서명 인증서가 곧 CA)
psql "host=localhost dbname=shop user=api sslmode=verify-full sslrootcert=/etc/ssl/certs/ssl-cert-snakeoil.pem"

# 인증서는 맞는데 접속한 이름이 인증서 이름(localhost)과 다르다
psql "host=192.0.2.2 dbname=shop user=api sslmode=verify-full sslrootcert=/etc/ssl/certs/ssl-cert-snakeoil.pem"
```

```text
psql: error: connection to server at "localhost" (127.0.0.1), port 5491 failed: root certificate file "/root/.postgresql/root.crt" does not exist
Either provide the file, use the system's trusted roots with sslrootcert=system, or change sslmode to disable server certificate verification.

 ssl | version
-----+---------
 t   | TLSv1.3
(1 row)

psql: error: connection to server at "192.0.2.2", port 5491 failed: server certificate for "localhost" (and 1 other name) does not match host name "192.0.2.2"
```

첫 번째 에러 메시지가 방법을 알려 준다. CA 인증서를 `~/.postgresql/root.crt`에 두거나 `sslrootcert`로 경로를 주고, 공인 CA 인증서라면 PostgreSQL 16부터 `sslrootcert=system`으로 운영체제의 신뢰 저장소를 쓴다. 세 번째처럼 IP로 접속하면서 인증서에 DNS 이름만 있으면 실패하니, 인증서의 이름(SAN)과 접속 문자열의 호스트를 맞춘다. 클라우드 DB(RDS 등)는 CA 번들을 내려받아 `sslrootcert`에 주는 방식이다.

## 서점마다 자기 주문만 보게 하기

서점 서비스가 커져서 여러 동네 책방이 입점하는 플랫폼이 됐다고 하자. 주문 테이블은 하나이고 `store_id`로 서점을 구분한다. 앱 코드의 모든 쿼리에 `WHERE store_id = ?`를 붙이면 되지만, 한 군데라도 빠뜨리면 다른 서점의 주문이 보인다. 행 단위 보안(Row Level Security, RLS)은 이 조건을 테이블에 붙여 둔다. 정책을 켜면 그 테이블을 읽고 쓰는 모든 쿼리에 DB가 조건을 자동으로 더한다.

```sql
-- shop_owner로
CREATE TABLE stores (id bigint PRIMARY KEY, name text NOT NULL);
INSERT INTO stores VALUES (1, '책방 하나'), (2, '책방 둘');
ALTER TABLE orders ADD COLUMN store_id bigint NOT NULL DEFAULT 1 REFERENCES stores (id);
UPDATE orders SET store_id = 2 WHERE id = 2;
CREATE INDEX orders_store_id_idx ON orders (store_id);

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;          -- RLS 켜기
CREATE POLICY store_isolation ON orders
  USING      (store_id = current_setting('app.store_id', true)::bigint)   -- 읽고 고치고 지울 수 있는 행
  WITH CHECK (store_id = current_setting('app.store_id', true)::bigint);  -- 새로 넣거나 바꾼 결과가 지켜야 할 조건
```

현재 서점이 누구인지는 세션 설정 `app.store_id`로 넘긴다. `app.`처럼 점이 들어간 이름은 사용자 정의 설정이라 아무 값이나 넣을 수 있다. `current_setting(이름, true)`의 두 번째 인자는 설정이 없을 때 에러 대신 NULL을 돌려 달라는 뜻이다. 조건이 NULL이면 거짓으로 취급되니 설정을 안 한 세션은 아무 행도 못 본다. 실수했을 때 다 보이는 게 아니라 아무것도 안 보이는 쪽으로 실패한다. `api`로 접속해서 확인한다.

```sql
SELECT id, store_id, status FROM orders ORDER BY id;    -- 설정 전
SET app.store_id = '1';
SELECT id, store_id, status FROM orders ORDER BY id;    -- 1번 서점
INSERT INTO orders (user_id, store_id) VALUES (1, 2);   -- 남의 서점 주문 만들기
UPDATE orders SET store_id = 2 WHERE id = 1;            -- 내 주문을 남의 서점으로 옮기기
UPDATE orders SET status = 'cancelled' WHERE id = 2;    -- 남의 서점 주문 고치기
```

```text
 id | store_id | status
----+----------+--------
(0 rows)

SET
 id | store_id | status
----+----------+---------
  1 |        1 | paid
  3 |        1 | shipped
(2 rows)

ERROR:  new row violates row-level security policy for table "orders"
ERROR:  new row violates row-level security policy for table "orders"
UPDATE 0
```

`USING`과 `WITH CHECK`가 다른 일을 한다는 게 보인다. 남의 서점 주문을 고치려는 마지막 문장은 에러가 아니라 `UPDATE 0`이다. `USING` 조건 때문에 그 행이 아예 안 보이니 고칠 대상이 없었다. 남의 서점으로 주문을 넣거나 옮기는 건 `WITH CHECK`가 결과 행을 검사해서 막았다. `WITH CHECK`를 빼면 `USING`과 같은 조건이 쓰이지만, 정책을 명령별로(`FOR SELECT`, `FOR INSERT` …) 나눠 만들 때는 직접 챙겨야 한다.

RLS는 마법이 아니라 WHERE 조건이다. 실행 계획을 보면 정책 조건이 쿼리 조건과 함께 붙어 있다.

```sql
EXPLAIN (COSTS OFF) SELECT * FROM orders WHERE status = 'paid';
```

```text
                                                     QUERY PLAN
--------------------------------------------------------------------------------------------------------------------
 Seq Scan on orders
   Filter: ((store_id = (current_setting('app.store_id'::text, true))::bigint) AND (status = 'paid'::order_status))
(2 rows)
```

그래서 성능도 WHERE 조건과 똑같이 다룬다. 지금은 주문이 세 줄이라 `Seq Scan`이지만, 주문이 많아지면 `store_id`(또는 `store_id`로 시작하는 복합 인덱스)로 인덱스를 탈 수 있어야 한다. 위에서 `orders_store_id_idx`를 만든 이유다. 정책 조건에 무거운 함수나 서브쿼리를 넣으면 모든 쿼리가 그만큼 느려진다.

### 커넥션 풀에서는 SET LOCAL

웹 서버는 커넥션을 풀에 두고 요청마다 돌려 쓴다. 요청 A가 `SET app.store_id = '1'`을 하고 커넥션을 돌려주면, 그 커넥션을 받은 요청 B도 1번 서점으로 보인다. 세션 설정은 커넥션이 끊길 때까지 남기 때문이다. 그래서 트랜잭션 안에서 `SET LOCAL`(또는 `set_config('app.store_id', '2', true)`)을 쓴다. 트랜잭션이 끝나면 원래 값으로 돌아간다. 아래 그림에서 다음을 누르면 요청 하나가 지나는 순서가 나온다.

### 주인과 슈퍼유저는 정책을 건너뛴다

RLS에는 예외가 있다. 테이블 주인, 슈퍼유저, `BYPASSRLS` 속성을 가진 역할은 정책을 적용받지 않는다.

```sql
SET ROLE shop_owner;
SELECT count(*) AS owner_sees FROM orders;              -- 주인: 정책 무시
ALTER TABLE orders FORCE ROW LEVEL SECURITY;            -- 주인에게도 정책 적용
SELECT count(*) AS owner_sees_forced FROM orders;
ALTER TABLE orders NO FORCE ROW LEVEL SECURITY;
RESET ROLE;
SELECT count(*) AS superuser_sees FROM orders;          -- 슈퍼유저는 FORCE와 상관없이 다 본다
```

```text
 owner_sees
------------
          3
(1 row)

 owner_sees_forced
-------------------
                 0
(1 row)

 superuser_sees
----------------
              3
(1 row)
```

앱이 테이블 주인으로 접속하면 RLS를 아무리 잘 짜도 다 보인다. 처음 장면의 구성(앱 = 주인)에서는 RLS도 소용이 없다는 뜻이다. `FORCE ROW LEVEL SECURITY`는 주인에게도 정책을 적용하는데, 그러면 주인 역할로 도는 배치 작업도 설정 없이는 0건이 되니 의도를 정하고 쓴다.

뷰도 조심해야 한다. 뷰는 기본으로 뷰 주인의 권한으로 테이블을 읽는다. `shop_owner`가 만든 뷰를 `api`가 읽으면, 테이블을 읽는 건 주인이라 정책이 빠진다. PostgreSQL 15부터는 `security_invoker` 옵션으로 호출한 사람 권한으로 읽게 할 수 있다.

```sql
-- shop_owner가 만든 두 뷰
CREATE VIEW order_summary AS SELECT id, store_id, status FROM orders;
CREATE VIEW order_summary_safe WITH (security_invoker = true) AS SELECT id, store_id, status FROM orders;

-- api로, app.store_id = '1' 상태에서
SELECT * FROM order_summary ORDER BY id;
SELECT * FROM order_summary_safe ORDER BY id;
```

```text
 id | store_id | status
----+----------+---------
  1 |        1 | paid
  2 |        2 | pending
  3 |        1 | shipped
(3 rows)

 id | store_id | status
----+----------+---------
  1 |        1 | paid
  3 |        1 | shipped
(2 rows)
```

첫 번째 뷰로 2번 서점의 주문이 새어 나왔다. RLS를 쓰는 테이블 위의 뷰는 `security_invoker = true`로 만든다. 전체 데이터를 봐야 하는 고객 지원 도구 같은 역할에는 `CREATE ROLE support_tool LOGIN BYPASSRLS`처럼 속성을 따로 준다. 이 역할은 `app_ro` 권한만 받아도 3건을 다 본다. 누가 정책을 건너뛰는지가 역할 목록(`\du`의 `Bypass RLS`)에 드러나니, 이 속성을 가진 역할은 적게 둔다.

## 누가 언제 들어왔는지 남기기

권한을 아무리 잘 나눠도 사고는 난다. 그때 "누가, 어디서, 무엇을"을 답할 수 있어야 한다. 기본 로그 설정으로 시작한다.

```sql
ALTER SYSTEM SET log_connections = on;          -- 접속과 인증 결과
ALTER SYSTEM SET log_disconnections = on;       -- 접속 종료와 세션 시간
ALTER SYSTEM SET log_statement = 'ddl';         -- CREATE, ALTER, DROP 문장
SELECT pg_reload_conf();
```

```text
2026-10-17 16:26:45.967 UTC [11354] api@shop LOG:  connection authenticated: identity="api" method=scram-sha-256 (/etc/postgresql/16/pg1/pg_hba.conf:125)
2026-10-17 16:26:45.967 UTC [11354] api@shop LOG:  connection authorized: user=api database=shop application_name=psql SSL enabled (protocol=TLSv1.3, cipher=TLS_AES_256_GCM_SHA384, bits=256)
```

어느 `pg_hba.conf` 줄로, 어떤 인증 방식으로, TLS로 들어왔는지까지 남는다. Ubuntu의 기본 `log_line_prefix`(`%m [%p] %q%u@%d `)가 시각, 프로세스 번호, `역할@DB`를 앞에 붙여 준다. 접속 IP도 남기려면 `%h`를 더한다. `log_statement = 'all'`은 모든 쿼리를 남겨서 로그가 감당이 안 되고, 앞에서 본 것처럼 비밀번호 같은 값도 그대로 찍히니 운영에서는 `ddl` 정도로 둔다.

"누가 어느 테이블의 행을 읽었나"까지 감사(audit)해야 하면 `pgaudit` 확장을 쓴다. Ubuntu에서는 `postgresql-16-pgaudit` 패키지를 설치하고 `shared_preload_libraries = 'pgaudit'`로 올린 뒤(재시작 필요) `pgaudit.log = 'ddl, role, write'`처럼 남길 종류를 고른다. 테이블 단위로 읽기 감사를 거는 방법도 있다. 감사 로그는 양이 많으니 남길 범위를 정하고 로그 서버로 내보낸다.

## SQL 인젝션은 권한보다 앞에서 막는다

지금까지의 권한은 인젝션이 일어났을 때 피해를 줄이는 장치다. 인젝션 자체는 쿼리를 문자열로 이어 붙이지 않는 것으로 막는다. 이메일로 회원을 찾는 코드가 입력값을 그대로 붙였다고 하자. 입력이 `x' OR '1'='1`이면 이런 쿼리가 된다.

```sql
SELECT id, name FROM users WHERE email = 'x' OR '1'='1';
```

```text
 id |  name
----+--------
  1 | 김민지
  2 | 이준호
  3 | 박서연
  4 | 최유진
  5 | 정하준
(5 rows)
```

준비된 문장(prepared statement)은 쿼리 모양과 값을 따로 보낸다. 서버는 쿼리를 먼저 해석하고, 값은 나중에 자리(`$1`)에 넣으니 값이 쿼리 문법이 될 수 없다.

```sql
PREPARE find_user(text) AS SELECT id, name FROM users WHERE email = $1;
EXECUTE find_user('x'' OR ''1''=''1');     -- 같은 입력을 값으로
EXECUTE find_user('kim@example.com');
```

```text
 id | name
----+------
(0 rows)

 id |  name
----+--------
  1 | 김민지
(1 row)
```

드라이버의 파라미터 바인딩(`$1`, `?`)과 ORM이 이 방식이다. 테이블 이름이나 정렬 컬럼처럼 바인딩할 수 없는 자리는 허용 목록에서 고르고, DB 함수 안에서 동적 SQL을 만들 때는 `format('... %I ... %L', 이름, 값)`으로 식별자와 리터럴을 따옴표 처리한다. 그다음 피해 범위를 줄이는 게 앞에서 만든 역할 구성이다. 앱 역할이 테이블 주인이 아니면 인젝션이 있어도 `DROP TABLE`은 안 된다.

## pg_hba 줄 고르기를 직접 구현해 보기

`pg_hba.conf`가 어떤 줄을 고르는지 함수로 만들어 보자. 규칙 배열과 접속 정보를 받아 처음 맞는 줄의 번호(1부터)와 방법을 `{ line, method }`로 돌려주고, 맞는 줄이 없으면 `null`(`no pg_hba.conf entry`)이다. 접속은 `local`(소켓 여부), `ssl`, `ip`, `database`, `user`, `groups`(속한 그룹 역할 목록)를 가진다. 규칙의 `database`와 `user`는 쉼표로 여러 개를 쓸 수 있고, `all`, `sameuser`(DB 이름 = 역할 이름), `+그룹`(그 그룹의 멤버)을 지원한다. 주소는 IPv4 CIDR만 다룬다.

## 앱 계정이 할 수 있는 일

처음의 `matt`는 테이블 주인이라 무엇이든 할 수 있었다. 이제 서점 DB는 로그인하지 않는 `shop_owner`가 소유하고, 앱은 `app_rw`에서 받은 네 가지 권한(`arwd`)만으로 일한다. 테이블은 마이그레이션 역할이 `SET ROLE shop_owner`로 만들고, 기본 권한이 새 테이블에도 같은 권한을 붙인다. 들어오는 길은 `pg_hba.conf`의 좁은 `hostssl` 줄과 `verify-full`로 막고, 서점 사이의 경계는 RLS가 쿼리마다 조건을 붙여 지킨다. 다음 글에서는 이 서점 DB로 PostgreSQL다운 SQL(`RETURNING`, `ON CONFLICT`, CTE, `LATERAL`)을 쓴다.

## 면접에서 나올 만한 질문

### PostgreSQL에서 사용자와 그룹은 어떻게 다른가요?

따로 없고 둘 다 역할이다. `LOGIN` 속성이 있으면 사용자처럼 접속에 쓰고, 다른 역할을 멤버로 두면 그룹처럼 권한을 묶는다. 멤버는 기본으로 그룹 권한을 상속하고, `SET ROLE`로 그 역할이 될 수도 있다. 16부터는 멤버십마다 INHERIT와 SET을 따로 켜고 끌 수 있어서, 평소엔 권한이 없다가 필요할 때만 `SET ROLE`하게 만들 수 있다.

### 앱 계정이 테이블 주인이면 무엇이 문제인가요?

주인은 GRANT와 상관없이 자기 테이블을 `DROP`, `ALTER`, `TRUNCATE`할 수 있어서 인젝션이나 실수 한 번에 스키마가 날아간다. RLS도 주인에게는 기본으로 적용되지 않는다. 그래서 주인은 NOLOGIN 역할로 두고, 앱은 SELECT·INSERT·UPDATE·DELETE만 받은 그룹의 멤버로 접속한다. 스키마 변경은 마이그레이션 역할이 주인 역할로 바꿔서 한다.

### GRANT SELECT ON ALL TABLES를 했는데 새 테이블이 안 읽히는 이유는요?

`ON ALL TABLES`는 실행한 순간의 테이블에만 적용되기 때문이다. 앞으로 만들 객체는 `ALTER DEFAULT PRIVILEGES`로 정해야 한다. 또 기본 권한은 `FOR ROLE`에 적은 역할이 만든 객체에만 붙어서, 마이그레이션 역할이 상속만으로 테이블을 만들면 주인이 마이그레이션 역할이 되고 기본 권한이 안 붙는다. `SET ROLE shop_owner` 후에 만들거나 역할 설정으로 고정한다.

### md5와 scram-sha-256의 차이는요?

md5는 `md5(비밀번호+역할 이름)` 하나를 저장해서 같은 조합이면 해시가 같고, md5 인증은 그 해시만 있으면 로그인할 수 있어 해시가 비밀번호와 다름없다. SCRAM은 무작위 솔트와 반복으로 만든 키를 저장하고 인증 때 서로 증명만 주고받아서, 저장값이 유출돼도 바로 로그인하지 못하고 통신을 엿봐도 비밀번호를 얻지 못한다. 14부터 기본값이 scram-sha-256이고, 옮길 때는 비밀번호를 다시 설정한 뒤 `pg_hba.conf`를 바꾼다.

### sslmode=require면 안전한가요?

암호화는 되지만 서버 인증서를 검증하지 않아서 중간자가 가짜 서버로 끼어드는 걸 못 막는다. `verify-ca`는 믿는 CA의 서명인지, `verify-full`은 거기에 인증서 이름과 접속한 호스트 이름이 맞는지까지 확인한다. 운영에서는 `verify-full`에 `sslrootcert`로 CA를 주고, 16부터는 공인 CA면 `sslrootcert=system`을 쓸 수 있다. 서버 쪽은 `pg_hba.conf`를 `hostssl`로 써서 평문 접속을 받지 않는다.

### RLS로 멀티 테넌트를 구현할 때 주의할 점은요?

테이블 주인, 슈퍼유저, BYPASSRLS 역할은 정책을 건너뛰니 앱은 주인이 아닌 역할로 접속해야 하고, 주인에게도 걸려면 `FORCE ROW LEVEL SECURITY`를 쓴다. 테넌트 값은 커넥션 풀에서 새지 않게 트랜잭션 안의 `SET LOCAL`로 넘기고, 설정이 없으면 `current_setting(..., true)`가 NULL을 줘서 아무것도 안 보이게 만든다. 기본 뷰는 뷰 주인 권한으로 읽어 정책이 빠지니 `security_invoker = true`로 만든다. 정책은 결국 WHERE 조건이라 테넌트 컬럼에 인덱스가 필요하다.

### USING과 WITH CHECK는 어떻게 다른가요?

`USING`은 기존 행 중 어떤 행을 보고 고치고 지울 수 있는지를 정하고, `WITH CHECK`는 INSERT나 UPDATE의 결과 행이 지켜야 할 조건이다. 실습에서 남의 서점 주문을 고치는 UPDATE는 `USING` 때문에 대상이 안 보여 `UPDATE 0`이 됐고, 내 주문을 남의 서점으로 옮기는 UPDATE는 `WITH CHECK`가 `new row violates row-level security policy`로 막았다. 명령별로 정책을 나누면 둘을 각각 챙겨야 한다.

### SQL 인젝션은 DB 권한으로 막을 수 있나요?

막는 건 준비된 문장과 파라미터 바인딩이다. 쿼리 모양과 값을 따로 보내니 값이 문법이 될 수 없다. 권한은 인젝션이 생겼을 때 피해 범위를 줄인다. 앱 역할이 주인이 아니면 `DROP TABLE`은 안 되고, RLS가 있으면 다른 테넌트 행은 기본으로 안 보인다. 다만 앱 역할은 `SET`을 할 수 있어서 RLS 설정값도 인젝션으로 바뀔 수 있으니 RLS를 인젝션 방어로 믿으면 안 된다.
