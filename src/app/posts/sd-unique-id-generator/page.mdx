쇼핑몰 주문 DB를 샤드 네 개로 나눈 다음 날, 고객센터에서 문의가 왔다. 주문 번호 1001로 검색했더니 주문이 두 건 나온다고 한다. 하나는 서울 고객의 신발, 하나는 부산 고객의 냉장고다. 원인은 단순하다. 샤드마다 자동 증가 열이 각자 1부터 세고 있었다. [⑧ 샤딩 입문](/posts/sd-sharding-intro)의 끝에서 미뤄 둔 문제가 이것이다.

DB 한 대일 때는 번호 매기기가 문제가 아니었다. DB가 하나뿐이니 "지금까지 몇 번까지 줬나"를 아는 곳도 하나였다. 서버가 여러 대가 되면 그 기억을 누가 들고 있을지부터 정해야 한다. 이 글은 면접 단골 질문인 "분산 시스템에서 고유 ID 생성기를 설계하라"를 따라, 가장 단순한 방법에서 시작해 무엇이 깨지는지 하나씩 본다.

## 어떤 번호가 필요한지부터 정한다

설계 면접이든 실무든 먼저 번호의 조건을 정한다. 조건에 따라 답이 완전히 달라지기 때문이다. 이 글에서는 주문, 리뷰, 메시지 같은 행에 붙일 번호로 다음을 요구한다고 하자.

- 어느 서버에서 만들어도 겹치지 않는다.
- 64비트 정수에 들어간다. PostgreSQL의 `bigint`, 자바의 `long`처럼 8바이트다. 기본 키는 인덱스에 들어가고 다른 테이블의 외래 키로도 복사되니 작을수록 좋다.
- 대략 시간 순서로 커진다. 번호로 정렬하면 최근 것이 뒤에 온다. 꼭 1씩 늘 필요는 없다.
- 초당 2만 개 이상 만들 수 있다. 저녁 피크에 주문, 결제, 알림 행이 함께 쏟아진다고 보고 넉넉히 잡았다.

시간 순서가 왜 필요할까. "최근 주문 20개"는 `ORDER BY id DESC LIMIT 20`이 가장 싸다. 그리고 새 번호가 늘 B-tree 인덱스의 오른쪽 끝에 붙어서 인덱스 페이지가 덜 쪼개진다. 무작위 번호가 인덱스에 어떤 부담을 주는지는 [키와 반정규화](/posts/db-keys-denormalization)에서 100만 줄로 재 봤다.

## 샤드마다 홀짝으로 나눠 세기

가장 먼저 떠오르는 고치기는 DB마다 출발점과 간격을 다르게 주는 것이다. DB가 두 대면 A는 1, 3, 5로, B는 2, 4, 6으로 센다. 간격이 DB 수와 같으니 절대 겹치지 않는다. 여러 DB가 각자 쓰기를 받는 구성을 멀티 마스터라고 부르는데, 그 구성에서 쓰는 방법이다. PostgreSQL 16의 시퀀스로 흉내 내 봤다.

```sql
-- 서버 A, B가 같은 테이블에 번호를 매긴다고 치고 시퀀스를 하나씩 준다
CREATE SEQUENCE seq_a START 1 INCREMENT 2;   -- A: 1, 3, 5, ...
CREATE SEQUENCE seq_b START 2 INCREMENT 2;   -- B: 2, 4, 6, ...
SELECT nextval('seq_a') AS a1, nextval('seq_a') AS a2, nextval('seq_b') AS b1;
-- A만 바빠서 50개를 더 받은 뒤, B가 하나를 받는다
SELECT max(n) AS a_last FROM (SELECT nextval('seq_a') AS n FROM generate_series(1, 50)) s;
SELECT nextval('seq_b') AS b_next;
```

```text
 a1 | a2 | b1 
----+----+----
  1 |  3 |  2
(1 row)

 a_last 
--------
    103
(1 row)

 b_next 
--------
      4
(1 row)
```

겹치지는 않는다. 그런데 마지막 두 결과를 보자. A가 103번을 준 뒤에 B가 준 번호가 4다. 나중에 생긴 주문이 훨씬 작은 번호를 받았다. 트래픽이 한쪽으로 쏠리면 번호와 시간 순서가 쉽게 어긋난다. MySQL에서는 같은 일을 `auto_increment_increment`와 `auto_increment_offset` 설정으로 한다.

## 번호표를 한 곳에서 나눠 주기

은행 창구의 번호표 기계를 떠올려 보자. 창구가 몇 개든 번호표 기계가 하나라 번호가 겹치지 않는다. 같은 생각으로 번호만 나눠 주는 DB를 따로 하나 둔다. 이런 서버를 티켓 서버라고 부른다. Flickr가 2010년쯤 MySQL 두 대로 이렇게 운영한다고 공개한 글이 널리 알려져 있다.

단순하고 번호도 1씩 깔끔하게 는다. 대신 주문 하나를 저장할 때마다 티켓 서버까지 왕복이 하나 더 생기고, 모든 쓰기가 이 서버 하나를 거친다. 이 서버가 죽으면 서비스 전체가 새 행을 만들 수 없다. 이렇게 하나가 죽으면 전체가 멈추는 지점을 단일 장애점(SPOF, single point of failure)이라고 한다.

두 문제를 줄이는 흔한 방법은 번호를 묶음으로 받는 것이다. 웹 서버가 한 번에 1,000개짜리 구간을 받아 두고 메모리에서 하나씩 쓴다.

```sql
-- 티켓 서버가 1000개씩 구간을 나눠 준다
CREATE SEQUENCE ticket_block INCREMENT 1000;
SELECT nextval('ticket_block') AS web1_from, nextval('ticket_block') AS web2_from;
```

```text
 web1_from | web2_from 
-----------+-----------
         1 |      1001
```

web 1은 1~1000을, web 2는 1001~2000을 쓴다. 이제 티켓 서버는 1,000번에 한 번만 불린다. 그 사이에 티켓 서버가 잠깐 죽어도 받아 둔 구간을 다 쓸 때까지는 버틴다. 대가는 순서다. web 2가 1500번을 쓰는 동안 web 1은 아직 300번을 쓰고 있을 수 있다. 웹 서버가 재시작하면 쓰다 남은 구간은 버려져 번호에 구멍이 생긴다. 구멍은 문제가 되지 않는 경우가 많지만, 번호가 연속이라고 믿는 코드가 있다면 깨진다. 티켓 서버 자체를 두 대로 만들고 홀짝으로 나누면 SPOF는 줄지만, 앞 절의 순서 문제가 다시 돌아온다.

## 아무에게도 묻지 않는 UUID

묻는 곳이 있으니 느리고 죽는다. 그렇다면 아무에게도 묻지 않으면 어떨까. UUID(Universally Unique Identifier)는 128비트 값으로, 버전 4는 그중 122비트를 무작위로 채운다. 웹 서버마다 각자 만들어도 겹칠 확률이 사실상 없다. Node 22에서 다섯 개를 만들어 정렬해 봤다.

```js
// uuid.js: v4는 어디서나 만들 수 있지만 만든 순서와 정렬 순서가 다르다
const { randomUUID } = require("node:crypto");
const made = Array.from({ length: 5 }, () => randomUUID());
made.forEach((u, i) => console.log(`made #${i + 1}`, u));
console.log("sorted order:", [...made].sort().map((u) => made.indexOf(u) + 1).join(" "));
// 생일 문제 근사: n개 만들 때 한 쌍이라도 겹칠 확률 ≈ n^2 / 2^(bits+1)
const p = (n, bits) => (n * n) / 2 ** (bits + 1);
console.log("1e9 per sec for 1 year:", p(1e9 * 3600 * 24 * 365, 122).toExponential(2));
```

```text
made #1 b6501892-55c5-4b0e-b589-007332439f40
made #2 569c9e13-a466-4d84-a264-dfe954aa6337
made #3 fb284a06-df5c-40ac-8cd9-4721db3110f1
made #4 5e2c767e-2d00-4211-a3a5-3383015ad2dc
made #5 bf6b85b5-b376-447c-9985-77a7bc5831ea
sorted order: 2 4 1 5 3
length: 36 chars, bits: 128 (random 122)
1e9 per sec for 1 year: 9.35e-5
```

초당 10억 개씩 1년을 만들어도 한 쌍이라도 겹칠 확률이 0.01% 정도다. 겹침 걱정은 접어도 된다. 문제는 나머지 조건이다. 만든 순서는 1, 2, 3, 4, 5인데 정렬하면 2, 4, 1, 5, 3이 된다. 시간 순서가 없다. 그리고 128비트라 64비트 조건을 넘고, 문자열로 다루면 36글자다.

시간 순서는 UUID 버전 7로 해결된다. 앞 48비트에 밀리초 단위 시각을 넣어서 정렬하면 만든 순서와 거의 같다. 2024년에 RFC 9562로 표준이 됐고, PostgreSQL에서 쓰는 법과 인덱스 크기 차이는 [PostgreSQL 데이터 타입](/posts/postgres-data-types)에 있다. 다만 v7도 128비트다. 64비트라는 조건이 꼭 필요하지 않다면, 실무에서는 v7이 가장 손이 덜 가는 답이다. 64비트가 꼭 필요하다면 다음 방법으로 간다.

## 64비트를 칸으로 나눠 담기

Twitter가 2010년에 공개한 Snowflake는 64비트 정수를 몇 개의 칸으로 나눠, 칸마다 다른 정보를 담는다. 앞쪽 칸에 시각을 넣으니 시간 순서로 정렬되고, 중간 칸에 기계 번호를 넣으니 서로 다른 기계는 절대 겹치지 않고, 마지막 칸에 순번을 넣으니 같은 기계가 같은 밀리초에 여러 개를 만들어도 겹치지 않는다. 기계는 아무에게도 묻지 않고 자기 시계와 자기 번호만으로 만든다.

비트 연산 몇 줄이면 만들고 다시 나눌 수 있다. 자바스크립트의 일반 숫자는 64비트 정수를 정확히 담지 못하니(뒤에서 다시 본다) `BigInt`로 계산했다.

```js
// snowflake.js: 64비트 = 1(부호) + 41(시각) + 5(DC) + 5(기계) + 12(순번)
const EPOCH = 1288834974657n;           // Twitter가 공개한 기준 시점
function make(ms, dc, machine, seq) {
  return ((BigInt(ms) - EPOCH) << 22n) | (BigInt(dc) << 17n) | (BigInt(machine) << 12n) | BigInt(seq);
}
function parse(id) {
  id = BigInt(id);
  return {
    time: new Date(Number((id >> 22n) + EPOCH)).toISOString(),
    dc: Number((id >> 17n) & 31n),
    machine: Number((id >> 12n) & 31n),
    seq: Number(id & 4095n),
  };
}
const ms = Date.parse("2026-10-22T01:00:00.000Z");
const id = make(ms, 3, 7, 5);
console.log("id      ", id.toString());
console.log("parsed  ", parse(id));
console.log("next ms ", make(ms + 1, 3, 7, 0).toString());
console.log("same ms, machine 8", make(ms, 3, 8, 0).toString());
```

```text
per machine per sec: 4096000  total machines: 1024
```

(`binary`와 마지막 두 줄은 같은 파일에서 출력만 더 한 것이다.) 시각을 22비트 왼쪽으로 민 이유는 그 아래에 데이터 센터 5, 기계 5, 순번 12, 합쳐 22비트가 들어가기 때문이다. 1밀리초 뒤의 번호는 순번이 0이어도 앞 번호보다 크다. 시각 칸이 위쪽에 있어서다. 같은 밀리초에 기계 8번이 만든 번호도 7번의 것과 다르다.

숫자도 따져 보자. 41비트로 셀 수 있는 밀리초는 약 69.7년이다. Twitter의 기준 시점에서 세면 2080년 7월에 칸이 넘친다. 그래서 자기 서비스를 시작하는 날을 기준 시점으로 정한다. 이걸 커스텀 에포크라고 한다. 1970년부터 세면 이미 56년을 써 버린 셈이라 손해다. 기계 하나는 1밀리초에 4,096개, 1초에 약 409만 개를 만들 수 있고, 기계는 1,024대까지 둘 수 있다. 처음에 잡은 초당 2만 개는 기계 한 대로도 넉넉하다.

## 1밀리초에 4,096개를 넘으면

순번 칸은 12비트라 0~4095까지다. 같은 밀리초에 4,097번째 요청이 오면 어떻게 할까. 번호를 만들 수 없으니 다음 밀리초가 될 때까지 기다린다. 길어야 1밀리초 미만이다. 시계가 거꾸로 가는 경우도 이 생성기가 직접 막아야 한다. 이 두 가지를 넣은 생성기다.

```js
// gen.js: 순번이 넘치면 다음 밀리초까지 기다리고, 시계가 뒤로 가면 거절한다
class Snowflake {
  constructor(dc, machine, now = () => Date.now()) {
    this.dc = BigInt(dc); this.machine = BigInt(machine); this.now = now;
    this.lastMs = -1; this.seq = 0; this.waits = 0;
  }
  next() {
    let ms = this.now();
    if (ms < this.lastMs) throw new Error(`clock moved backwards by ${this.lastMs - ms}ms`);
    if (ms === this.lastMs) {
      this.seq = (this.seq + 1) & 4095;
      if (this.seq === 0) {                 // 이번 밀리초의 4096개를 다 썼다
        this.waits++;
        while (ms <= this.lastMs) ms = this.now();   // 다음 밀리초까지 바쁘게 기다린다
      }
    } else this.seq = 0;
    this.lastMs = ms;
    return ((BigInt(ms) - EPOCH) << 22n) | (this.dc << 17n) | (this.machine << 12n) | BigInt(this.seq);
  }
}
// 한 기계에서 최대한 빨리 20만 개를 만든다
```

```text
200000 ids in 133ms, unique=200000, strictly increasing=true, waited for next ms 10 times
```

노트북 한 대의 Node 22에서 20만 개를 133ms에 만들었다. 모두 달랐고 앞 번호보다 늘 컸다. 그사이 4,096개를 한 밀리초 안에 다 써서 기다린 일이 10번 있었다. 아래 그림은 순번 칸이 밀리초 안에서 차오르고 넘치는 모양이다.

## 시계가 뒤로 가는 순간

Snowflake는 기계의 시계를 믿는다. 그런데 서버 시계는 조금씩 빨라지거나 느려져서, NTP(Network Time Protocol)라는 시간 맞추기 데몬이 주기적으로 바로잡는다. 오차가 크면 시계를 한 번에 뒤로 돌리기도 한다. 시계가 5ms 뒤로 가면 그 5ms 동안 만든 번호가 이미 준 번호와 겹칠 수 있다. 시계가 왜 어긋나고 chrony가 어떻게 맞추는지는 [시계 어긋남](/posts/clock-skew)에 자세히 있다.

위 생성기에 가짜 시계를 넣고 5ms 뒤로 돌려 봤다. 같은 기계 번호를 두 기계가 받은 경우도 함께 봤다.

```js
let fake = 1_800_000_000_000;
const h = new Snowflake(1, 2, () => fake);
console.log("t=fake      ", h.next().toString());
fake -= 5;   // NTP가 시계를 5ms 뒤로 돌렸다
try { h.next(); } catch (e) { console.log("t=fake-5ms  ", e.message); }
// 두 기계가 같은 기계 번호를 받으면
let f2 = 1_800_000_000_000;
const a = new Snowflake(1, 9, () => f2), b = new Snowflake(1, 9, () => f2);
console.log("same machine id, same ms:", a.next().toString(), b.next().toString());
```

```text
t=fake       2143981510456385536
t=fake-5ms   clock moved backwards by 5ms
same machine id, same ms: 2143981510456414208 2143981510456414208
```

생성기는 마지막으로 쓴 밀리초(`lastMs`)를 기억하고 있다가, 지금 시각이 그보다 작으면 거절했다. Twitter가 공개한 원래 구현도 이렇게 예외를 던지고 번호를 만들지 않았다. 거절 말고도 선택지가 있다.

뒤로 간 폭이 몇 밀리초 정도면 기다리는 게 가장 무난하다. 폭이 크면 그동안 이 기계가 번호를 못 만드니 거절하고, 로드 밸런서가 다른 기계로 요청을 돌리게 한다. 근본적으로는 NTP가 시계를 한 번에 돌리지 않고 천천히 늦추도록(slew) 설정해 둔다. 또 생성기가 꺼질 때 `lastMs`를 버리므로, 재시작 직후 시계가 뒤에 있으면 감지할 방법이 없다. 그래서 재시작한 생성기는 몇 밀리초 쉬었다가 시작하거나 마지막 시각을 디스크에 남겨 둔다.

## 기계 번호는 누가 나눠 주나

출력의 마지막 줄이 더 무섭다. 두 기계가 같은 기계 번호 9를 받으니, 같은 밀리초에 완전히 같은 번호가 나왔다. 시계 문제는 몇 밀리초짜리지만 기계 번호가 겹치면 계속 겹친다. 이 번호는 사람이 설정 파일에 손으로 적으면 언젠가 틀린다. 서버를 복제해 새로 띄울 때 설정까지 그대로 복사되기 쉽다.

흔한 방법은 서버가 시작할 때 etcd나 ZooKeeper 같은 조정 서비스에서 비어 있는 번호를 임대로 받는 것이다. 임대는 주기적으로 갱신해야 유지되니, 죽은 서버의 번호는 자연스럽게 돌아온다. 쿠버네티스라면 StatefulSet의 파드 순번(`orders-0`, `orders-1`)을 기계 번호로 쓰기도 한다. 어느 쪽이든 번호를 돌려받자마자 다른 서버에 주면 안 된다. 죽은 줄 알았던 서버가 네트워크만 끊겼다가 살아나면 같은 번호를 쓰는 서버가 둘이 된다. 임대가 끝난 뒤에도 시계 오차보다 넉넉한 시간을 비워 둔다.

조정 서비스는 시작할 때와 갱신할 때만 쓰이고, 번호 하나 만들 때마다 묻지 않는다. 티켓 서버와 가장 다른 점이다. 조정 서비스가 잠깐 죽어도 이미 번호를 받은 서버는 계속 일한다.

## 자바스크립트가 번호 끝자리를 바꾼다

Snowflake 번호를 API로 내보냈더니 웹 화면에서 주문 상세가 열리지 않는다는 버그가 들어온다. 이 번호를 JSON 숫자로 내보내고 브라우저가 읽으면 이렇게 된다.

```js
console.log("> 2^53? ", id > 2n ** 53n, " Number(id) =", Number(id), " back:", BigInt(Number(id)) === id);
console.log("JSON.parse:", JSON.parse(`{"id": ${id}}`).id);
```

```text
> 2^53?  true  Number(id) = 2113072845419868200  back: false
JSON.parse: 2113072845419868200
```

자바스크립트의 일반 숫자는 64비트 부동소수점이라 2^53(약 9천조)을 넘는 정수는 정확히 담지 못한다. 번호 끝의 `165`가 `200`으로 바뀌었다. 화면은 바뀐 번호로 주문을 다시 요청하니 404가 난다. 그래서 64비트 번호는 API에서 문자열로 내보낸다. Twitter API가 `id`와 함께 문자열인 `id_str`을 따로 내려 준 이유가 이것이다. 서버 코드가 자바나 Go라면 문제없이 다루지만, JSON을 거치는 순간 받는 쪽 언어를 생각해야 한다. JSON에서 큰 숫자 ID를 다루는 법은 [JSON으로 데이터 주고받기](/posts/json-crud-http)에 있다.

## 칸 크기는 서비스에 맞춘다

41, 5, 5, 12는 정답이 아니라 하나의 예다. 칸을 나누는 건 결국 64비트를 시간, 기계 수, 기계당 속도에 나눠 주는 일이다.

- 기계가 32대면 충분하다면 데이터 센터 칸을 없애고 기계 칸을 5비트로 줄인다. 남는 비트를 순번에 주면 기계당 밀리초 처리량이 늘어난다.
- 수명이 69년이나 필요 없다면 시각 칸을 줄인다. 대신 너무 줄이면 서비스가 살아 있는 동안 칸이 넘친다.
- 시각 단위를 밀리초 대신 10밀리초로 잡으면 같은 41비트로 약 700년을 쓴다. 대신 한 단위 안에서 더 많은 순번이 필요하다.

공개된 변형도 많다. Discord는 2015년 첫날을 기준 시점으로 쓰는 Snowflake를 문서에 공개해 두었다. Instagram은 2012년 엔지니어링 블로그에서 시각 41비트, 샤드 번호 13비트, 순번 10비트로 나누고 PostgreSQL 함수 안에서 번호를 만드는 방식을 소개했다. 기계 대신 샤드 번호를 넣으면 번호만 보고 어느 샤드에 있는지 바로 안다.

직접 만들어 보자. 밀리초 시각, 데이터 센터 번호, 기계 번호, 순번을 받아 Twitter 기준 시점의 Snowflake 번호를 문자열로 돌려주는 함수다. 일반 숫자로 비트 연산을 하면 32비트로 잘리니 `BigInt`를 써야 한다.

마지막 두 테스트를 비교해 보면, 같은 밀리초 안의 가장 큰 번호도 다음 밀리초의 가장 작은 번호(`2113072845424062464`)보다 작다. 시각 칸이 위에 있으니 시간 순서가 깨지지 않는다. 단, 이건 한 기계 안의 이야기다. 서로 다른 기계의 시계는 몇 밀리초씩 어긋나 있으니, 여러 기계가 만든 번호의 순서는 "대략" 시간 순서일 뿐이다. 두 이벤트의 앞뒤를 정확히 따져야 한다면 번호 순서에 기대지 않는다.

## 네 가지를 나란히 놓고 고르기

| | 홀짝 나눠 세기 | 티켓 서버 | UUID v4 / v7 | Snowflake |
|---|---|---|---|---|
| 크기 | 64비트 | 64비트 | 128비트 | 64비트 |
| 시간 순서 | 쏠리면 깨짐 | 거의 맞음 (묶음이면 느슨) | v4 없음, v7 있음 | 기계 안에서 맞음 |
| 만들 때 묻는 곳 | DB | 티켓 서버 | 없음 | 없음 (시작할 때 기계 번호만) |
| 약점 | 대수 바꾸기 | SPOF, 왕복 | 크기, v4의 인덱스 부담 | 시계, 기계 번호 관리 |

고르는 기준은 이렇게 정리된다. DB가 한 대라면 그냥 `bigint` 자동 증가가 가장 좋다. 여러 곳에서 만들어야 하고 128비트가 괜찮다면 UUID v7이 관리할 것이 가장 적다. 64비트가 꼭 필요하거나(기존 `bigint` 열, 저장 공간, 번호에 샤드 정보 넣기) 초당 수만 개를 지연 없이 만들어야 하면 Snowflake 계열을 쓴다. 번호가 1씩 연속이어야 하는 요구(예: 세금계산서 번호)라면 이 중 어느 것도 아니고, 한 곳에서 트랜잭션으로 매긴다.

## 다음에 읽을 글

여러 서버가 서로 묻지 않고 번호를 만들려면 번호 안에 "누가, 언제" 만들었는지를 넣으면 된다. Snowflake는 그것을 64비트 칸에 나눠 담고, 그 대가로 시계와 기계 번호를 관리하는 부담을 진다. 다음 글 [⑱ URL 단축기 ①](/posts/sd-url-shortener-api-redirect)은 이렇게 만든 번호를 짧은 주소로 바꾸는 서비스를 설계한다. 번호를 62진수 문자열로 바꾸는 부분은 [⑲ URL 단축기 ②](/posts/sd-url-shortener-key-generation)에서 이어진다. 시계 문제를 더 보고 싶다면 [시계 어긋남](/posts/clock-skew)으로 가면 된다.

## 면접에서 나올 만한 질문

### 분산 환경에서 DB 자동 증가 키를 그대로 쓰면 왜 안 되나요?

DB마다 따로 세면 같은 번호가 여러 DB에서 나온다. 간격과 출발점을 다르게 줘서 피할 수는 있지만, 트래픽이 한쪽에 몰리면 시간 순서가 깨지고 DB를 더하거나 뺄 때마다 간격을 다시 맞춰야 한다. 한 곳에서 세게 하면 그곳이 모든 쓰기의 병목이자 단일 장애점이 된다.

### UUID를 쓰면 되지 않나요?

겹치지 않는다는 조건만 보면 충분하다. 다만 128비트라 64비트 요구를 넘고, v4는 무작위라 시간 순서가 없어서 B-tree 인덱스의 아무 곳에나 들어가 쓰기 성능이 떨어진다. v7은 앞부분이 밀리초 시각이라 순서 문제는 풀리니, 64비트가 필수가 아니면 v7이 가장 관리할 것이 적은 답이다.

### Snowflake의 비트 구성을 설명해 주세요.

64비트를 부호 1비트, 기준 시점부터의 밀리초 41비트, 데이터 센터 5비트, 기계 5비트, 순번 12비트로 나눈다. 시각이 앞에 있어 정렬하면 시간 순서가 되고, 기계 번호 덕에 기계끼리 겹치지 않으며, 순번으로 같은 밀리초 안의 번호를 구분한다. 41비트는 약 69년이라 서비스 시작일을 기준 시점으로 잡는다.

### 한 기계가 1밀리초에 4,096개보다 많이 요청받으면요?

순번 칸이 꽉 차면 다음 밀리초가 될 때까지 기다렸다가 순번 0부터 다시 쓴다. 기다림은 1밀리초 미만이라 대개 문제가 되지 않는다. 그 정도 부하가 늘 온다면 기계를 늘리거나 데이터 센터 칸을 줄여 순번 칸에 비트를 더 준다.

### 시계가 뒤로 가면 어떻게 되나요?

마지막으로 쓴 밀리초보다 지금 시각이 작으면 이미 준 번호와 겹칠 수 있다. 생성기가 마지막 시각을 기억하고 있다가, 차이가 작으면 따라잡을 때까지 기다리고 크면 거절해 다른 기계로 넘긴다. 근본적으로는 NTP를 천천히 늦추는(slew) 모드로 두고, 재시작 직후에는 잠깐 쉬었다 시작하게 한다.

### 기계 번호가 겹치면 어떻게 되고, 어떻게 막나요?

같은 밀리초에 완전히 같은 번호가 계속 나온다. 사람이 설정 파일로 관리하지 않고, 시작할 때 etcd나 ZooKeeper에서 임대로 받게 한다. 임대가 끝난 번호는 죽은 줄 알았던 서버가 다시 살아날 수 있으니 한동안 비워 둔 뒤 다른 서버에 준다.

### 트래픽이 지금의 10배가 되면 어디가 먼저 문제가 되나요?

Snowflake는 기계마다 따로 만들기 때문에 생성기 자체는 기계를 늘리는 만큼 버틴다. 먼저 걸리는 건 기계 번호 칸이다. 5비트와 5비트면 1,024대가 한계라, 웹 서버마다 생성기를 두는 구조라면 그 수를 넘지 않게 생성기를 별도 서비스로 모으거나 칸 크기를 다시 정해야 한다. 칸 크기는 이미 나간 번호와 순서가 맞도록 시각 칸 위치를 유지한 채 바꾼다.

### 이 번호를 프런트엔드로 보낼 때 주의할 점이 있나요?

자바스크립트 숫자는 2^53을 넘는 정수를 정확히 담지 못해서 끝자리가 바뀐다. 그래서 64비트 번호는 JSON에 문자열로 내보낸다. 또 번호에 생성 시각이 들어 있으니, 주문 수 같은 정보를 숨겨야 한다면 외부 노출용 키를 따로 둔다.
