이 시리즈에서 이 글의 자리: [㊽ 이메일 서비스 설계 ①](/posts/sd-email-protocols)에서 메일이 SMTP로 서버 사이를 오가고, 받는 서버가 발신자를 검사하는 과정을 봤다. 이 글은 같은 장의 두 번째 글로, 받은 메일을 어디에 어떻게 담고 어떻게 찾는지를 설계한다. 다음 글부터는 새 장인 [㊿ 객체 저장소 설계 ①](/posts/sd-object-storage-architecture)이다. 이 글에서 첨부 파일을 맡기는 그 저장소를 직접 만든다.

메일 검색창에 "요금"을 쳤는데 지난달 클라우드 청구서가 나오지 않는다. 청구서 본문에는 분명히 "이번 달 사용 요금은 42,000원이다"라고 적혀 있다. 검색 엔진은 "요금은"이라는 낱말만 알고 있었고, "요금"과는 다른 낱말로 보았다.

이 글은 이런 문제를 하나씩 만나면서 메일 저장소를 키운다. 처음에는 메일을 어디에 둘지부터 정하고, 사용자가 많아지면 어떻게 나누는지, "안 읽은 메일만 보기"와 대화 묶기는 어떻게 하는지, 첨부 파일은 어디에 두는지, 마지막으로 내 메일함 안에서 단어를 찾는 색인을 만든다. 메타데이터 쿼리는 PostgreSQL 16에서, 검색과 첨부 실험은 Node 22에서 실제로 돌린 결과다.

## 메일 한 통을 성격대로 나눠 담는다

가장 작은 메일 서버는 메일 한 통을 파일 하나로 디스크에 저장한다. 사용자마다 폴더가 있고, 받은편지함 폴더에 새 파일이 생기면 새 메일이다. 사용자가 수백 명일 때는 잘 돈다. 사용자가 늘면 두 가지가 먼저 깨진다. 받은편지함을 열 때마다 파일 수천 개의 헤더를 읽어야 해서 디스크가 버티지 못하고, 그 서버의 디스크가 고장 나면 메일이 사라진다.

나누는 기준은 읽고 쓰는 모양이다. 목록 화면에는 보낸 사람, 제목, 시각, 읽음 여부만 있으면 된다. 이 값들은 작고, 메일함을 열 때마다 수십 개씩 읽히고, 읽음 표시나 폴더 이동으로 자주 바뀐다. 본문과 첨부는 크고, 쓴 뒤로 바뀌지 않고, 대개 한 번 열어 볼 때만 읽는다. 둘을 같은 곳에 두면 목록을 띄울 때 큰 본문까지 디스크에서 끌어오게 된다.

## 사용자 한 명의 메일은 한곳에

메타데이터 DB에 오는 질문을 적어 보면 공통점이 있다. "bob의 받은편지함 최신 20통", "bob의 안 읽은 메일 수", "bob의 메일 하나를 읽음으로", "bob의 메일을 보관함으로". 모든 질문에 사용자가 한 명씩 붙어 있다. 다른 사용자의 메일을 함께 보는 일은 거의 없다.

그래서 `user_id`를 기준으로 데이터를 나눈다. 한 사용자의 메일은 모두 같은 조각(파티션)에 있고, 조회는 그 조각 하나만 본다. PostgreSQL의 해시 파티셔닝으로 같은 모양을 만들어 봤다. 실제 서비스라면 조각 하나가 서버 한 대(샤드)가 되지만, 파티션 하나만 읽는다는 원리는 같다.

```sql
CREATE TABLE emails (
  user_id     bigint  NOT NULL,
  folder      text    NOT NULL,          -- inbox, sent, archive ...
  email_id    bigint  NOT NULL,          -- 시간순으로 커지는 id
  from_addr   text    NOT NULL,
  subject     text    NOT NULL,
  is_read     boolean NOT NULL DEFAULT false,
  body_key    text    NOT NULL,          -- 본문이 있는 객체 저장소 키
  PRIMARY KEY (user_id, folder, email_id)
) PARTITION BY HASH (user_id);
-- emails_p0 ~ emails_p7: 8개로 나눈다
CREATE TABLE emails_p0 PARTITION OF emails FOR VALUES WITH (MODULUS 8, REMAINDER 0);
-- ... p1 ~ p7 도 같은 모양

-- 사용자 2,000명 × 500통 = 100만 통
INSERT INTO emails
SELECT u, CASE WHEN n % 10 = 0 THEN 'archive' ELSE 'inbox' END, n,
       's' || (n % 97) || '@example.com', 'subject ' || n,
       n < 480 OR random() < 0.3, 'mail/' || u || '/' || n
FROM generate_series(1, 2000) u, generate_series(1, 500) n;

EXPLAIN (ANALYZE, COSTS OFF)
SELECT email_id, from_addr, subject, is_read FROM emails
WHERE user_id = 42 AND folder = 'inbox'
ORDER BY email_id DESC LIMIT 20;
```

```text
 Limit (actual time=0.225..0.360 rows=20 loops=1)
   ->  Index Scan Backward using emails_p2_pkey on emails_p2 emails (actual time=0.223..0.355 rows=20 loops=1)
         Index Cond: ((user_id = 42) AND (folder = 'inbox'::text))
 Planning Time: 3.016 ms
 Execution Time: 0.488 ms
```

두 가지를 보면 된다. 8개 파티션 중 `emails_p2` 하나만 읽었다. 그리고 `Index Scan Backward`로 기본 키를 거꾸로 따라가며 최신 20통을 꺼낸 뒤 바로 멈췄다. 정렬 단계가 따로 없다. 기본 키를 `(user_id, folder, email_id)` 순서로 잡았기 때문이다. 앞의 두 열이 "누구의 어느 폴더"를 정하고, 마지막 열이 그 안의 순서를 정한다.

`email_id`가 시간순으로 커져야 이 정렬이 공짜가 된다. 무작위 UUID라면 받은 시각 열을 따로 두고 인덱스를 하나 더 만들어야 한다. 시간이 앞부분에 들어가는 id는 [⑰ 고유 ID 생성기](/posts/sd-unique-id-generator)에서 만들었다.

Gmail 규모에서는 이 메타데이터를 관계형 DB보다 Bigtable이나 Cassandra 같은 와이드 컬럼 저장소에 두는 경우가 많다. 모양은 같다. "파티션 키"(`user_id`)가 데이터를 어느 서버에 둘지 정하고, "클러스터링 키"(`folder`, `email_id`)가 그 안의 정렬 순서를 정한다. 와이드 컬럼 저장소의 구조는 [와이드 컬럼 DB](/posts/db-type-wide-column)에 있다.

이렇게 나누면 사용자끼리 메일을 공유하는 기능(여러 사람이 함께 보는 공용 메일함)은 어려워진다. 한 메일이 여러 샤드에 걸치기 때문이다. 같은 메일을 여러 사람이 받으면 받는 사람마다 따로 한 줄씩 적는 것도 같은 이유다. 대신 메타데이터는 작으니 복사해도 부담이 적고, 큰 본문과 첨부는 아래에서 보듯 한 번만 저장할 수 있다.

## 안 읽은 메일만 보여 달라

목록 화면에 "안 읽은 메일만" 필터를 달았다. 같은 사용자에게 조건 하나만 더했는데 실행 계획이 달라졌다.

```sql
EXPLAIN (ANALYZE, COSTS OFF)
SELECT email_id, subject FROM emails
WHERE user_id = 42 AND folder = 'inbox' AND NOT is_read
ORDER BY email_id DESC LIMIT 20;
```

```text
 Limit (actual time=3.774..3.778 rows=11 loops=1)
   ->  Sort (actual time=3.773..3.775 rows=11 loops=1)
         Sort Key: emails.email_id DESC
         Sort Method: quicksort  Memory: 25kB
         ->  Bitmap Heap Scan on emails_p2 emails (actual time=3.614..3.640 rows=11 loops=1)
               Recheck Cond: ((user_id = 42) AND (folder = 'inbox'::text))
               Filter: (NOT is_read)
               Rows Removed by Filter: 439
               Heap Blocks: exact=450
               ->  Bitmap Index Scan on emails_p2_pkey (actual time=0.279..0.279 rows=450 loops=1)
                     Index Cond: ((user_id = 42) AND (folder = 'inbox'::text))
 Planning Time: 0.828 ms
 Execution Time: 3.838 ms
```

`Rows Removed by Filter: 439`가 문제다. 받은편지함 450통을 모두 읽은 뒤 읽은 메일 439통을 버렸다. `Heap Blocks: exact=450`은 그 450통이 서로 다른 450개 블록에 흩어져 있어서 블록을 450번 읽었다는 뜻이다. 메일함이 5만 통이면 5만 번이다. 오래 쓴 메일함일수록 대부분이 읽은 메일이라, 안 읽은 몇 통을 찾으려고 거의 전부를 읽게 된다.

PostgreSQL에서는 안 읽은 메일만 담는 부분 인덱스로 푼다.

```sql
CREATE INDEX emails_unread ON emails (user_id, folder, email_id) WHERE NOT is_read;
```

```text
 Limit (actual time=0.068..0.070 rows=11 loops=1)
   ->  Sort (actual time=0.067..0.068 rows=11 loops=1)
         Sort Key: emails.email_id DESC
         Sort Method: quicksort  Memory: 25kB
         ->  Bitmap Heap Scan on emails_p2 emails (actual time=0.040..0.055 rows=11 loops=1)
               Recheck Cond: ((user_id = 42) AND (folder = 'inbox'::text) AND (NOT is_read))
               Heap Blocks: exact=11
               ->  Bitmap Index Scan on emails_p2_user_id_folder_email_id_idx (actual time=0.032..0.032 rows=11 loops=1)
                     Index Cond: ((user_id = 42) AND (folder = 'inbox'::text))
 Planning Time: 0.310 ms
 Execution Time: 0.085 ms
```

블록을 11번만 읽었고 3.8ms가 0.085ms가 됐다. 안 읽은 메일만 들어 있으니 인덱스도 작다. 전체 기본 키 인덱스가 60MB일 때 이 인덱스는 1,312kB였다. 부분 인덱스를 고르는 기준은 [인덱스 설계](/posts/db-index-design)에 있다.

와이드 컬럼 저장소에는 부분 인덱스가 없고, 키가 아닌 열로 거르는 쿼리를 막아 두는 경우가 많다(Cassandra는 `ALLOW FILTERING` 없이는 거부한다). 그래서 같은 메일을 "읽은 메일 테이블"과 "안 읽은 메일 테이블"에 나눠 담는다. 읽음 표시는 한쪽에서 지우고 다른 쪽에 넣는 두 번의 쓰기가 된다. 읽기를 빠르게 하려고 쓰기를 늘리는 비정규화다. 둘 중 하나만 성공하면 메일이 사라지거나 두 번 보이니, 같은 파티션 안의 쓰기를 한 묶음(batch)으로 보낸다. 비정규화의 득실은 [키와 비정규화](/posts/db-keys-denormalization)에서 다뤘다.

## 답장끼리 대화로 묶는다

Gmail처럼 답장을 한 대화로 묶어 보여 주려면, 어떤 메일이 어떤 메일의 답장인지 알아야 한다. 제목의 "Re:"를 보고 묶으면 틀린다. 제목이 같은 다른 대화가 섞이고, 답장하면서 제목을 바꾸면 끊긴다. 대신 메일 헤더를 쓴다. 모든 메일에는 고유한 `Message-ID`가 있고, 답장에는 원래 메일을 가리키는 `In-Reply-To`와, 대화의 처음부터 지금까지의 `Message-ID` 목록인 `References`가 붙는다.


## 첨부 파일은 객체 저장소로

본문과 첨부는 S3 같은 객체 저장소에 두고, 메타데이터에는 그 키만 적는다. 객체 저장소는 파일 하나를 키 하나로 통째로 쓰고 읽으며, 용량을 거의 무한히 늘릴 수 있고, 내부에서 여러 벌로 복제해 잃지 않게 한다. 어떻게 만드는지는 [다음 장](/posts/sd-object-storage-architecture)에서 직접 설계한다.

여기서 하나 아낄 수 있다. 회사 공지에 2MB짜리 계획서를 붙여 50명에게 보내면, 받는 사람마다 같은 파일이 하나씩 생긴다. 파일 내용의 SHA-256 해시를 키로 쓰면 같은 내용은 한 번만 저장된다.

```js
const key = crypto.createHash("sha256").update(pdf).digest("hex");
if (!store.has(key)) store.set(key, { size: pdf.length, refs: 0 });
store.get(key).refs++;                       // 몇 통의 메일이 이 파일을 가리키나
refs.push({ mail: i, name: "2027-plan.pdf", key });
```

```text
메일마다 저장했다면: 100 MiB
내용 해시로 한 번만: 2 MiB, 참조 50 개
저장 키: 2a92a2e6396f772a…
한 바이트 다른 파일: 9848c068474b0344… 다른 키
```

참조 수를 세는 이유는 지울 때다. 50명 중 한 명이 메일을 지워도 파일은 남아야 하고, 마지막 참조가 사라졌을 때 지운다. 참조 수를 바로 줄이는 대신 주기적으로 "어떤 메일도 가리키지 않는 파일"을 찾아 지우는 방식이 실수에 더 강하다.

이 절약에는 조심할 점이 있다. 서로 다른 사용자 사이에서 중복을 없애면, 어떤 파일을 올렸을 때 "이미 있다"는 반응(업로드가 즉시 끝나는 등)으로 다른 사람이 같은 파일을 가지고 있는지 알아낼 수 있다. 그래서 중복 제거는 서버 안에서만 일어나게 하고 바깥으로 드러내지 않는다. 사용자별 키로 암호화하는 서비스라면 같은 파일도 암호문이 달라지니 사용자 사이의 중복 제거는 포기한다. 저장 데이터 암호화는 [저장 데이터 암호화](/posts/encryption-at-rest)에서 다뤘다.

## 내 메일함 안에서 찾기

이제 처음의 문제로 돌아온다. 메일 검색은 웹 검색과 모양이 다르다. 웹 검색은 인터넷 전체에서 찾고 관련도순으로 보여 주며, 새 문서가 몇 시간 뒤에 검색돼도 괜찮다. 메일 검색은 내 메일함 안에서만 찾고, 대개 날짜순으로 보여 주며, 방금 받은 메일이 바로 찾아져야 한다. 그리고 쓰기가 훨씬 많다. 메일은 계속 들어오고 지워지고 옮겨지는데, 검색창을 쓰는 일은 그보다 드물다.

`LIKE '%요금%'`로 본문을 훑는 방식은 메일함이 커지면 버티지 못한다. 대신 역색인(inverted index)을 만든다. 메일마다 본문을 낱말로 자르고, 낱말마다 "이 낱말이 나오는 메일 id 목록"을 적어 둔다. 책 뒤의 찾아보기와 같다. 낱말을 찾으면 페이지 번호가 바로 나온다. 역색인의 구조와 점수 계산은 [검색 엔진은 왜 빠른가](/posts/elasticsearch-inverted-index)에서 자세히 다뤘으니, 여기서는 메일에 맞춘 부분만 본다.

한국어는 낱말에 조사와 어미가 붙는다. 띄어쓰기로만 자르면 "요금은", "요금을", "요금이"가 모두 다른 낱말이 된다. 해결책은 둘이다. 형태소 분석기로 "요금"과 "은"을 떼어 내거나, 낱말을 두 글자씩 겹쳐 잘라(바이그램) 넣는 것이다. "요금은"은 "요금", "금은"이 되고, "요금"을 찾으면 "요금" 조각이 있는 메일이 나온다. 샘플 메일 9통(bob 8통, eve 1통)으로 두 방식을 비교했다. 색인 키에는 사용자 이름을 앞에 붙였다.

```text
색인 줄 수: 낱말만 58 / 두 글자 조각 포함 110
bob:요금         [2,8]
bob:요금은        [2,8]
bob:회의록        [1,3,4]
bob:회의록을       [1,4]

bob:예산         [1,3]
bob:budget     [6]
eve:회의록        [9]
낱말 색인으로 '요금'                         (없음)
두 글자 색인으로 '요금'                       #2 11월 청구서 | #8 10월 청구서
'회의록 예산'                             #1 12월 회의록 공유 | #3 Re: 12월 회의록 공유
'회의록 from:alice is:unread'           #4 Re: 12월 회의록 공유

```

두 글자 조각을 넣자 "요금"으로 청구서 두 통이 나왔다. 대가도 보인다. 색인 줄이 58개에서 110개로 두 배 가까이 늘었고, "회의"를 찾으면 "회의실 의자 할인"(#5)까지 걸린다. 조각은 뜻을 모르기 때문이다. 실제 서비스는 형태소 분석과 조각 색인을 함께 쓰고, 정확히 맞은 메일을 위로 올린다. `eve:회의록`이 따로 있는 것도 보자. 사용자마다 색인이 나뉘어 있어서 bob이 아무리 검색해도 eve의 메일은 나오지 않는다. 검색에서 다른 사람의 메일이 섞여 나오는 것은 성능 문제가 아니라 사고다.

여러 낱말을 함께 찾을 때는 각 낱말의 id 목록에서 겹치는 것만 남긴다. 목록을 id 순서로 정렬해 두면 두 목록을 한 번씩만 훑어서 교집합을 구할 수 있다.

`from:alice`, `is:unread`, `in:archive` 같은 조건은 낱말 색인으로 후보를 줄인 뒤 메타데이터로 거르거나, 보낸 사람과 폴더도 색인에 필드로 넣어 함께 찾는다.

얼마나 빨라지는지 쟀다. 사용자 20명에게 1만 통씩, 메일 20만 통을 만들고 "견적17"과 "영수증"이 모두 들어간 메일을 찾았다. 모두 메모리에 올려 둔 실험이다.

```text
메일 200000통 색인: 8098ms, 색인 키 32727개
전체를 훑기 (includes)              11.817ms  결과 99통
내 메일 10000통만 훑기                2.445ms  결과 99통
역색인 (견적17 AND 영수증)             0.116ms  결과 99통
```

세 줄이 각각 할 말이 있다. 전체 20만 통을 훑는 것보다 내 메일 1만 통만 훑는 것이 5배 빠르다. 사용자별로 나누는 것만으로 얻는 이득이다. 역색인은 거기서 다시 20배 빠르다. 그리고 실제로는 차이가 훨씬 크다. 이 실험은 본문이 모두 메모리에 있었지만, 실제 본문은 객체 저장소에 있어서 1만 통을 훑으려면 1만 번 읽어 와야 한다. 색인은 본문을 열지 않는다.

맨 윗줄도 중요하다. 20만 통을 색인하는 데 8초가 걸렸다. 검색은 빨라졌지만 그 비용을 쓰기 때 미리 냈다. 초당 3만 5천 통이 들어오는 서비스라면 이 비용이 계속 든다.

## 색인은 쓰기 때 비용을 낸다

메일이 들어올 때마다 색인을 바로 고치면 받기 경로가 느려지고, 색인 서버가 잠시 멈추면 메일 받기까지 멈춘다. 그래서 색인 갱신은 큐를 거쳐 비동기로 한다. 메일을 받고, 읽음 표시를 하고, 지우고, 폴더를 옮기는 모든 변경이 색인 작업이 된다.

비동기로 하면 방금 받은 메일이 1초쯤 검색되지 않을 수 있다. Elasticsearch는 기본적으로 1초마다 새 문서를 검색 가능하게 만든다(`refresh_interval`). 메일 서비스에서는 대개 받아들일 만한 지연이다. 다만 지우기가 늦게 반영되면 "지운 메일이 검색에 나온다"는 불만이 생기니, 검색 결과를 메타데이터와 맞춰 볼 때 이미 지워진 id는 걸러 낸다.

색인 저장소로는 Elasticsearch 같은 검색 엔진을 쓸 수 있다. 사용자 id로 라우팅해 한 사용자의 문서를 한 샤드에 모으면, 검색이 샤드 하나에서 끝난다. 장점은 바로 쓸 수 있다는 것이다. 단점은 메타데이터 DB와 별도로 운영할 큰 시스템이 하나 더 생기고, 둘 사이를 계속 맞춰야 한다는 것이다.

Gmail 규모의 서비스는 메일 저장소 안에 검색 색인을 직접 만들기도 한다. 이때 핵심 과제가 쓰기 비용이다. 색인을 디스크의 한 자리에서 계속 고치면 무작위 쓰기가 쏟아진다. 그래서 새 색인 항목을 메모리에 모았다가 정렬된 파일로 한 번에 내리고, 나중에 파일끼리 합치는 LSM 트리 구조를 쓴다. 쓰기는 늘 파일 끝에 붙이기만 하니 빠르다. 이 구조는 [⑯ 키-값 저장소의 쓰기·읽기 경로](/posts/sd-kv-store-write-read-path)에서 만들었다. 직접 만들면 메일에 맞게 최적화할 수 있지만 엔지니어링 비용이 크다. 면접에서는 "처음에는 검색 엔진을 붙이고, 규모와 비용이 커지면 저장소에 맞춘 색인을 검토한다"는 정도로 답한다.

## 메일은 잃으면 안 된다

마지막으로 장애 이야기다. 메일 서비스의 첫째 요구는 잃지 않는 것이다. 받았다고 250을 답한 메일이 사라지면 보낸 사람은 다시 보내지 않는다. 그래서 메타데이터 쓰기는 복제본에 기록된 뒤에 성공으로 치고, 객체 저장소도 여러 벌로 저장한다. 데이터센터 하나가 통째로 멈추는 경우를 위해 다른 데이터센터에 복제본을 두고, 장애가 나면 그쪽이 이어받는다([⑥ 여러 데이터센터](/posts/sd-multi-datacenter)).

이때 일관성과 가용성 중 하나를 고르게 된다. 메일 서비스는 대개 일관성을 고른다. 장애 조치 중 몇 초 동안 해당 사용자의 메일함이 읽기 전용이 되거나 잠시 응답하지 않는 것이, 읽음 표시나 지우기가 두 데이터센터에서 엇갈려 메일이 되살아나거나 사라지는 것보다 낫다. 받는 SMTP는 4xx로 잠시 미뤄도 보내는 쪽이 다시 시도하니, 받기 경로는 짧은 장애를 견딘다. 이 판단의 배경은 [CAP과 일관성](/posts/db-consistency-cap)에 있다.

개인정보도 걸린다. 메일은 개인정보 덩어리라 저장 위치(어느 나라)와 삭제 요청 처리가 법의 요구를 받는다. 사용자가 계정을 지우면 메타데이터, 본문, 첨부(참조가 0이 되면), 검색 색인, 백업까지 지워야 한다. 첨부 중복 제거와 색인 비동기 처리는 이 삭제를 더 복잡하게 만드니, 설계할 때 삭제 경로를 함께 그려 둔다.

## 다음 장: 객체 저장소를 직접 만든다

이메일 서비스 두 편을 모으면 이렇다. 메일은 서버끼리 SMTP로 오가고, SPF, DKIM, DMARC로 발신자를 확인한다. 받은 메일은 작고 자주 바뀌는 메타데이터와 크고 바뀌지 않는 본문·첨부로 나눠 담는다. 거의 모든 질문이 사용자 한 명 안에서 끝나니 `user_id`로 나누고, 시간순 id로 정렬을 공짜로 얻는다. 안 읽은 메일은 부분 인덱스나 별도 테이블로, 대화는 `References` 헤더로 묶는다. 검색은 사용자별 역색인으로 하고, 한국어는 조사 때문에 형태소 분석이나 두 글자 조각이 필요하며, 색인 갱신은 큐를 거쳐 비동기로 한다.

다음 장 [㊿ 객체 저장소 설계 ①](/posts/sd-object-storage-architecture)에서는 이 글에서 "객체 저장소에 둔다"고 한 마디로 넘긴 그 저장소를 직접 설계한다. 키 하나로 파일을 넣고 꺼내는 단순한 약속 뒤에서, 데이터와 메타데이터를 어떻게 나누고 몇 벌로 지키는지 본다.

## 면접에서 나올 만한 질문

### 메일의 메타데이터와 본문을 왜 따로 저장하나요?

읽고 쓰는 모양이 다르기 때문이다. 보낸 사람, 제목, 읽음 여부 같은 메타데이터는 작고 목록을 열 때마다 수십 개씩 읽히며 자주 바뀐다. 본문과 첨부는 크고 쓴 뒤 바뀌지 않으며 열어 볼 때만 읽힌다. 그래서 메타데이터는 빠른 DB에, 본문과 첨부는 싸고 큰 객체 저장소에 두고 메타데이터에는 객체 키만 적는다.

### 메타데이터 DB는 무엇을 기준으로 나누나요?

`user_id`다. 목록, 읽음 표시, 폴더 이동, 검색까지 거의 모든 요청이 한 사용자 안에서 끝나기 때문에, 한 사용자의 데이터를 한 샤드에 모으면 요청마다 샤드 하나만 본다. 실험에서도 해시 파티션 8개 중 하나만 읽었다. 그 안에서는 폴더와 시간순 id로 정렬해 최신 메일을 정렬 없이 꺼낸다. 여러 사용자가 함께 쓰는 공용 메일함은 이 구조에서 어려워진다. 이 대가도 함께 말한다.

### '안 읽은 메일만 보기'가 느려졌습니다. 어떻게 고치나요?

실행 계획에서 `Rows Removed by Filter`가 큰지 본다. 오래된 메일함은 대부분이 읽은 메일이라, 안 읽은 몇 통을 찾으려고 폴더 전체를 읽게 된다. PostgreSQL이면 `WHERE NOT is_read` 부분 인덱스로 안 읽은 메일만 따로 색인한다. 실험에서는 3.8ms가 0.085ms가 됐다. 와이드 컬럼 저장소라면 읽은 메일과 안 읽은 메일을 별도 테이블로 나눠 담는 비정규화를 한다.

### 같은 첨부 파일이 여러 사람에게 가면 어떻게 저장하나요?

내용의 SHA-256 해시를 키로 객체 저장소에 한 번만 저장하고, 메일마다 그 키를 참조한다. 실험에서 2MB 파일 50통이 100MiB 대신 2MiB만 차지했다. 지울 때는 마지막 참조가 사라졌을 때만 지운다. 사용자 사이의 중복 제거는 파일 존재 여부가 드러나지 않게 서버 안에서만 하고, 사용자별 키로 암호화하면 포기한다.

### 메일 검색은 웹 검색과 무엇이 다른가요?

범위가 내 메일함 하나이고, 대개 날짜순으로 보여 주며, 방금 받은 메일도 바로 찾아져야 한다. 쓰기(수신, 삭제, 이동)가 검색보다 훨씬 많다. 그래서 사용자별로 역색인을 나누고, 색인 갱신은 큐로 비동기 처리하며, 다른 사용자의 메일이 절대 섞이지 않게 색인 단계부터 사용자로 나눈다.

### 한국어 메일에서 '요금'으로 찾으면 '요금은'이 든 메일이 안 나옵니다. 왜죠?

띄어쓰기로만 낱말을 잘라 색인하면 조사가 붙은 '요금은'이 한 낱말로 들어가서 '요금'과 다른 낱말이 되기 때문이다. 형태소 분석기로 조사를 떼어 내거나, 두 글자씩 겹쳐 자른 조각을 함께 색인한다. 조각 색인은 색인 크기가 커지고 '회의'로 '회의실'이 걸리는 식의 오탐이 생기니, 정확히 맞은 결과를 위로 올리는 처리를 같이 한다.

### 새 메일이 하루 10배로 늘면 어디가 먼저 버거워지나요?

검색 색인 갱신이다. 실험에서도 검색은 0.1ms였지만 20만 통 색인에 8초가 걸렸다. 받기 경로와 색인을 큐로 떼어 놓았으니 색인 작업자를 늘리고, 큐의 지연(가장 오래된 작업의 나이)을 지표로 본다. 색인 저장소는 LSM 트리처럼 쓰기를 모아서 내리는 구조가 맞다. 메타데이터와 객체 저장소는 사용자별로 나뉘어 있어 샤드를 늘리면 된다.

### 데이터센터 하나가 멈추면 어떻게 되나요?

다른 데이터센터의 복제본이 이어받는다. 메일 서비스는 잃지 않는 것이 먼저라 일관성을 고르고, 장애 조치 중에는 영향받은 사용자의 쓰기가 잠시 멈추는 것을 받아들인다. 받는 SMTP가 4xx로 잠시 미뤄도 보내는 서버가 다시 시도하니 메일은 사라지지 않는다. 쓰기를 복제본에 기록한 뒤에 성공으로 쳐야 장애 조치 뒤에도 메일이 남는다.
