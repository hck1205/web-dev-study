## 팀에 넣었는데 DB에는 팀이 없다

팀과 회원을 양방향으로 이었다. 팀은 회원 목록을 갖고, 회원은 자기 팀을 안다.

```java
@Entity class Team {
  @Id @GeneratedValue Long id;
  String name;
  @OneToMany(mappedBy = "team") List<Member> members = new ArrayList<>();
}

@Entity class Member {
  @Id @GeneratedValue Long id;
  String name;
  @ManyToOne Team team;
}
```

팀을 만들고, 회원을 만들고, 팀의 목록에 회원을 넣었다.

```java
Team t = new Team("dev"); em.persist(t);
Member m = new Member("kim"); em.persist(m);
t.members.add(m);
```

```text
SQL: insert into team (name,id) values (?,?)
SQL: insert into member (name,team_id,id) values (?,?,?)
SQL: select team_id from member
team_id in db = null
```

INSERT는 나갔고 에러도 없다. 그런데 회원의 `team_id`가 `null`이다. 팀 목록에 넣은 건 DB에 아무 영향을 주지 않았다. 이번에는 반대로 회원 쪽만 바꿨다.

```java
Team t = new Team("dev"); em.persist(t);
Member m = new Member("kim"); m.team = t; em.persist(m);
System.out.println("set member.team only, team.members.size() = " + t.members.size());
em.flush();
System.out.println("after flush, team.members.size() = " + em.find(Team.class, t.id).members.size());
```

```text
set member.team only, team.members.size() = 0
SQL: insert into team (name,id) values (?,?)
SQL: insert into member (name,team_id,id) values (?,?,?)
after flush, team.members.size() = 0
```

이번에는 DB가 맞다. 대신 같은 트랜잭션 안에서 팀의 회원 목록이 여전히 비어 있다. flush한 뒤 `find()`로 다시 꺼내도 0이다. 둘 다 같은 규칙에서 나온다. 이 글은 그 규칙인 연관관계의 주인부터 시작해, `@ManyToOne`, `@OneToMany`, `@ManyToMany` 매핑과 cascade, orphanRemoval, 기본 fetch 전략, 그리고 양방향 연관이 만드는 `toString`·`equals` 함정을 실제 SQL로 본다.

엔티티 상태, 1차 캐시, 더티 체킹, 지연 로딩 프록시는 [JPA 영속성 컨텍스트](/posts/jpa-persistence-context)에서 다뤘다. 위의 "flush 뒤에도 0"이 왜 그런지도 거기서 본 1차 캐시로 설명된다. 연관을 따라 쿼리가 수백 개 나가는 N+1은 [N+1 쿼리 깊이 보기](/posts/n-plus-one-queries)에 있다. 예제는 JDK 21, Spring Boot 4.1.1(Hibernate 7.4.5), H2 메모리 DB로 돌렸고, SQL은 `logging.level.org.hibernate.SQL=DEBUG`로 찍었다.

## 외래 키는 한쪽 테이블에만 있다

객체와 테이블은 관계를 표현하는 방식이 다르다. 객체는 참조를 양쪽에 둘 수 있다. 팀이 회원 목록을, 회원이 팀을 들고 있으면 어느 쪽에서든 건너갈 수 있다. 테이블은 외래 키 하나로 관계를 표현한다. `member` 테이블의 `team_id` 칸 하나가 전부다. `team` 테이블에는 회원을 가리키는 칸이 없다. 조인하면 양쪽으로 건너갈 수 있으니 그걸로 충분하다.

```sql
-- Hibernate가 시작할 때 만든 DDL (H2)
create table member (id bigint not null, team_id bigint, name varchar(255), primary key (id))
create table team (id bigint not null, name varchar(255), primary key (id))
alter table if exists member add constraint FKcjte2jn9pvo9ud2hyfgwcja0k foreign key (team_id) references team
```

객체 참조는 둘인데 외래 키는 하나다. 둘이 서로 다른 값을 말하면 JPA는 어느 쪽을 믿어야 할지 정해야 한다. 그래서 둘 중 한쪽을 연관관계의 주인(owner)으로 정하고, 주인 쪽 참조만 외래 키에 반영한다. 다른 쪽은 읽기 전용 거울이다. 아래 그림이 객체 둘과 테이블 둘의 관계다. 점이 흐르는 실선이 실제로 DB에 쓰이는 길이다.

규칙은 단순하다. 외래 키가 있는 테이블의 엔티티가 주인이다. 일대다·다대일 관계에서 외래 키는 항상 "다" 쪽 테이블에 있으니 `@ManyToOne` 쪽이 주인이다. 주인이 아닌 쪽에는 `mappedBy`를 적어 "이 관계는 저쪽의 `team` 필드가 관리한다"고 알린다. 처음 장면에서 `Team.members`는 `mappedBy = "team"`이라 거울이었고, 거울에 넣은 회원은 무시됐다.

## mappedBy 쪽은 거울이다

거울이 DB에 쓰이지 않는다는 건 알았다. 두 번째 실험의 "목록이 비어 있다"는 다른 쪽 문제다. 그 트랜잭션 안에서 `Team` 객체는 `em.persist(t)`로 1차 캐시에 들어갔다. `em.find(Team.class, t.id)`는 DB에 가지 않고 그 객체를 그대로 돌려준다. 그 객체의 `members` 리스트에는 아무도 넣지 않았으니 비어 있다. DB의 외래 키가 맞아도, 이미 메모리에 있는 객체를 JPA가 대신 고쳐 주지 않는다. 다음 트랜잭션에서 새로 읽으면 그때는 회원이 보인다.

이 차이는 테스트에서 자주 드러난다. 서비스가 회원 쪽만 설정하고 같은 트랜잭션 안에서 팀의 회원 수를 세면 0이 나온다. 운영에서는 요청마다 새로 읽으니 맞게 나와서, "테스트만 깨진다"는 장면이 된다.

해결은 양쪽을 항상 함께 맞추는 것이다. 한쪽 엔티티에 편의 메서드를 두고, 그 메서드만 쓴다.

```java
@Entity class Team {
  @OneToMany(mappedBy = "team") List<Member> members = new ArrayList<>();

  void addMember(Member m) {
    members.add(m);   // 거울 쪽 (메모리 일관성)
    m.team = this;    // 주인 쪽 (DB에 쓰인다)
  }
}
```

팀을 옮기는 경우까지 생각하면, 예전 팀의 목록에서 빼는 일도 이 메서드가 맡는다. 편의 메서드는 양쪽 중 한 곳에만 둔다. 양쪽에 다 두면 서로를 부르다가 무한히 돈다.

### 양방향이 꼭 필요한가

처음 설계할 때는 다대일 단방향(`Member.team`만)으로 시작하는 편이 낫다. 외래 키를 쓰는 데는 그걸로 충분하고, 맞춰야 할 거울이 없다. 팀에서 회원 목록이 필요하면 `select m from Member m where m.team = :team` 쿼리로 읽는다. 양방향은 "팀 화면에서 회원을 자주 따라가야 한다"거나 cascade·orphanRemoval처럼 부모가 자식 목록을 관리해야 할 때 추가한다. 양방향 연관은 조회 편의를 위한 것이고, 그만큼 맞출 책임과 직렬화·`toString`의 함정을 함께 들인다.

## 일대다 단방향은 UPDATE를 더 보낸다

거꾸로 "일" 쪽에만 목록을 두고 싶을 때가 있다. 가게가 상품 목록을 들고, 상품은 가게를 모르게 한다. `mappedBy`가 없으니 이 목록이 주인이다. `@JoinColumn`으로 상대 테이블의 외래 키를 지정했다.

```java
@Entity class Shop {
  @Id @GeneratedValue Long id;
  @OneToMany @JoinColumn(name = "shop_id") List<Item> items = new ArrayList<>();
}
@Entity class Item { @Id @GeneratedValue Long id; String name; }

Shop sh = new Shop(); em.persist(sh);
Item i1 = new Item("a"); Item i2 = new Item("b"); em.persist(i1); em.persist(i2);
sh.items.add(i1); sh.items.add(i2);
```

```text
SQL: insert into shop (id) values (?)
SQL: insert into item (name,id) values (?,?)
SQL: insert into item (name,id) values (?,?)
SQL: update item set shop_id=? where id=?
SQL: update item set shop_id=? where id=?
```

상품 INSERT 뒤에 UPDATE가 상품 수만큼 더 나갔다. 외래 키는 `item` 테이블에 있는데 그 값을 관리하는 건 `Shop` 엔티티다. `Item`을 INSERT할 때 Hibernate는 `Item` 객체만 보고 `shop_id`를 모르니 비워 두고, 나중에 `Shop`의 목록을 처리하면서 채운다. `shop_id`에 `NOT NULL` 제약이 있으면 첫 INSERT부터 실패한다. `@JoinColumn`이 없으면 `shop_items` 같은 조인 테이블을 따로 만든다. 그래서 일대다 단방향보다는 다대일 단방향, 필요하면 다대일·일대다 양방향을 쓴다.

## cascade와 orphanRemoval은 다른 질문에 답한다

글과 댓글처럼 자식의 생명이 부모에 딸린 관계가 있다. 댓글은 글 없이 존재하지 않는다. 이때 두 옵션을 함께 쓴다.

```java
@Entity class Post {
  @OneToMany(mappedBy = "post", cascade = CascadeType.ALL, orphanRemoval = true)
  List<Comment> comments = new ArrayList<>();

  void addComment(Comment c) { comments.add(c); c.post = this; }
}
```

두 옵션이 답하는 질문이 다르다.

- cascade: 부모에게 한 일(persist, merge, remove 등)을 자식에게도 하라. "부모를 저장하면 자식도 저장하나?"
- orphanRemoval: 부모의 목록에서 빠진 자식을 지우라. "목록에서 뺐을 뿐인데 DB에서도 지우나?"

글 하나에 댓글 둘을 달아 글만 `persist`하고, 다음 트랜잭션에서 목록의 첫 댓글을 뺐다. 비교하려고 orphanRemoval 없이 cascade만 둔 게시판·메모 엔티티도 똑같이 돌렸다.

```text
persist post only
SQL: insert into post (title,id) values (?,?)
SQL: insert into comment (body,post_id,id) values (?,?,?)
SQL: insert into comment (body,post_id,id) values (?,?,?)
SQL: select p1_0.id,p1_0.title from post p1_0 where p1_0.id=?
SQL: select c1_0.post_id,c1_0.id,c1_0.body from comment c1_0 where c1_0.post_id=?
removed from list
SQL: delete from comment where id=?
comments left = 1

removed note from list (no orphanRemoval)
notes left = 2
```

글만 저장했는데 댓글 INSERT까지 나간 건 cascade 덕분이다. 목록에서 뺀 댓글이 DELETE된 건 orphanRemoval 덕분이다. orphanRemoval이 없는 메모는 목록에서 빼도 SQL이 하나도 없었다. 목록은 거울(`mappedBy`)이라 DB에 쓰이지 않는다. 메모의 `board_id`도 그대로라 다음에 게시판을 읽으면 그 메모가 다시 나온다.

글을 지울 때는 이렇게 나갔다.

```text
SQL: select p1_0.id,p1_0.title from post p1_0 where p1_0.id=?
SQL: select c1_0.post_id,c1_0.id,c1_0.body from comment c1_0 where c1_0.post_id=?
removed post
SQL: delete from comment where id=?
SQL: delete from post where id=?
```

아래 그림에서 다음을 누르며 글 하나를 지울 때 무엇이 오가는지 따라가 보자.

마지막 단계가 운영에서 문제가 된다. 자식이 수천, 수만 개면 SELECT로 전부 메모리에 올린 뒤 DELETE를 그 수만큼 보낸다. 자식이 많은 관계라면 JPQL 벌크 삭제(`delete from Comment c where c.post.id = :id`)를 먼저 하거나, DB의 `ON DELETE CASCADE` 외래 키에 맡긴다. 벌크 쿼리가 영속성 컨텍스트를 모른다는 점은 앞 글에서 본 그대로라, 그 뒤에는 컨텍스트를 비운다.

cascade를 어디에 걸지도 정해야 한다. 기준은 "자식이 이 부모 하나에만 딸려 있나"다. 댓글은 글 하나에만 속하니 걸어도 된다. 회원과 팀처럼 자식이 독립된 생명을 가지면 걸지 않는다. 특히 `@ManyToOne`에 `CascadeType.REMOVE`를 걸면, 회원 하나를 지울 때 팀까지 지우려 하다가 다른 회원이 참조하는 외래 키 때문에 실패하거나, 제약이 없으면 팀이 사라진다. 여러 부모가 공유하는 자식(태그 같은)에 orphanRemoval을 걸면 한 부모에서 뺄 때 다른 부모의 것까지 지워진다.

## 다대다는 중간 엔티티로 푼다

학생과 수업은 서로 여럿이다. `@ManyToMany`를 쓰면 조인 테이블을 알아서 만든다.

```java
@Entity class Student {
  @Id @GeneratedValue Long id;
  String name;
  @ManyToMany List<Course> courses = new ArrayList<>();
}
```

수업 셋을 등록한 학생에게서 하나를 뺐다.

```text
SQL: insert into student_courses (student_id,courses_id) values (?,?)
SQL: insert into student_courses (student_id,courses_id) values (?,?)
SQL: insert into student_courses (student_id,courses_id) values (?,?)
SQL: select s1_0.id,s1_0.name from student s1_0 where s1_0.id=?
SQL: select c1_0.student_id,c1_1.id,c1_1.title from student_courses c1_0 join course c1_1 on c1_1.id=c1_0.courses_id where c1_0.student_id=?
removed one course
SQL: delete from student_courses where student_id=?
SQL: insert into student_courses (student_id,courses_id) values (?,?)
SQL: insert into student_courses (student_id,courses_id) values (?,?)
```

하나를 뺐는데 그 학생의 조인 행을 모두 지우고 남은 둘을 다시 넣었다. 수업을 하나 더했을 때도 똑같이 전부 지우고 셋을 다시 넣었다. `List`로 선언한 다대다는 Hibernate에서 순서도 중복 구분도 없는 bag이다. 조인 테이블의 행 하나를 집어 지울 방법이 없어서 통째로 다시 쓴다. 같은 관계를 `Set`으로 바꾸자 달라졌다.

```text
set: removed one course
SQL: delete from student2_courses where student2_id=? and courses_id=?
set: added one course
SQL: insert into student2_courses (student2_id,courses_id) values (?,?)
```

아래 그림은 수업 하나를 뺄 때 bag 조인 테이블에서 일어난 일이다.

`Set`으로 바꾸면 SQL은 줄지만 다대다의 근본 문제는 남는다. 조인 테이블에 칸을 더할 수 없다. 수강 신청일, 성적, 출석률처럼 "학생과 수업의 관계"에 붙는 정보는 실무에서 거의 반드시 생긴다. 그때 `@ManyToMany`로는 담을 곳이 없다. 그래서 처음부터 관계를 엔티티로 올린다.

```java
@Entity class Enrollment {                         // 학생-수업 관계 자체가 엔티티다
  @Id @GeneratedValue Long id;
  @ManyToOne(fetch = FetchType.LAZY) Student student;
  @ManyToOne(fetch = FetchType.LAZY) Course course;
  LocalDate enrolledAt;
  String grade;
}
```

다대다 하나가 다대일 둘이 된다. 행마다 id가 있으니 하나를 집어 지울 수 있고, 칸을 마음대로 더할 수 있다. 같은 학생이 같은 수업에 두 번 들어가지 않도록 `(student_id, course_id)`에 유니크 제약을 건다. 테이블을 나누는 기준은 [정규화](/posts/db-modeling-normalization) 글에서 다뤘다.

## 기본 fetch 전략: ToOne은 즉시, ToMany는 지연

JPA 표준의 기본값은 `@ManyToOne`, `@OneToOne`이 EAGER(즉시), `@OneToMany`, `@ManyToMany`가 LAZY(지연)다. 위의 `Member.team`은 fetch를 적지 않았으니 EAGER다. 회원 하나를 `find()`할 때와 JPQL로 전부 읽을 때를 비교했다.

```text
-- find
SQL: select m1_0.id,m1_0.name,t1_0.id,t1_0.name from member m1_0 left join team t1_0 on t1_0.id=m1_0.team_id where m1_0.id=?
-- jpql
SQL: select m1_0.id,m1_0.name,m1_0.team_id from member m1_0
SQL: select t1_0.id,t1_0.name from team t1_0 where t1_0.id=?
SQL: select t1_0.id,t1_0.name from team t1_0 where t1_0.id=?
SQL: select t1_0.id,t1_0.name from team t1_0 where t1_0.id=?
```

`find()`는 조인 한 번으로 팀까지 가져왔다. JPQL은 회원만 읽은 뒤, EAGER라 팀을 곧바로 채워야 해서 팀마다 SELECT를 하나씩 더 보냈다. 팀을 쓰지 않는 화면에서도 그렇다. 회원이 100명이고 팀이 다 다르면 101개다. 그래서 실무에서는 모든 `@ManyToOne`, `@OneToOne`에 `fetch = FetchType.LAZY`를 붙이고, 함께 필요할 때만 fetch join이나 `@EntityGraph`로 가져온다. 이 전환과 그 뒤의 N+1 대처는 N+1 글에서 이어 간다.

`@OneToOne`에는 하나 더 주의할 점이 있다. 외래 키가 없는 쪽(주인이 아닌 쪽)의 `@OneToOne`은 LAZY로 적어도 즉시 로딩될 수 있다. 상대가 있는지 없는지 모르면 `null`과 프록시 중 무엇을 넣을지 정할 수 없어서, 확인하려면 조회해야 하기 때문이다. Hibernate는 바이트코드 강화 같은 설정이 있을 때만 이걸 피한다. 일대일은 외래 키를 자주 조회하는 쪽 테이블에 두고, 그쪽을 주인으로 삼는다.

## toString과 equals가 연관을 따라가면

양방향 연관을 둔 엔티티에 `toString()`을 양쪽 다 필드 전부로 만들었다(Lombok의 `@ToString`, `@Data`가 기본으로 하는 일과 같다).

```java
// Team
public String toString() { return "Team(" + name + ", members=" + members + ")"; }
// Member
public String toString() { return "Member(" + name + ", team=" + team + ")"; }

Team t = new Team("dev"); Member m = new Member("kim");
m.team = t; t.members.add(m);
System.out.println(t);
```

```text
StackOverflowError
```

팀은 회원 목록을 찍고, 회원은 팀을 찍고, 팀은 다시 회원 목록을 찍는다. 로그 한 줄에 엔티티를 넣었다가 서버 스레드가 스택 오버플로로 죽는 장면이다. JSON 직렬화도 같은 고리를 따라간다. `toString`에는 id와 단순 필드만 넣고 연관 필드는 빼며, Lombok을 쓰면 `@ToString.Exclude`를 연관에 붙인다. API 응답으로는 엔티티 대신 DTO를 내보내서 직렬화가 연관을 따라갈 일을 없앤다. 지연 로딩 연관을 찍으면 트랜잭션 밖에서 `LazyInitializationException`이 나거나, 안에서는 로그 한 줄이 쿼리를 날리는 일도 생긴다.

`equals`와 `hashCode`도 연관 필드를 쓰면 같은 고리에 빠진다. 그런데 연관을 빼고 id만 써도 함정이 있다. 생성된 id로 `hashCode`를 만든 엔티티를 `persist` 전에 `HashSet`에 넣었다.

```java
@Override public boolean equals(Object o) { return o instanceof Tag t && Objects.equals(id, t.id); }
@Override public int hashCode() { return Objects.hashCode(id); }

Set<Tag> tags = new HashSet<>(); Tag t = new Tag("jpa"); tags.add(t);
System.out.println("before persist contains=" + tags.contains(t) + " hash=" + t.hashCode());
em.persist(t);
System.out.println("after persist id=" + t.id + " contains=" + tags.contains(t) + " hash=" + t.hashCode());
```

```text
before persist contains=true hash=0
after persist id=1 contains=false hash=1
```

같은 객체인데 `contains`가 `false`가 됐다. 저장 전에는 id가 `null`이라 해시가 0이었고, `persist()`가 id를 채우면서 해시가 1로 바뀌었다. `HashSet`은 객체를 해시 0 칸에 넣어 두었으니 1 칸에서 찾지 못한다. `Set`으로 둔 `@OneToMany`에 새 자식을 넣고 저장하면 바로 이 일이 일어난다.

엔티티의 `equals`·`hashCode`는 이렇게 고른다.

- 이메일, 주문 번호처럼 변하지 않는 업무 키가 있으면 그것으로 만든다.
- 생성된 id만 있다면 `equals`는 id가 `null`이 아닐 때만 비교하고, `hashCode`는 클래스별 상수(`getClass().hashCode()`)를 돌려준다. 해시 성능은 조금 손해지만 저장 전후로 값이 바뀌지 않는다.
- `o instanceof Tag`처럼 쓰고 `getClass() ==`는 피한다. 지연 로딩 프록시는 엔티티의 하위 클래스라 클래스가 다르다.
- 상대 객체의 필드를 직접 읽지 말고 getter를 쓴다. 프록시의 필드는 비어 있다는 걸 [JPA 영속성 컨텍스트](/posts/jpa-persistence-context)의 프록시 절에서 봤다. `other.id`가 `null`로 읽혀 같은 행끼리 다르다고 판단한다.

## 연관을 설계할 때 고르는 순서

1. 외래 키를 어느 테이블에 둘지 먼저 정한다. 그 테이블의 엔티티에 `@ManyToOne`을 두고, 그게 주인이다.
2. 다대일 단방향으로 시작한다. 반대 방향 탐색이 정말 자주 필요할 때 `mappedBy`로 양방향을 더하고, 편의 메서드 하나로 양쪽을 맞춘다.
3. 모든 `@ManyToOne`, `@OneToOne`에 `LAZY`를 적는다.
4. cascade와 orphanRemoval은 자식이 그 부모 하나에만 딸린 관계에만 건다. 자식이 많으면 삭제를 벌크 쿼리나 DB에 맡긴다.
5. 다대다는 처음부터 중간 엔티티로 만든다. `@ManyToMany`를 쓸 거라면 `Set`으로 둔다.
6. `toString`, `equals`, `hashCode`, JSON 직렬화에서 연관 필드를 뺀다.

## 거울과 주인

객체는 참조 둘로, 테이블은 외래 키 하나로 관계를 표현한다. JPA는 그 차이를 "외래 키가 있는 쪽이 주인이고, `mappedBy` 쪽은 거울"이라는 규칙으로 메운다. 거울을 고쳐도 DB는 그대로고, 주인을 고쳐도 메모리의 거울은 그대로라서 편의 메서드로 둘을 함께 맞춘다. cascade는 부모에게 한 일을 자식에게 전하고, orphanRemoval은 목록에서 빠진 자식을 지운다. 처음 장면에서 팀 명단에 적은 회원이 DB에 반영되지 않은 건 명단이 거울이었기 때문이다.

## 면접에서 나올 만한 질문

### 연관관계의 주인이란 무엇이고 어떻게 정하나요?

양방향 연관에서 외래 키 값을 실제로 관리하는 쪽이다. 객체 참조는 둘인데 테이블 외래 키는 하나라 한쪽만 DB에 반영해야 해서 생긴 개념이다. 외래 키가 있는 테이블의 엔티티, 보통 `@ManyToOne` 쪽이 주인이 되고, 반대쪽은 `mappedBy`로 읽기 전용임을 표시한다. 주인이 아닌 쪽 컬렉션에 추가하거나 빼도 SQL은 나가지 않는다.

### 양방향 연관에서 한쪽만 설정하면 어떤 문제가 생기나요?

주인이 아닌 쪽만 설정하면 외래 키가 `null`로 저장된다. 주인 쪽만 설정하면 DB는 맞지만, 같은 트랜잭션 안에서는 1차 캐시의 객체를 그대로 돌려주므로 반대쪽 컬렉션이 비어 보인다. 테스트처럼 한 트랜잭션에서 저장과 조회를 함께 하면 드러난다. 양쪽을 한 번에 맞추는 편의 메서드를 한쪽 엔티티에 두고 그것만 쓴다.

### cascade와 orphanRemoval의 차이는 무엇인가요?

cascade는 부모에게 한 persist, remove 같은 동작을 자식에게도 전한다. orphanRemoval은 부모의 컬렉션에서 빠져 부모와의 관계가 끊긴 자식을 삭제한다. cascade만 있으면 목록에서 빼도 아무 SQL이 나가지 않고, orphanRemoval이 있으면 DELETE가 나간다. 둘 다 자식이 그 부모 하나에만 딸린 관계에만 쓴다.

### 일대다 단방향 매핑을 피하는 이유는 무엇인가요?

외래 키는 "다" 쪽 테이블에 있는데 관리는 "일" 쪽 엔티티가 해서, 자식을 INSERT한 뒤 외래 키를 채우는 UPDATE가 자식 수만큼 더 나간다. 외래 키에 NOT NULL 제약이 있으면 INSERT가 실패한다. `@JoinColumn`이 없으면 조인 테이블까지 생긴다. 다대일 단방향이나 양방향으로 바꾸는 편이 낫다.

### @ManyToMany를 실무에서 잘 쓰지 않는 이유는 무엇인가요?

조인 테이블에 수강일이나 상태 같은 관계의 정보를 더할 수 없고, 관계 정보는 실무에서 거의 반드시 생긴다. `List`로 두면 Hibernate가 bag으로 다뤄 하나만 바꿔도 그 부모의 조인 행을 전부 지우고 다시 넣는다. 관계를 중간 엔티티로 올려 다대일 둘로 풀고, 두 외래 키 조합에 유니크 제약을 건다.

### 연관관계의 기본 fetch 전략은 무엇이고 왜 바꾸나요?

`@ManyToOne`과 `@OneToOne`은 EAGER, `@OneToMany`와 `@ManyToMany`는 LAZY가 기본이다. EAGER는 `find`에서는 조인으로 가져오지만, JPQL에서는 결과를 읽은 뒤 연관마다 SELECT를 더 보내 N+1이 생기고 쓰지 않는 화면에서도 끌려온다. 그래서 ToOne도 모두 LAZY로 바꾸고 필요할 때 fetch join이나 `@EntityGraph`로 가져온다.

### JPA 엔티티의 equals와 hashCode는 어떻게 구현하나요?

변하지 않는 업무 키가 있으면 그걸 쓰고, 생성된 id만 있다면 id가 있을 때만 비교하고 `hashCode`는 상수로 둔다. id로 해시를 만들면 `persist` 전후로 해시가 바뀌어 `HashSet`에서 찾지 못한다. 프록시 때문에 `getClass()` 비교 대신 `instanceof`를 쓰고, 상대의 필드는 getter로 읽는다. 연관 필드는 넣지 않는다.

### 양방향 연관에서 toString이나 JSON 직렬화가 왜 문제가 되나요?

서로를 가리키는 필드를 양쪽에서 출력하면 끝없이 따라가 `StackOverflowError`가 난다. 지연 로딩 연관을 건드리면 트랜잭션 밖에서는 `LazyInitializationException`, 안에서는 로그 한 줄이 쿼리를 날린다. `toString`에서 연관 필드를 빼고, 응답은 엔티티 대신 DTO로 내보낸다.
