<EasyIntro>

[Merge Triplets to Form Target Triplet](https://leetcode.com/problems/merge-triplets-to-form-target-triplet/)은 LeetCode 1899번이다. 코드는 열 줄 남짓으로 끝나지만, 면접에서는 "왜 쓸 수 있는 것을 전부 합쳐도 되나"를 말로 증명하라는 질문이 따라온다. 그 답이 최댓값 연산의 성질 몇 가지에 다 들어 있어서, 그리디가 왜 맞는지를 연습하기에 좋은 문제다.

이 글은 네 풀이를 본다. 모든 부분집합을 합쳐 보는 풀이, 넘치는 것을 걸러 낸 뒤 합치는 풀이, 한 번 훑으며 합치는 풀이, 맞춘 칸만 표시하고 일찍 끝내는 풀이다. 뒤의 셋은 같은 생각을 메모리와 코드 모양만 바꿔 쓴 것이다. 그리디를 증명하는 일반적인 틀은 [그리디 알고리즘 글](/posts/greedy-algorithms)에 있다. 코드는 Node.js 22, Python 3, Java 21에서 돌렸다.

## 칸마다 큰 쪽만 남기는 합치기

길이 3인 정수 배열들의 목록 `triplets`와 목표 배열 `target = [x, y, z]`가 주어진다. 할 수 있는 연산은 하나다. 서로 다른 두 번호 i, j를 골라 `triplets[j]`를 칸마다 최댓값인 `[max(a_i, a_j), max(b_i, b_j), max(c_i, c_j)]`로 바꾼다. 이 연산을 몇 번이든(0번도 된다) 해서 `target`이 `triplets`의 원소 중 하나가 될 수 있으면 `true`다.

풀이 선택에 영향을 주는 제약은 이렇다.

- 묶음은 최대 10^5개다. 부분집합을 모두 보는 O(2^n)은 물론 O(n²)도 무리다.
- 숫자는 1 이상 1000 이하다. 합칠 때 최댓값만 고르니 넘침 걱정은 없다.
- 연산 순서와 횟수에 제한이 없다. 이 조건 덕분에 "어떤 묶음들을 고르느냐"만 남는다.

마지막 조건을 조금 더 풀어 보자. 묶음 몇 개를 골라 하나로 합치고 싶으면, 그중 하나를 j로 정해 두고 나머지를 차례로 i로 넣어 연산하면 된다. 최댓값은 순서를 바꿔도(교환 법칙), 묶는 방법을 바꿔도(결합 법칙), 같은 것을 두 번 넣어도(멱등성) 결과가 같다. 그래서 몇 번 어떤 순서로 합쳤는지는 상관없고, 결국 "고른 묶음들의 칸별 최댓값"만 만들 수 있다. 문제는 "칸별 최댓값이 정확히 target이 되는 묶음 집합이 있나"로 바뀐다.

## 작은 예시로 합쳐 본다

이 글에서 쓸 예시다. 목표는 `[2, 7, 5]`다.

```text
번호   묶음
0     [2, 5, 3]
1     [1, 8, 4]
2     [1, 7, 5]
```

1번을 섞으면 어떻게 될까. 가운데 칸이 8이 되는데, 목표는 7이다. 최댓값은 커지기만 하니 8은 다시 7로 내려오지 않는다. 1번은 어떤 조합에도 넣으면 안 된다.

남은 0번과 2번을 합치면 `[max(2, 1), max(5, 7), max(3, 5)] = [2, 7, 5]`다. 목표와 같으니 `true`다. 연산 한 번(2번에 0번을 합치기)이면 된다.

이번엔 `[[2, 9, 1], [1, 7, 5]]`에서 목표가 `[2, 7, 5]`인 경우다. 첫 칸 2를 가진 묶음은 0번뿐인데, 0번은 가운데 칸이 9라 쓸 수 없다. 1번만으로는 첫 칸이 1이다. 그래서 `false`다. 칸마다 따로 보면 2, 7, 5가 모두 어딘가에 있지만, 2를 가진 묶음이 독을 품고 있어서 못 쓴다. 이 예시가 뒤에서 흔한 오답을 잡는 입력이 된다.

## 모든 부분집합을 합쳐 본다

문제를 "칸별 최댓값이 target인 집합이 있나"로 바꿨으니, 비어 있지 않은 부분집합을 모두 만들어 보면 확실하다. n이 작을 때 답을 맞춰 보는 기준으로 쓰기 좋다.

```js
function mergeTriplets(triplets, target) {
  const n = triplets.length;
  for (let mask = 1; mask < (1 << n); mask++) {     // 비트마다 그 묶음을 고르는지
    const cur = [0, 0, 0];
    for (let i = 0; i < n; i++) if (mask & (1 << i))
      for (let d = 0; d < 3; d++) cur[d] = Math.max(cur[d], triplets[i][d]);
    if (cur[0] === target[0] && cur[1] === target[1] && cur[2] === target[2]) return true;
  }
  return false;
}
```

부분집합이 2^n개이고 하나마다 n개를 보니 O(2^n · n)이다. 공간은 O(1)이다. 비트로 부분집합을 고르는 방법은 [비트 연산 글](/posts/bit-manipulation)에 있다. 답이 없는 입력에서 재 봤다.

```text
subsets 16 false 20.7
subsets 20 false 292.1
```

묶음이 20개만 돼도 0.3초다. 10^5개는 생각할 수도 없다. 그런데 이 풀이를 보면 대부분의 부분집합이 쓸데없다는 게 드러난다. 넘치는 묶음을 하나라도 넣은 부분집합은 볼 필요가 없고, 넘치지 않는 묶음은 넣어서 손해 볼 일이 없다. 두 관찰을 차례로 확인해 본다.

## 한 칸이라도 넘치면 독이 된다

첫 번째 관찰이다. 어떤 칸에서 target보다 큰 값을 가진 묶음은 절대 쓰면 안 된다.

이유는 최댓값이 내려가지 않는다는 데 있다. 묶음 t의 가운데 칸이 8이고 목표가 7이라고 하자. t를 넣은 어떤 집합의 칸별 최댓값도 가운데 칸이 8 이상이다. 다른 묶음을 아무리 더 넣어도 최댓값은 그대로이거나 커질 뿐이다. 그러니 t가 든 집합은 모두 실패다. t를 버려도 잃는 것이 없다.

이런 묶음을 "독이 든 묶음"이라고 부르자. 판정은 세 칸 중 하나라도 target의 같은 칸보다 크면 독이다.

```js
const poisoned = t[0] > target[0] || t[1] > target[1] || t[2] > target[2];
```

독이 아닌 묶음은 세 칸이 모두 target 이하다. 이런 묶음을 "쓸 수 있는 묶음"이라고 부른다.

## 쓸 수 있는 묶음은 전부 합쳐도 손해가 없다

두 번째 관찰이다. 쓸 수 있는 묶음을 모두 합친 결과를 M이라 하자. 답이 있다면 M이 곧 target이다.

M의 칸은 모두 target 이하다. 쓸 수 있는 묶음의 칸이 모두 target 이하이니, 그 최댓값도 target 이하다. 이제 답이 되는 집합 S가 있다고 하자. S에는 독이 든 묶음이 없으니 S는 쓸 수 있는 묶음들의 일부다. 일부보다 전체의 최댓값이 작을 수는 없으니 칸마다 M은 S의 결과(= target) 이상이다. target 이하이면서 target 이상이니 M은 target과 같다.

반대로 M이 target이면 쓸 수 있는 묶음 전부가 답이 되는 집합이다. 그래서 판정은 "쓸 수 있는 묶음을 모두 합쳐서 target과 같은가" 하나로 끝난다. 어떤 묶음을 고를지 고민할 필요가 없다. 쓸 수 있으면 다 넣는다. 이게 이 문제의 그리디다.

이 증명은 [그리디 알고리즘 글](/posts/greedy-algorithms#그리디인지-확인하는-순서)에서 말하는 "선택해도 손해 보지 않는다"를 그대로 보인 것이다. 다른 그리디 문제와 다른 점은 순서조차 상관없다는 것이다. 최댓값은 교환·결합 법칙이 성립하고 같은 걸 두 번 넣어도 결과가 같아서, 어떤 순서로 넣어도 같은 M이 나온다.

## 두 칸으로 줄여 그려 보면

세 칸은 머릿속에 그리기 어려우니 칸을 두 개로 줄여 보자. 묶음 `[a, b]`를 평면 위의 점 (a, b)로 본다. 목표가 `[4, 3]`이면 목표는 점 (4, 3)이다.

```text
b
5 |    x
4 |
3 | o  o     T
2 |    o     o  x
1 | o     o
  +---------------- a
    1  2  3  4  5
```

`o`는 묶음, `x`는 독이 든 묶음, `T`는 목표 자리다. 쓸 수 있는 점은 목표의 왼쪽 아래, 즉 a가 4 이하이고 b가 3 이하인 직사각형 안에 있는 점이다. (2, 5)는 위로, (5, 2)는 오른쪽으로 직사각형을 벗어나서 독이다. 칸별 최댓값으로 합친다는 건 고른 점들을 모두 감싸는 직사각형의 오른쪽 위 꼭짓점을 찾는 일이다.

이 그림에서 증명이 한눈에 보인다. 직사각형 안의 점만 고르면 꼭짓점도 직사각형 안에 머문다. 꼭짓점이 목표와 정확히 겹치려면 오른쪽 변(a = 4) 위의 점이 하나, 위쪽 변(b = 3) 위의 점이 하나 있어야 한다. 그림에서는 (4, 2)와 (1, 3), (2, 3)이 그렇다. 직사각형 안의 점 여섯 개를 모두 감싸면 꼭짓점이 (4, 3)이 되어 목표와 겹친다. 한 점이 두 변에 모두 걸치면, 그게 바로 목표 점이다. 세 칸이면 직사각형이 상자가 되고, 상자의 세 면에 각각 닿는 점이 있는지 보는 문제가 된다. 뒤에 나올 "맞춘 칸 표시" 풀이가 정확히 이것을 센다.

## 걸러 낸 목록을 만들고 합친다

두 관찰을 그대로 코드로 옮긴다. 독이 든 묶음을 걸러 내고, 남은 것의 칸별 최댓값을 구한다.

```js
function mergeTriplets(triplets, target) {
  const good = triplets.filter(                     // 세 칸 모두 target 이하인 것만
    t => t[0] <= target[0] && t[1] <= target[1] && t[2] <= target[2]
  );
  if (good.length === 0) return false;              // 쓸 수 있는 묶음이 없다
  const cur = good.reduce((a, t) =>                 // 칸별 최댓값으로 합친다
    [Math.max(a[0], t[0]), Math.max(a[1], t[1]), Math.max(a[2], t[2])]
  );
  return cur[0] === target[0] && cur[1] === target[1] && cur[2] === target[2];
}
```

`reduce`에 초깃값을 주지 않았기 때문에 `good`이 비어 있으면 예외가 난다. 그래서 빈 목록을 먼저 걸렀다. 시간은 O(n), 공간은 걸러 낸 목록 O(n)이다. `reduce`가 단계마다 새 배열을 만드는 것도 메모리를 쓴다. 이 풀이는 생각을 코드로 옮기기 가장 쉽지만, 목록을 따로 만들 필요는 없다.

## 한 번 훑으며 합친다

걸러 내기와 합치기를 한 반복에 넣는다. 숫자가 1 이상이니 시작값을 `[0, 0, 0]`으로 두면 빈 목록 걱정도 사라진다.

```js
function mergeTriplets(triplets, target) {
  const cur = [0, 0, 0];                            // 지금까지 합친 결과
  for (const t of triplets) {
    if (t[0] > target[0] || t[1] > target[1] || t[2] > target[2]) continue; // 독이 든 묶음
    for (let d = 0; d < 3; d++) cur[d] = Math.max(cur[d], t[d]);
  }
  return cur[0] === target[0] && cur[1] === target[1] && cur[2] === target[2];
}
```

시간 O(n), 공간 O(1)이다. 쓸 수 있는 묶음을 넣는 동안 `cur`는 칸마다 target 이하로 유지되고, 끝에서 target과 같은지만 본다. 시작값 0은 "아무것도 합치지 않은 상태"를 뜻한다. 숫자가 음수일 수 있는 변형이라면 0 대신 `-Infinity`로 시작해야 한다.

## 맞춘 칸만 표시하고 일찍 끝낸다

한 번 더 줄일 수 있다. 쓸 수 있는 묶음의 칸은 모두 target 이하이니, 최댓값이 target과 같아지려면 그 칸이 target과 같은 묶음이 하나라도 있으면 된다. 그래서 최댓값을 들고 다닐 필요 없이 "x 칸을 맞춘 적이 있나", "y 칸은", "z 칸은" 세 개의 참거짓만 기억하면 된다. 셋 다 참이 되는 순간 나머지는 볼 필요가 없다.

```js
function mergeTriplets(triplets, target) {
  let x = false, y = false, z = false;             // 목표의 세 칸을 맞춘 적이 있나
  for (const [a, b, c] of triplets) {
    if (a > target[0] || b > target[1] || c > target[2]) continue; // 독이 든 묶음
    if (a === target[0]) x = true;
    if (b === target[1]) y = true;
    if (c === target[2]) z = true;
    if (x && y && z) return true;                  // 세 칸을 다 맞췄다
  }
  return false;
}
```

목표가 `[3, 6, 4]`인 예시로 칸마다 상태를 찍었다. 괄호 안은 참고로 함께 계산한 칸별 최댓값이다.

```text
0 use false true false [ 1, 6, 2 ]
1 skip false true false [ 1, 6, 2 ]
2 use false true true [ 2, 6, 4 ]
3 use true true true [ 3, 6, 4 ]
done
```

1번 `[3, 7, 4]`는 첫 칸과 끝 칸이 목표와 같지만 가운데 칸이 7이라 버린다. 이 묶음을 버리지 않았다면 1번에서 바로 x와 z가 켜지고, 그 결과가 실제로는 만들 수 없는 조합을 가리키게 된다. 아래 그림에서 다음을 누르면 묶음을 하나씩 보며 칸이 켜지는 과정을 볼 수 있다.

이 풀이가 "칸별 최댓값"을 들고 다니지 않아도 되는 이유를 한 번 더 짚자. 쓸 수 있는 묶음만 보고 있으니 최댓값은 target을 넘을 수 없다. 넘지 못하는 최댓값이 target과 같아지는 조건은 "target과 같은 값이 한 번이라도 나왔다"와 정확히 같다.

## 실제로 어떤 연산을 하면 되나

면접관이 "그럼 연산 순서를 보여 달라"고 하면 증명을 그대로 연산으로 옮기면 된다. 쓸 수 있는 묶음 중 하나를 j로 정하고, 나머지 쓸 수 있는 묶음 i를 차례로 j에 합친다. 연산 횟수는 쓸 수 있는 묶음 수에서 1을 뺀 값이다. 만든 연산을 배열 사본에 실제로 적용해 target이 나오는지까지 확인하는 코드다.

```js
function buildOps(triplets, target) {
  const good = [];                                   // 쓸 수 있는 묶음 번호
  for (let i = 0; i < triplets.length; i++) {
    const t = triplets[i];
    if (t[0] <= target[0] && t[1] <= target[1] && t[2] <= target[2]) good.push(i);
  }
  if (good.length === 0) return null;
  const j = good[0];                                 // 여기에 모두 합친다
  const ops = good.slice(1).map(i => [i, j]);        // [i, j]: triplets[j]를 i와 합친다
  const arr = triplets.map(t => [...t]);             // 사본에 실제로 적용해 본다
  for (const [i, k] of ops)
    for (let d = 0; d < 3; d++) arr[k][d] = Math.max(arr[k][d], arr[i][d]);
  return arr[j].every((v, d) => v === target[d]) ? ops : null;
}
```

```text
[[2,0]] [[2,0],[3,0]] null
```

첫 예시는 "0번에 2번을 합친다" 한 번, 목표 `[3, 6, 4]` 예시는 0번에 2번과 3번을 차례로 합치는 두 번이다. 독 예시는 만들 수 없어 `null`이다. 무작위 입력 3만 개에서 이 함수가 연산을 돌려주는 경우와 표시 풀이가 `true`인 경우가 정확히 겹쳤다.

연산은 j 자리를 덮어쓴다는 점에 주의한다. 원래 j에 있던 묶음은 사라지지만, 그 묶음도 쓸 수 있는 묶음이라 이미 최댓값에 들어가 있으니 잃는 것이 없다. 반대로 독이 든 묶음 자리에 합치면 그 자리의 큰 칸이 남아 target이 될 수 없다. j를 쓸 수 있는 묶음 중에서 고른 이유다. 이 연산 수가 최소는 아니다. 최소 횟수는 아래 "합치는 규칙이 바뀌면"에서 따로 구한다.

## Python과 Java로 옮긴 표시 풀이

```python
from typing import List


class Solution:
    def mergeTriplets(self, triplets: List[List[int]], target: List[int]) -> bool:
        x, y, z = target
        got = [False, False, False]            # 목표의 세 칸을 맞춘 적이 있나
        for a, b, c in triplets:
            if a > x or b > y or c > z:        # 한 칸이라도 넘치면 쓰면 안 된다
                continue
            if a == x: got[0] = True
            if b == y: got[1] = True
            if c == z: got[2] = True
            if all(got):                       # 세 칸을 다 맞췄으면 더 볼 필요가 없다
                return True
        return False
```

```text
[[2, 5, 3], [1, 8, 4], [1, 7, 5]] [2, 7, 5] True
[[3, 4, 5], [4, 5, 6]] [3, 2, 5] False
[[2, 9, 1], [1, 7, 5]] [2, 7, 5] False
[[1, 1, 1]] [1, 1, 1] True
[[3, 1, 2], [1, 3, 1], [2, 1, 3]] [3, 3, 3] True
```

Python은 `for a, b, c in triplets`처럼 풀어서 받으면 읽기 쉽다. `got`을 리스트로 둔 건 `all(got)`로 한 번에 보려고 해서다. 세 칸 조건을 `all(t[d] <= target[d] for d in range(3))`처럼 제너레이터로 쓰면 깔끔하지만 느리다. 10만 개 묶음을 끝까지 훑는 입력에서 풀어 쓴 쪽이 7ms, 제너레이터 쪽이 29ms였다. 칸이 세 개로 고정이면 풀어 쓰는 쪽이 낫다.

```java
import java.util.*;

class Solution {
    public boolean mergeTriplets(int[][] triplets, int[] target) {
        boolean x = false, y = false, z = false;          // 목표의 세 칸을 맞춘 적이 있나
        for (int[] t : triplets) {
            if (t[0] > target[0] || t[1] > target[1] || t[2] > target[2]) continue; // 넘치면 버린다
            x |= t[0] == target[0];
            y |= t[1] == target[1];
            z |= t[2] == target[2];
            if (x && y && z) return true;                  // 다 맞췄으면 바로 끝낸다
        }
        return false;
    }
}
```

```text
[[2, 5, 3], [1, 8, 4], [1, 7, 5]] [2, 7, 5] true
[[3, 4, 5], [4, 5, 6]] [3, 2, 5] false
[[2, 9, 1], [1, 7, 5]] [2, 7, 5] false
[[1, 1, 1]] [1, 1, 1] true
[[3, 1, 2], [1, 3, 1], [2, 1, 3]] [3, 3, 3] true
```

`main`에서 같은 다섯 입력을 넣은 결과다. `boolean`에 `|=`를 쓰면 한 번 켜진 값이 꺼지지 않는다. `x = t[0] == target[0]`처럼 `=`만 쓰면 다음 묶음에서 다시 꺼지니 주의한다. 숫자가 1000 이하라 `int`로 충분하다.

| 모든 부분집합 | O(2^n · n) | O(1) | 작은 입력으로 답을 맞춰 볼 때 |

## 역할을 합쳐 권한을 맞추는 일과 같은 모양

이 문제의 구조는 코딩 테스트 밖에서도 나온다. 권한 시스템에서 사용자의 권한은 보통 받은 역할(role)들의 권한을 합친 것이다. 권한을 비트로 적으면 역할을 합치는 일은 비트 OR이고, OR도 최댓값처럼 한 번 켜진 비트가 꺼지지 않는다.

"이 사용자에게 정확히 읽기와 쓰기만 주고 삭제는 주지 마라"는 요구가 들어왔다고 하자. 삭제 비트가 켜진 역할은 하나만 붙여도 삭제 권한이 생기니 독이다. 독이 아닌 역할을 전부 붙였을 때 읽기와 쓰기가 다 켜지면 요구를 맞출 수 있고, 안 켜지면 기존 역할만으로는 불가능하니 역할을 새로 만들어야 한다. 역할을 하나씩 붙여 보며 시행착오를 하기 전에 이 판정을 먼저 하면, "왜 이 조합으로는 안 되는지"를 바로 설명할 수 있다.

```js
const READ = 1, WRITE = 2, DELETE = 4;
const roles = { viewer: READ, editor: READ | WRITE, admin: READ | WRITE | DELETE };
function canGrantExactly(roleBits, target) {
  let got = 0;
  for (const bits of roleBits) {
    if ((bits & ~target) !== 0) continue;          // 목표에 없는 권한이 섞인 역할은 독
    got |= bits;
  }
  return got === target;
}
console.log(canGrantExactly(Object.values(roles), READ | WRITE));  // true
console.log(canGrantExactly([roles.viewer, roles.admin], READ | WRITE)); // false
```

```text
true
false
```

`bits & ~target`이 0이 아니면 목표에 없는 비트가 켜져 있다는 뜻이고, 이게 "한 칸이라도 넘친다"에 해당한다. 두 번째 호출은 쓰기 권한을 주는 역할이 관리자뿐인데 관리자에는 삭제가 섞여 있어서 `false`다. 첫 예시의 `[2, 9, 1]`과 똑같은 상황이다.

## 칸을 따로 보다가 틀리는 자리

### 칸마다 따로 찾는다

```js
function mergeTriplets(triplets, target) {
  return [0, 1, 2].every(d => triplets.some(t => t[d] === target[d])); // 독을 걸러 내지 않았다
}
```

"칸마다 target 값을 가진 묶음이 있나"만 보는 코드다. `[[2, 9, 1], [1, 7, 5]]`, 목표 `[2, 7, 5]`에서 `true`가 나온다. 2를 가진 묶음이 가운데 칸 9라는 독을 품고 있다는 걸 놓쳤다. 정답은 `false`다. 무작위 입력 3만 개로 모든 부분집합 풀이와 맞춰 보니 7천 개 넘게 어긋났다. 맞춰 본 코드는 이렇다.

```js

```

숫자 범위를 1~4로 좁혀야 칸이 목표와 같아지는 경우가 자주 생겨서 오답이 잘 드러난다. 가장 흔한 오답이고, 문제 설명만 읽고 코드를 짜면 거의 이렇게 된다.

### 독 판정을 한 칸만 한다

맞추려는 칸만 넘치는지 보는 실수도 있다. x 칸을 켤지 정할 때 `a === target[0]`과 `a <= target[0]`만 보고 b, c를 보지 않으면 앞의 오답과 같은 입력에서 틀린다. 묶음은 세 칸이 한꺼번에 따라온다. 한 칸을 쓰려면 나머지 두 칸도 함께 들어간다.

### 넘치는지를 등호로 판정한다

`t[d] >= target[d]`를 독으로 보면 목표와 같은 칸을 가진 묶음까지 버린다. 그러면 x, y, z가 영원히 켜지지 않는다. `[[1, 1, 1]]`, 목표 `[1, 1, 1]`처럼 목표가 이미 들어 있는 입력에서 `false`가 나온다. 독은 "크다"일 때만이다.

### 연산을 직접 흉내 낸다

문제의 연산을 그대로 따라 하려고 i, j 쌍을 골라 `triplets[j]`를 바꿔 가며 탐색하면, 상태 공간이 너무 커서 끝나지 않는다. 바꾼 결과를 원래 배열에 덮어써서 다른 조합을 망치기도 한다. "어떤 집합을 고르느냐"로 문제를 바꾸는 단계가 먼저다.

### 목표가 이미 들어 있거나 묶음이 하나뿐

연산을 0번 해도 되니 target이 처음부터 배열에 있으면 `true`다. 표시 풀이는 그 묶음 하나로 세 칸이 동시에 켜져서 따로 처리하지 않아도 된다. 묶음이 하나뿐이면 i와 j를 서로 다르게 고를 수 없어 연산을 아예 못 하지만, 그 하나가 target이면 여전히 `true`이고 아니면 `false`다. 이것도 표시 풀이가 그대로 맞힌다. 연산을 직접 흉내 내는 코드는 이 경우 i ≠ j 조건 때문에 따로 손봐야 한다.

같은 묶음이 여러 번 들어 있어도 답은 변하지 않는다. 최댓값은 같은 것을 두 번 넣어도 결과가 같기 때문이다.

### reduce의 초깃값을 빼먹는다

걸러 낸 목록에 `reduce`를 쓸 때 초깃값이 없으면 빈 목록에서 `TypeError: Reduce of empty array with no initial value`가 난다. 모든 묶음이 독인 `[[3, 4, 5], [4, 5, 6]]`, 목표 `[3, 2, 5]`가 그런 입력이다. 빈 목록을 먼저 거르거나 `[0, 0, 0]`을 초깃값으로 준다.

## 합치는 규칙이 바뀌면

### 합치는 횟수를 최소로 하라면

답이 되는 집합 중 가장 작은 것을 찾으면 연산 횟수는 그 크기에서 1을 뺀 값이다. 쓸 수 있는 묶음마다 "목표와 같은 칸"을 비트 세 개짜리 마스크로 만든다. x 칸이 맞으면 1, y는 2, z는 4를 켠다. 마스크는 1부터 7까지 일곱 종류뿐이니, 나온 종류를 기록해 두고 하나, 둘, 셋을 OR 해서 7이 되는지 보면 된다.

```js
function minTriplets(triplets, target) {
  const seen = new Array(8).fill(false);           // 어떤 칸 조합을 맞춘 묶음이 있나
  for (const t of triplets) {
    if (t[0] > target[0] || t[1] > target[1] || t[2] > target[2]) continue;
    let m = 0;
    for (let d = 0; d < 3; d++) if (t[d] === target[d]) m |= 1 << d;
    seen[m] = true;
  }
  const types = [];
  for (let m = 1; m < 8; m++) if (seen[m]) types.push(m);
  if (seen[7]) return 1;                           // 이미 목표인 묶음이 있다
  for (const a of types) for (const b of types) if ((a | b) === 7) return 2;
  for (const a of types) for (const b of types) for (const c of types) if ((a | b | c) === 7) return 3;
  return -1;                                       // 만들 수 없다
}
```

```text
min bad 0 2 3 -1
```

무작위 입력 2만 개에서 모든 부분집합 풀이로 구한 최솟값과 같았다. 이 글의 첫 예시는 2개(연산 1번), `[[3, 1, 2], [1, 3, 1], [2, 1, 3]]`은 3개(연산 2번), 독 예시는 -1이다. 답은 많아야 3개다. 칸이 세 개라 세 묶음이면 모든 칸을 덮는다. 칸이 k개로 늘어나면 이 부분은 집합 덮개(set cover) 문제가 되어 쉽게 풀리지 않는다.

### 칸이 k개라면

판정 문제는 그대로 O(n · k)다. 독 판정과 맞춘 칸 표시를 k칸 모두에서 하면 된다. 증명에도 칸 수가 들어가지 않는다. 참거짓 k개를 두고, 꺼져 있던 칸이 새로 켜질 때만 개수를 하나 올리면 다 켜졌는지를 매번 k칸을 보지 않고 알 수 있다. 같은 칸을 맞추는 묶음이 여러 개일 수 있으니 참거짓 없이 개수만 세면 두 번 세게 된다.

### 최솟값으로 합친다면

연산이 칸별 최솟값이면 방향만 뒤집힌다. 목표보다 작은 칸이 있는 묶음이 독이 되고, 나머지를 모두 합쳐 target과 같은지 본다. 최솟값도 교환·결합 법칙과 멱등성이 성립하니 증명이 그대로 통한다. 반대로 합처럼 같은 걸 두 번 넣으면 결과가 바뀌는 연산이라면 이 그리디는 성립하지 않는다. 묶음 `[1, 0, 0]`, `[1, 0, 0]`, `[0, 1, 1]`과 목표 `[1, 1, 1]`을 칸별 합으로 생각해 보자. 세 묶음 모두 칸이 목표 이하라 "쓸 수 있다". 그런데 모두 더하면 `[2, 1, 1]`로 넘친다. 첫째와 셋째만 더해야 `[1, 1, 1]`이 된다. 합에서는 넣을수록 커지기만 해서 "많이 넣어도 손해가 없다"가 깨지고, 어떤 것을 고르느냐가 다시 문제가 된다. 칸이 하나라면 부분집합 합 문제와 같고, [동적 계획법](/posts/dynamic-programming)이 필요한 영역이다. 최댓값, 최솟값, 비트 OR, 비트 AND처럼 같은 것을 두 번 넣어도 결과가 같은 연산에서만 이 그리디가 통한다.

### 목표가 여러 개 들어온다면

목표 q개마다 따로 훑으면 O(n · q)다. 숫자 범위가 1000 이하로 작다는 점을 쓰면 더 줄일 여지가 있지만, 목표마다 "목표 이하인 묶음들의 칸별 최댓값"을 구하는 일은 3차원 지배 관계를 다루는 문제라 오프라인 정렬과 2차원 자료구조가 필요해진다. 면접에서는 O(n · q)를 먼저 말하고, 한 축으로 정렬해 차례로 넣는 방향만 짚어도 충분하다.

### 어떤 묶음을 합쳤는지 돌려 달라면

쓸 수 있는 묶음의 번호를 모두 돌려주면 된다. 앞의 증명대로 쓸 수 있는 것을 전부 합쳐도 target이 나오니까. 가장 적은 개수가 필요하면 위의 마스크 풀이에서 마스크마다 번호 하나를 기억해 두고 고른 마스크의 번호를 돌려준다.

같은 그리디 패턴의 다른 문제로는 [Hand of Straights](/posts/leetcode-hand-of-straights), [Valid Parenthesis String](/posts/leetcode-valid-parenthesis-string), [Candy](/posts/leetcode-candy), [IPO](/posts/leetcode-ipo)가 있다. 한 번 훑으며 판정을 이어 가는 모양은 [Jump Game](/posts/leetcode-jump-game)과도 닮았다.

## 면접에서 나올 만한 질문

### 왜 한 칸이라도 target보다 큰 묶음은 버리나요?

합치기는 칸마다 최댓값을 고르니 한 번 커진 값은 내려오지 않는다. 그 묶음을 넣은 어떤 조합도 그 칸이 target보다 커서 실패한다. 그래서 버려도 잃는 답이 없다.

### 쓸 수 있는 묶음을 전부 합쳐도 되는 이유는 뭔가요?

쓸 수 있는 묶음은 모든 칸이 target 이하라 전부 합쳐도 target을 넘지 않는다. 답이 되는 집합이 있다면 그건 쓸 수 있는 묶음의 일부이고, 전체의 최댓값은 일부의 최댓값 이상이니 target 이상이다. 이하이면서 이상이니 같다. 그래서 고를 필요 없이 다 넣고 비교하면 된다.

### 합치는 순서는 상관없나요?

상관없다. 최댓값은 교환 법칙과 결합 법칙이 성립하고 같은 것을 두 번 넣어도 결과가 같다. 그래서 어떤 순서로 몇 번 합쳐도 결과는 고른 묶음들의 칸별 최댓값 하나뿐이다. 이 성질이 문제를 "어떤 집합을 고르느냐"로 바꿔 준다.

### 칸별 최댓값을 들고 다니지 않고 참거짓 세 개로 되는 이유는?

쓸 수 있는 묶음만 보니 최댓값은 target을 넘지 못한다. 넘지 못하는 최댓값이 target과 같아지는 건 그 칸에서 target과 같은 값이 한 번이라도 나왔을 때뿐이다. 그래서 "맞춘 적이 있나"만 기억하면 되고, 셋 다 켜지면 바로 끝낼 수 있다.

### 칸마다 target 값이 있는지만 보면 왜 틀리나요?

묶음의 세 칸은 한꺼번에 따라오기 때문이다. `[2, 9, 1]`이 첫 칸 2를 주지만 가운데 9도 함께 들어와 목표 7을 넘긴다. 독을 먼저 거르지 않으면 이런 묶음이 칸을 켜 버려서 `false`인 입력에 `true`를 낸다.

### 시간과 공간 복잡도는?

묶음을 한 번 훑으니 시간 O(n), 참거짓 세 개만 쓰니 공간 O(1)이다. 답이 `true`면 세 칸이 다 켜지는 순간 끝나서 실제로는 더 빨리 끝나는 경우가 많다. 최악은 끝까지 훑는 `false` 입력이다.

### 숫자에 0이나 음수가 섞이면 바뀌는 게 있나요?

판정 논리는 그대로다. 다만 칸별 최댓값을 직접 들고 다니는 풀이는 시작값을 `[0, 0, 0]`으로 두면 안 된다. 음수 target이면 아무것도 합치지 않은 0이 이미 target을 넘어 버린다. `-Infinity`로 시작하거나 첫 쓸 수 있는 묶음으로 시작한다. 표시 풀이는 시작값이 없어서 영향을 받지 않는다.

### O(n)보다 빠르게 할 수는 없나요?

일반적으로는 없다. `false`인 입력에서 보지 않은 묶음이 하나라도 남아 있으면, 그 묶음이 마지막 남은 칸을 맞춰 줄 수도 있으니 답을 확정할 수 없다. 그래서 최악에는 모든 묶음을 한 번은 봐야 한다. 정렬은 O(n log n)이라 오히려 느리다.

### 최댓값 대신 비트 OR로 합친다면?

그대로 통한다. OR도 한 번 켜진 비트가 꺼지지 않고, 같은 것을 두 번 넣어도 결과가 같다. 목표에 없는 비트가 켜진 값, 즉 `v & ~target`이 0이 아닌 값을 독으로 거르고 나머지를 모두 OR 해서 목표와 같은지 본다. 역할을 합쳐 권한을 정하는 시스템이 이 모양이다.

### 연산 횟수의 최솟값을 구하라면?

쓸 수 있는 묶음마다 맞춘 칸을 3비트 마스크로 만들고, 나온 마스크 종류 중 OR 해서 7이 되는 가장 적은 개수를 찾는다. 종류가 일곱 가지뿐이라 하나, 둘, 셋을 모두 해 봐도 상수 시간이다. 답은 그 개수에서 1을 뺀 값이고 많아야 2번이다.
