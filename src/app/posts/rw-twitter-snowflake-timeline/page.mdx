  다만 회사가 보여 준 코드는 전체가 아니다. 보이는 부분과 보이지 않는 부분을 나눠서 읽어야 한다.

이 글은 실제 서비스 사례 시리즈의 하나다. 분산 ID의 일반 원리(비트 칸 나누기, 순번 넘침, 시계 역행)는 [고유 ID 생성기 설계](/posts/sd-unique-id-generator)에서, 쓰기 시점 팬아웃과 읽기 시점 팬아웃의 일반 설계는 [뉴스 피드 ①: 게시](/posts/sd-news-feed-publishing)에서 다뤘다. 여기서는 그 원리를 반복하지 않고, Twitter가 직접 공개한 코드와 문서에 무엇이 적혀 있는지를 따라간다.

자료는 세 묶음이다. 첫째는 2010년에 공개된 Snowflake 저장소(`twitter-archive/snowflake`, `snowflake-2010` 태그)의 README와 Scala 코드다. 둘째는 Twitter의 Raffi Krikorian가 QCon San Francisco 2012에서 발표한 ["Timelines at Scale"](https://www.infoq.com/presentations/Twitter-Timeline-Scalability/)의 슬라이드다(InfoQ 게시 2013년 4월). 셋째는 2023년에 공개된 추천 알고리즘 저장소(`twitter/the-algorithm`)의 README와 Tweetypie·Home Mixer 코드다. Snowflake를 처음 알린 2010년 Twitter 블로그 글은 사이트가 자동 접근을 막아 열지 못했고, 그 글 대신 같은 해의 저장소 README를 근거로 삼았다. 첫 자료와 마지막 자료 사이에 13년이 있고, 그사이 회사 이름도 X로 바뀌었다. 저장소 README의 제목도 지금은 "X's Recommendation Algorithm"이다.

## MySQL을 떠나며 번호표가 사라졌다

Snowflake README의 첫 문단은 동기부터 적는다. "MySQL에서 Cassandra로 옮겨 가면서 ID를 만드는 새 방법이 필요해졌다. Cassandra에는 순차 ID 생성 기능이 없고, 있어서도 안 된다." 자동 증가 키가 하던 일을 저장소 밖으로 꺼내야 했다는 뜻이다.

README는 요구 사항을 여섯 가지로 적었다. 숫자가 붙은 것은 그대로 옮긴다.

- 성능: 프로세스 하나가 초당 최소 1만 개, 응답 2ms(네트워크 지연 별도).
- 조율 없음: 데이터 센터 안팎의 고가용성을 위해 ID를 만드는 기계끼리 서로 조율하지 않는다.
- 대략적인 시간 순서: "since this id"처럼 순서를 가정하는 API가 있다. 다만 비동기 작업이 많아서 이미 순서대로 전달한다고 보장하지는 않는다. 대신 k-정렬(k-sorted)을 보장하는데, 약속은 1초, 목표는 수십 ms다.
- 바로 정렬 가능: 객체 전체를 불러오지 않고 ID만으로 정렬할 수 있어야 한다.
- 작게: 128비트로 푸는 방법은 많지만 여러 이유로 64비트 아래로 둬야 한다.
- 고가용성: 저장소 같은 관련 서비스만큼은 살아 있어야 한다.

k-정렬은 "완전히 정렬돼 있지는 않지만, 제자리에서 k 이상 벗어난 원소는 없다"는 뜻이다. Twitter는 이 k를 시간으로 잡았다. 서로 다른 기계가 만든 두 ID의 순서는 1초 안쪽에서 뒤집힐 수 있다고 처음부터 밝힌 셈이다. 나는 이 문장이 README에서 가장 쓸모 있다고 본다. 면접에서 "Snowflake ID는 시간 순서인가"를 물으면 "README가 약속한 것은 1초 범위의 대략적 순서"라고 답할 수 있다.

128비트를 버린 이유를 README는 "여러 이유"라고만 적었다. UUID를 쓰지 않은 사정이 더 궁금하겠지만, 원문이 말하지 않으니 여기서도 추측하지 않는다. UUID와 Snowflake 계열의 일반적인 장단점은 [고유 ID 생성기 설계](/posts/sd-unique-id-generator)에 있다.

## README의 10비트와 코드의 5 + 5

README는 ID 구성을 이렇게 적었다.

```text
* id is composed of:
  * time - 41 bits (millisecond precision w/ a custom epoch gives us 69 years)
  * configured machine id - 10 bits - gives us up to 1024 machines
  * sequence number - 12 bits - rolls over every 4096 per machine
    (with protection to avoid rollover in the same ms)
```

그런데 같은 태그의 `IdWorker.scala`를 열면 기계 번호 10비트가 둘로 나뉘어 있다.

```scala
// IdWorker.scala (snowflake-2010 태그) 일부
val twepoch = 1288834974657L

private[this] val workerIdBits = 5L
private[this] val datacenterIdBits = 5L
private[this] val sequenceBits = 12L

private[this] val workerIdShift = sequenceBits                                    // 12
private[this] val datacenterIdShift = sequenceBits + workerIdBits                 // 17
private[this] val timestampLeftShift = sequenceBits + workerIdBits + datacenterIdBits  // 22
```

README의 "machine id 10비트"는 코드에서 데이터 센터 5비트와 워커 5비트다. 데이터 센터 32곳, 곳마다 워커 32대, 합쳐 1,024대다. 생성자는 두 값이 31을 넘거나 음수면 `IllegalArgumentException`을 던진다. 주석은 내가 시프트 값을 계산해 붙였다.

자주 보는 그림(1 + 41 + 5 + 5 + 12)과 README의 표기(41 + 10 + 12)는 같은 것을 다르게 쓴 것이다. 41 + 10 + 12는 63이라 64비트 `Long`의 맨 위 비트 하나가 남는다. 코드에는 그 비트를 비운다는 말이 따로 없다. 시각을 22비트 민 값이 2^63을 넘기 전까지는 그 비트가 0으로 남으니, 결과적으로 양수만 나온다.

`twepoch` 1288834974657을 날짜로 바꾸면 2010-11-04T01:42:54.657Z다. 41비트로 셀 수 있는 밀리초는 약 69.7년이라, 이 기준 시점에서 2080년 7월까지 쓸 수 있다. README의 "69 years"와 맞는다.

```text
epoch iso 2010-11-04T01:42:54.657Z
end       2080-07-10T17:30:30.209Z  years 69.68
```

(위 두 줄은 `new Date(1288834974657)`과 `new Date(1288834974657 + 2**41)`을 node로 찍은 값이다.)

## 기계 번호는 설정에서 오고, ZooKeeper는 겹침만 막는다

분산 ID 설계에서 가장 까다로운 부분은 "두 서버가 같은 기계 번호를 받지 않게 하는 법"이다. 2010년 코드는 이 일을 `SnowflakeServer.scala`의 `start`에서 한다. 순서는 세 단계다.

```scala
// SnowflakeServer.scala (snowflake-2010 태그) 일부
def start {
  if (!skipSanityChecks) {
    sanityCheckPeers()          // 1. 이미 떠 있는 서버들과 맞춰 본다
  }
  registerWorkerId(workerId)    // 2. ZooKeeper에 내 번호를 건다
  Thread.sleep(startupSleepMs)  // 3. 잠깐 기다린 뒤
  ...
  server.serve()                //    Thrift 서버를 연다
}
```

먼저 볼 것은 워커 번호가 어디서 오느냐다. `SnowflakeServer`는 `workerId`를 생성자 인자로 받는다. 개발용 설정 파일 `config/development.scala`에는 `workerIdMap = Map(0 -> 호스트 이름)`, `datacenterId = 0`, `workerIdZkPath = "/snowflake-servers"`, `startupSleepMs = 10000`이 적혀 있다. 즉 번호는 사람이 설정으로 정하고, ZooKeeper는 번호를 나눠 주지 않는다. 같은 번호를 두 서버가 동시에 쓰지 못하게 막을 뿐이다.

EPHEMERAL 노드는 그 노드를 만든 ZooKeeper 세션이 끊기면 저절로 지워진다. 서버가 죽으면 번호가 풀리고, 살아 있는 동안에는 같은 번호로 다른 서버가 노드를 만들 수 없다. 재시작 직후에는 이전 세션의 노드가 아직 남아 있을 수 있어서 1초씩 두 번 기다려 본다. 그래도 있으면 `NodeExistsException`을 그대로 던진다. 번호가 겹칠 바에야 뜨지 않는 쪽을 골랐다. 세션이 살아 있는 동안만 이름을 쥐는 이 임시 노드는 분산 락과 [리더 선출](/posts/leader-election)에서 쓰는 패턴과 같다. 여기서는 "워커 번호 하나에 주인 하나"를 지키는 데 썼다.

10초 검사도 눈여겨볼 만하다. 시계가 크게 틀어진 서버는 ID 칸의 맨 위(시각)를 엉뚱하게 채운다. 미래로 10분 앞선 서버가 만든 ID는 10분 동안 다른 서버들의 ID보다 크게 정렬된다. 2010년 코드는 그런 서버를 시작 단계에서 걸러 낸다. 다만 이 검사는 시작할 때 한 번뿐이고, 도는 중에 시계가 틀어지는 것은 아래의 역행 검사만 잡는다. 시계 차이 일반은 [시계 차이](/posts/clock-skew) 글에 있다.

`startupSleepMs`의 이유는 코드가 말하지 않는다. 내 추측으로는, 같은 번호로 막 죽은 이전 프로세스가 마지막으로 만든 밀리초를 확실히 지나간 뒤에 시작하려는 장치로 보인다. 새 프로세스는 `lastTimestamp`를 -1부터 시작하니, 이전 프로세스의 마지막 밀리초와 같은 밀리초에 순번 0부터 다시 쓰면 번호가 겹칠 수 있다. 10초를 쉬면 그 창이 닫힌다. 어디까지나 코드로 본 해석이다.

## 시계가 뒤로 가면 기다리지 않고 거절한다

번호를 만드는 `nextId`는 짧다.

```scala
// IdWorker.scala (snowflake-2010 태그) 일부
protected[snowflake] def nextId(): Long = synchronized {
  var timestamp = timeGen()
  if (timestamp < lastTimestamp) {
    throw new InvalidSystemClock("Clock moved backwards.  Refusing to generate id for %d milliseconds"
      .format(lastTimestamp - timestamp))
  }
  if (lastTimestamp == timestamp) {
    sequence = (sequence + 1) & sequenceMask
    if (sequence == 0) {
      timestamp = tilNextMillis(lastTimestamp)   // 4,096개를 다 쓰면 다음 ms까지 바쁘게 돈다
    }
  } else {
    sequence = 0
  }
  lastTimestamp = timestamp
  ((timestamp - twepoch) << timestampLeftShift) | (datacenterId << datacenterIdShift) |
    (workerId << workerIdShift) | sequence
}
```

세 가지를 읽을 수 있다. `synchronized`로 한 프로세스 안의 생성을 한 줄로 세웠다. README가 "기계끼리 조율하지 않는다"고 한 것은 기계 사이의 이야기고, 기계 안에서는 잠금을 건다. 시계가 뒤로 가면 기다리지 않고 바로 예외를 던진다. 클라이언트는 그 요청을 실패로 받는다. 순번이 넘치면 `tilNextMillis`가 sleep 없이 시계를 계속 읽으며 다음 밀리초를 기다린다.

README는 시계 문제에 처방도 붙였다. NTP로 시계를 정확하게 유지하고, 가능하면 NTP가 시계를 뒤로 돌리지 않는 모드로 돌리라고 한다. 거절과 대기 중 무엇을 고를지의 일반론과 단계별 그림은 [고유 ID 생성기 설계의 시계 역행 부분](/posts/sd-unique-id-generator)에 있다.

같은 파일의 `get_id`는 번호를 돌려주기 전에 두 가지를 더 한다. useragent별로 생성 개수를 센다(`ids_generated_%s`). 그리고 만든 ID와 useragent를 `AuditLogEntry`로 `reporter`에 넘긴다. 개발용 설정에서 이 reporter는 Scribe(`scribeCategory = "snowflake"`)로 로그를 보낸다. 어떤 서비스가 어떤 번호를 받아 갔는지 나중에 되짚을 수 있게 남긴 것이다. ID 서비스를 직접 만든다면 이 정도의 호출자 기록은 장애 분석에 바로 쓸모가 있다.

## 2010년 코드는 은퇴했다

같은 저장소의 기본 브랜치 README는 다른 이야기를 한다. 처음 공개한 Snowflake는 은퇴시켰고, Twitter-server 기반의 다음 버전을 Twitter 바깥에서도 돌 수 있는 모양으로 공개하려 한다고 적었다. 2010년판은 Apache Thrift 위에 만들어졌고 Twitter의 RPC 프레임워크인 Finagle보다 먼저 나왔다. 사내에서 쓰는 Snowflake는 "전체를 다시 쓴 것"이고 Twitter의 기존 인프라에 크게 기댄다고 한다. 공개 날짜는 약속하지 않았고, 저장소는 지금 보관(archived) 상태다.

그러니 2010년 코드를 "Twitter가 지금 쓰는 ID 서버"로 읽으면 안 된다. 다시 쓴 버전의 비트 구성이 같은지도 README는 말하지 않는다. 그런데 2023년 코드에서 그 답의 일부가 보인다.

## 2023년 코드에서 다시 만난 번호

2023년 공개 저장소의 Tweetypie는 트윗을 읽고 쓰는 핵심 서비스다. README는 클라이언트(GraphQL 경유)와 여러 내부 서비스가 트윗을 가져오고, 만들고, 지우고, 고칠 때 Tweetypie를 부른다고 설명한다. 이 서비스의 패키지 객체에 트윗의 작성 시각을 구하는 함수가 있다.

```scala
// tweetypie/server/.../tweetypie/package.scala 일부
import com.twitter.snowflake.id.SnowflakeId

def getTimestamp(tweet: Tweet): Time =
  if (SnowflakeId.isSnowflakeId(tweet.id)) SnowflakeId(tweet.id).time
  else Time.fromSeconds(getCreatedAt(tweet).toInt)
```

트윗 시각을 저장된 필드보다 ID에서 먼저 읽는다. ID가 Snowflake 형식이 아니면, 즉 Snowflake 이전에 만들어진 트윗이면 `createdAt` 필드로 돌아간다. 2010년 README가 말한 "객체를 불러오지 않고 정렬" 요구가 13년 뒤 코드에서 "객체 필드 대신 ID로 시각 계산"으로 남아 있는 셈이다. `SnowflakeId` 클래스 자체의 구현은 이 저장소에 없어서, 사내 버전의 비트 구성이 2010년판과 똑같은지는 이 코드만으로 확인할 수 없다. `isSnowflakeId`가 무엇으로 판별하는지도 보이지 않는다.

아래 플레이그라운드는 2010년판 구성(시각 41 · 데이터 센터 5 · 워커 5 · 순번 12, 기준 시점 1288834974657)으로 ID를 칸별로 풀어 본다. 64비트 정수는 자바스크립트 `Number`에 정확히 담기지 않으니 문자열로 받아 `BigInt`로 계산한다.

## 2012년: 트윗 하나를 팔로워 수만큼 Redis에 밀어 넣던 때

2023년 코드를 보기 전에, Twitter가 홈 타임라인을 어떻게 만들었는지 직접 설명한 자료부터 본다. Raffi Krikorian(당시 Twitter Applications Services 그룹 Senior Director)의 QCon SF 2012 발표 슬라이드다. 영상은 보지 않았고, 아래 숫자와 구조는 모두 슬라이드에 적힌 것이다.

슬라이드가 내건 과제는 세 줄이다. 전 세계 활성 사용자 1억 5천만 명 이상, 타임라인 조회 초당 30만 건 이상, 그리고 "순진한 타임라인 구체화(materialization)는 느릴 수 있다." 홈 타임라인을 읽을 때마다 팔로우한 사람들의 트윗을 모아 정렬하면 늦다는 뜻이다. 그래서 쓸 때 미리 만들어 둔다.

트윗이 Write API로 들어오면 Fanout이 Social Graph Service에서 작성자의 팔로워 목록을 받아, 팔로워마다 Timeline Cache(Redis)의 목록에 트윗을 넣는다. 슬라이드는 이 insert를 세 줄로 요약한다. 받는 사람(recipient) 기준으로 키를 잡고, 목적지 4천 개씩 파이프라인으로 묶어 보내고, 복제한다. Redis에는 기본 자료구조인 리스트를 쓰고, 항목 하나는 Tweet ID 8바이트, User ID 8바이트, 비트 필드 4바이트다. 트윗 본문은 넣지 않는다. 그리고 `RPUSHX`로 "이미 캐시에 있는 타임라인에만" 붙인다. `RPUSHX`는 키가 있을 때만 리스트에 넣는 Redis 명령이라, 캐시에 타임라인이 없는(최근에 오지 않은) 사용자에게는 쓰지 않는다.

읽을 때는 Timeline Service가 Redis에서 ID 목록을 꺼내고, Gizmoduck(사용자 서비스)과 TweetyPie(트윗 서비스)에서 내용을 채워 돌려준다. 2023년 코드의 Tweetypie가 이 TweetyPie다. 이것이 [뉴스 피드 ①](/posts/sd-news-feed-publishing)에서 본 쓰기 시점 팬아웃(push)이 실제 서비스에서 쓰인 모습이다. 캐시에 ID만 넣고 본문은 읽을 때 채우는 것도 그 글의 설계와 같다.

같은 슬라이드에 검색 쪽도 있다. 트윗은 Ingester를 거쳐 Earlybird(검색 색인)에도 들어가고, Blender가 "모든 색인의 복제본 하나씩에 질의해 결과를 합치고 순위를 매긴다." 슬라이드는 두 길을 나란히 놓고 비용을 적었다.

타임라인은 쓰기가 O(n)이고 읽기가 O(1)이다. 팔로워 n명에게 한 번씩 쓰고, 읽을 때는 내 리스트 하나만 읽는다. 검색은 반대로 쓰기 O(1), 읽기 O(n)이다. 색인에 한 번 넣고, 읽을 때 모든 색인 파티션에 묻는다. 슬라이드의 운영 숫자도 이 비대칭을 보여 준다. 트윗 입력은 하루 약 4억 건, 일 평균 초당 약 5천 건, 하루 최고 초당 약 7천 건, 큰 이벤트 때는 초당 1만 2천 건 이상이다. 그런데 배달은 하루 300억 건(분당 약 2,100만 건), 초당 약 30만 건이다. 들어온 트윗보다 수천 배 많은 쓰기가 팬아웃에서 생긴다. 읽기는 폴링 기반 타임라인이 초당 30만 건 이상에 p50 1ms, p99 4ms였고, 검색 기반 타임라인은 초당 3만 건 이상이었다.

### 팔로워 3천만 명의 트윗

슬라이드의 "과제 2부"는 "팬아웃이 정말 느릴 수 있다, 특히 팔로워가 많으면"이다. 예로 든 계정은 팔로워 3,100만(@ladygaga), 2,800만(@katyperry, @justinbieber), 2,300만(@barackobama)이다. 배달 통계의 한 줄, "100만 명에게 배달하는 데 p50 3.5초"를 대 보면, 팔로워 3천만 명의 트윗은 마지막 팔로워에게 닿기까지 훨씬 오래 걸린다고 짐작할 수 있다. 그동안 그 트윗에 답한 다른 사람의 트윗이 먼저 도착하는 일도 생긴다.

슬라이드는 이어서 검색 색인과 "팬아웃 색인"을 나란히 놓는다. 검색 색인은 `['hello', 'world']`처럼 단어로, 팬아웃 색인은 `[@danadanger, ...]`처럼 받는 사람으로 찾는다. 그리고 사용자 의도를 질의로 펼치는 표를 보여 준다. "@raffi의 홈 타임라인"은 `home_timeline:raffi`로 펼쳐지고, 다음 장에서는 `home_timeline:raffi OR user_timeline:taylorswift13`이 된다. 미리 채운 내 타임라인에, 팔로워가 아주 많은 계정의 사용자 타임라인을 읽을 때 합치는 모양이다. [뉴스 피드 ①](/posts/sd-news-feed-publishing)의 혼합 팬아웃(대부분은 밀고, 유명인만 당긴다)과 같은 생각이다. 다만 슬라이드만으로는 이것이 당시 운영 중이던 방식인지, 방향을 보여 준 예시인지 구분할 수 없다. 기준 팔로워 수 같은 숫자도 슬라이드에는 없다.

마지막 구조도는 경로를 셋으로 나눈다. Write API까지가 동기 경로, Ingester·Fanout·HTTP Push·Mobile Push가 비동기 경로, Blender와 Timeline Service가 질의 경로다. 트윗 저장은 응답 안에서 끝내고 팬아웃은 뒤에서 한다는 뜻이다. 2023년 코드의 `AsyncInsertTweet`가 같은 자리에 있다.

## 트윗 하나가 저장된 뒤 일어나는 일

이제 11년 뒤의 코드로 간다. Tweetypie README는 쓰기 경로를 이렇게 설명한다. `PostTweet.scala`가 요청을 받고, `TweetBuilder`가 텍스트 처리·검증·URL 단축·미디어 처리·중복 검사를 거쳐 트윗을 만들고, `InsertTweet.scala`에 적힌 저장소들에 쓴다.

`InsertTweet.scala`를 열면 저장소가 두 묶음으로 나뉘어 있다. 요청 안에서 바로 쓰는 묶음에는 Manhattan(트윗 본체를 담는 Twitter의 분산 DB), 캐시, 리미터, 비동기 큐 넣기, 사용자·트윗 카운트 갱신이 있다. 캐시와 리미터에는 `ignoreFailures`가 붙어 있어서 실패해도 트윗 저장을 막지 않는다. 비동기 묶음(`AsyncInsertTweet`)에는 아래 저장소들이 들어 있고, `FutureEffect.inParallel`로 동시에 실행된다.

```scala
// tweetypie/server/.../store/InsertTweet.scala 일부 (AsyncInsertTweet.Store)
val stores: Seq[Store] = Seq(
  replicatingStore,
  indexingStore,
  timelineUpdatingStore,     // TlsTimelineUpdatingStore
  eventBusEnqueueStore,
  fanoutServiceStore,        // FanoutServiceStore
  userGeotagUpdateStore,
  tweetCountsUpdatingStore,
  scribeMediaTagStore,
  geoSearchRequestIDStore
)
```

`FanoutServiceStore`는 `com.twitter.timelineservice.fanout`의 `FanoutService` 클라이언트로 `tweetCreateEvent2`를 부른다. 넘기는 값은 트윗, 작성자, 리트윗이면 원본 트윗과 원본 작성자다. `TlsTimelineUpdatingStore`는 타임라인 서비스(TLS)에 `FullTweetCreate` 이벤트를 보낸다. 이벤트에는 작성자 ID, 트윗 ID, 멘션된 사용자, 답글·리트윗·인용 관계, `createdAtMs`가 들어간다. 삭제와 복구도 같은 저장소가 `FullTweetDelete`, `FullTweetRestore`로 알린다. 두 저장소 모두 실패하면 `TweetStore.retry`로 다시 시도하는 경로가 있다.

여기까지가 코드가 보여 주는 쓰기 쪽이다. 팬아웃 서비스가 그 이벤트를 받아 팔로워 몇 명의 무엇에 어떻게 쓰는지는 이 저장소에 없다. 클라이언트 호출만 있고 서버 코드는 없다.

## 홈 타임라인은 읽을 때 다시 모은다

Home Mixer README는 홈 타임라인의 세 탭을 이 서비스가 만든다고 적었다. For You(팔로우한 사람의 좋은 트윗 + 추천), Following(팔로우한 사람의 트윗을 최신순으로), Lists(리스트 멤버의 트윗을 최신순으로)다. 탭마다 파이프라인 구성이 다르다.

```text
Following
- FollowingProductPipelineConfig
    - FollowingMixerPipelineConfig
        - FollowingEarlybirdCandidatePipelineConfig (fetch tweets from Search Index)
        ...
Lists
- ListTweetsProductPipelineConfig
    - ListTweetsMixerPipelineConfig
        - ListTweetsTimelineServiceCandidatePipelineConfig (fetch tweets from timeline service)
        ...
```

최신순 Following 탭조차 트윗 후보를 검색 색인(Earlybird)에서 가져온다. 리스트 탭은 타임라인 서비스에서 가져온다. 검색 README도 같은 말을 한다. "팔로우하는 사용자 목록이 주어지면 그들이 최근 올린 트윗을 찾는다. Earlybird가 Following 탭과 For You 탭 모두에서 팔로우한 사람 트윗의 주된 후보 소스다."

Earlybird는 Lucene 기반의 실시간 검색 시스템이다. README에 따르면 색인은 세 클러스터로 나뉜다. 최근 약 7일의 공개 트윗을 담는 realtime, 같은 기간의 비공개 트윗을 담는 protected, 약 이틀 전까지의 모든 트윗을 담는 archive다. 클러스터마다 여러 파티션으로 나뉘고, 루트가 요청을 파티션들로 펼쳤다가 응답을 합쳐 돌려준다. 하나의 쓰기 스레드와 여러 읽기 스레드 구조로 색인 갱신과 질의를 동시에 처리한다고 적었다. 단어 대신 작성자 ID로 찾는다는 점만 다를 뿐 [역색인](/posts/elasticsearch-inverted-index)이고, 루트가 파티션 전체에 묻고 합치는 방식은 [샤딩 입문](/posts/sd-sharding-intro)에서 본 scatter-gather 그대로다. 팔로우 목록은 샤드 키가 아니니 모든 파티션에 물어야 한다.

For You는 그 위에 단계가 더 붙는다. 후보 생성(Earlybird, UTEG, Cr Mixer, 팔로우 추천 서비스) → 약 6,000개 특징 붙이기 → ML 모델로 점수 → 필터(작성자 다양성, 팔로우 안팎 비율, 피드백 피로도, 이미 본 트윗 제거, 차단·뮤트) → 광고·팔로우 추천 섞기 순이다. README에는 점수 매기기 파이프라인이 실패할 때를 대비한 "backup reverse chron pipeline"도 적혀 있다. 추천이 죽으면 최신순으로라도 보여 주겠다는 장치다.

`timelineranker` README는 이 구성의 이전 모습을 살짝 보여 준다. TimelineRanker는 Earlybird와 UTEG에서 관련도 점수가 붙은 트윗을 가져다주는 "레거시 서비스"이고, 이름과 달리 이제 무거운 랭킹은 하지 않는다고 적었다. 랭킹이 Home Mixer와 별도 모델로 옮겨 간 흔적이다.

## 미는 길과 당기는 길이 함께 있다

정리하면 2023년 코드에는 두 길이 다 있다. 쓰기 경로는 트윗이 저장되면 팬아웃 서비스와 타임라인 서비스에 이벤트를 보낸다. 읽기 경로의 Home Mixer는 팔로우한 사람의 트윗을 검색 색인에서 읽을 때 다시 찾는다.

2012년 슬라이드와 나란히 놓으면 변화가 보인다. 2012년에는 홈 타임라인이 Redis에 미리 채운 목록(push)이었고, 검색 색인은 검색 기반 타임라인과 검색에 쓰였다. 2023년 코드에서는 팬아웃 서비스 호출이 쓰기 경로에 그대로 남아 있지만, Home Mixer의 For You와 Following 탭은 팔로우 안쪽 후보를 Earlybird에서 가져온다. 2012년 슬라이드에서 검색 쪽에 있던 "읽을 때 펼치는 길"이 홈 타임라인의 주 후보 소스가 됐다. 공개 코드만으로는 팬아웃 서비스가 2023년에 무엇을 채우는지, 그 결과를 Home Mixer가 어디서 읽는지는 확인할 수 없다. 리스트 탭이 타임라인 서비스에서 읽는다는 것까지만 보인다. 언제, 왜 바뀌었는지 설명한 1차 자료는 이번에 찾지 못했다.

그래서 이 그림에서 확실히 말할 수 있는 것은 이 정도다. 2023년 시점 For You와 Following 탭의 팔로우 안쪽 후보는 읽을 때 검색 색인에서 모은다. 색인은 최근 7일 클러스터를 따로 두고, 파티션으로 펼쳐 질의한다. 이 설계라면 팔로워가 수천만인 계정의 트윗도 색인에 한 번 들어가면 되니, 2012년 슬라이드가 "과제 2부"로 꼽은 유명인 팬아웃 지연이 이 탭들에서는 줄어들었을 것이다. 추천 랭킹이 들어오면서 어차피 후보를 넓게 모아 점수를 매겨야 했다는 사정도 있었을 것이다. 대신 홈을 열 때마다 파티션 전체에 질의가 펼쳐지는 비용, 슬라이드의 표현으로 O(n) 읽기를 낸다. 이 해석은 두 자료의 구조를 비교해 끌어낸 추론이다.

## 공개 코드가 말하지 않는 것

두 저장소 모두 회사가 고른 부분만 담았다. 2023년 저장소 README는 대부분의 구성 요소에 Bazel BUILD 파일은 있지만 최상위 BUILD나 WORKSPACE는 없다고 밝힌다. 공개 코드를 그대로 빌드해 돌릴 수는 없다. 팬아웃 서비스, 타임라인 서비스, `SnowflakeId` 클래스처럼 이름만 나오고 구현이 빠진 부품이 많다. 사내 저장소와 얼마나 맞춰지고 있는지도 알 수 없다. 2010년 Snowflake는 은퇴했다고 회사가 직접 말했다. 2012년 슬라이드는 운영 숫자를 주지만 발표 시점의 숫자이고, 영상에서 덧붙였을 맥락은 이 글에 없다. 2023년 코드에는 처리량이나 지연 같은 운영 지표가 없다. 장애 이야기, 운영 비용, 버린 대안의 실측치는 셋 중 어디에도 없다. 그래서 2012년과 2023년 사이에 무엇이 언제 왜 바뀌었는지는 비어 있는 채로 두었다.

## 번호표와 피드를 내 서비스에 들일 때

Snowflake의 요구 사항 목록은 그대로 체크리스트로 쓸 만하다. 프로세스당 초당 1만 개, 응답 2ms, 64비트 이하, 1초 범위의 대략적 순서, 데이터 센터 사이 조율 없음. 이 다섯 가지가 다 필요한 서비스가 Snowflake 같은 별도 ID 서버를 정당화한다. 쓰기가 DB 한 대에 모이고 초당 수백 건이라면 DB 시퀀스로 충분하다. 64비트 제약이 없고 정렬만 필요하면 UUIDv7이 서버 없이 같은 성질을 준다. 비교는 [고유 ID 생성기 설계](/posts/sd-unique-id-generator)에 있다.

처음부터 따라 하면 드는 비용도 코드에 보인다. ID 서버 하나에 ZooKeeper 클러스터, 시작 시 이웃 검사, 감사 로그 파이프라인이 따라온다. 워커 번호 표를 사람이 관리해야 하고, 시계를 NTP로 지켜봐야 하고, ID 서버가 죽으면 글쓰기가 멈추니 ID 서버 자체도 여러 대를 돌려야 한다. 샤드 번호를 ID에 넣어 같은 효과를 DB 안에서 낸 방식은 [Pinterest 사례](/posts/rw-pinterest-mysql-sharding)에 있다.

작은 팀이 지금 바로 가져올 만한 것은 둘이다. 하나는 "번호가 겹칠 바에야 뜨지 않는다"는 태도다. 워커 번호를 설정으로 주더라도, 시작할 때 임시 노드나 DB 임대 행으로 같은 번호가 이미 쓰이는지 확인하고 있으면 실패한다. 다른 하나는 시계 역행을 조용히 넘기지 않는 것이다. 역행을 감지하면 예외와 지표(역행 횟수, 역행한 ms)를 함께 남긴다. 임대와 리더 선출의 일반론은 [리더 선출](/posts/leader-election)에 있다.

비슷한 신호가 보이면 먼저 볼 곳도 정해 둔다. 중복 키 오류가 드물게 나는데 재현이 안 되면 같은 워커 번호로 뜬 프로세스가 둘인지, 재시작 직후에 몰렸는지부터 본다. 목록 순서가 가끔 뒤집힌다는 문의라면 서버들의 시계 차이와 NTP 로그를 본다. ID 순서는 1초 범위의 대략적 순서라는 README의 약속을 다시 떠올리면 된다.

홈 타임라인은 규모가 다르면 같은 답이 아니다. Twitter의 2023년 구성은 실시간 검색 색인이라는 큰 시스템이 이미 있었기에 가능한 선택이다. 그런 색인이 없는 서비스라면 [뉴스 피드 ①](/posts/sd-news-feed-publishing)의 혼합 팬아웃처럼 Redis 목록에 미리 넣어 두는 쪽이 훨씬 싸다. 2012년 슬라이드에서 가져올 습관도 하나 있다. 캐시에는 ID만 넣고, `RPUSHX`처럼 캐시에 이미 있는 타임라인에만 붙여서 오래 안 들어온 사람에게 쓰기를 낭비하지 않는다. 피드가 늦게 뜬다는 문의가 오면 팬아웃 큐의 적체와, 늦게 뜬 글의 작성자 팔로워 수부터 본다. 슬라이드가 100만 명 배달에 p50 3.5초를 적었듯, 팔로워가 많은 작성자의 글이 줄 앞을 막고 있을 수 있다. 반대로 추천과 랭킹이 중심인 서비스라면 미리 넣어 둔 목록은 후보의 일부일 뿐이고, 결국 읽을 때 다시 모아 점수를 매기게 된다. Home Mixer가 추천 파이프라인이 실패하면 최신순 파이프라인으로 돌아가게 해 둔 것처럼, 랭킹이 죽어도 보여 줄 기본 경로를 처음부터 둔다.

Snowflake 동기에 나온 Cassandra로 메시지 저장소를 옮겼다가 다시 옮긴 이야기는 같은 시리즈의 [Discord 사례](/posts/rw-discord-message-storage)에 있다.

## 면접에서 나올 만한 질문

### Twitter는 왜 Snowflake를 만들었나요?

MySQL에서 Cassandra로 옮기면서 자동 증가 키를 쓸 수 없게 됐기 때문이다. 2010년 README가 그렇게 적었다. 요구 사항은 프로세스당 초당 1만 개 이상, 응답 2ms, 기계 사이 조율 없음, 대략적인 시간 순서, 64비트 이하였다. DB 밖에서 조율 없이 정렬 가능한 64비트 번호를 만드는 것이 목표였다.

### Snowflake ID는 정확한 시간 순서인가요?

아니다. README는 k-정렬을 약속했고 그 범위를 1초로, 목표를 수십 ms로 적었다. 한 기계 안에서는 `synchronized`와 시계 역행 거절 덕분에 단조 증가하지만, 서로 다른 기계의 ID는 시계 차이만큼 뒤집힐 수 있다. 정확한 앞뒤가 필요한 곳에서는 ID 순서에 기대지 않는다.

### README에는 기계 번호가 10비트인데 코드는 왜 5비트 두 개인가요?

같은 10비트를 데이터 센터 5비트와 워커 5비트로 나눠 쓴 것이다. 그래서 시프트가 12(워커), 17(데이터 센터), 22(시각)가 된다. 데이터 센터마다 워커를 독립적으로 배정할 수 있어서 운영이 편해진다. 대신 한 데이터 센터에 32대를 넘게 둘 수 없다는 제약이 생긴다.

### 두 서버가 같은 워커 번호로 뜨는 것은 어떻게 막았나요?

번호 자체는 설정에서 오고, ZooKeeper에 그 번호로 EPHEMERAL 노드를 만들어 겹침을 막았다. 노드가 이미 있으면 1초씩 두 번 다시 시도하고, 그래도 있으면 시작을 포기한다. 시작 전에 이웃 서버들에게 RPC로 워커·데이터 센터 번호를 확인하고, 시각 평균과 10초 넘게 차이 나면 뜨지 않는다. 겹친 번호를 내주느니 서비스를 못 하는 쪽을 골랐다.

### 2012년 Twitter의 홈 타임라인은 어떻게 만들어졌나요?

쓸 때 미리 채웠다. QCon 2012 슬라이드에 따르면 Fanout이 Social Graph Service에서 팔로워를 받아 팔로워마다 Redis 리스트에 Tweet ID·User ID·비트 필드(합쳐 20바이트)를 넣었고, 목적지 4천 개씩 파이프라인으로 묶었다. `RPUSHX`로 캐시에 있는 타임라인에만 붙였다. 그래서 타임라인 읽기는 초당 30만 건 이상을 p50 1ms로 처리했지만, 하루 4억 건의 트윗이 하루 300억 건의 배달이 됐다.

### 팔로워가 3천만 명인 계정이 트윗하면 무엇이 문제였나요?

팬아웃이 느려진다. 슬라이드는 이를 "과제 2부"로 꼽고 팔로워 2,300만~3,100만 계정을 예로 들었고, 100만 명에게 배달하는 데 p50 3.5초라는 숫자를 적었다. 슬라이드는 미리 채운 홈 타임라인에 유명인의 사용자 타임라인을 읽을 때 합치는 질의 확장(`home_timeline:raffi OR user_timeline:taylorswift13`)을 보여 준다. 다만 슬라이드만으로는 그 방식이 운영 중이었는지 확인할 수 없다.

### 2023년 공개 코드로 보면 홈 타임라인은 push인가요, pull인가요?

둘 다 보인다. 트윗을 저장하면 Tweetypie가 비동기로 팬아웃 서비스와 타임라인 서비스에 이벤트를 보낸다. 그런데 Home Mixer의 For You와 Following 탭은 팔로우한 사람의 트윗을 Earlybird 검색 색인에서 읽을 때 가져오고, README는 For You 글의 약 50%가 그 소스에서 온다고 적었다. 팬아웃 서비스의 내부는 공개되지 않아 홈 탭에 어떻게 쓰이는지는 코드로 확인할 수 없다.

### 우리 서비스가 Twitter의 백분의 일 규모라면 같은 구조를 쓰나요?

대개 쓰지 않는다. Snowflake는 초당 1만 개, 조율 없는 다중 데이터 센터 생성이라는 요구에서 나왔고, 그 요구가 없으면 DB 시퀀스나 UUIDv7이 운영 부담이 적다. 홈 타임라인도 실시간 검색 색인이라는 큰 인프라가 이미 있어서 읽기 시점 수집이 가능했다. 그런 인프라가 없다면 미리 넣어 두는 피드 목록이 더 싸고, 유명인만 따로 당기는 혼합 방식으로 충분하다.
