회원 가입 폼에 이미 있는 이메일을 대문자만 바꿔 넣었다. 브라우저 개발자 도구에 이런 응답이 찍혔다.

```text
HTTP/1.1 500 Internal Server Error
content-type: application/json
Content-Length: 78

{"error":"duplicate key value violates unique constraint \"users_email_key\""}
```

사용자 잘못으로 생긴 일인데 서버 오류(500)가 났고, 응답 본문에는 DB 제약 이름이 그대로 실려 나왔다. 코드에는 컨트롤러, 서비스, 리포지토리 폴더가 다 있었다. 계층은 나눠 놓았지만, 계층 사이에서 해야 할 일 하나를 하지 않았다.

이 글은 레이어드 아키텍처를 다룬다. 계층을 나누는 규칙, 계층과 티어의 차이, 에러와 트랜잭션을 어느 계층이 맡는지, 그리고 이 구조가 한계에 닿는 지점까지 본다. 계층을 어떤 단위 안에 둘지는 [모듈러 모놀리스 글](/posts/modular-monolith)에서, 한 덩어리 구조 자체는 [모놀리스 아키텍처 글](/posts/monolith-architecture)에서 다뤘다.

## 위에서 아래로만 부른다

레이어드 아키텍처는 코드를 역할별 층으로 쌓고, 위층이 바로 아래층만 부르게 하는 구조다. 웹 백엔드에서 흔한 모양은 네 층이다.

- 프레젠테이션 계층: HTTP 요청을 해석하고 응답을 만든다. 컨트롤러, 라우트 핸들러가 여기 있다.
- 비즈니스 계층: 업무 규칙을 검사하고 일의 순서를 정한다. 서비스라고 부르는 곳이다.
- 퍼시스턴스 계층: 데이터를 읽고 쓰는 방법을 안다. 리포지토리, DAO가 여기 있다.
- 데이터베이스: 실제 저장소다.

규칙은 두 가지다. 의존은 위에서 아래로만 흐른다. 그리고 각 층은 자기 바로 아래층만 안다. 컨트롤러는 SQL을 모르고, 리포지토리는 HTTP 상태 코드를 모른다. 이렇게 하면 한 층을 바꿀 때 영향이 바로 위층에서 멈춘다. MySQL을 PostgreSQL로 바꾸면 퍼시스턴스 계층이, REST를 GraphQL로 바꾸면 프레젠테이션 계층이 바뀐다.

## 계층은 코드, 티어는 기계

레이어드 아키텍처를 N-tier 아키텍처라고 부르는 글도 많은데, 엄밀히는 두 단어가 가리키는 게 다르다. 레이어(layer)는 코드를 논리적으로 나눈 것이고, 티어(tier)는 그 코드가 실제로 돌아가는 물리적인 위치다.

네 계층을 서버 한 대, 프로세스 하나에 다 올릴 수 있다. 이건 4계층 1티어다. 흔히 말하는 3티어 구조는 브라우저(또는 웹 서버), 애플리케이션 서버, DB 서버가 서로 다른 기계에 있는 것이다. 이때 프레젠테이션·비즈니스·퍼시스턴스 계층은 보통 애플리케이션 서버 티어 하나에 함께 있다.

## 에러는 층을 건널 때 번역한다

처음 장면으로 돌아간다. Node 22와 PostgreSQL 16으로 같은 구조를 만들었다. 이메일 유니크 인덱스는 대소문자를 무시하게 `lower(email)`에 걸었다.

```sql
CREATE TABLE users (id serial PRIMARY KEY, email text NOT NULL, name text NOT NULL);
CREATE UNIQUE INDEX users_email_key ON users (lower(email));
```

리포지토리가 드라이버 에러를 그대로 던지고, 컨트롤러는 모르는 에러를 500으로 돌려주며 `message`를 본문에 실었다. 같은 이메일로 두 번 가입했다.

```bash
curl -s -i -X POST localhost:8702/users -d '{"email":"kim@example.com","name":"kim"}'
curl -s -i -X POST localhost:8702/users -d '{"email":"Kim@Example.com","name":"kim"}'
```

```text
HTTP/1.1 201 Created
content-type: application/json
Content-Length: 34

{"id":1,"email":"kim@example.com"}

HTTP/1.1 500 Internal Server Error
content-type: application/json
Content-Length: 78

{"error":"duplicate key value violates unique constraint \"users_email_key\""}
```

(응답 헤더 중 Date, Connection, Keep-Alive 줄은 뺐다.) 드라이버가 던진 에러 객체를 열어 보면 무엇이 새어 나갈 수 있는지 보인다.

고치는 방법은 층마다 자기 말로 바꿔 올리는 것이다. 리포지토리가 드라이버 에러를 업무 에러로 바꾸고, 컨트롤러가 업무 에러를 HTTP 상태 코드로 바꾼다. 서비스는 둘 다 모른 채 업무 에러만 다룬다.

```ts
// repository.ts: 드라이버 에러는 여기서 끝낸다
export class EmailTakenError extends Error {}

export const userRepository = {
  async insert(email: string, name: string) {
    try {
      const { rows } = await pool.query(
        "INSERT INTO users (email, name) VALUES ($1, $2) RETURNING id, email",
        [email, name],
      );
      return rows[0] as { id: number; email: string };
    } catch (e: any) {
      if (e.code === "23505") throw new EmailTakenError(email);
      throw e;
    }
  },
};
```

```ts
// controller.ts: 업무 에러를 상태 코드로 바꾼다. 모르는 에러는 내용을 숨긴다
} catch (e: any) {
  if (e instanceof InvalidEmailError) { res.statusCode = 400; res.end(JSON.stringify({ error: "invalid_email" })); return; }
  if (e instanceof EmailTakenError) { res.statusCode = 409; res.end(JSON.stringify({ error: "email_taken" })); return; }
  res.statusCode = 500;
  res.end(JSON.stringify({ error: "internal" }));
}
```

번역을 넣고 같은 요청을 다시 보냈다.

```text
HTTP/1.1 201 Created

Content-Length: 34

{"id":1,"email":"kim@example.com"}

HTTP/1.1 409 Conflict
content-type: application/json
Content-Length: 23

{"error":"email_taken"}
```

마지막 두 경우가 `Unknown`인 데 이유가 있다. 타임아웃이나 연결 실패는 사용자 잘못이 아니라 진짜 서버 문제라서 500이 맞다. 모든 에러를 400대로 바꾸려 들면 이번엔 장애가 알림에서 사라진다.

## 트랜잭션 경계는 서비스가 쥔다

가입하면 환영 쿠폰도 함께 만든다고 해 보자. 사용자 저장과 쿠폰 저장은 둘 다 리포지토리 일이다. 그럼 트랜잭션은 누가 여는가. 쿠폰 코드에 8자 제한 CHECK를 걸고, 일부러 11자 코드(`WELCOME2026`)를 넣어 두 방식을 비교했다.

```ts
// 잘못된 예: 리포지토리 호출마다 풀에서 따로 실행된다(각각 자동 커밋)
async function signUpNoTx(email: string) {
  const id = await repo.insertUser(pool, email);
  await repo.insertCoupon(pool, id, "WELCOME2026");
}

// 서비스 계층이 트랜잭션 경계를 쥔다
async function signUpTx(email: string) {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const id = await repo.insertUser(client, email);
    await repo.insertCoupon(client, id, "WELCOME2026");
    await client.query("COMMIT");
  } catch (e) {
    await client.query("ROLLBACK");
    throw e;
  } finally {
    client.release();
  }
}
```

`a@example.com`은 트랜잭션 없이, `b@example.com`은 트랜잭션으로 가입시키고 결과를 조회했다.

```text
no-tx: new row for relation "coupons" violates check constraint "coupons_code_check"
tx: new row for relation "coupons" violates check constraint "coupons_code_check"
┌─────────┬─────────────────┬─────────┐
│ (index) │ email           │ coupons │
├─────────┼─────────────────┼─────────┤
│ 0       │ 'a@example.com' │ '0'     │
└─────────┴─────────────────┴─────────┘
```

둘 다 같은 에러로 실패했다. 그런데 표에는 `a@example.com`만 남아 있다. 트랜잭션 없이 가입한 쪽은 회원은 생겼는데 쿠폰이 0개인 반쪽 상태다. 이 사용자가 다시 가입하려 하면 이메일 중복으로 막히고, 쿠폰은 영영 못 받는다. 트랜잭션으로 묶은 쪽은 회원까지 함께 사라져 처음부터 다시 할 수 있다.

트랜잭션 경계가 서비스에 있는 이유는 "무엇과 무엇이 함께 성공해야 하는가"가 업무 규칙이기 때문이다. 리포지토리는 테이블 하나를 알 뿐 그 조합을 모른다. 스프링이라면 서비스 메서드의 `@Transactional`이 이 일을 한다. 같은 클래스 안에서 `this.method()`로 부르면 프록시를 거치지 않아 트랜잭션이 안 걸리는 함정도 유명하다.

이 경계 안에서 하지 말아야 할 일도 있다. 트랜잭션을 연 채로 결제 API나 메일 서버를 부르면, 상대가 느린 만큼 DB 연결과 잠금을 붙잡는다. 외부 호출 몇 개가 느려지면 커넥션 풀이 마른다. 외부 호출은 커밋 뒤로 빼고, 꼭 함께 보장해야 하면 아웃박스로 넘긴다.

## 닫힌 계층과 열린 계층

바로 아래층만 부를 수 있는 층을 닫힌 계층이라고 한다. 앞의 그림에서 컨트롤러가 리포지토리를 바로 부르는 걸 막은 게 이것이다. 닫아 두면 서비스에 넣은 규칙(권한 확인, 감사 로그, 캐시 무효화)을 아무도 건너뛸 수 없다.

모든 층을 닫으면 불편한 경우가 있다. 날짜 계산, 로깅, 암호화처럼 여러 층이 함께 쓰는 공통 기능이다. 이런 것들을 공유 계층으로 따로 두고 열린 계층으로 표시하면, 어느 층이든 건너뛰어 부를 수 있다. 열린 계층은 적을수록 좋고, 업무 규칙이 들어가면 안 된다.

반대쪽 함정은 싱크홀 안티패턴이다. 요청이 층을 그냥 통과만 하는 경우를 말한다. 컨트롤러가 서비스를 부르고, 서비스는 아무 일도 하지 않고 리포지토리를 부르고, 리포지토리가 SQL 한 줄을 보낸다. 마크 리처즈는 『Software Architecture Patterns』에서 이런 통과 요청이 20% 정도면 자연스럽지만, 대부분이 그렇다면 계층 구조가 그 문제에 맞지 않는다는 신호로 봤다. 단순 조회가 대부분인 관리자 화면이라면 그 부분만 층을 열어 리포지토리나 읽기 전용 쿼리를 바로 쓰게 하는 것도 방법이다.

## 의존이 DB를 향할 때 생기는 일

전통적인 레이어드 구조에서 화살표는 모두 아래를 향한다. 비즈니스 계층이 퍼시스턴스 계층에 의존하고, 퍼시스턴스는 DB에 의존한다. 그래서 업무 규칙을 테스트하려면 리포지토리가, 리포지토리를 돌리려면 DB가 필요해진다. 가입 규칙 하나를 검사하는 테스트가 PostgreSQL 컨테이너를 띄워야 돌아간다.

비즈니스 계층에 "저장소가 해 줘야 하는 일"을 인터페이스로 두고, 퍼시스턴스 계층이 그 인터페이스를 구현하게 하면 화살표 하나가 뒤집힌다. 의존성 역전이다.

```ts
// business/user-store.ts: 비즈니스 계층이 필요한 것을 선언한다
export interface UserStore {
  insert(email: string, name: string): Promise<{ id: number; email: string }>;
}

// business/user-service.ts: 구현이 아니라 인터페이스에 기댄다
export function makeUserService(store: UserStore) {
  return {
    async signUp(email: string, name: string) {
      if (!email.includes("@")) throw new InvalidEmailError(email);
      return store.insert(email.trim(), name);
    },
  };
}

// persistence/pg-user-store.ts: 퍼시스턴스 계층이 비즈니스의 인터페이스를 구현한다
export const pgUserStore: UserStore = { insert: (email, name) => userRepository.insert(email, name) };
```

## 프런트엔드에서 보는 같은 층

브라우저 코드도 같은 층을 쌓는다. React 컴포넌트가 화면을 그리고, 커스텀 훅이 상태와 핸들러를 들고, API 모듈이 HTTP를 안다. 이 블로그 코드의 규칙도 그렇다. `{name}.view.tsx`는 마크업만, `{name}.ts` 컨테이너 훅은 상태와 핸들러를, `query/`는 TanStack Query 캐시를, `api/`는 axios 호출을 맡고, 컴포넌트에서 axios를 직접 부르지 않는다.

컴포넌트 안에서 `fetch`를 바로 부르는 코드가 컨트롤러에서 SQL을 쓰는 코드와 같은 문제를 만든다. 응답 형식이 바뀌면 그 API를 쓰는 화면을 전부 찾아 고쳐야 하고, 캐시와 재시도 정책이 화면마다 달라진다. 서버 데이터를 한 층에 모으는 이유는 [클라이언트 데이터 캐시 글](/posts/client-data-cache)에서 이어진다.

## 언제 이 구조로 충분한가

레이어드 아키텍처는 "무엇을 어디에 두는가"에 대한 가장 단순한 답이다. HTTP는 위, SQL은 아래, 업무 규칙은 가운데. 층을 건널 때 에러와 데이터를 그 층의 말로 바꾸고, 트랜잭션은 업무 규칙이 있는 층이 연다. CRUD가 대부분이고 팀이 작다면 이것으로 충분하다. 통과만 하는 층이 대부분이 되면 층을 열거나 줄이고, 업무 규칙이 복잡해져 테스트가 DB에 묶이기 시작하면 의존 방향을 뒤집는다. 그리고 서비스가 커지면 계층보다 먼저 업무 단위로 자르고, 그 안에서 계층을 나눈다.

## 면접에서 나올 만한 질문

### 레이어드 아키텍처란 무엇이고 왜 쓰나요?

코드를 프레젠테이션, 비즈니스, 퍼시스턴스 같은 역할별 층으로 쌓고 위층이 바로 아래층만 부르게 하는 구조다. 관심사가 분리돼 HTTP를 바꾸면 위층만, 저장소를 바꾸면 아래층만 고치면 되고, 처음 보는 사람도 코드 위치를 쉽게 찾는다. 단순한 CRUD 서비스에서 가장 비용이 낮은 구조다.

### 레이어와 티어의 차이는 무엇인가요?

레이어는 코드의 논리적 구분이고 티어는 물리적 배치다. 네 계층을 한 프로세스에 둘 수도 있고, 3티어 구조처럼 웹 서버, 앱 서버, DB 서버를 다른 기계에 둘 수도 있다. 계층을 나누는 건 비용이 거의 없지만 티어를 나누면 경계마다 네트워크 왕복과 운영 비용이 생기는 대신 따로 확장하고 보안 경계를 세울 수 있다.

### DB 에러를 컨트롤러까지 그대로 올리면 무엇이 문제인가요?

사용자 실수가 500으로 바뀌고, 제약 이름과 충돌 값 같은 내부 정보가 응답에 실린다. 충돌 값이 나가면 어떤 이메일이 가입돼 있는지 확인하는 수단이 될 수도 있다. 리포지토리가 SQLSTATE(예: 23505)를 업무 에러로, 컨트롤러가 업무 에러를 상태 코드(409)로 바꾸는 식으로 층마다 번역한다. 타임아웃처럼 진짜 서버 문제는 500으로 남겨 알림이 살아 있게 한다.

### 트랜잭션은 어느 계층에서 시작해야 하나요?

서비스 계층이다. 무엇과 무엇이 함께 성공해야 하는지는 업무 규칙이고, 리포지토리는 테이블 하나만 안다. 리포지토리마다 따로 커밋하면 회원은 생겼는데 쿠폰이 없는 반쪽 상태가 남는다. 트랜잭션 안에서 외부 API를 부르면 연결과 잠금을 오래 붙잡으니 외부 호출은 커밋 뒤로 뺀다.

### 닫힌 계층과 열린 계층은 무엇이고, 싱크홀 안티패턴은 무엇인가요?

닫힌 계층은 바로 아래층만 부를 수 있어 그 층의 규칙을 건너뛸 수 없게 한다. 로깅이나 날짜 계산 같은 공통 기능은 열린 공유 계층으로 둬서 어디서든 부를 수 있게 한다. 싱크홀은 요청이 아무 일도 하지 않는 층을 통과만 하는 상태로, 대부분의 요청이 그렇다면 층이 그 문제에 맞지 않는다는 신호다.

### 레이어드 아키텍처의 한계는 무엇이고 어떻게 넘어가나요?

의존이 아래로, 결국 DB로 향해서 업무 규칙 테스트가 DB에 묶이고 저장 방식이 업무 코드에 스며든다. 비즈니스 계층에 저장소 인터페이스를 두고 퍼시스턴스가 구현하게 해 의존을 뒤집으면 가짜 구현으로 테스트할 수 있다. 이를 끝까지 밀면 헥사고날이나 클린 아키텍처가 된다. 또 계층별 폴더는 기능이 많아지면 한 기능을 고치려고 모든 층을 오가야 해서, 큰 서비스는 업무 모듈로 먼저 나누고 그 안에서 계층을 둔다.
