## 캐시 장비 90대를 옮겨야 한다는 연락

카카오 기술 블로그의 [if(kakao)2020 코멘터리 "카카오톡 캐싱 시스템의 진화"(2020년 11월)](https://tech.kakao.com/posts/406)는 톡서버파트 개발자가 쓴 글이다. 톡서버파트는 카카오톡의 가입과 인증, 사용자 정보, 프로필, 친구 관계, 기기 설정 같은 API를 맡는다. 글은 이 파트가 초당 400만 건이 넘는 데이터 접근을 처리하고, DB 쿼리 결과를 캐시해 DB 부하를 나눈다고 적는다. 그 캐시는 물리 장비 256대 정도에 흩어진 Memcached였다.

이야기는 인프라팀의 연락으로 시작한다. 대규모 상면 계약이 끝나 물리 서버를 다른 IDC의 서버로 바꿔야 하는데, 그중에 톡서버파트의 Memcached 장비 90대가 들어 있었다. 글에 따르면 캐시 장비 한 대를 바꾸는 일은 이런 순서였다.

1. 인프라 엔지니어에게 장비 발주와 Memcached 설치를 요청한다.
2. 새 Memcached의 모니터링을 붙인다.
3. 새벽에 일어난다.
4. 캐시 클러스터마다 ZooKeeper로 관리하는 캐시 호스트 목록을 고친다.
5. DBA와 함께 애플리케이션 지표와 DB를 지켜본다.

새벽에 일어나야 했던 이유가 이 글의 출발점이다. 각 캐시 클러스터는 [일관된 해싱](/posts/consistent-hashing)으로 묶여 있어서 노드 하나를 바꾸면 전체 키의 n분의 1만 다시 해싱된다. 원리상으로는 충분히 적은 양이다. 그런데 글은 톡서버에서는 노드 하나의 트래픽이 워낙 커서 그 n분의 1을 다시 채우는 트래픽만으로도 너무 크다고 적는다. 그래서 트래픽이 가장 적은 새벽에 손으로 호스트 목록을 바꾸고, DB 부하를 지켜봐야 했다. 이걸 90대나 해야 했다.

일관된 해싱이 "옮기는 키를 최소로" 해 주는 건 맞지만, 최소가 곧 작다는 뜻은 아니다. 노드 하나가 맡는 몫 자체가 크면 그 몫이 한꺼번에 비는 순간 DB가 받는 충격도 크다. [캐시 스탬피드](/posts/caching-strategies)가 키 하나가 아니라 노드 하나 단위로 일어나는 셈이다.

### 카카오톡이 받는 트래픽의 크기

캐시 이야기를 하기 전에 카카오톡 전체 트래픽의 크기를 하나 짚어 둔다. 카카오의 [2024년 12월 보도자료](https://www.kakaocorp.com/page/detail/11387)는 카카오톡의 초당 메시지 발신량이 평균 4만 5천 건, 하루 수발신량이 100억 건 이상이라고 적는다. 12월 31일에서 1월 1일로 넘어가는 순간에는 평균의 3배 이상이 한꺼번에 몰리고, 주요 이벤트 때는 평소의 10배까지 늘어난다고 한다. 앞의 초당 400만 건은 톡서버의 데이터 접근 수라서 이 메시지 수와는 세는 대상이 다르다. 메시지 서버의 내부 구조는 이번에 읽은 자료에 나오지 않는다.

트래픽이 몰려 멈춘 기록도 회사가 직접 남겨 두었다. 카카오 기업 사이트의 [카카오톡 뒷이야기 글](https://www.kakaocorp.com/page/detail/9350)에는 2010년 12월 17일, 출시 뒤 처음으로 눈다운 눈이 온 날 이용자 300만 명이 눈 사진을 한꺼번에 보내 서버가 멈췄고 두 시간 뒤 복구됐다는 이야기가 있다. 2011년에 서버를 대대적으로 바꾼 일은 "겁나 빠른 황소 프로젝트"라는 이름으로 알렸다고 적혀 있지만, 그 글에 기술 내용은 없다.

## 메모리는 남는데 장비는 모자랐다

글은 상면 이전을 계기로 미뤄 두던 "마음의 짐" 네 가지를 함께 풀기로 했다고 적는다. 숫자가 붙은 첫 번째가 가장 구체적이다.

데이터 양은 정해져 있는데 트래픽을 나누려고 노드를 늘릴수록 노드 하나에 담긴 데이터가 줄었다. 어떤 캐시 클러스터는 트래픽 때문에 노드 60대로 구성했더니 32GB 장비에서 300MB만 쓰고 있었다. 전체로 보면 캐시 시스템 메모리 6.5TB 중 1.8TB만 쓰고 4.7TB가 놀고 있었다.

계산해 보면 300MB / 32GB는 약 0.9%이고, 1.8TB / 6.5TB는 약 27.7%다. 글이 결과에서 말하는 "이전 메모리 가용률 28%"가 이 숫자와 맞는다. 캐시의 병목이 메모리가 아니라 처리량일 때 생기는 모양이다. 노드 수는 처리량으로 정했는데 장비 크기는 메모리 기준으로 고정돼 있으니, 둘이 어긋난 만큼 메모리가 남는다.

나머지 세 가지는 운영 쪽이다. 노드를 바꿀 때뿐 아니라 노드가 죽었을 때도 복구가 손작업이라 늦거나 실수하면 장애가 커질 수 있었다. 노드를 바꾸거나 장애를 처리할 때마다 인프라 엔지니어와 DB 엔지니어에게 장비, 작업, 모니터링을 요청해야 해서 대화 비용이 컸다. 그리고 일부 단순 키-값 데이터는 Redis로 따로 운영하고 있었는데, 톡서버의 쓰임새에서는 Memcached와 Redis가 같은 일을 하고 있었다.

## 쿠버네티스 위에 Redis를 키우는 캐시 팜

글이 고른 답은 쿠버네티스 위에 Redis 파드를 잔뜩 띄워 두는 "캐시 팜"이다. 쿠버네티스를 고른 이유로 자원 요구와 제한에 맞춘 자동 배치, 장애 때 프로세스 자동 복구, 쉬운 확장, 선언적 자동화, 인프라 엔지니어와의 대화 비용 감소를 든다. 저장소는 Redis로 통일했다. 톡서버의 쓰임새에서는 성능 차이가 없을 거라 봤고, 기능이 더 많아 인메모리 저장소를 하나로 합칠 수 있어서라고 적는다.

Helm 차트로 Redis를 설치하는 길은 톡서버가 원하는 설계에 맞게 고치기 어려워서 StatefulSet을 직접 정의했다. 여기서 이 글만의 선택이 나온다. 보통은 쓰임새마다 StatefulSet을 하나씩 만드는데, 톡서버는 메모리 크기별로 타입을 나눠 StatefulSet을 만들었다. 어떤 Redis 파드가 어떤 데이터를 맡을지는 쿠버네티스가 아니라 다른 구성 요소가 정하게 하고, 쿠버네티스는 크기별 빈 Redis를 넉넉히 키워 두는 일만 한다. 글에 실린 설정은 이렇다.

```yaml
# values.yml에서 타입별 설정만 옮겼다 (원문은 JSON에 가까운 형태로 적혀 있다)
- type: M1
  resource: { memory: { request: 1.5Gi, limit: 1.5Gi } }
  conf: { maxMemory: 1gb }
  ports: [6378, 6379, 6380]
  replicas: 40
- type: M4
  resource: { memory: { request: 6Gi, limit: 6Gi } }
  conf: { maxMemory: 4gb }
  ports: [6381, 6382]
  replicas: 30
- type: M16
  resource: { memory: { request: 24Gi, limit: 24Gi } }
  conf: { maxMemory: 16gb }
  ports: [6383]
  replicas: 60
```

같은 글의 StatefulSet 템플릿은 타입과 포트를 함께 돌면서 `이름-타입-포트` 형태로 StatefulSet을 만든다. 포트마다 StatefulSet이 하나씩 생기는 셈인데, 뒤에서 볼 hostNetwork 때문으로 보인다. 파드가 장비의 포트를 직접 쓰면 한 장비에 같은 포트를 두 번 쓸 수 없으니 포트를 나눠야 한 장비에 여러 Redis를 올릴 수 있다. 글이 이 이유를 직접 적지는 않았으니 설정에서 읽은 추론이다.

이 예시 설정을 그대로 세어 보면 규모가 감이 온다. 포트마다 StatefulSet이 하나씩이니 M1은 3개 × 40개 = 120개, M4는 2개 × 30개 = 60개, M16은 1개 × 60개 = 60개, 모두 240개의 Redis 파드다. 메모리 요구값을 더하면 180Gi + 360Gi + 1,440Gi = 1,980Gi이고, `maxmemory` 합은 120GB + 240GB + 960GB = 1,320GB다. 글에 실린 값이 실제 운영 전체인지 한 클러스터의 예시인지는 적혀 있지 않으니 이 합계는 설정 읽기 연습으로만 본다.

메모리 요구값은 `maxmemory`보다 50% 크게 잡혀 있다. Redis는 `maxmemory` 말고도 버퍼, 복제, 자식 프로세스 같은 곳에 메모리를 더 쓴다. 쿠버네티스 limit을 `maxmemory`와 똑같이 두면 컨테이너가 OOM으로 죽기 쉽다. 이 여유를 얼마로 잡을지는 [Redis 메모리와 eviction](/posts/redis-memory-eviction)에서 다룬 내용과 이어진다. 1.5배라는 비율의 근거는 글에 없다.

### 노드마다 쓰던 데이터 크기로 타입을 고른다

기존 클러스터의 메모리 사용량을 분석해 1GB, 4GB, 16GB 타입을 만들었다고 했다. 노드당 300MB를 쓰던 클러스터는 이제 32GB 장비 대신 1GB 타입 파드를 쓰면 된다. 아래에서 노드당 쓰는 데이터 크기를 넣으면 맞는 타입과, 그 타입의 메모리 요구값 대비 사용률을 돌려주는 함수를 짜 볼 수 있다. 타입 표는 위 설정 그대로이고, 고르는 규칙(데이터가 들어가는 가장 작은 타입)은 글을 읽고 내가 정한 단순한 규칙이다.

### 업데이트는 파드를 지울 때만 일어나게

StatefulSet을 고른 이유로 글은 고정된 네트워크 식별자, 고정된 스토리지, 순서 있는 배포와 확장, 순서 있는 롤링 업데이트를 들고, 그중에서도 순서 있는 확장과 업데이트가 가장 필요했다고 적는다. 특히 OnDelete 업데이트 전략을 썼다. 템플릿을 바꿔도 파드를 바로 바꾸지 않고, 파드가 지워졌다 다시 만들어질 때만 새 설정으로 뜬다.

캐시는 이 전략이 특히 잘 맞는다. Redis 버전을 올리려고 이미지를 바꾸면 파드가 다시 뜨면서 그 파드의 캐시가 빈다. 자동 롤링 업데이트가 여러 파드를 연달아 바꾸면 DB가 그 미스를 한꺼번에 받는다. OnDelete로 두면 사람이 파드를 하나씩 지우면서 서비스와 DB가 부하를 회복하는 걸 지켜볼 수 있다. [StatefulSet](/posts/k8s-statefulset)에서 다룬 업데이트 전략이 캐시의 "다시 채우는 비용" 때문에 골라진 사례다.

설정으로는 한 줄이고, 바꾸는 쪽은 파드를 하나씩 지우는 손작업이 된다. 아래는 쿠버네티스 공식 필드를 쓴 일반적인 모양이고, 카카오가 쓴 실제 매니페스트는 글에 없다.

```yaml
# StatefulSet 일부: 템플릿을 바꿔도 파드를 지우기 전에는 그대로 둔다
spec:
  updateStrategy:
    type: OnDelete
```

```bash
# 파드 하나를 지우면 컨트롤러가 새 템플릿으로 다시 만든다 (이름은 접두사-타입-포트-번호 형태의 예시)
kubectl delete pod cache-m1-6379-0
# 새 파드가 Ready가 될 때까지 기다리며 지켜본다
kubectl get pod cache-m1-6379-0 -w
```

한 대를 지운 뒤 DB 지표와 캐시 적중률이 돌아오는 걸 확인하고 다음 파드로 넘어간다. 자동 롤링 업데이트의 `partition` 값을 한 칸씩 내리는 방법도 같은 효과를 낸다.

## 추상화를 빼고 속도를 얻으니 주소가 흔들렸다

부하를 나누는 게 목적이라 쿠버네티스 네트워크의 오버헤드와 병목을 최대한 줄이고 싶었다. 그래서 Ingress와 Service 계층을 없애고, 오버레이 네트워크를 타지 않도록 Redis 파드가 hostNetwork로 장비의 IP와 포트를 직접 쓰게 했다. 글은 캐시 전용으로 설계한 쿠버네티스 클러스터라 구조를 넓힐 일을 고려할 필요가 적어서 가능한 판단이었다고 적는다.

대가는 바로 왔다. 쿠버네티스가 장애 파드를 다시 띄우는 자동 복구(self-healing)는 Service가 파드들을 이름으로 묶어 주기 때문에 클라이언트에게 티가 나지 않는다. hostNetwork를 쓰면 클라이언트는 "장비 A의 K번 포트"로 Redis를 찾는데, 쿠버네티스는 다시 띄운 파드를 같은 장비 같은 포트에 둔다는 보장이 없다. 장비 B의 N번 포트로 옮겨 가면 클라이언트는 Redis를 잃는다. 결국 장애 복구를 다시 손으로 해야 하는 상황으로 돌아온다.

이 대목은 [쿠버네티스 Service](/posts/k8s-service-types)가 왜 있는지를 거꾸로 보여 준다. 파드의 주소는 언제든 바뀐다는 전제 위에 쿠버네티스의 자동 복구가 서 있고, 그 주소 변화를 숨기는 게 Service다. 성능 때문에 Service를 빼면 주소를 숨기는 일을 누군가 다시 맡아야 한다.

## 센티넬이 이름을 들고, Barn이 빈 파드를 골라 붙인다

글은 주소를 숨기는 일을 Redis Sentinel에게 맡겼다. [Redis Sentinel](/posts/redis-replication-sentinel)은 상태 확인, 장애 조치, 그리고 클라이언트가 이름으로 마스터를 찾게 해 주는 기능을 준다. 쿠버네티스에서 Redis 파드를 만들 때는 그 파드가 어떤 데이터를 맡을지 전혀 적지 않는다. 어떤 파드가 어떤 데이터를 맡을지는 관리용 애플리케이션이 센티넬에 등록한다. 글의 예시는 이 명령이다.

### 센티넬이 보여 주는 파티션 상태

글에는 센티넬에 파티션 목록을 물었을 때의 출력이 실려 있다. 필요한 줄만 옮기면 이렇다(가운데 줄은 원문에서도 생략돼 있다).

```text
redis-cli> sentinel masters
1)  1) "name"
    2) "User.id::0"
    3) "ip"
    4) "127.0.0.1"
    5) "port"
    6) "6379"
    9) "flags"
   10) "master,odown"
...
   31) "num-slaves"
   32) "0"
   33) "num-other-sentinels"
   34) "8"
   35) "quorum"
   36) "4"
   37) "failover-timeout"
   38) "3000"
```

볼 줄은 셋이다. `flags`의 `odown`은 정족수 이상의 센티넬이 이 마스터가 죽었다고 동의했다는 뜻이다. `num-slaves`가 0이면 올릴 복제본이 없다. 이 두 줄이 함께 나오는 파티션이 아래에서 볼 Barn이 직접 손대는 대상이다. `num-other-sentinels` 8은 이 파티션을 함께 지켜보는 다른 센티넬이 8대라는 뜻이니 모두 9대가 지켜보고, `quorum` 4는 그중 4대가 동의해야 ODOWN이 된다는 뜻이다. 앞의 등록 명령 예시는 정족수 2였으니 두 예시는 서로 다른 설정을 보여 준 것이다. 실제 운영 값이 무엇인지는 글에 없다.

운영하는 쪽에서는 이 출력이 장애 대시보드의 원천이 된다. 파티션마다 `odown`과 `num-slaves`를 모으면 "지금 죽었고 혼자서는 못 일어나는 파티션"이 한눈에 보인다. Barn의 컨트롤 루프가 하는 일도 결국 이 목록을 주기적으로 읽고 고치는 것이다.

### 복제를 쓰지 않으면 센티넬도 못 고친다

센티넬은 지켜보라고 한 마스터에 복제본이 있으면 장애 때 복제본을 마스터로 올려 준다. 그런데 글은 캐시 용도의 클러스터에는 보통 복제를 쓰지 않는다고 적는다. Redis 복제가 비동기라 장애 조치 중에 정합성이 깨질 수 있어서다. 복제본이 없으면 센티넬은 다른 Redis를 스스로 찾아 모니터링 주소를 바꿀 수 없다.

캐시에서 정합성이 깨진다는 건 이런 뜻으로 읽힌다. 마스터에 쓴 값이 복제본에 가기 전에 마스터가 죽고 복제본이 올라오면, 복제본에는 그 갱신 전 값이 남는다. DB는 이미 새 값인데 캐시가 옛 값을 내준다. 빈 캐시는 DB에서 다시 채우면 그만이지만, 틀린 캐시는 TTL이 끝날 때까지 틀린 답을 낸다. 이 해석은 글에 적힌 한 줄("정합성이 깨질 수가 있다")을 풀어 쓴 것이다.

그래서 Barn이라는 운영 도구를 만들었다. 개발자가 관리 화면에서 원하는 상태를 적으면,

```json
{
  "clusterName": "User.id",
  "clusterSize": 10,
  "partitionSize": 1
}
```

Barn이 컨트롤 루프를 돌며 센티넬에 등록된 파티션 상태와 비교해 이 상태를 맞춘다. 파티션이 10개여야 하니 `User.id::0`부터 `User.id::9`가 센티넬 목록에 있는지 본다. `User.id::0`이 없으면 쿠버네티스에 만들어 둔 Redis 파드 중 장애 분산에 가장 좋은 것을 골라 마스터로 정하고 센티넬에 모니터링을 명령한다. `partitionSize`가 1이니 복제 관계가 있으면 지운다. [쿠버네티스 컨트롤러의 reconcile 루프](/posts/k8s-controllers-reconcile)를 캐시 클러스터 운영에 그대로 가져온 것이다.

글은 "서버 쪽 장애는 쿠버네티스가, 클라이언트 쪽 장애는 Barn과 센티넬이 협업해 복구한다"고 정리한다. 마지막 단계의 빈 캐시는 글에 직접 적힌 장면은 아니다. 복제 없이 다른 파드로 갈아 끼우면 그 파드가 비어 있을 수밖에 없으니 DB가 그 몫을 받는다는 건 구조에서 나오는 결과다. 처음에 말한 "노드 하나 몫이 한꺼번에 비는 충격"은 이 구조에서도 사라지지 않았고, 사람이 새벽에 일어나지 않아도 된다는 점이 달라졌다.

## 결과: 장비 256대가 180대로

글이 적은 성과는 두 가지다. 물리 장비 256대로 하던 캐시 시스템을 180대로 줄였다. 예전에는 256대를 쓰면서도 새 서비스나 캐시 확장 때 장비를 새로 신청해야 했는데, 지금은 180대 안에 넉넉한 Redis 파드가 대기 중이라 언제든 꺼내 쓸 수 있다고 한다. 전체 메모리 가용률은 28%에서 48% 정도로 올렸다. 글은 이 숫자가 Memcached로는 기대할 수 없던 Redis의 영속성과 복제까지 고려한 배치라 의미가 크다고 덧붙인다. 그리고 관리 애플리케이션으로 운영이 자동화되면서 인프라팀과의 대화 비용이 줄고, 장애 복구도 자동으로 하게 됐다고 적는다.

[ARCUS](/posts/rw-naver-arcus)와 견주면 차이가 선명하다. 둘 다 처음엔 memcached 계열 노드를 ZooKeeper 명단과 일관된 해싱으로 묶었다. ARCUS는 그 구조를 다듬어 노드가 죽으면 명단에서 자동으로 빠지게 했다. 카카오 톡서버는 일관된 해싱의 링을 버리고, 파티션 수를 고정한 뒤 파티션 이름 뒤의 실제 Redis를 바꿔 끼우는 쪽으로 갔다. 링에서는 노드가 빠지면 이웃이 그 몫을 떠안는다. 고정 파티션에서는 이웃은 그대로이고 빈 파드 하나가 그 자리를 채운다. 노드가 빠질 때 다른 노드의 부하가 갑자기 늘지 않는다는 게 고정 파티션의 이점이고, 파티션 수를 바꾸는 일이 어려워진다는 게 비용이다. 이 비교는 두 회사 자료를 놓고 내가 한 해석이다.

## 글이 직접 남겨 둔 빈칸

이 글은 if(kakao)2020 발표를 앞두고 쓴 코멘터리다. 글 스스로 두 가지를 다 공유하지 못했다고 적는다. 이런 자동화 시스템에서 고려해야 할 "치명적인 리스크"가 있다는 것, 그리고 새 캐시 팜으로 기존 캐시 트래픽을 옮기는 과정이다. 둘 다 발표("카카오톡 4M/s 캐시 클러스터 전환기")로 넘겼는데, 이번에 그 발표 영상은 확인하지 못했다. 그래서 이 글은 전환 과정을 다루지 않는다.

치명적인 리스크가 무엇인지 짐작은 할 수 있다. 사람 대신 컨트롤 루프가 장애를 고치면, 루프가 잘못 판단할 때 사람보다 빠르게 잘못을 퍼뜨린다. 네트워크 분할로 센티넬이 멀쩡한 파드를 ODOWN으로 보면 Barn이 멀쩡한 파티션을 빈 파드로 갈아 끼울 수 있다. 하지만 이건 일반론이고, 카카오가 어떤 리스크를 말했는지는 모른다.

공개 자료의 한계도 있다. 2020년 글이라 지금의 캐시 구조가 같은지는 공개되지 않았다. 센티넬 몇 대로 몇 개의 파티션을 지켜보는지, 장애 복구에 몇 초가 걸리는지, 복구 직후 DB 부하가 얼마나 오르는지 같은 숫자는 없다. 회사 블로그에 실린 성공담이라 실패한 시도나 버린 설계는 거의 나오지 않는다. 카카오톡 메시지 서버의 구조는 [2023년 9월 Kakao Tech Meet](https://tech.kakao.com/posts/603) 소개 글에서 새해, 자연재해, 월드컵 같은 몰림에 어떻게 대처하는지 발표했다고만 알 수 있고, 내용은 영상에 있어 이 글에서 다루지 못했다. 같은 소개 글에서 발표자는 재건축 프로젝트로 서버 언어를 바꾸고 구조를 근본적으로 고칠 계획이라고 말한다.

## 캐시 노드 수와 메모리가 어긋나 보일 때

이 사례의 선택은 "캐시 노드가 수백 대이고, 노드 하나의 처리량이 커서 노드를 메모리가 아니라 처리량으로 늘려야 하며, 캐시를 바꾸는 일이 자주 있는" 조건에서 값을 한다. 캐시 노드가 몇 대뿐이면 관리형 Redis나 Memcached 서비스로 같은 문제를 훨씬 싸게 푼다. 노드 교체와 장애 조치를 서비스가 대신해 준다면 Barn 같은 도구를 만들 이유가 없다. 처음부터 따라 하면 캐시 전용 쿠버네티스 클러스터, 센티넬 무리, 상태를 맞추는 운영 도구를 만들고 지키는 사람이 필요하다. 그 도구가 잘못 판단할 때의 피해도 같이 떠안는다.

작은 팀이 지금 가져올 수 있는 것은 몇 가지다.

- 캐시 노드의 메모리 사용률을 처리량과 함께 본다. 메모리는 남는데 노드 수가 늘고 있다면 병목은 처리량이고, 큰 장비보다 작은 단위를 여러 개 두는 쪽이 맞을 수 있다.
- 클라이언트가 캐시를 IP 목록이 아니라 이름으로 찾게 한다. 센티넬이든 DNS든 관리형 엔드포인트든, 노드를 바꿀 때 애플리케이션 설정을 고치지 않아도 되게 해 두면 새벽 작업의 절반이 사라진다.
- 캐시 노드 교체나 Redis 버전 업그레이드를 한꺼번에 하지 않는다. StatefulSet이라면 OnDelete나 partition 업데이트로 한 대씩 바꾸고, 바꿀 때마다 DB 부하가 돌아오는 걸 보고 다음으로 넘어간다.

비슷한 신호가 보이면 이 순서로 본다. 캐시 노드 하나를 바꿀 때마다 DB CPU가 튄다면, 그 노드가 맡는 키 비율과 그 키들의 초당 요청 수부터 본다. 노드 하나 몫이 크면 노드를 더 잘게 나누는 게 먼저다. 장애 뒤 캐시가 옛 값을 내준다는 문의가 오면, 캐시에 비동기 복제를 쓰고 있고 장애 조치가 일어났는지 본다. 노드를 자동으로 갈아 끼우는 도구를 쓴다면, 그 도구가 최근에 무엇을 바꿨는지 기록이 남는지부터 확인한다.

## 면접에서 나올 만한 질문

### 일관된 해싱을 쓰는데도 왜 캐시 노드 교체를 새벽에 해야 했나

일관된 해싱은 옮기는 키를 전체의 n분의 1로 줄여 줄 뿐, 그 몫이 작다고 보장하지 않는다. 톡서버는 노드 하나의 트래픽이 커서 그 몫을 다시 채우는 미스만으로 DB가 크게 흔들렸다. 그래서 트래픽이 적은 새벽에 손으로 호스트 목록을 바꾸고 DB를 지켜봐야 했다.

### 메모리 사용률이 28%밖에 안 된 이유는

노드 수를 처리량에 맞춰 늘렸는데 장비는 32GB로 고정이었기 때문이다. 어떤 클러스터는 60대로 나누고 나니 노드당 300MB만 썼다. 전체 6.5TB 중 1.8TB만 쓰는 상태가 됐다. 메모리 크기별 Redis 파드로 바꾸자 같은 일을 180대에서 하면서 가용률이 48% 정도로 올랐다.

### 왜 Service를 빼고 hostNetwork를 썼고, 무엇을 잃었나

부하를 나누는 게 목적이라 Ingress와 Service, 오버레이 네트워크의 오버헤드를 없애고 싶었다. 대신 파드가 다른 장비나 포트로 옮겨 가면 클라이언트가 주소를 잃는다. 쿠버네티스의 자동 복구가 클라이언트에게 투명한 건 Service가 주소를 숨기기 때문인데, 그걸 뺐으니 주소를 숨기는 일을 센티넬에 다시 맡겼다.

### 캐시 클러스터에 왜 복제를 쓰지 않았나

Redis 복제는 비동기라 장애 조치 중에 정합성이 깨질 수 있어서다. 복제본에 아직 안 간 갱신이 있으면 승격된 복제본이 옛 값을 내준다. 캐시는 비어 있으면 DB에서 다시 채우면 되지만 틀린 값은 TTL 동안 틀린 답을 낸다. 그래서 복제 없이 빈 파드로 갈아 끼우는 쪽을 골랐고, 그 갈아 끼우기를 Barn이 자동으로 한다.

### 복제가 없는데 센티넬만으로 자동 복구가 되나

안 된다. 센티넬은 지켜보는 마스터의 복제본을 올릴 수는 있지만 다른 Redis를 스스로 찾아 주소를 바꾸지는 못한다. 그래서 Barn이 센티넬 목록에서 ODOWN이면서 복제본이 없는 파티션을 찾아, 대기 중인 파드를 골라 그 이름으로 다시 등록한다. 쿠버네티스는 죽은 파드를 되살려 대기열로 돌려놓는다.

### 일관된 해싱 링과 고정 파티션은 노드가 죽을 때 무엇이 다른가

링에서는 죽은 노드의 몫을 링의 다음 노드가 떠안아 그 노드의 부하가 갑자기 는다. 고정 파티션에 이름을 붙이고 빈 파드로 갈아 끼우면 이웃 노드는 그대로이고 새 파드 하나가 그 몫을 받는다. 대신 파티션 수를 바꾸는 일은 링보다 어렵다. 카카오 톡서버는 후자를 골랐다.

### 우리 서비스가 캐시 노드 몇 대 규모라면 같은 구조를 쓰나

대개 아니다. 캐시 전용 쿠버네티스 클러스터와 센티넬, 상태를 맞추는 운영 도구를 만들고 지키는 비용이 크고, 관리형 캐시가 노드 교체와 장애 조치를 대신해 준다면 더 그렇다. 대신 캐시를 이름으로 찾게 하기, 메모리 사용률을 처리량과 함께 보기, 노드 교체와 업그레이드를 한 대씩 하며 DB 부하를 보기는 작은 규모에서도 그대로 가져온다.
