이 시리즈에서 이 글의 자리: [⑤ 캐시 계층과 CDN](/posts/sd-cache-and-cdn-tier)까지 한 데이터 센터 안의 구조를 다 쌓았고, 이 글은 그 구조를 다른 지역에 하나 더 둔다. 다음 글은 [⑦ 큐, 로그, 자동화](/posts/sd-queue-logging-automation)다. 같은 장의 글은 [① 서버 한 대](/posts/sd-start-single-server), [② 웹과 DB 나누기](/posts/sd-split-web-and-db), [③ 로드 밸런서와 무상태 웹](/posts/sd-load-balancer-stateless), [④ DB 복제](/posts/sd-db-replication-intro), [⑧ 샤딩 입문](/posts/sd-sharding-intro)이다.

맛집 리뷰 앱의 서버는 지금 모두 서울에 있는 데이터 센터 한 곳에 있다. 로드 밸런서도 두 대, 웹 서버도 여러 대, DB에는 복제본까지 붙였으니 서버 한 대가 죽는 정도는 견딘다. 그런데 이 장비들은 같은 건물, 같은 전력선, 같은 인터넷 회선을 쓴다. 건물 전체의 전원이 나가거나 그 지역으로 들어오는 회선이 끊기면 이중화한 장비들이 함께 사라진다.

그리고 앱이 미국에서도 인기를 얻기 시작했다. 뉴욕의 사용자가 서울까지 요청을 보내고 받으려면 태평양을 건너 왕복해야 한다. 서울과 미국 동부 사이 왕복 시간은 경로에 따라 다르지만 보통 150~200ms 안팎이다. 화면 하나에 API를 다섯 번 순서대로 부르면 그것만으로 1초 가까이 기다린다.

두 문제 모두 같은 처방으로 이어진다. 멀리 떨어진 다른 데이터 센터에 같은 구조를 하나 더 두는 것이다. 이 글에서는 미국 버지니아에 두 번째 데이터 센터를 세우고, 그 뒤에 생기는 세 가지 일을 차례로 푼다. 사용자를 어느 쪽으로 보낼지, 두 곳의 데이터를 어떻게 맞출지, 한쪽이 멈추면 어떻게 넘길지다.

## 건물 하나에 모든 것을 두면

데이터 센터(data center, DC)는 서버와 네트워크 장비, 전원, 냉방을 갖춘 건물이다. 클라우드를 쓰면 건물을 직접 볼 일은 없지만 같은 개념이 이름만 바꿔 나온다. AWS를 예로 들면, 독립된 전원과 네트워크를 가진 데이터 센터 하나 이상을 묶어 가용 영역(Availability Zone, AZ)이라 부르고, 서로 가까운 AZ 여러 개를 묶어 서울, 버지니아 같은 리전(region)이라 부른다.

같은 리전 안의 AZ 두세 곳에 나눠 두면 건물 하나가 멈추는 일은 견딘다. AZ 사이는 보통 100km 안쪽이라 왕복 지연이 몇 ms를 넘지 않아서, DB를 동기로 복제해도 크게 느려지지 않는다. 이 글에서 다루는 것은 그 바깥, 수천 km 떨어진 곳에 두 번째 거점을 두는 일이다. 리전 전체가 멈추는 큰 장애에도 버티고, 먼 나라의 사용자에게 가까운 곳에서 답하기 위해서다. 거리가 멀어지는 대신 지연이 수십에서 수백 ms로 늘고, 그 지연이 이 글의 거의 모든 고민을 만든다.

## 같은 이름에 위치별로 다른 답: GeoDNS

사용자를 가까운 데이터 센터로 보내는 가장 흔한 방법은 DNS에서 나누는 것이다. [① 서버 한 대](/posts/sd-start-single-server)에서 본 것처럼 앱은 `api.matjip.example` 같은 이름을 먼저 IP로 바꾼 뒤 요청한다. 보통 DNS는 누가 묻든 같은 IP를 답한다. GeoDNS는 묻는 쪽의 위치를 짐작해서 서로 다른 IP를 답한다.

여기서 "묻는 쪽"은 대개 사용자의 휴대폰이 아니라 사용자가 쓰는 DNS 리졸버다. 리졸버(resolver)는 통신사나 구글 같은 곳에서 운영하며 사용자 대신 DNS 서버들을 돌아다니며 답을 찾아 주는 서버다. GeoDNS는 리졸버의 IP 주소를 IP 위치 데이터베이스에 넣어 나라나 도시를 추정한다. 리졸버가 사용자의 대략적인 주소 대역을 함께 보내 주는 확장(EDNS Client Subnet)을 쓰기도 한다.

실제로 아주 작은 GeoDNS를 만들어 봤다. Node의 `dns2` 패키지로 DNS 서버를 띄우고, 질의를 보낸 주소가 `127.0.0.2`면 한국, `127.0.0.3`이면 미국으로 친다. 실제 서비스라면 이 자리에 IP 위치 데이터베이스가 들어간다. `health.json`에는 헬스 체크(health check) 결과가 들어 있다고 가정했다. 헬스 체크는 각 데이터 센터에 주기적으로 요청을 보내 살아 있는지 확인하는 일이다.

```js
// geodns.js 일부
const DCS = { seoul: "203.0.113.10", virginia: "198.51.100.20" };
const REGION_OF = { "127.0.0.2": "kr", "127.0.0.3": "us" };           // 실제로는 IP 위치 DB를 쓴다
const PREFER = { kr: ["seoul", "virginia"], us: ["virginia", "seoul"] }; // 가까운 순서

handle: (request, send, rinfo) => {
  const health = JSON.parse(fs.readFileSync("health.json", "utf8")); // 헬스 체크 결과
  const region = REGION_OF[rinfo.address] ?? "us";
  const dc = PREFER[region].find((name) => health[name]);           // 살아 있는 가장 가까운 곳
  res.answers.push({ name: q.name, type: Packet.TYPE.A, class: Packet.CLASS.IN, ttl: 30, address: DCS[dc] });
  send(res);
}
```

`dig`의 `-b` 옵션으로 질의를 보내는 쪽 주소를 바꿔 가며 물었다. 세 번째 질의 전에는 `health.json`에서 서울을 `false`로 바꿨다.

```bash
# 한국 쪽(127.0.0.2)과 미국 쪽(127.0.0.3)에서 같은 이름을 묻는다
dig @127.0.0.1 -p 5391 -b 127.0.0.2 api.matjip.example +noall +answer
dig @127.0.0.1 -p 5391 -b 127.0.0.3 api.matjip.example +noall +answer
# 서울 헬스 체크가 실패했다고 기록한 뒤 한국 쪽에서 다시 묻는다
echo '{"seoul": false, "virginia": true}' > health.json
dig @127.0.0.1 -p 5391 -b 127.0.0.2 api.matjip.example +noall +answer
```

```text
api.matjip.example.	30	IN	A	203.0.113.10
api.matjip.example.	30	IN	A	198.51.100.20
api.matjip.example.	30	IN	A	198.51.100.20
```

첫 두 줄은 같은 이름에 서로 다른 IP가 돌아온 모습이다. 세 번째 줄은 한국에서 물었는데도 버지니아 IP가 왔다. 서울이 죽었다고 기록되자 "살아 있는 곳 중 가장 가까운 곳"이 버지니아가 된 것이다. 줄 가운데의 `30`이 TTL이다. 이 숫자가 장애 때 얼마나 빨리 넘어가는지를 크게 좌우한다.

DNS 말고 다른 방법도 있다. 애니캐스트(anycast)는 여러 지역이 같은 IP를 광고하고 인터넷 라우팅이 가까운 곳으로 보내게 한다. CDN과 일부 클라우드의 글로벌 로드 밸런서가 이 방식을 쓰고, DNS 캐시를 기다릴 필요가 없어 전환이 빠르다. 원리는 [CDN 엣지와 애니캐스트](/posts/cdn-edge-anycast)에 있다. 처음 설계에서는 GeoDNS로 시작하고, 전환 속도가 더 필요해지면 이쪽을 검토한다고 말하면 충분하다.

## 한쪽이 통째로 멈추면 넘어가기까지

서울 데이터 센터가 멈췄다고 하자. 위 실험처럼 GeoDNS가 한국 사용자에게 버지니아 IP를 주기 시작해도, 모든 사용자가 바로 넘어가지는 않는다. 넘어가는 데 걸리는 시간은 세 토막의 합이다.

첫 토막은 감지 시간이다. 10초 간격으로 세 번 연속 실패해야 죽었다고 보면 최대 30초가 걸린다. 한 번 실패로 바로 빼면 빠르지만, 잠깐의 흔들림에도 사용자를 태평양 너머로 보내는 잘못된 전환이 잦아진다. 감지를 얼마나 예민하게 할지의 트레이드오프는 [장애 조치](/posts/failover)에서 자세히 다룬다.

두 번째 토막은 DNS TTL이다. 이미 서울 IP를 받아 둔 리졸버는 TTL이 끝날 때까지 다시 묻지 않는다. TTL이 30초면 최대 30초가 더 걸린다. TTL을 5초로 줄이면 빨라지지만 DNS 질의가 그만큼 늘고, 일부 리졸버와 클라이언트는 짧은 TTL을 무시하고 더 오래 들고 있기도 해서 생각만큼 줄지 않는다.

세 번째 토막은 앱 쪽이다. 이미 서울과 맺어 둔 연결이 끊긴 걸 알아채고 다시 이름을 조회해 새로 연결해야 한다. 오래 열린 연결과 앱 안의 DNS 캐시가 이 시간을 늘린다. 여기에 데이터 쪽 전환, 즉 버지니아 DB를 쓰기 가능한 주 DB로 올리는 시간이 더해진다. 그 이야기는 다음 절에서 한다.

이 숫자들은 미리 정하고 재 둬야 한다. "리전 장애 때 몇 분 안에 넘어간다"는 목표를 RTO(Recovery Time Objective)라고 부르고, 그때 잃어도 되는 데이터의 양을 RPO(Recovery Point Objective)라고 부른다. 두 숫자를 어떻게 정하고 훈련하는지는 [재해 복구](/posts/disaster-recovery)에 있다.

## 넘어간 쪽이 다 받을 수 있나

데이터 센터가 넘어가는 순간 놓치기 쉬운 계산이 있다. 서울이 받던 트래픽을 버지니아가 혼자 받아야 한다는 점이다. 평소 두 곳이 각각 60%로 돌고 있었다면, 한쪽이 죽는 순간 남은 쪽은 120%가 돼서 함께 쓰러진다. 장애 조치가 장애를 두 배로 만드는 셈이다.

그래서 데이터 센터가 N곳이면, 하나가 빠져도 나머지가 버틸 만큼 여유를 남겨 둔다. 아래 함수를 완성해 보자. 각 데이터 센터의 평소 부하와 한 곳의 최대 처리량을 받는다. 어느 한 곳이 멈추면 그 부하가 나머지에 똑같이 나뉜다고 가정하고, 모든 경우 중 가장 바쁜 데이터 센터의 사용률(%)을 반올림해 돌려준다.

  caption="한 곳이 멈췄을 때 가장 바쁜 데이터 센터의 사용률"
  functionName="worstUtilAfterOneFails"
  initialCode={`function worstUtilAfterOneFails(loads, capacity) {
  // loads[i]: i번째 DC의 평소 초당 요청 수
  // capacity: DC 하나가 버티는 초당 요청 수
  // 각 DC가 멈추는 경우를 모두 따져, 가장 높은 사용률(%)을 반올림해 돌려준다
  return 0;
}`}
  solution={`function worstUtilAfterOneFails(loads, capacity) {
  let worst = 0;
  for (let failed = 0; failed < loads.length; failed++) {
    const share = loads[failed] / (loads.length - 1);
    for (let i = 0; i < loads.length; i++) {
      if (i === failed) continue;
      worst = Math.max(worst, Math.round(((loads[i] + share) / capacity) * 100));
    }
  }
  return worst;
}`}
  tests={[
    { args: [[600, 600], 1000], expected: 120, label: "두 곳 모두 60%" },
    { args: [[400, 400], 1000], expected: 80, label: "두 곳 모두 40%" },
    { args: [[400, 400, 400], 1000], expected: 60, label: "세 곳 모두 40%" },
    { args: [[600, 600, 600], 1000], expected: 90, label: "세 곳 모두 60%" },
    { args: [[700, 300], 1000], expected: 100, label: "서울 70%, 버지니아 30%" },
    { args: [[500, 500, 500, 500], 800], expected: 83, label: "네 곳, 용량 800" },
  ]}
/>

두 곳이면 평소에 50% 아래로 돌려야 하나가 빠져도 버틴다. 세 곳이면 60%씩 돌려도 하나가 빠졌을 때 90%로 버틴다. 데이터 센터를 늘릴수록 남겨 둘 여유의 비율이 줄어든다. 다섯 번째 줄처럼 부하가 한쪽에 치우쳐 있으면 계산이 더 빠듯해진다. 실제로는 오토스케일링으로 늘리는 방법도 있지만, 리전 장애 때는 다른 서비스들도 동시에 같은 리전으로 몰려 새 서버를 받기 어려울 수 있다. 그래서 핵심 서비스는 여유를 미리 띄워 두는 편이 안전하다.

캐시도 같이 봐야 한다. 버지니아의 캐시에는 미국 사용자가 보던 데이터만 들어 있다. 한국 사용자가 넘어오는 순간 그들이 찾는 데이터는 대부분 미스가 나고, [⑤ 캐시 계층과 CDN](/posts/sd-cache-and-cdn-tier)에서 계산한 것처럼 DB로 가는 읽기가 몇 배로 뛴다. 넘어간 쪽 DB가 이 미스 폭주까지 받을 수 있는지 함께 계산한다.

## 두 곳의 데이터를 맞추는 일

이제 가장 어려운 부분이다. 한국 사용자가 서울에서 리뷰를 썼는데, 서울이 멈추고 버지니아로 넘어갔더니 그 리뷰가 없다면 곤란하다. 두 데이터 센터의 데이터는 복제로 맞춘다. [④ DB 복제](/posts/sd-db-replication-intro)에서 한 데이터 센터 안의 주 DB와 복제본을 맞춘 것과 같은 원리인데, 거리가 멀어서 고민의 크기가 달라진다.

선택지는 두 가지다. 동기 복제는 서울 DB가 쓰기를 받으면 버지니아에 도착했다는 확인까지 받은 뒤 사용자에게 성공을 알린다. 비동기 복제는 서울에 쓰자마자 성공을 알리고, 버지니아에는 뒤따라 보낸다. 같은 데이터 센터 안이라면 왕복이 1ms 안쪽이라 동기도 부담이 작지만, 서울과 버지니아 사이라면 쓰기마다 왕복 시간만큼 더 기다려야 한다.

숫자로 따져 봤다. 실제 네트워크 대신 시간을 직접 세는 시뮬레이션이다. 서울에서 버지니아까지 편도 90ms(왕복 180ms), 서울 안에서 커밋하는 데 2ms, 리뷰가 10ms마다 하나씩 들어오고, 1초 시점에 서울이 통째로 멈춘다고 가정했다.

```js
// dcrepl.js 일부
for (let t = 0; t < CRASH_AT; t += WRITE_EVERY) {
  const commitAt = t + LOCAL_COMMIT;
  const remoteAt = commitAt + ONE_WAY;                 // 버지니아에 도착하는 시각
  const ackAt = mode === "async" ? commitAt : remoteAt + ONE_WAY; // 동기면 버지니아의 확인까지 기다린다
  if (ackAt < CRASH_AT) { acked++; latencySum += ackAt - t; }
  if (remoteAt < CRASH_AT) arrived++;
}
```

```text
async acked=100 in_virginia=91 lost_after_failover=9 avg_ack_ms=2
sync  acked=82 in_virginia=91 lost_after_failover=0 avg_ack_ms=182
```

비동기에서는 사용자가 2ms 만에 "등록됐다"는 답을 받았다. 대신 서울이 멈춘 순간 아직 바다를 건너는 중이던 9개는 버지니아에 없다. 사용자는 성공 화면을 봤는데 장애 조치 뒤에 리뷰가 사라진 것이다. 동기에서는 잃은 것이 0개지만 모든 쓰기가 182ms씩 기다렸다. 마지막 순간의 쓰기들은 버지니아에 도착했지만 확인이 돌아오기 전에 서울이 멈춰 사용자는 실패로 봤다. 이런 요청은 다시 시도하게 되니, 같은 리뷰가 두 번 들어가지 않게 [멱등성 키](/posts/idempotency-key) 같은 장치가 필요하다.

그래서 데이터 종류마다 다르게 고른다. 리뷰나 좋아요는 비동기로 복제하고, 리전 장애 같은 드문 일에 몇 초치를 잃을 수 있다고 받아들인다. 결제나 예약처럼 잃으면 안 되는 쓰기는 같은 리전 안 여러 AZ에 동기로 복제해 건물 하나가 멈추는 정도는 잃지 않게 하고, 리전을 넘는 복제는 비동기로 두는 조합이 흔하다. 리전 사이 동기 복제가 커밋을 얼마나 늦추는지는 [멀티 리전](/posts/multi-region)에서 실제로 잰다.

## 양쪽에서 쓰게 하면 생기는 일

지금까지는 쓰기를 받는 주 DB가 서울 한 곳에 있다고 봤다. 미국 사용자가 리뷰를 쓰면 버지니아의 웹 서버가 서울의 주 DB까지 가서 쓴다. 읽기는 가깝지만 쓰기는 여전히 멀다. 이렇게 한 곳만 쓰기를 받고 다른 곳은 대기하거나 읽기만 하는 구성을 액티브-패시브(active-passive)라고 한다.

양쪽 모두 쓰기를 받는 액티브-액티브(active-active)도 있다. 쓰기까지 가까워지지만, 같은 식당의 영업시간을 서울과 버지니아에서 동시에 다르게 고치면 두 값이 부딪친다. 둘 중 무엇을 남길지 정하는 규칙이 필요하고, 마지막에 쓴 것을 남기는 단순한 규칙은 조용히 한쪽 수정을 잃는다. 그래서 흔히 쓰는 타협은 사용자마다 "주인 데이터 센터"를 정하는 것이다. 한국 사용자의 데이터는 서울이, 미국 사용자의 데이터는 버지니아가 쓰기를 받는다. 이 방식과 충돌 처리는 [멀티 리전](/posts/multi-region)과 [최종 일관성](/posts/eventual-consistency)에서 이어진다.

처음 설계라면 액티브-패시브로 시작하고, 쓰기 지연이 정말 문제가 될 때 사용자별 주인을 나누는 쪽으로 간다고 말하는 것이 무난하다.

## 넘기는 연습과 되돌아오는 길

데이터 센터 전환은 자주 일어나지 않는다. 그래서 막상 필요할 때 안 된다. 버지니아에 둔 설정 파일이 서울보다 두 달 늦은 버전이었다거나, 버지니아 DB를 주 DB로 올리는 스크립트를 아무도 돌려 본 적이 없다거나 하는 식이다.

이걸 막는 방법은 두 가지다. 첫째, 두 데이터 센터를 같은 방법으로 만든다. 서버 설정과 네트워크를 코드로 적어 두고([IaC 기본 개념](/posts/iac-basics)), 같은 배포 파이프라인이 두 곳에 같은 버전을 올린다. 배포는 한 곳씩 한다. 서울에 먼저 올려 지표를 보고 문제가 없으면 버지니아에 올리면, 잘못된 배포가 두 곳을 동시에 쓰러뜨리는 일을 막는다. 사람이 손으로 하면 두 곳이 조금씩 어긋나기 때문에, 이 부분은 [⑦ 큐, 로그, 자동화](/posts/sd-queue-logging-automation)에서 다룰 자동화와 이어진다.

둘째, 정기적으로 실제로 넘겨 본다. 트래픽이 적은 시간에 서울을 빼고 버지니아만으로 돌려 보면, 감지·DNS·DB 승격·캐시 미스 폭주가 계산대로 움직이는지 확인할 수 있다. 일부러 장애를 일으켜 확인하는 연습은 [카오스 엔지니어링](/posts/chaos-engineering)의 게임 데이와 같은 생각이다.

## 다음 글

여기까지 오면 데이터 센터 하나가 통째로 사라져도 서비스는 돈다. 다만 장비가 두 배로 늘었고, 어딘가에서 문제가 나면 어느 데이터 센터의 어느 서버였는지 찾기도 두 배로 어려워졌다. 다음 글 [⑦ 큐, 로그, 자동화](/posts/sd-queue-logging-automation)에서는 오래 걸리는 일을 요청 밖으로 빼는 메시지 큐, 수십 대의 로그와 지표를 한곳에서 보는 법, 사람 손을 덜 타게 만드는 자동화를 붙인다.

더 깊이 보려면 리전 간 지연과 충돌은 [멀티 리전](/posts/multi-region), 주 DB를 넘기는 과정은 [장애 조치](/posts/failover), 백업과 복구 목표는 [재해 복구](/posts/disaster-recovery)로 가면 된다.

정리하면, 데이터 센터를 여러 곳에 두는 일은 사용자를 가까운 곳으로 보내는 일과 데이터를 멀리 복제하는 일로 나뉜다. 앞은 DNS의 TTL과 헬스 체크가 전환 시간을 정하고, 뒤는 동기냐 비동기냐가 잃는 양과 쓰기 지연을 맞바꾼다. 그리고 한쪽이 멈췄을 때 남은 쪽이 전부를 받을 여유가 있어야 전환이 의미가 있다.

## 면접에서 나올 만한 질문

### 왜 데이터 센터를 여러 곳에 두나요?

두 가지 이유다. 건물이나 리전 전체가 멈추는 장애에도 서비스를 이어 가기 위해서, 그리고 멀리 있는 사용자에게 가까운 곳에서 응답해 지연을 줄이기 위해서다. 같은 데이터 센터 안의 이중화는 서버 한 대의 고장은 막지만, 같은 전원과 회선을 쓰는 장비들이 함께 사라지는 경우는 막지 못한다.

### 사용자를 가까운 데이터 센터로 어떻게 보내나요?

보통 GeoDNS를 쓴다. 질의를 보낸 리졸버의 IP로 위치를 추정해 같은 도메인에 지역별로 다른 IP를 답한다. 헬스 체크 결과를 함께 봐서 죽은 데이터 센터는 답에서 뺀다. DNS 캐시 때문에 전환이 TTL만큼 늦는 것이 단점이라, 더 빠른 전환이 필요하면 같은 IP를 여러 지역에서 광고하는 애니캐스트 기반 글로벌 로드 밸런서를 쓴다.

### 한 데이터 센터가 멈추면 다른 곳으로 넘어가는 데 얼마나 걸리나요?

감지 시간, DNS TTL, 클라이언트가 다시 연결하는 시간의 합에 DB를 승격하는 시간이 더해진다. 10초 간격 헬스 체크를 세 번 실패로 판단하고 TTL이 30초면 DNS 쪽만 최대 1분 정도다. 감지를 예민하게 하면 빨라지지만 잘못된 전환이 늘고, TTL을 줄이면 질의가 늘며 일부 클라이언트는 TTL을 지키지 않는다. 그래서 목표 시간(RTO)을 정하고 실제 전환 연습으로 잰다.

### 데이터 센터 사이의 DB 복제는 동기로 하나요, 비동기로 하나요?

대부분 비동기로 한다. 리전 사이 왕복이 100ms를 넘으면 동기 복제는 모든 쓰기에 그만큼을 더하기 때문이다. 대신 장애 순간 아직 건너가지 못한 쓰기를 잃으니, 그 양(RPO)을 받아들일 수 있는 데이터인지 따져 본다. 잃으면 안 되는 쓰기는 같은 리전의 여러 AZ에 동기로 복제하고 리전 간은 비동기로 두는 조합이 흔하다.

### 한 곳이 멈췄는데 넘어간 데이터 센터도 함께 쓰러졌습니다. 왜 그럴까요?

남은 곳이 전체 트래픽을 받을 여유가 없었을 가능성이 크다. 두 곳이 평소 각각 60%로 돌면 하나가 빠질 때 남은 곳은 120%가 된다. 여기에 넘어간 사용자들의 데이터가 캐시에 없어 미스가 폭주하면 DB 부하가 더 오른다. 그래서 데이터 센터 수에 맞춰 평소 사용률 상한을 정하고, 리전 장애 때 오토스케일링이 늦을 수 있다는 점도 감안해 여유를 미리 둔다.

### 두 데이터 센터에서 모두 쓰기를 받으면 무엇이 어려워지나요?

같은 데이터를 양쪽에서 동시에 고치면 충돌이 생기고, 무엇을 남길지 정하는 규칙이 필요해진다. 마지막에 쓴 것을 남기는 규칙은 단순하지만 한쪽의 수정을 조용히 잃는다. 그래서 사용자나 데이터마다 쓰기를 받는 주인 데이터 센터를 하나로 정해 충돌 자체를 줄이는 방식을 많이 쓴다.

### 장애가 끝나 원래 데이터 센터로 되돌아갈 때 주의할 점은요?

바로 돌리면 안 된다. 원래 주 DB에는 장애 동안 쌓인 쓰기가 없고, 장애 직전 복제되지 못한 쓰기는 양쪽이 어긋난 채 남아 있다. 옛 주 DB를 새 주 DB의 복제본으로 다시 붙여 따라잡게 하고, 어긋난 기록을 확인한 뒤 계획된 시간에 트래픽을 조금씩 옮긴다.

### 두 데이터 센터를 어떻게 같은 상태로 유지하나요?

인프라와 설정을 코드로 관리하고, 같은 파이프라인이 두 곳에 같은 버전을 배포하게 한다. 배포는 한 곳씩 해서 문제가 생겨도 다른 곳은 멀쩡하게 남긴다. 그리고 정기적으로 실제 전환을 해 봐야 설정 차이나 돌려 본 적 없는 스크립트 같은 문제가 장애 전에 드러난다.
