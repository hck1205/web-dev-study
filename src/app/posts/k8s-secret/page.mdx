<EasyIntro>
  비밀번호 같은 값은 ConfigMap이 아니라 Secret에 넣으라고 한다. 이름이 비밀이니 안전해 보이지만, 기본 상태의 Secret은 값을 글자 모양만 살짝 바꿔 둔 평문이라 읽을 권한이 있는 사람은 명령 한 줄로 풀어 보고, 저장소에도 그대로 들어간다.

  Secret은 자물쇠 달린 금고가 아니라 비밀 전용 서랍에 가깝다. 서랍이라서 좋은 점은 있어서, 필요한 기계에만 보내고, 기계에서는 디스크가 아닌 메모리에만 머물고, 화면에 보여 줄 때 값을 가려 준다. 하지만 자물쇠는 직접 달아야 한다. 저장소에 쓸 때 암호화를 켜고, 읽을 수 있는 사람을 줄이고, 사람과 도구가 흘리는 길을 막는 일이 그것이다.

  이걸 알면 Secret에 넣었으니 끝이라는 생각이 왜 위험한지 보인다. 값이 클러스터 안에서 어디를 지나 어디에 머무는지 따라가며 지점마다 지켜야 한다.
</EasyIntro>

DB 비밀번호를 ConfigMap이 아니라 Secret에 넣었다. 이름부터 비밀이니 안전하다고 생각하기 쉽다. 그런데 이 네임스페이스의 Secret 목록을 볼 수 있는 사람은 명령 한 줄로 비밀번호를 읽는다.

```bash
# Secret 값을 꺼내서 base64를 푼다
kubectl get secret db-cred -n shop -o jsonpath='{.data.password}' | base64 -d; echo
```

```text
s3cr3t-Pr0d!
```

키도 비밀번호도 필요 없었다. Secret은 기본 상태로는 "비밀을 담는 전용 칸"일 뿐 암호화된 금고가 아니다. 이 글은 Secret 값이 클러스터 안에서 어디를 지나 어디에 머무는지 따라가면서 각 지점을 어떻게 지키는지 본다. etcd에 저장할 때의 암호화, 읽을 수 있는 사람을 줄이는 RBAC, Pod에 넣는 방식에 따른 차이, 레지스트리 인증, 클러스터 밖의 저장소와 잇는 방법까지 다룬다.

이 글의 출력은 [ConfigMap 글](/posts/k8s-configmap)과 같은 kwok 실습 클러스터(Kubernetes 1.30)에서 받았다. API 서버와 etcd는 진짜 바이너리라서 etcd에 저장된 원본 바이트와 저장 시 암호화까지 실제로 확인했다. 컨테이너 안에서 본 출력만 예시로 표시했다.

## base64는 암호가 아니다

Secret을 하나 만들어 YAML로 보면 값이 알아볼 수 없는 문자열로 바뀌어 있다.

```bash
# 사용자 이름과 비밀번호를 담은 Secret을 만든다
kubectl create secret generic db-cred -n shop \
  --from-literal=username=shop \
  --from-literal=password='s3cr3t-Pr0d!'

# 저장된 모습을 본다
kubectl get secret db-cred -n shop -o yaml
```

```text
secret/db-cred created
apiVersion: v1
data:
  password: czNjcjN0LVByMGQh
  username: c2hvcA==
kind: Secret
metadata:
  creationTimestamp: "2026-10-20T13:55:11Z"
  name: db-cred
  namespace: shop
  resourceVersion: "298"
  uid: 3b9a033b-136a-4427-badb-5be488b010bc
type: Opaque
```

`czNjcjN0LVByMGQh`는 암호문이 아니라 base64로 인코딩한 것이다. base64는 아무 바이트나 영문자와 숫자 64개로 표현하는 규칙이고, 키가 없다. 규칙만 알면 누구나 되돌린다. 아래 그림에서 네 글자씩 끊어 원래 글자 세 개로 되돌리는 과정을 볼 수 있다. base64 자체의 원리는 [Base64 글](/posts/base64)에서 다룬다.

그럼 base64는 왜 쓸까. 비밀번호가 아니라 TLS 개인 키나 키스토어 파일처럼 바이너리 값도 담기 위해서다. JSON과 YAML은 아무 바이트나 담지 못하니 글자로 바꿔 넣는다. 보호하려는 목적이 아니다.

손으로 base64를 만들 때 자주 하는 실수가 있다. `echo`는 끝에 줄바꿈을 붙인다.

```bash
# 줄바꿈 없이 인코딩한다
echo -n 's3cr3t-Pr0d!' | base64

# echo가 붙인 줄바꿈까지 인코딩된다
echo 's3cr3t-Pr0d!' | base64
```

```text
czNjcjN0LVByMGQh
czNjcjN0LVByMGQhCg==
```

두 번째 값을 Secret의 `data`에 넣으면 비밀번호가 `s3cr3t-Pr0d!\n`이 된다. 앱은 DB 인증 실패를 내고, 눈으로 봐서는 비밀번호가 맞아 보인다. `kubectl create secret --from-literal`이나 `stringData`를 쓰면 이 실수를 피한다. 아래에서 Secret의 `data`를 풀면서 줄바꿈이 끼어 있는 키를 찾아내는 함수를 짜 볼 수 있다.

## ConfigMap과 무엇이 다른가

값이 평문이나 다름없다면 ConfigMap과 다를 게 없어 보인다. 저장 형식만 보면 그렇다. 차이는 쿠버네티스가 Secret을 다루는 방식에 있다.

`kubectl describe`는 값을 보여 주지 않고 크기만 보여 준다. 어깨 너머로 보는 정도는 막는다.

```bash
# describe는 바이트 수만 보여 준다
kubectl describe secret db-cred -n shop
```

```text
Name:         db-cred
Namespace:    shop
Labels:       <none>
Annotations:  <none>

Type:  Opaque

Data
====
password:  12 bytes
username:  4 bytes
```

노드 쪽 차이가 더 크다. kubelet은 자기 노드에 뜬 Pod가 쓰는 Secret만 받아 온다. API 서버의 Node 인가가 다른 노드의 Secret을 읽지 못하게 막는다. 볼륨으로 넣은 Secret은 노드 디스크가 아니라 메모리 위의 tmpfs에 쓰이고, Pod가 지워지면 함께 사라진다. 노드 디스크를 떼어 가도 Secret 파일은 남아 있지 않다.

`type`도 다르다. 타입마다 꼭 있어야 하는 키가 정해져 있어서, API 서버가 모양을 검사한다.

```bash
# 인증서와 키로 TLS Secret을 만든다
kubectl create secret tls shop-tls -n shop --cert=tls.crt --key=tls.key

# TLS 타입인데 키 파일을 빠뜨린다
kubectl create secret generic bad-tls -n shop --type=kubernetes.io/tls --from-file=tls.crt=tls.crt

```

```text
secret/shop-tls created
error: failed to create secret Secret "bad-tls" is invalid: data[tls.key]: Required value
```

Ingress 컨트롤러는 `kubernetes.io/tls` 타입의 `tls.crt`와 `tls.key`를 읽는다. 타입을 맞춰 두면 키 이름 오타를 만들 때 바로 잡힌다. 아무 키나 넣는 일반 Secret은 `Opaque`다. 크기 한도는 ConfigMap과 같은 1MiB이고, `immutable`도 똑같이 쓸 수 있다.

## stringData와 last-applied에 남는 평문

YAML 파일에 직접 쓸 때는 base64를 손으로 만들지 않고 `stringData`에 평문을 쓴다. API 서버가 저장하면서 `data`로 옮겨 준다. 문제는 이 파일을 `kubectl apply`로 올릴 때 생긴다.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: smtp
  namespace: shop
type: Opaque
stringData:
  SMTP_USER: mailer
  SMTP_PASSWORD: m41l-Pa55
```

```bash
# stringData로 쓴 Secret을 apply한다
kubectl apply -f smtp.yaml

# 저장된 Secret을 본다
kubectl get secret smtp -n shop -o yaml
```

```text
secret/smtp created
apiVersion: v1
data:
  SMTP_PASSWORD: bTQxbC1QYTU1
  SMTP_USER: bWFpbGVy
kind: Secret
metadata:
  annotations:
    kubectl.kubernetes.io/last-applied-configuration: |
      {"apiVersion":"v1","kind":"Secret","metadata":{"annotations":{},"name":"smtp","namespace":"shop"},"stringData":{"SMTP_PASSWORD":"m41l-Pa55","SMTP_USER":"mailer"},"type":"Opaque"}
  creationTimestamp: "2026-10-20T13:55:44Z"
  name: smtp
  namespace: shop
  resourceVersion: "326"
  uid: 4756413b-5bd3-40b2-a5c9-22927cd519ba
type: Opaque
```

`data`는 base64인데 어노테이션에 평문 비밀번호가 그대로 있다. `kubectl apply`가 다음 번 비교를 위해 적용한 원본 전체를 `last-applied-configuration`에 저장하기 때문이다. 이 Secret을 화면 공유나 장애 티켓에 `-o yaml`로 붙이면 base64조차 거치지 않은 비밀번호가 나간다.

서버 쪽 apply를 쓰면 이 어노테이션이 생기지 않는다.

```bash
# 같은 내용을 서버 쪽 apply로 올리고 어노테이션을 본다
kubectl apply --server-side -f smtp-ssa.yaml
kubectl get secret smtp-ssa -n shop -o jsonpath='{.metadata.annotations}'; echo "[끝]"
```

```text
secret/smtp-ssa serverside-applied
[끝]
```

`kubectl create secret`이나 `kubectl replace`도 이 어노테이션을 남기지 않는다. Secret을 클라이언트 쪽 apply로 관리해 왔다면 `kubectl annotate secret smtp kubectl.kubernetes.io/last-applied-configuration-`로 지울 수 있다. 다만 지우는 것보다 비밀 값이 든 YAML을 애초에 git과 터미널에 두지 않는 게 먼저다. 그 방법은 뒤의 "클러스터 밖에 원본을 두는 방법"에서 본다.

## etcd에는 평문으로 들어간다

실습 클러스터의 etcd에서 Secret 원본 바이트를 꺼내 본다. 관리형 클러스터에서는 etcd에 직접 붙을 수 없지만, 직접 운영하는 클러스터나 etcd 백업 파일을 가진 사람은 이렇게 읽을 수 있다.

```bash
# etcd에 저장된 Secret 값에서 사람이 읽을 수 있는 문자열만 뽑는다
etcdctl get /registry/secrets/shop/db-cred --print-value-only | strings
```

```text
Secret
db-cred
shop"
*$3b9a033b-136a-4427-badb-5be488b010bc2
kubectl-create
Update
FieldsV1:A
?{"f:data":{".":{},"f:password":{},"f:username":{}},"f:type":{}}B
password
s3cr3t-Pr0d!
username
shop
Opaque
```

base64도 아니고 평문 그대로다. 쿠버네티스는 객체를 protobuf로 직렬화해서 `k8s\0`으로 시작하는 바이트로 저장할 뿐이다. 아래에서 바이트 단위로 다시 보게 된다.

etcd 스냅샷을 S3에 백업해 두었다면 그 버킷을 읽을 수 있는 사람이 모든 Secret을 가진다. etcd 디스크가 담긴 볼륨 스냅샷도 마찬가지다. etcd는 키-값 저장소라서 값의 의미를 모른다. etcd 자체는 [키-값 DB 글](/posts/db-type-key-value)에서 다룬다.

## API 서버가 etcd에 쓰기 전에 암호화하기

막는 방법은 API 서버에 암호화 설정 파일을 주는 것이다. API 서버가 etcd에 쓰기 직전에 암호화하고, 읽은 직후에 복호화한다. 사용자와 Pod는 아무것도 바뀌지 않은 것처럼 본다. 이를 저장 시 암호화(encryption at rest)라고 부른다.

```yaml
# /etc/kubernetes/enc/enc.yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets                  # 암호화할 리소스. configmaps를 더할 수도 있다
    providers:
      - aescbc:                  # 맨 위 provider로 새로 쓰는 값을 암호화한다
          keys:
            - name: key1     # 키는 head -c 32 /dev/urandom | base64로 만든다
              secret: wlMcFcu8hiUjFvOl3DWkjtIX4zHkqgsrNP5WGzLFkS0=
      - identity: {}             # 아직 암호화 안 된 옛 값을 읽기 위해 둔다
```

```bash
# kube-apiserver 실행 인자에 설정 파일을 준다 (kubeadm이면 /etc/kubernetes/manifests/kube-apiserver.yaml)
--encryption-provider-config=/etc/kubernetes/enc/enc.yaml
```

provider 목록의 순서에 의미가 있다. 새로 쓸 때는 맨 위 provider 하나만 쓰고, 읽을 때는 위에서부터 차례로 풀어 본다. `identity`는 "암호화하지 않음"이다. 위 설정에서 `identity`를 빼면 이전에 평문으로 저장된 Secret을 읽지 못하게 된다.

API 서버를 다시 띄운 뒤 새 Secret을 만들고 etcd를 보면 이렇다.

```bash
# 설정을 켠 뒤 새 Secret을 만든다
kubectl create secret generic api-key -n shop --from-literal=token=tk_live_9f8e7d

# 새 Secret과 옛 Secret의 앞부분을 비교한다
etcdctl get /registry/secrets/shop/api-key --print-value-only | head -c 40 | od -c | head -2
etcdctl get /registry/secrets/shop/db-cred --print-value-only | head -c 40 | od -c | head -2
```

새 Secret은 `k8s:enc:aescbc:v1:key1:`로 시작하는 암호문이다. 그런데 설정을 켜기 전에 만든 `db-cred`는 아직 평문이다. 설정은 앞으로 쓰는 값에만 적용되기 때문이다. 이미 있는 Secret은 한 번씩 다시 써야 암호화된다.

```bash
# 모든 Secret을 읽어서 그대로 다시 쓴다 (내용은 안 바뀌고 저장 형식만 바뀐다)
kubectl get secrets -A -o json | kubectl replace -f -

# 옛 Secret을 다시 본다
etcdctl get /registry/secrets/shop/db-cred --print-value-only | head -c 23; echo
```


provider는 무엇을 고를까. 쿠버네티스 문서는 로컬 키 방식 중에서 `secretbox`를 강하다고 보고, `aescbc`는 CBC 모드의 패딩 오라클 문제로 권하지 않는다. `aesgcm`은 쓰기 20만 번마다 키를 바꿔야 한다. 그래서 실습 클러스터도 `secretbox`로 옮겼다. 키를 바꾸는 순서는 "새 키를 목록 맨 위에 넣고 모든 API 서버를 다시 띄운다 → 모든 Secret을 다시 쓴다 → 옛 키를 뺀다"이다. 실습에서는 providers 맨 위에 `secretbox`(키 이름 `key2`)를 넣고 그 아래에 기존 `aescbc`의 `key1`과 `identity`를 남겼다.

```bash
# API 서버를 다시 띄운 뒤 전부 다시 쓰고, 저장된 머리말을 모아 본다
kubectl get secrets -A -o json | kubectl replace -f - > /dev/null
for k in $(etcdctl get /registry/secrets/ --prefix --keys-only); do
  printf "%s " "$k"; etcdctl get "$k" --print-value-only | head -c 26; echo
done
```

```text
/registry/secrets/shop/api-key k8s:enc:secretbox:v1:key2:
/registry/secrets/shop/db-cred k8s:enc:secretbox:v1:key2:
/registry/secrets/shop/ecr-pull k8s:enc:secretbox:v1:key2:
/registry/secrets/shop/shop-tls k8s:enc:secretbox:v1:key2:
/registry/secrets/shop/smtp k8s:enc:secretbox:v1:key2:
/registry/secrets/shop/smtp-ssa k8s:enc:secretbox:v1:key2:
```

모두 `key2`가 됐으니 이제 `aescbc` 항목을 빼도 된다. 다시 쓰기 전에 옛 키를 빼면 옛 키로 암호화된 Secret을 읽지 못해 그 Secret을 쓰는 Pod가 뜨지 못한다. 여러 대의 API 서버가 있으면 모두 같은 설정을 가져야 한다. 한 대라도 옛 설정이면 그 서버가 쓴 값은 다른 서버가 못 읽는다.

<Callout kind="warning" title="암호화 키를 잃으면 Secret도 잃는다">
설정 파일의 키가 없어지면 etcd에 있는 Secret을 영영 풀 수 없다. etcd를 백업할 때 암호화 설정 파일도 따로 백업하되, 같은 곳에 두지 않는다. 키를 바꾸다 문제가 생기면 옛 키를 목록에 다시 넣고 API 서버를 재시작하면 읽기가 돌아온다. 그래서 모든 값을 새 키로 다시 쓰고 확인하기 전까지 옛 키를 지우지 않는다.
</Callout>

로컬 키 방식에는 한계가 하나 있다. 키가 컨트롤 플레인 노드의 파일에 평문으로 있다. 노드 디스크를 가진 사람은 etcd 데이터와 키를 함께 가진다. 그래서 운영에서는 키를 AWS KMS 같은 외부 키 관리 서비스에 두는 `kms` provider를 쓴다. 쿠버네티스 1.29부터 KMS v2가 정식이고 v1은 쓰지 않는다. 동작은 봉투 암호화다.

흔히 놓치는 게 `list`다. "목록만 보는 권한"처럼 들리지만, `list` 응답에는 각 Secret의 `data`가 통째로 들어 있다. 실습해 본다.

```bash
# list만 할 수 있는 ServiceAccount를 만든다
kubectl create serviceaccount viewer -n shop
kubectl create role secret-lister -n shop --verb=list --resource=secrets
kubectl create rolebinding viewer-list -n shop --role=secret-lister --serviceaccount=shop:viewer

# get은 안 되고 list는 된다
kubectl auth can-i get secret/db-cred -n shop --as=system:serviceaccount:shop:viewer
kubectl auth can-i list secrets -n shop --as=system:serviceaccount:shop:viewer

# list로 값을 꺼내 본다
kubectl get secrets -n shop --as=system:serviceaccount:shop:viewer \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.data.password}{"\n"}{end}'

# 같은 사용자의 get은 막힌다
kubectl get secret db-cred -n shop --as=system:serviceaccount:shop:viewer
```

`get`은 거절되는데 `list` 결과에 비밀번호가 들어 있다. `watch`도 같다. 모니터링 도구나 대시보드에 "Secret 목록 보기"를 주면 사실상 전부 읽기 권한을 준 것이다.

앱에 필요한 권한은 보통 특정 Secret 하나의 `get`이다. `resourceNames`로 이름을 못 박는다.

```bash
# db-cred 하나만 get할 수 있는 Role을 만들어 api ServiceAccount에 준다
kubectl create role app-secret-reader -n shop --verb=get --resource=secrets --resource-name=db-cred
kubectl create serviceaccount api -n shop
kubectl create rolebinding api-read -n shop --role=app-secret-reader --serviceaccount=shop:api

# 정한 Secret만, get만 된다
kubectl auth can-i get secret/db-cred -n shop --as=system:serviceaccount:shop:api
kubectl auth can-i get secret/smtp -n shop --as=system:serviceaccount:shop:api
kubectl auth can-i list secrets -n shop --as=system:serviceaccount:shop:api
```

```text
role.rbac.authorization.k8s.io/app-secret-reader created
serviceaccount/api created
rolebinding.rbac.authorization.k8s.io/api-read created
yes
no
no
```

사실 Pod가 env나 볼륨으로 Secret을 쓰는 데에는 이 권한도 필요 없다. 그건 kubelet이 노드 자격으로 가져온다. ServiceAccount에 Secret 권한이 필요한 건 앱이 API 서버를 직접 부를 때뿐이다.

그림의 왼쪽 아래 길도 기억해 둔다. 네임스페이스에 Pod를 만들 수 있는 사람은 그 네임스페이스의 아무 Secret이나 마운트한 Pod를 띄워 내용을 읽을 수 있다. Deployment, Job, CronJob을 만들 권한도 같다. 그래서 Secret을 진짜로 나누고 싶다면 RBAC의 Secret 권한만이 아니라 네임스페이스 자체를 나눈다. 네임스페이스 단위로 권한을 거는 방법은 [Namespace 글](/posts/k8s-namespace)에 있다.

## 환경 변수로 넣을까, 파일로 넣을까

Secret을 Pod에 넣는 방법은 ConfigMap과 같다. `env.valueFrom.secretKeyRef`, `envFrom.secretRef`, `volumes.secret`이다. 편한 건 환경 변수인데, 새는 길이 더 많다.

```yaml
      containers:
        - name: api
          image: shop/api:1.4.2
          env:
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-cred
                  key: password
            - name: DEBUG_TOKEN
              value: "tk_live_9f8e7d"     # 매니페스트에 값을 직접 적은 경우
          envFrom:
            - secretRef:
                name: smtp
          volumeMounts:
            - name: db-cred
              mountPath: /etc/secrets/db
              readOnly: true
      volumes:
        - name: db-cred
          secret:
            secretName: db-cred
            defaultMode: 0400             # 소유자만 읽기
```

```bash
# describe가 환경 변수를 어떻게 보여 주는지 본다
kubectl describe pod api -n shop | sed -n '/Environment Variables from/,/Mounts:/p'

# set env --resolve는 참조를 풀어서 값을 보여 준다
kubectl set env pod/api -n shop --list --resolve
```

```text
    Environment Variables from:
      smtp  Secret  Optional: false
    Environment:
      DB_PASSWORD:  <set to the key 'password' in secret 'db-cred'>  Optional: false
      DEBUG_TOKEN:  tk_live_9f8e7d
    Mounts:
# Pod api, container api
DB_PASSWORD=s3cr3t-Pr0d!
DEBUG_TOKEN=tk_live_9f8e7d
```

`secretKeyRef`로 넣은 값은 describe에 참조만 보이지만, `value`로 직접 적은 토큰은 그대로 보인다. Pod 스펙은 Secret보다 훨씬 넓게 읽히는 객체다. Pod를 볼 권한만 있어도 보이니, 비밀 값을 `value`에 적으면 안 된다. `--resolve`는 Secret을 읽을 권한이 있는 사람에게 값을 풀어 보여 준다.

환경 변수가 새는 길은 컨테이너 안에도 많다. 같은 컨테이너의 모든 자식 프로세스가 환경을 물려받는다. 리눅스에서는 `/proc/<PID>/environ`으로 프로세스 환경을 읽을 수 있다. 앱이 시작할 때 설정을 전부 로그로 찍거나, 에러 리포터가 환경 변수를 함께 보내는 일도 흔하다. 그리고 환경 변수는 Secret이 바뀌어도 Pod를 다시 띄우기 전까지 그대로다.

파일로 넣으면 이런 문제가 줄어든다. 볼륨으로 넣은 Secret은 tmpfs에 쓰인다. 아래는 컨테이너 안에서 본 예시다.

```bash
# 마운트가 tmpfs인지, 파일 권한이 어떤지 본다
kubectl exec -n shop api -- sh -c 'mount | grep /etc/secrets/db; ls -lL /etc/secrets/db'
```

```text
tmpfs on /etc/secrets/db type tmpfs (ro,relatime,size=65536k)
total 8
-r--------    1 root     root            12 Oct 20 13:56 password
-r--------    1 root     root             4 Oct 20 13:56 username
```

파일은 읽을 사람을 파일 권한으로 좁힐 수 있고, 로그에 우연히 찍힐 일도 적다. Secret이 바뀌면 ConfigMap처럼 kubelet이 지연을 두고 파일을 바꿔 준다(subPath는 역시 제외). 앱이 파일 경로를 받아 읽도록 만들 수 있다면 파일 쪽이 낫다. 공식 postgres 이미지가 `POSTGRES_PASSWORD` 대신 `POSTGRES_PASSWORD_FILE`로 파일 경로를 받는 것처럼, 환경 변수에는 경로만 두고 값은 파일에서 읽는 방식이 흔히 쓰인다.

## 레지스트리 인증 imagePullSecrets

비공개 레지스트리에서 이미지를 받으려면 kubelet이 레지스트리 인증 정보를 알아야 한다. 이건 `kubernetes.io/dockerconfigjson` 타입 Secret에 담는다.

```bash
# 레지스트리 인증용 Secret을 만든다
kubectl create secret docker-registry ecr-pull -n shop \
  --docker-server=123456789012.dkr.ecr.ap-northeast-2.amazonaws.com \
  --docker-username=AWS \
  --docker-password=eyJwYXlsb2FkIjoi

# 안에 든 JSON을 풀어 본다
kubectl get secret ecr-pull -n shop -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d; echo
```

```text
secret/ecr-pull created
{"auths":{"123456789012.dkr.ecr.ap-northeast-2.amazonaws.com":{"username":"AWS","password":"eyJwYXlsb2FkIjoi","auth":"QVdTOmV5SndZWGxzYjJGa0lqb2k="}}}
```

`~/.docker/config.json`과 같은 형식이다. `auth`는 `사용자:비밀번호`를 base64로 한 번 더 감싼 것뿐이다. 이 Secret을 Pod마다 `imagePullSecrets`로 적어도 되지만, `kubectl patch serviceaccount default -n shop -p '{"imagePullSecrets":[{"name":"ecr-pull"}]}'`처럼 ServiceAccount에 붙여 두면 그 ServiceAccount로 뜨는 모든 Pod의 스펙에 ServiceAccount 어드미션이 `imagePullSecrets: [{"name":"ecr-pull"}]`를 자동으로 넣는다. 실습 클러스터에서 아무것도 적지 않은 Pod를 띄워 스펙에 들어간 것을 확인했다.

인증이 틀리면 Pod는 `ImagePullBackOff`가 되고 이벤트에 `401 Unauthorized`나 `no basic auth credentials`가 남는다. 상태별로 보는 순서는 [Pod 트러블슈팅 글](/posts/k8s-pod-troubleshooting)에 있다.

ECR에는 함정이 있다. ECR 로그인 토큰은 12시간 뒤 만료된다. 위처럼 토큰으로 Secret을 만들어 두면 반나절 뒤부터 새 노드에서 이미지를 못 받는다. 이미 노드에 받아 둔 이미지는 쓰니 당장은 멀쩡해 보이다가, 스케일 아웃이나 노드 교체 때 터진다. EKS에서는 노드의 IAM 역할에 ECR 읽기 권한을 주면 kubelet의 자격 증명 공급자가 알아서 토큰을 받아 오므로 imagePullSecrets가 필요 없다. 클러스터가 다른 클라우드에 있다면 토큰을 주기적으로 새로 받아 Secret을 고치는 CronJob이나 External Secrets의 ECR 토큰 생성기를 쓴다.

## 클러스터 밖에 원본을 두는 방법

지금까지는 Secret을 누군가 `kubectl`로 만든다고 가정했다. 그럼 그 원본은 어디에 두나. git에 평문으로 둘 수 없고, 사람이 손으로 만들면 환경마다 어긋난다. 방법은 크게 셋이다.

첫째는 git에 암호화해서 두는 것이다. SOPS로 값만 암호화한 파일을 두거나, Sealed Secrets로 클러스터만 풀 수 있는 `SealedSecret`을 둔다. 둘째는 Vault나 AWS Secrets Manager 같은 외부 저장소에 원본을 두고 External Secrets Operator(ESO)가 읽어 Secret을 만들게 하는 것이다. 이 두 갈래는 Helm으로 배포할 때의 흐름과 함께 [values와 비밀 값 글](/posts/helm-values-secrets)에서 자세히 본다.

셋째는 Secret 객체를 아예 만들지 않는 Secrets Store CSI Driver다. Pod가 뜰 때 CSI 드라이버가 외부 저장소에서 값을 읽어 Pod의 볼륨에 파일로 바로 넣는다. etcd에는 값이 들어가지 않는다.

셋을 고르는 기준은 원본을 어디에 두고 싶은지다. 외부 저장소가 이미 있고 비밀번호 교체를 배포와 떼어 놓고 싶으면 ESO가 무난하다. 앱은 평범한 Secret을 읽으니 바꿀 게 없다. etcd에 값이 들어가는 것 자체를 피해야 한다면 CSI 드라이버를 쓴다. 대신 Pod가 뜰 때마다 외부 저장소를 부르니 저장소 장애가 곧 Pod 시작 실패가 되고, 환경 변수로 쓰기 어렵다. 외부 저장소 없이 git만으로 끝내려면 Sealed Secrets나 SOPS다.

## 비밀 값이 새는 길과 새고 난 뒤

현장에서 Secret이 새는 곳은 대개 etcd가 아니라 사람과 도구 쪽이다. 장애 티켓에 붙인 `kubectl get secret -o yaml`, CI 로그에 찍힌 `helm upgrade --set password=...`, 앱이 시작할 때 출력한 설정 덤프, git에 올라간 `.env` 파일, 앞에서 본 last-applied 어노테이션이 흔한 경로다. Helm으로 배포했다면 values에 넣은 값이 릴리스 기록 Secret에도 남는다. 이건 [Helm 기본 글](/posts/helm-basics)에서 본 구조 때문이다.

새는 걸 막는 습관은 이렇다. 비밀 값을 명령줄 인자로 넘기지 않는다(셸 히스토리와 `ps`에 남는다). `kubectl get secret`의 출력은 공유하기 전에 `data`를 지운다. 앱의 설정 출력 코드는 비밀 키를 가린다. 누가 Secret을 읽었는지 알고 싶다면 API 서버의 감사 로그에서 `secrets` 리소스의 `get`, `list`, `watch`를 남긴다.

그래도 샜다면 할 일은 하나다. 값을 바꾼다. git 기록에서 지우는 것은 그다음이다. 이미 누군가 받아 간 값은 지워도 남아 있다. 바꾸는 순서는 이렇다.

```bash
# 1) DB에 새 비밀번호를 만든다 (옛 비밀번호도 잠시 살려 둘 수 있으면 둔다)
# 2) 새 비밀번호를 파일로 받아 Secret을 바꾼다 (명령줄에 값을 적지 않는다)
kubectl create secret generic db-cred -n shop \
  --from-literal=username=shop --from-file=password=./new-password.txt \
  --dry-run=client -o yaml | kubectl apply --server-side --force-conflicts -f -
shred -u ./new-password.txt

# 3) env로 읽는 앱은 다시 띄워야 새 값을 읽는다
kubectl rollout restart deploy/api -n shop
kubectl rollout status deploy/api -n shop

# 4) 모든 Pod가 새 값으로 붙은 걸 확인한 뒤 옛 비밀번호를 DB에서 막는다
```

```text
secret/db-cred serverside-applied
deployment.apps/api restarted
Waiting for deployment "api" rollout to finish: 1 old replicas are pending termination...
deployment "api" successfully rolled out
```

`--force-conflicts`가 붙은 이유가 있다. 이 Secret은 처음에 `kubectl create`로 만들어서 `data.password` 필드의 주인이 `kubectl-create`로 기록돼 있다. 서버 쪽 apply는 다른 주인이 가진 필드를 바꾸려 하면 `Apply failed with 1 conflict: conflict with "kubectl-create"`로 멈춘다. 내가 이 필드를 맡겠다는 뜻으로 강제한다.

순서를 거꾸로 해서 DB의 옛 비밀번호부터 막으면, 새 값을 아직 못 읽은 Pod가 모두 인증 실패로 쓰러진다. 볼륨으로 읽는 앱도 kubelet이 파일을 바꾸기까지 시간이 걸리니, 옛 값과 새 값이 잠시 함께 통하는 구간을 둔다. ConfigMap 글에서 본 롤아웃 방법이 여기서도 그대로 쓰인다.

## Secret이 지켜 주는 것과 아닌 것

Secret은 기본 상태에서 base64로 인코딩된 평문이고, etcd에도 평문으로 들어간다. Secret이 ConfigMap보다 나은 점은 필요한 노드에만 가고, 노드에서 tmpfs에 머물며, describe에서 값을 가리고, 타입별로 모양을 검사한다는 것이다. 나머지는 직접 켜야 한다. etcd와 백업은 저장 시 암호화(되도록 KMS)로, API로 읽는 길은 `list`까지 챙긴 RBAC와 네임스페이스 분리로, 사람과 도구로 새는 길은 서버 쪽 apply와 파일 마운트, 외부 저장소로 막는다. 데이터를 Pod보다 오래 남기는 일은 다음 글 [PV와 PVC](/posts/k8s-pv-pvc)에서 본다.

## 면접에서 나올 만한 질문

### Kubernetes Secret은 안전한가요?

기본 상태에서는 안전하지 않다. 값은 암호화가 아니라 base64 인코딩이고, etcd에도 평문으로 저장된다. 그래서 저장 시 암호화(되도록 KMS provider), Secret에 대한 get·list·watch 권한을 좁히는 RBAC, 필요하면 외부 저장소 연동을 함께 써야 한다. ConfigMap보다 나은 점은 필요한 노드에만 전달되고 노드에서 tmpfs에 머문다는 정도다.

### etcd 저장 시 암호화를 켜면 기존 Secret도 암호화되나요?

아니다. 설정은 앞으로 쓰는 값에만 적용된다. `kubectl get secrets -A -o json | kubectl replace -f -`처럼 모든 Secret을 한 번씩 다시 써야 암호화된다. 그때까지는 provider 목록에 `identity`를 남겨 옛 평문을 읽을 수 있게 둔다. etcd 값의 머리말 `k8s:enc:provider:v1:키이름:`으로 무엇으로 암호화됐는지 확인한다.

### 암호화 키는 어떻게 교체하나요?

새 키를 provider 목록 맨 위에 넣고 모든 API 서버를 재시작한다. 그러면 새로 쓰는 값은 새 키로 암호화되고 옛 값은 아래의 옛 키로 읽힌다. 모든 Secret을 다시 써서 새 키로 바꾼 뒤 옛 키를 뺀다. 다시 쓰기 전에 옛 키를 빼면 그 키로 된 Secret을 읽지 못한다.

### Secret을 list만 할 수 있는 권한은 안전한가요?

아니다. list와 watch 응답에는 각 Secret의 data가 그대로 들어 있어서 사실상 모든 Secret을 읽는 권한이다. 앱에는 resourceNames로 이름을 정한 get만 준다. 그리고 Pod를 만들 수 있는 사람은 그 네임스페이스의 아무 Secret이나 마운트해 읽을 수 있으므로, 강하게 나눠야 하면 네임스페이스를 나눈다.

### Secret을 환경 변수와 볼륨 중 어느 쪽으로 넣는 게 좋나요?

가능하면 볼륨이다. 환경 변수는 자식 프로세스에 상속되고, `/proc/PID/environ`, 설정 로그, 에러 리포트로 새기 쉬우며, Secret이 바뀌어도 재시작 전까지 그대로다. 볼륨은 tmpfs 위의 파일이라 권한으로 읽는 사람을 좁힐 수 있고, Secret이 바뀌면 지연을 두고 갱신된다. 다만 subPath로 마운트하면 갱신되지 않는다.

### kubectl apply로 Secret을 관리할 때 주의할 점은 무엇인가요?

클라이언트 쪽 apply는 적용한 원본 전체를 last-applied-configuration 어노테이션에 저장한다. stringData로 쓴 파일이면 평문 비밀번호가 그 어노테이션에 그대로 남는다. `kubectl apply --server-side`나 `kubectl create`를 쓰면 이 어노테이션이 생기지 않는다.

### ECR 이미지를 imagePullSecrets로 받다가 반나절 뒤 ImagePullBackOff가 납니다. 왜 그런가요?

ECR 로그인 토큰은 12시간 뒤 만료된다. 토큰으로 만든 dockerconfigjson Secret은 그 뒤로 401을 받는다. 이미 받아 둔 이미지는 쓰니 새 노드나 새 이미지에서만 실패한다. EKS라면 노드 IAM 역할에 ECR 읽기 권한을 주고 imagePullSecrets를 쓰지 않으며, 다른 환경이라면 토큰을 주기적으로 갱신하는 장치를 둔다.
