2단계 인증 앱을 처음 켜면 신기한 장면이 있다. 휴대폰은 비행기 모드인데도 서버가 받아 줄 여섯 자리 숫자가 30초마다 바뀌며 나온다. 휴대폰과 서버가 서로 연락하지 않는데 어떻게 같은 숫자를 알까. 답은 처음 QR 코드를 찍는 순간 둘이 비밀 하나를 나눠 가졌고, 그 뒤로는 시계만 보고 같은 계산을 한다는 데 있다.

이 글은 그 계산(TOTP, RFC 6238)을 Node 22의 `crypto`만으로 직접 구현해 RFC의 테스트 값과 맞춰 보고, 서버가 코드를 검증할 때 정해야 하는 것들(허용 칸, 재사용, 시도 횟수), 복구 코드, 그리고 SMS와 푸시 승인이 어디서 약한지를 따라간다. 숫자 코드로도 막지 못하는 피싱은 [패스키와 WebAuthn](/posts/passkeys-webauthn)이 다룬다.

## 두 번째 요소가 막는 것

로그인에 쓰는 증거는 보통 세 종류로 나눈다. 아는 것(비밀번호, PIN), 가진 것(휴대폰, 보안 키), 나 자신(지문, 얼굴)이다. 다중 인증(MFA)은 종류가 다른 증거를 둘 이상 요구하는 것이다. 비밀번호 두 개를 묻는 건 MFA가 아니다. 둘 다 "아는 것"이라 같은 방법으로 한꺼번에 샌다.

비밀번호가 새는 길은 다양하다. 다른 사이트에서 유출된 비밀번호를 그대로 넣어 보는 크리덴셜 스터핑(credential stuffing)이 가장 흔하다. 두 번째 요소가 있으면 비밀번호만 가진 공격자는 거기서 멈춘다. TOTP 앱은 "가진 것"을 증명한다. 비밀 키가 들어 있는 그 휴대폰이 있어야 지금의 숫자를 만들 수 있다.

## 시계를 숫자로 바꾸는 계산

TOTP는 HOTP(RFC 4226)에 시계를 얹은 것이다. HOTP는 "비밀 키와 카운터로 숫자를 만든다"이고, TOTP는 그 카운터 자리에 "1970년부터 지난 초 ÷ 30"을 넣는다. 30초 동안은 카운터가 같으니 숫자도 같다.

계산은 네 단계다. 카운터를 8바이트 빅 엔디언으로 쓰고, 비밀 키로 HMAC-SHA1을 계산해 20바이트를 얻는다. 마지막 바이트의 하위 4비트를 오프셋으로 삼아 그 자리부터 4바이트를 꺼내고 맨 위 비트를 지운다. 그 수를 10의 6제곱으로 나눈 나머지가 코드다. RFC 4226 부록의 테스트 키 `12345678901234567890`, 카운터 0으로 직접 계산했다.

```text
counter (8B)   : 0000000000000000
HMAC-SHA1      : cc93cf18508d94934c64b65d8ba7667fb7cde4b0
offset         : 0 (마지막 바이트 0xb0 & 0x0f)
4 bytes        : cc93cf18 -> & 0x7fffffff = 1284755224
mod 10^6      : 755224
count 0..9: 755224 287082 359152 969429 338314 254676 287922 162583 399871 520489
```

카운터 0부터 9까지의 값이 RFC 4226 부록 D의 표와 정확히 같다. 세 번째 단계, 오프셋으로 4바이트를 고르는 과정을 동적 절단(dynamic truncation)이라고 부른다. 아래 그림에서 칸은 HMAC 결과 20바이트다. RFC 본문의 다른 예시(마지막 바이트 `5a`)로 따라가 본다.

## 서버가 받아 줄 범위를 정한다

휴대폰 시계와 서버 시계는 조금씩 다르다. 사용자가 숫자를 보고 입력하는 사이에 30초 경계를 넘기도 한다. 그래서 서버는 현재 칸만이 아니라 앞뒤 한 칸 정도를 함께 받아 준다. 시각을 2025-10-25 00:00 UTC로 고정하고 앞뒤 칸의 코드와 검증 결과를 찍었다.

```text
now step 58711680
step -2 599530
step -1 588227
step +0 777039
step +1 401864
step +2 794640
verify current        : ok (drift +0)
verify same code again: replay (step 58711680 <= last 58711680)
verify previous step  : replay (step 58711679 <= last 58711680)
verify 3 steps old    : invalid
server 70s behind     : invalid
server 20s behind     : ok (drift +1)
```

두 번째와 세 번째 줄이 중요하다. 같은 코드를 5초 뒤에 다시 넣으면 거절한다. 사용자가 마지막으로 성공한 칸 번호를 저장해 두고, 그 칸이나 그보다 이전 칸의 코드는 받지 않는다. RFC 6238도 같은 코드를 두 번 받지 말라고 한다. 이걸 빼먹으면 어깨 너머로 본 숫자나 로그에 찍힌 숫자를 30~90초 안에 다시 쓸 수 있다.

마지막 두 줄은 서버 시계가 틀렸을 때다. 서버가 20초 느리면 사용자 코드가 서버 기준 다음 칸에 속해서 허용 범위로 통과한다. 70초 느리면 두 칸 넘게 벌어져 맞는 코드가 계속 틀렸다고 나온다. "2단계 인증이 갑자기 다 실패한다"는 문의가 몰리면 코드보다 서버 시계를 먼저 본다. VM의 NTP 동기화가 멈췄을 수 있다. Ubuntu라면 `timedatectl status`의 `System clock synchronized` 줄부터 본다. 시계를 확인하고 맞추는 방법은 [시계 어긋남](/posts/clock-skew)에 있다.

허용 칸을 넓히면 편해지지만 공격자가 맞힐 확률도 그만큼 오른다. 6자리 코드에 세 칸을 허용하면 아무 숫자나 넣었을 때 맞을 확률은 대략 3/1,000,000이다. 시도 횟수를 막지 않으면 이 확률이 쌓인다.

```text
     1 attempts -> 0.0003%
    10 attempts -> 0.0030%
   100 attempts -> 0.0300%
  1000 attempts -> 0.2996%
 10000 attempts -> 2.9555%
100000 attempts -> 25.9182%
```

십만 번이면 넷 중 하나는 뚫린다. 비밀번호를 이미 아는 공격자에게 OTP 입력을 무제한으로 열어 두면 6자리는 생각보다 약하다. 계정 단위로 실패 횟수를 세어 5회쯤에서 잠그고, 잠금은 IP가 아니라 계정에 건다. IP만 보면 여러 주소로 나눠 시도하는 걸 못 막는다. 요청 수 제한은 [레이트 리미팅 실무](/posts/rate-limiting-in-practice)에서 다룬 방식을 그대로 쓴다.

## 휴대폰을 잃었을 때를 먼저 만든다

2단계 인증을 켠 사용자가 휴대폰을 잃어버리면 스스로 들어올 방법이 없다. 그래서 등록할 때 복구 코드를 같이 준다. 일회용이고, 서버에는 해시만 둔다. 사용자가 대시를 빼거나 대문자로 넣어도 받아 주도록 정규화한 뒤 비교했다.

```text
show once to user: b2e86-9c9cd 1ce03-1fbb9 9f40d-3c7cd ...
stored (sha256)  : 4ac97e4398234b041533ad4e28ffc378...
use #1           : ok (9 left)
use #1 again     : already used
use #2 uppercase : ok (8 left)
```

이 데모는 코드 하나가 40비트(16진 10글자)라 SHA-256으로 저장했다. 비밀번호처럼 사람이 고른 값이 아니고 무작위라서 사전 공격은 통하지 않는다. 다만 40비트는 GPU로 전부 대입할 수 있는 크기라, 코드를 더 길게 만들거나 bcrypt·Argon2 같은 느린 해시를 쓰는 편이 안전하다. 쓸 때마다 지우고, 몇 개 남았는지 알려 주고, 다 쓰기 전에 새로 받게 한다.

복구 경로는 공격자가 가장 먼저 노리는 곳이다. "OTP를 못 받으세요? 이메일로 해제하기" 같은 버튼이 있으면 2단계 인증의 강도는 이메일 계정의 강도로 내려간다. 고객 센터가 전화 한 통에 2단계 인증을 풀어 주는 절차도 마찬가지다. 해제에는 복구 코드, 이미 등록된 다른 요소, 또는 신분 확인과 대기 시간을 요구한다.

## 푸시 승인과 반복 요청

푸시 승인은 휴대폰에 "로그인하시겠습니까? 승인 / 거부"를 띄우는 방식이다. 입력할 숫자가 없어 편하다. 그런데 비밀번호를 손에 넣은 공격자가 새벽에 로그인을 수십 번 시도하면, 알림에 지친 사용자가 결국 승인을 누르기도 한다. 이걸 MFA 피로 공격(push fatigue, MFA bombing)이라고 부른다.

막는 방법은 승인을 "누르기만 하면 되는 일"에서 벗어나게 하는 것이다. 로그인 화면에 두 자리 숫자를 띄우고 휴대폰 앱에 그 숫자를 입력하게 하는 번호 맞추기(number matching)가 대표적이다. 화면을 보고 있는 사람만 승인할 수 있다. 마이크로소프트 Authenticator는 2023년부터 이 방식을 기본으로 켰다. 짧은 시간에 푸시가 반복되면 막고, 알림에 접속 위치를 보여 주고, "내가 시도한 게 아니다"를 누르면 보안팀에 알리는 것도 함께 쓴다.

## 숫자 코드로는 못 막는 피싱

TOTP와 SMS, 번호 맞추기 없는 푸시는 같은 약점이 있다. 사용자를 속여 가짜 사이트에 입력하게 만들면 막지 못한다. 요즘 피싱 도구는 가짜 페이지를 따로 만들지 않고 진짜 사이트 앞에 중간자 프록시를 세운다(AiTM, adversary-in-the-middle). 사용자는 진짜와 똑같은 화면을 보고, 입력한 값은 그대로 진짜 사이트로 전달된다.

## 2단계 인증을 붙일 때 흔히 놓치는 것

등록을 확정하기 전에 첫 코드를 꼭 받는다. 그렇지 않으면 QR을 잘못 찍은 사용자가 다음 로그인부터 잠긴다. 비밀 키는 등록이 끝난 뒤 다시 보여 주지 않는다. 다른 기기에 추가하고 싶으면 새 비밀로 다시 등록하게 한다.

2단계 인증을 요구하는 곳이 로그인 화면 하나뿐이면 안 된다. 비밀번호 재설정, 이메일 변경, API 토큰 발급, OAuth 동의 같은 옆문이 비밀번호만으로 열리면 공격자는 그쪽으로 돈다. "이 기기 기억하기"는 기기 쿠키를 길게 주는 것이니, 그 쿠키를 비밀번호 변경 때 함께 끊는다.

로그에는 코드를 남기지 않는다. 디버깅하려고 입력값을 찍어 두면 재사용 방지가 없는 서버에서는 그대로 공격 재료가 된다. 실패 이유도 사용자에게는 "코드가 맞지 않는다" 하나로만 보여 준다. "시간이 지난 코드"와 "틀린 코드"를 구분해 알려 주면 공격자에게 힌트가 된다.

## 정리하며

TOTP는 처음에 나눠 가진 비밀 키와 시계로 같은 HMAC 계산을 하는 방식이다. 서버는 앞뒤 한 칸 정도를 허용하고, 이미 쓴 칸을 거절하고, 시도 횟수를 계정 단위로 막아야 6자리가 버틴다. 복구 경로와 옆문이 약하면 그쪽이 새고, 사용자가 가짜 사이트에 직접 입력하는 피싱은 숫자 코드로 막을 수 없다. 그 마지막 구멍을 막는 방법이 [패스키](/posts/passkeys-webauthn)이고, 회사 안에서 여러 앱의 로그인을 한곳으로 모으는 이야기는 [SSO: SAML과 OIDC](/posts/sso-saml-oidc)에서 이어진다.

## 면접에서 나올 만한 질문

### MFA는 무엇이고, 왜 같은 종류의 요소 두 개로는 부족한가요?

아는 것, 가진 것, 나 자신 중 종류가 다른 증거를 둘 이상 요구하는 인증이다. 비밀번호와 보안 질문처럼 둘 다 아는 것이면 유출 DB나 피싱 한 번에 함께 샌다. 종류가 다르면 한쪽이 새도 다른 쪽을 따로 훔쳐야 한다.

### TOTP는 어떻게 동작하나요?

등록할 때 서버와 앱이 무작위 비밀 키를 나눠 갖는다. 이후 둘 다 현재 시각을 30초로 나눈 몫을 카운터로 삼아 HMAC-SHA1을 계산하고, 동적 절단으로 4바이트를 골라 10의 6제곱으로 나눈 나머지를 코드로 쓴다. 네트워크 없이도 같은 숫자가 나오는 이유다.

### 서버는 TOTP 코드를 검증할 때 무엇을 챙겨야 하나요?

시계 차이를 감안해 앞뒤 한 칸 정도만 허용하고, 마지막으로 성공한 칸 번호를 저장해 같은 칸이나 이전 칸 코드를 거절한다. 실패 횟수는 계정 단위로 세어 잠근다. 6자리에 세 칸을 허용하면 한 번에 맞힐 확률이 약 3/1,000,000이라 무제한 시도에는 버티지 못한다.

### TOTP 비밀 키는 비밀번호처럼 해시로 저장하면 안 되나요?

안 된다. 검증하려면 원래 키로 같은 HMAC을 계산해야 해서 되돌릴 수 있는 형태로 가지고 있어야 한다. 대신 암호화해서 저장하고, 암호화 키는 DB와 분리된 KMS 같은 곳에 둔다.

### SMS 인증의 약점은 무엇인가요?

코드가 통신사망을 지나기 때문에 SIM 스와핑이나 통신망 가로채기에 노출되고, 지연과 미수신이 잦다. 사용자가 가짜 사이트에 입력하면 중계되는 건 TOTP와 같다. 그래서 NIST는 제한적 수단으로 분류하고, 실무에서는 앱이나 패스키를 못 쓰는 사용자의 대안으로 둔다.

### 푸시 피로 공격은 무엇이고 어떻게 막나요?

비밀번호를 가진 공격자가 승인 요청을 반복해서 보내 사용자가 지쳐 승인을 누르게 만드는 공격이다. 로그인 화면의 숫자를 앱에 입력하게 하는 번호 맞추기로 화면 앞의 사람만 승인할 수 있게 하고, 반복 요청을 제한하고, 알림에 위치를 보여 준다.

### TOTP를 켜도 피싱으로 계정이 털리는 이유는요?

TOTP 숫자는 어느 사이트에 입력되는지 모른다. 중간자 프록시가 사용자의 입력을 진짜 사이트로 바로 넘기면 로그인이 성공하고, 공격자는 그 뒤의 세션 쿠키를 가져간다. 이걸 구조적으로 막으려면 브라우저가 origin을 확인해 서명에 넣는 패스키 같은 피싱 저항 인증이 필요하다.

### 2단계 인증을 도입한 뒤에도 남는 구멍은 어디인가요?

복구 경로와 옆문이다. 이메일 링크 하나로 2단계 인증을 해제할 수 있거나, 비밀번호 재설정·API 토큰 발급이 비밀번호만으로 되면 공격자는 그쪽으로 돈다. 복구 코드는 해시로 저장하고 일회용으로 쓰며, 민감한 동작 앞에서는 다시 인증을 받는다.
