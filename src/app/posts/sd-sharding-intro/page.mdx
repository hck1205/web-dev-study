맛집 리뷰 앱이 잘돼서 리뷰가 수억 개가 됐다. 읽기는 캐시와 복제본이 나눠 받고 있어 견딘다. 문제는 쓰기다. 저녁 시간에 리뷰, 좋아요, 사진 정보가 초당 수천 건씩 들어오는데, 이 쓰기는 전부 주 DB 한 대가 받는다. 주 DB의 디스크 쓰기량과 CPU가 매일 저녁 한계에 닿고, 리뷰 테이블은 디스크 용량의 80%를 넘었다.

[② 웹과 DB 나누기](/posts/sd-split-web-and-db)에서 본 수직 확장, 즉 더 큰 서버로 바꾸는 방법은 이미 몇 번 썼다. 클라우드에서 고를 수 있는 가장 큰 DB 서버도 한계가 있고, 그 근처로 갈수록 가격이 성능보다 빠르게 오른다. 무엇보다 한 대라는 사실은 그대로다.

남은 방법은 데이터 자체를 여러 DB에 나눠 담는 것이다. 이걸 샤딩(sharding)이라고 하고, 나눠진 DB 하나하나를 샤드(shard)라고 부른다. 이 글은 샤딩을 처음 접하는 사람을 위해 무엇을 기준으로 나누는지, 나누고 나면 무엇이 어려워지는지를 작은 실험으로 따라간다.

## 복제본을 늘려도 쓰기는 줄지 않는다

먼저 왜 [④ DB 복제](/posts/sd-db-replication-intro)로는 이 문제가 풀리지 않는지 짚고 가자. 복제본은 주 DB의 모든 쓰기를 그대로 받아 다시 실행해서 같은 내용을 유지한다. 복제본이 열 대면 같은 쓰기가 열한 번 일어난다. 읽기는 열한 곳으로 나뉘지만, 쓰기는 어느 한 대에서도 줄지 않는다. 저장 용량도 마찬가지다. 모든 복제본이 전체 데이터를 다 들고 있다.

샤딩은 데이터를 겹치지 않게 나눈다. 사용자 1만 명을 샤드 네 개에 나누면 샤드마다 2,500명씩이다. 각 샤드는 같은 테이블 구조(스키마)를 갖지만 들어 있는 행은 서로 다르다. 쓰기도 그 행이 있는 샤드에서만 일어나니, 샤드 네 개면 각 샤드가 받는 쓰기는 대략 4분의 1이 된다.

## 같은 테이블을 네 DB에 나눠 담기

실제로 나눠 보자. PGlite(WASM으로 도는 PostgreSQL)를 네 개 띄워 샤드 네 개로 쓰고, 사용자 1만 명과 리뷰 4만 개를 넣었다. 어느 샤드에 넣을지는 `user_id % 4`, 즉 사용자 번호를 4로 나눈 나머지로 정했다. 이렇게 행이 갈 샤드를 정하는 기준 열을 샤딩 키(shard key)라고 한다. 리뷰는 작성자의 `user_id`를 따라 작성자와 같은 샤드에 넣었다.

```js
// shards.mjs 일부
const N = 4;
const shards = await Promise.all(Array.from({ length: N }, () => PGlite.create()));
const shardOf = (userId) => userId % N;                 // 샤딩 키: user_id

for (const db of shards) await db.exec(`
  CREATE TABLE users   (id int PRIMARY KEY, nickname text);
  CREATE TABLE reviews (id int PRIMARY KEY, user_id int, restaurant_id int, rating int, body text,
                        author_nickname text);           -- 작성자 닉네임을 같이 저장
`);
// 샤드 s에는 user_id % 4 = s인 사용자와 그 사람의 리뷰만 넣는다
```

```text
shard 0: users=2500 reviews=10198
shard 1: users=2500 reviews=9979
shard 2: users=2500 reviews=9815
shard 3: users=2500 reviews=10008
```

사용자는 정확히 2,500명씩, 리뷰는 사람마다 쓴 개수가 달라 1만 개 안팎으로 나뉘었다. 이제 앱은 쿼리를 보내기 전에 "이 사용자는 어느 샤드에 있나"를 먼저 계산해야 한다. 이 계산을 하는 곳을 라우터라고 부르자. 애플리케이션 코드 안의 함수일 수도 있고, DB 앞에 두는 별도 프록시일 수도 있다.

## 샤딩 키를 고르는 두 가지 기준

샤딩 설계에서 가장 중요한 결정이 샤딩 키다. 나중에 바꾸기가 매우 어렵기 때문이다. 기준은 두 가지다.

첫째, 데이터와 트래픽이 고르게 나뉘어야 한다. 사용자 10만 명을 세 가지 키로 나눠 봤다. 국가는 한국 70%, 미국 20%, 일본 10%로 두고, 가입 시기는 최근 24개월에 고르게 흩었다.

```js
// keys.js 일부
const byId = [0, 0, 0, 0]; users.forEach((u) => byId[u.id % 4]++);
const byCountry = { kr: 0, us: 0, jp: 0 }; users.forEach((u) => byCountry[u.country]++);
const byMonth = [0, 0, 0, 0]; users.forEach((u) => byMonth[Math.floor(u.month / 6)]++);  // 6개월씩 한 샤드
```

```text
== 1. 저장량 분포 (샤드 4개)
user_id % 4       25.0%  25.0%  25.0%  25.0%
country (3샤드)    69.9%  19.8%  10.3%  (kr us jp)
가입 6개월 단위    25.9%  25.7%  23.8%  24.5%
```

국가로 나누면 한국 샤드 하나가 70%를 떠안는다. 샤드를 셋 둔 효과가 거의 없다. 키가 가질 수 있는 값의 종류가 적거나 한쪽으로 쏠려 있으면 이렇게 된다.

가입 시기로 나눈 셋째 줄은 저장량만 보면 고르게 나뉘었다. 그런데 쓰기를 생각하면 문제가 보인다. 오늘 가입한 사람과 최근 가입자들이 쏟아 내는 쓰기는 모두 가장 최근 구간을 맡은 샤드로 간다. 나머지 세 샤드는 거의 놀고 한 샤드만 바쁘다. 날짜나 증가하는 번호처럼 값이 한 방향으로만 커지는 키로 구간을 나누면 늘 이 모양이 된다.

둘째, 자주 하는 질문에 샤딩 키가 들어 있어야 한다. 앞에서 본 것처럼 키가 있으면 한 샤드에서 끝나고, 없으면 모든 샤드에 물어야 한다. 맛집 앱에서 가장 많은 질문이 "내 리뷰", "내 피드"라면 `user_id`가 좋은 키다. 가장 많은 질문이 "이 식당의 리뷰"라면 `restaurant_id`가 더 맞을 수 있다. 정답은 서비스의 질문 모양이 정한다.

그래서 샤딩 키를 고르기 전에는 지금 쿼리 로그에서 어떤 조건으로 묻는 쿼리가 가장 많은지, 후보 키로 나눴을 때 데이터가 얼마나 고른지를 실제 데이터로 재 본다. 그 방법은 [샤딩](/posts/db-sharding)에 SQL로 정리되어 있다.

## 샤딩 키가 없는 질문은 모든 샤드에 묻는다

리뷰를 작성자 기준으로 나눴으니, 식당 상세 화면의 "이 식당의 최신 리뷰 3개"는 어느 샤드에 있는지 알 수 없다. 네 샤드에 모두 묻고 결과를 모아 다시 정렬해야 한다. 이렇게 흩어 묻고 모아 합치는 방식을 scatter-gather라고 부른다.

```js
// shards.mjs 일부: 식당 42의 최신 리뷰 3개
const parts = await Promise.all(shards.map((db) =>
  db.query("SELECT id, user_id, author_nickname, rating FROM reviews WHERE restaurant_id = 42 ORDER BY id DESC LIMIT 3")));
const merged = parts.flatMap((p) => p.rows).sort((a, b) => b.id - a.id).slice(0, 3);
```

```text
shard 0 returned 3 rows: ids 39337,37977,37205
shard 1 returned 3 rows: ids 37010,35963,32886
shard 2 returned 3 rows: ids 39388,33153,31366
shard 3 returned 3 rows: ids 37259,36842,36824
merged top 3: 39388(user3618) 39337(user2896) 37977(user8732)
```

샤드마다 자기 안에서 최신 3개를 보냈고, 앱이 12개를 모아 다시 정렬해 3개를 골랐다. 최종 결과의 1등은 shard 2에서, 2등과 3등은 shard 0에서 왔다. 한 샤드만 봤다면 틀린 답이 나왔을 것이다.

샤드가 네 개일 때는 견딜 만하다. 하지만 샤드가 64개가 되면 식당 화면 하나 열 때마다 64개 DB가 모두 일하고, 그중 가장 느린 하나가 응답 시간을 정한다. 그래서 자주 하는 질문이 샤딩 키와 다르면 그 질문을 위한 사본을 따로 만든다. 예를 들어 리뷰를 쓸 때 [⑦에서 만든 큐](/posts/sd-queue-logging-automation)로 이벤트를 보내, `restaurant_id`로 나눈 "식당별 리뷰 목록" 저장소에도 한 벌 더 넣어 두는 식이다. 쓰기는 두 번 하고 두 사본 사이에 잠깐의 차이가 생기지만, 읽기는 한 곳에서 끝난다. 쓰기 모델과 읽기 모델을 따로 두는 이 생각은 [CQRS](/posts/cqrs)에서 이어진다.

## 샤드를 넘는 조인 대신 반정규화

샤딩 전에는 리뷰 목록에 작성자 닉네임을 붙이려면 `reviews`와 `users`를 조인하면 됐다. 같은 DB 안에 있으니까. 샤딩 뒤에는 리뷰 작성자가 다른 샤드에 있을 수 있다. 위 실험에서는 리뷰를 작성자와 같은 샤드에 뒀지만, 식당별 목록처럼 여러 사람의 리뷰를 한꺼번에 보여 줄 때는 작성자들이 네 샤드에 흩어져 있다. SQL의 조인은 DB 한 대 안에서만 된다.

흔한 해결은 조인할 값을 미리 복사해 두는 것이다. 위 테이블의 `author_nickname`이 그 예다. 리뷰를 쓸 때 작성자 닉네임을 리뷰 행에 같이 저장해 두면, 리뷰만 읽어도 닉네임을 보여 줄 수 있다. 정규화된 설계에서 일부러 중복을 들이는 것이라 반정규화(denormalization)라고 부른다.

여러 샤드에 걸친 트랜잭션도 같은 이유로 어렵다. 샤드 0의 사용자가 샤드 2의 사용자에게 포인트를 보내는 일은 DB 하나의 트랜잭션으로 묶이지 않는다. 그래서 한 번의 작업이 한 샤드 안에서 끝나도록 샤딩 키를 고르는 것이 먼저고, 그래도 넘어가야 하면 [2단계 커밋](/posts/distributed-transactions-2pc)이나 [사가 패턴](/posts/saga-pattern)을 쓴다.

## 샤드를 늘리는 일: 리샤딩

리뷰가 계속 늘어 샤드 네 개도 부족해졌다. 다섯 개로 늘리면 끝일까? `user_id % 4`를 `user_id % 5`로 바꾸는 순간, 나머지가 바뀌는 사용자들은 모두 다른 샤드로 옮겨야 한다. 샤드 수를 바꿔 데이터를 다시 나누는 일을 리샤딩(resharding)이라고 한다. 얼마나 옮겨야 하는지 계산해 봤다.

```text
== 2. 샤드 수를 바꾸면 옮겨야 하는 키 (키 1..1,000,000)
 4 -> 5  shards: 80.0% moved
 4 -> 8  shards: 50.0% moved
 4 -> 3  shards: 75.0% moved
10 -> 11 shards: 90.9% moved
```

샤드 하나를 더했을 뿐인데 데이터의 80%가 이사를 가야 한다. 10개에서 11개로 늘리면 90.9%다. 이사하는 동안에도 서비스는 그 데이터를 읽고 써야 하니, 대부분을 옮기는 리샤딩은 몇 주짜리 작업이 된다. 직접 계산해 보자. 1부터 `totalKeys`까지의 키 중 나머지가 바뀌는 비율(%)을 소수 첫째 자리까지 돌려주는 함수다.

<CodePlayground
  caption="나머지로 나눌 때 샤드 수를 바꾸면 몇 %가 옮겨 가나"
  functionName="movedPercent"
  initialCode={`function movedPercent(totalKeys, fromShards, toShards) {
  // 키 1..totalKeys 중 (k % fromShards)와 (k % toShards)가 다른 비율(%)
  // 소수 첫째 자리까지 숫자로 돌려준다
  return 0;
}`}
  solution={`function movedPercent(totalKeys, fromShards, toShards) {
  let moved = 0;
  for (let k = 1; k <= totalKeys; k++) {
    if (k % fromShards !== k % toShards) moved++;
  }
  return Number(((moved / totalKeys) * 100).toFixed(1));
}`}
  tests={[
    { args: [100000, 4, 5], expected: 80, label: "4 → 5" },
    { args: [100000, 4, 8], expected: 50, label: "4 → 8 (두 배)" },
    { args: [100000, 2, 4], expected: 50, label: "2 → 4 (두 배)" },
    { args: [100000, 10, 11], expected: 90.9, label: "10 → 11" },
    { args: [100000, 4, 3], expected: 75, label: "4 → 3 (줄이기)" },
    { args: [100000, 4, 4], expected: 0, label: "그대로" },
  ]}
/>

결과를 보면 두 배로 늘릴 때가 가장 적게(50%) 옮긴다. 그래도 절반이다. 이 문제를 줄이는 방법이 두 가지 있다.

하나는 [일관된 해싱](/posts/consistent-hashing)이다. 키와 서버를 같은 원 위에 놓고, 키는 시계 방향으로 가장 가까운 서버에 둔다. 서버가 하나 늘면 그 서버 바로 앞 구간의 키만 옮겨 가서, 5개로 늘릴 때 옮기는 양이 대략 5분의 1로 줄어든다.

다른 하나는 처음부터 논리 샤드를 많이 만들어 두는 것이다. 예를 들어 `user_id % 16`으로 논리 샤드 16개를 만들고, 처음에는 서버 두 대에 8개씩 나눠 둔다. 서버를 늘릴 때는 키를 다시 계산하지 않고 논리 샤드 단위로 통째로 옮긴다. 어느 논리 샤드가 어느 서버에 있는지는 작은 표(디렉터리)에 적어 둔다.

이 방식은 앱 쪽 계산이 단순하고, 옮기는 단위가 커서 이사 계획을 세우기 쉽다. 대신 디렉터리를 모든 라우터가 같은 내용으로 알아야 하고, 처음 정한 논리 샤드 수가 서버 수의 상한이 된다. Redis Cluster가 키를 16,384개의 해시 슬롯으로 나눠 이렇게 운영한다([Redis Cluster](/posts/redis-cluster)).

## 유명한 식당 하나가 샤드 하나를 태운다

키를 잘 골라 데이터를 고르게 나눠도 트래픽은 고르지 않을 수 있다. 식당 리뷰를 `restaurant_id % 4`로 나눴는데, 7번 식당이 TV에 나와 리뷰 읽기의 40%가 그 식당으로 몰렸다고 하자. 읽기 1만 건이 샤드에 어떻게 퍼지는지 계산했다.

```text
== 3. 식당 리뷰 읽기 10,000건, 식당 7번이 방송에 나와 40%를 차지 (restaurant_id % 4)
reads per shard   15.3%  13.9%  15.2%  55.6%
```

7번 식당이 있는 shard 3이 절반 넘게 받는다. 7번 식당의 데이터는 한 행 묶음이라 더 쪼갤 수도 없다. 이런 문제를 유명인 문제(celebrity problem) 또는 핫스팟이라고 부른다. SNS에서 팔로워가 수천만인 계정 하나가 샤드 하나를 태우는 것과 같은 모양이다.

## 샤드마다 번호가 겹치지 않게

샤딩 전에는 리뷰 번호를 DB의 자동 증가 열이 1, 2, 3 하고 매겨 줬다. 샤드가 네 개면 네 DB가 각자 1부터 센다. shard 0의 리뷰 1번과 shard 2의 리뷰 1번이 생긴다. 리뷰 번호로 링크를 걸거나 다른 테이블에서 참조하면 어느 쪽인지 알 수 없다.

그래서 샤딩된 시스템은 DB에 맡기지 않고 전체에서 겹치지 않는 번호를 따로 만든다. 시간 순서를 담은 UUID v7이나, 시각과 서버 번호와 순번을 64비트에 나눠 담는 Snowflake 같은 방식이다. 위 실험에서 리뷰 번호를 미리 정해 넣은 것도 이 문제를 피하려고서다. 각 방식의 장단점은 [고유 ID 생성기](/posts/sd-unique-id-generator)에서 설계해 본다.

## 샤딩 전에 먼저 해 볼 것

여기까지 오면 샤딩이 얼마나 많은 것을 바꾸는지 보인다. 조인과 트랜잭션이 어려워지고, 키 없는 질문은 비싸지고, 리샤딩과 번호 매기기를 따로 설계해야 한다. 그래서 샤딩은 다른 방법을 다 쓴 뒤에 꺼내는 카드다. 그 전에 할 수 있는 것들이 있다.

- 느린 쿼리와 인덱스를 고친다. 쓰기가 무거운 원인이 쓸데없는 인덱스나 비효율적인 갱신인 경우가 많다.
- 서버를 한 단계 키운다. 여전히 가장 싸고 빠른 방법일 수 있다.
- 읽기는 복제본과 캐시로 뺀다. 이 장의 ④, ⑤가 한 일이다.
- 오래된 데이터를 다른 저장소로 옮기거나, 한 DB 안에서 테이블을 기간별로 나눈다. 같은 서버 안에서 테이블을 나누는 것은 [파티셔닝](/posts/db-partitioning)이라 부르고, 샤딩보다 훨씬 덜 아프다.
- 기능별로 DB를 나눈다. 리뷰 DB와 결제 DB를 따로 두면 각자 한 대씩으로 버틸 수 있다.

그래도 주 DB의 쓰기량이나 데이터 크기가 한 대의 한계에 계속 가까워지고, 그 추세가 몇 달 안에 넘을 것으로 보이면 샤딩을 준비한다. 준비는 샤딩 키 후보를 지금 데이터로 재 보는 데서 시작한다. 처음부터 샤딩된 저장소를 쓰고 싶다면 샤딩을 대신 해 주는 분산 SQL이나 키-값 저장소도 선택지다([DB 종류 한눈에 보기](/posts/db-types-overview)).

## 한 대에서 샤드까지, 다음은 숫자

이 글로 "서버 한 대에서 수백만 사용자까지" 장이 끝났다. 한 대로 시작해 DB를 떼고, 웹 계층을 무상태로 늘리고, 읽기를 복제본과 캐시와 CDN으로 나누고, 데이터 센터를 둘로 늘리고, 무거운 일을 큐로 빼고, 마지막으로 쓰기를 샤드로 나눴다. 각 단계는 앞 단계에서 터진 문제 하나에 대한 답이었다.

다음 글 [⑨ 꼭 알아 둘 숫자들](/posts/sd-latency-numbers)부터는 설계의 근거가 되는 숫자를 다룬다. 메모리와 디스크와 네트워크가 대략 얼마나 빠른지 알아야 "캐시를 둘까", "샤드를 몇 개로 할까"에 숫자로 답할 수 있다. 샤딩을 더 깊게 보려면 [샤딩](/posts/db-sharding)과 [일관된 해싱](/posts/consistent-hashing)으로 가면 된다.

샤딩을 한 줄로 줄이면 이렇다. 데이터를 겹치지 않게 나눠 쓰기와 용량을 나누는 대신, 키 하나로 답할 수 없는 모든 질문이 비싸진다. 그래서 샤딩 키는 가장 자주 하는 질문과 고른 분포를 기준으로 고르고, 나머지 질문은 사본과 반정규화로 따로 준비한다.

## 면접에서 나올 만한 질문

### 복제와 샤딩은 무엇이 다른가요?

복제는 같은 데이터를 여러 서버에 두는 것이고, 샤딩은 데이터를 겹치지 않게 나눠 두는 것이다. 복제는 읽기와 가용성을 늘리지만 모든 복제본이 모든 쓰기를 받으므로 쓰기와 용량은 그대로다. 샤딩은 쓰기와 용량을 나눈다. 실제로는 샤드마다 복제본을 붙여 둘을 함께 쓴다.

### 샤딩 키는 어떻게 고르나요?

두 가지를 본다. 데이터와 트래픽이 샤드에 고르게 퍼지는지, 그리고 가장 자주 하는 질문에 그 키가 들어 있어 한 샤드에서 끝나는지다. 국가처럼 값의 종류가 적거나 쏠린 키, 날짜나 증가 번호처럼 새 쓰기가 한쪽 끝으로만 가는 키는 피한다. 후보 키는 지금 데이터와 쿼리 로그로 분포를 재 보고 정한다.

### 샤딩 키가 없는 조건으로 조회해야 하면 어떻게 하나요?

모든 샤드에 물어 결과를 합치는 scatter-gather를 쓴다. 샤드가 적고 드문 질문이라면 괜찮지만, 샤드가 많아지면 모든 샤드가 일하고 가장 느린 샤드가 응답 시간을 정한다. 자주 하는 질문이라면 그 질문의 키로 나눈 사본을 큐나 변경 이벤트로 따로 만들어 둔다.

### 샤드를 늘려야 할 때 어떻게 하나요?

나머지 연산으로 나눴다면 샤드 수를 바꾸는 순간 대부분의 키가 옮겨 가야 한다. 4개에서 5개로 늘리면 80%다. 그래서 일관된 해싱으로 옮기는 양을 줄이거나, 처음부터 논리 샤드를 많이 만들어 두고 디렉터리로 서버에 배치해 통째로 옮긴다. 옮기는 동안에는 두 곳에 함께 쓰고 따라잡은 뒤 읽기를 넘기는 식으로 무중단을 유지한다.

### 특정 키 하나에 트래픽이 몰리면 어떻게 하나요?

몰리는 것이 읽기라면 먼저 캐시로 막는다. 그래도 부족하면 그 키를 전용 샤드로 빼고 복제본을 붙여 읽기를 나눈다. 쓰기까지 몰리면 키 뒤에 번호를 붙여 여러 샤드에 나눠 쓰고 읽을 때 합친다. 어떤 키가 뜰지 미리 알기 어려우니 샤드별 부하와 키별 요청 수를 지표로 지켜본다.

### 샤딩하면 조인과 트랜잭션은 어떻게 하나요?

샤드를 넘는 조인은 DB가 해 주지 않으므로, 자주 같이 읽는 값은 반정규화로 미리 복사해 둔다. 원본이 바뀌면 복사본을 큐로 천천히 갱신하고 잠깐의 차이를 받아들인다. 트랜잭션은 한 작업이 한 샤드 안에서 끝나도록 키를 고르는 것이 먼저고, 넘어가야 하면 2단계 커밋이나 사가 패턴을 쓴다.

### 샤딩은 언제 하나요?

다른 방법을 다 쓴 뒤에 한다. 쿼리와 인덱스 개선, 서버 키우기, 복제본과 캐시로 읽기 빼기, 파티셔닝과 오래된 데이터 이전, 기능별 DB 분리를 먼저 한다. 그래도 쓰기량이나 데이터 크기가 한 대의 한계에 가까워지고 그 추세가 이어질 때 샤딩 키를 재 보며 준비한다.
