주문 서비스를 새 서버로 옮기고 옛 서버를 껐다. 대부분의 호출자는 몇 초 안에 새 주소로 갔는데, 자바로 짠 정산 배치만 30초 가까이 옛 IP로 연결을 시도하다 실패했다. 레지스트리에도, DNS에도 새 주소가 이미 들어가 있었다. 옛 주소를 들고 있던 건 정산 배치 프로세스 자신이었다.

서비스 디스커버리는 "지금 이 서비스를 어디로 부르면 되나"에 답하는 장치다. 인스턴스가 고정된 서버 몇 대일 때는 설정 파일에 IP를 적으면 됐다. 오토스케일링, 컨테이너 재시작, 배포가 일상이 되면서 주소가 몇 분 단위로 바뀌고, 그 목록을 누군가 계속 맞춰 줘야 한다. 이 글은 그 목록을 누가 쓰고, 누가 읽고, 어디서 낡아지는지를 etcd와 Consul로 직접 돌려 보며 따라간다.

실습은 Ubuntu 24.04 컨테이너에서 etcd 3.4.30, Consul 1.19.2(개발 모드 에이전트), OpenJDK 21로 했다. 쿠버네티스 Service와 EndpointSlice가 패킷을 어떻게 나누는지는 [Service 타입 글](/posts/k8s-service-types)에, 클러스터 DNS 서버 자체는 [CoreDNS 글](/posts/k8s-coredns)에, DNS의 TTL과 캐시 일반은 [DNS 글](/posts/dns#캐시와-ttl이-만드는-시차)에 있다. 여기서는 그 위의 설계, 즉 등록과 조회와 낡음을 본다.

## 목록을 누가 들고 있나

서비스 디스커버리에는 세 역할이 있다. 인스턴스 목록을 저장하는 레지스트리, 목록에 자기를 올리는 등록, 목록을 읽어 호출할 곳을 고르는 조회다. 레지스트리로는 etcd, Consul, ZooKeeper, 넷플릭스의 Eureka 같은 것을 쓰고, 쿠버네티스에서는 API 서버(뒤에는 etcd)의 EndpointSlice가 그 자리에 있다.

조회 쪽에는 두 가지 방식이 있다. 호출하는 쪽이 레지스트리를 직접 읽고 인스턴스를 골라 바로 부르면 클라이언트 측 디스커버리다. 아래 그림에서 다음을 누르면 그 흐름을 볼 수 있다.

## 등록은 누가 하나

목록에 올리는 방법도 둘이다. 인스턴스가 뜰 때 스스로 레지스트리에 등록하고 꺼질 때 지우는 자기 등록(self-registration), 그리고 플랫폼이 인스턴스를 지켜보다 대신 올려 주는 제3자 등록이다. 쿠버네티스는 제3자 등록이다. 앱은 아무것도 하지 않는다.

자기 등록은 단순하지만, 인스턴스가 깔끔하게 내려가지 못하면(OOM으로 죽거나, 노드가 통째로 사라지거나) 지우는 코드가 실행되지 않는다. 그래서 어떤 방식이든 "살아 있다는 증거가 끊기면 빼는" 장치가 따로 필요하다. 그 장치가 임대(lease)와 헬스 체크다.

## 살아 있는 동안만 남는 등록

etcd는 키를 임대에 묶을 수 있다. 임대는 TTL이 있고, 클라이언트가 그 안에 keepalive를 보내면 연장된다. keepalive가 끊기면 TTL이 지나 임대가 만료되고, 묶인 키는 함께 지워진다. 같은 원리로 분산 락의 주인을 정하는 이야기는 [분산 락 글](/posts/distributed-lock)에 있다. 여기서는 등록에 쓴다.

실제로 돌린 명령과 출력이다. orders-1만 keepalive를 15초 동안 보내게 했다.

```bash
# 레지스트리 주소 (실습용 etcd)
export ETCDCTL_API=3 E="etcdctl --endpoints=127.0.0.1:23791"

# 다른 터미널: billing 역할로 목록 변화를 구독한다
$E watch --prefix /services/orders/

# TTL 5초 임대를 두 개 받는다
L1=$($E lease grant 5 | awk '{print $2}'); L2=$($E lease grant 5 | awk '{print $2}')

# 각 인스턴스를 임대에 묶어 등록한다
$E put /services/orders/10.0.1.11:8080 '{"addr":"10.0.1.11:8080","zone":"a","version":"1.4.2"}' --lease=$L1
$E put /services/orders/10.0.1.12:8080 '{"addr":"10.0.1.12:8080","zone":"b","version":"1.4.2"}' --lease=$L2

# orders-1만 계속 갱신한다 (orders-2는 죽은 셈)
$E lease keep-alive $L1 &

# 7초 뒤 목록과 orders-2 임대 상태
sleep 7; $E get --prefix /services/orders/ --keys-only; $E lease timetolive $L2
```

```text
/services/orders/10.0.1.11:8080

lease 390da159b688da08 already expired
```

구독하던 쪽에는 이벤트가 이렇게 왔다. keepalive를 15초 뒤 멈추자 orders-1도 5초 뒤 사라졌다.

```text
PUT
/services/orders/10.0.1.11:8080
{"addr":"10.0.1.11:8080","zone":"a","version":"1.4.2"}
PUT
/services/orders/10.0.1.12:8080
{"addr":"10.0.1.12:8080","zone":"b","version":"1.4.2"}
DELETE
/services/orders/10.0.1.12:8080

DELETE
/services/orders/10.0.1.11:8080
```

TTL을 고르는 건 트레이드오프다. 짧으면 죽은 인스턴스가 빨리 빠지지만, 레지스트리와 잠깐 네트워크가 끊기거나 GC로 프로세스가 몇 초 멈추기만 해도 멀쩡한 인스턴스가 빠졌다 들어온다. 길면 안정적이지만 그만큼 죽은 주소로 요청이 간다. 정상 종료할 때는 TTL을 기다리지 말고 `lease revoke`로 직접 지운다. 그래야 배포 때마다 TTL만큼의 실패가 생기지 않는다.

## 살아 있다는 것과 일할 수 있다는 것

임대는 "프로세스가 살아 있다"만 알려 준다. 프로세스는 살아 있는데 DB 연결이 끊겨 모든 요청에 500을 주는 인스턴스도 keepalive는 잘 보낸다. 그래서 Consul은 레지스트리가 직접 인스턴스에 물어보는 헬스 체크를 붙인다. 각 노드의 Consul 에이전트가 같은 노드의 서비스를 주기적으로 검사하고, 실패하면 그 인스턴스를 조회 결과에서 뺀다.

```hcl
service {
  name = "web"
  id   = "web-1"
  address = "10.0.1.11"
  port = 9101
  check {
    http     = "http://127.0.0.1:9101/health"
    interval = "2s"
    timeout  = "1s"
    deregister_critical_service_after = "1m"
  }
}
```

에이전트는 같은 호스트에 있으니 로컬 주소로 검사하고, 바깥에 알리는 주소는 `address`에 따로 적는다. `deregister_critical_service_after`는 실패 상태가 1분 넘게 이어지면 등록 자체를 지운다. 자기 등록의 "지우는 코드가 안 돌았다" 문제를 레지스트리 쪽에서 막는 설정이다.

두 인스턴스를 등록하고 Consul의 DNS 인터페이스(실습에서는 18600번 포트)로 물었다. A 레코드에는 포트가 없으니 포트까지 필요하면 SRV 레코드를 묻는다.

```bash
# web-2를 일부러 아프게 만든다 (/health가 503을 돌려준다)
curl -s 127.0.0.1:9102/sick

# 0.5초마다 A 레코드 개수를 센다
for i in $(seq 1 3); do sleep 0.5; echo "$(date +%T.%N | cut -c1-12) A records=$(dig @127.0.0.1 -p 18600 web.service.consul +short | wc -l)"; done

# 검사 결과
curl -s http://127.0.0.1:18500/v1/health/checks/web
```

```text
now sick
14:29:35.853 A records=1
14:29:36.385 A records=1
14:29:36.918 A records=1
web-1 passing 'HTTP GET http://127.0.0.1:9101/health: 200 OK Output: ok\n'
web-2 critical 'HTTP GET http://127.0.0.1:9102/health: 503 Service Unavailable Output: db down\n'
```

검사 결과는 JSON을 한 줄씩 줄여서 보였다. 2초 주기 검사가 곧바로 돌아서 0.5초 안에 빠졌지만, 검사 직후에 아팠다면 최대 2초(주기)에 응답 대기 1초까지 늦을 수 있다. Consul의 검사는 한 번 실패하면 바로 critical로 바뀐다. 한두 번의 일시 실패로 빠지는 게 싫으면 `failures_before_critical`을 올린다.

SRV 응답의 한 줄을 조각으로 나누면 이렇다.

DNS 대신 HTTP API를 쓰면 바뀔 때까지 기다리는 블로킹 쿼리가 된다. 응답 헤더의 `X-Consul-Index`를 다음 요청에 `index=`로 넘기면, 목록이 바뀌거나 `wait`가 끝날 때까지 응답을 붙들고 있다. 폴링 없이 변경을 바로 받는다. 실습에서 index 25로 기다리는 동안 web-2를 고쳤더니, 4초 뒤 `["web-1", "web-2"]`와 `X-Consul-Index: 27`이 돌아왔다.

```bash
# 마지막으로 본 index부터 최대 30초 기다린다
curl -s -D - "http://127.0.0.1:18500/v1/health/service/web?passing&index=25&wait=30s"
```

## DNS로 찾으면 캐시가 끼어든다

DNS는 모든 언어와 도구가 이미 쓸 줄 안다는 큰 장점이 있다. 쿠버네티스의 `orders.shop.svc.cluster.local`, Consul의 `web.service.consul`이 그렇다. 문제는 DNS가 변경을 밀어 주지 못한다는 것이다. 답을 받은 쪽이 TTL만큼, 또는 자기 마음대로 들고 있다.

처음 장면의 정산 배치가 이 경우다. JVM은 OS와 별개로 `InetAddress` 안에 자기 캐시를 둔다. JDK 21의 `java.security` 주석에 이렇게 적혀 있다. 보안 관리자가 없으면 성공한 조회를 30초 캐시하고(구현 기본값), 보안 관리자가 있으면 영원히 캐시한다. 실패한 조회는 10초 캐시한다. DNS 레코드의 TTL이 0이어도 상관없다.

직접 확인했다. 네트워크 네임스페이스에 전용 hosts 파일을 두고 `orders.internal`을 1초마다 조회하는 자바 프로그램을 돌리면서, 4초쯤 뒤 주소를 바꿨다.

```bash
# 이 네임스페이스에서만 보이는 hosts 파일
sudo ip netns add n5d
printf "127.0.0.1 localhost\n10.0.1.11 orders.internal\n" | sudo tee /etc/netns/n5d/hosts

# 1초마다 InetAddress.getByName("orders.internal")을 찍는 프로그램
sudo ip netns exec n5d java -cp . Resolve

# (4초 뒤 다른 터미널) 같은 파일을 덮어써서 주소를 바꾼다
printf "127.0.0.1 localhost\n10.0.1.21 orders.internal\n" | sudo tee /etc/netns/n5d/hosts
```

```text
14:30:09 orders.internal -> 10.0.1.11
14:30:12 orders.internal -> 10.0.1.11
14:30:13 orders.internal -> 10.0.1.11
14:30:14 orders.internal -> 10.0.1.11
14:30:38 orders.internal -> 10.0.1.11
14:30:39 orders.internal -> 10.0.1.21
```

주소는 14:30:13에 바꿨다. 그런데 처음 조회한 14:30:09에서 정확히 30초 뒤에야 새 주소가 나왔다. 가운데 줄은 줄였다. 같은 프로그램에 `networkaddress.cache.ttl=5`를 넣은 보안 속성 파일을 주면 바꾼 지 1초 만에 따라온다(이번에는 14:31:33에 바꿨다).

```bash
# JVM DNS 캐시를 5초로 줄인다 (보안 속성 파일로 넘김)
echo 'networkaddress.cache.ttl=5' > ttl5.security
sudo ip netns exec n5d java -Djava.security.properties=ttl5.security -cp . Resolve
```

```text

14:31:32 orders.internal -> 10.0.1.11
14:31:33 orders.internal -> 10.0.1.11
14:31:34 orders.internal -> 10.0.1.21
```

연결 풀은 DNS를 다시 보지 않는다. HTTP keep-alive 연결이나 DB 커넥션 풀은 한 번 연결하면 상대 주소가 고정이다. 옛 서버가 죽지 않고 살아 있으면(드레이닝 중이면) 계속 옛 서버로 간다. 그래서 커넥션 풀에는 최대 수명(HikariCP의 `maxLifetime`, HTTP 클라이언트의 연결 TTL)을 두어 가끔 새로 열게 한다.

언어마다 캐시 동작이 다르다. Node.js는 자체 DNS 캐시가 없어서 `http.request`마다 `getaddrinfo`를 부른다. 변경은 빨리 따라오지만 요청마다 조회 비용이 붙고, 조회가 libuv 스레드 풀(기본 4개)을 차지한다. Go는 기본 리졸버가 캐시하지 않는다. 어느 경우든 OS 쪽에 systemd-resolved나 nscd 같은 캐시가 있으면 그 겹이 또 생긴다.

DNS 기반 디스커버리의 다른 약점도 있다. DNS 응답에는 헬스 상태나 가중치, 영역 정보를 싣기 어렵고(SRV의 가중치 정도), 클라이언트가 A 레코드 여러 개 중 첫 번째만 쓰면 부하가 한쪽으로 몰린다. UDP 응답 크기 한계 때문에 인스턴스가 많으면 일부만 오거나 TCP로 다시 물어야 한다. 그래서 인스턴스 목록 전체가 필요한 클라이언트 측 방식은 DNS보다 레지스트리의 watch API를 쓰는 편이 낫다.

## 목록이 틀렸을 때 생기는 증상

현장에서 디스커버리 문제는 "가끔 실패"로 나타난다. 증상별로 어디를 보는지 정리한다.

배포할 때마다 몇 초씩 실패가 난다. 내려가는 인스턴스가 목록에서 빠지기 전에 프로세스가 먼저 끝난 것이다. 쿠버네티스라면 Pod가 Terminating이 된 뒤 EndpointSlice에서 빠지고 각 노드의 kube-proxy가 규칙을 고치기까지 시간이 걸린다. `preStop`에 몇 초 sleep을 두어 목록에서 빠질 시간을 벌고, 그다음에 종료한다. 순서는 [Pod 일생 글](/posts/k8s-pod-lifecycle)에, 로드 밸런서 쪽 드레이닝은 [로드 밸런서 글](/posts/load-balancer-basics#서버를-뺄-때는-드레이닝부터)에 있다.

특정 클라이언트만 옛 주소로 간다. 그 클라이언트 프로세스 안의 캐시를 의심한다. JVM이면 `networkaddress.cache.ttl`, 연결 풀의 최대 수명을 확인한다. 같은 노드의 다른 프로세스에서 `getent hosts orders.internal`이나 `dig`로 새 주소가 나오면 레지스트리와 DNS는 정상이고 문제는 프로세스 안이다.

```bash
# OS 리졸버가 보는 주소 (nsswitch를 따라 hosts 파일, DNS 순서로 찾는다)
getent hosts orders.shop.svc.cluster.local
# DNS 서버가 주는 답과 TTL
dig orders.shop.svc.cluster.local +noall +answer
# 쿠버네티스 레지스트리가 아는 엔드포인트 (ready 여부 포함)
kubectl get endpointslices -n shop -l kubernetes.io/service-name=orders -o wide
```

인스턴스가 목록에 있다 없다를 반복한다(flapping). TTL이나 헬스 체크 기준이 너무 빡빡하다. GC 정지나 순간 부하로 한 번 늦은 응답에 빠졌다 들어오기를 반복하면, 오히려 남은 인스턴스에 부하가 몰린다. 빼는 기준(연속 실패 횟수)과 넣는 기준(연속 성공 횟수)을 다르게 둔다.

레지스트리 자체가 죽는다. etcd나 Consul 서버가 과반을 잃으면 새 등록과 변경이 멈춘다. 대부분의 클라이언트 라이브러리는 마지막으로 받은 목록을 들고 버티는데, 이 동작을 확인해 두지 않으면 레지스트리 장애가 곧바로 전체 장애가 된다. 레지스트리를 3대나 5대로 두는 이유이고, 레지스트리에 요청마다 묻지 않고 구독해서 메모리에 들고 있어야 하는 이유다.

## 어떤 방식을 고를까

쿠버네티스 안에서만 통신한다면 Service와 DNS로 시작하는 게 맞다. 이미 제3자 등록, 헬스 체크(readiness), 서버 측 분산이 다 있다. gRPC처럼 연결 하나를 오래 쓰는 프로토콜은 ClusterIP의 연결 단위 분산으로는 한쪽에 몰리니, headless Service로 Pod IP 목록을 받아 클라이언트 측에서 나누거나 메시를 쓴다.

VM과 컨테이너가 섞여 있거나 여러 클러스터·데이터센터를 묶어야 한다면 Consul 같은 독립 레지스트리가 맞다. 헬스 체크와 DNS·HTTP 인터페이스를 함께 주고, 쿠버네티스 Service와 동기화할 수도 있다. etcd는 레지스트리로 쓸 수 있지만 헬스 체크가 없어 임대와 앱의 keepalive에 의존한다. 쿠버네티스가 이미 쓰는 etcd를 앱 레지스트리로 같이 쓰는 건 피한다. 클러스터 전체의 상태가 거기 있다.

어느 방식이든 같은 질문을 한다. 인스턴스가 죽은 순간부터 마지막 호출자가 그 주소를 버릴 때까지 몇 초인가. 검사 주기, 임대 TTL, DNS TTL, 프로세스 캐시, 연결 풀 수명을 다 더한 값이다. 그 시간 동안의 요청은 재시도나 다른 인스턴스로의 우회가 받아내야 한다.

## 면접에서 나올 만한 질문

### 서비스 디스커버리는 왜 필요한가요?

인스턴스 주소가 오토스케일링, 재시작, 배포로 계속 바뀌기 때문이다. 설정 파일에 IP를 적어 두면 바뀔 때마다 사람이 고쳐야 한다. 디스커버리는 인스턴스가 스스로 또는 플랫폼이 대신 레지스트리에 등록하고, 호출자는 이름으로 현재 주소를 찾게 해 준다.

### 클라이언트 측 디스커버리와 서버 측 디스커버리는 어떻게 다른가요?

누가 인스턴스를 고르느냐의 차이다. 클라이언트 측은 호출자가 레지스트리에서 목록을 받아 직접 골라서 중간 홉이 없고 정책이 자유롭지만, 언어마다 라이브러리가 필요하다. 서버 측은 호출자가 VIP나 로드 밸런서 이름 하나만 알고 중간이 고르니 호출자는 단순하지만, 홉과 장애 지점이 하나 는다. 쿠버네티스 ClusterIP는 서버 측, 메시는 앱에는 서버 측이면서 프록시가 클라이언트 측으로 고르는 혼합이다.

### 인스턴스가 정상 종료하지 못하고 죽으면 레지스트리에서 어떻게 빠지나요?

살아 있다는 신호가 끊기면 빼는 장치가 따로 있어야 한다. etcd는 TTL 임대에 키를 묶어 keepalive가 끊기면 TTL 뒤에 키가 지워지고, Consul은 에이전트의 헬스 체크가 실패하면 조회 결과에서 빼며 `deregister_critical_service_after`로 등록 자체를 지운다. 그 TTL이나 검사 주기만큼은 죽은 주소가 목록에 남는다는 점을 감안해야 한다.

### 프로세스가 살아 있으면 헬스 체크는 필요 없나요?

필요하다. 임대나 keepalive는 프로세스가 살아 있다는 것만 알려 주고, DB 연결이 끊겨 모든 요청을 실패시키는 인스턴스도 keepalive는 잘 보낸다. 실제 요청을 처리할 수 있는지를 보는 헬스 체크(쿠버네티스의 readiness)가 있어야 그런 인스턴스를 뺄 수 있다. 다만 공용 의존성까지 검사하면 그 의존성 장애에 전체가 빠지니 검사 범위를 조심한다.

### DNS 기반 디스커버리의 문제점은 무엇인가요?

변경을 밀어 주지 못하고 받은 쪽이 캐시한다는 점이다. 레코드 TTL이 0이어도 JVM은 기본 30초(보안 관리자가 있으면 영원히) 캐시하고, 연결 풀은 아예 DNS를 다시 보지 않는다. 또 응답에 헬스나 가중치 정보를 싣기 어렵고, 클라이언트가 첫 번째 레코드만 쓰면 부하가 쏠린다. 그래서 캐시 TTL과 연결 수명을 짧게 맞추거나, 목록 전체가 필요하면 레지스트리 watch API를 쓴다.

### 서버를 옮긴 뒤 한 서비스만 30초 동안 옛 IP로 갑니다. 어디를 보나요?

그 프로세스 안의 캐시를 먼저 본다. 같은 호스트에서 `getent hosts`나 `dig`로 새 주소가 나오면 레지스트리와 DNS는 정상이다. 자바라면 `networkaddress.cache.ttl` 기본값 30초가 원인일 가능성이 높고, 연결이 계속 열려 있다면 커넥션 풀의 최대 수명도 확인한다. 보안 속성으로 TTL을 줄이고 풀에 `maxLifetime`을 두어 해결한다.

### 레지스트리가 통째로 죽으면 어떻게 되나요?

잘 만든 클라이언트는 마지막으로 받은 목록으로 계속 호출한다. 그래서 레지스트리는 요청마다 묻는 대상이 아니라 구독해서 메모리에 들고 있는 대상이어야 한다. 장애 동안 새 인스턴스 등록과 죽은 인스턴스 제거가 멈추니, 레지스트리는 Raft 과반을 유지하도록 3대나 5대로 둔다.
