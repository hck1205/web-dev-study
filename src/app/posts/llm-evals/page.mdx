고객 지원 챗봇의 답이 너무 길다는 피드백이 와서 시스템 프롬프트에 "답은 짧고 친근하게"라는 줄을 하나 넣었다고 해 보자. 길다고 지적받은 질문 몇 개를 다시 물어보니 확실히 짧아졌다. 배포했다. 사흘 뒤 상담 팀에서 연락이 온다. 환불 문의에 "3~5일 걸려요"라고만 답해서 영업일 기준이라는 말이 빠졌고, 주문 상태를 JSON으로 받던 내부 화면은 앞에 "주문 상태:"라는 말이 붙어 파싱이 깨졌고, 취소 요청에는 취소 도구 대신 조회 도구를 부르고 있었다.

프롬프트를 고친 사람은 고치려던 질문 몇 개만 봤다. 사람이 손으로 확인할 수 있는 건 몇 개뿐이고, 망가진 건 그 밖에 있었다. 코드였다면 단위 테스트가 잡았을 일이다. LLM 기능에도 같은 것이 필요하다. 바꿀 때마다 자동으로 다시 치는 시험, 평가(eval)다.

이 글은 그 시험을 만드는 순서대로 간다. 시험지(평가 세트)를 만들고, 정답이 정해진 문제는 코드로, 정답이 하나가 아닌 문제는 LLM 채점관으로, 채점관이 믿을 만한지는 사람 평가로 확인한다. 그다음 RAG와 에이전트에서 따로 재는 지표, 확신도 보정, CI에 회귀 테스트로 넣는 법, 비결정성 때문에 몇 번 돌려야 하는지, 오프라인 점수와 실제 사용자 지표가 어긋나는 이유를 본다. RAG의 검색 단계만 따로 재는 recall@k·MRR 같은 지표는 [RAG 검색 품질 글](/posts/rag-retrieval-quality)에서 직접 계산해 봤으니 여기서는 생성 쪽을 본다. 프롬프트가 왜 확률적으로 반응하는지는 [LLM 기초 글](/posts/llm-basics-for-developers)에 있다.

## 고친 질문만 보면 망가진 질문은 안 보인다

LLM 기능이 일반 코드보다 회귀에 약한 이유가 몇 가지 있다.

첫째, 변경의 영향 범위를 읽을 수 없다. 함수 하나를 고치면 그 함수를 부르는 곳을 찾으면 된다. 프롬프트 한 줄은 모든 입력에 영향을 준다. "짧게"라는 말은 길어야 할 답까지 줄인다.

둘째, 같은 입력에 답이 매번 다르다. 한 번 물어서 맞았다고 다음에도 맞는다는 보장이 없다. 수동 확인은 운이 좋았던 한 번을 본 것일 수 있다.

셋째, 바뀌는 것이 프롬프트만이 아니다. 공급사가 모델 버전을 올리고, RAG가 붙인 문서가 바뀌고, 도구 설명을 고치고, temperature를 만진다. 모두 답을 바꾼다. 우리 코드는 그대로인데 결과가 달라질 수 있다.

그래서 "바꾸기 전에 시험을 치고, 바꾼 뒤에 같은 시험을 다시 친다"가 기본 습관이 된다. 시험이 있으면 처음 장면의 프롬프트 변경은 배포 전에 걸렸을 것이다.

## 시험지부터 만든다

평가 세트(골든 세트라고도 부른다)는 입력과 "이 답이 좋은지 판단할 기준"의 묶음이다. 기준은 정답 문자열일 수도 있고, 꼭 들어가야 할 사실 목록, 불러야 할 도구 이름, 지켜야 할 형식, 사람이 쓴 모범 답일 수도 있다.

좋은 문제는 대부분 이미 갖고 있다. 실제 사용 로그에서 자주 오는 질문을 뽑고, 버그로 보고됐던 질문을 넣고, 경계에 있는 질문(답하면 안 되는 질문, 모호한 질문, 아주 긴 입력, 다른 언어)을 일부러 섞는다. 사람이 상상으로 만든 질문만으로 채우면 실제 사용자 질문과 분포가 달라서, 점수는 높은데 현장에서는 틀리는 일이 생긴다.

```ts
// eval-set.ts: 문제마다 무엇으로 채점할지를 함께 적는다
type EvalCase = {
  id: string; // 바뀌지 않는 ID. 결과를 버전끼리 비교할 때 쓴다
  category: "refund" | "order" | "safety" | "tone";
  input: string;
  check:
    | { mustInclude: string[] } // 꼭 들어가야 할 말
    | { json: string[] } // JSON으로 파싱되고 이 필드가 있어야 한다
    | { tool: string } // 이 도구를 불러야 한다
    | { mustNotMatch: RegExp } // 나오면 안 되는 패턴
    | { maxChars: number }
    | { rubric: string }; // 정답이 하나가 아닌 문제는 채점 기준표
  source: "prod-log" | "bug-report" | "handmade"; // 어디서 왔는지
};
```

크기는 처음부터 클 필요 없다. 범주마다 수십 개, 합쳐서 50~200개로 시작해도 처음 장면 같은 회귀는 잡힌다. 대신 꾸준히 늘린다. 장애나 버그 제보가 오면 그 입력을 평가 세트에 넣는 걸 버그 수정의 마지막 단계로 정해 두면, 같은 실수가 두 번 배포되지 않는다.

문제를 사람이 다 쓰기 벅차면 LLM으로 늘리는 방법도 있다. 문서를 주고 "이 문서로 답할 수 있는 질문과 답을 만들어라"라고 시키는 식이다. Ragas의 테스트 세트 생성 기능이 이 일을 한다. 빠르게 수백 개를 만들 수 있지만, 만들어진 질문은 문서 문장을 거의 그대로 옮긴 모양이 되기 쉽다. 실제 사용자는 오타를 내고, 문서에 없는 말로 묻고, 두 가지를 한꺼번에 묻는다. 그래서 합성 문제는 사람이 훑어서 이상한 것을 빼고, 실제 로그에서 온 문제와 범주를 나눠 점수를 따로 본다. 합성 문제 점수만 오르고 실제 문제 점수는 그대로라면, 시험지에 맞춰진 것이다.

시험지를 다룰 때 흔한 실수가 있다. 하나는 평가 세트를 보면서 프롬프트를 계속 고치는 것이다. 이러면 프롬프트가 이 시험지에만 맞춰진다. 고칠 때 보는 개발용 세트와, 가끔만 열어 보는 검증용 세트를 나눠 두면 낫다. 다른 하나는 평가 세트를 버전 관리하지 않는 것이다. 문제가 바뀌면 점수도 바뀌니, 점수를 비교하려면 "어느 버전의 시험지로 친 점수인가"를 같이 남겨야 한다.

## 정답이 정해진 문제는 코드로 채점한다

가장 먼저 만들 채점기는 결정적(deterministic) 평가다. 같은 답에는 항상 같은 점수를 내는 코드 검사다. 빠르고, 공짜고, 흔들리지 않는다. 생각보다 많은 문제가 여기에 들어간다.

- 정확 일치: 분류 라벨, 숫자 답, 예/아니오
- 포함·불포함: 꼭 들어가야 할 사실("영업일"), 나오면 안 되는 것(다른 사용자의 주문 번호, 내부 URL)
- 정규식: 날짜 형식, 전화번호 마스킹
- JSON 스키마: 파싱되는지, 필수 필드가 있는지, 타입이 맞는지
- 도구 호출: 어떤 도구를 불렀는지, 인자가 맞는지
- 길이·언어: 몇 자 이하인지, 한국어로 답했는지

처음 장면을 가짜 모델로 재현해 봤다. 프롬프트 v1과 v2(짧고 친근하게)가 내는 답을 흉내 낸 고정 응답을 두고, 위의 검사를 돌린다. 진짜 모델을 부르지 않으니 채점기 자체를 테스트하기에도 좋다.

```js
// evals.mjs의 채점 부분
function grade(c, out) {
  const k = c.check;
  if (k.mustInclude) return k.mustInclude.every((w) => out.text.includes(w)) || `빠진 말: ${k.mustInclude}`;
  if (k.json) {
    try { const o = JSON.parse(out.text); return k.json.every((f) => f in o) || "필드 누락"; }
    catch { return "JSON 파싱 실패"; }
  }
  if (k.tool) return out.tool === k.tool || `도구 ${out.tool ?? "없음"} ≠ ${k.tool}`;
  if (k.mustNotMatch) return !k.mustNotMatch.test(out.text) || "다른 주문 번호 노출";
  if (k.maxChars) return out.text.length <= k.maxChars || "너무 김";
}
```

```text
$ node evals.mjs
v1 6/6 통과
v2 FAIL refund-01  빠진 말: 영업일
v2 FAIL refund-02  빠진 말: 부분 환불
v2 FAIL order-01   JSON 파싱 실패
v2 FAIL order-02   도구 get_order_status ≠ cancel_order
v2 2/6 통과
```

문제 여섯 개에 코드 스무 줄로 처음 장면의 세 가지 제보가 모두 배포 전에 나온다. 결정적 평가는 이렇게 "망가지면 안 되는 것"을 지키는 데 강하다. 반대로 "답이 친절한가", "설명이 정확한가"처럼 표현이 여러 가지일 수 있는 품질은 재지 못한다. 그건 다음 단계의 몫이다.

포함 검사는 너무 빡빡하게 걸면 안 된다는 점도 기억해 둔다. "영업일"을 요구했는데 모델이 "평일 기준 3~5일"이라고 쓰면 뜻은 맞는데 떨어진다. 이런 문제가 많아지면 LLM 채점으로 옮기거나, 허용하는 표현 목록을 넓힌다.

## 정답이 하나가 아닌 문제는 LLM에게 채점을 맡긴다

"이 답이 고객의 질문에 실제로 답하는가", "근거 문서에 없는 말을 지어냈는가" 같은 질문은 코드로 판단하기 어렵다. 사람이 하면 정확하지만 느리고 비싸다. 그래서 다른 LLM에게 채점 기준표(rubric)를 주고 채점을 맡긴다. 이를 LLM-as-a-judge라고 부른다.

채점관 프롬프트는 막연하게 "1~10점으로 평가해"라고 하지 않는다. 점수마다 무엇을 뜻하는지 적고, 판단 이유를 먼저 쓰게 한 뒤 점수를 내게 한다.

```text
너는 고객 지원 답변을 채점한다. 아래 기준만으로 판단한다.

<question>{질문}</question>
<reference>{상담 매뉴얼의 해당 문단}</reference>
<answer>{채점할 답}</answer>

기준:
- pass: reference에 있는 조건(기간, 기준, 예외)을 빠뜨리지 않고, reference에 없는 약속을 하지 않는다.
- fail: 조건 하나라도 빠졌거나, reference에 없는 내용을 사실처럼 말한다.
말투와 길이는 채점하지 않는다.

먼저 <reasoning>에 빠진 조건이나 지어낸 내용을 적고, 마지막 줄에 pass 또는 fail만 쓴다.
```

이 프롬프트에 판단을 돕는 장치가 몇 개 들어 있다. 점수를 10단계 대신 pass/fail 두 단계로 줄였다. 단계가 많을수록 채점관이 7점과 8점을 일관되게 가르지 못하고 점수가 흔들린다. 참고 문단(reference)을 함께 줬다. 채점관이 자기 지식으로 사실 여부를 판단하게 두면 채점관의 환각이 점수에 섞인다. "말투와 길이는 채점하지 않는다"처럼 보지 말 것도 적었다. 아래에서 볼 편향 때문이다.

채점관의 답을 읽는 코드도 결정적으로 짠다. 마지막 줄만 보고, 정해진 단어가 아니면 "채점 실패"로 따로 센다. 채점 실패를 fail로 섞어 버리면 채점관이 흔들린 것과 답이 나쁜 것이 구분되지 않는다.

```ts
type Verdict = "pass" | "fail" | "judge_error";

function parseVerdict(judgeText: string): Verdict {
  const last = judgeText.trim().split("\n").at(-1)?.trim().toLowerCase();
  if (last === "pass" || last === "fail") return last;
  return "judge_error"; // 형식을 어겼다. 다시 묻거나 사람에게 보낸다
}
```

채점관 호출에도 temperature를 0이나 낮은 값으로 두고, 채점 모델 이름과 채점 프롬프트 버전을 결과와 함께 저장한다. 나중에 점수가 튀었을 때 답이 바뀐 건지 채점관이 바뀐 건지 가를 수 있어야 한다.

채점 방식은 두 가지가 있다. 답 하나를 기준에 비춰 채점하는 방식(pointwise)과, 두 답을 나란히 놓고 어느 쪽이 나은지 고르는 방식(pairwise)이다. 프롬프트 v1과 v2를 비교할 때는 pairwise가 더 민감하다. 절대 점수로는 둘 다 "괜찮음"이어도, 나란히 놓으면 차이가 보인다. 대신 pairwise는 아래의 위치 편향에 특히 약하다.

### 채점관도 치우친다

LLM 채점관에게는 알려진 편향이 몇 가지 있다. 연구마다 크기가 다르고 모델마다 다르지만, 방향은 대체로 같게 보고된다.

위치 편향(position bias)은 pairwise에서 먼저 나온 답(또는 나중 답)을 더 좋게 보는 경향이다. 같은 두 답의 순서만 바꿨는데 승자가 바뀐다면 그 판단은 내용이 아니라 순서가 한 것이다. 막는 방법은 순서를 바꿔 두 번 채점하고, 두 번 모두 같은 쪽을 고른 경우만 승리로 세고, 엇갈리면 무승부로 치는 것이다.

길이 편향(verbosity bias)은 더 길고 자세한 답을 더 좋게 보는 경향이다. 처음 장면처럼 "짧게"가 목표인 변경을 채점할 때 특히 위험하다. 기준표에 길이를 보지 말라고 적고, 길이는 결정적 평가로 따로 잰다.

자기 선호 편향(self-preference bias)은 채점관이 자기와 같은 모델(또는 같은 계열)이 쓴 답을 더 좋게 보는 경향이다. 답을 쓰는 모델과 채점하는 모델을 다른 계열로 두거나, 적어도 사람 평가와 비교해서 치우침이 있는지 본다.

## 채점관을 사람과 맞춰 본다

LLM 채점관을 쓰기로 했다면 그 채점관도 평가해야 한다. 방법은 단순하다. 같은 답 수십 개를 사람이 채점하고, 채점관의 결과와 얼마나 일치하는지 본다.

여기서 일치율(같은 판정을 낸 비율)만 보면 속는다. 답의 90%가 원래 pass인 데이터에서 무조건 pass라고 하는 채점관은 일치율이 90%다. 아무것도 판단하지 않았는데도 그렇다. 그래서 우연히 일치할 확률을 빼고 보는 코헨의 카파(Cohen's kappa)를 쓴다.

카파 = (실제 일치율 − 우연 일치율) ÷ (1 − 우연 일치율)

우연 일치율은 각 라벨을 두 채점자가 고른 비율을 곱해 더한 값이다. 예를 들어 사람이 20개 중 12개를 pass, 채점관이 14개를 pass라고 했다면 둘이 우연히 pass에서 만날 확률은 0.6 × 0.7 = 0.42, fail에서 만날 확률은 0.4 × 0.3 = 0.12, 합쳐서 0.54다. 실제로 16개가 일치했다면(0.8) 카파는 (0.8 − 0.54) ÷ 0.46 ≈ 0.565다. 직접 짜 보자.

  // 2) 라벨마다 a 비율 × b 비율을 더한 우연 일치율 pe

  return 0;

  solution={`function cohenKappa(a, b) {
  const n = a.length;
  const labels = [...new Set([...a, ...b])];
  let agree = 0;
  for (let i = 0; i < n; i++) if (a[i] === b[i]) agree++;
  const po = agree / n;
  let pe = 0;
  for (const l of labels) {
    const pa = a.filter((x) => x === l).length / n;
    const pb = b.filter((x) => x === l).length / n;
    pe += pa * pb;
  }
  if (pe === 1) return 1;
  return Math.round(((po - pe) / (1 - pe)) * 1000) / 1000;
}`}

두 번째 테스트가 이 지표를 쓰는 이유다. 일치율 90%짜리 채점관의 카파가 0이다. 흔히 쓰는 해석 기준(Landis와 Koch)으로는 0.4~0.6이 중간, 0.6~0.8이 상당한 일치, 0.8 이상이 거의 완벽이다. 다만 이 경계는 관례일 뿐이라, 사람끼리의 카파를 먼저 재 보는 게 더 쓸모 있다. 사람 둘이 0.6밖에 안 맞는 기준이라면 채점관에게 0.8을 기대할 수 없다. 그건 기준표가 애매하다는 뜻이고, 고칠 곳은 채점관이 아니라 기준표다.

카파가 낮게 나오면 불일치한 사례를 모아서 읽는다. 채점관이 일관되게 틀리는 모양(긴 답을 봐준다, 참고 문단에 없는 상식을 사실로 친다)이 보이면 기준표에 그 경우를 적어 넣고 다시 잰다. 이렇게 사람 판정에 채점관을 맞춰 가는 일을 채점관 보정이라고 한다.

### 사람 평가는 샘플로 계속한다

사람 평가는 채점관을 처음 맞출 때만 하는 게 아니다. 운영 중에도 일부 샘플을 계속 사람이 본다. 전부 볼 수는 없으니 고르는 방법이 중요하다. 무작위 샘플은 전체 품질을 보여 주고, 채점관이 fail을 준 것, 사용자가 싫어요를 누른 것, 채점관의 확신이 낮았던 것을 더 많이 뽑으면 문제를 빨리 찾는다. 사람 채점자에게는 기준표와 예시를 주고, 같은 사례를 두 명이 보게 해서 사람끼리의 일치도도 가끔 잰다.

## RAG와 에이전트는 따로 재는 것이 있다

### RAG 답의 충실성

RAG 답은 "질문에 맞는 답인가"와 "근거 문서에 있는 내용인가"가 따로 논다. 둘을 섞어서 재면 어디가 문제인지 모른다. RAGAS 같은 도구가 재는 지표가 이걸 나눈다.

- 충실성(faithfulness): 답을 주장 단위로 쪼개고, 주장마다 검색된 문서로 뒷받침되는지 LLM에게 판단시켜 그 비율을 낸다. 낮으면 모델이 문서 밖의 말을 지어낸 것이다.
- 답 관련성(answer relevancy): 답만 보고 원래 질문을 거꾸로 만들어 보게 한 뒤, 그 질문이 실제 질문과 얼마나 비슷한지(임베딩 유사도) 본다. 낮으면 딴소리를 한 것이다.
- 컨텍스트 정밀도·재현율: 검색된 조각이 질문에 필요한 것이었는지, 필요한 정보가 다 검색됐는지 본다. 재현율은 정답 참고 답이 있어야 잴 수 있다.

충실성은 높은데 정답률이 낮으면 검색이 엉뚱한 문서를 가져온 것이고(모델은 그 문서를 충실히 따랐다), 검색은 좋은데 충실성이 낮으면 생성 쪽 문제다. 이 지표들도 내부에서 LLM 채점을 쓰니, 위의 편향과 보정 이야기가 그대로 적용된다.

### 에이전트는 결과와 과정을 함께 본다

도구를 부르는 에이전트는 최종 답이 맞아도 과정이 엉망일 수 있다. 환불을 처리했지만 조회 도구를 다섯 번 불렀거나, 승인 없이 취소 도구를 먼저 불렀을 수 있다. 그래서 재는 것이 늘어난다.

- 작업 성공률: 끝났을 때 원하는 상태가 되었나(주문이 실제로 취소됐나). 가능하면 답 문장이 아니라 바뀐 상태를 확인한다.
- 도구 선택 정확도: 각 단계에서 맞는 도구를 골랐나, 인자가 맞나.
- 궤적(trajectory) 평가: 도구 호출 순서가 허용된 범위인가. 꼭 지나야 할 단계(본인 확인 → 취소)를 건너뛰지 않았나.
- 단계 수, 토큰, 비용, 지연(p50과 p95): 같은 성공이라도 열 단계 걸리는 버전은 나쁘다.

테스트는 두 층으로 나눈다. 도구 하나하나는 가짜 모델로 단위 테스트한다. 모델이 "이 인자로 이 도구를 불러 달라"고 요청했다고 치고, 도구 코드가 권한 검사와 오류 처리를 제대로 하는지 본다. 모델을 부르지 않으니 빠르고 결정적이다. 흐름 전체는 진짜 모델로 통합 테스트하되, 외부 시스템은 테스트용 가짜(샌드박스 DB, 가짜 결제)로 바꾸고 궤적과 최종 상태를 채점한다.

```ts
// 도구 단위 테스트: 모델 없이 "모델이 이렇게 요청했다"를 직접 넣는다
test("cancel_order는 남의 주문을 취소하지 않는다", async () => {
  const session = { userId: "u-1" };
  const result = await tools.cancel_order.run({ orderId: "A-2002" }, session); // u-2의 주문
  expect(result.isError).toBe(true);
  expect(await db.order("A-2002")).toMatchObject({ status: "PAID" }); // 상태가 그대로인지 확인
});
```

## 모델이 말하는 확신을 그대로 믿을 수 있나

"확신이 낮으면 사람에게 넘긴다"는 설계를 흔히 한다. 모델에게 답과 함께 0~1 사이 확신도를 내게 하거나, "이 답이 맞는가"를 모델 스스로 다시 판단하게(자기 평가) 하는 식이다. 문제는 그 숫자가 실제 정답률과 맞는지다.

확신도가 잘 보정(calibration)되어 있다는 건 "0.9라고 한 답들을 모아 보면 실제로 90% 정도가 맞는다"는 뜻이다. 말로 내놓는 확신도는 대체로 과신하는 쪽으로 치우친다는 보고가 많다. 모르는 질문에도 0.9를 쓰는 식이다. 그래서 확신도를 그대로 문턱값으로 쓰기 전에 평가 세트로 확인한다. 확신도 구간(0.5~0.6, 0.6~0.7, …)마다 실제 정답률을 계산해 표로 그려 보면 바로 보인다. 구간별 차이를 크기로 가중 평균한 값이 ECE(Expected Calibration Error)다.

작은 예로 계산해 보자. 모델이 확신도와 함께 낸 답 20개를 사람이 채점했더니 이렇게 나왔다고 하자.

```text
모델이 말한 확신도   답 수   실제로 맞은 수   실제 정답률   차이
0.9                 10      6               0.600         0.300
0.7                 6       4               0.667         0.033
0.5                 4       2               0.500         0.000
```

ECE는 구간마다 차이에 그 구간의 답 비율을 곱해 더한 값이다. 10/20 × 0.3 + 6/20 × 0.033 + 4/20 × 0 = 0.16이다. 숫자보다 표의 첫 줄이 중요하다. 모델이 0.9라고 한 답의 40%가 틀렸다. "0.8 이상이면 자동 처리"라는 규칙을 이 모델에 그대로 걸면, 자동 처리된 답 열 개 중 네 개가 틀린 채 나간다. 문턱값은 모델이 말한 숫자가 아니라 이런 표를 보고 정한다.

말로 받는 확신도 대신 쓸 만한 신호도 있다. 같은 질문을 여러 번 샘플링해서 답이 얼마나 일치하는지 보는 방법이다. 다섯 번 중 다섯 번 같은 답이면 다섯 번 다 다른 답일 때보다 맞을 가능성이 높다는 경향이 있다. 호출이 다섯 배 들지만, 사람에게 넘길 대상을 고르는 용도라면 그만한 가치가 있는 경우가 많다. 여러 번 뽑아 다수결하는 이 아이디어는 [추론 프롬프트 글](/posts/prompt-reasoning-techniques)의 자기 일관성과 같은 뿌리다.

## 같은 시험을 몇 번 쳐야 하나

LLM은 같은 입력에도 답이 달라지니, 평가 점수도 돌릴 때마다 흔들린다. 그래서 점수 차이를 볼 때 두 가지를 따진다.

하나는 문제마다의 흔들림이다. 한 번 실행했을 때 90% 확률로 통과하는 문제가 있다고 하자. 다섯 번 돌려 다섯 번 다 통과할 확률은 0.9의 5제곱, 약 59%다. 한 번만 돌리는 CI는 이 문제를 열 번에 한 번꼴로 실패로 보고하고, 사람들은 곧 "LLM 테스트는 원래 깜빡인다"며 실패를 무시하기 시작한다. 그래서 문제마다 여러 번(3~5번) 돌려 통과율을 내고, 통과율이 기준(예: 80%) 아래로 떨어질 때만 실패로 친다. 반대로 "한 번이라도 실패하면 안 되는" 안전 문제는 여러 번 돌려 전부 통과해야 하는 기준을 쓴다. 실제 사용자는 같은 기능을 여러 번 쓰니, 매번 성공하는지가 중요한 기능이면 이 기준이 맞다.

다른 하나는 전체 점수의 우연한 차이다. 문제 100개에서 v1이 85개, v2가 82개를 통과했다면 v2가 나빠진 걸까. 정답률 85%에 문제 100개면 표준오차가 약 3.6%p, 95% 신뢰구간은 앞뒤로 약 7%p다. 3%p 차이는 이 범위 안에 있다. 같은 문제로 두 버전을 비교했으니 짝지은 비교를 하면 더 정확하다. 결과가 갈린 문제만 센다. v1만 통과한 문제가 7개, v2만 통과한 문제가 4개라면 맥니마 검정(정확 검정) p값은 약 0.55로, 우연으로 충분히 설명된다. 같은 3%p 차이라도 v1만 14개, v2만 2개였다면 p값은 약 0.004다. 이건 우연이라고 보기 어렵다. v2가 몇 문제를 고쳤지만 더 많은 문제를 망가뜨렸다는 뜻이고, 그 14개를 읽어 봐야 한다.

## CI에서 회귀 테스트로 돌린다

평가를 사람이 기억날 때 돌리면 결국 안 돌린다. 프롬프트·모델 설정·도구 설명이 바뀌는 PR마다 CI가 자동으로 돌리게 한다. 흐름은 이렇다.

몇 가지를 정해 두면 운영이 편하다.

- 실패 기준을 점수 하나로 두지 않는다. "안전 범주는 전부 통과", "JSON 범주는 통과율 100%", "전체 pass율은 기준 대비 2%p 넘게 떨어지지 않음"처럼 범주별로 둔다. 안전 문제 하나가 실패한 건 평균 점수로 가려지면 안 된다.
- 기준 결과를 저장해 둔다. main 브랜치의 결과를 저장해 두고 PR 결과와 문제 단위로 비교해서, "통과 → 실패로 바뀐 문제" 목록을 PR 댓글로 남긴다. 사람이 읽는 건 이 목록이다.
- 비용과 시간을 정해 둔다. 평가 세트 200개 × 3번 × 채점까지 돌리면 PR마다 수백~수천 번의 모델 호출이다. PR에서는 빠른 부분 세트만, 밤마다 전체 세트를 돌리는 식으로 나눈다. 결정적 평가가 실패하면 비싼 LLM 채점은 건너뛴다.
- 채점관도 고정한다. 채점 모델 버전과 채점 프롬프트를 바꾸면 점수 기준이 바뀐다. 채점관을 바꾸는 PR은 "같은 답에 대한 점수가 어떻게 바뀌었나"만 따로 본다.

이 틀 위에서 도구들이 무엇을 자동화하는지 보면 고르기가 쉽다. DeepEval은 pytest처럼 테스트 함수 안에서 지표(충실성, 답 관련성, 기준표로 채점하는 G-Eval 등)와 문턱값을 걸어 CI에서 돌리는 쪽에 가깝다. Ragas는 위에서 본 RAG 지표 계산과, 문서에서 평가용 질문을 만들어 주는 기능에 강하다. LangSmith는 운영 트레이스를 평가 세트로 옮기고, 실험(버전별 실행)을 나란히 비교하고, 사람 검수 큐를 돌리는 쪽이다. 어느 도구를 쓰든 시험지를 만드는 일과, 채점관을 사람과 맞추는 일은 대신해 주지 않는다.

## 시험 점수는 좋은데 사용자는 불만이다

오프라인 평가(미리 만든 시험지)와 온라인 지표(실제 사용자의 반응)는 자주 어긋난다. 시험지가 실제 질문 분포를 닮지 않았거나, 시험지가 재지 않는 것(지연, 말투, 여러 턴에 걸친 대화)이 불만의 원인이기 때문이다.

온라인에서 볼 수 있는 신호는 이런 것들이다. 좋아요/싫어요 버튼(누르는 사람이 적고 불만이 있는 사람이 더 누른다), 같은 질문을 바꿔 다시 묻는 비율, 답을 다시 생성하는 비율, 상담원 연결 요청 비율, 답을 복사하거나 링크를 누른 비율, 작업이 실제로 끝났는지(환불 신청 완료). 이 신호로 버전을 비교하려면 A/B 테스트를 하는데, 이건 일반 기능 실험과 같은 방법을 따른다.

두 쪽을 잇는 습관이 하나 있다. 온라인에서 나쁜 신호가 온 대화를 모아 주기적으로 읽고, 쓸 만한 것을 평가 세트에 넣는다. 그러면 시험지가 점점 실제 사용자를 닮아 간다. 오프라인 평가는 "배포해도 망가지지 않는가"를 빠르게 막는 문이고, 온라인 지표는 "실제로 좋아졌는가"를 확인하는 자리다. 하나로 다른 하나를 대신하지 않는다.

## 평가가 있어도 생기는 일들

"CI 평가가 어제는 통과, 오늘은 실패인데 코드는 그대로다"라면 먼저 모델 이름을 본다. `latest`처럼 움직이는 별칭을 쓰면 공급사가 뒤의 모델을 바꾸는 순간 점수가 바뀐다. 평가와 운영 모두 날짜가 박힌 고정 버전을 쓰고, 버전을 올리는 일을 PR로 만든다. 모델이 그대로라면 실패한 문제의 통과율을 본다. 3번 중 2번 통과하던 문제가 이번에 1번만 통과했다면 흔들림이고, 전부 실패로 바뀌었다면 무언가 바뀐 것이다.

"점수는 계속 오르는데 상담 팀 체감은 그대로다"라면 시험지를 의심한다. 문제 대부분이 처음 만든 날의 질문이라 지금 사용자 질문과 멀어졌거나, 프롬프트를 고칠 때 같은 세트를 계속 보며 맞춰 온 경우다. 최근 한 달 로그에서 무작위로 수십 개를 뽑아 새로 채점해 보면 차이가 보인다.

"LLM 채점 점수가 갑자기 전부 올랐다"면 채점관 쪽 변경을 본다. 채점 프롬프트를 고쳤거나 채점 모델을 바꿨거나, 채점관 답 파싱이 실패를 pass로 처리하고 있을 수 있다. judge_error 비율을 지표로 함께 띄워 두면 이런 경우가 바로 보인다.

"평가 비용이 운영 비용만큼 나온다"면 PR마다 전체 세트를 채점까지 돌리고 있을 가능성이 크다. 바뀐 파일에 따라 관련 범주만 돌리고, 결정적 평가가 실패하면 채점을 건너뛰고, 전체 세트는 밤에 한 번 돌리는 식으로 나눈다.

## 평가는 프롬프트의 단위 테스트다

LLM 기능에서 평가 세트는 일반 코드의 테스트 스위트와 같은 자리에 있다. 정답이 정해진 것은 코드로, 정답이 여러 개인 것은 기준표를 준 LLM 채점관으로, 채점관은 사람과의 카파로 확인한다. 답이 흔들리니 여러 번 돌리고, 평균보다 통과에서 실패로 바뀐 문제 목록을 먼저 본다. 처음 장면의 "짧고 친근하게"는 문제 여섯 개짜리 시험지만 있었어도 배포 전에 걸렸다. 평가를 붙였다면 다음으로 볼 것은 프롬프트 자체를 어떻게 바꿔 점수를 올리는지다. [추론 프롬프트 글](/posts/prompt-reasoning-techniques)에서 이어 간다.

## 면접에서 나올 만한 질문

### LLM 기능에 평가 세트가 왜 필요한가요?

프롬프트 한 줄, 모델 버전, 검색 문서 하나만 바뀌어도 모든 입력의 답이 달라지는데, 사람은 고친 질문 몇 개만 확인하기 때문이다. 게다가 답이 확률적이라 한 번 맞은 걸로는 다음에도 맞는다고 할 수 없다. 그래서 실제 로그와 버그 제보에서 모은 입력에 채점 기준을 붙인 평가 세트를 두고, 바꿀 때마다 같은 시험을 다시 쳐서 회귀를 막는다.

### 결정적 평가와 LLM-as-a-judge는 어떻게 나눠 쓰나요?

정답이나 형식이 정해진 것(라벨, JSON 스키마, 꼭 들어갈 사실, 불러야 할 도구, 금지 패턴)은 코드로 채점한다. 빠르고 공짜이고 흔들리지 않는다. 표현이 여러 가지일 수 있는 품질(질문에 답했는가, 근거에 충실한가)은 기준표와 참고 문서를 준 LLM 채점관에게 맡긴다. CI에서는 결정적 평가를 먼저 돌리고 실패하면 비싼 채점은 건너뛴다.

### LLM 채점관의 편향에는 무엇이 있고 어떻게 줄이나요?

먼저 나온 답을 좋아하는 위치 편향, 긴 답을 좋아하는 길이 편향, 자기 계열 모델의 답을 좋아하는 자기 선호 편향이 알려져 있다. pairwise는 순서를 바꿔 두 번 채점해 두 번 다 같은 쪽일 때만 승리로 세고, 기준표에 길이를 보지 말라고 적고 길이는 코드로 따로 재며, 답하는 모델과 다른 계열로 채점한다. 점수 단계는 적게, 이유를 먼저 쓰게 한다.

### 채점관이 믿을 만한지는 어떻게 확인하나요?

같은 답 수십 개를 사람이 채점해 채점관 결과와 코헨 카파로 비교한다. 단순 일치율은 pass가 많은 데이터에서 무조건 pass만 해도 높게 나오니 우연 일치를 뺀 카파를 본다. 사람끼리의 카파를 먼저 재서 기준표 자체가 명확한지 확인하고, 불일치 사례를 읽어 기준표를 고친다. 채점 모델을 바꿀 때도 이 비교를 다시 한다.

### 비결정성 때문에 평가를 몇 번 돌려야 하나요?

문제마다 3~5번 돌려 통과율로 판정하는 게 보통이다. 90% 확률로 통과하는 문제도 다섯 번 연속 통과할 확률은 약 59%라서, 한 번만 돌리면 깜빡이는 실패가 생기고 팀이 실패를 무시하게 된다. 안전처럼 매번 지켜야 하는 범주는 전부 통과를 요구한다. 버전 간 점수 차이는 같은 문제의 결과가 갈린 것만 세는 짝지은 비교로 우연인지 본다.

### 문제 100개에서 85%가 82%로 떨어졌다면 나빠진 건가요?

그것만으로는 말할 수 없다. 100개에서 85%면 95% 신뢰구간이 앞뒤로 약 7%p라 3%p는 우연 범위 안이다. 결과가 갈린 문제가 v1만 통과 7개, v2만 통과 4개라면 맥니마 검정 p값이 약 0.55로 우연이고, 14개 대 2개라면 약 0.004로 실제 회귀다. 그래서 평균보다 통과에서 실패로 바뀐 문제 목록을 먼저 읽는다.

### 에이전트는 무엇을 평가하나요?

최종 답뿐 아니라 끝난 상태(주문이 실제로 취소됐나), 단계마다의 도구 선택과 인자, 호출 순서가 허용된 궤적인지, 단계 수·비용·지연을 본다. 도구는 가짜 모델로 "이 인자로 불렸다"를 넣어 권한 검사와 오류 처리를 단위 테스트하고, 흐름은 진짜 모델과 샌드박스 외부 시스템으로 통합 테스트해 궤적과 최종 상태를 채점한다.

### 오프라인 평가 점수가 올랐는데 사용자 불만이 늘 수 있나요?

있다. 시험지가 실제 질문 분포를 닮지 않았거나, 시험지가 재지 않는 지연·말투·여러 턴 대화가 원인일 수 있다. 그래서 다시 묻기 비율, 재생성 비율, 상담원 연결 비율, 작업 완료 같은 온라인 지표를 함께 보고 A/B로 비교한다. 나쁜 신호가 온 대화를 주기적으로 읽어 평가 세트에 넣으면 시험지가 점점 실제 사용자를 닮아 간다.
