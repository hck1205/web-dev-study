"SNS의 뉴스 피드 화면을 설계해 보세요." 프런트엔드 설계 면접에서 가장 자주 나오는 문제 중 하나다. 백엔드라면 글 하나를 팔로워 피드에 어떻게 나눠 넣을지, 피드 캐시를 어떻게 둘지를 그린다. 그 이야기는 [뉴스 피드 설계 ①](/posts/sd-news-feed-publishing)과 [②](/posts/sd-news-feed-retrieval)에 있다. 이 글은 같은 피드를 휴대폰 화면 쪽에서 설계한다. 사용자가 엄지로 3초에 화면 다섯 장을 넘기는데 글이 끊기지 않게 나오고, 사진이 늦게 와도 글이 밀리지 않고, 좋아요가 바로 눌리고, 새 글이 와도 읽던 자리를 잃지 않게 하는 것이다.

순서는 [프런트엔드 시스템 디자인 면접](/posts/frontend-system-design-interview)에서 정리한 그대로 간다. 요구 사항, 컴포넌트, API와 데이터 모델, 상태, 그리고 깊이 파기다. 상태를 어디에 둘지는 [프런트엔드 상태 구조](/posts/frontend-state-architecture)에서, 끊기는 네트워크와 낙관적 업데이트의 순서 문제는 [분산 시스템으로서의 프런트엔드](/posts/frontend-as-distributed-system)에서 다뤘으니 여기서는 피드에 적용하는 자리만 짚는다. 측정은 Chromium 141(Playwright, 헤드리스)에서 390×844 화면으로 했고, 출력은 찍힌 그대로다.

## 무엇을 만들지 먼저 좁힌다

뉴스 피드는 기능을 다 넣으면 끝이 없다. 첫 5분에 범위를 정한다. 이 글에서는 이렇게 가정한다.

- 글은 작성자, 본문, 사진 0~4장, 좋아요 수와 내가 눌렀는지로 이뤄진다. 댓글은 개수만 보여 주고 상세는 다른 화면이다.
- 아래로 스크롤하면 끝없이 이어진다. 한 번에 10개씩 받는다.
- 좋아요는 누르자마자 바뀐다.
- 내가 보고 있는 동안 새 글이 올라오면 알려 준다.
- 주 사용 기기는 중저가 안드로이드 휴대폰이다. CPU가 데스크톱보다 몇 배 느리다고 본다.
- 첫 화면은 검색 엔진에 노출될 필요가 없다. 로그인한 사용자만 본다.

마지막 두 줄이 설계를 많이 정한다. 느린 기기라서 DOM을 적게 두는 게 중요해지고, 로그인 사용자만 보니 서버 렌더링보다 앱 셸을 빨리 띄우고 데이터를 받는 쪽으로 기운다. 첫 화면 렌더링 방식을 고르는 기준은 [CSR, SSR, SSG, ISR, 스트리밍](/posts/rendering-strategies)에 있다.

## 5,000개를 다 그리면 첫 프레임이 4초다

피드를 오래 스크롤하면 글이 수천 개 쌓인다. 글 카드 하나에 요소가 열 개쯤이다. 글 5,000개를 한 번에 그리는 경우와, 화면에 보이는 줄과 위아래 다섯 줄만 그리는 경우(가상화)를 비교했다. 각 조건을 세 번씩 돌려 가운데 값을 적었다. CPU ×4는 개발자 도구 프로토콜로 CPU를 네 배 느리게 만든 것이다. 중저가 휴대폰을 흉내 내는 흔한 설정이다.

```text
CPU x1 full     첫 프레임  1021ms  DOM 요소  50007  JS 힙  20.6MB  한 화면 스크롤 18ms
CPU x1 windowed 첫 프레임    13ms  DOM 요소    137  JS 힙   3.3MB  한 화면 스크롤 13ms
CPU x4 full     첫 프레임  3930ms  DOM 요소  50007  JS 힙  20.2MB  한 화면 스크롤 25ms
CPU x4 windowed 첫 프레임    59ms  DOM 요소    137  JS 힙   3.3MB  한 화면 스크롤 25ms
```

다 그린 쪽은 DOM 요소가 5만 개, 느린 CPU에서 첫 프레임까지 거의 4초가 걸렸다. 가상화한 쪽은 요소 137개, 59ms다. 실제 피드는 한 번에 5,000개를 받지 않지만, 무한 스크롤로 30분을 내려가면 같은 상황이 된다. 그때부터는 좋아요 하나를 눌러도, 화면을 돌려도 5만 개 요소의 스타일과 레이아웃이 다시 계산된다.

가상화의 원리는 간단하다. 전체 높이만큼 빈 상자를 만들어 스크롤바를 실제처럼 두고, 스크롤 위치에서 보이는 범위를 계산해 그 줄만 절대 위치로 그린다. 아래 그림에서 다음을 누르면 스크롤에 따라 그려지는 줄이 바뀌는 모습을 볼 수 있다.

실제 피드는 글마다 높이가 다르다. 사진 개수와 본문 길이가 다르니 고정 높이로 계산할 수 없다. TanStack Virtual이나 react-virtuoso 같은 라이브러리는 처음엔 추정 높이로 자리를 잡고, 줄이 그려진 뒤 실제 높이를 재서 고쳐 쓴다. 그래서 응답에 사진 크기가 있어야 추정이 정확해지고 스크롤바가 덜 튄다. 가상화의 비용도 말해야 한다. 그려지지 않은 글은 브라우저의 페이지 내 검색(Ctrl+F)에 걸리지 않고, 화면 낭독기가 전체 개수를 모른다. 목록에 `aria-setsize`와 `aria-posinset`을 붙여 몇 번째 글인지 알려 줄 수 있다. 가상화 대신 CSS의 `content-visibility: auto`로 화면 밖 줄의 렌더링만 건너뛰는 방법도 있다. DOM은 그대로 두니 검색은 되지만 요소 수가 줄지는 않는다. 둘의 차이와 측정은 [렌더링 성능 최적화](/posts/rendering-performance-optimization)에 있다.

## 바닥에 닿기 전에 다음 페이지를 부른다

무한 스크롤은 목록 끝에 감시용 요소를 두고, 그게 화면에 들어오면 다음 페이지를 부른다. 언제 "들어왔다"고 볼지가 IntersectionObserver의 `rootMargin`이다. 서버는 페이지마다 400ms가 걸리고, 사용자는 초당 1,500px쯤 빠르게 훑으며 8초 동안 내려간다고 했다. 감시용 요소가 화면에 실제로 들어올 때 부르는 경우와, 화면 아래 1000px 앞에서 미리 부르는 경우를 비교했다. 사용자가 바닥에 닿았는데 아직 다음 페이지가 안 온 순간을 "기다림"으로 셌다.

```text
rootMargin    0px: 요청 4번, 불러온 글 30개, 바닥에서 기다린 횟수 3번 (403, 390, 374ms)
rootMargin 1000px: 요청 4번, 불러온 글 40개, 바닥에서 기다린 횟수 1번 (400ms)
```

0px에서는 페이지마다 바닥에서 거의 0.4초씩 멈췄다. 사용자는 스피너를 세 번 봤고, 같은 8초 동안 읽은 글도 30개로 적다. 1000px 앞에서 부른 쪽은 한 번만 기다렸다. 이 한 번은 첫 화면을 받은 직후 바로 끝이 가까워져서 생긴 것으로, 첫 요청에서 두 페이지를 받아 두면 없앨 수 있다. 얼마나 앞에서 부를지는 "한 페이지 받는 시간 × 사용자가 스크롤하는 속도"보다 크게 잡는다. 400ms × 1,500px/s = 600px이니 1000px이면 여유가 있다. 너무 크게 잡으면 사용자가 보지도 않을 페이지를 받느라 데이터를 쓴다.

아래 그림은 이 흐름을 작은 화면에서 반복해 보여 준다.

<LoadingDemo patterns={["infinite-scroll"]} caption="목록 끝이 가까워지면 다음 묶음을 미리 불러와 이어 붙인다" />

무한 스크롤에서 같이 챙길 것이 있다. 요청이 진행 중이면 다시 부르지 않는다. 요청이 실패하면 감시용 요소 자리에 "다시 시도" 버튼을 둔다. 자동으로 계속 재시도하면 오프라인에서 요청이 쏟아진다. 피드 끝에 푸터가 있다면 무한 스크롤 때문에 영영 닿을 수 없으니, 푸터 링크는 다른 곳에 둔다. IntersectionObserver 자체의 동작은 [IntersectionObserver](/posts/scroll-triggered-intersection-observer) 글에 있다.

## 사진이 늦게 오면 글이 밀린다

글 여섯 개에 사진이 하나씩 있고, 사진은 300~600ms 늦게 온다. `<img>`에 크기를 주지 않은 경우와 원본 크기(`width="400" height="300"`)를 주고 CSS로 `width: 100%; height: auto`를 준 경우의 레이아웃 이동(CLS)을 쟀다.

```text
이미지 크기 지정 안 함: CLS 0.649, 레이아웃 이동 3번
이미지 크기 지정함 : CLS 0.000, 레이아웃 이동 0번
```

크기가 없으면 사진이 도착할 때마다 높이 0이던 자리가 늘어나며 아래 글을 밀었다. CLS 0.649는 "좋음" 기준인 0.1의 여섯 배가 넘는다. 사용자가 좋아요를 누르려는 순간 버튼이 밀려 다른 글을 누르게 되는 게 이 숫자다. 크기를 주면 브라우저가 `width`와 `height` 속성에서 비율을 계산해 자리를 미리 잡으니 이동이 0이 됐다. 피드 응답에 사진의 원본 크기를 넣어야 하는 이유가 이것이다.

사진 자체는 화면 크기에 맞는 것을 받는다. `srcset`과 `sizes`로 휴대폰에는 작은 파일을, AVIF·WebP로 더 가벼운 포맷을 준다. 화면 아래쪽 사진은 `loading="lazy"`로 미루되, 첫 화면에 보이는 첫 글의 사진은 미루지 않는다. 그 사진이 LCP 요소인 경우가 많다. 자세한 건 [이미지 최적화](/posts/image-optimization)와 [Core Web Vitals](/posts/core-web-vitals)에 있다.

## 새 글이 와도 읽던 자리를 지킨다

사용자가 20번째 글을 읽고 있는데 맨 위에 새 글 3개가 들어오면 어떻게 될까. 20번째 글을 화면 맨 위 근처에 둔 상태에서 목록 앞에 글 3개(각 151px)를 끼워 넣었다. Chromium의 기본 동작인 스크롤 앵커링을 켠 경우와 `overflow-anchor: none`으로 끈 경우를 비교했다.

```text
overflow-anchor: auto  위에 새 글 3개 삽입 전 p20 (top -10px) scrollY=3030 → 후 p20 (top -10px) scrollY=3483
overflow-anchor: none  위에 새 글 3개 삽입 전 p20 (top -10px) scrollY=3030 → 후 p17 (top -10px) scrollY=3030
```

스크롤 앵커링이 켜져 있으면 브라우저가 스크롤 위치를 453px(151 × 3) 내려서 사용자가 보던 20번 글이 제자리에 남았다. 끄면 스크롤 위치는 그대로인데 내용이 밀려 화면에 17번 글이 나왔다. 사용자는 읽던 글이 사라진 것처럼 느낀다. 크롬 계열과 파이어폭스는 스크롤 앵커링을 기본으로 켜 두지만, 사파리는 오랫동안 지원하지 않았으니 모든 브라우저에서 믿을 수는 없다. 가상화 라이브러리는 직접 위치를 계산하므로 이 기능과 상관없이 자체적으로 위치를 보정해야 한다.

그래서 많은 피드는 새 글을 바로 끼워 넣지 않는다. 서버가 새 글을 알리면 저장소의 대기 칸에 두고 화면 위에 "새 글 3개" 띠만 띄운다. 사용자가 띠를 누르면 그때 목록 앞에 붙이고 맨 위로 올린다. 사용자가 이미 맨 위에 있다면 바로 붙여도 된다.

## 글을 열었다 돌아오면 30번째 글로

피드에서 글 하나를 열어 상세를 보고 뒤로 가기를 누르면, 사용자는 방금 보던 30번째 글 앞으로 돌아가길 기대한다. 단순한 SPA로 재 봤다. 목록을 6,030px까지 내리고, 31번 글을 열고, 뒤로 갔다. 한 번은 돌아올 때 목록을 다시 받고(300ms), 한 번은 받아 둔 목록을 바로 그리고 떠날 때 기록해 둔 위치로 직접 옮겼다.

```js
// cached: 떠날 때 지금 위치를 기록에 적고, 돌아오면 받아 둔 목록을 바로 그린 뒤 옮긴다
history.scrollRestoration = "manual";
window.openPost = (id) => {
  history.replaceState({ y: scrollY }, "");               // 지금 칸에 위치를 적는다
  history.pushState({ detail: id }, "", `?post=${id}`);
  renderDetail(id);
};
// renderList() 끝에서: if (history.state?.y != null) scrollTo(0, history.state.y);
```

```text
== refetch: 상세로 가기 전 scrollY=6030 → 뒤로 가기 30ms 뒤 0, 500ms 뒤 0 (맨 위 글 p0)
== cached: 상세로 가기 전 scrollY=6030 → 뒤로 가기 30ms 뒤 6030, 500ms 뒤 6030 (맨 위 글 p30)
```

다시 받는 쪽은 맨 위로 튕겼다. 브라우저의 기본 스크롤 복원(`scrollRestoration = "auto"`)은 뒤로 가기 직후 위치를 되돌리려 하지만, 그 순간 목록이 비어 있어 높이가 없으니 0에 머문다. 300ms 뒤 목록이 채워져도 다시 옮겨 주지 않는다. 받아 둔 쪽은 목록을 바로 그릴 수 있으니 같은 자리로 돌아왔다.

그래서 피드는 상세를 다녀오는 동안 목록 데이터를 버리지 않는다. 쿼리 캐시에 남겨 두고 돌아오면 캐시로 먼저 그린다. 가상화를 쓰는 목록이라면 위치만으로는 부족하고, 그때까지 잰 줄 높이도 함께 기억해야 같은 글이 같은 자리에 온다. 상세를 모달이나 별도 레이어로 띄워 목록을 아예 화면에서 빼지 않는 방법도 있다. 목록을 다시 그리지 않으니 복원할 일도 없다. 주소에 둘 값과 기록 칸을 쌓는 방식은 [프런트엔드 상태 구조](/posts/frontend-state-architecture)에서 다뤘다.

## 좋아요는 누르자마자, 서버와는 나중에 맞춘다

좋아요는 서버 답을 기다리지 않는다. 저장소의 글 칸에서 `likedByMe`를 뒤집고 `likeCount`를 하나 바꾼 뒤 요청을 보낸다. 실패하면 되돌리고 짧은 알림을 띄운다. 정규화해 둔 덕분에 같은 글이 피드와 프로필 화면에 함께 있어도 한 칸만 바꾸면 둘 다 바뀐다.

여기서 꼬리 질문이 두 개 온다. 빠르게 두 번 누르면 어떻게 되나. 응답이 거꾸로 오면 화면과 서버가 어긋날 수 있다. 응답의 `version`을 비교해 낡은 것을 버리거나, 같은 글의 좋아요 요청을 한 줄로 세운다. 실제로 재현한 결과는 [분산 시스템으로서의 프런트엔드](/posts/frontend-as-distributed-system)에 있다. 다른 사람들이 누른 좋아요 수는 어떻게 맞추나. 실시간으로 맞출 필요가 거의 없다. 화면에 다시 들어오거나 새로고침할 때 서버 값으로 바꾼다. 내 좋아요만 바로 반영되면 사용자는 어긋남을 느끼지 않는다.

연타로 요청이 쏟아지는 것도 막는다. 누를 때마다 보내지 않고, 마지막 상태만 잠깐 뒤에 보내도 된다. 다섯 번 눌러 최종 상태가 "좋아요"라면 요청은 한 번이다. 낙관적 업데이트를 TanStack Query로 쓰는 방법은 [화면 데이터 캐시](/posts/client-data-cache)에, 기다리는 화면과 누르자마자 바뀌는 화면을 고르는 기준은 [로딩 패턴](/posts/loading-patterns)에 있다.

## 피드가 잘 도는지 숫자로 본다

배포한 뒤 볼 숫자를 미리 정한다. 피드에서는 이런 것들이다.

- 첫 글이 보이기까지의 시간과 LCP의 p75. 기기 등급과 네트워크로 나눈다.
- 스크롤 중 바닥에서 기다린 횟수와 시간. 앞에서 잰 "기다림"을 사용자 기기에서도 센다.
- 좋아요 버튼의 INP. 눌렀을 때 다음 프레임까지 걸린 시간이다.
- CLS. 사진 크기가 빠진 글이 섞이면 바로 오른다.
- 피드 요청 실패율과 자바스크립트 에러율. 배포 버전별로 나눠 본다.

숫자마다 목표를 두면 그게 이 화면의 SLO가 되고, 목표를 넘긴 몫이 에러 예산이 된다. 예를 들어 "바닥에서 기다린 비율 5% 이하"를 넘기면 다음 페이지를 더 일찍 부르거나 한 번에 받는 개수를 늘린다. 사용자 기기의 숫자를 모으는 방법은 [성능 지표는 어떻게 재나](/posts/performance-metrics-measurement)에, 에러를 모으는 방법은 [프런트엔드 에러 추적](/posts/frontend-error-tracking)에, 예산으로 배포를 정하는 방법은 [에러 예산과 소진 속도](/posts/error-budgets)에 있다.

마무리에서는 약점을 먼저 꺼낸다. 가상화는 페이지 내 검색과 화면 낭독기에 비용이 있다. 오래 스크롤하면 저장소에 글이 수천 개 쌓이니, 화면에서 멀어진 글의 본문은 버리고 id만 남기는 정리가 필요하다. 그런데 본문을 버리면 뒤로 가기로 돌아왔을 때 다시 받아야 하니 앞에서 본 위치 복원과 부딪친다. 이 셋을 말하고 각각의 대응을 붙이면 면접관이 꺼낼 꼬리 질문을 먼저 닫을 수 있다.

## 면접에서 나올 만한 질문

### 피드 API는 어떤 모양이 좋나요?

화면이 한 번에 그릴 수 있게 글, 작성자, 사진 크기, 좋아요 수와 내가 눌렀는지, 버전, 다음 커서를 한 응답에 담는다. 따로 물으면 글 10개에 요청이 수십 개가 된다. 페이지는 오프셋이 아니라 커서로 넘겨야 스크롤 중 새 글이 들어와도 겹치지 않는다. 사진의 원본 크기는 레이아웃 이동을 막고 가상화의 높이 추정을 정확하게 한다.

### 무한 스크롤에서 글이 계속 쌓이면 어떤 문제가 생기고 어떻게 푸나요?

DOM이 커져 렌더링과 스타일 계산이 느려진다. 실험에서 글 5,000개를 다 그리면 요소가 5만 개, CPU를 네 배 느리게 한 조건에서 첫 프레임까지 3.9초가 걸렸고, 보이는 줄만 그리는 가상화는 요소 137개, 59ms였다. 글마다 높이가 다르니 실제로는 추정 높이로 자리를 잡고 그린 뒤 재서 고치는 라이브러리를 쓴다. 대신 페이지 내 검색과 화면 낭독기의 전체 개수 파악에 비용이 있어 aria-setsize 같은 보완이 필요하다.

### 다음 페이지는 언제 불러야 하나요?

바닥에 닿기 전에 부른다. 한 페이지를 받는 시간과 사용자가 스크롤하는 속도를 곱한 거리보다 앞에서 부르면 기다림이 없다. 실험에서 rootMargin 0px은 페이지마다 약 0.4초씩 세 번 기다렸고, 1000px 앞에서 부르면 한 번으로 줄었다. 너무 앞에서 부르면 보지 않을 데이터를 받으니 측정해서 정한다.

### 사진 때문에 레이아웃이 밀리는 문제는 어떻게 막나요?

img에 원본 width와 height를 주고 CSS로 너비 100%, 높이 auto를 준다. 브라우저가 비율로 자리를 미리 잡아 사진이 늦게 와도 아래 글이 밀리지 않는다. 실험에서 크기를 주지 않으면 CLS가 0.649였고 주면 0이었다. 그래서 피드 응답에 사진 크기를 넣는다.

### 사용자가 스크롤 중일 때 새 글이 오면 어떻게 하나요?

바로 끼워 넣지 않고 "새 글 n개" 띠를 띄운 뒤 사용자가 누를 때 붙인다. 위에 끼워 넣으면 읽던 글이 밀린다. 크롬 계열의 스크롤 앵커링은 실험에서 스크롤 위치를 453px 보정해 읽던 글을 지켰지만, 끄면 다른 글이 보였고 모든 브라우저가 지원한다고 기대할 수 없다. 사용자가 이미 맨 위에 있을 때만 바로 붙인다.

### 글을 열었다 뒤로 오면 맨 위로 튕기는 이유는요?

브라우저가 뒤로 가기 직후 스크롤을 복원하려 할 때 목록이 아직 비어 있어 높이가 없기 때문이다. 실험에서 돌아올 때 목록을 다시 받으면 6,030px에서 0으로 튕겼고, 받아 둔 목록을 바로 그리고 기록해 둔 위치로 옮기면 그대로였다. 목록 데이터를 캐시에 남겨 두고, 필요하면 scrollRestoration을 manual로 두고 직접 옮긴다. 가상화 목록이면 줄 높이도 함께 기억한다.

### 좋아요는 어떻게 구현하나요?

정규화한 저장소의 글 칸을 바로 바꾸는 낙관적 업데이트로 하고, 실패하면 되돌린다. 빠르게 여러 번 누르면 응답 순서가 뒤집힐 수 있으니 응답의 버전을 비교하거나 같은 글의 요청을 한 줄로 세운다. 연타는 마지막 상태만 잠깐 뒤에 보내면 요청이 줄어든다. 다른 사람들의 좋아요 수는 화면에 다시 들어올 때 서버 값으로 맞춘다.

### 피드가 잘 동작하는지는 어떤 숫자로 보나요?

첫 글이 보이는 시간과 LCP, 좋아요의 INP, CLS, 스크롤 중 바닥에서 기다린 횟수와 시간, 피드 요청 실패율과 에러율을 사용자 기기에서 모은다. 기기 등급, 네트워크, 배포 버전으로 나눠 봐야 느린 사용자가 평균에 가려지지 않는다. 각 숫자에 목표를 두면 그게 이 화면의 SLO가 되고, 넘긴 몫으로 무엇을 고칠지 정한다.
