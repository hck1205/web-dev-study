사내 시스템에 두 가지 화면을 만든다. 하나는 급여 상위 3명을 보여 주는 표이고, 다른 하나는 사장부터 말단까지 들여쓰기로 내려가는 조직도다. 첫 번째는 쉬워 보인다. Oracle에서 `WHERE ROWNUM <= 3 ORDER BY sal DESC`라고 쓰면 될 것 같다. 돌려 보면 상위 3명이 아니라 엉뚱한 3명이 나온다. 두 번째는 `EMP` 테이블의 `mgr`(상사 사번)을 따라 몇 단계를 내려가야 하는지 모르니 조인 몇 번으로는 안 된다.

이 글은 SQLD에서 함께 묶여 나오는 세 주제를 다룬다. 위에서 n개만 자르는 Top-N 쿼리, 부모와 자식을 따라가는 계층형 쿼리, 행을 열로 돌리는 PIVOT이다. 끝에 정규 표현식 함수도 짧게 본다.

예제는 SCOTT의 `EMP` 14명이다. 데이터는 [SQLD 서브쿼리와 집합 연산자](/posts/sqld-subquery-set-operators) 글 앞부분에 있다. SQLD는 Oracle 문법으로 나오고, 이 글의 세 주제는 DB마다 문법 차이가 가장 큰 부분이다. Oracle 문법을 먼저 쓰고 SQL Server와 PostgreSQL 16의 방식을 나란히 둔다. 결과는 PostgreSQL 16.15에서 같은 뜻의 쿼리를 돌린 출력이고, Oracle 전용 문법은 결과가 같다는 것을 그렇게 확인했다.

## ROWNUM은 정렬보다 먼저 붙는다

`ROWNUM`은 Oracle이 결과 행에 1부터 붙여 주는 가상 컬럼이다. 함정은 번호가 붙는 시점이다. `ROWNUM`은 테이블에서 행을 읽어 WHERE를 통과할 때 붙고, `ORDER BY`는 그다음에 실행된다.

```sql
-- Oracle: 상위 3명을 뽑으려던 쿼리
SELECT ename, sal
FROM emp
WHERE ROWNUM <= 3
ORDER BY sal DESC;
```

행을 읽는 순서는 저장된 순서를 따르고 정해져 있지 않다. 행이 사번 순으로 읽혔다고 하면 처음 세 명은 SMITH, ALLEN, WARD다. 그 셋을 정렬한 결과가 나온다. PostgreSQL에서 "사번 순으로 읽어 3명에서 멈추고 그다음 정렬"을 그대로 흉내 내면 이렇다.

```sql
SELECT ename, sal
FROM (SELECT ename, sal, ROW_NUMBER() OVER (ORDER BY empno) AS rn FROM emp) t
WHERE rn <= 3            -- 읽은 순서대로 3명에서 자르고
ORDER BY sal DESC;       -- 그 셋만 정렬한다
```

```text
 ename | sal
-------+------
 ALLEN | 1600
 WARD  | 1250
 SMITH |  800
(3 rows)
```

급여 1위 KING(5000)이 없다. 아래 그림에서 다음을 누르면 `ROWNUM`이 붙는 순서가 나온다.

바른 방법은 정렬을 인라인 뷰 안에 넣고, 바깥에서 `ROWNUM`으로 자르는 것이다. 안쪽에서 정렬이 끝난 결과를 바깥에서 위부터 읽으며 번호를 붙이니, 번호가 곧 급여 순위가 된다.

```sql
-- Oracle: 정렬 먼저, 자르기는 바깥에서
SELECT ename, sal
FROM (SELECT ename, sal FROM emp ORDER BY sal DESC)
WHERE ROWNUM <= 3;
```

PostgreSQL에서는 `LIMIT`이나 표준 문법 `FETCH FIRST`로 쓴다. 정렬한 뒤 자른다.

```sql
SELECT ename, sal
FROM emp
ORDER BY sal DESC
FETCH FIRST 3 ROWS ONLY;     -- PostgreSQL: LIMIT 3 과 같다
```

```text
 ename | sal
-------+------
 KING  | 5000
 SCOTT | 3000
 FORD  | 3000
(3 rows)
```

`ROWNUM`에는 함정이 하나 더 있다. `WHERE ROWNUM = 2`나 `WHERE ROWNUM > 1`은 0행이다. 첫 행이 읽히면 ROWNUM 1을 받는데, 조건 `= 2`를 만족하지 못해 버려진다. 다음 행도 아직 통과한 행이 없으니 다시 1을 받고 또 버려진다. 끝까지 아무도 2가 되지 못한다. `ROWNUM = 1`과 `ROWNUM <= n`만 의미가 있다.

그래서 4~6위처럼 중간을 자르려면 번호를 컬럼으로 고정해 두고 한 번 더 감싼다.

```sql
-- Oracle: 4~6위
SELECT ename, sal
FROM (SELECT ROWNUM AS rn, a.*                       -- 번호를 컬럼으로 박제한다
      FROM (SELECT ename, sal FROM emp ORDER BY sal DESC) a
      WHERE ROWNUM <= 6)
WHERE rn >= 4;
```

PostgreSQL은 `OFFSET`으로 쓴다. Oracle 12c 이상도 같은 문법을 받는다.

```sql
SELECT ename, sal
FROM emp
ORDER BY sal DESC, empno
OFFSET 3 ROWS FETCH NEXT 3 ROWS ONLY;
```

```text
 ename | sal
-------+------
 JONES | 2975
 BLAKE | 2850
 CLARK | 2450
(3 rows)
```

## 동점자까지 보여 주는 WITH TIES

상위 2명을 뽑으면 KING 다음이 SCOTT일까 FORD일까. 둘 다 3000이다. 정렬 기준이 `sal`뿐이면 누가 2위가 될지 정해져 있지 않다. 동점자를 모두 포함하라는 요구라면 `WITH TIES`를 쓴다. 마지막 행과 정렬 값이 같은 행을 모두 더 가져온다.

```sql
SELECT ename, sal
FROM emp
ORDER BY sal DESC
FETCH FIRST 2 ROWS WITH TIES;    -- Oracle 12c+, PostgreSQL 13+
```

```text
 ename | sal
-------+------
 KING  | 5000
 FORD  | 3000
 SCOTT | 3000
(3 rows)
```

2행을 요청했는데 3행이 나왔다. 동점자 사이의 순서(FORD와 SCOTT)는 여전히 정해져 있지 않다. SQL Server는 `TOP`으로 같은 일을 한다.

```sql
-- SQL Server
SELECT TOP (2) WITH TIES ename, sal
FROM emp
ORDER BY sal DESC;               -- WITH TIES는 ORDER BY가 반드시 있어야 한다
```

`TOP (2)`만 쓰면 2행으로 자르고, `WITH TIES`를 붙이면 위와 같은 3행이 나온다. `TOP`은 `ORDER BY`보다 나중에 적용되니 `ROWNUM` 같은 함정이 없다. 반대로 동점자 없이 정확히 2명이 필요하면 정렬에 고유 컬럼을 더한다(`ORDER BY sal DESC, empno`).

윈도우 함수로도 Top-N을 만든다. 부서별 상위 n명처럼 묶음마다 자를 때는 이게 유일한 방법이다. `RANK`를 쓰면 동점 포함, `ROW_NUMBER`를 쓰면 정확히 n명이다. [SQLD 윈도우 함수](/posts/sqld-window-functions) 글의 마지막 절에 예제가 있다.

## 상사를 따라 내려가는 계층형 쿼리

이제 조직도다. `EMP`의 각 행은 `mgr`에 자기 상사의 `empno`를 들고 있다. 한 테이블 안에 부모와 자식이 같이 있는 구조라, 같은 테이블을 자기 자신과 조인하면(셀프 조인) 한 단계 위 상사는 바로 붙일 수 있다.

```sql
SELECT e.ename, m.ename AS mgr_name
FROM emp e
LEFT JOIN emp m ON m.empno = e.mgr     -- 사원 e의 상사 m
ORDER BY e.empno;
```

```text
 ename  | mgr_name
--------+----------
 SMITH  | FORD
 ALLEN  | BLAKE
 WARD   | BLAKE
 JONES  | KING
 MARTIN | BLAKE
 BLAKE  | KING
 CLARK  | KING
 SCOTT  | JONES
 KING   |
 TURNER | BLAKE
 ADAMS  | SCOTT
 JAMES  | BLAKE
 FORD   | JONES
 MILLER | CLARK
(14 rows)
```

`LEFT JOIN`이라서 상사가 없는 KING도 남았다. 하지만 SMITH의 상사의 상사의 상사까지 가려면 조인을 세 번 더 해야 하고, 몇 단계가 있는지 미리 알아야 한다. Oracle에는 이럴 때 쓰는 전용 문법 `CONNECT BY`가 있다.

```sql
-- Oracle
SELECT LEVEL,
       LPAD(' ', 4 * (LEVEL - 1)) || ename AS org_chart,   -- 단계만큼 들여쓰기
       empno, mgr
FROM emp
START WITH mgr IS NULL              -- 뿌리: 상사가 없는 사람
CONNECT BY PRIOR empno = mgr        -- 부모의 empno = 자식의 mgr
ORDER SIBLINGS BY ename;            -- 같은 부모 아래 형제끼리만 이름순
```

마지막 단계의 역방향 쿼리는 이렇게 쓴다. 이때 LEVEL은 시작점 SMITH가 1이다.

```sql
-- Oracle: SMITH에서 위로
SELECT LEVEL, ename, empno, mgr
FROM emp
START WITH ename = 'SMITH'
CONNECT BY PRIOR mgr = empno;   -- 자식(이미 찾은 행)의 mgr = 부모의 empno
```

```text
 level | ename | empno | mgr
-------+-------+-------+------
     1 | SMITH |  7369 | 7902
     2 | FORD  |  7902 | 7566
     3 | JONES |  7566 | 7839
     4 | KING  |  7839 |
(4 rows)
```

`PRIOR`가 어느 쪽에 붙느냐로 방향이 정해지고, `=`의 좌우를 바꾸는 것은 상관없다. `PRIOR empno = mgr`과 `mgr = PRIOR empno`는 같은 뜻이다.

## 계층형 쿼리가 주는 가상 컬럼

Oracle은 계층형 쿼리에서 쓸 수 있는 함수와 가상 컬럼을 몇 개 더 준다. JONES 아래만 보면서 확인하자.

```sql
-- Oracle
SELECT LEVEL,
       ename,
       CONNECT_BY_ROOT ename          AS root,     -- 이 행의 뿌리
       SYS_CONNECT_BY_PATH(ename, '/') AS path,     -- 뿌리부터 지금까지 경로
       CONNECT_BY_ISLEAF              AS is_leaf   -- 부하가 없으면 1
FROM emp
START WITH ename = 'JONES'
CONNECT BY PRIOR empno = mgr
ORDER SIBLINGS BY ename;
```

```text
 level | ename | root  |        path        | is_leaf
-------+-------+-------+--------------------+---------
     1 | JONES | JONES | /JONES             |       0
     2 | FORD  | JONES | /JONES/FORD        |       0
     3 | SMITH | JONES | /JONES/FORD/SMITH  |       1
     2 | SCOTT | JONES | /JONES/SCOTT       |       0
     3 | ADAMS | JONES | /JONES/SCOTT/ADAMS |       1
(5 rows)
```

`CONNECT_BY_ROOT`는 뿌리 행의 값이라 모든 행이 JONES다. `START WITH mgr = 7839`로 부서장 셋을 각각 뿌리로 삼으면 뿌리별로 부하 수를 셀 수 있다. BLAKE 6명, CLARK 2명, JONES 5명(자기 포함)이다. `SYS_CONNECT_BY_PATH`의 경로는 구분자로 시작한다는 점을 기억한다(`/JONES`). `CONNECT_BY_ISLEAF`는 부하가 없는 잎에서 1이다.

데이터에 순환이 있으면(예: A의 상사가 B이고 B의 상사가 A) Oracle은 오류를 낸다. `CONNECT BY NOCYCLE`을 쓰면 순환을 만나는 지점에서 멈추고, `CONNECT_BY_ISCYCLE`이 그 행에 1을 표시한다.

## WHERE에 거는 조건과 CONNECT BY에 거는 조건

계층형 쿼리에서 조건을 어디에 쓰느냐에 따라 결과가 크게 다르다. JONES를 빼고 조직도를 그리는 두 가지 방법을 보자.

```sql
-- Oracle 1) WHERE: 나무를 다 만든 뒤 JONES 한 행만 지운다
SELECT LEVEL, LPAD(' ', 4 * (LEVEL - 1)) || ename AS name
FROM emp
WHERE ename <> 'JONES'
START WITH mgr IS NULL
CONNECT BY PRIOR empno = mgr
ORDER SIBLINGS BY ename;
```

```text
 level |       name
-------+-------------------
     1 | KING
     2 |     BLAKE
     3 |         ALLEN
     3 |         JAMES
     3 |         MARTIN
     3 |         TURNER
     3 |         WARD
     2 |     CLARK
     3 |         MILLER
     3 |         FORD
     4 |             SMITH
     3 |         SCOTT
     4 |             ADAMS
(13 rows)
```

```sql
-- Oracle 2) CONNECT BY: JONES로는 내려가지 않는다. 그 아래도 같이 사라진다
SELECT LEVEL, LPAD(' ', 4 * (LEVEL - 1)) || ename AS name
FROM emp
START WITH mgr IS NULL
CONNECT BY PRIOR empno = mgr AND ename <> 'JONES'
ORDER SIBLINGS BY ename;
```

```text
 level |      name
-------+----------------
     1 | KING
     2 |     BLAKE
     3 |         ALLEN
     3 |         JAMES
     3 |         MARTIN
     3 |         TURNER
     3 |         WARD
     2 |     CLARK
     3 |         MILLER
(9 rows)
```

WHERE는 계층 전개가 끝난 결과에서 행을 거른다. 그래서 JONES만 빠지고 FORD와 SCOTT은 LEVEL 3 그대로 남는다(부모가 안 보이는 고아 행처럼 보인다). `CONNECT BY`에 쓴 조건은 자식을 찾는 연결 조건이라, JONES를 자식으로 잇지 않으니 JONES 아래 가지 전체(FORD, SMITH, SCOTT, ADAMS)가 잘려 9행이 된다. `START WITH`의 조건은 뿌리 고르기에만 쓰인다. 셋의 처리 순서는 `START WITH` → `CONNECT BY` → `WHERE`다.

## PostgreSQL과 SQL Server는 재귀 CTE로 쓴다

`CONNECT BY`는 Oracle 전용이다. 표준 SQL은 자기 자신을 참조하는 CTE(WITH 절)로 계층을 푼다. PostgreSQL은 `WITH RECURSIVE`, SQL Server는 `RECURSIVE` 없이 `WITH`만 쓴다. Oracle도 11g R2부터 이 방식을 지원한다.

```sql
-- PostgreSQL 16
WITH RECURSIVE org AS (
  -- 1) 앵커: 뿌리 행 (START WITH에 해당)
  SELECT empno, ename, mgr,
         1                  AS lvl,
         ARRAY[ename::text] AS path          -- 형제 정렬과 경로용
  FROM emp
  WHERE mgr IS NULL
  UNION ALL
  -- 2) 재귀: 직전 단계 결과(org)의 부하를 찾는다 (CONNECT BY에 해당)
  SELECT e.empno, e.ename, e.mgr,
         o.lvl + 1,
         o.path || e.ename::text
  FROM emp e
  JOIN org o ON e.mgr = o.empno              -- PRIOR empno = mgr
)
SELECT lvl, repeat('    ', lvl - 1) || ename AS org_chart, empno, mgr,
       '/' || array_to_string(path, '/') AS path,
       CASE WHEN EXISTS (SELECT 1 FROM emp c WHERE c.mgr = org.empno)
            THEN 0 ELSE 1 END AS is_leaf     -- CONNECT_BY_ISLEAF
FROM org
ORDER BY path;                               -- ORDER SIBLINGS BY ename 효과
```

```sql
WITH RECURSIVE org AS (
  SELECT empno, ename, mgr, 1 AS lvl FROM emp WHERE mgr IS NULL
  UNION ALL
  SELECT e.empno, e.ename, e.mgr, o.lvl + 1 FROM emp e JOIN org o ON e.mgr = o.empno
) SEARCH DEPTH FIRST BY ename SET ord
SELECT lvl, repeat('  ', lvl - 1) || ename AS name FROM org ORDER BY ord;
```

결과는 위 조직도와 같은 순서의 14행이다. 같은 위치에 `CYCLE empno SET is_cycle USING path`를 쓰면 `NOCYCLE`처럼 순환을 끊는다. 재귀 CTE에서 순환이 있는데 막지 않으면 끝나지 않는 쿼리가 된다. SQL Server는 기본으로 재귀를 100단계에서 끊는다(`OPTION (MAXRECURSION n)`으로 바꾼다).

</Callout>

## 행을 열로 돌리는 PIVOT

이번엔 직무별, 부서별 급여 합계를 표로 만든다. `GROUP BY job, deptno`는 9행이 세로로 나오는데, 보고서는 직무를 행으로, 부서를 열로 원한다. 행의 값(10, 20, 30)을 열 이름으로 돌리는 게 PIVOT이다. Oracle 11g와 SQL Server 2005부터 지원한다.

```sql
-- Oracle
SELECT *
FROM (SELECT job, deptno, sal FROM emp)                -- 필요한 컬럼만 고른다
PIVOT (SUM(sal) FOR deptno IN (10 AS d10, 20 AS d20, 30 AS d30))
ORDER BY job;
```

```sql
-- SQL Server
SELECT job, [10] AS d10, [20] AS d20, [30] AS d30
FROM (SELECT job, deptno, sal FROM emp) AS s
PIVOT (SUM(sal) FOR deptno IN ([10], [20], [30])) AS p
ORDER BY job;
```

PostgreSQL에는 `PIVOT`이 없다. 조건부 집계로 같은 표를 만든다. `FILTER`는 PostgreSQL 문법이고, `CASE`를 쓰면 어느 DB에서나 된다.

```sql
SELECT job,
       SUM(sal) FILTER (WHERE deptno = 10) AS d10,   -- = SUM(CASE WHEN deptno = 10 THEN sal END)
       SUM(sal) FILTER (WHERE deptno = 20) AS d20,
       SUM(sal) FILTER (WHERE deptno = 30) AS d30
FROM emp
GROUP BY job
ORDER BY job;
```

```text
    job    | d10  | d20  | d30
-----------+------+------+------
 ANALYST   |      | 6000 |
 CLERK     | 1300 | 1900 |  950
 MANAGER   | 2450 | 2975 | 2850
 PRESIDENT | 5000 |      |
 SALESMAN  |      |      | 5600
(5 rows)
```

빈칸은 그 조합에 사원이 없어서 `SUM`이 NULL을 낸 자리다. `COUNT`로 집계하면 빈 자리에 0이 나온다.

PIVOT에는 이 결과를 이해하는 데 꼭 필요한 규칙이 있다. `FOR`에 쓴 컬럼(`deptno`)과 집계하는 컬럼(`sal`)을 뺀 나머지 컬럼이 전부 자동으로 GROUP BY 기준이 된다. 그래서 인라인 뷰로 `job, deptno, sal`만 골랐다. 인라인 뷰 없이 `FROM emp PIVOT (...)`라고 쓰면 `empno, ename, job, mgr, hiredate, comm`이 모두 묶음 기준이 되고, `empno`가 사람마다 다르니 14행이 나온다. 표가 접히지 않고 사원마다 한 칸에만 값이 찬 결과다. PostgreSQL로 그 묶음 수를 세어 보면 14다.

```sql
SELECT COUNT(*)
FROM (SELECT 1 FROM emp GROUP BY empno, ename, job, mgr, hiredate, comm) t;
```

```text
 count
-------
    14
(1 row)
```

`IN` 목록의 값은 쿼리를 쓸 때 정해 둬야 한다. 부서가 새로 생기면 쿼리를 고쳐야 한다. 값 목록이 바뀌는 피벗은 SQL보다 애플리케이션이나 리포트 도구에서 돌리는 편이 낫다.

## 열을 행으로 되돌리는 UNPIVOT

`UNPIVOT`은 반대다. 위의 피벗 표(`d10`, `d20`, `d30` 열)를 `(job, deptno, sal)` 행으로 펼친다. 피벗 결과가 `job_sal`이라는 테이블에 저장돼 있다고 하자.

```sql
-- Oracle
SELECT job, deptno, sal
FROM job_sal
UNPIVOT (sal FOR deptno IN (d10 AS 10, d20 AS 20, d30 AS 30))
ORDER BY job, deptno;
```

`sal`은 값이 들어갈 새 컬럼, `deptno`는 원래 열 이름(을 바꾼 값)이 들어갈 새 컬럼이다. PostgreSQL에서는 `LATERAL`과 `VALUES`로 행마다 세 줄을 만든다.

```sql
WITH job_sal AS (
  SELECT job,
         SUM(sal) FILTER (WHERE deptno = 10) AS d10,
         SUM(sal) FILTER (WHERE deptno = 20) AS d20,
         SUM(sal) FILTER (WHERE deptno = 30) AS d30
  FROM emp GROUP BY job
)
SELECT j.job, u.deptno, u.sal
FROM job_sal j
CROSS JOIN LATERAL (VALUES (10, j.d10), (20, j.d20), (30, j.d30)) AS u(deptno, sal)
WHERE u.sal IS NOT NULL            -- Oracle UNPIVOT의 기본 동작 (EXCLUDE NULLS)
ORDER BY j.job, u.deptno;
```

```text
    job    | deptno | sal
-----------+--------+------
 ANALYST   |     20 | 6000
 CLERK     |     10 | 1300
 CLERK     |     20 | 1900
 CLERK     |     30 |  950
 MANAGER   |     10 | 2450
 MANAGER   |     20 | 2975
 MANAGER   |     30 | 2850
 PRESIDENT |     10 | 5000
 SALESMAN  |     30 | 5600
(9 rows)
```

5행 × 3열 = 15칸 중 값이 있는 9칸만 나왔다. Oracle `UNPIVOT`은 기본적으로 NULL 칸을 버린다. `UNPIVOT INCLUDE NULLS`라고 쓰면 15행이 다 나온다(PostgreSQL에서는 위의 WHERE를 지우면 15행이다). 원래의 `GROUP BY job, deptno` 결과 9행과 같다. 피벗하고 언피벗하면 집계된 상태로 돌아올 뿐, 사원 14명의 원래 행으로 돌아오지는 않는다.

## 패턴으로 찾는 정규 표현식 함수

`LIKE`는 `%`와 `_`만 쓸 수 있다. "A나 S로 시작", "L이 두 번 연속" 같은 패턴은 정규 표현식 함수로 찾는다. Oracle 10g부터 있었고, PostgreSQL도 15부터 같은 이름의 함수를 지원해서 아래 쿼리는 그대로 돌아간다.

```sql
SELECT ename FROM emp WHERE REGEXP_LIKE(ename, '^[AS]') ORDER BY ename;   -- A 또는 S로 시작
SELECT ename FROM emp WHERE REGEXP_LIKE(ename, 'L{2}') ORDER BY ename;    -- L이 연속 두 번
SELECT ename FROM emp WHERE REGEXP_LIKE(ename, '^.{4}$') ORDER BY ename;  -- 정확히 네 글자
```

```text
 ename
-------
 ADAMS
 ALLEN
 SCOTT
 SMITH
(4 rows)

 ename
--------
 ALLEN
 MILLER
(2 rows)

 ename
-------
 FORD
 KING
 WARD
(3 rows)
```

`^`는 시작, `$`는 끝, `.`은 아무 글자 하나, `[AS]`는 A나 S 중 하나, `{2}`는 앞 패턴의 두 번 반복이다. 값을 꺼내거나 바꿀 때는 `REGEXP_SUBSTR`, `REGEXP_REPLACE`, `REGEXP_COUNT`를 쓴다.

```sql
SELECT REGEXP_SUBSTR('010-1234-5678', '[0-9]+', 1, 2)        AS mid,     -- 1번째 글자부터, 2번째 일치
       REGEXP_REPLACE('010-1234-5678', '[0-9]{4}$', '****')  AS masked;  -- 끝 네 자리 가리기
```

```text
 mid  |    masked
------+---------------
 1234 | 010-1234-****
(1 row)
```

PostgreSQL에서는 `ename ~ '^[AS]'`처럼 `~` 연산자로도 쓴다. SQL Server는 오랫동안 정규 표현식 함수가 없어서 `LIKE '[AS]%'` 같은 제한된 패턴만 썼고, 2025 버전에 와서 `REGEXP_LIKE` 같은 함수가 들어왔다. 정규 표현식 조건은 일반 B-tree 인덱스를 타지 못하니, 큰 테이블에서는 조회 대상을 먼저 줄인 뒤에 쓴다.

## SQLD 시험 포인트

- `ROWNUM`은 WHERE를 통과할 때 붙고 `ORDER BY`보다 먼저다. 상위 N은 정렬한 인라인 뷰 바깥에서 `ROWNUM <= N`.
- `ROWNUM = 1`과 `ROWNUM <= N`은 되지만 `ROWNUM = 2`, `ROWNUM > 1`은 0행이다.
- SQL Server `TOP (N)`은 `ORDER BY` 뒤에 적용된다. `WITH TIES`는 마지막 값과 같은 동점 행을 더 포함하고, `ORDER BY`가 필수다. Oracle 12c+는 `FETCH FIRST N ROWS ONLY | WITH TIES`, `OFFSET`.
- 계층형 쿼리: `START WITH`(뿌리) → `CONNECT BY`(연결) → `WHERE`(거르기) 순서. `PRIOR 자식 = 부모`(예: `PRIOR empno = mgr`)는 순방향(위 → 아래), `PRIOR 부모 = 자식`(`PRIOR mgr = empno`)은 역방향.
- `LEVEL`은 뿌리가 1. `ORDER SIBLINGS BY`는 계층을 유지한 채 형제끼리 정렬. `CONNECT_BY_ROOT`, `SYS_CONNECT_BY_PATH`(경로가 구분자로 시작), `CONNECT_BY_ISLEAF`(잎이면 1), `NOCYCLE`/`CONNECT_BY_ISCYCLE`.
- WHERE 조건은 해당 행만 빠지고, CONNECT BY 조건은 그 아래 가지 전체가 빠진다. EMP에서 JONES 제외 시 13행과 9행.
- `START WITH`를 생략하면 모든 행이 뿌리가 된다.
- PIVOT은 `FOR` 컬럼과 집계 컬럼을 뺀 나머지가 GROUP BY 기준이 된다. 그래서 인라인 뷰로 컬럼을 줄인다. UNPIVOT은 기본적으로 NULL을 제외(`INCLUDE NULLS`로 포함).
- `REGEXP_LIKE`, `REGEXP_SUBSTR(문자, 패턴, 시작, 몇 번째)`, `REGEXP_REPLACE`, `REGEXP_COUNT`. `^`, `$`, `.`, `[]`, `{n}`, `+`, `*`.

## 면접에서 나올 만한 질문

### Oracle에서 ROWNUM으로 상위 N개를 뽑을 때 흔한 실수는요?

`WHERE ROWNUM <= 3 ORDER BY sal DESC`처럼 같은 쿼리에 쓰는 것이다. `ROWNUM`은 행이 WHERE를 통과할 때 붙고 정렬은 그 뒤라서, 먼저 읽힌 3행을 고른 뒤에 정렬한다. 정렬을 인라인 뷰에 넣고 바깥에서 `ROWNUM`으로 자르거나, 12c 이상이면 `FETCH FIRST 3 ROWS ONLY`를 쓴다. 또 `ROWNUM = 2`는 항상 0행이라 중간 구간은 번호를 컬럼으로 고정한 뒤 한 번 더 감싸서 거른다.

### 상위 N개에서 동점자는 어떻게 처리하나요?

요구 사항에 따라 정한다. 동점자를 모두 보여야 하면 `FETCH FIRST N ROWS WITH TIES`, SQL Server의 `TOP (N) WITH TIES`, 또는 `RANK() <= N`을 쓴다. 예제에서 상위 2명을 `WITH TIES`로 뽑으니 3000 동점 때문에 3명이 나왔다. 정확히 N명이 필요하면 정렬에 기본 키 같은 고유 컬럼을 더해 순서를 확정하고 `ROW_NUMBER`나 `FETCH FIRST ... ONLY`를 쓴다. 정렬이 확정되지 않으면 같은 쿼리가 실행마다 다른 사람을 줄 수 있다.

### CONNECT BY에서 PRIOR의 위치는 무엇을 뜻하나요?

`PRIOR`가 붙은 컬럼은 이미 찾은 부모 행의 값이다. `PRIOR empno = mgr`은 "부모의 사번과 같은 mgr을 가진 행을 자식으로"라서 위에서 아래로 내려가고, `PRIOR mgr = empno`는 "지금 행의 상사 사번과 같은 empno를 가진 행"이라 위로 올라간다. `=` 양쪽을 바꿔 쓰는 건 상관없고 `PRIOR`가 어느 컬럼에 붙었는지만 본다. 시작점은 `START WITH`로 정하고, 같은 부모 아래 순서는 `ORDER SIBLINGS BY`로 정한다.

### 계층형 쿼리에서 WHERE 조건과 CONNECT BY 조건의 차이는요?

WHERE는 계층을 다 만든 뒤 결과 행을 하나씩 거르고, CONNECT BY에 쓴 조건은 자식을 잇는 단계에서 적용된다. 그래서 WHERE로 JONES를 빼면 JONES 한 행만 사라지고 부하들은 남지만, CONNECT BY에 넣으면 JONES로 내려가지 않아 그 아래 가지 전체가 사라진다. EMP에서는 13행과 9행으로 갈렸다. 특정 부서만 보고 싶은지, 특정 조직 가지를 통째로 빼고 싶은지에 따라 위치를 고른다.

### Oracle 외의 DB에서는 계층 구조를 어떻게 조회하나요?

표준 재귀 CTE를 쓴다. 앵커 쿼리로 뿌리 행을 만들고, `UNION ALL` 아래의 재귀 쿼리가 직전 단계 결과와 테이블을 조인해 다음 단계를 만들며, 새 행이 안 나오면 멈춘다. PostgreSQL은 `WITH RECURSIVE`, SQL Server는 `WITH`만 쓰고, Oracle도 11g R2부터 지원한다. 재귀 CTE는 단계별로 행을 만들어서 조직도 순서가 필요하면 경로 배열이나 `SEARCH DEPTH FIRST BY`로 정렬하고, 데이터 순환에 대비해 `CYCLE` 절이나 깊이 제한을 둔다.

### 트리 구조를 저장하는 다른 방법도 있나요?

EMP처럼 부모 키를 들고 있는 방식(인접 리스트)이 가장 단순하고 수정이 쉽지만, 하위 전체를 읽으려면 재귀가 필요하다. `/KING/JONES/FORD`처럼 경로 문자열을 저장하면(경로 열거) 앞부분 일치 검색으로 하위를 한 번에 찾지만, 중간 노드가 옮겨지면 하위 경로를 모두 고쳐야 한다. 모든 조상-자손 쌍을 별도 테이블에 저장하는 클로저 테이블은 조회가 빠르고 쓰기와 저장 공간이 늘어난다. 깊이가 얕고 자주 바뀌면 인접 리스트와 재귀 CTE로 충분하다.

### PIVOT을 쓸 때 주의할 점은요?

`FOR` 컬럼과 집계 컬럼을 뺀 나머지 컬럼이 모두 자동으로 묶음 기준이 된다. 테이블을 통째로 넣으면 사번처럼 고유한 컬럼 때문에 행이 접히지 않으니, 인라인 뷰로 필요한 컬럼만 고른다. 그리고 `IN` 목록의 값을 쿼리에 미리 적어야 해서 값이 늘면 쿼리를 고쳐야 한다. PIVOT 문법이 없는 PostgreSQL에서는 `SUM(...) FILTER (WHERE ...)`나 `SUM(CASE WHEN ...)`로 같은 결과를 만든다.
