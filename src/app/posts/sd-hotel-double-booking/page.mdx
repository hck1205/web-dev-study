이 시리즈에서 이 글의 자리: 앞 글 [㊺ 광고 클릭 집계 ②](/posts/sd-ad-click-exactly-once)로 광고 클릭 집계를 마쳤다. 이 글부터 두 편은 호텔 예약 시스템을 설계한다. 이 글은 같은 방이 두 번 팔리는 이중 예약을 막는 데 집중한다. 같은 장의 다음 글 [㊼ 호텔 예약 시스템 설계 ②](/posts/sd-hotel-inventory-scaling)가 객실 유형별 재고 테이블, 캐시, 서비스 사이의 데이터 맞추기를 다루고, 그다음은 [㊽ 이메일 서비스 설계 ①](/posts/sd-email-protocols)이다.

크리스마스 이브에 디럭스 더블룸이 3개 남은 호텔이 있다. 예약 페이지를 열어 둔 손님 10명이 거의 같은 순간 "예약하기"를 눌렀다. 다음 날 아침 프런트에는 확정된 예약이 10건 있다. 방은 3개뿐인데 7명이 체크인하러 온다.

이 장면은 면접 문제 "호텔 예약 시스템을 설계하라"의 한가운데 있다. 화면과 API는 어렵지 않다. 어려운 건 "남은 방이 있나 확인하고, 있으면 잡는다"는 두 동작 사이의 틈이다. 이 글에서는 그 틈을 실제 PostgreSQL 16에서 열어 보고, 막는 방법 네 가지를 같은 조건에서 돌려 비교한다.

## 가장 작은 예약 시스템

처음에는 작게 시작한다. 호텔 체인이 하나 있고, 손님은 웹과 앱에서만 예약한다. 예약할 때 전액을 결제하고, 취소할 수 있다. 손님은 "1203호"가 아니라 "디럭스 더블 1개"를 예약한다. 방 번호는 체크인할 때 정해진다. 이렇게 방이 아니라 객실 유형을 파는 이유와 그에 맞춘 테이블 설계는 [다음 글](/posts/sd-hotel-inventory-scaling)에서 자세히 본다. 여기서는 테이블 두 개면 충분하다.

```sql
-- 호텔·객실 유형·날짜마다 한 줄: "이 날 이 유형은 몇 개 중 몇 개가 팔렸나"
CREATE TABLE room_type_inventory (
  hotel_id        int  NOT NULL,
  room_type_id    int  NOT NULL,
  date            date NOT NULL,
  total_inventory int  NOT NULL,          -- 팔 수 있는 방 수
  total_reserved  int  NOT NULL DEFAULT 0, -- 이미 팔린 방 수
  version         int  NOT NULL DEFAULT 0, -- 낙관적 잠금에서 쓴다
  PRIMARY KEY (hotel_id, room_type_id, date)
);

-- 예약 한 건에 한 줄
CREATE TABLE reservation (
  reservation_id text PRIMARY KEY,         -- 누가 만드는지가 뒤에서 중요해진다
  hotel_id       int  NOT NULL,
  room_type_id   int  NOT NULL,
  guest          text NOT NULL,
  check_in       date NOT NULL,
  check_out      date NOT NULL,            -- 이 날은 묵지 않는다
  room_count     int  NOT NULL,
  status         text NOT NULL DEFAULT 'pending',
  created_at     timestamptz NOT NULL DEFAULT now()
);
```

12월 24일에 들어와 26일에 나가는 손님은 24일과 25일 이틀 밤을 묵는다. 그래서 예약 하나가 재고 테이블의 두 줄을 건드린다. 예약 하나가 여러 줄을 고친다는 사실은 나중에 잠금 순서 문제로 돌아온다.

호텔 체인 하나라면 숫자는 작다. 객실 1만 개에 70%가 차고 평균 2박을 한다고 치면 하루 예약은 1만 × 0.7 ÷ 2 = 3,500건 정도다. 하루를 약 10만 초로 어림하면 초당 0.035건이다. 평균 부하는 걱정거리가 아니다. 문제는 평균이 아니라 같은 날짜, 같은 객실 유형에 요청이 몰리는 순간이다. 연휴 전날 밤, 할인 행사가 열린 직후가 그렇다.

## 같은 손님이 두 번 누른다

이중 예약에는 두 종류가 있다. 첫째는 손님 한 명이 같은 예약을 두 번 만드는 경우다. 버튼을 누르고 응답이 늦어 한 번 더 누르거나, 앱의 네트워크 라이브러리가 시간 초과 뒤 알아서 다시 보내거나, 결제 완료 화면에서 뒤로 가기를 눌러 폼이 다시 제출되는 경우다.

버튼을 누르면 회색으로 막는 것은 필요하지만 충분하지 않다. 앞의 세 경우 중 버튼으로 막을 수 있는 건 첫째뿐이다. 재시도는 화면 밖에서 일어난다. 그래서 서버가 "이 요청은 아까 그 요청"이라는 걸 알아야 한다.

먼저 서버가 예약 id를 만드는 흔한 구현으로 두 번 누르기를 재현했다. 손님 한 명 역할의 psql 세션 두 개를 같은 순간에 출발시켰다.

```sql
-- 서버가 id를 만든다: 요청마다 새 id가 붙는다
INSERT INTO reservation_serial (guest, check_in, check_out)
VALUES ('kim', '2026-12-24', '2026-12-26');
UPDATE room_type_inventory SET total_reserved = total_reserved + 1
 WHERE hotel_id = 1 AND room_type_id = 10
   AND date >= '2026-12-24' AND date < '2026-12-26';
```

```text
첫 클릭 created 105ms
둘째 클릭 created 52ms
예약 행: 2
재고: 2026-12-24 19/20, 2026-12-25 19/20
```

17개가 팔린 상태에서 시작했는데 19가 됐다. 손님은 방 하나를 원했는데 두 개가 잡혔고 결제도 두 번 나간다. 서버 입장에서 두 요청은 완전히 다른 요청이다. 구별할 근거가 없다.

고치는 방법은 예약 id를 서버가 요청을 받을 때가 아니라 주문서를 열 때 만들어 주는 것이다. 앱은 그 id를 들고 있다가 몇 번을 보내든 같은 id를 보낸다. 그리고 이 id를 `reservation` 테이블의 기본 키로 둔다. 이렇게 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같게 만드는 성질을 멱등성(idempotency)이라고 한다.

```sql
INSERT INTO reservation (reservation_id, hotel_id, room_type_id, guest, check_in, check_out, room_count)
VALUES ('7f3c9a2e-res', 1, 10, 'kim', '2026-12-24', '2026-12-26', 1)
ON CONFLICT (reservation_id) DO NOTHING   -- 이미 있으면 아무것도 하지 않는다
RETURNING reservation_id;                 -- 새로 넣었을 때만 한 줄이 돌아온다
-- 돌아온 줄이 없으면 재고를 건드리지 않고 기존 예약을 그대로 응답한다
```

```text
첫 클릭 created 52ms
둘째 클릭 duplicate -> 기존 예약을 돌려줌 53ms
예약 행: 1
재고: 2026-12-24 18/20, 2026-12-25 18/20
```

둘째 클릭이 53ms 걸린 것을 보자. 두 요청이 동시에 같은 기본 키를 넣으려 하면 PostgreSQL은 뒤의 것을 앞의 트랜잭션이 끝날 때까지 기다리게 한다. 앞의 것이 커밋되자 뒤의 것은 충돌로 판정되어 아무것도 하지 않았다. 앞의 것이 롤백됐다면 뒤의 것이 들어갔을 것이다. 그래서 "있나 먼저 SELECT해 보고 없으면 INSERT" 같은 확인 단계가 필요 없다. 그 확인 자체가 같은 틈을 다시 만든다.

`ON CONFLICT`를 쓰지 않고 그냥 INSERT하면 PostgreSQL은 이렇게 거절한다. 이 오류를 잡아 "이미 처리된 요청"으로 바꿔 응답해도 된다.

```text
ERROR:  duplicate key value violates unique constraint "reservation_pkey"
DETAIL:  Key (reservation_id)=(7f3c9a2e-res) already exists.
```

몇 가지를 더 정해야 한다. 같은 id로 내용이 다른 요청이 오면(날짜를 바꿔서) 그대로 옛 결과를 줄지 오류를 줄지, 처리 도중 서버가 죽으면 어떻게 되는지, 결제 결과까지 저장해 두고 그대로 돌려줄지다. 이런 문제와 응답 저장 방식은 [멱등성 키 구현](/posts/idempotency-key)에서 다뤘다. 호텔 예약에서는 예약 테이블의 기본 키가 그 역할을 겸한다.

## 마지막 세 방을 열 명이 노린다

두 번째 종류가 더 까다롭다. 서로 다른 손님이 같은 방을 동시에 잡는 경우다. 예약 id가 다르니 앞 절의 장치는 소용이 없다. 예약 서비스가 하는 일을 그대로 적으면 이렇다.

```sql
-- 1단계: 묵는 날짜의 재고를 읽는다
SELECT date, total_inventory, total_reserved
FROM room_type_inventory
WHERE hotel_id = 1 AND room_type_id = 10
  AND date >= '2026-12-24' AND date < '2026-12-26';

-- 앱: 모든 날짜에서 total_reserved + 1 <= total_inventory 인지 본다
--      가격을 계산하고 쿠폰을 확인한다 (실험에서는 30ms)

-- 2단계: 남았으면 잡는다
UPDATE room_type_inventory SET total_reserved = total_reserved + 1
 WHERE hotel_id = 1 AND room_type_id = 10
   AND date >= '2026-12-24' AND date < '2026-12-26';
INSERT INTO reservation VALUES (...);
```

손님 두 명, 남은 방 하나로 줄여서 시간 순서대로 보면 틈이 보인다.

이런 모양을 확인 후 실행(check-then-act) 경합이라고 부른다. 원리는 [경쟁 상태](/posts/race-conditions)에서 다뤘다. PostgreSQL의 기본 격리 수준인 READ COMMITTED는 각 문장이 실행되는 순간 커밋된 데이터를 보게 해 줄 뿐, 내가 읽은 값을 남이 바꾸지 못하게 막지는 않는다. 격리 수준마다 무엇을 막는지는 [트랜잭션과 격리 수준](/posts/db-transaction-isolation)에 있다.

실제로 돌려 봤다. 24일과 25일 모두 20개 중 17개가 팔린 상태로 두고, 손님 10명을 psql 세션 10개로 만들어 `pg_sleep_until`로 같은 순간에 출발시켰다. 앱이 하던 일은 세션마다 PL/pgSQL `DO` 블록으로 옮겼고, 가격 계산은 `pg_sleep(0.03)`으로 흉내 냈다. 방법마다 결과가 한 줄씩 나온다.

```text
naive      예약 10  매진  0  기타 0  충돌  0  평균   38ms  최대   45ms  예약 행 10  재고 1:2026-12-24=27/20 1:2026-12-25=27/20
```

방 3개에 10명이 예약했다. 재고는 27/20이다. 응답은 모두 빨랐고 오류는 하나도 없었다. 운영에서 이 버그가 무서운 이유가 여기 있다. 로그에는 아무것도 남지 않는다.

하나 짚을 것이 있다. 재고가 정확히 27로 올라간 건 `total_reserved = total_reserved + 1`처럼 DB 안에서 더했기 때문이다. UPDATE는 행을 고치기 직전에 최신 값을 다시 읽어서 더한다. 만약 앱이 읽은 값 17에 1을 더해 `SET total_reserved = 18`처럼 보냈다면, 10명 모두 18을 써서 재고는 18로 남는다. 방은 10개가 나갔는데 장부에는 1개만 적히는 갱신 손실이다. 이쪽이 더 나쁘다. 장부와 예약 기록이 서로 맞지 않아 나중에 찾기도 어렵다.

## 줄을 세운다: SELECT FOR UPDATE

첫 번째 해결책은 읽을 때부터 붙잡는 것이다. 1단계 SELECT 끝에 `FOR UPDATE`를 붙이면 읽은 행에 잠금이 걸리고, 같은 행을 `FOR UPDATE`로 읽으려는 다른 트랜잭션은 앞 트랜잭션이 커밋하거나 롤백할 때까지 기다린다. 충돌이 날 거라고 보고 미리 막으니 비관적 잠금(pessimistic locking)이라고 부른다.

```sql
SELECT date, total_inventory, total_reserved
FROM room_type_inventory
WHERE hotel_id = 1 AND room_type_id = 10
  AND date >= '2026-12-24' AND date < '2026-12-26'
ORDER BY date        -- 여러 날짜를 늘 같은 순서로 잠근다
FOR UPDATE;
```

기다리는 모습은 `pg_stat_activity`에서 바로 보인다. 잠금을 쥐는 시간을 400ms로 늘리고 손님 5명을 출발시킨 뒤, 그 사이에 다른 세션에서 조회했다.

ORDER BY xact_start;
```

-------+-----------------+---------------+---------------

(4 rows)
```

17363은 잠금을 쥔 채로 가격을 계산하는 중이다(`PgSleep`). 17360이 그 트랜잭션이 끝나기를 기다리고(`transactionid`), 나머지는 그 뒤에서 행 잠금 순서를 기다린다(`tuple`). `blocked_by`를 따라가면 줄의 맨 앞이 누구인지 나온다. 운영에서 "예약 API만 느리다"는 신고가 오면 이 쿼리부터 돌려 본다. 맨 앞 트랜잭션이 무엇을 하느라 오래 걸리는지 보면 대개 원인이 나온다. 잠금 대기를 읽는 법은 [비관적 잠금](/posts/pessimistic-locking)에 더 자세히 있다.

호텔 예약에서 특히 조심할 점이 두 가지다.

첫째, 잠금을 쥔 채로 결제를 부르지 않는다. 결제 회사 응답은 수백 ms에서 수 초까지 걸린다. 그동안 같은 날짜, 같은 객실 유형을 원하는 모든 손님이 줄을 선다. 방을 잡는 트랜잭션은 짧게 끝내고, 결제는 그 뒤에 따로 한다. 결제가 실패하면 잡은 방을 푸는 흐름은 [다음 글](/posts/sd-hotel-inventory-scaling)에서 다룬다.

둘째, 여러 날짜를 잠글 때는 늘 같은 순서로 잠근다. 위 쿼리의 `ORDER BY date`가 그 일을 한다. 손님 A는 24일 → 25일 순으로, 손님 B는 25일 → 24일 순으로 잠그면, 서로 상대가 쥔 행을 기다리다 둘 다 멈추는 교착 상태가 된다. PostgreSQL은 기본 1초(`deadlock_timeout`) 뒤 이를 찾아 한쪽을 `deadlock detected`로 끊는다. 교착 상태가 생기는 모양과 찾는 법은 [잠금과 교착 상태](/posts/db-locking-deadlock)에서 직접 재현했다.

## 버전을 보고 다시 한다: 낙관적 잠금

두 번째 해결책은 잠그지 않고, 쓰는 순간에 "내가 읽은 뒤로 바뀌었나"를 확인하는 것이다. 각 행에 `version` 열을 두고, 읽을 때 버전을 기억했다가 쓸 때 조건에 넣는다. 충돌이 드물 거라고 보고 일단 진행하니 낙관적 잠금(optimistic locking)이라고 부른다.

```sql
-- 읽을 때 버전을 같이 가져온다
SELECT date, total_inventory, total_reserved, version
FROM room_type_inventory
WHERE hotel_id = 1 AND room_type_id = 10
  AND date >= '2026-12-24' AND date < '2026-12-26'
ORDER BY date;
-- 24일 version=0, 25일 version=0 이었다고 하자

-- 쓸 때: 버전이 그대로일 때만 고친다. 날짜마다 한 줄씩
UPDATE room_type_inventory
   SET total_reserved = total_reserved + 1, version = version + 1
 WHERE hotel_id = 1 AND room_type_id = 10 AND date = '2026-12-24' AND version = 0;
-- UPDATE 0 이 나오면 누가 먼저 고친 것이다 → 전체를 롤백하고 처음부터 다시
```

실험에서는 충돌이 나면 처음부터 다시 읽어 최대 3번까지 시도하게 했다.

```text
optimistic 예약  3  매진  0  기타 7(gave_up,gave_up,gave_up,gave_up,gave_up,gave_up,gave_up)  충돌 24  평균   89ms  최대  102ms  예약 행 3  재고 1:2026-12-24=20/20 1:2026-12-25=20/20
```

재고는 정확하다. 그런데 7명이 매진이 아니라 "3번 시도하고 포기"로 끝났다. 충돌은 24번이다. 매 회차에 이긴 사람은 한 명뿐이기 때문이다.

방이 7개 남았는데 7명이 예약에 실패했다. 낙관적 잠금은 몰리는 곳에서 이렇게 무너진다. 재시도 횟수를 늘리거나 재시도 사이에 무작위로 기다리면 나아지지만, 그만큼 응답이 늦어지고 DB는 버려질 작업을 계속 한다. 반대로 요청이 여러 호텔로 흩어져 있으면 충돌이 거의 없어서 잠금 대기도 재시도도 없이 빠르다. 버전 검사의 세부(UPDATE 0을 받으면 무엇을 하나, 브라우저까지 버전을 들고 가는 법)는 [낙관적 잠금](/posts/optimistic-locking)에서 다뤘다.

## 넘치면 DB가 거절한다: CHECK 제약

세 번째 해결책은 미리 읽지도, 버전을 보지도 않는다. 그냥 더하고, 넘치면 DB가 거절하게 한다. 규칙을 테이블에 적어 둔다.

```sql
ALTER TABLE room_type_inventory
  ADD CONSTRAINT check_room_count CHECK (total_reserved <= total_inventory);
-- 남은 방은 2개인데 3개를 잡으려 한다
UPDATE room_type_inventory SET total_reserved = total_reserved + 3
 WHERE hotel_id = 1 AND room_type_id = 10 AND date >= '2026-12-24' AND date < '2026-12-26';
-- 2개는 된다
UPDATE room_type_inventory SET total_reserved = total_reserved + 2
 WHERE hotel_id = 1 AND room_type_id = 10 AND date >= '2026-12-24' AND date < '2026-12-26';
```

```text
ALTER TABLE
ERROR:  new row for relation "room_type_inventory" violates check constraint "check_room_count"
DETAIL:  Failing row contains (1, 10, 2026-12-24, 20, 21, 0).
UPDATE 2
```

첫 UPDATE는 24일 행을 21로 만들려다 막혔고, 같은 문장이니 25일 행도 함께 되돌려졌다. 이틀 중 하루만 잡히는 일은 없다. 앱은 `check_violation`(SQLSTATE 23514) 오류를 잡아 "매진"으로 바꿔 응답한다.

정확하고, 줄을 선 `FOR UPDATE`보다 훨씬 빠르다. 이 방법도 잠금이 아예 없는 건 아니다. UPDATE는 고치는 행을 커밋까지 잠그고, 뒤에 온 UPDATE는 기다린다. 다만 그 잠금은 "더하고, 예약 한 줄 넣고, 커밋"하는 몇 ms 동안만 쥔다. 가격 계산 30ms는 잠금 밖에서 끝났다. 잠그는 구간이 짧아서 빠른 것이다.

같은 효과를 제약 없이 UPDATE의 조건으로 낼 수도 있다. `WHERE ... AND total_reserved + 1 <= total_inventory`로 쓰고, 고친 줄 수가 묵는 날짜 수와 다르면 롤백한다. 이 조건부 UPDATE는 [재고 -1 막기](/posts/db-locking-deadlock)에서 다뤘다. CHECK 제약이 다른 점은, 앱 코드 어디에서 실수해도 DB가 마지막에 한 번 더 막아 준다는 데 있다. 그래서 다른 방법을 쓰더라도 안전망으로 같이 걸어 두는 경우가 많다.

단점도 있다. 제약은 스키마에 있어서 앱 코드처럼 리뷰하고 배포하기가 덜 자연스럽다. 마이그레이션 도구로 관리해야 한다. 규칙이 "한 행 안의 값"을 넘어서면 CHECK로 쓸 수 없다. 예를 들어 "이 손님은 같은 날 예약을 3개까지만"은 여러 행을 봐야 하니 CHECK로는 안 된다. MySQL은 8.0.16부터 CHECK 제약을 실제로 검사한다. 그 전 버전은 문법만 받아들이고 무시했으니, 오래된 MySQL에서는 이 방법이 조용히 효과가 없다.

## 같은 조건에서 네 가지를 돌려 보면

조건을 바꿔 가며 네 방법을 모두 돌렸다. 숫자는 평균과 최대 응답 시간(ms)이다. 응답 시간은 세션 출발부터 판정까지를 DB 안에서 잰 값이다.

| 방법 | 남은 방 3 · 손님 10 | 남은 방 10 · 손님 10 | 남은 방 20 · 손님 20 | 호텔 10곳에 1명씩 |
|---|---|---|---|---|
| 그냥 읽고 쓰기 | 10명 예약, 27/20 초과 · 38 / 45 | 10명 예약 · 38 / 44 | 20명 예약 · 47 / 63 | 10명 예약 · 32 / 34 |
| FOR UPDATE | 3명 예약 · 177 / 321 | 10명 예약 · 179 / 325 | 20명 예약 · 344 / 654 | 10명 예약 · 33 / 35 |
| 버전 (3번 시도) | 3명 예약, 7명 포기 · 89 / 102 | 3명 예약, 7명 포기 · 89 / 101 | 3명 예약, 17명 포기 · 94 / 107 | 10명 예약 · 33 / 36 |
| CHECK 제약 | 3명 예약 · 38 / 39 | 10명 예약 · 39 / 45 | 20명 예약 · 51 / 70 | 10명 예약 · 33 / 36 |

몇 가지가 눈에 들어온다.

"그냥 읽고 쓰기"는 방이 손님 수만큼 있을 때는 멀쩡해 보인다. 테스트에서 이 버그를 못 찾는 이유다. 넘치는 순간에만 터진다.

`FOR UPDATE`는 항상 맞지만 몰리면 손님 수에 비례해 느려진다. 손님 20명이면 마지막 사람이 654ms를 기다렸다. 잠금을 쥐는 시간이 길수록 이 숫자는 그대로 곱해진다.

버전 검사는 흩어진 요청에서는 가장 가볍고, 몰리는 요청에서는 남은 방이 있어도 손님을 돌려보낸다.

맨 오른쪽 열이 실제 호텔 예약의 보통 모습이다. 호텔 체인 전체의 예약은 수천 개 호텔과 수만 개 날짜에 흩어진다. 이때는 네 방법의 속도가 거의 같다. 차이는 왼쪽 세 열 같은 순간, 즉 같은 날짜와 같은 객실 유형에 몰릴 때 난다.

그래서 이렇게 고른다. 보통의 호텔 예약처럼 충돌이 드물면 버전 검사나 CHECK 제약이 단순하고 빠르다. 충돌이 잦고 실패보다 기다림이 나은 곳, 그리고 판단에 여러 행을 읽어야 하는 곳은 `FOR UPDATE`가 맞다. 잠그는 구간은 짧게 유지한다. 어느 쪽이든 CHECK 제약은 마지막 안전망으로 걸어 둔다. 격리 수준을 SERIALIZABLE로 올려 DB가 충돌을 찾게 하는 방법도 있다. 이 경우 PostgreSQL은 충돌한 트랜잭션을 `could not serialize access`(SQLSTATE 40001)로 끊으니, 앱은 버전 검사와 똑같이 재시도 코드를 갖춰야 한다.

아래에서 멱등성과 재고 검사를 함께 짜 보자. 요청은 순서대로 처리된다고 가정한다(DB가 잠금으로 줄을 세운 뒤의 모습이다).

## 이미 넘친 예약을 찾는 법

막는 장치를 넣기 전에 이미 넘친 예약이 있을 수 있다. 장치를 넣은 뒤에도 누군가 관리자 도구로 재고를 직접 고치다 넘길 수 있다. 그래서 정기적으로 점검한다. "그냥 읽고 쓰기" 실험 직후의 DB에서 돌렸다.

```sql
-- 재고 칸이 넘친 날짜
SELECT hotel_id, room_type_id, date, total_inventory, total_reserved
FROM room_type_inventory
WHERE total_reserved > total_inventory;
```

```text
 hotel_id | room_type_id |    date    | total_inventory | total_reserved 
----------+--------------+------------+-----------------+----------------
        1 |           10 | 2026-12-24 |              20 |             27
        1 |           10 | 2026-12-25 |              20 |             27
(2 rows)
```

이 쿼리가 행을 돌려주면 CHECK 제약을 걸 수도 없다. 제약을 추가하는 순간 기존 행을 검사해서 실패하기 때문이다. 넘친 예약을 먼저 처리(다른 객실로 옮기거나, 손님에게 연락하거나)하고 제약을 건다. 큰 테이블이라면 `NOT VALID`로 먼저 걸어 새 쓰기부터 막고 나중에 `VALIDATE CONSTRAINT`로 검사하는 방법이 있다.

현장에서 자주 보는 실수도 정리해 둔다. 하나는 모든 DB 오류를 "매진"으로 바꿔 응답하는 것이다. 제약 위반(23514)은 매진이 맞지만 연결 끊김이나 교착 상태는 다시 시도할 일이다. 다른 하나는 낙관적 잠금 충돌을 바로 다시 시도하는 것이다. 같은 순간 실패한 사람들이 같은 순간 다시 와서 또 부딪힌다. 무작위로 조금씩 기다리게 한다([지수 백오프와 지터](/posts/exponential-backoff-jitter)). 마지막은 재고 칸만 보고 예약 기록과 맞춰 보지 않는 것이다. 위의 갱신 손실처럼 장부와 기록이 어긋나는 버그는 재고 칸만 봐서는 안 보인다.

## 다음 글에서 재고 테이블을 키운다

이중 예약은 두 가지였다. 같은 손님의 중복은 주문서를 열 때 발급한 예약 id를 기본 키로 두어 막는다. 서로 다른 손님의 경합은 확인과 잡기 사이의 틈에서 생기고, 그 틈을 잠금으로 없애거나(`FOR UPDATE`), 쓸 때 알아채거나(버전), DB가 마지막에 거절하게(CHECK 제약) 해서 막는다. 무엇이 빠른지는 요청이 얼마나 한곳에 몰리느냐가 정한다.

[㊼ 호텔 예약 시스템 설계 ②](/posts/sd-hotel-inventory-scaling)에서는 이 글에서 미뤄 둔 것들을 다룬다. 방이 아니라 객실 유형을 날짜별로 세는 재고 테이블을 어떻게 미리 채우는지, 10% 초과 예약을 받는 호텔의 규칙을 어떻게 넣는지, 트래픽이 1,000배가 되면 DB와 캐시를 어떻게 나누는지, 그리고 결제가 실패했을 때 잡은 방을 어떻게 풀지다.

## 면접에서 나올 만한 질문

### 같은 사용자가 예약 버튼을 두 번 누르면 어떻게 막나요?

서버가 같은 요청인지 알아볼 수 있게 예약 id를 클라이언트가 들고 다니게 한다. 주문서를 열 때 서버가 id를 발급하고, 앱은 몇 번을 보내든 그 id를 보낸다. 이 id를 예약 테이블의 기본 키로 두고 `ON CONFLICT DO NOTHING`으로 넣으면 두 번째 요청은 아무것도 바꾸지 않고 기존 예약을 돌려받는다. 버튼 비활성화는 화면 밖에서 일어나는 재시도를 막지 못해서 보조 수단일 뿐이다.

### 예약 id를 요청을 받을 때 서버가 만들면 안 되나요?

안 된다. 요청이 올 때마다 새 id를 만들면 재시도도 새 요청으로 보여서 구별할 근거가 사라진다. 실제로 서버가 id를 만드는 구현에서 두 번 누르기를 재현하면 예약이 두 줄 생기고 재고가 2 올라간다. id는 요청보다 먼저, 주문서가 만들어질 때 정해져야 한다.

### 서로 다른 두 사람이 마지막 방을 동시에 예약하면 무엇이 잘못되나요?

둘 다 "남았다"를 읽고 둘 다 잡아서 방 하나에 두 명이 들어간다. 확인과 쓰기가 서로 다른 문장이고, 기본 격리 수준인 READ COMMITTED는 내가 읽은 값을 남이 바꾸지 못하게 막지 않기 때문이다. 손님 10명, 남은 방 3개로 실험하면 10명 모두 예약되고 재고가 27/20이 된다. 오류가 하나도 나지 않아서 로그로는 찾기 어렵다.

### 비관적 잠금과 낙관적 잠금 중 무엇을 고르나요?

충돌 빈도로 고른다. 보통의 호텔 예약처럼 요청이 여러 호텔과 날짜로 흩어지면 충돌이 드물어 낙관적 잠금이나 CHECK 제약이 단순하고 빠르다. 같은 행에 몰리면 낙관적 잠금은 매 회차 한 명만 이기고 나머지는 재시도하다 포기한다. 실험에서는 방이 7개 남았는데 7명이 포기했다. 몰리는 곳이고 기다림이 실패보다 나으면 `FOR UPDATE`를 쓰되, 잠금을 쥐는 구간을 짧게 둔다.

### FOR UPDATE를 쓸 때 조심할 점은요?

잠금을 쥔 채로 느린 일을 하지 않는 것이다. 특히 결제 회사 호출을 트랜잭션 안에 넣으면 그 시간 동안 같은 객실 유형을 원하는 모든 요청이 줄을 선다. 그리고 여러 날짜를 잠글 때는 `ORDER BY date`처럼 항상 같은 순서로 잠가 교착 상태를 피한다. 느려졌을 때는 `pg_stat_activity`의 `wait_event`와 `pg_blocking_pids`로 줄의 맨 앞을 찾는다.

### 격리 수준을 SERIALIZABLE로 올리면 해결되지 않나요?

해결된다. PostgreSQL의 SERIALIZABLE은 순서대로 실행한 것과 다른 결과가 나올 트랜잭션을 찾아 SQLSTATE 40001 오류로 끊는다. 대신 앱이 그 오류를 받으면 트랜잭션 전체를 다시 실행해야 하고, 몰리는 상황에서는 낙관적 잠금처럼 재시도가 많아진다. 모든 트랜잭션에 비용이 붙으니 예약 경로만 골라 쓰는 편이 낫다.

### 인기 행사로 같은 날짜 요청이 10배로 몰리면요?

한 행에 줄이 서는 게 병목이 된다. 잠그는 구간을 최소로 줄이고(CHECK 제약이나 조건부 UPDATE), 그래도 모자라면 DB 앞에 대기열을 두어 들어오는 속도를 제한한다. 재고를 미리 여러 칸으로 나눠 각 칸이 일부를 팔게 하는 방법도 있지만 남은 수를 합쳐 보여 주기가 어려워진다. 트래픽 자체가 커질 때 DB를 나누는 방법은 다음 글에서 다룬다.

### 예약을 확정한 직후 DB 주 서버가 죽으면요?

복제본에 그 쓰기가 아직 안 갔다면 장애 조치 뒤 예약이 사라질 수 있다. 손님은 확정 메일을 받았는데 기록이 없는 셈이다. 예약처럼 잃으면 안 되는 쓰기는 동기 복제로 최소 한 복제본에 기록된 뒤 응답하게 하고, 그만큼 쓰기 지연이 늘어나는 것을 받아들인다. 복제 방식의 차이는 [④ DB 복제](/posts/sd-db-replication-intro)에서 다뤘다.
