  커밋 하나를 지우려고 reset을 쳤는데 어제 한 작업까지 사라졌다. 등이 서늘해지지만 대개는 괜찮다. 커밋은 지워진 게 아니라 이름표를 잃어서 안 보일 뿐이고, Git은 이름표가 어디에서 어디로 움직였는지 전부 적어 두었다.

  이 글은 서랍과 생명줄 이야기다. 기능을 만들다 말았는데 급한 버그 수정이 들어오면 지금 변경을 stash라는 서랍에 넣어 두고 깨끗한 상태에서 일한 뒤 다시 꺼낸다. 이름표를 잃은 커밋은 reflog라는 생명줄로 찾는데, 이건 HEAD와 브랜치가 어느 커밋을 가리켰는지 시간순으로 적은 일기장이라 몇 단계 전 해시를 찾아 그 자리로 돌아가거나 브랜치를 새로 붙이면 된다.

  엉뚱한 브랜치에 한 커밋을 제자리로 옮기는 것도, 오래전에 지운 파일을 히스토리에서 꺼내는 것도 같은 원리다. 다만 서랍과 생명줄에도 한계가 있어서, 한 번도 add하거나 커밋하지 않은 변경은 Git 어디에도 없고 일기장도 기본 90일이 지나면 정리된다.
</EasyIntro>

커밋을 하나 지우려고 `git reset --hard HEAD~2`를 쳤는데, `git log`를 보니 어제 한 작업까지 사라졌다. 등이 서늘해지는 순간이지만 대개는 괜찮다. 커밋은 지워진 게 아니라 이름표를 잃어서 안 보일 뿐이고, Git은 이름표가 어디에서 어디로 움직였는지 다 적어 두었다.

비슷한 순간이 몇 가지 더 있다. 기능을 만들다 말았는데 급한 버그 수정 요청이 와서 지금 변경을 잠깐 치워야 한다. 로그인 커밋 두 개를 기능 브랜치가 아니라 main에 해 버렸다. 몇 달 전에 지운 파일이 다시 필요하다. 모두 "지금 상태를 망가뜨리지 않고 무언가를 잠깐 옮기거나 되찾는" 일이다.

restore, reset, revert로 실수의 위치에 맞춰 되돌리는 법은 [되돌리기 글](/posts/git-undo)에서 봤다. 이 글은 그 이어서 변경을 치워 두는 stash, 사라진 커밋을 찾는 reflog와 `fsck`, 엉뚱한 브랜치에 한 커밋 옮기기, 히스토리에서 지운 파일 꺼내기를 다룬다. 예제는 앞 글과 같은 저장소다. `server.js` 하나로 시작해 서버 시작, README, 로그 1, 로그 2 순서로 커밋이 쌓여 있다. 명령은 Ubuntu 24.04의 Git 2.43.0에서 실행했다.

## 잠깐 치워 두기

작업하다가 급한 버그 수정 요청이 왔는데 지금 변경은 커밋하기엔 어중간하다. `git stash`는 작업 트리와 인덱스의 변경을 따로 떼어 저장하고 깨끗한 상태로 만든다. 저장한 것은 스택처럼 쌓인다.

```bash
# 포트를 바꾸던 중이고, 새 메모 파일도 있다
git status -s

# 이름을 붙여서 치운다. 기본으로는 추적 중인 파일만 치운다
git stash push -m "포트 바꾸던 중"
git status -s

# untracked 파일까지 치우려면 -u
git stash push -u -m "메모 파일까지"
git status -s

# 쌓인 목록
git stash list
```

```text
 M server.js
?? notes.md

Saved working directory and index state On main: 포트 바꾸던 중

?? notes.md

Saved working directory and index state On main: 메모 파일까지

stash@{0}: On main: 메모 파일까지
stash@{1}: On main: 포트 바꾸던 중
```

`-u` 없이 stash하면 새 파일(`notes.md`)은 그대로 남는다. 다른 브랜치로 옮겨 가도 그 파일이 따라와서 "치웠는데 왜 남아 있지" 하게 된다. `stash@{0}`이 가장 최근 것이다. 아래 그림에서 다음을 누르면 명령마다 stash 목록이 어떻게 쌓이고 빠지는지 보인다.

꺼내기 전에 무엇이 들었는지 본다.

```bash
# 저장된 변경을 diff로
git stash show -p 'stash@{1}'

# untracked 파일까지 들어 있는 stash의 요약
git stash show --include-untracked 'stash@{0}'
```

```text
diff --git a/server.js b/server.js
index 84c111c..297540e 100644
--- a/server.js
+++ b/server.js
@@ -1,3 +1,3 @@
-const port = 3000;
+const port = 4000;
 // 로그 1
 // 로그 2

 notes.md | 1 +
 1 file changed, 1 insertion(+)
```

`stash@{1}`처럼 중괄호가 있는 이름은 셸에 따라 다르게 해석될 수 있어서 따옴표로 감싸는 습관을 들이면 좋다. `stash show`의 `--include-untracked` 옵션은 2.32부터 있다.

```bash
# 꺼내서 적용하고 목록에서 지운다
git stash pop
git stash list

# 적용만 하고 목록에는 남긴다
git stash apply 'stash@{0}'
git stash list

# 다 썼으면 지운다
git stash drop
```

```text
Already up to date.
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	notes.md

nothing added to commit but untracked files present (use "git add" to track)
Dropped refs/stash@{0} (3305077050dcc2ead63d0a2631f2899f6684f5c6)

stash@{0}: On main: 포트 바꾸던 중

On branch main
Changes not staged for commit:

	modified:   server.js

```

pop은 적용이 성공했을 때만 목록에서 지운다. 꺼낼 때 충돌이 나면 목록에 남겨 둔다. 치워 둔 사이 main에서 같은 줄이 바뀌었다면 이렇게 된다.

```bash
# 포트 4000으로 바꾸던 걸 치워 두고, 그사이 main에서 5000으로 커밋됐다
git stash pop
git status -s
git stash list
```

```text
Auto-merging server.js
CONFLICT (content): Merge conflict in server.js
On branch main
Unmerged paths:
  (use "git restore --staged <file>..." to unstage)
  (use "git add <file>..." to mark resolution)
	both modified:   server.js

no changes added to commit (use "git add" and/or "git commit -a")
The stash entry is kept in case you need it again.

UU server.js

stash@{0}: On main: 4000
```

`The stash entry is kept`가 안심해도 된다는 말이다. 파일의 충돌을 풀고, stash는 커밋을 만드는 게 아니니 `git add` 대신 `git restore --staged server.js`로 충돌 표시만 지워 변경을 작업 트리에 남긴다. 다 됐으면 `git stash drop`으로 지운다. 충돌이 귀찮으면 치워 둔 시점의 커밋에서 새 브랜치를 만들어 적용하는 `git stash branch`가 깔끔하다. 그 커밋 위에서 적용하니 충돌이 날 수 없다.

```bash
# 충돌을 버리고 원래대로 돌린 뒤
git restore server.js

# stash를 만든 시점의 커밋에서 새 브랜치를 만들고 거기에 적용한다
git stash branch fix/port-4000
git status -sb
```

```text
Switched to a new branch 'fix/port-4000'
On branch fix/port-4000
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   server.js

no changes added to commit (use "git add" and/or "git commit -a")
Dropped refs/stash@{0} (ab9de2d370f1797de0c42c12aadb1455418cee0f)

## fix/port-4000
 M server.js
```

stash는 잠깐 쓰는 서랍이다. 며칠씩 쌓아 두면 무엇이 무엇인지 잊어버리고, `git stash clear`나 실수한 drop 한 번에 사라진다. 하루를 넘길 것 같으면 브랜치를 만들어 "wip" 커밋으로 두는 편이 안전하다. 실수로 drop한 stash도 커밋 객체로 남아 있어서, drop할 때 출력된 해시나 `git fsck --unreachable | grep commit`으로 찾아 `git stash apply 해시`로 살릴 수 있다.

## reset --hard 뒤에 사라진 커밋 찾기

처음 상황으로 돌아간다. `git reset --hard HEAD~2`로 커밋 두 개가 사라졌다. 정확히는 main 이름표가 두 칸 뒤로 갔을 뿐, 커밋 객체는 `.git/objects`에 그대로 있다. 문제는 그 커밋의 해시를 모른다는 것이다. 그걸 알려 주는 게 reflog다. Git은 HEAD와 브랜치가 움직일 때마다 어디에서 어디로 갔는지 `.git/logs`에 적어 둔다. 다음을 누르면 찾아오는 과정을 따라간다.

```bash
# 커밋 두 개를 날렸다
git reset --hard HEAD~2
git log --oneline

# HEAD가 지나온 자리
git reflog
```

```text
HEAD is now at 3b10bfd README

3b10bfd README
a75bb4a 서버 시작

3b10bfd HEAD@{0}: reset: moving to HEAD~2
1c17a6f HEAD@{1}: commit: 로그 2
0d8de3c HEAD@{2}: commit: 로그 1
3b10bfd HEAD@{3}: commit: README
a75bb4a HEAD@{4}: commit (initial): 서버 시작
```

맨 윗줄이 방금 한 reset이고, 그 바로 아래 `HEAD@{1}`이 reset 직전의 1c17a6f다. 이름표를 붙여 살린다.

```bash
# 이름표를 붙여 붙잡아 두고
git branch rescue 'HEAD@{1}'
git log --oneline -3 rescue

# main을 그리로 되돌린 뒤 임시 이름표는 지운다
git reset --hard rescue
git branch -d rescue
```

```text
1c17a6f 로그 2
0d8de3c 로그 1
3b10bfd README

HEAD is now at 1c17a6f 로그 2
Deleted branch rescue (was 1c17a6f).
```

reflog에서 바로 `git reset --hard 'HEAD@{1}'`을 해도 된다. 다만 reset을 하면 reflog에 줄이 하나 더 쌓이면서 번호가 밀린다. 헷갈리지 않게 해시를 직접 쓰거나 이름표부터 붙이는 습관이 안전하다. 시간으로 찾을 수도 있다. `git reflog --date=iso`로 시각을 보고, `main@{1.hour.ago}`나 `main@{yesterday}`처럼 "그 시점에 main이 있던 곳"을 가리킬 수 있다.

reflog에는 몇 가지 한계가 있다.

- 로컬에만 있다. 클론을 새로 받으면 reflog는 비어 있고, 다른 사람의 reflog는 볼 수 없다.
- 영원하지 않다. 기본값으로 브랜치에서 닿는 커밋의 기록은 90일(`gc.reflogExpire`), 닿지 않는 커밋의 기록은 30일(`gc.reflogExpireUnreachable`)이 지나면 gc 때 지워진다. 기록이 지워지고 나면 그 커밋도 gc가 정리한다.
- 커밋만 지킨다. 한 번도 커밋하지 않은 변경은 reflog에 없다.

마지막 경우에도 add까지는 했다면 희망이 있다. add하는 순간 내용이 blob으로 저장되기 때문이다. `git fsck --lost-found`는 어디에서도 가리키지 않는 객체를 찾아 `.git/lost-found`에 모아 준다.

```bash
# 새 파일을 add만 하고 커밋하기 전에 reset --hard를 쳐 버렸다
echo 'const secretFeature = true;' > feature.js
git add feature.js
git reset --hard
git status -s

# 어디서도 가리키지 않는 객체를 찾는다
git fsck --lost-found

# 찾은 blob의 내용
git show a3ee690c8f8c8b43fae21040ef31a0181c3e93ea
```

```text
HEAD is now at 1c17a6f 로그 2

dangling blob a3ee690c8f8c8b43fae21040ef31a0181c3e93ea

const secretFeature = true;
```

`dangling blob`이 add했던 파일 내용이다. 파일 이름은 tree에 있었는데 tree를 만들기 전에 날렸으니 이름은 없다. 찾은 blob이 여러 개라면 하나씩 열어 보고 `git show 해시 > feature.js`로 꺼낸다. `dangling commit`이 나오면 그건 날아간 커밋(실수로 drop한 stash도 여기 나온다)이다.

## 엉뚱한 브랜치에 커밋했을 때

로그인 기능 커밋 두 개를 `feature/login`이 아니라 main에 했다. 아직 푸시하지 않았다면 이름표 두 개만 옮기면 된다.

```bash
# main이 원격보다 두 커밋 앞서 있다
git status -sb
git log --oneline -3

# 지금 위치에 새 브랜치 이름표를 붙인다 (커밋이 이 이름표로 살아남는다)
git branch feature/login

# main은 원격 위치로 되돌린다
git reset --hard origin/main

# 작업은 새 브랜치에서 이어 간다
git switch feature/login
git log --oneline --graph --decorate --all
```

```text
## main...origin/main [ahead 2]

8412066 로그인 검증
8129a47 로그인 폼
a75bb4a 서버 시작

HEAD is now at a75bb4a 서버 시작

Switched to branch 'feature/login'

* 8412066 (HEAD -> feature/login) 로그인 검증
* 8129a47 로그인 폼
* a75bb4a (origin/main, main) 서버 시작
```

아래 그림에서 다음을 누르면 명령마다 이름표가 어느 커밋을 가리키는지 바뀌는 게 보인다. 커밋 세 개는 그대로 있고 이름표만 움직인다.

순서가 중요하다. 이름표를 먼저 붙이고 나서 main을 되돌린다. 거꾸로 하면 커밋이 이름표 없이 떠서 reflog로 찾아야 한다. `reset --hard`이니 커밋하지 않은 변경이 없는지도 먼저 확인한다. 원격 대신 `HEAD~2`처럼 칸 수로 되돌려도 된다.

옮길 브랜치가 이미 있다면 `cherry-pick`으로 커밋을 복사하고 원래 브랜치에서 지운다. main에 한 핫픽스를 `hotfix/1`로 옮기는 예다.

```bash
# 원격 main에서 hotfix/1을 만들고 main의 마지막 커밋을 복사한다
git switch -c hotfix/1 origin/main
git cherry-pick main

# main에서는 그 커밋을 지운다 (푸시 전일 때만)
git switch main
git reset --hard HEAD~1
```

```text
Switched to a new branch 'hotfix/1'
[hotfix/1 2461e34] 핫픽스
 1 file changed, 1 insertion(+)

Switched to branch 'main'
HEAD is now at a75bb4a 서버 시작
```

cherry-pick한 커밋은 내용은 같아도 부모가 다른 새 커밋(`2461e34`)이다. 이미 main에 푸시했다면 main에서 reset하지 말고 revert로 되돌린다.

## 지운 파일을 히스토리에서 꺼내기

예전에 지운 파일이 다시 필요하다. 언제 지웠는지 찾고, 지우기 직전 커밋에서 꺼내 온다.

```bash
# legacy.js를 지운 커밋 (D = deleted)
git log --oneline --diff-filter=D -- legacy.js

# 그 파일이 나온 커밋 전체
git log --oneline --all -- legacy.js
```

```text
f7bd962 레거시 정리

f7bd962 레거시 정리
1e6059b 레거시 유틸
```

지운 커밋(`f7bd962`)에는 파일이 없으니, 그 부모(`f7bd962~1`)에서 꺼낸다.

```bash
# 지우기 직전 커밋의 legacy.js를 작업 트리로 꺼낸다
git restore --source=f7bd962~1 -- legacy.js
git status -s

# 인덱스에도 같이 올리려면 --staged --worktree
git restore --source=f7bd962~1 --staged --worktree -- legacy.js
git status -s
```

```text
?? legacy.js

A  legacy.js
```

`--source`를 주면 restore는 인덱스 대신 그 커밋에서 파일을 가져온다. 기본은 작업 트리만 바꾸니, 인덱스에도 올리려면 `--staged`를 함께 쓴다. 2.23 이전이라면 `git checkout f7bd962~1 -- legacy.js`가 같은 일을 한다(이건 인덱스에도 바로 올린다). 파일을 디스크에 쓰지 않고 내용만 보고 싶으면 `git show f7bd962~1:legacy.js`다.

## 서랍과 생명줄의 한계

stash와 reflog는 둘 다 로컬에만 있는 임시 장치다. stash는 며칠 두면 무엇이었는지 잊어버리고, reflog는 기본 90일(닿지 않는 커밋은 30일)이 지나면 gc가 정리한다. 다른 사람의 클론에는 내 reflog가 없으니, 노트북을 바꾸거나 저장소를 새로 받은 뒤에는 찾을 수 없다. 그래서 하루를 넘길 작업은 브랜치에 커밋해 두고, 위험한 명령 앞에서는 `git branch backup/...`으로 이름표를 하나 붙인다. 커밋했다면 reflog가, add까지 했다면 `fsck`가 찾아 주지만, 둘 다 안 한 변경은 Git도 모른다. 상황별 대처는 [문제 해결 글](/posts/git-troubleshooting)에 더 모아 두었다.

## 면접에서 나올 만한 질문

### reset --hard로 날린 커밋을 되살릴 수 있나요?

커밋했던 것이라면 대부분 된다. reset은 이름표만 옮기고 커밋 객체는 남겨 두므로, `git reflog`에서 reset 직전 줄의 해시를 찾아 `git branch rescue 해시`로 이름표를 붙이거나 `git reset --hard 해시`로 돌아간다. reflog는 로컬에만 있고 기본으로 닿지 않는 커밋 기록은 30일, 닿는 커밋 기록은 90일 뒤 만료된다. 커밋하지 않은 변경은 reflog에 없지만, add했다면 `git fsck --lost-found`로 blob을 찾을 수 있다.

### stash pop과 apply의 차이는 무엇인가요?

둘 다 저장한 변경을 작업 트리에 적용한다. pop은 적용에 성공하면 목록에서 지우고, apply는 목록에 남긴다. pop하다 충돌이 나면 목록에서 지우지 않으니 충돌을 풀고 직접 drop한다. 기본 stash는 untracked 파일을 넣지 않아서 새 파일까지 치우려면 `-u`를 붙이고, 충돌을 피하려면 stash를 만든 커밋에서 새 브랜치로 적용하는 `git stash branch`를 쓴다.

### 커밋 두 개를 엉뚱한 브랜치(main)에 했습니다. 어떻게 옮기나요?

푸시 전이라면 지금 위치에 `git branch feature/x`로 이름표를 먼저 붙이고, main은 `git reset --hard origin/main`(또는 `HEAD~2`)으로 되돌린 뒤 새 브랜치로 옮겨 간다. 이름표를 먼저 붙여야 커밋이 떠 버리지 않는다. 옮길 브랜치가 이미 있으면 그쪽에서 `git cherry-pick`으로 복사하고 main에서 reset한다. 이미 main에 푸시했다면 main은 revert로 되돌린다.

### reflog는 어디에 있고 언제까지 남나요?

`.git/logs` 아래에 HEAD와 브랜치마다 "어디서 어디로, 무슨 명령으로" 움직였는지가 한 줄씩 쌓인다. 로컬에만 있고 push로 공유되지 않아서 새로 clone하면 비어 있다. 기본으로 브랜치에서 닿는 커밋의 기록은 90일(`gc.reflogExpire`), 닿지 않는 커밋의 기록은 30일(`gc.reflogExpireUnreachable`) 뒤 gc 때 지워지고, 그 뒤에는 커밋 객체도 정리된다.

### 예전에 지운 파일을 되살리려면 어떻게 하나요?

`git log --diff-filter=D -- 경로`로 그 파일을 지운 커밋을 찾고, 그 커밋에는 파일이 없으니 부모 커밋에서 꺼낸다. `git restore --source=커밋~1 -- 경로`는 작업 트리로, `--staged`를 더하면 인덱스에도 올린다. 내용만 보려면 `git show 커밋~1:경로`다.

### add만 하고 커밋하지 않은 파일을 reset --hard로 날렸습니다. 찾을 수 있나요?

add하는 순간 내용이 blob으로 저장되니 찾을 수 있다. `git fsck --lost-found`가 어디서도 가리키지 않는 객체를 `dangling blob`으로 보여 주고, `git show 해시`로 내용을 확인해 파일로 꺼낸다. 파일 이름은 tree에 들어갈 정보라 남지 않는다. add조차 하지 않은 변경은 Git 어디에도 없어서 되살릴 수 없다.
