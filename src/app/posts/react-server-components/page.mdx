상품 설명을 마크다운으로 받아서 `marked`로 HTML로 바꿔 보여 주는 페이지를 Next.js App Router로 두 번 만들었다. 한 번은 파일 맨 위에 `"use client"`를 붙였고, 한 번은 아무것도 붙이지 않았다. 화면은 똑같다. 그런데 빌드 결과에서 이 페이지 전용 JS 청크를 찾아보면 크기가 다르다.

```text
"use client" 페이지    38,211 B  (gzip 11,770 B)  marked가 들어 있다
서버 컴포넌트 페이지     315 B  (gzip    277 B)  찜 버튼 하나만 들어 있다
```

두 번째 페이지의 315바이트에는 찜 버튼 컴포넌트만 있다. `marked`는 서버에서만 돌았고 브라우저로는 그 결과만 갔다. 이 글은 React 서버 컴포넌트(RSC)가 결과를 어떤 형식으로 보내는지, `"use client"` 경계가 무엇을 가르는지, 그 경계를 넘을 수 있는 값이 무엇인지를 직접 받은 payload와 빌드 에러로 따라간다. 렌더링 방식 전체 속에서 RSC가 어디에 있는지는 [CSR, SSR, SSG, ISR, 스트리밍](/posts/rendering-strategies)에서 짧게 정리했다. 예제는 Next.js 16.4.1과 React 19.3.1로 빌드하고 `next start`로 띄워 받은 결과다.

## SSR은 시점의 이야기, RSC는 코드의 이야기

먼저 두 낱말을 떼어 놓는다. SSR은 첫 HTML을 서버에서 만든다는 뜻이다. 서버에서 만들었어도 그 컴포넌트 코드는 전부 브라우저로 내려가고, 브라우저에서 [하이드레이션](/posts/hydration)으로 한 번 더 실행된다. 서버는 첫 화면을 미리 그려 줄 뿐이다. 요청마다 HTML을 만드는 서버 쪽 비용은 [SSR 깊게](/posts/rendering-ssr)에서 다뤘다.

RSC는 "어떤 컴포넌트가 브라우저에서 실행될 필요가 없나"를 묻는다. 서버 컴포넌트는 서버에서만 실행된다. 코드가 번들에 들어가지 않으니 브라우저가 내려받지도, 다시 실행하지도 않는다. 대신 상태(`useState`), 효과(`useEffect`), 이벤트 핸들러를 쓸 수 없다. 그런 게 필요한 컴포넌트만 `"use client"`를 붙인 클라이언트 컴포넌트로 만든다.

두 축은 섞여서 쓰인다. App Router의 첫 요청에서 서버 컴포넌트는 서버에서 실행되고, 클라이언트 컴포넌트도 첫 HTML을 위해 서버에서 한 번 렌더링(SSR)된 뒤 브라우저에서 하이드레이션된다. 이름과 달리 클라이언트 컴포넌트는 "브라우저에서만 도는 컴포넌트"가 아니라 "브라우저에서도 도는 컴포넌트"다.

## 서버가 보내는 것은 HTML이 아니다

서버 컴포넌트의 결과는 HTML이 아니라 React가 읽는 트리 데이터다. 이걸 RSC payload, React 내부에서는 Flight라고 부른다. Next.js에서는 `RSC: 1` 헤더를 붙여 요청하면 HTML 대신 이 payload를 준다.

```bash
# RSC 헤더를 붙여 payload를 받는다. Next 16은 먼저 ?_rsc 주소로 307을 보내므로 -L로 따라간다
curl -sL -D headers.txt -H 'RSC: 1' http://127.0.0.1:3200/rsc
grep -i -E '^HTTP|content-type|location' headers.txt
```

```text
HTTP/1.1 307 Temporary Redirect
location: /rsc?_rsc
HTTP/1.1 200 OK
Content-Type: text/x-component
```

Next 16은 `RSC` 헤더와 `_rsc` 쿼리 값이 맞지 않으면 쿼리를 붙인 주소로 돌려보낸다. 같은 주소의 HTML과 payload가 캐시에서 섞이지 않게 주소 자체를 다르게 만드는 장치로 보인다. `-L` 없이 받으면 본문이 비어 있어서 처음에 헷갈리기 쉽다.

받은 payload(3,506바이트)에서 페이지 본문에 해당하는 줄만 고르면 이렇다.

## 경계는 파일 단위로 그어진다

`"use client"`는 컴포넌트에 붙이는 표시가 아니라 모듈(파일)에 붙이는 표시다. 번들러는 서버 쪽 모듈 그래프를 따라가다 이 지시어가 있는 파일을 만나면 "여기서부터는 브라우저 번들"이라고 갈라 낸다. 그리고 그 파일이 import하는 모든 것을 지시어가 없어도 클라이언트 쪽으로 끌고 간다.

그래서 흔히 하는 실수가 둘이다. 하나는 `"use client"`를 위쪽에 붙이는 것이다. 레이아웃이나 페이지 꼭대기에 붙이면 그 아래 전부가 클라이언트 쪽이 되어 서버 컴포넌트를 쓰는 의미가 없어진다. 처음 장면의 38KB 페이지가 그 경우다. 다른 하나는 "지시어가 없으니 서버 컴포넌트겠지" 하고 넘어가는 것이다. 지시어 없는 파일은 누가 import하느냐에 따라 서버 쪽에도, 클라이언트 쪽에도 들어간다. 위 그림의 `format.ts`가 그렇다.

이 블로그에도 실제 예가 있다. 글 끝의 퀴즈 링크(`QuizLink`)는 클라이언트 컴포넌트이고, 문제 수를 세려고 퀴즈 레지스트리를 import한다. 레지스트리는 모든 글의 문제를 담고 있어서, 위에서 띄운 빌드의 글 페이지 청크 하나(657,305바이트)에 문제 870개의 본문이 통째로 들어 있었다. 화면에 보이는 건 "이 토픽 문제 N개" 한 줄이다. 서버 쪽에서 개수만 계산해 숫자를 props로 넘기면 그 데이터는 번들에서 빠진다.

규칙을 함수로 옮겨 보자. 모듈 그래프와 시작 파일을 받아 브라우저 번들에 들어가는 파일 목록을 돌려준다. 지시어가 있는 파일을 만나면 그 파일부터 아래는 모두 클라이언트 쪽이다.

세 번째 테스트의 `format.ts`는 서버 쪽 `page.tsx`도 쓰고 클라이언트 쪽 `tabs.tsx`도 쓴다. 이런 모듈은 서버용과 브라우저용으로 두 번 번들된다. 그래서 양쪽에서 쓰는 유틸은 React나 브라우저 API, 서버 비밀값에 기대지 않게 짜야 한다.

## 경계를 넘을 수 있는 값

서버 컴포넌트가 클라이언트 컴포넌트에 넘기는 props는 payload에 적혀 네트워크를 건넌다. 적을 수 있는 값만 넘어간다. React 19가 받아 주는 것은 문자열·숫자·불리언·`null`·`undefined`, 일반 객체와 배열, `Date`, `Map`, `Set`, `BigInt`, 타입 배열, `Promise`, JSX, 그리고 서버 액션이다. 함수와 클래스 인스턴스는 안 된다.

일부러 잘못 넘겨 보면 에러가 그 자리를 정확히 짚는다. 함수를 넘긴 페이지와 `Date`·`Set`·클래스 인스턴스를 섞어 넘긴 페이지를 요청했을 때 `next start` 로그다.

```text
⨯ Error: Functions cannot be passed directly to Client Components unless you explicitly expose it by marking it with "use server". Or maybe you meant to call this function rather than return it.
  {format: function format}
           ^^^^^^^^^^^^^^^
    at ignore-listed frames {
  digest: '654355239'
}
⨯ Error: Only plain objects, and a few built-ins, can be passed to Client Components from Server Components. Classes or null prototypes are not supported.
  {at: Date, tags: Set, price: {won: 89000}}
                               ^^^^^^^^^^^^
    at ignore-listed frames {
  digest: '3743059337'
}
```

두 번째 에러에서 `Date`와 `Set`은 통과하고 `Price` 클래스의 인스턴스에서 멈췄다. prop 이름이 `onSelect`처럼 `on`으로 시작하면 메시지가 "Event handlers cannot be passed to Client Component props."로 바뀐다. 둘 다 빌드가 아니라 렌더링할 때 나는 에러라서, 동적 페이지라면 요청이 와야 500과 함께 드러난다. 사용자 화면에는 메시지 대신 `digest` 값만 보이니 서버 로그에서 그 값을 찾는다.

함수를 넘기고 싶은 이유는 대개 둘이다. 클릭 같은 동작을 넘기고 싶다면 그 동작을 클라이언트 컴포넌트 안에서 정의한다. 서버에서 그린 내용을 클라이언트 컴포넌트 안에 넣고 싶다면 `children`으로 넘긴다. `children`은 이미 렌더링된 JSX라 직렬화된다.

```tsx
// tabs.tsx — "use client". 탭 전환 상태만 가진다
"use client";
export function Tabs({ labels, children }) {
  const [i, setI] = useState(0);
  return (
    <>
      {labels.map((l, n) => <button key={l} onClick={() => setI(n)}>{l}</button>)}
      {children[i]}
    </>
  );
}

// page.tsx — 서버 컴포넌트. 무거운 내용은 여기서 그려 children으로 넣는다
export default async function Page() {
  const product = await db.product.find(42);
  return (
    <Tabs labels={["설명", "스펙"]}>
      <Description md={product.descriptionMd} /> {/* 서버에서 marked 실행 */}
      <Specs specs={product.specs} />
    </Tabs>
  );
}
```

`Tabs`는 클라이언트 번들에 들어가지만 `Description`과 `Specs`는 들어가지 않는다. 클라이언트 컴포넌트가 서버 컴포넌트를 import할 수는 없어도, 서버 컴포넌트가 만든 결과를 자리에 받아 놓을 수는 있다.

## 컴포넌트가 직접 데이터를 가져온다

서버 컴포넌트는 `async` 함수가 될 수 있다. API 경로를 만들고 브라우저에서 부르는 대신 컴포넌트 안에서 DB나 내부 API를 바로 부른다. 데이터를 쓰는 곳과 가져오는 곳이 붙어 있고, 브라우저와 API 사이의 왕복이 서버 안의 짧은 왕복으로 바뀐다.

편한 만큼 워터폴도 쉽게 생긴다. 부모가 `await`를 끝내야 자식이 렌더링을 시작하니, 트리 깊이대로 요청이 줄을 선다.

```tsx
// 부모가 상품을 받은 뒤에야 Reviews가 시작한다: 상품 → 리뷰가 이어진다
export default async function Page({ params }) {
  const { id } = await params;
  const product = await getProduct(id);
  return <><Info product={product} /><Reviews id={id} /></>;
}

// 서로 기다릴 이유가 없으면 같이 시작한다
export default async function Page({ params }) {
  const { id } = await params;
  const [product, reviews] = await Promise.all([getProduct(id), getReviews(id)]);
  return <><Info product={product} /><ReviewList reviews={reviews} /></>;
}
```

느린 부분이 있으면 `Suspense`로 감싸 [스트리밍](/posts/streaming-ssr-suspense)으로 넘긴다. 서버 컴포넌트에서 `Promise`를 만들어 기다리지 않고 클라이언트 컴포넌트에 넘기면, 클라이언트 쪽에서 `use(promise)`로 받아 쓸 수도 있다. `Promise`도 경계를 넘는 값이라서 payload 안에서 나중에 채워질 조각으로 표시된다.

같은 요청 안에서 여러 컴포넌트가 같은 데이터를 부르는 일도 잦다. 레이아웃과 페이지가 둘 다 현재 사용자를 읽는 식이다. React의 `cache()`로 감싼 함수는 한 요청 안에서 같은 인자면 한 번만 실행된다. 요청이 끝나면 버려지니 사용자끼리 섞일 걱정은 없다. 요청을 넘어 오래 두는 캐시는 Next의 별도 캐시 기능이 맡는데, 그 이야기는 [Next.js의 정적·동적 렌더링](/posts/nextjs-static-dynamic-rendering)에서 이어진다.

## 서버 전용 코드가 브라우저로 새지 않게

경계가 파일 단위라는 말은 실수로 서버 코드를 브라우저로 끌고 갈 수 있다는 뜻이기도 하다. DB 클라이언트나 비밀 키를 쓰는 모듈을 클라이언트 컴포넌트가 import하면 그 코드가 번들에 들어간다. 이걸 빌드 단계에서 막는 장치가 `server-only` 패키지다. 이 패키지를 import한 모듈이 클라이언트 쪽 그래프에 들어오면 빌드가 실패한다.

```ts
// lib/db.ts
import "server-only";
export async function getPrice() {
  return { won: 89000, key: process.env.DB_PASSWORD };
}
```

이 함수를 클라이언트 컴포넌트에서 import하고 빌드하면 이렇게 멈춘다.

```text
./lib/db.ts:1:1
Error: 'server-only' cannot be imported from a Client Component module
> 1 | import "server-only";
    | ^^^^^^^^^^^^^^^^^^^^^
It should only be used from a Server Component.
Import traces:
  Client Component Browser:
    ./lib/db.ts [Client Component Browser]
    ./components/price-tag.tsx [Client Component Browser]
    ./components/price-tag.tsx [Server Component]
    ./app/err-so/page.tsx [Server Component]
```

Import traces는 아래에서 위로 읽는다. 서버 컴포넌트인 페이지가 `price-tag.tsx`를 import했고, 그 파일이 경계 너머 브라우저 쪽에서 `db.ts`를 끌어왔다. `[Server Component]`에서 `[Client Component Browser]`로 바뀌는 줄이 경계다.

반대 방향의 실수도 빌드가 잡는다. 지시어 없는 페이지에서 `useState`를 쓰면 이렇게 나온다.

```text
Error: You're importing a module that depends on `useState` into a React Server Component module. This API is only available in Client Components. To fix, mark the file (or its parent) with the `"use client"` directive.
> 1 | import { useState } from "react";
```

환경 변수는 따로 기억해 둔다. Next는 `NEXT_PUBLIC_`으로 시작하는 변수만 브라우저 번들에 값으로 박아 넣는다. 나머지는 클라이언트 코드에서 읽으면 `undefined`다. 그래서 비밀값이 번들에 바로 새지는 않지만, 서버 컴포넌트가 그 값을 props로 넘기면 payload에 그대로 실린다. payload는 HTML 안에 그대로 보이는 텍스트다.

## 서버 액션은 경계를 넘는 함수다

함수는 경계를 넘을 수 없다고 했는데 예외가 있다. 파일이나 함수에 `"use server"`를 붙인 서버 액션이다. 클라이언트 컴포넌트가 이 함수를 import해 부르면 함수 본문이 아니라 함수 id만 번들에 들어가고, 호출은 POST 요청이 된다. 장바구니 담기 버튼을 눌렀을 때 Chromium이 보낸 요청이다.

```text
POST http://127.0.0.1:3200/action
  next-action: 60818a8f335fe8fe742f61184256b7f6160520936f
  content-type: text/plain;charset=UTF-8
  accept: text/x-component
  body: [42,2]
```

`next-action` 헤더가 어떤 함수를 부를지 정하고, 본문은 인자 배열이다. 이 요청을 `curl`로 그대로 다시 보내되 수량만 바꿔 봤다.

```bash
curl -s -X POST http://127.0.0.1:3200/action \
  -H 'Next-Action: 60818a8f335fe8fe742f61184256b7f6160520936f' \
  -H 'Accept: text/x-component' -H 'Content-Type: text/plain;charset=UTF-8' \
  --data '[42,999]'
```

```text
0:{"a":"$@1","q":"","i":false,"b":"42-qp9bUyDP_LEePFVpPI"}
1:{"ok":true,"count":999}
```

서버 로그에는 `addToCart 42 999`가 찍혔다. 버튼의 UI는 수량 2만 보내게 만들었지만, 서버 액션은 누구나 부를 수 있는 공개 엔드포인트다. 액션 안에서 로그인 여부, 권한, 입력값 범위를 매번 다시 확인해야 한다. 클라이언트 컴포넌트에서 버튼을 숨겼다고 막힌 게 아니다.

## props가 무거우면 payload도 무겁다

서버 컴포넌트에서 DB 결과를 통째로 클라이언트 컴포넌트에 넘기는 코드가 흔하다. 목록 컴포넌트가 이름과 가격만 쓰는데 상품 객체 전체를 넘기는 식이다. 상품 500개를 두 방식으로 넘긴 정적 페이지를 받아 크기를 쟀다. 상품마다 긴 설명과 판매자 메모가 붙어 있다.

```tsx
// 통째로
return <ProductList items={getProducts()} />;
// 쓰는 필드만
const items = getProducts().map(({ id, name, price }) => ({ id, name, price }));
return <ProductList items={items} />;
```

```text
           HTML 전체   그중 payload 스크립트   RSC 요청 응답
통째로      483,355 B   461,816 B              443,181 B
쓰는 필드만  51,812 B    30,289 B               25,681 B
```

화면은 같지만 HTML이 아홉 배 넘게 차이 난다. 넘긴 props는 화면에 쓰든 안 쓰든 전부 payload에 적힌다. 화면에 안 보이는 판매자 메모도 페이지 소스에서 읽힌다. 크기 문제이기 전에 노출 문제다. gzip으로 압축하면 차이가 11,811바이트 대 8,454바이트로 줄어드는데, 예제 데이터가 같은 문장을 반복해서 압축이 잘 된 탓이다. 압축과 상관없이 브라우저는 풀어진 문자열을 파싱해야 한다.

## 현장에서 서버 컴포넌트를 들여다보는 법

"번들이 왜 이렇게 크지?"에서 출발하면 먼저 어떤 파일에 `"use client"`가 붙어 있고 그 파일이 무엇을 import하는지 본다. 빌드 산출물에서 그 페이지가 쓰는 클라이언트 청크 목록은 `.next/server/app/{경로}/page_client-reference-manifest.js`에 있다.

```bash
# 페이지가 쓰는 클라이언트 청크와 크기 (원본 / gzip)
cd .next
grep -o 'static/chunks/[^"]*' server/app/rsc/page_client-reference-manifest.js | sort -u |
  while read f; do echo "$f $(wc -c < $f) $(gzip -c $f | wc -c)"; done

# 특정 라이브러리가 브라우저 청크에 들어갔는지
grep -l "marked" static/chunks/*.js
```

```text
static/chunks/0umf92h1sb77c.js 13822 3546
static/chunks/2yr-ema31jnzx.js 315 277
```

"화면에 안 쓰는 데이터가 소스 보기에 보인다"면 payload를 본다. `curl -sL -H 'RSC: 1'`로 받아 큰 줄을 찾거나, 브라우저 개발자 도구의 네트워크 탭에서 `_rsc`로 걸러 화면 이동 때의 응답을 본다. 큰 줄이 어느 컴포넌트의 props인지 찾고, 쓰는 필드만 골라 넘긴다.

```bash
# payload에서 길이가 긴 줄 다섯 개
curl -sL -H 'RSC: 1' http://127.0.0.1:3200/big-full | awk '{ print length($0), substr($0, 1, 60) }' | sort -rn | head -5
```

```text
439923 7:[["children",{"s":"__PAGE__","h":512,"d":{"r":["$","$1","c
2112 0:{"P":null,"c":["","big-full"],"q":"","i":false,"t":{"t":{"
410 5:[["children",{"s":"big-full","h":512,"d":{"r":["$","$1","c
125 e:[["$","meta","0",{"charSet":"utf-8"}],["$","meta","1",{"na
109 a:["$","script","script-0",{"src":"/_next/static/chunks/3jbi
```

44만 자짜리 한 줄이 페이지(`__PAGE__`) 조각이다. 그 줄을 열어 보면 상품마다 `description`과 `sellerMemo`가 반복된다.

500 응답에 메시지 없이 `digest`만 남았다면 서버 로그에서 같은 digest를 찾는다. 함수나 클래스 인스턴스를 넘긴 경우는 로그가 문제의 prop을 `^^^^`로 짚어 준다.

## 다시 315바이트로

처음의 두 페이지는 화면이 같았지만 하나는 `marked`를 브라우저로 보냈고 하나는 결과만 보냈다. 서버 컴포넌트는 서버에서 실행된 결과를 payload라는 트리 데이터로 보내고, 클라이언트 컴포넌트는 그 트리 안에 참조와 props로 남는다. `"use client"`는 파일 단위로 경계를 긋고 그 아래 import를 모두 끌고 가므로 상호작용이 필요한 말단에만 붙인다. 경계를 넘는 props는 직렬화되어 페이지에 그대로 실리니 필요한 만큼만, 공개해도 되는 것만 넘긴다. 이 결과가 빌드 때 만들어질지 요청 때 만들어질지는 [Next.js App Router는 언제 정적이고 언제 동적인가](/posts/nextjs-static-dynamic-rendering)에서 다룬다.

## 면접에서 나올 만한 질문

### React 서버 컴포넌트와 SSR은 무엇이 다른가요?

SSR은 첫 HTML을 서버에서 만드는 렌더링 시점의 이야기고, RSC는 어떤 컴포넌트 코드가 브라우저에 가느냐의 이야기다. SSR한 컴포넌트도 코드가 번들로 내려가 하이드레이션되지만, 서버 컴포넌트는 서버에서만 실행되고 결과만 payload로 보낸다. App Router에서는 둘이 함께 쓰여서 클라이언트 컴포넌트도 첫 요청에서는 SSR된다.

### RSC payload에는 무엇이 들어 있나요?

서버 컴포넌트가 실행된 결과인 엘리먼트 트리와, 클라이언트 컴포넌트를 가리키는 참조(모듈 id, 받아야 할 청크, export 이름), 그리고 그 컴포넌트에 넘긴 props가 들어 있다. 한 줄이 하나의 조각이고 다른 조각을 `$번호`로 가리키며, 준비된 조각부터 스트리밍된다. 첫 요청에서는 HTML 안의 스크립트로, 화면 이동 때는 `RSC: 1` 요청의 응답으로 온다.

### "use client"를 붙이면 정확히 무엇이 바뀌나요?

그 파일이 서버와 클라이언트 모듈 그래프의 경계가 된다. 그 파일과 그 파일이 import하는 모든 모듈이 브라우저 번들에 들어가고, 그 컴포넌트는 첫 요청 때 SSR된 뒤 하이드레이션된다. 그래서 상호작용이 필요한 말단에만 붙이고, 서버에서 그린 내용은 `children`으로 넣는다.

### 서버 컴포넌트에서 클라이언트 컴포넌트로 함수를 넘기면 어떻게 되나요?

렌더링할 때 "Functions cannot be passed directly to Client Components" 에러가 난다. props는 payload에 직렬화되어야 하는데 함수와 클래스 인스턴스는 직렬화할 수 없기 때문이다. 동작은 클라이언트 컴포넌트 안에서 정의하고, 서버에서 실행해야 하는 동작이면 `"use server"` 서버 액션으로 만든다.

### 서버 액션을 쓸 때 보안상 주의할 점은요?

서버 액션은 `Next-Action` 헤더와 인자 배열을 담은 POST로 불리는 공개 엔드포인트다. UI가 어떤 값만 보내게 만들었어도 누구나 같은 요청을 다른 인자로 보낼 수 있으니, 액션 안에서 인증과 권한, 입력값 검증을 매번 다시 한다.

### 서버 전용 코드가 클라이언트 번들에 들어가는 걸 어떻게 막나요?

서버 전용 모듈에 `import "server-only"`를 넣으면 클라이언트 쪽 그래프에 들어왔을 때 빌드가 실패하고 import 경로를 보여 준다. 환경 변수는 `NEXT_PUBLIC_`만 번들에 들어가지만, 서버 컴포넌트가 비밀값을 props로 넘기면 payload에 실리니 넘기는 값도 확인한다.

### 서버 컴포넌트를 쓰는데 HTML이 오히려 커졌다면 무엇을 보나요?

클라이언트 컴포넌트에 넘긴 props를 본다. 첫 HTML에는 화면 HTML과 payload가 함께 들어가서, 쓰지 않는 필드까지 넘기면 그만큼 커진다. 실험에서는 상품 500개를 통째로 넘기면 483KB, 쓰는 세 필드만 넘기면 52KB였다. `RSC: 1`로 payload를 받아 긴 줄을 찾고 필요한 필드만 골라 넘긴다.
