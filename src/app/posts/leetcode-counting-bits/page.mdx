[Counting Bits](https://leetcode.com/problems/counting-bits/)는 LeetCode 338번이다. 0부터 n까지 모든 수의 1 비트 개수를 배열로 돌려준다. 수 하나의 1 개수를 세는 건 [Number of 1 Bits](/posts/leetcode-number-of-1-bits)에서 했다. 그걸 n + 1번 부르면 답은 나온다. 이 문제가 묻는 건 그보다 나은 방법, 앞에서 구한 답을 다시 쓰는 방법이다. 그래서 비트 문제이면서 동시에 가장 짧은 [동적 계획법](/posts/dynamic-programming) 문제이기도 하다.

이 글은 수마다 따로 세는 풀이에서 출발해, 점화식 세 가지(가장 높은 비트, 한 칸 민 수, 가장 낮은 1을 끈 수)와 배열을 두 배로 늘려 가는 풀이까지 간다. 비트 연산 기본은 [비트 연산 글](/posts/bit-manipulation)에 있다. 코드는 Node.js 22, Python 3.13, Java 21에서 직접 돌렸다.

## 0부터 n까지 1의 개수를 한 줄로

정수 `n`이 주어진다. 길이 n + 1인 배열 `ans`를 만들어, `ans[i]`에 i를 이진수로 썼을 때 1의 개수를 넣어 돌려준다.

- `n`은 0 이상 10^5 이하다. `n = 0`이면 `[0]`이다.
- 후속 질문으로 "O(n log n)은 쉽다. 한 번 훑어서 O(n)에 할 수 있나", "내장 함수(`__builtin_popcount` 같은 것) 없이 할 수 있나"가 붙어 있다.

10^5개에 수마다 최대 17번(2^17 = 131072) 세는 건 170만 번 정도라 시간 제한에는 걸리지 않는다. 문제의 진짜 요구는 후속 질문 쪽이다. 수마다 독립적으로 세지 말고, 이웃한 수의 답 사이 관계를 찾으라는 뜻이다.

## 0부터 8까지 손으로 써 보면

예시는 `n = 8`로 끝까지 간다.

```text
i       0   1   2    3    4     5     6     7     8
이진수  0   1   10   11   100   101   110   111   1000
1 개수  0   1   1    2    1     2     2     3     1
```

답은 `[0, 1, 1, 2, 1, 2, 2, 3, 1]`이다. 표를 오래 보면 여러 규칙이 눈에 들어온다.

- 2, 4, 8처럼 2의 거듭제곱은 1이 하나뿐이다.
- 4부터 7까지(`100`~`111`)는 0부터 3까지(`00`~`11`) 앞에 1을 붙인 모양이다. 그래서 개수가 0~3의 개수에 1씩 더한 값이다.
- 6(`110`)은 3(`11`) 뒤에 0을 붙였고, 7(`111`)은 3 뒤에 1을 붙였다. 짝수는 절반과 같고, 홀수는 절반보다 하나 많다.
- 6(`110`)에서 가장 낮은 1을 끄면 4(`100`)가 되고, 개수가 하나 준다.

이 관찰 하나하나가 점화식 하나가 된다. 그 전에 관찰 없이 푸는 방법부터 본다.

## 수마다 따로 세기

[Number of 1 Bits](/posts/leetcode-number-of-1-bits)의 풀이를 0부터 n까지 반복한다. 맨 아래 비트를 보고 한 칸씩 미는 방법을 그대로 쓰면 이렇다.

```js
function countBits(n) {
  const ans = [];
  for (let i = 0; i <= n; i++) {
    let x = i, c = 0;
    while (x !== 0) {
      c += x & 1; // 맨 아래 비트
      x >>>= 1;   // 한 칸 민다
    }
    ans.push(c);
  }
  return ans;
}

console.log(JSON.stringify(countBits(8)), JSON.stringify(countBits(0)));
```

```text
[0,1,1,2,1,2,2,3,1] [0]
```

수 i 하나에 비트 길이만큼, 즉 약 log₂ i번 돈다. 전체는 O(n log n)이다. 공간은 답 배열을 빼면 O(1)이다.

안쪽 반복을 Kernighan(`x &= x - 1`)으로 바꾸면 켜진 비트 수만큼만 돈다. 0부터 n까지의 1 개수를 모두 더한 값은 평균 약 (log₂ n) / 2개라 반복이 절반쯤으로 준다. 측정에서도 1000만 개에서 730ms가 172ms로 줄었다. 등급은 여전히 O(n log n)이다.

이 풀이의 한계는 수마다 처음부터 센다는 점이다. 7을 셀 때 7 = `111`의 세 비트를 다 보는데, 바로 앞 단계에서 3 = `11`을 이미 셌다. 7은 3 뒤에 1을 붙인 것뿐이다. 이미 아는 답을 다시 계산하고 있다.

## 한 칸 민 수의 답에 맨 아래 비트를 더한다

i를 오른쪽으로 한 칸 밀면(`i >> 1`) 맨 아래 비트 하나가 빠지고 나머지는 그대로다. 그러니 i의 1 개수는 "한 칸 민 수의 1 개수"에 "빠진 비트(`i & 1`)"를 더한 값이다.

```text
ans[i] = ans[i >> 1] + (i & 1)

ans[6] = ans[3] + 0 = 2     110 → 11 에 0을 붙였다
ans[7] = ans[3] + 1 = 3     111 → 11 에 1을 붙였다
```

`i >> 1`은 i보다 항상 작다(i가 1 이상일 때). 그래서 0부터 차례로 채우면 `ans[i]`를 계산하는 순간 `ans[i >> 1]`은 이미 채워져 있다. 작은 문제의 답으로 큰 문제의 답을 만드는, 동적 계획법의 바텀업 모양이다.

```js
function countBits(n) {
  const ans = new Array(n + 1).fill(0); // ans[0] = 0
  for (let i = 1; i <= n; i++) {
    ans[i] = ans[i >> 1] + (i & 1);     // 절반의 답 + 맨 아래 비트
  }
  return ans;
}

console.log(JSON.stringify(countBits(8)), JSON.stringify(countBits(0)), JSON.stringify(countBits(5)));
```

```text
[0,1,1,2,1,2,2,3,1] [0] [0,1,1,2,1,2]
```

아래 그림에서 다음을 누르면 i가 하나씩 오른쪽으로 가며 답이 쌓인다. 강조된 칸이 지금 꺼내 쓰는 `i >> 1`이다. 칸에는 i의 이진수를 적었다.

칸 하나에 배열 조회 한 번, 시프트·AND·덧셈 한 번씩이다. 시간 O(n), 공간은 답 배열 말고는 O(1)이다. 내장 함수도 쓰지 않으니 후속 질문 두 개를 모두 만족한다. 면접에서 이 문제의 기본 답으로 내는 풀이다.

### Python과 Java

```python
from typing import List

class Solution:
    def countBits(self, n: int) -> List[int]:
        ans = [0] * (n + 1)
        for i in range(1, n + 1):
            ans[i] = ans[i >> 1] + (i & 1)  # 맨 아래 비트를 뺀 수의 답 + 맨 아래 비트
        return ans

    def countBitsBuiltin(self, n: int) -> List[int]:
        return [i.bit_count() for i in range(n + 1)]

s = Solution()
print(s.countBits(8), s.countBits(0))
print(s.countBitsBuiltin(8))
```

```text
[0, 1, 1, 2, 1, 2, 2, 3, 1] [0]
[0, 1, 1, 2, 1, 2, 2, 3, 1]
```

Python에서는 재미있는 일이 생긴다. `n = 10^5`에서 점화식 풀이가 6.92ms, 수마다 `bit_count()`를 부르는 풀이가 3.15ms였다. 등급은 점화식이 낫지만, 파이썬 반복문에서 리스트 조회와 연산을 하는 비용이 C로 구현된 `bit_count` 한 번보다 크다. 면접에서는 점화식을 쓰고, "실제로는 내장 함수가 더 빠를 수 있다"고 말할 수 있으면 좋다. 다만 문제의 후속 질문이 내장 함수를 쓰지 말라고 하니 답으로는 점화식을 낸다.

```java
import java.util.Arrays;

class Solution {
    public int[] countBits(int n) {
        int[] ans = new int[n + 1];          // 0으로 채워져 있다. ans[0] = 0
        for (int i = 1; i <= n; i++) {
            ans[i] = ans[i >> 1] + (i & 1);  // 한 칸 민 수의 답에 맨 아래 비트를 더한다
        }
        return ans;
    }

    public static void main(String[] args) {
        Solution s = new Solution();
        System.out.println(Arrays.toString(s.countBits(8)) + " " + Arrays.toString(s.countBits(0)));
    }
}
```

```text
[0, 1, 1, 2, 1, 2, 2, 3, 1] [0]
```

Java의 `int[]`는 만들 때 0으로 채워지니 `ans[0]`을 따로 넣지 않아도 된다. i가 양수라서 `>>`와 `>>>`의 차이도 없다. `ans[i >> 1] + (i & 1)`의 괄호는 Java와 JavaScript 모두 꼭 필요하다. 이유는 뒤의 "틀리기 쉬운 곳"에서 본다.

### 위에서 내려오며 기억하는 버전

같은 점화식을 재귀로 쓰면 탑다운 DP가 된다. "i의 답은 `i >> 1`의 답에 맨 아래 비트를 더한 것"을 그대로 함수로 옮기고, 한 번 구한 답은 메모에 적어 둔다.

```js
function countBits(n) {
  const memo = new Map([[0, 0]]); // 0의 답은 0
  let calls = 0;
  const f = (i) => {
    calls++;
    if (memo.has(i)) return memo.get(i); // 이미 구했다
    const v = f(i >> 1) + (i & 1);       // 절반의 답을 먼저 구한다
    memo.set(i, v);
    return v;
  };
  const ans = [];
  for (let i = 0; i <= n; i++) ans.push(f(i));
  return [ans, calls];
}
const [a, c] = countBits(8);
console.log(JSON.stringify(a), c);
```

```text
[0,1,1,2,1,2,2,3,1] 17
```

0부터 차례로 부르면 `i >> 1`은 언제나 이미 메모에 있어서 호출이 i마다 두 번(자기 자신과 절반)으로 끝난다. n = 8에서 17번, n = 10^5에서 200001번이었다. 재귀 깊이는 메모가 비어 있어도 비트 길이(최대 17) 정도라 스택이 넘칠 걱정은 없다. 그래도 이 문제에서는 탑다운을 고를 이유가 없다. 어차피 0부터 n까지 전부 구해야 하니 순서가 정해져 있고, 바텀업 반복문이 `Map` 조회와 함수 호출 비용 없이 같은 일을 한다. 탑다운이 빛나는 건 일부 값만 필요해서 필요한 칸만 채우고 싶을 때다.

## 앞의 절반에 1을 붙인 수

0~8 표에서 본 두 번째 규칙을 쓰는 점화식도 있다. 4부터 7까지는 0부터 3까지 앞에 1을 하나 붙인 수다. 일반적으로 i가 2^k 이상 2^(k+1) 미만이면, i에서 가장 높은 비트 2^k를 뗀 수 `i - 2^k`는 이미 구한 작은 수이고, 1이 하나 적다.

```text
ans[i] = ans[i - offset] + 1     (offset = i 이하의 가장 큰 2의 거듭제곱)

ans[6] = ans[6 - 4] + 1 = ans[2] + 1 = 2
ans[7] = ans[7 - 4] + 1 = ans[3] + 1 = 3
```

`offset`은 i가 다음 2의 거듭제곱에 닿을 때마다 바꾼다.

```js
function countBits(n) {
  const ans = new Array(n + 1).fill(0);
  let offset = 1;                           // 지금 구간의 가장 높은 비트 값
  for (let i = 1; i <= n; i++) {
    if (offset * 2 === i) offset = i;       // 2, 4, 8, ...에 닿으면 구간이 바뀐다
    ans[i] = ans[i - offset] + 1;           // 가장 높은 비트를 뗀 수의 답 + 1
  }
  return ans;
}

console.log(JSON.stringify(countBits(8)));
```

```text
[0,1,1,2,1,2,2,3,1]
```

아래 그림은 같은 n = 8을 이 점화식으로 채운다. 4에 닿는 순간 offset이 4로 바뀌고, 4~7은 0~3의 답을 하나씩 올려 그대로 베낀다.

## 가장 낮은 1을 끈 수의 답에 1을 더한다

세 번째 점화식은 Number of 1 Bits에서 쓴 `i & (i - 1)`이다. 이 연산은 i에서 가장 낮은 1 하나를 끈다. 끈 수는 i보다 작고, 1이 정확히 하나 적다.

```text
ans[i] = ans[i & (i - 1)] + 1

ans[6] = ans[110 & 101] + 1 = ans[4] + 1 = 2
ans[7] = ans[111 & 110] + 1 = ans[6] + 1 = 3
```

```js
function countBits(n) {
  const ans = new Array(n + 1).fill(0);
  for (let i = 1; i <= n; i++) {
    ans[i] = ans[i & (i - 1)] + 1; // 가장 낮은 1을 끈 수는 1이 하나 적다
  }
  return ans;
}

console.log(JSON.stringify(countBits(8)));
```

```text
[0,1,1,2,1,2,2,3,1]
```

시간 O(n), 공간 O(1)(답 제외)이다. 세 점화식 중 가장 짧다. offset 같은 상태도, 맨 아래 비트를 더하는 덧셈도 없이 "1을 하나 뺀 수에 1을 더한다"가 전부다. 왜 맞는지 설명하려면 `i & (i - 1)`을 알아야 해서, 면접에서는 첫 번째 점화식을 먼저 쓰고 이걸 대안으로 말하는 경우가 많다.

세 점화식이 가리키는 "이미 구한 작은 수"가 다르다는 점이 재미있다. 6을 예로 들면 첫 번째는 3(`110` → `11`), 두 번째는 2(`110` → `10`), 세 번째는 4(`110` → `100`)를 본다. 어느 쪽이든 6보다 작은 수라 이미 채워져 있고, 6과 1의 개수 차이가 정확히 알려져 있다. 동적 계획법에서 "어떤 작은 문제에 기대느냐"를 바꾸면 점화식이 여러 개 나오는 좋은 예다.

## 배열을 두 배씩 늘려 가기

두 번째 점화식을 배열 연산으로 쓰면 이렇게도 된다. `[0]`에서 시작해, 지금 배열 전체에 1을 더한 것을 뒤에 붙인다. `[0]` → `[0, 1]` → `[0, 1, 1, 2]` → `[0, 1, 1, 2, 1, 2, 2, 3]`. 길이가 두 배가 될 때마다 앞에 1이 붙은 구간 하나가 채워진다.

```js
function countBits(n) {
  let ans = [0];
  while (ans.length <= n) {
    ans = ans.concat(ans.map((c) => c + 1)); // 앞 구간에 1씩 더해 뒤에 붙인다
  }
  return ans.slice(0, n + 1);                // 넘친 부분을 잘라 낸다
}

console.log(JSON.stringify(countBits(8)), JSON.stringify(countBits(0)));
```

```text
[0,1,1,2,1,2,2,3,1] [0]
```

반복마다 `ans`를 찍어 보면 배열이 어떻게 자라는지 보인다. n = 8이면 길이 16까지 만든 뒤 9개만 남긴다.

```text
[0,1]
[0,1,1,2]
[0,1,1,2,1,2,2,3]
[0,1,1,2,1,2,2,3,1,2,2,3,2,3,3,4]
```

시간은 등급으로는 O(n)이다. 1 + 2 + 4 + ... 가 최종 길이의 두 배를 넘지 않기 때문이다. 하지만 `concat`과 `map`이 매번 새 배열을 만들고, 최악에는 필요한 길이의 거의 두 배까지 만든다. 측정에서 1000만 개에 541ms로 점화식 풀이보다 4~6배 느렸다. 코드가 그림처럼 읽힌다는 것 말고는 고를 이유가 적다.

## 여섯 풀이를 재 보면

| 풀이 | 시간 | 추가 공간 | 언제 고르나 |
|---|---|---|---|
| 수마다 시프트로 세기 | O(n log n) | O(1) | 출발점. 관찰 없이 바로 쓸 때 |
| 수마다 Kernighan | O(n log n) | O(1) | 같은 등급이지만 반복이 절반쯤 |
| `ans[i >> 1] + (i & 1)` | O(n) | O(1) | 기본 답. 가장 설명하기 쉽다 |
| `ans[i - offset] + 1` | O(n) | O(1) | 구간을 베끼는 그림으로 설명할 때 |
| `ans[i & (i - 1)] + 1` | O(n) | O(1) | 가장 짧은 코드 |
| 두 배씩 늘리기 | O(n) | O(n) 임시 배열 | 그림으로 보여 줄 때. 실제로는 느리다 |

### 답을 담는 그릇이 더 크게 갈린다

1000만 칸이면 풀이보다 배열 종류가 더 중요해진다. 1의 개수는 32비트 수라도 최대 32라서 한 바이트에 들어간다. `Uint8Array`에 같은 점화식을 돌려 봤다.

```js
function countBitsTyped(n) {
  const ans = new Uint8Array(n + 1);              // 칸마다 1바이트, 0으로 채워져 있다
  for (let i = 1; i <= n; i++) ans[i] = ans[i >> 1] + (i & 1);
  return ans;
}
```

```text

10000000 typedRaw  19.25ms sum 114434632
```

일반 배열 풀이의 130ms가 19ms로 줄었다. 메모리도 `node --expose-gc`로 재 보니 일반 배열이 76.3MB, `Uint8Array`가 9.5MB였다. 일반 배열은 칸마다 8바이트 가까이 쓰고, 타입 배열은 정확히 1바이트다. 데이터가 작은 정수로 정해져 있으면 타입 배열이 속도와 메모리 둘 다 낫다. 단, LeetCode는 일반 배열을 기대하니 `Array.from`으로 바꿔 돌려줘야 하고, 그 변환에만 400ms 넘게 걸렸다. 이 문제의 답으로 쓸 일은 없고, 실무에서 큰 표를 만들 때 기억해 둘 일이다.

## 틀리기 쉬운 곳

### 괄호를 빼먹은 점화식

```js
function wrong(n) {
  const ans = new Array(n + 1).fill(0);
  for (let i = 1; i <= n; i++) ans[i] = ans[i >> 1] + i & 1; // 괄호가 없다
  return ans;
}
console.log(JSON.stringify(wrong(8)));
```

```text
[0,1,1,0,1,0,0,1,1]
```

JavaScript, Java, C 계열에서 `&`는 `+`보다 우선순위가 낮다. 그래서 `ans[i >> 1] + i & 1`은 `(ans[i >> 1] + i) & 1`로 계산돼 0과 1만 나온다. 에러 없이 그럴듯한 숫자가 나와서 알아채기 어렵다. 비트 연산이 섞인 식에는 괄호를 아끼지 않는다. Python도 `&`가 `+`보다 낮아서 같은 실수가 그대로 난다.

### ans[0]을 채우지 않기

```js
function wrong2(n) {
  const ans = [];
  for (let i = 1; i <= n; i++) ans[i] = ans[i >> 1] + (i & 1);
  return ans;
}
console.log(JSON.stringify(wrong2(4)));
```

```text
[null,null,null,null,null]
```

`ans[0]`이 비어 있으면 `undefined + 1`이 `NaN`이 되고, 그 `NaN`이 모든 칸으로 번진다. JSON으로 찍으면 `null`이 된다. `new Array(n + 1).fill(0)`처럼 0으로 채워 두거나 `ans[0] = 0`을 먼저 넣는다. Java의 `int[]`나 Python의 `[0] * (n + 1)`은 이 문제가 없다.

### offset을 바꾸는 조건

두 번째 점화식에서 offset을 `i === offset * 2`일 때 바꾸는 건 맞다. 흔한 실수는 `Math.log2`로 offset을 매번 계산하다 부동소수점 오차를 만나거나, offset을 `i & -i`(가장 낮은 1)와 헷갈리는 것이다. offset은 가장 높은 1의 값이다. 매번 계산하고 싶으면 `1 << (31 - Math.clz32(i))`로 정수 연산만 쓴다.

### n = 0

답은 `[0]`이다. 반복이 한 번도 돌지 않고 0으로 채운 길이 1짜리 배열이 그대로 나가면 맞다. 두 배씩 늘리는 풀이는 `ans.length <= n`이 처음부터 거짓이라 `[0]`을 잘라 그대로 돌려준다.

## 조건을 바꿔 묻는다면

### 배열이 아니라 1의 총개수만 필요하다면

0부터 n까지 1의 개수를 다 더한 값만 묻는다면 배열을 만들 필요가 없다. 자리마다 따로 센다. 0, 1, 2, ...를 이진수로 나열하면 맨 아래 자리는 `0101...`, 둘째 자리는 `0011 0011...`, 셋째 자리는 `0000 1111...`처럼 값 p = 2^b마다 0이 p개, 1이 p개씩 번갈아 나온다. 0부터 n까지 n + 1개를 이 주기로 나누면 꽉 찬 주기마다 1이 p개, 남는 부분에서 p를 넘친 만큼 1이 더 있다.

```js
function totalOnes(n) {
  let total = 0;
  for (let p = 1; p <= n; p *= 2) {      // p = 2^b, 이 자리의 값
    const cycle = p * 2;                 // 0이 p개, 1이 p개씩 번갈아 나온다
    const full = Math.floor((n + 1) / cycle);
    const rest = (n + 1) % cycle;
    total += full * p + Math.max(0, rest - p);
  }
  return total;
}
console.log(totalOnes(8), totalOnes(100000), totalOnes(10000000), totalOnes(0), totalOnes(1e12));
```

```text
13 815030 114434632 0 19809942118413
```

앞의 측정에서 배열을 다 더한 합(815030, 114434632)과 같다. 자리 수만큼만 도니 O(log n)이고, 10^12처럼 배열을 만들 수 없는 크기도 바로 답한다. 10^12의 결과는 BigInt로 같은 계산을 한 값과도 맞췄다. 2^53을 넘는 n이면 처음부터 BigInt로 계산한다.

### l부터 r까지의 1 개수 합을 여러 번 묻는다면

배열을 한 번 만들고 누적 합 `prefix[i] = ans[0] + ... + ans[i]`을 같이 만들어 두면 질문마다 `prefix[r] - prefix[l - 1]`로 O(1)에 답한다. n이 너무 커서 배열을 못 만들면 위의 `totalOnes(r) - totalOnes(l - 1)`로 질문마다 O(log n)이다.

### 수 하나의 1 개수만 필요하다면

[Number of 1 Bits](/posts/leetcode-number-of-1-bits)다. 여기서 쓴 점화식은 "여러 수의 답을 함께 구할 때"만 이득이다. 수 하나라면 Kernighan이나 내장 함수가 낫다. 반대로 Number of 1 Bits의 8비트 표 풀이는 이 문제의 점화식으로 표를 채운다. 두 문제가 서로를 돕는다.

### 비슷한 문제

- [Climbing Stairs](/posts/leetcode-climbing-stairs): 앞에서 구한 답 두 개로 다음 답을 만드는 1차원 DP. 이 문제의 점화식과 같은 바텀업 모양이다.
- [Power of Two](/posts/leetcode-power-of-two): 이 표에서 값이 1인 칸이 곧 2의 거듭제곱이다.
- 같은 패턴의 다른 문제: [Single Number](/posts/leetcode-single-number), [Reverse Bits](/posts/leetcode-reverse-bits), [Sum of Two Integers](/posts/leetcode-sum-of-two-integers).

이 문제에서 기억할 건 비트 요령보다 "이웃한 수의 답 사이 관계"다. i의 답은 i보다 작은 어떤 수의 답과 정확히 정해진 만큼 차이 난다. 그 작은 수를 `i >> 1`로 잡느냐, 가장 높은 비트를 뗀 수로 잡느냐, 가장 낮은 1을 끈 수로 잡느냐에 따라 점화식이 셋 나온다.

## 면접에서 나올 만한 질문

### O(n)에 푸는 점화식을 설명해 주세요.

`ans[i] = ans[i >> 1] + (i & 1)`이다. i를 한 칸 오른쪽으로 밀면 맨 아래 비트만 빠지고 나머지 1은 그대로라서, 한 칸 민 수의 답에 빠진 비트를 더하면 된다. `i >> 1`은 i보다 작으니 0부터 차례로 채우면 항상 이미 구해 둔 값이다. 칸마다 상수 번 연산이라 O(n)이다.

### 이게 왜 동적 계획법인가요?

큰 문제(i의 답)를 이미 푼 작은 문제(i보다 작은 수의 답)로 만들고, 작은 문제의 답을 표에 저장해 다시 계산하지 않기 때문이다. 작은 수부터 채우는 바텀업 방식이다. 수마다 독립적으로 세는 O(n log n) 풀이와의 차이가 바로 이 재사용이다.

### 다른 점화식도 있나요?

두 가지가 더 있다. 가장 높은 비트를 떼면 1이 하나 줄어드니 `ans[i - offset] + 1`(offset은 i 이하의 가장 큰 2의 거듭제곱)이고, 가장 낮은 1을 끄면 하나 줄어드니 `ans[i & (i - 1)] + 1`이다. 셋 다 O(n)이고, 기대는 작은 수가 다를 뿐이다.

### 공간 복잡도는 얼마인가요?

답 배열 n + 1칸은 반드시 돌려줘야 하니 빼고 보면 추가 공간은 O(1)이다. 답 배열까지 세면 O(n)이다. 1000만 칸처럼 크면 일반 배열 대신 `Uint8Array`를 쓰면 메모리가 76MB에서 9.5MB로 줄었다. 1의 개수는 최대 32라 한 바이트에 들어가기 때문이다.

### 0부터 n까지 1의 총개수만 필요하고 n이 10^12라면요?

배열을 만들 수 없으니 자리마다 센다. 값이 p인 자리는 0이 p개, 1이 p개씩 번갈아 나오니, n + 1개를 2p 주기로 나눠 꽉 찬 주기마다 p개, 남은 부분에서 p를 넘친 만큼 더한다. 자리 수만큼 도니 O(log n)이다.

### `ans[i >> 1] + i & 1`로 쓰면 무엇이 잘못되나요?

`&`가 `+`보다 우선순위가 낮아서 `(ans[i >> 1] + i) & 1`로 계산된다. 결과가 0이나 1만 나오는데 에러가 없어서 놓치기 쉽다. JavaScript, Java, Python 모두 같으니 비트 연산이 섞인 식에는 괄호를 친다.
