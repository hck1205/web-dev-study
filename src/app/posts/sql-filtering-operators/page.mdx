10월 수강 신청 건수를 뽑았다. 대시보드는 7건인데 내 쿼리는 5건이다.

```sql
SELECT count(*) FROM enrollments
WHERE enrolled_at BETWEEN '2026-10-01' AND '2026-10-31';
```

같은 날 강의 검색창에 `%`를 쳤다. 제목에 퍼센트가 들어간 `100% 실습 Git`을 찾으려던 건데 강의 다섯 개가 다 나왔다. 둘 다 에러가 없고, 쿼리만 보면 맞아 보인다. `WHERE`에 쓰는 연산자는 몇 개 안 되지만, 저마다 경계를 어디에 두는지, NULL을 어떻게 보는지, 어떤 글자를 특별하게 읽는지가 다르다. 그 차이가 이렇게 조용히 숫자를 바꾼다.

이 글은 `IN`과 `NOT IN`, `BETWEEN`과 시간 범위, `LIKE`와 `ILIKE`를 PostgreSQL 16으로 하나씩 따져 보고, 검색 조건이 인덱스를 타는지까지 실행 계획으로 확인한다. 같은 데이터로 이어지는 시리즈의 두 번째 글이다. 첫 글 [SELECT의 논리적 처리 순서](/posts/sql-logical-order)에서 문장 전체의 순서를 봤고, 여기서는 ② `WHERE` 단계 안을 들여다본다. 다음 글은 [집계 함정](/posts/sql-aggregation-pitfalls)이다. NULL과 3값 논리의 기초, 서브쿼리 `NOT IN`이 0행이 되는 이유는 [SELECT와 NULL 글](/posts/sql-select-where-null)에 있다.

기준은 Ubuntu 24.04의 PostgreSQL 16.15, DB 시간대는 `Asia/Seoul`, 정렬 규칙(collation)은 `C.UTF-8`이다. 출력은 모두 실제로 돌린 결과다. MySQL 8과 다른 점은 문서로 확인해 짧게 덧붙였다.

## 목록에 NULL 하나가 섞이면

`IN`은 `=`를 `OR`로 이은 것이다. `city IN ('seoul', 'busan')`은 `city = 'seoul' OR city = 'busan'`과 같다. 그러니 `NOT IN`은 `<>`를 `AND`로 이은 것이 된다. `city NOT IN ('seoul', 'busan')`은 `city <> 'seoul' AND city <> 'busan'`이다. 이 한 줄이 이 섹션의 전부다.

화면의 필터에서 "서울 제외"를 고르면 앱이 `NOT IN`을 만든다고 해 보자. 목록을 만드는 코드가 선택되지 않은 값을 NULL로 채워 넘기는 버그가 있었다.

```sql
SELECT name, city FROM students WHERE city NOT IN ('seoul');
SELECT name, city FROM students WHERE city NOT IN ('seoul', NULL);
```

```text
 name | city
------+-------
 lee  | busan
 jung | daegu
(2 rows)

 name | city
------+------
(0 rows)
```

첫 쿼리에서도 park은 빠졌다. 도시를 모르니 서울이 아닌지도 모른다. 둘째 쿼리는 아무것도 안 나온다. 아래 그림에서 다음을 누르면 행마다 `<>`를 `AND`로 이어 계산한다.

`IN ('seoul', NULL)`은 이런 문제가 없다. `OR`로 이었으니 `seoul = 'seoul'`이 참이면 나머지가 모름이어도 참이다. NULL이 섞여도 결과가 줄지 않으니 버그가 드러나지 않고 지나간다. 같은 목록을 `IN`과 `NOT IN` 양쪽에 쓰는 코드라면 `NOT IN` 쪽만 갑자기 0행이 된다.

앱에서 값 목록을 넘길 때는 `IN (...)`보다 배열 하나를 받는 `= ANY($1)`가 낫다. 자리표시자 개수가 목록 길이에 따라 바뀌지 않아서 문장이 하나로 고정되고, 빈 목록도 처리된다. `IN ()`은 문법 에러다.

```sql
SELECT name FROM students WHERE id IN ();
SELECT name FROM students WHERE id = ANY ('{}'::int[]);       -- 빈 배열: 아무것도 안 맞는다
SELECT count(*) FROM students WHERE id <> ALL ('{}'::int[]);  -- 빈 배열: 모두 맞는다
```

```text
ERROR:  syntax error at or near ")"
LINE 1: SELECT name FROM students WHERE id IN ();
                                               ^
 name
------
(0 rows)

 count
-------
     5
(1 row)
```

`NOT IN`에 해당하는 건 `<> ALL`이다. 빈 배열이면 "제외할 게 없다"는 뜻이라 모두 나온다. 의도와 맞는지는 화면에 따라 다르다. "아무것도 고르지 않으면 전체"인 필터라면 맞고, "고른 것만 빼라"인데 목록이 비는 것 자체가 버그라면 앱에서 먼저 막는다. 배열에 NULL이 섞이면 `<> ALL`도 `NOT IN`과 똑같이 0행이 된다.

"NULL은 다른 값으로 친다"가 의도라면 NULL을 직접 다룬다. `city IS DISTINCT FROM 'seoul'`은 NULL을 하나의 값처럼 비교해서 park까지 돌려준다. 서브쿼리 결과로 `NOT IN`을 쓰는 경우는 같은 함정에 실행 계획 문제까지 겹친다. `NOT EXISTS`와의 비교는 [서브쿼리와 EXISTS·LATERAL 글](/posts/sql-subqueries-exists-lateral)에서 다룬다.

MySQL 8도 `NOT IN`과 NULL의 결과는 같다. 표준 3값 논리를 따르기 때문이다. 대신 배열 타입이 없어서 `= ANY(배열)`은 못 쓰고, 드라이버가 `IN (?, ?, ?)`를 목록 길이만큼 펼쳐 준다.

## 10월은 31일 0시에 끝난다

처음의 5건으로 돌아간다. 어느 행이 빠졌는지 본다.

```sql
SELECT id, enrolled_at FROM enrollments
WHERE enrolled_at BETWEEN '2026-10-01' AND '2026-10-31'
ORDER BY id;
```

```text
 id |      enrolled_at
----+------------------------
  2 | 2026-10-01 00:00:00+09
  3 | 2026-10-05 13:20:00+09
  4 | 2026-10-12 09:00:00+09
  5 | 2026-10-15 08:00:00+09
  6 | 2026-10-20 21:00:00+09
(5 rows)
```

10월 31일에 들어온 7번(18:30)과 8번(23:59:30)이 없다. `BETWEEN a AND b`는 `>= a AND <= b`이고, `enrolled_at`은 시각까지 가진 `timestamptz`다. 날짜만 쓴 `'2026-10-31'`은 그날의 0시가 된다.

```sql
SELECT timestamptz '2026-10-31' AS end_value;
```

```text
       end_value
------------------------
 2026-10-31 00:00:00+09
(1 row)
```

그래서 범위가 31일 0시에서 끝나 버렸다. 흔한 땜질은 끝을 `'2026-10-31 23:59:59'`로 바꾸는 것이다. 이 데이터에서는 7건이 나와서 고쳐진 것처럼 보인다. 그런데 `timestamptz`는 마이크로초까지 저장한다. 23:59:59.4에 들어온 수강을 트랜잭션 안에서 하나 넣어 보면 차이가 난다.

```sql
BEGIN;
INSERT INTO enrollments (student_id, course_id, status, score, enrolled_at)
VALUES (5, 5, 'active', NULL, '2026-10-31 23:59:59.4+09');

SELECT count(*) AS between_235959 FROM enrollments
WHERE enrolled_at BETWEEN '2026-10-01' AND '2026-10-31 23:59:59';

SELECT count(*) AS half_open FROM enrollments
WHERE enrolled_at >= '2026-10-01' AND enrolled_at < '2026-11-01';
ROLLBACK;
```

```text
INSERT 0 1
 between_235959
----------------
              7
(1 row)

 half_open
-----------
         8
(1 row)
```

마지막 0.6초가 빠졌다. 시간 범위는 시작은 포함하고 끝은 빼는 반열린 구간 `[시작, 다음 시작)`으로 쓴다. `>= '2026-10-01' AND < '2026-11-01'`이면 10월 31일의 몇 시 몇 분이든, 소수점 몇 자리든 다 들어온다. 끝 날짜를 계산할 필요도 없다. 월의 마지막 날이 28일인지 31일인지 몰라도 "다음 달 1일 미만"이면 된다.

`BETWEEN`의 양쪽 포함은 반대 방향으로도 틀린다. 9월과 10월을 각각 `BETWEEN '2026-09-01' AND '2026-10-01'`, `BETWEEN '2026-10-01' AND '2026-11-01'`로 세면 2건과 8건이 나온다. 9개 행인데 합이 10이다. 10월 1일 0시의 2번과 11월 1일 0시의 9번이 경계에 걸려 두 달에 다 들어갔다. 반열린 구간끼리는 맞닿아도 겹치지 않는다.

`BETWEEN`은 정수나 날짜(`date`)처럼 값이 끊어져 있는 타입에는 괜찮다. `date` 컬럼이면 `BETWEEN '2026-10-01' AND '2026-10-31'`가 10월 전체다. 문제는 연속된 값인 `timestamp`, `timestamptz`, `numeric`이다. 하나 더, `BETWEEN 10 AND 1`처럼 작은 값을 뒤에 쓰면 에러 없이 거짓이 된다. 순서를 상관없게 하려면 PostgreSQL의 `BETWEEN SYMMETRIC`을 쓴다(MySQL에는 없다).

## 같은 쿼리, 다른 시간대

반열린 구간으로 고친 쿼리를 배치 서버에서 돌렸다. 숫자는 7건으로 같았다. 그런데 행이 달랐다. 배치 서버의 DB 연결은 세션 시간대가 UTC였다.

```sql
SET timezone = 'UTC';
SELECT id, enrolled_at FROM enrollments
WHERE enrolled_at >= '2026-10-01' AND enrolled_at < '2026-11-01'
ORDER BY id;
```

```text
 id |      enrolled_at
----+------------------------

  4 | 2026-10-12 00:00:00+00
  5 | 2026-10-14 23:00:00+00
  6 | 2026-10-20 12:00:00+00
  7 | 2026-10-31 09:30:00+00
  8 | 2026-10-31 14:59:30+00

(7 rows)
```

`timestamptz`는 저장할 때 시각을 UTC 기준의 한 순간으로 바꿔 두고, 보여 줄 때 세션 시간대로 바꿔 준다. 문제는 입력이다. 시간대 없이 쓴 `'2026-10-01'`은 세션 시간대의 0시로 읽힌다. UTC 세션에서는 한국 시각 10월 1일 오전 9시다. 그래서 한국 시각 10월 1일 0시의 2번이 빠지고, 한국 시각 11월 1일 0시(UTC 10월 31일 15시)의 9번이 들어왔다. 개수가 같아서 대시보드만 보면 모른다.

고치는 방법은 경계에 시간대를 명시하는 것이다. `'2026-10-01 00:00+09'`처럼 오프셋을 붙이거나, `timestamp '2026-10-01' AT TIME ZONE 'Asia/Seoul'`로 "서울 기준 0시"를 계산한다. UTC 세션에서 후자는 `2026-09-30 15:00:00+00`이 된다. 서머타임이 있는 지역이라면 고정 오프셋보다 지역 이름(`'America/New_York'`)을 쓰는 쪽이 맞다.

UTC 세션에서 이 두 방법으로 고친 쿼리는 모두 7건, 2번부터 8번을 돌려줬다. 현장에서 "로컬에서는 맞는데 서버에서만 숫자가 다르다"는 문의가 오면 `SHOW timezone;`부터 양쪽에서 친다. DB 기본값(`postgresql.conf`나 `ALTER DATABASE ... SET timezone`), 접속하는 역할에 걸린 설정, 드라이버가 연결할 때 보내는 값이 모두 세션 시간대를 바꿀 수 있다. MySQL 8의 `TIMESTAMP` 컬럼도 세션의 `time_zone`으로 변환되고, `DATETIME`은 시간대 없이 적힌 그대로 저장된다.

## 날짜로 잘라 비교하면 인덱스를 못 쓴다

"10월 15일 하루"를 고를 때 `enrolled_at::date = '2026-10-15'`라고 쓰기 쉽다. 결과는 맞지만 행이 많아지면 느리다. 20만 줄짜리 `enrollments_big`([첫 글](/posts/sql-logical-order#논리-순서와-실제-실행은-다르다)에서 만든 테이블, `enrolled_at`에 인덱스가 있다)으로 비교한다.

```sql
EXPLAIN ANALYZE SELECT count(*) FROM enrollments_big
WHERE enrolled_at::date = '2026-10-15';
```

```text
                                                       QUERY PLAN
-------------------------------------------------------------------------------------------------------------------------
 Aggregate  (cost=4602.50..4602.51 rows=1 width=8) (actual time=29.217..29.218 rows=1 loops=1)
   ->  Seq Scan on enrollments_big  (cost=0.00..4600.00 rows=1000 width=0) (actual time=26.225..29.175 rows=631 loops=1)
         Filter: ((enrolled_at)::date = '2026-10-15'::date)
         Rows Removed by Filter: 199369
 Planning Time: 0.513 ms
 Execution Time: 29.293 ms
(6 rows)
```

```sql
EXPLAIN ANALYZE SELECT count(*) FROM enrollments_big
WHERE enrolled_at >= '2026-10-15' AND enrolled_at < '2026-10-16';
```

```text

------------------------------------------------------------------------------------------------------------------------------------------------------------------
 Aggregate  (cost=25.88..25.89 rows=1 width=8) (actual time=0.216..0.217 rows=1 loops=1)
   ->  Index Only Scan using enrollments_big_enrolled_at_idx on enrollments_big  (cost=0.42..24.38 rows=598 width=0) (actual time=0.100..0.180 rows=631 loops=1)
         Index Cond: ((enrolled_at >= '2026-10-15 00:00:00+09'::timestamp with time zone) AND (enrolled_at < '2026-10-16 00:00:00+09'::timestamp with time zone))
         Heap Fetches: 0
 Planning Time: 0.129 ms
 Execution Time: 0.242 ms
```

첫 계획의 `Seq Scan`과 `Rows Removed by Filter: 199369`는 20만 줄을 다 읽고 631줄만 남겼다는 뜻이다. 둘째는 `Index Cond`로 범위만 읽었다. 29ms가 0.24ms가 됐다. `Index Cond`에 문자열이 `+09`로 바뀌어 들어간 것도 보인다. 앞 섹션의 세션 시간대가 여기서 적용된다.

컬럼에 함수를 씌우면 인덱스를 못 쓰는 일반 원리는 [인덱스가 안 타는 이유 글](/posts/db-index-pitfalls)에 있다. `timestamptz`에는 사정이 하나 더 있다. 그럼 `enrolled_at::date`로 식 인덱스를 만들면 되지 않을까.

```sql
CREATE INDEX ON enrollments_big ((enrolled_at::date));
```

```text
ERROR:  functions in index expression must be marked IMMUTABLE
```

`timestamptz`를 날짜로 바꾼 결과는 세션 시간대에 따라 달라진다. 같은 입력에 같은 결과가 보장되지 않으니(IMMUTABLE이 아니니) 인덱스에 저장할 수 없다. 범위 조건으로 쓰는 게 답이다.

## LIKE가 특별하게 읽는 두 글자

이제 검색창의 `%`다. `LIKE`의 패턴에서 `%`는 "아무 글자나 0개 이상", `_`는 "아무 글자 하나"다. 앱은 사용자 입력을 `'%' || 입력 || '%'`로 감싸 보냈다. 입력이 `%`면 패턴은 `'%%%'`가 되고, 세 글자가 모두 "아무 글자나"라서 전부 맞는다.

```sql
SELECT title FROM courses WHERE title LIKE '%%%';     -- 모두 나온다
SELECT title FROM courses WHERE title LIKE '%\%%';    -- %라는 글자가 들어간 것만
```

```text
      title
-----------------
 SQL 기초
 PostgreSQL 튜닝
 React 입문
 Docker 실전
 100% 실습 Git
(5 rows)

     title
---------------
 100% 실습 Git
(1 row)
```

PostgreSQL의 `LIKE`는 기본 이스케이프 문자가 백슬래시다. `\%`는 진짜 퍼센트 글자, `\_`는 진짜 밑줄이다. 아래 패턴을 조각으로 나눠 보면 각 글자가 어떻게 읽히는지 나온다.

```sql
SELECT t, t LIKE '100%' AS plain, t LIKE '100\%%' AS escaped
FROM (VALUES ('100% 실습 Git'), ('1000명 SQL'), ('100 SQL')) v(t);
```

```text

---------------+-------+---------
 100% 실습 Git | t     | t
 1000명 SQL    | t     | f
 100 SQL       | t     | f
(3 rows)
```

`_`도 같다. 아이디 검색에 `a_b`를 치면 `axb`도 맞는다. 사용자 입력을 패턴에 넣을 때는 앱에서 세 글자(`\`, `%`, `_`)를 먼저 이스케이프한다. 백슬래시를 먼저 바꿔야 나중에 붙인 백슬래시가 다시 바뀌지 않는다.

```js
// 사용자 입력을 LIKE 패턴 안에 글자 그대로 넣기
const escapeLike = (s) => s.replace(/[\\%_]/g, (c) => "\\" + c);
const pattern = `%${escapeLike(input)}%`;   // 값은 반드시 바인딩 파라미터로 넘긴다
```

이스케이프는 SQL 주입 방어가 아니다. 패턴의 의미를 지키는 일이다. 값 자체는 언제나 바인딩 파라미터로 넘긴다([SQL 주입 글](/posts/sql-injection)).

대소문자를 무시하려면 `ILIKE`를 쓴다. PostgreSQL 전용이다. 정규식이 필요하면 `~`(대소문자 구분)와 `~*`(무시)가 있다. 실제로 `'React' LIKE 'react'`는 `f`, `'React' ILIKE 'react'`와 `'React' ~* '^re'`는 `t`다.

MySQL 8은 여기서 크게 다르다. 기본 정렬 규칙(`utf8mb4_0900_ai_ci`)이 대소문자와 악센트를 무시해서 `LIKE` 자체가 대소문자를 가리지 않고, `ILIKE`는 없다. 같은 쿼리를 옮기면 PostgreSQL에서 검색 결과가 줄어든다. 이스케이프 기본값이 백슬래시인 건 같다.

## 앞이 열린 검색과 인덱스

검색이 느려지는 건 패턴 모양 때문이다. 20만 개의 강의 제목을 가진 `courses_big`을 만들고, 제목에 보통 B-tree 인덱스를 건다.

```sql
CREATE TABLE courses_big AS
SELECT g AS id,
       (ARRAY['PostgreSQL','React','Docker','Kubernetes','Redis','Kafka','Spring'])[1 + g % 7]
       || ' ' || (ARRAY['입문','실전','튜닝','심화','기초'])[1 + (g / 7) % 5]
       || ' ' || g AS title                       -- 'React 입문 1', 'Docker 입문 2', ...
FROM generate_series(1, 200000) g;
ALTER TABLE courses_big ADD PRIMARY KEY (id);
CREATE INDEX courses_big_title_idx ON courses_big (title);
ANALYZE courses_big;
SET max_parallel_workers_per_gather = 0;          -- 계획을 읽기 쉽게
```

앞이 정해진 `LIKE 'Redis 튜닝 1234%'`부터 본다.

```text
 Aggregate  (cost=3908.05..3908.06 rows=1 width=8) (actual time=19.306..19.307 rows=1 loops=1)
   ->  Seq Scan on courses_big  (cost=0.00..3908.00 rows=20 width=0) (actual time=13.385..19.297 rows=3 loops=1)
         Filter: (title ~~ 'Redis 튜닝 1234%'::text)
         Rows Removed by Filter: 199997
 Planning Time: 0.153 ms
 Execution Time: 19.330 ms
```

인덱스가 있는데 `Seq Scan`이다(`~~`는 `LIKE`의 내부 이름이다). 같은 범위를 `>=`와 `<`로 직접 쓰면 이 인덱스로 `Index Only Scan`이 되는데, `LIKE`는 그 범위로 바꿔 주지 않았다. 이 DB의 정렬 규칙이 `C`가 아니라서다. 이럴 때는 글자 단위로 비교하는 `text_pattern_ops` 인덱스를 따로 만든다. 그 이유는 [인덱스가 안 타는 이유 글](/posts/db-index-pitfalls)에서 자세히 다룬다.

```sql
CREATE INDEX courses_big_title_pattern_idx ON courses_big (title text_pattern_ops);
```

```text
 Aggregate  (cost=8.49..8.50 rows=1 width=8) (actual time=0.107..0.108 rows=1 loops=1)
   ->  Index Only Scan using courses_big_title_pattern_idx on courses_big  (cost=0.42..8.44 rows=20 width=0) (actual time=0.096..0.099 rows=3 loops=1)
         Index Cond: ((title ~>=~ 'Redis 튜닝 1234'::text) AND (title ~<~ 'Redis 튜닝 1235'::text))
         Filter: (title ~~ 'Redis 튜닝 1234%'::text)
         Heap Fetches: 3
 Planning Time: 0.401 ms
 Execution Time: 0.142 ms
```

`Index Cond`를 보면 `LIKE`가 "1234 이상, 1235 미만"이라는 범위로 바뀌었다. 19.3ms가 0.14ms가 됐다. 검색창은 대개 앞이 열린 `'%튜닝 1234%'`라서 이 인덱스로는 안 된다. B-tree는 앞글자부터 정렬돼 있어서 시작점을 모르면 범위를 못 만든다. 중간 일치를 인덱스로 찾으려면 `pg_trgm` 확장의 GIN 인덱스를 쓴다. 문자열을 세 글자 조각으로 잘라 조각마다 행 목록을 만들어 두는 방식이다. 조각이 어떻게 잘리는지는 [JSONB와 검색 글](/posts/postgres-jsonb-search)에 그림으로 있다.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX courses_big_title_trgm_idx ON courses_big USING gin (title gin_trgm_ops);
EXPLAIN ANALYZE SELECT count(*) FROM courses_big WHERE title LIKE '%튜닝 1234%';
```

```text
 Aggregate  (cost=129.04..129.05 rows=1 width=8) (actual time=1.254..1.256 rows=1 loops=1)
   ->  Bitmap Heap Scan on courses_big  (cost=55.89..128.99 rows=20 width=0) (actual time=1.235..1.246 rows=21 loops=1)
         Recheck Cond: (title ~~ '%튜닝 1234%'::text)
         Heap Blocks: exact=2
         ->  Bitmap Index Scan on courses_big_title_trgm_idx  (cost=0.00..55.89 rows=20 width=0) (actual time=1.220..1.220 rows=21 loops=1)
               Index Cond: (title ~~ '%튜닝 1234%'::text)
 Planning Time: 0.450 ms
 Execution Time: 1.312 ms
```

34.7ms(같은 쿼리를 인덱스 전에 돌린 값)가 1.3ms가 됐다. 같은 인덱스가 `ILIKE`도 받는다. `ILIKE '%redis 튜닝 1234%'`는 `Index Cond: (title ~~* ...)`로 2.6ms였다. 대소문자를 무시하려고 `lower(title)` 식 인덱스를 따로 만들 필요가 없다.

다 되는 건 아니다. 검색어가 두 글자면 온전한 세 글자 조각이 나오지 않아서 인덱스가 범위를 좁히지 못한다.

```sql
EXPLAIN ANALYZE SELECT count(*) FROM courses_big WHERE title LIKE '%34%';
```

```text
 Aggregate  (cost=3928.20..3928.21 rows=1 width=8) (actual time=20.523..20.524 rows=1 loops=1)
   ->  Seq Scan on courses_big  (cost=0.00..3908.00 rows=8081 width=0) (actual time=0.011..20.073 rows=7940 loops=1)
         Filter: (title ~~ '%34%'::text)
         Rows Removed by Filter: 192060
 Planning Time: 0.088 ms
 Execution Time: 20.539 ms
```

플래너는 `Seq Scan`을 골랐다. 한국어는 두 글자 단어가 많아서 이 한계가 자주 걸린다. 검색창에서 두 글자 미만은 막거나, 단어 단위 검색이 필요하면 전문 검색(`tsvector`)으로 간다. 그리고 GIN 인덱스는 공짜가 아니다. 여기서 trgm 인덱스는 6072kB로 테이블(11MB)의 반을 넘었고, 쓰기 때마다 조각을 모두 갱신한다.

## 검색 조건을 리뷰할 때 보는 것

`WHERE` 조건이 들어간 코드를 리뷰할 때 이 글의 내용은 몇 가지 질문으로 줄어든다.

목록 필터에 `NOT IN`이나 `<> ALL`이 있으면 목록에 NULL이 들어올 수 있는 경로를 찾는다. 컬럼 쪽이 NULL인 행이 빠지는 게 의도인지도 묻는다. 빠지면 안 되는 행이라면 `IS DISTINCT FROM`이나 `OR col IS NULL`을 쓴다.

시간 범위는 `BETWEEN`과 `23:59:59`를 보면 반열린 구간으로 바꾼다. 경계 문자열에 시간대가 없으면 그 쿼리가 어느 세션 시간대에서 돌지 확인한다. 배치, 리포트 도구, 앱 서버의 시간대가 서로 다른 경우가 많다. `col::date =`나 `date_trunc(...) =`처럼 컬럼을 잘라 비교하면 범위로 바꾼다.

검색창 `LIKE`는 사용자 입력의 `%`, `_`, `\`를 이스케이프하는지, 앞이 열린 패턴이라면 trgm 인덱스가 있는지, 너무 짧은 검색어를 막는지를 본다. 테이블이 작을 때는 모두 빠르게 돌아서, 이런 문제는 데이터가 늘어난 뒤 운영에서 처음 드러난다. 개발 DB에서도 `EXPLAIN`으로 `Seq Scan`과 `Rows Removed by Filter`가 큰지 확인해 둔다.

## LIKE를 직접 구현해 보기

`LIKE`의 규칙은 세 가지뿐이다. `%`는 아무 글자나 0개 이상, `_`는 아무 글자 하나, 백슬래시 다음 글자는 그 글자 자체. 그리고 문자열 전체가 맞아야 한다. `likeMatch(text, pattern)`를 완성해 보자. 테스트의 기대값은 같은 입력을 PostgreSQL에서 돌린 결과와 맞췄다.

    dp = next;
  }

## 경계와 특수 문자를 의심한다

`WHERE` 연산자가 숫자를 조용히 바꾸는 방식은 몇 가지로 모인다. `NOT IN`은 `<>`를 `AND`로 이은 것이라 목록의 NULL 하나에 전부 모름이 된다. `BETWEEN`은 양쪽 끝을 포함해서 연속된 시간에서는 끝이 짧거나 경계가 겹치니 반열린 구간을 쓰고, 경계에는 시간대를 적는다. `LIKE`는 `%`와 `_`를 특별하게 읽으니 사용자 입력은 이스케이프하고, 앞이 열린 검색은 trgm 인덱스로 받친다. 거른 행을 묶고 세는 단계에서 생기는 함정은 [집계 함정 글](/posts/sql-aggregation-pitfalls)에서 이어 간다.

## 면접에서 나올 만한 질문

### NOT IN 목록에 NULL이 있으면 왜 결과가 0행인가요?

`NOT IN`은 `<>`를 `AND`로 이은 것이라 `x <> NULL`이 항상 모름(NULL)이 되기 때문이다. 참 AND 모름은 모름이고, `WHERE`는 참인 행만 남기니 어떤 행도 통과하지 못한다. `IN`은 `OR`로 이어서 다른 값이 참이면 통과하니 같은 목록이어도 `NOT IN` 쪽만 깨진다.

### 앱에서 가변 길이 목록을 조건으로 넘길 때 IN 대신 무엇을 쓰나요?

PostgreSQL에서는 배열 하나를 바인딩하는 `= ANY($1)`가 낫다. 목록 길이와 상관없이 문장이 하나로 고정되고, `IN ()`은 문법 에러지만 빈 배열은 0행으로 처리된다. 제외는 `<> ALL($1)`인데 빈 배열이면 모든 행이 나오니 의도와 맞는지 확인한다.

### timestamptz 컬럼에 BETWEEN으로 한 달을 고르면 무엇이 문제인가요?

날짜만 쓴 끝 값이 그날 0시로 해석돼 마지막 날 대부분이 빠진다. `23:59:59`로 바꿔도 소수 초가 빠지고, 양쪽 포함이라 월 경계의 0시 행이 두 달에 다 들어간다. `>= 시작 AND < 다음 시작`인 반열린 구간으로 쓴다.

### 같은 쿼리가 서버마다 다른 행을 돌려줍니다. 어디부터 보나요?

시간대 없는 날짜 문자열이 있으면 세션 시간대부터 본다. `timestamptz` 비교에서 `'2026-10-01'`은 세션 `TimeZone`의 0시로 해석되니 UTC 세션과 KST 세션의 범위가 9시간 어긋난다. 양쪽에서 `SHOW timezone;`을 확인하고, 경계에 `+09`나 `AT TIME ZONE 'Asia/Seoul'`을 명시한다.

### enrolled_at::date = '2026-10-15'는 왜 느리고, 식 인덱스로 해결되나요?

컬럼을 변환하면 B-tree 인덱스의 정렬 순서를 쓸 수 없어 전체를 읽는다. `timestamptz`를 `date`로 바꾸는 결과는 세션 시간대에 따라 달라 IMMUTABLE이 아니므로 식 인덱스도 만들 수 없다. 하루 범위를 `>= '2026-10-15' AND < '2026-10-16'`로 쓰면 기존 인덱스로 범위만 읽는다.

### 사용자 검색어를 LIKE에 넣을 때 주의할 점은요?

`%`와 `_`가 와일드카드라서 입력에 섞이면 의도보다 많이 맞는다. 앱에서 `\`, `%`, `_`를 백슬래시로 이스케이프한 뒤 앞뒤에 `%`를 붙이고, 값은 바인딩 파라미터로 넘긴다. 이스케이프는 패턴의 의미를 지키는 일이고, SQL 주입 방어는 바인딩이 맡는다.

### LIKE '%키워드%' 검색을 빠르게 하려면 어떻게 하나요?

B-tree는 앞이 열린 패턴의 시작점을 모르니 `pg_trgm`의 GIN 인덱스(`gin_trgm_ops`)를 만든다. 세 글자 조각으로 후보 행을 찾고 다시 확인하는 방식이라 `ILIKE`도 같은 인덱스로 된다. 다만 두 글자 이하 검색어는 조각이 없어 인덱스가 소용없고, 인덱스가 크고 쓰기가 무거워지는 비용이 있다.

### 앞이 정해진 LIKE 'abc%'인데도 인덱스를 안 탑니다. 왜 그런가요?

DB 정렬 규칙이 `C`가 아니면 기본 B-tree는 `LIKE`를 범위 조건으로 바꾸지 못한다. 실행 계획에 `Seq Scan`과 `Filter: (title ~~ ...)`가 보이면 이 경우다. `text_pattern_ops`로 인덱스를 따로 만들면 `Index Cond`에 `~>=~`, `~<~` 범위가 나타난다.
