주문 API의 응답이 갑자기 느려졌다. 주문 코드를 열어 보니 저장 뒤에 포인트 적립, 알림 발송, 검색 색인 갱신을 차례로 HTTP로 부르고 있다. 그날 느려진 건 알림 서버 하나였는데, 주문 API가 알림 서버의 응답을 기다리느라 같이 느려졌다. 다음 주에는 추천 팀이 "주문이 나면 우리도 알려 달라"고 했고, 주문 서비스는 또 배포해야 했다.

이 글은 이 구조를 이벤트로 바꿀 때 정해야 하는 것들을 본다. 무엇을 이벤트로 만들고 안에 무엇을 담을지, 흐름을 누가 쥘지, DB에 쓴 사실을 빠짐없이 내보내는 방법, 데이터가 잠깐 어긋나는 걸 어떻게 받아 낼지, 그리고 이벤트가 어디서 사라졌는지 찾는 법이다. 예제는 PostgreSQL 16에서 직접 돌렸다.

이 주제의 다른 글: 동기 호출과 비동기 메시징의 기본 비교, 사가의 개념은 [모놀리스에서 마이크로서비스로](/posts/microservices)에, 아웃박스 테이블을 `SKIP LOCKED`로 폴링하는 기본 구현은 [서비스 규모별 DB 설계](/posts/db-architecture-by-scale)에 있다. 큐의 ack와 재전달은 [메시지 큐 기초](/posts/message-queue-basics), 토픽과 소비자 그룹은 [발행·구독](/posts/pub-sub), 사가를 단계별로 짜는 법은 [사가 패턴](/posts/saga-pattern)에서 다룬다. 여기서는 그 위에서 설계를 고르는 질문만 본다.

## 명령은 부탁하고 이벤트는 알린다

메시지를 브로커에 올린다고 다 이벤트는 아니다. 먼저 명령과 이벤트를 구분해야 설계가 흔들리지 않는다.

명령(command)은 "이걸 해 달라"는 부탁이다. `ReserveStock`, `SendEmail`처럼 동사 원형으로 짓고, 받는 쪽이 정해져 있다. 받는 쪽은 거절할 수 있다. 재고가 없으면 `ReserveStock`은 실패한다. 보내는 쪽은 결과에 관심이 있다.

이벤트(event)는 "이런 일이 있었다"는 알림이다. `OrderPaid`, `StockReserved`처럼 과거형으로 짓는다. 이미 일어난 일이라 거절할 수 없고, 받는 쪽이 몇인지 보내는 쪽은 모른다. 듣는 쪽이 그 사실을 보고 무엇을 할지는 듣는 쪽이 정한다.

그림의 화살표 방향이 의존 방향이다. 명령은 주문이 재고를 안다. 이벤트는 포인트와 알림이 주문의 이벤트를 안다. 새 구독자가 생겨도 주문 쪽은 바뀌지 않는다.

흔한 실수는 이름만 이벤트이고 속은 명령인 메시지다. 주문 서비스가 `WelcomeEmailRequested`를 발행하고 알림 서비스만 그걸 듣는다면, 그건 이름을 바꾼 `SendWelcomeEmail` 명령이다. 주문 서비스가 여전히 "가입하면 메일을 보내야 한다"는 알림 서비스의 규칙을 알고 있다. 이벤트라면 `UserSignedUp`을 내고, 메일을 보낼지는 알림 서비스가 정한다.

둘을 섞어 써도 된다. 재고 예약처럼 결과를 꼭 알아야 하는 일은 명령으로 보내고 응답(또는 결과 이벤트)을 받는다. 일어난 사실을 퍼뜨리는 일은 이벤트로 한다. 브로커가 같아도 토픽이나 큐를 나눠서 어느 쪽인지 드러나게 둔다.

## 이벤트 하나에 무엇을 담을까

이벤트의 몸통에 무엇을 넣을지는 세 갈래로 나뉜다. 이름은 마틴 파울러가 정리한 것을 그대로 쓴다.

첫째는 이벤트 알림(event notification)이다. "1042번 주문이 결제됐다"와 ID만 담는다. 자세한 내용이 필요하면 구독자가 주문 서비스 API를 다시 부른다. 메시지가 작고 스키마를 바꿀 일이 적다.

둘째는 이벤트 운반 상태 전이(Event-Carried State Transfer)다. 구독자가 필요한 상태를 이벤트에 같이 싣는다. 금액, 사용자, 상품 목록까지 넣어서 구독자가 다시 묻지 않아도 되게 한다. 구독자는 그걸로 자기 DB에 사본을 만든다.

아래 그림에서 두 방식의 차이가 보인다. 알림 방식은 이벤트가 한 번 가고 조회가 한 번 돌아온다. 구독자가 열이면 조회도 열이다.

알림 방식에서 놓치기 쉬운 게 네 번째 단계다. 구독자가 다시 조회한 상태는 이벤트가 난 순간의 상태가 아니다. 결제 이벤트를 받고 조회했는데 그 사이 취소가 일어났다면 "결제됨"을 처리하면서 "취소됨" 데이터를 보게 된다. 순서에 민감한 처리라면 이벤트에 그 시점의 값을 넣는 쪽이 낫다.

상태를 실어 보내면 이번엔 필드가 약속이 된다. 주문 서비스가 `amount`의 단위를 원에서 센트로 바꾸면 구독자 전부가 깨진다. 그래서 필드는 더하기만 하고, 의미가 바뀌면 새 타입(`order.paid.v2`)으로 낸다. 구독자는 모르는 필드를 무시하고 필요한 필드만 읽는다(tolerant reader).

어떤 방식이든 봉투는 같게 맞추는 편이 좋다. CNCF의 CloudEvents 1.0 규격이 이 봉투를 정해 두었다. 아래 조각을 누르면 각 필드가 왜 필요한지 나온다.

`specversion`, `id`, `source`, `type`이 필수이고 나머지는 선택이다. 꼭 이 규격을 따르지 않아도 되지만, 이벤트 ID, 발생 시각, 타입과 버전, 대상의 버전 번호 넷은 어떤 형식이든 넣는다. 뒤에서 중복과 순서를 다룰 때 전부 쓰인다.

## 상태 대신 사건을 저장하는 이벤트 소싱

세 번째 갈래는 결이 다르다. 이벤트 소싱(event sourcing)은 이벤트를 다른 서비스에 알리는 방법이 아니라 저장하는 방법이다. 포인트 잔액을 `balance = 200`으로 덮어쓰지 않고, 잔액을 바꾼 사건을 차례로 쌓는다. 현재 잔액은 사건을 처음부터 더해서 얻는다.

```sql
-- 사건을 쌓는 표. 같은 지갑(stream_id)에서 version은 1부터 빈틈없이 는다
CREATE TABLE events (
  stream_id   text        NOT NULL,
  version     int         NOT NULL,
  event_type  text        NOT NULL,
  data        jsonb       NOT NULL,
  recorded_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (stream_id, version)   -- 같은 버전을 두 번 쓰면 여기서 막힌다
);

INSERT INTO events (stream_id, version, event_type, data) VALUES
  ('wallet-7', 1, 'PointsEarned',  '{"amount": 410, "orderId": 1042}'),
  ('wallet-7', 2, 'PointsUsed',    '{"amount": 200, "orderId": 1050}'),
  ('wallet-7', 3, 'PointsEarned',  '{"amount": 90,  "orderId": 1051}'),
  ('wallet-7', 4, 'PointsExpired', '{"amount": 100}');

-- 사건을 모두 더해 현재 잔액을 얻는다
SELECT sum(CASE event_type WHEN 'PointsEarned' THEN 1 ELSE -1 END
           * (data->>'amount')::int) AS balance,
       max(version) AS version
FROM events WHERE stream_id = 'wallet-7';
```

```text
 balance | version 
---------+---------
     200 |       4
(1 row)
```

얻는 것은 분명하다. 무슨 일이 왜 일어났는지가 전부 남아서 감사와 디버깅이 쉽다. "지난달 15일 기준 잔액"도 그날까지의 사건만 더하면 나온다. 새 화면이 필요하면 사건을 처음부터 다시 흘려서 새 조회용 테이블(프로젝션)을 만든다.

대가도 크다. 사건이 쌓일수록 다시 읽는 비용이 커져서 몇백 건마다 스냅숏을 저장해 두고 그 뒤만 읽는다. 조회는 거의 항상 따로 만든 프로젝션에서 하니 쓰기와 읽기 모델이 갈라지고(CQRS), 프로젝션은 잠깐 늦는다. 사건의 스키마는 영원히 남는다. 3년 전 형식의 사건도 지금 코드가 읽을 수 있어야 해서, 읽을 때 옛 형식을 새 형식으로 바꿔 주는 변환(업캐스팅)을 계속 끌고 간다. 개인정보 삭제 요청이 오면 지울 수 없는 로그에서 어떻게 지울지도 정해야 한다(사람별 키로 암호화해 두고 키를 버리는 방법을 쓰기도 한다).

그래서 이벤트 소싱은 서비스 전체에 거는 게 아니라, 이력 자체가 업무인 곳(원장, 포인트, 재고 이동, 주문 상태 변화)에만 쓴다. 이벤트 기반 아키텍처를 한다고 이벤트 소싱까지 해야 하는 것도 아니다. 앞의 두 갈래는 평범한 상태 저장과 잘 맞는다.

직접 짜 보자. 사건 목록을 받아 잔액과 버전을 돌려주는 함수다. 사건은 순서가 섞여 올 수 있으니 버전 순으로 정렬해서 접고, 버전이 1부터 이어지지 않으면 빠진 사건이 있다는 뜻이니 `{ error: "gap", at: 빠진 버전 }`을 돌려준다.

## 흐름을 누가 쥐나

이벤트만으로 여러 단계를 잇는 걸 코레오그래피라고 한다. 지휘자 없이 각자 앞 사람의 동작을 보고 다음 동작을 하는 춤이라는 뜻이다. 주문이 `OrderPlaced`를 내면 재고가 듣고 예약한 뒤 `StockReserved`를 내고, 결제가 그걸 듣고 결제한 뒤 `PaymentCompleted`를 내고, 배송이 그걸 듣는다.

단계가 셋쯤일 때는 깔끔하다. 중앙이 없으니 한 곳이 병목이 되지 않고, 서비스끼리 서로를 직접 부르지 않는다. 문제는 단계가 늘 때다. 마지막 단계를 보면 결제가 실패했을 때 재고와 주문이 각자 그 이벤트를 들어야 한다. 전체 흐름을 아는 코드가 어디에도 없어서 "주문이 지금 몇 단계에 있나"를 물을 곳이 없다. 어느 단계가 이벤트를 안 내고 조용히 멈추면 아무도 모른다. 순서를 바꾸려면 여러 서비스의 구독을 같이 고쳐야 한다.

오케스트레이션은 흐름을 한 곳에 둔다. 주문 사가 오케스트레이터가 재고에 `ReserveStock` 명령을 보내고, 결과를 받고, 결제에 `ChargePayment`를 보낸다. 흐름이 코드 한 곳에 보이고, 단계마다 타임아웃을 걸 수 있고, 상태를 물을 곳이 생긴다. 대신 오케스트레이터가 모든 참여자를 알고, 업무 규칙이 그쪽으로 몰리기 쉽다.

고르는 기준은 이렇게 잡는다. 서로 독립적인 반응(포인트 적립, 알림, 검색 색인)은 코레오그래피로 둔다. 순서가 있고, 실패하면 앞 단계를 되돌려야 하고, "지금 어디까지 했나"를 사용자에게 보여 줘야 하는 흐름(주문, 결제, 환불)은 오케스트레이션으로 짠다. 한 시스템 안에 둘이 섞이는 게 보통이다. 보상 트랜잭션과 오케스트레이터 구현은 [사가 패턴](/posts/saga-pattern)에서 이어진다.

## 아웃박스를 id 순서로 읽으면 이벤트가 빠진다

DB에 쓴 사실을 브로커로 내보낼 때는 아웃박스를 쓴다. 주문과 이벤트를 한 트랜잭션에 쓰고, 따로 도는 릴레이가 이벤트 행을 브로커로 옮긴다. 왜 필요한지와 `published_at` 표시 + `FOR UPDATE SKIP LOCKED`로 옮기는 기본형은 [서비스 규모별 DB 설계](/posts/db-architecture-by-scale)에 있다.

여기서는 그 다음에 흔히 하는 최적화의 함정을 본다. 보낸 행에 표시하는 대신 "마지막으로 보낸 id"만 기억해 두고 `WHERE id > 마지막 id`로 읽으면, 행을 고칠 필요가 없어 가볍다. Kafka Connect의 JDBC 소스 커넥터가 증가하는 열로 읽는 방식도 이 원리다. 그런데 `bigserial`의 번호는 INSERT 순서로 정해지고, 다른 트랜잭션에 보이는 건 커밋 순서다. 둘은 다르다.

트랜잭션 A가 먼저 1번을 받고 커밋을 늦게 하고, 트랜잭션 B가 2번을 받고 먼저 커밋했다. 그 사이 릴레이가 두 번 읽었다.

```sql
-- 세션 A: 1번을 받았지만 아직 커밋하지 않았다
BEGIN;
INSERT INTO outbox (aggregate_id, event_type, payload)
VALUES (201, 'OrderPaid', '{"orderId":201}') RETURNING id;

-- 세션 B: 2번을 받고 바로 커밋 (자동 커밋)
INSERT INTO outbox (aggregate_id, event_type, payload)
VALUES (202, 'OrderPaid', '{"orderId":202}') RETURNING id;

-- 릴레이 1회차: 마지막으로 보낸 id는 0
SELECT id, aggregate_id, event_type FROM outbox WHERE id > 0 ORDER BY id;

-- 세션 A: 이제 커밋
COMMIT;

-- 릴레이 2회차: 1회차에서 2번까지 보냈으니 2보다 큰 것만
SELECT id, aggregate_id, event_type FROM outbox WHERE id > 2 ORDER BY id;
```

```text

----+--------------+------------
  2 |          202 | OrderPaid
(1 row)

-- 릴레이 2회차
 id | aggregate_id | event_type 
----+--------------+------------
(0 rows)

-- 표에는 둘 다 있다
 id | aggregate_id | event_type 
----+--------------+------------
  1 |          201 | OrderPaid
  2 |          202 | OrderPaid
(2 rows)
```

고치는 방법은 세 가지다. 첫째는 기본형으로 돌아가 행마다 보냈다는 표시를 하는 것이다. 늦게 커밋된 행도 `published_at IS NULL`이니 다음 차례에 잡힌다. 쓰기가 한 번 더 들지만 가장 단순하다.

둘째는 "아직 끝나지 않은 트랜잭션보다 앞선 것만 읽는" 방법이다. 행마다 트랜잭션 ID를 적어 두고, 현재 스냅숏에서 아직 진행 중인 가장 오래된 트랜잭션(`pg_snapshot_xmin`)보다 작은 것만 읽는다. 같은 실험을 다시 했다.

```sql
-- 행마다 쓴 트랜잭션의 ID를 기본값으로 남긴다 (xid8은 PostgreSQL 13부터)
CREATE TABLE outbox2 (
  id           bigserial PRIMARY KEY,
  txid         xid8      NOT NULL DEFAULT pg_current_xact_id(),
  aggregate_id bigint    NOT NULL,
  event_type   text      NOT NULL
);

-- 릴레이: 진행 중인 트랜잭션 중 가장 오래된 것보다 앞선 행만 읽는다
SELECT id, txid, aggregate_id, pg_snapshot_xmin(pg_current_snapshot()) AS xmin
FROM outbox2
WHERE txid < pg_snapshot_xmin(pg_current_snapshot())
ORDER BY txid, id;
```

```text

----+------+--------------+------
(0 rows)

-- A가 커밋한 뒤
 id |  txid  | aggregate_id |  xmin  
----+--------+--------------+--------
  1 | 905472 |          201 | 905474
  2 | 905473 |          202 | 905474
(2 rows)
```

A가 열려 있는 동안에는 이미 커밋된 2번도 내보내지 않고 기다린다. A가 끝나면 둘이 함께 나간다. 대신 DB 어딘가에 오래 열린 트랜잭션이 하나라도 있으면(분석 쿼리, 잊힌 `BEGIN`) xmin이 멈추고 릴레이 전체가 멈춘다. 이 방식을 쓰면 `pg_stat_activity`에서 오래된 트랜잭션을 감시하고 `idle_in_transaction_session_timeout`을 걸어 둔다.

셋째는 테이블을 읽지 않고 WAL을 읽는 방법이다. 다음 절에서 본다.

## WAL에서 바로 읽는 아웃박스

PostgreSQL은 모든 변경을 WAL(먼저 쓰는 로그)에 남긴다. `wal_level = logical`이면 이 로그를 "어느 테이블에 어떤 행이 들어갔다"로 풀어서 읽을 수 있다. 이걸 논리 디코딩이라고 하고, Debezium 같은 CDC 도구가 이 위에서 돈다. 읽는 쪽이 어디까지 읽었는지는 복제 슬롯이 기억한다.

공유 클러스터의 설정을 바꿀 수 없어서 `wal_level = logical`로 띄운 별도 인스턴스에서 돌렸다. 디코딩 플러그인은 PostgreSQL에 들어 있는 `test_decoding`이다(Debezium은 보통 `pgoutput`을 쓴다).

```sql
-- 슬롯을 만든다. 이 순간부터의 변경을 슬롯이 붙잡아 둔다
SELECT * FROM pg_create_logical_replication_slot('outbox_slot', 'test_decoding');

-- 1) 주문과 아웃박스 행을 한 트랜잭션에
BEGIN;
INSERT INTO orders (user_id, amount, status) VALUES (7, 41000, 'paid');
INSERT INTO outbox (aggregate_id, event_type, payload)
VALUES (currval('orders_id_seq'), 'OrderPaid', '{"orderId": 1, "amount": 41000}');
COMMIT;

-- 2) 테이블 없이 WAL에 메시지만 남기기 (true = 트랜잭션과 함께 커밋될 때만)
BEGIN;
INSERT INTO orders (user_id, amount, status) VALUES (8, 9000, 'paid');
SELECT pg_logical_emit_message(true, 'outbox', '{"type":"OrderPaid","orderId":2}');
COMMIT;

-- 3) 롤백한 이벤트
BEGIN;
INSERT INTO outbox (aggregate_id, event_type, payload) VALUES (3, 'OrderPaid', '{"orderId": 3}');
ROLLBACK;

-- 슬롯이 무엇을 내보낼지 미리 본다 (peek은 위치를 옮기지 않는다)
SELECT lsn, xid, data FROM pg_logical_slot_peek_changes('outbox_slot', NULL, NULL);
```

```text
    lsn    | xid |                    data
-----------+-----+------------------------------------------------------------------------
 0/1928798 | 733 | BEGIN 733
 0/1928800 | 733 | table public.orders: INSERT: id[bigint]:1 user_id[bigint]:7 amount[integer]:41000 status[text]:'paid'
 0/1928958 | 733 | table public.outbox: INSERT: id[bigint]:1 aggregate_id[bigint]:1 event_type[text]:'OrderPaid' payload[jsonb]:'{"amount": 41000, "orderId": 1}' created_at[timestamp with time zone]:'2026-10-20 14:25:13.518031+00'
 0/1928AC0 | 733 | COMMIT 733
 0/1928AC0 | 734 | BEGIN 734
 0/1928AC0 | 734 | table public.orders: INSERT: id[bigint]:2 user_id[bigint]:8 amount[integer]:9000 status[text]:'paid'
 0/1928BB0 | 734 | message: transactional: 1 prefix: outbox, sz: 32 content:{"type":"OrderPaid","orderId":2}
 0/1928BE0 | 734 | COMMIT 734
(8 rows)
```

볼 곳이 세 군데다. 변경이 트랜잭션 단위로 `BEGIN`과 `COMMIT` 사이에 묶여 커밋된 순서대로 나온다. 앞 절의 "번호는 먼저, 커밋은 나중" 문제가 생기지 않는다. 롤백한 3번 이벤트는 아예 없다. 그리고 `pg_logical_emit_message`로 남긴 메시지는 테이블에 행을 만들지 않고도 같은 트랜잭션의 일부로 나온다. 아웃박스 테이블이 커지는 걸 걱정하지 않아도 된다는 뜻이다(Debezium도 이 메시지를 읽을 수 있다).

그림의 마지막 단계가 운영에서 가장 조심할 부분이다. 슬롯은 읽는 쪽이 확인한 위치까지 WAL을 지우지 못하게 붙잡는다. CDC가 멈춘 채 주문이 계속 들어오면 WAL이 쌓인다. 슬롯을 만들어 둔 채 아웃박스 20만 건을 넣고 확인했다.

```sql
-- 슬롯이 붙잡고 있는 WAL 양
SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
FROM pg_replication_slots;
```

```text
  slot_name  | active | retained_wal 
-------------+--------+--------------
 outbox_slot | f      | 38 MB
(1 row)
```

20만 건에 38MB다. CDC가 주말 내내 멈춰 있으면 이게 디스크를 채우고, 디스크가 차면 DB 전체가 쓰기를 못 한다.

<Callout kind="warning">
`active`가 `f`인 채 `retained_wal`이 계속 크는 슬롯은 디스크를 채우는 중이다. 쓰지 않는 슬롯이면 `SELECT pg_drop_replication_slot('outbox_slot');`로 지운다. 지우면 CDC는 그 사이 변경을 잃으니, 다시 붙일 때 아웃박스 테이블을 처음부터 다시 읽게(스냅숏) 해야 한다. 미리 막으려면 PostgreSQL 13부터 있는 `max_slot_wal_keep_size`로 슬롯이 붙잡을 수 있는 WAL 상한을 걸어 둔다. 상한을 넘으면 슬롯이 무효가 되어 DB는 살고 CDC만 다시 맞춘다.
</Callout>

슬롯과 복제 지연을 보는 법은 [읽기 복제본과 샤딩](/posts/db-replication-sharding)에서도 다룬다. CDC를 쓰면 이 슬롯 감시가 아웃박스 운영의 대부분이다.

## 잠깐 어긋나는 데이터를 받아 내는 법

이벤트로 잇는 순간 데이터는 결과적으로 일관된다. 주문은 결제됨인데 포인트 서비스에는 아직 적립 전인 몇백 밀리초가 생긴다. 그 틈에서 생기는 문제는 대개 셋이다.

하나는 방금 쓴 걸 못 보는 문제다. 결제 직후 마이페이지에 포인트가 그대로면 사용자는 다시 결제를 누른다. 쓰기 응답에 바뀔 결과를 함께 돌려줘서 화면이 먼저 반영하거나, 처리 중 상태를 보여 주거나, 방금 쓴 사용자의 조회만 원본으로 보낸다.

둘은 순서다. 대부분의 브로커는 전체 순서를 보장하지 않는다. Kafka는 파티션 안에서만 순서를 지키니, 같은 주문의 이벤트는 같은 키로 보내 한 파티션에 모은다. 그래도 재시도, DLQ에서 되돌려 보내기, 여러 토픽을 합쳐 읽기에서 순서는 깨진다. 그래서 이벤트에 대상별 버전(`aggregateVersion`)을 넣고, 받는 쪽은 자기가 반영한 버전보다 작거나 같은 이벤트를 버린다. 앞의 CloudEvents 예시에서 `data`에 버전을 넣은 이유다.

셋은 중복이다. 아웃박스도, CDC도, 브로커도 "적어도 한 번" 보낸다. 같은 이벤트가 두 번 와도 결과가 같게 받는 쪽을 만든다. 처리한 이벤트 ID를 업무 데이터와 한 트랜잭션에 기록하는 인박스 테이블, 그리고 어디까지가 "정확히 한 번"인지는 [메시지 전달 보장](/posts/message-delivery-semantics)에서 따로 다룬다.

스키마 변경도 일관성 문제다. 구독자가 몇인지 모르는 상태에서 필드를 지우거나 이름을 바꾸면 어딘가가 조용히 깨진다. 필드는 추가만 하고, 지워야 하면 새 타입을 내고 옛 타입을 한동안 같이 낸 뒤 구독자가 다 옮겨 갔는지 확인하고 멈춘다. Kafka를 쓰면 스키마 레지스트리에 호환성 규칙(BACKWARD 등)을 걸어 깨는 변경을 등록 단계에서 막을 수 있다. 규칙을 고르는 법과 옛 이벤트를 다시 읽는 법은 [스키마 버전 관리 글](/posts/schema-versioning)에 있다.

## 이벤트가 어디서 사라졌는지 따라가기

이벤트 기반 시스템의 장애 문의는 대개 "주문했는데 포인트가 안 들어왔다"로 온다. 에러 로그는 어디에도 없다. 이벤트가 지나는 길을 앞에서부터 하나씩 확인한다.

먼저 이벤트가 생겼는지 본다. 주문 DB에 아웃박스 행이 있는지, 아직 안 나간 게 쌓였는지 확인한다.

```sql
-- 그 주문의 이벤트가 만들어졌나
SELECT id, event_type, created_at, published_at
FROM outbox WHERE aggregate_id = 1042 ORDER BY id;

-- 안 나간 이벤트가 몇 개이고, 가장 오래된 게 얼마나 됐나
SELECT count(*) AS pending, now() - min(created_at) AS oldest
FROM outbox WHERE published_at IS NULL;
```

`oldest`가 몇 초를 넘으면 릴레이가 멈췄거나 느린 것이다. CDC라면 앞의 `pg_replication_slots` 쿼리로 슬롯이 `active`인지, 붙잡은 WAL이 크는지 본다.

다음은 브로커다. 이벤트가 토픽에 있는지, 구독자가 얼마나 밀렸는지 본다. Kafka라면 `kafka-consumer-groups --describe`의 LAG 열이고, RabbitMQ라면 큐의 `messages_ready`와 `messages_unacknowledged`다. 명령과 출력은 [Kafka 기초](/posts/kafka-basics)와 [RabbitMQ 기초](/posts/rabbitmq-basics)에 있다. 랙은 0인데 포인트가 없다면 구독자가 받긴 했는데 처리에 실패하고 넘어갔거나 DLQ로 보낸 것이니 [데드 레터 큐](/posts/dead-letter-queue)를 본다.

이 추적을 빠르게 하려면 이벤트마다 꼬리표 둘을 단다. 상관 ID(correlation id)는 처음 요청에서 만들어 이후 모든 이벤트에 그대로 물려준다. 원인 ID(causation id)는 "이 이벤트를 만든 바로 앞 이벤트의 ID"다. 둘이 있으면 주문 요청 하나에서 갈라져 나간 이벤트 나무를 로그 검색 한 번으로 그릴 수 있다. 분산 추적을 쓴다면 메시지 헤더에 W3C `traceparent`를 실어 보내 비동기 구간도 한 트레이스로 잇는다([분산 추적](/posts/distributed-tracing)).

마지막으로 흐름 자체를 문서로 남긴다. 코레오그래피에서는 "누가 무엇을 내고 누가 듣는가"가 코드 여러 곳에 흩어지니, 토픽마다 발행자와 구독자, 스키마를 적은 목록(AsyncAPI 같은 형식)을 둔다. 이게 없으면 토픽 하나를 지울 때마다 누가 쓰는지 몰라서 못 지운다.

## 이벤트로 가지 않는 편이 나을 때

사용자가 결과를 바로 봐야 하고 실패를 바로 알려야 하는 일은 동기 호출이 맞다. 결제 승인, 재고 확인, 로그인은 이벤트로 돌리면 화면이 "처리 중"만 보여 준다.

팀 하나가 서비스 하나를 운영하고 구독자가 늘 일이 없다면, 브로커와 아웃박스와 멱등 소비자를 들이는 비용이 얻는 것보다 크다. 같은 프로세스 안에서 함수를 부르는 게 가장 빠르고 디버깅도 쉽다. 이벤트로 나눌 경계는 "다른 팀이 이 사실에 반응해야 한다"가 생길 때 긋는다.

강한 일관성이 꼭 필요한 불변식도 이벤트 사이에 두지 않는다. "잔액은 음수가 될 수 없다"는 한 트랜잭션 안에서 지킨다. 서비스 두 개에 걸친 불변식을 이벤트로 맞추면 반드시 어긋나는 순간이 생긴다.

## 처음의 주문 API로 돌아가면

알림 서버가 느려져도 주문이 느려지지 않게 하려면, 주문은 "결제됐다"는 사실을 자기 DB에 남기고 끝내면 된다. 그 사실을 빠짐없이 내보내는 건 아웃박스(또는 WAL을 읽는 CDC)가, 두 번 와도 괜찮게 받는 건 구독자가 맡는다. 사실에 무엇을 담을지, 흐름을 누가 쥘지는 구독자가 몇이고 순서가 얼마나 중요한지로 고른다. 그리고 어긋나는 몇백 밀리초를 화면과 버전 번호로 받아 낼 준비가 됐을 때 이벤트로 넘어간다.

## 면접에서 나올 만한 질문

### 이벤트와 명령은 무엇이 다른가?

명령은 정해진 받는 쪽에 "이걸 해 달라"고 부탁하는 것이고 거절될 수 있다. 이벤트는 이미 일어난 사실이라 거절할 수 없고, 보내는 쪽은 누가 듣는지 모른다. 그래서 명령은 보내는 쪽이 받는 쪽에 의존하고, 이벤트는 듣는 쪽이 보내는 쪽에 의존한다. 이름만 이벤트이고 실제로는 한 서비스만 듣고 그 서비스의 할 일을 지시하는 메시지는 명령으로 봐야 한다.

### 이벤트에 ID만 담는 방식과 상태를 담는 방식은 언제 고르나?

구독자가 적고 최신 상태를 다시 조회해도 되면 ID만 담는 알림 방식이 단순하다. 구독자가 많거나 원본 서비스가 죽어도 구독자가 계속 돌아야 하면 상태를 싣는 Event-Carried State Transfer가 낫다. 알림 방식은 조회 시점의 상태를 받아서 이벤트 시점과 어긋날 수 있고, 상태 방식은 담은 필드가 구독자와의 약속이 되어 스키마를 바꾸기 어려워진다. 어느 쪽이든 이벤트 ID, 타입과 버전, 발생 시각, 대상의 버전 번호는 넣는다.

### 이벤트 소싱은 무엇이고 언제 쓰나?

상태를 덮어쓰지 않고 상태를 바꾼 사건을 순서대로 쌓은 뒤, 사건을 다시 접어 현재 상태를 만드는 저장 방식이다. (stream_id, version)에 유일 제약을 걸어 같은 버전을 동시에 쓰는 걸 막는다. 이력이 업무 자체인 원장, 포인트, 재고 이동 같은 곳에 맞고, 대가로 스냅숏, 별도 조회 모델, 옛 스키마 사건을 읽는 업캐스팅, 개인정보 삭제 문제를 떠안는다. 이벤트 기반 아키텍처를 한다고 이벤트 소싱이 필수는 아니다.

### 코레오그래피와 오케스트레이션 중 무엇을 고르나?

서로 독립적인 반응은 코레오그래피로, 순서와 보상이 있는 흐름은 오케스트레이션으로 짠다. 코레오그래피는 중앙이 없어 결합이 적지만, 단계가 늘면 흐름이 구독 관계에 흩어져 "지금 어디까지 했나"를 물을 곳이 없어진다. 오케스트레이션은 흐름과 타임아웃이 한 곳에 보이지만 오케스트레이터가 참여자를 다 알고 규칙이 몰리기 쉽다. 실제 시스템은 둘을 섞어 쓴다.

### 아웃박스를 마지막으로 보낸 id보다 큰 것만 읽으면 무엇이 문제인가?

번호는 INSERT할 때 정해지고 다른 세션에 보이는 건 커밋할 때라서, 번호를 먼저 받고 늦게 커밋한 트랜잭션의 이벤트를 영영 건너뛴다. 직접 재현하면 1번이 열려 있는 동안 2번이 커밋되고, 릴레이가 2까지 읽은 뒤 1번이 커밋되자 1번은 다시 읽히지 않았다. 행마다 보냄 표시를 하거나, 트랜잭션 ID를 적고 `pg_snapshot_xmin`보다 앞선 것만 읽거나, WAL을 커밋 순서대로 읽는 CDC로 바꾼다. xmin 방식은 오래 열린 트랜잭션 하나가 릴레이 전체를 멈추니 그것도 같이 감시한다.

### CDC로 아웃박스를 읽을 때 운영에서 조심할 점은?

복제 슬롯은 읽는 쪽이 확인한 위치까지 WAL을 붙잡기 때문에, CDC가 멈추면 WAL이 쌓여 디스크를 채운다. `pg_replication_slots`에서 `active`와 붙잡은 WAL 양을 감시하고, PostgreSQL 13 이상이면 `max_slot_wal_keep_size`로 상한을 건다. CDC도 확인 전에 죽으면 다시 보내니 구독자는 여전히 멱등해야 한다. 대신 커밋된 것만 커밋 순서대로 나오니 폴링의 순서 문제는 사라진다.

### "주문했는데 포인트가 안 들어왔다"는 문의를 받으면 어디부터 보나?

이벤트가 지나는 길을 앞에서부터 확인한다. 아웃박스에 그 주문의 이벤트가 있는지와 안 나간 이벤트 중 가장 오래된 것의 나이를 보고, 브로커에서 그 구독자의 랙을 보고, 랙이 0이면 구독자 로그와 DLQ를 본다. 이 추적을 빨리 하려면 이벤트에 상관 ID와 원인 ID를 달고 메시지 헤더로 트레이스 컨텍스트를 넘겨 둔다.
