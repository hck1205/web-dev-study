로그를 시각순으로 쌓아 둔 배열이 있다. 화면에서 "이 시각까지의 로그"를 보여 주려면, 주어진 시각 이하인 마지막 로그의 위치를 찾아야 한다. 배열이 정렬돼 있으니 이분 탐색으로 짰다. 시각은 자정부터 센 분이다.

```js
const times = [540, 545, 545, 552, 600, 601, 615]; // 09:00 ~ 10:15

function lastAtOrBefore(arr, x) {
  let lo = 0, hi = arr.length - 1;
  while (lo < hi) {
    const mid = Math.floor((lo + hi) / 2);
    if (arr[mid] <= x) lo = mid; // mid도 답일 수 있으니 남긴다
    else hi = mid - 1;
  }
  return lo;
}
```

09:12(552)와 10:00(600)을 넣으면 3과 4가 나온다. 맞다. 그런데 "지금까지 전부"를 보려고 현재 시각 11:40(700)을 넣으면 함수가 돌아오지 않는다. 반복 횟수에 상한을 걸고 다시 돌려 봤다.

```text
3
4
stuck lo=5 hi=6
```

`lo`가 5, `hi`가 6에서 멈춰 있다. `mid`는 (5 + 6) / 2를 내린 5이고, `arr[5]`는 601이라 700 이하이니 `lo = mid`, 즉 다시 5다. 범위가 한 칸도 줄지 않는다. 가장 자주 쓰일 질문("지금까지")에서만 걸리는 버그라 테스트 데이터 몇 개로는 안 보인다.

이분 탐색은 원리가 단순한데 코드가 자주 틀린다. 이 글은 그 이유를 "구간을 어떻게 정의하느냐"에서 찾는다. 이분 탐색이 사실 정렬된 배열이 아니라 참거짓이 한 번만 바뀌는 조건의 경계를 찾는 방법이라는 것, 같은 값이 여러 개일 때의 lower bound와 upper bound, 실수 범위와 "답을 놓고 찾는" 탐색, 회전된 배열 같은 변형까지 따라간다. 이분 탐색이 왜 O(log n)인지는 [Big O 글](/posts/big-o-notation)에서, 정렬된 배열을 얻는 방법은 [정렬 알고리즘 글](/posts/sorting-algorithms)에서 다뤘다. 실행 결과는 모두 Node.js 22에서 돌린 값이다.

## 참이 한 번만 바뀌는 곳을 찾는다

정렬된 배열에서 x를 찾는다는 말을 바꿔 보자. 각 칸에 "이 값이 x 이상인가?"를 물으면 답이 이렇게 늘어선다.

```text
times      540  545  545  552  600  601  615
>= 552 ?     F    F    F    T    T    T    T
```

앞쪽은 전부 F, 어느 지점부터 전부 T다. 한 번 T가 되면 다시 F로 돌아가지 않는다. 이분 탐색이 찾는 건 이 경계, 즉 처음 T가 되는 자리다. 가운데 하나를 물어서 F면 그 왼쪽은 다 F라 버리고, T면 그 오른쪽은 다 T라 버린다. 매번 절반이 사라진다.

이렇게 보면 정렬된 배열은 조건을 만드는 한 가지 방법일 뿐이다. "용량이 c면 5일 안에 배송이 끝나나", "이 커밋에서 테스트가 깨지나", "동시 접속 n명에서 p99가 200ms를 넘나"처럼 F에서 T로 한 번만 바뀌는 질문이면 무엇이든 이분 탐색을 쓸 수 있다. 배열이 없어도 된다. 뒤에서 이 형태를 다시 쓴다.

거꾸로, 조건이 단조롭지 않으면 이분 탐색은 아무 답이나 낸다. 정렬 안 된 배열에 이분 탐색을 돌리면 에러 없이 틀린 위치를 돌려준다. 이분 탐색 함수 앞에 "정렬돼 있다"는 전제가 정말 지켜지는지가 첫 번째 확인 사항이다.

## 구간의 정의가 코드를 정한다

이분 탐색 코드가 틀리는 지점은 거의 다 세 군데다. 반복 조건(`lo < hi`인가 `lo <= hi`인가), 줄이는 방법(`hi = mid`인가 `hi = mid - 1`인가), `mid`를 내림하느냐 올림하느냐. 이 셋을 따로따로 외우면 섞여서 처음 장면 같은 버그가 난다. 대신 "답이 있을 수 있는 구간"을 하나로 정하고 거기서 나머지를 끌어낸다.

가장 덜 헷갈리는 정의는 반열린 구간 `[lo, hi)`다. `lo`는 후보에 들어가고 `hi`는 안 들어간다. 처음엔 `lo = 0`, `hi = arr.length`라서 "끝까지 가도 없으면 length를 돌려준다"가 자연스럽게 된다.

## 같은 값이 여러 개면 경계도 두 개다

같은 값이 여러 번 나오면 "x를 찾았다"만으로는 부족하다. 545가 1번 칸에도 2번 칸에도 있는데, 가운데에서 우연히 걸린 쪽을 돌려주면 "첫 545부터 보여 주기"가 틀린다. 그래서 경계를 두 개로 나눠 찾는다.

- lower bound: x 이상이 처음 나오는 자리. 조건은 `a[mid] < x`면 F.
- upper bound: x 초과가 처음 나오는 자리. 조건은 `a[mid] <= x`면 F.

```js
function lowerBound(arr, x) { // x 이상이 처음 나오는 자리
  let lo = 0, hi = arr.length;
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;
    if (arr[mid] < x) lo = mid + 1; else hi = mid;
  }
  return lo;
}

function upperBound(arr, x) { // x 초과가 처음 나오는 자리
  let lo = 0, hi = arr.length;
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;
    if (arr[mid] <= x) lo = mid + 1; else hi = mid; // 부등호 하나만 다르다
  }
  return lo;
}
```

두 함수는 부등호 하나만 다르다. 545를 lower bound로 찾는 과정을 따라가 보자.

두 경계를 알면 여러 질문이 뺄셈 한 번으로 풀린다.

```js
for (const x of [500, 545, 550, 615, 700]) {
  const lb = lowerBound(times, x), ub = upperBound(times, x);
  console.log(`x=${x}  lower=${lb}  upper=${ub}  count=${ub - lb}  lastAtOrBefore=${ub - 1}`);
}
```

```text
x=500  lower=0  upper=0  count=0  lastAtOrBefore=-1
x=545  lower=1  upper=3  count=2  lastAtOrBefore=2
x=550  lower=3  upper=3  count=0  lastAtOrBefore=2
x=615  lower=6  upper=7  count=1  lastAtOrBefore=6
x=700  lower=7  upper=7  count=0  lastAtOrBefore=6
```

`count` 열은 x가 몇 개 있는지다. lower와 upper가 같으면 하나도 없다는 뜻이다(550). `lastAtOrBefore` 열이 처음 장면에서 원하던 답이다. 700에서도 6이 나왔고, 맨 앞보다 이른 500에서는 -1, 즉 "없다"가 나왔다. lower bound는 "x를 넣어도 정렬이 유지되는 가장 앞자리"이기도 해서, 정렬된 배열에 값을 끼워 넣을 위치를 찾을 때도 그대로 쓴다. 범위 질문도 된다. `[a, b]` 사이의 값은 `lowerBound(a)`부터 `upperBound(b)` 앞까지다.

자바스크립트에는 내장 이분 탐색이 없다. `indexOf`, `includes`, `findIndex`, `findLastIndex`는 전부 앞이나 뒤에서부터 훑는 O(n)이다. 정렬된 배열이어도 알아서 반으로 자르지 않는다. 직접 짜거나 lodash의 `sortedIndex`(lower bound), `sortedLastIndex`(upper bound) 같은 검증된 함수를 쓴다.

## 정렬해 두고 여러 번 찾을 때의 계산

100만 개 정렬된 배열에서 값을 찾는 방법 세 가지를 재 봤다. `includes`는 너무 느려서 질문 1,000개만, 나머지는 10만 개다.

```text
includes   x1,000   986.9ms hits=334
binary     x100,000 30.0ms hits=33334
Set.has    x100,000 21.4ms hits=33334 (build 104.6ms)
range [300000, 300030]: 300000,300003,300006,300009,300012,300015,300018,300021,300024,300027,300030
```

`includes`는 질문 1,000개에 1초다. 10만 개였다면 100초쯤 걸렸을 것이다. 이분 탐색은 10만 개에 30ms, `Set`은 21ms로 조금 더 빠르지만 만드는 데 105ms가 들고 원소마다 메모리를 더 쓴다. 그리고 마지막 줄 같은 범위 질문은 `Set`으로는 할 수 없다. "있나 없나"만 물을 거라면 해시, 범위·최근접·순위가 필요하면 정렬과 이분 탐색이다. 해시 쪽 이야기는 [해시맵 글](/posts/ds-hash-map)에 있다.

정렬된 상태를 유지하면서 자주 넣고 빼야 한다면 배열은 맞지 않는다. 이분 탐색으로 자리는 log n에 찾아도 `splice`로 끼우는 데 O(n)이 든다. 이럴 때는 균형 이진 탐색 트리나 B-트리처럼 넣고 빼기도 log n인 구조를 쓴다. [이진 탐색 트리 글](/posts/ds-binary-tree-bst)과 [DB 인덱스 글](/posts/db-index)이 그 이야기다. DB 인덱스로 `WHERE created_at >= ...`를 찾는 것도 결국 B-트리 위에서 lower bound를 찾는 일이다.

## 가운데를 구하다 넘치는 경우

`mid`를 구할 때 `(lo + hi) / 2`가 넘친다는 이야기는 32비트 정수를 쓰는 자바나 C에서 나온 것이다. 자바스크립트 숫자는 2⁵³까지 정수를 정확히 담으니 `Math.floor((lo + hi) / 2)` 자체는 안전하다. 문제는 거기서 빨라 보이려고 비트 연산을 쓸 때 생긴다. 비트 연산은 피연산자를 32비트 정수로 바꾼다.

```js
const f = (lo, hi) => [(lo + hi) >> 1, (lo + hi) >>> 1, Math.floor((lo + hi) / 2), lo + ((hi - lo) >> 1)];
console.log("lo=2**30, hi=2**31  ", f(2 ** 30, 2 ** 31));
console.log("lo=2**31, hi=2**32-1", f(2 ** 31, 2 ** 32 - 1));
console.log("lo=2**32, hi=2**33  ", f(2 ** 32, 2 ** 33));
```

```text
lo=2**30, hi=2**31   [ -536870912, 1610612736, 1610612736, 1610612736 ]
lo=2**31, hi=2**32-1 [ 1073741823, 1073741823, 3221225471, 3221225471 ]
lo=2**32, hi=2**33   [ 0, 0, 6442450944, 4294967296 ]
```

`>> 1`은 합이 2³¹을 넘자마자 음수가 됐다. `>>> 1`은 합이 2³²를 넘는 둘째 줄부터 틀렸다. 자바식 해법인 `lo + ((hi - lo) >> 1)`도 차이가 2³¹을 넘으면 틀린다. 마지막 줄은 차이가 2³²라 0이 더해져 4294967296이 나왔다. 실제 배열은 메모리 한계 때문에 이 크기에 닿지 않으니 인덱스에는 `>>> 1`로 충분하다. 하지만 뒤에서 볼 "답을 놓고 찾는" 탐색은 범위가 금액이나 타임스탬프처럼 클 수 있으니 `Math.floor((lo + hi) / 2)`를 쓴다. 실제로 짐 무게가 5억씩인 아래 연습 문제를 `>> 1`로 풀면 `mid`가 음수로 튀어 끝나지 않는다.

## 실수 범위에서 찾을 때는 횟수로 끊는다

값이 정수가 아니어도 된다. 제곱근을 이분 탐색으로 구해 보자. 흔히 "구간이 충분히 좁아질 때까지" 돈다.

```js
function sqrtEps(x, eps = 1e-9) {
  let lo = 0, hi = Math.max(1, x);
  while (hi - lo > eps) {
    const mid = (lo + hi) / 2;
    if (mid * mid < x) lo = mid; else hi = mid;
  }
  return lo;
}
```

```text
eps   2       1.4142135614529252 (31 iterations)
eps   1e20    stuck after 2000 iterations, lo=9999999999.999998, hi=10000000000, gap=0.0000019073486328125
fixed 2       1.414213562373095
fixed 1e20    9999999999.999998
Math.sqrt     1.4142135623730951 10000000000
```

2에서는 31번에 끝났다. 1e20에서는 끝나지 않았다. 답이 100억 근처인데, 그 크기의 부동소수점 수는 이웃한 값끼리 0.0000019쯤 떨어져 있다. 그보다 가까운 두 수는 표현할 수 없으니 `hi - lo`가 1e-9보다 작아질 수가 없다. `mid`가 `lo`나 `hi`와 같아지면서 구간이 더 줄지 않는다.

그래서 실수 이분 탐색은 횟수로 끊는다. 100번이면 처음 구간을 2¹⁰⁰분의 1로 줄이니 double이 담을 수 있는 정밀도를 넘는다. 위의 `fixed` 줄이 100번 고정 반복의 결과다. 허용 오차가 꼭 필요하면 절대 오차 대신 답의 크기에 비례한 상대 오차를 쓴다.

## 답을 놓고 거꾸로 찾는다

이제 배열 없이 조건만으로 이분 탐색을 써 보자. 짐 무게가 순서대로 `[1, 2, …, 10]`이고 순서를 바꾸지 않고 하루에 한 트럭씩 싣는다. 5일 안에 다 보내려면 트럭 용량이 최소 얼마여야 할까.

```js
function shipWithinDays(weights, days) {
  const fits = (cap) => { // 용량 cap이면 days일 안에 되나
    let need = 1, load = 0;
    for (const w of weights) {
      if (load + w > cap) { need++; load = 0; }
      load += w;
    }
    return need <= days;
  };
  let lo = Math.max(...weights);
  let hi = weights.reduce((a, b) => a + b, 0);
  while (lo < hi) {
    const mid = Math.floor((lo + hi) / 2);
    if (fits(mid)) hi = mid; else lo = mid + 1;
  }
  return lo;
}
```

이 방식을 매개 변수 탐색(parametric search)이라고 부른다. 최적화 문제("최소 용량은?")를 판정 문제("용량 c면 되나?")로 바꾸고, 판정의 경계를 이분 탐색으로 찾는다. 판정이 O(n)이고 답의 범위가 R이면 전체는 O(n log R)이다. 효과를 재 봤다. 짐 10만 개, 무게 1~500, 50일이다.

```text
binary: cap=496496 checks=25 11.7ms
linear: cap=496496 checks=495997 99380.5ms
```

가장 무거운 짐부터 1씩 올려 가며 판정하면 49만 번 판정에 99초가 걸렸다. 이분 탐색은 25번, 12ms다. 면접에서 "최솟값의 최댓값", "최댓값의 최솟값", "~하려면 최소 얼마"가 나오면 이 형태를 먼저 의심한다. 바나나를 시간 안에 먹는 최소 속도, 공유기 사이 거리의 최댓값, 나무를 잘라 필요한 만큼 얻는 높이가 다 같은 문제다. 판정 함수가 단조로운지만 확인하면 된다.

현장에서도 같은 사고방식을 쓴다. 배치 크기를 키우다 어느 지점부터 메모리가 터지는지, 동시 사용자 수를 얼마까지 올리면 p99 지연이 기준을 넘는지 찾을 때 1씩 올리지 않고 반씩 좁힌다. 버그가 들어온 커밋을 찾는 `git bisect`가 가장 유명한 예이고, 실제 사용법과 `git bisect run` 출력은 [Git 고급 기능 글](/posts/git-tips-advanced)에 있다. 조건은 같다. 한 번 깨지면 계속 깨져 있어야(단조로워야) 한다. 부하 테스트 결과가 흔들려서 같은 값에서 됐다 안 됐다 하면 이분 탐색도 엉뚱한 경계를 낸다. 그럴 때는 지점마다 여러 번 재서 판정을 안정시킨다.

## 정렬이 반쯤 깨진 배열에서

이분 탐색의 변형 문제는 "전체가 정렬돼 있지 않아도 절반을 버릴 근거가 있는가"를 묻는다.

회전된 정렬 배열이 대표적이다. `[3, 6, 9, 12, 15, 18, 22]`를 돌려서 `[15, 18, 22, 3, 6, 9, 12]`가 된 배열에서 값을 찾는다. 전체는 정렬이 아니지만, 가운데로 자르면 두 절반 중 적어도 하나는 정렬돼 있다. 정렬된 쪽의 양 끝을 보면 x가 그 안에 있는지 바로 알 수 있으니, 있으면 그쪽, 없으면 반대쪽으로 간다.

```js
function searchRotated(a, x) {
  let lo = 0, hi = a.length - 1; // 여기서는 닫힌 구간 [lo, hi]
  while (lo <= hi) {
    const mid = (lo + hi) >>> 1;
    if (a[mid] === x) return mid;
    if (a[lo] <= a[mid]) { // 왼쪽 절반이 정렬돼 있다
      if (a[lo] <= x && x < a[mid]) hi = mid - 1; else lo = mid + 1;
    } else {               // 오른쪽 절반이 정렬돼 있다
      if (a[mid] < x && x <= a[hi]) lo = mid + 1; else hi = mid - 1;
    }
  }
  return -1;
}
```

```text
22->2  3->3  12->6  15->0  7->-1
```

이 코드는 값 하나를 찾자마자 돌아오는 문제라 닫힌 구간 `[lo, hi]`로 썼다. 닫힌 구간에서는 `lo <= hi`, `hi = mid - 1`이 짝이다. 구간 정의를 바꾸면 세 군데를 함께 바꾼다는 원칙은 같다. 같은 값이 섞인 회전 배열(`[2, 2, 2, 0, 2]`)은 `a[lo] === a[mid]`일 때 어느 쪽이 정렬됐는지 알 수 없어서 `lo`를 한 칸씩 올려야 하고, 최악은 O(n)이 된다. 면접의 꼬리 질문으로 자주 나온다.

봉우리 찾기도 같은 생각이다. 시간대별 부하가 올라갔다 내려오는 배열 `[12, 30, 55, 71, 64, 40, 22]`에서 가장 높은 지점을 찾는다. `a[mid] < a[mid + 1]`이면 오르막 위에 있으니 봉우리는 오른쪽에 있다. 아니면 mid를 포함한 왼쪽에 있다. 정렬은 아니지만 "오르막인가"라는 조건이 F, T로 한 번만 바뀌니 lower bound와 똑같은 코드가 된다.

```js
function findPeak(a) {
  let lo = 0, hi = a.length - 1;
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;
    if (a[mid] < a[mid + 1]) lo = mid + 1; else hi = mid;
  }
  return lo;
}
```


## 연습: 처음과 끝 찾기

## 범위를 반으로 줄이는 근거

이분 탐색은 정렬된 배열의 기술이 아니라 참거짓이 한 번만 바뀌는 경계를 찾는 기술이다. 코드는 구간 정의 하나에서 나온다. 반열린 `[lo, hi)`라면 `lo < hi`, `lo = mid + 1`, `hi = mid`가 짝이고, 같은 값이 여러 개면 lower bound와 upper bound로 양쪽 경계를 따로 찾는다. 실수는 횟수로 끊고, 큰 범위에서는 비트 연산을 피한다. 판정 함수만 단조롭다면 배열이 없어도, 답 자체를 놓고도 찾을 수 있다. 다음은 한 갈래씩 끝까지 들어갔다 되돌아오는 [재귀와 백트래킹](/posts/recursion-backtracking)이다.

## 면접에서 나올 만한 질문

### 이분 탐색의 시간 복잡도와 쓸 수 있는 조건은 무엇인가요?

O(log n)이다. 비교 한 번마다 후보의 절반을 버리니 100만 개도 20번이면 끝난다. 조건은 정렬 그 자체가 아니라, 묻는 조건이 앞쪽은 전부 거짓, 어느 지점부터 전부 참처럼 한 번만 바뀌는 단조성이다. 정렬된 배열은 그 조건을 만드는 대표적인 방법이고, 단조롭지 않으면 에러 없이 틀린 답을 낸다.

### lower bound와 upper bound의 차이는 무엇이고 어디에 쓰나요?

lower bound는 x 이상이 처음 나오는 자리, upper bound는 x 초과가 처음 나오는 자리다. 코드는 부등호 하나(`<`와 `<=`)만 다르다. 둘의 차이가 x의 개수이고, upper bound − 1이 x 이하인 마지막 자리, lower bound가 정렬을 유지하며 x를 끼울 자리다. 범위 `[a, b]` 질문도 두 경계로 푼다.

### 이분 탐색이 무한 루프에 빠지는 이유는 무엇인가요?

구간이 한 칸도 줄지 않는 갈래가 있기 때문이다. 대표적으로 `lo = mid`인데 mid를 내림하면, 두 칸 남았을 때 mid가 lo와 같아져 그대로 머문다. 구간을 반열린 `[lo, hi)`로 정하고 `lo = mid + 1`, `hi = mid`, 내림한 mid를 짝으로 쓰면 어느 갈래로 가도 구간이 준다. mid를 남기는 쪽이 lo라면 mid를 올림해야 한다.

### 자바스크립트에서 mid를 (lo + hi) >> 1로 구하면 안 되나요?

배열 인덱스 정도면 괜찮지만 범위가 커지면 틀린다. 비트 연산은 32비트 정수로 바꾸기 때문에 `>> 1`은 합이 2³¹을 넘으면 음수가 되고, `>>> 1`도 2³²를 넘으면 틀린다. 자바스크립트 숫자는 2⁵³까지 정확하니 금액이나 타임스탬프처럼 큰 범위에서는 `Math.floor((lo + hi) / 2)`가 안전하다. 자바나 C에서의 오버플로 이야기와 원인이 다르다.

### 실수 범위에서 이분 탐색을 할 때 주의할 점은 무엇인가요?

`hi - lo > eps` 같은 종료 조건은 답이 크면 끝나지 않을 수 있다. 100억 근처의 double은 이웃 간격이 약 0.0000019라서 1e-9 오차까지 줄어들 수 없다. 그래서 100번처럼 고정 횟수로 반복하거나, 답의 크기에 비례한 상대 오차를 쓴다.

### "최소 용량은 얼마인가" 같은 문제에 이분 탐색을 어떻게 쓰나요?

답을 직접 구하지 않고 "용량 c면 조건을 만족하나"라는 판정 함수를 만든 뒤, 판정이 처음 참이 되는 c를 이분 탐색으로 찾는다. 매개 변수 탐색이라고 부르고, 판정이 O(n)이면 전체는 O(n log R)이다. 짐 10만 개 측정에서 1씩 올리면 99초, 이분 탐색은 12ms였다. 판정 함수가 단조로운지 먼저 확인해야 한다.

### 회전된 정렬 배열에서 값을 O(log n)에 찾을 수 있나요?

가운데로 자르면 적어도 한쪽 절반은 정렬돼 있어서 가능하다. `a[lo] <= a[mid]`면 왼쪽이 정렬된 쪽이고, x가 그 범위 안이면 왼쪽, 아니면 오른쪽으로 간다. 다만 중복 값이 있으면 `a[lo] === a[mid]`일 때 어느 쪽이 정렬됐는지 알 수 없어 한 칸씩 줄여야 하고, 최악은 O(n)이 된다.

### 정렬된 배열의 이분 탐색과 Set 중 무엇을 고르나요?

있나 없나만 묻는다면 평균 O(1)인 `Set`이 조금 더 빠르다. 100만 개에서 질문 10만 개에 `Set`은 21ms, 이분 탐색은 30ms였다. 대신 `Set`은 만드는 비용과 원소마다 추가 메모리가 들고, 범위·최근접·순위 질문은 못 한다. 그런 질문이 필요하거나 메모리가 빠듯하면 정렬과 이분 탐색이다.
