상품 상세 화면에 "설명", "리뷰", "Q&A" 세 탭이 있다. 리뷰 탭은 리뷰 수백 개를 한꺼번에 그려서 느리다. 리뷰 탭을 누르면 화면이 0.4초쯤 굳는데, 문제는 그다음이다. 잘못 눌렀다 싶어 바로 "Q&A"를 눌러도 반응이 없다. 리뷰 탭이 다 그려진 다음에야 Q&A로 넘어간다. 사용자 입장에서는 두 번 기다린다.

```tsx
function ProductTabs() {
  const [tab, setTab] = useState("desc");
  return (
    <>
      <TabButtons current={tab} onSelect={setTab} />
      {tab === "desc" && <Description />}
      {tab === "reviews" && <Reviews />}   {/* 렌더링에 400ms */}
      {tab === "qna" && <QnA />}
    </>
  );
}
```

`onSelect={(t) => startTransition(() => setTab(t))}`로 한 줄을 바꾸면 리뷰 탭을 그리는 도중에도 Q&A 클릭이 바로 먹는다. 이 글은 그 한 줄 뒤에서 일어나는 일을 따라간다. 업데이트에 붙는 우선순위(lane), transition이 표시되는 방식, 하던 렌더를 버리는 조건, 외부 저장소와 tearing, React 19의 async transition이다. `useDeferredValue`로 검색 목록을 미루는 기본 예제와 디바운스와의 큰 차이는 [React는 언제 다시 그리나](/posts/react-rerender)에서 다뤘고, 렌더 작업이 Fiber 단위로 쪼개지는 구조는 [Fiber와 렌더·커밋 단계](/posts/react-fiber-render-commit)에 있다. 실험은 React 19.3.1을 Node 22와 jsdom 위에서 돌렸다.

## 긴 렌더는 다음 입력을 줄 세운다

장면을 숫자로 재 보자. 한 번 렌더링에 0.3ms를 쓰는 `Item` 300개를 두고, 목록 값을 바꾸는 업데이트를 일으킨 뒤 20ms 뒤에 버튼 클릭을 예약했다. 먼저 transition 없이 했다.

```text
 152ms setQ('b') (no transition)
 253ms commit q=b count=0 isPending=false
 254ms click (count+1)
 258ms commit q=b count=1 isPending=false
```

20ms 뒤에 와야 할 클릭이 102ms 뒤에 처리됐다. 목록 렌더링이 약 100ms 동안 메인 스레드를 쥐고 있어서, 클릭 이벤트를 실어 나를 태스크가 끼어들 틈이 없었다. 렌더링이 끝나고 커밋까지 해야 클릭이 처리된다. 브라우저에서 이 시간은 그대로 INP(입력부터 다음 화면까지의 시간)에 들어간다.

같은 실험을 `startTransition`으로 감싸서 했다.

```text
 151ms startTransition(setQ('b'))
 153ms commit q=a count=0 isPending=true
 179ms click (count+1)
 183ms commit q=a count=1 isPending=true
 292ms commit q=b count=1 isPending=false
Item renders: {"b":358}
```

클릭이 거의 제시간(28ms 뒤)에 처리되고 4ms 만에 커밋됐다. 그 커밋에서 목록은 아직 이전 값 `a`다. 목록은 그 뒤에 따로 끝났다. 그리고 마지막 줄을 보면 `Item`이 300번이 아니라 358번 렌더링됐다. 58번은 클릭 때문에 버려진 렌더링이다. 이 세 가지, 우선순위가 다른 업데이트, 쪼개진 렌더링, 버려지는 렌더링이 동시성 렌더링의 전부다.

## 업데이트마다 차선이 있다

React는 업데이트를 만들 때마다 우선순위를 하나 붙인다. 이 우선순위를 lane(차선)이라고 부르고, 31비트 정수의 비트 하나로 나타낸다. 여러 업데이트가 쌓여 있으면 비트를 OR로 합쳐 하나의 정수(`lanes`)로 들고 있고, 그중 가장 급한 것을 고를 때는 `lanes & -lanes`로 가장 낮은 비트를 뽑는다. 숫자가 작을수록 급하다. 집합 연산이 비트 연산 한 번이라 Fiber 수천 개를 걸으며 확인해도 싸다.

주요 lane을 개념 수준으로 보면 이렇다. 이름은 `ReactFiberLane.js`에 있는 그대로다.

- `SyncLane`: 클릭, 키 입력, 포커스처럼 하나하나 끊어지는(discrete) 입력에서 생긴 업데이트. `flushSync` 안의 업데이트도 여기다.
- `InputContinuousLane`: 마우스 이동, 드래그, 스크롤, 포인터 이동처럼 연속으로 쏟아지는 입력.
- `DefaultLane`: `setTimeout`, 네트워크 응답, 렌더링 밖의 일반 코드처럼 이벤트와 상관없는 곳의 업데이트.
- `TransitionLanes`: `startTransition`으로 감싼 업데이트. 여러 개의 비트가 있어서 서로 다른 transition을 구분할 수 있다.
- `RetryLanes`: Suspense가 프로미스를 기다렸다가 다시 렌더링해 볼 때.
- `IdleLane`, `OffscreenLane`: 가장 뒤. 화면에 보이지 않는 트리를 미리 렌더링하는 일 같은 것들이다.

React 19.3.1 빌드에서는 `SyncLane`이 2, `InputContinuousLane`이 8, `DefaultLane`이 32이고, transition은 256부터 시작하는 비트들이다. 값은 버전마다 바뀌어 왔으니 외울 필요는 없고, "작은 비트가 급하다"만 기억하면 된다.

어떤 이벤트가 어느 lane이 되는지는 React DOM의 `getEventPriority`가 이벤트 이름으로 정한다. `click`, `keydown`, `input`은 discrete, `mousemove`, `scroll`, `pointermove`는 continuous다. 업데이트를 만드는 `requestUpdateLane`은 먼저 지금 transition 안인지 보고, 아니면 지금 처리 중인 이벤트의 우선순위를 쓴다. 이벤트 밖이면 DefaultLane이다.

lane이 정해지면 렌더링 방식도 정해진다. 앞의 세 가지(Sync, InputContinuous, Default)는 막는(blocking) 업데이트라서 `renderRootSync`로 끝까지 한 번에 렌더링한다. transition, retry, idle만 `renderRootConcurrent`로 5ms씩 쪼개며 렌더링한다. 첫 실험에서 transition 없는 업데이트가 100ms를 한 덩어리로 쓴 건 `setTimeout` 안에서 생긴 DefaultLane이었기 때문이다.

transition이 무한정 밀리지는 않는다. lane마다 만료 시간이 있어서, 급한 업데이트가 계속 들어와 transition이 오래 굶으면 React가 그 lane을 만료된 것으로 보고 더는 쪼개지 않고 한 번에 끝낸다. React 19.3.1 소스의 `computeExpirationTime`에서는 막는 입력 lane이 250ms, DefaultLane과 transition lane이 5초다. 계속 밀려서 화면이 영영 안 바뀌는 일은 없다는 정도로 알아 두면 된다.

## startTransition은 업데이트에 표시만 붙인다

`startTransition`이 하는 일은 생각보다 단순하다. 콜백을 실행하는 동안 React 내부의 "지금 transition 중" 표시(`ReactSharedInternals.T`)를 켜 두고, 콜백이 끝나면 끈다. 그 사이에 불린 `setState`는 `requestUpdateLane`에서 이 표시를 보고 transition lane을 받는다. 콜백 자체는 바로 동기로 실행된다. 미뤄지는 건 그 안에서 예약된 렌더링이다.

그래서 표시가 켜져 있는 동안 동기로 불린 `setState`만 transition이 된다. 실제로 네 가지 모양으로 돌려서, 렌더링이 몇 조각으로 나뉘었는지(쪼개졌다면 transition)를 셌다.

```tsx
startTransition(() => setQ("b"));                                   // inside
startTransition(() => { setTimeout(() => setQ("b"), 0); });         // setTimeoutInside
startTransition(async () => { await sleep(1); setQ("b"); });        // afterAwait
startTransition(async () => {
  await sleep(1);
  startTransition(() => setQ("b"));                                 // afterAwaitRewrapped
});
```

```text
inside               slices=19 first=11,17,17
setTimeoutInside     slices=1 first=300
afterAwait           slices=1 first=300
afterAwaitRewrapped  slices=19 first=12,17,17
```

`setTimeout` 안의 업데이트는 콜백이 끝난 뒤에 실행되니 표시가 이미 꺼져 있다. 일반 업데이트로 한 번에 렌더링됐다. `await` 뒤도 마찬가지다. `await` 뒤의 코드는 마이크로태스크로 나중에 이어지는데, 그때는 표시가 없다. React 19 문서도 이걸 알려진 한계로 적어 두고 `await` 뒤의 `setState`는 `startTransition`으로 한 번 더 감싸라고 안내한다. 언젠가 JavaScript에 비동기 문맥을 이어 주는 기능이 들어오면 필요 없어질 수 있다고 한다.

`useTransition`이 주는 `isPending`은 별도의 급한 업데이트로 만들어진다. `startTransition`을 부르면 React는 먼저 높은 우선순위로 `isPending = true`를 렌더링하고, transition 업데이트를 따로 렌더링한다. 위 로그에서 transition을 시작하자마자 `commit q=a isPending=true`가 찍힌 게 그것이다. transition이 커밋될 때 `isPending`이 함께 `false`가 된다. 그러니 `isPending`으로 탭 버튼을 흐리게 하거나 작은 스피너를 띄우는 건 바로 보인다.

`useTransition`의 `startTransition`과 `react`에서 바로 import하는 `startTransition`은 같은 표시를 붙인다. 차이는 `isPending`이 있느냐뿐이다. 컴포넌트 밖, 예를 들어 라우터나 상태 라이브러리 코드에서는 훅을 쓸 수 없으니 import한 쪽을 쓴다.

버린다는 게 낭비처럼 보이지만 이유가 있다. 클릭으로 바뀐 상태는 transition이 렌더링하던 트리의 어디에든 영향을 줄 수 있다. 예전 상태 위에서 그리던 초안을 이어 쓰면 서로 다른 시점의 상태가 섞인다. 그래서 React는 상태를 바꾼 급한 업데이트가 끼어들면 초안을 버리고, 급한 업데이트가 반영된 `current` 위에서 transition을 다시 시작한다. 초안은 화면에 연결되지 않은 `workInProgress` 트리라서 버려도 흔적이 없다.

처음 탭 화면도 그대로 재현했다. 탭 버튼의 `onClick`에서 `useTransition`의 `startTransition(() => setTab(t))`를 부르고, 리뷰 탭을 누른 뒤 30ms 만에 Q&A 탭을 눌렀다.

```text
 148ms click reviews
 156ms commit tab=desc isPending=true
 184ms click qna
 291ms commit tab=qna isPending=false
Item renders: {"reviews":79,"qna":300}
```

리뷰 탭은 한 번도 커밋되지 않았다. 79개까지 그리던 리뷰 렌더링은 Q&A 클릭에 밀려 버려졌고, 같은 state(`tab`)에 쌓인 두 transition은 서로 묶여(소스에서는 `entangleTransitions`) 최신 값 `qna`로 한 번에 렌더링됐다. 처음 장면에서 두 번 기다리던 문제가 여기서 풀린다.

다만 이건 두 번째 클릭이 급한 업데이트(`isPending` 갱신)를 함께 만들어서 진행 중인 렌더링을 끊었기 때문이다. 클릭 없이 타이머에서 transition 두 개를 30ms 차이로 예약하면 결과가 다르다.

```text
 160ms transition tab=reviews
 194ms transition tab=qna
 272ms commit tab=reviews other=0
 375ms commit tab=qna other=0
```

나중 transition은 앞의 transition보다 우선순위가 높지 않으니 진행 중인 렌더링을 끊지 못한다. 리뷰가 끝까지 그려져 한 번 커밋되고, 그다음에 Q&A가 따로 렌더링됐다. "새 transition이 오면 이전 transition은 항상 버려진다"고 외우면 틀린다. 버려지는 건 더 급한 업데이트가 끼어들었을 때다.

한 이벤트 안에서 `startTransition`을 여러 번 부르는 건 걱정하지 않아도 된다. React는 같은 이벤트 안의 transition에 같은 lane을 준다(`requestTransitionLane`이 이벤트마다 lane 하나를 기억한다). 두 state를 각각 다른 `startTransition`으로 바꿨더니 커밋은 한 번이었다.

```text
 142ms two transitions in one event
 245ms commit tab=reviews other=1
```

버려지는 렌더링이 있다는 사실이 렌더 중 부작용을 금지하는 가장 직접적인 이유다. 위 실험에서 `Item` 렌더 함수가 조회수를 서버로 보냈다면 58번은 화면에 나타나지도 않은 항목의 조회수가 된다.

## 쪼개면 얼마나 빨리 대답하나

시간 쪼개기의 효과는 단순한 계산으로 짐작할 수 있다. 렌더 작업이 `unitMs`짜리 단위 `units`개이고, 렌더 단계는 한 조각에서 `sliceMs`를 넘기면 양보한다. 입력이 `inputAt`에 들어오면 그 시점에 돌고 있던 조각이 끝나야 처리된다. 입력이 기다린 시간을 돌려주는 함수를 짜 보자. 쪼개지 않는 경우는 조각 크기를 전체보다 크게(1000ms) 주면 된다.

## 입력칸의 값은 transition에 넣지 않는다

transition을 처음 쓸 때 가장 흔한 실수는 입력칸 자체를 transition으로 바꾸는 것이다.

```tsx
// 잘못된 예: 입력칸의 value가 transition 상태를 따른다
const [query, setQuery] = useState("");
<input value={query} onChange={(e) => startTransition(() => setQuery(e.target.value))} />
```

제어 컴포넌트의 입력칸은 React가 커밋할 때 DOM의 값을 `value` prop으로 되돌려 놓는다. 사용자가 글자를 쳤는데 그 글자를 담은 업데이트가 transition으로 밀리면, 그사이 다른 급한 렌더링이 커밋되면서 입력칸이 이전 값으로 돌아갔다가 나중에 다시 바뀐다. 글자가 늦게 찍히거나 커서가 튀는 처음 문제를 오히려 transition이 만든다. React 문서도 텍스트 입력을 제어하는 데는 transition을 쓸 수 없다고 적어 두었다.

상태를 둘로 나누는 게 정석이다. 입력칸이 보여 줄 값은 급한 업데이트로 바로 바꾸고, 그 값으로 그리는 무거운 화면은 다른 상태를 transition으로 바꾼다.

```tsx
const [query, setQuery] = useState("");          // 입력칸: 급한 업데이트
const [filter, setFilter] = useState("");        // 목록: transition
const [isPending, startTransition] = useTransition();

function onChange(e) {
  setQuery(e.target.value);
  startTransition(() => setFilter(e.target.value));
}

<input value={query} onChange={onChange} />
<div style={{ opacity: isPending ? 0.6 : 1 }}>
  <ResultList filter={filter} />                 {/* memo로 감싸 둔다 */}
</div>
```

`ResultList`가 `memo`가 아니면 효과가 없다는 점도 같이 기억한다. 급한 업데이트(`setQuery`)로 부모가 렌더링될 때 `ResultList`도 따라 렌더링되면, 무거운 일이 급한 쪽으로 다시 들어온다. 이 조합을 한 줄로 줄인 것이 `useDeferredValue`다. 상태를 둘로 나누는 대신 값 하나를 받아 "이 값의 뒤처진 버전"을 돌려준다. 내부적으로는 새 값으로 렌더링을 한 번 더 예약하는데, 그 렌더링이 transition처럼 낮은 우선순위로 돈다. 업데이트하는 코드를 고칠 수 있으면 `useTransition`, 값을 props로 받기만 하면 이쪽을 쓴다. React 19부터는 두 번째 인자로 첫 렌더링에서 쓸 값(`initialValue`)을 줄 수 있다.

디바운스와는 목적이 다르다. 디바운스는 고정 시간을 기다렸다가 한 번 실행해서 요청 횟수를 줄이고, transition은 기다리지 않고 바로 시작하되 입력에 밀려 양보한다. 빠른 기기에서는 transition이 거의 바로 끝나고, 느린 기기에서는 입력을 막지 않는다. 검색 API 호출을 줄이는 건 여전히 [디바운스](/posts/debounce-throttle)의 일이고, 둘은 함께 쓴다.

## 화면 일부만 새 값을 볼 때

렌더링을 쪼개면 새로운 종류의 버그가 생긴다. React의 state는 렌더링 하나 안에서 같은 값으로 고정되지만, React 밖에 있는 값은 그렇지 않다. 전역 변수, 직접 만든 저장소, `window`의 값처럼 아무 때나 바뀔 수 있는 값을 렌더 중에 직접 읽으면, 조각과 조각 사이에 그 값이 바뀌었을 때 트리의 앞쪽과 뒤쪽이 서로 다른 값을 본다. 화면이 찢어진다고 해서 tearing이라고 부른다.

실제로 만들어 봤다. 바깥 저장소 `store.v`를 렌더 중에 그대로 읽는 `Cell` 60개를 transition으로 다시 렌더링하고, 렌더링이 진행 중인 15ms 시점에 저장소 값을 1에서 2로 바꿨다. 커밋된 화면에서 각 칸의 값을 셌다.

```tsx
const Cell = memo(function Cell({ tick }) {
  const v = store.v;          // 렌더 중에 바깥 값을 직접 읽는다
  busy(1);
  return <span>{v}</span>;
});
```

```text
plain {"1":14,"2":46}
uses {"2":60}
```

직접 읽은 쪽(`plain`)은 앞의 14칸이 1, 뒤의 46칸이 2로 커밋됐다. 한 화면 안에서 같은 값을 보여 줘야 할 칸들이 서로 다른 값을 보여 준다. 장바구니 개수가 헤더와 사이드바에서 다르게 보이는 식이다. `useSyncExternalStore`로 읽은 쪽(`uses`)은 60칸 모두 2였다.

`useSyncExternalStore(subscribe, getSnapshot)`는 두 가지를 한다. 렌더 중에 `getSnapshot()`으로 읽은 값을 기억해 두고, 커밋하기 전에 저장소의 현재 스냅숏과 다시 비교한다(`checkIfSnapshotChanged`). 달라졌으면 그 렌더링을 커밋하지 않고 동기 우선순위로 다시 렌더링한다. 또 `subscribe`로 들어온 변경 알림은 항상 동기 업데이트(`forceStoreRerender`)로 처리한다.

이게 트레이드오프다. 외부 저장소의 변경은 transition이 될 수 없다. React 문서도 transition 도중 저장소가 바뀌면 그 업데이트를 막는 업데이트로 처리한다고 적어 두었다. Redux, Zustand, Jotai 같은 라이브러리가 `useSyncExternalStore`로 구독하니, 그 저장소의 값을 `startTransition` 안에서 바꿔도 시간 쪼개기는 일어나지 않는다. 무거운 화면을 미루고 싶다면 저장소에서 읽은 값을 `useDeferredValue`로 받거나, 무거운 부분이 보는 값을 React state로 한 번 옮겨 그 state를 transition으로 바꾼다. `getSnapshot`은 저장소가 그대로면 같은 참조를 돌려줘야 한다는 것도 기억한다. 매번 새 객체를 돌려주면 React가 계속 "바뀌었다"고 보고 다시 렌더링한다. 개발 모드에서는 `The result of getSnapshot should be cached to avoid an infinite loop` 경고가 뜬다.

## React 19의 async transition

React 19부터 `startTransition`에 async 함수를 넘길 수 있다. React는 이런 transition을 액션(Action)이라고 부른다. 함수가 끝날 때까지, 즉 반환한 프로미스가 끝날 때까지 `isPending`이 `true`로 남는다. 서버에 저장하는 동안 버튼을 비활성화하는 코드를 `isLoading` 상태 없이 쓸 수 있다.

```tsx
function RenameButton({ name }) {
  const [label, setLabel] = useState(name);
  const [isPending, startTransition] = useTransition();

  function onClick() {
    startTransition(async () => {
      const saved = await renameOnServer(label);   // 100ms
      startTransition(() => setLabel(saved));      // await 뒤라서 한 번 더 감싼다
    });
  }
  return <button disabled={isPending} onClick={onClick}>{label}</button>;
}
```

`await` 앞뒤로 커밋 시각을 찍으면 이렇게 나온다.

```text
  16ms commit name=old isPending=false
  28ms action start
  31ms commit name=old isPending=true
 129ms server done
 132ms commit name=new isPending=false
```

`isPending`이 `true`인 커밋과 새 이름이 들어간 커밋 사이에 `isPending=false`인 중간 화면이 없다. 서버 응답과 상태 반영이 한 transition으로 묶여서, 저장은 끝났는데 이름은 아직 옛것인 화면이 나오지 않는다.

액션 안에서 던진 에러는 가장 가까운 에러 경계로 간다. 30ms 뒤에 에러를 던지는 액션을 실행하면 `pending=true`였던 화면이 에러 경계의 fallback(`boundary: save failed`)으로 바뀌었다. 사용자에게 토스트만 띄우고 화면은 그대로 두고 싶다면 액션 안에서 `try/catch`로 잡아 상태로 바꾼다. 에러 경계가 어떻게 잡는지는 [Suspense와 에러 경계](/posts/react-suspense-error-boundary)에서 다룬다.

여러 액션이 겹칠 때도 생각할 것이 있다. 같은 버튼을 빠르게 두 번 누르면 두 액션이 동시에 돌고, `isPending`은 둘 다 끝날 때까지 `true`다. 서버 응답 순서는 보장되지 않으니 늦게 시작한 요청이 먼저 끝나면 결과가 뒤바뀔 수 있다. 순서가 중요하면 진행 중일 때 버튼을 막거나, 이전 요청을 취소하거나, 액션을 순서대로 처리해 주는 폼 쪽 훅을 쓴다.

## transition을 넣었는데 여전히 버벅일 때

현장에서 "transition을 넣었는데 효과가 없다"는 말은 대개 아래 중 하나다. 순서대로 본다.

업데이트가 실제로 transition이 됐는지부터 확인한다. `setTimeout`이나 `await` 뒤에서 `setState`를 불렀다면 표시가 빠졌다. 데이터를 받아 와서 무거운 목록에 넣는 코드에서 특히 자주 보인다.

```tsx
// 표시가 빠진다: await 뒤의 setReviews는 일반 업데이트다
startTransition(async () => {
  const data = await fetchReviews();
  setReviews(data);
});

// 다시 감싼다
startTransition(async () => {
  const data = await fetchReviews();
  startTransition(() => setReviews(data));
});
```

 React 19.2 이상 개발 빌드라면 크롬 Performance 패널의 React Scheduler 트랙에서 그 렌더링이 Blocking 줄에 찍혔는지 Transition 줄에 찍혔는지 바로 보인다.

외부 저장소의 값으로 그리는 화면인지 본다. 상태 라이브러리의 값이 바뀌어서 그리는 무거운 화면은 앞에서 본 이유로 transition이 되지 않는다.

급한 업데이트가 무거운 쪽을 같이 렌더링하고 있지 않은지 본다. 입력칸과 무거운 목록이 같은 부모 아래 있고 목록이 `memo`가 아니면, 입력 한 글자마다 목록이 급한 우선순위로 같이 렌더링된다. Profiler에서 입력 커밋에 목록 컴포넌트가 들어 있으면 이 경우다.

혼자 오래 걸리는 컴포넌트가 있는지 본다. 앞의 계산처럼 컴포넌트 하나가 쪼갤 수 없는 단위다. 큰 배열 정렬, 수천 개짜리 `map` 안의 무거운 계산은 `useMemo`로 다시 계산하지 않게 하거나, 화면에 보이는 줄만 그리는 가상화로 단위 자체를 줄인다.

어딘가에서 `flushSync`를 부르지 않는지 본다. `flushSync`는 그 안의 업데이트를 SyncLane으로 즉시 처리하면서, 진행 중이던 transition 렌더링도 끊는다. 스크롤 위치를 맞추려고 넣어 둔 `flushSync`가 매 입력마다 transition을 처음으로 돌려보내는 경우가 있다.

마지막으로, 측정은 INP로 한다. transition이 잘 동작하면 렌더링 총시간은 오히려 조금 늘 수 있다(버려지는 렌더링과 양보 비용). 대신 입력에서 다음 화면까지의 시간이 줄어든다. 개발자 노트북보다 사용자 휴대폰이 몇 배 느리니 CPU를 4~6배 느리게 걸고 비교한다.

## 탭 화면으로 돌아가서

리뷰 탭이 Q&A 클릭을 막았던 건 탭을 바꾸는 업데이트가 클릭과 같은 막는 우선순위였기 때문이다. `startTransition`은 콜백 안에서 동기로 불린 `setState`에 transition lane을 붙이고, React는 그 렌더링을 5ms씩 쪼개 양보한다. 그사이 클릭이 오면 클릭을 먼저 커밋하고 transition 초안은 버린 뒤 최신 상태 위에서 다시 시작한다. 그래서 입력칸처럼 바로 보여야 하는 값은 transition에 넣지 않고, 렌더 중에 바깥 값을 직접 읽지 않으며, 외부 저장소는 `useSyncExternalStore`로 읽는다. 그 대가로 외부 저장소 변경은 transition이 되지 못한다. 데이터를 기다리는 화면에서 transition이 이미 보이던 내용을 지켜 주는 방법은 [Suspense와 에러 경계](/posts/react-suspense-error-boundary)에서 이어진다.

## 면접에서 나올 만한 질문

### 동시성 렌더링은 무엇을 해결하나요?

긴 렌더링이 메인 스레드를 붙잡아 사용자 입력이 늦게 처리되는 문제를 푼다. 업데이트마다 우선순위를 두고, 낮은 우선순위 렌더링은 5ms쯤마다 브라우저에 양보하며 진행한다. 그사이 급한 입력이 오면 그걸 먼저 커밋하고 하던 렌더링은 버린 뒤 다시 시작한다. 렌더링이 빨라지는 게 아니라 입력이 막히지 않게 되는 것이다.

### lane은 무엇인가요?

React가 업데이트에 붙이는 우선순위로, 31비트 정수의 비트 하나로 나타낸다. 클릭 같은 discrete 입력은 SyncLane, 드래그·스크롤은 InputContinuousLane, 이벤트 밖은 DefaultLane, `startTransition`은 TransitionLanes를 받는다. 여러 업데이트를 OR로 합쳐 들고 있다가 가장 낮은 비트를 골라 렌더링한다. Sync·InputContinuous·Default는 끝까지 한 번에, transition 계열은 쪼개서 렌더링한다.

### startTransition 안에서 setTimeout으로 setState하면 transition이 되나요?

안 된다. `startTransition`은 콜백이 동기로 실행되는 동안만 transition 표시를 켜 두고, 그 사이에 불린 `setState`만 transition lane을 받는다. `setTimeout` 콜백이나 `await` 뒤 코드는 표시가 꺼진 뒤에 실행되니 일반 업데이트가 된다. React 19에서도 `await` 뒤의 `setState`는 `startTransition`으로 한 번 더 감싸야 한다.

### 입력칸의 상태를 transition으로 업데이트하면 안 되는 이유는요?

제어 입력칸은 커밋할 때 DOM 값을 `value`로 맞추는데, 입력 업데이트가 밀리면 그사이 다른 커밋이 입력칸을 이전 값으로 되돌린다. 글자가 늦게 찍히거나 커서가 튄다. 입력칸이 보여 줄 값은 급한 업데이트로 바로 바꾸고, 그 값으로 그리는 무거운 화면만 별도 상태를 transition으로 바꾸거나 `useDeferredValue`로 미룬다.

### tearing은 무엇이고 useSyncExternalStore는 어떻게 막나요?

쪼개진 렌더링 사이에 React 밖의 값이 바뀌어, 한 번 커밋된 화면 안에서 컴포넌트마다 다른 값을 보여 주는 현상이다. `useSyncExternalStore`는 렌더 중에 읽은 스냅숏을 커밋 직전에 다시 확인해서 달라졌으면 그 렌더링을 버리고 동기로 다시 렌더링한다. 저장소 변경 알림도 동기 업데이트로 처리한다. 그래서 외부 저장소의 변경은 transition이 될 수 없다.

### transition을 썼는데 여전히 입력이 버벅입니다. 무엇을 보나요?

업데이트가 정말 transition이 됐는지(`setTimeout`·`await` 뒤인지), 외부 저장소의 값으로 그리는지, 급한 렌더링에 무거운 자식이 `memo` 없이 같이 그려지는지, 컴포넌트 하나가 혼자 오래 걸리는지, 어딘가의 `flushSync`가 transition을 끊는지 순서대로 본다. 시간 쪼개기는 컴포넌트 사이에서만 일어나니 하나의 무거운 컴포넌트는 transition으로 해결되지 않는다.

### React 19의 async transition은 무엇이 달라졌나요?

`startTransition`에 async 함수를 넘길 수 있고, 반환한 프로미스가 끝날 때까지 `isPending`이 `true`로 남는다. 서버 요청과 상태 반영이 한 transition으로 묶여 중간 화면이 나오지 않는다. 안에서 던진 에러는 가장 가까운 에러 경계로 간다. 여러 액션이 겹치면 응답 순서가 보장되지 않으니 버튼을 막거나 이전 요청을 취소한다.
