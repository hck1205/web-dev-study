`User`에 `role` 필드를 추가하고 API 응답, 목록 화면까지 고쳤다. 그런데 회원 정보 수정 폼은 `role` 없이 그대로 저장 요청을 보냈고, 타입 검사도 아무 말이 없었다. 폼 타입을 `User`에서 손으로 베껴 만들어 뒀기 때문이다.

```ts
interface User {
  id: number;
  name: string;
  email: string;
  role: "admin" | "member";
}

// 손으로 베낀 폼 타입: role이 추가된 걸 모른다
interface UserFormCopied {
  name: string;
  email: string;
}
// User에서 뽑아낸 폼 타입
type UserForm = Omit<User, "id">;

const copied: UserFormCopied = { name: "Kim", email: "kim@example.com" };
const derived: UserForm = { name: "Kim", email: "kim@example.com" };
```

TypeScript 5.9의 `tsc --strict`로 검사하면 베낀 쪽은 통과하고, 뽑아낸 쪽만 걸린다.

```text
drift.ts(17,7): error TS2741: Property 'role' is missing in type '{ name: string; email: string; }' but required in type 'UserForm'.
```

타입을 복사하면 원본과 사본이 따로 늙는다. 원본 하나를 두고 나머지를 거기서 계산해 내면, 원본이 바뀔 때 사본도 같이 바뀌고 어긋난 곳은 컴파일 에러로 드러난다. 이 글은 그 계산 도구를 다룬다. 표준 유틸리티 타입(`Partial`, `Pick`, `Omit`, `Record`)에서 시작해 그것들을 만드는 재료인 매핑된 타입, 조건부 타입, `infer`, 템플릿 리터럴 타입을 열어 보고, 마지막으로 `satisfies`를 본다. 출력은 TypeScript 5.9.3과 Node.js 22에서 실제로 돌린 결과다. 타입을 펼쳐 보여 주는 출력은 에디터의 hover와 같은 일을 하는 작은 스크립트(컴파일러 API의 `typeToString`)로 찍었다.

이 주제의 다른 글: 구조적 타이핑과 `any`·`unknown`·`never`는 [타입 시스템 기초](/posts/ts-type-system-basics)에서, 타입 매개변수와 제약(`extends`)은 [제네릭](/posts/ts-generics)에서 다룬다. 여기서는 그 위에서 "타입으로 타입을 만드는 법"만 본다.

## 원본 하나에서 뽑아내는 다섯 가지 모양

자주 쓰는 다섯 개부터 보자. 모두 `lib.es5.d.ts`에 들어 있는 평범한 타입 별칭이라 따로 설치할 것이 없다.

```ts
type UserPatch = Partial<User>;                 // 모든 필드를 선택으로
type UserPreview = Pick<User, "id" | "name">;   // 고른 필드만
type NewUser = Omit<User, "id">;                // 고른 필드를 빼고
type ByRole = Record<User["role"], User[]>;     // 키 집합 → 같은 값 타입
type FrozenUser = Readonly<User>;               // 모든 필드를 읽기 전용으로
```

펼쳐 보면 이렇게 된다.

```text
type UserPatch = { id?: number | undefined; name?: string | undefined; email?: string | undefined; role?: "admin" | "member" | undefined; }
type UserPreview = { id: number; name: string; }
type NewUser = { name: string; email: string; role: "admin" | "member"; }
type ByRole = { admin: User[]; member: User[]; }
type FrozenUser = { readonly id: number; readonly name: string; readonly email: string; readonly role: "admin" | "member"; }
```

`User["role"]`은 인덱스 접근 타입이다. 객체 타입에서 필드 하나의 타입을 꺼낸다. 여기서는 `"admin" | "member"`가 나왔고, 그걸 `Record`의 키로 넣었으니 역할이 하나 늘면 `ByRole`에도 키가 저절로 늘어난다.

아래 그림은 이 관계를 보여 준다. 화살표를 따라 흐르는 점이 원본의 변경이 퍼져 나가는 방향이다.


빈 객체 `{}`가 통과하는 것도 봐 둘 만하다. `Partial`은 "아무것도 안 보내도 된다"까지 허용한다. 최소 한 필드는 있어야 한다면 `Partial`만으로는 표현이 안 되고, 런타임 검사나 더 복잡한 타입이 필요하다.

`Record`는 키를 빠짐없이 채우게 강제한다는 점이 쓸모 있다. 역할별 라벨, 상태별 색처럼 "경우마다 하나씩" 있어야 하는 표를 `Record<유니온, 값>`으로 적어 두면, 유니온에 경우가 늘었을 때 표를 안 고친 곳이 모두 에러가 된다. `Readonly`는 얕다. `frozen.name`은 막지만 필드가 객체라면 그 안쪽은 여전히 바꿀 수 있고, 런타임에서 `Object.freeze`처럼 막아 주지도 않는다.

### Omit은 오타를 잡아 주지 않는다

`Pick`과 `Omit`은 짝처럼 보이지만 키를 검사하는 방식이 다르다.

```ts
type A = Omit<User, "emial">;
type B = Pick<User, "emial">;
```

```text
omit-typo.ts(8,21): error TS2344: Type '"emial"' does not satisfy the constraint 'keyof User'.
```

에러는 `Pick` 줄 하나뿐이다. 선언을 보면 이유가 보인다.

```ts
type Pick<T, K extends keyof T> = { [P in K]: T[P] };
type Omit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>;
```

`Pick`의 `K`는 `keyof T` 안에 있어야 하지만, `Omit`의 `K`는 아무 키(`string | number | symbol`)나 받는다. 그래서 `"emial"`을 빼라고 하면 "그런 키는 원래 없으니 뺄 것도 없다"로 끝나고, `A`는 `User`와 똑같아진다. 필드 이름을 바꾸는 리팩터링 뒤에 `Omit`이 조용히 효력을 잃는 일이 여기서 생긴다. 키를 엄격하게 검사하고 싶으면 직접 만든다.

```ts
type StrictOmit<T, K extends keyof T> = Omit<T, K>;
```

### 유니온에 Omit을 씌우면 판별 필드가 뭉개진다

```ts
interface Circle { kind: "circle"; id: string; radius: number }
interface Square { kind: "square"; id: string; size: number }
type Shape = Circle | Square;
type ShapeNoId = Omit<Shape, "id">;
```

```text
type ShapeNoId = { kind: "circle" | "square"; }
```

`radius`와 `size`가 사라졌다. `keyof (Circle | Square)`는 두 타입에 공통으로 있는 키(`kind`, `id`)뿐이라서, `Omit`은 그중 `id`를 빼고 `kind` 하나만 남긴다. 유니온의 각 멤버에 따로 적용하려면 뒤에 나올 분배 조건부 타입으로 감싼다. 판별 유니온을 좁히는 방법 자체는 [타입 좁히기](/posts/ts-narrowing)에서 다룬다.

## Partial을 열어 보면 키를 도는 반복문이다

`Partial`의 실제 선언은 한 줄이다.

```ts
type Partial<T> = { [P in keyof T]?: T[P] };
```

이 문법을 매핑된 타입(mapped type)이라고 한다. `[P in 키 유니온]`은 타입 수준의 for 문이다. 키 유니온의 멤버 하나하나를 `P`에 넣고, 콜론 오른쪽의 값 타입을 계산해 필드를 하나씩 만든다. 아래 그림에서 다음을 누르면 `keyof User`를 한 칸씩 돌며 결과 타입이 쌓인다.

이 반복문에는 손댈 곳이 세 군데 있다. 수식어(`?`, `readonly`)를 붙이거나 떼는 것, 키 이름을 바꾸는 것(`as`), 값 타입을 바꾸는 것이다.

```ts
interface User {
  id: number;
  name: string;
  email?: string;
  readonly createdAt: Date;
}
type Mutable<T> = { -readonly [K in keyof T]: T[K] };
type Concrete<T> = { [K in keyof T]-?: T[K] };
type Getters<T> = { [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K] };
type OnlyStrings<T> = { [K in keyof T as T[K] extends string ? K : never]: T[K] };
```

```text
type M = { id: number; name: string; email?: string | undefined; createdAt: Date; }
type C = { id: number; name: string; email: string; readonly createdAt: Date; }
type G = { getId: () => number; getName: () => string; getEmail?: (() => string | undefined) | undefined; readonly getCreatedAt: () => Date; }
type O = { name: string; }
```

`-readonly`와 `-?`는 수식어를 뗀다. `Required<T>`가 바로 `-?` 한 줄이다. `as` 뒤에는 새 키 이름을 계산하는 식이 오고(TypeScript 4.1부터), 결과가 `never`인 키는 아예 빠진다. `OnlyStrings`가 그렇게 문자열 필드만 걸러 냈다.

출력에서 놓치기 쉬운 두 가지가 있다. 첫째, `Getters`의 `getEmail`에 `?`가, `getCreatedAt`에 `readonly`가 남아 있다. `[K in keyof T]`처럼 원본의 키를 그대로 도는 매핑된 타입은 원본의 수식어를 물려받는다. 이걸 동형(homomorphic) 매핑이라고 부른다. 반대로 `[K in "a" | "b"]`처럼 키를 따로 주면 수식어가 따라오지 않는다. 둘째, `OnlyStrings`에서 `email`이 빠졌다. 선택 필드의 `T[K]`는 `string | undefined`라서 `string`에 포함되지 않는다. 걸러 내는 조건을 짤 때 선택 필드는 따로 생각해야 한다.

## 타입에 if를 거는 조건부 타입

`T extends U ? X : Y`는 "T가 U에 들어가면 X, 아니면 Y"다. 여기서 `extends`는 상속이 아니라 "할당할 수 있나"를 묻는다.

```ts
type IsString<T> = T extends string ? "yes" : "no";
type A1 = IsString<"hi">;
type A2 = IsString<42>;
type A3 = IsString<"hi" | 42>;
type NoDist<T> = [T] extends [string] ? "yes" : "no";
type A4 = NoDist<"hi" | 42>;
type A5 = IsString<never>;
type A6 = NoDist<never>;
```

```text
type A1 = "yes"
type A2 = "no"
type A3 = "yes" | "no"
type A4 = "no"
type A5 = never
type A6 = "yes"
```

`A3`가 흥미롭다. `"hi" | 42`는 통째로 보면 `string`이 아니니 `"no"`가 나와야 할 것 같은데, `"yes" | "no"`가 나왔다. 검사하는 자리에 맨 타입 매개변수(`T extends ...`)가 오면 조건부 타입은 유니온을 멤버별로 쪼개 따로 계산하고 결과를 다시 합친다. 이걸 분배 조건부 타입(distributive conditional type)이라고 한다. `Exclude`와 `Extract`가 이 성질로 만들어졌다.

```ts
type Exclude<T, U> = T extends U ? never : T;
type Status = "idle" | "loading" | "success" | "error";
type Done = Exclude<Status, "idle" | "loading">;   // "success" | "error"
```

분배를 끄고 유니온을 통째로 묻고 싶으면 `[T] extends [string]`처럼 양쪽을 튜플로 감싼다. 맨 타입 매개변수가 아니게 되니 쪼개지 않는다. `A4`가 그렇게 `"no"`를 냈다.

`never`는 함정이 된다. `never`는 멤버가 0개인 유니온이라, 분배하면 계산할 멤버가 없어서 결과도 `never`다(`A5`). "이 타입이 never인지" 검사하려고 `T extends never ? true : false`를 쓰면 항상 `never`가 나온다. 이때도 `[T] extends [never]`로 감싸야 한다(`A6`).

앞에서 뭉개졌던 `Omit`도 분배로 고친다.

```ts
type DistOmit<T, K extends PropertyKey> = T extends unknown ? Omit<T, K> : never;
type ShapeNoId2 = DistOmit<Shape, "id">;
```

```text
type ShapeNoId2 = Omit<Circle, "id"> | Omit<Square, "id">
```

`T extends unknown`은 항상 참이다. 조건 자체엔 뜻이 없고, 분배를 일으키려고 쓰는 관용구다.

가장 많이 쓰는 곳은 함수에서 타입을 끌어내는 일이다. API 함수의 반환 타입을 손으로 적지 않고 함수에서 뽑는다.

```ts
async function fetchUser(id: number) {
  return { id, name: "Kim", tags: ["a", "b"] };
}
type ElementOf<T> = T extends readonly (infer E)[] ? E : never;
type R1 = ReturnType<typeof fetchUser>;
type R2 = Awaited<ReturnType<typeof fetchUser>>;
type R3 = Parameters<typeof fetchUser>;
type R4 = ElementOf<R2["tags"]>;
type R5 = ElementOf<string>;
```

```text
type R1 = Promise<{ id: number; name: string; tags: string[]; }>
type R2 = { id: number; name: string; tags: string[]; }
type R3 = [id: number]
type R4 = string
type R5 = never
```

`async` 함수의 `ReturnType`은 `Promise`로 감싸여 나온다. 그 안을 꺼내는 게 `Awaited`다(TypeScript 4.5부터). `Awaited`는 `Promise<Promise<T>>`처럼 겹쳐도 끝까지 벗기고, `then` 메서드가 있는 객체도 Promise처럼 다룬다. `typeof fetchUser`는 값을 타입 자리로 옮기는 연산이다. 타입 수준 `typeof`는 변수나 함수 이름에만 쓸 수 있다.

이 방식에는 방향 문제가 있다. 함수 구현이 타입의 원천이 되니, 구현에서 실수로 필드 하나를 빠뜨리면 그게 그대로 "정답 타입"이 된다. 서버 응답처럼 바깥에서 들어오는 값은 함수에서 뽑지 말고 계약(스키마나 직접 쓴 interface)을 원본으로 둔 뒤, 함수의 반환 타입을 그 계약으로 못 박는 편이 안전하다. 반대로 내부 헬퍼처럼 구현이 곧 계약인 곳에서는 뽑아 쓰는 쪽이 중복이 적다.

## 문자열도 타입으로 조립한다

자바스크립트의 템플릿 리터럴 문법을 타입 자리에 쓰면 문자열 리터럴 타입을 조립할 수 있다. TypeScript 4.1부터 생긴 템플릿 리터럴 타입이다. 유니온을 넣으면 가능한 조합을 모두 펼친다.

```ts
type EventName = "click" | "focus";
type Handler = `on${Capitalize<EventName>}`;
type Variant = `${"sm" | "md"}-${"red" | "blue"}`;
type Px = `${number}px`;
const w: Px = "12rem";
const ok: Px = "1.5px";
```

```text
type Handler = "onClick" | "onFocus"
type Variant = "sm-red" | "sm-blue" | "md-red" | "md-blue"
tpl-err.ts(10,7): error TS2322: Type '"12rem"' is not assignable to type '`${number}px`'.
```

`Capitalize`, `Uncapitalize`, `Uppercase`, `Lowercase`는 컴파일러에 내장된 문자열 변환 타입이다. 조합은 곱셈으로 늘어난다. 크기 4개 × 색 8개 × 상태 5개면 160개짜리 유니온이고, 유니온이 10만 개에 이르면 컴파일러가 "Expression produces a union type that is too complex to represent"(TS2590)로 멈춘다.

`infer`와 섞으면 문자열을 파싱할 수도 있다. 라우트 패턴에서 매개변수 이름을 뽑아내는 타입이다.

```ts
type Params<P extends string> =
  P extends `${string}:${infer Name}/${infer Rest}`
    ? Name | Params<`/${Rest}`>
    : P extends `${string}:${infer Name}`
      ? Name
      : never;

type T1 = Params<"/users/:userId/posts/:postId">;   // "userId" | "postId"
type T2 = Params<"/about">;                         // never

declare function link<P extends string>(path: P, params: { [K in Params<P>]: string }): string;
link("/users/:userId/posts/:postId", { userId: "1" });
```

```text
tpl-err.ts(8,38): error TS2345: Argument of type '{ userId: string; }' is not assignable to parameter of type '{ userId: string; postId: string; }'.
  Property 'postId' is missing in type '{ userId: string; }' but required in type '{ userId: string; postId: string; }'.
```

## satisfies로 검사만 받기

타입 표기, `as const`, `satisfies`가 리터럴 타입을 각각 어떻게 남기는지는 [타입 시스템 기초](/posts/ts-type-system-basics)에서 봤다. 여기서는 키를 모르는 객체 타입(`Record<string, ...>`)과 만났을 때 생기는 사고를 본다. 설정 객체를 만들 때 흔히 이렇게 쓴다.

```ts
type Route = { path: string; auth: boolean };

const annotated: Record<string, Route> = {
  home: { path: "/", auth: false },
  settings: { path: "/settings", auth: true },
};
console.log(annotated.setings.path);
```

`tsc --strict`는 아무 말이 없다. 그런데 Node 22로 실행하면 터진다.

```text
console.log(annotated.setings.path);
                              ^

TypeError: Cannot read properties of undefined (reading 'path')
```

`: Record<string, Route>`라고 적는 순간 변수의 타입은 "아무 문자열 키에 Route가 있는 객체"가 된다. 객체 리터럴에 실제로 어떤 키가 있었는지는 버려진다. 그러니 오타 난 `setings`도 "있을 수 있는 키"로 통과한다. 타입 주석은 검사도 하지만 변수의 타입을 그 타입으로 넓혀 버린다.

TypeScript 4.9에서 생긴 `satisfies`는 검사만 하고 넓히지 않는다.

```ts
const checked = {
  home: { path: "/", auth: false },
  settings: { path: "/settings", auth: true },
} satisfies Record<string, Route>;
checked.setings.path;

const typo = {
  home: { path: "/", auth: "no" },
} satisfies Record<string, Route>;
```

```text
sat.ts(13,9): error TS2551: Property 'setings' does not exist on type '{ home: { path: string; auth: false; }; settings: { path: string; auth: true; }; }'. Did you mean 'settings'?
sat.ts(16,22): error TS2322: Type 'string' is not assignable to type 'boolean'.
```

오타 접근도, 잘못된 값도 둘 다 잡혔다. 아래 그림은 같은 객체가 두 길을 지날 때 변수 타입이 어떻게 갈리는지 보여 준다.

값 쪽 타입도 좁게 남는다. 색과 간격을 섞은 토큰 객체로 보면 차이가 더 분명하다.

```ts
const palette = { primary: "#2563eb", gap: 8 } satisfies Record<string, string | number>;
palette.primary.toUpperCase();   // string으로 남아 있어 통과
const loose: Record<string, string | number> = { primary: "#2563eb", gap: 8 };
loose.primary.toUpperCase();
```

```text
sat.ts(22,15): error TS2339: Property 'toUpperCase' does not exist on type 'string | number'.
  Property 'toUpperCase' does not exist on type 'number'.
```

세 가지 도구를 정리하면 이렇다.

| 쓰는 법 | 검사 | 변수 타입 | 쓰는 곳 |
|---|---|---|---|
| `const x: T = ...` | 한다 | `T`로 넓어진다 | 나중에 다른 값이 들어올 변수, 함수 매개변수·반환값 |
| `const x = ... satisfies T` | 한다 | 리터럴에서 추론한 좁은 타입 | 설정 객체, 라우트 표, 토큰처럼 모양이 고정된 상수 |
| `const x = ... as T` | 거의 안 한다 | `T`로 바뀐다 | 검사기가 모르는 사실을 내가 보장할 때만 |

`as`는 검사가 아니라 단언이다. `{ path: 1 } as unknown as Record<string, Route>`도 에러 없이 통과한다. 마지막으로 `as const satisfies T`를 함께 쓰면 리터럴 값까지(`path: "/"`) 읽기 전용으로 고정하면서 모양을 검사한다. 상수 표를 만들 때 많이 쓰는 조합이다.

## 타입이 너무 영리해지면

타입 수준 프로그래밍은 재미있지만 비용이 있다. 재귀 타입은 깊이 제한에 걸린다.

```ts
type BuildTuple<N extends number, T extends unknown[] = []> =
  T["length"] extends N ? T : BuildTuple<N, [...T, unknown]>;
type Big = BuildTuple<1000>["length"];
```

```text
d1000.ts(3,12): error TS2589: Type instantiation is excessively deep and possibly infinite.
```

TypeScript 5.9에서 `BuildTuple<999>`는 통과하고 `1000`부터 TS2589가 났다. 꼬리 재귀 형태의 조건부 타입은 4.5부터 1000단계까지 허용되는데, 그 경계에 걸린 것이다. 재귀 호출 결과에 `1 | ...`처럼 무언가를 덧붙이는 꼬리 재귀가 아닌 버전은 같은 환경에서 48단계부터 걸렸다.

실무에서 더 자주 겪는 건 에러가 아니라 느려짐이다. 큰 객체 타입(예: DOM 타입 전체)에 "모든 경로를 문자열로" 같은 재귀 매핑을 걸면 에디터 자동 완성이 몇 초씩 멈추고, hover에는 `... 171 more ...`처럼 잘린 타입이 뜬다. 증상이 보이면 `tsc --extendedDiagnostics`로 `Instantiations`와 `Check time`을 보고, `tsc --generateTrace 폴더`로 어느 파일의 어느 타입이 오래 걸리는지 찾는다. 이 옵션들은 [tsconfig와 strict 옵션](/posts/tsconfig-strict) 글에서 실제 출력과 함께 본다.

고르는 기준은 단순하다. 같은 팀원이 hover 결과를 읽고 에러 메시지를 이해할 수 있는가. 유틸리티 타입 두세 개를 겹친 정도는 괜찮다. 다섯 겹이 넘어가고 재귀까지 들어가면, 그 결과를 이름 있는 interface로 한 번 적어 두는 편이 읽기도 쉽고 검사도 빠르다. 에러 메시지에 `Omit<Partial<Pick<...>>>`가 그대로 찍혀 읽기 어렵다면 매핑된 타입 한 겹으로 펼쳐 보여 주는 관용구도 있다.

```ts
type Prettify<T> = { [K in keyof T]: T[K] } & {};
```

## React 코드에서 자주 만나는 조합

React에서는 기존 컴포넌트의 props를 원본으로 두고 뽑아 쓰는 일이 많다.

```tsx
import type { ComponentProps } from "react";

// input의 모든 속성을 받되 onChange만 문자열을 넘기게 바꾼다
type TextFieldProps = Omit<ComponentProps<"input">, "onChange"> & {
  onChange: (value: string) => void;
};

// 남이 만든 컴포넌트의 props를 꺼내 쓴다
type ButtonProps = ComponentProps<typeof Button>;

// 상태별 표시를 빠짐없이 채우게 강제한다
const statusColor = {
  idle: "gray",
  loading: "blue",
  success: "green",
  error: "red",
} satisfies Record<Status, string>;
```

`Omit`으로 원래 `onChange`를 빼지 않고 `&`로 덮으면 두 시그니처가 교차되어 어느 쪽도 제대로 맞지 않는 타입이 된다. 덮어쓸 때는 빼고 더한다. props 타이핑의 나머지(children, 이벤트, ref, 판별 props)는 [React에서 TypeScript 쓰기](/posts/typescript-in-react)에서 다룬다.

## 연습: 라우트 매칭 함수 만들기

앞의 `Params` 타입은 컴파일 시간에 이름만 뽑는다. 이번에는 실제 경로 문자열을 패턴에 맞춰 보고 매개변수 값을 꺼내는 런타임 함수를 직접 만들어 보자. 규칙은 이렇다. 세그먼트 수가 다르면 `null`, 콜론으로 시작하는 세그먼트는 값을 꺼내되(퍼센트 인코딩은 풀고) 비어 있으면 `null`, 나머지 세그먼트는 정확히 같아야 한다. 타입은 실행할 때 지워진다.

## 다시 role이 빠진 폼으로

처음의 폼 버그는 타입을 복사해서 생겼다. 원본을 하나 두고 `Pick`, `Omit`, `Partial`, `Record`로 뽑아내면 원본이 바뀔 때 어긋난 곳이 컴파일 에러로 드러난다. 그 유틸리티들은 매핑된 타입(키를 도는 반복문)과 조건부 타입(멤버마다 분배되는 if), `infer`(안쪽 타입 붙잡기)로 만든 평범한 별칭이라서, 원리를 알면 필요한 것을 직접 만들 수 있다. 다만 `Omit`의 느슨한 키 검사, 유니온에서 뭉개지는 필드, 분배되는 `never` 같은 모서리를 알고 써야 하고, 영리한 타입이 읽기 어려워지면 이름 있는 interface로 돌아가는 것도 선택지다. 다음은 이 검사들을 실제로 얼마나 엄격하게 할지 정하는 [tsconfig의 strict 옵션](/posts/tsconfig-strict)이다.

## 면접에서 나올 만한 질문

### Pick과 Omit은 무엇이 다른가요?

`Pick`은 고른 키만 남기고, `Omit`은 고른 키를 뺀다. 결정적인 차이는 키 검사다. `Pick<T, K>`는 `K`가 `keyof T` 안에 있어야 하지만, `Omit<T, K>`는 아무 키나 받아서 오타가 나도 에러 없이 원본을 그대로 돌려준다. 필드 이름이 바뀌는 리팩터링 뒤에 `Omit`이 조용히 효력을 잃을 수 있어서, 엄격하게 쓰고 싶으면 `K extends keyof T`로 제약을 건 별칭을 만든다.

### Partial은 어떻게 구현되어 있나요?

`{ [P in keyof T]?: T[P] }` 한 줄짜리 매핑된 타입이다. `keyof T`의 각 키를 돌면서 원래 값 타입(`T[P]`)에 `?`를 붙인 필드를 만든다. 원본의 키를 그대로 도는 동형 매핑이라 `readonly` 같은 원래 수식어도 유지된다. `Required`는 같은 모양에 `-?`를 써서 선택 표시를 뗀다.

### 분배 조건부 타입이란 무엇이고 어떻게 막나요?

조건부 타입의 검사 자리에 맨 타입 매개변수가 오고 거기에 유니온이 들어오면, 멤버마다 따로 계산해서 결과를 합치는 동작이다. `Exclude<"a" | "b", "a">`가 `"b"`를 내는 것이 이 덕분이다. 유니온을 통째로 검사하고 싶으면 `[T] extends [U]`처럼 양쪽을 튜플로 감싸 분배를 끈다. `never`가 들어오면 분배할 멤버가 없어 결과가 `never`가 되기 때문에, never 검사도 이렇게 감싸서 해야 한다.

### infer는 어디에 쓰나요?

조건부 타입의 `extends` 오른쪽에서 "이 자리의 타입을 이름 붙여 잡아 달라"고 할 때 쓴다. `ReturnType`, `Parameters`, `Awaited` 같은 표준 타입이 모두 `infer`로 만들어졌고, 배열의 원소 타입이나 템플릿 리터럴 안의 문자열 조각을 꺼낼 때도 쓴다. 실무에서는 `Awaited<ReturnType<typeof fetchUser>>`처럼 함수에서 결과 타입을 뽑는 데 많이 쓰는데, 외부 데이터라면 구현보다 계약을 원본으로 두는 편이 안전하다.

### satisfies와 타입 주석은 어떻게 다른가요?

둘 다 값이 타입에 맞는지 검사하지만, 타입 주석은 변수의 타입을 주석의 타입으로 넓히고 `satisfies`는 리터럴에서 추론한 좁은 타입을 그대로 둔다. 그래서 `Record<string, Route>`로 주석을 달면 없는 키 접근이 통과해 런타임에서 터지고, `satisfies`로 쓰면 컴파일 에러로 잡힌다. TypeScript 4.9부터 쓸 수 있고, 설정 객체나 상수 표처럼 모양이 고정된 값에 잘 맞는다. `as`는 검사가 아니라 단언이라 셋 중 가장 약하다.

### 유니온 타입에 Omit을 쓰면 왜 필드가 사라지나요?

`Omit`은 내부에서 `keyof T`를 쓰는데, 유니온의 `keyof`는 모든 멤버에 공통으로 있는 키뿐이기 때문이다. 그래서 각 멤버에만 있던 필드가 빠지고 공통 필드만 남는다. `T extends unknown ? Omit<T, K> : never`처럼 분배 조건부 타입으로 감싸면 멤버마다 따로 `Omit`을 적용해 유니온 구조가 유지된다.

### 복잡한 타입이 문제가 되는 순간은 언제이고 어떻게 다루나요?

재귀 타입이 깊이 제한에 걸리면 TS2589(excessively deep)가 나고, 유니온이 너무 커지면 TS2590이 난다. 더 흔한 증상은 에디터가 느려지고 hover와 에러 메시지를 읽을 수 없게 되는 것이다. `tsc --extendedDiagnostics`로 인스턴스화 수와 검사 시간을, `--generateTrace`로 느린 타입의 위치를 찾고, 결과를 이름 있는 interface로 적어 두거나 타입 계산을 단순화해서 푼다.
