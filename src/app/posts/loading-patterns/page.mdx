설정 화면에서 저장 버튼을 눌렀다. 아무 변화가 없다. 한 번 더 눌렀더니 요청이 두 번 나갔고, 1초쯤 뒤에 "저장되었습니다" 토스트가 두 개 겹쳐 떴다. 서버는 멀쩡했다. 화면이 "지금 듣고 있다"는 말을 하지 않았을 뿐이다.

이걸 고치려고 "로딩 좀 넣어 주세요"라고 부탁하면 대개 화면 한가운데 스피너가 생긴다. 버튼 하나 눌렀는데 페이지 전체가 가려진다. 로딩 표시에는 이름이 붙은 패턴이 여럿 있고, 상황마다 맞는 게 따로 있다. 이름을 알면 "저장 버튼을 loading button으로 바꿔 주세요"처럼 짧고 정확하게 부탁할 수 있다. 사람에게든 AI에게든 마찬가지다.

## 기다리는 시간이 표시를 정한다

UX 쪽에서 오래 쓰여 온 기준이 있다. Jakob Nielsen이 1993년 글에서 정리한 응답 시간의 세 경계다(더 앞선 HCI 연구를 정리한 것이라 정확한 실험값이라기보다 어림 기준으로 쓴다).

- 약 0.1초 안이면 사용자는 결과가 즉시 나왔다고 느낀다. 아무것도 보여 줄 필요가 없다.
- 약 1초 안이면 지연은 느끼지만 생각의 흐름은 끊기지 않는다. 눈에 띄는 로딩 표시가 없어도 되지만, 누른 버튼이 눌렸다는 정도는 알려 준다.
- 약 10초를 넘기면 사용자는 딴 데로 주의를 돌린다. 얼마나 남았는지와 취소 방법을 보여 줘야 한다.

NN/g는 이어서 2~10초쯤은 도는 애니메이션(스피너)으로, 10초가 넘으면 진행률을 보여 주는 쪽을 권한다. 숫자는 경계가 칼같이 정해진 게 아니다. 방향만 가져가면 된다. 짧은 기다림에 요란한 표시를 붙이면 오히려 느려 보이고, 긴 기다림에 스피너 하나만 두면 멈췄는지 도는지 알 수 없다.

## 얼마나 남았는지 아는가

진행 표시는 두 종류로 나뉜다. 끝을 모르는 비결정형(indeterminate)과 남은 양을 아는 결정형(determinate)이다. 스피너는 앞쪽, 프로그레스 바와 링, 스테퍼는 뒤쪽이다.

<LoadingDemo
  caption="스피너는 끝을 모를 때, 나머지 셋은 남은 양을 알 때 쓴다."
  patterns={["spinner", "progress-bar", "progress-ring", "stepper"]}
/>

파일 업로드처럼 전체 크기와 보낸 양을 아는 작업은 프로그레스 바를 쓴다. 좁은 자리(아바타 위, 다운로드 아이콘 안)에는 같은 정보를 원으로 그린 프로그레스 링을 쓴다. 회원 가입이나 배포처럼 몇 단계로 나뉜 작업은 바이트가 아니라 단계를 세는 스테퍼가 낫다. "3단계 중 2단계"는 퍼센트보다 이해하기 쉽다.

업로드 진행률은 아직 `fetch`로 얻기 어렵다. 업로드 쪽 진행 이벤트가 표준에 없어서, 실무에서는 `XMLHttpRequest`의 `upload.onprogress`를 쓴다.

```tsx
"use client";
import { useState } from "react";

function uploadFile(file: File, onProgress: (ratio: number) => void) {
  return new Promise<void>((resolve, reject) => {
    const xhr = new XMLHttpRequest();
    // 보낸 바이트 / 전체 바이트. 전체 크기를 모르면 lengthComputable이 false다
    xhr.upload.onprogress = (e) => {
      if (e.lengthComputable) onProgress(e.loaded / e.total);
    };
    xhr.onload = () => (xhr.status < 400 ? resolve() : reject(new Error(String(xhr.status))));
    xhr.onerror = () => reject(new Error("network"));
    xhr.open("POST", "/api/upload");
    xhr.send(file);
  });
}

export function UploadProgress({ file }: { file: File }) {
  const [percent, setPercent] = useState(0);

  return (
    <>
      <button onClick={() => uploadFile(file, (r) => setPercent(Math.round(r * 100)))}>올리기</button>
      {/* 스크린 리더가 "사진 업로드, 42%"처럼 읽는다 */}
      <div role="progressbar" aria-label="사진 업로드" aria-valuemin={0} aria-valuemax={100} aria-valuenow={percent}>
        <div style={{ width: `${percent}%` }} />
      </div>
    </>
  );
}
```

`role="progressbar"`에 `aria-valuenow`를 넣으면 결정형, 빼면 비결정형으로 읽힌다. 네이티브 `<progress>`도 같다. `value`를 주면 결정형, 빼면 비결정형이다.

하지 말아야 할 건 가짜 진행률이다. 실제 진행과 상관없이 타이머로 90%까지 채우고 거기서 멈추는 바는 처음엔 빨라 보이지만, 99%에서 30초를 서 있으면 사용자는 고장 났다고 판단한다. 진짜 수치가 없다면 차라리 스피너와 "보통 20초쯤 걸린다" 같은 문장이 정직하다. 단계를 안다면 스테퍼로 바꾼다.

## 무엇이 올지 모양을 아는가

글 목록, 프로필 카드, 상품 그리드처럼 내용은 몰라도 모양은 아는 화면이 있다. 이럴 땐 회색 블록으로 자리를 먼저 그려 두는 스켈레톤 UI를 쓴다.

<LoadingDemo
  caption="스켈레톤은 자리를 먼저 잡아 두고, 내용이 오면 그 자리에 채운다."
  patterns={["skeleton"]}
/>

스켈레톤의 이득은 두 가지다. 사용자는 무엇이 올지 미리 보고 눈을 옮겨 둔다. 그리고 내용이 들어와도 레이아웃이 밀리지 않는다. 스피너 하나만 두다가 내용이 쏟아지면 아래 요소들이 한꺼번에 내려가는데, 이게 [Core Web Vitals](/posts/core-web-vitals)의 CLS(누적 레이아웃 이동) 점수를 깎는다.

React에서는 `Suspense`의 `fallback`이 스켈레톤을 둘 자리다.

```tsx
import { Suspense } from "react";

export function PostsPage() {
  return (
    <Suspense fallback={<PostListSkeleton rows={5} />}>
      <PostList />
    </Suspense>
  );
}

function PostListSkeleton({ rows }: { rows: number }) {
  return (
    // 이 영역이 아직 채워지는 중이라고 알린다
    <ul aria-busy="true" aria-label="글 목록 불러오는 중">
      {Array.from({ length: rows }, (_, i) => (
        // 실제 PostItem과 같은 높이·여백을 써야 내용이 와도 밀리지 않는다
        <li key={i} className="post-item skeleton">
          <span className="skeleton-line" style={{ width: "40%" }} />
          <span className="skeleton-line" style={{ width: "90%" }} />
        </li>
      ))}
    </ul>
  );
}
```

스켈레톤은 실제 화면과 닮아야 의미가 있다. 세 줄짜리 스켈레톤을 보여 주고 카드 열 개를 띄우거나, 높이가 다르면 오히려 레이아웃 이동을 두 번 겪는다. 공용 회색 블록 하나를 모든 화면에 돌려쓰면 이렇게 된다. 반대로 모양을 전혀 모르는 화면(검색 결과 유형이 매번 다르다든가)에는 억지로 스켈레톤을 만들기보다 작은 스피너가 낫다.

서버 렌더링에서 스켈레톤을 먼저 흘려보내고 내용을 나중에 채우는 이야기는 [Streaming SSR과 Suspense](/posts/streaming-ssr-suspense)에, 렌더링 방식별로 처음 보이는 화면이 어떻게 다른지는 [렌더링 전략](/posts/rendering-strategies)에 정리했다.

## 스피너가 깜빡이면 더 느려 보인다

빠른 API에 스피너를 붙이면 묘한 일이 생긴다. 응답이 150ms 만에 오면 스피너는 한 프레임 번쩍하고 사라진다. 사용자는 뭔가 깜빡였다는 것만 느끼고, 표시가 없을 때보다 느리다고 느낀다.

흔히 쓰는 처방은 두 개를 같이 거는 것이다. 300ms쯤은 기다렸다가 그때도 안 끝났으면 스피너를 띄운다. 일단 띄웠으면 최소 500ms쯤은 보여 준다. 300ms와 500ms는 정해진 표준이 아니라 많이 쓰는 값이니, 화면에 맞게 조절한다.

아래 함수는 로딩에 걸린 시간을 받아, 스피너를 언제 띄우고 언제 내릴지 돌려준다. 안 띄우면 `null`이다.

<CodePlayground
  caption="스피너를 늦게 띄우고, 띄웠으면 최소 시간은 보여 주기"
  functionName="spinnerWindow"
  initialCode={`function spinnerWindow(loadMs, delayMs, minShowMs) {
  // 1. delayMs 안에 끝났으면 스피너를 띄우지 않는다 (null)
  // 2. 아니면 delayMs에 띄운다
  // 3. 내리는 시각은 로딩이 끝난 시각과 (띄운 시각 + minShowMs) 중 늦은 쪽
  // 반환: [띄우는 시각, 내리는 시각] 또는 null
  return null;
}`}
  solution={`function spinnerWindow(loadMs, delayMs, minShowMs) {
  if (loadMs <= delayMs) return null;
  return [delayMs, Math.max(loadMs, delayMs + minShowMs)];
}`}

450ms에 끝난 요청을 보자. 스피너는 300ms에 떴다가 원래라면 450ms에 사라져야 하지만, 150ms짜리 깜빡임이 되지 않도록 800ms까지 남는다. 응답을 350ms 늦게 보여 주는 셈이라 손해 같지만, 사람 눈에는 이쪽이 안정적으로 보인다. 컴포넌트에서는 이렇게 쓴다.

```tsx
import { useEffect, useRef, useState } from "react";

export function useDelayedSpinner(loading: boolean, delayMs = 300, minShowMs = 500) {
  const [visible, setVisible] = useState(false);
  const shownAt = useRef(0);

  useEffect(() => {
    if (loading) {
      if (visible) return; // 이미 떠 있으면 그대로 둔다
      const t = setTimeout(() => {
        shownAt.current = Date.now();
        setVisible(true);
      }, delayMs);
      return () => clearTimeout(t); // delayMs 전에 끝나면 아예 안 띄운다
    }
    if (!visible) return;
    const left = minShowMs - (Date.now() - shownAt.current);
    const t = setTimeout(() => setVisible(false), Math.max(0, left));
    return () => clearTimeout(t);
  }, [loading, visible, delayMs, minShowMs]);

  return visible;
}
```

## 버튼을 누른 사람에게 먼저 답한다

처음 장면으로 돌아가자. 저장 버튼은 사용자가 직접 누른 것이니, 대답도 그 버튼이 해야 한다. 페이지 전체를 덮는 스피너는 상관없는 영역까지 막아 버린다. 누른 자리에서 "저장 → 도는 중 → 저장됨"으로 바뀌는 loading button이 맞다.

<LoadingDemo

React 19에서는 `useActionState`가 진행 중 여부를 같이 돌려준다.

```tsx
"use client";
import { useActionState } from "react";

type SaveState = { status: "idle" | "saved" | "error" };

export function SettingsForm() {
  const [state, save, isPending] = useActionState<SaveState, FormData>(async (_prev, formData) => {
    const res = await fetch("/api/settings", { method: "POST", body: formData });
    return { status: res.ok ? "saved" : "error" };
  }, { status: "idle" });

  return (
    <form action={save}>
      <input name="nickname" />
      {/* 진행 중에는 다시 못 누르게 해서 중복 요청을 막는다. 라벨이 바뀌어도 폭이 흔들리지 않게 min-width를 준다 */}
      <button type="submit" disabled={isPending} style={{ minWidth: "6rem" }}>
        {isPending ? "저장 중…" : state.status === "saved" ? "저장됨" : "저장"}
      </button>
      <p role="status">{state.status === "error" ? "저장하지 못했다. 다시 눌러 보자." : ""}</p>
    </form>
  );
}
```

  ]}
/>

React 19의 `useOptimistic`은 되돌리기를 공짜로 준다. 낙관적 값은 액션이 진행되는 동안에만 보이고, 액션이 끝나면 원래 상태로 돌아간다. 성공했을 때 원래 상태를 서버 값으로 바꿔 두면 그 값이 남고, 실패해서 안 바꾸면 이전 값이 다시 보인다.

```tsx
"use client";
import { startTransition, useOptimistic, useState } from "react";

type Like = { liked: boolean; count: number };

export function LikeButton({ postId, initial }: { postId: string; initial: Like }) {
  const [like, setLike] = useState(initial); // 서버가 확인한 값
  const [shown, setShown] = useOptimistic(like); // 화면에 보이는 값
  const [error, setError] = useState("");

  function toggle() {
    const next = { liked: !shown.liked, count: shown.count + (shown.liked ? -1 : 1) };
    startTransition(async () => {
      setShown(next); // 지금 바로 화면을 바꾼다
      try {
        const res = await fetch(`/api/posts/${postId}/like`, { method: "POST", body: JSON.stringify(next) });
        if (!res.ok) throw new Error(String(res.status));
        const saved: Like = await res.json();
        startTransition(() => setLike(saved)); // await 뒤의 갱신도 transition으로 감싼다
      } catch {
        setError("좋아요를 저장하지 못했다."); // like는 그대로라 화면이 이전 값으로 돌아간다
      }
    });
  }

  return (
    <>
      <button aria-pressed={shown.liked} onClick={toggle}>♥ {shown.count}</button>
      <p role="status">{error}</p>
    </>
  );
}
```

결제, 송금, 삭제처럼 실패하면 곤란하거나 되돌리기 어려운 동작에는 쓰지 않는다. 화면이 "결제 완료"를 보여 줬다가 "사실 실패"로 바꾸면 신뢰를 잃는다. 여기에는 loading button이 맞다. TanStack Query로 캐시를 직접 고치고 롤백하는 방식은 [클라이언트 데이터 캐시](/posts/client-data-cache)에서 다뤘다.

모든 응답이 한 덩어리로 오지는 않는다. 끝까지 기다렸다 한 번에 보여 주는 대신, 오는 대로 보여 주는 패턴들이다.

<LoadingDemo
  caption="받는 대로 보여 주거나, 필요할 때 받는 패턴"
  patterns={["streaming-text", "infinite-scroll", "lazy-loading", "blur-up"]}
/>

### 글자가 오는 대로 쓰기

LLM 답변은 전부 만들어지기까지 수십 초가 걸리기도 한다. 그동안 스피너만 돌리면 10초 경계를 쉽게 넘는다. 그래서 서버가 토큰을 만드는 대로 보내고 화면은 받는 대로 이어 쓰는 streaming text를 쓴다. 첫 글자가 1초 안에 보이면 전체 시간이 같아도 훨씬 빠르게 느껴진다. 전송은 보통 SSE나 `fetch`의 `ReadableStream`이고, 차이는 [실시간 통신](/posts/realtime-communication)에서 비교했다.

접근성에서 실수하기 쉬운 곳이다. 답변 영역 전체에 `aria-live="polite"`를 걸면 스크린 리더가 토큰이 붙을 때마다 읽으려 들어서 듣기 힘들어진다. 스트리밍 중에는 영역에 `aria-busy="true"`를 두고, 별도의 상태 영역에서 "답변 작성 중", "답변 완료" 정도만 알린 뒤 다 받으면 읽게 하는 편이 낫다. 다만 `aria-busy`를 존중하는 정도는 스크린 리더마다 다르니 실제 기기로 확인한다.

### 끝에 닿으면 더 붙이기

infinite scroll(무한 스크롤)은 목록 끝에 보이지 않는 감시용 요소를 두고, 그 요소가 화면에 가까워지면 다음 페이지를 받아 붙인다. 스크롤 이벤트를 매번 계산하지 않고 `IntersectionObserver`에 맡긴다.

```tsx
import { useEffect, useRef } from "react";

export function useLoadMore(onLoadMore: () => void, hasMore: boolean) {
  const sentinel = useRef<HTMLDivElement>(null);

  useEffect(() => {
    const el = sentinel.current;
    if (!el || !hasMore) return;
    const io = new IntersectionObserver(
      ([entry]) => entry.isIntersecting && onLoadMore(),
      { rootMargin: "400px 0px" }, // 끝에 닿기 400px 전에 미리 받는다
    );
    io.observe(el);
    return () => io.disconnect();
  }, [onLoadMore, hasMore]);

  return sentinel; // 목록 맨 끝의 <div ref={sentinel} />에 붙인다
}
```

피드나 사진처럼 훑어보는 화면에는 잘 맞지만 문제도 분명하다. 푸터에 영영 닿지 못한다. 글을 열었다가 뒤로 오면 스크롤 위치와 불러온 페이지를 잃기 쉽다. 키보드 사용자는 목록 뒤의 링크로 가려면 계속 늘어나는 항목을 다 지나야 한다. "50번째쯤 있던 그 상품"으로 돌아갈 주소도 없다. 검색 결과나 관리 화면처럼 특정 위치를 다시 찾아야 하는 곳에는 페이지 번호나 "더 보기" 버튼이 낫다. 무한 스크롤을 쓰더라도 "더 보기" 버튼을 대안으로 함께 두면 키보드와 보조 기술 사용자가 덜 막힌다. 서버 쪽에서 offset 대신 커서로 다음 페이지를 주는 이유는 [REST API 설계](/posts/rest-api-design)에 있다.

### 보일 때 받기, 흐린 것부터 보여 주기

lazy loading(지연 로딩)은 화면 밖 이미지를 처음부터 받지 않고, 스크롤이 가까워졌을 때 받는다. 지금은 HTML 속성 하나면 된다.

```tsx
export function Thumbnail({ src, alt }: { src: string; alt: string }) {
  // width·height를 적어야 이미지가 오기 전에도 자리가 잡혀 레이아웃이 밀리지 않는다
  return <img src={src} alt={alt} width={320} height={180} loading="lazy" decoding="async" />;
}
```

자주 하는 실수는 첫 화면의 큰 이미지에까지 `loading="lazy"`를 붙이는 것이다. 그 이미지는 대개 LCP(가장 큰 콘텐츠가 그려지는 시점) 대상이라, 늦게 받으면 LCP가 그대로 늦어진다. Lighthouse도 이걸 따로 경고한다. 첫 화면 이미지는 즉시 받고, 아래쪽만 지연시킨다. 이미지가 아닌 컴포넌트를 필요할 때 받는 건 [코드 스플리팅](/posts/code-splitting)의 영역이다.

blur-up은 진짜 이미지가 오기 전에 아주 작은 흐린 미리보기를 먼저 보여 주는 방식이다. 미리보기는 20px 안팎으로 줄인 이미지를 base64로 HTML에 박아 두는 LQIP(Low Quality Image Placeholder)나, 이미지를 20~30자쯤의 문자열로 줄인 BlurHash로 만든다. 사용자는 회색 상자 대신 대략의 색과 구도를 먼저 본다. Next.js의 `next/image`는 `placeholder="blur"`로 이걸 지원한다. 정적으로 import한 이미지는 빌드 때 미리보기를 자동으로 만들고, 원격 이미지는 `blurDataURL`을 직접 넘겨야 한다.

```tsx
import Image from "next/image";
import hero from "./hero.jpg";

export function Hero() {
  // 첫 화면 이미지라 priority로 즉시 받고, 오는 동안 흐린 미리보기를 깐다
  return <Image src={hero} alt="산 위의 일출" placeholder="blur" priority />;
}
```

## 손가락으로 당겨서 새로고침

모바일 피드에서 맨 위를 아래로 당기면 새 글을 받는 pull to refresh는 손에 익은 제스처다. 맨 위에 있을 때만, 일정 거리 이상 당겼을 때만 동작하게 하고, 당기는 동안 아이콘이 따라 돌며 "놓으면 새로고침"을 알려 준다.

<LoadingDemo
  caption="일정 거리 이상 당겼다 놓으면 새로 받는다."
  patterns={["pull-to-refresh"]}
/>

웹에서 직접 구현하면 브라우저의 기본 당겨서 새로고침과 겹친다. 크롬 안드로이드에서는 당기는 순간 페이지 전체가 새로고침된다. CSS 한 줄로 기본 동작을 막고 내 구현만 남긴다.

```css
/* 스크롤이 끝에 닿았을 때 바깥(페이지)으로 넘기지 않는다. 브라우저 기본 당겨서 새로고침도 꺼진다 */
.feed {
  overscroll-behavior-y: contain;
}
```

제스처는 숨겨진 기능이라 모르는 사람도 있다. 마우스와 키보드 사용자는 당길 수가 없다. 새로고침 버튼을 따로 두거나, 포커스가 돌아올 때 알아서 다시 받는 쪽을 함께 쓴다.

## 모든 로딩 표시에 같이 챙길 것

로딩 표시는 눈으로만 보이면 반쪽이다. 스크린 리더 사용자는 회색 블록도, 도는 원도 보지 못한다. 앞에서 패턴마다 짚은 걸 모으면 이렇다.

- 채워지는 중인 영역에는 `aria-busy="true"`를 두고, 다 채워지면 지운다.
- 진행률이 있으면 `role="progressbar"`와 `aria-valuenow`, 없으면 `aria-valuenow`를 뺀다.
- "저장됨", "불러오지 못했다" 같은 결과는 `role="status"`(polite 라이브 영역)로 알린다. 토큰마다 읽히게 하지는 않는다.
- 움직임 줄이기 설정을 켠 사용자에게는 반짝임과 회전을 멈춘다.

```css
@media (prefers-reduced-motion: reduce) {
  .skeleton,
  .spinner {
    animation: none; /* 움직임은 멈추고, 회색 블록과 "불러오는 중" 문구는 남긴다 */
  }
}
```

마지막으로 로딩에는 끝이 있어야 한다. 실패하면 스피너를 그대로 두지 말고 에러와 다시 시도 버튼으로 바꾼다. 요청에 타임아웃이 없으면 스피너는 영원히 돈다. 현장에서 "화면이 멈췄다"는 문의의 상당수는 실제로 멈춘 게 아니라 끝나지 않는 로딩 표시다.

### 디자인 시스템의 로딩 표시 컴포넌트로 만들면

이 규칙을 화면마다 지키게 하려면 디자인 시스템에 `Spinner`(또는 `LoadingIndicator`) 하나를 두고 기본값에 넣어 버리는 게 가장 확실하다. props는 이 정도면 된다.

```tsx
type SpinnerProps = {
  size?: "sm" | "md" | "lg";   // 크기 토큰에 묶는다. 16·24·40px처럼 임의 px를 받지 않는다
  label?: string;              // 기본 "불러오는 중". 화면에는 안 보이고 스크린 리더만 읽는다
  delayMs?: number;            // 기본 300. 이 시간 안에 사라지면 아예 그리지 않는다
  minShowMs?: number;          // 기본 500. 한 번 떴으면 이만큼은 남는다
  announce?: boolean;          // 기본 true. role="status"로 label을 알린다
};
```

`delayMs`와 `minShowMs`는 앞의 `useDelayedSpinner`를 컴포넌트 안에 넣은 것이다. 기본값이 있으니 쓰는 쪽은 `loading && <Spinner />`만 써도 깜빡임이 생기지 않는다. 바깥은 기본으로 `role="status"`이고 회전하는 그림은 `aria-hidden="true"`로 숨긴다. 그래야 그림이 아니라 "불러오는 중"이라는 이름이 읽힌다.

`announce`를 끌 수 있게 두는 이유가 있다. 목록 행마다 스피너가 하나씩 뜨면 라이브 영역이 열 개가 되어 같은 말을 열 번 읽는다. 이럴 때는 목록 바깥 한 곳에만 상태를 두고 행의 스피너는 알리지 않게 한다. 버튼 안의 로딩 표시도 같은 이유로 알리지 않는 쪽이 기본이고, 버튼 쪽의 약속(너비 유지, 이름 유지)은 [버튼 컴포넌트 설계 글](/posts/core-component-api-design#로딩-중에도-너비와-이름을-지킨다)에 있다. 색은 `currentColor`를 써서 버튼 위, 어두운 배경 위 어디에 놓여도 주변 글자색을 따르게 한다.

## 이름을 알면 부탁이 짧아진다

처음 이야기로 돌아가면, 저장 버튼 문제는 "로딩 넣어 주세요"가 아니라 "저장 버튼을 loading button으로, 진행 중엔 비활성화"라고 말하면 끝난다. 목록 화면은 "spinner 말고 실제 행과 같은 높이의 skeleton", 좋아요는 "optimistic UI, 실패하면 롤백과 토스트"다. 디자이너에게 말할 때도, AI에게 코드를 부탁할 때도 패턴 이름이 곧 명세다. 고르는 기준도 짧다. 짧은 기다림은 드러내지 않고, 끝을 알면 진행률을, 모양을 알면 스켈레톤을, 사용자가 시작했으면 그 자리에서 대답한다. 움직임 쪽 패턴의 이름은 [애니메이션 패턴](/posts/animation-patterns)에 같은 방식으로 모았다.

## 면접에서 나올 만한 질문

### 스켈레톤과 스피너는 언제 각각 쓰나요?

결과의 모양을 미리 알면 스켈레톤, 모르면 스피너다. 스켈레톤은 무엇이 올지 미리 보여 주고 자리를 잡아 두어서 내용이 와도 레이아웃이 밀리지 않으니 CLS에도 유리하다. 대신 실제 화면과 높이·구조가 같아야 하고, 다르면 이동이 두 번 생긴다. 모양을 모르는 결과나 버튼 하나 같은 작은 영역에는 스피너가 맞다.

### 응답이 빠른데 스피너가 깜빡여서 거슬립니다. 어떻게 하나요?

스피너를 300ms쯤 늦게 띄우고, 한 번 띄웠으면 최소 500ms쯤 유지한다. 대부분의 빠른 응답은 아무 표시 없이 끝나고, 느린 응답에서만 스피너가 안정적으로 보인다. 짧은 깜빡임은 표시가 없을 때보다 오히려 느리게 느껴지기 때문이다. 숫자는 표준이 아니라 많이 쓰는 값이라 화면에 맞게 조절한다.

### 결정형과 비결정형 진행 표시는 어떻게 고르나요? 가짜 진행률은 왜 안 되나요?

남은 양을 측정할 수 있으면 결정형(프로그레스 바, 링, 스테퍼), 없으면 비결정형(스피너)이다. 대략 10초를 넘기는 작업은 진행률이 있어야 사용자가 기다릴지 판단할 수 있다. 타이머로 채우는 가짜 진행률은 끝에서 멈춰 버려 고장처럼 보이고 신뢰를 잃는다. 진짜 수치가 없으면 단계를 세는 스테퍼나 예상 시간 문구가 낫다.

### 낙관적 업데이트는 어디에 쓰고, 실패하면 어떻게 하나요?

좋아요, 북마크처럼 거의 성공하고 되돌리기 쉬운 동작에 쓴다. 화면을 먼저 바꾸고 이전 값을 기억해 두었다가, 서버가 실패를 돌려주면 그 값으로 되돌리고 사용자에게 알린다. React 19의 `useOptimistic`은 액션이 끝나면 확정된 상태로 돌아가서 롤백을 자연스럽게 처리한다. 결제·송금·삭제처럼 실패가 치명적인 동작에는 쓰지 않고 loading button으로 결과를 기다린다.

### 무한 스크롤 대신 페이지네이션을 고르는 경우는요?

특정 위치로 다시 돌아와야 하는 화면이다. 무한 스크롤은 푸터에 닿지 못하고, 뒤로 가기에서 위치를 잃기 쉽고, 키보드 사용자가 뒤쪽 요소에 가기 어렵고, 위치를 주소로 공유할 수 없다. 그래서 검색 결과나 관리 화면에는 페이지 번호나 "더 보기" 버튼이 낫고, 훑어보는 피드에만 무한 스크롤을 쓴다. 구현은 스크롤 이벤트 대신 `IntersectionObserver`로 끝 요소를 감시한다.

### 이미지 지연 로딩에서 주의할 점은요?

첫 화면의 큰 이미지에는 `loading="lazy"`를 붙이지 않는다. 그 이미지는 보통 LCP 대상이라 늦게 받으면 LCP가 그대로 늦어진다. 지연 로딩하는 이미지에는 `width`·`height`를 적어 자리를 잡아야 레이아웃 이동이 없다. 빈 자리가 어색하면 LQIP나 BlurHash로 흐린 미리보기를 먼저 깔고, Next.js에서는 `placeholder="blur"`를 쓴다.
