운영 클러스터에서 오래된 인덱스를 정리하려고 `DELETE /orders-2026.*`를 쳤다. 지우려던 건 `orders-2026.01`부터 `.06`까지였는데, 와일드카드가 이번 달 인덱스까지 모두 지웠다. 누군가 "레플리카가 1이니까 괜찮지 않나"라고 했다. 괜찮지 않았다. 레플리카는 프라이머리와 똑같은 상태를 실시간으로 따라 하는 복사본이라, 인덱스 삭제도 그대로 따라 했다. 노드가 죽는 장애에는 레플리카가 답이지만, 사람의 실수나 잘못된 배포, 랜섬웨어 같은 "데이터가 잘못 바뀌는 사고"에는 답이 아니다. 이 구분은 DB에서도 같아서 [백업 전략](/posts/backup-strategy) 글에서 자세히 다뤘다.

이 글은 Elasticsearch에서 그 사고를 대비하는 장치를 따라간다. 클러스터 밖에 스냅숏 저장소를 두고, 스냅숏이 세그먼트 파일 단위로 증분 복사되는 원리, SLM으로 주기와 보관을 정책으로 만드는 법, 인덱스 하나만 다른 이름으로 되살리는 법과 버전 호환 규칙을 본다. 이어서 다른 리전에 읽기 전용 사본을 두는 CCR, 오래된 데이터를 스냅숏에 둔 채 검색하는 searchable snapshot과 데이터 계층까지 간다. 마지막에 RPO와 RTO를 숫자로 정해 어느 조합을 쓸지 고른다. API는 Elasticsearch 8.x~9.x 공식 문서 기준이고, 응답은 문서에 나오는 형식에서 필요한 필드만 남겨 보인다. OpenSearch는 스냅숏과 복원 API가 거의 같지만 SLM과 CCR은 다른 플러그인으로 제공한다.

## 스냅숏은 세그먼트 파일을 복사한다

Elasticsearch의 샤드는 결국 Lucene 세그먼트 파일 묶음이다([역색인 글](/posts/elasticsearch-inverted-index)의 세그먼트 참고). 세그먼트는 한 번 쓰면 고치지 않는다. 새 문서는 새 세그먼트로, 수정과 삭제는 새 세그먼트와 삭제 표시로 기록되고, 병합이 작은 세그먼트 여럿을 큰 것 하나로 바꾼다.

스냅숏은 이 성질을 그대로 이용한다. 샤드마다 지금 있는 세그먼트 파일 목록을 보고, 저장소에 아직 없는 파일만 올린다. 이미 올라간 파일은 다음 스냅숏이 이름만 가리킨다. 그래서 매시간 떠도 두 번째부터는 그 사이 새로 생긴 세그먼트만큼만 올라간다. DB 백업의 "전체 + 증분"과 비슷해 보이지만 차이가 있다. 스냅숏 하나하나가 그 자체로 완전한 목록이라, 중간 스냅숏을 지워도 다른 스냅숏을 복원하는 데 지장이 없다. 저장소는 어느 스냅숏도 가리키지 않게 된 파일만 지운다.

다만 병합이 일어나면 이야기가 달라진다. 작은 세그먼트 셋이 큰 세그먼트 하나로 합쳐지면 그 큰 파일은 저장소에 없는 새 파일이라 통째로 올라간다. 데이터는 거의 같은데 업로드 양은 크다. 쓰기와 병합이 잦은 인덱스는 스냅숏마다 올라가는 양이 생각보다 많고, `_forcemerge`를 돌린 직후의 스냅숏은 거의 인덱스 전체를 다시 올린다.

스냅숏마다 그 시점 샤드에 있던 세그먼트 파일 이름이 주어질 때, 스냅숏마다 새로 올라가는 파일 수를 세어 보자.

스냅숏은 색인과 검색을 멈추지 않는다. 각 샤드의 스냅숏이 시작되는 순간의 세그먼트 목록을 복사하므로, 그 뒤에 들어온 문서는 다음 스냅숏에 들어간다. 샤드마다 시작 시점이 조금씩 달라서 클러스터 전체가 한 순간에 멈춘 사진은 아니라는 점도 알아 둔다.

## 클러스터 밖에 저장소를 둔다

스냅숏은 저장소(repository)에 쌓인다. 운영에서는 S3, GCS, Azure Blob 같은 객체 저장소를 쓰고, 실습이나 사내망이라면 모든 노드가 같은 경로로 마운트한 공유 파일 시스템(`fs`)을 쓴다. `fs`는 노드 설정 `path.repo`에 그 경로를 미리 적어 둬야 등록된다.

```http
PUT _snapshot/s3-backup
{
  "type": "s3",
  "settings": {
    "bucket": "acme-es-snapshots",
    "base_path": "prod-search",
    "client": "default"
  }
}

POST _snapshot/s3-backup/_verify
```

`_verify`는 모든 노드가 그 저장소에 쓰고 읽을 수 있는지 확인한다. 한 노드만 권한이 없으면 그 노드에 있는 샤드의 스냅숏만 실패하는데, 이걸 등록할 때 잡는다. 접근 키는 요청 본문이 아니라 각 노드의 키스토어(`elasticsearch-keystore`)에 넣는다.

저장소에서 지켜야 할 규칙이 몇 가지 있다.

- 저장소 파일을 사람이 직접 고치거나 지우지 않는다. 버킷의 수명 주기 규칙으로 오래된 객체를 지우면 아직 다른 스냅숏이 가리키는 세그먼트까지 사라져 저장소가 깨진다. 지우는 건 SLM의 보관 규칙이나 스냅숏 삭제 API에 맡긴다.
- 같은 저장소에 쓰는 클러스터는 하나여야 한다. 복원 연습용 클러스터나 다른 리전 클러스터가 같은 버킷을 등록할 때는 `"readonly": true`로 등록한다. 두 클러스터가 동시에 쓰면 저장소 메타데이터가 꼬인다.
- 버킷은 운영 클러스터와 다른 계정이나 리전, 적어도 다른 권한 아래에 둔다. 운영 클러스터의 자격 증명을 가진 사람(또는 공격자)이 스냅숏까지 지울 수 있다면 랜섬웨어 앞에서 백업이 아니다. 객체 잠금(S3 Object Lock 같은)을 쓸 때는 Elasticsearch가 스냅숏 삭제 때 객체를 지워야 한다는 점과 충돌하지 않는지 먼저 확인한다.
- 노드의 데이터 디렉터리를 파일 복사로 백업하지 않는다. 쓰고 있는 Lucene 파일을 복사하면 일관되지 않은 사본이 되고, 복원이 된다는 보장이 없다. 공식 문서도 스냅숏만을 지원하는 백업 방법으로 둔다.

## 스냅숏을 뜨고 확인하기

손으로 하나 떠 보자. 위험한 작업(매핑 변경, 대량 `_delete_by_query`, [대량 재색인](/posts/elasticsearch-bulk-indexing)) 직전에 이렇게 하나 떠 두는 습관이 가장 싸고 효과가 크다.

```http
PUT _snapshot/s3-backup/before-orders-cleanup?wait_for_completion=true
{
  "indices": "orders-*",
  "include_global_state": false
}

GET _snapshot/s3-backup/before-orders-cleanup

GET _snapshot/s3-backup/_current
```

`include_global_state`를 `true`로 두면 인덱스 템플릿, 영구 클러스터 설정, ILM 정책 같은 클러스터 전체 상태도 함께 담긴다. 보안 인덱스처럼 기능별 시스템 데이터는 `feature_states`로 따로 고른다. 인덱스만 되살릴 일이 대부분이라 수동 스냅숏은 `false`로 두고, 클러스터 전체를 잃는 경우를 대비하는 정기 스냅숏에는 전체 상태를 넣는 식으로 나눈다.

결과에서 봐야 할 건 `state`와 샤드 수다. 형식은 이렇다.

```json
{
  "snapshots": [
    {
      "snapshot": "before-orders-cleanup",
      "indices": ["orders-2026.01", "orders-2026.02", "orders-2026.10"],
      "state": "SUCCESS",
      "shards": { "total": 6, "failed": 0, "successful": 6 }
    }
  ]
}
```

`state`가 `PARTIAL`이면 일부 샤드를 담지 못한 것이다. 그 샤드가 있던 노드가 저장소에 쓰지 못했거나 그 시점에 샤드가 배정되지 않은 경우가 흔하다. "스냅숏 작업은 돌았다"와 "모든 샤드를 담았다"는 다르니, 모니터링은 `PARTIAL`과 `FAILED`를 둘 다 경보로 잡는다.

## SLM: 주기와 보관을 정책으로

매일 사람이 스냅숏을 뜰 수는 없으니 SLM(Snapshot Lifecycle Management)에 맡긴다. 언제 뜨고, 무엇을 담고, 얼마나 남길지를 정책 하나로 쓴다.

```http
PUT _slm/policy/nightly
{
  "schedule": "0 30 1 * * ?",
  "name": "<nightly-{now/d}>",
  "repository": "s3-backup",
  "config": {
    "indices": ["orders-*", "products"],
    "include_global_state": true
  },
  "retention": {
    "expire_after": "30d",
    "min_count": 5,
    "max_count": 50
  }
}

POST _slm/policy/nightly/_execute

GET _slm/stats
```

`schedule`은 초부터 시작하는 크론 식이라 위 값은 매일 01:30(UTC)이다. 이름의 `now/d`는 날짜 수식이라 스냅숏마다 날짜가 붙고, 실제로는 뒤에 겹치지 않는 접미사가 더 붙는다. `retention`은 30일이 지난 것을 지우되 최소 5개는 남기고, 개수가 50개를 넘으면 오래된 것부터 지운다. 스냅숏이 몇 번 연속으로 실패해도 `min_count` 덕분에 성공한 옛 스냅숏이 보관 규칙에 지워지지 않는다.

정책을 만들면 `_execute`로 바로 한 번 돌려 보고, 성공했는지 확인한다. 하룻밤 기다렸다가 실패를 발견하는 것보다 낫다. 이후 `GET _slm/stats`의 실패 수와 `GET _slm/policy/nightly`의 `last_failure`를 모니터링에 연결한다. SLM이 조용히 실패하는 가장 흔한 원인은 저장소 권한 만료(키 교체 후 키스토어를 안 고친 경우)다.

주기는 RPO에서 나온다. 매일 1회면 최악의 경우 하루치를 잃는다. 30분마다 뜨는 정책도 흔한데, 증분이라 비용이 생각보다 작다. 다만 스냅숏이 앞의 것보다 오래 걸리면 다음 주기와 겹치니, 실제 걸리는 시간을 보고 주기를 정한다.

OpenSearch에는 SLM이 없고, Index Management 플러그인의 snapshot management(`_plugins/_sm/policies`)가 같은 역할을 한다. 정책 필드 이름이 다르니 그대로 옮겨 쓰지 않는다.

## 인덱스 하나만 다른 이름으로 되살리기

처음 장면으로 돌아가자. 지워진 `orders-2026.10`만 되살리고 싶다. 클러스터 전체를 되돌리면 그 뒤에 들어온 다른 인덱스의 데이터까지 잃으니, 인덱스 하나만 고른다. 운영 중인 이름과 겹치지 않게 다른 이름으로 먼저 복원해 내용을 확인하는 게 안전하다.

```http
POST _snapshot/s3-backup/nightly-2026.10.23-xyz/_restore
{
  "indices": "orders-2026.10",
  "include_global_state": false,
  "include_aliases": false,
  "rename_pattern": "(.+)",
  "rename_replacement": "restored-$1",
  "index_settings": { "index.number_of_replicas": 0 }
}

GET _cat/recovery/restored-orders-2026.10?v&active_only=true
```

`rename_pattern`과 `rename_replacement`는 정규식 치환이라 `orders-2026.10`이 `restored-orders-2026.10`으로 복원된다. 같은 이름으로 복원하려면 그 이름의 열린 인덱스가 없어야 한다. 이미 있으면 닫거나 지운 뒤에 복원한다. 복원하는 동안은 레플리카를 0으로 두면 프라이머리만 받아 빨리 끝나고, 확인이 끝나면 레플리카를 올린다. 복원 진행은 `_cat/recovery`에서 `type`이 `snapshot`인 줄로 보인다.

내용을 확인한 뒤 운영 이름으로 돌리는 방법은 둘이다. 앱이 별칭으로 접근하고 있다면 별칭을 복원한 인덱스로 돌리면 끝이다([매핑 글](/posts/elasticsearch-mapping)의 별칭 교체 참고). 별칭이 없다면 `_reindex`로 원래 이름에 옮기거나, 복원을 원래 이름으로 한 번 더 한다.

그런데 스냅숏은 01:30에 떴고 사고는 오후 3시에 났다. 그 사이 13시간 반의 주문은 스냅숏에 없다. 원본 DB가 따로 있다면 그 기간을 DB에서 다시 흘려 넣어 채운다. Elasticsearch가 유일한 원본인 데이터(로그 등)라면 그만큼은 잃는다. 이 차이가 뒤에서 RPO를 정할 때 바로 돌아온다.

복원에는 버전 규칙이 있다. 스냅숏은 만든 클러스터와 같은 버전이나 더 새 버전에 복원할 수 있고, 거꾸로는 안 된다. 그리고 새 버전은 한 메이저 전에 만든 인덱스까지만 읽는다. 9.x 클러스터는 8.x에서 만든 인덱스를 복원할 수 있지만, 7.x에서 만들어 8.x로 그대로 올라온 인덱스는 정상 인덱스로 복원하지 못한다. 기준은 스냅숏을 뜬 버전이 아니라 인덱스가 처음 만들어진 버전이다. 8.3 이후로는 그보다 오래된 인덱스를 읽기 전용 아카이브 인덱스로 일부 읽을 수 있지만 기능 제한이 크다. 메이저 업그레이드 전에 오래된 인덱스를 재색인해 두는 이유다.

## 다른 리전에 읽기 전용 사본: CCR

스냅숏 복원은 시간이 걸린다. 리전 하나가 통째로 멈췄을 때 수 TB를 복원하며 몇 시간을 기다릴 수 없다면, 다른 리전에 이미 데이터가 들어 있는 클러스터를 두어야 한다. CCR(Cross-Cluster Replication)이 그 일을 한다. 원래 클러스터의 인덱스를 리더(leader), 다른 클러스터의 사본을 팔로워(follower)라고 하고, 팔로워 쪽이 리더에게서 연산 기록을 당겨 와 똑같이 적용한다.

```http
PUT _cluster/settings
{
  "persistent": {
    "cluster": { "remote": { "seoul": { "seeds": ["10.0.1.10:9300"] } } }
  }
}

PUT /orders-2026.10/_ccr/follow
{
  "remote_cluster": "seoul",
  "leader_index": "orders-2026.10"
}

GET /orders-2026.10/_ccr/stats
```

첫 두 요청은 팔로워 클러스터(도쿄라고 하자)에서 보낸다. 리더 클러스터를 `seoul`이라는 원격 클러스터로 등록하고, 같은 이름의 팔로워 인덱스를 만든다. 날짜별로 새로 생기는 인덱스를 매번 손으로 따라가게 할 수 없으니 실제로는 `_ccr/auto_follow` 패턴으로 `orders-*`를 자동으로 따라가게 한다. `_ccr/stats`의 `leader_global_checkpoint`와 `follower_global_checkpoint` 차이가 얼마나 뒤처졌는지(복제 지연)다. CCR은 Elastic의 유료 라이선스(Platinum 이상) 기능이고, OpenSearch는 별도의 cross-cluster replication 플러그인으로 비슷한 일을 한다.

팔로워 인덱스는 읽기 전용이다. 도쿄의 검색 트래픽을 받을 수는 있지만 쓰기는 리더에만 간다. 서울이 멈춰서 도쿄를 운영으로 올려야 할 때의 순서를 아래 그림에서 다음을 눌러 따라가 보자.

승격은 되돌릴 수 없는 일방통행이다. 한 번 unfollow한 인덱스는 다시 팔로워로 만들 수 없고, 서울로 돌아가려면 반대 방향으로 팔로워를 새로 만들어 처음부터 받는다. 그래서 장애 판단과 승격 결정은 사람이 하고, 순서는 런북으로 미리 적어 연습해 둔다.

알아 둘 제약이 몇 가지 더 있다. 팔로워는 리더의 soft delete 기록을 당겨 오는데, 리더는 그 기록을 보존 기간(기본 12시간) 동안만 팔로워를 위해 남긴다. 네트워크가 그보다 오래 끊기면 팔로워는 이어서 받지 못하고 처음부터 다시 만들어야 한다. 또 CCR은 리더 인덱스의 실수도 그대로 복제한다. 서울에서 `_delete_by_query`를 잘못 돌리면 도쿄에서도 지워진다. 인덱스 삭제 자체는 따라가지 않지만, 팔로워가 리더를 잃어 더 이상 갱신되지 않는다. CCR은 리전 장애 대비이고, 실수 대비는 여전히 스냅숏이다.

## 오래된 데이터는 스냅숏 위에서 검색한다

hot과 warm은 일반 인덱스다. 프라이머리와 레플리카가 노드 디스크에 있고, warm은 더 큰 디스크에 쓰기 없이 둔다. cold와 frozen에서 searchable snapshot이 등장한다. cold 계층은 인덱스를 스냅숏에서 "전체 마운트"한다. 데이터 전체를 노드 디스크에 복사해 두지만, 레플리카를 두지 않는다. 노드가 죽으면 레플리카 대신 저장소에서 다시 받아 오면 되기 때문이다. 디스크가 절반으로 줄고 검색 속도는 거의 그대로다. frozen 계층은 "부분 마운트"다. 노드는 공유 캐시만 가지고 있고, 검색이 닿는 부분만 저장소에서 읽어 와 캐시에 둔다. 노드 디스크보다 훨씬 많은 데이터를 맡을 수 있는 대신 캐시에 없는 부분을 검색하면 초 단위로 느리다.

ILM 정책에서는 단계에 `searchable_snapshot` 동작을 넣으면 그 단계로 넘어갈 때 스냅숏을 뜨고 마운트하는 일을 자동으로 한다.

```http
PUT _ilm/policy/orders
{
  "policy": {
    "phases": {
      "hot":    { "actions": { "rollover": { "max_primary_shard_size": "50gb", "max_age": "30d" } } },
      "warm":   { "min_age": "30d",  "actions": { "forcemerge": { "max_num_segments": 1 } } },
      "cold":   { "min_age": "90d",  "actions": { "searchable_snapshot": { "snapshot_repository": "s3-backup" } } },
      "frozen": { "min_age": "180d", "actions": { "searchable_snapshot": { "snapshot_repository": "s3-backup" } } },
      "delete": { "min_age": "730d", "actions": { "delete": {} } }
    }
  }
}
```

롤오버와 ILM 단계 자체는 [ELK 스택 글](/posts/elk-stack-basics)과 [OpenSearch 운영 글](/posts/opensearch-cluster-operations)에서 다뤘으니 여기서는 백업과 맞물리는 부분만 짚는다. 마운트된 인덱스는 그 스냅숏에 기대고 있으므로, 스냅숏이나 저장소를 지우면 인덱스가 깨진다. 버킷 수명 주기 규칙을 쓰지 말라는 앞의 규칙이 여기서 더 중요해진다. 그리고 searchable snapshot도 Elastic의 유료 라이선스(Enterprise) 기능이다. 무료로 쓴다면 warm까지 쓰고, 오래된 인덱스는 스냅숏만 남긴 뒤 지웠다가 필요할 때 복원하는 방식으로 대신한다.

## 잃어도 되는 양과 멈춰도 되는 시간부터

여기까지의 장치는 셋으로 정리된다. 스냅숏(+SLM)은 실수와 랜섬웨어에서 되돌릴 지점을 남긴다. CCR은 리전이 멈췄을 때 이미 데이터가 들어 있는 사본을 준다. 데이터 계층과 searchable snapshot은 오래된 데이터를 싸게 들고 있는다. 무엇을 고를지는 [재해 복구](/posts/disaster-recovery) 글의 두 숫자, RPO(얼마나 잃어도 되나)와 RTO(얼마나 멈춰도 되나)에서 시작한다.

먼저 Elasticsearch가 원본인지 사본인지 본다. 상품 검색처럼 원본이 DB에 있다면 RPO는 DB가 지키고, Elasticsearch의 문제는 RTO뿐이다. 스냅숏에서 복원한 뒤 그 이후 변경을 DB에서 다시 흘려 넣거나, 아예 DB에서 처음부터 재색인할 수 있다. 이때 RTO는 "복원 + 재생" 또는 "전체 재색인" 중 짧은 쪽이다. 로그나 이벤트처럼 Elasticsearch가 유일한 저장소라면 스냅숏 주기가 곧 RPO다. 30분 주기면 최악 30분에 스냅숏 하나가 걸리는 시간을 더한 만큼 잃는다.

RTO는 복원 시간을 직접 어림한다. 프라이머리 합계가 2TB이고, 데이터 노드 6대가 저장소에서 각각 초당 100MB를 받는다고 가정하면 2,000,000MB ÷ 600MB/s ≈ 3,333초, 약 56분이다. 여기에 클러스터를 새로 띄우는 시간, 레플리카를 다시 만드는 시간, 별칭과 앱 설정을 바꾸는 시간이 더해진다. 실제 받는 속도는 저장소, 네트워크, `indices.recovery.max_bytes_per_sec` 같은 복구 속도 제한에 따라 다르고 기본값도 버전과 노드 역할마다 다르다. 그래서 숫자는 가정으로 두지 말고 복원 연습에서 잰다. 연습용 클러스터에 저장소를 `readonly`로 등록하고 실제 스냅숏을 복원해 걸린 시간을 기록하는 것이 가장 정확한 RTO 측정이다.

이렇게 정한 숫자에 맞춰 조합을 고른다. RTO가 몇 시간이어도 되면 SLM 스냅숏만으로 충분하다. 1시간 안이어야 하는데 데이터가 수 TB라면 복원으로는 어렵고, CCR로 다른 리전에 팔로워를 두거나 원본 DB에서 빠르게 다시 만들 수 있는 구조를 갖춘다. 어느 쪽이든 스냅숏은 빼지 않는다. CCR도 레플리카도 실수를 그대로 복제하기 때문이다.

## 면접에서 나올 만한 질문

### 레플리카가 있는데 스냅숏이 따로 필요한가요?

필요하다. 레플리카는 프라이머리를 실시간으로 따라 하는 복사본이라 노드 장애에는 답이지만, 인덱스 삭제나 잘못된 `_delete_by_query` 같은 사람의 실수도 그대로 따라 한다. 과거 시점으로 되돌릴 수 있는 건 클러스터 밖 저장소에 둔 스냅숏뿐이다. CCR 팔로워도 같은 이유로 실수 대비가 되지 않는다.

### Elasticsearch 스냅숏은 어떻게 증분으로 동작하나요?

샤드의 Lucene 세그먼트 파일은 한 번 쓰면 바뀌지 않으므로, 스냅숏은 저장소에 아직 없는 세그먼트 파일만 올리고 이미 있는 파일은 이름만 가리킨다. 그래서 스냅숏마다 완전한 목록이면서 업로드는 증분이다. 중간 스냅숏을 지워도 다른 스냅숏 복원에 지장이 없고, 어떤 스냅숏도 가리키지 않는 파일만 지워진다. 병합으로 새 큰 세그먼트가 생기면 그만큼은 통째로 올라간다.

### SLM 정책에는 무엇을 정하나요?

크론 식으로 주기, 대상 인덱스와 전체 상태 포함 여부, 저장소, 그리고 `expire_after`, `min_count`, `max_count`로 보관 규칙을 정한다. `min_count`가 있으면 연속 실패 중에도 성공한 옛 스냅숏이 지워지지 않는다. 만든 뒤 `_execute`로 바로 한 번 돌려 확인하고, 실패 수와 `PARTIAL` 상태를 모니터링에 연결한다.

### 실수로 지운 인덱스 하나만 되살리려면 어떻게 하나요?

`_restore`에 그 인덱스만 지정하고 `rename_pattern`, `rename_replacement`로 다른 이름으로 복원해 내용을 확인한 뒤, 별칭을 돌리거나 원래 이름으로 옮긴다. 같은 이름으로 복원하려면 그 이름의 열린 인덱스가 없어야 한다. 스냅숏 이후의 변경은 원본 DB가 있으면 다시 흘려 넣고, 없으면 그만큼 잃는다.

### 스냅숏을 다른 버전 클러스터에 복원할 수 있나요?

같은 버전이나 더 새 버전으로만 복원되고, 새 버전은 한 메이저 전에 만든 인덱스까지만 정상 인덱스로 읽는다. 기준은 스냅숏을 뜬 버전이 아니라 인덱스가 처음 만들어진 버전이라, 7.x에서 만든 인덱스는 9.x에 정상 복원되지 않는다. 그래서 메이저 업그레이드 전에 오래된 인덱스를 재색인해 둔다.

### CCR 팔로워를 운영으로 승격하는 절차는요?

팔로워 클러스터에서 `pause_follow`로 따라가기를 멈추고, 인덱스를 닫고 `unfollow`한 뒤 다시 열면 쓰기를 받는 일반 인덱스가 된다. 그다음 앱의 트래픽을 옮긴다. 승격은 되돌릴 수 없어서, 원래 리전으로 돌아가려면 반대 방향으로 팔로워를 새로 만들어야 한다. 마지막 몇 초 동안 복제되지 않은 쓰기는 잃을 수 있다.

### searchable snapshot은 무엇이고 cold와 frozen은 어떻게 다른가요?

스냅숏 저장소에 있는 인덱스를 복원하지 않고 마운트해서 검색하는 기능이다. cold는 전체 마운트라 데이터를 노드 디스크에 다 받아 두되 레플리카를 두지 않고, 장애 때 저장소에서 다시 받는다. frozen은 부분 마운트라 공유 캐시만 두고 검색이 닿는 부분을 그때 읽어 와 훨씬 많은 데이터를 싸게 맡지만, 캐시에 없는 부분은 느리다. 마운트된 동안 그 스냅숏을 지우면 안 된다.

### Elasticsearch의 RPO와 RTO는 어떻게 정하나요?

먼저 Elasticsearch가 원본인지 본다. 원본이 DB라면 RPO는 DB가 지키고, RTO는 스냅숏 복원 후 재생과 전체 재색인 중 짧은 쪽이다. Elasticsearch가 유일한 저장소라면 스냅숏 주기가 RPO가 된다. RTO는 프라이머리 용량을 복원 처리량으로 나눠 어림하고, 실제로는 읽기 전용으로 등록한 연습 클러스터에서 복원해 재며, 목표를 못 맞추면 CCR이나 DB 재구축 경로를 더한다.
