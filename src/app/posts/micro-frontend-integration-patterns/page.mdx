상품 상세 페이지를 서버에서 조각 세 개로 이어 붙이기로 했다. 헤더, 상품 정보, 추천 영역이다. 헤더는 20ms, 상품 정보는 60ms 만에 오는데 추천 영역은 1.5초가 걸린다. 그런데 사용자 브라우저가 첫 바이트를 받은 시각은 1.56초였다. 상품 정보는 이미 다 준비돼 있었는데 추천 영역 하나를 기다리느라 아무것도 보내지 않은 것이다.

화면을 팀별 조각으로 나누는 이유와 합치는 방식의 큰 그림은 [마이크로 프런트엔드](/posts/micro-frontends) 글에, 브라우저에서 합치는 Module Federation의 내부는 [Module Federation 깊게 보기](/posts/module-federation-deep-dive)에 정리했다. 이 글은 나머지 방식, 즉 서버 조합, iframe, Web Components, single-spa, import map을 실제로 만들어 보면서 각 방식이 어디서 깨지고 무엇을 따로 챙겨야 하는지 본다. 비교표를 다시 그리지 않고, 만들어 봐야 보이는 것만 적는다.

예제는 모두 Node 22로 띄운 로컬 서버와 Chromium 141(Playwright, 헤드리스)에서 돌렸다. 출력은 실제로 찍힌 그대로다.

## 가장 느린 조각이 첫 바이트를 정한다

처음 장면을 그대로 만들었다. 조각 서버는 경로마다 정해진 시간만큼 기다렸다가 HTML 조각을 돌려준다. 페이지 서버는 세 조각을 동시에 요청해서 하나의 문서로 합친다. 합치는 방법을 세 가지로 바꿔 가며 쟀다.

```js
// page.js 중 핵심
async function getFragment(name, timeoutMs) {
  try {
    const res = await fetch(`http://localhost:${fragPort}/${name}`, timeoutMs ? { signal: AbortSignal.timeout(timeoutMs) } : {});
    return await res.text();
  } catch (e) {
    console.log(`[page] ${name} 실패: ${e.name}`);
    return fallback(name);                              // 빈 자리 표시 조각
  }
}

if (mode === "stream") {
  res.write("<!doctype html><html><body>");
  const pending = names.map((n) => getFragment(n, 3000));   // 동시에 시작
  for (const p of pending) res.write(await p);              // 순서대로 흘려보낸다
  res.end("</body></html>");
} else {
  const timeout = mode === "timeout" ? 300 : undefined;
  const parts = await Promise.all(names.map((n) => getFragment(n, timeout)));
  res.end(`<!doctype html><html><body>${parts.join("")}</body></html>`);
}
```

`curl`로 첫 바이트 시각(`time_starttransfer`)과 전체 시각을 쟀다.

```bash
# 세 가지 모드의 첫 바이트와 전체 응답 시간
for m in all timeout stream; do
  curl -s -o /dev/null -w "mode=$m  ttfb=%{time_starttransfer}s  total=%{time_total}s\n" "http://localhost:18560/?mode=$m"
done
```

```text
mode=all  ttfb=1.560361s  total=1.560426s
mode=timeout  ttfb=0.307629s  total=0.307688s
mode=stream  ttfb=0.002583s  total=1.505170s
```

`all`은 세 조각을 다 기다렸다 보내니 가장 느린 추천 영역이 첫 바이트를 정했다. `timeout`은 조각마다 300ms 제한을 두고 넘으면 빈 자리 표시로 바꿨다. 첫 바이트가 0.3초로 줄었지만 추천 영역은 이번 응답에서 빠졌다. `stream`은 문서 머리를 바로 보내고 조각이 준비되는 대로 흘려보낸다. 조각마다 언제 도착하는지 클라이언트에서 찍어 봤다.

```text
== all
 1619ms  header, product, reco
== stream
   52ms  <!doctype html><html><body>
   69ms  header
  108ms  product
 1551ms  reco
```

스트리밍이면 상품 정보가 108ms에 브라우저에 닿는다. 브라우저는 받은 HTML부터 그리기 시작하니 사용자는 1.5초 동안 빈 화면이 아니라 헤더와 상품 정보를 본다. 아래 그림에서 다음을 누르면 세 방식이 차례로 지나간다.

마지막 단계의 단서가 중요하다. HTML 스트리밍은 앞에서부터 순서대로 쓴다. 느린 추천 영역이 문서 맨 위에 있다면 그 뒤의 조각도 모두 막힌다. 순서를 바꿀 수 없다면 자리만 먼저 보내 두고 나중에 내용을 끼워 넣는 방식이 필요한데, React의 스트리밍 SSR이 Suspense 경계에서 하는 일이 바로 그것이다. [스트리밍 SSR과 Suspense](/posts/streaming-ssr-suspense)에서 다뤘다.

CDN에서 합치는 ESI도 같은 문제를 가진다. ESI 1.0 명세에는 `<esi:include src="/fragments/reco" alt="/fragments/reco-fallback" onerror="continue" />`처럼 대체 주소와 실패 시 계속 진행하는 속성이 있다. 시간 제한 값과 지원 범위는 CDN 제품마다 다르니 문서를 확인해야 한다. 어느 쪽이든 조각마다 제한 시간과 빈 자리 표시를 정해 두지 않으면, 조각 하나의 장애가 페이지 전체의 응답 시간이 된다. [타임아웃](/posts/timeouts) 글의 원칙이 프런트엔드 조합에도 그대로 적용된다.

## iframe은 높이부터 알려 줘야 한다

iframe은 격리가 가장 확실한 방식이다. 리모트가 자기 문서와 전역 변수를 따로 쓰니 CSS도 자바스크립트도 부딪치지 않는다. 대신 셸은 iframe 안에 무엇이 얼마나 있는지 모른다. 결제 리모트를 다른 출처(포트 18563)에서 띄우고, 높이를 맞추는 코드 없이 열어 봤다. 안에는 40px짜리 항목이 10개 있다.

```text
[동기화 없음] iframe 높이 150px
```

내용은 400px인데 iframe은 150px이다. 브라우저의 iframe 기본 높이가 150px이라서, 셸이 높이를 정해 주지 않으면 리모트 안쪽에 스크롤바가 생기거나 내용이 잘린다. 셸은 다른 출처 문서의 높이를 직접 읽을 수 없으니 리모트가 알려 줘야 한다.

`origin` 검사를 빼는 건 흔한 실수다. 높이 정도면 화면이 깨지는 데서 끝나지만, 같은 통로로 "결제 완료"나 "로그인 토큰" 같은 메시지를 주고받기 시작하면 다른 출처의 프레임이 가짜 메시지를 보내는 공격 경로가 된다. 보내는 쪽도 `"*"` 대신 받을 출처를 적어야 리모트가 엉뚱한 페이지에 끼워졌을 때 데이터가 새지 않는다.

높이 말고도 iframe이 따로 챙기게 만드는 것들이 있다. 다른 사이트의 iframe은 브라우저의 서드파티 쿠키 정책을 받는다. 사파리는 기본으로 서드파티 쿠키를 막고, 크롬 계열도 설정과 버전에 따라 막거나 사이트별로 나눠 저장한다. 그래서 리모트를 셸과 다른 사이트(등록 도메인이 다른 곳)에 두면 리모트 쪽 로그인 쿠키가 안 붙을 수 있다. 셸과 같은 사이트의 하위 도메인에 두는 편이 안전하다. 셸이 반대로 남의 페이지에 끼워지는 걸 막으려면 응답에 `Content-Security-Policy: frame-ancestors`를 준다. 포커스 이동과 스크린 리더 흐름이 iframe 경계에서 끊기는 문제는 앞 글에서 짚었다.

## Web Components로 감쌀 때 넘어가는 것과 막히는 것

Custom Elements로 리모트를 `<cart-list>` 같은 태그로 만들면 셸이 무슨 프레임워크든 상관없다. 대신 셸이 React라면 React가 이 태그에 값을 어떻게 넘기는지가 중요해진다. 같은 코드를 React 18.3.1과 19.2.0으로 각각 빌드해서 돌렸다.

```js
class CartList extends HTMLElement {
  static observedAttributes = ["items"];
  constructor() { super(); this.attachShadow({ mode: "open" }); }
  set items(v) { this._items = v; this.render(); }   // 속성(property)으로 받는 setter
  get items() { return this._items; }
  // ... render는 shadowRoot에 <p>를 그린다
}
customElements.define("cart-list", CartList);

createRoot(root).render(
  React.createElement("cart-list", {
    id: "cl",
    items: ["키보드", "마우스"],
    onCheckout: (e) => console.log(`  onCheckout 호출됨 (event.type=${e.type})`),
  }),
);
// 렌더링 뒤 확인하고 이벤트 두 개를 보낸다
node.dispatchEvent(new CustomEvent("checkout"));
node.dispatchEvent(new CustomEvent("Checkout"));
```

```text
React 18.3.1
  property items: undefined
  attribute items: "키보드,마우스"
  attribute oncheckout: null
  dispatch checkout
  dispatch Checkout
React 19.2.0
  property items: ["키보드","마우스"]
  attribute items: null
  attribute oncheckout: null
  dispatch checkout
  dispatch Checkout
  onCheckout 호출됨 (event.type=Checkout)
```

React 18은 커스텀 요소에 주는 props를 HTML 속성(attribute)으로 썼다. 배열이 문자열 `"키보드,마우스"`가 됐고, 함수인 `onCheckout`은 아예 사라졌다. React 19는 요소에 같은 이름의 속성(property)이 있으면 그쪽으로 넘겨서 배열이 그대로 들어갔다. 이벤트도 붙었는데, `on` 뒤의 글자를 그대로 이벤트 이름으로 쓴다. 그래서 `onCheckout`은 `Checkout` 이벤트만 받았고 소문자 `checkout`에는 반응하지 않았다. 리모트가 `checkout`을 보낸다면 React 19에서는 `oncheckout`이라고 적어야 한다. 셸이 React 18이라면 `ref`로 요소를 잡아 `el.items = ...`, `el.addEventListener(...)`를 직접 하는 감싸기 컴포넌트를 둔다.

Shadow DOM이 스타일을 얼마나 막는지도 같이 봤다. 셸 문서에는 이런 스타일을 넣었다.

```css
:root { --brand: rgb(0, 128, 0); }
body { color: rgb(0, 0, 255); font-family: serif; }
p { color: rgb(255, 0, 0); font-size: 30px; margin: 20px; }
```

리모트는 Shadow DOM 안에 `<style>p { margin: 0 }</style>`과 `<p style="background: var(--brand)">`를 그렸다. 두 `<p>`의 계산된 스타일이다.

```text
--- Shadow DOM 안의 <p>
  color: rgb(0, 0, 255)
  fontFamily: serif
  fontSize: 16px
  margin: 0px
  background: rgb(0, 128, 0)
--- 셸의 <p>
  color: rgb(255, 0, 0)
  margin: 20px
```

셸의 `p` 선택자(빨간색, 30px)는 안으로 들어가지 못했다. 리모트의 `p { margin: 0 }`도 셸 문단에 새지 않았다. 그런데 글자색은 파란색, 글꼴은 serif다. `body`에서 상속되는 속성은 경계를 넘는다. CSS 변수 `--brand`도 넘어왔다.

이 성질은 쓰기에 따라 장점이다. 앞 글에서 디자인 토큰을 셸이 CSS 변수로 한 번만 내려 주라고 했는데, Shadow DOM 안의 리모트도 그 변수를 그대로 받는다. 반대로 상속을 막고 싶다면 리모트가 자기 루트에 `:host { all: initial; }`을 주고 필요한 것만 다시 정한다. 전역 CSS에 기대는 UI 라이브러리(모달을 `document.body`에 붙이는 것 같은)는 Shadow DOM 밖에 그려져서 리모트의 스타일을 못 받는다는 점도 흔한 함정이다.

## single-spa는 생명주기 세 개를 지키게 한다

single-spa는 리모트를 "주소에 따라 켜고 끄는 앱"으로 다룬다. 각 앱은 `bootstrap`, `mount`, `unmount` 세 함수를 내보내고, 루트 설정이 `activeWhen`으로 어느 경로에서 켤지 정한다. 리모트 코드를 어떻게 받아 올지는 정하지 않아서, import map이나 Module Federation과 같이 쓰는 경우가 많다. single-spa 6.0.3으로 앱 두 개를 등록하고 경로를 오가 봤다. search 앱은 `mount`에서 `resize` 리스너를 달고 `unmount`에서 떼지 않게 일부러 잘못 만들었다.

```js
registerApplication({ name: "search", app: async () => makeApp("search", { leaky: true }), activeWhen: "/search", customProps: { user: "kim" } });
registerApplication({ name: "checkout", app: async () => makeApp("checkout", { leaky: false }), activeWhen: ["/checkout"], customProps: { user: "kim" } });
window.addEventListener("single-spa:app-change", () => log(`[app-change] ${location.pathname} → mounted=${JSON.stringify(getMountedApps())}`));
start();
```

## 배포 포인터를 import map으로 두기

리모트를 따로 배포하려면 "지금 쓰는 버전이 어디 있는지"를 가리키는 포인터가 필요하다. 앞 글에서는 설정 서버를 예로 들었다. 브라우저 표준인 import map을 쓰면 이 포인터를 HTML 안에 둘 수 있다. import map은 `import "@shop/checkout"` 같은 이름(bare specifier)을 실제 주소로 바꿔 주는 표다. 크롬 계열은 89, 파이어폭스는 108, 사파리는 16.4부터 지원해서 지금 쓰이는 주요 브라우저에서는 그대로 쓸 수 있다.

```js

  mod.mount(document.getElementById("app"));
  const m = performance.measure(`${name} mount`, `${name}:start`);

mountRemote("@shop/checkout");
```

## 리모트마다 따로 재고 따로 잡는다

위 예제의 에러 귀속이 잘 된 건 import map 모듈이 CORS 규칙으로 로드되기 때문이다. 리모트가 다른 출처의 CDN에 있고 평범한 `<script src>`로 로드되면 이야기가 달라진다. 셸(:18568)이 다른 출처(:18569)의 스크립트를 불렀고, 그 스크립트가 `null.price`를 읽다 터지게 했다.

```text
<script src> (crossorigin 없음)
  message="Script error." filename="" error=null
<script src crossorigin="anonymous"> + Access-Control-Allow-Origin: *
  message="Uncaught TypeError: Cannot read properties of null (reading 'price')" filename="http://127.0.0.1:18569/remote.js" error=TypeError
```

`crossorigin` 없이 다른 출처 스크립트에서 난 에러는 브라우저가 내용을 가린다. 메시지는 `Script error.`, 파일 이름은 빈 문자열, 에러 객체는 `null`이다. 어느 리모트에서 났는지 알 길이 없다. 스크립트 태그에 `crossorigin="anonymous"`를 주고 리모트 CDN이 `Access-Control-Allow-Origin`을 돌려줘야 전체가 보인다. webpack의 Module Federation이라면 `output.crossOriginLoading: "anonymous"`가 청크 스크립트 태그에 이 속성을 붙인다. 에러 수집 도구 대시보드가 `Script error.`로 가득하다면 대개 이 설정이 빠져 있다. 소스맵과 수집 파이프라인은 [프런트엔드 에러 추적](/posts/frontend-error-tracking)에서 다룬다.

리모트 단위로 숫자를 남기는 습관도 같이 들이면 좋다. 위의 `performance.measure`처럼 리모트 이름과 버전을 붙인 마운트 시간, 로드 실패 수, Error Boundary가 잡은 에러 수를 실제 사용자 측정에 보낸다. 그래야 "페이지가 느려졌다"가 아니라 "추천 리모트 v88부터 마운트가 200ms 늘었다"로 좁혀진다. 백엔드까지 이어 보고 싶다면 리모트가 보내는 API 요청에도 같은 이름을 헤더나 추적 속성으로 실어 둔다. [분산 추적](/posts/distributed-tracing)의 `traceparent`가 그 연결을 맡는다.

## 무엇을 고를지 정하는 질문들

여기까지 만들어 보면 방식마다 따로 챙겨야 할 것이 분명해진다. 그래서 고를 때도 질문으로 접근하는 편이 낫다.

첫 화면과 검색 노출이 중요한가. 그렇다면 서버나 엣지에서 HTML 조각을 합치고, 조각마다 시간 제한과 빈 자리 표시를 둔다. 느린 조각은 문서 뒤로 보내거나 스트리밍으로 나중에 끼운다.

리모트를 믿을 수 있는가. 외부 업체 위젯, 결제 대행 화면처럼 셸과 같은 권한을 줄 수 없는 코드라면 iframe의 벽이 비용보다 값지다. 높이 동기화와 `origin` 검사, 쿠키 정책은 처음부터 설계에 넣는다.

팀마다 프레임워크가 다른가, 혹은 앞으로 바뀔 수 있는가. 그렇다면 Web Components로 겉을 감싸고 single-spa 같은 생명주기 계약을 둔다. 셸의 React 버전에 따라 속성 전달 방식이 달라진다는 것, unmount 정리를 계약에 넣어야 한다는 것을 같이 챙긴다.

모두 같은 React를 쓰고 상태와 디자인 시스템을 긴밀하게 나눠야 하는가. 그렇다면 Module Federation이 가장 자연스럽다. 공유 스코프와 장애 전파 방식은 [Module Federation 깊게 보기](/posts/module-federation-deep-dive)에서 본 대로다.

실제 서비스는 이 중 하나만 쓰지 않는 경우가 많다. 경로 단위로는 서버에서 앱을 나누고(멀티 존), 한 화면 안에서는 Module Federation으로 섞고, 외부 결제창만 iframe으로 띄우는 식이다. 어떤 조합이든 배포 포인터, 리모트별 관측, 실패했을 때의 빈 자리 표시는 공통으로 필요하다.

## 다시 1.56초 앞에서

처음 장면에서 첫 바이트가 늦은 건 조합하는 쪽이 가장 느린 조각을 기다렸기 때문이었다. 어떤 방식으로 합치든 같은 질문이 반복된다. 조각 하나가 늦거나 죽으면 나머지는 어떻게 되는가. 서버 조합에서는 시간 제한과 스트리밍 순서가, iframe에서는 높이와 메시지 검증이, Web Components에서는 셸 React 버전에 따른 값 전달이, single-spa에서는 unmount 정리가, import map에서는 포인터와 캐시 정책이 그 답을 정한다. 그리고 그 답이 맞는지는 리모트 이름과 버전을 붙인 관측값으로만 확인할 수 있다.

## 면접에서 나올 만한 질문

### 서버에서 HTML 조각을 합칠 때 가장 조심할 점은 무엇인가요?

가장 느린 조각이 페이지 전체의 응답 시간이 되지 않게 하는 것이다. 모든 조각을 모아서 보내면 실험처럼 1.5초짜리 조각 하나 때문에 첫 바이트가 1.56초에 나간다. 조각마다 시간 제한과 빈 자리 표시를 두거나, 문서 머리부터 스트리밍해서 준비된 조각을 먼저 보낸다. 스트리밍은 앞에서부터 쓰니 느린 조각은 문서 뒤쪽에 두거나 자리를 먼저 보내고 나중에 채운다.

### iframe으로 리모트를 붙일 때 높이는 어떻게 맞추나요?

셸은 다른 출처 문서의 크기를 읽을 수 없으니 리모트가 알려 줘야 한다. 리모트가 `ResizeObserver`로 자기 높이를 지켜보다가 `postMessage`로 셸에 보내고, 셸은 그 값을 iframe 높이에 반영한다. 아무것도 하지 않으면 기본 높이 150px로 남는다. 셸은 `e.origin`과 `e.source`를 확인해서 허용한 리모트가 보낸 메시지만 받고, 리모트는 받을 출처를 `"*"` 대신 명시한다.

### React에서 Web Component에 배열이나 함수를 넘기면 어떻게 되나요?

React 18까지는 커스텀 요소의 props를 HTML 속성으로 써서, 배열은 쉼표로 이은 문자열이 되고 함수는 사라진다. React 19는 요소에 같은 이름의 property가 있으면 그쪽으로 넘기고, `on` 뒤의 글자를 이벤트 이름으로 써서 리스너를 단다. 그래서 `onCheckout`은 `Checkout` 이벤트를 받고 소문자 `checkout`은 받지 않는다. React 18 셸이라면 `ref`로 요소를 잡아 property와 리스너를 직접 다는 감싸기 컴포넌트를 둔다.

### Shadow DOM이면 스타일이 완전히 격리되나요?

선택자는 막지만 완전한 격리는 아니다. 셸의 `p` 같은 규칙은 안으로 못 들어오고 리모트 규칙도 밖으로 새지 않는다. 하지만 `color`, `font-family`처럼 상속되는 속성과 CSS 변수는 경계를 넘는다. 디자인 토큰을 CSS 변수로 내려 주는 데는 장점이고, 상속까지 끊으려면 `:host { all: initial; }`로 초기화한다.

### single-spa의 생명주기는 어떻게 동작하고 흔한 실수는 무엇인가요?

앱마다 `bootstrap`은 처음 한 번, `mount`와 `unmount`는 `activeWhen`이 맞고 안 맞을 때마다 불린다. 이전 앱의 `unmount`가 끝난 뒤에 다음 앱의 `mount`가 불린다. 흔한 실수는 `unmount`에서 DOM만 지우고 전역 리스너, 타이머, 구독을 정리하지 않는 것이다. 문서가 살아 있으니 켤 때마다 쌓이고, 실험에서는 세 번 켠 뒤 꺼진 앱의 핸들러가 이벤트 한 번에 세 번 돌았다.

### 리모트를 롤백하는 구조는 어떻게 만드나요?

리모트 결과물을 버전 경로에 쌓고 지우지 않은 채, "지금 버전"을 가리키는 포인터만 바꾸게 만든다. import map을 쓰면 셸 HTML 안의 이름과 주소 표가 그 포인터가 된다. HTML은 `no-cache`, 버전 경로의 파일은 `immutable`로 캐시하면 포인터를 바꾸는 즉시 다음 요청부터 반영되고 빌드는 다시 하지 않는다. 포인터를 사용자 일부에게만 새 버전으로 주면 리모트 단위 카나리가 된다.

### 리모트 에러가 `Script error.`로만 찍히는 이유는 무엇인가요?

다른 출처에서 `crossorigin` 속성 없이 로드한 스크립트의 에러는 브라우저가 메시지, 파일 이름, 에러 객체를 가리기 때문이다. 스크립트 태그에 `crossorigin="anonymous"`를 주고 리모트 CDN이 `Access-Control-Allow-Origin`을 돌려주면 전체 내용이 보인다. Module Federation이라면 `output.crossOriginLoading`을 켠다. 그다음 파일 경로나 import map으로 에러를 리모트 이름과 버전에 묶어서 수집해야 어느 팀의 어느 배포가 원인인지 바로 나온다.
