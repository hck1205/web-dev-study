과일 바구니 이야기로 포장돼 있지만 벗겨 보면 "서로 다른 값이 많아야 두 개인 가장 긴 연속 구간"을 구하는 문제다. 이 번역을 해내면 [슬라이딩 윈도 패턴](/posts/sliding-window-pattern)의 가장 긴 창 틀에 상태 하나(창 안의 종류별 개수)만 얹으면 된다. 반대로 이 번역을 못 하면 "어느 나무에서 시작할까"를 고민하다가 시간을 다 쓴다.

틀 자체는 허브 글에 있으니 여기서는 이 문제에서만 볼 수 있는 것을 판다. 바구니가 두 개라는 조건 덕분에 해시맵 없이 변수 네 개로 끝내는 풀이가 있고, 창을 줄이지 않고 미끄러뜨려도 되는 이유도 이 문제에서 깔끔하게 보인다. 시작점마다 따 보기, 길이 이분 탐색, 해시맵 창, 줄어들지 않는 창, 마지막 위치로 건너뛰는 창, 마지막 덩어리 길이 풀이까지 여섯 가지를 차례로 본다. 문제 원문은 [LeetCode 904](https://leetcode.com/problems/fruit-into-baskets/)다. 코드는 Node.js 22, Python 3.13, Java로 모두 돌렸다.

## 바구니 두 개로 딸 수 있는 가장 긴 줄

정수 배열 `fruits`가 주어진다. `fruits[i]`는 i번 나무에 열린 과일 종류다. 바구니는 두 개이고 바구니마다 한 종류만, 개수는 얼마든지 담을 수 있다. 아무 나무에서 시작해 오른쪽으로 가며 나무마다 정확히 하나씩 따고, 담을 수 없는 종류를 만나면 멈춘다. 딸 수 있는 과일의 최대 개수를 구한다.

조건을 하나씩 바꿔 말하면 이렇다.

- 시작점을 고르고 오른쪽으로 쭉 간다: 연속 구간이다.
- 바구니 두 개, 바구니마다 한 종류: 구간 안의 서로 다른 값이 2개 이하다.
- 딴 과일 개수: 구간 길이다.

풀이를 고르는 데 영향을 주는 제약은 두 개다.

- 길이가 1 이상 10만 이하다. 구간이 50억 개쯤이라 모든 구간을 보는 O(n²)은 위험하다.
- 과일 종류 번호는 0 이상 n 미만이다. 종류가 많을 수 있으니 길이 26 배열 같은 고정 크기 표가 아니라 해시맵이나 길이 n 배열이 필요하다.

## 나무 여덟 그루를 손으로 따 보기

`fruits = [1, 2, 1, 3, 3, 2, 2, 1]`로 해 보자. 시작점별로 멈출 때까지 따 본다.

```text
시작  따는 과일              멈춘 이유            개수
 0    1 2 1                 3번에서 세 번째 종류    3
 1    2 1                   3번에서 세 번째 종류    2
 2    1 3 3                 5번(2)에서 세 번째     3
 3    3 3 2 2               7번(1)에서 세 번째     4
 4    3 2 2                 7번(1)에서 세 번째     3
 5    2 2 1                 끝까지 갔다            3
 6    2 1                   끝까지 갔다            2
 7    1                     끝까지 갔다            1
```

답은 4, 3번 나무부터 6번 나무까지 `3 3 2 2`다.

표를 보면 시작점이 하나 오른쪽으로 갈 때 멈추는 자리는 절대 왼쪽으로 가지 않는다. 0번에서 시작하면 3번에서 멈추고, 2번에서 시작하면 5번, 3번에서 시작하면 7번이다. 시작이 오른쪽으로 가면 구간에서 앞쪽 과일이 빠질 뿐이라 종류가 늘 일은 없기 때문이다. 이 성질이 창이 되돌아가지 않고 한 방향으로만 가도 되는 근거다.

## 나무마다 출발해 본다

표를 그대로 코드로 옮긴다. 시작 `i`마다 `Set`에 종류를 넣으며 오른쪽으로 가다가, 종류가 셋이 되면 멈춘다.

```js
function fruitBrute(fruits) {
  let best = 0;
  for (let i = 0; i < fruits.length; i++) {
    const kinds = new Set(); // 이번 출발에서 담은 종류
    for (let j = i; j < fruits.length; j++) {
      kinds.add(fruits[j]);
      if (kinds.size > 2) break; // 세 번째 종류: 여기서 멈춘다
      best = Math.max(best, j - i + 1);
    }
  }
  return best;
}
```

시간 O(n²), 공간 O(1)이다(`Set`에는 많아야 세 개가 들어간다). 손으로 푼 표처럼 일찍 멈추는 입력에서는 빠르지만, 두 종류만 번갈아 나오는 입력에서는 시작점마다 끝까지 간다. `[0, 1, 0, 1, ...]` 1만 개에서 387ms였고, 10만 개면 그 100배라 시간 초과다.

`break`가 있어서 이미 브루트포스치고 영리하다. 하지만 시작이 하나 옮겨질 때마다 바로 앞에서 했던 일을 거의 그대로 다시 한다. 0번에서 출발해 1, 2번을 이미 봤는데 1번에서 출발할 때 또 본다.

## 길이를 정해 놓고 되는지 묻는다

길이로 보면 단조로운 성질이 있다. 길이 L로 딸 수 있는 구간이 있으면, 거기서 한쪽 끝을 빼면 길이 L − 1로도 딸 수 있다. 종류가 늘 수는 없으니까. 그래서 "길이 L로 되나"는 L이 작을 때 예, 어느 지점부터 아니오로 갈린다. 그 경계를 [이분 탐색](/posts/binary-search)으로 찾는다.

길이를 정하면 고정 길이 창을 밀면서 창 안 종류 수가 2 이하인 곳이 있는지 본다.

```js
function fruitBinary(fruits) {
  const n = fruits.length;
  // 길이 len인 구간 중 종류가 2개 이하인 곳이 있나
  const ok = (len) => {
    const cnt = new Map();
    for (let r = 0; r < n; r++) {
      cnt.set(fruits[r], (cnt.get(fruits[r]) ?? 0) + 1);
      if (r >= len) {
        const o = fruits[r - len]; // 창 밖으로 나간 과일
        cnt.set(o, cnt.get(o) - 1);
        if (cnt.get(o) === 0) cnt.delete(o);
      }
      if (r >= len - 1 && cnt.size <= 2) return true;
    }
    return false;
  };
  let lo = 1, hi = n; // 길이 1은 언제나 된다
  while (lo < hi) {
    const mid = Math.ceil((lo + hi) / 2); // lo = mid를 쓰니 올림
    if (ok(mid)) lo = mid;
    else hi = mid - 1;
  }
  return lo;
}
```

`lo`를 1에서 시작하는 건 나무가 적어도 한 그루라서 길이 1은 언제나 되기 때문이다. `mid`를 올림으로 잡는 이유는 `lo = mid`로 좁히는 쪽이라서다. 내림으로 잡으면 `lo`와 `hi`가 한 칸 차이일 때 `mid`가 `lo`와 같아져 범위가 줄지 않고 무한 루프에 빠진다.

판정 한 번이 O(n), 그걸 log n번이라 O(n log n)이다. 공간은 창 안 종류만큼이라 O(1)에 가깝다(많아야 3개). 아래 측정에서 79ms였다. 브루트포스보다는 한참 낫지만, 다음 풀이는 길이를 따로 정하지 않고 한 번에 끝낸다.

## 종류가 셋이 되면 앞에서 덜어 낸다

시작점을 하나씩 옮길 때 멈추는 자리가 뒤로 가지 않는다는 걸 이용한다. 오른쪽 끝 `r`을 한 칸씩 늘리며 과일을 바구니에 담고, 종류가 셋이 되면 왼쪽 끝 `l`을 당겨 앞쪽 과일을 덜어 낸다. 어떤 종류의 개수가 0이 되는 순간 종류가 둘로 돌아온다.

창 상태는 "종류 → 창 안 개수" 해시맵이다. 개수가 0이 된 종류는 지워서 `size`가 곧 종류 수가 되게 한다.

```js
function totalFruit(fruits) {
  const cnt = new Map(); // 바구니: 종류 → 창 안 개수
  let l = 0, best = 0;
  for (let r = 0; r < fruits.length; r++) {
    cnt.set(fruits[r], (cnt.get(fruits[r]) ?? 0) + 1); // 오른쪽 나무에서 딴다
    while (cnt.size > 2) {      // 종류가 셋이면
      const f = fruits[l++];    // 맨 앞 과일을 덜어 낸다
      cnt.set(f, cnt.get(f) - 1);
      if (cnt.get(f) === 0) cnt.delete(f); // 다 빠진 종류는 바구니를 비운다
    }
    best = Math.max(best, r - l + 1); // 지금 창은 종류가 2개 이하다
  }
  return best;
}
```

손으로 푼 예시를 따라가 본다. 초록 칸이 지금 창이고, 메모리 칸은 바구니 안 종류별 개수와 지금까지의 최고 기록이다.

`l`과 `r`이 각각 한 방향으로 많아야 n번 움직이니 전체 O(n)이다. 해시맵에는 많아야 세 종류가 들어가니 공간 O(1)이다. 10만 개에서 7.8ms였다.

## 창을 줄이지 않고 미끄러뜨리기

우리가 원하는 건 가장 긴 길이 하나다. 그렇다면 한 번 길이 4인 창을 찾은 뒤로는 길이 3 이하인 창에 관심이 없다. 창을 줄이지 말고, 조건이 깨지면 길이를 그대로 둔 채 한 칸 옆으로 밀기만 해도 된다.

```js
function fruitNoShrink(fruits) {
  const cnt = new Map();
  let l = 0;
  for (let r = 0; r < fruits.length; r++) {
    cnt.set(fruits[r], (cnt.get(fruits[r]) ?? 0) + 1); // 창이 한 칸 커진다
    if (cnt.size > 2) {          // 깨졌으면 왼쪽도 한 칸만 민다
      const f = fruits[l++];
      cnt.set(f, cnt.get(f) - 1);
      if (cnt.get(f) === 0) cnt.delete(f);
    }
  }
  return fruits.length - l; // 창 길이는 줄지 않았으니 마지막 길이가 최고 기록
}
```

창 길이는 `r`이 한 칸 갈 때 커지거나(조건 만족) 그대로(조건 깨짐)다. 줄어드는 일이 없으니 마지막 창 길이 `n - l`이 지나온 길이 중 가장 크다. 그리고 창이 커지는 건 조건을 만족하는 창을 만났을 때뿐이라, 그 길이는 실제로 딸 수 있는 길이다.

예시 `[1, 2, 1, 3, 3, 2, 2, 1]`에 돌리면 끝났을 때 `l`이 4라서 8 − 4 = 4가 나온다. 창 길이는 1, 2, 3, 3, 3, 3, 4, 4로 변했다. 3번 칸에서 3이 들어왔을 때 해시맵 창은 두 칸을 줄였지만, 이 창은 한 칸만 밀고 길이 3을 유지했다.

중간의 창은 종류가 셋 이상인 "가짜 창"일 수 있다. 예시에서 7번 칸까지 오면 창은 4번부터 7번까지 `3 2 2 1`인데 종류가 셋이다. 그래도 상관없다. 이 창은 "길이 4는 이미 달성했다"는 기록을 들고 미끄러질 뿐이다. 이 틀은 [Longest Repeating Character Replacement](/posts/leetcode-longest-repeating-character-replacement)에서 자세히 증명했다. 그 문제에서는 판정 값을 정확히 유지하기 어려워서 이 틀이 꼭 필요했는데, 이 문제에서는 둘 다 쉬워서 취향 차이다.

시간 O(n), 공간 O(1)이고 10만 개에서 9.1ms였다. 줄이는 반복문이 없어 각 `r`마다 하는 일이 정확히 한 번으로 정해진다. 대신 답으로 구간 자체(어디서 어디까지)를 돌려 달라고 하면 마지막 창이 가짜일 수 있으니, 길이가 커지는 순간의 `l`, `r`을 따로 적어 둬야 한다.

## 마지막 위치만 기억하고 건너뛴다

해시맵 창에서 `while`이 하는 일은 "두 종류 가운데 하나가 다 빠질 때까지 빼기"다. 어느 종류가 먼저 다 빠질까. 창 안에서 마지막으로 나온 위치가 더 앞에 있는 종류다. 그 위치 바로 다음으로 `l`을 한 번에 옮기면 `while`이 필요 없다.

```js
function fruitJump(fruits) {
  const last = new Map(); // 종류 → 창 안에서 마지막으로 나온 위치
  let l = 0, best = 0;
  for (let r = 0; r < fruits.length; r++) {
    last.set(fruits[r], r);
    if (last.size > 2) {
      // 마지막 위치가 가장 앞인 종류를 버린다 (세 개 중 하나라 금방 찾는다)
      let minPos = Infinity, minKey;
      for (const [k, p] of last) if (p < minPos) { minPos = p; minKey = k; }
      last.delete(minKey);
      l = minPos + 1; // 그 종류가 마지막으로 나온 다음 칸부터 시작
    }
    best = Math.max(best, r - l + 1);
  }
  return best;
}
```

예시의 3번 칸에서 `last`는 1→2, 2→1, 3→3이다. 마지막 위치가 가장 앞인 건 2(1번 칸)라 2를 버리고 `l = 2`로 간다. 해시맵 창이 두 번 빼서 도달한 자리와 같다.

왜 마지막 위치가 앞인 쪽을 버려야 하는지는 반대로 해 보면 보인다. `[1, 2, 1, 1, 3]`에서 3이 들어올 때 `last`는 1→3, 2→1이다. 2를 버리면 `l = 2`가 되어 창은 `1 1 3`이다. 1을 버리려면 1이 창에서 모두 빠져야 하는데 1의 마지막 위치가 3번이라 `l = 4`, 창은 `3` 하나뿐이다. 두 선택 모두 종류를 둘로 만들지만, 마지막 위치가 앞인 종류를 버려야 창이 덜 줄어든다. 창을 필요 이상으로 줄이면 그 사이에서 시작하는 답을 놓친다.

`last`에는 많아야 세 개가 있으니 최솟값 찾기는 O(1)이고 전체 O(n)이다. 10만 개에서 3.8ms였다. [Longest Substring Without Repeating Characters](/posts/leetcode-longest-substring-without-repeating)의 "마지막으로 본 위치로 점프"와 같은 생각인데, 거기서는 `l`이 뒤로 가는 버그를 조심해야 했다. 여기서는 버린 종류의 마지막 위치가 언제나 지금 `l` 이상이라 그런 일이 없다. 창 안에 있는 종류의 마지막 위치는 창 안에 있기 때문이다.

## 마지막 덩어리 길이만 들고 가기

바구니가 두 개뿐인 조건을 끝까지 쓰면 해시맵도 필요 없다. 지금 창은 언제나 두 종류로 되어 있고, 새 종류가 들어오면 살아남는 건 "바로 앞에서 이어지던 같은 종류의 덩어리"뿐이다.

예를 들어 창이 `1 2 1 1`일 때 3이 들어오면 새 창은 `1 1 3`이다. 바로 앞 덩어리(이어진 1 두 개)만 남는다. 그 앞의 2와 1은 2를 버리는 순간 함께 떨어져 나간다. 그러니 들고 다닐 것은 넷이다.

- `b`: 마지막으로 딴 종류
- `a`: 창 안의 다른 한 종류
- `runB`: 맨 끝에서 `b`가 몇 개 이어졌나(마지막 덩어리 길이)
- `cur`: 지금 창 길이

```js
function fruitLastRun(fruits) {
  let a = -1, b = -1; // b: 마지막 종류, a: 창 안의 다른 종류 (-1은 아직 없음)
  let cur = 0, runB = 0, best = 0;
  for (const f of fruits) {
    if (f === a || f === b) cur++; // 바구니가 있는 종류: 창이 늘어난다
    else cur = runB + 1;           // 새 종류: 마지막 덩어리 + 지금 과일만 남는다
    if (f === b) runB++;           // 마지막 덩어리가 이어진다
    else { runB = 1; a = b; b = f; } // 덩어리가 바뀐다. 직전 종류가 a가 된다
    best = Math.max(best, cur);
  }
  return best;
}
```

`a`와 `b`를 -1로 시작하는 건 "아직 없음"을 나타내려는 것이다. 실은 0으로 시작해도 답은 같다. 처음 0번 과일이 들어와 가짜 `a`와 맞아떨어져도, 그때는 실제 종류가 둘 이하라 창 길이를 늘리는 게 맞기 때문이다. 0으로 시작한 판을 무작위 입력 2만 개에 돌려 봐도 차이가 없었다. 그래도 읽는 사람이 이걸 따져 보게 만들 필요는 없으니 있을 수 없는 값으로 시작하는 쪽이 낫다.

`f === a`일 때도 `a = b; b = f`로 둘을 바꾸는 게 요점이다. 마지막 종류가 바뀌었으니 다음에 새 종류가 오면 살아남는 덩어리도 바뀐다. 같은 예시로 따라간다.

## 바구니 창의 Python·Java 코드

바구니 수가 바뀌는 변형까지 생각하면 해시맵 창이 가장 쓸모가 넓다. 세 언어로 맞춰 둔다.

```python
from collections import defaultdict
from typing import List

class Solution:
    def totalFruit(self, fruits: List[int]) -> int:
        cnt = defaultdict(int)  # 바구니: 종류 → 창 안 개수
        l = best = 0
        for r, f in enumerate(fruits):
            cnt[f] += 1
            while len(cnt) > 2:          # 종류가 셋이 되면
                g = fruits[l]
                cnt[g] -= 1
                if cnt[g] == 0:
                    del cnt[g]           # 0이 된 종류는 지워야 len이 맞다
                l += 1
            best = max(best, r - l + 1)
        return best
```

```java
import java.util.HashMap;
import java.util.Map;

class Solution {
    public int totalFruit(int[] fruits) {
        Map<Integer, Integer> cnt = new HashMap<>(); // 종류 → 창 안 개수
        int l = 0, best = 0;
        for (int r = 0; r < fruits.length; r++) {
            cnt.merge(fruits[r], 1, Integer::sum);
            while (cnt.size() > 2) {
                int g = fruits[l++];
                if (cnt.merge(g, -1, Integer::sum) == 0) cnt.remove(g); // 0이면 지운다
            }
            best = Math.max(best, r - l + 1);
        }
        return best;
    }
}
```

`[1,2,1]`, `[0,1,2,2]`, `[1,2,3,2,2]`, `[3,3,3,1,2,1,1,2,3,3,4]`, `[1,2,1,3,3,2,2]`, `[5]`, `[4,4,4,4]`, `[1,2,3,4,5]`를 넣어 세 언어 모두 3, 3, 4, 5, 4, 1, 4, 2가 나왔다. 여섯 JS 풀이가 같은 답을 내는지는 종류 0~3, 길이 12 이하 무작위 배열 5,000개로 확인했다.

언어별로 짚을 것들이다.

- Python `defaultdict`는 `cnt[g]`를 읽기만 해도 키가 생긴다. 줄이는 쪽에서 `if cnt[g] == 0` 대신 `if cnt[x] == 0`처럼 엉뚱한 키를 읽으면 그 키가 0으로 생겨나 `len(cnt)`가 늘어난다. 읽는 키를 조심하거나 일반 `dict`와 `get`을 쓴다.
- Java `merge`는 결과 값을 돌려주니 줄이고 0인지 보는 걸 한 줄에 할 수 있다. `merge`에 넘긴 함수가 `null`을 돌려주면 키를 지워 주기도 해서 `(x, y) -> x + y == 0 ? null : x + y`로 써도 된다. `Integer` 상자끼리 `==`로 비교하는 실수는 여기서는 없지만, `cnt.get(g) == cnt.get(h)`처럼 두 값을 비교할 때는 128 이상에서 틀린다.
- 종류 번호가 0 이상 n 미만이라는 제약을 쓰면 해시맵을 배열로 바꿀 수 있다. 바로 아래에서 본다.

## 종류 번호를 배열 칸으로 쓰기

문제의 제약에 과일 종류 번호가 0 이상 n 미만이라고 되어 있다. 그렇다면 종류 번호를 그대로 배열 인덱스로 쓸 수 있다. 길이 n 배열 `cnt`에 종류별 개수를 두고, `size` 대신 "개수가 0이 아닌 종류 수" `kinds`를 따로 센다.

```js
function totalFruitArray(fruits) {
  const cnt = new Int32Array(fruits.length); // 종류 번호가 0 이상 n 미만
  let kinds = 0, l = 0, best = 0;
  for (let r = 0; r < fruits.length; r++) {
    if (cnt[fruits[r]]++ === 0) kinds++;      // 0에서 1이 되면 새 종류
    while (kinds > 2) {
      if (--cnt[fruits[l++]] === 0) kinds--;  // 1에서 0이 되면 종류가 빠진다
    }
    best = Math.max(best, r - l + 1);
  }
  return best;
}
```

`kinds`는 개수가 0에서 1로 갈 때만 늘고, 1에서 0으로 갈 때만 준다. 해시맵에서 "0이 되면 지운다"를 잊으면 무한 루프가 났는데, 배열에서는 그 일을 이 두 줄이 대신한다. 아래 측정과 같은 입력에서 5.9ms로 해시맵 창(7.8ms)보다 조금 빨랐다. 대신 공간이 O(n)으로 커진다. 해시맵 창은 종류가 많아야 셋이라 공간이 O(1)이었으니, 속도와 메모리를 맞바꾼 셈이다. 종류 번호에 범위 제약이 없거나 문자열이면 이 방법은 쓸 수 없다.

## 바구니가 엉키는 코드

개수가 0이 된 종류를 해시맵에서 지우지 않으면 끝나지 않는다.

```js
while (cnt.size > 2) {
  const f = fruits[l++];
  cnt.set(f, cnt.get(f) - 1); // 0이 돼도 남는다
}
```

`[1, 2, 1, 3, 3]`에 넣으면 3번 칸에서 영영 빠져나오지 못한다. 2의 개수가 0이 돼도 키가 남아 `size`가 3에서 내려가지 않으니 `l`이 배열 끝을 넘어서까지 계속 간다. 끝을 넘으면 `fruits[l]`이 `undefined`라 `undefined` 키까지 생긴다. 무한 루프로 시간 초과가 나면 이 줄부터 의심한다.

변수 네 개 풀이에서 새 종류가 오면 창을 무조건 2로 되돌리는 코드도 흔하다. "바로 앞 과일 하나와 새 과일"만 남는다고 착각한 것이다.

```js
if (f === a || f === b) cur++;
else cur = 2; // 바로 앞 과일 하나 + 새 과일이라고 가정
```

`[1, 2, 2, 2, 3, 3]`에서 4가 나온다. 정답은 5(`2 2 2 3 3`)다. 3이 들어올 때 살아남는 건 앞의 2 하나가 아니라 이어진 2 세 개다. 덩어리 길이 `runB`가 필요한 이유다. 첫 과일에서도 문제인데, `[5]`처럼 하나뿐이면 창 길이 2라는 있을 수 없는 답이 나온다.

연속이라는 조건을 놓치고 전체에서 가장 많은 두 종류의 개수를 더하는 풀이도 있다.

```js
const v = [...cnt.values()].sort((x, y) => y - x); // 전체 개수 내림차순
return (v[0] ?? 0) + (v[1] ?? 0);
```

`[1, 2, 3, 1, 2]`에서 4가 나오지만, 1과 2가 이어진 구간은 길이 2가 최대다. 시작점을 고르고 오른쪽으로 가며 "멈춘다"는 문장이 연속 구간을 뜻한다는 걸 놓치면 이렇게 된다.

마지막으로, 창 길이를 `r - l`로 재면 `[5]`에서 0이 나온다. 닫힌 구간 `[l, r]`의 길이는 `r - l + 1`이다.

## 바구니 수와 조건을 바꾸면

### 바구니가 K개라면 (LeetCode 340, 프리미엄 문제)

해시맵 창의 `2`를 `k`로 바꾸면 끝이다. 문자열에서 서로 다른 글자가 많아야 k개인 가장 긴 부분 문자열을 구하는 340번 Longest Substring with At Most K Distinct Characters가 정확히 이 모양이고, k = 2로 고정한 159번 Longest Substring with At Most Two Distinct Characters(프리미엄 문제)는 이 문제를 문자열로 바꾼 것이다. 시간은 O(n)으로 그대로이고, 공간은 O(k)가 된다. 변수 네 개 풀이는 K가 3만 돼도 성립하지 않고, 마지막 위치 풀이는 "가장 앞 위치 찾기"가 O(k)가 되어 O(nk)로 느려진다. K가 크면 해시맵 창이 맞다.

```js
function atMostKDistinct(s, k) {
  const cnt = new Map();
  let l = 0, best = 0;
  for (let r = 0; r < s.length; r++) {
    cnt.set(s[r], (cnt.get(s[r]) ?? 0) + 1);
    while (cnt.size > k) { // 바구니 수만 k로 바뀌었다
      const c = s[l++];
      cnt.set(c, cnt.get(c) - 1);
      if (cnt.get(c) === 0) cnt.delete(c);
    }
    best = Math.max(best, r - l + 1);
  }
  return best;
}
console.log(atMostKDistinct("eceba", 2), atMostKDistinct("aabbcc", 1), atMostKDistinct("aabbcc", 3), atMostKDistinct("abaccc", 2));
```

```text
3 2 6 4
```

`"eceba"`에서 k = 2면 `"ece"`, `"abaccc"`에서 k = 2면 `"accc"`다. 과일 문제의 배열이 문자열로 바뀌었을 뿐 코드는 그대로다. k = 0이면 `while`이 매번 창을 비워 0이 나온다. 면접에서 k = 0을 물으면 이 동작을 말하면 된다.

### 종류가 정확히 2개인 구간만 친다면

종류가 하나뿐인 구간(`[4, 4, 4, 4]`)은 빼라고 하면, 창의 조건을 그대로 두고 답을 잴 때 `cnt.size === 2`인 경우만 기록한다. 가장 긴 것을 구하는 문제라 이 정도로 충분하다. 개수를 세라고 하면 사정이 달라진다. 정확히 K개인 부분 배열의 개수(992번)는 "많아야 K개 − 많아야 K − 1개"로 구하는데, 그 이유와 코드는 [슬라이딩 윈도 패턴](/posts/sliding-window-pattern)의 "정확히 K개는 많아야 K개 둘의 차로"에 있다.

### 어디서 어디까지 땄는지 돌려 달라면

해시맵 창에서 `best`를 갱신할 때 `l`과 `r`도 같이 적어 두면 된다. 같은 길이가 여러 개면 처음 것(`>`로 비교)인지 마지막 것(`>=`)인지 면접관에게 물어본다. 줄어들지 않는 창은 마지막 창이 가짜일 수 있으니, 길이가 커지는 순간의 위치를 따로 적어야 한다는 점을 다시 짚는다.

### 나무 줄이 끝없이 이어진다면

과일이 스트림으로 하나씩 온다면 해시맵 창은 `l`이 가리키는 옛 과일을 다시 봐야 해서 창 안의 과일을 버퍼에 들고 있어야 한다. 창이 길면 메모리가 많이 든다. 변수 네 개 풀이는 지난 과일을 다시 볼 일이 없어서 메모리 O(1)로 스트림에 그대로 쓸 수 있다. 바구니 두 개라는 조건이 실제로 쓸모를 보이는 경우다.

### 오른쪽으로만 가지 않아도 된다면

시작한 나무에서 왼쪽으로 가도 된다고 바꿔도 답은 같다. 어느 방향으로 걷든 딴 나무들은 결국 이어진 구간이고, 같은 구간을 오른쪽 끝에서 왼쪽으로 걸은 것뿐이다. 이런 질문은 "조건이 바뀐 척하지만 같은 문제인가"를 보려는 것이라, 구간이라는 본질이 그대로인지 먼저 말하면 된다. 반대로 걷다가 나무를 건너뛸 수 있다고 하면 연속이 깨지니 창이 아니다. 이때는 종류별 전체 개수를 세서 가장 많은 두 종류를 더하는, 위에서 틀린 코드로 본 풀이가 오히려 정답이 된다.

비슷한 연습으로는 같은 묶음의 [Longest Substring Without Repeating Characters](/posts/leetcode-longest-substring-without-repeating)(조건이 "중복 0개"), [Max Consecutive Ones III](/posts/leetcode-max-consecutive-ones-iii)(조건이 "0이 k개 이하"), [Permutation in String](/posts/leetcode-permutation-in-string)(길이가 고정된 창)이 있다.

## 면접에서 나올 만한 질문

### 이 문제를 한 문장으로 바꾸면 무엇인가요?

서로 다른 값이 많아야 두 개인 가장 긴 연속 부분 배열의 길이를 구하는 문제다. 시작점에서 오른쪽으로 쭉 간다는 건 연속 구간, 바구니 두 개에 한 종류씩은 종류 수 2개 이하, 딴 과일 수는 구간 길이다. 이렇게 바꾸면 가장 긴 가변 창 문제가 된다.

### 왜 슬라이딩 윈도가 맞나요?

시작점을 오른쪽으로 옮기면 구간에서 앞쪽 과일이 빠질 뿐이라 종류가 늘 수 없다. 그래서 멈추는 자리가 왼쪽으로 돌아가지 않고, 두 포인터가 한 방향으로만 움직여도 모든 후보를 놓치지 않는다. 각 포인터가 많아야 n번 움직이니 O(n)이다.

### 해시맵에서 개수가 0이 된 키를 지워야 하는 이유는요?

`size`를 종류 수로 쓰기 때문이다. 지우지 않으면 빠진 종류가 계속 세어져 `size`가 3에서 내려가지 않고, 줄이는 `while`이 끝나지 않는다. Python이면 `len(cnt)`, Java면 `cnt.size()`도 같은 문제다.

### 공간을 더 줄일 수 있나요?

바구니가 두 개로 고정이면 해시맵 없이 마지막 종류, 다른 종류, 마지막 덩어리 길이, 창 길이 네 값으로 된다. 새 종류가 오면 바로 앞에서 이어지던 같은 종류의 덩어리만 살아남으니 창 길이가 덩어리 길이 + 1이 된다. 다만 바구니가 K개로 늘면 이 성질이 깨져서 해시맵 창으로 돌아가야 한다.

### 창을 줄이지 않는 풀이가 맞는 이유는요?

답이 최대 길이 하나라서 한 번 달성한 길이보다 짧은 창은 볼 필요가 없다. 조건이 깨지면 길이를 유지한 채 한 칸 밀고, 조건을 만족할 때만 길이가 커진다. 그래서 마지막 창 길이가 지나온 최대 길이이고, 실제로 만족한 창의 길이다. 중간 창이 조건을 어겨도 답에는 영향이 없다.

### 바구니가 K개라면 복잡도는 어떻게 되나요?

해시맵 창은 조건만 `size > k`로 바꾸면 되고 시간 O(n), 공간 O(k)다. 마지막 위치로 건너뛰는 풀이는 버릴 종류를 찾느라 매번 k개를 훑어 O(nk)가 된다. K가 크면 해시맵 창이 낫다.

### 해시맵과 길이 n 배열 중 무엇을 쓰나요?

종류 번호가 0 이상 n 미만으로 보장되면 배열이 해시 비용이 없어 조금 빠르다. 대신 공간이 O(n)이고, 개수가 0에서 1, 1에서 0으로 바뀔 때 종류 수를 직접 고쳐야 한다. 해시맵은 종류가 많아야 셋이라 공간이 O(1)이고 값의 범위를 가리지 않는다. 제약을 확인할 수 없으면 해시맵이 안전하다.
