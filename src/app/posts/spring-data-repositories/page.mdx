스프링 부트 프로젝트에 처음 들어갔을 때 이 코드를 보고 한참 찾았다.

```java
interface OrderRepository extends JpaRepository<Order, Long> {
  List<Order> findByStatusAndAmountGreaterThanOrderByIdDesc(String status, BigDecimal amount);
}
```

인터페이스만 있고 구현 클래스가 어디에도 없다. 그런데 서비스에서 주입받아 부르면 SQL이 나가고 결과가 온다. 메서드 이름에 오타를 내면 애플리케이션이 아예 뜨지 않는다. 처음엔 마법처럼 보이지만, 무엇이 언제 만들어지는지 알면 이 추상화가 어디서 새는지도 보인다.

이 글은 Spring Data의 리포지토리 모델을 따라간다. 인터페이스 뒤에서 구현이 생기는 과정, 메서드 이름으로 쿼리를 만드는 규칙과 한계, `@Query`, 페이징의 Page와 Slice, 필요한 열만 읽는 프로젝션을 본 다음, 같은 리포지토리 모델이 Spring Data JDBC와 MongoDB에서 어떻게 다르게 움직이는지 비교한다. 영속성 컨텍스트와 더티 체킹은 [JPA 영속성 컨텍스트 글](/posts/jpa-persistence-context)에서, 연관관계 매핑은 [JPA 연관관계 글](/posts/jpa-entity-relationships)에서, 리포지토리가 등록되는 자동 구성 자체는 [자동 구성 글](/posts/spring-boot-auto-configuration)에서 다뤘다. 실행 결과는 Spring Boot 4.1.1(Spring Data JPA·JDBC 4.1.1, Hibernate 7.4), Java 21, H2 메모리 DB에서 직접 돌린 것이다.

## 예제 테이블


```java
@Entity

class Order {
```

## 인터페이스 뒤에는 프록시가 서 있다

주입받은 리포지토리가 실제로 무엇인지 찍어 봤다.

```java
System.out.println("proxy = " + repo.getClass().getName());
System.out.println("target = " + ((Advised) repo).getTargetSource().getTarget().getClass().getName());
System.out.println("interfaces = " + Arrays.toString(repo.getClass().getInterfaces()));
```

```text
proxy = lab.$Proxy105
target = org.springframework.data.jpa.repository.support.SimpleJpaRepository
interfaces = [interface lab.OrderRepository, interface org.springframework.data.repository.Repository, interface org.springframework.transaction.interceptor.TransactionalProxy, interface org.springframework.aop.framework.Advised, interface org.springframework.core.DecoratingProxy]
```

`$Proxy105`는 JDK 동적 프록시다. 내가 만든 `OrderRepository` 인터페이스를 구현한 클래스를 런타임에 만든 것이다. 그 프록시 뒤의 진짜 대상은 `SimpleJpaRepository`라는 Spring Data JPA의 기본 구현이다. `save`, `findById`, `findAll`, `delete` 같은 공통 메서드는 이 클래스에 이미 있다. `TransactionalProxy`가 붙어 있다는 건 이 프록시가 트랜잭션도 건다는 뜻이다. `SimpleJpaRepository`의 메서드에는 클래스 수준으로 `@Transactional(readOnly = true)`가, 쓰기 메서드에는 따로 `@Transactional`이 붙어 있다.

그럼 `findByStatusAndAmountGreaterThan...` 같은 내 메서드는 어디서 처리될까. 애플리케이션이 뜰 때 리포지토리 팩토리가 인터페이스의 메서드를 하나씩 훑으며 "이 메서드는 어떻게 실행할지"를 미리 정해 둔다. 공통 메서드면 `SimpleJpaRepository`로 넘기고, 이름 규칙을 따르는 메서드면 이름을 파싱해 쿼리를 만들어 두고, `@Query`가 붙어 있으면 그 문자열을 쿼리로 준비한다.

마지막 단계의 `save` 판단은 실수가 자주 나는 곳이다. `SimpleJpaRepository.save`는 엔티티가 새것이면 `persist`, 아니면 `merge`를 부른다. 기본 판단 기준은 id가 null인지다. id를 직접 넣는 엔티티(UUID를 애플리케이션에서 만드는 경우)는 늘 "새것이 아님"으로 보여서 `merge`로 가고, `merge`는 먼저 SELECT로 DB를 확인한다. INSERT 한 번이면 될 일에 SELECT가 하나씩 붙는다. 이럴 때는 `Persistable`을 구현해 `isNew()`를 직접 알려 주거나 `@Version` 필드를 둔다.

## 메서드 이름이 쿼리가 된다

이름 규칙으로 만드는 쿼리를 파생 쿼리(derived query)라고 한다. `find…By`, `count…By`, `exists…By`, `delete…By`로 시작하고, `By` 뒤는 속성 이름과 조건 키워드를 `And`, `Or`로 잇고, `OrderBy`로 정렬을 붙인다.

```java
List<Order> findByStatusAndAmountGreaterThanOrderByIdDesc(String status, BigDecimal amount);
long countByStatus(String status);
boolean existsByCustomer(String customer);
List<Order> findTop2ByStatusOrderByAmountDesc(String status);
```

각각 실제로 나간 SQL과 결과다.

```text
select o1_0.id,o1_0.amount,o1_0.customer,o1_0.status from orders o1_0 where o1_0.status=? and o1_0.amount>? order by o1_0.id desc
[5, 2, 1]
select count(o1_0.id) from orders o1_0 where o1_0.status=?
select o1_0.id from orders o1_0 where o1_0.customer=? fetch first ? rows only
4 true
select o1_0.id,o1_0.amount,o1_0.customer,o1_0.status from orders o1_0 where o1_0.status=? order by o1_0.amount desc fetch first ? rows only
[5, 2]
```

`existsByCustomer`가 `count`가 아니라 id 하나만 `fetch first ? rows only`로 읽는 걸 볼 만하다. 존재 여부만 궁금할 때 `countBy… > 0`으로 쓰면 맞는 행을 다 세지만, `existsBy`는 하나를 찾으면 멈춘다. 큰 테이블에서 차이가 크다. `Top2`도 `fetch first ? rows only`(PostgreSQL에서는 `fetch first`나 `limit`, MySQL에서는 `limit`)로 바뀌었다.

이름이 틀리면 애플리케이션이 뜨지 않는다. `customer`를 `custmer`로 잘못 쓴 메서드를 하나 넣고 실행했다.

```java
List<Order> findByStatusAndCustmer(String status, String customer);
```

```text
Caused by: org.springframework.data.repository.query.QueryCreationException: Cannot create query for method [OrderRepository.findByStatusAndCustmer(java.lang.String,java.lang.String)]; No property 'custmer' found for type 'Order'; Did you mean 'customer'
Caused by: org.springframework.data.core.PropertyReferenceException: No property 'custmer' found for type 'Order'; Did you mean 'customer'
```

기동 시점에 메서드를 다 파싱하기 때문에 생기는 장점이다. 런타임에 그 메서드를 처음 부를 때가 아니라 배포 직후 바로 터진다. 테스트에서 컨텍스트만 띄워도 잡힌다.

이름을 쿼리로 바꾸는 규칙이 어떻게 생겼는지 작게 만들어 보면 감이 온다. 아래 함수는 메서드 이름을 받아 `동사: where … order by … limit …` 꼴의 문자열을 돌려준다. 접미사(`GreaterThan`, `IsNull`, `Not` 등)는 긴 것부터 확인해야 `GreaterThanEqual`이 `GreaterThan`으로 잘못 잘리지 않는다. 규칙에 맞지 않는 이름(예: `save`)이면 `null`을 돌려준다.

  const OPS = [["GreaterThanEqual", ">= ?"], ["LessThanEqual", "<= ?"], ["GreaterThan", "> ?"], ["LessThan", "< ?"], ["IsNull", "is null"], ["Containing", "like ?"], ["In", "in (?)"], ["Not", "<> ?"]];

  if (!m) return null;
  const [, verb, top, rest] = m;
  const [wherePart, orderPart] = rest.split("OrderBy");
  const lower = (s) => s[0].toLowerCase() + s.slice(1);
  const conds = wherePart.split("And").map((p) => {

## 이름이 문장이 되면 @Query로 옮긴다

파생 쿼리는 조건이 두세 개일 때까지가 좋다. `findByStatusAndCustomerAndAmountGreaterThanAndCreatedAtBetweenOrderByCreatedAtDesc`처럼 이름이 문장이 되면 읽기도 어렵고, 조인이나 집계는 아예 표현이 안 된다. 그때는 `@Query`로 JPQL을 직접 쓴다.

```java
@Query("""
    select new lab.CustomerTotal(o.customer, sum(o.amount))
    from Order o where o.status = :status
    group by o.customer order by o.customer""")
List<CustomerTotal> totals(@Param("status") String status);

record CustomerTotal(String customer, BigDecimal total) {}
```

```text
select o1_0.customer,sum(o1_0.amount) from orders o1_0 where o1_0.status=? group by o1_0.customer order by o1_0.customer
[CustomerTotal[customer=kim, total=20000.00], CustomerTotal[customer=lee, total=75000.00]]
```

`select new`로 결과를 레코드에 바로 담았다. 엔티티가 아니라서 영속성 컨텍스트에 올라가지 않고, 더티 체킹 대상도 아니다. 화면에 보여 줄 집계 결과는 이렇게 받는 편이 가볍다. JPQL은 앱이 뜰 때 문법과 엔티티 이름을 검사해서, 오타가 있으면 파생 쿼리처럼 기동이 멈춘다. `nativeQuery = true`로 쓴 SQL은 DB에 보내 봐야 틀린 걸 안다.

삭제는 특히 조심해야 한다. "이 상태인 주문 지우기"를 파생 쿼리(CANCELLED)와 `@Modifying` 쿼리(PENDING)로 비교했다.

```java
@Transactional long deleteByStatus(String status);

@Modifying @Transactional
@Query("delete from Order o where o.status = :status")
int bulkDeleteByStatus(@Param("status") String status);
```

```text
--- deleteBy
select o1_0.id,o1_0.amount,o1_0.customer,o1_0.status from orders o1_0 where o1_0.status=?
delete from orders where id=?
deleted=1

--- bulk delete
delete from orders o1_0 where o1_0.status=?
deleted=1
```

`deleteByStatus`는 맞는 행을 전부 엔티티로 읽은 다음 하나씩 `delete`를 보낸다. 엔티티마다 `@PreRemove` 콜백과 cascade를 지켜 주려는 동작이라 틀린 건 아니다. 다만 10만 건이면 SELECT 한 번에 DELETE 10만 번이다. `@Modifying` 쿼리는 DELETE 한 번으로 끝나지만 영속성 컨텍스트를 거치지 않는다. 이미 읽어 둔 엔티티는 지워진 줄 모르고 남아 있으니, 같은 트랜잭션에서 이어서 읽을 거라면 `@Modifying(clearAutomatically = true)`를 준다. 이 함정은 [영속성 컨텍스트 글](/posts/jpa-persistence-context)의 벌크 UPDATE 절과 같은 이야기다.

## Page와 Slice는 count 쿼리 하나 차이다

목록 API에 페이징을 붙일 때 반환 타입으로 `Page`와 `Slice` 중 하나를 고른다. 같은 조건, 같은 `PageRequest.of(0, 2, Sort.by("id"))`로 둘을 불렀다.

```java
Page<Order> findByStatus(String status, Pageable p);
Slice<Order> findSliceByStatus(String status, Pageable p);
```

```text
--- page
select o1_0.id,o1_0.amount,o1_0.customer,o1_0.status from orders o1_0 where o1_0.status=? order by o1_0.id fetch first ? rows only
binding parameter (1:VARCHAR) <- [PAID]
binding parameter (2:INTEGER) <- [2]
select count(o1_0.id) from orders o1_0 where o1_0.status=?
binding parameter (1:VARCHAR) <- [PAID]
page total=4 pages=2 content=[1, 2]

--- slice
select o1_0.id,o1_0.amount,o1_0.customer,o1_0.status from orders o1_0 where o1_0.status=? order by o1_0.id fetch first ? rows only
binding parameter (1:VARCHAR) <- [PAID]
binding parameter (2:INTEGER) <- [3]
slice hasNext=true content=[1, 2]
```

`Page`는 내용을 가져온 뒤 `count` 쿼리를 한 번 더 보내서 전체 개수(4)와 전체 페이지 수(2)를 안다. `Slice`는 count를 보내지 않는 대신 요청한 크기보다 하나 더(2가 아니라 3) 가져와 본다. 세 번째 행이 있으면 `hasNext=true`고, 화면에는 두 개만 돌려준다.

작은 테이블에서는 차이가 없다. 수천만 행 테이블에 복잡한 조건이 붙으면 `count`가 본 쿼리보다 느려지는 일이 흔하다. "더 보기" 버튼이나 무한 스크롤처럼 전체 페이지 수가 필요 없는 화면은 `Slice`면 충분하다. `Page`를 꼭 써야 하는데 조인 때문에 count가 무거우면 `@Query`에 `countQuery`를 따로 줘서 조인 없는 count를 쓰게 한다. 아주 깊은 페이지(offset 수십만)는 Page든 Slice든 offset 자체가 느리니 키셋 페이지네이션(`where id > :lastId`)으로 바꾼다. Spring Data 3.1부터는 `Window`와 `ScrollPosition`으로 키셋 스크롤을 리포지토리 수준에서 지원한다.

## 프로젝션: 필요한 열만 읽는다

목록 화면에 고객 이름과 금액만 보여 준다면 엔티티 전체를 읽을 이유가 없다. 반환 타입을 getter만 있는 인터페이스로 바꾸면 Spring Data가 그 속성만 SELECT한다.

```java
interface OrderSummary { String getCustomer(); BigDecimal getAmount(); }

List<OrderSummary> findByCustomer(String customer);
```

```text
select o1_0.customer,o1_0.amount from orders o1_0 where o1_0.customer=?
kim 12000.00
kim 8000.00
```

`id`와 `status`가 SELECT에서 빠졌다. 열이 수십 개인 엔티티나 큰 텍스트 열이 있는 테이블에서 효과가 크다. 이런 인터페이스 프로젝션(닫힌 프로젝션)은 열을 줄이지만, getter에 `@Value("#{target.customer + ' ' + target.status}")` 같은 SpEL을 쓰는 열린 프로젝션은 무엇이 필요한지 미리 알 수 없어서 엔티티 전체를 읽는다. 앞의 레코드처럼 클래스 기반 DTO 프로젝션도 가능하다. 반환 타입을 제네릭으로 두는 동적 프로젝션(`<T> List<T> findByCustomer(String c, Class<T> type)`)도 있다.

## Spring Data JDBC: 같은 인터페이스, 다른 철학

Spring Data JDBC는 같은 리포지토리 모델을 JPA 없이 구현한다. 인터페이스 모양은 거의 같다.

```java
record PurchaseOrder(@Id Long id, String customer, String status,
                     @MappedCollection(idColumn = "PURCHASE_ORDER") Set<OrderLine> lines) {}
record OrderLine(String product, int qty) {}

interface PurchaseOrderRepository extends ListCrudRepository<PurchaseOrder, Long> {
  List<PurchaseOrder> findByStatus(String status);
  @Query("select count(*) from order_line")
  long countLines();
}
```

```sql
-- 스키마는 schema.sql로 직접 만든다 (JDBC 모듈은 DDL을 만들어 주지 않는다)
create table purchase_order (id bigint generated by default as identity primary key, customer varchar(50), status varchar(20));
create table order_line (purchase_order bigint not null references purchase_order(id), product varchar(50), qty int);
```

차이는 모델에 있다. JDBC 모듈에는 영속성 컨텍스트가 없다. 1차 캐시도, 더티 체킹도, 지연 로딩도 없다. 대신 DDD의 애그리거트 개념을 그대로 따른다. 주문(`PurchaseOrder`)이 애그리거트 루트고 주문 줄(`OrderLine`)은 루트에 딸린 값이다. 리포지토리는 루트에만 있고, 루트를 저장하면 딸린 것까지 통째로 저장하고, 읽으면 통째로 읽는다. 레코드(불변 객체)를 엔티티로 쓸 수 있는 것도 이 때문이다. JPA는 프록시와 더티 체킹을 위해 기본 생성자와 바뀔 수 있는 필드가 필요하다. 애그리거트의 경계를 나누는 법은 [DDD 전술 패턴 글](/posts/ddd-tactical-patterns)에서 다뤘다.

주문 줄 두 개짜리 주문을 저장하고, 다시 읽고, 줄 하나의 수량만 바꿔 저장했다. JdbcTemplate 로그를 켜 두었다.

```text
--- save aggregate
INSERT INTO "PURCHASE_ORDER" ("CUSTOMER", "STATUS") VALUES (?, ?)
INSERT INTO "ORDER_LINE" ("PURCHASE_ORDER", "PRODUCT", "QTY") VALUES (?, ?, ?)

--- findById
SELECT "PURCHASE_ORDER"."ID" AS "ID", "PURCHASE_ORDER"."STATUS" AS "STATUS", "PURCHASE_ORDER"."CUSTOMER" AS "CUSTOMER" FROM "PURCHASE_ORDER" WHERE "PURCHASE_ORDER"."ID" = ?
SELECT "ORDER_LINE"."QTY" AS "QTY", "ORDER_LINE"."PRODUCT" AS "PRODUCT" FROM "ORDER_LINE" WHERE "ORDER_LINE"."PURCHASE_ORDER" = ?
PurchaseOrder[id=1, customer=kim, status=PAID, lines=[OrderLine[product=note, qty=1], OrderLine[product=pen, qty=2]]]

--- change one line qty and save
UPDATE "PURCHASE_ORDER" SET "CUSTOMER" = ?, "STATUS" = ? WHERE "PURCHASE_ORDER"."ID" = ?
DELETE FROM "ORDER_LINE" WHERE "ORDER_LINE"."PURCHASE_ORDER" = ?
INSERT INTO "ORDER_LINE" ("PURCHASE_ORDER", "PRODUCT", "QTY") VALUES (?, ?, ?)

--- derived
SELECT "PURCHASE_ORDER"."ID" AS "ID", ... FROM "PURCHASE_ORDER" WHERE "PURCHASE_ORDER"."STATUS" = ?
SELECT "ORDER_LINE"."QTY" AS "QTY", ... FROM "ORDER_LINE" WHERE "ORDER_LINE"."PURCHASE_ORDER" = ?
```

(줄 INSERT는 배치로 한 번 실행됐고 로그 줄 일부는 생략했다.) 세 가지가 보인다.

첫째, 줄 하나의 수량만 바꿨는데 주문 줄을 전부 DELETE하고 다시 INSERT했다. 무엇이 바뀌었는지 추적하지 않으니 "루트를 저장하면 딸린 것을 통째로 갈아 끼운다"가 가장 단순하고 올바른 방법이다. 줄이 몇 개인 주문이면 아무 문제 없다. 줄이 수천 개인 애그리거트라면 경계를 잘못 잡았다는 신호다.

둘째, `findById`가 루트와 줄을 쿼리 두 번으로 읽었다. 지연 로딩이 없으니 읽을 때 다 읽는다. `findByStatus`로 주문 100건을 읽으면 주문 줄 SELECT가 100번 더 나간다. JPA의 N+1과 같은 모양이지만, 여기서는 지연 로딩 프록시 때문이 아니라 애그리거트를 다 채우는 규칙 때문이다. 목록 화면은 리포지토리 대신 `@Query`나 `JdbcClient`로 필요한 열만 조인해서 읽는다. 3.2부터는 단순한 애그리거트를 쿼리 하나로 읽는 단일 쿼리 로딩 옵션이 생겼지만 기본으로 켜져 있지 않다.

셋째, 식별자를 큰따옴표로 감싼다. 처음에 `@MappedCollection(idColumn = "purchase_order")`로 소문자를 줬더니 H2에서 `Column "purchase_order" not found`로 실패했다. H2는 따옴표 없는 이름을 대문자로 저장하는데, 따옴표로 감싼 소문자는 다른 이름이 된다. PostgreSQL은 반대로 따옴표 없는 이름을 소문자로 저장해서 대소문자 문제가 DB마다 다르게 터진다. 이름을 DB의 규칙에 맞춰 쓰거나 `NamingStrategy`를 정해 둔다.

그리고 JDBC 모듈에서는 `save()`를 부르지 않으면 아무것도 저장되지 않는다. [영속성 컨텍스트 글](/posts/jpa-persistence-context) 첫 장면의 "save를 안 했는데 UPDATE가 나간다"가 여기서는 일어나지 않는다. 마법이 적은 대신 코드에 쓴 그대로 동작한다.

## Spring Data MongoDB: 같은 이름, 문서 쿼리

Spring Data MongoDB도 같은 리포지토리 모델을 쓴다. 이 글을 쓴 환경에서는 MongoDB 서버를 띄울 수 없어서 출력 없이 모양만 본다.

```java
@Document("orders")
record OrderDoc(@Id String id, String customer, String status, long amount, List<Line> lines) {}
record Line(String product, int qty) {}

interface OrderDocRepository extends MongoRepository<OrderDoc, String> {
  List<OrderDoc> findByStatusAndAmountGreaterThan(String status, long amount);

  @Query("{ 'lines.product': ?0 }")
  List<OrderDoc> findHavingProduct(String product);
}
```

메서드 이름 규칙은 같지만 결과는 SQL이 아니라 MongoDB 쿼리 문서다. `findByStatusAndAmountGreaterThan`은 `{ "status": "PAID", "amount": { "$gt": 10000 } }` 꼴의 필터가 된다. `@Query`에는 JSON 필터를 쓰고 `?0`이 첫 번째 인자다. 실제로 나가는 쿼리는 `logging.level.org.springframework.data.mongodb.core.MongoTemplate=debug`로 본다.

모델로 보면 MongoDB는 Spring Data JDBC와 가깝다. 주문 줄을 별도 컬렉션이 아니라 주문 문서 안에 배열로 넣으니, 애그리거트 하나가 문서 하나다. 읽을 때 한 번에 오고 지연 로딩도 없다. 다른 문서를 참조하는 `@DBRef`나 `@DocumentReference`는 조인이 아니라 추가 조회라서 목록에서 쓰면 N+1이 된다.

다른 점도 분명하다. 여러 문서에 걸친 트랜잭션은 레플리카 셋이나 샤드 클러스터에서만 되고, 스프링 부트는 `MongoTransactionManager`를 자동으로 등록하지 않아서 직접 빈을 만들어야 `@Transactional`이 몽고 작업을 묶는다. 인덱스 없이 파생 쿼리를 늘리면 컬렉션 전체 스캔이 된다. 문서 설계와 인덱스는 [MongoDB 문서 모델 글](/posts/mongodb-document-model)과 [MongoDB 인덱스 글](/posts/mongodb-indexes-explain)에서 이어진다.

JPA는 엔티티 그래프가 복잡하고, 한 트랜잭션에서 여러 엔티티를 읽고 고치는 일이 많은 도메인에서 강하다. 더티 체킹과 1차 캐시가 코드를 줄여 준다. 대신 영속성 컨텍스트의 규칙(flush 시점, 지연 로딩, merge)을 팀이 알아야 하고, 모르면 앞에서 본 `deleteBy`나 `merge`의 숨은 SELECT 같은 일을 겪는다.

Spring Data JDBC는 애그리거트 경계가 분명하고, 저장한 그대로 SQL이 나가는 예측 가능성을 원할 때 맞다. 레코드를 엔티티로 쓸 수 있고 시작이 가볍다. 대신 연관관계를 탐색하는 편의는 없어서, 다른 애그리거트는 id로만 참조하고 조회는 직접 SQL을 쓰는 습관이 필요하다.

MongoDB는 데이터가 원래 문서 모양이고(주문과 줄, 게시글과 댓글 일부), 스키마가 자주 바뀌거나 필드가 제각각인 경우에 맞다. RDB의 조인과 여러 행 트랜잭션에 기대는 설계를 그대로 옮기면 고생한다.

규모로 보면 이렇다. 작은 서비스에서는 팀이 익숙한 JPA로 시작해도 문제가 거의 없다. 테이블이 커지면서 목록 화면이 느려지기 시작하면(count 쿼리가 수백 ms, 엔티티 전체 로딩으로 메모리가 튄다) 그 화면만 프로젝션과 Slice, 직접 쓴 쿼리로 옮긴다. 리포지토리 하나에 모든 조회를 몰아넣지 않고, 쓰기는 애그리거트 리포지토리로, 읽기는 화면에 맞는 쿼리로 나누는 게 다음 단계다.

## 현장에서 리포지토리가 새는 순간

리포지토리 추상화가 편한 만큼, 숫자가 커질 때 새는 곳도 정해져 있다.

목록 API가 느린데 쿼리 하나는 빠르다면 count를 본다. SQL 로그에 같은 조건의 `select count(...)`가 따라 나가고 그게 본 쿼리보다 느리면 `Slice`나 `countQuery`로 바꾼다.

배치 작업이 이상하게 오래 걸리면 `deleteBy…`와 `saveAll`을 의심한다. 로그에 `delete from orders where id=?`가 행 수만큼 찍히면 `@Modifying` 벌크 쿼리로 바꾼다. `IDENTITY` 전략 엔티티의 `saveAll`은 JDBC 배치가 안 되는 문제가 있는데, [영속성 컨텍스트 글](/posts/jpa-persistence-context)의 쓰기 지연 절에서 다뤘다.

INSERT 하나에 SELECT가 하나씩 붙어 있으면 id를 직접 넣는 엔티티의 `save`가 `merge`로 가는 경우다. `Persistable.isNew()`를 구현한다.

배포 직후 `QueryCreationException`으로 기동이 실패하면 엔티티 필드 이름을 바꾸고 리포지토리 메서드 이름을 그대로 둔 경우다. 리팩터링 도구가 메서드 이름 속 속성명까지는 바꿔 주지 않는다. `@DataJpaTest`처럼 리포지토리 계층만 띄우는 테스트를 CI에 두면 배포 전에 잡힌다([스프링 부트 테스트 글](/posts/spring-boot-testing)).

## 이름 뒤의 실제 쿼리를 본다

Spring Data 리포지토리는 인터페이스와 메서드 이름이라는 같은 말투로 JPA, JDBC, MongoDB를 다루게 해 준다. 그 아래에서 프록시는 기동 시점에 메서드마다 쿼리를 준비하고, 모듈마다 그 쿼리를 다른 방식으로 실행한다. 그래서 리포지토리 메서드를 하나 추가할 때마다 SQL이나 쿼리 로그로 실제로 무엇이 나가는지 한 번은 확인한다. count가 붙는지, 하나씩 지우는지, 열을 다 읽는지, 딸린 줄을 다시 읽는지. 이름은 같아도 나가는 쿼리는 다르다.

## 면접에서 나올 만한 질문

### Spring Data 리포지토리는 인터페이스만 있는데 어떻게 동작하나요?

애플리케이션이 뜰 때 리포지토리 팩토리가 그 인터페이스를 구현한 JDK 동적 프록시를 만든다. 프록시 뒤에는 `SimpleJpaRepository` 같은 기본 구현이 있어서 `save`, `findById` 같은 공통 메서드를 처리하고, 이름 규칙 메서드와 `@Query` 메서드는 기동 시점에 쿼리로 미리 준비해 둔다. 트랜잭션과 예외 변환도 이 프록시가 건다.

### 파생 쿼리 메서드 이름에 오타가 있으면 언제 알 수 있나요?

애플리케이션 기동 시점이다. 팩토리가 메서드 이름을 파싱해서 엔티티 속성과 맞춰 보고, 없는 속성이면 `QueryCreationException`과 "Did you mean" 메시지로 컨텍스트 생성을 멈춘다. JPQL `@Query`도 기동 때 검사되지만 `nativeQuery`는 실행해 봐야 틀린 걸 안다. 그래서 리포지토리 계층만 띄우는 테스트로 배포 전에 잡는다.

### Page와 Slice는 어떻게 다르고 언제 무엇을 쓰나요?

`Page`는 내용 쿼리 뒤에 count 쿼리를 한 번 더 보내 전체 개수와 페이지 수를 알려 준다. `Slice`는 count 없이 요청한 크기보다 하나 더 가져와서 다음이 있는지만 안다. 실제 로그에서 크기 2를 요청하면 Slice는 3을 바인딩했다. 전체 페이지 수가 필요 없는 무한 스크롤이나 더 보기는 Slice로 충분하고, 큰 테이블에서 count가 느릴 때 특히 효과가 있다.

### deleteBy 파생 메서드와 @Modifying 삭제 쿼리는 어떻게 다른가요?

`deleteBy…`는 맞는 행을 엔티티로 전부 읽은 뒤 하나씩 DELETE를 보내서, 콜백과 cascade를 지키는 대신 행 수만큼 쿼리가 나간다. `@Modifying` JPQL은 DELETE 한 번으로 끝나지만 영속성 컨텍스트를 거치지 않아 이미 읽은 엔티티가 남아 있을 수 있다. 대량 삭제는 벌크 쿼리를 쓰고, 이어서 읽을 거면 `clearAutomatically`를 켠다.

### 인터페이스 프로젝션은 성능에 어떤 도움이 되나요?

getter만 있는 인터페이스를 반환 타입으로 쓰면 그 속성의 열만 SELECT한다. 실제로 `customer`와 `amount`만 있는 프로젝션은 두 열만 읽었다. 엔티티로 올라가지 않으니 영속성 컨텍스트 비용도 없다. 다만 SpEL을 쓰는 열린 프로젝션은 필요한 열을 미리 알 수 없어 엔티티 전체를 읽는다.

### Spring Data JDBC는 JPA와 무엇이 다른가요?

영속성 컨텍스트가 없어서 1차 캐시, 더티 체킹, 지연 로딩이 없다. 애그리거트 루트 단위로 저장하고 읽으며, 루트를 저장하면 딸린 엔티티를 전부 지우고 다시 넣는다. `save()`를 부르지 않으면 아무것도 바뀌지 않아 동작이 예측 가능하고 불변 레코드를 엔티티로 쓸 수 있다. 대신 연관관계 탐색 편의가 없고, 목록 조회에서 딸린 컬렉션을 루트마다 따로 읽는 N+1이 생기니 조회는 직접 쿼리로 푼다.

### Spring Data MongoDB에서 트랜잭션을 쓰려면 무엇이 필요한가요?

여러 문서에 걸친 트랜잭션은 MongoDB가 레플리카 셋이나 샤드 클러스터로 떠 있어야 하고, 스프링 부트가 `MongoTransactionManager`를 자동 등록하지 않아서 빈을 직접 만들어야 한다. 그래야 `@Transactional`이 몽고 작업을 묶는다. 애초에 애그리거트를 문서 하나에 담으면 단일 문서 쓰기는 원자적이라 트랜잭션이 필요 없는 경우가 많다.
