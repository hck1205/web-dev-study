[LeetCode 704. Binary Search](https://leetcode.com/problems/binary-search/)는 Easy로 분류되지만 면접에서 자주 첫 문제로 나온다. 이분 탐색을 아는지 보려는 게 아니라, 경계 조건까지 한 번에 맞게 짜는지를 본다. 나도 처음에는 `while (lo < hi)`와 `while (lo <= hi)`를 기분에 따라 골랐고, 그러다 원소가 하나뿐인 배열에서 틀린 답을 냈다.

문제는 이렇다. 오름차순으로 정렬된 정수 배열 `nums`와 정수 `target`이 주어진다. `target`이 배열에 있으면 그 자리(인덱스)를, 없으면 `-1`을 돌려준다. 배열 안의 값은 모두 서로 다르다. 그리고 실행 시간이 O(log n)이어야 한다는 조건이 붙는다. 앞에서부터 하나씩 보는 O(n) 풀이도 통과는 하지만, 문제가 요구하는 답은 아니다.

배열 길이는 최대 10^4이고 값은 -10^4에서 10^4 사이다. 숫자가 작아서 이 문제 안에서는 정수 오버플로가 일어나지 않는다. 그래도 면접에서는 "배열이 20억 칸이면?"이 꼬리 질문으로 나오니 아래에서 같이 본다.

이분 탐색 자체의 원리(단조성, lower bound와 upper bound, 실수 범위)는 [이분 탐색 글](/posts/binary-search)에서 넓게 다뤘다. 이 글은 문제 하나를 놓고 풀이 다섯 가지를 느린 것부터 차례로 짜 보고, 각 풀이가 어디서 틀리는지 직접 돌려 본다. 실행 결과는 모두 Node.js 22, Python 3, OpenJDK에서 돌린 값이다.

## 여덟 칸에서 17을 손으로 찾아보기

예시 배열을 하나 정하고 끝까지 이걸로 간다.

```text
index   0   1   2   3   4   5   6   7
nums   -4   1   3   8  12  17  25  31
```

17을 찾는다. 앞에서부터 보면 -4, 1, 3, 8, 12를 지나 여섯 번째에 17을 만난다. 찾는 값이 31이면 여덟 번을 다 봐야 하고, 40처럼 없는 값이면 역시 여덟 번을 본 뒤에야 없다고 말할 수 있다.

이번엔 가운데부터 본다. 0번부터 7번 사이의 가운데는 3번이고 값은 8이다. 8은 17보다 작다. 배열이 오름차순이니 3번 왼쪽 칸들은 전부 8보다 작고, 당연히 17보다도 작다. 그래서 0~3번 네 칸을 한꺼번에 버린다. 남은 4~7번의 가운데는 5번이고 값이 17이다. 두 번 만에 찾았다.

없는 값 10도 해 보자. 3번(8)은 10보다 작으니 왼쪽을 버린다. 4~7번의 가운데 5번(17)은 10보다 크니 오른쪽을 버린다. 남은 건 4번(12) 하나인데 12도 10보다 크다. 이제 남은 칸이 없다. 세 번 보고 "없다"고 말할 수 있다.

손으로 해 보면 두 가지가 보인다. 하나는 한 번 볼 때마다 후보가 절반으로 준다는 것. 다른 하나는 "남은 후보가 어디서 어디까지인가"를 정확히 들고 있어야 한다는 것이다. 코드에서 틀리는 곳은 거의 다 두 번째다.

## 처음부터 끝까지 훑기

가장 먼저 떠오르는 풀이는 앞에서부터 하나씩 비교하는 것이다. 정렬돼 있다는 정보를 조금은 쓸 수 있다. 지금 칸의 값이 `target`보다 커지면 그 뒤는 더 크니 바로 멈춰도 된다.

```js
function search(nums, target) {
  for (let i = 0; i < nums.length; i++) {
    if (nums[i] === target) return i; // 찾았다
    if (nums[i] > target) return -1;  // 정렬돼 있으니 뒤는 더 크다. 더 볼 필요 없다
  }
  return -1; // 끝까지 갔는데 없다
}
```

JavaScript라면 `nums.indexOf(target)` 한 줄로도 같은 일을 한다. `indexOf`는 없으면 `-1`을 돌려주니 이 문제의 반환 형식과도 딱 맞는다. 다만 `indexOf`는 정렬 여부를 모르니 일찍 멈추지 않고 끝까지 본다.

시간은 O(n)이다. 최악의 경우(맨 끝 값이나 맨 끝보다 큰 값) 모든 칸을 본다. 일찍 멈추는 조건은 평균을 조금 줄일 뿐 최악을 바꾸지 못한다. 공간은 변수 몇 개라 O(1)이다.

길이가 10^4이면 이 풀이도 1ms 안에 끝난다. 그래서 LeetCode 채점은 통과한다. 하지만 문제는 O(log n)을 요구했고, 면접에서 이 답을 내면 "더 빠르게 할 수 있나요?"가 바로 나온다. 정렬돼 있다는 정보를 거의 버렸기 때문이다.

## 가운데를 보고 절반을 버린다: 재귀

손으로 했던 그대로 옮기면 재귀 함수가 나온다. "lo번부터 hi번 사이에서 target을 찾아라"를 함수 하나로 정하고, 가운데를 본 뒤 남은 절반에 같은 질문을 다시 던진다.

```js
function search(nums, target, lo = 0, hi = nums.length - 1) {
  if (lo > hi) return -1;                    // 후보가 하나도 없다
  const mid = lo + Math.floor((hi - lo) / 2); // 가운데 칸
  if (nums[mid] === target) return mid;
  if (nums[mid] < target) {
    return search(nums, target, mid + 1, hi); // 왼쪽 절반과 mid를 버린다
  }
  return search(nums, target, lo, mid - 1);   // 오른쪽 절반과 mid를 버린다
}
```

여기서 함수 인자 `lo`, `hi`는 "답이 있을 수 있는 칸은 lo번부터 hi번까지, 양 끝 포함"이라는 뜻이다. 이렇게 양 끝을 모두 포함하는 범위를 닫힌 구간이라 부르고 `[lo, hi]`로 쓴다. 이 뜻을 정하고 나면 나머지가 저절로 정해진다.

- 처음 호출은 배열 전체이니 `lo = 0`, `hi = nums.length - 1`이다.
- `lo > hi`이면 닫힌 구간이 비었다는 뜻이다. `lo === hi`는 칸이 하나 남았다는 뜻이라 아직 끝나면 안 된다.
- `nums[mid]`를 이미 봤으니 다음 구간에서 mid는 빼야 한다. 그래서 `mid + 1`, `mid - 1`이다.

재귀가 낯설다면 [재귀와 백트래킹 글](/posts/recursion-backtracking)을 먼저 보면 좋다. 여기서는 한 번 호출할 때마다 구간이 절반 이하로 줄고, 구간이 비면 멈춘다는 것만 확인하면 된다.

시간은 O(log n)이다. 길이 n인 구간이 n/2, n/4, …로 줄어 1이 될 때까지 걸리는 횟수가 log₂ n이다. 10^4칸이면 14번이면 된다. 공간은 재귀 호출이 쌓이는 깊이만큼, 즉 O(log n)이다. 깊이가 14 정도라 스택이 넘칠 걱정은 없지만, 같은 일을 반복문으로 하면 이 공간마저 없앨 수 있다. 재귀의 마지막 동작이 자기 자신을 부르는 것뿐이라(꼬리 재귀) 반복문으로 옮기기가 아주 쉽다.

## 반복문으로 옮기고 닫힌 구간을 끝까지 지킨다

재귀 함수의 인자를 지역 변수로 바꾸고, "다시 부르기"를 "변수를 바꾸고 한 바퀴 더 돌기"로 바꾼다. 이 문제의 정석 풀이다.

```js
function search(nums, target) {
  let lo = 0, hi = nums.length - 1;   // 닫힌 구간 [lo, hi]: 양 끝 모두 후보
  while (lo <= hi) {                  // lo === hi도 한 칸이 남은 것이라 돈다
    const mid = lo + Math.floor((hi - lo) / 2);
    if (nums[mid] === target) return mid;
    if (nums[mid] < target) lo = mid + 1; // mid와 그 왼쪽은 전부 target보다 작다
    else hi = mid - 1;                     // mid와 그 오른쪽은 전부 target보다 크다
  }
  return -1; // lo가 hi를 넘었다. 후보가 비었다
}
```

아래 그림은 이 코드가 17을 찾는 과정이다. 오른쪽 상자의 `lo`, `hi`가 지금 남은 후보 범위다.


시간은 O(log n), 공간은 O(1)이다. 반복이 한 번 돌 때마다 구간 길이 `hi - lo + 1`이 적어도 절반으로 준다. mid를 빼고 남는 쪽은 많아야 원래 길이의 절반이기 때문이다. 그러니 많아야 ⌊log₂ n⌋ + 1번 돈다. 8칸이면 4번, 10^4칸이면 14번, 10^7칸이면 24번이다.

### 파이썬과 자바로 옮기면

코딩 테스트에서는 파이썬과 자바도 많이 쓴다. 로직은 같고, 언어마다 달라지는 곳이 두 군데 있다. 정수 나눗셈과 오버플로다.

```python
from typing import List

class Solution:
    def search(self, nums: List[int], target: int) -> int:
        lo, hi = 0, len(nums) - 1          # 닫힌 구간 [lo, hi]
        while lo <= hi:
            mid = (lo + hi) // 2           # 파이썬 int는 크기 제한이 없어 넘치지 않는다
            if nums[mid] == target:
                return mid
            if nums[mid] < target:
                lo = mid + 1
            else:
                hi = mid - 1
        return -1
```

파이썬은 `//`가 내림 나눗셈이고 정수 크기에 제한이 없어서 `(lo + hi) // 2`를 그대로 써도 된다. `/`를 쓰면 실수(float)가 나와 `nums[mid]`에서 `TypeError`가 난다.

```java
class Solution {
    public int search(int[] nums, int target) {
        int lo = 0, hi = nums.length - 1;   // 닫힌 구간 [lo, hi]
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;   // (lo + hi) / 2는 int 범위를 넘을 수 있다
            if (nums[mid] == target) return mid;
            if (nums[mid] < target) lo = mid + 1;
            else hi = mid - 1;
        }
        return -1;
    }
}
```

자바의 `int`는 2^31 - 1(약 21억)을 넘으면 음수로 돌아간다. 이 문제의 배열은 짧아서 상관없지만, `lo`와 `hi`가 둘 다 10억을 넘는 상황(아래 "답을 놓고 찾는" 문제에서 흔하다)에서는 `(lo + hi) / 2`가 음수가 된다. 직접 찍어 봤다.

```java
int lo = 2_000_000_000, hi = 2_100_000_000;
System.out.println((lo + hi) / 2 + " " + (lo + (hi - lo) / 2) + " " + ((lo + hi) >>> 1));
```

```text
-97483648 2050000000 2050000000
```

`lo + (hi - lo) / 2`는 `hi - lo`가 넘치지 않는 한 안전하다. `(lo + hi) >>> 1`은 넘친 합을 부호 없는 수로 읽어서 반으로 나누는 방법인데, `lo`와 `hi`가 음수가 아닐 때만 맞다. 인덱스는 음수가 아니니 둘 다 쓸 수 있다. 2006년에 자바 표준 라이브러리의 `Arrays.binarySearch`에서도 이 버그가 발견돼 `>>> 1`로 고쳐졌다.

### 맞게 짰는지 무작위로 확인하기

손으로 몇 개 넣어 보는 걸로는 경계 버그를 잘 못 잡는다. 확실한 방법은 느리지만 틀릴 수 없는 풀이(`indexOf`)와 결과를 맞춰 보는 것이다. 길이 0~6의 정렬 배열과 범위 안팎의 target을 10만 번 만들어 비교했다. 비교 대상으로 `while (lo < hi)`로 잘못 쓴 코드(`buggy`)도 같이 돌렸다.

```js
function randomSorted(maxLen) {
  const n = Math.floor(Math.random() * (maxLen + 1));     // 길이 0 ~ maxLen
  const set = new Set();
  while (set.size < n) set.add(Math.floor(Math.random() * 41) - 20); // -20 ~ 20, 중복 없이
  return [...set].sort((a, b) => a - b);
}
function check(fn, rounds = 100000) {
  for (let r = 0; r < rounds; r++) {
    const nums = randomSorted(6);
    const target = Math.floor(Math.random() * 45) - 22;   // 범위 밖 값도 섞는다
    const want = nums.indexOf(target);
    if (fn(nums, target) !== want) return { nums, target, got: fn(nums, target), want };
  }
  return "ok";
}
console.log("search:", check(search));
console.log("buggy:", check(buggy));
```

```text
search: ok
buggy: { nums: [ -18, -8, -1, 3, 16 ], target: -8, got: -1, want: 1 }
```

정석 풀이는 10만 번 모두 맞았고, 잘못된 코드는 금방 반례를 내놓았다. 반례는 돌릴 때마다 달라지지만 늘 "마지막 한 칸을 확인하지 않고 끝나는" 경우다. 배열 길이를 일부러 작게(0~6) 잡은 이유는 경계 버그가 구간이 한두 칸 남았을 때 나기 때문이다. 길이 1,000짜리 배열 몇 개보다 길이 3짜리 배열 수만 개가 버그를 훨씬 잘 찾는다. 면접에서도 코드를 다 쓴 뒤 `[]`, `[5]`, `[1, 3]`을 손으로 넣어 보는 습관이 같은 역할을 한다.

이 풀이가 맞는 이유를 한 문장으로 하면 이렇다. 반복이 도는 내내 "target이 배열에 있다면 반드시 `[lo, hi]` 안에 있다"가 참으로 유지된다. 처음엔 배열 전체이니 참이고, 버리는 쪽은 정렬 때문에 target이 있을 수 없는 쪽이니 계속 참이다. 구간 길이가 매번 적어도 1씩 주니 반복은 반드시 끝나고, 구간이 비어서 끝났다면 target은 배열에 없다. 이렇게 반복 내내 지켜지는 조건을 루프 불변식이라 부른다.

## 경계를 먼저 찾고 나중에 확인한다: 반열린 구간

닫힌 구간 풀이는 "찾으면 바로 돌려준다"는 문제에 딱 맞다. 그런데 같은 값이 여러 개거나, 없을 때 들어갈 자리를 물으면 다른 틀이 편하다. "target 이상이 처음 나오는 자리"를 먼저 찾고, 그 자리 값이 target인지 마지막에 한 번만 확인하는 방법이다.

```js
function search(nums, target) {
  let lo = 0, hi = nums.length;      // 반열린 구간 [lo, hi): hi는 후보가 아니다
  while (lo < hi) {                  // lo === hi면 구간이 비었다
    const mid = (lo + hi) >>> 1;
    if (nums[mid] < target) lo = mid + 1; // mid는 target보다 작으니 답이 아니다
    else hi = mid;                         // mid가 답일 수도 있으니 남긴다
  }
  // lo: target 이상이 처음 나오는 자리 (없으면 nums.length)
  return lo < nums.length && nums[lo] === target ? lo : -1;
}
```

여기서 구간 `[lo, hi)`는 "lo는 후보, hi는 후보가 아니다"라는 뜻이다. 처음 `hi`가 `nums.length`인 이유는 "target 이상인 값이 하나도 없다"도 답이 될 수 있어서다. 그 답을 배열 끝 바로 다음 자리로 표현한다. 반복 안에서 `nums[mid] === target`이어도 멈추지 않는다. 같은 값이 더 왼쪽에 있을 수도 있으니 `hi = mid`로 계속 왼쪽을 좁힌다.

17을 찾으면 이렇게 움직인다.

```text
lo=0 hi=8 mid=4 nums[mid]=12  -> 12 < 17, lo = 5
lo=5 hi=8 mid=6 nums[mid]=25  -> 25 >= 17, hi = 6
lo=5 hi=6 mid=5 nums[mid]=17  -> 17 >= 17, hi = 5
lo=5 hi=5 끝. nums[5] === 17 이므로 5
```

닫힌 구간 풀이는 두 번 만에 찾았는데 이 풀이는 세 번 돈다. 찾자마자 멈추지 않기 때문이다. 대신 반복 안의 비교가 하나뿐이고(`<`), 결과가 항상 경계 하나로 정해진다. 같은 값이 여러 개일 때 첫 번째를 보장하고, 없을 때 들어갈 자리도 그대로 `lo`다. [이분 탐색 글](/posts/binary-search)의 lower bound가 바로 이 함수다.

파이썬과 자바로 옮기면 이렇다. `[2, 2, 2]`에서 2를 찾으면 둘 다 첫 자리인 0을 돌려준다.

```python
def search(nums, target):
    lo, hi = 0, len(nums)            # 반열린 구간 [lo, hi)
    while lo < hi:
        mid = (lo + hi) // 2
        if nums[mid] < target:
            lo = mid + 1             # mid는 답이 아니다
        else:
            hi = mid                 # mid가 답일 수 있다
    return lo if lo < len(nums) and nums[lo] == target else -1
```

```java
static int search(int[] nums, int target) {
    int lo = 0, hi = nums.length;          // 반열린 구간 [lo, hi)
    while (lo < hi) {
        int mid = (lo + hi) >>> 1;         // 인덱스는 음수가 아니니 >>> 1이 안전하다
        if (nums[mid] < target) lo = mid + 1;
        else hi = mid;
    }
    return lo < nums.length && nums[lo] == target ? lo : -1;
}
```

```text
python: [5, -1, 0, 7, -1, -1] -1 0
java:   5 -1 0 7 -1 -1 -1 0
```

시간 O(log n), 공간 O(1)로 닫힌 구간 풀이와 같다. 둘 중 어느 것을 써도 이 문제는 맞는다. 다만 한 코드 안에서 두 틀을 섞으면 안 된다. `hi = nums.length`로 시작해 놓고 `while (lo <= hi)`를 쓰면 `nums[nums.length]`를 읽고, `hi = nums.length - 1`로 시작해 놓고 `hi = mid`를 쓰면 마지막 칸을 영영 확인하지 않는 코드가 된다.

## 표준 라이브러리에 맡기기

실무에서는 이분 탐색을 손으로 짜기보다 언어가 주는 함수를 쓴다. 면접에서도 "직접 짜 보라"는 말이 없으면 써도 되고, 동작을 정확히 설명할 수 있으면 더 좋다.

파이썬은 `bisect` 모듈이 있다. `bisect_left(nums, x)`는 위의 반열린 구간 풀이와 똑같이 "x 이상이 처음 나오는 자리"를 돌려준다.

```python
from bisect import bisect_left

def search(nums, target):
    i = bisect_left(nums, target)      # target 이상이 처음 나오는 자리
    return i if i < len(nums) and nums[i] == target else -1

a = [-4, 1, 3, 8, 12, 17, 25, 31]
print([search(a, t) for t in [17, 10, -4, 31, 40, -9]])
print(bisect_left(a, 10), bisect_left(a, 40))
```

```text
[5, -1, 0, 7, -1, -1]
4 8
```

`bisect_left`는 값이 없어도 예외를 내지 않고 자리를 돌려준다. 그래서 `i < len(nums)` 확인을 빼먹으면 40을 찾을 때 `nums[8]`에서 `IndexError`가 난다.

자바는 `Arrays.binarySearch`가 있다. 찾으면 그 자리를, 못 찾으면 `-(들어갈 자리) - 1`을 돌려준다.

```java
int[] a = {-4, 1, 3, 8, 12, 17, 25, 31};
System.out.println(Arrays.binarySearch(a, 17) + " " + Arrays.binarySearch(a, 10) + " " + Arrays.binarySearch(a, 40));
```

```text
5 -5 -9
```

10이 들어갈 자리는 4라서 `-4 - 1 = -5`, 40은 8이라서 `-9`다. 그냥 `-1`이 아닌 이유는 들어갈 자리가 0일 때도 음수로 표현하려고 1을 더 뺀 것이다. 그래서 이 문제에 쓰려면 `Math.max(-1, …)`처럼 바꾸면 안 되고 `r >= 0 ? r : -1`로 바꿔야 한다. 또 같은 값이 여러 개면 그중 아무 자리나 돌려준다고 문서에 적혀 있다. 첫 번째를 보장하지 않는다.

JavaScript에는 정렬 배열용 이분 탐색 함수가 없다. `indexOf`, `includes`, `findIndex`는 모두 앞에서부터 훑는 O(n)이다. 그래서 JS로 코딩 테스트를 본다면 위의 함수를 직접 쓸 수 있어야 한다.

## 실제로 얼마나 빨라지나

LeetCode의 10^4칸에서는 차이가 잘 안 보인다. 1,000만 칸짜리 배열에 1,000번 질문해 봤다. 찾는 값은 일부러 배열 끝 근처로 골라 훑기에 불리하게 했다.

```js
const N = 1e7;
const big = Array.from({ length: N }, (_, i) => i * 2); // 0, 2, 4, ... 정렬됨
// searchLinear: 앞에서부터 훑는 풀이, search: 닫힌 구간 이분 탐색
```

```text
linear 1000 queries 16589.4 ms
binary 1000 queries 1.2 ms
iters 23
```

훑기는 16초, 이분 탐색은 1.2ms다. 1,000만 칸에서 없는 값을 찾을 때도 반복은 23번이면 끝났다. 정렬해 두는 비용(O(n log n))은 한 번만 내면 되니, 질문이 여러 번 올수록 이분 탐색이 유리하다. 반대로 질문이 한 번뿐이고 배열이 정렬돼 있지 않다면 정렬하느니 그냥 훑는 게 낫다. 이 계산은 [정렬 알고리즘 글](/posts/sorting-algorithms)과 [Big O 글](/posts/big-o-notation)에 자세히 있다.

## 다섯 풀이를 한 표에

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 앞에서부터 훑기 | O(n) | O(1) | 배열이 작거나 정렬이 안 돼 있을 때. 이 문제의 답으로는 부족하다 |
| 재귀 이분 탐색 | O(log n) | O(log n) | 구간을 나누는 생각을 설명할 때. 실제 제출은 반복문이 낫다 |
| 닫힌 구간 반복문 | O(log n) | O(1) | 값이 서로 다르고 "찾으면 바로 돌려준다"는 이 문제 그대로 |
| 반열린 구간(lower bound) | O(log n) | O(1) | 중복이 있거나 들어갈 자리, 첫 번째 위치가 필요할 때 |
| 표준 라이브러리 | O(log n) | O(1) | 파이썬 `bisect`, 자바 `Arrays.binarySearch`. 반환 형식을 정확히 알 때 |

면접에서는 닫힌 구간 풀이를 먼저 쓰고, "중복이 있다면?"이 나오면 반열린 구간으로 바꾸는 흐름이 자연스럽다.

## 이렇게 짜면 틀린다

이분 탐색에서 나는 버그는 대부분 에러 없이 틀린 답을 내거나 영영 돌아오지 않는다. 직접 틀린 코드를 돌려 봤다.

### 닫힌 구간인데 `lo < hi`로 돌기

```js
let lo = 0, hi = nums.length - 1;
while (lo < hi) { /* 나머지는 정석 풀이와 같다 */ }
return -1;
```

`[5]`에서 5를 찾으면 `lo = hi = 0`이라 반복을 한 번도 돌지 않고 `-1`이 나온다. `[1, 3]`에서 3을 찾아도 `lo = 1`이 된 순간 반복이 끝나 `-1`이다. 닫힌 구간에서 `lo === hi`는 한 칸이 남은 것이지 빈 구간이 아니다. 빈 구간은 `lo > hi`다. 그래서 조건이 `lo <= hi`다.

### mid를 빼지 않고 lo = mid로 남기기

```js
if (nums[mid] < target) lo = mid; // mid + 1이어야 한다
```

`[1, 3]`에서 3을 찾으면 `lo = 0`, `hi = 1`, `mid = 0`이고 `1 < 3`이라 `lo = 0`, 다시 같은 상태다. 반복 횟수에 상한을 걸고 돌렸더니 `[1, 3]`에서 3을 찾을 때도, 없는 2를 찾을 때도 둘 다 멈추지 않았다. 이미 본 mid를 구간에 남기면 두 칸 남았을 때 구간이 줄지 않는다. 이 무한 루프가 왜 생기는지는 [이분 탐색 글의 구간 정의 절](/posts/binary-search)에서 그림으로 따라갔다.

### 자바스크립트에서 큰 수에 `>> 1`

```js
const lo = 2 ** 31 - 2, hi = 2 ** 31 - 1;
console.log((lo + hi) >> 1, (lo + hi) >>> 1, Math.floor((lo + hi) / 2));
```

```text
-2 2147483646 2147483646
```

JS의 숫자는 2^53까지 정수를 정확히 담는 실수라 덧셈 자체는 넘치지 않는다. 그런데 비트 연산 `>>`는 피연산자를 32비트 부호 있는 정수로 바꾼 뒤 계산해서, 합이 2^31을 넘으면 음수가 된다. 배열 인덱스에서는 생길 일이 거의 없지만 값 범위(10억, 20억)를 놓고 이분 탐색할 때는 진짜로 터진다. `>>> 1`은 2^32까지, `Math.floor`는 2^53까지 안전하다.

### 같은 값이 여러 개일 때 아무 자리나 나온다

이 문제는 값이 서로 다르다고 보장했다. 그 보장이 깨지면 닫힌 구간 풀이는 처음 걸린 자리를 돌려준다.

```text
search([2, 2, 2, 2, 2], 2) -> 2
search([1, 2, 2, 2, 3], 2) -> 2
```

둘 다 2번 칸이다. 첫 번째 2(0번, 1번)가 필요했다면 틀린 답이다. 이럴 때는 반열린 구간 풀이로 바꾼다.

### 빈 배열

`nums.length - 1`이 `-1`이라 닫힌 구간 풀이는 반복을 돌지 않고 `-1`을 돌려준다. 반열린 구간 풀이는 `lo = hi = 0`이라 마지막 확인에서 `lo < nums.length`가 거짓이 되어 `-1`이다. 둘 다 따로 처리할 필요는 없지만, 마지막 확인에서 길이 검사를 빼면 `nums[0]`을 읽는다. JS는 `undefined`를 돌려줘서 우연히 맞고, 파이썬과 자바는 예외가 난다.

## 면접관이 이어서 묻는 것

이 문제 자체는 짧아서, 면접에서는 거의 항상 변형이 따라온다. 어디를 바꾸면 되는지 하나씩 본다.

### 없으면 들어갈 자리를 달라 (35. Search Insert Position)

위에서 본 대로 닫힌 구간 풀이가 실패로 끝날 때의 `lo`가 답이다. 반열린 구간 풀이라면 마지막 확인을 지우고 `lo`를 그대로 돌려준다.

```js
function searchInsert(nums, target) {
  let lo = 0, hi = nums.length;
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;
    if (nums[mid] < target) lo = mid + 1; else hi = mid;
  }
  return lo; // 10 -> 4, 40 -> 8, -9 -> 0
}
```

### 중복이 있을 때 처음과 마지막 자리 (34. Find First and Last Position)

lower bound를 두 번 쓴다. `target` 이상이 처음 나오는 자리와, `target + 1` 이상이 처음 나오는 자리 - 1이다. [이분 탐색 글의 연습 문제](/posts/binary-search)에 플레이그라운드가 있다. 찾은 뒤 양옆으로 훑으면 전부 같은 값인 배열에서 O(n)이 되니 안 된다.

### 배열 길이를 모른다 (702. Search in a Sorted Array of Unknown Size)

`reader.get(i)`로만 값을 읽을 수 있고, 범위를 넘으면 아주 큰 값(2^31 - 1)이 돌아오는 변형이다. 길이를 모르니 `hi`를 정할 수 없다. 그래서 1, 2, 4, 8, …로 두 배씩 늘려 `target`을 넘는 지점을 먼저 찾고, 그 앞 절반에서 이분 탐색한다. 이런 방식을 지수 탐색(exponential search)이라 부른다.

```js
function searchUnknown(reader, target) {
  let hi = 1;
  while (reader.get(hi) < target) hi *= 2; // target 이상인 지점까지 두 배씩
  let lo = hi >> 1;                         // 바로 앞 단계는 target보다 작았다
  while (lo <= hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    const v = reader.get(mid);
    if (v === target) return mid;
    if (v < target) lo = mid + 1; else hi = mid - 1;
  }
  return -1;
}
```

```text
17 5 calls 7
31 7 calls 6
10 -1 calls 5
-4 0 calls 2
```

답의 자리가 p라면 늘리는 데 log p번, 찾는 데 log p번이라 O(log p)다. 배열 전체 길이가 아니라 답의 위치에 따라 시간이 정해진다는 게 장점이다. 로그 파일처럼 끝을 모르는 데이터나, 앞쪽에 답이 몰려 있는 경우에 쓴다.

### 2차원 행렬에서 찾기 (74. Search a 2D Matrix)

각 행이 정렬돼 있고 다음 행의 첫 값이 이전 행의 마지막 값보다 크다면, 행렬 전체가 한 줄로 이어 붙인 정렬 배열과 같다. 길이 `m * n`인 가상의 배열에서 이분 탐색하고, 인덱스 `i`를 `matrix[Math.floor(i / n)][i % n]`으로 읽는다. 새 배열을 만들지 않으니 공간은 O(1)이다.

### 배열이 회전돼 있다면

`[12, 17, 25, 31, -4, 1, 3, 8]`처럼 정렬된 배열을 한 번 돌린 경우다. 전체 정렬이 깨져서 위 코드가 그대로는 안 되지만, 가운데로 자르면 한쪽은 반드시 정렬돼 있다는 성질로 여전히 O(log n)에 찾는다. [Search in Rotated Sorted Array 글](/posts/leetcode-search-in-rotated-sorted-array)에서 다룬다. 회전된 배열의 최솟값 찾기는 [Find Minimum in Rotated Sorted Array 글](/posts/leetcode-find-minimum-in-rotated-sorted-array)에 있다.

### 배열이 아니라 답의 범위에서 찾는다면

"바나나를 h시간 안에 다 먹는 가장 느린 속도"처럼 배열에 값이 없어도, 답 후보를 늘어놓았을 때 "된다/안 된다"가 한 번만 바뀌면 이분 탐색을 쓴다. [Koko Eating Bananas 글](/posts/leetcode-koko-eating-bananas)이 대표 문제다. 이때 `lo`, `hi`가 10억 근처까지 커지니 위에서 본 오버플로 이야기가 진짜 문제가 된다. 두 정렬 배열의 중앙값을 O(log)로 구하는 [Median of Two Sorted Arrays 글](/posts/leetcode-median-of-two-sorted-arrays)은 "어디서 자를까"를 이분 탐색한다.

비슷한 문제로 69. Sqrt(x)(답의 범위에서 찾기), 278. First Bad Version(F에서 T로 바뀌는 첫 지점), 162. Find Peak Element(오르막인가로 판정)가 있다. 문제를 패턴으로 묶어 공부하는 순서는 [LeetCode 공부 가이드](/posts/leetcode-study-guide)에 정리했다.

## 구간 하나를 정하면 코드가 따라온다

이 문제의 풀이는 결국 하나다. 가운데를 보고, 정렬돼 있으니 한쪽 절반에는 답이 없다고 확신하고 버린다. 틀리는 곳은 "남은 후보가 어디부터 어디까지인가"를 코드의 세 군데(초깃값, 반복 조건, 줄이는 방식)가 서로 다르게 이해할 때다. 닫힌 구간 `[lo, hi]`라면 `hi = n - 1`, `lo <= hi`, `mid ± 1`이 짝이고, 반열린 구간 `[lo, hi)`라면 `hi = n`, `lo < hi`, `lo = mid + 1`과 `hi = mid`가 짝이다. 하나를 골라 끝까지 지키면, 두 칸 남았을 때와 빈 배열에서도 따로 생각할 게 없다.

## 면접에서 나올 만한 질문

### 이 문제를 O(log n)에 풀 수 있는 이유는 무엇인가요?

배열이 정렬돼 있어서 가운데 값 하나만 보고도 절반에는 답이 없다고 확신할 수 있기 때문이다. 가운데 값이 target보다 작으면 그 왼쪽은 전부 더 작다. 한 번 볼 때마다 후보가 절반이 되니 n칸은 약 log₂ n번이면 한 칸으로 줄어든다. 10^4칸이면 14번이다.

### while 조건을 `lo <= hi`로 쓰는 경우와 `lo < hi`로 쓰는 경우는 어떻게 다른가요?

구간을 어떻게 정의했느냐에 따라 정해진다. 닫힌 구간 `[lo, hi]`는 `lo === hi`일 때 한 칸이 남은 것이라 `lo <= hi`로 돌고, 줄일 때 mid를 빼서 `mid + 1`, `mid - 1`을 쓴다. 반열린 구간 `[lo, hi)`는 `lo === hi`가 빈 구간이라 `lo < hi`로 돌고, `hi = mid`로 줄인다. 세 군데를 같은 정의에서 끌어내지 않고 섞으면 한 칸짜리 배열을 놓치거나 무한 루프에 빠진다.

### mid를 `(lo + hi) / 2`로 구하면 어떤 문제가 있나요?

자바나 C++의 32비트 `int`에서는 `lo + hi`가 약 21억을 넘으면 음수가 되어 잘못된 인덱스가 나온다. `lo + (hi - lo) / 2`나 `(lo + hi) >>> 1`로 피한다. 자바스크립트는 덧셈이 넘치지 않지만 `>> 1`을 쓰면 32비트로 잘려 같은 문제가 생기고, 파이썬은 정수 크기 제한이 없어 상관없다. 이 문제는 배열이 짧아서 실제로 터지지 않지만, 값 범위를 놓고 탐색하는 변형에서는 진짜로 터진다.

### 이 코드가 맞다는 걸 어떻게 확신하나요?

반복이 도는 동안 "target이 배열에 있다면 반드시 `[lo, hi]` 안에 있다"는 불변식이 지켜진다고 말한다. 처음엔 배열 전체라 참이고, 버리는 절반은 정렬 때문에 target이 있을 수 없는 쪽이라 계속 참이다. 구간 길이가 매번 줄어드니 반복은 반드시 끝나고, 구간이 비어 끝났다면 target은 없다. 말로 한 뒤에는 `indexOf`와 비교하는 무작위 테스트로 확인한다.

### 값이 중복될 수 있다면 무엇을 바꾸나요?

닫힌 구간 풀이는 처음 걸린 자리를 돌려주니 첫 번째나 마지막 자리를 보장하지 못한다. `[2, 2, 2, 2, 2]`에서 2를 찾으면 2번 칸이 나온다. 그래서 같은 값을 만나도 멈추지 않고 왼쪽으로 계속 좁히는 lower bound(반열린 구간)로 바꾼다. 마지막 자리는 `target + 1`의 lower bound에서 1을 빼거나 upper bound를 쓴다.

### 파이썬 bisect_left나 자바 Arrays.binarySearch를 써도 되나요?

직접 짜라는 조건이 없으면 써도 되고, 반환 형식을 정확히 아는지가 중요하다. `bisect_left`는 값이 없어도 들어갈 자리를 돌려주니 그 자리 값이 target인지 확인해야 한다. `Arrays.binarySearch`는 못 찾으면 `-(들어갈 자리) - 1`을 돌려주고, 중복이 있으면 어느 자리를 줄지 보장하지 않는다. 자바스크립트에는 이런 함수가 없어서 직접 짜야 한다.

### 정렬되지 않은 배열에서 한 번만 찾는다면 이분 탐색을 쓰나요?

쓰지 않는다. 정렬에 O(n log n)이 드는데 한 번 찾는 데는 O(n) 훑기면 충분하다. 같은 배열에 질문이 여러 번 온다면 한 번 정렬해 두고 매번 O(log n)에 찾는 쪽이 이긴다. 값이 있는지만 묻고 순서나 범위가 필요 없다면 해시 셋이 평균 O(1)이라 더 빠르다.
