<EasyIntro>
  보통 우리는 계산식을 3 더하기 4처럼 숫자 사이에 기호를 넣어서 쓴다. 그런데 기호를 숫자 뒤에 쓰는 방식도 있다. 3, 4, 더하기라고 쓰면 앞의 두 숫자를 더하라는 뜻이다. 이렇게 쓰면 괄호가 하나도 없어도 어떤 순서로 계산할지 헷갈리지 않는다. 계산하는 방법은 접시 쌓기와 비슷하다. 숫자가 나오면 접시를 하나 올리고, 기호가 나오면 맨 위 접시 두 개를 내려서 계산한 다음 그 결과를 새 접시로 다시 올린다. 끝까지 하면 접시가 딱 하나 남고, 거기 적힌 숫자가 답이다. 빼기와 나누기는 순서가 중요해서 나중에 올린 접시가 오른쪽 숫자가 된다는 것만 조심하면 된다.
</EasyIntro>

오래된 공학용 계산기 중에는 `=` 버튼이 없는 것이 있다. `3`, `Enter`, `4`, `+`를 누르면 7이 나온다. 숫자를 먼저 넣고 연산은 나중에 누르는 방식이다. 처음 보면 불편해 보이는데, 써 보면 괄호를 한 번도 누르지 않고 `(3 + 4) × 2`를 계산할 수 있다.

이 표기법이 역폴란드 표기법(Reverse Polish Notation, RPN)이다. 폴란드 논리학자 얀 우카시에비치가 1920년대에 만든, 연산자를 앞에 쓰는 표기(폴란드 표기, 전위 표기)를 뒤집은 것이라 이런 이름이 붙었다. 연산자를 피연산자 뒤에 쓴다고 해서 후위 표기법이라고도 한다. [LeetCode 150. Evaluate Reverse Polish Notation](https://leetcode.com/problems/evaluate-reverse-polish-notation/)은 이 표기법으로 적힌 식을 계산하는 문제다. 스택을 처음 배울 때 괄호 짝 맞추기([Valid Parentheses](/posts/leetcode-valid-parentheses)) 다음으로 많이 만나는 문제이고, 컴파일러와 계산기가 식을 다루는 방식과 바로 이어진다.

이 글에서는 가장 앞 연산자부터 하나씩 접어 가는 느린 풀이, 스택 풀이, 뒤에서부터 읽는 재귀 풀이, 식 트리를 세워 두는 풀이, 입력 배열을 스택으로 다시 쓰는 풀이까지 다섯 가지를 본다. 스택 자체는 [스택·큐·덱 글](/posts/ds-stack-queue-deque)에 있다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 연산자가 숫자 뒤에 오는 식

문자열 배열 `tokens`가 주어진다. 원소 하나하나가 정수이거나 `"+"`, `"-"`, `"*"`, `"/"` 중 하나다. 이 배열은 올바른 역폴란드 표기식이라고 보장된다. 식을 계산한 정수를 돌려주면 된다.

규칙이 세 가지 붙는다.

- 나눗셈은 정수 나눗셈이고 소수점 아래는 0 쪽으로 버린다. `7 / 2`는 3, `-7 / 2`는 -3이다.
- 0으로 나누는 경우는 나오지 않는다.
- 답과 중간 계산 값은 모두 32비트 정수 범위 안에 들어간다.

토큰 수는 최대 10^4이다. O(n²)도 1억 번 언저리라 아슬아슬하게 돌아가긴 하지만, 이 문제는 O(n)이 자연스럽게 나온다. 정수 토큰에는 `"-11"`처럼 음수가 섞일 수 있다는 점도 기억해 둔다. 빼기 기호 `"-"`와 음수 `"-11"`이 둘 다 `-`로 시작한다.

## 손으로 읽어 보기: 기호가 나오면 바로 앞 두 수를 묶는다

이 글에서 계속 쓸 예시다.

```text
tokens = ["4", "2", "5", "*", "+", "9", "3", "/", "-"]
```

왼쪽부터 읽다가 처음 연산자를 만나면, 그 바로 앞의 두 수에 그 연산자를 적용한다. 그 결과가 두 수와 연산자 자리를 대신한다. 이걸 반복한다.

```text
4  2  5  *  +  9  3  /  -
4  (2*5)    +  9  3  /  -     →  4 10 + 9 3 / -
(4+10)         9  3  /  -     →  14 9 3 / -
14             (9/3)    -     →  14 3 -
(14-3)                        →  11
```

답은 11이다. 보통 쓰는 중위 표기로 옮기면 `(4 + 2 * 5) - 9 / 3`이다. 중위 표기에서는 곱셈이 먼저라는 우선순위 규칙과 괄호가 있어야 계산 순서가 정해지는데, 후위 표기에서는 연산자가 나오는 순서가 곧 계산 순서다. 그래서 괄호도 우선순위 표도 필요 없다.

손으로 읽으면서 눈여겨볼 곳이 있다. 연산자는 언제나 "바로 앞에 남아 있는 두 값"을 쓴다. 이미 계산된 값이든 원래 숫자든 상관없이, 가장 최근에 생긴 두 값이다. 가장 최근 것부터 꺼내 쓰는 구조, 이게 스택이다.

## 가장 먼저 나온 연산자부터 하나씩 접기

손으로 한 걸 그대로 코드로 옮겨 보자. 배열에서 첫 연산자를 찾고, 그 앞 두 칸과 연산자 자리를 계산 결과 하나로 바꾼다. 배열에 값이 하나만 남을 때까지 반복한다.

첫 연산자 바로 앞 두 칸이 그 연산자의 피연산자라는 게 이 방법이 맞는 이유다. 첫 연산자 앞에는 연산자가 없으니 전부 숫자이고, 올바른 식이라면 그중 마지막 두 개가 이 연산자의 짝이다.

```js
const OPS = new Set(["+", "-", "*", "/"]);

function apply(a, b, op) {
  switch (op) {
    case "+": return a + b;
    case "-": return a - b;
    case "*": return a * b;
    default: return Math.trunc(a / b); // 0 쪽으로 버린다
  }
}

function evalRPN(tokens) {
  const t = tokens.map((x) => (OPS.has(x) ? x : Number(x)));
  while (t.length > 1) {
    let i = 0;
    while (!OPS.has(t[i])) i++; // 첫 연산자 찾기
    t.splice(i - 2, 3, apply(t[i - 2], t[i - 1], t[i])); // 세 칸을 결과 한 칸으로
  }
  return t[0];
}
```

연산자가 n/2개쯤 있으니 바깥 반복은 O(n)번이다. 반복마다 첫 연산자를 찾는 데 O(n), `splice`로 뒤 원소들을 당기는 데 O(n)이 든다. 그래서 전체 O(n²)이다. 공간은 복사한 배열 O(n)이다.

토큰 9999개로 재 보았다. `1 1 + 1 + 1 + ...`처럼 연산자가 앞쪽에 몰린 식은 `splice`가 매번 배열 거의 전체를 당겨서 113ms, `1 1 1 ... + + +`처럼 연산자가 뒤에 몰린 식은 첫 연산자를 찾느라 매번 끝까지 걸어서 148ms가 걸렸다. 뒤에서 볼 스택 풀이는 같은 입력에서 0.2~1.7ms였다.

느린 이유는 분명하다. 한 번 접을 때마다 "첫 연산자가 어디 있나"를 처음부터 다시 찾는다. 그런데 방금 접은 자리 바로 뒤가 다음 연산자의 후보다. 지금까지 읽은 값들을 버리지 않고 들고 가면 처음으로 돌아갈 필요가 없다.

## 숫자를 쌓아 두었다가 연산자가 오면 두 개를 꺼낸다

배열을 왼쪽부터 한 번만 읽는다. 아직 쓰이지 않은 값들을 스택에 쌓아 둔다.

- 숫자가 나오면 스택에 넣는다.
- 연산자가 나오면 스택에서 두 개를 꺼낸다. 먼저 꺼낸 것이 오른쪽 피연산자 `b`, 그다음이 왼쪽 피연산자 `a`다. `a 연산자 b`를 계산해 스택에 다시 넣는다.
- 끝까지 읽으면 스택에 값이 하나 남는다. 그게 답이다.

계산 결과를 다시 스택에 넣는 게 중요하다. 그 결과는 다음 연산자의 피연산자가 될 "가장 최근 값"이기 때문이다. 아래 그림에서 다음을 누르면 토큰마다 스택이 어떻게 바뀌는지 볼 수 있다.

3번째 칸의 곱하기를 보자. 스택에는 `4, 2, 5`가 있었는데, 곱하기는 맨 위 두 개인 2와 5만 가져간다. 바닥의 4는 아직 자기 차례가 아니라서 그대로 기다린다. 4번째 칸의 더하기가 와서야 4와 방금 만든 10이 묶인다. 손으로 풀 때 "바로 앞 두 값"이라고 했던 것이 스택의 맨 위 두 칸이다.

```js
function evalRPN(tokens) {
  const stack = []; // 아직 연산자에 쓰이지 않은 값들
  for (const tok of tokens) {
    if (OPS.has(tok)) {
      const b = stack.pop(); // 나중에 넣은 값이 오른쪽 피연산자
      const a = stack.pop();
      stack.push(apply(a, b, tok)); // 결과는 다음 연산자의 피연산자가 된다
    } else {
      stack.push(Number(tok)); // "-11" 같은 음수도 Number가 그대로 읽는다
    }
  }
  return stack.pop();
}
```

토큰마다 넣기나 꺼내기를 상수 번 하니 시간은 O(n)이다. 공간은 스택 크기 O(n)인데, 최악은 숫자가 앞에 몰리고 연산자가 뒤에 몰린 `1 1 1 ... + + +` 같은 식이다. 숫자 n/2개가 한꺼번에 쌓인다.

### 왜 먼저 꺼낸 값이 오른쪽인가

`a - b`를 계산하려면 `a`를 먼저 넣고 `b`를 나중에 넣었어야 한다. 식이 `a b -` 순서로 적히기 때문이다. 스택은 나중에 넣은 것이 먼저 나오니, 첫 `pop()`이 `b`, 두 번째 `pop()`이 `a`다. 더하기와 곱하기는 순서를 바꿔도 같아서 실수가 드러나지 않고, 빼기와 나누기에서만 답이 틀린다. 이 실수는 뒤에서 실제 입력으로 다시 본다.

### 스택에 값이 하나 남는 이유

숫자는 스택 크기를 1 늘리고, 연산자는 두 개를 꺼내 하나를 넣으니 1 줄인다. 올바른 식에서는 숫자가 연산자보다 정확히 하나 많아서 끝에 크기가 1이 된다. 그리고 중간 어느 지점에서도 연산자를 만났을 때 스택에 두 개 이상이 있다. 이 두 조건이 "올바른 후위 표기식"의 정의와 같다. 입력이 올바르다는 보장이 없을 때는 이 두 조건을 검사하면 된다. 꼬리 질문에서 다시 다룬다.

### Python과 Java에서 나눗셈이 다르게 끝난다

이 문제를 Python으로 풀 때 가장 많이 틀리는 곳이 나눗셈이다. Python의 `//`는 내림(floor)이라 음수에서 -무한대 쪽으로 간다. `-7 // 2`는 -4다. 문제는 0 쪽으로 버리라고 했으니 -3이 나와야 한다. `int(a / b)`를 쓰면 실수 나눗셈 뒤 0 쪽으로 잘라서 -3이 나온다.

```python
from typing import List

def eval_rpn(tokens: List[str]) -> int:
    stack = []
    for tok in tokens:
        if tok in ("+", "-", "*", "/"):
            b = stack.pop()  # 나중에 넣은 것이 오른쪽 피연산자
            a = stack.pop()
            if tok == "+":
                stack.append(a + b)
            elif tok == "-":
                stack.append(a - b)
            elif tok == "*":
                stack.append(a * b)
            else:
                stack.append(int(a / b))  # 0 쪽으로 버린다. a // b 는 내림이라 음수에서 틀린다
        else:
            stack.append(int(tok))
    return stack.pop()
```

`int(a / b)`는 중간에 실수(float)를 거친다. 이 문제는 값이 32비트 범위라서 실수 오차로 몫이 틀어질 일이 없지만, 수십 자리 정수가 오는 변형이라면 실수가 정밀도를 잃는다. 그때는 부호를 따로 떼고 절댓값끼리 `//`로 나눈 뒤 부호를 붙인다.

Java의 `int` 나눗셈은 원래 0 쪽으로 버리므로 `a / b` 그대로 맞다. 내림이 필요할 때 쓰는 건 `Math.floorDiv`다. 숫자는 많아야 토큰 수만큼 쌓이니 `int[]`를 스택으로 쓰면 `Deque<Integer>`의 박싱을 피할 수 있다.

```java
class Solution {
    public int evalRPN(String[] tokens) {
        int[] stack = new int[tokens.length]; // 숫자는 많아야 tokens 개수만큼 쌓인다
        int top = 0;
        for (String tok : tokens) {
            switch (tok) {
                case "+" -> { int b = stack[--top], a = stack[--top]; stack[top++] = a + b; }
                case "-" -> { int b = stack[--top], a = stack[--top]; stack[top++] = a - b; }
                case "*" -> { int b = stack[--top], a = stack[--top]; stack[top++] = a * b; }
                case "/" -> { int b = stack[--top], a = stack[--top]; stack[top++] = a / b; } // int 나눗셈은 0 쪽으로 버린다
                default -> stack[top++] = Integer.parseInt(tok);
            }
        }
        return stack[top - 1];
    }
}
```

`switch`를 문자열로 하는 덕분에 `"-11"`은 `"-"`와 같지 않아 `default`로 가서 숫자로 읽힌다. 세 언어 모두 예시에서 11, `["6", "-4", "/"]`에서 -1(내림이었다면 -2), `["7", "-2", "/", "3", "*"]`에서 -9를 낸다.

같은 입력으로 비교해 보면 언어별 차이가 한눈에 보인다.

```text
식         JS Math.trunc  JS Math.floor  Python int(a/b)  Python //  Java /  Java Math.floorDiv
-7 / 2         -3             -4              -3             -4        -3          -4
-6 / 4         -1             -2              -1             -2        -1          -2
```

## 뒤에서부터 읽으면 재귀가 된다

후위 표기식의 맨 마지막 토큰은 언제나 가장 나중에 계산되는 연산자, 식 전체의 뿌리다. 예시의 마지막 `-`가 `(4 + 2 * 5)`와 `9 / 3`을 빼는 연산이었다. 그러면 뒤에서부터 읽으면서 "이 연산자의 오른쪽 식, 그다음 왼쪽 식"을 차례로 재귀로 계산할 수 있다.

```js
function evalRPN(tokens) {
  let pos = tokens.length - 1; // 뒤에서부터 읽는다
  function evalNext() {
    const tok = tokens[pos--];
    if (!OPS.has(tok)) return Number(tok); // 숫자는 그 자체로 식 하나
    const b = evalNext(); // 뒤에서 읽으니 오른쪽 식이 먼저 나온다
    const a = evalNext();
    return apply(a, b, tok);
  }
  return evalNext();
}
```

예시를 따라가면 `-`를 읽고 오른쪽 식을 구하러 들어가서 `/`, `3`, `9`를 읽어 3을 얻는다. 그다음 왼쪽 식으로 `+`, `*`, `5`, `2`, `4`를 읽어 14를 얻고, 14 - 3 = 11을 돌려준다. 토큰을 정확히 한 번씩 읽으니 O(n)이다.

이 풀이는 스택이 없어진 게 아니라 호출 스택으로 옮겨 간 것이다. 공간은 재귀 깊이만큼인데, `1 1 + 1 + 1 + ...`이나 `1 1 1 ... + + +`처럼 한쪽으로 길게 늘어진 식에서는 깊이가 연산자 수만큼, 토큰 9999개면 5000쯤 된다. Node.js는 기본 설정에서 이 깊이를 버텼지만 Python은 기본 재귀 한도가 1000이라 같은 입력에서 `RecursionError: maximum recursion depth exceeded`가 났다. `sys.setrecursionlimit`으로 늘릴 수는 있어도 면접에서 먼저 꺼낼 풀이는 아니다. 재귀와 호출 스택 이야기는 [재귀와 백트래킹 글](/posts/recursion-backtracking)에 있다.

그래도 이 관점은 알아 둘 만하다. 후위 표기식이 사실 "식 트리를 후위 순회한 결과"라는 걸 보여 주기 때문이다. 뿌리가 맨 끝에 있고, 그 앞에 오른쪽 부분 트리, 다시 그 앞에 왼쪽 부분 트리가 있다. 이 구조를 알면 뒤에 나오는 "중위 표기로 바꿔라" 같은 변형이 쉬워진다.

## 식 트리를 세워 두면 여러 번 계산할 수 있다

재귀 풀이에서 본 식 트리를 실제로 만들어 둘 수도 있다. 스택 풀이와 똑같이 왼쪽부터 읽되, 숫자 대신 노드를 쌓는다. 연산자가 오면 노드 두 개를 꺼내 그 연산자 노드의 오른쪽, 왼쪽 자식으로 붙이고 새 노드를 다시 쌓는다. 끝에 남은 노드 하나가 뿌리다.

```js
function buildTree(tokens) {
  const stack = [];
  for (const tok of tokens) {
    if (OPS.has(tok)) {
      const right = stack.pop(); // 계산 대신 노드로 묶는다
      const left = stack.pop();
      stack.push({ op: tok, left, right });
    } else stack.push({ value: tok }); // 잎 노드
  }
  return stack.pop();
}

function evaluate(node, vars = {}) {
  if (node.op === undefined) return node.value in vars ? vars[node.value] : Number(node.value);
  return apply(evaluate(node.left, vars), evaluate(node.right, vars), node.op); // 후위 순회
}
```

예시로 만든 트리는 높이가 4이고 `evaluate`가 11을 낸다. 아래 그림은 그 트리에서 값이 잎에서 뿌리 쪽으로 올라가는 모습이다. 화살표 위 숫자가 그 부분 식을 계산한 값이다.

이 트리를 왼쪽 자식, 오른쪽 자식, 자기 자신 순서로 방문하면(후위 순회) `4 2 5 * + 9 3 / -`가 그대로 나온다. 후위 표기식은 이 트리를 한 줄로 펼친 것이고, 스택 풀이는 펼친 줄을 다시 접으면서 값을 계산하는 과정이다.

이 문제 하나만 계산한다면 노드를 만드는 비용만 더 드는 풀이다. 쓸모가 생기는 건 같은 식을 여러 번 계산할 때다. 잎에 `x` 같은 변수를 허용하면, 트리는 한 번만 세우고 값만 바꿔 계산할 수 있다. `["x", "x", "*", "3", "x", "*", "-", "2", "+"]`는 `x * x - 3 * x + 2`인데, `x`에 0부터 4까지 넣으면 `2, 0, 0, 2, 6`이 나온다. 스프레드시트 수식이나 템플릿 엔진이 식을 미리 해석해 두고 값만 바꿔 다시 계산하는 방식이 이것이다.

시간은 세우기 O(n), 계산 한 번에 O(n)이다. 공간은 노드 n개와 계산할 때의 재귀 깊이다. `evaluate`도 재귀라서 한쪽으로 긴 식에서는 앞 절과 같은 깊이 문제가 있다. 트리 순회 자체는 [이진 트리 직렬화 글](/posts/leetcode-serialize-and-deserialize-binary-tree)에서 더 다룬다.

## 입력 배열을 스택으로 다시 쓰기

스택 풀이에서 스택 크기는 지금까지 읽은 토큰 수를 넘지 않는다. 토큰 하나를 읽으면 스택이 많아야 한 칸 늘어나기 때문이다. 그러면 따로 배열을 만들지 않고, 이미 읽고 지나간 `tokens`의 앞부분을 스택으로 써도 된다. 스택의 맨 위 위치 `top`은 언제나 지금 읽는 위치 `i` 이하라서, 아직 읽지 않은 토큰을 덮어쓸 일이 없다.

```js
function evalRPN(tokens) {
  let top = 0; // tokens[0..top-1]이 스택이다
  for (let i = 0; i < tokens.length; i++) {
    const tok = tokens[i];
    if (OPS.has(tok)) {
      tokens[top - 2] = apply(tokens[top - 2], tokens[top - 1], tok); // 두 칸을 한 칸으로
      top--;
    } else {
      tokens[top++] = Number(tok); // 읽은 자리 이하에만 쓴다
    }
  }
  return tokens[0];
}
```

아래 그림은 같은 예시에서 배열 앞부분이 스택처럼 쓰이는 모습이다. 칸의 글자는 원래 토큰이고, 기억 장소가 그 순간 배열 앞 `top`칸에 들어 있는 값이다. 초록색 칸은 이미 읽고 지나가 스택 자리로 다시 쓸 수 있게 된 칸이다.

## 다섯 가지 계산법의 비용

| 풀이 | 시간 | 추가 공간 | 언제 고르나 |
|---|---|---|---|
| 첫 연산자부터 접기 | O(n²) | O(n) | 손으로 푸는 과정을 확인할 때, 정답 비교용 |
| 스택 | O(n) | O(n) | 기본 답. 언어와 상관없이 안전하다 |
| 뒤에서 재귀 | O(n) | O(n) 호출 스택 | 식 트리 관점을 보여 줄 때. Python은 깊이 제한에 걸린다 |
| 식 트리 세우기 | 세우기 O(n), 계산마다 O(n) | O(n) | 같은 식을 변수 값만 바꿔 여러 번 계산할 때 |

## 빼기, 나누기, 음수에서 틀리는 코드

예시처럼 더하기와 곱하기가 많은 식에서는 맞게 나오다가, 빼기·나누기·음수가 들어가면 틀리는 코드가 많다. 실제로 돌려 본 결과와 함께 정리한다.

### 꺼내는 순서를 거꾸로 쓴다

```js
const a = stack.pop(); // 틀림: 먼저 꺼낸 것은 오른쪽 피연산자다
const b = stack.pop();
stack.push(a - b);
```

`["2", "3", "-"]`에서 정답 -1 대신 1이 나온다. `["6", "3", "/"]`은 2가 아니라 3 / 6을 0 쪽으로 버린 0이 나오고, 본문 예시는 11 대신 -14가 나왔다. 더하기와 곱하기만 있는 테스트로는 이 실수가 안 잡힌다.

### 나눗셈을 내림으로 한다

JavaScript에서 `Math.floor(a / b)`, Python에서 `a // b`를 쓰면 양수끼리는 맞고 음수가 섞이면 하나 작게 나온다. `["7", "-2", "/"]`에서 -3이 아니라 -4다. 나눗셈 자체를 빼먹고 `a / b`만 쓰면 `["7", "2", "/", "2", "*"]`가 6이 아니라 7이 된다. 3.5가 버려지지 않고 다음 곱셈까지 따라가기 때문이다.

JavaScript에서는 `Math.trunc(-1 / 3)`이 `-0`이 된다는 것도 알아 둔다. `-0 === 0`은 참이고 `JSON.stringify(-0)`은 `"0"`이라 채점에서는 문제가 없지만, `Object.is(x, 0)`으로 비교하면 다르게 나온다. `(a / b) | 0`은 32비트 정수로 바꾸면서 `-0`도 0으로 만든다. 이 문제는 값이 32비트 범위라 `| 0`도 맞는 답이다.

### 첫 글자로 연산자를 판단한다

```js
if ("+-*/".includes(tok[0])) { /* 연산자로 처리 */ } // 틀림: "-11"도 '-'로 시작한다
```

`["3", "-11", "+"]`에서 `"-11"`을 빼기로 읽어 스택에 3 하나만 있는데 두 개를 꺼내려 한다. 결과는 `NaN`이었다. 연산자인지는 토큰 전체가 연산자 문자열과 같은지로 판단한다. 길이로 거르고 싶다면 `tok.length === 1 && "+-*/".includes(tok)`처럼 길이를 먼저 본다.

### 숫자를 문자열 그대로 쌓는다

`stack.push(tok)`로 문자열을 넣으면 `"4" + 10`이 `"410"`이 된다. 빼기와 곱하기는 JavaScript가 알아서 숫자로 바꿔 주기 때문에 어떤 식은 맞고 어떤 식은 틀려서 원인을 찾기 더 어렵다. 넣을 때 `Number(tok)`로 바꾼다.

## 식의 모양을 바꿔 묻는 꼬리 질문

### 후위 표기식을 사람이 읽는 식으로 바꿔라

계산 대신 문자열을 쌓으면 된다. 연산자가 나오면 두 문자열을 꺼내 괄호로 감싸 다시 넣는다.

```js
function toInfix(tokens) {
  const stack = [];
  for (const tok of tokens) {
    if (OPS.has(tok)) {
      const b = stack.pop();
      const a = stack.pop();
      stack.push(`(${a} ${tok} ${b})`); // 계산 대신 문자열로 묶는다
    } else stack.push(tok);
  }
  return stack.pop();
}
// ["4","2","5","*","+","9","3","/","-"] → ((4 + (2 * 5)) - (9 / 3))
```

괄호를 꼭 필요한 곳에만 넣으라고 하면 연산자의 우선순위를 함께 들고 다니면서, 자식 식의 우선순위가 부모보다 낮을 때만 감싼다. 빼기와 나누기의 오른쪽 자식은 우선순위가 같아도 감싸야 한다. `8 - (3 - 2)`의 괄호는 지우면 값이 바뀐다.

### 반대로 보통 식을 후위 표기로 바꿔라

다익스트라의 차량기지(shunting-yard) 알고리즘이다. 숫자는 바로 출력하고, 연산자는 연산자 스택에 쌓는다. 새 연산자가 오면 스택 맨 위의 연산자가 우선순위가 같거나 높은 동안 꺼내 출력한 뒤 새 연산자를 넣는다. 여는 괄호는 쌓고, 닫는 괄호가 오면 여는 괄호까지 꺼낸다.

```js
function toRPN(expr) {
  const prec = { "+": 1, "-": 1, "*": 2, "/": 2 };
  const out = [], ops = [];
  for (const tok of expr.match(/\d+|[-+*/()]/g)) {
    if (/\d/.test(tok)) out.push(tok);
    else if (tok === "(") ops.push(tok);
    else if (tok === ")") { while (ops.at(-1) !== "(") out.push(ops.pop()); ops.pop(); }
    else {
      // 같은 우선순위도 먼저 꺼낸다: 왼쪽부터 계산하는 결합 방향
      while (ops.length && ops.at(-1) !== "(" && prec[ops.at(-1)] >= prec[tok]) out.push(ops.pop());
      ops.push(tok);
    }
  }
  while (ops.length) out.push(ops.pop());
  return out;
}
// "4 + 2 * 5 - 9 / 3" → ["4","2","5","*","+","9","3","/","-"]
// "8 - 3 - 2"         → ["8","3","-","2","-"]
```

첫 번째 결과가 이 글의 예시와 똑같다. `>=`의 등호가 "같은 우선순위는 왼쪽부터"를 만든다. 등호를 빼면 `8 - 3 - 2`가 `8 3 2 - -`이 되어 7이 나온다. 정답은 3이다. 거듭제곱처럼 오른쪽부터 묶는 연산자는 이 등호를 빼야 한다.

이 변환과 이 문제의 계산을 합치면 보통 식을 계산하는 계산기가 된다. LeetCode 224 Basic Calculator(괄호와 덧셈·뺄셈), 227 Basic Calculator II(사칙연산, 괄호 없음)가 이 흐름이다. 실제로는 변환과 계산을 따로 하지 않고 숫자 스택과 연산자 스택 두 개를 동시에 돌린다.

### 입력이 올바르다는 보장이 없다면

앞에서 본 두 조건을 검사한다. 연산자를 만났는데 스택에 두 개가 없으면 피연산자가 모자란 식이고, 끝났을 때 스택에 하나가 아니면 피연산자가 남는 식이다. 0으로 나누기, 숫자도 연산자도 아닌 토큰, 32비트를 넘는 중간값도 오류로 돌려준다. 실무에서 사용자가 입력한 식을 계산한다면 이 검사가 계산보다 길어진다.

### 연산자가 앞에 오는 전위 표기라면

`- + 4 * 2 5 / 9 3`처럼 연산자가 피연산자 앞에 오는 폴란드 표기는 배열을 뒤에서부터 읽으면 후위 표기와 같은 방식으로 풀린다. 달라지는 건 꺼내는 순서 하나다. 뒤에서 읽으면 왼쪽 피연산자가 나중에 읽혀 나중에 쌓이니, 이번에는 먼저 꺼낸 값이 왼쪽이다.

```js
function evalPrefix(tokens) {
  const stack = [];
  for (let i = tokens.length - 1; i >= 0; i--) {
    const tok = tokens[i];
    if (OPS.has(tok)) {
      const a = stack.pop(); // 뒤에서 읽으니 이번엔 먼저 꺼낸 값이 왼쪽
      const b = stack.pop();
      stack.push(apply(a, b, tok));
    } else stack.push(Number(tok));
  }
  return stack.pop();
}
// ["-", "+", "4", "*", "2", "5", "/", "9", "3"] → 11
```

같은 식이라 답도 11이다. "어느 쪽이 먼저 꺼내지나"를 외우지 말고 "어느 쪽이 나중에 쌓였나"를 따지면 두 표기 모두 헷갈리지 않는다.

### 단항 연산자나 함수가 섞인다면

`neg`(부호 바꾸기)처럼 피연산자가 하나인 연산자는 스택에서 하나만 꺼낸다. `max`처럼 인자가 둘인 함수는 이항 연산자와 똑같이 다룬다. 연산자마다 몇 개를 꺼내는지(arity)를 표로 들고 있으면 스택 풀이는 그대로 확장된다. 후위 표기는 괄호 없이도 인자 수만 알면 식이 하나로 정해지기 때문이다.

### 토큰이 스트림으로 들어온다면

스택 풀이는 왼쪽부터 한 번 읽고 지나가므로 토큰을 하나씩 받으면서 계산할 수 있다. 메모리는 그 순간 스택 크기만큼만 쓴다. 재귀 풀이는 뒤에서부터 읽어야 하니 전체를 다 받기 전에는 시작할 수 없다. 자바 가상 머신(JVM)이나 파이썬 바이트코드도 이런 스택 기계 방식이다. `a - b`를 컴파일하면 `a`를 쌓고, `b`를 쌓고, 빼기 명령이 두 값을 꺼내 결과를 쌓는다.

## 계산 순서가 곧 쓰는 순서

후위 표기에서 연산자는 늘 바로 앞에 남아 있는 두 값을 쓴다. 가장 최근 값부터 쓰니 스택에 쌓아 두고, 연산자가 오면 두 개를 꺼내 계산한 값을 다시 넣으면 O(n)에 끝난다. 먼저 꺼낸 값이 오른쪽 피연산자이고, 나눗셈은 언어마다 다른 기본 동작을 확인해 0 쪽으로 버린다. 식 끝의 연산자가 식 트리의 뿌리라는 걸 알면 재귀 풀이와 표기 변환 문제까지 같은 그림으로 이어진다.

## 면접에서 나올 만한 질문

### 왜 스택을 쓰나요?

후위 표기식에서 연산자는 바로 앞에 남아 있는 두 값을 피연산자로 쓴다. 가장 최근에 생긴 값부터 먼저 쓰이니 나중에 넣은 것을 먼저 꺼내는 스택과 정확히 맞는다. 계산 결과도 다음 연산자의 피연산자가 되므로 다시 스택에 넣는다.

### 스택에서 꺼낸 두 값 중 어느 쪽이 왼쪽 피연산자인가요?

두 번째로 꺼낸 값이 왼쪽이다. 식이 `a b -` 순서로 적혀 `a`가 먼저 쌓이고 `b`가 나중에 쌓이니, 첫 `pop()`이 `b`다. 순서를 바꾸면 더하기·곱하기는 맞고 빼기·나누기만 틀려서, `["2", "3", "-"]`처럼 빼기가 들어간 테스트로 확인한다.

### 음수 나눗셈은 어떻게 처리하나요?

문제는 0 쪽으로 버리라고 한다. Java의 `int` 나눗셈은 원래 그렇게 동작하지만 Python의 `//`와 JavaScript의 `Math.floor`는 내림이라 `-7 / 2`가 -4로 나온다. Python은 `int(a / b)`, JavaScript는 `Math.trunc(a / b)`를 쓴다. Python의 `int(a / b)`는 실수를 거치니 아주 큰 정수에서는 부호를 떼고 정수 나눗셈을 한다.

### 시간과 공간 복잡도는요? 공간을 줄일 수 있나요?

토큰마다 상수 번 넣고 꺼내니 시간 O(n), 스택은 숫자가 앞에 몰린 식에서 n/2까지 커져 공간 O(n)이다. 스택 크기가 읽은 토큰 수를 넘지 않으니 입력 배열의 읽고 지나간 앞부분을 스택으로 쓰면 추가 공간 O(1)이 된다. 다만 입력을 바꾸므로 그래도 되는지 먼저 확인한다.

### 스택 없이 풀 수 있나요?

맨 끝 토큰이 식 트리의 뿌리이니 뒤에서부터 읽는 재귀로 풀 수 있다. 오른쪽 식을 먼저 계산하고 왼쪽 식을 계산한다. 하지만 스택이 호출 스택으로 옮겨 간 것뿐이라 공간은 같고, 한쪽으로 긴 식에서는 깊이가 수천이 되어 Python 기본 재귀 한도 1000을 넘는다.

### 입력이 잘못된 식일 수 있다면 무엇을 검사하나요?

연산자를 만났을 때 스택에 두 개 이상 있는지, 끝났을 때 스택에 정확히 하나 남는지를 본다. 숫자는 스택을 1 늘리고 연산자는 1 줄이니, 이 두 조건이 올바른 후위 표기식의 조건과 같다. 그 밖에 0으로 나누기, 알 수 없는 토큰, 오버플로를 오류로 처리한다.

### 보통 쓰는 중위 표기식은 어떻게 계산하나요?

차량기지 알고리즘으로 후위 표기로 바꾼 뒤 이 문제처럼 계산하거나, 숫자 스택과 연산자 스택을 동시에 돌리며 바로 계산한다. 연산자가 들어올 때 스택 맨 위 연산자의 우선순위가 같거나 높으면 먼저 꺼내 계산하는데, 같은 우선순위도 꺼내야 `8 - 3 - 2`가 왼쪽부터 계산되어 3이 된다.
