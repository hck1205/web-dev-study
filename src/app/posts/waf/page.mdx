  WAF는 문 안쪽에 서서 편지를 뜯어 읽는 문지기다. 공격처럼 생긴 표현을 찾을 때마다 점수를 매기고, 편지를 끝까지 읽은 뒤 점수가 기준을 넘으면 돌려보낸다. 문제는 문지기가 사람이 만든 모양 목록으로 판단하다 보니, 공부 기록으로 쓴 평범한 댓글도 공격으로 오해해 막을 수 있다는 점이다.

웹 방화벽을 켜고 하루가 지나자 문의가 들어왔다. "댓글을 쓰면 403이 떠요." 댓글 내용은 `오늘 배운 쿼리: select name from users where id = 1; 생각보다 쉽다`였다. 공격이 아니라 공부 기록이다. 같은 날 접근 로그에는 `id=1' OR '1'='1` 같은 진짜 공격도 403으로 막혀 있었다. 둘을 같은 이유로 막은 장치가 WAF(Web Application Firewall, 웹 애플리케이션 방화벽)다.

이 글은 WAF가 무엇을 읽고 어떻게 점수를 매겨 막는지, 그리고 이 댓글 같은 오탐을 어떻게 좁게 풀어 주는지를 따라간다. 실습은 Ubuntu 24.04 컨테이너에서 nginx 1.24 + ModSecurity v3(3.0.12) + OWASP CRS 3.3.5(모두 Ubuntu 패키지)를 127.0.0.1에만 띄워서 했다. 막히는 요청은 한두 개만 보냈고, 우회 기법은 개념으로만 다룬다.

이 주제의 다른 글: 패킷 내용을 네트워크 길목에서 보는 [IDS와 IPS](/posts/ids-ips), 요청 수로 막는 [레이트 리밋 실전](/posts/rate-limiting-in-practice). 요청 내용이 아니라 양으로 밀어붙이는 공격은 [DDoS 방어](/posts/ddos-protection)에서 층별로 다룬다. WAF가 막으려는 공격 자체는 [SQL 인젝션](/posts/sql-injection), [XSS](/posts/xss), [CSRF](/posts/csrf), [SSRF](/posts/ssrf) 글에서 자세히 본다.

## 443번이 열려 있으면 방화벽은 할 일이 끝난다

[iptables](/posts/iptables-basics)나 [보안 그룹](/posts/security-groups-nacl) 같은 L3/L4 방화벽은 출발지 IP, 목적지 포트, 연결 상태를 본다. 443번을 열었으면 443번으로 오는 TCP는 다 들여보낸다. 그 안의 HTTP 요청이 `id=1`인지 `id=1' OR '1'='1`인지는 모른다. TLS로 암호화돼 있으니 봐도 읽을 수 없다.

WAF는 그 위층에서 일한다. TLS가 풀린 뒤의 HTTP 요청을 해석해서 메서드, URI, 쿼리 인자, 헤더, 쿠키, 본문(폼, JSON, XML, multipart)을 꺼내고, 규칙과 맞춰 본다. 응답 본문을 보고 스택 트레이스나 SQL 에러 문구가 새어 나가는지 검사하는 규칙도 있다. 아래 그림에서 다음을 누르면 같은 클라이언트가 보낸 요청 네 개가 어디서 갈리는지 볼 수 있다.

[IDS/IPS](/posts/ids-ips)도 패킷 내용을 보지만 출발점이 다르다. IDS/IPS는 네트워크 길목에서 여러 프로토콜의 패킷을 다시 이어 붙여 보는 장치이고, WAF는 HTTP 하나만 깊게 해석하는 [리버스 프록시](/posts/proxy-reverse-proxy) 계층의 장치다. HTTPS를 그대로 통과시키는 네트워크 IPS는 내용을 못 보지만, WAF는 TLS를 끝내는 자리(로드 밸런서, CDN 엣지, nginx)에 붙어 있어서 평문을 본다. 반대로 말하면 WAF는 TLS가 끝나는 곳에만 둘 수 있다.

## 규칙은 점수를 더하고 마지막에 한 번 판정한다

ModSecurity는 규칙 엔진이고, 실제 규칙 묶음은 OWASP CRS(Core Rule Set)다. CRS의 기본 동작은 이상 점수(anomaly scoring) 방식이다. 규칙 하나가 걸렸다고 바로 막지 않는다. 걸린 규칙마다 심각도에 따라 점수를 더하고, 요청 본문까지 다 본 뒤에 합계를 문턱값과 비교한다.

CRS 3.3.5의 `REQUEST-901-INITIALIZATION.conf`에 적힌 기본값은 이렇다. CRITICAL 5점, ERROR 4점, WARNING 3점, NOTICE 2점. 요청 문턱값(`tx.inbound_anomaly_score_threshold`)은 5, 응답 문턱값은 4다. SQL 인젝션 규칙은 대부분 CRITICAL이라 하나만 걸려도 5점이고, 문턱 5에 바로 닿는다. 프로토콜 위반 같은 가벼운 규칙은 하나로는 안 막히고 여러 개가 겹쳐야 막힌다.

요청이 ModSecurity 안에서 지나는 단계는 다섯 개다. phase 1은 요청 헤더, phase 2는 요청 본문, phase 3은 응답 헤더, phase 4는 응답 본문, phase 5는 로그다. CRS의 판정 규칙 949110은 phase 2 끝에서 돈다. 아래 그림은 앞의 댓글 요청이 지나간 길이다.

점수 방식이 생긴 이유는 오탐 때문이다. 옛 ModSecurity 규칙은 규칙 하나가 걸리면 바로 막았다(self-contained 방식). 그러면 가벼운 이상 징후 하나에도 사용자가 막힌다. 점수를 모으면 "가벼운 의심 하나는 넘기고, 여러 개가 겹치거나 확실한 것 하나면 막는다"를 문턱값 하나로 조절할 수 있다. 대신 판정이 마지막에 한 번이라 로그를 볼 때 949110 한 줄만 보면 안 되고, 그 앞에 쌓인 규칙들을 같이 봐야 한다.

직접 점수를 계산해 보자. 걸린 규칙들의 심각도와 문턱값을 받아 점수와 판정을 돌려주는 함수다.

## 막힌 요청과 로그 한 줄

로컬 nginx에 CRS를 붙이고 요청 다섯 개를 보냈다. Host 헤더를 이름으로 준 건, IP를 Host로 쓰면 920350("Host header is a numeric IP address", WARNING 3점) 규칙이 매번 걸려 점수가 섞이기 때문이다.

```bash
# 로컬 실습용 nginx (127.0.0.1:18916 → 백엔드 127.0.0.1:18917)
U=http://127.0.0.1:18916; H="Host: shop.example.test"
curl -s -o /dev/null -w 'normal   %{http_code}\n' -H "$H" "$U/products?id=1"                               # 평범한 조회
curl -s -o /dev/null -w 'sqli     %{http_code}\n' -H "$H" "$U/products?id=1%27%20OR%20%271%27=%271"          # 따옴표로 조건을 깨려는 요청
curl -s -o /dev/null -w 'search   %{http_code}\n' -H "$H" "$U/search?q=select+chair"                       # 의자를 검색했을 뿐
curl -s -o /dev/null -w 'name     %{http_code}\n' -H "$H" "$U/search?q=O%27Brien"                          # 따옴표가 든 이름
curl -s -o /dev/null -w 'comment  %{http_code}\n' -H "$H" -X POST \
  --data-urlencode "body=오늘 배운 쿼리: select name from users where id = 1; 생각보다 쉽다" "$U/posts/42/comments"
```

```text
normal   200
sqli     403
search   200
name     200
comment  403
```

`select chair`와 `O'Brien`은 통과했다. 단어 하나, 따옴표 하나로 막지 않는다는 뜻이다. 막힌 두 요청은 nginx 에러 로그에 이렇게 남는다(태그 항목은 길어서 뺐다).

원인은 감사 로그(`SecAuditLog`)에 있다. 감사 로그는 요청 하나를 `---ID---A--`부터 `---ID---Z--`까지 섹션으로 나눠 쓴다. A는 시간과 주소, B는 요청 헤더, F는 응답 헤더, H는 걸린 규칙 목록이다. 댓글 요청의 H 섹션은 이랬다.


한글이 `\xec\x98\xa4`처럼 바이트로 찍혀 있다. 그리고 여기에 오탐의 이유가 보인다. 942360의 정규식은 `^[\W\d]+\s*?` 다음에 `select` 같은 키워드가 오는 값을 잡는다. "값의 맨 앞이 기호나 숫자뿐이고 바로 SQL 키워드가 시작한다"를 공격의 모양으로 본 것이다. 그런데 이 정규식에게 한글은 `\w`(영문, 숫자, 밑줄)가 아니라 `\W`다. 영어로 쓴 같은 문장과 비교해 봤다.

```text
200 <- today I learned: select name from users where id = 1; easy
403 <- 오늘 배운 쿼리: select name from users where id = 1; 생각보다 쉽다
200 <- select name from users
```

영어 문장은 `today`가 단어 문자라 패턴의 앞부분에 맞지 않아 통과한다. 한글 문장은 "기호 덩어리 뒤에 select"로 읽혀 걸렸다. 한국어 서비스에서 CRS를 그대로 켜면 영어권 서비스보다 오탐이 더 나올 수 있다는 걸 보여 주는 실제 사례다. 규칙을 만든 사람의 입력 분포와 우리 사용자의 입력 분포가 다르다.

## 막기 전에 먼저 세기만 한다

처음부터 막는 모드로 켜면 위의 댓글 같은 사고가 운영에서 터진다. 그래서 WAF는 거의 항상 탐지 전용 모드로 시작한다. ModSecurity는 `SecRuleEngine DetectionOnly`, AWS WAF는 규칙 그룹의 Count 동작, Cloudflare는 Log 동작이 같은 역할이다. 규칙은 다 돌고 로그도 남지만 막지는 않는다.

```bash
# 엔진을 탐지 전용으로 바꾸고 설정을 다시 읽는다
sed -i 's/^SecRuleEngine On/SecRuleEngine DetectionOnly/' modsecurity.conf
nginx -p "$PWD" -c "$PWD/nginx.conf" -s reload
```

같은 다섯 요청을 다시 보냈다.

```text
normal   200
sqli     200
search   200
name     200
comment  200
```

전부 200이다. 이때 nginx 에러 로그는 0줄이었다. 막지 않았으니 error 레벨로 남길 게 없다. 판정 기록은 감사 로그에만 `ModSecurity: Warning.`으로 남는다.

```text

```

여기서 흔한 실수가 하나 나온다. 탐지 모드로 일주일 돌린 뒤 에러 로그만 보고 "아무것도 안 걸렸다"며 막는 모드로 바꾸는 것이다. 탐지 모드의 결과는 감사 로그(또는 클라우드 WAF의 샘플 요청, 로그 대시보드)에서 봐야 한다. 이 기간에 할 일은 정해져 있다.

1. 949110이 "막았을" 요청을 전부 모은다.
2. 그중 정상 요청을 골라 원인 규칙과 인자(위의 `ARGS:body`)를 적는다.
3. 같은 규칙과 인자 조합이 반복되면 예외를 만든다.
4. 문턱을 높게 두고 막는 모드로 바꾼 뒤, 오탐이 잦아들면 문턱을 내린다.

어느 정도면 충분한지는 트래픽 모양에 달려 있다. 월말 정산, 이벤트 페이지처럼 가끔만 쓰는 기능이 있으면 그 기능이 한 번은 돌아가는 기간을 지켜본다.

## 오탐은 규칙을 끄지 말고 과녁을 좁힌다

오탐을 만나면 가장 쉬운 해결은 942360을 통째로 끄는 것이다(`SecRuleRemoveById 942360`). 그러면 사이트 전체의 모든 인자에서 그 규칙이 사라진다. 댓글 하나 때문에 상품 검색, 로그인 폼까지 구멍이 생긴다. 예외는 "어느 경로의, 어느 인자를, 어느 규칙에서" 빼는지 세 가지를 다 좁혀서 쓴다.

```text
# 댓글 본문(body)은 SQL 인젝션 규칙에서만 빼고, 나머지 규칙과 다른 인자는 그대로 검사한다
SecRule REQUEST_URI "@rx ^/posts/[0-9]+/comments$" \
    "id:1000100,phase:1,pass,nolog,\
    ctl:ruleRemoveTargetByTag=attack-sqli;ARGS:body"
```

ModSecurity의 예외 도구는 크게 네 가지다. 시작할 때 적용되는 `SecRuleRemoveById`(규칙 통째로 끄기)와 `SecRuleUpdateTargetById`(특정 인자만 빼기), 요청마다 조건을 보고 적용하는 `ctl:ruleRemoveById`와 `ctl:ruleRemoveTargetById`(또는 `ByTag`)다. 넓은 것부터 좁은 것 순이니, 좁은 쪽을 먼저 고려한다. ## 편집증 수준을 올리면 생기는 일

CRS는 규칙마다 편집증 수준(Paranoia Level, PL) 1~4가 붙어 있다. PL1은 오탐이 거의 없는 규칙만, PL2부터는 더 공격적으로 잡는 규칙이 추가된다. 금융이나 관리자 화면처럼 오탐 비용보다 침해 비용이 훨씬 큰 곳은 PL2~3을 쓴다. 3.x에서는 `tx.paranoia_level`, CRS 4.x에서는 `tx.blocking_paranoia_level`로 이름이 바뀌었다.

```text
SecAction "id:900000,phase:1,pass,nolog,t:none,setvar:tx.paranoia_level=2"
```

PL2로 올리고 같은 요청을 보내자 점수가 크게 바뀌었다. 아래 그림은 SQL 인젝션 요청 하나에 걸린 규칙이 차례로 점수를 쌓는 모습이다.

## JSON 본문은 따로 켜야 읽는다

이번 실습에서 직접 겪은 실수다. 처음 설정에는 ModSecurity 권장 설정 파일(`modsecurity.conf-recommended`)에 있는 JSON 처리 규칙을 넣지 않았다. 그 상태에서 JSON 본문에 SQL 인젝션을 실어 보냈다.

```bash
# JSON 본문의 id 필드에 같은 SQLi를 넣는다
curl -s -o /dev/null -w 'json-sqli %{http_code}\n' -H "$H" -H 'Content-Type: application/json' \
  --data '{"id":"1'"'"' OR '"'"'1'"'"'='"'"'1"}' "$U/products/search"
```

```text
json-sqli 200
```

통과했다. ModSecurity v3는 Content-Type만 보고 JSON 파서를 고르지 않는다. 폼 본문은 기본으로 인자로 나누지만, JSON은 아래 규칙으로 파서를 지정해야 `ARGS:json.id` 같은 인자가 생긴다.

```text
SecRule REQUEST_HEADERS:Content-Type "^application/json" \
     "id:'200001',phase:1,t:none,t:lowercase,pass,nolog,ctl:requestBodyProcessor=JSON"
```

```text
json-sqli 403
[id "942100"] [data "Matched Data: s&sos found within ARGS:json.id: 1' OR '1'='1"] [id "949110"] Total Score: 5
```

API 서버 앞에 WAF를 두고 폼 요청으로만 테스트하면 이 구멍을 못 본다. `application/vnd.api+json`이나 `text/plain`으로 JSON을 보내는 클라이언트가 있으면 정규식도 넓혀야 한다. WAF가 본문을 어떻게 해석하는지와 앱이 어떻게 해석하는지가 다르면, 그 차이 자체가 우회 통로가 된다. 이걸 파서 차이(parser differential)라고 부른다.

### 검사 비용은 인자 수에 비례한다

같은 설정으로 요청 지연을 쟀다. WAF가 없는 server 블록(18918)과 CRS가 붙은 블록(18916)에 순서대로 요청을 보내 중앙값(p50)과 p99를 봤다. POST 본문은 상품 250개(필드 750개)가 든 14,011바이트 JSON이다.

```text
body bytes 14011
waf off GET p50/p99 ms 0.738 4.007
waf off POST p50/p99 ms 0.7 1.354
waf on  GET p50/p99 ms 4.213 6.894
waf on  POST p50/p99 ms 191.192 305.634
```

GET은 약 3~4ms가 붙었다. JSON을 켠 뒤의 POST는 190ms 정도로 뛰었다. 900개 넘는 규칙이 인자 750개를 하나씩 훑기 때문이다. 이 숫자는 CPU 4개짜리 컨테이너에서 nginx 워커 하나로 잰 것이라 절대값은 환경마다 다르지만, "인자가 많은 큰 JSON은 WAF가 비싸다"는 방향은 같다. 그래서 큰 업로드나 대량 등록 API는 본문 크기 제한, 검사 대상에서의 경로 제외, 별도 검증 경로 같은 결정을 따로 한다. 성능 때문에 경로를 빼면 그 경로는 WAF의 보호를 못 받는다는 것도 같이 기록한다.

## 어디에 세울까: 엣지, 프록시, 앱 안

WAF를 놓는 자리는 세 가지다. CDN이나 클라우드 로드 밸런서에 붙은 관리형 WAF(AWS WAF, Cloudflare WAF, Cloud Armor), 직접 운영하는 리버스 프록시(nginx나 Apache에 ModSecurity, Go 기반 Coraza), 앱 프로세스 안에서 함수 호출을 보는 방식(RASP)이다. 관리형은 공격 트래픽을 오리진에 오기 전에 버리고 규칙 갱신을 맡길 수 있다. 직접 운영은 규칙과 로그를 마음대로 다룰 수 있지만 사람과 CPU가 든다.

마지막 단계는 오리진 IP가 드러나 엣지를 건너뛰는 문제다. 관리형 WAF를 붙였다면 오리진의 [보안 그룹](/posts/security-groups-nacl)을 CDN 대역만 받게 잠그거나, CDN이 붙이는 비밀 헤더나 mTLS(Cloudflare의 Authenticated Origin Pulls 같은 기능)로 엣지를 거친 요청인지 확인한다.

## 관리형 WAF 규칙은 이렇게 생겼다

AWS WAF의 웹 ACL은 JSON으로 표현된다. 아래는 공통 규칙 그룹을 넣되 본문 크기 규칙만 Count로 돌리고, SQLi 규칙 그룹은 그룹 전체를 Count(탐지 전용)로 시작하는 예시다. 이 컨테이너에는 AWS 계정이 없어서 실제로 적용해 보지는 않았고, 필드 이름과 구조는 AWS WAFv2 API 형식 그대로다.

```json
{
  "Name": "shop-web-acl",
  "Scope": "REGIONAL",
  "DefaultAction": { "Allow": {} },
  "Rules": [
    {
      "Name": "AWS-AWSManagedRulesCommonRuleSet",
      "Priority": 10,
      "Statement": {
        "ManagedRuleGroupStatement": {
          "VendorName": "AWS",
          "Name": "AWSManagedRulesCommonRuleSet",
          "RuleActionOverrides": [
            { "Name": "SizeRestrictions_BODY", "ActionToUse": { "Count": {} } }
          ]
        }
      },
      "OverrideAction": { "None": {} },
      "VisibilityConfig": {
        "SampledRequestsEnabled": true,
        "CloudWatchMetricsEnabled": true,
        "MetricName": "common"
      }
    },
    {
      "Name": "AWS-AWSManagedRulesSQLiRuleSet",
      "Priority": 20,
      "Statement": {
        "ManagedRuleGroupStatement": { "VendorName": "AWS", "Name": "AWSManagedRulesSQLiRuleSet" }
      },
      "OverrideAction": { "Count": {} },
      "VisibilityConfig": {
        "SampledRequestsEnabled": true,
        "CloudWatchMetricsEnabled": true,
        "MetricName": "sqli"
      }
    }
  ],
  "VisibilityConfig": {
    "SampledRequestsEnabled": true,
    "CloudWatchMetricsEnabled": true,
    "MetricName": "shop-web-acl"
  }
}
```

`OverrideAction: Count`는 그룹 안 규칙들이 Block이어도 세기만 하게 만든다. 앞에서 본 탐지 전용 모드다. `RuleActionOverrides`는 그룹 안의 규칙 하나만 동작을 바꾼다. `SizeRestrictions_BODY`는 본문이 8KB를 넘으면 막는 규칙이라 파일 업로드나 큰 JSON을 받는 API에서 가장 먼저 오탐을 내는 규칙으로 자주 꼽힌다. 막힌 요청은 WAF 로그에 이런 모양으로 남는다(예시).

```json
{
  "timestamp": 1792541975000,
  "formatVersion": 1,
  "webaclId": "arn:aws:wafv2:ap-northeast-2:111122223333:regional/webacl/shop-web-acl/0b1c2d3e-4f50-6172-8394-a5b6c7d8e9f0",
  "terminatingRuleId": "AWS-AWSManagedRulesCommonRuleSet",
  "terminatingRuleType": "MANAGED_RULE_GROUP",
  "action": "BLOCK",
  "httpSourceName": "ALB",
  "ruleGroupList": [
    {
      "ruleGroupId": "AWS#AWSManagedRulesCommonRuleSet",
      "terminatingRule": { "ruleId": "CrossSiteScripting_BODY", "action": "BLOCK" }
    }
  ],
  "httpRequest": {
    "clientIp": "203.0.113.7",
    "country": "KR",
    "uri": "/posts/42/comments",
    "args": "",
    "httpVersion": "HTTP/1.1",
    "httpMethod": "POST",
    "requestId": "1-6715a417-0a1b2c3d4e5f60718293a4b5"
  }
}
```

`terminatingRuleId`는 그룹 이름까지만 알려 준다. 어떤 규칙이 막았는지는 `ruleGroupList[].terminatingRule.ruleId`를 봐야 한다. ModSecurity에서 949110 한 줄만 보면 안 되는 것과 같은 구조다.

관리형 WAF는 본문을 끝까지 보지 않는다는 점도 알아 둔다. AWS WAF는 ALB 앞에서 본문 앞쪽 8KB만 검사하고, CloudFront 등에서는 기본 16KB(설정으로 64KB까지)를 본다. 그 뒤에 붙은 내용은 검사 밖이다. 그래서 크기를 넘는 본문을 어떻게 처리할지(통과, 막기, 규칙 일치로 보기)를 설정에서 정한다. 업로드가 없는 API라면 크기를 넘는 본문은 막는 쪽이 안전하다.

## 우회는 어디서 생기나

WAF는 "공격처럼 생긴 문자열"을 찾는 장치라 근본적인 한계가 있다. 우회 페이로드 목록을 외울 필요는 없고, 우회가 생기는 구조만 알면 된다.

- 표현을 바꾸는 것. 같은 SQL을 대소문자, 주석, 인코딩을 바꿔 쓰면 정규식이 놓칠 수 있다. CRS가 규칙마다 `t:urlDecodeUni`, `t:lowercase` 같은 변환(정규화)을 걸어 두는 이유다. 변환이 앱의 해석과 다르면 틈이 생긴다.
- 해석이 다른 것. 앞에서 본 JSON처럼 WAF가 본문을 못 읽거나 다르게 읽는 경우다. 같은 이름의 파라미터가 두 번 오면 WAF는 첫 번째를, 앱은 마지막을 쓰는 식의 차이도 있다.
- 검사 범위 밖. 본문 크기 제한 뒤, 검사에서 뺀 경로, 엣지를 거치지 않는 오리진 직접 접근.
- 알려지지 않은 패턴. 비즈니스 로직 취약점(남의 주문 번호로 조회하기 같은 IDOR)은 요청이 완벽하게 정상으로 생겼다. WAF는 이걸 원리적으로 못 막는다.

그래서 WAF는 앱의 입력 검증과 파라미터 바인딩을 대신하지 않는다. 앱을 고치기 전까지 시간을 버는 장치로 본다. 대표적인 쓰임이 가상 패치(virtual patching)다. 2021년 12월 Log4Shell 때 라이브러리를 업데이트하는 데 며칠이 걸리는 조직이 많았고, 관리형 WAF 벤더들은 `${jndi:` 패턴을 잡는 규칙을 며칠 안에 배포했다. AWS는 이 규칙을 Known bad inputs 그룹에 넣었다. 그동안 패치를 하고, 패치가 끝나면 가상 패치는 남겨 두되 의존하지 않는다.

## 403 문의가 왔을 때 보는 순서

"갑자기 저장이 안 돼요", "어떤 글만 403이 떠요" 같은 문의는 앱 로그를 아무리 봐도 안 나온다. 요청이 앱에 오지 않았기 때문이다. 보는 순서를 정해 두면 빠르다.

먼저 403의 주인을 가린다. nginx 기본 403 페이지인지, 클라우드 WAF의 차단 페이지인지, 앱이 내린 403인지 응답 본문과 헤더로 구분한다. 차단 응답에 요청 ID를 넣어 두면(ModSecurity의 `unique_id`, AWS WAF는 커스텀 응답 본문에 요청 ID를 넣을 수 있다) 사용자에게서 그 값만 받으면 된다.

```bash
# 시각과 경로로 차단 줄을 찾는다
grep 'id "949110"' /var/log/nginx/error.log | grep 'uri "/posts/42/comments"' | tail -3

# unique_id로 감사 로그에서 그 요청의 걸린 규칙만 뽑는다
UID=179252777586.450732
awk -v id="$UID" '$0 ~ id {f=1} f && /---H--/ {h=1; next} h && /^---/ {exit} h' /var/log/modsec_audit.log \
  | grep -o '\[id "[0-9]*"\]\|\[msg "[^"]*"\]\|against variable `[^'"'"']*'
```

```text
against variable `ARGS:body
[id "942360"]
[msg "Detects concatenated basic SQL injection and SQLLFI attempts"]
against variable `TX:ANOMALY_SCORE
[id "949110"]
[msg "Inbound Anomaly Score Exceeded (Total Score: 5)"]
```

실습한 댓글 요청의 감사 로그에 같은 명령을 돌린 결과다(로그 경로는 설정마다 다르다). 어느 인자(`ARGS:body`)가 어느 규칙(942360)에 걸렸는지가 한눈에 나온다.

그다음은 판단이다. 걸린 인자가 사용자 자유 입력(댓글, 검색어, 자기소개)이고 같은 규칙·인자 조합이 여러 사용자에게서 나오면 오탐일 가능성이 높다. 반대로 한 IP에서 여러 경로에 다양한 규칙이 걸리면 스캐너다. 오탐이면 앞에서 본 대로 경로·인자·규칙을 좁힌 예외를 만들고, 막혀야 할 요청이 여전히 막히는지 확인한 뒤 배포한다.

흔한 실수 몇 가지를 덧붙인다. 탐지 모드 결과를 에러 로그에서만 찾는 것, 오탐 하나에 규칙 전체를 끄는 것, 엣지 WAF만 믿고 오리진을 열어 두는 것, JSON API 앞에 JSON 파서 없이 WAF를 두는 것, 그리고 WAF가 막아 주니 앱의 입력 검증을 미루는 것이다.

## 문자열을 보는 문지기

WAF는 TLS가 풀린 HTTP 요청을 해석해서 공격처럼 생긴 모양에 점수를 매기는 장치다. CRS는 규칙마다 점수를 쌓고 마지막에 문턱과 비교해 막는다. 그 방식 덕분에 문턱 하나로 민감도를 조절할 수 있지만, 규칙은 사람이 만든 모양 목록이라 한글 댓글 같은 정상 입력도 공격으로 읽는다. 그래서 탐지 모드로 먼저 세고, 오탐은 좁게 예외 처리하고, 앱의 검증은 그대로 둔다.

## 면접에서 나올 만한 질문

### WAF와 일반 방화벽(보안 그룹, iptables)은 무엇이 다른가요?

보는 층이 다르다. L3/L4 방화벽은 IP, 포트, 연결 상태만 보고, 443번을 열면 그 안의 HTTP 내용은 보지 않는다. WAF는 TLS가 끝난 뒤의 HTTP 요청을 해석해서 URI, 인자, 헤더, 본문을 규칙과 맞춘다. 그래서 WAF는 TLS를 끝내는 자리(CDN, 로드 밸런서, 리버스 프록시)에 둔다.

### OWASP CRS의 이상 점수 방식은 어떻게 동작하나요?

규칙 하나가 걸렸다고 바로 막지 않고, 걸린 규칙의 심각도마다 점수를 더한 뒤 요청 본문까지 다 본 시점에 합계를 문턱과 비교한다. 기본값은 CRITICAL 5점, 요청 문턱 5라 SQLi 규칙 하나면 막히고, 가벼운 경고 하나는 넘어간다. 문턱 하나로 민감도를 조절할 수 있어서 도입 초기에 문턱을 높였다가 내리는 운영이 가능하다. 대신 로그에서 판정 규칙(949110)만 보지 말고 앞에 걸린 규칙을 함께 봐야 한다.

### WAF를 처음 도입할 때 바로 차단 모드로 켜면 안 되는 이유는요?

규칙이 우리 서비스의 정상 입력을 공격으로 볼 수 있기 때문이다. 실제로 한글 댓글 안의 SQL 예시가 CRS 942360에 걸려 막혔다. 그래서 탐지 전용(DetectionOnly, Count) 모드로 먼저 돌려 "막았을" 요청을 모으고, 오탐을 예외로 정리한 뒤 높은 문턱부터 차단을 켠다. 탐지 모드의 기록은 에러 로그가 아니라 감사 로그나 WAF 로그에 있다는 점도 챙긴다.

### 오탐이 났을 때 규칙을 끄면 안 되나요?

규칙을 통째로 끄면 사이트 전체의 모든 인자에서 그 검사가 사라진다. 경로, 인자, 규칙 세 가지를 좁혀 "이 경로의 이 인자만 이 규칙 묶음에서 뺀다"로 예외를 건다. 예외를 넣은 뒤에는 같은 경로의 다른 공격이 여전히 막히는지 확인하고, 예외마다 이유와 날짜를 남긴다.

### WAF가 있으면 SQL 인젝션은 안전한가요?

아니다. WAF는 공격처럼 생긴 문자열을 찾는 장치라 표현을 바꾸거나, WAF와 앱의 본문 해석이 다르거나, 검사 크기 제한 밖에 실리면 놓칠 수 있다. IDOR 같은 로직 취약점은 요청이 정상으로 생겨서 원리적으로 못 막는다. 근본 대책은 파라미터 바인딩과 입력 검증이고, WAF는 패치 전까지 시간을 버는 가상 패치와 대량 스캔 차단에 쓴다.

### 관리형 WAF를 CDN에 붙였는데도 공격이 오리진에 닿았습니다. 무엇을 의심하나요?

오리진 IP로 직접 오는 우회 경로를 먼저 본다. 엣지 WAF는 엣지를 지나는 요청만 보니, 오리진 주소가 DNS 기록이나 인증서 로그로 새면 소용이 없다. 오리진 보안 그룹을 CDN 대역만 허용하게 잠그거나, 비밀 헤더나 mTLS로 엣지를 거친 요청만 받게 한다. 그다음 본문 검사 크기 제한이나 검사에서 뺀 경로로 들어왔는지 본다.

### WAF가 지연을 늘리는 정도는 무엇에 따라 달라지나요?

규칙 수와 검사할 인자 수에 비례한다. 실습에서 GET은 3~4ms가 붙었지만, 필드 750개짜리 14KB JSON을 파싱해서 검사하자 p50이 190ms 정도로 뛰었다. 그래서 큰 본문을 받는 API는 크기 제한, 경로별 정책, 별도 검증 같은 결정을 따로 하고, 검사에서 뺀 경로는 보호 밖이라는 걸 기록한다.
