  그래서 컴포넌트 이름은 대문자로 시작하고, 받은 재료는 고치지 않고, 그리는 동안에는 바깥을 건드리지 않는다는 규칙이 생겼다.

장바구니가 비어 있으면 아무것도 보이지 않아야 하는 자리에 숫자 `0`이 하나 찍혀 있다. 다른 화면에서는 새로 만든 버튼 컴포넌트가 아예 나오지 않는다. 콘솔을 열면 `The tag <myButton> is unrecognized in this browser`라는 경고가 있다. 검색창에 글자를 한 자 칠 때마다 커서가 빠져나가는 입력칸도 있다.

세 증상은 서로 상관없어 보이지만 원인이 한 곳에 있다. JSX가 실제로 무엇으로 바뀌는지, 그 결과물이 어떤 모양인지를 모르고 쓰면 생기는 일들이다. 이 글은 JSX 한 줄이 함수 호출로 바뀌는 과정에서 시작해 컴포넌트를 쓸 때 지켜야 하는 규칙들이 왜 생겼는지 따라간다. 리렌더링이 언제 일어나는지는 [React는 언제 다시 그리나](/posts/react-rerender)에서 다뤘으니, 여기서는 그보다 한 단계 아래인 "컴포넌트와 JSX가 무엇인가"를 본다.

## JSX는 함수 호출로 바뀐다

브라우저는 JSX를 모른다. `<div className="card">`를 자바스크립트 파일에 그대로 넣으면 문법 오류다. 빌드 도구(TypeScript, Babel, SWC, esbuild)가 이 모양을 평범한 함수 호출로 바꿔서 브라우저에 넘긴다.

```tsx
function Greeting({ name }) {
  return (
    <div className="card">
      <h1>안녕, {name}</h1>
      <Avatar size={48} />
    </div>
  );
}
```

이 코드를 TypeScript 5.9의 `transpileModule`에 `jsx: "react-jsx"` 설정으로 넣으면 이렇게 나온다.

```js
import { jsxs as _jsxs, jsx as _jsx } from "react/jsx-runtime";
function Greeting({ name }) {
    return (_jsxs("div", { className: "card", children: [_jsxs("h1", { children: ["안녕, ", name] }), _jsx(Avatar, { size: 48 })] }));
}
```

`<div ...>`는 `_jsxs("div", 속성 객체)`가 됐다. 태그 이름은 첫 번째 인자, 속성은 두 번째 인자의 객체, 안에 든 것들은 그 객체의 `children` 속성으로 들어갔다. 자식이 여러 개면 `jsxs`, 하나면 `jsx`를 부른다. 차이는 `children`이 배열인지 하나인지다. 한글 문자열이 `안녕`으로 바뀐 건 출력 형식일 뿐이고 값은 그대로 "안녕"이다.

같은 코드를 예전 방식(`jsx: "react"`)으로 바꾸면 모양이 다르다.

```js
function Greeting({ name }) {
    return (React.createElement("div", { className: "card" },
        React.createElement("h1", null,
            "안녕, ",
            name),
        React.createElement(Avatar, { size: 48 })));
}
```

여기서는 `React.createElement(타입, 속성, ...자식)`를 부르고, 자식은 세 번째 인자부터 나열된다. 이 코드에는 `import`가 없는데 `React`라는 이름을 쓴다. 그래서 React 16까지는 JSX를 쓰는 모든 파일 맨 위에 `import React from "react"`가 있어야 했다. 안 쓰는 것처럼 보여도 지우면 `React is not defined`로 깨졌다.

React 17에서 들어온 새 JSX 변환(이후 16.14 같은 일부 이전 버전에도 백포트됐다)은 컴파일러가 `react/jsx-runtime`에서 필요한 함수를 알아서 import한다. 파일마다 React를 불러올 필요가 없어졌고, `key`를 props와 따로 받는 함수 모양이라 런타임이 할 일도 조금 줄었다. 개발 빌드에서는 `react/jsx-dev-runtime`의 `jsxDEV`를 불러서, 경고를 띄울 때 쓸 정보를 함께 넘긴다.

설정은 `tsconfig.json`의 `jsx`에서 고른다. `react-jsx`가 새 변환, `react`가 예전 변환이고, `preserve`는 JSX를 그대로 두고 뒤에 오는 도구(예전 Next.js라면 SWC)에게 맡긴다. 이 블로그가 쓰는 Next.js 16은 `react-jsx`로 둔다.

새 변환에도 예외가 하나 있다. props를 펼친 뒤에 `key`를 쓰면 옛 함수로 돌아간다.

```tsx
const spread = <Btn {...props} key="k" />;
```

```js
import { createElement as _createElement } from "react";
const spread = _createElement(Btn, { ...props, key: "k" });
```

`props` 안에 `key`가 들어 있을지 컴파일러가 알 수 없으니, 둘을 섞어서 처리하는 `createElement`를 쓴다. 동작은 같다. `key`를 펼치기보다 앞에 쓰면(`<Btn key="k" {...props} />`) 새 변환을 그대로 쓴다.

아래 그림에서 다음을 누르면 JSX 한 줄이 화면이 되기까지 누가 무엇을 넘기는지 보인다.

## 엘리먼트는 그냥 객체다

`jsx()`가 돌려주는 것을 React 엘리먼트라고 부른다. 직접 찍어 보면 정말 평범한 객체다. React 19.3, Node 22에서 개발 빌드(`NODE_ENV=development`)와 프로덕션 빌드로 같은 엘리먼트를 만들어 출력했다.

```js
const { jsx, jsxs } = require("react/jsx-runtime");
const el = jsxs("div", {
  className: "card",
  children: [jsx("h1", { children: "안녕" }), jsx(Avatar, { size: 48 }, "a1")],
});
console.log(el);
console.log(el.props.children[1]);
```

```text
  _store: {}

--- 프로덕션 빌드

  props: { className: 'card', children: [ [Object], [Object] ] }

```

볼 칸은 네 개다. `type`은 무엇을 그릴지다. 문자열 `'div'`면 HTML 태그이고, 함수 `Avatar`면 컴포넌트다. `props`는 넘긴 속성과 `children`이다. `key`는 형제 사이에서 이 엘리먼트를 알아볼 이름표인데, props 안이 아니라 바깥 칸에 따로 있다. 그래서 컴포넌트 안에서 `props.key`를 읽으면 `undefined`가 나온다. 개발 빌드에만 있는 `_owner`, `_store`는 경고 메시지를 만들 때 쓰는 내부 정보다.

`$$typeof`는 이 객체가 React가 만든 엘리먼트라는 표시다. 값이 `Symbol`인 데는 이유가 있다. 서버가 사용자 입력을 JSON으로 내려 주고 그 값을 그대로 자식으로 그리는 코드가 있다고 하자. 공격자가 `type`과 `props`를 갖춘 객체를 JSON에 심어도, JSON에는 Symbol을 담을 수 없으니 `$$typeof`가 맞지 않아 React가 엘리먼트로 취급하지 않는다. 객체를 자식으로 넣으면 `Objects are not valid as a React child` 오류가 나는 것도 같은 검사다. 이 장치가 막는 건 엘리먼트 위조 한 가지이고, `dangerouslySetInnerHTML`이나 `href="javascript:..."` 같은 다른 길은 [XSS](/posts/xss)에서 따로 다뤘다.

React 19부터 `ref`는 props의 한 칸으로 들어간다. 함수 컴포넌트가 `forwardRef` 없이 `props.ref`로 받을 수 있게 된 이유다. 프로덕션 출력에 남은 `ref: null`은 예전 모양과의 호환을 위한 칸이고, 개발 빌드에서 `element.ref`를 읽으면 경고가 뜬다.

엘리먼트가 객체라는 사실에서 몇 가지가 따라 나온다. 엘리먼트를 변수에 담아 두었다가 나중에 쓸 수 있다. 배열에 넣어 목록으로 그릴 수 있다. props로 다른 컴포넌트에 넘길 수도 있다(`icon={<Star />}`). 그리고 만드는 비용이 싸다. 객체 하나를 만드는 것뿐이라서, 화면 전체의 엘리먼트를 매번 새로 만들어도 그 자체는 느리지 않다. 느려지는 건 그 엘리먼트를 따라 컴포넌트 함수를 부르고 이전 트리와 비교하는 일이다.

## 컴포넌트, 엘리먼트, 인스턴스

세 말이 자주 섞여 쓰이는데 가리키는 게 다르다.

컴포넌트는 함수다. `function Avatar(props) { ... }`라고 정의한 그것이다. props를 받아 엘리먼트를 돌려준다.

엘리먼트는 그 함수가 돌려주는 객체, 또는 JSX가 만드는 객체다. `<Avatar size={48} />`는 "Avatar를 size 48로 그려 달라"는 주문서이고 Avatar 함수를 부르지 않는다. 부르는 건 React다.

인스턴스는 React가 화면의 한 자리마다 들고 있는 기록이다. 클래스 컴포넌트 시절에는 `new`로 만든 객체가 실제로 있었다. 함수 컴포넌트에는 그런 객체가 없지만, React 내부에 자리마다 기록이 있어서 그 자리의 state와 effect가 거기 저장된다. 같은 `Avatar` 컴포넌트를 화면 세 곳에 쓰면 함수는 하나, 엘리먼트는 렌더링마다 새로 만들어지는 세 개, 자리 기록은 세 개다. 함수 컴포넌트가 렌더링마다 처음부터 다시 실행되는데도 `useState`가 값을 기억하는 건, 값이 함수 안이 아니라 이 자리 기록에 있기 때문이다.

## 이름이 소문자면 태그가 된다

처음 증상의 두 번째, 버튼이 안 보이던 문제다. 컴포넌트 이름을 `myButton`으로 지었다.

```tsx
function myButton() {
  return <b>hi</b>;
}

<div><myButton /></div>
```

변환 결과를 보면 이유가 바로 보인다.

```js
const lower = _jsx("myButton", {});
```

소문자로 시작한 JSX 태그는 문자열이 된다. 변수 `myButton`이 아니라 글자 `"myButton"`이다. React는 이걸 HTML 태그 이름으로 보고 `document.createElement("myButton")`을 한다. React 19.3 개발 빌드로 jsdom에서 그려 보면 경고 두 줄과 함께 빈 태그가 생긴다.

```text
<myButton /> is using incorrect casing. Use PascalCase for React components, or lowercase for HTML elements.
The tag <myButton> is unrecognized in this browser. If you meant to render a React component, start its name with an uppercase letter.
```

```text
<div><mybutton></mybutton></div>
```

HTML은 태그 이름의 대소문자를 구분하지 않으니 `mybutton`이라는 이름 없는 태그가 됐고, 안에는 아무것도 없다. 오류가 아니라 경고라서 화면은 멀쩡히 뜨고 버튼만 없다. 규칙은 하나다. 컴포넌트 이름은 대문자로 시작한다.

같은 이유로 태그를 변수로 고를 때도 대문자 변수에 담는다.

```tsx
function Heading({ level, children }) {
  const Tag = `h${level}`;          // "h2" 같은 문자열
  return <Tag>{children}</Tag>;     // 대문자 변수라 _jsx(Tag, ...)가 된다
}

const icons = { star: Star, heart: Heart };
const Icon = icons[name];           // icons[name]을 JSX 태그에 바로 쓸 수는 없다
<Icon size={16} />
```

점이 들어간 이름(`<Menu.Item />`)은 소문자로 시작해도 변수로 읽힌다. `<motion.div />` 같은 라이브러리 문법이 그래서 동작한다.

## props는 읽기 전용이다

앞의 출력에서 개발 빌드의 props는 얼어 있었다(`Object.isFrozen`이 `true`). 컴포넌트 안에서 props를 고치면 어떻게 되는지 같은 환경에서 시험했다.

```js
"use strict";
el.props.className = "x";
```

```text
--- 개발 빌드
Cannot assign to read only property 'className' of object '#<Object>'
--- 프로덕션 빌드
(오류 없음. 값이 바뀐다)
```

개발 빌드에서는 엄격 모드 코드라면 바로 `TypeError`가 난다. ES 모듈과 클래스 본문은 자동으로 엄격 모드라서 보통의 React 코드는 여기에 걸린다. 프로덕션 빌드는 props를 얼리지 않으니 조용히 바뀐다. 개발 중에 안 보던 오류가 프로덕션에서는 없어진 것처럼 보이지만, 버그가 사라진 게 아니라 숨은 것이다.

props를 읽기 전용으로 두는 이유는 props의 주인이 부모이기 때문이다. 자식이 받은 객체를 고치면 부모가 들고 있는 값도 함께 바뀌는데, 부모는 그 사실을 모르니 다시 렌더링하지 않는다. 화면과 데이터가 어긋난다. 그리고 React가 "바뀌었나"를 `Object.is`로 참조 비교하기 때문에, 같은 객체 안을 고친 변화는 비교에 잡히지 않는다. 바꿔야 하는 값이면 부모의 state로 두고 부모가 바꾸게 한다. 자식은 `onChange` 같은 함수 props로 부모에게 알린다. 이 흐름은 [useState와 상태 스냅샷](/posts/react-state-snapshot-batching)에서 이어서 본다.

기본값은 구조 분해의 기본값으로 준다.

```tsx
function Avatar({ size = 40, alt = "" }) {
  return <img width={size} height={size} alt={alt} />;
}
```

함수 컴포넌트의 `defaultProps`와 `propTypes` 검사는 React 19에서 빠졌다. 오래된 코드에 남아 있으면 조용히 무시되니, 옮길 때 기본값을 구조 분해 쪽으로 옮긴다. 클래스 컴포넌트의 `defaultProps`는 여전히 동작한다. props 타입을 TypeScript로 적는 방법은 [React에서 TypeScript 쓰기](/posts/typescript-in-react#props-타입을-적는-자리)에 있다.

## children도 props 하나다

여는 태그와 닫는 태그 사이에 넣은 것은 `props.children`으로 들어온다. 특별한 통로가 아니라 이름이 `children`인 prop일 뿐이다.

```tsx
function Card({ title, children }) {
  return (
    <section className="card">
      <h2>{title}</h2>
      {children}
    </section>
  );
}

<Card title="주문 요약">
  <p>상품 3개</p>
  <p>합계 42,000원</p>
</Card>
```

자식이 하나면 `children`은 그 엘리먼트 하나, 여럿이면 배열, 문자열만 있으면 문자열, 없으면 `undefined`다. 앞의 변환 결과에서 `jsx`와 `jsxs`가 갈리던 그 차이다. 그래서 `children.length`나 `children.map`을 바로 쓰면 자식 개수에 따라 깨진다. 자식을 직접 세거나 고쳐야 하는 일은 드물고, 꼭 필요하면 `Children.toArray`를 쓸 수 있지만 React 문서도 이 API를 흔하지 않은 경우로 분류한다. 대부분은 `children`을 그대로 어딘가에 놓는 것으로 충분하다.

이렇게 받은 내용을 끼워 넣는 방식을 합성이라고 부른다. `Card`는 안에 무엇이 들어올지 몰라도 된다. 상속 대신 이 방식으로 재사용한다. 합성은 성능에도 쓸모가 있다. `children`으로 받은 엘리먼트는 부모가 만든 것이라, `Card`의 state가 바뀌어도 그 엘리먼트는 같은 객체로 남는다. 이 효과는 [상태는 내리고 내용은 올린다](/posts/react-rerender#상태는-내리고-내용은-올린다)에서 봤다.

컴포넌트는 엘리먼트 하나를 돌려줘야 한다. 형제 둘을 나란히 돌려주고 싶은데 감싸는 `div`를 두기 싫으면 Fragment를 쓴다.

```tsx
const frag = <><A /><B /></>;
```

```js
const frag = _jsxs(_Fragment, { children: [_jsx(A, {}), _jsx(B, {})] });
```

Fragment도 `type`이 특별한 값인 엘리먼트일 뿐이고, DOM에는 아무것도 남기지 않는다. 표의 `tr` 안에 `td` 여러 개를 돌려주는 컴포넌트처럼, 감싸는 요소가 HTML 구조를 깨는 곳에서 꼭 필요하다. 짧은 문법 `<>`에는 속성을 줄 수 없어서, 목록 안에서 key가 필요하면 `<Fragment key={id}>`로 길게 쓴다.

## 조건에 따라 그릴 때 새어 나오는 값

처음 증상의 첫 번째, 화면에 찍힌 `0`이다.

```tsx
function CartBadge({ items }) {
  return <div>{items.length && <span>목록</span>}</div>;
}
```

```text
<div>0</div>
```

`&&`는 왼쪽이 falsy면 왼쪽 값을 그대로 돌려준다. `items.length`가 0이면 식의 결과는 `false`가 아니라 숫자 0이다. React는 `false`, `true`, `null`, `undefined`는 그리지 않지만 숫자 0은 텍스트로 그린다. 이 동작과 `||`를 쓸 때 객체가 새는 경우는 [단락 평가](/posts/js-short-circuit#jsx-안에서-새어-나오는-값)에서 실제 출력과 함께 봤다. 규칙만 적으면, `&&` 왼쪽은 `items.length > 0`처럼 불리언으로 만들고, 둘 중 하나를 그릴 때는 삼항 연산자를 쓴다.

아무것도 그리지 않으려면 `null`을 돌려준다. React 18부터는 `undefined`를 돌려줘도 오류가 나지 않지만, 실수로 `return`을 빠뜨린 것과 구분되지 않으니 의도했다면 `null`이 읽기 좋다.

조건으로 컴포넌트를 아예 바꿀 때는 그 자리의 state가 어떻게 되는지도 생각해야 한다. `isEditing ? <Editor /> : <Viewer />`는 같은 자리에 다른 타입이 오니 바뀔 때마다 이전 것의 state가 사라진다. 같은 컴포넌트를 props만 바꿔 쓰면(`<Panel mode={isEditing ? "edit" : "view"} />`) state가 남는다. 어느 쪽이 맞는지는 원하는 동작에 따라 다르고, 이 규칙은 [이전 트리와 짝을 맞추는 규칙](/posts/react-rerender#이전-트리와-짝을-맞추는-규칙)에 있다.

## 배열을 그리면 key를 묻는다

배열은 자식으로 바로 넣을 수 있다. 보통 `map`으로 데이터를 엘리먼트 배열로 바꾼다.

```tsx
function Items({ items }) {
  return <ul>{items.map((i) => <li>{i}</li>)}</ul>;
}
```

화면은 나오지만 개발 빌드는 경고를 남긴다.

```text
Each child in a list should have a unique "key" prop.

Check the render method of `Items`. See https://react.dev/link/warning-keys for more information.
```

key는 다음 렌더링에서 "이 줄이 지난번 그 줄인가"를 알아보는 이름표다. 정적인 JSX의 자식들은 코드 위치가 곧 이름표라서 key가 필요 없다. 배열은 길이와 순서가 바뀔 수 있으니 위치만으로는 알 수 없다. 그래서 배열을 만드는 자리에서 key를 준다.

```tsx
<ul>
  {orders.map((order) => (
    <OrderRow key={order.id} order={order} />
  ))}
</ul>
```

key를 줄 때 자주 하는 실수가 있다. key는 `map` 안의 `li`가 아니라 `map`이 바로 돌려주는 엘리먼트에 준다. `OrderRow` 안쪽의 `li`에 key를 줘 봐야 배열의 원소는 `OrderRow`이니 의미가 없다. key는 형제 사이에서만 겹치지 않으면 되고, 화면 전체에서 고유할 필요는 없다. 렌더링마다 `Math.random()`으로 만든 key는 매번 다른 줄로 보여서 모든 줄이 새로 만들어진다. 인덱스를 key로 쓰면 언제 문제가 되는지는 [React는 언제 다시 그리나](/posts/react-rerender#이전-트리와-짝을-맞추는-규칙)의 그림에서 줄마다 따라가 봤다.

## 렌더링은 같은 입력에 같은 결과를 내야 한다

React는 컴포넌트 함수를 언제, 몇 번 부를지 약속하지 않는다. 부모가 렌더링되면 부르고, 동시성 렌더링에서는 하던 렌더링을 버리고 다시 부르기도 하고, 개발 모드의 `StrictMode`에서는 일부러 두 번 부른다. 그래서 컴포넌트는 같은 props와 state를 받으면 몇 번을 불러도 같은 엘리먼트를 돌려줘야 하고, 렌더링 도중에 바깥의 무엇도 바꾸지 않아야 한다. 순수 함수라는 말이 이 뜻이다.

이걸 어긴 코드를 일부러 만들었다. 렌더링할 때마다 바깥 변수의 번호표를 하나씩 뽑는다.

```tsx
let ticket = 0;

function Ticket({ name }) {
  ticket++;                                   // 렌더링 중에 바깥 변수를 바꾼다
  return <li>{name}: {ticket}번</li>;
}

function Queue() {
  return (
    <ul>
      <Ticket name="가" />
      <Ticket name="나" />
      <Ticket name="다" />
    </ul>
  );
}
```

React 19.3 개발 빌드로 그대로 그린 것과 `StrictMode`로 감싸 그린 것을 비교했다.

```text
일반:       가: 1번 나: 2번 다: 3번
StrictMode: 가: 2번 나: 4번 다: 6번
```

`StrictMode`는 컴포넌트를 두 번씩 불렀고, 화면에는 두 번째 결과가 남았다. 일반 모드에서는 맞아 보이지만, 부모가 한 번 더 렌더링되기만 해도 번호가 4, 5, 6으로 바뀐다. 화면이 렌더링 횟수에 따라 달라지는 컴포넌트다. `StrictMode`의 이중 호출은 이렇게 숨어 있는 의존을 개발 중에 드러내려는 장치다. 프로덕션 빌드에서는 한 번만 부른다.

같은 실험에서 컴포넌트 안의 `console.log`도 두 번 찍혔다. React DevTools가 설치된 브라우저에서는 두 번째 줄을 흐리게 보여 준다. 렌더링 로그가 두 번 나오는 걸 보고 버그로 오해하는 일이 많은데, 개발 모드에서는 정상이다.

순수하다고 해서 함수 안에서 아무것도 바꾸면 안 된다는 뜻은 아니다. 렌더링 중에 새로 만든 배열에 `push`하는 건 괜찮다. 아직 아무도 보지 못한 값이기 때문이다. 바꾸면 안 되는 건 렌더링 전부터 있던 것이다. props, state, 바깥 변수, DOM, 그리고 네트워크 요청이나 `localStorage` 쓰기 같은 외부 작업이 그렇다. 그런 일은 두 자리에서 한다. 사용자가 무언가를 해서 생기는 일이면 이벤트 핸들러에서, 화면이 그려졌으니 바깥을 맞춰야 하는 일이면 effect에서 한다. effect는 [useEffect를 제대로 쓰기](/posts/react-useeffect)에서 따로 다룬다. 순수 함수의 일반적인 정의와 React가 순수함에 기대는 자리는 [순수 함수와 부수 효과](/posts/js-pure-functions)에 있다.

React Compiler도 이 규칙에 기댄다. 컴파일러는 같은 입력이면 같은 결과가 나온다고 보고 계산을 기억해 두는데, 렌더링 중에 바깥을 바꾸는 컴포넌트에서는 그 가정이 깨진다.

## 컴포넌트 안에서 컴포넌트를 정의하면

처음 증상의 세 번째, 글자를 칠 때마다 커서가 빠져나가는 입력칸이다. 검색어 상태를 바깥에 두고 입력칸을 안쪽 컴포넌트로 뺐다.

```tsx
function SearchBox() {
  const [q, setQ] = useState("");

  function Field() {                     // SearchBox가 렌더링될 때마다 새로 만들어진다
    return <input value={q} onChange={(e) => setQ(e.target.value)} />;
  }

  return <Field />;
}
```

jsdom에서 입력칸에 포커스를 두고 "r"을 친 뒤, 렌더링 전후의 `input` 노드를 비교했다.

```text
같은 input 노드인가: false | 값: r | 포커스 유지: false
```

값은 `r`로 맞게 들어갔다. 상태가 바깥 `SearchBox`에 있으니까. 하지만 `input` 노드가 새것으로 바뀌었고 포커스는 사라졌다. 사용자는 한 글자 칠 때마다 입력칸을 다시 눌러야 한다.

원인은 엘리먼트의 `type`이다. `SearchBox`가 렌더링될 때마다 `function Field`가 다시 실행되어 새 함수가 만들어진다. 렌더링 1의 `Field`와 렌더링 2의 `Field`는 이름만 같고 다른 함수다. React는 같은 자리의 `type`을 `Object.is`로 비교하고, 다르면 이전 자리를 통째로 버린 뒤 새로 만든다. 그 아래 DOM 노드와 state도 함께 사라진다. 아래 그림에서 다음을 누르면 렌더링마다 React가 무엇을 보는지 따라간다.


고치는 방법은 `Field`를 바깥으로 꺼내 모듈 최상위에 정의하는 것이다. 안쪽에서 정의한 이유는 대개 `q`와 `setQ`를 클로저로 쓰고 싶어서인데, 그건 props로 넘기면 된다.

```tsx
function Field({ value, onChange }) {
  return <input value={value} onChange={(e) => onChange(e.target.value)} />;
}

function SearchBox() {
  const [q, setQ] = useState("");
  return <Field value={q} onChange={setQ} />;
}
```

`useCallback`으로 안쪽 컴포넌트를 감싸서 참조를 고정하는 우회도 있지만, 의존성이 바뀔 때마다 같은 일이 생기니 고친 게 아니다. 같은 증상은 `const Row = styled.div`를 렌더 함수 안에서 만들 때, 고차 컴포넌트를 렌더링 중에 호출할 때(`const Wrapped = withAuth(Page)`)도 나온다. 컴포넌트를 만드는 코드는 렌더링 바깥에서 한 번만 실행되게 둔다.

## createElement를 직접 만들어 본다

엘리먼트가 객체라는 걸 손으로 확인하는 가장 빠른 방법은 `createElement`를 직접 짜 보는 것이다. 아래 함수는 예전 JSX 변환이 부르던 모양을 따른다. `config`에서 `key`는 꺼내서 바깥 칸으로 옮기고(문자열로 바꾼다), 나머지는 props로 복사한다. 세 번째 인자부터 들어온 자식이 하나면 그대로, 여럿이면 배열로 `props.children`에 넣는다. 자식 인자가 있으면 `config.children`보다 우선한다. 실제 React의 `createElement`도 이 규칙대로 동작한다.

## 0 하나와 사라진 커서가 남긴 것

화면의 `0`은 `&&`가 숫자를 돌려줬고 React가 숫자를 그렸기 때문이었다. 사라진 버튼은 소문자 태그가 문자열 타입으로 바뀌었기 때문이었고, 빠져나가는 커서는 렌더링마다 새 함수가 다른 타입이 됐기 때문이었다. 셋 다 JSX가 `jsx(type, props, key)` 호출이고 그 결과가 `type`, `props`, `key`를 가진 객체라는 걸 알면 바로 풀린다. React는 이 객체 트리를 이전 것과 비교해 화면을 맞추고, 그 비교가 믿을 만하려면 컴포넌트가 같은 입력에 같은 객체를 돌려줘야 한다. 다음 글 [useState와 상태 스냅샷](/posts/react-state-snapshot-batching)에서는 그 입력 중 하나인 state가 렌더링 사이에 어떻게 이어지는지 본다.

## 면접에서 나올 만한 질문

### JSX는 무엇이고, 브라우저에서 어떻게 실행되나요?

JSX는 자바스크립트 안에서 엘리먼트를 만드는 함수 호출을 짧게 쓰는 문법이다. 브라우저는 모르기 때문에 빌드 단계에서 TypeScript나 Babel, SWC가 `jsx(type, props, key)` 같은 호출로 바꾼다. 그 함수는 화면을 그리지 않고 `type`, `props`, `key`를 가진 객체를 돌려주며, 그 객체를 받아 DOM을 만드는 건 React다.

### React 17의 새 JSX 변환은 무엇이 달라졌나요?

예전에는 JSX가 `React.createElement`로 바뀌어서 파일마다 `React`를 import해야 했다. 새 변환은 컴파일러가 `react/jsx-runtime`에서 `jsx`, `jsxs`를 알아서 불러오고, `key`를 props와 따로 받는다. 그래서 React import가 필요 없어졌고 런타임이 하는 일도 조금 줄었다. props를 펼친 뒤에 `key`를 쓰면 예외로 `createElement`로 돌아간다.

### 컴포넌트, 엘리먼트, 인스턴스는 어떻게 다른가요?

컴포넌트는 props를 받아 엘리먼트를 돌려주는 함수다. 엘리먼트는 "무엇을 어떤 props로 그릴지" 적은 평범한 객체로, 렌더링마다 새로 만들어진다. 인스턴스는 React가 트리의 자리마다 유지하는 기록이고, 함수 컴포넌트의 state와 effect가 여기 붙어 있어서 함수가 다시 실행돼도 값이 이어진다.

### 엘리먼트 객체의 `$$typeof`는 왜 Symbol인가요?

React가 만든 엘리먼트인지 확인하는 표시이고, JSON에는 Symbol을 담을 수 없어서 서버 응답에 심은 가짜 엘리먼트 객체를 걸러 낸다. 사용자 데이터가 그대로 자식으로 들어가도 React는 그걸 엘리먼트로 그리지 않고 오류를 낸다. 다만 이건 엘리먼트 위조만 막고, `dangerouslySetInnerHTML`이나 `javascript:` URL 같은 XSS 경로는 따로 막아야 한다.

### 컴포넌트 이름은 왜 대문자로 시작해야 하나요?

JSX 변환이 소문자로 시작하는 태그를 문자열로, 대문자로 시작하는 태그를 변수로 바꾸기 때문이다. `myButton`은 `"myButton"`이라는 HTML 태그가 되어 빈 요소만 생기고 개발 빌드에서 경고만 뜬다. 태그를 변수로 고를 때도 `const Tag = ...`처럼 대문자 변수에 담는다.

### props를 고치면 안 되는 이유는요? 고치면 어떻게 되나요?

props의 주인은 부모라서, 자식이 고치면 부모는 바뀐 걸 모른 채 다시 렌더링하지 않고 화면과 데이터가 어긋난다. React는 참조로 변화를 비교하니 같은 객체 안을 고친 변화는 잡히지도 않는다. 개발 빌드는 props를 얼려 두어 엄격 모드 코드에서 `TypeError`가 나고, 프로덕션은 얼리지 않아 조용히 바뀐다. 바꿔야 하는 값은 부모 state로 두고 콜백으로 바꿔 달라고 알린다.

### StrictMode에서 컴포넌트가 두 번 렌더링되는 이유는요?

렌더링이 순수한지 드러내려고 개발 모드에서 일부러 두 번 부르는 것이다. React는 렌더링을 몇 번 할지 약속하지 않으니, 렌더링 중에 바깥 변수를 바꾸거나 요청을 보내는 코드는 횟수에 따라 결과가 달라진다. 두 번 불러서 결과가 달라지면 그 코드가 문제다. 프로덕션에서는 한 번만 부르고, 이중 호출을 끄기보다 원인을 고친다.

### 컴포넌트 안에서 다른 컴포넌트를 정의하면 어떤 문제가 생기나요?

바깥이 렌더링될 때마다 안쪽 함수가 새로 만들어져서 React 눈에는 매번 다른 타입이 된다. 타입이 다르면 그 자리를 버리고 새로 마운트하니, 안쪽의 state가 초기화되고 DOM 노드가 바뀌어 입력칸 포커스가 날아간다. 컴포넌트는 모듈 최상위에 정의하고 필요한 값은 props로 넘긴다. 렌더 함수 안에서 styled 컴포넌트나 고차 컴포넌트를 만드는 것도 같은 문제다.
