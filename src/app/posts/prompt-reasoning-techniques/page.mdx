이런 문제를 모델에게 냈다고 하자. "식당에 사과가 23개 있었다. 점심에 20개를 쓰고 6개를 더 샀다. 사과는 몇 개인가?" 답만 한 단어로 쓰라고 하면 모델이 가끔 27이나 29를 내놓는다. 같은 문제에 "먼저 풀이를 쓰고 마지막 줄에 답을 써라"라고 하면 "23 − 20 = 3, 3 + 6 = 9"를 쓰고 9라고 답하는 경우가 늘어난다. 이 예는 Chain-of-Thought 논문(Wei 외, 2022)이 쓴 예제다. 모델은 같고 문제도 같은데, 답을 내는 순서만 바꿨다.

이 글은 이 차이에서 출발해 "생각을 시키는" 프롬프트 기법들을 비용과 함께 본다. 예시 없이 묻는 제로샷과 예시를 주는 퓨샷 위에 얹는 CoT, 여러 번 뽑아 다수결하는 자기 일관성, 생각의 가지를 펼쳐 평가하는 Tree of Thoughts, 한 걸음 물러서서 원리부터 묻는 step-back, 프롬프트 여러 개를 합치는 앙상블, 프롬프트를 자동으로 찾는 APE와 DSPy다. 그리고 스스로 생각하는 추론 모델이 나온 뒤 이 기법들이 왜 덜 먹히는지, 언제 여전히 쓰는지까지 간다. 프롬프트가 왜 확률을 미는 일인지와 퓨샷의 기본은 [LLM 기초 글](/posts/llm-basics-for-developers)에 있고, 기법을 바꿨을 때 정말 나아졌는지 재는 방법은 [LLM 평가 글](/posts/llm-evals)에 있다. 여기서는 그 둘을 알고 있다고 보고 이어 간다.

## 답부터 쓰면 되돌릴 수 없다

왜 순서가 답을 바꿀까. 모델은 앞의 토큰들을 보고 다음 토큰 하나를 고르는 일을 반복하고, 이미 고른 토큰은 되돌리지 않는다. 답을 첫 토큰으로 쓰게 하면 모델은 문제를 읽은 직후 한 번의 계산으로 "9"를 골라야 한다. 풀이를 먼저 쓰게 하면 "23 − 20 = 3"이라는 중간 결과가 글로 창 안에 놓인다. 마지막에 답을 고를 때 모델은 "3 + 6"이라는 훨씬 쉬운 문제를 보고 있다.

어려운 계산 하나를 쉬운 계산 여러 개로 쪼개고, 각 중간 결과를 종이(컨텍스트)에 적어 두는 셈이다. 모델이 한 토큰을 고를 때 할 수 있는 계산량은 정해져 있는데, 토큰을 더 쓰게 하면 그만큼 계산을 더 할 수 있다. 이게 CoT(Chain-of-Thought, 생각의 사슬)가 먹히는 이유를 가장 단순하게 설명하는 방법이다.

반대로 이 설명에서 한계도 나온다. 풀이 토큰이 늘어나는 만큼 출력 토큰 비용과 지연이 늘어난다. 그리고 쪼갤 계산이 없는 일(사실 하나를 묻는 질문, 짧은 분류)에서는 풀이를 써도 나아질 것이 별로 없다.

## 제로샷 CoT와 퓨샷 CoT

CoT를 거는 방법은 두 가지다.

제로샷 CoT는 예시 없이 지시만 더한다. Kojima 외(2022)의 논문은 답 앞에 "Let's think step by step"이라는 한 문장만 붙여도 당시 모델(InstructGPT 계열)의 산수 문제 정답률이 크게 오른다고 보고했다. 논문에서 MultiArith는 17.7%에서 78.7%로, GSM8K는 10.4%에서 40.7%로 올랐다. 한 문장의 효과로는 놀라운 숫자라서 이 문장이 유명해졌다.

```text
식당에 사과가 23개 있었다. 점심에 20개를 쓰고 6개를 더 샀다. 사과는 몇 개인가?

먼저 한 단계씩 풀이를 쓰고, 마지막 줄에 "답: 숫자" 형식으로만 답을 쓴다.
```

퓨샷 CoT는 풀이가 들어 있는 예시를 몇 개 보여 준다. Wei 외(2022)의 원래 CoT 논문이 이 방식이었다. 예시는 "질문 → 풀이 → 답"의 모양을 보여 주고, 모델은 그 모양을 이어 쓴다.

```text
<example>
질문: 주차장에 차가 3대 있었고 2대가 더 왔다. 차는 몇 대인가?
풀이: 처음 3대에 2대가 더해졌다. 3 + 2 = 5.
답: 5
</example>
<example>
질문: 레아는 초콜릿 32개, 언니는 42개가 있었다. 둘이 35개를 먹었다. 남은 것은 몇 개인가?
풀이: 둘이 가진 것은 32 + 42 = 74개. 35개를 먹었으니 74 − 35 = 39.
답: 39
</example>

질문: 식당에 사과가 23개 있었다. 점심에 20개를 쓰고 6개를 더 샀다. 사과는 몇 개인가?
풀이:
```

퓨샷은 풀이의 길이와 형식까지 통제할 수 있어서, 답을 코드로 뽑아야 할 때 편하다. 대신 예시 몇 개가 매 요청의 입력 토큰에 붙는다. 예시가 문제 유형과 안 맞으면 엉뚱한 풀이 방식을 베끼기도 한다. 할인율 문제에 덧셈 예시만 주면 덧셈으로 풀려고 드는 식이다.

실무에서 CoT를 쓸 때 걸리는 점이 하나 있다. 풀이와 답이 섞여 나오니 답만 뽑아내야 한다. "답: 숫자"처럼 마지막 줄 형식을 정해 두고 코드로 파싱하거나, 구조화 출력을 쓴다면 JSON 필드 순서를 `reasoning` 다음에 `answer`가 오게 둔다. 모델은 필드도 앞에서부터 쓰니, `answer`를 먼저 두면 풀이를 쓰기 전에 답을 정해 버린다. 풀이 필드를 뒤에 두면 CoT를 건 의미가 사라진다.

답 추출과 필드 순서를 코드로 쓰면 이렇다.

```ts
// 풀이 끝의 "답: ..." 줄만 뽑는다. 풀이 중간의 숫자를 답으로 오해하지 않게 마지막 것을 쓴다
function extractAnswer(text: string): string | null {
  const matches = [...text.matchAll(/^답:\s*(.+)$/gm)];
  return matches.length ? matches[matches.length - 1][1].trim() : null;
}

// 구조화 출력으로 받을 때는 풀이 필드를 먼저 둔다
const schema = {
  type: "object",
  properties: {
    reasoning: { type: "string", description: "단계별 풀이" }, // 먼저 쓰게 한다
    answer: { type: "number" }, // 풀이를 다 쓴 뒤에 답을 고른다
  },
  required: ["reasoning", "answer"],
  additionalProperties: false,
};
```

추출에 실패한 응답(형식을 어긴 응답)은 오답과 따로 센다. 둘을 섞으면 "CoT를 넣었더니 점수가 떨어졌다"가 사실은 "답 형식이 깨졌다"인 경우를 놓친다.

## 다섯 번 풀고 다수결로 고르기

자기 일관성(self-consistency, Wang 외 2022)은 CoT를 한 번만 뽑지 않고, temperature를 0보다 높게 두고 여러 번 뽑은 뒤, 마지막 답만 모아 가장 많이 나온 것을 고른다. 풀이는 버리고 답만 투표한다. 논문은 PaLM 540B에서 GSM8K 정답률이 CoT 한 번보다 17.9%p 올랐다고 보고했다.

왜 먹힐까. 맞는 풀이는 여러 길이 있어도 같은 답으로 모이지만, 틀린 풀이는 저마다 다른 곳에서 틀려 답이 흩어지는 경향이 있다. 다섯 번 중 셋이 9이고 나머지가 27, 29라면 9가 이긴다. 아래 그림에서 다음을 누르며 한 질문이 다섯 번의 샘플을 거쳐 답 하나가 되는 과정을 보자.

다수결의 효과를 숫자로 따져 보자. 샘플 하나가 맞을 확률이 0.6이고, 틀린 답이 열 가지 서로 다른 값으로 고르게 흩어진다고 하자(각 0.04). 가능한 모든 경우를 세어 정확히 계산하면(동점이면 무작위로 하나를 고른다고 쳤다) 다수결의 정답률은 1번일 때 0.6, 3번일 때 0.7344, 5번일 때 0.8873이다. 같은 0.6이라도 틀린 답이 한 값으로 몰리면(0.4) 3번에 0.648, 5번에 0.6826으로 덜 오른다.

더 중요한 경우가 있다. 샘플 하나가 맞을 확률이 0.4인데 틀린 답이 한 값으로 몰려 있으면(0.6), 다수결은 오히려 정답률을 떨어뜨린다. 3번에 0.352, 5번에 0.3174다. 모델이 일관되게 같은 실수를 하는 문제라면 투표는 그 실수를 더 확실하게 만든다. 같은 0.4라도 틀린 답이 흩어지면 5번에 0.6391까지 오른다. 자기 일관성은 "가장 흔한 답"을 고르는 방법이지 "맞는 답"을 고르는 방법이 아니다. 우리 문제에서 틀린 답이 흩어지는지 몰리는지는 평가 세트로 확인한다.

  const norm = (a) => {
    if (a == null) return "";
    const t = String(a).trim();
    const n = t.replace(/,/g, "");
    if (n !== "" && !Number.isNaN(Number(n))) return String(Number(n));
    return t;
  };
  const counts = new Map();

    if (k === "") continue;
    counts.set(k, (counts.get(k) || 0) + 1);

  let best = null;
  let bestCount = 0;
  for (const [k, c] of counts) {

      best = k;
      bestCount = c;

  }

서버 코드로는 요청 다섯 개를 동시에 보내고 위 투표기로 합친다. 일치율이 낮으면 다른 경로로 보낸다.

```ts
async function selfConsistent(question: string, n = 5) {
  const runs = await Promise.all(
    Array.from({ length: n }, () =>
      client.messages.create({
        model: process.env.FAST_MODEL!,
        max_tokens: 600,
        temperature: 0.7, // 0이면 다섯 번 다 같은 풀이가 나온다
        messages: [{ role: "user", content: cotPrompt(question) }],
      }),
    ),
  );
  const answers = runs.map((r) => extractAnswer(textOf(r)));
  const best = majorityVote(answers);
  const agreement = answers.filter((a) => a !== null && majorityVote([a]) === best).length / n;
  return { answer: best, agreement }; // agreement가 0.6 미만이면 사람 확인으로
}
```

`Promise.all`로 동시에 보내면 지연은 가장 느린 한 개만큼만 늘지만, 공급사의 분당 요청 한도는 다섯 배로 빨리 닿는다. 트래픽이 많은 기능이라면 한도부터 계산해 둔다.

자기 일관성은 답이 짧고 비교할 수 있을 때(숫자, 선택지, 분류 라벨) 쓰기 좋다. 요약이나 글쓰기처럼 답이 매번 다른 문장이면 "같은 답"을 셀 수 없다. 그럴 때는 답 여러 개를 모델에게 다시 주고 "가장 많은 답과 일치하는 것을 골라라"라고 시키는 변형(universal self-consistency라고 불린다)이 있지만, 호출이 하나 더 들고 그 선택도 확률적이다.

## 생각의 가지를 펼쳐 보는 Tree of Thoughts

CoT는 풀이를 한 줄로 쭉 쓴다. 중간에 길을 잘못 들면 되돌아오지 못한다. Tree of Thoughts(ToT, Yao 외 2023)는 풀이를 단계로 나누고, 단계마다 후보 생각을 여러 개 만들고, 각 후보가 가망이 있는지 모델에게 평가시킨 뒤, 가망 있는 것만 남겨 다음 단계로 펼친다. 막다른 가지는 버리고 다른 가지로 돌아간다. 사람이 퍼즐을 풀 때 "이 길로 가면 안 되겠다" 하고 지우개를 쓰는 것과 같다.

논문이 쓴 예제는 24 게임이다. 숫자 네 개를 사칙연산으로 한 번씩 써서 24를 만든다. 4, 9, 10, 13이 주어졌다고 하자. 첫 단계에서 두 수를 골라 계산하면 남는 수가 세 개가 된다. 각 후보를 "남은 세 수로 24를 만들 수 있을까"로 평가한다. 아래 그림에서 후보 여덟 개를 훑으며 남길 가지를 고르는 과정을 보자. 평가는 원래 모델이 "확실/아마/불가능"으로 하지만, 여기서는 모든 경우를 직접 계산해 정답을 표시했다.

## 한 걸음 물러서서 묻기

step-back 프롬프팅(Zheng 외 2023)은 질문에 바로 답하지 않고, 먼저 한 단계 일반적인 질문을 만들어 그 답(원리, 개념, 배경)을 얻은 뒤, 그 답을 근거로 원래 질문에 답하게 한다.

```text
[1단계: 물러선 질문 만들기]
원래 질문: "이상 기체의 온도를 두 배로, 부피를 여덟 배로 하면 압력은 어떻게 되나?"
이 질문에 답하려면 먼저 알아야 할 일반 원리를 묻는 질문 하나를 쓴다.
→ "이상 기체의 압력, 부피, 온도 사이에는 어떤 관계가 있나?"

[2단계: 원리에 답하기]
→ "PV = nRT. n이 같으면 P는 T에 비례하고 V에 반비례한다."

[3단계: 원리를 근거로 원래 질문에 답하기]
→ "P는 2 ÷ 8 = 1/4배가 된다."
```

먹히는 이유는 CoT와 비슷한데 방향이 다르다. CoT는 문제를 앞으로 쪼개고, step-back은 위로 올라가 원리를 먼저 꺼내 놓는다. 세부 사항이 많은 질문에서 모델이 세부에 끌려 엉뚱한 공식을 쓰는 실수를 줄인다.

이 기법이 실무에서 특히 쓸모 있는 곳은 검색이다. 사용자가 "작년 3분기 서울 지점 환불 규정 예외 건"처럼 아주 구체적으로 물으면, 그 문장 그대로는 관련 문서가 잘 안 걸린다. 한 단계 일반적인 질문("환불 규정의 예외 조건은 무엇인가")을 만들어 함께 검색하면 원리 문서가 걸린다. 질문을 고쳐서 검색하는 다른 방법들(쿼리 재작성, HyDE)은 [RAG 검색 품질 글](/posts/rag-retrieval-quality)에 있다. 대가는 호출 하나가 더 드는 것과, 그 호출을 기다리는 지연이다.

```ts
// step-back 검색: 원래 질문과 물러선 질문으로 함께 찾고 합친다
async function stepBackRetrieve(question: string) {
  const general = await ask(
    `다음 질문에 답하려면 먼저 알아야 할 일반 원리를 묻는 질문 하나만 쓴다.\n질문: ${question}`,
  );
  const [specific, broad] = await Promise.all([search(question, 5), search(general, 5)]);
  return dedupe([...specific, ...broad]); // 두 목록을 합쳐 답 생성에 넘긴다
}
```

## 프롬프트 여러 개를 섞고, 프롬프트를 자동으로 찾기

### 프롬프트 앙상블

자기 일관성은 같은 프롬프트를 여러 번 뽑는다. 프롬프트 앙상블은 서로 다른 프롬프트(다른 지시 문장, 다른 퓨샷 예시 묶음, 다른 예시 순서)로 같은 질문을 묻고 답을 합친다. 퓨샷 결과가 예시 선택과 순서에 꽤 민감하다는 보고가 많아서, 한 묶음에 운을 걸지 않고 여러 묶음의 평균을 내려는 생각이다. 분류처럼 답을 셀 수 있는 일에서 흔들림을 줄이는 데 쓴다. 비용은 프롬프트 수만큼 곱해진다.

### APE와 DSPy

어떤 지시 문장이 잘 먹힐지 사람이 하나씩 바꿔 보는 대신, 모델에게 후보 지시를 만들게 하고 평가 세트 점수로 고르는 방법이 있다. APE(Automatic Prompt Engineer, Zhou 외 2022)가 이 방식이다. 이 논문에서 찾은 문장 "Let's work this out in a step by step way to be sure we have the right answer."가 사람이 쓴 "Let's think step by step"보다 당시 모델에서 점수가 높게 나왔다는 결과로 알려졌다.

DSPy는 이 생각을 프레임워크로 만들었다. 프롬프트 문자열을 직접 쓰는 대신 "입력은 질문과 문서, 출력은 답"처럼 모듈의 입출력(시그니처)을 선언하고, 평가 지표와 학습용 예제를 주면, 옵티마이저가 퓨샷 예시를 고르거나 지시 문장을 바꿔 가며 지표가 가장 높은 프롬프트를 찾는다. 모델을 바꾸면 다시 돌려서 그 모델에 맞는 프롬프트를 새로 얻는다.

DSPy의 모양을 짧게 보면 이렇다(파이썬, DSPy 2.5 이후 문법).

```python
import dspy

dspy.configure(lm=dspy.LM("openai/gpt-4o-mini"))  # 쓸 모델

# "question을 받아 answer를 낸다"는 시그니처에 CoT 모듈을 씌운다
qa = dspy.ChainOfThought("question -> answer")

# 지표: 예제의 정답과 예측이 같으면 통과
def exact(example, pred, trace=None):
    return example.answer.strip() == pred.answer.strip()

trainset = [
    dspy.Example(question="23개에서 20개를 쓰고 6개를 사면?", answer="9").with_inputs("question"),
    # ... 평가 세트와 겹치지 않는 예제 수십 개
]

# 지표를 통과한 풀이를 퓨샷 예시로 모아 프롬프트에 넣는 옵티마이저
optimizer = dspy.BootstrapFewShot(metric=exact, max_bootstrapped_demos=4)
compiled = optimizer.compile(qa, trainset=trainset)
```

`compiled`는 모델이 실제로 맞힌 풀이를 예시로 골라 담은 프롬프트를 들고 있다. 사람이 프롬프트 문장을 고치는 대신 예제와 지표를 고친다는 점이 다르다.

둘 다 전제가 같다. 믿을 만한 평가 세트와 지표가 있어야 한다. 지표가 엉성하면 옵티마이저는 지표의 빈틈에 맞춘 프롬프트를 찾는다. 평가 세트가 작으면 그 세트에만 맞춘 프롬프트가 나온다. 자동 최적화는 [LLM 평가 글](/posts/llm-evals)의 시험지가 먼저 있어야 쓸 수 있는 도구다.

## 기법마다 드는 비용

기법을 고를 때는 정답률만 보지 않고 호출 수, 토큰, 지연을 같이 본다. 질문 200토큰, 바로 답할 때 출력 20토큰, 풀이를 쓰면 출력 300토큰, 퓨샷 예시 3개가 750토큰이라고 놓고 계산하면 이렇다. step-back은 첫 호출에서 원리 150토큰을 받고, 두 번째 호출에 질문과 원리를 함께 넣는다고 쳤다.

```text
기법                     호출   입력 토큰   출력 토큰   호출을 기다리는 순서
바로 답하기               1      200         20          1
제로샷 CoT               1      210         300         1
퓨샷 CoT (예시 3개)       1      950         300         1
자기 일관성 (5번)         5      1,050       1,500       1 (5개를 동시에)
step-back                2      550         450         2 (앞 호출을 기다린다)
ToT (위 설정)             30     -           -           3단계, 단계마다 기다린다
```

몇 가지가 보인다. CoT의 비용은 거의 출력 토큰에서 나온다. 출력 토큰 단가가 입력보다 몇 배 비싼 경우가 많아서, 출력 20토큰에서 300토큰으로 늘어난 것이 생각보다 크다. 자기 일관성은 호출을 동시에 보내면 지연은 거의 그대로지만 비용은 다섯 배다. 같은 프롬프트를 반복하니 공급사의 프롬프트 캐시가 입력 쪽 비용은 줄여 주지만 출력 쪽은 그대로다. step-back과 ToT는 호출을 순서대로 기다려야 해서 지연이 늘어나고, 대화형 화면에서는 이게 비용보다 먼저 걸린다.

## 스스로 생각하는 추론 모델이 나온 뒤

2024년 가을 OpenAI의 o1을 시작으로, 답하기 전에 스스로 긴 생각을 쓰도록 학습한 추론(reasoning) 모델들이 나왔다. DeepSeek-R1, Claude의 확장 사고(extended thinking), Gemini의 thinking 모델이 같은 계열이다. 이 모델들은 강화학습으로 "풀이를 길게 쓰고, 틀린 길을 되짚고, 검산하는" 습관을 몸에 익혔다. 말하자면 CoT가 프롬프트 기법에서 모델의 기본 동작으로 들어간 것이다.

그래서 위의 기법 몇 개는 효과가 줄었다. "한 단계씩 생각하라"는 지시는 이미 하는 일을 다시 시키는 셈이라 나아지는 게 거의 없다. OpenAI의 추론 모델 가이드도 이런 모델에는 CoT를 따로 지시하지 말고 지시를 단순하고 직접적으로 쓰라고 권한다. DeepSeek-R1 논문은 퓨샷 예시를 주면 오히려 성능이 떨어졌다며 제로샷으로 문제와 출력 형식만 적으라고 권했다. 예시의 짧은 풀이가 모델 자신의 긴 생각을 방해한다고 볼 수 있다.

대신 새로 신경 써야 할 것이 생겼다. 생각 토큰의 비용과 지연이다.

```ts
// Claude 확장 사고: 생각에 쓸 토큰 예산을 정한다
const res = await client.messages.create({
  model: process.env.REASONING_MODEL!,
  max_tokens: 16000, // 생각 + 답을 합친 상한
  thinking: { type: "enabled", budget_tokens: 8000 }, // 생각에 쓸 최대 토큰
  messages: [{ role: "user", content: question }],
});
// res.content에는 thinking 블록과 text 블록이 함께 온다
// 생각 토큰은 출력 토큰으로 청구된다
```

OpenAI 쪽은 생각의 양을 `reasoning_effort`(low, medium, high 같은 단계)로 정하고, 생각 자체는 보여 주지 않지만 사용량의 `reasoning_tokens`로 몇 토큰을 썼는지 알려 준다. 어느 쪽이든 생각 토큰은 출력 토큰 요금으로 청구된다. Claude의 일부 모델처럼 생각을 요약해서 보여 주는 경우에도, 청구는 요약이 아니라 실제로 쓴 생각 토큰 기준이다. 쉬운 질문에도 생각을 수천 토큰 쓰면, 출력 20토큰짜리 답에 비용과 지연이 수십 배 붙는다.

### 그래도 기법을 쓰는 자리

추론 모델이 있다고 위의 기법이 다 쓸모없어진 건 아니다.

작고 빠른 비추론 모델을 쓰는 자리가 여전히 많다. 대량 분류, 추출, 실시간 응답처럼 지연과 단가가 중요한 일이다. 이런 모델에 짧은 CoT를 거는 건 여전히 잘 먹히고, 추론 모델을 쓰는 것보다 싸다.

자기 일관성은 추론 모델에도 쓸 수 있다. 여러 번 뽑아 일치율을 보는 건 정답률을 올리는 용도보다, 확신이 낮은 답을 골라 사람에게 넘기는 용도로 쓸 만하다. 다만 추론 모델 한 번의 비용이 이미 크니 다섯 번은 부담이 커서, 위험이 큰 일에만 건다.

step-back은 검색 쪽에서 계속 쓴다. 모델이 혼자 생각을 잘해도 검색 질문을 고쳐 주는 일은 별개다.

생각의 양을 일에 맞게 고르는 것이 새로운 기법이 됐다. 쉬운 요청은 생각을 끄거나 낮게, 어려운 요청만 높게 두고, 요청을 먼저 작은 모델로 분류해서 어느 쪽으로 보낼지 정하는 라우팅을 둔다. 생각 예산을 올렸을 때 평가 점수가 어디서 더 안 오르는지를 재 두면, 예산을 정하는 근거가 된다.

### 풀이가 진짜 이유라고 믿지는 않는다

CoT나 생각 블록을 보면 모델이 왜 그 답을 냈는지 알 수 있을 것 같다. 꼭 그렇지는 않다. Turpin 외(2023)의 연구는 퓨샷 예시의 정답을 늘 (A)로 몰아 두는 식으로 모델을 한쪽으로 기울이면, 모델이 그 영향을 받아 답을 바꾸면서도 풀이에는 그 이유를 전혀 쓰지 않는 경우가 많다고 보고했다. 풀이는 그럴듯한 설명일 수 있지 실제 계산 과정의 기록이라는 보장이 없다.

실무에서는 이게 두 가지 뜻이다. 풀이를 감사 기록처럼 믿고 "모델이 이렇게 판단했다"를 근거로 쓰지 않는다. 그리고 풀이 내용을 사용자에게 그대로 보여 줄 때는, 풀이와 답이 어긋나는 경우(풀이는 9인데 답은 27)를 코드로 확인한다. 생각 블록을 보여 주는 모델이라도 공급사들이 그 내용을 사용자 화면에 그대로 노출하는 것을 권하지 않는 이유 중 하나다.

## 정답률이 안 오를 때 보는 곳

"CoT를 넣었는데 정답률이 그대로다"라면 문제의 종류부터 본다. 쪼갤 계산이 없는 사실 질문이나, 모델이 아예 모르는 지식이 필요한 질문이면 풀이를 써도 소용없다. 그건 RAG로 자료를 줘야 하는 문제다. 또 답 추출이 실패하고 있지 않은지 본다. 풀이 중간의 숫자를 답으로 뽑고 있으면 CoT가 오히려 점수를 떨어뜨린 것처럼 보인다.

"자기 일관성을 켰는데 오히려 떨어졌다"면 틀린 답이 한 값으로 몰리는 문제인지 본다. 평가 세트에서 문제마다 다섯 샘플의 답 분포를 찍어 보면, 일관되게 같은 오답을 내는 문제가 보인다. 그런 문제는 투표가 아니라 프롬프트나 자료로 고친다. temperature가 너무 낮아 다섯 샘플이 같은 답만 내는 것도 흔한 실수다.

"추론 모델로 바꿨더니 느리고 비싸졌는데 점수는 비슷하다"면 생각 예산을 낮춰 보고, 요청을 분류해 어려운 것만 추론 모델로 보내는 라우팅을 둔다. 퓨샷 예시와 "단계별로 생각하라"는 지시를 그대로 옮겨 왔다면 먼저 빼고 다시 잰다.

"응답이 중간에 잘린다"면 `max_tokens`를 본다. CoT나 생각 토큰은 출력 한도를 함께 쓴다. 풀이가 길어진 만큼 답이 나오기 전에 한도에 닿아 끝날 수 있다. Claude 확장 사고에서는 `max_tokens`가 `budget_tokens`보다 커야 한다.

## 생각에도 값이 붙는다

생각을 시키는 기법들은 모두 같은 원리 위에 있다. 모델이 답을 고르기 전에 쓸 수 있는 토큰을 늘려 주거나(CoT, step-back), 여러 번 뽑아 흔한 답을 고르거나(자기 일관성, 앙상블), 가지를 나눠 막다른 길을 버린다(ToT). 그리고 모두 토큰과 호출로 값을 치른다. 추론 모델은 이 생각을 모델 안으로 가져왔고, 이제 고를 것은 기법이 아니라 생각의 양과 그 값이다. 어느 쪽이든 정말 나아졌는지는 평가 세트로 잰다.

## 면접에서 나올 만한 질문

### Chain-of-Thought는 왜 정답률을 올리나요?

모델은 한 토큰씩 고르고 이미 쓴 토큰을 되돌리지 않아서, 답을 먼저 쓰게 하면 한 번의 계산으로 답을 정해야 한다. 풀이를 먼저 쓰게 하면 중간 결과가 컨텍스트에 남아, 마지막 답을 고를 때 훨씬 쉬운 문제를 보게 된다. 토큰을 더 쓰는 만큼 계산을 더 하게 해 주는 셈이다. 그래서 여러 단계 계산이 있는 문제에서 효과가 크고, 사실 하나를 묻는 질문에는 효과가 작다.

### 제로샷 CoT와 퓨샷 CoT는 어떻게 다르고 언제 무엇을 쓰나요?

제로샷 CoT는 "한 단계씩 풀이를 쓰라"는 지시만 붙이고, 퓨샷 CoT는 풀이가 든 예시를 몇 개 보여 준다. 퓨샷은 풀이의 길이와 형식을 통제하기 좋아 답 추출이 쉽지만, 예시만큼 입력 토큰이 늘고 예시가 문제 유형과 안 맞으면 잘못된 풀이 방식을 베낀다. 추론 모델에는 퓨샷이 오히려 방해가 된다는 보고가 있어 제로샷으로 출력 형식만 적는 편이 낫다.

### 자기 일관성은 어떻게 동작하고, 언제 역효과가 나나요?

temperature를 높여 같은 질문의 풀이를 여러 번 뽑고, 답만 모아 다수결한다. 맞는 풀이는 같은 답으로 모이고 틀린 풀이는 흩어지는 경향을 이용한다. 하지만 모델이 같은 오답을 일관되게 내면 투표가 그 오답을 굳힌다. 한 번 정답률 0.4에 오답이 한 값으로 몰리면 5번 투표의 정답률은 0.3174로 떨어진다. 답이 셀 수 있는 형태여야 하고 비용은 샘플 수만큼 곱해진다.

### Tree of Thoughts는 어떤 문제에 맞나요?

단계마다 후보 생각을 여러 개 만들고 가망을 평가해 남은 가지만 펼치는 탐색이라, 막다른 길이 있고 중간 상태를 평가할 수 있는 퍼즐·계획·제약 문제에 맞는다. 논문의 24 게임에서 GPT-4 기준 CoT 4%가 ToT 74%로 올랐다. 대신 호출이 수십 번으로 늘고 단계마다 기다려야 해서 일반 질문 답변에는 비싸다. 실무에서는 평가를 코드(테스트, 제약 검사)로 하는 탐색으로 옮기는 경우가 많다.

### step-back 프롬프팅은 무엇이고 어디에 쓰나요?

원래 질문에 바로 답하지 않고, 먼저 한 단계 일반적인 원리를 묻는 질문을 만들어 답을 얻은 뒤 그 원리를 근거로 원래 질문에 답하게 한다. 세부 사항에 끌려 엉뚱한 공식을 쓰는 실수를 줄인다. 검색에서 특히 쓸모 있어서, 너무 구체적인 사용자 질문을 일반 질문으로 바꿔 함께 검색하면 원리 문서가 걸린다. 호출이 하나 더 들고 그만큼 지연이 생긴다.

### 추론 모델에서는 왜 이 기법들의 효과가 줄었나요?

추론 모델은 강화학습으로 답하기 전에 긴 생각을 스스로 쓰고, 되짚고, 검산하도록 학습되어 CoT가 기본 동작이 됐기 때문이다. "단계별로 생각하라"는 이미 하는 일이고, 짧은 풀이가 든 퓨샷 예시는 오히려 방해가 될 수 있다. 대신 생각 토큰이 출력 요금으로 청구되고 지연이 늘어나니, 생각 예산이나 reasoning effort를 일에 맞게 고르고 쉬운 요청은 작은 모델로 보내는 라우팅이 새로운 고민이 된다.

### 모델이 쓴 풀이를 판단 근거로 믿어도 되나요?

그대로 믿으면 안 된다. 예시의 정답 위치를 한쪽으로 몰아 모델을 기울이면, 모델이 그 영향으로 답을 바꾸면서도 풀이에는 그 이유를 쓰지 않는 경우가 많다는 연구가 있다. 풀이는 그럴듯한 설명일 수 있지 실제 계산의 기록이라는 보장이 없다. 감사나 설명 책임이 필요한 결정은 모델 풀이가 아니라 코드와 규칙으로 근거를 남기고, 풀이와 답이 어긋나는지도 코드로 확인한다.

### 프롬프트를 자동으로 최적화하는 방법은 무엇이고, 전제는 무엇인가요?

APE는 모델이 후보 지시 문장을 만들게 하고 평가 세트 점수로 고르며, DSPy는 모듈의 입출력을 선언하고 지표와 예제를 주면 옵티마이저가 퓨샷 예시와 지시를 바꿔 가며 지표를 최대화한다. 모델을 바꾸면 다시 돌려 그 모델에 맞는 프롬프트를 얻는다. 전제는 믿을 만한 평가 세트와 지표다. 지표가 엉성하거나 세트가 작으면 그 빈틈과 그 세트에만 맞춘 프롬프트가 나온다.
