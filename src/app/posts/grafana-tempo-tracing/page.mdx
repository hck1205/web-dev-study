<EasyIntro>
  대시보드는 "느린 요청이 있다"는 숫자는 보여 주지만, 그게 어떤 요청이었는지는 알려 주지 않는다. 느린 요청 하나가 서비스들을 어떻게 거쳐 갔는지 적힌 기록을 trace라고 하고, Grafana Tempo는 이 trace를 쌓아 두고 찾아 주는 저장소다.

  Tempo는 큰 창고에 상자를 쌓는 방식과 닮았다. 물건마다 색인 카드를 만들지 않고, 같은 주문의 물건을 상자 하나에 넣어 그대로 쌓은 뒤 상자마다 "들어 있을 수 있는 주문 번호" 짧은 메모만 붙인다. 주문 번호를 알면 메모를 보고 해당 상자만 열면 되니 빠르다. 반대로 "결제가 느렸던 주문" 같은 조건으로 찾으면 그 기간의 상자를 다 열어 봐야 해서, 기간을 좁게 잡을수록 빠르다.

  그래서 숫자 그래프의 튄 점마다 주문 번호를 하나씩 붙여 두고, 그 번호로 곧장 상자를 여는 길을 먼저 만든다. 방금 보낸 기록이 조건 검색에 바로 안 나오는 건 최근 30초를 일부러 빼고 찾기 때문이다.
</EasyIntro>

결제 API의 p99가 0.95초로 올라갔다. 대시보드는 숫자를 정확히 보여 준다.

```text
histogram_quantile(0.99, sum by (le) (increase(traces_spanmetrics_latency_bucket{service="payments", span_kind="SPAN_KIND_SERVER"}[10m])))
=> 0.946773333333333
```

그런데 이 숫자만으로는 어떤 요청이 느렸는지, 결제 수단 때문인지 특정 고객 때문인지 알 수 없다. 느린 요청 하나를 열어 보려면 trace가 있어야 하고, 그 trace를 지표에서 바로 찾아 들어갈 길이 있어야 한다. 이 글은 Grafana Tempo로 trace를 저장하고 찾는 과정을 따라간다. Tempo가 찾아보기(색인) 없이 trace를 저장하는 방식, trace ID로 찾을 때와 조건으로 찾을 때의 차이, TraceQL로 span을 고르는 법, 저장된 trace로 지표를 만드는 두 가지 길(TraceQL 지표, metrics-generator), 지표의 튄 점에서 trace로 건너가는 exemplar까지 다룬다.

trace와 span, traceparent 전파와 샘플링은 [분산 추적 글](/posts/distributed-tracing)에서, span이 Tempo에 오기 전 거치는 Collector는 [Collector 파이프라인 글](/posts/otel-collector-pipeline)에서 다뤘다. 세 신호를 잇는 생각 자체는 [관측 가능성 글](/posts/observability-basics)에, Grafana 화면 쪽 설정은 [Grafana 대시보드 글](/posts/grafana-dashboards)에 있다. 여기서는 저장소인 Tempo를 본다.

실습은 Ubuntu 24.04에서 Tempo 3.1.1 바이너리를 하나의 프로세스(`-target=all`)로 띄우고 저장소는 로컬 디스크로 했다. 지표는 Prometheus 3.15.0이 Tempo의 remote write를 받는다. Node.js 22로 만든 생성기가 gateway → orders → (PostgreSQL, payments) 구조의 주문 trace 900건을 초당 5건씩 보냈다. 결제 수단(`payment.provider`)은 card, bank, kpay 중 하나이고, kpay의 15%쯤은 결제 서버가 0.85~0.95초 걸리게, 전체의 3%쯤은 결제가 502로 실패하게 만들었다. 실제로 느린 trace 60건, 실패 35건이 나갔다. 처음 확인용으로 보낸 5건이 섞여 있어 아래 일부 숫자는 905건 기준이다.

## 찾아보기 없이 쌓아 두는 저장소

Jaeger를 Elasticsearch나 Cassandra 위에 올리면, span이 들어올 때마다 서비스 이름·태그·시간으로 찾아보기를 만든다. 아무 조건으로나 빨리 찾을 수 있지만, 찾아보기를 만들고 들고 있는 비용이 span 수에 비례해 커진다. trace가 하루 수십억 개가 되면 저장 비용의 대부분이 찾아보기 몫이 된다.

Tempo는 반대로 간다. span을 trace 단위로 모아 블록이라는 큰 파일로 만들어 객체 저장소(S3, GCS, Azure Blob, 실습에서는 로컬 디스크)에 올리고, 블록마다 trace ID용 bloom 필터만 둔다. 실습이 끝난 뒤 저장소 디렉터리는 이랬다.

```bash
# Tempo 로컬 백엔드: 테넌트 아래에 블록 디렉터리가 하나씩 생긴다
ls -la tempo-data/blocks/single-tenant/25f0fdc6-7e40-4e11-b5ee-22e089cf8f42/
```

```text
-rw-r--r-- 1 root root 102424 Oct 22 01:24 bloom-0
-rw-r--r-- 1 root root  98024 Oct 22 01:24 data.parquet
-rw-r--r-- 1 root root     42 Oct 22 01:24 index
-rw-r--r-- 1 root root    742 Oct 22 01:24 meta.json
```

`data.parquet`가 span 본문이다. Parquet은 열 단위로 저장하는 형식이라, 서비스 이름이나 지속 시간 같은 열 하나만 읽어서 조건을 거를 수 있다. `meta.json`에는 블록의 시간 범위와 trace 수가 있다.

```text
"format": "vParquet5",
"startTime": "2026-10-22T01:24:09Z",
"endTime": "2026-10-22T01:24:45Z",
"totalObjects": 175,
"size": 98024,
"compactionLevel": 0,
```

블록 여섯 개가 각각 35초 안팎을 맡았고 trace 수를 더하면 905였다. 데이터 파일을 다 더하면 531,320바이트, span 5,430개라 span 하나에 98바이트쯤이다. 이 실습은 블록이 작아서 bloom 필터(102KB)가 데이터보다 컸지만, 블록이 쌓이고 합쳐지면(compaction) 비율은 뒤집힌다.

들어온 span이 블록이 되기까지의 길은 Tempo 3.0에서 크게 바뀌었다. 2.x까지는 ingester가 받아서 메모리와 WAL에 들고 있다가 블록을 만들었다. 3.0 변경 이력을 보면 ingester가 없어지고, 분산 구성에서는 distributor가 Kafka 호환 로그에 쓰면 live-store가 최근 데이터를 맡아 바로 답하고, block-builder가 같은 로그를 읽어 객체 저장소에 블록을 쓴다. 블록을 합치고 보관 기간이 지난 블록을 지우는 일은 backend-scheduler와 backend-worker가 나눠 한다. 실습처럼 한 프로세스로 띄우면 Kafka 없이 distributor가 live-store와 metrics-generator에 바로 넘긴다. 아래 그림에서 다음을 누르면 쓰기와 읽기가 지나는 길이 보인다.

## trace ID 하나는 bloom 필터로 찾는다

trace ID로 찾는 길이 Tempo가 가장 잘하는 일이다. 느린 trace의 ID로 바로 꺼냈다.

```bash
# trace 하나를 ID로 꺼낸다 (v2 API)
curl -s 127.0.0.1:19532/api/v2/traces/4492ca174d92bfa9693ec8c09d7cb973
```

꺼낸 span을 서비스, 이름, 종류, 길이로 줄여 찍었다.

```text
gateway GET /checkout SPAN_KIND_SERVER 957 ms
gateway POST /orders SPAN_KIND_CLIENT 955 ms
orders POST /orders SPAN_KIND_SERVER 953 ms
orders SELECT stock SPAN_KIND_CLIENT 7 ms
orders POST /pay SPAN_KIND_CLIENT 940 ms
payments POST /pay SPAN_KIND_SERVER 939 ms
```

957ms 중 939ms가 결제 서버 안이다. DB 조회는 7ms뿐이다. Tempo는 이 trace를 찾으려고 모든 블록의 데이터를 읽지 않는다. 블록마다 bloom 필터에 "이 ID가 있을 수 있나"를 묻고, "있을 수 있다"고 답한 블록만 연다. bloom 필터는 "없다"는 답은 틀리지 않고, "있다"는 답은 가끔 틀린다. 그래서 헛걸음을 조금 하더라도 놓치지는 않는다.

어느 블록에 있었는지는 trace 시작 시각(01:26:51)과 블록 시간 범위로 맞췄고, bloom 검사 과정은 Tempo의 동작 원리를 따라 그렸다. 실제 응답에는 `"metrics":{"inspectedBytes":"934354"}`가 붙어 왔다.

없는 ID를 물으면 API 버전에 따라 답이 다르다. v1(`/api/traces/<id>`)은 404를, v2는 200과 빈 `{"trace":{},"metrics":{}}`를 돌려줬다. 스크립트에서 "찾았나"를 HTTP 상태로만 판단하면 v2에서는 늘 찾은 것으로 보인다.

## 방금 보낸 trace가 검색에 안 나온다

trace를 하나 보내고, 그 trace에만 있는 속성으로 1초마다 검색해 봤다.

```bash
# probe.id가 고유한 trace 하나를 보내고 ID로, 조건으로 각각 찾는다
T=$(node probe.js $ID)
curl -s -o /dev/null -w "by-id: %{http_code}\n" 127.0.0.1:19532/api/v2/traces/$T
until [ "$(tq.sh "{ span.probe.id = \"$ID\" }" | jq '.traces | length')" = "1" ]; do sleep 1; done
```

```text
trace 02b15f8a332289d3a77a572d1db10d13
by-id: 200
search found after 31.0s
```

ID로는 바로 나왔는데 조건 검색에는 31초 뒤에 나왔다. Tempo 3.0부터 `query_frontend.query_end_cutoff`가 기본 30초다. 최근 30초는 아직 모든 live-store에 다 도착하지 않았을 수 있으니 검색 범위에서 뺀다. 불완전한 결과를 보여 주는 것보다 조금 늦게 보여 주는 쪽을 고른 것이다. 장애 대응 중에 "방금 재현한 요청이 검색에 안 잡힌다"면 이 30초를 먼저 떠올린다. 로그에서 trace ID를 복사해 ID로 열면 바로 보인다.

## TraceQL은 span 묶음을 고른다

조건으로 찾을 때는 TraceQL을 쓴다. 중괄호 하나가 "이 조건에 맞는 span들(spanset)"이고, 결과는 그런 span을 가진 trace다. 느린 결제를 찾는 질의를 조각내 보자.

실습 데이터에 여러 질의를 던져 trace 수를 셌다. 범위는 지난 1시간이다.

```bash
# tq.sh: /api/search에 TraceQL을 보내는 작은 스크립트 (limit=1000, 지난 1시간)
tq.sh '{ resource.service.name = "payments" && duration > 500ms }' | jq '.traces | length'
```

```text
{ resource.service.name = "payments" && duration > 500ms }                         → 60
{ span.payment.provider = "kpay" && resource.service.name = "payments" && duration > 500ms } → 60
{ span.payment.provider != "kpay" && resource.service.name = "payments" && duration > 500ms } → 0
{ resource.service.name = "orders" && span.payment.provider = "kpay" } | count() > 0 → 367
{ status = error }                                                                   → 35
{ resource.service.name = "orders" } >> { resource.service.name = "payments" && status = error } → 35
{ } | avg(duration) > 300ms                                                          → 60
{ duration > 500ms } | select(span.payment.provider)                                → 60
```

느린 결제 60건이 모두 kpay였고, kpay가 아닌 느린 결제는 0건이다. kpay 주문은 367건이니 그중 16%가 느렸다. 대시보드의 p99만 봐서는 나오지 않는 답이다.

몇 가지 문법이 더 보인다. `|` 뒤는 trace 안의 spanset에 대한 계산이다. `count() > 0`은 조건에 맞는 span이 하나라도 있는 trace, `avg(duration) > 300ms`는 그 trace span들의 평균 길이로 거른다. `select(...)`는 거르지 않고 결과에 그 속성을 함께 실어 달라는 뜻이다. `>>`는 구조 연산자로, 왼쪽 span의 자손 중에서 오른쪽 조건에 맞는 span을 고른다. `>`는 바로 아래 자식, `~`는 형제다. "orders가 부른 결제 중 실패한 것"처럼 호출 관계로 묻는 질의는 로그로는 만들기 어렵다.

각 응답의 `metrics.inspectedBytes`는 22만~25만 바이트였다. 블록 여섯 개(데이터 531KB) 중 필요한 열만 읽은 양이다. 찾아보기가 없으니 조건 검색은 시간 범위 안의 블록을 다 훑는다. 데이터가 커지면 질의 시간을 정하는 건 조건이 아니라 시간 범위다. "지난 7일 전체에서 이 사용자"처럼 넓게 훑는 질의는 느리고 비싸다.

그래서 자주 거르는 속성은 열로 따로 뺀다. 블록의 `meta.json`에는 따로 뺀 열(dedicated columns) 목록이 있었다.

```text

```

## 저장된 trace로 바로 숫자를 뽑는다

TraceQL에는 지표 함수도 있다. 검색처럼 블록을 읽어서, 고른 span으로 비율이나 분위수를 계산한다. 결제 서버의 p50과 p99를 결제 수단별로 물었다.

```bash
# TraceQL 지표: 지난 15분, 결제 수단별 p50·p99 (초)
curl -s -G 127.0.0.1:19532/api/metrics/query \
  --data-urlencode 'q={ resource.service.name = "payments" } | quantile_over_time(duration, .5, .99) by (span.payment.provider)' \
  --data-urlencode "start=$S" --data-urlencode "end=$E"
```

```text
bank  p=0.5   0.027287830935952107
bank  p=0.99  0.06608308843347035
card  p=0.5   0.027036513731551675
card  p=0.99  0.06576760446669115
kpay  p=0.5   0.03106720007396346
kpay  p=0.99  0.9347465497178078
```

(JSON 응답에서 라벨과 값만 옮겼다.) kpay의 p99만 0.93초로 튀었다. 그런데 bank의 p99가 66ms로 나온 건 이상하다. 생성기에서 bank 결제는 20~39ms 사이로만 만들었다. 분위수를 정확한 값이 아니라 2의 거듭제곱 간격 칸에 넣어 근사하기 때문에, 39ms짜리가 32~64ms 칸에 들어가 칸 안에서 보간된 값이 나온 것으로 보인다. 칸으로 세는 분위수가 어떻게 틀어지는지는 [지표 타입 글](/posts/metrics-types)의 히스토그램 절과 같은 이야기다. 경향을 보는 데는 충분하지만 SLO 숫자로 쓰지는 않는다.

실패 수도 바로 센다.

```text
{ resource.service.name = "payments" && status = error } | count_over_time()  → 35
```

TraceQL 지표는 미리 정하지 않은 속성으로도 나눠 볼 수 있다는 게 장점이다. `payment.provider`로 나눌 생각을 미리 하지 않았어도 trace에 그 속성만 있으면 된다. 대가는 질의할 때마다 블록을 읽는다는 것이다. 3.0 변경 이력 기준으로 질의 범위는 기본 최대 하루다. 그리고 앞에서 샘플링해 버린 trace는 셀 수 없다. 3.1에는 tracestate에 실린 샘플링 확률로 개수를 되돌려 추정하는 질의 힌트(`with(extrapolate=true)`)가 실험 기능으로 들어왔다.

## metrics-generator는 들어오는 span으로 지표를 미리 만든다

매번 블록을 읽는 대신, span이 들어올 때 지표를 만들어 Prometheus로 보내는 길도 있다. metrics-generator가 그 일을 하고, 실습에서는 두 가지 처리기를 켰다.

```yaml
metrics_generator:
  storage:
    path: /var/tempo/generator/wal
    remote_write:
      - url: http://127.0.0.1:19590/api/v1/write   # Prometheus (remote write 수신을 켜 둔다)
        send_exemplars: true
overrides:
  defaults:
    metrics_generator:
      processors: [span-metrics, service-graphs]
```

Prometheus에 생긴 지표 이름이다.

```text
traces_service_graph_request_client_seconds_bucket
traces_service_graph_request_failed_total
traces_service_graph_request_server_seconds_bucket
traces_service_graph_request_total
traces_spanmetrics_calls_total
traces_spanmetrics_latency_bucket
traces_spanmetrics_size_total
```

span-metrics는 서비스·span 이름·종류·상태별 호출 수와 지연 히스토그램이다. 결제 서버 span의 칸별 누적 개수를 봤다.

```text
le      누적
0.016   0
0.032   552
0.064   845
0.128   845
0.512   845
1.024   905
+Inf    905
```

기본 칸이 2ms에서 16.384초까지 두 배씩 늘어난다. 845건이 64ms 안이고, 60건이 0.512~1.024초 칸에 있다. 글 처음의 p99 0.947초가 이 칸에서 나왔다. 상태별 호출 수에서는 실패가 따로 보인다.

```text
traces_spanmetrics_calls_total{service="payments", span_name="POST /pay", span_kind="SPAN_KIND_SERVER", status_code="STATUS_CODE_ERROR"} 35
traces_spanmetrics_calls_total{service="payments", span_name="POST /pay", span_kind="SPAN_KIND_SERVER", status_code="STATUS_CODE_UNSET"} 870
```

service-graphs는 부르는 쪽 client span과 받는 쪽 server span을 짝지어 서비스 사이의 선을 만든다.

```text
client=user     server=gateway  connection_type=virtual_node  905
client=gateway  server=orders                                 905
client=orders   server=payments                               905
client=orders   server=shop     connection_type=database      905
```

gateway 앞에는 부른 쪽 span이 없으니 `user`라는 가상 노드가 생겼다. DB 호출에는 받는 쪽 span이 없지만 `db.namespace` 속성으로 `shop`이라는 데이터베이스 노드를 만들었다. 실패 수(`traces_service_graph_request_failed_total`)는 user→gateway, gateway→orders, orders→payments 세 선에 각각 35였다. 실패가 결제에서 시작해 위로 번졌다는 게 선마다 보인다.

## exemplar로 튄 점에서 trace를 연다

이 연결은 Grafana 데이터 소스 설정으로 만든다. 실습에서는 Grafana를 띄우지 않았으니 아래는 프로비저닝 파일의 예시다. 화면에서 어디를 누르는지는 [Grafana 대시보드 글](/posts/grafana-dashboards)에 있다.

```yaml
# grafana/provisioning/datasources/tracing.yaml (예시)
apiVersion: 1
datasources:
  - name: Prometheus
    uid: prom
    type: prometheus
    url: http://prometheus:9090
    jsonData:
      exemplarTraceIdDestinations:
        - name: traceID              # exemplar 라벨 이름 (Tempo는 traceID로 보낸다)
          datasourceUid: tempo
  - name: Tempo
    uid: tempo
    type: tempo
    url: http://tempo:3200
    jsonData:
      serviceMap:
        datasourceUid: prom          # 서비스 그래프는 Prometheus의 지표로 그린다
      tracesToLogsV2:
        datasourceUid: loki
        spanStartTimeShift: "-5m"
        spanEndTimeShift: "5m"
        filterByTraceID: true
  - name: Loki
    uid: loki
    type: loki
    url: http://loki:3100
    jsonData:
      derivedFields:
        - name: trace_id
          matcherRegex: '"trace_id":"(\w+)"'
          url: "$${__value.raw}"
          datasourceUid: tempo
```

exemplar 라벨 이름은 보내는 쪽마다 다르다. 실습에서 Tempo는 `traceID`로 보냈고, 앱의 Prometheus 클라이언트는 보통 `trace_id`로 붙인다. 이름이 어긋나면 점은 찍히는데 눌러도 아무 데도 가지 않는다. 로그 쪽 정규식도 로그 형식과 맞아야 한다. 로그에 trace ID를 남기는 법은 [구조화 로그 글](/posts/structured-logging)에 있다.

## 보관 기간과 trace 크기 한도

Tempo의 비용은 거의 객체 저장소 용량이고, 용량은 보관 기간이 정한다. 3.1.1 바이너리의 기본값을 봤다.

```bash
./tempo -h 2>&1 | grep -A1 "block-retention"
```

```text
  -backend-scheduler.provider.work.compaction.block-retention duration
    	Duration to keep blocks/traces. (default 336h0m0s)
```

기본 14일이다. 지표는 몇 달, 로그는 몇 주, trace는 며칠에서 2주로 두는 구성이 흔하다. trace는 장애를 볼 때 "최근 것"이 주로 필요하고, 오래된 경향은 metrics-generator가 만든 지표로 남기 때문이다.

다른 한도 하나는 일부러 부딪쳐 봤다. 테넌트 한도 `max_bytes_per_trace`를 500바이트로 낮추고 주문 20건(span 120개)을 보냈다.

```text
tempo_distributor_spans_received_total{tenant="single-tenant"} 120
tempo_discarded_spans_total{reason="trace_too_large",tenant="single-tenant"} 100
level=warn ... msg=TRACE_TOO_LARGE max=500 traceSz=555 totalSize=837 trace=c05e81e9ffe87d467700c0918743d81f insight=true
```

span 120개 중 100개가 버려졌다. 그 trace를 열어 보니 span이 하나만 남아 있었다.

```text
payments POST /pay SPAN_KIND_SERVER
```

서비스마다 따로 보낸 묶음 중 먼저 도착한 결제 서버의 span만 한도 안에 들었고, 나머지가 버려졌다. trace가 통째로 없는 게 아니라 일부만 남아서 더 헷갈린다. 반복문 안에서 span을 수천 개 만드는 배치 작업 하나가 이 한도에 걸리기 쉽다. "trace의 위쪽이 비어 있다"는 문의가 오면 `tempo_discarded_spans_total`의 `reason`부터 본다. 다른 흔한 이유는 테넌트 수집 속도 한도(`rate_limited`)다.

## Tempo에서 trace가 안 보일 때

현장에서 "trace가 없다"는 말은 원인이 여럿이라 순서대로 지운다.

- 방금 보낸 것인가: 조건 검색은 최근 30초를 빼고 본다. ID로 열어 본다.
- 버려졌나: `tempo_discarded_spans_total`의 이유(trace_too_large, rate_limited)와 Collector의 거절·큐 넘침 지표([Collector 글](/posts/otel-collector-pipeline))를 본다.
- 샘플링에서 빠졌나: 헤드 샘플링의 sampled 플래그가 00이면 처음부터 안 보냈다. 로그에 trace ID가 있어도 trace는 없을 수 있다.
- 보관 기간이 지났나: 기본 14일이다.
- ID 형식이 맞나: W3C trace ID는 32자 16진수다. 64비트(16자) ID를 쓰는 오래된 계측이 섞여 있으면 앞을 0으로 채운 32자로 물어야 하는 경우가 있다. 3.0에는 테넌트별로 앞을 채우는 설정이 들어왔다.

검색이 느리다면 시간 범위부터 줄이고, 자주 거르는 속성을 따로 뺀 열에 넣고, 범위 없는 `.속성` 대신 `span.`이나 `resource.`를 붙인다. 서비스 그래프에서 선이 빠졌다면 양쪽 서비스가 client와 server span을 모두 남기는지, 문맥 전파가 끊기지 않았는지를 본다. 짝이 없는 span은 선이 되지 않는다.

## 다시 0.95초 앞에서

처음의 p99 0.95초는 결제 서버 span-metrics의 1.024초 칸에서 나왔고, 그 칸의 exemplar가 trace 하나를 가리켰고, 그 trace는 결제 서버 안에서 939ms를 썼고, TraceQL로 같은 모양의 trace를 모으자 60건이 모두 kpay였다. Tempo는 찾아보기를 만들지 않는 대신 trace ID 조회를 bloom 필터로 싸게 하고, 조건 검색은 시간 범위만큼 블록을 훑는다. 그래서 지표의 exemplar나 로그의 trace ID처럼 ID를 쥐고 들어가는 길을 먼저 만들어 두고, TraceQL은 좁은 시간 범위에서 "이런 모양의 trace가 또 있나"를 묻는 데 쓴다.

## 면접에서 나올 만한 질문

### Tempo는 Jaeger + Elasticsearch 같은 구성과 저장 방식이 어떻게 다른가요?

Tempo는 속성마다 찾아보기를 만들지 않고, trace 단위로 모은 span을 Parquet 블록으로 객체 저장소에 올리고 블록마다 trace ID용 bloom 필터만 둔다. 그래서 저장 비용이 싸고 운영할 것이 객체 저장소뿐이다. 대신 조건 검색은 시간 범위 안의 블록을 열 단위로 훑어야 해서 범위가 넓으면 느리다. 찾아보기형은 아무 조건이나 빠른 대신 찾아보기를 만들고 들고 있는 비용이 크다.

### trace ID로 찾는 것과 TraceQL로 찾는 것은 내부에서 어떻게 다른가요?

ID 조회는 블록마다 bloom 필터에 ID가 있을 수 있는지 묻고, 있을 수 있다는 블록만 열어 꺼낸다. bloom의 "없다"는 틀리지 않으니 놓치지 않고 헛걸음만 가끔 한다. TraceQL은 시간 범위에 걸친 블록을 나눠 여러 querier가 필요한 열만 읽으며 조건을 검사한다. 그래서 운영에서는 exemplar나 로그로 ID를 쥐고 들어가는 길을 먼저 만들고, TraceQL은 좁은 범위의 탐색에 쓴다.

### 방금 보낸 trace가 ID로는 보이는데 검색에는 안 나옵니다. 왜인가요?

Tempo 3.0부터 검색은 기본으로 최근 30초(`query_end_cutoff`)를 뺀다. 최근 데이터가 모든 live-store에 다 도착하지 않았을 수 있어서, 불완전한 결과 대신 조금 늦은 결과를 고른 것이다. 실습에서도 ID 조회는 바로 됐고 검색은 31초 뒤에 나왔다.

### TraceQL에서 `resource.`, `span.`, 범위 없는 `.`은 무엇이 다른가요?

`resource.`는 span을 보낸 프로세스의 속성(서비스 이름, 파드)이고 `span.`은 span 하나의 속성이다. 범위 없이 `.속성`으로 쓰면 둘을 모두 뒤져서 결과는 넓지만 느리다. duration, status, name, kind 같은 고유 필드는 점 없이 쓴다. 자주 거르는 속성은 따로 뺀 열(dedicated columns)에 넣어 읽는 양을 줄인다.

### metrics-generator와 TraceQL 지표는 언제 무엇을 쓰나요?

metrics-generator는 span이 들어올 때 호출 수, 지연 히스토그램, 서비스 그래프를 미리 만들어 Prometheus로 보낸다. 대시보드와 알림처럼 늘 보는 숫자에 맞다. TraceQL 지표는 질의할 때 블록을 읽어 계산하므로 미리 정하지 않은 속성으로도 나눠 볼 수 있지만 매번 비용이 들고 범위가 제한된다. 둘 다 Tempo에 도착한 span만 보니, 앞에서 샘플링했다면 개수를 보정하거나 샘플링 전에 지표를 만든다.

### exemplar로 지표에서 trace로 건너가려면 무엇이 필요한가요?

히스토그램에 trace ID가 붙은 exemplar가 있어야 하고(metrics-generator의 send_exemplars, 앱 클라이언트의 exemplar 기능), Prometheus가 exemplar를 저장해야 하고(exemplar-storage 기능), Grafana의 Prometheus 데이터 소스에서 exemplar 라벨을 Tempo 데이터 소스와 이어야 한다. 라벨 이름(traceID와 trace_id)이 어긋나면 점은 보이는데 링크가 동작하지 않는 일이 흔하다.

### trace의 일부 span만 보입니다. 어디부터 의심하나요?

Tempo가 trace 크기 한도(`max_bytes_per_trace`)나 수집 속도 한도로 span을 버렸는지 `tempo_discarded_spans_total`의 reason으로 본다. 실습에서 한도를 넘긴 trace는 먼저 도착한 서비스의 span 하나만 남았다. 그다음 문맥 전파가 끊겨 trace가 둘로 쪼개졌는지, Collector에서 일부 묶음이 거절됐는지를 본다.
