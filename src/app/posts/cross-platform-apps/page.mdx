## 웹 서비스를 앱으로도 내야 할 때

웹으로 잘 돌아가던 서비스에 요청이 두 개 들어왔다. 하나는 "앱 스토어에 올려 주세요, 푸시 알림이 필요해요", 다른 하나는 "사내에서 쓰게 데스크톱 프로그램으로 만들어 주세요, 로컬 파일을 열어야 해요". 프런트엔드 개발자 셋이 있는 팀이 iOS, Android, Windows, macOS 앱을 따로 만들 수는 없다. 그래서 웹 기술을 재사용하는 길을 찾게 된다.

설치 없이 홈 화면에 올리고 오프라인에서 여는 정도라면 [PWA](/posts/pwa-install-offline)로 충분할 수 있다. 문제는 PWA가 닿지 못하는 곳이다. 앱 스토어 노출, iOS에서 PWA가 쓰지 못하는 네이티브 기능, 파일 시스템과 시스템 트레이 같은 데스크톱 기능이 필요하면 진짜 앱 껍데기가 있어야 한다.

선택지는 많아 보이지만 "화면을 누가 그리나"로 나누면 셋으로 줄어든다.

웹뷰 계열은 HTML과 CSS를 그대로 쓰고 OS가 가진 브라우저 엔진이 그린다. React Native는 우리 코드가 "버튼 하나, 글자 하나"를 말하면 OS의 진짜 버튼과 글자 위젯이 그린다. Flutter는 OS 위젯을 쓰지 않고 자기 렌더링 엔진으로 모든 픽셀을 직접 칠한다. Electron은 웹뷰 계열이지만 OS의 웹뷰를 빌리지 않고 크로미움을 통째로 들고 간다. 이 차이에서 용량, 성능, "OS다운 느낌", 플랫폼별 버그가 전부 갈린다.

## 웹뷰 안에 웹 앱을 넣는 하이브리드

가장 가까운 길은 지금 있는 웹 앱을 네이티브 앱 껍데기 속 웹뷰에 넣는 것이다. iOS에서는 WKWebView, Android에서는 Android System WebView(크로미움 기반)가 화면을 그린다. Capacitor가 이 껍데기를 만들어 주는 런타임이고, Ionic은 그 위에서 쓰는 모바일 모양 UI 컴포넌트 묶음이다. 둘은 같은 팀이 만들지만 따로 쓸 수 있다. Capacitor는 예전 Cordova가 하던 자리를 이어받았다.

웹뷰 안의 자바스크립트는 카메라나 푸시 알림을 직접 부르지 못한다. 그래서 플러그인이 다리를 놓는다. 자바스크립트에서 플러그인 메서드를 부르면 Capacitor가 메시지를 네이티브 쪽(Swift, Kotlin)으로 넘기고, 결과를 Promise로 돌려준다.

```ts
import { Camera, CameraResultType } from "@capacitor/camera";

// 웹뷰 안의 코드가 네이티브 카메라를 연다. 결과는 Promise로 돌아온다
const photo = await Camera.getPhoto({
  resultType: CameraResultType.Uri,
  quality: 80,
});
```

장점은 코드 공유가 거의 전부라는 것이다. 웹과 앱이 같은 번들을 쓰고, 웹 개발자가 그대로 개발한다. 대가는 두 가지다. 하나는 화면이 웹 페이지라는 사실이 손끝에 남는다는 것이다. 긴 목록 스크롤, 화면 전환 제스처, 키보드가 올라올 때의 레이아웃이 네이티브 앱과 미묘하게 다르다. 다른 하나는 iOS에서는 WebKit, Android에서는 크로미움이 그린다는 것이다. 같은 CSS가 두 엔진에서 다르게 보이면 웹에서 사파리 버그를 잡던 일을 앱에서도 똑같이 한다.

그래서 하이브리드는 콘텐츠·폼 중심 앱(사내 업무 앱, 예약, 설정 화면이 많은 앱)에 잘 맞고, 화면 전환과 애니메이션이 앱의 얼굴인 서비스에는 덜 맞는다.

## React Native는 OS 위젯에게 그리게 한다

React Native는 React로 컴포넌트를 쓰지만 결과물이 DOM이 아니다. `<View>`는 iOS의 UIView, Android의 ViewGroup이 되고, `<Text>`는 각 OS의 글자 위젯이 된다. 화면이 진짜 네이티브 위젯이라 스크롤과 입력이 OS다운 느낌을 낸다. 대신 `<div>`와 CSS를 그대로 쓸 수는 없다. 스타일은 CSS 문법을 닮은 자바스크립트 객체이고, 레이아웃은 Yoga라는 Flexbox 엔진이 계산한다.

예전 구조에서는 자바스크립트와 네이티브 사이에 브리지가 있었다. 자바스크립트 스레드가 "이 뷰를 만들어라", "이 값을 바꿔라" 같은 메시지를 JSON으로 직렬화해 큐에 넣으면, 네이티브 쪽이 나중에 꺼내 처리하는 비동기 방식이었다. 메시지가 많아지면 직렬화 비용과 지연이 쌓였다. 빠르게 스크롤하는 목록에서 빈 칸이 잠깐 보이거나, 제스처에 맞춰 움직이는 애니메이션이 한 박자 늦는 문제가 여기서 왔다.

새 아키텍처는 이 다리를 걷어 냈다. 중심은 JSI(JavaScript Interface)다. 자바스크립트 엔진이 C++ 객체의 참조를 직접 들고 메서드를 부를 수 있게 하는 인터페이스라, JSON으로 바꿔 줄 필요가 없고 필요하면 동기 호출도 된다. 그 위에 새 렌더러 Fabric과, 필요할 때 늦게 불러오는 네이티브 모듈 TurboModules가 올라간다. 새 아키텍처는 0.76부터 기본값이 되었고, 0.82부터는 옛 아키텍처로 돌아갈 수 없다. 자바스크립트 엔진은 0.70부터 기본값인 Hermes가 미리 바이트코드로 컴파일해 앱 시작을 줄인다.

```tsx
import { FlatList, Text, View } from "react-native";

// DOM이 아니라 OS 위젯이 된다. 스타일은 객체, 레이아웃은 Flexbox(Yoga)다
export function OrderList({ orders }: { orders: { id: string; title: string }[] }) {
  return (
    <FlatList
      data={orders}
      keyExtractor={(o) => o.id}
      renderItem={({ item }) => (
        <View style={{ padding: 16, borderBottomWidth: 1 }}>
          <Text>{item.title}</Text>
        </View>
      )}
    />
  );
}
```

웹과의 코드 공유는 하이브리드보다 적다. 상태 관리, API 호출, 검증 같은 로직은 그대로 가져가지만 화면 컴포넌트는 다시 쓴다. react-native-web으로 반대 방향(RN 컴포넌트를 웹에 그리기)을 쓰는 팀도 있지만, 웹을 먼저 가진 팀이라면 로직만 공유하고 화면은 플랫폼마다 쓰는 쪽이 흔하다. 실무에서는 빌드·배포 도구 묶음인 Expo 위에서 시작하는 경우가 많다.

웹과 앱을 한 저장소에 두는 팀은 보통 로직 패키지를 따로 뺀다. 모노레포에 `packages/core`(API 클라이언트, 검증 스키마, 가격 계산 같은 순수 로직)를 두고, `apps/web`(Next.js)과 `apps/mobile`(React Native)이 그걸 가져다 쓴다. core에는 DOM도 React Native 컴포넌트도 import하지 않는다는 규칙 하나만 지키면 양쪽에서 그대로 돈다. 저장소 경계를 어떻게 긋는지는 [프런트엔드 모노레포](/posts/frontend-monorepo)에서 다뤘다.

```text
apps/
  web/          Next.js 화면
  mobile/       React Native 화면
packages/
  core/         API 호출, 검증, 계산 (DOM·RN import 금지)
  ui-tokens/    색·간격 값만 (양쪽이 각자 스타일로 변환)
```

플랫폼마다 조금씩 달라야 하는 파일은 확장자로 나눈다. React Native의 번들러 Metro는 `price-label.ios.tsx`, `price-label.android.tsx`, `price-label.native.tsx`처럼 플랫폼 확장자가 붙은 파일을 먼저 찾는다. import는 `./price-label` 하나로 쓰고, 플랫폼에 맞는 파일이 골라진다. 웹 번들러에는 `.native.tsx`를 건너뛰고 `.tsx`를 고르게 하면 같은 import가 웹에서도 맞는 파일을 찾는다.

## Flutter는 자기 붓으로 모든 픽셀을 칠한다

Flutter는 언어부터 Dart라서 웹 코드를 재사용하는 선택지는 아니다. 그래도 같은 비교 자리에 늘 나오는 이유는 접근이 정반대라서다. OS 위젯을 빌리지 않고 자체 렌더링 엔진이 캔버스에 모든 픽셀을 칠한다. 예전에는 Skia를 썼고, 지금은 셰이더를 미리 준비해 첫 애니메이션 끊김을 줄인 Impeller가 iOS(3.10부터)와 Android(3.27부터)의 기본값이다. Dart는 릴리스 빌드에서 네이티브 코드로 미리 컴파일된다.

자기가 다 그리니 iOS와 Android에서 픽셀 단위로 같은 화면이 나오고, 애니메이션을 원하는 대로 다룰 수 있다. 반대로 OS가 새 위젯 모양을 내놓으면 Flutter가 따라 그려 줄 때까지 기다려야 하고, 접근성·텍스트 입력처럼 OS가 원래 해 주던 일을 엔진이 다시 연결해야 한다. 앱 용량도 엔진만큼 늘어난다. 웹 팀이 Flutter를 고른다면 "웹 코드 재사용"이 아니라 "모바일 앱을 한 코드베이스로, 디자인을 픽셀 단위로 통일"이 이유여야 한다.

## Electron은 브라우저를 통째로 들고 간다

데스크톱으로 넘어오면 가장 많이 보이는 이름이 Electron이다. 크로미움과 Node.js를 하나로 묶어 앱마다 함께 배포한다. 어느 OS에서든 같은 크로미움이 그리니 렌더링 차이가 없고, Node.js로 파일 시스템과 프로세스까지 다룬다. VS Code, Slack, Discord 데스크톱 앱이 이 위에 있다.

Electron 앱은 여러 프로세스로 나뉜다. 메인 프로세스는 하나다. Node.js 환경에서 돌고 창을 만들고, 메뉴와 트레이를 다루고, 파일을 읽는다. 창마다 렌더러 프로세스가 따로 있다. 크로미움의 탭과 같은 프로세스라 여기서 웹 페이지가 돈다. 둘은 메모리를 공유하지 않으니 IPC(프로세스 사이 통신)로 메시지를 주고받는다. 그 사이에 프리로드 스크립트가 있다. 렌더러에서 페이지보다 먼저 실행되고, 페이지에 꼭 필요한 기능만 골라 열어 준다.

import { readFile } from "node:fs/promises";
import path from "node:path";

app.whenReady().then(() => {

      preload: path.join(__dirname, "preload.js"),
      contextIsolation: true, // 12부터 기본값. 프리로드와 페이지의 전역을 분리한다

    if (!isTrustedSender(event.senderFrame?.url)) throw new Error("blocked");

## Electron 앱에서 XSS가 원격 코드 실행이 되는 길

웹에서 XSS는 그 사이트 권한으로 스크립트가 도는 문제다([XSS](/posts/xss)). Electron에서는 같은 XSS가 사용자 컴퓨터의 명령 실행으로 커질 수 있다. 렌더러가 Node.js 권한을 들고 있으면 그렇다.

`nodeIntegration: true`로 만든 창에 채팅 메시지 같은 사용자 입력이 HTML로 들어가 스크립트가 실행됐다고 하자. 그 스크립트는 `require("child_process").exec(...)`로 셸 명령을 돌릴 수 있다. 웹 페이지 하나의 버그가 그대로 내 PC의 파일과 계정을 넘긴다. 그래서 Electron 기본값이 해마다 바뀌어 왔다. 5부터 `nodeIntegration`이 꺼졌고, 12부터 `contextIsolation`이 켜졌고, 20부터 렌더러가 기본으로 샌드박스에 들어간다.

기본값을 지켜도 구멍은 프리로드에서 다시 생긴다.

```ts
// 하지 말 것: ipcRenderer를 통째로 내놓으면 페이지가 아무 채널이나 부른다
contextBridge.exposeInMainWorld("ipc", ipcRenderer);

// 하지 말 것: 채널 이름을 페이지가 고르게 하면 같은 문제다
contextBridge.exposeInMainWorld("api", {
  send: (channel: string, ...args: unknown[]) => ipcRenderer.invoke(channel, ...args),
});
```

contextIsolation은 프리로드와 페이지의 자바스크립트 세계를 나눌 뿐이다. 프리로드가 강한 함수를 그대로 건네면 분리한 의미가 없다. 함수는 하는 일 하나씩 좁게 열고, 메인 프로세스는 채널마다 보낸 쪽을 검사한다. Electron 공식 보안 체크리스트가 권하는 항목도 이 방향이다. 원격 콘텐츠를 불러오는 창에는 Node 권한을 주지 않는다, CSP를 건다([보안 헤더](/posts/web-security-headers)), `will-navigate`와 `setWindowOpenHandler`로 앱이 낯선 주소로 넘어가거나 새 창을 여는 것을 막는다, `shell.openExternal`에 검증하지 않은 URL을 넘기지 않는다, `webSecurity`를 끄지 않는다.

보낸 쪽 검사에서 가장 흔한 실수는 문자열 앞부분 비교다. `"https://app.example.com.evil.io/".startsWith("https://app.example.com")`는 `true`다. 주소를 URL로 파싱해 스킴과 호스트(포트 포함)를 통째로 비교해야 한다. 하나 더 있다. Node.js 22의 `URL`에서 `new URL("app://bundle/index.html").origin`은 `"null"`이다. 사용자 정의 스킴은 WHATWG URL 규칙에서 출처를 갖지 않는 스킴이라서다. 그래서 `origin`만 비교하면 앱 내부 화면까지 거절하거나, 반대로 `"null"`끼리 같다고 통과시키는 실수가 생긴다. 아래에서 직접 짜 볼 수 있다.

## Tauri는 OS의 웹뷰를 빌린다

Electron의 가장 큰 불만은 무게다. Electron 45 런타임 zip을 내려받기 전에 크기만 확인해 보면 macOS arm64가 약 120MB, Linux x64가 약 124MB, Windows x64가 약 158MB다(압축 상태, 앱 코드 제외). 앱마다 크로미움 한 벌을 들고 가니 설치 용량과 메모리가 앱 수만큼 늘어난다.

Tauri는 크로미움을 들고 가지 않는다. OS가 이미 가진 웹뷰를 빌린다. Windows에서는 WebView2(Edge의 크로미움 엔진), macOS에서는 WKWebView, Linux에서는 WebKitGTK다. 백엔드는 Node.js 대신 Rust로 쓴다. 그래서 설치 파일이 수 MB 수준으로 작아지고, Tauri 문서는 아주 작은 앱이 1MB도 안 되게 나온다고 소개한다. 2.0(2024년 10월)부터는 iOS와 Android도 같은 구조로 빌드한다.

페이지에서 Rust 쪽을 부르는 방법은 Electron의 invoke와 닮았다.

```rust
// src-tauri/src/lib.rs — 페이지에서 부를 수 있는 명령을 Rust 함수로 정의한다
#[tauri::command]
fn order_total(prices: Vec<u32>) -> u32 {
    prices.iter().sum()
}
```

```ts
import { invoke } from "@tauri-apps/api/core";

// 등록된 명령만 이름으로 부를 수 있다
const total = await invoke<number>("order_total", { prices: [12000, 18000] });
```

보안 기본값도 다르다. 페이지는 처음부터 OS 기능에 손댈 수 없고, 2.0의 권한(capabilities) 설정 파일에 창마다 쓸 수 있는 명령과 플러그인 권한을 적어야 열린다. Electron에서 체크리스트로 지키던 "필요한 것만 열기"가 설정의 기본 모양이 된 셈이다.

대가는 렌더링 엔진이 OS마다 다르다는 것이다. Windows는 크로미움, macOS는 WebKit, Linux는 WebKitGTK가 그리니, 웹에서 브라우저 호환성을 챙기던 일이 데스크톱에서도 그대로 남는다. 특히 Linux의 WebKitGTK는 배포판에 따라 버전이 달라 최신 CSS나 웹 API가 늦게 들어올 수 있다. 백엔드 로직을 Rust로 써야 한다는 점도 팀에 따라 진입 장벽이다.

## 데스크톱 앱을 내보낼 때 따라오는 일

웹은 배포하면 끝이지만 데스크톱 앱은 사용자 PC에 설치된다. 그래서 웹에서는 없던 일이 셋 생긴다.

첫째는 코드 서명이다. macOS는 개발자 인증서로 서명하고 애플의 공증(notarization)을 거친 앱이 아니면 Gatekeeper가 실행을 막는다. Windows는 서명이 없거나 평판이 쌓이지 않은 실행 파일에 SmartScreen 경고를 띄운다. 인증서 발급과 CI에서의 서명 단계를 첫 배포 일정에 넣어 둬야 한다.

둘째는 자동 업데이트다. Electron은 electron-updater 같은 도구로, Tauri는 updater 플러그인으로 새 버전을 받아 설치한다. Tauri의 updater는 업데이트 파일 서명을 필수로 요구하고, 앱에 넣어 둔 공개 키로 검증한다. 업데이트 경로는 공격자가 가장 노리는 길이라, 서명 없이 HTTPS만 믿는 구성은 피한다.

셋째는 런타임 자체를 잠그는 일이다. Electron에는 빌드할 때 기능을 끄는 퓨즈(fuses)가 있다. 예를 들어 `RunAsNode` 퓨즈를 끄면 `ELECTRON_RUN_AS_NODE` 환경 변수로 앱 실행 파일을 일반 Node.js처럼 돌리는 길이 막힌다. 서명된 앱 실행 파일이 남의 스크립트를 돌리는 도구로 쓰이지 않게 하는 장치다.

## 무엇을 고를지 정하는 질문

정답은 없고, 질문 순서가 있다.

먼저 웹 코드를 얼마나 그대로 쓰고 싶은지 묻는다. 웹 앱을 거의 그대로 앱으로 내고 싶다면 모바일은 Capacitor, 데스크톱은 Electron이나 Tauri다. 화면은 다시 써도 되고 로직만 공유하면 된다면 React Native가 들어온다. 웹과는 별개로 모바일 앱 하나를 잘 만들고 싶다면 Flutter도 후보다.

다음으로 화면이 얼마나 "앱다워야" 하는지 묻는다. 목록·폼·설정이 대부분이면 웹뷰로 충분하다. 제스처에 붙어 움직이는 화면, 긴 목록의 매끄러운 스크롤이 서비스의 얼굴이면 React Native나 Flutter 쪽으로 기운다.

그다음은 네이티브 기능이다. 블루투스, 백그라운드 위치, 결제 SDK처럼 플랫폼 기능이 깊이 들어가면 어느 길을 골라도 결국 Swift·Kotlin 코드를 조금은 쓰게 된다. 이미 그 기능의 플러그인이 잘 관리되고 있는지가 고르는 기준이 된다.

데스크톱에서는 용량과 렌더링 일관성 중 무엇이 더 아픈지 묻는다. 모든 OS에서 같은 화면과 최신 크로미움 기능이 필요하고, 팀이 Node.js에 익숙하면 Electron이다. 설치 용량과 메모리가 중요하고 OS별 웹뷰 차이를 감당할 수 있으면 Tauri다.

마지막은 업데이트다. 웹뷰 계열은 앱 껍데기 안의 웹 번들만 바꿔 스토어 심사 없이 배포하고 싶은 유혹이 생긴다. 스토어마다 원격으로 받아 실행하는 코드에 대한 규정이 있으니, 무엇을 원격으로 바꿀 수 있는지 미리 확인한다. 데스크톱 앱은 자동 업데이트에 코드 서명이 필요하고, 서명이 없으면 macOS와 Windows가 설치를 경고하거나 막는다.

## 현장에서 자주 막히는 지점

하이브리드 앱에서 "웹에서는 되는데 아이폰 앱에서만 깨진다"는 제보가 오면, 앱의 문제가 아니라 WKWebView(사파리와 같은 WebKit)의 CSS·API 지원 차이부터 본다. iOS 사파리에서 같은 페이지를 열어 재현되는지가 첫 확인이다.

React Native에서 스크롤 중 빈 칸이 보이거나 애니메이션이 끊기면 자바스크립트 스레드가 막혔는지부터 본다. 무거운 계산이 렌더링과 같은 스레드에서 돌고 있지 않은지, 목록 아이템이 매번 다시 렌더링되지 않는지 확인한다. 리렌더 원인을 좁히는 방법은 웹 React와 같다.

Electron 앱이 느리고 메모리를 많이 쓰면 창과 숨긴 창이 몇 개인지, 메인 프로세스에서 동기 IPC(`sendSync`)나 동기 파일 읽기로 이벤트 루프를 막고 있지 않은지 본다. 메인이 막히면 모든 창이 같이 멈춘다.

Tauri 앱이 Windows에서는 되는데 Linux에서만 화면이 깨지면, 그 배포판의 WebKitGTK 버전에서 해당 CSS나 API를 지원하는지 먼저 확인한다.

## 면접에서 나올 만한 질문

### 하이브리드 앱, React Native, Flutter는 무엇이 다른가요?

화면을 누가 그리느냐가 다르다. 하이브리드는 OS의 웹뷰가 HTML·CSS를 그리고, React Native는 우리 코드가 말한 대로 OS의 네이티브 위젯이 그리며, Flutter는 자체 렌더링 엔진이 모든 픽셀을 직접 칠한다. 그래서 하이브리드는 웹 코드 재사용이 가장 크고, React Native는 OS다운 느낌이 나고, Flutter는 플랫폼 사이 화면이 픽셀 단위로 같다.

### React Native의 새 아키텍처는 무엇을 바꿨나요?

자바스크립트와 네이티브 사이의 비동기 JSON 브리지를 JSI로 바꿨다. JSI는 자바스크립트가 C++ 객체 참조를 직접 들고 메서드를 부르게 해서 직렬화 비용이 없고 동기 호출도 된다. 그 위에 새 렌더러 Fabric과 필요할 때 불러오는 TurboModules가 올라간다. 0.76부터 기본값이고 0.82부터는 옛 구조로 돌아갈 수 없다.

### Electron의 메인 프로세스와 렌더러 프로세스는 무엇인가요?

메인 프로세스는 앱에 하나 있고 Node.js 환경에서 창, 메뉴, 파일 같은 OS 기능을 다룬다. 렌더러 프로세스는 창마다 있고 크로미움 탭처럼 웹 페이지를 돌린다. 둘은 메모리를 공유하지 않아 IPC로 통신하고, 프리로드 스크립트가 contextBridge로 페이지에 필요한 함수만 열어 준다.

### contextIsolation과 nodeIntegration은 왜 중요한가요?

렌더러에 Node.js 권한이 있으면 XSS 하나가 사용자 PC에서 명령을 실행하는 원격 코드 실행으로 커진다. nodeIntegration을 끄면 페이지가 require를 못 쓰고, contextIsolation을 켜면 프리로드와 페이지의 자바스크립트 세계가 분리되어 페이지가 프리로드의 전역을 건드리지 못한다. 각각 Electron 5와 12부터 기본값이고 20부터는 렌더러 샌드박스도 기본이다.

### 기본값을 다 지켰는데도 Electron 앱이 위험해질 수 있나요?

있다. 프리로드에서 ipcRenderer를 통째로 내놓거나 채널 이름을 페이지가 고르게 하면 분리한 의미가 사라진다. 함수는 하는 일 하나씩 좁게 열고, 메인은 채널마다 event.senderFrame.url을 URL로 파싱해 스킴과 호스트를 정확히 비교한다. 문자열 앞부분 비교는 비슷한 도메인에 뚫린다. 그 밖에 원격 콘텐츠 창에 권한 주지 않기, CSP, 낯선 주소로의 이동과 새 창 막기, shell.openExternal 검증이 체크리스트에 있다.

### Electron 대신 Tauri를 고르는 이유와 대가는 무엇인가요?

Tauri는 크로미움을 들고 가지 않고 OS의 웹뷰를 빌려 써서 설치 용량과 메모리가 크게 줄어든다. 백엔드가 Rust이고, 2.0의 권한 설정으로 창마다 쓸 수 있는 명령을 적어야 열리는 구조라 기본이 더 닫혀 있다. 대가는 Windows는 크로미움, macOS와 Linux는 WebKit 계열이 그려 OS별 렌더링 차이를 챙겨야 한다는 점과, 네이티브 로직을 Rust로 써야 한다는 점이다.

### PWA로 충분한 경우와 앱 껍데기가 필요한 경우는 어떻게 가르나요?

홈 화면 설치, 오프라인 열기, 웹 푸시 정도면 PWA로 충분하다. 앱 스토어 노출이 필요하거나, iOS에서 PWA가 쓰지 못하는 네이티브 기능이 필요하거나, 데스크톱의 파일 시스템·트레이·자동 실행 같은 기능이 필요하면 Capacitor나 Electron·Tauri 같은 껍데기가 있어야 한다.
