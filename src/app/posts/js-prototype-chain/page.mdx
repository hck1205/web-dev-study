<EasyIntro>
  빈 객체를 사전처럼 써서 단어 수를 셌는데, constructor나 toString이라는 단어만 숫자가 아니라 이상한 글자가 되는 일이 있다. 빈 객체가 사실은 비어 있지 않기 때문이다. 모든 객체에는 부모 객체를 가리키는 숨은 연결이 하나 있고, 없는 이름을 읽으면 그 연결을 따라 부모에게, 부모의 부모에게 계속 물어본다. 이렇게 이어진 줄을 프로토타입 체인이라고 부른다.

  덕분에 배열마다 메서드를 복사하지 않고 부모 하나에만 두고 모두가 나눠 쓸 수 있다. 읽기는 위로 올라가지만 쓰기는 올라가지 않고 자기 자리에 새 속성을 만드는 것이 두 번째 규칙이다.

  이 성질을 모르면 사전 객체에 엉뚱한 값이 나오고, 외부 입력을 그대로 합치다가 모든 객체의 조상이 바뀌는 보안 사고도 난다. 사용자 입력을 이름표로 쓰는 사전은 부모 연결을 끊은 객체나 Map으로 만든다.
</EasyIntro>

문장에서 단어 수를 세는 함수다. 객체를 사전처럼 쓰는, 흔히 보는 코드다.

```js
function countWords(text) {
  const counts = {};
  for (const w of text.split(" ")) {
    counts[w] = (counts[w] || 0) + 1;
  }
  return counts;
}
const c = countWords("the constructor calls the toString");
console.log(c.the, c.calls);
console.log(c.constructor);
console.log(typeof c.toString, String(c.toString).slice(0, 40));
console.log(Object.keys(c));
```

Node.js 22에서 돌린 출력이다.

```text
2 1
function Object() { [native code] }1
string function toString() { [native code] }1
[ 'the', 'constructor', 'calls', 'toString' ]
```

`the`와 `calls`는 맞게 셌다. 그런데 `constructor`와 `toString`은 숫자가 아니라 함수 소스에 `1`이 붙은 문자열이 됐다. 빈 객체 `{}`에 `constructor`라는 키를 넣은 적이 없는데 `counts["constructor"]`가 처음부터 무언가를 돌려준 것이다. 그 무언가는 `Object` 함수였고, `함수 || 0`은 함수 그대로라 `+ 1`이 문자열 이어 붙이기가 됐다.

빈 객체가 비어 있지 않은 이유가 프로토타입 체인이다. 이 글은 객체가 없는 속성을 어디서 찾는지, 쓸 때는 왜 다르게 동작하는지, 그리고 이 구조 때문에 생기는 버그와 보안 문제를 따라간다. 출력은 Node.js 22에서 실제로 돌린 결과다.

이 주제의 다른 글: `this`가 정해지는 규칙은 [this 바인딩](/posts/js-this-binding)에, 이 체인 위에 얹은 문법은 [클래스와 상속](/posts/js-classes)에 있다. 객체를 복사해 새 객체를 만드는 설계 패턴은 [프로토타입 패턴](/posts/pattern-prototype)에서 따로 다룬다. 이름만 같고 다른 이야기다.

## 객체마다 숨은 연결이 하나 있다

모든 객체에는 `[[Prototype]]`이라는 내부 슬롯이 있다. 다른 객체 하나(또는 `null`)를 가리키는 연결이다. 객체에서 속성을 찾다가 없으면 엔진은 이 연결을 따라 올라가 다시 찾는다. 거기에도 없으면 또 올라간다. `null`에 닿으면 멈추고 `undefined`를 돌려준다. 이렇게 이어진 줄이 프로토타입 체인이다.

`{}`로 만든 객체의 `[[Prototype]]`은 `Object.prototype`이다. `constructor`, `toString`, `hasOwnProperty` 같은 것이 거기 있다. 그래서 빈 객체에서 `counts["constructor"]`를 읽으면 한 칸 위의 `Object.prototype.constructor`, 즉 `Object` 함수가 나온다.

아래 그림에서 다음을 누르면 `countWords`가 단어를 하나씩 셀 때 엔진이 어디까지 올라가는지 볼 수 있다.

이 연결을 코드로 확인하는 표준 방법은 `Object.getPrototypeOf(obj)`다. `obj.__proto__`도 같은 값을 돌려주지만, 이건 `Object.prototype`에 달린 getter라서 프로토타입이 없는 객체에서는 동작하지 않는다. 명세에서도 웹 호환을 위해 남겨 둔 기능으로 분류한다.

## 함수의 prototype 속성은 따로 있다

여기서 가장 많이 헷갈리는 부분이 이름이다. 객체의 숨은 연결 `[[Prototype]]`과, 함수가 갖는 평범한 속성 `prototype`은 다른 것이다. 함수의 `prototype` 속성은 "이 함수를 `new`로 불러 만든 객체의 `[[Prototype]]`을 무엇으로 할지" 정해 두는 객체다.

```js
class Animal {
  constructor(name) { this.name = name; }
  speak() { return `${this.name} makes a sound`; }
}
class Dog extends Animal {
  speak() { return `${this.name} barks`; }
}
const rex = new Dog("rex");
const chain = [];
for (let o = rex; o; o = Object.getPrototypeOf(o)) {
  chain.push(o === rex ? "rex" : o.constructor.name + ".prototype");
}
console.log(chain.join(" -> ") + " -> null");
console.log(Object.getPrototypeOf(rex) === Dog.prototype, rex.__proto__ === Dog.prototype);
console.log(Dog.prototype.constructor === Dog, Object.getOwnPropertyNames(rex));
console.log(Object.getPrototypeOf(Dog) === Animal, Object.getPrototypeOf(Animal) === Function.prototype);
console.log(typeof rex.prototype, typeof Dog.prototype);
```

```text
rex -> Dog.prototype -> Animal.prototype -> Object.prototype -> null
true true
true [ 'name' ]
true true
undefined object
```

`rex` 자신에게는 `name` 하나만 있다. `speak`는 `Dog.prototype`에 있다. `rex`의 `[[Prototype]]`이 `Dog.prototype`이고, `Dog.prototype.constructor`가 다시 `Dog`를 가리킨다. `rex.prototype`은 없다. 일반 객체에는 `prototype` 속성이 없고, 함수만 갖는다. 클래스 자체(`Dog`)도 객체라서 자기 `[[Prototype]]`이 있는데, 그건 `Animal`이다. 정적 메서드가 상속되는 길이 이것이다. 이 두 번째 줄은 [클래스와 상속](/posts/js-classes)에서 따로 본다.

쓰기(`[[Set]]`)는 다르다. 대입은 보통 체인을 올라가 원본을 바꾸지 않고, 대상 객체 자신에게 새 속성을 만든다. 예외가 두 가지 있다. 체인 위에 setter가 있으면 그 setter가 불리고, 체인 위의 같은 이름이 쓰기 금지(`writable: false`)면 대입이 막힌다.

```js
const child = Object.create(base);
child.greeting = "yo";
console.log(child.greeting, base.greeting, child.loud);
child.nick = "kim";
console.log(Object.keys(child), base._nick);
child.version = 2;
```

## 내 것인지 물려받은 것인지

체인 때문에 "이 객체에 이 키가 있나"라는 질문이 둘로 나뉜다. 자기 속성만 볼지, 물려받은 것까지 볼지다.

```js
const base = { inherited: 1 };
const obj = Object.create(base);
obj.own = 2;
console.log("in:", "inherited" in obj, "hasOwn:", Object.hasOwn(obj, "inherited"));
const forIn = [];
for (const k in obj) forIn.push(k);
console.log("for...in:", forIn, "keys:", Object.keys(obj));
console.log("toString in {}:", "toString" in {}, Object.keys({}));
```

```text
in: true hasOwn: false
for...in: [ 'own', 'inherited' ] keys: [ 'own' ]
toString in {}: true []
```

`in` 연산자와 `for...in`은 체인을 올라간다. `Object.hasOwn`, `Object.keys`, `Object.entries`, 전개 문법은 자기 속성만 본다. `for...in`이 물려받은 것 중에서도 열거 가능한(enumerable) 것만 보여 주기 때문에 `toString` 같은 내장 메서드는 안 나온다. 그런데 누군가 내장 프로토타입에 메서드를 대입으로 추가하면 열거 가능한 속성이 되어 모든 `for...in`에 끼어든다.

```js
Array.prototype.last = function () { return this[this.length - 1]; };
const keys = [];
for (const k in [10, 20]) keys.push(k);
console.log("for...in over array:", keys);
```

```text
for...in over array: [ '0', '1', 'last' ]
```

배열을 `for...in`으로 돌던 코드가 어느 날 `last`라는 키를 만나 `undefined`를 처리하다 죽는다. 내장 프로토타입을 고치지 말아야 하는 이유이고, 배열은 `for...of`로 도는 이유다. ES2015 이전에 MooTools 같은 라이브러리가 `Array.prototype`에 메서드를 넣어 둔 탓에, 표준이 `Array.prototype.contains`라는 이름을 포기하고 `includes`로 정했던 일도 있다.

## 사전으로 쓸 객체는 체인을 끊는다

처음 단어 세기 버그로 돌아간다. 사용자가 넣는 문자열을 키로 쓰는 객체는 `Object.prototype`의 이름과 부딪힐 수 있다. 고치는 방법은 둘이다. 프로토타입이 없는 객체를 쓰거나, `Map`을 쓴다.

```js
const dict = Object.create(null);
dict.constructor = 1;
console.log("null proto:", dict.constructor, "toString" in dict, Object.getPrototypeOf(dict));
const m = new Map([["constructor", 1]]);
console.log("map:", m.get("constructor"), m.get("toString"));
```

```text
null proto: 1 false null
map: 1 undefined
```

`Object.create(null)`은 체인 맨 위가 처음부터 `null`이라 물려받는 이름이 하나도 없다. 대신 `dict.hasOwnProperty` 같은 메서드도 없으니 `Object.hasOwn(dict, key)`로 확인한다. 이 방법은 [call, apply, bind](/posts/js-call-apply-bind#남의-메서드를-빌려-쓰기)에서 봤다. 키가 계속 추가되고 지워지는 사전이라면 `Map`이 낫다. 키로 아무 문자열이나 넣어도 안전하고, 크기를 `size`로 바로 알 수 있고, 넣은 순서대로 돈다.

## 요청 하나가 모든 객체를 바꾸는 법

읽기가 체인을 올라간다는 성질은 보안 문제로도 이어진다. 서버가 요청 본문을 설정 객체에 깊게 합치는 흔한 코드를 보자.

```js
function merge(target, source) {
  for (const key in source) {
    if (typeof source[key] === "object" && source[key] !== null) {
      if (!target[key]) target[key] = {};
      merge(target[key], source[key]);
    } else {
      target[key] = source[key];
    }
  }
  return target;
}
const body = JSON.parse('{"theme": "dark", "__proto__": {"isAdmin": true}}');
console.log("own keys of parsed:", Object.keys(body));
const settings = merge({}, body);
const someoneElse = {};
console.log("someoneElse.isAdmin:", someoneElse.isAdmin);
```

```text
own keys of parsed: [ 'theme', '__proto__' ]
someoneElse.isAdmin: true
```

전혀 상관없는 새 객체 `someoneElse`에 `isAdmin: true`가 생겼다. 이게 프로토타입 오염(prototype pollution)이다. `JSON.parse`는 `"__proto__"`를 평범한 자기 속성으로 만든다. 그런데 `merge`가 `target["__proto__"]`를 읽는 순간 `Object.prototype`의 `__proto__` getter가 불려 `Object.prototype` 자체가 나온다. 그 위에 `isAdmin = true`를 쓰니 모든 객체의 조상이 바뀌었다.

방어는 여러 겹으로 한다. 합치는 함수에서 `__proto__`, `constructor`, `prototype` 키를 건너뛰고, 대상이 사전이라면 `Object.create(null)`이나 `Map`을 쓴다. 들어오는 본문은 스키마 검증(zod, ajv 등)으로 모르는 키를 버린다. Node.js에는 `--disable-proto=delete`(접근자를 없앰)나 `--disable-proto=throw`(접근하면 에러) 옵션도 있다.

```text
$ node --disable-proto=throw p6.cjs
Error: Accessing Object.prototype.__proto__ has been disallowed with --disable-proto=throw
```

이 옵션은 `__proto__`를 쓰는 의존성까지 깨뜨릴 수 있어서, 켜기 전에 테스트를 전부 돌려 봐야 한다. lodash의 `merge`, `defaultsDeep` 같은 함수가 과거에 이 문제로 여러 번 CVE를 받았다. 의존성 감사(`npm audit`)에서 "Prototype Pollution"이라는 제목이 자주 보이는 이유다. JSON 쪽의 다른 함정은 [JSON으로 데이터 주고받기](/posts/json-crud-http)에 있다.

## 프로토타입에 둔 배열은 모두가 같이 쓴다

ES2015 클래스 이전 코드에서 자주 보던 실수다. 프로토타입에 기본값으로 배열이나 객체를 두면 모든 인스턴스가 같은 것을 공유한다.

```js
function Dog(name) { this.name = name; }
Dog.prototype.tricks = [];
Dog.prototype.addTrick = function (t) { this.tricks.push(t); };
const a = new Dog("a");
const b = new Dog("b");
a.addTrick("sit");
console.log("b.tricks:", b.tricks, Object.hasOwn(a, "tricks"));
```

```text
b.tricks: [ 'sit' ] false
```

`this.tricks.push`는 대입이 아니라 읽기다. `this.tricks`를 읽으면 체인을 올라가 프로토타입의 배열을 찾고, 그 배열을 바꾼다. `a`에는 자기 `tricks`가 생기지 않았다. 숫자나 문자열처럼 대입으로만 바꾸는 값은 섀도잉이 일어나 문제가 안 되지만, 바꿀 수 있는 객체는 공유된다. 그래서 상태는 생성자(클래스라면 필드)에서 인스턴스마다 만들고, 프로토타입에는 메서드만 둔다.

## instanceof는 체인을 훑는다

`a instanceof F`는 "a가 F로 만들어졌나"를 묻는 것처럼 보이지만, 실제로는 "a의 체인 어딘가에 `F.prototype`이 있나"를 본다.

그래서 연결만 맞으면 생성자를 거치지 않은 객체도 통과하고, 연결을 바꾸면 진짜 인스턴스도 떨어진다.

```js
class Animal {}
class Cat extends Animal {}
const tom = new Cat();
console.log(tom instanceof Cat, tom instanceof Animal, tom instanceof Object);
Object.setPrototypeOf(tom, Object.prototype);
console.log("after setPrototypeOf:", tom instanceof Cat);
const fake = Object.create(Cat.prototype);
console.log("fake instanceof Cat:", fake instanceof Cat);
class Even { static [Symbol.hasInstance](n) { return n % 2 === 0; } }
console.log("4 instanceof Even:", 4 instanceof Even);
```

```text
true true true
after setPrototypeOf: false
fake instanceof Cat: true
4 instanceof Even: true
```

`Symbol.hasInstance`를 정의하면 `instanceof`의 판단 자체를 바꿀 수 있다. 실무에서 더 자주 만나는 함정은 realm이다. iframe이나 Node.js의 `vm` 모듈에서 만든 배열은 그쪽의 `Array.prototype`을 가리켜서 `instanceof Array`가 `false`다. 배열 판별은 `Array.isArray`, 에러 판별은 Node.js 22라면 `util.types.isNativeError`, 최신 엔진이라면 ES2026의 `Error.isError`(Node.js 22에는 아직 없다)처럼 체인에 기대지 않는 방법을 쓴다. 이 이야기는 [truthy, falsy와 typeof](/posts/js-truthy-falsy-typeof)에도 있다.

## 체인이 길면 느릴까

체인을 매번 올라간다면 깊은 상속은 느려야 한다. Node.js 22에서 같은 속성 `x`를 500만 번 읽으며, 자기 속성인 경우와 한 칸 위, 열한 칸 위에 있는 경우를 세 번씩 쟀다.

```js
const N = 5_000_000;
function bench(label, make) {
  const objs = Array.from({ length: 1000 }, make);
  let s = 0;
  const t = performance.now();
  for (let i = 0; i < N; i++) s += objs[i % 1000].x;
  console.log(label.padEnd(26), (performance.now() - t).toFixed(1) + "ms");
  return s;
}
const proto = { x: 1 };
let deep = proto;
for (let i = 0; i < 10; i++) deep = Object.create(deep);
bench("own property", () => ({ x: 1 }));
bench("1 level up", () => Object.create(proto));
bench("11 levels up", () => Object.create(deep));
```

```text
own property               18.0ms
1 level up                 17.2ms
11 levels up               25.1ms
own property               33.8ms
1 level up                 18.8ms
11 levels up               19.3ms
own property               23.0ms
1 level up                 17.2ms
11 levels up               22.5ms
```

실행마다 순서가 뒤바뀔 만큼 차이가 잡음 수준이다. V8은 같은 모양(hidden class)의 객체가 반복해서 오면 "이 이름은 이 프로토타입의 이 자리에 있다"는 답을 인라인 캐시에 기억해 둔다. 그래서 체인 길이보다 그 자리에 오는 객체 모양이 얼마나 일정한지가 더 중요하다.

캐시를 깨는 쪽은 프로토타입을 바꾸는 일이다. MDN은 이미 쓰고 있는 객체의 `[[Prototype]]`을 `Object.setPrototypeOf`나 `__proto__` 대입으로 바꾸는 것을 모든 엔진에서 매우 느린 작업이라고 경고한다. 그 객체뿐 아니라 그 프로토타입을 거쳐 속성을 찾던 코드의 최적화가 무효가 될 수 있어서다. 상속 구조는 `Object.create`나 `class extends`로 만들 때 정하고, 만든 뒤에는 바꾸지 않는다.

## 체인이 끊기는 경계들

프로토타입은 객체의 자기 속성이 아니라서, 자기 속성만 다루는 연산을 거치면 사라진다. 전개 문법 `{ ...user }`는 메서드와 클래스 정체성을 잃은 평범한 객체를 만든다. 이 사례는 [전개와 나머지](/posts/js-spread-rest)에서 봤다. `JSON.stringify`와 `structuredClone`도 클래스 인스턴스를 평범한 객체로 바꾼다. React 상태에 클래스 인스턴스를 넣고 `setUser({ ...user, name })`로 갱신하면, 다음 렌더링에서 `user.fullName()`이 `is not a function`으로 터진다.

Next.js의 서버 컴포넌트에서 클라이언트 컴포넌트로 props를 넘길 때도 같은 경계가 있다. 이 경계는 직렬화를 거치므로 React가 프로토타입을 검사해서 막는다. Next.js 16에 들어 있는 React 서버 렌더러로 직접 확인했다.

```js
class Money { constructor(v) { this.v = v; } format() { return this.v + "원"; } }
// 클라이언트 컴포넌트에 price로 각각 넘겨 본다
[["plain", { v: 1000 }], ["class", new Money(1000)], ["nullproto", Object.assign(Object.create(null), { v: 1 })]]
```

```text
plain -> ok
class -> Only plain objects, and a few built-ins, can be passed to Client Components from Server Components. Classes or null prototypes are not supported.
nullproto -> Only plain objects, and a few built-ins, can be passed to Client Components from Server Components. Classes or null prototypes are not supported.
```

`[[Prototype]]`이 `Object.prototype`인 객체만 통과한다. 클래스 인스턴스도, 앞에서 사전용으로 권한 `Object.create(null)` 객체도 막힌다. 서버에서 ORM 엔티티나 `Decimal` 같은 객체를 그대로 넘기다 이 에러를 만나면, 경계에서 평범한 객체로 바꿔(`{ v: money.v }`) 넘기고 메서드는 클라이언트 쪽 유틸로 옮긴다.

## 없으면 위에 물어본다

처음 단어 세기 함수는 빈 객체가 정말 비어 있다고 믿어서 틀렸다. `{}`는 `Object.prototype`에 연결된 객체이고, 없는 키를 읽으면 위로 물어본다. 읽기는 올라가고 쓰기는 제자리에 만든다. 이 두 줄만 기억하면 메서드 공유, 오버라이드, 사전 객체의 함정, 프로토타입 오염, `instanceof`의 동작이 모두 같은 그림으로 풀린다.

## 면접에서 나올 만한 질문

### 프로토타입 체인이란 무엇인가요?

모든 객체가 `[[Prototype]]` 내부 슬롯으로 다른 객체(또는 `null`)를 가리키고, 속성을 찾다 없으면 그 연결을 따라 올라가는 구조다. `null`에 닿을 때까지 못 찾으면 `undefined`가 된다. 메서드를 인스턴스마다 복사하지 않고 프로토타입 하나에 두고 공유할 수 있는 이유이고, 상속과 메서드 오버라이드도 이 탐색 규칙의 결과다.

### prototype과 __proto__의 차이는요?

`prototype`은 함수가 갖는 평범한 속성으로, 그 함수를 `new`로 불러 만든 객체의 `[[Prototype]]`이 될 객체다. `__proto__`는 아무 객체의 `[[Prototype]]`을 읽고 쓰는 `Object.prototype`의 접근자로, 웹 호환을 위해 남은 기능이다. 그래서 `new Dog().__proto__ === Dog.prototype`이 참이다. 코드에서는 `Object.getPrototypeOf`와 `Object.create`를 쓴다.

### 상속받은 속성에 값을 대입하면 부모가 바뀌나요?

보통은 바뀌지 않고 자식 객체에 같은 이름의 자기 속성이 새로 생겨 부모 것을 가린다. 예외로 체인 위에 setter가 있으면 그 setter가 자식을 `this`로 불리고, 위의 속성이 `writable: false`면 대입이 막힌다. 막힐 때 엄격 모드는 `TypeError`, 느슨한 모드는 조용히 무시한다. 다만 `this.list.push()`처럼 읽어서 바꾸는 건 대입이 아니라서 부모의 객체가 바뀐다.

### in과 hasOwn, for...in과 Object.keys의 차이는 무엇인가요?

`in`과 `for...in`은 체인을 올라가 물려받은 속성까지 보고, `Object.hasOwn`과 `Object.keys`는 자기 속성만 본다. `for...in`은 열거 가능한 것만 보여서 내장 메서드는 안 나오지만, 누가 내장 프로토타입에 대입으로 메서드를 추가하면 끼어든다. 데이터 처리에는 자기 속성만 보는 쪽을 쓴다.

### 객체를 사전(해시맵)처럼 쓸 때 주의할 점은요?

`{}`는 `Object.prototype`의 `constructor`, `toString` 같은 이름을 물려받아서, 사용자 입력을 키로 쓰면 없는 키인데 값이 나온다. `Object.create(null)`로 체인을 끊거나 `Map`을 쓴다. 키가 자주 추가·삭제되거나 문자열 외의 키가 필요하면 `Map`이 맞다.

### 프로토타입 오염 공격은 어떻게 일어나고 어떻게 막나요?

깊은 병합이나 경로로 값을 설정하는 함수가 `__proto__` 키를 그대로 처리하면, `target["__proto__"]`가 `Object.prototype`을 돌려주고 거기에 값이 쓰여 모든 객체가 오염된다. 권한 검사 같은 곳에서 없는 속성을 읽을 때 공격자가 넣은 값이 나온다. 병합 함수에서 `__proto__`, `constructor`, `prototype`을 건너뛰고, 스키마 검증으로 모르는 키를 버리고, 사전에는 `Map`이나 `Object.create(null)`을 쓴다. Node.js의 `--disable-proto` 옵션도 있다.

### instanceof는 어떻게 동작하고 언제 틀리나요?

왼쪽 객체의 체인을 올라가며 오른쪽 함수의 `prototype`과 같은 객체가 있는지 본다. 그래서 생성자를 거치지 않은 `Object.create(Dog.prototype)`도 참이고, `setPrototypeOf`로 연결을 바꾸면 진짜 인스턴스도 거짓이 된다. iframe이나 `vm`처럼 다른 realm에서 만든 객체는 그쪽 `prototype`을 가리켜 거짓이 나오므로 배열은 `Array.isArray`로 판별한다.

### 프로토타입 체인이 깊으면 성능이 나빠지나요?

측정해 보면 체인 깊이 자체는 거의 차이가 없었다. V8이 같은 모양의 객체라면 속성 위치를 인라인 캐시에 기억하기 때문이다. 성능을 해치는 건 이미 쓰고 있는 객체의 프로토타입을 `setPrototypeOf`로 바꾸거나 한 자리에 모양이 제각각인 객체가 오는 경우다. 상속 구조는 만들 때 정하고 바꾸지 않는다.
