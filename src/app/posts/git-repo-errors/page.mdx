<EasyIntro>
  저장 명령을 치다 프로그램이 멈춰 강제로 껐더니, 그다음부터 Git이 "잠금 파일이 있다"며 아무것도 안 해 준다. 다른 날엔 평소처럼 받아 오기를 했을 뿐인데 이름이 부딪힌다고 하고, 도커 안에서는 멀쩡한 저장소를 두고 주인이 다르다고 한다.

  이런 오류는 내 커밋이나 작업 방식과는 관계가 없다. Git이 쓰는 숨은 폴더 안의 파일 하나가 남았거나, 깨졌거나, 이름이 겹치거나, 소유자가 다른 것이다. 창고 문에 걸린 자물쇠가 안 풀린 것과 같아서, 어느 파일이 문제인지 알면 그 파일을 지우거나 다시 만들어 푼다.

  중요한 건 무엇을 지워도 되고 무엇은 절대 지우면 안 되는지 가르는 일이다. 잠금 파일, 원격에서 다시 받을 수 있는 기록, 다시 만들 수 있는 목록은 지워도 잃는 게 없지만, 내 커밋 자체가 담긴 파일은 손대면 되살리기 어렵다.
</EasyIntro>

커밋 메시지를 쓰다 IDE가 멈춰서 강제로 껐다. 다시 터미널에서 `git add`를 쳤더니 `index.lock: File exists`라며 아무것도 안 된다. 다른 날에는 평소처럼 `git fetch`를 했을 뿐인데 `cannot lock ref`가 나오고, 도커 컨테이너 안에서는 멀쩡한 저장소를 두고 `dubious ownership`이라고 한다.

이런 오류는 내 커밋이나 브랜치 전략과는 관계가 없다. `.git` 폴더 안의 파일 하나가 남았거나, 깨졌거나, 이름이 부딪히거나, 주인이 다른 것이다. 그래서 고칠 때도 그 파일이 무엇인지 알면 된다. 무엇을 지워도 되고 무엇은 절대 지우면 안 되는지가 갈린다. `.git` 안의 구성은 [Git 객체 글](/posts/git-internals-basics)에서 열어 봤다.

이 글은 [Git 문제 해결 글](/posts/git-troubleshooting)에 이어 저장소 자체가 명령을 거부하는 오류를 모았다. ref 잠금, `index.lock`, 깨진 인덱스, 저장소를 못 찾거나 소유자가 다를 때, 비어 있는 서브모듈, 작성자 정보가 없을 때다. 기준은 Ubuntu 24.04의 Git 2.43이고 출력은 그 버전에서 재현한 결과다.

## cannot lock ref 오류가 난다

브랜치를 만들 때 이렇게 나온다.

```bash
# feature라는 브랜치가 있는 상태에서 feature/login을 만들려고 하면
git branch feature/login
```

```text
fatal: cannot lock ref 'refs/heads/feature/login': 'refs/heads/feature' exists; cannot create 'refs/heads/feature/login'
```

브랜치 이름은 `.git/refs/heads/` 아래 파일 경로로 저장된다. `feature`가 이미 파일이니 같은 이름의 폴더 `feature/`를 만들 수 없다. `feature`와 `feature/login`은 동시에 있을 수 없다는 뜻이다. 하나를 다른 이름으로 바꾸거나 지운다(`git branch -m feature feature/base`).

브랜치 이름이 파일 경로라는 걸 그림으로 보면 왜 부딪히는지 분명해진다. 점이 흐르는 방향으로 Git이 경로를 따라 내려간다.

```bash
# 원격에서 사라진 원격 추적 브랜치를 지우면서 받는다
git fetch --prune

# 앞으로는 매번 자동으로
git config --global fetch.prune true
```

같은 이름의 오류가 `unable to resolve reference`나 `reference broken`과 함께 나오면 ref 파일이 깨진 경우다. 디스크가 꽉 찼거나 Git이 도중에 죽었을 때 생긴다. `git gc --prune=now`를 먼저 시도하고, 그래도 안 되면 `.git/refs/remotes/origin/` 아래 문제의 파일을 지우고 다시 fetch한다. 원격 추적 브랜치는 fetch로 언제든 다시 만들 수 있으니 지워도 잃는 게 없다. 로컬 브랜치(`.git/refs/heads/`) 파일은 함부로 지우지 않는다.

## index.lock 파일이 있다며 아무것도 안 된다

```text
fatal: Unable to create '/home/matt/shop/.git/index.lock': File exists.

Another git process seems to be running in this repository, e.g.
an editor opened by 'git commit'. Please make sure all processes
are terminated then try again. If it still fails, a git process
may have crashed in this repository earlier:
remove the file manually to continue.
```

Git은 인덱스를 고치는 동안 다른 프로세스가 동시에 고치지 못하게 `index.lock` 파일을 만들고, 끝나면 지운다. 이 파일이 남아 있으면 다른 Git 명령이 돌고 있거나, 앞선 명령이 강제 종료되면서 못 지운 것이다.

이 파일은 인덱스를 안전하게 바꾸려는 장치다. Git은 `.git/index`를 바로 고치지 않고, 잠금 파일에 새 내용을 다 쓴 다음 이름을 바꿔 한 번에 갈아 끼운다. 아래 그림에서 다음을 누르면 정상일 때와 도중에 죽었을 때가 어떻게 다른지 보인다.

```bash
# 정말 돌고 있는 git이 없는지 먼저 본다 (IDE의 Git 연동, 커밋 메시지 편집기 등)
pgrep -a git

# 없으면 남은 잠금 파일을 지운다
rm -f .git/index.lock
```

돌고 있는 프로세스가 있는데 지우면 두 프로세스가 동시에 인덱스를 써서 망가질 수 있다. 꼭 먼저 확인한다.

## index file corrupt

```text
error: bad signature 0x62726167
fatal: index file corrupt
```

인덱스 파일(`.git/index`)이 깨졌다. 디스크 오류, 동기화 프로그램(Dropbox, iCloud 등)이 `.git` 폴더를 건드린 경우, 쓰는 도중 전원이 나간 경우에 생긴다. 인덱스는 "다음 커밋에 들어갈 내용"의 목록일 뿐이라 커밋과 작업 폴더의 파일은 안전하다. 지우고 HEAD에서 다시 만든다.

```bash
# 깨진 인덱스를 치우고 (만약을 위해 지우지 않고 옮겨 둔다)
mv .git/index .git/index.broken

# HEAD 커밋을 기준으로 인덱스를 다시 만든다 (작업 폴더 파일은 안 건드린다)
git reset

git status
```

```text
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean
```

`git reset`은 기본이 `--mixed`라 인덱스만 HEAD에 맞추고 작업 폴더는 그대로 둔다. 스테이징해 둔 내용은 사라지니 다시 `git add` 한다. 다른 데이터도 의심된다면 `git fsck`로 저장소 전체를 검사한다. 저장소를 클라우드 동기화 폴더 안에 두지 않는 게 가장 좋은 예방이다.

## not a git repository

```text
fatal: not a git repository (or any of the parent directories): .git
```

지금 폴더와 그 위 어느 폴더에도 `.git`이 없다. 대개 엉뚱한 폴더에서 명령을 쳤거나, clone이 만든 하위 폴더로 들어가지 않은 경우다.

```bash
# 지금 위치와 저장소 루트 확인
pwd
git rev-parse --show-toplevel

# clone은 저장소 이름으로 폴더를 만든다. 그 안으로 들어가야 한다
git clone git@github.com:matt/shop.git && cd shop
```

비슷하게 생겼지만 원인이 다른 오류가 있다. Git 2.35.2부터는 다른 사용자가 소유한 저장소에서 명령을 거부한다. 도커 컨테이너에 마운트한 소스나 `sudo`로 만든 폴더에서 자주 본다.

```text
fatal: detected dubious ownership in repository at '/srv/shop'
To add an exception for this directory, call:

	git config --global --add safe.directory /srv/shop
```

남이 만든 저장소의 `.git/config`에 심어 둔 설정(예: 훅 경로)이 내 권한으로 실행되는 것을 막는 보안 장치다. 믿을 수 있는 저장소면 안내대로 예외를 추가하거나, 소유자를 맞춘다(`sudo chown -R $USER /srv/shop`). `safe.directory '*'`로 모든 곳을 풀어 버리는 건 장치를 끄는 것과 같으니 피한다.

## 서브모듈 폴더가 비어 있다

clone한 프로젝트의 `vendor/lib` 폴더가 비어 있어서 빌드가 실패한다.

```bash
# 서브모듈 상태: 맨 앞이 -면 아직 초기화하지 않은 것
git submodule status

# 초기화하고 기록된 커밋으로 받는다 (서브모듈 안의 서브모듈까지)
git submodule update --init --recursive
git submodule status
```

```text
-c34eceea6b8effd5cafac03bcb0c87469f960d6f vendor/lib
```

```text
Submodule 'vendor/lib' (git@github.com:acme/lib.git) registered for path 'vendor/lib'
Cloning into '/home/matt/shop/vendor/lib'...
done.
Submodule path 'vendor/lib': checked out 'c34eceea6b8effd5cafac03bcb0c87469f960d6f'
 c34eceea6b8effd5cafac03bcb0c87469f960d6f vendor/lib (heads/main)
```

서브모듈은 "이 경로에는 저 저장소의 이 커밋을 꺼내 둔다"는 기록만 부모 저장소에 남긴다. 그냥 clone하면 그 기록만 받고 내용은 받지 않는다. 처음부터 `git clone --recurse-submodules`로 받거나, `git config --global submodule.recurse true`를 켜 두면 pull과 checkout 때도 서브모듈을 따라 움직인다. 서브모듈 안에 들어가면 브랜치가 아니라 detached HEAD 상태인 것도 정상이다. 부모가 정한 커밋을 그대로 꺼냈기 때문이다. 서브모듈과 subtree의 차이는 [Git 고급 기능 글](/posts/git-tips-advanced)에서 다룬다.

## Author identity unknown

새 서버나 새 컨테이너에서 처음 커밋하면 나온다.

```text
Author identity unknown

*** Please tell me who you are.

Run

  git config --global user.email "you@example.com"
  git config --global user.name "Your Name"

to set your account's default identity.
Omit --global to set the identity only in this repository.

fatal: unable to auto-detect email address (got 'root@vm.(none)')
```

커밋에는 작성자 이름과 이메일이 꼭 들어가야 하는데 설정이 없고, 호스트 이름으로 추측한 값도 쓸 수 없는 모양이라 멈췄다.

```bash
# 전역 설정 (이 사용자의 모든 저장소)
git config --global user.name "Matt"
git config --global user.email "matt@example.com"

# 회사 저장소만 다른 이메일을 쓰려면 그 저장소 안에서 --global 없이
git config user.email "matt@company.example"

# 지금 적용되는 값과 어느 파일에서 왔는지 확인
git config --show-origin user.email
```

이메일은 GitHub 계정에 등록한 주소여야 커밋이 내 프로필과 연결된다. 이메일을 공개하기 싫으면 GitHub가 주는 `아이디@users.noreply.github.com` 주소를 쓴다. 이미 틀린 이메일로 커밋했다면 `git commit --amend --reset-author --no-edit`로 마지막 커밋의 작성자를 지금 설정으로 바꾼다. 회사와 개인 저장소를 폴더로 나눈다면 `includeIf "gitdir:~/work/"`로 폴더마다 다른 설정 파일을 자동으로 불러오게 할 수 있다. 설정 방법은 [.gitignore와 설정 글](/posts/git-ignore-config)에 실제 출력과 함께 있다.

## 지워도 되는 파일과 지우면 안 되는 파일

이 글의 오류는 거의 다 `.git` 안의 파일 하나를 지우거나 다시 만들어서 풀린다. 그래서 무엇을 건드려도 되는지 구분해 두는 게 가장 중요하다. `index.lock`처럼 끝난 명령이 남긴 잠금 파일, 원격에서 다시 받을 수 있는 `refs/remotes/` 아래의 원격 추적 브랜치, HEAD에서 다시 만들 수 있는 `index`는 지워도 잃는 게 없다. 반대로 `refs/heads/`의 로컬 브랜치 파일과 `objects/`는 내 커밋 그 자체라서 지우면 되살리기 어렵다. 손대기 전에는 `.git`을 통째로 복사해 두고, 지운 뒤에는 `git fsck`로 저장소 전체를 확인한다.

## 면접에서 나올 만한 질문

### cannot lock ref 오류는 왜 나고 어떻게 고치나요?

브랜치 이름이 `.git/refs/` 아래 파일 경로로 저장되기 때문이다. `feature`라는 ref가 파일로 있으면 같은 이름의 폴더가 필요한 `feature/login`을 만들 수 없다. fetch에서 나면 대개 원격에서 지워진 `origin/feature`가 내 저장소에 남아 있어서라, `git fetch --prune`으로 정리하고 `fetch.prune true`를 켜 둔다. 로컬 브랜치끼리 부딪히면 한쪽 이름을 바꾼다.

### index.lock 파일은 그냥 지워도 되나요?

돌고 있는 Git 프로세스가 없을 때만 지운다. Git은 인덱스를 바꿀 때 `index.lock`에 새 내용을 쓰고 이름을 바꿔 갈아 끼우는데, 프로세스가 도중에 죽으면 이 잠금 파일만 남는다. IDE의 Git 연동이나 커밋 메시지 편집기가 아직 열려 있는데 지우면 두 프로세스가 동시에 인덱스를 써서 망가질 수 있으니, `pgrep -a git`으로 먼저 확인한다.

### index file corrupt가 나면 커밋이 날아간 건가요?

아니다. 인덱스는 다음 커밋에 들어갈 파일 목록일 뿐이고 커밋은 `objects/`에, 작업 중인 파일은 디스크에 따로 있다. 깨진 `.git/index`를 옮겨 두고 `git reset`으로 HEAD 기준 인덱스를 다시 만들면 된다. 스테이징해 둔 내용만 사라지니 다시 add하고, 불안하면 `git fsck`로 나머지를 검사한다. 저장소를 클라우드 동기화 폴더에 두지 않는 게 예방이다.

### detected dubious ownership은 어떤 보안 장치인가요?

Git 2.35.2부터 다른 사용자가 소유한 저장소에서 명령을 거부한다. 남이 만든 저장소의 `.git/config`에 심어 둔 설정(훅 경로 같은)이 내 권한으로 실행되는 걸 막으려는 것이다. 도커에 마운트한 소스나 `sudo`로 만든 폴더에서 자주 보고, 믿을 수 있으면 그 경로만 `safe.directory`에 추가하거나 소유자를 맞춘다. `safe.directory '*'`는 장치를 끄는 것과 같다.

### clone했는데 서브모듈 폴더가 비어 있는 이유는 무엇인가요?

부모 저장소에는 "이 경로에 저 저장소의 이 커밋을 꺼낸다"는 기록만 있고, 일반 clone은 그 기록만 받기 때문이다. `git submodule update --init --recursive`로 받거나 처음부터 `git clone --recurse-submodules`를 쓴다. 서브모듈 안이 detached HEAD인 것은 부모가 정한 커밋을 그대로 꺼냈기 때문이라 정상이다.

### 커밋 작성자 이메일은 왜 정확히 맞춰야 하나요?

GitHub는 커밋의 이메일로 계정을 찾아서, 등록하지 않은 주소면 커밋이 내 프로필과 연결되지 않는다. 새 서버나 컨테이너에서는 설정이 없어 `Author identity unknown`으로 멈추기도 한다. 전역으로 이름과 이메일을 넣고, 회사 저장소는 local이나 `includeIf`로 따로 두며, 공개하기 싫으면 `users.noreply.github.com` 주소를 쓴다. 이미 틀리게 찍힌 마지막 커밋은 `--amend --reset-author`로 고친다.
