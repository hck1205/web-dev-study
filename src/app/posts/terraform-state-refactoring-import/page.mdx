루트에 몰려 있던 네트워크 리소스를 `modules/network`로 옮겼다. 코드는 한 글자도 안 바꾸고 위치만 옮겼으니 plan은 조용할 거라고 생각했다.

```text
  # local_file.inventory must be replaced
  # random_pet.vpc will be destroyed
  # (because random_pet.vpc is not in configuration)
  # terraform_data.subnet["a"] will be destroyed
  # (because terraform_data.subnet is not in configuration)
  # terraform_data.subnet["c"] will be destroyed
  # (because terraform_data.subnet is not in configuration)
  # module.network.random_pet.vpc will be created
  # module.network.terraform_data.subnet["a"] will be created
  # module.network.terraform_data.subnet["c"] will be created
Plan: 4 to add, 0 to change, 4 to destroy.
```

전부 지우고 다시 만든다고 한다. 실습이라 `random_pet`과 `terraform_data`지만, 실제로는 VPC와 서브넷이었다면 그 위의 모든 것이 끊긴다. Terraform에게 리소스의 정체성은 내용이 아니라 주소다. `random_pet.vpc`와 `module.network.random_pet.vpc`는 다른 리소스다.

이 글은 이렇게 코드 구조를 바꿀 때 state를 함께 옮기는 법을 다룬다. 주소를 읽는 법, 코드로 남기는 `moved`·`import`·`removed` 블록과 명령으로 고치는 `state mv`·`rm`·`push`의 차이, state를 손으로 고치기 전 백업 순서, 그리고 커진 state를 쪼개고 쪼갠 state끼리 값을 넘기는 방법까지 간다. state가 무엇이고 원격 백엔드와 잠금이 어떻게 동작하는지는 [Terraform 기본](/posts/terraform-basics)에, 모듈 구조는 [모듈과 tfvars](/posts/terraform-modules-tfvars)에 있다.

실습은 Ubuntu 24.04에서 Terraform 1.16.6과 클라우드가 필요 없는 프로바이더(`random`, `local`, 내장 `terraform_data`)로 했다. 출력은 모두 직접 돌린 결과다. S3 백엔드 부분은 계정 없이 돌릴 수 없어 명령만 적었다.

## 주소를 읽는 법

state를 다루는 모든 명령은 주소로 리소스를 가리킨다. `terraform state list`로 지금 state에 있는 주소를 보고, `state show`로 한 리소스에 저장된 속성을 본다.

```bash
# state에 있는 모든 리소스 주소
terraform state list
# 한 리소스의 저장된 속성 (따옴표로 감싸야 셸이 대괄호를 건드리지 않는다)
terraform state show 'terraform_data.subnet["a"]'
```

```text
local_file.inventory
random_pet.vpc
terraform_data.subnet["a"]
terraform_data.subnet["c"]
```

```text
# terraform_data.subnet["a"]:
resource "terraform_data" "subnet" {
    id     = "6f2f0632-f7d7-431e-0eef-1af2d5c7181c"
    input  = "vpc-guided-elk-a"
    output = "vpc-guided-elk-a"
}
```

주소는 몇 조각으로 이루어진다. 아래 그림에서 조각을 누르면 각각이 무엇을 뜻하는지 나온다.

이름과 인스턴스 키는 붙여 쓰지만 서로 다른 조각이다. 모듈 경로, 종류, 이름, 키 중 하나만 바뀌어도 Terraform에게는 다른 리소스다. 리팩터링의 대부분은 결국 "주소가 바뀌는데 실제 리소스는 그대로 두기"다.

## 코드로 남기는 방식: moved 블록

처음 장면은 `moved` 블록(1.1 이상)으로 푼다. 옛 주소와 새 주소를 코드에 적는다.

```hcl
# moved.tf
moved {
  from = random_pet.vpc
  to   = module.network.random_pet.vpc
}

moved {
  from = terraform_data.subnet
  to   = module.network.terraform_data.subnet
}
```

```text
  # random_pet.vpc has moved to module.network.random_pet.vpc
    resource "random_pet" "vpc" {
        id        = "vpc-guided-elk"
        # (3 unchanged attributes hidden)
    }

  # terraform_data.subnet["a"] has moved to module.network.terraform_data.subnet["a"]
    resource "terraform_data" "subnet" {
        id     = "6f2f0632-f7d7-431e-0eef-1af2d5c7181c"
        # (2 unchanged attributes hidden)
    }

  # terraform_data.subnet["c"] has moved to module.network.terraform_data.subnet["c"]
    resource "terraform_data" "subnet" {
        id     = "513c1366-ef7e-341f-40e8-75d9f3571fc5"
        # (2 unchanged attributes hidden)
    }

Plan: 0 to add, 0 to change, 0 to destroy.
```

`for_each` 리소스는 키를 적지 않고 리소스 전체(`terraform_data.subnet`)를 옮기면 인스턴스가 키 그대로 따라온다. 키를 바꾸는 이동도 된다. `count`에서 `for_each`로 바꿀 때는 인스턴스마다 하나씩 적는다.

```hcl
moved {
  from = aws_subnet.private[0]
  to   = aws_subnet.private["a"]
}

moved {
  from = aws_subnet.private[1]
  to   = aws_subnet.private["c"]
}
```

`moved`가 명령보다 나은 이유는 세 가지다. PR로 리뷰를 받는다. plan에 `has moved to`로 미리 보인다. 그리고 같은 코드를 쓰는 모든 환경(dev, stg, prod)과 모든 모듈 사용자에게 똑같이 적용된다. 모듈을 배포하는 쪽이라면 이게 결정적이다. 모듈 안에서 리소스 이름을 바꾸고 `moved`를 함께 넣어 두면, 그 모듈을 쓰는 수십 개의 루트가 새 버전으로 올릴 때 아무도 state 명령을 칠 필요가 없다.

`moved` 블록은 apply한 뒤에도 한동안 남겨 둔다. 아직 새 버전을 apply하지 않은 환경이 있을 수 있기 때문이다. 모든 환경과 사용자가 넘어온 것을 확인한 뒤에 지운다. 너무 일찍 지우면 늦게 올라온 환경에서 처음 장면이 그대로 재현된다. 이동이 여러 번이면 `A → B`, `B → C`를 이어서 적어도 된다. Terraform이 사슬을 따라간다.

할 수 없는 것도 있다. `moved`는 같은 state 안에서만 옮긴다. 다른 state로 넘기는 법은 뒤에서 본다. 리소스 종류를 바꾸는 이동(`aws_s3_bucket_object`를 `aws_s3_object`로)은 1.8부터 프로바이더가 그 변환을 지원할 때만 된다. 지원하지 않으면 `removed`와 `import`로 우회한다.

## 명령으로 고치는 방식: state mv와 state rm

`moved` 이전에는 `terraform state mv`로 state 안의 주소를 직접 바꿨다. 지금도 쓸 자리는 있다. 한 환경에서 한 번만 하면 되는 정리, 또는 `moved`로 표현할 수 없는 조작이다. 실행 전에 `-dry-run`으로 무엇을 할지 본다.

```bash
# 실제로 옮기지 않고 무엇을 옮길지만 출력한다
terraform state mv -dry-run 'module.network.random_pet.vpc' 'random_pet.vpc'
```

```text
Would move "module.network.random_pet.vpc" to "random_pet.vpc"
```

명령 방식의 위험은 기록이 남지 않는다는 데 있다. state는 바뀌었는데 코드가 그에 맞게 바뀌지 않으면 다음 plan이 반대 방향으로 되돌리려 한다. 그 사이 다른 사람이 옛 코드로 plan을 돌리면 삭제가 계획된다. 그래서 명령으로 고칠 때는 코드 변경과 같은 PR에서, 같은 시간에, 다른 사람이 apply하지 못하게 막아 두고 한다.

`terraform state rm`은 state에서 리소스를 빼되 실제 리소스는 그대로 둔다. 다른 팀의 Terraform으로 넘기거나, Terraform 관리를 그만둘 때 쓴다. 이것도 지금은 코드로 남기는 `removed` 블록이 있다.

## import 블록으로 데려오기

반대 방향은 콘솔이나 다른 도구로 이미 만든 리소스를 state에 올리는 것이다. 1.5부터는 `import` 블록으로 코드에 적는다. 리소스 코드를 직접 쓰기 귀찮으면 `-generate-config-out`이 초안을 만든다. 실습은 `random_string`으로 했다(이 리소스는 결과 문자열 자체가 ID다).

```hcl
import {
  to = random_string.api_key
  id = "Xk9pQ2mZ"
}
```

```bash
# import 계획을 세우고, 대상 리소스 코드가 없으면 초안을 파일로 만든다
terraform plan -generate-config-out=generated.tf
```

```text
  # random_string.api_key will be imported
  # (config will be generated)
    resource "random_string" "api_key" {
        id          = "Xk9pQ2mZ"
        length      = 8
        ...
        special     = true
        upper       = true
    }

Plan: 1 to import, 0 to add, 0 to change, 0 to destroy.
```

```hcl
# __generated__ by Terraform from "Xk9pQ2mZ"
resource "random_string" "api_key" {
  keepers          = null
  length           = 8
  lower            = true
  min_lower        = 0
  min_numeric      = 0
  min_special      = 0
  min_upper        = 0
  numeric          = true
  override_special = null
  special          = true
  upper            = true
}
```

생성된 코드에는 `= null`인 줄과 기본값이 전부 적혀 있다. 그대로 두면 읽기 어렵고, AWS 리소스라면 서브넷 ID 같은 값이 참조가 아닌 문자열로 박혀 있다. 빈 줄은 지우고 박힌 ID는 참조로 바꾼 뒤 apply한다.

```text
random_string.api_key: Importing... [id=Xk9pQ2mZ]
random_string.api_key: Import complete [id=Xk9pQ2mZ]
Apply complete! Resources: 1 imported, 0 added, 0 changed, 0 destroyed.
```

`terraform import 주소 ID` 명령도 아직 있다. 차이는 앞의 `moved`와 `state mv`의 차이와 같다. 명령은 그 자리에서 state를 바꾸고, 미리 보기가 없으며, 리소스 코드가 먼저 있어야 한다. 블록은 plan으로 미리 보고, 리뷰를 거치고, 코드 초안까지 만들어 준다. 1.7부터는 `import` 블록에 `for_each`를 써서 여러 개를 한 번에 가져올 수도 있다.

```hcl
import {
  for_each = { a = "subnet-0a1b...", c = "subnet-0c2d..." }
  to       = aws_subnet.private[each.key]
  id       = each.value
}
```

가장 중요한 것은 import 뒤의 plan이다. 코드가 실제 리소스와 조금이라도 다르면 import하자마자 Terraform이 그 차이를 "고치려" 든다. 교체가 필요한 속성이 다르면 가져온 리소스를 바로 지운다. 뒤에서 state 사이로 리소스를 옮길 때 이 일이 실제로 일어나는 것을 본다. 규칙은 하나다. import 블록이 든 plan에서 `1 to import` 옆의 add·change·destroy가 모두 0이 될 때까지 코드를 맞춘 뒤에 apply한다.

## removed: 코드에서 빼되 지우지 않는다

1.7부터 있는 `removed` 블록은 `state rm`을 코드로 적는 방법이다. 리소스 블록을 지우고 그 자리에 이렇게 적는다.

```hcl
removed {
  from = local_file.inventory

  lifecycle {
    destroy = false
  }
}
```

```text
 # local_file.inventory will no longer be managed by Terraform, but will not be destroyed
 # (destroy = false is set in the configuration)
 . resource "local_file" "inventory" {
        id                   = "41c802e8bf1e7141ae56b51448418ff06408601f"
        # (10 unchanged attributes hidden)
    }

Plan: 0 to add, 0 to change, 0 to destroy.

Warning: Some objects will no longer be managed by Terraform

If you apply this plan, Terraform will discard its tracking information for
the following objects, but it will not delete them:
 - local_file.inventory
```

plan이 "더는 관리하지 않지만 지우지는 않는다"고 분명히 말한다. 블록 없이 리소스 코드만 지웠다면 같은 자리에 `will be destroyed`가 떴을 것이다. `destroy = true`로 두면 반대로 "지우겠다"는 뜻을 명시적으로 남기는 용도가 된다. [의존성 그래프와 lifecycle](/posts/terraform-dependency-graph-lifecycle)에서 본 것처럼 `prevent_destroy`는 블록을 지우는 순간 사라지니, 운영 리소스를 코드에서 뺄 때는 이 블록을 쓰는 것이 안전하다.

## state를 통째로 다루는 pull, push, replace-provider

`terraform state pull`은 지금 백엔드의 state를 JSON으로 출력한다. 원격 백엔드라도 똑같이 동작해서 백업과 조사에 쓴다.

```bash
# 현재 state를 파일로 받아 버전, serial, lineage를 확인한다
terraform state pull > pulled.json
python3 -c "import json;d=json.load(open('pulled.json'));print(d['version'],d['terraform_version'],d['serial'],d['lineage'])"
```

```text
4 1.16.6 6 0c6b5310-2fab-5ab4-8cde-66e6e3d9e626
```

두 값을 기억해 두자. `serial`은 state가 바뀔 때마다 1씩 오르는 번호이고, `lineage`는 이 state가 처음 만들어질 때 정해지는 ID다. `terraform state push`는 파일을 백엔드에 덮어쓰는데, 이 두 값으로 사고를 막는다. 옛 백업을 실수로 올리면 거절한다.

```bash
# 예전에 떠 둔 state를 올려 본다
terraform state push pre.tfstate
```

```text
Failed to write state: cannot import state with serial 5 over newer state with serial 6
```

lineage가 다른 파일, 즉 다른 프로젝트의 state를 올려도 거절한다.

```text
Failed to write state: cannot import state with lineage "11111111-2222-3333-4444-555555555555" over unrelated state with lineage "0c6b5310-2fab-5ab4-8cde-66e6e3d9e626"
```

`-force`를 주면 이 검사를 건너뛴다. 백업으로 되돌리는 경우처럼 일부러 옛 serial을 올려야 할 때만 쓰고, 그 전에 lineage가 같은지는 반드시 눈으로 확인한다.

`terraform state replace-provider`는 state에 적힌 프로바이더 주소를 바꾼다. 사내 레지스트리로 옮기거나, 프로바이더가 다른 네임스페이스로 이사했을 때 쓴다.

```bash
# state 안의 hashicorp/random을 사내 레지스트리 주소로 바꾼다
terraform state replace-provider hashicorp/random registry.example.com/acme/random
```

```text
Terraform will perform the following actions:

  ~ Updating provider:
    - registry.terraform.io/hashicorp/random
    + registry.example.com/acme/random

Changing 2 resources:

  random_string.api_key
  module.network.random_pet.vpc

Successfully replaced provider for 2 resources.
```

코드의 `required_providers`도 같은 주소로 바꾸고 `terraform init`을 다시 해야 한다. 둘 중 하나만 바꾸면 plan이 "이 프로바이더를 찾을 수 없다"며 멈춘다.

## 손으로 고치기 전 백업 순서

state를 명령으로 고치는 일은 대개 급할 때 한다. 급할수록 순서를 지킨다.

1. 다른 사람이 apply하지 못하게 막는다. CI 파이프라인을 잠시 멈추고 팀에 알린다. 원격 백엔드의 잠금은 명령 하나가 도는 동안만 걸리므로, 여러 명령을 이어 치는 동안 끼어드는 apply는 잠금이 막아 주지 않는다.
2. `terraform state pull > backup-$(date +%Y%m%d-%H%M%S).tfstate`로 지금 state를 받는다. 이 파일에는 비밀 값이 그대로 들어 있으니 저장소 밖, 권한이 제한된 곳에 둔다.
3. `serial`과 `lineage`를 적어 둔다.
4. 고친다. `state mv`, `rm`, `import`는 그 자체로 백엔드의 state를 바꾼다. 로컬 백엔드라면 `terraform.tfstate.backup`도 자동으로 생기지만 원격 백엔드에서는 생기지 않는다.
5. `terraform plan`을 돌려 `No changes`(또는 의도한 변화만)인지 본다. 여기서 이상하면 멈춘다.
6. 되돌려야 하면 2번 파일을 `terraform state push -force`로 올린다. 이때 serial이 낮아서 `-force`가 필요하다.
7. 코드 변경을 PR로 올리고 파이프라인을 다시 연다.

## 커진 state를 쪼개는 기준

리소스가 수백 개를 넘으면 state 하나가 여러 문제를 만든다. plan 한 번에 모든 리소스를 refresh하느라 몇 분이 걸린다. 앱 태그 하나 고치는 PR이 VPC와 DB까지 같은 plan에 올린다. 잠금이 하나라 네트워크 팀이 apply하는 동안 앱 팀은 기다린다. 그리고 실수 한 번의 폭발 반경이 전체다.

쪼개는 기준은 대개 셋을 같이 본다.

- 바뀌는 빈도: VPC와 서브넷은 몇 달에 한 번, 앱 설정은 하루에 몇 번 바뀐다. 자주 바뀌는 것과 거의 안 바뀌는 것을 한 plan에 두지 않는다.
- 소유자: 리뷰하고 apply하는 팀이 다르면 state도 나눈다. 권한(IAM 역할, 백엔드 접근)도 그 경계로 나눈다.
- 지워졌을 때의 피해: 데이터가 든 리소스(RDS, S3, KMS)는 되돌릴 수 없으니 따로 떼어 변경을 드물고 신중하게 만든다.

그래서 흔한 모양은 계층별 분리다. 네트워크(VPC, 서브넷, 라우팅) → 데이터(DB, 캐시, 버킷) → 앱(컴퓨트, 로드 밸런서, DNS) 순으로 아래 계층의 출력이 위 계층의 입력이 된다. 환경(dev, prod)과 리전까지 곱하면 디렉터리가 여럿 생긴다.

## 쪼갠 뒤 값을 넘기는 세 가지

state를 나누면 앱 계층이 네트워크 계층의 서브넷 ID를 알아야 한다. 방법은 셋이다.

첫째, `terraform_remote_state` data source로 다른 state의 출력을 읽는다. 실습에서는 로컬 백엔드로 했다.

```hcl
# network/main.tf 쪽 출력
output "private_subnet_ids" {
  value = ["subnet-${random_pet.vpc.id}-a", "subnet-${random_pet.vpc.id}-c"]
}
```

```hcl
# app/main.tf
data "terraform_remote_state" "network" {
  backend = "local"
  config = {
    path = "../network/terraform.tfstate"
  }
}

resource "terraform_data" "app" {
  input = data.terraform_remote_state.network.outputs.private_subnet_ids
}
```

```text
data.terraform_remote_state.network: Reading...
data.terraform_remote_state.network: Read complete after 0s
...
  # terraform_data.app will be created
  + resource "terraform_data" "app" {
      + input  = [
          + "subnet-vpc-hardy-asp-a",
          + "subnet-vpc-hardy-asp-c",
        ]
```

간단하고 출력만 읽는다. 하지만 백엔드 수준에서는 state 파일 전체를 읽을 권한이 있어야 한다. 출력으로 내보내지 않은 비밀 값(DB 비밀번호 같은 것)도 그 파일 안에 있으니, 앱 팀이 네트워크 state를 읽을 수 있다는 것은 그 안의 모든 것을 읽을 수 있다는 뜻이다. 또 두 state가 코드로 묶여서, 네트워크 쪽 출력 이름을 바꾸면 앱 쪽이 깨진다.

둘째, data source로 실제 리소스를 찾는다. `data "aws_subnets"`에 태그 필터를 걸어 서브넷을 찾는 식이다([HCL 문법과 data source](/posts/terraform-hcl-expressions-data-sources)). state 파일에 접근할 필요가 없고, 그 서브넷을 누가 무엇으로 만들었는지 몰라도 된다. 대신 태그 규칙이 계약이 되니 태그를 바꾸면 조용히 다른 것을 찾거나 아무것도 못 찾는다.

셋째, 아래 계층이 값을 SSM Parameter Store 같은 저장소에 쓰고 위 계층이 읽는다.

```hcl
# network 쪽: 값을 쓴다
resource "aws_ssm_parameter" "private_subnets" {
  name  = "/shop/${var.env}/network/private_subnet_ids"
  type  = "StringList"
  value = join(",", aws_subnet.private[*].id)
}

# app 쪽: 값을 읽는다
data "aws_ssm_parameter" "private_subnets" {
  name = "/shop/${var.env}/network/private_subnet_ids"
}
```

파라미터 하나씩 IAM으로 권한을 줄 수 있고, Terraform이 아닌 도구(배포 스크립트, 람다)도 같은 값을 읽는다. 파라미터 이름이 계약이다. 셋 중 무엇을 고를지는 권한 경계로 정한다. 한 팀이 둘 다 관리하면 `terraform_remote_state`가 가장 간단하다. 팀이 다르거나 비밀이 섞인 state면 SSM이나 data source로 필요한 값만 연다.

실습에서 네트워크 state의 `random_string.db_suffix`를 앱 state로 옮겼다. 보내는 쪽은 문제없이 놓아줬다. 받는 쪽에서 원래 코드를 옮겨 적으면서 `special = false`를 넣었는데, plan이 이렇게 나왔다.

```text
  # random_string.db_suffix must be replaced
  # (imported from "oqsRAI")
  # Warning: this will destroy the imported resource
-/+ resource "random_string" "db_suffix" {
      ~ id          = "oqsRAI" -> (known after apply)
        length      = 6
        ...
      ~ result      = "oqsRAI" -> (known after apply)
      ~ special     = true -> false # forces replacement
        upper       = true
    }

Plan: 1 to import, 2 to add, 0 to change, 1 to destroy.
```

`Warning: this will destroy the imported resource`. 가져오자마자 지우겠다는 계획이다. 이 리소스는 import할 때 `special` 같은 생성 옵션을 실제 값에서 알아낼 방법이 없어 기본값(`true`)을 state에 적는다. 코드의 `false`와 다르니 교체다. 실제 클라우드 리소스에서도 같은 일이 생긴다. import로는 읽히지 않는 속성(생성할 때만 쓰는 비밀번호, 일부 생성 옵션)이 있고, 프로바이더마다 문서의 Import 절에 그 목록이 있다. 코드를 `special = true`로 맞추자 plan이 바로 조용해졌다.

```text
  # random_string.db_suffix will be imported
  # terraform_data.app will be created
Plan: 1 to import, 1 to add, 0 to change, 0 to destroy.
```

교체가 꼭 막아야 하는 리소스라면 받는 쪽 리소스에 잠시 `prevent_destroy`를 걸어 두는 것도 방법이다. 코드가 어긋나 있으면 plan이 실패하니 apply까지 가지 않는다. 옮기는 동안 보내는 쪽 apply는 이미 끝났고 받는 쪽은 아직이니, 그 사이 리소스는 어느 state에도 없다. 이 시간을 짧게 잡고 그동안 둘 다 apply를 막는다.

## S3 버전 관리로 state 되돌리기

원격 백엔드로 S3를 쓴다면 버킷에 버전 관리를 반드시 켠다. 잘못된 apply나 `state push` 뒤에 이전 state로 돌아갈 마지막 수단이다. 순서는 이렇다.

```bash
# 버킷 버전 관리를 켠다 (백엔드 버킷을 만들 때 한 번)
aws s3api put-bucket-versioning --bucket acme-tfstate \
  --versioning-configuration Status=Enabled

# state 파일의 버전 목록을 본다 (최근 것이 위)
aws s3api list-object-versions --bucket acme-tfstate \
  --prefix prod/network/terraform.tfstate \
  --query 'Versions[].[VersionId,LastModified,Size]' --output table

# 되돌릴 버전을 받는다
aws s3api get-object --bucket acme-tfstate \
  --key prod/network/terraform.tfstate \
  --version-id '버전ID' restore.tfstate

# 지금 state를 먼저 백업하고, lineage가 같은지 확인한 뒤 올린다
terraform state pull > before-restore.tfstate
terraform state push -force restore.tfstate
terraform plan
```

S3 콘솔에서 옛 버전을 "최신으로 복사"하는 방법도 있지만, DynamoDB 잠금을 쓰는 백엔드는 테이블에 state의 체크섬을 따로 저장해서 파일만 바꾸면 다음 plan이 체크섬 불일치로 멈춘다. Terraform 명령(`state push`)으로 올리면 체크섬도 함께 갱신된다. S3 자체 잠금(`use_lockfile`)만 쓰는 구성에서는 이 체크섬 테이블이 없다. 버전이 끝없이 쌓이지 않게 수명 주기 규칙으로 오래된 이전 버전(예: 90일 지난 것)을 정리하되, 너무 짧게 잡지 않는다.

되돌린 state는 "그 시점의 기억"일 뿐이다. 그 뒤에 실제로 만들어진 리소스는 state에 없으니, 되돌린 뒤의 plan이 그것들을 다시 만들겠다고 할 수 있다. 그 목록을 하나씩 import하거나 지우는 것까지가 복구다.

## 현장에서 state 리팩터링이 사고가 되는 순간

- 모듈로 옮긴 PR이 리뷰 없이 다른 환경에 먼저 apply되었다: `moved`가 없었다면 그 환경의 리소스가 교체된다. 리팩터링 PR은 plan의 destroy가 0인지부터 본다.
- `moved`를 지웠더니 늦게 업그레이드한 환경에서 교체가 뜬다: 모든 사용자가 넘어올 때까지 남겨 둔다.
- import 직후 apply에서 리소스가 사라졌다: import가 든 plan의 destroy를 보지 않았다. `Warning: this will destroy the imported resource`가 신호다.
- 원격 state에 `state push`를 했더니 다른 사람의 변경이 사라졌다: 백업한 뒤 다른 apply가 있었다. 고치는 동안 파이프라인을 멈춘다.
- 쪼갠 뒤 앱 팀이 네트워크 state 전체를 읽고 있다: `terraform_remote_state`의 권한은 파일 단위다. 필요한 값만 SSM으로 연다.

## 주소를 옮길 때는 코드에 적는다

Terraform에게 리소스는 주소다. 주소가 바뀌는 리팩터링은 `moved`로, 코드 밖의 리소스를 데려올 때는 `import`로, 코드에서 빼되 남길 때는 `removed`로 적는다. 셋 다 plan으로 미리 보고 리뷰를 받는다. 명령으로 state를 고쳐야 한다면 apply를 막고, 백업하고, plan이 조용한지 확인한 뒤에 연다. state가 커지면 바뀌는 빈도와 소유자로 쪼개고, 쪼갠 state 사이에는 필요한 값만 넘긴다.

## 면접에서 나올 만한 질문

### 리소스를 모듈로 옮겼더니 plan이 삭제 후 생성을 계획합니다. 왜 그렇고 어떻게 하나요?

Terraform은 리소스를 주소로 식별하는데, 모듈로 옮기면 주소 앞에 `module.이름`이 붙어 다른 리소스가 된다. 옛 주소는 코드에 없으니 삭제, 새 주소는 state에 없으니 생성이다. `moved` 블록에 옛 주소와 새 주소를 적으면 plan이 `has moved to`로 바뀌고 변경이 0이 된다.

### moved 블록과 terraform state mv는 무엇이 다른가요?

`moved`는 코드에 남아 PR로 리뷰되고, plan에서 미리 보이며, 같은 코드를 쓰는 모든 환경과 모듈 사용자에게 똑같이 적용된다. `state mv`는 실행하는 순간 그 state만 바꾸고 기록이 남지 않아서, 코드와 어긋나면 다음 plan이 되돌리려 한다. 모든 환경이 넘어올 때까지 `moved`는 지우지 않는다.

### import 블록과 terraform import 명령의 차이는요?

블록은 plan으로 무엇을 가져오는지 미리 보여 주고, 리뷰를 거쳐 apply 때 가져오며, `-generate-config-out`으로 코드 초안도 만든다. 1.7부터는 `for_each`로 여러 개를 가져올 수 있다. 명령은 리소스 코드가 먼저 있어야 하고 즉시 state를 바꾼다. 어느 쪽이든 가져온 뒤 plan이 조용해질 때까지 코드를 맞춰야 한다.

### import했더니 바로 교체가 계획됐습니다. 왜 그런가요?

코드와 실제 리소스가 교체가 필요한 속성에서 다르기 때문이다. 어떤 속성은 import로 읽을 수 없어 기본값이 state에 들어가는데, 실습에서 `random_string`의 `special`이 그랬다. plan에 `Warning: this will destroy the imported resource`가 뜨면 apply하지 말고 `forces replacement`가 붙은 속성을 코드에서 맞춘다.

### 리소스를 지우지 않고 Terraform 관리에서만 빼려면 어떻게 하나요?

1.7 이상이면 리소스 블록을 지우고 `removed` 블록에 `lifecycle { destroy = false }`를 적는다. plan이 "관리하지 않지만 지우지 않는다"고 보여 주고, 코드로 기록이 남는다. 예전 방식은 `terraform state rm`이다. 블록 없이 코드만 지우면 삭제가 계획된다.

### state를 손으로 고치기 전에 무엇을 하나요?

다른 apply가 끼어들지 못하게 파이프라인을 멈추고, `state pull`로 지금 state를 받아 안전한 곳에 둔다. serial과 lineage를 적어 두고, 고친 뒤 plan이 의도한 변화만 보이는지 확인한다. 되돌릴 때는 백업을 `state push -force`로 올린다. push는 serial이 낮거나 lineage가 다르면 거절하는데, `-force`는 그 검사를 끄는 것이니 lineage는 눈으로 확인한다.

### 큰 state는 어떤 기준으로 쪼개고, 쪼갠 뒤 값은 어떻게 넘기나요?

바뀌는 빈도, 소유 팀, 지워졌을 때의 피해를 함께 보고 보통 네트워크, 데이터, 앱 계층으로 나눈다. 값은 `terraform_remote_state`, 태그로 찾는 data source, SSM 같은 파라미터 저장소로 넘긴다. `terraform_remote_state`는 간단하지만 state 파일 전체를 읽을 권한이 필요해서, 팀이 다르거나 비밀이 섞여 있으면 필요한 값만 파라미터로 연다.

### 잘못된 apply 뒤에 이전 state로 되돌리려면요?

S3 백엔드라면 버전 관리로 이전 버전을 받아, 지금 state를 백업한 뒤 `state push -force`로 올린다. 콘솔에서 파일만 바꾸면 DynamoDB 잠금을 쓰는 구성에서는 체크섬이 어긋난다. 되돌린 state에는 그 뒤에 만든 리소스가 없으니, 다음 plan에서 그것들을 import하거나 정리하는 것까지 해야 복구가 끝난다.
