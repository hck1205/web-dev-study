이 시리즈에서 이 글의 자리: 앞 글은 [㊱ 주변 친구 설계](/posts/sd-nearby-friends)이고, 다음 글은 같은 장의 두 번째 글인 [㊳ 지도 서비스 ②: 위치 수집과 ETA](/posts/sd-maps-location-eta)다. 위치 장의 첫 글은 [㉟ 주변 검색 설계](/posts/sd-proximity-service)였다. 이 글은 지도 화면을 그리는 법과 길을 찾는 법을 다루고, 실시간 교통과 도착 시간은 다음 글로 넘긴다.

지도 앱을 열고 서울을 확대하면 화면이 한 번에 뜨지 않는다. 회색 네모 몇 칸이 먼저 보이고, 그 자리에 정사각형 그림이 하나씩 채워진다. 손가락으로 끌면 가장자리에 다시 빈 칸이 생겼다가 채워진다. 그 정사각형 하나하나가 타일이다. 면접에서는 "구글 지도 같은 지도 서비스를 설계하라"로 나온다. 범위가 넓어서 보통 지도 그리기, 길 찾기, 위치 수집과 도착 시간 예측으로 나눈다. 이 글은 앞의 둘이다.

## 세계 지도를 그림 한 장으로 보내면

가장 단순한 버전을 떠올려 본다. 세계 지도를 아주 큰 그림 한 장으로 만들어 두고, 앱이 그 그림을 받아 확대해서 보여 준다. 건물 하나가 보일 만큼 자세한 세계 지도는 가로세로 수천만 픽셀이 넘는다. 내가 보고 싶은 건 화면 한 장 크기의 강남역 주변뿐인데, 지구 전체를 받아야 한다. 휴대폰 메모리에도 안 들어간다.

그래서 지도를 잘게 잘라 둔다. 화면에 보이는 부분의 조각만 받고, 확대 정도에 맞는 해상도의 조각을 받는다. 이 조각이 타일이고, 웹 지도에서는 거의 모두 가로세로 256픽셀(고해상도 화면용은 512픽셀) 정사각형을 쓴다.

## 둥근 지구를 네모로 펴기

조각을 내려면 먼저 둥근 지구를 평평한 네모로 펴야 한다. 이 변환을 투영(projection)이라고 하는데, 구를 평면에 펴면 어딘가는 반드시 늘어나거나 줄어든다. 웹 지도 대부분은 웹 메르카토르라는 투영을 쓴다. 경선과 위선이 직각으로 만나서 북쪽이 늘 위이고, 작은 영역의 모양(각도)이 유지된다. 길모퉁이가 직각으로 보이니 거리 지도에 맞는다.

대가는 넓이다. 극으로 갈수록 크게 늘어나서, 그린란드가 아프리카만큼 커 보인다. 그리고 극까지 펴면 무한히 늘어나니 위도 약 85.0511도에서 자른다. 이 값은 지도 전체가 정확히 정사각형이 되도록 고른 위도다. 정사각형이어야 반씩 자르기 좋다.

좌표를 타일 번호로 바꾸는 식은 짧다. 경도는 그대로 비율로 바꾸면 되고, 위도만 메르카토르 식을 거친다. 서울시청 좌표로 몇 단계를 계산해 봤다.

```js
// tiles.js: 위도·경도 → 웹 메르카토르 타일 z/x/y
function lonLatToTile(lon, lat, z) {
  const n = 2 ** z, rad = (lat * Math.PI) / 180;
  const x = Math.floor(((lon + 180) / 360) * n);
  const y = Math.floor(((1 - Math.log(Math.tan(rad) + 1 / Math.cos(rad)) / Math.PI) / 2) * n);
  return [x, y];
}
const cityHall = [126.978, 37.5665];
for (const z of [0, 1, 5, 10, 15, 18]) {
  const [x, y] = lonLatToTile(...cityHall, z);
  const mpp = (156543.03392 * Math.cos((cityHall[1] * Math.PI) / 180)) / 2 ** z;   // 256px 타일에서 1픽셀이 몇 m
  console.log(`z=${z} tile ${z}/${x}/${y} tiles in world ${4 ** z} ${mpp.toFixed(2)} m/px`);
}
```

## 타일은 미리 그려 CDN에 둔다

요청이 올 때마다 도로 데이터로 타일을 그리면 서버가 감당하지 못한다. 같은 타일을 수백만 명이 받는데 매번 다시 그릴 이유도 없다. 지도 그림은 며칠에 한 번 바뀌니 미리 그려서 파일로 저장하고 CDN(사용자 가까운 곳에 사본을 두는 캐시 서버망)에서 내준다. 정적 파일이라 캐시하기 아주 좋다.

앱이 타일 주소를 직접 계산하는 방식은 서버를 한 번 덜 거친다. 대신 계산 규칙을 바꾸기 어렵다. 이미 깔린 앱은 옛 규칙으로 계산하고, 사람들에게 앱을 업데이트하라고 강제하기는 힘들다. 그래서 "이 영역에 필요한 타일 주소 목록"을 돌려주는 작은 API를 두는 서비스도 있다. 요청이 한 번 늘지만 규칙은 서버에서 바꿀 수 있다. 버전 숫자 정도는 앱이 시작할 때 설정 API로 받는 식으로 둘을 섞기도 한다.

## 저장 공간과 비어 있는 바다

z=18까지 모든 타일을 그리면 앞의 출력대로 약 916억 장이다. 한 장에 평균 20KB라고 가정하면 1.8PB쯤 된다. 그런데 지구의 70%는 바다다. 바다 한복판의 타일은 파란 네모 하나로 모두 똑같다. 내용을 해시해서 같은 그림은 한 번만 저장하고 주소만 여러 개가 가리키게 하면 크게 준다. 사막과 빙하도 비슷하다. 아무도 확대해 보지 않는 깊은 줌의 바다 타일은 아예 그리지 않고, 요청이 오면 한 단계 위 타일을 늘려 보여 주기도 한다.

## 그림 대신 도형을 보내는 벡터 타일

지금까지는 타일을 PNG 같은 그림(래스터 타일)으로 생각했다. 요즘 지도 앱은 대부분 벡터 타일을 쓴다. 타일 안에 그림 대신 "이 선은 도로, 이 다각형은 공원" 같은 도형 데이터를 담아 보내고, 앱이 GPU로 직접 그린다. 형식은 Mapbox Vector Tile(MVT)처럼 protobuf로 압축한 바이너리가 흔하다.

벡터 타일은 같은 영역에서 그림보다 대개 작고, 확대 사이를 부드럽게 이어 그린다. 지도를 돌려도 글자가 똑바로 서고, 다크 모드처럼 색을 바꿀 때 타일을 다시 받을 필요가 없다. 대신 그리는 일이 기기로 넘어가서, 오래된 휴대폰에서는 버벅일 수 있고 앱이 렌더링 엔진을 품어야 한다. 위성 사진은 본래 그림이라 래스터로 남는다.

## 교차로는 점, 도로는 선

이제 길 찾기다. 도로망을 그래프로 본다. 교차로가 노드(점), 교차로 사이의 도로가 간선(선)이다. 간선에는 무게를 붙이는데, 길이보다 지나가는 시간을 쓴다. 3km 고속도로가 1.6km 골목보다 빠를 수 있기 때문이다. 일방통행은 한쪽 방향 간선만 두면 된다. 그래프 자체를 다루는 DB 이야기는 [그래프 DB](/posts/db-type-graph)에 있다.

작은 도로망을 직접 만들었다. 교차로 9개, 도로 13개다. 도로마다 종류에 따라 속도를 정했다. 골목은 시속 30km, 간선도로는 60km, 고속도로는 90km다.

```js
// route.js 일부: 그림 1칸 = 20m, 도로 종류별 속도로 간선 무게(분)를 정한다
const SPEED = { local: 30, arterial: 60, highway: 90 };   // km/h
const roads = [["S","A","local"],["A","C","local"],["C","F","local"],["F","G","local"],["S","H","local"],["H","B","local"],
  ["A","B","local"],["B","E","arterial"],["C","E","local"],["E","G","arterial"],["H","D","arterial"],["D","G","highway"],["B","D","local"]];
const minutes = (m, kmh) => (m / 1000 / kmh) * 60;
```

S에서 G까지 가는 길은 여러 개다. 아래쪽 골목을 따라 S→A→C→F→G로 가면 거리는 가장 짧은 편이지만 14.23분이 걸린다. 위로 돌아 고속도로를 타는 S→H→D→G는 거리는 길어도 10.15분이다.

## 가까운 곳부터 확정하는 다익스트라

## 목적지 쪽으로 기울이는 A*

다익스트라는 목적지가 어느 방향인지 모른다. 출발점을 중심으로 원을 넓혀 가듯 모든 방향을 똑같이 뒤진다. G가 동쪽에 있어도 서쪽 노드까지 확정한다. A*(에이스타)는 대기열의 순서를 "여기까지 온 시간 + 여기서 목적지까지 남은 시간의 추정"으로 바꾼다. 추정에는 직선거리를 최고 속도(시속 90km)로 달린다고 친 시간을 쓴다.

이 추정은 실제 남은 시간보다 절대 크지 않다. 직선보다 짧은 길은 없고, 90km보다 빨리 달리는 도로도 없기 때문이다. 이렇게 실제보다 크지 않은 추정을 쓰면 A*도 최단 경로를 보장한다. 추정이 실제보다 커지면 더 빨리 끝나지만 가장 빠른 길을 놓칠 수 있다.

## 그래프가 크면 타일로 자른다

나라 하나의 도로망은 교차로가 수백만 개를 넘는다. 전 세계를 그래프 하나로 메모리에 올려 두고 뒤지기는 어렵다. 그래서 지도 그림처럼 도로 그래프도 칸으로 자른다. 이것을 라우팅 타일이라고 부른다. 타일 하나에는 그 칸 안의 교차로와 도로가 들어 있고, 칸 경계를 넘는 도로는 "옆 타일의 몇 번 교차로로 이어진다"는 참조를 갖는다. 길 찾기는 출발점이 든 타일부터 읽고, 탐색이 경계에 닿으면 그때 옆 타일을 읽는다.

200m 간격 격자 도로 160×160개(교차로 25,600개)를 만들고, 20×20 교차로씩 타일 64장으로 잘랐다. 탐색이 어떤 교차로의 이웃을 물을 때마다 그 교차로의 타일을 읽었다고 세었다.

```js
// route-grid.js 일부: 이웃을 물을 때 그 교차로가 든 타일을 읽은 것으로 센다
const graph = { adj(u) {
  const [x, y] = xy(u);
  tilesLoaded.add(`${Math.floor(x / TILE)},${Math.floor(y / TILE)}`);
  /* ... 상하좌우 이웃과 간선 무게(분) ... */
} };
const start = id(10, 10), goal = id(70, 40);
```

```text
Dijkstra 17.23min  settled  5065 of 25600  tiles read 19 of 64  36.7ms
A*       17.23min  settled  1556 of 25600  tiles read  9 of 64  7.6ms
```

같은 답(17.23분)을 내면서 A*는 확정한 교차로가 3분의 1 아래, 읽은 타일이 절반 아래다. 시간은 이 컨테이너에서 한 번 잰 값이라 돌릴 때마다 조금씩 다르다. 읽는 타일이 줄면 메모리와 저장소에서 가져오는 양이 줄어든다. 길 찾기 서버는 자주 쓰는 타일을 메모리에 캐시해 두고, 없는 타일만 저장소에서 읽는다.

## 먼 길은 굵은 도로만 본다

서울에서 부산까지 가는 길을 골목 단위 타일로 찾으면 수백 장을 이어 붙여야 한다. 사람도 그렇게 길을 찾지 않는다. 동네를 빠져나와 고속도로를 타고, 목적지 근처에서 다시 골목으로 들어간다. 라우팅 타일도 단계를 둔다.

라우팅 타일은 DB에 넣을 이유가 별로 없다. 질의할 일 없이 통째로 읽기만 하니, 인접 리스트를 압축한 바이너리 파일로 만들어 객체 저장소에 둔다. 원본 도로 데이터(여러 출처에서 모은 수 TB의 지도 자료)는 정기 배치가 정리해서 타일로 굽는다. 지도 그림 타일과 같은 길이다.

## 현장에서 길 찾기가 틀리는 순간

길 찾기 버그는 대개 그래프를 만드는 쪽에서 난다. 일방통행을 양방향으로 넣으면 역주행 경로가 나온다. 좌회전 금지나 유턴 금지 같은 회전 제한은 노드와 간선만으로는 표현이 안 돼서, 간선과 간선 사이의 금지 목록을 따로 두거나 간선을 노드로 바꾼 그래프를 쓴다. 이걸 빼먹으면 지도에서는 멀쩡해 보이는 금지 좌회전을 안내한다.

타일 경계에서 끊기는 문제도 흔하다. 경계를 넘는 간선의 참조가 한쪽 타일에만 있으면, 한 방향으로는 길이 찾아지고 반대 방향으로는 "경로 없음"이 나온다. 타일을 새로 구운 뒤에는 무작위 출발·도착 쌍 수천 개로 경로를 찾아 보고, 이전 버전과 결과가 크게 다른 쌍을 뽑아 확인한다.

## 다음 글

지도 화면은 웹 메르카토르로 편 세계를 줌마다 넷으로 쪼갠 타일로 그렸다. 타일은 미리 그려 버전을 붙인 주소로 CDN에 두고, 요즘은 그림 대신 도형을 보내는 벡터 타일이 많다. 길 찾기는 교차로와 도로를 그래프로 보고 다익스트라나 A*로 찾되, 그래프가 크니 라우팅 타일로 자르고 먼 길은 굵은 도로만 담은 높은 단계 타일로 건넜다.

여기까지는 도로 속도를 고정값으로 썼다. 다음 글 [㊳ 지도 서비스 ②: 위치 수집과 ETA](/posts/sd-maps-location-eta)에서는 수많은 사람의 위치를 모아 지금의 도로 속도를 알아내고, 그걸로 도착 시간을 고치고 막힌 길을 피해 다시 안내한다.

## 면접에서 나올 만한 질문

### 지도를 왜 타일로 나누나요?

화면에 보이는 부분만, 확대 정도에 맞는 해상도로 받으려고 나눈다. 세계 지도를 한 장으로 보내면 내가 보는 한 블록 때문에 지구 전체를 받는다. 타일은 (z, x, y) 세 숫자로 정해져서 앱이 주소를 계산할 수 있고, 같은 타일을 모두가 받으니 CDN 캐시가 잘 맞는다. 줌 레벨이 하나 오를 때마다 타일 수는 4배가 된다.

### 타일은 요청이 올 때 그리나요, 미리 그리나요?

미리 그린다. 지도 그림은 며칠에 한 번 바뀌는데 같은 타일을 수백만 명이 받으니, 요청마다 그리면 서버가 같은 일을 반복한다. 배치가 타일을 그려 객체 저장소에 올리고 CDN이 내준다. 버전을 주소에 넣어 긴 캐시 기한을 걸고, 다시 그리면 버전을 올려 새 주소로 받게 한다.

### 래스터 타일과 벡터 타일은 무엇이 다른가요?

래스터는 그림을, 벡터는 도로와 건물의 도형 데이터를 보낸다. 벡터는 대개 더 작고, 앱이 직접 그리니 확대가 부드럽고 회전·색 변경에 다시 받을 필요가 없다. 대신 기기가 그리는 비용을 진다. 위성 사진처럼 본래 그림인 데이터는 래스터로 남는다.

### 다익스트라와 A*의 차이는요?

다익스트라는 출발점에서 가까운 순으로 모든 방향을 확정해 나가고, A*는 남은 거리의 추정을 더해 목적지 쪽부터 뒤진다. 추정이 실제보다 크지 않으면 A*도 최단 경로를 보장한다. 격자 도로 실험에서 같은 답을 내며 A*가 확정한 교차로는 5,065개 대신 1,556개였다. 시간 기준 길 찾기라면 추정은 직선거리를 최고 속도로 나눈 값을 쓴다.

### 전 세계 도로망에서 길을 찾으려면 어떻게 하나요?

그래프를 라우팅 타일로 잘라 필요한 타일만 읽는다. 경계를 넘는 도로는 옆 타일 참조를 갖고, 탐색이 경계에 닿으면 그때 옆 타일을 읽는다. 먼 길은 고속도로만 담은 높은 단계 타일로 건너고, 출발과 도착 근처에서만 자세한 타일을 쓴다. 실제 엔진은 지름길을 미리 계산해 두는 Contraction Hierarchies 같은 기법을 더한다.

### 지도 데이터가 바뀌면 이미 깔린 앱은 어떻게 되나요?

타일 주소에 버전이 있으니, 앱이 시작할 때 설정 API로 새 버전 번호만 받으면 새 타일을 받는다. 앱이 타일 주소 계산 규칙 자체를 갖고 있으면 그 규칙은 바꾸기 어렵다. 그래서 규칙은 단순하게 고정하고, 바뀔 수 있는 값은 서버가 내려 주게 둔다. 영역별 타일 주소를 돌려주는 API를 두면 요청 하나가 늘지만 규칙까지 서버에서 바꿀 수 있다.

### 길 찾기 결과가 틀렸다는 신고가 오면 어디부터 보나요?

그래프를 만든 쪽부터 본다. 일방통행 방향, 회전 금지 목록, 타일 경계를 넘는 간선의 참조가 빠졌는지 확인한다. 한 방향만 길이 찾아지면 경계 참조가 한쪽에만 있는 경우가 많다. 타일을 새로 구울 때마다 무작위 출발·도착 쌍으로 이전 버전과 결과를 비교하면 이런 문제를 배포 전에 잡는다.
