DB 백업 스크립트를 cron에 걸어 두고 몇 주가 지났다. 매일 아침 `backup done` 로그가 찍혀 있었고 종료 코드도 0이었다. 복구 연습을 하려고 백업 파일을 열었더니 크기가 20바이트였다. 그 스크립트를 그대로 돌려 봤다.

```bash
#!/bin/bash
BACKUP_DIR="${BACKUP_DIR:-/var/backups/shop}"
out="$BACKUP_DIR/shop-$(date +%F).sql.gz"
mkdir -p "$BACKUP_DIR"
pg_dump -p "${PGPORT:-5432}" shop | gzip > "$out"
echo "backup done: $out"
```

```text
pg_dump: error: connection to server on socket "/var/run/postgresql/.s.PGSQL.5499" failed: No such file or directory
	Is the server running locally and accepting connections on that socket?
backup done: ./backups/shop-2026-10-22.sql.gz
exit=0
-rw-r--r-- 1 root root 20 Oct 22 00:41 shop-2026-10-22.sql.gz
```

`pg_dump`는 DB에 붙지 못하고 실패했다. 그런데 파이프 뒤의 `gzip`은 빈 입력을 받아 20바이트짜리 빈 압축 파일을 만들었고, 스크립트는 다음 줄로 넘어가 "끝났다"고 말했다. bash는 기본적으로 실패를 만나도 멈추지 않는다. 사람이 터미널에서 명령을 하나씩 칠 때는 그게 맞는 동작이지만, 아무도 보지 않는 스크립트에서는 실패가 조용히 묻힌다.

이 글은 bash가 실패를 어떻게 알리는지(종료 코드)에서 시작해 `set -euo pipefail`이 막아 주는 것과 막지 못하는 것, 따옴표와 배열, 함수의 출력과 로그 나누기, trap으로 뒷정리하기, shellcheck까지 보고 이 백업 스크립트를 제대로 고친다. 기준은 Ubuntu 24.04의 bash 5.2이고, 22.04의 bash 5.1도 이 글의 내용은 같다. 모든 출력은 직접 돌린 결과다. 스크립트로 자동화한 작업을 언제 돌릴지는 [크론 잡 글](/posts/cron-jobs)에서, 백업을 몇 벌 어디에 둘지는 [백업 전략 글](/posts/backup-strategy)에서 다룬다.

## 종료 코드 하나가 성공과 실패를 가른다

모든 명령은 끝날 때 0에서 255 사이의 숫자 하나를 남긴다. 0이 성공이고 나머지는 모두 실패다. 바로 앞 명령의 값은 `$?`에 있다.

```bash
true; echo "true -> $?"
false; echo "false -> $?"
nosuchcmd; echo "nosuchcmd -> $?"
./backups; echo "dir as cmd -> $?"          # 디렉터리를 실행하려 했다
sleep 30 & p=$!; kill $p; wait $p; echo "killed by TERM -> $?"
grep -q nothing /etc/hostname; echo "grep no match -> $?"
grep -q x /nonexistent; echo "grep error -> $?"
```

```text
true -> 0
false -> 1
nosuchcmd -> 127
dir as cmd -> 126
killed by TERM -> 143
grep no match -> 1
grep error -> 2
```

127은 명령을 찾지 못한 것, 126은 찾았지만 실행할 수 없는 것이다. 시그널로 죽으면 128에 시그널 번호를 더한 값이 된다. SIGTERM이 15라서 143, SIGKILL이면 137이다. 컨테이너가 137로 끝났다면 OOM이나 강제 종료를 의심하는 이유가 이거다. 시그널 번호는 [프로세스와 시그널 글](/posts/linux-processes-signals)에 정리해 두었다. `grep`은 1과 2를 구분한다. 1은 "찾는 줄이 없다"는 정상적인 대답이고, 2가 진짜 오류다. 이 차이가 뒤에서 `set -e`와 부딪힌다. `if`, `&&`, `||`, `while`은 모두 이 종료 코드를 보고 갈 길을 고른다. `if [ ... ]`의 `[`도 종료 코드를 내는 명령 하나다.

## 파이프는 마지막 명령의 성적만 낸다

`a | b | c`의 종료 코드는 기본적으로 맨 오른쪽 `c`의 것이다. 앞의 명령이 얼마나 실패했든 `c`가 0이면 파이프 전체가 0이다. 각 명령의 성적은 `PIPESTATUS` 배열에 남는다.

```bash
pg_dump -p 5499 shop 2>/dev/null | gzip > /dev/null
echo "PIPESTATUS=${PIPESTATUS[*]}"
```

```text
PIPESTATUS=1 0
```

`set -o pipefail`을 켜면 파이프의 종료 코드가 "0이 아닌 값을 낸 가장 오른쪽 명령의 값"으로 바뀐다. 모두 0일 때만 0이다. 아래 그림에서 단계를 넘기면 두 프로세스가 동시에 돌다가 끝나는 순서와, 셸이 무엇을 성적으로 삼는지 볼 수 있다.

이제 실패로 끝나고 `backup done`도 찍히지 않는다. 그런데 20바이트 파일은 여전히 남았다. 리다이렉션은 파이프가 돌기 전에 파일을 만들어 버리기 때문이다. 다음 날 보관 정리 스크립트가 이 파일을 "어제 백업"으로 세면 곤란하다. 이건 뒤에서 trap과 임시 파일로 고친다.

`pipefail`에도 함정이 하나 있다. `cmd | head -1`처럼 뒤쪽이 일찍 읽기를 멈추면 앞쪽 명령이 SIGPIPE를 받고 141로 끝날 수 있다. 출력이 길 때만 가끔 실패하는 스크립트가 되니, 그런 자리는 앞쪽 명령이 출력을 줄이게 하거나(`grep -m1`) 그 줄만 `|| true`로 받아 준다.

## set -e가 멈추지 않는 자리

`set -e`(errexit)는 "명령이 실패하면 스크립트를 끝낸다"로 알려져 있지만 정확히는 그보다 좁다. 종료 코드를 누가 검사하고 있는 자리에서는 발동하지 않는다. 일부러 함정만 모은 스크립트를 돌렸다.

```bash
#!/bin/bash
set -e
check() {
  false            # 여기서 멈출까?
  echo "check: false 다음 줄까지 왔다"
}
if check; then echo "if: check 성공으로 봤다"; fi
check || echo "never"
echo "--- local"
f() {
  local v=$(false)
  echo "local: 상태 $? 로 계속 간다"
  local w
  w=$(false)
  echo "여기는 안 온다"
}
f
```

```text
check: false 다음 줄까지 왔다
if: check 성공으로 봤다
check: false 다음 줄까지 왔다
--- local
local: 상태 0 로 계속 간다
exit=1
```

`if check`와 `check || ...` 안에서는 함수 속의 `false`까지 모두 errexit가 꺼진다. 그래서 `check`는 실패를 무시하고 끝까지 돈 뒤 마지막 `echo`의 0을 돌려주고, `if`는 성공으로 본다. "실패하면 멈추겠지" 하고 함수 안에 검사를 넣은 다음 `if`로 부르면 그 검사들이 모두 무력해진다. 함수가 성공과 실패를 알려야 한다면 함수 안에서 `|| return 1`로 직접 돌려준다.

`local v=$(false)`도 멈추지 않았다. 이 줄의 종료 코드는 `$(false)`가 아니라 `local`이라는 명령의 것이고, `local`은 변수를 만드는 데 성공했으니 0이다. `export x=$(...)`, `readonly x=$(...)`도 같다. 선언과 대입을 두 줄로 나누면(`local w` 다음 `w=$(false)`) 그제야 멈춘다.

조용히 죽는 쪽도 있다. `set -e` 아래에 `count=0`과 `((count++))`, `echo`만 둔 스크립트는 아무 메시지 없이 `exit=1`로 끝났다. `((count++))`는 증가하기 전 값 0을 식의 결과로 쓰고, 산술 결과가 0이면 종료 코드가 1이다. 같은 이유로 `n=$(grep -c ERROR app.log)`는 ERROR가 한 줄도 없을 때 `grep`이 1을 내서 스크립트가 죽는다. 오류가 없어서 죽는 셈이다. 이런 자리는 `count=$((count + 1))`로 쓰거나 `grep -c ... || true`로 "없음"을 받아 준다.

명령 치환 `$(...)` 안은 또 다르다. bash는 기본적으로 그 안의 서브셸에 errexit를 물려주지 않는다.

```bash
set -e; x=$(false; echo "subshell kept going"); echo "x=$x"
set -e; shopt -s inherit_errexit; x=$(false; echo "subshell kept going"); echo "x=$x"
```

```text
x=subshell kept going
exit=0
exit=1
```

`shopt -s inherit_errexit`(bash 4.4부터)를 켜야 안에서도 멈춘다. 이렇게 구멍이 많아서 `set -e`를 아예 쓰지 말고 모든 명령에 `|| die`를 붙이자는 사람도 있다. 나는 `set -e`를 켜 두고, 위의 자리들을 알고 피하는 쪽이 현실적이라고 본다. 켜 두면 적어도 맨 위 백업 같은 사고는 막는다.

## 없는 변수는 빈 문자열로 펼쳐진다

bash는 정의되지 않은 변수를 오류로 보지 않고 빈 문자열로 펼친다. 로그를 지우는 스크립트에서 인자를 빠뜨렸을 때 무슨 일이 생기는지, 지우기 대신 `ls`로 대상만 찍어 봤다.

```bash
#!/bin/bash
cd rmdemo
LOG_DIR=$1
echo "targets of $LOG_DIR/*:"
ls -d $LOG_DIR/*
```

```text
targets of app/*:
app/a.log
---
targets of /*:
/bin
/bin.usr-is-merged
/boot
/container_info.json
/dev
/etc
/home
```

출력은 앞부분만 옮겼다. 인자가 없으니 `$LOG_DIR/*`가 `/*`가 됐고, 루트의 모든 항목이 대상이 됐다. 여기에 `rm -rf`가 있었다면 서버가 사라진다. Steam의 리눅스 클라이언트가 2015년에 `rm -rf "$STEAMROOT/"*`로 사용자 파일을 지운 일이 바로 이 모양이다.

`set -u`(nounset)를 켜면 정의되지 않은 변수를 쓰는 순간 멈춘다. 더 좋은 건 꼭 필요한 값을 처음부터 검사하는 것이다.

```bash
#!/bin/bash
set -u
LOG_DIR=${1:?usage: clean.sh LOG_DIR}
echo "target: ${LOG_DIR:?}/*"
```

```text
clean2.sh: line 4: $1: unbound variable
exit=1
===
clean3.sh: line 3: 1: usage: clean.sh LOG_DIR
exit=1
```

첫 줄은 `set -u`만 켠 버전, 아래는 `${1:?메시지}`로 검사한 버전이다. `:?`는 비어 있어도 멈추기 때문에 `clean.sh ""`처럼 빈 문자열을 넘겨도 같은 메시지로 끝난다. `rm -rf "${LOG_DIR:?}/"*`처럼 위험한 줄에 한 번 더 붙여 두면 앞에서 누가 변수를 지워도 막힌다.

반대로 값이 없어도 되는 변수는 기본값을 준다. 콜론이 있으면 "없거나 비었을 때", 없으면 "없을 때만"이다. 세 변수로 확인했다(A는 정의 안 됨, B는 빈 문자열, C는 x).

```bash
unset A; B=""; C=x
for v in A B C; do
  printf '%s: [%s] [%s] [%s] [%s]\n' "$v" "${!v:-d}" "${!v-d}" "${!v:+alt}" "${!v+alt}"
done
```

```text
A: [d] [d] [] []
B: [d] [] [] [alt]
C: [x] [x] [alt] [alt]
```

칸 순서는 `:-`, `-`, `:+`, `+`이다. `${!v}`는 v에 든 이름의 변수를 읽는 간접 참조다. B 줄이 차이를 보여 준다. 빈 문자열은 `:-`에게는 "없음"이지만 `-`에게는 "있음"이다. `set -u`를 켠 스크립트에서 선택적인 환경 변수를 읽을 때는 `${DEBUG:-}`처럼 빈 기본값을 붙인다.

## 따옴표가 인자 개수를 정한다

따옴표 없이 쓴 `$f`는 값으로 바뀐 뒤 두 번 더 손을 탄다. 공백(정확히는 IFS의 문자)에서 잘리고(단어 분할), 잘린 조각에 `*`나 `?`가 있으면 파일 이름으로 펼쳐진다(글로빙). 받은 인자를 하나씩 찍는 `show` 함수로 확인했다. 디렉터리에는 `monthly report.csv`와 `a.csv`가 있다.

```bash
show() { echo "인자 $#개:"; for a in "$@"; do echo "  [$a]"; done; }
f="monthly report.csv"
show $f
show "$f"
pat="*.csv"
show $pat
show "$pat"
```

```text
인자 2개:
  [monthly]
  [report.csv]
인자 1개:
  [monthly report.csv]
인자 2개:
  [a.csv]
  [monthly report.csv]
인자 1개:
  [*.csv]
```

`cp $f backup/`이었다면 cp는 `monthly`와 `report.csv`라는 없는 파일 두 개를 찾는다. 반대로 `$pat`은 따옴표가 없어서 패턴으로 쓰였다. 패턴으로 쓰고 싶을 때만 따옴표를 뺀다. 아래 그림은 셸이 `cp $f backup/` 한 줄을 인자로 바꾸는 순서다.

받은 그대로 넘기는 건 `"$@"` 하나뿐이다. 래퍼 스크립트(`exec java ... "$@"`)나 Docker 엔트리포인트에서 이걸 틀리면 공백이 든 인자가 쪼개진다. `[ ]` 안에서도 따옴표가 필요하다. `v=""`일 때 `[ $v == "" ]`는 `[ == "" ]`가 되어 `[: ==: unary operator expected`를 낸다. `[[ ]]`는 bash 문법이라 안에서 단어 분할을 하지 않아서 이 오류가 없다. 스크립트가 bash 전용이라면 `[[ ]]`를 쓴다.

## 옵션 목록은 배열에 담는다

curl 옵션을 문자열 변수에 모아 두었다가 넘기는 코드는 흔하고, 거의 항상 틀린다.

```bash
opts="-H 'Content-Type: application/json' --retry 3"
show curl $opts

args=(-H "Content-Type: application/json" --retry 3)
[[ -n "${DEBUG:-}" ]] && args+=(-v)
show curl "${args[@]}"
echo "개수 ${#args[@]}, 첫 번째 [${args[0]}], 마지막 [${args[-1]}]"
```

```text
인자 6개:
  [curl]
  [-H]
  ['Content-Type:]
  [application/json']
  [--retry]
  [3]
인자 6개:
  [curl]
  [-H]
  [Content-Type: application/json]
  [--retry]
  [3]
  [-v]
개수 5, 첫 번째 [-H], 마지막 [-v]
```

문자열 안의 작은따옴표는 따옴표 역할을 하지 않는다. 변수를 펼친 결과에 따옴표 해석은 다시 일어나지 않아서, `'Content-Type:`이 따옴표를 글자로 단 채 잘렸다. 배열은 원소 하나가 인자 하나라서 이 문제가 없고, 조건에 따라 `+=`로 옵션을 붙이기도 쉽다. `"${args[@]}"`의 따옴표를 빼면 다시 쪼개지니 꼭 붙인다.

이름과 값을 짝으로 두려면 연관 배열(`declare -A port=([web]=80 [api]=8080)`, bash 4부터)을 쓴다. 키 순서는 보장되지 않아서 순서가 필요하면 `sort`를 거친다.

## 함수는 stdout으로 값을, stderr로 로그를

bash 함수의 `return`은 종료 코드(0~255)만 돌려준다. 문자열 값은 표준 출력으로 내보내고 호출하는 쪽이 `$(...)`로 받는다. 그래서 함수 안에서 로그를 표준 출력에 찍으면 값에 섞인다.

```bash
f() { echo "log: starting" ; echo "1.4.2"; }; v=$(f); echo "v=[$v]"
f() { echo "log: starting" >&2; echo "1.4.2"; }; v=$(f); echo "v=[$v]"
```

```text
v=[log: starting
1.4.2]
log: starting
v=[1.4.2]
```

두 번째처럼 로그는 `>&2`로 표준 에러에 보낸다. 그러면 값은 깨끗하게 받고, 로그는 터미널이나 cron 메일, journald에 그대로 남는다. 함수 안의 변수는 `local`로 묶는다. 안 그러면 함수 안의 `i`가 밖의 반복문 `i`를 덮어쓴다. 앞에서 본 대로 `local x=$(cmd)`는 실패를 가리니 선언과 대입을 나눈다. 세 통로를 나눠 쓰는 그림이다.

## trap으로 뒷정리를 맡긴다

임시 파일, 잠금, 띄워 둔 백그라운드 프로세스는 스크립트가 어떻게 끝나든 정리해야 한다. 성공했을 때만 맨 끝에서 지우면, 중간에 실패하거나 누가 Ctrl+C를 누를 때 남는다. `trap '명령' EXIT`는 스크립트가 끝날 때 무조건 그 명령을 돌린다. SIGTERM을 받았을 때 어떻게 되는지 두 가지로 확인했다.

```bash
#!/bin/bash
# t1.sh: EXIT trap만 건다
tmp=$(mktemp -p .)
trap 'echo "EXIT trap: cleaning $tmp" >&2; rm -f -- "$tmp"' EXIT
echo "pid $$, tmp $tmp"
sleep 5
```

```bash
# 백그라운드로 띄우고 0.5초 뒤 SIGTERM을 보낸다
bash t1.sh & P=$!; sleep 0.5; kill -TERM $P; wait $P; echo "exit=$?"
# 부모가 PID 1로 바뀐 sleep을 찾는다
ps -o pid=,ppid=,cmd= -C sleep | awk '$2 == 1'
```

```text
pid 32757, tmp ./tmp.iQoaucoovx
EXIT trap: cleaning ./tmp.iQoaucoovx
exit=143
32760     1 sleep 5
```

bash는 SIGTERM으로 죽을 때도 EXIT trap을 돌려서 임시 파일은 지웠다. 그런데 `sleep 5`는 부모가 사라진 채 PID 1 밑에서 계속 돈다. 스크립트가 띄운 자식은 스크립트와 함께 죽지 않는다. systemd 서비스라면 cgroup 전체를 정리해 주지만([systemd 글](/posts/linux-systemd-systemctl)), cron이나 손으로 띄운 스크립트에서는 남는다.

이번엔 TERM에도 trap을 걸고, 자식을 앞에서 기다리는 경우와 `& wait`로 기다리는 경우를 비교했다.

```bash
#!/bin/bash
# t2.sh: TERM을 잡아서 정리 후 143으로 끝낸다
tmp=$(mktemp -p .)
trap 'echo "EXIT trap: cleaning $tmp" >&2; rm -f -- "$tmp"' EXIT
trap 'echo "got SIGTERM" >&2; exit 143' TERM
echo "pid $$, tmp $tmp"
sleep 5 & wait $!       # t3.sh는 이 줄이 그냥 sleep 5
```

```bash
for s in t2.sh t3.sh; do
  echo "== $s"
  start=$(date +%s%N)
  bash $s & P=$!; sleep 0.5; kill -TERM $P; wait $P
  echo "exit=$? after $(( ($(date +%s%N) - start) / 1000000 ))ms"
done
```

```text
== t2.sh
pid 32572, tmp ./tmp.VvywWdznYP
got SIGTERM
EXIT trap: cleaning ./tmp.VvywWdznYP
exit=143 after 510ms
== t3.sh
pid 32580, tmp ./tmp.qEjqZcfZEL
got SIGTERM
EXIT trap: cleaning ./tmp.qEjqZcfZEL
exit=143 after 5012ms
```

같은 trap인데 t3는 5초 뒤에야 반응했다. bash는 앞에서 돌고 있는 명령이 끝나기 전에는 trap을 돌리지 않는다. `wait`는 시그널이 오면 바로 돌아오기 때문에 t2는 0.51초 만에 정리했다. 컨테이너의 엔트리포인트 스크립트가 `docker stop`에 늦게 반응하다가 10초 뒤 SIGKILL로 죽는 흔한 이유가 이거다. 엔트리포인트라면 마지막 줄을 `exec 앱 "$@"`로 써서 셸을 앱으로 바꿔치기하면 시그널이 앱에 바로 간다. 아래 그림은 t2의 흐름이다.

`ERR` trap은 실패한 명령과 줄 번호를 알려 준다. 함수 안의 실패까지 잡으려면 `set -E`(errtrace)가 필요하다.

```bash
#!/bin/bash
set -Eeuo pipefail
trap 'echo "ERR: line $LINENO: \"$BASH_COMMAND\" exited $?" >&2' ERR
load_config() {
  grep -q '^db_host=' ./app.conf
}
echo "start"
load_config
echo "unreachable"
```

```text
start
ERR: line 5: "grep -q '^db_host=' ./app.conf" exited 1
exit=1
=== without -E
start
exit=1
```

`-E`를 빼면 함수 안의 실패에서 trap이 돌지 않아서, 스크립트는 아무 말 없이 1로 끝났다. 새벽에 실패한 스크립트를 아침에 볼 때 이 한 줄이 있고 없고의 차이가 크다.

```bash
#!/bin/bash
# PostgreSQL DB 하나를 gzip으로 백업하고 오래된 백업을 지운다
set -Eeuo pipefail
shopt -s inherit_errexit

readonly DB="${1:?usage: pg-backup.sh DBNAME}"
readonly BACKUP_DIR="${BACKUP_DIR:-/var/backups/pg}"
readonly KEEP_DAYS="${KEEP_DAYS:-7}"

log() { printf '%s %-5s %s\n' "$(date +%T)" "$1" "${*:2}" >&2; }
die() { log ERROR "$*"; exit 1; }
trap 'log ERROR "line $LINENO: \"$BASH_COMMAND\" exited $?"' ERR

mkdir -p -- "$BACKUP_DIR"

# 같은 백업이 두 번 겹쳐 돌지 않게 잠근다 (fd 9를 잠금 파일에 연다)
exec 9>"$BACKUP_DIR/.lock"
flock -n 9 || die "another backup is running"

# 같은 디렉터리에 임시 파일로 쓰고, 끝까지 성공하면 이름을 바꾼다
tmp=$(mktemp -- "$BACKUP_DIR/.${DB}.XXXXXX")
trap 'rm -f -- "$tmp"' EXIT

out="$BACKUP_DIR/${DB}-$(date +%F).sql.gz"
log INFO "dump $DB -> $out"
runuser -u postgres -- pg_dump --no-owner "$DB" | gzip > "$tmp"
mv -- "$tmp" "$out"
log INFO "done, $(stat -c %s -- "$out") bytes"

find "$BACKUP_DIR" -maxdepth 1 -name "${DB}-*.sql.gz" -mtime +"$KEEP_DAYS" -print -delete |
  while IFS= read -r old; do log INFO "removed $old"; done
```

세 가지 상황에서 돌렸다. 정상 백업(10일 전 백업 하나가 보관 기간을 넘겨 있다), 없는 DB, 그리고 다른 프로세스가 잠금을 쥐고 있을 때다. `runuser`를 쓰니 root로 돌린다.

```bash

echo "== no db";   ./pg-backup.sh lx1_nope; echo "exit=$?"
ls -lA bk
echo "== locked";  (flock 9; sleep 2) 9>bk/.lock & sleep 0.3
./pg-backup.sh lx1_shop; echo "exit=$?"; wait
```


실패했을 때 디렉터리에 반쪽짜리 파일이 남지 않았다. EXIT trap이 임시 파일을 지웠고, 이름을 바꾸는 `mv`까지 가지 못했으니 `lx1_nope-...sql.gz`는 생기지도 않았다. 같은 파일 시스템 안의 `mv`는 원자적이라서, 다른 프로그램은 완성된 파일이나 아무것도 없는 상태만 본다. 덤으로 `mktemp`가 만든 파일은 권한이 600이라 백업 파일도 `-rw-------`로 남았다. DB 덤프를 아무나 읽을 수 없게 된 건 좋은 부작용이다.

ERR 로그에 하나 볼 게 있다. 실패한 건 `pg_dump`인데 `BASH_COMMAND`는 파이프의 마지막 조각 `gzip > "$tmp"`를 가리킨다. pipefail로 파이프 전체가 1이 됐지만, 누가 실패했는지는 그 직후의 `PIPESTATUS`를 봐야 안다. 잠금은 `flock -n`이 이미 잠긴 걸 보고 바로 포기한 것이다. 겹치는 실행을 막는 다른 방법들은 [크론 잡 글](/posts/cron-jobs)에 있다. cron에서 돌릴 때는 환경이 다르다는 걸 기억한다. cron의 PATH는 `/usr/bin:/bin` 정도라서 `/usr/local/bin`의 명령을 못 찾고 127로 끝나곤 한다. 스크립트 안에서 PATH를 정하거나 명령을 절대 경로로 쓴다.

## shellcheck가 먼저 읽게 한다

여기까지의 실수 대부분은 shellcheck가 실행 전에 찾아 준다. Ubuntu에서는 `sudo apt install shellcheck`로 설치한다. 일부러 흔한 실수를 넣은 배포 스크립트를 읽혔다.

```bash
#!/bin/bash
release=$1
cd /srv/app/releases/$release
for f in $(ls *.tar.gz); do
  tar xzf $f
done
local_ver=$(cat VERSION)
if [ $local_ver == "" ]; then
  echo "no version"
fi
echo "deployed `date`"
```

```bash
shellcheck deploy.sh
```

```text
In deploy.sh line 3:
cd /srv/app/releases/$release
^---------------------------^ SC2164 (warning): Use 'cd ... || exit' or 'cd ... || return' in case cd fails.
                     ^------^ SC2086 (info): Double quote to prevent globbing and word splitting.

Did you mean: 
cd /srv/app/releases/"$release" || exit


In deploy.sh line 4:
for f in $(ls *.tar.gz); do
         ^------------^ SC2045 (error): Iterating over ls output is fragile. Use globs.
              ^-- SC2035 (info): Use ./*glob* or -- *glob* so names with dashes won't become options.
```

출력은 앞의 두 곳만 옮겼다. 나머지 줄의 `$f`, `$local_ver`(SC2086)와 백틱(SC2006)도 짚어 준다(Ubuntu 24.04의 shellcheck 0.9.0). SC2164가 제일 무섭다. `cd`가 실패하면 스크립트는 원래 있던 디렉터리에서 다음 줄을 계속 돈다. 그 다음 줄이 지우는 명령이라면 엉뚱한 디렉터리가 지워진다. `$(ls ...)`를 반복하면 공백이 든 파일 이름이 쪼개지니 `for f in ./*.tar.gz`처럼 글롭을 그대로 쓴다. SC2035는 `-rf.tar.gz` 같은 이름이 옵션으로 읽히는 걸 막으려고 `./`를 붙이라는 뜻이다. 경고를 일부러 무시해야 하는 줄은 그 줄 위에 `# shellcheck disable=SC2086`처럼 이유와 함께 적는다. CI에서 `shellcheck **/*.sh`를 돌리고, 저장소에 `.shellcheckrc`를 두면 팀 규칙을 맞출 수 있다. 앞의 백업 스크립트는 경고 없이 통과했다.

## 스크립트를 따라가 보는 법

어디서 엇나가는지 모를 때는 `set -x`로 실행되는 명령을 펼친 모양 그대로 찍는다. `PS4`를 바꾸면 각 줄에 파일, 줄 번호, 함수 이름이 붙는다.

```bash
#!/bin/bash
set -euo pipefail
PS4='+ ${BASH_SOURCE##*/}:${LINENO}:${FUNCNAME[0]:-main}: '
[[ "${TRACE:-}" == 1 ]] && set -x
name=${1:-world}
greet() { printf 'hello %s\n' "$1"; }
greet "$name"
```

```text
$ TRACE=1 bash x.sh "matt kim"
+ x.sh:5:main: name='matt kim'
+ x.sh:7:main: greet 'matt kim'
+ x.sh:6:greet: printf 'hello %s\n' 'matt kim'
hello matt kim
```

`name='matt kim'`처럼 따옴표까지 보여 주기 때문에 인자가 쪼개졌는지 바로 보인다. 처음에는 `PS4=... bash -x x.sh`처럼 환경 변수로 넘겼는데 root로 돌리니 적용되지 않았고, 일반 사용자로는 적용됐다. 그래서 스크립트 안에서 PS4를 정한다. `set -x`는 비밀번호나 토큰이 든 변수도 그대로 찍으니, 비밀을 다루는 구간은 `set +x`로 끈다.

## bash를 그만 써야 할 때

bash는 명령을 잇고, 파일을 옮기고, 종료 코드로 흐름을 가르는 데 맞는 도구다. 스크립트가 100줄을 넘어가면서 JSON을 파싱하고, 재시도와 타임아웃을 계산하고, 자료 구조가 연관 배열 몇 개를 넘으면 Python 같은 언어로 옮길 때다. `jq`로 JSON 몇 칸을 읽는 정도는 괜찮지만, 응답을 고쳐서 다시 보내기 시작하면 따옴표 지옥이 된다. 같은 기준으로 Ansible이나 [IaC 도구](/posts/iac-basics)가 이미 하는 일(패키지 설치, 설정 파일 배포)을 bash로 다시 만들지 않는다. `#!/bin/sh`로 쓴 스크립트는 Ubuntu에서 bash가 아니라 dash로 돈다. 배열, `[[ ]]`, `pipefail`, `${var:offset}` 같은 bash 문법이 없다. bash 문법을 쓰면 첫 줄을 `#!/bin/bash`로 쓰고, `sh script.sh`가 아니라 `bash script.sh`나 `./script.sh`로 돌린다. Ubuntu 24.04의 dash 0.5.12에서 `set -o pipefail`을 치면 `dash: 1: set: Illegal option -o pipefail`로 실패한다.

## 실패가 들리게 만드는 일

bash 스크립트를 믿을 만하게 만드는 건 결국 실패를 숨기지 않는 일이다. 종료 코드를 정확히 남기고, `set -Eeuo pipefail`로 묻힌 실패를 드러내고, 그게 물러나는 자리(`if` 안의 함수, `local x=$(...)`, `((i++))`, `grep`의 1)를 알아 둔다. 변수는 따옴표로 감싸고 목록은 배열에 담고, 정리는 trap에 맡기고, 결과물은 임시 파일에 쓴 뒤 `mv`로 바꾼다. 마지막으로 shellcheck를 CI에 건다.

## 면접에서 나올 만한 질문

### set -euo pipefail은 각각 무엇을 하나?

`-e`는 검사받지 않는 명령이 실패하면 스크립트를 끝내고, `-u`는 정의되지 않은 변수를 쓰면 끝내고, `-o pipefail`은 파이프 중간 명령의 실패가 파이프 전체의 종료 코드에 드러나게 한다. 셋이 없으면 bash는 실패를 만나도 다음 줄로 넘어가서 `pg_dump | gzip` 같은 줄이 실패해도 0으로 끝난다. 함수 안까지 ERR trap을 쓰려면 `-E`도 붙인다.

### set -e를 켰는데도 실패에서 멈추지 않는 경우는?

종료 코드를 누가 검사하고 있는 자리다. `if`, `while`의 조건, `&&`와 `||`의 왼쪽, `!` 뒤에서는 발동하지 않고, 그 자리에서 부른 함수 안의 실패까지 모두 무시된다. `local x=$(cmd)`는 `local`의 성공이 안쪽 실패를 가린다. 명령 치환 안은 `inherit_errexit`를 켜야 멈춘다. 반대로 `((i++))`가 0을 내거나 `grep`이 못 찾고 1을 내면 오류가 아닌데도 조용히 끝난다.

### 변수를 따옴표로 감싸야 하는 이유는?

따옴표가 없으면 펼친 값이 IFS 공백에서 잘리고 글롭 문자가 파일 이름으로 펼쳐지기 때문이다. `f="monthly report.csv"`일 때 `cp $f`는 인자 두 개를 받는다. 값이 비면 인자 자체가 사라져서 `[ $v == "" ]`가 문법 오류가 되고, `rm -rf $DIR/*`가 `/*`가 된다. 패턴으로 쓰려는 경우가 아니면 항상 감싼다.

### 명령 옵션을 문자열 변수가 아니라 배열로 다루는 이유는?

변수를 펼친 결과에서는 따옴표가 다시 해석되지 않아서, 문자열 안의 따옴표가 글자로 남은 채 공백에서 잘리기 때문이다. 배열은 원소 하나가 인자 하나로 넘어가고, `args+=(-v)`처럼 조건부로 붙이기도 쉽다. 넘길 때는 `"${args[@]}"`로 감싼다.

### trap EXIT로 정리하는 이유와, TERM을 받았는데 정리가 늦는 경우는?

EXIT trap은 정상 종료, 실패, `exit`, 대부분의 시그널 종료에서 모두 돌아서 정리 코드를 한 곳에만 쓰면 된다. 다만 bash는 앞에서 돌고 있는 명령이 끝나야 trap을 실행해서, `sleep 5`를 기다리는 중에 받은 TERM은 5초 뒤에 처리됐다. 자식을 `&`로 띄우고 `wait`로 기다리거나, 엔트리포인트라면 `exec`로 셸을 앱으로 바꾼다. 스크립트가 죽어도 자식은 남을 수 있다는 점도 함께 본다.

### 백업 파일이 반쪽으로 남지 않게 하려면?

같은 디렉터리에 `mktemp`로 임시 파일을 만들어 쓰고, 끝까지 성공했을 때만 `mv`로 최종 이름으로 바꾼다. 같은 파일 시스템 안의 이름 바꾸기는 원자적이라 다른 프로그램은 완성된 파일만 본다. 실패하면 EXIT trap이 임시 파일을 지우고, `pipefail` 덕분에 `mv`까지 가지 않는다. `>`로 바로 쓰면 파이프가 시작되기 전에 파일이 생겨서 실패해도 빈 파일이 남는다.

### shellcheck는 어떤 실수를 잡아 주나?

따옴표 없는 변수(SC2086), 실패를 검사하지 않는 `cd`(SC2164), `ls` 출력 반복(SC2045), `-`로 시작하는 파일 이름이 옵션으로 읽히는 글롭(SC2035) 같은, 실행해 보기 전에는 드러나지 않는 실수를 정적으로 찾는다. CI에 걸어 두면 리뷰에서 사람이 볼 필요가 없어진다. 일부러 어기는 줄은 `# shellcheck disable=코드`와 이유를 남긴다.
