<EasyIntro>
  Helm으로 프로그램을 새 버전으로 바꾸는 일은 한 번에 끝나는 게 아니라 여러 단계를 거친다. 먼저 새 번호의 기록을 예약하고, 준비 작업을 돌리고, 바뀐 부분만 고치고, 프로그램이 제대로 뜨는지 기다린 뒤, 마지막에 성공이나 실패를 적는다. 어느 단계에서 멈추느냐에 따라 남는 흔적이 다르다.

  이 기록은 일기장과 같다. 작업을 시작하면 오늘 칸에 진행 중이라고 먼저 적어 두는데, 그 도중에 프로그램이 강제로 꺼지면 진행 중이라는 글자가 지워지지 않고 남는다. 다음 사람은 그 글자를 보고 누가 아직 작업 중이라고 착각해 손을 대지 않는다. 그럴 때는 마지막으로 성공한 칸으로 되돌리면 풀린다.

  이걸 알면 배포가 꼬였을 때 기록부터 펼쳐 보게 된다. 급할 때 클러스터에서 손으로 고친 값은 다음 배포에 덮여 사라진다는 것도 함께 기억해야 한다.
</EasyIntro>

CI 배포 단계가 네트워크 끊김으로 중간에 죽었다. 다시 돌렸더니 이번에는 이런 메시지와 함께 바로 실패한다.

```text
Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress
```

아무도 배포하고 있지 않은데 무슨 작업이 진행 중이라는 걸까. `helm list`를 쳐 보면 릴리스가 목록에서 아예 사라져 있다. 이 상황은 Helm이 릴리스 상태를 어떻게 기록하는지 알면 1분 안에 풀린다. 이 글은 업그레이드 한 번에 Helm이 무슨 순서로 일하는지, 클러스터에서 손으로 고친 값은 어떻게 되는지, 훅과 CRD가 왜 따로 노는지, 그리고 업그레이드가 꼬였을 때 상태별로 푸는 법을 따라간다.

릴리스와 리비전이라는 말은 [Helm 기본 글](/posts/helm-basics)에서 정리했다. 출력은 Helm 3.16과 kwok 실습 클러스터(Kubernetes 1.30)에서 받았다. kwok는 노드와 컨테이너를 흉내만 내지만 스케줄러와 컨트롤러는 진짜라서, Pod가 `Pending`에 걸리는 상황이나 Job의 성공·실패는 실제와 같다.

## 업그레이드 한 번에 일어나는 일

CI에서 많이 쓰는 형태는 이렇다.

```bash
# 없으면 설치, 있으면 업그레이드. 준비될 때까지 기다리고 실패하면 되돌린다
helm upgrade --install shop-api ./shop-api -n shop-prod \
  -f values-prod.yaml --set-string image.tag="$GIT_SHA" \
  --atomic --timeout 5m
```

`--install`은 릴리스가 없으면 설치로 바꿔 준다. `--wait`는 리소스를 적용한 뒤 Pod가 Ready가 될 때까지 기다린다. Deployment라면 원하는 레플리카에서 `maxUnavailable`을 뺀 만큼은 준비돼야 한다. Job까지 끝나길 기다리려면 `--wait-for-jobs`를 더한다. `--timeout`은 기다리는 시간(기본 5분)이고, `--atomic`은 실패하면 직전 성공 리비전으로 자동 롤백한다. `--atomic`을 주면 `--wait`는 저절로 켜진다. Helm 4에서는 `--atomic`의 이름이 `--rollback-on-failure`로 바뀌었으니 버전을 확인한다.

실제로 해 보자. 맞는 노드가 없는 `nodeSelector`를 넣어 Pod가 뜰 수 없게 만들었다.

```bash

helm upgrade shop-api ./shop-api -n shop-prod --set replicaCount=2 \
  --set nodeSelector.disk=nvme --set image.tag=1.27.2 --atomic --timeout 30s

# 리비전 기록과 실제 이미지를 확인한다
helm history shop-api -n shop-prod
kubectl get deploy shop-api -n shop-prod -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
```

`--atomic` 없이 `--wait`만 줬다면 리비전은 failed로 남고 클러스터는 반쯤 바뀐 채 그대로다. 옛 Pod 두 개는 계속 돌고, 새 Pod 하나는 Pending이다.


Deployment의 롤링 업데이트가 옛 Pod를 남겨 두니 당장 장애는 아니다. 하지만 다음 배포 전에 누군가 `helm rollback`으로 정리해야 한다. `--atomic`을 쓸지는 팀의 선택이다. 자동으로 되돌아가니 편하지만, 실패한 상태를 들여다볼 틈 없이 사라진다. 원인을 보려면 `helm history`의 설명과 이벤트를 롤백 전에 남겨 두도록 CI 로그에 찍어 두는 게 좋다. Pod가 왜 Ready가 안 되는지 보는 순서는 [프로브 글](/posts/k8s-pod-probes)과 [Pod의 일생 글](/posts/k8s-pod-lifecycle)에 있다.

## 롤백도 새 리비전이다

손으로 롤백할 때는 돌아갈 리비전 번호를 준다. 번호를 빼면 바로 전 리비전으로 간다.

```bash
# 리비전 4의 내용으로 되돌린다
helm rollback shop-api 4 -n shop-prod

# 최근 세 개만 본다
helm history shop-api -n shop-prod --max 3
```

```text
Rollback was a success! Happy Helming!
REVISION	UPDATED                 	STATUS    	CHART         	APP VERSION	DESCRIPTION                                         
4       	Sun Oct 18 23:44:50 2026	superseded	shop-api-0.1.0	1.16.0     	Rollback to 2                                       
5       	Sun Oct 18 23:44:52 2026	failed    	shop-api-0.1.0	1.16.0     	Upgrade "shop-api" failed: context deadline exceeded
6       	Sun Oct 18 23:45:21 2026	deployed  	shop-api-0.1.0	1.16.0     	Rollback to 4                                       
```

롤백은 그 리비전의 매니페스트를 다시 적용하는 업그레이드다. 몇 가지는 되돌아가지 않는다. 훅으로 돌린 DB 마이그레이션은 되돌아가지 않는다. 컬럼을 지운 마이그레이션 뒤에 옛 앱으로 롤백하면 옛 앱이 없는 컬럼을 찾는다. 그래서 마이그레이션은 옛 버전과 새 버전이 함께 돌 수 있게(컬럼 추가 먼저, 삭제는 다음 배포에) 나눠 쓴다. PVC 안의 데이터, 외부 시스템에 보낸 요청도 그대로다. 그리고 `--history-max`(기본 10)보다 오래된 리비전은 지워져서 돌아갈 수 없다.

## 손으로 고친 값은 다음 배포에 어떻게 되나

장애 중에 `kubectl scale`로 레플리카를 6으로 늘리고, 팀 표시용 어노테이션도 하나 달았다. 그 뒤 원래 values 그대로 업그레이드하면 어떻게 될까.

```bash
# 클러스터에서 직접 바꾼다
kubectl scale deploy shop-api -n shop-prod --replicas=6
kubectl annotate deploy shop-api -n shop-prod team=payments

# 차트 값은 그대로 replicaCount=2로 업그레이드한다
helm upgrade shop-api ./shop-api -n shop-prod --set replicaCount=2

# 레플리카와 어노테이션을 본다
kubectl get deploy shop-api -n shop-prod -o jsonpath='{.spec.replicas} {.metadata.annotations.team}{"\n"}'
```

```text
2 payments
```

레플리카는 2로 돌아갔고 어노테이션은 남았다. Helm 3는 업그레이드할 때 세 가지를 비교한다. 지난 리비전의 매니페스트, 클러스터의 지금 상태, 새로 렌더링한 매니페스트. 이걸 three-way merge라고 부른다. 규칙은 이렇다. 새 매니페스트에 적힌 필드는 그 값으로 맞춘다. 지난 매니페스트에 있었는데 새 매니페스트에서 빠진 필드는 지운다. 어느 매니페스트에도 없고 클러스터에만 있는 필드는 건드리지 않는다. 아래에서 필드 하나씩 판단을 따라가 보자.

이 규칙에서 실무 교훈 두 개가 나온다. 하나, 급할 때 `kubectl`로 고친 값은 values에도 반영해야 다음 배포 뒤에 남는다. 아니면 새벽에 늘린 레플리카가 아침 배포에 조용히 2로 돌아간다. HPA를 쓰는 Deployment라면 차트가 `replicas`를 아예 렌더링하지 않게 해야 한다. `helm create`의 템플릿에 `{{- if not .Values.autoscaling.enabled }}`가 감싸고 있는 이유다. 둘, 서비스 메시가 넣는 사이드카나 다른 컨트롤러가 붙이는 어노테이션처럼 차트가 모르는 필드는 Helm이 지우지 않는다. Helm 2는 지난 매니페스트와 새 매니페스트만 비교해서, 클러스터에서 바뀐 값을 보지 못했다.

## 바꾸기 전에 diff로 보기

업그레이드가 무엇을 바꿀지 미리 보는 도구가 helm-diff 플러그인이다.

```bash
# 플러그인 설치
helm plugin install https://github.com/databus23/helm-diff --version v3.9.14

# 이번 업그레이드가 바꿀 내용을 본다 (앞뒤 두 줄씩만)
helm diff upgrade shop-api ./shop-api -n shop-prod \
  --set replicaCount=2 --set image.tag=1.27.3 -C 2
```


여기에 함정이 있다. 기본 diff는 지난 리비전의 매니페스트와 새 매니페스트만 비교한다. 위 출력은 누군가 `kubectl scale`로 레플리카를 5로 바꿔 둔 상태에서 받은 것인데, 레플리카 이야기가 없다. 클러스터의 지금 상태와 비교하려면 `--three-way-merge`를 준다.

```bash
# 클러스터의 현재 상태까지 넣어 비교한다
helm diff upgrade shop-api ./shop-api -n shop-prod \
  --set replicaCount=2 --set image.tag=1.27.3 -C 2 --three-way-merge
```

```text

...

+   replicas: 2
    revisionHistoryLimit: 10

...

        containers:
-       - image: nginx:1.27.2
```

## 훅은 릴리스 밖에서 돈다

훅은 설치나 업그레이드의 특정 시점에 따로 실행되는 리소스다. 템플릿에 어노테이션을 붙여 만든다. 가장 흔한 쓰임은 업그레이드 전 DB 마이그레이션 Job이다.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ include "shop-api.fullname" . }}-migrate
  annotations:
    "helm.sh/hook": pre-install,pre-upgrade
    "helm.sh/hook-weight": "0"
    "helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded
spec:
  backoffLimit: 0
  activeDeadlineSeconds: 300
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          command: ["./migrate", "up"]
```

## another operation is in progress

글 처음의 상황으로 돌아가자. Helm은 작업을 시작할 때 새 리비전을 `pending-install`, `pending-upgrade`, `pending-rollback` 중 하나로 먼저 기록하고, 끝나면 `deployed`나 `failed`로 바꾼다. 작업 도중에 프로세스가 죽으면(CI 러너가 취소되거나, 노트북 덮개를 닫거나, `kill -9`) 상태를 바꿀 사람이 없어서 pending이 그대로 남는다. 다음 Helm 작업은 이 pending을 보고 누가 작업 중이라고 판단해 거절한다.

아래 그림은 릴리스 리비전이 거치는 상태들이다. 점선이 프로세스가 죽었을 때 멈추는 자리다.

`helm list`는 기본으로 deployed와 failed만 보여 줘서 릴리스가 목록에서 사라진 것처럼 보인다. `--pending`이나 `-a`를 붙여야 보인다. 리비전 7이 `pending-upgrade`로 남아 있고, 이 상태에서 업그레이드하면 글 처음의 오류가 난다.

먼저 정말로 다른 작업이 돌고 있지 않은지 확인한다. CI 파이프라인 두 개가 동시에 돌고 있다면 기다리는 게 맞다. 아무도 없다면 상태에 따라 푼다.

`pending-upgrade`나 `pending-rollback`이면 마지막 `deployed` 리비전으로 롤백한다. 롤백은 pending 상태를 무시하고 진행되며, 새 리비전으로 정상 상태를 만든다.

```bash
# 마지막으로 정상이던 리비전 6으로 되돌린다
helm rollback shop-api 6 -n shop-prod
helm history shop-api -n shop-prod --max 3
```

```text

REVISION	UPDATED                 	STATUS         	CHART         	APP VERSION	DESCRIPTION      
6       	Sun Oct 18 23:45:21 2026	superseded     	shop-api-0.1.0	1.16.0     	Rollback to 4    
7       	Sun Oct 18 23:45:27 2026	pending-upgrade	shop-api-0.1.0	1.16.0     	Preparing upgrade
8       	Sun Oct 18 23:45:38 2026	deployed       	shop-api-0.1.0	1.16.0     	Rollback to 6    
```

7은 pending으로 기록에 남지만 이제 최신이 아니라서 다음 업그레이드를 막지 않는다. 첫 설치가 중간에 죽은 `pending-install`은 돌아갈 리비전이 없다.

```bash
# 첫 설치가 끊긴 릴리스는 롤백할 곳이 없다
helm rollback shop-api -n shop-new
```

```text

```

이때는 `helm uninstall`로 반쯤 만들어진 릴리스를 지우고 다시 설치한다. 운영 데이터가 없는 첫 설치라서 가능한 방법이다.

인터넷에서 자주 보이는 다른 방법은 pending 리비전의 Secret을 직접 지우는 것이다.

<Callout kind="warning" title="릴리스 Secret을 지우기 전에">
  `kubectl delete secret sh.helm.release.v1.shop-api.v7 -n shop-prod`처럼 pending 리비전의 Secret만 지워도 잠금은 풀린다. 하지만 이건 Helm의 기록을 손으로 고치는 일이라, 번호를 잘못 보고 deployed 리비전을 지우면 Helm은 릴리스가 없다고 판단하고 다음 install에서 모든 리소스가 이미 있다는 오류를 낸다. 지우기 전에 `kubectl get secret -n shop-prod -l owner=helm,name=shop-api --show-labels`로 status 라벨을 확인하고, `kubectl get secret 이름 -o yaml > backup.yaml`로 백업한다. 되돌릴 때는 백업을 `kubectl apply -f backup.yaml`로 다시 넣는다. 가능하면 `helm rollback`을 먼저 쓴다.
</Callout>

재발을 막으려면 원인을 없앤다. CI에서 같은 릴리스로 가는 배포가 겹치지 않게 동시 실행을 막고(파이프라인의 동시성 그룹), 러너가 취소될 때 Helm에 SIGTERM이 전달되게 한다. `--timeout`을 CI 작업 제한 시간보다 짧게 잡으면, CI가 Helm을 강제로 죽이기 전에 Helm이 스스로 실패를 기록하고 끝낸다.

## 바꿀 수 없는 필드를 바꾸면

차트를 고치다 셀렉터 라벨에 `app.kubernetes.io/component: api`를 추가했다. 업그레이드하면 이렇게 된다.

```text
Error: UPGRADE FAILED: cannot patch "shop-api" with kind Deployment: Deployment.apps "shop-api" is invalid: spec.selector: Invalid value: v1.LabelSelector{MatchLabels:map[string]string{"app.kubernetes.io/component":"api", "app.kubernetes.io/instance":"shop-api", "app.kubernetes.io/name":"shop-api"}, MatchExpressions:[]v1.LabelSelectorRequirement(nil)}: field is immutable
```

Deployment의 `spec.selector`, StatefulSet의 `volumeClaimTemplates`, Service의 `clusterIP`, Job의 `spec.template`처럼 만든 뒤 바꿀 수 없는 필드가 있다. 셀렉터가 바뀌면 지금 Pod들이 누구 소속인지가 흔들리니 쿠버네티스가 막는다.

진짜 문제는 이 오류가 반쯤 적용된 상태를 남긴다는 것이다. Helm은 리소스를 종류 순서대로 적용하는데 Service가 Deployment보다 먼저다. Service의 셀렉터는 바꿀 수 있는 필드라서 새 라벨로 먼저 바뀌고, Deployment에서 실패했다.

```bash
# 실패한 업그레이드 뒤 Service가 가리키는 Pod를 본다
kubectl get svc shop-api -n shop-prod -o jsonpath='{.spec.selector}{"\n"}'
kubectl get endpoints shop-api -n shop-prod
```

```text
{"app.kubernetes.io/component":"api","app.kubernetes.io/instance":"shop-api","app.kubernetes.io/name":"shop-api"}
NAME       ENDPOINTS   AGE
shop-api   <none>      116s
```

Service가 새 라벨을 찾는데 Pod에는 아직 그 라벨이 없으니 엔드포인트가 비었다. 이 Service로 오는 요청은 모두 실패한다. [Ingress](/posts/kubernetes-ingress) 앞에서는 503으로 보인다. `--atomic`이었다면 바로 되돌아갔을 것이고, 아니라면 즉시 롤백한다.

```bash
# 마지막 정상 리비전으로 되돌리고 엔드포인트가 돌아왔는지 본다
helm rollback shop-api 9 -n shop-prod
kubectl get endpoints shop-api -n shop-prod
```

```text
Rollback was a success! Happy Helming!
NAME       ENDPOINTS                 AGE
shop-api   10.0.0.4:80,10.0.1.4:80   2m1s
```

`--force`로 밀어붙여도 소용없다. Helm 3의 `--force`는 패치 대신 객체를 통째로 교체(replace)하는데, 교체도 바꿀 수 없는 필드 검사를 똑같이 받는다.

```text
Error: UPGRADE FAILED: failed to replace object: Deployment.apps "shop-api" is invalid: spec.selector: Invalid value: ...
```

셀렉터를 꼭 바꿔야 한다면 Deployment를 지우고 다시 만들어야 한다. Pod까지 지우지 않으려면 `--cascade=orphan`으로 Deployment만 지운다.

```bash
# Deployment만 지우고 ReplicaSet과 Pod는 남긴다
kubectl delete deploy shop-api -n shop-prod --cascade=orphan

# 새 셀렉터로 Deployment를 다시 만든다
helm upgrade shop-api ./shop-api -n shop-prod -f values-prod.yaml --wait --timeout 5m

# 옛 ReplicaSet과 새 ReplicaSet을 본다
kubectl get rs -n shop-prod
```

```text
deployment.apps "shop-api" deleted
Release "shop-api" has been upgraded. Happy Helming!
NAME                  DESIRED   CURRENT   READY   AGE
shop-api-848cdf4675   2         2         2       2s
shop-api-99877487d    2         2         2       23s
```

새 ReplicaSet(`848cdf4675`)의 Pod가 Ready가 되고 Service가 새 라벨로 그쪽을 찾으면, 주인을 잃은 옛 ReplicaSet(`99877487d`)을 `kubectl delete rs`로 지운다. 여기까지가 번거로우니 처음부터 셀렉터 라벨에는 릴리스 이름과 앱 이름처럼 절대 안 바뀌는 값만 넣는다. 버전이나 차트 버전을 넣으면 매 배포가 이 오류다.

## CRD는 처음 한 번만 설치된다

오퍼레이터를 담은 차트는 CustomResourceDefinition(CRD)을 함께 배포한다. 차트의 `crds/` 디렉터리에 둔 CRD는 특별 취급을 받는다. 템플릿이 아니라서 값을 넣을 수 없고, 다른 리소스보다 먼저 설치되며, 업그레이드와 삭제 때는 건드리지 않는다.

```bash
# crds/backups.yaml에 retentionDays 필드를 추가한 차트로 업그레이드한다
helm upgrade shop-api ./shop-api -n crd

# CRD 스키마가 바뀌었는지 본다
kubectl get crd backups.shop.example.com \
  -o jsonpath='{.spec.versions[0].schema.openAPIV3Schema.properties.spec.properties}{"\n"}'

# 릴리스를 지워도 CRD는 남는다
helm uninstall shop-api -n crd
kubectl get crd | grep backups
```

```text
{"schedule":{"type":"string"}}
release "shop-api" uninstalled
backups.shop.example.com   2026-10-18T23:46:51Z
```

차트에는 `retentionDays`가 있는데 클러스터의 CRD에는 없다. 오퍼레이터 새 버전이 새 필드를 기대하다 이상하게 동작하는 원인이 된다. Helm이 이렇게 보수적인 이유는 CRD가 클러스터 전체에 하나뿐이기 때문이다. CRD를 지우면 그 종류의 커스텀 리소스가 모든 네임스페이스에서 함께 사라진다. 한 릴리스의 업그레이드나 삭제가 그런 일을 일으키지 않게 막아 둔 것이다.

그래서 CRD는 차트 업그레이드와 별도로 올린다.

```bash
# CRD를 서버 사이드 적용으로 직접 올린다 (Helm이 소유한 필드라 충돌을 넘긴다)
kubectl apply --server-side --force-conflicts -f ./shop-api/crds/
```

```text
customresourcedefinition.apiextensions.k8s.io/backups.shop.example.com serverside-applied
```

`--force-conflicts` 없이 하면 `conflict with "helm" using apiextensions.k8s.io/v1: .spec.versions` 오류가 난다. Helm이 처음 만들 때 이 필드의 관리자로 기록됐기 때문이다. 큰 CRD는 일반 `kubectl apply`가 남기는 어노테이션이 크기 제한을 넘기 쉬워서 서버 사이드 적용을 쓴다. 차트에 따라서는 CRD를 `crds/`가 아니라 `templates/`에 넣고 업그레이드까지 관리하게 하거나, CRD만 담은 차트를 따로 두기도 한다. 어느 방식인지 차트 문서에서 먼저 확인한다.

## 릴리스가 꼬였을 때 보는 순서

정리하면 업그레이드는 리비전 예약, 훅, three-way 패치, 대기, 기록 확정 순으로 진행되고, 각 단계에서 멈추면 남는 흔적이 다르다. `another operation is in progress`는 pending 리비전이 남은 것이니 `helm history`로 상태를 보고 롤백하거나 지운다. 손으로 고친 값은 차트에 적힌 필드라면 다음 배포에 덮이고, 차트가 모르는 필드는 남는다. 바꿀 수 없는 필드 오류는 반쯤 적용된 상태를 남기니 엔드포인트부터 확인하고, CRD는 Helm이 업그레이드하지 않으니 따로 올린다. 다음 글에서는 차트를 여러 개 묶고, 저장소에 올리고, ArgoCD로 배포하는 흐름을 본다.

## 면접에서 나올 만한 질문

### helm upgrade --atomic과 --wait는 무엇이 다른가요?

`--wait`는 리소스를 적용한 뒤 Pod가 Ready가 될 때까지 `--timeout`만큼 기다리고, 안 되면 리비전을 failed로 남긴다. `--atomic`은 거기에 더해 실패하면 직전 성공 리비전으로 자동 롤백하고, `--wait`를 저절로 켠다. 자동 복구는 편하지만 실패 상태를 볼 틈이 없어지니 CI 로그에 history와 이벤트를 남겨 둔다.

### Helm 3의 three-way merge는 무엇인가요?

지난 리비전의 매니페스트, 클러스터의 현재 상태, 새 매니페스트를 비교해 패치를 만드는 방식이다. 새 매니페스트에 적힌 필드는 그 값으로 맞추고, 차트에서 빠진 필드는 지우고, 차트가 모르는 필드는 그대로 둔다. 그래서 `kubectl scale`로 바꾼 레플리카는 다음 배포에 되돌아가지만 사이드카나 다른 도구가 붙인 어노테이션은 남는다.

### `another operation (install/upgrade/rollback) is in progress`는 어떻게 해결하나요?

이전 Helm 작업이 중간에 죽어 리비전이 pending 상태로 남은 것이다. `helm history`로 확인하고, 정말 다른 작업이 없다면 pending-upgrade는 마지막 deployed 리비전으로 `helm rollback`, 첫 설치가 끊긴 pending-install은 `helm uninstall` 후 재설치한다. 재발을 막으려면 같은 릴리스의 배포가 겹치지 않게 하고, `--timeout`을 CI 제한 시간보다 짧게 둔다.

### Helm 훅은 어떤 경우에 쓰고, 주의할 점은 무엇인가요?

DB 마이그레이션처럼 본 리소스 적용 전후에 한 번 돌릴 작업에 쓴다. pre 훅이 실패하면 본 리소스는 적용되지 않는다. 훅 리소스는 릴리스로 관리되지 않아 uninstall이나 롤백이 결과를 되돌리지 않으니, 마이그레이션은 옛 버전과 새 버전이 함께 동작하게 나눠 쓴다.

### 셀렉터를 바꾸는 업그레이드가 실패했는데 서비스 장애가 났습니다. 왜인가요?

Helm은 Service를 Deployment보다 먼저 적용한다. Service 셀렉터는 바꿀 수 있어서 새 라벨로 먼저 바뀌고, Deployment 셀렉터는 바꿀 수 없어 실패한다. 그러면 Service가 아직 새 라벨이 없는 Pod를 찾지 못해 엔드포인트가 비고 요청이 실패한다. 즉시 롤백하고, 셀렉터는 `--cascade=orphan`으로 Deployment를 지운 뒤 다시 만드는 식으로 바꾼다.

### 차트의 crds/ 디렉터리에 둔 CRD는 왜 업그레이드되지 않나요?

CRD는 클러스터에 하나뿐이고 지우면 모든 네임스페이스의 커스텀 리소스가 함께 사라진다. 한 릴리스의 업그레이드나 삭제가 그런 영향을 주지 않게 Helm은 `crds/`의 CRD를 처음 설치할 때만 만들고 이후로는 건드리지 않는다. 그래서 CRD 변경은 `kubectl apply --server-side`로 따로 올리거나, CRD 전용 차트로 관리한다.

### helm diff는 무엇을 보여 주고, 무엇을 놓치나요?

이번 업그레이드가 바꿀 매니페스트를 diff로 보여 준다. 기본 모드는 지난 리비전 매니페스트와 새 매니페스트만 비교해서, 누군가 클러스터에서 직접 바꾼 값을 보지 못한다. `--three-way-merge`를 주면 현재 상태까지 넣어 실제로 바뀔 내용을 보여 준다.
