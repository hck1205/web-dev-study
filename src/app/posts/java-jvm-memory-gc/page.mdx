메모리 한도 512MiB인 Pod에 자바 서비스를 올렸다. 힙이 모자라면 안 되니 `-Xmx480m`을 줬다. 한도보다 작으니 안전해 보였다. 그런데 트래픽이 붙자 Pod가 `OOMKilled`로 재시작하기 시작했다. 애플리케이션 로그에는 `OutOfMemoryError`가 한 줄도 없다. 힙 사용량 그래프도 400MB를 넘은 적이 없었다.

같은 상황을 cgroup으로 그대로 만들어 봤다. 힙에 380MB를 붙잡고, 잠든 스레드 200개와 다이렉트 버퍼 64MB를 쓰는 작은 프로그램이다. 한 번은 `-Xmx480m`, 한 번은 `-XX:MaxRAMPercentage=60`으로 돌렸다.

```bash
# 실습용 메모리 cgroup을 만들고 한도를 512MiB로 건다 (cgroup v1)
sudo mkdir -p /sys/fs/cgroup/memory/t2jvm
echo $((512*1024*1024)) | sudo tee /sys/fs/cgroup/memory/t2jvm/memory.limit_in_bytes
# 셸을 그룹에 넣고 자바를 실행한다: 힙 380MB, 스레드 200개, 다이렉트 버퍼 64MB
sudo sh -c 'echo $$ > /sys/fs/cgroup/memory/t2jvm/cgroup.procs; java -Xmx480m MemApp 380 200 64; echo "exit=$?"'
grep oom_kill /sys/fs/cgroup/memory/t2jvm/memory.oom_control   # 커널이 이 그룹에서 죽인 횟수
```

```text
== -Xmx480m
Killed
exit=137
oom_kill 1
== -XX:MaxRAMPercentage=60
Exception in thread "main" java.lang.OutOfMemoryError: Java heap space
	at MemApp.main(MemApp.java:24)
exit=1
oom_kill 1
```

`-Xmx480m`은 커널이 죽였다(137 = SIGKILL). 힙은 480MB까지 쓸 수 있다고 믿었는데, 힙 밖에서 쓰는 메모리를 더하니 512MiB를 먼저 넘었다. `MaxRAMPercentage=60`은 힙을 307MB로 잡아서, 380MB를 넣으려는 순간 JVM이 스스로 `OutOfMemoryError`를 던졌다. 같은 코드가 한쪽은 아무 흔적 없이 죽고, 다른 쪽은 원인과 줄 번호를 남겼다(oom_kill 카운터가 그대로 1인 것도 그래서다).

이 글은 JVM 프로세스의 메모리가 어디에 쓰이는지부터 시작해, 힙 안의 세대 구분, OOM 메시지마다 다른 원인, 컨테이너 한도에서 힙 몫을 정하는 법, 그리고 메모리 다음으로 서비스를 멈추게 하는 스레드 풀 고갈과 Java 21의 가상 스레드를 다룬다. 멈춘 서비스에서 `jcmd`로 무엇을 뜨는지도 함께 본다. 환경은 Ubuntu 24.04, OpenJDK 21.0.12다.

이 주제의 다른 글: G1과 ZGC의 멈춤을 GC 로그로 비교하고 Node·Go와 함께 컨테이너 힙 한도를 다룬 [가비지 컬렉션 글](/posts/garbage-collection), 스레드 덤프로 데드락을 찾는 [데드락 글](/posts/deadlocks), 같은 서버 언어 런타임을 Go 쪽에서 본 [Go 동시성 글](/posts/go-concurrency-basics)이 있다. GC 알고리즘 설명은 그쪽으로 넘기고, 여기서는 메모리 지도와 스레드에 집중한다.

## JVM 프로세스가 쓰는 메모리 지도

`-Xmx`는 자바 힙의 최대 크기일 뿐이다. JVM 프로세스는 힙 말고도 여러 곳에 메모리를 쓴다.

- 자바 힙: `new`로 만든 객체가 사는 곳. GC가 관리한다.
- 메타스페이스(Metaspace): 클래스의 구조, 메서드 정보 같은 메타데이터. JDK 8부터 힙 밖 네이티브 메모리로 옮겨졌고, 기본으로는 상한이 없다.
- 스레드 스택: 스레드마다 하나. 리눅스 x64 기본 예약 크기는 1MiB(`-Xss`)이고, 실제로 쓴 만큼만 물리 메모리가 잡힌다.
- 코드 캐시: JIT 컴파일러가 만든 기계어. 기본 예약 240MB.
- 다이렉트 버퍼: `ByteBuffer.allocateDirect`로 잡는 힙 밖 메모리. Netty 같은 네트워크 라이브러리가 많이 쓴다. 상한(`MaxDirectMemorySize`)을 따로 안 주면 최대 힙 크기와 같다.
- GC 자체의 자료 구조, JIT 컴파일러의 작업 공간, 심볼 표, 그리고 JNI로 붙은 네이티브 라이브러리가 쓰는 메모리.

아래 그림에서 점이 흐르는 방향은 "이 영역이 컨테이너 한도를 함께 채운다"는 뜻이다. 커널은 이 모두를 합친 RSS로 한도를 지킨다.

어디에 얼마가 쓰이는지는 Native Memory Tracking(NMT)으로 본다. 켜는 데 약간의 오버헤드(문서상 5~10% 정도의 성능 비용)가 있어서 시작 옵션으로만 켤 수 있다.

```bash
# NMT를 켜고 시작한다: 힙 256MB 한도에 150MB를 채우고, 스레드 200개, 다이렉트 버퍼 64MB
java -Xmx256m -XX:NativeMemoryTracking=summary MemApp 150 200 64 &
grep VmRSS /proc/$!/status                              # 커널이 보는 실제 사용량
jcmd $! VM.native_memory summary scale=MB               # JVM이 아는 영역별 사용량
```

```text
VmRSS:	  315076 kB

Total: reserved=1938MB, committed=414MB
       malloc: 78MB #14022
       mmap:   reserved=1860MB, committed=336MB

-                 Java Heap (reserved=256MB, committed=256MB)
-                     Class (reserved=1024MB, committed=0MB)
                            (classes #718)
-                    Thread (reserved=222MB, committed=23MB)
                            (threads #221)

-                      Code (reserved=242MB, committed=7MB)

                            (malloc=64MB #64) (at peak)
-        Shared class space (reserved=16MB, committed=13MB, readonly=0MB)
-                 Metaspace (reserved=64MB, committed=0MB)
```

출력이 길어서 1MB 미만 줄과 일부 세부 줄을 뺐다. 읽는 법은 이렇다.

`reserved`는 주소 공간만 잡아 둔 양이고 `committed`가 실제로 메모리를 받은 양이다. 그래서 `Total`의 reserved 1938MB는 신경 쓰지 않는다. 볼 것은 committed 414MB다. 스레드 줄이 좋은 예다. 스레드 221개가 스택으로 221MB를 예약했지만 실제로 받은 건 22MB다. 스레드 하나에 1MiB가 드는 게 아니라 쓴 깊이만큼 든다.

힙 다음으로 큰 건 GC 46MB와 Other 64MB다. GC 줄은 G1이 영역(region)마다 들고 있는 기억 집합(remembered set)과 카드 테이블 같은 자료 구조다. Other의 64MB는 다이렉트 버퍼 64개다. 힙 그래프만 보는 대시보드에는 이 110MB가 보이지 않는다.

VmRSS(308MiB)가 committed(414MB)보다 작은 건 committed된 힙 256MB를 아직 다 만지지 않아서다. 시간이 지나 힙이 한 바퀴 다 쓰이면 RSS는 committed에 가까워진다. 처음 장면의 `-Xmx480m`에서 바로 이게 일어났다. 힙 480MB에 이 110MB만 더해도 512MiB를 넘는다.

비교할 기준점을 잡으려면 시작 직후 `jcmd <pid> VM.native_memory baseline`을 뜨고, 한참 뒤 `VM.native_memory summary.diff`로 어느 영역이 늘었는지 본다. 메타스페이스가 계속 늘면 클래스 로더 누수, Thread가 늘면 스레드 누수, Other가 늘면 다이렉트 버퍼다.

## 힙 안에서 객체가 늙어 가는 길

지금 힙 상태는 `jcmd`와 `jstat`으로 본다. 앞의 NMT 실험 프로세스에서 떴다.

```bash
jcmd <pid> GC.heap_info        # 힙 크기, 영역 크기, young/survivor 영역 수, 메타스페이스
jstat -gcutil <pid>            # 영역별 사용률(%)과 GC 횟수·누적 시간
```

  region size 1024K, 8 young (8192K), 3 survivors (3072K)

`jstat`에서 `O`(Old 사용률)가 81%, young GC(`YGC`)가 9번에 누적 0.132초, 전체 GC(`FGC`)는 0번이다. 운영에서는 `jstat -gcutil <pid> 1000`처럼 1초 간격으로 찍으며 `O`가 GC 뒤에도 내려오지 않고 오르는지, `FGC`가 늘어나는지를 본다. Old가 GC 뒤에도 계속 오르면 살아 있는 데이터가 늘고 있다는 뜻이다.

### 영역보다 큰 객체

이 실습을 처음 짤 때 힙 256MB에 1MB짜리 배열 150개를 넣으려다 `OutOfMemoryError`가 났다. 150MB면 넉넉해 보이는데 그랬다. 원인은 위 출력의 `region size 1024K`에 있다. G1은 영역 크기의 절반 이상인 객체를 거대 객체(humongous object)로 따로 다룬다. 1MB 배열은 헤더 16바이트 때문에 영역 하나(1MB)를 살짝 넘어서, 연속된 영역 두 개를 차지하고 두 번째 영역의 거의 전부를 버린다. 150개가 영역 300개를 원했고 힙에는 256개뿐이었다. 배열을 256KB로 줄이자 문제가 사라졌다.

운영에서는 큰 JSON 응답을 통째로 `byte[]`로 읽거나 큰 배열을 쓰는 코드에서 이 모양이 나온다. `-Xlog:gc`에 `Pause Young (Concurrent Start) (G1 Humongous Allocation)`이 자주 보이면 의심하고, 스트리밍으로 바꾸거나 `-XX:G1HeapRegionSize`를 키운다.

## OOM 메시지마다 다른 곳이 찼다

`OutOfMemoryError`는 하나의 오류가 아니다. 메시지 뒷부분이 어느 영역이 찼는지 알려 준다. 영역마다 하나씩 일부러 채워 봤다.

```bash
java -Xmx64m Oom heap                                   # 힙에 1MB 배열을 계속 쌓는다
java -Xmx64m -XX:+UseParallelGC Oom gcoverhead          # 작은 객체로 HashMap을 계속 키운다
java -XX:MaxMetaspaceSize=32m Oom metaspace             # 같은 클래스를 숨은 클래스로 계속 정의한다
java -XX:MaxDirectMemorySize=32m Oom direct             # 다이렉트 버퍼를 계속 잡는다
# 프로세스가 가질 수 있는 태스크 수를 120개로 묶고 스레드를 계속 만든다
sudo mkdir -p /sys/fs/cgroup/pids/t2pids && echo 120 | sudo tee /sys/fs/cgroup/pids/t2pids/pids.max
sudo sh -c 'echo $$ > /sys/fs/cgroup/pids/t2pids/cgroup.procs; exec java -Xmx64m Oom threads'
```

```text
== heap
Exception in thread "main" java.lang.OutOfMemoryError: Java heap space
	at Oom.main(Oom.java:10)
== gcoverhead
Exception in thread "main" java.lang.OutOfMemoryError: GC overhead limit exceeded
	at java.base/java.lang.Integer.valueOf(Integer.java:1083)
	at Oom.main(Oom.java:13)
== metaspace
Exception in thread "main" java.lang.OutOfMemoryError: Metaspace
	at java.base/java.lang.ClassLoader.defineClass0(Native Method)
== direct
Exception in thread "main" java.lang.OutOfMemoryError: Cannot reserve 1048576 bytes of direct buffer memory (allocated: 33554432, limit: 33554432)
	at java.base/java.nio.Bits.reserveMemory(Bits.java:178)
== threads
threads started: 100
[0.197s][warning][os,thread] Failed to start thread "Unknown thread" - pthread_create failed (EAGAIN) for attributes: stacksize: 1024k, guardsize: 0k, detached.
Exception in thread "main" java.lang.OutOfMemoryError: unable to create native thread: possibly out of memory or process/resource limits reached
```

메시지마다 보는 곳이 다르다.

`Java heap space`는 힙이 찼는데 GC가 더 비울 게 없다는 뜻이다. 살아 있는 데이터가 진짜 많은지(누수, 상한 없는 캐시, 한 번에 너무 많이 읽는 쿼리) 힙 덤프로 확인한다. 운영에는 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps`를 미리 걸어 둔다. 덤프는 힙 크기만큼 크니 경로는 넉넉한 볼륨으로 잡는다.

`GC overhead limit exceeded`는 힙이 꽉 차기 직전에 GC만 하다가 포기한 것이다. Parallel GC는 시간의 98% 이상을 GC에 쓰고도 힙을 2%도 못 비우면 이 오류를 던진다. JDK 21에서 같은 코드를 G1(기본 GC)로 돌리면 이 메시지 대신 `Java heap space`가 났다. G1 쪽이 오히려 빨리(1초, Parallel은 5초) 포기했다. 메시지는 달라도 원인은 같다.

`Metaspace`는 클래스가 너무 많다. 실제로는 클래스 로더 누수가 흔하다. 앱 서버에 재배포를 반복하거나, 요청마다 프록시 클래스나 스크립트 엔진 클래스를 새로 만드는 코드가 옛 클래스 로더를 붙잡는다. `jcmd <pid> VM.classloader_stats`로 로더별 클래스 수를 본다. `MaxMetaspaceSize`를 안 주면 상한이 없어서 이 오류 대신 컨테이너가 커널에 죽는다.

`direct buffer memory`는 힙 밖 버퍼 몫이 찼다. 다이렉트 버퍼는 그걸 가리키는 작은 힙 객체가 GC될 때 풀리는데, 힙이 한가해서 GC가 드물면 오래 남는다. 버퍼를 재사용하는 풀을 쓰는지, 한도가 힙 크기와 같아서 사실상 무제한이 아닌지 본다.

`unable to create native thread`는 메모리 문제처럼 이름이 붙었지만 대개 개수 한도다. 컨테이너의 `pids.max`, `ulimit -u`, 커널의 `threads-max`에 닿았거나 스레드를 끝없이 만드는 코드가 있다. 위 출력에서 스레드 100개 근처에서 `pthread_create failed (EAGAIN)`이 났다. 쿠버네티스에서는 노드의 PID 한도(`podPidsLimit`)로도 걸린다.

마지막으로 메시지 없이 `exit=137`은 처음 장면의 커널 OOM이다. JVM이 아니라 커널이 죽였으니 JVM 로그에는 아무것도 없고, `kubectl describe pod`의 `Last State: Terminated, Reason: OOMKilled`와 노드의 `dmesg`에서만 보인다. 쿠버네티스에서 이걸 읽는 법은 [Pod 리소스 글](/posts/k8s-pod-resources)이 다룬다.

## 요청 스레드 네 개가 모두 결제를 기다린다

메모리 다음으로 자바 서비스를 멈추게 하는 건 스레드 풀이다. 요청 처리 스레드를 4개로 둔 작은 HTTP 서버를 만들었다. `/order`는 결제 서비스를 부르는데, 결제 서비스는 연결을 받기만 하고 응답하지 않는다. 그리고 호출에 읽기 타임아웃이 없다. `/health`는 바로 `ok`를 돌려준다.

```java
server.createContext("/order", ex -> {
    try (Socket s = new Socket("127.0.0.1", 17991)) { // 읽기 타임아웃 없음
        s.getInputStream().read();                    // 여기서 영원히 기다린다
    }
    ex.sendResponseHeaders(200, -1);
    ex.close();
});
ThreadFactory named = Thread.ofPlatform().name("http-worker-", 0).factory();
server.setExecutor(Executors.newFixedThreadPool(4, named)); // 요청 스레드 4개
```

```bash
curl -s -m 2 -o /dev/null -w "before: /health %{http_code} %{time_total}s\n" http://127.0.0.1:17990/health
for i in 1 2 3 4; do (curl -s -m 30 -o /dev/null http://127.0.0.1:17990/order &); done   # 주문 4건
curl -s -m 3 -o /dev/null -w "after: /health %{http_code} %{time_total}s\n" http://127.0.0.1:17990/health
```

```text

after: /health 000 3.003088s
```

함정이 하나 있다. 상태가 `RUNNABLE`이다. 기다리고 있는데 실행 중이라고 나온다. JVM 입장에서 네이티브 소켓 읽기 안에 들어간 스레드는 `RUNNABLE`로 보이기 때문이다. 그래서 덤프에서 `WAITING`, `BLOCKED`만 찾으면 이 문제를 놓친다. 봐야 할 건 상태가 아니라 스택 맨 위다. 같은 프레임(`SocketDispatcher.read0`)에 풀 스레드 전부가 모여 있고, 바로 아래 내 코드가 어느 줄인지(`Shop.java:17`)가 범인이다. `cpu=0.97ms`처럼 오래 살았는데 CPU를 거의 안 쓴 것도 기다리고 있다는 신호다. 덤프를 5~10초 간격으로 두세 번 떠서 같은 스레드가 같은 자리에 계속 있는지 확인한다. 서로 락을 기다리는 `BLOCKED` 고리라면 [데드락 글](/posts/deadlocks)의 방법으로 읽는다.

고치는 순서는 대개 이렇다. 먼저 모든 원격 호출에 연결·읽기 타임아웃을 준다(`socket.setSoTimeout`, HTTP 클라이언트의 `connectTimeout`과 요청 타임아웃, JDBC의 쿼리 타임아웃). 다음으로 하류마다 동시에 부를 수 있는 수를 따로 묶어서, 결제가 느려도 다른 요청이 쓸 스레드는 남게 한다. 마지막으로 대기열에 상한을 둔다. `new ThreadPoolExecutor(core, max, keepAlive, unit, new ArrayBlockingQueue<>(100), rejectPolicy)`처럼 만들면 넘치는 요청은 바로 거절되고 클라이언트는 빨리 실패한다. 늦게 성공하는 것보다 빨리 실패하는 게 나은 경우가 많다. 이 패턴들은 [회복 탄력성 패턴 글](/posts/resilience-patterns)에 정리돼 있다.

## 가상 스레드는 기다림을 싸게 만든다

스레드 풀을 크게 잡으면 되지 않을까. 플랫폼 스레드 하나는 OS 스레드 하나다. 스택과 커널 자원을 쓰고, 수천 개가 되면 문맥 전환 비용과 메모리가 부담이 된다. 앞 절의 계산기에서 본 그대로다. Java 21에 정식으로 들어온 가상 스레드(virtual thread, JEP 444)는 이 제약을 바꾼다. Go의 고루틴과 비슷하게, JVM이 적은 수의 OS 스레드(캐리어 스레드) 위에 많은 가상 스레드를 번갈아 올린다. 가상 스레드가 I/O나 `sleep`에서 기다리면 캐리어에서 내려오고(unmount), 캐리어는 다른 가상 스레드를 돌린다.

100ms씩 기다리는 작업 1만 개를 돌려 봤다. 캐리어 수는 4로 고정했다.

```java
Runnable io = () -> sleep100();   // 100ms 기다리는 I/O라고 생각한다
run("platform pool(200), 10k tasks", Executors.newFixedThreadPool(200), 10_000, io);
run("virtual per task, 10k tasks", Executors.newVirtualThreadPerTaskExecutor(), 10_000, io);
```

```bash
java -Djdk.virtualThreadScheduler.parallelism=4 Vt   # 캐리어 스레드 4개
```

```text
platform pool(200), 10k tasks       5247 ms
virtual per task, 10k tasks          263 ms
```

플랫폼 스레드 200개는 한 번에 200개씩, 50번을 돌아야 해서 5초가 걸렸다. 가상 스레드는 작업마다 하나씩 1만 개를 만들고 0.26초에 끝났다. 캐리어는 4개뿐인데도 그렇다. 기다리는 동안 캐리어를 놓아주기 때문이다. 코드는 평범한 블로킹 코드 그대로다. 이게 가상 스레드의 장점이다. 콜백이나 리액티브 체인 없이 위에서 아래로 쓴 코드가 기다림을 겹친다.

### 캐리어에 붙어 버리는 경우

가상 스레드가 내려오지 못하고 캐리어를 붙잡는 경우가 있다. 이걸 고정(pinning)이라고 한다. JDK 21~23에서는 `synchronized` 블록 안에서 기다리면 고정된다. 100ms 기다리는 작업 100개를 `synchronized`와 `ReentrantLock`으로 감싸 비교했다.

```java
Runnable pinned = () -> { synchronized (new Object()) { sleep100(); } };
Runnable unpinned = () -> {
    ReentrantLock l = new ReentrantLock();
    l.lock();
    try { sleep100(); } finally { l.unlock(); }
};
```

```text
virtual, synchronized, 100 tasks    2506 ms
virtual, ReentrantLock, 100 tasks    107 ms
```

`synchronized` 안에서 잔 가상 스레드는 캐리어를 놓지 못해서, 캐리어 4개가 한 번에 4개씩만 처리했다. 100 ÷ 4 × 100ms = 2.5초다. `ReentrantLock`은 0.1초였다. 고정이 어디서 생기는지는 JDK 21에서 시스템 속성으로 찍을 수 있다.

```bash
java -Djdk.tracePinnedThreads=short Pin   # 고정된 채 기다리면 위치를 찍는다
```

```text
VirtualThread[#19]/runnable@ForkJoinPool-1-worker-1 reason:MONITOR
    Pin.lambda$main$0(Pin.java:5) <== monitors:1
```

`reason:MONITOR`가 `synchronized`(모니터) 때문이라는 뜻이다. JDK 24(JEP 491)부터는 `synchronized`에서도 내려올 수 있게 바뀌어서 이 문제가 크게 줄었다. 네이티브 메서드나 외부 함수 호출 안에서 기다리는 경우는 여전히 고정된다. JDK 21을 쓴다면 오래된 JDBC 드라이버나 라이브러리의 `synchronized` 안 I/O가 흔한 원인이다.

가상 스레드를 쓸 때 다른 실수도 있다.

- 가상 스레드를 풀로 묶지 않는다. 만드는 비용이 작으니 작업마다 새로 만든다. 동시 실행 수를 제한하고 싶으면 풀 크기가 아니라 `Semaphore`로 하류 호출 수를 묶는다. 가상 스레드 1만 개가 DB 커넥션 풀 20개 앞에 줄 서는 것은 정상이지만, 상한 없이 하류에 1만 요청을 보내는 건 사고다.
- CPU만 쓰는 일은 빨라지지 않는다. 캐리어 수(기본 CPU 수)보다 많이 동시에 돌 수 없다. 가상 스레드는 기다림을 겹칠 뿐이다.
- `ThreadLocal`에 큰 객체를 캐시하던 코드는 스레드가 1만 개가 되면 1만 벌을 만든다. 스레드 재사용을 가정한 캐시를 다시 본다.
- 스레드 덤프가 달라진다. `jcmd Thread.print`는 플랫폼 스레드만 보여 준다. 가상 스레드 1000개가 자는 프로세스에서 `Thread.print`에는 23개만 나왔다. 가상 스레드까지 보려면 JSON 덤프를 뜬다.

```bash
jcmd <pid> Thread.dump_to_file -format=json /tmp/threads.json   # 가상 스레드까지 모두 담는다
```

```text
<root> 7
java.util.concurrent.ThreadPerTaskExecutor@44c862c0 1000
ForkJoinPool-1/jdk.internal.vm.SharedThreadContainer@da2ef69 4
```

파일에서 컨테이너별 스레드 수를 뽑은 결과(일부)다. 작업마다 가상 스레드를 만든 실행기 안에 1000개가 있고, 캐리어 풀(`ForkJoinPool-1`)은 4개다. 각 스레드의 스택도 `VirtualThread.parkNanos` → `Thread.sleep` → 내 코드 순으로 들어 있다.

## 멈춘 자바 서비스에서 뜨는 순서

장애 중에는 재시작하기 전에 증거부터 남긴다. 재시작하면 스레드 상태와 힙이 함께 사라진다. 컨테이너 안에서 같은 사용자로 실행해야 `jcmd`가 붙는다.

```bash
jcmd                                              # JVM 목록과 pid
jcmd <pid> Thread.print > td1.txt; sleep 5; jcmd <pid> Thread.print > td2.txt   # 덤프 두 번
jcmd <pid> GC.heap_info                           # 힙 크기와 사용량
jstat -gcutil <pid> 1000 5                        # 1초 간격 5번: Old 추세와 GC 횟수
jcmd <pid> VM.native_memory summary               # NMT를 켜 둔 경우만: 힙 밖 메모리
jcmd <pid> GC.heap_dump /dumps/heap.hprof         # 메모리 문제가 확실할 때만 (멈춤이 길다)
```

```text
5137 MemApp 150 200 64
```

`jcmd`만 치면 이렇게 pid와 메인 클래스, 인자가 나온다(이 머신의 다른 JVM 줄은 뺐다). 증상별로 보면 이렇다.

CPU는 낮고 요청이 쌓인다. 스레드 덤프에서 요청 풀 스레드가 모두 같은 스택 위치에 있는지 본다. 상태가 `RUNNABLE`이어도 소켓 읽기라면 기다리는 중이다. 하류 타임아웃과 풀 대기열 길이를 확인한다.

CPU가 한 코어 이상 꾸준히 높다. `top -H -p <pid>`로 CPU를 많이 쓰는 스레드 번호를 찾아 덤프와 맞춘다. 위 JDK 21 덤프는 `[7806]`과 `nid=7806`이 모두 10진수라 그대로 찾으면 된다. JDK 8·11의 덤프는 `nid=0x1e7e`처럼 16진수라 `printf '%x\n' 7806`으로 바꿔서 찾는다. GC 스레드라면 힙이 모자란 것이다.

컨테이너가 137로 재시작한다. JVM 로그에 OOM이 없다면 힙 밖 몫이 모자라다. NMT로 영역별 크기를 재고 힙 비율을 낮춘다. `Java heap space`가 있다면 힙 덤프를 분석한다(Eclipse MAT의 Dominator Tree로 가장 많이 붙잡은 객체를 본다).

GC 멈춤으로 p99가 튄다. GC 로그와 지연 그래프를 맞춘다. 이 부분은 [가비지 컬렉션 글](/posts/garbage-collection)의 순서를 따른다.

## 다시 512MiB Pod로

처음의 Pod는 힙이 아니라 프로세스 전체가 한도를 넘어서 죽었다. `-Xmx`는 힙의 한도일 뿐이고, 메타스페이스, 스레드 스택, 다이렉트 버퍼, GC 자료 구조가 그 위에 얹힌다. 그래서 힙은 한도의 비율로 주되 힙 밖 몫을 NMT로 재서 남기고, OOM이 나면 메시지로 어느 영역인지 읽는다. 스레드도 같은 예산에서 나온다. 기다리는 일이 많으면 플랫폼 스레드를 늘리기보다 타임아웃과 벌크헤드를 먼저 두고, Java 21이라면 가상 스레드로 기다림을 싸게 만든다.

## 면접에서 나올 만한 질문

### JVM 메모리 구조를 설명해 주세요.

크게 GC가 관리하는 힙과 힙 밖 네이티브 메모리로 나눕니다. 힙은 young(Eden, Survivor)과 old로 나뉘고, 힙 밖에는 클래스 메타데이터를 담는 메타스페이스, 스레드마다 하나씩 있는 스택, JIT 결과를 담는 코드 캐시, 다이렉트 버퍼, GC 자료 구조가 있습니다. 컨테이너 한도는 이 모두를 합친 프로세스 메모리로 걸립니다.

### -Xmx를 컨테이너 한도 바로 아래로 줬는데 OOMKilled가 납니다. 왜 그런가요?

`-Xmx`는 힙만 묶고, 힙 밖 메모리가 그 위에 더해지기 때문입니다. 실험에서는 512MiB 한도에 `-Xmx480m`을 주자 JVM 로그 없이 137로 죽었고, `MaxRAMPercentage=60`으로 낮추자 JVM이 `Java heap space`를 남겼습니다. NMT로 힙 밖 사용량을 재서 그만큼 남기고 힙은 한도의 비율로 줍니다.

### OutOfMemoryError의 종류와 각각 무엇을 보나요?

`Java heap space`는 살아 있는 객체가 많은 것이라 힙 덤프를 봅니다. `Metaspace`는 클래스가 너무 많은 것이라 클래스 로더 누수를 의심합니다. `direct buffer memory`는 힙 밖 버퍼, `unable to create native thread`는 대개 pids 같은 개수 한도입니다. 메시지 없이 137로 죽었다면 JVM이 아니라 커널이 죽인 것입니다.

### 스레드 덤프에서 RUNNABLE인데 실제로는 멈춰 있을 수 있나요?

네, 네이티브 소켓 읽기 안에서 기다리는 스레드는 JVM이 RUNNABLE로 표시합니다. 그래서 상태보다 스택 맨 위 프레임을 봐야 합니다. 같은 읽기 프레임에 풀 스레드가 모두 몰려 있고 CPU 시간이 거의 늘지 않으면 하류 응답을 기다리는 것이고, 타임아웃이 없거나 너무 긴 겁니다.

### newFixedThreadPool을 운영에서 그대로 쓰면 무엇이 문제인가요?

대기열이 상한 없는 `LinkedBlockingQueue`라서 처리하지 못한 요청이 거절되지 않고 계속 쌓입니다. 하류가 느려지면 지연이 끝없이 늘고 메모리도 찹니다. `ThreadPoolExecutor`를 직접 만들어 대기열에 상한을 두고 거절 정책을 정하고, 하류 호출에 타임아웃과 벌크헤드를 둡니다.

### 가상 스레드는 무엇이고 언제 효과가 있나요?

JVM이 적은 수의 캐리어 OS 스레드 위에 많이 올리는 가벼운 스레드로, Java 21에서 정식이 됐습니다. 기다릴 때 캐리어에서 내려오기 때문에 I/O를 기다리는 작업이 많을 때 효과가 큽니다. 실험에서 100ms짜리 작업 1만 개가 플랫폼 스레드 200개로는 5.2초, 가상 스레드로는 0.26초였습니다. CPU만 쓰는 작업은 빨라지지 않습니다.

### 가상 스레드의 pinning은 무엇이고 어떻게 피하나요?

가상 스레드가 기다리는 동안 캐리어에서 내려오지 못하고 붙잡는 현상입니다. JDK 21~23에서는 `synchronized` 안에서 기다리면 생겨서, 실험에서 100개 작업이 0.1초 대신 2.5초 걸렸습니다. `-Djdk.tracePinnedThreads`로 위치를 찾고 `ReentrantLock`으로 바꾸거나, JDK 24 이상으로 올리면 `synchronized` 고정은 해소됩니다.

### 가상 스레드를 쓰면 스레드 풀 크기 고민이 없어지나요?

스레드 개수 고민은 사라지지만 동시성 상한 고민은 남습니다. 가상 스레드는 풀로 묶지 않고 작업마다 만들기 때문에, 하류 DB나 API에 보내는 동시 요청 수는 `Semaphore`나 커넥션 풀로 따로 묶어야 합니다. 그러지 않으면 기다림이 싸진 만큼 하류에 부하가 그대로 몰립니다.
