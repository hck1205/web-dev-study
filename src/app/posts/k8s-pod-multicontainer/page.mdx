<EasyIntro>
  한 Pod에 컨테이너를 여러 개 넣으면 편할 것 같지만, 순서 문제가 따라온다. 일반 컨테이너들은 정해진 순서 없이 한꺼번에 뜨고 한꺼번에 끝내라는 신호를 받아서, 앱이 아직 준비 안 된 옆 컨테이너를 부르다 죽거나, 끝날 때 옆 컨테이너가 먼저 사라져 버린다. 밤에 도는 작업 옆에 기록을 모으는 컨테이너를 붙였더니 작업이 끝나도 Pod가 영원히 일하는 중으로 보이는 일도 생긴다.

  이건 무대 공연과 비슷하다. 주인공이 나오기 전에 조명과 음향이 먼저 켜져 있어야 하고, 공연이 끝난 뒤에야 꺼져야 한다. 쿠버네티스는 먼저 뜨고 끝나야 다음으로 넘어가는 init 컨테이너에, 끝나지 않고 계속 도는 성질을 더한 네이티브 사이드카를 만들어 이 문제를 풀었다. 이 보조 컨테이너는 순서대로 먼저 뜨고, 주인공 컨테이너가 끝난 뒤에야 내려간다.

  이걸 알면 사이드카를 어디에 적어야 Job이 제대로 끝나는지, 그리고 보조 컨테이너도 자리와 메모리를 차지하니 정말 같은 파일이나 같은 주소를 써야 할 때만 붙여야 한다는 것이 보인다.
</EasyIntro>

밤마다 도는 정산 Job이 있다. 로그를 모으려고 같은 Pod에 fluent-bit 컨테이너를 하나 붙였다. 다음 날 아침 보니 정산은 새벽 2시 10분에 끝났다고 로그에 찍혀 있는데, Job은 아직 `0/1` Completions에 머물러 있고 Pod는 `1/2 Running`이다. 정산 컨테이너는 끝났지만 로그 컨테이너는 끝날 이유가 없으니 계속 돈다. 쿠버네티스 눈에는 Pod가 아직 일하는 중이다.

같은 시기에 다른 서비스에서는 배포할 때마다 Pod 몇 개가 `CrashLoopBackOff`로 한 번씩 튀었다. 로그는 `ECONNREFUSED 127.0.0.1:15001`. 앱이 사이드카 프록시보다 먼저 떠서, 아직 듣고 있지 않은 프록시 포트로 요청을 보낸 것이다. 한 Pod에 컨테이너를 여럿 두면 이렇게 순서 문제가 따라온다. 이 글은 init 컨테이너, 사이드카, 어댑터·앰배서더 패턴을 보고, 쿠버네티스가 이 순서 문제를 풀려고 만든 네이티브 사이드카(`initContainers`의 `restartPolicy: Always`)를 따라간다. `kubectl` 출력은 실습용 클러스터(kwok, Kubernetes 1.30)에서 받았다. 이 클러스터는 컨테이너를 실제로 돌리지 않아서, 컨테이너 시작 순서는 같은 머신에서 Node 프로세스 두 개로 재현했다.

## 한 Pod에 함께 두는 세 가지 모양

[Pod 기초](/posts/k8s-pod-basics)에서 봤듯 같은 Pod의 컨테이너는 같은 노드에 놓이고, `localhost`와 Pod 볼륨을 나눠 쓴다. 이걸 이용하는 보조 컨테이너는 하는 일에 따라 보통 세 가지로 부른다. 아래 그림의 점이 데이터가 흐르는 방향이다.

사이드카는 주 컨테이너 옆에서 부가 기능을 맡는다. 파일로 쓴 로그를 읽어 로그 서버로 보내는 로그 전달기, 설정 저장소를 지켜보다 바뀌면 파일을 갱신하는 설정 리로더, 서비스 메시의 프록시(Envoy)가 대표적이다. 앱 코드를 고치지 않고 기능을 붙일 수 있다는 게 장점이다.

어댑터는 앱이 밖으로 내놓는 것의 모양을 바꾼다. 자기 형식으로만 상태를 보여 주는 오래된 앱 옆에 exporter를 두고, Prometheus가 읽을 수 있는 `/metrics`로 바꿔 내놓는 식이다. 앰배서더는 반대로 앱이 밖으로 나가는 길을 대신 연다. 앱은 `localhost:5432`로 평범하게 접속하고, 옆의 프록시가 인증과 TLS를 붙여 클라우드 DB에 이어 준다. 클라우드 DB 접속용 프록시가 이런 모양으로 많이 쓰인다.

세 이름은 패턴을 부르는 말일 뿐 쿠버네티스 API에 따로 있는 개념이 아니다. 쿠버네티스가 구분하는 건 언제 뜨고 언제 끝나느냐뿐이다. 그래서 문제도 거기서 생긴다.

## 로그 사이드카를 붙일 때 챙길 것

가장 흔한 사이드카인 로그 전달기를 실제로 붙여 보면 매니페스트 밖에서 챙길 게 몇 가지 나온다. fluent-bit 설정은 ConfigMap으로 넣는다.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: shop-fluent-bit
data:
  fluent-bit.conf: |
    [SERVICE]
        Flush        1
        Log_Level    info

    [INPUT]
        Name         tail
        Path         /var/log/shop/*.log
        Tag          shop.*
        DB           /fluent-bit/state/tail.db

    [OUTPUT]
        Name         forward
        Match        *
        Host         fluentd.logging.svc
        Port         24224
```

```yaml
# Pod 쪽 볼륨: 로그는 크기 제한을 두고, 읽은 위치 기록은 따로 둔다
volumes:
  - name: logs
    emptyDir:
      sizeLimit: 500Mi
  - name: flb-state
    emptyDir: {}
  - name: flb-config
    configMap:
      name: shop-fluent-bit
```

`DB`는 어디까지 읽었는지 적어 두는 파일이다. 이게 없으면 사이드카가 재시작할 때마다 처음부터 다시 읽어 로그가 중복으로 들어간다. 그런데 로그 볼륨은 사이드카에 `readOnly`로 붙였으니 같은 볼륨에는 이 파일을 못 쓴다. 그래서 상태용 emptyDir을 하나 더 둔다.

`sizeLimit`도 중요하다. 앱이 로그를 돌려쓰지(rotate) 않으면 emptyDir은 노드 디스크를 계속 먹는다. 크기 제한을 넘으면 kubelet이 그 Pod를 쫓아내고, 제한이 없으면 결국 노드 전체가 DiskPressure에 걸려 다른 Pod까지 쫓겨난다. 쫓겨나는 순서는 [requests와 limits](/posts/k8s-pod-resources)의 eviction 부분과 같다. 앱이 일정 크기마다 파일을 돌려쓰게 하고, sizeLimit은 그보다 넉넉하게 잡는다.

## 일반 컨테이너끼리는 순서가 없다

`spec.containers`에 여러 개를 적으면 kubelet은 적힌 순서대로 하나씩 시작을 요청하지만, 앞의 것이 준비될 때까지 기다리지 않는다. 사실상 동시에 뜬다. 앱이 먼저 떠서 아직 듣고 있지 않은 프록시로 요청을 보내면 어떻게 되는지 재현해 봤다. 프록시 흉내는 2초 뒤에야 15001을 열고, 앱 흉내는 뜨자마자 그 포트로 설정을 받아 온다.

```js
// proxy.js: 사이드카 흉내. 2초 뒤에야 15001에서 듣는다
const http = require("node:http");
setTimeout(() => {
  http.createServer((req, res) => res.end("from proxy\n")).listen(15001, () => console.log("[proxy] listening :15001"));
}, 2000);

// boot.js: 앱 흉내. 뜨자마자 프록시를 거쳐 설정을 받는다
fetch("http://127.0.0.1:15001/config")
  .then((r) => r.text())
  .then((t) => console.log("[app] config:", t.trim()))
  .catch((e) => { console.error("[app] 시작 실패:", e.cause?.code ?? e.message); process.exit(1); });
```

```bash
node proxy.js & PX=$!                 # 사이드카와 앱이 거의 동시에 뜬다
node boot.js; echo "app exit=$?"
sleep 2.5                             # kubelet이 재시작할 때쯤에는 프록시가 떠 있다
node boot.js; echo "app exit=$?"
kill $PX
```

```text
[app] 시작 실패: ECONNREFUSED
app exit=1
[proxy] listening :15001
[app] config: from proxy
app exit=0
```

첫 시도는 연결 거부로 죽고, 재시작한 두 번째 시도는 성공한다. 쿠버네티스에서는 이게 "배포할 때마다 RESTARTS가 1씩 붙는 Pod"로 보인다. 결국은 뜨니까 그냥 넘기기 쉽지만, 재시작이 붙은 만큼 배포가 느려지고 알람이 시끄러워진다.

종료할 때도 거꾸로 같은 문제가 있다. Pod를 지우면 일반 컨테이너들은 동시에 SIGTERM을 받는다. 프록시가 먼저 끝나 버리면, 아직 처리 중인 요청을 마무리하려던 앱의 바깥 호출이 실패한다. 예전에는 앱이 프록시 준비를 기다리는 재시도 루프를 넣거나, 엔트리포인트 스크립트에서 프록시의 헬스 체크를 기다리거나, 서비스 메시 쪽 옵션(Istio의 `holdApplicationUntilProxyStarts`)으로 버텼다.

## init 컨테이너는 끝나야 다음으로 간다

순서가 보장되는 컨테이너가 하나 있긴 했다. init 컨테이너다. `spec.initContainers`에 적은 컨테이너는 하나씩, 적힌 순서대로 돌고, 종료 코드 0으로 끝나야 다음 것이 시작한다. 모두 끝나야 일반 컨테이너가 뜬다. DB가 열릴 때까지 기다리기, 마이그레이션, 설정 파일을 받아 emptyDir에 놓아두기 같은 "먼저 끝나야 하는 일"에 맞다. 동작 순서와 STATUS 칸의 `Init:0/2` 표시는 [Pod의 일생](/posts/k8s-pod-lifecycle)에서 봤다.

문제는 "끝나야" 한다는 조건이다. 로그 전달기나 프록시는 끝나면 안 된다. Pod가 살아 있는 내내 같이 돌아야 한다. init 컨테이너로는 시작 순서를 얻을 수 있지만 계속 돌 수가 없고, 일반 컨테이너로는 계속 돌 수 있지만 순서가 없다. 둘 다 필요한 게 사이드카였다.

## 네이티브 사이드카는 init 자리에서 계속 돈다

쿠버네티스는 init 컨테이너에 `restartPolicy: Always`를 줄 수 있게 해서 이 둘을 합쳤다. 1.28에 알파로 들어왔고, 1.29부터 기본으로 켜진 베타, 1.33에서 GA가 됐다. 실습 클러스터는 1.30이라 그대로 쓸 수 있다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: shop-sidecar
spec:
  initContainers:
    - name: migrate                 # 보통 init 컨테이너. 끝나야 다음으로 간다
      image: ghcr.io/example/shop:1.4.2
      command: ["./migrate", "up"]
    - name: log-shipper             # 네이티브 사이드카. 시작하면 다음으로 넘어가고 계속 돈다
      image: fluent/fluent-bit:3.1
      restartPolicy: Always
      volumeMounts:
        - name: logs
          mountPath: /var/log/shop
          readOnly: true
  containers:
    - name: app
      image: ghcr.io/example/shop:1.4.2
      volumeMounts:
        - name: logs
          mountPath: /var/log/shop
  volumes:
    - name: logs
      emptyDir: {}
```

이 필드는 init 컨테이너에만 쓸 수 있다. 일반 컨테이너에 같은 줄을 넣으면 API 서버가 거절한다.

```bash
kubectl apply -f sidecar.yaml
kubectl get pod shop-sidecar --watch

# containers 쪽에 restartPolicy: Always를 넣은 잘못된 버전
kubectl apply -f bad.yaml
```

```text
pod/shop-sidecar created
NAME           READY   STATUS     RESTARTS   AGE
shop-sidecar   0/2     Pending    0          1s
shop-sidecar   0/2     Init:0/2   0          6s
The Pod "bad-sidecar" is invalid: spec.containers[0].restartPolicy: Forbidden: may not be set for non-init containers
```

READY가 `0/2`다. 컨테이너는 initContainers에 둘, containers에 하나로 셋인데, 끝나고 마는 migrate는 빼고 계속 도는 사이드카는 세어서 2다. 실제 노드에서는 이 Pod가 `2/2 Running`이 되어야 다 뜬 것이다. 아래 그림에서 다음을 누르면 이 Pod가 뜨고 지는 순서가 보인다.

이 순서가 앞의 두 문제를 푼다. 시작할 때 사이드카가 앱보다 먼저 떠 있으니 `ECONNREFUSED`로 한 번 죽고 시작하는 일이 없다. 사이드카에 startupProbe를 달면 "포트를 열고 준비가 끝날 때까지"로 기다리는 조건을 더 정확히 줄 수 있다. 종료할 때는 앱이 다 끝난 뒤에 사이드카가 끝나니, 앱이 마지막으로 쓴 로그와 마지막 바깥 호출이 사이드카를 거쳐 나갈 수 있다. 다만 유예 시간(`terminationGracePeriodSeconds`)은 앱과 사이드카가 함께 쓴다. 앱이 30초를 거의 다 쓰면 사이드카는 정리할 틈 없이 SIGKILL을 받는다.

사이드카도 일반 컨테이너처럼 liveness, readiness, startup 프로브를 달 수 있다. 사이드카의 readiness가 실패하면 Pod 전체가 Ready가 아니게 된다. 프록시가 준비되지 않은 Pod로는 트래픽이 들어오지 않으니 맞는 동작이다. 그런데 로그 전달기의 readiness를 로그 서버 연결에 묶어 두면 로그 서버 장애가 서비스 장애가 된다. [프로브 글](/posts/k8s-pod-probes)에서 본 "공유 의존성을 프로브에 넣지 말라"는 이야기가 사이드카에도 그대로 적용된다.

## Job이 끝나지 않는 이유

처음의 정산 Job으로 돌아가 보자. Job은 Pod가 Succeeded가 되어야 완료로 친다. Pod가 Succeeded가 되려면 모든 일반 컨테이너가 끝나야 한다. 로그 전달기를 `containers`에 넣으면 정산 컨테이너가 끝나도 로그 전달기가 계속 도니 Pod는 영원히 Running이다. 아래 그림에서 다음을 누르면 두 방식의 차이가 보인다.

네이티브 사이드카가 나오기 전에는 정산 컨테이너가 끝날 때 공유 볼륨에 파일을 하나 남기고, 사이드카가 그 파일을 보면 스스로 끝나게 하는 식으로 맞췄다. 서비스 메시 프록시라면 정산 컨테이너가 끝나면서 프록시의 종료 엔드포인트(Istio의 `/quitquitquit`)를 불렀다. 두 방법 다 앱과 사이드카가 서로를 알아야 해서 깨지기 쉬웠다. 1.29 이상이라면 사이드카를 init 자리로 옮기는 게 가장 깔끔하다. 클러스터 버전이 섞여 있다면 가장 낮은 버전에서 기능이 켜져 있는지부터 확인한다.

같은 이유로 restartPolicy가 Never인 Job Pod에서도 네이티브 사이드카는 죽으면 다시 뜬다. 사이드카의 `restartPolicy: Always`가 Pod의 restartPolicy보다 우선한다. 정산이 도는 동안 로그 전달기가 한 번 죽어도 Job이 실패로 끝나지 않는다.

## 사이드카도 자리를 차지한다

컨테이너가 늘면 requests도 늘어난다. 스케줄러가 Pod 하나에 필요한 자원을 어떻게 계산하는지 알아야 Pending의 이유를 읽을 수 있다. init 컨테이너는 하나씩 돌고 끝나니, 원래는 "가장 큰 init 컨테이너"와 "일반 컨테이너의 합" 중 큰 값이 Pod의 요구량이었다. 네이티브 사이드카는 끝나지 않고 계속 자리를 쓰니 계산이 바뀐다. 사이드카는 자기보다 뒤에 오는 init 컨테이너가 돌 때도, 일반 컨테이너가 돌 때도 함께 자리를 쓴다.

실습 클러스터의 빈 노드(CPU 2코어)로 확인했다. 앱이 1코어, 프록시 사이드카가 500m, 캐시를 데우는 init 컨테이너가 1800m를 요청한다. 같은 컨테이너인데 init 컨테이너와 사이드카의 순서만 바꿨다.

```bash
# warmup(1800m) 다음에 proxy(사이드카 500m)
kubectl get pod init-before -o wide | awk '{print $1, $3, $7}'   # 이름, 상태, 노드만
kubectl describe node node-3 | sed -n '/Allocated resources/,/memory  /p'

# proxy(사이드카 500m) 다음에 warmup(1800m)
kubectl get events --field-selector involvedObject.name=init-after,reason=FailedScheduling -o custom-columns=M:.message --no-headers
```

```text

  Resource           Requests     Limits

  memory             0 (0%)       0 (0%)
```

warmup이 먼저면 warmup이 도는 동안 사이드카는 아직 없으니 1800m, 그 뒤에는 사이드카와 앱이 500m + 1000m = 1500m다. 큰 쪽인 1800m가 이 Pod의 요구량이고 2코어 노드에 들어갔다. 사이드카가 먼저면 warmup이 도는 동안 사이드카도 돌고 있어 1800m + 500m = 2300m가 필요하다. 2코어 노드에는 안 들어가 Insufficient cpu다. 아래에서 이 계산을 직접 해 볼 수 있다. 숫자는 밀리코어이고, 테스트의 앞 두 값이 위 두 Pod다.

실무에서 기억할 것은 두 가지다. 사이드카에도 requests를 꼭 적는다. 서비스 메시처럼 모든 Pod에 프록시가 자동으로 붙는 환경에서는 사이드카 몫이 클러스터 전체 requests의 꽤 큰 부분이 된다. 그리고 사이드카의 requests를 비워 두면 Pod 전체가 Guaranteed가 될 수 없다. QoS 계산은 [requests와 limits](/posts/k8s-pod-resources)에서 다뤘다.

## 컨테이너를 골라서 들여다본다

컨테이너가 여럿인 Pod에서는 거의 모든 명령에 컨테이너 이름이 필요하다. 먼저 이 Pod에 무엇이 어느 자리에 있는지부터 본다.

```bash
# init 자리와 일반 자리의 컨테이너, 사이드카 여부를 한 번에
kubectl get pod shop-sidecar -o jsonpath='{range .spec.initContainers[*]}{.name}{"\t"}restartPolicy={.restartPolicy}{"\n"}{end}{range .spec.containers[*]}{.name}{"\t"}(main){"\n"}{end}'
```

```text
migrate	restartPolicy=
log-shipper	restartPolicy=Always
app	(main)
```

restartPolicy가 비어 있는 init 컨테이너는 한 번 돌고 끝나는 것이고, Always인 것이 사이드카다. 그다음은 증상에 따라 컨테이너를 골라 본다.

```bash
# 특정 컨테이너의 로그. init 컨테이너와 사이드카도 이름으로 고른다
kubectl logs shop-sidecar -c migrate
kubectl logs shop-sidecar -c log-shipper --tail=50

# 모든 컨테이너 로그를 컨테이너 이름을 붙여 섞어 본다
kubectl logs shop-sidecar --all-containers --prefix

# 사이드카 안에 들어가 공유 볼륨에 무엇이 쌓였는지 본다
kubectl exec -it shop-sidecar -c log-shipper -- ls -l /var/log/shop

# 컨테이너별 재시작 횟수. 어느 컨테이너가 Pod를 흔드는지 바로 보인다
kubectl get pod shop-sidecar -o jsonpath='{range .status.initContainerStatuses[*]}{.name}={.restartCount}{" "}{end}{range .status.containerStatuses[*]}{.name}={.restartCount}{" "}{end}{"\n"}'
```

`-c`를 빼면 kubectl은 `kubectl.kubernetes.io/default-container` 어노테이션에 적힌 컨테이너를, 없으면 첫 번째 일반 컨테이너를 고르고 `Defaulted container "app" out of: ...`라고 알려 준다. 사이드카가 자동으로 주입되는 환경에서는 이 어노테이션을 앱 컨테이너로 지정해 두면 매번 `-c`를 치지 않아도 된다.

READY가 `1/2`처럼 모자랄 때는 describe에서 `Init Containers:`와 `Containers:` 두 덩어리를 따로 본다. 사이드카는 Init Containers 쪽에 있다. 많이 하는 실수는 Containers 쪽만 보고 "다 Running인데 왜 1/2지" 하며 헤매는 것이다. RESTARTS도 Pod 전체의 합이라, 사이드카가 계속 죽어서 숫자가 오르는 경우를 앱 문제로 오해하기 쉽다. 위의 컨테이너별 재시작 횟수가 그걸 갈라 준다.

## 언제 컨테이너를 더 붙이나

보조 컨테이너는 편하지만 공짜가 아니다. Pod마다 이미지를 하나 더 받고, 메모리와 CPU를 더 쓰고, 장애 지점이 하나 더 생긴다. 노드가 100개, Pod가 2000개인 클러스터에서 Pod마다 로그 전달기를 붙이면 로그 전달기가 2000개다. 같은 일을 노드마다 하나씩 도는 DaemonSet으로 하면 100개면 된다. 앱이 표준 출력으로 로그를 쓰면 노드의 로그 수집기가 `/var/log/containers`에서 읽어 갈 수 있으니, 파일로만 로그를 쓰는 앱이 아니라면 사이드카가 필요 없다.

그래서 기준은 "이 Pod의 파일 시스템이나 localhost를 꼭 같이 써야 하는가"다. 파일로만 로그를 쓰는 앱, Pod마다 다른 인증서를 쥐고 통신해야 하는 프록시, 앱과 같은 설정 파일을 실시간으로 바꿔 줘야 하는 리로더는 사이드카가 맞다. 노드 수준에서 해도 되는 일(로그 수집, 노드 메트릭)은 DaemonSet이, 클러스터 수준에서 해도 되는 일(공용 프록시, 게이트웨이)은 별도 Deployment가 낫다.

## 여러 컨테이너를 다시 정리하면

같은 Pod의 일반 컨테이너는 순서 없이 함께 뜨고 함께 SIGTERM을 받는다. 그래서 앱이 아직 안 뜬 프록시를 부르거나, 종료 때 프록시가 먼저 사라지는 문제가 생긴다. init 컨테이너는 순서를 지키지만 끝나야 하고, 네이티브 사이드카(init 자리의 `restartPolicy: Always`, 1.29 베타·1.33 GA)는 순서대로 먼저 뜨고, 계속 돌고, 일반 컨테이너가 끝난 뒤에 끝난다. 덕분에 Job도 정상적으로 완료된다. 사이드카도 requests를 차지하고 순서에 따라 Pod의 요구량이 달라지니 함께 계산한다. 여러 컨테이너가 얽힌 Pod가 안 뜰 때 어느 컨테이너부터 볼지는 [Pod가 안 뜰 때 보는 순서](/posts/k8s-pod-troubleshooting)에 정리했다.

## 면접에서 나올 만한 질문

### 한 Pod에 컨테이너를 여러 개 두는 건 언제인가요?

같은 노드의 파일 시스템이나 localhost를 꼭 함께 써야 하는 보조 기능일 때다. 파일 로그를 읽어 보내는 로그 전달기, 앱 대신 바깥 연결에 인증과 TLS를 붙이는 프록시(앰배서더), 앱의 지표를 표준 형식으로 바꾸는 exporter(어댑터)가 그런 예다. 따로 늘리고 따로 배포할 수 있는 것은 다른 Pod로 나누고, 노드 단위로 해도 되는 일은 DaemonSet으로 한다.

### init 컨테이너와 사이드카 컨테이너는 어떻게 다른가요?

init 컨테이너는 적힌 순서대로 하나씩 돌고 종료 코드 0으로 끝나야 다음 것이 시작하며, 모두 끝나야 일반 컨테이너가 뜬다. 사이드카는 Pod가 사는 내내 같이 돌아야 하는 보조 컨테이너다. 예전에는 일반 컨테이너로 넣어 순서를 보장받지 못했고, 지금은 init 자리에 restartPolicy: Always로 두는 네이티브 사이드카로 순서와 계속 실행을 함께 얻는다.

### 네이티브 사이드카는 어떻게 동작하나요?

initContainers에 restartPolicy: Always를 준 컨테이너다. 적힌 순서에 시작되고, 끝나기를 기다리지 않고 시작(startupProbe가 있으면 그 성공)만 확인하면 다음으로 넘어가며 Pod가 사는 동안 계속 돈다. 죽으면 Pod의 restartPolicy와 상관없이 다시 뜬다. 종료할 때는 일반 컨테이너가 모두 끝난 뒤 정의 역순으로 끝난다. 1.28 알파, 1.29부터 기본으로 켜진 베타, 1.33에서 GA다.

### 사이드카를 붙인 Job이 끝나지 않습니다. 왜 그런가요?

Job은 Pod가 Succeeded가 되어야 완료되고, 그러려면 모든 일반 컨테이너가 끝나야 한다. 로그 전달기 같은 사이드카를 일반 컨테이너로 넣으면 주 작업이 끝나도 사이드카가 계속 돌아 Pod가 Running에 머문다. 네이티브 사이드카로 옮기면 kubelet이 주 컨테이너가 끝난 뒤 사이드카를 끝내 Job이 완료된다. 예전에는 공유 파일로 신호를 주거나 프록시의 종료 엔드포인트를 불러 맞췄다.

### 앱이 사이드카 프록시보다 먼저 떠서 시작할 때마다 한 번씩 죽습니다. 어떻게 고치나요?

일반 컨테이너끼리는 시작 순서가 보장되지 않아서 생기는 문제다. 1.29 이상이면 프록시를 네이티브 사이드카로 옮기고 startupProbe를 달아, 프록시가 준비된 뒤에 앱이 뜨게 한다. 그 전 버전이라면 앱에서 재시도하거나 엔트리포인트에서 프록시 헬스 체크를 기다리고, 서비스 메시의 시작 순서 옵션을 쓴다.

### 사이드카가 있으면 Pod의 자원 요구량은 어떻게 계산되나요?

일반 컨테이너가 돌 때는 사이드카와 일반 컨테이너 requests의 합이 필요하다. init 컨테이너가 돌 때는 그 init 컨테이너의 requests에 그보다 앞에 시작한 사이드카의 requests가 더해진다. 둘 중 큰 값이 Pod의 요구량이라, 같은 컨테이너라도 사이드카를 무거운 init 컨테이너 앞에 두면 요구량이 커져 Pending이 날 수 있다.
