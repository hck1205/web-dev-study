서버를 새 장비로 옮기는 중이다. DNS를 바꾸기 전에 새 서버가 제대로 뜨는지 실제 도메인으로 확인하고 싶다. IP로 직접 들어가면 HTTPS 인증서가 안 맞고, 가상 호스트 설정도 도메인 이름을 보고 사이트를 고르니 제대로 확인이 안 된다. 그렇다고 DNS를 먼저 바꾸면 모든 사용자가 검증 안 된 서버로 간다.

이럴 때 쓰는 게 hosts 파일이다. 내 컴퓨터에서만 "이 도메인은 이 IP"라고 우겨 넣는 파일이다. 한 줄이면 되는 간단한 파일인데, 고쳤는데도 반영이 안 되는 일이 잦아서 생각보다 자주 사람을 헤매게 한다.

## DNS보다 먼저 보는 파일

hosts 파일은 이름과 IP의 짝을 적어 둔 텍스트 파일이다. 운영체제는 이름을 IP로 바꿀 때 보통 이 파일을 DNS보다 먼저 본다. 여기에 이름이 있으면 DNS에는 묻지도 않는다.

위치는 운영체제마다 다르다.

- 리눅스: `/etc/hosts`
- macOS: `/etc/hosts` (실제로는 `/private/etc/hosts`를 가리키는 링크)
- 윈도: `C:\Windows\System32\drivers\etc\hosts`

어디서든 관리자 권한이 있어야 고칠 수 있다. 윈도에서는 메모장을 관리자 권한으로 열어야 저장이 되고, 저장할 때 메모장이 `hosts.txt`로 확장자를 붙여 버리는 실수가 흔하다. 파일 이름은 확장자 없이 정확히 `hosts`여야 한다.

이 파일은 DNS보다 오래됐다. 인터넷 초창기에는 전 세계 호스트 목록이 `HOSTS.TXT` 파일 하나였고, 모든 컴퓨터가 중앙에서 이 파일을 내려받아 썼다. 호스트가 늘면서 이 방식이 한계에 부딪혀 1980년대에 DNS가 나왔고, hosts 파일은 "내 컴퓨터에만 적용되는 예외 목록"으로 남았다. DNS 자체가 어떻게 동작하는지는 [DNS 글](/posts/dns)에서 자세히 다뤘다.

운영체제마다 세부는 다르다.

리눅스는 glibc의 NSS(Name Service Switch)가 `/etc/nsswitch.conf`를 읽어 순서를 정한다. 보통 `hosts: files dns`처럼 files가 먼저다. 배포판에 따라 `mdns4_minimal`(로컬 네트워크의 `.local` 이름)이나 `resolve`(systemd-resolved)가 끼어 있기도 하다. systemd-resolved를 쓰는 배포판은 resolved도 `/etc/hosts`를 직접 읽어서, `127.0.0.53`의 로컬 리졸버로 묻는 프로그램에도 hosts 내용이 반영된다.

macOS는 mDNSResponder라는 시스템 서비스가 이름 해석과 캐시를 맡고, 이 서비스가 `/etc/hosts`를 읽는다. 맥에서 `.local`로 끝나는 이름은 로컬 네트워크의 멀티캐스트 DNS(Bonjour)로 먼저 찾으려 해서, hosts에 적어도 조회가 몇 초씩 늦어지는 일이 있다. 개발용 이름에 `.local`을 피하는 이유다.

윈도는 DNS Client 서비스가 hosts 파일 내용을 미리 DNS 캐시에 올려 두고 시작한다. 그래서 `ipconfig /displaydns`로 캐시를 보면 hosts에 적은 이름이 같이 보인다. 그 다음이 DNS 서버이고, DNS에서도 못 찾으면 LLMNR이나 NetBIOS 같은 로컬 네트워크 이름 해석으로 넘어간다.

이 순서를 따르지 않는 프로그램도 있다. `dig`와 `nslookup`은 DNS 서버에 직접 묻는 도구라 hosts를 보지 않는다. "hosts에 넣었는데 nslookup에는 안 나온다"는 건 정상이다. hosts가 적용됐는지 확인하려면 운영체제의 이름 해석을 거치는 명령을 써야 한다. 리눅스는 `getent hosts myapp.test`, 맥은 `dscacheutil -q host -a name myapp.test`, 윈도 PowerShell은 `Resolve-DnsName myapp.test`(옵션 `-DnsOnly`를 주면 DNS에만 묻는다)를 쓴다. 반대로 Go처럼 자체 리졸버를 가진 런타임이나 크롬의 내장 DNS 클라이언트는 hosts 파일을 스스로 읽어서 반영한다.

## 어디에 쓰나

### 로컬 개발용 도메인

`localhost:3000` 대신 `myapp.test`처럼 실제 서비스와 비슷한 이름으로 개발하고 싶을 때 쓴다. 서브도메인별로 동작이 달라지는 서비스(`api.`, `admin.`)나, 도메인 단위로 묶이는 쿠키를 확인할 때 특히 유용하다.

이름을 고를 때는 `.test`를 권한다. `.test`, `.example`, `.invalid`, `.localhost`는 표준(RFC 2606)으로 예약돼 있어서 실제 인터넷 도메인과 겹칠 일이 없다. 반대로 `.dev`는 피한다. 구글이 운영하는 진짜 최상위 도메인이고, 도메인 전체가 브라우저의 HSTS 프리로드 목록에 들어 있다. hosts로 `myapp.dev`를 127.0.0.1에 연결해도 브라우저는 무조건 HTTPS로만 접속하려 해서, 로컬 HTTP 서버로는 열리지 않는다. 맥에서 `.local`이 느린 건 앞에서 말한 그대로다.

### 광고나 사이트 차단

광고·추적 도메인을 쓸모없는 주소로 보내 버리는 방법이다. `0.0.0.0 ads.example.com`처럼 적는다. 127.0.0.1을 쓰면 내 컴퓨터에 웹 서버가 떠 있을 때 그 서버로 요청이 간다. 0.0.0.0은 보통 연결이 바로 실패해서 더 깔끔하지만, 리눅스와 맥은 0.0.0.0으로의 연결을 자기 자신으로 처리하기도 해서 완전히 같은 결과를 보장하지는 않는다. 수만 줄짜리 차단 목록을 hosts에 넣으면 이름 조회 때마다 파일을 훑는 비용이 커질 수 있다. 큰 목록은 Pi-hole 같은 DNS 단계의 차단이 더 맞다.

hosts에 `203.0.113.20 shop.example.com`을 넣고 브라우저로 `https://shop.example.com`에 들어간다. 브라우저는 주소창의 도메인 이름 그대로 TLS의 SNI와 HTTP의 `Host` 헤더를 보내니, 새 서버의 인증서와 가상 호스트 설정까지 실제 상황과 똑같이 확인된다. IP로 접속해서는 확인할 수 없는 부분이다. 확인이 끝나면 hosts 줄을 지우는 걸 잊으면 안 된다. 몇 달 뒤 그 서버를 내렸을 때 내 PC에서만 사이트가 안 열리는 원인이 된다.

명령줄에서 한 번만 확인할 거라면 hosts를 건드리지 않는 방법도 있다. `curl --resolve shop.example.com:443:203.0.113.20 https://shop.example.com/`은 그 요청 하나에만 이름과 IP의 짝을 지정한다. 끝나고 되돌릴 것도 없다.

컨테이너 안에도 각자의 `/etc/hosts`가 있다. 도커는 `--add-host`로, 쿠버네티스는 파드 스펙의 `hostAliases`로 이 파일에 줄을 추가한다. 내 PC의 hosts를 고쳐도 컨테이너 안에는 반영되지 않는다.

운영체제 캐시를 비우는 명령은 이렇다.

```bash
# 윈도 (관리자 명령 프롬프트)
ipconfig /flushdns

# macOS
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder

# 리눅스 (systemd-resolved를 쓰는 경우)
resolvectl flush-caches

# 리눅스 (nscd를 쓰는 경우)
sudo nscd -i hosts
```

리눅스는 systemd-resolved나 nscd 같은 캐시 서비스가 없으면 운영체제 수준의 DNS 캐시가 아예 없어서, 비울 것도 없다. 윈도는 hosts 파일이 바뀌면 DNS Client 서비스가 알아서 다시 읽으니 보통 flush 없이도 반영된다.

브라우저의 보안 DNS(DoH)를 켜 두면 hosts가 무시되지 않느냐는 걱정도 있다. 크롬은 보안 DNS를 켜도 hosts 파일을 먼저 본다. 내장 DNS 클라이언트가 hosts 파일을 직접 읽어서 DoH 질의 전에 확인하기 때문이다. 파이어폭스도 기본 설정에서는 hosts에 적힌 이름을 존중하지만, 버전과 DoH 모드 설정에 따라 동작이 달랐던 적이 있다. 특정 브라우저에서만 hosts가 안 먹는다면 그 브라우저의 보안 DNS 설정을 먼저 꺼 보고 비교하는 게 빠르다.

<Callout kind="warning" title="프록시를 쓰면 hosts가 끼어들 틈이 없다">
회사망처럼 브라우저가 HTTP 프록시나 PAC 파일을 쓰는 환경에서는 브라우저가 이름을 직접 풀지 않는다. 도메인 이름을 그대로 프록시에 넘기고, 이름 해석은 프록시 서버가 한다. 내 PC의 hosts가 아무리 맞아도 효과가 없다. 테스트할 도메인을 프록시 예외 목록에 넣어야 한다.
</Callout>

`localhost`에서도 비슷한 혼란이 생긴다. 많은 시스템에서 `localhost`는 IPv4 `127.0.0.1`과 IPv6 `::1` 둘 다로 풀린다. 개발 서버가 127.0.0.1에만 떠 있는데 클라이언트가 `::1`을 먼저 시도하면 연결이 거부된다. Node.js 17부터 이름 해석 결과를 운영체제가 준 순서 그대로 쓰도록 바뀌면서 이 증상을 겪은 사람이 많았다. 이럴 땐 주소를 `127.0.0.1`로 명시하거나 서버를 IPv6에도 띄운다.

## 포트도, 와일드카드도 안 된다

hosts로 `myapp.test`를 `127.0.0.1:3000`으로 보내고 싶어지는 순간이 온다. 안 된다. hosts가 하는 일은 이름을 IP 주소로 바꾸는 것뿐이고, 포트는 이름 해석과 상관없는 정보다. 포트는 URL에 적거나(`http://myapp.test:3000`) 스킴의 기본값(http는 80, https는 443)으로 정해진다. 이름 해석 함수가 돌려주는 것도 주소 목록이라 포트를 실을 자리가 없다. DNS에는 포트까지 담는 SRV 레코드가 있지만 브라우저는 일반 웹 접속에 SRV를 쓰지 않는다.

포트를 숨기고 싶으면 80·443에 리버스 프록시(nginx, Caddy 등)를 띄운다. 모든 개발용 이름을 127.0.0.1로 보내 두고, 프록시가 `Host` 헤더를 보고 `myapp.test`는 3000번, `api.myapp.test`는 4000번으로 넘겨주는 식이다.

와일드카드도 마찬가지다. `*.myapp.test` 같은 패턴은 hosts 형식에 없다. 파일은 정확히 같은 이름만 찾는다. 서브도메인이 많다면 방법이 몇 가지 있다.

- dnsmasq 같은 로컬 DNS 서버를 띄우고 `address=/myapp.test/127.0.0.1`처럼 도메인 전체를 한 번에 지정한다.
- `.localhost`를 쓴다. 크롬과 파이어폭스는 `*.localhost`를 hosts 설정 없이도 루프백 주소로 처리하고, systemd-resolved도 같은 규칙을 따른다. 다만 모든 도구와 운영체제가 그렇지는 않다.
- `127.0.0.1.nip.io`처럼 이름 안에 IP를 넣으면 그 IP를 돌려주는 공개 DNS 서비스를 쓴다. 대신 외부 서비스가 멈추면 같이 멈춘다.

## 악성코드가 노리는 파일

hosts 파일은 DNS보다 먼저 적용되고, 사용자는 평소에 열어 보지 않는다. 공격자 입장에서 좋은 자리다. 실제로 악성코드가 hosts를 고쳐서 은행이나 로그인 페이지 도메인을 가짜 서버 IP로 돌리거나, 백신 업데이트 서버 도메인을 0.0.0.0으로 막아 업데이트를 끊는 수법이 오래 쓰였다.

이걸 막는 1차 방어선은 파일 권한이다. 관리자 권한 없이는 hosts를 쓸 수 없으니, 일반 권한으로 도는 악성코드는 손댈 수 없다. 2차 방어선은 HTTPS다. hosts로 은행 도메인을 가짜 서버에 돌려도, 가짜 서버는 그 도메인의 정상 인증서를 갖고 있지 않아서 브라우저가 경고를 띄운다. 그래서 공격자는 hosts 변조와 함께 자기 루트 인증서를 시스템에 설치하려 한다. 둘 다 관리자 권한이 필요하니, 결국 지켜야 할 건 관리자 권한이다. 윈도 디펜더 같은 보안 프로그램도 특정 도메인을 돌리는 hosts 수정을 위협으로 표시하기도 한다.

내 hosts 파일을 가끔 열어 보는 것만으로도 이상한 줄을 찾을 수 있다. 기본 파일은 주석 몇 줄과 localhost 줄 정도가 전부다. 직접 넣은 기억이 없는 은행·포털·보안 업체 도메인이 있다면 의심해야 한다.

## 가장 앞에 있는 한 줄짜리 DNS

hosts 파일은 운영체제가 DNS보다 먼저 보는, 내 컴퓨터에만 적용되는 이름표다. 이름을 IP로 바꾸는 일만 하고, 포트나 패턴은 모른다. 고쳤는데 반영이 안 될 때는 파일보다 앞에 있는 브라우저 캐시, 열린 연결, OS 캐시, 프록시를 차례로 의심하면 대부분 풀린다.

## 면접에서 나올 만한 질문

### hosts 파일이 무엇이고, DNS와 어떤 관계인가요?

이름과 IP의 짝을 적은 로컬 텍스트 파일로, 운영체제가 이름을 해석할 때 보통 DNS보다 먼저 확인한다. 여기 이름이 있으면 DNS에 묻지 않는다. DNS 이전 시절 중앙에서 배포하던 HOSTS.TXT의 흔적이고, 지금은 내 컴퓨터에만 적용되는 예외 목록 역할을 한다.

### 이름 해석 순서는 어떻게 정해지나요?

리눅스는 `/etc/nsswitch.conf`의 `hosts:` 줄이 정하고, 보통 `files dns`라서 hosts 파일이 먼저다. 맥은 mDNSResponder가, 윈도는 DNS Client 서비스가 hosts를 읽어 캐시에 반영한다. 그 앞에 브라우저 자체 캐시와 OS 캐시가 있고, dig나 nslookup처럼 DNS 서버에 직접 묻는 도구는 이 순서를 따르지 않는다.

### hosts를 수정했는데 반영되지 않으면 무엇을 확인하나요?

먼저 브라우저의 DNS 캐시와 이미 열린 keep-alive 연결을 의심한다. 크롬은 net-internals에서 host cache를 비우고 socket pool을 정리한다. 그다음 OS 캐시를 비우고(`ipconfig /flushdns`, `resolvectl flush-caches` 등), 확인은 nslookup이 아니라 getent 같은 OS 해석 경로로 한다. 프록시를 쓰는 환경이면 프록시가 이름을 풀기 때문에 hosts가 적용되지 않는다.

### DNS를 바꾸기 전에 새 서버를 검증하려면 어떻게 하나요?

내 PC의 hosts에 도메인과 새 서버 IP를 적고 실제 도메인으로 접속한다. 그러면 SNI와 Host 헤더가 실제와 같아서 인증서와 가상 호스트 설정까지 검증된다. 요청 하나만 확인하려면 `curl --resolve`로 hosts를 건드리지 않고 같은 효과를 낼 수 있다. 끝나면 hosts 줄을 지워야 나중에 내 PC만 다른 서버로 가는 일을 막는다.

### hosts 파일로 포트나 와일드카드를 지정할 수 없는 이유는요?

hosts는 이름을 주소로 바꾸는 역할만 하고, 이름 해석 함수가 돌려주는 것도 주소 목록뿐이라 포트를 실을 자리가 없다. 포트는 URL이나 스킴 기본값이 정한다. 형식에 패턴 문법도 없어서 정확히 같은 이름만 맞춘다. 포트는 Host 헤더로 나눠 주는 리버스 프록시로, 와일드카드는 dnsmasq 같은 로컬 DNS나 `.localhost`로 해결한다.

### 브라우저에서 DoH를 켜면 hosts 파일이 무시되나요?

크롬은 보안 DNS를 켜도 내장 리졸버가 hosts 파일을 먼저 확인하므로 hosts가 적용된다. 파이어폭스는 기본 설정에서 hosts를 존중하지만 버전과 DoH 모드에 따라 달랐던 적이 있어서, 문제가 생기면 보안 DNS를 끄고 비교해 본다. 브라우저마다 구현이 다르니 단정하기보다 확인하는 게 맞다.

### hosts 파일은 어떤 보안 위험이 있나요?

DNS보다 먼저 적용되고 잘 들여다보지 않는 파일이라, 악성코드가 은행 도메인을 가짜 서버로 돌리거나 백신 업데이트 도메인을 막는 데 써 왔다. 수정에 관리자 권한이 필요하고, HTTPS를 쓰면 가짜 서버가 정상 인증서를 내밀 수 없어 경고가 뜬다는 게 방어선이다. 그래서 공격자는 루트 인증서 설치까지 노리는데, 이것도 관리자 권한이 있어야 한다.
