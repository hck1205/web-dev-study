<EasyIntro>
  편집 화면에서 원본을 지키려고 사본을 만들어 고쳤는데, 취소를 눌러도 원본의 안쪽 값이 이미 바뀌어 있는 일이 있다. 사본을 만든 건 맞지만 한 층짜리 사본이었기 때문이다. 점 세 개로 펼쳐 복사하면 바깥 그릇만 새로 만들고, 안에 든 객체나 배열은 원본과 같은 것을 함께 가리킨다.

  이렇게 바깥만 새로 만드는 것을 얕은 복사, 안쪽까지 전부 새로 만드는 것을 깊은 복사라고 한다. 규칙은 하나다. 펼치기 한 번에 한 층씩 새로 생기니, 사본의 칸에 새 값을 넣는 건 안전하고 칸을 따라 들어가 그 안을 고치면 원본도 고쳐진다.

  깊은 복사가 필요하면 structuredClone을 쓰는데, 함수나 클래스 정보 같은 것은 따라오지 않고 데이터가 크면 수십 밀리초가 걸린다. 리액트에서는 바뀐 길만 새로 만드는 게 기본이고, 통째로 깊게 복사하면 무엇이 바뀌었는지 알 수 없어서 화면 전체를 다시 그리게 된다.
</EasyIntro>

메뉴 편집 화면이 있다. 목록에서 메뉴를 고르면 편집 폼이 뜨고, 폼은 원본을 건드리지 않으려고 사본을 만들어 고친다. 저장을 누르면 사본을 서버에 보내고, 취소를 누르면 사본을 버린다. 그런데 샷을 하나 추가하고 취소했더니 목록의 메뉴가 이미 "샷 2"로 바뀌어 있었다.

```js
const item = { id: 7, name: "라떼", options: { size: "M", shots: 1 }, tags: ["hot"] };
const draft = { ...item };       // 편집용 사본
draft.name = "바닐라 라떼";
draft.options.shots = 2;
draft.tags.push("sweet");
// 사용자가 취소를 눌렀다
console.log(item);
console.log(draft.options === item.options, draft.tags === item.tags);
```

```text
{
  id: 7,
  name: '라떼',
  options: { size: 'M', shots: 2 },
  tags: [ 'hot', 'sweet' ]
}
true true
```

이름은 원본이 지켜졌는데 샷과 태그는 원본까지 바뀌었다. 사본을 만든 건 맞지만 한 층짜리 사본이었다. 이 글은 "사본이 어디까지 따로인가"를 재는 글이다. 복사 방법마다 몇 층까지 새로 만드는지, `structuredClone`이 무엇을 바꿔 놓는지, 큰 데이터를 복사하면 얼마나 걸리는지, 그리고 React 코드에서 복사가 어디서 문제를 만드는지를 Node 22로 직접 돌려 보며 본다.

이 주제의 다른 글도 있다. 변수 칸에 참조가 들어 있다는 기초는 [원시값과 참조값](/posts/js-primitive-vs-reference)에, JSON 왕복과 `structuredClone`이 `Date`·`Map`·`BigInt`에서 무엇을 잃는지 비교한 표와 깊은 복사 함수를 직접 만드는 연습은 [프로토타입 패턴](/posts/pattern-prototype)에 있다. 여기서는 그 표를 반복하지 않는다.

## 사본의 첫 층만 따로다

`{ ...item }`은 새 객체를 하나 만들고 `item`의 속성 칸을 하나씩 베낀다. 칸에 든 게 문자열이나 숫자면 값이 그대로 복사되고, 객체면 그 객체를 가리키는 참조가 복사된다. 그래서 `draft.name`은 따로지만 `draft.options`와 `item.options`는 같은 객체를 가리킨다. 이렇게 바깥 그릇만 새로 만들고 안쪽은 같이 쓰는 복사를 얕은 복사라고 한다. 안쪽까지 전부 새로 만드는 것은 깊은 복사다.

규칙은 하나다. 사본의 칸에 새 값을 넣는 건 안전하고, 사본의 칸을 따라 들어가 그 안을 고치는 건 원본을 고친다. `draft.name = ...`은 칸을 바꿨고, `draft.options.shots = ...`는 칸을 따라 들어갔다. 점이 두 번 이상 찍힌 대입이나 `push` 같은 메서드 호출이 보이면 그 객체가 누구와 공유되는지 확인해야 한다.

편집 폼이라면 고칠 수 있는 깊이까지 새로 만들어 두면 된다. `{ ...item, options: { ...item.options }, tags: [...item.tags] }`로 두 번째 층까지 복사하거나, 폼이 다루는 데이터가 작고 단순하면 `structuredClone(item)`으로 통째로 복사한다.

## 복사 방법마다 몇 층을 새로 만드나

배열을 복사하는 방법이 여럿인데, 이름이 달라도 깊이는 같은 경우가 많다. 주문 배열 하나를 여러 방법으로 복사하고, 층마다 원본과 같은 객체인지 비교했다.

```js
const orders = [{ id: 1, items: [{ sku: "A", qty: 1 }] }];
const ways = {
  "[...arr]": (a) => [...a],
  "arr.slice()": (a) => a.slice(),
  "Array.from(arr)": (a) => Array.from(a),
  "[].concat(arr)": (a) => [].concat(a),
  "arr.map(o => ({...o}))": (a) => a.map((o) => ({ ...o })),
  "JSON.parse(stringify)": (a) => JSON.parse(JSON.stringify(a)),
  "structuredClone": (a) => structuredClone(a),
};
for (const [name, copy] of Object.entries(ways)) {
  const c = copy(orders);
  console.log(
    name.padEnd(24),
    "배열", c === orders ? "공유" : "새로",
    "| 주문", c[0] === orders[0] ? "공유" : "새로",
    "| items", c[0].items === orders[0].items ? "공유" : "새로",
  );
}
```

```text
[...arr]                 배열 새로 | 주문 공유 | items 공유
arr.slice()              배열 새로 | 주문 공유 | items 공유
Array.from(arr)          배열 새로 | 주문 공유 | items 공유
[].concat(arr)           배열 새로 | 주문 공유 | items 공유
arr.map(o => ({...o}))   배열 새로 | 주문 새로 | items 공유
JSON.parse(stringify)    배열 새로 | 주문 새로 | items 새로
structuredClone          배열 새로 | 주문 새로 | items 새로
```

### fill로 만든 칸은 전부 같은 객체다

복사는 아니지만 같은 원리로 자주 터지는 코드가 있다. 2차원 배열이나 체크 목록을 `fill`로 초기화하는 코드다.

```js
const grid = new Array(3).fill([]);
grid[0].push("x");
console.log(grid);
const rows = Array(2).fill({ done: false });
rows[0].done = true;
console.log(rows, rows[0] === rows[1]);
const fixed = Array.from({ length: 3 }, () => []);  // 칸마다 새 배열을 만든다
fixed[0].push("x");
console.log(fixed);
```

```text
[ [ 'x' ], [ 'x' ], [ 'x' ] ]
[ { done: true }, { done: true } ] true
[ [ 'x' ], [], [] ]
```

## structuredClone이 바꿔 놓는 것들

깊은 복사가 필요할 때 요즘은 `structuredClone`을 먼저 떠올린다. 브라우저(크롬 98, 파이어폭스 94, 사파리 15.4부터)와 Node 17부터 전역 함수로 있다. 원래는 `postMessage`로 다른 스레드에 값을 보낼 때, IndexedDB에 값을 저장할 때 쓰던 구조화된 복제 알고리즘(structured clone algorithm)을 직접 부를 수 있게 꺼내 놓은 것이다. 그래서 동작도 "저장하고 다시 꺼낸 것"에 가깝다. `Date`와 `Map`을 살린다는 것은 [프로토타입 패턴](/posts/pattern-prototype)에서 봤으니, 여기서는 사본이 원본과 달라지는 부분을 본다.

```js
const sym = Symbol("trace");
const src = {
  get total() { return 18200; },   // getter
  [sym]: "abc",                    // 심볼 키
  shared: null,
};
Object.defineProperty(src, "internal", { value: 1, enumerable: false }); // 열거 불가
const style = { color: "red" };
src.a = style; src.b = style;      // 같은 객체를 두 곳에서 가리킨다
Object.freeze(src.a);
const c = structuredClone(src);
console.log(c);
console.log("getter?", Object.getOwnPropertyDescriptor(c, "total"));
console.log("shared kept:", c.a === c.b, "frozen kept:", Object.isFrozen(c.a));
```

```text
{
  total: 18200,
  shared: null,
  a: { color: 'red' },
  b: { color: 'red' }
}
getter? { value: 18200, writable: true, enumerable: true, configurable: true }
shared kept: true frozen kept: false
```

getter는 복사하는 순간 불려 그 값이 일반 속성으로 박혔다. 심볼 키와 열거 불가 속성은 사라졌다. 얼려 둔 객체는 사본에서 다시 열렸다. 속성 설명자는 하나도 따라오지 않고, 사본의 속성은 모두 `writable`, `enumerable`, `configurable`이 `true`다(설명자는 [객체 메서드](/posts/js-object-methods) 참고). 반대로 원본에서 `a`와 `b`가 같은 객체였다는 관계는 사본에서도 유지됐다. 사본의 `a`와 `b`도 서로 같은 하나의 객체다. 아래 그림이 복제 알고리즘이 객체를 하나씩 들르며 "이미 복사한 것"을 기억하는 과정이다.

마지막 단계의 "기억해 둔 짝" 덕분에 순환 참조도 끝없이 돌지 않는다. 클래스 인스턴스는 프로토타입을 잃고 평범한 객체가 되고, 함수나 심볼 값, `Proxy`는 아예 복사하지 못하고 에러를 던진다.

```js
try { structuredClone(new Proxy({}, {})); } catch (e) { console.log(e.name + ": " + e.message); }
try { structuredClone({ el: Symbol("x") }); } catch (e) { console.log(e.name + ": " + e.message); }
```

```text
DataCloneError: #<Object> could not be cloned.
DataCloneError: Symbol(x) could not be cloned.
```

`Proxy`가 에러를 낸다는 점은 실무에서 의외의 곳에서 걸린다. Vue의 반응형 객체나 MobX가 관리하는 객체, Immer가 넘겨주는 초안(draft)은 `Proxy`라서 그대로 `structuredClone`에 넣으면 실패한다. Vue는 `toRaw`, Immer는 `current(draft)`로 그 순간의 일반 객체를 꺼낸 뒤 복사한다. Immer 11에서 초안을 그대로 넣으면 `DataCloneError: #<Object> could not be cloned.`가 났고, `current`를 거치면 복사됐다.

에러 객체는 복사되지만 일부만 살아남는다.

```js
const err = new RangeError("too big", { cause: { limit: 10 } });
err.code = "E_LIMIT";
const ce = structuredClone(err);
console.log(ce instanceof RangeError, ce.name, ce.message, ce.cause, ce.code, typeof ce.stack);
```

```text
true RangeError too big { limit: 10 } undefined string
```

종류, 메시지, `cause`는 따라오는데 직접 붙인 `code`는 빠졌다. 워커에서 난 에러를 메인 스레드로 보내 에러 코드로 분기하는 코드가 이래서 조용히 실패한다. 필요한 필드는 `{ name, message, code }`처럼 일반 객체로 옮겨서 보낸다.

## 큰 데이터를 깊게 복사하면 드는 시간

깊은 복사는 데이터 크기에 비례해서 시간이 든다. 주문 1만 건(고객 정보와 품목 두 개씩, JSON으로 약 1.9MB)을 방법별로 복사해 중앙값을 쟀다. lodash는 4.x의 `cloneDeep`이다.

```js
const cloneDeep = require("lodash/cloneDeep");
const orders = Array.from({ length: 10_000 }, (_, i) => ({
  id: i, status: i % 3 ? "paid" : "pending", memo: "문 앞에 두세요",
  customer: { name: "user" + i, address: { city: "Seoul", zip: "04524" } },
  items: [{ sku: "A" + i, qty: 1, price: 4500 }, { sku: "B" + i, qty: 2, price: 5200 }],
}));
const ways = {
  "[...orders]": (a) => [...a],
  "JSON.parse(stringify)": (a) => JSON.parse(JSON.stringify(a)),
  "structuredClone": (a) => structuredClone(a),
  "lodash cloneDeep": (a) => cloneDeep(a),
};
for (const [name, fn] of Object.entries(ways)) {
  for (let i = 0; i < 3; i++) fn(orders); // 워밍업
  const times = [];
  for (let i = 0; i < 7; i++) { const t = performance.now(); fn(orders); times.push(performance.now() - t); }
  times.sort((a, b) => a - b);
  console.log(name.padEnd(22), "중앙값", times[3].toFixed(2), "ms");
}
```

```text
[...orders]            중앙값 0.05 ms
JSON.parse(stringify)  중앙값 32.67 ms
structuredClone        중앙값 52.78 ms
lodash cloneDeep       중앙값 68.24 ms
```

얕은 복사는 칸 1만 개만 베끼니 0.05ms다. 깊은 복사는 셋 다 수십 ms가 걸렸고, 이 데이터에서는 JSON 왕복이 `structuredClone`보다 빨랐다. 두 번째 실행에서도 29ms, 53ms로 순서가 같았다. 엔진은 JSON 문자열 처리를 오래 최적화해 왔고, `structuredClone`은 더 많은 타입과 공유 참조를 챙기는 대신 그만큼 일을 더 한다. 그렇다고 JSON 왕복을 고르라는 뜻은 아니다. 날짜와 `undefined`를 조용히 망가뜨리는 문제가 속도보다 크다. 숫자는 엔진 버전과 데이터 모양에 따라 바뀌니, 고민될 때는 자기 데이터로 직접 잰다.

화면 기준으로 보면 크기가 감이 온다. 60fps 화면의 한 프레임은 약 16.7ms다. 클릭 한 번에 이 정도 데이터를 깊게 복사하면 그것만으로 두세 프레임이 밀린다. 깊은 복사를 매 렌더나 매 키 입력마다 하면 안 되는 이유다.

lodash `cloneDeep`은 느린 대신 클래스 인스턴스의 프로토타입을 지켜 준다. `structuredClone`에서 `instanceof`가 `false`가 되는 문제가 걸린다면 대안이 된다. 다만 함수는 복사하지 않고 참조를 그대로 둔다.

```js
class Money { constructor(v) { this.v = v; } add(n) { return new Money(this.v + n); } }
const c = cloneDeep({ price: new Money(100) });
console.log(c.price instanceof Money, c.price.add(1));
console.log(structuredClone(new Money(100)) instanceof Money);
```

```text
true Money { v: 101 }
false
```

## React 코드에서 복사가 문제를 만드는 곳

React에서는 복사를 너무 적게 해도, 너무 많이 해도 버그가 난다.

### 모듈에 둔 초깃값을 고치면 다음 화면이 물려받는다

폼의 빈 상태를 상수로 빼 두는 건 흔한 습관이다. 이 상수를 `useState`의 초깃값으로 쓰고 안쪽 배열을 고치면, 상수 자체가 바뀐다. React 19와 jsdom으로 컴포넌트를 띄웠다 닫았다 다시 띄워 봤다.

```jsx
const EMPTY_FORM = { title: "", tags: [] };   // 모듈에 하나뿐인 객체

function TagForm({ name }) {
  const [form, setForm] = useState(EMPTY_FORM);
  useEffect(() => {
    form.tags.push(name);        // 원본 배열을 고치는 실수
    setForm({ ...form });
  }, []);
  return <p>{name}: {form.tags.join(",")}</p>;
}
// first를 그리고, 닫았다가, second를 다시 그린다
```

```text
first: first
second: first,second
EMPTY_FORM: {"title":"","tags":["first","second"]}
```

두 번째로 연 폼에 첫 번째 폼의 태그가 남아 있다. `useState(EMPTY_FORM)`은 객체를 복사하지 않고 그 참조를 상태로 쓴다. `{ ...form }`으로 바깥을 새로 만들어도 `tags`는 여전히 `EMPTY_FORM.tags`다. 컴포넌트가 사라져도 모듈 상수는 남으니 다음 인스턴스가 오염된 값을 받는다. 테스트에서 "혼자 돌리면 통과하는데 같이 돌리면 실패한다"는 증상으로도 나타난다. 고치는 방법은 `setForm({ ...form, tags: [...form.tags, name] })`처럼 원본을 고치지 않는 것이고, 실수를 일찍 잡으려면 상수를 [깊게 얼려](/posts/js-object-methods) 둔다. 초깃값을 함수로 만들어 매번 새 객체를 받게 하는 방법(`useState(() => ({ title: "", tags: [] }))`)도 있다.

### 전부 깊게 복사하면 memo가 일을 못 한다

반대 방향의 실수는 "불변성을 지키려면 깊게 복사하면 된다"는 생각에서 나온다. 주문 세 개를 `React.memo`로 감싼 행에 그리고, 2번 주문의 상태만 바꿨다. 한 번은 `structuredClone`으로 통째로 복사한 뒤 고치고, 한 번은 바뀐 주문만 새로 만들었다.

```js
update = () => setOrders((prev) => {
  if (mode === "deep") {
    const next = structuredClone(prev);      // 전부 새로 만든다
    next[1].status = "paid";
    return next;
  }
  return prev.map((o) => (o.id === 2 ? { ...o, status: "paid" } : o)); // 바뀐 것만 새로
});
```

```text
deep  2번 주문만 바꿨을 때 다시 그린 행: [ 1, 2, 3 ]
path  2번 주문만 바꿨을 때 다시 그린 행: [ 2 ]
```

깊은 복사는 내용이 그대로인 1번과 3번 주문도 새 객체로 만든다. `memo`는 props를 참조로 비교하니 세 행을 모두 다시 그렸다. 바뀐 주문만 새로 만들면 나머지 두 행은 같은 객체라 건너뛴다. 원본을 지키는 것만 보면 둘 다 맞지만, 깊은 복사는 "무엇이 바뀌었는지"라는 정보를 지워 버린다. React가 다시 그릴지를 정하는 규칙은 [React는 언제 다시 그리나](/posts/react-rerender)에 있다.

그래서 React 상태에서 깊은 복사가 맞는 자리는 좁다. 서버에서 받은 데이터를 편집용 초안으로 떼어 낼 때, 되돌리기 기능을 위해 스냅숏을 남길 때처럼 "원본과 완전히 끊어야 하는" 경계에서 한 번 쓴다. 상태를 바꿀 때마다 쓰는 도구가 아니다.

## 공유된 객체를 찾는 법

복사 버그를 의심할 때 확인하는 방법은 단순하다. 원본과 사본의 같은 경로를 `===`로 비교한다. 개발자 도구 콘솔에서 `draft.options === item.options`를 찍으면 바로 답이 나온다. 테스트에서는 Jest·Vitest의 `expect(copy.options).not.toBe(original.options)`로 같은 것을 확인한다. `toBe`는 참조를 비교하고, `toEqual`은 내용을 비교하니 이 경우엔 `toBe`를 써야 한다.

경로가 많으면 하나씩 비교하기 어렵다. 원본과 사본을 같이 훑으며 같은 객체를 가리키는 경로를 모두 찾는 함수를 만들어 보자. 지금 코드는 첫 층만 보고, `null`을 객체로 착각한다. 모든 테스트가 통과하도록 고쳐 보자.

## 면접에서 나올 만한 질문

### 얕은 복사와 깊은 복사의 차이는?

얕은 복사는 바깥 객체만 새로 만들고 속성 칸에 든 참조를 그대로 베끼니 안쪽 객체는 원본과 같이 쓴다. 깊은 복사는 안쪽 객체까지 끝까지 새로 만든다. 그래서 얕은 사본의 칸에 새 값을 넣는 건 안전하지만, 칸을 따라 들어가 안쪽을 고치면 원본도 바뀐다. 전개, `Object.assign`, `slice`, `Array.from`은 모두 얕은 복사다.

### `[...arr]`와 `arr.slice()`, `Array.from(arr)`의 차이는?

복사 깊이는 셋 다 같다. 배열 한 층만 새로 만들고 원소가 객체면 참조를 같이 쓴다. 차이는 입력에 있다. 전개와 `Array.from`은 이터러블(Set, NodeList 등)을 받고, `Array.from`은 유사 배열(`length`가 있는 객체)과 변환 함수도 받는다. `slice`는 배열 메서드라 배열에만 쓴다.

### structuredClone으로 복사하면 잃는 것은?

getter는 복사하는 순간의 값으로 바뀌고, 심볼 키와 열거 불가 속성은 빠지며, 속성 설명자와 `freeze` 상태도 따라오지 않는다. 클래스 인스턴스는 프로토타입을 잃어 일반 객체가 되고, 에러 객체는 이름·메시지·`cause`만 남는다. 함수, 심볼 값, `Proxy`는 `DataCloneError`를 던진다. 대신 `Date`, `Map`, `Set`, 순환 참조, 공유 참조는 지킨다.

### JSON 왕복과 structuredClone 중 어느 것이 빠른가?

Node 22에서 주문 1만 건을 복사했을 때 JSON 왕복이 약 30ms, `structuredClone`이 약 53ms로 JSON이 빨랐다. 그래도 JSON 왕복은 `Date`를 문자열로, `Map`을 빈 객체로 바꾸고 `undefined`를 지우니 데이터가 순수 JSON일 때만 고려한다. 엔진과 데이터 모양에 따라 결과가 달라지니 직접 잰다. 둘 다 수십 ms라 렌더마다 부를 만한 비용은 아니다.

### structuredClone의 transfer 옵션은 무엇인가?

`ArrayBuffer` 같은 Transferable 객체를 복사하지 않고 사본 쪽으로 소유권을 넘기는 옵션이다. 8MB 버퍼 복사가 17~36ms 걸릴 때 넘기기는 0.1ms 아래였다. 넘긴 뒤 원본 버퍼는 떨어져 나가 길이가 0이 되고, 쓰면 무시되고 읽으면 `undefined`가 나온다. 워커와 큰 데이터를 주고받을 때 `postMessage`의 두 번째 인자로 같은 일을 한다.

### React 상태를 업데이트할 때마다 structuredClone으로 복사하면 안 되는 이유는?

원본은 지켜지지만 바뀌지 않은 부분까지 모두 새 객체가 돼서 `memo`, `useMemo`, 의존성 배열의 참조 비교가 전부 "바뀌었다"고 판단한다. 실제로 주문 하나만 바꿨는데 memo 행 세 개가 모두 다시 그려졌다. 데이터가 크면 복사 자체도 프레임 하나를 넘긴다. 바뀐 경로만 새로 만들고 나머지는 같이 쓰는 것이 맞다.

### useState 초깃값으로 모듈 상수를 넘길 때 주의할 점은?

`useState`는 초깃값을 복사하지 않고 그 참조를 상태로 쓴다. 그래서 상태의 안쪽 배열을 `push`로 고치면 모듈 상수가 바뀌고, 다음에 마운트되는 컴포넌트나 다음 테스트가 오염된 초깃값을 받는다. 원본을 고치지 않는 업데이트를 쓰고, 상수를 깊게 얼려 실수를 드러내거나 초깃값을 함수로 만들어 매번 새 객체를 받는다.
