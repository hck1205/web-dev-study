빌드 도구가 패키지를 설치할 때, 스프레드시트가 수식 셀을 다시 계산할 때, 작업 스케줄러가 일을 돌릴 때 모두 같은 질문을 한다. "먼저 끝나야 하는 일"이 있을 때, 모든 일을 끝낼 수 있는 순서가 있나. 셀 A1이 B1을 참조하고 B1이 다시 A1을 참조하면 엑셀은 순환 참조 경고를 띄운다. 그 경고가 이 문제의 답이 `false`인 경우다.

[LeetCode 207. Course Schedule](https://leetcode.com/problems/course-schedule/)은 이 질문을 수강 신청으로 묻는다. 방향 그래프에 사이클(한 바퀴 돌아 제자리로 오는 길)이 있는지 찾는 문제다. 이 글은 매번 전체를 훑으며 들을 과목을 고르는 느린 풀이부터 시작해, 지금 길만 기억하는 DFS가 왜 지수 시간이 되는지, 세 가지 색 DFS, 칸의 알고리즘(진입 차수 BFS), 재귀 없는 DFS, 그리고 자주 떠올리지만 틀리는 유니온 파인드까지 본다. 사이클 찾기와 위상 정렬의 원리는 [그래프와 BFS·DFS 글](/posts/ds-graph-bfs-dfs)에서 한 번 다뤘다. 여기서는 그 원리를 이 문제에 맞춰 풀이마다 따져 보고, 언어별로 어디서 막히는지 재 본다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 선수 과목이 꼬여 있지 않은가

과목은 `0`부터 `numCourses - 1`까지 번호가 붙어 있다. `prerequisites`의 쌍 `[a, b]`는 "a를 들으려면 b를 먼저 들어야 한다"는 뜻이다. 모든 과목을 들을 수 있으면 `true`, 아니면 `false`를 돌려준다.

풀이에 영향을 주는 조건은 이렇다.

- 과목은 최대 2,000개, 쌍은 최대 5,000개다. O(V + E)면 몇 천 번이고, O(V · E)도 천만 번이라 간신히 된다. 지수 시간은 안 된다.
- 쌍의 방향이 `[나중, 먼저]`다. 그래프로 그릴 때 선은 `b → a`(먼저 들은 과목에서 그다음 과목으로)로 긋는 게 생각하기 편하다. 이 방향을 헷갈려도 사이클 여부는 같지만, 순서를 돌려주는 [Course Schedule II](/posts/leetcode-course-schedule-ii)에서는 순서가 거꾸로 나온다.
- 같은 쌍은 두 번 나오지 않는다. 선수 관계가 하나도 없는 과목도 있을 수 있다.

이 글의 예시는 과목 여섯 개다.

```text
numCourses = 6
prerequisites = [[1,0], [2,0], [3,1], [3,2], [4,3], [5,2]]

0 → 1 → 3 → 4
 ↘     ↗
   2 → 5          (2는 3과 5의 선수 과목)
```

0을 들으면 1과 2를 들을 수 있다. 3은 1과 2를 모두 들어야 한다. 4는 3 다음, 5는 2 다음이다. 0, 1, 2, 3, 5, 4 순서로 들으면 되니 답은 `true`다.

여기에 `[1, 4]`를 하나 더하면 "1을 들으려면 4를 먼저"가 된다. 그런데 4를 들으려면 3을, 3을 들으려면 1을 먼저 들어야 한다. 1 → 3 → 4 → 1로 고리가 생겨서 셋 중 어느 것도 먼저 들을 수 없다. 답은 `false`다. 이 글에서는 이 두 입력을 "예시"와 "고리 예시"로 부른다.

## 들을 수 있는 과목을 매번 다시 찾는다

사람이 손으로 푸는 방법을 그대로 옮겨 보자. 아직 안 들은 과목 중에서 선수 과목을 다 들은 과목을 모두 찾아 듣는다. 이걸 더 들을 과목이 없을 때까지 반복한다. 끝났을 때 들은 과목 수가 전체와 같으면 `true`다.

```js
function canFinish(numCourses, prerequisites) {
  const taken = new Uint8Array(numCourses);
  let count = 0;
  while (true) {
    const blocked = new Uint8Array(numCourses);
    for (const [a, b] of prerequisites) {
      if (!taken[b]) blocked[a] = 1;        // 아직 안 들은 선수 과목이 있다
    }
    let progress = false;
    for (let c = 0; c < numCourses; c++) {
      if (!taken[c] && !blocked[c]) {       // 지금 들을 수 있는 과목
        taken[c] = 1;
        count++;
        progress = true;
      }
    }
    if (!progress) break;                   // 이번 라운드에 들은 과목이 없다
  }
  return count === numCourses;
}
```

고리 예시에서는 첫 라운드에 0, 둘째 라운드에 2, 셋째 라운드에 5를 듣고, 넷째 라운드에는 1, 3, 4가 모두 막혀 아무것도 못 듣는다. 들은 과목이 셋뿐이라 `false`다.

라운드마다 쌍 전체를 훑는다. 과목이 한 줄로 이어진 입력(0 → 1 → 2 → ...)에서는 라운드마다 한 과목만 들으니 V번 라운드가 돈다. 시간 O(V · E), 공간 O(V)다. 과목 2,000개가 한 줄로 이어진 입력에서 31ms가 걸렸다. 이 문제 크기에서는 통과하지만, 과목이 10만 개면 100억 번이 된다.

낭비는 매 라운드 쌍 전체를 다시 보는 데 있다. 과목 하나를 들었을 때 바뀌는 건 그 과목을 기다리던 과목들뿐인데, 상관없는 쌍까지 매번 다시 확인한다. 이 생각은 뒤에서 칸의 알고리즘으로 고친다. 그 전에 다른 방향, 고리를 직접 찾는 방법부터 보자.

## 지금 걷는 길만 기억하면 지수 시간이 된다

고리가 있다는 건 어떤 과목에서 출발해 선을 따라가다 같은 과목으로 돌아온다는 뜻이다. 그러니 과목마다 DFS(깊이 우선 탐색, 한 길을 끝까지 가 본 뒤 돌아오는 탐색)를 하면서, 지금 걷고 있는 길 위의 과목을 표시해 둔다. 다음 과목이 이미 길 위에 있으면 고리다. 길에서 빠져나올 때는 표시를 지운다.

```js
function canFinish(numCourses, prerequisites) {
  const graph = Array.from({ length: numCourses }, () => []);
  for (const [a, b] of prerequisites) graph[b].push(a); // b를 들으면 a로 갈 수 있다
  const onPath = new Uint8Array(numCourses);            // 지금 걷는 길 위의 과목
  const hasCycle = (u) => {
    if (onPath[u]) return true;     // 길 위로 돌아왔다: 고리
    onPath[u] = 1;
    for (const v of graph[u]) if (hasCycle(v)) return true;
    onPath[u] = 0;                  // 길에서 빠져나온다
    return false;
  };
  for (let c = 0; c < numCourses; c++) if (hasCycle(c)) return false;
  return true;
}
```

답은 맞는다. 그런데 고리가 없는 그래프에서 이 풀이는 같은 과목을 끝없이 다시 탐색한다. 과목 3에서 고리가 없다는 걸 확인했어도, 다른 길로 3에 다시 오면 3 아래를 처음부터 다시 훑는다. 3에 오는 길이 1을 거치는 길과 2를 거치는 길 두 개라면 3 아래는 두 번 훑인다.

이게 겹치면 폭발한다. 마름모를 사슬처럼 이어 붙인 그래프를 만들어 보자. 0 → 1, 0 → 2, 1 → 3, 2 → 3이 마름모 하나이고, 3에서 다음 마름모가 시작된다. 마름모가 k개면 처음부터 끝까지 가는 길이 2^k개다. 실제로 재 보면 이렇다.

```text
마름모 수   과목 수   선수 관계   호출 수        시간
   10         31         40        16,299         4ms
   15         46         60       524,168        10ms
   20         61         80    16,777,061       262ms
   22         67         88    67,108,695       955ms
```

과목 67개, 선수 관계 88개짜리 입력에 1초가 걸렸다. 마름모 하나를 더할 때마다 두 배가 되니, 문제 조건(과목 2,000개)에서는 끝나지 않는다. 같은 입력을 다음 풀이로 돌리면 1ms도 안 걸린다. 이 풀이에 빠진 건 "이 과목 아래에는 고리가 없다고 이미 확인했다"는 기억이다.

마름모는 억지로 만든 모양이 아니다. 패키지 의존성에서는 여러 패키지가 같은 라이브러리를 쓰고, 그 라이브러리가 다시 공통 유틸리티를 쓰는 일이 흔하다. 의존성 그래프는 마름모투성이라, 확인한 곳을 기억하지 않는 검사기는 실제 저장소에서 금방 멈춘다.

같은 사정은 [동적 계획법](/posts/dynamic-programming)의 메모와 닮았다. 한 번 답을 구한 칸은 다시 계산하지 않는다는 생각을, 여기서는 "고리 없음"이라는 답에 적용한다.

## 세 가지 색으로 칠하는 DFS

과목의 상태를 둘이 아니라 셋으로 나눈다.

- 흰색(0): 아직 안 가 봤다.
- 회색(1): 지금 걷는 길 위에 있다. 이 과목 아래를 탐색하는 중이다.
- 검은색(2): 이 과목 아래를 다 훑었고 고리가 없었다.

회색 과목을 다시 만나면 고리다. 검은색 과목을 만나면 이미 안전하다고 확인한 곳이라 바로 돌아온다. 앞의 풀이와 다른 건 길에서 빠져나올 때 표시를 지우지 않고 검은색으로 바꾼다는 한 줄뿐이다.

```js
function canFinish(numCourses, prerequisites) {
  const graph = Array.from({ length: numCourses }, () => []);
  for (const [a, b] of prerequisites) graph[b].push(a);
  const state = new Uint8Array(numCourses); // 0 흰색, 1 회색(길 위), 2 검은색(끝남)
  const hasCycle = (u) => {
    if (state[u] === 1) return true;   // 지금 길 위로 돌아왔다: 고리
    if (state[u] === 2) return false;  // 이미 안전하다고 확인했다
    state[u] = 1;
    for (const v of graph[u]) if (hasCycle(v)) return true;
    state[u] = 2;                      // 아래를 다 봤다. 다시 볼 필요 없다
    return false;
  };
  for (let c = 0; c < numCourses; c++) if (hasCycle(c)) return false;
  return true;
}
```

왜 회색과 검은색을 나눠야 할까. 상태를 "방문함" 하나로 합치면, 고리 없이 두 길이 한 과목에서 만나는 경우(마름모의 아래 꼭짓점)를 고리로 잘못 본다. 1을 거쳐 3을 방문했고, 나중에 2를 거쳐 다시 3에 오면 3은 "방문함"이다. 그런데 3은 지금 길 위에 있지 않으니 고리가 아니다. 방향 그래프에서 "이미 본 곳을 다시 만났다"와 "지금 길 위로 돌아왔다"는 다르다. 무방향 그래프에서는 둘을 구분하지 않아도 되는 것과 대비된다.

과목마다 흰색에서 회색, 회색에서 검은색으로 한 번씩만 바뀌고, 선마다 한 번씩 따라간다. 시간 O(V + E), 공간은 인접 리스트 O(V + E)와 재귀 깊이 O(V)다.

이 재귀 깊이가 언어에 따라 문제가 된다. 과목 2,000개가 한 줄로 이어진 입력은 문제 조건 안이다. JavaScript는 2,000단계 재귀를 문제없이 버텼다. 과목 10만 개짜리 사슬에서는 `RangeError`가 났다. Python은 기본 재귀 한도가 1,000이라, 문제 조건 안의 2,000개 사슬에서 `RecursionError`가 났다. Python으로 DFS를 쓴다면 `sys.setrecursionlimit`을 올리거나, 재귀를 쓰지 않는 다음 두 풀이 중 하나를 쓴다.

## 선수 과목 수를 세어 두는 칸의 알고리즘

처음의 "들을 수 있는 과목을 매번 다시 찾는" 풀이로 돌아가자. 낭비는 매번 쌍 전체를 다시 훑는 데 있었다. 대신 과목마다 "아직 안 들은 선수 과목 수"를 세어 둔다. 이 숫자를 진입 차수(그 점으로 들어오는 선의 수)라고 한다. 진입 차수가 0인 과목은 지금 바로 들을 수 있으니 큐에 넣는다. 큐에서 과목을 하나 꺼내 들을 때마다, 그 과목을 기다리던 과목들의 진입 차수를 하나씩 줄인다. 0이 된 과목은 큐에 넣는다.

이 방법을 1962년에 발표한 사람의 이름을 따 칸(Kahn)의 알고리즘이라고 부른다. 과목을 꺼낸 순서가 그대로 위상 정렬(모든 선이 앞에서 뒤로 향하도록 점을 한 줄로 세운 순서)이다.

```js
function canFinish(numCourses, prerequisites) {
  const graph = Array.from({ length: numCourses }, () => []);
  const indeg = new Int32Array(numCourses);     // 아직 안 들은 선수 과목 수
  for (const [a, b] of prerequisites) {
    graph[b].push(a);                           // b를 들으면 a의 선수 과목 하나가 풀린다
    indeg[a]++;
  }
  const queue = [];
  for (let c = 0; c < numCourses; c++) if (indeg[c] === 0) queue.push(c);
  let taken = 0;
  for (let head = 0; head < queue.length; head++) {
    const u = queue[head];
    taken++;                                    // u를 듣는다
    for (const v of graph[u]) {
      if (--indeg[v] === 0) queue.push(v);      // 마지막 선수 과목이 풀린 순간
    }
  }
  return taken === numCourses;                  // 못 들은 과목이 남았으면 고리가 있다
}
```

고리가 있으면 왜 과목이 남을까. 고리 위의 과목들은 서로가 서로의 선수 과목이라, 고리 안의 어떤 과목도 진입 차수가 0이 되지 못한다. 고리 바깥에서 아무리 과목을 들어도 고리 안의 선 하나는 늘 남는다. 반대로 고리가 없으면 진입 차수가 0인 과목이 늘 하나는 있다. 들을 수 있는 과목이 하나도 없다면, 남은 과목마다 안 들은 선수 과목이 있고, 그 선수 과목을 거꾸로 따라가다 보면 과목 수가 유한하니 언젠가 같은 과목을 다시 만나 고리가 생기기 때문이다.

아래 그림은 고리 없는 예시를 이 풀이로 따라간 것이다. 초록 칸이 들은 과목, 아래 칸이 큐다.

### Python과 Java로 쓰면

Python은 재귀 한도 걱정이 없는 이 풀이가 특히 맞다. 앞의 세 색 DFS를 Python 재귀로 쓰면 2,000개 사슬에서 멈췄다.

```python
from collections import deque
from typing import List


def can_finish(num_courses: int, prerequisites: List[List[int]]) -> bool:
    graph = [[] for _ in range(num_courses)]  # b -> a: b를 들으면 a의 선수 과목 하나가 풀린다
    indeg = [0] * num_courses                 # 아직 안 들은 선수 과목 수
    for a, b in prerequisites:
        graph[b].append(a)
        indeg[a] += 1
    queue = deque(c for c in range(num_courses) if indeg[c] == 0)
    taken = 0
    while queue:
        u = queue.popleft()
        taken += 1
        for v in graph[u]:
            indeg[v] -= 1
            if indeg[v] == 0:   # 마지막 선수 과목이 풀린 순간 들을 수 있다
                queue.append(v)
    return taken == num_courses


dag = [[1, 0], [2, 0], [3, 1], [3, 2], [4, 3], [5, 2]]
print(can_finish(6, dag), can_finish(6, dag + [[1, 4]]))
```

`[[]] * num_courses`로 인접 리스트를 만들면 빈 리스트 하나를 모든 과목이 나눠 써서, 한 과목에 선을 넣으면 모든 과목에 들어간다. 컴프리헨션으로 과목마다 새 리스트를 만든다.

Java는 인접 리스트를 `List<List<Integer>>`로 둔다. 과목 수가 정해져 있으니 `int[][]` 배열 두 번 훑기(먼저 개수를 세고 나서 채우기)로 박싱을 없앨 수도 있지만, 이 크기에서는 차이가 작다.

```java
import java.util.*;

class Solution {
    public boolean canFinish(int numCourses, int[][] prerequisites) {
        List<List<Integer>> graph = new ArrayList<>();
        for (int i = 0; i < numCourses; i++) graph.add(new ArrayList<>());
        int[] indeg = new int[numCourses];            // 아직 안 들은 선수 과목 수
        for (int[] p : prerequisites) {
            graph.get(p[1]).add(p[0]);                // p[1]을 들어야 p[0]을 들을 수 있다
            indeg[p[0]]++;
        }
        ArrayDeque<Integer> queue = new ArrayDeque<>();
        for (int c = 0; c < numCourses; c++) if (indeg[c] == 0) queue.add(c);
        int taken = 0;
        while (!queue.isEmpty()) {
            int u = queue.poll();
            taken++;
            for (int v : graph.get(u)) {
                if (--indeg[v] == 0) queue.add(v);   // 마지막 선수 과목이 풀렸다
            }
        }
        return taken == numCourses;
    }
}
```

## 큐 대신 스택이나 힙을 써도 된다

칸의 알고리즘에서 큐가 하는 일은 "지금 들을 수 있는 과목"을 모아 두는 것뿐이다. 그중 무엇을 먼저 꺼내든 진입 차수가 0인 과목만 꺼내니 선수 관계를 어기지 않는다. 그래서 큐를 스택으로 바꿔도 이 문제의 답은 같고, 나오는 순서만 달라진다. 예시에서 세 가지로 꺼내 보면 이렇다.

```text
큐 (먼저 들어온 것부터)       0, 1, 2, 3, 5, 4
스택 (나중에 들어온 것부터)   0, 2, 5, 1, 3, 4
최소 힙 (번호가 작은 것부터)  0, 1, 2, 3, 4, 5
```

셋 다 올바른 위상 정렬이다. 위상 정렬은 보통 하나로 정해지지 않는다. 그래서 순서를 돌려주는 문제는 "아무 순서나 하나"를 받는 경우가 많고, "가능한 순서 중 사전순으로 가장 앞선 것"을 요구하면 최소 힙을 쓴다. 그때는 꺼낼 때마다 O(log V)가 붙어 O((V + E) log V)가 된다.

실무에서도 이 차이가 드러난다. 빌드 도구가 모듈을 병렬로 빌드할 때는 "지금 준비된 것"을 한꺼번에 일꾼들에게 나눠 준다. 큐에 있는 과목을 한 학기에 다 듣는 것과 같은 그림이다. 순서가 실행마다 달라지면 로그를 비교하기 어려우니, 결과를 재현해야 하는 도구는 준비된 것들 사이에서 이름순 같은 고정 규칙으로 고른다.

## 재귀 없이 세 가지 색을 칠하려면

DFS의 장점(고리를 찾는 순간 바로 멈추고, 고리가 어디인지 알 수 있다)을 살리면서 재귀를 피하고 싶다면 스택을 직접 쓴다. 까다로운 건 "아래를 다 봤다"는 순간을 알아내는 것이다. 재귀에서는 반복문이 끝나는 자리가 그 순간이었다. 스택에서는 과목마다 "다음에 볼 이웃의 번호"를 따로 들고 있다가, 이웃을 다 보면 검은색으로 바꾸고 스택에서 뺀다.

```js
function canFinish(numCourses, prerequisites) {
  const graph = Array.from({ length: numCourses }, () => []);
  for (const [a, b] of prerequisites) graph[b].push(a);
  const state = new Uint8Array(numCourses);   // 0 흰색, 1 회색, 2 검은색
  const next = new Int32Array(numCourses);    // 과목마다 다음에 볼 이웃의 위치
  for (let s = 0; s < numCourses; s++) {
    if (state[s] !== 0) continue;
    const stack = [s];
    state[s] = 1;
    while (stack.length > 0) {
      const u = stack[stack.length - 1];      // 꺼내지 않고 맨 위를 본다
      if (next[u] < graph[u].length) {
        const v = graph[u][next[u]++];        // 다음 이웃 하나로 내려간다
        if (state[v] === 1) return false;     // 회색: 고리
        if (state[v] === 0) {
          state[v] = 1;
          stack.push(v);
        }
      } else {
        state[u] = 2;                         // 이웃을 다 봤다
        stack.pop();
      }
    }
  }
  return true;
}
```

BFS처럼 이웃을 한꺼번에 스택에 넣고 꺼낼 때 처리하는 방식으로 쓰면, 어떤 과목의 아래를 "다 봤다"는 순간을 알 수 없어서 검은색으로 바꿀 자리가 없다. 이웃을 하나씩 내려가는 이 모양을 지켜야 한다. 스택에는 지금 걷는 길, 즉 회색 과목만 쌓인다는 점이 확인 포인트다. 시간과 공간은 재귀 DFS와 같고, 과목 10만 개짜리 사슬도 43ms에 끝났다.

## 유니온 파인드로는 방향을 알 수 없다

사이클 찾기라면 [유니온 파인드](/posts/ds-union-find)가 떠오를 수 있다. 선마다 두 끝을 합치다가, 이미 같은 묶음인 두 점을 잇는 선이 나오면 사이클이다. [Redundant Connection](/posts/leetcode-redundant-connection)이 그렇게 푼다. 하지만 그건 무방향 그래프 이야기다.

```js
// 틀린 풀이: 방향을 무시하고 묶는다
function canFinish(numCourses, prerequisites) {
  const parent = Array.from({ length: numCourses }, (_, i) => i);
  const find = (x) => (parent[x] === x ? x : (parent[x] = find(parent[x])));
  for (const [a, b] of prerequisites) {
    const ra = find(a), rb = find(b);
    if (ra === rb) return false;   // 이미 이어져 있으면 사이클이라고 본다
    parent[ra] = rb;
  }
  return true;
}
// numCourses 3, [[1,0], [2,0], [2,1]] -> false (정답 true)
```

0 → 1, 0 → 2, 1 → 2는 0, 1, 2 순서로 들으면 되는 정상 입력이다. 방향을 지우면 세 점이 삼각형을 이뤄 사이클처럼 보인다. 유니온 파인드는 "이어져 있다"만 알고 "어느 쪽으로"를 모른다. 예시 그래프에서도 마름모(0 → 1 → 3, 0 → 2 → 3) 때문에 `false`를 돌려준다. 방향 그래프의 사이클에는 DFS의 색이나 진입 차수가 필요하다.

## 여섯 풀이를 과목 수로 고르면

V는 과목 수, E는 선수 관계 수다.

| 풀이 | 시간 | 추가 공간 | 언제 고르나 |
|---|---|---|---|
| 들을 과목을 매번 다시 찾기 | O(V · E) | O(V) | 손으로 푸는 생각 그대로. 작은 입력 |
| 지금 길만 기억하는 DFS | 최악 지수 시간 | O(V) | 쓰지 않는다. 마름모 사슬에서 폭발한다 |
| 세 색 재귀 DFS | O(V + E) | O(V + E) | 고리 위치가 필요할 때. Python은 재귀 한도에 걸린다 |
| 칸의 알고리즘 | O(V + E) | O(V + E) | 기본 답. 재귀가 없고 순서도 함께 나온다 |
| 세 색 스택 DFS | O(V + E) | O(V + E) | DFS가 필요한데 그래프가 깊을 때 |
| 유니온 파인드 | O(E · α(V)) | O(V) | 틀린다. 방향을 모른다 |

## 방향을 뒤집고, 회색을 빼먹고

가장 흔한 실수는 세 색을 두 색으로 줄이는 것이다.

```js
const seen = new Uint8Array(numCourses);
const hasCycle = (u) => {
  if (seen[u]) return true;          // 한 번이라도 본 과목이면 고리라고 본다
  seen[u] = 1;
  for (const v of graph[u]) if (hasCycle(v)) return true;
  return false;
};
// 글의 예시 -> false (정답 true)
```

0 → 1 → 3을 훑고 나서 0 → 2 → 3으로 다시 3에 오면, 3은 이미 본 과목이라 고리로 판정한다. 사실 더 단순한 입력에서도 틀린다. 선이 하나뿐인 `[[1, 0]]`도 `false`가 나온다. 0에서 1까지 훑고 나면, 바깥 반복이 1에서 다시 시작할 때 1이 이미 본 과목이라서다. 무방향 그래프의 "방문 표시" 습관을 그대로 가져오면 이렇게 된다. 반대로 길에서 나올 때 표시를 지우기만 하면(앞의 지금 길만 기억하는 DFS) 답은 맞지만 지수 시간이 된다. 회색은 지우고 검은색은 남기는 것, 이 둘을 함께 해야 한다.

두 번째는 쌍의 방향을 뒤집어 진입 차수를 세는 것이다.

```js
for (const [a, b] of prerequisites) { graph[a].push(b); indeg[b]++; } // a -> b로 그었다
```

이 문제의 답(`true`/`false`)은 그대로다. 모든 선을 뒤집어도 고리는 고리이고, 고리가 없는 그래프는 여전히 없다. 그래서 테스트를 통과하고 실수를 모르고 넘어간다. 그런데 순서를 돌려줘야 하는 Course Schedule II에서는 듣는 순서가 정확히 거꾸로 나와서 틀린다. 처음부터 "먼저 듣는 과목에서 나중 과목으로" 선을 긋는 습관을 들인다.

세 번째는 DFS를 과목 0에서만 시작하는 것이다. 테스트의 "떨어진 고리"처럼 0과 이어지지 않은 곳에 고리가 있으면 놓친다. 모든 과목에서 시작하되, 검은색이면 건너뛴다. 칸의 알고리즘은 진입 차수 0인 과목을 처음에 모두 큐에 넣으니 이 실수가 생기지 않는다.

그 밖에 이 문제에서 조심할 것들이다.

- 선수 관계가 없는 입력. 모든 과목의 진입 차수가 0이라 모두 큐에 들어가고 `true`다.
- 자기 자신이 선수 과목인 쌍 `[0, 0]`. 진입 차수가 영원히 1로 남아 `false`다. 세 색 DFS도 자기 자신이 회색이라 바로 고리를 찾는다.
- 같은 쌍이 두 번 들어오는 실제 의존성 데이터라도 답은 맞다. 진입 차수를 두 번 세고, 같은 선을 두 번 따라가며 두 번 줄이기 때문이다.

[Course Schedule II](/posts/leetcode-course-schedule-ii)(210)다. 칸의 알고리즘에서 큐에서 꺼낸 순서를 배열에 모으면 그대로 답이다. 고리가 있으면 빈 배열을 돌려준다. 세 색 DFS라면 검은색이 되는 순서를 모아 뒤집는다. 과목은 아래가 다 끝나야 검은색이 되니, 검은색이 된 순서는 "나중 과목부터"다.

### 한 학기에 여러 과목을 들을 수 있다면, 최소 몇 학기가 걸리나

칸의 알고리즘을 층별로 돌린다. 지금 큐에 있는 과목을 한 학기에 모두 듣고, 그다음 큐가 다음 학기다. 층의 수가 최소 학기 수다. 그래프에서 가장 긴 경로의 길이와 같다. LeetCode 1136. Parallel Courses(프리미엄 문제)가 이 문제이고, 한 학기에 k과목까지만 들을 수 있다는 제한이 붙으면(1494. Parallel Courses II) 비트 마스크 DP가 필요한 어려운 문제가 된다.

### 고리가 어디인지 알려 달라면

세 색 DFS에서 회색을 다시 만났을 때, 스택(또는 재귀 경로)에서 그 과목부터 끝까지가 고리다. 부모 배열을 들고 다니다가 거꾸로 따라가도 된다. 빌드 도구나 패키지 매니저가 "순환 의존: a → b → c → a"를 보여 주는 게 이 방식이다. 칸의 알고리즘은 고리가 있다는 것과 고리에 걸린 과목들(끝까지 진입 차수가 남은 과목)은 알려 주지만, 고리 하나의 순서는 바로 주지 않는다.

### 선수 관계가 계속 추가된다면

관계 하나가 추가될 때마다 전체를 다시 돌리면 O(V + E)씩 든다. 새 선 b → a를 넣기 전에 a에서 b로 가는 길이 이미 있는지만 DFS로 확인하면 된다. 있으면 이 선이 고리를 만든다. 최악은 같지만 보통 훨씬 적게 본다. 스프레드시트가 수식을 고칠 때 순환 참조를 바로 알려 주는 것도 이런 방식으로 할 수 있다.

## 고리가 있으면 누군가는 영원히 기다린다

모든 과목을 들을 수 있다는 말은 선수 관계 그래프에 고리가 없다는 말과 같다. 이걸 확인하는 길은 둘이다. 하나는 선수 과목이 남지 않은 과목부터 듣고, 들을 때마다 기다리던 과목의 남은 수를 줄이는 칸의 알고리즘이다. 끝까지 들은 과목 수가 전체보다 적으면 고리가 있다. 다른 하나는 세 색 DFS다. 지금 걷는 길(회색)로 돌아오면 고리이고, 다 훑은 과목(검은색)은 다시 보지 않는다. 회색만 쓰면 지수 시간이, 검은색만 쓰면 오답이 된다. 재귀 깊이 걱정이 없고 순서까지 함께 나오는 칸의 알고리즘이 기본 답이다.

## 면접에서 나올 만한 질문

### 이 문제를 그래프로 바꾸면 무엇을 묻는 건가요?

과목을 점, 선수 관계 `[a, b]`를 b에서 a로 가는 선으로 보면, 방향 그래프에 사이클이 있는지 묻는 문제다. 사이클이 있으면 그 위의 과목들이 서로를 먼저 들으라고 해서 어느 것도 들을 수 없다. 사이클이 없으면 위상 정렬 순서대로 모두 들을 수 있다.

### 칸의 알고리즘은 왜 고리를 찾아내나요?

고리 위의 과목들은 서로가 서로의 선수 과목이라 진입 차수가 0이 될 수 없다. 그래서 큐에 들어가지 못하고, 끝났을 때 들은 과목 수가 전체보다 적다. 반대로 고리가 없으면 남은 과목 중 진입 차수가 0인 과목이 반드시 있어서 모두 들을 수 있다. 시간은 O(V + E)다.

### DFS에서 상태를 왜 세 가지로 나누나요?

"지금 길 위"(회색)와 "다 훑음"(검은색)을 구분해야 해서다. 방문함 하나로 합치면 두 길이 한 과목에서 만나는 마름모를 고리로 잘못 본다. 길에서 나올 때 표시를 지우기만 하면 답은 맞지만, 같은 과목 아래를 길마다 다시 훑어서 마름모 사슬에서 지수 시간이 된다. 과목 67개짜리 입력에서 6,700만 번을 호출했다.

### BFS와 DFS 중 무엇을 고르나요?

기본은 칸의 알고리즘(BFS)이다. 재귀가 없어서 Python의 재귀 한도 1,000에 걸리지 않는다. 실제로 과목 2,000개짜리 사슬에서 Python 재귀 DFS는 `RecursionError`를 냈다. 고리의 위치를 알려 줘야 하거나 고리를 찾는 즉시 멈추고 싶다면 DFS를 쓰되, 깊은 그래프라면 스택으로 바꾼다.

### 유니온 파인드로 풀 수 없나요?

방향 그래프에서는 안 된다. 유니온 파인드는 두 점이 이어져 있는지만 알고 방향을 모른다. 0 → 1, 0 → 2, 1 → 2는 고리가 없는데, 방향을 지우면 삼각형이라 사이클로 판정한다. 유니온 파인드는 무방향 그래프의 사이클(Redundant Connection)에 쓴다.

### 시간과 공간 복잡도는요?

칸의 알고리즘과 세 색 DFS 모두 시간 O(V + E)다. 과목마다 큐나 색 변경이 한 번, 선마다 진입 차수 감소나 탐색이 한 번이다. 공간은 인접 리스트 O(V + E)와 진입 차수 배열이나 색 배열 O(V)다. 선수 관계를 매번 다시 훑는 풀이는 O(V · E)다.
