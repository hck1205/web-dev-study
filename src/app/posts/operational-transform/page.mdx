<EasyIntro>
  두 사람이 같은 문서를 동시에 고친다. 나는 맨 앞 글자를 지우고, 상대는 두 번째 자리에 글자를 넣었다. 상대의 편집은 "두 번째 자리"라고 말하는데, 내 문서는 이미 한 칸씩 당겨져서 그대로 적용하면 엉뚱한 자리에 들어간다.

  OT는 상대의 편집을 받을 때 내가 먼저 한 편집에 맞춰 자리를 고쳐 쓴 다음 적용하는 방법이다. 상대가 내 앞에 글자를 넣었으면 내 자리를 한 칸 밀고, 지웠으면 한 칸 당기는 식이다. 그런데 세 사람 이상이 서로 다른 순서로 편집을 받으면 고쳐 쓰는 순서에 따라 결과가 갈라질 수 있어서, 실제 서비스는 서버 한 곳이 모든 편집에 번호를 매겨 순서를 하나로 정한다.

  그래서 구글 문서 같은 편집기는 서버 없이는 돌아가지 않고, 각 기기는 서버가 받았다고 확인해 주기 전까지 편집을 하나만 띄워 두고 기다린다. 서버 없이도 합쳐지게 하려면 다른 방법이 필요하다.
</EasyIntro>

공유 문서에 `cats`라고 적혀 있다. 나는 맨 앞의 c를 지웠고, 같은 순간 다른 사람이 c와 a 사이에 h를 넣었다. 둘 다 네트워크가 느린 카페에 있었다. 몇 초 뒤 내 화면에는 `ahts`, 상대 화면에는 `hats`가 남았다. 둘 다 저장 버튼을 눌렀고, 둘 다 "저장됨"을 봤다. 어느 쪽 문서가 진짜인가.

공동 편집기는 이 문제를 매 키 입력마다 푼다. 구글 문서처럼 서버가 있는 편집기가 오래 써 온 방법이 Operational Transformation(OT)이다. 상대가 보낸 편집을 그대로 적용하지 않고, 내가 그사이에 한 편집에 맞게 위치를 고쳐 쓴 뒤 적용한다. 이 글은 그 "고쳐 쓰기"가 정확히 무엇인지, 왜 둘이 아니라 셋이 되면 깨지는지, 그래서 왜 OT는 거의 언제나 중앙 서버와 버전 번호를 함께 쓰는지를 직접 돌려 보며 본다. 실행 환경은 Node.js 22, 실제 라이브러리는 ShareDB 6.0.5와 그 텍스트 타입 ot-text-unicode 4.0.0이다.

이 주제의 다른 글: 서버 없이도 어떤 순서로 합쳐도 같아지는 자료형은 [CRDT](/posts/crdt)에서 다룬다. 이 글은 위치를 고쳐 쓰는 쪽에서 출발한다.

## 위치로 말하는 편집은 동시에 오면 어긋난다

편집 하나를 "몇 번째 칸에 무엇을 넣는다/지운다"로 표현해 보자. 이걸 연산(operation)이라고 부른다. 연산은 보내기 쉽다. 문서 전체를 보내는 대신 `ins(1, "h")` 몇 바이트만 보내면 된다. 문제는 이 위치가 보낸 사람의 문서 기준이라는 데 있다.

아래 그림은 서버 없이 두 사람이 연산을 그대로 주고받는 장면이다. 다음을 누르면 한 단계씩 진행된다.

실제로 돌려 보면 그대로다.

```text
start           : cats
A local         : del(0) -> ats
B local         : ins(1,"h") -> chats
-- 변환 없이 상대 연산을 그대로 적용
A gets B as-is  : ahts
B gets A as-is  : hats
```

B 쪽은 우연히 맞았다. 지운 위치(0)가 넣은 위치(1)보다 앞이었기 때문에 B의 0번은 여전히 c였다. A 쪽은 틀렸다. A의 문서에서는 c가 사라져 모든 글자가 한 칸씩 당겨졌는데, B의 연산은 그걸 모른다. 연산은 그 연산이 만들어진 문서 상태를 전제로 한다. 같은 연산을 다른 상태에 적용하면 뜻이 바뀐다.

잠금으로 막을 수도 있다. 한 사람이 편집하는 동안 다른 사람은 기다리게 하면 된다. 하지만 공동 편집기에서 네트워크 왕복을 기다렸다가 글자를 찍게 하면 타자 한 번에 수십~수백 ms가 걸린다. 공동 편집기가 원하는 건 세 가지다. 내 입력은 내 화면에 즉시 보인다. 결국 모두가 같은 문서를 본다. 그리고 각자가 하려던 편집이 살아남는다.

## 상대 연산을 내 문서에 맞게 고쳐 쓴다

OT의 생각은 단순하다. 상대 연산 b를 받았는데 내가 그사이에 a를 이미 적용했다면, b를 a가 적용된 문서에 맞게 바꾼 b′를 적용한다. 이 바꾸는 함수를 변환 함수 T라고 부른다. `T(b, a)`는 "a가 먼저 적용됐다고 치고 b를 다시 쓴 것"이다.

A 쪽은 `T(b, a)`를, B 쪽은 `T(a, b)`를 적용한다. 그 결과가 같아야 한다는 조건을 TP1(Transformation Property 1)이라고 한다.

```text
apply(apply(S, a), T(b, a))  ==  apply(apply(S, b), T(a, b))
```

같은 예제에 변환을 넣으면 이렇다.

```text
-- 변환해서 적용
A gets T(b,a)   : ins(0,"h") -> hats
B gets T(a,b)   : del(0) -> hats
```

B 쪽에서는 `T(del(0), ins(1,h))`가 그대로 `del(0)`이다. 삽입이 삭제 위치보다 뒤라서 지울 칸의 번호가 바뀌지 않았다. 변환이 하는 일은 결국 "상대가 내 앞에 무엇을 넣었거나 지웠으면 그만큼 내 위치를 민다"다.

## 네 가지 짝마다 규칙이 다르다

한 글자 단위의 삽입·삭제만 있다고 하면 짝은 네 가지다. a를 b 뒤에 적용할 수 있게 바꾸는 규칙은 이렇다.

```js
// a를, b가 먼저 적용된 문서에 맞게 바꾼다
function transform(a, b) {
  if (a.t === "ins" && b.t === "ins") {
    // 같은 위치면 site(사용자 id)로 순서를 정한다. 양쪽이 같은 규칙을 써야 한다
    if (a.pos < b.pos || (a.pos === b.pos && a.site < b.site)) return a;
    return { ...a, pos: a.pos + 1 };
  }
  if (a.t === "ins" && b.t === "del") return a.pos <= b.pos ? a : { ...a, pos: a.pos - 1 };
  if (a.t === "del" && b.t === "ins") return a.pos < b.pos ? a : { ...a, pos: a.pos + 1 };
  // 둘 다 삭제
  if (a.pos < b.pos) return a;
  if (a.pos > b.pos) return { ...a, pos: a.pos - 1 };
  return NOOP; // 같은 글자를 둘 다 지웠다. 두 번 지우면 안 된다
}
```

경계에서 틀리기 쉽다. 같은 위치에 둘 다 넣는 경우가 그렇다. A가 1번에 X, B가 1번에 Y를 넣으면 `cXYats`도 `cYXats`도 말이 된다. 어느 쪽이든 상관없지만 양쪽이 같은 답을 골라야 한다. 그래서 사용자 id처럼 양쪽이 똑같이 아는 값으로 순서를 정한다. 한쪽은 "내가 먼저", 다른 쪽도 "내가 먼저"라고 판단하면 그 자리에서 문서가 갈라진다.

같은 글자를 둘 다 지운 경우도 있다. 둘 다 `del(0)`을 보냈다면 상대 것을 받을 때 이미 그 글자는 없다. 변환하지 않으면 그 다음 글자를 지운다. 그래서 결과가 아무것도 안 하는 연산(NOOP)이 된다.

이 네 규칙이 TP1을 지키는지 무작위로 확인했다. 1~5글자 문서에 두 사람이 임의의 삽입·삭제를 하나씩 하는 경우를 10만 번 만들었다.

```text
TP1 (두 연산): 100000번 중 같음 100000, 다름 0
```

두 사람이 한 번씩 동시에 고치는 상황은 이걸로 해결이다. 실제 편집기는 글자 하나가 아니라 "3칸 건너뛰고, 2칸 지우고, 'ab' 넣기" 같은 묶음 연산을 쓰고, 서식(굵게, 링크), 표, 목록까지 연산 종류가 늘어난다. 연산 종류가 n개면 변환 규칙은 n²개 짝마다 필요하다. OT 구현이 어렵다는 말은 대부분 여기서 나온다.

## 세 명이 되면 변환 순서가 결과를 바꾼다

이제 서버 없이 세 사람이 서로 연산을 직접 주고받는다고 하자. 문서는 `d` 한 글자다. A는 d를 지우고, B는 d 뒤에 z를 넣고, C는 d 앞에 x를 넣는다. 셋 다 동시에 했다.

C의 연산을 받은 사람은 그 전에 A와 B의 연산을 이미 적용했을 수 있다. 그런데 어떤 사람은 A → B 순서로, 다른 사람은 B → A 순서로 받았다. C의 연산은 두 경로로 변환된다. 경로가 달라도 결과가 같아야 한다는 조건이 TP2다.

```text
T(T(c, a), T(b, a))  ==  T(T(c, b), T(a, b))
```

위 네 규칙으로 세 연산짜리 경우를 10만 번 만들어 보면 TP2는 깨진다. 찾은 반례가 바로 이 `d` 예제다.

```text
TP2 (세 연산): 100000번 중 같음 97457, 다름 2543
반례 문서: "d"  a: del(0)@A  b: ins(1,"z")@B  c: ins(0,"x")@C
  a→b→c 경로의 c': ins(1,"x")@C  결과: zx
  b→a→c 경로의 c': ins(0,"x")@C  결과: xz
```

원인은 정보가 사라지는 데 있다. 경로 1에서는 d가 먼저 지워져 x와 z가 같은 0번을 두고 다툰다. 이 순간 "x는 d 앞, z는 d 뒤였다"는 사실을 위치 숫자로는 더 이상 표현할 수 없다. 그래서 동점 규칙(site)이 원래 순서와 다른 답을 낸다. TP2를 만족하는 변환 함수를 만들려면 지운 글자를 표시만 해 두는 식으로 정보를 남겨야 하는데, 1990년대 논문 여러 편이 TP2를 만족한다고 주장한 함수에서 나중에 반례가 나왔다. 1989년의 첫 OT 알고리즘(dOPT)도 이런 퍼즐에서 깨진다.

## 서버가 순서를 정하면 TP1만 있으면 된다

현실의 해법은 TP2를 피해 가는 것이다. 연산이 퍼지는 경로를 하나로 만들면 된다. 모든 연산이 서버를 거치고, 서버가 받은 순서대로 번호(리비전)를 매긴다. 그러면 누구도 서로 다른 순서로 연산을 받지 않는다. 변환은 언제나 "클라이언트 한 명과 서버" 두 쪽 사이에서만 일어나고, 두 쪽 사이에는 TP1만 있으면 충분하다.

이 구조는 1995년 Xerox PARC의 Jupiter 시스템에서 나왔고, 구글 웨이브가 이 방식을 바탕으로 만들었다고 밝혔다. 구글 문서도 2010년 공식 블로그에서 서버가 있는 OT로 동시 편집을 처리한다고 설명했다.

동작은 이렇다.

1. 클라이언트는 연산을 만들면 바로 자기 화면에 적용하고, "나는 리비전 v까지 본 상태에서 이걸 만들었다"는 v를 붙여 서버로 보낸다.
2. 서버는 v 이후에 자기가 받은 연산들(클라이언트가 아직 못 본 것들)에 맞춰 그 연산을 차례로 변환한다.
3. 변환한 연산을 적용하고 새 리비전 번호를 붙여 기록한다. 보낸 사람에게는 확인(ack)을, 나머지에게는 변환된 연산을 보낸다.
4. 클라이언트는 남의 연산을 받으면 아직 확인받지 못한 내 연산들에 맞춰 변환한 뒤 적용한다.

## 메시지가 늦게, 뒤바뀌어 오면

서버 중심 OT는 한 가지를 당연하게 여긴다. 서버와 클라이언트 사이의 메시지가 보낸 순서대로 도착한다는 것이다. 보통은 WebSocket이 TCP 위에 있어서 지켜진다. 그런데 재연결하면서 다른 서버로 붙거나, 메시지를 여러 경로(예: HTTP 요청과 별도 푸시 채널)로 나눠 보내면 깨진다.

두 클라이언트와 서버를 시뮬레이션으로 만들어 확인했다. 클라이언트마다 연산 6개를 무작위 시각에 만들고, 메시지마다 1~20의 무작위 지연을 줬다. 채널을 세 가지로 바꿔 1,000번씩 돌렸다.

```text
fifo         1000번 중 수렴 1000, 불일치 0 (그중 위치 오류로 적용 실패 0)
reorder      1000번 중 수렴 173, 불일치 827 (그중 위치 오류로 적용 실패 412)
reorder+seq  1000번 중 수렴 1000, 불일치 0 (그중 위치 오류로 적용 실패 0)
```

- `fifo`: 지연은 무작위지만 같은 채널 안에서는 순서가 유지된다(TCP 하나와 같다). 1,000번 모두 수렴했다.
- `reorder`: 순서까지 섞인다. 83%가 실패했고, 그중 절반은 문서 길이를 넘는 위치를 받아 적용 자체가 실패했다. 나머지는 오류 없이 조용히 다른 문서가 됐다(예: 서버 `aaab`, A `aaaa`).
- `reorder+seq`: 순서는 섞이지만 받는 쪽이 번호를 보고 다시 줄을 세운다. 서버는 클라이언트별 seq를, 클라이언트는 서버 리비전을 기다렸다가 차례대로 적용한다. 다시 1,000번 모두 수렴했다.

같은 원리가 재전송에도 필요하다. 연결이 끊긴 사이 서버가 연산을 받았는지 모르는 클라이언트는 다시 보낼 수밖에 없다. ShareDB는 연결 id(`src`)와 `seq`로 이걸 걸러 낸다. 같은 메시지를 두 번 보내 봤다.

```text
reply {"src":"a51fa02adf32496e2509bb63821023d2","seq":102,"v":1,"a":"op","c":"docs","d":"memo"}
reply {"src":"a51fa02adf32496e2509bb63821023d2","seq":102,"v":1,"a":"op","c":"docs","d":"memo"}
snapshot v2 "cats!"
```

두 번 모두 같은 v1 확인을 받았고, 문서에는 느낌표가 하나만 있다. 반대로 서버보다 앞선 버전을 붙이면 바로 거절한다.

```text
ShareDBError: Invalid op submitted. Op version newer than current snapshot
```

이 오류는 보통 클라이언트가 자기 버전을 잘못 올렸거나, 서로 다른 저장소를 보는 서버 두 대 사이를 오가며 붙었을 때 나온다.

## 수렴했다고 사용자가 원한 결과는 아니다

OT 논문들은 세 가지 조건을 말한다. 모두가 같은 문서로 수렴할 것, 원인이 된 편집이 결과보다 먼저 적용될 것(인과 순서), 그리고 각자의 의도가 보존될 것이다. 앞의 두 개는 기계적으로 확인할 수 있지만 마지막은 사람의 기대에 달려 있다. ot-text-unicode로 경계 상황을 돌려 봤다.

```text
같은 위치에 둘 다 삽입              A [1,"X"] B [1,"Y"] => "cXYats" (수렴)
지운 범위 안에 삽입                A [{"d":6}] B [3,"LP"] => "LPworld" (수렴)
겹치는 범위 삭제                  A [1,{"d":3}] B [2,{"d":3}] => "af" (수렴)
같은 글자를 둘 다 삭제              A [{"d":1}] B [{"d":1}] => "ats" (수렴)
```

모두 수렴했다. 그런데 두 번째 줄을 보자. A는 `hello `를 통째로 지웠고, B는 같은 순간 그 단어 한가운데에 `LP`를 넣었다. 결과는 `LPworld`다. 삽입은 지워지지 않는다는 규칙 덕에 B의 입력은 살아남았지만, B가 고치던 단어는 사라졌다. 앞뒤 맥락 없이 `LP`만 덩그러니 남는다. 어느 쪽이 옳은지는 정할 수 없다. 대부분의 편집기는 이렇게 입력을 살리는 쪽을 고르고, 사용자가 화면을 보고 고치게 둔다.

겹치는 범위 삭제는 `abcdef`에서 A가 `bcd`, B가 `cde`를 지운 경우다. 합집합 `bcde`가 지워져 `af`가 됐다. 두 사람 다 지우려던 글자가 모두 지워졌으니 의도에 맞다. 범위 연산의 변환은 이렇게 "겹친 부분은 한 번만" 처리해야 하고, 직접 구현하면 여기서 버그가 많이 난다.

되돌리기(undo)는 더 까다롭다. 내가 3분 전에 한 삭제를 되돌리려면 그 뒤에 들어온 남의 연산들에 맞춰 역연산을 변환해야 한다. 내 연산만 되돌리는 선택적 undo는 TP2와 비슷한 추가 조건이 필요해서, 많은 편집기가 undo 스택을 로컬 연산 기준으로만 관리하고 남의 연산에 맞춰 계속 변환해 둔다.

  return ["noop"]; // 같은 글자를 이미 지웠다
}`}
  tests={[
    { label: "cats: h 삽입을 c 삭제에 맞춤", args: [["ins", 1, "h", "B"], ["del", 0, "A"]], expected: ["ins", 0, "h", "B"] },
    { label: "cats: c 삭제를 h 삽입에 맞춤", args: [["del", 0, "A"], ["ins", 1, "h", "B"]], expected: ["del", 0, "A"] },

`ins` vs `del`의 `<=`와 `del` vs `ins`의 `<`가 비대칭인 걸 눈여겨보자. 삽입 위치와 삭제 위치가 같으면 삽입은 "그 글자 앞"이라 삭제의 영향을 받지 않고, 삭제할 글자는 그 앞에 새 글자가 끼어들었으니 한 칸 밀린다. 이 부등호 하나를 틀리면 TP1 퍼즈 테스트에서 바로 드러난다.

## 공동 편집이 이상할 때 보는 곳

증상은 대개 둘 중 하나다. 한 사람 화면에서만 글자가 엉뚱한 곳에 들어가 있거나, 새로고침하면 내가 쓴 글이 바뀌어 있다. 둘 다 클라이언트 문서와 서버 문서가 갈라진 상태다.

먼저 갈라진 시점을 찾는다. OT 서버는 리비전마다 연산을 기록하므로, 스냅숏 하나와 그 뒤 연산 기록을 재생하면 어느 리비전에서든 문서를 다시 만들 수 있다. 클라이언트 로그에 "로컬 버전, 서버에서 받은 리비전, 보류 중인 연산"을 남겨 두면 서버 재생 결과와 비교해 첫 차이가 난 리비전을 찾을 수 있다. 그 리비전 앞뒤의 연산 짝이 변환 함수의 버그를 가리킨다.

자주 보는 원인은 이렇다.

- 위치 단위가 서로 다르다. 자바스크립트 문자열의 `length`는 UTF-16 코드 단위다. `"hi😀cats".length`는 8이지만 글자 수(코드 포인트)는 7이다. ot-text-unicode는 코드 포인트로 센다. 브라우저 편집기에서 얻은 UTF-16 위치를 그대로 연산에 넣으면 이모지 뒤에서 한 칸씩 어긋나고, 이모지를 반으로 잘라 `hi\ud83dcats` 같은 깨진 문자열이 생긴다.
- 확인 전에 연산을 여러 개 보낸다. 두 번째 연산의 기준 버전이 틀려서 서버가 잘못 변환한다. 위의 세 상태를 지키는지 본다.
- 재연결 때 보류 연산을 버리거나 두 번 적용한다. 재연결하면 서버에서 마지막으로 본 리비전 이후 연산을 받아 보류 연산과 변환하고, 보류 연산은 같은 `src`·`seq`로 다시 보낸다.
- 편집 서버를 여러 대로 늘리면서 문서별 순서가 깨진다. 한 문서의 연산은 한 곳에서 순서가 매겨져야 한다. 문서 id로 서버를 고정하거나(ShareDB는 연산 기록을 DB에 쓸 때 버전 충돌을 감지해 재시도한다), 문서별 리더를 둔다.
- 오래 오프라인이던 클라이언트가 돌아온다. 서버는 그동안 쌓인 연산 전부에 맞춰 변환해야 한다. 연산 기록을 너무 일찍 지웠다면 ShareDB는 `Op submit failed. DB missing ops needed to transform it up to the current snapshot version`으로 거절한다. 오프라인을 길게 허용해야 하는 앱이라면 연산 기록 보존 기간을 그만큼 잡거나 CRDT를 검토한다.

전송 쪽 설정은 [실시간 통신 글](/posts/realtime-communication)에서 다룬 WebSocket 재연결·하트비트와 같다. OT는 그 위에 "기준 버전"과 "연속 번호"를 얹는다.

## 언제 OT를 고르나

OT는 서버가 있고, 문서마다 순서를 매길 곳 하나를 둘 수 있을 때 잘 맞는다. 연산이 위치와 내용뿐이라 작고, 서버에 연산 기록이 남아 감사·재생·권한 검사를 서버에서 할 수 있다. 서버가 모든 연산을 보니 "이 사용자는 이 문단을 못 고친다" 같은 규칙도 쉽게 건다. 구글 문서가 대표적이고, ShareDB나 ot.js 같은 라이브러리가 있다.

반대로 서버 없이 기기끼리 동기화해야 하거나, 며칠씩 오프라인으로 편집하다 합쳐야 하거나, 서버 한 곳이 문서마다 순서를 매기는 게 부담이라면 [CRDT](/posts/crdt)가 맞다. CRDT는 변환 대신 글자마다 고유 id를 붙여 TP2 문제를 처음부터 없애는 대신, 지운 글자를 계속 들고 다니는 메모리 비용을 낸다. 둘 다 최종적으로 같아지는 [최종 일관성](/posts/eventual-consistency)을 목표로 하지만, OT는 서버의 순서에, CRDT는 자료형의 수학적 성질에 기댄다.

OT는 위치로 말하는 연산을 서로의 편집에 맞게 다시 쓰는 방법이다. 두 쪽 사이의 변환(TP1)은 쉽게 맞출 수 있지만 여러 쪽이 서로 다른 순서로 받으면(TP2) 깨지기 쉽다. 그래서 서버가 리비전 번호로 순서를 하나로 정하고, 클라이언트는 확인받지 못한 연산을 하나만 띄워 둔 채 들어오는 연산을 변환한다.

이 주제의 다른 글: [CRDT](/posts/crdt)

## 면접에서 나올 만한 질문

### OT가 해결하는 문제는 무엇인가

여러 사람이 같은 문서를 동시에 고칠 때 각자 화면에 즉시 반영하면서도 결국 같은 문서로 수렴하게 만드는 문제다. 편집을 위치 기반 연산으로 보내는데, 그 위치는 보낸 사람의 문서 기준이라 상대 문서에 그대로 적용하면 엉뚱한 곳에 들어간다. OT는 상대 연산을 내가 먼저 적용한 연산에 맞게 변환해서 적용한다. cats에서 c 삭제와 h 삽입이 동시에 오면 삽입 위치를 1에서 0으로 당기는 식이다.

### TP1과 TP2는 무엇이고 왜 TP2가 어려운가

TP1은 두 연산 a, b가 있을 때 a 뒤에 변환된 b를 적용한 결과와 b 뒤에 변환된 a를 적용한 결과가 같아야 한다는 조건이다. TP2는 세 번째 연산 c를 a, b 순서로 변환하든 b, a 순서로 변환하든 결과가 같아야 한다는 조건이다. 위치만 보는 변환은 삭제로 글자가 사라지면 "누가 어느 쪽에 있었는지" 정보를 잃어서 TP2를 깨기 쉽다. 실제로 `d`에서 삭제, 뒤 삽입, 앞 삽입을 동시에 하면 경로에 따라 `zx`와 `xz`로 갈라진다.

### OT에 왜 중앙 서버가 필요한가

서버가 모든 연산에 하나의 순서(리비전)를 매기면 모든 클라이언트가 같은 순서로 연산을 받는다. 그러면 변환은 클라이언트 하나와 서버 사이에서만 일어나고 TP1만 있으면 수렴한다. 서버 없이 피어끼리 보내면 사람마다 받는 순서가 달라져 TP2가 필요해지는데, 이를 만족하는 변환 함수를 만들기가 매우 어렵다. Jupiter, 구글 웨이브, 구글 문서가 모두 이 구조다.

### 클라이언트가 확인받지 못한 연산을 하나만 보내는 이유는

연산에 붙이는 기준 버전 때문이다. 두 번째 연산은 첫 번째 연산이 적용된 상태에서 만들어졌는데, 첫 번째가 서버의 몇 번 리비전이 될지는 확인이 와야 안다. 그래서 확인 대기 중에는 새 연산을 버퍼에 모으고, 그 사이 들어온 남의 연산에 맞춰 보낸 연산과 버퍼를 함께 변환한다. 확인이 오면 버퍼를 다음 연산으로 보낸다.

### 메시지 순서가 뒤바뀌면 어떻게 되나

서버 중심 OT는 채널 안의 순서가 유지된다고 가정한다. 시뮬레이션에서 순서를 섞자 1,000번 중 827번이 갈라졌고 그중 절반은 범위를 벗어난 위치로 적용조차 실패했다. 서버가 붙이는 리비전 번호와 클라이언트의 seq로 받는 쪽이 줄을 다시 세우면 모두 수렴했다. 재연결 후 재전송은 연결 id와 seq로 중복을 거른다.

### 수렴하면 의도도 보존되는가

아니다. 수렴은 모두가 같은 문서를 본다는 것뿐이다. A가 단어를 통째로 지우는 동안 B가 그 단어 안에 글자를 넣으면 대개 B의 글자만 남는다. 모두 같은 결과를 보지만 B가 고치던 단어는 사라졌다. 편집기는 입력을 살리는 쪽을 고르고 사용자가 보고 고치게 두는 경우가 많다.

### OT와 CRDT 중 무엇을 고르나

서버가 있고 문서마다 순서를 매길 곳을 둘 수 있으며 서버에서 권한 검사와 기록이 필요하다면 OT가 단순하고 연산도 작다. 서버 없는 동기화, 긴 오프라인 편집, 기기 간 직접 동기화가 필요하면 CRDT가 맞다. CRDT는 변환 대신 원소마다 고유 id를 붙여 순서 문제를 없애지만 지운 원소를 기록으로 남기는 메모리 비용이 있다.
