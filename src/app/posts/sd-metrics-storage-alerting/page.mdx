이 시리즈에서 이 글의 자리: 앞 글 [㊷ 지표 수집: pull과 push, 큐](/posts/sd-metrics-collection)에서 1만 대의 숫자를 모아 큐 앞까지 가져왔다. 이 글은 같은 장의 두 번째 글로, 큐 뒤에서 1년치를 줄여 담고, 묻고, 사람을 부르는 쪽을 설계한다. 다음 글은 새 사례인 [㊹ 광고 클릭 집계 ①: 이벤트 시간과 윈도](/posts/sd-ad-click-stream-windows)다.

지난 글의 규모를 그대로 이어 간다. 시계열 1,000만 개, 10초마다 한 점, 초당 100만 점이다. 그런데 요구 사항에 이런 줄이 있었다. "1년 보관한다. 최근 7일은 원본, 30일까지는 1분 단위, 그 뒤는 1시간 단위로 줄여도 된다." 이 한 줄을 실제로 굴러가게 만드는 게 이 글의 절반이다. 나머지 절반은 "CPU가 90%를 1분 넘게 넘으면 전화를 걸어라"가 두 번 울리지도, 빠지지도 않게 하는 일이다.

시계열 저장소 하나의 내부, 즉 압축과 파티션과 PostgreSQL로 직접 쌓아 보는 실험은 [시계열 DB](/posts/db-type-time-series)에서 했다. 알림 규칙을 잘 쓰는 법과 Alertmanager의 묶기·누르기는 [알림 설계](/posts/alerting)에 있다. 이 글은 그 부품들을 엮어 회사 규모의 시스템으로 만드는 쪽을 본다.

## 원본을 1년 동안 다 두면

가장 작은 버전은 들어온 점을 하나도 버리지 않고 1년 동안 두는 것이다. 얼마나 될까. 점 하나를 압축 없이 16바이트로 잡으면 하루 1.4TB, 1년이면 약 505TB다. 압축을 잘해서 10분의 1로 줄여도 50TB가 넘는다. 디스크 값보다 더 아픈 건 읽기다. "지난 6개월 CPU 추이" 패널 하나가 시계열 하나에서만 155만 점을 읽는다.

그런데 6개월 그래프를 그릴 때 10초 간격의 점이 다 필요할까. 화면의 패널 폭은 많아야 1,000~2,000픽셀이다. 155만 점을 읽어도 결국 1,000개 남짓으로 뭉쳐서 그린다. 오래된 데이터는 미리 뭉쳐 두면 된다. 이게 다운샘플링이고, 이 시스템의 저장 설계는 이 생각 하나에서 출발한다.

## 쓰기는 쉬지 않고 읽기는 몰려서 온다

저장소를 고르기 전에 이 데이터가 어떻게 쓰이는지 다시 보자. 쓰기는 초당 100만 점이 밤낮없이 들어온다. 고치거나 지우는 일은 거의 없고, 늘 끝에 붙는다. 읽기는 평소엔 대시보드 몇 개와 알림 규칙이 전부다. 장애가 나면 수십 명이 같은 대시보드를 동시에 열고, 범위를 바꿔 가며 계속 묻는다.

읽기가 어느 시간대에 몰리는지도 뚜렷하다. Facebook이 Gorilla 논문에서 밝힌 바로는 운영 지표 조회의 85% 이상이 최근 26시간 안의 데이터였다. 그래서 최근 데이터는 메모리에 두고, 오래된 데이터는 디스크로, 더 오래된 데이터는 더 싼 곳으로 내려보내는 계층 구조가 자연스럽다.

이런 성질 때문에 범용 관계형 DB보다 시계열 전용 저장소를 쓴다. Prometheus, InfluxDB, VictoriaMetrics, M3, Amazon Timestream 같은 것들이다. 이들은 시계열마다 점을 시간 순으로 붙여 압축하고, 라벨마다 색인을 만들어 `region=ap-ne-2`인 시계열을 빨리 찾는다. 내부를 다 알 필요는 없다. 면접에서는 "쓰기가 많고 끝에만 붙는 시계열이라 전용 저장소를 쓰고, 라벨 가짓수를 낮게 유지한다"까지 말하면 충분하다. 왜 일반 DB로는 힘든지는 [시계열 DB](/posts/db-type-time-series)에서 직접 쌓아 보며 확인했다.

## 1년을 세 해상도로 나눠 담는다

요구 사항의 보관 규칙을 그대로 세 단계로 만든다. 원본(10초)은 7일, 1분 단위는 30일, 1시간 단위는 1년이다. 1분 칸 하나에는 그 1분 동안 들어온 점 6개의 건수, 합계, 최솟값, 최댓값을 담는다. 평균이 아니라 합계와 건수를 두는 이유는 [시계열 DB](/posts/db-type-time-series)의 "오래된 데이터는 요약으로 바꾼다"에서 숫자로 확인했다.

단계를 언제 만들지가 설계 포인트다. 원본이 7일을 넘겨 지워지기 직전에 접어 올리면, 최근 7일 동안은 1분 단계에 데이터가 없다. 그러면 "최근 2일"을 물을 때 원본 1만 7천 점을 읽어야 한다. 그래서 원본이 들어오는 대로(실제로는 몇 분이나 몇 시간 단위로) 위 단계도 함께 채우고, 원본은 기한이 지나면 지운다. 각 단계가 자기 기간을 통째로 갖고 있어야 조회가 단계 하나만 보면 된다.

이 구조를 Node 22로 80줄쯤 되는 작은 저장소로 만들어 봤다. 시계열 하나에 400일 동안 10초마다 하루 주기로 오르내리는 CPU 값을 넣고, 하루에 한 번 정리 작업을 돌린다.

```js
// tsdb.js 일부: 하루에 한 번 도는 정리 작업
compact(now) {
  for (; this.rolled < this.raw.length; this.rolled++) {      // 새로 들어온 원본을 1분, 1시간 칸에 접는다
    const [ts, v] = this.raw[this.rolled];
    for (const [k, tier] of [[0, TIERS[1]], [1, TIERS[2]]]) {
      const b = ts - (ts % tier.step);
      const r = this.roll[k].get(b) ?? { count: 0, sum: 0, min: Infinity, max: -Infinity };
      r.count++; r.sum += v; r.min = Math.min(r.min, v); r.max = Math.max(r.max, v);
      this.roll[k].set(b, r);
    }
  }
  let i = 0;                                                  // 7일 지난 원본은 지운다
  while (i < this.raw.length && this.raw[i][0] < now - TIERS[0].keep) i++;
  this.raw.splice(0, i); this.rolled -= i;
  for (const [k, tier] of [[0, TIERS[1]], [1, TIERS[2]]])     // 칸도 단계마다 기한이 지나면 지운다
    for (const b of this.roll[k].keys()) if (b < now - tier.keep) this.roll[k].delete(b);
}
```

```text
raw 10s  points= 60480 bytes=967680
1m       points= 43200 bytes=1728000
1h       points=  8760 bytes=350400
total=3046080 bytes, raw for 1y would be 50457600 bytes (16.6x)
```

세 단계를 합쳐 약 3MB, 원본을 1년 두는 것의 16.6분의 1이다. 그런데 한 줄이 눈에 띈다. 1분 단계가 원본보다 크다. 칸 하나에 시각과 값 네 개를 담아 40바이트라서, 점 수가 원본보다 적어도 바이트는 더 든다. 1분 칸을 30일이나 두니 7일짜리 원본보다 커졌다. 계산을 직접 해 보자.

## 스파이크는 평균 속에 묻힌다

칸에 평균만 담으면 무엇을 잃는지 보자. 앞의 400일 데이터에서 200일째 오후 2시에 30초 동안 CPU가 100%로 튀게 해 뒀다. 그 시각의 1시간 칸을 열어 보면 이렇다.

```text
1h bucket: avg=14.6 max=100 min=12.9 count=360
```

평균은 14.6%다. 평소와 다를 게 없다. 30초짜리 스파이크는 1시간 동안의 360점 중 3점이라 평균에 거의 흔적을 남기지 않는다. 최댓값을 함께 담아 둔 덕분에 "그 시간 어딘가에서 100%를 찍었다"는 사실은 남았다. 그래서 칸에는 최소한 건수, 합계, 최솟값, 최댓값을 둔다. 응답 시간처럼 백분위가 중요한 지표는 히스토그램 칸 수를 그대로 합쳐 두면 나중에도 p99를 근사할 수 있다. 히스토그램을 합치는 방식은 [지표 타입](/posts/metrics-types)에 있다.

이 차이는 알림에도 영향을 준다. 알림 규칙은 원본 해상도에서 돌린다. 1시간 칸으로 "CPU 90% 초과"를 검사하면 짧은 스파이크는 영영 잡히지 않는다. 다운샘플링된 데이터는 추세를 보는 용도다.

## 패널 폭이 읽을 해상도를 정한다

단계가 셋이면 조회할 때마다 어느 단계를 읽을지 골라야 한다. 기준은 패널 폭이다. 패널이 1,000점을 그릴 수 있다면, 요청 범위를 1,000으로 나눈 값이 점 하나가 맡을 간격이다. 그 간격보다 촘촘하면서 요청 범위를 다 덮는 가장 거친 단계를 읽는다. 그다음 그 단계의 간격의 배수로 한 번 더 묶어 1,000점 안쪽으로 맞춘다.

```js
// tsdb.js 일부: 패널 폭으로 원하는 간격을 구하고, 읽을 단계를 고른다
query(now, from, to, maxPoints) {
  const want = Math.ceil((to - from) / maxPoints);
  let pick = null;
  for (const [idx, tier] of TIERS.entries()) {
    const oldest = idx === 0 ? (this.raw[0]?.[0] ?? now) : now - tier.keep;
    if (from >= oldest && tier.step <= Math.max(want, TIERS[0].step)) pick = tier;
    if (from >= oldest && !pick) pick = tier;          // 원본이 범위를 못 덮으면 덮는 첫 단계
  }
  const step = Math.max(pick.step, Math.ceil(want / pick.step) * pick.step);
  return { tier: pick.name, rowsRead: Math.ceil((to - from) / pick.step), step, points: Math.ceil((to - from) / step) };
}
```

이 선택은 조회하는 쪽이 신경 쓰지 않게 숨긴다. 그게 다음에 볼 조회 서비스의 일이다. 단계가 바뀌는 경계에서는 그래프의 모양이 달라진다. 7일 전까지는 뾰족하던 선이 그 이전에서 뭉툭해진다. 데이터가 이상해진 게 아니라 읽는 단계가 바뀐 것이다. 이걸 모르면 "일주일 전부터 트래픽 변동이 줄었다"는 엉뚱한 결론을 낸다.

## 조회 서비스 앞에 캐시를 둔다

조회 서비스는 대시보드와 알림이 저장소에 직접 붙지 않게 하는 층이다. 위에서 본 단계 고르기, 여러 저장소 노드에 나눠 묻고 합치기, 권한 확인, 너무 무거운 쿼리 막기를 여기서 한다. 저장소를 바꾸더라도 조회 서비스의 API만 지키면 대시보드는 그대로다. 저장소의 쿼리 기능이 충분히 강하면 이 층을 얇게 두거나 생략하기도 한다.

장애가 나면 같은 대시보드를 수십 명이 30초마다 새로 고친다. 캐시를 두면 좋을 것 같은데, 캐시 키를 잘못 잡으면 한 번도 맞지 않는다. "최근 1시간, 1분 간격" 패널을 30초마다 20번 새로 고치는 상황을 세 가지로 비교했다.

```js
// qcache.js 일부: 끝난 1분 칸만 칸 단위로 캐시하고, 진행 중인 마지막 칸은 매번 읽는다
const lastFull = now - (now % STEP);
for (let b = lastFull - RANGE; b < lastFull; b += STEP) {
  if (c.has(b)) { hit(); continue; }
  miss(); c.set(b, true); rows += rowsFor(b, b + STEP);
}
return rows + rowsFor(lastFull, now);
```

```text
no cache               db rows read=  7200 cache hits=0 misses=0
key = (from, to)       db rows read=  7200 cache hits=0 misses=20
key = 1m bucket        db rows read=   484 cache hits=1131 misses=69
```

요청 범위 `(from, to)`를 그대로 키로 쓰면 새로 고칠 때마다 `now`가 달라서 20번 모두 빗나간다. 캐시를 안 둔 것과 똑같다. 범위를 1분 칸으로 잘라 칸마다 캐시하면, 이미 끝난 칸은 한 번 읽은 뒤 다시 읽지 않는다. 저장소가 읽은 양이 7,200줄에서 484줄로 줄었다. 아직 끝나지 않은 마지막 칸은 값이 계속 바뀌니 캐시하지 않고 매번 읽는다. Thanos나 Grafana Mimir의 쿼리 프런트엔드가 이렇게 간격에 맞춰 범위를 자르고 캐시한다.

캐시를 넣기 전에 저장소 자체의 캐시가 충분한지 먼저 본다. 잘 고른 시계열 저장소는 최근 데이터를 이미 메모리에 두고 있어서, 별도 캐시가 얻는 게 생각보다 적을 수 있다. 캐시가 크게 이득인 곳은 장애 중의 같은 대시보드 반복 조회, 그리고 오래된 칸을 읽는 긴 범위 조회다.

1년이 넘은 데이터는 지우거나, 객체 저장소 같은 싼 저장소로 옮긴다. Prometheus 생태계의 Thanos와 Mimir는 2시간 단위 블록을 객체 저장소에 올리고 거기서 바로 읽는다. 어떻게 블록을 올리는지는 [Prometheus 내부 구조](/posts/prometheus-basics)에 정리해 뒀다. 조회 서비스가 오래된 범위만 그쪽으로 보내면 대시보드는 저장소가 바뀐 걸 모른다.

## 알림은 규칙을 주기적으로 묻는 일이다

이제 알림이다. 알림 시스템이 하는 일을 한 문장으로 줄이면 "규칙마다 정해진 간격으로 조회 서비스에 묻고, 조건이 일정 시간 버티면 사람을 부른다"다. 부품은 다섯이다.

규칙은 YAML 같은 설정 파일로 쓰고 저장소에 둔다. 평가기는 규칙을 읽어 캐시해 두고, 15초 같은 간격마다 조회 서비스에 묻는다. 조건이 맞으면 알림 이벤트를 만든다. 이벤트는 큐에 넣고, 발송기가 꺼내 메일, 전화, PagerDuty, 웹훅으로 보낸다. 그리고 알림마다 지금 어떤 상태인지 적어 두는 알림 저장소가 있다.

평가기와 발송기 사이에 큐를 두는 이유는 수집 쪽과 같다. PagerDuty가 잠깐 응답하지 않아도 평가는 계속되고, 이벤트는 큐에 남는다. 발송기는 실패하면 다시 보낸다. 다시 보낸다는 건 같은 알림이 두 번 갈 수 있다는 뜻이다. 그 문제를 바로 다음에서 다룬다.

알림이 얼마나 늦게 울리는지도 이 그림에서 나온다. 점이 수집되는 간격, 큐에서 저장소까지의 지연, 평가 간격, 규칙의 버티는 시간(`for`), 발송기가 비슷한 알림을 묶으려고 기다리는 시간이 모두 더해진다. 10초 수집에 15초 평가, `for: 1m`이면 문제가 생긴 뒤 빨라야 1분 남짓, 보통 1분 반 정도 뒤에 울린다. `for`와 창이 더해지는 방식은 [알림 설계](/posts/alerting)에서 promtool로 재 봤다.

## 알림 상태를 어디에 두나

평가기는 알림마다 상태를 들고 있다. 조건이 아직 안 맞는 비활성(inactive), 맞기 시작해 버티는 중인 대기(pending), 울린 발생(firing)이다. 조건이 풀리면 해소(resolved)를 알리고 비활성으로 돌아간다. 알림의 이름은 규칙 이름과 라벨을 합친 지문이다. `cpu_high{host="web-1"}`과 `cpu_high{host="web-2"}`는 다른 알림이다.

이 상태를 평가기 메모리에만 두면 평가기가 재시작될 때 문제가 생긴다. 15초마다 평가하고 60초를 버텨야 울리는 규칙으로 직접 돌려 봤다. web-1은 15초부터 계속 90%를 넘고, 평가기는 105초에 재시작된다. 발송기는 첫 알림을 보낸 직후 오프셋을 올리기 전에 한 번 죽는다.

```js
// alerts.js 일부: 상태 기계와, 보낸 키를 기억하는 발송기
if (bad && s.state === "inactive") store.set(fp, { state: "pending", since: now });
else if (bad && s.state === "pending" && now - s.since >= FOR) {
  store.set(fp, { state: "firing", since: s.since });
  publish({ key: `${fp}@${s.since}`, fp, status: "firing", at: now });   // 지문 + 시작 시각 = 중복 판별 키
} else if (!bad && s.state === "firing") {
  store.set(fp, { state: "inactive" });
  publish({ key: `${fp}@${s.since}:resolved`, fp, status: "resolved", at: now });
}
// 발송기: 이미 보낸 키면 건너뛴다
if (sentKeys.has(msg.key)) console.log(`  notifier: skip duplicate ${msg.key}`);
```

```text
== 상태를 바깥 저장소에 두고, 발송기가 한 번 죽는 경우
  PAGE t=75s firing cpu_high{host="web-1"}
  notifier crashed before commit
  notifier: skip duplicate cpu_high{host="web-1"}@15
  t=105s evaluator restarted (state kept: firing)
  PAGE t=180s resolved cpu_high{host="web-1"}
pages sent: 2

== 상태를 평가기 메모리에만 두면
  PAGE t=75s firing cpu_high{host="web-1"}
  t=105s evaluator restarted (state lost)
  PAGE t=165s firing cpu_high{host="web-1"}
  PAGE t=180s resolved cpu_high{host="web-1"}
pages sent: 3
```

위쪽은 상태를 바깥 저장소에 둔 경우다. 발송기가 보낸 직후 죽어서 같은 메시지를 다시 받았지만, 키(`지문@시작 시각`)를 이미 보냈다고 기억하고 있어 건너뛰었다. 평가기가 재시작돼도 저장소에서 "firing"을 읽어 이어 갔다. 전화는 발생 한 번, 해소 한 번이다. 보낸 키도 발송기 메모리가 아니라 알림 저장소에 남겨야 발송기 재시작을 견딘다.

아래쪽은 메모리에만 둔 경우다. 재시작한 평가기는 web-1이 이미 울렸다는 걸 모른다. 처음부터 대기를 다시 시작해 60초 뒤인 165초에 같은 사건으로 또 전화를 걸었다. 그사이 1분 동안은 아무도 지켜보지 않은 셈이기도 하다. 그래서 알림 저장소는 Cassandra 같은 키-값 저장소나 평가기끼리 복제하는 저장소에 둔다. Prometheus는 이 문제를 줄이려고 2.4부터 `for` 상태를 `ALERTS_FOR_STATE`라는 시계열로 저장해 재시작 뒤 복원한다.

이 방식은 결국 "최소 한 번 보내고, 받는 쪽에서 키로 거른다"다. 알림은 빠지는 것보다 두 번 가는 게 낫다. 그래서 발송은 최소 한 번을 지키고, 중복은 키로 줄인다. PagerDuty 같은 서비스도 같은 키(dedup key)로 들어온 이벤트를 하나의 사건으로 묶어 주니, 키를 잘 정해 넘기면 받는 쪽에서 한 번 더 걸러진다. 같은 원리를 메시지 일반으로 넓힌 이야기는 [메시지 전달 보장](/posts/message-delivery-semantics)에 있다.

## 알림 시스템이 죽으면 누가 알려 주나

알림 시스템에는 고약한 실패 방식이 하나 있다. 고장 나면 조용해진다. 평가기가 멈추거나 조회 서비스가 빈 결과만 돌려주면, 알림이 하나도 오지 않는다. 그런데 "알림이 없다"는 평소의 정상 상태와 똑같아 보인다.

이걸 잡는 흔한 장치가 늘 울리는 알림이다. 조건이 항상 참인 규칙(`vector(1)` 같은 것)을 하나 두고, 그 알림을 1분마다 바깥의 다른 시스템으로 보낸다. 바깥 시스템은 이 신호가 몇 분 동안 오지 않으면 사람을 부른다. 죽은 사람의 손이 떨어지면 기차가 서는 장치에 빗대 dead man's switch라고 부른다. 바깥 시스템은 반드시 이 알림 파이프라인과 다른 곳에 있어야 한다. 같은 Kafka, 같은 데이터 센터에 있으면 함께 죽는다.

이 원리는 수집 쪽에도 그대로 적용된다. 수집이 멈춰 저장소에 새 점이 안 들어오면 "CPU 90% 초과" 같은 규칙은 조건을 만족하지 않으니 울리지 않는다. 데이터가 없을 때 조용해지는 규칙만 있으면 수집 장애가 알림 공백이 된다. 중요한 대상에는 "점이 5분 동안 없다"(`absent()`나 `up == 0`)를 묻는 규칙을 따로 건다.

## 만들지, 가져다 쓸지

면접에서는 알림과 시각화를 직접 설계하라고 하지만, 실제로 이 둘을 처음부터 만드는 회사는 드물다. 대시보드는 [Grafana](/posts/grafana-dashboards)가 사실상 표준이고, 알림 발송과 묶기는 Alertmanager나 PagerDuty, Opsgenie 같은 서비스가 맡는다. 질 좋은 시각화 도구를 만드는 데 드는 노력은 이 시스템의 다른 부품을 다 합친 것보다 크다.

그래서 면접에서는 "알림과 시각화는 검증된 도구를 쓰고, 우리는 수집과 저장, 조회 서비스의 규모를 책임진다"고 말하는 게 현실적인 답이다. 면접관이 더 깊이 들어가고 싶어 하면 그때 위의 상태 저장과 중복 거르기를 꺼낸다.

## 현장에서 이 구조가 드러나는 순간

장애 중에 대시보드가 느려지거나 멈춘다면 조회 서비스의 쿼리 수와 한 쿼리가 읽는 시계열 수를 본다. 정규식 라벨(`host=~".*"`)로 수십만 시계열을 한 번에 읽는 패널이 하나만 있어도 저장소가 버티지 못한다. 자주 묻는 무거운 합계는 기록 규칙(recording rule)으로 미리 계산해 두고, 조회 서비스에 쿼리당 시계열 수 상한을 둔다.

알림이 늦게 왔다는 문의가 오면 앞에서 더한 지연을 하나씩 잰다. 큐의 컨슈머 랙이 쌓여 있으면 평가기는 몇 분 전 세상을 보고 있다. 평가 한 바퀴가 간격(15초)보다 오래 걸리면 평가가 밀린다. Prometheus는 이걸 `prometheus_rule_group_last_duration_seconds`로 보여 준다.

같은 알림이 두 번 왔다면 중복 판별 키를 본다. 키에 발생 시각(`at`)처럼 매번 바뀌는 값을 넣으면 같은 사건도 다른 키가 돼서 거르지 못한다. 키는 사건이 시작된 시각처럼 같은 사건 동안 바뀌지 않는 값으로 만든다. 평가기를 두 대 띄워 이중화했다면, 두 대가 같은 키를 만들어야 받는 쪽에서 하나로 합쳐진다.

오래된 기간의 그래프가 이상하게 매끈하다면 읽는 단계가 바뀐 경계다. 패널의 간격을 확인하고, 필요하면 최댓값 칸으로 그려 스파이크가 있었는지 본다.

## 다음에 읽을 글

저장은 해상도 세 단계로 나눠 1년을 담았다. 원본이 들어오는 대로 위 단계를 채우고, 칸에는 합계와 건수, 최솟값과 최댓값을 둔다. 조회 서비스가 패널 폭에 맞춰 읽을 단계를 고르고, 끝난 칸만 칸 단위로 캐시한다. 알림은 상태를 바깥 저장소에 두고, 최소 한 번 보내되 사건마다 변하지 않는 키로 중복을 거른다. 알림 시스템 자체는 바깥에서 늘 울리는 신호로 지켜본다.

다음 사례 [㊹ 광고 클릭 집계 ①](/posts/sd-ad-click-stream-windows)은 비슷한 모양의 파이프라인을 다룬다. 이번엔 숫자 몇 개를 잃어도 되는 지표가 아니라, 하나라도 틀리면 돈이 틀어지는 광고 클릭이다. 그래서 늦게 온 이벤트와 중복을 훨씬 엄격하게 다룬다. 시계열 저장소 자체를 더 알고 싶다면 [시계열 DB](/posts/db-type-time-series)를, 알림 규칙을 잘 쓰는 법은 [알림 설계](/posts/alerting)를 보자.

## 면접에서 나올 만한 질문

### 1년치 지표를 어떻게 저장하나요?

해상도를 단계로 나눈다. 예를 들어 원본 10초는 7일, 1분 칸은 30일, 1시간 칸은 1년 둔다. 원본이 들어오는 대로 위 단계도 채워 두고, 단계마다 기한이 지나면 지운다. 압축 전 기준으로 원본만 1년이면 약 505TB인데 세 단계로 나누면 약 30TB가 된다.

### 다운샘플링한 칸에는 무엇을 담나요?

평균이 아니라 건수와 합계, 최솟값, 최댓값을 담는다. 평균은 건수가 다른 칸끼리 다시 합칠 수 없고, 짧은 스파이크를 묻어 버린다. 30초짜리 100% 스파이크가 1시간 평균으로는 14.6%였지만 최댓값에는 100이 남았다. 응답 시간 같은 지표는 히스토그램 칸 수를 그대로 합쳐 둔다.

### 조회할 때 어느 해상도를 읽을지 어떻게 정하나요?

패널이 그릴 수 있는 점 수로 범위를 나눠 원하는 간격을 구하고, 그 간격보다 촘촘하면서 범위를 다 덮는 가장 거친 단계를 읽는다. 최근 2일은 원본 대신 1분 칸을 읽어 읽는 양이 6분의 1로 줄었고, 6개월은 1시간 칸을 읽고 5시간씩 한 번 더 묶었다. 이 선택은 조회 서비스가 숨긴다.

### 대시보드 조회를 캐시하면 효과가 있나요?

키를 잘 잡아야 있다. 요청 범위를 그대로 키로 쓰면 새로 고칠 때마다 현재 시각이 달라져 한 번도 맞지 않는다. 범위를 간격에 맞춰 칸으로 자르고 끝난 칸만 캐시하면, 실험에서 저장소가 읽은 양이 7,200줄에서 484줄로 줄었다. 진행 중인 마지막 칸은 매번 새로 읽는다.

### 알림 평가기가 재시작되면 어떤 문제가 생기나요?

상태를 메모리에만 두면 이미 울린 알림을 잊고, 대기부터 다시 시작해 같은 사건으로 또 울린다. 그사이 버티는 시간 동안은 감시 공백도 생긴다. 상태를 바깥 저장소에 두고 재시작할 때 읽어 오면 이어서 평가한다. Prometheus는 대기 상태를 시계열로 저장해 복원한다.

### 알림이 두 번 가지도, 빠지지도 않게 하려면요?

빠지지 않게 발송은 최소 한 번으로 하고, 두 번 가지 않게 키로 거른다. 키는 규칙 이름과 라벨로 만든 지문에 사건이 시작된 시각을 붙여, 같은 사건이면 언제 다시 보내도 같게 만든다. 발송기가 보낸 키는 저장소에 남기고, PagerDuty 같은 받는 쪽에도 같은 키를 넘겨 한 번 더 거른다.

### 알림 시스템 자체가 죽으면 어떻게 알 수 있나요?

늘 울리는 알림을 하나 두고 바깥의 다른 시스템이 그 신호를 받게 한다. 신호가 몇 분 끊기면 바깥 시스템이 사람을 부른다. 바깥 시스템은 알림 파이프라인과 다른 큐, 다른 지역에 둬야 함께 죽지 않는다. 수집이 멈춘 경우를 잡으려면 점이 없을 때 울리는 규칙도 따로 건다.

### 지표 수가 10배가 되면 어디부터 손보나요?

먼저 늘어난 이유를 본다. 라벨 하나가 가짓수를 키운 경우가 많아서, 라벨을 고치는 게 저장소를 늘리는 것보다 싸다. 정말 늘었다면 저장소를 시계열 해시로 샤딩해 노드를 늘리고, 중간 단계 해상도를 줄여 용량을 확보한다. 조회 쪽에는 쿼리당 시계열 수 상한을 두고 무거운 합계는 미리 계산해 둔다.
