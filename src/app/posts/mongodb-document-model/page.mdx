이 문서 하나로 주문 상세 화면이 그려진다. 조인이 없고, 디스크에서도 한 곳에 모여 있어 한 번에 읽힌다. 문서 모델의 장점은 이게 거의 전부이고, 나머지는 이 장점을 지키면서 생기는 부작용을 다루는 이야기다.

관계형 모델은 반대 방향에서 출발한다. 데이터를 중복 없이 정규화해 두고, 어떤 질문이 와도 조인으로 답할 수 있게 한다. 질문을 미리 몰라도 된다는 게 강점이다. 문서 모델은 질문(접근 패턴)을 먼저 알고, 그 질문에 맞는 모양으로 저장한다. 질문이 바뀌면 모양도 바꿔야 한다.

## 넣을까, 가리킬까

문서 설계의 대부분은 관련 데이터를 내장(embed)할지 참조(reference)할지 고르는 일이다. 기준은 몇 가지로 정리된다.

함께 읽히는가. 주문 상품처럼 부모를 읽을 때 늘 같이 읽으면 넣는다. 따로 읽히는 일이 많으면 나눈다.

얼마나 많은가. MongoDB 쪽에서 자주 쓰는 구분이 있다.

- 1 대 몇 개(one-to-few): 회원의 배송지 서너 개. 그냥 배열로 넣는다.
- 1 대 여러 개(one-to-many): 상품 하나의 리뷰 수백~수천 개. 부모에 넣으면 문서가 계속 커진다. 리뷰를 별도 컬렉션에 두고 `productId`로 부모를 가리키되, 상품 문서에는 최근 리뷰 몇 개와 리뷰 수만 복사해 둔다(subset 패턴). 상품 페이지 첫 화면은 상품 문서 하나로 그린다.
- 1 대 엄청 많이(one-to-squillions): 서버 하나의 로그 수억 건. 부모에 id 배열조차 둘 수 없다. 로그 쪽에 부모 id를 적는다.

크기 제한. 문서 하나는 최대 16MB다. 이 제한에 실제로 부딪히는 경우는 대부분 끝없이 자라는 배열(unbounded array) 때문이다. 리뷰나 댓글, 이벤트 기록을 부모 배열에 계속 `$push`하는 설계는 언젠가 16MB에 닿는다. 그 전에도 문제가 생긴다. 문서가 클수록 읽을 때마다 메모리에 올리는 양이 커지고, 배열에 걸린 인덱스 항목도 원소 수만큼 늘어난다.

바뀌는가, 고정인가. 주문의 상품 가격과 배송지는 주문 시점에 고정돼야 해서 일부러 복사한다. 이건 중복이 아니라 스냅샷이다. 반대로 상품 설명처럼 자주 바뀌고 여러 곳에서 보여 주는 값을 여기저기 복사하면, 바꿀 때마다 모든 사본을 찾아 고쳐야 한다.

참조한 데이터를 같이 읽어야 할 때는 애플리케이션에서 쿼리를 두 번 하거나 집계의 `$lookup`으로 붙인다. `$lookup`은 조인과 비슷하지만, 관계형 DB만큼 최적화돼 있다고 기대하면 안 된다. 화면마다 `$lookup`이 필요하다면 문서 경계를 잘못 그은 신호인 경우가 많다.

## 스키마가 없다는 건 검사도 내가 한다는 뜻

MongoDB는 컬렉션에 어떤 모양의 문서든 넣을 수 있다. 처음엔 편하다. 필드를 하나 추가할 때 마이그레이션이 필요 없다. 그런데 시간이 지나면 같은 컬렉션 안에 `price`가 숫자인 문서와 문자열인 문서, `status`가 `"paid"`인 문서와 `"PAID"`인 문서가 섞인다. 코드는 모든 경우를 처리해야 하고, 쿼리는 조용히 일부 문서를 놓친다.

그래서 운영하는 컬렉션에는 검증 규칙을 거는 편이 낫다. `$jsonSchema`로 필수 필드와 타입, 허용 값을 정한다.

```js
db.createCollection("orders", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["user", "items", "status", "total"],
      properties: {
        status: { enum: ["pending", "paid", "shipped", "cancelled"] },
        total: { bsonType: "number", minimum: 0 },  // int·long·double 모두 허용
        items: { bsonType: "array", minItems: 1 },
      },
    },
  },
  validationLevel: "strict",   // 모든 쓰기를 검사
  validationAction: "error",   // 어기면 거절 ("warn"은 로그만)
});
```

이미 데이터가 있는 컬렉션에 규칙을 새로 걸 때는 `validationLevel: "moderate"`가 쓸모 있다. 이미 규칙을 어기던 문서를 수정할 때는 검사하지 않아서, 옛 문서를 한 번에 고치지 않고도 새 문서부터 규칙을 지키게 할 수 있다. 스키마가 바뀌는 중간 기간에는 문서에 `schemaVersion` 필드를 두고, 읽을 때 버전에 따라 변환하거나 백그라운드로 천천히 옮긴다.

## 인덱스 필드 순서는 ESR

인덱스가 없으면 MongoDB도 컬렉션 전체를 훑는다(COLLSCAN). 인덱스 구조는 관계형 DB와 같은 B-tree 계열이라, 복합 인덱스는 앞 필드부터 정렬된다. 그래서 필드 순서가 중요하다. MongoDB 문서가 권하는 규칙이 ESR이다. 같음(Equality) 조건 필드를 먼저, 정렬(Sort) 필드를 다음, 범위(Range) 조건 필드를 마지막에 둔다.

예를 들어 "이 회원의 결제 완료 주문 중 5만 원 이상을 최근 순으로"라는 쿼리가 있다.

```js
db.orders.find({ "user._id": uid, status: "paid", total: { $gte: 50000 } })
         .sort({ createdAt: -1 })
         .limit(20);
```

인덱스가 제대로 쓰이는지는 `explain("executionStats")`로 확인한다. 볼 숫자는 세 개다. 돌려준 문서 수(`nReturned`), 훑은 인덱스 키 수(`totalKeysExamined`), 읽은 문서 수(`totalDocsExamined`). 셋이 비슷할수록 좋은 인덱스다. 20개를 돌려주려고 문서 10만 개를 읽었다면 인덱스가 조건을 못 걸러 주고 있는 것이고, 실행 계획에 `SORT` 단계가 보이면 정렬을 메모리에서 하고 있는 것이다.

알아 둘 성질이 몇 가지 더 있다. 복합 인덱스 `{a, b, c}`는 `a`, `a+b`, `a+b+c`로 시작하는 쿼리에 쓰이지만 `b`만으로는 못 쓴다(접두사 규칙). 배열 필드에 인덱스를 걸면 원소마다 항목이 생기는 멀티키 인덱스가 되는데, 복합 인덱스 하나에 배열 필드를 두 개 넣을 수는 없다. 인덱스는 쓰기마다 함께 갱신되니, 읽기를 빠르게 하는 만큼 쓰기를 느리게 하고 메모리를 차지한다. 자주 쓰는 인덱스가 메모리(WiredTiger 캐시)에 다 올라가 있는지가 성능을 크게 가른다.

## 문서 하나는 원자적이다

MongoDB에서 문서 하나에 대한 쓰기는 원자적이다. 문서 안의 배열과 중첩 객체까지 포함해서, 한 번의 `updateOne`은 전부 반영되거나 하나도 반영되지 않는다. 위 주문에서 `items`에 상품을 추가하고 `total`을 고치는 건 한 번의 쓰기로 끝난다.

```js
db.orders.updateOne(
  { _id: orderId, status: "pending" },
  {
    $push: { items: { productId: 3001, name: "이어팁", price: 5000, qty: 1 } },
    $inc: { total: 5000 },
  }
);
```

여러 문서를 묶는 트랜잭션도 있다. 4.0부터 복제본 셋에서, 4.2부터 샤드 클러스터에서 쓸 수 있다. 재고 차감과 주문 생성을 한 번에 처리하는 식으로 쓴다. 그런데도 MongoDB에서는 트랜잭션이 필요 없도록 설계하라고 권한다. 이유는 비용이다.

- 트랜잭션이 열려 있는 동안 바뀐 내용을 캐시에 붙잡아 두므로, 길어지면 메모리 압박이 커진다. 기본 실행 시간 제한은 60초(`transactionLifetimeLimitSeconds`)다.
- 같은 문서를 건드리는 다른 트랜잭션과 부딪히면(write conflict) 한쪽이 실패하고, 애플리케이션이 `TransientTransactionError`를 보고 다시 시도해야 한다. 드라이버의 `withTransaction`이 이 재시도를 해 준다.
- 샤드 여러 개에 걸치면 샤드끼리 2단계 커밋을 하므로 더 느리다.

트랜잭션이 자주 필요하다면, 함께 바뀌어야 하는 데이터가 여러 문서로 흩어져 있다는 뜻이다. 먼저 문서 경계를 다시 그어 볼 일이다. 그래도 계좌 이체나 재고처럼 여러 엔티티가 꼭 같이 바뀌어야 하는 곳에는 트랜잭션을 쓰는 게 맞다. 문서 하나 안에서는 `{ _id, status: "pending" }`처럼 조건을 걸고 업데이트해서, 다른 요청이 먼저 바꿨으면 아무 일도 안 일어나게 하는 방식(낙관적 동시성 제어)도 자주 쓴다.

## 쓰기가 끝났다는 건 어디까지인가

운영 환경의 MongoDB는 보통 복제본 셋(replica set)이다. 프라이머리 하나가 쓰기를 받고, 세컨더리 둘 이상이 프라이머리의 변경 기록(oplog)을 가져가 똑같이 적용한다. 프라이머리가 죽으면 남은 멤버끼리 투표해서 새 프라이머리를 뽑는다. 투표에서 과반이 필요하니 멤버는 보통 3개 이상 홀수로 둔다.

여기서 문제가 하나 생긴다. 앱이 쓰기 성공 응답을 받은 시점에, 그 데이터는 몇 대에 있을까. 이걸 정하는 게 쓰기 확인 수준(write concern)이다. 아래 그림은 `w: "majority"`로 주문을 넣는 과정이다.

`w: 1`이면 프라이머리 한 대만 쓰고 바로 성공이라고 답한다. 빠르지만, 그 직후 세컨더리로 복제되기 전에 프라이머리가 죽으면 새 프라이머리에는 그 주문이 없다. 옛 프라이머리가 돌아오면 자기만 가진 쓰기를 되돌린다(rollback). 앱은 성공 응답을 받았는데 데이터는 사라지는 것이다. `w: "majority"`는 과반이 가진 데이터만 성공으로 답해서 이걸 막는다. 5.0부터는 대부분의 구성에서 기본 write concern이 `majority`다(아비터가 있는 일부 구성은 예외). `j: true`를 함께 주면 디스크 저널까지 기록된 뒤에 확인한다.

읽기 쪽에도 두 개의 손잡이가 있다.

- read preference: 어느 멤버에서 읽을지. 기본은 `primary`다. `secondaryPreferred`로 읽기를 세컨더리에 나누면 프라이머리 부하가 줄지만, 복제가 늦은 만큼 옛 데이터를 읽는다. 주문 직후 "내 주문 목록"을 세컨더리에서 읽으면 방금 한 주문이 안 보일 수 있다.
- read concern: 어떤 상태의 데이터를 읽을지. 기본 `local`은 그 멤버가 가진 최신 값을 읽는데, 나중에 rollback될 수도 있는 값이다. `majority`는 과반에 반영된 값만 읽는다. `linearizable`은 가장 강하지만 느리다.

내가 쓴 걸 내가 바로 읽어야 하는 화면은 프라이머리에서 읽거나, 인과적 일관성(causal consistency) 세션과 majority 읽기·쓰기를 함께 써서 순서를 보장한다.

## 샤드 키 하나가 클러스터 모양을 정한다

샤드 키는 컬렉션의 문서를 나누는 기준 필드다. 좋은 샤드 키를 고를 때 보는 성질은 이렇다.

카디널리티. 서로 다른 값이 충분히 많아야 한다. `status`처럼 값이 네 개뿐인 필드로 나누면 데이터를 네 덩어리 이상으로 쪼갤 수 없다.

빈도. 특정 값에 몰리면 안 된다. 회원 id로 나눴는데 대형 판매자 계정 하나가 주문의 절반을 만든다면 그 키가 있는 샤드만 바쁘다.

단조 증가 여부. 가장 흔한 실수가 여기서 나온다. 기본 `_id`(ObjectId)나 `createdAt`처럼 시간이 갈수록 커지는 값으로 범위 샤딩을 하면, 새 문서가 전부 가장 큰 키 범위, 즉 마지막 샤드 한 곳으로 몰린다. 샤드가 열 개여도 쓰기는 한 대가 다 받는 핫스팟이 된다. 해시 샤딩(`{ _id: "hashed" }`)으로 바꾸면 쓰기가 고르게 퍼지지만, 이번엔 "최근 일주일 주문" 같은 범위 쿼리가 모든 샤드로 흩어진다.

쿼리 격리. 자주 하는 쿼리에 샤드 키가 들어 있어야 `mongos`가 샤드 하나로만 보낸다(targeted query). 없으면 모든 샤드에 묻고 결과를 모은다(scatter-gather). 샤드가 늘수록 비싸진다.

그래서 주문 컬렉션이라면 `{ "user._id": 1, createdAt: 1 }`처럼 복합 키를 고려한다. 회원 id로 고르게 퍼지고, "내 주문 목록"은 샤드 하나에서 끝나며, 같은 회원 안에서는 시간 순 범위 조회가 된다. 샤드 키는 예전엔 한 번 정하면 못 바꿨지만, 4.4부터 키 뒤에 필드를 덧붙이는 refine이, 5.0부터 아예 다른 키로 다시 나누는 resharding이 가능하다. 그래도 resharding은 컬렉션 전체를 옮기는 무거운 작업이라, 처음 고를 때 신중해야 한다는 건 그대로다.

## 모아서 계산하기: 집계 파이프라인

"회원별 결제 금액 합계 순위" 같은 질문은 `find`로 못 한다. 집계 파이프라인을 쓴다. 문서들이 단계(stage)를 차례로 통과하면서 걸러지고, 묶이고, 정렬된다.

```js
db.orders.aggregate([
  { $match: { status: "paid" } },
  { $group: { _id: "$user.name", total: { $sum: "$total" } } },
  { $sort: { total: -1 } },
]);
```

아래 그림에서 "다음"을 누르면 주문 다섯 건이 이 파이프라인을 지나간다. 금액 단위는 만 원이다.

파이프라인에서 성능을 가르는 건 순서다. `$match`와 `$sort`를 맨 앞에 두면 인덱스를 쓸 수 있지만, `$group`이나 `$project` 뒤로 가면 인덱스를 못 쓰고 이미 메모리에 올린 문서들을 대상으로 돈다. 그래서 거를 수 있는 건 최대한 일찍 거른다. `$group`이나 `$sort` 같은 단계는 단계마다 메모리 100MB 제한이 있고, 넘으면 디스크를 쓰도록(`allowDiskUse`) 해야 한다. 6.0부터는 이게 기본으로 허용된다.

그 밖에 자주 쓰는 단계로는 배열을 원소마다 한 문서로 펼치는 `$unwind`(상품별 판매량을 셀 때 `items`를 펼친다), 다른 컬렉션을 붙이는 `$lookup`, 한 번에 여러 집계를 돌리는 `$facet`이 있다. 대시보드처럼 같은 집계를 자주 돌린다면 결과를 `$merge`로 별도 컬렉션에 저장해 두고 그걸 읽는 것도 방법이다.

## 느린 쿼리 로그에 COLLSCAN이 보이면

주문 목록 API가 가끔 수백 ms씩 걸린다는 알림이 온다. MongoDB는 기본으로 100ms(`slowms`)를 넘긴 연산을 서버 로그에 남기니 거기서 시작한다. 4.4부터 로그가 한 줄짜리 JSON이라 `jq`로 거르기 쉽다. 이 절의 출력은 이 글을 쓴 환경에서 MongoDB를 띄울 수 없어서 형식에 맞춰 적은 예시다.

```bash
# 느린 쿼리만 골라 컬렉션, 실행 계획 요약, 읽은 문서 수, 걸린 시간을 본다
sudo grep '"Slow query"' /var/log/mongodb/mongod.log | tail -n 5 \
  | jq -c '.attr | {ns, planSummary, keysExamined, docsExamined, nreturned, durationMillis}'
```

```text
{"ns":"shop.orders","planSummary":"COLLSCAN","keysExamined":0,"docsExamined":184213,"nreturned":20,"durationMillis":412}
```

`planSummary`가 `COLLSCAN`이고, 20개를 돌려주려고 문서 18만 개를 읽었다. 앞에서 본 세 숫자(nReturned, totalKeysExamined, totalDocsExamined)가 로그에도 그대로 있는 셈이다. `IXSCAN { user._id: 1, ... }`인데도 `docsExamined`가 `nreturned`보다 훨씬 크면 인덱스가 조건 일부만 걸러 주는 것이고, `hasSortStage: true`가 함께 찍히면 ESR 순서가 어긋나 메모리에서 정렬하고 있는 것이다. 로그에서 쿼리 모양(`attr.command.filter`, `sort`)을 꺼내 `explain("executionStats")`로 다시 확인하고 인덱스를 고친다.

로그보다 자세히 보고 싶으면 프로파일러를 잠깐 켠다. 켜 둔 동안 쓰기 부담이 생기니 기준을 정해 짧게 쓰고 끈다.

```js
// 50ms 넘는 연산을 이 DB의 system.profile 컬렉션에 남긴다
db.setProfilingLevel(1, { slowms: 50 });
db.system.profile.find().sort({ ts: -1 }).limit(5);

// 지금 5초 넘게 돌고 있는 연산. 급하면 opid로 끊는다
db.currentOp({ active: true, secs_running: { $gte: 5 } });
db.killOp(12345);

db.setProfilingLevel(0); // 다 봤으면 끈다
```

인덱스를 새로 만들 때는 운영 시간을 피한다. 4.2부터 인덱스 생성이 컬렉션 전체를 오래 잠그지는 않지만, 큰 컬렉션을 훑는 동안 디스크와 캐시를 많이 쓴다.

두 번째로 자주 받는 문의는 "방금 주문했는데 주문 목록에 없다"다. 읽기를 세컨더리로 보내 두었다면(`secondaryPreferred`) 먼저 복제 지연을 본다.

```js
rs.printSecondaryReplicationInfo();
```

```text
source: mongo-2.shop.internal:27017
{
  syncedTo: 'Sun Oct 18 2026 02:20:19 GMT+0000 (Coordinated Universal Time)',
  replLag: '-12 secs (0 hrs) behind the primary '
}
```

세컨더리가 12초 늦다면, 주문 직후 12초 동안은 목록에서 안 보이는 게 정상 동작이다. 앞에서 본 것처럼 방금 쓴 걸 바로 보여 줘야 하는 화면은 프라이머리에서 읽게 하고, 지연 자체가 크면 세컨더리의 디스크나 큰 일괄 쓰기를 의심한다. 복제 지연을 모니터링 지표로 걸어 두면 이런 문의가 오기 전에 안다.

세 번째는 연결이다. 배포로 Pod가 늘어난 날 MongoDB의 메모리와 CPU가 같이 오른다면 연결 수를 본다.

```js
db.serverStatus().connections;
```

```text
{ current: 4870, available: 46330, totalCreated: 98123, active: 312 }
```

드라이버는 프로세스마다 연결 풀을 갖는다(Node.js 드라이버의 `maxPoolSize` 기본값은 100). Pod 40개에 프로세스 하나씩이면 최대 4,000개다. 연결 하나마다 서버 쪽 메모리와 스레드가 들어서, `active`는 300인데 `current`가 5천 가까이 되면 대부분 놀고 있는 연결 비용만 내는 것이다. 풀 크기를 실제 동시 쿼리 수에 맞춰 줄이고, `totalCreated`가 빠르게 는다면 요청마다 클라이언트를 새로 만드는 코드를 찾는다.

검증 규칙을 건 컬렉션에서는 배포 뒤 `MongoServerError: Document failed validation`이 갑자기 늘기도 한다. 새 코드가 규칙에 없는 `status` 값을 쓰기 시작한 경우가 많다. 5.0부터는 에러의 `errInfo`에 어떤 필드가 어떤 규칙에 걸렸는지가 담겨 오니, 로그에 이 필드까지 남겨 두면 원인을 바로 찾는다.

## 결국 읽는 모양에서 출발한다

MongoDB 설계는 화면과 API가 데이터를 어떤 모양으로 읽는지에서 출발한다. 함께 읽는 건 한 문서에 넣고, 끝없이 자라거나 따로 읽히는 건 나눠서 참조한다. 그러면 대부분의 쓰기가 문서 하나에서 끝나 트랜잭션 없이도 원자적이고, 인덱스는 ESR 순서로 그 읽기를 받쳐 준다. 규모가 커지면 그 읽기 패턴에 맞춰 샤드 키를 고른다. 스키마가 자유로운 만큼, 검증 규칙과 쓰기 확인 수준은 내가 정해 줘야 한다.

## 면접에서 나올 만한 질문

### 문서 모델은 관계형 모델과 무엇이 다른가요?

관계형은 데이터를 정규화해 테이블로 나누고 읽을 때 조인으로 붙인다. 문서 모델은 함께 읽는 데이터를 한 문서에 중첩해 저장해서 조인 없이 한 번에 읽는다. 관계형은 질문을 미리 몰라도 대응할 수 있고, 문서 모델은 접근 패턴을 먼저 정하고 그 모양에 맞춰 저장한다. 그래서 접근 패턴이 바뀌면 문서 구조도 바꿔야 한다.

### 내장과 참조는 어떤 기준으로 고르나요?

함께 읽히고, 개수가 한정돼 있고, 부모 없이 쓰이지 않으면 내장한다. 수백 개 이상으로 자라거나 따로 조회되거나 여러 곳에서 공유되며 자주 바뀌면 참조한다. 끝없이 자라는 배열은 16MB 제한에 닿고 성능도 나빠지므로 피한다. 주문의 가격처럼 시점 값을 남겨야 하는 경우는 일부러 복사해 스냅샷으로 둔다.

### 스키마가 없으면 어떤 문제가 생기고 어떻게 막나요?

같은 필드가 문서마다 다른 타입이나 값으로 섞여서 코드가 모든 경우를 처리해야 하고 쿼리가 조용히 문서를 놓친다. `$jsonSchema` 검증 규칙으로 필수 필드와 타입, 허용 값을 강제한다. 기존 데이터가 있으면 `validationLevel: "moderate"`로 새 쓰기부터 지키게 하고, `schemaVersion` 필드로 점진적으로 옮긴다.

### 복합 인덱스의 필드 순서는 어떻게 정하나요?

ESR 규칙을 따른다. 같음 조건 필드, 정렬 필드, 범위 조건 필드 순이다. 범위를 정렬 앞에 두면 인덱스 구간이 범위 필드 순으로 놓여 메모리 정렬이 필요해진다. explain의 nReturned, totalKeysExamined, totalDocsExamined가 비슷하고 SORT 단계가 없는지로 확인한다.

### MongoDB도 트랜잭션이 있는데 왜 피하라고 하나요?

4.0부터 복제본 셋, 4.2부터 샤드 클러스터에서 다중 문서 트랜잭션을 쓸 수 있다. 하지만 캐시에 변경을 붙잡아 두고, 충돌 시 재시도가 필요하고, 샤드에 걸치면 2단계 커밋으로 느려진다. 문서 하나의 쓰기는 원자적이니 함께 바뀌는 데이터를 한 문서에 두면 대부분 트랜잭션이 필요 없다. 여러 엔티티가 꼭 같이 바뀌어야 하는 곳에만 쓴다.

### write concern w:1과 majority는 무엇이 다른가요?

w:1은 프라이머리만 쓰면 성공으로 답해서 빠르지만, 복제 전에 프라이머리가 죽으면 그 쓰기가 롤백되어 사라질 수 있다. majority는 과반 멤버가 적용한 뒤 답하므로 장애 조치 후에도 남는다. 5.0부터 대부분의 구성에서 기본값이 majority다. 세컨더리에서 읽으면 복제 지연 때문에 방금 쓴 값이 안 보일 수 있으니 read preference와 read concern도 함께 정한다.

### 샤드 키는 어떻게 고르고, ObjectId로 샤딩하면 왜 문제가 되나요?

카디널리티가 높고, 값이 고르게 분포하고, 자주 하는 쿼리에 포함되는 필드를 고른다. ObjectId는 앞부분이 시각이라 계속 커지므로 범위 샤딩하면 새 쓰기가 전부 마지막 샤드로 몰리는 핫스팟이 된다. 해시 샤딩은 쓰기를 퍼뜨리지만 범위 쿼리가 모든 샤드로 흩어진다. 그래서 회원 id와 시간 같은 복합 키를 많이 고려한다.

### 집계 파이프라인 성능을 위해 무엇을 신경 쓰나요?

`$match`와 `$sort`를 앞에 둬서 인덱스를 쓰고 이후 단계로 넘어가는 문서 수를 줄인다. 블로킹 단계는 단계마다 메모리 100MB 제한이 있어 넘으면 디스크를 써야 한다. `$lookup`이 자주 필요하면 문서 경계를 다시 보고, 반복되는 무거운 집계는 `$merge`로 결과를 저장해 둔다.
