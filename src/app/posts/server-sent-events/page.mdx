<EasyIntro>
  주문 상태 화면을 서버가 소식을 이어 보내는 SSE로 만들었다. 내 컴퓨터에서는 잘 됐는데 배포하자 소식이 몇 분씩 안 오다가 한꺼번에 오고, 탭을 여러 개 열면 사이트가 멈추고, 배포 중에 접속했던 사람의 화면은 영영 안 바뀐다고 한다.

  SSE는 라디오 방송처럼 서버가 한 응답을 끝내지 않고 소식이 생길 때마다 한 줄씩 이어 쓰는 방식이다. 평범한 웹 요청이라 쉽지만, 그래서 웹 요청이 지나는 길의 모든 규칙을 그대로 받는다. 중간 서버가 방송을 모아 뒀다가 한꺼번에 내보내기도 하고, 오래된 방식의 브라우저는 방송 채널을 여섯 개까지만 열어 주고, 서버가 오류 응답을 한 번만 보내도 브라우저는 다시 듣기를 포기한다.

  브라우저가 언제 알아서 다시 붙고 언제 포기하는지, 어디서 소식이 붙잡히는지를 알면 이 세 가지 신고가 모두 설명된다. 서버에서만 소식이 오는 기능이라면 길만 잘 비워 두면 SSE가 가장 가벼운 선택이다.

주문 상태 화면을 SSE로 만들었다. 로컬에서는 이벤트가 바로바로 왔는데 배포하자 이상한 일이 생긴다. 어떤 사용자는 이벤트가 몇 분씩 안 오다가 한꺼번에 온다고 하고, 어떤 사용자는 탭을 여러 개 열면 사이트 전체가 멈춘다고 하고, 배포 중에 접속해 있던 사용자의 화면은 그 뒤로 영영 갱신되지 않는다. SSE는 "그냥 HTTP"라서 쉽다고들 하는데, 그냥 HTTP라서 HTTP 경로의 모든 장비와 브라우저 규칙을 그대로 받는다.

SSE가 폴링이나 WebSocket과 비교해 어디에 서는지는 [서버가 먼저 말하게 하기](/posts/realtime-communication)에서 봤다. 그 글에 이벤트 스트림 필드와 파서도 있다. 이 글은 SSE를 운영할 때 부딪히는 질문에 답한다. 브라우저가 끊긴 스트림에 실제로 어떻게 다시 붙는지, 어떤 응답에서 영영 포기하는지, HTTP/1.1의 연결 6개 제한이 정말 사이트를 멈추는지, 압축과 프록시가 이벤트를 어디서 붙잡는지, LLM 답변 스트리밍은 왜 `EventSource`를 안 쓰는지를 Chromium 141, Node.js 22, nginx 1.24(Ubuntu 24.04)로 직접 확인했다.

## 서버가 내려보내는 바이트 그대로 보기

SSE 응답은 평범한 HTTP 응답인데 끝나지 않는다. `curl -N`은 출력 버퍼링을 꺼서 받는 대로 찍어 준다.

```bash
# -N: 받는 즉시 출력, -i: 응답 헤더도 보기
curl -sN -i --max-time 3 http://127.0.0.1:19790/stream
```

```text
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no
Date: Tue, 20 Oct 2026 19:56:14 GMT
Connection: keep-alive
Keep-Alive: timeout=5
Transfer-Encoding: chunked

retry: 2000

id: 1
event: status
data: order 42 step 1

id: 2
event: status
data: order 42 step 2
```

`Content-Length`가 없고 `Transfer-Encoding: chunked`다. 서버가 본문 길이를 모른 채로 조각을 계속 보낸다는 뜻이다. HTTP/2에서는 chunked 대신 DATA 프레임으로 같은 일을 한다. 헤더 하나하나가 왜 들어가는지 눌러 보자.

## id와 retry는 다음 이벤트까지 남는다

필드 규칙은 개요 글에 정리했고, 여기서는 운영에서 헷갈리는 부분만 짚는다. 브라우저는 스트림을 읽으면서 상태 몇 개를 들고 있다. 마지막 이벤트 id, 재연결 대기 시간, 지금 모으고 있는 data와 이벤트 이름이다. 이 중 id와 retry는 이벤트가 끝나도 지워지지 않는다. 아래 그림에서 스트림을 한 줄씩 읽어 보자.

실무에서 의미가 큰 건 넷째, 다섯째 단계다. id를 일부 이벤트에만 붙이면 재연결 때 서버가 받는 Last-Event-ID가 그 이벤트들 사이 어딘가를 가리켜서, 서버는 이미 보낸 이벤트를 다시 보내게 된다. 이어 받기가 필요한 스트림이라면 모든 이벤트에 id를 붙인다.

서버에서 이 형식을 만들 때 흔한 실수는 템플릿 문자열에 값을 그대로 넣는 것이다. `data: ${text}\n\n`에 사용자가 쓴 채팅 내용이 들어가는데 그 안에 빈 줄과 `event: admin` 같은 줄이 있으면, 받는 쪽에서는 이벤트가 둘로 쪼개지고 가짜 이벤트가 생긴다. data는 줄마다 `data:`를 붙여 나누고, id와 event에는 줄바꿈이 들어가지 못하게 막아야 한다. 아래 함수로 직접 만들어 보자.

## 끊기면 다시 붙고, 어떤 응답에는 포기한다

이제 브라우저가 실제로 어떻게 다시 붙는지 보자. 서버가 `retry: 2000`을 보내고, 이벤트 세 개를 보낸 뒤 일부러 소켓을 끊게 했다. Chromium 페이지에서 `EventSource`를 열고 모든 이벤트에 시각을 찍었다.

```text
  0.01s open
  0.11s status id=1 data=order 42 step 1
  0.21s status id=2 data=order 42 step 2
  0.31s status id=3 data=order 42 step 3
  0.36s error readyState=0
Failed to load resource: net::ERR_INCOMPLETE_CHUNKED_ENCODING
  2.36s open
  2.46s status id=4 data=order 42 step 4
  2.56s status id=5 data=order 42 step 5
  2.66s status id=6 data=order 42 step 6
  2.71s error readyState=0
```

같은 시각 서버 로그다.

```text
 10.43s GET /stream Last-Event-ID=(none)
 10.74s cut after id 3
 12.79s GET /stream Last-Event-ID=3
 13.09s cut after id 6
 15.15s GET /stream Last-Event-ID=6
```

끊기자 `error` 이벤트가 오고 `readyState`가 0(CONNECTING)이 됐다. 정확히 2초 뒤 다시 붙었고, 요청에 `Last-Event-ID: 3`이 자동으로 실렸다. 서버는 그 다음인 4번부터 보냈다. 페이지 코드는 재연결에 관해 한 줄도 쓰지 않았다. `retry`를 보내지 않는 서버로 같은 실험을 하면 Chromium 141은 약 3초 뒤에 다시 붙었다. 이 기본값은 표준이 정하지 않아서 브라우저마다 다를 수 있다.

그럼 포기하는 경우는 언제일까. 500을 돌려주는 경로와 204를 돌려주는 경로에 각각 붙여서 6초 동안 지켜봤다.

```text
== /broken
Failed to load resource: the server responded with a status of 500 (Internal Server Error)
  0.00s error readyState=2
== /stop
  0.01s error readyState=2
```

둘 다 `readyState`가 2(CLOSED)가 됐고, 서버 로그에는 각각 요청이 한 번씩만 찍혔다. 다시 붙지 않는다. 표준은 네트워크 오류로 끊긴 경우에만 다시 연결하고, 200이 아닌 응답이나 `text/event-stream`이 아닌 응답에는 연결을 실패로 끝내라고 정한다. 204는 서버가 "이제 그만 붙어라"라고 말하는 정상적인 방법이다.

여기서 처음의 세 번째 신고가 설명된다. 배포 중에 앞단 nginx나 로드 밸런서가 잠깐 502나 503을 돌려주면, 그 순간 재연결을 시도한 `EventSource`는 전부 CLOSED가 되고 다시는 붙지 않는다. 인증이 만료돼 401이 와도 마찬가지로 조용히 멈춘다. 그래서 `onerror`에서 `readyState`가 CLOSED인지 보고, 그때는 앱이 직접 백오프와 지터를 섞어 새 `EventSource`를 만든다.

```js
function connect(attempt = 0) {
  const es = new EventSource("/orders/42/stream");
  es.onopen = () => { attempt = 0; };
  es.onerror = () => {
    if (es.readyState !== EventSource.CLOSED) return; // 브라우저가 알아서 다시 붙는 중
    es.close();
    const delay = Math.random() * Math.min(30000, 1000 * 2 ** attempt); // full jitter
    setTimeout(() => connect(attempt + 1), delay);
  };
  return es;
}
```

이렇게 새로 만든 `EventSource`는 이전 객체의 마지막 id를 모른다. 이어 받으려면 마지막 id를 앱이 기억했다가 URL 쿼리(`?lastEventId=9`)로 넘기고, 서버는 헤더와 쿼리를 둘 다 확인한다.

## 탭 일곱 개째에서 사이트가 멈춘다

두 번째 신고, "탭을 여러 개 열면 사이트 전체가 멈춘다"는 HTTP/1.1의 연결 수 제한이다. 크롬 계열은 HTTP/1.1에서 출처 하나에 동시 연결을 6개까지만 연다. 끝나지 않는 SSE 응답은 연결 하나를 계속 차지한다. 같은 SSE 서버를 HTTP/1.1과 HTTP/2(TLS)로 각각 열고, 한 페이지에서 `EventSource` 7개를 연 뒤 평범한 `fetch("/ping")`이 언제 끝나는지 봤다. 서버 쪽에서 맺힌 TCP 연결 수도 `ss`로 셌다.

```text
http://127.0.0.1:19791 server-side established: 6
http://127.0.0.1:19791 {"proto":"http/1.1","states":"1,1,1,1,1,1,0","fetch":"(still pending after 5s)","ms":5001}
https://127.0.0.1:19792 server-side established: 1
https://127.0.0.1:19792 {"proto":"h2","states":"1,1,1,1,1,1,1","fetch":"pong","ms":10}
```

HTTP/1.1에서는 TCP 연결이 6개 맺혔고, 일곱째 `EventSource`는 `readyState` 0에서 멈췄다. 더 큰 문제는 `fetch`다. 아무 관계 없는 짧은 요청이 5초가 지나도 끝나지 않았다. 빈 연결이 없으니 줄을 서 있는 것이다. 탭 여러 개도 같은 출처라면 이 6개를 나눠 쓴다. HTTP/2에서는 연결 하나에 스트림 7개와 `fetch`가 함께 실렸고 `fetch`는 10ms에 끝났다.

해결책은 순서대로 이렇다. 먼저 HTTP/2를 쓴다. 대부분의 CDN과 로드 밸런서가 브라우저 쪽은 HTTP/2로 받으니 앞단 설정을 확인한다. 개발 서버나 사내 도구처럼 HTTP/1.1로 남는 환경이라면 페이지 하나에 SSE를 하나만 열고, 필요한 이벤트를 이름(`event:`)으로 나눠 한 스트림에 섞는다. 탭 여러 개 문제는 `BroadcastChannel`이나 `SharedWorker`로 한 탭만 연결하고 나머지 탭에 나눠 주는 방법이 있다. ## 프록시와 압축이 이벤트를 붙잡는 곳

첫 번째 신고, "이벤트가 몇 분씩 안 오다가 한꺼번에 온다"는 경로 어딘가의 버퍼다. 개요 글에서 nginx의 `proxy_buffering`이 이벤트를 붙잡는 것을 봤다. 이번에는 같은 앱에 nginx 설정만 바꿔 가며 0.5초마다 오는 이벤트를 2.2초 동안 받아 봤다. 줄 앞의 시각은 받은 시각이다.

```bash
# 받은 줄마다 시각을 붙인다
ts() { while IFS= read -r l; do [ -n "$l" ] && printf '%s %s\n' "$(date +%T.%1N)" "$l"; done; }
curl -sN --max-time 2.2 http://127.0.0.1:19770/sse10/tick | ts       # proxy_http_version 기본(1.0), 버퍼링 기본
curl -sN --max-time 2.2 http://127.0.0.1:19770/sse10/tick-hdr | ts   # 위와 같고 앱이 X-Accel-Buffering: no
```

```text
== /sse10/tick
19:58:15.7
== /sse10/tick-hdr
19:58:18.0
19:58:18.5 id: 1
19:58:18.5 data: tick 1
19:58:19.0 id: 2
19:58:19.0 data: tick 2
19:58:19.5 id: 3
19:58:19.5 data: tick 3
19:58:20.0 id: 4
19:58:20.0 data: tick 4
```

nginx 설정을 하나도 바꾸지 않고 앱이 응답 헤더 `X-Accel-Buffering: no`를 붙이는 것만으로 이벤트가 제때 왔다. 헤더가 없는 쪽은 2.2초 동안 한 줄도 오지 않았다. 덧붙이면, 같은 실습에서 `proxy_http_version 1.1`을 준 경로는 헤더 없이도 이벤트가 제때 왔다. 업스트림 응답 형식에 따라 동작이 달라지는 셈인데, 이런 세부 동작에 기대지 말고 SSE 경로는 `proxy_buffering off`나 `X-Accel-Buffering: no`로 명시하는 편이 안전하다.

압축은 두 군데서 끼어든다. 앱의 압축 미들웨어와 프록시의 압축이다. 앱이 Node.js `zlib`으로 직접 gzip을 걸고 flush를 안 한 경우, 이벤트마다 flush한 경우, nginx가 `gzip on; gzip_types text/event-stream;`으로 압축한 경우(`proxy_buffering off`)를 비교했다.

```text
== app gzip, no flush
19:58:37.8
== app gzip, flush per event
19:58:41.0
19:58:41.5 id: 1
19:58:41.5 data: tick 1
19:58:42.0 id: 2
19:58:42.0 data: tick 2
19:58:42.5 id: 3
19:58:42.5 data: tick 3
== nginx gzip on, proxy_buffering off
19:58:33.5
19:58:34.1 id: 1
19:58:34.1 data: tick 1
19:58:34.6 id: 2
19:58:34.6 data: tick 2
19:58:35.1 id: 3
19:58:35.1 data: tick 3
```

flush 없는 앱 압축은 3초 동안 아무것도 내보내지 않았다. gzip은 압축 효율을 위해 입력을 모았다가 내보내기 때문이다. 이벤트마다 `flush()`를 부르면 제때 왔다. Express의 `compression` 미들웨어를 쓴다면 이벤트를 쓴 뒤 `res.flush()`를 불러야 하는 이유가 이것이다. nginx의 gzip은 버퍼링을 끈 경로에서 업스트림에서 받은 조각마다 내보내서 이 실습에서는 늦지 않았다. 다만 이벤트가 작으면 압축으로 얻는 게 거의 없으니 SSE 경로는 압축을 끄는 경우가 많다.

## 조용한 스트림은 끊기고, 끊긴 줄도 모른다

하트비트가 왜 필요한지도 직접 봤다. 처음에 이벤트 하나만 보내고 조용해지는 SSE를 nginx 뒤에 두고, 실습을 빨리 보려고 `proxy_read_timeout`을 5초로 줄였다(기본값은 60초). 한 경로는 아무것도 안 보내고, 다른 경로는 2초마다 `: ping` 주석을 보낸다. Chromium에서 각각 12.5초 동안 열어 뒀다.

```bash
# nginx 경로 /sse-idle/ (proxy_buffering off, proxy_read_timeout 5s) 뒤의 두 엔드포인트를 Chromium으로 연다
BASE=http://127.0.0.1:19770/sse-idle/ node sse-browser.js 0 /sse-idle/quiet 12500   # 주석 없음
BASE=http://127.0.0.1:19770/sse-idle/ node sse-browser.js 0 /sse-idle/hb 12500      # 2초마다 : ping
```

```text
  0.01s open
  0.01s message(onmessage) hello
  5.01s error readyState=0
  6.01s open
  6.01s message(onmessage) hello
 11.02s error readyState=0
 12.02s open
 12.02s message(onmessage) hello
---
  0.00s open
  0.00s message(onmessage) hello
```

```text
127.0.0.1 "GET /sse-idle/quiet HTTP/1.1" 200 37 rt=5.005
127.0.0.1 "GET /sse-idle/quiet HTTP/1.1" 200 37 rt=5.005
127.0.0.1 "GET /sse-idle/hb HTTP/1.1" 200 115 rt=12.503
2026/10/20 19:59:02 [error] 13980#13980: *21 upstream timed out (110: Connection timed out) while reading upstream, client: 127.0.0.1, server: , request: "GET /sse-idle/quiet HTTP/1.1", upstream: "http://127.0.0.1:19794/quiet", host: "127.0.0.1:19770", referrer: "http://127.0.0.1:19770/sse-idle/"
```

`---` 위가 주석 없는 경로, 아래가 하트비트 경로다. 주석 없는 스트림은 5초마다 끊기고 1초 뒤(`retry: 1000`) 다시 붙었다. `EventSource`가 알아서 다시 붙으니 화면은 멀쩡해 보인다. 그래서 이 문제는 오래 숨어 있다. 하지만 기본값 60초라면 사용자마다 1분에 한 번씩 연결과 요청이 새로 생기고, 그때마다 인증 확인과 구독 등록이 다시 돈다. access.log에서는 SSE 경로의 200 응답이 `rt`가 한 값에 몰린 채로 쌓이는 것으로 보인다. 응답 헤더를 이미 보낸 뒤라 상태 코드가 200으로 남는다는 것도 눈여겨볼 점이다. 오류율 지표에 잡히지 않는다.

이 실습에는 버그가 하나 더 숨어 있다. 다시 붙을 때마다 `hello`를 또 받았다. 서버 로그에는 두 번째 요청부터 `Last-Event-ID=1`이 찍혔는데, 실습 서버가 그 헤더를 무시하고 매번 1번을 보냈기 때문이다. 하트비트가 없어서 생긴 재연결이 Last-Event-ID를 처리하지 않는 서버를 만나면 사용자는 같은 알림을 1분마다 받는다.

주석 하트비트는 브라우저에 이벤트를 만들지 않는다. 그래서 클라이언트가 "서버가 살아 있나"를 확인하는 용도로는 못 쓴다. 클라이언트 쪽에서 스트림이 멈췄는지 알고 싶으면 하트비트를 `event: heartbeat`처럼 이름 있는 이벤트로 보내고, 일정 시간 안 오면 앱이 연결을 닫고 새로 연다. 서버 쪽에서는 하트비트를 쓰다가 실패하는 순간(쓰기 오류, `close` 이벤트)이 클라이언트가 떠났다는 신호다. 하트비트가 없으면 떠난 클라이언트의 구독을 한참 동안 정리하지 못한다.

## LLM 답변 스트리밍은 EventSource를 쓰지 않는다

LLM API가 답을 토큰 단위로 흘려보낼 때 쓰는 형식이 대부분 `text/event-stream`이다. 그런데 브라우저 `EventSource`는 GET만 보낼 수 있고 요청 헤더도 못 붙인다. 질문이 긴 본문으로 가야 하고 `Authorization` 헤더가 필요한 LLM 호출과 맞지 않는다. 그래서 `fetch`로 POST를 보내고, 응답 본문 스트림을 직접 읽어 빈 줄 단위로 나눈다. 80ms마다 토큰 하나를 보내는 서버로 재 봤다.

```js
// fetch로 POST를 보내고 응답 본문을 조각 단위로 읽는다
const res = await fetch("/chat", {
  method: "POST",
  headers: { "Content-Type": "application/json", Accept: "text/event-stream" },
  body: JSON.stringify({ q: "SSE가 뭐야?" }),
});
const reader = res.body.pipeThrough(new TextDecoderStream()).getReader();
let buf = "";
for (;;) {
  const { value, done } = await reader.read();
  if (done) break;
  buf += value;
  let i;
  while ((i = buf.indexOf("\n\n")) !== -1) {   // 조각 경계와 이벤트 경계는 다르다
    handle(buf.slice(0, i));
    buf = buf.slice(i + 2);
  }
}
```

```text
 181ms first token
1134ms done: SSE는 응답 하나를 끝내지 않고 이어 쓰는 방식이다.
```

토큰 12개를 다 받기까지 1.1초가 걸렸지만 첫 토큰은 0.18초에 보였다. 사용자가 느끼는 대기 시간은 첫 토큰까지의 시간이다. 화면에서 이 흐름을 어떻게 보여 주는지는 [로딩 패턴](/posts/loading-patterns)의 스트리밍 텍스트 부분에 있다.

이 방식은 `EventSource`가 해 주던 것을 전부 직접 해야 한다. 네트워크에서 받는 조각은 이벤트 경계와 맞지 않으니 버퍼에 모았다가 빈 줄에서 자른다(위 코드의 `while`). 한글처럼 여러 바이트인 글자가 조각 사이에서 잘릴 수 있으니 `TextDecoderStream`으로 디코딩한다. 재연결과 Last-Event-ID는 없다. LLM 답변은 보통 재연결보다 처음부터 다시 요청하는 쪽을 택한다. 사용자가 "중지"를 누르면 `AbortController`로 요청을 끊고, 서버는 연결이 닫힌 걸 보고 생성을 멈춰야 비용이 줄어든다. 프록시 버퍼링 문제는 똑같이 걸리니 앞에서 본 설정이 그대로 필요하다.

## SSE를 고를 때와 WebSocket을 고를 때

서버에서 클라이언트로만 흐르는 데이터라면 SSE가 대부분 이긴다. 알림, 주문·배포 진행 상태, 대시보드 지표, 로그 꼬리 보기, LLM 답변이 그렇다. 평범한 HTTP라서 기존 쿠키·토큰 인증, 로드 밸런서, 접근 로그, 모니터링을 그대로 쓰고, 재연결과 이어 받기가 표준에 들어 있다. 연결 하나를 서버가 붙잡는 비용은 WebSocket과 비슷하지만 서버 쪽 코드는 응답에 줄을 쓰는 것이 전부다. HTTP/2 위에서는 연결 수 제한도 사라진다.

WebSocket이 나은 경우는 클라이언트도 자주, 짧게 말할 때다. 채팅, 멀티플레이 게임, 공동 편집, 커서 위치 공유처럼 클라이언트 메시지가 초당 여러 번이라면 메시지마다 HTTP 요청을 보내는 비용이 커진다. 바이너리를 많이 보내야 하는 경우도 WebSocket이다. SSE는 UTF-8 텍스트라 바이너리는 Base64로 33% 부풀려야 한다.

둘 다 놓치기 쉬운 공통점도 있다. 연결이 오래 열려 있으니 경로의 유휴 한도보다 짧은 하트비트, 서버를 여러 대로 늘릴 때의 메시지 버스, 배포 때의 재연결 폭주는 SSE에도 똑같이 필요하다. 그 부분은 [WebSocket 깊게 보기](/posts/websocket-deep-dive)에서 재현한 내용이 그대로 적용된다. SSE가 대신해 주는 건 재연결과 이어 받기, 그리고 프레임 형식뿐이다.

## SSE 장애를 만났을 때

이벤트가 몰려서 늦게 오면 배포 환경과 같은 경로로 `curl -sN`을 찍고 줄마다 시각을 붙인다. 앱에 직접 붙었을 때는 제때 오는데 프록시를 거치면 몰린다면 프록시 버퍼링, 앱에 직접 붙어도 몰린다면 압축 미들웨어다. 응답 헤더에 `Content-Encoding`이 있는지부터 본다.

일정 시간마다 재연결이 반복되면 access.log에서 SSE 경로의 `rt`를 본다. 한 값에 몰려 있으면 하트비트 간격이 그 한도보다 긴 것이다. 상태 코드가 200이라 오류율에는 안 잡힌다.

배포 뒤 일부 사용자의 화면이 멈췄다면 브라우저 개발자 도구에서 그 요청의 상태 코드를 본다. 502·503·401이면 `EventSource`가 포기한 것이니, 클라이언트에 CLOSED 상태를 다시 여는 코드가 있는지 확인한다.

여러 탭에서 사이트가 멈추면 개발자 도구 Network 탭의 Protocol 열을 켠다. `http/1.1`이면 연결 수 제한이다. 같은 이벤트가 반복해서 오면 서버가 `Last-Event-ID`를 읽는지, 모든 이벤트에 id를 붙이는지 본다.

## 경로를 비우면 가장 가벼운 선택

SSE는 응답 하나를 끝내지 않는 것뿐이라 서버 코드는 단순하다. 대신 HTTP 경로의 모든 규칙을 그대로 받는다. 버퍼와 압축이 이벤트를 붙잡고, 유휴 한도가 조용한 스트림을 끊고, HTTP/1.1의 연결 제한이 사이트 전체를 막고, 200이 아닌 응답 한 번에 브라우저가 영영 포기한다. 이 네 가지를 알고 경로를 비우면, 서버에서만 소식이 오는 기능에는 SSE가 가장 적은 코드로 가장 많은 것을 해 준다.

## 면접에서 나올 만한 질문

### EventSource는 끊기면 어떻게 다시 연결하나요?

네트워크 오류로 끊기면 `error` 이벤트를 알리고 `readyState`를 CONNECTING으로 둔 채, 서버가 `retry`로 알려 준 시간(없으면 브라우저 기본값, Chromium에서 약 3초)만큼 기다렸다 다시 요청한다. 이때 마지막으로 받은 id를 `Last-Event-ID` 헤더에 자동으로 싣는다. 서버는 그 id 다음 이벤트부터 보내면 된다. 페이지 코드는 재연결에 관여하지 않는다.

### EventSource가 다시 연결하지 않는 경우는요?

응답이 200이 아니거나 Content-Type이 `text/event-stream`이 아니면 연결을 실패로 끝내고 CLOSED가 된다. 서버가 204를 보내는 건 재연결을 멈추게 하는 정상적인 방법이다. 문제는 배포 중의 502·503이나 인증 만료의 401에도 똑같이 포기한다는 점이라, `onerror`에서 CLOSED를 확인하고 앱이 백오프를 두고 새로 연결해야 한다.

### HTTP/1.1에서 SSE를 쓰면 무엇이 문제인가요?

브라우저가 출처당 동시 연결을 6개로 제한해서, 끝나지 않는 SSE 응답이 연결을 하나씩 계속 차지한다. 실습에서 SSE 7개를 열자 일곱째는 연결되지 않았고, 관계없는 fetch까지 5초 넘게 대기했다. HTTP/2에서는 연결 하나에 스트림을 여러 개 실어서 SSE 7개와 fetch가 TCP 연결 하나로 처리됐다.

### SSE 이벤트가 로컬에서는 바로 오는데 운영에서는 몰려서 오면 무엇을 보나요?

경로의 버퍼를 본다. nginx `proxy_buffering`이 켜져 있으면 응답을 모았다가 보낼 수 있으니 SSE 경로는 끄거나 앱이 `X-Accel-Buffering: no`를 보낸다. 앱의 압축 미들웨어가 flush 없이 gzip을 걸어도 같은 증상이 나서, 실습에서 flush 없는 gzip은 3초 동안 아무것도 내보내지 않았다. CDN의 버퍼링과 캐시 설정도 확인한다.

### SSE에 하트비트가 왜 필요한가요?

조용한 스트림은 프록시나 로드 밸런서의 유휴 한도에 걸려 끊긴다. EventSource가 자동으로 다시 붙어서 화면은 멀쩡해 보이지만, 1분마다 재연결과 인증, 구독 등록이 반복되고 상태 코드는 200이라 지표에도 안 잡힌다. 한도보다 짧은 간격으로 주석 줄(`: ping`)을 보내면 막힌다. 서버는 하트비트 쓰기가 실패하는 순간 클라이언트가 떠난 것을 안다.

### LLM 답변 스트리밍에 EventSource 대신 fetch를 쓰는 이유는요?

EventSource는 GET만 하고 요청 헤더를 붙일 수 없어서, 긴 질문을 본문으로 보내고 Authorization 헤더가 필요한 호출에 맞지 않는다. 그래서 fetch로 POST를 보내고 응답 본문 스트림을 읽어 빈 줄 단위로 이벤트를 자른다. 대신 재연결, Last-Event-ID, 조각 경계 처리는 직접 해야 한다.

### SSE와 WebSocket 중 무엇을 고르나요?

데이터 방향으로 고른다. 서버에서만 오는 알림, 진행 상태, LLM 답변은 SSE가 기존 HTTP 인프라를 그대로 쓰고 재연결과 이어 받기도 표준이라 유리하다. 클라이언트도 자주 짧게 말하는 채팅, 게임, 공동 편집이나 바이너리가 많으면 WebSocket이다. 어느 쪽이든 하트비트, 서버 간 메시지 버스, 재연결 폭주 대비는 똑같이 필요하다.
