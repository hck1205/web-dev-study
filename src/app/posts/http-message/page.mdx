  HTTP 메시지는 생각보다 단순한 텍스트 편지다. 맨 첫 줄에 무엇을 원하는지 적고, 그 아래 "이름: 값" 모양의 머리말을 여러 줄 적고, 빈 줄 하나를 두고, 그 뒤에 내용물을 붙인다. 응답도 첫 줄만 다를 뿐 같은 모양이다.

  머리말이 하는 일이 많다. 어느 사이트에 온 편지인지, 내용물이 몇 바이트에서 끝나는지, 어떤 형식이고 어떤 압축을 쓰는지, 답장을 받은 뒤 이 연결을 계속 쓸지가 모두 머리말 한 줄씩이다. 그래서 API가 이상하게 굴면 코드를 뒤지기 전에 실제로 오간 편지 원문을 한 번 보는 게 빠르다.
</EasyIntro>

Postman으로 주문 API를 부르면 잘 되는데, 프론트엔드 코드에서 같은 걸 부르면 서버가 `415 Unsupported Media Type`을 돌려준다. 코드는 이랬다.

```js
fetch("/api/orders", {
  method: "POST",
  body: JSON.stringify({ name: "Matt", qty: 2 }),
});
```

본문은 분명 JSON이다. 그런데 서버 입장에서는 그걸 알 방법이 없다. `fetch`는 문자열 본문에 `Content-Type: text/plain;charset=UTF-8`을 붙여 보낸다. JSON만 받도록 만든 엔드포인트는 "텍스트는 못 읽는다"며 415로 거절하고, Express처럼 형식이 안 맞으면 조용히 넘어가는 서버라면 `req.body`가 그냥 비어 있다. Postman은 Body 탭에서 JSON을 고르면 이 헤더를 알아서 넣어 줬을 뿐이다.

이런 문제는 실제로 오간 메시지를 한 번 보면 바로 풀린다. HTTP 메시지는 생각보다 단순한 텍스트라서, 생김새만 알면 헤더 한 줄이 왜 문제였는지 눈에 들어온다. 요청이 전체 흐름에서 어디쯤 있는지는 [주소창에 google.com을 치면 일어나는 일](/posts/what-happens-google-com)에서 다뤘고, 여기서는 메시지 자체를 뜯어본다.

## curl로 날것의 메시지를 본다

`curl -v`를 붙이면 curl이 보낸 요청과 받은 응답의 머리 부분이 그대로 찍힌다. `>`로 시작하는 줄이 보낸 것, `<`가 받은 것, `*`는 curl이 남기는 연결 정보다. HTTPS 서버는 보통 HTTP/2로 협상하므로, 텍스트 모양을 보려면 `--http1.1`을 붙인다.

```
$ curl -v --http1.1 https://api.example.com/health
* Connected to api.example.com ... port 443
* SSL connection using TLSv1.3 ...
> GET /health HTTP/1.1
> Host: api.example.com
> User-Agent: curl/8.5.0
> Accept: */*
>
< HTTP/1.1 200 OK
< Content-Type: application/json
< Content-Length: 15
<
{"status":"ok"}
```

브라우저에서는 개발자 도구 Network 탭의 Headers에서 같은 내용을 본다. 크롬은 "Raw" 토글을 켜면 줄 단위 원문에 가깝게 보여 준다. 다만 HTTP/2 연결이면 브라우저가 보여 주는 건 프레임을 다시 텍스트처럼 풀어 쓴 것이다. 실제로 선 위로 흐른 바이트는 아니다.

## Host가 없으면 400이다

HTTP/1.0 시절 요청 줄은 `GET /index.html HTTP/1.0`이 전부였다. 서버 하나에 사이트 하나가 있던 때라 문제가 없었다. 그런데 IP 하나에 여러 도메인을 올리는 가상 호스팅이 흔해지자, 서버는 같은 IP로 들어온 `GET /`가 `blog.example.com`의 첫 페이지인지 `shop.example.com`의 첫 페이지인지 알 수 없게 됐다. TCP 연결에는 IP와 포트만 있고 도메인 이름은 없다.

그래서 HTTP/1.1은 `Host` 헤더를 필수로 만들었다. nginx의 `server_name`, 쿠버네티스 Ingress의 `host` 규칙, 로드 밸런서의 호스트 기반 라우팅이 모두 이 헤더 값을 보고 갈 곳을 나눈다. HTTPS에서는 TLS 핸드셰이크 때 SNI로 도메인을 한 번 더 알린다. 암호화를 시작하기 전에 어느 인증서를 내밀지 정해야 하는데, 그때는 아직 HTTP 헤더를 읽을 수 없기 때문이다.

Host 값은 클라이언트가 마음대로 정할 수 있다는 것도 기억해 둘 만하다. 비밀번호 재설정 메일의 링크를 요청의 Host로 만들면, 공격자가 `Host: evil.example`로 요청해 피해자에게 공격자 도메인 링크가 담긴 메일을 보내게 할 수 있다(Host 헤더 주입). 외부로 나가는 절대 주소는 설정에 박아 둔 도메인으로 만든다.

## 본문이 어디서 끝나는지 알려 주기

한 연결 위로 메시지가 여러 개 오가면, 받는 쪽은 "이 본문이 어디까지인가"를 정확히 알아야 다음 메시지의 첫 줄을 찾을 수 있다. 방법은 두 가지다.

`Content-Length`는 길이를 미리 적는다. 가장 단순하지만, 보내기 전에 본문 전체 크기를 알아야 한다. 서버가 DB에서 행을 읽어 가며 HTML을 흘려 보내고 싶거나, 큰 파일을 압축하면서 바로 보내고 싶을 때는 끝까지 만들어 보기 전엔 길이를 모른다.

그럴 때 `Transfer-Encoding: chunked`를 쓴다. 본문을 조각(chunk)으로 나눠, 조각마다 앞에 16진수 바이트 수를 적어 보낸다. 크기가 0인 조각이 오면 끝이다. 아래 그림은 받는 쪽이 조각을 읽어 본문을 이어 붙이는 과정이다.

실제 바이트로 쓰면 이렇다.

```
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Transfer-Encoding: chunked

13
<ul><li>사과</li>
11
<li>배</li></ul>
0

```

둘 다 없으면 어떻게 될까. 요청은 본문이 없는 것으로 본다. 응답은 서버가 연결을 끊을 때까지를 본문으로 본다. HTTP/1.0 방식인데, 이러면 연결을 재사용할 수 없다.

둘 다 있으면 더 위험하다. 스펙은 둘을 같이 보내지 말라고 하고, 같이 왔으면 `Transfer-Encoding`을 우선하라고 한다. 문제는 앞단 프록시와 뒷단 서버가 이 규칙을 똑같이 지키지 않을 때다. 프록시는 `Content-Length`로 메시지 경계를 자르고 서버는 `chunked`로 자르면, 공격자가 본문 끝에 숨겨 둔 바이트를 서버는 "다음 요청의 시작"으로 읽는다. 다른 사용자의 요청 앞에 공격자의 요청이 붙어 버리는 HTTP 요청 스머글링(request smuggling)이다. 그래서 요즘 서버와 프록시는 둘이 같이 오거나 `Content-Length` 값이 여러 개면 대부분 400으로 거절하고 연결을 닫는다.

## 연결을 끊을지 말지

HTTP/1.0은 기본이 요청 하나에 연결 하나였다. 계속 쓰고 싶으면 `Connection: keep-alive`를 따로 보내야 했다. HTTP/1.1은 거꾸로 기본이 연결 유지(persistent connection)이고, 끊고 싶을 때 `Connection: close`를 보낸다. 그래서 HTTP/1.1 요청에 `Connection: keep-alive`가 보이면 대개 1.0 시절 습관이 남은 것이다. `Keep-Alive: timeout=5, max=100`처럼 유지 시간을 알려 주는 헤더도 있지만 참고용이다.

`Connection`은 다음 한 구간에만 적용되는 hop-by-hop 헤더다. 프록시는 이 헤더와, 여기에 이름을 적은 헤더를 지우고 다음 구간으로 넘긴다. `Transfer-Encoding`도 구간마다 다시 정한다. 반대로 `Content-Type`, `Content-Encoding` 같은 대부분의 헤더는 끝에서 끝까지 그대로 간다(end-to-end).

연결 유지에서 실무로 자주 터지는 건 타임아웃 순서다. 로드 밸런서가 뒷단 서버와의 연결을 60초 동안 쥐고 있으려 하는데 뒷단 서버는 5초 동안 조용하면 연결을 닫는다고 해 보자. 서버가 닫는 순간과 로드 밸런서가 그 연결로 다음 요청을 보내는 순간이 겹치면, 요청은 닫힌 연결로 들어가고 사용자는 간헐적인 502를 본다. Node.js의 `keepAliveTimeout` 기본값이 5초라서 AWS ALB(기본 60초) 뒤에 둘 때 자주 보이는 증상이다. 뒷단의 유지 시간을 앞단보다 길게 잡는다.

## 같은 주소, 다른 표현

`/products/42`라는 같은 자원을 JSON으로 줄 수도, HTML로 줄 수도, 한국어나 영어로 줄 수도, gzip으로 압축해서 줄 수도 있다. 이렇게 자원 하나를 실제로 보낼 모양 하나하나를 표현(representation)이라고 부른다. 클라이언트가 `Accept*` 헤더로 원하는 걸 알리고 서버가 그중에서 고르는 걸 콘텐츠 협상이라고 한다.

```
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
Accept-Language: ko-KR,ko;q=0.9,en-US;q=0.8,en;q=0.7
Accept-Encoding: gzip, deflate, br, zstd
```

`q`는 선호도다. 0부터 1까지 소수점 셋째 자리까지 쓰고, 안 적으면 1이다. `q=0`은 "이건 절대 주지 마라"라는 뜻이다. `*`는 나머지 전부를 가리키고, 더 구체적인 항목이 있으면 그쪽이 이긴다.

서버가 고르는 규칙을 직접 짜 보면 이 헤더가 금방 익숙해진다. 아래 `negotiate`는 `Accept-Encoding` 같은 헤더 문자열과 서버가 줄 수 있는 목록을 받아 가장 선호도가 높은 것을 고른다. 선호도가 같으면 서버 목록에서 앞에 있는 것을 고르고, 줄 수 있는 게 없으면 `null`을 돌려준다.

## 압축은 Accept-Encoding으로 고른다

협상이 가장 많이 쓰이는 곳은 압축이다. 브라우저가 `Accept-Encoding`으로 풀 수 있는 방식을 알리면, 서버는 하나를 골라 본문을 압축하고 `Content-Encoding`에 적는다. 이때 `Content-Length`는 압축된 크기다.

gzip은 모든 클라이언트가 풀 수 있는 기본값이다. Brotli(`br`)는 텍스트에서 gzip보다 더 작게 줄인다. 상품 100개짜리 JSON(8,010바이트)을 Node.js로 압축해 보면 gzip(레벨 6)은 866바이트, Brotli(품질 11)는 473바이트가 나왔다. 반복이 많은 데이터라 차이가 큰 편이고, 보통의 JS·CSS에서는 그보다 차이가 작다. 대신 Brotli 최고 품질은 압축이 느리다. 그래서 빌드할 때 정적 파일을 미리 최고 품질로 압축해 두고, 요청마다 만드는 동적 응답은 Brotli 4~6 정도나 gzip으로 압축하는 식으로 나눈다. 크롬 계열과 파이어폭스는 Brotli를 HTTPS 연결에서만 광고하고, 최근 버전은 `zstd`도 함께 보낸다.

`Vary`는 남발하면 캐시가 잘게 쪼개진다. `Vary: User-Agent`를 붙이면 브라우저 버전 문자열마다 사본이 따로 생겨 적중률이 바닥으로 떨어진다. 대부분의 CDN은 `Accept-Encoding`을 알아서 몇 가지로 정규화해 이 문제를 줄인다. 캐시 쪽 이야기는 [HTTP 캐시와 CDN](/posts/http-caching-cdn)에 더 있다.

압축하지 않는 게 나은 경우도 있다.

- 이미 압축된 형식. JPEG, PNG, WebP, MP4, woff2는 내부에서 이미 압축했다. 무작위에 가까운 바이트 50,000개를 gzip으로 압축하면 50,038바이트로 오히려 늘어난다. CPU만 쓰고 이득이 없다.
- 아주 작은 응답. `{"ok":true}`(11바이트)를 gzip으로 압축하면 헤더와 체크섬이 붙어 31바이트가 된다. nginx나 CDN에 최소 크기 설정이 있는 이유다.
- 비밀값과 사용자 입력이 한 응답에 섞일 때. HTTPS여도 압축된 크기는 밖에서 보인다. 공격자가 요청에 넣은 글자가 응답 안의 비밀(CSRF 토큰 등)과 겹치면 더 잘 압축되어 응답이 작아진다. 이걸 여러 번 반복해 비밀을 한 글자씩 맞히는 공격이 BREACH다. 토큰을 요청마다 다른 값으로 가려 넣거나, 그런 응답은 압축하지 않는다.

`Content-Encoding`과 `Transfer-Encoding`도 구분해 둔다. `Content-Encoding: gzip`은 표현 자체가 gzip이라는 뜻이라 끝에서 끝까지 유지된다. `Transfer-Encoding: chunked`는 이번 구간에서 실어 나르는 방식이라 프록시를 지날 때마다 바뀔 수 있다.

## 본문 형식은 Content-Type이 말한다

`Content-Type`은 미디어 타입과 매개변수로 되어 있다. `text/html; charset=utf-8`에서 `charset`은 글자를 바이트로 바꾼 방식이다. 텍스트 형식에 이게 없으면 브라우저가 인코딩을 짐작하다 한글이 깨질 수 있으니 HTML과 텍스트에는 꼭 적는다. 반면 `application/json`에는 charset 매개변수가 정의되어 있지 않다. JSON 표준(RFC 8259)이 네트워크로 주고받는 JSON은 UTF-8로 쓰라고 정해 두었기 때문이다. `application/json; charset=utf-8`이라고 붙여도 해는 없지만 의미도 없다.

API에서 자주 만나는 본문 형식은 셋이다.

`application/json`은 요즘 API의 기본이다. 중첩 구조를 표현하기 쉽다. 처음 장면처럼 `fetch`에 문자열을 넣을 때는 헤더를 직접 적어야 한다.

`application/x-www-form-urlencoded`는 HTML 폼의 기본값이다. 쿼리 문자열과 같은 모양으로, 공백은 `+`가 되고 `&`, `=` 같은 구분 문자는 퍼센트 인코딩된다.

```
name=Matt+Kim&memo=a%26b%3Dc
```

`multipart/form-data`는 파일을 올릴 때 쓴다. 본문을 여러 부분으로 나누고, 부분 사이에 경계 문자열(boundary)을 끼운다. 경계 값은 `Content-Type` 헤더에 들어 있고, 마지막 경계 뒤에는 `--`가 붙는다.

```
POST /upload HTTP/1.1
Content-Type: multipart/form-data; boundary=----x7MA4YWxk

------x7MA4YWxk
Content-Disposition: form-data; name="title"

여름 사진
------x7MA4YWxk
Content-Disposition: form-data; name="file"; filename="beach.jpg"
Content-Type: image/jpeg

(JPEG 바이트)
------x7MA4YWxk--
```

파일 바이트를 퍼센트 인코딩이나 Base64로 바꾸지 않고 그대로 실을 수 있어서 큰 파일에 유리하다. 여기서 흔한 실수가 하나 있다. `fetch`에 `FormData`를 넘기면서 `Content-Type: multipart/form-data`를 직접 적는 것이다. 그러면 브라우저가 만들어 붙이던 `boundary=...`가 빠져서, 서버는 본문을 어디서 잘라야 할지 몰라 파싱에 실패한다. `FormData`를 쓸 때는 `Content-Type`을 비워 두고 브라우저에 맡긴다.

받는 쪽이 지원하지 않는 형식이 오면 `415 Unsupported Media Type`, 보내 달라는 형식을 줄 수 없으면 `406 Not Acceptable`이다. 처음 장면의 415는 앞쪽, 요청 본문의 문제였다.

## 헤더 이름과 크기에 관한 규칙

헤더 이름은 대소문자를 가리지 않는다. `Content-Type`, `content-type`, `CONTENT-TYPE`은 같은 헤더다. 서버 코드에서 헤더를 꺼낼 때 대소문자를 맞춰 비교하면 HTTP/2에서 바로 깨진다. Node.js의 `req.headers`가 이름을 전부 소문자로 바꿔 주는 것도 그래서다. 값은 헤더마다 다르다. 미디어 타입은 대소문자를 가리지 않지만, 쿠키 값이나 토큰은 글자 그대로 비교한다.

같은 이름의 헤더가 여러 줄 오면 쉼표로 이어 한 줄로 합쳐도 의미가 같아야 한다는 규칙이 있다. `Accept-Encoding: gzip`과 `Accept-Encoding: br` 두 줄은 `Accept-Encoding: gzip, br`과 같다. 예외는 `Set-Cookie`다. 쿠키의 `Expires` 날짜에 쉼표가 들어가서 합치면 망가진다. 그래서 `Set-Cookie`만은 쿠키 하나에 한 줄씩 따로 보낸다. 쿠키가 어떻게 오가는지는 [쿠키와 세션으로 로그인 상태 유지하기](/posts/cookie-session-login)에서 다뤘다.

헤더 크기에 정해진 상한은 스펙에 없다. 대신 서버마다 한도가 있다. Node.js는 헤더 전체 기본 16KB, nginx는 한 줄당 기본 8KB(`large_client_header_buffers`), Tomcat과 스프링 부트 내장 서버는 기본 8KB 정도다. 넘으면 Node.js는 `431 Request Header Fields Too Large`를, nginx는 `400 Request Header Or Cookie Too Large`를 돌려준다. 원인은 대개 쿠키다. 같은 상위 도메인에 서비스가 여러 개 붙어 각자 쿠키를 심다 보면 어느 날 일부 사용자만 접속이 안 된다. 커다란 JWT를 쿠키나 `Authorization` 헤더에 싣는 경우도 비슷하다([토큰으로 로그인하기](/posts/token-login)). 서버 한도를 늘리기 전에 무엇이 헤더를 키우는지부터 본다. 앞단 프록시와 뒷단 서버의 한도가 다르면 어디서 거절됐는지 찾기 어려우니 같이 맞춘다.

직접 만든 헤더에는 예전에 `X-` 접두어를 붙였다. 표준이 아니라는 표시였는데, 실험용 헤더가 널리 쓰이다 표준이 되면 이름을 바꾸기 어렵다는 문제가 생겼다. `X-Forwarded-For`가 대표적이다. 표준 `Forwarded` 헤더가 나왔지만 지금도 `X-Forwarded-For`가 훨씬 많이 쓰인다. 그래서 RFC 6648(2012)은 새 헤더에 `X-`를 붙이지 말라고 권한다. 새로 만든다면 `Acme-Request-Id`처럼 회사나 서비스 이름을 앞에 두면 충돌도 피한다. 이미 쓰고 있는 `X-Request-Id` 같은 이름을 굳이 바꿀 필요는 없다.

## HTTP/2에서는 모양이 바뀐다

여기까지는 HTTP/1.1의 텍스트 모양이다. HTTP/2부터는 메시지가 텍스트 줄이 아니라 바이너리 프레임으로 오간다. 헤더는 HEADERS 프레임에, 본문은 DATA 프레임에 실린다. 의미는 그대로지만 표기가 바뀐다.

```
:method: POST
:scheme: https
:authority: shop.example.com
:path: /api/orders
content-type: application/json
content-length: 23
```

요청 줄은 콜론으로 시작하는 의사 헤더(pseudo-header) 넷으로 쪼개지고, `Host`의 자리는 `:authority`가 맡는다. 응답의 상태 줄은 `:status: 201` 하나가 된다. 헤더 이름은 반드시 소문자여야 하고, 반복되는 헤더는 HPACK이라는 방식으로 압축해서 두 번째 요청부터는 거의 공짜에 가깝게 보낸다. 프레임마다 길이가 붙으니 `Transfer-Encoding: chunked`는 쓰지 않고, `Connection`, `Keep-Alive` 같은 연결 관련 헤더는 보내면 오류다. 이 변화가 왜 생겼고 HTTP/3에서는 무엇이 또 달라지는지는 [HTTP/1.1, HTTP/2, HTTP/3](/posts/http-versions)에서 이어서 본다.

## 헤더 한 줄이 장애가 되는 순간

운영에서 메시지를 뜯어볼 일은 대개 "앱 코드는 그대로인데 요청이 이상하게 도착한다"는 증상에서 시작한다. 아래 출력은 Ubuntu 24.04에 Node.js 22 앱(`localhost:18601`)을 띄우고, 그 앞에 nginx 1.24(`localhost:18610`, `/api/`를 앱으로 넘김)를 세워 재현한 것이다.

처음 장면을 curl로 재현하려다 한 번 더 헷갈리는 경우가 있다. `-d`만 붙이면 curl도 `Content-Type`을 알아서 정한다.

```bash
# -v 출력에서 curl이 보낸 줄(>) 중 요청 줄과 본문 관련 헤더만 고른다
curl -sv http://localhost:18601/echo -d '{"qty":2}' 2>&1 | grep -E '^> (POST|Content-)'

# --json은 Content-Type과 Accept를 application/json으로 붙인다 (curl 7.82 이상)
curl -s http://localhost:18601/echo --json '{"qty":2}'
```

```text
> POST /echo HTTP/1.1
> Content-Length: 9
> Content-Type: application/x-www-form-urlencoded
{"method":"POST","contentType":"application/json","body":"{\"qty\":2}"}
```

`-d`는 폼 형식이라고 적어 보낸다. 서버가 JSON 파서만 달고 있으면 브라우저의 `text/plain` 때와 똑같이 본문을 건너뛴다. "Postman에서는 되는데"를 풀 때는 양쪽 요청을 같은 모양으로 꺼내 비교하는 게 가장 빠르다. 크롬 개발자 도구 Network 탭에서 요청을 오른쪽 클릭하고 Copy → Copy as cURL을 고르면, 브라우저가 실제로 붙인 헤더가 모두 들어간 curl 명령이 나온다. 그걸 `-v`로 돌려 Postman 쪽과 헤더를 한 줄씩 맞춰 본다.

다음은 "일부 사용자만 접속이 안 된다"는 신고다. 앞에서 본 헤더 크기 한도에 걸린 경우인데, 같은 원인이 층마다 다른 응답으로 보인다. 20KB짜리 쿠키를 실어 보내 봤다.

```bash
# 20,000바이트짜리 쿠키 값을 만든다
BIG=$(head -c 20000 /dev/zero | tr '\0' 'a')

# Node.js에 바로 보낸다
curl -s -i -H "Cookie: session=$BIG" http://localhost:18601/ | head -1

# nginx를 거쳐 보낸다
curl -s -i -H "Cookie: session=$BIG" http://localhost:18610/api/ | head -1
```

```text
HTTP/1.1 431 Request Header Fields Too Large
HTTP/1.1 400 Bad Request
```

nginx는 이 요청을 앱에 넘기지도 않으니 앱 로그에는 흔적이 없다. nginx error.log에는 이렇게 남는다(쿠키 값은 nginx가 잘라서 적는다).

```text
2026/10/18 11:04:46 [info] 899#899: *672 client sent too long header line: "Cookie: session=aaaaaaaa......" while reading client request headers, client: 127.0.0.1, server: , request: "GET /api/ HTTP/1.1", host: "localhost:18610"
```

레벨이 `[info]`인 것을 봐야 한다. Ubuntu 기본 설정의 `error_log /var/log/nginx/error.log;`는 `error` 이상만 남기므로, 기본 설정에서는 이 줄이 아예 찍히지 않는다. 원인을 찾는 동안만 `error_log /var/log/nginx/error.log info;`로 낮췄다가 되돌린다. 어떤 쿠키가 큰지는 개발자 도구 Application → Cookies 표를 Size 열로 정렬하면 나온다. `HttpOnly` 쿠키는 `document.cookie`에 나오지 않아서 콘솔로 세면 놓친다. 서버 한도를 늘리는 건 마지막 수단이고, 쿠키 `Domain`을 상위 도메인으로 넓게 잡은 서비스가 없는지부터 본다.

마지막은 트래픽이 적을 때 간헐적으로 섞이는 502다. 연결 유지에서 본 타임아웃 순서 문제일 가능성이 크다. Node.js의 기본값부터 확인한다.

```bash
# keepAliveTimeout, headersTimeout, requestTimeout 기본값(밀리초)
node -e 'const s = require("http").createServer(); console.log(s.keepAliveTimeout, s.headersTimeout, s.requestTimeout)'
```

```text
5000 60000 300000
```

Node는 5초 동안 조용한 연결을 먼저 닫는다. 앞단 로드 밸런서가 60초까지 연결을 재사용하려 하면, 그 사이 어느 순간 이미 닫힌 연결에 요청을 싣게 된다. 앞단이 nginx라면 error.log에 `upstream prematurely closed connection while reading response header from upstream`이 502와 같은 시각에 찍힌다. 트래픽이 많을 때는 연결이 쉴 틈이 없어 덜 보이고, 새벽처럼 한산할 때 튀는 게 이 문제의 특징이다. 앱 쪽 유지 시간을 앞단보다 길게 잡는다.

```js
const server = app.listen(3000);
server.keepAliveTimeout = 65_000; // 앞단 유휴 시간(60초)보다 길게
server.headersTimeout = 66_000;   // keepAliveTimeout보다 조금 더 길게
```

정말 앱이 먼저 닫는지 눈으로 보고 싶으면 앱 서버에서 패킷을 잡아, 502가 난 요청 직전에 앱 쪽 FIN이 먼저 나갔는지 본다. 잡는 방법은 [tcpdump로 계층을 눈으로 보기](/posts/packet-capture-tcpdump)에, 증상에서 층을 좁혀 가는 순서는 [계층별로 장애 좁히기](/posts/network-troubleshooting-by-layer)에 정리했다.

## 다시 415로 돌아가서

처음 장면의 요청에는 `Content-Type` 한 줄이 빠져 있었다. 서버는 본문을 열어 보기 전에 이 헤더로 "무엇이 왔는가"를 판단하고, 그 판단이 틀리면 본문이 완벽해도 읽지 않는다. HTTP 메시지는 첫 줄, 헤더, 빈 줄, 본문이 전부다. 헤더는 본문을 해석하는 설명서이고, 길이·압축·형식·연결 유지가 모두 그 설명서에 적힌다. 이상한 응답을 만나면 `curl -v`로 그 설명서부터 읽는다.

## 면접에서 나올 만한 질문

### HTTP 메시지는 어떤 구조로 되어 있나요?

첫 줄, 헤더, 빈 줄, 본문으로 되어 있다. 요청의 첫 줄은 메서드·요청 대상·버전이고, 응답의 첫 줄은 버전·상태 코드·이유 문구다. 헤더는 `이름: 값` 모양으로 여러 줄 오고, CRLF만 있는 빈 줄이 헤더의 끝을 알린다. HTTP/2부터는 같은 의미를 바이너리 프레임과 의사 헤더로 표현한다.

### HTTP/1.1에서 Host 헤더가 필수인 이유는요?

IP 하나에 여러 도메인을 올리는 가상 호스팅 때문이다. TCP 연결에는 도메인 정보가 없어서 서버는 Host를 봐야 어느 사이트로 온 요청인지 안다. 그래서 HTTP/1.1은 Host가 없거나 두 개인 요청을 400으로 거절하게 했다. HTTPS에서는 TLS 단계에서 SNI가 같은 역할을 먼저 하고, HTTP/2에서는 `:authority`가 Host를 대신한다.

### Content-Length와 Transfer-Encoding: chunked는 언제 쓰나요?

보내기 전에 본문 크기를 알면 Content-Length, 만들면서 흘려 보내야 해서 크기를 모르면 chunked를 쓴다. chunked는 조각마다 16진수 바이트 수를 앞에 적고 크기 0인 조각으로 끝을 알린다. 둘을 같이 보내면 안 되고, 받는 쪽이 둘을 다르게 해석하면 요청 스머글링이 생기므로 서버와 프록시는 이런 요청을 거절한다. HTTP/2에서는 프레임이 길이를 가지므로 chunked를 쓰지 않는다.

### 콘텐츠 협상이 무엇이고, Vary 헤더는 왜 필요한가요?

같은 자원을 형식·언어·압축 방식이 다른 여러 표현으로 줄 수 있을 때, 클라이언트가 `Accept`, `Accept-Language`, `Accept-Encoding`과 q값으로 선호를 알리고 서버가 고르는 방식이다. 이렇게 같은 주소의 응답이 요청 헤더에 따라 달라지면, 캐시가 그걸 모르고 한 사본을 모두에게 주는 사고가 난다. `Vary`는 어떤 요청 헤더가 응답을 바꿨는지 알려서 캐시가 그 값까지 키로 쓰게 한다. 대신 `Vary: User-Agent`처럼 값이 다양한 헤더를 넣으면 캐시 적중률이 떨어진다.

### gzip과 Brotli 중 무엇을 쓰나요? 압축하면 안 되는 경우도 있나요?

텍스트는 Brotli가 대개 더 작게 줄이므로 지원하는 클라이언트에는 Brotli, 나머지에는 gzip을 준다. Brotli 최고 품질은 느려서 정적 파일은 빌드 때 미리 압축하고 동적 응답은 낮은 품질이나 gzip을 쓴다. 이미 압축된 이미지·영상·폰트와 아주 작은 응답은 압축해도 크기가 줄지 않거나 오히려 는다. 비밀값과 사용자 입력이 섞인 응답은 BREACH 공격 위험이 있어 압축을 끄거나 토큰을 요청마다 다르게 가린다.

### fetch로 FormData를 보낼 때 Content-Type을 직접 지정하면 어떻게 되나요?

multipart 본문을 나누는 boundary 값이 헤더에서 빠져 서버가 본문을 파싱하지 못한다. 브라우저는 FormData를 보낼 때 boundary를 만들어 `Content-Type: multipart/form-data; boundary=...`를 직접 붙이므로 비워 두면 된다. 반대로 JSON 문자열을 보낼 때는 헤더를 적지 않으면 `text/plain`으로 가서 서버가 415를 돌려주거나 본문을 무시한다.

### 헤더가 너무 커서 요청이 실패하는 건 어떤 경우인가요?

스펙에는 상한이 없지만 서버마다 8~16KB 정도의 한도가 있고, 넘으면 431이나 400을 돌려준다. 원인은 대부분 같은 도메인에 쌓인 쿠키나 큰 JWT다. 한도를 늘리기 전에 쿠키 범위를 좁히고 토큰 크기를 줄이며, 앞단 프록시와 뒷단 서버의 한도를 맞춘다.

### 커스텀 헤더에 X- 접두어를 붙여야 하나요?

새로 만드는 헤더에는 붙이지 않는 게 권장이다. RFC 6648이 실험용 이름이 표준으로 굳으면 바꾸기 어렵다는 이유로 X- 관례를 폐기했다. 대신 회사나 서비스 이름을 앞에 붙여 충돌을 피한다. 이미 널리 쓰는 `X-Forwarded-For`, `X-Request-Id` 같은 이름은 그대로 쓴다.
