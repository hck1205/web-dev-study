<EasyIntro>
  운영 중인 서비스에서 급한 버그가 발견됐는데, 고칠 코드가 들어갈 자리에는 아직 공개하면 안 되는 반쯤 만든 기능이 같이 들어 있다. 거기서 고쳐 내보내면 덜 된 기능까지 같이 나가고, 다른 곳에서 고치면 다음 버전에서 같은 버그가 되살아난다.

  이런 질문에 미리 답을 정해 두는 것이 브랜치 전략이다. 브랜치는 책의 원고를 복사해 따로 고치는 사본 같은 것인데, 어디서 사본을 뜨고 어디로 되돌려 합치며 무엇을 배포할지에 관한 팀의 약속이다. 출시 날짜가 정해진 앱처럼 버전을 묶어 내보내는 곳은 출시용과 개발용 원고를 따로 두는 방식이 맞고, 하루에도 여러 번 배포하는 웹 서비스는 원고를 하나만 두고 작은 수정을 자주 합치는 방식이 맞다.

  고르는 기준은 결국 얼마나 자주 합치느냐다. 자주 배포할수록 사본은 짧게 살아야 충돌이 적고, 그러려면 자동 테스트와 덜 된 기능을 숨기는 스위치가 받쳐 줘야 한다.
</EasyIntro>

릴리스 날 오후, 운영 중인 1.4.0에서 장바구니 합계가 소수점으로 찍힌다는 제보가 들어왔다. 고칠 코드는 한 줄이다. 그런데 `develop` 브랜치에는 반쯤 만든 위시리스트와 아직 켜면 안 되는 추천 기능이 이미 들어가 있다. develop에서 고쳐서 배포하면 덜 된 기능까지 같이 나간다. main에서 고치면 develop에는 그 수정이 없어서 다음 릴리스 때 같은 버그가 되살아난다.

이 질문에 답을 정해 두는 게 브랜치 전략이다. 어디서 따고, 어디로 합치고, 무엇을 배포하고, 급한 수정은 어느 길로 보내는지에 대한 팀의 약속이다. 이 글은 Git Flow, GitHub Flow, GitLab Flow, 트렁크 기반 개발을 차례로 보고, 위 상황을 Git Flow로 푸는 명령을 실제로 돌려 본 뒤, 같은 일을 트렁크 기반에서는 어떻게 하는지 비교한다. PR을 합치는 방식, 커밋 메시지 규칙, 버전 태그까지 이어서 본다.

명령과 출력은 Ubuntu 24.04의 Git 2.43에서 실제로 돌린 결과다. 브랜치를 만들고 합치는 기본 동작은 [브랜치와 머지 글](/posts/git-branch-merge)에, 원격과 PR의 흐름은 [원격 협업 글](/posts/git-remote-collaboration)에 있다.

## 전략이 정하는 것은 통합하는 때와 곳이다

전략마다 이름은 달라도 정하는 건 비슷하다.

- 오래 사는 브랜치가 몇 개인가 (main 하나인가, main과 develop 둘인가, 환경마다 하나씩인가)
- 기능 브랜치는 얼마나 오래 사는가 (몇 시간인가, 몇 주인가)
- 배포하는 것은 무엇인가 (main의 매 커밋인가, 태그를 붙인 커밋인가)
- 급한 수정은 어디서 시작해 어디로 퍼지는가

브랜치가 오래 살수록 main과 멀어지고, 합칠 때 충돌이 커진다. 그래서 전략을 고르는 일은 결국 "얼마나 자주 합칠 것인가"를 고르는 일이다. 자주 합치려면 자동 테스트와 미완성 기능을 숨기는 장치가 필요하고, 드물게 합치려면 릴리스를 관리하는 절차가 필요하다.

## Git Flow는 브랜치를 역할별로 나눈다

Git Flow는 Vincent Driessen이 2010년에 정리한 모델이다. 브랜치마다 역할이 정해져 있다.

- `main`: 출시된 코드만 있다. 커밋마다 버전 태그가 붙는다.
- `develop`: 다음 릴리스를 모으는 통합 브랜치다.
- `feature/*`: develop에서 따서 develop으로 합친다.
- `release/*`: 출시 준비. develop에서 따고, 버그 수정만 받은 뒤 main과 develop 양쪽으로 합친다.
- `hotfix/*`: 운영 긴급 수정. main에서 따서 main과 develop 양쪽으로 합친다.

Git Flow가 잘 맞는 곳은 버전을 붙여서 내보내는 소프트웨어다. 앱스토어 심사를 거치는 모바일 앱, 고객이 직접 설치하는 패키지, 여러 버전을 동시에 지원해야 하는 라이브러리처럼 "출시"가 하루에 여러 번 일어날 수 없는 곳이다. 출시 전에 QA 기간을 두고 그 사이 다음 기능 개발을 멈추지 않아야 할 때 release 브랜치가 제 역할을 한다.

반대로 하루에도 여러 번 배포하는 웹 서비스에는 무겁다. main과 develop이 늘 같은 내용을 두 번 관리하는 꼴이 되고, 합치는 방향을 하나라도 빼먹으면 수정이 사라진다. Driessen도 2020년에 원문 앞에 덧붙인 글에서, 지속적으로 배포하는 웹 앱이라면 GitHub Flow 같은 더 단순한 흐름을 고려하라고 적었다.

## Git Flow로 핫픽스 내보내기

처음 상황을 실제로 해 본다. main에는 `v1.4.0` 태그가 있고, develop에는 미완성 커밋 두 개가 있다.

```bash
# 지금 상태 확인
git log --oneline --graph --all --decorate
```

```text
* 29a3fe8 (develop) feat(reco): WIP recommendation
* fac927c feat(wishlist): add skeleton
* 367ebea (HEAD -> main, tag: v1.4.0) chore: init
```

hotfix 브랜치는 develop이 아니라 운영 중인 버전, 즉 main에서 딴다.

```bash
# main(운영 버전)에서 hotfix 브랜치를 딴다
git switch -c hotfix/1.4.1 main

# 고치고 커밋한다
git commit -am "fix(cart): round total to integer"

# main에 합친다. --no-ff로 머지 커밋을 남겨 "여기서 핫픽스가 들어왔다"를 기록한다
git switch main
git merge --no-ff hotfix/1.4.1 -m "Merge branch 'hotfix/1.4.1'"

# 버전 태그를 붙인다
git tag -a v1.4.1 -m "v1.4.1"
```

```text
Switched to a new branch 'hotfix/1.4.1'
Switched to branch 'main'
Merge made by the 'ort' strategy.
 price.txt | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

이제 같은 수정을 develop에도 합친다. 이 단계가 Git Flow에서 가장 자주 빠뜨리는 부분이다.

```bash
# develop에도 같은 hotfix를 합친다
git switch develop
git merge --no-ff hotfix/1.4.1 -m "Merge branch 'hotfix/1.4.1' into develop"

# 두 곳에 다 들어갔으면 hotfix 브랜치를 지운다
git branch -d hotfix/1.4.1

# 결과 그래프
git log --oneline --graph --all --decorate
```

```text
Deleted branch hotfix/1.4.1 (was e63eb61).
*   bf290e6 (HEAD -> develop) Merge branch 'hotfix/1.4.1' into develop
|\  
* | 29a3fe8 feat(reco): WIP recommendation
* | fac927c feat(wishlist): add skeleton
| | * c11cc7e (tag: v1.4.1, main) Merge branch 'hotfix/1.4.1'
| |/| 
|/|/  
| * e63eb61 fix(cart): round total to integer
|/  
* 367ebea (tag: v1.4.0) chore: init
```

그래프에서 `e63eb61` 하나가 main(`c11cc7e`)과 develop(`bf290e6`) 두 머지 커밋의 부모로 들어가 있다. 수정 커밋은 하나인데 두 브랜치가 모두 포함한다. 이 상태에서 develop의 `git describe`는 `v1.4.0-4-gbf290e6`이다. v1.4.1이 아니라 v1.4.0 기준으로 나온다. v1.4.1 태그는 main의 머지 커밋에 붙어 있고, 그 커밋은 develop의 조상이 아니기 때문이다. Git Flow에서 태그는 main에만 있다는 걸 보여 주는 장면이다.

`git flow hotfix start 1.4.1`처럼 이 과정을 줄여 주는 git-flow 확장(`sudo apt install git-flow`)도 있다. 하는 일은 위 명령과 같으니, 먼저 손으로 한 번 해 보고 쓰는 편이 무슨 일이 일어나는지 알기 쉽다.

## 릴리스 브랜치의 수정은 cherry-pick으로 돌려보낸다

release 브랜치에서 QA 중에 버그를 고쳤는데, release를 main에 합치기 전에 develop에도 그 수정이 당장 필요할 때가 있다. 브랜치 전체를 합치면 release에만 있어야 할 버전 번호 변경까지 넘어간다. 이럴 때 커밋 하나만 복사하는 cherry-pick을 쓴다.

```bash
# develop에서 release/1.5.0을 딴다. 이제 이 브랜치는 버그 수정만 받는다
git switch -c release/1.5.0 develop
echo "1.5.0" > VERSION && git commit -am "chore(release): 1.5.0"

# QA에서 나온 버그를 release에서 고친다
git commit -am "fix(reco): hide empty list"

# 그 커밋 하나만 develop에 복사한다. -x는 원본 커밋 해시를 메시지에 남긴다
git switch develop
git cherry-pick -x release/1.5.0
git log -1 --format=%B
```

```text
[develop c976ffa] fix(reco): hide empty list
 Date: Sat Oct 17 08:34:54 2026 +0000
 1 file changed, 1 insertion(+), 1 deletion(-)
fix(reco): hide empty list

(cherry picked from commit f45d6f226b5a2768c63147646af7321ba18b7dc1)
```

cherry-pick은 같은 변경을 담은 새 커밋을 만든다. 해시가 다르니 Git 입장에서는 다른 커밋이다. `-x`로 남긴 "(cherry picked from ...)" 한 줄이 나중에 "이 수정이 어느 브랜치들에 들어갔나"를 추적하는 단서가 된다. 공개 브랜치 사이에서 복사할 때는 늘 붙인다.

방향도 정해 둬야 한다. Git Flow는 release에서 고치고 develop으로 돌려보낸다. 트렁크 기반이나 GitLab Flow는 반대로 "upstream first", 즉 main에서 먼저 고치고 release 브랜치로 cherry-pick한다. main에 먼저 넣어야 수정이 다음 버전에서 빠질 일이 없다. 어느 쪽이든 한 방향으로만 흐르게 정한다. 양방향으로 오가면 어디가 원본인지 알 수 없다. cherry-pick의 범위 지정과 충돌 처리는 [Git 고급 기능 글](/posts/git-tips-advanced)에서 자세히 본다.

release를 마무리할 때는 hotfix와 같은 모양이다.

```bash
# release를 main에 합치고 태그
git switch main
git merge --no-ff release/1.5.0
git tag -a v1.5.0 -m "v1.5.0"

# release의 나머지 수정도 develop에 돌려보낸다 (버전 파일 충돌은 develop 쪽 값으로 정리)
git switch develop
git merge --no-ff release/1.5.0

# 태그까지 함께 밀고 release 브랜치 정리
git push origin main develop --follow-tags
git branch -d release/1.5.0
```

## GitHub Flow는 main 하나로 버틴다

이 흐름에서는 처음 상황 자체가 생기지 않는다. 덜 된 기능이 main에 들어가지 않기 때문에, 운영 버그는 main에서 브랜치를 따서 고치고 똑같은 PR 절차로 내보내면 된다. 핫픽스라고 다른 길이 없다. 대신 기능 브랜치가 길어지면 똑같이 충돌이 커지므로, PR을 작게 유지하는 습관이 전제다.

여러 버전을 동시에 유지해야 하거나 출시 전에 긴 QA가 필요하면 GitHub Flow만으로는 모자란다. 그럴 때는 필요한 버전에만 `release/1.4` 같은 브랜치를 그때 만들어 쓴다.

## GitLab Flow는 환경마다 브랜치를 둔다

GitLab Flow는 GitHub Flow에 배포 환경을 더한 모양이다. main에 합친 것을 `staging` 브랜치로, 검증이 끝나면 `production` 브랜치로 옮기는 식으로 환경마다 브랜치를 두고, 변경은 늘 main에서 아래 환경으로 한 방향으로만 흐른다(upstream first). 배포 시점을 직접 고르고 싶은데 Git Flow까지는 필요 없을 때 쓴다. 요즘은 환경 브랜치 대신 같은 커밋을 태그나 배포 도구로 환경마다 승격하는 방식도 많이 쓴다. 브랜치가 환경을 나타내면 환경 사이의 차이가 커밋 차이로 남아 관리할 것이 늘기 때문이다.

## 트렁크 기반 개발은 하루에도 여러 번 합친다

트렁크 기반 개발(Trunk-Based Development)은 모두가 하나의 브랜치(trunk, 보통 main)에 자주, 작게 합치는 방식이다. 브랜치를 쓰더라도 하루이틀 안에 끝나는 짧은 브랜치만 쓴다. DORA(DevOps Research and Assessment)의 연구는 이 방식을 배포 성과가 좋은 팀의 특징 중 하나로 꼽아 왔다. 상관관계이지 이것만 바꾸면 빨라진다는 뜻은 아니다.

그러려면 세 가지가 받쳐 줘야 한다.

첫째, 자동 테스트와 CI다. 하루에 수십 번 main에 합치는데 사람이 매번 확인할 수는 없다. 합치기 전에 테스트가 돌고, 깨지면 바로 고치거나 되돌리는 문화가 있어야 한다.

둘째, 피처 플래그(feature flag)다. 덜 된 기능도 main에 합치되, 설정값으로 꺼 둔다. 코드는 운영에 배포되어 있지만 사용자에게는 보이지 않는다. "배포"와 "출시"를 떼어 놓는 장치다.

셋째, 작은 변경이다. 큰 기능은 보이지 않는 조각(데이터 구조, API, 화면 뼈대)부터 차례로 합친다.

새 결제 화면을 만드는 짧은 브랜치를 실제로 따라가 본다.

```bash
# 최신 main에서 짧은 브랜치를 딴다
git switch main && git pull
git switch -c feat/new-checkout

# 플래그를 꺼 둔 채로 코드를 넣는다
echo '{ "newCheckout": false }' > flags.json
git add flags.json && git commit -m "feat(checkout): add new checkout behind flag"
git add checkout.test.js && git commit -m "test(checkout): cover new flow"

# 합치기 직전에 main을 다시 받아 위로 올린다 (반나절 사이에도 main은 움직인다)
git fetch
git rebase origin/main

# 밀고 PR, CI 통과 후 squash로 합친다
git push -u origin feat/new-checkout
```

```text
Current branch feat/new-checkout is up to date.
 * [new branch]      feat/new-checkout -> feat/new-checkout
branch 'feat/new-checkout' set up to track 'origin/feat/new-checkout'.
```

코드에서는 플래그로 길을 나눈다.

```tsx
// 플래그가 꺼져 있으면 기존 화면을 그대로 쓴다. 켜는 건 배포와 별개로 설정에서 한다
export function CheckoutPage() {
  return flags.newCheckout ? <NewCheckout /> : <LegacyCheckout />;
}
```

이 방식에서는 운영 버그가 생겨도 처음 상황 같은 고민이 없다. 덜 된 기능은 플래그로 꺼져 있으니 main에서 고치고 그대로 배포하면 된다. 플래그에도 비용은 있다. 켜고 끈 조합이 늘어나면 테스트해야 할 경우가 늘고, 다 켠 뒤에도 지우지 않은 플래그는 죽은 코드로 남는다. 플래그를 만들 때 지울 날짜나 담당자를 같이 적어 두는 팀이 많다.

릴리스 버전이 필요하면 main에서 태그를 붙이고, 이미 나간 버전에 수정이 필요할 때만 그 태그에서 `release/1.4` 브랜치를 딴다. 수정은 main에 먼저 넣고 release로 cherry-pick한다.

## 무엇을 고를지는 배포 주기가 정한다

| 상황 | 잘 맞는 전략 | 이유 |
|---|---|---|
| 웹 서비스, 하루 여러 번 배포 | GitHub Flow, 트렁크 기반 | main이 곧 운영이고, 브랜치를 짧게 유지할 수 있다 |
| 모바일 앱, 정해진 날 출시 | Git Flow 또는 트렁크 + release 브랜치 | 심사·QA 기간에도 다음 개발을 이어 가야 한다 |
| 여러 버전을 동시에 지원하는 라이브러리 | 트렁크 + 버전별 release 브랜치 | 오래된 버전에 보안 수정을 cherry-pick해야 한다 |
| 배포 전 스테이징 검증이 필수 | GitLab Flow, 또는 태그 승격 | 환경마다 무엇이 올라가 있는지 분명해야 한다 |
| 테스트 자동화가 약한 팀 | GitHub Flow부터 | 트렁크 기반은 CI가 받쳐 줘야 안전하다 |

팀 규모는 생각보다 결정에 덜 영향을 준다. 사람이 많아질수록 오히려 브랜치를 짧게 가져가야 충돌이 줄어든다. 판단에 쓸 만한 신호는 이렇다. 기능 브랜치가 평균 일주일을 넘기고 머지할 때마다 충돌을 푸느라 반나절을 쓴다면 브랜치가 너무 오래 산다. develop과 main의 차이를 맞추는 작업이 정기적으로 생긴다면 Git Flow가 그 팀에 무겁다. 반대로 main이 자주 깨진다면 트렁크 기반으로 가기 전에 CI부터 손봐야 한다.

어느 쪽이 맞는지는 커밋을 얼마나 잘 나누는 팀인지에 달려 있다. PR 안의 커밋이 "wip", "리뷰 반영"처럼 섞여 있다면 squash가 낫다. 커밋 하나하나가 의미 있고 따로 빌드되도록 다듬는 팀이라면 merge commit이나 rebase가 그 정보를 살린다.

[git bisect](/posts/git-tips-advanced)로 버그를 찾을 때도 차이가 난다. squash는 PR 하나가 커밋 하나라 bisect가 "이 PR이 범인이다"까지는 빨리 가지만 PR 안의 어느 단계인지는 못 가른다. merge commit 방식에서 PR 안에 빌드가 깨진 중간 커밋이 있으면 bisect가 거기서 헛걸음을 한다. 이때 Git 2.29부터 있는 `git bisect start --first-parent`를 쓰면 머지 커밋만 따라가서 PR 단위로 찾을 수 있다.

squash에는 자잘한 함정이 하나 있다. main에 생긴 커밋이 PR 브랜치의 커밋과 다른 커밋이라, Git은 그 브랜치가 머지됐다는 걸 모른다.

```bash
# squash로 합친 뒤 로컬 브랜치를 지우려고 하면
git switch main
git merge --squash feat/new-checkout && git commit -m "feat(checkout): add new checkout behind flag (#42)"
git branch -d feat/new-checkout
```

```text
warning: deleting branch 'feat/new-checkout' that has been merged to
         'refs/remotes/origin/feat/new-checkout', but not yet merged to HEAD
Deleted branch feat/new-checkout (was c8d1120).
```

이번에는 upstream에 다 밀어 둔 브랜치라 경고만 하고 지웠다. upstream이 없거나 원격 브랜치가 이미 지워진 상태라면 `error: the branch 'feat/new-checkout' is not fully merged.`와 함께 `-D`로 지우라는 안내를 내고 거부한다. 내용이 main에 들어간 건 PR 화면에서 확인하고 `-D`로 지운다. squash로 합친 브랜치에서 작업을 이어 가면 같은 변경이 두 번 들어가 충돌이 나니, 합친 브랜치는 버리고 main에서 새로 딴다.

## 버전 번호와 태그

Semantic Versioning(SemVer)은 버전을 `MAJOR.MINOR.PATCH`로 쓰고 올리는 자리에 의미를 준다. 호환을 깨는 변경이면 MAJOR, 호환되는 기능 추가면 MINOR, 호환되는 버그 수정이면 PATCH를 올린다. Conventional Commits와 짝이 맞는다. 지난 태그 이후 `fix`만 있으면 1.4.0에서 1.4.1, `feat`가 하나라도 있으면 1.5.0, `!`나 `BREAKING CHANGE`가 있으면 2.0.0이다. semantic-release나 release-please 같은 도구가 이 규칙으로 다음 버전과 변경 로그를 자동으로 만든다.

정식 출시 전 후보는 `1.5.0-rc.1`처럼 하이픈 뒤에 붙인다. SemVer에서 `1.5.0-rc.1`은 `1.5.0`보다 앞선 버전이다. `0.y.z`는 초기 개발 단계라 MINOR가 바뀌어도 호환이 깨질 수 있다는 뜻으로 읽힌다. 사전 배포 버전의 정렬 규칙과 npm의 `^`·`~` 범위가 0.x에서 어떻게 달라지는지는 [Semantic Versioning](/posts/semantic-versioning)에서 따로 다룬다.

```bash
# 릴리스 후보 태그
git tag -a v1.5.0-rc.1 -m "v1.5.0-rc.1" release/1.5.0

# 버전 순서로 태그 정렬 (문자열 순서가 아니라 숫자 순서)
git tag -l --sort=-v:refname "v1.*"

# 지금 커밋이 가장 가까운 태그에서 몇 커밋 떨어졌나
git describe
```

```text
v1.5.0-rc.1
v1.4.1
v1.4.0
```

```text
v1.4.0-5-gc976ffa
```

`describe` 출력은 "v1.4.0 태그에서 5커밋 뒤, 커밋 해시 c976ffa"로 읽는다. `g`는 git의 머리글자다. 빌드할 때 이 값을 버전 문자열로 넣어 두면 운영에서 어느 커밋이 돌고 있는지 바로 알 수 있다.

## main을 지키는 규칙은 서버에 둔다

전략이 문서로만 있으면 급할 때 깨진다. GitHub의 브랜치 보호 규칙(branch protection)이나 그 후속인 ruleset으로 서버에서 강제한다. 흔히 켜는 것은 이렇다.

- PR 없이 main에 직접 푸시 금지, 강제 푸시와 브랜치 삭제 금지
- 승인 리뷰 최소 1명, 새 커밋이 올라오면 기존 승인 무효화
- 필수 상태 검사(테스트, 빌드)가 통과해야 머지 가능
- 머지 전에 최신 main을 반영하도록 요구하거나, 머지 큐(merge queue)로 순서대로 검사 후 합치기
- 선형 히스토리 요구(merge commit 금지), 서명된 커밋 요구

`CODEOWNERS` 파일에 경로별 담당자를 적어 두면 그 경로를 건드린 PR에 자동으로 리뷰어가 지정되고, "코드 오너 승인 필수"와 묶을 수 있다. 관리자도 규칙을 따르게 할지 고르는 옵션이 있다. 급할 때 관리자가 우회할 수 있으면 결국 우회하게 되니, 꼭 필요한 경우가 아니면 관리자에게도 적용한다.

## 모노레포에서는 브랜치보다 경로가 경계다

여러 앱과 패키지를 한 저장소에 두는 모노레포는 대개 트렁크 기반과 잘 맞는다. 서로 의존하는 패키지를 한 PR에서 같이 바꿀 수 있다는 게 모노레포의 장점인데, 패키지마다 긴 브랜치를 두면 그 장점이 사라진다. 대신 경계를 브랜치가 아니라 경로로 나눈다. CODEOWNERS로 경로마다 리뷰어를 정하고, CI는 바뀐 경로에 해당하는 패키지만 빌드·테스트하고, 버전과 태그는 `web@1.5.0`, `ui@0.8.2`처럼 패키지별로 붙인다. 저장소가 커지면 개발자는 부분 clone과 sparse-checkout으로 자기 영역만 받는다.

## 처음 질문으로 돌아가면

develop에 덜 된 기능이 있는 상태에서 운영 버그를 고치려면, Git Flow에서는 main에서 hotfix를 따서 main과 develop 양쪽에 합친다. GitHub Flow와 트렁크 기반에서는 애초에 덜 된 기능이 main에 노출되지 않게(짧은 브랜치, 피처 플래그) 해서 main에서 고치고 바로 내보낸다. 어느 쪽을 고를지는 얼마나 자주 배포하느냐가 정한다. 자주 배포할수록 브랜치는 짧고 단순해야 한다.

## 면접에서 나올 만한 질문

### Git Flow와 GitHub Flow의 차이는 무엇인가요?

Git Flow는 main(출시본)과 develop(통합) 두 개의 긴 브랜치에 feature, release, hotfix 보조 브랜치를 두고, 정해진 시점에 버전을 내는 데 맞춰져 있다. GitHub Flow는 늘 배포 가능한 main 하나와 짧은 기능 브랜치, PR, 머지 후 즉시 배포가 전부다. 버전을 묶어 출시하는 모바일 앱이나 패키지에는 Git Flow가, 하루 여러 번 배포하는 웹 서비스에는 GitHub Flow가 잘 맞는다.

### Git Flow에서 핫픽스는 어떻게 처리하나요?

운영 버전인 main에서 hotfix 브랜치를 따서 고치고, main에 합쳐 패치 버전 태그를 붙인 뒤 같은 브랜치를 develop에도 합친다. develop에서 따지 않는 이유는 아직 출시하면 안 되는 기능이 섞여 있어서다. develop에 합치는 걸 빼먹으면 다음 릴리스에서 버그가 되살아나므로 두 방향 머지를 꼭 확인한다.

### 트렁크 기반 개발에서 미완성 기능은 어떻게 다루나요?

피처 플래그로 꺼 둔 채 main에 합친다. 코드는 배포되지만 사용자에게는 보이지 않아서, 배포와 출시를 분리할 수 있다. 큰 기능은 보이지 않는 조각부터 작게 나눠 합치고, 다 켠 뒤에는 플래그와 옛 코드를 지워 죽은 코드가 남지 않게 한다.

### PR을 squash로 합칠 때와 merge commit으로 합칠 때의 장단점은 무엇인가요?

squash는 PR 하나가 main의 커밋 하나가 되어 히스토리가 깔끔하고 revert가 쉽지만, PR 안의 세부 커밋 정보가 main에서 사라지고 원래 브랜치가 머지된 것으로 인식되지 않는다. merge commit은 모든 커밋과 합친 시점을 그대로 남기지만, 정리 안 된 커밋까지 남아 히스토리가 복잡해진다. bisect로 범인을 찾을 때 squash는 PR 단위까지만 좁혀지고, merge commit 방식은 `--first-parent`로 PR 단위 탐색과 세부 탐색을 둘 다 할 수 있다.

### 릴리스 브랜치에 수정을 반영할 때 어느 방향으로 cherry-pick하나요?

트렁크 기반이나 GitLab Flow에서는 main에 먼저 고치고 release 브랜치로 cherry-pick하는 upstream first를 쓴다. 그래야 다음 버전에서 수정이 빠지는 일이 없다. Git Flow는 release에서 고치고 develop으로 되돌려 합친다. 어느 쪽이든 한 방향으로 정하고 `-x`로 원본 해시를 남겨 추적할 수 있게 한다.

### Conventional Commits를 쓰면 무엇이 좋은가요?

커밋 첫 줄이 `타입(범위): 설명`으로 정형화되어 사람이 히스토리를 훑기 쉽고, 도구가 그것을 읽어 변경 로그와 다음 버전 번호를 자동으로 정할 수 있다. fix는 패치, feat는 마이너, `!`나 BREAKING CHANGE는 메이저로 SemVer와 짝이 맞는다. 규칙은 commit-msg 훅이나 CI의 commitlint로 강제하고, squash 머지 저장소라면 PR 제목에 적용한다.

### 브랜치 전략을 고를 때 무엇을 기준으로 보나요?

가장 큰 기준은 배포 주기와 동시에 유지해야 하는 버전 수다. 하루에도 여러 번 배포하면 짧은 브랜치와 main 하나가, 정해진 날 출시하고 QA 기간이 길면 release 브랜치가 있는 모델이 맞는다. 테스트 자동화 수준도 본다. CI가 약한 팀이 트렁크 기반으로 가면 main이 자주 깨지므로 GitHub Flow로 시작해 브랜치를 점점 짧게 가져가는 편이 현실적이다.
