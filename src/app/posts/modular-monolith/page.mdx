재고 팀이 `stock` 테이블의 수량 컬럼 계산 방식을 바꿨다. 재고 화면과 주문 흐름은 테스트를 모두 통과했다. 배포 다음 날, 환불하면 재고가 두 번 늘어난다는 문의가 들어왔다. 결제 모듈의 환불 코드가 재고 모듈 안쪽의 저장소 객체를 직접 가져다 쓰고 있었고, 재고 팀은 그런 코드가 있는 줄 몰랐다.

이 글은 이런 일을 막는 구조, 모듈러 모놀리스를 다룬다. 배포는 하나로 두면서 코드와 데이터 안에 업무 경계를 세우고, 그 경계를 사람의 주의력이 아니라 도구로 지키는 방법이다. 한 덩어리 구조 자체의 장단점과 장애 양상은 [모놀리스 아키텍처 글](/posts/monolith-architecture)에서, 경계를 떼어 서비스로 옮기는 과정은 [마이크로서비스 분해 글](/posts/microservices-decomposition)에서 다룬다.

## 배포는 하나, 경계는 여러 개

모듈러 모놀리스는 하나로 빌드하고 하나로 배포하지만, 내부를 업무 단위 모듈로 나누고 모듈 사이의 규칙을 강제하는 구조다. 규칙은 대체로 세 가지다.

1. 모듈은 다른 모듈의 공개 API만 부른다. 내부 파일, 내부 클래스는 건드리지 않는다.
2. 모듈은 자기 데이터만 직접 읽고 쓴다. 남의 테이블이 필요하면 그 모듈의 API나 공개 뷰를 거친다.
3. 모듈 사이 의존에는 순환이 없다.

그냥 폴더를 나눈 모놀리스와의 차이는 세 번째 단어, 강제에 있다. 폴더는 처음부터 있었다. 처음 장면의 환불 코드도 `payments` 폴더 안에 깔끔하게 들어 있었다. 다만 그 파일이 `inventory/internal`을 import하는 걸 막는 장치가 없었다.

| | 모놀리스 | 모듈러 모놀리스 | 마이크로서비스 |
|---|---|---|---|
| 배포 단위 | 하나 | 하나 | 서비스마다 |
| 모듈 사이 호출 | 아무 함수나 | 공개 API 함수 호출 | 네트워크 호출 |
| 경계를 지키는 것 | 사람의 주의 | 빌드·CI 규칙, DB 권한 | 프로세스와 네트워크 |
| 여러 모듈의 트랜잭션 | 쉽다 | 가능하지만 줄인다 | 사가 등으로 대체 |
| 운영 부담 | 낮다 | 낮다 | 서비스 수만큼 |

마이크로서비스에서는 네트워크가 경계를 공짜로 강제한다. 남의 DB에 접속할 비밀번호가 없으니 직접 읽을 수가 없다. 모듈러 모놀리스는 그 강제를 네트워크 없이 빌드 규칙과 DB 권한으로 얻으려는 시도다.

## 기술 계층이 아니라 업무로 자른다

모듈을 나누는 기준이 가장 먼저 틀리기 쉽다. `controllers/`, `services/`, `repositories/`로 나누면 모듈처럼 보이지만, 주문 기능 하나를 고치려면 세 폴더를 모두 건드려야 한다. 이건 계층이지 모듈이 아니다. 계층은 모듈 안에서 나눈다. 계층을 나누는 법은 [레이어드 아키텍처 글](/posts/layered-architecture)에 있다.

모듈은 업무 능력 단위로 자른다. 주문, 재고, 결제, 회원처럼 담당자에게 물었을 때 "그건 우리 일"이라고 답이 나오는 단위다. 같은 단어가 모듈마다 다른 뜻이면 경계를 잘 그은 것이다. 주문 모듈의 "상품"은 주문 당시 가격과 이름의 스냅숏이고, 재고 모듈의 "상품"은 창고 위치와 수량이다. 이 생각을 체계화한 게 DDD의 바운디드 컨텍스트이고, [바운디드 컨텍스트 글](/posts/ddd-bounded-context)이 경계를 찾는 방법을 자세히 다룬다.

데모로 만든 프로젝트는 이렇게 생겼다.

```text
src/
  shared/event-bus.ts           모듈 사이 이벤트 전달
  modules/
    orders/
      index.ts                  공개 API: placeOrder, orderTotal
      internal/order-service.ts
    inventory/
      index.ts                  공개 API: available
      internal/stock-repo.ts
    payments/
      index.ts                  공개 API: charge, refund
      internal/refund.ts
  main.ts
```

모듈마다 `index.ts`가 공개 API이고, `internal/` 아래는 모듈 바깥에서 import하면 안 된다. 이 블로그 코드도 같은 규칙을 쓴다. `features/{scope}/components/{name}/index.ts`로만 import하고 폴더 안쪽 파일은 직접 부르지 않는다. React 프로젝트에서 Feature-Sliced Design 같은 폴더 규칙이 노리는 것도 같다.

## 규칙은 CI가 지킨다

폴더 규칙은 문서에 적어 두면 석 달 안에 깨진다. 마감 전날 한 줄짜리 지름길은 늘 합리적으로 보이기 때문이다. 그래서 규칙을 실행 가능한 검사로 만든다. 자바스크립트·타입스크립트라면 dependency-cruiser가 흔한 선택이다. 데모 프로젝트에 넣은 설정이다.

```js
// .dependency-cruiser.cjs
module.exports = {
  forbidden: [
    {
      name: "no-reaching-into-internal",
      comment: "다른 모듈은 index.ts(공개 API)로만 부른다",
      severity: "error",
      from: { path: "^src/modules/([^/]+)/" },
      to: { path: "^src/modules/([^/]+)/internal/", pathNot: "^src/modules/$1/" },
    },
    { name: "no-circular", severity: "error", from: {}, to: { circular: true } },
  ],
  options: { tsPreCompilationDeps: true, doNotFollow: { path: "node_modules" } },
};
```

첫 규칙이 조금 까다로워 보이는데, 조각으로 나눠 읽으면 단순하다.

## 패키지 경계로 막는 더 단단한 방법

검사 도구는 위반을 찾지만 import 자체를 막지는 못한다. 모노레포에서 모듈을 워크스페이스 패키지로 나누면 Node의 `exports` 필드가 import를 막는다. 재고 모듈을 `@shop/inventory` 패키지로 만들고 공개 진입점만 적었다.

```json
{
  "name": "@shop/inventory",
  "type": "module",
  "exports": { ".": "./src/index.js" }
}
```

공개 진입점으로 부르는 코드와 내부 파일을 부르는 코드를 각각 실행했다.

```js
// app/ok.mjs
import { available } from "@shop/inventory";
console.log("available", available());

// app/bad.mjs
import { stockRepo } from "@shop/inventory/src/internal/stock-repo.js";
```

```text
Error [ERR_PACKAGE_PATH_NOT_EXPORTED]: Package subpath './src/internal/stock-repo.js' is not defined by "exports" in .../node_modules/@shop/inventory/package.json imported from .../app/bad.mjs

```

`exports`에 적지 않은 경로는 패키지 이름으로 접근할 수 없다. TypeScript도 `moduleResolution`이 `node16`, `nodenext`, `bundler`일 때 같은 규칙으로 타입 검사에서 막는다. 다만 `../../packages/inventory/src/internal/...` 같은 상대 경로는 이 장치를 우회한다. 그래서 패키지 경계와 검사 도구를 함께 쓴다. 패키지를 나누면 모듈마다 의존성 목록이 생겨서, 재고 모듈이 결제 모듈을 쓰려면 `package.json`에 적어야 하고 그게 리뷰에서 눈에 띈다는 장점도 있다.

## 데이터도 모듈이 가진다

코드 경계만 세우고 테이블은 다 같이 쓰면, 경계는 SQL 한 줄로 무너진다. 결제 모듈이 `SELECT ... FROM stock`을 직접 날리기 시작하면 재고 팀은 컬럼 하나 못 바꾼다. 그래서 테이블에도 주인을 정한다.

가장 가벼운 방법은 DB는 하나로 두고 모듈마다 스키마와 접속 역할을 나누는 것이다. PostgreSQL 16에서 재현했다.

```sql
-- 모듈마다 스키마와 접속 역할을 따로 둔다
CREATE ROLE a1_orders_app LOGIN;
CREATE ROLE a1_inventory_app LOGIN;
CREATE SCHEMA orders AUTHORIZATION a1_orders_app;
CREATE SCHEMA inventory AUTHORIZATION a1_inventory_app;

SET ROLE a1_inventory_app;
CREATE TABLE inventory.stock (sku text PRIMARY KEY, qty int NOT NULL, cost_price int NOT NULL);
INSERT INTO inventory.stock VALUES ('sku-1', 3, 21000);
-- 다른 모듈에 보여 줄 것만 담은 공개 뷰
CREATE VIEW inventory.available_stock AS SELECT sku, qty FROM inventory.stock;
RESET ROLE;

SET ROLE a1_orders_app;
SELECT * FROM inventory.stock;
```

```text
ERROR:  permission denied for schema inventory
LINE 1: SELECT * FROM inventory.stock;
                      ^
```

스키마 사용 권한(`USAGE`)부터 없으니 안을 들여다볼 수조차 없다. 이제 재고 모듈이 공개하고 싶은 것만 뷰로 열어 준다. 원가(`cost_price`)는 뷰에 넣지 않았다.

```sql
SET ROLE a1_inventory_app;
GRANT USAGE ON SCHEMA inventory TO a1_orders_app;
GRANT SELECT ON inventory.available_stock TO a1_orders_app;
RESET ROLE;

SET ROLE a1_orders_app;
SELECT * FROM inventory.available_stock;
SELECT cost_price FROM inventory.stock;
```

```text
  sku  | qty 
-------+-----
 sku-1 |   3
(1 row)

ERROR:  permission denied for table stock
```

뷰는 읽히고 원본 테이블은 막힌다. 뷰가 DB 쪽의 `index.ts`인 셈이다. 재고 팀은 뷰의 모양만 지키면 테이블 구조를 마음대로 바꿀 수 있다. 역할과 권한을 더 자세히 쓰는 법은 [PostgreSQL 역할과 권한 글](/posts/postgres-roles-security)에 있다.

이 방식에는 트레이드오프가 하나 있다. DB가 하나라서 원하면 두 모듈의 테이블을 트랜잭션 하나로 묶을 수 있다. 처음엔 편하지만 그 트랜잭션이 많아질수록 나중에 모듈을 떼어 낼 때 사가로 바꿔야 할 곳도 늘어난다. 모듈 사이 트랜잭션은 허용하되 목록을 관리하고, 새로 만들 때는 이벤트로 풀 수 있는지 먼저 본다.

## 모듈끼리 알리는 두 가지 방법

주문이 저장되면 재고를 줄여야 한다. 주문 모듈이 재고 모듈의 함수를 직접 부를 수도 있고, "주문됨" 이벤트를 발행하고 재고 모듈이 구독하게 할 수도 있다. 앞의 방식은 주문이 재고를 알고, 뒤의 방식은 재고가 주문 이벤트를 안다. 의존 방향이 반대다.

```ts
// 동기 방식: 구독자의 예외가 발행자에게 그대로 올라간다
export async function publishSync(type: string, event: unknown) {
  for (const h of handlers.get(type) ?? []) await h(event);
}

// 격리 방식: 구독자마다 따로 실행하고, 실패는 기록만 한다
export async function publishIsolated(type: string, event: unknown) {
  const results = await Promise.allSettled((handlers.get(type) ?? []).map(async (h) => h(event)));
  results.forEach((r) => {
    if (r.status === "rejected") console.log(`[bus] ${type} handler failed: ${r.reason.message}`);
  });
}
```

정상일 때, 재고 구독자가 실패할 때(동기 방식), 재고 구독자가 실패할 때(격리 방식)를 차례로 돌렸다.

```bash
node src/main.ts
BREAK_INVENTORY=1 node src/main.ts
BREAK_INVENTORY=1 ISOLATE=1 node src/main.ts
```

```text

[inventory] ord-101: sku-1 left 2
[api] 201 ord-101
---
[orders] saved ord-101
[api] 500 stock table locked
---
[orders] saved ord-101
[bus] OrderPlaced handler failed: stock table locked
[api] 201 ord-101
```

두 번째 결과가 위험하다. 주문은 이미 저장됐는데 사용자는 500을 받았다. 사용자가 다시 누르면 주문이 두 개 생긴다. 재고 모듈의 문제가 주문 API의 응답을 결정해 버렸으니, 이벤트로 바꿨어도 결합은 그대로다.

세 번째는 주문 API를 지켰지만 재고가 줄지 않았다. 실패가 로그 한 줄로 사라졌다. 이 틈을 메우려면 이벤트를 주문과 같은 트랜잭션으로 DB에 적어 두고 나중에 꺼내 전달하는 아웃박스가 필요하다. 그 구현은 [트랜잭셔널 아웃박스 글](/posts/transactional-outbox)에서 다룬다. 구독자가 같은 이벤트를 두 번 받아도 괜찮게 만드는 멱등 처리도 함께 따라온다.

## 경계가 새는 흔한 모습

규칙을 도구로 지켜도 새는 곳이 있다. 실무에서 자주 보이는 모습들이다.

공용 모듈이 커진다. `shared`나 `common`에 처음엔 날짜 포맷 함수만 있다가, 어느새 `User` 엔티티와 주문 상태 enum이 들어간다. 모든 모듈이 공용 모듈에 기대니 공용 모듈을 바꾸면 전체가 흔들린다. 공용에는 업무 지식이 없는 것(로깅, 시간, 이벤트 버스 같은 배관)만 둔다.

엔티티를 그대로 넘긴다. 주문 모듈이 공개 API로 ORM 엔티티 객체를 돌려주면, 받는 쪽이 그 객체의 지연 로딩 관계를 따라가 결국 남의 테이블을 읽는다. 공개 API는 필요한 필드만 담은 평범한 객체를 돌려준다.

ORM 관계가 경계를 넘는다. JPA라면 주문 엔티티에 `@ManyToOne Member member`를 거는 순간 회원 테이블과 묶인다. 다른 모듈의 것은 객체가 아니라 id로만 들고 있는 편이 안전하다.

리포트가 모든 테이블을 조인한다. 관리자 통계는 성격상 모든 모듈의 데이터를 본다. 이걸 모듈 경계 안에 억지로 넣지 말고, 각 모듈의 이벤트로 채우는 읽기 전용 모델을 따로 둔다. 쓰기와 읽기 모델을 나누는 생각은 [CQRS 글](/posts/cqrs)에서 이어진다.

## 떼어 낼 때 무엇이 쉬워지나

모듈러 모놀리스가 마이크로서비스로 가는 중간 단계로 자주 소개되지만, 그 자체로 끝 상태여도 괜찮다. 떼어 낼 필요가 생겼을 때 쉬워지는 이유는 경계가 이미 검증돼 있어서다.

공개 API만 쓰였다면 그 함수들의 몸통을 HTTP나 gRPC 클라이언트로 바꾸면 된다. 부르는 쪽 코드는 그대로다. 모듈 스키마에 남의 접근이 없었다면 스키마를 통째로 새 DB로 옮기면 된다. 같은 프로세스 이벤트를 쓰고 있었다면 버스를 Kafka나 RabbitMQ로 바꾸면 된다. 반대로 경계 검사 없이 폴더만 나눈 상태라면, 떼어 내기 전에 이 글의 작업을 먼저 해야 한다. 그 순서는 [마이크로서비스 분해 글](/posts/microservices-decomposition)에서 이어 간다.

모듈러 모놀리스는 마이크로서비스의 경계 규칙을 네트워크 없이 빌려 오는 구조다. 업무 단위로 모듈을 자르고, 공개 API와 공개 뷰만 열고, 순환과 침범을 CI가 막는다. 그러면 트랜잭션과 단순한 배포를 지키면서도, 한 팀의 변경이 다른 팀 코드를 몰래 깨는 일을 줄일 수 있다.

## 면접에서 나올 만한 질문

### 모듈러 모놀리스란 무엇인가요?

배포는 하나로 하면서 내부를 업무 단위 모듈로 나누고, 모듈 사이 규칙을 강제하는 구조다. 모듈은 다른 모듈의 공개 API만 부르고, 자기 데이터만 직접 다루며, 모듈 사이 의존에 순환이 없어야 한다. 그냥 폴더를 나눈 모놀리스와 다른 점은 이 규칙을 빌드·CI 검사와 DB 권한으로 강제한다는 것이다.

### 모듈 경계는 어떻게 강제하나요?

코드는 검사 도구로, 데이터는 권한으로 막는다. 자바스크립트는 dependency-cruiser나 ESLint 규칙으로 남의 internal import와 순환을 CI에서 실패시키고, 모노레포라면 패키지 `exports`로 내부 경로 import 자체를 막는다. 자바는 ArchUnit이나 Spring Modulith의 verify를 쓴다. DB는 모듈마다 스키마와 역할을 나누고 공개 뷰에만 권한을 준다.

### 계층별 폴더로 나누면 모듈러 모놀리스가 아닌가요?

아니다. controllers, services, repositories로 나눈 건 계층이고, 기능 하나를 고칠 때 모든 폴더를 건드려야 한다. 모듈은 주문, 재고처럼 업무 단위로 자르고, 계층은 그 모듈 안에서 나눈다.

### 모듈 사이 순환 의존은 왜 문제이고 어떻게 끊나요?

순환 안의 모듈은 사실상 하나라서 따로 바꾸거나 떼어 낼 수 없고, 영향 범위 테스트도 의미가 없어진다. 끊는 방법은 공통으로 필요한 것을 별도 모듈로 내리거나, 한쪽 방향을 이벤트 구독으로 바꿔 import를 없애는 것이다. 검사는 깊이 우선 탐색으로 지금 걷는 경로에 있는 모듈을 다시 만나는지 보면 된다.

### 같은 프로세스 안에서 이벤트를 쓰면 무엇을 조심해야 하나요?

구독자 실패를 어디로 보낼지 정해야 한다. 동기로 실행하면 구독자의 예외가 발행자의 응답을 바꿔서, 주문은 저장됐는데 500이 나가는 식의 일이 생긴다. 격리하면 발행자는 지키지만 실패한 처리가 사라진다. 이벤트를 같은 트랜잭션으로 저장하는 아웃박스와 재시도, 멱등 처리를 함께 둔다.

### 모듈마다 DB를 따로 둬야 하나요?

처음부터 그럴 필요는 없다. DB 하나에 모듈별 스키마와 역할을 두고 공개 뷰로만 열면 소유권은 지키면서 운영은 단순하다. 이 경우 모듈을 넘는 트랜잭션도 가능한데, 많아질수록 나중에 떼어 낼 비용이 커지니 목록을 관리하고 새로 만들 때는 이벤트로 풀 수 있는지 먼저 본다.

### 모듈러 모놀리스와 마이크로서비스 중 무엇을 먼저 고르나요?

대부분은 모듈러 모놀리스로 시작한다. 경계가 맞는지 확인하기 전에 네트워크로 나누면 잘못 그은 경계를 바꾸기 어렵고 분산 모놀리스가 되기 쉽다. 팀이 서로의 배포를 기다리거나, 특정 모듈만 전혀 다른 확장이 필요해질 때 경계가 안정적인 모듈부터 서비스로 뗀다.
