통합 테스트 하나를 고쳤을 뿐인데 CI가 12분에서 20분이 됐다. 로그를 보니 `Started ... in 14.2 seconds`가 테스트 클래스 수만큼 찍혀 있었다. 테스트 클래스마다 스프링 앱이 새로 뜨고 있었다. 원인을 따라가 보니 클래스마다 `@MockitoBean`으로 바꾸는 빈이 조금씩 달랐다.

이 글은 그 현상을 작은 주문 앱으로 재현하고, Spring Boot 테스트 도구가 각각 무엇을 띄우는지 확인한다. `@SpringBootTest`의 웹 환경, `@WebMvcTest`와 `@DataJpaTest` 같은 슬라이스, MockMvc와 `RestTestClient`, 컨텍스트 캐시와 `@MockitoBean`, 테스트 트랜잭션 롤백의 함정, Testcontainers까지다. 테스트를 어느 층에 얼마나 둘지는 [테스트 피라미드와 단위 테스트](/posts/test-pyramid-unit-tests)에서, 실제 DB에 붙는 테스트의 롤백 함정 일반은 [실제 DB로 도는 통합 테스트](/posts/integration-tests-real-db)에서 다뤘다. 여기서는 스프링이 그 일을 어떻게 하는지에 집중한다.

환경은 JDK 21, Maven 3.9, Spring Boot 4.1.1(Spring Framework 7.0.9)이다. 테스트 DB는 H2 메모리 DB를 썼다. 앱은 주문(`Order`) 엔티티와 저장소, 결제 게이트웨이를 부르는 `PaymentClient`, 주문 서비스, 컨트롤러가 전부다. `PaymentClient.charge()`는 테스트에서 진짜로 불리면 예외를 던지게 해 두었다.

## 클래스 여덟 개에 컨텍스트 여덟 개

먼저 증상부터 재현했다. 내용이 빈 `@SpringBootTest` 테스트 클래스 여덟 개를 만들고, 클래스마다 목으로 바꾸는 빈 조합만 다르게 했다.

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class Mixed2Test {
  @MockitoBean PaymentClient mPaymentClient;
  @MockitoBean Mailer mMailer;
  @Test void ok() {}
}
// Mixed1Test: PaymentClient만, Mixed3Test: PaymentClient + Sms, ... 여덟 가지 조합

한 번만 떴다. 이 앱은 빈이 230개 남짓이라 두 번째부터는 1초도 안 걸리지만(JVM이 이미 데워져서다), 빈이 수천 개이고 DB 마이그레이션까지 도는 실제 서비스에서는 한 번에 10~20초가 흔하다. 클래스 50개가 서로 다른 목 조합을 쓰면 컨텍스트 시작에만 10분 넘게 쓴다. 왜 이런 일이 생기는지 보려면 `@SpringBootTest`가 무엇을 하는지부터 봐야 한다.

캐시 통계는 이 설정 한 줄로 찍힌다. CI가 느려졌을 때 가장 먼저 켜 볼 로그다.

```properties
# src/test/resources/application.properties
logging.level.org.springframework.test.context.cache=DEBUG
```

## @SpringBootTest는 앱 전체를 띄운다

`@SpringBootTest`는 `@SpringBootApplication`이 붙은 클래스를 찾아 운영과 같은 방식으로 컨텍스트를 만든다. 자동 구성이 모두 돌고, 컴포넌트 스캔으로 찾은 빈이 모두 만들어진다. 이 앱에서는 빈 정의가 230개였다. 차이는 웹 서버를 어떻게 하느냐다.

```java
@SpringBootTest                                             // MOCK: 기본값. 서블릿 컨테이너 없이 가짜 웹 환경
@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)  // 진짜 톰캣을 빈 포트에 띄운다
@SpringBootTest(webEnvironment = WebEnvironment.DEFINED_PORT) // server.port 그대로. 병렬 실행 시 충돌
@SpringBootTest(webEnvironment = WebEnvironment.NONE)         // 웹 없이. 배치·메시지 소비자 테스트
```

기본값인 `MOCK`은 톰캣을 띄우지 않는다. 컨트롤러를 부르려면 `@AutoConfigureMockMvc`를 붙여 MockMvc로 부른다. `RANDOM_PORT`는 진짜 포트에서 HTTP를 받으니 필터, 오류 페이지, 직렬화까지 운영과 같은 길을 지난다. 대신 테스트 코드와 서버가 다른 스레드에서 돈다. 이 차이가 뒤에서 볼 트랜잭션 함정의 원인이다.

## 필요한 층만 띄우는 슬라이스

컨트롤러가 404와 400을 제대로 내는지 보려고 DB와 결제까지 띄울 필요는 없다. 슬라이스 테스트는 한 층에 필요한 자동 구성과 빈만 골라 띄운다.

```java
@WebMvcTest(OrderController.class)
class OrderControllerTest {
  @Autowired MockMvcTester mvc;
  @MockitoBean OrderService service;   // 컨트롤러가 의존하는 빈은 직접 채워 준다

  @Test void returns404WhenMissing() {
    given(service.find(99)).willThrow(new OrderNotFound(99));
    assertThat(mvc.get().uri("/orders/99")).hasStatus(404);
  }

  @Test void rejectsZeroQty() {
    given(service.place("A-1", 0)).willThrow(new IllegalArgumentException("qty must be positive"));
    assertThat(mvc.post().uri("/orders").contentType(MediaType.APPLICATION_JSON)
        .content("{\"sku\":\"A-1\",\"qty\":0}"))
        .hasStatus(400).bodyText().isEqualTo("qty must be positive");
  }
}
```

```java
@DataJpaTest
class OrderRepositoryTest {
  @Autowired OrderRepository repo;
  @Autowired TestEntityManager em;

  @Test void findsByStatusInIdOrder() {
    em.persist(new Order("A-1", 1));
    Order b = new Order("B-2", 2); b.setStatus("PAID"); em.persist(b);
    em.persist(new Order("C-3", 3));
    em.flush(); em.clear();   // 1차 캐시를 비워야 진짜 SELECT가 나간다
    assertThat(repo.findByStatusOrdered("NEW")).extracting(Order::getSku).containsExactly("A-1", "C-3");
  }

  @Test void eachTestStartsEmpty() { System.out.println("[jpa] count at start=" + repo.count()); }
}
```

각 슬라이스 안에서 빈이 몇 개인지, 무엇이 없는지 찍어 봤다.

```text
[slice] beans=124 hasRepository=0 hasPaymentClient=0
[jpa] beans=80 hasController=0 count=3
[jpa] count at start=0
```

`@WebMvcTest`는 컨트롤러, `@ControllerAdvice`, 필터, `WebMvcConfigurer`, Jackson 같은 웹 층만 올리고 서비스·저장소는 스캔하지 않는다. 그래서 `OrderService`를 목으로 채우지 않으면 컨트롤러를 만들지 못해 시작부터 실패한다. `@DataJpaTest`는 JPA, `DataSource`, 저장소만 올리고 컨트롤러는 없다. 그리고 테스트 메서드마다 트랜잭션을 열고 끝나면 롤백한다. 앞 테스트에서 세 줄을 넣었는데 다음 테스트가 0줄로 시작한 이유다. 아래 그림은 한 앱에서 세 가지 테스트가 각각 어디까지 띄우는지 보여 준다.

슬라이스는 빠르지만 슬라이스끼리 컨텍스트를 나눠 쓰지 못한다. `@WebMvcTest(OrderController.class)`와 `@WebMvcTest(PaymentController.class)`는 올리는 컨트롤러가 다르니 다른 컨텍스트다. 슬라이스를 컨트롤러마다 잘게 쪼개면 그만큼 컨텍스트가 늘어난다. 컨트롤러가 많지 않으면 `@WebMvcTest`에 클래스를 지정하지 않고 웹 층 전체를 한 번에 올리는 쪽이 캐시에는 유리하다. 그 대신 모든 컨트롤러의 의존성을 목으로 채워야 한다. 이건 트레이드오프라 정답이 없다.

`@DataJpaTest`의 `DataSource`도 알아 둘 것이 있다. 기본값 `@AutoConfigureTestDatabase(replace = NON_TEST)`는 운영용 `DataSource`를 내장 DB로 바꾸되, Testcontainers의 `@ServiceConnection`이나 `@DynamicPropertySource`로 잡은 테스트용 연결은 그대로 둔다. 4.1.1 소스의 기본값이 `NON_TEST`다. 내장 DB로 바뀌면 PostgreSQL 전용 문법이나 인덱스 동작은 검증되지 않으니, 그걸 보려면 뒤에서 볼 컨테이너를 붙인다.

## MockMvc와 진짜 포트의 차이

MockMvc는 HTTP 요청을 만들지 않는다. `DispatcherServlet`을 직접 불러서 컨트롤러, 메시지 변환기, 예외 처리기를 지나게 한다. 그래서 빠르고, 테스트와 컨트롤러가 같은 스레드에서 돈다. `MockMvcTester`는 Spring Framework 6.2에 들어온 AssertJ 스타일 API이고, 기존 `MockMvc`의 `perform().andExpect()`도 그대로 쓸 수 있다.

진짜 포트에 요청을 보낼 때는 Framework 7에 새로 생긴 `RestTestClient`를 쓴다. `WebTestClient`와 같은 모양의 API를 WebFlux 의존성 없이 쓸 수 있다. Boot 4.1.1에서는 `spring-boot-resttestclient` 의존성과 `@AutoConfigureRestTestClient`가 필요했다. 예전에 쓰던 `TestRestTemplate`도 이 모듈로 옮겨 갔다.

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureRestTestClient
class ApiATest {
  @Autowired RestTestClient client;
  @MockitoBean PaymentClient payment;

  @Test void placesOrder() {
    given(payment.charge("A-1", 2)).willReturn(true);
    client.post().uri("/orders").body(new OrderController.PlaceRequest("A-1", 2)).exchange()
        .expectStatus().isCreated()
        .expectBody().jsonPath("$.status").isEqualTo("PAID");
  }
}
```

무엇을 고를지는 무엇을 확인하고 싶은지에 달렸다. 컨트롤러의 상태 코드, 검증, 직렬화 모양은 MockMvc로 충분하다. 서블릿 필터 순서, 톰캣의 오류 처리, 실제 HTTP 헤더, 트랜잭션이 요청 경계에서 커밋되는 모습까지 보려면 진짜 포트가 필요하다. `MOCK` 환경의 MockMvc에서는 서비스의 `@Transactional`이 컨트롤러 호출 안에서 시작하고 끝나니 이 차이가 덜 보이지만, 테스트 메서드에 `@Transactional`을 붙이면 이야기가 달라진다. 그 이야기는 아래에서 한다.

## 컨텍스트 캐시는 무엇을 키로 삼나

Spring TestContext는 테스트 클래스의 설정을 모아 `MergedContextConfiguration`이라는 키를 만들고, 그 키로 이미 만든 컨텍스트를 찾는다. 키에는 이런 것들이 들어간다.

- 설정 클래스와 `@SpringBootTest(classes = ...)`, `@Import`
- 활성 프로필(`@ActiveProfiles`)
- `@TestPropertySource`와 `@SpringBootTest(properties = ...)`로 준 속성
- 컨텍스트 커스터마이저. `@MockitoBean`, `@MockitoSpyBean`, `@AutoConfigureMockMvc`, `webEnvironment`가 여기로 들어간다
- 슬라이스가 고른 자동 구성 목록

`@MockitoBean`은 테스트 클래스의 필드에 붙지만, 실제로는 "이 컨텍스트에서 이 타입의 빈을 목으로 바꿔라"라는 컨텍스트 설정이다. 그러니 목으로 바꿀 빈이 다르면 다른 컨텍스트가 필요하다. 목 객체의 동작(`given(...)`)은 키에 들어가지 않는다. 테스트가 끝날 때마다 목은 기본값으로 리셋되니, 같은 목 집합을 쓰는 클래스끼리는 컨텍스트를 나눠 써도 서로 영향을 주지 않는다.

이번 실험 앱의 테스트 여섯 클래스를 실제로 돌린 순서대로 따라가 본다. 클래스가 시작할 때 키를 만들어 캐시에서 찾고, 없으면 새로 띄워 넣는다.

마지막 통계는 `size = 4, missCount = 4`였다. `ApiCTest`는 `@TestPropertySource(properties = "spring.jpa.show-sql=true")` 한 줄 때문에 따로 떴다. 디버깅하려고 잠깐 붙인 속성이 그대로 커밋되면 이렇게 컨텍스트가 하나 늘어난다.

캐시는 기본 최대 32개이고 넘치면 가장 오래 안 쓴 것부터 닫는다(`spring.test.context.cache.maxSize`로 바꾼다). 캐시는 JVM 하나 안에서만 공유된다. Maven Surefire의 `forkCount`로 JVM을 여러 개 띄우면 JVM마다 캐시가 따로라, 같은 컨텍스트가 JVM 수만큼 뜬다. 병렬화가 생각보다 덜 빨라지는 이유다.

## 캐시를 깨는 것들을 정리하는 법

캐시 키를 줄이는 방법은 목 집합과 설정을 몇 가지 "표준 판"으로 모으는 것이다. 앞의 `IntegrationTestBase`처럼 부모 클래스에 목을 모아 두거나, 메타 어노테이션을 만든다.

```java
// 통합 테스트의 표준 판 하나
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureRestTestClient
@ActiveProfiles("test")
public @interface ApiTest {}

@ApiTest
class PlaceOrderTest extends ExternalMocks { ... }  // ExternalMocks: 바깥 시스템 목만 모은 부모 클래스
```

목을 모으면 어떤 테스트는 쓰지도 않는 목을 들고 시작한다. 그래도 목은 기본적으로 아무것도 하지 않으니 해가 없다. 정말 진짜 빈이 필요한 테스트만 다른 판을 쓴다.

`@DirtiesContext`는 캐시를 아예 버린다. 테스트가 싱글턴 빈의 상태를 바꿔 놓아서 붙였다면, 그 상태를 테스트 끝에 되돌리는 쪽이 낫다. `@MockBean`과 `@SpyBean`은 Boot 3.4에서 deprecated가 됐고 4.0에서 지워졌다. 대신 Spring Framework의 `@MockitoBean`, `@MockitoSpyBean`을 쓴다(패키지는 `org.springframework.test.context.bean.override.mockito`). 옮기는 과정은 [Spring Boot 4 마이그레이션](/posts/spring-boot-4-migration)에 있다. `@MockitoBean`은 `@Configuration` 클래스 안에서는 쓸 수 없고, 테스트 클래스나 그 부모 클래스에 둔다.

## 테스트 트랜잭션이 되돌리지 못하는 것

`@DataJpaTest`처럼 테스트 메서드에 `@Transactional`을 붙이면 메서드가 끝날 때 롤백된다. 그래서 `RANDOM_PORT` 통합 테스트에도 붙이면 깨끗해질 거라고 생각하기 쉽다. 실제로 붙여 봤다.

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureRestTestClient
@Transactional
@TestMethodOrder(MethodOrderer.OrderAnnotation.class)
class TxPitfallTest {
  @Autowired RestTestClient client;
  @Autowired OrderRepository repo;
  @MockitoBean PaymentClient payment;

  @Test @Order(1) void savedInTestIsInvisibleToServer() {
    Order o = repo.save(new Order("T-1", 1));
    System.out.println("[tx] saved id=" + o.getId() + " repo.count()=" + repo.count());
    client.get().uri("/orders/" + o.getId()).exchange().expectStatus().isNotFound();
  }

  @Test @Order(2) void savedByServerIsNotRolledBack() {
    given(payment.charge(any(), anyInt())).willReturn(true);
    client.post().uri("/orders").body(new OrderController.PlaceRequest("T-2", 1)).exchange()
        .expectStatus().isCreated();
    System.out.println("[tx] after POST countBySku(T-2)=" + repo.countBySku("T-2"));
  }

  @Test @Order(3) void leftover() {
    System.out.println("[tx] next test countBySku(T-2)=" + repo.countBySku("T-2"));
  }
}
```

```text
[tx] saved id=3 repo.count()=3
[tx] after POST countBySku(T-2)=1
[tx] next test countBySku(T-2)=1
```

세 가지가 한꺼번에 보인다. 첫째, 테스트에서 저장한 주문을 서버는 못 찾았다(404 단언이 통과했다). 둘째, 서버가 저장한 주문은 롤백되지 않고 다음 테스트에 남았다. 셋째, 처음 저장한 주문의 id가 3이고 `count()`가 3이다. 이 컨텍스트를 먼저 쓴 `ApiATest`, `ApiBTest`가 넣은 두 줄이 남아 있었다. 아래 그림에서 스레드 두 개가 각자 무엇을 보는지 따라가 본다.

JPA의 flush도 마찬가지라, 롤백 전에 `em.flush()`를 부르지 않으면 INSERT가 DB까지 가지 않아 제약 위반을 놓친다.

그래서 `RANDOM_PORT` 테스트에는 테스트 트랜잭션을 쓰지 않고, 테스트 앞이나 뒤에 데이터를 지운다. 테이블이 몇 개 안 되면 `@Sql(scripts = "/cleanup.sql", executionPhase = AFTER_TEST_METHOD)`가 간단하다. 다른 테스트 클래스가 남긴 데이터에 영향을 받지 않도록, 단언은 "전체 개수가 1" 대신 "이 테스트가 만든 SKU가 1개"처럼 자기 데이터로 좁힌다. 위 실험에서 `count()` 대신 `countBySku`를 쓴 이유다.

## 진짜 DB는 컨테이너로 붙인다

H2는 PostgreSQL이 아니다. `ON CONFLICT`, 부분 인덱스, `jsonb`, 시퀀스 동작이 다르다. 운영 DB와 같은 엔진으로 확인하려면 Testcontainers로 컨테이너를 띄운다. Spring Boot 3.1부터는 `@ServiceConnection`을 붙이면 컨테이너의 주소, 계정, 포트를 `spring.datasource.*`에 자동으로 넣어 준다. Boot 4.1.1이 관리하는 Testcontainers는 2.0.5이고, 2.x에서 모듈 이름이 `testcontainers-postgresql`로, 클래스가 `org.testcontainers.postgresql.PostgreSQLContainer`로 바뀌었다.

```xml
<dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-testcontainers</artifactId><scope>test</scope></dependency>
<dependency><groupId>org.testcontainers</groupId><artifactId>testcontainers-postgresql</artifactId><scope>test</scope></dependency>
<dependency><groupId>org.testcontainers</groupId><artifactId>testcontainers-junit-jupiter</artifactId><scope>test</scope></dependency>
```

```java
@DataJpaTest
@Testcontainers
class PgRepositoryTest {
  @Container
  @ServiceConnection
  static PostgreSQLContainer postgres = new PostgreSQLContainer("postgres:16-alpine");

  @Autowired OrderRepository repo;

  @Test void savesOnRealPostgres() { repo.save(new Order("A-1", 1)); }
}
```

이 실험 환경에는 Docker 데몬이 없어서 위 코드는 컴파일까지만 확인했다. 실행 결과는 싣지 않는다.

컨테이너와 컨텍스트 캐시가 만나는 곳에 함정이 있다. `@Container` 정적 필드는 그 테스트 클래스가 끝나면 컨테이너를 멈춘다. 그런데 컨텍스트는 캐시에 남아 다음 클래스에 재사용될 수 있다. 다음 클래스가 그 컨텍스트를 꺼내면 이미 죽은 DB 주소를 들고 있다. 여러 클래스가 같은 컨테이너를 쓰려면 `@Container`의 생명주기에 맡기지 말고, 정적 초기화 블록에서 한 번 `start()`해서 JVM이 끝날 때까지 두는 싱글턴 컨테이너 방식을 쓴다. 또는 `@TestConfiguration` 클래스에 `@Bean @ServiceConnection`으로 컨테이너를 빈으로 등록해, 컨테이너의 수명을 컨텍스트에 맞춘다. 어느 쪽이든 모든 통합 테스트가 같은 방식으로 컨테이너를 얻게 해야 캐시 키가 갈리지 않는다. 컨테이너를 CI에서 어떻게 돌리는지는 [실제 DB로 도는 통합 테스트](/posts/integration-tests-real-db)에 있다.

## CI가 느려졌을 때 보는 순서

처음의 20분짜리 CI로 돌아가서, 실제로 줄여 나가는 순서다.

```bash
# 1) 컨텍스트가 몇 번 떴는지 센다
mvn -B test | tee test.log
grep -c "Started .* in" test.log

# 2) 어떤 클래스가 새 컨텍스트를 띄웠는지와 걸린 시간
grep "Started .* in" test.log | sed 's/.*Started //'

# 3) 캐시 통계의 마지막 줄 (DEBUG 로그를 켰을 때)
grep "cache statistics" test.log | tail -1
```

`Started` 수가 테스트 클래스 수에 가깝다면 캐시가 거의 안 맞는 것이다. 새 컨텍스트를 띄운 클래스들을 나란히 놓고 목 집합, 속성, 프로필, 슬라이스 종류를 비교한다. 대부분은 목 조합 차이, 디버깅용 속성, `@DirtiesContext` 세 가지 중 하나다.

그다음은 층을 내린다. 컨트롤러의 검증과 상태 코드만 보는 `@SpringBootTest`는 `@WebMvcTest`로, 저장소 쿼리만 보는 것은 `@DataJpaTest`로 옮긴다. 비즈니스 규칙은 스프링 없이 생성자에 목을 넣어 테스트할 수 있으면 그게 가장 빠르다. 생성자 주입을 쓰면 이게 쉬워진다([IoC 컨테이너와 DI](/posts/spring-ioc-di)). 남은 `@SpringBootTest`는 표준 판 한두 개로 모은다. 마지막으로 `forkCount`를 늘릴 때는 JVM마다 컨텍스트가 다시 뜬다는 점을 계산에 넣는다.

테스트 도구를 고르는 기준은 결국 "이 테스트가 무엇이 틀렸을 때 빨간불이 들어와야 하나"다. 그 질문에 필요한 만큼만 띄우고, 띄운 것은 최대한 나눠 쓴다. 나눠 쓰는 단위가 컨텍스트 캐시 키라는 것만 기억하면 대부분의 느린 테스트는 원인이 보인다.

## 면접에서 나올 만한 질문

### @SpringBootTest와 @WebMvcTest는 어떻게 다른가요?

`@SpringBootTest`는 운영과 같은 방식으로 앱 전체 컨텍스트를 띄우고, `@WebMvcTest`는 컨트롤러·필터·메시지 변환기 같은 웹 층만 띄운다. 이 앱에서 빈 정의가 230개와 124개였다. `@WebMvcTest`는 서비스와 저장소를 스캔하지 않으니 컨트롤러가 의존하는 빈을 `@MockitoBean`으로 채워야 한다. 컨트롤러의 상태 코드와 검증은 슬라이스로, 여러 층이 함께 맞는지는 `@SpringBootTest`로 본다.

### 테스트 컨텍스트 캐시는 어떻게 동작하나요?

테스트 클래스의 설정(설정 클래스, 프로필, 속성, 목으로 바꿀 빈 같은 커스터마이저)을 모아 `MergedContextConfiguration` 키를 만들고, 같은 키면 이미 띄운 컨텍스트를 재사용한다. 캐시는 JVM 안에서만 공유되고 기본 최대 32개다. 넘치면 오래 안 쓴 것부터 닫는다. 설정이 한 글자만 달라도 다른 키가 되어 새로 뜬다.

### @MockitoBean이 테스트를 느리게 만드는 이유는요?

`@MockitoBean`은 필드에 붙지만 실제로는 컨텍스트의 빈을 바꾸는 설정이라 캐시 키에 들어간다. 클래스마다 목으로 바꾸는 빈 조합이 다르면 클래스마다 컨텍스트를 새로 띄운다. 실험에서 조합이 다른 여덟 클래스는 컨텍스트 8개, 부모 클래스로 목을 모은 여덟 클래스는 1개였다. 목의 동작(`given`)은 키에 안 들어가니 목 선언만 모으면 된다.

### @MockBean 대신 @MockitoBean을 쓰는 이유는요?

`@MockBean`과 `@SpyBean`은 Spring Boot가 제공하던 것으로 3.4에서 deprecated가 됐고 4.0에서 지워졌다. 같은 역할을 Spring Framework 6.2부터 `@MockitoBean`, `@MockitoSpyBean`이 맡는다. Boot에 묶이지 않은 테스트 컨텍스트 기능이라 일반 Spring 테스트에서도 쓴다. 옮길 때는 import만 바꾸면 되는 경우가 많지만 `@Configuration` 안에 선언하던 목은 테스트 클래스로 옮겨야 한다.

### 통합 테스트에 @Transactional을 붙이면 항상 롤백되나요?

테스트 스레드의 트랜잭션만 롤백된다. `RANDOM_PORT`로 진짜 HTTP 요청을 보내면 서버는 톰캣 스레드에서 자기 트랜잭션으로 커밋하므로 서버가 넣은 데이터는 남는다. 반대로 테스트가 넣은 커밋 전 데이터는 서버가 못 본다. MockMvc처럼 같은 스레드면 롤백은 되지만 커밋 시점이 테스트 끝으로 밀려 커밋 때의 제약 위반이나 `AFTER_COMMIT` 리스너를 놓친다.

### MockMvc와 RestTestClient는 언제 각각 쓰나요?

MockMvc는 서블릿 컨테이너 없이 `DispatcherServlet`을 직접 불러 빠르고, 컨트롤러·직렬화·예외 처리를 확인하기에 충분하다. `RestTestClient`는 Framework 7에서 생긴 클라이언트로 진짜 포트에 HTTP 요청을 보내 필터, 톰캣 오류 처리, 실제 헤더까지 운영과 같은 길을 지난다. 대신 서버가 다른 스레드라 테스트 트랜잭션 롤백에 기대면 안 된다.

### Testcontainers를 쓸 때 컨텍스트 캐시와 관련해 주의할 점은요?

`@Container` 정적 필드는 테스트 클래스가 끝나면 컨테이너를 멈추는데, 컨텍스트는 캐시에 남아 다음 클래스가 죽은 DB 주소로 재사용할 수 있다. 여러 클래스가 공유하려면 JVM 동안 한 번만 띄우는 싱글턴 컨테이너나 `@Bean @ServiceConnection`으로 컨테이너 수명을 컨텍스트에 맞춘다. 모든 테스트가 같은 방식으로 컨테이너를 얻어야 캐시 키도 하나로 모인다.
