이 시리즈에서 이 글의 자리: 앞 글 [㊾ 이메일 서비스 설계 ②](/posts/sd-email-storage-search)에서 첨부 파일을 객체 저장소에 넣는다고만 하고 넘어갔다. 이 글부터 세 편은 그 객체 저장소를 직접 설계한다. 면접의 "S3 같은 객체 저장소를 설계해 보세요"가 이 주제다. 이 글은 전체 구조, 즉 본문을 두는 곳과 이름을 적는 곳을 나누는 일을 맡는다. 같은 장의 다음 글은 [객체 저장소 설계 ②: 복제와 이레이저 코딩, 체크섬](/posts/sd-object-storage-durability), 그다음은 [객체 저장소 설계 ③: 버전, 멀티파트 업로드, 가비지 컬렉션](/posts/sd-object-storage-versioning-multipart)이다. 시리즈의 다음 사례는 [리더보드 설계 ①](/posts/sd-leaderboard-sorted-set)이다.

사진 앱을 만들었다. 사용자가 올린 사진은 웹 서버의 `/var/app/uploads/` 아래에 파일로 저장한다. 처음 석 달은 아무 문제가 없다. 그러다 디스크 사용률 알림이 온다. 2TB 디스크가 92% 찼다. 디스크를 늘리려고 서버를 내리면 그동안 아무도 사진을 못 본다. 웹 서버를 두 대로 늘렸더니 이번엔 1번 서버에 올린 사진을 2번 서버가 못 찾는다.

파일을 "어느 서버의 어느 디스크"에 묶어 둔 것이 문제다. 객체 저장소는 그 묶음을 풀어서, 앱이 이름 하나만 알면 본문을 넣고 꺼낼 수 있게 해 주는 저장소다. 이 글은 사진 서버 한 대에서 출발해 객체 저장소의 뼈대를 하나씩 세운다.

## 블록, 파일, 객체는 쌓는 층이 다르다

저장소는 흔히 세 종류로 나눈다. 셋은 경쟁 관계라기보다 위로 쌓이는 층이다.

블록 저장소는 디스크 그 자체다. 운영체제는 디스크를 정해진 크기의 칸(블록) 번호로만 본다. "1,048,576번 블록을 읽어라" 같은 명령이 오간다. AWS EBS처럼 네트워크 너머에 있어도 서버 입장에서는 꽂힌 디스크처럼 보인다. 데이터베이스나 가상 머신 디스크처럼 작은 조각을 자주 고치는 일에 맞는다.

파일 저장소는 그 블록 위에 파일 시스템(ext4, XFS 같은 것)을 얹은 것이다. 폴더와 파일 이름이 생기고, 파일 중간의 몇 바이트만 고칠 수도 있다. 여러 서버가 같이 쓰려면 NFS나 SMB 같은 프로토콜로 나눠 쓴다.

객체 저장소는 한 단계 더 단순하게 만든다. 폴더 트리가 없고, `버킷 이름 + 키` 하나로 객체 전체를 넣고 꺼낸다. 객체 중간을 고치는 명령은 없다. 바꾸려면 통째로 다시 올린다. 대신 HTTP로 어디서든 접근하고, 용량을 사실상 무한히 늘릴 수 있고, 같은 용량을 싸게 저장한다.

## 버킷, 객체, 키

용어를 정리한다. 버킷(bucket)은 객체를 담는 이름 붙은 그릇이다. S3에서는 일반 버킷 이름이 전 세계에서 하나만 존재할 수 있어서, `photos` 같은 이름은 이미 누군가 쓰고 있다. 권한, 버전 관리 여부, 수명 주기 규칙은 보통 버킷 단위로 건다.

객체(object)는 저장되는 데이터 한 덩어리다. 본문(바이트)과 메타데이터(크기, 콘텐츠 타입, 만든 시각, 사용자가 붙인 `x-amz-meta-*` 값)로 이루어진다. 키(key)는 버킷 안에서 객체를 가리키는 이름이다. `2026/10/cat.jpg`처럼 슬래시가 들어가도 폴더가 생기는 게 아니다. 이 문자열 전체가 키 하나다. 콘솔에서 폴더처럼 보이는 건 키의 앞부분(접두사)을 `/`로 끊어 묶어 보여 주는 것뿐이다.

## 무엇을 얼마나 담을지 숫자로 정한다

면접이라면 그림을 그리기 전에 범위를 정한다. 이 글은 이렇게 가정한다.

- 기능: 버킷 만들기, 객체 올리기와 내려받기, 접두사로 목록 보기, 버전 관리
- 객체 크기는 수 KB짜리 썸네일부터 수 GB짜리 동영상까지 섞여 있다
- 전체 용량 50PB(페타바이트, 1PB = 1,000TB)를 지금 절반쯤 쓰고 있다
- 데이터를 잃지 않는 것(내구성)이 가장 중요하고, 서비스가 응답하는 비율(가용성)은 99.99%
- 쓰기 한 번에 읽기가 여러 번이다. 사진은 한 번 올리고 수없이 본다

여기서 병목이 어디인지 감을 잡아 두자. 디스크 용량과 디스크가 초당 처리하는 입출력 횟수(IOPS)다. 7200rpm 하드디스크는 헤드가 움직여야 해서 무작위 읽기가 초당 대략 100~200번 수준이다. 그래서 작은 객체 수백만 개를 무작위로 읽으면 용량보다 IOPS가 먼저 바닥난다. 이 이야기는 뒤에서 다시 나온다.

용량에서 객체 수와 메타데이터 크기를 뽑아 보자. 크기 구간별로 객체 비율과 평균 크기를 정하면, 평균 객체 크기를 구할 수 있고, 쓰는 용량을 그걸로 나누면 객체 수가 나온다. 객체 하나당 메타데이터를 1KiB로 잡으면 메타데이터 전체 크기도 나온다.

## 본문과 이름표를 따로 둔다

본문과 메타데이터는 성격이 완전히 다르다. 본문은 크고, 한 번 쓰면 바뀌지 않고, 통째로 읽는다. 메타데이터는 작고, 이름으로 찾고, 접두사로 정렬해 훑고, 권한이나 버전 같은 정보가 자주 바뀐다. 같은 시스템에 두면 둘 중 하나에 맞춘 설계가 다른 쪽을 망친다.

그래서 객체 저장소는 둘을 나눈다. 비유 하나로 이 글을 끝까지 가 보자. 메타데이터 저장소는 창고의 장부다. "photos 버킷의 2026/10/cat.jpg는 7c1e… 상자"라고 적는다. 데이터 저장소는 창고다. 상자 번호만 알면 상자를 꺼내 주고, 상자 안에 무엇이 들었는지, 누구 것인지는 모른다. 장부는 작고 정교한 DB가 맡고, 창고는 싸고 큰 디스크 수천 장이 맡는다. 둘을 따로 키울 수 있다.

전체 구성은 이렇다.

- 로드 밸런서: 요청을 API 서비스 여러 대에 나눈다.
- API 서비스: 상태를 갖지 않는 서버다. 인증을 확인하고, 장부와 창고를 순서대로 부른다.
- IAM(Identity and Access Management): 이 요청을 보낸 사람이 누구이고 이 버킷에 쓸 권한이 있는지 판단한다.
- 데이터 저장소: 본문을 받아 저장하고 객체 ID(UUID)를 돌려준다. ID로만 일한다.
- 메타데이터 저장소: 버킷, 객체 이름, 객체 ID, 크기 같은 정보를 저장한다.

왜 본문을 먼저 쓰고 장부를 나중에 쓸까. 반대로 하면 장부에는 있는데 창고에는 없는 객체가 생긴다. 누군가 그 사이에 GET을 하면 "있다고 했는데 못 읽는" 상태가 된다. 본문을 먼저 쓰면 최악의 경우가 "아무도 가리키지 않는 본문"이고, 이건 사용자에게 보이지 않는다. 나중에 청소하면 된다. 실패했을 때 남는 쓰레기가 덜 해로운 쪽으로 순서를 정한 것이다.

내려받기는 거꾸로다. 권한을 확인하고, 장부에서 (버킷, 키)로 object_id를 찾고, 그 ID로 창고에서 본문을 읽어 흘려보낸다. 장부에 행이 없으면 창고에 가 보지도 않고 404다.

S3는 2020년 12월부터 새로 쓴 객체를 바로 다음 GET과 LIST에서 볼 수 있는 강한 쓰기 후 읽기 일관성을 기본으로 준다. 그 전에는 덮어쓰기와 목록이 잠시 옛 값을 보일 수 있었다. 우리 설계에서는 장부 한 행을 쓰는 순간이 "보이기 시작하는 순간"이 되도록 만들었으니 같은 성질을 얻는다.

## 창고 안을 들여다보면

데이터 저장소도 한 덩어리가 아니다. 안에 세 가지 역할이 있다.

데이터 라우팅 서비스는 창고의 출입구다. API 서비스가 보낸 본문을 받아 어느 데이터 노드에 쓸지 정하고, 읽을 때는 그 노드에서 꺼내 온다. 상태가 없어서 대수를 늘리면 처리량이 늘어난다.

배치 서비스(placement service)는 창고의 배치도를 들고 있다. 데이터 노드가 어느 랙, 어느 데이터센터에 있고 디스크가 얼마나 찼는지를 알고, "이 객체는 이 노드 셋에 둔다"를 정한다. 데이터 노드는 몇 초마다 하트비트를 보내 "살아 있고, 디스크 12장 중 11장이 정상이고, 각각 이만큼 찼다"고 알린다. 하트비트가 끊긴 노드는 배치도에서 빠진다. 배치도가 틀리면 데이터가 엉뚱한 곳에 가니, 이 서비스는 5대나 7대로 띄우고 [Raft 합의](/posts/raft-consensus)로 같은 배치도를 유지한다. 5대면 2대, 7대면 3대가 죽어도 과반이 남는다.

데이터 노드는 실제 디스크를 가진 서버다. 본문을 받아 디스크에 쓰고, 다른 노드에 복제한다.

## 사진 한 장을 파일 하나로 두면

이제 데이터 노드 한 대 안으로 들어간다. 가장 쉬운 방법은 객체 하나를 파일 하나로 쓰는 것이다. 파일 이름을 object_id로 하면 끝이다. 그런데 작은 객체가 많으면 이게 금방 무너진다. 300바이트짜리 객체 2,000개를 파일 2,000개로 쓴 것과, 큰 파일 하나에 이어 쓴 것을 ext4에서 비교했다.

```js
// smallfiles.mjs: 작은 객체 2,000개를 파일 하나씩 vs 큰 파일 하나에 이어 쓰기
import fs from "node:fs";
fs.mkdirSync("./sf/each", { recursive: true });
const body = Buffer.alloc(300, "x");
for (let i = 0; i < 2000; i++) fs.writeFileSync(`./sf/each/obj-${i}`, body);
for (let i = 0; i < 2000; i++) fs.appendFileSync("./sf/volume.dat", body);
```

```bash
node smallfiles.mjs
stat -f -c 'block size: %S bytes' .        # 파일 시스템 블록 크기
du -sh --apparent-size sf/each && du -sh sf/each          # 내용 크기 vs 실제로 차지한 크기
du -sh --apparent-size sf/volume.dat && du -sh sf/volume.dat
```

```text
block size: 4096 bytes
586K	sf/each
7.9M	sf/each
586K	sf/volume.dat
588K	sf/volume.dat
```

내용은 둘 다 586K인데, 파일 2,000개는 디스크를 7.9M 차지했다. 파일 하나가 아무리 작아도 4KiB 블록 하나를 통째로 잡기 때문이다. 300바이트를 위해 4,096바이트를 쓰니 13배가 넘게 낭비된다. 파일마다 inode(파일 정보를 담는 구조체)도 하나씩 쓴다. inode는 파일 시스템을 만들 때 개수가 정해지고, 수억 개가 되면 디렉터리 탐색과 백업이 눈에 띄게 느려진다. 디스크에 빈 용량이 남았는데 `No space left on device`가 나면 `df -i`로 inode가 바닥났는지부터 본다.

## 큰 파일에 이어 쓰고 위치를 적는다

해결책은 작은 객체 여러 개를 큰 파일 하나에 차례로 이어 붙이는 것이다. 이 큰 파일을 볼륨 파일이라고 부르자. 볼륨이 정한 크기(실무에서는 수 GB)에 이르면 닫고 새 볼륨을 연다. 이미 쓴 자리는 고치지 않고 끝에만 붙이니, 하드디스크가 가장 잘하는 순차 쓰기가 된다.

대신 "이 객체가 어느 볼륨의 몇 번째 바이트부터 몇 바이트인가"를 따로 적어야 한다. 이 표를 객체 위치표(object_mapping)라고 하자. object_id, 파일 이름, 시작 위치(오프셋), 크기 네 칸이다. 이 표는 데이터 노드 안의 SQLite에 둔다. 표 하나를 모든 노드가 같이 쓰는 큰 DB 클러스터에 두면 읽기마다 네트워크를 한 번 더 타고, 그 클러스터가 전체의 병목이 된다. 노드는 자기 디스크에 있는 객체의 위치만 알면 되니, 노드마다 작은 DB를 하나씩 들고 있는 편이 낫다. 쓰기는 객체를 만들 때 한 번, 읽기는 GET마다 있으니 읽기에 강한 관계형 DB가 잘 맞는다.

아래 그림은 객체 넷이 볼륨에 쌓이면서 위치표가 채워지는 과정이다. 볼륨 크기는 실험이라 64KiB로 작게 잡았다.

직접 만들어 돌려 봤다. 데이터 노드는 볼륨에 이어 쓰고 위치표를 SQLite에 적는다. 장부(메타데이터 저장소)도 SQLite 하나로 흉내 낸다. Node 22의 내장 `node:sqlite`를 썼다(Node 22에서는 실험 기능이라 경고가 나온다).

```js
// ministore.mjs (발췌): 데이터 노드
class DataNode {
  put(buf) {
    let file = path.join(this.dir, this.vol());
    let offset = fs.existsSync(file) ? fs.statSync(file).size : 0;
    if (offset + buf.length > this.maxVolume) {        // 가득 차면 새 볼륨
      this.volNo++; file = path.join(this.dir, this.vol()); offset = 0;
    }
    fs.appendFileSync(file, buf);                      // 덮어쓰지 않고 끝에 붙인다
    const id = crypto.randomUUID();
    this.db.prepare("INSERT INTO object_mapping VALUES (?,?,?,?)")
      .run(id, path.basename(file), offset, buf.length);
    return id;
  }
  get(id) {
    const m = this.db.prepare("SELECT * FROM object_mapping WHERE object_id=?").get(id);
    const fd = fs.openSync(path.join(this.dir, m.file), "r");
    const buf = Buffer.alloc(m.size);
    fs.readSync(fd, buf, 0, m.size, m.file_offset);   // 오프셋에서 크기만큼만 읽는다
    fs.closeSync(fd);
    return buf;
  }
}

// 장부: (버킷, 키) -> object_id
function putObject(bucket, key, body, type) {
  const id = node.put(Buffer.from(body));             // 1) 본문을 창고에
  meta.prepare("INSERT OR REPLACE INTO object VALUES (?,?,?,?,?)")
    .run(bucket, key, id, Buffer.byteLength(body), type); // 2) 이름을 장부에
  return id;
}
function list(bucket, prefix) {                       // 접두사 범위를 이름순으로 훑는다
  return meta.prepare(`SELECT object_name, size FROM object
    WHERE bucket_name=? AND object_name >= ? AND object_name < ? ORDER BY object_name`)
    .all(bucket, prefix, prefix + "￿").map((r) => `${r.object_name} (${r.size}B)`);
}
```

볼륨 두 개에 객체 넷이 들어갔고, 위치표가 각 객체의 자리를 정확히 가리킨다. `get`은 파일을 처음부터 읽지 않고 오프셋으로 바로 가서 크기만큼만 읽는다. 하드디스크에서 무작위 읽기 한 번이면 끝난다. `nope.txt`는 장부에 없으니 창고에 가지도 않고 `null`(HTTP로는 404)이다. 접두사 `2026/10/`로 목록을 보면 11월 사진은 빠진다. 폴더가 없어도 키를 이름순으로 정렬해 두면 "폴더 안 보기"가 범위 검색 하나로 된다.

이어 쓰기에는 대가가 있다. 볼륨 하나에 여러 요청이 동시에 쓰면 끝 위치를 두고 다툰다. 쓰기를 한 줄로 세워야 해서 CPU 코어가 많아도 볼륨 하나는 한 번에 한 쓰기만 받는다. 그래서 코어마다 자기 볼륨을 따로 열어 다툼을 없앤다. 그리고 지운 객체의 자리가 볼륨 중간에 구멍으로 남는다. 이 구멍을 메우는 컴팩션은 [③편](/posts/sd-object-storage-versioning-multipart)에서 직접 돌린다.

## 장부는 무엇을 담고 어떻게 나누나

메타데이터 저장소에는 표가 두 개 있다.

```sql
-- 버킷: 사용자당 개수 제한이 있어서 전체가 작다
CREATE TABLE bucket (
  bucket_id   uuid PRIMARY KEY,
  bucket_name text UNIQUE NOT NULL,
  owner_id    bigint NOT NULL,
  versioning  boolean NOT NULL DEFAULT false
);

-- 객체: 수십억 행이 된다
CREATE TABLE object (
  bucket_name  text NOT NULL,
  object_name  text NOT NULL,
  object_id    uuid NOT NULL,      -- 창고의 상자 번호
  size         bigint NOT NULL,
  content_type text,
  created_at   timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (bucket_name, object_name)
);
```

장부가 답해야 할 질문은 셋이다. 이름으로 object_id 찾기, 이름으로 넣고 지우기, 접두사로 목록 보기. 버킷 표는 작아서 DB 한 대에 다 들어간다. 읽기가 많으니 [읽기 복제본](/posts/sd-db-replication-intro)만 붙이면 된다. 객체 표는 앞에서 계산한 대로 10억 행, 1TB를 넘으니 [샤딩](/posts/sd-sharding-intro)해야 한다. 무엇으로 나눌지가 문제다.

버킷으로 나누면 한 버킷의 객체가 한 샤드에 모여서 목록 보기가 쉽다. 하지만 버킷 하나에 객체가 수십억 개 들어가는 일이 흔하다. 로그를 쌓는 버킷 하나가 샤드 하나를 터뜨린다. 객체 ID로 나누면 고르게 퍼지지만, 질문은 늘 이름으로 오니 이름으로 ID를 찾을 방법이 없다. 그래서 `hash(bucket_name, object_name)`으로 나눈다. 이름으로 찾기와 넣기는 샤드 하나만 보면 되고, 큰 버킷도 고르게 흩어진다.

// listing.mjs (발췌): 샤드마다 "token 뒤, 접두사 안, 이름순 limit개"를 묻고 합친다
function listPage(bucket, prefix, token, limit) {
  const after = token ?? prefix;
  const rows = shards.flatMap((s) => s.prepare(
    "SELECT name FROM object WHERE bucket=? AND name > ? AND name < ? ORDER BY name LIMIT ?")
    .all(bucket, after, prefix + "￿", limit).map((r) => r.name));
  const page = rows.sort().slice(0, limit);
  return { page, next: page.length === limit ? page[page.length - 1] : null, asked: rows.length };
}

S3의 `ListObjectsV2`도 `continuation-token`과 페이지당 최대 1,000개(`max-keys`)로 이렇게 넘긴다.

그래도 목록이 자주 쓰이는 서비스라면 목록 전용 표를 하나 더 둔다. 같은 내용을 `bucket_name`으로 샤딩한 사본이다. 이름으로 찾기는 원래 표가, 목록은 이 사본이 맡는다. 쓰기가 두 번이 되고 둘이 잠깐 어긋날 수 있다는 대가가 있다. 객체 저장소는 목록 성능을 최우선으로 하지 않는 시스템이라 이 정도 타협이 흔하다. 콘솔에서 폴더를 열 때 오래 걸리는 건 설계상 예상된 일이다.

## 장애가 나면 어디부터 보나

이 구조를 알면 증상에서 원인을 좁히는 순서가 보인다.

GET이 403이면 IAM 단계다. 버킷 정책, 사용자 권한, 서명 시각(서버 시계가 15분쯤 어긋나면 서명이 거부된다)을 본다. 404인데 분명히 올렸다면 장부를 의심한다. 키 철자, 앞의 `/` 유무, 대소문자, 그리고 올리기가 실제로 200으로 끝났는지를 확인한다. PUT이 500으로 끝났다면 본문은 창고에 들어갔어도 장부에는 없을 수 있다.

GET이 성공하는데 느리다면 크기에 따라 갈린다. 큰 객체가 느리면 네트워크 대역폭이나 데이터 노드 디스크 처리량이고, 작은 객체 여러 개가 느리면 IOPS나 장부 조회다. 목록이 느리면 샤드 수와 페이지 크기를 본다. 같은 접두사로 짧은 시간에 요청이 몰리면 그 접두사를 맡은 쪽만 뜨거워질 수 있다. S3는 접두사 하나당 초당 GET 5,500개, PUT 3,500개 정도를 기준으로 안내하고, 그보다 많으면 접두사를 여러 개로 나누라고 권한다.

## 면접에서 나올 만한 질문

### 블록, 파일, 객체 저장소는 어떻게 다른가요?

블록 저장소는 디스크를 블록 번호로 다루고, 파일 저장소는 그 위에 폴더와 파일을 얹고, 객체 저장소는 버킷과 키로 객체 전체를 넣고 꺼낸다. 객체는 중간을 고칠 수 없고 통째로 다시 올려야 하지만, HTTP로 어디서든 접근하고 용량을 거의 무한히 늘릴 수 있다. DB나 VM 디스크는 블록, 여러 서버의 공유 폴더는 파일, 사진과 백업과 로그는 객체가 맞다.

### 메타데이터와 데이터를 왜 나누나요?

크기와 접근 방식이 전혀 달라서다. 본문은 크고 바뀌지 않아 싼 디스크에 순차로 쓰면 되고, 메타데이터는 작고 이름으로 찾고 정렬해 훑어야 해서 DB가 맞다. 나누면 각자 따로 늘릴 수 있다. 계산해 보면 본문 25PB에 메타데이터 1TB 수준이라, 같은 시스템에 두면 어느 한쪽에 맞춘 설계가 다른 쪽에 낭비가 된다.

### 올릴 때 본문과 메타데이터 중 무엇을 먼저 쓰나요?

본문을 먼저 쓰고 복제까지 끝난 뒤 메타데이터를 쓴다. 반대로 하면 장부에는 있는데 본문이 없는 객체가 생겨 GET이 실패한다. 본문을 먼저 쓰면 실패했을 때 남는 건 아무도 가리키지 않는 본문뿐이고, 이건 가비지 컬렉터가 나중에 치운다. 메타데이터 한 행을 쓰는 순간이 객체가 보이기 시작하는 순간이 되어 쓰기 후 읽기 일관성도 얻는다.

### 작은 객체를 파일 하나씩 저장하면 무엇이 문제인가요?

파일마다 최소 한 블록(보통 4KiB)과 inode 하나를 쓴다. 300바이트 객체 2,000개를 파일로 쓰니 내용은 586K인데 디스크는 7.9M을 썼다. inode가 수억 개가 되면 탐색과 백업이 느려지고 inode가 먼저 바닥날 수 있다. 그래서 큰 볼륨 파일에 이어 쓰고 (파일, 오프셋, 크기)를 위치표에 적는다.

### 위치표는 어디에 두나요?

데이터 노드마다 SQLite 같은 작은 DB로 둔다. 노드는 자기 디스크에 있는 객체만 알면 되고, 중앙 DB 클러스터에 두면 읽기마다 네트워크를 한 번 더 타고 그 클러스터가 전체의 병목이 된다. 쓰기는 객체를 만들 때 한 번이고 읽기가 대부분이라 관계형 DB로 충분하다.

### 객체 표는 무엇으로 샤딩하나요?

`hash(bucket_name, object_name)`으로 나눈다. 버킷으로 나누면 객체가 수십억 개인 버킷 하나가 샤드 하나를 터뜨리고, 객체 ID로 나누면 이름으로 오는 질문을 받을 수 없다. 대가는 목록 보기다. 접두사가 같은 키가 모든 샤드에 흩어져서 샤드마다 묻고 합쳐야 한다.

### 그러면 목록 보기는 어떻게 빠르게 하나요?

먼저 페이지를 번호(OFFSET)가 아니라 마지막으로 본 키를 토큰으로 넘긴다. 그러면 샤드마다 그 키 뒤부터 limit개만 읽어 합치면 된다. 그래도 샤드 수만큼 질문이 나가니, 목록이 중요하면 같은 내용을 버킷으로 샤딩한 목록 전용 표를 따로 두고 한 샤드에서 끝낸다. 쓰기가 두 번이 되고 잠시 어긋날 수 있다는 걸 받아들인다.

### 트래픽이 10배가 되면 어디부터 늘리나요?

API 서비스와 데이터 라우팅 서비스는 상태가 없어서 대수만 늘리면 된다. 저장 용량은 데이터 노드를 더하고 배치 서비스가 새 노드에 새 객체를 보낸다. 메타데이터는 샤드를 늘리고 읽기 복제본을 붙인다. 작은 객체가 많아 IOPS가 먼저 바닥나면 자주 읽는 객체 앞에 캐시나 CDN을 두는 게 디스크를 늘리는 것보다 싸다.
