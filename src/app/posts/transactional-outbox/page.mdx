아웃박스를 붙인 지 한 달이 지났다. 주문은 빠짐없이 이벤트로 나간다. 그런데 새 문의가 들어온다. 배송 서비스 로그에 `OrderShipped`가 `OrderPaid`보다 먼저 찍혀서 배송 준비가 거절됐다. 결제 직후 알림이 1초쯤 늦게 온다는 말도 있다. 아웃박스 테이블은 3억 행이 넘었고, 보낸 행을 지우는 배치가 돌 때마다 DB CPU가 튄다. 아웃박스의 원리는 알고 있었는데, 릴레이를 운영하는 법은 몰랐던 것이다.

트랜잭셔널 아웃박스(transactional outbox)는 업무 데이터와 "보낼 이벤트"를 같은 DB 트랜잭션에 쓰고, 따로 도는 릴레이가 그 행을 읽어 브로커로 보내는 패턴이다. DB 커밋과 브로커 전송을 하나로 묶을 수 없어서 생기는 이중 쓰기 문제를 푼다. 이 패턴이 왜 필요한지와 `FOR UPDATE SKIP LOCKED`로 옮기는 기본형은 [서비스 규모별 DB 설계](/posts/db-architecture-by-scale)에, 보낸 뒤 표시하기 전에 죽으면 두 번 나가는 문제는 [사가 패턴](/posts/saga-pattern)에, id 순서로 읽으면 늦게 커밋된 행을 놓치는 문제와 WAL을 읽는 CDC는 [이벤트 기반 아키텍처](/posts/event-driven-architecture)에 있다.

이 글은 그 다음, 릴레이를 직접 운영할 때 고를 것들을 본다. 언제 깨어날지, 여럿 띄울 때 순서를 어떻게 지킬지, 계속 실패하는 사건 하나를 어떻게 다룰지, 쌓인 테이블을 어떻게 비울지, 브로커가 아닌 외부 API에 보낼 때는 무엇이 다른지다. 예제는 Node 22와 PGlite 0.2.17(PostgreSQL 16.4의 WebAssembly 빌드)에서 돌렸다. PGlite는 연결이 하나뿐이라, 동시에 도는 릴레이 둘은 메모리 시뮬레이션으로 보여 준다.

## 두 군데에 쓰는 순간 어디서든 끊긴다

짧게 짚고 넘어가자. 주문을 DB에 커밋하고 이어서 브로커에 보내면, 그 사이에 프로세스가 죽을 때 주문은 있는데 이벤트가 없다. 순서를 바꿔 먼저 보내고 커밋하면, 커밋이 실패할 때 없는 주문의 이벤트가 나간다. 어떤 순서로도 두 저장소에 걸친 쓰기는 원자적이지 않다.

아웃박스는 쓰는 곳을 하나로 줄인다. 주문과 이벤트 행이 같은 트랜잭션이니 둘 다 남거나 둘 다 없다. 그 뒤의 전송은 "DB에 남은 행을 언젠가 반드시 보낸다"는 별개의 문제가 되고, 실패하면 다시 보내면 된다. 그 대가로 이벤트는 "적어도 한 번" 나가고, 받는 쪽이 중복을 거른다([메시지 전달 보장](/posts/message-delivery-semantics)). 여기까지가 앞의 글들에서 다룬 내용이다.

## 릴레이가 언제 깨어나나

가장 단순한 릴레이는 1초마다 테이블을 본다. 이 간격이 그대로 지연이 된다. 주문을 불규칙한 간격으로 30건 넣으면서, 행을 만든 시각부터 릴레이가 집어 간 시각까지를 쟀다.

```js
async function drain() {
  await db.transaction(async (tx) => {
    const { rows } = await tx.query(
      `SELECT id, extract(epoch FROM clock_timestamp() - created_at) * 1000 AS waited
       FROM outbox WHERE published_at IS NULL
       ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED`);
    for (const r of rows) delays.push(Number(r.waited));   // 여기서 브로커로 보낸다
    if (rows.length)
      await tx.query("UPDATE outbox SET published_at = now() WHERE id = ANY($1)", [rows.map((r) => r.id)]);
  });
}

// 1초마다 폴링
while (!stop) { await drain(); await sleep(1000); }
```

간격을 100ms로 줄이면 지연은 줄지만, 릴레이가 하루에 86만 번 빈 쿼리를 던진다. 릴레이가 여러 개면 그 배수다. PostgreSQL에는 다른 방법이 있다. 쓰는 쪽이 `NOTIFY`를 보내고 릴레이가 `LISTEN`으로 기다리다가 신호가 오면 바로 읽는 것이다.

```js
// 주문을 쓰는 트랜잭션 안에서 신호를 남긴다. 커밋될 때 전달된다
await db.transaction(async (tx) => {
  await tx.query("INSERT INTO outbox (aggregate_id, event_type, payload) VALUES ($1, 'OrderPaid', '{}')", [id]);
  await tx.query("NOTIFY outbox_new");
});

// 릴레이: 신호가 오면 바로 읽고, 놓친 신호에 대비해 5초 폴링도 남긴다
await db.listen("outbox_new", () => drain());
while (!stop) { await sleep(5000); await drain(); }
```

```text
poll 1000ms      n=30 p50=537ms max=980ms
notify + 5s poll n=30 p50=4ms max=11ms
wakeups: 30
after rollback wakeups: 0
```

1초 폴링은 중앙값 537ms, 최대 980ms를 기다렸다. 평균적으로 간격의 절반이다. 신호로 깨우니 중앙값 4ms가 됐다. 이 숫자는 DB와 릴레이가 한 프로세스에 있는 PGlite에서 잰 것이라 네트워크를 건너는 실제 환경보다 작다. 봐야 할 건 지연이 폴링 간격에 묶이지 않게 됐다는 점이다. 마지막 줄은 `BEGIN; NOTIFY outbox_new; ROLLBACK;`의 결과다. 롤백한 트랜잭션의 신호는 아예 전달되지 않는다.

신호는 알림일 뿐 보장이 아니다. 듣는 연결이 끊겨 있던 동안 보낸 신호는 사라지고, 다시 연결해도 받을 수 없다. 그래서 신호에 이벤트 내용을 싣고 그것만 믿으면 안 된다. 신호는 "테이블을 보라"는 뜻으로만 쓰고, 긴 간격의 폴링을 함께 남긴다. 같은 트랜잭션 안의 같은 채널, 같은 내용의 신호는 하나로 합쳐지니 주문이 몰려도 릴레이가 그만큼 여러 번 깨어나지는 않는다. 또 `LISTEN`은 연결을 붙잡고 있어야 해서, 트랜잭션 단위로 연결을 돌려쓰는 PgBouncer 뒤에서는 동작하지 않는다. 릴레이는 DB에 직접 붙거나 세션 모드 풀을 쓴다. `LISTEN`과 `NOTIFY` 자체는 [PostgreSQL 함수와 트리거](/posts/postgres-functions-triggers)에서 더 다룬다.

## 릴레이를 둘 띄우면 순서가 바뀐다

처리량이 모자라 릴레이를 둘로 늘렸다. `FOR UPDATE SKIP LOCKED` 덕분에 두 릴레이는 같은 행을 집지 않는다. 그런데 같은 주문의 사건을 서로 나눠 가질 수는 있다. 주문 201의 사건 셋과 주문 202의 사건 하나가 쌓여 있고, 릴레이 A가 GC 멈춤으로 잠깐 느려진 상황을 메모리에서 흉내 냈다.

```js
const outbox = [
  { id: 1, agg: 201, type: "OrderPlaced" }, { id: 2, agg: 202, type: "OrderPlaced" },
  { id: 3, agg: 201, type: "OrderPaid" },   { id: 4, agg: 201, type: "OrderShipped" },
];
// LIMIT 2 FOR UPDATE SKIP LOCKED 를 흉내 낸다: 잠기지 않은 행 중 앞의 둘
const take = (n) => outbox.filter((r) => !locked.has(r.id)).slice(0, n).map((r) => (locked.add(r.id), r));
await Promise.all([relay("relay-A", 30), relay("relay-B", 5)]);   // A는 한 건 보내는 데 30ms
```

```text
relay-A took #1,#2
relay-B took #3,#4
consumer saw: 201:OrderPaid  201:OrderShipped  201:OrderPlaced  202:OrderPlaced
```

주문 201의 `OrderPaid`와 `OrderShipped`가 `OrderPlaced`보다 먼저 도착했다. 처음에 말한 배송 서비스의 거절이 이것이다. 아래 그림이 그 순간을 따라간다.

릴레이가 하나여도 같은 일이 생길 수 있다. 배치 안에서 병렬로 보내거나, 보내기 실패한 사건을 다음 차례로 미루고 뒤의 사건을 먼저 보내면 된다. 받는 쪽이 사건의 대상별 버전을 보고 옛 버전을 버리게 하는 방어는 [이벤트 기반 아키텍처](/posts/event-driven-architecture)에서 다룬다. 그 방어는 "늦게 온 옛 사건을 버린다"까지는 해 주지만, "먼저 온 뒤 사건을 기다렸다가 처리한다"까지는 해 주지 않는다. 순서는 보내는 쪽에서 지키는 편이 싸다.

## 주문마다 맨 앞 사건만 보낸다

순서를 지키는 규칙은 하나로 줄일 수 있다. 같은 대상의 사건은 앞의 것이 나가기 전에 뒤의 것을 보내지 않는다. 쿼리로 쓰면 "대상마다 아직 안 나간 사건 중 가장 앞선 것 하나"만 고른다.

```sql
-- 주문마다 아직 안 나간 사건 중 가장 앞선 것 하나만, 그것이 지금 보낼 때일 때만
SELECT id, aggregate_id, event_type, attempts
FROM (
  SELECT DISTINCT ON (aggregate_id) *
  FROM outbox
  WHERE published_at IS NULL
  ORDER BY aggregate_id, id
) head
WHERE next_attempt_at <= now()
ORDER BY id
LIMIT 100;
```

같은 데이터로 돌려 봤다. 주문 202의 첫 사건(#2)은 받는 쪽이 계속 400을 돌려줘서 세 번 실패했고, 다음 시도가 8분 뒤로 미뤄진 상태다.

```text

round 2: #3 201:OrderPaid
round 3: #4 201:OrderShipped
```

주문 201의 사건은 한 차례에 하나씩 순서대로 나갔다. 주문 202는 아무것도 나가지 않았다. 머리인 #2가 쉬는 중이라 뒤의 `OrderPaid`(#6)도 기다린다. 이게 이 방식의 대가다. 한 주문 안에서 직렬이 되니 주문 하나에 사건이 몰리면 느리고, 머리 하나가 막히면 그 주문 전체가 멈춘다.

`DISTINCT ON`에는 `FOR UPDATE`를 붙일 수 없어서(`FOR UPDATE is not allowed with DISTINCT clause`), 이 쿼리만으로는 릴레이 여럿이 같은 머리를 동시에 집을 수 있다. 그래서 릴레이를 여럿 띄울 때는 주문 ID로 담당을 나눈다. 릴레이 N개가 각자 `hashtext(aggregate_id::text) % N = 내 번호`인 주문만 맡으면, 한 주문은 늘 한 릴레이가 보낸다. 같은 번호를 두 프로세스가 맡지 않게 `pg_try_advisory_lock(내 번호)`로 담당을 잡아 둔다. 잠금은 연결이 끊기면 풀리니, 죽은 릴레이의 몫은 다른 프로세스가 이어받는다.

## 계속 실패하는 사건 하나

브로커는 살아 있는데 특정 사건만 계속 실패하는 경우가 있다. 메시지가 브로커의 크기 제한을 넘었거나, 웹훅을 받는 쪽이 그 사건의 형식을 거부하거나(400), 직렬화 코드가 그 데이터에서만 예외를 던진다. 이런 사건을 그냥 다시 시도하면 릴레이가 같은 행을 몇 밀리초마다 붙잡고 같은 에러를 찍는다.

그래서 아웃박스 행에 실패 기록을 둔다.

```sql
ALTER TABLE outbox
  ADD COLUMN attempts int NOT NULL DEFAULT 0,
  ADD COLUMN next_attempt_at timestamptz NOT NULL DEFAULT now(),
  ADD COLUMN last_error text;

-- 보내기에 실패하면: 횟수를 올리고, 다음 시도를 지수적으로 미룬다 (1, 2, 4, 8 … 분, 최대 1시간)
UPDATE outbox
SET attempts = attempts + 1,
    next_attempt_at = now() + least(interval '1 minute' * power(2, attempts), interval '1 hour'),
    last_error = $2
WHERE id = $1;
```

`attempts`가 상한(예: 10)을 넘으면 더 시도하지 않고 사람에게 알린다. 앞 절의 실행 결과에서 남은 행을 보면 무엇이 막혔는지 바로 보인다.

```text
[
  {
    id: 2,
    aggregate_id: 202,
    event_type: 'OrderPlaced',
    attempts: 3,
    last_error: '400 schema mismatch'
  },
  {
    id: 4,
    aggregate_id: 201,
    event_type: 'OrderShipped',
    attempts: 0,
    last_error: null
  },
  {
    id: 6,
    aggregate_id: 202,
    event_type: 'OrderPaid',
    attempts: 0,
    last_error: null
  }
]
```

여기서 하나를 정해야 한다. 순서를 지키는 사건이면, 막힌 머리(#2)를 옆으로 치우는 순간 뒤의 `OrderPaid`(#6)가 먼저 나가 순서가 깨진다. 그래서 순서가 중요한 흐름에서는 머리를 치우지 않고 그 주문을 멈춘 채 알림을 보내 사람이 고치게 한다. 순서가 상관없는 사건이면 상한을 넘은 행을 별도 테이블(`outbox_parked`)로 옮기고 나머지를 계속 보낸다. 브로커 쪽에서 같은 문제를 다루는 방법은 [데드 레터 큐](/posts/dead-letter-queue)에 있다.

이 절에서 흔한 실수는 실패 기록을 남기는 `UPDATE`를 보내기와 같은 트랜잭션에 넣는 것이다. 보내기 도중 예외가 나서 트랜잭션이 통째로 롤백되면 `attempts`도 함께 사라져, 몇 번을 실패해도 0으로 남는다. 실패 기록은 예외를 잡은 뒤 별도로 커밋한다.

## 아웃박스 테이블 청소

보낸 행은 언젠가 지워야 한다. 지우지 않으면 아웃박스 테이블이 업무 테이블보다 커진다. 하루 10만 건씩 열흘치, 100만 행을 넣고 하루치를 지우는 두 방법을 비교했다.

```sql
-- A: 한 테이블에 쌓고 DELETE로 지운다
DELETE FROM outbox_flat WHERE created_at < '2026-10-12';
VACUUM outbox_flat;

-- B: 하루 단위 파티션으로 쌓고 하루치를 떼어 낸다
CREATE TABLE outbox_p (
  id bigserial, created_at timestamptz NOT NULL, payload jsonb NOT NULL, published_at timestamptz,
  PRIMARY KEY (id, created_at)          -- 파티션 키가 기본 키에 들어가야 한다
) PARTITION BY RANGE (created_at);
CREATE TABLE outbox_p_11 PARTITION OF outbox_p FOR VALUES FROM ('2026-10-11') TO ('2026-10-12');
-- … 날짜마다 하나씩
ALTER TABLE outbox_p DETACH PARTITION outbox_p_11;
DROP TABLE outbox_p_11;
```

```text
flat size before: 132 MB
DELETE one day (100k rows)         496ms
flat size after DELETE: 132 MB
VACUUM                             423ms
flat size after VACUUM: 132 MB
partition 11 size: 14 MB
DETACH + DROP one day partition    7ms
{ count: 900000 }
```

`DELETE`는 10만 행을 지우는 데 496ms가 걸렸고, 지운 뒤에도 테이블은 132MB 그대로다. 지운 행은 죽은 튜플로 남아 있다가 `VACUUM`이 돌아야 재사용할 수 있는 빈자리가 되고, 파일 크기는 `VACUUM`을 해도 줄지 않는다. 운영 중인 아웃박스에서는 이 `DELETE`가 WAL을 만들고, 복제본으로 흘러가고, 릴레이의 쿼리와 경쟁한다. 파티션을 떼어 내는 쪽은 7ms였다. 행을 하나씩 지우지 않고 파일째 버리기 때문이다.

<Callout kind="warning">
`DETACH PARTITION`은 기본적으로 부모 테이블에 강한 잠금을 잡아서, 그 순간 아웃박스에 쓰는 주문 트랜잭션이 잠깐 기다린다. PostgreSQL 14부터 있는 `DETACH PARTITION … CONCURRENTLY`는 더 약한 잠금으로 떼어 내지만 트랜잭션 블록 안에서는 쓸 수 없다. 떼어 낼 파티션에 아직 안 나간 행이 없는지(`published_at IS NULL`인 행 수가 0인지) 먼저 확인하고, 잘못 떼어 냈다면 `DROP` 전에 `ATTACH PARTITION`으로 되돌릴 수 있다.
</Callout>

파티션을 쓸 때 미래 날짜의 파티션을 미리 만들어 두는 일을 잊으면, 그날 0시에 아웃박스 INSERT가 `no partition of relation "outbox_p" found for row`로 실패하고 주문 트랜잭션 전체가 롤백된다. 파티션 생성은 며칠치를 앞서 만드는 작업(pg_partman 같은 도구나 매일 도는 배치)으로 맡긴다. CDC로 아웃박스를 읽는다면 행을 남겨 둘 필요조차 없다. 넣자마자 같은 트랜잭션에서 지워도 WAL에는 INSERT가 남기 때문이다(Debezium 문서도 이 방식을 소개한다).

## 브로커가 아닌 곳으로 보내는 아웃박스

아웃박스는 브로커 전용이 아니다. "DB 커밋과 함께 반드시 일어나야 하는 바깥 일"이면 다 된다. 가입하면 환영 메일을 보낸다, 결제가 끝나면 파트너사 웹훅을 부른다, 주문이 들어오면 외부 ERP에 등록한다. 이것들을 커밋 직후 바로 HTTP로 부르면 처음의 이중 쓰기 문제가 그대로 생긴다.

외부 API로 보낼 때는 중복을 받는 쪽이 거를 수 있게 이벤트 ID를 멱등성 키로 넘긴다. 메일 발송 API를 흉내 낸 로컬 서버에 보내고, 첫 시도는 응답을 받은 직후 표시하기 전에 죽게 했다.

```js
async function relay(crashAfterSend) {
  const { rows } = await db.query(
    "SELECT id, event_id FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT 10");
  for (const r of rows) {
    const res = await fetch(url, {
      method: "POST",
      headers: { "Idempotency-Key": r.event_id },   // 아웃박스 행의 UUID를 그대로 키로
      body: "{}",
    });
    console.log(`#${r.id} -> ${res.status} replayed=${res.headers.get("idempotent-replayed") ?? "-"} ${await res.text()}`);
    if (crashAfterSend) { console.log("relay crashed before marking published"); return; }
    await db.query("UPDATE outbox SET published_at = now() WHERE id = $1", [r.id]);
  }
}
await relay(true);
await relay(false);
```

```text
#1 -> 202 replayed=- {"messageId":"msg-1"}
relay crashed before marking published
#1 -> 200 replayed=true {"messageId":"msg-1"}
mails actually sent: 1
```

릴레이는 같은 행을 두 번 보냈지만, 받는 쪽이 같은 키를 알아보고 첫 응답을 다시 돌려줬다. 메일은 한 통만 나갔다. 아래 그림에서 다음을 누르면 그 두 번의 시도가 차례로 나온다.

외부 API는 브로커보다 훨씬 자주, 오래 실패한다. 앞 절의 `attempts`와 지수 백오프가 여기서 특히 중요하다. 파트너사가 30분 점검에 들어가도 릴레이는 몇 번만 두드리고 기다린다.

## 아웃박스 말고 고를 수 있는 것

같은 문제를 푸는 다른 방법들과 비교하면 아웃박스의 자리가 보인다.

| 방법 | 어떻게 | 얻는 것 | 치르는 것 |
|---|---|---|---|
| 폴링 아웃박스 | 테이블에 쓰고 릴레이가 읽는다 | 단순하다. DB만 있으면 된다 | 폴링 지연, 테이블 청소, 릴레이 운영 |
| CDC 아웃박스 | 테이블이나 `pg_logical_emit_message`를 WAL에서 읽는다 | 커밋 순서 그대로, 폴링 쿼리 없음 | 복제 슬롯 감시, Debezium 같은 부품 |
| 자기 이벤트 듣기 | 브로커에 먼저 쓰고, 자기 DB도 그 이벤트를 소비해 고친다 | 이중 쓰기가 사라진다 | 내 쓰기를 내가 바로 못 본다. 검증을 이벤트 전에 해야 한다 |
| Kafka 트랜잭션 | Kafka에서 읽고 Kafka에 쓰는 것을 원자적으로 | 브로커 안에서는 정확히 한 번 | 외부 DB 쓰기에는 해당하지 않는다 |
| 2단계 커밋 | DB와 브로커가 함께 prepare, commit | 원자적 | 대부분의 브로커가 참여하지 못하고, 코디네이터가 죽으면 잠금이 걸린 채 멈춘다 |

자기 이벤트 듣기(listen to yourself)는 "사실을 먼저 브로커에 남기고 내 DB는 소비자 중 하나로 취급하는" 방법이다. 이중 쓰기는 없어지지만, 주문 API가 주문을 넣은 직후 자기 DB에서 그 주문을 못 볼 수 있고, "재고가 있어야 주문을 받는다" 같은 검증을 DB 트랜잭션 안에서 할 수 없다. Kafka 트랜잭션과 정확히 한 번의 범위는 [메시지 전달 보장](/posts/message-delivery-semantics)에서, 2단계 커밋이 막히는 지점은 [분산 트랜잭션과 2단계 커밋](/posts/distributed-transactions-2pc)에서 다룬다.

대부분의 서비스는 폴링 아웃박스로 시작하고, 지연이 문제면 `NOTIFY`를 더하고, 처리량이나 지연이 그것으로도 모자라거나 이미 Kafka Connect를 운영하고 있으면 CDC로 옮긴다.

## 브라우저에도 아웃박스가 있다

같은 모양은 프런트엔드에도 있다. 지하철에서 앱으로 댓글을 달았는데 네트워크가 끊겼다. 화면에는 댓글이 보이는데 서버에는 없다. 오프라인을 지원하는 웹 앱은 요청을 바로 보내지 않고 IndexedDB에 "보낼 요청" 목록으로 먼저 저장한 뒤, 연결이 돌아오면 순서대로 보낸다. 서비스 워커의 Background Sync(크롬 계열에서 지원, 모든 브라우저가 지원하지는 않는다)나 Workbox의 재시도 큐가 이 릴레이 역할을 한다.

React 쪽에서는 TanStack Query가 오프라인일 때 mutation을 멈춰 두었다가 연결되면 다시 실행한다. 캐시를 저장소에 남기는 플러그인을 함께 쓰면 앱을 닫았다 열어도 멈춘 mutation을 이어서 보낼 수 있다. 서버 아웃박스와 똑같은 규칙이 따라온다. 요청마다 클라이언트에서 만든 ID를 붙여 서버가 중복을 거르게 하고, 같은 대상의 요청은 순서대로 보낸다. 화면에 먼저 반영하는 쪽은 [클라이언트 데이터 캐시](/posts/client-data-cache)의 낙관적 업데이트에 있다.

## 아웃박스가 밀린다는 알림이 왔을 때

지표 둘을 늘 보고 있어야 한다. 안 나간 행의 수와 가장 오래된 행의 나이다.

```sql
-- 안 나간 행이 몇 개이고, 가장 오래 기다린 게 얼마나 됐나
SELECT count(*) AS pending,
       now() - min(created_at) AS oldest,
       count(*) FILTER (WHERE attempts > 0) AS retrying
FROM outbox WHERE published_at IS NULL;

-- 어떤 주문, 어떤 에러에서 막혀 있나
SELECT aggregate_id, event_type, attempts, next_attempt_at, last_error
FROM outbox WHERE published_at IS NULL AND attempts > 0
ORDER BY attempts DESC LIMIT 20;
```

`oldest`가 계속 늘고 `retrying`이 0이면 릴레이가 아예 돌지 않는 것이다. 프로세스가 죽었는지, `LISTEN` 연결이 끊긴 채 폴링마저 꺼 두었는지, 담당 번호의 advisory lock을 죽은 연결이 아직 쥐고 있는지 본다(`pg_locks`에서 `locktype = 'advisory'`). `retrying`이 늘면 브로커나 외부 API 쪽 문제이니 `last_error`를 본다.

`pending`은 큰데 `oldest`가 몇 초로 일정하면 릴레이가 따라가고는 있는데 처리량이 모자란 것이다. 배치 크기를 키우거나, 순서가 필요 없는 사건이면 병렬도를 올리고, 순서가 필요하면 담당 번호를 늘린다. 특정 주문 하나에 사건이 몰려 그 주문만 밀리는 경우도 있으니 `aggregate_id`별 개수를 함께 본다.

마지막으로 릴레이 쿼리 자체가 느려지지 않았는지 `EXPLAIN`으로 확인한다. `published_at IS NULL` 부분 인덱스가 없거나, `DELETE`로만 청소해 죽은 튜플이 쌓이면 안 나간 행 몇 개를 찾는 쿼리가 테이블 전체를 훑는다.

## 릴레이까지가 아웃박스다

아웃박스는 테이블 하나와 INSERT 한 줄로 시작하지만, 실제 일은 릴레이에 있다. 신호로 깨워 지연을 줄이고, 대상마다 맨 앞 사건만 보내 순서를 지키고, 실패한 사건에는 횟수와 다음 시각을 적고, 테이블은 파티션째 비운다. 브로커가 아닌 외부 API로 보낼 때는 이벤트 ID를 멱등성 키로 넘긴다. 이 결정들은 "어떤 사건이 순서를 요구하는가"라는 질문 하나에서 대부분 갈린다.

## 면접에서 나올 만한 질문

### 트랜잭셔널 아웃박스는 어떤 문제를 푸나요?

DB 커밋과 브로커 전송을 하나의 트랜잭션으로 묶을 수 없어서 생기는 이중 쓰기 문제를 푼다. 업무 데이터와 보낼 이벤트를 같은 DB 트랜잭션에 쓰니 둘 다 남거나 둘 다 없고, 따로 도는 릴레이가 남은 행을 브로커로 보낸다. 대가로 이벤트는 적어도 한 번 나가니 받는 쪽이 이벤트 ID로 중복을 걸러야 한다.

### 폴링 간격을 줄이지 않고 지연을 줄이려면 어떻게 하나요?

PostgreSQL이라면 쓰는 트랜잭션에서 NOTIFY를 보내고 릴레이가 LISTEN으로 기다리게 한다. NOTIFY는 커밋될 때 전달되고 롤백되면 사라져서, 신호가 오면 행이 이미 보인다. 다만 듣는 연결이 끊긴 동안의 신호는 잃으니 긴 간격의 폴링을 함께 남기고, 트랜잭션 모드 PgBouncer 뒤에서는 LISTEN이 동작하지 않는다는 점을 챙긴다.

### 릴레이를 여러 개 띄우면 무엇이 문제인가요?

SKIP LOCKED로 행이 겹치지는 않지만, 같은 주문의 사건을 서로 다른 릴레이가 나눠 가져 순서가 뒤집힐 수 있다. 순서가 중요하면 대상마다 아직 안 나간 사건 중 가장 앞선 것 하나만 보내고, 주문 ID 해시로 릴레이의 담당을 나눠 한 주문은 늘 한 릴레이가 보내게 한다. 담당은 advisory lock으로 잡아 두면 죽은 릴레이의 몫을 다른 프로세스가 이어받는다.

### 계속 실패하는 이벤트는 어떻게 다루나요?

행에 시도 횟수, 다음 시도 시각, 마지막 에러를 적고 지수 백오프로 미루다가 상한을 넘으면 알린다. 순서가 상관없는 사건이면 별도 테이블로 치우고 나머지를 계속 보내지만, 순서가 중요한 사건이면 치우는 순간 뒤의 사건이 먼저 나가니 그 대상만 멈추고 사람이 고친다. 실패 기록은 보내기와 다른 트랜잭션으로 커밋해야 롤백에 쓸려 가지 않는다.

### 아웃박스 테이블은 어떻게 비우나요?

날짜 단위 파티션으로 만들고 지난 파티션을 떼어 내 버리는 게 가장 가볍다. 예제에서 10만 행 DELETE는 496ms가 걸렸고 테이블 크기도 줄지 않았지만, 파티션 DROP은 7ms였다. 미래 파티션을 미리 만들어 두지 않으면 INSERT가 실패해 주문까지 롤백되니 생성을 자동화하고, CDC를 쓴다면 넣자마자 지워도 된다.

### 아웃박스로 외부 HTTP API를 부를 때 주의할 점은?

릴레이가 같은 요청을 두 번 보낼 수 있으니 이벤트 ID를 멱등성 키로 넘겨 받는 쪽이 중복을 거르게 한다. 멱등성 키를 받지 않는 API라면 두 번 가도 되는 일인지 따지고, 안 되는 일이면 보내기 전에 이미 처리됐는지 조회한다. 외부 API는 오래 실패하는 일이 잦아서 지수 백오프와 재시도 상한이 브로커보다 더 중요하다.

### 아웃박스 대신 CDC나 자기 이벤트 듣기를 고르는 기준은?

CDC는 커밋 순서 그대로 폴링 없이 읽지만 복제 슬롯과 Debezium 같은 부품을 운영해야 하니, 처리량과 지연 요구가 크거나 이미 Kafka Connect를 운영할 때 고른다. 자기 이벤트 듣기는 이중 쓰기를 없애지만 자기 쓰기를 바로 못 보고 DB 트랜잭션 안의 검증을 못 하니, 검증이 단순하고 결과적 일관성을 받아들일 수 있는 흐름에 맞다. 대부분은 폴링 아웃박스에서 시작한다.
