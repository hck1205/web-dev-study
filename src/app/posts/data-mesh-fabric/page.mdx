마케팅 팀이 "가을 세일 캠페인으로 들어온 고객의 첫 주문 금액"을 대시보드로 보고 싶다고 요청을 넣었다. 중앙 데이터 팀의 요청 게시판에는 이미 마흔 건이 쌓여 있고, 예상 착수일은 6주 뒤다. 6주 뒤 담당자가 붙었지만 주문 테이블의 `status` 값 중 `HOLD`가 무슨 뜻인지 몰라 주문 팀에 물어보느라 또 한 주가 갔다. 대시보드가 나온 다음 주, 주문 팀이 컬럼 이름을 바꾸는 배포를 했고 파이프라인이 깨졌다. 데이터 팀은 장애 알림을 받고 나서야 그 배포가 있었다는 걸 알았다.

이 장면에서 느린 사람은 아무도 없다. 데이터를 만드는 팀(주문), 데이터를 쓰는 팀(마케팅) 사이에 중앙 팀 하나가 끼어 있고, 그 팀이 모든 도메인의 뜻을 다 알아야 하는 구조가 느리다. 데이터 메시(data mesh)는 이 구조를 사람과 소유권 쪽에서 바꾸자는 제안이고, 데이터 패브릭(data fabric)은 기술과 메타데이터로 흩어진 저장소를 하나처럼 보이게 하자는 제안이다. 이름이 비슷해서 자주 섞이는데, 둘은 출발점이 다르다.

웨어하우스를 원본·정제·쓰임새 층으로 나누는 기본 설계는 [데이터 웨어하우스 설계](/posts/data-warehouse-architecture)에, 데이터가 생겨서 대시보드에 닿기까지의 전체 흐름은 [데이터 엔지니어링 한 바퀴](/posts/data-engineering-lifecycle)에 있다. 이 글은 그 웨어하우스를 누가 소유하고 어떻게 나누느냐를 본다. 예시 쿼리는 DuckDB 1.5로 직접 돌렸다.

## 사람을 더 뽑아도 줄이 줄지 않는다

중앙 데이터 팀 구조는 처음에는 잘 돌아간다. 원본 DB 몇 개를 웨어하우스로 복사하고, 데이터 엔지니어 두세 명이 정제 테이블과 대시보드를 만든다. 문제는 회사가 커질 때 나타난다. 제품 팀은 열 개, 스무 개로 늘어나는데 그 팀들이 만드는 데이터는 전부 같은 팀을 거친다.

이때 병목은 세 군데서 생긴다.

첫째, 도메인 지식이 중앙에 없다. 주문 팀은 `HOLD`가 결제 승인 대기라는 걸 알지만, 데이터 팀은 물어봐야 안다. 데이터 팀 한 사람이 주문, 정산, 배송, 회원, 광고의 규칙을 다 외울 수는 없다.

둘째, 바꾸는 사람과 깨지는 사람이 다르다. 주문 팀은 자기 서비스 DB를 바꿀 자유가 있고, 그 DB를 읽는 파이프라인이 있는지 모른다. 깨지는 쪽은 데이터 팀이다. 이 비대칭이 있으면 파이프라인은 늘 뒤따라가며 고친다.

셋째, 우선순위를 정하는 사람이 한 곳이다. 마흔 건의 요청 중 무엇이 먼저인지 중앙 팀이 정해야 하는데, 각 요청의 가치는 요청한 팀이 더 잘 안다.

사람을 더 뽑으면 요청 처리량은 늘지만 첫째와 둘째 문제는 그대로다. 새로 온 사람도 `HOLD`의 뜻을 물어봐야 하고, 주문 팀의 배포는 여전히 예고 없이 온다. 2019년 자막 데가니(Zhamak Dehghani)가 마틴 파울러 사이트에 "모놀리식 데이터 레이크를 넘어 분산 데이터 메시로"라는 글을 쓰면서 이 구조를 정면으로 문제 삼았다. 데이터 레이크와 웨어하우스가 기술적으로는 커졌는데 조직 구조는 여전히 중앙 집중형 모놀리스라는 지적이었다.

## 도메인이 데이터를 제품처럼 낸다

데이터 메시는 네 가지 원칙으로 정리된다. 하나씩 떼어 보면 낯설지 않은데, 네 개가 함께 있어야 돌아간다.

첫째, 도메인 소유(domain ownership). 주문 데이터는 주문 팀이 책임진다. 원본 테이블만이 아니라 분석에 쓸 수 있게 다듬은 결과까지다. 도메인은 보통 회사의 업무 경계를 따르고, 이미 마이크로서비스를 나눈 회사라면 그 경계와 거의 겹친다.

둘째, 제품으로서의 데이터(data as a product). 주문 팀이 내놓는 데이터는 "우리 DB 테이블 그냥 읽어 가세요"가 아니라, 쓰는 사람을 고객으로 보고 만든 결과물이다. 이름과 설명이 있고, 신선도 약속이 있고, 바뀔 때 미리 알린다.

셋째, 셀프서비스 데이터 플랫폼(self-serve data platform). 도메인 팀마다 저장소, 스케줄러, 권한, 카탈로그를 처음부터 만들게 하면 비용이 폭발한다. 플랫폼 팀이 "데이터 제품 하나 찍어 내기"를 몇 줄 설정으로 할 수 있게 만든다. 이 팀은 데이터를 만들지 않고 도구를 만든다.

넷째, 연합된 계산형 거버넌스(federated computational governance). 도메인이 제각각 굴러가면 서로 이어 붙일 수가 없다. 그래서 공통 규칙(식별자 형식, 개인정보 처리, 품질 기준)은 도메인 대표와 플랫폼 팀이 함께 정하고(연합), 그 규칙은 회의록이 아니라 코드로 자동 검사한다(계산형).

## 데이터 제품에 붙는 것들

"제품"이라는 말이 막연하게 들리면, 쓰는 사람이 이 데이터를 처음 발견했을 때 누구에게도 묻지 않고 쓸 수 있는지를 기준으로 보면 된다. 데가니는 데이터 제품이 찾을 수 있고(discoverable), 주소가 있고(addressable), 믿을 수 있고(trustworthy), 스스로 설명하고(self-describing), 다른 제품과 이어지고(interoperable), 안전해야(secure) 한다고 썼다.

실제로는 이런 정보가 한 덩어리로 묶인다. 형식은 회사마다 다르고, 아래는 주문 제품을 설명하는 파일을 예로 지어 본 것이다.

```yaml
# data-products/orders/product.yaml (예시 형식)
name: orders
domain: order
owner: order-team@example.com        # 장애와 질문이 가는 곳
description: 결제가 끝난 주문. HOLD(결제 승인 대기)는 포함하지 않는다.
output_ports:
  - type: table
    address: warehouse.order.orders_v1   # 다른 팀은 이 주소만 읽는다
    schema_ref: ./schema/orders_v1.json
slo:
  freshness: "매일 06:00 KST까지 전날 주문 반영"
  completeness: "원본 주문 수와 0.1% 이내 차이"
classification:
  pii: [customer_email]                 # 공통 규칙이 마스킹을 강제한다
deprecation_policy: "깨지는 변경은 새 버전으로 내고 이전 버전을 90일 유지"
```

이 파일에서 중요한 줄은 `description`과 `output_ports`다. 설명에 HOLD를 빼는지 적혀 있으면 앞 장면의 한 주짜리 질문이 사라진다. 출력 포트가 따로 있으면 주문 팀은 서비스 DB를 자유롭게 바꾸면서도 `orders_v1`이라는 약속만 지키면 된다. 서비스 DB는 내부 구현이고, 출력 포트가 공개 API다. 마이크로서비스가 DB를 숨기고 API만 내놓는 것과 같은 생각이다.

출력 포트는 꼭 테이블일 필요가 없다. 같은 제품을 웨어하우스 테이블로, 이벤트 스트림으로, 파일로 낼 수 있다. 원본을 받아 오는 쪽은 입력 포트라고 부르는데, 주문 팀이라면 서비스 DB의 변경을 [CDC](/posts/cdc-change-data-capture)로 받는 것이 흔한 입력 포트다.

## 메시가 사일로로 끝나는 이유

데이터 메시를 도입한 회사가 가장 자주 겪는 실패는 도메인마다 데이터를 잘 만들었는데 서로 합칠 수가 없는 상태다. 각자 자기 책장은 깔끔한데 책장끼리 번호 체계가 다르다. 원래 중앙 팀이 하던 "맞추는 일"이 사라졌기 때문이다.

예를 들어 보자. 주문 도메인과 마케팅 도메인이 각자 낸 제품이다.

```sql
-- 주문 도메인의 orders 제품 (ordered_at은 UTC로 저장)
SELECT * FROM orders;
-- 마케팅 도메인의 campaign_clicks 제품 (clicked_at은 KST로 저장)
SELECT * FROM campaign_clicks;
```

```text
┌──────────┬─────────────┬────────┬─────────────────────┐
│ order_id │ customer_id │ amount │     ordered_at      │
│  int32   │   varchar   │ int32  │      timestamp      │
├──────────┼─────────────┼────────┼─────────────────────┤
│        1 │ C-1001      │  32000 │ 2026-10-20 23:40:00 │
│        2 │ C-1002      │  15000 │ 2026-10-21 09:10:00 │
│        3 │ C-1001      │   8000 │ 2026-10-21 14:05:00 │
└──────────┴─────────────┴────────┴─────────────────────┘

┌───────────┬─────────────┬─────────────────────┐
│ member_no │  campaign   │     clicked_at      │
│   int32   │   varchar   │      timestamp      │
├───────────┼─────────────┼─────────────────────┤
│      1001 │ autumn-sale │ 2026-10-20 14:30:00 │
│      1002 │ autumn-sale │ 2026-10-21 00:05:00 │
└───────────┴─────────────┴─────────────────────┘
```

같은 고객인데 주문 쪽은 `C-1001` 문자열, 마케팅 쪽은 `1001` 정수다. 컬럼 이름도 `customer_id`와 `member_no`로 다르다. 그대로 조인하면 이렇게 된다.

```sql
SELECT c.campaign, sum(o.amount)
FROM campaign_clicks c
JOIN orders o ON o.customer_id = c.member_no   -- 문자열과 정수를 비교한다
GROUP BY 1;
```

```text
ConversionException Conversion Error: Could not convert string 'C-1001' to INT32 when casting from source column customer_id
```

오류가 나면 차라리 낫다. 소비하는 팀이 `'C-' || member_no::VARCHAR`처럼 변환식을 손으로 붙이면 조인은 된다. 그러면 이 변환 규칙이 소비하는 팀마다 하나씩 생긴다. 규칙이 바뀌는 날(예: 고객 번호 체계 개편) 어디가 깨질지 아무도 모른다.

시간대는 더 조용하게 틀린다. 같은 orders 테이블로 "10월 21일 매출"을 구해 봤다.

```sql
SELECT 'UTC 기준' AS basis, sum(amount) AS revenue_1021
FROM orders WHERE ordered_at::DATE = DATE '2026-10-21'
UNION ALL
SELECT 'KST 기준', sum(amount)
FROM orders WHERE (ordered_at + INTERVAL 9 HOUR)::DATE = DATE '2026-10-21';
```

```text
┌──────────┬──────────────┐
│  basis   │ revenue_1021 │
│ varchar  │    int128    │
├──────────┼──────────────┤
│ UTC 기준 │        23000 │
│ KST 기준 │        55000 │
└──────────┴──────────────┘
```

세 건짜리 테이블에서도 두 배가 넘게 차이 난다. UTC 20일 23시 40분 주문은 한국 시각으로 21일 아침 8시 40분이라 KST 기준에서만 21일에 들어간다. 오류 메시지도 없다. 마케팅 팀은 KST로 생각하고 UTC 컬럼을 날짜로 잘랐다가 숫자가 이상하다는 문의를 받게 된다.

그래서 메시에서 상호 운용성(interoperability)은 선택 사항이 아니다. 공통으로 맞출 것을 정하고 코드로 강제해야 한다.

- 공통 식별자: 고객, 상품, 매장 같은 핵심 개체는 회사 전체에서 하나의 키 형식을 쓴다. 도메인 내부에서는 다른 번호를 써도 되지만, 출력 포트에는 공통 키를 함께 낸다.
- 공통 타입과 단위: 시각은 UTC `timestamptz`로 내고 표시할 때만 바꾼다. 금액은 통화 코드와 함께, 최소 단위(원, 센트) 정수로 낸다.
- 스키마 표준: 컬럼 이름 규칙(`_at`은 시각, `_id`는 공통 키), 스키마 정의 형식(JSON Schema, Avro, Protobuf 중 하나)을 정한다.
- 계약: 각 제품의 스키마와 의미, 신선도 약속을 기계가 읽을 수 있는 파일로 두고, 바꿀 때 검사한다. 이 부분은 다음 절에서 본다.

이 목록은 결국 중앙 팀이 하던 일 중 일부다. 데이터 메시는 중앙을 없애는 게 아니라, 중앙이 할 일을 "모든 데이터 만들기"에서 "모두가 지킬 최소 규칙 정하고 자동화하기"로 좁히는 것이다.

계약 검사의 뼈대는 생각보다 단순하다. 읽는 쪽 입장에서 무엇이 깨지는지만 판단하면 된다. 컬럼을 추가하는 건 기존 쿼리를 깨지 않는다. 컬럼을 지우거나 이름을 바꾸면 깨진다. 타입을 바꾸면 깨지는데, `int`를 `bigint`로 넓히는 것처럼 읽는 쪽이 그대로 받을 수 있는 변경은 예외로 둔다. 그리고 NULL이 없던 컬럼이 NULL을 허용하게 바뀌면, NULL이 없다고 믿고 짠 집계가 조용히 틀어지므로 이것도 깨지는 변경으로 본다.

## 규칙은 회의가 아니라 코드로 지킨다

연합 거버넌스라는 말에서 "연합"은 규칙을 정하는 방식이다. 도메인 대표와 플랫폼, 보안 담당이 모여 무엇을 전사 규칙으로 할지 정한다. 핵심은 규칙의 수를 적게 유지하는 것이다. 모든 도메인이 반드시 지켜야 하는 것(공통 키, 개인정보 분류, 소유자 표시)만 전사 규칙으로 두고, 나머지는 도메인이 정한다.

"계산형"은 그 규칙을 지키게 만드는 방식이다. 규칙을 위키에 적어 두면 지켜지지 않는다. 플랫폼이 데이터 제품을 찍어 낼 때, 그리고 제품이 바뀔 때마다 자동으로 검사한다.

```text
# 플랫폼이 제품 배포 전에 도는 정책 검사 예 (형식은 도구마다 다르다)
- owner 필드가 비어 있으면 배포를 막는다
- classification.pii에 적힌 컬럼은 출력 포트에서 마스킹 뷰로만 낸다
- _id로 끝나는 컬럼 중 공통 키 목록에 있는 것은 정해진 형식(C-숫자)인지 표본 검사한다
- 시각 컬럼은 timestamptz여야 한다
- slo.freshness가 없으면 카탈로그에 "실험용"으로만 올린다
```

이런 검사는 OPA(Open Policy Agent) 같은 정책 엔진으로 짜기도 하고, 데이터 계약 형식에 검사 규칙을 넣기도 한다. 데이터 계약을 표준화하려는 시도로 리눅스 재단 산하 Bitol 프로젝트의 ODCS(Open Data Contract Standard) 같은 것이 있지만, 아직 업계 전체가 하나로 모인 형식은 없다. 도구보다 중요한 건 규칙이 배포 경로에 걸려 있어서 우회하기 어려운가다.

## 데이터 패브릭은 메타데이터에서 출발한다

데이터 패브릭은 가트너가 2010년대 후반부터 밀어 온 개념이다. 데이터 메시가 "누가 소유하나"를 묻는다면, 패브릭은 "흩어진 저장소를 어떻게 하나처럼 쓰게 하나"를 묻는다. 조직을 바꾸기보다 그 위에 지능적인 연결 층을 깐다.

패브릭을 이루는 재료는 대략 이렇다.

메타데이터를 모으고 해석한다. 각 저장소의 스키마, 쿼리 로그, 계보, 사용 빈도를 계속 수집하고(가트너는 이걸 "능동 메타데이터"라고 부른다), 어떤 테이블이 자주 함께 조인되는지, 어떤 컬럼이 개인정보처럼 보이는지 추천한다. 데이터 메시의 카탈로그보다 자동화 쪽에 무게가 있다.

개념 사이의 관계를 그래프로 둔다. "고객"이 CRM에서는 `account`, 주문 DB에서는 `customer_id`, 마케팅에서는 `member_no`라는 것을 지식 그래프에 연결해 둔다. 앞 절에서 손으로 붙이던 변환 규칙을 한곳에 모으는 셈이다.

옮기지 않고 읽는다. 데이터 가상화(virtualization)로 Trino 같은 연합 쿼리 엔진이 PostgreSQL, S3, Elasticsearch를 한 SQL로 묶어 읽는다. 복사본을 덜 만들지만, 원본 시스템에 분석 쿼리가 그대로 내려가므로 운영 DB가 느려지는 위험이 있다. 자주 쓰는 결과는 결국 복사해 둔다.

통합을 자동화한다. 새 원본이 등록되면 수집 파이프라인 틀을 만들어 주고, 스키마가 바뀌면 영향받는 곳을 알려 준다.

패브릭은 "패브릭 제품 하나를 사면 끝"인 것처럼 팔리는 경우가 많다. 실제로는 카탈로그, 연합 쿼리, 수집 도구, 정책 엔진을 엮은 구조라 한 제품이 다 해 주지 않는다. 그리고 메타데이터가 아무리 똑똑해도 `HOLD`가 무슨 뜻인지는 주문 팀이 적어 줘야 한다. 이 지점에서 두 접근이 만난다.

## 메시와 패브릭은 고르는 대상이 아니다

두 개념을 나란히 놓으면 이렇다. 표로 볼 만한 비교라 표로 둔다.

| | 데이터 메시 | 데이터 패브릭 |
|---|---|---|
| 출발점 | 조직과 소유권 | 기술과 메타데이터 |
| 데이터는 누가 만드나 | 각 도메인 팀 | 중앙 팀(그대로일 수 있음) |
| 흩어진 데이터를 잇는 방법 | 공통 규칙과 계약 | 지식 그래프, 가상화, 자동 통합 |
| 바뀌는 것 | 팀의 책임과 역할 | 도구와 플랫폼 |
| 실패하는 모습 | 도메인끼리 못 합치는 사일로 | 메타데이터는 많은데 뜻을 아무도 모름 |

둘은 서로 배타적이지 않다. 패브릭이 내세우는 카탈로그, 계보 자동 수집, 정책 엔진은 메시의 셀프서비스 플랫폼이 갖춰야 할 것과 거의 같다. 그래서 "도메인이 데이터를 소유하고(메시), 플랫폼은 메타데이터 자동화로 그걸 하나처럼 찾고 잇게 해 준다(패브릭의 기술)"는 조합이 현실적인 답이 되는 경우가 많다. 면접에서 "둘 중 무엇을 고르겠나"라는 질문을 받으면 이 관계부터 짚는 게 좋다.

[데이터 웨어하우스 설계](/posts/data-warehouse-architecture)에서 본 데이터 허브나 중앙 웨어하우스도 사라지지 않는다. 메시를 하는 회사도 저장소는 하나의 클라우드 웨어하우스나 레이크하우스를 쓰는 경우가 많다. 메시는 저장소를 쪼개라는 말이 아니라, 그 안의 스키마와 테이블의 소유자를 도메인으로 나누라는 말이다.

## 아직 메시가 필요 없는 회사

데이터 메시는 비싸다. 도메인 팀마다 데이터를 다룰 사람이 있어야 하고, 플랫폼 팀이 따로 있어야 하고, 공통 규칙을 정하고 지키는 데 시간이 든다. 이 비용보다 중앙 팀 병목의 비용이 커야 의미가 있다.

메시가 아직 맞지 않는 신호는 이렇다.

- 데이터 엔지니어가 다섯 명 안팎이고, 제품 도메인도 몇 개 되지 않는다. 이 규모에서는 중앙 팀이 모든 도메인을 아는 게 가능하다.
- 도메인 팀에 데이터를 맡을 사람이 없다. 주문 팀이 "데이터 제품 소유"를 받아도 할 사람이 없으면, 이름만 바뀐 방치가 된다.
- 데이터를 쓰는 곳이 대시보드 몇 개뿐이다. 소비자가 적으면 제품으로 만들 이유가 약하다.
- 플랫폼이 없다. 셀프서비스 없이 도메인에 책임만 넘기면 팀마다 다른 도구로 같은 바퀴를 다시 만든다.

반대로 넘어갈 때가 됐다는 신호도 숫자로 보인다. 요청 대기 시간이 몇 주 단위로 늘고, 중앙 팀 시간의 상당 부분이 도메인 팀에 뜻을 물어보는 데 쓰이고, 원본 스키마 변경 때문에 파이프라인이 매주 깨진다면 구조를 의심할 때다. 이때도 한 번에 바꾸지 않는다. 데이터를 가장 많이 만들고 가장 많이 깨지는 도메인 하나를 골라 첫 데이터 제품을 내 보고, 플랫폼이 그 과정에서 반복된 일을 도구로 만든다.

작은 회사가 메시에서 빌려 올 만한 것도 있다. 테이블마다 소유 팀을 적고, 원본 스키마 변경을 CI에서 검사하고, 출력 테이블과 내부 테이블을 구분하는 것. 이 세 가지는 중앙 팀 구조에서도 바로 효과가 있다.

## 첫 데이터 제품 하나를 내는 순서

도메인 하나를 골랐다면 순서는 대략 이렇게 간다. 가장 먼저 할 일은 지금 그 도메인의 테이블을 누가 읽는지 세는 것이다. 소비자를 모르면 출력 포트를 무엇으로 낼지도, 이전 기간을 얼마로 잡을지도 정할 수 없다.

클라우드 웨어하우스는 쿼리 기록에 읽은 테이블을 남긴다. BigQuery라면 `INFORMATION_SCHEMA.JOBS` 뷰의 `referenced_tables`로 지난 30일 동안 주문 데이터셋을 읽은 사람과 횟수를 볼 수 있다.

```sql
-- BigQuery: 지난 30일 동안 order 데이터셋의 테이블을 읽은 사용자와 쿼리 수
SELECT
  t.table_id,
  j.user_email,
  COUNT(*) AS queries
FROM `region-asia-northeast3`.INFORMATION_SCHEMA.JOBS AS j,
  UNNEST(j.referenced_tables) AS t
WHERE j.creation_time > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
  AND t.dataset_id = 'order'
  AND j.job_type = 'QUERY'
GROUP BY 1, 2
ORDER BY queries DESC;
```

리전 이름과 권한(프로젝트의 작업 목록을 볼 수 있는 역할)은 환경에 맞게 바꾼다. Snowflake는 `ACCOUNT_USAGE.ACCESS_HISTORY`, PostgreSQL 기반이라면 `pg_stat_statements`나 접속 로그가 비슷한 역할을 한다. 결과에서 사람 이메일보다 서비스 계정이 많이 보이면, 그 계정 뒤에 있는 파이프라인과 대시보드가 진짜 소비자다.

그다음은 이렇게 간다.

1. 많이 읽히는 테이블 두세 개를 첫 출력 포트 후보로 고른다. 전부를 한 번에 제품으로 만들지 않는다.
2. 그 테이블의 컬럼 뜻, 제외하는 행(HOLD 같은), 갱신 시각을 주문 팀이 직접 설명 파일에 적는다. 이 작업이 생각보다 오래 걸리고, 여기서 처음 발견되는 오해가 많다.
3. 공통 키와 시각 타입을 규칙에 맞춘 뷰(`orders_v1`)를 만들고, 기존 소비자는 그대로 둔 채 새 소비자부터 이 뷰를 쓰게 한다.
4. 스키마 계약 파일을 저장소에 두고 CI에 검사를 건다. 이 순간부터 주문 팀의 변경이 먼저 멈춘다.
5. 기존 소비자를 하나씩 옮기고, 옛 테이블 직접 접근 권한을 거둔다.

이 과정에서 플랫폼 팀은 2번에서 5번까지 반복된 손작업을 메모해 둔다. 두 번째 도메인이 같은 일을 할 때 그게 도구가 된다.

## 도입하다 흔히 막히는 곳

메시를 시작한 회사에서 반복해서 보이는 실수가 있다.

이름만 바꾸는 경우가 가장 흔하다. 중앙 데이터 팀을 "데이터 플랫폼 팀"으로 바꾸고 도메인 팀에 "이제 데이터는 여러분 것"이라고 공지한다. 도메인 팀의 목표(OKR)에 데이터 제품이 없으면 아무도 하지 않는다. 소유권은 평가와 일정에 들어가야 진짜가 된다.

플랫폼부터 완벽하게 만드는 경우도 있다. 1년 동안 플랫폼을 짓고 나서 첫 데이터 제품을 받으려 하면, 실제로 필요한 기능과 만든 기능이 어긋난다. 첫 제품 한두 개와 플랫폼을 함께 키우는 편이 낫다.

거버넌스가 회의가 되는 경우도 있다. 모든 스키마 변경을 위원회 승인으로 받으면 병목이 중앙 팀에서 위원회로 옮겨 갈 뿐이다. 승인은 자동 검사가 하고, 사람은 규칙 자체를 바꿀 때만 모인다.

출력 포트 없이 내부 테이블을 열어 주는 경우도 있다. 도메인의 서비스 DB 복제본을 그대로 공개하면 내부 구조가 곧 계약이 된다. 주문 팀은 다시 DB를 바꿀 때마다 누군가를 깨뜨린다.

## 마이크로서비스와 닮은 이유

데이터 메시는 마이크로서비스 아키텍처가 애플리케이션에 한 일을 데이터에 하려는 시도다. 그래서 장점과 함께 단점도 그대로 닮았다.

닮은 점부터 보면, 둘 다 도메인 경계로 자른다. 어디서 자를지는 [DDD 바운디드 컨텍스트](/posts/ddd-bounded-context)에서 말하는 "같은 말이 같은 뜻으로 쓰이는 범위"가 기준이 된다. 주문 팀의 "주문"과 정산 팀의 "주문"이 다른 뜻이라면 다른 제품이다. 둘 다 내부를 숨기고 약속된 인터페이스(API, 출력 포트)만 낸다. 둘 다 팀이 독립적으로 배포하게 하고, 콘웨이의 법칙(시스템 구조는 조직의 소통 구조를 닮는다)을 거꾸로 이용해 원하는 구조에 맞게 팀을 짠다.

단점도 같다. 분산하면 맞추는 비용이 생긴다. 마이크로서비스가 분산 트랜잭션과 서비스 간 호출 실패를 떠안듯, 메시는 도메인 간 식별자 정합성과 버전 관리를 떠안는다. 작은 조직에 마이크로서비스가 과하듯 메시도 과하다. 그리고 경계를 잘못 자르면 둘 다 고치기 어렵다. 서비스 경계를 고르는 구체적인 순서는 [마이크로서비스 분해](/posts/microservices-decomposition)에 있다.

다른 점도 하나 있다. 서비스는 요청 하나를 처리하는 단위라 경계 너머 호출을 줄이면 되지만, 분석은 본래 여러 도메인을 합쳐 보는 일이다. "캠페인별 첫 주문 금액"은 마케팅과 주문을 반드시 합친다. 그래서 메시에서는 경계를 넘어 합치는 일이 예외가 아니라 일상이고, 그만큼 상호 운용성 규칙의 무게가 마이크로서비스보다 크다.

## 다시 6주짜리 대시보드로

처음 장면을 메시로 다시 보면, 마케팅 팀은 카탈로그에서 주문 제품을 찾고 설명에서 HOLD가 빠져 있다는 걸 읽은 뒤 공통 고객 키로 자기 클릭 데이터와 합친다. 주문 팀이 컬럼 이름을 바꾸려 하면 그 팀의 CI가 먼저 멈추고 새 버전을 내게 된다. 중앙 팀은 이 과정이 몇 줄 설정으로 되도록 플랫폼을 만든다. 데이터 메시는 소유권을 데이터를 아는 사람에게 돌려주는 대신, 공통 규칙이 없으면 사일로가 된다는 비용을 함께 준다. 데이터 패브릭은 그 규칙과 연결을 메타데이터 자동화로 돕는 기술 묶음이다.

## 면접에서 나올 만한 질문

### 데이터 메시란 무엇이고 왜 나왔나?

도메인 팀이 자기 데이터를 분석용 제품으로 직접 소유하고 내놓게 하는 조직·아키텍처 방식이다. 중앙 데이터 팀이 모든 도메인의 데이터를 받아 가공하는 구조에서는 도메인 지식이 중앙에 없고, 원본을 바꾸는 팀과 깨지는 팀이 달라 병목이 생긴다. 원칙은 도메인 소유, 제품으로서의 데이터, 셀프서비스 플랫폼, 연합된 계산형 거버넌스 네 가지다.

### 데이터 메시의 단점은 무엇인가?

도메인마다 데이터를 다룰 사람과 별도 플랫폼 팀이 필요해서 비싸다. 공통 식별자, 타입, 계약 같은 상호 운용성 규칙이 없으면 도메인끼리 합칠 수 없는 사일로가 된다. 도메인 팀의 목표에 데이터 제품이 들어가지 않으면 이름만 바뀐 방치가 되기 쉽고, 작은 조직에서는 중앙 팀 하나가 더 효율적이다.

### 메시가 사일로가 되지 않게 하려면 무엇을 맞춰야 하나?

고객·상품 같은 핵심 개체의 공통 키, 시각(UTC)과 금액 단위 같은 타입 규칙, 컬럼 이름과 스키마 정의 형식, 그리고 출력 포트의 계약이다. 규칙은 적게 정하되 플랫폼이 배포 경로에서 자동으로 검사해야 한다. 예를 들어 고객 키가 한쪽은 문자열 C-1001, 다른 쪽은 정수 1001이면 조인이 깨지거나 소비자마다 변환 규칙이 따로 생긴다.

### 데이터 제품은 일반 테이블과 무엇이 다른가?

소유자, 설명, 주소가 있는 출력 포트, 신선도 같은 SLO, 스키마 계약, 폐기 정책이 함께 붙어 있어서 쓰는 사람이 묻지 않고 쓸 수 있다. 서비스 내부 DB는 숨기고 출력 포트만 공개하므로 도메인 팀은 내부를 자유롭게 바꾸면서 약속만 지키면 된다. 깨지는 변경은 새 버전으로 내고 이전 버전을 일정 기간 유지한다.

### 데이터 메시와 데이터 패브릭은 어떻게 다른가?

메시는 조직과 소유권에서 출발해 도메인이 데이터를 만들게 하고, 패브릭은 메타데이터 수집, 지식 그래프, 데이터 가상화, 통합 자동화로 흩어진 저장소를 하나처럼 쓰게 하는 기술 접근이다. 둘은 배타적이지 않아서 패브릭의 카탈로그·계보·정책 자동화가 메시의 셀프서비스 플랫폼 역할을 하는 조합이 흔하다.

### 데이터 메시와 마이크로서비스의 닮은 점은?

둘 다 도메인 경계로 시스템과 팀을 자르고, 내부를 숨긴 채 약속된 인터페이스만 내며, 팀이 독립적으로 바꾸게 한다. 그래서 단점도 닮아서 분산된 것을 맞추는 비용이 생기고 작은 조직에는 과하다. 다만 분석은 원래 여러 도메인을 합치는 일이라 메시에서는 경계를 넘는 조인이 일상이고, 그만큼 상호 운용성 규칙이 더 중요하다.

### 우리 회사에 데이터 메시를 도입할지 어떻게 판단하나?

요청 대기 시간, 중앙 팀이 도메인 뜻을 물어보는 데 쓰는 시간, 원본 스키마 변경으로 깨지는 빈도를 먼저 본다. 이게 크고 도메인 팀에 데이터를 맡을 사람과 플랫폼을 만들 여력이 있으면 가장 많이 깨지는 도메인 하나로 시작한다. 그렇지 않으면 테이블별 소유자 표시, 스키마 변경 CI 검사, 출력 테이블과 내부 테이블 구분만 먼저 들여온다.
