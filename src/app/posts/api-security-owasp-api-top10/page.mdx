프런트엔드 개발자가 브라우저 개발자 도구의 네트워크 탭을 열어 두고 작업하다 우연히 발견한다. 내 주문 상세를 부르는 요청이 `GET /api/orders/18822`였다. 주소창의 `18822`를 `18821`로 바꿔 다시 보냈더니, 남의 주문이 그대로 내려왔다. 이름, 주소, 전화번호까지. 로그인은 정상이었고 토큰도 내 것이었다. 서버는 "너 맞아?"는 물었지만 "이 주문이 네 거야?"는 묻지 않았다.

이게 API 보안에서 가장 흔하고 가장 비싼 실수다. 웹 OWASP Top 10이 주입·XSS 같은 "입력을 믿은 죄"에 무게를 둔다면([OWASP Top 10 지도](/posts/owasp-top-10-map) 참고), API 쪽은 "인가를 빠뜨린 죄"가 목록 위쪽을 차지한다. 화면이 없으니 숨길 데가 없고, 엔드포인트 하나하나가 그대로 노출돼 있기 때문이다. 이 글은 OWASP API Security Top 10(2023년 판)을 실제 요청 위에 얹어, 각 항목이 어떤 요청으로 터지고 무엇으로 막는지 본다.

인증과 인가의 차이, 객체 수준 인가(BOLA)의 기본 개념은 [인증과 인가 글](/posts/authn-vs-authz)에, 서버를 시켜 내부 주소를 부르게 하는 SSRF의 상세는 [SSRF 글](/posts/ssrf)에 있다. 여기서는 그것들이 API 표면 위에서 어떻게 묶이는지, 그리고 아직 다루지 않은 항목들을 중심으로 본다.

## 번호만 대면 남의 것이 나온다 (BOLA)

API1:2023, 객체 수준 인가 실패(Broken Object Level Authorization). 위 주문 사고가 정확히 이것이다. URL이나 본문에 들어간 `id`를 서버가 그대로 믿고, 그 객체가 요청한 사람 것인지 확인하지 않는다. API 보안 사고의 가장 큰 덩어리가 여기 모인다.

아래 그림에서 다음을 누르면, 토큰은 멀쩡한데 인가만 빠진 요청이 어떻게 남의 데이터를 꺼내는지 볼 수 있다.

막는 법은 단순하다. 조회·수정·삭제 쿼리에 항상 주인 조건을 붙인다. "이 id의 행"이 아니라 "이 사용자의, 이 id의 행"을 찾는다.

```sql
-- 취약: id만 믿는다
SELECT * FROM orders WHERE id = 18821;

-- 안전: 토큰에서 꺼낸 사용자 id를 조건에 함께 넣는다
SELECT * FROM orders WHERE id = 18821 AND user_id = $currentUserId;
```

인가 판단은 데이터 접근 지점에 못 박아야 한다. 컨트롤러 맨 앞에서 한 번 검사하고 끝내면, 새 엔드포인트를 추가할 때마다 빠뜨린다. 추측 가능한 연속 숫자 id 대신 UUID를 쓰면 무작위 대입은 어려워지지만, 그건 보완책일 뿐 인가를 대신하지 못한다. id를 알아내는 경로(공유 링크, 로그, Referer)는 늘 있다.

아래에서 직접 고쳐 볼 수 있다. `authorizeRead`는 사용자가 특정 리소스를 읽어도 되는지 판단하는 순수 함수다. 지금은 무조건 허용한다. 주인 검사와 역할 기반 예외(관리자는 전부 볼 수 있음)를 넣어 보자.

## 보낸 적 없는 필드가 저장된다 (대량 할당)

API3:2023, 객체 속성 수준 인가 실패. 이건 두 얼굴을 가진다. 하나는 **과다 노출**, 응답에 필요 이상의 필드를 담아 내려보내는 것이다. 사용자 프로필 응답에 `passwordHash`, `isAdmin`, 내부 메모가 섞여 나간다. 화면이 안 쓴다고 안전한 게 아니다. 응답 JSON은 누구나 본다.

다른 하나는 **대량 할당(mass assignment)**이다. 받은 JSON을 객체에 통째로 복사하는 편한 코드가 범인이다.

```js
// 취약: 요청 본문을 그대로 덮어쓴다
const user = await User.findById(req.userId);
Object.assign(user, req.body);  // {name, email} 만 올 줄 알았다
await user.save();
```

사용자가 이름만 바꾸는 화면이지만, 요청 본문에 `{"name":"...","role":"admin","emailVerified":true}`를 끼워 보내면 서버가 그대로 저장한다. 화면에 없는 필드라고 서버가 막아 주지는 않는다. 아래에서 요청 본문의 각 조각을 눌러 보면, 겉보기엔 평범한 수정 요청에 어떤 위험한 필드가 섞일 수 있는지 보인다.

막는 법은 "받을 필드를 명시적으로 고르는 것"이다. 들어온 것을 다 쓰지 말고, 허용 목록(allowlist)만 뽑아 쓴다.

```js
// 안전: 받을 필드를 직접 고른다
const { name, bio } = req.body;
await User.update(req.userId, { name, bio });
```

응답도 같다. DB 엔티티를 그대로 `res.json(user)` 하지 말고, 내보낼 필드만 담은 전용 응답 형태(DTO)로 매핑한다. TypeScript를 써도 `any`로 받으면 소용없다. 입력 스키마(zod 같은 검증기)로 모양을 먼저 좁히고, 거기 없는 키는 버린다.

## 한 번에 얼마나 요청할 수 있나 (자원 소비 제한 없음)

API4:2023, 무제한 자원 소비. 로그인 시도에 횟수 제한이 없으면 무차별 대입이 되고([크리덴셜 스터핑](/posts/owasp-top-10-map) 쪽과 이어진다), 목록 API에 `?limit=1000000`을 막지 않으면 DB가 통째로 메모리에 올라간다. GraphQL이면 중첩 질의 하나로 서버를 무릎 꿇릴 수 있다. 이미지 변환·PDF 생성처럼 비싼 작업은 요청 몇 개로 CPU를 다 먹는다.

막는 수단은 층을 이룬다. [레이트 리밋 알고리즘](/posts/rate-limiting-in-practice)으로 분당 요청 수를 제한하고, 페이지네이션의 `limit`에 상한을 두고(기본값과 최댓값을 함께 정한다), 요청 본문 크기·중첩 깊이·실행 시간에 한계를 건다. 비용이 큰 작업은 큐로 넘겨 동시 실행 수를 제어한다. OWASP가 "DoS"가 아니라 "무제한 소비"라고 이름 붙인 이유는, 악의 없는 클라이언트의 버그 한 줄로도 같은 일이 벌어지기 때문이다.

## 관리자용 문이 열려 있다 (기능 수준 인가)

API5:2023, 기능 수준 인가 실패(Broken Function Level Authorization). BOLA가 "남의 데이터"라면 이건 "남의 기능"이다. 화면에서는 관리자만 삭제 버튼을 보지만, `DELETE /api/admin/users/42`는 일반 사용자 토큰으로도 그대로 동작한다. 버튼을 숨긴 것과 기능을 막은 것은 전혀 다르다.

흔한 변형이 "추측 가능한 관리자 경로"다. `/api/users/me`가 있으니 `/api/admin/users`도 있겠지, 하는 식으로 찾는다. HTTP 메서드만 바꿔 보는 경우도 많다. `GET`은 막혀 있는데 `POST`나 `PUT`은 안 막혀 있다. 역할 검사를 엔드포인트마다 손으로 다는 대신, 기본을 "거부"로 두고 공개할 것만 명시적으로 여는 구조가 안전하다.

## 사람은 막았는데 흐름을 막지 않았다 (업무 흐름 남용)

API6:2023, 민감한 업무 흐름에 대한 무제한 접근. 기술적으로는 아무 취약점이 없는데도 터지는 종류다. 콘서트 티켓 예매 API가 정상 동작하지만, 봇이 1초에 수백 건을 예약해 재고를 싹쓸이한 뒤 되판다. 할인 쿠폰 발급 API가 멀쩡하지만, 계정을 수천 개 만들어 쿠폰을 쓸어 담는다.

여기서 막아야 할 것은 "공격"이 아니라 "사람이라면 하지 않을 속도와 규모"다. 봇 탐지, 기기 지문, 결제 전 단계에서의 챌린지(CAPTCHA), 계정당·IP당 수량 제한, 의심스러운 패턴에 대한 수동 검토 큐가 수단이다. 이 항목이 Top 10에 들어온 것은, 보안을 "코드의 버그"로만 보면 놓치는 영역이 있다는 신호다.

## 서버에게 심부름을 시킨다 (SSRF)

API7:2023, 서버 측 요청 위조. 사용자가 준 URL을 서버가 그대로 불러오는 모든 곳이 후보다. 웹훅 등록, 이미지 URL로 썸네일 만들기, "이 링크 미리보기" 기능. 공격자는 `http://169.254.169.254/...` 같은 내부 주소를 넣어 클라우드 메타데이터나 내부 서비스를 끄집어낸다. 상세한 재현과 방어(IMDSv2, 해석한 IP 검사, egress 정책)는 [SSRF 글](/posts/ssrf)에 있다. API 관점에서 기억할 것은 하나다. URL을 받는 필드는 전부 SSRF 입구다.

## 기본값 그대로 열려 있다 (잘못된 설정)

API8:2023, 보안 설정 오류. 디버그 모드가 운영에 켜져 스택 트레이스가 그대로 나가고, CORS가 `Access-Control-Allow-Origin: *`에 credentials까지 허용돼 있고([CORS 글](/posts/cors) 참고), 안 쓰는 HTTP 메서드(`TRACE`, `PUT`)가 열려 있고, 에러 응답이 DB 종류와 버전을 알려 준다. 하나하나는 사소하지만 공격자에게는 지도가 된다.

[웹 보안 헤더](/posts/web-security-headers)를 빠짐없이 넣고, 에러 응답은 내부 정보를 숨긴 일반 메시지로 통일하고, 기본 계정·기본 비밀번호를 지우고, 설정을 코드로 관리해(IaC) 운영과 개발의 차이를 없앤다. 수동으로 맞추면 반드시 어긋난다.

## 오래된 문이 아직 살아 있다 (재고 관리 실패)

API9:2023, 부적절한 재고 관리(Improper Inventory Management). `/api/v2`를 내면서 `/api/v1`을 끄지 않으면, 옛 버전에만 있던 취약점이 그대로 공격 표면으로 남는다. 테스트용으로 띄운 `staging.api.example.com`이 인증 없이 열려 있거나, 문서에 없는 "그림자 API"가 떠다닌다. "우리가 무슨 엔드포인트를 몇 개나 운영 중인지" 목록이 없으면 지킬 수도 없다.

대응은 지루하지만 확실하다. 모든 버전·환경·엔드포인트의 목록을 자동으로 수집하고(게이트웨이 로그, OpenAPI 스펙), 구버전에 폐기 일정(deprecation)을 붙여 실제로 끄고, 운영과 테스트 환경을 네트워크로 분리한다. [API 버전 관리](/posts/api-versioning)는 "어떻게 바꾸나"를 다루고, 여기서는 "옛것을 어떻게 끄나"가 핵심이다.

## 외부 API를 너무 믿는다 (안전하지 않은 API 사용)

API10:2023, 안전하지 않은 API 소비(Unsafe Consumption of APIs). 내 서버가 서드파티 API를 호출할 때, 그쪽 응답을 내 사용자 입력처럼 의심 없이 쓰는 것이다. 결제 대행사가 돌려준 JSON을 검증 없이 DB에 넣고, 외부 API가 준 리다이렉트 URL을 그대로 따라가고(또 SSRF), 외부 응답의 크기·시간 제한을 안 둬서 그쪽이 느려지면 내 서비스도 멈춘다.

외부도 신뢰 경계 밖이다. 응답 스키마를 검증하고, 타임아웃과 크기 제한을 걸고, TLS 인증서를 확인하고([전송 구간 암호화](/posts/encryption-in-transit) 참고), 리다이렉트는 따라가지 않거나 허용 목록으로 제한한다.

## REST와 GraphQL에서 달라지는 공격 표면

같은 취약점도 API 스타일에 따라 다르게 터진다. REST는 엔드포인트가 자원별로 나뉘어 있어, BOLA는 경로의 id를 바꾸는 식으로 드러난다(`/orders/18821`). 반면 [GraphQL](/posts/graphql-schema-type-system)은 질의 하나로 여러 자원을 한 번에 가져오고 중첩할 수 있어, 자원 소비 문제(API4)가 더 쉽게 터진다. 깊게 중첩한 질의 하나로 서버가 수천 건을 조인하게 만들 수 있다. 그래서 GraphQL에서는 질의 깊이 제한, 복잡도 점수 제한, 가져올 항목 수 제한이 레이트 리밋만큼 중요하다.

과다 노출도 양쪽이 다르다. REST는 서버가 정한 필드를 돌려주니, 응답에 민감 필드를 담지 않도록 서버에서 DTO로 거른다. GraphQL은 클라이언트가 필드를 고르니, 스키마에 노출된 필드는 누구나 요청할 수 있다. `passwordHash` 필드가 스키마에 있으면 화면이 안 써도 공격자는 요청한다. 그래서 GraphQL에서는 스키마 수준에서 민감 필드를 아예 빼거나, 필드별 인가(resolver에서 권한 확인)를 건다. 인가를 "엔드포인트 하나"가 아니라 "필드 하나하나"에 걸어야 한다는 점이 REST와 가장 다르다.

## 응답에 무엇이 담겼는지 눈으로 본다

과다 노출은 코드 리뷰에서 가장 자주 놓치는 항목이다. 응답 JSON을 실제로 펼쳐 놓고 "이 필드가 밖에 나가도 되나"를 하나씩 물어야 보인다. 아래는 사용자 프로필 응답인데, 화면은 이름과 자기소개만 쓰지만 서버가 엔티티를 통째로 내보낸 경우다.

해결은 엔티티를 그대로 직렬화하지 않는 것이다. 내보낼 필드만 담은 응답 전용 객체로 매핑한다.

```ts
// 취약: 엔티티를 그대로 내보낸다 (숨은 필드까지 함께)
res.json(user);

// 안전: 내보낼 필드만 담은 응답 형태로 매핑한다
res.json({ id: user.id, name: user.name, bio: user.bio });
```

이 매핑을 타입으로 강제하면 실수가 준다. 응답 타입에 `passwordHash`가 아예 없게 정의하면, 거기에 넣으려다 컴파일에서 걸린다. 자동 직렬화에 기대지 말고 "내보낼 것을 적는" 방향이 안전하다.

## 현장에서 이 목록을 쓰는 순간

사고가 났을 때 가장 먼저 보는 건 액세스 로그다. 한 토큰이 짧은 시간에 연속된 id를 훑고 다녔다면 BOLA 긁기다(`/orders/18821`, `/18822`, `/18823`…). 같은 엔드포인트에 404가 아니라 200이 줄줄이 떴다면 이미 데이터가 나갔다는 뜻이다. 그래서 인가 실패는 403으로, 존재하지 않는 리소스는 404로 명확히 구분해 로그에 남기는 게 사후 추적의 출발점이다.

새 엔드포인트를 리뷰할 때 질문은 세 개로 압축된다. "이 리소스가 요청자 것인지 확인하나(BOLA)", "받는 필드와 내보내는 필드를 명시했나(과다 노출·대량 할당)", "이 기능을 쓸 권한을 확인하나(기능 수준 인가)". 이 세 질문만 코드 리뷰 체크리스트에 박아 둬도 Top 10의 절반이 막힌다. 나머지는 설정과 운영의 문제라 배포 파이프라인과 게이트웨이에서 잡는다.

자동 스캐너는 BOLA를 잘 못 잡는다. 어떤 id가 누구 것인지 모르기 때문이다. 결국 사람이 데이터 모델을 알아야 찾을 수 있고, 그래서 API 보안은 도구보다 리뷰 문화에 더 기댄다.

## 면접에서 나올 만한 질문

### 웹 OWASP Top 10과 API Top 10은 왜 목록이 다른가?

웹 목록은 브라우저가 렌더링하는 애플리케이션을 전제로 해서 XSS, 주입처럼 "입력을 믿은 결과"가 위쪽에 온다. API는 화면이 없고 엔드포인트가 그대로 노출돼, 인가를 빠뜨리는 실수가 가장 치명적이다. 그래서 API 목록은 BOLA(객체 수준 인가), 기능 수준 인가, 속성 수준 인가처럼 인가 실패가 1·3·5위를 차지한다. 둘은 경쟁 관계가 아니라, 같은 서비스의 다른 표면을 덮는 보완 관계다.

### BOLA(IDOR)를 어떻게 막나?

조회·수정·삭제 쿼리에 항상 "요청자 소유" 조건을 함께 건다. id만 보고 찾는 게 아니라 "이 사용자의, 이 id의 행"을 찾는다. 검사를 컨트롤러 입구 한 곳에 두지 말고 데이터 접근 지점에 못 박아야 새 엔드포인트에서 빠뜨리지 않는다. UUID로 id를 추측 불가능하게 만드는 건 보완책이지 인가의 대체가 아니다. id는 로그·공유 링크·Referer로 늘 샌다.

### 대량 할당(mass assignment)은 왜 생기고 어떻게 막나?

받은 요청 본문을 객체에 통째로 복사하는 편한 코드(`Object.assign(user, req.body)`)가 원인이다. 화면에 입력칸이 없어도 `role`, `isAdmin` 같은 필드를 본문에 끼워 보내면 서버가 저장한다. 막으려면 들어온 것을 다 쓰지 말고 허용할 필드만 명시적으로 뽑아 쓰고, 입력 스키마 검증으로 모양을 먼저 좁힌다. 응답도 대칭이다. 엔티티를 그대로 내보내지 말고 내보낼 필드만 담은 DTO로 매핑해 과다 노출을 막는다.

### 기능 수준 인가(API5)와 객체 수준 인가(API1·BOLA)는 어떻게 다른가?

BOLA는 "이 데이터가 네 것이냐"의 문제고, 기능 수준 인가는 "이 작업을 할 권한이 있느냐"의 문제다. 전자는 일반 사용자가 남의 주문을 보는 것, 후자는 일반 사용자가 관리자용 `DELETE /admin/...`을 호출하는 것이다. 화면에서 버튼을 숨기는 것은 둘 다 막지 못한다. 기능 쪽은 기본을 거부로 두고 공개할 엔드포인트만 여는 구조가, 데이터 쪽은 쿼리에 소유 조건을 거는 것이 해법이다.

### "민감한 업무 흐름 남용"(API6)은 취약점이 없는데 왜 보안 문제인가?

코드에 버그가 없어도 정상 기능을 비정상적인 속도·규모로 쓰면 피해가 난다. 티켓을 봇이 쓸어 담아 되팔거나, 쿠폰을 계정 수천 개로 긁는 경우다. 막아야 할 대상이 "공격 페이로드"가 아니라 "사람이라면 하지 않을 패턴"이라서, 봇 탐지·수량 제한·결제 전 챌린지 같은 수단이 필요하다. 보안을 코드 버그로만 보면 놓치는 영역이라 Top 10에 따로 들어왔다.

### 옛 API 버전(`/v1`)을 안 끄면 왜 위험한가?

`/v2`를 내도 `/v1`을 살려 두면, 구버전에만 있는 취약점과 느슨한 검증이 그대로 공격 표면으로 남는다. 보통 신버전만 패치하고 구버전은 방치하기 때문에 오히려 더 약하다. 여기에 문서에 없는 테스트 환경·그림자 API까지 더해지면, "우리가 무엇을 운영 중인지"조차 모르는 상태가 된다. 그래서 재고 관리(API9)는 엔드포인트 목록 자동 수집, 폐기 일정을 붙여 실제로 끄기, 환경 분리로 대응한다.

### 외부 API 응답을 왜 검증해야 하나?

내 서버가 호출하는 서드파티도 신뢰 경계 밖이다. 그쪽이 침해당했거나 응답 형식을 바꾸면, 검증 없이 쓴 내 서버가 함께 무너진다. 외부가 준 URL을 따라가면 SSRF가 되고, 응답에 크기·시간 제한이 없으면 그쪽이 느려질 때 내 서비스도 멈춘다. 그래서 외부 응답도 스키마를 검증하고, 타임아웃·크기 제한을 걸고, 리다이렉트는 허용 목록으로 묶는다.
