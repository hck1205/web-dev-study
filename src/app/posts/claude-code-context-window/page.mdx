세션 초반에 "테스트는 `pnpm test:unit`으로만 돌려라"라고 말해 뒀다. 파일을 수십 개 읽히고 로그를 몇 번 붙여 넣으며 두 시간쯤 일하자, Claude Code가 아무렇지 않게 `pnpm test` 전체를 돌린다. 방금 고친 함수의 이름을 다시 틀리기도 한다. 모델이 갑자기 나빠진 게 아니다. 처음 한 말이 들어 있던 대화가 요약으로 바뀌었거나, 너무 많은 내용 사이에 묻혔다.

이 글은 그 현상을 컨텍스트 창 하나로 설명한다. 무엇이 창을 채우는지, 창이 차면 무엇이 남고 무엇이 사라지는지, 그래서 CLAUDE.md를 어떻게 쓰고 언제 `/clear`를 치고 어떤 일을 서브에이전트에 넘기는지 본다. 뒤쪽에서는 일이 꼬였을 때 되돌아가는 체크포인트와, 손대기 전에 계획부터 받는 플랜 모드를 다룬다. 둘 다 컨텍스트를 아끼고 실수를 줄이는 장치라서 같이 묶었다.

설정 파일의 위치와 우선순위는 [Claude Code 프로젝트 구조](/posts/claude-code-project-structure), 스킬·서브에이전트·훅을 만드는 법은 [Claude Code 확장](/posts/claude-code-extensions)에 있다. 여러 세션을 동시에 돌리거나 예약해 두는 이야기는 [병렬 세션과 예약 작업](/posts/claude-code-parallel-and-scheduled)으로 넘긴다. 내용은 2026년 10월의 공식 문서(code.claude.com/docs)와 Claude Code 2.1.306 CLI 기준이다. 기능이 빠르게 바뀌는 도구라서, 버전이 붙은 동작은 문서에 적힌 범위로만 쓴다.

## 책상 위에 올라가는 것들

컨텍스트 창은 모델이 한 번의 요청에서 볼 수 있는 전부다. 비유를 하나만 쓰자면 책상이다. 모델은 책상 위에 펼쳐 놓은 것만 보고 일한다. 서랍 속 파일이나 어제 한 대화는 책상에 다시 올리지 않으면 없는 것과 같다. 책상 넓이는 토큰 수로 정해져 있다(모델에 따라 20만 토큰이나 100만 토큰).

공식 문서의 컨텍스트 창 설명을 따라가면, 사용자가 첫 글자를 치기 전에 이미 책상 위에 올라가는 것이 있다.

- 시스템 프롬프트와 내장 도구 정의
- CLAUDE.md(작업 폴더와 그 위 폴더들의 것), 경로 조건이 없는 `.claude/rules/` 규칙
- 자동 메모리 `MEMORY.md`의 앞부분(200줄이나 25KB 중 먼저 닿는 곳까지)
- MCP 서버의 도구 이름과 서버 안내문. 도구 정의 전체는 기본값으로 미뤄 두었다가 필요할 때 불러온다(tool search)
- 스킬의 설명(description). 본문은 스킬을 쓸 때 올라간다

일을 시작하면 그 위로 계속 쌓인다. 내가 보낸 메시지, Claude의 답, 읽은 파일 내용, 명령 출력, 훅이 덧붙인 텍스트, 그리고 특정 경로에만 걸리는 규칙(`paths:`가 있는 rules)과 하위 폴더의 CLAUDE.md는 그 폴더의 파일을 건드리는 순간 올라간다. 아래 그림은 한 세션이 책상을 채워 가는 모습이다. 퍼센트는 20만 토큰 창을 가정한 설명용 숫자다.

내 질문이 차지하는 몫은 아주 작다. 책상을 채우는 주범은 Claude가 일하면서 가져오는 것, 곧 파일 내용과 명령 출력이다. "이 폴더 전체를 훑어봐" 한 마디가 수만 토큰이 된다.

지금 내 세션의 실제 사용량은 `/context`로 본다. 범주별로 색칠한 격자와 함께 어떤 CLAUDE.md와 메모리 파일이 올라갔는지, 무엇이 자리를 많이 먹는지 알려 준다. `/memory`는 그 파일들을 열어 고치는 명령이다.

## 요청마다 책상 전체를 다시 보낸다

모델은 요청 사이에 아무것도 기억하지 않는다. 그래서 Claude Code는 메시지를 보낼 때마다 시스템 프롬프트, 프로젝트 지침, 지금까지의 대화와 도구 결과 전부에 새 메시지를 붙여 한 요청으로 다시 보낸다. 대화가 길어지면 요청 하나하나가 커진다.

얼마나 커지는지 계산해 봤다. 시작할 때 2만 토큰이 깔리고 턴마다 4천 토큰(질문, 답, 파일 읽기, 출력)이 붙는 30턴짜리 세션을 가정했다. 캐시 쪽은 API 가격표의 기본 배율(캐시 읽기 0.1배, 5분 캐시 쓰기 1.25배)로 셈했다.

```js
const START = 20_000, PER_TURN = 4_000, TURNS = 30, WINDOW = 200_000;
let ctx = START, noCache = 0, withCache = 0;
const rows = [];
for (let t = 1; t <= TURNS; t++) {
  const prefix = ctx;          // 앞 턴까지 이미 캐시된 부분
  ctx += PER_TURN;             // 이번 턴에 새로 붙는 부분
  noCache += ctx;              // 캐시가 없으면 전부 기본 입력 가격
  withCache += prefix * 0.1 + PER_TURN * 1.25; // 읽기 0.1배 + 새 부분 쓰기 1.25배
  if ([1, 10, 20, 30].includes(t)) rows.push({ turn: t, context: ctx, used: `${(ctx / WINDOW * 100).toFixed(0)}%` });
}
console.table(rows);
console.log("30턴 동안 보낸 입력 토큰 합계:", noCache.toLocaleString("en-US"));
console.log("캐시 적용 시 기본 입력 환산:", Math.round(withCache).toLocaleString("en-US"));
console.log("절약 비율:", (100 - withCache / noCache * 100).toFixed(1) + "%");
// 같은 30턴을 15턴씩 두 작업으로 나눠 사이에 /clear
let a = 0, c = START;
for (let t = 1; t <= 15; t++) { c += PER_TURN; a += c; }
const split = a * 2;
console.log("15턴마다 /clear 했을 때 입력 합계:", split.toLocaleString("en-US"), `(${(split / noCache * 100).toFixed(0)}%)`);
```

```text
┌─────────┬──────┬─────────┬───────┐
│ (index) │ turn │ context │ used  │
├─────────┼──────┼─────────┼───────┤
│ 0       │ 1    │ 24000   │ '12%' │
│ 1       │ 10   │ 60000   │ '30%' │
│ 2       │ 20   │ 100000  │ '50%' │
│ 3       │ 30   │ 140000  │ '70%' │
└─────────┴──────┴─────────┴───────┘
30턴 동안 보낸 입력 토큰 합계: 2,460,000
캐시 적용 시 기본 입력 환산: 384,000
절약 비율: 84.4%
15턴마다 /clear 했을 때 입력 합계: 1,560,000 (63%)
```

창은 30턴에 70%까지만 찼지만, 그동안 보낸 입력은 246만 토큰이다. 매 요청이 앞의 것을 전부 싣고 가니 합계는 턴 수의 제곱에 가깝게 는다. 프롬프트 캐시가 이 비용 대부분을 덜어 준다(이 가정에서 84%). 다만 캐시는 비용과 속도의 문제이고, 모델이 그 많은 내용 속에서 무엇에 주의를 기울이느냐는 문제는 그대로다. 같은 30턴을 서로 관계없는 두 작업으로 나누고 사이에 `/clear`를 치면, 캐시와 상관없이 보낼 양 자체가 63%로 준다.

캐시가 어떻게 나뉘는지 알면 어떤 행동이 비싼지 보인다. Claude Code는 잘 바뀌지 않는 것을 앞에 둔다. API는 요청의 앞부분(prefix)이 직전 요청과 글자 그대로 같을 때만 캐시를 쓰므로, 앞쪽 층이 바뀌면 그 뒤가 전부 다시 계산된다.

여기서 실무에 바로 쓰이는 사실 하나가 나온다. 프로젝트 루트와 사용자 수준의 CLAUDE.md는 세션 시작 때 한 번 읽어 메모리에 들고 있는다. 세션 도중에 CLAUDE.md를 고쳐도 캐시는 깨지지 않지만, 고친 내용도 반영되지 않는다. 새 내용은 다음 `/clear`, `/compact`, 재시작 때 올라간다. "CLAUDE.md에 규칙을 추가했는데 Claude가 안 지킨다"는 질문의 상당수가 이 경우다. 반면 모델을 바꾸면 모델마다 캐시가 따로라서 다음 요청이 전체를 새로 처리한다. 모델과 effort는 세션 처음에 정하고 중간에 바꾸지 않는 편이 싸다.

## 창이 차면 요약이 대신한다

책상이 가득 차도 세션이 끝나지는 않는다. Claude Code는 한도에 가까워지면 먼저 오래된 도구 출력을 치우고, 그래도 모자라면 대화 전체를 구조화된 요약 하나로 바꾼다. 이것이 자동 압축(auto-compaction)이다. 언제 도는지는 모델과 설정에 따라 다르다. 문서 기준으로 100만 토큰 창을 가진 모델은 약 967K에서, 확장 컨텍스트 없이 쓰는 Sonnet 4.6·Opus 4.6은 200K 경계에서 압축한다. `/autocompact 500k`처럼 더 일찍 돌게 할 수도 있다.

문제는 요약이 원문이 아니라는 데 있다. 문서도 "요청과 핵심 코드는 남기지만, 대화 초반의 자세한 지시는 잃을 수 있다"고 적는다. 처음의 `pnpm test:unit` 지시가 바로 이렇게 사라진다. 그래서 무엇이 어떻게 살아남는지 알아 둬야 한다. 같은 "남는다"도 디스크에서 다시 읽는 것과 요약에 녹아드는 것은 전혀 다르다.

| 들어온 경로 | 압축 뒤 |
| :- | :- |
| 시스템 프롬프트, 출력 스타일 | 그대로 적용된다 |
| 프로젝트 루트 CLAUDE.md, 경로 조건 없는 rules | 디스크에서 다시 읽어 넣는다 |
| 자동 메모리 | 디스크에서 다시 읽어 넣는다 |
| 플랜 모드에서 쓴 계획 | 디스크에서 다시 읽어 넣는다 |
| `paths:`가 있는 rules, 하위 폴더 CLAUDE.md | 요약으로 사라지고, 그 파일을 다시 건드릴 때 다시 올라간다 |
| 읽거나 고친 파일 | 최근에 수정된 것부터 최대 5개를 다시 읽는다 |
| 실행한 스킬 본문 | 스킬당 5,000 토큰, 합계 25,000 토큰까지. 오래된 것부터 버린다 |
| 훅이 앞서 덧붙인 내용 | 나머지 대화와 함께 요약된다 |
| `compact` 소스에 걸린 SessionStart 훅 | 다시 실행해 출력을 붙인다 |

이 표에서 원칙 하나가 나온다. 끝까지 지켜야 하는 규칙은 대화로 말하지 말고 프로젝트 루트 CLAUDE.md에 적는다. 대화로 한 말은 요약 품질에 운을 맡기는 것이고, CLAUDE.md는 압축 직후 원문 그대로 다시 올라간다. 경로 조건이 있는 rules도 압축을 넘기지 못하니, 압축 뒤에도 꼭 필요하면 `paths:`를 빼거나 루트 CLAUDE.md로 옮긴다. 스킬 본문은 잘릴 때 앞부분이 남으므로 중요한 지시를 `SKILL.md` 위쪽에 둔다.

자동 압축을 기다리지 않고 직접 다룰 수도 있다.

```text
/compact focus on the auth bug fix       # 요약에 남길 초점을 정해 지금 압축
/autocompact 500k                        # 이만큼 차면 자동 압축이 돌게 한다
/clear                                   # 관계없는 작업으로 넘어갈 때 대화를 비운다
/btw 이 저장소의 Node 버전이 몇이지?     # 대화 기록에 남지 않는 곁가지 질문
```

CLAUDE.md에 압축 지침을 적어 두는 방법도 문서에 있다. "Compact Instructions" 같은 절을 두고 "압축할 때 수정한 파일 목록과 테스트 명령은 꼭 남겨라"처럼 쓰면 요약이 그것을 챙긴다.

압축에도 비용이 든다. 요약을 만드는 별도 요청이 대화 전체를 다시 읽는다. 캐시가 살아 있으면 대부분 캐시 읽기라 싸지만, 오래 쉬었다가 재개한 세션은 캐시가 식어 있어서 그 요약 요청이 가장 비싸다. 문서가 권하는 습관은 작업 사이의 자연스러운 쉼표에서 직접 `/compact`를 치는 것이다. 작업 한가운데서 자동 압축이 돌면 요약이 지금 하던 일의 세부를 놓치기 쉽다.

압축이 아예 실패하는 경우도 있다. 파일 하나나 출력 하나가 너무 커서 요약하자마자 다시 창이 차면, Claude Code는 몇 번 시도한 뒤 반복을 멈추고 오류를 띄운다(문서의 thrashing 오류). 수 MB짜리 로그를 통째로 읽힌 경우가 전형적이다. 이럴 때는 `/clear`로 새로 시작하고, 큰 출력은 `tail`이나 `grep`으로 잘라서 읽힌다.

## 압축 뒤에 돌아오는 파일 다섯 개

압축 직후 Claude Code는 이번 세션에서 읽거나 고친 파일 가운데 최근에 수정된 것부터 다섯 개까지 다시 읽어 넣는다. 5,000 토큰이 넘는 파일은 내용 없이 경로만 남기고, 그 줄은 `Read` 대신 `Referenced file`로 표시된다. 아래에서 그 규칙을 직접 구현해 본다. 파일마다 `path`, `tokens`, `modified`(클수록 최근)가 주어진다.

## CLAUDE.md는 짧을수록 잘 지켜진다

CLAUDE.md는 매 세션, 매 요청에 실린다. 문서는 파일 하나를 200줄 아래로 유지하라고 권하고, 길수록 컨텍스트를 더 먹고 "지시를 따르는 정도(adherence)가 떨어진다"고 적는다. Best practices 문서는 더 직설적이다. CLAUDE.md가 너무 길면 중요한 규칙이 잡음에 묻혀 Claude가 절반을 무시한다고 한다.

이 블로그 저장소의 CLAUDE.md를 재 봤다.

```bash
wc -l -c CLAUDE.md   # 줄 수와 바이트 수
```

```text
  326 40011 CLAUDE.md
```

326줄, 40KB로 권장치를 훌쩍 넘는다. 글쓰기 규칙, 퀴즈 형식, 어휘 사전 규칙이 한 파일에 다 있다. 그런데 어휘 사전 규칙은 `features/vocabulary`를 만질 때만 필요하다. 이런 것이 경로 조건 rules로 옮길 후보다. `.claude/rules/vocabulary.md`에 `paths:`를 주면 그 폴더의 파일을 읽을 때만 올라간다. 방금 본 대로 압축을 넘기지는 못하지만, 그 폴더를 다시 건드리면 다시 올라오니 이런 부분 규칙에는 충분하다.

줄이는 기준은 문서가 준 것이 쓸 만하다. 이 줄을 지워도 Claude가 이미 올바르게 한다면 지운다. 매번 반드시 지켜야 해서 모델의 판단에 맡길 수 없다면 훅으로 바꾼다(CLAUDE.md는 "지시"일 뿐 강제가 아니다. 막아야 하는 동작은 PreToolUse 훅으로 막는다). `@path` import는 파일을 나눠 정리하는 데는 좋지만, 가져온 파일도 시작할 때 전부 올라가므로 컨텍스트는 줄지 않는다. 사람에게만 남기는 메모는 블록 HTML 주석(`<!-- ... -->`)으로 쓰면 Claude에게 보내기 전에 지워져서 토큰을 쓰지 않는다. 파일 위치와 우선순위는 [프로젝트 구조 글](/posts/claude-code-project-structure)에서 자세히 다룬다.

## 조사는 서브에이전트에게 맡긴다

"인증이 어떻게 동작하는지 찾아봐"는 파일을 수십 개 읽는 일이다. 결과로 필요한 것은 몇 문단의 요약인데, 읽은 파일은 전부 내 책상에 남는다. 서브에이전트는 이 문제를 책상을 하나 더 놓는 것으로 푼다. 서브에이전트는 자기 컨텍스트 창, 자기 시스템 프롬프트, 제한된 도구로 일하고, 끝나면 요약과 작은 메타데이터만 돌려준다. 아래 그림에서 다음을 누르면 무거운 읽기가 어디에 쌓이는지 보인다.

세부가 몇 가지 있다. 내장 Explore·Plan 서브에이전트는 빠르고 싸게 조사하려고 CLAUDE.md와 git 상태 없이 시작한다. 직접 만든 서브에이전트는 기본으로 CLAUDE.md를 싣는다. fork는 지금까지의 대화를 복사해서 시작하는 서브에이전트라, 맥락은 이어받지만 그만큼 무겁다. 공짜도 아니다. 서브에이전트는 자기 요청을 따로 보내서 같은 사용량 한도에서 깎이고, 여러 개를 동시에 돌리면 사용량도 그만큼 곱해진다.

그리고 서브에이전트가 돌려준 요약이 틀릴 수 있다. 요약만 받으니 근거를 볼 수 없다. 중요한 결론이면 "근거가 된 파일 경로와 줄 번호를 같이 달라"고 시키고, 그 몇 줄만 메인 세션에서 확인한다. 서브에이전트를 직접 정의하는 법은 [확장 글](/posts/claude-code-extensions)에 있다.

## Esc 두 번으로 되돌아가기

컨텍스트를 아끼는 또 하나의 방법은 잘못 간 길을 지우는 것이다. Claude Code는 내가 턴을 시작하는 프롬프트를 보낼 때마다, 그 직전 코드 상태를 체크포인트로 잡아 둔다. 프롬프트 입력이 비어 있을 때 `Esc`를 두 번 누르거나 `/rewind`를 치면 지금까지 보낸 프롬프트 목록이 뜨고, 하나를 골라 할 일을 정한다. 입력창에 글자가 있으면 `Esc` 두 번은 그 글자를 지운다(지운 글은 입력 기록에 남아 `Up`으로 되살린다).

## 되돌리지 못하는 것들

체크포인트는 Claude의 파일 편집 도구(Edit, Write 같은 것)가 만든 변경만 추적한다. 아래 그림은 세 번의 프롬프트에서 생긴 변경을 되감을 때 무엇이 돌아오고 무엇이 남는지 보여 준다.

문서가 밝힌 한계를 정리하면 이렇다.

- Bash로 바꾼 파일은 추적하지 않는다. `rm`, `mv`, `cp`, 코드 생성기, 포매터가 쓴 파일은 되감기로 돌아오지 않는다.
- 서브에이전트가 고친 파일은 대개 돌아오지 않는다. 내가 이미 이 대화에서 고친 파일만 되돌아가고, 서브에이전트만 건드린 파일은 남는다(포그라운드로 도는 `context: fork` 스킬은 예외). 이런 변경은 git으로 되돌린다.
- 내가 에디터에서 직접 고친 것, 동시에 도는 다른 세션이 고친 것은 보통 잡히지 않는다.
- 심볼릭 링크와 하드 링크는 건너뛰고 `Restored the code, but skipped N files` 경고를 띄운다. pnpm이 하드 링크로 깔아 둔 파일, dotfile 관리자가 링크한 설정 파일이 여기 걸린다.
- 그리고 바깥 세상은 당연히 돌아오지 않는다. DB 마이그레이션, 원격 push, 외부 API 호출, 보낸 메시지는 되감기와 무관하다.

그래서 체크포인트는 세션 안에서 빨리 되돌리는 장치이고 git을 대신하지 않는다. 실무에서는 큰 작업 전에 커밋을 하나 찍어 두고, 위험한 셸 명령과 바깥에 흔적을 남기는 명령은 권한 설정에서 묻게 둔다. 되감기를 믿고 `git push`나 마이그레이션을 허용 목록에 넣어 두면, 되감아도 돌아오지 않는 일을 가장 쉽게 저지르게 된다.

## 손대기 전에 계획부터 받는다

컨텍스트를 아끼는 가장 싼 방법은 처음부터 엉뚱한 방향으로 가지 않는 것이다. 플랜 모드는 Claude에게 조사하고 변경안을 내되 소스는 고치지 말라고 하는 모드다. Claude는 파일을 읽고, 탐색용 셸 명령을 돌리고, 계획을 써서 보여 준다. 내가 계획을 승인하기 전까지 편집은 막힌다.

들어가는 방법은 세 가지다. 세션 중에 `Shift+Tab`으로 권한 모드를 돌려 `plan`에 맞추거나, 프롬프트 한 번에만 `/plan`을 앞에 붙이거나, 처음부터 `--permission-mode plan`으로 시작한다. 지금 설치된 CLI의 도움말에도 모드 목록이 그대로 나온다.

```bash
claude --help | grep -A3 "permission-mode"   # 2.1.306에서 받을 수 있는 권한 모드
```

```text
  --permission-mode <mode>              Permission mode to use for the session
                                        (choices: "acceptEdits", "auto",
                                        "bypassPermissions", "manual",
                                        "dontAsk", "plan")
```

플랜 모드에서 자주 오해하는 것이 하나 있다. 플랜 모드는 "소스를 고치지 않는다"이지 "아무것도 실행하지 않는다"가 아니다. 탐색용 셸 명령은 돈다. 문서 기준으로 자동 모드를 쓸 수 있고 `useAutoModeDuringPlan`이 켜져 있으면(기본값) 분류기가 명령을 검토해 통과한 것은 실행하고, 자동 모드를 못 쓰면 읽기 전용 목록 밖의 명령은 나에게 묻는다. bypass permissions를 쓸 수 있는 터미널 세션에서는 계획 중의 명령에 분류기도 확인 창도 적용되지 않는다. 플랜 모드를 샌드박스로 여기면 안 되는 이유다.

언제 쓰나도 판단이 필요하다. 오타 수정이나 한 줄짜리 변경에 플랜 모드는 왕복만 늘린다. 파일 여러 개에 걸치는 변경, 처음 보는 코드베이스, 되돌리기 어려운 작업(스키마, 공개 API)일 때 값을 한다. 팀 저장소에서 늘 계획부터 받고 싶다면 `.claude/settings.json`의 `defaultMode`를 `plan`으로 둔다. VS Code 확장은 이 프로젝트 설정을 시작 모드로 읽지 않아서 `claudeCode.initialPermissionMode`를 따로 준다.

## 현장에서 컨텍스트가 일을 망치는 순간

증상에서 원인으로 거슬러 가는 순서로 정리한다.

- 초반에 말한 규칙을 어긴다. 압축이 돌았는지부터 본다. 대화 중간에 압축 표시가 보이거나 `/context`의 사용량이 갑자기 줄었다면 규칙이 요약에서 빠졌을 가능성이 크다. 그 규칙을 루트 CLAUDE.md로 옮기고, 이미 열린 세션에는 `/compact`나 `/clear`로 새 CLAUDE.md를 읽힌다.
- CLAUDE.md를 고쳤는데 반영이 안 된다. 세션 시작 때 읽은 판을 계속 쓰는 중이다. `/clear`, `/compact`, 재시작 가운데 하나가 필요하다. 하위 폴더 CLAUDE.md는 아직 안 읽혔다면 고친 내용이 바로 적용된다.
- 같은 실수를 고쳐 달라고 두 번 넘게 말했다. 대화에 실패한 시도가 쌓여 오히려 그쪽으로 끌려간다. 문서도 두 번 고쳐서 안 되면 `/clear` 하고, 배운 것을 담아 더 구체적인 첫 프롬프트로 다시 시작하라고 권한다.
- 응답이 점점 느리고 사용량이 빨리 준다. `/context`로 무엇이 자리를 먹는지 본다. 큰 로그, 연결만 해 둔 MCP 서버, 긴 CLAUDE.md가 흔한 범인이다. 모델이나 effort를 중간에 바꿨다면 그 다음 요청은 캐시 없이 처리된다.
- 압축이 반복되다 오류로 멈춘다. 거대한 파일이나 출력이 원인이다. `/clear` 후 잘라서 읽힌다.
- 되감았는데 파일이 그대로다. Bash나 서브에이전트가 만든 변경인지 본다. `git status`와 `git diff`로 확인하고 git으로 되돌린다.

처음 장면으로 돌아가면, 두 시간 동안 쌓인 파일과 로그 때문에 압축이 돌았고 `pnpm test:unit` 지시는 요약 속에서 흐려졌다. 끝까지 지켜야 할 규칙은 CLAUDE.md에, 무거운 조사는 서브에이전트에, 관계없는 작업 사이에는 `/clear`, 잘못 간 길은 `/rewind`, 큰 변경 전에는 계획부터. 책상을 넓히는 것보다 책상에 무엇을 올릴지 고르는 쪽이 결과를 더 바꾼다. 같은 원리를 여러 세션으로 넓히는 이야기는 [병렬 세션과 예약 작업](/posts/claude-code-parallel-and-scheduled)에서 이어 간다.

## 면접에서 나올 만한 질문

### 컨텍스트 창이 차면 Claude Code는 어떻게 하나요?

세션을 끝내지 않고 자동으로 압축한다. 먼저 오래된 도구 출력을 치우고, 그래도 모자라면 대화 전체를 구조화된 요약으로 바꾼다. 요청과 핵심 코드는 남지만 초반의 세세한 지시는 잃을 수 있어서, 끝까지 지킬 규칙은 CLAUDE.md에 둔다. 언제 도는지는 모델과 설정에 따라 다르고 `/autocompact`로 앞당길 수 있다.

### 압축 뒤에도 남는 것과 사라지는 것은 무엇인가요?

디스크에서 다시 읽는 것은 원문 그대로 남는다. 루트 CLAUDE.md, 경로 조건 없는 rules, 자동 메모리, 플랜 모드의 계획이 그렇다. 경로 조건 rules와 하위 폴더 CLAUDE.md, 훅이 덧붙인 내용은 요약에 녹아 사라지고, 읽은 파일은 최근 수정 순으로 다섯 개까지만 다시 읽는다. 5,000 토큰이 넘는 파일은 경로만 남는다.

### 세션 중에 CLAUDE.md를 고쳤는데 왜 적용되지 않나요?

루트와 사용자 수준 CLAUDE.md는 세션 시작 때 한 번 읽어 들고 있기 때문이다. 고쳐도 프롬프트 캐시는 깨지지 않지만 새 내용도 올라가지 않는다. `/clear`, `/compact`, 재시작 중 하나를 해야 다시 읽는다. 아직 읽지 않은 하위 폴더 CLAUDE.md는 예외로, 고친 내용이 처음 읽힐 때 반영된다.

### 프롬프트 캐시가 있는데 왜 /clear를 자주 하라고 하나요?

캐시는 비용과 속도를 덜어 줄 뿐, 모델이 보는 내용의 양은 그대로이기 때문이다. 관계없는 대화가 쌓이면 지금 필요한 파일과 지시가 묻히고, 매 요청이 그 전부를 다시 싣는다. 30턴 계산에서 캐시는 비용을 84% 줄였지만, 작업을 나눠 `/clear`를 치면 보낼 양 자체가 63%로 줄었다. 둘은 다른 문제를 푼다.

### 서브에이전트가 컨텍스트를 아끼는 원리는 무엇인가요?

자기만의 컨텍스트 창에서 일하고 결과 요약만 돌려주기 때문이다. 파일 수십 개를 읽은 내용은 서브에이전트 창에 남고 메인 세션에는 요약과 메타데이터만 붙는다. 대신 자기 요청을 따로 보내 사용량을 쓰고, 근거 없이 요약만 오니 중요한 결론은 파일 경로와 줄 번호를 받아 확인한다. fork는 대화를 복사해 시작하므로 맥락은 있지만 그만큼 무겁다.

### 체크포인트로 되돌리면 모든 변경이 사라지나요?

아니다. Claude의 파일 편집 도구가 만든 변경만 되돌린다. Bash로 지우거나 옮긴 파일, 대부분의 서브에이전트 편집, 직접 고친 파일, 링크된 파일은 남고, DB 마이그레이션이나 push 같은 바깥의 부작용은 당연히 그대로다. 그래서 체크포인트는 세션 안의 빠른 되돌리기로 쓰고, 영구 기록과 복구는 git에 맡긴다.

### 버리고 싶은 방향으로 한참 갔을 때 /compact와 /rewind 중 무엇이 낫나요?

`/rewind`가 낫다. 압축은 잘못된 시도까지 요약에 담아 남기고 새 prefix를 만들지만, 되감기는 그 시도를 지우고 이미 캐시된 앞부분으로 돌아간다. 앞쪽 지시는 살리고 뒤쪽 디버깅만 줄이고 싶다면 되감기 메뉴의 Summarize from here가 중간 선택지다.

### 플랜 모드면 아무것도 실행되지 않으니 안전한가요?

그렇지 않다. 플랜 모드는 승인 전까지 소스 편집을 막을 뿐, 탐색용 셸 명령은 돈다. 자동 모드 분류기가 검토하거나 나에게 묻는 식으로 통제되지만, bypass permissions를 쓸 수 있는 세션에서는 그 확인도 빠진다. 위험한 명령은 권한 규칙과 샌드박스로 막고, 플랜 모드는 방향을 먼저 맞추는 도구로 쓴다.
