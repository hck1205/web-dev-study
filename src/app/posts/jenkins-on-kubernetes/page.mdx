Jenkins를 Kubernetes로 옮기고 나서 첫 주에 이런 빌드가 나왔다. 콘솔에는 "Still waiting to schedule task"만 떠 있고 10분째 움직이지 않는다. 대기열에 마우스를 올리면 에이전트가 오프라인이라고 한다. 고정 에이전트 시절이라면 그 서버에 들어가 보면 됐다. 지금은 들어갈 서버가 없다. 에이전트는 빌드가 들어올 때 만들어지는 파드이고, 그 파드는 `Pending`에서 멈춰 있었다. 빌드 하나에 컨테이너 셋이 요청한 CPU를 합치면 남은 노드 어디에도 들어가지 않았던 것이다.

Kubernetes 위의 Jenkins는 Jenkinsfile을 거의 그대로 둔 채 에이전트를 빌드마다 새로 띄운다. 덕분에 놀고 있는 에이전트 서버와 빌드끼리 섞이는 작업 공간이 사라진다. 대신 새로 생기는 문제가 있다. 파드가 안 뜨는 이유, 파드 안에서 컨트롤러로 다시 접속하는 길, docker 없이 이미지를 만드는 법, 매번 빈 디스크로 시작하는 빌드의 캐시다.

Jenkinsfile 문법, 컨트롤러와 에이전트의 역할, shared library의 기본은 [Jenkins 파이프라인](/posts/jenkins-pipeline-basics)에서 다뤘다. 여기서는 그 위에서 Kubernetes에서 달라지는 부분만 쓴다. 이렇게 만든 이미지를 환경별로 배포하는 흐름은 [Jenkins와 ArgoCD로 나눠 배포하기](/posts/jenkins-argocd-push-pull)에 있다.

출력 이야기를 먼저 해 둔다. Jenkins 2.580.1 LTS의 war 파일을 JDK 21로 직접 띄우고, 인바운드 에이전트를 WebSocket으로 붙여 빌드를 돌린 출력은 실제 결과다. 글을 쓴 환경에서는 Jenkins 업데이트 센터에 접속할 수 없어 Kubernetes 플러그인과 JCasC 플러그인을 설치하지 못했다. 그래서 플러그인 설정, kubectl, 파드 이벤트 출력은 예시다.

## 빌드가 들어올 때 파드가 생긴다

Kubernetes 플러그인은 Jenkins에 "cloud"를 하나 추가한다. 고정 에이전트는 미리 등록돼 있어서 빌드가 들어오면 빈 executor를 찾기만 하면 된다. cloud는 반대로, 대기열에 레이블과 맞는 에이전트가 없을 때 새로 만들어 준다. 그 에이전트가 파드다.

이 파드 안에는 컨테이너가 최소 하나 있다. `jnlp`라는 이름의 컨테이너로, 기본 이미지는 `jenkins/inbound-agent`다. 이 컨테이너가 컨트롤러로 먼저 접속해서 "나 pod-xyz다"라고 등록하는 인바운드 에이전트 역할을 한다. 빌드 도구(maven, node, kaniko)는 같은 파드에 컨테이너를 더 두고, Jenkinsfile에서 `container('maven') { ... }`로 어느 컨테이너에서 명령을 돌릴지 고른다. 빌드가 끝나면 파드는 지워진다.

## 파드 안의 jnlp 컨테이너가 하는 일

파드 에이전트가 컨트롤러에 붙는 과정은 일반 인바운드 에이전트와 같다. 그래서 플러그인 없이도 이 부분은 직접 볼 수 있다. Jenkins war를 JDK 21로 띄우고, 초기화 스크립트(`init.groovy.d`)로 인바운드 에이전트 노드 `pod-agent-1`을 등록했다. 컨트롤러는 executor를 0으로 두어 빌드가 에이전트에서만 돌게 했다.

```bash
# 설치 마법사를 끄고 로컬에서 Jenkins를 띄운다
java -Djenkins.install.runSetupWizard=false -DJENKINS_HOME=$PWD/jhome \
  -jar jenkins.war --httpPort=19900 --httpListenAddress=127.0.0.1
```

에이전트가 연결되지 않은 채로 빌드를 넣으면 대기열은 이유를 이렇게 적는다. Jenkins API로 대기열을 읽은 결과의 일부다.

```bash
# 대기열에 있는 항목과 기다리는 이유
```

## podTemplate 한 장에 컨테이너 여럿

파드 모양은 podTemplate으로 정한다. 화면이나 JCasC에 전역으로 적을 수도 있고, Jenkinsfile 안에 YAML로 바로 적을 수도 있다. 선언형 파이프라인에서는 `agent { kubernetes { ... } }`로 쓴다(예시).

```groovy
pipeline {
  agent {
    kubernetes {
      defaultContainer 'maven'          // container()를 안 쓴 sh는 여기서 돈다
      yaml '''
apiVersion: v1
kind: Pod
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
  containers:
    - name: maven
      image: maven:3.9-eclipse-temurin-21
      command: ["sleep"]
      args: ["infinity"]
      resources:
        requests: { cpu: "1", memory: 2Gi }
        limits: { memory: 2Gi }
    - name: buildkit
      image: moby/buildkit:rootless       # buildkitd가 uid 1000으로 계속 떠 있다
      args: ["--oci-worker-no-process-sandbox"]
      securityContext:
        seccompProfile: { type: Unconfined }   # rootless가 사용자 네임스페이스를 만들 수 있게
        appArmorProfile: { type: Unconfined }
      resources:
        requests: { cpu: 500m, memory: 1Gi }
'''
    }
  }
  stages {
    stage('Test') { steps { sh 'mvn -B verify' } }
    stage('Image') {
      steps {
        container('buildkit') {
          sh 'buildctl --addr unix:///run/user/1000/buildkit/buildkitd.sock build --frontend dockerfile.v0 --local context=. --local dockerfile=. --output type=image,name=registry.example.com/shop/shop-api:$GIT_COMMIT,push=true'
        }
      }
    }
  }
}
```

maven 컨테이너에 `sleep infinity`를 주는 이유가 있다. 이 컨테이너는 Jenkins가 `exec`로 명령을 넣어 줄 때까지 살아 있어야 한다. 이미지의 기본 명령이 바로 끝나는 것이면 컨테이너가 종료되고 파드가 실패한다. buildkit 컨테이너는 buildkitd 자체가 계속 떠 있는 프로세스라 그대로 두고, `buildctl`이 그 소켓으로 빌드를 맡긴다. 두 `Unconfined` 줄은 BuildKit 문서가 rootless 모드에 요구하는 완화이고, 클러스터 정책에 따라 허용되지 않을 수 있다. `jnlp` 컨테이너는 적지 않아도 플러그인이 기본값으로 넣는다. 직접 적으면 그 정의가 쓰인다.

## 빌드 파드가 Pending에서 멈출 때

처음 장면으로 돌아가자. 빌드 파드가 노드에 들어가려면 모든 컨테이너 요청량의 합이 한 노드의 남은 할당 가능량 안에 들어가야 한다. 위 템플릿은 maven 1 CPU·2Gi, buildkit 0.5 CPU·1Gi에 jnlp 기본 요청까지 더해진다. 컨테이너 하나하나는 작아 보여도 합은 크다. 파드 이벤트는 이렇게 보인다(예시).

```bash
# 대기 중인 에이전트 파드와 그 이벤트
kubectl -n jenkins get pods -l jenkins/label
kubectl -n jenkins describe pod shop-api-main-12-7k2xq-0f3bd | tail -5
```

```text
NAME                           READY   STATUS    RESTARTS   AGE
shop-api-main-12-7k2xq-0f3bd   0/3     Pending   0          9m41s

Events:

  ----     ------            ----   ----               -------
  Warning  FailedScheduling  9m41s  default-scheduler  0/4 nodes are available: 4 Insufficient cpu. preemption: 0/4 nodes are available: 4 No preemption victims found for incoming pod.
```

스케줄러가 하는 계산을 줄여서 직접 짜 보자. 노드마다 남은 CPU·메모리가 있고, 파드의 컨테이너 요청을 모두 더해 들어가는 첫 노드를 고른다. 단위는 CPU가 `500m`(밀리코어) 또는 `1`, 메모리는 `Mi`와 `Gi`만 쓴다고 하자.

## docker 소켓 없이 이미지를 만든다

고정 에이전트 시절에는 에이전트 서버의 docker 데몬으로 `docker build`를 했다. 파드 안에서 같은 일을 하려고 노드의 `/var/run/docker.sock`을 파드에 붙이는 설정이 아직 많이 돈다. 이건 빌드 파드에 노드의 root를 주는 것과 같다. 그 소켓으로 `docker run --privileged -v /:/host`를 하면 노드 파일 시스템 전체가 열린다. 빌드 스크립트는 PR을 올린 누구나 고칠 수 있으니, PR 하나가 노드를 차지할 수 있다는 뜻이다. 요즘 노드는 docker가 아니라 containerd로 도는 경우가 많아서 소켓 자체가 없기도 하다.

대안은 데몬 없이, 또는 권한 없이 이미지를 만드는 도구다.

| 방식 | 권한 | 메모 |
|---|---|---|
| docker.sock 마운트 | 노드 root와 같다 | 노드에 docker가 있어야 하고, 쓰지 않는 쪽으로 간다 |
| Docker-in-Docker | privileged 컨테이너 | 격리가 약하고, 빌드 캐시가 파드와 함께 사라진다 |
| BuildKit rootless | 일반 사용자, 단 seccomp·AppArmor 완화가 필요할 수 있다 | Dockerfile 그대로, 레지스트리 캐시 내보내기 지원 |
| Buildah | rootless 가능, 설정에 따라 추가 권한 | Dockerfile과 스크립트 방식 둘 다 |
| kaniko | root 사용자지만 privileged는 아님 | 원래 구글 프로젝트는 2025년에 보관(archived) 처리됐고, 커뮤니티 포크가 이어 가고 있다 |

kaniko는 오래 표준처럼 쓰였다. 새로 고른다면 프로젝트 상태를 먼저 확인한다. 이미 쓰고 있다면 당장 깨지지는 않지만, 보안 패치가 어디서 나오는지 정해 둬야 한다. BuildKit rootless는 Kubernetes에서 돌릴 때 사용자 네임스페이스를 만들 수 있어야 해서, 클러스터의 Pod Security 수준이나 노드 커널 설정에 따라 막힐 수 있다. 어느 도구든 네임스페이스의 Pod Security Admission이 `restricted`면 거부될 수 있으니, 빌드 네임스페이스에 맞는 수준을 따로 정한다([Pod Security Admission](/posts/k8s-pod-security-admission)).

빌드 컨테이너가 레지스트리에 올릴 때 쓰는 자격 증명도 Jenkins credentials가 아니라 Kubernetes Secret으로 줄 수 있다. EKS라면 빌드 파드의 서비스 어카운트에 ECR push 역할만 붙이는 편이 정적 키를 두는 것보다 낫다. 아래 그림에서 다음을 누르면 두 길이 비교된다.

## 빈 디스크에서 시작하는 빌드의 캐시

파드 에이전트의 장점이 매번 깨끗한 환경이라면, 단점은 매번 의존성을 처음부터 받는다는 것이다. Maven 저장소나 `node_modules`를 매번 받으면 빌드 시간의 대부분이 다운로드가 된다. 캐시를 붙이는 방법은 세 갈래다.

첫째는 PVC를 의존성 디렉터리에 붙이는 것이다. 간단하지만 볼륨 접근 모드를 봐야 한다. 클라우드 블록 스토리지(EBS 같은)는 대부분 `ReadWriteOnce`라서 한 노드에서만 붙는다. 빌드 파드 둘이 다른 노드에 뜨면 두 번째 파드는 이런 이벤트와 함께 멈춘다(예시).

```text
Warning  FailedAttachVolume  2m  attachdetach-controller  Multi-Attach error for volume "pvc-3c1f…" Volume is already used by pod(s) shop-api-main-11-p9d4r-1m2kq
```

여러 파드가 함께 써야 하면 `ReadWriteMany`를 지원하는 파일 스토리지(EFS 같은 NFS 계열)를 쓴다. 대신 여러 빌드가 동시에 같은 캐시를 쓰다 깨질 수 있다. Maven 로컬 저장소는 동시 쓰기에 강하지 않아서, 읽기 전용 공용 캐시와 빌드마다 쓰는 디렉터리를 나누는 팀도 있다.

둘째는 원격 캐시다. Gradle Build Cache나 사내 Nexus·Artifactory 프록시를 두면 파드가 바뀌어도 가까운 곳에서 받는다. 사내망 안의 프록시 저장소는 외부 저장소가 느리거나 끊겼을 때도 빌드를 살린다.

셋째는 이미지 레이어 캐시다. BuildKit은 `--export-cache type=registry,ref=…`와 `--import-cache`로 캐시를 레지스트리에 두고 받는다. 앞 그림의 cache repo가 이것이다. 캐시 키를 어떻게 정하고, 캐시가 오염됐을 때 어떻게 되는지는 [빌드 캐시](/posts/build-caching)에서 자세히 다뤘다.

## 컨트롤러도 코드로 둔다

에이전트가 일회용이 되면 남는 상태는 컨트롤러뿐이다. 컨트롤러는 보통 공식 Helm 차트로 StatefulSet 하나와 `$JENKINS_HOME`용 PVC로 띄운다. 이 디스크에 잡 기록, 빌드 로그, credentials가 있다. 컨트롤러 파드가 다른 노드로 옮겨 가면 PVC도 따라가야 하니, 블록 스토리지라면 같은 가용 영역 안에서만 옮겨 갈 수 있다.

설정은 화면에서 누르지 않고 JCasC(Configuration as Code 플러그인)로 YAML에 적는다. 컨트롤러 이미지는 플러그인 목록을 고정해 미리 넣어 만든다. 그러면 화면에서 플러그인을 하나 업데이트했다가 파이프라인 전체가 멈추는 사고를 이미지 버전으로 되돌릴 수 있다. JCasC에 Kubernetes cloud를 적으면 이런 모양이다(예시).

```yaml
jenkins:
  numExecutors: 0
  clouds:
    - kubernetes:
        name: "k8s"
        namespace: "jenkins-agents"
        jenkinsUrl: "http://jenkins.jenkins.svc.cluster.local:8080/"
        webSocket: true
        containerCapStr: "20"
        templates:
          - name: "maven"
            label: "maven"
            yaml: |
              spec:
                containers:
                  - name: maven
                    image: maven:3.9-eclipse-temurin-21
                    command: ["sleep"]
                    args: ["infinity"]
credentials:
  system:
    domainCredentials:
      - credentials:
          - string:
              scope: GLOBAL
              id: "deploy-repo-token"
              secret: "${DEPLOY_REPO_TOKEN}"
```

`jenkinsUrl`을 클러스터 안 서비스 주소로 적는 게 앞에서 본 Handshake 문제를 피하는 길이다. 화면의 Jenkins URL(사람이 보는 외부 주소)과 에이전트가 붙는 주소를 나눠 둔다. `containerCapStr`은 이 cloud가 동시에 띄울 파드 수의 상한이다. PR이 몰리는 날 빌드 파드가 클러스터를 다 차지하지 않게 막는다. `${DEPLOY_REPO_TOKEN}` 같은 값은 YAML에 직접 적지 않고 Kubernetes Secret을 환경 변수나 파일로 넣어 읽게 한다.

빌드 에이전트를 같은 클러스터에 둘지도 정해야 한다. 컨트롤러와 에이전트를 서비스 클러스터와 같은 곳에 두면 운영 비용은 줄지만, 빌드 파드가 뚫렸을 때 서비스와 같은 클러스터 안에 있게 된다. 적어도 에이전트 네임스페이스를 나누고 [NetworkPolicy](/posts/k8s-network-policy)로 빌드 파드가 서비스 네임스페이스에 닿지 못하게 한다. 운영 클러스터 안에는 빌드를 두지 않는 편이 낫다.

## podTemplate을 여러 저장소가 나눠 쓸 때

서비스마다 Jenkinsfile에 같은 YAML을 복사하면 이미지 버전을 올릴 때 스무 군데를 고친다. 템플릿을 공용으로 두는 방법은 둘이다. JCasC에 전역 템플릿을 두고 Jenkinsfile에서는 `inheritFrom 'maven'`으로 상속받으며 필요한 것만 덧붙이는 방법, 그리고 shared library의 `resources/`에 YAML을 두고 `libraryResource('podtemplates/maven.yaml')`로 읽어 넣는 방법이다. 상속할 때 컨테이너 목록이 합쳐지는지 덮어써지는지는 `yamlMergeStrategy` 설정에 따라 다르니, 상속한 템플릿에 컨테이너를 추가했는데 사라졌다면 이 값부터 본다.

shared library 버전을 태그로 고정하는 이유는 [Jenkins 파이프라인](/posts/jenkins-pipeline-basics)에서 봤다. podTemplate도 같다. 공용 템플릿의 이미지를 바꾸는 건 모든 서비스의 빌드 환경을 바꾸는 일이니 라이브러리 태그를 새로 따고 서비스 하나에서 먼저 돌려 본다.

## 다시 그 Pending 빌드

처음 장면의 빌드는 Jenkinsfile 문제가 아니었다. 빌드 파드 하나의 요청량 합이 노드의 남은 CPU보다 컸고, 빌드는 "오프라인 에이전트"를 기다렸다. 원인을 찾은 곳도 Jenkins 화면이 아니라 파드 이벤트였다. Kubernetes 위의 Jenkins에서 빌드가 기다리기만 하면, 파드가 생겼는지 → 노드에 올라갔는지 → 이미지를 받았는지 → jnlp가 접속했는지 순서로 본다. 그 앞 단계가 모두 지나야 비로소 Jenkinsfile을 볼 차례다.

## 면접에서 나올 만한 질문

### Jenkins Kubernetes 플러그인은 어떻게 동작하나요?

대기열에 레이블과 맞는 에이전트가 없으면 그 레이블의 podTemplate으로 파드를 만든다. 파드 안의 jnlp 컨테이너가 컨트롤러로 인바운드 접속해 에이전트로 등록되고, 빌드 단계는 `container()`로 고른 컨테이너에서 실행된다. 빌드가 끝나면 파드를 지워서 다음 빌드는 깨끗한 환경에서 시작한다.

### 파드 에이전트에서 빌드가 "에이전트 오프라인"으로 계속 기다리면 어디부터 보나요?

파드가 생겼는지, 생겼다면 어느 상태에서 멈췄는지 본다. Pending이면 요청량 합과 taint, ImagePullBackOff면 이미지와 레지스트리 인증, Running인데 접속을 못 하면 jnlp 로그의 Handshake error와 컨트롤러 로그의 "incorrect secret", 그리고 jenkinsUrl이 파드 안에서 닿는 주소인지 본다. 파드가 금방 지워지면 podRetention을 잠시 onFailure로 둔다.

### 빌드 파드에 docker.sock을 마운트하면 왜 위험한가요?

docker 데몬은 노드에서 root로 돌기 때문에, 소켓을 쓸 수 있으면 privileged 컨테이너를 띄워 노드 파일 시스템 전체에 닿을 수 있다. 빌드 스크립트는 PR 작성자가 고칠 수 있으니 PR 하나가 노드를 차지할 수 있다. 그래서 BuildKit rootless, Buildah 같은 데몬 없는 빌드 도구를 쓰고 hostPath와 privileged를 정책으로 막는다.

### kaniko를 지금 새로 도입해도 되나요?

원래 구글 프로젝트가 2025년에 보관 처리돼서, 새로 고른다면 포크의 유지 상태를 확인하거나 BuildKit rootless, Buildah를 먼저 검토한다. 이미 쓰고 있다면 바로 깨지지는 않지만 보안 패치를 어디서 받을지 정해야 한다. 어느 도구든 레이어 캐시를 레지스트리에 두는 설정을 함께 한다.

### 빌드마다 새 파드가 뜨면 캐시는 어떻게 하나요?

의존성 디렉터리에 PVC를 붙이거나, Nexus 같은 프록시 저장소와 Gradle 원격 캐시를 쓰거나, BuildKit의 레지스트리 캐시로 이미지 레이어를 재사용한다. PVC는 ReadWriteOnce면 다른 노드의 파드가 동시에 못 붙어 Multi-Attach error가 나니, 여러 파드가 쓰려면 ReadWriteMany 스토리지를 쓰고 동시 쓰기 문제를 따로 다룬다.

### 컨트롤러를 Kubernetes에 둘 때 무엇을 챙기나요?

`$JENKINS_HOME`이 상태의 전부라 PVC와 백업을 챙긴다. 플러그인은 목록을 고정해 컨트롤러 이미지에 넣고, 설정은 JCasC로 YAML에 둬서 이미지와 설정을 버전으로 되돌릴 수 있게 한다. 컨트롤러의 executor는 0으로 두고, 에이전트가 붙는 jenkinsUrl은 클러스터 안 서비스 주소로 적는다.

### WebSocket 에이전트와 TCP 에이전트 포트는 어떻게 고르나요?

WebSocket은 컨트롤러의 HTTP 포트 하나로 붙어서 Ingress나 로드 밸런서 뒤에서도 포트를 따로 열 필요가 없다. 대신 앞단 프록시가 WebSocket과 오래 열린 연결을 통과시켜야 하고, 유휴 타임아웃에 끊기지 않게 설정해야 한다. TCP 포트 방식은 별도 포트(흔히 50000)를 서비스로 열어야 하지만 프록시를 거치지 않는다.
