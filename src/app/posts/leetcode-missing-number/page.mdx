[Missing Number](https://leetcode.com/problems/missing-number/)는 LeetCode 268번이다. 0부터 n까지의 수 중 하나가 빠진 배열이 주어지고, 빠진 수를 찾는다. 해시 집합으로 금방 풀리는데, 문제가 "추가 공간 O(1), 시간 O(n)으로도 풀 수 있겠느냐"고 따로 묻는다. 그 질문에 답하는 길이 산수(합)와 비트(XOR) 두 갈래로 나뉘고, 둘의 차이를 아는지가 면접에서 갈린다.

XOR가 같은 수를 지우는 성질은 [Single Number](/posts/leetcode-single-number#같은-수를-두-번-섞으면-사라진다)에서 자세히 봤다. 이 글은 그 성질을 "짝을 내가 만들어 넣는" 쪽으로 한 걸음 더 쓴다. 느린 풀이부터 여섯 가지로 풀고, 정렬된 배열, 빠진 수가 둘, 중복과 빠짐이 함께 있는 경우까지 넓힌다. 코드는 Node.js 22, Python 3.13, Java 21에서 직접 돌렸다.

## 0부터 n까지에서 한 칸이 빈다

길이 n인 배열 `nums`가 주어진다. 원소는 모두 다르고, 0 이상 n 이하의 정수다. 0부터 n까지는 n + 1개인데 배열에는 n개만 있으니 정확히 하나가 빠진다. 그 수를 돌려준다.

풀이를 고르는 데 영향을 주는 제약은 이 정도다.

- n은 1 이상 10^4 이하다. 빈 배열은 없다.
- 원소는 서로 다르다. 중복이 없다는 보장이 있어서 합이나 XOR가 성립한다.
- 덧붙인 질문: 추가 공간 O(1), 시간 O(n)으로 풀 수 있는가.

n이 만 개라 O(n²)도 1억 번 정도라 겨우 돈다. 진짜 조건은 덧붙인 질문 쪽이다. 배열 길이만큼 커지는 장부 없이 풀라는 뜻이다.

## 다섯 칸짜리 예시를 손으로

이 글 끝까지 쓸 예시다.

```text
인덱스   0   1   2   3   4
nums     3   0   4   1   5
```

길이가 5이니 n = 5이고, 있어야 할 수는 0, 1, 2, 3, 4, 5 여섯 개다. 배열에 있는 건 3, 0, 4, 1, 5다. 하나씩 지워 보면 2가 남는다.

손으로 풀 때 머릿속에서는 두 가지 일을 한다. 하나는 "있어야 할 목록"을 떠올리는 것, 다른 하나는 "실제로 있는 수"를 그 목록에서 지우는 것이다. 풀이마다 이 두 목록을 어떻게 맞대느냐가 다르다. 목록을 그대로 대 보면 브루트포스, 줄을 세워 대 보면 정렬, 장부에 적어 대 보면 해시, 숫자 하나로 눌러 담아 대 보면 합과 XOR다.

이 문제에는 눈여겨볼 점이 하나 더 있다. 배열의 인덱스는 0부터 n - 1까지다. 있어야 할 수 0부터 n까지와 n 하나만 빼고 똑같다. 인덱스가 "있어야 할 목록"을 공짜로 들고 있는 셈이고, 뒤의 순환 정렬과 XOR 풀이가 이 점을 쓴다.

## 후보를 하나씩 배열에서 찾아본다

정의를 그대로 옮긴다. 0부터 n까지 후보 k마다 배열에 k가 있는지 찾아보고, 없으면 그게 답이다.

```js
function missingNumber(nums) {
  const n = nums.length;
  for (let k = 0; k <= n; k++) {
    // includes는 배열을 처음부터 끝까지 훑는다
    if (!nums.includes(k)) return k;
  }
}

console.log(missingNumber([3, 0, 4, 1, 5]), missingNumber([0]), missingNumber([1]), missingNumber([1, 2]), missingNumber([0, 1]));
```

```text
2 1 0 0 2
```

후보가 n + 1개이고 후보마다 `includes`가 최대 n칸을 본다. 시간은 O(n²), 공간은 O(1)이다. 빠진 수가 클수록 늦게 끝난다. 0부터 19999까지 다 있고 20000이 빠진 배열에서 226ms가 걸렸다. LeetCode 제약 n ≤ 10^4에서는 통과할 수도 있지만, 면접에서 이 답으로 끝내면 안 된다.

느린 이유는 "있어야 할 목록"과 "있는 목록"이 서로 아무 순서 없이 놓여 있어서, 하나를 찾을 때마다 전부 뒤지기 때문이다. 둘 중 하나에 질서를 주면 뒤지는 일이 줄어든다.

## 정렬하면 자리와 값이 어긋나는 곳이 답이다

배열을 정렬하면 빠진 수 앞까지는 `a[i] === i`가 성립한다. 0번 칸에 0, 1번 칸에 1이 온다. 빠진 수 자리에서 처음으로 어긋난다.

```text
정렬 후   0   1   3   4   5
인덱스    0   1   2   3   4
                  ↑ 처음으로 값 ≠ 인덱스. 답은 2
```

```js
function missingNumber(nums) {
  const a = [...nums].sort((x, y) => x - y); // 숫자 비교 함수가 꼭 필요하다
  for (let i = 0; i < a.length; i++) {
    if (a[i] !== i) return i; // 처음 어긋난 자리
  }
  return a.length; // 끝까지 맞았다면 빠진 수는 n이다
}

console.log(missingNumber([3, 0, 4, 1, 5]), missingNumber([0]), missingNumber([1]), missingNumber([1, 2]), missingNumber([0, 1]));
```

```text
2 1 0 0 2
```

마지막 줄 `return a.length`를 빼먹기 쉽다. `[0, 1]`처럼 n이 빠진 배열은 모든 칸이 맞아서 반복 안에서 아무것도 돌려주지 않는다. 이 실수는 뒤의 엣지 케이스 절에서 실제 출력으로 다시 본다.

시간은 정렬 때문에 O(n log n), 공간은 복사본 O(n)이다(입력을 고쳐도 되면 정렬 구현이 쓰는 만큼). 덧붙인 질문의 두 조건을 다 놓친다. 그래도 "정렬돼 있으면 값과 인덱스가 어긋나는 첫 자리"라는 생각은 정렬된 입력 변형에서 이진 탐색이 된다.

## 본 수를 집합에 적어 두기

이번엔 "있는 목록"을 장부에 적는다. 해시 집합에 배열을 다 넣고, 0부터 n까지 집합에 없는 수를 찾는다.

```js
function missingNumber(nums) {
  const seen = new Set(nums); // 있는 수를 모두 적는다
  for (let k = 0; k <= nums.length; k++) {
    if (!seen.has(k)) return k; // 평균 O(1)로 확인한다
  }
}

console.log(missingNumber([3, 0, 4, 1, 5]), missingNumber([0]), missingNumber([1]), missingNumber([1, 2]), missingNumber([0, 1]));
```

```text
2 1 0 0 2
```

시간은 평균 O(n), 공간은 O(n)이다. 해시 집합이 왜 평균 O(1)에 찾는지는 [해시맵 글](/posts/ds-hash-map)에 있다. 값의 범위가 0부터 n으로 정해져 있으니 집합 대신 길이 n + 1짜리 불리언 배열을 써도 된다. 해시 계산이 없어 더 빠르고, 하는 일은 같다.

면접에서는 이 풀이를 "일단 동작하는 답"으로 먼저 말하기 좋다. 빠진 수가 여러 개여도, 중복이 섞여 있어도 그대로 쓸 수 있기 때문이다. 다만 공간이 O(n)이라 덧붙인 질문에는 답하지 못한다.

## 값을 제자리로 돌려보내는 순환 정렬

장부를 따로 만들지 않고 배열 자체를 장부로 쓰는 방법이 있다. 값 v는 v번 칸에 있어야 한다. 그러니 칸마다 값을 제 칸으로 보내고(맞바꾸기), 다 끝난 뒤 처음으로 `a[i] !== i`인 칸을 찾는다. 이런 정렬을 순환 정렬(cyclic sort)이라 부른다. 값의 범위가 인덱스와 딱 맞을 때만 쓸 수 있는 정렬이다.

n은 갈 칸이 없다. 배열 칸은 n - 1번까지라서다. 그래서 n을 만나면 건드리지 않고 넘어간다. n이 앉은 칸이 곧 빈 의자 자리다.

```js
function missingNumber(nums) {
  const a = [...nums]; // 입력을 고쳐도 되면 복사하지 않아도 된다
  const n = a.length;
  let i = 0;
  while (i < n) {
    const v = a[i];
    if (v < n && a[v] !== v) {
      [a[i], a[v]] = [a[v], a[i]]; // v를 제 칸으로 보낸다. i는 그대로 두고 새로 온 값을 다시 본다
    } else {
      i++; // 이미 제자리이거나 n이라 갈 곳이 없다
    }
  }
  for (let i = 0; i < n; i++) {
    if (a[i] !== i) return i; // 주인이 오지 않은 칸
  }
  return n;
}

console.log(missingNumber([3, 0, 4, 1, 5]), missingNumber([0]), missingNumber([1]), missingNumber([1, 2]), missingNumber([0, 1]));
```

```text
2 1 0 0 2
```

아래 그림에서 다음을 누르면 값이 제 칸을 찾아 자리를 바꾼다. 기억 칸에는 지금 배열 상태를 0번 칸부터 적었다.

`while`문 안에서 맞바꿨을 때 `i`를 늘리지 않는 이유가 그림에 보인다. 0번 칸에 1이 왔을 때 넘어가 버리면 1은 영영 제자리에 못 간다. 새로 온 값도 제 칸으로 보내야 한다.

맞바꾸기가 몇 번 일어나는지 세어 보면 시간이 보인다. 한 번 맞바꿀 때마다 값 하나가 제 칸에 확정되고, 확정된 값은 다시 움직이지 않는다. 그래서 맞바꾸기는 최대 n번, `i++`도 n번이라 전체는 O(n)이다. 공간은 입력을 고쳐도 된다면 O(1)이다.

덧붙인 질문의 조건을 만족하지만 입력을 망가뜨린다는 대가가 있다. 호출한 쪽이 배열을 계속 쓰면 곤란하다. 이 문제에서는 다음 두 풀이가 입력을 건드리지 않고 O(1)을 내서 순환 정렬을 꼭 쓸 이유는 없다. 그래도 이 기법은 LeetCode 41. First Missing Positive처럼 합이나 XOR가 통하지 않는 문제에서 거의 유일한 O(1) 공간 답이 된다.

## 있어야 할 합에서 실제 합을 뺀다

0부터 n까지의 합은 공식으로 바로 나온다. n(n + 1) / 2다. 가우스가 1부터 100까지를 더할 때 쓴 그 공식이다. 배열의 합은 빠진 수 하나만큼 모자란다. 둘을 빼면 빠진 수다.

```text
있어야 할 합   0 + 1 + 2 + 3 + 4 + 5 = 5 × 6 / 2 = 15
실제 합        3 + 0 + 4 + 1 + 5     = 13
빠진 수        15 - 13               = 2
```

```js
function missingNumber(nums) {
  const n = nums.length;
  let sum = 0;
  for (const x of nums) sum += x;
  return (n * (n + 1)) / 2 - sum; // 있어야 할 합 - 실제 합
}

console.log(missingNumber([3, 0, 4, 1, 5]), missingNumber([0]), missingNumber([1]), missingNumber([1, 2]), missingNumber([0, 1]));
```

```text
2 1 0 0 2
```

시간 O(n), 공간 O(1)이다. 원소가 서로 다르다는 보장 덕분에 성립한다. 같은 수가 두 번 있으면 합이 엉뚱하게 늘어서 틀린다.

### 합이 넘치지 않게 차이만 쌓는다

JavaScript의 수는 2^53까지 정수를 정확히 담으니 이 문제의 범위에서는 걱정할 일이 없다. Java나 C++의 `int`라면 다르다. n이 65536만 돼도 `n * (n + 1)`이 2^31을 넘는다.

```java
class Overflow {
    public static void main(String[] args) {
        int n = 65536;
        int expected = n * (n + 1) / 2;          // int끼리 곱하다 넘친다
        long safe = (long) n * (n + 1) / 2;
        System.out.println(expected + " " + safe);
    }
}
```

```text
32768 2147516416
```

`int`로 계산한 값은 32768이라는 엉터리가 나온다. 예외도 경고도 없다. LeetCode 제약(n ≤ 10^4)에서는 5천만 정도라 넘지 않지만, 면접에서 "n이 더 크면?"이라고 물으면 이 지점을 짚어야 한다. 고치는 방법은 두 가지다. 하나는 `long`으로 계산하는 것이고, 다른 하나는 큰 합을 아예 만들지 않는 것이다.

두 번째 방법은 이렇다. 있어야 할 수와 있는 수를 하나씩 짝지어 그 차이만 쌓는다. i번째 단계에서 있어야 할 수 i를 더하고 있는 수 `nums[i]`를 뺀다. 인덱스로 나오지 않는 n은 처음에 넣어 둔다.

```js
function missingNumber(nums) {
  let acc = nums.length; // 인덱스로는 나오지 않는 n
  for (let i = 0; i < nums.length; i++) {
    acc += i - nums[i]; // 있어야 할 수 i를 더하고 있는 수를 뺀다
  }
  return acc;
}

console.log(missingNumber([3, 0, 4, 1, 5]), missingNumber([0]), missingNumber([1]), missingNumber([1, 2]), missingNumber([0, 1]));
```

```text
2 1 0 0 2
```

이 방식이 Java에서 안전한 이유는 조금 미묘하다. 누적값이 중간에 커질 수는 있다(큰 값이 앞에 몰리면 음수로 크게 내려간다). 그래도 Java의 `int`는 넘치면 2^32로 나눈 나머지로 돌고, 더하기와 빼기만 쓰면 중간에 몇 번 넘쳐도 최종 결과가 `int` 범위 안이기만 하면 맞는 값으로 돌아온다. 앞의 공식이 틀린 건 넘친 곱에 나눗셈 `/ 2`를 했기 때문이다. 나눗셈은 이 나머지 계산과 순서를 바꿀 수 없다. 넘침을 아예 생각하지 않아도 되는 쪽이 XOR다.

## 인덱스와 값을 함께 XOR한다

합 풀이는 "있어야 할 것을 더하고 있는 것을 뺀다"였다. XOR는 더하기와 빼기가 같은 연산이다. `a ^ b ^ b = a`라서 넣은 것을 다시 넣으면 빠진다. 그러니 있어야 할 수 0부터 n까지와 있는 수를 모두 한 그릇에 XOR하면, 두 번씩 들어간 수는 지워지고 한 번만 들어간 빠진 수만 남는다.

```text
있어야 할 수   0 1 2 3 4 5
있는 수        3 0 4 1 5
전부 XOR       (0^0)(1^1)(3^3)(4^4)(5^5) ^ 2 = 2
```

[Single Number](/posts/leetcode-single-number)에서는 짝이 배열 안에 이미 있었다. 여기서는 짝 한쪽(있어야 할 수)을 우리가 만들어 넣는다. 그 짝을 따로 만들 필요도 없다. 인덱스 0부터 n - 1이 그 역할을 하고, 남는 n 하나만 처음에 넣어 두면 된다.

```js
function missingNumber(nums) {
  let acc = nums.length; // 인덱스로는 나오지 않는 n을 먼저 넣는다
  for (let i = 0; i < nums.length; i++) {
    acc ^= i ^ nums[i]; // 있어야 할 수(인덱스)와 있는 수를 함께 섞는다
  }
  return acc; // 짝이 있는 수는 지워지고 빠진 수만 남는다
}

console.log(missingNumber([3, 0, 4, 1, 5]), missingNumber([0]), missingNumber([1]), missingNumber([1, 2]), missingNumber([0, 1]));
```

```text
2 1 0 0 2
```

시간은 O(n), 공간은 O(1)이다. 입력을 고치지 않고, 넘칠 걱정이 없다. XOR 결과는 0부터 n까지의 수들을 섞은 값이라 n의 비트 수를 넘지 않는다. 덧붙인 질문에 가장 깔끔하게 답하는 풀이다.

### n을 먼저 넣는 이유

인덱스는 0부터 n - 1까지라 n이 한 번도 들어가지 않는다. `acc`를 0으로 시작하면 n이 짝 없이 빠진 셈이 되어, 결과가 "빠진 수 ^ n"이 된다. 예시에서는 2 ^ 5 = 7이 나온다. 반복이 끝난 뒤 `acc ^ n`을 해도 같지만, 처음에 넣어 두면 잊을 일이 없다.

### Python과 Java

```python
from typing import List

class Solution:
    def missingNumber(self, nums: List[int]) -> int:
        acc = len(nums)              # 인덱스로는 나오지 않는 n을 먼저 넣는다
        for i, x in enumerate(nums):
            acc ^= i ^ x             # 인덱스와 값을 함께 섞는다
        return acc

    def missingNumberSum(self, nums: List[int]) -> int:
        n = len(nums)
        return n * (n + 1) // 2 - sum(nums)   # 정수 나눗셈 // 를 쓴다

s = Solution()
print(s.missingNumber([3, 0, 4, 1, 5]), s.missingNumber([0]), s.missingNumber([1]), s.missingNumber([0, 1]))
print(s.missingNumberSum([3, 0, 4, 1, 5]), s.missingNumberSum([0, 1]))
```

```text
2 1 0 2
2 2
```

Python의 정수는 크기 제한이 없어서 합 공식이 넘치지 않는다. 그래서 Python에서는 합 풀이가 가장 짧고 읽기 쉽다. 대신 `/`를 쓰면 실수가 나와 `2.0`처럼 돌려주니 정수 나눗셈 `//`를 쓴다. `enumerate`가 인덱스와 값을 함께 꺼내 주는 것도 Python에서 XOR 풀이를 짧게 만든다.

```java
class Solution {
    public int missingNumber(int[] nums) {
        int acc = nums.length;               // 인덱스로는 나오지 않는 n
        for (int i = 0; i < nums.length; i++) {
            acc ^= i ^ nums[i];              // 인덱스와 값을 함께 섞는다
        }
        return acc;
    }

    public int missingNumberSum(int[] nums) {
        int acc = nums.length;
        for (int i = 0; i < nums.length; i++) {
            acc += i - nums[i];              // 큰 합을 만들지 않고 차이만 쌓는다
        }
        return acc;
    }

    public static void main(String[] args) {
        Solution s = new Solution();
        System.out.println(s.missingNumber(new int[] { 3, 0, 4, 1, 5 }) + " " + s.missingNumber(new int[] { 0 }) + " " + s.missingNumber(new int[] { 0, 1 }));
        System.out.println(s.missingNumberSum(new int[] { 3, 0, 4, 1, 5 }) + " " + s.missingNumberSum(new int[] { 1 }));
    }
}
```

```text
2 1 2
2 0
```

Java에서는 합 공식을 `int`로 쓰면 앞에서 본 넘침이 생기니, 합으로 풀려면 차이를 쌓는 방식이나 `long`을 쓴다. XOR 풀이는 언어마다 거의 같은 모양이다.

## 백만 칸 배열에서 여섯 풀이를 재 보면

| 풀이 | 시간 | 추가 공간 | 언제 고르나 |
|---|---|---|---|
| 후보마다 배열 훑기 | O(n²) | O(1) | 출발점. 설명용 |
| 정렬 후 첫 어긋남 | O(n log n) | O(1)~O(n) | 이미 정렬돼 있다면 이진 탐색으로 바꾼다 |
| 해시 집합 | O(n) | O(n) | 빠진 수가 여럿이거나 중복이 섞일 수 있을 때 |
| 순환 정렬 | O(n) | O(1), 입력 변경 | 합·XOR가 안 통하는 변형(41번 등) |
| 합 공식 / 차이 쌓기 | O(n) | O(1) | 설명이 가장 쉽다. 고정 폭 정수면 넘침 주의 |
| 인덱스와 값 XOR | O(n) | O(1) | 기본 답. 넘침도 입력 변경도 없다 |

0부터 1,000,000까지에서 777777을 빼고 무작위로 섞은 배열로 풀이마다 다섯 번 돌려 가장 빠른 시간을 쟀다(Node.js 22). 브루트포스는 앞에서 따로 쟀다(n = 20000에서 226ms).


같은 O(n)인데 해시 집합은 120ms, 순환 정렬은 40ms, 합과 XOR는 1ms가 안 된다. 해시 집합은 백만 개의 원소를 넣느라 메모리를 할당하고 해시를 계산한다. 순환 정렬은 배열을 복사하고, 맞바꾸기가 배열 여기저기를 건드려 캐시를 잘 못 쓴다. 합과 XOR는 배열을 앞에서부터 한 번 읽으며 변수 하나만 고친다. 합과 XOR 사이의 차이는 측정 오차 수준이다. 둘 중 무엇을 고를지는 속도가 아니라 넘침 걱정과 설명하기 쉬운 쪽으로 정한다.

## 빈칸이 끝에 있거나 처음에 있을 때

### n이 빠진 배열

`[0, 1]`은 2가 빠졌다. 정렬 풀이에서 반복이 끝까지 맞으면 빠진 수는 n인데, 이 경우를 빼먹으면 이렇게 된다.

```js
    if (a[i] !== i) return i;
  }
  // 끝까지 맞으면? 아무것도 돌려주지 않는다
}
```

LeetCode에 내면 오답이다. 순환 정렬도 마지막 `return n`이 같은 역할을 한다. 해시 집합 풀이는 반복을 `k <= n`까지 돌아야 n을 확인한다. `k < n`으로 쓰면 같은 버그가 난다.

### 0이 빠진 배열

`[1]`이나 `[1, 2]`는 0이 빠졌다. 정렬 풀이는 0번 칸에서 바로 어긋나 0을 돌려준다. 합 풀이는 있어야 할 합과 실제 합이 같아 보이지 않을까 걱정되지만, `[1, 2]`의 있어야 할 합은 0 + 1 + 2 = 3, 실제 합도 3이라 답 0이 맞게 나온다. 0은 더해도 합이 그대로라 차이가 정확히 0으로 나온다.

정답은 2, 2, 1이다. 앞에서 말한 대로 n이 짝 없이 빠져서 "빠진 수 ^ n"이 나온다. n이 1 이상이라 "빠진 수 ^ n"이 빠진 수와 같아지는 입력은 없다. 그래서 테스트 하나만 돌려도 잡히는 버그지만, `[0]`에서 0이 나오면 "0이 빠졌나" 하고 그럴듯하게 넘어가기 쉽다. n이 빠진 경우와 0이 빠진 경우를 함께 테스트한다.

## 정렬돼 있거나, 빈칸이 둘이거나, 중복이 섞이면

### 배열이 이미 정렬돼 있다면

정렬된 배열이면 O(n)도 아깝다. 빠진 수 앞에서는 `a[i] === i`이고, 그 뒤에서는 모든 값이 한 칸씩 밀려 `a[i] === i + 1`이다. "값이 인덱스와 같은가"가 참에서 거짓으로 한 번만 바뀌니 [이진 탐색](/posts/binary-search)으로 바뀌는 첫 지점을 찾는다.

```js
function missingSorted(a) {
  let lo = 0, hi = a.length; // 답은 0부터 n까지라 hi를 n으로 둔다
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    if (a[mid] === mid) lo = mid + 1; // 여기까지는 온전하다 → 빠진 수는 오른쪽
    else hi = mid;                     // 이미 밀렸다 → 빠진 수는 mid 이하
  }
  return lo;
}
console.log(missingSorted([0, 1, 2, 4, 5]), missingSorted([1, 2, 3]), missingSorted([0, 1, 2]));
```

```text
3 0 3
```

`hi`를 `a.length - 1`이 아니라 `a.length`로 두는 게 요점이다. `[0, 1, 2]`처럼 n이 빠지면 답이 배열 밖 인덱스 3이기 때문이다. 시간 O(log n), 공간 O(1)이다.

### 빠진 수가 둘이라면

0부터 n + 1까지에서 둘이 빠진 배열이면, 전부 XOR한 값은 두 빠진 수의 XOR다. [Single Number](/posts/leetcode-single-number#외톨이가-둘이라면)의 외톨이 둘 변형과 똑같이 푼다. 그 값에서 켜진 비트 하나를 골라, 그 비트가 켜진 무리와 꺼진 무리로 나눠 따로 XOR한다.

```js
function twoMissing(nums) {
  const n = nums.length + 2; // 있어야 할 수는 0부터 n - 1까지
  let both = 0;
  for (let v = 0; v < n; v++) both ^= v;
  for (const x of nums) both ^= x;   // 두 빠진 수의 XOR
  const bit = both & -both;          // 두 수가 다른 자리 하나
  let a = 0;
  for (let v = 0; v < n; v++) if (v & bit) a ^= v;
  for (const x of nums) if (x & bit) a ^= x;
  return [a, both ^ a].sort((x, y) => x - y);
}
console.log(JSON.stringify(twoMissing([0, 1, 3, 5])), JSON.stringify(twoMissing([2, 3])));
```

```text
[2,4] [0,1]
```

합으로 풀려면 식이 두 개 필요하다. 합의 차이로 a + b를, 제곱합의 차이로 a² + b²를 얻어 연립방정식을 푼다. 가능하지만 제곱합은 금방 넘쳐서 XOR 쪽이 깔끔하다.

### 하나는 두 번, 하나는 빠졌다면

LeetCode 645. Set Mismatch는 1부터 n까지에서 한 수가 두 번 나오고 한 수가 빠진다. 원소가 서로 다르다는 전제가 깨졌으니 합 하나로는 부족하다. 합 차이는 "빠진 수 - 중복 수"를 준다. 해시 집합으로 중복을 찾아 합 차이에 더하거나, 순환 정렬로 제자리를 찾은 뒤 주인이 아닌 칸의 값(중복)과 인덱스(빠진 수)를 함께 읽는다. XOR로도 풀리지만 위의 둘 변형처럼 무리를 나눠야 해서 길어진다.

### 수가 아주 많아 메모리에 다 올릴 수 없다면

파일에서 숫자를 한 줄씩 읽는 상황이라면 합이나 XOR가 그대로 통한다. 값을 하나 읽을 때마다 누적값만 고치면 되고, 몇 번째 줄인지(인덱스)는 세면 된다. 해시 집합이나 정렬은 전부 메모리에 올려야 해서 쓸 수 없다. 다만 "정확히 하나만 빠지고 중복은 없다"는 보장이 있어야 한다. 데이터가 깨져서 중복이 섞이면 합도 XOR도 조용히 틀린 값을 낸다. 보장이 없으면 범위를 나눠 여러 번 읽으며 구간마다 개수를 세는 방식(구간마다 개수가 모자라는 곳으로 좁혀 가기)을 쓴다.

## 면접에서 나올 만한 질문

### 공간 O(1)로 빠진 수를 찾는 방법은 무엇인가요?

두 가지가 있다. 0부터 n까지의 합 n(n + 1) / 2에서 배열의 합을 빼거나, n과 모든 인덱스와 모든 값을 XOR한다. 둘 다 시간 O(n), 공간 O(1)이고 입력을 고치지 않는다. 순환 정렬도 O(1) 공간이지만 입력을 바꾼다.

### 합 풀이와 XOR 풀이 중 무엇이 더 나은가요?

속도는 거의 같다. 차이는 넘침이다. 합 풀이는 고정 폭 정수 언어에서 n이 커지면 곱셈이 넘치고, XOR는 결과가 n의 비트 수를 넘지 않아 넘칠 일이 없다. Python처럼 정수에 끝이 없으면 합 풀이가 더 읽기 쉽고, Java라면 XOR나 차이 쌓기를 고른다.

### XOR 풀이에서 acc를 왜 n으로 시작하나요?

인덱스는 0부터 n - 1까지라 있어야 할 수 중 n만 빠지기 때문이다. 0으로 시작하면 결과가 "빠진 수 ^ n"이 된다. 처음에 n을 넣어 두면 0부터 n까지가 모두 한 번씩 들어간다.

### 합 공식이 Java에서 틀릴 수 있나요?

`int`로 `n * (n + 1) / 2`를 계산하면 n이 65536일 때 이미 넘쳐서 엉뚱한 값이 나온다. `long`으로 바꾸거나, 큰 합을 만들지 않고 `acc += i - nums[i]`로 차이만 쌓는다. LeetCode 제약 n ≤ 10^4에서는 넘치지 않지만 n이 커질 수 있다면 짚어야 한다.

### 배열이 정렬돼 있으면 어떻게 하나요?

이진 탐색으로 O(log n)에 찾는다. 빠진 수 앞에서는 값과 인덱스가 같고 뒤에서는 값이 인덱스보다 1 크다. `a[mid] === mid`면 오른쪽, 아니면 왼쪽으로 좁힌다. n이 빠질 수 있으니 탐색 범위의 끝을 배열 길이로 둔다.

### 중복이 있을 수 있다면 합 풀이가 여전히 맞나요?

맞지 않는다. 합과 XOR는 원소가 서로 다르고 정확히 하나만 빠졌다는 전제에 기댄다. 중복이 섞이면 조용히 틀린 값을 낸다. 전제를 믿을 수 없으면 해시 집합이나 순환 정렬로 바꾸고, 하나 중복·하나 빠짐(645번)은 합 차이와 중복 찾기를 함께 쓴다.

### 빠진 수가 두 개라면요?

전체를 XOR하면 두 빠진 수의 XOR가 남는다. 거기서 켜진 비트 하나를 골라, 그 비트 기준으로 있어야 할 수와 있는 수를 두 무리로 나눠 각각 XOR하면 하나씩 나온다. 합과 제곱합으로 연립방정식을 세워도 되지만 제곱합이 쉽게 넘친다.
