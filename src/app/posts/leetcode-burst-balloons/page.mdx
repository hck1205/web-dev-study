[LeetCode 312. Burst Balloons](https://leetcode.com/problems/burst-balloons/)는 Hard 문제 중에서도 "처음 보면 손을 못 대는" 문제로 꼽힌다. 점화식 자체는 짧은데, 그 점화식을 떠올리려면 생각의 방향을 한 번 뒤집어야 하기 때문이다. 면접에서도 답을 외웠는지보다 "왜 첫 번째가 아니라 마지막을 고르나"를 설명할 수 있는지를 본다.

이 글은 풀이 다섯 개를 느린 것부터 놓는다. 모든 순서를 다 해 보기, 남은 풍선 집합을 기억하는 비트마스크 DP, 첫 번째로 터뜨릴 풍선을 고르는 (틀린) 시도, 마지막 풍선을 고르는 구간 DP의 탑다운과 바텀업이다. 앞의 2차원 DP 문제들([Unique Paths](/posts/leetcode-unique-paths), [Longest Common Subsequence](/posts/leetcode-longest-common-subsequence))은 표의 두 축이 "격자의 행과 열", "두 문자열"이었다. 여기서는 두 축이 한 배열 위 구간의 왼쪽 끝과 오른쪽 끝이다. 이런 모양을 구간 DP라고 부른다. DP 일반은 [동적 계획법 글](/posts/dynamic-programming)에 있다. 코드는 모두 Node.js 22, Python 3, Java 21에서 돌렸다.

## 터뜨리면 이웃이 바뀐다

정수 배열 `nums`가 풍선 n개의 숫자다. i번 풍선을 터뜨리면 `nums[i-1] × nums[i] × nums[i+1]`점을 얻는다. 여기서 i-1과 i+1은 지금 남아 있는 풍선 중 바로 왼쪽과 오른쪽이다. 배열 밖은 숫자 1인 풍선이 있다고 본다. 모든 풍선을 터뜨려 얻을 수 있는 점수의 최댓값을 돌려준다.

- n은 1 이상 300 이하다.
- 각 숫자는 0 이상 100 이하다.

n이 300이라 O(n³)이면 450만 번 남짓으로 넉넉하고, O(2^n)이나 O(n!)은 불가능하다. 숫자에 0이 있을 수 있다는 점도 챙긴다. 0은 터뜨려도 0점이고, 이웃에 0이 있으면 그 곱도 0이다.

## 2, 4, 3, 5를 손으로 터뜨려 보기

예시로 `nums = [2, 4, 3, 5]`를 쓴다. 몇 가지 순서를 해 본다.

```text
왼쪽부터 차례로:  2 → 1×2×4 = 8   [4,3,5]
                  4 → 1×4×3 = 12  [3,5]
                  3 → 1×3×5 = 15  [5]
                  5 → 1×5×1 = 5   []        합 40

가운데 3부터:     3 → 4×3×5 = 60  [2,4,5]
                  4 → 2×4×5 = 40  [2,5]
                  2 → 1×2×5 = 10  [5]
                  5 → 1×5×1 = 5   []        합 115
```

순서에 따라 40과 115로 세 배 가까이 차이가 난다. 115가 최댓값이다. 잘 된 순서를 보면 큰 숫자 5가 마지막까지 남아 여러 번 곱해지는 쪽으로 쓰이고, 작은 숫자들이 먼저 터지면서 5를 이웃으로 삼는다.

그럼 "작은 것부터 터뜨린다"가 정답일까. `[1, 2, 3]`에서 해 보면 1(1×1×2 = 2), 2(1×2×3 = 6), 3(3) 순서로 11점인데, 2를 먼저 터뜨리면(1×2×3 = 6) 남은 `[1, 3]`에서 1(1×1×3 = 3), 3(3)으로 12점이다. "지금 가장 많이 주는 것부터"도 `[0, 1, 2]`에서 틀린다. 처음에 2가 2점으로 가장 크지만, 0을 먼저 치우고 1을 2 옆에서 터뜨려야 4점이 된다. 지금의 선택이 이웃을 바꿔 뒤의 점수를 바꾸니, 눈앞의 이득만 보는 [그리디](/posts/greedy-algorithms)는 통하지 않는다.

## 모든 순서를 다 해 보기

정직하게 모든 순서를 시도한다. 남은 풍선 중 하나를 골라 터뜨리고, 남은 배열로 다시 같은 일을 한다.

```js
function maxCoins(nums) {
  let best = 0;
  function go(arr, coins) {
    if (arr.length === 0) { best = Math.max(best, coins); return; }
    for (let i = 0; i < arr.length; i++) {
      const left = i > 0 ? arr[i - 1] : 1, right = i < arr.length - 1 ? arr[i + 1] : 1;
      go([...arr.slice(0, i), ...arr.slice(i + 1)], coins + left * arr[i] * right); // i를 터뜨린 뒤
    }
  }
  go(nums, 0);
  return best;
}
console.log(maxCoins([2, 4, 3, 5])); // 115
```

순서는 n!가지이고, 매번 배열을 새로 만드니 O(n · n!)이다. 재 보면 n = 9에서 97 ms, n = 10에서 716 ms다. n이 1 늘 때마다 7~10배씩 뛰어서 12쯤에서 이미 쓸 수 없다. [순열 생성](/posts/leetcode-permutations)과 같은 크기의 탐색이다.

## 남은 풍선 집합을 기억하기

순서가 달라도 "지금 남아 있는 풍선이 같으면" 앞으로 얻을 수 있는 최대 점수는 같다. 2를 먼저 터뜨리고 4를 터뜨렸든, 4를 먼저 터뜨리고 2를 터뜨렸든 남은 게 `[3, 5]`이면 같은 상황이다. 남은 풍선 집합을 n비트 정수(비트마스크)로 나타내 메모한다.

```js
function maxCoins(nums) {
  const n = nums.length;
  const memo = new Map();
  function go(mask) {              // mask의 i번째 비트가 1이면 i번 풍선이 남아 있다
    if (mask === 0) return 0;
    if (memo.has(mask)) return memo.get(mask);
    let best = 0;
    for (let i = 0; i < n; i++) {
      if (!(mask & (1 << i))) continue;
      let l = i - 1; while (l >= 0 && !(mask & (1 << l))) l--;  // 남은 것 중 왼쪽 이웃
      let r = i + 1; while (r < n && !(mask & (1 << r))) r++;   // 남은 것 중 오른쪽 이웃
      const gain = (l >= 0 ? nums[l] : 1) * nums[i] * (r < n ? nums[r] : 1);
      best = Math.max(best, gain + go(mask & ~(1 << i)));
    }
    memo.set(mask, best);
    return best;
  }
  return go((1 << n) - 1);
}
```

상태는 2^n개이고 상태마다 n개의 풍선을 보며 이웃을 찾으니 O(2^n · n²)이다. n! 대신 2^n이라 훨씬 낫다. n = 18에서 139 ms, n = 20에서 1.1초였다. 하지만 300은 어림도 없다. `1 << i`는 i가 31 이상이면 깨진다는 문제도 있다.

여기까지 오면 막힌다. 상태를 "어느 풍선이 남았나"로 잡는 한 상태 수가 지수다. 남은 풍선이 아무 모양이나 될 수 있기 때문이다. 상태를 "구간" 하나로 줄일 방법이 필요하다.

## 처음 터뜨릴 풍선으로 나누면 안 되는 이유

구간 DP의 흔한 틀은 "구간 `[i, j]`에서 무언가 하나를 고르고, 양쪽 구간으로 나눈다"이다. 그대로 해 본다. 구간에서 처음 터뜨릴 풍선 k를 고르면 점수는 `nums[k-1] × nums[k] × nums[k+1]`이고, 남은 일은 `[i, k-1]`과 `[k+1, j]`를 터뜨리는 것이다.

문제는 두 구간이 독립이 아니라는 것이다. k가 사라지면 `nums[k-1]`과 `nums[k+1]`이 이웃이 된다. 왼쪽 구간의 오른쪽 끝 풍선을 터뜨릴 때 이웃은 오른쪽 구간의 풍선이고, 그게 아직 남았는지는 오른쪽 구간을 어떤 순서로 터뜨렸는지에 달렸다. 두 구간을 따로 풀 수가 없다.

억지로 따로 푼다고 치고 코드를 짜면 답이 틀린다.

```js
function wrongFirst(nums) {
  const n = nums.length, memo = new Map();
  const v = (x) => (x < 0 || x >= n ? 1 : nums[x]);
  function go(i, j) {
    if (i > j) return 0;
    const key = i + "," + j;
    if (memo.has(key)) return memo.get(key);
    let b = 0;
    for (let k = i; k <= j; k++)  // k를 처음에 터뜨린다고 치고 양쪽을 "따로" 푼다 (틀림)
      b = Math.max(b, v(k - 1) * nums[k] * v(k + 1) + go(i, k - 1) + go(k + 1, j));
    memo.set(key, b);
    return b;
  }
  return go(0, n - 1);
}
console.log(wrongFirst([2, 4, 3, 5])); // 107 (답은 115)
```

107은 실제로 만들 수 없는 순서의 점수일 수도 있고, 만들 수 있는 더 좋은 순서를 놓친 결과일 수도 있다. 어느 쪽이든 부분 문제의 정의가 실제 상황과 맞지 않으면 DP는 틀린다.

## 마지막에 터뜨릴 풍선으로 나눈다

방향을 뒤집는다. 구간에서 맨 마지막에 터뜨릴 풍선 k를 고른다.

k가 마지막이라는 건, k가 터지는 순간 구간 안의 다른 풍선은 모두 사라졌다는 뜻이다. 그러면 k의 이웃은 구간 바깥의 양 끝 풍선으로 정해진다. 더 중요한 건 k가 터지기 전까지다. k는 끝까지 남아 있으니 왼쪽 무리와 오른쪽 무리 사이에 벽처럼 서 있다. 왼쪽 무리의 풍선이 아무리 터져도 오른쪽 이웃은 k이거나 왼쪽 무리 안의 풍선이다. 오른쪽 무리도 마찬가지다. 두 무리는 서로 영향을 주지 않는다.

이걸 식으로 쓰려면 경계 풍선을 구간에 포함해 두는 게 편하다.

1. 배열 양 끝에 1을 붙인다. `a = [1, ...nums, 1]`. 붙인 풍선은 절대 터뜨리지 않는다.
2. `dp[l][r]`을 "l과 r은 남겨 두고, 그 사이(열린 구간)의 풍선을 모두 터뜨려 얻는 최대 점수"로 정의한다.
3. 사이에서 마지막으로 남는 풍선을 k라고 하면, 왼쪽 무리 `(l, k)`와 오른쪽 무리 `(k, r)`을 먼저 다 터뜨리고, 마지막에 k를 터뜨린다. 그때 k의 이웃은 l과 r이다.

```text
dp[l][r] = max over l < k < r of  dp[l][k] + a[l] × a[k] × a[r] + dp[k][r]
dp[l][l+1] = 0   (사이에 풍선이 없다)
답 = dp[0][n+1]
```

k가 양쪽 부분 문제에서 "남겨 두는 끝"으로 쓰인다는 점이 열린 구간 정의의 장점이다. 왼쪽 무리는 l과 k 사이, 오른쪽 무리는 k와 r 사이라서 k를 끝으로 둔 같은 모양의 문제가 된다.

이 분할이 빠뜨리는 순서가 없는지도 짚어 둔다. 구간 `(l, r)` 사이의 풍선을 터뜨리는 어떤 순서든 마지막에 터지는 풍선이 하나 있다. 그 풍선을 k라고 하면, 그 순서에서 k보다 왼쪽에 있던 풍선들이 터지는 차례만 뽑아 보면 `(l, k)`를 터뜨리는 하나의 순서가 되고, 오른쪽도 마찬가지다. 왼쪽 풍선이 터질 때 이웃은 l, k, 또는 왼쪽 무리 안의 풍선뿐이라 오른쪽 무리가 언제 터졌는지와 상관없이 점수가 같다. 그러니 모든 순서의 점수는 알맞은 k 하나를 골라 "왼쪽 순서의 점수 + 오른쪽 순서의 점수 + `a[l]·a[k]·a[r]`"로 쓸 수 있고, 각 부분을 최대로 고르면 전체가 최대다. 반대로 왼쪽과 오른쪽 순서를 아무렇게나 섞은 뒤 k를 마지막에 두면 실제로 가능한 순서가 되니, 이 식이 만들 수 없는 점수를 지어내지도 않는다.

## 위에서 내려가는 구간 DP

점화식을 메모이제이션으로 옮긴다.

```js
function maxCoins(nums) {
  const a = [1, ...nums, 1];          // 양 끝의 가짜 풍선
  const n = a.length;
  const memo = Array.from({ length: n }, () => new Array(n).fill(-1)); // -1 = 아직 모름
  function go(l, r) {                 // l과 r은 남기고 그 사이를 모두 터뜨린다
    if (l + 1 === r) return 0;        // 사이에 풍선이 없다
    if (memo[l][r] !== -1) return memo[l][r];
    let best = 0;
    for (let k = l + 1; k < r; k++)   // k를 이 구간에서 마지막으로 터뜨린다
      best = Math.max(best, go(l, k) + a[l] * a[k] * a[r] + go(k, r));
    return (memo[l][r] = best);
  }
  return go(0, n - 1);
}
console.log(maxCoins([2, 4, 3, 5])); // 115
```

상태는 `(l, r)` 쌍이라 O(n²)개, 상태마다 k를 O(n)개 보니 시간은 O(n³)이다. 공간은 메모 O(n²)에 재귀 깊이 O(n)이다. 여기서도 "모름" 표시는 `-1`이다. 0이 섞인 배열에서는 0점이 정상 답인 구간이 흔하다.

재귀 깊이는 n + 2 정도라 Python 기본 한도 1000 안이다. 다만 Python에서 재귀 호출이 450만 번 쌓이면 느리다. 아래 바텀업이 더 낫다.

## 짧은 구간부터 채우는 바텀업

`dp[l][r]`은 `dp[l][k]`와 `dp[k][r]`을 쓰는데, 둘 다 `(l, r)`보다 짧은 구간이다. 그러니 구간 길이 순서로 채우면 필요한 값이 늘 먼저 있다.

```js
function maxCoins(nums) {
  const a = [1, ...nums, 1];
  const n = a.length;
  const dp = Array.from({ length: n }, () => new Array(n).fill(0)); // 길이 1(이웃한 두 끝)은 0
  for (let len = 2; len < n; len++) {           // r - l = len. 사이에 풍선이 len - 1개
    for (let l = 0; l + len < n; l++) {
      const r = l + len;
      for (let k = l + 1; k < r; k++)           // k를 마지막으로 터뜨린다
        dp[l][r] = Math.max(dp[l][r], dp[l][k] + a[l] * a[k] * a[r] + dp[k][r]);
    }
  }
  return dp[0][n - 1];
}
```

아래 그림은 `[2, 4, 3, 5]`에 양 끝 1을 붙인 배열 위에서 몇 개의 구간이 채워지는 모습이다. 초록 칸은 구간의 양 끝(남겨 두는 풍선), 가리키는 칸은 마지막으로 터뜨리는 k다.

### 0은 미리 빼도 된다

숫자가 0인 풍선은 터뜨려도 0점이고, 이웃에 있으면 곱을 0으로 만든다. 0을 처음에 모두 터뜨려 없애면 그 이웃들은 0 대신 0보다 큰 수를 이웃으로 갖게 되니 점수가 줄 일이 없다. 그래서 `nums.filter(x => x > 0)`로 미리 빼도 답이 같다. 길이 7 이하 무작위 배열 3000개로 확인했다. 0이 많은 입력에서는 n이 줄어 O(n³)이 크게 빨라진다.

### 터뜨린 순서 되짚기

어떤 순서로 터뜨렸는지 알려면 구간마다 고른 k를 따로 적어 두고, 전체 구간에서부터 "왼쪽 무리, 오른쪽 무리, 그다음 k" 순서로 펼친다.

```js
function burstOrder(nums) {
  const a = [1, ...nums, 1];
  const n = a.length;
  const dp = Array.from({ length: n }, () => new Array(n).fill(0));
  const last = Array.from({ length: n }, () => new Array(n).fill(-1)); // 구간에서 마지막으로 터뜨린 풍선
  for (let len = 2; len < n; len++)
    for (let l = 0; l + len < n; l++) {
      const r = l + len;
      for (let k = l + 1; k < r; k++) {
        const v = dp[l][k] + a[l] * a[k] * a[r] + dp[k][r];
        if (v > dp[l][r]) { dp[l][r] = v; last[l][r] = k; }
      }
    }
  const order = [];
  (function walk(l, r) {
    if (l + 1 >= r) return;
    const k = last[l][r];
    if (k === -1) { for (let x = l + 1; x < r; x++) order.push(x - 1); return; } // 모든 선택이 0점: 아무 순서나
    walk(l, k); walk(k, r);          // 양쪽 구간을 먼저 다 터뜨리고
    order.push(k - 1);               // k를 마지막에 (원래 배열의 인덱스로)
  })(0, n - 1);
  return { coins: dp[0][n - 1], order };
}
console.log(burstOrder([2, 4, 3, 5]));
```

## Python과 Java의 구간 DP

```python
from typing import List

class Solution:
    def maxCoins(self, nums: List[int]) -> int:
        a = [1] + [x for x in nums if x > 0] + [1]   # 0은 미리 빼도 답이 같다
        n = len(a)
        dp = [[0] * n for _ in range(n)]             # dp[l][r]: 열린 구간 (l, r)
        for length in range(2, n):
            for l in range(0, n - length):
                r = l + length
                al_ar = a[l] * a[r]
                row_l = dp[l]
                best = 0
                for k in range(l + 1, r):            # k를 마지막으로 터뜨린다
                    v = row_l[k] + al_ar * a[k] + dp[k][r]
                    if v > best:
                        best = v
                row_l[r] = best
        return dp[0][n - 1]

s = Solution()
print(s.maxCoins([2, 4, 3, 5]), s.maxCoins([7]), s.maxCoins([5, 0, 5]))
```

```text
115 7 30
```

Python에서는 450만 번의 안쪽 반복이 그대로 시간이다. 길이 300짜리 입력에서 이 코드가 0.48초, 모두 100인 입력에서 0.5초였다. 반복문 안에서 `a[l] * a[r]`과 `dp[l]`을 미리 꺼내 두고, `max()` 함수 호출 대신 `if` 비교를 쓴 것이 그 때문이다. 함수 호출과 이중 인덱싱이 Python에서는 꽤 비싸다. `lru_cache` 탑다운은 같은 일을 하면서 호출 오버헤드가 붙어 더 느리다.

```java
class Solution {
    public int maxCoins(int[] nums) {
        int n = nums.length + 2;
        int[] a = new int[n];
        a[0] = a[n - 1] = 1;                          // 양 끝에 가짜 풍선 1
        for (int i = 0; i < nums.length; i++) a[i + 1] = nums[i];
        int[][] dp = new int[n][n];                   // dp[l][r]: 열린 구간 (l, r)
        for (int len = 2; len < n; len++) {
            for (int l = 0; l + len < n; l++) {
                int r = l + len;
                for (int k = l + 1; k < r; k++)       // k를 마지막으로 터뜨린다
                    dp[l][r] = Math.max(dp[l][r], dp[l][k] + a[l] * a[k] * a[r] + dp[k][r]);
            }
        }
        return dp[0][n - 1];
    }

    public static void main(String[] args) {
        Solution s = new Solution();
        System.out.println(s.maxCoins(new int[] { 2, 4, 3, 5 }) + " " + s.maxCoins(new int[] { 7 }) + " " + s.maxCoins(new int[] { 5, 0, 5 }));
        int[] big = new int[300];
        java.util.Arrays.fill(big, 100);
        System.out.println(s.maxCoins(big));
    }
}
```

```text
115 7 30
298010100
```

Java에서는 `int`로 충분한지 따져야 한다. 한 번에 얻는 점수는 많아야 100 × 100 × 100 = 10^6이고 풍선은 300개라 합은 3×10^8을 넘지 않는다. 실제로 모두 100인 300개에서 298,010,100이 나왔다. `int` 최댓값 약 2.1×10^9 안이다. 숫자 상한이 1000이었다면 한 번에 10^9이라 `long`이 필요했을 것이다.

## 다섯 접근 비교

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 모든 순서 | O(n · n!) | O(n²) | n이 8 이하. 다른 풀이 검증용 |
| 남은 집합 비트마스크 | O(2^n · n²) | O(2^n) | n이 20 이하이고 구간 구조를 못 찾았을 때 |
| 처음 터뜨릴 풍선으로 나누기 | 틀림 | | 왜 안 되는지 설명할 수 있어야 한다 |
| 마지막 풍선 탑다운 | O(n³) | O(n²) | 점화식을 그대로 옮기기 쉽다 |
| 마지막 풍선 바텀업 | O(n³) | O(n²) | 기본 답. Python에서도 시간 안에 든다 |

공간을 더 줄이는 방법은 없다. 구간 `(l, r)`이 쓰는 칸이 같은 행 l의 왼쪽과 같은 열 r의 아래쪽 전체라서, 앞 문제들처럼 한 줄만 남길 수 없다. O(n³)을 일반적으로 줄이는 잘 알려진 방법도 이 문제에는 없다.

## 이 문제에서 실제로 틀리는 곳

### 양 끝 1을 빼먹는 경우

`a = [1, ...nums, 1]`을 만들지 않고 `nums` 위에서 바로 구간을 잡으면, 실제 풍선이 "남겨 두는 끝"이 되어 끝까지 터지지 않는다. `[7]` 하나만 있어도 답 7 대신 0이 나온다. 가짜 풍선 두 개는 "배열 밖은 1"이라는 규칙을 표현하면서, 동시에 모든 실제 풍선을 열린 구간 안에 넣어 준다.

### 닫힌 구간과 열린 구간을 섞는 경우

닫힌 구간 `[i, j]`로 정의해도 된다. 그때는 마지막 풍선 k의 이웃이 `nums[i-1]`과 `nums[j+1]`(구간 바로 바깥)이고, 부분 문제는 `[i, k-1]`과 `[k+1, j]`다. 이 정의도 `[2, 4, 3, 5]`에서 115를 낸다. 두 정의 중 하나를 골라 끝까지 지키면 되는데, 섞어 쓰면 k가 양쪽 부분 문제에 들어가거나 빠져서 틀린다.

```js
function maxCoinsClosed(nums) {
  const n = nums.length, memo = new Map();
  const v = (x) => (x < 0 || x >= n ? 1 : nums[x]);   // 배열 밖은 1
  function go(i, j) {                                  // 닫힌 구간 [i, j]를 모두 터뜨린다
    if (i > j) return 0;
    const key = i + "," + j;
    if (memo.has(key)) return memo.get(key);
    let b = 0;
    for (let k = i; k <= j; k++)                       // k가 마지막: 이웃은 i-1과 j+1
      b = Math.max(b, go(i, k - 1) + v(i - 1) * nums[k] * v(j + 1) + go(k + 1, j));
    memo.set(key, b);
    return b;
  }
  return go(0, n - 1);
}
console.log(maxCoinsClosed([2, 4, 3, 5])); // 115
```

앞의 틀린 "처음 터뜨리기" 코드와 비교하면 곱하는 이웃만 다르다. 그쪽은 `v(k - 1)`과 `v(k + 1)`, 이쪽은 `v(i - 1)`과 `v(j + 1)`이다. 한 줄 차이가 107과 115를 가른다. 열린 구간은 바깥 경계를 `a`에 미리 넣어 두어서 `v` 같은 경계 검사가 필요 없고 코드가 짧다.

### 반복 순서

앞에서 본 대로 l을 작은 쪽부터 돌리면 안 채워진 칸을 쓴다. 길이 순서, 또는 l 내림차순 + r 오름차순이다.

### 그리디나 "처음 터뜨릴 것"으로 접근하는 경우

작은 것부터는 `[1, 2, 3]`에서 11(답 12), 지금 가장 많이 주는 것부터는 `[0, 1, 2]`에서 3(답 4)이 나온다. 처음 터뜨릴 것으로 나누는 DP는 `[2, 4, 3, 5]`에서 107이다. 면접에서 처음 떠오르는 생각이 이것들이라, 반례를 하나씩 들 수 있으면 "왜 마지막인가"를 설득력 있게 말할 수 있다.

## 같은 생각으로 풀리는 구간 문제들

### 막대를 자르는 비용

LeetCode 1547. Minimum Cost to Cut a Stick은 자를 위치 목록이 주어지고, 자를 때마다 지금 막대 길이만큼 비용이 든다. 여기서는 "처음 자르는 위치"로 나눠도 된다. 한 번 자르면 두 조각이 정말로 독립이기 때문이다. 자를 위치 양 끝에 0과 막대 길이를 붙이고 `dp[l][r] = min(dp[l][k] + dp[k][r]) + (c[r] - c[l])`이다. 풍선과 모양이 거의 같은데 "처음"과 "마지막"이 다른 이유를 설명할 수 있으면 구간 DP를 이해한 것이다. 풍선은 터지면 이웃이 바뀌어 처음을 고르면 양쪽이 엮이고, 막대는 자르면 양쪽이 바로 떨어진다.

### 행렬을 곱하는 순서

행렬 여러 개를 곱할 때 괄호를 어디에 치느냐에 따라 곱셈 횟수가 크게 달라진다. 행렬 연쇄 곱셈은 "마지막에 곱하는 위치 k"로 나누는 구간 DP이고, 점화식이 풍선과 똑같다. `dp[l][r] = min(dp[l][k] + dp[k][r] + d[l]·d[k]·d[r])`. 사실 풍선 문제는 이 고전 문제를 max로 뒤집어 놓은 것이라고 봐도 된다. 같은 O(n³) 틀에 들어가는 문제로 다각형 삼각분할(LeetCode 1039. Minimum Score Triangulation of Polygon)도 있다.

### 같은 색을 모아서 지우기

LeetCode 546. Remove Boxes는 같은 색 상자 k개를 한 번에 지우면 k²점을 받는다. 구간 `(l, r)`만으로는 부족하고 "l 왼쪽에 같은 색이 몇 개 붙어 있나"를 상태에 하나 더 넣어 3차원 DP가 된다. 이웃이 바뀌는 문제에서 상태를 무엇으로 잡느냐가 늘 관건이라는 것을 보여 주는 예다.

### 다른 2차원 DP와 비교하면

[Unique Paths](/posts/leetcode-unique-paths)와 [Edit Distance](/posts/leetcode-edit-distance)는 칸마다 이웃 몇 칸만 봐서 O(1)에 채우고, 한 줄로 공간을 줄일 수 있었다. 구간 DP는 칸마다 분할점 k를 O(n)개 봐서 O(n³)이고, 공간도 줄지 않는다. 문자열 매칭에서 패턴의 `*`가 여러 글자를 먹을 수 있는 [Regular Expression Matching](/posts/leetcode-regular-expression-matching)은 다시 칸마다 O(1)인 쪽에 속한다.

## 면접에서 나올 만한 질문

### 왜 처음이 아니라 마지막에 터뜨릴 풍선을 고르나요?

처음 터뜨린 풍선으로 나누면 그 풍선이 사라지면서 양쪽 끝 풍선이 이웃이 되어, 두 구간의 점수가 서로의 터뜨리는 순서에 따라 달라진다. 마지막에 터뜨릴 풍선 k를 고르면 k가 끝까지 남아 양쪽을 갈라놓으니 왼쪽과 오른쪽 구간이 독립이 된다. k를 터뜨리는 순간의 이웃도 구간 양 끝으로 정해져서 점수 `a[l]·a[k]·a[r]`이 하나로 정해진다.

### 양 끝에 1을 붙이는 이유는요?

두 가지다. "배열 밖은 1"이라는 규칙을 실제 풍선처럼 다룰 수 있고, 열린 구간 정의에서 실제 풍선이 모두 구간 안에 들어간다. 붙이지 않으면 첫 번째와 마지막 풍선이 남겨 두는 끝이 되어 영영 터지지 않는다. 붙인 풍선 두 개는 절대 터뜨리지 않는다.

### 시간과 공간 복잡도는요? 더 줄일 수 있나요?

상태가 구간 쌍이라 O(n²)개, 상태마다 분할점을 O(n)개 보니 O(n³) 시간, O(n²) 공간이다. n = 300이면 안쪽 반복이 약 450만 번이다. 각 칸이 같은 행과 같은 열의 여러 칸을 쓰니 한 줄로 줄일 수 없다. 0인 풍선을 미리 빼서 n을 줄이는 정도의 최적화가 있다.

### 그리디로는 왜 안 되나요?

지금의 선택이 남은 풍선의 이웃을 바꿔 뒤의 점수를 바꾸기 때문이다. 작은 숫자부터 터뜨리면 `[1, 2, 3]`에서 11점인데 2를 먼저 터뜨리면 12점이고, 지금 가장 많이 주는 것부터 터뜨리면 `[0, 1, 2]`에서 3점인데 0부터 치우면 4점이다. 모든 분할점을 비교하는 DP가 필요하다.

### 반복문 순서는 어떻게 정하나요?

`dp[l][r]`이 쓰는 `dp[l][k]`와 `dp[k][r]`이 먼저 채워져 있어야 한다. 둘 다 더 짧은 구간이니 길이 순서로 돌면 안전하다. 길이 대신 l을 큰 쪽부터, r을 작은 쪽부터 돌아도 된다. l을 작은 쪽부터 돌리면 `dp[k][r]`이 비어 있어 `[2, 4, 3, 5]`에서 40 같은 틀린 값이 나온다.

### Java에서 int로 충분한가요?

이 제약에서는 충분하다. 한 번에 얻는 점수가 최대 10^6이고 풍선이 300개라 합이 3×10^8을 넘지 않는다. 모두 100인 300개가 298,010,100이었다. 숫자 상한이 커지면 곱 하나만으로 `int`를 넘을 수 있어 `long`으로 바꾼다.

### 비슷한 구조의 다른 문제를 아나요?

행렬 연쇄 곱셈이 같은 점화식에 min을 쓴 고전 문제이고, 다각형 삼각분할도 같다. 막대 자르기 비용은 같은 구간 DP이지만 자르면 양쪽이 바로 독립이라 "처음 자르는 위치"로 나눠도 된다. 차이는 선택 후에 두 부분이 서로 영향을 주는지다.
