보안 점검에서 이런 지적을 받았다. "애플리케이션 로그에 고객 휴대폰 번호가 평문으로 남아 있습니다. 이 로그는 누가 볼 수 있고, 얼마나 보관합니까?" 확인해 보니 로그는 검색 시스템에 90일, S3에 1년치가 있었다. 개발자 전원이 검색 화면에 들어갈 수 있었다. 전화번호를 남기자고 한 사람은 없었다. 문자 발송이 실패했을 때 요청 내용을 통째로 찍는 디버그 로그가 원인이었다.

개인정보 규정은 법률가의 일처럼 보이지만, 실제로 지적받는 곳은 대부분 이런 코드 한 줄이다. 이 글은 개인정보가 서비스 안에서 어디로 퍼지는지, 로그와 DB와 백업에서 각각 어떻게 다루는지, 카드 번호를 내 서버에 두지 않는 방법, 그리고 GDPR·한국 개인정보 보호법·PCI DSS 같은 규정이 개발자에게 공통으로 요구하는 것을 다룬다.

먼저 범위를 밝혀 둔다. 이 글은 법률 해석이 아니다. 법과 고시는 자주 바뀌고, 같은 조항도 서비스 성격에 따라 적용이 다르다. 숫자는 글을 쓴 2026년 10월에 공개된 원문 기준으로 적었고, 실제 판단은 회사의 개인정보 보호 책임자나 법무와 함께 원문을 보고 내린다.

## 개인정보는 생각보다 넓다

PII(Personally Identifiable Information, 개인 식별 정보)라고 하면 이름과 주민등록번호를 먼저 떠올린다. 규정은 그보다 넓게 본다. GDPR은 "식별되었거나 식별할 수 있는 사람에 관한 모든 정보"를 개인정보로 보고, 한국 개인정보 보호법도 다른 정보와 쉽게 결합해 알아볼 수 있으면 개인정보로 본다. 그래서 IP 주소, 기기 ID, 광고 ID, 쿠키 값도 상황에 따라 개인정보가 된다.

하나만으로는 누군지 모르는 값도 모이면 사람을 가리킨다. 미국에서 우편번호, 생년월일, 성별 세 가지만으로 인구의 대부분(약 87%)을 특정할 수 있다는 연구(Latanya Sweeney, 2000)가 자주 인용된다. "이름을 뺐으니 괜찮다"는 판단이 위험한 이유다.

그 안에서도 더 무겁게 다루는 묶음이 있다.

- 민감 정보: 건강, 종교·사상, 정치적 견해, 노조 가입, 성생활, 유전 정보, 생체 인식 정보, 범죄 경력 같은 것이다. GDPR은 특수 범주(Art. 9), 한국 법은 민감정보(제23조)라고 부르고 따로 동의나 법적 근거를 요구한다.
- 고유식별정보: 한국 법에서 주민등록번호, 여권번호, 운전면허번호, 외국인등록번호를 말한다. 특히 주민등록번호는 법령에 근거가 있을 때만 처리할 수 있다(제24조의2). 본인 확인이 필요하면 직접 받지 말고 본인 인증 서비스의 결과(CI·DI 같은 값)를 받는다.
- 카드 정보: 카드 번호(PAN)와 CVC는 법이 아니라 카드 업계 표준인 PCI DSS가 다룬다. 뒤에서 따로 본다.
- 건강 정보: 미국에서 의료 기관과 그 협력사가 다루는 건강 정보(PHI)는 HIPAA가 다룬다.

개발할 때 쓰기 좋은 방법은 컬럼마다 등급을 붙이는 것이다. 공개, 내부, 개인정보, 민감·고유식별, 카드 정보 정도로 나누고 스키마 옆 문서나 컬럼 주석에 적어 둔다. 그 등급이 있어야 "이 컬럼은 로그에 찍으면 안 된다", "이 컬럼은 분석 DB로 넘기지 않는다"를 기계적으로 검사할 수 있다.

점선이 이번에 지적받은 길이다. 아무도 일부러 만들지 않았는데 생겼다. 나머지 길도 각각 이유가 있다. 그래서 개인정보 작업은 이 지도를 그리는 데서 시작한다. GDPR은 이런 기록을 처리 활동 기록(Art. 30)으로 남기라고 하고, 한국 법도 개인정보 처리방침에 수집 항목, 목적, 보관 기간, 제3자 제공과 위탁을 적게 한다. 처리방침에 적힌 위탁 업체 목록과 실제 코드가 호출하는 외부 API 목록이 다르면 그것부터 문제다.

지도를 그리면 해야 할 일이 보인다. 화살표마다 "이 필드가 정말 필요한가, 필요하면 원문이어야 하나, 얼마나 두나"를 묻는다. 대부분의 화살표는 원문 대신 사용자 ID만 넘기면 된다.

## 처음부터 덜 모은다

가장 확실한 보호는 갖고 있지 않은 것이다. GDPR은 이걸 데이터 최소화(Art. 5)라고 부르고, 한국 법도 목적에 필요한 최소한만 수집하라고 한다.

- 생년월일 전체 대신 만 14세 이상인지만 저장한다. 한국 법은 만 14세 미만이면 법정대리인 동의를 요구해서 이 여부는 꼭 필요하지만, 날짜까지 필요한 서비스는 많지 않다.
- 배송 주소는 주문에만 붙이고, 배송이 끝나고 보관 기간이 지나면 지운다. 회원 정보에 "기본 주소"를 꼭 둘지 따져 본다.
- 분석 이벤트에는 이메일이나 전화번호를 넣지 않는다. 사용자 ID도 분석 전용 가명 ID로 바꿔 넘기면 분석 DB가 뚫려도 피해가 줄어든다.
- 비밀번호 재설정 링크처럼 URL에 이메일을 넣지 않는다. 쿼리 문자열은 nginx 접근 로그, 프록시 로그, 브라우저 기록, `Referer` 헤더에 그대로 남는다. 식별 값은 POST 본문이나 서버에 둔 일회용 토큰으로 옮긴다.

마지막 것은 실제로 자주 걸린다. 앱 로그는 조심해도 웹 서버 접근 로그는 아무도 신경 쓰지 않아서다.

수집 화면도 코드의 일이다. 서비스에 꼭 필요한 항목과 마케팅 수신처럼 선택인 항목을 나누고, 선택 항목을 거부해도 가입이 되게 만든다. 동의는 "언제, 어떤 문구 버전에, 무엇에" 했는지를 남겨야 나중에 증명할 수 있다. 문구를 바꾸면 버전이 바뀌니, 동의 기록에 문구 버전 번호를 함께 저장한다.

```sql
-- 동의 기록은 덮어쓰지 않고 쌓는다. 철회도 한 줄로 남긴다
CREATE TABLE consents (
  user_id      bigint      NOT NULL,
  purpose      text        NOT NULL,   -- 'marketing_sms', 'overseas_transfer' 같은 목적 코드
  terms_ver    text        NOT NULL,   -- 동의할 때 보여 준 문구 버전
  granted      boolean     NOT NULL,   -- true 동의, false 철회
  created_at   timestamptz NOT NULL DEFAULT now()
);
```

현재 상태는 사용자·목적별로 가장 최근 줄을 보면 된다. 덮어쓰는 컬럼 하나(`marketing_agreed`)로 두면 언제 동의했다가 언제 철회했는지가 사라진다.

## 로그에 남기기 전에 가린다

이번 지적의 범위부터 셌다. 실습용으로 비슷한 로그 두 파일을 만들어 같은 명령을 돌렸다.

```bash
# 파일마다 휴대폰 번호처럼 보이는 줄이 몇 개인지
grep -cE '01[016789]-?[0-9]{3,4}-?[0-9]{4}' applog/*.log

# 어떤 필드 이름에 들어 있는지 모아 본다
grep -oE '"[a-z_]+":"01[016789]-?[0-9]{3,4}-?[0-9]{4}"' applog/*.log | cut -d: -f2 | sort | uniq -c
```

```text
applog/app-2026-10-23.log:2
applog/app-2026-10-24.log:2
```

```text
      2 "phone"
      2 "to"
```

`phone` 필드는 가입 로그에서, `to` 필드는 문자 발송 실패 로그에서 나왔다. 필드 이름이 보이면 고칠 코드 위치도 보인다. 실제 로그 저장소에서는 같은 정규식을 검색 쿼리로 돌린다.

가리는 위치는 로거다. 검색 화면에서 가리면 저장소에는 원문이 남는다. 구조화 로그의 직렬화 단계에서 `phone`, `email`, `password`, `authorization` 같은 필드를 지우거나 가리는 방법은 [구조화 로그 글](/posts/structured-logging)에 자세히 있다. 필드 이름으로 거르는 것이 기본이고, 정규식은 `msg`처럼 자유 문자열에 섞여 들어온 값을 잡는 두 번째 그물이다.

두 번째 그물을 직접 짜 보자. 카드 번호는 숫자 13~19자리라 주문 번호, 추적 ID와 헷갈리기 쉽다. 그래서 Luhn 검사(카드 번호 끝자리 검증 숫자 계산)를 통과할 때만 가린다.

  let sum = 0;
  for (let i = 0; i < digits.length; i++) {
    let d = Number(digits[digits.length - 1 - i]);
    if (i % 2 === 1) { d *= 2; if (d > 9) d -= 9; }
    sum += d;
  }
  return sum % 10 === 0;
}

function maskPii(line) {
  let out = line.replace(/\\b\\d(?:[ -]?\\d){12,18}\\b/g, (m) => {
    const digits = m.replace(/[ -]/g, "");
    return luhn(digits) ? "[CARD ****" + digits.slice(-4) + "]" : m;
  });
  out = out.replace(/\\b(01[016789])-?(\\d{3,4})-?(\\d{4})\\b/g, (_, a, b, c) => a + "-****-" + c);

  return out;
}`}

이 그물에는 구멍이 있다. 아무 16자리 숫자도 열 개 중 하나꼴로 Luhn을 우연히 통과하니 주문 번호가 가끔 가려진다. 반대로 `010 1234 5678`처럼 공백으로 쓴 번호, 국제 형식(`+82 10-...`), 이름과 주소는 못 잡는다. 정규식은 사고를 줄이는 장치이지 보장이 아니다. 그래서 순서는 언제나 "필드를 애초에 로그에 넣지 않는다 → 필드 이름으로 가린다 → 정규식으로 한 번 더"다.

로그 말고도 비슷한 구멍이 있다. 에러 추적 도구(Sentry 같은 것)는 기본 설정에 따라 요청 본문, 헤더, 쿠키를 함께 보낼 수 있다. APM의 SQL 추적은 바인딩 값까지 남기기도 한다. 도입할 때 무엇을 보내는지 설정을 열어 확인하고, 개인정보가 지나는 엔드포인트는 본문 수집을 끈다.

이미 남은 로그는 따로 처리한다. 검색 시스템의 색인은 보존 기간을 줄이거나 그 기간만 다시 색인하고, S3에 쌓인 원본은 수명 주기 정책으로 앞당겨 지운다. 고친 날짜와 처리한 범위를 기록해 두면 다음 점검 때 그대로 답이 된다.

## 암호화, 토큰화, 가명 처리는 서로 다르다

DB에 남겨야 하는 값은 어떻게 둘지 고른다. 네 가지가 자주 섞여서 쓰인다.

암호화는 키가 있으면 원문으로 되돌릴 수 있다. 디스크 전체, 테이블, 컬럼 단위로 걸 수 있고, 어느 층에 걸어야 무엇을 막는지는 [저장 데이터 암호화 글](/posts/encryption-at-rest)에서 다룬다. 한국의 안전성 확보조치 기준은 고유식별정보, 비밀번호, 생체 인식 정보 등을 저장할 때 암호화하라고 정하고 있다(비밀번호는 되돌릴 수 없는 일방향 암호화).

토큰화는 원문을 별도 금고(vault)에 넣고, 서비스 DB에는 아무 의미 없는 대체 값(토큰)을 둔다. 토큰은 원문과 수학적인 관계가 없어서 키를 훔쳐도 풀 수 없고, 금고에 물어봐야만 원문을 얻는다. 카드 결제에서 PG사가 돌려주는 빌링 키가 대표적인 토큰이다. 금고를 내가 운영하지 않으면 원문이 내 시스템에 아예 없다는 게 가장 큰 장점이다.

가명 처리는 다른 정보 없이는 누군지 알 수 없게 바꾸는 것이다. 분석용으로 사용자 ID나 전화번호를 HMAC(비밀 키를 넣은 해시)으로 바꾸면 같은 사람은 늘 같은 값이 되어 집계가 되고, 키가 없으면 되돌리지 못한다. 그래도 키를 가진 쪽은 다시 이을 수 있으니 GDPR에서도 한국 법(가명정보)에서도 여전히 개인정보로 다룬다. 한국 법은 가명정보를 통계·연구 목적 등에 동의 없이 쓸 수 있는 길을 열어 두었지만, 재식별 금지와 별도 보관 같은 조건이 붙는다.

익명 처리는 누구도 다시 사람을 찾을 수 없게 만든 것이다. 그렇게 되면 개인정보가 아니라서 규정 밖으로 나간다. 다만 "정말 되돌릴 수 없나"의 기준이 높다. 집계값, 일정 수 이하의 그룹을 지운 통계 정도가 여기에 가깝다.

흔한 실수가 "전화번호를 SHA-256으로 해시했으니 익명"이라고 여기는 것이다. 휴대폰 번호는 `010` 뒤에 여덟 자리라 경우의 수가 1억 개뿐이다. 해시값 하나를 받아 처음부터 다 대 봤다.

```bash
# 01087654321의 SHA-256을 구한 뒤, 010으로 시작하는 1억 개를 차례로 해시해 찾는다 (Node.js, 한 코어)
H=$(printf '01087654321' | sha256sum | cut -d' ' -f1)
node crack.js "$H"
```

```text
found 01087654321 after 87654322 tries, 75.7 s
```

노트북급 CPU 코어 하나로 76초다. GPU면 훨씬 빠르다. 키 없는 해시는 경우의 수가 작은 값 앞에서 가명도 익명도 못 된다. 쓰려면 서버에만 있는 키로 HMAC을 만들고, 그 키를 분석 쪽과 따로 둔다.

스키마로 쓰면 이런 모양이 된다.

```sql
-- PostgreSQL 16 기준
CREATE TABLE users (
  id             bigserial PRIMARY KEY,
  email          text NOT NULL,          -- 로그인에 쓰므로 원문 (접근 권한으로 보호)
  phone_enc      bytea,                  -- 문자 발송용. 앱이 KMS 데이터 키로 암호화해서 넣는다
  phone_lookup   bytea,                  -- HMAC(서버 키, 정규화한 번호). 중복 가입 검사에만 쓴다
  is_over_14     boolean NOT NULL,       -- 생년월일 대신 필요한 사실만
  billing_key    text,                   -- PG사가 준 토큰. 카드 번호는 없다
  deleted_at     timestamptz             -- 탈퇴 표시. 이 값만으로는 파기가 아니다
);
```

`phone_enc`로는 검색을 못 하니 같은 번호로 가입했는지 보려고 `phone_lookup`을 따로 둔다. 이 패턴(블라인드 인덱스)의 장단점도 저장 데이터 암호화 글에 있다.

## 개발·분석용 사본은 처음부터 가짜로 만든다

운영 밖으로 나가는 사본이 생각보다 많다. 버그를 재현하려고 만든 스테이징 DB, QA용 테스트 데이터, 분석가가 쓰는 추출본이 그렇다. 이 사본들은 권한과 감사 기록이 운영보다 느슨하다. 그래서 원문을 복사한 다음 가리는 게 아니라, 밖으로 나갈 때 이미 가려진 값이 되게 만든다.

여기서 쓰는 방법이 정적 마스킹이다. 사본의 값을 실제로 덮어써서 되돌릴 수 없게 만든다. 원본은 그대로 두고 특정 역할이 읽을 때만 가려 보여 주는 동적 마스킹과 다르다. 동적 마스킹은 운영 DB에 붙는 분석 역할에 쓰고, 운영 밖으로 옮기는 사본에는 정적 마스킹을 쓴다. PostgreSQL에서 확장으로 두 방식을 모두 거는 방법은 [PostgreSQL 역할과 보안 글](/posts/postgres-roles-security#스테이징에-복사할-때는-개인정보부터-가린다)에 있다.

가린 값을 `***`로만 채우면 테스트가 깨진다. 전화번호 형식을 검사하는 코드, 이메일로 조인하는 쿼리, 길이를 가정한 화면이 모두 실패한다. 그래서 형식은 지키고 값만 가짜인 대체 값을 넣는다. 키를 넣은 HMAC으로 원본에서 가짜 값을 뽑으면 같은 원본은 늘 같은 가짜 값이 되어서, 테이블 여러 개에 흩어진 같은 번호도 그대로 이어진다.

```js
// 원본 번호 → HMAC → 숫자 8자리 → 010-XXXX-XXXX 형식의 가짜 번호
const h = crypto.createHmac("sha256", KEY).update(phone).digest();
const s = String(h.readUInt32BE(0) % 100000000).padStart(8, "0");
const fake = `010-${s.slice(0, 4)}-${s.slice(4)}`;
```

```text
010-8765-4321 -> 010-2321-9356
010-1234-5678 -> 010-5758-4262
010-8765-4321 -> 010-2321-9356
```

같은 번호가 두 번 나와도 같은 가짜 값이 됐다. 키는 마스킹 작업에만 두고 개발 환경에는 주지 않는다. 키가 새면 앞에서 본 1억 개 대입이 다시 가능해진다. 그리고 가짜 번호가 실제 누군가의 번호와 우연히 같을 수 있으니, 개발 환경에서는 문자·메일 발송을 실제 수신자에게 나가지 않게 막아 둔다.

분석용 추출본은 사정이 다르다. 분석가는 한 사람의 값이 아니라 분포가 필요하다. 그래서 값을 지우는 대신 분포를 지키며 흐리는 통계적 난독화를 쓴다. 정확한 나이를 `20대`로, 우편번호를 앞 세 자리로 묶는 일반화, 개별 값이나 집계 결과에 작은 무작위 잡음을 더하는 잡음 추가가 대표적이다. 잡음은 평균 같은 큰 집계에서는 상쇄되고 한 사람의 값에서는 크게 드러난다.

일반화를 얼마나 했는지 재는 기준이 k-익명성이다. 나이대와 우편번호 앞자리처럼 다른 데이터와 맞춰 볼 수 있는 컬럼(준식별자) 조합마다 같은 행이 적어도 k개 있게 만드는 것이다. 여섯 줄짜리 진료 기록을 일반화해 세어 봤다.

```text
20대 062** k=3 감기,위염,감기
30대 045** k=3 당뇨,당뇨,당뇨
k-anonymity = 3
```

두 묶음 모두 세 명이라 k=3이다. 그런데 30대 045** 묶음은 세 명 모두 당뇨다. 이웃 중 30대가 그 동네에 산다는 것만 알면 누군지는 몰라도 병명은 안다. 이걸 동질성 공격이라고 부르고, k-익명성은 이걸 막지 못한다. 묶음 안의 민감 값이 여러 가지가 되게 하는 l-다양성이 나왔지만 그것도 배경 지식을 가진 공격자 앞에서는 한계가 있다. 그래서 공개용 통계는 쿼리 결과에 수학적으로 정한 만큼 잡음을 더하는 차분 프라이버시(differential privacy)로 가는 추세다. 일반화나 잡음을 거친 데이터라도 원본과 다시 이을 수 있으면 가명정보로 보고 앞 절의 규칙을 그대로 따른다.

## 지워 달라는 요청은 모든 사본에 닿아야 한다

백업이 가장 까다롭다. 변경 불가 설정을 건 백업에서 한 사람만 골라 지우기는 어렵고, 그러려고 백업을 풀었다 다시 만드는 것은 위험하다. 실무에서 흔한 답은 두 가지를 같이 하는 것이다. 백업 보관 기간을 정해 두고(예: 35일) 그 기간이 지나면 자연히 사라지게 하는 것, 그리고 삭제 요청을 별도 목록(지운 사용자 ID만 담은 표)에 남겨 백업을 복원할 때 그 목록을 다시 적용하는 것이다. 처리방침에 "백업에 남은 정보는 보관 주기에 따라 파기된다"는 문장을 넣는 이유다.

이벤트 저장소처럼 지울 수 없는 로그에 개인정보를 넣어야 한다면, 사람마다 다른 키로 암호화해서 넣고 삭제 요청 때 키만 지우는 방법이 있다. 이 방법(크립토 셰딩)은 [이벤트 소싱 글](/posts/event-sourcing)에서 다룬다. 백업에도 같은 생각을 적용할 수 있다. 키 저장소가 백업과 따로 있고, 키 저장소의 사본은 짧게 보관해야 효과가 있다.

지우면 안 되는 것도 있다. 한국에서는 전자상거래법이 계약·청약철회와 대금 결제 기록을 5년, 소비자 불만 처리 기록을 3년 보관하라고 하고, 통신비밀보호법은 로그인 기록 같은 통신사실확인자료를 3개월 보관하게 한다(흔히 인용되는 기간이고, 업종에 따라 다르다). 이런 기록은 탈퇴해도 남겨 두되, 목적에 필요한 컬럼만 떼어 별도 테이블로 옮기고 접근을 좁힌다. 회원 테이블에 그대로 두고 `deleted_at`만 찍으면 "보존해야 하는 것"과 "지워야 하는 것"이 섞인다.

보존 기간이 지난 데이터를 지우는 배치는 한 번에 크게 지우지 않는다. 수백만 행을 한 트랜잭션으로 지우면 잠금이 길어지고 복제가 밀린다.

```sql
-- 보존 기간(5년)이 지난 결제 기록을 1000행씩 지운다. 배치가 0행을 지울 때까지 반복한다
DELETE FROM payment_records
WHERE id IN (
  SELECT id FROM payment_records
  WHERE created_at < now() - interval '5 years'
  ORDER BY id
  LIMIT 1000
);
```

PostgreSQL의 `DELETE`는 `LIMIT`을 직접 받지 않아서 하위 쿼리로 묶었다. MySQL 8은 `DELETE ... ORDER BY id LIMIT 1000`을 바로 쓸 수 있다. `created_at`에 인덱스가 없으면 배치마다 테이블 전체를 훑는다.

## 카드 번호는 내 서버에 두지 않는다

카드 결제를 붙이면 PCI DSS(Payment Card Industry Data Security Standard, 카드 업계 보안 표준)를 만난다. 법이 아니라 카드 브랜드들이 만든 표준인데, 가맹점 계약으로 지켜야 한다. 글을 쓰는 시점에 널리 쓰이는 판은 v4.0.1이다.

PCI DSS에서 가장 중요한 말은 범위(scope)다. 카드 번호를 저장하거나 처리하거나 지나가게 하는 모든 시스템과, 그 시스템과 연결된 시스템이 점검 대상이 된다. 카드 번호가 내 API 서버를 한 번이라도 지나가면 그 서버, 그 서버의 로그 저장소, 그 서버에 접속하는 배포 도구까지 범위에 들어간다. 그래서 가장 좋은 전략은 카드 번호가 내 서버를 아예 지나가지 않게 하는 것이다.

이렇게 결제 입력을 통째로 PG에 맡기면 가맹점이 작성하는 자체 점검 설문(SAQ)도 가장 짧은 종류(SAQ A)에 가까워진다. 반대로 내 페이지가 카드 입력 칸을 직접 그리고 자바스크립트로 PG에 보내면, 카드 번호가 내 서버를 지나지 않아도 그 페이지를 내려주는 서버가 범위에 들어가는 종류(SAQ A-EP)가 된다. 내 서버가 카드 번호를 직접 받으면 요구 사항 전체(SAQ D)를 본다. 어떤 SAQ가 맞는지는 PG사와 매입사가 정하니, 연동 방식을 고를 때 미리 물어본다.

카드 번호를 꼭 다뤄야 하는 쪽이라면 기억할 규칙이 몇 개 있다. CVC와 마그네틱·칩의 전체 데이터 같은 민감 인증 데이터(SAD)는 승인 뒤에 저장하면 안 된다. 암호화해도 안 된다. 저장하는 카드 번호는 읽을 수 없게(강한 암호화, 토큰화, 키 있는 해시 등) 만들어야 하고, 화면에 보일 때는 앞 6자리와 끝 4자리 정도까지만 보인다. 그리고 앞 섹션의 Luhn 그물이 여기서 쓰인다. 카드 번호가 로그에 한 번 찍히면 로그 저장소가 범위에 들어가 버린다.

## 규정마다 다르지만 요구는 겹친다

규정 이름이 많아 보이지만, 개발자에게 내려오는 요구를 모으면 겹치는 부분이 크다. 차이가 나는 숫자만 표로 모았다. 모두 범위와 예외가 있으니 원문 확인이 전제다.

| 규정 | 누구에게 | 개발자가 자주 만나는 요구 |
|---|---|---|
| GDPR (EU) | EU에 있는 사람의 정보를 다루는 곳. EU 밖 회사도 EU 사람에게 서비스하면 대상 | 처리 근거, 최소화, 설계 단계의 보호(Art. 25), 열람·이동·삭제 요청에 원칙적으로 한 달 안 응답, 유출을 안 뒤 72시간 안에 감독기관 신고, 과징금 상한 2천만 유로 또는 전 세계 매출 4% 중 큰 쪽 |
| 개인정보 보호법 (한국) | 개인정보를 처리하는 모든 사업자 | 수집·이용 동의와 처리방침, 주민등록번호 처리 제한, 고유식별정보 암호화, 접속 기록 보관, 유출 시 정보주체 통지와 신고(2023년 개정 뒤 72시간 기준), 과징금은 전체 매출 3% 이하(위반과 무관한 매출 제외 가능) |
| CCPA/CPRA (캘리포니아) | 매출이나 처리 규모 기준을 넘는 사업자 | 수집 정보 열람·삭제, 판매·공유 거부("Do Not Sell or Share"), 요청에 45일 안 응답 |
| HIPAA (미국) | 의료 기관, 보험사와 그 협력사(BA) | 건강 정보(PHI) 접근 통제와 감사 로그, 전송·저장 암호화, 협력사 계약(BAA). 클라우드도 BAA를 맺은 서비스만 |
| PCI DSS | 카드를 받는 가맹점과 처리 업체 | 범위 최소화, 카드 번호 저장 시 읽을 수 없게, SAD 저장 금지, 접근 기록과 로그 검토 |

표를 세로로 읽으면 공통분모가 보인다. 무엇을 어디에 두는지 아는 것(데이터 지도), 필요한 것만 받는 것, 접근을 좁히고 누가 봤는지 남기는 것, 저장과 전송을 암호화하는 것, 기간이 지나면 지우는 것, 사람이 요청하면 찾아서 보여 주고 지우는 것, 유출되면 빨리 알리는 것. 어느 규정을 만나도 이 일곱 가지를 해 둔 시스템은 크게 고칠 일이 없다.

데이터를 어느 나라에 두는지도 규정의 일부다. GDPR은 EU 밖으로 개인정보를 옮길 때 적정성 결정을 받은 나라이거나 표준 계약 조항(SCC) 같은 장치를 요구한다. 한국은 2021년 12월 EU의 적정성 결정을 받았다. 한국 법도 국외 이전에 동의나 다른 근거를 요구하고 처리방침에 이전 국가와 업체를 적게 한다. 리전을 고르면 백업 복제 대상 리전, CDN 로그, 외부 SaaS의 서버 위치까지 같이 따져야 한다. 나라별로 데이터를 나눠 두는 구조는 [글로벌 출시 글](/posts/global-rollout-localization)에서 다룬다.

### 데이터로 모델을 만든다면: EU AI Act

학습 데이터를 모으고 모델을 만드는 팀이라면 EU의 AI법(AI Act)도 만난다. 2024년 8월 1일 발효됐고 의무가 단계적으로 걸린다. 금지 관행은 2025년 2월, 범용 AI 모델(GPAI) 제공자의 의무는 2025년 8월부터 적용됐다. 고위험 시스템 의무는 원래 2026년 8월(제품 안전 규제에 묶인 것은 2027년 8월)부터였는데, 2025년 11월 EU 집행위원회가 이 시점을 늦추는 개정안(디지털 옴니버스)을 냈다. 확정된 일정은 원문으로 확인한다.

이 법은 데이터가 아니라 AI 시스템의 쓰임새로 위험 등급을 나눈다. 사회 점수 매기기처럼 금지되는 것, 채용 서류 심사·신용 평가·교육 평가·생체 인식처럼 고위험인 것, 챗봇이나 생성 이미지처럼 투명성 의무만 있는 것(사람에게 AI와 대화 중임을 알리고, 생성물에 기계가 읽을 수 있는 표시를 단다), 나머지 최소 위험으로 나뉜다. 같은 분류 모델도 스팸 필터면 최소 위험이고 이력서 거르기면 고위험이다.

데이터 쪽 개발자에게 직접 내려오는 건 고위험 시스템의 데이터 거버넌스(제10조)다. 학습·검증·테스트 데이터가 목적에 맞고 충분히 대표성이 있으며 가능한 한 오류 없이 완전해야 하고, 편향을 점검해야 한다. 어디서 모았는지, 어떻게 정제하고 라벨을 붙였는지, 어떤 가정을 했는지를 기술 문서(제11조, 부속서 IV)에 남기고, 운영 중에는 자동 기록(제12조)을 둔다. 편향 점검에 꼭 필요하면 민감 정보를 엄격한 조건 아래 처리할 수 있다는 예외도 있다. 범용 모델 제공자는 기술 문서, 저작권 정책, 학습에 쓴 콘텐츠의 요약 공개가 의무다.

GDPR을 대신하는 법이 아니라 그 위에 얹히는 법이다. 학습 데이터에 개인정보가 있으면 처리 근거, 최소화, 삭제 요청은 여전히 GDPR이 다룬다. 실무에서 해 둘 일은 앞에서 본 것과 이어진다. 데이터셋마다 출처와 버전과 처리 내역을 남기고([실험 추적 글](/posts/ml-experiment-tracking)의 데이터 버전 관리가 그 기록이 된다), 품질 검사를 자동으로 돌린다([데이터 품질 검사 글](/posts/data-quality-checks)).

## 누가 언제 봤는지 남긴다

규정들이 빠짐없이 요구하는 게 접근 기록이다. 한국의 안전성 확보조치 기준은 개인정보취급자가 개인정보처리시스템에 접속한 기록을 1년 이상(처리하는 정보주체가 많거나 고유식별정보·민감정보를 다루면 2년 이상) 보관하고 월 1회 이상 점검하라고 정한다(2023년 개정 고시 기준). 이건 서버 로그인 기록이 아니라 "관리자 화면에서 누가 어느 회원의 정보를 조회·수정·다운로드했나"의 기록이다.

앱 안의 접근 로그는 이렇게 남긴다.

```json
{"ts":"2026-10-24T09:12:03Z","actor":"admin:park","action":"view","resource":"user","resource_id":42,"fields":["phone"],"reason":"CS-20261024-118","ip":"10.0.4.17"}
```

값이 아니라 "어떤 필드를 봤다"를 남긴다. 감사 로그에 전화번호를 찍으면 감사 로그가 또 하나의 개인정보 저장소가 된다. 상담원이 전화번호를 보려면 문의 번호(`reason`)를 넣게 하면, 월 점검 때 이유 없는 조회를 바로 걸러 낼 수 있다. 엑셀 다운로드는 따로 표시하고, 한 번에 많은 건을 내려받으면 경보를 건다.

클라우드 콘솔과 API에서 일어난 일은 클라우드의 감사 로그가 맡는다. AWS라면 CloudTrail이다. 몇 가지는 기본값을 알아야 한다. 관리 이벤트(리소스 생성·삭제, IAM 변경)는 이벤트 기록 화면에서 90일까지만 보이고, 그보다 오래 두려면 trail을 만들어 S3로 보내야 한다. S3 객체를 누가 읽었는지 같은 데이터 이벤트는 기본으로 기록되지 않고, 켜면 따로 비용이 든다. 개인정보가 든 버킷이라면 데이터 이벤트를 켜는 것을 검토한다. 로그 파일 무결성 검증을 켜고, 로그는 운영 계정과 다른 계정의 버킷에 변경 불가 설정으로 둔다. 운영 계정을 잃어도 기록은 남아야 하기 때문이다.

이렇게 모은 로그를 한곳에서 엮어 이상 징후를 찾는 일은 [보안 로깅과 SIEM 글](/posts/security-logging-detection-siem), 쿠버네티스 API의 감사 로그는 [쿠버네티스 감사 로그 글](/posts/k8s-audit-logging)에서 다룬다.

## 지적을 받은 뒤에 하는 일

처음 장면으로 돌아가서 실제로 한 일을 순서대로 적으면 이렇다.

먼저 범위를 셌다. 어떤 필드에 몇 건이 언제부터 남았는지, 그 로그를 누가 볼 수 있었는지 확인했다. 범위를 알아야 유출 신고 대상인지도 판단할 수 있다. 내부 직원이 볼 수 있었던 것과 외부에 나간 것은 다르게 다뤄진다.

다음은 새로 쌓이는 것을 막았다. 로거 직렬화 단계에 필드 이름 기반 마스킹을 넣고, 자유 문자열에는 정규식 그물을 걸었다. 문자 발송 실패 로그는 수신 번호 대신 사용자 ID만 남기게 바꿨다.

그다음 이미 남은 것을 처리했다. 검색 시스템의 해당 기간 색인을 지우고 가린 데이터로 다시 만들었다. S3 원본은 보존 기간을 1년에서 실제 필요한 기간으로 줄이고 수명 주기 정책으로 정리했다. 로그 검색 화면 접근도 운영 담당자로 좁혔다.

마지막으로 재발을 막는 검사를 붙였다. 테스트에서 로거 출력에 개인정보 패턴이 나오면 실패하게 하고, 매일 로그 샘플을 같은 정규식으로 훑어 건수가 0이 아니면 알림을 보낸다. 새 필드를 추가할 때 등급을 적게 하면 이 검사가 무엇을 봐야 할지도 알게 된다.

## 맡은 것만큼만 갖고 있기

개인정보 규정은 이름이 여럿이지만, 시스템에 요구하는 건 결국 "무엇을 어디에 두는지 알고, 필요한 만큼만, 필요한 동안만 갖고 있으라"는 것이다. 지도를 그리면 퍼지는 길이 보이고, 로거에서 가리면 로그가 새 저장소가 되지 않고, 토큰화를 쓰면 카드 번호가 내 범위 밖에 머문다. 삭제는 모든 사본에 닿아야 하니, 처음부터 사본에 원문 대신 ID를 보내는 설계가 나중의 삭제 요청을 가볍게 만든다.

## 면접에서 나올 만한 질문

### 개인정보(PII)는 어디까지인가요?

살아 있는 사람을 식별했거나 다른 정보와 결합해 식별할 수 있는 모든 정보입니다. 이름, 전화번호, 이메일뿐 아니라 IP, 기기 ID, 쿠키 값도 상황에 따라 들어가고, 우편번호·생년월일·성별처럼 하나씩은 약한 값도 모이면 사람을 특정합니다. 그 안에서 건강·생체 같은 민감 정보, 주민등록번호 같은 고유식별정보, 카드 정보는 더 강한 규칙을 받습니다.

### 로그에 개인정보가 남지 않게 하려면 어떻게 하나요?

애초에 요청 전체를 찍지 않고, 로거의 직렬화 단계에서 필드 이름으로 지우거나 가리고, 자유 문자열에는 정규식(카드 번호는 Luhn 검사 포함)으로 한 번 더 거릅니다. 검색 화면에서 가리는 건 저장소에 원문이 남아서 소용이 없습니다. 웹 서버 접근 로그에 남는 URL 쿼리 문자열과 에러 추적 도구가 보내는 요청 본문도 함께 확인합니다.

### 암호화, 토큰화, 가명 처리, 익명 처리의 차이는요?

암호화는 키로 되돌릴 수 있고, 토큰화는 원문을 금고에 두고 수학적 관계가 없는 대체 값만 쓰는 방식입니다. 가명 처리는 키나 추가 정보 없이는 누군지 모르게 바꾼 것이라 여전히 개인정보이고, 익명 처리는 누구도 다시 찾을 수 없게 만든 것이라 규정 밖으로 나갑니다. 전화번호를 키 없이 해시하면 1억 개 경우의 수를 몇 분 안에 다 대 볼 수 있어서 익명이 아닙니다.

### 삭제 요청이 오면 백업에 있는 데이터는 어떻게 하나요?

변경 불가 백업을 한 명만 골라 고치지 않고, 백업 보관 기간을 정해 만료되게 둡니다. 대신 삭제한 사용자 ID 목록을 따로 남겨 백업을 복원할 때 다시 적용합니다. 지울 수 없는 저장소에는 사람마다 다른 키로 암호화해 넣고 키를 지우는 크립토 셰딩을 쓸 수 있고, 처리방침에 백업 파기 주기를 적어 둡니다.

### 탈퇴했는데 결제 기록은 남겨야 합니다. 어떻게 설계하나요?

법정 보존 대상(한국이라면 전자상거래법의 결제 기록 등)만 별도 테이블로 떼어 내고, 회원 테이블의 나머지 개인정보는 파기합니다. 분리한 테이블은 접근을 좁히고 보존 기간이 끝나면 배치로 나눠 지웁니다. `deleted_at`만 찍는 소프트 삭제는 파기가 아니고, 보존할 것과 지울 것이 섞이게 만듭니다.

### PCI DSS 범위를 줄이려면 어떻게 하나요?

카드 번호가 내 서버를 아예 지나가지 않게 PG의 결제창(iframe이나 리다이렉트)을 쓰고, 내 서버는 토큰과 결제 키만 받습니다. 카드 번호를 저장하거나 처리하거나 지나가게 하는 시스템과 그에 연결된 시스템이 모두 범위라서, 한 번이라도 로그에 찍히면 로그 저장소까지 들어갑니다. CVC 같은 민감 인증 데이터는 승인 후에 암호화해서라도 저장하면 안 됩니다.

### 감사 로그에는 무엇을 남기고 무엇을 남기지 않나요?

누가, 언제, 어디서, 어떤 대상의 어떤 필드를 조회·수정·다운로드했는지와 그 이유를 남기고, 조회한 값 자체는 남기지 않습니다. 값을 찍으면 감사 로그가 또 하나의 개인정보 저장소가 됩니다. 클라우드 쪽은 CloudTrail 같은 감사 로그를 별도 계정의 변경 불가 저장소로 보내 오래 보관하고, 개인정보 버킷은 데이터 이벤트 기록을 검토합니다.

### 개발·테스트용으로 운영 데이터를 쓰려면 어떻게 가리나요?

운영 밖으로 나가는 사본에는 값을 실제로 덮어쓰는 정적 마스킹을 쓰고, 형식은 지키되 값만 가짜인 대체 값을 넣습니다. 키를 넣은 HMAC으로 가짜 값을 만들면 같은 원본이 늘 같은 값이 되어 조인과 형식 검사가 그대로 돌아갑니다. 분석용이면 일반화와 잡음 추가로 분포를 지키는데, k-익명성을 맞춰도 한 묶음의 민감 값이 모두 같으면 병명이 드러나는 동질성 공격이 남습니다. 다시 이을 수 있는 데이터는 여전히 가명정보로 다룹니다.
