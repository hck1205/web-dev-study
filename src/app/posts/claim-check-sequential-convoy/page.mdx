주문 서비스가 영수증을 만들면 "영수증 생성됨" 메시지를 큐에 넣고, 알림 서비스가 받아서 고객에게 보낸다. 어느 날 기획이 바뀌어 메시지에 영수증 썸네일 이미지를 함께 넣기로 했다. 테스트에서는 잘 되다가 운영에서 일부 메시지가 거절되기 시작했다. 큐의 최대 메시지 크기가 256KiB(262,144바이트)로 설정되어 있었고, 썸네일이 큰 영수증이 그 선을 넘었다.

200KiB짜리 이미지라 한도 안이라고 생각했는데, JSON에 넣으려고 base64로 바꾼 게 문제였다. 직접 재 봤다.

```bash
# 200KiB 바이너리를 base64로 JSON에 넣었을 때의 크기
node size.js
```

```text
binary bytes: 204800
base64 chars: 273068
message bytes: 273130
256 KiB limit: 262144 over by: 10986
```

base64는 3바이트를 4글자로 바꾸니 크기가 약 4/3배가 된다. 204,800바이트가 273,068글자가 되어 한도를 11KB쯤 넘었다. 한도를 올리면 당장은 해결되지만, 다음에 더 큰 이미지가 오면 같은 일이 생긴다. 그리고 메시지 브로커는 큰 짐을 나르라고 만든 물건이 아니다.

이 글은 메시징에서 자주 같이 나오는 두 가지 설계 패턴을 다룬다. 큰 본문을 저장소에 맡기고 참조만 보내는 클레임 체크(claim check), 그리고 전체 순서 대신 키별 순서만 지키며 병렬로 처리하는 순차 호송(sequential convoy)이다. 둘 다 마이크로소프트의 클라우드 설계 패턴 목록에 이 이름으로 실려 있다. 실험은 Node 22로 했고, 클라우드 계정이 없어서 AWS·Azure 쪽은 공식 문서의 설정 형식만 적었다.

큐의 ack와 가시성 타임아웃은 [메시지 큐 기초](/posts/message-queue-basics)에서, 파티션과 오프셋은 [Kafka 기초](/posts/kafka-basics)에서, 계속 실패하는 메시지를 빼 두는 법은 [데드 레터 큐](/posts/dead-letter-queue)에서 다룬다. 여기서는 그 위에서 생기는 두 문제, "너무 크다"와 "순서가 깨진다"만 본다.

## 메시지 크기 한도는 시스템마다 다르다

한도는 브로커마다, 같은 브로커라도 설정마다 다르다. 글을 쓰는 시점에 공식 문서에서 확인한 값은 이렇다. 바뀌는 값이니 쓰기 전에 다시 본다.

- Amazon SQS: 오랫동안 256KiB였고 2025년에 최대 1MiB로 올라갔다. 큐마다 `MaximumMessageSize` 속성이 있어서 그 값이 실제 한도다. 처음 장면처럼 큐가 262,144로 설정되어 있으면 그게 한도다.
- Amazon SNS, EventBridge: 이벤트 하나에 256KB.
- Apache Kafka: 브로커의 `message.max.bytes` 기본값이 약 1MB(1,048,588바이트)다. 올릴 수는 있지만 프로듀서 `max.request.size`, 컨슈머 `fetch.max.bytes`, 토픽의 `max.message.bytes`를 함께 맞춰야 한다.
- Azure Service Bus: Standard 티어는 256KB, Premium 티어는 그보다 훨씬 크게(최대 100MB) 설정할 수 있다.

한도를 끝까지 올리지 않는 이유가 있다. 브로커는 메시지를 메모리에 버퍼로 들고, 복제본에 그대로 복사하고, 보관 기간 동안 디스크에 둔다. 메시지 하나가 커지면 이 모든 비용이 메시지 수만큼 곱해진다. Kafka에서 큰 메시지는 복제 지연과 컨슈머 fetch 지연을 늘리고, 한 배치에 들어가는 메시지 수를 줄여 처리량을 떨어뜨린다. 요금도 커진다. SQS는 64KB 단위로 요청 수를 세서, 1MiB 메시지 하나는 요청 16번으로 과금된다. 무엇보다 메시지를 받는 쪽 대부분은 큰 본문이 필요 없는 경우가 많다. 영수증 알림을 보내는 서비스는 썸네일을 보내지만, 같은 메시지를 구독하는 통계 서비스는 금액만 본다.

순서가 중요하다. 본문을 먼저 올리고 메시지를 나중에 보내야 한다. 반대로 하면 받는 쪽이 메시지를 받았을 때 아직 객체가 없을 수 있다. S3는 2020년부터 새로 쓴 객체를 바로 읽을 수 있는 강한 일관성을 주므로, 업로드가 성공한 뒤에 보낸 메시지라면 받는 쪽은 항상 객체를 읽을 수 있다.

키를 덮어쓰지 않는 것도 같은 이유다. 같은 키에 새 본문을 올리면, 옛 메시지를 늦게 처리하는 컨슈머가 새 본문을 읽는다. 메시지와 본문이 서로 다른 시점의 것이 된다. 키를 매번 새로 만들거나(UUID), 본문의 해시를 키로 쓰면(내용 주소) 이 문제가 없다. 해시를 키로 쓰면 같은 본문을 두 번 올려도 객체가 하나로 합쳐지는 덤도 있다.

AWS는 이 패턴을 라이브러리로도 준다. SQS Extended Client Library(Java, Python)는 메시지가 정한 크기를 넘으면 본문을 S3에 올리고 SQS에는 포인터만 보내며, 받는 쪽에서 포인터를 따라가 본문을 돌려준다. 직접 만들든 라이브러리를 쓰든, 아래에서 볼 정리와 보안 문제는 똑같이 남는다.

## 맡긴 짐은 누가 언제 치우나

클레임 체크에서 가장 많이 실수하는 곳은 객체의 수명이다. 지울 시점을 잘못 고르면 두 방향으로 깨진다.

너무 늦게 지우거나 안 지우면 고아 객체가 쌓인다. 업로드는 성공했는데 메시지 보내기가 실패한 경우, 메시지는 처리됐는데 객체를 지우는 코드가 없는 경우다. 아무도 참조하지 않는 객체가 버킷에 계속 쌓여 저장 요금이 된다.

너무 일찍 지우면 참조가 먼저 죽는다. 이쪽이 더 위험하다. 메시지가 큐에 머무는 시간은 생각보다 길 수 있다. 컨슈머가 며칠 장애였거나, 메시지가 DLQ로 갔다가 고친 뒤 되돌려 보내지는 경우다. 수명 규칙이 객체를 7일 뒤 지우는데 DLQ에서 10일째에 되돌려 보내면, 그 메시지는 존재하지 않는 객체를 가리킨다.

그래서 수명은 "메시지가 살아 있을 수 있는 가장 긴 시간"보다 길게 잡는다. SQS 메시지 보관 기간은 최대 14일이고, DLQ로 옮겨진 메시지에는 DLQ의 보관 기간이 적용되는데, 표준 큐는 원래 큐에 처음 들어온 시각부터 세고 FIFO 큐는 DLQ로 옮겨진 시각부터 다시 센다. DLQ를 사람이 보고 되돌려 보내는 시간까지 생각하면 원래 큐 보관 기간 + DLQ 보관 기간 + 여유를 수명으로 둔다.

```json
{
  "Rules": [
    {
      "ID": "expire-claims",
      "Filter": { "Prefix": "" },
      "Status": "Enabled",
      "Expiration": { "Days": 35 },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 1 }
    }
  ]
}
```

```bash
# 클레임 전용 버킷에 수명 규칙을 건다: 35일 뒤 삭제, 덜 올라간 멀티파트는 하루 뒤 정리
aws s3api put-bucket-lifecycle-configuration \
  --bucket receipts-claims \
  --lifecycle-configuration file://lifecycle.json
```

컨슈머가 처리 직후 객체를 지우는 방법도 있지만, 구독자가 여럿이면(SNS에서 SQS 여러 개로 퍼지는 구조) 누가 마지막인지 알 수 없다. 한 구독자가 지우면 다른 구독자의 메시지가 고아 참조가 된다. 그래서 대개 수명 규칙에 맡기고, 저장 요금이 문제가 될 만큼 크면 그때 "모든 구독자가 처리했음"을 세는 장치를 따로 둔다. 객체 저장소의 수명 규칙과 스토리지 클래스는 [S3 스토리지 클래스와 수명 주기](/posts/s3-storage-classes-lifecycle)에서 다룬다.

참조가 죽은 메시지를 받았을 때의 동작도 정해 둔다. 객체를 못 찾으면(S3의 `NoSuchKey`) 재시도해도 결과가 같으니 바로 DLQ로 보내고, 그 건수에 알림을 건다. 이 알림이 울린다면 수명이 메시지 생존 시간보다 짧다는 신호다.

## 맡긴 짐에 자물쇠를 채운다

본문이 메시지 밖으로 나가면 보안 경계도 둘이 된다. 큐에 대한 권한과 버킷에 대한 권한이 따로 있고, 둘 다 맞아야 한다.

- 암호화: 클레임 버킷에 기본 암호화(SSE-S3 또는 SSE-KMS)를 건다. KMS 키를 쓰면 컨슈머 역할에 `s3:GetObject`뿐 아니라 그 키의 `kms:Decrypt`도 있어야 한다. 이걸 빠뜨리면 컨슈머는 메시지는 받는데 본문을 읽을 때 `AccessDenied`를 본다. 저장 암호화의 선택지는 [저장 데이터 암호화](/posts/encryption-at-rest)에 있다.
- 권한 범위: 컨슈머에는 그 버킷(또는 접두사)의 읽기만, 프로듀서에는 쓰기만 준다. 참조를 위조한 메시지가 다른 버킷의 객체를 가리켜도 읽지 못하게, 컨슈머는 메시지의 버킷 이름이 기대한 값인지도 확인한다.
- 바깥 소비자: 같은 계정 밖의 시스템에 넘겨야 하면 버킷 권한을 열지 말고 짧은 만료의 미리 서명된 URL을 참조로 보낸다. 대신 URL의 만료가 메시지 처리 시간보다 짧으면 위의 "참조가 먼저 죽는" 문제가 그대로 생긴다.
- 무결성: 메시지에 크기와 해시를 넣고 컨슈머가 비교한다. 누군가 객체를 바꿔치기하거나 업로드가 잘린 경우를 잡는다.

개인정보가 든 본문이라면 클레임 체크가 오히려 도움이 된다. 큐와 DLQ, 메시지 로그에는 참조만 남고, 지워야 할 때 객체 하나만 지우면 되기 때문이다. 반대로 본문을 메시지에 넣어 두면 DLQ와 재처리 로그, 디버깅용 메시지 덤프 곳곳에 개인정보가 복사된다.

## 전체 순서는 비싸다

이제 두 번째 문제로 넘어간다. 같은 주문의 이벤트 "생성됨 → 결제됨 → 배송됨"은 이 순서로 반영되어야 한다. 배송됨이 먼저 반영되고 생성됨이 나중에 오면 주문 상태가 뒤로 간다. 그런데 모든 메시지의 전체 순서를 지키려면 컨슈머가 한 번에 하나씩만 처리해야 한다. 컨슈머를 늘리는 순간 끝나는 순서가 섞인다([메시지 큐 기초](/posts/message-queue-basics)에서 직접 봤다).

다행히 대부분의 업무에서 필요한 건 전체 순서가 아니다. 주문 7번의 이벤트끼리만 순서가 맞으면 되고, 주문 7번과 주문 9번 사이의 순서는 상관없다. 순차 호송은 메시지를 키(주문 ID, 계좌 번호, 사용자 ID)로 묶어 키마다 한 줄로 세우고, 줄끼리는 동시에 처리하는 패턴이다. 같은 줄 안에서는 앞 메시지가 끝나야 다음이 나가고, 줄이 많을수록 병렬성이 커진다.

## 키마다 줄을 세우는 세 가지 방법

브로커마다 이 줄을 만드는 장치가 이름만 다르게 있다.

Kafka는 파티션이 줄이다. 프로듀서가 키를 해시해 파티션을 고르므로 같은 키는 같은 파티션에 들어가고, 파티션 하나는 컨슈머 그룹 안에서 컨슈머 하나만 읽는다. 줄의 수가 파티션 수로 고정된다는 점이 특징이다. 키가 10만 개여도 파티션이 12개면 줄은 12개고, 한 파티션 안에서는 서로 상관없는 키들도 앞 메시지를 기다린다.

```ts
// kafkajs: 주문 ID를 키로 보내 같은 주문은 같은 파티션에 들어가게 한다
await producer.send({
  topic: "orders",
  messages: [{ key: order.id, value: JSON.stringify({ type: "paid", orderId: order.id, version: 2 }) }],
});
```

SQS FIFO 큐는 메시지 그룹이 줄이다. `MessageGroupId`가 같은 메시지는 순서대로 하나씩 나가고, 한 그룹의 메시지가 처리 중(받았지만 지우지 않음)이면 그 그룹의 다음 메시지는 나가지 않는다. 그룹 수에는 제한이 없어서 주문 ID를 그대로 그룹으로 써도 된다. 대신 FIFO 큐는 처리량 한도가 표준 큐보다 낮다. 기본 모드는 API 동작마다 초당 300건(배치 10개로 묶으면 3,000건)이고, 높은 처리량 모드를 켜면 리전별로 그보다 훨씬 높은 한도를 준다.

```bash
# FIFO 큐에 주문 ID를 메시지 그룹으로 보낸다
aws sqs send-message \
  --queue-url https://sqs.us-east-1.amazonaws.com/111122223333/orders.fifo \
  --message-group-id ord_7 \
  --message-deduplication-id ord_7-paid-v2 \
  --message-body '{"type":"paid","orderId":"ord_7","version":2}'
```

`--message-deduplication-id`는 5분 안에 같은 ID로 다시 보낸 메시지를 버리는 중복 제거용이다. 순서와는 다른 장치지만 FIFO 큐에서는 함께 정해야 한다(큐에 내용 기반 중복 제거를 켜 두면 생략할 수 있다).

Azure Service Bus는 세션이 줄이다. 세션을 켠 큐에 `SessionId`를 붙여 보내면, 수신자가 세션 하나를 잠그고 그 세션의 메시지를 순서대로 받는다. 세션을 잠근 동안 다른 수신자는 그 세션을 받지 못한다. 세션마다 작은 상태(session state)를 저장할 수 있어서 "이 주문의 마지막으로 처리한 버전"을 거기에 둘 수도 있다.

세 방식 모두 같은 약속을 한다. 같은 키는 한 번에 한 소비자만, 순서대로. 다른 점은 줄의 수다. Kafka는 파티션 수로 고정되고, SQS FIFO 그룹과 Service Bus 세션은 키마다 줄이 따로 생긴다. 이 차이가 뒤에서 볼 핫 키의 피해 범위를 바꾼다.

## 재시도와 DLQ가 순서를 깨는 길

줄을 잘 세워도 순서는 실패 처리에서 깨진다. 가장 흔한 길은 "실패한 메시지를 뒤로 보내기"다. Kafka에서 처리에 실패한 메시지를 재시도 토픽으로 보내고 원래 파티션은 계속 읽는 구조가 흔한데, 그 순간 실패한 메시지는 줄에서 빠진다. 파티션 하나를 흉내 내 결제 이벤트가 한 번 실패하게 해 봤다.

```bash
# 파티션 하나와 재시도 토픽을 흉내 낸다. ord-7:paid가 한 번 실패한다
node retry.js
```

```text
apply  ord-7:created    state[ord-7]=created
fail   ord-7:paid -> retry topic
apply  ord-9:created    state[ord-9]=created
apply  ord-7:shipped    state[ord-7]=shipped
apply  ord-7:paid       state[ord-7]=paid
final {"ord-7":"paid","ord-9":"created"}
```

주문 7번은 배송됨까지 갔다가 재시도된 결제됨이 마지막에 반영되어 상태가 결제됨으로 돌아갔다. 아래 그림은 같은 과정을 칸 단위로 다시 보여 준다.

SQS FIFO는 기본 동작이 반대다. 실패한 메시지는 지워지지 않았으니 가시성 타임아웃 뒤 다시 나오고, 그동안 같은 그룹의 뒷 메시지는 나가지 않는다. 줄이 막히는 대신 순서는 지켜진다. 그런데 `maxReceiveCount`를 넘겨 DLQ로 옮겨지는 순간 줄이 다시 풀리고, 그 그룹의 뒷 메시지들이 실패한 메시지 없이 처리된다. 결국 DLQ로 가는 길이 순서를 깨는 길이다.

이걸 막는 방법은 대략 셋이다.

- 줄 안에서 기다린다: 실패한 메시지를 뒤로 보내지 않고 그 자리에서 백오프하며 재시도한다. 순서는 지켜지지만 그 파티션(또는 그룹) 전체가 멈춘다. 일시적인 장애에 맞다.
- 키를 격리한다: 실패한 메시지가 DLQ로 갈 때 그 키를 "격리됨"으로 표시하고, 같은 키의 뒷 메시지는 처리하지 않고 따로 쌓아 둔다(주차). 사람이 고친 뒤 격리된 메시지부터 차례로 다시 흘린다. 다른 키는 계속 흐른다.
- 순서에 덜 기대게 만든다: 메시지에 키별 버전(또는 시퀀스 번호)을 넣고, 컨슈머가 저장된 버전보다 낮은 메시지는 버린다. 위 장면에서 결제됨(v2)이 배송됨(v3) 뒤에 오면 무시된다. 대신 건너뛴 v2에 담긴 정보가 필요 없는지는 업무로 따져야 한다.

버전 확인은 DB 갱신 한 줄로 만든다. 저장된 버전보다 새 메시지의 버전이 클 때만 바뀌고, 0줄이 바뀌면 늦게 온 옛 메시지라는 뜻이다.

```sql
-- 저장된 버전보다 새로운 이벤트만 반영한다
UPDATE orders
SET status = 'paid', version = 2
WHERE id = 'ord_7' AND version < 2;
-- UPDATE 0 이면 이미 더 새로운 상태가 있다. 무시하고 ack한다
```

이 방식은 중복 메시지도 같이 걸러 준다. 같은 메시지가 두 번 와도 두 번째는 버전이 같아서 바뀌지 않는다. 중복 처리 쪽 이야기는 [메시지 전달 보장](/posts/message-delivery-semantics)과 [멱등성 키](/posts/idempotency-key)에서 이어진다.

순서를 깨는 길이 하나 더 있다. Kafka의 파티션 수를 늘리면 키가 가는 파티션이 바뀐다. 기본 파티셔너는 키의 해시를 파티션 수로 나눈 나머지를 쓰기 때문이다. 파티션을 12개에서 24개로 늘린 직후, 주문 7번의 옛 메시지는 3번 파티션에 남아 있고 새 메시지는 15번 파티션으로 간다. 두 파티션을 다른 컨슈머가 읽으면 새 메시지가 먼저 처리될 수 있다. 키 순서가 중요한 토픽은 처음부터 파티션을 넉넉히 잡거나, 늘릴 때 프로듀서를 잠깐 멈추고 옛 파티션의 랙이 0이 된 걸 본 뒤 재개한다.

## 보내는 쪽에서 먼저 섞이는 순서

컨슈머 쪽을 아무리 잘 만들어도, 브로커에 들어갈 때 이미 순서가 섞여 있으면 소용없다. 줄은 "브로커가 받은 순서"를 지켜 줄 뿐이다.

Kafka 프로듀서는 응답을 기다리지 않고 배치 여러 개를 동시에 보낼 수 있다(`max.in.flight.requests.per.connection`). 배치 1이 일시적인 오류로 실패하고 배치 2가 성공한 뒤 배치 1이 재시도되면, 파티션 안에서 배치 2가 앞에 놓인다. 멱등 프로듀서(`enable.idempotence=true`)를 켜면 브로커가 프로듀서의 시퀀스 번호를 보고 순서를 맞추므로, 동시에 보내는 배치가 5개 이하일 때 재시도가 있어도 순서가 지켜진다. Kafka 3.0부터는 이 설정과 `acks=all`이 기본값이지만, 옛 클라이언트나 설정을 직접 덮어쓴 프로듀서에서는 꺼져 있을 수 있다.

```properties
# 키별 순서가 필요한 토픽의 프로듀서 설정 (Java 클라이언트 이름 기준)
enable.idempotence=true
acks=all
max.in.flight.requests.per.connection=5   # 멱등 프로듀서에서 순서를 지키는 상한
retries=2147483647                        # 재시도는 delivery.timeout.ms가 끊는다
```

SQS FIFO도 같은 문제가 있다. 같은 그룹 ID의 메시지를 여러 스레드나 여러 인스턴스가 동시에 보내면, 그룹 안의 순서는 SQS가 받은 순서가 된다. 앱에서는 "생성 → 결제"로 보냈어도 두 요청이 다른 스레드에서 동시에 나갔다면 결제가 먼저 도착할 수 있다. 같은 키의 메시지는 한 곳에서 차례로 보내거나, 아웃박스 테이블에 시퀀스를 매겨 두고 릴레이 하나가 순서대로 내보내게 한다([트랜잭셔널 아웃박스](/posts/transactional-outbox)).

순서가 깨졌다는 의심이 들면 먼저 어디서 섞였는지부터 가른다. 메시지에 키별 시퀀스 번호를 넣어 두면, 브로커에 들어간 순서(Kafka라면 파티션과 오프셋)와 시퀀스를 나란히 놓고 볼 수 있다. 오프셋 순서와 시퀀스 순서가 다르면 보내는 쪽에서 섞인 것이고, 같은데 반영 결과가 틀렸다면 컨슈머의 재시도나 병렬 처리에서 섞인 것이다.

```bash
# 파티션 3의 메시지를 키·오프셋과 함께 본다 (Kafka에 들어 있는 kafka-console-consumer)
kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic orders --partition 3 --offset earliest --max-messages 20 \
  --property print.key=true --property print.offset=true
```

## 한 키가 줄 전체를 막을 때

키별 순서의 대가는 핫 키다. 키 하나에 메시지가 몰리면 그 키는 컨슈머 하나의 속도를 넘을 수 없다. 대형 판매자 한 곳의 주문이 전체의 40%라면, 판매자 ID를 키로 쓰는 순간 그 판매자의 줄이 전체 처리 시간을 정한다.

Kafka에서는 피해가 더 넓다. 그 핫 키와 같은 파티션에 해시된 다른 키들도 같은 줄에 서 있으니 함께 밀린다. 파티션 수를 늘려도 핫 키 자체는 여전히 한 파티션에 있다. 아래 함수로 키별 처리 시간이 파티션마다 어떻게 쌓이는지 계산해 볼 수 있다. 해시는 계산을 쉽게 하려고 키 글자 코드의 합으로 단순하게 잡았다.

네 번째 테스트가 핵심이다. 파티션을 두 배로 늘려도 가장 바쁜 파티션은 여전히 80이다. 병렬성을 늘리는 장치로는 핫 키를 풀 수 없다. 다섯 번째는 반대 경우로, 서로 다른 키라도 해시가 겹치면 한 줄에 서서 서로를 기다린다.

핫 키를 푸는 방법은 결국 키를 다시 고르는 것이다.

- 순서가 실제로 필요한 단위로 키를 좁힌다. 판매자 단위가 아니라 주문 단위로 순서가 필요하다면 키를 주문 ID로 바꾼다. 같은 판매자의 주문끼리는 순서가 필요 없다.
- 키 하나 안에서도 메시지 처리 시간을 줄인다. 외부 API 호출처럼 오래 걸리는 일은 순서가 필요 없는 다음 단계로 떼어 낸다. 줄 안에서는 상태 갱신만 하고, 느린 일은 다른 큐로 넘긴다.
- 정말 큰 키는 따로 뗀다. 대형 고객 하나를 전용 토픽이나 전용 큐로 옮기면 다른 키들이 그 줄에 같이 서지 않는다.
- 파티션 안에서 키별로 병렬 처리한다. 컨슈머가 파티션 하나를 받아 키마다 내부 줄을 만들고, 서로 다른 키는 동시에 처리하는 방식이다(Confluent Parallel Consumer 같은 라이브러리가 이렇게 한다). 오프셋 커밋이 복잡해지니 라이브러리에 맡기는 편이 낫다.

## 두 패턴을 같이 쓸 때

둘은 자주 함께 나온다. 순서가 필요한 주문 이벤트에 큰 첨부가 붙는 경우다. 이때 지켜야 할 것은 하나로 모인다. 메시지가 순서를 지켜 도착해도, 그 메시지가 가리키는 객체가 메시지와 같은 시점의 것이어야 한다.

그래서 순서가 필요한 메시지의 객체 키에는 버전을 넣는다. `orders/ord_7/v2.json`, `orders/ord_7/v3.json`처럼 버전마다 다른 객체를 두면, 늦게 처리되는 v2 메시지는 v2 객체를 읽는다. 같은 키 `orders/ord_7.json`에 덮어쓰면 v2 메시지가 v3 본문을 읽고, 위에서 만든 버전 확인은 v2라서 통과시키는 이상한 상태가 생긴다.

수명도 순서와 엮인다. 앞에서 키를 격리하고 뒷 메시지를 주차해 두는 방법을 썼다면, 그 메시지들이 기다리는 동안에도 객체가 살아 있어야 한다. 주차가 길어질 수 있는 시스템이라면 수명을 더 길게 두거나, 주차할 때 객체의 수명을 연장하는(태그를 바꿔 다른 수명 규칙에 걸리게 하는) 장치를 둔다.

## 현장에서 이 두 패턴이 아플 때

증상별로 먼저 볼 곳을 적어 둔다.

메시지가 가끔 거절된다. 실패한 메시지의 크기를 로그로 남기고 있는지부터 본다. 대부분 base64 인코딩이나 배열 필드가 커지는 경우다. 큐의 실제 한도(SQS의 `MaximumMessageSize`, Kafka의 토픽 `max.message.bytes`)를 확인하고, 한도 근처의 메시지가 늘고 있다면 한도를 올리기 전에 클레임 체크로 옮길 필드를 고른다.

```bash
# SQS 큐의 실제 최대 메시지 크기와 보관 기간을 본다
aws sqs get-queue-attributes \
  --queue-url https://sqs.us-east-1.amazonaws.com/111122223333/receipts \
  --attribute-names MaximumMessageSize MessageRetentionPeriod
```

컨슈머가 `NoSuchKey`로 실패한다. 객체 수명과 메시지 나이를 비교한다. SQS라면 메시지의 `ApproximateFirstReceiveTimestamp`와 `SentTimestamp`, 객체라면 업로드 시각을 본다. DLQ에서 되돌려 보낸 메시지에서만 나면 수명이 짧은 것이고, 새 메시지에서도 나면 업로드보다 메시지가 먼저 나가는 코드 경로가 있는 것이다.

클레임 버킷 요금이 계속 오른다. 수명 규칙이 실제로 걸려 있는지, 접두사 필터가 맞는지 본다. 덜 올라간 멀티파트 업로드는 객체 목록에 보이지 않으면서 요금이 나오니 `AbortIncompleteMultipartUpload` 규칙도 확인한다.

랙이 한 파티션에만 쌓인다. 파티션별 랙을 보고(`kafka-consumer-groups.sh --describe`), 그 파티션에 들어간 키 분포를 센다. 키 하나가 대부분이면 핫 키이고, 키가 고른데 그 파티션만 느리면 그 컨슈머 인스턴스나 그 키들의 처리 경로(특정 외부 API)가 느린 것이다. SQS FIFO에서는 처리 중인 메시지 수(`ApproximateNumberOfMessagesNotVisible`)가 줄지 않는지, 받은 메시지의 `ApproximateReceiveCount`가 계속 올라가는지 본다. 같은 메시지가 몇 번째로 다시 오고 있다면 그 그룹이 실패한 메시지 하나에 막혀 있는 것이다.

## 면접에서 나올 만한 질문

### 클레임 체크 패턴은 무엇이고 왜 쓰나?

큰 본문을 객체 저장소에 올리고 메시지에는 참조만 보내는 패턴이다. 브로커에는 크기 한도가 있고, 큰 메시지는 메모리, 복제, 보관 비용을 메시지 수만큼 키운다. 구독자 대부분이 본문 전체가 필요 없다는 점도 이유다. 참조로 보내면 메시지는 작게 유지되고 필요한 쪽만 본문을 꺼낸다.

### 본문 업로드와 메시지 보내기는 어떤 순서로 하나?

업로드를 먼저 하고 성공을 확인한 뒤 메시지를 보낸다. 반대로 하면 받는 쪽이 아직 없는 객체를 읽으려 한다. S3는 새로 쓴 객체를 바로 읽을 수 있는 강한 일관성을 줘서, 업로드 성공 뒤 보낸 메시지라면 항상 읽힌다. 키는 매번 새로 만들거나 내용 해시로 정하고 덮어쓰지 않는다. 덮어쓰면 늦게 처리되는 옛 메시지가 새 본문을 읽는다.

### 객체는 언제 지우나?

대개 수명 규칙에 맡기고, 수명은 메시지가 살아 있을 수 있는 가장 긴 시간보다 길게 둔다. 원래 큐 보관 기간, DLQ 보관 기간, 사람이 고쳐서 되돌려 보내는 시간까지 더한다. 구독자가 여럿이면 한 컨슈머가 지울 때 다른 구독자의 메시지가 참조를 잃는다. 객체를 못 찾는 메시지는 재시도해도 결과가 같으니 바로 DLQ로 보내고 그 건수에 알림을 건다.

### 순차 호송 패턴은 무엇인가?

전체 순서 대신 키별 순서만 지키고, 키가 다르면 병렬로 처리하는 패턴이다. 같은 주문의 이벤트끼리만 순서가 맞으면 되는 경우가 대부분이라, 키마다 줄을 세우고 줄끼리 동시에 처리한다. Kafka는 키 해시로 고른 파티션, SQS FIFO는 MessageGroupId, Azure Service Bus는 세션이 그 줄이다.

### 키별 순서를 지켰는데도 순서가 깨질 수 있나?

실패 처리에서 깨진다. 실패한 메시지를 재시도 토픽으로 보내고 파티션을 계속 읽으면 같은 키의 뒷 메시지가 앞질러 간다. SQS FIFO는 실패하면 그룹을 막아 순서를 지키지만, maxReceiveCount를 넘겨 DLQ로 옮겨지면 뒷 메시지가 처리된다. Kafka 파티션 수를 늘려 키의 파티션이 바뀌는 순간에도 깨진다. 그래서 키별 버전을 넣어 오래된 메시지를 버리거나, 실패한 키를 격리하고 뒷 메시지를 주차한다.

### 브로커에 들어가기 전에 순서가 바뀔 수도 있나?

바뀐다. Kafka 프로듀서가 배치 여러 개를 동시에 보내다가 앞 배치만 재시도되면 파티션 안에서 순서가 뒤집힌다. 멱등 프로듀서를 켜면 시퀀스 번호로 순서를 맞춰 주고, Kafka 3.0부터는 기본값이다. SQS FIFO도 같은 그룹을 여러 스레드가 동시에 보내면 SQS가 받은 순서가 곧 그룹의 순서가 되니, 같은 키는 한 곳에서 차례로 보낸다.

### 핫 키가 한 파티션을 막으면 어떻게 하나?

파티션을 늘리는 건 답이 아니다. 핫 키는 여전히 한 파티션에 있고 그 파티션은 컨슈머 하나의 속도를 넘지 못한다. 순서가 실제로 필요한 단위로 키를 좁히거나(판매자 대신 주문), 줄 안의 처리를 상태 갱신만 남기고 줄이거나, 큰 키를 전용 토픽으로 떼어 낸다. 파티션 안에서 키별로 병렬 처리하는 컨슈머 라이브러리를 쓰는 방법도 있다.

### 순서가 필요한 메시지에 클레임 체크를 함께 쓰면 무엇을 조심하나?

메시지와 객체가 같은 시점의 것이어야 한다. 객체 키에 버전을 넣어 버전마다 다른 객체를 두고 덮어쓰지 않는다. 같은 키에 덮어쓰면 늦게 처리되는 옛 메시지가 새 본문을 읽는다. 키를 격리해 메시지를 오래 주차하는 구조라면 그 기간까지 객체 수명이 버텨야 한다.
