메인 페이지에 들어왔을 뿐인데 개발자 도구 Network 탭에 `main.js` 하나가 압축해서 400KB로 찍힌다. 열어 보면 관리자 화면의 표 컴포넌트, 글 편집기, 차트 라이브러리, 날짜 라이브러리의 모든 로케일이 들어 있다. 이 사용자는 관리자 화면에 들어갈 일이 평생 없다.

번들러는 기본적으로 진입점에서 닿는 모든 코드를 한 파일로 묶는다(모듈을 찾고 묶는 과정은 [번들러 기초](/posts/bundler-basics)에서 따로 다룬다). 앱이 커질수록 첫 화면과 상관없는 코드가 첫 화면의 비용이 된다. 이걸 덜어 내는 방법이 둘 있다. 지금 필요 없는 코드를 뒤로 미루는 코드 스플리팅, 아예 쓰지 않는 코드를 빼는 트리 셰이킹이다.

## import()가 번들을 가르는 자리

코드 스플리팅의 출발점은 동적 `import()`다. 파일 맨 위의 `import` 문은 정적이라 번들러가 같은 파일에 묶는다. 함수처럼 부르는 `import()`는 Promise를 돌려주고, 번들러는 이걸 보면 그 모듈을 별도 파일(청크)로 떼어 낸다.

```js
button.addEventListener("click", async () => {
  const { openEditor } = await import("./editor");
  openEditor();
});
```

빌드 결과에는 `main.js`와 별도의 `editor.[hash].js`가 생긴다. 버튼을 누르기 전에는 편집기 코드를 받지도 실행하지도 않는다. 대신 처음 누를 때 네트워크 왕복 한 번만큼 늦어진다. 코드 스플리팅은 첫 화면의 비용을 나중 동작의 지연과 맞바꾸는 일이다.

경로에 변수를 넣으면 번들러는 어떤 파일이 올지 모른다. 그래서 `` import(`./locales/${lang}.json`) ``처럼 쓰면 `locales` 폴더에서 패턴에 맞는 파일마다 청크를 하나씩 만든다. 언어별로 하나씩만 받게 되니 의도한 대로라면 좋지만, 폴더에 큰 파일이 섞여 있으면 그것도 청크가 된다.

## 라우트로 자를까, 컴포넌트로 자를까

어디서 자를지는 두 가지 기준이 있다.

라우트 단위는 페이지마다 자르는 것이다. 사용자는 한 번에 한 페이지만 보니 가장 손해가 적고 효과가 크다. Next.js의 App Router는 라우트 세그먼트마다 자동으로 자른다. React Router라면 라우트의 컴포넌트를 `lazy`로 불러온다.

컴포넌트 단위는 한 페이지 안에서도 당장 안 보이는 덩어리를 떼어 내는 것이다. 모달, 탭 뒤의 차트, 스크롤해야 보이는 댓글 편집기, 무거운 지도 같은 것이다. React에서는 `React.lazy`와 `Suspense`를 쓴다.

```jsx
import { lazy, Suspense } from "react";

const Chart = lazy(() => import("./chart"));
// default export가 아니라면 모양을 맞춰 준다
const Map = lazy(() => import("./map").then((m) => ({ default: m.Map })));

function Stats({ open }) {
  return open ? (
    <Suspense fallback={<div style={{ height: 320 }} />}>
      <Chart />
    </Suspense>
  ) : null;
}
```

`fallback`에 실제 컴포넌트와 같은 높이를 주는 데는 이유가 있다. 높이 없는 스피너를 두면 차트가 도착하는 순간 아래 내용이 밀려서 CLS가 생긴다.

Next.js에서는 `next/dynamic`이 같은 일을 한다. `ssr: false`를 주면 서버 렌더링을 건너뛰고 브라우저에서만 불러온다. `window`를 바로 만지는 라이브러리에 쓰는데, App Router에서는 이 옵션을 클라이언트 컴포넌트 안에서만 쓸 수 있다.

```jsx
"use client";
import dynamic from "next/dynamic";

const Editor = dynamic(() => import("./editor"), {
  ssr: false,
  loading: () => <div style={{ height: 480 }} />,
});
```

첫 화면에 보이는 컴포넌트는 자르지 않는다. 잘라 봐야 어차피 바로 받아야 하고, 요청 하나와 렌더링 한 번이 더 늦어질 뿐이다. 특히 LCP 요소를 품은 컴포넌트를 lazy로 만들면 LCP가 그대로 밀린다.

## 안 쓰는 export를 털어 내기

코드 스플리팅은 코드를 뒤로 미룰 뿐 줄이지는 않는다. 아예 안 쓰는 코드를 빼는 건 트리 셰이킹이다. 나무를 흔들어 죽은 잎을 떨어뜨린다는 비유에서 이름이 나왔다.

이게 가능한 건 ES 모듈의 `import`·`export`가 정적이기 때문이다. 파일 맨 위에만 올 수 있고, 조건문 안에 넣을 수 없고, 가져오는 이름이 문자열 그대로 적혀 있다. 그래서 번들러는 코드를 실행하지 않고도 누가 무엇을 가져가는지 알 수 있다.

## 사이드 이펙트가 있으면 지우지 못한다

모듈을 import하는 것만으로 무언가 일어나는 경우가 있다. 전역 객체에 폴리필을 붙이는 코드, CSS 파일, `Array.prototype`을 고치는 코드, 모듈 최상위에서 이벤트를 등록하는 코드다. 이런 걸 사이드 이펙트라고 한다.

```js
import "./polyfills"; // 가져오는 이름이 없지만 지우면 안 된다
import "./button.css";
```

번들러는 모듈의 export를 아무도 쓰지 않아도, 그 모듈을 실행했을 때 무슨 일이 생기는지 확신하지 못하면 남겨 둔다. 이 판단을 돕는 게 `package.json`의 `sideEffects` 필드다.

```json
{
  "sideEffects": ["*.css", "./src/polyfills.js"]
}
```

`false`로 적으면 "이 패키지의 모든 파일은 가져다 쓰지 않으면 지워도 된다"는 약속이다. 흔한 실수가 여기서 나온다. CSS를 `import "./button.css"`로 불러오는 프로젝트에 `"sideEffects": false`를 적으면, 가져다 쓰는 이름이 없는 CSS import가 통째로 사라져서 프로덕션에서만 스타일이 깨진다. 위처럼 CSS와 폴리필을 목록으로 빼 둔다.

함수 호출 하나에도 같은 문제가 있다. 모듈 최상위의 `const Button = styled.button(...)`은 결과를 아무도 안 써도, 미니파이어는 함수 호출이 뭔가를 바꿀지 몰라 남긴다. `/*#__PURE__*/` 주석은 "이 호출은 결과를 안 쓰면 지워도 된다"고 알려 준다. 라이브러리 빌드 도구와 Babel 플러그인이 이 주석을 자동으로 붙이는 경우가 많다.

## CommonJS는 흔들어도 안 떨어진다

`require`와 `module.exports`를 쓰는 CommonJS는 트리 셰이킹이 거의 안 된다. `require`는 함수 호출이라 조건문 안에서도 부를 수 있고, 경로를 변수로 만들 수도 있다. `module.exports`는 평범한 객체라 실행 중에 속성을 추가하거나 `exports[name] = fn`처럼 계산된 이름으로 넣을 수 있다. 실행해 보기 전에는 무엇이 export되는지 확정할 수 없으니, 번들러는 안전하게 통째로 넣는다. webpack 5가 단순한 CommonJS 패턴 일부를 분석하긴 하지만 ES 모듈만큼 믿을 수는 없다.

대표적인 예가 lodash다. `lodash` 패키지는 CommonJS라서 `import { debounce } from "lodash"`라고 써도 라이브러리 전체(minify 기준 70KB 안팎)가 들어온다. ES 모듈로 배포하는 `lodash-es`를 쓰거나, `lodash/debounce`처럼 파일 하나를 직접 가져오면 해결된다.

라이브러리를 고를 때 `package.json`에 `"module"` 필드나 `"exports"`의 `"import"` 조건이 있는지 보면 ES 모듈 빌드를 제공하는지 알 수 있다. 내 라이브러리를 배포할 때도 ES 모듈 빌드와 `sideEffects`를 함께 내보내야 쓰는 쪽에서 트리 셰이킹이 된다. 또 Babel 설정에서 `modules: "commonjs"`로 모듈을 변환해 버리면 번들러가 ES 모듈을 볼 기회 자체가 사라지니 `modules: false`로 둔다.

## 배럴 파일이 끌고 오는 것들

폴더마다 `index.ts`를 두고 안의 모듈을 모두 다시 내보내는 파일을 배럴(barrel) 파일이라고 한다. import 경로가 짧고 깔끔해진다.

```ts
// components/index.ts
export * from "./button";
export * from "./data-grid"; // 무거운 표 컴포넌트
export * from "./rich-editor"; // 더 무거운 편집기
```

```ts
import { Button } from "@/components"; // Button 하나만 쓰고 싶었다
```

번들러가 `Button`만 남기려면 `data-grid`와 `rich-editor`를 실행하지 않아도 된다는 확신이 있어야 한다. `sideEffects`가 없으면 그 확신이 없으니 세 모듈을 모두 끌고 온다. 프로덕션 번들만의 문제도 아니다. 개발 서버와 테스트 러너는 트리 셰이킹을 하지 않아서, 버튼 하나를 가져오려고 배럴 아래의 모듈 수백 개를 매번 변환하고 실행한다. 아이콘 라이브러리처럼 export가 수천 개인 패키지에서 개발 서버가 눈에 띄게 느려지는 이유다.

대책은 `sideEffects`를 정확히 적거나, 무거운 모듈은 배럴에서 빼고 경로를 직접 적어 가져오는 것이다. Next.js에는 이런 패키지의 import를 실제 파일 경로로 바꿔 주는 `optimizePackageImports` 옵션이 있다(버전에 따라 `experimental` 아래에 있다).

## 번들 안을 들여다보기

줄이기 전에 무엇이 들어 있는지부터 본다. 짐작으로 고르면 2KB짜리를 떼어 내느라 하루를 쓰고, 정작 300KB짜리 로케일 데이터는 못 본다.

- `webpack-bundle-analyzer`(Next.js는 `@next/bundle-analyzer`)는 청크마다 모듈 크기를 사각형 넓이로 그려 준다. stat은 변환 전, parsed는 minify 후, gzip은 압축 후 크기다. 실행 비용은 parsed, 전송 비용은 gzip을 본다.
- `source-map-explorer`는 소스맵만 있으면 번들러와 상관없이 쓸 수 있다. `npx source-map-explorer dist/assets/*.js`처럼 돌린다.
- 크롬 개발자 도구의 Coverage 패널은 페이지를 쓰는 동안 실제로 실행된 바이트를 빨강·초록으로 보여 준다. 첫 화면에서 실행되지 않는 비율이 높다면 자를 곳이 있다는 뜻이다.

찾게 되는 건 대개 비슷하다. 날짜 라이브러리의 모든 로케일, 같은 라이브러리의 버전 두 개(의존성끼리 버전이 안 맞아서), CommonJS로 들어온 유틸 라이브러리, 서버에서만 써야 할 코드가 클라이언트 번들에 섞인 경우다. 번들 크기 예산을 CI에 걸어 두면(`size-limit` 같은 도구) 다시 커지는 걸 막을 수 있다.

## 파일 이름에 내용의 지문을 넣는다

코드를 쪼개는 데는 캐시 이점도 있다. 청크 이름에 내용 해시를 넣으면, 바뀐 청크만 이름이 바뀐다. 편집기 코드에 `return 1;` 한 줄을 넣으면 위 예의 해시는 `f4989926`에서 `48f13322`로 바뀌고, 나머지 청크 이름은 그대로다. 사용자는 바뀐 청크 하나만 새로 받는다.

이름이 내용을 대표하니 해시가 붙은 파일은 영원히 캐시해도 된다. 대신 그 파일 이름을 적고 있는 HTML은 캐시하지 않는다.

```
/assets/*.js   Cache-Control: public, max-age=31536000, immutable
/index.html    Cache-Control: no-cache
```

`immutable`은 새로고침해도 서버에 다시 확인하지 말라는 뜻이다. `no-cache`는 캐시하지 말라는 게 아니라 쓸 때마다 서버에 바뀌었는지 물어보라는 뜻이다.

해시가 쓸데없이 바뀌는 함정도 있다. 청크 사이의 연결 정보(어떤 ID의 청크가 어떤 파일 이름인지)를 담은 런타임 코드가 진입 청크 안에 있으면, 아무 청크 하나만 바뀌어도 진입 청크의 해시까지 바뀐다. webpack에서는 `runtimeChunk: "single"`로 런타임을 따로 빼고, 모듈 ID를 내용 기반으로 정하는 `moduleIds: "deterministic"`(webpack 5 프로덕션 기본값)을 쓴다.

배포 직후의 장애도 알아 둔다. 사용자가 이전 버전의 HTML을 열어 둔 상태에서 새 배포가 이전 청크 파일을 지우면, 나중에 그 페이지에서 동적 import가 없는 파일을 요청해 `ChunkLoadError`가 난다. 이전 버전 파일을 한동안 남겨 두거나, 이 에러를 잡으면 페이지를 새로 고치게 한다.

## 배포 직후 쏟아지는 청크 에러, 한 줄에 불어난 번들

코드를 쪼개고 나면 운영에서 새로 생기는 장애가 하나 있다. 배포 직후 몇십 분 동안 에러 수집기에 청크 로드 실패가 몰린다. 앞에서 말한 "옛 HTML이 지워진 청크를 찾는" 상황을 로컬에서 그대로 만들었다. 페이지를 연 뒤 서버에서 `editor.f4989926.js`를 지우고(새 배포), 그다음 편집기 버튼을 눌렀다. 크롬 141의 콘솔이다.

```text
# 서버가 지운 파일에 404를 줄 때
[console.error] Failed to load resource: the server responded with a status of 404 (Not Found)
[catch] TypeError: Failed to fetch dynamically imported module: http://localhost:8051/assets/editor.f4989926.js

# 서버가 없는 경로에 SPA 폴백으로 index.html을 200으로 줄 때
[console.error] Failed to load module script: Expected a JavaScript-or-Wasm module script but the server responded with a MIME type of "text/html". Strict MIME type checking is enforced for module scripts per HTML spec.
[catch] TypeError: Failed to fetch dynamically imported module: http://localhost:8052/assets/editor.f4989926.js
```

네이티브 `import()`를 쓰는 Vite 계열 빌드에서는 이 문장으로 보이고, webpack은 자기 런타임이 청크를 받기 때문에 `ChunkLoadError: Loading chunk 123 failed.` 형태로 보인다. 이름은 달라도 원인은 같다. 두 번째 경우처럼 MIME 타입 에러가 같이 찍히면 정적 호스팅의 폴백 규칙이 `/assets/` 아래까지 덮고 있다는 뜻이다. 없는 JS 파일은 HTML이 아니라 404를 돌려주게 해야 원인이 바로 보인다.

에러가 배포 시각부터 늘었다가 서서히 줄어든다면 이 경우다. 줄어드는 건 옛 탭을 들고 있던 사용자들이 새로 고치거나 탭을 닫기 때문이다. 확인은 세 가지로 한다. 에러 이벤트의 청크 파일명이 지금 배포에 있는지, 그 사용자가 페이지를 연 시각이 배포 전인지, 서버 로그에 그 파일명의 404가 있는지다.

대응은 두 겹으로 둔다. 서버 쪽에서는 이전 한두 번 배포의 해시 파일을 지우지 않고 남긴다. 해시가 다르니 새 파일과 섞일 일이 없다. 화면 쪽에서는 이 에러를 잡았을 때 한 번만 새로 고친다.

```js
async function loadEditor() {
  try {
    const m = await import("./editor");
    sessionStorage.removeItem("chunk-reload"); // 성공하면 표시를 지운다
    return m;
  } catch (e) {
    // 새로 고쳤는데도 실패하면 진짜 장애다. 무한 새로고침을 막는다
    if (!sessionStorage.getItem("chunk-reload")) {
      sessionStorage.setItem("chunk-reload", "1");
      location.reload();
    }
    throw e;
  }
}
```

Vite는 자기가 만든 preload 단계에서 실패하면 `window`에 `vite:preloadError` 이벤트를 보내 주니, 앱 진입점에서 이 이벤트를 받아 같은 처리를 해도 된다. 표시를 지우지 않는 실수가 흔하다. 그러면 한 번 새로 고친 사용자는 그 탭에서 다음 배포 때 자동 복구를 못 받는다. 반대로 횟수 제한 없이 새로 고치게 두면, 파일이 정말 없을 때 탭이 새로고침을 반복한다.

두 번째로 자주 보는 건 "기능 하나 넣었을 뿐인데 번들 크기 검사가 깨졌다"는 PR이다. diff를 보면 대개 import 한 줄이다. esbuild 0.24로 같은 `debounce` 하나를 세 가지 방식으로 가져와 minify한 결과다.

```bash
# 같은 함수를 세 가지 방식으로 가져와 각각 번들하고 크기를 잰다
for f in a b c; do
  npx esbuild $f.js --bundle --minify --format=esm --outfile=out-$f.js
  echo "$(wc -c < out-$f.js) bytes, gzip $(gzip -9c out-$f.js | wc -c) bytes"
done
```

```text
import { debounce } from "lodash"        73473 bytes  gzip 26327 bytes
import { debounce } from "lodash-es"      2858 bytes  gzip 1419 bytes
import debounce from "lodash/debounce"    3441 bytes  gzip 1618 bytes
```

CommonJS인 `lodash`는 함수 하나를 가져와도 라이브러리 전체가 들어와 25배가 된다. 앞에서 말한 "흔들어도 안 떨어진다"가 이 숫자다. PR에서 크기가 갑자기 늘면 새로 들어온 import가 CommonJS 패키지인지, 배럴 파일을 거치는지부터 본다. `size-limit` 같은 도구를 CI에 걸어 두면 이런 PR이 머지 전에 숫자로 걸린다. 다만 예산은 gzip 크기와 minify 크기를 둘 다 본다. 전송량은 gzip이 정하지만 파싱과 실행 비용은 풀린 크기를 따르기 때문이다.

## 덜 보내는 게 가장 빠르다

처음 장면의 400KB짜리 `main.js`로 돌아가 보면 순서가 보인다. 먼저 분석 도구로 무엇이 들어 있는지 보고, CommonJS 라이브러리와 배럴 파일처럼 트리 셰이킹을 막는 것을 치워서 안 쓰는 코드를 뺀다. 그다음 관리자 화면과 편집기처럼 첫 화면에 필요 없는 것을 라우트와 컴포넌트 단위로 잘라 뒤로 미룬다. 잘라 낸 것 중 곧 쓸 것만 미리 받고, 내용 해시로 캐시를 오래 유지한다. 쪼갤 때마다 워터폴이 생기지 않았는지 확인하고, 마지막에는 번들 크기가 아니라 실제 사용자의 LCP와 INP로 효과를 잰다.

## 면접에서 나올 만한 질문

### 번들이 크면 왜 느린가요? 압축하면 해결되지 않나요?

다운로드 뒤에 압축 해제, 파싱, 컴파일, 실행이 이어지고 실행은 메인 스레드에서 한다. 압축은 전송량만 줄일 뿐, 이후 단계의 비용은 풀린 코드 크기를 따른다. 그래서 저가형 모바일에서는 받은 뒤의 처리 시간이 더 길기도 하고, 그동안 입력을 처리하지 못해 INP가 나빠진다.

### 코드 스플리팅은 어떻게 동작하나요?

번들러가 동적 `import()`를 만나면 그 모듈을 별도 청크로 떼어 내고, 호출 시점에 그 파일을 받아 실행하는 코드로 바꾼다. React에서는 `React.lazy`와 `Suspense`, Next.js에서는 `next/dynamic`으로 컴포넌트를 나누고, 라우트 단위 분할은 프레임워크가 자동으로 해 주는 경우가 많다. 첫 화면 비용을 줄이는 대신 그 기능을 처음 쓸 때 네트워크 왕복만큼 늦어지는 교환이다.

### 라우트 단위와 컴포넌트 단위 분할은 언제 쓰나요?

라우트 단위가 기본이다. 사용자가 한 번에 한 페이지만 보니 손해가 적고 효과가 크다. 컴포넌트 단위는 모달, 탭 뒤의 차트, 편집기처럼 당장 안 보이면서 무거운 것에만 쓴다. 첫 화면에 보이는 컴포넌트, 특히 LCP 요소를 품은 것은 자르면 오히려 느려지고, `fallback`은 실제 크기로 잡아 CLS를 막는다.

### 트리 셰이킹은 어떻게 동작하고, 왜 ES 모듈에서만 잘 되나요?

ES 모듈의 import·export는 정적이라 실행하지 않고도 어떤 export가 쓰이는지 알 수 있다. 번들러가 쓰이지 않는 export를 표시하고 미니파이어가 죽은 코드로 지운다. CommonJS의 `require`는 조건문 안에서도 부를 수 있는 함수 호출이고 `module.exports`는 실행 중에 바뀌는 객체라 미리 확정할 수 없어서, 번들러가 통째로 넣는다.

### package.json의 sideEffects 필드는 무엇이고, 잘못 쓰면 어떻게 되나요?

모듈을 import만 해도 무언가 일어나는지 번들러에 알려 주는 필드다. `false`면 쓰이지 않는 모듈은 통째로 지워도 된다는 뜻이라 배럴 파일 아래의 안 쓰는 모듈까지 뺄 수 있다. 그런데 `import "./style.css"`나 폴리필이 있는 프로젝트에 그냥 `false`를 적으면 그 import가 지워져 프로덕션에서만 스타일이 깨지니, 그런 파일은 배열로 빼서 적는다.

### 배럴 파일이 성능에 왜 문제가 되나요?

`index.ts`가 여러 모듈을 다시 내보내면, 하나만 가져와도 번들러는 사이드 이펙트가 없다는 확신이 없을 때 나머지 모듈을 모두 포함한다. 개발 서버와 테스트는 트리 셰이킹을 하지 않아서 매번 배럴 아래 모듈 전부를 변환하고 실행해 느려진다. `sideEffects`를 정확히 적거나, 무거운 모듈은 직접 경로로 가져오거나, Next.js의 `optimizePackageImports`를 쓴다.

### prefetch와 preload의 차이는요?

preload는 지금 페이지에 곧 필요한 리소스를 높은 우선순위로 당장 받고, prefetch는 다음 이동에 쓸 것을 한가할 때 낮은 우선순위로 받아 둔다. preload를 남발하면 정말 급한 CSS나 LCP 이미지와 대역폭을 다투고, prefetch는 안 쓰면 사용자 데이터를 낭비한다. 그래서 갈 확률이 높은 곳만 prefetch하고, 보통 링크가 보이거나 마우스를 올렸을 때 시작한다.

### 너무 잘게 쪼개면 어떤 문제가 생기나요?

청크가 다른 청크를 동적으로 부르는 구조가 깊어지면, 앞 청크를 실행해야 다음 청크를 알게 되어 왕복이 줄줄이 쌓이는 워터폴이 생긴다. 파일이 많으면 요청마다 처리 비용이 붙고 압축 효율도 떨어진다. 함께 쓰이는 것은 같은 청크로 합치고, 나눠야 하면 나란히 요청하거나 modulepreload로 미리 알린다. 해시를 붙인 청크는 `immutable`로 오래 캐시하고, 배포 직후 이전 청크가 사라져 나는 `ChunkLoadError`에 대비한다.
