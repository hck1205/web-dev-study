양수 배열에서 합이 목표 이상이 되는 가장 짧은 연속 구간을 찾는 문제다. [슬라이딩 윈도 패턴](/posts/sliding-window-pattern)의 "가장 짧은 창" 틀이 거의 그대로 답이고, 같은 글의 "창이 통하지 않는 입력"에서는 이 문제에 음수를 넣어 창이 틀리는 모습도 봤다. 그래서 이 글은 틀을 다시 설명하기보다 이 문제가 따로 묻는 것에 집중한다.

LeetCode가 문제 끝에 붙여 둔 꼬리 질문이 하나 있다. O(n) 풀이를 찾았다면 O(n log n) 풀이도 짜 보라는 것이다. 더 느린 풀이를 왜 짜 보라는 걸까. 누적 합과 이분 탐색이라는 다른 도구로 같은 문제를 푸는 연습이고, 실제로 음수가 섞인 변형으로 넘어갈 때 창이 아니라 그쪽 도구가 살아남는다. 이 글은 출발점마다 더하기, 누적 합 위의 이분 탐색, 길이 이분 탐색, 창 네 가지를 보고, 음수 변형(862번)을 푸는 덱 풀이까지 간다. 문제 원문은 [LeetCode 209](https://leetcode.com/problems/minimum-size-subarray-sum/)다. 코드는 Node.js 22, Python 3.13, Java로 모두 돌렸다.

## 합이 target에 닿는 가장 짧은 구간

양의 정수 배열 `nums`와 양의 정수 `target`이 주어진다. 합이 `target` 이상인 연속 부분 배열 가운데 가장 짧은 것의 길이를 구한다. 그런 구간이 없으면 0을 돌려준다.

풀이에 영향을 주는 조건은 이렇다.

- 배열 길이는 1 이상 10만 이하다. O(n²)은 50억 번 근처라 위험하다.
- 원소는 1 이상 1만 이하다. 모두 양수라는 게 이 문제의 전부라고 해도 될 만큼 중요하다. 구간을 늘리면 합이 반드시 커지고, 줄이면 반드시 작아진다.
- `target`은 1 이상 10억 이하다. 배열 합의 최댓값도 10만 × 1만 = 10억이라 Java `int`(약 21억)에 들어간다. 오버플로 걱정은 없지만 여유가 크지 않다는 건 알아 둔다.
- 답이 없을 수 있다. 전체 합이 `target`보다 작으면 0이다.

## 일곱 칸으로 손풀기

예시는 `target = 8`, `nums = [1, 4, 2, 1, 5, 3, 1]`이다. 길이별로 합이 8 이상인 구간이 있는지 본다.

```text
길이  합이 가장 큰 구간    합    8 이상?
 1    [5]                  5     아니다
 2    [5, 3]               8     그렇다
```

길이 2에서 바로 찾았다. 답은 2, 4번과 5번 칸 `[5, 3]`이다.

답이 없는 경우도 손으로 한 번 본다. 같은 배열에 `target = 18`이면 전체 합이 1 + 4 + 2 + 1 + 5 + 3 + 1 = 17이라 어떤 구간도 18에 닿지 못한다. 답은 0이다. 전체 합이 모자란지는 한 번 더하면 바로 알 수 있어서, 풀이 앞에 이 검사를 넣으면 답이 없는 입력을 빨리 끝낼 수 있다. 길이 이분 탐색 풀이가 `ok(n)`부터 보는 게 이 검사다. 길이 2짜리 구간을 다 보면 1+4, 4+2, 2+1, 1+5, 5+3, 3+1이라 합이 5, 6, 3, 6, 8, 4다. 8 이상인 건 하나뿐이다.

일곱 칸짜리 배열에는 연속 구간이 7 × 8 / 2 = 28개 있다. 손으로는 다 볼 만하지만 길이 10만이면 50억 개다. 아래 풀이들은 이 28개 가운데 볼 필요가 없는 것을 얼마나 많이 건너뛰느냐로 나뉜다. 창은 많아야 2n번, 여기서는 14번 정도만 움직인다.

하나 더 보이는 게 있다. 어떤 구간이 조건을 만족하면 그걸 감싸는 더 긴 구간도 모두 만족한다. 원소가 양수라 칸을 보탤수록 합이 커지기 때문이다. 반대로 어떤 구간이 모자라면 그 안에 든 짧은 구간도 모두 모자라다. 이 두 줄이 아래 풀이 모두의 근거다.

## 출발점마다 합이 찰 때까지 더한다

출발점 `i`를 고정하고 오른쪽으로 하나씩 더하다가 합이 `target`에 닿으면 멈춘다. 더 가면 길이만 늘어나니 멈춰도 된다.

```js
function minBrute(target, nums) {
  let best = Infinity;
  for (let i = 0; i < nums.length; i++) {
    let sum = 0;
    for (let j = i; j < nums.length; j++) {
      sum += nums[j];
      if (sum >= target) {            // i에서 출발하는 가장 짧은 구간
        best = Math.min(best, j - i + 1);
        break;                        // 더 길게 볼 필요가 없다
      }
    }
  }
  return best === Infinity ? 0 : best; // 한 번도 못 찾았으면 0
}
```

구간마다 합을 처음부터 다시 구하면 O(n³)인데, 출발점 안에서 합을 이어 더하니 O(n²)이다. 공간은 O(1)이다. 길이 10만, 원소 1~1만 무작위, 답이 4만 칸쯤 되게 `target`을 2억으로 둔 입력에서 3.4초가 걸렸다. 출발점마다 4만 칸씩 더한 셈이다.

`break`는 위에서 본 "감싸는 구간도 만족한다" 덕분에 맞다. 하지만 출발점이 하나 옮겨질 때마다 거의 같은 덧셈을 처음부터 다시 한다. 0번 출발에서 1번부터 4만 번 칸까지 더한 합이 있는데, 1번 출발에서 그걸 또 더한다.

## 누적 합 위에서 끝점을 이분 탐색한다

반복되는 덧셈을 없애는 표준 도구가 누적 합이다. `pre[i]`를 앞에서 i칸의 합으로 두면(`pre[0] = 0`) i번부터 j − 1번까지의 합은 `pre[j] - pre[i]`로 한 번에 나온다. 누적 합 자체는 [배열과 행렬](/posts/ds-array-matrix)에서 다뤘다.

그리고 원소가 양수라 `pre`는 오름차순이다. 출발점 i에서 합이 `target` 이상이 되는 첫 끝점은 `pre[j] >= pre[i] + target`인 가장 작은 j다. 정렬된 배열에서 "처음으로 어떤 값 이상인 자리"를 찾는 것이니 [이분 탐색](/posts/binary-search)의 lower bound다.

```js
function minPrefixBS(target, nums) {
  const n = nums.length;
  const pre = new Array(n + 1).fill(0); // pre[i] = 앞에서 i칸의 합
  for (let i = 0; i < n; i++) pre[i + 1] = pre[i] + nums[i];
  let best = Infinity;
  for (let i = 0; i < n; i++) {
    const want = pre[i] + target;  // pre[j]가 이 값 이상이면 i..j-1의 합이 target 이상
    let lo = i + 1, hi = n + 1;    // [i+1, n] 안에서 찾고, 없으면 n+1
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (pre[mid] >= want) hi = mid;
      else lo = mid + 1;
    }
    if (lo <= n) best = Math.min(best, lo - i); // 구간 i..lo-1의 길이
  }
  return best === Infinity ? 0 : best;
}
```

시간은 누적 합 O(n), 출발점마다 O(log n)이라 O(n log n)이다. 공간은 `pre` 배열 O(n)이다. 같은 입력에서 6.1ms였다. 브루트포스의 3.4초와 비교하면 500배 넘게 빠르다.

이분 탐색의 경계를 짚어 둔다. `hi`를 `n`이 아니라 `n + 1`로 잡은 건 "없다"를 표현하려는 것이다. 끝까지 더해도 모자라면 `lo`가 `n + 1`에 머물고, `lo <= n` 검사가 그 경우를 걸러 낸다. `hi = n`으로 잡으면 마지막 칸이 정답인 경우와 없는 경우가 둘 다 `lo = n`으로 끝나 구분이 안 된다.

## 길이를 정해 놓고 창 합을 본다

이분 탐색을 길이 쪽에 걸 수도 있다. "길이 L로 되는 구간이 있나"는 L이 커질수록 아니오에서 예로 한 번만 바뀐다. 길이 L로 되면 한 칸 더 붙인 L + 1로도 되기 때문이다. 그 경계를 찾는다.

```js
function minLenBS(target, nums) {
  const n = nums.length;
  // 길이 len인 구간 중 합이 target 이상인 게 있나 (고정 창)
  const ok = (len) => {
    let sum = 0;
    for (let r = 0; r < n; r++) {
      sum += nums[r];
      if (r >= len) sum -= nums[r - len];        // 창 밖으로 나간 칸
      if (r >= len - 1 && sum >= target) return true;
    }
    return false;
  };
  if (!ok(n)) return 0;   // 전체를 더해도 모자라면 답이 없다
  let lo = 1, hi = n;     // 답은 [1, n] 안에 있다
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    if (ok(mid)) hi = mid;  // mid로 되면 더 짧은 쪽을 본다
    else lo = mid + 1;
  }
  return lo;
}
```

여기서는 `mid`를 내림(`>> 1`)으로 잡는다. 줄이는 쪽이 `hi = mid`라서 내림이어야 `lo`와 `hi`가 한 칸 차이일 때 `mid = lo`가 되어 범위가 줄어든다. 가장 긴 길이를 찾는 이분 탐색에서 올림을 쓰는 것과 반대다.

판정이 O(n), 그걸 log n번 하니 O(n log n)이다. 공간은 O(1)이라 누적 합 풀이보다 메모리가 적다. 같은 입력에서 3.7ms로 누적 합 풀이보다 빨랐다. 판정이 단순한 덧셈 반복이라 캐시를 잘 타고, 이분 탐색 횟수도 17번 정도뿐이라서다.

LeetCode가 묻는 O(n log n) 풀이로는 이쪽과 누적 합 쪽 모두 답이 된다. 면접에서는 누적 합 풀이가 더 자주 기대된다. 음수가 섞이는 변형으로 넘어갈 때 누적 합이 그대로 바탕이 되기 때문이다. 길이 이분 탐색은 "길이 L로 되면 L + 1로도 된다"는 단조성이 양수라서 성립하니, 음수가 섞이면 함께 무너진다.

## 넘치면 앞을 덜어 내는 창

위 그림에서 끝점이 뒤로 가지 않는다는 걸 봤다. 그렇다면 출발점마다 끝점을 새로 찾을 필요가 없다. 끝점 `r`을 계속 오른쪽으로 늘리고, 합이 `target` 이상이 되면 출발점 `l`을 당겨 본다. 당겨도 여전히 이상이면 더 짧은 답이다.

```js
function minSubArrayLen(target, nums) {
  let l = 0, sum = 0, best = Infinity;
  for (let r = 0; r < nums.length; r++) {
    sum += nums[r];                      // 오른쪽 칸을 넣는다
    while (sum >= target) {              // 조건을 만족하는 동안
      best = Math.min(best, r - l + 1);  // 줄이기 전에 잰다
      sum -= nums[l++];                  // 왼쪽 칸을 덜어 낸다
    }
  }
  return best === Infinity ? 0 : best;
}
```

가장 짧은 창 틀 그대로다. 답을 `while` 안에서, 줄이기 직전에 잰다는 점이 가장 긴 창과 다르다. 예시를 따라가 본다.

## 덜어 낸 앞 칸이 다시 필요 없는 이유

`l`을 한번 옮기면 다시 돌아오지 않는다. 그 사이에 답이 숨어 있을 수는 없을까. 예시의 4번 칸 단계를 보자. 5가 들어올 때 `l`이 1에서 3으로 갔다. 그러면 1번이나 2번에서 출발하는 구간은 다시 보지 않는다.

- 1번 출발: 4번 칸에서 끝나는 `[4, 2, 1, 5]`(길이 4)를 기록했다. 1번에서 출발해 5번, 6번에서 끝나는 구간은 이것보다 길어서 답이 될 수 없다. 1번에서 출발해 3번 이전에서 끝나는 구간은 앞 단계에서 이미 "합이 모자라다"고 확인됐다.
- 2번 출발: `[2, 1, 5]`(길이 3)를 기록했다. 마찬가지로 더 뒤에서 끝나면 더 길다.
- 3번 출발: `[1, 5]`는 합 6이라 모자라서 `l`이 여기 멈췄다. 3번 출발은 다음 단계에서 계속 본다.

일반적으로 말하면 이렇다. `l`을 당기는 건 "지금 `r`로 `target`을 채웠다"는 걸 확인한 다음이다. 그 출발점은 지금 `r`에서 가장 짧은 답을 이미 기록했고, 더 뒤의 끝점은 길이만 늘린다. 그리고 합이 모자라 멈춘 출발점은 계속 창의 왼쪽 끝으로 남는다. 어느 출발점도 자기 가장 짧은 구간을 확인받지 못한 채 버려지지 않는다.

이 논리에서 쓴 건 두 가지다. 끝점이 뒤로 갈수록 합이 커진다(그래서 처음 채운 끝점이 그 출발점의 최단). 출발점이 앞으로 갈수록 합이 작아진다(그래서 모자라면 거기서 멈추면 된다). 둘 다 원소가 양수라서 성립한다. 원소에 0이 끼어도 "커지거나 같다"로 바뀔 뿐 그대로 맞지만, 음수가 끼면 둘 다 깨져서 창이 틀린다. 그 반례는 [허브 글](/posts/sliding-window-pattern)에 있다.

## 창 풀이의 Python·Java 판

Python은 O(n log n) 풀이를 `bisect`로 아주 짧게 쓸 수 있어서 둘 다 적는다.

```python
from bisect import bisect_left
from itertools import accumulate
from typing import List

class Solution:
    def minSubArrayLen(self, target: int, nums: List[int]) -> int:
        l = total = 0
        best = len(nums) + 1          # 나올 수 없는 길이를 "없음"으로 쓴다
        for r, x in enumerate(nums):
            total += x                # 오른쪽 칸을 넣는다
            while total >= target:    # 조건을 만족하는 동안
                best = min(best, r - l + 1)  # 줄이기 전에 잰다
                total -= nums[l]
                l += 1
        return 0 if best == len(nums) + 1 else best

    def minSubArrayLenBisect(self, target: int, nums: List[int]) -> int:
        pre = [0, *accumulate(nums)]  # pre[i] = 앞에서 i칸의 합
        best = len(nums) + 1
        for i in range(len(nums)):
            j = bisect_left(pre, pre[i] + target)  # pre[j] >= pre[i] + target인 첫 j
            if j <= len(nums):
                best = min(best, j - i)
        return 0 if best == len(nums) + 1 else best
```

```java
class Solution {
    public int minSubArrayLen(int target, int[] nums) {
        int l = 0, sum = 0, best = Integer.MAX_VALUE;
        for (int r = 0; r < nums.length; r++) {
            sum += nums[r];                  // 합은 많아야 10^5 * 10^4 = 10^9라 int에 들어간다
            while (sum >= target) {
                best = Math.min(best, r - l + 1);
                sum -= nums[l++];
            }
        }
        return best == Integer.MAX_VALUE ? 0 : best;
    }
}
```

`(8, [1,4,2,1,5,3,1])`, `(7, [2,3,1,2,4,3])`, `(4, [1,4,4])`, `(11, [1]*8)`, `(5, [5])`, `(6, [5])`, `(15, [1,2,3,4,5])`, `(3, [1,1,1])`을 넣어 세 언어 모두 2, 2, 1, 0, 1, 0, 5, 3이 나왔고, Python의 `bisect` 판도 같았다. 네 JS 풀이가 서로 같은 답을 내는지는 원소 1~6, 길이 12 이하 무작위 배열 5,000개로 확인했다.

언어별로 짚을 점이다.

- Python `bisect_left(pre, x)`는 정렬된 리스트에서 x 이상이 처음 나오는 위치를 돌려준다. `bisect_right`를 쓰면 x보다 큰 첫 위치라, 합이 정확히 `target`인 구간을 놓친다. `(5, [5])`에서 0이 나온다.
- `bisect_left(pre, x)`는 `pre` 전체에서 찾으니 j가 i 이하로 나올 수 있을 것 같지만, `target`이 1 이상이라 `pre[i] + target`은 `pre[i]`보다 크고 `pre`가 오름차순이니 j는 언제나 i보다 크다. `target`이 0일 수 있는 변형이면 `lo=i+1`을 넘겨야 한다.
- Java에서 합의 최댓값은 10억으로 `int` 범위 안이다. 원소나 길이 제약이 더 크면 `long`으로 바꿔야 한다. 누적 합 배열도 마찬가지다.
- JS는 숫자가 2^53까지 정확하니 이 문제 크기에서는 걱정할 게 없다.

## 네 가지 풀이를 한눈에

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 출발점마다 더하기 | O(n²) | O(1) | 정답 확인용 |
| 누적 합 + 끝점 이분 탐색 | O(n log n) | O(n) | 문제가 묻는 O(n log n). 음수 변형의 출발점 |
| 길이 이분 탐색 + 고정 창 | O(n log n) | O(1) | 길이의 단조성을 보여 줄 때 |
| 넘치면 덜어 내는 창 | O(n) | O(1) | 기본 답 |
| 누적 합 + 단조 덱 (862번 풀이) | O(n) | O(n) | 음수가 섞여도 맞다. 이 문제에는 과하다 |

길이 10만, 원소 1~1만 무작위, `target` 2억(답 40,335)에서 세 번 잰 평균이다.

```text
출발점마다 더하기          3417.86 ms
누적 합 + 끝점 이분 탐색      6.12 ms
길이 이분 탐색                3.67 ms
넘치면 덜어 내는 창           2.00 ms
```

마지막 줄의 덱 풀이는 아래 "음수가 섞이거나 조건이 바뀌면"에서 본다. 양수 배열에서도 정답을 내지만(862번은 답이 없으면 −1이라 그 부분만 바꾸면 된다), 누적 합 배열과 덱이 필요해 창보다 메모리를 더 쓴다. 이 문제에서 덱을 꺼내면 "양수 조건을 안 썼다"는 신호로 읽힐 수 있으니, 창을 먼저 내고 음수 질문이 나오면 덱으로 넘어가는 순서가 자연스럽다.

O(n log n)과 O(n)의 차이는 이 크기에서 몇 ms라 실전에서는 무엇을 내도 통과한다. 면접에서 중요한 건 셋 다 설명할 수 있고, 각각이 양수 조건의 어느 부분에 기대는지 말할 수 있는 것이다.

## 답을 재는 자리가 틀린 코드들

가장 긴 창에 익숙하면 답을 `while` 밖에서 재는 실수를 한다.

```js
while (sum >= target) sum -= nums[l++];
best = Math.min(best, r - l + 1); // 줄인 뒤에 잰다
```

`(8, [1,4,2,1,5,3,1])`에서 1이 나온다. 정답은 2다. `while`을 빠져나온 창은 합이 `target`보다 작은 창이다. 조건을 만족하지 않는 창의 길이를 재고 있으니 답이 짧게 나온다. `(5, [5])`에서는 창이 비어 0이 나온다. 가장 짧은 창은 "만족하는 동안, 줄이기 직전"에 잰다.

줄이기를 `if`로 쓰면 한 번에 한 칸만 덜어 낸다.

```js
if (sum >= target) {
  best = Math.min(best, r - l + 1);
  sum -= nums[l++]; // 한 칸만 덜어 내고 다음 r로 간다
}
```

`(10, [1,1,1,1,10])`에서 5가 나온다. 10이 들어온 순간 창 합은 14인데, 1을 하나 덜어 내고 끝나 버려 `[10]` 한 칸까지 줄일 기회가 없다. 정답은 1이다. 예시 `(8, [1,4,2,1,5,3,1])`에서도 2 대신 4가 나온다. 4번 칸에서 5가 들어올 때 두 칸을 덜어 내야 하는데 하나만 덜어 내서다.

"없음"을 나타내는 초깃값을 n으로 잡는 것도 흔하다.

```js
let best = nums.length; // 답이 없을 때도 n이 남는다
// ... 창 ...
return best;
```

`(3, [1, 1])`에서 2가 나온다. 전체 합이 2라 답이 없으니 0이어야 한다. n은 실제로 나올 수 있는 답(전체 구간)이라 "없음"과 구분이 안 된다. `Infinity`나 n + 1처럼 나올 수 없는 값으로 시작하고, 끝에서 0으로 바꾼다.

연속이라는 조건을 잊고 큰 수부터 고르는 탐욕도 처음에 자주 떠올린다.

```js
const s = [...nums].sort((a, b) => b - a); // 큰 수부터
let sum = 0;
for (let i = 0; i < s.length; i++) { sum += s[i]; if (sum >= target) return i + 1; }
return 0;
```

`(10, [5, 1, 1, 5])`에서 2가 나온다. 5 두 개를 고른 건데 둘은 붙어 있지 않다. 이어진 구간으로는 네 칸을 다 써야 10이 되니 정답은 4다. 예시 `(8, [1,4,2,1,5,3,1])`에서는 우연히 5와 3이 붙어 있어 2로 맞는다. 이런 우연 때문에 예시 몇 개로는 틀린 걸 모르고 지나가기 쉽다. 정렬은 순서를 바꾸니 "연속 구간" 문제에서는 거의 언제나 쓸 수 없다.

마지막으로 음수다. 이 문제의 원소는 1 이상이라 괜찮지만, 같은 코드를 음수가 섞인 배열에 쓰면 틀린다. `[1, -5, 3, 4]`에서 합 4 이상인 가장 짧은 구간은 `[4]`인데 창은 0을 낸다. 이 실행 결과와 이유는 [허브 글](/posts/sliding-window-pattern)의 "창이 통하지 않는 입력"에 있다.

## 음수가 섞이거나 조건이 바뀌면

### 음수가 있는 배열이라면 (LeetCode 862)

862번 Shortest Subarray with Sum at Least K는 이 문제에 음수를 허용한 판이다. 창은 틀리고, 누적 합 위의 끝점 이분 탐색도 틀린다. 누적 합이 더 이상 오름차순이 아니라서다. 대신 누적 합 인덱스를 단조 덱에 담는다.

```js
function shortestSubarray(nums, k) {
  const n = nums.length;
  const pre = new Array(n + 1).fill(0);
  for (let i = 0; i < n; i++) pre[i + 1] = pre[i] + nums[i];
  const dq = []; // 누적 합 인덱스, pre 값이 증가하는 순서
  let head = 0, best = Infinity;
  for (let j = 0; j <= n; j++) {
    while (head < dq.length && pre[j] - pre[dq[head]] >= k) {
      best = Math.min(best, j - dq[head]); // 가장 앞 후보로 답을 재고 버린다
      head++;
    }
    while (dq.length > head && pre[dq[dq.length - 1]] >= pre[j]) dq.pop(); // 더 크거나 같은 누적 합은 쓸모없다
    dq.push(j);
  }
  return best === Infinity ? -1 : best;
}
console.log(shortestSubarray([1, -5, 3, 4], 4), shortestSubarray([1, 2, -3, 3], 3), shortestSubarray([2, -1, 2], 3), shortestSubarray([1, 2], 4));
```

```text
1 1 3 -1
```

두 개의 `while`이 하는 일이 다르다. 앞쪽 `while`은 "이 출발점은 지금 j로 답이 됐고, 더 뒤의 j로는 길이만 길어지니 버린다"이다. 뒤쪽 `while`은 "나보다 뒤에 있으면서 누적 합이 같거나 작은 출발점이 생겼으니, 나는 앞으로도 그 출발점보다 나을 일이 없다"이다. 더 뒤에서 시작하고 합이 더 크게 남으니까. 그래서 덱 안의 누적 합은 늘 증가 순서다. 각 인덱스가 한 번 들어오고 한 번 나가니 O(n)이다. 덱으로 후보를 정리하는 생각은 [단조 스택 패턴](/posts/monotonic-stack-pattern)과 [Sliding Window Maximum](/posts/leetcode-sliding-window-maximum)에서 더 자세히 다룬다. 이 코드는 원소 −5~5 무작위 배열 5,000개로 이중 반복문과 같은 답을 내는지 확인했다. 862번은 답이 없으면 0이 아니라 −1을 돌려준다는 점도 다르다.

### 합이 정확히 target인 구간이라면

"정확히"면 가장 짧은 것이든 개수든 창보다 누적 합과 해시맵이 낫다. 지금까지의 누적 합에서 `target`을 뺀 값이 앞에 나왔는지 찾는다. 개수를 세는 560번 Subarray Sum Equals K의 코드는 [허브 글](/posts/sliding-window-pattern)에 있다. 원소가 모두 양수라면 창으로도 된다. 합이 `target`을 넘을 때 줄이고, 같을 때만 기록한다.

```js
function minExact(target, nums) {
  let l = 0, sum = 0, best = Infinity;
  for (let r = 0; r < nums.length; r++) {
    sum += nums[r];
    while (sum > target) sum -= nums[l++];                // 넘으면 줄인다
    if (sum === target) best = Math.min(best, r - l + 1); // 같을 때만 기록
  }
  return best === Infinity ? 0 : best;
}
console.log(minExact(8, [1, 4, 2, 1, 5, 3, 1]), minExact(7, [1, 4, 2, 1, 5, 3, 1]), minExact(100, [1, 2]));
```

```text
2 3 0
```

합이 정확히 7인 가장 짧은 구간은 `[4, 2, 1]`이다. 줄이는 조건이 `>=`에서 `>`로 바뀌었다는 점만 다르다. `>=`로 두면 합이 딱 맞는 창을 기록하기도 전에 줄여 버린다.

### 합이 target 이상인 구간의 개수를 세라면

양수 배열이면 창이 그대로 쓰인다. `r`을 고정했을 때 합이 `target` 이상이 되는 출발점은 0부터 어떤 경계까지다. 창을 "합이 `target` 미만"으로 유지하면 그 경계가 `l`이라, `r`마다 `l`개(0부터 l − 1까지)를 더하면 된다.

```js
function countAtLeast(target, nums) {
  let l = 0, sum = 0, count = 0;
  for (let r = 0; r < nums.length; r++) {
    sum += nums[r];
    while (sum >= target) sum -= nums[l++]; // 창을 "합이 target 미만"으로 유지한다
    count += l; // 0..l-1에서 출발해 r에서 끝나는 구간은 모두 target 이상
  }
  return count;
}
console.log(countAtLeast(8, [1, 4, 2, 1, 5, 3, 1]));
```

```text
14
```

예시에서 합이 8 이상인 구간은 14개다. 무작위 입력 3,000개로 이중 반복문과 같은 개수가 나오는지 확인했다. 이 "오른쪽 끝마다 개수를 더한다" 생각은 [Subarray Product Less Than K](/posts/leetcode-subarray-product-less-than-k)에서 곱으로 다시 나온다.

### 배열이 원형이라면

마지막 칸 다음에 첫 칸이 이어진다고 하면 `[5, 1, 1, 5]`, 목표 10의 답은 끝의 5와 앞의 5를 이은 2가 된다. 배열을 두 번 이어 붙인 것처럼 인덱스를 `% n`으로 읽고, 창이 n칸을 넘지 않게 막으면 같은 창이 그대로 쓰인다.

```js
function minCircular(target, nums) {
  const n = nums.length;
  let l = 0, sum = 0, best = Infinity;
  for (let r = 0; r < 2 * n; r++) {
    sum += nums[r % n];                         // 두 번 이어 붙인 것처럼 읽는다
    while (r - l + 1 > n) sum -= nums[l++ % n]; // 창은 n칸을 넘을 수 없다
    while (sum >= target) {
      best = Math.min(best, r - l + 1);
      sum -= nums[l++ % n];
    }
  }
  return best === Infinity ? 0 : best;
}
console.log(minCircular(10, [5, 1, 1, 5]), minCircular(13, [5, 1, 1, 5]));
```

```text
2 0
```

n칸 제한이 없으면 같은 원소를 두 번 쓰는 창이 생긴다. `[5, 1, 1, 5]`의 전체 합은 12라 목표 13은 원형으로도 불가능한데, 제한을 빼면 5를 두 번 넣은 창이 답으로 잡힌다. 이 코드는 무작위 입력 5,000개로 출발점마다 원형으로 더하는 풀이와 같은 답을 내는지 확인했다.

### 원소에 0이 있거나 target이 0이라면

원소에 0이 끼는 건 괜찮다. 합이 "커지거나 같다"로 바뀔 뿐이라 창이 그대로 맞는다. `(3, [0, 0, 3, 0])`은 1, `(3, [1, 0, 0, 2])`는 4가 나온다. 문제는 `target`이 0일 때다. 빈 창도 합 0이라 조건을 만족하니, `while`이 창을 끝까지 비우고 길이 0을 기록한다. `(0, [1, 2, 3])`에서 0이 나오는데, 이 0은 "빈 구간이면 된다"는 뜻이라 "답이 없다"는 0과 겹친다. 이 문제는 `target`이 1 이상이라 생기지 않는 일이지만, 조건을 바꾼 변형에서는 `while (l <= r && sum >= target)`처럼 창이 비지 않게 막고 답의 뜻을 정해야 한다.

### 구간이 어디인지 돌려 달라면

`best`를 갱신할 때 `l`과 `r`을 같이 적는다. 가장 짧은 구간이 여럿이면 처음 것인지 마지막 것인지를 정해야 하는데, 창은 `r`이 작은 순서로 기록하니 `<`로 비교하면 가장 앞의 것이 남는다.

### 가장 긴 구간이라면

합이 `target` 이하인 가장 긴 구간이면 같은 창을 가장 긴 창 틀로 바꾼다. 합이 넘으면 줄이고, 줄인 뒤에 잰다. [Max Consecutive Ones III](/posts/leetcode-max-consecutive-ones-iii)가 "0의 개수가 k 이하인 가장 긴 구간"이라 이 모양이다.

## 면접에서 나올 만한 질문

### 왜 슬라이딩 윈도가 맞나요?

원소가 모두 양수라 구간을 늘리면 합이 커지고 줄이면 작아진다. 그래서 출발점이 오른쪽으로 갈수록 합을 채우는 끝점도 오른쪽으로만 간다. 두 포인터를 한 방향으로만 움직여도 모든 출발점의 가장 짧은 구간을 확인할 수 있고, 각 포인터가 n번씩 움직이니 O(n)이다.

### O(n log n) 풀이는 어떻게 짜나요?

누적 합 `pre`를 만들면 양수라서 오름차순이다. 출발점 i마다 `pre[j] >= pre[i] + target`인 첫 j를 이분 탐색으로 찾으면 길이는 j − i다. 다른 방법으로 길이 L을 이분 탐색하고 고정 창으로 "길이 L로 되나"를 판정해도 된다. 두 방법 모두 단조성이 양수에서 나온다.

### 답을 while 안에서 재는 이유는요?

가장 짧은 창은 줄일수록 좋아지니, 조건을 만족하는 동안 재고 줄여야 한다. `while`을 빠져나온 창은 이미 합이 `target`보다 작은 창이라 그걸 재면 조건을 어긴 길이를 답으로 잡는다. 가장 긴 창은 반대로 조건이 깨지면 줄이고 빠져나온 뒤에 잰다.

### 음수가 섞이면 어떻게 하나요?

창도, 누적 합 이분 탐색도 틀린다. 둘 다 "줄이면 합이 작아진다", "누적 합이 오름차순"이라는 양수의 성질에 기대기 때문이다. 862번처럼 누적 합 인덱스를 덱에 담고, 뒤에서 더 작거나 같은 누적 합이 오면 앞 후보를 버려 덱을 증가 순서로 유지하면 O(n)이다.

### 답이 없을 때 처리는 어떻게 하나요?

`best`를 `Infinity`나 n + 1처럼 실제로 나올 수 없는 값으로 시작하고, 끝에서 그 값이면 0을 돌려준다. n으로 시작하면 전체 배열이 답인 경우와 답이 없는 경우를 구분할 수 없어서 틀린다.

### 합이 오버플로할 수 있나요?

이 문제는 원소 1만 이하, 길이 10만 이하라 합이 10억을 넘지 않아 Java `int`에 들어간다. 제약이 더 커지면 `long`을 써야 하고, 누적 합 배열도 `long[]`로 잡는다. JS는 2^53까지 정확하고 Python은 정수 크기 제한이 없다.

### 시간이 더 걸리는 O(n log n)을 왜 알아야 하나요?

음수 변형으로 넘어갈 때 바탕이 되는 게 누적 합이기 때문이다. 창은 양수가 아니면 바로 무너지지만, 누적 합은 덱이나 정렬된 구조와 결합해서 살아남는다. 같은 문제를 다른 도구로 풀 수 있는지 보는 질문이기도 하다.
