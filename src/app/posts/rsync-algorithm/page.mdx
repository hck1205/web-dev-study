매일 새벽 46MB짜리 로그 파일을 백업 서버로 보낸다. 하루 동안 바뀐 건 줄 몇 개뿐이다. 그런데 `scp`로 보내면 매번 46MB가 통째로 건너간다. `rsync`로 바꾸면 같은 파일이 8만 바이트 남짓만 주고받고 끝난다. 백업 서버는 새 파일을 본 적이 없고, 보내는 쪽은 백업 서버에 있는 옛 파일을 본 적이 없는데, 어떻게 바뀐 곳만 골라 보낼 수 있을까.

이 글은 rsync가 쓰는 델타 전송 알고리즘을 따라간다. 받는 쪽이 블록마다 지문을 보내고, 보내는 쪽이 한 바이트씩 창을 밀며 그 지문을 찾는 방식이다. 핵심 부품인 굴리는 체크섬(rolling checksum)을 직접 계산해 보고, Ubuntu 24.04의 rsync 3.2.7로 큰 파일 한 줄을 고쳐 보내며 `Matched data`와 `Literal data`가 어떻게 나오는지, 블록 크기와 압축 파일, 건너뛰기 판단이 결과를 어떻게 바꾸는지 실제 출력으로 본다.

이 주제의 다른 글: 파일 하나가 아니라 수많은 블록 묶음에서 다른 곳을 찾는 방법은 [머클 트리](/posts/merkle-tree)에서 다룬다. 큰 전송이 다른 트래픽을 밀어낼 때 `--bwlimit`로 속도를 묶는 이야기는 [트래픽 셰이핑 글](/posts/traffic-shaping-qos)에 있다.

## 두 쪽이 서로의 파일을 모른다

`diff`는 두 파일을 한 컴퓨터에 놓고 비교한다. 여기서는 그럴 수 없다. 새 파일은 보내는 쪽(A)에, 옛 파일은 받는 쪽(B)에 있다. 비교하려고 한쪽 파일을 다른 쪽으로 보내면 그게 이미 전체 전송이다.

해시로 "같은가"를 묻는 것까지는 쉽다. 파일 전체 해시를 비교하면 된다. 하지만 46MB 중 한 줄이 다르다는 사실만 알 뿐 어디가 다른지는 모른다. 파일을 일정한 크기의 블록으로 잘라 블록마다 해시를 비교하는 방법도 떠올릴 수 있다. 이건 고친 자리가 원래 길이를 유지할 때만 통한다. 파일 맨 앞에 한 줄을 끼워 넣으면 뒤의 모든 바이트가 밀려서, 블록 경계가 전부 어긋나고 모든 블록의 해시가 달라진다.

1996년 앤드루 트리젤과 폴 매커라스가 정리한 rsync 알고리즘은 이 두 문제를 같이 푼다. 받는 쪽은 옛 파일을 고정된 블록으로 자르되, 보내는 쪽은 새 파일의 모든 바이트 위치에서 블록 하나 크기의 창을 놓고 맞는 블록을 찾는다. 경계가 어디로 밀렸든 같은 내용은 찾아낸다.

## 받는 쪽이 먼저 블록 지문을 보낸다

순서는 이렇다. 받는 쪽은 옛 파일을 블록 크기 B로 자르고, 블록마다 두 가지 지문을 계산해 보낸다. 싸게 계산하는 약한 체크섬과, 비싸지만 거의 틀리지 않는 강한 해시다. 보내는 쪽은 그 목록으로 표를 만들어 두고, 새 파일 처음부터 창을 한 바이트씩 밀며 표에 맞는 블록이 있는지 본다. 맞으면 "옛 파일의 k번 블록"이라는 짧은 지시를, 안 맞는 구간은 바이트 그대로(literal)를 보낸다. 받는 쪽은 옛 파일과 이 지시를 합쳐 새 파일을 만든다.

받는 쪽이 먼저 지문을 보내는 데는 이유가 있다. 비싼 일, 즉 모든 바이트 위치에서 창을 밀어 보는 일은 새 파일을 가진 쪽만 할 수 있다. 받는 쪽은 블록 수만큼만 계산하면 된다. 반대 방향으로 짠 도구도 있다. HTTP로 배포하는 zsync는 서버가 지문을 미리 계산해 파일 옆에 두고, 내려받는 클라이언트가 자기 옛 파일 위에서 창을 민다. 서버가 요청마다 계산하지 않아도 되게 바꾼 것이다.

## 한 칸씩 미는 체크섬

보내는 쪽의 일을 단순하게 하면, 새 파일이 N바이트일 때 N개 위치마다 블록 크기 B만큼 읽어 체크섬을 구해야 한다. N·B번 계산이다. 46MB 파일, 블록 6,832바이트면 3천억 번이 넘는다. 이걸 N번으로 줄이는 게 굴리는 체크섬이다.

rsync의 약한 체크섬은 두 16비트 값을 붙인 것이다. 창 안 바이트 x₁…x_B에 대해

- a = 바이트의 합 (mod 2¹⁶)
- b = 앞 바이트일수록 큰 가중치를 곱한 합, B·x₁ + (B−1)·x₂ + … + 1·x_B (mod 2¹⁶)

창을 한 칸 밀면 맨 앞 바이트(out)가 빠지고 새 바이트(in)가 들어온다. 이때 처음부터 다시 더할 필요가 없다.

- a′ = a − out + in
- b′ = b − B·out + a′

덧셈 몇 번이면 다음 위치의 체크섬이 나온다. 아래 그림은 옛 파일 `abcdefgh`(블록 4바이트: `abcd`, `efgh`)를 가진 받는 쪽에, 새 파일 `abXcdefgh`를 보내는 과정이다. 숫자는 실제로 계산한 값이다.

아래 `delta`는 위 과정을 그대로 구현한 것이다. `roll` 함수만 비어 있다. 채우지 않으면 첫 블록 다음부터 체크섬이 틀려서 아무 블록도 맞지 않는다. 받는 쪽의 마지막 블록이 B보다 짧으면 이 코드는 그 블록을 표에 넣지 않는다. 실제 rsync는 짧은 마지막 블록도 맞춘다.

## 약한 체크섬과 강한 해시를 같이 쓰는 이유

약한 체크섬은 굴릴 수 있다는 장점 하나로 뽑힌 값이다. 32비트라 충돌이 흔하고, 바이트 합이라 내용이 달라도 같은 값이 나오기 쉽다. 그래서 약한 체크섬이 맞으면 그때만 강한 해시를 계산해 진짜인지 확인한다. 강한 해시는 굴릴 수 없어서 창마다 계산하면 느리지만, 후보가 나왔을 때만 계산하니 괜찮다.

강한 해시 종류는 버전에 따라 바뀌었다. 프로토콜 30(rsync 3.0) 전에는 MD4, 그 뒤로 MD5였고, 3.2.0부터 양쪽이 xxHash 계열을 협상한다. 설치된 rsync가 지원하는 목록과 실제로 고른 값은 이렇게 본다.

```bash
rsync --version | sed -n '/Checksum list/,+1p'          # 지원하는 체크섬
rsync -a --no-whole-file --debug=nstr,deltasum1 src/ dst/   # 협상 결과와 대조 통계
```

```text
Checksum list:
    xxh128 xxh3 xxh64 (xxhash) md5 md4 sha1 none
Client negotiated checksum: xxh128
total: matches=6847  hash_hits=7461  false_alarms=0 data=6836
```

`hash_hits`는 약한 체크섬 표에서 후보를 찾은 횟수, `matches`는 실제로 블록이 맞은 횟수, `false_alarms`는 약한 체크섬은 같았는데 강한 해시가 달랐던 횟수다. 6,848개 블록 중 6,847개가 맞았고 나머지 하나가 literal로 갔다.

강한 해시를 블록마다 다 보내지는 않는다. 앞의 `s2length=3`이 블록마다 보낸 강한 해시의 길이, 3바이트다. 파일 크기와 블록 수를 보고 충분할 만큼만 잘라 보내 지문 목록을 줄인다. 3바이트면 우연히 맞을 수도 있다. 그래서 조립이 끝나면 파일 전체 해시를 한 번 더 비교하고, 다르면 그 파일을 긴 해시로 다시 보낸다. 지문 목록이 블록당 7바이트(약한 4 + 강한 3)라서 6,848개 블록의 목록이 47,974바이트였다.

## 46MB 파일 한 줄을 고쳐 보내 보기

## 블록 크기가 정하는 것

블록 크기는 `-B`로 직접 정하지 않으면 파일 크기의 제곱근 근처에서 8의 배수로 잡는다. √46,782,813 ≈ 6,839.8이라 6,832바이트가 됐다. 프로토콜 30 이상에서 상한은 128KB(131,072바이트)다. 같은 한 줄 수정을 블록 크기만 바꿔 보냈다.

```bash
rsync -a --no-whole-file --stats -B 1024   src/ dst/   # 작은 블록
rsync -a --no-whole-file --stats -B 131072 src/ dst/   # 상한 크기 블록
```

```text
-B 1024
Literal data: 1,028 bytes
Total bytes sent: 183,908
Total bytes received: 319,863
-B 131072
Literal data: 131,076 bytes
Total bytes sent: 132,652
Total bytes received: 2,180
-B default (6832)
Literal data: 6,836 bytes
Total bytes sent: 34,352
Total bytes received: 47,974
```

작은 블록은 literal이 작지만 블록 수가 4만 5천 개를 넘어 지문 목록이 32만 바이트가 됐다. 큰 블록은 지문 목록이 2KB로 줄었지만, 한 줄을 고쳤는데 128KB를 통째로 보냈다. 오간 바이트를 합치면 1024는 약 50만, 131072는 약 13만, 기본값은 약 8만 2천이다. 제곱근 규칙은 "지문 목록 크기"와 "블록 하나가 깨질 때의 손해"가 비슷해지는 지점을 고른 것이다. 수정이 아주 드문 큰 파일이면 블록을 키우는 편이, 수정이 촘촘하게 흩어진 파일이면 줄이는 편이 이득이지만, 기본값에서 크게 벗어날 일은 드물다.

## 델타 전송이 통하지 않는 파일

압축 파일이 대표적이다. 압축된 바이트는 앞부분의 내용에 따라 뒤가 모두 달라진다. 같은 로그를 gzip으로 압축해 보내 두고, 원본 한 줄을 고쳐 다시 압축해 보냈다.

```bash
gzip -n -c a.log > src/app.log.gz              # 일반 gzip
gzip -n --rsyncable -c a.log > src/app.log.gz  # 일정 간격으로 압축 상태를 초기화한다
rsync -a --no-whole-file --stats src/ dst/
```

```text
gzip (plain): 10366071 bytes
Literal data: 4,522,599 bytes
Matched data: 5,843,472 bytes
gzip --rsyncable: 10522074 bytes
Literal data: 37,434 bytes
Matched data: 10,484,640 bytes
```

일반 gzip에서는 고친 줄 뒤쪽 절반이 모두 literal이 됐다. `--rsyncable`은 입력 내용으로 정해지는 지점마다 압축 상태를 초기화해서, 한 곳의 변화가 다음 초기화 지점까지만 번지게 한다. 압축 파일은 1.5% 커졌고 literal은 120분의 1로 줄었다. zstd도 같은 이름의 `--rsyncable` 옵션이 있다. 암호화된 파일은 이런 방법이 없다. 바이트 하나만 바뀌어도 이후 전부가 달라지게 만드는 게 암호화의 목적이라서다. 암호화 백업에서 델타가 필요하면, 암호화하기 전에 내용 기준으로 조각을 나누는 도구(restic, borg)를 쓴다.

실행 중인 DB 데이터 파일은 다른 이유로 rsync 대상이 아니다. 델타는 잘 통하지만, 복사하는 동안 파일이 계속 바뀌어 서로 다른 시점의 페이지가 섞인 깨진 사본이 생긴다. DB는 `pg_basebackup` 같은 전용 도구로 백업한다.

## 아예 보내지 않고 건너뛰는 판단

델타 알고리즘보다 먼저 일어나는 일이 있다. rsync는 기본으로 크기와 수정 시각이 같은 파일을 "같다"고 보고 열어 보지도 않는다(quick check). 수천 개 파일을 매번 읽지 않으려는 선택이지만, 이 가정이 깨지면 바뀐 파일을 놓친다. 설정 파일의 숫자 하나를 크기가 같게 바꾸고 수정 시각을 원래대로 돌려놓았다. 빌드 도구나 압축 해제가 시각을 보존할 때 실제로 생기는 일이다.

```bash
sed -i 's/100/900/' src/app.conf && touch -r stamp src/app.conf   # 내용만 바꾸고 시각은 그대로
rsync -av --itemize-changes src/ dst/      # 기본: 크기와 시각만 본다
rsync -avc --itemize-changes src/ dst/     # -c: 양쪽 내용의 해시를 비교한다
```

```text
# rsync -av
sending incremental file list

sent 74 bytes  received 12 bytes  172.00 bytes/sec
total size is 22  speedup is 0.26
max_connections = 100

# rsync -avc
sending incremental file list
>fc........ app.conf

sent 159 bytes  received 35 bytes  388.00 bytes/sec
total size is 22  speedup is 0.11
max_connections = 900
```

기본 실행은 아무것도 보내지 않았고 받는 쪽은 여전히 `100`이다. `-c`를 주자 `>fc`(파일을 받는다, 체크섬이 다르다)로 표시되며 보냈다. 대신 `-c`는 양쪽이 모든 파일을 끝까지 읽어 해시하므로 파일이 많으면 매우 느리다. 평소에는 기본값으로 돌리고, 주기적으로 한 번씩 `-c`로 검증하거나 배포 산출물처럼 시각을 믿을 수 없는 경우에만 쓴다.

- 같은 데이터센터 안, 10Gbps 링크에서 rsync가 `scp`보다 느리다. 네트워크가 디스크보다 빠르면 델타 계산이 병목이다. `-W`(`--whole-file`)로 델타를 끄면 빨라진다. 로컬 복사가 기본으로 그렇게 하는 이유와 같다.
- 받는 서버의 디스크가 거의 찼는데 큰 파일 하나가 계속 실패한다. rsync는 임시 파일에 새 파일을 다 만든 뒤 이름을 바꾸므로, 그 파일 크기만큼 빈 공간이 더 필요하다. `--inplace`는 제자리에서 고쳐 공간을 아끼지만, 전송 중에 끊기면 반쯤 고쳐진 파일이 남고 그동안 읽는 프로그램은 섞인 내용을 본다. 공간이 부족하면 차라리 볼륨을 늘리는 쪽을 먼저 본다.
- 큰 파일 전송이 중간에 끊기면 처음부터 다시 한다. `--partial`을 주면 받다 만 파일을 남겨 두고, 다음 실행이 그걸 옛 파일 삼아 델타로 이어 간다.
- `-z`(압축)를 켰는데 CPU만 오르고 빨라지지 않는다. 이미 압축된 파일(`.gz`, `.jpg`, `.zst`)은 더 줄지 않는다. rsync 3.2는 흔한 압축 확장자를 기본으로 건너뛰지만, 대부분이 그런 파일이면 `-z`를 끈다.
- 백업 대상이 매번 전체 전송된다. 압축이나 암호화된 파일인지, 로컬 경로끼리라 `--whole-file`이 켜졌는지, 파일 이름이 날짜별로 바뀌어 받는 쪽에 옛 파일이 없는지 본다. 마지막 경우에는 `--fuzzy`가 받는 쪽에서 이름이 비슷한 파일을 옛 파일로 삼는다.

rsync는 파일 한 쌍을 맞추는 데 최적화돼 있다. 백업 도구 restic과 borg는 반대로 접근한다. 굴리는 해시로 내용의 특정 패턴이 나오는 지점을 찾아 거기서 파일을 자른다(내용 기준 조각 나누기, content-defined chunking). 경계가 내용에 따라 정해지니 앞에 바이트가 끼어도 뒤 조각의 경계는 그대로고, 같은 조각은 해시로 한 번만 저장한다. 상대의 옛 파일이 없어도 저장소 전체에서 중복을 찾는다는 점이 rsync와 다르다. 조각이 수백만 개로 늘어나 "어느 조각이 다른가"를 물어야 할 때는 [머클 트리](/posts/merkle-tree)가 그 질문을 맡는다. 고정 블록과 내용 기준 조각을 같은 파일로 나란히 재 본 결과는 [파일 동기화 설계 ①](/posts/sd-file-sync-block-upload)에 있다.

## 굴려서 찾고 해시로 확인한다

rsync는 받는 쪽이 옛 파일의 블록 지문을 보내고, 보내는 쪽이 새 파일 위에서 창을 한 바이트씩 밀며 그 지문을 찾는다. 창을 미는 비용을 덧셈 몇 번으로 줄이는 굴리는 체크섬이 이 방법을 가능하게 했고, 약한 체크섬이 맞을 때만 강한 해시로 확인해 속도와 정확성을 같이 얻는다. 그래서 내용이 밀리거나 순서가 바뀌어도 같은 부분을 찾고, 바뀐 블록과 지문 목록만 오간다. 대신 양쪽이 파일을 끝까지 읽는 CPU와 디스크를 쓰므로 빠른 네트워크에서는 통째로 보내는 편이 낫고, 압축·암호화된 파일에서는 효과가 사라진다.

## 면접에서 나올 만한 질문

### rsync는 어떻게 바뀐 부분만 보내나요?

받는 쪽이 옛 파일을 고정 크기 블록으로 잘라 블록마다 약한 체크섬과 강한 해시를 보낸다. 보내는 쪽은 새 파일의 모든 바이트 위치에서 블록 크기의 창을 놓고 약한 체크섬을 표와 대조하고, 맞으면 강한 해시로 확인한 뒤 블록 번호만 보낸다. 맞지 않는 구간은 바이트 그대로 보내고, 받는 쪽이 옛 파일의 블록과 합쳐 새 파일을 만든다.

### 굴리는 체크섬이 왜 필요한가요?

모든 바이트 위치에서 블록 체크섬을 처음부터 계산하면 파일 크기 × 블록 크기만큼 일한다. rsync의 약한 체크섬은 바이트 합 a와 가중 합 b로 이뤄져서, 창을 한 칸 밀 때 빠지는 바이트와 들어오는 바이트만으로 다음 값을 구할 수 있다(a′ = a − out + in, b′ = b − B·out + a′). 그래서 위치마다 상수 시간이 들고 전체가 파일 크기에 비례한다.

### 약한 체크섬만 쓰면 안 되나요?

32비트 바이트 합이라 다른 내용이 같은 값을 갖기 쉬워 그대로 믿으면 파일이 깨진다. 그래서 약한 체크섬이 맞을 때만 MD5나 xxHash 같은 강한 해시를 계산해 확인한다. 강한 해시는 굴릴 수 없어 비싸지만 후보에만 쓰니 부담이 작다. 블록마다 강한 해시를 짧게 잘라 보내는 대신 마지막에 파일 전체 해시를 비교하고, 다르면 다시 보낸다.

### 블록 크기는 어떻게 정하고, 크거나 작으면 무엇이 달라지나요?

기본은 파일 크기의 제곱근 근처, 8의 배수이고 상한은 128KB다. 블록이 작으면 수정 하나에 깨지는 블록이 작아 literal이 줄지만 지문 목록이 커진다. 실측에서 46MB 파일에 1KB 블록은 지문만 32만 바이트였고, 128KB 블록은 한 줄 수정에 128KB를 literal로 보냈다. 기본값은 이 두 비용이 비슷해지는 지점이다.

### 같은 서버 안에서 rsync로 복사할 때 델타가 안 쓰이는 이유는요?

양쪽이 로컬 경로면 rsync가 `--whole-file`을 기본으로 켠다. 같은 디스크 안에서는 옛 파일을 읽어 지문을 만들고 새 파일 위에서 창을 미는 비용이 그냥 복사하는 비용보다 커서다. 같은 이유로 아주 빠른 네트워크에서는 `-W`로 델타를 끄는 편이 빠를 수 있다. 로컬에서 델타를 보고 싶으면 `--no-whole-file`을 준다.

### 압축 파일이나 암호화 파일은 왜 델타 전송 효과가 없나요?

압축은 앞의 내용에 따라 뒤의 바이트가 모두 달라지고, 암호화는 일부러 그렇게 만든다. 원본 한 줄을 고쳤을 뿐인데 그 뒤 압축 바이트가 전부 바뀌어 literal이 된다. 실측에서 일반 gzip은 10MB 중 4.5MB가 literal이었고, 압축 상태를 주기적으로 초기화하는 `gzip --rsyncable`은 37KB였다. 암호화 백업은 암호화 전에 내용 기준으로 조각을 나누는 도구를 쓴다.

### rsync가 바뀐 파일을 놓칠 수 있나요?

기본 quick check가 크기와 수정 시각만 보기 때문에 둘 다 같으면 내용이 달라도 건너뛴다. 시각을 보존하는 압축 해제나 같은 초에 두 번 바뀐 파일에서 실제로 생긴다. `-c`를 주면 양쪽이 내용 해시를 비교해 잡아내지만 모든 파일을 끝까지 읽으므로 느리다. 평소 기본값으로 돌리고 주기적으로 `-c` 검증을 하는 식으로 나눈다.
