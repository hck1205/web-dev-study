월요일에 원본 팀이 `orders` 테이블에서 쓰지 않는 것 같던 `discount_amount` 컬럼을 지웠다. 그날은 아무 일도 없었다. 목요일 아침, 마케팅 팀의 쿠폰 효과 대시보드가 빈 화면이 됐다. 그 대시보드는 하루 한 번 도는 집계 테이블을 읽고, 그 집계 테이블은 주 1회 도는 정제 테이블을 읽고, 정제 테이블이 수요일 밤에 처음으로 `discount_amount`를 찾다가 실패한 것이다. 사흘 동안 아무도 몰랐고, 원본 팀은 그 컬럼을 누가 쓰는지 물어볼 곳이 없었다.

이 장면에 빠진 건 두 가지다. 이 컬럼을 누가 쓰는지 알려 주는 지도(계보)와, 그 지도를 찾아볼 장소(카탈로그)다. 이 글은 메타데이터의 종류, 데이터 카탈로그가 하는 일, 테이블과 컬럼 단위의 계보를 SQL 파싱과 실행 이벤트(OpenLineage) 두 방법으로 모으는 법, 그리고 바꾸기 전에 영향을 따져 보는 법을 다룬다. 실험은 [dbt 변환](/posts/dbt-transformations)에서 만든 작은 쇼핑몰 프로젝트를 그대로 쓴다. sqlglot 30.24와 openlineage-python 1.54를 썼다.

## 데이터를 설명하는 데이터를 셋으로 나눈다

메타데이터는 데이터를 설명하는 데이터다. 한데 섞어 부르면 누가 무엇을 채워야 하는지 흐려지니 보통 셋으로 나눈다.

- 기술 메타데이터: 테이블 이름, 컬럼과 타입, 파티션 키, 저장 위치, 어느 모델이 어느 테이블을 읽는지(계보). 시스템에서 기계적으로 뽑을 수 있다.
- 업무 메타데이터: "매출"이 무엇을 뜻하는지, 이 테이블의 담당 팀, 개인정보가 들어 있는 컬럼 표시, 용어집. 사람이 알고 있어서 사람이 적어야 한다.
- 운영 메타데이터: 마지막으로 언제 갱신됐는지, 몇 행이 들어왔는지, 실행이 몇 분 걸렸는지, 최근 30일간 누가 이 테이블을 쿼리했는지. 실행할 때마다 생긴다.

처음 장면을 이 셋으로 다시 보면, 원본 팀에 필요했던 건 기술 메타데이터 중 계보("이 컬럼을 읽는 곳")와 업무 메타데이터 중 담당자("물어볼 사람")였다. 운영 메타데이터("이 정제 테이블은 주 1회 돈다")가 있었으면 왜 사흘 뒤에 터졌는지도 바로 보였을 것이다.

## 카탈로그는 메타데이터를 한곳에 모아 찾게 해 준다

데이터 카탈로그는 이 메타데이터를 모아 검색하게 해 주는 시스템이다. 오픈소스로는 LinkedIn이 내놓은 DataHub, Uber에서 데이터 플랫폼을 만들던 사람들이 시작한 OpenMetadata, Lyft의 Amundsen이 많이 알려졌다. 클라우드 쪽에는 AWS Glue Data Catalog, Google Dataplex, Databricks Unity Catalog가 있다. 이름은 달라도 하는 일은 비슷하다.

- 검색: "매출"을 치면 관련 테이블, 컬럼, 대시보드가 나온다.
- 상세: 스키마, 설명, 담당자, 태그(PII 등), 샘플 값, 최근 갱신 시각.
- 계보: 이 테이블의 위아래로 무엇이 이어져 있는지 그래프로 보여 준다.
- 사용 통계: 자주 쓰이는 테이블과 아무도 안 쓰는 테이블을 가른다.
- 접근과 분류: 개인정보 컬럼에 태그를 달고 권한 정책과 엮는다. 개인정보를 어떻게 다뤄야 하는지는 [데이터 개인정보와 규정 준수](/posts/data-privacy-compliance)에 있다.

메타데이터가 카탈로그에 들어오는 길은 둘이다. 카탈로그가 주기적으로 각 시스템에 붙어 읽어 가는 끌어오기(pull)와, 파이프라인이 일하면서 카탈로그로 보내는 밀어 넣기(push)다. 아래 그림에서 왼쪽 위 두 화살표가 끌어오기, 아래 두 화살표가 밀어 넣기다.

## 계보를 만드는 첫 번째 방법: SQL을 읽는다

계보는 "무엇을 읽어서 무엇을 만들었나"의 그래프다. 테이블 단위 계보는 테이블끼리, 컬럼 단위 계보는 "이 출력 컬럼이 어느 입력 컬럼에서 왔나"까지 잇는다. 처음 장면처럼 컬럼 하나를 지울 때는 컬럼 단위가 있어야 쓸모가 있다. 테이블 단위만 있으면 `orders`를 읽는 테이블 서른 개가 다 걸려 나와서, 결국 하나씩 SQL을 열어 봐야 한다.

가장 흔한 방법은 SQL 문장을 파싱하는 것이다. 웨어하우스의 쿼리 기록이나 dbt가 컴파일한 SQL을 파서에 넣으면 FROM, JOIN에서 입력 테이블을, SELECT 목록에서 출력 컬럼과 그 재료를 뽑아낸다. Python 파서 sqlglot으로 [dbt 글](/posts/dbt-transformations)의 `fct_daily_sales` SQL을 넣어 봤다.

```python
# col_lineage.py
from sqlglot.lineage import lineage

schema = {   # 파서가 컬럼이 어느 테이블 것인지 알려면 스키마가 필요하다
    "stg_orders": {"order_id": "int", "customer_id": "int", "status": "text",
                   "amount": "int", "updated_at": "timestamp"},
    "stg_customers": {"customer_id": "int", "name": "text", "grade": "text"},
}
sql = """
select
    cast(o.updated_at as date) as day,
    c.grade,
    count(*) as orders,
    sum(o.amount) as sales
from stg_orders o
join stg_customers c using (customer_id)
where o.status = 'paid'
group by 1, 2
"""
for col, node in lineage(None, sql, schema, dialect="duckdb").items():
    srcs = sorted({f"{n.source.name}.{n.name.split('.')[-1]}"
                   for n in node.walk() if not n.downstream and n.source.name})
    print(f"{col:7} <- {', '.join(srcs) or '(없음)'}")
```


출력 컬럼 넷의 재료가 정확히 나왔다. `orders`는 `count(*)`라 특정 컬럼에서 오지 않는다. 여기서 볼 점이 두 가지 있다.

하나는 `status`가 어디에도 없다는 것이다. `where o.status = 'paid'`는 값을 만드는 데 쓰이지 않고 행을 거르는 데만 쓰였으니, 값의 계보로는 잡히지 않는다. 그런데 `status`를 지우면 이 쿼리는 깨진다. 그래서 영향 분석을 할 때는 "값이 흘러가는 계보"와 "쿼리가 참조하는 컬럼" 둘 다 본다. OpenLineage도 이 구분을 위해 컬럼 계보에 직접 쓰임(DIRECT)과 간접 쓰임(INDIRECT, 필터·조인·그룹 키 등)을 나눠 적을 수 있게 해 뒀다.

다른 하나는 스키마를 줘야 했다. `using (customer_id)`나 별칭 없는 컬럼은 어느 테이블 것인지 SQL만 봐서는 모른다. `select *`도 그렇다. 파서 기반 계보가 정확하려면 카탈로그가 이미 스키마를 알고 있어야 한다. 기술 메타데이터가 계보의 재료가 되는 셈이다.

SQL 파싱이 약한 곳도 분명하다.

- SQL이 아닌 변환. Python으로 쓴 Spark 잡, pandas 스크립트, Kafka 컨슈머는 파싱할 SQL이 없다.
- 실행 시점에 조립되는 SQL. 문자열을 이어 붙여 만든 쿼리, 테이블 이름이 변수인 쿼리는 실행 전에는 모양을 모른다.
- 방언 차이. 웨어하우스마다 문법이 조금씩 달라서 파서가 못 읽는 문장이 생긴다. 못 읽은 문장은 계보에서 조용히 빠진다.
- 저장 프로시저와 뷰 안의 뷰. 한 겹씩 풀어야 끝 재료가 보인다.

## 두 번째 방법: 실행하면서 알린다

다른 방법은 실행 엔진이 일하면서 "나는 이걸 읽어서 저걸 썼다"는 이벤트를 내보내게 하는 것이다. 이걸 표준으로 정한 게 OpenLineage다. LF AI & Data 재단의 프로젝트로, 작업(job), 실행(run), 데이터셋(dataset) 세 가지와 거기 붙는 부가 정보(facet)로 이벤트 모양을 정했다. Airflow(`apache-airflow-providers-openlineage`), Spark(SparkListener로 붙는 `openlineage-spark`), dbt(`dbt-ol` 래퍼), Flink용 통합이 있고, 받는 쪽으로는 참조 구현인 Marquez와 DataHub, OpenMetadata 같은 카탈로그가 이 이벤트를 받는다.

이벤트가 실제로 어떻게 생겼는지 Python 클라이언트로 만들어 직렬화해 봤다. 빈 값과 `_producer` 같은 반복 필드는 줄였다.

```python
# ol_event.py 일부
event = RunEvent(
    eventType=RunState.COMPLETE,
    eventTime=datetime(2026, 10, 22, 2, 14, 5, tzinfo=timezone.utc).isoformat(),
    run=Run(runId="0192b3c4-5d6e-7f80-9a1b-2c3d4e5f6a7b"),
    job=Job(namespace="dbt", name="shop.fct_daily_sales"),
    producer="https://example.com/shop-pipeline",
    inputs=[InputDataset(namespace=ns, name="main.stg_orders"),
            InputDataset(namespace=ns, name="main.stg_customers")],
    outputs=[OutputDataset(namespace=ns, name="main.fct_daily_sales", facets=out_facets)],
)
print(Serde.to_json(event))
```

데이터셋은 `namespace`와 `name` 두 값으로 구별된다. 이 둘이 계보 그래프의 노드 이름이다. Spark 잡이 `s3://lake/orders`라고 보내고 dbt가 `analytics.orders`라고 보내면, 같은 데이터라도 카탈로그에는 노드가 둘 생기고 선이 끊긴다. OpenLineage는 저장소마다 이름 짓는 규칙(naming convention)을 정해 두었지만, 같은 데이터를 경로로도 테이블로도 읽는 레이크 환경에서는 이 둘을 잇는 작업을 따로 해야 하는 경우가 많다. 계보가 군데군데 끊겨 보인다면 대개 이 이름 문제다.

실행 이벤트 방식의 장점은 정직하다는 것이다. 실제로 실행된 것만 선이 된다. 파싱으로는 알 수 없던 Python 잡의 입출력, 변수로 정해진 테이블 이름이 다 잡힌다. 단점은 반대쪽에 있다. 한 번도 실행되지 않은 경로(분기 안의 코드, 월말에만 도는 잡)는 아직 그래프에 없다. 통합이 없는 도구는 직접 이벤트를 보내야 한다. 그래서 실무에서는 dbt의 `manifest.json`처럼 정적으로 아는 그래프를 먼저 깔고, 실행 이벤트로 그 위에 실제 실행과 SQL이 아닌 잡을 덧붙인다. Databricks Unity Catalog처럼 실행 엔진과 카탈로그가 한 제품이면 엔진이 계보를 직접 남긴다.

dbt 프로젝트라면 이 그래프가 이미 `manifest.json`에 들어 있다. `child_map`이 노드마다 자식 목록을 들고 있어서, 몇 줄이면 아래쪽을 훑을 수 있다(테스트 노드는 뺐다).

```python
# impact.py: dbt manifest로 테이블 단위 영향 범위 보기
import json
m = json.load(open("shop/target/manifest.json"))
child = m["child_map"]
def downstream(node, depth=0, seen=set()):
    for c in sorted(child.get(node, [])):
        if c in seen or c.startswith("test."): continue
        seen.add(c)
        print("  " * depth + "└ " + c)
        downstream(c, depth + 1, seen)
downstream("seed.shop.raw_orders")
```

```text
└ model.shop.stg_orders
  └ model.shop.fct_daily_sales
  └ model.shop.fct_orders
```

영향 분석을 사람 손에 맡기면 결국 안 한다. 그래서 잘 굴러가는 팀은 이걸 PR 검사에 넣는다. 원본 스키마나 dbt 모델이 바뀌는 PR이 올라오면 CI가 계보에서 아래쪽 노드를 찾아 PR 댓글로 달고, 그 노드의 담당 팀을 리뷰어로 붙인다. 컬럼 삭제처럼 깨지는 변경이면, 아래쪽에 쓰는 곳이 남아 있는 한 병합을 막는다. 원본 팀과 이런 약속을 문서로 맺는 데이터 계약은 [데이터 품질 검사](/posts/data-quality-checks)의 데이터 계약 부분에서 다룬다.

## 틀린 숫자에서 거꾸로 올라간다

계보는 아래로만 쓰지 않는다. "오늘 아침 매출 대시보드 숫자가 어제 그대로다"라는 문의가 오면 이번에는 화살표를 거꾸로 따라 올라간다. 이때 계보만 있으면 반쪽이고, 노드마다 운영 메타데이터(마지막 실행 상태, 갱신 시각, 테스트 결과)가 붙어 있어야 어디서 멈췄는지 바로 보인다.

dbt 프로젝트라면 `manifest.json`의 `parent_map`(위쪽 목록)과 마지막 실행 결과인 `run_results.json`을 합치면 된다. [dbt 글](/posts/dbt-transformations)에서 원본에 `paied` 오타가 섞인 날의 `dbt build` 결과로 돌려 봤다.

```python
# upstream.py: 결과 테이블에서 위로 올라가며 상태와 실패한 테스트를 붙인다
import json
m = json.load(open("shop/target/manifest.json"))
r = json.load(open("shop/target/run_results.json"))
status = {x["unique_id"]: x["status"] for x in r["results"]}
def failed_tests(node):   # 이 노드에 붙은 테스트 중 실패한 것
    return [c.split(".")[2] for c in m["child_map"].get(node, [])
            if c.startswith("test.") and status.get(c) == "fail"]
def upstream(node, depth=0):
    for p in sorted(m["parent_map"].get(node, [])):
        bad = failed_tests(p)
        print("  " * depth + f"↑ {p} [{status.get(p, '-')}]" + (f" 실패한 테스트: {bad}" if bad else ""))
        upstream(p, depth + 1)
target = "model.shop.fct_daily_sales"
print(f"{target} [{status.get(target)}]")
upstream(target)
```

```text
model.shop.fct_daily_sales [skipped]
↑ model.shop.stg_customers [success]
  ↑ seed.shop.raw_customers [success]
↑ model.shop.stg_orders [success] 실패한 테스트: ['accepted_values_stg_orders_status__paid__refunded__cancelled']
  ↑ seed.shop.raw_orders [success]
```

첫 줄에서 대시보드가 읽는 `fct_daily_sales`가 이번 실행에서 건너뛰어졌다(`skipped`)는 게 보이고, 위로 올라가면 `stg_orders`에 붙은 상태값 테스트가 실패했다는 게 보인다. 대시보드가 어제 숫자인 이유와 고칠 곳이 한 화면에 나온다. 카탈로그 제품이 계보 화면에 노드별 최근 실행 상태와 품질 검사 결과를 같이 띄우는 이유가 이것이다. 계보만 보면 "어디서 왔나"는 알지만 "어디서 멈췄나"는 모른다.

거꾸로 올라갈 때 자주 걸리는 함정이 있다. 위쪽 노드가 모두 `success`인데 숫자가 틀린 경우다. 실행은 성공했지만 데이터가 틀린 것이라, 상태값만 보면 원인이 안 보인다. 이때는 노드마다 행 수와 갱신 시각을 본다. 원본 테이블의 마지막 적재 시각이 이틀 전이면 원본이 안 들어온 것이고, 행 수가 평소의 절반이면 원본이 반만 들어온 것이다. 이런 신호를 미리 검사로 걸어 두는 법은 [데이터 품질 검사](/posts/data-quality-checks)에서 다룬다.

## 메타데이터를 나중에 적지 않고 먼저 내보낸다

카탈로그 도입이 실패하는 가장 흔한 모습은 이렇다. 도입 첫 달에 데이터 팀이 주요 테이블 200개에 설명을 열심히 적는다. 석 달 뒤 테이블은 350개가 되고, 새로 생긴 150개에는 설명이 없고, 처음 200개 중 절반은 컬럼이 바뀌어 설명이 틀렸다. 사람들은 카탈로그를 믿지 않게 되고, 다시 슬랙에서 "이 테이블 누가 알아요?"라고 묻는다. 아무도 갱신하지 않는 카탈로그는 없는 것보다 나쁘다. 틀린 답을 자신 있게 준다.

원인은 메타데이터를 데이터를 만든 뒤에 따로 적는 문서로 다룬 데 있다. 문서는 코드가 바뀔 때 같이 바뀌지 않는다. 메타데이터 우선(metadata-first) 설계는 순서를 뒤집는다. 메타데이터를 파이프라인 코드 옆에 두고, 파이프라인이 실행되면서 그걸 내보내게 한다. 카탈로그는 그걸 받아서 보여 주는 읽기 전용 창이 된다.

- 설명과 담당자는 코드 저장소에 둔다. dbt의 `schema.yml`에 `description`과 `meta: owner`를 쓰면 PR로 리뷰되고, 빌드할 때마다 `manifest.json`으로 카탈로그에 올라간다.
- 스키마는 생산자가 등록한다. Kafka 토픽은 스키마 레지스트리에 스키마를 먼저 등록하고, 호환되지 않는 변경은 레지스트리가 거절하게 한다.
- 계보는 실행이 낸다. 오케스트레이터와 엔진에 OpenLineage 통합을 켜 두면 새 파이프라인도 첫 실행부터 그래프에 들어온다.
- 운영 메타데이터는 저절로 쌓인다. 실행 이벤트의 시각과 상태가 곧 신선도와 실행 이력이다.
- 빠진 것은 CI가 막는다. 새 모델에 `description`이나 담당자가 없으면 PR 검사가 실패하게 한다. 강제하지 않으면 바빠서 안 쓴다.

이렇게 해도 사람이 적어야 하는 업무 메타데이터는 남는다. "활성 사용자"가 30일 기준인지 7일 기준인지는 코드가 모른다. 다만 이것도 코드 옆 YAML에 두면 지표 정의가 바뀔 때 같은 PR에서 고치게 된다. 지표 정의를 한 곳에 모으는 시맨틱 레이어 이야기는 [데이터 웨어하우스 구조](/posts/data-warehouse-architecture)의 매출 정의 부분에 있다.

## 모델 학습 데이터의 계보

ML에서도 같은 질문이 나온다. 다만 끝 노드가 대시보드가 아니라 모델이다. 지난주 배포한 추천 모델의 성능이 떨어졌는데, 그 모델이 어느 시점의 어떤 테이블로 학습됐는지 모르면 원인을 좁힐 수 없다. 원본 테이블에 버그가 있었다는 걸 알게 됐을 때 "그 데이터로 학습한 모델이 어느 것인가"를 거꾸로 찾는 것도 계보다.

ML 계보에는 테이블 이름만으로는 부족하다. 테이블은 계속 바뀌니 "어느 시점의" 데이터인지까지 남겨야 한다. Delta Lake나 Iceberg 테이블이면 학습에 쓴 테이블 버전(스냅숏 id)을, 파일이면 경로와 해시를, 피처 테이블이면 조회 시점을 함께 적는다. 그리고 데이터셋 버전 → 학습 실행 → 모델 버전 → 배포를 한 줄로 잇는다. 실험 추적 도구(MLflow 등)는 실행마다 입력 데이터셋을 기록하는 기능을 두고 있고, 이 실행 기록을 카탈로그의 데이터 계보와 같은 이름 규칙으로 이으면 원본 컬럼에서 배포된 모델까지 한 그래프로 본다. 실행 기록을 남기는 법은 [ML 실험 추적](/posts/ml-experiment-tracking)에서, 데이터와 모델을 함께 관리하는 전체 흐름은 [MLOps란](/posts/what-is-mlops)에서 이어진다.

개인정보 삭제 요청을 처리할 때도 이 계보가 필요하다. 어떤 사용자의 데이터를 지워야 한다면 원본뿐 아니라 그 데이터가 흘러간 파생 테이블과 학습 데이터셋까지 찾아야 한다.

## 카탈로그를 고를 때 보는 것

제품 비교표는 금방 낡으니 기준만 적는다.

먼저 우리 스택에 커넥터가 있는지 본다. 웨어하우스, BI 도구, 오케스트레이터, dbt, Kafka에 붙는 커넥터가 이미 있으면 첫 달에 그래프가 채워지고, 없으면 직접 수집기를 짜야 한다. 다음은 수집 방식이다. 끌어오기만 되는지, OpenLineage 같은 이벤트를 받아 주는지, 받는다면 컬럼 계보까지 그리는지 확인한다.

운영 부담도 크다. DataHub와 OpenMetadata는 직접 띄우면 검색 엔진(Elasticsearch나 OpenSearch), 관계형 DB, DataHub는 Kafka까지 함께 굴려야 한다. 플랫폼 팀이 작으면 관리형 서비스나 클라우드 제공 카탈로그가 낫다. 반대로 클라우드 제공 카탈로그(Glue, Dataplex, Unity Catalog)는 자기 플랫폼 안에서는 계보를 저절로 잘 남기지만, 바깥 시스템(다른 클라우드, 온프레미스 DB, SaaS)까지 잇기는 어려운 경우가 많다.

마지막으로 권한 관리와 이어지는지 본다. 카탈로그가 개인정보 태그를 들고 있다면, 그 태그로 실제 접근 제어(마스킹, 행 필터)까지 걸 수 있는지에 따라 카탈로그가 "보는 도구"에 그치는지 "거버넌스의 중심"이 되는지 갈린다.

## 계보가 있어도 아무도 안 볼 때

계보 그래프를 만들어 놓고도 효과가 없는 경우가 있다. 몇 가지 원인과 처방이다.

- 그래프가 너무 크다. 노드 3,000개짜리 그래프를 화면에 띄우면 아무도 못 읽는다. 기본 화면은 위아래 한두 겹만 보여 주고, 영향 분석은 목록과 담당자로 보여 준다.
- 끊긴 곳이 많다. 같은 데이터를 다른 이름으로 부르는 시스템(경로와 테이블, 대소문자, 스키마 접두어)을 잇지 않아서다. 처음에 이름 규칙부터 맞춘다.
- 담당자가 비어 있다. 영향 범위를 알아도 연락할 사람이 없으면 소용없다. 담당자를 사람 이름이 아니라 팀(슬랙 채널, 호출 그룹)으로 적는다. 사람은 퇴사한다.
- 쓰는 순간에 없다. 카탈로그를 따로 열어야 볼 수 있으면 잘 안 연다. PR 댓글, 쿼리 편집기, 대시보드 화면처럼 이미 일하는 자리에 계보와 설명을 띄운다.
- 측정하지 않는다. "설명이 있는 테이블 비율", "담당자가 있는 테이블 비율", "계보가 연결된 대시보드 비율"을 지표로 둔다. 숫자가 내려가면 메타데이터가 낡아 가는 중이다.

작은 팀이라면 카탈로그 제품부터 들일 필요는 없다. dbt를 쓰고 있으면 `dbt docs`가 이미 모델 설명과 의존 그래프를 보여 준다. 테이블이 수백 개를 넘고, "이거 누가 써요?"라는 질문이 일주일에 몇 번씩 나오고, 데이터 팀 밖의 소비자(BI, 리버스 ETL, ML)가 생기면 그때 카탈로그를 들인다.

## 지도는 길을 다니는 차가 그린다

메타데이터는 기술, 업무, 운영 셋으로 나뉘고, 카탈로그는 그걸 모아 검색과 계보, 담당자를 보여 준다. 계보는 SQL을 파싱해 만들 수도 있고 실행 엔진이 OpenLineage 이벤트로 알려 줄 수도 있는데, 앞의 것은 SQL이 아닌 잡과 동적 SQL을 놓치고 뒤의 것은 아직 안 돈 경로를 모른다. 계보의 쓸모는 바꾸기 전에 아래쪽을 훑는 영향 분석에서 나오고, 그게 PR 검사에 들어가야 실제로 쓰인다. 무엇보다 메타데이터를 나중에 손으로 적으면 낡는다. 파이프라인이 일하면서 내보내게 해야 지도가 길과 같이 바뀐다.

## 면접에서 나올 만한 질문

### 데이터 계보란 무엇이고 왜 필요한가요

어떤 데이터가 어디서 와서 어디로 가는지, 무엇을 읽어서 무엇을 만들었는지를 이은 그래프다. 컬럼을 지우거나 로직을 바꾸기 전에 영향받는 테이블과 대시보드를 찾는 영향 분석, 숫자가 틀렸을 때 거꾸로 올라가 원인을 찾는 근본 원인 분석, 개인정보가 흘러간 곳을 찾는 규정 대응에 쓴다. 테이블 단위만으로는 범위가 너무 넓게 잡혀서 컬럼 단위 계보가 있어야 실무에서 쓸 만하다.

### 계보는 어떻게 수집하나요

크게 두 방법이다. 웨어하우스 쿼리 기록이나 dbt가 컴파일한 SQL을 파싱해 입력과 출력 컬럼을 뽑는 방법, 그리고 실행 엔진이 실행 시점에 읽은 것과 쓴 것을 OpenLineage 같은 이벤트로 보내는 방법이다. 파싱은 붙이기 쉽지만 SQL이 아닌 잡과 실행 때 조립되는 SQL을 놓친다. 실행 이벤트는 실제 입출력을 정확히 주지만 아직 실행되지 않은 경로는 모르고 통합이 없는 도구에는 직접 붙여야 한다. 보통 dbt manifest 같은 정적 그래프 위에 실행 이벤트를 덧붙인다.

### SQL 파싱 기반 계보가 틀리거나 빠지는 경우는 언제인가요

`select *`나 별칭 없는 컬럼처럼 스키마를 알아야 풀리는 경우, 문자열로 조립하거나 테이블 이름이 변수인 동적 SQL, 파서가 지원하지 않는 방언 문법, Python이나 Spark 코드처럼 SQL이 없는 변환이다. 또 WHERE나 JOIN 조건에만 쓰인 컬럼은 값의 계보로 잡히지 않아서, 그 컬럼을 지우면 쿼리가 깨지는데도 영향 분석에서 빠질 수 있다. 그래서 직접 쓰임과 간접 쓰임을 나눠 본다.

### OpenLineage 이벤트에는 무엇이 들어 있나요

작업(job), 실행(run), 입력·출력 데이터셋이 기본이고, 이벤트 종류는 START, COMPLETE, FAIL, ABORT 등이다. 데이터셋은 namespace와 name으로 구별하고, 스키마, 컬럼 계보, 행 수 같은 부가 정보를 facet으로 붙인다. 부모 실행의 runId를 실어 Airflow 태스크와 그 안의 Spark 잡을 잇는다. 같은 데이터를 시스템마다 다른 이름으로 보내면 그래프가 끊기는 게 흔한 문제다.

### 데이터 카탈로그 도입이 실패하는 이유는 무엇인가요

아무도 갱신하지 않기 때문이다. 처음에 설명을 손으로 열심히 적어도 테이블은 늘고 컬럼은 바뀌는데 문서는 따라가지 않는다. 틀린 설명이 쌓이면 사람들이 카탈로그를 믿지 않고 다시 사람에게 묻는다. 그래서 설명과 담당자를 코드 옆에 두고 빌드 때 올리고, 계보와 운영 정보는 실행이 내보내게 하며, 새 테이블에 설명이나 담당자가 없으면 CI가 막는 식으로 갱신을 사람의 성실함에 맡기지 않는다.

### 메타데이터 우선 설계란 무엇인가요

메타데이터를 데이터를 만든 뒤에 따로 적는 문서로 두지 않고, 파이프라인 코드 옆에 두고 실행할 때 내보내게 하는 설계다. 스키마는 생산자가 레지스트리에 먼저 등록하고, 설명과 담당자는 모델 YAML에 쓰고, 계보와 실행 기록은 OpenLineage 같은 이벤트로 자동으로 쌓인다. 카탈로그는 그걸 받아 보여 주는 읽기 전용 창이 된다. 그래서 코드가 바뀌면 메타데이터도 같은 PR에서 바뀐다.

### ML 모델의 학습 데이터 계보는 무엇을 남겨야 하나요

테이블 이름뿐 아니라 어느 시점의 데이터인지까지 남긴다. 테이블 포맷의 스냅숏 id, 파일 경로와 해시, 피처 조회 시점 같은 것이다. 그리고 데이터셋 버전, 학습 실행, 모델 버전, 배포를 한 줄로 잇는다. 그래야 원본 버그가 발견됐을 때 그 데이터로 학습한 모델을 찾고, 성능이 떨어진 모델의 학습 데이터를 다시 꺼내 비교할 수 있다.
