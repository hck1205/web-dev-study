API 응답이 느려져서 서버에 들어갔다. `uptime`의 load average는 8을 넘는데 `top`을 보면 CPU는 절반 넘게 놀고 있다. CPU가 남는데 부하가 높다는 건 이상해 보이지만, 리눅스의 load average는 CPU를 쓰는 프로세스만 세지 않는다. 디스크나 네트워크 저장소를 기다리며 꼼짝 못 하는 프로세스(`D` 상태)도 함께 센다. `ps`의 STAT 칸 한 글자를 읽을 줄 알면 여기서 바로 방향이 잡힌다.

이 글은 프로세스가 어떻게 생기고 어떤 상태를 오가는지, `ps`와 `/proc`으로 무엇을 읽는지, 시그널이 프로세스에 어떻게 닿고 프로그램이 그걸 어떻게 받는지를 본다. 좀비와 고아 프로세스는 직접 만들어 보고, 컨테이너의 PID 1이 왜 좀비를 거둬야 하는지까지 간다. 기준은 Ubuntu 24.04 LTS이고 22.04도 같다.

## 프로세스는 부모가 만든다

리눅스에서 프로세스는 모두 다른 프로세스가 만든다. 부모가 `fork()`로 자기를 복제하고, 복제된 자식이 `exec()`로 다른 프로그램으로 바뀐다. 그래서 모든 프로세스에는 자기 번호(PID)와 부모 번호(PPID)가 있고, 전체가 하나의 나무가 된다. 뿌리는 커널이 처음 띄우는 PID 1이고, Ubuntu에서는 systemd다.

nginx를 띄워 보면 이 나무가 잘 보인다. 실습에서는 `/srv/r1ngx/nginx.conf`로 따로 띄웠고, 패키지로 설치한 nginx라면 PID 파일은 `/run/nginx.pid`에 있다.

```bash
# 마스터와 그 자식(워커)을 함께 본다
ps -o pid,ppid,user,stat,cmd --ppid $(cat /srv/r1ngx/nginx.pid) -p $(cat /srv/r1ngx/nginx.pid)

# 나무 모양으로 본다
pstree -p $(cat /srv/r1ngx/nginx.pid)
```

```text
  PID  PPID USER     STAT CMD
10822     1 root     Ss   nginx: master process nginx -c /srv/r1ngx/nginx.conf -p /srv/r1ngx
10824 10822 www-data S    nginx: worker process
10825 10822 www-data S    nginx: worker process
nginx(10822)-+-nginx(10824)
             `-nginx(10825)
```

워커 두 개의 PPID가 마스터다. 마스터는 root로 떠서 80 포트를 열고 설정을 읽은 뒤, 실제 요청을 처리하는 워커는 `www-data`로 낮춰 띄운다. 마스터의 PPID가 1인 것도 눈여겨본다. 나는 셸에서 nginx를 띄웠는데 부모가 셸이 아니다. nginx가 스스로 데몬이 되면서 한 번 더 fork하고 원래 프로세스를 끝냈기 때문이다. 부모가 먼저 사라진 프로세스는 PID 1의 자식으로 입양된다. 이 규칙은 뒤에서 좀비 이야기와 이어진다.

필요한 칸만 골라 보는 게 읽기 편하다.

```bash
# 원하는 칸만 고르고, CPU 사용률 순으로 위 5개
ps -eo pid,ppid,user,stat,ni,%cpu,rss,etime,cmd --sort=-%cpu | head -6

# 나무 모양으로 전체를 본다 (부모 자식 관계가 들여쓰기로 보인다)
ps -eo pid,ppid,stat,cmd --forest
```

`top`은 같은 정보를 몇 초마다 다시 그린다. `top -b -n 1`로 한 번만 찍으면 스크립트에도 쓸 수 있다. htop(`sudo apt install htop`)은 같은 정보를 색과 막대로 보여 주고 나무 보기(F5)와 프로세스 골라 시그널 보내기(F9)가 편하다. 칸 이름과 뜻은 셋 다 같다.

대부분의 프로세스는 `S`에 있다. 소켓에 요청이 오기를, 타이머가 끝나기를 기다린다. `S`는 시그널이 오면 깨어나서 처리할 수 있다. `D`는 다르다. 커널 안에서 I/O가 끝나기를 기다리는 중이라 시그널을 받아도 깨어나지 않는다. `kill -9`도 바로 듣지 않는다.

`D` 상태는 평소엔 아주 짧게 지나가서 보기 어렵다. 실습에서는 cgroup v1의 freezer로 프로세스를 얼려서 같은 상태를 만들었다.

```bash
# 프로세스 하나를 얼려서 D 상태로 만든다 (cgroup v1 freezer, 실습용)
sleep 120 & S=$!
echo $S > /sys/fs/cgroup/freezer/r1demo/cgroup.procs
echo FROZEN > /sys/fs/cgroup/freezer/r1demo/freezer.state

# 상태와 커널 안에서 기다리는 함수(wchan)를 본다
ps -o pid,stat,wchan:22,cmd -p $S
grep State /proc/$S/status

# SIGKILL을 보내도 그대로다
kill -9 $S; ps -o pid,stat,cmd -p $S
```

```text
  PID STAT WCHAN                  CMD
 9790 D    refrigerator           sleep 120
State:	D (disk sleep)
  PID STAT CMD
 9790 D    sleep 120
```

SIGKILL은 사라진 게 아니라 쌓여 있다. 얼음을 풀자(`THAWED`) 그제야 `Killed`가 찍히고 프로세스가 끝났다. 현장에서 `D`는 대개 응답 없는 NFS 서버, 죽어 가는 디스크, 꽉 찬 블록 장치 대기열에서 나온다. 처음 상황처럼 load average가 높은데 CPU가 놀고 있으면 이렇게 확인한다.

```bash
# D 상태 프로세스와 기다리는 커널 함수
ps -eo pid,stat,wchan:32,cmd | awk '$2 ~ /^D/'

# 디스크별 대기 시간과 사용률 (sysstat 패키지)
iostat -x 1 3
```

`wchan`에 `nfs_`나 `rpc_`로 시작하는 이름이 보이면 NFS 쪽이고, 블록 I/O 함수가 보이고 `iostat`의 `%util`이 100에 붙어 있으면 디스크 쪽이다. 프로세스를 죽여서 풀리는 문제가 아니라 기다리는 대상을 살려야 풀린다. NFS를 `hard`로 마운트하면 서버가 돌아올 때까지 영원히 기다리는 게 기본 동작이다.

## proc 파일 시스템에 프로세스가 다 있다

`ps`와 `top`은 사실 `/proc/<PID>/` 아래 파일을 읽어서 보여 준다. 도구가 없는 작은 컨테이너에서도 이 파일들은 있으니 직접 읽는 법을 알아 두면 편하다.

실습 nginx를 다시 띄웠더니 마스터는 2712, 워커는 2713이었다.

```bash
# nginx 워커 하나의 상태 요약
grep -E '^(Name|State|PPid|Uid|Gid|Groups|Threads|VmRSS)' /proc/2713/status

# 실행할 때의 명령줄 (구분자가 NUL이라 공백으로 바꾼다)
tr '\0' ' ' < /proc/2712/cmdline; echo

# 열어 둔 파일과 소켓
sudo ls -l /proc/2712/fd

# 이 프로세스에 걸린 한도
grep -E 'Max open files|Max processes' /proc/2712/limits
```

## 시그널은 커널이 전하는 번호 하나

시그널은 프로세스에게 "이 일이 일어났다"고 알리는 번호다. 내용은 번호뿐이다. 다른 프로세스가 `kill()`로 보내기도 하고, 커널이 직접 보내기도 한다(잘못된 메모리 접근이면 SIGSEGV, 자식이 끝나면 부모에게 SIGCHLD). `kill -l`로 전체 목록을 본다.

```bash
# 시그널 번호와 이름
kill -l
```

```text
 1) SIGHUP	 2) SIGINT	 3) SIGQUIT	 4) SIGILL	 5) SIGTRAP
 6) SIGABRT	 7) SIGBUS	 8) SIGFPE	 9) SIGKILL	10) SIGUSR1
11) SIGSEGV	12) SIGUSR2	13) SIGPIPE	14) SIGALRM	15) SIGTERM
16) SIGSTKFLT	17) SIGCHLD	18) SIGCONT	19) SIGSTOP	20) SIGTSTP
```

실무에서 자주 만나는 건 몇 개 안 된다.

- SIGTERM(15): "정리하고 끝내라". `kill`의 기본값이고, systemd와 쿠버네티스가 서비스를 멈출 때 먼저 보낸다.
- SIGKILL(9): 커널이 바로 끝낸다. 프로그램은 받지도 못하고 정리할 기회도 없다.
- SIGINT(2): 터미널에서 Ctrl+C. 포그라운드 프로세스 그룹 전체에 간다.
- SIGHUP(1): 원래는 터미널 연결이 끊겼다는 뜻이다. SSH가 끊기면 그 세션에서 띄운 프로그램이 이걸 받고 죽는다. 데몬은 터미널이 없으니 관례로 "설정을 다시 읽어라"로 쓴다.
- SIGQUIT(3): Ctrl+\. 기본 동작이 코어 덤프를 남기고 끝내는 것이다.
- SIGSTOP(19)과 SIGCONT(18): 멈추고 다시 돌린다. SIGSTOP도 막을 수 없다.
- SIGCHLD(17): 자식이 끝났다. 좀비를 거두는 신호가 된다.

시그널을 받은 프로세스는 셋 중 하나를 한다. 등록해 둔 핸들러를 실행하거나, 무시하거나, 기본 동작(대부분 종료)을 한다. SIGKILL과 SIGSTOP은 핸들러도 무시도 안 되고 항상 기본 동작이다. 아래 그림에서 다음을 누르면 SIGTERM과 SIGKILL이 어떻게 다르게 처리되는지 보인다.

## 핸들러를 등록한 프로그램과 안 한 프로그램

SIGTERM과 SIGHUP을 받는 작은 파이썬 서비스로 확인했다.

```python
# svc.py
import signal, time, sys
def on_term(sig, frame):
    print("SIGTERM 받음: 처리 중인 요청을 끝내고 종료", flush=True); sys.exit(0)
def on_hup(sig, frame):
    print("SIGHUP 받음: 설정 다시 읽기", flush=True)
signal.signal(signal.SIGTERM, on_term)
signal.signal(signal.SIGHUP, on_hup)
while True: time.sleep(1)
```

```bash
# 띄운 뒤 HUP, TERM 순서로 보내고 종료 코드를 본다
python3 svc.py & P=$!
kill -HUP $P
kill -TERM $P; wait $P; echo "exit=$?"

# 핸들러가 없는 sleep에 기본 SIGTERM을 보내면
sleep 100 & S=$!; kill $S; wait $S; echo "sleep exit=$?"

# SIGKILL은 핸들러가 있어도 바로 죽는다
python3 svc.py & P=$!; kill -KILL $P; wait $P; echo "exit=$?"
```

```text
SIGHUP 받음: 설정 다시 읽기
SIGTERM 받음: 처리 중인 요청을 끝내고 종료
exit=0
sleep exit=143
exit=137
```

어떤 프로세스가 어떤 시그널을 받을 준비가 돼 있는지는 `/proc/<PID>/status`의 비트 마스크로 보인다. `SigCgt`는 핸들러를 등록한 시그널, `SigIgn`은 무시하는 시그널이다. 16진수 숫자의 n번째 비트(0부터)가 n+1번 시그널이다.

```bash
# 시그널 마스크 보기
grep -E '^Sig(Cgt|Ign)' /proc/$P/status
```

```text
SigIgn:	0000000001001000
SigCgt:	0000000000004003
```

"SIGTERM 처리를 넣었는데 왜 안 먹지?"라는 의심이 들 때 이걸 본다. `SigCgt`에 SIGTERM 비트가 없으면 코드가 실제로는 핸들러를 등록하지 못한 것이다. 아래에서 마스크를 이름으로 바꾸는 함수를 직접 써 보자. 마지막 테스트는 nginx 워커에서 읽은 실제 값이다.

로그 파일을 돌릴 때는 SIGUSR1을 쓴다. 파일 이름을 바꿔도 nginx는 열어 둔 파일 디스크립터로 계속 옛 파일에 쓴다. 이름이 아니라 열린 파일을 붙잡고 있기 때문이다.

```bash
# 로그 파일 이름을 바꾸고 요청을 하나 보낸다

curl -s -o /dev/null http://127.0.0.1:18081/
ls -l /srv/r1ngx/logs/

# SIGUSR1: 로그 파일을 다시 연다. 이후 요청은 새 파일에 쓰인다
sudo kill -USR1 $(cat /srv/r1ngx/nginx.pid)
curl -s -o /dev/null http://127.0.0.1:18081/
ls -l /srv/r1ngx/logs/
```

-rw-r--r-- 1 root     root  85 Oct 20 14:35 access.log.1

첫 요청은 이름을 바꾼 `access.log.1`에 들어갔고, SIGUSR1 뒤의 요청은 새 `access.log`에 들어갔다. Ubuntu의 logrotate 설정(`/etc/logrotate.d/nginx`)도 `postrotate`에서 같은 신호를 보낸다. 직접 만든 앱이 로그 파일을 열어 두고 쓰는데 이런 신호 처리가 없으면, 돌린 뒤에도 지운 파일에 계속 써서 디스크가 줄지 않는다. 그때 `/proc/<PID>/fd`에 `(deleted)`가 보인다. logrotate의 `copytruncate`는 앱을 건드리지 않는 대신 복사와 비우기 사이에 쓴 몇 줄을 잃을 수 있다.

종료도 둘로 나뉜다. nginx에서 SIGTERM과 SIGINT는 빠른 종료(연결을 바로 끊음), SIGQUIT는 우아한 종료(처리 중인 요청을 끝내고 종료)다. 프로그램마다 의미가 다르니 문서에서 확인한다.

## 좀비와 고아

자식 프로세스가 끝나도 바로 사라지지 않는다. 커널은 부모가 `wait()`로 종료 코드를 가져갈 때까지 프로세스 표에 작은 항목(PID, 종료 상태)을 남겨 둔다. 이 상태가 좀비(`Z`, `<defunct>`)다. 메모리와 파일은 이미 다 돌려줬고 PID 하나와 표 항목만 차지한다.

wait를 부르지 않는 부모를 만들어서 확인했다.

```python
# zombie.py: 자식은 바로 끝나고, 부모는 wait()를 부르지 않는다
import os, time
pid = os.fork()
if pid == 0:
    os._exit(3)
print("parent", os.getpid(), "child", pid, flush=True)
time.sleep(60)
```

```bash
python3 zombie.py & PP=$!
ps -o pid,ppid,stat,cmd -p $PP --ppid $PP

# 좀비에게 SIGKILL을 보내 본다
kill -9 $(pgrep -P $PP); ps -o pid,ppid,stat,cmd --ppid $PP

# 부모를 끝내면 좀비도 사라진다
kill $PP; ps -o pid,stat,cmd --ppid $PP || echo "zombie gone"
```

```text
parent 8755 child 8757
  PID  PPID STAT CMD
 8755  8752 S    python3 zombie.py
 8757  8755 Z    [python3] <defunct>
  PID  PPID STAT CMD
 8757  8755 Z    [python3] <defunct>
  PID STAT CMD
zombie gone
```

좀비는 이미 죽어 있어서 SIGKILL로 없앨 수 없다. 거둘 수 있는 건 부모뿐이다. 부모가 끝나면 좀비는 PID 1에게 입양되고, PID 1이 거둔다. 부모가 먼저 끝나서 살아 있는 자식이 입양되는 경우를 고아라고 부른다. 아래 그림은 이 과정을 프로세스 표로 따라간다.

좀비 몇 개는 해가 없다. 문제는 쌓일 때다. PID는 한정돼 있어서(`/proc/sys/kernel/pid_max`, 컨테이너라면 cgroup의 `pids.max`) 좀비가 수천 개 쌓이면 새 프로세스를 못 만든다. 그때 증상은 `fork: Resource temporarily unavailable`이나 `fork: retry: Resource temporarily unavailable`이다. `top` 두 번째 줄의 `zombie` 숫자가 계속 느는지 보고, 좀비의 PPID를 찾아 그 부모를 고치거나 재시작한다.

```bash
# 좀비와 그 부모를 찾는다
ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^Z/'
```

고아는 부모를 먼저 죽였을 때 생긴다. 셸 스크립트 부모만 죽이면 그 자식들은 살아남는다.

```bash
# parent.sh는 sleep 두 개를 띄우고 기다린다. 부모만 죽인 뒤 본다
ps -o pid,ppid,pgid,stat,cmd -C sleep

# 프로세스 그룹 전체에 보낸다 (PGID 앞에 -)
kill -TERM -- -3
```

```text
    PID    PPID    PGID STAT CMD
      5       1       3 S    sleep 301
      6       1       3 S    sleep 302
```

PPID가 1로 바뀌었다. PGID(프로세스 그룹)는 그대로 3이라서, 그룹 번호에 `-`를 붙여 보내면 남은 자식까지 한 번에 끝난다. 데스크톱 Ubuntu에서는 PID 1 대신 `systemd --user`처럼 자식 거두기(subreaper)를 맡은 프로세스가 입양하기도 해서 PPID가 1이 아닐 수 있다.

## 컨테이너의 PID 1은 좀비를 거둬야 한다

컨테이너는 자기만의 PID namespace를 갖고, 그 안에서 처음 뜬 프로세스가 PID 1이다. 보통은 앱 자신이다. 앱이 PID 1이면 두 가지 일을 떠맡는다. 핸들러가 없는 SIGTERM을 무시하게 되는 문제는 [Pod의 일생](/posts/k8s-pod-lifecycle)에서 재현했으니 여기서는 다른 하나, 고아를 입양하고 거두는 일을 본다.

헬스 체크 스크립트를 여러 번 돌리는 앱을 PID 1로 띄웠다. 스크립트는 백그라운드 작업을 하나 남기고 먼저 끝난다. 남은 작업은 고아가 되어 PID 1에게 입양되는데, 이 앱은 자기가 만들지 않은 자식을 기다릴 생각이 없다.

```python
# app.py
import subprocess, time
for _ in range(5):
    subprocess.run(["sh", "-c", "(sleep 1 &)"])
time.sleep(30)
```

```bash
# 새 PID namespace에서 app.py를 PID 1로 띄운다 (docker run과 같은 상황)
sudo unshare --pid --fork --mount-proc python3 app.py &
# 3초 뒤 namespace 안의 프로세스를 본다
sudo nsenter -t <app.py의 호스트 PID> -p -m ps -o pid,ppid,stat,cmd

# 같은 앱을 tini 아래에서 띄운다
sudo apt install -y tini
sudo unshare --pid --fork --mount-proc tini -- python3 app.py &
```

```text
    PID    PPID STAT CMD
      1       0 S    python3 app.py
      4       1 Z    [sleep] <defunct>
      7       1 Z    [sleep] <defunct>
     10       1 Z    [sleep] <defunct>
     13       1 Z    [sleep] <defunct>
     16       1 Z    [sleep] <defunct>
```

```text
    PID    PPID STAT CMD
      1       0 S    tini -- python3 app.py
      2       1 S    python3 app.py
```

앱이 PID 1이면 `sleep`이 끝날 때마다 좀비가 하나씩 남는다. tini가 PID 1이면 tini가 SIGCHLD를 받아 고아를 거두고, 받은 SIGTERM은 앱에게 넘겨준다. 오래 도는 컨테이너에서 셸 스크립트, `exec`로 띄우는 헬스 체크, 크롬 같은 자식을 많이 만드는 프로그램을 쓴다면 이 차이가 몇 주 뒤의 `fork` 실패로 나타난다. Docker는 `docker run --init`으로 tini를 넣어 주고, 쿠버네티스에는 같은 옵션이 없어서 이미지에 넣는다(`ENTRYPOINT ["tini", "--"]`). Pod의 `shareProcessNamespace: true`를 켜면 pause 컨테이너가 PID 1이 되어 거두는 일을 맡는다.

## kill, pkill, killall 고르기

`kill`은 PID로, `pkill`은 이름 패턴으로, `killall`은 정확한 프로그램 이름으로 보낸다(`killall`은 `psmisc` 패키지). `pkill`과 짝인 `pgrep`으로 먼저 무엇이 걸리는지 보는 습관이 사고를 막는다.

```bash
# 무엇이 걸리는지 먼저 본다 (-a: 명령줄까지)
pgrep -af queue_worker

# 프로세스 이름(comm)이 정확히 같은 것만
pkill -x nginx

# 살아 있는지만 확인 (시그널은 보내지 않는다)
kill -0 $PID && echo alive
```

`pkill -f`는 프로그램 이름이 아니라 명령줄 전체에서 패턴을 찾는다. 그래서 패턴이 들어간 다른 명령줄까지 맞는다. `stop_queue_worker.sh`라는 스크립트 안에 `pkill -f queue_worker`를 썼더니 이렇게 됐다.

```text
19480 python3 queue_worker.py
SIGTERM 받음: 처리 중인 요청을 끝내고 종료
Terminated
exit=143
```

worker는 잘 끝났지만 스크립트의 마지막 줄 `echo "중지 완료"`가 찍히지 않았다. 스크립트의 명령줄 `bash stop_queue_worker.sh`에도 `queue_worker`가 들어 있어서 스크립트가 자기 자신을 죽였다(종료 코드 143). `pkill`은 자기 자신은 빼 주지만 자기를 부른 셸은 빼 주지 않는다. `ssh server "pkill -f myapp"`처럼 원격으로 칠 때도 같은 일이 생긴다. 패턴을 `'^python3 queue_worker.py'`처럼 좁히거나, PID 파일을 쓰거나, 서비스로 등록해 `systemctl stop`으로 멈추는 게 안전하다.

종료는 순서대로 한다. SIGTERM을 보내고 몇 초 기다렸다가, 그래도 살아 있을 때만 SIGKILL이다. 처음부터 `kill -9`를 치면 DB 연결이 정리되지 않고, 임시 파일과 잠금 파일이 남아 다음 기동이 실패하기도 한다. systemd의 `TimeoutStopSec`, 쿠버네티스의 `terminationGracePeriodSeconds`가 바로 이 "기다리는 몇 초"다.

## nice로 CPU를 양보한다

백업이나 리포트 생성처럼 급하지 않은 작업이 웹 서버와 CPU를 다투면 nice 값을 올린다. nice는 -20(가장 욕심 많음)부터 19(가장 양보)까지이고 기본은 0이다. 일반 사용자는 올리기만 할 수 있고, 내리는 건 root만 된다.

CPU 하나에 무한 루프 두 개를 묶고 한쪽만 nice 10으로 띄웠다.

```bash
# 같은 CPU 0번에서 두 프로세스가 경쟁하게 한다
taskset -c 0 sh -c 'while :; do :; done' & A=$!
taskset -c 0 nice -n 10 sh -c 'while :; do :; done' & B=$!
sleep 6; ps -o pid,ni,pri,stat,%cpu,time,cmd -p $A,$B

# 이미 떠 있는 프로세스의 nice 바꾸기
sudo renice -n 0 -p $B
```

```text
  PID  NI PRI STAT %CPU     TIME CMD
11230   0  19 R    88.6 00:00:05 sh -c while :; do :; done
11231  10   9 RN    9.5 00:00:00 sh -c while :; do :; done
11231 (process ID) old priority 10, new priority 0
```

거의 9 대 1로 나뉘었다. 리눅스 스케줄러는 nice 값마다 가중치를 두는데 0은 1024, 10은 110이라 1024:110이 대략 90:10이다. nice 한 단계가 약 10% 차이라고 기억하면 된다. STAT의 `N`이 낮은 우선순위 표시다. `top`의 PR 칸(20, 30)과 `ps`의 PRI 칸(19, 9)은 같은 걸 다른 눈금으로 보여 주니 헷갈리지 않는다.

nice는 CPU만 나눈다. 백업이 디스크를 다 먹고 있다면 `ionice -c3`(유휴 시간에만 I/O)를 함께 쓴다. 그리고 CPU가 남는 서버에서는 nice가 아무것도 바꾸지 않는다. 경쟁할 때만 효과가 있다. 컨테이너처럼 한도를 정해서 나눠야 한다면 cgroup의 CPU 제한이 맞는 도구다.

## 현장에서 프로세스를 따라가는 순서

증상별로 처음 치는 명령을 정리하면 이렇다.

- load average는 높은데 CPU는 논다: `ps -eo pid,stat,wchan:32,cmd | awk '$2 ~ /^D/'`로 D 상태와 기다리는 함수를 본다. 그다음 `iostat -x`, NFS라면 `mount | grep nfs`와 서버 상태다.
- `fork: Resource temporarily unavailable`: `top`의 zombie 수와 `ps -eLf | wc -l`(스레드까지 센 수)을 보고 `ulimit -u`, cgroup `pids.max`와 비교한다. 좀비라면 PPID를 따라 부모를 찾는다.
- 프로세스가 `kill`로 안 죽는다: STAT이 `Z`면 부모 문제, `D`면 I/O 대기, `T`면 멈춰 있어서 SIGCONT가 필요하다. 그것도 아니면 `SigCgt`/`SigIgn`으로 SIGTERM을 잡거나 무시하는지 본다.
- 재시작할 때마다 30초씩 걸린다: SIGTERM을 무시하고 SIGKILL을 기다리는 중이다. PID 1 문제인지 [Pod의 일생](/posts/k8s-pod-lifecycle)을 보고 확인한다.
- SSH를 끊었더니 작업이 죽었다: SIGHUP이다. 긴 작업은 `nohup`, `setsid`, tmux로 띄우거나 아예 서비스로 등록한다. 서비스로 돌리는 방법은 [systemd와 systemctl](/posts/linux-systemd-systemctl)에서 본다.

## 번호와 나무, 그리고 거두는 일

프로세스는 부모가 fork로 만든 나무이고, 상태 글자 하나(R, S, D, Z, T)가 지금 무엇을 기다리는지 알려 준다. 시그널은 번호 하나를 전하는 것이며 SIGTERM은 받아서 정리할 수 있고 SIGKILL은 못 한다. 끝난 자식은 부모가 거둬야 사라지고, 부모가 없으면 PID 1이 맡는다. 그래서 컨테이너의 PID 1은 신호를 전달하고 좀비를 거둘 줄 알아야 한다.

## 면접에서 나올 만한 질문

### 프로세스 상태 D와 S의 차이는 무엇인가요?

둘 다 무언가를 기다리며 잠든 상태지만 S는 시그널로 깨울 수 있고 D는 커널 안에서 I/O 완료를 기다리느라 깨울 수 없다. 그래서 D 상태 프로세스는 SIGKILL도 바로 듣지 않고, 시그널은 대기 상태가 풀릴 때까지 쌓여 있다. 리눅스의 load average는 D도 세기 때문에 CPU가 놀아도 부하가 높게 나오고, 이때는 디스크나 NFS를 본다.

### SIGTERM과 SIGKILL의 차이는요? 왜 바로 SIGKILL을 쓰면 안 되나요?

SIGTERM은 프로그램이 핸들러로 받아서 처리 중인 요청을 끝내고 자원을 정리한 뒤 끝낼 수 있는 요청이고, SIGKILL은 커널이 프로그램을 거치지 않고 바로 없앤다. 바로 SIGKILL을 쓰면 버퍼의 로그, 쓰다 만 파일, 잠금 파일, DB 트랜잭션이 정리되지 않는다. 그래서 systemd와 쿠버네티스 모두 SIGTERM을 먼저 보내고 유예 시간 뒤에만 SIGKILL을 보낸다. 시그널로 죽은 프로세스의 종료 코드는 128+번호라 143, 137로 보인다.

### 좀비 프로세스는 무엇이고 어떻게 없애나요?

자식이 끝났는데 부모가 wait로 종료 상태를 가져가지 않아 프로세스 표에 항목만 남은 상태다. 이미 죽었기 때문에 kill -9로는 없어지지 않고, 부모가 wait를 하게 고치거나 부모를 끝내야 한다. 부모가 끝나면 PID 1이 입양해서 거둔다. 몇 개는 해가 없지만 쌓이면 PID가 바닥나 fork가 실패한다.

### 고아 프로세스는 좀비와 어떻게 다른가요?

고아는 부모가 먼저 끝났는데 아직 살아 있는 프로세스이고, 좀비는 이미 끝났는데 거둬지지 않은 프로세스다. 고아는 PID 1이나 subreaper로 지정된 프로세스에게 입양되어 PPID가 바뀐다. 부모만 죽여서 자식이 남는 걸 막으려면 프로세스 그룹(`kill -- -PGID`)이나 cgroup 단위로 멈추는데, systemd가 서비스를 cgroup으로 묶는 이유가 이것이다.

### 컨테이너에서 tini 같은 init을 쓰는 이유는요?

컨테이너 안 PID 1은 고아를 입양하고 거두는 일과 시그널을 받는 일을 맡는데, 보통의 앱은 둘 다 할 생각이 없다. 앱이 PID 1이면 자식이 남긴 고아가 끝날 때마다 좀비가 쌓이고, 핸들러 없는 SIGTERM은 무시되어 종료가 유예 시간 끝까지 늦어진다. tini는 SIGCHLD로 좀비를 거두고 받은 시그널을 앱에 전달한다. Docker는 `--init`, 쿠버네티스는 이미지의 ENTRYPOINT로 넣는다.

### nginx -s reload는 어떻게 연결을 끊지 않고 설정을 바꾸나요?

마스터에 SIGHUP을 보내면 마스터가 새 설정을 검사하고, 새 설정으로 워커를 띄운 뒤 옛 워커에 우아한 종료(SIGQUIT)를 보낸다. 리스닝 소켓은 마스터가 쥐고 있어 새 워커가 바로 이어받고, 옛 워커는 처리 중인 요청을 끝내고 나간다. 설정에 오류가 있으면 옛 설정으로 계속 돌기 때문에 reload 전에 `nginx -t`로 검사한다.

### pkill -f를 조심해야 하는 이유는요?

pkill -f는 명령줄 전체에서 패턴을 찾기 때문에 의도하지 않은 프로세스, 특히 그 명령을 실행한 셸 스크립트나 ssh 세션까지 맞을 수 있다. 실제로 `stop_queue_worker.sh` 안의 `pkill -f queue_worker`가 스크립트 자신을 죽였다. pgrep -af로 먼저 확인하고, 패턴을 좁히거나 PID 파일, systemctl로 멈춘다.

### nice 값은 어떻게 동작하나요?

nice는 -20부터 19까지이고 높을수록 CPU를 양보한다. 스케줄러가 nice마다 가중치를 둬서 CPU를 다툴 때 그 비율로 나누는데, nice 0과 10은 1024 대 110이라 실제로 약 9 대 1로 나뉘었다. CPU가 남을 때는 효과가 없고, 디스크 경쟁은 ionice, 확실한 상한은 cgroup으로 정한다.
