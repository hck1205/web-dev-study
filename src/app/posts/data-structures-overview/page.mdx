느린 코드 중에는 알고리즘이 복잡해서가 아니라, 데이터를 담은 그릇이 던지는 질문과 맞지 않아서 느린 것이 있다. 사용자 목록에서 id로 사람을 찾는데 배열을 `find`로 훑는다. 가장 급한 작업을 꺼내려고 넣을 때마다 배열을 다시 정렬한다. 먼저 온 요청부터 처리하려고 `shift`를 부른다. 셋 다 동작은 맞다. Node 22에서 그대로 재 봤다.

```js
// 1) 사용자 10만 명 중 id로 1만 번 찾기
users.find((u) => u.id === id);        // 배열을 앞에서부터 훑는다
byId.get(id);                          // Map: 키를 해시해 바로 칸으로 간다

// 2) 작업을 5만 번 넣으면서, 일정 개수를 넘으면 가장 작은 것을 꺼낸다
a.push(x); a.sort((p, q) => p - q); a.shift();   // 넣을 때마다 정렬
/* 배열 전체에서 최솟값을 훑어 찾기 */            // scan
/* 이진 힙: 위로 올리고(sift up), 꺼낸 뒤 아래로 내린다(sift down) */

// 3) 큐에 10만 개 넣고 먼저 넣은 것부터 다 빼기
q.shift();                             // 앞을 빼고 나머지를 당긴다
q[head++];                             // 머리 위치만 옮긴다
```

```text

pop min (keep 100) sort-each 110.4ms  scan 5.4ms  heap 22.3ms  same=true
pop min (keep 20000) scan 567.5ms  heap 25.4ms  same=true
FIFO 100k       shift 13036.3ms  head index 3.2ms
```

id로 찾기는 700배, 큐는 4,000배 차이가 났다. 두 번째와 세 번째 줄은 조금 더 재미있다. 들고 있는 작업이 100개뿐일 때는 매번 훑는 단순한 방법(5.4ms)이 힙(22.3ms)보다 빨랐다. 2만 개로 늘리자 훑기는 567ms, 힙은 25ms로 뒤집혔다. 자료구조를 고르는 일은 "어떤 질문을 얼마나 자주, 얼마나 큰 데이터에 던지나"를 먼저 정하는 일이다.

이 글은 코딩 면접에 단골로 나오는 자료구조 13개를 한자리에 모은 지도다. 각 구조의 자세한 설명과 측정은 개별 글에 있고, 여기서는 고르는 법을 다룬다. 필요한 연산에서 출발해 구조를 고르는 법, 연산별 비용을 한 표로 보는 법, 문제 문장에서 구조를 알아채는 법이다. 복잡도 표기 자체가 낯설면 [Big O 표기법](/posts/big-o-notation)을 먼저 읽는다.

## 재료는 두 가지뿐이다

이 구분이 실제로 의미가 있는 이유는 CPU 캐시다. 배열은 칸이 붙어 있어서 하나를 읽으면 옆 칸들이 같이 캐시에 올라온다. 노드 구조는 다음 노드가 메모리 어디에 있을지 몰라서 따라갈 때마다 캐시를 놓칠 수 있다. 그래서 복잡도가 같으면 배열 기반이 대개 빠르고, 메모리도 적게 쓴다. [트라이 글](/posts/ds-trie)에서 단어 10만 개가 해시 집합으로는 2.6MB, 노드로 만든 트라이로는 126MB였던 것도 같은 이유다.

힙과 유니온 파인드가 배열 위에 있는 게 처음엔 의외다. 둘 다 개념은 나무인데, 나무 모양을 번호 규칙(`i`의 자식은 `2i+1`, `2i+2`)이나 부모 번호 배열로 표현해서 포인터 없이 만든다. 면접에서 "힙을 왜 배열로 구현하나요"를 물으면 이 이야기를 하면 된다.

## 필요한 연산에서 출발하기

구조 이름부터 떠올리지 말고, 이 데이터에 어떤 질문을 가장 자주 던지는지부터 적는다. 질문이 정해지면 구조는 거의 따라 나온다.

키로 바로 찾아야 하면 [해시맵](/posts/ds-hash-map)이다. 있나 없나, 몇 번 나왔나, 전에 본 적이 있나가 모두 여기다. 대신 해시맵은 순서를 모른다. "키가 100에서 200 사이인 것"이나 "다음으로 큰 키"는 답하지 못한다.

순서를 유지하면서 찾아야 하면 정렬된 배열이나 균형 [이진 탐색 트리](/posts/ds-binary-tree-bst)다. 데이터가 거의 안 바뀌면 정렬 배열에 이진 탐색이 가장 싸고, 넣고 빼기가 잦으면 트리다. 자바스크립트에는 균형 트리가 내장되어 있지 않아서, 코딩 테스트에서는 정렬 배열이나 힙으로 돌아가는 경우가 많다.

매번 가장 작은 것(또는 큰 것)만 꺼내면 [힙](/posts/ds-heap)이다. 전체를 정렬할 필요 없이 맨 위 하나만 보장한다. 작업 스케줄러, 상위 k개, 다익스트라가 모두 이것을 쓴다. 위 측정처럼 개수가 아주 적으면 그냥 훑는 게 빠를 수도 있다.

들어온 순서가 중요하면 끝을 정한 구조들이다. 가장 최근 것부터 처리하면 스택, 먼저 온 것부터 처리하면 큐, 양쪽 끝을 다 쓰면 덱이다([스택·큐·덱](/posts/ds-stack-queue-deque)). 괄호 짝 맞추기, 되돌리기, 방금 본 것보다 큰 첫 값 찾기는 스택이고, BFS와 작업 대기열은 큐, 창을 밀면서 최댓값 유지하기는 덱이다.

인덱스로 바로 접근하거나 구간을 다루면 [배열](/posts/ds-array-matrix)이다. 두 포인터, 슬라이딩 윈도, 누적 합이 모두 배열이 칸 번호로 O(1) 접근을 주는 데서 나온다. 격자, 이미지, 게임판처럼 2차원이면 행렬인데, 메모리에서는 결국 한 줄로 놓인다.

노드를 손에 쥔 채로 중간에 넣고 빼야 하면 [연결 리스트](/posts/ds-linked-list)다. 위치를 찾는 건 느리지만, 위치를 이미 알면 앞뒤 포인터만 바꾸면 된다. 그래서 단독보다 해시맵과 짝을 이룰 때 빛난다. LRU 캐시가 대표다.

접두사로 묻는 질문이면 [트라이](/posts/ds-trie)다. 관계와 경로, 최소 단계를 묻는다면 [그래프와 BFS·DFS](/posts/ds-graph-bfs-dfs)이고, 연결이 계속 추가되면서 같은 그룹인지만 물으면 [유니온 파인드](/posts/ds-union-find)다.

## 연산별 비용 한 장

13개를 같은 표에 놓으면 구조마다 무엇을 싸게 주고 무엇을 대가로 받는지가 보인다. n은 원소 수, L은 문자열 길이, V와 E는 정점과 간선 수다.

| 구조 | 싼 연산 | 비싼 연산·한계 |
|---|---|---|
| 배열 | 인덱스 접근 O(1), 끝에 넣기 분할 상환 O(1) | 값으로 찾기 O(n), 앞·중간 넣기/빼기 O(n) |
| 행렬 | 칸 접근 O(1) | 전체 훑기 O(R·C), 열 방향으로 훑으면 캐시에 불리 |
| 연결 리스트 | 노드를 알 때 넣기/빼기 O(1) | k번째 접근·찾기 O(n), 노드마다 메모리 오버헤드 |
| 스택 | 위에 넣기/빼기 O(1) | 중간 접근은 목적 밖 |
| 큐 | 뒤에 넣기, 앞에서 빼기 O(1) | 배열 `shift`로 만들면 빼기가 O(n) |
| 덱 | 양끝 넣기/빼기 O(1) | 중간 접근은 목적 밖 |
| 해시맵 | 키로 찾기/넣기/빼기 평균 O(1) | 순서·범위 질문 불가, 최악 O(n) |
| 이진 트리 | 순회 O(n) | 규칙이 없으면 찾기 O(n) |
| BST | 찾기/넣기/빼기 균형일 때 O(log n), 정렬 순회 | 치우치면 O(n) |
| 힙 | 최솟값 보기 O(1), 넣기/빼기 O(log n), 만들기 O(n) | 임의 값 찾기 O(n) |
| 트라이 | 넣기/찾기/접두사 O(L) | 노드가 많아 메모리가 크다 |
| 그래프 | 이웃 훑기 O(차수), 전체 탐색 O(V+E) | 인접 리스트에서 간선 확인 O(차수) |
| 유니온 파인드 | 합치기/대표 찾기 분할 상환 O(α(n)) | 쪼개기 불가, 경로 모름 |

표에서 두 가지를 읽을 수 있다. 하나는 공짜가 없다는 것이다. 해시맵은 찾기를 O(1)로 주는 대신 순서를 버렸고, 힙은 최솟값 하나만 보장하는 대신 나머지 정렬을 포기했다. 다른 하나는 같은 O(1)이어도 무게가 다르다는 것이다. 해시맵의 O(1)은 해시 계산과 충돌 처리를 포함한 평균이고, 배열 인덱스의 O(1)은 주소 계산 한 번이다. 측정이 복잡도와 다르게 나오면 이 상수를 의심한다.

## 대표 문제를 구조에 짝지어 두기

문제 이름과 구조를 짝지어 두면 처음 보는 문제도 "어디서 본 모양인가"로 접근할 수 있다. 아래는 시리즈 글에서 다룬 문제와, 같은 구조로 풀리는 대표 문제를 섞어 적었다. 외울 것은 문제 번호가 아니라 괄호 안의 이유다.

배열에서는 Two Sum II(정렬돼 있으면 양끝에서 좁혀 오는 두 포인터), Longest Substring Without Repeating Characters(조건이 깨질 때만 왼쪽을 당기는 창), Range Sum Query(누적 합의 뺄셈 한 번), Rotate Image(행렬을 전치한 뒤 행마다 뒤집기)가 대표다. 모두 칸 번호로 바로 접근할 수 있다는 성질 하나에서 나온다.

연결 리스트는 Reverse Linked List(다음 노드를 먼저 잡아 두고 화살표 돌리기), Linked List Cycle(두 배로 달리는 포인터가 언젠가 만난다), Merge Two Sorted Lists(더미 노드로 경계 처리 없애기)다. 포인터를 바꾸는 순서를 틀리면 리스트가 끊긴다는 게 공통 함정이다.

스택은 Valid Parentheses(가장 최근에 연 괄호와 짝 맞추기), Daily Temperatures(아직 답을 못 찾은 날을 쌓아 두는 단조 스택)이고, 덱은 Sliding Window Maximum(창 안에서 앞으로 최댓값이 될 가능성이 있는 것만 남기기)이다. 큐는 문제 이름보다 BFS 안에서 더 자주 만난다.

해시맵은 Two Sum(필요한 짝을 이미 봤는지 찾기), Group Anagrams(정렬한 글자를 키로 묶기), Subarray Sum Equals K(앞에서 본 누적 합의 횟수)다. "전에 본 적이 있나"를 O(1)로 바꾸면 이중 반복문이 단일 반복문이 된다.

트리는 Binary Tree Level Order Traversal(큐로 한 층씩), Validate BST(위에서 내려오는 범위를 들고 다니기), Lowest Common Ancestor(두 노드가 갈라지는 지점)다. 힙은 Kth Largest Element(크기 k짜리 최소 힙), Merge k Sorted Lists(리스트마다 머리 하나씩만 힙에), Find Median from Data Stream(작은 쪽 최대 힙과 큰 쪽 최소 힙)이다.

트라이는 Implement Trie와 Word Search II(판을 한 번 훑으며 접두사로 가지치기), 그래프는 Number of Islands(격자의 연결 요소), Course Schedule(사이클이 없으면 위상 정렬이 끝까지 간다), 유니온 파인드는 Redundant Connection(고리를 처음 닫는 간선)과 Number of Provinces(남은 그룹 수)다. Number of Islands처럼 같은 문제가 BFS와 유니온 파인드 양쪽으로 풀리는 경우가 꼬리 질문으로 자주 이어진다. 격자가 고정이면 BFS가 단순하고, 땅이 하나씩 추가되면 유니온 파인드가 낫다.

## 메모리를 내주고 시간을 사는 거래

여러 구조를 나란히 놓으면 대부분이 같은 거래를 한다는 게 보인다. 메모리를 더 써서 나중의 질문을 싸게 만드는 거래다.

해시맵은 원소마다 칸과 해시 값을 더 들고 있는 대신 찾기를 O(n)에서 O(1)로 줄인다. 누적 합 배열은 원래 배열만큼의 칸을 더 써서 구간 합을 O(1)로 만든다. 트라이는 노드 수십만 개를 써서 접두사 질문을 접두사 길이만큼으로 줄인다. 반대로 힙은 메모리를 거의 더 쓰지 않는 대신 맨 위 하나만 보장하는 쪽으로 질문을 좁혔고, 유니온 파인드는 경로 정보를 버리고 "같은 그룹인가" 하나만 남겨 배열 하나로 끝낸다.

그래서 면접에서 "더 빠르게 할 수 있나요?"라는 꼬리 질문이 오면 두 방향으로 생각한다. 메모리를 더 써서 미리 계산해 둘 수 있는지, 아니면 질문을 좁혀서 덜 기억해도 되는지. "메모리가 부족하면요?"라는 반대 질문에는 정렬 배열과 이진 탐색, 비트 배열, [블룸 필터](/posts/bloom-filter)처럼 조금 느리거나 조금 틀리는 대신 훨씬 작은 선택지를 꺼내면 된다.

## 고른 구조가 틀렸다는 신호

운영에서 자료구조를 잘못 골랐을 때의 증상은 비슷하다. 개발 데이터에서는 멀쩡하다가 데이터가 늘어난 날 갑자기 느려진다. 늘어난 비율보다 느려진 비율이 훨씬 크면, 안쪽 어딘가에 O(n) 연산이 반복문 안에 들어가 있다는 뜻이다. 처음 측정의 `array.find`와 `shift`가 정확히 그 모양이다. 이런 반복 안의 `includes`, `indexOf`, `find`, `shift`, `splice`, 매번 하는 `sort`를 먼저 의심한다. 프로파일러에서 그 줄이 시간의 대부분을 차지하면 거의 확정이다.

반대 방향의 실수도 있다. 데이터가 작은데 무거운 구조를 쓰는 것이다. 작업 100개를 들고 있는 대기열에 힙을 붙이면 위 측정처럼 단순 훑기보다 느릴 수 있고, 코드는 복잡해진다. 단어 몇 백 개 사전에 트라이를 만들면 메모리만 쓴다. 크기가 작고 앞으로도 작을 거라면 배열과 반복문이 정답인 경우가 많다. 구조를 바꾸기 전에 n이 실제로 얼마인지, 앞으로 얼마가 될지 먼저 적어 본다.

자바스크립트 특유의 함정도 있다. 객체를 해시맵처럼 쓰면 키가 문자열로 바뀌고 `__proto__` 같은 키가 문제를 일으킨다. `Map`과 `Set`을 쓰는 게 안전하다. 배열은 V8이 원소 종류에 따라 내부 표현을 바꿔서, 중간에 구멍을 내거나 타입을 섞으면 느려질 수 있다. 큐는 `shift`로 만들지 않는다. 힙, 균형 트리, 덱은 내장되어 있지 않으니 직접 짜거나 검증된 라이브러리를 쓴다.

## 이 지도로 공부하는 순서

처음이라면 배열, 해시맵, 스택·큐·덱 순서로 읽는다. 이 셋과 두 포인터, 슬라이딩 윈도는 뒤의 구조를 다룰 때도 계속 부품으로 다시 나온다. 그다음 연결 리스트와 이진 트리로 포인터와 재귀에 익숙해지고, 힙으로 "전체 정렬 없이 맨 위 하나"라는 생각을 익힌다. 마지막으로 그래프, 트라이, 유니온 파인드로 넘어간다. 그래프는 트리와 격자를 일반화한 것이라 앞의 내용이 쌓여 있어야 수월하다.

각 글은 같은 순서로 쓰여 있다. 메모리에 어떻게 놓이는지, 연산 비용이 왜 그렇게 나오는지, Node 22에서 잰 숫자, 대표 면접 문제 두세 개, 흔한 실수, 다른 구조를 골라야 할 때. 한 구조를 읽고 나면 이 글의 비용표와 신호 목록으로 돌아와 자리를 확인하면 된다.

## 면접에서 나올 만한 질문

### 자료구조를 고를 때 무엇부터 보나요?

이 데이터에 가장 자주 던지는 질문과 데이터 크기부터 본다. 키로 찾기면 해시맵, 매번 최솟값이면 힙, 들어온 순서면 큐처럼 연산이 구조를 정한다. 같은 연산이라도 n이 작으면 단순한 배열 훑기가 더 빠를 수 있어서, 크기가 앞으로 얼마가 될지도 함께 정한다.

### 해시맵이 O(1)인데 왜 트리나 정렬 배열을 쓰나요?

해시맵은 키를 흩어 놓아서 순서를 모른다. 범위 질의, 다음으로 큰 키, 정렬된 순회가 필요하면 BST나 정렬 배열을 쓴다. 또 해시맵의 O(1)은 평균이고, 충돌이 몰리면 최악 O(n)이 된다.

### 힙과 정렬 배열의 차이는요?

정렬 배열은 전체 순서를 유지해서 끼워 넣기가 O(n)이고, 힙은 맨 위 하나만 보장해서 넣기와 빼기가 O(log n)이다. 값이 계속 들어오면서 최솟값만 꺼내면 힙이 맞고, 한 번 만들고 범위로 찾으면 정렬 배열이 맞다.

### 배열 기반 구조가 노드 기반보다 빠른 경우가 많은 이유는요?

배열은 칸이 붙어 있어 하나를 읽을 때 옆 칸이 같이 캐시에 올라오고, 노드는 다음 노드를 따라갈 때마다 캐시를 놓칠 수 있다. 노드마다 객체 헤더와 포인터가 붙어 메모리도 더 쓴다. 그래서 힙, 유니온 파인드처럼 나무 모양도 배열로 구현하는 경우가 많다.

### 스택과 큐는 각각 어떤 문제에 쓰나요?

가장 최근에 연 것을 먼저 닫는 구조면 스택이다. 괄호 짝, 되돌리기, 단조 스택으로 다음 큰 값 찾기, 재귀를 반복문으로 바꾸기가 그렇다. 먼저 온 것을 먼저 처리하면 큐로, BFS와 작업 대기열이 대표다. 자바스크립트에서 큐를 배열 shift로 만들면 빼기가 O(n)이라 10만 개에서 13초가 걸렸다.

### LRU 캐시는 어떤 구조로 만드나요?

해시맵과 이중 연결 리스트를 함께 쓴다. 해시맵이 키로 리스트 노드를 O(1)에 찾고, 리스트는 노드를 O(1)에 떼어 맨 앞으로 옮기거나 맨 뒤를 뺀다. 둘 중 하나만으로는 찾기와 순서 유지를 동시에 O(1)로 할 수 없다.

### 그래프 문제에서 BFS, DFS, 유니온 파인드는 어떻게 고르나요?

최소 단계나 최단 거리는 BFS, 사이클과 위상 정렬과 모든 경로는 DFS다. 간선이 계속 추가되면서 같은 그룹인지만 자주 물으면 유니온 파인드가 질문당 거의 상수라 가장 싸다. 경로가 필요하거나 연결이 끊기는 일이 잦으면 유니온 파인드는 맞지 않는다.
