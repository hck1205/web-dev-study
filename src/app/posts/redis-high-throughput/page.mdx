"Redis는 초당 100만 건도 거뜬하다"는 말을 듣고 우리 서비스 Redis를 보니 초당 2만 건 근처에서 응답이 늘어지기 시작한다. CPU는 30%밖에 안 쓴다. 서버가 놀고 있는데 왜 느린가. 반대로 어떤 날은 CPU가 100%인데 처리량이 더 안 오른다. 둘은 원인이 다르고, 손댈 곳도 다르다.

이 글은 Redis 한 대가 시간을 어디에 쓰는지부터 쪼갠다. 네트워크 왕복, 시스템 콜, 명령 실행 가운데 무엇이 병목인지에 따라 파이프라이닝, 연결 수, I/O 스레드, 클라이언트 측 캐시, 샤딩 중 맞는 손잡이가 정해진다. Redis가 왜 단일 스레드로 빠른지는 [Redis 기본 글](/posts/redis-basics)에, Redis와 Valkey의 차이는 [Valkey와 Redis 글](/posts/valkey-vs-redis)에 있다.

숫자는 모두 이 글을 쓴 기계에서 직접 잰 것이다. Intel Xeon 2.1GHz 4 vCPU의 Ubuntu 24.04 가상 서버이고, 다른 작업과 함께 쓰는 기계라 실행마다 값이 흔들린다. 벤치마크 클라이언트도 같은 기계에서 돌렸다. 그러니 절대값보다 설정을 바꿨을 때 몇 배 달라지는지를 본다. 서버는 Redis 7.0.15(우분투 패키지)와 소스로 빌드한 Valkey 9.0.6이다.

```bash
# 영속성을 끈 실험용 서버 (19601번 포트)
redis-server --port 19601 --bind 127.0.0.1 --save "" --appendonly no --daemonize yes
```

이 길에서 시간이 드는 곳은 세 군데다. 패킷이 오가는 네트워크 왕복(RTT), 커널을 드나드는 시스템 콜, 그리고 실제 명령 실행이다. 같은 기계 안(루프백)이라 네트워크가 거의 없는 상태에서 연결 하나로 재면 이렇다.

```bash
# 연결 1개(-c 1)로 GET 10만 번. -q는 요약만 보여 준다
redis-benchmark -p 19601 -t get -n 100000 -c 1 -q
```

```text
GET: 50709.94 requests per second, p50=0.015 msec
```

p50이 0.015ms(15µs)다. 연결 하나가 왕복을 한 번씩 기다리면 초당 5만 번 남짓이 한계다. 같은 데이터센터 안 다른 서버면 RTT가 보통 수백 µs, 다른 가용 영역이면 1ms 가까이 되니(환경마다 다르니 `ping`이나 아래의 `--latency`로 직접 잰다), 연결 하나로 할 수 있는 일은 그만큼 더 줄어든다.

## 시간은 커널 안에서 더 많이 쓴다

명령 실행이 1µs라면 Redis 한 대가 초당 100만 건을 못 할 이유가 없다. 실제로 못 하는 이유는 시스템 콜이다. Redis 프로세스에 `strace -c`를 붙여 GET 10만 번 동안 시스템 콜을 세어 봤다.

```bash
# Redis 프로세스의 시스템 콜을 종류별로 센다 (Ctrl+C로 멈추면 표가 나온다)
sudo strace -c -f -p $(pidof redis-server)
# 다른 터미널에서 연결 50개, 파이프라인 없이 GET 10만 번
redis-benchmark -p 19601 -t get -n 100000 -c 50 -P 1 -q
```

```text
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 67.48    0.454864           4    100001           write
 29.32    0.197668           1    100101           read
  2.05    0.013787           6      2234           epoll_wait
  0.39    0.002626          10       255           setsockopt
  0.21    0.001407          14       100           close
```

`calls` 열을 본다. GET 10만 번에 `write`가 100,001번, `read`가 100,101번이다. 명령마다 한 번씩 커널을 드나들었다. 같은 일을 명령 16개씩 묶어(`-P 16`) 보내면 이렇게 바뀐다.

```text
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 56.36    0.052228           8      6251           write
 29.93    0.027733           4      6317           read
  6.15    0.005700          22       255           setsockopt
  1.98    0.001837           9       192           epoll_wait
```

`write`가 6,251번, 10만을 16으로 나눈 6,250과 거의 같다. 한 번의 `read`로 명령 16개를 읽고, 응답 16개를 한 번의 `write`로 내보낸 것이다. (strace를 붙이면 시스템 콜마다 멈춰서 처리량이 크게 떨어진다. 운영 서버에는 붙이지 않는다.)

CPU 시간으로 보면 더 분명하다. `INFO cpu`의 `used_cpu_sys`(커널 안에서 쓴 시간)와 `used_cpu_user`(Redis 코드가 쓴 시간)를 GET 100만 번 전후로 읽어 차이를 냈다.

```bash
# 벤치마크 전후로 used_cpu_sys와 used_cpu_user를 읽어 차이를 낸다
cpu(){ redis-cli -p 19601 INFO cpu | grep -E "^used_cpu_(sys|user):" | cut -d: -f2 | tr -d '\r' | paste -sd' '; }
for P in 1 16; do
  a=$(cpu)
  redis-benchmark -p 19601 -t get -n 1000000 -c 50 -P $P -q
  b=$(cpu)
  echo "$a | $b" | awk '{printf "P'$P' sys=%.2fs user=%.2fs\n", $4-$1, $5-$2}'
done
```

```text
GET: 88550.43 requests per second, p50=0.287 msec
P1 sys=6.32s user=1.77s
GET: 1101321.62 requests per second, p50=0.527 msec
P16 sys=0.43s user=0.41s
```

`GET:` 줄이 벤치마크 결과, `P1`·`P16` 줄이 그동안 늘어난 CPU 시간이다. 파이프라인 없이는 100만 건에 8.09초, 명령 하나에 약 8µs를 썼고 그중 78%가 커널 안이었다. 16개씩 묶으니 0.84초, 명령 하나에 약 0.8µs로 열 배 가까이 줄었다. Redis가 바쁜 이유의 대부분은 명령이 아니라 소켓을 드나드는 비용이다. 처리량을 올리는 방법은 거의 다 이 비용을 줄이거나 여러 코어에 나누는 쪽이다.

GET: 80755.88 requests per second, p50=0.351 msec
SET: 619962.81 requests per second, p50=1.007 msec
GET: 813669.69 requests per second, p50=0.759 msec

두 줄씩 깊이 1, 16, 64, 256이다. GET은 8만에서 81만, 154만, 172만으로 올랐다. 깊이 16에서 이미 열 배이고 그 뒤로는 오르는 폭이 줄어든다. 시스템 콜을 줄일 만큼 줄이면 남는 건 실행 비용과 버퍼 복사라서다.

같이 봐야 할 건 p50이다. 0.35ms에서 0.76, 1.8, 6.1ms로 늘었다. 이 p50은 명령 묶음 하나가 왕복하는 시간이다. 묶음이 클수록 첫 명령의 응답도 마지막 명령이 끝날 때까지 기다린다. 처리량을 위해 깊이를 무한정 키우면 개별 요청의 지연이 늘고, 큰 묶음 하나가 실행되는 동안 다른 연결의 명령도 뒤에서 기다린다. 실무에서는 수십~수백 개 단위로 끊는다. 대량 적재처럼 지연이 상관없는 작업은 더 크게 묶어도 된다.

## 1ms 떨어진 서버에서 반복문을 돌리면

루프백에서는 RTT가 15µs라 파이프라인의 효과가 덜 극적이다. 실제로는 앱 서버와 Redis가 다른 기계다. 그 상황을 흉내 내려고 양방향으로 0.5ms씩 늦춰 전달하는 작은 TCP 프록시(Node 22로 짠 것)를 19610번에 두고 같은 실험을 했다.

```bash
# 프록시를 거치면 왕복이 약 1ms 늘어난다
redis-cli -p 19610 --latency
```

```text
1 24 2.82 76
```

터미널이 아닌 곳으로 출력하면 이렇게 숫자만 나온다. 순서대로 최소, 최대, 평균(ms), 표본 수다. 평균 왕복이 2.8ms이고 프록시 자체가 흔들려서 최대 24ms까지 튀었다. 이제 연결 하나로 깊이만 바꿔 본다.

```bash
for P in 1 16 100; do redis-benchmark -p 19610 -t get -n 20000 -c 1 -P $P -q; done
```

```text
GET: 717.51 requests per second, p50=1.111 msec
GET: 13175.23 requests per second, p50=1.079 msec
GET: 82304.52 requests per second, p50=1.111 msec
```

연결 하나, 파이프라인 없이 초당 717건이다. 깊이 16이면 18배, 100이면 115배가 된다. p50은 거의 그대로다. 왕복 한 번에 실어 보내는 양만 늘었기 때문이다. 처음에 말한 "CPU는 30%인데 초당 2만 건에서 막힌다"가 이 경우다. Redis는 놀고 있고 앱이 왕복을 기다리고 있다.

이게 앱 코드에서 나타나는 모양은 대개 `for` 문 안의 `await`다. 상품 1000개의 가격을 읽는 세 가지 방법을 같은 프록시 뒤에서 재 봤다. RESP를 직접 쓰는 30줄짜리 Node 스크립트로, 클라이언트 라이브러리의 오버헤드는 빠져 있다.

```js
// 1) 하나씩 기다린다
for (const k of keys) await send(cmd("GET", k), one);
// 2) 다 보내 놓고 응답을 한꺼번에 기다린다 (파이프라인)
await Promise.all(keys.map((k) => send(cmd("GET", k), one)));
// 3) 명령 하나로 1000개를 읽는다
await send(cmd("MGET", ...keys), arr);
```

```text
await GET x1000 : 1247.8 ms
파이프라인 GET x1000: 10.1 ms
MGET 1000개 한 번  : 1.8 ms
```

1.2초와 10ms, 2ms다. 세 번 더 돌렸을 때 첫 줄은 1.2~1.5초, 둘째는 7~10ms, 셋째는 약 2ms로 순서가 바뀌지 않았다. 첫 방법은 왕복을 1000번 했고, 나머지는 사실상 한 번이다. MGET이 파이프라인보다 빠른 건 명령 해석과 응답 헤더가 1000개에서 1개로 줄어서다. 대신 MGET은 Cluster에서 키가 모두 같은 슬롯에 있어야 하고(해시 태그, [Cluster 글](/posts/redis-cluster) 참고), 파이프라인은 노드별로 나눠 보내면 된다. 하나 더, 파이프라인은 원자적이지 않다. 사이사이에 다른 클라이언트의 명령이 끼어든다.

ioredis나 Lettuce 같은 클라이언트는 한 연결에 여러 요청을 겹쳐 보내는 방식(ioredis의 `enableAutoPipelining`, Lettuce의 비동기 API)을 제공한다. 코드에서 `await`를 반복하지 않고 `Promise.all`로 여러 요청을 동시에 띄우면 라이브러리가 알아서 묶는다. 처리량과 지연이 왕복, 묶음 크기, 연결 수에 따라 어떻게 바뀌는지는 아래에서 단순한 모델로 직접 계산해 볼 수 있다.

  // pipeline: 한 번에 보내는 명령 수, conns: 연결 수
  // 연결 하나가 묶음 하나를 끝내는 시간 = 왕복 + 묶음 실행 시간
  // 서버는 한 스레드라 초당 1e6 / cmdUs 건을 넘을 수 없다
  // 초당 처리량을 반올림해서 돌려준다
  return 0;
}`}
  solution={`function estimateOps(rttMs, cmdUs, pipeline, conns) {
  const batchMs = rttMs + (pipeline * cmdUs) / 1000;
  const perConn = (pipeline * 1000) / batchMs;
  const serverMax = 1e6 / cmdUs;
  return Math.round(Math.min(perConn * conns, serverMax));
}`}
  tests={[
    { label: "1ms, 연결 1, 하나씩", args: [1, 10, 1, 1], expected: 990 },
    { label: "1ms, 연결 1, 16개씩", args: [1, 10, 16, 1], expected: 13793 },
    { label: "1ms, 연결 50, 하나씩", args: [1, 10, 1, 50], expected: 49505 },
    { label: "1ms, 연결 50, 100개씩", args: [1, 10, 100, 50], expected: 100000 },
    { label: "루프백 20µs, 연결 1", args: [0.02, 10, 1, 1], expected: 33333 },
    { label: "0.5ms, 연결 4, 64개씩", args: [0.5, 5, 64, 4], expected: 200000 },
  ]}
/>

모델의 명령당 10µs는 위에서 잰 파이프라인 없는 경우(약 8µs)에 가깝게 잡은 값이다. 실제로는 파이프라인을 깊게 하면 명령당 비용 자체가 줄어서 서버 한계가 더 올라간다.

## 연결은 늘리되 매번 새로 열지 않는다

파이프라인 없이 왕복을 겹치는 다른 방법은 연결을 여러 개 쓰는 것이다. 루프백에서 연결 수만 바꿔 봤다.

```bash
for c in 1 10 50 500; do redis-benchmark -p 19601 -t get -n 300000 -c $c -q; done
```

```text
GET: 50709.94 requests per second, p50=0.015 msec
GET: 84961.77 requests per second, p50=0.071 msec
GET: 79782.98 requests per second, p50=0.359 msec
GET: 66427.53 requests per second, p50=4.479 msec
```

(실제로는 연결 1개는 10만 번, 10개는 30만 번, 50개와 500개는 50만 번으로 돌렸다.) 연결 10개에서 이미 서버 한계(초당 8만 대)에 닿았다. 그 뒤로 연결을 늘리면 처리량은 그대로거나 줄고 p50만 늘어난다. 연결 500개면 4.5ms다. 줄 서는 사람이 늘었을 뿐 계산대는 하나이기 때문이다. 1ms 프록시 뒤에서는 연결 1개가 초당 717건, 10개가 6,223건이었다. 왕복이 길수록 연결을 늘리는 효과가 커진다. (연결 50개는 21,132건이었는데, 이때는 Node 프록시 자체가 병목이었다.)

더 나쁜 건 요청마다 연결을 새로 여는 것이다. `-k 0`은 명령마다 연결을 끊고 다시 연다.

```bash
redis-benchmark -p 19601 -t get -n 50000 -c 50 -k 1 -q   # 연결 유지 (기본값)
redis-benchmark -p 19601 -t get -n 50000 -c 50 -k 0 -q   # 매번 새 연결
redis-cli -p 19601 INFO stats | grep total_connections_received
```

```text
GET: 84602.37 requests per second, p50=0.295 msec
GET: 14064.70 requests per second, p50=1.287 msec
total_connections_received:50102
```

같은 기계 안에서도 처리량이 6분의 1이 됐다. TCP 3방향 핸드셰이크, `accept`, 클라이언트 구조체 생성과 해제가 명령마다 붙는다. TLS를 쓰면 핸드셰이크가 더 무거워진다. 서버리스 함수가 호출될 때마다 Redis에 새로 접속하거나, 요청마다 클라이언트를 만들고 닫는 코드가 이렇게 된다. `INFO stats`의 `total_connections_received`가 요청 수만큼 빠르게 오르면 이걸 의심한다.

그래서 연결은 몇 개를 오래 유지하고, 그 위에 요청을 겹쳐 싣는다. 앱 인스턴스 하나에 연결 수십 개를 두면 대부분 충분하다. 앱 인스턴스가 수백 대로 늘면 Redis가 받는 연결이 수만 개가 되고, 연결마다 버퍼 메모리를 쓰며 `maxclients`(기본 10000)에 걸릴 수 있다. 연결 풀의 크기 계산과 돌려주지 않은 연결 같은 일반론은 [연결 풀 글](/posts/connection-pool)에 있다.

## I/O 스레드는 남는 코어가 있을 때 듣는다

Redis 6과 7의 I/O 스레드는 메인 스레드가 한 이벤트 루프마다 일을 나눠 주고 다 끝날 때까지 기다리는 방식이다. 기다리는 동안 I/O 스레드는 바쁘게 돌며(busy-wait) 일을 기다린다. Valkey 8.0은 이걸 비동기 방식으로 다시 짜서 메인 스레드가 작업을 큐에 넣고 기다리지 않게 했고, 키를 찾기 전에 메모리를 미리 불러오는 프리페치를 더했다. Redis 8.0도 릴리스 노트에 새 I/O 스레드 구현을 넣었다고 적었다.

설정은 이렇다. Redis 7.x는 재시작해야 바뀌고, Valkey 9.0은 실행 중에 바꿀 수 있다.

```bash
redis-cli -p 19601 CONFIG SET io-threads 3   # Redis 7.0.15
redis-cli -p 19602 CONFIG SET io-threads 3   # Valkey 9.0.6
```

```text
ERR CONFIG SET failed (possibly related to argument 'io-threads') - can't set immutable config
OK
```

```bash
# Redis 7.x는 시작할 때 준다. 읽기까지 나누려면 io-threads-do-reads도 켠다 (Valkey 8.1부터는 이 설정이 없어도 읽기를 나눈다)
redis-server --port 19605 --io-threads 2 --io-threads-do-reads yes --save "" --daemonize yes
```

같은 조건으로 I/O 스레드를 끈 서버와 켠 서버를 두 번씩 쟀다. 클라이언트도 스레드 2개(`--threads 2`)로 돌렸다. 공식 설정 파일 주석이 I/O 스레드 효과를 보려면 벤치마크도 `--threads`로 돌리라고 적어 두었다.

```bash
redis-benchmark -p <포트> -t set,get -n 1000000 -c 100 --threads 2 -q
```

```text
Redis 7.0.15  io-threads 1  SET 128816 / 124937   GET 142592 / 124890
Redis 7.0.15  io-threads 2  SET 166306 / 166500   GET 159897 / 173792
Valkey 9.0.6  io-threads 1  SET 124766 / 128783   GET 117453 / 137703
Valkey 9.0.6  io-threads 2  SET  97380 / 108061   GET 114064 / 114051
```

벤치마크 출력에서 초당 처리량만 모아 한 줄에 두 번의 결과를 적은 것이다. Redis는 I/O 스레드 2개로 30% 남짓 올랐고, Valkey는 오히려 떨어졌다. 이걸 보고 "Valkey의 I/O 스레드가 나쁘다"고 결론 내리면 틀린다. 이 기계는 코어가 4개뿐이고, 그 위에서 서버 메인 스레드, I/O 스레드, 벤치마크 스레드 둘이 함께 돌았다. 측정 직후 `uptime`의 load average는 9.83이었다. 다른 작업까지 코어를 나눠 쓰고 있었다는 뜻이다.

더 붐비던 시간에 I/O 스레드를 3개로 놓고 GET만 잰 결과는 더 극단적이었다(그때 load average 8.70).

```text
Redis 7.0.15  io-threads 1  GET 72297 / 74599
Redis 7.0.15  io-threads 3  GET 15816 / 12046
Valkey 9.0.6  io-threads 1  GET 77081 / 74019
Valkey 9.0.6  io-threads 3  GET 18624 / 34634
```

둘 다 4~6분의 1로 떨어졌다. 이유는 스레드별 CPU 시간에 보인다.

```bash
# 스레드마다 지금까지 쓴 CPU 시간(TIME)
ps -T -p $(cat r5/pid)
```

```text
  PID  SPID TTY          TIME CMD
30364 30364 ?        00:01:21 redis-server
30364 30366 ?        00:00:00 bio_close_file
30364 30367 ?        00:00:00 bio_aof_fsync
30364 30368 ?        00:00:00 bio_lazy_free
30364 30369 ?        00:01:21 io_thd_1
30364 30370 ?        00:01:21 io_thd_2
30364 30371 ?        00:00:00 jemalloc_bg_thd
```

`io_thd_1`, `io_thd_2`가 메인 스레드와 똑같이 1분 21초를 썼다. 일이 없을 때도 돌며 기다렸기 때문이다. 코어가 남으면 이 기다림은 공짜지만, 코어가 모자라면 메인 스레드가 쓸 시간을 빼앗는다. Redis 설정 파일은 4코어 이상에서 남는 코어를 하나 두고 켜라고 하고(Valkey 9.0.6 설정 파일은 3코어 이상), 실제로 CPU를 많이 쓰는 성능 문제가 있을 때만 쓰라고 한다.

그래서 I/O 스레드는 이런 조건이 다 맞을 때 고르는 손잡이다. Redis 메인 스레드가 한 코어를 100% 쓰고 있고, `used_cpu_sys`가 `used_cpu_user`보다 크며(시스템 콜이 병목), 같은 기계에 남는 코어가 있다. 관리형 서비스라면 노드 크기에 따라 이 설정을 서비스가 정해 두는 경우가 많다. 내 장비에서 효과를 보려면 클라이언트를 다른 기계에 두고, 실제 명령 비율로, 여러 번 재야 한다.

## 큰 값 하나가 대역폭을 다 쓴다

지금까지는 값이 3바이트였다. 값 크기만 바꿔 SET과 GET을 돌려 봤다(`-d`가 값 크기다).

```bash
for d in 100 10000 100000 1000000; do redis-benchmark -p 19601 -t set,get -n 10000 -c 50 -d $d -q; done
```

```text
SET: 81967.21 requests per second, p50=0.367 msec
GET: 76923.08 requests per second, p50=0.399 msec
SET: 55248.62 requests per second, p50=0.447 msec
GET: 72992.70 requests per second, p50=0.431 msec
SET: 25380.71 requests per second, p50=1.103 msec
GET: 21367.52 requests per second, p50=0.983 msec
SET: 3558.72 requests per second, p50=7.111 msec
GET: 2124.50 requests per second, p50=8.431 msec
```

100바이트와 10KB는 GET 처리량이 비슷하다. 100KB부터 확 떨어지고, 1MB면 초당 2,124건, 약 2GB/s다. 루프백이라 이 정도지 실제 네트워크라면 10Gbps(1.25GB/s) 링크에서 1MB 값을 초당 1,000번 남짓 읽으면 링크가 찬다. 그리고 1MB 응답 하나를 쓰는 동안 메인 스레드는 그 일에 묶여 있다.

원소가 많은 키는 다른 방식으로 멈춘다. 원소 200만 개짜리 셋을 Redis 7.0.15에서 `DEL`로 지우는 데 847ms가 걸렸고 그동안 다른 모든 요청이 멈췄다. 같은 키를 `UNLINK`로 지우면 10ms였다. 이 차이와 Valkey의 기본값이 다른 이유는 [Valkey와 Redis 글](/posts/valkey-vs-redis)에, 큰 키를 찾는 `--bigkeys`와 `--memkeys`는 [메모리 글](/posts/redis-memory-eviction)에 있다. 처리량 관점에서 기억할 것은 하나다. `HGETALL`, `SMEMBERS`, `LRANGE 0 -1`처럼 원소 전체를 돌려주는 명령은 원소 수만큼 느려지니, 큰 컬렉션은 `HSCAN`, `SSCAN`이나 범위를 잘라 읽는다.

## 한 키에만 몰릴 때는 가까이에 둔다

샤드를 늘려도 키 하나는 노드 하나에 있다. 타임세일 상품 하나에 요청이 몰리면 그 노드만 CPU가 100%가 된다. 핫 키를 막는 일반적인 방법(로컬 캐시, 키 복제, 레플리카 읽기)은 [캐시 전략 글](/posts/caching-strategies)에 정리되어 있다. 여기서는 찾는 법과, Redis 6부터 있는 클라이언트 측 캐싱을 직접 본다.

먼저 찾기. 축출 정책이 LFU일 때 `--hotkeys`가 키마다 기록된 접근 빈도를 훑는다. Valkey 9.0.6에서 키 1만 개를 고르게 읽고, `product:1001:detail` 하나만 20만 번 읽은 뒤 돌렸다.

```bash
redis-cli -p 19602 CONFIG SET maxmemory-policy allkeys-lfu
valkey-benchmark -p 19602 -t set -r 10000 -n 100000 -q            # 키 1만 개를 만든다
valkey-benchmark -p 19602 -t get -r 10000 -n 100000 -q            # 고르게 읽는다
redis-cli -p 19602 SET product:1001:detail '{"name":"keyboard"}'
valkey-benchmark -p 19602 -n 200000 -q GET product:1001:detail   # 한 키만 20만 번
valkey-cli -p 19602 --hotkeys
```

```text
-------- Summary --------

Sampled 10001 keys in the keyspace!
hot key found with counter: 206	keyname: "product:1001:detail"
hot key found with counter: 11	keyname: "key:000000004099"
hot key found with counter: 11	keyname: "key:000000000539"
```

카운터가 20만이 아니라 206인 건 LFU 카운터가 로그 단위로 오르기 때문이다([메모리 글의 LFU 절](/posts/redis-memory-eviction)). 다른 키가 11 근처일 때 혼자 200이 넘으면 핫 키다. Valkey는 9.0부터 `valkey-cli`에 `--hotkeys-count` 옵션을, 8.0부터 슬롯별 CPU와 네트워크를 보여 주는 `CLUSTER SLOT-STATS`를 넣어 클러스터에서 몰리는 곳을 찾기 쉽게 했다.

찾았으면 그 키를 Redis까지 가지 않고 앱 메모리에서 읽게 하는 게 가장 효과가 크다. 문제는 값이 바뀌었을 때다. 클라이언트 측 캐싱(`CLIENT TRACKING`)은 서버가 "이 연결이 이 키를 읽었다"를 기억해 두었다가, 누가 그 키를 바꾸면 그 연결에 무효화 메시지를 밀어 준다. RESP3 연결에서는 같은 연결로 푸시가 온다. 아래 그림에서 다음을 누르면 순서가 보인다.

RESP를 직접 쓰는 Node 스크립트로 Redis 7.0.15와 Valkey 9.0.6에서 이 순서를 돌렸고, 두 서버의 결과가 같았다.

```text
A GET 응답: "$5\r\n42000\r\n" -> 로컬 캐시에 저장
A 푸시 수신: ">2\r\n$10\r\ninvalidate\r\n*1\r\n$18\r\nproduct:1001:price\r\n"
A 로컬 캐시: []
B SET 응답: "+OK\r\n"
```

`>`로 시작하는 줄이 RESP3 푸시다. 키 이름이 실려 오고, A의 로컬 캐시가 비었다. 이 실행에서는 B가 `OK`를 받기도 전에 A의 푸시가 먼저 찍혔다. 무효화는 쓰기 명령을 처리하는 그 자리에서 만들어진다.

이 방식에는 대가가 있다. 기본 모드에서 서버는 연결마다 읽은 키를 기억하므로 키가 많으면 메모리를 쓴다(`tracking-table-max-keys`로 상한을 둔다). 키 접두사로 구독하는 `BCAST` 모드는 서버 메모리를 덜 쓰는 대신 관심 없는 키의 무효화도 받는다. 연결이 끊긴 사이의 무효화는 잃어버리므로, 다시 붙으면 로컬 캐시를 통째로 비워야 한다. 이 원칙은 [캐시 무효화 글](/posts/cache-invalidation)의 실험과 같다. 직접 구현하기보다 이 기능을 지원하는 클라이언트(redis-py, Lettuce, node-redis의 최근 버전 등, 라이브러리 문서에서 확인)를 쓰는 편이 안전하다.

## 한 대로 안 되면 코어 수만큼 나눈다

명령 실행 자체로 메인 스레드가 꽉 찼다면(파이프라인을 했는데도 `used_cpu_user`가 크다), 한 프로세스로는 더 갈 곳이 없다. 다음 단계는 키를 나눠 여러 프로세스에 담는 것이다. 한 기계에 인스턴스를 코어 수만큼 띄우든, 여러 기계에 나누든 원리는 같고, 표준 방법이 [Redis Cluster](/posts/redis-cluster)다. 처리량은 샤드 수에 거의 비례해 오르지만 조건이 붙는다.

## 벤치마크 숫자를 믿기 전에

"초당 100만"과 "우리 서버의 초당 2만"은 둘 다 맞는 숫자일 수 있다. 위에서 본 것처럼 파이프라인 깊이 하나로 20배가 차이 나고, 값 크기, 연결 수, 클라이언트 위치, 같은 기계의 다른 작업이 모두 결과를 바꾼다. 남의 숫자를 볼 때도, 내가 잴 때도 이 조건을 함께 적는다.

```bash
# 내 환경의 기준선을 잴 때 쓰는 옵션들
#  -t: 명령 종류, -n: 총 요청 수, -c: 연결 수, -P: 파이프라인 깊이
#  -d: 값 크기(바이트), -r: 키를 무작위로 고를 범위, --threads: 클라이언트 스레드 수
#  --csv: 결과를 CSV로
redis-benchmark -h <redis 주소> -t set,get -n 1000000 -c 50 -P 16 -d 512 -r 100000 --threads 2 --csv
```

클라이언트는 앱 서버와 같은 위치(같은 가용 영역의 다른 기계)에서 돌린다. Redis와 같은 기계에서 돌리면 코어를 서로 빼앗아 이 글의 I/O 스레드 실험처럼 엉뚱한 결론이 나온다. 처리량만 보지 말고 지연 분포도 본다. `redis-benchmark`는 `-q` 없이 돌리면 백분위 표를 보여 준다. 평균이나 p50이 괜찮아도 p99가 튀면 사용자는 느리다고 느낀다([꼬리 지연 글](/posts/tail-latency)).

기계 자체가 흔들리는지도 먼저 본다. `--intrinsic-latency`는 Redis와 상관없이 그 기계에서 프로세스가 CPU를 못 받고 멈춘 최대 시간을 잰다.

```bash
# 5초 동안 이 기계 자체의 지연을 잰다 (Redis 서버가 도는 기계에서 실행)
redis-cli --intrinsic-latency 5
```

```text
Max latency so far: 4585 microseconds.

83343959 total runs (avg latency: 0.0600 microseconds / 59.99 nanoseconds per run).
Worst run took 76426x longer than the average latency.
```

이 공용 가상 서버는 아무 일도 안 하는데 4.6ms까지 멈췄다. 이런 기계에서는 Redis를 아무리 다듬어도 p99가 4~5ms 아래로 내려가지 않는다. 운영 중에는 `INFO stats`의 `instantaneous_ops_per_sec`(최근 초당 명령 수), `instantaneous_input_kbps`, `instantaneous_output_kbps`와 `INFO cpu`의 `used_cpu_sys`·`used_cpu_user`를 시계열로 모아 두면, 처리량이 막힐 때 어느 쪽이 먼저 찼는지 바로 보인다.

```text
instantaneous_ops_per_sec:91125
instantaneous_input_kbps:3203.64
instantaneous_output_kbps:444.82
```

## 느려졌다는 말을 들으면 보는 순서

앱 로그에 Redis 타임아웃이 늘었다. Redis의 `instantaneous_ops_per_sec`와 CPU부터 본다. CPU가 낮으면 Redis는 기다리고 있다. 앱 쪽에서 반복문 안의 `await`, 요청마다 새 연결(`total_connections_received`가 빠르게 오른다), 연결 풀 고갈, 앱과 Redis 사이의 RTT를 의심한다. `redis-cli --latency`를 앱 서버에서 돌려 왕복을 잰다.

CPU가 한 코어를 꽉 채웠다. `SLOWLOG GET`으로 느린 명령(큰 키에 대한 `HGETALL`, `DEL`, `KEYS`)이 있는지 본다. 느린 명령이 없는데 차 있다면 `used_cpu_sys`와 `used_cpu_user`를 비교한다. sys가 크면 파이프라인으로 시스템 콜을 줄이거나, 남는 코어가 있을 때 I/O 스레드를 켠다. user가 크면 샤드를 나눈다.

클러스터 노드 하나만 바쁘다. 핫 키다. `--hotkeys`나 Valkey의 `CLUSTER SLOT-STATS`로 찾고, 로컬 캐시와 `CLIENT TRACKING`, 키 복제로 분산한다.

네트워크 출력이 링크 한도에 붙었다. 큰 값이다. `instantaneous_output_kbps`가 높으면 `--bigkeys`로 큰 키를 찾아 값을 줄이거나 압축하고, 필요한 필드만 읽게 바꾼다.

### 원인을 보려고 MONITOR를 켜면 더 느려진다

이때 "무슨 명령이 들어오는지 보자"며 `redis-cli MONITOR`를 켜는 경우가 많다. `MONITOR`는 서버가 처리하는 모든 명령을 시각·클라이언트 주소와 함께 문자열로 만들어 그 연결로 다시 내보낸다. 명령 하나마다 출력 버퍼 쓰기가 하나 더 붙는 셈이다. 같은 기계에서 `GET`을 재 봤다.

```text
MONITOR 없음   -c 50          약 100,000~116,000 req/s
MONITOR 1개    -c 50          약  77,000~ 82,000 req/s
MONITOR 없음   -c 50 -P 16    약 818,000~931,000 req/s
MONITOR 1개    -c 50 -P 16    약 380,000~395,000 req/s
```

파이프라인을 써서 처리량이 높은 서버일수록 손해가 커서 절반 아래로 떨어졌다. 모니터 연결은 일반 클라이언트로 분류되고 일반 클라이언트의 `client-output-buffer-limit` 기본값은 0(무제한)이라, 화면이 출력을 늦게 읽으면 끊기지 않고 출력 버퍼만 계속 불어난다(`CLIENT LIST`의 `omem`). 바쁜 운영 서버에서는 켜지 않거나, 몇 초만 켜고 바로 끈다.

대신 쓸 것이 있다. 느린 명령은 `SLOWLOG GET`이 실행 시간과 인자를 남긴다(기본 10ms 넘는 것만, `slowlog-log-slower-than`). 이벤트 단위의 지연은 `CONFIG SET latency-monitor-threshold 10`을 걸어 두고 `LATENCY LATEST`, `LATENCY DOCTOR`로 본다. 8억 번째 비트를 켜는 `SETBIT` 하나([HyperLogLog 글](/posts/hyperloglog)의 비트맵 함정)를 넣자 `LATENCY DOCTOR`가 `command: 1 latency spikes (average 58ms ...)`로 짚어 냈다. 누가 보내는지는 `CLIENT LIST`의 `addr`, `cmd`(그 연결의 마지막 명령), `idle`로 좁힌다. 명령의 흐름 자체가 필요하면 서버가 아니라 앱 쪽에서 본다. 클라이언트 라이브러리의 명령 훅이나 OpenTelemetry 계측으로 명령 이름·키 접두사·소요 시간을 남기면 서버에 부담을 주지 않고 "어느 API가 어떤 명령을 몇 번 부르는지"까지 보인다.

Redis 한 대의 한계는 대부분 명령이 아니라 왕복과 시스템 콜에서 온다. 그래서 먼저 한 번에 실어 보내는 양을 늘리고(파이프라인, MGET), 연결을 오래 쓰고, 그래도 코어가 모자라면 그때 스레드와 샤드를 늘린다. 순서를 거꾸로 하면 서버를 늘려도 앱은 여전히 왕복을 기다린다.

## 면접에서 나올 만한 질문

### Redis가 단일 스레드인데 초당 수십만 건을 처리할 수 있는 이유는요?

명령 실행 자체는 메모리 안의 해시 테이블 조회라 1µs 안팎이라서다. 실제 비용은 소켓을 읽고 쓰는 시스템 콜과 네트워크 왕복에서 나온다. 실험에서 파이프라인 없이 GET 100만 번에 Redis가 쓴 CPU의 78%가 커널 안이었다. 파이프라인으로 명령을 묶으면 시스템 콜이 묶음 크기만큼 줄어서 같은 기계에서 초당 8만이 80만~170만으로 올랐다.

### 파이프라인 깊이는 클수록 좋은가요?

처리량은 오르지만 묶음 하나의 지연도 같이 는다. 연결 50개에서 깊이 1, 16, 64, 256으로 바꾸자 GET 처리량은 8만에서 172만으로 올랐지만 p50은 0.35ms에서 6.1ms로 늘었다. 큰 묶음이 실행되는 동안 다른 연결의 명령도 기다린다. 사용자 요청 경로에서는 수십~수백 개로 끊고, 대량 적재처럼 지연이 상관없을 때만 크게 묶는다.

### 파이프라인, MGET, MULTI/EXEC는 어떻게 다른가요?

파이프라인은 왕복을 줄이는 전송 방식이고 원자적이지 않아 사이에 다른 명령이 끼어든다. MGET은 명령 하나라 해석 비용까지 줄어 가장 빠르지만 Cluster에서는 키가 같은 슬롯에 있어야 한다. MULTI/EXEC는 원자적 실행을 위한 것이고 왕복을 줄이려는 도구가 아니다. 실험에서 1ms 왕복 뒤의 1000개 읽기가 반복문 1.2초, 파이프라인 10ms, MGET 2ms였다.

### Redis CPU는 낮은데 응답이 느립니다. 무엇을 의심하나요?

Redis가 아니라 왕복을 기다리는 쪽을 의심한다. 반복문 안에서 명령마다 `await`하거나, 요청마다 연결을 새로 열거나, 연결 풀이 모자라 줄을 서는 경우다. 1ms 왕복에서는 연결 하나로 초당 700건 남짓이 한계였다. `total_connections_received` 증가 속도, 앱 서버에서 잰 `redis-cli --latency`, 앱의 풀 대기 시간을 본다.

### I/O 스레드를 켜면 항상 빨라지나요?

아니다. I/O 스레드는 소켓 읽기·쓰기만 나누고 실행은 여전히 메인 스레드 하나라, 시스템 콜이 병목이고 남는 코어가 있을 때만 효과가 있다. 4 vCPU 공용 서버에서 재 보니 한 번은 Redis가 30% 올랐지만, 붐비는 시간에는 Redis와 Valkey 모두 4~6분의 1로 떨어졌다. Redis 7의 I/O 스레드는 일을 기다리며 돌아서 메인 스레드만큼 CPU를 쓰고, 코어가 모자라면 메인 스레드의 시간을 빼앗는다.

### Valkey 8의 I/O 스레드는 Redis 6·7과 무엇이 다른가요?

Redis 6·7은 메인 스레드가 이벤트 루프마다 일을 나눠 주고 I/O 스레드가 끝날 때까지 기다린다. Valkey 8.0은 이를 비동기로 바꿔 메인 스레드가 작업을 넘기고 기다리지 않게 했고, 실행 전에 키의 메모리를 미리 불러오는 프리페치를 넣었다. Valkey 9.0은 `io-threads`를 실행 중에 바꿀 수 있다. Redis 8.0도 새 I/O 스레드 구현을 넣었다고 밝혔고, 어느 쪽이 빠른지는 내 장비에서 재야 한다.

### 핫 키 하나 때문에 클러스터 노드 하나만 바쁩니다. 샤드를 늘리면 되나요?

안 된다. 키 하나는 슬롯 하나에 있고 슬롯은 노드 하나에 있어서, 샤드를 늘려도 그 키는 계속 한 노드로 간다. `--hotkeys`(LFU 정책일 때)나 Valkey의 `CLUSTER SLOT-STATS`로 찾은 뒤 앱 로컬 캐시를 둔다. 값이 바뀔 때 늦지 않게 하려면 `CLIENT TRACKING`으로 서버가 무효화를 밀어 주게 하고, 연결이 끊겼다 붙으면 로컬 캐시를 통째로 비운다.

### redis-benchmark 숫자를 보고 용량을 정해도 되나요?

조건을 맞추지 않으면 안 된다. 파이프라인 깊이, 값 크기, 연결 수, 명령 비율, 클라이언트 위치 하나하나가 몇 배씩 결과를 바꾼다. 내 앱의 실제 명령 비율과 값 크기로, 앱 서버와 같은 위치의 다른 기계에서 여러 번 돌리고, 처리량과 함께 p99를 본다. `--intrinsic-latency`로 기계 자체가 흔들리는지도 먼저 확인한다.
