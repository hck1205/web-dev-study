사무실 구석의 스위치 두 대를 남는 랜선으로 한 번 더 이었다. 연결이 두 가닥이면 하나가 끊겨도 버티겠다는 생각이었다. 몇 분 뒤 층 전체 인터넷이 멈추고 스위치 불빛이 쉬지 않고 깜빡인다. 그런데 라우터 두 대 사이에 경로를 잘못 넣어 서로를 가리키게 만들면, 그 대역으로 가는 패킷만 사라지고 나머지 망은 멀쩡하다.

둘 다 "고리"를 만든 실수인데 결과가 이렇게 다르다. 스위치와 라우터가 패킷을 다루는 방식이 근본부터 다르기 때문이다. 이 글은 두 장비를 같은 실습 망에 세워 놓고 프레임이 지나갈 때 무엇이 바뀌고 무엇이 그대로인지, 표를 어떻게 찾는지, 고리가 생기면 왜 한쪽만 망 전체를 멈추는지, 그리고 둘 사이 어딘가에 있는 L3 스위치까지 본다.

스위치가 MAC을 배우는 과정과 ARP는 [데이터 링크 계층 글](/posts/layer-link-ethernet-arp)에서, 라우팅 테이블과 최장 접두사 일치, TTL과 traceroute는 [라우팅과 ICMP 글](/posts/layer-ip-routing-icmp)에서 자세히 다뤘다. 여기서는 그 둘을 나란히 놓고 차이에 집중한다. 기준 OS는 Ubuntu 24.04이고, 스위치는 리눅스 브리지, 라우터는 `ip_forward`를 켠 네트워크 네임스페이스로 만들었다. 출력은 모두 이 실습 망에서 실제로 받은 것이다.

## 실습 망 하나에 두 장비

망은 이렇게 생겼다. 스위치 `sw1`(브리지 `br0`)에 호스트 A(`10.0.1.11`), B(`10.0.1.12`), 그리고 라우터의 한쪽 다리(`10.0.1.1`)가 꽂혀 있다. 라우터의 다른 다리(`10.0.2.1`)에는 다른 대역의 호스트 C(`10.0.2.13`)가 붙어 있다. 읽기 쉽게 MAC은 `02:00:00:00:01:11`처럼 IP 끝자리와 맞췄다.

```bash
# 스위치: 네임스페이스 안에 브리지를 만들고, 호스트와 이은 veth 끝을 포트로 꽂는다
sudo ip netns exec n1-sw1 ip link add br0 type bridge
sudo ip netns exec n1-sw1 ip link set pa master br0 up
# 라우터: 두 다리에 주소를 주고 포워딩을 켠다
sudo ip netns exec n1-rt ip addr add 10.0.1.1/24 dev eth0
sudo ip netns exec n1-rt ip addr add 10.0.2.1/24 dev eth1
sudo ip netns exec n1-rt sysctl -w net.ipv4.ip_forward=1
```

이 글 전체에서 쓸 비유는 하나다. 패킷은 봉투 안에 든 편지다. 바깥 봉투(이더넷 헤더)에는 이번 구간의 보내는 MAC과 받는 MAC이, 안쪽 봉투(IP 헤더)에는 처음 보낸 사람과 최종 받는 사람의 IP가 적혀 있다. 스위치는 바깥 봉투만 읽고 그대로 넘긴다. 라우터는 바깥 봉투를 버리고 새 봉투에 넣어 보낸다.

## 스위치는 봉투를 뜯지 않는다

A에서 같은 대역의 B로 ping을 보내고, 스위치의 A쪽 포트(`pa`)와 B쪽 포트(`pb`)에서 동시에 찍었다.

```bash
# 스위치의 두 포트에서 각각 캡처한다. -e는 MAC, -v는 TTL과 IP id까지 보여 준다
sudo ip netns exec n1-sw1 tcpdump -i pa -n -e -v icmp
sudo ip netns exec n1-sw1 tcpdump -i pb -n -e -v icmp
```

```text
--- pa (들어온 쪽)
08:05:33.041203 02:00:00:00:01:11 > 02:00:00:00:01:12, ethertype IPv4 (0x0800), length 98: (tos 0x0, ttl 64, id 44467, offset 0, flags [DF], proto ICMP (1), length 84)
    10.0.1.11 > 10.0.1.12: ICMP echo request, id 15945, seq 1, length 64
--- pb (나간 쪽)
08:05:33.041209 02:00:00:00:01:11 > 02:00:00:00:01:12, ethertype IPv4 (0x0800), length 98: (tos 0x0, ttl 64, id 44467, offset 0, flags [DF], proto ICMP (1), length 84)
    10.0.1.11 > 10.0.1.12: ICMP echo request, id 15945, seq 1, length 64
```

두 줄이 시각을 빼면 글자 하나 다르지 않다. 보내는 MAC, 받는 MAC, TTL 64, IP id 44467이 그대로다. 스위치는 6µs 사이에 받는 MAC `02:00:00:00:01:12`를 표에서 찾아 `pb`로 내보냈을 뿐이다. 그 표가 이것이다.

```bash
# 스위치가 배운 MAC 표. -s는 마지막으로 쓰인 뒤 지난 초를 보여 준다
sudo ip netns exec n1-sw1 bridge -s fdb show br br0 | grep -v permanent
```

```text
02:00:00:00:01:11 dev pa used 5/5 master br0 
02:00:00:00:01:12 dev pb used 5/5 master br0 
```

`used 5/5`는 이 항목이 5초 전에 쓰이고 5초 전에 갱신됐다는 뜻이다. 리눅스 브리지는 `ageing_time 30000`(1/100초 단위, 300초) 동안 안 쓰인 항목을 지운다. 표에 없는 MAC이나 브로드캐스트는 들어온 포트를 뺀 모든 포트로 뿌린다. 받는 MAC이 들어온 포트 쪽에 있다고 표에 적혀 있으면 아무 데도 보내지 않는다.

스위치의 판단을 함수로 옮기면 몇 줄이다. 표에 있으면 그 포트로, 없거나 브로드캐스트면 들어온 포트만 빼고 전부, 들어온 포트와 같으면 버린다.

스위치가 IP를 보지 않는다는 건 장점이다. IPv4든 IPv6든 ARP든, 이더넷 프레임이기만 하면 똑같이 나른다. 헤더를 고치지 않으니 체크섬을 다시 계산할 일도 없다. 상용 스위치는 이 판단을 전용 칩에서 포트 속도 그대로 처리한다.

## 라우터는 봉투를 갈아 끼운다

이번에는 A에서 다른 대역의 C로 ping을 보냈다. 먼저 라우터의 `ip_forward`를 끈 상태다.

```text
2 packets transmitted, 0 received, 100% packet loss, time 1004ms
```

리눅스는 기본으로 남의 패킷을 넘기지 않는다. `net.ipv4.ip_forward=1`을 켠 뒤 라우터의 두 다리에서 동시에 찍었다.

```text
--- 라우터 eth0 (A 쪽에서 들어옴)
08:05:46.893891 02:00:00:00:01:11 > 02:00:00:00:01:01, ethertype IPv4 (0x0800), length 98: (tos 0x0, ttl 64, id 63223, offset 0, flags [DF], proto ICMP (1), length 84)
    10.0.1.11 > 10.0.2.13: ICMP echo request, id 16124, seq 1, length 64
--- 라우터 eth1 (C 쪽으로 나감)
08:05:46.893926 02:00:00:00:02:01 > 02:00:00:00:02:13, ethertype IPv4 (0x0800), length 98: (tos 0x0, ttl 63, id 63223, offset 0, flags [DF], proto ICMP (1), length 84)
    10.0.1.11 > 10.0.2.13: ICMP echo request, id 16124, seq 1, length 64
```

안쪽 봉투인 `10.0.1.11 > 10.0.2.13`과 IP id 63223은 그대로다. 바깥 봉투는 통째로 바뀌었다. 들어올 때는 A의 MAC에서 라우터 MAC(`01:01`)으로, 나갈 때는 라우터의 다른 다리 MAC(`02:01`)에서 C의 MAC(`02:13`)으로. TTL은 64에서 63이 됐다. A 쪽에서 받은 응답이 `ttl=63`으로 찍히는 것도 같은 이유다.

```text
64 bytes from 10.0.2.13: icmp_seq=1 ttl=63 time=0.296 ms
```

A는 C의 MAC을 알 필요가 없다. 다른 대역이면 게이트웨이의 MAC만 알면 된다. 처음 보내는 순간부터 C가 받을 때까지를 순서대로 그렸다. 다음을 누르면 주체 사이를 메시지가 오간다.

MAC 표는 정확히 같은 값을 찾는다. 48비트 MAC 하나가 표에 있거나 없거나다. 라우팅 테이블은 범위를 찾고, 여러 줄이 맞으면 가장 길게 맞는 줄을 고른다(`10.0.0.0/8`과 `10.0.2.0/24`가 둘 다 맞으면 `/24`). 상용 장비에서 MAC 표는 정확 일치에 맞는 CAM이나 해시 표에, 라우팅 테이블은 범위 비교를 한 번에 하는 TCAM에 들어가는 경우가 많다. TCAM은 비싸고 전력을 많이 써서, 스위치가 담을 수 있는 경로 수가 라우터보다 훨씬 적은 이유가 된다.

## 브로드캐스트는 라우터 앞에서 멈춘다

A가 없는 주소 `10.0.1.99`의 MAC을 ARP로 물었다. 같은 스위치의 B와, 라우터 너머의 C에서 동시에 찍었다.

```text

08:05:57.621196 02:00:00:00:01:11 > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42: Request who-has 10.0.1.99 tell 10.0.1.11, length 28
08:05:58.637845 02:00:00:00:01:11 > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42: Request who-has 10.0.1.99 tell 10.0.1.11, length 28
08:05:59.661518 02:00:00:00:01:11 > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42: Request who-has 10.0.1.99 tell 10.0.1.11, length 28
```

## 고리가 생기면 갈리는 운명

처음 장면을 재현했다. 스위치 `sw2`(브리지 `br1`)를 하나 더 만들고 호스트 D(`10.0.1.14`)를 꽂았다. `sw1`과 `sw2`를 veth 두 가닥으로 이었다. 리눅스 브리지는 STP가 기본으로 꺼져 있다. 망이 완전히 멈추지 않도록 두 가닥에 tbf로 100kbit 속도 제한을 걸었다.

<Callout kind="warning">
아래 실험은 격리된 네트워크 네임스페이스에서만 했다. 실제 사무실이나 서버망에서 STP를 끈 채 스위치 사이에 두 번째 선을 꽂으면 몇 초 만에 같은 대역 전체가 멈춘다. 실수로 만들었다면 가장 먼저 그 선을 뽑는다(리눅스 브리지라면 `ip link del` 또는 `ip link set <포트> nomaster`). 그 뒤에 STP를 켜고 다시 잇는다.
</Callout>

A에서 ARP 요청을 딱 한 번 보냈다(`busybox arping -c 1`). 3초 동안 D가 받은 프레임 수와, 첫 번째 연결선의 송신 카운터다.

```bash
# 3초 동안 D에서 ARP를 센다 / 연결선 up1의 송신 패킷 수를 전후로 본다
sudo ip netns exec n1-hd timeout 3 tcpdump -i eth0 -n -e arp
sudo ip netns exec n1-sw1 ip -s link show up1
```

한 번 보낸 ARP가 3초 동안 D에게 1490번 도착했다. 똑같은 프레임이다. `sw1`이 브로드캐스트를 두 연결선으로 다 뿌리면, `sw2`는 한 선으로 받은 것을 다른 선으로 되돌려 보내고, `sw1`은 그걸 또 다른 선으로 보낸다. 이더넷 헤더에는 TTL 같은 칸이 없어서 프레임은 끝나지 않고 돈다. 속도 제한이 없었다면 선의 대역폭을 다 채울 때까지 늘어났을 것이다. 스위치가 셋 이상 고리로 엮이면 한 바퀴마다 복사본이 늘어 더 빨리 터진다. 이것이 브로드캐스트 스톰이다. 같은 MAC이 여러 포트에서 번갈아 들어오니 MAC 표도 계속 고쳐 써져서, 평범한 유니캐스트까지 엉뚱한 포트로 간다.

라우터의 고리는 다르게 끝났다. 라우터에 `10.9.0.0/16`을 B로 보내는 경로를 넣고, B에는 포워딩을 켜서 기본 경로(라우터)로 돌려보내게 했다. 두 장비가 서로를 가리킨다.

```text
PING 10.9.0.1 (10.9.0.1) 56(84) bytes of data.
From 10.0.1.12 icmp_seq=1 Time to live exceeded
```

B에서 찍은 같은 패킷은 63번 지나갔고, TTL이 `63, 62, 61, ... 3, 2, 1`로 줄다가 끝났다. 패킷 하나가 몇 밀리초 동안 고리를 돌고 사라졌을 뿐, 다른 대역의 통신에는 아무 영향이 없다. L3에는 TTL이라는 안전장치가 있고 L2에는 없다. 처음 장면의 차이가 이것이다.

## 고리를 끊어 두는 STP

L2에서는 장비가 스스로 고리를 찾아 끊어야 한다. STP(Spanning Tree Protocol, 802.1D)가 그 일을 한다. 스위치끼리 BPDU라는 작은 메시지를 주고받아 대장(루트 브리지)을 하나 뽑고, 루트까지 가는 길이 둘 이상인 곳에서는 한 포트를 막아(blocking) 망을 나무 모양으로 만든다. 막힌 포트도 BPDU는 계속 듣고 있다가, 쓰던 길이 끊기면 열린다.

두 브리지에 STP를 켜고(`sw1`을 우선순위 4096으로 낮춰 루트로 정했다) 같은 두 가닥을 다시 이었다.

```bash
# 브리지에 STP를 켠다. forward_delay는 1/100초 단위라 400이면 4초
sudo ip netns exec n1-sw1 ip link set br0 type bridge stp_state 1 forward_delay 400 priority 4096
sudo ip netns exec n1-sw2 ip link set br1 type bridge stp_state 1 forward_delay 400
# 포트 상태를 본다
sudo ip netns exec n1-sw2 bridge link
```

```text
3: pd@if25: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br1 state forwarding priority 32 cost 2 
4: up2@if26: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br1 state forwarding priority 32 cost 2 
6: upb@if28: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br1 state blocking priority 32 cost 2 
```

```text
08:07:27.981560 STP 802.1d, Config, Flags [Topology change], bridge-id 1000.02:00:00:00:0a:01.8004, length 35
08:07:29.997487 STP 802.1d, Config, Flags [Topology change], bridge-id 1000.02:00:00:00:0a:01.8004, length 35
```

`upb`가 `blocking`이다. BPDU는 2초(hello time)마다 오고, `bridge-id 1000.02:00:00:00:0a:01`이 루트로 뽑힌 `sw1`이다(앞의 `1000`이 우선순위 4096을 16진수로 쓴 것). 같은 ARP를 한 번 보내자 D는 정확히 한 번 받았다.

```text
08:07:12.819627 02:00:00:00:01:11 > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42: Request who-has 10.0.1.98 (ff:ff:ff:ff:ff:ff) tell 10.0.1.11, length 28

1 packet captured
```

이제 쓰던 선 `up1`을 끊었다. A에서 D로 0.5초마다 ping을 보내며 `upb`의 상태를 1초마다 봤다.

```text
08:07:32 state listening
08:07:35 state listening
08:07:36 state learning
08:07:39 state learning
08:07:40 state forwarding
```

```text
30 packets transmitted, 18 received, 40% packet loss, time 14839ms
```

막혀 있던 포트가 바로 열리지 않는다. listening 4초, learning 4초(forward_delay 두 번)를 거쳐 8초 뒤에야 forwarding이 됐고, 그동안 ping 12개가 사라졌다. 열기 전에 기다리는 건 다른 스위치들이 새 나무 모양을 다 알아차리기 전에 열었다가 잠깐이라도 고리가 생기는 걸 막기 위해서다. 802.1D 기본값(forward_delay 15초, max age 20초)이면 이 공백이 30초에서 50초까지 간다.

이 공백이 너무 길어서 RSTP(802.1w)가 나왔다. 이웃 스위치와 직접 합의(proposal과 agreement)해서 포트를 바로 열기 때문에 보통 몇 초 안에 끝난다. 상용 스위치는 대부분 RSTP나 여러 VLAN별로 나무를 따로 만드는 MSTP를 쓴다. 리눅스 커널 브리지는 802.1D만 구현하고, RSTP가 필요하면 사용자 공간 데몬(mstpd)을 붙인다. 서버나 PC가 꽂히는 포트에는 PortFast(edge port) 설정을 줘서 listening과 learning을 건너뛰게 한다. 이걸 빠뜨리면 서버를 꽂고 30초 동안 DHCP가 안 되는 증상이 나온다. 반대로 edge port에 스위치를 꽂으면 고리가 생길 수 있어서 BPDU Guard로 그 포트를 끄게 해 둔다.

데이터센터는 다른 답을 골랐다. 막힌 포트는 대역폭을 놀리는 셈이라, 스위치 사이를 아예 L3로 라우팅하고(링크를 모두 쓰는 ECMP), 같은 L2가 필요하면 그 위에 [VXLAN 오버레이](/posts/sdn-vxlan-overlay)를 얹는다. 두 선을 다 쓰고 싶을 뿐이라면 두 선을 하나의 논리 링크로 묶는 LACP(링크 묶기)가 정답이다. 처음 장면의 직원이 원한 것도 사실 이쪽이었다.

## L3 스위치는 어느 쪽인가

장비 이름으로 둘을 가르면 헷갈린다. L3 스위치는 스위치처럼 생겼고 스위치처럼 포트가 수십 개지만, VLAN마다 IP 주소를 가진 가상 인터페이스(SVI, 예: `interface vlan 10`)를 두고 VLAN 사이를 라우팅한다. 라우팅도 스위칭과 같은 전용 칩에서 하니 VLAN 사이 트래픽이 포트 속도로 지나간다. 사무실과 데이터센터 안쪽에서 VLAN 사이를 잇는 건 대개 L3 스위치다.

그럼 라우터는 왜 따로 있나. 라우터가 잘하는 건 따로 있다. 인터넷 회선이나 전용선 같은 WAN 인터페이스, NAT와 VPN, 수십만 줄짜리 인터넷 전체 경로(BGP 풀 테이블), 혼잡을 견디는 깊은 버퍼와 QoS다. L3 스위치는 TCAM에 담을 수 있는 경로 수가 적고 이런 기능이 빠져 있거나 제한된 경우가 많다. 반대로 라우터 하나에 VLAN 여러 개를 트렁크 한 선으로 물려 라우팅하는 방식(router on a stick)은 값싸지만 모든 VLAN 사이 트래픽이 그 한 선을 두 번씩 지난다.

| | 스위치 (L2) | L3 스위치 | 라우터 |
|---|---|---|---|
| 보는 헤더 | 이더넷(MAC) | 이더넷 + IP | 이더넷 + IP (+ NAT면 포트까지) |
| 표 | MAC 표, 정확 일치 | MAC 표 + 작은 경로 표 | 큰 경로 표, 최장 접두사 일치 |
| 프레임을 바꾸나 | 그대로 | 라우팅할 때만 MAC, TTL | 매번 MAC, TTL, 체크섬 |
| 브로드캐스트 | 넘긴다 | VLAN 안에서만 | 막는다 |
| 고리 대책 | STP, LACP | STP + TTL | TTL |
| 주로 서는 곳 | 같은 대역 안 | VLAN 사이, 데이터센터 안 | 망 끝, WAN, 인터넷 |

리눅스 서버 한 대가 둘 다 하기도 한다. Docker 호스트가 그렇다. `docker0`은 컨테이너들을 잇는 브리지(스위치)이고, 호스트 자신은 `ip_forward`를 켜고 NAT를 하는 라우터다. 컨테이너끼리 안 될 때는 브리지 쪽을(`bridge fdb`, `bridge link`), 밖으로 안 나갈 때는 라우터 쪽을(`ip route`, `sysctl net.ipv4.ip_forward`, [NAT 규칙](/posts/iptables-nat)) 보는 이유다. 자세한 건 [Docker 네트워크 드라이버 글](/posts/docker-network-drivers)에 있다. 클라우드 VPC에는 눈에 보이는 스위치가 없고, 서브넷 사이와 바깥으로 가는 길은 [라우트 테이블](/posts/vpc-subnets-route-tables) 한 장이 정한다.

## 어느 쪽이 문제인지 가르는 순서

"통신이 안 된다"를 들으면 먼저 두 주소가 같은 대역인지 본다. 같은 대역이면 스위치 쪽, 다른 대역이면 라우터 쪽이다.

같은 대역인데 안 될 때는 L2를 본다.

```bash
# 상대 MAC을 얻었는지: FAILED나 INCOMPLETE면 L2에서 막힌 것
ip neigh show 10.0.1.12
# 리눅스 브리지라면 상대 MAC이 어느 포트에 배워졌는지
sudo bridge fdb show br br0 | grep 02:00:00:00:01:12
# 포트가 브리지에 붙어 있고 forwarding 상태인지 (blocking, disabled면 STP 문제)
sudo bridge link
```

상대 MAC이 엉뚱한 포트에 있거나 계속 바뀐다면 고리나 MAC 중복을 의심한다. 포트가 VLAN이 다르면 같은 대역 주소여도 닿지 않는다([VLAN 글](/posts/vlan-basics)).

다른 대역이면 L3를 본다.

```bash
# 내 기기가 게이트웨이로 보내고 있는지
ip route get 10.0.2.13
# 라우터 역할 장비에서 포워딩이 켜져 있는지
sysctl net.ipv4.ip_forward
# 돌아오는 길: 상대 쪽 라우팅 테이블에 내 대역으로 가는 경로가 있는지
ip route
```

흔한 실수는 가는 길만 만들고 돌아오는 길을 잊는 것이다. 요청은 도착했는데 응답이 다른 길로 가거나 길이 없어서 사라진다. 상대 쪽에서 tcpdump를 걸어 요청이 오는지부터 보면 반을 가를 수 있다.

망 전체가 느려지고 스위치 불빛이 미친 듯이 깜빡이면 고리다. 리눅스에서는 `ip -s link`의 수신·송신 패킷 수가 몇 초 사이에 수천씩 뛰는 걸로 보인다. 실습의 연결선도 3개이던 송신 패킷이 3초 만에 1469개가 됐다. 최근에 꽂은 선부터 뽑는다.

ping의 TTL로 몇 홉을 지났는지도 짐작할 수 있다. 리눅스는 64, 윈도우는 128로 시작하는 경우가 많아서, 응답 `ttl=63`이면 라우터 하나를 지난 것이다. 스위치는 몇 대를 지나도 TTL이 줄지 않는다. traceroute에 스위치가 나오지 않는 이유도 같다.

## 봉투를 뜯느냐 마느냐

스위치는 바깥 봉투의 MAC만 보고 그대로 넘긴다. 표는 정확 일치, 모르면 모두에게 뿌리고, 헤더에 TTL이 없어서 고리가 생기면 망이 멈춘다. 그래서 STP로 고리를 미리 끊어 둔다. 라우터는 안쪽 IP를 보고 범위로 길을 찾고, 바깥 봉투를 새로 씌우고 TTL을 줄인다. 브로드캐스트는 라우터에서 멈추고, 경로 고리는 TTL이 끝낸다. L3 스위치는 이 둘을 한 칩에 담은 장비다. 다음에는 라우터가 안쪽 봉투의 주소까지 고쳐 쓰는 경우, [NAT를 넘어 연결하는 법](/posts/nat-traversal)을 본다.

## 면접에서 나올 만한 질문

### 스위치와 라우터의 차이를 설명해 주세요

스위치는 L2 장비로 이더넷 프레임의 받는 MAC을 MAC 표에서 정확히 찾아 그 포트로 넘기고, 프레임을 고치지 않는다. 라우터는 L3 장비로 받는 IP를 라우팅 테이블에서 최장 접두사 일치로 찾아 다음 칸을 정하고, 이더넷 헤더를 새로 씌우고 TTL을 줄인다. 그래서 스위치는 같은 대역 안을 잇고 라우터는 대역과 대역 사이를 잇는다. 브로드캐스트는 스위치를 넘고 라우터에서 멈춘다.

### 패킷이 라우터를 지날 때 바뀌는 것과 그대로인 것은 무엇인가요?

이더넷 헤더의 보내는 MAC과 받는 MAC은 구간마다 바뀌고, IP 헤더의 TTL이 하나 줄며 그래서 IP 체크섬도 다시 계산된다. 출발지와 목적지 IP, IP id, 그 위의 TCP·UDP 내용은 그대로다. NAT를 하는 라우터라면 IP 주소와 포트까지 바뀐다. 실제 캡처에서 같은 IP id가 라우터 양쪽에서 TTL 64와 63으로 찍혔다.

### 스위치 사이에 선을 하나 더 꽂았더니 망이 멈췄습니다. 왜 그런가요?

L2 고리가 생겨 브로드캐스트 스톰이 일어난 것이다. 스위치는 브로드캐스트를 모든 포트로 뿌리는데 이더넷 헤더에는 TTL이 없어 고리 속 프레임이 끝나지 않고 돈다. 실습에서는 ARP 한 장이 3초 동안 1490번 도착했다. 같은 MAC이 여러 포트에서 들어와 MAC 표도 흔들린다. STP가 꺼져 있었거나 그 포트에서 BPDU를 막아 둔 것이 원인이고, 두 선을 다 쓰고 싶었다면 LACP로 묶어야 한다.

### STP는 어떻게 고리를 막고, 단점은 무엇인가요?

BPDU를 주고받아 루트 브리지를 뽑고, 루트까지 길이 여럿인 곳의 한 포트를 blocking으로 막아 망을 나무 모양으로 만든다. 막힌 포트는 BPDU를 계속 들으며 쓰던 길이 끊기면 listening과 learning을 거쳐 열린다. 단점은 막힌 링크의 대역폭을 놀린다는 것과 수렴이 느리다는 것이다. 802.1D 기본값이면 30~50초가 걸리고, 실습에서 forward_delay를 4초로 줄여도 8초 동안 ping이 끊겼다. 그래서 RSTP나 MSTP를 쓰고, 데이터센터는 L3 라우팅과 ECMP로 STP 자체를 피한다.

### 라우터에서 경로가 서로를 가리키면 어떻게 되나요?

패킷이 두 라우터 사이를 오가다 TTL이 0이 되면 버려지고, 보낸 쪽에 ICMP Time Exceeded가 돌아간다. 실습에서는 같은 패킷이 63번 오가고 끝났다. 그 대역으로 가는 트래픽만 사라지고 다른 통신은 멀쩡하다. L2 고리와 달리 L3에는 TTL이라는 안전장치가 있기 때문이다.

### L3 스위치가 있는데 라우터는 왜 필요한가요?

L3 스위치는 VLAN 사이 라우팅을 전용 칩에서 포트 속도로 하지만, 담을 수 있는 경로 수가 적고 WAN 인터페이스, NAT, VPN, 깊은 버퍼와 세밀한 QoS 같은 기능은 빠져 있거나 제한된 경우가 많다. 그래서 망 안쪽의 VLAN 사이는 L3 스위치가, 인터넷과 맞닿는 가장자리와 지점 사이 연결은 라우터가 맡는 구성이 흔하다.

### 같은 대역 두 서버가 통신이 안 될 때와 다른 대역일 때 확인 순서는 어떻게 다른가요?

같은 대역이면 L2부터 본다. `ip neigh`로 상대 MAC을 얻었는지, 스위치 MAC 표에서 그 MAC이 맞는 포트에 있는지, 포트의 VLAN과 STP 상태가 맞는지를 본다. 다른 대역이면 L3다. 내 쪽이 게이트웨이로 보내는지, 중간 장비의 포워딩이 켜져 있는지, 상대 쪽에 돌아오는 경로가 있는지를 본다. 돌아오는 길을 잊는 실수가 특히 흔해서 상대 쪽 캡처로 요청이 도착하는지부터 확인한다.
