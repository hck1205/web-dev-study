<EasyIntro>
  클라우드의 사설망 A와 B를 잇고 다시 B와 C를 이었는데, A에서 C로 보낸 것은 조용히 사라졌다. 새로 이어야 할 망 D는 하필 A와 주소 범위가 똑같았다.

  사설망 하나를 섬 하나라고 생각하면 잇는 방법이 세 가지다. 피어링은 두 섬 사이에 다리를 하나 놓는 것인데, B 섬은 A에서 온 사람을 C로 가는 다리에 태워 주지 않는다. 섬이 많아지면 한가운데 환승 섬을 두고 모든 섬을 그곳에 잇는 트랜싯 게이트웨이를 쓴다. 섬 전체가 아니라 가게 하나만 열어 주고 싶으면, 상대 섬 안에 그 가게로 통하는 주문 창구만 하나 놓아 주는 프라이빗링크를 쓴다.

  주소가 같은 섬끼리는 다리를 놓을 수 없다. 길 안내판에 같은 주소가 두 곳이 되어 어디로 갈지 고를 수 없기 때문이다. 이럴 때는 주문 창구 방식만 통하니, 처음부터 회사 전체의 주소 범위가 겹치지 않게 나눠 둔다.
</EasyIntro>

결제 서비스 VPC(A)와 공용 로그 수집 VPC(B)를 피어링으로 이었다. 잘 된다. 몇 주 뒤 정산 서비스 VPC(C)도 B와 피어링했다. A와 B, B와 C가 이어졌으니 A에서 C의 정산 API도 부를 수 있을 거라 생각하고 A의 라우트 테이블에 C 대역을 B 쪽 피어링으로 넣었다. 그런데 패킷이 사라진다. 같은 주에 인수한 회사의 VPC(D)와도 이어야 하는데, D의 대역이 하필 A와 똑같은 `10.0.0.0/16`이다.

VPC끼리 잇는 방법은 크게 셋이다. 피어링, Transit Gateway, PrivateLink. 셋은 "무엇을 연결하는가"부터 다르다. 피어링은 망 둘을, Transit Gateway는 망 여럿을 허브로, PrivateLink는 망이 아니라 서비스 하나를 잇는다. 이 글은 셋이 패킷을 어떻게 보내는지, 왜 위 장면처럼 막히는지, 언제 무엇을 고르는지를 본다. [VPC 기본 글](/posts/vpc-basics)과 [라우트 테이블 글](/posts/vpc-subnets-route-tables)의 내용을 안다고 보고, 실습은 Ubuntu 24.04의 네트워크 네임스페이스로 VPC 넷을 만들어 진행한다.

## 다리 하나에 VPC 둘: 피어링

VPC 피어링은 VPC 두 개를 사설 IP로 직접 잇는다. 따로 장비가 생기지 않는다. AWS 망 안에서 두 VPC의 라우트 테이블이 서로의 대역을 알게 될 뿐이라 대역폭 한도나 단일 장애점이 없다. 같은 계정이든 다른 계정이든, 같은 리전이든 다른 리전이든 맺을 수 있다.

맺는 과정은 한쪽이 요청하고 다른 쪽이 수락하는 순서다. 수락만으로는 아무것도 통하지 않는다는 게 흔한 함정이다. 다음을 누르면 순서대로 볼 수 있다.

## 친구의 친구는 친구가 아니다

처음 장면의 문제로 가자. A–B, B–C 피어링이 있어도 A에서 C로는 갈 수 없다. 피어링은 전이되지 않는다(non-transitive). B가 라우터처럼 A의 패킷을 받아 C로 넘겨 주지 않는다. 피어링으로 들어온 패킷은 그 VPC 안의 목적지에만 닿을 수 있다.

같은 이유로 상대 VPC의 출구도 빌려 쓸 수 없다. B에 NAT 게이트웨이나 VPN 연결이 있어도 A가 B의 피어링을 지나 그걸 쓰지 못한다. AWS 문서는 이걸 엣지 간 라우팅(edge-to-edge routing)을 지원하지 않는다고 적는다. 아래 그림에서 다음을 누르면 네 가지 경우가 차례로 지나간다.

모형에서도 같은 상황을 만들었다. VPC마다 라우터 네임스페이스(`vp-ra`, `vp-rb`, `vp-rc`)와 서버 네임스페이스 하나씩을 두고, 라우터끼리 veth로 피어링 링크를 만들었다. 리눅스 라우터는 받으면 넘겨 주는 게 기본이라, AWS의 "피어링끼리는 넘기지 않는다"는 규칙을 B 라우터의 FORWARD 규칙 두 줄로 흉내 냈다.

```bash
# B 라우터: 피어링에서 들어와 다른 피어링으로 나가는 패킷은 버린다 (AWS 규칙을 흉내)
sudo ip netns exec vp-rb iptables -A FORWARD -i pcx-ba -o pcx-bc -j DROP
sudo ip netns exec vp-rb iptables -A FORWARD -i pcx-bc -o pcx-ba -j DROP
# A에서 C로 가는 경로가 아직 없을 때
sudo ip netns exec vp-a1 ping -c2 -W1 10.2.1.10
```

```text

From 10.0.1.1 icmp_seq=2 Destination Net Unreachable
```

경로가 없으니 A의 라우터(`10.0.1.1`)가 바로 "망에 닿을 수 없다"고 답했다. 이제 처음 장면처럼 A의 테이블에 C 대역을 B 쪽 피어링으로 넣는다.

```bash
# A 라우터에 C 대역을 B 쪽 피어링으로 넣는다 (처음 장면의 시도)
sudo ip netns exec vp-ra ip route add 10.2.0.0/16 via 169.254.10.2
sudo ip netns exec vp-a1 ping -c2 -W1 10.2.1.10
# B 라우터에서 버려진 패킷 수
sudo ip netns exec vp-rb iptables -L FORWARD -v -n
```

## 대역이 겹치면 다리를 놓을 자리가 없다

D가 A와 같은 `10.0.0.0/16`이면 피어링 요청 자체가 실패한다. AWS가 겹치는 대역끼리의 피어링을 허용하지 않는다. 허용한다 해도 쓸 수가 없다. A의 라우트 테이블에서 `10.0.0.0/16`은 이미 `local`이라 D로 보낼 경로를 둘 자리가 없기 때문이다. 모형에서 B에 D 쪽 경로를 같은 대역으로 하나 더 넣어 보면 리눅스도 거절한다.

```bash
# B 라우터에 10.0.0.0/16을 다른 방향으로 하나 더 넣으려 하면
sudo ip netns exec vp-rb ip route add 10.0.0.0/16 via 169.254.11.2
```

```text
RTNETLINK answers: File exists
```

같은 목적지에 두 길이 있으면 어느 쪽인지 고를 수 없다. 대역이 일부만 겹쳐도(예: `10.0.0.0/8`과 `10.20.0.0/16`) 겹치는 구간은 최장 일치 때문에 한쪽으로만 간다. 그래서 VPC를 만들 때 회사 전체의 대역 표를 보고 겹치지 않게 고른다. 대역 목록을 받아 겹치는 쌍을 찾는 함수를 직접 짜 보자. 결과는 겹치는 두 항목의 인덱스 쌍 목록이다.

  const toInt = (a) => a.split(".").reduce((n, o) => n * 256 + Number(o), 0);
  const range = (c) => {
    const [net, len] = c.split("/");
    const size = 2 ** (32 - Number(len));

    return [start, start + size - 1];

    for (let j = i + 1; j < cidrs.length; j++) {

      const [b1, b2] = range(cidrs[j]);
      if (a1 <= b2 && b1 <= a2) out.push([i, j]);
    }
  }
  return out;
}`}

## VPC가 많아지면 다리 대신 허브: Transit Gateway

피어링은 전이되지 않으니 VPC가 n개면 서로 다 이으려면 n(n-1)/2개가 필요하다. 5개면 10개, 10개면 45개, 20개면 190개다. 피어링마다 양쪽 라우트 테이블에 경로를 넣어야 하니 관리할 줄 수는 훨씬 많다. VPC당 피어링 할당량도 기본 50개(최대 125개)라 언젠가 막힌다.

Transit Gateway(TGW)는 리전 안의 허브 라우터다. VPC, VPN, Direct Connect를 각각 하나의 연결(attachment)로 TGW에 붙이면, TGW가 자기 라우트 테이블을 보고 연결 사이로 패킷을 넘긴다. 피어링과 달리 전이가 된다. 그게 목적이니까. VPC가 n개여도 연결은 n개다.

TGW의 라우트 테이블은 두 가지 설정으로 움직인다.

- 연결(association): 이 attachment에서 들어온 패킷은 어느 TGW 라우트 테이블을 볼까. attachment 하나는 테이블 하나에 연결된다.
- 전파(propagation): 이 attachment의 대역을 어느 테이블에 자동으로 적어 넣을까.

이 둘을 나눠 쓰면 망을 쪼갤 수 있다. prod와 dev가 공용(shared) VPC에는 닿되 서로는 못 닿게 하려면, prod와 dev attachment가 보는 테이블에는 shared 대역만 전파하고, shared가 보는 테이블에는 모두를 전파한다. 아래 그림에서 다음을 누르면 이 분리가 패킷 단위로 보인다.

모형에서는 TGW 네임스페이스에 attachment마다 veth를 하나씩 두고, `ip rule iif`로 attachment별 테이블을 고르게 했다. 서브넷별 라우트 테이블을 만들 때와 같은 방법이다.

```bash
# prod(att-a)와 dev(att-c)는 shared 대역만 아는 테이블을, shared(att-b)는 전부 아는 테이블을 본다
sudo ip netns exec vp-tgw ip route add 10.1.0.0/16 via 169.254.21.2 table 210   # rtb-prod
sudo ip netns exec vp-tgw ip route add 10.1.0.0/16 via 169.254.21.2 table 230   # rtb-dev
sudo ip netns exec vp-tgw ip rule add iif att-a table 210 pref 100
sudo ip netns exec vp-tgw ip rule add iif att-b table 200 pref 101
sudo ip netns exec vp-tgw ip rule add iif att-c table 230 pref 102
sudo ip netns exec vp-tgw ip rule
```

```text
0:	from all lookup local
100:	from all iif att-a lookup 210
101:	from all iif att-b lookup 200
102:	from all iif att-c lookup 230
32766:	from all lookup main
32767:	from all lookup default
```

prod 서버에서 shared와 dev를 차례로 찔러 보고, TGW에게 직접 경로를 물어본다.

```bash
# prod → shared
sudo ip netns exec vp-a1 ping -c1 -W1 10.1.1.10
# prod → dev
sudo ip netns exec vp-a1 ping -c2 -W1 10.2.1.10
# TGW가 prod attachment에서 들어온 패킷의 경로를 어떻게 고르는지
sudo ip netns exec vp-tgw ip route get 10.2.1.10 from 10.0.1.10 iif att-a
sudo ip netns exec vp-tgw ip route get 10.1.1.10 from 10.0.1.10 iif att-a
```

```text

PING 10.2.1.10 (10.2.1.10) 56(84) bytes of data.

10.1.1.10 from 10.0.1.10 via 169.254.21.2 dev att-b table 210

```

`table 210`에는 dev 대역이 없으니 `Network is unreachable`이다. AWS의 TGW도 맞는 경로가 없으면 패킷을 버린다. TGW 라우트 테이블에는 일부러 버리는 blackhole 경로도 넣을 수 있어서, 넓은 대역을 전파받더라도 특정 구간만 확실히 막을 수 있다.

TGW는 공짜가 아니다. attachment마다 시간당 요금(us-east-1 기준 0.05달러)과 처리한 데이터 GB당 요금(0.02달러)이 붙는다. 같은 AZ 안의 피어링 트래픽은 전송 요금이 없으니, 트래픽이 아주 많은 두 VPC는 TGW와 별개로 피어링을 하나 더 두는 설계도 흔하다. 피어링 경로와 TGW 경로가 함께 있으면 더 구체적인 쪽이 이기니, 대역을 같은 크기로 넣었는지 확인해야 한다.

한 가지 더. TGW 뒤에 상태를 기억하는 방화벽 장비를 여러 AZ에 두면, 요청은 AZ a의 방화벽으로, 응답은 AZ c의 방화벽으로 가서 버려지는 일이 생긴다. 방화벽 VPC의 attachment에 어플라이언스 모드(appliance mode)를 켜면 한 흐름의 양방향이 같은 AZ로 가도록 맞춰 준다.

## 망을 잇지 않고 서비스 하나만 내놓기: PrivateLink

D 회사의 문제로 돌아가자. 대역이 겹치니 피어링도 TGW도 안 된다. 그런데 D가 필요한 건 A의 망 전체가 아니라 A의 결제 API 하나다. PrivateLink는 이럴 때 쓴다.

- 서비스 제공자(A)는 서비스 앞에 NLB(네트워크 로드 밸런서)를 두고 엔드포인트 서비스로 등록한다.
- 소비자(D)는 자기 서브넷에 인터페이스 엔드포인트를 만든다. 그러면 D의 서브넷에 ENI가 하나 생기고, D 대역의 사설 IP를 받는다.
- D의 서버는 그 ENI의 IP(또는 DNS 이름)로 요청한다. AWS가 그 연결을 A의 NLB로 넘기고, NLB가 A의 서버로 보낸다.

라우팅이 아니라 연결을 대신 이어 주는 방식이라 대역이 겹쳐도 상관없다. D는 A의 대역을 알 필요가 없고 A도 D의 대역을 모른다. 방향도 한쪽뿐이다. 소비자만 연결을 시작할 수 있고 제공자는 소비자 망으로 먼저 들어갈 수 없다. Datadog이나 Snowflake 같은 SaaS가 고객 VPC에 사설 연결을 제공할 때 쓰는 방법이 이것이다.

## 셋 중 무엇을 고르나

결정은 "무엇을 잇고 싶은가"에서 시작한다.

- VPC 두세 개를 망 대 망으로 잇고, 대역이 겹치지 않는다: 피어링. 장비가 없어 대역폭 걱정이 없고, 같은 AZ 안의 트래픽은 전송 요금도 없다. 같은 리전이면 상대 VPC의 보안 그룹 ID를 규칙에 쓸 수도 있다.
- VPC가 열 개를 넘어가거나, VPN·Direct Connect로 사내망까지 한곳에 모아야 한다: Transit Gateway. 라우트 테이블로 망을 나누고 중앙 방화벽을 둘 수 있다. 대신 attachment와 데이터 처리 요금이 붙는다.
- 망 전체가 아니라 서비스 하나만 내놓고 싶다, 대역이 겹친다, 상대가 다른 회사다: PrivateLink. 한 방향이고 서비스 단위라 노출 범위가 가장 좁다.

규모로 보면 대체로 이렇게 흘러간다. VPC 두세 개일 때는 피어링으로 시작한다. 피어링 수가 VPC 수보다 빠르게 늘어나고 라우트 테이블 관리가 버거워지면 TGW로 옮긴다. 회사 밖과 이어야 하거나 대역 정리를 할 수 없는 상대는 처음부터 PrivateLink로 간다. 서비스 단위 연결을 HTTP 수준에서 더 세밀하게 관리하려면 VPC Lattice 같은 서비스 네트워크 제품도 있는데, 이건 [서비스 메시](/posts/service-mesh)와 비슷한 문제를 클라우드 쪽에서 푸는 방식이다.

## 연결했는데 안 통할 때 보는 순서

VPC끼리 이었는데 timeout이 나면 이 순서로 본다.

1. 연결 상태: 피어링이 `active`인지, TGW attachment가 `available`인지, 엔드포인트가 `available`(제공자 수락이 필요한 서비스면 `pendingAcceptance`가 아닌지)인지.
2. 양쪽 VPC 라우트 테이블: 출발 서브넷과 도착 서브넷 테이블에 상대 대역이 들어 있는지. 한쪽만 넣는 실수가 가장 흔하다.
3. TGW 라우트 테이블: attachment가 어느 테이블에 연결되어 있고, 그 테이블에 목적지 대역이 전파되어 있는지.
4. 보안 그룹과 NACL: 도착 쪽 인바운드가 출발 대역을 허용하는지. NACL은 응답용 임시 포트까지 열려 있는지([보안 그룹과 NACL 글](/posts/security-groups-nacl)).
5. DNS: 엔드포인트를 쓰는데 서비스 이름이 공인 IP로 풀린다면 사설 DNS 설정을 본다.

```bash
# 피어링 상태와 양쪽 대역을 한 번에 본다
aws ec2 describe-vpc-peering-connections \
  --vpc-peering-connection-ids pcx-0ab12cd34ef567890 \
  --query 'VpcPeeringConnections[].{Status:Status.Code,Requester:RequesterVpcInfo.CidrBlock,Accepter:AccepterVpcInfo.CidrBlock}'
```

```text
[
    {
        "Status": "active",
        "Requester": "10.0.0.0/16",
        "Accepter": "10.1.0.0/16"
    }
]
```

(예시 출력이다. 형식은 AWS CLI v2와 같다.) 상태가 `active`인데도 안 되면 2번 이후를 본다. 실제로 패킷이 어디서 버려지는지는 양쪽 ENI의 [흐름 로그](/posts/network-flow-logs)에서 REJECT가 찍히는 쪽을 찾으면 된다.

## 다시 처음 장면으로

A에서 C로 가는 패킷이 사라진 건 피어링이 전이되지 않아서 B가 넘겨 주지 않았기 때문이다. A–C 피어링을 하나 더 맺거나, VPC가 계속 늘어날 거라면 Transit Gateway로 허브를 만든다. A와 대역이 똑같은 D는 라우팅으로는 이을 수 없으니, D가 필요한 결제 API만 PrivateLink로 내놓는다. 망을 잇는 일은 결국 "누가 누구의 대역을 알아야 하나"를 정하는 일이다. 피어링과 TGW는 서로의 대역을 알게 하고, PrivateLink는 몰라도 되게 한다.

## 면접에서 나올 만한 질문

### VPC 피어링은 왜 전이되지 않나요? 그러면 어떻게 하나요?

피어링은 두 VPC의 라우트 테이블이 서로의 대역을 아는 직접 연결일 뿐이고, 가운데 VPC가 다른 피어링으로 패킷을 넘겨 주지 않게 설계되어 있다. 같은 이유로 상대 VPC의 NAT, IGW, VPN도 빌려 쓸 수 없다. A와 C가 통해야 하면 A–C 피어링을 추가하거나 Transit Gateway 같은 허브로 옮긴다.

### 피어링을 수락했는데 통신이 안 됩니다. 무엇이 빠졌을까요?

수락은 연결을 만들 뿐이고 경로는 직접 넣어야 한다. 양쪽 VPC의 해당 서브넷 라우트 테이블에 상대 대역 → pcx 경로가 있는지 보고, 한쪽만 있으면 응답이 돌아오지 못해 timeout이 난다. 그다음 도착 쪽 보안 그룹과 NACL이 출발 대역을 허용하는지 본다.

### 대역이 겹치는 두 VPC를 연결해야 하면 어떻게 하나요?

피어링과 Transit Gateway는 라우팅이라 겹치는 대역 사이를 이을 수 없다. 필요한 게 특정 서비스라면 PrivateLink로 제공자 쪽 NLB를 엔드포인트 서비스로 내놓고, 소비자 VPC에 인터페이스 엔드포인트를 만든다. 망 전체가 필요하면 한쪽 대역을 바꾸거나 중간에 NAT를 두는 방법뿐이라 비용이 크다. 그래서 처음부터 대역 표를 관리한다.

### Transit Gateway에서 prod와 dev를 서로 못 닿게 하려면 어떻게 하나요?

TGW 라우트 테이블을 나누고 연결과 전파를 따로 설정한다. prod와 dev attachment가 보는 테이블에는 shared 대역만 전파하고, shared가 보는 테이블에는 모두를 전파한다. 그러면 prod에서 dev로 가는 경로가 TGW 테이블에 없어 버려지고, 확실히 하려면 blackhole 경로를 넣는다.

### 피어링과 Transit Gateway 중 무엇을 고르나요?

VPC가 몇 개 안 되고 트래픽이 많으면 피어링이 싸고 단순하다. 장비가 없어 대역폭 한도가 없고 같은 AZ 트래픽은 전송 요금도 없다. VPC가 많아져 n(n-1)/2개 연결 관리가 버거워지거나 VPN과 사내망까지 한곳에 모아야 하면 TGW로 간다. TGW는 attachment와 GB당 요금이 붙으니 트래픽이 큰 쌍은 피어링을 따로 두기도 한다.

### PrivateLink를 쓰면 제공자 서버에 보이는 출발지 IP는 무엇인가요?

제공자 쪽 NLB의 사설 IP가 보인다. 소비자의 실제 주소나 대역은 전달되지 않는다. 어느 소비자에서 왔는지 구분하려면 NLB에서 프록시 프로토콜 v2를 켜고 엔드포인트 ID 정보를 읽는다.

### 인터페이스 엔드포인트를 만들었는데 트래픽이 여전히 NAT로 나갑니다. 왜 그럴까요?

사설 DNS가 꺼져 있거나 VPC의 DNS 속성이 꺼져 있어서 서비스 이름이 여전히 공인 IP로 풀리는 경우가 대부분이다. 엔드포인트의 사설 DNS를 켜고 VPC의 enableDnsSupport와 enableDnsHostnames를 둘 다 켠다. VPC 안에서 dig로 서비스 이름이 엔드포인트 ENI의 사설 IP로 풀리는지 확인한다.
