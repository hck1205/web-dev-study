상품 42번 가격을 39,000원에서 35,000원으로 내렸다. 상품 상세 페이지에는 새 가격이 바로 떴다. 그런데 신발 카테고리 목록에는 한참 옛 가격이 보였고, 앱 서버 세 대 중 한 대는 계속 39,000원을 돌려줬다. 캐시를 지우는 코드는 분명히 돌았다.

캐시를 지우는 명령은 한 줄이다. 어려운 건 그 한 줄을 어디에 보내야 하는지 아는 것이다. 가격 하나는 CDN의 상품 페이지, 카테고리 목록, 메인 페이지, 앱 서버마다 있는 로컬 캐시, Redis에 각각 사본으로 퍼져 있다. 이 글은 그 사본들을 지우는 방법(퍼지, ban, 태그, 버전), 변경을 사본들에 알리는 방법(TTL과 이벤트), 그리고 지운 직후 옛 값이 다시 들어오는 경쟁을 직접 재현하고 막는다. 실습은 Ubuntu 24.04에서 Varnish 7.1, Redis 7.0, PostgreSQL 16, Node 22로 했다.

이 주제의 다른 글: 캐시를 언제 채우고 쓰기 때 지울지 고칠지, 지연 이중 삭제와 CDC 같은 기본기는 [캐시 전략](/posts/caching-strategies)에서 다뤘다. 이 글은 그 다음 질문, 사본이 여러 곳에 있을 때 변경을 어떻게 모두에게 전하는지를 본다. CDN의 캐시 키와 상한 사본은 [엣지 캐싱](/posts/edge-caching)에, HTTP 캐시 헤더는 [HTTP 캐시와 CDN](/posts/http-caching-cdn)에 있다.

## 주소 하나를 지우는 퍼지

Varnish로 엣지를 세우고 지우는 방법을 차례로 비교했다. 오리진은 상품과 카테고리 JSON을 `s-maxage=300`으로 보내고, 응답마다 어떤 데이터가 들어 있는지를 태그로 붙인다(`Surrogate-Key` 헤더, 뒤에서 쓴다).

```vcl
sub vcl_recv {
  if (req.method == "PURGE") {                  # 정확히 이 URL 하나를 지운다
    if (client.ip !~ purgers) { return (synth(405)); }
    return (purge);
  }
  if (req.method == "BAN") {                    # 조건에 맞는 사본을 모두 무효로 표시한다
    if (client.ip !~ purgers) { return (synth(405)); }
    if (req.http.X-Ban-Url) {
      ban("obj.http.x-url ~ " + req.http.X-Ban-Url);
    } else if (req.http.X-Ban-Tag) {
      ban("obj.http.Surrogate-Key ~ (^|\s)" + req.http.X-Ban-Tag + "($|\s)");
    }
    return (synth(200, "Ban added"));
  }
}
sub vcl_backend_response {
  set beresp.http.x-url = bereq.url;            # ban 조건에 쓰려고 URL을 사본에 적어 둔다
}
```

상품 셋과 카테고리 둘을 데워 둔 뒤 오리진에서 42번 가격만 바꿨다. 출력은 경로, 엣지 캐시 상태, 응답 본문이다.

```bash
# 오리진의 가격만 바꾸고(무효화 없음) 다시 읽는다
curl -s "127.0.0.1:19442/__set?id=42&price=35000"
# 상품 주소 하나를 퍼지하고 다시 읽는다
curl -s -X PURGE http://127.0.0.1:19441/product/42
```

```text
# 2. 오리진에서 42번 가격 변경 (무효화 없음)
/product/42        HIT   {"id":42,"price":39000}
/category/shoes    HIT   [{"id":42,"price":39000},{"id":43,"price":52000}]
# 3. PURGE /product/42
200
/product/42        MISS  {"id":42,"price":35000}
/category/shoes    HIT   [{"id":42,"price":39000},{"id":43,"price":52000}]
```

퍼지(purge)는 정확히 그 키의 사본을 즉시 지운다. 상품 페이지는 새 가격이 됐다. 하지만 같은 가격을 담은 카테고리 목록은 여전히 39,000원이다. 처음 장면의 "상세는 새 가격, 목록은 옛 가격"이 이것이다. 퍼지는 빠르고 정확하지만, 지울 주소 목록을 호출하는 쪽이 전부 알아야 한다. 상품 하나가 목록 페이지 수십 장과 검색 결과에 들어 있다면 그 목록을 만드는 일 자체가 어렵다.

## 조건으로 지우는 ban

Varnish의 ban은 "이 조건에 맞는 사본은 이제 쓰지 마라"는 규칙을 목록에 올린다. 사본을 그 자리에서 찾아 지우지 않는다. 요청이 사본을 찾을 때 그 사본이 ban보다 오래됐으면 조건과 대조해서, 맞으면 버리고 오리진에서 새로 받는다. 그래서 수백만 개의 사본이 있어도 ban 추가는 즉시 끝난다.

```bash
# 관리 포트로 ban 목록 보기, URL 조건으로 ban 걸기
varnishadm -T 127.0.0.1:19449 -S secret ban.list
varnishadm -T 127.0.0.1:19449 -S secret "ban req.url ~ ^/category/"
```

```text
Present bans:
1792528482.594686     0 -  req.url ~ ^/category/
1792528470.408135     4 -  obj.http.Surrogate-Key ~ (^|\s)product-42($|\s)
1792528459.549402     1 C
```

ban 조건이 무엇을 보는지에 따라 처리 방식이 갈린다. `obj.http.*`(사본에 저장된 헤더)만 보는 조건은 Varnish의 ban lurker가 뒤에서 사본들을 훑으며 미리 처리할 수 있다. 위 VCL이 URL을 `x-url` 헤더로 사본에 적어 두는 이유가 이것이다. `req.url`처럼 요청을 봐야 하는 조건은 lurker가 평가할 수 없어서, 사본이 요청될 때까지 목록에 남는다. 1분 뒤 목록을 다시 봤다.

```text
# 60초 뒤
Present bans:
1792528482.594686     0 -  req.url ~ ^/category/
1792528470.408135     5 C
```

`obj.http` 조건의 ban은 lurker가 처리를 끝내 완료(C)로 바뀌었다. lurker는 `ban_lurker_age`(기본 60초)보다 오래된 ban만 처리한다. `req.url` 조건은 그대로 남았다. 목록이 길어지면 요청마다 대조할 조건이 늘어 느려지니, ban 조건은 lurker가 처리할 수 있는 `obj.*` 형태로 쓴다.

ban의 강점은 지울 주소 목록 없이 "카테고리 페이지 전부", "이 패턴의 이미지 전부"처럼 묶어서 지울 수 있다는 것이다. 약점은 조건이 넓을수록 필요 없는 사본까지 지워 오리진에 미스가 몰린다는 것이다.

CDN마다 같은 기능이 있다. Fastly는 `Surrogate-Key`로 키 단위 퍼지를 하고, 사본을 지우는 대신 상한 상태로 표시하는 soft purge도 준다. Cloudflare는 `Cache-Tag`, Akamai는 `Edge-Cache-Tag` 헤더를 쓴다(요금제에 따라 쓸 수 있는지가 다르다). Varnish는 정규식 ban 대신 태그 색인을 두는 xkey 모듈을 많이 쓴다. CloudFront의 무효화는 경로 단위라서 태그처럼 쓰려면 경로를 설계로 맞춘다. Next.js의 `revalidateTag`도 같은 생각을 프레임워크 안으로 가져온 것이다.

## 지울 필요를 없애는 버전

지우는 대신 이름을 바꾸는 방법도 있다. 정적 파일 이름에 내용 해시를 넣거나(`main.3f9c2b1e.css`), 캐시 키에 스키마 버전을 넣는 방법은 [HTTP 캐시와 CDN](/posts/http-caching-cdn)과 [캐시 전략](/posts/caching-strategies)에서 다뤘다. 바뀐 내용은 새 이름으로 받으니 옛 사본은 아무도 안 읽다가 수명이 끝나 사라진다. 지우기가 실패할 일도, 전파 시간도 없다.

같은 생각을 데이터 묶음에 쓰면 세대 번호가 된다. 카테고리 목록 캐시가 페이지마다 따로 있을 때, 키에 세대 번호를 넣고 무효화할 때는 번호만 올린다.

```bash
# 카테고리의 세대 번호를 두고 목록 캐시 키에 넣는다
redis-cli SET gen:category:shoes 1
redis-cli SET "cache:g1:category:shoes:page:1" '[42,43]' EX 300
redis-cli SET "cache:g1:category:shoes:page:2" '[51,52]' EX 300
# 카테고리 전체 무효화: 키를 찾아 지우지 않고 세대 번호만 올린다
redis-cli INCR gen:category:shoes
# 읽는 쪽은 세대 번호를 먼저 읽고 새 키를 만든다
redis-cli EXISTS "cache:g2:category:shoes:page:1"
redis-cli TTL "cache:g1:category:shoes:page:1"
```

```text
OK
OK
OK
2
0
300
```

`INCR` 한 번으로 페이지가 몇 장이든 모두 무효가 됐다. 새 세대의 키는 아직 없으니(0) 다음 읽기가 새로 채우고, 옛 세대 키는 아무도 안 읽다가 300초 뒤 사라진다. `SCAN`으로 키를 찾아 지우는 것보다 빠르고 원자적이다. 대가는 읽을 때마다 세대 번호를 한 번 더 읽는 왕복이고, 옛 세대 사본이 TTL까지 메모리를 차지한다는 것이다.

## TTL에 맡길까, 변경을 알릴까

모든 무효화는 두 갈래 중 하나다. 수명(TTL)이 끝나기를 기다리거나, 변경이 생길 때 사본에 알리는 것이다. TTL은 아무것도 안 해도 되고 실패할 일이 없지만, 수명만큼 옛 값이 보인다. 알리기는 즉시 맞출 수 있지만, 알림이 빠지면 그 사본은 수명이 끝날 때까지 틀린 값을 들고 있다. 그래서 실무에서는 둘을 같이 쓴다. 알리기로 평소의 지연을 줄이고, TTL로 알림이 빠졌을 때의 피해 상한을 정한다.

앱 서버마다 둔 로컬 캐시가 알리기의 약점을 가장 잘 보여 준다. 앱 서버 세 대(a, b, c)가 상품을 60초 동안 프로세스 메모리에 두고, 가격이 바뀌면 Redis의 `invalidate` 채널로 키 이름을 발행하게 했다. 각 서버는 그 채널을 구독하다가 메시지를 받으면 자기 로컬 사본을 지운다. 발행과 구독의 기본은 [발행 구독](/posts/pub-sub) 글에 있다.

```bash
# 가격을 바꾸고 무효화를 발행한다. PUBLISH는 메시지를 받은 구독자 수를 돌려준다
curl -s "127.0.0.1:19442/__set?id=42&price=35000"
redis-cli -p 19450 PUBLISH invalidate product:42
```

```text
3
{"from":"a db","id":42,"price":35000}
{"from":"b db","id":42,"price":35000}
{"from":"c db","id":42,"price":35000}
```

세 대 모두 받았고(3), 다음 읽기에서 DB의 새 가격을 가져왔다. 이번에는 c가 잠깐 멈춘 사이 구독 연결이 끊긴 상황을 만들었다. GC 멈춤이나 네트워크 순단으로 흔히 생긴다.

```bash
# c 프로세스를 멈추고, 그 구독 연결을 끊고, 그사이 가격 변경과 발행
kill -STOP $C_PID
redis-cli -p 19450 CLIENT KILL ID 5
curl -s "127.0.0.1:19442/__set?id=42&price=31000"
redis-cli -p 19450 PUBLISH invalidate product:42
kill -CONT $C_PID
```

```text
1
2
{"from":"a db","id":42,"price":31000}
{"from":"b db","id":42,"price":31000}
{"from":"c local","id":42,"price":33000}
```

이번에는 c도 새 가격을 가져왔다. 메시지를 놓쳤을 수 있는 순간(연결이 끊겼다 붙은 순간)에 가진 것을 모두 버린 것이다. Redis 6부터 있는 클라이언트 측 캐싱(`CLIENT TRACKING`)도 같은 원칙을 쓴다. 서버가 클라이언트가 읽은 키를 기억해 두었다가 바뀌면 알려 주는데, 연결이 끊기면 클라이언트 라이브러리가 로컬 캐시를 비운다. 메시지가 꼭 도착해야 한다면 쌓이는 전달 방식(Redis Streams, Kafka)을 쓰고, DB 변경 로그를 읽어 무효화를 만드는 CDC를 쓰면 응용 코드가 발행을 빠뜨리는 일도 없어진다([캐시 전략](/posts/caching-strategies)). 어느 쪽이든 로컬 캐시의 TTL은 남겨 둔다. 그게 모든 알림이 실패했을 때의 상한이다.

## 지운 직후 옛 값이 다시 들어온다

알림이 제대로 도착해도 틀린 값이 남는 경우가 있다. 읽기 A가 캐시 미스를 보고 DB에서 옛 값을 읽은 뒤 잠깐 멈춘 사이, 쓰기 B가 DB를 고치고 캐시를 지운다. A가 깨어나 들고 있던 옛 값을 캐시에 넣는다. 이 경쟁의 원리는 [캐시 전략](/posts/caching-strategies) 글에 그림으로 있으니, 여기서는 PostgreSQL과 Redis로 직접 일으키고 다른 방법으로 막는다.

```bash
# A: GET 미스 → SELECT → 300ms 멈춤 → SET / B: 100ms 뒤 UPDATE → DEL
node race.js plain
```

```text
  95ms A GET cache -> null
 101ms A SELECT -> price=39000 version=1
 197ms B UPDATE price=35000 COMMIT
 198ms B DEL cache
 401ms A (300ms 멈춤: GC, 직렬화, 느린 네트워크)
 403ms A SET cache {"price":39000,"version":1}
 404ms = DB price=35000 v2 | cache {"price":39000,"version":1} (TTL 300s)
```

B는 할 일을 다 했다. DB를 고치고 캐시를 지웠다. 그런데 DB는 35,000원, 캐시는 39,000원이고 앞으로 300초 동안 그대로다. B의 삭제가 A의 채우기보다 먼저 일어났기 때문이다.

막는 방법으로 리스(lease)를 썼다. 페이스북이 memcache를 대규모로 운영하며 쓴 방법으로 알려져 있다. 미스가 나면 채울 권리를 나타내는 토큰을 먼저 받아 두고, 채울 때 그 토큰이 아직 살아 있을 때만 값을 넣는다. 쓰기는 캐시와 함께 토큰도 지운다. 그러면 삭제보다 먼저 시작된 채우기는 토큰을 잃어 거절된다.

```js
// 채우기: 토큰이 그대로일 때만 SET (Lua로 원자적으로)
const FILL = `if redis.call('GET', KEYS[2]) == ARGV[1] then
  redis.call('SET', KEYS[1], ARGV[2], 'EX', 300); redis.call('DEL', KEYS[2]); return 1
else return 0 end`;
// 미스 때: SET lease:product:42 <token> NX PX 5000
// 쓰기 때: DEL cache:product:42 lease:product:42
```

```text
  73ms A GET cache -> null
  74ms A SET lease 64444980 NX -> OK
  78ms A SELECT -> price=39000 version=1
 177ms B UPDATE price=35000 COMMIT
 178ms B DEL cache + lease
 378ms A (300ms 멈춤: GC, 직렬화, 느린 네트워크)
 383ms A fill with lease -> rejected (lease gone)
 386ms = DB price=35000 v2 | cache null (TTL -2s)
```

A의 채우기가 거절됐고 캐시는 비어 있다. 다음 읽기가 새 값 35,000원으로 채운다. 이 실험을 단계별로 다시 보면 이렇다.

비슷한 다른 방법은 지우는 대신 버전이 든 묘비(tombstone)를 남기는 것이다. B가 `DEL` 대신 "버전 2부터 유효"라는 표시를 넣고, 채우기는 자기가 읽은 버전이 그보다 낮으면 거절한다. 그냥 `DEL`한 키에는 버전을 비교할 대상이 없으니, 버전 비교만으로는 이 경쟁을 막지 못한다는 점이 함정이다. 두 방법 모두 Redis 왕복이 하나 늘고 Lua 스크립트를 관리해야 하니, 값이 잠깐 틀려도 되는 데이터라면 짧은 TTL과 지연 이중 삭제로 충분하다.

## CDN 퍼지가 복제본보다 빠를 때

엣지에서도 같은 경쟁이 일어난다. 오리진이 읽기 전용 복제본에서 값을 읽는데, 쓰기가 복제본에 반영되기까지 500ms가 걸린다고 하자. 배포 스크립트는 가격을 고치자마자 퍼지를 보낸다.

```bash
# 가격 변경(복제본 반영 500ms 지연) 직후 PURGE, 100ms 뒤 사용자 요청
curl -s "127.0.0.1:19442/__set?id=44&price=15000&lag=500"
curl -s -X PURGE http://127.0.0.1:19441/product/44
```

```text
20:37:34.771 GET /product/44 MISS Age: 0 {"id":44,"price":18000}
20:37:34.820 GET /product/44 HIT Age: 0 {"id":44,"price":18000}
# 가격 변경(복제본 반영 500ms 지연) 직후 PURGE
20:37:34.892 PURGE 200
20:37:35.035 GET /product/44 MISS Age: 0 {"id":44,"price":18000}
20:37:36.118 GET /product/44 HIT Age: 1 {"id":44,"price":18000}
{"id":44,"price":15000} <- origin now
```

퍼지는 성공했다. 그런데 퍼지 직후 들어온 요청이 MISS로 오리진에 갔고, 아직 반영이 안 된 복제본에서 옛 가격 18,000원을 받아 엣지에 다시 저장했다. 1초 뒤 오리진은 15,000원인데 엣지는 18,000원을 HIT로 준다. 이 사본은 `s-maxage=300`이 끝날 때까지 남는다. 퍼지가 너무 빨랐다.

```text
20:37:44.232 PURGE (2nd, delayed) 200
20:37:44.277 GET /product/44 MISS Age: 0 {"id":44,"price":15000}
20:37:44.319 GET /product/44 HIT Age: 0 {"id":44,"price":15000}
```

복제가 끝난 뒤 한 번 더 퍼지하자 새 가격이 들어갔다. 실무에서는 퍼지를 "커밋 직후"가 아니라 "오리진이 새 값을 줄 수 있게 된 뒤"에 보낸다. 복제본의 변경 이벤트(CDC)를 받아 퍼지하거나, 복제 지연보다 넉넉한 시간 뒤에 한 번 더 퍼지하거나, 퍼지 직후 오리진이 새 값을 돌려주는지 확인하는 단계를 둔다.

CDN이 크면 퍼지 자체에도 시간이 걸린다. 전 세계 엣지에 명령이 퍼지는 동안 어떤 엣지는 새 값을, 어떤 엣지는 옛 값을 준다. 아래 그림에서 다음을 누르면 퍼지가 엣지마다 다른 시각에 도착하는 모습이 보인다.

전파 시간은 CDN마다 크게 다르다. Fastly와 Cloudflare는 전 세계 퍼지가 1초 안쪽에 끝난다고 내세우고, CloudFront 무효화는 몇 분 안쪽에 반영된다(각 사 문서 기준이고 상황에 따라 다르다). 몇 분이 걸리는 CDN이라면 무효화에 기대는 설계보다 버전이 든 주소가 낫다. 그리고 퍼지가 모든 엣지에서 동시에 일어나면 그 순간 모든 엣지의 미스가 오리진에 몰린다. 인기 페이지를 지울 때는 오리진 실드와 요청 병합이 켜져 있는지([엣지 캐싱](/posts/edge-caching)), 아니면 사본을 지우는 대신 상한으로 표시하는 soft purge를 쓸 수 있는지 본다.

## "고쳤는데 안 바뀐다"를 층별로 좁히기

옛 값이 보인다는 문의가 오면, 어느 층의 사본인지부터 찾는다. 바깥에서 안으로 간다.

```bash
# 1) CDN: 캐시 상태와 Age. Age가 크고 HIT면 엣지 사본이다
curl -sI https://example.com/product/42 | grep -iE "x-cache|cf-cache-status|age|surrogate"
# 2) 엣지를 건너뛰고 오리진에 직접 물어본다 (오리진 주소나 캐시 우회 헤더)
curl -s https://origin.example.com/product/42
# 3) Redis 사본과 남은 수명
redis-cli GET cache:product:42
redis-cli TTL cache:product:42
# 4) DB 원본
psql -c "SELECT price, version FROM products WHERE id = 42;"
```

DB는 새 값인데 Redis가 옛 값이면 삭제가 빠졌거나 위의 경쟁이다. Redis가 비어 있는데 앱 응답이 옛 값이면 로컬 캐시다. 앱 서버마다 결과가 다르면 그 서버가 무효화 메시지를 놓쳤다. 오리진은 새 값인데 엣지가 옛 값이면 퍼지 대상이 빠졌거나(목록 페이지), 퍼지가 너무 일렀거나, 아직 전파 중이다. 오리진도 엣지도 새 값인데 사용자만 옛 값이면 브라우저 사본이니 서버에서 할 수 있는 일은 없다.

흔한 실수도 정리해 둔다.

- 커밋 전에 지운다. 지운 직후 읽기가 커밋 전 값을 다시 채운다. 순서는 커밋 다음 삭제다.
- 무효화 메시지 하나에만 기댄다. pub/sub처럼 쌓이지 않는 전달은 빠질 수 있다. TTL을 안전망으로 남기고, 재연결 때 로컬 캐시를 비운다.
- 배포마다 CDN 전체(`/*`)를 퍼지한다. 해시가 든 정적 파일까지 모든 엣지에서 다시 받아 오리진이 튄다.
- 퍼지 대상을 주소로만 생각한다. 같은 데이터가 들어간 목록, 검색, 메인 페이지를 빠뜨린다. 태그로 묶는다.
- 사본이 있는 곳을 문서로 남기지 않는다. 새 로컬 캐시를 추가한 사람이 무효화 경로를 모른다.

## 어려운 건 지우는 일이 아니다

"컴퓨터 과학에서 어려운 건 캐시 무효화와 이름 짓기 두 가지뿐"이라는 오래된 농담이 있다. 직접 해 보면 어려운 부분이 정확히 보인다. 지우는 명령은 한 줄이다. 어려운 건 사본이 어디에 몇 개 있는지 아는 일(태그와 사본 지도), 그 모두에게 빠짐없이 알리는 일(쌓이지 않는 메시지와 재연결), 그리고 지우는 순간과 다시 채우는 순간의 순서(리스, 늦은 퍼지)다. 그래서 무효화는 언제나 TTL이라는 상한과 함께 설계한다. 알림이 모두 실패해도 그 시간이 지나면 맞아진다.

## 면접에서 나올 만한 질문

### 퍼지, ban, 태그 무효화는 어떻게 다른가요?

퍼지는 정확히 한 키의 사본을 즉시 지우고, ban은 조건에 맞는 사본을 앞으로 쓰지 않도록 규칙을 올려 요청 때나 뒤에서 대조하며, 태그 무효화는 응답에 붙인 데이터 태그로 관련 사본을 묶어 지운다. 퍼지는 지울 주소를 호출자가 다 알아야 해서 목록 페이지를 빠뜨리기 쉽다. 실험에서 상품 퍼지 뒤에도 카테고리 목록은 옛 가격이었고, product-42 태그로 지우자 그 상품이 든 페이지만 정확히 다시 받았다.

### 지우는 대신 버전을 바꾸는 방법은 언제 좋나요?

전파 시간이 길거나 지우기가 실패할 수 있는 곳, 그리고 많은 키를 한 번에 무효화해야 할 때 좋다. 해시가 든 정적 파일 이름이나 캐시 키의 세대 번호가 그렇다. 세대 번호는 INCR 한 번으로 페이지가 몇 장이든 모두 무효로 만든다. 대신 읽을 때 버전을 한 번 더 확인해야 하고 옛 사본이 TTL까지 메모리를 차지한다.

### 앱 서버마다 로컬 캐시가 있을 때 무효화는 어떻게 하나요?

변경을 pub/sub 같은 채널로 알려 각 서버가 자기 사본을 지우게 한다. Redis PUBLISH는 그 순간 연결된 구독자에게만 전달되어, 연결이 끊긴 서버는 메시지를 영영 놓친다. 실험에서도 PUBLISH가 2를 돌려줬고 끊겼던 서버는 TTL까지 옛 값을 줬다. 그래서 재연결 때 로컬 캐시를 통째로 비우고, TTL을 안전망으로 남기고, 꼭 도착해야 하면 Streams나 CDC처럼 쌓이는 전달을 쓴다.

### TTL만으로 충분한 경우와 이벤트 무효화가 필요한 경우는 어떻게 가르나요?

데이터가 최악의 경우 얼마나 낡아도 되는지로 가른다. 순위나 추천처럼 1분 늦어도 되는 값은 TTL만으로 충분하다. 가격이나 권한처럼 바뀐 즉시 맞아야 하는 값은 이벤트로 지우되, TTL을 함께 둬서 알림이 실패했을 때의 피해 상한을 정한다. 둘은 고르는 관계가 아니라 같이 쓰는 관계다.

### 캐시를 지웠는데 옛 값이 다시 들어가는 이유와 막는 방법은?

삭제보다 먼저 DB를 읽은 요청이 삭제 뒤에 그 옛 값을 캐시에 넣기 때문이다. PostgreSQL과 Redis로 재현했을 때 DB는 35,000원인데 캐시는 39,000원으로 300초가 남았다. 미스 때 채울 권리 토큰을 받고 쓰기가 토큰까지 지우게 하는 리스를 쓰면 늦게 온 채우기가 거절된다. 버전이 든 묘비를 남기는 방법도 있고, 가벼운 대안은 짧은 TTL과 지연 이중 삭제다.

### CDN 퍼지를 했는데 옛 값이 다시 캐시됐습니다. 왜 그런가요?

퍼지 직후 들어온 요청이 아직 새 값을 모르는 오리진(복제 지연이 있는 읽기 복제본 등)에서 옛 값을 받아 다시 저장했을 가능성이 크다. 실험에서 복제 지연 500ms 안에 퍼지하자 엣지가 옛 가격을 300초짜리 사본으로 다시 들고 있었다. 퍼지는 오리진이 새 값을 줄 수 있게 된 뒤에 보내고, 복제 이벤트로 퍼지하거나 지연된 두 번째 퍼지를 둔다.

### "가격을 바꿨는데 일부 사용자만 옛 가격을 본다"는 문의가 오면 어디부터 보나요?

바깥 층부터 사본을 하나씩 확인한다. CDN 응답의 캐시 상태와 Age, 오리진 직접 응답, Redis 값과 TTL, DB 원본 순서다. 앱 서버마다 결과가 다르면 로컬 캐시가 무효화를 놓친 것이고, 엣지 위치마다 다르면 퍼지 전파 중이거나 퍼지 대상이 빠진 것이다. 서버의 모든 층이 새 값이면 브라우저 캐시라서 서버에서 지울 수 없다.
