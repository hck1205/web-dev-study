기획서에 적힌 건 세 줄이다. "상품 금액 2만 원 이상이면 10% 할인. 최대 5천 원. 세일 상품은 제외." 그리고 메시지가 온다. "쿠폰 기능 테스트 좀 해 주세요. 내일 배포예요."

막막한 건 할 일이 너무 많아서가 아니라, 어디서 멈춰야 할지 몰라서다. 금액만 해도 1원부터 수백만 원까지 있다. 쿠폰을 두 장 쓰면? 결제를 취소하면 쿠폰이 돌아오나? 아이폰 앱에서 간편결제로 새벽배송을 고르면? 다 해 보려면 끝이 없고, 감으로 몇 개 해 보면 "이거 테스트했어요?"라는 질문에 답을 못 한다.

테스트 설계 기법은 이 질문에 답하는 도구다. 무엇을 확인했고 무엇을 일부러 안 했는지, 그 근거가 무엇인지를 말할 수 있게 해 준다. 이 글에서는 같은 쿠폰 기능 하나로 동등 분할, 경계값 분석, 결정 표, 상태 전이, 페어와이즈를 차례로 적용해 실제 케이스를 뽑고, 결과가 맞는지 판정하는 기준(테스트 오라클)과 코드를 보고 빠진 길을 찾는 커버리지까지 본다. 테스트를 어느 층에 얼마나 둘지는 [테스트 피라미드와 단위 테스트](/posts/test-pyramid-unit-tests)에서, 바뀐 코드 앞에서 무엇을 다시 돌릴지는 [스모크, 새니티, 회귀 테스트](/posts/smoke-sanity-regression-testing)에서 다룬다. 예제 코드는 Node 22.22에서 돌렸다.

## 제대로 만들었나, 맞는 걸 만들었나

케이스를 뽑기 전에 질문을 둘로 나눈다. 소프트웨어 공학에서는 이걸 검증(verification)과 확인(validation)이라고 부르고, 배리 보엠(Barry Boehm)이 남긴 한 쌍의 문장으로 흔히 설명한다. 검증은 "제품을 올바르게 만들고 있나(building the product right)", 확인은 "올바른 제품을 만들고 있나(building the right product)"다.

쿠폰으로 말하면, "2만 원 이상에서 10%를 깎고 5천 원에서 멈춘다"를 코드가 지키는지가 검증이다. 명세가 기준이고, 이 글에서 다루는 기법 대부분이 여기에 쓰인다. 확인은 그 명세 자체가 맞는지를 본다. 2만 원이라는 기준 때문에 1만 9천 원어치를 담은 고객이 쿠폰을 못 써서 이탈하고 있다면, 코드가 명세를 완벽히 지켜도 실패다. 확인은 기획 리뷰, 사용자 인수 테스트, 운영 지표로 한다.

QA(Quality Assurance, 품질 보증)라는 말도 여기서 자리를 잡는다. 테스트는 만들어진 것에서 결함을 찾는 활동이고, 품질 관리(QC)는 결과물이 기준을 넘는지 판정하는 활동이다. QA는 그보다 앞에서, 결함이 덜 생기도록 과정을 다듬는 일이다. 명세가 모호한 걸 개발 전에 짚고, 리뷰 기준과 테스트 기준을 정하고, 사고가 나면 같은 종류가 다시 안 나도록 과정을 바꾼다. "QA가 품질을 보증한다"는 말은 QA가 버그를 다 잡는다는 뜻이 아니라, 품질이 우연에 맡겨지지 않게 한다는 뜻이다.

그래서 QA의 사고방식은 "이게 동작하나"보다 "이게 어떻게 깨질 수 있나"에 가깝다. 개발자는 자기 코드가 도는 길을 머릿속에 가지고 있어서, 그 길 위에서만 확인하기 쉽다. 테스트 설계 기법은 그 습관을 깨려고 쓰는 체계적인 방법이다.

## 안을 보느냐 안 보느냐

케이스를 어디서 뽑느냐에 따라 관점이 셋으로 나뉜다.

블랙박스 테스트는 코드를 보지 않는다. 명세와 요구 사항만 보고 입력과 기대 출력을 정한다. 동등 분할, 경계값, 결정 표, 상태 전이, 페어와이즈가 모두 여기에 속한다. 장점은 구현이 바뀌어도 케이스가 그대로 살아남는다는 것, 그리고 명세에 없는 동작(구현에서 빠뜨린 요구)을 찾을 수 있다는 것이다. 코드를 보면 코드에 있는 것만 확인하게 된다.

화이트박스 테스트는 코드 구조를 보고 케이스를 만든다. 모든 분기를 한 번씩 지나가게 하거나, 반복문을 0번·1번·여러 번 돌게 하는 식이다. 명세에는 안 드러나는 구현의 갈림길(캐시가 비었을 때, 재시도 루프)을 확인할 수 있다. 대신 코드에 없는 요구는 원리상 못 찾는다.

그레이박스 테스트는 그 사이다. 내부를 일부 알고 있되, 확인은 바깥 인터페이스로 한다. 예를 들어 쿠폰 사용이 DB에서 이렇게 구현된 걸 안다고 하자.

```sql
-- 쿠폰을 '사용됨'으로 바꾸되, 아직 '발급됨'일 때만 바꾼다
UPDATE coupons
   SET status = 'USED', used_at = now()
 WHERE id = $1 AND status = 'ISSUED';
-- 바뀐 행이 0이면 이미 쓴 쿠폰이다
```

이걸 알면 "같은 쿠폰으로 두 탭에서 동시에 결제하기"라는 케이스가 자연스럽게 나온다. 명세만 봐서는 떠올리기 어렵고, 코드만 봐서는 동시성을 재현할 방법이 안 보인다. 테스트는 API 두 개를 동시에 호출하고, 정확히 하나만 성공하는지, DB의 쿠폰 행이 `USED` 하나인지를 본다. API 테스트, 통합 테스트 대부분이 사실 그레이박스다.

## 같은 결과를 내는 입력은 하나만 고른다

동등 분할(equivalence partitioning)은 입력을 "프로그램이 똑같이 다룰 것으로 기대되는 묶음"으로 나누고, 묶음마다 대표값 하나만 확인한다. 같은 묶음 안의 값은 같은 결함을 함께 드러내거나 함께 숨긴다고 가정하는 것이다.

쿠폰의 주문 금액(원 단위 정수)을 나눠 보자.

| 구역 | 범위 | 기대 동작 | 대표값 |
|---|---|---|---|
| 무효 | 0 이하, 정수가 아님 | 거절(계산하지 않음) | -1000, 1.5 |
| 적용 안 됨 | 1 ~ 19,999 | 할인 0원 | 10,000 |
| 비율 할인 | 20,000 ~ 49,999 | 10%, 원 단위 버림 | 30,000 |
| 상한 | 50,000 이상 | 5,000원 | 80,000 |

여기서 이미 명세의 구멍이 하나 보인다. 기획서에는 "10%"라고만 있고 원 미만을 어떻게 할지가 없다. 23,456원이면 2,345.6원인데, 버림이냐 반올림이냐. 표를 채우다 보면 이런 질문이 저절로 나오고, 그게 동등 분할의 숨은 효과다. 여기서는 버림으로 정했다고 하자.

무효 구역을 따로 두는 것도 중요하다. 유효한 묶음은 여러 개를 한 케이스에 섞어도 되지만, 무효 입력은 케이스 하나에 하나씩만 넣는다. 금액도 음수이고 쿠폰 코드도 틀린 요청을 보내서 에러가 났다면, 어느 쪽 검사가 동작했는지 알 수 없다. 둘 중 하나의 검사가 빠져 있어도 테스트는 통과한다.

## 버그는 경계에 산다

동등 분할의 대표값 30,000원은 잘 동작할 가능성이 높다. 실수는 구역이 바뀌는 자리에서 난다. `>=`를 `>`로 쓰거나, 상한 비교를 할인 전 금액에 하거나, 0을 유효로 보는 식이다. 경계값 분석(boundary value analysis)은 그래서 구역의 가장자리 값을 고른다.

몇 개를 고르냐가 면접 단골이다. ISTQB 강의 계획서는 두 가지를 소개한다. 2값 경계 분석은 경계값과 그 바로 바깥 이웃(다른 구역의 첫 값)을 고른다. 3값 경계 분석은 경계값과 양쪽 이웃을 모두 고른다. 2만 원 경계라면 2값은 19,999와 20,000, 3값은 19,999, 20,000, 20,001이다.

3값이 더 잡는 건 무엇일까. 조건이 `amount >= 20000`이어야 하는데 실수로 `amount == 20000`이라고 썼다면, 19,999(거짓)와 20,000(참)은 두 식에서 결과가 같다. 20,001에서야 차이가 난다. 비교 연산자가 잘못된 경우는 2값으로도 잡히지만, 경계에서만 우연히 맞는 식은 3값이어야 잡힌다. 그래서 금액·한도처럼 돈이 걸린 경계에는 3값을, 덜 중요한 경계에는 2값을 쓰는 식으로 나눠 쓴다.

쿠폰의 경계는 세 곳이다.

- 0과 1: 무효와 유효의 경계
- 19,999와 20,000: 할인이 시작되는 경계
- 49,999, 50,000, 50,001: 상한에 닿는 경계. 50,000원의 10%가 정확히 5,000원이라 여기가 경계다

상한 경계는 명세에 숫자로 적혀 있지 않다. "최대 5천 원"에서 거꾸로 계산해야 나온다. 이런 숨은 경계가 실무에서 자주 빠진다. 날짜(월말, 윤년, 자정을 넘는 주문), 문자열 길이(정확히 최대 길이, 한 글자 초과), 목록 크기(0개, 1개, 페이지 크기와 같은 개수)도 같은 방식으로 찾는다.

날짜 경계는 따로 한 번 더 본다. 쿠폰에 "10월 31일까지"라고 적혀 있고, 개발자가 만료일을 `"2026-10-31"` 문자열로 저장한 뒤 현재 시각의 UTC 날짜와 비교했다고 하자.

```js
// 만료일 "2026-10-31"을 날짜 문자열로만 저장했다
const expiresOn = "2026-10-31";
function isExpired(now) {
  return now.toISOString().slice(0, 10) > expiresOn;   // UTC 날짜로 비교
}
for (const t of ["2026-10-31T23:59:59+09:00", "2026-11-01T00:00:00+09:00",
                 "2026-11-01T08:59:59+09:00", "2026-11-01T09:00:00+09:00"]) {
  console.log(t, isExpired(new Date(t)));
}
```

```text
2026-10-31T23:59:59+09:00 false
2026-11-01T00:00:00+09:00 false
2026-11-01T08:59:59+09:00 false
2026-11-01T09:00:00+09:00 true
```

한국 시각 11월 1일 0시가 지나도 아홉 시간 동안 쿠폰이 살아 있다. 경계값 분석을 "10월 31일 23:59:59와 11월 1일 00:00:00"으로 적어 두고, 그 시각을 사용자 시간대로 넣어야 이 버그가 보인다. 테스트가 서버 시간대(대개 UTC)로만 시각을 만들면 경계 자체가 아홉 시간 어긋난 자리에서 확인된다. 시계를 테스트가 쥐는 방법은 [테스트 피라미드와 단위 테스트](/posts/test-pyramid-unit-tests#시계와-난수를-테스트-손에-쥐여-준다)에 있다.

경계 주변을 하나 더 본다. 반올림 규칙은 구역 안의 특정 값에서만 드러난다. 20,455원의 10%는 2,045.5원이다. 버림이면 2,045원, 반올림이면 2,046원이다. 끝자리가 5 이상인 값을 일부러 하나 넣어야 반올림 실수가 보인다.

## 조건이 얽히면 표로 편다

금액 하나만 볼 때는 수직선으로 충분하다. 그런데 기획서에는 조건이 더 있다. 세일 상품은 쿠폰에서 빠지고, 쿠폰은 주문당 한 장만 쓸 수 있다. 조건이 여러 개 얽히면 결정 표(decision table)로 편다. 조건을 행으로, 가능한 조합을 열로 놓고, 각 조합의 기대 동작을 적는다.

조건 셋이 모두 예/아니오면 조합은 2의 3승, 8개다.

| 조건 / 규칙 | R1 | R2 | R3 | R4 | R5 | R6 | R7 | R8 |
|---|---|---|---|---|---|---|---|---|
| 다른 쿠폰을 이미 적용했다 | Y | Y | Y | Y | N | N | N | N |
| 세일 상품만 담았다 | Y | Y | N | N | Y | Y | N | N |
| 쿠폰 대상 금액 ≥ 20,000 | Y | N | Y | N | Y | N | Y | N |
| 동작 | 한 장만 | 한 장만 | 한 장만 | 한 장만 | 대상 없음 | 대상 없음 | 할인 | 최소 금액 안내 |

R1~R4는 결과가 같다. 다른 쿠폰이 이미 있으면 나머지 조건은 볼 필요가 없다. 이런 열은 "상관없음(–)"으로 합쳐서 하나로 줄인다. R5와 R6도 합친다. 그러면 규칙은 넷이 되고, 케이스도 넷이면 된다.

| 조건 / 규칙 | A | B | C | D |
|---|---|---|---|---|
| 다른 쿠폰을 이미 적용했다 | Y | N | N | N |
| 세일 상품만 담았다 | – | Y | N | N |
| 쿠폰 대상 금액 ≥ 20,000 | – | – | Y | N |
| 동작 | 한 장만 쓸 수 있다는 안내 | 대상 상품 없음 | 할인 | 최소 금액 안내 |

결정 표의 진짜 값은 표를 그리는 동안 나온다. 세 가지가 나왔다.

첫째, 조건의 우선순위다. 다른 쿠폰도 있고 금액도 모자라면 어느 메시지를 보여 주나. 표의 A가 "다른 쿠폰 검사가 먼저"라는 결정을 적은 것이다. 기획서에는 없었다.

둘째, "세일 상품만"이 아니라 섞여 있으면? 일반 상품 15,000원과 세일 상품 10,000원을 담았다면 쿠폰 대상 금액은 15,000원이라 최소 금액에 못 미친다. 그래서 세 번째 조건을 "상품 금액"이 아니라 "쿠폰 대상 금액"으로 고쳐 적었다. 표를 만들지 않았다면 개발자는 장바구니 합계 25,000원으로 판정했을 것이다.

셋째, 합친 열은 정말 상관없는지 확인한다. A를 하나로 합쳤다는 건 "다른 쿠폰이 있으면 세일 여부와 금액은 결과에 영향이 없다"는 주장이다. 구현이 조건 순서를 다르게 짰다면 이 주장이 틀린다. 그래서 합친 열은 그 안의 조합 하나쯤을 더 넣어 확인하기도 한다.

## 쿠폰에도 일생이 있다

금액과 조건은 입력 한 번으로 끝나는 이야기다. 쿠폰은 시간이 지나며 상태가 바뀐다. 발급되고, 쓰이고, 결제가 취소되면 돌아오고, 기한이 지나면 만료된다. 이런 대상은 상태 전이 테스트(state transition testing)로 본다. 상태와 이벤트, 전이를 그림으로 그린 다음, 그 그림 위의 길을 케이스로 만든다.

더 중요한 건 일어나면 안 되는 전이다. 상태 전이 표를 그리면 빈칸이 보인다.

| 상태 \ 이벤트 | 결제 | 결제 취소 | 기한 지남 |
|---|---|---|---|
| ISSUED | → USED | (무효) | → EXPIRED |
| USED | (무효: 이중 사용) | → ISSUED 또는 EXPIRED | 그대로 |
| EXPIRED | (무효) | (무효) | 그대로 |

무효 칸마다 "그 이벤트가 들어오면 거절되고 상태가 그대로인가"를 확인한다. 사용된 쿠폰으로 다시 결제하기, 만료된 쿠폰으로 결제하기, 쓰지 않은 쿠폰의 결제를 취소하기. 실제 사고는 대부분 이 칸에서 난다. 앞의 그레이박스 예처럼 "사용됨에서 결제"가 동시에 두 번 들어오는 경우가 대표적이다.

이벤트를 이어 붙인 시나리오도 하나 따라가 보자. 연속된 전이 두 개를 묶어 확인하는 걸 1-스위치 커버리지라고 한다. 취소해서 돌아온 쿠폰을 다시 쓸 수 있는지는 전이 하나씩만 볼 때는 확인되지 않는다.

## 조합이 서른여섯 개면 아홉 개로

이번엔 결제 화면이다. 결제 수단 셋(카드, 계좌이체, 간편결제), 기기 셋(iOS, Android, 웹), 회원 등급 둘(일반, VIP), 배송 둘(일반, 새벽). 모든 조합은 3 × 3 × 2 × 2 = 36가지다. 변수가 하나 늘 때마다 곱으로 늘어나는 조합 폭발이다.

페어와이즈(pairwise, all-pairs) 테스트는 모든 조합 대신, 아무 변수 둘을 골라도 그 두 변수의 모든 값 쌍이 적어도 한 케이스에 나오게 한다. 근거는 경험적이다. 실제 결함의 대부분은 변수 하나나 둘의 상호작용에서 나오고, 셋 이상이 동시에 특정 값이어야 나는 결함은 드물다. 미국 NIST의 연구들이 여러 분야의 결함 데이터를 분석해 이 경향을 보고했다.

위 네 변수에서 확인해야 할 쌍은 결제×기기 9개, 결제×등급 6개, 결제×배송 6개, 기기×등급 6개, 기기×배송 6개, 등급×배송 4개로 37개다. 이걸 아홉 케이스로 모두 덮을 수 있다.

```text
카드 / iOS / 일반 / 일반배송
카드 / Android / VIP / 일반배송
카드 / 웹 / 일반 / 새벽
계좌 / iOS / VIP / 새벽
계좌 / Android / VIP / 일반배송
계좌 / 웹 / 일반 / 새벽
간편 / iOS / 일반 / 새벽
간편 / Android / 일반 / 새벽
간편 / 웹 / VIP / 일반배송
```

직교 배열 L9를 바탕으로 만들고, 37쌍이 모두 들어 있는지 스크립트로 확인한 결과다(빠진 쌍 0개). 값이 가장 많은 두 변수의 곱(3 × 3 = 9)보다 적게는 만들 수 없으니 이게 최소다. 실무에서는 손으로 만들지 않고 PICT(마이크로소프트의 오픈소스 도구) 같은 생성기에 변수와 제약을 넣는다.

제약도 함께 다뤄야 한다. "웹에서는 간편결제 중 일부만 된다"거나 "새벽배송은 VIP만"처럼 불가능한 조합이 있으면, 생성기에 제약으로 알려 주지 않으면 실행할 수 없는 케이스가 나온다. 반대로 위험이 큰 조합(가장 많이 쓰는 기기 × 가장 많이 쓰는 결제 수단)은 페어와이즈와 상관없이 따로 넣는다. 페어와이즈는 조합 수를 줄이는 도구이지, 무엇이 중요한지 알려 주지는 않는다.

## 시나리오와 케이스는 크기가 다르다

여기까지 뽑은 것은 테스트 케이스다. 케이스는 사전 조건, 입력, 실행 단계, 기대 결과가 정해진 하나의 확인이다. 시나리오는 그보다 크다. "VIP 회원이 쿠폰을 써서 결제하고, 다음 날 취소한 뒤, 같은 쿠폰으로 다시 주문한다"는 시나리오이고, 그 안에 케이스 여러 개가 들어간다.

```text
케이스 ID: CPN-BVA-03
제목: 쿠폰 대상 금액이 정확히 20,000원이면 2,000원 할인된다
사전 조건: ISSUED 상태 쿠폰 1장, 세일 아닌 상품 20,000원 1개를 담은 장바구니
단계: 1) 주문서에서 쿠폰 선택  2) 결제 금액 확인
기대 결과: 할인 2,000원, 결제 금액 18,000원, 쿠폰 상태는 결제 전까지 ISSUED
근거: 경계값 분석(할인 시작 경계), 결정 표 규칙 C
```

시나리오는 "무엇을 확인할지"를 업무 흐름으로 정하는 데 좋고, 기획자나 업무 담당자와 이야기할 때 쓴다. 케이스는 "어떻게 확인할지"를 재현 가능하게 적는다. 시나리오만 있으면 사람마다 다르게 실행해서 결과를 비교할 수 없고, 케이스만 있으면 전체 흐름에서 빠진 곳이 안 보인다. 케이스에 근거(어느 기법, 어느 규칙)를 적어 두면, 나중에 명세가 바뀔 때 어떤 케이스를 고쳐야 하는지 바로 찾는다.

## 무엇이 맞는 답인지는 누가 아나

케이스에는 기대 결과가 있어야 한다. 그 기대 결과를 정하는 근거를 테스트 오라클(test oracle)이라고 한다. 쿠폰은 쉽다. 명세가 오라클이다. 2만 원이면 2천 원. 그런데 늘 이렇게 쉽지는 않다.

추천 목록이 맞는지, 배송 예정일 계산이 맞는지, 세금 계산 엔진을 새로 짰는데 결과가 맞는지는 명세 한 줄로 판정이 안 된다. 이걸 오라클 문제라고 한다. 이때 쓰는 오라클은 몇 종류가 있다.

이전 버전도 오라클이 된다. 세금 엔진을 다시 짰다면 같은 입력 만 건을 옛 엔진과 새 엔진에 넣고 결과를 비교한다(back-to-back 테스트). 운영 트래픽을 복제해 새 버전에도 보내고 응답을 비교하는 섀도 테스트도 같은 원리다. 단점은 옛 버전의 버그까지 정답으로 굳힌다는 것이다. 차이가 나면 누가 맞는지는 사람이 판단한다.

일관성 규칙도 오라클이다. 정확한 값은 몰라도 지켜야 하는 관계는 안다. 결제 금액은 상품 합계에서 할인을 빼고 배송비를 더한 값이어야 하고, 할인은 0 이상이고 쿠폰 대상 금액의 10%를 넘을 수 없다. 이 관계를 무작위 입력 수백 개에 대고 확인하는 게 속성 기반 테스트(property-based testing)다. JavaScript에서는 fast-check가 대표적이다.

반올림으로 잘못 짠 구현에 "할인은 금액의 10%를 넘지 않는다"는 속성을 걸어 봤다.

```js
import { test } from "node:test";
import fc from "fast-check";

// 반올림으로 잘못 짠 버전
function couponDiscount(amount) {
  if (amount < 20000) return 0;
  return Math.min(Math.round(amount * 0.1), 5000);
}

test("할인은 주문 금액의 10%를 넘지 않는다", () => {
  fc.assert(
    fc.property(fc.integer({ min: 1, max: 1_000_000 }), (amount) => {
      return couponDiscount(amount) <= amount * 0.1;
    }),
    { seed: 42 }
  );
});
```

```text
✔ 할인은 주문 금액의 10%를 넘지 않는다 (7.157114ms)
ℹ tests 1
ℹ pass 1
ℹ fail 0
```

통과했다. 버그가 있는데도. 1부터 100만 사이에서 무작위로 100개를 뽑으면 대부분 5만 원을 넘어서 상한 5,000원에 걸린다. 반올림이 드러나는 구간(2만~5만 원 중 끝자리가 5 이상인 값)은 전체의 1.5% 정도라 100번 안에 안 나올 수 있다. 무작위 입력도 경계를 의식해서 범위를 잡아야 한다는 뜻이다. 범위를 1~60,000으로 좁히자 바로 걸렸다.

```text
✖ 할인은 주문 금액의 10%를 넘지 않는다 (8.863267ms)
  Error: Property failed after 2 tests
  { seed: 42, path: "1:2:0:6:1:1:0", endOnFailure: true }
  Counterexample: [20455]
  Shrunk 6 time(s)
```

`Counterexample: [20455]`가 반례다. 20,455원의 10%는 2,045.5원인데 반올림해서 2,046원을 깎았다. `Shrunk 6 time(s)`는 처음 찾은 실패 입력을 더 단순한 값으로 여섯 번 줄여 봤다는 뜻이다. `seed`를 기록해 두면 같은 무작위 순서로 다시 돌려 실패를 재현할 수 있다. CI에서 속성 테스트가 실패하면 이 시드부터 로그에서 찾는다.

정확한 출력을 아예 모를 때는 입력 사이의 관계를 쓴다. 검색에 조건을 하나 더 붙이면 결과 수는 늘어날 수 없다. 같은 주문을 금액만 1원 올려 넣으면 할인은 줄어들 수 없다. 이런 관계로 확인하는 걸 변성 테스트(metamorphic testing)라고 한다. 머신러닝 모델이나 검색처럼 정답표가 없는 시스템에서 자주 쓴다.

## 코드를 보고 빠진 길을 찾는다

블랙박스 기법으로 뽑은 케이스가 코드를 얼마나 지나갔는지는 화이트박스 쪽에서 잰다. 구문 커버리지(statement coverage)는 문장이 한 번이라도 실행됐는지, 분기 커버리지(branch coverage)는 모든 조건문의 참과 거짓이 각각 한 번이라도 실행됐는지를 본다.

같은 쿠폰 함수를 if 두 개로 짜 보자.

```js
// coupon.js
export function couponDiscount(amount) {
  let discount = 0;
  if (amount >= 20000) {
    discount = Math.floor(amount * 0.1);
  }
  if (discount > 5000) {
    discount = 5000;
  }
  return discount;
}
```

6만 원 케이스 하나만 돌리면 두 if가 모두 참이라 모든 문장이 실행된다. 구문 커버리지 100%다. 하지만 두 if의 거짓 쪽은 한 번도 안 갔으니, 교과서 정의로는 분기 4개 중 2개, 50%다. 도구로 재 보면 흥미로운 차이가 나온다. Jest 29.7(기본 커버리지 도구가 istanbul)로 잰 결과다.

```text
-----------|---------|----------|---------|---------|-------------------
File       | % Stmts | % Branch | % Funcs | % Lines | Uncovered Line #s 
-----------|---------|----------|---------|---------|-------------------
All files  |     100 |       50 |     100 |     100 |                   
 coupon.js |     100 |       50 |     100 |     100 | 3-6               
-----------|---------|----------|---------|---------|-------------------
```

같은 코드와 테스트를 Node 22 내장 커버리지(`node --test --experimental-test-coverage`)로 재면 이렇게 나온다.

```text
ℹ file      | line % | branch % | funcs % | uncovered lines
ℹ coupon.js | 100.00 |   100.00 |  100.00 | 
```

분기 100%다. Node 내장 커버리지는 V8 엔진이 실행한 코드 블록을 세는 방식이라, else가 없는 if의 "안 들어간 쪽"은 셀 블록이 없어서 놓친다. 3만 원 케이스로 바꾸면 두 번째 if의 몸통이 실행되지 않으니 그제야 `branch % 66.67`, 7~8행 미실행으로 잡힌다. 같은 "분기 커버리지"라는 이름이 도구마다 다른 것을 잰다. 팀에서 커버리지 기준을 걸 때는 어느 도구의 숫자인지까지 같이 정한다.

커버리지가 알려 주는 건 "어느 길을 아직 안 갔나"다. 그 길에서 결과가 맞는지는 알려 주지 않는다. 단언 없이 실행만 해도 100%가 나오는 함정, 그리고 테스트가 버그를 잡는지 재는 변이 테스트는 [테스트 피라미드와 단위 테스트](/posts/test-pyramid-unit-tests#커버리지-100인데-버그가-그대로다)에서 직접 돌려 봤다. 그래서 순서는 이렇다. 블랙박스 기법으로 케이스를 뽑고, 커버리지로 안 간 길을 찾고, 그 길이 명세의 어떤 구역에 해당하는지 거꾸로 확인한다. 명세에 해당하는 구역이 없는 길이라면 죽은 코드이거나 명세에 빠진 요구다.

## 기법이 못 떠올리는 결함은 경험이 찾는다

여기까지는 명세에서 기계적으로 케이스를 뽑는 방법이었다. 그런데 운영 장애 목록을 보면 명세 어디에도 없던 입력이 자주 나온다. 결제 버튼을 두 번 누른다. 쿠폰 코드 앞뒤에 공백을 붙여 붙여 넣는다. 주문서를 열어 둔 채 다른 탭에서 쿠폰을 써 버린다. 네트워크가 끊긴 뒤 다시 시도한다. 이런 케이스는 오류 추측(error guessing)으로 찾는다. 과거 결함과 경험을 바탕으로 "이런 곳은 보통 깨진다"를 목록으로 만들어 두고 대 보는 방법이다.

팀에 쌓인 목록을 체크리스트로 두면 사람이 바뀌어도 남는다. 쿠폰·결제 쪽이라면 이런 식이다.

```text
[입력]   앞뒤 공백, 전각 문자, 대소문자 섞인 코드, 아주 긴 값, 빈 값
[반복]   같은 요청 두 번(더블 클릭, 재시도), 뒤로 가기 후 다시 제출
[동시성] 두 탭·두 기기에서 같은 쿠폰, 결제 중 쿠폰 만료
[시간]   자정·월말 경계, 사용자 시간대와 서버 시간대가 다를 때
[실패]   결제사 타임아웃 뒤 재시도, 결제는 됐는데 응답이 끊겼을 때
[권한]   남의 쿠폰 ID로 요청, 로그아웃 뒤 남은 탭에서 제출
```

목록의 각 줄은 결국 앞의 기법으로 다시 들어간다. "같은 요청 두 번"은 상태 전이의 무효 칸이고, "자정 경계"는 경계값이다. 오류 추측은 기법을 대신하지 않고, 기법이 어느 변수를 봐야 하는지를 알려 준다. 체계적으로 뽑은 케이스로 바닥을 깔고, 경험으로 위험한 곳을 더 판다. 사람이 직접 화면을 만지며 이런 곳을 파는 탐색적 테스트는 [스모크, 새니티, 회귀 테스트](/posts/smoke-sanity-regression-testing#자동화가-못-보는-것은-사람이-본다)에서 다룬다.

## 현장에서 이 기법들이 쓰이는 순간

배포 전날 "테스트했나요?"에 답할 때 쓴다. "금액은 경계 세 곳을 3값으로, 조건 조합은 결정 표 규칙 네 개로, 쿠폰 상태는 유효 전이 네 개와 무효 전이 다섯 칸으로 확인했고, 기기·결제 조합은 페어와이즈 아홉 개만 돌렸다"고 말할 수 있으면, 무엇을 안 했는지도 함께 드러난다. 위험을 받아들일지는 그다음에 함께 정한다.

버그가 운영에서 나왔을 때도 쓴다. 쿠폰 할인이 가끔 1원씩 틀린다는 문의가 오면, 경계값보다는 "구역 안의 특정 값"(반올림, 부동소수점) 문제부터 의심한다. 특정 기기에서만 결제가 안 되면 페어와이즈에서 그 쌍이 들어 있었는지, 제약 때문에 빠졌는지를 본다. 같은 쿠폰이 두 번 쓰였다면 상태 전이 표의 무효 칸, 특히 동시 요청을 확인했는지 본다.

흔한 실수도 정리해 둔다. 무효 입력 여러 개를 한 케이스에 섞는다. 숨은 경계(상한에서 거꾸로 계산한 값, 날짜·길이)를 빠뜨린다. 결정 표에서 "상관없음"으로 합친 열을 한 번도 확인하지 않는다. 상태 전이에서 유효한 길만 돌린다. 기대 결과를 "정상 동작"처럼 판정할 수 없는 말로 적는다. 마지막 것이 의외로 가장 흔하다. 기대 결과가 숫자나 상태로 적혀 있지 않으면, 실행한 사람이 그때 본 화면이 곧 정답이 된다.

## 경계와 표와 길

테스트 설계는 무한한 입력 공간에서 결함이 숨어 있을 만한 곳을 골라내는 일이다. 같게 다뤄질 입력은 묶어서 하나만 보고(동등 분할), 묶음이 바뀌는 자리는 앞뒤를 본다(경계값). 조건이 얽히면 표로 펴서 빠진 칸과 우선순위를 찾고(결정 표), 상태가 있으면 길과 막힌 길을 따라간다(상태 전이). 조합이 폭발하면 쌍만 덮는다(페어와이즈). 그리고 정답을 무엇으로 판정할지(오라클)를 먼저 정한다. 이렇게 뽑은 케이스가 어느 층의 테스트가 될지, 바뀐 코드 앞에서 무엇을 다시 돌릴지는 [스모크, 새니티, 회귀 테스트](/posts/smoke-sanity-regression-testing)에서 이어진다. 케이스를 코드보다 먼저 쓰는 방식은 [TDD, BDD, ATDD](/posts/tdd-bdd-atdd)에서 본다.

## 면접에서 나올 만한 질문

### 검증과 확인은 어떻게 다른가요?

검증은 명세대로 만들었는지, 확인은 명세가 사용자에게 맞는 것인지를 본다. 보엠의 표현으로 "제품을 올바르게 만들었나"와 "올바른 제품을 만들었나"다. 쿠폰 할인 계산이 기획서와 일치하는지는 검증이고, 2만 원 기준 때문에 고객이 이탈하는지는 확인이다. 검증은 테스트와 리뷰로, 확인은 기획 리뷰, 인수 테스트, 운영 지표로 한다.

### 블랙박스, 화이트박스, 그레이박스 테스트의 차이는요?

블랙박스는 명세만 보고 입력과 기대 결과를 정해서 구현이 바뀌어도 케이스가 살아남고 빠진 요구를 찾을 수 있다. 화이트박스는 코드 구조를 보고 분기와 반복을 덮는 케이스를 만들지만 코드에 없는 요구는 못 찾는다. 그레이박스는 내부(DB 스키마, 조건부 UPDATE 같은 구현)를 일부 알고 케이스를 떠올리되 확인은 바깥 인터페이스로 한다. 동시 결제로 쿠폰 이중 사용을 확인하는 테스트가 그레이박스의 예다.

### 동등 분할과 경계값 분석을 설명해 주세요.

동등 분할은 같은 동작을 기대하는 입력을 묶어 묶음마다 대표값 하나만 확인하는 기법이고, 무효 묶음은 케이스 하나에 하나씩만 넣는다. 경계값 분석은 결함이 몰리는 묶음의 가장자리를 고른다. 쿠폰이라면 0과 1, 19,999와 20,000, 그리고 상한에서 거꾸로 계산한 49,999·50,000·50,001이다. 경계는 명세에 숫자로 적혀 있지 않은 경우가 많아서 계산해서 찾아야 한다.

### 경계에서 값을 몇 개 고르나요?

2값 분석은 경계값과 바깥쪽 이웃 둘, 3값 분석은 경계값과 양쪽 이웃 셋을 고른다. `>=`를 `>`로 쓴 실수는 2값으로도 잡히지만, `>=`를 `==`로 쓴 것처럼 경계에서만 우연히 맞는 식은 경계 안쪽 이웃까지 봐야 잡힌다. 그래서 돈이나 한도처럼 위험이 큰 경계에는 3값을 쓰고 나머지는 2값으로 줄인다. 반올림처럼 구역 안 특정 값에서만 드러나는 결함은 그런 값을 따로 넣어야 한다.

### 조합 폭발은 어떻게 줄이나요?

먼저 결정 표에서 결과가 같은 열을 "상관없음"으로 합쳐 규칙 수를 줄인다. 독립적인 설정 변수가 많으면 페어와이즈로 모든 두 변수 쌍만 덮는다. 3·3·2·2 변수의 36개 조합은 9개로 37쌍을 모두 덮을 수 있다. 다만 불가능한 조합은 제약으로 빼고, 사용량이 많거나 위험이 큰 조합은 따로 추가해야 한다.

### 상태 전이 테스트에서 무엇을 확인하나요?

유효한 전이를 모두 한 번씩 지나는 0-스위치 커버리지가 기본이고, 취소 후 재사용처럼 연속 전이에서만 드러나는 동작은 1-스위치로 본다. 더 중요한 건 상태 전이 표의 무효 칸이다. 사용된 쿠폰으로 다시 결제하거나 만료된 쿠폰을 쓰는 이벤트가 거절되고 상태가 그대로인지 확인한다. 동시 요청으로 무효 전이가 뚫리는지도 이 칸에서 확인한다.

### 테스트 오라클이 없을 때는 무엇을 보나요?

정확한 정답을 모르면 지켜야 하는 관계를 오라클로 쓴다. 할인이 금액의 10%를 넘지 않는다 같은 속성을 무작위 입력에 거는 속성 기반 테스트, 조건을 추가하면 검색 결과가 늘 수 없다 같은 입력 간 관계를 보는 변성 테스트가 있다. 시스템을 다시 짰다면 이전 버전과 결과를 비교하는 back-to-back이나 섀도 테스트도 쓴다. 이전 버전 비교는 옛 버그까지 정답으로 굳힐 수 있으니 차이는 사람이 판정한다.

### 분기 커버리지 100%면 충분한가요?

아니다. 커버리지는 어느 길을 실행했는지만 알려 주고, 결과를 확인했는지는 모른다. 게다가 도구마다 재는 게 다르다. else 없는 if 두 개를 참으로만 지나가는 테스트는 istanbul 기반 Jest에서 분기 50%였지만 V8 기반 Node 내장 커버리지에서는 100%였다. 커버리지는 안 간 길을 찾는 데 쓰고, 테스트가 결함을 잡는지는 변이 테스트나 블랙박스 기법으로 뽑은 케이스로 본다.
