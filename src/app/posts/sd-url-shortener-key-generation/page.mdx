이 시리즈에서 이 글의 자리: [⑱ URL 단축기 ①: API와 리다이렉트](/posts/sd-url-shortener-api-redirect)에서 API와 301·302, 테이블을 정했다. 이 글은 같은 장의 두 번째 글로, 그때 미뤄 둔 짧은 키를 만드는 법과 인기 링크를 캐시로 받는 법을 다룬다. 번호를 만드는 부분은 [⑰ 고유 ID 생성기](/posts/sd-unique-id-generator)에 기댄다. 다음 글은 새 사례인 [⑳ 웹 크롤러 구조](/posts/sd-web-crawler-architecture)다.

⑱의 작은 서버는 번호 125000을 `ww8`로 바꿨다. 그런데 키를 정하는 방법은 그것만 있는 게 아니다. 가장 먼저 떠오르는 건 긴 주소를 해시해서 앞 몇 글자만 쓰는 방법이다. 번호가 필요 없고, 같은 주소는 늘 같은 키가 나온다. 이 방법을 실제로 돌려 보면 무엇이 깨지는지, 번호를 바꾸는 방법은 무엇이 다른지 차례로 본다. ⑱에서 잡은 규모, 즉 10년 동안 약 315억 개의 링크를 기준으로 삼는다.

## 해시를 잘라 쓰면 생기는 일

해시 함수는 어떤 길이의 입력이든 정해진 길이의 값으로 바꾼다. MD5는 128비트, 16진수로 32글자를 낸다. 32글자는 너무 기니 앞 7글자만 키로 쓰면 어떨까. 서로 다른 주소 100만 개를 만들어 직접 세 봤다.

```js
// collide.js: 긴 URL을 해시해서 앞부분만 잘라 쓰면 얼마나 겹치나
const { createHash } = require("node:crypto");
const ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";
const md5 = (s) => createHash("md5").update(s).digest();
function toBase62(buf, len) {            // 해시 앞 8바이트를 숫자로 보고 62진수 len자리만 쓴다
  let n = buf.readBigUInt64BE(0); let s = "";
  for (let i = 0; i < len; i++) { s = ALPHABET[Number(n % 62n)] + s; n /= 62n; }
  return s;
}
const N = 1_000_000;
const urls = Array.from({ length: N }, (_, i) => `https://shop.example.com/items/${i}?ref=newsletter`);
const schemes = [
  ["hex 7자 (md5 앞 7글자)", (h) => h.toString("hex").slice(0, 7), 16 ** 7],
  ["base62 5자", (h) => toBase62(h, 5), 62 ** 5],
  ["base62 6자", (h) => toBase62(h, 6), 62 ** 6],
  ["base62 7자", (h) => toBase62(h, 7), 62 ** 7],
];
for (const [name, cut, space] of schemes) {
  const seen = new Set(); let coll = 0;
  for (const u of urls) { const k = cut(md5(u)); if (seen.has(k)) coll++; else seen.add(k); }
  const expected = N - space * (1 - Math.exp(-N / space));   // 기대 충돌 수
  console.log(`${name.padEnd(22)} space=${space.toExponential(2)}  collisions=${coll}  expected≈${expected.toFixed(1)}`);
}
```

```text
hex 7자 (md5 앞 7글자)     space=2.68e+8  collisions=1863  expected≈1860.3
base62 5자              space=9.16e+8  collisions=562  expected≈545.6
base62 6자              space=5.68e+10  collisions=8  expected≈8.8
base62 7자              space=3.52e+12  collisions=0  expected≈0.1
```

16진수 7글자는 가능한 값이 약 2억 6,800만 개다. 링크 100만 개는 그 0.4%밖에 안 되는데도 1,863번이나 겹쳤다. 겹침을 충돌이라고 한다. 같은 7글자를 62가지 글자로 쓰면 가능한 값이 3조 5천억 개로 늘어 100만 개에서는 한 번도 겹치지 않았다. 옆의 `expected`는 확률로 계산한 기대 충돌 수인데, 실제 숫자와 거의 같다.

빈자리가 넉넉해 보이는데 왜 이렇게 자주 겹칠까. 새 링크 하나가 이미 있는 키 하나와 겹칠 확률은 작지만, 겹칠 수 있는 짝의 수는 링크 수의 제곱에 비례해서 늘어난다. 23명만 모여도 생일이 같은 두 사람이 있을 확률이 절반을 넘는 것과 같은 이유라서 생일 문제라고 부른다. 대략 가능한 값 개수의 제곱근만큼 넣으면 충돌이 시작된다. 2억 6,800만의 제곱근은 약 1만 6천이다.

## 겹치면 다시 해시하고, 다시 묻는다

충돌은 피할 수 없으니 감지하고 피해 가야 한다. 흔한 방법은 키를 만든 뒤 DB에 있는지 묻고, 있으면 긴 주소 뒤에 정해 둔 글자(`#1`, `#2`…)를 붙여 다시 해시하는 것이다. 같은 긴 주소가 이미 있는 경우와 다른 주소가 우연히 같은 키를 받은 경우는 구분해야 한다. 앞의 것은 있던 키를 돌려주면 되고, 뒤의 것만 다시 해시한다.

그림의 키 글자는 설명용으로 지은 것이다. 실제로 신경 쓸 것은 몇 번 묻게 되느냐다. 키 공간이 차오를수록 다시 하는 횟수가 늘어난다. 실험을 빨리 끝내려고 3글자(238,328칸)짜리 작은 공간을 10%, 50%, 90%까지 채운 뒤, 새 주소 2만 개를 넣을 때 DB에 몇 번 묻는지 셌다.

```js
// retry.js 일부: 키 공간이 차오를수록 "겹치면 덧붙여 다시 해시"가 몇 번 도나
const LEN = 3, SPACE = 62 ** LEN;            // 238,328칸짜리 작은 공간으로 줄여서 실험
let attempt = 0, key;
do { key = short(attempt === 0 ? url : `${url}#${attempt}`, LEN); attempt++; } while (used.has(key));
```

```text
filled 10%: avg DB lookups 1.12, worst 5
filled 50%: avg DB lookups 2.01, worst 14
filled 90%: avg DB lookups 10.05, worst 141
```

평균은 1 ÷ (1 − 채운 비율)과 거의 같다. 절반이 차면 두 번, 90%가 차면 열 번 묻는다. 운이 나쁜 요청은 141번까지 물었다. 우리 규모에 대 보면, 7글자 공간에 315억 개가 차도 0.9%라 거의 한 번에 끝난다. 6글자로 줄이면 55%가 차서 평균 두 번을 넘긴다. 해시 방식을 쓴다면 키 길이를 넉넉히 잡아야 하는 이유다.

매번 DB에 묻는 비용은 [블룸 필터](/posts/bloom-filter)로 줄일 수 있다. 지금까지 쓴 키를 비트 배열에 도장 찍어 두면 "확실히 없다"는 답은 메모리에서 바로 나온다. "있을지도 모른다"고 할 때만 DB에 묻는다. 그래도 두 서버가 동시에 같은 키를 고르는 경쟁은 블룸 필터로 막지 못하니, 마지막 판정은 `short_key`의 `UNIQUE` 제약에 맡긴다. 삽입이 제약 위반으로 실패하면 다시 해시한다.

## 번호를 62진수로 바꾸기

두 번째 방법은 해시 대신 [⑰의 고유 ID](/posts/sd-unique-id-generator)를 받아 그 번호를 짧은 글자로 다시 쓰는 것이다. 번호가 겹치지 않으니 키도 절대 겹치지 않는다. DB에 미리 물어볼 필요도 없다.

짧게 만드는 원리는 진법이다. 10진수는 0~9 열 글자로 수를 쓰고, 16진수는 0~9와 a~f 열여섯 글자로 쓴다. 쓸 수 있는 글자가 많을수록 같은 수를 더 적은 자리로 쓴다. URL에 그대로 넣어도 안전한 글자인 숫자 10개, 소문자 26개, 대문자 26개를 모두 쓰면 62진수, 흔히 Base62라고 부르는 표기가 된다. 비슷한 이름의 [Base64](/posts/base64)는 바이트를 글자로 바꾸는 인코딩이고 `+`와 `/`가 섞여 URL에 그대로 넣기 불편하다.

바꾸는 법은 초등학교의 진법 변환과 같다. 62로 나눈 나머지가 맨 끝 자리, 몫을 다시 62로 나눈 나머지가 그 앞자리다. 125000을 바꿔 보자.

Node 22로 여러 번호를 바꾸고 다시 돌려 봤다.

```js
// base62.js: 숫자를 0-9, a-z, A-Z 62글자로 다시 쓴다
const ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";
function encode(n) {
  if (n === 0) return "0";
  let s = "";
  while (n > 0) { s = ALPHABET[n % 62] + s; n = Math.floor(n / 62); }
  return s;
}
function decode(s) {
  let n = 0;
  for (const ch of s) n = n * 62 + ALPHABET.indexOf(ch);
  return n;
}
for (const n of [0, 61, 62, 3843, 3844, 125000, 1_000_000_000, 100_000_000 * 365 * 10]) {
  const e = encode(n);
  console.log(String(n).padStart(13), "->", e.padEnd(8), "len", e.length, "decode ok", decode(e) === n);
}
for (let len = 5; len <= 8; len++) console.log(`62^${len} =`, (62 ** len).toLocaleString("en-US"));
```

61은 한 글자 `Z`, 62에서 처음으로 두 글자 `10`이 된다. 10진수에서 9 다음이 10인 것과 같다. 10억도 6글자다. 6글자는 568억 개, 7글자는 3조 5천억 개를 담으니 우리의 315억 개는 6글자 안에 들어간다. 길이는 번호가 커지면서 1글자에서 점점 늘어난다. 키 길이를 처음부터 고정하고 싶다면 번호를 7글자 공간 안에서 시작하거나 앞을 `0`으로 채운다.

## 다음 키가 보이는 문제

번호를 그대로 바꾸면 키가 차례로 나온다. 한 사람이 링크를 만들어 `4c92`를 받으면, `4c93`, `4c94`도 누군가의 링크라는 걸 쉽게 짐작한다. 비공개 문서나 쿠폰 링크를 이렇게 하나씩 열어 볼 수 있고, 하루에 키가 얼마나 늘었는지로 경쟁사가 서비스 규모를 읽을 수도 있다.

간단한 처방은 번호를 키로 바꾸기 전에 겹치지 않게 섞는 것이다. 62^7과 공약수가 없는 큰 수 P를 곱하고 62^7로 나눈 나머지를 쓰면, 서로 다른 번호는 반드시 서로 다른 값이 된다. P의 모듈러 역원을 곱하면 원래 번호도 되돌린다.

```js
// scramble.js 일부: 연속된 번호를 겹치지 않게 섞어서 7자리 키로 만든다
const SPACE = 62n ** 7n;                 // 3,521,614,606,208칸
const P = 2176477521739n;                // 62^7의 약 0.618배. 2로도 31로도 나눠지지 않는다
const plainKey = (id) => enc(BigInt(id), 7);
const mixedKey = (id) => enc((BigInt(id) * P) % SPACE, 7);
```

```text
gcd(P, 62^7) = 1
1000000 plain 0004c92 mixed ZiyTMpa
1000001 plain 0004c93 mixed BChHEKf
1000002 plain 0004c94 mixed dW0vx5k
1000003 plain 0004c95 mixed QfJjpqp
decode dW0vx5k -> 1000002
1..1000000 unique keys: 1000000
```

1씩 늘어나는 번호가 서로 닮지 않은 키가 됐고, 100만 개가 모두 달랐다. 다만 이건 가리기일 뿐 암호가 아니다. 키 몇 개와 번호를 아는 사람은 P를 계산해 낼 수 있다. 정말로 짐작하면 안 되는 링크라면 키를 무작위로 만들고 충돌을 확인하는 방식, 즉 앞의 해시 방식과 같은 구조로 돌아간다. 이때는 7글자보다 길게 잡는다. 키를 아는 사람만 열 수 있다는 것은 보호가 아니라 운에 기대는 것이니, 정말 비공개라면 링크에 로그인이나 만료를 붙인다.

## 키를 미리 만들어 두는 서버

## 세 방법을 고르는 기준

| | 해시 후 자르기 | 번호의 Base62 | 미리 만든 키(KGS) |
|---|---|---|---|
| 키 길이 | 고정 (예: 7자) | 번호에 따라 늘어남 | 고정 |
| 충돌 | 있음, 확인과 재시도 필요 | 없음 | 없음 (KGS가 미리 확인) |
| 필요한 부품 | 없음 (DB 확인만) | 고유 ID 생성기 | KGS와 키 저장소 |
| 다음 키 짐작 | 어려움 | 쉬움 (섞으면 줄어듦) | 어려움 |
| 같은 주소면 같은 키 | 자연스럽게 됨 | 따로 조회 필요 | 따로 조회 필요 |

시작은 번호의 Base62가 가장 단순하다. DB의 자동 증가 열 하나와 변환 함수면 된다. 키를 짐작하지 못하게 해야 한다면 섞기를 넣거나 무작위 키로 간다. 해시 방식은 같은 주소에 같은 키를 주는 것이 꼭 필요할 때 고르고, 이때는 키를 7글자 이상으로 잡아 키 공간이 차오르지 않게 한다. 트래픽이 커져 쓰기 경로의 DB 왕복조차 아깝다면 KGS를 둔다.

## 인기 링크는 캐시가 받는다

이제 읽기 쪽이다. ⑱에서 리다이렉트는 쓰기보다 20배 많았다. 그런데 링크가 고르게 눌리지는 않는다. 쿠폰 문자 하나가 수십만 명에게 가면 그 링크 하나에 클릭이 몰리고, 대부분의 링크는 몇 번 눌리고 잊힌다. 링크 10만 개에 클릭 100만 번을 인기 순위에 반비례하게(1등 링크가 2등의 두 배, 3등의 세 배) 나눠 주고, 작은 LRU 캐시가 얼마나 막는지 시뮬레이션했다. LRU는 가장 오래 안 쓴 것부터 버리는 캐시다.

```js
// hot.js 일부: 클릭이 일부 링크에 몰릴 때 작은 LRU 캐시가 얼마나 막아 주나
for (const size of [1000, 5000, 20000]) {
  const lru = new Map(); let hit = 0;
  for (const k of clicks) {
    if (lru.has(k)) { hit++; lru.delete(k); lru.set(k, 1); }         // 적중: 맨 뒤로 옮긴다
    else { lru.set(k, 1); if (lru.size > size) lru.delete(lru.keys().next().value); }  // 가장 오래된 것을 버린다
  }
}
```

```text
top 1% links get 61.9% of clicks
cache  1000 keys ( 1% of links): hit 50.7%, DB reads 493268
cache  5000 keys ( 5% of links): hit 66.5%, DB reads 335226
cache 20000 keys (20% of links): hit 80.7%, DB reads 193187
```

상위 1% 링크가 클릭의 62%를 받는다. 링크의 1%만 담는 캐시가 클릭의 절반을 막고, 20%를 담으면 81%를 막는다. 캐시를 네 배로 늘려도 적중률은 조금씩만 오른다. 많이 눌리는 링크는 적은 칸으로도 잡히고, 나머지는 드물게 눌리는 긴 꼬리라서다. 실제 클릭 분포는 이 가정보다 더 쏠리거나 덜 쏠릴 수 있으니, 운영에서는 적중률을 지표로 보며 크기를 정한다.

이렇게 앱이 캐시를 먼저 보고 없을 때 채우는 방식을 cache-aside라고 한다. 방식들의 차이와 고르는 기준은 [캐시 전략](/posts/caching-strategies)에 있다. Redis 7.0에서 위 명령을 그대로 쳐 봤다.

```bash
# 메모리 2MB, 가득 차면 가장 오래 안 쓴 키부터 버리는 연습용 Redis를 띄운다
redis-server --port 6391 --save "" --appendonly no --maxmemory 2mb --maxmemory-policy allkeys-lru &
# 명령을 차례로 보낸다
redis-cli -p 6391 <<'EOF'
SET link:ww8 "https://shop.example.com/items/8812?utm_source=sms" EX 86400
GET link:ww8
TTL link:ww8
SET link:zzzz "" EX 60
GET link:zzzz
CONFIG GET maxmemory-policy
EOF
```

```text
OK
https://shop.example.com/items/8812?utm_source=sms
86400
OK

maxmemory-policy
allkeys-lru
```

`maxmemory-policy allkeys-lru`가 위 시뮬레이션의 LRU 역할을 한다. 메모리가 차면 Redis가 가장 오래 안 쓴 키부터 버린다. 다섯째 줄이 비어 있다. 키가 없었다면 nil이 왔을 텐데, 일부러 넣어 둔 빈 문자열이 돌아왔다. 앱은 이걸 보고 "DB에 물어볼 필요 없이 없는 링크"라고 판단해 바로 404를 준다. 없는 것을 기억하는 이 캐시를 부정 캐시(negative cache)라고 한다. 키를 무작위로 찍어 보는 스캐너가 DB를 두드리는 것을 막는다.

마지막으로 클릭 수다. 302로 모든 클릭을 받기로 했다면, 리다이렉트 응답을 보내기 전에 클릭 통계를 DB에 쓰면 안 된다. 리다이렉트가 쓰기만큼 느려진다. 클릭 이벤트는 [⑦의 메시지 큐](/posts/sd-queue-logging-automation)에 던져 두고 응답부터 보낸다. 집계는 큐 뒤에서 천천히 한다.

## 키 만들기 셋, 다음은 URL 모으기

짧은 키를 만드는 방법은 셋이었다. 해시를 잘라 쓰면 부품이 필요 없지만 충돌을 확인해야 하고, 키 공간이 차오를수록 재시도가 늘어난다. 번호를 Base62로 바꾸면 충돌이 없지만 고유 ID가 필요하고 다음 키가 보인다. 미리 만든 키는 둘의 장점을 갖지만 KGS를 운영해야 한다. 읽기 쪽은 클릭이 소수 링크에 몰리는 성질 덕에 작은 캐시로도 절반 넘게 막고, 없는 키는 부정 캐시로 막는다.

이걸로 URL 단축기 장을 마친다. 다음 글 [⑳ 웹 크롤러 구조](/posts/sd-web-crawler-architecture)부터는 반대로 수많은 URL을 모으는 쪽을 설계한다. 거기서도 "이 URL을 이미 봤나"를 빨리 판정해야 해서, 이 글의 해시와 블룸 필터가 다시 나온다.

## 면접에서 나올 만한 질문

### 짧은 키는 어떻게 만드나요?

긴 주소를 해시해 앞부분을 잘라 쓰는 방법과, 고유 ID를 Base62로 바꾸는 방법이 기본이다. 해시 방식은 길이가 고정이고 추가 부품이 없지만 충돌을 확인하고 재시도해야 한다. Base62 방식은 충돌이 없지만 ID 생성기가 필요하고 키가 차례로 나온다. 규모가 커지면 키를 미리 만들어 두는 KGS도 쓴다.

### 해시를 잘라 쓰면 충돌이 얼마나 나나요?

생일 문제 때문에 키 공간의 제곱근 근처부터 충돌이 시작된다. 16진수 7글자(약 2억 6,800만 칸)에 100만 개를 넣었더니 1,863번 겹쳤고, Base62 7글자(3조 5천억 칸)는 한 번도 겹치지 않았다. 공간이 차오르면 재시도 횟수가 1 ÷ (1 − 채운 비율)로 늘어나니 길이를 넉넉히 잡는다.

### 충돌 확인 때문에 매번 DB에 묻는 비용은 어떻게 줄이나요?

블룸 필터에 쓴 키를 기록해 두면 "확실히 없다"는 답은 메모리에서 끝난다. "있을 수도 있다"일 때만 DB에 묻는다. 동시에 두 서버가 같은 키를 고르는 경쟁은 블룸 필터로 막지 못하니 `short_key`의 UNIQUE 제약을 최종 판정으로 쓰고, 실패하면 다시 해시한다.

### Base62 키가 차례로 나오는 게 왜 문제인가요?

남이 만든 링크를 다음 키로 짐작해 열어 볼 수 있고, 키가 늘어나는 속도로 서비스 규모가 드러난다. 62^7과 서로소인 수를 곱해 섞으면 겹치지 않으면서 연속성이 사라지지만, 이건 가리기일 뿐 암호가 아니다. 정말 짐작하면 안 되는 링크는 무작위 키에 길이를 늘리고, 로그인이나 만료를 붙인다.

### 키 길이는 몇 글자로 하나요?

필요한 링크 수를 담는 62의 거듭제곱으로 정한다. 6글자는 약 568억, 7글자는 약 3조 5천억이라 10년 315억 개면 6글자로 되지만, 해시 방식이라면 키 공간이 절반 넘게 차서 재시도가 늘어나니 7글자를 쓴다. 성장 여유와 충돌 확률을 같이 본다.

### 인기 링크 하나에 클릭이 몰리면 어떻게 하나요?

먼저 Redis 같은 캐시가 받는다. 한 키에 몰리면 웹 서버 메모리에 몇 초짜리 로컬 캐시를 한 겹 더 두고, 기한이 끝날 때 한 요청만 DB에서 채우게 해 스탬피드를 막는다. 목적지가 거의 바뀌지 않으니 기한을 길게 잡고 무작위 시간을 더해 동시에 끝나지 않게 한다.

### 없는 키를 마구 찍어 보는 요청이 DB를 두드립니다. 어떻게 막나요?

없다는 결과를 빈 값으로 짧게 캐시하는 부정 캐시를 둔다. 같은 없는 키는 DB까지 가지 않는다. 키가 매번 다르면 부정 캐시로는 부족하니, 쓴 키를 담은 블룸 필터로 걸러 내고 IP별 요청 수 제한을 함께 건다. 404 비율 지표가 갑자기 오르면 이런 스캔을 의심한다.
