## 스테이징에서 확인한 이미지가 운영에서 결제를 못 받는다

스테이징에서 하루 동안 확인한 컨테이너 이미지를 운영에 그대로 올렸다. 화면은 잘 뜨고 로그인도 된다. 그런데 결제 건이 하나도 실제로 잡히지 않는다. 결제 대행사 대시보드에는 테스트 결제만 쌓이고 있다.

원인은 이미지 안에 있었다. Dockerfile의 `COPY . .`가 개발자 PC의 `.env` 파일까지 이미지에 넣었고, 앱은 시작할 때 이 파일을 읽는다. 운영 매니페스트에는 `DATABASE_URL`만 넣고 나머지 값은 빠뜨렸다. 같은 상황을 Node.js 22의 `--env-file`로 재현했다(Ubuntu 24.04).

```bash
# 이미지에 같이 들어간 .env (스테이징 값)
cat .env
# 스테이징: .env만으로 실행
node --env-file=.env app.mjs
# 운영: DATABASE_URL만 환경 변수로 넣고 실행
DATABASE_URL=postgres://prod-db:5432/app node --env-file=.env app.mjs
```

```text
--- 스테이징
DATABASE_URL=postgres://staging-db:5432/app
REDIS_URL=redis://staging-redis:6379
PAYMENT_MODE=sandbox
--- 운영 (DATABASE_URL만 넣음)
DATABASE_URL=postgres://prod-db:5432/app
REDIS_URL=redis://staging-redis:6379
PAYMENT_MODE=sandbox
```

환경 변수로 넣은 값은 파일보다 우선하니 DB는 운영으로 붙었다. 빠뜨린 두 값은 파일의 스테이징 값으로 조용히 채워졌다. 운영 서버가 스테이징 Redis에 세션을 쓰고, 결제는 샌드박스 모드로 돌았다. 에러는 한 줄도 없었다.

프런트엔드에서도 같은 일이 생긴다. Next.js의 `NEXT_PUBLIC_` 변수는 빌드할 때 자바스크립트 번들에 문자열로 박힌다. 스테이징 주소로 빌드한 이미지를 운영에 올리면 브라우저는 스테이징 API를 부른다. 실행할 때 환경 변수를 바꿔도 이미 박힌 값은 그대로다.

두 사고 모두 설정이 빌드 결과물에 섞여 들어가서 생겼다. 이런 실수를 구조적으로 막자고 정리한 것이 12요소 앱(The Twelve-Factor App)이다. Heroku 공동 창업자 Adam Wiggins가 2011년쯤 수많은 앱을 운영하며 얻은 원칙을 열두 항목으로 묶어 공개했다. Heroku 같은 PaaS를 전제로 썼지만, 컨테이너와 쿠버네티스가 사실상 그 원칙을 플랫폼 기능으로 만들어 놓았다. 그래서 지금 읽으면 "쿠버네티스가 왜 이렇게 생겼나"의 설명서처럼 읽힌다. 2024년 말에는 Heroku가 이 문서를 오픈소스로 돌려 커뮤니티가 요즘 환경에 맞게 고쳐 가고 있다.

열두 항목을 순서대로 외우기보다, 묶어서 보면 이해가 쉽다. 이 글은 "한 번 만들고 어디서나 돌리기", "언제든 늘리고 죽이기", "운영을 같은 방식으로" 세 묶음으로 읽는다.

## 코드는 하나, 배포는 여럿

첫째 항목(코드베이스)은 앱 하나에 저장소 하나, 그 저장소에서 여러 배포(개발, 스테이징, 운영)가 나온다는 것이다. 배포마다 브랜치를 따로 두고 코드를 조금씩 다르게 고치기 시작하면 "운영에만 있는 버그"가 생긴다. 환경별 차이는 코드가 아니라 설정이 맡는다.

모노레포라면 저장소 하나에 앱이 여럿 있으니 이 문장이 안 맞아 보인다. 요점은 "앱 하나가 하나의 코드 뿌리에서 나온다"는 것이라, 앱마다 빌드 단위가 분명하면 된다. 반대로 두 앱이 같은 코드를 복사해서 쓰고 있다면 그 코드는 라이브러리로 빼라는 것이 원래 권고다.

둘째 항목(의존성)은 의존성을 명시적으로 선언하고 격리하라는 것이다. `package.json`과 lockfile로 버전을 고정하고, 서버에 우연히 깔려 있던 `curl`이나 ImageMagick에 기대지 않는다. 컨테이너 이미지는 이 항목을 거의 자동으로 지키게 해 준다. 앱이 쓰는 시스템 패키지까지 Dockerfile에 적어야 이미지가 만들어지기 때문이다. lockfile이 왜 필요한지와 버전 충돌은 [의존성 지옥](/posts/dependency-hell)에 있다.

## 설정은 코드 밖에 둔다

셋째 항목(설정)이 처음 장면과 직결된다. 12요소에서 설정은 "배포마다 달라지는 것"이다. DB와 Redis 주소, 외부 API 키, 결제 모드, 도메인 이름이 여기에 든다. 이건 코드와 엄격하게 분리해 환경 변수로 넣으라고 한다. 반대로 라우팅 표나 의존성 주입 연결처럼 배포마다 같은 것은 설정이 아니라 코드다.

판별 기준도 하나 준다. "지금 이 저장소를 공개해도 비밀이 하나도 새지 않는가." 저장소에 `config/production.json`이 있고 그 안에 비밀번호가 있다면 이미 실패다.

환경 이름으로 설정을 묶는 방식(`development`, `staging`, `production` 묶음)도 피하라고 한다. 환경이 `qa`, `staging-2`, `perf`로 늘 때마다 묶음이 곱으로 늘고, 묶음 사이 차이를 아무도 모르게 된다. 값마다 독립된 변수로 두면 환경은 그 변수들의 조합일 뿐이다.

쿠버네티스에서는 ConfigMap과 Secret이 이 일을 한다. 이미지는 그대로 두고 환경마다 다른 ConfigMap을 붙인다.

```yaml
# 같은 이미지, 환경마다 다른 값
containers:
  - name: api
    image: registry.example.com/api@sha256:4f1c…   # 태그가 아니라 다이제스트로 고정
    envFrom:
      - configMapRef: { name: api-config }          # REDIS_URL, PAYMENT_MODE 등
    env:
      - name: DATABASE_URL
        valueFrom: { secretKeyRef: { name: api-db, key: url } }
```

ConfigMap이 언제 Pod에 닿는지(환경 변수는 시작할 때 한 번, 마운트한 파일은 늦게 바뀜)는 [ConfigMap](/posts/k8s-configmap)에서 실제로 재 봤다.

설정을 밖으로 뺐으면 앱은 시작할 때 설정을 검사하고, 빠진 값이 있으면 바로 죽어야 한다. 처음 장면의 사고는 빠진 값을 기본값이나 파일로 조용히 채워서 생겼다. 운영에서 "일단 뜨고 나중에 이상하게 동작하는" 것보다 "아예 안 뜨는" 쪽이 훨씬 빨리 발견된다. 쿠버네티스라면 Pod가 `CrashLoopBackOff`에 빠지고 롤링 배포가 멈춰 옛 버전이 계속 서비스한다.

```bash
# DATABASE_URL 없이 띄우면 바로 죽는다
node server.mjs; echo "exit=$?"
```

```text
{"level":"fatal","msg":"DATABASE_URL is not set"}
exit=1
```

검사하는 함수를 직접 써 보자. 필수 값은 없으면 에러, 숫자는 범위를 보고, 기본값은 정말로 어느 환경에서나 같은 값일 때만 둔다. 에러는 첫 하나에서 멈추지 말고 모두 모아서 보여 준다. 그래야 배포를 한 번 실패할 때 빠진 값을 한꺼번에 고친다.

## 환경 변수가 맞지 않게 된 것들

12요소가 쓰일 당시 환경 변수는 "언어와 OS에 상관없이 어디서나 쓸 수 있는 표준"이라 골랐다. 지금 보면 두 가지가 맞지 않는다.

하나는 비밀 값이다. 환경 변수는 생각보다 많은 곳에 보인다. 같은 사용자로 도는 다른 프로세스가 `/proc/PID/environ`으로 읽을 수 있고, 자식 프로세스에 그대로 물려지며, 에러 리포터가 크래시 때 환경을 통째로 보내기도 하고, `kubectl describe pod`에는 Secret이 아니라 평문 `value`로 넣은 변수가 그대로 찍힌다. 그래서 비밀 값은 파일로 마운트하거나, 앱이 시작할 때 비밀 저장소에서 짧게 빌려 오는 방식을 권한다. 어디로 새는지와 동적 비밀, 회전은 [비밀 관리](/posts/secrets-management)에서 직접 재현했다. 12요소의 정신(코드와 분리, 배포마다 주입)은 그대로이고, 전달 수단만 환경 변수에서 파일과 저장소로 옮겨 간 셈이다.

다른 하나는 크고 자주 바뀌는 설정이다. 기능 플래그, 사용자 비율, 요금표처럼 구조가 있고 재시작 없이 바꾸고 싶은 값은 환경 변수에 맞지 않는다. 환경 변수는 프로세스가 시작할 때 한 번 읽히기 때문이다. 이런 값은 [기능 플래그](/posts/feature-flags) 시스템이나 설정 서버에 두고, 환경 변수에는 "그 서버의 주소"만 둔다.

## DB도 갈아 끼우는 부품이다

넷째 항목(백엔드 서비스)은 DB, 캐시, 메시지 큐, 메일 발송 같은 바깥 서비스를 모두 "붙였다 뗄 수 있는 자원"으로 다루라는 것이다. 앱이 같은 서버에 깔린 PostgreSQL을 쓰든 관리형 RDS를 쓰든, 코드는 같고 `DATABASE_URL`만 다르다. DB 장애가 나서 복제본으로 바꿀 때 코드를 고치지 않고 주소만 바꾼다.

이 항목을 어기는 흔한 모습은 "로컬 서비스는 특별 취급"이다. 개발 환경에서는 `localhost`의 Redis를 코드에 박아 두고, 운영에서만 설정으로 바꾸는 식이다. 그러면 개발 환경에서 Redis를 끄고 켜는 실험을 할 수 없고, 설정 이름이 운영에서 처음 쓰인다.

## 빌드, 릴리스, 실행을 섞지 않는다

다섯째 항목이 처음 장면의 정답이다. 배포는 세 단계로 엄격히 나뉜다. 빌드는 코드와 의존성을 실행 가능한 묶음(지금은 컨테이너 이미지)으로 만든다. 릴리스는 그 묶음에 특정 환경의 설정을 붙인 것이고, 고유 ID를 갖는다. 실행은 그 릴리스를 프로세스로 띄운다. 아래 그림에서 점이 흐르는 방향을 따라가 보자.

이미지 화살표가 두 릴리스로 똑같이 갈라진다. 스테이징에서 확인한 것은 이미지 `sha256:4f1c…`이고, 운영에는 바로 그 이미지가 간다. 빌드를 환경마다 다시 하면 스테이징에서 본 것과 운영에 올라간 것이 다른 바이트가 된다. 그 사이 의존성의 새 패치 버전이 끼어들 수도 있다.

설정을 이미지에 굽지 말아야 하는 이유가 여기서 정리된다.

- 같은 이미지를 환경 사이에서 승격(promote)할 수 없다. 환경마다 빌드해야 하니 "확인한 것을 그대로 올린다"는 보장이 깨진다.
- 비밀 값이 이미지 레이어에 남는다. 나중 레이어에서 파일을 지워도 앞 레이어에는 남아 있어, 레지스트리에서 이미지를 받을 수 있는 사람은 모두 꺼낼 수 있다. [Dockerfile과 이미지 레이어](/posts/dockerfile-image-layers)에 이 동작이 있다.
- 설정만 바꾸고 싶어도 빌드와 테스트를 다시 돌아야 한다. 장애 중에 타임아웃 값 하나를 바꾸려고 20분짜리 파이프라인을 기다리게 된다.

릴리스에 고유 ID가 있으면 되돌리기도 단순해진다. 이전 릴리스(이전 이미지 다이제스트 + 이전 설정)로 다시 실행하면 된다. 실무에서 걸리는 지점은 두 가지다. 이미지 태그(`api:latest`, `api:1.4`)는 다시 밀어 넣으면 다른 이미지를 가리키니, 매니페스트에는 다이제스트를 쓰거나 태그를 불변으로 운영한다. 그리고 ConfigMap을 고쳐도 Deployment는 바뀌지 않아 롤링이 일어나지 않고, 롤백해도 설정은 돌아가지 않는다. 설정 해시를 Pod 템플릿 애너테이션에 넣거나, Kustomize의 `configMapGenerator`처럼 이름에 해시를 붙여 설정 변경을 새 릴리스로 만든다. Helm은 차트와 값을 묶어 릴리스 리비전으로 기록하니 이 항목을 그대로 구현한 셈이다([Helm 기초](/posts/helm-basics)).

## 이미지에 설정이 섞였는지 확인하기

처음 장면 같은 사고를 의심할 때 확인할 곳은 세 군데다. 이미지 안의 파일, 이미지 메타데이터에 박힌 환경 변수, 그리고 실제로 떠 있는 프로세스가 본 값이다.

```bash
# 1) 이미지 안에 .env나 환경별 설정 파일이 들어 있는지 (작업 디렉터리가 /app이라고 가정)
docker run --rm --entrypoint sh registry.example.com/api:1.4 -c 'ls -la /app | grep -i -E "env|config"'

# 2) Dockerfile의 ENV·ARG로 이미지에 박힌 값 (Config.Env 배열)
docker image inspect registry.example.com/api:1.4 --format '{{json .Config.Env}}'

# 3) 레이어마다 어떤 명령으로 만들어졌는지 (ARG로 넘긴 값이 명령 줄에 남기도 한다)
docker history --no-trunc registry.example.com/api:1.4

# 4) 운영 Pod 안의 프로세스가 실제로 본 환경 변수 (비밀 값이 화면에 찍히니 주의)
kubectl exec deploy/api -- printenv | grep -E '^(REDIS_URL|PAYMENT_MODE)='
```

1번에서 `.env`가 보이면 `.dockerignore`가 빠진 것이다. 2번의 `Config.Env`에는 `PATH`나 `NODE_VERSION` 같은 런타임 값만 있어야 하고, 주소나 키가 보이면 Dockerfile의 `ENV`에 설정이 들어간 것이다. 3번은 빌드 인자로 비밀을 넘긴 흔적을 찾는 용도다. 4번에서 값이 스테이징을 가리키면 원인은 매니페스트에서 빠진 변수다.

고치는 쪽은 간단하다. 빌드 컨텍스트에서 설정 파일을 빼고, 앱이 설정 파일을 읽더라도 운영에서는 읽지 않게 한다.

```text
# .dockerignore
.env
.env.*
!.env.example
*.pem
config/local*.json
```

`.env.example`은 변수 이름과 설명만 담은 견본이라 저장소와 이미지에 남겨 둬도 된다. 앞의 `parseConfig` 같은 검사가 있으면, 이미지에서 `.env`를 뺀 순간 운영 매니페스트에 빠진 변수가 시작 실패로 바로 드러난다. 그게 원하는 결과다.

## 프로세스는 아무것도 기억하지 않는다

여섯째 항목(프로세스)은 앱 프로세스가 무상태(stateless)이고 서로 아무것도 공유하지 않아야 한다는 것이다. 남겨야 하는 상태는 모두 DB나 Redis 같은 백엔드 서비스에 둔다. 프로세스 메모리와 로컬 디스크는 요청 하나를 처리하는 동안의 임시 공간일 뿐이다.

어기면 바로 증상이 보인다. 세션을 프로세스 메모리에 두면 로드 밸런서가 다른 Pod로 보낸 순간 로그아웃된다. 이걸 스티키 세션으로 막으면 그 Pod가 죽을 때 그 Pod의 사용자가 모두 로그아웃된다. 업로드 파일을 컨테이너 디스크에 쓰면 Pod가 재시작될 때 사라지고, 다른 Pod에서는 처음부터 안 보인다. 세션을 Redis로 옮기는 과정과 스티키 세션의 대가는 [무상태 웹 서버](/posts/sd-load-balancer-stateless)에 있다.

일곱째 항목(포트 바인딩)은 앱이 스스로 HTTP 서버를 띄워 포트로 서비스를 내놓으라는 것이다. 예전 자바 서버처럼 WAR 파일을 이미 떠 있는 Tomcat에 끼워 넣는 방식이 아니라, Spring Boot의 내장 서버나 Node의 `http.createServer`처럼 앱 안에 서버가 들어 있다. 포트 번호도 설정이라 `PORT` 환경 변수로 받는다. 쿠버네티스의 Service가 그 포트를 묶어 다른 앱에 내놓는다. 그러면 이 앱 자체가 다른 앱의 백엔드 서비스가 될 수 있다.

여덟째 항목(동시성)은 늘릴 때 프로세스를 더 띄우는 방식으로 늘리라는 것이다. 웹 요청을 받는 프로세스, 큐를 처리하는 워커, 주기 작업을 도는 프로세스를 "프로세스 종류"로 나누고, 종류마다 개수를 따로 정한다. 쿠버네티스에서는 종류마다 Deployment를 하나씩 두고 HPA로 개수를 정하는 모습이 된다. 웹은 CPU로, 워커는 큐 길이로 늘리는 식이다([HPA](/posts/k8s-hpa)). 앱이 직접 데몬이 되거나 PID 파일을 쓰지 않고, 프로세스 관리는 systemd나 쿠버네티스 같은 바깥 관리자에게 맡긴다.

여섯째부터 여덟째까지가 한 묶음이다. 아무것도 기억하지 않으니(무상태) 어느 프로세스가 요청을 받아도 같고, 그래서 개수를 마음대로 늘릴 수 있다(동시성). 그리고 마음대로 줄일 수도 있어야 한다. 그게 다음 항목이다.

## 언제 죽여도 괜찮아야 한다

아홉째 항목(폐기 가능성, disposability)은 프로세스가 빨리 뜨고, SIGTERM을 받으면 깔끔하게 끝나고, 갑자기 죽어도 데이터가 깨지지 않아야 한다는 것이다. 쿠버네티스에서는 롤링 배포, 노드 비우기(drain), 오토스케일러의 축소가 모두 "Pod에 SIGTERM을 보내고 기다린다"로 일어난다. 기본 유예 시간(`terminationGracePeriodSeconds`)은 30초이고, 그 안에 안 끝나면 SIGKILL이다.

SIGTERM을 무시하는 서버와 처리하는 서버를 비교했다. 2초 걸리는 요청을 보내 놓고 0.5초 뒤에 SIGTERM을 보냈다.

```bash
# GRACEFUL=0은 처리기 없이, 1은 SIGTERM 처리기를 켜고 띄운다
for G in 0 1; do
  echo "--- GRACEFUL=$G"
  PORT=18080 DATABASE_URL=postgres://db:5432/app GRACEFUL=$G node server.mjs & P=$!
  sleep 0.5
  # 2초 걸리는 요청을 보내 놓고
  curl -sS -w 'curl http=%{http_code} time=%{time_total}\n' "http://127.0.0.1:18080/work?ms=2000" & C=$!
  # 0.5초 뒤 서버에 SIGTERM
  sleep 0.5; kill -TERM $P
  wait $C; wait $P; echo "server exit=$?"
done
```

```text
--- GRACEFUL=0
{"ts":"2026-10-23T12:49:39.248Z","level":"info","msg":"listening","port":18080}
curl: (52) Empty reply from server
curl http=000 time=0.502532
server exit=143
--- GRACEFUL=1
{"ts":"2026-10-23T12:49:40.270Z","level":"info","msg":"listening","port":18080}
{"ts":"2026-10-23T12:49:41.201Z","level":"info","msg":"SIGTERM received, draining"}
ok
{"ts":"2026-10-23T12:49:42.712Z","level":"info","msg":"request done","path":"/work?ms=2000"}
curl http=200 time=2.007856
{"ts":"2026-10-23T12:49:42.714Z","level":"info","msg":"closed, exit 0"}
server exit=0
```

처리기가 없으면 Node는 SIGTERM에 바로 죽는다(종료 코드 143 = 128 + 15). 처리 중이던 요청은 응답 없이 끊겼다(`Empty reply from server`). 처리기를 둔 쪽은 새 연결을 그만 받고(`server.close()`), 처리 중인 요청이 끝나기를 기다렸다가 0으로 나갔다. 사용자는 200을 받았다. 처리기는 이 정도면 된다.

```js
process.on("SIGTERM", () => {
  log({ level: "info", msg: "SIGTERM received, draining" });
  server.close(() => process.exit(0));            // 새 연결 거절, 진행 중인 요청은 마저 처리
  setTimeout(() => process.exit(1), 25000).unref(); // 유예 시간(30초)보다 조금 짧게 스스로 끊는다
});
```

다만 이것만으로는 롤링 배포 중 에러가 0이 되지 않는다. 같은 서버를 18081 포트로 띄워 긴 요청을 걸어 둔 채 SIGTERM을 보내고, 0.2초 뒤에 새 요청을 보내 봤다.

```text
curl: (7) Failed to connect to 127.0.0.1 port 18081 after 0 ms: Couldn't connect to server
```

`server.close()` 이후 들어온 연결은 거절된다. 쿠버네티스는 SIGTERM과 "이 Pod를 엔드포인트에서 빼라"를 동시에 시작하는데, 로드 밸런서와 각 노드의 kube-proxy가 이걸 반영하기까지 몇 초가 걸린다. 그 사이 들어온 요청이 이 거절을 받는다. 그래서 `preStop`에 짧은 `sleep`을 두어 엔드포인트에서 빠질 시간을 벌고 나서 SIGTERM을 받게 한다. 이 순서와 PID 1이 시그널을 넘기지 않는 문제(셸 형태 `CMD`, `npm start`)는 [Pod의 일생](/posts/k8s-pod-lifecycle)에, 롤링 배포에서 빼고 넣는 순서는 [롤링 배포](/posts/rolling-deployment)에 실측과 함께 있다.

큐 워커는 사정이 조금 다르다. 웹 요청은 몇 초 안에 끝나지만 작업 하나가 몇 분일 수 있다. 워커가 지켜야 할 것은 "받은 작업을 잃어버리지 않는다"는 것이다. 아래 그림에서 단계를 넘기면 축소되는 워커가 작업을 어떻게 넘기는지 보인다.

마지막 단계가 이 항목의 진짜 요구다. 깔끔한 종료는 대부분의 경우를 좋게 만들지만, 전원이 나가거나 OOM으로 SIGKILL을 맞는 경우는 처리기가 돌 기회가 없다. 그래서 "갑자기 죽어도 괜찮게" 설계한다. 작업은 확인하기 전까지 큐에 남게 하고, 다시 돌아도 같은 결과가 나오게 만든다. 이 둘이 있으면 종료 처리는 손실을 막는 장치가 아니라 재처리를 줄이는 최적화가 된다.

빨리 뜨는 것도 같은 항목이다. 시작에 2분이 걸리는 앱은 트래픽이 몰려 늘려야 할 때 2분 동안 늘지 않고, 롤링 배포도 그만큼 길어진다. 시작할 때 캐시를 통째로 데우거나 큰 파일을 내려받는 일은 미리 해 두거나 뒤로 미룬다. 정말 오래 걸린다면 startup 프로브로 그동안 liveness 검사를 미룬다.

## 개발 환경을 운영과 닮게 둔다

열째 항목(개발/운영 일치)은 개발과 운영 사이의 세 가지 간격을 줄이라는 것이다. 시간 간격(코드를 쓰고 운영에 올라가기까지 몇 주), 사람 간격(개발자가 쓰고 운영팀이 배포), 도구 간격(개발은 SQLite, 운영은 PostgreSQL)이다. 처음 두 간격은 지금은 CI/CD와 DevOps 문화로 많이 좁혀졌다. 남은 것은 도구 간격이다.

개발에서 SQLite나 메모리 DB를 쓰면 편하지만, 운영의 PostgreSQL과는 잠금, 트랜잭션 격리, 날짜 함수, 대소문자 비교가 다르다. 테스트는 다 통과했는데 운영에서 `ON CONFLICT` 구문이나 JSON 연산자가 실패하는 식이다. 지금은 Docker Compose로 운영과 같은 버전의 PostgreSQL과 Redis를 개발 PC에 띄우고, 통합 테스트는 Testcontainers로 진짜 DB를 띄워 돌리는 것이 흔하다([Docker Compose](/posts/docker-compose), [진짜 DB로 하는 통합 테스트](/posts/integration-tests-real-db)). 버전까지 맞춘다. 개발은 PostgreSQL 16인데 운영이 14라면 개발에서 쓴 문법이 운영에서 없다.

## 로그는 흘려보내기만 한다

열한째 항목(로그)은 앱이 로그 파일을 관리하지 말고 표준 출력(stdout)으로 이벤트를 한 줄씩 흘려보내기만 하라는 것이다. 어디에 모을지, 얼마나 보관할지, 어떻게 돌릴지(rotate)는 실행 환경이 정한다. 앞의 데모 서버도 `process.stdout.write`로 JSON 한 줄씩 쓰기만 했다.

컨테이너에서는 이게 거의 강제된다. 컨테이너 런타임이 stdout과 stderr를 노드의 파일로 받아 두고, `kubectl logs`가 그걸 읽고, Fluent Bit 같은 수집기가 노드에서 그 파일을 읽어 중앙 저장소로 보낸다. 앱이 컨테이너 안의 `/var/log/app.log`에 쓰면 `kubectl logs`에는 아무것도 안 보이고, 디스크가 차면 Pod가 축출(evict)되며, Pod가 사라지면 로그도 같이 사라진다. 로그를 한 줄 JSON으로 남겨 나중에 묻기 쉽게 하는 방법은 [구조화 로그](/posts/structured-logging)에 있다.

12요소는 로그만 말한다. 지금은 지표(metrics)와 추적(trace)도 같은 위치에 둔다. 2016년 Kevin Hoffman이 쓴 "Beyond the Twelve-Factor App"은 여기에 텔레메트리, API 우선 설계, 인증·인가를 더해 15개 항목으로 늘렸다. 관측 신호 세 가지의 관계는 [관측 가능성 기초](/posts/observability-basics)에서 다룬다.

## 관리 작업도 같은 릴리스로 돌린다

열두째 항목(관리 프로세스)은 DB 마이그레이션, 데이터 보정 스크립트, 콘솔 접속 같은 일회성 작업을 앱과 같은 릴리스(같은 코드, 같은 설정)로, 같은 환경에서 돌리라는 것이다. 개발자 PC에서 운영 DB로 직접 마이그레이션을 돌리면 PC의 코드 버전과 운영 이미지가 다를 수 있다.

쿠버네티스라면 같은 이미지로 Job을 하나 띄우는 모습이 된다.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: api-migrate-p17
spec:
  backoffLimit: 0                 # 마이그레이션은 실패하면 자동 재시도하지 않는다
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: registry.example.com/api@sha256:4f1c…   # 앱과 같은 다이제스트
          command: ["node", "dist/migrate.js"]
          envFrom:
            - configMapRef: { name: api-config }
```

`kubectl exec`로 떠 있는 Pod에 들어가 스크립트를 돌리는 것도 같은 릴리스이긴 하다. 하지만 그 Pod가 작업 도중 롤링 배포로 내려가면 스크립트도 같이 죽고, 무엇을 돌렸는지 기록도 남지 않는다. Job은 실행 기록과 로그가 남는다. 마이그레이션을 배포 전에 돌릴지 후에 돌릴지, 여러 Pod가 동시에 돌리지 않게 잠그는 방법은 [마이그레이션 도구](/posts/db-migration-tools)와 [Job과 CronJob](/posts/k8s-job-cronjob)에 있다.

## 쿠버네티스에서는 누가 맡나

열두 항목을 다 읽고 나면 대부분이 쿠버네티스 오브젝트 하나씩에 대응한다는 게 보인다. 플랫폼이 원칙을 강제하는 곳과, 여전히 앱이 지켜야 하는 곳을 나눠 보면 이렇다.

- 플랫폼이 거의 강제한다: 의존성 격리(이미지), 포트 바인딩(`containerPort`와 Service), 동시성(Deployment의 `replicas`와 HPA), 로그(컨테이너 stdout 수집), 관리 프로세스(Job).
- 플랫폼이 도구를 주지만 쓰는 건 사람이다: 설정(ConfigMap·Secret, 그러나 이미지에 굽는 건 막지 못한다), 빌드·릴리스·실행(다이제스트와 리비전, 그러나 `latest` 태그를 쓰면 무너진다), 백엔드 서비스(Service와 외부 주소).
- 앱 코드가 지켜야 한다: 무상태(세션과 파일을 어디에 두나), 폐기 가능성(SIGTERM 처리, 빠른 시작, 멱등한 작업), 개발/운영 일치(개발 환경을 어떻게 꾸리나), 그리고 설정 검사.

면접에서 "쿠버네티스를 쓰면 12요소는 자동으로 지켜지나"라고 물으면 셋째 묶음을 답하면 된다. 플랫폼은 SIGTERM을 보내 줄 뿐, 받아서 무엇을 할지는 앱이 정한다.

## 12요소가 말하지 않는 것

12요소는 웹 앱과 워커를 위한 원칙이다. 모든 것에 그대로 맞지는 않는다.

DB, Kafka 브로커, 검색 엔진처럼 상태 자체가 본업인 프로그램은 무상태가 될 수 없다. 쿠버네티스에서는 이런 것을 StatefulSet과 영구 볼륨으로 따로 다루고, 12요소 앱 입장에서는 "백엔드 서비스"로 바깥에 둔다. 앱을 무상태로 만든다는 건 상태를 없앤다는 뜻이 아니라 상태를 이런 서비스로 몰아넣는다는 뜻이다.

설정을 모두 밖으로 빼다 보면 설정이 코드만큼 커진다. 환경 변수가 80개인 서비스는 무엇이 필수이고 무엇이 기본값으로 충분한지 아무도 모른다. 앞의 `parseConfig`처럼 앱 안에 설정 스키마를 한곳에 두고, 그 스키마에서 문서와 검사를 함께 만드는 편이 낫다.

그리고 12요소는 보안과 관측을 거의 말하지 않는다. 앞에서 본 비밀 값 전달, 지표와 추적, 서비스 사이 인증은 원래 목록 밖에 있다. 그래서 면접에서 12요소를 물으면 열두 항목을 외워 말하기보다, 어떤 항목이 쿠버네티스의 어떤 기능으로 이어졌는지, 지금은 어디를 보완해야 하는지를 함께 말하는 편이 좋다.

## 한 번 만들고, 어디서나 돌리고, 언제든 죽인다

12요소를 한 문장으로 줄이면 이렇다. 이미지는 한 번 만들고 설정은 배포할 때 붙이며, 프로세스는 아무것도 기억하지 않아서 늘리고 죽이기가 자유롭다. 처음 장면의 결제 사고는 설정이 이미지에 섞여 들어가고, 빠진 값을 앱이 조용히 채워서 생겼다. 설정을 밖에 두고 시작할 때 검사했다면 운영 Pod는 뜨지도 않았고, 옛 버전이 계속 결제를 받았을 것이다.

## 면접에서 나올 만한 질문

### 12요소 앱이 무엇이고 왜 나왔나요?

Heroku가 수많은 앱을 운영하며 얻은 원칙을 2011년쯤 열두 항목으로 정리한 것이다. 같은 앱을 여러 환경에 안전하게 배포하고, 프로세스를 늘리고 줄이기 쉽게 만드는 것이 목표다. 설정은 환경에, 프로세스는 무상태로, 로그는 stdout으로, 빌드·릴리스·실행은 분리하라는 것이 대표적이다. 컨테이너와 쿠버네티스가 이 원칙 대부분을 플랫폼 기능으로 만들어 두었다.

### 설정을 이미지에 구우면 안 되는 이유는요?

같은 이미지를 스테이징에서 운영으로 승격할 수 없게 되기 때문이다. 환경마다 다시 빌드하면 확인한 바이트와 운영에 올라간 바이트가 달라진다. 비밀 값이 이미지 레이어에 남아 레지스트리 접근 권한만 있으면 꺼낼 수 있고, 설정 하나 바꾸는 데도 빌드와 테스트를 다시 돌아야 한다. 빠진 값이 이미지 안의 스테이징 값으로 조용히 채워지는 사고도 생긴다.

### 환경 변수로 비밀 값을 넘기는 건 지금도 괜찮은가요?

12요소는 환경 변수를 권했지만 지금은 비밀 값에는 권하지 않는다. 환경 변수는 `/proc/PID/environ`, 자식 프로세스, 크래시 리포트, 평문 매니페스트로 새기 쉽다. 비밀은 파일로 마운트하거나 시작할 때 비밀 저장소에서 짧게 빌려 온다. 코드와 분리해 배포마다 주입한다는 원칙은 그대로이고 전달 수단만 바뀐 것이다.

### 빌드, 릴리스, 실행을 나누면 무엇이 좋아지나요?

이미지 하나를 만들어 환경마다 설정만 붙여 릴리스로 만들 수 있어서, 확인한 것을 그대로 올리고 이전 릴리스로 바로 되돌릴 수 있다. 쿠버네티스에서는 이미지 다이제스트와 ConfigMap 버전이 릴리스가 된다. 다만 ConfigMap만 고치면 롤링이 일어나지 않으니 설정 해시를 Pod 템플릿에 넣거나 이름에 해시를 붙여 설정 변경도 새 릴리스로 만든다.

### 폐기 가능성은 롤링 배포와 어떻게 이어지나요?

롤링 배포, 축소, 노드 비우기가 모두 Pod에 SIGTERM을 보내고 유예 시간을 기다리는 방식으로 일어나기 때문이다. 앱이 SIGTERM을 무시하면 처리 중인 요청이 끊기고, 처리하면 새 연결을 멈추고 진행 중인 요청을 끝낸 뒤 나간다. 엔드포인트에서 빠지는 데 시간이 걸리니 `preStop`에 짧은 sleep을 둔다. 갑자기 죽는 경우도 있으니 작업은 확인 전까지 큐에 남게 하고 멱등하게 만든다.

### 무상태 프로세스를 지키지 않으면 어떤 문제가 생기나요?

세션을 메모리에 두면 다른 Pod로 요청이 갈 때 로그아웃되고, 스티키 세션으로 막으면 그 Pod가 죽을 때 그 사용자들이 모두 끊긴다. 로컬 디스크에 둔 업로드 파일은 재시작하면 사라지고 다른 Pod에서는 안 보인다. 상태를 Redis나 DB, 객체 저장소 같은 백엔드 서비스로 옮겨야 개수를 자유롭게 늘리고 줄일 수 있다.

### 로그를 파일 대신 stdout으로 쓰라는 이유는요?

로그를 어디에 모으고 얼마나 보관할지는 실행 환경이 정할 일이라서다. 컨테이너에서는 런타임이 stdout을 받아 `kubectl logs`와 수집기가 읽는다. 앱이 컨테이너 안 파일에 쓰면 `kubectl logs`에 안 보이고, 디스크가 차면 축출되며, Pod와 함께 로그도 사라진다.

### 12요소에서 지금 보완해야 할 부분은요?

비밀 값 전달, 관측, 크고 자주 바뀌는 설정이다. 비밀은 파일이나 비밀 저장소로, 지표와 추적은 로그와 함께 표준으로 내보내고, 기능 플래그처럼 재시작 없이 바꿀 값은 설정 서버에 둔다. "Beyond the Twelve-Factor App"이 텔레메트리와 인증·인가 같은 항목을 더한 것도 같은 이유다. DB처럼 상태가 본업인 프로그램은 무상태 원칙의 대상이 아니라 백엔드 서비스로 둔다.
