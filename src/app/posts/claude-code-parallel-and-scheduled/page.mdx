터미널 두 개에 Claude Code를 하나씩 띄웠다. 한쪽에는 가격 계산 버그를, 다른 쪽에는 로그인 기능을 맡겼다. 둘 다 같은 폴더에서 일한다. 몇 분 뒤 한 세션이 테스트를 돌리려고 `git stash`를 하자, 다른 세션이 방금 고친 파일이 사라졌다. 다시 꺼내자 두 세션의 변경이 한 커밋에 섞였다. 사람 둘이 키보드 하나를 나눠 쓰는 꼴이다.

이 글은 Claude Code를 여러 개 동시에, 또는 내가 없는 시간에 돌리는 방법을 다룬다. 앞부분은 git worktree로 세션마다 작업 폴더를 나누는 이야기이고 실제 명령 출력과 함께 본다. 뒷부분은 시간을 축으로 한 기능들이다. 세션 안에서 같은 프롬프트를 되풀이하는 `/loop`, 조건이 맞을 때까지 턴을 이어 가는 `/goal`, 노트북을 덮어도 클라우드에서 도는 예약 작업, 그리고 결과를 링크 하나로 남기는 아티팩트다.

worktree 명령 자체는 [Git 고급 기능 글](/posts/git-tips-advanced)에 정리해 두었으니 여기서는 에이전트를 여럿 돌릴 때 생기는 문제에 집중한다. 한 세션의 컨텍스트를 다루는 법은 [컨텍스트 창 글](/posts/claude-code-context-window)에 있다. 기능 설명은 2026년 10월의 공식 문서(code.claude.com/docs)와 Claude Code 2.1.306 CLI 기준이다. 기능이 빠르게 바뀌고 일부는 research preview라서, 이름과 한도는 바뀔 수 있다.

## 한 폴더에 세션 둘을 띄우면

같은 폴더에서 세션 둘이 일하면 파일, 브랜치, 인덱스(staging area)를 전부 나눠 쓴다. 한쪽이 브랜치를 바꾸면 다른 쪽의 작업 파일이 통째로 바뀌고, 한쪽이 포매터를 돌리면 다른 쪽이 고치던 파일까지 건드린다. 각 세션의 체크포인트도 다른 세션이 고친 파일은 추적하지 않아서, 되감아도 서로의 흔적이 섞여 남는다.

해법은 세션마다 작업 폴더를 따로 주는 것이다. clone을 하나 더 하면 되지만 저장소 크기만큼 디스크를 더 쓰고, 한쪽 커밋을 다른 쪽에서 보려면 push와 fetch를 거쳐야 한다. git worktree는 `.git` 하나를 공유하면서 작업 폴더만 여러 개 만든다. 객체와 브랜치가 하나라서 한쪽 커밋이 다른 쪽에서 바로 보이고, 작업 파일과 인덱스와 HEAD는 폴더마다 따로다.

## 저장소 하나에 작업 폴더 셋

Claude Code가 `--worktree`로 만드는 모양을 손으로 흉내 내 봤다. 기본 위치가 저장소 루트의 `.claude/worktrees/<이름>/`이고 브랜치 이름이 `worktree-<이름>`이라서 그대로 따랐다. 데모 저장소는 임시 폴더에 만들었고, 출력의 긴 경로는 `~`로 줄였다(Git 2.43).

```bash
git worktree add .claude/worktrees/fix-price -b worktree-fix-price   # 세션 A의 작업 폴더
git worktree add .claude/worktrees/add-auth -b worktree-add-auth     # 세션 B의 작업 폴더
git worktree list                                                    # 연결된 작업 폴더 목록
```

```text
$ git worktree add .claude/worktrees/fix-price -b worktree-fix-price
Preparing worktree (new branch 'worktree-fix-price')
HEAD is now at e51c88e init shop
$ git worktree add .claude/worktrees/add-auth -b worktree-add-auth
Preparing worktree (new branch 'worktree-add-auth')
HEAD is now at e51c88e init shop
$ git worktree list
~/shop                              e51c88e [main]
~/shop/.claude/worktrees/add-auth   e51c88e [worktree-add-auth]
~/shop/.claude/worktrees/fix-price  e51c88e [worktree-fix-price]
```

`list`의 세 줄이 같은 커밋 `e51c88e`에서 출발한 세 작업 폴더다. 대괄호 안이 각 폴더에 꺼내진 브랜치다. 여기서 규칙 하나가 바로 보인다. 같은 브랜치는 두 폴더에 동시에 꺼낼 수 없다.

```text
$ git worktree add .claude/worktrees/again worktree-fix-price
Preparing worktree (checking out 'worktree-fix-price')
fatal: 'worktree-fix-price' is already used by worktree at '~/shop/.claude/worktrees/fix-price'
```

이 제약이 오히려 안전장치다. 두 세션이 같은 브랜치를 꺼내면 한쪽이 커밋할 때 다른 쪽의 작업 폴더가 브랜치 끝과 어긋난다. Git이 그 상황을 처음부터 막는다. 그래서 에이전트마다 브랜치를 하나씩 준다.

## 각자 커밋하고 한곳에서 합친다

두 폴더에서 각각 고치고 커밋한 뒤 원래 폴더로 돌아와 봤다. 원래 폴더의 `git status`는 비어 있다. 다른 폴더의 변경이 이쪽 작업 파일에는 전혀 닿지 않았다.

```text
$ git status --short
$ git log --oneline --all --graph
* c5d0b45 feat: block inactive users
| * 4364d0e fix: add VAT to price
|/  
* e51c88e init shop
$ git merge --no-edit worktree-fix-price
Updating e51c88e..4364d0e
Fast-forward
 src/price.js | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git merge --no-edit worktree-add-auth
Merge made by the 'ort' strategy.
 src/auth.js | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

`--all` 그래프에서 두 브랜치가 `e51c88e`에서 갈라진 것이 보인다. 둘이 다른 파일을 고쳤으니 첫 merge는 fast-forward, 두 번째는 충돌 없는 merge 커밋이다.

worktree가 막아 주는 것은 작업 중의 충돌이지 합칠 때의 충돌이 아니다. 세션 둘에게 같은 파일을 고치게 하면 결국 merge에서 만난다. 할인을 넣는 세션과 반올림을 바꾸는 세션에게 둘 다 `price.js`를 맡겨 봤다.

```text
$ git merge --no-edit worktree-discount
Updating 2069d98..38c3540
Fast-forward
 src/price.js | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git merge --no-edit worktree-rounding
Auto-merging src/price.js
CONFLICT (content): Merge conflict in src/price.js
Automatic merge failed; fix conflicts and then commit the result.
$ cat src/price.js
<<<<<<< HEAD
export function price(p){ return Math.round(p * 1.1 * 0.9); }
=======
export function price(p){ return Math.ceil(p * 1.1); }
>>>>>>> worktree-rounding
```

같은 줄을 두 세션이 서로 모르는 채로 고쳤다. 이 충돌은 기계적으로 풀 수 없다. 할인 뒤에 올림을 할지, 올림 뒤에 할인할지는 요구 사항의 문제다. 그래서 병렬로 맡길 때는 일을 나누는 단계에서 파일이 겹치지 않게 자른다. 문서도 agent teams처럼 worktree를 쓰지 않는 방식에서는 팀원마다 맡을 파일 묶음을 나누라고 권한다. 충돌 해결 자체는 [병합 충돌 글](/posts/git-merge-conflict)에 있다.

## 파일은 갈라져도 포트와 DB는 하나다

worktree는 fresh checkout이라 Git이 추적하지 않는 파일은 따라오지 않는다. 데모 저장소의 `.env`는 `.gitignore`에 있어서 새 작업 폴더에 없다.

```text
$ ls -a .claude/worktrees/fix-price
.
..
.git
.gitignore
src
$ cat .claude/worktrees/fix-price/.env
cat: .claude/worktrees/fix-price/.env: No such file or directory
```

새 폴더의 `.git`은 디렉터리가 아니라 공유 저장소를 가리키는 작은 파일이다. `node_modules`도 없으니 의존성은 폴더마다 다시 설치해야 한다. Claude Code는 이 문제에 `.worktreeinclude`를 둔다. 저장소 루트에 `.gitignore` 문법으로 적으면, Claude가 만드는 worktree에 패턴과 맞으면서 gitignore된 파일만 복사한다. 추적되는 파일은 이미 checkout으로 오니까 복사하지 않는다.

```text
.env
.env.local
config/secrets.json
```

더 까다로운 것은 컴퓨터 단위의 자원이다. 두 폴더에서 같은 dev 서버를 띄워 봤다(Node 22).

```text
$ node ~/server.cjs   # discount 폴더
listening on 18450 from discount
$ node ~/server.cjs   # rounding 폴더
node:events:497
      throw er; // Unhandled 'error' event
      ^

Error: listen EADDRINUSE: address already in use 0.0.0.0:18450
    at Server.setupListenHandle [as _listen2] (node:net:1940:16)
$ PORT=18451 node ~/server.cjs   # rounding 폴더
listening on 18451 from rounding
$ curl -s localhost:18450 localhost:18451
discount
rounding
```

포트만이 아니다. 같은 로컬 DB에 두 세션이 각자 마이그레이션을 돌리거나, 같은 테스트 DB를 비우고 채우면 서로의 테스트를 깨뜨린다. Docker Compose의 컨테이너 이름, 홈 폴더의 캐시, 외부 API의 사용량 한도도 공유된다. 실무에서는 세션마다 포트와 DB 이름을 다르게 주는 방법을 정해 둔다. 폴더 이름이나 브랜치 이름에서 포트 번호와 DB 접미사를 만들어 `.env`에 쓰는 스크립트를 두면, 세션을 몇 개 띄워도 겹치지 않는다.

## claude --worktree가 대신 해 주는 것

여기까지를 Claude Code는 플래그 하나로 해 준다. 설치된 CLI 도움말에서 확인했다.

```bash
claude --help | grep -A1 -- "-w, --worktree"   # 2.1.306의 worktree 플래그
```

```text
  -w, --worktree [name]                 Create a new git worktree for this
                                        session (optionally specify a name)
```

`claude --worktree feature-auth`를 치면 `.claude/worktrees/feature-auth/`에 `worktree-feature-auth` 브랜치로 작업 폴더를 만들고 그 안에서 세션을 연다. 이름을 빼면 `bright-running-fox` 같은 이름을 지어 준다. 다른 터미널에서 다른 이름으로 한 번 더 치면 두 번째 격리 세션이다. 세션 중에 "worktree에서 작업해"라고 말해도 `EnterWorktree` 도구로 만든다. `.claude/worktrees/`는 원래 폴더에서 추적되지 않은 파일로 보이니 `.gitignore`에 넣는다.

문서에서 실무에 영향이 큰 세부를 골랐다.

- 기준 브랜치: 기본값 `worktree.baseRef: "fresh"`는 원격의 기본 브랜치(보통 `origin/main`)에서 갈라진다. 내 로컬 브랜치의 푸시 안 한 커밋은 따라오지 않는다. 지금 작업을 이어받게 하려면 `"head"`로 바꾼다. 특정 브랜치 이름은 줄 수 없으니 그때는 `git worktree add`로 직접 만든다.
- PR에서 시작: `claude --worktree "#1234"`는 그 PR의 head 커밋을 받아 `.claude/worktrees/pr-1234`를 만든다. 셸이 `#`을 주석으로 먹지 않게 따옴표로 감싼다.
- 격리 검사: worktree 세션에서 Claude가 원래 폴더의 파일을 Edit·Write하거나, 원래 폴더에서 명령을 돌리거나, `git -C`·`GIT_DIR` 등으로 git을 원래 폴더로 돌리면 도구 호출을 막는다. 다만 `cp`나 셸 리다이렉트로 원래 폴더에 쓰는 것까지 추적하지는 않는다. 그건 권한 설정과 샌드박스의 몫이다.
- 공유되는 것: `.git`, 프로젝트 범위 플러그인, "다시 묻지 않기"로 승인한 Bash 권한(원래 폴더의 `.claude/settings.local.json`에 저장된다)은 모든 worktree가 함께 쓴다.
- 훅 경로: worktree에 들어가도 훅의 `${CLAUDE_PROJECT_DIR}`는 세션을 시작한 원래 폴더를 가리킨다. 훅이 worktree의 파일을 다뤄야 하면 입력 JSON의 `cwd`를 읽는다. 이걸 모르면 포매터 훅이 엉뚱하게 원래 폴더의 파일을 고친다.
- 자동 메모리: 같은 저장소의 worktree는 자동 메모리 폴더 하나를 같이 쓴다. 반면 gitignore된 `CLAUDE.local.md`는 만든 폴더에만 있다.

서브에이전트에도 같은 격리를 줄 수 있다. 서브에이전트 정의의 frontmatter에 `isolation: worktree`를 넣으면 실행할 때마다 임시 worktree에서 돌고, 바꾼 것이 없으면 끝날 때 지워진다. 번들 스킬 `/batch`는 큰 변경 하나를 5~30개의 worktree 격리 서브에이전트로 나눠 돌리는 것으로, 서브에이전트와 worktree를 묶어 놓은 쓰임새다.

## 다 쓴 작업 폴더 치우기

worktree는 만들기보다 치우기에서 실수가 난다. Git은 작업이 남은 폴더를 지우지 않는다.

```text
$ git worktree remove .claude/worktrees/add-auth
fatal: '.claude/worktrees/add-auth' contains modified or untracked files, use --force to delete it
$ git worktree lock --reason "agent running" .claude/worktrees/rounding
$ git worktree remove .claude/worktrees/rounding
fatal: cannot remove a locked working tree, lock reason: agent running
use 'remove -f -f' to override or unlock first
$ rm -rf .claude/worktrees/discount
$ git worktree list
~/shop                              38c3540 [main]
~/shop/.claude/worktrees/add-auth   c5d0b45 [worktree-add-auth]
~/shop/.claude/worktrees/discount   38c3540 [worktree-discount] prunable
~/shop/.claude/worktrees/fix-price  4364d0e [worktree-fix-price]
~/shop/.claude/worktrees/rounding   dd672c5 [worktree-rounding] locked
$ git worktree prune -v
Removing worktrees/discount: gitdir file points to non-existent location
```

볼 곳이 세 군데다. `locked`는 누군가 쓰는 중이라는 표시다. Claude Code는 에이전트가 도는 동안 자기 worktree에 `git worktree lock`을 걸어 두고 끝나면 푼다. 그러니 잠긴 worktree를 `-f -f`로 지우기 전에 그 세션이 정말 끝났는지 확인한다. `prunable`은 폴더를 `rm -rf`로 지워서 기록만 남은 상태이고 `prune`이 정리한다.

그리고 worktree를 지워도 브랜치는 남는다.

```text
$ git worktree list
~/shop  38c3540 [main]
$ git branch
* main
  worktree-add-auth
  worktree-discount
  worktree-fix-price
  worktree-rounding
```

에이전트를 하루에 몇 개씩 돌리면 `worktree-*` 브랜치가 빠르게 쌓인다. Claude Code는 대화형 세션을 끝낼 때 worktree를 검사해서, 깨끗하고 이름 없는 세션이면 worktree와 브랜치를 함께 지우고, 변경이나 새 커밋이 있으면 남길지 묻는다. `-p`로 돌린 비대화형 실행은 종료 확인이 없어서 직접 치워야 한다. 서브에이전트와 백그라운드 세션의 worktree는 `cleanupPeriodDays`보다 오래되면 주기적으로 정리하지만, 작업이 남은 것은 건드리지 않는다.

`/loop`는 세션 범위다. 터미널을 닫거나 세션이 끝나면 멈추고, 바쁜 동안 놓친 회차는 몰아서 돌지 않고 한가해질 때 한 번만 돈다. 반복 작업은 만든 지 7일이 지나면 마지막으로 한 번 돌고 스스로 지워진다. 잊힌 루프가 끝없이 토큰을 쓰는 것을 막는 장치다. 세션 하나에 최대 50개까지 둘 수 있고, "3시에 릴리스 브랜치 push하라고 알려 줘"처럼 말로 한 번짜리 알림도 건다.

## 조건이 맞을 때까지 턴을 잇는다

`/loop`가 시계를 기준으로 다음 턴을 시작한다면, `/goal`은 조건을 기준으로 한다. `/goal all tests in test/auth pass and the lint step is clean`처럼 완료 조건을 주면 Claude가 바로 일을 시작하고, 턴이 끝날 때마다 별도의 작은 모델이 조건이 맞았는지 판정한다. 아직이면 그 이유를 지침 삼아 다음 턴을 스스로 시작한다. 문서에 따르면 `/goal`은 세션 범위의 프롬프트 기반 Stop 훅을 감싼 것이다.

조건을 쓰는 요령이 이 기능의 전부다. 평가 모델은 명령을 돌리거나 파일을 읽지 않고, 대화에 드러난 것만 보고 판정한다. 그래서 "코드가 깔끔해질 때까지"처럼 대화로 증명할 수 없는 조건은 끝나지 않거나 엉뚱하게 끝난다. 측정할 수 있는 끝 상태 하나(테스트 결과, 종료 코드, 파일 수), 확인 방법("`npm test`가 0으로 끝난다"), 지켜야 할 제약("다른 테스트 파일은 고치지 않는다")을 함께 적는다. 상한도 넣는다. `or stop after 20 turns` 같은 절을 붙이면 Claude가 매 턴 그 진행을 보고하고 평가 모델이 판정한다.

멈추는 조건도 알아 둔다. 조건이 맞거나 불가능하다고 판정되면 풀리고, 인증 실패·크레딧 소진·압축으로도 못 푼 컨텍스트 초과·쓸 수 없는 모델 같은 오류가 나면 풀린다. 몇 턴 연속 도구를 쓰지 않고 말만 하면 경고를 띄우고 나에게 제어를 넘긴다(목표는 남아 있다). `/goal`은 권한 모드를 바꾸지 않는다. 수동 모드에서는 허용되지 않은 명령마다 여전히 묻고, 무인으로 돌리려면 자동 모드와 함께 쓴다. 평가에 쓰는 토큰은 작은 모델 몫이라 본 작업에 비하면 적지만, 본 작업 턴은 조건이 맞을 때까지 계속 쓴다.

## 노트북을 덮어도 도는 예약 작업

`/loop`와 `/goal`은 내 컴퓨터에서 세션이 열려 있어야 돈다. 매일 아침 9시에 이슈를 정리하고 PR을 열어 두는 일은 클라우드 예약 작업(cloud scheduled task)의 몫이다. 문서에서 예전 이름인 routines가 아직 주소(`claude.ai/code/routines`)와 CLI 별칭(`/routines`)에 남아 있고, 현재 research preview다. Pro, Max, Team, Enterprise 플랜에서 웹이나 데스크톱 앱, CLI의 `/schedule`로 만든다.

설계는 무인 실행에서 출발한다. 실행 중에는 권한 확인 창이 없으니, 작업이 닿을 수 있는 범위를 처음에 좁힌다. 문서가 꼽는 세 가지는 고른 저장소, 클라우드 환경의 네트워크 접근과 변수, 포함한 커넥터다. 커넥터는 만들 때 연결된 것이 전부 기본으로 들어가고, 포함된 커넥터의 도구는 쓰기까지 묻지 않고 쓴다. 필요 없는 것은 빼야 한다. 푸시 범위는 GitHub의 브랜치 보호 규칙이나 ruleset으로 막는다. 그리고 실행이 남기는 모든 흔적, 곧 커밋, PR, Slack 메시지, 티켓은 내 계정 이름으로 남는다.

한도도 있다. 스케줄 트리거의 최소 간격은 1시간이고, 그보다 잦은 cron은 거부된다. 계정당 스케줄 실행은 시간당 100회이며 구독 사용량을 똑같이 쓴다. GitHub 연결이 끊기면 최대 72시간 동안 실행을 건너뛰다가, 그 뒤에는 작업이 꺼진다.

내 컴퓨터의 파일이 필요하면 데스크톱 앱의 로컬 예약 작업이 있다. 앱이 열려 있고 컴퓨터가 깨어 있을 때만 돌지만 로컬 파일과 도구를 쓸 수 있고, 최소 간격이 1분이다. 기본으로는 작업 폴더의 현재 상태(커밋 안 한 변경 포함)에서 돌고, 편집 화면에서 Worktree를 고르면 실행마다 격리된 worktree를 쓴다. 세 가지를 문서의 비교표에서 골라 옮겼다.

| | 클라우드 예약 작업 | 데스크톱 예약 작업 | `/loop` |
| :- | :- | :- | :- |
| 도는 곳 | 클라우드 | 내 컴퓨터 | 내 컴퓨터 |
| 컴퓨터가 켜져 있어야 | 아니다 | 그렇다 | 그렇다 |
| 세션이 열려 있어야 | 아니다 | 아니다 | 그렇다 |
| 로컬 파일 | 없다(새 clone) | 있다 | 있다 |
| 권한 확인 | 없다(무인) | 작업마다 설정 | 세션을 따른다 |
| 최소 간격 | 1시간 | 1분 | 1분 |

정해진 시각이 아니라 사건에 반응해야 한다면 폴링 대신 다른 길이 있다. 클라우드 예약 작업의 GitHub 트리거(`pull_request.opened` 같은 이벤트)나 API 트리거를 쓰거나, CI가 실패를 세션에 바로 밀어 넣는 channels를 쓴다. GitHub Actions의 `schedule`도 여전히 선택지다.

## 결과를 링크 하나로 남기기

예약 작업이 밤새 일했다면 아침에 무엇을 볼까. 터미널 출력은 길고, Slack에 붙인 로그는 읽히지 않는다. Claude Code의 아티팩트(artifact)는 세션의 결과를 claude.ai의 비공개 웹 페이지로 올리는 기능이다. 주석 달린 diff, 배포 실패 대시보드, 설계안 비교처럼 읽기보다 보는 편이 빠른 것에 쓴다. 처음 올리면 나만 보는 비공개 주소이고, 페이지 머리의 Share에서 조직이나 특정 사람과 나눈다. 같은 세션이 다시 올리면 같은 주소에서 새 버전으로 바뀐다.

아티팩트는 claude.ai 채팅만의 기능이 아니라 Claude Code 문서에 올라 있는 공식 기능이다. 문서 기준으로 Pro, Max, Team, Enterprise 플랜에서 claude.ai 계정으로 `/login`한 CLI나 데스크톱 앱 세션이 올릴 수 있다. API 키, LLM 게이트웨이 토큰, Amazon Bedrock·Google Cloud·Microsoft Foundry 같은 클라우드 제공자 인증으로 쓰는 세션은 올리지 못하고, `-p` 비대화형 실행과 Agent SDK, GitHub Action에서는 기본으로 꺼져 있다. 그 조건이 안 맞으면 Claude는 로컬 HTML 파일만 쓰거나 올릴 수 없다고 말한다.

페이지는 백엔드 없는 정적 페이지 한 장이다. 엄격한 CSP 아래서 몇몇 CDN의 스크립트와 Google Fonts만 불러올 수 있고, 다른 외부 이미지와 요청은 막히며, 크기는 16MiB까지다. 그래서 사내 도구를 배포하는 용도가 아니라 작업을 보여 주는 용도다.

예약 작업과 묶을 때는 문서의 규칙 하나를 알아 둔다. 스케줄이나 Run now로 시작한 실행은 새 아티팩트를 묻지 않고 올릴 수 있다(나만 볼 수 있는 상태로). 이미 공유한 페이지를 고치거나, 커넥터 호출 같은 런타임 기능을 선언하거나, API·GitHub 트리거로 시작한 실행이면 먼저 묻는다. 무인 실행에서 묻는 단계가 나오면 일이 거기서 막힐 수 있으니, 매일 갱신할 페이지는 미리 한 번 올려 두고 그 주소를 예약 작업에 준다.

## 현장에서 병렬과 예약이 꼬이는 순간

- 두 세션이 서로의 파일을 덮는다. 같은 폴더에서 돌고 있다. `git worktree list`로 확인하고 세션마다 `claude --worktree <이름>`으로 다시 연다.
- 새 worktree에서 앱이 안 뜬다. `.env`와 `node_modules`가 없다. `.worktreeinclude`에 env 파일을 적고, 의존성 설치는 Claude에게 시키거나 설정 스크립트로 둔다.
- 두 번째 세션의 테스트만 이상하게 실패한다. 포트나 테스트 DB를 같이 쓰는지 본다. `EADDRINUSE`, 다른 세션이 만든 테이블, 예상 못 한 행 수가 신호다.
- 훅이 엉뚱한 파일을 고친다. 훅 스크립트가 `${CLAUDE_PROJECT_DIR}`를 기준으로 경로를 잡고 있다. 입력 JSON의 `cwd`를 쓰게 고친다.
- worktree에서 시작했는데 내 최근 커밋이 없다. 기본 `baseRef`가 원격 기본 브랜치에서 갈라지기 때문이다. push하거나 `worktree.baseRef`를 `"head"`로 둔다.
- `/loop` 작업이 정각에 안 돈다. jitter다. 매시 작업은 최대 30분 늦는다. 시각이 중요하면 분을 정각에서 비켜 걸거나 다른 수단을 쓴다.
- `/goal`이 끝나지 않는다. 조건이 대화로 증명할 수 없는 말로 쓰여 있다. `/goal`로 상태와 평가 이유를 보고, `/goal clear` 후 측정 가능한 조건과 턴 상한을 넣어 다시 건다.
- 아침에 예약 작업이 아무것도 안 했다. 실행 세션을 열어 본다. GitHub 연결이 끊겼거나, 클라우드 환경의 네트워크 허용 목록 밖으로 나가다 `403`을 받았거나, 아티팩트 게시처럼 묻는 단계에서 멈췄을 수 있다.

처음 장면의 두 세션은 폴더를 나누는 것만으로 서로를 덮지 않게 된다. 그 다음 문제는 합칠 때의 충돌과 포트·DB 같은 공유 자원이고, 이건 도구가 아니라 일을 나누는 방식으로 푼다. 시간 쪽은 무엇이 다음 턴을 시작하느냐로 고른다. 세션 안에서 시계로 되풀이하면 `/loop`, 조건으로 이어 가면 `/goal`, 내가 없을 때 돌려야 하면 예약 작업이다. 전체 그림은 [Claude Code 기본기 지도](/posts/claude-code-fundamentals-map)에 모아 두었다.

## 면접에서 나올 만한 질문

### 여러 AI 코딩 세션을 동시에 돌릴 때 왜 git worktree를 쓰나요?

세션마다 작업 파일, 인덱스, HEAD를 따로 주면서 저장소 이력은 하나로 공유하기 때문이다. 같은 폴더에서 돌리면 한쪽의 checkout, stash, 포매터가 다른 쪽 작업을 덮는다. clone을 여러 개 하는 것보다 디스크를 덜 쓰고 push 없이 바로 merge할 수 있다. 같은 브랜치를 두 폴더에 꺼낼 수 없는 Git의 제약도 세션끼리 브랜치를 공유하지 못하게 막아 준다.

### worktree를 쓰면 충돌이 사라지나요?

작업 중의 충돌만 사라진다. 두 세션이 같은 파일의 같은 줄을 고치면 merge에서 충돌이 나고, 그건 요구 사항을 알아야 풀 수 있다. 포트, 로컬 DB, 컨테이너 이름, 캐시처럼 컴퓨터 단위의 자원도 나누지 않는다. 그래서 일을 나눌 때 파일이 겹치지 않게 자르고, 세션마다 포트와 DB 이름을 다르게 준다.

### 새 worktree에서 앱이 안 뜨는 흔한 이유는 무엇인가요?

worktree는 추적되는 파일만 꺼내는 새 checkout이라서다. `.env` 같은 gitignore 파일과 `node_modules`가 없다. Claude Code에서는 `.worktreeinclude`에 복사할 gitignore 파일을 적고, 의존성은 폴더마다 설치한다. 기본 기준 브랜치가 원격 기본 브랜치라 로컬의 푸시 안 한 커밋이 없는 것도 자주 헷갈리는 지점이다.

### /loop와 /goal은 어떻게 다른가요?

다음 턴을 시작하는 기준이 다르다. `/loop`는 시간 간격이 지나면 같은 프롬프트를 다시 돌리고, 배포 확인처럼 바깥 상태를 주기적으로 볼 때 쓴다. `/goal`은 턴이 끝날 때마다 작은 모델이 완료 조건을 판정해 아직이면 바로 다음 턴을 시작하고, 테스트 통과 같은 끝 상태가 있는 작업에 쓴다. 둘 다 세션이 열려 있어야 돈다.

### /goal의 조건은 어떻게 써야 하나요?

대화에 드러난 결과로 증명할 수 있게 쓴다. 평가 모델은 명령을 돌리거나 파일을 읽지 않고 대화만 보기 때문이다. 측정 가능한 끝 상태, 확인 방법, 지켜야 할 제약, 그리고 "20턴 뒤에는 멈춘다" 같은 상한을 함께 적는다. "코드가 깔끔해질 때까지"처럼 모호한 조건은 끝나지 않거나 엉뚱하게 끝난다.

### /loop로 건 매시 작업이 왜 정각에 돌지 않나요?

모든 세션이 같은 시각에 API를 부르지 않도록 시각을 흩기 때문이다. 반복 작업은 간격의 절반만큼, 최대 30분까지 늦게 돌고, 5분 간격만 예외로 15초 일찍 돈다. 바쁜 동안 놓친 회차는 몰아서 돌지 않는다. 시각이 중요하면 정각을 피해 걸고, 정확한 실행이 필요한 일은 CI 스케줄 같은 다른 수단을 쓴다.

### 클라우드 예약 작업을 설계할 때 무엇을 조심하나요?

무인으로 돌아서 실행 중에 권한 확인이 없다. 그래서 닿을 수 있는 저장소, 네트워크, 커넥터를 필요한 만큼만 주고, 기본으로 다 들어가는 커넥터에서 쓰지 않는 것을 뺀다. push는 `claude/` 브랜치로 가지만 브랜치 보호로 한 번 더 막고, 모든 흔적이 내 계정으로 남는다는 것을 염두에 둔다. 프롬프트에는 할 일과 성공 기준을 빠짐없이 적는다.

### 아티팩트는 사내 도구 배포에 써도 되나요?

맞지 않는다. 아티팩트는 세션의 결과를 claude.ai의 비공개 페이지 한 장으로 올리는 기능이라, 백엔드도 여러 경로도 없고 엄격한 CSP 아래서 외부 요청이 대부분 막힌다. 주석 달린 diff나 대시보드처럼 작업을 보여 주고 공유하는 데 쓰고, 백엔드가 있는 도구는 자기 인프라에 배포한다.
