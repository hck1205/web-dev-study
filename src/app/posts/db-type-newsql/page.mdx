<EasyIntro>
  회원 번호로 데이터베이스를 여러 대에 나눠 담았더니, 친구에게 책을 선물하는 기능에서 문제가 생겼다. 보내는 사람과 받는 사람이 다른 서버에 있으면 포인트 차감과 주문 생성을 한 번에 묶을 수 없어서, 한쪽만 성공하면 포인트만 사라진다.

  분산 SQL은 이 나누고 묶는 일을 데이터베이스가 대신 해 준다. 겉으로는 익숙한 질의문을 그대로 쓰고, 안에서는 데이터를 번호 순서대로 여러 구간으로 잘라 서버에 나눠 둔다. 구간마다 세 사람이 같은 공책을 들고, 그중 둘 이상이 받아 적었다고 답해야 기록이 확정된다. 그래서 서버 한 대가 죽어도 기록이 남고, 두 구간에 걸친 일도 함께 성공하거나 함께 취소된다.

  대가는 기다림이다. 모든 쓰기가 다른 서버의 답을 기다리니 멀리 떨어진 곳에 공책을 두면 쓰기마다 수십 ms가 붙고, 충돌하면 처음부터 다시 하라는 에러를 받는다. 번호가 계속 커지는 키를 쓰면 새 기록이 맨 끝 구간 하나로 몰린다는 점도 알아 둔다.
</EasyIntro>

주문이 서버 한 대를 넘어서 회원 id로 샤드를 나눴다고 하자. 회원 1~100만은 샤드 A, 100만~200만은 샤드 B. 대부분의 쿼리는 회원 한 명 안에서 끝나니 잘 돈다. 그러다 "친구에게 책 선물하기" 기능이 들어온다. 보내는 사람의 포인트를 빼고 받는 사람의 주문을 만든다. 두 사람이 다른 샤드에 있으면 트랜잭션 하나로 묶을 수 없다. 한쪽만 성공하고 다른 쪽이 실패하면 포인트만 사라진다.

[복제와 샤딩 글](/posts/db-replication-sharding)에서 본 대로, 애플리케이션이 샤드를 나누면 샤드를 넘는 조인과 트랜잭션, 재분배를 전부 직접 떠안는다. 분산 SQL(흔히 NewSQL이라고 부른다)은 이 일을 DB가 대신 하겠다는 시도다. 겉으로는 PostgreSQL이나 MySQL처럼 SQL과 트랜잭션을 그대로 쓰고, 안에서는 데이터를 여러 서버에 나누고 복제한다. 이 글은 [DB 종류 시리즈](/posts/db-types-overview)의 여덟 번째 글로, 그 "안에서"가 어떻게 돌고 무엇을 대가로 치르는지 따라간다.

## SQL은 그대로, 저장은 여러 대에

TiDB도 같은 생각이다. 행은 `t{테이블id}_r{행id}`, 인덱스 항목은 `t{테이블id}_i{인덱스id}_{인덱스값}` 모양의 키가 된다. 키가 정렬돼 있으니 "회원 1~4만"처럼 연속된 범위를 한 구간에 담을 수 있고, `WHERE id BETWEEN ...` 같은 범위 조회가 구간 몇 개만 읽고 끝난다.

## 구간이 커지면 둘로 쪼갠다

구간은 크기가 정해진 한도를 넘으면 자동으로 둘로 갈라진다. CockroachDB의 기본 range 최대 크기는 512MiB이고, TiKV의 region은 버전에 따라 96MiB에서 256MiB 정도다. 갈라진 구간은 부하가 적은 노드로 옮겨지고, 노드를 추가하면 구간이 알아서 퍼진다. 애플리케이션이 샤드를 다시 나누던 일을 DB가 대신 하는 셈이다.

그래서 분산 SQL에서는 기본 키를 고르는 방식이 달라진다. CockroachDB는 `gen_random_uuid()`를 기본 키로 권하고, 시간 순 컬럼에 인덱스가 필요하면 해시 샤드 인덱스(`USING HASH`)를 쓴다. TiDB는 `AUTO_INCREMENT` 대신 앞 비트를 무작위로 채우는 `AUTO_RANDOM`을 쓴다.

```sql
-- CockroachDB: 기본 키는 무작위 UUID, 시간 순 조회용 인덱스는 해시로 흩는다
CREATE TABLE orders (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id    INT8 NOT NULL,
  book_id    INT8 NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  INDEX orders_created_idx (created_at) USING HASH
);
```

```sql
-- TiDB: 앞 비트가 무작위인 정수 기본 키
CREATE TABLE orders (
  id      BIGINT PRIMARY KEY AUTO_RANDOM,
  user_id BIGINT NOT NULL,
  book_id BIGINT NOT NULL
);
```

이 두 문법은 각 제품 문서 기준이고, 이 컨테이너에는 설치돼 있지 않아 실행하지 않았다.

## 구간마다 Raft로 과반에 적는다

구간 하나는 세 대(설정하면 다섯 대)에 복제된다. 복제본끼리는 Raft 합의 알고리즘으로 맞춘다. 복제본 중 하나가 리더가 되어 쓰기를 받고, 과반이 기록했다고 답하면 커밋한다. CockroachDB에서는 읽기와 쓰기를 맡는 복제본을 leaseholder라고 부르는데, 보통 Raft 리더와 같은 노드다. 아래 그림에서 다음을 누르면 포인트 차감 하나가 커밋되는 과정이 보인다.

이 그림이 분산 SQL의 지연을 거의 다 설명한다. 쓰기 하나가 커밋되려면 리더에서 과반까지 왕복 한 번이 필요하다. 복제본을 한 데이터센터 안에 두면 1ms가 안 되고, 서울·도쿄·싱가포르에 두면 30ms가 넘는다. 리전 하나가 통째로 죽어도 버티는 대가가 쓰기마다 붙는 30ms다.

## 구간 두 개에 걸친 트랜잭션

이제 처음 문제인 선물하기로 돌아간다. 보내는 사람(42번)과 받는 사람(77777번)이 다른 구간에 있다. 각 구간은 Raft로 원자적으로 쓰지만, 두 구간을 함께 성공하거나 함께 실패하게 하려면 그 위에 분산 트랜잭션이 필요하다. 방식은 제품마다 다른데, TiDB가 쓰는 Percolator 방식(구글이 2010년 논문으로 공개한 2단계 커밋 변형)이 단계를 따라가기 좋다.

## 시계가 다르면 순서도 다르다

분산 트랜잭션에는 "무엇이 먼저 커밋됐나"를 정하는 시계가 필요하다. 서버마다 시계가 조금씩 어긋나기 때문에, 제품마다 이 문제를 다르게 푼다.

TiDB는 시각을 PD라는 중앙 서버 한 곳에서 발급한다(TSO). 단순하고 정확하지만, 모든 트랜잭션이 PD에 다녀와야 하니 PD가 멀리 있는 리전에서는 그 왕복이 그대로 지연이 된다.

Spanner는 GPS 수신기와 원자시계를 데이터센터마다 두고, 현재 시각을 "지금은 [가장 이른 시각, 가장 늦은 시각] 사이"라는 구간으로 알려 주는 TrueTime을 쓴다. 이 불확실성 폭은 논문 기준으로 수 ms 정도다. 커밋할 때는 이 폭만큼 일부러 기다렸다가(commit wait) 응답한다. 그러면 커밋 시각이 실제 시각 순서와 어긋나지 않는 것을 보장할 수 있다. 하드웨어로 시계 오차를 줄이고, 남은 오차는 기다림으로 산다.

CockroachDB는 특수한 하드웨어 없이 하이브리드 논리 시계(HLC, 물리 시각과 논리 카운터를 합친 것)를 쓰고, 노드 사이 시계 오차의 상한(기본 500ms)을 가정한다. 읽을 때 자기 시각보다 조금 뒤, 오차 범위 안에 있는 값을 만나면 그게 먼저인지 나중인지 확신할 수 없어서 트랜잭션을 더 늦은 시각으로 다시 시작한다(uncertainty restart). 노드 시계가 그 상한보다 크게 어긋나면 노드가 스스로 내려간다. 그래서 운영할 때 NTP 같은 시각 동기화가 필수다.

## 충돌하면 다시 하라고 돌려보낸다

CockroachDB의 기본 격리 수준은 SERIALIZABLE이다(23.2 무렵부터 READ COMMITTED도 고를 수 있다). 트랜잭션끼리 충돌하면 한쪽에 SQLSTATE `40001` 에러를 돌려주고 다시 시도하라고 한다. 분산 환경에서는 충돌 감지와 시계 불확실성 때문에 이 에러가 단일 서버보다 자주 나온다. 같은 에러를 PostgreSQL 16에서도 만들 수 있다. 재고 1권 남은 책을 두 세션이 동시에 확인하고 각각 선물 주문을 넣는다.

```sql
-- 세션 A와 B가 각각 같은 순서로 실행한다
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT qty FROM stock WHERE book_id = 42;                       -- 둘 다 1
SELECT count(*) FROM gift_orders WHERE book_id = 42;            -- 둘 다 0
INSERT INTO gift_orders (book_id, buyer) VALUES (42, 'kim');    -- B는 'lee'
COMMIT;                                                          -- A가 먼저, 다음 B
```

```text
-- 세션 A
COMMIT

-- 세션 B
ERROR:  could not serialize access due to read/write dependencies among transactions
DETAIL:  Reason code: Canceled on identification as a pivot, during commit attempt.
HINT:  The transaction might succeed if retried.
```

B는 A의 주문을 못 본 채 판단했으니, 둘 다 성공하면 직렬로 실행했을 때는 나올 수 없는 결과(재고 1권에 주문 2건)가 된다. 그래서 DB가 B를 취소했다. `HINT`대로 애플리케이션이 트랜잭션 전체를 처음부터 다시 실행해야 한다. 격리 수준과 이 이상 현상은 [트랜잭션 격리 글](/posts/db-transaction-isolation)에서 자세히 다뤘다. 분산 SQL로 옮길 때는 모든 쓰기 경로에 재시도 루프가 있는지부터 확인한다.

```js
// 40001이면 지수적으로 쉬었다가 트랜잭션 전체를 다시 실행한다
async function withRetry(pool, fn, max = 5) {
  for (let attempt = 0; ; attempt++) {
    const client = await pool.connect();
    try {
      await client.query("BEGIN");
      const result = await fn(client);
      await client.query("COMMIT");
      return result;
    } catch (err) {
      await client.query("ROLLBACK");
      if (err.code !== "40001" || attempt >= max) throw err;
      await new Promise((r) => setTimeout(r, 2 ** attempt * 10 + Math.random() * 10));
    } finally {
      client.release();
    }
  }
}
```

트랜잭션 안에서 외부 API를 부르거나 메일을 보내면, 재시도할 때 그 일이 두 번 일어난다. 재시도될 수 있는 블록 안에는 DB 작업만 둔다.

## 멀리 있는 사용자의 데이터는 가까이 둔다

여러 리전에 걸쳐 쓰면 지연이 문제의 대부분이다. 분산 SQL은 데이터를 어디에 둘지 SQL로 정하게 해 준다. CockroachDB에서는 행마다 사는 리전을 정할 수 있다.

```sql
-- CockroachDB 멀티 리전: 데이터베이스에 리전을 등록하고
ALTER DATABASE shop SET PRIMARY REGION "ap-northeast-2";
ALTER DATABASE shop ADD REGION "us-west-2";

-- 회원 행은 그 회원의 리전에 리더를 둔다 (crdb_region 컬럼이 생긴다)
ALTER TABLE users SET LOCALITY REGIONAL BY ROW;

-- 책 목록처럼 모두가 읽고 드물게 바뀌는 테이블은 모든 리전에서 빠르게 읽게
ALTER TABLE books SET LOCALITY GLOBAL;

-- 조금 낡아도 되는 읽기는 가까운 복제본에서 (follower read)
SELECT title FROM books AS OF SYSTEM TIME follower_read_timestamp() WHERE id = 42;
```

`GLOBAL` 테이블은 읽기가 어느 리전에서나 빠른 대신 쓰기가 느리다. `AS OF SYSTEM TIME`은 몇 초 전 시점을 읽는 대신 리더까지 가지 않는다. 결국 어떤 데이터가 얼마나 최신이어야 하는지, 어디서 주로 쓰이는지를 테이블마다 정하는 일이다. 이 선택이 [CAP과 PACELC 글](/posts/db-consistency-cap)에서 말하는 지연과 일관성의 교환이다.

## 호환된다는 말의 범위

CockroachDB와 YugabyteDB는 PostgreSQL 통신 규약을 쓴다. psql과 PostgreSQL 드라이버로 접속된다. TiDB는 MySQL 규약을 쓴다. Spanner는 자체 SQL 방언(GoogleSQL)과 PostgreSQL 방언을 함께 지원한다. 그렇다고 기존 앱이 그대로 옮겨진다는 뜻은 아니다.

- 확장 기능, 저장 프로시저, 트리거, 일부 데이터 타입은 지원 범위가 제품과 버전마다 다르다. YugabyteDB는 PostgreSQL의 쿼리 계층 코드를 그대로 가져다 써서 호환 폭이 넓은 편이고, CockroachDB는 SQL 계층을 새로 구현해서 차이가 더 있다.
- 순차 기본 키, 긴 트랜잭션, 한 행에 몰리는 카운터처럼 단일 서버에서는 멀쩡하던 패턴이 핫스팟과 재시도를 만든다.
- 조인과 집계도 여러 노드에 흩어진 데이터를 모아야 해서, 같은 쿼리가 단일 PostgreSQL보다 느릴 수 있다.

TiDB는 행 저장(TiKV) 옆에 컬럼 저장 복제본(TiFlash)을 둘 수 있어서, 운영 쿼리와 분석 쿼리를 한 클러스터에서 나눠 받는 HTAP을 내세운다. 분석만 놓고 보면 [컬럼형 분석 DB](/posts/db-type-columnar-olap)와 겹치는 영역이다.

## 분산 SQL을 고르기 전에

먼저 PostgreSQL 한 대가 정말 모자란지 본다. 요즘 서버 한 대는 수 TB 디스크와 수백 GB 메모리를 갖고, 읽기는 복제본으로 나눌 수 있다. 쓰기가 한 대를 넘거나, 데이터가 한 대에 안 들어가거나, 리전 하나가 통째로 죽어도 쓰기가 멈추면 안 되는 요구가 있을 때가 분산 SQL의 자리다. 결제, 원장, 재고처럼 트랜잭션이 꼭 필요한데 규모도 큰 데이터가 대표적이다.

치르는 값도 분명하다. 쓰기마다 과반 복제 왕복이 붙어 단일 서버보다 지연이 크고(같은 리전 안에서도 몇 ms), 노드 수만큼 비용이 들고, 재시도와 키 설계 같은 새 규칙을 팀이 익혀야 한다. 단일 노드 성능은 같은 하드웨어의 PostgreSQL보다 낮게 나오는 경우가 많다. 서버 한 대로 충분한 서비스라면 분산 SQL은 느리고 비싼 PostgreSQL이 된다.

다른 길도 있다. 쓰기를 회원 단위로 나눌 수 있고 샤드를 넘는 트랜잭션이 드물면, PostgreSQL 위에서 샤딩을 대신 해 주는 Citus나 애플리케이션 샤딩이 더 싸다. 트랜잭션이 필요 없고 키로만 읽는다면 [키-값 저장소](/posts/db-type-key-value)나 [와이드 컬럼 DB](/posts/db-type-wide-column)가 더 빠르고 단순하다.

## 샤딩을 DB 안으로 옮긴 값

분산 SQL은 행을 정렬된 키로 바꾸고, 키 공간을 구간으로 잘라 노드에 나누고, 구간마다 Raft로 과반에 복제하고, 구간을 넘는 트랜잭션은 시각 발급과 2단계 커밋으로 묶는다. 그래서 SQL과 트랜잭션을 지키면서 노드를 늘릴 수 있다. 대신 모든 쓰기가 과반 왕복만큼 느리고, 구간을 넘을 때마다 더 느려지고, 충돌은 재시도로 돌려받는다. 순차 키를 피하고, 같이 바뀌는 행을 같은 구간에 두고, 복제본의 과반을 가까이 두는 것이 이 지연을 줄이는 방법이다.

## 면접에서 나올 만한 질문

### NewSQL은 무엇이고 왜 생겼나요?

SQL과 ACID 트랜잭션을 유지하면서 여러 노드로 수평 확장하는 DB다. 애플리케이션 샤딩은 샤드를 넘는 트랜잭션, 조인, 재분배를 개발자가 직접 떠안고, NoSQL은 확장은 되지만 트랜잭션과 SQL을 포기한다. Spanner, CockroachDB, TiDB, YugabyteDB가 대표적이고, 키 범위로 데이터를 나눠 Raft로 복제하고 분산 트랜잭션을 DB가 처리한다.

### 데이터는 어떻게 나뉘고 복제되나요?

행과 인덱스 항목을 정렬된 키-값으로 바꾸고, 키 공간을 연속된 구간(range, region)으로 자른다. 구간이 한도(CockroachDB 기본 512MiB)를 넘으면 자동으로 쪼개지고 부하가 적은 노드로 옮겨진다. 구간마다 보통 3개 복제본이 Raft 그룹을 이루고, 리더가 쓰기를 받아 과반이 기록하면 커밋한다.

### 쓰기 지연은 무엇으로 정해지나요?

리더에서 과반이 기록할 때까지의 왕복 시간이다. 리더 포함 과반이 모이는 순간이라, 3개 복제본이면 가장 가까운 복제본 하나의 왕복이 커밋 지연이 된다. 리전을 넘어 복제하면 장애 내성은 커지지만 쓰기마다 수십 ms가 붙는다. 여러 구간에 걸친 트랜잭션은 2단계 커밋이 더해져 더 느리다.

### 자동 증가 기본 키가 왜 문제인가요?

키가 정렬돼 저장되니 계속 커지는 키는 새 행이 전부 키 공간의 맨 끝 구간 하나로 몰린다. 노드가 많아도 쓰기는 한 노드가 다 받는 핫스팟이 되고, 구간이 쪼개져도 새 끝 구간으로 다시 몰린다. UUID, 해시 샤드 인덱스, TiDB의 AUTO_RANDOM으로 흩고, 대신 시간 순 범위 조회는 여러 구간을 읽게 된다는 걸 감수한다.

### 분산 DB는 트랜잭션 순서를 어떻게 정하나요?

TiDB는 PD라는 중앙 서버가 계속 커지는 시각 번호를 발급하고, Spanner는 원자시계와 GPS로 오차 범위를 아는 TrueTime을 쓰고 그 오차만큼 커밋 때 기다린다. CockroachDB는 하이브리드 논리 시계와 최대 시계 오차 가정(기본 500ms)을 쓰고, 오차 범위 안의 값을 만나면 트랜잭션을 다시 시작한다. 그래서 CockroachDB 운영에는 시각 동기화가 필수다.

### 40001 에러는 왜 나오고 어떻게 다루나요?

SERIALIZABLE에서 트랜잭션끼리 충돌해 직렬 실행과 다른 결과가 나올 수 있으면 DB가 한쪽을 취소하며 돌려주는 직렬화 실패다. CockroachDB는 기본이 SERIALIZABLE이고 분산 환경이라 단일 서버보다 자주 나온다. 애플리케이션이 트랜잭션 전체를 백오프와 함께 다시 실행해야 하고, 그 블록 안에는 외부 호출처럼 두 번 일어나면 안 되는 일을 두지 않는다.

### 언제 분산 SQL 대신 PostgreSQL 한 대를 쓰나요?

데이터와 쓰기가 서버 한 대에 들어가고, 리전 장애에도 쓰기가 멈추면 안 된다는 요구가 없으면 PostgreSQL 한 대와 복제본이 더 빠르고 싸다. 분산 SQL은 쓰기마다 과반 복제 왕복이 붙고 노드 비용과 재시도·키 설계 같은 새 규칙이 따라온다. 쓰기 확장과 강한 일관성, 리전 장애 내성이 함께 필요할 때 고른다.
