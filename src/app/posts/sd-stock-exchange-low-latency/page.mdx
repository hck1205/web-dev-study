<EasyIntro>
  거래소는 아주 빠르면서도 언제나 똑같이 움직여야 한다. 대부분 백만 분의 1초 안에 끝나던 주문 처리가 가끔 몇십 배, 몇만 배 느려지면 누군가의 주문만 늦게 처리된다. 처리하는 프로그램이 죽어 예비 프로그램이 이어받을 때 주문 목록이 한 줄이라도 다르면 큰 사고가 난다.

  똑같이 움직이게 하려고 들어오는 모든 주문에 한 곳에서 1, 2, 3 순번을 찍어 기록장에 적는다. 처리하는 쪽은 이 순번대로만 처리하니, 같은 기록장을 다시 넣으면 언제나 같은 결과가 나온다. 예비 프로그램도 같은 기록장을 따라 읽고 있다가 멈춘 자리부터 바로 이어받고, 중간 순번이 비면 기다렸다가 다시 달라고 한다.

  빠르게 하려고 부품을 서버 한 대에 모으고, 한 일꾼이 쉬지 않고 돌며 혼자 처리하게 해서 서로 기다리는 시간을 없앤다. 미리 마련한 고리 모양 칸에 값만 써서 주고받으면 메모리 청소로 잠깐 멈추는 일도 줄어든다. 대신 일꾼 하나가 할 일이 없어도 컴퓨터의 두뇌 하나를 계속 붙잡고 있다.
</EasyIntro>

이 시리즈에서 이 글의 자리: 앞 글 [증권 거래소 설계 ①](/posts/sd-stock-exchange-order-book)에서 호가창과 가격-시간 우선 매칭 엔진을 만들었다. 이 글은 그 엔진을 거래소답게 만든다. 모든 입력에 순번을 찍는 시퀀서, 잠금 없이 한 스레드로 도는 루프, 같은 입력이면 같은 호가창을 되살리는 결정적 재생, 그리고 시장 데이터를 공정하게 나눠 주는 법이다. 시리즈의 마지막 사례이고, 다음은 전체를 한 번에 훑는 [시스템 설계 공부 순서](/posts/system-design-study-path)다. 재생 원리는 [디지털 지갑 설계 ②](/posts/sd-wallet-event-sourcing)에서 먼저 봤다.

앞 글에서 만든 매칭 엔진에 주문 100만 건을 넣었을 때 건당 지연은 중간값 0.46µs였다. 그런데 최댓값이 20,764µs, 즉 20밀리초였다. 대부분 반 마이크로초에 끝나는 일이 가끔 4만 배 넘게 느려진다. 장이 열리는 9시 정각에 그 순간이 겹치면 누군가의 주문은 남보다 20밀리초 늦게 처리된다.

다른 문제도 있다. 주 엔진이 죽어서 대기 엔진이 이어받았는데, 대기 엔진의 호가창이 죽기 직전의 호가창과 한 주라도 다르면 어떻게 될까. 이미 체결 알림을 받은 주문이 다시 호가창에 나타나거나, 있던 주문이 사라진다. 이 글은 빠른 것과 똑같은 것, 두 가지를 함께 푼다.

## 서비스를 건널 때마다 밀리초가 쌓인다

앞 글의 거래 경로는 게이트웨이 → 주문 관리 → 시퀀서 → 매칭 엔진이었다. 이것들을 각각 다른 서버에 두면 주문 하나가 네트워크를 몇 번 건너고, 시퀀서가 일지를 디스크에 쓸 때마다 fsync를 기다린다. 같은 데이터센터 안의 네트워크 왕복은 보통 수십~수백 마이크로초이고 디스크 fsync는 밀리초 단위다. 정확한 값은 장비와 네트워크에 따라 다르고, 대략의 크기는 [지연 시간 숫자 글](/posts/sd-latency-numbers)에 모아 뒀다. 이렇게 짜면 주문 하나의 왕복이 수십 밀리초가 되기 쉽다.

거래소가 원하는 건 수십 마이크로초다. 1,000배 차이다. 줄이는 길은 두 가지뿐이다. 거래 경로 위의 일을 줄이거나, 각 일에 걸리는 시간을 줄인다.

일을 줄이는 쪽은 앞 글에서 이미 시작했다. 주문 저장, 보고, 시장 데이터 계산을 거래 경로 밖으로 뺐다. 더 나아가 거래 경로 위에서는 로그도 바로 쓰지 않는다. 시간을 줄이는 쪽은 더 과감하다. 거래 경로의 구성 요소를 모두 서버 한 대에 올리고, 네트워크 대신 공유 메모리로 잇는다. 대부분의 웹 서비스가 서버를 늘려 가는 것과 반대 방향이다.

## 모든 입력에 번호를 찍는 단 하나의 작성자

같은 가격이면 먼저 온 주문이 먼저다. 그런데 "먼저"는 누가 정하나. 게이트웨이가 여러 대이고 각자 주문을 받는다. 각자의 시계는 조금씩 다르고, 같은 순간 도착한 두 주문 중 무엇이 먼저인지는 운에 가깝다.

그래서 거래 경로에는 순서를 정하는 곳이 딱 하나 있다. 시퀀서다. 들어오는 모든 주문과 취소에 1, 2, 3 … 순번을 찍어 일지에 쓴다. 그 뒤로는 모두가 이 순번만 믿는다. 매칭 엔진은 순번 순서대로 처리하고, 순번이 같은 입력은 같은 것으로 보고 두 번 처리하지 않는다.

이게 얼마나 필요한지 실험했다. 게이트웨이 두 대(G1, G2)가 각자 정해진 주문 500건을 보내고, 도착 시각에 0~20ms의 무작위 지연을 섞었다. 시퀀서는 도착하는 대로 순번을 찍는다. 같은 주문 1,000건으로 두 번 돌렸다.

```js
// 시퀀서: 도착하는 대로 순번과 시각을 찍어 일지에 쓴다. 쓰는 곳은 여기 하나뿐이다
const receive = (o) => journal.push({ seq: journal.length + 1, ts: Number(process.hrtime.bigint() - t0), ...o });
```

```text
실행 1 도착 순서: G1-25 G1-28 G1-31 G1-41 G1-60 G1-63
실행 2 도착 순서: G1-0 G1-2 G1-10 G1-30 G1-36 G1-71
실행 1 체결 796건 출력 해시 653013b072b4 / 실행 2 체결 803건 출력 해시 74937191e788
```

주문은 같은데 도착 순서가 달라서 체결이 796건과 803건으로 갈렸다. 순서가 결과를 바꾼다. 그러니 순서는 한 곳에서 정해 기록으로 남겨야 한다. 시퀀서가 찍은 일지의 첫 두 줄은 이렇다.

```text
{"seq":1,"ts":4699057,"id":"G1-25","side":"buy","price":69900,"qty":3}
{"seq":2,"ts":4729317,"id":"G1-28","side":"sell","price":70200,"qty":6}
```

`ts`는 시퀀서가 찍은 시각(시작부터의 나노초)이다. 엔진이 시각이 필요할 때도 자기 시계 대신 이 값을 쓴다. 이유는 다음 절에서 본다.

시퀀서가 하나라는 건 병목이 하나라는 뜻이기도 하다. 그래서 시퀀서는 순번을 찍고 쓰는 일 말고는 아무것도 하지 않는다. Kafka 같은 메시지 큐도 파티션 안에서는 같은 역할을 하지만, 브로커까지 네트워크를 타는 지연 때문에 거래 경로에는 보통 직접 만든 시퀀서를 둔다. 큐의 파티션과 오프셋 개념은 [분산 메시지 큐 설계 ①](/posts/sd-mq-storage-partitions)에 있다.

## 같은 일지면 같은 호가창

시퀀서가 일지를 남기면 매칭 엔진은 일지만 보고 언제든 같은 상태를 되살릴 수 있다. 앞 글의 엔진을 일지 1에 다시 돌렸다.

```text
일지 1을 다시 재생: 체결 796건 출력 해시 653013b072b4 상태 해시 bc6d3840c964
```

처음 실행 때와 출력 해시가 같다. 같은 일지를 같은 순서로 넣으면 같은 체결이 같은 번호로 나온다. 이 성질을 결정성이라고 하고, 거래소의 장애 대응이 전부 여기에 기댄다.

주 엔진과 같은 일지를 따라 읽는 대기 엔진을 하나 더 두고, 주 엔진을 600번에서 멈췄다. 대기 엔진은 601번부터 이어서 처리했다.

```text
600번에서 주 엔진 상태 a67783f75bdd, 대기 엔진 상태 a67783f75bdd, 마지막 체결 번호 479 / 479
대기 엔진이 601번부터 이어서 처리: 전체 출력 해시 653013b072b4 (끊김 없이 돈 것과 같음)
```

600번 시점의 호가창 해시와 마지막 체결 번호가 같고, 이어받아 끝까지 낸 출력도 한 번도 끊기지 않은 실행과 같다. 대기 엔진은 그동안 출력을 내보내지 않았을 뿐 같은 일을 똑같이 하고 있었다.

결정성은 쉽게 깨진다. 체결 기록에 붙는 시각을 엔진이 `Date.now()`로 찍게 바꿔 같은 일지를 두 번 돌렸다.

```text
체결 시각을 Date.now()로 찍으면: 첫 실행 cf0ed7a52933, 재생 2dfe46e54ac3
```

체결 가격과 수량은 같아도 출력이 다르다. 대기 엔진이 이어받은 뒤 같은 체결에 다른 시각이 붙어 나가면, 증권사는 같은 체결을 두 개로 볼 수도 있다. 엔진 안에서는 시계, 난수, 해시 맵의 순회 순서처럼 실행마다 달라질 수 있는 것을 쓰지 않는다. 시각이 필요하면 시퀀서가 찍은 `ts`를 쓴다. 지갑에서 수수료를 사건에 적었던 것과 같은 원리다.

지연에도 결정성이라는 말을 쓴다. 이건 결과가 아니라 걸리는 시간이 늘 비슷하냐는 뜻이다. 결과의 결정성은 시퀀서와 일지로 지키고, 지연의 결정성은 p99, p99.99 같은 꼬리 지연을 계속 재면서 지킨다. 꼬리를 읽는 법은 [꼬리 지연 글](/posts/tail-latency)에 있다.

## 순번이 비면 멈추고 다시 달라고 한다

엔진은 순번이 하나라도 비면 그다음 것을 처리하지 않는다. 일지가 다른 서버로 복제될 때나 네트워크로 받을 때 메시지 하나가 빠질 수 있다. 빠진 걸 모르고 넘어가면 그 엔진의 호가창은 영영 다른 엔진과 달라진다. 300번을 일부러 빼고 넣어 봤다.

```js
if (m.seq !== next) {                       // 기다리던 순번이 아니다
  for (const missing of sequencerJournal.slice(next - 1, m.seq - 1)) handle(missing);  // 빠진 것부터 받아 처리
}
```

```text
일지 전송 중 순번 300이 빠졌다:
   300번 대신 301번이 왔다 → 시퀀서에 300~300번 재전송 요청
   재전송 뒤 출력 해시 653013b072b4 (같음)
```

## 한 스레드가 쉬지 않고 도는 루프

이제 지연의 꼬리다. 일반적인 서버는 여러 스레드가 공유 자료 구조를 잠금으로 지키며 나눠 쓴다. 잠금을 기다리는 시간, 운영체제가 스레드를 바꿔 끼우는 시간(컨텍스트 스위치)이 들쭉날쭉하게 끼어든다.

거래소의 핵심 구성 요소는 반대로 간다. 매칭 엔진은 스레드 하나가 `while (true)`로 일지를 읽고 처리하기를 반복한다. 스레드가 하나뿐이니 호가창을 지킬 잠금이 필요 없다. 그리고 이 스레드를 CPU 코어 하나에 고정(pinning)해서 운영체제가 다른 일로 바꿔 끼우지 않게 한다. 리눅스라면 `taskset`이나 `isolcpus` 같은 설정을 쓴다. 엔진이 스레드 하나로 충분한 이유는 앞 글에서 봤다. 매칭 자체는 1마이크로초 안팎이다.

Node의 JavaScript 실행도 원래 스레드 하나다. 그런데 앞 글의 측정에서 최대 20밀리초가 나왔다. 잠금도 컨텍스트 스위치도 없는데 무엇이 멈췄을까. 가장 흔한 범인은 가비지 컬렉션(GC)이다. 주문마다 객체를 새로 만들면 쓰레기가 쌓이고, 런타임이 그걸 치우는 동안 잠깐 멈춘다. GC가 언제, 왜 멈추는지는 [가비지 컬렉션 글](/posts/garbage-collection)에 있다.

같은 스레드 안에서 메시지를 넘기는 두 방식을 비교했다. 하나는 메시지마다 객체를 만들어 배열에 `push`하고 `shift`로 꺼내는 큐, 하나는 미리 잡아 둔 typed array 칸에 값만 쓰는 링 버퍼다. GC가 일어날 때마다 `PerformanceObserver`로 셌다.

```text
배열 큐(객체): 5,000,000건 156ms, GC 305번 합계 26.4ms 최대 0.79ms (검산 5000000)
링 버퍼(미리 할당): 5,000,000건 31ms, GC 0번 합계 0.0ms 최대 0.00ms (검산 5000000)
배열 큐(객체): 5,000,000건 155ms, GC 152번 합계 18.9ms 최대 2.07ms (검산 5000000)
링 버퍼(미리 할당): 5,000,000건 33ms, GC 0번 합계 0.0ms 최대 0.00ms (검산 5000000)
```

링 버퍼는 5배 빨랐고 GC가 한 번도 일어나지 않았다. 새로 만드는 객체가 없으니 치울 것도 없다. 배열 큐 쪽은 GC가 수백 번, 한 번에 최대 2밀리초 멈췄다. 이 실험은 짧은 객체만 만들어서 멈춤이 짧았지만, 호가창처럼 오래 사는 객체가 많아지면 더 길게 멈출 수 있다. 앞 글의 20밀리초가 그런 경우로 보인다. 그래서 지연에 민감한 엔진은 Java로 짜더라도 객체를 미리 만들어 재사용하고, 거래 경로에서 새로 할당하지 않는 식으로 쓴다.

## 스레드 사이는 링 버퍼로 잇는다

거래 경로의 구성 요소는 각자 자기 스레드(또는 프로세스)에서 돌고, 그 사이를 메시지가 오간다. 링 버퍼는 크기가 정해진 배열의 끝과 처음을 이어 붙인 원형 큐다. 쓰는 쪽은 "다음에 쓸 순번", 읽는 쪽은 "다음에 읽을 순번" 하나씩만 움직인다. 칸 위치는 순번을 크기로 나눈 나머지다. 쓰는 쪽이 하나, 읽는 쪽이 하나면 잠금 없이 순번 두 개만으로 안전하게 주고받을 수 있다.

```js
offer(v) {
  const w = Atomics.load(this.seq, 0), r = Atomics.load(this.seq, 1);
  if (w - r === this.cap) return false;        // 꽉 찼다
  this.slots[w % this.cap] = v;
  Atomics.store(this.seq, 0, w + 1);           // 값을 쓴 뒤에 순번을 올린다
  return true;
}
```

값을 칸에 먼저 쓰고 순번을 나중에 올리는 순서가 중요하다. 반대로 하면 읽는 쪽이 아직 비어 있는 칸을 읽을 수 있다. `Atomics.store`는 이 순서가 다른 스레드에서도 그대로 보이게 해 준다.

중간값이 30배 넘게, p99는 100배 넘게 차이 난다. `postMessage`는 메시지를 복사하고, 받는 쪽 이벤트 루프를 깨우고, 콜백을 부르는 과정을 거친다. 링 버퍼는 메모리 한 칸을 쓰고 읽을 뿐이다. 같은 이유로 실행할 때마다 `postMessage` 쪽 숫자가 크게 흔들렸다(다른 실행에서는 p50이 11µs였다).

공짜는 아니다. 바쁜 대기는 메시지가 없어도 코어 하나를 계속 쥔다. 메시지 없이 1초를 기다리게 해 봤다.

```text
메시지 없이 1001ms 기다리는 동안 CPU 974ms
```

1초 동안 코어 하나를 거의 다 썼다. 거래소처럼 지연 한 자릿수 마이크로초가 돈이 되는 곳에서는 코어를 통째로 바치는 게 남는 장사다. 웹 서비스라면 대개 손해다. 멀티코어에서 쓰는 쪽과 읽는 쪽의 순번 칸이 같은 캐시 라인(보통 64바이트)에 있으면 서로의 캐시를 계속 무효화해 느려진다. 그래서 순번 칸 사이에 빈 공간(패딩)을 넣는다. 이 측정에서는 순번 두 개가 8바이트 안에 붙어 있었으니 개선할 여지가 남아 있다.

## 디스크 대신 메모리에 쓰는 일지

시퀀서의 일지는 어디에 쓸까. 디스크에 쓰고 매번 fsync하면 그게 가장 느린 단계가 된다. 많이 쓰는 방법은 `mmap`이다. 파일을 프로세스의 메모리 주소에 그대로 겹쳐 놓는 시스템 콜이라서, 메모리에 쓰듯 쓰면 운영체제가 알아서 파일에 반영한다. 여러 프로세스가 같은 파일을 `mmap`하면 같은 메모리를 보게 되니 프로세스 사이의 통로로도 쓸 수 있다. 파일을 리눅스의 `/dev/shm`(메모리에 있는 파일 시스템, tmpfs)에 만들면 디스크를 아예 건드리지 않는다.

```bash
# /dev/shm이 메모리 위의 파일 시스템인지 확인한다
df -h /dev/shm
```

```text
Filesystem      Size  Used Avail Use% Mounted on
tmpfs            16G  2.1M   16G   1% /dev/shm
```

Node에는 `mmap`이 기본으로 없어서, 같은 일지 5,000줄을 `/dev/shm`과 보통 디스크에 써서 차이만 봤다.

```text
[/dev/shm]
쓰기만(fsync 없음)          5000건     9.6ms  초당 519,243건
한 건마다 fsync            5000건    10.3ms  초당 483,964건
100건마다 fsync           5000건     4.3ms  초당 1,156,467건
[디스크]
쓰기만(fsync 없음)          5000건     8.5ms  초당 585,467건
한 건마다 fsync            5000건  4877.9ms  초당 1,025건
100건마다 fsync           5000건    26.5ms  초당 188,497건
```

`/dev/shm`에서는 fsync가 사실상 아무 일도 하지 않는다. 내릴 디스크가 없어서다. 디스크에서 한 건마다 fsync하면 초당 1,025건이다. [지갑 글](/posts/sd-wallet-event-sourcing)에서 같은 측정을 했을 때는 4천 건 남짓이었으니, 같은 머신에서도 fsync 비용은 크게 흔들린다.

메모리에 쓴다는 건 전원이 나가거나 서버가 재부팅되면 일지가 사라진다는 뜻이다. 그래서 일지는 다른 서버에도 실시간으로 복제한다. 지갑에서 사건 기록을 Raft로 복제한 것과 같은 이유다. 잃으면 안 되는 건 순번이 찍힌 입력 일지이고, 호가창은 그 일지에서 언제든 다시 만든다.

어려운 건 "죽었다"를 판정하는 일이다. 주 엔진이 잠깐 느려졌을 뿐인데 대기 엔진이 발행을 시작하면 둘이 동시에 체결을 내보낸다. 그래서 누가 지금 주인인지를 한 명만 정하도록 리더 선출(예: Raft)을 쓰고, 옛 주인이 돌아와도 발행하지 못하게 막는다. 동작은 [리더 선출 글](/posts/leader-election)과 [Raft 글](/posts/raft-consensus)에 있다. 처음 운영할 때는 장애 유형을 충분히 알기 전까지 자동 대신 사람이 확인하고 넘기는 경우도 있다.

모든 복제본이 같은 버그로 같이 죽을 수도 있다. 결정적 재생은 여기서 양날이다. 특정 주문 순서에서 엔진이 죽는다면, 같은 일지를 재생하는 대기 엔진도 같은 자리에서 죽는다. 그래서 일지에서 그 주문을 찾아 원인을 재현하는 데는 좋지만, 대기 엔진이 이 경우를 구해 주지는 못한다. 일부러 장애를 넣어 보는 카오스 실험이 이런 경우를 미리 찾는 데 쓰인다.

목표가 가용성 99.99%라면 하루에 허용되는 중단은 86,400초 × 0.0001 = 8.64초다. 그 안에 감지하고 넘겨야 한다. 일지는 대기 서버가 받았다고 답한 뒤에 체결을 내보내야 잃지 않는다. 그만큼 지연이 늘어나는 걸 받아들이는 지점이다.

## 시장 데이터를 모두에게 같은 순간에

체결과 호가 변화는 시장 데이터로 퍼진다. 거래소에서는 빠른 것만큼 공정한 것이 중요하다. 어떤 증권사가 같은 데이터를 다른 곳보다 1밀리초 먼저 받으면 그 1밀리초 동안 남보다 먼저 주문을 낼 수 있다.

구독자마다 따로 보내면(유니캐스트) 목록의 앞쪽과 뒤쪽이 받는 시각이 다르다. 그래서 하나를 보내면 네트워크 장비가 구독자 모두에게 복제해 주는 멀티캐스트를 쓴다. 멀티캐스트는 UDP 위에서 돌아서 패킷이 빠질 수 있다. 여기에도 순번이 붙는다. 받는 쪽은 순번이 비면 재전송 채널에 다시 달라고 한다. 엔진이 일지에서 하던 것과 똑같다. UDP의 성질은 [UDP와 QUIC 글](/posts/udp-and-quic)에 있다.

같은 이유로 거래소는 증권사가 거래소 데이터센터 안에 서버를 두는 코로케이션을 판다. 모든 코로케이션 서버까지의 케이블 길이를 같게 맞추는 곳도 있다. 시장 데이터 발행기는 봉 차트도 링 버퍼에 담는다. 최근 몇 개 구간만 메모리에 두고 오래된 것은 칸을 덮어쓰면, 메모리가 일정하고 새로 할당하지 않는다.

외부에 열린 부분(시세 조회 API, 웹사이트)은 공격 대상이 된다. 거래 경로와 분리하고, 자주 바뀌지 않는 데이터는 캐시에 두고, 캐시가 잘 되도록 주소를 고정된 형태(`/data/recent`처럼)로 만든다. 요청 수 제한은 [처리율 제한기 설계](/posts/sd-rate-limiter-design)에서 다뤘다.

현장에서 이 구조를 운영할 때 자주 마주치는 증상과 첫 확인 지점을 적어 둔다. 장 시작 직후 p99가 튀면 GC 로그(Node라면 `--trace-gc`)와 거래 경로의 할당부터 본다. 대기 엔진의 상태가 주 엔진과 어긋나면 일정 순번마다 두 엔진의 상태 해시를 비교해 처음 갈라진 순번을 찾고, 그 근처에서 시계나 난수를 쓰는 코드를 찾는다. 재전송 요청이 몰리면 그 구간의 네트워크 손실률과 수신 버퍼 크기를 본다.

## 마지막 사례를 닫으며

거래소는 빠르고 똑같아야 한다. 똑같음은 시퀀서가 모든 입력에 순번을 찍어 일지로 남기고, 엔진이 그 순서대로만 결정적으로 처리하는 데서 나온다. 그래서 대기 엔진이 같은 일지를 따라 읽다가 언제든 이어받을 수 있고, 빠진 메시지는 순번으로 알아채 다시 받는다. 빠름은 거래 경로를 한 서버에 모으고, 한 스레드 루프로 잠금을 없애고, 미리 할당한 링 버퍼로 GC와 이벤트 루프를 피하는 데서 나온다. 대가는 코어를 통째로 쓰는 바쁜 대기와 메모리 일지의 복제다.

시스템 설계 사례는 여기까지다. [시스템 설계 공부 순서](/posts/system-design-study-path)에서 서버 한 대에서 시작한 첫 글부터 이 글까지를 한 줄씩 다시 훑는다.

## 면접에서 나올 만한 질문

### 거래소에 시퀀서가 왜 필요한가요?

같은 가격에서 누가 먼저인지를 한 곳에서 정하고 기록으로 남기기 위해서다. 게이트웨이가 여러 대면 도착 순서가 실행마다 달라지고, 실험에서 같은 주문 1,000건이 순서만 달라 체결이 796건과 803건으로 갈렸다. 시퀀서가 모든 입력에 순번을 찍어 일지에 쓰면 엔진은 그 순서만 따르고, 재생과 중복 제거도 순번으로 한다.

### 매칭 엔진이 결정적이어야 하는 이유는요?

같은 일지를 같은 순서로 넣으면 같은 호가창과 같은 체결이 나와야 대기 엔진이 언제든 이어받을 수 있다. 실험에서 600번에서 멈춘 주 엔진과 대기 엔진의 상태 해시가 같았고, 대기 엔진이 601번부터 이어 낸 출력도 끊김 없는 실행과 같았다. 엔진 안에서 `Date.now()`로 체결 시각을 찍자 같은 일지에서 다른 출력이 나왔다. 시각은 시퀀서가 찍은 값을 쓴다.

### 순번 중간이 빠진 메시지를 받으면 엔진은 어떻게 하나요?

다음 순번을 처리하지 않고 붙들어 둔 채 빠진 순번을 다시 요청한다. 받아서 순서대로 처리하면 결과가 빠짐없이 받은 엔진과 같다. 이미 처리한 순번이 다시 오면 버리니, 전송은 적어도 한 번이어도 처리는 정확히 한 번이 된다.

### 왜 서버를 여러 대 두지 않고 한 대에 모으나요?

거래 경로의 지연 목표가 수십 마이크로초인데, 서비스 사이의 네트워크 왕복과 디스크 fsync가 한 번에 수십 마이크로초에서 밀리초씩 더한다. 구성 요소를 한 서버에 모아 공유 메모리로 이으면 그 비용이 사라진다. 대신 그 서버가 단일 장애점이 되니 일지를 대기 서버로 복제하고 장애 조치를 준비한다.

### 단일 스레드 루프가 멀티스레드보다 빠를 수 있나요?

지연의 꼬리가 중요할 때는 그렇다. 스레드 하나가 호가창을 혼자 다루면 잠금이 필요 없고, 코어에 고정하면 컨텍스트 스위치도 없다. 매칭 자체가 1마이크로초 안팎이라 한 스레드로 초당 100만 건 남짓을 처리했다. 남는 꼬리는 GC 같은 런타임 멈춤인데, 거래 경로에서 새로 할당하지 않는 식으로 줄인다.

### 링 버퍼가 일반 큐보다 빠른 이유는요?

칸을 미리 잡아 두고 순번 두 개만 움직여서 할당과 잠금이 없다. 같은 스레드 실험에서 객체 큐보다 5배 빨랐고 GC가 한 번도 없었다. 워커 스레드 사이 왕복에서는 postMessage의 p50이 31µs, 공유 메모리 링 버퍼의 p50이 0.88µs였다. 대신 받는 쪽이 바쁜 대기를 하면 메시지가 없어도 코어 하나를 거의 다 쓴다.

### mmap 일지를 /dev/shm에 두면 무엇을 얻고 무엇을 잃나요?

fsync가 디스크를 기다리지 않으니 일지 쓰기가 메모리 쓰기만큼 빨라진다. 실험에서 디스크는 한 건마다 fsync하면 초당 1,025건이었고 /dev/shm은 48만 건을 넘었다. 대신 재부팅이나 전원 장애에 일지가 사라지니 다른 서버로 실시간 복제하고, 대기 서버가 받았다고 답한 뒤에 체결을 내보낸다.

### 시장 데이터를 공정하게 나눠 주려면 어떻게 하나요?

구독자마다 따로 보내면 순서에 따라 받는 시각이 달라지니, 네트워크가 한 번에 복제해 주는 멀티캐스트를 쓴다. 멀티캐스트는 UDP라 패킷이 빠질 수 있어 순번을 붙이고 빠진 것을 재전송 채널로 다시 받는다. 거래소 안에 서버를 두는 코로케이션도 같은 조건으로 제공하고, 케이블 길이까지 맞추기도 한다.
