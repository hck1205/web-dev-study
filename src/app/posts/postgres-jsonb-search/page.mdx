서점이 책 말고도 키보드, 마우스, 전자책 리더기, 독서대 같은 굿즈를 팔기 시작했다. 키보드에는 스위치 종류와 배열이 있고, 리더기에는 화면 크기와 저장 용량이 있고, 책에는 저자와 쪽수가 있다. 카테고리마다 컬럼을 추가하다 보면 `products` 테이블에 대부분 NULL인 컬럼이 서른 개쯤 생긴다.

검색도 문제다. 상품 검색창은 `WHERE name LIKE '%키보드%'`로 만들었는데 상품이 10만 개를 넘자 검색 한 번에 테이블 전체를 읽는다. 오타를 내면 아무것도 안 나온다.

이 글은 이 두 문제를 PostgreSQL 안에서 푸는 방법을 다룬다. 앞쪽은 카테고리마다 다른 속성을 담는 `jsonb`, 뒤쪽은 전문 검색(`tsvector`)과 `pg_trgm`이다. 둘 다 GIN 인덱스로 빨라진다. 기준은 Ubuntu 24.04의 PostgreSQL 16.15이고, 출력은 모두 실제로 돌린 결과다. 앞 글 [함수, 프로시저, 트리거](/posts/postgres-functions-triggers)의 감사 로그에서 잠깐 쓴 `jsonb`를 여기서 제대로 본다. B-tree 같은 인덱스 기본기는 [인덱스 글](/posts/db-index)에 있다.

## 카테고리마다 속성이 다른 상품

시리즈의 `shop` DB에 `products` 테이블을 더한다. 공통인 것(카테고리, 이름, 가격)은 컬럼으로, 카테고리마다 다른 것은 `attrs jsonb` 하나에 담는다.

```sql
CREATE TABLE products (
  id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  category text NOT NULL,                 -- keyboard, mouse, ereader, stand, book
  name     text NOT NULL,
  price    integer NOT NULL,
  attrs    jsonb NOT NULL DEFAULT '{}'    -- 카테고리별 속성
);

INSERT INTO products (category, name, price, attrs) VALUES
  ('keyboard', '키크론 K8 무선 기계식 키보드', 119000, '{"brand": "키크론", "switch": "갈축", "layout": "텐키리스", "wireless": true, "colors": ["gray", "white"]}'),
  ('keyboard', '로지텍 MX Keys 무선 키보드',   139000, '{"brand": "로지텍", "layout": "풀배열", "wireless": true, "battery": {"type": "충전식", "hours": 240}}'),
  ('ereader',  '크레마 S 전자책 리더기',       199000, '{"brand": "크레마", "screen": 6, "storage_gb": 32, "colors": ["black"]}'),
  ('stand',    '원목 독서대 L',                 45000, '{"material": "원목", "angle_steps": 5}'),
  ('keyboard', '레오폴드 FC900R 유선 키보드',   149000, '{"brand": "레오폴드", "switch": "적축", "layout": "풀배열", "wireless": false}');

SELECT id, category, name, attrs FROM products ORDER BY id;
```

```text
----+----------+------------------------------+------------------------------------------------------------------------------------------------------------
  1 | keyboard | 키크론 K8 무선 기계식 키보드 | {"brand": "키크론", "colors": ["gray", "white"], "layout": "텐키리스", "switch": "갈축", "wireless": true}
```

넣을 때와 키 순서가 다르다. 이 차이가 `json`과 `jsonb`의 차이에서 나온다.

## json과 jsonb는 저장 방식이 다르다

PostgreSQL에는 JSON 타입이 두 개 있다. `json`은 받은 문자열을 그대로 저장하고 쓸 때마다 다시 해석한다. `jsonb`는 저장할 때 한 번 해석해서 이진 형식으로 바꿔 둔다.

```sql
SELECT '{"b": 1, "a": 2, "a": 3,  "c": [1, 2]}'::json  AS as_json,
       '{"b": 1, "a": 2, "a": 3,  "c": [1, 2]}'::jsonb AS as_jsonb;
```

```text
                as_json                 |           as_jsonb
----------------------------------------+-------------------------------
 {"b": 1, "a": 2, "a": 3,  "c": [1, 2]} | {"a": 3, "b": 1, "c": [1, 2]}
(1 row)
```

`json`은 공백, 키 순서, 중복 키까지 그대로 둔다. `jsonb`는 중복 키 중 마지막 것만 남기고, 키를 자기 순서(짧은 키 먼저, 같은 길이면 바이트 순)로 정렬하고, 공백을 버린다. 그 대가로 읽을 때 다시 해석할 필요가 없고, 포함 연산자(`@>`)와 GIN 인덱스를 쓸 수 있다. 크기는 비슷하다(`{"brand": "키크론", "wireless": true}`가 json 44바이트, jsonb 46바이트).

`json`을 쓸 이유는 받은 원문을 바이트 하나 안 바꾸고 보관해야 할 때 정도다(웹훅 서명 검증용 원문 같은). 그 밖에는 `jsonb`를 쓴다.

## 화살표로 꺼내고 포함 연산자로 찾기

꺼내는 연산자는 결과 타입이 둘로 갈린다. `->`는 `jsonb`를, `->>`는 `text`를 돌려준다. 중첩된 곳은 경로 배열을 받는 `#>`, `#>>`로 꺼낸다.

```sql
SELECT name,
       attrs -> 'brand'             AS brand_json,   -- jsonb: 따옴표가 붙어 있다
       attrs ->> 'brand'            AS brand_text,   -- text
       attrs #>  '{battery,hours}'  AS hours_json,   -- 경로로 꺼내기
       attrs #>> '{battery,hours}'  AS hours_text,
       attrs -> 'colors' -> 0       AS first_color   -- 배열은 0부터
FROM products WHERE id IN (1, 2);
```

```text
             name             | brand_json | brand_text | hours_json | hours_text | first_color
------------------------------+------------+------------+------------+------------+-------------
 키크론 K8 무선 기계식 키보드 | "키크론"   | 키크론     |            |            | "gray"
 로지텍 MX Keys 무선 키보드   | "로지텍"   | 로지텍     | 240        | 240        |
(2 rows)
```

없는 키는 오류 없이 NULL이 된다. 편하지만, 키 이름을 `"brnad"`로 잘못 써도 아무도 알려 주지 않는다는 뜻이기도 하다. 숫자로 비교하려면 `(attrs ->> 'screen')::int >= 6`처럼 꺼내서 형 변환해야 하고, 그 키에 숫자가 아닌 값이 하나라도 있으면 쿼리 전체가 형 변환 오류로 멈춘다.

조건 검색에는 포함 연산자 `@>`가 핵심이다. "왼쪽 JSON이 오른쪽 JSON을 품고 있나"를 본다. 배열이면 원소 일부만 적어도 된다.

```sql
SELECT id, name FROM products WHERE attrs @> '{"wireless": true}';      -- 무선 제품
SELECT id, name FROM products WHERE attrs @> '{"colors": ["white"]}';   -- 색 중에 white가 있는 것
```

```text
 id |             name
----+------------------------------
  1 | 키크론 K8 무선 기계식 키보드
  2 | 로지텍 MX Keys 무선 키보드
(2 rows)

 id |             name
----+------------------------------
  1 | 키크론 K8 무선 기계식 키보드
(1 row)
```

키가 있는지만 보는 연산자도 있다. `?`는 키 하나, `?|`는 배열 중 하나라도, `?&`는 배열 전부다.

```sql
SELECT id, name FROM products WHERE attrs ? 'switch';                          -- switch 키가 있다
SELECT id, name FROM products WHERE attrs ?| array['battery', 'storage_gb'];   -- 둘 중 하나라도
SELECT id, name FROM products WHERE attrs ?& array['switch', 'wireless'];      -- 둘 다
```

```text
 id |             name
----+------------------------------
  1 | 키크론 K8 무선 기계식 키보드
  5 | 레오폴드 FC900R 유선 키보드
(2 rows)

 id |            name
----+----------------------------
  2 | 로지텍 MX Keys 무선 키보드
  3 | 크레마 S 전자책 리더기
(2 rows)

 id |             name
----+------------------------------
  1 | 키크론 K8 무선 기계식 키보드
  5 | 레오폴드 FC900R 유선 키보드
(2 rows)
```

JDBC처럼 `?`를 바인드 변수 자리로 쓰는 드라이버에서는 `??`로 이스케이프하거나 같은 일을 하는 함수 `jsonb_exists(attrs, 'switch')`를 쓴다. 다만 함수로 쓰면 아래에서 볼 GIN 인덱스를 못 탄다.

## 일부만 고치는 jsonb_set과 JSON 경로

속성 하나만 바꿀 때는 `jsonb_set(대상, 경로, 새 값)`을 쓴다. 키를 지울 때는 `-`, 여러 키를 덮어쓸 때는 `||`로 합친다.

```sql
UPDATE products SET attrs = jsonb_set(attrs, '{battery,hours}', '300')   -- 중첩된 값 바꾸기
WHERE id = 2 RETURNING attrs;
BEGIN;
UPDATE products SET attrs = attrs || '{"switch": "청축"}'                -- 합치면 같은 키는 덮어쓴다
WHERE id = 1 RETURNING attrs ->> 'switch';
ROLLBACK;                                                                -- 시험만 하고 되돌린다
UPDATE products SET attrs = jsonb_set(attrs, '{battery,hours}', '100')   -- battery가 없는 행
WHERE id = 4 RETURNING attrs;
```

```text
                                                 attrs
--------------------------------------------------------------------------------------------------------
 {"brand": "로지텍", "layout": "풀배열", "battery": {"type": "충전식", "hours": 300}, "wireless": true}
(1 row)

 ?column?
----------
 청축
(1 row)

                 attrs
----------------------------------------
 {"material": "원목", "angle_steps": 5}
(1 row)
```

세 번째가 함정이다. 중간 경로(`battery`)가 없으면 `jsonb_set`은 아무것도 만들지 않고 원래 값을 돌려준다. 오류도 없다. 또 새 값 자리에 SQL `NULL`을 넘기면 결과 전체가 NULL이 된다. `jsonb_set('{"a": 1}', '{b}', NULL)`은 `NULL`이고, 컬럼이 `NOT NULL`이 아니라면 속성 전체가 날아간다. 13부터 있는 `jsonb_set_lax`는 이 경우 JSON `null`을 넣는 식으로 고를 수 있다.

복잡한 조건은 SQL/JSON 경로 언어(12부터)로 쓴다. `$`가 문서 전체, `[*]`가 배열의 모든 원소, `? (...)`가 필터다.

```sql
SELECT id, jsonb_path_query(attrs, '$.colors[*]') FROM products WHERE attrs ? 'colors';  -- 배열 펼치기
SELECT id, name FROM products WHERE attrs @? '$.battery ? (@.hours > 200)';             -- 배터리 200시간 초과
SELECT id, name FROM products WHERE attrs @@ '$.screen >= 6';                           -- 화면 6인치 이상
```

```text
 id | jsonb_path_query
----+------------------
  3 | "black"
  1 | "gray"
  1 | "white"
(3 rows)

 id |            name
----+----------------------------
  2 | 로지텍 MX Keys 무선 키보드
(1 row)

 id |          name
----+------------------------
  3 | 크레마 S 전자책 리더기
(1 row)
```

`@?`는 "경로에 맞는 값이 있나", `@@`는 "경로 조건식이 참인가"다. 경로 안에서는 숫자가 숫자로 비교되니 `->>`로 꺼내 형 변환하는 것보다 안전하다. 두 연산자는 GIN 인덱스도 쓸 수 있다.

## 10만 개에서 포함 검색을 빠르게 하는 GIN

상품을 10만 개로 늘린다. 카테고리 비율은 책 75%, 키보드 10%, 마우스 8%, 리더기 4%, 독서대 3% 정도로 잡았다. `LATERAL`로 행마다 속성을 먼저 만들고, 그 속성으로 이름을 짓는다.

```sql
SELECT setseed(0.42);
INSERT INTO products (category, name, price, attrs)
SELECT g.category,
       CASE g.category
         WHEN 'keyboard' THEN (a.attrs->>'brand') || CASE WHEN (a.attrs->>'wireless')::boolean THEN ' 무선 ' ELSE ' 유선 ' END
                              || (ARRAY['기계식 키보드', '키보드', '저소음 키보드', '텐키리스 키보드'])[1 + floor(random() * 4)::int]
         WHEN 'mouse'    THEN (a.attrs->>'brand') || CASE WHEN (a.attrs->>'wireless')::boolean THEN ' 무선 ' ELSE ' 유선 ' END
                              || (ARRAY['마우스', '게이밍 마우스', '버티컬 마우스'])[1 + floor(random() * 3)::int]
         WHEN 'ereader'  THEN (a.attrs->>'brand') || ' 전자책 리더기 ' || (a.attrs->>'screen') || '인치'
         WHEN 'stand'    THEN (a.attrs->>'material') || ' 독서대'
         ELSE (ARRAY['데이터베이스', '자료구조', '운영체제', '네트워크', '파이썬', '자바', '리액트', '쿠버네티스'])[1 + floor(random() * 8)::int]
              || ' ' || (ARRAY['입문', '실전', '완벽 가이드', '핵심 정리', '레시피'])[1 + floor(random() * 5)::int]
       END || ' ' || g.i,
       (5 + floor(random() * 300)::int) * 1000,
       a.attrs
FROM (
  SELECT i, CASE WHEN r < 0.10 THEN 'keyboard' WHEN r < 0.18 THEN 'mouse' WHEN r < 0.22 THEN 'ereader'
                 WHEN r < 0.25 THEN 'stand' ELSE 'book' END AS category
  FROM (SELECT i, random() AS r FROM generate_series(6, 100000) AS i) s
) g
CROSS JOIN LATERAL (
  SELECT CASE g.category
    WHEN 'keyboard' THEN jsonb_build_object(
        'brand',    (ARRAY['키크론', '로지텍', '레오폴드', '앱코', '한성'])[1 + floor(random() * 5)::int],
        'switch',   (ARRAY['갈축', '적축', '청축', '흑축'])[1 + floor(random() * 4)::int],
        'layout',   (ARRAY['풀배열', '텐키리스', '미니'])[1 + floor(random() * 3)::int],
        'wireless', random() < 0.4)
    WHEN 'mouse' THEN jsonb_build_object(
        'brand', (ARRAY['로지텍', '앱코', '레이저'])[1 + floor(random() * 3)::int],
        'dpi', (4 + floor(random() * 8)::int) * 1000, 'wireless', random() < 0.6)
    WHEN 'ereader' THEN jsonb_build_object(
        'brand', (ARRAY['크레마', '리디', '킨들'])[1 + floor(random() * 3)::int],
        'screen', (ARRAY[6, 7, 10])[1 + floor(random() * 3)::int],
        'storage_gb', (ARRAY[16, 32, 64])[1 + floor(random() * 3)::int])
    WHEN 'stand' THEN jsonb_build_object(
        'material', (ARRAY['원목', '철제', '아크릴'])[1 + floor(random() * 3)::int],
        'angle_steps', 3 + floor(random() * 5)::int)
    ELSE jsonb_build_object(
        'author', 'author' || floor(random() * 2000)::int, 'pages', 150 + floor(random() * 600)::int,
        'publisher', (ARRAY['한빛', '길벗', '인사이트', '위키북스'])[1 + floor(random() * 4)::int])
  END AS attrs
  OFFSET 0
) a;
VACUUM ANALYZE products;

SELECT id, category, name, attrs FROM products WHERE id IN (6, 8, 12) ORDER BY id;
```

```text
 id | category |             name             |                                   attrs
----+----------+------------------------------+---------------------------------------------------------------------------
  6 | book     | 데이터베이스 실전 6          | {"pages": 711, "author": "author724", "publisher": "한빛"}
  8 | mouse    | 로지텍 유선 마우스 8         | {"dpi": 6000, "brand": "로지텍", "wireless": false}
 12 | keyboard | 로지텍 무선 기계식 키보드 12 | {"brand": "로지텍", "layout": "미니", "switch": "청축", "wireless": true}
(3 rows)
```

"키크론 갈축 키보드"를 찾는다. 아래 실행 계획들은 병렬 실행을 끄고(`max_parallel_workers_per_gather = 0`) 비교했다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM products WHERE attrs @> '{"brand": "키크론", "switch": "갈축"}';
```

```text
   ->  Seq Scan on products  (cost=0.00..3191.00 rows=968 width=0) (actual time=0.010..26.312 rows=516 loops=1)
         Filter: (attrs @> '{"brand": "키크론", "switch": "갈축"}'::jsonb)
         Rows Removed by Filter: 99484
         Buffers: shared hit=1941
 Execution Time: 26.467 ms
```

516건을 찾으려고 10만 행을 모두 읽고(1,941페이지) 99,484행을 버렸다. B-tree는 값 하나를 정렬해 두는 구조라 "이 문서가 이 조각을 품었나"에는 못 쓴다. 여기에 맞는 인덱스가 GIN(Generalized Inverted Index)이다. 이름 그대로 역색인이다. 문서를 조각(키, 값)으로 쪼개고, 조각마다 "이 조각이 들어 있는 행 목록(posting list)"을 적어 둔다. 책 뒤의 찾아보기가 단어마다 쪽수를 적어 두는 것과 같다.

```sql
CREATE INDEX products_attrs_gin ON products USING gin (attrs);   -- 기본 연산자 클래스 jsonb_ops
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM products WHERE attrs @> '{"brand": "키크론", "switch": "갈축"}';
```

```text
   ->  Bitmap Heap Scan on products  (cost=43.95..1686.92 rows=968 width=0) (actual time=0.536..1.407 rows=516 loops=1)
         Recheck Cond: (attrs @> '{"brand": "키크론", "switch": "갈축"}'::jsonb)
         Heap Blocks: exact=453
         Buffers: shared hit=476
         ->  Bitmap Index Scan on products_attrs_gin  (cost=0.00..43.71 rows=968 width=0) (actual time=0.495..0.495 rows=516 loops=1)
               Index Cond: (attrs @> '{"brand": "키크론", "switch": "갈축"}'::jsonb)
               Buffers: shared hit=23
 Execution Time: 1.482 ms
```

26.5ms가 1.5ms로, 1,941페이지가 476페이지로 줄었다. 인덱스에서 읽은 건 23페이지이고 나머지 453페이지는 결과 행이 있는 힙 페이지다. 인덱스 안에서 일어난 일을 그림으로 보자.

마지막 단계의 재확인이 중요하다. 기본 `jsonb_ops`는 키와 값을 따로따로 조각으로 넣는다. 그래서 `{"a": {"brand": "키크론"}}`처럼 다른 깊이에 있는 값도 같은 조각에 걸릴 수 있어서, 후보를 받은 뒤 힙에서 다시 확인한다.

## jsonb_ops와 jsonb_path_ops

GIN에는 jsonb용 연산자 클래스가 두 개 있다. 기본 `jsonb_ops`는 키와 값을 각각 조각으로 넣어서 `@>`, `?`, `?|`, `?&`, `@?`, `@@`를 모두 지원한다. `jsonb_path_ops`는 "경로와 값"을 묶어 해시 하나로 넣는다. `brand:키크론`이 하나의 조각이 되는 셈이라 더 작고 `@>`가 더 정확하지만, 키만 있는지 보는 `?` 계열은 못 쓴다.

```sql
DROP INDEX products_attrs_gin;
CREATE INDEX products_attrs_pathops ON products USING gin (attrs jsonb_path_ops);

EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM products WHERE attrs @> '{"brand": "키크론", "switch": "갈축"}';
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM products WHERE attrs ? 'switch';
```

```text
-- @>: jsonb_path_ops를 쓴다
         ->  Bitmap Index Scan on products_attrs_pathops  (cost=0.00..26.34 rows=968 width=0) (actual time=0.173..0.174 rows=516 loops=1)
               Index Cond: (attrs @> '{"brand": "키크론", "switch": "갈축"}'::jsonb)
               Buffers: shared hit=7
 Execution Time: 1.254 ms

-- ?: 인덱스를 못 쓴다
   ->  Seq Scan on products  (cost=0.00..3191.00 rows=9278 width=0) (actual time=0.008..14.054 rows=9940 loops=1)
         Filter: (attrs ? 'switch'::text)
         Rows Removed by Filter: 90060
 Execution Time: 14.582 ms
```

인덱스 크기는 `jsonb_ops` 1752kB, `jsonb_path_ops` 1272kB였고, 같은 `@>` 검색에서 인덱스 페이지를 23개 대신 7개 읽었다. `jsonb_ops`였을 때 `attrs ? 'switch'`는 인덱스를 써서 9.4ms였다. 쿼리가 `@>` 위주면 `jsonb_path_ops`, 키 존재 검사도 많으면 기본값을 고른다.

GIN은 공짜가 아니다. 행 하나를 넣으면 조각 수만큼 인덱스 항목이 생긴다. 그래서 GIN은 새 항목을 일단 대기 목록(pending list)에 쌓았다가 VACUUM이나 목록이 `gin_pending_list_limit`(기본 4MB)를 넘을 때 한꺼번에 정리한다(`fastupdate`, 기본 켜짐). 쓰기는 빨라지지만 목록이 큰 동안에는 검색이 그 목록까지 훑어서 느려지고, 정리하는 순간의 `INSERT` 하나가 갑자기 오래 걸리기도 한다.

## 자주 찾는 키는 식 인덱스로

"브랜드가 키크론인 상품"처럼 키 하나를 같다로 비교하는 일이 대부분이라면 GIN보다 그 키 하나에 거는 B-tree 식 인덱스가 작고 빠르다. 이번에는 `->>`로 쓴 쿼리다. 위의 GIN은 `->>` 비교에는 쓰이지 않는다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM products WHERE attrs ->> 'brand' = '키크론';

CREATE INDEX products_brand_idx ON products ((attrs ->> 'brand'));   -- 괄호 두 겹: 식 인덱스
ANALYZE products;

EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM products WHERE attrs ->> 'brand' = '키크론';
```

```text
-- 식 인덱스 전
   ->  Seq Scan on products  (cost=0.00..3441.00 rows=500 width=0) (actual time=0.009..13.793 rows=1952 loops=1)
         Filter: ((attrs ->> 'brand'::text) = '키크론'::text)
         Rows Removed by Filter: 98048
 Execution Time: 13.919 ms

-- 식 인덱스 후
   ->  Bitmap Heap Scan on products  (cost=22.40..2036.38 rows=1820 width=0) (actual time=0.376..2.598 rows=1952 loops=1)
         ->  Bitmap Index Scan on products_brand_idx  (cost=0.00..21.94 rows=1820 width=0) (actual time=0.211..0.211 rows=1952 loops=1)
               Index Cond: ((attrs ->> 'brand'::text) = '키크론'::text)
 Execution Time: 2.781 ms
```

인덱스 크기는 696kB다. 그런데 시간보다 예상 행 수를 보자. 인덱스 전에는 `rows=500`으로 예상했는데 실제는 1,952행이다. 500은 통계가 없을 때 쓰는 기본 추정치(같다 비교는 0.5%)다. 식 인덱스를 만들고 `ANALYZE`를 하면 PostgreSQL이 그 식의 통계를 따로 모아서 `rows=1820`으로 실제에 가까워졌다. 통계가 없는 다른 키는 여전히 엉터리다.

```sql
EXPLAIN SELECT * FROM products WHERE (attrs ->> 'pages')::int > 700;
SELECT count(*) FROM products WHERE (attrs ->> 'pages')::int > 700;
```

```text
-----------------------------------------------------------------
```

범위 비교의 기본 추정치는 3분의 1이라 33,333행으로 예상했다. 실제는 6,185행이다. 이 조건이 조인 안에 들어가면 플래너가 조인 순서와 방법을 잘못 고를 수 있다.

## jsonb에 넣을 것과 컬럼으로 뺄 것

여기까지 보면 기준이 생긴다. jsonb가 잘 맞는 것은 카테고리마다 다르고, 자주 바뀌고, 주로 통째로 읽거나 `@>`로 거르는 속성이다. 외부 API 응답, 설정, 상품 옵션이 그렇다.

컬럼으로 빼야 하는 것은 그 반대다. 모든 행에 있는 값, 외래 키가 필요한 값, `NOT NULL`이나 범위 같은 제약이 필요한 값, 범위 조건과 정렬과 조인에 쓰는 값이다. 제약은 `CHECK (jsonb_typeof(attrs -> 'wireless') = 'boolean')`처럼 jsonb에도 걸 수는 있지만 키마다 쓰다 보면 결국 컬럼을 흉내 내게 된다. 통계도 앞에서 본 대로 식 인덱스를 만든 키만 생긴다.

갱신 비용도 다르다. jsonb는 값 하나라서 키 하나를 바꿔도 문서 전체를 새로 쓴다. 행이 약 2KB를 넘으면 큰 값을 압축하고, 그래도 크면 TOAST라는 별도 저장소로 옮겨 둔다. 일반 컬럼만 바꾸면 TOAST 쪽은 그대로 두고 포인터만 복사하지만 jsonb를 바꾸면 TOAST 데이터까지 다시 쓴다. 리뷰 2,000개를 품은 87KB짜리 jsonb가 있는 행에서 재고 하나를 바꿔 WAL(변경 기록) 양을 쟀다.

```sql
CREATE TABLE big_attrs (id int PRIMARY KEY, stock int NOT NULL, attrs jsonb NOT NULL);
INSERT INTO big_attrs
SELECT 1, 10, jsonb_build_object('brand', '키크론', 'stock', 10,
  'reviews', (SELECT jsonb_agg(jsonb_build_object('user', 'u' || i, 'stars', 1 + i % 5,
                                                  'text', md5(i::text) || md5((i + 1)::text)))
              FROM generate_series(1, 2000) i));
SELECT pg_column_size(attrs) AS stored_bytes FROM big_attrs;     -- 87298

-- psql 변수에 WAL 위치를 담아 가며 잰다
SELECT pg_current_wal_lsn() AS lsn0 \gset
UPDATE big_attrs SET stock = 5 WHERE id = 1;                                  -- 일반 컬럼
SELECT pg_current_wal_lsn() AS lsn1 \gset
UPDATE big_attrs SET attrs = jsonb_set(attrs, '{stock}', '5') WHERE id = 1;  -- jsonb 안의 키
SELECT pg_current_wal_lsn() AS lsn2 \gset
SELECT pg_wal_lsn_diff(:'lsn1', :'lsn0') AS wal_column_update,
       pg_wal_lsn_diff(:'lsn2', :'lsn1') AS wal_jsonb_update;
```

```text
 wal_column_update | wal_jsonb_update
-------------------+------------------
               168 |            96032
(1 row)
```

같은 "재고 5로 바꾸기"가 168바이트와 96KB다. 세 번 반복해도 거의 같았다. 자주 바뀌는 값(재고, 조회수, 상태)을 큰 jsonb 안에 넣으면 디스크, WAL, 복제가 모두 이만큼 부풀고, 죽은 행이 커서 VACUUM도 바빠진다. 자주 바뀌는 값은 컬럼으로 뺀다.

MySQL 8의 `JSON` 타입은 PostgreSQL의 jsonb처럼 이진 형식으로 저장한다. GIN 같은 범용 인덱스는 없어서 생성 컬럼에 인덱스를 걸거나 8.0.17부터 배열용 다중 값 인덱스(`CAST(... AS ... ARRAY)`)를 쓴다. `->>` 연산자 문법은 비슷하다.

## 한국어는 어디서 막히나

같은 일을 한국어로 하면 문제가 드러난다. PostgreSQL 16에 들어 있는 텍스트 검색 설정은 29개이고(`SELECT cfgname FROM pg_ts_config`), 한국어 설정은 없다. 언어 규칙 없이 공백과 문장 부호로만 자르는 `simple`을 쓰게 된다.

```sql
SELECT to_tsvector('simple', '무선 기계식 키보드를 샀는데 키보드 소리가 크다');
SELECT to_tsvector('simple', '무선 기계식 키보드를 샀는데') @@ to_tsquery('simple', '키보드')   AS exact,
       to_tsvector('simple', '무선 기계식 키보드를 샀는데') @@ to_tsquery('simple', '키보드:*') AS prefix;
```

```text
                                to_tsvector
----------------------------------------------------------------------------
 '기계식':2 '무선':1 '샀는데':4 '소리가':6 '크다':7 '키보드':5 '키보드를':3
(1 row)

 exact | prefix
-------+--------
 f     | t
(1 row)
```

한국어는 단어에 조사와 어미가 붙는다. `키보드를`과 `키보드`가 다른 어휘소가 되어 "키보드"로 찾으면 못 찾는다. 앞부분 일치(`키보드:*`)로 조사 붙은 경우는 건지지만, `무선키보드`처럼 붙여 쓴 복합어 가운데 있는 `키보드`는 여전히 못 찾는다. `english` 설정에 한국어를 넣어도 결과는 `simple`과 같다.

방법은 몇 가지다. 기본으로 들어 있는 `pg_trgm`은 단어가 아니라 세 글자 조각으로 비교해서 조사, 붙여 쓰기와 상관없이 부분 문자열을 찾는다(바로 다음 섹션). 따로 설치하는 확장으로는 두 글자 조각을 쓰는 `pg_bigm`이 있다. 한국어는 두 글자 단어가 많은데 `pg_trgm`은 두 글자 검색어에 약해서 그 빈틈을 메운다. 형태소 분석기(mecab-ko와 그 사전)를 PostgreSQL 텍스트 검색 파서로 붙이는 확장도 있어서, 이걸 쓰면 `키보드를`에서 `키보드`를 뽑아낸다. 둘 다 이 글의 환경에는 설치하지 않았다. 직접 빌드하거나 패키지를 찾아야 하고, RDS 같은 관리형 서비스는 허용된 확장만 쓸 수 있으니 그 서비스의 확장 목록에서 먼저 확인한다.

상품명처럼 조사가 거의 없는 짧은 텍스트는 `simple`로도 쓸 만하다. 상품 10만 개에 검색용 `tsvector` 컬럼을 만든다. 앞 글에서 본 generated column으로 만들면 이름이 바뀔 때 저절로 다시 계산된다. `setweight`로 이름은 A, 브랜드와 스위치는 B 가중치를 준다.

```sql
-- 인덱스 없이 매번 tsvector를 계산하면
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM products
WHERE to_tsvector('simple', name) @@ websearch_to_tsquery('simple', '무선 기계식 키보드');

ALTER TABLE products
  ADD COLUMN search_vec tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('simple', name), 'A') ||
    setweight(to_tsvector('simple', coalesce(attrs ->> 'brand', '') || ' ' || coalesce(attrs ->> 'switch', '')), 'B')
  ) STORED;
CREATE INDEX products_search_gin ON products USING gin (search_vec);

SELECT search_vec FROM products WHERE id = 1;
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM products
WHERE search_vec @@ websearch_to_tsquery('simple', '무선 기계식 키보드');
```

```text

   ->  Seq Scan on products  (cost=0.00..28191.00 rows=1 width=0) (actual time=0.019..178.098 rows=957 loops=1)
         Filter: (to_tsvector('simple'::regconfig, name) @@ '''무선'' & ''기계식'' & ''키보드'''::tsquery)
         Rows Removed by Filter: 99043
 Execution Time: 178.313 ms

                             search_vec
--------------------------------------------------------------------
 'k8':2A '갈축':7B '기계식':4A '무선':3A '키보드':5A '키크론':1A,6B
(1 row)

-- 컬럼과 GIN 후
   ->  Bitmap Heap Scan on products  (cost=43.13..125.57 rows=22 width=0) (actual time=0.601..1.521 rows=957 loops=1)
         ->  Bitmap Index Scan on products_search_gin  (cost=0.00..43.12 rows=22 width=0) (actual time=0.516..0.517 rows=957 loops=1)

```

178ms가 1.6ms가 됐다. 인덱스 전에는 행마다 `to_tsvector`를 다시 계산하느라 LIKE보다도 느렸다. `to_tsvector`는 설정 이름을 명시해야 IMMUTABLE이라 generated column에 쓸 수 있다(설정을 생략하면 `default_text_search_config`를 따라서 안 된다). GIN 인덱스 크기는 6168kB였다.

검색어는 `websearch_to_tsquery`(11부터)로 받는 게 편하다. 검색창에 사람이 치는 문법을 그대로 해석하고, 잘못된 문법에도 오류를 내지 않는다. `to_tsquery`는 `&`, `|` 같은 연산자 문법이라 사용자 입력을 그대로 넣으면 문법 오류가 난다.

```sql
SELECT websearch_to_tsquery('simple', '무선 키보드 -게이밍 "기계식 키보드" or 마우스');
```

```text
                       websearch_to_tsquery
------------------------------------------------------------------
 '무선' & '키보드' & !'게이밍' & '기계식' <-> '키보드' | '마우스'
(1 row)
```

공백은 AND, `-`는 NOT, 따옴표는 붙어 있는 구절(`<->`), `or`는 OR이 된다.

순위는 `ts_rank`로 매긴다. 검색어가 많이, 높은 가중치 자리에 나올수록 점수가 높다. 기본 가중치는 D, C, B, A가 0.1, 0.2, 0.4, 1.0이다.

```sql
SELECT id, name, attrs ->> 'switch' AS switch, round(ts_rank(search_vec, q)::numeric, 4) AS rank
FROM products, to_tsquery('simple', '키보드 | 갈축') AS q
WHERE search_vec @@ q AND id < 60
ORDER BY rank DESC, id;
```

```text

----+------------------------------+--------+--------
  1 | 키크론 K8 무선 기계식 키보드 | 갈축   | 0.4255

  2 | 로지텍 MX Keys 무선 키보드   |        | 0.3040
  5 | 레오폴드 FC900R 유선 키보드  | 적축   | 0.3040
```

이름(A)의 "키보드"와 스위치(B)의 "갈축"이 둘 다 맞은 행이 위로 왔다. `ts_rank`는 결과마다 `tsvector`를 읽어 계산하므로 `WHERE`로 후보를 줄인 뒤에 정렬한다. 결과가 수만 건이면 정렬 비용이 커지는데, 이 지점이 PostgreSQL 전문 검색이 검색 엔진보다 약한 곳이다. 검색 결과에서 맞은 단어를 강조할 때는 `ts_headline`을 쓴다.

```sql
  websearch_to_tsquery('simple', '무선 갈축'),
  'StartSel=<b>, StopSel=</b>, MaxWords=8, MinWords=4');
```

```text
(1 row)
```

`ts_headline`은 저장된 `tsvector`가 아니라 원문을 다시 분석해서 느리다. 화면에 보여 줄 10~20건에만 쓴다. 그리고 결과 HTML을 그대로 화면에 넣으면 원문에 있던 태그도 살아나니, 원문을 먼저 이스케이프하거나 강조 표시를 화면 쪽에서 입힌다.

## 세 글자씩 잘라 비교하는 pg_trgm

`pg_trgm`은 PostgreSQL에 함께 배포되는 확장(contrib)이다. 문자열을 세 글자 조각(트라이그램)으로 잘라서, 조각이 얼마나 겹치는지로 비슷한 정도를 잰다. 처음의 `LIKE '%기계식 키보드%'`를 인덱스로 빠르게 하는 것도 이 확장이다.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
SELECT show_trgm('cat'), show_trgm('Hello, World!');
```

```text
        show_trgm        |                           show_trgm
-------------------------+---------------------------------------------------------------
 {"  c"," ca","at ",cat} | {"  h","  w"," he"," wo",ell,hel,"ld ",llo,"lo ",orl,rld,wor}
(1 row)
```

규칙이 출력에 보인다. 소문자로 바꾸고, 글자나 숫자가 아닌 것(공백, 쉼표, 느낌표)에서 단어를 나누고, 단어마다 앞에 공백 두 개, 뒤에 공백 하나를 붙여서 세 글자씩 자른다. 그래서 `cat` 한 단어가 조각 네 개가 된다. 한글도 글자로 인식되지만 `show_trgm('키보드')`는 `{0x9fa68f,...}`처럼 해시로 보여 준다. 한 글자가 여러 바이트인 조각은 해시로 줄여 저장하기 때문이다. 아래 그림에서 `키보드`가 잘리는 과정을 보자.

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM products WHERE name LIKE '%기계식 키보드%';
```

한국어에서 아픈 곳은 두 글자 검색어다. `LIKE '%독서%'`처럼 앞뒤가 열린 두 글자 패턴에서는 단어 가운데의 세 글자 조각을 하나도 만들 수 없다. 앞뒤 공백 조각(`␣␣독`, `독서␣`)은 단어 경계라는 뜻이라 쓸 수 없다. 그래서 인덱스가 거를 수 없고, 플래너는 Seq Scan을 고른다.

## 오타도 찾는 similarity

트라이그램은 오타에 강하다. 두 문자열의 조각 집합에서 "겹치는 조각 수 ÷ 전체 조각 수(합집합)"를 계산한 것이 `similarity()`다. `%` 연산자는 이 값이 `pg_trgm.similarity_threshold`(기본 0.3) 이상인지 보고, 같은 GIN 인덱스를 쓴다.

```sql
SELECT name, similarity(name, '키크론 기계식 키보더') AS sim
FROM products
WHERE name % '키크론 기계식 키보더'          -- 오타: 키보더
ORDER BY sim DESC, id
LIMIT 5;
```

```text

-------------------------------+------------

 키크론 무선 기계식 키보드 140 |       0.45
 키크론 무선 기계식 키보드 353 |       0.45
```

`키보더`라고 잘못 쳐도 키크론 기계식 키보드가 맨 위에 나온다. 실행 계획을 보면 인덱스가 후보 3,926행을 내놓고 재확인에서 3,418행을 버려 508행이 남았다(15ms). 조각이 흔하면 후보가 많아진다. 임계값을 올리면 후보가 줄지만 덜 비슷한 결과를 놓친다. 단어 하나를 긴 문장 안에서 찾을 때는 문장 전체와 비교하는 `similarity` 대신 `word_similarity`와 `<%` 연산자가 맞다.

`similarity`를 직접 계산해 보자. 위 규칙대로 조각을 만들고 자카드 유사도를 구한다. 테스트의 기대값은 실제 `similarity()` 결과를 소수 넷째 자리로 반올림한 것이다(`similarity('키보드', '키보드 커버')`는 `0.5714286`).

PostgreSQL 안에서 버티는 동안의 장점은 크다. 데이터와 검색 색인이 같은 트랜잭션 안에 있어서 상품을 고치면 커밋하는 순간 검색에 반영된다. 동기화 파이프라인도, 운영할 클러스터도 하나 줄어든다. 상품 수십만 개, 검색 요청이 DB가 감당할 만한 수준이고, 정확도 요구가 "단어가 들어 있으면 나온다" 정도라면 `pg_trgm`과 `tsvector`로 충분하다.

## 조각을 쪼개 두는 방식이 결국 같다

jsonb의 `@>`, 전문 검색의 `@@`, `pg_trgm`의 `LIKE`는 모두 같은 생각 위에 있다. 값을 조각(키와 값, 어휘소, 세 글자)으로 쪼개고, GIN이 조각마다 행 목록을 적어 두고, 검색할 때 목록을 교집합한 뒤 힙에서 다시 확인한다. 어떤 조각으로 쪼개느냐가 무엇을 찾을 수 있는지를 정한다. 그래서 한국어의 조사는 어휘소 방식에서, 두 글자 검색어는 세 글자 방식에서 걸린다. 다음 글 [PostgreSQL 내부 구조](/posts/postgres-architecture)에서는 이 인덱스들과 테이블이 실제로 디스크의 페이지와 WAL에 어떻게 쓰이는지 내려가 본다.

## 면접에서 나올 만한 질문

### json과 jsonb는 무엇이 다르고, 무엇을 쓰나요?

`json`은 원문 문자열을 그대로 저장하고 읽을 때마다 해석한다. `jsonb`는 저장할 때 이진 형식으로 바꿔서 공백과 중복 키를 버리고 키를 정렬하지만, 읽기가 빠르고 `@>` 연산자와 GIN 인덱스를 쓸 수 있다. 원문 보존이 꼭 필요한 경우가 아니면 `jsonb`를 쓴다.

### jsonb 컬럼 검색은 어떻게 인덱싱하나요?

`@>`나 키 존재(`?`) 검색은 GIN 인덱스를 건다. 기본 `jsonb_ops`는 키와 값을 각각 넣어 모든 연산자를 지원하고, `jsonb_path_ops`는 경로와 값을 해시로 묶어 더 작고 `@>`에 빠르지만 `?`는 못 쓴다. 예제 10만 행에서 `@>` 검색이 26.5ms에서 약 1.3ms로 줄었다. 특정 키 하나를 같다로 자주 비교하면 `((attrs ->> 'brand'))` B-tree 식 인덱스가 더 작고, 그 식의 통계까지 생긴다.

### 어떤 데이터를 jsonb에 넣고 어떤 데이터를 컬럼으로 두나요?

카테고리마다 다르고 주로 통째로 읽거나 포함 조건으로 거르는 속성은 jsonb가 맞다. 외래 키, `NOT NULL` 같은 제약, 정렬과 범위 조건과 조인에 쓰는 값, 자주 바뀌는 값은 컬럼으로 뺀다. jsonb 안의 키는 통계가 없어 예상 행 수가 기본값(같다 0.5%, 범위 1/3)이 되고, 키 하나를 바꿔도 문서 전체와 TOAST까지 다시 써서 예제에서는 WAL이 168바이트 대 96KB였다.

### PostgreSQL 전문 검색은 어떻게 동작하나요?

문서를 `to_tsvector`로 어휘소와 위치 목록으로 바꾸고, 검색어를 `tsquery`로 바꿔 `@@`로 맞춘다. 언어 설정이 불용어 제거와 어간 추출을 해서 `jumping`과 `jumped`가 같은 `jump`가 된다. 실무에서는 `tsvector`를 generated column으로 저장하고 GIN을 걸며, 검색어는 `websearch_to_tsquery`, 순위는 `ts_rank`, 강조는 `ts_headline`을 쓴다. 예제에서 178ms가 1.6ms가 됐다.

### 한국어 검색은 왜 어렵고 어떻게 하나요?

PostgreSQL에는 한국어 텍스트 검색 설정이 없어서 `simple`로 공백 기준으로 자르게 되고, 조사가 붙은 `키보드를`과 `키보드`가 다른 어휘소가 된다. 부분 문자열은 `pg_trgm` GIN으로 찾을 수 있지만 두 글자 검색어는 인덱스를 못 쓴다. 이를 보완하는 확장으로 `pg_bigm`(두 글자 조각)과 mecab-ko 기반 형태소 파서가 있지만 따로 설치해야 하고 관리형 서비스에서는 지원 여부를 확인해야 한다. 요구가 커지면 형태소 분석기가 있는 검색 엔진으로 간다.

### LIKE '%키워드%'를 빠르게 하려면요?

앞이 열린 LIKE는 B-tree를 못 쓰니 `pg_trgm` 확장의 `gin_trgm_ops` 인덱스를 건다. 검색어를 세 글자 조각으로 나눠 조각을 모두 가진 행을 찾고 재확인한다. 예제에서 19ms가 2.9ms가 됐고 `ILIKE`도 같은 인덱스를 쓴다. 검색어가 두 글자 이하면 조각이 안 나와 인덱스를 못 쓰고, 오타 검색은 `similarity`와 `%` 연산자로 한다.

### PostgreSQL 검색에서 Elasticsearch로 넘어갈 시점은 언제인가요?

형태소 분석, 동의어, 자동 완성, 패싯, 정교한 관련도 점수가 필요해지거나 검색 부하가 주 DB를 압박할 때다. 그 전까지는 데이터와 색인이 같은 트랜잭션에 있어 즉시 일관되고 운영할 시스템이 하나 적다는 장점이 크다. 넘어가면 CDC나 아웃박스로 동기화해야 하고 검색 결과가 조금 늦어지는 것을 받아들여야 한다.
