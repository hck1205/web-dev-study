회원 가입 API에 이런 코드가 있다. 같은 이메일이 있는지 `SELECT ... FOR UPDATE`로 잠가서 확인하고, 없으면 `INSERT`한다. 중복 가입을 막으려고 일부러 잠금까지 걸었다. 그런데 가입이 몰리는 시간에 로그에 `Deadlock found when trying to get lock`이 찍힌다. 두 사람의 이메일은 `kim@ex.com`과 `lee@ex.com`으로 서로 다르다. 다른 행을 건드렸는데 왜 서로를 기다렸을까.

이 질문에 답하려면 MySQL의 저장 엔진 InnoDB가 데이터를 어떻게 쌓고, 고치고, 잠그는지 알아야 한다. 이 글은 그 순서로 간다. 테이블이 어떤 모양으로 저장되는지, 메모리의 버퍼 풀이 무엇을 남기는지, 커밋할 때 어떤 로그가 남는지, 옛 버전을 어떻게 다시 만드는지, 마지막으로 잠금이 어디에 걸리는지를 본다.

PostgreSQL 쪽 이야기는 이미 여러 글에 있다. 프로세스와 WAL은 [PostgreSQL 내부 구조](/posts/postgres-architecture), 격리 수준의 이론은 [트랜잭션과 격리 수준](/posts/db-transaction-isolation), 인덱스의 기본은 [인덱스: 책 뒤의 찾아보기](/posts/db-index)에서 다뤘다. 여기서는 그 설명을 반복하지 않고 InnoDB가 다르게 움직이는 부분만 깊게 판다. 복제와 스키마 변경은 이어지는 글 [MySQL 복제와 온라인 DDL](/posts/mysql-replication-online-ddl)에서 다룬다.

## 없으면 넣는 코드가 서로를 죽였다

먼저 장면을 그대로 재현해 본다. 두 세션 A와 B가 거의 동시에 가입을 처리한다.

```sql
-- [1] A: kim@ex.com이 있는지 잠가서 확인한다
START TRANSACTION;
SELECT * FROM users WHERE email = 'kim@ex.com' FOR UPDATE;

-- [2] B: lee@ex.com이 있는지 잠가서 확인한다
START TRANSACTION;
SELECT * FROM users WHERE email = 'lee@ex.com' FOR UPDATE;

-- [3] A: 없으니 넣는다 (여기서 멈춘다)
INSERT INTO users VALUES (40, 'kim@ex.com', 'Kim');

-- [4] B: 없으니 넣는다
INSERT INTO users VALUES (50, 'lee@ex.com', 'Lee');
```

두 세션의 화면은 이렇게 끝났다. 출력은 모두 아래 환경에서 직접 돌린 것이고, 세션 여러 개를 스크립트로 몰았기 때문에 에러 뒤에 `at line N`이 붙어 있다.

```text
-- A
SELECT * FROM users WHERE email = 'kim@ex.com' FOR UPDATE
Empty set (0.00 sec)

INSERT INTO users VALUES (40, 'kim@ex.com', 'Kim')
Query OK, 1 row affected (0.50 sec)

-- B
SELECT * FROM users WHERE email = 'lee@ex.com' FOR UPDATE
Empty set (0.00 sec)

INSERT INTO users VALUES (50, 'lee@ex.com', 'Lee')
ERROR 1213 (40001) at line 2: Deadlock found when trying to get lock; try restarting transaction
```

A의 `INSERT`가 0.50초 걸린 걸 보자. A는 B를 기다리고 있었고, B가 `INSERT`를 하자 InnoDB가 교착 상태를 알아채고 B를 롤백했다. 그제야 A가 풀려났다. 아래 그림에서 다음을 누르면 네 단계가 차례로 그려진다.

## 실험 환경과 두 테이블

기준은 Ubuntu 24.04 패키지의 MySQL 8.0.46(`8.0.46-0ubuntu0.24.04.4`)이다. 기본 격리 수준 `REPEATABLE-READ`, `binlog_format=ROW`, 버퍼 풀 128MB(기본값) 그대로 띄웠다. 8.4 LTS에서도 이 글의 동작 원리는 같지만 일부 기본값이 달라졌으니, 쓰는 서버에서는 `SELECT version(), @@transaction_isolation`과 `SHOW VARIABLES`로 직접 확인한다.

예제 테이블은 회원과 주문 두 개다. 글 끝까지 이 두 테이블로 간다.

```sql
CREATE TABLE users (
  id    BIGINT PRIMARY KEY,
  email VARCHAR(100) NOT NULL UNIQUE,   -- 유니크 보조 인덱스 email이 생긴다
  name  VARCHAR(50)  NOT NULL
);

CREATE TABLE orders (
  id      BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_id BIGINT      NOT NULL,
  amount  INT         NOT NULL,
  status  VARCHAR(10) NOT NULL,
  KEY idx_user (user_id)                -- 유니크가 아닌 보조 인덱스
);

INSERT INTO users VALUES (10,'ann@ex.com','Ann'),(20,'min@ex.com','Min'),(30,'zoe@ex.com','Zoe');
INSERT INTO orders (user_id, amount, status) VALUES
  (10,12000,'paid'),(10,8000,'paid'),(20,15000,'ready'),(30,4000,'paid'),(30,22000,'ready');
```

```text
+----+------------+------+        +----+---------+--------+--------+
| id | email      | name |        | id | user_id | amount | status |
+----+------------+------+        +----+---------+--------+--------+
| 10 | ann@ex.com | Ann  |        |  1 |      10 |  12000 | paid   |
| 20 | min@ex.com | Min  |        |  2 |      10 |   8000 | paid   |
| 30 | zoe@ex.com | Zoe  |        |  3 |      20 |  15000 | ready  |
+----+------------+------+        |  4 |      30 |   4000 | paid   |
                                  |  5 |      30 |  22000 | ready  |
                                  +----+---------+--------+--------+
```

메모리와 성능을 볼 때는 같은 모양의 큰 테이블 `orders_big`(150만 행, 회원 5만 명)을 따로 쓴다.

## 테이블은 기본 키 순서로 줄 선 B-tree다

InnoDB의 테이블은 기본 키로 정렬된 B-tree 하나다. 잎 페이지에 행 전체가 들어 있어서 클러스터드 인덱스라고 부른다. `email`이나 `user_id` 같은 보조 인덱스의 잎에는 행의 위치 대신 기본 키 값이 들어 있다. 이 구조 자체는 [인덱스 글의 MySQL 절](/posts/db-index#mysql-8은-표-자체가-인덱스다)에 그림과 함께 있으니, 여기서는 그 결과를 실제 숫자로만 확인한다.

```sql
-- 보조 인덱스만 읽으면 끝나는 쿼리 (id는 보조 인덱스 잎에 이미 있다)
EXPLAIN ANALYZE SELECT id FROM orders_big WHERE user_id = 42;
-- 행 전체가 필요한 쿼리 (기본 키로 한 번 더 내려가야 한다)
EXPLAIN ANALYZE SELECT * FROM orders_big WHERE user_id = 42;
```

```text
-> Covering index lookup on orders_big using idx_user (user_id=42)  (cost=3.26 rows=30) (actual time=0.0303..0.0389 rows=30 loops=1)

-> Index lookup on orders_big using idx_user (user_id=42)  (cost=26.8 rows=30) (actual time=0.269..0.535 rows=30 loops=1)
```

첫 줄의 `Covering index lookup`은 보조 인덱스만 읽었다는 뜻이고, 둘째 줄의 `Index lookup`은 찾은 기본 키 30개로 클러스터드 인덱스를 30번 더 내려갔다는 뜻이다. `actual time`의 끝값이 0.039ms와 0.535ms로 열 배 넘게 차이 난다. 회원 42의 주문은 5만 번째마다 하나씩 흩어져 있어서 30개 행이 모두 다른 페이지에 있기 때문이다. `cost`도 3.26과 26.8로 그 차이를 미리 계산하고 있다.

기본 키 범위는 반대로 행이 붙어 있어서 싸다.

```sql
EXPLAIN ANALYZE SELECT * FROM orders_big WHERE id BETWEEN 1000 AND 1029;
```

```text
-> Filter: (orders_big.id between 1000 and 1029)  (cost=6.83 rows=30) (actual time=0.0223..0.0402 rows=30 loops=1)
    -> Index range scan on orders_big using PRIMARY over (1000 <= id <= 1029)  (cost=6.83 rows=30) (actual time=0.0197..0.0339 rows=30 loops=1)
```

행 30개를 다 가져오는데 0.034ms다. 같은 30행이라도 기본 키로 붙어 있으면 한두 페이지면 되고, 보조 인덱스로 흩어져 있으면 30페이지를 읽는다. 그래서 InnoDB에서는 기본 키를 무엇으로 잡느냐가 곧 디스크 위의 행 순서를 정하는 일이다.

페이지 수는 통계 테이블에서 바로 보인다. 페이지 한 장은 16KB(`innodb_page_size=16384`)다. PostgreSQL의 8KB 두 배다.

```sql
SELECT index_name, stat_name, stat_value
FROM mysql.innodb_index_stats
WHERE database_name = 'shop' AND table_name = 'orders_big'
  AND stat_name IN ('size', 'n_leaf_pages');
```

```text
+------------+--------------+------------+
| index_name | stat_name    | stat_value |
+------------+--------------+------------+
| PRIMARY    | n_leaf_pages |      13764 |
| PRIMARY    | size         |      13809 |
| idx_user   | n_leaf_pages |       2449 |
| idx_user   | size         |       2855 |
+------------+--------------+------------+
```

`PRIMARY`가 곧 테이블이다. 13,809페이지 × 16KB = 약 216MB이고, `user_id`와 기본 키만 담은 `idx_user`는 그 5분의 1쯤이다. 디스크에서는 테이블 하나가 `.ibd` 파일 하나다(`innodb_file_per_table=ON`, 기본값). `ls -lh /var/lib/mysql/shop/`으로 보면 `orders_big.ibd`가 272M으로 통계보다 큰데, 페이지를 묶음(익스텐트, 1MB) 단위로 미리 잡아 두기 때문이다. 숨은 열도 있다. 행마다 그 행을 마지막으로 고친 트랜잭션 번호 `DB_TRX_ID`(6바이트)와 옛 버전을 가리키는 `DB_ROLL_PTR`(7바이트)가 붙는다. 이 두 열이 뒤에서 MVCC를 만든다.

## 버퍼 풀은 오래된 쪽 머리에 새 페이지를 넣는다

InnoDB는 디스크의 페이지를 메모리의 버퍼 풀에 올려 놓고 거기서 읽고 고친다. 기본 128MB는 테스트용 크기다. DB만 도는 서버라면 램의 절반에서 4분의 3 정도를 흔히 주고, `innodb_dedicated_server=ON`이면 램 크기를 보고 알아서 정한다. PostgreSQL은 `shared_buffers`를 작게 잡고 OS 페이지 캐시에 기대는 편인데, InnoDB는 버퍼 풀이 사실상 유일한 캐시가 되도록 크게 잡는 쪽이다.

버퍼 풀이 꽉 차면 LRU 목록의 끝에서 페이지를 내보낸다. 그런데 순진한 LRU라면 `orders_big`을 한 번 훑는 리포트 쿼리가 216MB를 밀어 넣어 128MB 버퍼 풀의 자주 쓰는 페이지를 모두 쫓아낸다. InnoDB는 이걸 막으려고 LRU를 둘로 나눈다. 앞쪽 63%가 young, 뒤쪽 37%가 old(`innodb_old_blocks_pct=37`)이고, 새로 읽은 페이지는 맨 앞이 아니라 old 구역의 머리에 들어간다. old에 들어온 뒤 `innodb_old_blocks_time`(기본 1000ms)이 지나서 다시 읽혀야 young으로 올라간다.

실제로 확인해 본다. `orders`를 1.2초 간격으로 두 번 읽어 young으로 만든 뒤, `orders_big`을 끝까지 훑고, 버퍼 풀에 `orders` 페이지가 남았는지 본다.

```sql
SELECT * FROM orders WHERE id = 1;   -- 1.2초 쉬고 한 번 더
SELECT COUNT(*) FROM orders_big WHERE memo <> 'y';   -- 클러스터드 인덱스 전체 스캔

-- 버퍼 풀 LRU에 orders 페이지가 남아 있나
SELECT table_name, index_name, is_old, COUNT(*) AS pages
FROM information_schema.innodb_buffer_page_lru
WHERE table_name = '`shop`.`orders`'
GROUP BY 1, 2, 3;
```

스캔 전에도 같은 한 줄이 나왔고, 스캔 후에도 그대로다.

```text
-- 스캔 후, innodb_old_blocks_time = 1000 (기본값)
+-----------------+------------+--------+-------+
| table_name      | index_name | is_old | pages |
+-----------------+------------+--------+-------+
| `shop`.`orders` | PRIMARY    | NO     |     1 |
+-----------------+------------+--------+-------+
```

같은 실험을 `SET GLOBAL innodb_old_blocks_time = 0`으로 바꿔서 하면 스캔 후 결과가 비어 있다(`Empty set`). 스캔 페이지가 읽히자마자 young으로 올라가 `orders` 페이지를 끝까지 밀어냈다. `is_old` 열이 `NO`라는 것도 확인해 둔다. young 구역에 있다는 뜻이다. `information_schema.innodb_buffer_page_lru`는 버퍼 풀 전체를 훑기 때문에 운영 서버에서 함부로 돌리지 않는다.

평소에 보는 숫자는 `SHOW ENGINE INNODB STATUS`의 버퍼 풀 절이다.

```text
----------------------
BUFFER POOL AND MEMORY
----------------------
Buffer pool size   8192
Database pages     8187
Old database pages 3002
Pages made young 15419, not young 53579
538.85 youngs/s, 1502.00 non-youngs/s
Buffer pool hit rate 710 / 1000, young-making rate 145 / 1000 not 405 / 1000
Pages read ahead 945.31/s, evicted without access 2.70/s, Random read ahead 0.00/s
```

`Buffer pool size 8192`는 페이지 수(8192 × 16KB = 128MB)다. `Buffer pool hit rate 710 / 1000`은 지난번 출력 이후 구간의 적중률이라서, 바로 앞에 대량 스캔을 돌린 이 순간에는 낮게 나왔다. 평소 OLTP 서버가 990 / 1000 아래로 자주 떨어지면 버퍼 풀이 작업 집합보다 작다는 신호다. `not young`이 크면 스캔이 old 구역에서 걸러지고 있다는 뜻이고, `Pages read ahead`는 순차 스캔을 알아채고 미리 읽어 온 양이다. 누적값은 `SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%'`로 본다. `Innodb_buffer_pool_reads`(디스크에서 읽은 횟수)를 `Innodb_buffer_pool_read_requests`(논리 읽기)로 나누면 놓친 비율이다.

## 커밋 한 번에 남는 기록 세 가지

`UPDATE orders SET amount = 13000 WHERE id = 1`을 커밋하면 InnoDB와 MySQL 서버는 세 가지 기록을 남긴다.

redo 로그는 "어느 페이지의 어디를 이렇게 바꿨다"는 물리적인 기록이다. 버퍼 풀의 페이지는 고친 뒤에도 한참 디스크에 쓰지 않는다. 그 사이에 서버가 죽어도 redo만 디스크에 있으면 다시 적용해서 되살린다. PostgreSQL의 WAL과 같은 역할이다. 8.0.30부터 크기를 `innodb_redo_log_capacity`(기본 100MB) 하나로 정하고, 데이터 디렉터리의 `#innodb_redo` 안에 파일 32개로 나눠 돌려 쓴다.

undo 로그는 "바꾸기 전 값"이다. 롤백할 때 되돌리는 데 쓰고, 다른 트랜잭션이 옛 버전을 읽을 때도 쓴다. 기본으로 `undo_001`, `undo_002` 두 개의 undo 테이블스페이스에 쌓인다. PostgreSQL에는 이게 없다. PostgreSQL은 옛 버전을 테이블 안에 그대로 두고 나중에 VACUUM으로 치운다.

binlog는 MySQL 서버 층이 남기는 논리적인 변경 기록이다. 복제와 시점 복구에 쓴다. InnoDB 바깥의 기록이라 redo와 binlog가 서로 어긋나지 않게 내부적으로 2단계 커밋을 한다. redo에 prepare를 쓰고, binlog를 쓰고, redo에 commit을 표시한다. binlog의 자세한 모양은 [복제 글](/posts/mysql-replication-online-ddl)에서 본다.

커밋마다 디스크까지 내리는 fsync가 두 번 들어가니 비싸다. 그래서 설정이 두 개 있다. 같은 `INSERT` 3,000개를 자동 커밋으로 넣어 시간을 재 봤다. 이 장비는 가상 디스크라 절댓값보다 비율을 본다.

`innodb_flush_log_at_trx_commit`은 1이면 커밋마다 redo를 fsync하고, 2면 OS에만 쓰고 1초마다 fsync하고, 0이면 1초마다 쓰고 fsync한다. `sync_binlog`는 1이면 커밋마다 binlog를 fsync하고 0이면 OS에 맡긴다. 둘 다 `SET GLOBAL`로 바로 바꿀 수 있다.

```text
trx_commit=1 sync_binlog=1: 2.678137562 s
trx_commit=2 sync_binlog=1: 1.862534891 s
trx_commit=2 sync_binlog=0: .450878910 s
trx_commit=0 sync_binlog=0: .527280379 s
```

둘 다 1인 "쌍 1" 설정이 여섯 배쯤 느리다. 대신 이것만 커밋이 끝난 트랜잭션을 정전에도 잃지 않는다. `innodb_flush_log_at_trx_commit=2`는 MySQL 프로세스가 죽는 건 견디지만(OS 캐시에 이미 있다) 서버 전원이 나가면 최대 1초쯤의 커밋을 잃는다. `sync_binlog=0`이면 정전 뒤에 binlog가 redo보다 짧아져 레플리카와 원본이 어긋날 수 있다. 돈이 오가는 서비스는 쌍 1을 기본으로 두고, 쓰기 처리량은 여러 커밋을 fsync 한 번에 묶는 그룹 커밋과 빠른 디스크로 푼다. 대량 적재처럼 다시 돌리면 되는 작업에서만 잠깐 낮춘다.

페이지를 디스크에 쓸 때도 장치가 하나 더 있다. 16KB 페이지를 쓰다가 전원이 나가면 반쪽만 써진 페이지가 남는다. redo는 "이 페이지의 이 부분을 바꿔라"라서 페이지 자체가 깨져 있으면 쓸 수 없다. InnoDB는 페이지를 먼저 doublewrite 파일(`#ib_16384_0.dblwr`)에 쓰고 나서 제자리에 쓴다. 깨지면 doublewrite의 사본으로 고친다. PostgreSQL은 같은 문제를 체크포인트 뒤 첫 수정 때 WAL에 페이지 통째를 쓰는 방식(full page writes)으로 푼다.

## 서버가 죽어도 커밋은 남고 커밋 안 한 것은 사라진다

redo와 undo가 실제로 어떻게 쓰이는지 서버를 죽여서 본다. 빈 테이블 `commit_log`에 세션 A는 `START TRANSACTION; INSERT INTO commit_log (v) VALUES (111);`까지만 하고 커밋하지 않는다. 다른 세션은 `INSERT INTO commit_log (v) VALUES (222)`를 자동 커밋으로 넣는다. 그 상태에서 테스트 서버의 `mysqld`를 `sudo kill -9 <pid>`로 끝내고 다시 띄운다.

다시 뜰 때 에러 로그(`log_error_verbosity=3`)에서 필요한 줄만 골랐다.

순서가 그대로 보인다. 마지막 체크포인트 LSN부터 redo를 읽어 48개 레코드를 다시 적용한다(커밋된 222가 살아난다). 그다음 커밋되지 않은 트랜잭션 하나를 찾아 undo로 되돌린다(111이 사라진다). 중간의 binlog 줄은 prepare까지만 하고 죽은 트랜잭션이 있었는지 binlog와 맞춰 보는 단계다. 여기서는 그런 트랜잭션이 없었다. id 1이 비어 있는 건 롤백된 111이 이미 번호를 가져갔기 때문이다. `AUTO_INCREMENT` 값은 롤백해도 돌려주지 않는다.

롤백이 백그라운드에서 돈다는 것도 기억해 둔다. 몇천만 행을 고치던 거대한 트랜잭션이 죽으면, 서버는 금방 뜨지만 그 롤백이 끝날 때까지 관련 행의 잠금이 남고 디스크가 바쁘다. 큰 배치를 잘게 나누는 이유 중 하나다.

## 옛 버전은 undo에서 다시 만들어 읽는다

InnoDB의 일반 `SELECT`는 잠금 없이 스냅숏을 읽는다(일관된 읽기, consistent read). 트랜잭션이 첫 `SELECT`를 하는 순간 read view라는 명단을 만든다. 명단에는 그 순간 아직 커밋하지 않은 트랜잭션 번호들, 그중 가장 작은 번호, 다음에 발급될 번호가 들어 있다. 행을 읽을 때마다 그 행의 `DB_TRX_ID`를 명단과 비교한다.

- 내가 고친 행이면 보인다.
- 명단의 가장 작은 번호보다 작으면 read view를 만들기 전에 커밋됐으니 보인다.
- 다음 발급 번호 이상이면 그 뒤에 시작한 트랜잭션이라 안 보인다.
- 그 사이에서 명단에 있으면 아직 커밋 전이라 안 보이고, 없으면 보인다.

안 보이면 `DB_ROLL_PTR`을 따라 undo의 한 단계 옛 버전으로 가서 같은 검사를 한다. 보이는 버전이 나올 때까지 되감는다.

이 방식의 비용은 오래 열린 트랜잭션이 치른다. read view가 살아 있는 동안에는 그 read view가 볼 수도 있는 undo를 지울 수 없다. 지우는 일은 purge 스레드가 하는데, 가장 오래된 read view보다 옛것만 치운다. 실제로 재 봤다. A가 스냅숏을 열어 두고, 다른 세션이 `orders`의 한 행을 2만 번 고친다.

```sql
-- A
START TRANSACTION WITH CONSISTENT SNAPSHOT;
SELECT id, amount FROM orders WHERE id = 1;

-- 다른 세션: 자동 커밋으로 2만 번
UPDATE orders SET amount = amount + 1 WHERE id = 1;
```

치우지 못한 undo의 양은 `SHOW ENGINE INNODB STATUS\G`의 `History list length`로 본다. 고치기 전 755였던 값이 이렇게 됐다.

```text
History list length 20001

-- 다른 세션: 최신 버전을 바로 읽는다
|  1 |  32000 |
1 row in set (0.00 sec)

-- A: 버전 2만 개를 되감는다
|  1 |  12000 |
1 row in set (0.02 sec)
```

행 하나를 읽는 데 20ms다. 같은 행을 계속 고치는 카운터 같은 테이블에서, 몇 시간 열린 트랜잭션은 이 값이 수백만이 되고 읽기가 눈에 띄게 느려진다. A가 커밋하자 몇 초 안에 `History list length 0`으로 내려갔다. undo 테이블스페이스 파일은 커진 채 남을 수 있는데, 8.0은 `innodb_undo_log_truncate=ON`(기본값)으로 일정 크기를 넘은 undo 테이블스페이스를 나중에 잘라 낸다.

오래 열린 트랜잭션은 이렇게 찾는다.

```sql
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_s,
       trx_mysql_thread_id, trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started;
```

```text
+-----------------+-----------+---------------------+-------+---------------------+-----------+
| trx_id          | trx_state | trx_started         | age_s | trx_mysql_thread_id | trx_query |
+-----------------+-----------+---------------------+-------+---------------------+-----------+
| 421848509091032 | RUNNING   | 2026-10-21 12:40:49 |     3 |                  75 | NULL      |
+-----------------+-----------+---------------------+-------+---------------------+-----------+
```

`trx_query`가 `NULL`이면 지금 실행 중인 문장이 없다는 뜻이다. 트랜잭션을 연 채로 앱이 다른 일을 하고 있는, 이른바 idle in transaction 상태다. 이 `trx_id`처럼 아주 큰 숫자는 아직 아무것도 고치지 않은 읽기 전용 트랜잭션에 붙는 임시 번호다. PostgreSQL에서는 같은 원인이 테이블 부풀림과 VACUUM 지연으로 나타난다([VACUUM과 autovacuum](/posts/postgres-mvcc-vacuum)). 증상은 달라도 처방은 같다. 트랜잭션을 짧게 유지한다.

## 같은 트랜잭션 안에서 SELECT와 UPDATE가 보는 세상이 다르다

`REPEATABLE READ`의 일반 `SELECT`는 스냅숏을 읽지만 `UPDATE`, `DELETE`, `SELECT ... FOR UPDATE`는 최신 커밋 값을 읽고 잠근다(잠금 읽기, locking read). 이론은 [격리 수준 글](/posts/db-transaction-isolation#mysql-innodb는-어떻게-다른가)에 있다. 실제로는 이런 모습이 된다.

```sql
-- A
START TRANSACTION;
SELECT id, user_id, status FROM orders WHERE user_id = 20;   -- 스냅숏을 만든다

-- B: 회원 20의 주문을 하나 더 넣고 커밋
INSERT INTO orders (user_id, amount, status) VALUES (20, 7000, 'ready');

-- A
SELECT id, user_id, status FROM orders WHERE user_id = 20;   -- 다시 읽는다
UPDATE orders SET status = 'paid' WHERE user_id = 20;        -- 고친다
SELECT id, user_id, status FROM orders WHERE user_id = 20;   -- 또 읽는다
ROLLBACK;
```

```text
-- 첫 SELECT
+----+---------+--------+
| id | user_id | status |
+----+---------+--------+
|  3 |      20 | ready  |
+----+---------+--------+

-- B가 커밋한 뒤 두 번째 SELECT도 3번 한 건뿐이다

-- UPDATE: 보이지 않던 6번까지 2건을 고쳤다
Query OK, 2 rows affected (0.01 sec)
Rows matched: 2  Changed: 2  Warnings: 0

-- 세 번째 SELECT: 이제 6번이 보인다
+----+---------+--------+
| id | user_id | status |
+----+---------+--------+
|  3 |      20 | paid   |
|  6 |      20 | paid   |
+----+---------+--------+
```

A의 스냅숏에는 6번 주문이 없었는데 `UPDATE`는 최신 데이터에서 6번을 찾아 고쳤다. 고친 순간 그 행의 `DB_TRX_ID`가 A 자신이 되니, 규칙상 다음 `SELECT`에 보인다. 이 동작 때문에 "`SELECT`로 개수를 세고, 같은 조건으로 `UPDATE`한 뒤, 세어 둔 개수와 비교하는" 코드는 InnoDB에서 맞지 않는다. 판단에 쓸 값은 처음부터 `FOR UPDATE`로 읽거나, `UPDATE`가 돌려준 영향받은 행 수를 쓴다. (B가 넣은 6번은 다음 실험을 위해 지웠다.)

PostgreSQL의 `REPEATABLE READ`는 여기서 다르게 반응한다. 스냅숏 이후에 다른 트랜잭션이 고친 행을 `UPDATE`하려 하면 `could not serialize access due to concurrent update`로 실패시킨다. 새로 들어온 행은 아예 `UPDATE` 대상에 들어가지 않는다. 같은 이름의 격리 수준이 이렇게 다르다.

## 잠금은 행이 아니라 인덱스 위에 걸린다

InnoDB의 행 잠금은 인덱스 레코드에 걸린다. 그리고 `REPEATABLE READ`에서 잠금 읽기가 인덱스를 훑으면, 찾은 레코드뿐 아니라 그 앞의 빈 간격도 잠근다. 레코드 잠금과 바로 앞 간격 잠금을 합친 것이 넥스트 키 잠금이다. 다른 트랜잭션이 그 간격에 새 행을 끼워 넣지 못하게 해서, 같은 잠금 읽기를 다시 해도 새 행이 끼어들지 않게(팬텀 방지) 만든다. binlog를 문장 단위로 복제하던 시절에 원본과 레플리카의 결과를 같게 만들려던 이유도 있다.

잠금이 실제로 어디에 걸리는지는 `performance_schema.data_locks`가 보여 준다. 다섯 가지 쿼리를 하나씩 `FOR UPDATE`로 돌리고, 롤백하기 전에 확인했다.

```sql
START TRANSACTION;
SELECT * FROM users WHERE id = 20 FOR UPDATE;       -- 쿼리만 바꿔 가며 반복
SELECT index_name, lock_type, lock_mode, lock_data
FROM performance_schema.data_locks;
ROLLBACK;
```

기본 키로 있는 행 하나를 찾으면 그 행만 잠근다.

```text
-- WHERE id = 20
+------------+-----------+---------------+-----------+
| index_name | lock_type | lock_mode     | lock_data |
+------------+-----------+---------------+-----------+
| NULL       | TABLE     | IX            | NULL      |
| PRIMARY    | RECORD    | X,REC_NOT_GAP | 20        |
+------------+-----------+---------------+-----------+
```

`IX`는 "이 테이블 어딘가의 행에 X 잠금을 걸겠다"는 표시(의도 잠금)라서 다른 행 잠금과는 부딪히지 않는다. `X,REC_NOT_GAP`이 간격 없이 레코드만 잠근 것이다. 유니크 인덱스로 정확히 한 행을 찾았으니 간격을 잠글 필요가 없다.

유니크 인덱스로 찾았는데 행이 없으면 간격을 잠근다.

```text
-- WHERE email = 'kim@ex.com' (없는 값)
+------------+-----------+-----------+------------------+
| index_name | lock_type | lock_mode | lock_data        |
+------------+-----------+-----------+------------------+
| NULL       | TABLE     | IX        | NULL             |
| email      | RECORD    | X,GAP     | 'min@ex.com', 20 |
+------------+-----------+-----------+------------------+
```

`X,GAP`에 `lock_data`가 `'min@ex.com', 20`이다. min 레코드 자체가 아니라 그 앞의 간격, 즉 ann과 min 사이를 잠갔다는 뜻이다. 처음 장면의 kim과 lee가 모두 이 간격에 들어간다.

유니크가 아닌 인덱스는 같은 값이 더 있을 수 있으니 뒤쪽 간격까지 잠근다.

```text
-- orders WHERE user_id = 20
+------------+-----------+---------------+-----------+
| index_name | lock_type | lock_mode     | lock_data |
+------------+-----------+---------------+-----------+
| NULL       | TABLE     | IX            | NULL      |
| idx_user   | RECORD    | X,GAP         | 30, 4     |
| idx_user   | RECORD    | X             | 20, 3     |
| PRIMARY    | RECORD    | X,REC_NOT_GAP | 3         |
+------------+-----------+---------------+-----------+
```

세 줄을 위에서부터 읽으면, `idx_user`의 (20, 3) 레코드와 그 앞 간격(넥스트 키, `X`), 다음 레코드 (30, 4) 앞의 간격(`X,GAP`), 그리고 클러스터드 인덱스의 행 3(`REC_NOT_GAP`)이다. 보조 인덱스 레코드에는 기본 키가 붙어 있어서 `lock_data`가 `20, 3`처럼 두 값으로 나온다. 이제 `user_id`가 10과 30 사이인 주문은 아무도 넣을 수 없다. 범위로 찾으면 끝까지 간다.

```text
-- users WHERE id > 15
+------------+-----------+-----------+------------------------+
| index_name | lock_type | lock_mode | lock_data              |
+------------+-----------+-----------+------------------------+
| NULL       | TABLE     | IX        | NULL                   |
| PRIMARY    | RECORD    | X         | supremum pseudo-record |
| PRIMARY    | RECORD    | X         | 20                     |
| PRIMARY    | RECORD    | X         | 30                     |
+------------+-----------+-----------+------------------------+
```

`supremum pseudo-record`는 페이지 끝의 가상 레코드다. 이걸 잠갔으니 30보다 큰 id는 모두 막힌다. 다음 회원 가입(id 40)도 이 트랜잭션이 끝날 때까지 기다린다.

인덱스가 없는 열로 찾으면 훑은 행을 전부 잠근다.

```text
-- orders WHERE status = 'ready' (status에 인덱스 없음)
+------------+-----------+-----------+------------------------+
| index_name | lock_type | lock_mode | lock_data              |
+------------+-----------+-----------+------------------------+
| NULL       | TABLE     | IX        | NULL                   |
| PRIMARY    | RECORD    | X         | supremum pseudo-record |
| PRIMARY    | RECORD    | X         | 1                      |
| PRIMARY    | RECORD    | X         | 2                      |
| PRIMARY    | RECORD    | X         | 3                      |
| PRIMARY    | RECORD    | X         | 4                      |
| PRIMARY    | RECORD    | X         | 5                      |
+------------+-----------+-----------+------------------------+
```

조건에 맞는 행은 3번과 5번 둘뿐인데 다섯 행과 그 사이 간격이 모두 잠겼다. 테이블 전체를 잠근 것과 같다. 운영 중인 테이블에서 인덱스 없는 `UPDATE ... WHERE`가 서비스를 멈추는 가장 흔한 경로다.

`READ COMMITTED`로 내리면 같은 두 쿼리의 잠금이 확 줄어든다.

없는 이메일 조회는 테이블의 `IX` 한 줄만 남고, 인덱스 없는 조회는 이렇게 된다.

```text
-- READ COMMITTED, WHERE status = 'ready'
+------------+-----------+---------------+-----------+
| index_name | lock_type | lock_mode     | lock_data |
+------------+-----------+---------------+-----------+
| NULL       | TABLE     | IX            | NULL      |
| PRIMARY    | RECORD    | X,REC_NOT_GAP | 3         |
| PRIMARY    | RECORD    | X,REC_NOT_GAP | 5         |
+------------+-----------+---------------+-----------+
```

`READ COMMITTED`에서는 간격을 잠그지 않는다(외래 키 검사와 중복 키 검사만 예외다). 조건에 안 맞는 행은 평가가 끝나면 잠금을 바로 놓는다. 없는 이메일을 조회하면 아무것도 잠기지 않는다. 그 대가로 팬텀이 생길 수 있고, binlog 형식은 `ROW`여야 한다. `STATEMENT` 형식과 `READ COMMITTED`를 함께 쓰면 InnoDB가 쓰기를 거부한다.

## 처음 장면을 잠금으로 다시 읽기

이제 처음의 교착 상태를 `SHOW ENGINE INNODB STATUS`의 `LATEST DETECTED DEADLOCK` 절로 읽을 수 있다. 실제 출력에서 줄을 조금 덜어 냈다.

```text
*** (1) TRANSACTION:
TRANSACTION 1323, ACTIVE 2 sec inserting
LOCK WAIT 3 lock struct(s), heap size 1128, 2 row lock(s), undo log entries 1
INSERT INTO users VALUES (40, 'kim@ex.com', 'Kim')

*** (1) HOLDS THE LOCK(S):
RECORD LOCKS space id 2 page no 5 n bits 72 index email of table `shop`.`users` trx id 1323 lock_mode X locks gap before rec
 0: len 10; hex 6d696e4065782e636f6d; asc min@ex.com;;

*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS space id 2 page no 5 n bits 72 index email of table `shop`.`users` trx id 1323 lock_mode X locks gap before rec insert intention waiting
 0: len 10; hex 6d696e4065782e636f6d; asc min@ex.com;;

*** (2) TRANSACTION:
TRANSACTION 1324, ACTIVE 1 sec inserting
INSERT INTO users VALUES (50, 'lee@ex.com', 'Lee')
(HOLDS와 WAITING은 trx id 1324로 (1)과 똑같은 두 줄이다)

*** WE ROLL BACK TRANSACTION (2)
```

읽는 순서는 이렇다. 두 트랜잭션 모두 `index email`의 `min@ex.com` 앞 간격(`locks gap before rec`)을 쥐고 있다. 그리고 둘 다 같은 간격에 `insert intention`(삽입 의도) 잠금을 기다린다. 간격 잠금끼리는 서로 막지 않아서 두 `SELECT ... FOR UPDATE`가 모두 통과했지만, 삽입 의도 잠금은 남이 쥔 간격 잠금과 충돌한다. 서로가 서로의 간격 잠금을 기다리니 원이 생겼다.

InnoDB는 잠금을 기다리기 시작할 때마다 대기 그래프를 검사해서(`innodb_deadlock_detect=ON`) 원을 찾으면 바로 한쪽을 롤백한다. 고른 기준은 고친 행과 잠금이 더 적은, 되돌리기 싼 쪽이다. 롤백된 쪽은 트랜잭션 전체가 사라지니 앱이 처음부터 다시 해야 한다.

고치는 방법은 여러 가지다. 이 경우 가장 깔끔한 건 잠금으로 확인하는 단계를 없애는 것이다. `email`에 유니크 제약이 이미 있으니 그냥 `INSERT`하고, 중복 에러(`ERROR 1062 (23000): Duplicate entry`)를 "이미 가입됨"으로 처리한다. 덮어써도 되는 데이터라면 `INSERT ... ON DUPLICATE KEY UPDATE`를 쓴다. 이 방식에서도 중복 키 검사 때 잠금이 잠깐 걸리지만, 확인과 삽입 사이의 틈이 없어 교착 가능성이 크게 준다. 서비스 전체가 간격 잠금 때문에 자주 부딪힌다면 격리 수준을 `READ COMMITTED`로 내리는 선택지도 있다. 다만 팬텀을 허용하는 대가를 코드가 감당하는지 먼저 따진다.

어떤 방법을 쓰든 교착 상태를 0으로 만들 수는 없다. `ERROR 1213`(SQLSTATE `40001`)은 트랜잭션 전체를 짧게 재시도하는 대상에 넣는다. 다른 DB와 공통인 교착 상태 이론과 잠금 순서 맞추기는 [재고 -1 막기](/posts/db-locking-deadlock)와 [데드락](/posts/deadlocks)에 있다.

## 잠금 대기를 현장에서 좁혀 가는 순서

"API가 50초 뒤에 `Lock wait timeout exceeded`를 낸다"는 신고가 들어오면 이렇게 좁힌다. 먼저 지금 누가 누구를 막고 있는지 본다. `sys` 스키마의 뷰가 `data_locks`와 `data_lock_waits`를 묶어서 보여 준다. 아래는 A가 `user_id = 20`을 `FOR UPDATE`로 잡은 채 쉬고 있고, B가 `user_id = 25` 주문을 넣으려다 막힌 장면이다.

```sql
SELECT waiting_pid, waiting_query, waiting_lock_mode,
       blocking_pid, blocking_query, blocking_lock_mode,
       wait_age, sql_kill_blocking_query
FROM sys.innodb_lock_waits\G
```

```text
*************************** 1. row ***************************
            waiting_pid: 30
          waiting_query: INSERT INTO orders (user_id, a ... us) VALUES (25, 9000, 'ready')
      waiting_lock_mode: X,GAP,INSERT_INTENTION
           blocking_pid: 29
         blocking_query: NULL
     blocking_lock_mode: X,GAP
               wait_age: 00:00:01
sql_kill_blocking_query: KILL QUERY 29
```

25는 20과 30 사이니 A가 잠근 (20, 30) 간격에 들어간다. `blocking_query`가 `NULL`이라는 데 주목한다. 막고 있는 쪽은 아무 쿼리도 돌리지 않는다. 트랜잭션을 열어 둔 채 앱 코드가 외부 API를 부르거나, 예외가 나서 커밋도 롤백도 안 한 채 연결이 풀에 돌아간 경우가 대부분이다. 이때 제안된 `KILL QUERY 29`는 실행 중인 문장이 없으니 아무 효과가 없다. 연결을 끊는 `KILL 29`(뷰의 `sql_kill_blocking_connection` 열)를 써야 트랜잭션이 롤백되고 잠금이 풀린다.

기다리던 B는 `innodb_lock_wait_timeout`(기본 50초, 이 실험에서는 세션에서 5초로 낮췄다)이 지나면 이렇게 끝난다.

```text
INSERT INTO orders (user_id, amount, status) VALUES (25, 9000, 'ready')
ERROR 1205 (HY000) at line 1: Lock wait timeout exceeded; try restarting transaction
```

InnoDB는 기본 설정(`innodb_rollback_on_timeout=OFF`)에서 이때 그 문장만 되돌리고 트랜잭션은 열어 둔다. 앱이 에러를 무시하고 커밋하면 앞부분만 반영된다. 사용자 요청을 처리하는 연결은 `SET SESSION innodb_lock_wait_timeout = 5`처럼 짧게 걸고, 에러가 나면 반드시 `ROLLBACK`한다.

정리하면 이 순서다.

1. `sys.innodb_lock_waits`로 막는 쪽 pid와 잠금 모드를 본다. `X,GAP`이면 간격 잠금, `REC_NOT_GAP`이면 같은 행 경합이다.
2. 막는 쪽이 `NULL` 쿼리면 `information_schema.innodb_trx`에서 `trx_started`를 보고 얼마나 오래 열려 있었는지 확인한다. 몇 분 넘게 열린 트랜잭션이면 앱의 트랜잭션 경계를 의심한다.
3. 막는 쿼리가 있다면 `EXPLAIN`으로 인덱스를 타는지 본다. 인덱스 없는 잠금 읽기는 위에서 본 것처럼 테이블 전체를 잠근다.
4. 교착 상태가 반복되면 `SET GLOBAL innodb_print_all_deadlocks = ON`으로 모든 교착 상태를 에러 로그에 남긴다. `SHOW ENGINE INNODB STATUS`는 마지막 하나만 보여 준다.

`FOR UPDATE`, `NOWAIT`, `SKIP LOCKED` 같은 잠금 문법 자체는 PostgreSQL과 거의 같으니 [비관적 잠금](/posts/pessimistic-locking)을 참고한다.

## PostgreSQL과 나란히 놓고 보기

여기까지 본 차이를 한 표에 모은다. 같은 SQL을 써도 운영에서 부딪히는 문제가 달라지는 지점들이다.

| | MySQL 8 InnoDB | PostgreSQL 16 |
|---|---|---|
| 연결 | 연결마다 스레드 | 연결마다 프로세스 |
| 테이블 저장 | 기본 키 순 B-tree (클러스터드) | 순서 없는 힙 + 인덱스가 위치(ctid)를 가리킴 |
| 페이지 | 16KB | 8KB |
| 캐시 | 버퍼 풀을 크게 (램의 절반 이상) | shared_buffers는 작게 + OS 페이지 캐시 |
| 옛 버전 | undo 로그에 두고 되감아 읽음, purge가 치움 | 테이블 안에 새 튜플로 남김, VACUUM이 치움 |
| 부분 쓰기 대비 | doublewrite 파일 | WAL에 페이지 통째 기록 (full page writes) |
| 복제용 로그 | binlog (redo와 별도, 2단계 커밋) | WAL 그대로 |
| 기본 격리 수준 | REPEATABLE READ | READ COMMITTED |
| 간격 잠금 | 있음 (RR에서) | 없음 |
| RR에서 동시 수정 | 최신 값으로 진행 | 직렬화 오류로 실패 |

어느 쪽이 낫다기보다 무엇이 싸고 무엇이 비싼지가 다르다. InnoDB는 기본 키 조회와 기본 키 범위가 아주 싸고, 고치는 일이 제자리에서 일어나 테이블이 덜 부푼다. 대신 보조 인덱스 조회가 한 번 더 내려가고, 무작위 기본 키에 약하며, 간격 잠금 때문에 PostgreSQL에서는 없던 교착 상태를 만난다. 같은 앱을 옮길 때는 이 표의 아래쪽 세 줄부터 확인한다.

## InnoDB는 기본 키 B-tree와 undo로 움직인다

처음 질문으로 돌아가면, 다른 이메일 두 개가 서로를 기다린 건 둘 다 "없는 행"을 잠갔기 때문이다. `REPEATABLE READ`의 InnoDB는 없는 행을 인덱스 위의 간격으로 잠그고, 간격 잠금은 함께 쥘 수 있지만 그 간격에 넣으려는 삽입과는 부딪힌다. 이 동작은 테이블이 기본 키 B-tree이고, 잠금이 인덱스 레코드와 간격에 걸리며, 일반 읽기는 undo로 옛 버전을 되감는 구조에서 나온다. 이 구조가 레플리카로 어떻게 전달되고, 큰 테이블의 구조를 바꿀 때 무엇이 막히는지는 [MySQL 복제와 온라인 DDL](/posts/mysql-replication-online-ddl)에서 이어서 본다.

## 면접에서 나올 만한 질문

### InnoDB의 클러스터드 인덱스는 무엇이고, 보조 인덱스 조회는 왜 느릴 수 있나

InnoDB 테이블은 기본 키로 정렬된 B-tree 하나이고 잎에 행 전체가 들어 있다. 보조 인덱스의 잎에는 기본 키 값이 들어 있어서, 보조 인덱스로 찾은 뒤 기본 키로 한 번 더 내려가야 행을 얻는다. 찾은 행이 흩어져 있으면 행마다 다른 페이지를 읽는다. 필요한 열이 모두 보조 인덱스에 있으면 커버링이 되어 두 번째 탐색이 사라지고, 기본 키는 모든 보조 인덱스에 공짜로 들어 있다.

### 버퍼 풀에서 대량 스캔이 자주 쓰는 페이지를 밀어내지 않는 이유는

LRU를 young과 old 두 구역으로 나누고, 새로 읽은 페이지를 old 구역 머리에 넣기 때문이다. old에 들어온 뒤 `innodb_old_blocks_time`(기본 1초)이 지나서 다시 읽혀야 young으로 올라간다. 스캔은 한 페이지를 짧은 시간에 몰아서 읽고 떠나니 old에서 빠져나간다. 이 값을 0으로 두면 스캔이 young을 채워 핫 페이지를 내보내는 것을 직접 확인할 수 있다.

### redo, undo, binlog는 각각 무엇을 위한 로그인가

redo는 페이지를 어떻게 바꿨는지 적은 물리 로그로, 커밋된 변경을 크래시 뒤에 되살린다. undo는 바꾸기 전 값으로, 롤백과 MVCC의 옛 버전 읽기에 쓴다. binlog는 서버 층의 논리적 변경 기록으로 복제와 시점 복구에 쓴다. redo와 binlog가 어긋나지 않게 커밋은 redo prepare, binlog 쓰기, redo commit의 2단계로 진행된다.

### InnoDB의 MVCC는 PostgreSQL과 어떻게 다른가

InnoDB는 행을 제자리에서 고치고 옛 값을 undo에 둔다. 일반 `SELECT`는 read view와 행의 `DB_TRX_ID`를 비교해서 안 보이면 `DB_ROLL_PTR`을 따라 undo를 되감는다. PostgreSQL은 고칠 때마다 새 튜플을 테이블에 쓰고 옛 튜플은 VACUUM이 치운다. 그래서 오래 열린 트랜잭션이 InnoDB에서는 History list length 증가와 느린 일관된 읽기로, PostgreSQL에서는 테이블 부풀림으로 나타난다.

### REPEATABLE READ인데 같은 트랜잭션에서 SELECT와 UPDATE의 결과가 달라지는 이유는

일반 `SELECT`는 첫 읽기 때 만든 스냅숏을 보지만 `UPDATE`, `DELETE`, `FOR UPDATE`는 최신 커밋 값을 읽고 잠그기 때문이다. 스냅숏 이후 다른 트랜잭션이 넣은 행도 `UPDATE` 대상이 되고, 고친 뒤에는 자기 변경이라 `SELECT`에 보인다. 판단에 쓸 값은 잠금 읽기로 읽거나 `UPDATE`의 영향받은 행 수를 써야 한다. PostgreSQL의 RR은 이 상황에서 직렬화 오류를 낸다.

### 갭 잠금과 넥스트 키 잠금은 언제 생기고, 왜 교착 상태를 만드나

`REPEATABLE READ`에서 잠금 읽기가 인덱스를 범위로 훑거나, 유니크하지 않은 인덱스로 찾거나, 없는 값을 찾을 때 생긴다. 다른 트랜잭션이 그 간격에 행을 넣지 못하게 해서 팬텀을 막는다. 간격 잠금끼리는 충돌하지 않아 둘이 같은 간격을 쥘 수 있는데, 각자 그 간격에 `INSERT`하려 하면 삽입 의도 잠금이 서로의 간격 잠금을 기다려 교착 상태가 된다. "확인 후 삽입" 대신 유니크 제약과 중복 에러 처리를 쓰거나, `READ COMMITTED`로 내려 간격 잠금을 끄는 방법이 있다.

### 잠금 대기 시간 초과가 나는데 막는 쪽 쿼리가 NULL이다. 무엇을 의심하나

막는 트랜잭션이 아무 문장도 실행하지 않은 채 열려 있는, 앱 쪽 트랜잭션 누수를 의심한다. `information_schema.innodb_trx`의 `trx_started`로 얼마나 오래 열렸는지 보고, 급하면 `KILL QUERY`가 아니라 연결을 끊는 `KILL <pid>`로 롤백시킨다. 근본적으로는 트랜잭션 안에서 외부 호출을 하지 않는지, 예외 경로에서 롤백하는지 코드를 고친다. 또 `ERROR 1205`가 기본 설정에서 문장만 롤백한다는 점을 알고 앱에서 직접 `ROLLBACK`해야 한다.
