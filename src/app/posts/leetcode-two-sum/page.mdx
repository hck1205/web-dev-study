LeetCode를 처음 열면 1번에 [Two Sum](https://leetcode.com/problems/two-sum/)이 있다. 쉬운 문제로 분류돼 있지만 면접에서는 이 문제 하나로 꽤 오래 이야기한다. 이중 반복문으로 풀면 "더 빠르게는요?", 해시맵으로 풀면 "정렬돼 있으면요?", "메모리가 부족하면요?", "답을 전부 찾으라면요?"가 이어진다. 그래서 이 글은 답 하나를 외우는 대신 풀이 다섯 개를 느린 것부터 차례로 놓고, 각각이 왜 그다음 풀이로 넘어가게 만드는지 따라간다.

해시맵이 왜 평균 O(1)에 찾는지는 [해시맵 글](/posts/ds-hash-map)에서, O(n²)와 O(n)의 차이가 실제로 얼마나 큰지는 [Big O 글](/posts/big-o-notation)에서 다뤘다. 문제 풀이 전체의 흐름은 [LeetCode 공부 가이드](/posts/leetcode-study-guide)에 있다. 코드는 모두 Node.js 22, Python 3, Java 21에서 직접 돌린 결과다.

## 문제를 내 말로 다시 쓰면

정수 배열 `nums`와 정수 `target`이 주어진다. 배열에서 서로 다른 두 칸을 골라 그 값을 더했을 때 `target`이 되는 두 칸의 인덱스를 돌려준다. 문제는 이런 약속을 함께 준다.

- 답은 정확히 하나만 있다. 답이 없는 입력은 들어오지 않는다.
- 같은 칸을 두 번 쓸 수 없다. 값이 같은 서로 다른 두 칸은 써도 된다.
- 인덱스 두 개의 순서는 상관없다.
- 배열 길이는 2 이상 10^4 이하, 값과 `target`은 -10^9 이상 10^9 이하다.

길이 상한이 10^4이라서 O(n²) 풀이도 1억 번 안쪽의 연산이라 통과는 한다. 그래서 문제 끝에 "O(n²)보다 빠른 풀이를 생각해 볼 수 있나"라는 꼬리가 붙어 있다. 면접에서도 브루트포스로 끝내면 거기서 대화가 멈추지 않는다.

값이 음수일 수 있다는 점도 중요하다. 음수가 있으면 "합이 이미 target을 넘었으니 더 볼 필요 없다" 같은 가지치기를 쓸 수 없다. 큰 수 뒤에 음수가 와서 합을 다시 끌어내릴 수 있기 때문이다.

## 손으로 먼저 찾아 보기

예시를 하나 정해 두고 글 끝까지 쓴다.

```text
인덱스   0   1   2   3   4
nums     5   2   8  11   4      target = 12
```

사람이 이 배열을 보면 무엇을 할까. 아마 5를 보고 "7이 있나?"를 찾고, 없으니 2를 보고 "10이 있나?"를 찾을 것이다. 8을 볼 때 "4가 있나?"를 찾으면 맨 끝에 4가 있다. 답은 인덱스 2와 4다.

여기서 이미 두 가지 방식이 섞여 있다. 하나는 "지금 수와 나머지 수를 하나씩 더해 본다"이고, 다른 하나는 "지금 수에 필요한 짝이 무엇인지 계산하고 그 짝을 찾는다"다. 짝을 계산하는 말을 이 글에서는 보수라고 부른다. 지금 값이 `x`면 보수는 `target - x`다. 5의 보수는 7, 8의 보수는 4다.

두 번째 방식으로 바꾸는 순간 문제가 "두 수를 고르는 문제"에서 "어떤 값이 배열에 있는지 찾는 문제"로 바뀐다. 아래 풀이들은 결국 이 찾기를 얼마나 빨리 하느냐의 차이다.

## 모든 쌍을 다 대 보는 풀이

가장 먼저 떠오르는 방법이다. 첫 칸 `i`를 고르고, 그 뒤의 칸 `j`를 하나씩 대 보며 합을 확인한다.

```js
function twoSum(nums, target) {
  for (let i = 0; i < nums.length; i++) {
    // j는 i 다음부터 시작한다. 같은 칸을 두 번 쓰지 않고, 이미 본 쌍을 다시 보지 않는다.
    for (let j = i + 1; j < nums.length; j++) {
      if (nums[i] + nums[j] === target) return [i, j];
    }
  }
  return []; // 문제는 답이 항상 있다고 했지만, 함수가 끝까지 값을 돌려주게 둔다
}

console.log(twoSum([5, 2, 8, 11, 4], 12));
```

```text
[ 2, 4 ]
```

`j`를 `i + 1`부터 시작하는 이유가 두 개다. `j = i`부터 시작하면 같은 칸을 두 번 쓰게 되고, `j = 0`부터 시작하면 (0, 2)와 (2, 0)처럼 같은 쌍을 두 번 본다. 앞의 것은 오답을 만들고 뒤의 것은 시간만 버린다.

시간 복잡도는 O(n²)다. 쌍의 개수가 n(n-1)/2이고, 최악의 경우(답이 맨 끝 두 칸) 그 쌍을 거의 다 본다. n이 10^4이면 약 5천만 번이다. 공간은 변수 몇 개라 O(1)이다.

이 풀이가 느린 이유를 정확히 짚어 두면 다음 풀이가 자연스럽게 나온다. 안쪽 반복문이 하는 일은 "nums[i]의 보수가 i 뒤에 있나"를 찾는 것인데, 그 찾기를 매번 처음부터 한 칸씩 훑는다. 이미 한 번 본 값들을 다시 보고 또 본다. 찾기를 빠르게 만들면 된다. 빠르게 찾는 방법은 크게 두 갈래다. 정렬해 두고 찾거나, 해시맵에 넣어 두고 찾거나.

## 정렬해 놓고 양 끝에서 좁히기

배열이 정렬돼 있다면 양 끝에 손가락을 하나씩 두고 합을 본다. 합이 target보다 작으면 합을 키워야 하니 왼쪽 손가락을 오른쪽으로 옮기고, 크면 오른쪽 손가락을 왼쪽으로 옮긴다. 이것이 [투 포인터](/posts/two-pointers-pattern)다.

문제는 이 문제가 정렬된 배열을 주지 않고, 원래 인덱스를 돌려 달라고 한다는 점이다. 값만 정렬하면 원래 자리를 잃는다. 그래서 값이 아니라 인덱스 배열을 정렬한다. `[0, 1, 2, 3, 4]`를 "그 인덱스가 가리키는 값" 기준으로 정렬하면 `[1, 4, 0, 2, 3]`이 된다(값 2, 4, 5, 8, 11 순서).

```js
function twoSum(nums, target) {
  // 원래 인덱스를 값 기준으로 정렬한다. 값만 정렬하면 원래 자리를 잃는다.
  const idx = nums.map((_, i) => i);
  idx.sort((a, b) => nums[a] - nums[b]);

  let lo = 0, hi = idx.length - 1;
  while (lo < hi) {
    const sum = nums[idx[lo]] + nums[idx[hi]];
    if (sum === target) return [idx[lo], idx[hi]];
    if (sum < target) lo++; // 합을 키워야 한다 → 작은 쪽을 버린다
    else hi--;              // 합을 줄여야 한다 → 큰 쪽을 버린다
  }
  return [];
}

console.log(twoSum([5, 2, 8, 11, 4], 12));
```

```text
[ 4, 2 ]
```

인덱스 순서가 `[4, 2]`로 나왔는데, 문제는 순서를 상관하지 않는다. 아래 그림은 정렬된 순서로 놓은 값 위에서 두 손가락이 움직이는 모습이다. 칸 아래에 원래 인덱스를 함께 적었다.

왜 한쪽 손가락을 옮겨도 답을 놓치지 않을까. 합이 13으로 target보다 크다고 하자. 오른쪽 끝의 11은 지금 왼쪽 끝인 2, 즉 남은 값 중 가장 작은 값과 더해도 이미 크다. 그러면 11은 누구와 더해도 크다. 11이 들어간 쌍은 전부 답이 될 수 없으니 통째로 버려도 된다. 합이 작을 때도 같은 논리로 왼쪽 끝이 버려진다. 매 걸음 후보 하나를 확실히 지우니 최대 n-1걸음에 끝난다.

시간은 정렬 O(n log n) + 훑기 O(n)이라 O(n log n)이다. 공간은 인덱스 배열 때문에 O(n)이다. 값만 필요했다면 제자리 정렬로 O(1) 추가 공간에 할 수 있었지만, 이 문제는 인덱스가 필요해서 그렇게 못 한다.

JavaScript의 `sort`에 비교 함수를 빼먹으면 값이 문자열로 바뀌어 정렬된다. `[10, 9, 1, 2].sort()`는 `[1, 10, 2, 9]`가 된다. 정렬을 쓰는 풀이에서 가장 흔하게 틀리는 지점이라 `(a, b) => a - b` 모양을 꼭 붙인다. 정렬 자체의 동작은 [정렬 알고리즘 글](/posts/sorting-algorithms)에 있다.

이 풀이의 한계는 정렬 비용이다. 해시맵 풀이가 O(n)인데 굳이 O(n log n)을 쓸 이유는 입력이 이미 정렬돼 있을 때뿐이다. 그 경우는 [Two Sum II](/posts/leetcode-two-sum-ii)가 정확히 그 문제고, 거기서는 정렬 단계가 사라져 O(n) 시간, O(1) 공간이 된다.

## 정렬한 뒤 짝을 이분 탐색으로 찾기

정렬한 배열에서 "보수가 있나"를 찾는 방법이 투 포인터만 있는 건 아니다. 각 값마다 보수를 [이분 탐색](/posts/binary-search)으로 찾아도 된다.

```js
function twoSum(nums, target) {
  const idx = nums.map((_, i) => i).sort((a, b) => nums[a] - nums[b]);

  for (let i = 0; i < idx.length; i++) {
    const need = target - nums[idx[i]];
    // i 뒤쪽 [i+1, n)에서 need 이상이 처음 나오는 자리를 찾는다 (lower bound)
    let lo = i + 1, hi = idx.length;
    while (lo < hi) {
      const mid = (lo + hi) >>> 1;
      if (nums[idx[mid]] < need) lo = mid + 1;
      else hi = mid;
    }
    if (lo < idx.length && nums[idx[lo]] === need) return [idx[i], idx[lo]];
  }
  return [];
}

console.log(twoSum([5, 2, 8, 11, 4], 12));
console.log(twoSum([3, 3], 6));
```

```text
[ 4, 2 ]
[ 0, 1 ]
```

탐색 범위를 `i + 1`부터 잡는 게 중요하다. 0부터 잡으면 `[3, 3]`처럼 값이 같을 때 자기 자신을 찾아 버릴 수 있다. 뒤쪽만 보면 자기 자신은 범위에 없고, 같은 값의 다른 칸은 정렬 후 바로 옆에 있으니 찾힌다.

시간은 정렬 O(n log n) + 값마다 이분 탐색 O(log n) × n = O(n log n)이다. 투 포인터와 같은 등급인데 상수가 더 크다. 그럼에도 이 풀이를 알아 둘 이유가 있다. "한쪽 배열은 고정돼 있고, 다른 쪽에서 값이 하나씩 들어온다"처럼 두 손가락을 함께 움직일 수 없는 상황에서는 이분 탐색이 남는 길이다. 예를 들어 큰 정렬 배열 하나에 질문 값이 하나씩 들어온다면 질문마다 O(log n)에 답할 수 있다.

## 짝을 기억해 두는 장부: 해시맵 두 번 훑기

정렬은 "빨리 찾기"를 위해 순서를 만든다. 순서가 아니라 "값으로 바로 찾기"가 목적이라면 해시맵이 더 직접적이다. 값을 키로, 인덱스를 값으로 담아 두면 "보수가 있나, 있으면 어느 칸인가"를 평균 O(1)에 답한다. 이 글에서는 이 해시맵을 장부라고 부른다.

먼저 쉬운 버전. 한 번 훑어 장부를 다 채우고, 두 번째로 훑으며 각 값의 보수를 장부에 묻는다.

```js
function twoSum(nums, target) {
  // 1) 값 → 인덱스 장부를 만든다. 같은 값이 여러 번 나오면 마지막 인덱스가 남는다.
  const pos = new Map();
  for (let i = 0; i < nums.length; i++) pos.set(nums[i], i);

  // 2) 각 값의 보수를 장부에 묻는다.
  for (let i = 0; i < nums.length; i++) {
    const j = pos.get(target - nums[i]);
    if (j !== undefined && j !== i) return [i, j]; // 자기 자신이면 안 된다
  }
  return [];
}

console.log(twoSum([5, 2, 8, 11, 4], 12));
console.log(twoSum([3, 2, 4], 6));
console.log(twoSum([3, 3], 6));
```

```text
[ 2, 4 ]
[ 1, 2 ]
[ 0, 1 ]
```

`j !== i` 확인이 이 풀이의 급소다. `[3, 2, 4]`, target 6에서 3의 보수는 3이고, 장부에는 3 → 0이 있다. 확인을 빼면 `[0, 0]`을 돌려준다. 같은 칸을 두 번 쓴 오답이다.

그럼 `[3, 3]`은 왜 맞을까. 장부를 채울 때 3 → 0을 넣었다가 3 → 1로 덮어쓴다. 두 번째 훑기에서 i = 0의 보수 3을 물으면 1이 나오고, 0과 다르니 `[0, 1]`이다. 덮어쓰기가 오히려 같은 값 두 개를 구해 준다. 같은 값이 세 번 이상 나와도 답이 하나뿐이라는 약속 덕분에 이 경우는 생기지 않는다(같은 값 세 개가 짝이 되면 답이 여러 개다).

시간은 두 번 훑으니 O(2n) = O(n), 공간은 장부 O(n)이다. 브루트포스와 비교하면 n이 5배 늘 때 시간이 25배가 아니라 5배 정도만 는다. 실측 숫자는 [해시맵 글의 두 수의 합 절](/posts/ds-hash-map#두-수의-합)에 있다.

한계는 크지 않다. 다만 장부를 먼저 다 채우고 나서 찾으니, 답이 앞쪽에 있어도 끝까지 한 번은 다 훑는다. 그리고 `j !== i` 같은 예외 처리가 필요하다. 이 둘을 한꺼번에 없애는 방법이 있다.

## 한 번만 훑어도 된다

장부를 미리 채우지 않고, 훑으면서 채운다. 각 칸에서 할 일은 두 가지이고, 순서가 정해져 있다.

1. 지금 값의 보수가 장부에 있나 묻는다. 있으면 답이다.
2. 없으면 지금 값과 인덱스를 장부에 적는다.

장부에는 항상 "지금 칸보다 앞에 있는 칸들"만 들어 있다. 그래서 자기 자신을 찾을 일이 없다. 답이 (2, 4)라면 2번 칸을 볼 때는 4가 아직 장부에 없지만, 4번 칸을 볼 때 보수 8이 장부에 있다. 쌍의 두 칸 중 뒤에 있는 칸에서 반드시 찾힌다.

```js
function twoSum(nums, target) {
  const seen = new Map(); // 값 → 인덱스. 지금 칸보다 앞의 칸만 들어 있다.
  for (let i = 0; i < nums.length; i++) {
    const need = target - nums[i]; // 지금 값의 짝(보수)
    if (seen.has(need)) return [seen.get(need), i]; // 1) 먼저 묻고
    seen.set(nums[i], i);                           // 2) 그다음 적는다
  }
  return [];
}

console.log(twoSum([5, 2, 8, 11, 4], 12));
```


두 번 훑기와 비교해 점근적으로는 같다. 차이는 답이 앞쪽에 있으면 일찍 끝난다는 것, 자기 자신 확인이 구조적으로 필요 없다는 것, 그리고 배열이 아니라 값이 하나씩 들어오는 흐름(스트림)에도 그대로 쓸 수 있다는 것이다. 뒤의 "변형" 절에서 이 마지막 성질을 다시 쓴다.

"먼저 묻고 그다음 적는다"의 순서를 바꾸면 어떻게 될까. 적고 나서 물으면 `[3, 2, 4]`, target 6에서 3을 적은 직후 보수 3을 물어 자기 자신을 찾는다.

```js
// 틀린 순서: 적고 나서 묻는다
function twoSumWrongOrder(nums, target) {
  const seen = new Map();
  for (let i = 0; i < nums.length; i++) {
    seen.set(nums[i], i);
    const need = target - nums[i];
    if (seen.has(need)) return [seen.get(need), i];
  }
  return [];
}
console.log(twoSumWrongOrder([3, 2, 4], 6));
```

## Python과 Java로 옮길 때

한 번 훑기 풀이를 코딩 테스트에서 많이 쓰는 두 언어로 옮겼다. 구조는 같고, 언어마다 신경 쓸 곳이 조금 다르다.

```python
from typing import List

class Solution:
    def twoSum(self, nums: List[int], target: int) -> List[int]:
        seen = {}  # 값 -> 인덱스
        for i, x in enumerate(nums):
            need = target - x
            if need in seen:          # dict의 in은 평균 O(1)
                return [seen[need], i]
            seen[x] = i
        return []

s = Solution()
print(s.twoSum([5, 2, 8, 11, 4], 12), s.twoSum([3, 2, 4], 6), s.twoSum([3, 3], 6))
```

```text
[2, 4] [1, 2] [0, 1]
```

Python에서는 `dict`가 해시맵이다. `enumerate`로 인덱스와 값을 함께 받으면 깔끔하다. `if seen.get(need):`처럼 쓰면 인덱스 0이 거짓으로 취급돼 놓친다. 이 실수는 JavaScript에서도 똑같이 나오니 아래 "틀리기 쉬운 입력" 절에서 다시 본다. Python 정수는 크기 제한이 없어서 오버플로 걱정이 없다.

```java
import java.util.*;

class Solution {
    public int[] twoSum(int[] nums, int target) {
        Map<Integer, Integer> seen = new HashMap<>(); // 값 -> 인덱스
        for (int i = 0; i < nums.length; i++) {
            int need = target - nums[i];
            Integer j = seen.get(need);    // 없으면 null
            if (j != null) return new int[] { j, i };
            seen.put(nums[i], i);
        }
        return new int[0];
    }

    public static void main(String[] args) {
        Solution s = new Solution();
        System.out.println(Arrays.toString(s.twoSum(new int[] { 5, 2, 8, 11, 4 }, 12)));
        System.out.println(Arrays.toString(s.twoSum(new int[] { 3, 2, 4 }, 6)));
        System.out.println(Arrays.toString(s.twoSum(new int[] { 3, 3 }, 6)));
    }
}
```

```text
[2, 4]
[1, 2]
[0, 1]
```

Java에서 짚을 곳은 세 군데다.

`HashMap`은 `int` 같은 기본형을 담지 못하고 `Integer` 객체로 감싼다(박싱). `containsKey`와 `get`을 따로 부르면 해시를 두 번 계산하니, `get` 한 번으로 받아 `null`인지 보는 쪽이 낫다.

`Integer`끼리 `==`로 비교하면 안 된다. `==`는 객체가 같은지를 보는데, Java는 -128부터 127까지의 `Integer`만 미리 만들어 재사용한다. 그래서 `Integer a = 100, b = 100;`의 `a == b`는 `true`인데 `Integer a = 1000, b = 1000;`의 `a == b`는 `false`다. 실제로 돌려 보면 그렇게 나온다. 장부에서 꺼낸 값을 비교할 일이 생기면 `equals`나 `intValue()`를 쓴다.

정수 범위도 한 번 따져 본다. 값과 target이 -10^9 이상 10^9 이하라서 `target - nums[i]`는 -2×10^9 이상 2×10^9 이하다. `int`의 범위는 약 ±2.147×10^9라 아슬아슬하게 들어간다. 제약이 조금만 넓었어도 `long`이 필요했을 것이다. 비슷한 문제에서 세 수, 네 수를 더하면 바로 넘친다. [3Sum](/posts/leetcode-3sum) 계열 문제에서 Java로 풀 때 이 점을 다시 본다.

## 틀리기 쉬운 입력들

예시 하나로 맞게 나와도 아래 입력에서 틀리는 코드가 많다. 직접 만든 테스트를 몇 개 넣어 보는 습관이 여기서 차이를 만든다.

### 보수가 자기 자신인 경우

`[3, 2, 4]`, target 6. 3의 보수가 3이다. 두 번 훑기에서 `j !== i`를 빼거나, 한 번 훑기에서 적고 나서 물으면 `[0, 0]`이 나온다. 위에서 둘 다 실제로 확인했다.

### 값이 같은 두 칸이 답인 경우

`[3, 3]`, target 6. 이번에는 같은 값 두 칸이 진짜 답이다. "같은 값이면 건너뛴다"처럼 앞의 실수를 과하게 막으면 여기서 답을 못 찾는다. 막아야 하는 건 같은 값이 아니라 같은 인덱스다.

### 인덱스 0을 거짓으로 읽는 경우

JavaScript 객체나 Python `dict`를 쓰면서 존재 여부를 값의 참거짓으로 확인하면 인덱스 0이 사라진다.

```js
function twoSumFalsy(nums, target) {
  const seen = {};
  for (let i = 0; i < nums.length; i++) {
    const need = target - nums[i];
    if (seen[need]) return [seen[need], i]; // 0번 칸이면 seen[need]가 0이라 거짓
    seen[nums[i]] = i;
  }
  return [];
}
console.log(twoSumFalsy([3, 5, 1], 8)); // 답은 [0, 1]
```

```text
[]
```

3이 0번 칸에 있어서 `seen[3]`이 0이고, `if (0)`은 거짓이다. `Map.has`, `in`, `!== undefined`처럼 "있느냐"를 직접 묻는 방법을 쓴다. 객체를 키 저장소로 쓸 때의 다른 함정(프로토타입 키, 숫자 키가 문자열로 바뀜)은 [해시맵 글](/posts/ds-hash-map)에 정리돼 있다.

### 음수와 0

`[-4, 7, 0, -1, 4]`, target 0이면 답은 `[0, 4]`다. `[0, 5, 0]`, target 0이면 `[0, 2]`다. 해시맵 풀이는 부호를 신경 쓰지 않으니 그대로 맞는다. 문제는 "정렬하고 합이 target을 넘으면 멈춘다" 같은 조기 종료를 섞을 때다. 음수가 있으면 합은 다시 줄 수 있다.

### 값만 정렬해서 인덱스를 잃는 경우

투 포인터를 쓰려고 `[...nums].sort((a, b) => a - b)`만 하면, 돌려주는 인덱스가 정렬된 배열의 인덱스가 된다. 예시 배열에서 답 대신 `[1, 3]`(정렬 후 4와 8의 자리)이 나온다. 인덱스 배열을 정렬하거나 `[값, 원래 인덱스]` 쌍을 정렬한다.

## 면접관이 이어서 묻는 변형

### 배열이 정렬돼 있다면

정렬 단계가 사라지니 양 끝 투 포인터로 O(n) 시간, O(1) 공간에 푼다. 해시맵보다 메모리를 덜 쓰고 상수도 작다. 이것이 [Two Sum II](/posts/leetcode-two-sum-ii)이고, 그 글에서 왜 놓치는 쌍이 없는지 더 자세히 증명한다.

### 답을 하나가 아니라 전부 구하라면

"합이 target인 모든 쌍"을 구하라면 무엇을 돌려줄지부터 정해야 한다. 인덱스 쌍 전부라면 같은 값이 여러 번 나올 때 쌍 수가 O(n²)까지 늘 수 있어서(예: 전부 3이고 target 6), 출력 크기 때문에 O(n²)보다 빠를 수 없다. 값 쌍을 중복 없이 구하라면 정렬 후 투 포인터를 돌리며 같은 값을 건너뛰는 게 깔끔하다. 이 "중복 건너뛰기"가 [3Sum](/posts/leetcode-3sum)의 핵심 기술이다.

### 쌍의 개수만 세라면

한 번 훑기를 조금 바꾸면 된다. 장부에 인덱스 대신 "그 값이 지금까지 몇 번 나왔나"를 적고, 각 칸에서 보수의 개수를 답에 더한다.

```js
function countPairs(nums, target) {
  const count = new Map(); // 값 → 지금까지 나온 횟수
  let pairs = 0;
  for (const x of nums) {
    pairs += count.get(target - x) ?? 0; // 앞에 있는 보수 하나하나가 쌍이 된다
    count.set(x, (count.get(x) ?? 0) + 1);
  }
  return pairs;
}
console.log(countPairs([1, 5, 3, 3, 3], 6)); // (1,5) 하나, 3끼리 3쌍
```

```text
4
```

3이 세 개면 3끼리 쌍은 3개(첫째-둘째, 첫째-셋째, 둘째-셋째)다. 세 번째 3을 볼 때 앞의 3 두 개가 각각 쌍이 되니 2를 더하고, 두 번째 3에서 1을 더해 합이 3이다. 여기에 (1, 5)를 더해 4다.

### 값이 하나씩 흘러 들어온다면

"`add(x)`로 수가 들어오고, 아무 때나 `find(t)`로 합이 t인 쌍이 있는지 묻는다"는 설계 문제가 있다(LeetCode 170. Two Sum III - Data structure design). 두 연산 중 무엇이 잦은지로 고른다. `add`가 잦으면 값별 개수만 해시맵에 적고(O(1)), `find`에서 키를 다 돌며 보수를 묻는다(O(n)). `find`가 잦으면 `add`할 때 가능한 합을 전부 집합에 미리 넣어 두고(O(n)) `find`를 O(1)로 만든다. 대신 합 집합이 O(n²)까지 커진다.

### 메모리가 부족하다면

해시맵을 못 쓰면 정렬 기반으로 돌아간다. 배열을 고칠 수 있고 인덱스가 필요 없다면 제자리 정렬 + 투 포인터로 추가 공간 O(1)(정렬 구현에 따라 O(log n))이다. 데이터가 메모리에 안 들어갈 만큼 크면 디스크에서 외부 정렬을 한 뒤 양 끝에서 읽어 오는 방식으로 같은 투 포인터를 쓴다.

### 가장 가까운 합, 세 수의 합

"합이 target에 가장 가까운 쌍"이면 해시맵은 쓸 수 없다. 해시맵은 정확히 같은 값만 찾기 때문이다. 정렬 후 투 포인터로 움직이며 차이의 최솟값을 기록한다. 세 수로 늘리면 한 수를 고정하고 나머지 두 수를 Two Sum으로 푸는 구조가 되고, 이것이 [3Sum](/posts/leetcode-3sum)이다. 네 수(LeetCode 18. 4Sum)는 두 수를 고정하고 같은 방법을 쓴다.

비슷하게 "보수를 장부에 묻는" 생각으로 풀리는 문제로는 [Contains Duplicate](/posts/leetcode-contains-duplicate)(본 값을 집합에 적어 두기), [Group Anagrams](/posts/leetcode-group-anagrams)(같은 그룹이 같은 키를 갖게 만들기)가 있다. 누적 합과 결합하면 LeetCode 560. Subarray Sum Equals K가 된다. "지금까지의 합 − k"를 장부에 묻는다는 점에서 이 문제와 같은 모양이다.

## 면접에서 나올 만한 질문

### 왜 해시맵을 썼나요?

이중 반복문의 안쪽이 하는 일이 "보수가 있나"를 찾는 것이고, 그 찾기를 평균 O(1)로 만들 수 있는 구조가 해시맵이기 때문이다. 값을 키로, 인덱스를 값으로 담으면 보수의 존재와 위치를 한 번에 알 수 있다. 그래서 전체가 O(n²)에서 O(n)이 되고, 대가로 O(n) 공간을 쓴다.

### 해시맵 풀이가 최악에도 O(n)인가요?

평균 O(n)이다. 해시 조회가 평균 O(1)이라는 전제 위에 있어서, 충돌이 한 칸에 몰리면 조회가 느려지고 이론상 최악은 O(n²)다. 언어 구현은 문자열 해시에 실행마다 바뀌는 시드를 섞거나(Python) 충돌이 많은 칸을 트리로 바꿔(Java 8 이후 `HashMap`) 최악을 줄여 둔다. 다만 Python의 정수 해시는 값 그대로라 예측할 수 있다. 최악을 보장해야 하면 정렬 기반 풀이가 O(n log n)을 지킨다.

### 먼저 묻고 나중에 넣는 순서가 왜 중요한가요?

장부에 지금 칸보다 앞의 칸만 들어 있게 만들어서 자기 자신과 짝이 되는 일을 구조적으로 막기 때문이다. 순서를 바꾸면 `[3, 2, 4]`, target 6에서 3을 넣자마자 3을 찾아 `[0, 0]`을 돌려준다. 쌍의 뒤쪽 칸을 볼 때 앞쪽 칸은 이미 장부에 있으니 답을 놓치지도 않는다.

### 공간을 O(1)로 줄일 수 있나요?

정렬되지 않은 입력에서 O(n) 시간을 유지하면서는 어렵다. 공간을 O(1)로 하려면 정렬 후 투 포인터를 써야 하는데, 정렬에 O(n log n)이 들고 원래 인덱스를 지키려면 인덱스 배열이 필요해 결국 O(n) 공간을 쓴다. 입력이 이미 정렬돼 있거나 인덱스 대신 값만 돌려줘도 된다면 O(n log n) 시간, O(1) 추가 공간이 가능하다.

### 투 포인터에서 한쪽을 옮겨도 답을 놓치지 않는 이유는요?

합이 target보다 크면, 오른쪽 끝 값은 남은 값 중 가장 작은 왼쪽 끝과 더해도 크다. 그러니 그 값이 들어간 모든 쌍이 답이 아니어서 통째로 버려도 된다. 합이 작을 때는 같은 논리로 왼쪽 끝을 버린다. 매번 답이 아닌 후보만 지우니 답은 끝까지 남는다.

### 이 문제를 Java로 풀 때 조심할 점은요?

`Integer`를 `==`로 비교하면 -128에서 127 밖의 값에서 `false`가 나올 수 있으니 `equals`를 쓴다. `containsKey` 후 `get`을 하면 조회가 두 번이라 `get`의 `null` 여부로 한 번에 확인한다. 이 문제는 제약상 `target - nums[i]`가 `int`에 들어가지만, 세 수 이상을 더하는 변형에서는 `long`이 필요할 수 있다.

### 같은 값이 여러 번 나오면 장부의 인덱스가 덮어써지는데 괜찮나요?

한 번 훑기에서는 덮어쓰기 전에 물어보기 때문에 괜찮다. 두 번째 같은 값을 볼 때 장부에는 첫 번째 값의 인덱스가 있어서 `[3, 3]`이 `[0, 1]`로 찾힌다. 그 뒤에 덮어써지는 건 앞으로 올 칸이 더 가까운 인덱스를 받는 것뿐이고, 답이 하나라는 약속 아래에서 결과가 달라지지 않는다.
