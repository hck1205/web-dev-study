<EasyIntro>
  저장 중 에러가 나면 전부 되돌리라는 표시를 메서드에 분명히 붙였는데, 넣은 데이터가 그대로 남아 있었다. 같은 클래스 안의 다른 메서드가 그 메서드를 직접 불렀다는 것만 달랐다.

  스프링에서는 객체가 자기가 쓸 부품을 직접 만들지 않는다. 회사에서 직원이 필요한 장비를 직접 사러 다니지 않고 총무팀이 책상에 갖다 놓아 주는 것과 같다. 스프링의 컨테이너가 이 총무팀이라, 부품끼리 필요한 순서를 따져 만들고 생성자로 건네준다. 덕분에 테스트할 때는 가짜 부품을 끼워 넣기 쉽고, 부품끼리 서로를 원하는 꼬인 관계는 시작할 때 바로 드러난다.

  처음 장면의 비밀은 총무팀이 건네는 객체가 원본이 아니라 앞에 안내 데스크를 세운 대리인이라는 데 있다. 되돌리기 기능은 바깥에서 안내 데스크를 거쳐 들어오는 호출에만 붙는다. 원본 안에서 자기 메서드를 바로 부르면 데스크를 지나지 않아서 아무 일도 일어나지 않는다.
</EasyIntro>

`@Transactional`을 붙인 메서드에서 예외가 났는데 앞에서 넣은 행이 그대로 남아 있다. 어노테이션은 분명히 붙어 있고, 오타도 없다. 차이는 그 메서드를 부른 곳이었다. 같은 클래스 안의 다른 메서드가 `this.save()`로 불렀다. 바깥에서 부르면 트랜잭션이 열리고, 안에서 부르면 열리지 않는다.

이 현상은 스프링이 객체를 어떻게 만들고 건네주는지 알면 바로 설명된다. 이 글은 그 바닥인 IoC 컨테이너와 의존성 주입(DI)을 다룬다. 왜 컨테이너가 필요해졌는지, 빈이 어떤 순서로 만들어지는지, 주입 방식과 스코프, 프록시, 순환 참조, 생명주기까지 실제로 돌려 본 출력과 함께 본다. 자동 구성이 이 위에서 어떻게 빈을 끼워 넣는지는 [Spring Boot 자동 구성](/posts/spring-boot-auto-configuration)에서, 3.x에서 4로 올리는 이야기는 [Spring Boot 4 마이그레이션](/posts/spring-boot-4-migration)에서 이어 간다.

예제는 JDK 21, Spring Boot 4.1.1(Spring Framework 7.0.9)로 돌렸다. 의존성은 `spring-boot-starter-jdbc`와 H2뿐이다. 이 글에서 다루는 동작은 Spring Boot 3.x(Framework 6.x)에서도 같고, 다른 곳은 따로 적었다.

## new가 곳곳에 흩어져 있으면 생기는 일

주문 서비스가 결제 게이트웨이와 저장소를 쓴다고 해 보자. 가장 단순하게는 서비스가 필요한 걸 직접 만든다.

```java
class OrderService {
  private final PaymentGateway pg = new TossGateway(System.getenv("TOSS_KEY"));
  private final OrderRepository repo = new OrderRepository(new HikariDataSource(...));
}
```

동작은 한다. 문제는 바꿀 때다. 테스트에서 가짜 결제를 쓰려면 이 클래스를 고쳐야 한다. `OrderRepository`를 쓰는 클래스가 열 개면 커넥션 풀도 열 개가 생긴다. 결제사를 바꾸면 `new TossGateway`를 찾아다니며 고쳐야 한다. 객체가 "무엇을 쓸지"와 "그걸 어떻게 만들지"를 함께 알고 있어서다.

해법은 만드는 일을 밖으로 빼는 것이다. 서비스는 생성자로 받기만 하고, 조립은 한곳에서 한다.

```java
class OrderService {
  private final PaymentGateway pg; private final OrderRepository repo;
  OrderService(PaymentGateway pg, OrderRepository repo) { this.pg = pg; this.repo = repo; }
  void place(String id, int amount) { System.out.println(pg.charge(amount)); repo.save(id); }
}

public class PlainMain {
  public static void main(String[] args) {
    // 조립을 한곳에서 손으로 한다
    OrderService svc = new OrderService(new FakePsp(), new OrderRepository());
    svc.place("o-1", 12000);
  }
}
```

```text
fake-ok:12000
saved o-1
```

이게 의존성 주입이다. 프레임워크가 없어도 된다. `main` 같은 조립 지점을 [헥사고날 아키텍처](/posts/hexagonal-architecture) 글에서는 composition root라고 불렀다. 객체가 자기 의존성을 직접 찾지 않고 받는다는 점에서 제어가 뒤집혔다고 하고, 이걸 제어의 역전(Inversion of Control, IoC)이라고 부른다.

손으로 조립하는 방식은 클래스가 수십 개일 때까지는 괜찮다. 수백 개가 되면 `main`이 수백 줄의 `new`가 되고, 순서도 맞춰야 한다(저장소보다 DataSource가 먼저). 게다가 트랜잭션, 보안, 캐시처럼 여러 객체에 똑같이 끼워야 하는 일이 생긴다. 스프링의 IoC 컨테이너는 이 조립과 끼워 넣기를 대신한다.

## 컨테이너가 빈을 만드는 순서

스프링에서 컨테이너가 만들고 관리하는 객체를 빈(bean)이라고 한다. 컨테이너는 객체를 곧바로 만들지 않는다. 먼저 "무엇을 어떻게 만들지"를 적은 설계도인 빈 정의(BeanDefinition)를 모으고, 그다음에 의존 관계를 따라 실제 객체를 만든다.

1. 정의 수집. `@SpringBootApplication`이 붙은 클래스의 패키지부터 하위 패키지를 훑어(컴포넌트 스캔) `@Component`, `@Service`, `@Repository`, `@Controller`, `@Configuration`이 붙은 클래스를 찾는다. `@Bean` 메서드와 자동 구성이 만든 정의도 여기에 더해진다.
2. 정의 후처리. `BeanFactoryPostProcessor`가 정의를 고친다. `${...}` 자리표시자를 채우는 일이 여기서 일어난다.
3. 객체 생성. 싱글턴 빈을 하나씩 만든다. 생성자 인자가 필요하면 그 빈을 먼저 만든다. 그래서 순서는 의존 관계가 정한다.
4. 주입과 초기화. setter·필드 주입, `@PostConstruct` 같은 초기화 콜백을 부른다.
5. 후처리기 감싸기. `BeanPostProcessor`가 완성된 객체를 받아 필요하면 프록시로 감싸서 돌려준다. 컨테이너에 등록되는 건 이 돌려받은 객체다.

아래 그림은 주문 서비스 하나가 준비되기까지를 따라간다. 마지막 단계에서 컨테이너가 원본이 아니라 프록시를 쥔다는 사실이 이 글 뒤쪽의 이야기로 이어진다.

## 주입 방식은 생성자로 고른다

빈을 받는 방법은 생성자, setter, 필드 세 가지다. 지금은 생성자 주입이 기본이다. Spring 4.3부터는 생성자가 하나뿐이면 `@Autowired`를 붙이지 않아도 그 생성자로 주입한다.

```java
@Service
class OrderService {
  private final OrderRepository repo;
  OrderService(OrderRepository repo) { this.repo = repo; }   // @Autowired 없이도 주입된다
}
```

필드 주입은 짧아서 한때 많이 쓰였다. 문제는 컨테이너 밖에서 드러난다. 단위 테스트에서 그냥 `new`로 만들면 필드가 비어 있다.

```java
class OrderService {
  @Autowired private OrderRepository repo;   // 필드 주입
  void place(String id) { repo.save(id); }
}

// 단위 테스트에서 컨테이너 없이 만들어 본다
new OrderService().place("o-1");
```

```text
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "demo.fieldnpe.OrderRepository.save(String)" because "this.repo" is null
	at demo.fieldnpe.OrderService.place(FieldNpe.java:9)
	at demo.fieldnpe.FieldNpe.main(FieldNpe.java:15)
```

생성자 주입이 나은 이유를 정리하면 이렇다. 의존성이 없으면 객체를 만들 수조차 없으니 반쯤 준비된 객체가 생기지 않는다. 필드를 `final`로 둘 수 있어 나중에 바뀌지 않는다. 테스트에서 컨테이너 없이 가짜를 넣어 만들 수 있다([단위 테스트](/posts/test-pyramid-unit-tests) 글의 테스트 더블이 그대로 쓰인다). 그리고 생성자 인자가 일곱 개, 여덟 개로 늘어나면 그 자체가 "이 클래스가 일을 너무 많이 한다"는 신호로 보인다.

setter 주입은 선택적인 의존성이나, 만든 뒤에 바꿔 끼울 일이 있을 때만 쓴다. 테스트 클래스 안에서는 필드 주입(`@Autowired`)이 여전히 흔하다. 테스트 클래스는 컨테이너가 만들기 때문에 문제가 덜하다.

## 같은 타입이 둘이면 컨테이너는 고르지 않는다

결제 게이트웨이를 두 개 등록하고 서비스가 `PaymentGateway` 하나를 달라고 하면 어떻게 될까. 컨테이너는 대충 하나를 고르지 않고 시작을 멈춘다.

```java
interface PaymentGateway { String charge(int amount); }
@Component class TossGateway implements PaymentGateway { ... }
@Component class KcpGateway implements PaymentGateway { ... }

@Service
class OrderService {
  OrderService(PaymentGateway gateway) { }
}
```

```text
***************************
APPLICATION FAILED TO START
***************************

Description:

Parameter 0 of constructor in demo.unique.OrderService required a single bean, but 2 were found:
	- kcpGateway: defined in file [.../classes/demo/unique/KcpGateway.class]
	- tossGateway: defined in file [.../classes/demo/unique/TossGateway.class]

This may be due to missing parameter name information

Action:

Consider marking one of the beans as @Primary, updating the consumer to accept multiple beans, or using @Qualifier to identify the bean that should be consumed
```

경로는 줄여서 옮겼다. `Action`에 나온 세 가지가 실제 선택지다. 평소에 쓸 하나가 정해져 있으면 그쪽에 `@Primary`를 붙인다. 자리마다 다르면 받는 쪽에서 `@Qualifier("kcpGateway")`로 이름을 고른다. 둘 다 써야 하면 `List<PaymentGateway>`나 `Map<String, PaymentGateway>`로 모두 받는다. `Map`의 키는 빈 이름이라, 요청에 따라 결제사를 고르는 코드가 [전략 패턴](/posts/pattern-strategy)처럼 짧아진다.

출력의 "missing parameter name information" 줄은 생성자 인자 이름으로 빈을 고르는 방식과 관련이 있다. 인자 이름이 `kcpGateway`면 그 이름의 빈을 고를 수 있는데, 컴파일할 때 `-parameters`를 켜야 이름이 남는다. Spring Boot의 Maven·Gradle 플러그인은 이걸 켜 둔다. 이름에 기대는 방식은 리팩터링에 약하니 `@Qualifier`를 쓰는 편이 읽기 쉽다.

## @Transactional이 붙은 건 프록시였다

처음의 이야기로 돌아간다. 같은 메서드를 세 가지 방식으로 불러 보고, 그때마다 트랜잭션이 열렸는지 찍어 봤다.

```java
@Service
class OrderService {
  private final OrderWriter writer;
  OrderService(OrderWriter writer) { this.writer = writer; }

  @Transactional
  public void save() {
    System.out.println("  save: tx active = " + TransactionSynchronizationManager.isActualTransactionActive());
  }

  public void placeAll() { this.save(); }            // 같은 객체 안에서 부른다

  public void placeAllViaWriter() { writer.save(); } // 다른 빈으로 분리한 쪽을 부른다
}
```

```text
bean class = demo.tx.OrderService$$SpringCGLIB$$0
is AOP proxy = true
--- 바깥에서 save() 호출
  save: tx active = true
--- 바깥에서 placeAll() 호출 (안에서 this.save())
  save: tx active = false
--- 다른 빈으로 분리한 writer.save() 호출
  writer.save: tx active = true
```

첫 줄이 답이다. 컨테이너가 준 객체의 클래스는 `OrderService`가 아니라 `OrderService$$SpringCGLIB$$0`이다. CGLIB이라는 바이트코드 생성 라이브러리로 `OrderService`를 상속한 클래스를 실행 중에 만든 것이다. 이 프록시는 메서드가 불리면 트랜잭션을 열고, 원본 객체의 메서드를 부르고, 끝나면 커밋하거나 롤백한다. [프록시 패턴](/posts/pattern-proxy)을 컨테이너가 자동으로 적용한 셈이다.

고치는 방법은 몇 가지다. 가장 깔끔한 건 위처럼 트랜잭션 경계를 다른 빈으로 빼는 것이다. "주문 저장"이 따로 떼어 낼 만한 책임이라는 신호이기도 하다. 자기 자신의 프록시를 주입받아(`@Lazy` 자기 주입, `ObjectProvider<OrderService>`) 그걸로 부르는 방법도 있지만 읽는 사람이 헷갈린다. 짧은 범위만 트랜잭션으로 묶고 싶으면 `TransactionTemplate`으로 코드 블록을 직접 감싼다. 정말 모든 내부 호출까지 가로채야 하면 바이트코드를 직접 고치는 AspectJ 모드가 있지만, 빌드 설정이 늘어서 잘 쓰지 않는다.

프록시라는 사실에서 나오는 함정은 더 있다.

- final 클래스와 final 메서드: CGLIB은 상속으로 프록시를 만드니 `final` 클래스는 감쌀 수 없다. 시작할 때 바로 실패한다. Kotlin은 클래스가 기본으로 `final`이라 `kotlin-spring` 플러그인(all-open)이 스프링 어노테이션이 붙은 클래스를 열어 준다.

  ```text
  Caused by: org.springframework.aop.framework.AopConfigException: Could not generate CGLIB subclass of class demo.finalcls.OrderService: Common causes of this problem include using a final class or a non-visible class
  Caused by: java.lang.IllegalArgumentException: Cannot subclass final class demo.finalcls.OrderService
  ```

  `final` 메서드는 더 나쁘다. 클래스는 감싸지지만 그 메서드만 재정의되지 않아서, 오류 없이 트랜잭션이 빠진다.
- private 메서드: 하위 클래스가 재정의할 수 없으니 가로채지 못한다. Spring 6.0부터는 클래스 기반 프록시에서 `protected`와 패키지 범위 메서드까지 트랜잭션이 걸리지만, `private`은 여전히 안 된다.
- @PostConstruct 안에서의 호출: 초기화 콜백은 프록시로 감싸기 전, 원본 객체에서 불린다. 그 안에서 `@Transactional` 메서드를 불러도 트랜잭션이 없다. 시작할 때 데이터를 채워야 하면 `ApplicationReadyEvent` 리스너처럼 컨테이너 준비가 끝난 뒤에 부른다.
- 체크 예외: 기본 규칙은 `RuntimeException`과 `Error`에서만 롤백한다. `IOException` 같은 체크 예외는 던져도 커밋된다. `@Transactional(rollbackFor = Exception.class)`로 바꿀 수 있다. 롤백 자체의 의미는 [ACID 트랜잭션](/posts/acid-transactions) 글에서 다뤘다.

`@Async`, `@Cacheable`, `@Retryable`, 메서드 보안(`@PreAuthorize`)도 같은 프록시 방식이라 같은 함정을 그대로 가진다. "어노테이션이 안 먹는다"는 증상을 보면 먼저 그 호출이 프록시를 지났는지 본다.

## 같은 프록시에 내 코드를 끼워 넣는 AOP

`@Transactional`이 하는 일, 곧 "메서드 앞뒤에 무언가를 끼워 넣는 일"을 직접 만들 수도 있다. 이게 AOP(관점 지향 프로그래밍)다. 실행 시간 측정, 감사 로그, 권한 확인처럼 여러 클래스에 똑같이 붙는 관심사를 한곳에 모은다. 용어가 셋 나온다.

조인 포인트(join point)는 끼워 넣을 수 있는 실행 지점이다. 스프링 AOP는 프록시로 동작하니 조인 포인트가 "빈의 메서드 실행" 하나뿐이다. 포인트컷(pointcut)은 그중 어디에 끼울지 고르는 식이다. `execution(* demo..*Service.*(..))`처럼 메서드 모양으로 고르거나, `@annotation(demo.aop.Timed)`처럼 어노테이션으로 고른다. 어드바이스(advice)는 거기서 실제로 실행할 코드이고, 언제 실행하느냐에 따라 `@Before`, `@AfterReturning`, `@AfterThrowing`, `@After`, `@Around`로 나뉜다. 포인트컷과 어드바이스를 묶은 클래스가 애스펙트(aspect)다.

Spring Boot 4에서는 `spring-boot-starter-aspectj`(3.x까지는 `spring-boot-starter-aop`)를 넣고 `@Aspect`를 붙인 빈을 만들면 된다. `@Timed`라는 어노테이션을 만들고 애스펙트 둘을 붙여 봤다.

```java
@Aspect @Component @Order(1)
class LoggingAspect {
  @Pointcut("@annotation(demo.aop.Timed)")
  void timed() {}                       // 포인트컷에 이름을 붙여 재사용한다

  @Before("timed()")
  void before(JoinPoint jp) { System.out.println("  [log  @Order(1)] before " + jp.getSignature().toShortString()); }

  @AfterThrowing(pointcut = "timed()", throwing = "ex")
  void failed(Exception ex) { System.out.println("  [log  @Order(1)] threw " + ex.getClass().getSimpleName()); }
}

@Aspect @Component @Order(2)
class TimingAspect {
  @Around("@annotation(demo.aop.Timed)")
  Object time(ProceedingJoinPoint pjp) throws Throwable {
    System.out.println("  [time @Order(2)] start");
    try { return pjp.proceed(); }       // proceed()를 불러야 원본 메서드가 실행된다
    finally { System.out.println("  [time @Order(2)] end"); }
  }
}

@Service
class OrderService {
  @Timed public void place(String id) { System.out.println("    place " + id); }
  public void placeTwice() { this.place("B-1"); this.place("B-2"); }
  @Timed public void cancel(String id) { if (id.isEmpty()) throw new IllegalArgumentException("empty id"); }
}
```

```text
--- orders.place("A-1")
  [log  @Order(1)] before OrderService.place(..)
  [time @Order(2)] start
    place A-1
  [time @Order(2)] end
--- orders.placeTwice() (안에서 this.place)
    place B-1
    place B-2
--- orders.cancel("") 예외
  [log  @Order(1)] before OrderService.cancel(..)
  [time @Order(2)] start
  [time @Order(2)] end
  [log  @Order(1)] threw IllegalArgumentException
caller caught: empty id
```

순서부터 보자. `@Order` 숫자가 작은 애스펙트가 바깥 껍질이다. 들어갈 때는 `@Order(1)`의 `@Before`가 먼저 돌고, 나올 때는 `@Order(2)`의 `finally`가 끝난 뒤에야 `@Order(1)`의 `@AfterThrowing`이 돈다. 양파처럼 감싼다고 보면 된다. 이 순서는 `@Transactional`과 섞일 때 중요하다. 트랜잭션 어드바이저의 순서는 기본이 가장 낮은 우선순위(가장 안쪽)라서, 재시도 애스펙트에 `@Order`를 주지 않으면 같은 우선순위끼리 순서가 정해지지 않는다. 재시도가 트랜잭션 바깥에서 돌아야 매번 새 트랜잭션으로 다시 시도하니, 재시도 쪽에 더 작은 숫자를 준다.

`@Around`는 `proceed()`를 부르지 않으면 원본이 아예 실행되지 않고, 반환값을 돌려주지 않으면 호출한 쪽은 null을 받는다. `@AfterThrowing`은 예외를 지켜볼 뿐 삼키지 않아서, 예외는 그대로 호출한 쪽까지 올라갔다(`caller caught`).

그리고 `placeTwice()`에서는 어떤 어드바이스도 돌지 않았다. 앞 절의 `this.save()`와 똑같다. 애스펙트도 같은 프록시에 붙으니 프록시가 못 거는 자리가 그대로 이어진다. 같은 클래스 안의 호출, `private`·`final` 메서드, `@PostConstruct` 안의 호출, 그리고 `new`로 직접 만든 객체처럼 컨테이너가 모르는 객체다. 생성자나 필드 접근에 끼워 넣어야 하거나 이런 자리까지 잡아야 하면 컴파일·로드 시점에 바이트코드를 고치는 AspectJ 위빙으로 가야 한다. 포인트컷을 넓게 쓰는 것도 조심한다. `execution(* *(..))`처럼 모든 메서드를 고르면 자동 구성이 만든 빈까지 프록시가 되어 시작이 느려지고, `final` 클래스인 남의 빈에 걸려 시작이 실패하기도 한다.

## 서로를 생성자로 원하면 시작하지 않는다

주문 서비스가 쿠폰 서비스를 쓰고, 쿠폰 서비스가 주문 서비스를 쓴다고 해 보자. 둘 다 생성자 주입이면 컨테이너는 어느 쪽도 먼저 만들 수 없다. 주문을 만들려면 쿠폰이 있어야 하고, 쿠폰을 만들려면 주문이 있어야 한다.

컨테이너는 "지금 만드는 중인 빈" 목록을 들고 다니다가, 이미 목록에 있는 빈을 또 만들려고 하면 고리를 알아챈다. 아래에서 다음을 누르면 그 목록이 쌓이는 모습을 따라간다.

## 싱글턴 안에 넣은 프로토타입은 한 번만 만들어진다

빈마다 수명 범위(스코프)가 있다. 기본은 싱글턴이다. 컨테이너 하나에 객체 하나를 만들어 모든 곳에 같은 걸 넣어 준다. [싱글턴 패턴](/posts/pattern-singleton)처럼 클래스가 스스로 하나만 지키는 게 아니라, 컨테이너가 하나만 만들어 나눠 주는 것이다. 그래서 테스트에서는 얼마든지 따로 만들 수 있다.

`prototype`은 요청할 때마다 새로 만든다. 웹 환경에는 `request`, `session`, `application`, `websocket` 스코프가 더 있다.

싱글턴은 여러 요청 스레드가 동시에 같은 객체를 쓴다는 뜻이기도 하다. 그래서 싱글턴 빈에 요청마다 바뀌는 값을 필드로 들고 있으면 안 된다. 사용자 A의 값이 사용자 B의 요청에서 보이는 사고가 여기서 난다. 싱글턴 빈은 상태가 없게(설정과 다른 빈 참조만 들고 있게) 만든다.

흔한 실수가 하나 더 있다. 싱글턴 빈에 프로토타입 빈을 생성자로 넣으면, 싱글턴이 만들어질 때 딱 한 번 주입되고 끝이다. 매번 새 장바구니를 기대했는데 같은 장바구니가 계속 나온다.

```java
@Component @Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
class Cart {
  static final AtomicInteger SEQ = new AtomicInteger();
  final int id = SEQ.incrementAndGet();
}

@Component
class Checkout {
  private final Cart cart;                    // 시작할 때 한 번 주입된다
  private final ObjectProvider<Cart> carts;   // 꺼낼 때마다 컨테이너에 부탁한다
  Checkout(Cart cart, ObjectProvider<Cart> carts) { this.cart = cart; this.carts = carts; }
  Cart injected() { return cart; }
  Cart fresh() { return carts.getObject(); }
}
```

```text
singleton same? true
prototype same? false
injected cart:  1, 1
provider cart:  4, 5
```

`injected`는 두 번 불러도 1번 장바구니다. `provider`는 부를 때마다 새것이다. 2번과 3번은 그 앞의 `prototype same?` 확인에서 `getBean`을 두 번 부르며 만들어졌다. `ObjectProvider` 말고도 `@Lookup` 메서드나 스코프 프록시(`@Scope(proxyMode = ScopedProxyMode.TARGET_CLASS)`)로 같은 문제를 푼다. `request` 스코프 빈을 싱글턴에 넣을 때 스코프 프록시를 쓰는 이유도 같다.

## 빈이 태어나서 치워지기까지

빈 하나의 생명주기를 콜백마다 번호를 찍어 확인했다. `PriceCache`는 생성자, setter 주입, `@PostConstruct`, `InitializingBean`, 준비 완료 이벤트, 종료 콜백을 모두 갖고 있다.

```java
@Component
class PriceCache implements InitializingBean, DisposableBean {
  private Clock clock;
  PriceCache() { System.out.println("2. PriceCache 생성자 (clock = " + clock + ")"); }
  @Autowired void setClock(Clock c) { this.clock = c; System.out.println("3. setter 주입"); }
  @PostConstruct void warmUp() { System.out.println("4. @PostConstruct (clock 있음: " + (clock != null) + ")"); }
  @Override public void afterPropertiesSet() { System.out.println("5. afterPropertiesSet"); }
  @EventListener(ApplicationReadyEvent.class) void ready() { System.out.println("6. ApplicationReadyEvent"); }
  @PreDestroy void flush() { System.out.println("7. @PreDestroy"); }
  @Override public void destroy() { System.out.println("8. DisposableBean.destroy"); }
}
```

```text
1. Clock 생성자
2. PriceCache 생성자 (clock = null)
3. setter 주입
4. @PostConstruct (clock 있음: true)
5. afterPropertiesSet
6. ApplicationReadyEvent
== context.close()
7. @PreDestroy
8. DisposableBean.destroy
```

## 작은 컨테이너를 직접 만들어 본다

컨테이너가 하는 일의 뼈대는 "의존 관계를 따라 먼저 필요한 것부터 만들고, 만드는 중인 것을 또 만나면 고리로 본다"는 것이다. 아래 함수 `creationOrder(defs)`를 채워 보자. `defs`는 빈 이름에서 생성자 의존성 목록으로 가는 객체다. 정의 순서대로 빈을 만들되 의존성을 먼저 만들고, 만들어진 순서를 배열로 돌려준다. 고리를 만나면 `"cycle: a -> b -> a"` 문자열을, 정의가 없는 빈을 원하면 `"missing: 이름"`을 돌려준다.

## 시작이 실패하거나 어노테이션이 안 먹을 때 보는 곳

증상별로 처음 볼 곳을 모아 둔다.

- `required a single bean, but 2 were found`: 같은 타입 빈이 둘이다. 자동 구성이 만든 빈과 내가 만든 빈이 겹친 경우도 많다. `@Primary`, `@Qualifier`로 정하거나, 하나를 지운다.
- `required a bean of type '...' that could not be found`: 그 클래스가 컴포넌트 스캔 범위 밖에 있는지 본다. `@SpringBootApplication` 클래스보다 위나 옆 패키지에 있으면 스캔되지 않는다. 자동 구성이 조건 때문에 빈을 안 만든 경우는 `--debug`의 조건 평가 리포트로 확인한다([자동 구성](/posts/spring-boot-auto-configuration) 글).
- `form a cycle`: 고리 그림에 찍힌 빈들의 공통 책임을 꺼낸다. 설정으로 덮지 않는다.
- `@Transactional`, `@Async`, `@Cacheable`이 안 먹는다: 같은 클래스 안의 호출인지, `private`·`final` 메서드인지, `@PostConstruct` 안인지 본다. 디버거에서 그 객체의 클래스 이름에 `$$SpringCGLIB$$`가 있는지 보면 프록시 여부를 바로 안다.
- 요청끼리 값이 섞인다: 싱글턴 빈에 요청별 상태를 필드로 들고 있지 않은지 본다.

빈 목록이 궁금하면 액추에이터의 `/actuator/beans`가 모든 빈과 의존 관계를 JSON으로 보여 준다. 운영에서는 노출 범위를 꼭 좁힌다.

## 프록시 하나가 설명하는 것들

IoC는 객체가 자기 의존성을 직접 만들지 않고 받는다는 생각이고, 스프링 컨테이너는 그 조립을 빈 정의와 의존 관계를 따라 대신해 준다. 생성자 주입을 쓰면 고리와 과한 의존이 시작 시점에 드러난다. 그리고 컨테이너가 건네는 객체는 원본이 아니라 프록시일 수 있다. `@Transactional`이 가끔 사라지는 이유, `final`과 `private`이 문제가 되는 이유가 모두 이 한 가지에서 나온다. 다음 글 [Spring Boot 자동 구성](/posts/spring-boot-auto-configuration)에서는 내가 만든 적 없는 `DataSource`와 트랜잭션 매니저가 어디서 왔는지 본다.

## 면접에서 나올 만한 질문

### IoC와 DI는 어떻게 다른가요?

IoC는 객체가 자기가 쓸 것을 직접 만들거나 찾지 않고 바깥에서 받는다는 원칙이고, DI는 그 원칙을 구현하는 방법 중 하나로 생성자나 setter로 의존성을 넣어 주는 것이다. 스프링에서는 컨테이너가 빈 정의를 모아 의존 관계를 따라 객체를 만들고 넣어 준다. 프레임워크 없이도 `main`에서 손으로 조립하면 DI다.

### 생성자 주입을 권장하는 이유는 무엇인가요?

의존성 없이는 객체를 만들 수 없어서 반쯤 준비된 상태가 생기지 않고, 필드를 `final`로 둘 수 있다. 컨테이너 없이 `new`로 가짜를 넣어 단위 테스트를 할 수 있다. 생성자끼리의 순환 참조는 시작할 때 바로 실패해서 설계 문제가 일찍 드러난다. 인자가 많아지면 클래스가 너무 많은 일을 한다는 신호로도 읽힌다.

### 같은 클래스 안에서 @Transactional 메서드를 부르면 왜 트랜잭션이 안 걸리나요?

컨테이너가 주는 객체는 원본을 감싼 프록시이고, 트랜잭션은 프록시가 호출을 가로챌 때 열린다. 원본 안에서 `this.method()`로 부르면 `this`가 원본이라 프록시를 지나지 않는다. 트랜잭션 경계를 다른 빈으로 빼거나, `TransactionTemplate`으로 감싸거나, 꼭 필요하면 AspectJ 모드를 쓴다. `@Async`, `@Cacheable`도 같은 이유로 같은 함정이 있다.

### JDK 동적 프록시와 CGLIB 프록시는 무엇이 다른가요?

JDK 동적 프록시는 인터페이스를 구현한 객체를 만들고, CGLIB은 클래스를 상속한 하위 클래스를 만든다. 그래서 CGLIB은 `final` 클래스를 감쌀 수 없고 `final`·`private` 메서드는 가로채지 못한다. Spring Boot는 기본으로 인터페이스가 있어도 CGLIB을 쓴다. 인터페이스 프록시에 구체 클래스 타입으로 주입받으려다 실패하는 문제를 피하려는 선택이다.

### 순환 참조는 왜 막혔고, 어떻게 푸나요?

Spring Boot 2.6부터 기본으로 금지됐다. 예전에는 필드·setter 주입끼리의 고리를 덜 만든 객체의 이른 참조로 풀어 줬지만, 덜 초기화된 객체가 돌아다니는 위험이 있었다. `spring.main.allow-circular-references=true`로 되살릴 수 있지만 생성자끼리의 고리는 그래도 못 푼다. 두 빈이 함께 쓰는 부분을 세 번째 빈으로 꺼내거나 이벤트로 바꾸는 게 근본 해법이고, `@Lazy`는 문제를 첫 호출로 미루는 임시방편이다.

### 싱글턴 빈에 프로토타입 빈을 주입하면 어떻게 되나요?

싱글턴이 만들어질 때 한 번만 주입되니 계속 같은 프로토타입 객체를 쓰게 된다. 매번 새 객체가 필요하면 `ObjectProvider`로 꺼낼 때마다 받거나, `@Lookup` 메서드, 스코프 프록시를 쓴다. 프로토타입 빈은 컨테이너가 넘긴 뒤 추적하지 않아서 `@PreDestroy`도 불리지 않는다는 점도 함께 기억한다.

### 싱글턴 빈은 스레드 안전한가요?

컨테이너가 객체를 하나만 만들어 줄 뿐 동시성을 지켜 주지는 않는다. 여러 요청 스레드가 같은 객체를 동시에 쓰니, 요청마다 바뀌는 값을 필드에 두면 값이 섞인다. 싱글턴 빈은 설정과 다른 빈 참조만 들고 상태 없이 만들고, 요청별 값은 메서드 지역 변수나 인자로 다룬다.

### @PostConstruct에서 DB 초기화를 하면 어떤 문제가 있나요?

`@PostConstruct`는 후처리기가 프록시로 감싸기 전, 원본 객체에서 불린다. 그 안에서 자기 `@Transactional` 메서드를 불러도 트랜잭션이 없고, 다른 빈이 아직 준비되지 않았을 수도 있다. 시작 시 작업은 `ApplicationReadyEvent` 리스너나 `ApplicationRunner`에서 하는 편이 안전하다.
