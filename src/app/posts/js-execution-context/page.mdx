댓글 화면을 만들었다. 서버는 답글을 "답글의 답글" 식으로 한 줄로 이어 붙인 구조로 준다. 각 댓글이 다음 답글 하나를 `reply`에 들고 있는 모양이다. id만 모으는 함수는 재귀로 짰다.

```js
function collectIds(node) {
  if (!node) return [];
  return [node.id, ...collectIds(node.reply)];
}

// 테스트용: 댓글 n개를 한 줄로 이어 붙인다
function makeThread(n) {
  let head = null;
  for (let i = n; i >= 1; i--) head = { id: i, reply: head };
  return head;
}

console.log(collectIds(makeThread(1000)).length);
try {
  console.log(collectIds(makeThread(20000)).length);
} catch (e) {
  console.log(e.constructor.name + ": " + e.message);
}
```

```text
1000
RangeError: Maximum call stack size exceeded
```

1,000개일 때는 멀쩡하고 2만 개에서 죽는다. 메모리가 모자란 것도 아니다. 2만 개짜리 배열쯤은 아무 문제 없이 만든다. 모자란 건 함수 호출을 쌓아 두는 공간, 콜 스택이다. 이 글은 함수를 부를 때 엔진이 무엇을 만들어 쌓는지(실행 컨텍스트), 그 더미가 어떻게 넘치는지, 넘치지 않게 고치는 방법과 운영에서 스택 정보를 읽는 법을 본다.

## 함수를 부를 때마다 작업 공간이 하나 생긴다

함수를 실행하려면 엔진은 몇 가지를 알아야 한다. 이 함수의 지역 변수는 무엇이고 지금 값은 얼마인가. 여기 없는 이름은 어디서 찾나. `this`는 무엇인가. 끝나면 어디로 돌아가나. 이 정보를 한데 묶은 것을 명세는 실행 컨텍스트(execution context)라고 부른다. 함수를 한 번 부를 때마다 새 실행 컨텍스트가 하나 생긴다. 같은 함수를 열 번 부르면 열 개가 생긴다.

종류는 셋이다. 스크립트나 모듈이 처음 돌 때의 전역(모듈) 컨텍스트, 함수를 부를 때의 함수 컨텍스트, `eval` 안의 코드를 돌릴 때의 eval 컨텍스트다. 실무에서 신경 쓰는 건 앞의 둘이다.

- 환경 레코드(Environment Record): 이 범위에서 선언된 이름과 값의 표다. 함수 컨텍스트라면 매개변수, 지역 변수, 안에서 선언한 함수가 여기 들어간다.
- LexicalEnvironment, VariableEnvironment: 이름을 찾을 때 어느 환경 레코드부터 볼지 가리키는 두 개의 포인터다. 함수에 막 들어섰을 때는 보통 같은 레코드를 가리키고, `let`·`const` 블록에 들어가면 LexicalEnvironment만 새 블록 레코드로 옮겨 간다. `var`가 블록을 무시하는 이유가 이 구분이다.
- `[[OuterEnv]]`: 환경 레코드마다 바깥 레코드를 가리키는 링크가 있다. 여기 없는 이름은 이 링크를 따라 바깥으로 찾는다. 이 사슬이 스코프 체인이다.
- `this`: 함수 환경 레코드가 `this` 값을 함께 들고 있다. 화살표 함수는 자기 `this`를 갖지 않아서 바깥 레코드의 것을 쓴다.

여기서 하나만 기억하면 된다. 실행 컨텍스트는 호출마다 새로 생기고, 그 안의 환경 레코드는 함수가 어디서 쓰였는지(렉시컬 위치)에 따라 바깥과 연결된다. 실행 컨텍스트가 "언제"를 맡고 환경 레코드의 사슬이 "어디서 찾나"를 맡는다.

## 만들어질 때 한 번, 실행할 때 한 번

함수 컨텍스트는 두 단계로 일한다. 먼저 환경을 만든다. 코드를 한 줄도 실행하기 전에 함수 본문을 훑어 선언된 이름을 전부 레코드에 등록한다. 그다음 위에서부터 한 줄씩 실행하며 값을 채운다.

```js
function order(qty) {
  console.log(typeof price, typeof calc, typeof qty);
  var price = 1200;
  function calc() {
    return price * qty;
  }
  return calc();
}
console.log(order(3));
console.log(order(2));
```

```text
undefined function number
3600
undefined function number
2400
```

첫 줄에서 `price`는 아직 대입 전인데 에러가 나지 않고 `undefined`다. `calc`는 벌써 함수다. 만드는 단계에서 `var`는 `undefined`로, 함수 선언은 함수 객체로 미리 채워 두기 때문이다. `let`·`const`는 이름만 등록하고 초기화하지 않아서 그 전에 읽으면 에러가 난다. 이 차이는 [호이스팅과 TDZ](/posts/js-hoisting-tdz)에서 자세히 봤다.

또 하나 보이는 게 있다. `order(3)`과 `order(2)`는 같은 함수인데 `price`, `qty`, `calc`가 서로 섞이지 않는다. 호출마다 레코드를 새로 만들기 때문이다. 아래 그림에서 다음을 눌러 `order(3)` 한 번의 일생을 따라가 보자.

## 콜 스택은 컨텍스트를 쌓는 접시 더미다

함수 안에서 함수를 부르면 새 컨텍스트가 지금 것 위에 올라간다. 안쪽 함수가 끝나야 바깥 함수가 이어서 돈다. 이 더미가 콜 스택이고, 엔진은 늘 맨 위 컨텍스트 하나만 실행한다. 이 글에서 쓰는 비유는 접시 더미 하나다. 맨 위에만 올리고 맨 위에서만 뺀다.

재귀는 같은 함수의 컨텍스트를 여러 장 쌓는다. 배열 합을 재귀로 구하는 예를 보자.

```js
function total(items) {
  if (items.length === 0) return 0;
  const [first, ...rest] = items;
  return first + total(rest);
}
console.log(total([3, 5, 2]));
```

```text
10
```

## 몇 장까지 쌓이나

콜 스택은 무한하지 않다. V8은 스택 크기를 바이트로 제한한다. 몇 번 호출할 수 있는지는 한 장(스택 프레임)이 얼마나 큰지에 달렸다. Node.js 22에서 지역 변수가 없는 함수와 10개 있는 함수를 끝까지 재귀시켜 봤다.

```js
let depth = 0;
function small() { depth++; small(); }
try { small(); } catch (e) {}
console.log("지역 변수 없음:", depth);

depth = 0;
function big() {
  depth++;
  const a = 1, b = 2, c = 3, d = 4, e = 5, f = 6, g = 7, h = 8, i = 9, j = 10;
  big();
  return a + b + c + d + e + f + g + h + i + j;
}
try { big(); } catch (e) {}
console.log("지역 변수 10개:", depth);
```

```text
지역 변수 없음: 12556
지역 변수 10개: 6278
```

`node --stack-size=2000`으로 한도를 올리면 이렇게 바뀐다.

```text
지역 변수 없음: 25561
지역 변수 10개: 12780
```

숫자 자체는 외울 필요가 없다. 엔진 버전, JIT가 함수를 최적화했는지, 운영체제의 스레드 스택 크기에 따라 달라진다. 크롬, 파이어폭스, 사파리도 저마다 다르다. 기억할 건 두 가지다. 한도는 "호출 수"가 아니라 "바이트"라서 프레임이 클수록 빨리 넘친다. 그리고 수천~수만 단계가 대략적인 천장이다. 사용자가 보낸 데이터의 깊이만큼 재귀하는 코드는 언젠가 이 천장에 닿는다.

`--stack-size`를 올리는 건 답이 아니다. V8이 생각하는 크기만 바뀌고 운영체제가 준 실제 스레드 스택은 그대로라서, 너무 크게 잡으면 `RangeError` 대신 프로세스가 세그멘테이션 폴트로 죽을 수 있다. 브라우저에서는 바꿀 방법도 없다.

## 넘치는 곳은 재귀만이 아니다

내가 재귀를 쓰지 않았는데도 넘치는 경우가 있다. 가장 흔한 건 세터가 자기 자신을 부르는 실수다.

```js
class User {
  constructor(name) {
    this.name = name;
  }
  set name(v) {
    this.name = v.trim(); // 세터 안에서 다시 세터를 부른다
  }
}
new User(" kim ");
```

```text
/app/user.js:6
    this.name = v.trim(); // 세터 안에서 다시 세터를 부른다
              ^

RangeError: Maximum call stack size exceeded
    at set name (/app/user.js:6:15)
    at set name (/app/user.js:6:15)
    at set name (/app/user.js:6:15)
    at set name (/app/user.js:6:15)
```

(경로는 `/app`으로 줄였고, 반복되는 줄은 일부만 옮겼다.) 스택 트레이스에 같은 줄이 끝없이 반복되면 무한 재귀다. 값은 `this._name`이나 `#name` 같은 다른 이름에 저장해야 한다. `toString`, `valueOf`, `toJSON` 안에서 자기 자신을 문자열로 바꾸는 코드, `Proxy`의 `get` 트랩 안에서 같은 프록시를 읽는 코드도 같은 모양으로 넘친다.

내장 함수도 안쪽은 재귀인 경우가 있다. 배열을 10만 단계로 중첩해 Node.js 22에 넣어 봤다.

```js
const n = 100000;
```

## await 너머의 스택

비동기 코드에서는 사진에 찍히지 않는 부분이 생긴다. `await`에서 함수가 멈추면 그 실행 컨텍스트는 콜 스택에서 내려온다. 지역 변수와 "어디까지 실행했는지"는 따로 보관해 두고, 기다리던 값이 오면 마이크로태스크로 다시 스택에 올라온다. 그때의 스택 바닥에는 원래 부른 쪽이 없다.

## 깊이를 스택에서 빼내는 방법

다시 댓글 2만 개로 돌아가자. 고치는 방법은 깊이를 콜 스택 대신 다른 곳에 맡기는 것이다.

### 반복문으로 바꾼다

한 줄로 이어진 구조는 재귀가 필요 없다.

```js
function collectIds(node) {
  const ids = [];
  for (let cur = node; cur; cur = cur.reply) ids.push(cur.id);
  return ids;
}
```

### 스택을 직접 들고 간다

트리는 갈래가 있어서 반복문 하나로는 안 된다. 그때는 콜 스택이 하던 일을 배열로 직접 한다. 배열은 힙에 있으니 메모리가 허락하는 만큼 깊어질 수 있다. 아래 그림은 댓글 트리를 앞에서부터(전위 순회) 펼치는 과정이다. 칸은 댓글이고 아래 상자가 직접 관리하는 스택이다.

```js
function preorder(root) {
  const out = [];
  const stack = [root];
  while (stack.length) {
    const n = stack.pop();
    out.push(n.id);
    // 앞 답글이 먼저 나오게 거꾸로 넣는다
    for (let i = n.replies.length - 1; i >= 0; i--) stack.push(n.replies[i]);
  }
  return out;
}
```

### 트램펄린

코드 모양을 재귀 그대로 두고 싶을 때 쓰는 기법이다. 함수가 자기 자신을 부르는 대신 "다음에 부를 함수"를 돌려주고, 바깥 반복문이 그걸 계속 실행한다. 매번 한 장만 쌓였다가 빠지니 깊어지지 않는다.

```js
function trampoline(fn) {
  return (...args) => {
    let r = fn(...args);
    while (typeof r === "function") r = r();
    return r;
  };
}
const sumIds = trampoline(function go(node, acc = 0) {
  if (!node) return acc;
  return () => go(node.reply, acc + node.id);
});
console.log(sumIds(makeThread(100000)));
```

```text
5000050000
```

돌려줄 값이 함수일 수 있는 경우엔 쓸 수 없고, 호출마다 화살표 함수를 하나씩 만드는 비용이 있다. 실무에서는 반복문이나 명시적 스택이 더 흔하다.

### 꼬리 호출 최적화는 기대하지 않는다

ES2015 명세에는 꼬리 위치의 호출(`return f(x)`처럼 호출 뒤에 할 일이 없는 호출)은 스택을 쌓지 않는다는 규칙(proper tail calls)이 있다. 하지만 이걸 구현한 주요 엔진은 사파리의 JavaScriptCore뿐이다. V8(크롬, Node.js)과 파이어폭스는 구현하지 않았다. 디버깅할 때 스택 트레이스에서 프레임이 사라지는 문제 등이 이유였다. 그러니 "꼬리 재귀로 바꾸면 괜찮다"는 자바스크립트에서는 사파리에서만 맞는 말이다.

어느 방법을 고를지는 이렇게 정한다. 입력의 깊이를 내가 통제할 수 있고 수백 단계를 넘지 않는다면(폴더 깊이, 메뉴 트리) 재귀가 가장 읽기 쉽다. 사용자나 외부 시스템이 보낸 데이터라 깊이가 정해지지 않았다면 명시적 스택으로 바꾸거나 깊이 제한을 걸어 일찍 거절한다.

## React에서 콜 스택을 만나는 자리

컴포넌트도 함수라서 렌더링할 때마다 실행 컨텍스트가 생긴다. 다만 컴포넌트 트리가 깊다고 그만큼 콜 스택이 깊어지지는 않는다. React 16에서 들어온 Fiber 구조는 렌더 단계에서 트리를 함수 재귀 대신 반복 루프로 돈다. 자식 컴포넌트는 부모 함수 안에서 불리는 게 아니라 루프가 다음 차례에 부른다. 댓글 컴포넌트가 자기 자신을 자식으로 그리는 재귀 컴포넌트도 그래서 꽤 깊어도 버틴다. 렌더 안에서 내가 직접 부르는 재귀 유틸(트리를 펼치는 함수)은 여전히 스택을 쓴다.

자주 헷갈리는 에러 두 개는 스택 오버플로가 아니다.

- `Too many re-renders`: 렌더하는 도중에 `setState`를 불러 다시 렌더하는 일이 25번을 넘으면 React가 멈춘다. `onClick={setOpen(true)}`처럼 핸들러 자리에서 함수를 바로 호출했을 때 흔히 난다.
- `Maximum update depth exceeded`: 커밋 뒤 effect나 `componentDidUpdate`에서 상태를 바꾸고, 그게 다시 effect를 부르는 고리가 50번을 넘으면 난다. 의존성 배열에 매번 새로 만들어지는 객체를 넣었을 때가 단골이다.

두 숫자(25, 50)는 React 19의 `react-dom` 소스에 있는 상수 `RE_RENDER_LIMIT`, `NESTED_UPDATE_LIMIT`이다. 엔진의 스택 한도가 아니라 React가 무한 루프를 일찍 끊으려고 센 횟수다. 그래서 에러 메시지도 `RangeError`가 아니라 React가 던지는 일반 `Error`다. 진짜 `RangeError: Maximum call stack size exceeded`가 React 앱에서 났다면, 내 재귀 유틸이나 세터, 서로를 부르는 두 함수부터 본다.

## 현장에서 스택 오버플로를 좁히는 순서

증상은 대개 둘 중 하나다. 특정 데이터를 열 때만 페이지가 하얗게 죽거나, 특정 요청에서만 서버가 500을 낸다. 이렇게 좁힌다.

1. 트레이스에서 반복되는 프레임을 찾는다. 같은 함수 한 줄이 반복되면 무한 재귀다(세터, `toJSON`). 두세 함수가 번갈아 반복되면 서로를 부르는 고리다.
2. 반복이 끝없이 이어지는 게 아니라 입력 크기와 비례한다면 무한 재귀가 아니라 깊은 입력이다. 그 데이터의 깊이를 재 본다.
3. 트레이스가 10줄이라 시작점이 안 보이면 `Error.stackTraceLimit`을 잠시 올려서 재현한다.
4. 재현 테스트를 깊은 입력(1만, 10만 단계)으로 만든다. 1,000 정도로는 통과해 버리니 고친 뒤에도 같은 테스트로 확인한다.

`try`/`catch`로 `RangeError`를 잡을 수는 있다. 그러나 잡은 자리가 이미 한도 근처라서, `catch` 안에서 로깅 함수를 부르다 다시 넘치는 일이 있다. 잡아서 넘기는 건 응급처치이고 고치는 건 깊이를 줄이는 쪽이다.

## 다시 댓글 2만 개로

`collectIds`가 죽은 건 메모리가 아니라 콜 스택 때문이었다. 호출 하나가 실행 컨텍스트 한 장이고, 재귀는 입력 깊이만큼 장을 쌓는다. 스택은 바이트 단위로 정해진 크기라 수천~수만 장에서 넘친다. 깊이가 정해지지 않은 데이터라면 깊이를 콜 스택이 아니라 힙의 배열에 맡긴다. 같은 콜 스택이 비어야 다음 일이 돈다는 규칙은 [이벤트 루프](/posts/event-loop)와 [마이크로태스크와 매크로태스크](/posts/js-microtask-macrotask)로 이어진다.

## 면접에서 나올 만한 질문

### 실행 컨텍스트가 무엇인가요?

코드를 실행하는 데 필요한 정보를 묶은 단위다. 어떤 이름이 어떤 값인지 담은 환경 레코드, 바깥 환경으로 가는 링크, `this` 값, 실행 중인 위치를 들고 있다. 전역 코드가 시작할 때 하나, 함수를 부를 때마다 하나씩 새로 만들어져 콜 스택에 쌓인다.

### 실행 컨텍스트가 만들어지는 과정은 어떻게 되나요?

두 단계다. 만드는 단계에서 본문을 훑어 선언을 환경 레코드에 등록한다. `var`는 `undefined`로, 함수 선언은 함수 객체로 채우고, `let`·`const`는 초기화하지 않은 채 둔다. 그다음 실행 단계에서 한 줄씩 돌며 값을 대입한다. 호이스팅과 TDZ는 이 첫 단계에서 생기는 현상이다.

### 콜 스택과 힙은 무엇이 다른가요?

콜 스택은 지금 실행 중인 함수 호출의 순서를 쌓는 곳이고 크기가 정해져 있다. 객체, 배열, 클로저가 잡고 있는 환경 레코드는 힙에 있고 GC가 관리한다. 그래서 함수가 끝나 컨텍스트가 스택에서 빠져도 누군가 참조하는 환경 레코드는 힙에 남는다. 이게 클로저가 동작하는 이유다.

### Maximum call stack size exceeded는 왜 나고, 어떻게 고치나요?

콜 스택에 쌓인 프레임이 엔진의 한도를 넘었다는 뜻이다. 무한 재귀(자기 자신을 부르는 세터, 서로 부르는 함수)이거나, 끝은 있지만 입력이 너무 깊은 재귀다. 무한 재귀는 종료 조건을 고치고, 깊은 입력은 반복문이나 직접 관리하는 스택 배열로 바꾸거나 깊이 제한을 둔다.

### 꼬리 재귀로 바꾸면 스택 오버플로를 피할 수 있나요?

자바스크립트에서는 보장되지 않는다. ES2015 명세에 proper tail calls가 있지만 사파리만 구현했고 V8과 파이어폭스는 구현하지 않았다. 크롬과 Node.js에서는 꼬리 재귀도 똑같이 프레임을 쌓으니 반복문이나 트램펄린으로 바꿔야 한다.

### 콜 스택 한도는 몇인가요? 늘릴 수 있나요?

호출 횟수가 아니라 바이트 단위 한도라서 프레임 크기에 따라 다르다. Node.js 22에서 빈 재귀 함수는 약 1만 2천 단계, 지역 변수가 많은 함수는 그 절반 정도에서 넘쳤다. Node.js는 `--stack-size`로 바꿀 수 있지만 실제 스레드 스택은 그대로라 크게 올리면 프로세스가 죽을 수 있고, 브라우저는 바꿀 수 없다. 한도를 늘리기보다 깊이를 줄이는 게 맞다.

### await 다음에서 에러가 나면 스택 트레이스는 어떻게 보이나요?

`await`에서 멈춘 함수는 콜 스택에서 내려왔다가 마이크로태스크로 다시 올라오기 때문에 실제 스택에는 원래 호출자가 없다. V8은 Promise를 누가 기다리는지 따라가 `at async 함수명` 줄을 이어 붙여 준다. 다만 `setTimeout` 콜백이나 이벤트 리스너는 예약한 자리가 기록되지 않아서 트레이스가 타이머 내부 함수에서 끝난다.

### React의 Maximum update depth exceeded도 스택 오버플로인가요?

아니다. React가 커밋 뒤 effect에서 상태를 바꾸고 다시 effect가 도는 고리를 50번까지 세다가 넘으면 직접 던지는 에러다. 렌더 도중 `setState`를 반복하면 25번에서 `Too many re-renders`를 던진다. 엔진의 콜 스택과는 상관이 없고, 의존성 배열이나 핸들러 자리의 함수 호출을 고쳐야 한다.
