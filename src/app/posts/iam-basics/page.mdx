리포트 버킷의 파일을 내려받으려는데 `AccessDenied`가 난다. 내 사용자에 붙은 정책을 열어 보면 `s3:GetObject`를 `shop-reports/*`에 허락한다고 분명히 적혀 있다. 동료는 같은 정책으로 잘 받는다. 차이는 파일 경로였다. 내가 받으려던 파일은 `finance/` 아래에 있었고, 같은 정책 아래쪽에 `finance/*`를 막는 `Deny` 문장이 한 줄 있었다.

IAM(Identity and Access Management)은 "누가 어떤 자원에 무슨 동작을 해도 되나"를 요청마다 판정하는 시스템이다. 판정 규칙은 짧다. 명시적인 거부가 있으면 거부, 그다음 허락이 있으면 허락, 아무것도 없으면 거부. 그런데 정책이 사용자, 역할, 버킷, 조직, 세션에 여러 겹으로 붙으면서 이 짧은 규칙이 헷갈려진다. 이 글은 AWS IAM을 기준으로 주체와 정책의 종류, 판정 순서, 역할을 빌리는 STS의 임시 자격 증명, RBAC와 ABAC, 그리고 `AccessDenied`가 났을 때 어디부터 보는지를 정리한다. 판정기를 직접 짜 보는 코드도 있다.

AWS 계정이 없어서 moto 5.2.4 모의 서버에 aws-cli 1.46.1로 요청을 보냈다. moto는 IAM 정책의 Allow·Deny를 실제로 평가하지만 신뢰 정책의 조건 같은 일부는 검사하지 않는다. 모의 서버에서 받은 출력은 그렇다고 밝히고, 실제 AWS에서만 볼 수 있는 출력은 실제 형식을 따른 예시라고 적는다. Pod에 IAM 역할을 주는 IRSA와 Pod Identity는 [EKS 글](/posts/eks-cluster-basics#pod에-aws-권한-주기)에, CI가 키 없이 역할을 빌리는 OIDC 신뢰 정책은 [GitHub Actions와 ECR 글](/posts/github-actions-docker-ecr#신뢰-정책의-sub-조건이-문을-정한다)에 있다. 이 글은 그 아래에 깔린 판정 규칙을 다룬다.

## 요청 하나에 담기는 것

IAM이 판정하는 단위는 API 요청 하나다. `aws s3 cp`를 실행하면 CLI는 `GetObject` 요청에 서명을 붙여 보내고, AWS는 서명에서 누가 보냈는지 알아낸 뒤 요청 컨텍스트를 만든다. 컨텍스트에는 네 가지가 들어간다. 주체(principal, 누가), 동작(action, `s3:GetObject`), 자원(resource, 어떤 객체), 그리고 조건에 쓸 값들(출발 IP, MFA를 썼는지, 시각, 태그)이다.

자원과 주체는 ARN(Amazon Resource Name)이라는 주소로 가리킨다. 역할을 빌린 세션의 ARN을 조각내 보면 이렇다.

판정은 이 컨텍스트를 들고 관련된 정책을 모두 모아서 한다. 그래서 "내 정책에는 허락이 있는데 왜 막히나"라는 질문의 답은 대개 내 정책 밖, 다른 겹에 있다.

## 사람에게는 사용자, 일에는 역할

주체는 크게 셋이다. IAM 사용자는 사람이나 프로그램에 붙는 오래 사는 신원이다. 비밀번호와 액세스 키(`AKIA...`로 시작)를 가진다. 액세스 키는 지우기 전까지 유효해서 [비밀 관리 글](/posts/secrets-management)에서 본 모든 경로로 샐 수 있다.

IAM 역할(role)은 자격 증명을 갖지 않는다. 대신 "누가 이 역할을 빌릴 수 있나"를 적은 신뢰 정책(trust policy)이 있고, 허락된 주체가 빌리면 STS가 수명이 정해진 임시 자격 증명(`ASIA...`로 시작하는 키와 세션 토큰)을 내준다. EC2 인스턴스, Lambda, EKS의 Pod, GitHub Actions 잡, 다른 계정의 사용자, 사내 SSO로 로그인한 직원이 모두 역할을 빌려 일한다.

세 번째는 AWS 서비스 자신이다. CloudTrail이 S3에 로그를 쓰거나 EventBridge가 Lambda를 부를 때 주체는 `cloudtrail.amazonaws.com` 같은 서비스 주체다.

요즘 권하는 모양은 사람도 IAM 사용자를 만들지 않는 것이다. 직원은 IAM Identity Center(옛 AWS SSO)로 로그인해 역할을 빌리고, 프로그램은 실행 환경이 주는 역할을 쓴다. 장기 액세스 키가 남는 곳은 AWS 밖에서 도는데 OIDC를 쓸 수 없는 오래된 도구 정도다. 계정을 만들 때 생기는 루트 사용자는 어떤 정책으로도 제한되지 않으므로(조직의 SCP만 예외) MFA를 걸고 금고에 넣어 둔다. 액세스 키는 만들지 않는다.

## 정책 한 장 뜯어보기

처음 장면의 정책이다. 모의 서버에 이 정책을 만들어 alice에게 붙였다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "ReadReports", "Effect": "Allow", "Action": ["s3:GetObject"], "Resource": "arn:aws:s3:::shop-reports/*" },
    { "Sid": "NoFinance", "Effect": "Deny", "Action": "s3:*", "Resource": "arn:aws:s3:::shop-reports/finance/*" }
  ]
}
```

```bash
# 사용자를 만들고 관리형 정책을 붙인다
aws iam create-user --user-name alice
aws iam create-policy --policy-name reports-read --policy-document file://reports-read.json
aws iam attach-user-policy --user-name alice \
  --policy-arn arn:aws:iam::123456789012:policy/reports-read
```

```text
{
    "User": {
        "Path": "/",
        "UserName": "alice",
        "UserId": "yyde5vgw1iy189p20ju3",
        "Arn": "arn:aws:iam::123456789012:user/alice",

}

        "PolicyName": "reports-read",

        "UpdateDate": "2026-10-21T00:14:17.514210Z"
    }

```

(모의 서버 출력이다. 실제 AWS의 UserId는 `AIDA`로 시작하는 21자다.)

문장(Statement) 하나는 Effect, Action, Resource, 그리고 선택인 Condition으로 이뤄진다. 몇 가지가 실수를 부른다.

`Version`은 날짜처럼 생겼지만 정책 문법의 버전이다. 지금 쓰는 값은 `2012-10-17` 하나다. 빼먹으면 옛 문법(`2008-10-17`)으로 해석되어 `${aws:username}` 같은 정책 변수가 그냥 문자열이 된다. 정책 변수를 쓴 정책이 아무 데도 맞지 않는 이유가 이것일 때가 있다.

Action은 대소문자를 가리지 않고, `*`와 `?` 와일드카드를 쓴다. `s3:Get*`는 `GetObject`, `GetBucketPolicy`를 비롯해 Get으로 시작하는 동작을 모두 연다. 서비스가 새 동작을 추가하면 와일드카드에 자동으로 들어간다는 뜻이기도 하다. Resource는 대소문자를 가리는 ARN 패턴이다. 버킷 자체(`arn:aws:s3:::shop-reports`)와 그 안의 객체(`arn:aws:s3:::shop-reports/*`)는 다른 자원이라, `ListBucket`은 앞쪽에, `GetObject`는 뒤쪽에 걸어야 한다. 둘을 섞어 쓰고 목록이 안 보인다는 문의가 정말 많다.

`NotAction`, `NotResource`는 "이것 빼고 전부"다. `Deny`와 함께 쓰면 유용하지만(`iam:*` 빼고 다 막기), `Allow`와 함께 쓰면 앞으로 생길 모든 동작까지 허락하게 된다.

## 거부가 언제나 이긴다

이제 alice로 세 가지 요청을 보냈다. 모의 서버에서 정책 평가를 켠 상태다.

```bash
# 허락된 경로의 파일을 읽는다
aws s3 cp s3://shop-reports/2026/10.csv - ; echo "exit=$?"
# Deny 문장이 덮는 경로를 읽는다
aws s3 cp s3://shop-reports/finance/salary.csv - ; echo "exit=$?"
# 정책에 없는 동작(삭제)을 한다
aws s3 rm s3://shop-reports/2026/10.csv ; echo "exit=$?"
```

```text
date,orders
2026-10-01,1342
exit=0
download failed: s3://shop-reports/finance/salary.csv to - An error occurred (403) when calling the HeadObject operation: Forbidden
exit=1
delete failed: s3://shop-reports/2026/10.csv An error occurred (AccessDenied) when calling the DeleteObject operation: Access Denied
exit=1
```

두 번째와 세 번째는 똑같이 막혔지만 이유가 다르다. 두 번째는 `ReadReports`가 허락했는데도 `NoFinance`가 명시적으로 거부했다(explicit deny). 세 번째는 아무도 허락하지 않았다(implicit deny). IAM은 기본이 거부라서, 허락이 하나도 없으면 막힌다. 두 번째 줄의 `403 Forbidden`이 `HeadObject`인 건 `aws s3 cp`가 내려받기 전에 객체 정보를 먼저 물어보기 때문이다. HEAD 요청은 응답 본문이 없어서 에러 코드 대신 상태 코드만 보인다.

순서가 상관없다는 게 중요하다. 방화벽 규칙처럼 위에서부터 처음 맞는 것을 따르는 게 아니다. 모든 문장을 모아서 Deny가 하나라도 맞으면 거부, 아니면 Allow가 하나라도 맞으면 허락, 둘 다 없으면 거부다. 그래서 거부 문장은 "어떤 허락을 받더라도 이건 안 된다"는 가드레일로 쓴다.

판정기를 직접 짜 보자. 정책 배열과 요청을 받아 `"ExplicitDeny"`, `"Allow"`, `"ImplicitDeny"` 중 하나를 돌려준다. Action은 대소문자를 무시하고 Resource는 가린다. 조건은 `StringEquals`, `StringLike`, `Bool`만 다루고, 요청에 그 조건 키가 없으면 그 문장은 맞지 않는 것으로 본다.

  // 1) 모든 문장에서 Action·Resource·Condition이 맞는지 본다 (* 와 ? 와일드카드)
  // 2) Deny가 하나라도 맞으면 "ExplicitDeny"
  // 3) Allow가 하나라도 맞으면 "Allow", 아니면 "ImplicitDeny"
  return "ImplicitDeny";
}`}
  solution={`function evaluate(policies, req) {
  const list = (v) => (Array.isArray(v) ? v : [v]);
  const glob = (pattern, value, ci) => {
    const re = "^" + pattern.replace(/[.+^\${}()|[\\]\\\\]/g, "\\\\$&").replace(/\\*/g, ".*").replace(/\\?/g, ".") + "$";
    return new RegExp(re, ci ? "i" : "").test(value);
  };
  const condOk = (cond = {}) =>
    Object.entries(cond).every(([op, kv]) =>
      Object.entries(kv).every(([key, want]) => {
        const have = req.context?.[key];
        if (have === undefined) return false;
        if (op === "StringEquals" || op === "Bool") return list(want).map(String).includes(String(have));
        if (op === "StringLike") return list(want).some((w) => glob(w, String(have), false));
        return false;
      })
    );
  let allowed = false;
  for (const p of policies) {
    for (const s of list(p.Statement)) {
      const actionHit = list(s.Action).some((a) => glob(a, req.action, true));
      const resourceHit = list(s.Resource).some((r) => glob(r, req.resource, false));
      if (!actionHit || !resourceHit || !condOk(s.Condition)) continue;
      if (s.Effect === "Deny") return "ExplicitDeny";
      if (s.Effect === "Allow") allowed = true;
    }
  }
  return allowed ? "Allow" : "ImplicitDeny";
}`}

## 역할을 빌리는 과정

역할을 빌리는 것은 두 개의 문을 지나는 일이다. 빌리려는 쪽의 정책이 `sts:AssumeRole`을 허락해야 하고, 역할의 신뢰 정책이 빌리려는 주체를 받아들여야 한다. 모의 서버에 `report-writer` 역할을 만들었다. 신뢰 정책은 alice가 MFA를 썼을 때만 받는다.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::123456789012:user/alice" },
    "Action": "sts:AssumeRole",
    "Condition": { "Bool": { "aws:MultiFactorAuthPresent": "true" } }
  }]
}
```

```bash
# 신뢰 정책으로 역할을 만들고, 역할에 권한 정책을 붙인다
aws iam create-role --role-name report-writer \
  --assume-role-policy-document file://trust.json --max-session-duration 3600
aws iam put-role-policy --role-name report-writer --policy-name write-2026 \
  --policy-document file://report-writer.json
# alice로 역할을 15분 빌린다
aws sts assume-role --role-arn arn:aws:iam::123456789012:role/report-writer \
  --role-session-name alice-fix-report --duration-seconds 900
```

        "AccessKeyId": "ASIARZPUZDIKOI6CZZDM",
        "SecretAccessKey": "HQ8+...",

(모의 서버 출력이고, 비밀 키와 세션 토큰은 줄였다.) moto는 신뢰 정책의 MFA 조건을 검사하지 않아서 MFA 없이도 빌려졌다. 실제 AWS라면 `--serial-number`와 `--token-code`로 MFA 코드를 함께 보내야 한다. 받은 세 값(키, 비밀 키, 세션 토큰)으로 다시 요청을 보냈다.

```bash

aws s3 cp 10.csv s3://shop-reports/2026/10.csv ; echo "exit=$?"
# alice 사용자 정책에는 있던 읽기
aws s3 cp s3://shop-reports/2026/10.csv - ; echo "exit=$?"
```

마지막 줄이 핵심이다. alice는 원래 이 파일을 읽을 수 있었다. 그런데 역할을 빌린 세션은 읽지 못한다. 역할을 빌리면 원래 권한에 역할 권한이 더해지는 게 아니라, 역할의 권한으로 갈아입는다. 권한을 잠깐 좁히고 싶을 때 역할을 빌리는 이유가 이것이고, "역할을 빌렸더니 원래 되던 게 안 된다"는 혼란도 여기서 생긴다.

다른 회사(SaaS 모니터링 업체 등)에 내 계정의 역할을 빌려줄 때는 신뢰 정책에 `sts:ExternalId` 조건을 건다. 업체가 고객마다 다른 ExternalId를 쓰지 않으면, 다른 고객이 내 역할 ARN을 자기 설정에 적어 업체를 거쳐 내 계정을 읽는 혼동된 대리인(confused deputy) 문제가 생긴다. AWS 서비스가 역할을 빌릴 때는 같은 목적으로 `aws:SourceArn`, `aws:SourceAccount` 조건을 쓴다.

첫 단계가 실무에서 자주 사고를 낸다. 인스턴스에 역할을 잘 붙였는데도 권한이 이상하면, 누군가 디버깅하다 남긴 `~/.aws/credentials`의 장기 키가 먼저 쓰이고 있는 경우가 있다. 그래서 권한 문제는 항상 "지금 누구로 요청하고 있나"부터 확인한다. IMDSv1이 SSRF로 어떻게 털리는지, v2가 무엇을 막는지는 [SSRF 글](/posts/ssrf#imdsv2는-한-겹을-더-둔다)에 실습과 함께 있다. 같은 구조가 EKS에서는 IRSA와 Pod Identity로, CI에서는 OIDC로 바뀐다. 셋 다 "플랫폼이 보증하는 신원을 STS에 내밀고 역할을 잠깐 빌린다"는 같은 뼈대다.

## 역할로 묶을까, 태그로 고를까

권한을 나누는 방식은 두 갈래다. RBAC(역할 기반 접근 제어)는 직무별로 역할을 만들고 권한을 붙인다. `reports-reader`, `reports-writer`, `billing-admin`처럼. 이해하기 쉽고 감사하기 쉽다. 대신 팀과 프로젝트가 늘면 역할도 곱으로 는다. 프로젝트 20개에 직무 3개면 역할 60개이고, 새 프로젝트마다 정책을 고쳐야 한다.

ABAC(속성 기반 접근 제어)는 주체와 자원의 속성(AWS에서는 태그)을 비교하는 정책 하나로 처리한다.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["ec2:StartInstances", "ec2:StopInstances"],
    "Resource": "arn:aws:ec2:*:123456789012:instance/*",
    "Condition": {
      "StringEquals": { "aws:ResourceTag/team": "${aws:PrincipalTag/team}" }
    }
  }]
}
```

`team=search` 태그가 붙은 사람은 `team=search` 태그가 붙은 인스턴스만 켜고 끈다. 새 팀이 생겨도 정책은 그대로이고 태그만 붙이면 된다. SSO에서 넘어오는 사용자 속성을 세션 태그로 받으면 사람마다 역할을 만들 필요도 없다.

ABAC에서는 태그가 곧 권한이다. 누군가 자원에 태그를 붙이거나 바꿀 수 있으면 권한을 스스로 넓힌다. 그래서 `ec2:CreateTags`를 막거나 `aws:RequestTag`, `aws:TagKeys` 조건으로 정해진 태그만 쓰게 하고, 태그를 바꾸는 권한을 따로 관리해야 한다. 또 "누가 이 인스턴스를 끌 수 있나"를 정책만 보고 답하기 어려워진다. 태그를 다 뒤져야 한다. 보통은 큰 틀(계정 분리, 직무 역할)은 RBAC로 잡고, 그 안에서 팀·프로젝트 단위 구분을 ABAC로 하는 식으로 섞는다. 계정 자체를 팀이나 환경별로 나누는 것이 가장 강한 경계라는 것도 기억해 둔다. 계정 사이에는 기본적으로 아무 권한도 없기 때문이다.

## 최소 권한은 한 번에 정해지지 않는다

최소 권한(least privilege)은 일에 필요한 권한만 준다는 원칙이다. 말은 쉬운데, 처음부터 필요한 동작 목록을 정확히 아는 사람은 거의 없다. 그래서 현실에서는 넓게 시작해서 좁혀 간다. 개발 계정에서 서비스 단위(`s3:*`를 특정 버킷에만)로 열어 두고 돌린 뒤, 실제로 쓴 동작만 남긴다.

좁히는 데 쓰는 도구가 있다. IAM 콘솔과 `aws iam generate-service-last-accessed-details`는 역할이 각 서비스를 마지막으로 언제 썼는지 보여 준다. 90일 동안 한 번도 안 쓴 서비스 권한은 지운다. IAM Access Analyzer는 CloudTrail 기록을 읽어 실제로 쓴 동작으로 정책 초안을 만들어 주고, 외부 계정이나 공개로 열린 자원(버킷 정책의 `"Principal": "*"`)을 찾아 준다.

흔한 실수 몇 가지는 이렇다. `"Action": "*", "Resource": "*"`를 임시로 붙이고 잊는다. `iam:PassRole`이나 `iam:CreatePolicyVersion`처럼 권한 상승으로 이어지는 동작을 와일드카드(`iam:*`)에 섞어 준다. 관리형 정책 `ReadOnlyAccess`가 안전하다고 여기지만, 읽기 권한에도 민감한 데이터가 들어간다. 이 정책의 `s3:Get*`만으로 계정 안 모든 버킷의 객체를 읽을 수 있다. 그리고 사람에게 붙인 권한을 프로그램이 같이 쓴다. 사람이 퇴사하면 배치가 멈춘다.

## AccessDenied가 났을 때 보는 순서

현장에서는 대부분 이 순서로 풀린다.

```bash
# 1) 지금 누구로 요청하고 있나 (프로필, 남아 있는 env 키, 빌린 역할)
aws sts get-caller-identity
# 2) 오류 메시지 전체를 읽는다: 어느 겹에서 막혔는지 적혀 있는 경우가 많다
aws ec2 stop-instances --instance-ids i-0abc1234def567890
# 3) 인코딩된 상세 사유를 푼다 (sts:DecodeAuthorizationMessage 권한 필요)
aws sts decode-authorization-message --encoded-message <메시지> --query DecodedMessage --output text | jq .
# 4) 정책 시뮬레이터로 동작별 판정을 본다
aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::123456789012:user/alice \
  --action-names s3:GetObject s3:DeleteObject \
  --resource-arns arn:aws:s3:::shop-reports/finance/salary.csv arn:aws:s3:::shop-reports/2026/10.csv \
  --query 'EvaluationResults[].[EvalActionName,EvalResourceName,EvalDecision]' --output text
```

2번과 4번의 출력은 실제 AWS에서만 나오는 것이라 형식을 따른 예시로 적는다.

```text
An error occurred (UnauthorizedOperation) when calling the StopInstances operation: You are not authorized to perform this operation. User: arn:aws:iam::123456789012:user/alice is not authorized to perform: ec2:StopInstances on resource: arn:aws:ec2:ap-northeast-2:123456789012:instance/i-0abc1234def567890 because no identity-based policy allows the ec2:StopInstances action. Encoded authorization failure message: 4fE0kV...
s3:GetObject	arn:aws:s3:::shop-reports/finance/salary.csv	explicitDeny
s3:GetObject	arn:aws:s3:::shop-reports/2026/10.csv	allowed
s3:DeleteObject	arn:aws:s3:::shop-reports/finance/salary.csv	explicitDeny
s3:DeleteObject	arn:aws:s3:::shop-reports/2026/10.csv	implicitDeny
```

오류 메시지 끝의 이유 문구가 겹을 알려 준다. `because no identity-based policy allows`면 허락이 없는 것이고, `with an explicit deny in a service control policy`면 조직 SCP, `in a permissions boundary`면 권한 경계, `in a resource-based policy`면 버킷 정책 같은 자원 쪽이다. 서비스와 요청 종류에 따라 이유 문구 없이 `Access Denied`만 오기도 한다(앞의 모의 서버 S3 응답처럼). 그때는 CloudTrail에서 `errorCode`가 `AccessDenied`인 이벤트를 찾아 `userIdentity.arn`과 요청 자원을 확인한다. 시뮬레이터는 SCP와 권한 경계까지 반영하지만 자원 기반 정책은 따로 넣어 줘야 하니, 계정을 넘는 접근은 시뮬레이터 결과만 믿지 않는다.

처음 장면은 1번에서 내가 맞는 사용자인 걸 확인하고, 4번 시뮬레이터에서 `explicitDeny`를 보고 끝난다. 남은 일은 그 Deny가 의도된 것인지 묻는 것이다. 대부분은 의도된 것이다.

IAM은 요청 하나를 놓고 모든 겹의 정책을 모아 "Deny 하나면 거부, Allow가 있으면 허락, 없으면 거부"로 판정한다. 역할은 갈아입는 권한이고, STS가 주는 임시 자격 증명은 짧게 살아서 장기 키가 새는 문제를 줄인다. 최소 권한은 쓴 기록을 보고 계속 좁혀 가는 일이다. 이 신원으로 비밀 값을 받는 이야기는 [비밀 관리 글](/posts/secrets-management)에, 쿠버네티스 안의 권한 모델은 [쿠버네티스 RBAC 글](/posts/k8s-rbac)에 있다.

## 면접에서 나올 만한 질문

### IAM 정책은 어떤 순서로 평가되나요?

요청에 관련된 모든 정책을 모은 뒤, 명시적 Deny가 하나라도 맞으면 거부, 아니면 Allow가 하나라도 있으면 허락, 둘 다 없으면 거부(암묵적 거부)한다. 문장의 순서나 정책이 붙은 위치는 상관없다. 여기에 SCP, 권한 경계, 세션 정책 같은 상한 겹이 교집합으로 걸리고, 계정을 넘는 접근은 요청한 쪽의 자격 증명 정책과 자원 쪽의 자원 기반 정책이 모두 허락해야 한다.

### IAM 사용자와 역할은 무엇이 다른가요?

사용자는 비밀번호와 장기 액세스 키를 가진 고정된 신원이고, 역할은 자격 증명이 없고 신뢰 정책이 허락한 주체가 빌려 쓰는 권한 묶음이다. 역할을 빌리면 STS가 기본 1시간짜리 임시 자격 증명을 준다. 그래서 사람은 SSO로 역할을 빌리고, 서버·Pod·CI는 플랫폼이 주는 역할을 쓰는 것이 권장되며 장기 키는 가능한 한 없앤다.

### 역할을 빌리면 원래 권한은 어떻게 되나요?

더해지지 않고 역할의 권한으로 바뀐다. 실습에서 GetObject가 되던 alice가 쓰기 전용 역할을 빌리자 같은 파일을 읽지 못했다. 세션 정책을 넘기면 역할 권한보다 더 좁힐 수도 있다.

### SCP에 Allow를 넣으면 권한이 생기나요?

생기지 않는다. SCP와 권한 경계는 상한을 긋는 정책이라 허락을 주지 못하고, 실제 허락은 자격 증명 기반 정책이나 자원 기반 정책이 줘야 한다. 결과는 두 쪽의 교집합이다. SCP는 조직의 관리 계정에는 적용되지 않는다는 점도 함께 기억한다.

### Condition에서 키가 요청에 없으면 어떻게 되나요?

일반 연산자는 거짓이 되어 그 문장이 맞지 않는다. 그래서 MFA가 있을 때만 허락하는 Allow는 액세스 키 요청에서 맞지 않아 안전하지만, MFA가 false면 막는 Deny를 `Bool`로 쓰면 키가 없는 요청이 빠져나간다. 거부 쪽에는 키가 없을 때도 참으로 보는 `BoolIfExists` 같은 IfExists 연산자를 쓴다.

### RBAC와 ABAC 중 무엇을 고르나요?

직무가 분명하고 수가 적으면 RBAC가 이해와 감사가 쉽고, 팀·프로젝트가 계속 늘면 태그를 비교하는 ABAC가 정책 하나로 확장된다. ABAC는 태그를 바꾸는 권한이 곧 권한 상승이 되므로 태그 변경을 따로 통제해야 하고, 누가 무엇에 접근하는지 정책만으로 답하기 어렵다. 실무에서는 계정과 직무 역할로 큰 틀을 잡고 그 안을 ABAC로 나누는 식으로 섞는다.

### ExternalId는 왜 쓰나요?

제3자에게 역할을 빌려줄 때 생기는 혼동된 대리인 문제를 막으려고 쓴다. 업체가 여러 고객의 역할을 빌리는 구조에서 ExternalId가 없으면, 다른 고객이 내 역할 ARN을 자기 설정에 적어 업체를 거쳐 내 계정에 접근할 수 있다. 신뢰 정책에 고객마다 다른 `sts:ExternalId` 조건을 걸어 업체가 그 값을 함께 보낼 때만 빌려지게 한다.

### AccessDenied가 나면 무엇부터 보나요?

`aws sts get-caller-identity`로 실제 요청 주체부터 확인한다. 남아 있는 환경 변수 키나 다른 프로필이 쓰이는 경우가 많다. 그다음 오류 메시지의 이유 문구로 막힌 겹(SCP, 경계, 자원 정책, 허락 없음)을 확인하고, 인코딩된 메시지는 `decode-authorization-message`로 풀며, 정책 시뮬레이터와 CloudTrail로 동작별 판정을 맞춰 본다.
