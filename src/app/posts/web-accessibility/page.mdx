## 자동 검사를 통과한 가입 폼

회원 가입 폼을 하나 만들고 axe-core 4.10으로 검사했다. axe는 크롬 개발자 도구 확장, Lighthouse, Playwright 테스트 안에서 돌아가는 접근성 검사 엔진이다. WCAG 2.2 A·AA 규칙만 켜고 돌린 결과다.

```text
button-name      critical  1  Buttons must have discernible text
color-contrast   serious   3  Elements must meet minimum color contrast ratio thresholds
image-alt        critical  1  Images must have alternative text
label            critical  1  Form elements must have labels
```

하나씩 고쳤다. 아이콘 버튼에 `aria-label`을 달고, 그림에 `alt`를 넣고, 비밀번호 칸에 `label`을 붙이고, 회색 글자를 진하게 바꿨다. 다시 돌리니 위반이 0개, 통과 18개가 나왔다. 그런데 고친 폼은 이렇다.

```html
<img src="banner.png" alt="배너">
<img src="hero.jpg" alt="이미지">
<input type="email" placeholder="이메일">
<label for="pw">비밀번호</label>
<input type="password" id="pw" style="border: 1px solid #d00">
<span style="color: #c00000">형식이 틀렸습니다</span>
<button type="button" aria-label="button"><svg>…</svg></button>
<div class="btn" onclick="submit()">가입하기</div>
```

`alt="이미지"`는 그림이 무엇인지 아무것도 말해 주지 않는다. 아이콘 버튼의 이름은 영어로 "button"이다. 이메일 칸은 입력을 시작하면 무슨 칸인지 사라진다. 오류 문구는 빨간 글자일 뿐 어느 칸의 오류인지 이어져 있지 않다. 가장 큰 문제는 가입 버튼이 `div`라서 키보드로는 가입할 수 없다는 것이다. axe는 이 중 어느 것도 잡지 못했다.

자동 검사는 출발점이다. 웹 접근성이 무엇을 요구하는지, 어디까지가 숫자로 정해져 있고 어디부터 사람이 판단해야 하는지를 이 폼을 고쳐 가며 따라간다. 태그 고르기는 [시맨틱 HTML](/posts/html-semantics)에, ARIA와 포커스 관리는 [ARIA와 키보드·포커스](/posts/aria-keyboard-focus)에 따로 있다.

## 네 단어로 묶은 기준

웹 접근성의 국제 기준은 W3C의 WCAG(Web Content Accessibility Guidelines)다. 현재 판은 2023년 10월에 나온 WCAG 2.2다. 기준은 네 가지 원칙 아래 정리되어 있고, 머리글자를 따서 POUR라고 부른다. 아래 그림의 각 원칙 밑에 붙은 것이 그 원칙의 대표적인 성공 기준이다.

- 인식 가능: 정보를 어떤 감각으로든 받을 수 있어야 한다. 그림에는 글로 된 대체 텍스트, 영상에는 자막, 글자에는 충분한 대비가 필요하다. 색으로만 정보를 전하면 안 된다(1.4.1).
- 운용 가능: 마우스 없이 키보드만으로 모든 기능을 쓸 수 있어야 하고(2.1.1), 키보드 포커스가 빠져나오지 못하는 곳이 없어야 하며(2.1.2), 포커스가 어디 있는지 보여야 한다(2.4.7). 시간 제한과 깜빡임도 여기 들어간다.
- 이해 가능: 입력칸에 레이블과 안내가 있고(3.3.2), 오류가 나면 무엇이 틀렸는지 글로 알려 주며(3.3.1), 페이지 언어가 지정되어 있어야 한다(3.1.1).
- 견고성: 보조 기술이 요소의 이름, 역할, 상태를 읽을 수 있어야 한다(4.1.2). 직접 만든 컴포넌트가 여기서 가장 많이 걸린다.

처음 폼의 문제를 대 보면 `alt="이미지"`는 1.1.1, 빨간 글자뿐인 오류는 1.4.1과 3.3.1, 키보드로 못 누르는 가입 버튼은 2.1.1과 4.1.2에 걸린다.

## AA는 어디까지인가

성공 기준마다 A, AA, AAA 등급이 붙는다. A는 지키지 않으면 어떤 사람에게는 아예 쓸 수 없는 페이지가 되는 최소한이고, AA는 대부분의 법과 사내 기준이 목표로 삼는 수준이며, AAA는 모든 콘텐츠에 요구하기 어려운 높은 수준이다. "WCAG 2.2 AA를 지킨다"는 말은 A와 AA 기준을 모두 만족한다는 뜻이다. 2.2 기준으로 A가 31개, AA가 24개다.

2.2에서 새로 생긴 기준 중 A·AA는 여섯 개다. 프런트엔드 코드에 바로 영향을 주는 것만 추리면 이렇다.

- 2.4.11 가려지지 않는 포커스(AA): 포커스를 받은 요소가 고정 머리글, 쿠키 배너, 채팅 버튼 같은 것에 완전히 가려지면 안 된다. 고정 머리글이 있으면 `scroll-padding-top`으로 그만큼 여유를 준다.
- 2.5.7 끌기 동작(AA): 끌어서만 할 수 있는 기능(드래그로 순서 바꾸기, 슬라이더)에는 클릭이나 버튼 같은 단일 포인터 대안이 있어야 한다.
- 2.5.8 누르는 대상 크기(AA): 누를 수 있는 대상이 최소 24×24 CSS 픽셀이거나, 그만한 간격을 둬야 한다. 이 블로그가 쓰는 44px 기준은 AAA(2.5.5)에 해당하는 더 넉넉한 값이다.
- 3.3.7 중복 입력(A): 같은 과정에서 이미 입력한 정보를 다시 쓰게 하지 않는다. 배송지와 같은 청구지는 고르기만 하게 한다.
- 3.3.8 접근 가능한 인증(AA): 비밀번호를 외워 치게 하거나 글자를 옮겨 적게 하는 것만으로 인증하지 않는다. 비밀번호 칸에 붙여넣기를 막거나 `autocomplete`를 꺼서 비밀번호 관리자를 막으면 여기에 걸린다.
- 3.2.6 일관된 도움말(A): 도움말 링크나 연락처가 여러 페이지에 있으면 같은 순서 위치에 둔다.

빠진 것도 하나 있다. 4.1.1 구문 분석(Parsing)이 2.2에서 없어졌다. 브라우저가 틀린 HTML을 모두 같은 방식으로 고쳐 읽게 되면서(그 규칙은 [시맨틱 HTML](/posts/html-semantics)에 있다) 따로 둘 이유가 사라졌다. 중복 `id`도 그래서 더는 WCAG 위반 항목이 아니다. 다만 `aria-labelledby`가 가리키는 `id`가 중복이면 엉뚱한 이름이 붙으니 실제 문제는 남는다.

## 대비 비율을 직접 계산한다

1.4.3 대비(최소)는 숫자로 정해진 몇 안 되는 기준이다. 본문 글자는 배경과 4.5:1 이상, 큰 글자는 3:1 이상이어야 한다. 큰 글자는 18pt(24px) 이상이거나 14pt(약 18.66px) 이상의 굵은 글자다. 1.4.11 비텍스트 대비는 입력칸 테두리, 포커스 표시, 의미 있는 아이콘 같은 UI 요소와 그래픽에 3:1을 요구한다. AAA(1.4.6)는 7:1과 4.5:1이다. 로고와 비활성 상태의 컨트롤은 예외다.

대비 비율은 두 색의 상대 휘도(relative luminance)로 계산한다. 상대 휘도는 그 색이 사람 눈에 얼마나 밝게 보이는지를 0(검정)부터 1(흰색) 사이로 나타낸 값이다.

1. 16진수 색을 0~255 정수 R, G, B로 나누고, 각각 255로 나눠 0~1로 만든다.
2. 각 값을 선형 값으로 바꾼다. 값이 0.04045 이하이면 12.92로 나누고, 그보다 크면 `((c + 0.055) / 1.055)`를 2.4제곱한다. 화면 색 값은 감마가 걸려 있어서 밝기와 비례하지 않기 때문이다.
3. 상대 휘도 L = 0.2126 × R + 0.7152 × G + 0.0722 × B. 초록의 무게가 가장 큰 건 사람 눈이 초록에 가장 민감해서다.
4. 대비 비율 = (밝은 쪽 L + 0.05) ÷ (어두운 쪽 L + 0.05). 결과는 1(같은 색)부터 21(검정과 흰색)까지다.

`#767676` 회색 글자를 흰 배경에 놓고 계산해 보자. `0x76`은 118이다.

```text
118 ÷ 255             = 0.4627
(0.4627 + 0.055) ÷ 1.055 = 0.4908
0.4908 ^ 2.4          = 0.1812   ← 회색이라 R=G=B, L = 0.1812
흰색 L                = 1
(1 + 0.05) ÷ (0.1812 + 0.05) = 4.54
```

4.54:1이라 본문 글자로 통과한다. 한 단계 밝은 `#777777`(119)은 같은 계산으로 4.47:1이 나와 탈락한다. 이 경계 때문에 `#767676`이 "흰 배경에서 쓸 수 있는 가장 밝은 회색"으로 자주 쓰인다. 기준은 반올림하지 않는다. 4.47을 4.5로 올려 통과시키면 안 된다. axe도 결과를 보여 줄 때 소수 셋째 자리부터 버린다(2.849는 2.84로 나온다). 처음 폼의 `#999999`는 2.84:1, 오류 문구의 순수한 빨강 `#ff0000`은 3.99:1이었다. 빨강은 밝아 보이지만 휘도의 대부분을 차지하는 초록 성분이 0이라 생각보다 어둡지 않다.

다크 모드도 따로 잰다. 같은 `#767676`을 `#1a1a1a` 배경에 놓으면 3.83:1로 떨어진다. 라이트 모드에서 통과한 회색을 그대로 쓰면 다크 모드에서는 걸린다.

위 계산을 함수로 옮겨 보자. 결과는 axe처럼 소수 둘째 자리까지 남기고 버린다.

    let h = hex.replace("#", "");
    if (h.length === 3) h = h.split("").map((c) => c + c).join("");
    return [0, 2, 4].map((i) => parseInt(h.slice(i, i + 2), 16));

실무에서는 크롬 개발자 도구에서 글자 요소를 고르고 Styles 패널의 색 견본을 누르면 대비 비율과 AA·AAA 통과선이 함께 보인다. 디자인 토큰을 정할 때 이 계산을 한 번에 돌려 표로 만들어 두면 화면마다 다시 잴 필요가 없다. 배경이 사진이나 그라데이션이면 글자 뒤에서 가장 밝은 지점을 기준으로 잰다. 자동 검사가 배경 이미지 위 글자를 "확인 필요"로 넘기는 이유다.

WCAG 3 초안에서는 APCA라는 다른 대비 계산법이 논의되고 있다. 글자 굵기와 크기를 함께 보는 방식이지만 아직 기준이 아니고, 법과 감사는 지금의 2.x 공식을 쓴다.

## 그림에 붙이는 말

`alt`는 그림을 볼 수 없을 때 그 자리에 들어갈 말이다. 무엇을 쓸지는 그림이 페이지에서 하는 일로 정한다.

- 정보를 주는 그림: 그 정보를 짧게 쓴다. 상품 사진이면 `alt="회색 울 코트 앞모습"`. "이미지", "사진" 같은 말은 붙이지 않는다. 스크린리더가 이미 "그림"이라고 말해 준다.
- 꾸미는 그림: `alt=""`로 비워 둔다. 비운 `alt`는 "읽지 말라"는 뜻이라 접근성 트리에서 빠진다. `alt` 속성 자체를 빼면 다르다. 스크린리더에 따라 파일 이름을 읽기도 해서 "banner 언더바 final 점 png" 같은 소리가 난다.
- 링크나 버튼 안의 그림: 그림이 아니라 동작을 쓴다. 돋보기 아이콘 링크라면 `alt="검색"`이다. `alt="돋보기"`는 무엇을 하는 링크인지 말해 주지 않는다.
- 글자가 든 그림: 그림 속 글자를 그대로 쓴다. 할인 배너라면 배너에 적힌 문구다. 가능하면 글자는 그림에 넣지 말고 HTML로 쓴다(1.4.5).
- 차트처럼 복잡한 그림: `alt`에는 요약 한 줄을 쓰고, 자세한 숫자는 그림 바로 옆이나 `figcaption`, 표로 따로 둔다.

인라인 SVG에는 `alt`가 없다. 의미 있는 SVG는 `role="img"`와 `aria-label`을 주고, 꾸미는 SVG는 `aria-hidden="true"`로 숨긴다. CSS `background-image`로 넣은 그림은 접근성 트리에 아예 나타나지 않으니 정보를 주는 그림은 `img`로 넣는다.

같은 그림이라도 맥락이 바뀌면 `alt`가 바뀐다. 상품 목록에서는 "회색 울 코트"면 되지만, 색상 선택 화면에서는 "회색"이 핵심이다. 그래서 `alt`는 CMS에 그림을 올릴 때 한 번 적어 두는 값이 아니라, 그림을 쓰는 자리에서 정하는 값이다.

## 틀렸다는 걸 모두에게 알리기

처음 폼의 오류 문구는 빨간 글자로 칸 옆에 붙어 있었다. 색을 못 구별하는 사람은 그게 오류인지 모르고, 스크린리더 사용자는 그 글자를 듣지 못한 채 다음 칸으로 넘어간다. 오류 안내는 세 가지를 갖춰야 한다. 글로 쓰고(3.3.1), 어떻게 고칠지 알려 주고(3.3.3), 그 칸과 연결한다(1.3.1).

```html
<label for="email">이메일</label>
<input
  id="email"
  type="email"
  autocomplete="email"
  aria-invalid="true"
  aria-describedby="email-error email-hint"
>
<p id="email-hint">회사 메일도 된다</p>
<p id="email-error">@가 빠졌다. 예: name@example.com</p>
```

`aria-invalid="true"`는 칸의 상태를 "잘못됨"으로 바꾸고, `aria-describedby`는 오류 문구를 그 칸의 설명으로 잇는다. Chromium의 접근성 트리에서 이 입력칸을 꺼내 보면 이렇다.

```text
textbox "이메일"  desc="@가 빠졌다. 예: name@example.com 회사 메일도 된다"  invalid="true"
```

`aria-describedby`에 적은 `id` 순서대로 설명이 이어 붙는다. 오류를 먼저 적었으니 오류가 먼저 들린다. 이제 포커스가 이 칸에 오면 스크린리더는 이름, 역할, "잘못됨" 상태, 설명을 차례로 읽는다.

제출했을 때 일어나는 일을 순서대로 보면 아래와 같다. 다음을 누르며 화살표를 따라가 보자.

몇 가지를 더 챙긴다.

- 입력 중에는 오류를 띄우지 않는다. 첫 글자를 치자마자 "형식이 틀렸습니다"가 뜨면 시끄럽다. 칸을 떠날 때(blur)나 제출할 때 검사한다.
- 칸이 많은 폼은 맨 위에 오류 요약을 두고, 각 항목을 해당 칸으로 가는 링크로 만든다. 제출하면 요약으로 포커스를 옮긴다.
- 입력한 값을 지우지 않는다. 비밀번호 하나 틀렸다고 폼을 비우면 처음부터 다시 써야 한다.
- 제출 버튼을 비활성으로 두지 않는다. 비활성 버튼은 포커스도 받지 않아서, 왜 누를 수 없는지 알 길이 없다. 눌리게 두고 누르면 오류를 알린다.
- 브라우저 기본 검증(`required`, `type="email"`)도 접근성 면에서 나쁘지 않다. 메시지 문구와 모양을 바꾸기 어려울 뿐이다. 직접 검증할 거라면 `form`에 `novalidate`를 주고 위 방식으로 알린다.

포커스를 옮기지 않고 결과만 알려야 할 때(장바구니 담기 성공, 검색 결과 개수)는 라이브 리전을 쓴다. `role="status"` 영역에 글자를 바꿔 넣으면 스크린리더가 하던 말을 마치고 읽어 준다. 이건 [ARIA와 키보드·포커스](/posts/aria-keyboard-focus)에서 자세히 본다.

## 움직임과 깜빡임

움직이는 화면은 어떤 사람에게는 어지럼증과 구토를 일으킨다. 전정 기관 장애가 있는 사람이 대표적이다. 운영체제의 "동작 줄이기" 설정을 켠 사용자에게는 CSS의 `prefers-reduced-motion` 미디어 쿼리가 맞게 된다. 이 값으로 애니메이션을 줄이는 방법과 성능 쪽 이야기는 [애니메이션 성능과 접근성](/posts/animation-performance)에 있다.

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```

이 블로그의 그림들도 같은 방식이라, 설정을 켜면 애니메이션이 끝난 모습으로 바로 보인다. 그래서 그림은 마지막 장면만 봐도 뜻이 통하게 만든다.

움직임 줄이기 설정과 상관없이 지켜야 하는 기준도 있다. 저절로 움직이거나 5초 넘게 바뀌는 콘텐츠(자동 넘김 캐러셀, 흐르는 공지)에는 멈춤 버튼이 있어야 한다(2.2.2, A). 1초에 세 번 넘게 번쩍이는 화면은 광과민성 발작을 일으킬 수 있어 금지다(2.3.1, A). 동영상의 자막(1.2.2), 저절로 3초 넘게 재생되는 소리를 끌 방법(1.4.2)도 같은 무게다.

## 색만으로 말하지 않는다

처음 폼의 오류 문구가 빨간 글자였고, 비밀번호 칸은 빨간 테두리로만 틀렸다고 알렸다. 색각 이상은 흔히 남성의 8%, 여성의 0.5% 정도로 알려져 있고(인구 집단마다 비율은 다르다), 그중 가장 흔한 적록 색각 이상은 빨강과 초록을 잘 구별하지 못한다. 흑백으로 인쇄하거나 햇빛 아래에서 화면을 볼 때도 색은 쉽게 사라진다. 1.4.1(색 사용)은 색을 쓰지 말라는 기준이 아니라, 색 말고 다른 단서도 함께 주라는 기준이다.

- 오류: 빨간 테두리에 경고 아이콘과 "형식이 틀렸습니다" 같은 글자를 더한다.
- 본문 속 링크: 색만 다르게 하면 주변 글자와 구별되지 않는다. 밑줄을 두는 게 가장 확실하다. 밑줄을 빼려면 링크 색과 본문 색이 3:1 이상 차이 나고, 마우스를 올리거나 포커스를 받으면 밑줄 같은 다른 표시가 생겨야 한다.
- 차트: 선 색만으로 구분하지 말고 선 끝에 이름표를 달거나 모양(실선·점선, 동그라미·네모 표식)을 다르게 한다.
- 필수 항목: "빨간 글자는 필수"가 아니라 레이블에 "(필수)"를 쓰고 입력칸에 `required`를 준다.

확인은 크롬 개발자 도구의 Rendering 탭에서 "Emulate vision deficiencies"로 적색맹·녹색맹·흑백 화면을 흉내 내 보면 된다. 그 상태에서 무엇이 틀렸는지, 어느 것이 링크인지 알 수 있어야 한다.

## 확대해도 읽혀야 한다

저시력 사용자는 화면을 200%, 400%로 확대해서 쓴다. 노안이 온 사람은 브라우저 기본 글자 크기를 키워 둔다. 이 상황을 다루는 AA 기준이 셋 있다.

- 1.4.4 텍스트 크기 조절: 글자를 200%로 키워도 내용과 기능이 사라지지 않아야 한다.
- 1.4.10 리플로(reflow): 너비 320 CSS 픽셀에서 가로 스크롤 없이 읽혀야 한다. 1280px 모니터에서 400%로 확대한 상태와 같은 너비다. 지도, 큰 데이터 표, 편집 도구처럼 2차원 배치가 꼭 필요한 것은 예외다.
- 1.4.12 텍스트 간격: 사용자가 줄 간격을 글자 크기의 1.5배, 문단 간격을 2배, 자간을 0.12em, 어간을 0.16em으로 넓혀도 글자가 잘리거나 겹치지 않아야 한다. 난독증이 있는 사람이 읽기 도구로 이렇게 바꿔 쓴다.

320px 너비의 Chromium에서 두 가지를 재 봤다. 먼저 카드 묶음에 `width: 960px`를 준 경우와 `max-width: 960px`를 준 경우다.

```text
.wrap { width: 960px }      scrollWidth 968 / clientWidth 320  ← 가로 스크롤이 생긴다
.wrap { max-width: 960px }  scrollWidth 320 / clientWidth 320
```

다음은 높이를 48px로 고정하고 `overflow: hidden`을 준 카드에 1.4.12의 간격을 적용했을 때다.

```text
height: 48px; overflow: hidden   내용 높이 72px, 보이는 높이 48px  ← 한 줄이 잘린다
min-height: 48px                 내용 높이 72px, 보이는 높이 72px
```

고정 너비와 고정 높이가 대부분의 원인이다. 너비는 `max-width`와 유동 그리드로, 높이는 `min-height`로 두고 내용이 늘어날 자리를 남긴다. 글자 크기는 `rem`으로 쓴다. `px`로 고정하면 화면 확대는 되지만, 사용자가 브라우저 설정에서 키운 기본 글자 크기는 무시된다. 확대를 막는 `meta viewport` 설정이 왜 문제인지는 [시맨틱 HTML](/posts/html-semantics)의 "문서 맨 위 세 줄"에 있다.

마우스를 올리거나 포커스를 받으면 나타나는 툴팁과 펼침 내용에도 기준이 있다(1.4.13). `Esc`로 닫을 수 있어야 하고, 확대한 사용자가 툴팁 위로 마우스를 옮겨도 사라지지 않아야 하며, 사용자가 닫거나 벗어나기 전에는 저절로 사라지면 안 된다. 400%로 확대하면 툴팁이 버튼을 덮어서 마우스를 옮기는 순간 사라지는 일이 흔하다.

## 자동 검사가 잡는 것과 못 잡는 것

처음의 axe 결과로 돌아가 보면 경계가 선명하다. 자동 검사는 "있는가, 없는가"와 "숫자가 넘는가"를 잘 잡는다.

- 잡는다: `alt` 없는 `img`, 이름 없는 버튼과 링크, 레이블 없는 입력칸(placeholder는 통과시킨다), 계산 가능한 대비, `lang` 없는 `html`, 잘못된 ARIA 속성 값, 필수 ARIA 자식이 빠진 역할, 양수 `tabindex`(모범 사례 규칙).
- 못 잡는다: `alt`나 `aria-label`의 내용이 맞는지, `div onclick` 같은 키보드로 못 쓰는 요소, 포커스 순서가 화면 흐름과 맞는지, 모달이 포커스를 가두는지, 오류가 칸과 연결됐는지, 색으로만 전한 정보, 움직임과 시간 제한, 자막의 정확도.

axe를 만든 Deque는 자기들의 감사 데이터에서 자동 검사가 찾은 이슈가 전체 이슈 개수의 57% 정도였다고 밝혔다. 성공 기준 개수로 세면 자동으로 판정할 수 있는 기준은 훨씬 적다. 자동 검사 점수가 100점이어도 접근성이 100점인 것은 아니다. Lighthouse의 접근성 감사도 axe-core의 규칙 일부를 돌려 가중 평균한 점수라 같은 한계를 갖는다. 점수 계산 방식은 [Lighthouse는 무엇을 재나](/posts/lighthouse-explained)에 있다.

그래서 검사를 층으로 쌓는다.

1. 코드 작성: `eslint-plugin-jsx-a11y`가 `alt` 누락, `div`의 클릭 핸들러, 잘못된 ARIA 속성을 편집기에서 바로 잡는다.
2. 컴포넌트 테스트: Testing Library의 `getByRole("button", { name: "가입하기" })`로 요소를 찾으면, 역할과 이름이 맞지 않는 컴포넌트는 테스트가 실패한다. 접근성을 따로 검사하지 않아도 기본이 지켜진다.
3. E2E 테스트: `@axe-core/playwright`로 주요 화면을 돌리고 위반이 생기면 CI를 멈춘다.

```ts
import { test, expect } from "@playwright/test";
import AxeBuilder from "@axe-core/playwright";

test("가입 화면에 WCAG A·AA 위반이 없다", async ({ page }) => {
  await page.goto("/signup");
  const results = await new AxeBuilder({ page })
    .withTags(["wcag2a", "wcag2aa", "wcag21aa", "wcag22aa"])
    .analyze();
  expect(results.violations).toEqual([]);
});
```

4. 사람의 확인: 마우스를 치우고 Tab만으로 주요 흐름을 끝까지 해 보고, 스크린리더를 켜서 들어 본다. 자동 검사가 놓친 처음 폼의 문제는 모두 여기서 드러난다.

## 스크린리더를 직접 켜 본다

처음엔 낯설지만 주요 키 몇 개만 알면 10분 안에 내 화면을 들어 볼 수 있다. WebAIM의 스크린리더 사용자 설문을 보면 데스크톱은 윈도우의 NVDA와 JAWS가, 모바일은 iOS VoiceOver가 가장 많이 쓰인다. 개발자는 쓰는 기기에 맞춰 둘 중 하나를 고르면 된다.

macOS VoiceOver는 `⌘ + F5`로 켜고 끈다. VO 키는 `Control + Option`이다.

```text
VO + →        다음 항목으로 이동하며 읽기
VO + Space    지금 항목 누르기
VO + U        로터 열기 (←→로 제목·링크·랜드마크·폼 컨트롤 목록 전환)
VO + ⌘ + H    다음 제목
VO + A        여기서부터 계속 읽기
Control       읽기 멈춤
```

윈도우 NVDA는 무료로 받아 설치하고, 설치할 때 만든 바로 가기 `Ctrl + Alt + N`으로 켠다. NVDA 키는 기본이 `Insert`다. 웹 페이지에서는 탐색 모드(browse mode)라서 글자 키 하나가 이동 명령이 된다.

```text
↓ / ↑          다음 / 이전 줄 읽기
H, 1~6         다음 제목, 다음 수준 n 제목
D              다음 랜드마크
K / F / B / T  다음 링크 / 폼 컨트롤 / 버튼 / 표
NVDA + F7      요소 목록 (링크·제목·랜드마크를 한눈에)
NVDA + Space   탐색 모드와 포커스 모드 전환
Ctrl           읽기 멈춤
```

NVDA의 도구 메뉴에서 "음성 뷰어(Speech viewer)"를 켜면 읽는 말이 창에 글자로도 찍힌다. 소리 없이 확인하거나 버그 리포트에 붙일 때 편하다.

모바일은 iOS의 설정 › 손쉬운 사용 › VoiceOver에서 켠다. 오른쪽으로 쓸면 다음 항목, 두 번 두드리면 누르기, 두 손가락을 돌리면 로터다. 측면 버튼 세 번 누르기에 VoiceOver를 걸어 두면 켜고 끄기 쉽다. 안드로이드는 TalkBack을 같은 식으로 쓴다.

들어 볼 때는 다음을 본다. 페이지를 열면 제목이 읽히는가. 로터나 요소 목록에 랜드마크와 제목이 페이지 구조대로 나오는가. 모든 버튼과 링크가 무엇을 하는지 이름만으로 알 수 있는가("여기", "더보기"가 열 개면 안 된다). 폼에서 오류가 나면 들리는가. 모달이 열리면 모달 안만 읽히는가.

탐색 모드에는 개발자가 알아 둘 함정이 있다. 탐색 모드에서는 스크린리더가 글자 키를 먼저 가져가기 때문에, 페이지에 `H`나 `K` 같은 단축키를 만들어 두면 스크린리더 사용자에게는 동작하지 않는다. 반대로 입력칸이나 `role="application"` 안에서는 포커스 모드로 바뀌어 키가 페이지로 간다. 직접 만든 위젯이 방향키에 반응하지 않는다는 제보는 대개 이 경계 문제다.

## 접근성 제보를 받았을 때

접근성 문제는 대개 "안 된다"는 짧은 제보로 온다. 증상별로 먼저 볼 곳이 정해져 있다.

- "스크린리더가 버튼을 '버튼'이라고만 읽는다": 이름이 비었다. 개발자 도구 Accessibility 탭에서 Name이 비었는지, 아이콘만 있는지 본다.
- "가입 버튼을 키보드로 못 누른다": 요소가 `div`나 `span`인지, `button`이라도 `disabled`인지 본다.
- "오류가 났는지 모르겠다": 오류 문구가 `aria-describedby`로 칸에 이어졌는지, 포커스가 오류 쪽으로 옮겨 갔는지 본다.
- "다크 모드에서 회색 글자가 안 보인다": 라이트 모드 토큰만 대비를 쟀다. 다크 모드 배경으로 다시 계산한다.
- "휴대폰에서 확대가 안 된다": `meta viewport`에 `maximum-scale`이나 `user-scalable=no`가 있다.
- "확대하면 가로로 밀린다", "글자가 잘린다": 고정 너비나 고정 높이가 있다. 320px 너비에서 `document.documentElement.scrollWidth`를 잰다.
- "움직임 때문에 어지럽다": `prefers-reduced-motion`을 처리하지 않았거나, 자동 재생에 멈춤 버튼이 없다.

고친 뒤에는 같은 증상이 다시 생기지 않게 테스트로 묶는다. 이름과 역할은 `getByRole`, 대비와 속성은 axe, 키보드 흐름은 Playwright의 `keyboard.press`와 `toBeFocused()`로 잡을 수 있다. 제보한 사람에게 실제 보조 기술로 다시 확인해 달라고 부탁하는 것까지가 수정이다.

## 법이 요구하는 것

짧게만 적는다. 한국은 장애인차별금지법이 웹 접근성을 차별 금지 대상에 넣었고, 공공기관은 지능정보화 기본법에 따라 웹 접근성을 지켜야 한다. 기준은 WCAG를 바탕으로 만든 한국형 웹 콘텐츠 접근성 지침(KWCAG)이고, 과학기술정보통신부가 지정한 기관이 품질 인증 마크를 준다. EU는 유럽 접근성법(EAA)이 2025년 6월 28일부터 적용되어 전자상거래, 은행, 전자책 같은 민간 서비스까지 범위가 넓어졌다. 미국은 ADA를 근거로 한 웹 접근성 소송이 해마다 수천 건 제기된다. 세부 의무와 적용 대상은 나라와 업종마다 다르니, 실제 대응은 법무와 함께 확인한다. 개발자 입장에서 목표는 대부분 WCAG 2.1 또는 2.2 AA로 같다.

## 다시 가입 폼으로

axe가 0개라고 말한 폼에서 남은 문제를 고치면 이렇다. 배너가 꾸밈이면 `alt=""`, 정보가 있으면 그 내용을 쓴다. 아이콘 버튼의 이름은 "비밀번호 보기"처럼 동작을 쓴다. 이메일 칸에는 보이는 `label`을 둔다. 오류는 `aria-invalid`와 `aria-describedby`로 칸에 잇고, 빨간색과 함께 아이콘이나 글자로도 알린다. 가입 버튼은 `button type="submit"`으로 바꾼다. 이 중 숫자로 잴 수 있는 건 대비 하나뿐이다. 나머지는 Tab을 눌러 보고, 스크린리더로 들어 보고, "이 말만 듣고 무엇인지 알 수 있나"를 묻는 사람의 판단이다.

## 면접에서 나올 만한 질문

### 웹 접근성이란 무엇이고 왜 중요한가요?

장애가 있는 사람을 포함해 누구나 어떤 기기와 보조 기술로든 웹을 인식하고 조작하고 이해할 수 있게 만드는 것이다. 스크린리더, 키보드만 쓰는 사람, 저시력, 색각 이상, 인지 장애, 일시적인 부상까지 대상이 넓다. 한국의 장애인차별금지법이나 EU의 EAA처럼 법적 의무이기도 하고, 대비·레이블·키보드 지원은 모든 사용자의 사용성도 높인다.

### WCAG의 네 원칙은 무엇인가요?

인식 가능, 운용 가능, 이해 가능, 견고성(POUR)이다. 대체 텍스트와 대비는 인식, 키보드 조작과 포커스 표시는 운용, 레이블과 오류 안내는 이해, 보조 기술이 이름·역할·값을 읽을 수 있는 마크업은 견고성에 속한다. 성공 기준마다 A, AA, AAA 등급이 있고 보통 A와 AA를 모두 지키는 것을 목표로 한다.

### 대비 비율 4.5:1은 어떻게 계산하나요?

두 색의 상대 휘도를 구해 (밝은 쪽 + 0.05) ÷ (어두운 쪽 + 0.05)로 나눈다. 상대 휘도는 RGB를 0~1로 바꾸고 감마를 풀어 선형 값으로 만든 뒤 0.2126, 0.7152, 0.0722를 곱해 더한 값이다. 흰 배경의 `#767676`이 4.54로 본문 기준을 넘는 가장 밝은 회색이고, `#777777`은 4.47로 떨어진다. 큰 글자와 UI 요소는 3:1이고, 반올림해서 통과시키면 안 된다.

### alt는 어떻게 써야 하나요?

그림이 그 자리에서 하는 일을 쓴다. 정보를 주면 그 정보를 짧게, 꾸밈이면 `alt=""`로 비우고, 링크나 버튼 안이면 동작을 쓴다. "이미지", "사진" 같은 말은 스크린리더가 이미 알려 주니 붙이지 않는다. `alt` 속성을 아예 빼면 파일 이름을 읽기도 하니, 꾸밈 그림도 빈 값으로 명시한다.

### 폼 오류는 어떻게 알려야 하나요?

색만이 아니라 글로 알리고, 고치는 방법을 함께 쓰고, 그 칸과 연결한다. 칸에 `aria-invalid="true"`를 주고 오류 문구를 `aria-describedby`로 이은 뒤, 첫 오류 칸이나 오류 요약으로 포커스를 옮기면 스크린리더가 상태와 문구를 읽는다. 입력 중에는 띄우지 않고, 입력값을 지우지 않고, 제출 버튼을 비활성으로 막지 않는다.

### axe나 Lighthouse 점수가 100이면 접근성은 충분한가요?

아니다. 자동 검사는 속성이 있는지, 대비 숫자가 넘는지는 잡지만 `alt` 내용이 맞는지, `div` 버튼이 키보드로 눌리는지, 포커스 순서가 맞는지, 오류가 칸과 이어졌는지는 판단하지 못한다. axe가 위반 0개로 판정한 폼도 키보드로 가입할 수 없을 수 있다. 린트, 역할 기반 테스트, axe 자동 검사 위에 키보드와 스크린리더로 직접 써 보는 확인을 더한다.

### 스크린리더 사용자가 페이지 단축키를 못 쓰는 이유는 무엇인가요?

NVDA나 JAWS는 웹 페이지에서 탐색 모드로 동작하며 `H`, `K` 같은 글자 키를 제목·링크 이동에 먼저 쓴다. 그래서 페이지가 만든 한 글자 단축키는 페이지까지 오지 않는다. 입력칸이나 위젯에 포커스가 가면 포커스 모드로 바뀌어 키가 페이지로 전달된다. 단축키는 조합키로 만들고, 같은 기능을 버튼으로도 제공한다.

### WCAG 2.2에서 무엇이 바뀌었나요?

새 기준이 아홉 개 생겼고 그중 A·AA는 여섯 개다. 포커스가 고정 요소에 가려지지 않기(2.4.11), 끌기 동작의 대안(2.5.7), 누르는 대상 최소 24×24 CSS 픽셀(2.5.8), 기억력 테스트에 기대지 않는 인증(3.3.8), 중복 입력 피하기(3.3.7), 일관된 도움말(3.2.6)이다. 브라우저 파싱이 표준화되면서 4.1.1 구문 분석은 빠졌다.
