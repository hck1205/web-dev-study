3Sum을 처음 풀면 대개 두 번 틀린다. 한 번은 세 겹 반복문으로 시간 초과가 나고, 정렬과 투 포인터로 고친 다음에는 `[-2, 0, 2]`가 결과에 두 번 들어가서 틀린다. 같은 값이 여러 개 있을 때 조합을 한 번만 내는 일이 이 문제의 진짜 난이도다.

[LeetCode 15. 3Sum](https://leetcode.com/problems/3sum/)은 [Two Sum II](/posts/leetcode-two-sum-ii)를 반복문 안에 넣은 문제다. 이 글은 세 겹 반복에서 시작해, 정렬 후 해시 집합, 정렬 후 투 포인터, 값별 개수 세기까지 네 가지 풀이를 본다. 그리고 중복을 건너뛰는 코드가 왜 그 자리에 있어야 하는지, 한 줄씩 위치를 바꿔 실제로 틀려 본다. 패턴 설명은 [투 포인터 패턴 글](/posts/two-pointers-pattern)에 있다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 세 수를 고르되 같은 조합은 한 번만

문제를 내 말로 줄이면 이렇다. 정수 배열 `nums`가 주어진다. 서로 다른 세 칸의 값을 더해 0이 되는 조합을 모두 찾는다. 결과에 같은 값 조합이 두 번 들어가면 안 된다. 조합 안의 순서나 결과 목록의 순서는 상관없다.

여기서 "같은 조합"이 무슨 뜻인지가 중요하다. 칸이 다르더라도 값이 같으면 같은 조합이다.

```text
nums = [2, -1, -2, 1, 0, 2, -2]

-2(2번 칸) + 0 + 2(0번 칸)  = 0
-2(2번 칸) + 0 + 2(5번 칸)  = 0   ← 값이 같으니 같은 조합
-2(6번 칸) + 0 + 2(0번 칸)  = 0   ← 이것도 같은 조합
-1 + 0 + 1                  = 0

답: [[-2, 0, 2], [-1, 0, 1]]
```

칸 기준으로 세면 `-2, 0, 2` 조합이 네 번 나온다(-2 두 개 × 2 두 개). 값 기준으로는 한 번이다. 반대로 `[-1, -1, 2]`처럼 같은 값을 두 번 쓰는 조합은 그 값이 배열에 두 개 이상 있을 때만 된다. 한 칸을 두 번 쓸 수는 없다.

풀이를 고를 때 영향을 주는 제약은 길이다. 최대 3000이라 세 수 조합은 약 45억 개, O(n³)은 안 된다. O(n²)이면 900만 번 정도라 넉넉하다. 값은 ±10^5라 세 수를 더해도 `int` 범위 안이다.

## 세 겹으로 다 골라 본다

정의를 그대로 옮기면 반복문 세 개다. 중복 조합은 세 수를 정렬해 문자열 키로 만들고 집합으로 거른다.

```js
// 풀이 1: 모든 세 수 조합
function threeSum(nums) {
  const seen = new Set(), out = [];
  const n = nums.length;
  for (let i = 0; i < n; i++)
    for (let j = i + 1; j < n; j++)
      for (let k = j + 1; k < n; k++) {
        if (nums[i] + nums[j] + nums[k] !== 0) continue;
        const t = [nums[i], nums[j], nums[k]].sort((a, b) => a - b); // 값 순서로 맞춘다
        const key = t.join(",");                                   // "-2,0,2" 같은 키
        if (!seen.has(key)) { seen.add(key); out.push(t); }
      }
  return out;
}
```

세 수를 정렬해 키로 만드는 이유는 `[2, -2, 0]`과 `[-2, 0, 2]`를 같은 조합으로 보기 위해서다. 정렬하지 않으면 순서만 다른 조합이 따로 들어간다.

시간은 O(n³), 공간은 결과와 키 집합 크기만큼이다. 값이 ±10^5인 무작위 배열로 재 봤다.

```text
500 brute 82 77.8ms
brute1500 1872
```

500개에 78ms, 1500개에 1.9초다. 길이가 세 배 늘면 시간은 약 27배 늘어난다. 3000개면 그보다 8배쯤, 15초 안팎일 것으로 짐작한다. 시간 제한을 한참 넘는다.

이 풀이에서 가져갈 생각은 하나다. 중복을 결과에 넣은 뒤에 거르면 키 문자열을 만들고 집합을 관리하는 비용이 따로 든다. 처음부터 중복이 생기지 않게 만들 수는 없을까.

## 하나를 고정하면 Two Sum이 된다

세 수 중 하나를 `a`로 정하면 나머지 둘은 합이 `-a`가 되는 두 수를 찾는 문제다. 바로 Two Sum이다. 바깥 반복문 하나로 `a`를 고르고, 안쪽은 [해시 집합](/posts/ds-hash-map)으로 짝을 찾으면 세 겹이 두 겹이 된다.

중복을 막기 위해 먼저 정렬한다. 정렬하면 같은 값이 나란히 붙어서, "바로 앞과 같으면 건너뛴다" 한 줄로 같은 첫 수를 한 번만 고를 수 있다.

```js
// 풀이 2: 정렬 + 첫 수 고정 + 해시 집합
function threeSum(nums) {
  nums.sort((a, b) => a - b);
  const out = [];
  for (let i = 0; i < nums.length; i++) {
    if (i > 0 && nums[i] === nums[i - 1]) continue; // 같은 첫 수는 한 번만
    const seen = new Set();                         // i 뒤에서 지금까지 본 값
    for (let j = i + 1; j < nums.length; j++) {
      const need = -nums[i] - nums[j];
      if (seen.has(need)) {
        out.push([nums[i], need, nums[j]]);
        while (j + 1 < nums.length && nums[j] === nums[j + 1]) j++; // 같은 셋째 수 건너뛰기
      }
      seen.add(nums[j]);
    }
  }
  return out;
}
```

시간은 바깥 n번 × 안쪽 n번이라 O(n²)이다. 정렬 O(n log n)은 그보다 작아서 묻힌다. 공간은 `seen` 집합이 O(n)이다.

```text
3000 hashWay 16533 305.8ms
```

3000개에 0.3초로 시간 안에 들어온다. 그런데 정렬을 해 놓고도 안쪽에서 해시 집합을 쓰는 건 [Two Sum II](/posts/leetcode-two-sum-ii)에서 본 것과 같은 낭비다. 정렬된 배열의 두 수 합은 투 포인터로 추가 공간 없이 찾을 수 있다. 그리고 셋째 수의 중복을 건너뛰는 위치(찾은 직후에 같은 값 건너뛰기)가 맞는지 따지기도 까다롭다.

## 정렬하고 하나 고정한 뒤 양 끝에서 좁힌다

풀이 2의 해시 집합 자리에 Two Sum II의 투 포인터를 넣는다. 단계로 쓰면 이렇다.

1. 배열을 오름차순으로 정렬한다.
2. `i`를 0부터 옮기며 `nums[i]`를 첫 수로 고정한다. 바로 앞 칸과 값이 같으면 건너뛴다. `nums[i]`가 양수면 반복을 끝낸다.
3. `l = i + 1`, `r = n - 1`에서 시작해 세 수의 합을 본다. 작으면 `l++`, 크면 `r--`.
4. 합이 0이면 답에 담는다. 그다음 `l` 쪽 같은 값과 `r` 쪽 같은 값을 건너뛰고, 양쪽을 한 칸씩 좁힌다.

2번의 "양수면 끝"은 정렬 덕분이다. 첫 수가 고정된 범위에서 가장 작은 수인데, 그게 양수면 뒤에 오는 수들도 모두 양수라 합이 0이 될 수 없다.

```js
// 풀이 3: 정렬 + 첫 수 고정 + 투 포인터
function threeSum(nums) {
  nums.sort((a, b) => a - b);                       // 비교 함수 필수
  const out = [];
  for (let i = 0; i < nums.length - 2; i++) {
    if (nums[i] > 0) break;                          // 가장 작은 수가 양수면 끝
    if (i > 0 && nums[i] === nums[i - 1]) continue;  // 같은 첫 수는 한 번만
    let l = i + 1, r = nums.length - 1;
    while (l < r) {
      const sum = nums[i] + nums[l] + nums[r];
      if (sum < 0) l++;                              // 작다 → 작은 쪽을 키운다
      else if (sum > 0) r--;                         // 크다 → 큰 쪽을 줄인다
      else {
        out.push([nums[i], nums[l], nums[r]]);
        while (l < r && nums[l] === nums[l + 1]) l++; // 같은 둘째 수 건너뛰기
        while (l < r && nums[r] === nums[r - 1]) r--; // 같은 셋째 수 건너뛰기
        l++;
        r--;
      }
    }
  }
  return out;
}
```

시간은 바깥 반복 n번마다 안쪽 투 포인터가 O(n)이라 O(n²)이다. 안쪽에서 같은 값을 건너뛰는 `while`도 `l`과 `r`을 한 방향으로만 움직이니 투 포인터의 O(n) 안에 들어간다. 공간은 결과를 빼면 포인터 몇 개뿐이다. 다만 정렬이 필요한 공간은 언어마다 다르다. V8의 `Array.prototype.sort`는 TimSort라 O(n) 보조 공간을 쓸 수 있고, Java의 `Arrays.sort(int[])`는 듀얼 피벗 퀵정렬이라 재귀 스택 O(log n) 정도다. 면접에서 "공간 O(1)인가요?"라고 물으면 "결과를 빼고 포인터는 O(1), 정렬에 언어별 보조 공간이 든다"고 답하는 게 정확하다.

```text
3000 hashWay 16533 305.8ms
3000 threeSum 16533 28.1ms
```

같은 O(n²)인데 해시 집합 풀이보다 열 배 남짓 빠르다. 해시 집합을 i마다 새로 만들고 값을 넣고 찾는 비용이 사라졌다.

### 중복 건너뛰기가 그 자리에 있어야 하는 이유

이 코드의 중복 처리는 세 군데다. 각각이 무엇을 막는지 보자.

- `nums[i] === nums[i - 1]`이면 건너뛴다. 같은 값으로 첫 수를 다시 고정하면, 안쪽 투 포인터가 앞에서 찾은 조합을 똑같이 다시 찾는다. 그림의 1번 칸 -2가 이 경우다.
- 찾은 직후 `l` 쪽 같은 값을 건너뛴다. 같은 둘째 수로는 셋째 수도 같은 값일 수밖에 없다(합이 정해져 있으니까). 그러니 같은 조합만 또 나온다.
- 찾은 직후 `r` 쪽도 마찬가지다.

반대로, 답을 찾기 전에는 같은 값을 건너뛰지 않는다. 그림에서 -1을 고정했을 때 `r`이 6번(2)에서 5번(2)으로 한 칸 움직인 게 그렇다. 건너뛰어도 틀리지는 않지만, 코드가 복잡해질 뿐 얻는 게 거의 없다. 같은 값이면 합도 같아서 바로 다음 비교에서 같은 방향으로 움직인다.

첫 수의 비교 방향도 중요하다. `nums[i] === nums[i - 1]`(뒤를 돌아본다)가 맞고, `nums[i] === nums[i + 1]`(앞을 내다본다)은 틀리다. 그 이유는 "자주 틀리는 곳"에서 실제로 돌려 본다.

### Python과 Java로 옮기면

```python
from typing import List

def three_sum(nums: List[int]) -> List[List[int]]:
    nums.sort()
    n, out = len(nums), []
    for i in range(n - 2):
        if nums[i] > 0:
            break                                # 가장 작은 수가 양수면 합이 0이 될 수 없다
        if i > 0 and nums[i] == nums[i - 1]:
            continue                             # 같은 첫 수는 한 번만
        l, r = i + 1, n - 1
        while l < r:
            s = nums[i] + nums[l] + nums[r]
            if s < 0:
                l += 1
            elif s > 0:
                r -= 1
            else:
                out.append([nums[i], nums[l], nums[r]])
                while l < r and nums[l] == nums[l + 1]:
                    l += 1
                while l < r and nums[r] == nums[r - 1]:
                    r -= 1
                l += 1
                r -= 1
    return out
```

Python의 `list.sort()`는 비교 함수 없이도 수를 수로 정렬한다. 입력 리스트를 직접 바꾸니, 호출한 쪽의 리스트를 보존해야 하면 `sorted(nums)`로 사본을 쓴다.

```java
class Solution {
    public List<List<Integer>> threeSum(int[] nums) {
        Arrays.sort(nums);
        List<List<Integer>> out = new ArrayList<>();
        for (int i = 0; i < nums.length - 2; i++) {
            if (nums[i] > 0) break;
            if (i > 0 && nums[i] == nums[i - 1]) continue;
            int l = i + 1, r = nums.length - 1;
            while (l < r) {
                int sum = nums[i] + nums[l] + nums[r]; // |값| ≤ 10^5라 int로 충분하다
                if (sum < 0) l++;
                else if (sum > 0) r--;
                else {
                    out.add(Arrays.asList(nums[i], nums[l], nums[r]));
                    while (l < r && nums[l] == nums[l + 1]) l++;
                    while (l < r && nums[r] == nums[r - 1]) r--;
                    l++;
                    r--;
                }
            }
        }
        return out;
    }
}
```

세 언어 모두 같은 결과를 냈다.

```text

[[0, 0, 0]]
[]
[[-1, -1, 2], [-1, 0, 1]]
```

Java에서 주의할 점은 `int[]`와 `Integer`다. `nums`는 `int[]`라 `==`로 값을 비교해도 되지만, 결과를 `List<Integer>`로 꺼낸 뒤 두 원소를 `==`로 비교하면 -128~127 밖에서는 객체 비교가 되어 틀린다. 값 비교는 `equals`다.

## 값마다 개수를 세어 조합한다

값의 종류가 적다면 다른 길도 있다. 배열을 훑어 값별 개수를 세고, 서로 다른 값만 정렬해 `a ≤ b ≤ c` 순서로 조합을 만든다. `a`와 `b`를 고르면 `c = -a - b`는 정해지니, 그 값이 있는지와 개수가 충분한지만 본다.

```js
// 풀이 4: 값별 개수
function threeSum(nums) {
  const cnt = new Map();
  for (const x of nums) cnt.set(x, (cnt.get(x) || 0) + 1);
  const vals = [...cnt.keys()].sort((a, b) => a - b);  // 서로 다른 값만
  const out = [];
  for (let i = 0; i < vals.length; i++) {
    const a = vals[i];
    if (a > 0) break;
    for (let j = i; j < vals.length; j++) {            // b는 a와 같을 수 있다
      const b = vals[j], c = -a - b;
      if (c < b) break;                                // a ≤ b ≤ c 순서만 본다
      if (!cnt.has(c)) continue;
      const need = new Map();                          // 같은 값을 몇 번 쓰나
      for (const v of [a, b, c]) need.set(v, (need.get(v) || 0) + 1);
      if ([...need].every(([v, k]) => cnt.get(v) >= k)) out.push([a, b, c]);
    }
  }
  return out;
}
```

`a ≤ b ≤ c`로 순서를 못 박았기 때문에 같은 조합이 두 번 나올 수가 없다. 중복 건너뛰기 코드가 아예 필요 없다. 대신 `[0, 0, 0]`이나 `[-1, -1, 2]`처럼 같은 값을 여러 번 쓰는 조합은 개수를 확인해야 한다. `0`이 하나뿐인 배열에서 `[0, 0, 0]`을 내면 안 된다.

시간은 서로 다른 값의 수를 u라 하면 O(n + u²)이다. 값의 범위가 좁을 때 빛난다.

```text

3000 R=1000 threeSum 230932 32.1ms
3000 R=1000 counting 230932 199.5ms
3000 R=10 threeSum 61 1.0ms
3000 R=10 counting 61 0.7ms
```

값이 ±10^5로 넓으면(첫 줄) 투 포인터보다 두 배 넘게 느리고, ±1000일 때는 서로 다른 값 쌍이 많아져 여섯 배쯤 느렸다. 값이 ±10(R=10)이면 서로 다른 값이 21개뿐이라 투 포인터보다 조금 빨랐다. 실무에서 "값의 종류가 몇 개냐"를 먼저 묻는 습관이 이런 데서 쓸모 있다. 코딩 테스트에서는 범위가 넓으니 풀이 3을 낸다.

## 자주 틀리는 곳

### 첫 수 중복을 앞을 내다보며 거른다

```js
if (i + 1 < nums.length && nums[i] === nums[i + 1]) continue; // 틀림
```

`[-4, -1, -1, 0, 1, 2]`를 넣으면 이렇다.

```text
forward skip [[-1,0,1]]
```

정답 `[[-1, -1, 2], [-1, 0, 1]]`에서 `[-1, -1, 2]`가 빠졌다. 1번 칸 -1에서 "다음 칸도 -1이니 건너뛴다"를 했는데, `[-1, -1, 2]`는 1번 칸 -1을 첫 수로, 2번 칸 -1을 둘째 수로 써야만 나오는 조합이다. 앞을 내다보며 건너뛰면 같은 값 두 개 중 앞의 것을 버리게 되고, 그 값을 두 번 쓰는 조합을 잃는다. 뒤를 돌아보는 `nums[i - 1]`은 첫 번째 -1은 쓰고 두 번째부터 건너뛰니 이런 일이 없다.

### 중복 건너뛰기를 아예 빼먹는다

```text
noskip [[-2,0,2],[-2,0,2],[-1,0,1]] [[0,0,0],[0,0,0]]
```

세 군데 건너뛰기를 다 빼고 찾은 뒤 `l++`, `r--`만 했더니 `[-2, 0, 2]`가 두 번, `[0, 0, 0]`이 두 번 나왔다. 결과를 집합에 넣어 나중에 거르면 맞기는 하지만, 풀이 1처럼 키를 만드는 비용이 든다.

### 비교 함수 없이 정렬한다

JavaScript의 `sort()`는 비교 함수가 없으면 원소를 문자열로 바꿔 사전 순으로 정렬한다.

```text
default sort [] [-1,-9,10,2]
good [[-9,-1,10]]
```

`[-1, 10, -9, 2]`를 그냥 `sort()`하면 `[-1, -9, 10, 2]`가 된다. 문자열 "-1"이 "-9"보다 앞이고, "10"이 "2"보다 앞이기 때문이다. 정렬이 깨진 배열에서 투 포인터를 돌리니 `[-9, -1, 10]`을 놓치고 빈 배열이 나왔다. 한 자리 수만 있는 예시에서는 우연히 맞게 정렬돼서 안 보이는 버그다.

### 찾은 뒤 포인터를 움직이지 않는다

```js
else {
  out.push([nums[i], nums[l], nums[r]]);
  while (l < r && nums[l] === nums[l + 1]) l++;
  while (l < r && nums[r] === nums[r - 1]) r--;
  // l++; r--; 를 빼먹음

```

건너뛰기 `while`은 "다음 칸이 같은 값이면" 움직인다. 같은 값이 없으면 한 칸도 움직이지 않아서, 다음 반복에서 같은 `l`, `r`로 같은 합 0을 또 찾는다. 결과에 같은 조합이 끝없이 쌓이다가 메모리가 터지거나 시간 초과가 난다. 건너뛰기 뒤의 `l++`, `r--`가 실제로 다음 후보로 넘어가는 줄이다.

## 면접관이 이어서 바꾸는 문제들

### 합이 0이 아니라 target에 가장 가까운 세 수라면

LeetCode 16(3Sum Closest)이다. 같은 틀에서 답을 모으는 대신 "지금까지 가장 가까운 합"을 기억한다. 정확히 같은 합이 나오면 바로 끝낸다. 중복을 건너뛰지 않아도 결과는 같다(값 하나만 돌려주니까).

```js
function threeSumClosest(nums, target) {
  nums.sort((a, b) => a - b);
  let best = nums[0] + nums[1] + nums[2];
  for (let i = 0; i < nums.length - 2; i++) {
    let l = i + 1, r = nums.length - 1;
    while (l < r) {
      const sum = nums[i] + nums[l] + nums[r];
      if (Math.abs(sum - target) < Math.abs(best - target)) best = sum; // 더 가까우면 갱신
      if (sum === target) return sum;
      if (sum < target) l++;
      else r--;
    }
  }
  return best;
}
```


`[4, -3, 1, 9, -6]`, 목표 5에서는 -6 + 1 + 9 = 4가 가장 가깝고, `[0, 0, 0]`, 목표 1에서는 0이다.

### 네 수, k개의 수라면

LeetCode 18(4Sum)이다. 하나를 더 고정하면 된다. 일반화하면 "k개의 합은 수 하나를 고정한 k − 1개의 합"이라는 재귀가 되고, 바닥인 2개의 합에서 투 포인터를 쓴다.

```js
function kSum(nums, target, k) {
  nums.sort((a, b) => a - b);
  const go = (start, k, target) => {
    const res = [];
    if (k === 2) {                          // 바닥: 정렬된 배열의 모든 짝 찾기
      let l = start, r = nums.length - 1;
      while (l < r) {
        const s = nums[l] + nums[r];
        if (s < target) l++;
        else if (s > target) r--;
        else {
          res.push([nums[l], nums[r]]);
          while (l < r && nums[l] === nums[l + 1]) l++;
          while (l < r && nums[r] === nums[r - 1]) r--;
          l++;
          r--;
        }
      }
      return res;
    }
    for (let i = start; i < nums.length - k + 1; i++) {
      if (i > start && nums[i] === nums[i - 1]) continue; // 같은 수로 다시 고정하지 않는다
      for (const rest of go(i + 1, k - 1, target - nums[i])) res.push([nums[i], ...rest]);
    }
    return res;
  };
  return go(0, k, target);
}
```


`[1, 0, -1, 0, -2, 2]`의 4Sum(목표 0), `[2, 2, 2, 2, 2]`의 4Sum(목표 8), 이 글의 예시를 k = 3으로 넣은 결과다. 시간은 O(n^(k−1))이다. 중복 건너뛰기 조건이 `i > 0`이 아니라 `i > start`인 점이 다르다. 재귀 한 층의 시작점 앞은 그 층의 후보가 아니기 때문이다. 4Sum은 값이 ±10^9라 네 수의 합이 `int`를 넘는다. Java라면 `long`으로 더해야 한다.

### 합이 target보다 작은 세 수의 개수라면

LeetCode 259(3Sum Smaller)다. [Two Sum II 글](/posts/leetcode-two-sum-ii)에서 본 "짝 개수 묶어 세기"를 안쪽에 넣는다. 합이 target보다 작으면 `l`과 `l + 1`부터 `r`까지 모두 짝이 되니 `count += r - l` 하고 `l++`, 아니면 `r--`다. O(n²)이다. 개수만 세니 중복 건너뛰기는 하지 않는다.

### 입력이 아주 커서 정렬할 수 없다면

값 범위가 좁다면 풀이 4처럼 개수 배열을 만든다. 값 범위가 넓고 메모리도 부족하면 정렬 대신 외부 정렬을 하거나 값 범위로 나눠 여러 번 훑어야 한다. 같은 문제를 같은 컴퓨터 안에서 여러 번 받는다면, 정렬을 한 번 해 두고 첫 수 고정 루프만 다시 도는 게 가장 큰 절약이다.

## 줄이고, 고정하고, 건너뛴다

3Sum은 정렬해서 같은 값을 붙여 놓고, 수 하나를 고정해 Two Sum II로 줄이는 문제다. O(n²)은 첫 수 n개 × 투 포인터 O(n)에서 나온다. 같은 조합을 한 번만 내는 일은 세 군데의 건너뛰기가 맡는다. 첫 수는 바로 앞 칸과 비교해 같으면 건너뛰고, 둘째와 셋째 수는 답을 찾은 직후에만 같은 값을 건너뛴다. 이 세 줄의 위치가 틀리면 조합이 빠지거나 두 번 나온다. 같은 투 포인터지만 합이 아니라 넓이를 최대로 만드는 [Container With Most Water](/posts/leetcode-container-with-most-water)에서는 "어느 쪽을 움직이나"의 근거가 또 달라진다.

## 면접에서 나올 만한 질문

### 3Sum의 시간 복잡도는 얼마고 왜 그런가요?

O(n²)이다. 정렬에 O(n log n), 첫 수를 고정하는 바깥 반복이 n번, 각각에서 나머지 두 수를 투 포인터로 찾는 데 O(n)이 든다. 중복 건너뛰기도 포인터를 한 방향으로만 움직이니 O(n) 안에 들어간다. 비교만으로 O(n²)보다 크게 빠른 방법은 알려져 있지 않다.

### 왜 먼저 정렬하나요?

두 가지 이유다. 정렬돼야 나머지 두 수를 투 포인터로 추가 공간 없이 찾을 수 있다. 그리고 같은 값이 나란히 붙어서, 바로 앞 칸과 같은지만 보면 중복 조합을 만들지 않을 수 있다. 정렬 비용 O(n log n)은 본체 O(n²)보다 작아서 전체 복잡도를 바꾸지 않는다.

### 중복 조합은 어떻게 막나요?

세 군데에서 막는다. 첫 수는 `nums[i] === nums[i - 1]`이면 건너뛰고, 답을 찾은 직후 `l`과 `r` 쪽의 같은 값을 건너뛴 뒤 한 칸씩 좁힌다. 첫 수 비교를 `nums[i + 1]`로 하면 같은 값을 두 번 쓰는 `[-1, -1, 2]` 같은 조합을 잃는다. 결과를 집합에 넣고 나중에 거르는 방법도 맞지만 키를 만드는 비용이 든다.

### nums[i]가 양수면 왜 멈춰도 되나요?

정렬돼 있으니 `nums[i]`는 고정 범위에서 가장 작은 수다. 그게 양수면 `l`과 `r`이 가리킬 수도 모두 양수라 세 수의 합은 0보다 크다. 그 뒤의 `i`도 마찬가지라 더 볼 필요가 없다. 합이 target인 일반 버전에서는 이 조건이 `nums[i] > target`처럼 바로 바뀌지 않으니(음수 target) 조심해야 한다.

### 해시 집합 풀이와 투 포인터 풀이 중 무엇을 고르나요?

둘 다 O(n²)이지만 투 포인터가 추가 공간이 없고 실제로도 빨랐다. 3000개 입력에서 해시 집합이 0.3초, 투 포인터가 0.03초였다. 해시 집합은 i마다 새 집합을 만들고 넣고 찾는 비용이 든다. 이미 정렬했다면 투 포인터를 쓰지 않을 이유가 없다.

### 공간 복잡도가 O(1)인가요?

결과 목록을 빼면 포인터 몇 개라 O(1)이다. 다만 정렬의 보조 공간이 언어마다 다르다. JavaScript V8의 TimSort는 O(n)까지 쓸 수 있고, Java의 `int[]` 정렬은 퀵정렬 계열이라 O(log n) 정도다. 입력 배열을 직접 정렬해 바꾼다는 점도 함께 말하는 게 좋다.

### 4Sum이나 kSum으로 넓히면 어떻게 되나요?

수 하나를 고정할 때마다 k가 하나 줄어드는 재귀로 짜고, 바닥인 2Sum에서 투 포인터를 쓴다. 시간은 O(n^(k−1))이다. 중복 건너뛰기 조건은 그 층의 시작점 기준(`i > start`)으로 바꿔야 하고, 4Sum처럼 값이 크면 합이 정수 범위를 넘지 않게 `long`으로 더한다.
