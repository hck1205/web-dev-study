상품 카드 300개가 있는 목록에 "화면에 들어오면 서서히 나타나기"를 붙였다. 코드는 단순하다. `scroll` 이벤트마다 카드를 하나씩 돌면서 `getBoundingClientRect()`로 위치를 재고, 화면 안이면 클래스를 붙인다. 눈으로 보기에는 멀쩡한데 성능 트레이스를 떠 보면 스크롤 이벤트 하나에 자바스크립트만 0.5ms씩 쓴다. CPU를 4배 느리게 하면 2.4ms다. 한 프레임 예산이 16.7ms인 걸 생각하면 카드가 더 많아지거나 다른 일이 겹치는 순간 끊긴다.

"보이는지"를 매번 직접 재지 말고 브라우저에게 알려 달라고 하면 된다. 그게 IntersectionObserver다. 이 글은 크로미움 141(Playwright, 헤드리스)에서 관찰자가 실제로 언제, 어떤 값을 들고 부르는지 기록해 본다. threshold가 정확히 그 값에서 불리지 않는 이유, `rootMargin`으로 미리 불러오기, 무한 스크롤 센티널이 한 번 불리고 멈추는 버그까지 다룬다.

스크롤 패턴 전체 지도는 [스크롤 패턴 한눈에 보기](/posts/scroll-patterns-overview)에 있다. 스크롤 양에 비례해 연속으로 움직이는 효과는 [스크롤 기반 애니메이션](/posts/scroll-driven-animations)이 맡고, 이 글은 "어느 지점을 지날 때 한 번 일어나는 일"을 맡는다. 관찰자로 장면을 바꾸는 스크롤리텔링은 [패럴랙스와 스크롤리텔링](/posts/parallax-scrollytelling)에서 이어진다.

## 스크롤마다 300개를 재고 있었다

처음 코드는 이랬다.

```js
const cards = [...document.querySelectorAll(".card")];

addEventListener("scroll", () => {
  for (const c of cards) {
    const r = c.getBoundingClientRect();           // 위치를 잰다
    if (r.top < innerHeight && r.bottom > 0 && !c.classList.contains("in")) {
      c.classList.add("in");                       // 화면 안이면 나타나게 한다
    }
  }
}, { passive: true });
```

같은 화면(390×800, 카드 300개, `.in`이 붙으면 opacity transition)을 관찰자로 바꾼 것과 나란히 재 봤다. 휠을 120px씩 100번 굴리는 동안 성능 트레이스를 뜨고, 콜백 안에서 쓴 시간은 `performance.now()`로 더했다. 두 번째 묶음은 CDP의 `Emulation.setCPUThrottlingRate`로 CPU를 4배 느리게 한 결과다.

```text
CPU x1 scroll + rect  | 콜백 100회 54.5ms | Layout 93회 26.7ms | Style 457회 33.2ms
CPU x1 IO + class     | 콜백 94회 3.4ms | Layout 94회 28.1ms | Style 393회 34.2ms
CPU x1 IO only        | 콜백 94회 1.9ms | Layout 0회 0.0ms | Style 0회 0.0ms
CPU x4 scroll + rect  | 콜백 100회 240.2ms | Layout 93회 129.8ms | Style 454회 129.4ms
CPU x4 IO + class     | 콜백 94회 23.0ms | Layout 93회 136.7ms | Style 387회 169.2ms
CPU x4 IO only        | 콜백 94회 10.4ms | Layout 0회 0.0ms | Style 0회 0.0ms
```

읽는 법이 있다. 자바스크립트 시간(콜백 열)은 리스너가 관찰자보다 16배쯤 크다. 300개를 매번 재기 때문이다. 반면 Layout과 Style은 둘이 비슷하다. 이건 재는 비용이 아니라 클래스를 붙여 transition을 시작하는 비용이라서, 어느 방식으로 감지하든 똑같이 낸다. 세 번째 줄 `IO only`는 클래스를 붙이지 않고 관찰만 한 경우다. 관찰자 자체는 레이아웃도 스타일 계산도 따로 일으키지 않았다.

이 리스너는 그나마 운이 좋은 편이다. 루프 안에서 읽기(`getBoundingClientRect`)와 쓰기(`classList.add`)가 섞여 있지만, 프레임마다 클래스를 새로 붙이는 카드는 몇 개뿐이라 쓰기 뒤에 읽어서 생기는 강제 동기 레이아웃이 몇 번 안 난다. 요소마다 매번 스타일을 쓰는 코드라면 이야기가 다르다. [패럴랙스와 스크롤리텔링](/posts/parallax-scrollytelling)에서 그렇게 짠 패럴랙스가 스크롤 80번에 레이아웃을 2400번 하는 것을 쟀다. 자세한 이야기는 [DOM 기초](/posts/dom-basics)와 [Core Web Vitals](/posts/core-web-vitals)에 있다. 리스너를 꼭 써야 한다면 [디바운스와 스로틀](/posts/debounce-throttle)에서 본 것처럼 rAF 한 번에 묶는다.

## 관찰자에게 맡기면 프레임마다 브라우저가 계산한다

IntersectionObserver는 "이 요소들이 이 영역(root)과 얼마나 겹치는지, 정해 둔 경계(threshold)를 넘으면 알려 달라"는 부탁이다. 브라우저는 매 프레임 화면을 그리는 과정에서 레이아웃이 끝난 뒤 겹침을 한꺼번에 계산한다. 이미 계산된 레이아웃을 쓰니 따로 재지 않는다. 경계를 넘은 요소가 있으면 그 결과를 묶어서 콜백을 태스크로 예약한다.

## 처음 한 번은 무조건 불린다

관찰을 시작하면 요소가 화면 밖에 있어도 콜백이 한 번 불린다. 문서 위에서 1000px 지점에 높이 200px 카드(`card`)를, 그 아래에 화면보다 큰 1600px 블록(`tall`)을 두고 관찰을 걸었다.

```js
const log = [];
const io = new IntersectionObserver((entries) => {
  for (const e of entries) {
    log.push({ id: e.target.id, scrollY, isIntersecting: e.isIntersecting,
      ratio: +e.intersectionRatio.toFixed(3), top: Math.round(e.boundingClientRect.top) });
  }
}, { threshold: [0, 0.5, 1] });
io.observe(document.getElementById("card"));
// tall은 threshold [0, 1]인 다른 관찰자로 본다
```

```text
== observe 직후
{"id":"card","scrollY":0,"isIntersecting":false,"ratio":0,"top":1000}
{"id":"tall","scrollY":0,"isIntersecting":false,"ratio":0}
```

둘 다 `isIntersecting: false`로 불렸다. 처음 기록이 "지금 상태"를 알려 주는 것이다. 그래서 콜백에서 `isIntersecting`을 확인하지 않고 바로 "보였다"고 처리하면, 페이지를 열자마자 모든 이미지를 불러오거나 화면 밖 광고의 노출 이벤트를 보내는 버그가 생긴다.

## threshold는 넘어간 다음에 알려 준다

이제 30px씩 내려 가며 카드의 기록을 모았다. 화면 높이가 800px이니 카드는 `scrollY` 200에서 걸치기 시작하고, 400에서 완전히 들어오고, 1000에서 나가기 시작해서 1200에서 다 빠진다.

```text
== 30px씩 0→1300
{"id":"card","scrollY":210,"isIntersecting":true,"ratio":0.05,"top":790}
{"id":"card","scrollY":300,"isIntersecting":true,"ratio":0.5,"top":700}
{"id":"card","scrollY":420,"isIntersecting":true,"ratio":1,"top":580}
{"id":"card","scrollY":1020,"isIntersecting":true,"ratio":0.9,"top":-20}
{"id":"card","scrollY":1110,"isIntersecting":true,"ratio":0.45,"top":-110}
{"id":"card","scrollY":1230,"isIntersecting":false,"ratio":0,"top":-230}
```

들어올 때 첫 기록의 비율이 0이 아니라 0.05다. 관찰자는 경계를 "지나는 순간"을 잡는 게 아니라, 프레임마다 잰 값이 지난번과 다른 구간에 있으면 알려 준다. 스크롤이 30px씩 뛰었으니 0을 넘은 뒤 처음 잰 값이 10px, 즉 0.05다. 나갈 때도 0.5가 아니라 0.45에서 불렸다. 스크롤이 빠르면 이 차이가 더 커진다. 그러니 "비율이 정확히 0.5일 때"를 기대하는 코드는 쓰면 안 되고, 받은 `intersectionRatio`를 그대로 쓰거나 `>=`로 비교한다.

세 번째 테스트를 보면 `threshold: 1`만 줘도 들어오기 시작할 때(프레임 2) 불린다. 경계 구간은 그대로지만 `isIntersecting`이 바뀌었기 때문이다. "완전히 보일 때만"을 원한다면 콜백에서 `intersectionRatio >= 1`을 다시 확인해야 한다.

마지막 테스트는 실제로 재 본 `tall`의 경우다. 1600px 블록은 800px 화면에 절반까지만 들어갈 수 있어서 비율이 0.5를 넘지 못한다.

```text
== 0에서 2000으로 한 번에
{"id":"tall","scrollY":2000,"isIntersecting":true,"ratio":0.375}
== 100px씩 2000→4000
{"id":"tall","scrollY":3900,"isIntersecting":false,"ratio":0}
```

`threshold: 1`을 걸어 두고 "다 보이면 재생"을 기다리면 이런 요소에서는 영원히 오지 않는다. 큰 요소에는 작은 threshold를 쓰거나, 요소 대신 그 안의 작은 표식 요소를 관찰하거나, `rootMargin`으로 화면 안쪽 선을 만들어 그 선을 넘는 순간을 잡는다.

첫 출력에는 다른 사실도 있다. 0에서 2000으로 한 번에 뛰었더니 `card`의 기록은 하나도 없다. 그 사이 어느 프레임에서도 카드가 화면에 있지 않았기 때문이다. 앵커 링크로 점프하거나 "맨 아래로" 버튼을 누르면 중간 요소는 관찰자 입장에서 지나간 적이 없다. 노출 집계라면 맞는 동작이지만, "지나간 섹션 표시"처럼 순서대로 다 거쳐야 하는 로직이라면 현재 위치를 기준으로 상태를 다시 계산해야 한다.

## 미리 당겨 오는 rootMargin

이미지 지연 로딩은 화면에 들어온 뒤 요청하면 늦다. 사용자는 빈칸을 보게 된다. `rootMargin`으로 영역을 화면 밖까지 넓히면 들어오기 전에 알려 준다. 1500px 지점의 요소를 10px씩 내려 가며 기록했다.

```text
rootMargin 0px         [{"y":0,"is":false,"r":0,"top":1500},{"y":700,"is":true,"r":0,"top":800}]
rootMargin 200px 0px   [{"y":0,"is":false,"r":0,"top":1500},{"y":500,"is":true,"r":0,"top":1000}]
rootMargin -100px 0px  [{"y":0,"is":false,"r":0,"top":1500},{"y":800,"is":true,"r":0,"top":700}]
```

`200px 0px`는 요소 윗변이 화면 아래 200px 바깥(1000)에 닿았을 때 알려 줬다. 0px보다 200px 일찍이다. `-100px 0px`는 화면 아랫변보다 100px 안쪽에 닿았을 때 알려 줬다.

세 줄 모두 `isIntersecting`이 `true`인데 비율 `r`은 0이다. 요소의 윗변이 영역의 아랫변에 딱 닿기만 해도 겹친 것으로 친다. 그래서 "보였는지"를 `intersectionRatio > 0`으로 판단하면 이 순간을 놓친다. 항상 `isIntersecting`을 쓴다. 같은 이유로 높이 0인 요소도 영역 안에 있으면 `isIntersecting: true`, 비율 1로 온다. 반대로 `display: none`인 요소는 상자가 없어서 끝까지 `false`다.

```text
== 높이 0, display:none
{"id":"zero","isIntersecting":true,"ratio":1}
{"id":"hidden","isIntersecting":false,"ratio":0}
```

이미지 하나 미리 불러오기는 요즘 브라우저에서 `<img loading="lazy">`가 대신 해 준다. 브라우저가 거리 기준을 네트워크 상황에 맞춰 정하므로 직접 만든 관찰자보다 나은 경우가 많다. 관찰자가 필요한 것은 배경 이미지, 동영상, 컴포넌트 묶음처럼 속성 하나로 지연시킬 수 없는 것들이다. 지연 로딩의 화면 쪽 선택지는 [로딩 패턴](/posts/loading-patterns)에 정리되어 있다.

<LoadingDemo patterns={["lazy-loading"]} caption="화면에 가까워진 이미지만 받아 온다. 아래쪽은 자리만 잡아 둔다" />

`rootMargin`에는 함정이 하나 있다. 기본 root(화면)를 쓰면서 교차 출처 iframe 안에서 관찰하면 명세상 `rootMargin`이 무시된다. 광고나 임베드 위젯 안에서 "미리 불러오기가 안 된다"면 이걸 의심한다.

## 무한 스크롤의 센티널이 한 번만 불린다

무한 스크롤은 목록 끝에 높이 1px짜리 빈 요소(센티널)를 두고, 그게 보이면 다음 페이지를 불러오는 식으로 만든다.

<LoadingDemo patterns={["infinite-scroll"]} caption="목록 끝이 가까워지면 다음 묶음을 불러와 이어 붙인다" />

흔히 쓰는 코드를 그대로 돌려 봤다. 한 번에 다섯 줄(줄마다 40px)을 불러오고, `rootMargin`으로 아래 300px을 넓혔다. 화면이 800px이니 첫 묶음 200px로는 센티널이 여전히 보인다.

```js
const io = new IntersectionObserver((entries) => {
  if (entries[entries.length - 1].isIntersecting && loads < 20) load();
}, { rootMargin: "0px 0px 300px 0px" });

async function load() {
  loads++;
  await fetchNextPage();          // 여기서는 50ms 기다린 뒤 li 다섯 개를 붙였다
  // 고친 쪽만: 다시 관찰해서 현재 상태를 새로 받는다
  // io.unobserve(sentinel); io.observe(sentinel);
}
io.observe(sentinel);
```

```text
bug {"loads":1,"items":5,"sentinelTop":200}
fix {"loads":6,"items":30,"sentinelTop":1200}
```

고치기 전에는 한 번 불러오고 끝났다. 센티널이 200px 지점, 즉 화면 안에 그대로 있는데도 더 부르지 않는다. 관찰자는 "구간이 바뀔 때"만 알리는데, 센티널은 처음부터 계속 보이는 상태였으니 바뀐 게 없다. 사용자가 스크롤할 내용도 없으니 영원히 멈춘다. 큰 모니터나 첫 페이지가 짧은 목록에서 잘 나는 증상이다.

무한 스크롤에는 이것 말고도 챙길 것이 있다.

- 요청이 진행 중일 때는 다시 부르지 않는다. 콜백이 연달아 오면 같은 페이지를 두 번 붙인다. `loading` 플래그나 요청 취소로 막는다.
- 더 불러올 게 없으면 `disconnect()`한다. 빈 응답을 받고도 계속 요청하는 경우가 흔하다.
- 푸터에 닿을 수 없다. 끝없이 늘어나는 목록 아래의 연락처나 약관 링크는 사실상 숨겨진다. 푸터가 필요하면 "더 보기" 버튼 방식을 섞는다.
- 키보드와 화면 읽기 프로그램 사용자는 새 항목이 붙었는지 모를 수 있다. 붙은 개수를 `aria-live` 영역으로 알려 주는 방법이 있다.

## React에서는 정리까지 한 묶음이다

React에서 관찰자를 붙일 때 실수하는 곳은 정리다. 컴포넌트가 사라졌는데 관찰자가 남아 있으면 떠난 화면의 콜백이 불리고, 요소를 계속 붙잡아 메모리가 샌다. 개발 모드의 Strict Mode는 effect를 일부러 두 번 실행하는데, 정리를 안 하면 관찰자가 둘 생겨서 콜백도 두 번 온다.

```tsx
function useInView<T extends Element>(options?: IntersectionObserverInit) {
  const ref = useRef<T>(null);
  const [inView, setInView] = useState(false);

  useEffect(() => {
    const el = ref.current;
    if (!el) return;
    const io = new IntersectionObserver(([entry]) => {
      if (entry.isIntersecting) {
        setInView(true);
        io.unobserve(entry.target);   // 한 번 보이면 그만 본다
      }
    }, options);
    io.observe(el);
    return () => io.disconnect();      // 사라질 때 반드시 끊는다
  }, [options?.root, options?.rootMargin, options?.threshold]);

  return [ref, inView] as const;
}
```

의존성 배열에 `options` 객체를 통째로 넣으면 렌더링마다 새 객체라서 관찰자를 매번 다시 만든다. 그래서 값 단위로 풀어 넣었다. 배열인 `threshold`는 그래도 매번 새로 만들어지니 컴포넌트 밖 상수로 두는 게 안전하다. 이 블로그의 그림들도 `useInView` 훅으로 화면에 들어온 뒤에 재생을 시작한다.

카드가 수백 개면 카드마다 관찰자를 만들지 말고 관찰자 하나에 `observe`를 여러 번 부른다. 콜백은 한 번에 여러 기록을 묶어서 받는다. 브라우저 입장에서도 관찰자 수보다 관찰 대상 수가 비용을 정한다.

`unobserve`와 `disconnect`의 차이도 짚어 두자. `unobserve(el)`은 요소 하나만 놓고 관찰자는 살아 있다. "한 번 나타나면 끝"인 효과에 쓴다. `disconnect()`는 전부 놓는다. 정리 함수에 쓴다. 놓기 직전에 아직 콜백으로 전달되지 않은 기록이 필요하면 `takeRecords()`로 꺼낸다.

## 관찰자가 안 불릴 때 보는 순서

관찰자 버그는 대개 "안 불린다"나 "너무 일찍 불린다"로 온다. 아래 순서로 좁히면 빠르다.

1. 처음 한 번은 불리는지 본다. 콜백 맨 위에 `console.log(entries)`를 찍는다. 이것도 안 오면 `observe`가 실행되지 않았거나 다른 요소를 관찰 중이다. React라면 ref가 아직 비어 있는 시점에 effect가 돈 경우가 많다.
2. 요소에 상자가 있는지 본다. `display: none`이면 끝까지 `false`다. 조건부 렌더링으로 나중에 생기는 요소라면 생긴 뒤에 관찰해야 한다.
3. threshold가 닿을 수 있는 값인지 본다. 화면보다 큰 요소에 `1`을 걸면 오지 않는다.
4. root를 직접 줬다면 그 요소가 정말 스크롤되는 컨테이너인지, 관찰 대상이 그 자손인지 본다. 스크롤은 바깥 문서가 하는데 root를 안쪽 래퍼로 주면 아무 변화가 없다.
5. 중간 조상의 `overflow: hidden`이 요소를 잘라 내고 있는지 본다. 관찰자는 잘린 영역을 빼고 겹침을 재기 때문에, 잘린 캐러셀 안의 슬라이드는 화면 안에 있어도 보이지 않는 것으로 나온다.
6. "너무 일찍"이라면 처음 기록의 `isIntersecting: false`를 거르지 않았는지, `rootMargin`을 크게 잡았는지 본다.

<ScrollDemo patterns={["scroll-reveal"]} caption="화면에 들어온 카드에 클래스를 붙이고 관찰을 끝낸다. 다시 올라가도 그대로 보인다" />

스크롤 위치를 매번 재지 말고 브라우저가 레이아웃 뒤에 계산한 결과를 받는다. 관찰자는 경계 구간이 바뀔 때만 알려 주고, 처음 한 번은 무조건 알려 준다. 이 두 가지만 기억하면 무한 스크롤이 멈추는 이유, threshold가 정확히 오지 않는 이유, 화면 밖 요소가 "보였다"고 찍히는 이유가 다 풀린다. 이 관찰자로 장면을 바꾸는 방법은 [패럴랙스와 스크롤리텔링](/posts/parallax-scrollytelling)에서 이어 간다.

## 면접에서 나올 만한 질문

### IntersectionObserver를 쓰는 이유가 뭔가요?

요소가 화면이나 특정 영역과 겹치는지를 브라우저가 대신 계산하고, 경계를 넘을 때만 알려 주기 때문이다. scroll 리스너로 `getBoundingClientRect()`를 매번 부르면 스크롤 이벤트마다 모든 요소를 메인 스레드에서 재야 하고, 쓰기와 섞이면 강제 레이아웃까지 일어난다. 관찰자는 프레임마다 이미 계산된 레이아웃으로 겹침을 재고 바뀐 것만 묶어서 콜백으로 준다.

### 콜백은 언제 불리나요?

관찰을 시작한 직후 한 번, 그 뒤로는 겹친 비율이 threshold 구간을 바꾸거나 `isIntersecting`이 바뀔 때다. 계산은 렌더링 과정에서 레이아웃 뒤에 하고, 콜백은 태스크로 나중에 불린다. 그래서 동기적으로 정확한 순간을 잡지 못하고, 빠르게 스크롤하면 0.5 경계인데 0.45 같은 값으로 온다.

### threshold를 1로 줬는데 안 불려요.

요소가 root보다 크면 비율이 1에 닿을 수 없다. 1600px 요소는 800px 화면에서 최대 0.5다. 작은 threshold를 쓰거나, 요소 안의 작은 표식을 관찰하거나, `rootMargin`으로 화면 안쪽 선을 만들어 그 선을 넘는 순간을 본다. 반대로 `threshold: 1`만 줘도 들어오기 시작할 때 한 번 불리니 콜백에서 비율을 다시 확인해야 한다.

### 무한 스크롤이 첫 페이지만 불러오고 멈춰요.

센티널이 처음부터 계속 보이는 상태면 구간이 바뀌지 않아 관찰자가 다시 알리지 않는다. 첫 묶음이 화면을 다 채우지 못하는 큰 화면에서 잘 생긴다. 불러온 뒤 `unobserve`와 `observe`로 다시 관찰해 현재 상태를 받거나, 센티널 위치를 직접 한 번 재서 아직 보이면 또 부른다. 요청 중 중복 호출과 끝났을 때의 `disconnect`도 함께 처리한다.

### rootMargin은 언제 쓰나요?

영역을 화면 밖으로 넓혀서 미리 알림을 받거나, 안쪽으로 줄여서 화면 가운데 선 같은 기준을 만들 때 쓴다. 지연 로딩은 양수로 몇백 px 앞서 받고, 스크롤리텔링은 `-50% 0px -50% 0px`로 가운데 선을 만든다. 교차 출처 iframe 안에서 기본 root를 쓰면 무시된다는 점은 알아 둔다.

### intersectionRatio > 0과 isIntersecting은 같은가요?

같지 않다. 요소가 영역 가장자리에 딱 닿기만 해도 `isIntersecting`은 true인데 비율은 0이다. 높이 0인 요소도 영역 안에 있으면 true로 온다. 보였는지는 `isIntersecting`으로 판단하고, 얼마나 보였는지가 필요할 때만 비율을 쓴다.

### React에서 주의할 점은요?

effect 정리 함수에서 `disconnect()`를 꼭 부른다. 안 하면 사라진 컴포넌트의 콜백이 불리고, Strict Mode에서는 관찰자가 두 개 생긴다. 옵션 객체를 의존성에 통째로 넣으면 렌더링마다 관찰자를 다시 만드니 값 단위로 넣고, 요소가 많으면 관찰자 하나를 공유한다.

### 스크롤 기반 애니메이션과는 어떻게 나눠 쓰나요?

관찰자는 경계를 지날 때 상태를 바꾸는 사건에 맞고, 스크롤 타임라인은 스크롤 양에 연속으로 비례하는 움직임에 맞다. 이미지 로딩, 다음 페이지, 노출 집계, 한 번 나타나고 유지되는 효과는 관찰자다. 진행 막대나 지나가는 동안의 패럴랙스는 CSS 타임라인이고, 관찰자로 흉내 내면 비동기라서 늘 한 박자 늦다.
