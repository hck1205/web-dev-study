<EasyIntro>
  쿠버네티스 클러스터에는 전체를 지휘하는 컨트롤 플레인과 실제로 앱을 돌리는 워커 노드가 있다. kubeadm은 빈 리눅스 서버에 이 컨트롤 플레인을 세우고, 다른 서버를 워커로 붙여 주는 도구다.

  학교 동아리로 치면 kubeadm init은 동아리를 만들고 회원 명부와 도장을 준비하는 일이다. 새 회원은 임시 출입증 하나를 들고 와서 진짜 동아리가 맞는지 도장 모양부터 확인한 다음, 정식 회원증을 발급받아 들어온다.

  지휘하는 쪽이 한 대뿐이면 그 서버가 꺼지는 순간 아무것도 바꿀 수 없다. 그래서 운영에서는 세 대를 두고 과반이 살아 있으면 계속 일하게 만든다. 클라우드 회사의 관리형 서비스는 이 지휘 쪽을 대신 돌봐 주는 대신 요금을 받는다. 직접 세우면 그 돈은 아끼지만 인증서, 업그레이드, 백업을 사람이 챙겨야 한다.
</EasyIntro>

EKS 요금표를 처음 봤을 때 컨트롤 플레인 요금이 시간당 0.10달러, 한 달이면 70달러 남짓이었다. 노드 비용은 따로다. 클러스터를 환경마다 하나씩 두면 이 숫자가 곱해진다. 그러면 EC2 몇 대에 kubeadm으로 직접 세우면 그 돈을 아낄 수 있지 않을까. 이 질문에 답하려면 kubeadm이 무엇을 해 주고, 무엇을 사람에게 남기는지부터 알아야 한다.

이 글은 kubeadm 1.37.0으로 `init`과 `join`이 하는 일을 따라가고, HA 컨트롤 플레인과 노드를 붙이고 빼는 순서를 본 다음, 관리형 서비스가 대신 맡는 것과 남는 것을 비교한다. 기준 OS는 Ubuntu 24.04 LTS다.

실습 환경을 먼저 밝혀 둔다. 이 글을 쓴 컨테이너에는 containerd와 kubelet을 돌릴 수 없어서 실제 클러스터는 세우지 못했다. 대신 진짜 kubeadm 바이너리로 preflight 검사와 `--dry-run`을 돌렸고, 토큰과 join 명령은 kwok으로 띄운 1.37.0 API 서버를 상대로 받았다. 이 셋은 실제 출력이다. `init` 성공 메시지와 `join` 출력처럼 돌릴 수 없었던 것은 공식 문서의 형식만 보이고 그렇다고 표시한다.

컨트롤 플레인 부품이 각각 무엇을 하는지는 [쿠버네티스 구조](/posts/k8s-architecture), kubeadm이 만드는 인증서는 [쿠버네티스 인증서](/posts/k8s-certificates-pki), 세운 뒤 버전을 올리는 법은 [클러스터 업그레이드](/posts/k8s-cluster-upgrade)에서 다룬다.

## 노드마다 먼저 깔아 둘 것

kubeadm은 컨트롤 플레인 부품을 컨테이너로 띄우는 도구라서, 그 컨테이너를 돌릴 런타임과 kubelet이 먼저 있어야 한다. 컨트롤 플레인이 될 서버와 워커가 될 서버 모두에서 똑같이 한다.

```bash
# 1. 커널 모듈과 네트워크 설정 (Pod 트래픽이 iptables를 지나고 노드 사이로 전달되게)
cat <<'EOF' | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF
sudo modprobe overlay
sudo modprobe br_netfilter

cat <<'EOF' | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sudo sysctl --system

# 2. 컨테이너 런타임 (Ubuntu 저장소의 containerd)
sudo apt-get update
sudo apt-get install -y containerd
sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml > /dev/null
# kubelet과 같은 cgroup 드라이버(systemd)를 쓰게 한다
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
sudo systemctl restart containerd

# 3. kubeadm, kubelet, kubectl (마이너 버전마다 저장소 주소가 다르다)
sudo apt-get install -y apt-transport-https ca-certificates curl gpg
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.37/deb/Release.key \
  | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.37/deb/ /' \
  | sudo tee /etc/apt/sources.list.d/kubernetes.list
sudo apt-get update
sudo apt-get install -y kubelet kubeadm kubectl
# apt upgrade가 멋대로 버전을 올리지 않게 묶어 둔다
sudo apt-mark hold kubelet kubeadm kubectl
```

containerd 설정 파일의 `SystemdCgroup` 줄은 containerd 버전에 따라 기본 설정 파일 모양이 달라서 sed가 안 먹힐 수 있다. 바꾼 뒤 `grep SystemdCgroup /etc/containerd/config.toml`로 `true`가 들어갔는지 꼭 확인한다. cgroup 드라이버가 kubelet과 다르면 컨트롤 플레인 Pod가 뜨다가 계속 재시작한다.

swap은 꺼 두는 게 가장 단순하다. kubelet은 기본 설정(`failSwapOn: true`)에서 swap이 켜져 있으면 시작하지 않는다. 최근 버전에는 swap을 쓰게 하는 설정이 있지만 일부러 고른 게 아니라면 끄고 시작한다.

```bash
# swap 끄기 (재부팅 뒤에도 유지하려면 /etc/fstab의 swap 줄을 주석 처리)
sudo swapoff -a
sudo sed -i '/\sswap\s/ s/^/#/' /etc/fstab
```

RHEL 계열이라면 패키지 저장소가 `yum.repos.d`의 rpm 저장소로 바뀌고, SELinux와 firewalld에서 6443, 10250 같은 포트를 열어 줘야 하는 차이가 있다.

## preflight가 먼저 막는다

`kubeadm init`은 아무것도 바꾸기 전에 이 서버가 컨트롤 플레인이 될 수 있는지부터 검사한다. 런타임도 kubelet도 없는 이 실습 컨테이너에서 돌리면 이렇게 멈춘다. 실습 환경의 프록시 설정 때문에 나온 경고 한 줄은 뺐다.

```bash
sudo kubeadm init --kubernetes-version v1.37.0
```


`ERROR CRI` 줄은 containerd 소켓(`/var/run/containerd/containerd.sock`)이 없다는 뜻이고, 그 아래 둘은 kubelet 실행 파일이 없다는 뜻이다. 실제 서버에서 자주 보는 것은 이것 말고도 swap이 켜져 있다는 경고, CPU가 2개 미만이라는 `NumCPU`, 6443 포트를 이미 누가 쓰고 있다는 `Port-6443`이다. 마지막 줄의 `--ignore-preflight-errors`는 이유를 알 때만 쓴다. 런타임 오류를 무시하고 넘어가면 init이 한참 뒤 컨트롤 플레인을 기다리다 시간 초과로 끝날 뿐이다.

## init이 하는 일을 dry-run으로 본다

`--dry-run`을 주면 kubeadm은 파일을 시스템 경로에 쓰지 않고 임시 디렉터리에 만든 뒤 무엇을 하려는지 출력한다. 위의 런타임 오류만 무시하고, HA를 염두에 두고 `--control-plane-endpoint`를 줘서 돌렸다.

```bash
# 결과물을 쓸 디렉터리를 지정하고 init을 흉내만 낸다
export KUBEADM_INIT_DRYRUN_DIR=$PWD/dry
sudo -E kubeadm init --dry-run --kubernetes-version v1.37.0 \
  --control-plane-endpoint cp.lab.internal:6443 \
  --ignore-preflight-errors=all
```

출력은 700줄이 넘는다. 단계를 알리는 줄만 골라 보면 init이 하는 일이 순서대로 보인다.

순서를 풀어 쓰면 이렇다. 먼저 CA와 인증서를 만들고(certs), 부품마다 API 서버에 접속할 kubeconfig를 쓴다(kubeconfig). 그다음 etcd, API 서버, 컨트롤러 매니저, 스케줄러를 static Pod 매니페스트로 `/etc/kubernetes/manifests`에 놓는다. kubelet은 이 디렉터리를 지켜보다가 파일이 생기면 그 Pod를 직접 띄운다. API 서버가 아직 없는데도 컨트롤 플레인이 뜰 수 있는 이유가 이것이다. API 서버가 살아나면 클러스터 설정을 ConfigMap으로 올리고, 이 노드에 control-plane taint를 붙이고, 워커가 들어올 때 쓸 부트스트랩 토큰을 만든다.

첫 줄의 인증서 이름 목록에 `cp.lab.internal`이 들어 있는 걸 봐 둔다. `--control-plane-endpoint`로 준 이름이 API 서버 인증서에 박힌다. 나중에 HA로 바꾸려고 이 이름을 새로 만들면 인증서를 다시 찍어야 하므로, 지금 한 대로 시작하더라도 처음부터 DNS 이름 하나를 정해 주는 편이 낫다.

만들어진 etcd 매니페스트와 API 서버 매니페스트에서 etcd 관련 플래그만 꺼내 봤다.

```bash
grep -E -- "--(initial-cluster|listen-client-urls|data-dir)=" dry/etcd.yaml
grep -E -- "--etcd-servers=" dry/kube-apiserver.yaml
```

```text
    - --data-dir=/var/lib/etcd
    - --initial-cluster=vm=https://192.0.2.2:2380
    - --listen-client-urls=https://127.0.0.1:2379,https://192.0.2.2:2379
    - --etcd-servers=https://127.0.0.1:2379
```

API 서버가 `127.0.0.1:2379`, 같은 노드의 etcd를 바라본다. kubeadm의 기본값은 이렇게 etcd를 컨트롤 플레인 노드 위에 함께 올리는 stacked etcd다. 이 선택이 HA에서 무엇을 뜻하는지는 뒤에서 본다.

기본값 몇 개는 `kubeadm config print init-defaults`로 직접 볼 수 있다. 운영에서 신경 쓸 줄만 남겼다.

```bash
kubeadm config print init-defaults
```

```text
bootstrapTokens:
- groups:
  - system:bootstrappers:kubeadm:default-node-token
  token: abcdef.0123456789abcdef
  ttl: 24h0m0s
...
```

부트스트랩 토큰은 24시간, CA는 10년(87600h), 나머지 인증서는 1년(8760h)이다. 1년짜리 인증서는 업그레이드할 때 함께 갱신되므로, 1년 넘게 업그레이드를 안 한 클러스터는 어느 날 아침 API 서버가 인증서 만료로 멈춘다. 그 장면과 갱신 방법은 [쿠버네티스 인증서](/posts/k8s-certificates-pki)에 있다.

## init이 끝나면 할 일

실제 서버에서 init이 끝나면 이런 안내가 나온다. 이 부분은 실습에서 받을 수 없어서 공식 문서에 실린 형식을 옮긴다.

```text
Your Kubernetes control-plane has initialized successfully!

To start using your cluster, you need to run the following as a regular user:

  mkdir -p $HOME/.kube
  sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
  sudo chown $(id -u):$(id -g) $HOME/.kube/config

You should now deploy a Pod network to the cluster.
Run "kubectl apply -f [podnetwork].yaml" with one of the options listed at:
  /docs/concepts/cluster-administration/addons/

You can now join any number of machines by running the following on each node
as root:

  kubeadm join <control-plane-host>:<control-plane-port> --token <token> --discovery-token-ca-cert-hash sha256:<hash>
```

여기서 처음 하는 실수가 CNI를 깔지 않고 노드를 보는 것이다. kubeadm은 Pod 네트워크를 설치하지 않는다. CNI 플러그인(Calico, Cilium, Flannel 등)을 올리기 전까지 노드는 `NotReady`이고 CoreDNS Pod는 `Pending`에 머문다. CNI가 무엇을 하는지는 [Pod 네트워크와 CNI](/posts/k8s-cni-pod-network)에서 다룬다. CNI가 쓸 Pod 대역을 따로 정해야 하는 플러그인이라면 init 때 `--pod-network-cidr`을 함께 준다.

`admin.conf`는 클러스터 관리자 권한을 가진 kubeconfig라서 사람마다 나눠 주면 안 된다. 사람에게 권한을 주는 방법은 [RBAC](/posts/k8s-rbac)를 따른다.

## 워커는 토큰 하나로 들어온다

init 출력의 마지막 줄, `kubeadm join` 명령에는 값이 두 개 들어 있다. 토큰과 CA 인증서 해시다. kwok으로 띄운 1.37.0 API 서버를 상대로 토큰을 새로 만들어 봤다.

```bash
# 1시간짜리 부트스트랩 토큰을 만들고 join 명령을 출력한다 (컨트롤 플레인에서)
sudo kubeadm token create --print-join-command --ttl 1h
kubeadm token list
```

```text
kubeadm join 127.0.0.1:32764 --token 08nvwo.ili5e9e77pmkit4t --discovery-token-ca-cert-hash sha256:95dcf334e0f57e458a4d7075ad93a39006c80d39ecd28df5ddddf8a5d0566832
```

```text
TOKEN                     TTL         EXPIRES                USAGES                   DESCRIPTION                                                EXTRA GROUPS
08nvwo.ili5e9e77pmkit4t   59m         2026-10-23T20:30:24Z   authentication,signing   <none>                                                     system:bootstrappers:kubeadm:default-node-token
```

토큰은 점으로 나뉜 두 부분이다. 앞의 `08nvwo`는 토큰 ID, 뒤의 16글자는 비밀이다. 실체는 `kube-system`에 있는 Secret 하나다.

```bash
kubectl -n kube-system get secret bootstrap-token-08nvwo -o yaml
```

```text
apiVersion: v1
data:
  auth-extra-groups: c3lzdGVtOmJvb3RzdHJhcHBlcnM6a3ViZWFkbTpkZWZhdWx0LW5vZGUtdG9rZW4=
  expiration: MjAyNi0xMC0yM1QyMDozMDoyNFo=
  token-id: MDhudndv
  token-secret: aWxpNWU5ZTc3cG1raXQ0dA==
  usage-bootstrap-authentication: dHJ1ZQ==
  usage-bootstrap-signing: dHJ1ZQ==
kind: Secret
metadata:
  name: bootstrap-token-08nvwo
  namespace: kube-system
type: bootstrap.kubernetes.io/token
```

`expiration`을 base64로 풀면 `2026-10-23T20:30:24Z`다. 이 시각이 지나면 토큰 정리 컨트롤러가 Secret을 지운다. 쓰임새는 두 가지다. `authentication`은 새 노드가 이 토큰으로 API 서버에 로그인하는 데, `signing`은 아래에서 볼 cluster-info에 서명하는 데 쓴다.

해시는 클러스터 CA 인증서 공개 키의 SHA-256이다. 공식 문서에 나오는 openssl 명령으로 직접 계산하면 join 명령의 값과 같다.

```bash
# CA 인증서의 공개 키(SubjectPublicKeyInfo)를 DER로 뽑아 SHA-256을 낸다
openssl x509 -pubkey -in /etc/kubernetes/pki/ca.crt \
  | openssl rsa -pubin -outform der 2>/dev/null \
  | openssl dgst -sha256 -hex | sed 's/^.* //'
```


## 컨트롤 플레인을 세 대로

컨트롤 플레인이 한 대면 그 서버를 재부팅하는 동안 `kubectl`이 안 되고, 컨트롤러가 멈추니 죽은 Pod도 다시 뜨지 않는다. 이미 돌던 Pod는 계속 돌지만 아무것도 바꿀 수 없다. 운영 클러스터는 보통 컨트롤 플레인을 세 대 둔다.

필요한 것은 세 가지다.

1. API 서버 앞의 로드 밸런서. `--control-plane-endpoint`로 준 이름이 이 로드 밸런서를 가리킨다. 클라우드라면 NLB 같은 L4 로드 밸런서, 온프레미스라면 HAProxy와 keepalived 한 쌍이나 kube-vip를 쓴다. 헬스 체크는 6443의 `/readyz`를 본다.
2. 첫 번째 노드에서 `--upload-certs`를 준 init. 다른 컨트롤 플레인이 같은 CA와 키를 써야 하니 그걸 옮길 방법이 필요하다.
3. 나머지 노드에서 `--control-plane`을 붙인 join.

```bash
# 첫 번째 컨트롤 플레인 (cp1)
sudo kubeadm init --control-plane-endpoint cp.lab.internal:6443 --upload-certs

# 인증서를 다시 올리고 새 키를 받아야 할 때 (cp1에서)
sudo kubeadm init phase upload-certs --upload-certs

# 나머지 컨트롤 플레인 (cp2, cp3)
sudo kubeadm join cp.lab.internal:6443 --token <토큰> \
  --discovery-token-ca-cert-hash sha256:<해시> \
  --control-plane --certificate-key <인증서 키>
```

`--upload-certs`는 CA와 서비스 어카운트 키 같은 파일을 `kubeadm-certs`라는 Secret에 암호화해 올리고, 그 암호화 키(certificate key)를 출력한다. 이 키는 32바이트를 16진수로 쓴 값이고 `kubeadm certs certificate-key`로 직접 만들어 볼 수 있다.

```bash
kubeadm certs certificate-key
```

```text
0632d3efa90bff2019712e4f4b87a6e75574c4881f48063dccfa07329c22fe77
```

`kubeadm-certs` Secret은 2시간 뒤 지워진다. dry-run에서 `--upload-certs`를 줬을 때 kubeadm은 이 Secret의 수명을 관리할 토큰을 따로 만들었다.

```text
[upload-certs] Storing the certificates in Secret "kubeadm-certs" in the "kube-system" Namespace
...
data:
  description: UHJveHkgZm9yIG1hbmFnaW5nIFRUTCBmb3IgdGhlIGt1YmVhZG0tY2VydHMgc2VjcmV0
  expiration: MjAyNi0xMC0yM1QyMToyNjoyMlo=
```

`description`을 풀면 "Proxy for managing TTL for the kubeadm-certs secret", `expiration`을 풀면 `2026-10-23T21:26:22Z`로 명령을 돌린 19시 26분에서 정확히 2시간 뒤다. 클러스터의 모든 인증서를 서명할 수 있는 CA 키가 Secret에 오래 남아 있지 않게 하려는 장치다. 그래서 2시간 안에 cp2, cp3을 붙이지 못했다면 `init phase upload-certs`로 다시 올리고 새 키를 받는다.

## stacked etcd와 외부 etcd

kubeadm HA에는 두 가지 모양이 있다. 기본인 stacked etcd는 컨트롤 플레인 노드마다 etcd를 함께 올리고, 각 API 서버가 같은 노드의 etcd만 바라본다(위 dry-run의 `--etcd-servers=https://127.0.0.1:2379`). 외부 etcd는 etcd를 별도 서버 세 대(또는 다섯 대)에 따로 두고 API 서버들이 그 클러스터 전체를 바라본다.

stacked는 서버가 세 대로 끝나고 kubeadm이 etcd 멤버 추가·제거까지 알아서 해 준다. 대신 노드 하나를 잃으면 API 서버와 etcd 멤버를 함께 잃는다. 외부 etcd는 서버가 여섯 대로 늘고 etcd 인증서와 멤버 관리를 직접 해야 하지만, API 서버 부하와 etcd 디스크 I/O가 서로 방해하지 않고 장애가 한쪽에만 머문다. 대부분의 클러스터는 stacked로 충분하고, 노드와 객체가 아주 많아 etcd 지연이 문제가 되거나 etcd를 따로 운영하는 팀이 있을 때 외부를 고른다.

어느 쪽이든 etcd 멤버 수는 홀수로 둔다. etcd는 Raft로 과반이 동의해야 쓰기를 끝내는데([Raft 합의](/posts/raft-consensus)), 과반은 `floor(n/2) + 1`이다. 3대의 과반은 2라서 1대가 꺼져도 되고, 4대의 과반은 3이라서 역시 1대만 꺼져도 된다. 4대는 3대보다 버티는 수는 같은데 고장 날 서버만 하나 많다. 2대는 1대보다 나쁘다. 둘 중 하나만 꺼져도 멈추기 때문이다.

아래에서 직접 계산해 본다. 멤버 수와 꺼진 수를 받아 쓰기가 되는지 돌려준다.

<CodePlayground
  caption="etcd 멤버 n대 중 down대가 꺼졌을 때 쓰기가 되나"
  functionName="canWrite"
  initialCode={`function canWrite(members, down) {
  // 과반 = floor(members / 2) + 1
  // 살아 있는 멤버가 과반 이상이면 true

}`}
  solution={`function canWrite(members, down) {
  const quorum = Math.floor(members / 2) + 1;

5대는 2대까지 버티지만 쓰기마다 복제할 곳이 늘어 지연이 조금 늘어난다. 영역(AZ) 세 곳에 1대씩 두는 3대가 가장 흔한 선택이다. 2개 영역에 2대와 1대를 두면, 2대가 있는 영역이 통째로 끊기는 순간 과반을 잃는다. etcd를 되돌리는 법은 [etcd 백업과 복원](/posts/k8s-etcd-backup)에 있다.

## 노드를 빼는 순서

워커를 하나 빼는 순서는 비우기 → 정리 → 객체 삭제다.

```bash
# 1. 새 Pod가 오지 않게 막고 기존 Pod를 다른 노드로 내보낸다 (컨트롤 플레인에서)
kubectl drain worker-3 --ignore-daemonsets --delete-emptydir-data

# 2. 노드에서 kubeadm이 만든 파일과 kubelet 설정을 지운다 (worker-3에서)
sudo kubeadm reset

# 3. reset이 지우지 않는 것들을 직접 정리한다 (worker-3에서)
sudo rm -rf /etc/cni/net.d
sudo iptables -F && sudo iptables -t nat -F && sudo iptables -t mangle -F && sudo iptables -X

# 4. 클러스터에서 Node 객체를 지운다 (컨트롤 플레인에서)
kubectl delete node worker-3
```

drain이 PodDisruptionBudget에 막히는 경우와 플래그가 포기하게 하는 것은 [노드 점검](/posts/k8s-node-maintenance)에서 다뤘다. `kubeadm reset`은 CNI 설정과 iptables 규칙을 남겨 두니, 같은 서버를 다른 클러스터에 붙일 생각이면 3번을 빼먹지 않는다. 남은 규칙 때문에 새 클러스터에서 Pod 통신이 이상하게 끊기는 일이 생긴다.

<Callout kind="warning">
  3번의 iptables 초기화는 그 서버의 방화벽 규칙도 함께 지운다. ufw나 직접 건 규칙이 있는 서버라면 먼저 `sudo iptables-save > ~/iptables.bak`으로 떠 두고, 원격 접속 중이라면 기본 정책이 DROP인지 `sudo iptables -S | head -3`으로 확인한 뒤 돌린다. 되돌릴 때는 `sudo iptables-restore < ~/iptables.bak`이다.
</Callout>

컨트롤 플레인 노드를 뺄 때는 etcd 멤버도 함께 빠져야 한다. stacked etcd라면 그 노드에서 `kubeadm reset`이 자기 etcd 멤버를 클러스터에서 제거하는 단계를 실행한다. 노드가 이미 죽어서 reset을 돌릴 수 없다면 남은 노드에서 `etcdctl member remove`로 직접 지워야 한다. 이걸 놓치면 etcd는 없는 멤버를 계속 셈에 넣는다. 3대 클러스터에서 죽은 멤버를 안 지운 채 하나가 더 죽으면 실제로는 1대가 살아 있어도 과반을 잃는다.

## 관리형 서비스가 대신 맡는 것

EKS, GKE, AKS가 해 주는 일은 거의 위에서 사람이 하던 컨트롤 플레인 쪽 일이다.

- 컨트롤 플레인 가용성. API 서버와 etcd를 여러 영역에 나눠 띄우고, 앞의 로드 밸런서까지 제공한다. 사용자는 etcd를 보지도 못한다.
- 인증서와 etcd 백업. 컨트롤 플레인 인증서 만료나 etcd 스냅숏을 사람이 챙기지 않는다.
- 컨트롤 플레인 업그레이드. 버튼이나 명령 하나로 API 서버 버전을 올린다. 마이너를 한 칸씩만 올릴 수 있다는 규칙은 똑같다.
- 클라우드 인증 연동. 사람과 Pod가 클라우드 IAM으로 클러스터와 클라우드 API에 접근하게 엮는다. EKS가 이걸 어떻게 하는지는 [EKS 기본](/posts/eks-cluster-basics)에 있다.

남는 것도 분명하다. 노드는 여전히 내 몫이다(관리형 노드 그룹이 교체 절차를 대신해 주긴 한다). EKS Fargate나 GKE Autopilot처럼 노드까지 맡기는 모드도 있지만 DaemonSet이나 특권 컨테이너 같은 제약이 생긴다. CNI, CoreDNS, kube-proxy 같은 애드온 버전, 노드 업그레이드, 지원 기간 안에 버전을 따라가는 일, 그 위에 올린 Ingress·모니터링·워크로드는 모두 사용자가 한다.

요금은 이 글을 쓰는 시점에 공개된 요금표 기준이고 바뀔 수 있으니 직접 확인한다. EKS는 표준 지원 기간의 클러스터가 시간당 0.10달러이고, 표준 지원이 끝난 버전을 연장 지원으로 계속 쓰면 시간당 0.60달러로 뛴다. GKE도 클러스터 관리 요금이 시간당 0.10달러이지만 결제 계정마다 영역 클러스터나 Autopilot 클러스터 하나 분량을 상쇄하는 무료 크레딧이 있다. AKS는 컨트롤 플레인 요금이 없는 Free 등급과, SLA를 붙이는 대신 시간당 0.10달러를 받는 Standard 등급이 있다.

## 직접 운영하면 무엇을 떠안나

시간당 0.10달러는 한 달 73달러 정도다. kubeadm으로 직접 세우면 이 돈 대신 다음을 떠안는다.

- 컨트롤 플레인 서버 세 대와 API 서버 앞 로드 밸런서. 클라우드에서 직접 세우면 이 서버와 로드 밸런서 비용만으로 73달러를 쉽게 넘긴다.
- 1년마다 돌아오는 인증서 만료와, 1년에 세 번 나오는 마이너 버전을 한 칸씩 따라가는 업그레이드. 업그레이드를 미루면 인증서도 함께 밀린다.
- etcd 백업과 복원 연습, 컨트롤 플레인 장애 때 새벽에 깨는 사람.
- 노드 OS 패치와 containerd 업그레이드. 이건 관리형에서도 남지만, 직접 운영하면 컨트롤 플레인 노드까지 대상이 된다.

결국 비교는 요금 대 사람 시간이다. 클라우드에 있고 클러스터가 몇 개 안 되면 관리형이 거의 항상 싸다. 직접 세우는 쪽이 맞는 경우는 따로 있다. 온프레미스나 인터넷이 막힌 망처럼 관리형 서비스가 아예 없는 곳, 규제 때문에 컨트롤 플레인까지 내 손에 있어야 하는 곳, 엣지에 작은 클러스터를 수백 개 뿌려야 하는 곳, 그리고 쿠버네티스 내부를 배우려는 경우다. 엣지나 작은 서버라면 kubeadm 대신 부품을 한 바이너리로 묶은 k3s 같은 배포판을 고르기도 한다.

연습용 클러스터를 몇 초 만에 띄우는 도구는 [로컬 쿠버네티스 고르기](/posts/local-k8s-kind-minikube)에서 비교했다. kind는 노드마다 컨테이너를 하나 띄우고 그 안에서 kubeadm을 돌리니, 이 글의 init과 join을 노트북에서 진짜로 돌려 보고 싶다면 kind로 시작하는 게 가장 가깝다.

## 세우는 일보다 지키는 일이 크다

kubeadm init은 인증서를 찍고, static Pod 매니페스트를 놓고, 부트스트랩 토큰을 만드는 것까지다. join은 그 토큰과 CA 해시로 서로를 확인한 뒤 노드에 진짜 인증서를 준다. 여기까지는 몇 분이면 끝난다. 그 뒤의 로드 밸런서, etcd 과반, 인증서 만료, 업그레이드가 직접 운영의 진짜 비용이고, 관리형 서비스의 요금은 그 대부분을 사는 값이다.

## 면접에서 나올 만한 질문

### kubeadm init은 무엇을 하나?

preflight 검사를 하고, 클러스터 CA와 부품별 인증서, kubeconfig를 만든 다음 etcd와 API 서버, 컨트롤러 매니저, 스케줄러를 static Pod 매니페스트로 놓는다. kubelet이 그 매니페스트를 보고 컨트롤 플레인을 띄우면, 설정을 ConfigMap으로 올리고 노드에 control-plane taint를 붙이고 부트스트랩 토큰과 cluster-info를 만든다. CNI는 설치하지 않아서 따로 올려야 노드가 Ready가 된다.

### kubeadm join의 토큰과 discovery-token-ca-cert-hash는 각각 무엇을 증명하나?

토큰은 새 노드가 API 서버에 들어와도 되는 노드라는 걸 증명하고, 해시는 노드가 붙은 곳이 진짜 그 클러스터라는 걸 확인한다. 노드는 cluster-info의 CA 공개 키 SHA-256이 해시와 같은지 보고, 토큰으로 서명도 확인한 뒤에야 토큰으로 로그인해 CSR을 보낸다. 해시 검사를 건너뛰면 가짜 API 서버에 속을 수 있다.

### 토큰이 만료된 뒤 노드를 추가하려면?

컨트롤 플레인에서 kubeadm token create --print-join-command로 새 토큰과 join 명령을 받는다. 기본 토큰 수명은 24시간이고 만료되면 Secret이 지워져 join이 첫 단계에서 실패한다. 만료 없는 토큰은 새면 아무나 노드를 붙일 수 있어서 쓰지 않는다.

### HA 컨트롤 플레인은 어떻게 구성하나?

API 서버 앞에 L4 로드 밸런서를 두고 그 주소를 --control-plane-endpoint로 init에 준다. 첫 노드에서 --upload-certs로 CA와 키를 암호화해 올리고, 나머지 노드는 --control-plane과 --certificate-key를 붙여 join한다. 엔드포인트 이름은 API 서버 인증서에 들어가므로 한 대로 시작해도 처음부터 정해 두는 게 낫다.

### stacked etcd와 외부 etcd는 어떻게 고르나?

stacked는 서버 세 대로 끝나고 kubeadm이 etcd 멤버까지 관리해 줘서 대부분 이걸로 충분하다. 대신 노드 하나를 잃으면 API 서버와 etcd 멤버를 함께 잃는다. 외부 etcd는 서버가 두 배로 늘고 직접 관리해야 하지만 장애와 부하가 분리돼서, 규모가 커서 etcd 지연이 문제가 되거나 etcd 전담 운영이 가능할 때 고른다.

### etcd 멤버를 짝수로 두면 안 되는 이유는?

쓰기에 과반이 필요한데 과반은 floor(n/2)+1이라서, 4대는 3대와 똑같이 1대 장애만 버티면서 고장 날 서버만 하나 더 많다. 2대는 하나만 꺼져도 멈춰서 1대보다 나쁘다. 그래서 3대나 5대로 두고 영역 세 곳에 나눈다.

### 작은 팀이 EKS 대신 kubeadm으로 직접 운영하면 돈을 아낄 수 있나?

클라우드에서는 대개 아니다. 컨트롤 플레인 요금은 한 달 70달러 남짓인데, 직접 세우면 컨트롤 플레인 서버 세 대와 로드 밸런서 비용에 인증서 갱신, 업그레이드, etcd 백업, 장애 대응을 사람이 떠안는다. 직접 운영은 관리형이 없는 온프레미스, 규제, 엣지, 학습 같은 이유가 있을 때 고른다.
