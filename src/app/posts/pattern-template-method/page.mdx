관리자 화면에 "상품 CSV 올리기"가 있다. 몇 달 뒤 "쿠폰 JSON 올리기"가 생겼고, 누군가 상품 쪽 함수를 복사해서 만들었다. 이번 주에 "빈 줄이 있으면 실패하지 말고 건너뛰어 주세요"라는 요청을 받아 상품 쪽을 고쳤다. 다음 날 같은 문의가 쿠폰 쪽에서 들어왔다. 복사된 함수는 고쳐지지 않았다.

두 함수는 순서가 똑같다. 읽고, 줄로 나누고, 한 줄씩 검사하고, 저장하고, 결과를 알린다. 다른 건 "어떻게 나누나"와 "무엇을 검사하나" 정도다. 템플릿 메서드(Template Method) 패턴은 이 순서를 상위 클래스의 메서드 하나에 고정하고, 달라지는 단계만 하위 클래스가 채우게 한다. GoF 23개 중 상속을 직접 쓰는 몇 안 되는 패턴이라, 같은 문제를 합성으로 푸는 [전략 패턴](/posts/pattern-strategy)과 함께 보면 언제 무엇을 고를지가 분명해진다.

## 복사된 흐름에서 버그는 한쪽만 고쳐진다

처음 모양은 이렇다. 두 함수가 같은 뼈대를 따로 들고 있다.

```ts
declare function readFile(path: string, enc: "utf8"): Promise<string>;
declare const db: { products: { insert(p: object): Promise<void> }; coupons: { insert(c: object): Promise<void> } };

async function importProducts(path: string) {
  const raw = await readFile(path, "utf8");
  const rows = raw.split("\n").slice(1).filter((l) => l.trim() !== ""); // 빈 줄 건너뛰기를 여기만 넣었다
  let inserted = 0;
  for (const line of rows) {
    const [sku, price] = line.split(",");
    if (!sku || Number(price) <= 0) continue;
    await db.products.insert({ sku, price: Number(price) });
    inserted++;
  }
  return inserted;
}

async function importCoupons(path: string) {
  const raw = await readFile(path, "utf8");
  const rows = JSON.parse(raw) as { code: string; rate: number }[];
  let inserted = 0;
  for (const row of rows) {
    if (row.rate <= 0 || row.rate > 90) continue;
    await db.coupons.insert(row);
    inserted++;
  }
  return inserted; // 어느 줄이 왜 빠졌는지는 둘 다 알려 주지 않는다
}
```

여기에 "건너뛴 줄과 이유를 결과에 담아 달라", "끝나면 슬랙으로 알려 달라"는 요구가 붙으면 같은 수정을 두 번(회원 엑셀이 생기면 세 번) 해야 한다. 하나를 빠뜨리는 순간 화면마다 동작이 달라진다. 흐름은 하나인데 코드가 흐름 수만큼 있다는 게 문제다.

## 순서는 위에서, 단계는 아래에서

템플릿 메서드는 흐름을 한 번만 쓴다. 상위 클래스의 `run()`이 단계를 차례로 부르고, 각 단계는 추상 메서드나 기본 구현이 있는 메서드로 둔다. 하위 클래스는 `run()`을 건드리지 않고 단계만 채운다.

단계에는 두 종류가 있다. 추상 메서드(primitive operation)는 하위 클래스가 반드시 채워야 하는 단계다. 훅(hook)은 상위 클래스가 기본 구현(대개 아무것도 안 함)을 주고, 필요한 하위 클래스만 바꾸는 단계다. 훅은 확장 지점을 미리 열어 두는 장치다.

```ts
declare function readFile(path: string, enc: "utf8"): Promise<string>;

interface ImportReport {
  inserted: number;
  skipped: number;
  errors: string[];
}

abstract class ImportJob<Row> {
  // 템플릿 메서드: 순서는 여기서만 정한다
  async run(source: string): Promise<ImportReport> {
    const raw = await this.read(source);
    const rows = this.parse(raw);
    const report: ImportReport = { inserted: 0, skipped: 0, errors: [] };
    for (const [i, row] of rows.entries()) {
      const error = this.validate(row);
      if (error) {
        report.skipped++;
        report.errors.push(`${i + 1}번째: ${error}`);
        continue;
      }
      await this.save(row);
      report.inserted++;
    }
    await this.afterImport(report);
    return report;
  }

  protected read(source: string): Promise<string> {
    return readFile(source, "utf8"); // 기본 구현. 필요하면 바꾼다
  }
  protected abstract parse(raw: string): Row[];
  protected abstract validate(row: Row): string | null;
  protected abstract save(row: Row): Promise<void>;
  protected async afterImport(_report: ImportReport): Promise<void> {} // 훅: 비어 있는 기본 구현
}

type Product = { sku: string; price: number };

class ProductCsvImport extends ImportJob<Product> {
  readonly saved: Product[] = [];
  protected parse(raw: string) {
    return raw
      .split("\n")
      .slice(1) // 머리글 줄
      .filter((line) => line.trim() !== "")
      .map((line) => {
        const [sku = "", price = ""] = line.split(",");
        return { sku: sku.trim(), price: Number(price) };
      });
  }
  protected validate(p: Product) {
    if (!p.sku) return "SKU가 비어 있다";
    if (!Number.isInteger(p.price) || p.price <= 0) return `가격이 이상하다 (${p.price})`;
    return null;
  }
  protected async save(p: Product) {
    this.saved.push(p);
  }
}

type CouponRow = { code: string; rate: number };

class CouponJsonImport extends ImportJob<CouponRow> {
  protected parse(raw: string) {
    return JSON.parse(raw) as CouponRow[];
  }
  protected validate(c: CouponRow) {
    return c.rate > 0 && c.rate <= 90 ? null : `할인율은 1~90이어야 한다 (${c.rate})`;
  }
  protected async save(_c: CouponRow) {}
  protected override async afterImport(report: ImportReport) {
    console.log(`[slack] 쿠폰 ${report.inserted}개 등록, ${report.skipped}개 건너뜀`);
  }
}
```

파일 대신 문자열을 돌려주게 `read` 훅만 바꾼 하위 클래스로 둘을 돌려 봤다. 상품 쪽에는 빈 줄, 음수 가격, 빈 SKU를 일부러 섞었다.

}

건너뛴 이유를 모으는 일, 결과를 세는 일은 `run()`에 한 번만 있다. 다음에 "건너뛴 줄이 절반을 넘으면 저장하지 말고 멈춰 달라"는 요구가 와도 `run()` 한 곳만 고치면 상품, 쿠폰, 앞으로 생길 회원 가져오기가 함께 바뀐다. 테스트에서 `read`를 바꿔 끼운 것처럼, 훅은 운영 코드를 고치지 않고 동작 일부를 갈아 끼우는 자리로도 쓰인다.

## 부르는 쪽은 상위 클래스다

평범한 상속에서는 하위 클래스가 상위 클래스의 메서드를 불러 쓴다. 템플릿 메서드는 방향이 반대다. 상위 클래스가 하위 클래스의 메서드를 부른다. 이걸 할리우드 원칙("Don't call us, we'll call you", 연락하지 마라, 우리가 연락하겠다)이라고 부른다. 아래 그림에서 다음을 누르면 `run()` 한 번에 호출이 위아래를 어떻게 오가는지 보인다.

## Node.js 스트림은 _transform만 채우게 한다

템플릿 메서드는 프레임워크가 확장 지점을 여는 가장 오래된 방법이다. Node.js `stream` 모듈이 좋은 예다. 직접 변환 스트림을 만들 때는 `Transform`을 상속하고 `_transform`(필요하면 `_flush`)만 구현한다. 버퍼 관리, 배압(받는 쪽이 느리면 읽기를 늦추는 것), `pipe`와 에러 전파는 상위 클래스가 맡는다. Node.js 문서도 `_transform`은 하위 클래스가 구현하고 내부에서만 부르는 메서드이며, 애플리케이션 코드가 직접 부르면 안 된다고 적어 둔다.

줄 단위로 나누는 변환 스트림을 만들어 일부러 줄 중간에서 잘린 조각 셋을 흘려 봤다.

```ts
import { Transform, Readable, type TransformCallback } from "node:stream";
import { pipeline } from "node:stream/promises";

class LineSplitter extends Transform {
  private rest = "";
  constructor() {
    super({ readableObjectMode: true });
  }
  override _transform(chunk: Buffer, _enc: BufferEncoding, done: TransformCallback) {
    const lines = (this.rest + chunk.toString("utf8")).split("\n");
    this.rest = lines.pop() ?? ""; // 마지막 조각은 다음 청크와 이어 붙인다
    for (const line of lines) this.push(line);
    done();
  }
  override _flush(done: TransformCallback) {
    if (this.rest) this.push(this.rest); // 끝에 줄바꿈이 없던 마지막 줄
    done();
  }
}

async function demo() {
  const chunks = ["id,name\n1,ki", "m\n2,lee\n3,pa", "rk"];
  const out: string[] = [];
  await pipeline(
    Readable.from(chunks.map((c) => Buffer.from(c))),
    new LineSplitter(),
    async function (source: AsyncIterable<string>) {
      for await (const line of source) out.push(line);
    },
  );
  console.log(out);
}
demo();
```

같은 구조가 여러 곳에 있다. 자바 서블릿의 `HttpServlet.service()`는 요청 메서드를 보고 하위 클래스의 `doGet`, `doPost`를 부른다. 자바 `AbstractList`는 `get`과 `size`만 구현하면 반복, `indexOf`, `subList`를 상위 클래스가 그 두 메서드로 만들어 준다. React 클래스 컴포넌트의 `componentDidMount`, `render`도 React가 정한 순서에 맞춰 불리는 단계였다. 반대로 Spring의 `JdbcTemplate`은 이름과 달리 상속을 쓰지 않는다. 연결 열기, 예외 변환, 닫기 같은 뼈대는 템플릿이 쥐고, 바뀌는 단계(`RowMapper`)는 콜백 객체로 받는다. 템플릿 메서드의 생각을 합성으로 옮긴 모양이다.

## 생성자에서 단계를 부르면 생기는 일

템플릿 메서드를 처음 짤 때 흔히 하는 실수가 있다. "만들자마자 준비해야 하니까" 상위 클래스 생성자에서 재정의할 메서드를 부르는 것이다. 자바스크립트와 타입스크립트에서는 이 순간 하위 클래스의 필드가 아직 초기화되지 않았다.

```ts
abstract class Exporter {
  constructor() {
    this.setup(); // 상위 생성자에서 재정의 메서드를 부른다
  }
  protected abstract setup(): void;
}

class CsvExporter extends Exporter {
  private delimiter = ",";
  header = "";
  protected setup() {
    console.log("setup에서 본 delimiter:", JSON.stringify(this.delimiter));
    this.header = ["id", "name"].join(this.delimiter);
  }
}

const e = new CsvExporter();
console.log("생성 후 header:", JSON.stringify(e.header));
```

```text
setup에서 본 delimiter: undefined
생성 후 header: ""
```

버그가 두 개 겹쳐 있다. `setup`이 불릴 때 `delimiter`는 아직 `undefined`다. 하위 클래스의 필드 초기화는 `super()`가 끝난 뒤에 실행되기 때문이다(`join(undefined)`가 우연히 쉼표를 써서 여기서는 티가 안 났다). 그리고 `setup`이 채운 `header`를, 뒤늦게 실행된 필드 초기화 `header = ""`가 덮어썼다. 타입 검사는 둘 다 잡지 못한다.

자바도 생성자에서 재정의 가능한 메서드를 부르지 말라고 권하고(『이펙티브 자바』), 이유도 같다. 템플릿 메서드는 생성자가 아니라 객체가 다 만들어진 뒤 부르는 `run()`, `init()` 같은 메서드에 둔다. 앞의 `ImportJob`이 생성자에서 아무것도 하지 않는 이유다.

## 상속이 무거워지는 순간

템플릿 메서드의 약점은 상속의 약점 그대로다. 하위 클래스는 상위 클래스의 구현에 묶인다. 상위 클래스의 `run()`이 단계를 부르는 순서나 횟수를 바꾸면, 그 순서를 가정하고 짠 하위 클래스가 조용히 깨진다(취약한 기반 클래스 문제). 타입스크립트에는 자바의 `final` 같은 수식어가 없어서 하위 클래스가 `run()` 자체를 재정의하는 것도 막을 수 없다. 코드 리뷰에서 "템플릿 메서드를 재정의하지 않는다"를 규칙으로 두는 수밖에 없다.

단계가 늘어날수록 또 다른 문제가 생긴다. 바뀌는 축이 둘이라고 하자. 읽는 형식(CSV, JSON, 엑셀)과 저장할 곳(상품, 쿠폰, 회원). 템플릿 메서드로는 조합마다 하위 클래스가 생긴다. 이럴 때는 단계를 객체로 받는 쪽이 낫다.

```ts
interface ImportReport { inserted: number; skipped: number; errors: string[] }
interface Steps<Row> {
  parse(raw: string): Row[];
  validate(row: Row): string | null;
  save(row: Row): Promise<void>;
  afterImport?(report: ImportReport): Promise<void>;
}

// 뼈대는 함수 하나가 쥐고, 단계는 인자로 받는다
function createImportJob<Row>(read: (src: string) => Promise<string>, steps: Steps<Row>) {
  return async (source: string): Promise<ImportReport> => {
    const rows = steps.parse(await read(source));
    const report: ImportReport = { inserted: 0, skipped: 0, errors: [] };
    for (const [i, row] of rows.entries()) {
      const error = steps.validate(row);
      if (error) {
        report.skipped++;
        report.errors.push(`${i + 1}번째: ${error}`);
        continue;
      }
      await steps.save(row);
      report.inserted++;
    }
    await steps.afterImport?.(report);
    return report;
  };
}
```

순서를 한 곳에 고정하는 건 그대로이고, 단계를 상속 대신 인자로 받는다. 읽기 방식과 단계 묶음을 따로 골라 끼울 수 있고, 생성자 함정도 없다. 사실상 단계 묶음을 [전략](/posts/pattern-strategy)으로 받는 모양이다. 고르는 기준은 이렇다. 단계들이 서로의 상태(필드)를 공유하며 함께 움직이고 계층이 얕다면 클래스 상속이 읽기 쉽다. 단계를 따로따로 바꿔 끼워야 하거나 하위 클래스가 조합으로 늘어나기 시작하면 합성으로 옮긴다.

[팩토리 메서드](/posts/pattern-factory-method)와의 관계도 짚어 두자. 팩토리 메서드는 템플릿 메서드의 단계 하나가 "객체를 만드는 일"인 경우다. 상위 클래스의 흐름 중간에 `createX()`가 있고 하위 클래스가 무엇을 만들지 정한다.

## 직접 채우는 단계

`importLines(kind, lines)`를 완성해 보자. 상위 클래스 `Importer`의 `run()`은 이미 있다. 빈 줄을 건너뛰고, 줄마다 `parse` → `normalize`(훅) → `validate`를 부르고, `[저장한 id 목록, 실패한 줄 번호 목록]`을 돌려준다. 하위 클래스 두 개의 단계만 채우면 된다.

- 상품 줄은 `"A-1,12000"`. id가 비어 있지 않고 가격이 양의 정수여야 한다.
- 쿠폰 줄은 `"welcome=10"`. id가 비어 있지 않고 할인율이 1~90이어야 한다. 쿠폰만 `normalize` 훅에서 id를 대문자로 바꾼다.

## 면접에서 나올 만한 질문

### 템플릿 메서드 패턴은 무엇인가요?

알고리즘의 뼈대(단계의 순서)를 상위 클래스의 메서드 하나에 고정하고, 단계 중 달라지는 부분만 하위 클래스가 재정의하게 하는 패턴이다. 여러 곳에 같은 흐름이 복사되어 있고 몇 단계만 다를 때 쓴다. 공통 규칙이 한 곳에 모이니 수정도 한 곳에서 끝난다.

### 추상 메서드와 훅은 어떻게 다른가요?

추상 메서드는 하위 클래스가 반드시 구현해야 하는 단계이고, 훅은 상위 클래스가 기본 구현(보통 아무것도 하지 않음)을 주고 필요한 하위 클래스만 재정의하는 단계다. 훅은 지금은 쓰는 곳이 없어도 확장 지점을 열어 두는 역할을 한다. 끝난 뒤 알림을 보내는 `afterImport`나 Node.js 스트림의 `_flush`가 훅에 가깝다.

### 할리우드 원칙이 무엇이고 템플릿 메서드와 어떤 관계인가요?

"우리가 연락하겠다"는 뜻으로, 하위 클래스가 상위 클래스를 부르는 게 아니라 상위 클래스(프레임워크)가 하위 클래스의 단계를 부른다는 원칙이다. 템플릿 메서드가 정확히 그렇게 동작한다. 덕분에 "재정의할 때 `super`를 꼭 먼저 부르라" 같은, 지키지 않아도 컴파일되는 규칙이 필요 없어진다.

### 템플릿 메서드와 전략 패턴은 어떻게 다른가요?

둘 다 알고리즘의 일부를 바꾸지만 템플릿 메서드는 상속, 전략은 합성으로 바꾼다. 템플릿 메서드는 컴파일 시점에 하위 클래스로 정해지고 순서를 상위 클래스가 강하게 지킨다. 전략은 실행 중에 바꿔 끼울 수 있고 여러 축을 따로 조합하기 쉽다. 바뀌는 축이 둘 이상이면 하위 클래스가 곱으로 늘어나니 전략 쪽으로 옮긴다.

### 상위 클래스 생성자에서 재정의 메서드를 부르면 왜 문제가 되나요?

그 시점에는 하위 클래스의 필드 초기화가 아직 실행되지 않았기 때문이다. 자바스크립트와 타입스크립트에서는 필드 초기화가 `super()`가 끝난 뒤에 돌아서, 재정의 메서드가 본 필드는 `undefined`이고, 그 메서드가 채운 값도 뒤늦은 필드 초기화에 덮어써진다. 템플릿 메서드는 객체가 다 만들어진 뒤 부르는 `run()` 같은 메서드에 둔다.

### 실제 라이브러리에서 템플릿 메서드를 본 적이 있나요?

Node.js에서 변환 스트림을 만들 때 `Transform`을 상속해 `_transform`과 `_flush`만 구현하는 것이 대표적이다. 버퍼와 배압, 에러 전파는 상위 클래스가 맡는다. 자바의 `HttpServlet`이 `service()`에서 `doGet`, `doPost`를 부르는 구조와 `AbstractList`도 같다. Spring의 `JdbcTemplate`은 이름과 달리 바뀌는 단계를 콜백으로 받는 합성 버전이다.

### 템플릿 메서드의 단점은 무엇인가요?

상속의 단점을 그대로 가진다. 하위 클래스가 상위 클래스의 구현과 호출 순서에 묶여서, 상위 클래스를 고치면 하위 클래스가 조용히 깨질 수 있다. 타입스크립트에는 `final`이 없어 템플릿 메서드 자체의 재정의를 막을 수도 없다. 계층이 깊어지거나 축이 늘면 단계를 인자로 받는 합성 방식이 낫다.
