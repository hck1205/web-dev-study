대시보드의 평균 응답 시간은 12ms로 평온했다. 그런데 고객센터에는 "가끔 결제 버튼을 누르면 1초쯤 멈춘다"는 문의가 쌓였다. 둘 다 맞는 말이었다. 평균은 대부분의 빠른 요청 쪽으로 끌려가고, 1초짜리 요청 몇 개는 그 안에 묻힌다. 응답 시간은 숫자 하나가 아니라 분포다.

이 글은 응답 시간 분포를 숫자로 읽는 법을 다룬다. 실제로 요청을 수만 번 보내 시간을 모으고, 거기서 p50, p95, p99, p99.9를 뽑는다. 그다음 실무에서 자주 틀리는 두 가지를 직접 재현한다. 서버별 p99를 평균 내는 실수와, 부하 생성기가 느린 구간을 통째로 빼먹는 coordinated omission이다. 실습은 Ubuntu 24.04, Node 22, autocannon 8.0, hdr-histogram-js 3.0으로 했다.

이 주제의 다른 글: 손실 1%가 p99를 1초로 만드는 네트워크 쪽 사례는 [지연, 대역폭, 처리량](/posts/latency-bandwidth-throughput)에서 봤다. 이렇게 잰 꼬리가 서버 여러 대를 거치며 왜 커지고 어떻게 줄이는지는 [꼬리 지연](/posts/tail-latency)에서 이어 간다.

## 평균 9ms 뒤에 숨은 1초

먼저 일부러 꼬리가 있는 API를 만들었다. 요청의 98.9%는 5ms, 1%는 200ms(느린 DB 경로를 흉내), 0.1%는 1초가 걸린다.

```js
// server.js: 대부분 5ms, 1%는 200ms, 0.1%는 1000ms 걸리는 API
const http = require("http");
http.createServer((req, res) => {
  const r = Math.random();
  const ms = r < 0.001 ? 1000 : r < 0.011 ? 200 : 5;
  setTimeout(() => res.end("ok"), ms);
}).listen(3001, "127.0.0.1");
```

여기에 HTTP 부하 생성기 autocannon으로 연결 50개를 20초 동안 걸었다.

```bash
# autocannon 설치 없이 실행: 연결 50개, 20초
npx autocannon -c 50 -d 20 http://127.0.0.1:3001/
```

```text
┌─────────┬──────┬──────┬───────┬────────┬─────────┬──────────┬─────────┐
│ Stat    │ 2.5% │ 50%  │ 97.5% │ 99%    │ Avg     │ Stdev    │ Max     │
├─────────┼──────┼──────┼───────┼────────┼─────────┼──────────┼─────────┤
│ Latency │ 5 ms │ 6 ms │ 13 ms │ 200 ms │ 9.47 ms │ 36.12 ms │ 1006 ms │
└─────────┴──────┴──────┴───────┴────────┴─────────┴──────────┴─────────┘
...
100k requests in 20.09s, 12.4 MB read
```

평균(Avg)은 9.47ms다. 그런데 이 서버에서 9ms 근처에 끝난 요청은 거의 없다. 대부분은 5~6ms에 끝났고, 일부는 200ms, 몇 개는 1초가 걸렸다. 평균은 서로 다른 두 무리 사이 아무도 없는 곳을 가리킨다. 표준편차(Stdev 36ms)가 평균의 네 배라는 것도 분포가 한쪽으로 길게 늘어졌다는 신호다.

요청마다 걸린 시간을 직접 모으는 작은 클라이언트도 짰다. 동시 50개로 2만 건을 보내고 정렬해서 읽는다.

```bash
# 2만 건을 보내 평균, 백분위, 평균보다 느린 요청 비율을 출력
node client.js http://127.0.0.1:3001/ 20000
```

```text
n=20000 mean=14.4ms p50=9.4ms p95=24.1ms p99=201.9ms p99.9=1000.1ms max=1011.5ms
requests slower than mean: 3182 (15.9%)
```

autocannon보다 p50이 높은 건 Node로 짠 이 클라이언트가 동시 50개를 다루며 쓰는 시간이 섞여서다. 측정 도구도 시간을 먹는다는 점은 뒤에서 다시 나온다. 여기서 볼 것은 마지막 줄이다. 평균보다 느린 요청은 16%뿐이다. 평균은 "보통 요청"도 "느린 요청"도 설명하지 못한다.

## 줄 세워 몇 번째 값을 읽는다

백분위(percentile)는 시간을 작은 순서로 줄 세웠을 때 앞에서 몇 퍼센트 위치의 값이다. p99가 200ms라면 "요청 100개 중 99개는 200ms 안에 끝났다"는 뜻이고, 거꾸로 말하면 100번에 한 번은 그보다 오래 걸린다는 뜻이다. p50은 중앙값, p99.9는 1000번에 한 번을 본다.

여기서 쓴 방법은 nearest-rank 방식이다. 순위 = ⌈p/100 × n⌉번째 값을 그대로 쓴다. 도구마다 정의가 조금씩 다르다. NumPy의 `percentile` 기본값은 이웃한 두 값 사이를 선형 보간한다. 표본이 수만 개면 차이가 무시할 만하지만, 표본이 적은 꼬리에서는 도구마다 다른 숫자가 나온다. 두 시스템의 p99를 비교할 때는 같은 도구, 같은 정의로 뽑았는지부터 확인한다.

그리고 마지막 단계가 보여 주듯, 표본 수보다 세밀한 백분위는 의미가 없다. 20개로는 p99를 잴 수 없다. p99를 말하려면 적어도 수백 개, p99.9를 말하려면 수천 개 이상이 필요하다.

## 꼬리 백분위는 표본이 많아야 흔들리지 않는다

같은 서버, 같은 클라이언트로 2만 건을 한 번 더 보냈다.

```text
n=20000 mean=12.6ms p50=8.4ms p95=19.9ms p99=200.7ms p99.9=248.1ms max=1017.6ms
```

첫 실행의 p99.9는 1000.1ms였는데 이번에는 248.1ms다. 서버는 그대로다. 2만 건의 0.1%는 20건이고, 1초짜리 요청은 확률 0.1%로 섞이니 실행마다 대략 20건 안팎으로 나온다. 20건을 넘으면 p99.9 자리에 1초짜리가 앉고, 조금 모자라면 200ms대가 앉는다. p99는 두 번 다 200ms 근처로 안정적이었다. p99 위쪽에는 200건이 있어서 몇 건 늘거나 줄어도 자리가 바뀌지 않는다.

실무에서는 이게 "트래픽이 적은 시간대에 p99 그래프가 톱니처럼 튄다"로 나타난다. 새벽에 1분 동안 요청이 300건이면, 그 1분의 p99는 위에서 세 번째 요청 하나가 정한다. 그 요청 하나가 GC에 걸리면 그래프가 솟는다. 그래서 다음을 지킨다.

- 꼬리 백분위는 집계 창 안의 요청 수가 충분할 때만 믿는다. p99면 창 하나에 최소 수백 건, p99.9면 수천 건.
- 트래픽이 적은 서비스는 창을 넓히거나(1분 대신 5분), p99 대신 "300ms를 넘은 요청 수" 같은 개수로 본다.
- 최댓값(max)은 따로 그린다. 백분위가 놓치는 단 한 번의 큰 멈춤을 max가 보여 준다.

## 서버별 p99를 평균 내면 안 된다

서버가 여러 대면 대시보드는 대개 서버마다 p99를 계산한 다음 그걸 다시 합친다. 여기서 실수가 생긴다. 두 대를 따로 띄웠다. host A는 트래픽의 90%를 받는 건강한 서버이고(200ms 경로 0.2%), host B는 10%를 받는데 디스크가 느려 꼬리가 길다(200ms 8%, 1초 1%).

```bash
# A에 18000건, B에 2000건을 보내고 각자의 원본 시간을 파일로 남긴다
CONC=10 DUMP=a.json node client.js http://127.0.0.1:3002/ 18000
CONC=10 DUMP=b.json node client.js http://127.0.0.1:3003/ 2000
# 서버별 p99를 여러 방식으로 합쳐 본다
node merge.js
```

```text
host A n=18000 p99=13.4ms
host B n=2000 p99=205.0ms
avg of p99s           = 109.2ms
weighted avg of p99s  = 32.5ms
max of p99s           = 205.0ms
true p99 (all 20000) = 200.2ms
```

전체 2만 건을 한 줄로 세운 진짜 p99는 200.2ms다. 두 p99를 그냥 평균 내면 109.2ms, 요청 수로 가중 평균을 내도 32.5ms다. 둘 다 틀렸다. 가중 평균은 진짜의 6분의 1이다. 백분위는 "위에서 몇 번째"라는 순위인데, 순위는 평균으로 합쳐지지 않는다. B의 느린 요청 200건가량은 전체에서 보면 상위 1%를 거의 다 차지하는데, A의 p99와 평균을 내는 순간 그 사실이 사라진다.

## 히스토그램은 더할 수 있다

히스토그램은 "10ms 이하 몇 건, 25ms 이하 몇 건" 하는 식으로 구간별 개수만 센다. 개수는 그냥 더하면 되니 서버 100대의 히스토그램을 합쳐도, 1분짜리 100개를 합쳐 100분짜리를 만들어도 정확하다. 같은 데이터를 두 가지 경계로 나눠 더해 봤다.

```text
le           5    10    25    50   100   250   500  1000  2500
host A     431 16937   574    25     3    30     0     0     0
host B      48  1679    68    15     0   177     0     1    12
sum        479 18616   642    40     3   207     0     1    12
p99 from summed buckets: bucket (100, 250] -> interpolated 114.5ms
```

```text
le           5    10    25    50   100   200   250   500  1000  2500
host A     431 16937   574    25     3     1    29     0     0     0
host B      48  1679    68    15     0     5   172     0     1    12
sum        479 18616   642    40     3     6   201     0     1    12
p99 from summed buckets: bucket (200, 250] -> interpolated 203.5ms
```

두 경우 모두 p99가 들어 있는 버킷은 맞게 찾았다. 차이는 버킷 안에서 값을 어림하는 단계에서 생긴다. 버킷 안의 값은 모르니 고르게 퍼져 있다고 보고 선형 보간한다. 첫 번째는 (100, 250] 버킷이 넓어서 114.5ms라는 엉뚱한 값이 나왔다. 실제 값들은 200~210ms에 몰려 있었다. 200 경계 하나를 넣자 203.5ms로 진짜(200.2ms)에 붙었다. Prometheus의 `histogram_quantile`도 같은 방식(버킷 안 선형 보간)으로 계산한다.

여기서 실무 규칙 두 개가 나온다. 버킷 경계는 SLO 기준값 바로 위아래에 둔다. "300ms 안에 99%"가 목표라면 300 경계가 꼭 있어야 한다. 그리고 미리 계산된 백분위만 내보내는 형식(Prometheus의 summary가 그렇다)은 서버끼리 합칠 수 없으니, 여러 대를 묶어 볼 지표는 히스토그램으로 내보낸다. 히스토그램과 summary를 고르는 기준과 PromQL은 [메트릭 타입 글](/posts/metrics-types)에서 다룬다.

<Callout kind="warning" title="Grafana에서 자주 보는 잘못된 쿼리">
`avg(histogram_quantile(0.99, rate(..._bucket[5m])))`는 서버별 p99를 구한 뒤 평균을 낸다. 위 실험의 109ms와 같은 실수다. 버킷을 먼저 더하고 그다음 백분위를 구한다. `histogram_quantile(0.99, sum by (le) (rate(..._bucket[5m])))` 순서다. 시간 방향도 마찬가지라서, 5분짜리 p99를 한 시간 동안 `avg_over_time`으로 평균 내도 한 시간의 p99가 되지 않는다.
</Callout>

## HDR 히스토그램: 넓은 범위를 같은 정밀도로

고정 경계 히스토그램은 경계를 잘못 고르면 위처럼 크게 틀린다. 그렇다고 1µs 단위로 1분까지 칸을 만들면 6천만 칸이 필요하다. HdrHistogram(High Dynamic Range Histogram)은 이 문제를 유효숫자로 푼다. "값의 크기와 상관없이 유효숫자 3자리까지 맞힌다"를 목표로, 2의 거듭제곱 구간마다 같은 개수의 칸을 둔다.

유효숫자 3자리면 첫 구간은 1µs 단위로 약 2ms까지 2048칸이고, 그다음부터는 구간마다 1024칸씩 칸 너비가 두 배로 커진다. 200ms 근처에서는 칸 너비가 128µs, 1초 근처에서는 512µs다. 어느 값이든 0.1% 안쪽으로 맞힌다는 뜻이다. 칸 수는 범위와 자릿수로만 정해지니 기록이 몇 건이든 메모리는 같다. 앞의 2만 건을 µs 단위로 넣어 봤다.

```js
// 1µs ~ 60초를 유효숫자 3자리로
const hdr = require("hdr-histogram-js");
const mk = () => hdr.build({ lowestDiscernibleValue: 1, highestTrackableValue: 60_000_000, numberOfSignificantValueDigits: 3 });
const ha = mk(), hb = mk();
// a.json, b.json의 ms 값을 µs로 바꿔 recordValue
const merged = mk(); merged.add(ha); merged.add(hb);   // 서버 두 대 합치기
```

```text
merged count=20000 estimatedFootprint=70656 bytes
compressed base64 length=1796
```

합친 p99가 200.3ms로 원본을 줄 세운 값(200.2ms)과 0.1ms 차이다. 메모리는 약 69KB이고, 압축해서 보내면 1,796자다. 서버가 1분마다 이 문자열을 보내고 수집 쪽에서 `add`로 합치면 원본 없이도 정확한 전체 백분위를 얻는다. 분포 전체도 출력해 볼 수 있다(값은 ms로 나눠 찍었다).

`1/(1-Percentile)` 열은 "몇 번에 한 번꼴인가"다. 1024번에 한 번은 206ms, 2048번에 한 번은 1초다. p99.9에서 p99.95 사이에 절벽이 있다는 게 한눈에 보인다.

같은 문제를 푸는 다른 자료 구조도 있다. t-digest는 양 끝(아주 낮거나 아주 높은 백분위)에 칸을 촘촘히 두는 근사 구조이고, DDSketch는 HDR처럼 상대 오차를 보장하면서 칸을 필요한 만큼만 만든다. Prometheus의 네이티브 히스토그램도 지수형 버킷이라 생각이 같다. 고르는 기준은 대개 쓰는 모니터링 도구가 무엇을 지원하느냐다.

## 부하 생성기가 꼬리를 지울 때

이번에는 측정하는 쪽의 함정이다. 평소엔 바로 답하다가 시작 3초 뒤 이벤트 루프를 2초 동안 완전히 막는 서버를 만들었다. 긴 GC 멈춤이나 동기 I/O로 프로세스가 멈춘 상황이다. 10초 중 2초, 즉 20%의 시간 동안 이 서버에 온 요청은 모두 최대 2초를 기다려야 한다.

```bash
# 연결 하나로 10초 동안 최대한 빨리 보낸다
npx autocannon -c 1 -d 10 http://127.0.0.1:3010/
```

```text
┌─────────┬──────┬──────┬───────┬──────┬─────────┬─────────┬─────────┐
│ Stat    │ 2.5% │ 50%  │ 97.5% │ 99%  │ Avg     │ Stdev   │ Max     │
├─────────┼──────┼──────┼───────┼──────┼─────────┼─────────┼─────────┤
│ Latency │ 0 ms │ 0 ms │ 0 ms  │ 0 ms │ 0.05 ms │ 8.29 ms │ 2000 ms │
└─────────┴──────┴──────┴───────┴──────┴─────────┴─────────┴─────────┘

58k requests in 10.01s, 7.24 MB read
```

서버가 2초 동안 죽어 있었는데 p99는 0ms다. 5만 8천 건 중 2초를 기다린 건 단 한 건이기 때문이다. 부하 생성기가 응답을 기다리느라 그 2초 동안 요청을 보내지 않았다. 실제 사용자들은 서버가 멈췄다고 요청을 멈추지 않는다. 그 2초 동안 도착했어야 할 수천 건의 대기 시간이 측정에서 통째로 빠졌다. 측정 도구가 측정 대상과 보조를 맞추는(coordinate) 바람에 나쁜 표본을 빠뜨린다(omit)는 뜻에서, HdrHistogram을 만든 Gil Tene가 이걸 coordinated omission이라고 불렀다.

고치는 방법은 재는 기준점을 "실제로 보낸 시각"에서 "보내려던 시각"으로 바꾸는 것이다. 10ms마다 하나씩 보내기로 정해 두고, 늦게 보냈더라도 원래 계획한 시각부터 잰다. 같은 클라이언트가 두 기준으로 기록하게 했다.

```bash
# 10ms 간격 계획으로 10초, 연결 하나. 두 기준으로 모두 기록
node co-client.js
```

```text
from actual send   n=1000 mean=3.1ms p50=1.0ms p90=1.4ms p99=6.8ms max=1994.6ms
from intended send n=1000 mean=211.1ms p50=1.2ms p90=1049.0ms p99=1899.9ms max=1994.6ms
```

같은 1000건인데 p99가 6.8ms와 1899.9ms다. 두 번째가 그 시간 동안 일정한 간격으로 들어온 사용자가 겪은 값이다. 열 명 중 한 명(p90)이 1초 넘게 기다렸다.

이 구분을 부하 모델로 말하면, 앞 응답을 받아야 다음을 보내는 닫힌 모델(closed model)과 응답과 상관없이 정해진 속도로 도착하는 열린 모델(open model)이다. 웹 서비스의 사용자는 대부분 열린 모델이다. 그래서 부하 시험 도구를 고를 때 이걸 본다.

- wrk2는 `-R`로 초당 요청 수를 고정하고, 지연을 계획된 시각부터 잰다.
- k6는 `constant-arrival-rate` 실행기가 열린 모델이다. 가상 사용자가 모자라 계획대로 못 보낸 요청은 `dropped_iterations`로 따로 센다.
- autocannon이나 wrk(원판)처럼 연결 수를 정하고 최대한 빨리 보내는 도구는 닫힌 모델이다. 처리량 한계를 재는 데는 좋지만, 그 결과의 p99를 사용자 경험으로 읽으면 안 된다.
- 직접 기록할 때는 HdrHistogram의 `recordValueWithExpectedInterval`이 기대 간격보다 긴 값을 받으면 빠진 표본을 채워 넣는다.

## 버킷을 더해 전체 p99 구하기

서버 여러 대의 히스토그램을 받아 전체 백분위를 어림하는 함수를 직접 짜 보자. 버킷 경계(`bounds`)는 모든 서버가 같고, `hosts[i][j]`는 서버 i에서 `bounds[j-1]` 초과 `bounds[j]` 이하인 요청 수다. 첫 버킷의 아래 끝은 0으로 본다. 답은 소수 첫째 자리로 반올림하고, 요청이 하나도 없으면 `null`을 돌려준다. 테스트의 첫 번째 값은 위 실험의 실제 버킷이다.

  // 3. 그 버킷 안에서 선형 보간한다

  solution={`function mergedQuantile(hosts, bounds, q) {
  const sum = bounds.map((_, i) => hosts.reduce((acc, h) => acc + h[i], 0));
  const total = sum.reduce((a, b) => a + b, 0);
  if (total === 0) return null;
  const target = q * total;
  let cum = 0;
  for (let i = 0; i < bounds.length; i++) {
    if (sum[i] === 0) continue;
    if (cum + sum[i] >= target) {
      const lo = i === 0 ? 0 : bounds[i - 1];
      const v = lo + (bounds[i] - lo) * (target - cum) / sum[i];
      return Math.round(v * 10) / 10;
    }
    cum += sum[i];
  }
  return bounds[bounds.length - 1];
}`}

    { label: "요청 없음", args: [[[0, 0], [0, 0]], [100, 200], 0.5], expected: null },

세 번째 테스트가 보간의 한계를 보여 준다. A만의 진짜 p99는 13.4ms인데 버킷으로 어림하면 21.8ms다. p99 자리가 (10, 25] 버킷에 떨어졌고 그 안을 고르게 퍼진 것으로 봤기 때문이다. 버킷이 넓으면 백분위는 버킷 경계 사이 어딘가라는 것까지만 믿는다.

## 응답 시간 지표를 읽고 고르는 법

현장에서 "느리다"는 말이 들어오면 이렇게 좁힌다.

먼저 어느 백분위가 움직였는지 본다. p50까지 같이 올랐다면 전체가 느려진 것이다. 배포, DB 플랜 변경, CPU 포화처럼 모든 요청에 걸리는 원인을 찾는다. p50은 그대로인데 p99만 올랐다면 일부 요청만 느린 것이다. 특정 경로, 특정 서버 한 대, GC 멈춤, 커넥션 풀 대기, 재시도처럼 가끔 걸리는 원인을 찾는다. 위의 host B처럼 서버 한 대가 꼬리를 만드는 경우가 흔하니, 서버별로 쪼개 본 다음 합친 값을 본다.

다음은 대시보드가 숫자를 맞게 만들고 있는지 확인한다.

- 백분위를 평균 내는 쿼리가 없나. 서버 방향(`avg` of quantile)이든 시간 방향(`avg_over_time` of quantile)이든 틀린다.
- 집계 창 안의 요청 수가 그 백분위를 말할 만큼 되나. 새벽 시간대 p99가 튀는 건 표본 부족일 수 있다.
- 버킷 경계가 SLO 기준값을 품고 있나. 경계가 100과 250뿐인데 목표가 200ms면 그 대시보드는 목표를 판정할 수 없다.
- 부하 시험 결과의 p99가 닫힌 모델에서 나온 것인가. 그렇다면 처리량 숫자로만 쓴다.

목표를 정할 때는 백분위보다 비율이 다루기 쉽다. "p99 300ms 이하"는 계산 방식에 따라 숫자가 흔들리지만, "300ms 안에 끝난 요청의 비율 99% 이상"은 `le="0.3"` 버킷 개수 ÷ 전체 개수로 정확히 구해지고 서버끼리, 시간끼리 더해도 맞다. SLO를 이 비율로 적는 이유가 여기 있다. 목표를 세우고 남은 여유를 관리하는 일은 [SLI와 SLO](/posts/sli-slo) 글에서 이어진다.

흔한 실수도 몇 가지 적어 둔다. 평균만 알람으로 거는 것, p99만 보고 max를 버리는 것, 성공한 요청만 지연 히스토그램에 넣고 타임아웃 난 요청을 빼는 것이다. 마지막 것은 특히 위험하다. 가장 느린 요청이 타임아웃으로 실패하면 지연 지표에서 사라져, 장애가 심해질수록 p99가 오히려 좋아 보인다. 실패한 요청도 걸린 시간을 기록하고 상태 코드로 라벨을 나눈다.

## 분포를 숫자 몇 개로 줄일 때

응답 시간은 분포이고, 평균은 그 분포에서 가장 쓸모없는 숫자 중 하나다. p50은 보통의 경험, p99와 p99.9는 운 나쁜 사용자의 경험, max는 단 한 번의 큰 멈춤을 보여 준다. 백분위는 순위라서 평균 낼 수 없고, 합칠 때는 개수(히스토그램)를 더한다. 그리고 숫자를 믿기 전에 그 숫자를 만든 측정이 느린 순간을 빼먹지 않았는지 의심한다. 이렇게 잰 꼬리가 서버 수십 대를 거치는 요청에서 어떻게 커지는지는 [꼬리 지연](/posts/tail-latency)에서 이어 간다.

## 면접에서 나올 만한 질문

### 응답 시간을 평균으로 보면 왜 안 되나요?

응답 시간 분포는 대부분 빠르고 일부가 아주 느린 한쪽으로 긴 모양이라 평균이 어느 요청도 대표하지 못한다. 실험에서 평균은 9.47ms였지만 실제 요청은 5~6ms와 200ms, 1초로 갈렸고 평균보다 느린 요청은 16%뿐이었다. 그래서 p50으로 보통의 경험을, p99·p99.9와 max로 느린 쪽을 따로 본다.

### p99가 200ms라는 건 정확히 무슨 뜻인가요?

요청 시간을 줄 세웠을 때 99%가 200ms 안에 끝났고, 100번에 한 번은 그보다 오래 걸렸다는 뜻이다. 순위로 정의되는 값이라 계산 방식(nearest-rank인지 보간인지)과 표본 수에 따라 조금씩 다르다. 표본이 20개면 p99는 최댓값과 같으니, p99를 말하려면 창 안에 수백 건 이상이 있어야 한다.

### 서버 10대의 p99를 평균 내면 전체 p99가 되나요?

안 된다. 백분위는 순위라서 평균으로 합쳐지지 않는다. 실험에서 서버 두 대의 p99를 평균 내니 109ms, 가중 평균은 32.5ms였는데 전체를 줄 세운 진짜 p99는 200ms였다. 경계가 같은 히스토그램의 버킷 개수를 더한 뒤 백분위를 구하거나 HdrHistogram처럼 합칠 수 있는 구조를 쓴다.

### 히스토그램으로 구한 백분위는 얼마나 정확한가요?

백분위가 들어 있는 버킷은 정확히 찾지만, 버킷 안의 값은 고르게 퍼졌다고 보고 선형 보간하므로 버킷 너비만큼 틀릴 수 있다. 같은 데이터에서 (100, 250] 버킷으로는 114.5ms, 200 경계를 넣으니 203.5ms가 나왔다. 그래서 SLO 기준값 근처에 경계를 두고, 넓은 범위를 균일한 상대 오차로 보려면 HdrHistogram 같은 지수형 버킷을 쓴다.

### coordinated omission이 무엇이고 어떻게 피하나요?

부하 생성기가 응답을 기다리느라 서버가 멈춘 동안 요청을 보내지 않아, 그 시간에 왔어야 할 느린 표본이 통째로 빠지는 현상이다. 서버를 2초 멈췄는데 autocannon의 p99는 0ms였고, 보내려던 시각 기준으로 다시 재니 p99가 1.9초였다. 일정한 도착률로 보내고 계획된 시각부터 재는 열린 모델 도구(wrk2의 `-R`, k6의 constant-arrival-rate)를 쓰거나 기록 시 빠진 표본을 보정한다.

### 앱 지표의 p99는 괜찮은데 사용자는 느리다고 합니다. 어디를 보나요?

앱 히스토그램은 핸들러가 시작된 뒤만 재니, 그 앞의 대기 시간이 빠져 있을 수 있다. LB의 응답 시간이나 실사용자 측정과 앱 p99를 나란히 놓고 차이가 어디서 벌어지는지 본다. 차이가 크면 accept 큐 대기, 연결 수립, 프로세스 멈춤, 커넥션 풀 대기를 의심한다. 타임아웃으로 실패한 요청이 지연 지표에서 빠지지 않았는지도 확인한다.

### SLO를 "p99 300ms"로 쓰는 것과 "300ms 안에 끝난 비율 99%"로 쓰는 것은 무엇이 다른가요?

비율 쪽이 계산이 정확하고 합치기 쉽다. 비율은 300ms 경계 버킷의 개수를 전체 개수로 나누면 되어서 서버끼리, 시간끼리 더해도 맞다. p99는 계산 방식과 버킷 보간에 따라 흔들리고 평균 낼 수 없다. 대신 비율로 쓰려면 히스토그램에 그 경계가 꼭 있어야 한다.
