  헬스 체크는 식당 홀 매니저가 주방마다 "지금 주문 받아도 되나"를 묻는 일과 같다. 그런데 주방 셋이 같은 창고를 쓰는데 "창고에 재료가 있나"까지 대답에 넣으면, 창고가 비는 순간 주방 셋이 한꺼번에 "못 받는다"고 답해 식당 전체가 문을 닫는다. 그 창고 없이도 만들 수 있는 음식이 많은데도 그렇다.

장바구니 정보를 담는 Redis가 잠깐 내려갔다. 장바구니가 안 되는 건 그렇다 쳐도, Redis와 아무 상관 없는 상품 목록까지 모두 503이 됐다. 서버 세 대는 멀쩡히 떠 있었고, 직접 붙어 보면 상품 목록도 잘 줬다. 로드 밸런서만 "줄 서버가 없다"고 말했다. 이 글의 실습에서 실제로 이렇게 됐다. 원인은 헬스 체크 엔드포인트가 Redis까지 확인하고 있었다는 것 하나다.

헬스 체크는 "이 서버에 요청을 보내도 되나"를 묻는 장치다. 질문은 단순한데, 무엇을 확인해야 하는지는 묻는 쪽이 실패했을 때 무엇을 하느냐에 따라 달라진다. 이 글은 얕은 검사와 깊은 검사의 차이, 공유 의존성을 확인하는 검사가 전체 장애를 부르는 과정, 헬스 체크 자체가 만드는 부하와 타임아웃, 뜰 때 하는 검사, 그리고 `/healthz` 엔드포인트를 어떻게 설계할지를 HAProxy와 Node 서버, Redis로 따라간다.

이 주제의 다른 글: 로드 밸런서의 수동·능동 검사와 판정 숫자(interval, fall, rise), 드레이닝은 [로드 밸런서 기본](/posts/load-balancer-basics)에, 쿠버네티스의 liveness·readiness·startup 프로브 설정은 [프로브 글](/posts/k8s-pod-probes)에 있다. 여기서는 그 둘이 공통으로 두드리는 엔드포인트 쪽, 즉 서버가 "나 괜찮다"고 답하는 기준을 다룬다.

실습 환경은 Ubuntu 24.04, HAProxy 2.8.16, Node.js 22, Redis 7.0.15다. 같은 Node 서버 세 대(19301~19303)를 HAProxy(19300) 뒤에 두고, 서버들은 같은 Redis(19379)를 쓴다.

## 얕은 검사와 깊은 검사

얕은(shallow) 검사는 프로세스 자신만 본다. HTTP 요청을 받아 응답할 수 있으면 통과다. 실습 서버의 `/livez`가 이렇다. 그냥 `ok`를 돌려준다. 이 핸들러가 응답한다는 것 자체가 이벤트 루프가 돌고, 포트가 열려 있고, 프로세스가 멈추지 않았다는 증거다.

깊은(deep) 검사는 요청을 제대로 처리하는 데 필요한 것까지 본다. DB나 캐시에 실제로 질의를 보내고, 디스크 여유와 내부 큐 길이를 확인한다. 실습 서버의 `/readyz`는 Redis에 PING을 보내고, 자기가 종료 준비 중(draining)인지도 본다. 응답은 IETF 초안인 "Health Check Response Format for HTTP APIs"의 모양을 빌렸다.

```bash
# 깊은 검사 엔드포인트를 직접 두드린다
curl -s -i 127.0.0.1:19301/readyz
```

```text

Connection: keep-alive
Keep-Alive: timeout=5
Transfer-Encoding: chunked

{"status":"pass","checks":{"redis:ping":[{"status":"pass","observedValue":1,"observedUnit":"ms"}],"self:draining":[{"status":"pass"}]}}
```

## 공유 의존성을 물으면 전부 같이 빠진다

HAProxy가 `/readyz`를 1초마다 묻고, 2번 연속 실패하면 빼게 했다.

```text
# haproxy-deep.cfg (backend 부분)
backend be_api
  option httpchk GET /readyz
  http-check expect status 200
  default-server inter 1s fall 2 rise 2
  server s1 127.0.0.1:19301 check
  server s2 127.0.0.1:19302 check
  server s3 127.0.0.1:19303 check
```

먼저 서버 한 대만 아플 때를 보자. s2에 종료 준비 플래그를 켰다. 이건 s2만의 사정이다.

```bash
# s2만 종료 준비 상태로 바꾼다
curl -s "127.0.0.1:19302/admin/drain?on=1"
# 런타임 API로 서버별 상태를 본다 (st.sh: show stat에서 필요한 칸만 뽑는다)
bash st.sh
# 상품 목록을 여섯 번 요청한다
for i in $(seq 6); do curl -s 127.0.0.1:19300/api/products; done
```

## 빼지 말고 그 요청만 실패시킨다

같은 상황에서 HAProxy가 얕은 `/livez`를 보게 바꿨다. Redis는 여전히 내려가 있다.

```bash
# 얕은 검사로 바꾼 설정으로 다시 띄운다 (option httpchk GET /livez)
haproxy -db -f haproxy-shallow.cfg &
# 상품 목록과 장바구니를 두 번씩
for u in products products cart cart; do
  curl -s -o /dev/null -w "/api/$u %{http_code} %{time_total}s\n" 127.0.0.1:19300/api/$u
done
curl -s 127.0.0.1:19300/api/cart
```

```text
s1 UP L7OK 200
s2 UP L7OK 200
s3 UP L7OK 200
BACKEND UP  
/api/products 200 0.001266s
/api/products 200 0.001420s
/api/cart 503 0.004539s
/api/cart 503 0.001216s
cart unavailable (ECONNREFUSED)
```

서버는 모두 UP이다. Redis가 필요한 장바구니만 빠르게 503을 받고, 상품 목록은 계속 된다. Redis를 다시 올리자 장바구니도 바로 돌아왔다. 장애가 의존성이 필요한 기능 크기로 줄었다. 이걸 우아한 저하(graceful degradation)라고 한다.

그렇다고 의존성 상태를 아무도 몰라도 된다는 뜻은 아니다. Redis가 죽은 건 바깥 감시와 알림이 잡아야 한다. 헬스 체크는 트래픽을 어디로 보낼지 정하는 장치고, 의존성 장애를 사람에게 알리는 건 [알림](/posts/alerting)의 일이다. 요청 단위로 빠르게 실패하는 코드에는 타임아웃과 [서킷 브레이커](/posts/circuit-breaker)가 들어간다.

정리하면 트래픽을 빼는 검사에는 그 서버만의 사정만 넣는다. 종료 준비 중인가, 시작 작업(캐시 채우기, 설정 읽기)이 끝났나, 그 서버의 디스크가 찼나, 그 서버의 스레드 풀이나 연결 풀이 바닥났나. 다른 서버로 보내면 나아지는 문제들이다.

로드 밸런서 쪽에도 안전장치가 있다. AWS ALB는 대상 그룹의 모든 대상이 검사에 실패하면 모두를 건강하다고 보고 트래픽을 보낸다(fail open). Envoy는 건강한 호스트 비율이 패닉 문턱(기본 50%) 아래로 내려가면 건강 여부를 무시하고 모든 호스트로 나눈다. "다 빠지는 것보다는 아픈 서버에라도 보내는 게 낫다"는 판단이다. HAProxy는 기본으로 이런 동작이 없어서, 실습처럼 `<NOSRV>` 503이 된다. `backup` 서버를 두는 식으로 대신한다. 어느 쪽이든 이건 마지막 그물이다. 검사 기준을 잘 고르는 게 먼저다.

## 헬스 체크도 트래픽이다

깊은 검사는 의존성에 요청을 보낸다. 묻는 쪽이 많아지면 그 요청도 많아진다. Redis의 명령 통계로 10초 동안 PING이 몇 번 왔는지 셌다.

```bash
# 통계를 비우고 10초 뒤 PING 호출 수를 본다
redis-cli -p 19379 config resetstat
sleep 10
redis-cli -p 19379 info commandstats | grep ping
```

로드 밸런서 수와 캐시 설정을 바꿔 가며 세 번 쟀다.

```text
LB 1대:
cmdstat_ping:calls=30,usec=59,usec_per_call=1.97,rejected_calls=0,failed_calls=0
LB 2대:
cmdstat_ping:calls=60,usec=122,usec_per_call=2.03,rejected_calls=0,failed_calls=0
LB 2대, 결과 5초 캐시:
cmdstat_ping:calls=6,usec=14,usec_per_call=2.33,rejected_calls=0,failed_calls=0
```

서버 3대를 1초마다 물으니 초당 3번, HAProxy를 한 대 더 띄우니 두 배가 됐다. 실제 환경에서는 로드 밸런서 노드가 여러 개고(클라우드 로드 밸런서는 가용 영역마다 노드가 따로 검사한다), 쿠버네티스 kubelet도 따로 묻고, 바깥 감시도 묻는다. 서버가 수백 대면 의존성이 받는 검사 요청이 실제 트래픽보다 많아지기도 한다. 그리고 의존성이 느려지는 순간에도 검사 요청은 줄지 않는다.

마지막 줄은 서버가 의존성 검사 결과를 5초 동안 재사용하게 한 결과다. 묻는 쪽이 몇이든 서버 한 대당 5초에 한 번만 Redis에 간다. 아래에서 로드 밸런서 수, 서버 수, 검사 간격(초), 캐시 시간(초, 0이면 캐시 없음)을 받아 의존성이 받는 초당 검사 요청 수를 계산해 보자.

## 느린 의존성은 검사도 느리게 만든다

의존성이 죽는 것보다 흔한 건 느려지는 것이다. Redis를 6초 동안 멈추고(`CLIENT PAUSE`, 그 사이 모든 명령이 대기한다) 깊은 검사로 돌아갔다. s1과 s3는 의존성 검사 타임아웃이 300ms, s2는 일부러 10초로 띄웠다.

```bash
# Redis를 6초 동안 멈춘다: 연결은 되지만 응답이 오지 않는다
redis-cli -p 19379 client pause 6000 ALL
```

```text

Server be_api/s3 is DOWN, reason: Layer7 wrong status, code: 503, info: "Service Unavailable", check duration: 302ms. 1 active and 0 backup servers left. 0 sessions active, 0 requeued, 0 remaining in queue.
```

## 뜰 때 한 번 하는 검사

실행 중에 반복하는 검사와 별개로, 뜰 때 한 번 하는 검사가 있다. 여기서 확인할 것과 하지 말아야 할 것이 다르다.

설정은 뜰 때 확인하고, 틀리면 바로 죽는다(fail fast). 필수 환경 변수가 없거나, 비밀번호 파일을 못 읽거나, 설정 값이 범위를 벗어나면 서버는 시작하지 않아야 한다. 틀린 설정으로 떠서 요청을 받기 시작하면 실패가 사용자에게 간다. 바로 죽으면 배포가 멈추고 이전 버전이 계속 서비스한다.

반대로 의존성은 뜰 때 "없으면 죽는다"로 만들지 않는다. DB가 잠깐 재시작 중일 때 모든 서버가 동시에 배포되거나 재시작되면, 전부 죽고 다시 떠서 또 죽는 고리를 돈다. 의존성은 연결을 재시도하며 기다리고, 그동안 readiness를 실패로 둬서 트래픽만 받지 않는다.

## 검사 엔드포인트를 만들 때 정할 것들

엔드포인트를 둘로 나눈다. 프로세스만 보는 `/livez`와 그 서버만의 준비 상태를 보는 `/readyz`다. 쿠버네티스 API 서버도 이 이름을 쓰고, 예전의 `/healthz` 하나는 1.16부터 사용 중단(deprecated)으로 바뀌었다. Spring Boot는 2.3부터 `/actuator/health/liveness`와 `/actuator/health/readiness`를 따로 준다. 이름은 달라도 생각은 같다.

검사는 빠르고 부작용이 없어야 한다. 쓰기 쿼리, 외부 결제 API 호출, 로그 대량 출력 같은 건 넣지 않는다. 검사 요청은 하루에 수십만 번 온다.

인증을 걸면 로드 밸런서가 못 묻는다. 그래서 보통 인증 없이 열어 두는데, 그러면 아무나 볼 수 있다. 항목별 결과(어떤 DB를 쓰는지, 버전, 내부 호스트 이름)는 내부 전용 포트나 내부 경로로만 보이게 하고, 공개 경로에는 상태 코드와 짧은 본문만 둔다.

접근 로그와 지표에서 검사 요청을 따로 표시한다. 그대로 두면 로그의 상당 부분이 검사로 차고, 검사가 대부분 성공하니 성공률을 실제보다 좋게 만든다. SLI에서 검사 요청을 빼는 이유는 [SLI와 SLO 글](/posts/sli-slo)에 있다.

검사도 판정 숫자가 있다. 너무 예민하면(간격 짧고 fall 1) 순간 지연에 서버가 빠졌다 들어오기를 반복하고, 너무 둔하면 죽은 서버로 오래 보낸다. 숫자를 고르는 법은 [로드 밸런서 기본](/posts/load-balancer-basics)에서 다뤘다.

## 헬스 체크가 장애를 만드는 순간

현장에서는 헬스 체크가 장애를 막기보다 키우는 경우가 꽤 있다. 증상으로 거꾸로 찾아가면 이렇다.

서버는 다 떠 있는데 로드 밸런서가 503을 준다. HAProxy라면 로그에 `<NOSRV>`와 `has no server available!`, 클라우드 로드 밸런서라면 대상 그룹이 모두 unhealthy다. 서버에 직접 검사 경로를 두드려 본문을 읽는다. 공유 의존성 이름이 fail로 찍혀 있다면 이 글의 첫 장면이다. 급하게는 검사 경로를 얕은 쪽으로 바꾸고, 길게는 깊은 검사에서 공유 의존성을 뺀다.

서버가 주기적으로 빠졌다 들어온다. 검사 응답 시간을 본다. `check duration`이 검사 간격이나 타임아웃에 가깝다면 서버가 바쁠 때 검사가 밀리는 것이다. 검사 핸들러가 일반 요청과 같은 스레드 풀이나 큐를 쓰면, 바쁠 때 검사부터 늦어져서 바쁜 서버가 빠지고 남은 서버가 더 바빠진다. 검사를 가볍게 하고, 판정 숫자를 조금 둔하게 한다.

의존성이 느려지면서 검사 요청이 그 의존성을 더 누른다. 의존성의 연결 수와 초당 요청을 보고, 검사 출처(로드 밸런서 노드 IP)별로 나눠 본다. 캐시와 백그라운드 갱신으로 검사 부하를 고정한다.

새 버전이 배포되자마자 트래픽을 받고 첫 몇 초 동안 오류가 난다. readiness가 준비를 제대로 보지 않거나, 시작하자마자 200을 준다. 준비가 끝난 뒤에 200으로 바뀌게 고친다.

<Callout kind="warning" title="운영 중에 검사 경로를 바꿀 때">
검사 경로나 기대 상태 코드를 바꾸는 설정을 한 번에 모든 로드 밸런서에 올리면, 새 경로가 아직 없는 서버들이 한꺼번에 빠질 수 있다. 서버 쪽에 새 경로를 먼저 배포하고, 직접 두드려 200을 확인한 뒤 로드 밸런서 설정을 바꾼다. HAProxy는 `haproxy -c -f`로 문법을 검사하고 reload로 적용하며, 문제가 생기면 이전 설정 파일로 다시 reload하면 된다.
</Callout>

## 다시 상품 목록 503 앞에서

Redis가 잠깐 내려간 일은 장바구니만의 문제였다. 그런데 검사가 Redis를 확인한 탓에 세 서버가 같은 순간 "나는 못 받는다"고 답했고, 로드 밸런서는 줄 곳이 없어 모든 요청에 503을 줬다. 트래픽을 빼는 검사에는 그 서버만의 사정만 넣고, 공유 의존성의 장애는 요청 단위로 빠르게 실패시키며 알림으로 사람에게 알린다. 검사는 빠르고 가볍게, 안쪽 타임아웃은 짧게, 결과는 잠깐 캐시하고, 설정은 뜰 때 확인해 바로 죽는다. 묻는 쪽이 실패에 무엇을 하는지 먼저 떠올리면 무엇을 확인할지는 대부분 정해진다.

## 면접에서 나올 만한 질문

### 얕은 헬스 체크와 깊은 헬스 체크는 어떻게 다르고, 언제 무엇을 쓰나요

얕은 검사는 프로세스가 요청에 응답할 수 있는지만 보고, 깊은 검사는 DB·캐시 같은 의존성까지 실제로 확인한다. 트래픽을 빼거나 재시작하는 검사에는 그 행동으로 나아지는 문제만 넣어야 해서, 보통 얕은 검사와 그 서버만의 준비 상태를 쓴다. 의존성 상태는 사람이 보는 진단 경로나 바깥 감시와 알림에서 확인한다.

### 깊은 검사가 왜 연쇄 장애를 만드나요

여러 서버가 같은 의존성을 확인하면, 그 의존성 하나가 죽을 때 모든 서버가 같은 순간 실패를 답한다. 로드 밸런서는 전부 빼고 직접 503을 준다. 실습에서도 Redis를 내리자 3초 만에 세 서버가 빠져 Redis가 필요 없는 상품 목록까지 503이 됐다. 다른 서버로 보내도 결과가 같은 문제를 트래픽 판정에 넣은 탓이다.

### 그럼 의존성이 죽었을 때 서버는 어떻게 동작해야 하나요

트래픽에서 빠지지 않고, 그 의존성이 필요한 요청만 빠르게 실패시킨다. 실습에서 얕은 검사로 바꾸자 장바구니만 503을 받고 상품 목록은 계속 됐다. 요청 단위로는 짧은 타임아웃과 서킷 브레이커로 빨리 포기하고, 의존성 장애 자체는 알림이 사람에게 알린다.

### 헬스 체크가 의존성에 주는 부하는 어떻게 줄이나요

묻는 쪽 수 × 서버 수 / 검사 간격만큼 요청이 가니, 로드 밸런서 노드와 서버가 많으면 커진다. 실습에서도 HAProxy를 한 대 더 띄우자 Redis PING이 두 배가 됐다. 서버가 검사 결과를 몇 초 캐시하거나 백그라운드에서 갱신해 엔드포인트는 마지막 결과만 읽게 하면, 묻는 쪽이 몇이든 의존성 부하가 일정해진다. 5초 캐시로 10초 PING이 60번에서 6번으로 줄었다.

### 검사 안의 의존성 타임아웃은 어떻게 잡나요

검사 간격과 로드 밸런서의 검사 타임아웃보다 한참 짧게 잡는다. 안쪽이 길면 바깥이 먼저 포기해서 실패 이유가 `Layer7 timeout`으로만 남고, 포기한 검사의 의존성 연결이 서버 안에 쌓인다. 짧게 잡으면 서버가 스스로 원인을 담은 503을 돌려주고 연결도 정리된다.

### 모든 서버가 헬스 체크에 실패하면 로드 밸런서는 어떻게 하나요

제품마다 다르다. AWS ALB는 모든 대상이 실패하면 모두에게 보내는 fail open으로 동작하고, Envoy는 건강한 호스트가 패닉 문턱(기본 50%) 아래면 건강 여부를 무시하고 나눈다. HAProxy는 기본으로 그런 동작이 없어 503을 주니 backup 서버로 대신한다. 이런 장치는 마지막 그물이고, 먼저 검사 기준이 공유 의존성에 묶이지 않게 해야 한다.

### 서버가 뜰 때는 무엇을 확인하나요

설정과 비밀 값은 뜰 때 확인하고 틀리면 바로 죽어서 배포가 멈추게 한다. 의존성은 없다고 죽지 않고 재시도하며 기다리고, 그동안 readiness를 실패로 둬서 트래픽만 받지 않는다. 의존성 때문에 죽게 만들면 DB가 잠깐 재시작할 때 모든 서버가 함께 죽고 다시 뜨는 고리를 돈다.
