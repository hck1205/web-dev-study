[My Calendar I](https://leetcode.com/problems/my-calendar-i/)은 LeetCode 729번이다. `book(start, end)`가 호출될 때마다 이미 받은 예약과 겹치는지 보고, 겹치지 않으면 받아서 `true`를, 겹치면 받지 않고 `false`를 돌려주는 달력 클래스를 만든다.

지금까지 구간 문제는 구간 목록이 한꺼번에 주어졌다. 이 문제는 구간이 하나씩 들어오고, 그때마다 바로 답해야 한다. 그래서 "한 번 정렬하고 훑기"를 쓸 수 없고, 정렬된 상태를 유지하면서 빠르게 찾고 넣는 자료구조가 필요하다. [Meeting Rooms](/posts/leetcode-meeting-rooms) 글 끝에서 TreeMap 풀이를 짧게 소개했는데, 이 글은 그 풀이를 포함해 다섯 가지를 비교하고 이중·삼중 예약으로 넓히는 길까지 본다. 겹침 판정과 끝점 경계는 [구간 문제 패턴](/posts/interval-problems-pattern)에, 이분 탐색은 [이분 탐색 글](/posts/binary-search)에 있다. 코드는 Node.js 22, Python 3.13, Java 21에서 돌렸다.

## 겹치면 거절하는 달력

`MyCalendar` 클래스를 만든다. 생성자는 빈 달력을 만들고, `book(start, end)`는 반쯤 열린 구간 `[start, end)`를 예약하려고 시도한다. 받은 예약 중 하나라도 겹치면 `false`를 돌려주고 달력은 그대로 둔다. 겹치지 않으면 예약을 넣고 `true`다.

풀이를 고르는 데 영향을 주는 조건은 이렇다.

- `book`은 많아야 1,000번 호출된다. 호출마다 O(n)이어도 전체 50만 번 비교라 통과는 한다.
- 시각은 0 이상 10^9 이하이고 `start < end`다. 시각마다 칸을 만드는 배열은 쓸 수 없다.
- 구간은 `[start, end)`다. `[10, 20)`과 `[20, 30)`은 겹치지 않는다.
- 거절한 예약은 달력에 남지 않는다. 그래서 달력 안의 예약끼리는 언제나 서로 겹치지 않는다.

마지막 조건이 이 문제를 쉽게 만드는 불변식이다. 달력 안의 예약은 "정렬하면 서로 떨어져 있는 구간 목록"이고, 이 성질을 끝까지 지키는 게 풀이의 바닥이 된다.

## 겹침 판정은 부등식 두 개

반쯤 열린 구간 `[s, e)`와 `[bs, be)`가 겹치는 조건은 `s < be && bs < e`다. 겹치지 않는 경우는 "새 구간이 완전히 앞"(`e <= bs`)이거나 "완전히 뒤"(`be <= s`) 둘뿐이고, 그 둘의 부정을 쓴 것이다. 등호가 없어서 끝점이 닿는 경우는 겹치지 않는다.

이 식을 "새 구간의 시작이나 끝이 기존 예약 안에 들어가나"로 바꿔 쓰는 실수가 흔하다.

```js
const overlap = (bs <= s && s < be) || (bs < e && e <= be);   // 끝점이 안에 들어가는지만 본다
```

`[3, 4)`가 있는 달력에 `[1, 10)`을 넣으면 이 식은 겹치지 않는다고 판정한다. 새 구간의 시작 1도 끝 10도 `[3, 4)` 안에 없기 때문이다. 하지만 새 구간이 기존 예약을 통째로 품고 있다. 경우를 나누지 말고 부등식 두 개를 쓴다.

## 받은 예약을 모두 훑는다

가장 단순한 달력은 받은 예약을 배열에 쌓고, 요청마다 전부와 비교한다.

```js
class MyCalendar {
  constructor() { this.books = []; }
  book(s, e) {
    for (const [bs, be] of this.books) {
      if (s < be && bs < e) return false;   // 하나라도 겹치면 거절
    }
    this.books.push([s, e]);
    return true;
  }
}
```

요청 하나에 O(n), n번 호출하면 O(n²)이다. 공간 O(n). 호출 1,000번(무작위 시각)에서 2.6ms로 이 문제의 제한에서는 충분하다. 호출이 10만 번이면 32.6초가 걸렸다. 받은 예약끼리 겹치지 않는다는 불변식을 전혀 쓰지 않아서, 멀리 떨어진 예약까지 다 비교한다.

## 시작 순으로 꽂아 두고 양옆만 본다

예약을 시작 순으로 정렬된 배열에 담아 두자. 새 요청 `[s, e)`가 오면 이분 탐색으로 "시작이 s 이상인 첫 예약"의 자리 `lo`를 찾는다. 그러면 바로 앞 예약은 `lo - 1`, 바로 뒤 예약은 `lo`다. 이 둘만 보면 된다.

```js
class MyCalendar {
  constructor() { this.books = []; }        // [시작, 끝]을 시작 순으로
  book(s, e) {
    const a = this.books;
    let lo = 0, hi = a.length;              // 시작이 s 이상인 첫 자리
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (a[mid][0] < s) lo = mid + 1; else hi = mid;
    }
    if (lo > 0 && a[lo - 1][1] > s) return false;     // 앞 예약이 s 이후까지 이어진다
    if (lo < a.length && a[lo][0] < e) return false;  // 뒤 예약이 e 전에 시작한다
    a.splice(lo, 0, [s, e]);                          // 그 자리에 끼워 넣는다
    return true;
  }
}
```

### 양옆 둘이면 충분한 이유

달력 안의 예약은 서로 겹치지 않고 시작 순으로 정렬돼 있다. 그러면 끝도 시작 순서와 같은 순서로 정렬된다. 앞 예약이 끝나야 다음 예약이 시작하니까.

새 요청보다 앞에 있는 예약(시작이 s보다 작은 것) 중 새 요청과 겹칠 수 있는 건 끝이 s보다 큰 것이다. 끝이 정렬돼 있으니 그런 예약이 있다면 가장 뒤의 것, 즉 바로 앞 예약 `a[lo - 1]`이 반드시 그중 하나다. 바로 앞 예약의 끝이 s 이하면 더 앞의 예약은 더 일찍 끝나서 모두 괜찮다.

뒤쪽도 같다. 시작이 s 이상인 예약 중 새 요청과 겹칠 수 있는 건 시작이 e보다 작은 것이다. 시작이 정렬돼 있으니 가장 앞의 것, 바로 뒤 예약 `a[lo]`를 보면 된다. 그 시작이 e 이상이면 더 뒤의 예약은 더 늦게 시작한다.

이 논증은 "달력 안의 예약끼리는 겹치지 않는다"가 깨지면 성립하지 않는다. 거절한 예약을 넣지 않는다는 규칙이 매 호출마다 불변식을 지킨다.

복잡도는 이분 탐색 O(log n)에 `splice`의 끼워 넣기 O(n)이 더해진다. 끼워 넣을 때 뒤의 원소를 한 칸씩 밀어야 하기 때문이다. 그래도 원소 이동은 메모리를 연속으로 옮기는 일이라 빠르다. 호출 10만 번(무작위)에서 641ms였고, 요청이 시간 순으로 들어오면 늘 끝에 붙어서 33ms였다. 이 문제의 제한에서는 이 풀이로 충분하고, 표준 라이브러리에 균형 트리가 없는 JavaScript와 Python에서 가장 현실적인 답이다.

## 예약을 나무에 매단다

끼워 넣기 O(n)이 거슬린다면 이진 탐색 트리를 직접 만들 수 있다. 노드마다 예약 하나를 담고, 새 요청이 그 노드보다 완전히 앞이면(`e <= 노드.시작`) 왼쪽으로, 완전히 뒤면(`s >= 노드.끝`) 오른쪽으로 내려간다. 둘 다 아니면 겹치니 거절이다. 빈 자리에 닿으면 거기에 매단다.

```js
class MyCalendar {
  constructor() { this.root = null; }
  book(s, e) {
    const node = { s, e, left: null, right: null };
    if (!this.root) { this.root = node; return true; }
    let cur = this.root;
    for (;;) {
      if (e <= cur.s) {                       // 완전히 앞
        if (!cur.left) { cur.left = node; return true; }
        cur = cur.left;
      } else if (s >= cur.e) {                // 완전히 뒤
        if (!cur.right) { cur.right = node; return true; }
        cur = cur.right;
      } else {
        return false;                         // 이 노드와 겹친다
      }
    }
  }
}
```

내려가는 길에 만나는 노드만 확인하는데도 맞는 이유는 앞 절과 같다. 왼쪽으로 내려가는 순간 오른쪽 부분 트리의 예약은 전부 지금 노드보다 뒤에 있으니, 지금 노드보다 앞에 있는 새 요청과 만날 수 없다.

시간은 트리 높이 h에 비례해 호출 하나에 O(h)다. 요청이 무작위로 오면 h는 O(log n) 정도라 호출 10만 번에 33ms로 가장 빨랐다. 하지만 요청이 시간 순으로 오면 모든 노드가 오른쪽으로만 매달려 트리가 한 줄이 된다. 1,000번 넣었을 때 깊이가 1,000이었고, 10만 번에서는 14.1초가 걸렸다. 같은 입력에서 정렬 배열은 33ms였다. 예약 시스템에 들어오는 요청은 대개 시간 순에 가까워서, 균형을 잡지 않는 트리는 실제 데이터에서 오히려 가장 나쁠 수 있다.

## 균형 트리가 있는 언어라면

Java의 `TreeMap`은 레드블랙 트리라 높이가 늘 O(log n)이다. "s 이하인 가장 큰 키"(`floorEntry`)와 "s 이상인 가장 작은 키"(`ceilingKey`)를 O(log n)에 찾고, 넣기도 O(log n)이다. 앞 절의 양옆 확인을 그대로 옮기면 된다.

```java
import java.util.*;

public class MyCalendar {
    private final TreeMap<Integer, Integer> books = new TreeMap<>();   // 시작 -> 끝

    public boolean book(int start, int end) {
        Map.Entry<Integer, Integer> prev = books.floorEntry(start);    // 시작이 start 이하인 마지막 예약
        Integer next = books.ceilingKey(start);                         // 시작이 start 이상인 첫 예약의 시작
        if (prev != null && prev.getValue() > start) return false;     // 앞 예약이 아직 안 끝났다
        if (next != null && next < end) return false;                  // 뒤 예약이 내가 끝나기 전에 시작한다
        books.put(start, end);
        return true;
    }

    public static void main(String[] args) {
        MyCalendar cal = new MyCalendar();
        int[][] req = {{10, 20}, {15, 25}, {20, 30}, {5, 10}, {8, 12}, {30, 35}};
        StringBuilder sb = new StringBuilder();
        for (int[] r : req) sb.append(cal.book(r[0], r[1])).append(' ');
        System.out.println(sb.toString().trim());
    }
}
```

```text
true false true true false true
```

시작이 정확히 같은 예약이 이미 있으면 `floorEntry`와 `ceilingKey`가 둘 다 그 예약을 가리킨다. 그 예약의 끝은 start보다 크니 첫 번째 검사에서 거절된다. 키가 시작 시각이라 같은 시작의 예약 두 개를 담을 수 없는데, 그런 두 예약은 반드시 겹치니 문제가 되지 않는다.

시간은 호출 하나에 O(log n), 공간 O(n)이다. 요청 순서와 상관없이 일정하다. Java로 푼다면 이게 기본 답이다.

Python 표준 라이브러리에는 균형 트리가 없다. `bisect`로 정렬 리스트를 유지하는 것이 JavaScript의 정렬 배열 풀이와 같은 방법이다.

```python
from bisect import bisect_left

class MyCalendar:
    def __init__(self):
        self.books = []                      # (시작, 끝)을 시작 순으로 정렬해 둔다

    def book(self, start, end):
        i = bisect_left(self.books, start, key=lambda b: b[0])  # 시작이 start 이상인 첫 자리 (3.10+)
        if i > 0 and self.books[i - 1][1] > start:              # 앞 예약이 아직 안 끝났다
            return False
        if i < len(self.books) and self.books[i][0] < end:      # 뒤 예약이 내가 끝나기 전에 시작한다
            return False
        self.books.insert(i, (start, end))                      # O(n) 끼워 넣기
        return True

cal = MyCalendar()
print([cal.book(s, e) for s, e in [(10, 20), (15, 25), (20, 30), (5, 10), (8, 12), (30, 35)]])
```

```text
[True, False, True, True, False, True]
```

`bisect_left`의 `key` 인자는 Python 3.10부터 있다. 그 전 버전이라면 시작 시각만 담은 리스트를 따로 두고 두 리스트를 같이 `insert`한다.

```python
from bisect import bisect_left

class MyCalendar:
    def __init__(self):
        self.starts, self.ends = [], []      # 같은 인덱스가 같은 예약

    def book(self, start, end):
        i = bisect_left(self.starts, start)
        if i > 0 and self.ends[i - 1] > start:
            return False
        if i < len(self.starts) and self.starts[i] < end:
            return False
        self.starts.insert(i, start)         # 두 리스트를 같은 자리에 함께 넣는다
        self.ends.insert(i, end)
        return True

cal = MyCalendar()
print([cal.book(s, e) for s, e in [(10, 20), (15, 25), (20, 30), (5, 10), (8, 12), (30, 35)]])
```

```text
[True, False, True, True, False, True]
```

두 리스트가 같은 자리에 같이 들어가야 인덱스가 맞는다. 한쪽만 넣는 실수를 막으려면 넣기를 한 곳에 모아 둔다. LeetCode의 Python 환경에는 서드파티 `sortedcontainers`가 들어 있어서 `SortedList`로 O(log n)에 가까운 넣기를 쓸 수 있지만, 일반 코딩 테스트 환경에는 없을 수 있다.

## 시각 축 전체를 나무로 나눈다

지금까지는 예약을 담는 자료구조였다. 반대로 시각 축 `[0, 10^9)`를 반씩 나눠 가는 세그먼트 트리를 만들고, 노드마다 "이 범위에 예약이 하나라도 있나"와 "이 범위가 통째로 예약됐나"를 적을 수도 있다. 범위가 10억이라 노드를 미리 다 만들 수 없으니, 필요할 때만 자식을 만드는 동적 세그먼트 트리로 짠다.

```js
class MyCalendar {
  constructor() { this.root = { full: false, any: false }; }
  query(n, lo, hi, s, e) {                  // [s, e)와 [lo, hi)가 만나는 곳에 예약이 있나
    if (!n || !n.any || e <= lo || hi <= s) return false;
    if (n.full || (s <= lo && hi <= e)) return true;
    const mid = Math.floor((lo + hi) / 2);
    return this.query(n.l, lo, mid, s, e) || this.query(n.r, mid, hi, s, e);
  }
  fill(n, lo, hi, s, e) {                   // [s, e)를 예약으로 채운다
    if (e <= lo || hi <= s || n.full) return;
    n.any = true;
    if (s <= lo && hi <= e) { n.full = true; return; }
    const mid = Math.floor((lo + hi) / 2);
    n.l ??= { full: false, any: false };
    n.r ??= { full: false, any: false };
    this.fill(n.l, lo, mid, s, e);
    this.fill(n.r, mid, hi, s, e);
  }
  book(s, e) {
    if (this.query(this.root, 0, 1e9, s, e)) return false;
    this.fill(this.root, 0, 1e9, s, e);
    return true;
  }
}
```

구간 하나는 트리의 각 깊이에서 많아야 노드 몇 개로 쪼개지고, 깊이는 log₂(10^9) ≈ 30이다. 그래서 호출 하나에 O(log C), C는 시각 범위다. 호출 10만 번에서 1,239ms로 이 문제만 보면 느리고 코드도 길다. 노드를 객체로 만들고 재귀를 도는 비용이다.

이 풀이를 알아 두는 이유는 확장성이다. `any`, `full` 대신 "이 범위에서 겹친 예약 수의 최댓값"과 "범위 전체에 더할 값"(지연 전파)을 적으면, 이중 예약까지 허용하는 731번 My Calendar II와 최대 겹침 수를 묻는 732번 My Calendar III를 같은 틀로 푼다. 예약을 담는 자료구조로는 이 변형들에서 "양옆 둘만 본다"가 무너진다. 달력 안의 예약끼리 겹칠 수 있게 되기 때문이다.

## 겹침 수를 세는 장부로

732번에서 많이 쓰는 또 하나의 방법은 [Car Pooling](/posts/leetcode-car-pooling)의 차분 장부다. 시각을 키로 하는 맵에 시작 +1, 끝 −1을 적고, 요청마다 키 순으로 누적하며 2 이상이 되는 곳이 있는지 본다. 있으면 방금 적은 두 칸을 되돌리고 거절한다.

```js
class MyCalendar {
  constructor() { this.diff = new Map(); }
  book(s, e) {
    const d = this.diff;
    d.set(s, (d.get(s) ?? 0) + 1);
    d.set(e, (d.get(e) ?? 0) - 1);
    let cur = 0, ok = true;
    for (const k of [...d.keys()].sort((x, y) => x - y)) {   // 시각 순으로 누적
      cur += d.get(k);
      if (cur > 1) { ok = false; break; }                    // 두 예약이 겹치는 순간이 있다
    }
    if (!ok) { d.set(s, d.get(s) - 1); d.set(e, d.get(e) + 1); }  // 되돌린다
    return ok;
  }
}
```

JavaScript의 `Map`은 정렬되지 않아서 요청마다 키를 정렬했다. 호출 하나에 O(n log n), 1,000번에서 156ms로 가장 느렸다. Java라면 `TreeMap`이 이미 정렬돼 있어 O(n)이다. 이 문제에는 과하지만 `cur > 1`의 1을 2로 바꾸면 그대로 My Calendar II가 되고, `cur`의 최댓값을 돌려주면 III이 된다. 세 문제를 한 코드로 묶어 설명할 수 있다는 게 장점이다.

## 다섯 달력에 같은 요청을 넣어 본다

바로 앞 예약만 보는 정렬 배열 코드를 모두 훑기 풀이와 같은 방식으로 맞춰 봤더니 세 번째 묶음에서 갈렸다. `[[24,28],[13,14],[16,21],[3,6],[16,17]]`의 마지막 요청 `[16, 17)`이다. 이미 같은 시각에 시작하는 `[16, 21)`이 있는데, 이분 탐색이 찾은 자리 바로 앞은 `[13, 14)`라 앞만 보는 코드는 받아 버렸다. 시작이 같은 예약은 "바로 뒤" 자리에 있다는 것을 보여 주는 반례다.

## 호출 수와 입력 순서로 고른다

| 풀이 | 호출 하나 | 공간 | 언제 고르나 |
|---|---|---|---|
| 모두 훑기 | O(n) | O(n) | 호출이 적을 때. 검증 기준 |
| 정렬 배열 + 이분 탐색 | O(log n) 찾기 + O(n) 넣기 | O(n) | JavaScript, Python의 현실적인 답 |
| 직접 만든 이진 탐색 트리 | 평균 O(log n), 최악 O(n) | O(n) | 요청이 무작위일 때만. 시간 순 입력에서 무너진다 |
| TreeMap (균형 트리) | O(log n) | O(n) | Java의 기본 답 |
| 동적 세그먼트 트리 | O(log C) | O(n log C) | 이중·삼중 예약으로 넓힐 때 |
| 차분 맵 | O(n) ~ O(n log n) | O(n) | II, III과 한 코드로 설명할 때 |

C는 시각 범위(10^9)다. 호출 10만 번(무작위)에서 직접 만든 트리 33ms, 정렬 배열 641ms, 세그먼트 트리 1,239ms, 모두 훑기 32.6초였다. 시간 순 요청 10만 번에서는 정렬 배열 33ms, 세그먼트 트리 356ms, 직접 만든 트리 14.1초, 모두 훑기 13.9초였다. 입력 순서 하나로 1등과 꼴찌가 뒤바뀐다.

## 경계 하나로 예약이 잘못 받아지는 코드

### 바로 앞 예약만 본다

```js
if (lo > 0 && a[lo - 1][1] > s) return false;
// 뒤 예약 확인을 빠뜨렸다
a.splice(lo, 0, [s, e]);
```

`book(10, 20)` 다음 `book(5, 12)`를 받아 버린다. `[5, 12)`의 자리는 0이라 앞 예약이 없다. 겹치는 `[10, 20)`은 뒤에 있다. 앞만 보는 건 "새 요청이 기존 예약 뒤에서 시작하는" 경우만 막는다. 새 요청이 먼저 시작해서 기존 예약을 덮치는 경우는 뒤 예약 확인이 막는다.

### 비교에 등호를 넣는다

```js
if (s <= be && bs <= e) return false;   // 닿아도 겹친다고 본다
```

`book(10, 20)` 다음 `book(20, 30)`을 거절한다. 반쯤 열린 구간이라 20에 끝나는 예약과 20에 시작하는 예약은 함께 들어갈 수 있다. 정렬 배열 풀이라면 `a[lo - 1][1] >= s`나 `a[lo][0] <= e`로 쓴 경우가 같은 버그다.

### Java에서 null을 int로 받는다

```java
int prevStart = books.floorKey(10);   // 비어 있으면 null을 int에 넣으려다 터진다
```

빈 달력에서 `NullPointerException`이 난다. `floorKey`, `ceilingKey`, `floorEntry`는 해당하는 키가 없으면 `null`을 돌려준다. `Integer`로 받고 `null`인지 먼저 확인한다. 위 TreeMap 코드가 `Integer next`로 받은 이유다.

### 거절한 요청을 달력에 남긴다

차분 맵 풀이에서 되돌리기를 빠뜨리면 거절한 요청의 +1, −1이 장부에 남는다. 다음 요청은 실제로는 비어 있는 시간인데도 유령 예약과 겹쳐 거절된다. 예약을 먼저 넣고 검사하는 코드는 늘 "실패하면 되돌리기"를 짝으로 쓴다. 다른 풀이들은 검사를 통과한 뒤에만 넣어서 이 문제가 없다.

### 정렬된 요청에 균형 없는 트리를 쓴다

틀린 답은 아니지만 시간 초과의 원인이다. 앞에서 본 대로 시간 순 요청 10만 번에 14초가 걸렸다. 면접에서 직접 BST를 짰다면 "입력이 정렬돼 있으면 한 줄로 기울어서 O(n)이 된다, 그래서 실제로는 균형 트리를 쓴다"를 함께 말한다.

## 이중 예약까지 받는다면

### 같은 시간에 두 예약까지는 허용한다면

731번 My Calendar II다. 예약이 두 겹으로 겹친 구간 목록을 따로 들고 간다. 새 요청이 그 두 겹 구간과 겹치면 거절하고, 아니면 기존 예약과 겹치는 부분을 두 겹 목록에 더한 뒤 예약을 넣는다. 겹치는 부분은 `[max(시작), min(끝)]`이다. 요청 하나에 O(n)이다. 또는 차분 맵에서 `cur > 2`로 판정한다.

```js
class MyCalendarTwo {
  constructor() {
    this.books = [];      // 받은 예약 전부 (서로 겹칠 수 있다)
    this.doubles = [];    // 두 겹으로 겹친 구간 (서로 겹치지 않는다)
  }
  book(s, e) {
    for (const [ds, de] of this.doubles) {
      if (s < de && ds < e) return false;               // 세 겹이 된다
    }
    for (const [bs, be] of this.books) {
      const lo = Math.max(s, bs), hi = Math.min(e, be);
      if (lo < hi) this.doubles.push([lo, hi]);         // 새로 두 겹이 되는 부분
    }
    this.books.push([s, e]);
    return true;
  }
}

const cal = new MyCalendarTwo();
console.log([[10, 20], [15, 25], [20, 30], [5, 10], [8, 12], [30, 35], [16, 18]].map(([s, e]) => cal.book(s, e)).join(" "));
```

```text
true true true true true true false
```

이 글의 여섯 요청은 두 겹까지 허용하면 모두 받아진다. `[15, 25)`는 `[10, 20)`과 15~20에서 두 겹이 되고, `[8, 12)`도 두 예약과 각각 두 겹이 될 뿐이다. 마지막에 더한 `[16, 18)`은 이미 두 겹인 15~20 안에 들어가 세 겹이 되니 거절한다. 두 겹 목록 안의 구간끼리는 서로 겹치지 않는다. 겹친다면 그곳이 이미 세 겹이라는 뜻이고, 그런 요청은 받지 않았기 때문이다. 시각마다 예약 수를 세는 풀이와 무작위 2만 묶음에서 같은 답을 냈다.

### 지금까지 가장 많이 겹친 수를 묻는다면

732번 My Calendar III다. 모든 요청을 받고, 요청마다 "동시에 겹친 예약 수의 최댓값"을 돌려준다. 차분 맵을 시각 순으로 누적한 최댓값이고, 호출이 많으면 지연 전파 세그먼트 트리로 O(log C)에 한다. 이 수가 [Meeting Rooms II](/posts/leetcode-meeting-rooms-ii)의 필요한 회의실 수와 같다. 배치로 주어지면 Meeting Rooms II, 하나씩 들어오면 My Calendar III다.

### 예약 취소도 지원하라면

정렬 배열이면 이분 탐색으로 찾아 `splice`로 지운다. TreeMap이면 `remove(start)`다. 직접 만든 BST라면 노드 삭제(자식 둘인 노드는 후계자와 바꾸기)를 짜야 해서 코드가 길어진다. 차분 맵은 +1, −1을 되돌리면 끝이다.

### 예약이 데이터베이스에 저장된다면

서버가 여러 대면 메모리 안의 달력 하나로는 동시에 들어온 두 요청을 막을 수 없다. 둘 다 "겹치는 예약 없음"을 읽고 둘 다 넣을 수 있다. PostgreSQL이라면 범위 타입과 배제 제약으로 겹침 검사를 데이터베이스에 맡길 수 있다. `tstzrange`의 기본 경계가 `[)`라서 이 문제와 같은 반쯤 열린 구간이고, 닿기만 하는 예약은 함께 들어간다.

```sql
-- 방 번호의 = 비교를 GiST 인덱스에서 쓰려면 btree_gist가 필요하다
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE bookings (
  room   int       NOT NULL,
  during tstzrange NOT NULL,
  EXCLUDE USING gist (room WITH =, during WITH &&)  -- 같은 방에서 시간이 겹치면 넣지 못한다
);
```

```sql
INSERT INTO bookings VALUES (1, tstzrange('2026-10-24 10:00+09', '2026-10-24 11:00+09'));  -- 들어간다
INSERT INTO bookings VALUES (1, tstzrange('2026-10-24 11:00+09', '2026-10-24 12:00+09'));  -- 닿기만 해서 들어간다
INSERT INTO bookings VALUES (1, tstzrange('2026-10-24 10:30+09', '2026-10-24 11:30+09'));  -- 겹친다
```

```text
INSERT 0 1
INSERT 0 1
ERROR:  conflicting key value violates exclusion constraint "bookings_room_during_excl"
DETAIL:  Key (room, during)=(1, ["2026-10-24 01:30:00+00","2026-10-24 02:30:00+00")) conflicts with existing key (room, during)=(1, ["2026-10-24 01:00:00+00","2026-10-24 02:00:00+00")).
```

PostgreSQL 16에서 돌린 결과다. `DETAIL`에 범위가 `[`로 열고 `)`로 닫혀 있는 게 반쯤 열린 구간이라는 표시다. 시각은 UTC로 바뀌어 찍혔다.

겹치는 예약을 넣으면 제약 위반 오류가 나고, 애플리케이션은 그걸 `false`로 바꿔 돌려주면 된다. 안에서 쓰는 GiST 인덱스가 하는 일이 이 글의 "정렬해 두고 근처만 본다"와 같다.

### 회의실이 여러 개라면

방마다 달력을 하나씩 두고, 방 번호 순으로 받아 주는 첫 방에 넣는다. 방이 k개면 요청 하나에 O(k log n)이다. "가장 먼저 비는 방"을 찾는 시뮬레이션은 2402번 Meeting Rooms III와 연결된다.

같은 묶음에서 이어 볼 문제로는 정렬된 목록에 구간 하나를 끼워 넣고 합치는 [Insert Interval](/posts/leetcode-insert-interval)(57번), 정렬된 두 목록의 교집합을 구하는 [Interval List Intersections](/posts/leetcode-interval-list-intersections)(986번), 모두의 빈 시간을 찾는 [Employee Free Time](/posts/leetcode-employee-free-time)(759번, 프리미엄 문제)이 있다.

## 면접에서 나올 만한 질문

### 두 예약이 겹치는지 어떻게 판정하나요?

반쯤 열린 구간 `[s, e)`와 `[bs, be)`는 `s < be && bs < e`일 때 겹친다. 겹치지 않는 경우가 완전히 앞이거나 완전히 뒤 둘뿐이라 그 부정이다. 등호가 없어서 끝점이 닿는 예약은 함께 받는다. 시작이나 끝이 안에 들어가는지만 보면 기존 예약을 품는 요청을 놓친다.

### 왜 바로 앞과 바로 뒤 예약만 보면 되나요?

달력 안의 예약은 서로 겹치지 않아서 시작 순으로 정렬하면 끝도 같은 순서로 정렬된다. 앞쪽에서 겹칠 수 있는 예약은 끝이 s보다 큰 것인데, 있다면 바로 앞 예약이 그중 하나다. 뒤쪽은 시작이 e보다 작은 것인데 바로 뒤 예약을 보면 된다. 거절한 예약을 넣지 않는 규칙이 이 불변식을 지킨다.

### 시간 복잡도는요?

Java TreeMap이면 호출 하나에 찾기와 넣기 모두 O(log n)이다. JavaScript나 Python에서 정렬 배열과 이분 탐색을 쓰면 찾기는 O(log n)이지만 끼워 넣기가 O(n)이다. 호출이 1,000번인 이 문제에서는 둘 다 충분하다.

### 이진 탐색 트리를 직접 짜면 안 되나요?

평균은 O(log n)이지만 균형을 잡지 않으면 요청이 시간 순으로 들어올 때 트리가 한 줄로 기울어 O(n)이 된다. 시간 순 요청 10만 번에서 14초가 걸렸다. 실제 예약 요청은 시간 순에 가까운 경우가 많아서, 직접 짠다면 이 약점을 먼저 말하고 실무에서는 레드블랙 트리 같은 균형 트리를 쓴다고 답한다.

### 이중 예약까지 허용하면 어떻게 바꾸나요?

달력 안의 예약끼리 겹칠 수 있게 되니 양옆만 보는 논증이 무너진다. 두 겹으로 겹친 구간 목록을 따로 들고 가서 새 요청이 그것과 겹치면 거절하거나, 시각별 차분 맵을 누적해 3 이상이 되는지 본다. 호출이 많으면 지연 전파 세그먼트 트리로 구간 최댓값을 관리한다.

### Meeting Rooms와는 어떤 관계인가요?

Meeting Rooms는 회의 목록이 한꺼번에 주어져서 한 번 정렬하고 이웃만 보면 됐다. 이 문제는 요청이 하나씩 오니 정렬된 상태를 유지하는 자료구조가 필요하다. 이웃만 본다는 원리는 같고, 정렬을 한 번 하느냐 매번 유지하느냐가 다르다.
