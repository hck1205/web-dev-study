이 시리즈에서 이 글의 자리: [② 웹과 DB 나누기](/posts/sd-split-web-and-db)에서 웹 계층과 데이터 계층을 나눈 다음 단계다. 다음 글은 [④ DB 복제](/posts/sd-db-replication-intro)다. 같은 장의 글은 [① 서버 한 대](/posts/sd-start-single-server), [⑤ 캐시와 CDN](/posts/sd-cache-and-cdn-tier), [⑥ 데이터 센터 여러 곳](/posts/sd-multi-datacenter), [⑦ 큐, 로그, 자동화](/posts/sd-queue-logging-automation), [⑧ 샤딩 입문](/posts/sd-sharding-intro)이다.

맛집 리뷰 앱은 이제 웹 서버 한 대와 DB 서버 한 대로 돈다. [① 서버 한 대](/posts/sd-start-single-server)에서 본 문제가 아직 남아 있다. 배포할 때마다 몇 초씩 모든 요청이 실패한다. 웹 서버가 한 대뿐이라 그 서버를 내리면 갈 곳이 없다.

그래서 웹 서버를 두 대로 늘리고 앞에 요청을 나눠 주는 장치를 붙였다. 배포 문제는 풀렸는데 다른 문제가 생겼다. 로그인한 사용자가 페이지를 몇 번 넘기면 갑자기 "로그인이 필요합니다"가 뜬다. 다시 누르면 또 멀쩡하다.

이 글은 웹 서버를 여러 대로 늘리는 데 필요한 두 가지를 다룬다. 요청을 나눠 주는 로드 밸런서, 그리고 어느 서버가 받아도 같은 답을 하도록 웹 서버에서 상태를 빼내는 일이다. 데모는 Node.js 22로 만든 웹 서버 두 대, 100줄이 안 되는 로드 밸런서, 세션을 담을 Redis 7.0으로 돌렸다.

## 서버가 두 대면 누가 나눠 주나

서버가 두 대가 되면 첫 질문은 "사용자는 어느 서버로 가나"다. DNS에 IP 두 개를 등록해 번갈아 알려 주는 방법도 있다. 하지만 DNS 답은 TTL 동안 클라이언트에 캐시되고, DNS는 서버가 살아 있는지 모른다. 한 대가 죽어도 그 IP를 계속 알려 준다. 그 차이는 [로드 밸런서 기본 글](/posts/load-balancer-basics)의 "DNS로 나누면 안 되나"에 자세히 있다.

그래서 앞에 로드 밸런서(LB, Load Balancer)를 둔다. 사용자는 로드 밸런서의 주소 하나만 알고, 로드 밸런서가 뒤에 있는 웹 서버 중 하나를 골라 요청을 넘긴다. DNS는 이제 웹 서버가 아니라 로드 밸런서의 공인 IP를 알려 준다. 웹 서버들은 사설 IP만 가지고 안쪽 망에 숨는다.

로드 밸런서가 생기면 두 가지가 해결된다. 한 대가 죽어도 나머지가 받는다(이중화, redundancy). 그리고 요청이 늘면 서버를 더 붙이기만 하면 된다(확장성, scalability). 배포할 때도 한 대씩 빼고 고친 뒤 다시 넣으면 서비스는 계속 돈다.

어느 서버를 고를지는 알고리즘이 정한다. 차례대로 도는 라운드 로빈이 가장 단순하고, 연결이 가장 적은 서버를 고르는 방식, 응답이 가장 빠른 서버를 고르는 방식도 있다. 이 글에서는 라운드 로빈만 쓴다. 나머지는 [로드 밸런싱 알고리즘 글](/posts/load-balancing-algorithms)에 있다.

## 로그인했는데 한 번씩 풀린다

로드 밸런서를 붙이자마자 이상한 일이 생겼다. 데모로 재현해 보자. 웹 서버 두 대는 로그인 세션을 자기 프로세스의 메모리(`Map`)에 저장한다. 서버 한 대일 때는 아무 문제 없던 코드다.

세션(session)은 서버가 "이 사용자는 로그인한 kim이다"를 기억해 두는 기록이다. 로그인하면 서버가 세션을 만들고, 그 번호(세션 ID)를 쿠키에 담아 브라우저에 준다. 브라우저는 다음 요청마다 쿠키를 같이 보내고, 서버는 번호로 세션을 찾는다.

```bash
# 로드 밸런서(8000)로 로그인한 뒤, 쿠키를 붙여 /me를 네 번 부른다
curl -s -c jar.txt -X POST 'http://127.0.0.1:8000/login?user=kim'
curl -s -b jar.txt -o - -w '%{http_code}\n' http://127.0.0.1:8000/me   # 네 번 반복
```

```text
{"server":"web1","login":"ok"}
{"server":"web2","error":"login required"}
401
{"server":"web1","user":"kim"}
200
{"server":"web2","error":"login required"}
401
{"server":"web1","user":"kim"}
200
```

로그인은 web1이 받았다. 세션도 web1의 메모리에만 생겼다. 그다음 요청이 web2로 가면 web2는 그 세션 번호를 처음 본다. 그래서 401(인증 필요)을 돌려준다. 라운드 로빈이니 정확히 한 번 걸러 한 번씩 풀린다.

이런 서버를 상태를 가진(stateful) 서버라고 한다. 요청에 답하려면 그 서버만 아는 정보가 필요한 서버다. 반대로 어느 서버가 받아도 같은 답을 할 수 있는 서버를 상태가 없는(stateless) 서버, 무상태 서버라고 한다.

## 상태를 빼내는 세 가지 방법

방법은 크게 세 가지다.

첫째, 같은 사용자를 늘 같은 서버로 보낸다. 세션 고정(sticky session)이라고 한다. 로드 밸런서가 쿠키를 보고 "이 사람은 web1 손님"이라고 기억한다. 코드를 안 고쳐도 되지만, web1이 죽거나 배포로 내려가면 그 손님들의 세션은 사라진다. 서버를 새로 늘려도 기존 손님은 옛 서버에 묶여 있어서 부하가 고르게 퍼지지 않는다. 설정 방법과 함정은 [로드 밸런서 기본 글](/posts/load-balancer-basics)에 있다.

둘째, 세션을 웹 서버 밖 공유 저장소로 옮긴다. 모든 웹 서버가 같은 Redis(메모리 기반 키-값 저장소)나 DB에서 세션을 읽는다. 어느 서버가 받아도 같은 세션을 본다. 시스템 설계 면접에서 기본으로 기대하는 답이 이것이다.

셋째, 서버가 아무것도 기억하지 않고 필요한 정보를 서명한 토큰(JWT 등)에 담아 클라이언트가 들고 다니게 한다. 저장소가 필요 없지만, 이미 내준 토큰을 중간에 무효로 만들기 어렵다. 이 방식은 [토큰 로그인 글](/posts/token-login)에서 다룬다.

## 세션을 Redis로 옮겨 보기

데모의 웹 서버 코드에서 세션을 저장하는 두 줄만 바꿨다. `Map`에 넣던 것을 Redis에 넣는다. 키는 `sess:세션번호`, 값은 JSON, 만료는 30분이다.

```js
// 메모리: mem.set(sid, data)   →   Redis: 30분(1800초) 뒤 자동으로 지워진다
await redis.set(`sess:${sid}`, JSON.stringify(data), { EX: 1800 });
const s = JSON.parse((await redis.get(`sess:${sid}`)) ?? "null");
```

같은 요청을 다시 보냈다.

```text
{"server":"web1","login":"ok"}
{"server":"web2","user":"kim"}
200
{"server":"web1","user":"kim"}
200
{"server":"web2","user":"kim"}
200
{"server":"web1","user":"kim"}
200
```

web1에서 로그인했는데 web2도 kim을 알아본다. 둘 다 같은 Redis를 보기 때문이다. Redis에 들어간 세션도 직접 확인할 수 있다.

```bash
# 세션 값과 남은 수명(초)을 본다
redis-cli -p 7201 GET sess:f2130b8fa4829e0d
redis-cli -p 7201 TTL sess:f2130b8fa4829e0d
```

```text
{"user":"kim"}
1800
```

`TTL`이 1800이면 30분 뒤 이 세션은 자동으로 사라진다. 메모리 저장소에 만료를 걸지 않으면 로그아웃하지 않은 세션이 영원히 쌓인다. 쿠키 쪽 옵션(`HttpOnly`, `Secure`, `SameSite`)과 세션 탈취 대응은 [쿠키와 세션 로그인 글](/posts/cookie-session-login)에 있다.

## 세션 말고도 숨은 상태가 있다

로그인 세션은 눈에 잘 띄는 상태다. 웹 서버를 여러 대로 늘리면 덜 눈에 띄는 상태들이 하나씩 문제를 일으킨다.

업로드한 파일을 웹 서버 디스크에 저장하면, web1에 올린 사진을 web2는 보여 주지 못한다. 파일은 S3 같은 객체 저장소에 둔다.

프로세스 안에 둔 캐시(예: 메모리에 저장한 인기 목록)는 서버마다 값이 달라진다. web1은 5분 전 순위를, web2는 방금 순위를 보여 준다. 사용자가 새로고침할 때마다 순위가 바뀌어 보인다. 잠깐 어긋나도 되는 값만 로컬 캐시에 두고, 나머지는 공유 캐시로 간다.

서버마다 같이 도는 예약 작업도 상태의 일종이다. "매일 밤 12시에 쿠폰 발송"을 웹 서버 코드에 넣어 두면 서버가 세 대일 때 쿠폰이 세 번 나간다. 이런 작업은 웹 서버 밖의 작업 실행기 한 곳에서 돌리거나, 실행 전에 락을 잡는다. 이 부분은 [⑦ 큐, 로그, 자동화](/posts/sd-queue-logging-automation)와 [크론 작업 글](/posts/cron-jobs)에서 다룬다.

WebSocket처럼 오래 붙어 있는 연결은 그 연결이 어느 서버에 붙었는지 자체가 상태다. 채팅처럼 연결을 유지해야 하는 서비스는 무상태로 만들 수 없어서 따로 설계한다.

점검하는 질문은 하나다. "이 서버를 지금 꺼도, 그리고 같은 서버를 하나 더 켜도 사용자가 차이를 모르나?" 그렇다면 무상태다.

## 서버 하나가 죽는 순간

무상태로 만들었으니 이제 서버 하나를 꺼 보자. 세션은 Redis에 있다. 0.1초마다 `/me`를 부르는 도중에 web1을 PID로 껐다. 로드 밸런서는 1초마다 헬스 체크를 하고, 두 번 연속 실패하면 서버를 뺀다.

```bash
# 0.1초 간격으로 4초 동안 /me를 부르는 도중 web1을 끈다
node drive.mjs kill
```


이 틈을 메우는 방법이 하나 더 있다. 로드 밸런서가 서버에 연결하지 못하면 그 요청을 다른 서버로 한 번 더 보내는 것이다. 데모 로드 밸런서에 "GET 요청이 실패하면 다음 서버로 한 번 재시도"를 넣고 같은 실험을 했다.

```text
$ kill 6785   # web1을 끈다
  [lb]  1401ms web1 request failed -> retry next
  [lb]  1516ms web1 request failed -> retry next
  ... (같은 retry 줄 11개 생략)
  [lb]  2904ms web1 request failed -> retry next
```

실패가 0개가 됐다. 사용자 대신 로드 밸런서가 다시 시도한 것이다. 다만 재시도는 같은 요청을 두 번 보내도 결과가 같은 요청(조회 같은 GET)에만 건다. 결제 POST를 재시도하면 결제가 두 번 될 수 있다. nginx는 기본값으로 연결 오류 때 다음 서버로 넘기되, POST 같은 요청은 따로 허용하지 않으면 넘기지 않는다. 이런 요청을 안전하게 다시 보내는 방법은 [멱등성 키 글](/posts/idempotency-key)에 있다.

## 배포와 자동 확장이 쉬워진다

웹 서버가 무상태가 되면 서버를 다루는 방식이 달라진다.

배포는 한 대씩 한다. 로드 밸런서에서 web1을 빼고, 처리 중이던 요청이 끝날 때까지 기다리고(드레이닝), 새 버전으로 바꾸고, 헬스 체크를 통과하면 다시 넣는다. 그다음 web2를 같은 순서로 바꾼다. 이 방식이 롤링 배포다. [① 서버 한 대](/posts/sd-start-single-server)에서 배포마다 실패하던 181개의 요청이 여기서 사라진다. 순서와 설정은 [롤링 배포 글](/posts/rolling-deployment)에 있다.

트래픽에 따라 서버 수를 자동으로 늘리고 줄이는 오토스케일링도 무상태여야 가능하다. 저녁 시간에 서버를 두 대에서 여섯 대로 늘렸다가 새벽에 두 대로 줄일 때, 줄이면서 꺼지는 네 대에 세션이 있었다면 그 사용자들은 모두 로그아웃된다. 상태가 밖에 있으면 아무 서버나 꺼도 된다. 늘리는 기준과 속도는 [오토스케일링 글](/posts/autoscaling)에서 본다.

## 새로 생긴 약점들

웹 서버는 여러 대가 됐지만, 그림을 다시 보면 아직 한 대짜리가 남아 있다.

로드 밸런서 자신이 한 대다. 로드 밸런서가 죽으면 웹 서버가 몇 대든 아무도 들어오지 못한다. 그래서 로드 밸런서도 두 대를 두고 하나가 죽으면 다른 하나가 같은 IP를 이어받게 한다(VRRP 같은 방식). 클라우드의 관리형 로드 밸런서는 이 이중화를 제공자가 대신 해 준다. 자세한 방법은 [로드 밸런서 기본 글](/posts/load-balancer-basics)의 "로드 밸런서가 죽으면"에 있다.

세션 저장소도 한 대다. Redis가 멈추면 모든 사용자가 로그인 상태를 잃는다. Redis도 복제본을 두고 자동으로 넘기는 구성이 필요하다. 그 방법은 [Redis 복제와 Sentinel 글](/posts/redis-replication-sentinel)에 있다.

그리고 DB는 여전히 한 대다. 웹 계층을 아무리 늘려도 모든 웹 서버가 결국 같은 DB 한 대에 묻는다. 그 DB가 다음 글의 주제다.

## 몇 대에 어떻게 나뉘나 직접 돌려 보기

라운드 로빈은 살아 있는 서버 목록을 차례대로 돈다. 아래 함수를 완성해 보자. `servers`는 서버 이름 목록, `down`은 헬스 체크에서 빠진 서버 목록, `count`는 들어온 요청 수다. 요청마다 어느 서버로 갔는지 배열로 돌려주고, 살아 있는 서버가 하나도 없으면 그 요청은 `"503"`으로 적는다.

## 현장에서 이 구조가 아플 때

"로그인이 가끔 풀린다", "장바구니가 비었다 찼다 한다"는 증상은 거의 항상 상태가 웹 서버 안에 남아 있다는 뜻이다. 응답 헤더나 로그에 어느 서버가 답했는지 남겨 두면 바로 보인다. 데모에서 응답에 `server` 필드를 넣어 둔 것도 그래서다.

"배포 직후 몇 초간 502가 몰린다"면 로드 밸런서가 서버를 빼기 전에 프로세스가 먼저 내려간 것이다. 드레이닝 순서와 헬스 체크 간격을 본다.

"서버 한 대만 CPU가 높다"면 세션 고정이 켜져 있거나, 연결을 오래 유지하는 클라이언트가 한 서버에 몰렸을 가능성이 크다. 로드 밸런서의 서버별 요청 수 지표부터 확인한다.

"Redis가 재시작되자 전원이 로그아웃됐다"면 세션 저장소가 단일 장애 지점이었다는 뜻이다. 복제와 영속화 설정을 본다.

## 이어서 읽을 글

다음 글 [④ DB 복제](/posts/sd-db-replication-intro)에서는 마지막으로 남은 한 대짜리, DB를 다룬다. 쓰기를 받는 주 DB 한 대와 그 복사본인 복제본 여러 대로 나눠 읽기를 분산하고, 어느 한 대가 죽었을 때 무슨 일이 생기는지 직접 꺼 보며 확인한다.

웹 서버를 여러 대로 늘리려면 앞에서 나눠 주는 로드 밸런서와, 어느 서버가 받아도 같은 답을 하는 무상태 웹 서버가 함께 필요하다. 세션, 업로드 파일, 로컬 캐시, 예약 작업처럼 서버 안에 남은 상태를 공유 저장소로 빼내면, 서버는 언제 꺼도 되고 언제 늘려도 되는 부품이 된다.

## 면접에서 나올 만한 질문

### 로드 밸런서는 무엇을 해 주나요?

여러 웹 서버 앞에서 요청을 받아 그중 하나로 넘겨 주는 장치다. 한 대가 죽으면 헬스 체크로 빼서 나머지가 받게 하고, 트래픽이 늘면 서버를 더 붙이면 된다. 웹 서버는 사설망에 두고 로드 밸런서만 공인 IP를 가지게 해서 보안에도 도움이 된다.

### 웹 계층을 무상태로 만들어야 하는 이유는 무엇인가요?

로드 밸런서는 같은 사용자의 요청도 매번 다른 서버로 보낼 수 있기 때문이다. 세션이 서버 메모리에 있으면 다른 서버로 간 요청은 로그인이 풀린 것처럼 보이고, 서버를 끄거나 줄일 때 그 서버의 사용자 상태가 사라진다. 상태를 공유 저장소로 빼면 어느 서버가 받아도 같은 답을 하고, 서버를 자유롭게 늘리고 줄일 수 있다.

### 세션은 어디에 두나요? 세션 고정과 비교하면요?

Redis 같은 공유 저장소에 만료 시간과 함께 둔다. 세션 고정은 코드 변경 없이 같은 사용자를 같은 서버로 보내지만, 그 서버가 죽으면 세션이 사라지고 새 서버를 붙여도 부하가 고르게 퍼지지 않는다. 공유 저장소는 매 요청에 저장소 왕복이 하나 붙는 대신 웹 서버를 진짜로 바꿔 끼울 수 있게 해 준다. 토큰 방식은 저장소가 필요 없지만 발급한 토큰을 즉시 무효로 만들기 어렵다.

### 웹 서버 한 대가 갑자기 죽으면 어떻게 되나요?

세션이 밖에 있다면 로그인은 유지되지만, 로드 밸런서가 그 서버를 빼기 전까지 일부 요청이 실패한다. 데모에서는 1초 간격, 2회 실패 기준이라 약 1.6초 동안 요청 7개가 502였다. GET처럼 다시 보내도 안전한 요청은 로드 밸런서가 다른 서버로 재시도하게 하면 실패를 없앨 수 있다. 서버 수는 한 대가 빠져도 나머지가 감당하도록 여유를 둔다.

### 로드 밸런서 자체가 죽으면요?

로드 밸런서도 단일 장애 지점이라 두 대 이상으로 이중화한다. 직접 운영하면 VRRP 같은 방식으로 대기 장비가 같은 IP를 이어받게 하고, 클라우드 관리형 로드 밸런서는 제공자가 여러 대로 운영해 준다. 세션 저장소인 Redis도 같은 이유로 복제와 자동 장애 조치를 붙인다.

### 트래픽이 10배가 되면 이 구조에서 무엇을 하나요?

웹 계층은 무상태라 서버를 더 붙이거나 오토스케일링 범위를 늘리면 된다. 그다음 병목이 옮겨 가는 곳을 본다. 서버 수 × 커넥션 풀 크기가 DB 연결 한도를 넘지 않는지, 세션 저장소와 DB가 10배의 읽기를 버티는지가 다음 문제다. 읽기가 많으면 DB 복제본과 캐시로 나눈다.

### 웹 서버 안에 남기 쉬운 상태에는 무엇이 있나요?

로그인 세션 외에 업로드 파일, 프로세스 안의 캐시, 서버마다 도는 예약 작업, WebSocket 연결이 있다. 파일은 객체 저장소로, 캐시는 공유 캐시로, 예약 작업은 한 곳에서만 돌도록 옮긴다. 확인하는 기준은 "이 서버를 지금 꺼도, 같은 서버를 하나 더 켜도 사용자가 차이를 모르는가"다.
