주문이 끝나면 영수증을 이메일로 보내는 함수가 있다. 어느 날 문자로도 보내 달라는 요청이 와서 `if`를 하나 붙였다. 몇 달 뒤 카카오 알림톡이 추가되자 같은 `if`가 결제, 환불, 비밀번호 재설정, 마케팅 발송 네 군데에 복사돼 있다는 걸 알게 된다. 테스트를 돌리면 진짜 메일 서버에 접속하려다 타임아웃이 난다. 함수 안에 `new EmailClient()`가 박혀 있어서 가짜로 바꿀 틈이 없다.

```ts
export async function sendReceipt(order: Order) {
  const body = renderReceipt(order);
  if (order.channel === "email") {
    const client = new EmailClient(process.env.SMTP_URL ?? "");
    await client.send(order.email, "주문 영수증", body);
  } else if (order.channel === "sms") {
    const client = new SmsClient(process.env.SMS_API_KEY ?? "");
    await client.send(order.phone, body);
  }
}
```

이 함수는 두 가지 일을 한다. 영수증을 만들어 보내는 흐름, 그리고 어떤 클라이언트를 쓸지 고르는 일이다. 흐름은 거의 바뀌지 않는데 고르는 일은 채널이 늘 때마다 바뀐다. 바뀌는 쪽을 메서드 하나로 떼어 내는 것이 팩토리 메서드 패턴이다. 패턴 전체 지도는 [디자인 패턴 개요](/posts/design-patterns-overview)에 정리해 두었다.

## new가 박힌 자리를 메서드로 바꾼다

GoF는 이 패턴을 이렇게 정의한다. 객체를 만드는 인터페이스는 정의하되, 어떤 클래스의 인스턴스를 만들지는 하위 클래스가 정하게 한다. 그래서 가상 생성자(virtual constructor)라는 별명도 있다. 등장인물은 넷이다.

Creator(`ReceiptSender`)는 제품을 쓰는 흐름을 가진다. Product(`Channel`)는 Creator가 기대하는 인터페이스다. ConcreteCreator(`SmsReceiptSender`)가 팩토리 메서드를 구현해 ConcreteProduct(`SmsChannel`)를 만든다. Creator는 끝까지 인터페이스만 안다.

```ts
export interface Channel {
  send(to: Recipient, text: string): Promise<void>;
}

export abstract class ReceiptSender {
  // 팩토리 메서드: 어떤 채널을 만들지는 하위 클래스가 정한다
  protected abstract createChannel(): Channel;

  // 흐름은 상위 클래스가 쥔다
  async send(order: Order): Promise<void> {
    const text = renderReceipt(order);
    const channel = this.createChannel();
    await channel.send(order.recipient, text);
  }
}

export class EmailReceiptSender extends ReceiptSender {
  protected createChannel(): Channel {
    return new EmailChannel("smtp://mail.internal:587");
  }
}

export class SmsReceiptSender extends ReceiptSender {
  protected createChannel(): Channel {
    return new SmsChannel();
  }
}
```

`send()` 안에서 `new`가 사라지고 `this.createChannel()`이 그 자리를 차지했다. 이 한 줄이 팩토리 메서드의 전부다. 선언 한 줄을 조각내 보면 각 키워드가 맡은 일이 보인다.

## 이름이 비슷한 세 가지

"팩토리"라는 말은 셋을 섞어서 부른다. 면접에서도 자주 헷갈리는 부분이라 나눠 둔다.

첫째는 흔히 심플 팩토리라 부르는 것이다. `createChannel(kind)`처럼 `switch`로 골라 만드는 함수 하나다. GoF 23개에 들지 않는 관용구지만 실무에서 가장 많이 쓴다. Node.js의 `crypto.createHash("sha256")`가 이 모양이다. 문자열로 알고리즘을 고르면 맞는 해시 객체를 준다.

둘째는 정적 팩토리 메서드다. Effective Java의 첫 항목이 "생성자 대신 정적 팩토리 메서드를 고려하라"다. `Integer.valueOf(42)`, `List.of(1, 2)`처럼 이름을 붙일 수 있고, 캐시된 객체를 줄 수 있고, 하위 타입을 돌려줄 수 있다. 자바스크립트의 `Array.from`, `Promise.resolve`도 같은 부류다. 이것도 GoF의 팩토리 메서드와는 다르다. 상속으로 바꿔 끼우는 구조가 없다.

셋째가 이 글의 GoF 팩토리 메서드다. 생성이 "재정의할 수 있는 메서드"이고, 그 메서드를 부르는 흐름이 상위 클래스에 있다. 구조로 보면 [템플릿 메서드](/posts/pattern-template-method)의 한 단계를 "만드는 일"로 특화한 것이다.

## 매일 쓰는 팩토리 메서드

자바스크립트에서 가장 많이 쓰이는 팩토리 메서드는 `for...of` 뒤에 숨어 있다. `for...of`는 컬렉션의 `[Symbol.iterator]()`를 불러 반복자를 받는다. 어떤 반복자를 만들지는 컬렉션마다 다르다.

```js
const collections = [[10, 20], new Set(["a"]), new Map([["k", 1]]), "hi"];
for (const c of collections) {
  const it = c[Symbol.iterator](); // 컬렉션마다 자기 반복자를 만든다
  console.log(Object.prototype.toString.call(it).padEnd(26), JSON.stringify(it.next()));
}
```

```text
[object Array Iterator]    {"value":10,"done":false}
[object Set Iterator]      {"value":"a","done":false}
[object Map Iterator]      {"value":["k",1],"done":false}
[object String Iterator]   {"value":"h","done":false}
```

`for...of`는 무엇을 돌고 있는지 모른 채 `next()`만 부른다. 내가 만든 클래스에 `[Symbol.iterator]()`를 구현하면 그 클래스도 `for...of`, 전개 연산자, `Array.from`에 그대로 들어간다. 자바의 `Collection.iterator()`가 GoF 책 이후 이 패턴의 대표 예로 꼽히는 것도 같은 구조라서다. 반복자 자체는 [이터레이터 패턴](/posts/pattern-iterator)에서 따로 다룬다.

DOM의 `document.createElement("input")`도 문서 객체의 팩토리 메서드다. HTML 문서에서는 태그 이름에 맞춰 `HTMLInputElement`, `HTMLDivElement` 같은 하위 클래스를 돌려주고, 부른 쪽은 `Element`로 받아 쓴다. Spring의 `FactoryBean<T>`은 `getObject()`로 무엇을 만들지 빈이 정하게 하는 확장점이다. Go에는 클래스 상속이 없어서 `http.NewRequest`처럼 `New`로 시작하는 생성 함수를 쓰고, 바꿔 끼울 필요가 있으면 함수를 필드나 인자로 받는다.

## 상속 대신 함수를 넘기면

하위 클래스를 채널마다 하나씩 만드는 건 자바스크립트에서는 손이 많이 간다. 팩토리 메서드가 결국 "제품을 돌려주는 함수"라면 그 함수를 그냥 넘겨도 된다.

```ts
export type ChannelKind = "email" | "sms";

const channelFactories = {
  email: () => new EmailChannel("smtp://mail.internal:587"),
  sms: () => new SmsChannel(),
} satisfies Record<ChannelKind, () => Channel>;

export function createReceiptSender(createChannel: () => Channel) {
  return {
    async send(order: Order): Promise<void> {
      await createChannel().send(order.recipient, renderReceipt(order));
    },
  };
}

export const senderFor = (kind: ChannelKind) => createReceiptSender(channelFactories[kind]);
```

`satisfies`가 쓸모 있는 건 채널을 추가할 때다. `ChannelKind`에 `"kakao"`를 넣고 팩토리를 빠뜨리면 컴파일러가 바로 알려 준다.

```text
fn.ts(8,3): error TS1360: Type '{ email: () => EmailChannel; sms: () => SmsChannel; }' does not satisfy the expected type 'Record<ChannelKind, () => Channel>'.
  Property 'kakao' is missing in type '{ email: () => EmailChannel; sms: () => SmsChannel; }' but required in type 'Record<ChannelKind, () => Channel>'.
```

`if` 사슬은 새 분기를 빠뜨려도 조용히 아무것도 안 한다. 표로 바꾸면 빠뜨린 곳을 컴파일러가 찾아 준다.

그렇다고 클래스 형태가 쓸모없어지는 건 아니다. Creator가 바꿀 지점을 여러 개 가진 큰 흐름이라면 클래스가 낫다. 영수증 발송에 "채널 만들기", "문구 만들기", "실패 시 재시도 정책"이 모두 바뀌어야 한다면, 함수 세 개를 따로 넘기는 것보다 하위 클래스 하나가 세 메서드를 묶어 재정의하는 편이 읽기 쉽다. 프레임워크가 확장점을 열어 줄 때 추상 클래스를 쓰는 이유가 이것이다. 바꿀 것이 하나면 함수, 여러 개가 함께 바뀌면 클래스라고 기억하면 된다.

## 채널 하나를 추가할 때 고치는 곳

## 테스트에서 가짜 채널 끼우기

처음 장면의 테스트 문제는 생성이 바꿀 수 있는 자리로 나오면서 풀린다. 클래스 형태라면 테스트 안에서 하위 클래스를 만들어 팩토리 메서드만 재정의하고, 함수 형태라면 가짜를 돌려주는 함수를 넘긴다.

```ts
class FakeChannel implements Channel {
  sent: string[] = [];
  async send(to: Recipient, text: string) {
    this.sent.push(`${to.phone} ${text}`);
  }
}

test("하위 클래스로 팩토리 메서드를 바꿔 끼운다", async () => {
  const fake = new FakeChannel();
  class TestSender extends ReceiptSender {
    protected createChannel() {
      return fake;
    }
  }
  await new TestSender().send(order);
  assert.deepEqual(fake.sent, ["010-1234-5678 주문 A-1042 결제 금액 39,000원"]);
});

test("함수를 넘겨 바꿔 끼운다", async () => {
  const fake = new FakeChannel();
  await createReceiptSender(() => fake).send(order);
  assert.equal(fake.sent.length, 1);
});
```

## 팩토리 메서드가 과한 경우

패턴을 들이면 클래스나 함수 하나가 늘고, 읽는 사람은 "실제로 무엇이 만들어지나"를 찾으러 한 번 더 이동해야 한다. 만드는 대상이 하나뿐이고 바뀔 계획도 없다면 `new`를 그대로 쓰는 게 낫다. 테스트를 위해서만이라면 생성자 인자로 의존성을 받는 것으로 충분하다.

클래스 형태에는 상속의 비용도 따라온다. 제품 종류와 다른 축(예: 국내·해외 발송)이 함께 갈리면 `EmailDomesticSender`, `EmailGlobalSender`, `SmsDomesticSender`처럼 하위 클래스가 곱으로 는다. 이럴 때는 상속 대신 축마다 객체를 따로 넘기는 조합으로 바꾼다.

비슷한 패턴과의 경계도 짚어 두자. 팩토리 메서드는 제품 하나를 만드는 메서드 하나다. 서로 짝이 맞아야 하는 제품 여러 개를 한 벌로 만들어야 한다면(AWS용 저장소와 큐, GCP용 저장소와 큐) [추상 팩토리](/posts/pattern-abstract-factory)가 그 일을 한다. 만드는 과정이 길고 단계가 많다면 [빌더](/posts/pattern-builder), 이미 있는 객체를 복제해 만든다면 [프로토타입](/posts/pattern-prototype)이 맞다.

처음의 영수증 함수로 돌아가면, 바뀌지 않는 흐름과 자주 바뀌는 생성을 갈라놓은 것이 이 패턴이 한 일의 전부다. 그 덕에 새 채널은 추가만으로 끝나고, 테스트는 가짜를 끼울 자리를 얻었다.

## 면접에서 나올 만한 질문

### 팩토리 메서드 패턴이 무엇인가요?

객체를 만드는 일을 재정의할 수 있는 메서드로 떼어 내고, 어떤 클래스를 만들지는 하위 클래스가 정하게 하는 패턴이다. 상위 클래스는 제품 인터페이스만 알고 흐름을 진행하며, 생성 순간에만 하위 클래스의 메서드를 부른다. 그래서 흐름을 고치지 않고 제품을 바꿔 끼울 수 있다.

### 심플 팩토리, 정적 팩토리 메서드와는 어떻게 다른가요?

심플 팩토리는 switch로 골라 만드는 함수 하나이고 GoF 패턴은 아니다. 정적 팩토리 메서드는 List.of처럼 생성자 대신 이름 있는 정적 메서드를 쓰는 관용구로, 캐시나 하위 타입 반환이 장점이지만 상속으로 바꿔 끼우는 구조가 없다. GoF 팩토리 메서드는 생성이 재정의 가능한 메서드이고 그걸 부르는 흐름이 상위 클래스에 있다는 점이 다르다.

### 이 패턴이 어떤 설계 원칙과 연결되나요?

개방 폐쇄 원칙과 의존성 역전 원칙이다. 새 제품은 하위 클래스나 팩토리 항목을 추가하는 것으로 끝나고 기존 흐름은 고치지 않는다. 상위 흐름은 구체 클래스가 아니라 제품 인터페이스에 의존하게 된다.

### 자바스크립트에서 실제로 쓰이는 예를 들어 주세요.

for...of가 부르는 `[Symbol.iterator]()`가 대표적이다. 배열, Set, Map, 문자열이 각자 자기 반복자를 만들어 주고 for...of는 인터페이스인 next()만 부른다. DOM의 document.createElement도 태그에 맞는 HTMLElement 하위 클래스를 돌려주는 팩토리 메서드다.

### 클래스 상속 대신 함수를 넘기면 안 되나요?

바꿀 지점이 하나라면 함수를 넘기는 쪽이 더 간단하고 자바스크립트에서는 그게 일반적이다. 다만 생성, 문구, 재시도처럼 함께 바뀌는 지점이 여럿이면 하위 클래스 하나가 묶어서 재정의하는 편이 읽기 쉽다. 프레임워크 확장점이 추상 클래스로 열려 있는 이유다.

### 팩토리를 표(객체)로 만들 때 주의할 점은요?

키가 바깥 입력에서 오면 toString, constructor처럼 프로토타입에서 물려받은 이름이 걸려 엉뚱한 함수가 불릴 수 있다. Object.hasOwn으로 확인하거나 Map, Object.create(null)을 쓴다. 타입스크립트에서는 satisfies Record로 모든 종류가 채워졌는지 컴파일 시점에 검사한다.

### 팩토리 메서드와 추상 팩토리는 어떻게 고르나요?

만들 제품이 하나면 팩토리 메서드, 서로 짝이 맞아야 하는 제품 여러 개를 한 벌로 만들어야 하면 추상 팩토리다. 팩토리 메서드는 상속으로 메서드 하나를 바꾸고, 추상 팩토리는 제품군 전체를 만드는 객체를 통째로 바꾼다. 실제로 추상 팩토리의 각 메서드를 팩토리 메서드로 구현하는 경우가 많다.
