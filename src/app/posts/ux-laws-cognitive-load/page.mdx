결제 화면을 고치는 일을 맡았다고 하자. 기획 회의마다 하나씩 붙었다. 쿠폰 입력칸, 포인트 사용 토글, 배송 방법 다섯 가지, "선물 포장" 체크박스, 회원 가입 유도 배너, 하단의 "장바구니로 돌아가기"와 "다른 상품 보기" 버튼. 하나하나는 다 이유가 있었다. 그런데 배포 후 퍼널을 보니 결제 화면에서 이탈이 늘었다.

이런 일을 설명할 때 UX 법칙들이 자주 나온다. 힉의 법칙, 피츠의 법칙, 인지 부하, 기본값 효과. 이름만 들으면 디자이너의 말 같지만, 대부분은 개발자가 직접 정하는 값으로 바뀐다. 버튼의 높이와 간격, 처음 화면에 몇 개를 보여 줄지, 어떤 라디오가 미리 선택돼 있을지, 누른 뒤 몇 ms 안에 무엇이 바뀔지. 이 글은 법칙을 하나씩 그런 값으로 옮겨 보고, 법칙이 맞지 않는 경우와 그 숫자들의 근거가 어디까지인지도 같이 본다. 법칙으로 고친 뒤 정말 좋아졌는지 재는 법은 [제품 분석과 퍼널](/posts/product-analytics-funnels)에서, 사람에게 직접 시켜 보는 법은 [사용성 테스트와 프로토타입](/posts/ux-research-usability-testing)에서 다룬다.

## 선택지가 늘면 결정이 느려진다

힉의 법칙(Hick–Hyman law)은 1950년대 실험에서 나왔다. 불이 켜지는 등에 맞춰 버튼을 누르는 과제에서, 고를 수 있는 등의 개수가 늘수록 반응 시간이 로그를 그리며 늘었다.

```text
T = a + b · log2(n + 1)
```

`n`은 똑같이 그럴듯한 선택지 수, `a`와 `b`는 사람과 과제마다 실험으로 구하는 상수다. 왜 로그일까. 사람이 목록을 하나씩 다 보는 게 아니라 절반씩 거르기 때문이라고 설명한다. 선택지가 정렬돼 있고 무엇을 찾는지 알면, 사람은 "앞쪽 절반인가 뒤쪽 절반인가"를 묻듯 범위를 좁힌다. 아래는 가나다순으로 정렬된 은행 여덟 개에서 "신한"을 찾을 때 범위가 줄어드는 모습이다.

`b`를 150ms로 가정해 계산해 보면(실제 값은 과제마다 다르다) 선택지가 2개면 238ms, 4개면 348ms, 8개면 475ms, 16개면 613ms다. 개수가 8배가 돼도 시간은 2.6배 정도다. 그러니 이 법칙은 "선택지를 무조건 줄여라"가 아니라 "선택지가 늘수록 결정 비용이 쌓이고, 정렬과 묶음으로 그 비용을 줄일 수 있다"는 말에 가깝다.

여기서 중요한 조건이 둘 있다. 선택지가 비슷하게 그럴듯해야 하고, 사람이 무엇을 찾는지 알아야 한다. 은행 목록처럼 이미 답이 머릿속에 있으면 로그로 늘지만, 처음 보는 요금제 다섯 개를 비교하는 일은 거르기가 아니라 하나하나 읽고 따지는 일이다. 그때는 개수에 거의 비례해서 늘고, 각 항목이 복잡할수록 더 늘어난다.

결제 화면의 배송 방법 다섯 가지가 이 경우다. 사용자는 다섯 개를 다 읽고 가격과 도착일을 비교해야 한다. 개발자가 할 수 있는 일은 이런 것이다.

- 고를 이유가 없는 선택지를 뺀다. 지난 30일 동안 1%도 안 고른 배송 방법은 "다른 배송 방법 보기" 아래로 접는다.
- 비교할 값을 같은 자리에 같은 형식으로 둔다. 가격은 오른쪽, 도착일은 "10월 27일(월) 도착"처럼 한 형식으로.
- 정렬 기준을 정해 둔다. 빠른 순이든 싼 순이든 한 가지로 일관되게.
- 긴 목록(국가, 은행)에는 검색을 붙인다. 검색은 고르는 문제를 떠올리는 문제로 바꾼다.

## 너무 많이 보여 주면 아예 안 고른다

선택지가 많으면 느려질 뿐 아니라, 아예 결정을 미루기도 한다. 이걸 선택 과부하(choice overload)라고 부른다. 가장 많이 인용되는 건 2000년 아이엥거와 레퍼의 잼 실험이다. 마트 시식대에 잼 24가지를 깔았을 때와 6가지를 깔았을 때를 비교했더니, 24가지 쪽이 사람을 더 많이 멈춰 세웠지만 실제로 산 비율은 6가지 쪽이 훨씬 높았다(약 30% 대 3%).

이 숫자는 그대로 믿기보다 범위를 알고 써야 한다. 2010년 셰이베헤네 등이 비슷한 연구 50편을 모아 메타 분석을 했더니 평균 효과는 0에 가까웠다. 과부하가 나타나는 연구도 있고, 선택지가 많을수록 오히려 좋아지는 연구도 있었다. 뒤이은 연구들은 과부하가 생기는 조건을 좁혀 가는 쪽으로 갔다. 선택지끼리 비교하기 어려울 때, 고르는 사람이 무엇을 원하는지 아직 모를 때, 결정을 빨리 내려야 할 때, 선택이 어렵다고 느낄 때 더 잘 나타난다.

그래서 실무에서 쓸 결론은 "선택지는 N개 이하"가 아니다. 사용자가 원하는 걸 아직 모르는 화면(첫 방문자에게 요금제를 고르게 하는 화면)에서는 선택지를 줄이고 추천을 하나 표시한다. 원하는 걸 이미 아는 사용자(옵션을 찾아 들어온 사람)에게는 많이 보여 주되 거르기 도구를 준다.

같은 이유로 "7±2 규칙"도 조심해서 쓴다. 밀러의 1956년 논문은 단기 기억에 한꺼번에 붙잡을 수 있는 덩어리 수에 대한 이야기다. 메뉴 항목을 일곱 개로 제한하라는 뜻이 아니다. 메뉴는 화면에 계속 보이니 외울 필요가 없다. 이후 연구(코완, 2001)는 그 수를 4 안팎으로 더 작게 본다. 기억해야 하는 양을 줄이라는 원칙은 맞지만, 숫자를 메뉴 개수 상한으로 쓰는 건 근거가 없다.

## 머리가 쓰는 힘을 어디에 쓰게 할까

본질적 부하는 일 자체가 어려운 것이다. 보험 상품을 고르는 일은 원래 복잡하다. 이건 없앨 수 없고, 단계로 나누거나 순서를 정해 주는 정도만 할 수 있다. 외재적 부하는 화면이 만든 어려움이다. 무엇을 눌러야 할지 모르는 버튼 배치, 이전 화면에서 본 숫자를 기억해 다시 입력하게 하는 흐름, 의미 없는 장식, 깜빡이는 배너가 다 여기 들어간다. UI가 줄여야 할 것은 이쪽이다. 세 번째는 사람이 새로운 걸 익히는 데 쓰는 힘인데, 학습 도구가 아니라면 크게 신경 쓸 일은 적다.

외재적 부하를 줄이는 방법은 개발 작업으로 바로 바뀐다.

- 기억하게 하지 않는다. 장바구니 금액, 고른 옵션, 적용된 쿠폰을 결제 화면에 계속 보여 준다. 다른 탭에서 확인하고 돌아오게 만들지 않는다.
- 다시 묻지 않는다. 한 번 입력한 주소, 지난번 결제 수단, 휴대폰 번호는 기억해서 채운다. `autocomplete` 속성으로 브라우저 자동 완성을 돕는 법은 [폼 입력과 검증](/posts/html-form-validation)에 있다.
- 형식을 사람에게 맞춘다. 전화번호에 하이픈을 넣든 빼든 받아들이고 저장할 때 정리한다. "하이픈 없이 입력하세요"는 사람에게 일을 넘기는 문장이다.
- 방해 요소를 치운다. 결제 화면에서는 전체 내비게이션, 추천 상품, 가입 배너를 걷어 낸다. 지금 할 일과 상관없는 것은 모두 외재적 부하다.
- 반복을 자동화한다. 매일 같은 필터를 거는 사용자에게는 마지막 필터를 기억하거나 저장된 필터를 제공한다.

## 기본값은 가장 강한 선택지다

사람은 미리 골라진 답을 그대로 두는 경향이 강하다. 행동경제학에서는 기본값 효과(default effect)라고 부른다. 자주 인용되는 예가 장기 기증이다. 존슨과 골드스타인(2003)은 기증 의사를 "원하면 표시"하게 하는 나라와 "원하지 않으면 표시"하게 하는 나라 사이에 동의율이 크게 갈린다는 걸 보였다. 문화나 제도 차이가 섞여 있어 기본값만의 효과로 보기는 어렵지만, 기본값이 결과를 크게 움직인다는 방향은 여러 연구에서 반복된다.

화면에서 기본값은 개발자가 넣는 `checked`, `defaultValue`, `selected` 하나다. 그래서 어떤 값을 넣을지가 곧 설계다.

- 대부분이 고르는 값을 기본으로 둔다. 배송 방법 중 85%가 고르는 일반 배송을 미리 선택해 두면 85%는 그 질문을 건너뛴다.
- 이전 선택을 기본으로 둔다. 지난번 결제 수단, 마지막으로 고른 정렬 방식.
- 맥락에서 추론한다. 접속 위치로 국가를, 브라우저 언어로 언어를 미리 고른다. 다만 틀렸을 때 바꾸기 쉬워야 한다.
- 안전한 쪽을 기본으로 둔다. 공개 범위는 "나만 보기", 삭제 확인 대화상자의 기본 포커스는 "취소".

반대로 기본값을 쓰지 말아야 할 때도 있다. 마케팅 수신 동의를 미리 체크해 두는 것은 사용자의 이익이 아니라 회사의 이익을 기본값에 넣은 것이다. 이런 걸 다크 패턴이라고 부르고, 개인정보 보호법이나 GDPR처럼 명시적인 동의를 요구하는 규정이 있는 곳에서는 법적으로도 문제가 된다. 의견이 정말 갈리는 질문(성별, 정치 성향)에도 기본값을 두지 않는다. 기본값을 두면 그대로 둔 사람과 실제로 그렇게 답한 사람을 구분할 수 없어서 데이터도 오염된다.

## 큰 과녁이 가까이 있으면 빨리 누른다

피츠의 법칙은 과녁을 가리키는 데 걸리는 시간이 거리와 크기로 정해진다는 법칙이다. 지금 흔히 쓰는 형태(섀넌 공식)는 이렇다.

```text
MT = a + b · log2(D / W + 1)
```

`D`는 출발점에서 과녁 중심까지 거리, `W`는 움직이는 방향으로 잰 과녁 폭이다. 로그 안의 `log2(D / W + 1)`을 난이도 지수(ID)라고 부른다. 거리를 두 배로 늘리는 것과 폭을 절반으로 줄이는 것이 같은 만큼 어려워진다. 직접 계산해 보자.

    { args: [200, 44, 100, 150], expected: 471, label: "200px 떨어진 44px 버튼" },
    { args: [200, 24, 100, 150], expected: 583, label: "같은 거리, 24px 버튼" },
    { args: [200, 88, 100, 150], expected: 357, label: "폭을 두 배로" },
    { args: [400, 44, 100, 150], expected: 600, label: "거리를 두 배로" },
    { args: [50, 44, 100, 150], expected: 264, label: "바로 옆의 버튼" },
    { args: [0, 44, 100, 150], expected: 100, label: "이미 올려 둔 자리" },
  ]}
/>

`a = 100`, `b = 150`은 계산을 보여 주려고 넣은 값이다. 실제 상수는 입력 장치(마우스, 터치패드, 손가락)와 사람에 따라 다르다. 그래도 비율은 읽을 수 있다. 같은 거리에서 버튼을 44px에서 24px로 줄이면 시간이 약 24% 늘고, 폭을 88px로 키우면 약 24% 준다.

개발자가 정하는 값으로 옮기면 이렇다.

- 누르는 영역을 키운다. WCAG 2.2의 2.5.8(AA)은 터치 대상을 최소 24×24 CSS px로, 2.5.5(AAA)는 44×44로 요구한다. 애플은 44pt, 머티리얼은 48dp를 권한다. 아이콘이 20px이어도 버튼의 padding으로 누르는 영역을 44px 이상으로 만든다.
- 글자 링크는 줄 전체를 누를 수 있게 한다. 목록 줄의 제목 링크가 줄 전체를 덮게 만들면(`::after`로 `inset: 0`) 과녁이 수십 배 커진다.
- 자주 누르는 것을 손 가까이 둔다. 휴대폰에서 주요 버튼은 화면 아래 엄지가 닿는 곳에. 결제 버튼을 화면 하단에 붙이는(sticky) 이유다.
- 화면 가장자리를 쓴다. 마우스 포인터는 화면 끝에서 멈추니, 가장자리에 붙은 대상은 깊이가 무한한 것처럼 동작한다. 데스크톱 운영체제의 메뉴 막대가 맨 위에 붙어 있는 이유다. 웹 페이지 안에서는 브라우저 창 테두리 때문에 이 효과가 거의 없다.
- 위험한 버튼은 거꾸로 멀리, 작게 둔다. "주문 취소"를 "결제하기" 바로 옆에 같은 크기로 두면 잘못 누르기 쉽다. 간격을 두고 보조 스타일로.

```css
.action {
  min-block-size: 44px;
  min-inline-size: 44px;
  padding-inline: 1rem;
}

.action + .action {
  margin-inline-start: 0.5rem; /* 붙은 버튼 사이 최소 8px */
}

.checkout-bar {
  position: sticky;
  inset-block-end: 0;
  padding-block-end: max(0.75rem, env(safe-area-inset-bottom));
}
```

## 어디를 누를지 한눈에 보이게

선택지를 줄이고 과녁을 키운 다음에는, 그중 무엇이 주인공인지 보여 줘야 한다. 시각적 위계는 크기, 색의 대비, 위치, 여백으로 만든다.

규칙을 몇 개로 정해 두면 화면마다 고민하지 않아도 된다.

- 한 화면(또는 한 영역)에 주 버튼(primary)은 하나다. 둘이면 둘 다 주인공이 아니다. 나머지는 보조(secondary)나 글자 버튼으로 낮춘다.
- 주 버튼의 문구는 동사로, 무엇이 일어나는지 쓴다. "확인"보다 "32,000원 결제하기", "다음"보다 "배송지 저장하고 계속". 누르기 전에 결과를 알면 망설임이 준다.
- 읽는 순서대로 배치한다. 위에서 아래, 왼쪽에서 오른쪽으로 읽으며 마지막에 주 버튼을 만난다. 모바일 폼에서는 한 열이 기본이다. 두 열로 놓으면 시선이 지그재그로 움직이고 칸을 빠뜨린다.
- 관계는 거리로 보여 준다. 라벨과 칸은 붙이고, 다른 묶음 사이는 넓게 띄운다. 묶음을 구분하려고 선이나 상자를 늘리기 전에 여백부터 쓴다.
- 비활성 버튼으로 숨바꼭질하지 않는다. 결제 버튼을 회색으로 꺼 두면 사용자는 무엇이 빠졌는지 모른다. 눌리게 두고 누르면 빠진 칸으로 데려가며 이유를 알려 주는 쪽이 낫다. 왜 못 누르는지 알려 주는 구현은 [체크박스, 라디오, 스위치, 셀렉트 꾸미기](/posts/custom-form-controls)의 disabled와 aria-disabled 절에 있다.

"전문적이고 아름다운 화면"도 결국 이 규칙의 결과에 가깝다. 간격과 글자 크기가 정해진 단계 안에서만 움직이고, 정렬선이 맞고, 색이 몇 가지로 제한되면 사람들은 그 화면을 믿을 만하다고 느낀다. 디자인 시스템이 간격과 글자 단계를 토큰으로 묶는 이유가 여기 있다. 단계를 정하는 법은 [간격·크기·타이포그래피 단계](/posts/spacing-sizing-type-scale)에서 다룬다.

## 누른 다음에는 바로 대답한다

사용자가 버튼을 누른 뒤 아무 변화가 없으면 다시 누른다. 결제 버튼이면 두 번 결제가 된다. 피드백은 친절이 아니라 오작동을 막는 장치다.

응답 시간에는 오래 쓰여 온 기준이 있다. 1968년 밀러의 연구에서 출발해 닐슨이 정리한 세 구간이다. 0.1초 안이면 사용자는 자기가 직접 바꾼 것처럼 느낀다. 1초 안이면 흐름이 끊기지 않지만 지연은 알아챈다. 10초를 넘기면 주의가 다른 데로 간다. 이 경계는 실험 하나로 정해진 상수라기보다 경험칙이지만, 화면에서 무엇을 보여 줄지 정할 때는 쓸 만하다.

- 0.1초 안: 누른 상태(`:active`), 체크 표시, 토글. 서버를 기다리지 않고 바로 바꾼다.
- 1초 근처: 버튼 안에 작은 로딩 표시를 넣고 버튼을 잠근다. 같은 버튼을 또 누를 수 없게.
- 몇 초 이상: 진행 단계와 남은 일을 보여 준다. 여러 단계가 있으면 단계 표시로.

아래는 버튼 안 로딩과 단계 표시가 실제로 움직이는 모습이다.

<LoadingDemo

끝났다는 것도 분명히 보여 준다. 결제가 끝났으면 화면을 바꾸고 주문 번호와 다음에 일어날 일(언제 도착하는지, 영수증은 어디로 갔는지)을 쓴다. 토스트 하나만 잠깐 띄우고 같은 폼을 그대로 두면 사용자는 정말 끝났는지 확신하지 못하고 새로 고친다. 저장처럼 자주 하는 일은 반대로 조용히 처리하고 "저장됨" 표시만 남긴다. 무게가 큰 일일수록 완료를 크게 보여 준다. 로딩 표시를 고르는 기준은 [로딩 패턴](/posts/loading-patterns)에서 자세히 다룬다.

```tsx
function PayButton({ amount, onPay }: { amount: number; onPay: () => Promise<void> }) {
  const [pending, setPending] = useState(false);
  return (
    <button
      type="button"
      aria-busy={pending}
      disabled={pending} // 요청 중에는 의미가 없으니 진짜로 막는다
      onClick={async () => {
        setPending(true);
        try {
          await onPay();
        } finally {
          setPending(false);
        }
      }}
    >
      {pending ? "결제하는 중…" : `${amount.toLocaleString("ko-KR")}원 결제하기`}
    </button>
  );
}
```

## 익숙한 자리에 두면 배우지 않아도 된다

사용자는 내 서비스보다 다른 서비스에서 훨씬 많은 시간을 보낸다. 그래서 내 화면도 다른 곳과 비슷하게 동작하리라 기대한다. 닐슨 노먼 그룹의 제이컵 닐슨이 이걸 "제이컵의 법칙"이라고 불렀다. 실험에서 나온 공식은 아니지만, 앞의 인지 부하 이야기와 같은 방향을 가리킨다. 익숙한 패턴은 따로 배울 필요가 없으니 외재적 부하가 없다.

개발할 때 이 말은 "관례를 깨려면 이유가 있어야 한다"로 바뀐다.

- 로고를 누르면 홈으로 간다. 장바구니는 오른쪽 위에 있다. 검색은 돋보기다.
- 링크는 밑줄이나 색으로 링크처럼 보이고, 버튼은 버튼처럼 보인다. 버튼처럼 생긴 링크, 글자처럼 생긴 버튼이 섞이면 사용자는 눌러 봐야 안다.
- 브라우저의 뒤로 가기, 새 탭에서 열기, 길게 눌러 복사하기가 동작한다. SPA에서 링크를 `div`의 클릭 핸들러로 만들면 이 셋이 다 깨진다.
- 폼은 Enter로 제출되고, Esc는 대화상자를 닫는다.

반대로, 새 패턴이 정말 나은 경우도 있다. 당겨서 새로 고침도 한때는 낯선 동작이었다. 그럴 때는 기존 방법을 같이 남겨 두고(새로 고침 버튼), 처음 한 번 알려 주고, 사용 데이터를 보며 옮겨 간다.

## 복잡함은 사라지지 않고 옮겨 갈 뿐이다

래리 테슬러는 "어떤 일에는 줄일 수 없는 복잡함이 있고, 그건 사용자든 시스템이든 누군가 떠안아야 한다"고 말했다. 이걸 복잡성 보존의 법칙이라고 부른다. 화면에서 칸을 하나 줄이면 그 칸이 하던 일을 누군가 대신해야 한다.

주소 입력이 좋은 예다. 시, 구, 동, 번지, 우편번호를 각각 받으면 화면은 단순하지만 사용자가 다섯 번 생각해야 한다. 주소 검색 하나로 바꾸면 화면도 단순하고 사용자도 편하지만, 그 복잡함은 주소 검색 API 연동, 결과 파싱, 우편번호 자동 채움이라는 개발자의 일로 옮겨 간다.

```ts
// 사람에게 형식을 맞추게 하지 않고, 받은 뒤 시스템이 정리한다
export function normalizePhone(input: string): string | null {
  const digits = input.replace(/\D/g, "");      // 공백, 하이픈, 괄호를 모두 뺀다
  const local = digits.startsWith("82") ? "0" + digits.slice(2) : digits; // +82 처리
  return /^01[016789]\d{7,8}$/.test(local) ? local : null;
}
```

사용자가 `010-1234-5678`, `010 1234 5678`, `+82 10 1234 5678` 중 무엇을 쳐도 같은 값이 된다. 반복되는 일도 마찬가지다. 매번 같은 배송지와 결제 수단을 고르는 사용자에게 "기본 배송지로 저장"을 주는 건, 그 반복을 시스템이 떠안는 일이다. 개발 비용은 들지만 그 비용은 한 번이고, 사용자의 비용은 매번이다.

## 고친 게 효과가 있었는지 화면에서 재기

법칙으로 고쳤다면 결과도 재야 한다. 전환율 같은 큰 숫자는 [제품 분석과 퍼널](/posts/product-analytics-funnels)이 다루는 영역이고, 여기서는 화면 단위로 법칙과 직접 이어지는 신호를 본다.

- 결정 시간: 단계가 보인 순간부터 첫 선택까지 걸린 시간. 선택지를 줄였다면 이 값이 줄어야 한다.
- 잘못 누름: 누른 직후 바로 되돌리는 일(체크했다가 바로 해제, 들어갔다가 바로 뒤로). 버튼이 너무 붙어 있거나 작으면 늘어난다.
- 분노 클릭(rage click): 같은 자리를 짧은 시간에 여러 번 누르는 것. 눌러도 반응이 없을 때 나온다. 피드백이 없거나 눌릴 것처럼 생긴 게 안 눌릴 때다.
- 죽은 클릭(dead click): 누를 수 있어 보이는데 아무 일도 안 일어나는 자리를 누른 것.

분노 클릭은 클릭 기록만 있으면 간단히 찾을 수 있다.

```ts
type Click = { t: number; x: number; y: number };

// 700ms 안에 반경 30px 안을 세 번 이상 누르면 분노 클릭으로 본다
export function findRageClicks(
  clicks: Click[],
  { count = 3, windowMs = 700, radius = 30 } = {},
) {
  const found: Click[] = [];
  for (let i = 0; i + count - 1 < clicks.length; i++) {
    const first = clicks[i];
    const last = clicks[i + count - 1];
    if (last.t - first.t > windowMs) continue;
    const group = clicks.slice(i, i + count);
    if (group.every((c) => Math.hypot(c.x - first.x, c.y - first.y) <= radius)) {
      found.push(first);
      i += count - 1; // 같은 묶음을 두 번 세지 않는다
    }
  }
  return found;
}
```

0ms, 180ms, 390ms에 거의 같은 자리를 누르고 한참 뒤 다른 곳을 두 번 누른 기록을 넣으면 첫 묶음 하나만 나온다. 기준값(세 번, 700ms, 30px)은 예시로 잡은 것이라 서비스의 실제 클릭 기록을 보며 조정한다. 이 값이 결제 버튼 근처에 몰려 있으면, 누른 뒤의 피드백부터 의심한다.

## 법칙이 틀리는 곳

이 법칙들은 대개 처음 쓰는 사람, 가끔 쓰는 화면에서 잘 맞는다. 맞지 않는 곳도 분명히 있다.

전문가 도구가 대표적이다. 사진 편집기, IDE, 회계 프로그램에는 메뉴가 수백 개다. 힉의 법칙대로 줄이면 오히려 일이 느려진다. 이 사용자들은 무엇을 찾는지 정확히 알고, 위치를 외우고, 단축키를 쓴다. 이런 화면에서는 선택지를 줄이는 대신 찾는 길을 여러 개 준다. 명령 팔레트(Ctrl/⌘ + K), 단축키, 최근 사용 목록, 사용자가 바꿀 수 있는 도구 막대가 그 길이다. 처음 쓰는 사람에게는 자주 쓰는 것만 보이고, 익숙해지면 나머지가 열리는 점진적 공개(progressive disclosure)가 두 사용자를 같이 챙기는 방법이다.

숨기는 것도 공짜가 아니다. 메뉴를 "더 보기" 아래로 접으면 선택지 수는 줄지만, 그 메뉴가 필요한 사람에게는 한 번 더 눌러야 하는 일이 되고, 아예 없다고 생각하게 만든다. 접을 항목은 감이 아니라 사용 빈도로 고른다.

숫자의 근거도 기억해 둔다. 힉의 법칙은 등과 버튼을 짝짓는 실험실 과제에서, 피츠의 법칙은 한 방향으로 손을 움직이는 과제에서 나왔다. 실제 화면에서 사람은 읽고, 비교하고, 망설이고, 스크롤한다. 공식으로 "이 버튼은 112ms 빨라진다"고 말할 수는 없다. 법칙은 어느 방향으로 고칠지 알려 주는 나침반이고, 고친 결과는 실제 사용자 데이터로 확인한다.

## 폼을 여러 단계로 나누면 항상 좋을까

결제 폼을 고칠 때 가장 자주 나오는 질문이다. 답은 "항상은 아니다"이고, 기준을 몇 가지로 볼 수 있다.

나누면 좋은 경우가 있다. 칸이 많아서 한 화면에 다 놓으면 시작하기도 전에 겁을 주는 폼, 앞의 답에 따라 뒤의 질문이 달라지는 폼(개인/사업자), 묶음이 분명한 폼(배송 → 결제 → 확인)이다. 한 단계에 한 가지 일만 보이니 외재적 부하가 줄고, 앞 단계의 입력을 단계마다 서버에 저장해 두면 중간에 나가도 다시 이어 갈 수 있다. 쉬운 질문을 앞에 두면 사람은 이미 시작한 일을 끝내려는 경향이 있어서 끝까지 갈 확률이 오른다는 설명도 있다.

나누면 나쁜 경우도 있다. 칸이 대여섯 개뿐인 폼을 세 단계로 쪼개면 누를 버튼과 화면 전환만 늘어난다. 단계마다 서버를 다녀오면 기다리는 시간도 늘고, 단계가 바뀔 때마다 이탈할 기회가 생긴다. 앞 단계 내용을 다시 보고 싶을 때 뒤로 가기가 데이터를 날리면 최악이다. 몇 단계가 남았는지 모르게 만드는 것도 불안을 키운다.

나눈다면 지킬 것이 있다.

- 단계 표시로 전체 개수와 지금 위치를 보여 준다("2/3 결제 정보").
- 브라우저 뒤로 가기가 이전 단계로 가고 입력이 남게 만든다. 단계를 URL에 넣으면 이 동작이 자연스럽다.
- 마지막에 전체를 한 번 보여 주고 고칠 수 있게 한다.
- 단계마다 퍼널 이벤트를 남겨, 어느 단계에서 나가는지 본다. 나누기 전과 후를 같은 기준으로 비교한다.

결국 "나누기"도 하나의 가설이다. 어떤 화면에 맞는지는 실험으로 가린다.

## 결제 화면으로 돌아가서

처음의 결제 화면에 이 규칙을 적용하면 할 일 목록이 나온다. 가입 유도 배너와 "다른 상품 보기"를 걷어 내고(외재적 부하), 배송 방법은 가장 많이 고르는 하나를 기본으로 두고 나머지를 접고(기본값, 선택지 줄이기), 쿠폰 입력칸은 "쿠폰이 있나요?" 링크 아래로 접고(점진적 공개), 결제 버튼은 하나만 주 버튼으로 금액과 함께 화면 하단에 붙이고(위계, 피츠), 누르면 버튼이 잠기며 진행을 보여 주고 끝나면 주문 번호를 크게 보여 준다(피드백). 그리고 배포한 뒤 결제 화면의 이탈률이 정말 줄었는지 이전과 같은 기준으로 잰다. 법칙은 고칠 곳을 알려 줄 뿐이고, 고쳤는지는 숫자가 말한다.

## 면접에서 나올 만한 질문

### 힉의 법칙은 무엇이고, UI에 어떻게 적용하나요?

선택지가 늘수록 결정 시간이 log2(n + 1)에 비례해 는다는 법칙이다. 사람이 정렬된 목록을 절반씩 거르기 때문이라고 설명한다. 그래서 필요 없는 선택지를 빼고, 정렬과 묶음을 일관되게 하고, 긴 목록에는 검색을 붙인다. 다만 처음 보는 선택지를 비교하는 일은 거르기가 아니라 하나하나 읽는 일이라 개수에 더 가깝게 늘어난다.

### 피츠의 법칙을 근거로 버튼 크기와 위치를 어떻게 정하나요?

누르는 시간은 거리와 폭의 비율 log2(D/W + 1)로 정해지니, 자주 누르는 것은 크게, 가까이 둔다. 터치 대상은 WCAG 2.5.8 최소 24px, 권장 44px 이상으로 하고, 아이콘이 작아도 padding으로 누르는 영역을 키운다. 모바일 주요 버튼은 엄지가 닿는 하단에 두고, 위험한 버튼은 간격을 두고 보조 스타일로 낮춘다.

### 인지 부하를 줄이려면 개발자가 무엇을 하나요?

화면이 만든 외재적 부하를 줄인다. 이전 화면의 정보를 기억하게 하지 않고 계속 보여 주고, 한 번 입력한 값은 다시 묻지 않고, 형식은 서버에서 정리하고, 지금 할 일과 상관없는 내비게이션과 배너를 치운다. 일 자체의 어려움인 본질적 부하는 없앨 수 없으니 단계로 나누거나 순서를 정해 준다.

### 선택 과부하는 항상 일어나나요?

아니다. 잼 실험에서는 24가지보다 6가지일 때 구매율이 높았지만, 50편을 모은 메타 분석의 평균 효과는 0에 가까웠다. 선택지를 비교하기 어렵거나, 원하는 걸 아직 모르거나, 빨리 정해야 할 때 잘 나타난다. 그래서 처음 오는 사용자에게는 추천을 하나 보여 주고, 원하는 걸 아는 사용자에게는 많이 보여 주되 거르기 도구를 준다.

### 기본값은 어떻게 정하고, 언제 쓰면 안 되나요?

대부분이 고르는 값, 사용자의 이전 선택, 맥락에서 추론한 값, 안전한 쪽을 기본으로 둔다. 사용자는 기본값을 그대로 두는 경향이 강해서 기본값이 곧 결과가 된다. 마케팅 동의처럼 회사 이익을 미리 체크해 두는 것은 다크 패턴이고 명시적 동의를 요구하는 규정에도 걸린다. 의견이 갈리는 질문에 기본값을 두면 데이터도 오염된다.

### UX 법칙이 맞지 않는 경우는 언제인가요?

전문가 도구처럼 사용자가 무엇을 찾는지 알고 위치를 외우는 화면이다. 메뉴를 줄이면 오히려 느려지니 명령 팔레트, 단축키, 점진적 공개처럼 찾는 길을 늘린다. 법칙 자체도 실험실의 단순 과제에서 나온 것이라 실제 화면의 시간을 예측하지는 못한다. 고칠 방향으로만 쓰고 결과는 실제 데이터로 확인한다.

### 폼을 여러 단계로 나누면 항상 좋은가요?

아니다. 칸이 많거나 앞의 답에 따라 질문이 바뀌거나 묶음이 분명하면 나누는 게 좋지만, 칸이 몇 개 없는 폼을 쪼개면 버튼과 화면 전환과 이탈 기회만 는다. 나눈다면 단계 수와 현재 위치를 보여 주고, 뒤로 가기에 입력이 남게 하고, 단계마다 퍼널 이벤트를 남겨 전후를 비교한다.

### 버튼을 누른 뒤 피드백은 어떻게 설계하나요?

0.1초 안에는 눌린 모양과 상태 변화를 바로 보여 주고, 1초 근처면 버튼 안에 로딩을 넣고 버튼을 잠가 두 번 누르지 못하게 하고, 그 이상이면 진행 단계를 보여 준다. 끝났을 때는 일의 무게에 맞게 완료를 보여 주는데, 결제처럼 큰 일은 화면을 바꿔 주문 번호와 다음 일을 쓴다. 화면 쪽 잠금과 별개로 서버는 멱등 키로 중복 요청을 막는다.
