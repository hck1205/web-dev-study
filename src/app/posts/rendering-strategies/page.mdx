React로 만든 쇼핑몰의 상품 페이지 링크를 메신저에 붙여 넣었다. 미리보기 카드에 상품 이름도 사진도 없이 사이트 이름만 뜬다. 느린 휴대폰으로 같은 링크를 열면 흰 화면이 한참 보이다가 상품이 나타난다. 페이지 소스 보기를 눌러 보면 이유가 보인다.

```html
<body>
  <div id="root"></div>
  <script src="/assets/index-3f9a1c.js"></script>
</body>
```

서버가 보낸 HTML에는 상품 정보가 한 글자도 없다. 상품 이름은 자바스크립트가 내려받아 실행되고, 그 코드가 API를 불러서 데이터를 받은 다음에야 생긴다. 메신저의 미리보기 봇은 그걸 기다리지 않는다.

이 글은 "HTML을 누가, 언제 만드느냐"라는 질문 하나로 CSR, SSR, SSG, ISR, 스트리밍을 정리한다. 이름은 다섯 개지만 결국 이 질문에 대한 답이 다를 뿐이다.

## HTML은 어디서 언제 만들어지나

페이지의 HTML을 만들 수 있는 시점은 세 번이다. 빌드할 때, 요청이 왔을 때 서버에서, 요청이 끝난 뒤 브라우저에서.

- CSR(Client-Side Rendering)은 브라우저에서 만든다. 서버는 빈 껍데기와 JS만 보낸다.
- SSR(Server-Side Rendering)은 요청이 올 때마다 서버에서 만든다.
- SSG(Static Site Generation)는 빌드할 때 미리 만들어 파일로 둔다.
- ISR(Incremental Static Regeneration)은 SSG처럼 미리 만들어 두되, 정해진 시간이 지나거나 신호를 받으면 서버가 뒤에서 다시 만든다.
- 스트리밍 SSR은 요청 시점에 서버에서 만들지만, 다 만들 때까지 기다리지 않고 준비된 부분부터 조각으로 보낸다.

TTFB(Time To First Byte)는 요청부터 응답 첫 바이트가 올 때까지, FCP(First Contentful Paint)는 글자나 이미지가 처음 그려질 때까지, LCP(Largest Contentful Paint)는 화면에서 가장 큰 요소(보통 상품 사진이나 제목)가 그려질 때까지의 시간이다. FCP와 LCP는 좋아졌지만 대가가 셋 있다. 첫째, TTFB가 늘어난다. 데이터 조회와 렌더링이 끝날 때까지 첫 바이트가 나가지 않는다. 느린 API 하나가 페이지 전체를 붙잡는다. 둘째, 서버 비용이다. 요청마다 렌더링하니 트래픽이 몰리면 렌더링 서버를 늘려야 하고, 서버가 죽으면 페이지도 죽는다. 셋째, 4번과 6번 사이의 구간이다. 화면은 다 보이는데 누르면 반응이 없다. 사용자는 눌렀는데 안 되니 몇 번 더 누른다.

SSR 결과도 캐시할 수 있다. 로그인 여부와 상관없이 모두에게 같은 페이지라면 `Cache-Control: public, s-maxage=60`처럼 CDN이 잠깐 들고 있게 할 수 있다. 사용자마다 다른 내용(이름, 장바구니 수, 개인화 가격)이 HTML에 들어가면 공유 캐시에 넣으면 안 된다. 남의 장바구니가 보이는 사고가 난다. 이런 페이지는 `private, no-store`로 막거나, 개인화 부분을 HTML에서 빼서 브라우저에서 따로 불러온다. 요청 사이에 상태가 새는 문제와 서버 부하는 [SSR](/posts/rendering-ssr)에서 재현해 봤다.

## 하이드레이션은 공짜가 아니다

하이드레이션(hydration)은 서버가 만든 "마른" HTML에 브라우저가 물을 부어 살려 내는 일이다. React는 서버에서 했던 렌더링을 브라우저에서 한 번 더 하면서, 새로 DOM을 만드는 대신 이미 있는 DOM 노드를 순서대로 짚어 가며 자기 트리와 짝을 맞추고 이벤트 핸들러를 붙인다.

여기서 비용이 나온다. 서버에서 이미 렌더링한 컴포넌트도 그 코드가 전부 JS 번들에 들어가 브라우저로 와야 하고, 브라우저에서 다시 실행된다. 데이터도 두 번 온다. HTML 안에 그려진 형태로 한 번, 하이드레이션에 쓸 JSON으로 한 번. SSR은 첫 화면을 빠르게 해 줄 뿐 JS 양을 줄여 주지 않는다. 하이드레이션을 아예 덜 하는 방식은 [아일랜드와 재개 가능성](/posts/islands-resumability)에서 다룬다.

짝을 맞추다가 서버 결과와 브라우저 결과가 다르면 문제가 된다. 이걸 하이드레이션 불일치(hydration mismatch)라고 한다. 아래는 React가 서버 HTML을 앞에서부터 짚어 가는 모습이다. 상품 페이지에 "오늘 10:00:01 기준 재고"처럼 렌더링한 시각을 찍어 둔 경우다.

불일치를 만드는 흔한 원인은 정해져 있다.

- `Date.now()`, `new Date()`, `Math.random()`처럼 실행할 때마다 다른 값
- `toLocaleString()`처럼 서버와 브라우저의 시간대·언어 설정에 따라 결과가 바뀌는 포맷
- `typeof window !== "undefined"`로 갈라서 브라우저에서만 다른 걸 렌더링하는 코드, `localStorage`에 저장한 테마나 로그인 상태를 첫 렌더에서 읽는 코드
- `<p>` 안에 `<div>`를 넣는 것처럼 HTML 규칙에 어긋난 중첩. 브라우저가 HTML을 파싱하면서 구조를 고쳐 버려서 React가 기대한 트리와 달라진다
- 브라우저 확장 프로그램이 하이드레이션 전에 DOM에 끼워 넣은 요소

고치는 방법은 두 가지다. 첫 렌더는 서버와 똑같이 그리고, 브라우저에서만 알 수 있는 값은 `useEffect` 안에서 state로 바꿔 한 번 더 그린다. 또는 그 값을 서버에서 정해 데이터로 내려보낸다(시각을 서버에서 찍어 props로 넘기는 식). 시각 표시처럼 달라도 괜찮은 텍스트 한 곳이라면 그 요소에 `suppressHydrationWarning`을 붙여 경고를 끌 수 있다. 이 옵션은 그 요소 한 단계에만 적용되는 탈출구라서 불일치를 덮는 용도로 넓게 쓰면 안 된다. 속성 값 불일치는 React가 고쳐 준다는 보장이 없어서 서버 값이 그대로 남을 수 있다는 점도 기억해 둔다. 불일치 원인별 실제 메시지와 선택적 하이드레이션은 [하이드레이션](/posts/hydration)에 정리했다.

## SSG: 빌드할 때 미리 만든다

블로그 글, 회사 소개, 이용 약관처럼 모두에게 같고 자주 바뀌지 않는 페이지는 요청마다 만들 이유가 없다. SSG는 빌드할 때 HTML을 파일로 만들어 CDN에 올린다. 요청은 사용자와 가까운 CDN 서버에서 바로 끝난다. TTFB가 가장 짧고, 렌더링 서버가 없으니 트래픽이 몰려도 비용이 거의 늘지 않으며 서버 장애와도 상관이 없다. 내용이 HTML에 다 들어 있으니 검색 노출과 링크 미리보기도 문제없다. 하이드레이션은 SSR과 똑같이 필요하다.

약점은 두 가지다. 페이지 수만큼 빌드 시간이 늘어난다. 상품이 10만 개면 빌드 한 번에 10만 페이지를 만들어야 한다. 그리고 다시 빌드하기 전까지 내용이 바뀌지 않는다. 가격 하나 고치려고 전체를 다시 빌드하고 배포하는 건 현실적이지 않다.

## ISR: 정적 페이지를 뒤에서 다시 만든다

ISR은 SSG의 이 두 약점을 노린다. 빌드할 때는 인기 상품 몇천 개만 만들고, 나머지는 처음 요청이 올 때 만들어 캐시에 둔다. 그리고 페이지마다 유효 시간을 둬서 시간이 지나면 다시 만든다. 다시 만드는 방식이 독특하다. 아래 그림은 유효 시간을 60초로 둔 상품 페이지다.

그래서 시간 기반 갱신만으로는 가격처럼 틀리면 안 되는 값을 맡기기 어렵다. 이때 쓰는 게 요청 기반 갱신(on-demand revalidation)이다. Next.js App Router라면 관리 화면에서 가격을 저장하는 서버 코드가 `revalidatePath("/p/42")`나 `revalidateTag("product-42")`를 불러 그 페이지의 캐시를 바로 무효화한다. 시간 기반 설정은 페이지 파일에 `export const revalidate = 60`처럼 적는다. 아직 만들지 않은 상품 페이지는 `generateStaticParams`로 빌드할 목록을 정하고, 목록 밖 주소는 첫 요청 때 만들어 캐시한다.

Next.js가 아니어도 같은 생각을 HTTP 헤더로 할 수 있다. SSR 응답에 `Cache-Control: public, s-maxage=60, stale-while-revalidate=300`을 붙이면, 이 헤더를 지원하는 CDN은 60초 동안 캐시로 답하고 그 뒤 300초 동안은 옛 응답을 주면서 뒤에서 새로 받아 온다.

재고 수량처럼 몇 초도 틀리면 안 되는 값은 ISR 페이지에 굽지 않는다. 페이지는 정적으로 두고, 그 부분만 브라우저에서 API로 따로 불러오거나 스트리밍으로 채운다. 재생성 시점과 요청 기반 갱신을 Next.js로 직접 잰 결과는 [SSG와 ISR](/posts/rendering-ssg-isr)에 있다.

## 스트리밍: 준비된 부분부터 보낸다

SSR의 TTFB 문제로 돌아가 보자. 상품 페이지의 상품 정보는 50ms면 오는데, 리뷰 API가 800ms 걸린다면 페이지 전체가 800ms를 기다린다. 리뷰는 화면 아래쪽이라 사용자가 처음 보는 것도 아닌데 그렇다.

React 18의 스트리밍 SSR은 HTML을 한 번에 보내지 않고 조각으로 나눠 보낸다. `Suspense`로 감싼 부분은 데이터가 준비될 때까지 fallback(로딩 표시)으로 먼저 보내고, 준비되면 그 자리를 채울 HTML 조각을 같은 응답에 이어서 흘려보낸다. Node.js라면 `renderToPipeableStream`, 웹 스트림 환경이라면 `renderToReadableStream`이 이 일을 한다.

```tsx
export default function ProductPage({ id }) {
  return (
    <main>
      <ProductInfo id={id} />
      <Suspense fallback={<ReviewsSkeleton />}>
        <Reviews id={id} />
      </Suspense>
    </main>
  );
}
```

스트리밍은 SSR의 "가장 느린 데이터가 전체를 붙잡는" 문제와 "전체 JS가 와야 하이드레이션이 시작되는" 문제를 Suspense 경계 단위로 쪼갠다. 다만 제약이 따라온다.

첫 조각을 보낼 때 HTTP 상태 코드와 헤더도 함께 나간다. 그 뒤에 데이터를 읽다가 상품이 없다는 걸 알아도 상태 코드를 404로 바꾸거나 리다이렉트할 수 없다. 404나 리다이렉트를 판단하는 데이터는 셸을 보내기 전, Suspense 경계 바깥에서 기다려야 한다. 그리고 중간에 있는 프록시나 압축 설정이 응답을 끝까지 모았다가 보내면 스트리밍이 소용없어진다. nginx의 `proxy_buffering`이 대표적이다. 배포 환경에서 응답이 정말 조각으로 오는지 개발자 도구의 네트워크 탭에서 확인해 봐야 한다.

Suspense 경계를 어디에 둘지도 설계다. 경계가 너무 잘면 스켈레톤이 여기저기서 따로 깜빡이고 레이아웃이 들썩인다(CLS가 나빠진다). 사용자가 한 덩어리로 보는 단위로 묶고, 스켈레톤은 실제 내용과 같은 크기로 만든다. 조각이 오가는 방식과 프록시 버퍼링은 [스트리밍 SSR과 Suspense](/posts/streaming-ssr-suspense)에서 더 깊게 본다.

## 서버 컴포넌트는 SSR과 다른 이야기다

여기까지의 전략은 모두 같은 전제를 깔고 있다. 서버에서 무엇을 렌더링했든 그 컴포넌트 코드는 전부 브라우저로 내려가 다시 실행된다. React Server Components(RSC)는 이 전제를 바꾼다.

서버 컴포넌트는 서버에서만 실행되는 컴포넌트다. 렌더링 결과만 브라우저로 보내고 코드는 보내지 않는다. 그래서 하이드레이션도 하지 않는다. 상품 설명의 마크다운을 HTML로 바꾸는 큰 라이브러리를 서버 컴포넌트에서 쓰면, 그 라이브러리는 번들에 한 바이트도 들어가지 않는다. DB나 내부 API를 직접 부를 수도 있다. 대신 state, effect, 이벤트 핸들러를 쓸 수 없다. 그런 게 필요한 부분은 파일 맨 위에 `"use client"`를 적은 클라이언트 컴포넌트로 만든다.

헷갈리기 쉬운 점이 둘 있다. 하나, RSC와 SSR은 다른 축이다. SSR은 "첫 HTML을 서버에서 만든다"는 이야기고, RSC는 "어떤 컴포넌트 코드가 브라우저에 가느냐"는 이야기다. Next.js App Router에서 클라이언트 컴포넌트도 첫 요청에서는 서버에서 HTML로 렌더링되고 브라우저에서 하이드레이션된다. 이름과 달리 클라이언트 컴포넌트는 "브라우저에서만 실행되는 컴포넌트"가 아니라 "브라우저에서도 실행되는 컴포넌트"다. 둘, 서버 컴포넌트에서 클라이언트 컴포넌트로 넘기는 props는 직렬화할 수 있어야 한다. 함수나 클래스 인스턴스는 넘길 수 없다(서버 액션은 예외다).

`"use client"`는 경계를 표시한다. 그 파일이 import하는 모든 것이 클라이언트 번들에 들어간다. 페이지 꼭대기 레이아웃에 `"use client"`를 붙이면 그 아래 전부가 클라이언트 컴포넌트가 되어 RSC의 이점이 사라진다. 상호작용이 필요한 말단(버튼, 폼, 탭)에만 붙이고, 그 안에 서버에서 그린 내용을 넣고 싶으면 `children`으로 넘긴다. RSC 페이로드와 경계를 넘는 props는 [React 서버 컴포넌트](/posts/react-server-components)에서 이어진다.

## 큰 쇼핑몰에서 페이지마다 고르기

전략은 사이트 하나에 하나를 고르는 게 아니라 페이지마다 고른다. Next.js 같은 프레임워크는 라우트마다 다르게 정할 수 있다. App Router가 라우트를 정적·동적으로 가르는 기준은 [Next.js App Router는 언제 정적이고 언제 동적인가](/posts/nextjs-static-dynamic-rendering)에 있다. 판단 기준은 몇 가지 질문으로 정리된다. 모두에게 같은 내용인가, 얼마나 자주 바뀌고 틀리면 얼마나 곤란한가, 검색과 링크 미리보기에 나와야 하는가, 얼마나 많은 상호작용이 있는가.

| 페이지 | 고를 만한 전략 | 이유 |
|---|---|---|
| 홈·기획전 | ISR + 요청 기반 갱신 | 모두에게 같고 트래픽이 가장 많다. 배너를 바꿀 때 갱신 신호를 보낸다 |
| 상품 상세 | ISR 본문 + 스트리밍 또는 브라우저 조회 | 검색 노출이 중요하다. 재고·개인화 가격·리뷰처럼 자주 바뀌는 부분만 따로 채운다 |
| 검색 결과 | SSR(짧은 CDN 캐시) | 검색어 조합이 끝이 없어 미리 만들 수 없다. 인기 검색어는 잠깐 캐시한다 |
| 장바구니·결제 | SSR(no-store) 또는 CSR | 사용자마다 다르고 검색에 나올 이유가 없다. 공유 캐시에 넣으면 안 된다 |
| 관리자 화면 | CSR | 로그인 뒤에서 오래 머물며 조작한다. 첫 화면보다 전환 속도와 개발 편의가 중요하다 |

상품 상세가 가장 많은 걸 섞는다. 상품 이름, 사진, 설명은 ISR로 구워 CDN에서 내준다. 메신저 미리보기와 검색이 이걸 본다. 재고 수량과 회원별 할인가는 HTML에 굽지 않고, 스트리밍으로 채우거나 하이드레이션 뒤 브라우저에서 불러온다. 리뷰는 Suspense 경계 안에 넣는다. 설명의 마크다운 변환이나 무거운 포맷팅은 서버 컴포넌트에 두어 번들에서 뺀다. 장바구니 버튼만 클라이언트 컴포넌트다.

반대로 하지 말아야 할 조합도 있다. 개인화된 HTML을 `public` 캐시에 넣는 것, 가격처럼 틀리면 곤란한 값을 시간 기반 ISR에만 맡기는 것, 관리 화면까지 SSR로 만들어 렌더링 서버 비용과 하이드레이션 문제만 떠안는 것이다.

<Callout kind="warning" title="개인화 HTML은 공유 캐시에 넣지 않는다">
CDN이나 ISR 캐시는 모든 사용자가 같은 응답을 받는다. 쿠키를 읽어 이름이나 장바구니를 HTML에 넣은 페이지가 여기 들어가면 다른 사람의 정보가 노출된다. 개인화 페이지는 `Cache-Control: private, no-store`로 응답하거나, 개인화 부분을 HTML 밖으로 뺀다.
</Callout>

## 고른 전략대로 나가는지 밖에서 확인하기

전략을 골라 배포했다고 그대로 동작한다는 보장은 없다. 프레임워크 설정 한 줄, 중간 프록시 설정 한 줄로 SSR이 CSR처럼, 스트리밍이 한 덩어리처럼 나간다. 그래서 브라우저가 아니라 밖에서, 봇과 같은 눈으로 응답을 본다. 아래는 React 19.2의 `renderToPipeableStream`으로 상품 페이지를 띄우고(리뷰는 1.5초 걸리는 Suspense 경계), 앞에 nginx를 세워 확인한 결과다.

처음 장면처럼 링크 미리보기가 비어 있다면 HTML에 무엇이 들어 있는지부터 본다. 미리보기 봇은 JS를 실행하지 않으니 `curl`이 보는 것이 곧 봇이 보는 것이다.

```bash
# 받은 HTML에서 제목, og 태그, h1만 뽑아 본다
curl -s https://shop.example.com/p/42 | grep -o -E '<title>[^<]*</title>|<meta property="og:title"[^>]*>|<h1>[^<]*</h1>'
```

```text
# SSR로 나간 페이지
<title>무선 이어폰</title>
<meta property="og:title" content="무선 이어폰"/>
<h1>무선 이어폰</h1>

# CSR로 나간 페이지
<title>Shop</title>
<div id="root"></div>
```

아래쪽처럼 나오면 그 경로는 서버에서 내용을 만들지 않고 있다. Next.js라면 페이지가 통째로 클라이언트에서만 데이터를 받게 짜였거나, `ssr: false`로 감싼 컴포넌트 안에 제목이 들어간 경우가 많다.

스트리밍은 조각이 언제 도착하는지를 재야 한다. 응답 본문을 읽으면서 조각마다 시각을 찍는 짧은 스크립트를 썼다.

```js
// chunks.mjs: 응답 조각이 도착한 시각을 찍는다
const t0 = performance.now();
const res = await fetch(process.argv[2]);
const reader = res.body.getReader();
let i = 0;
for (;;) {
  const { done, value } = await reader.read();
  if (done) break;
  console.log(`chunk ${++i}  ${Math.round(performance.now() - t0)}ms  ${value.length} bytes`);
}
```

```text
== Node 서버에 직접
chunk 1    240ms  309 bytes
chunk 2   1708ms  929 bytes
== nginx 뒤 (기본 설정)
chunk 1   1629ms  1238 bytes
== nginx 뒤 (proxy_buffering off)
chunk 1    159ms  309 bytes
chunk 2   1652ms  929 bytes
```

직접 받으면 셸과 스켈레톤(309바이트)이 먼저 오고 리뷰 조각이 1.5초 뒤에 온다. nginx 기본 설정을 거치면 같은 응답이 1.6초에 한 덩어리로 온다. nginx가 upstream 응답을 버퍼에 모았다가 보내서다. 사용자 입장에서는 스트리밍을 안 쓴 SSR과 똑같다. `curl`로 보면 더 간단하다. `curl -sN -o /dev/null -w 'starttransfer=%{time_starttransfer}s total=%{time_total}s\n'`의 두 값이 거의 같다면(이번 측정에서 버퍼링을 거친 응답은 1.5045s와 1.5046s) 첫 바이트가 끝까지 기다린 것이다. 직접 받았을 때는 0.0027s와 1.5038s였다.

해결은 그 location에 `proxy_buffering off;`를 주거나, 애플리케이션이 응답 헤더에 `X-Accel-Buffering: no`를 붙여 nginx가 그 응답만 버퍼링하지 않게 하는 것이다. 압축을 하는 프록시나 CDN, 서버리스 플랫폼의 응답 방식도 같은 문제를 만들 수 있으니, 운영 경로 그대로 한 번은 재 본다. 프록시가 요청과 응답을 어떻게 받아 넘기는지는 [프록시와 리버스 프록시](/posts/proxy-reverse-proxy)에서 다뤘다.

하이드레이션 불일치는 개발 빌드 콘솔에서 바로 보인다. 앞 절의 재고 시각 예를 서버는 UTC, 브라우저는 서울 시간대로 렌더링하게 해서 띄웠다.

```text
Hydration failed because the server rendered text didn't match the client. As a result this tree will be regenerated on the client. This can happen if a SSR-ed Client Component used:
...
- Date formatting in a user's locale which doesn't match the server.
...
  <Stock>
    <main>
      <h1>
      <p>
        <time>
+         오전 2:58:43
-         오후 5:58:43
```

`+`가 브라우저, `-`가 서버의 결과다. 어느 요소의 어떤 텍스트가 갈렸는지까지 트리로 보여 주니 이 메시지를 보면 원인을 거의 바로 찾는다. 문제는 운영이다. 같은 코드를 프로덕션 빌드로 띄우면 남는 건 `Minified React error #418; visit https://react.dev/errors/418?args[]=text&args[]= ...` 한 줄이다. 어느 요소인지는 빠지고, 화면은 브라우저 렌더링으로 갈아치워진 채 멀쩡해 보인다. 그래서 "가끔 첫 화면이 깜빡인다", "LCP가 이유 없이 나쁘다" 같은 증상으로 돌아온다. 컨테이너의 `TZ`와 서버 로케일을 사용자 쪽과 맞추거나, 시각·숫자 포맷을 서버에서 정해 데이터로 내려보내는 게 확실하다. 개발 환경에서는 서버와 브라우저의 시간대가 같아서 이 문제가 안 보이는 경우가 많다. 스테이징 서버를 UTC로 두고 한 번은 확인해 본다.

## 다시 미리보기 카드로

처음의 빈 미리보기 카드는 HTML을 브라우저에서 만들었기 때문에 생겼다. 다섯 가지 전략은 그 HTML을 빌드 때, 요청 때, 브라우저에서, 혹은 그 사이 어딘가에서 만드는 선택이고, 각자 TTFB와 LCP, 서버 비용, 데이터 신선도를 다르게 맞바꾼다. 서버에서 HTML을 만들면 첫 화면은 빨라지지만 하이드레이션이라는 비용이 따라오고, 스트리밍과 서버 컴포넌트는 그 비용을 조각내고 줄이는 방법이다. 페이지마다 "누구에게 같은가, 얼마나 자주 바뀌나, 검색에 나와야 하나"를 물으면 고를 전략이 거의 정해진다. 하이드레이션 뒤 브라우저에서 일어나는 렌더링은 [React는 언제 다시 그리나](/posts/react-rerender)에서 이어서 다뤘다.

## 면접에서 나올 만한 질문

### CSR과 SSR의 차이와 각각의 장단점은요?

차이는 HTML을 만드는 곳이다. CSR은 서버가 빈 HTML과 JS를 보내고 브라우저가 데이터를 받아 화면을 만들어서, 첫 화면과 검색 노출이 불리하지만 서버가 단순하고 이후 화면 전환이 빠르다. SSR은 요청마다 서버가 데이터를 넣은 HTML을 만들어 FCP와 LCP가 빠르고 크롤러가 내용을 바로 읽는다. 대신 TTFB가 늘고 요청마다 서버 비용이 들며, 하이드레이션 전까지는 보여도 동작하지 않는다.

### 하이드레이션이 무엇이고 왜 비용이 드나요?

서버가 만든 HTML에 React가 브라우저에서 같은 컴포넌트를 다시 실행해 기존 DOM과 짝을 맞추고 이벤트 핸들러를 붙이는 과정이다. 서버에서 그린 컴포넌트 코드도 전부 번들로 내려와 다시 실행되고, 데이터도 HTML과 JSON으로 두 번 온다. 그래서 SSR은 첫 화면을 앞당기지만 JS 양과 상호작용 가능 시점은 그대로 남는다.

### 하이드레이션 불일치는 왜 생기고 어떻게 고치나요?

서버와 브라우저의 첫 렌더 결과가 다를 때 생긴다. 현재 시각이나 난수, 시간대에 따라 바뀌는 포맷, `window`나 `localStorage`를 첫 렌더에서 읽는 코드, 잘못된 HTML 중첩이 흔한 원인이다. React 18부터는 그 지점의 가장 가까운 Suspense 경계까지 브라우저에서 다시 그리므로 성능 이점을 잃는다. 첫 렌더는 서버와 같게 두고 브라우저 전용 값은 `useEffect`에서 반영하거나 서버에서 값을 정해 내려보낸다.

### SSG와 ISR은 어떻게 다르고, ISR은 언제 페이지를 다시 만드나요?

SSG는 빌드할 때 모든 페이지를 만들고 다시 빌드하기 전까지 바뀌지 않는다. ISR은 미리 만든 페이지에 유효 시간을 두고, 시간이 지난 뒤 첫 요청이 오면 옛 페이지를 주면서 뒤에서 다시 만든다. 그래서 만료 뒤 첫 사용자는 낡은 페이지를 보고, 요청이 없으면 갱신도 일어나지 않는다. 즉시 반영이 필요하면 `revalidatePath`나 `revalidateTag` 같은 요청 기반 갱신을 쓴다.

### 스트리밍 SSR은 무엇을 해결하고, 어떤 제약이 있나요?

느린 데이터 하나가 페이지 전체의 TTFB를 붙잡는 문제를 푼다. Suspense 경계 바깥을 먼저 보내고 안쪽은 준비되는 대로 같은 응답에 이어 보내며, 하이드레이션도 경계 단위로 먼저 온 부분부터 한다. 다만 첫 조각과 함께 상태 코드와 헤더가 나가므로 그 뒤에는 404나 리다이렉트를 할 수 없고, 중간 프록시가 응답을 버퍼링하면 효과가 사라진다.

### React Server Components와 SSR은 같은 건가요?

다르다. SSR은 첫 HTML을 서버에서 만드는 렌더링 시점의 이야기고, RSC는 어떤 컴포넌트 코드가 브라우저 번들에 들어가는지의 이야기다. 서버 컴포넌트는 서버에서만 실행되어 코드가 번들에 들어가지 않고 하이드레이션도 하지 않는다. 클라이언트 컴포넌트도 첫 요청에서는 SSR되고 브라우저에서 하이드레이션된다.

### 쇼핑몰을 만든다면 페이지마다 어떤 전략을 고르겠어요?

모두에게 같고 트래픽이 많은 홈과 상품 상세는 ISR로 CDN에서 내주고, 가격 변경 같은 이벤트에 요청 기반 갱신을 건다. 상품 상세의 재고나 개인화 가격, 리뷰는 HTML에 굽지 않고 스트리밍이나 브라우저 조회로 채운다. 검색 결과는 조합이 끝이 없어 SSR에 짧은 CDN 캐시를, 장바구니와 결제는 공유 캐시 없이 SSR이나 CSR을, 로그인 뒤 관리자 화면은 CSR을 쓴다.

### CSR이면 검색 엔진에 안 나오나요?

꼭 그렇지는 않다. 구글은 JS를 실행해 렌더링하지만 대기열을 거쳐 늦어질 수 있고, 다른 검색 엔진이나 메신저·SNS 미리보기 봇 상당수는 JS를 실행하지 않고 첫 HTML만 본다. 그래서 검색과 공유가 중요한 페이지는 HTML에 내용과 메타 태그가 들어 있도록 SSR이나 SSG, ISR을 쓰는 게 안전하다.
