유튜브 링크를 눌렀는데 제목과 댓글, 추천 목록은 다 뜨고 영상 자리만 빙글빙글 돈다. 다른 날은 페이지 자체가 하얗게 멈춰 있다. 둘 다 "유튜브가 안 된다"로 신고가 들어오지만 고장 난 곳은 전혀 다르다. 유튜브는 서버 한 대가 아니라 이름이 여러 개인 서비스이고, 페이지와 영상이 서로 다른 길로 오기 때문이다.

주소창에 입력한 뒤 일어나는 기본 순서(DNS, TCP, TLS, HTTP, 렌더링)는 [google.com을 입력하면 일어나는 일](/posts/what-happens-google-com)에서 따라갔다. 노트북이 와이파이에 붙어 IP를 받는 데서 시작하는 이야기는 [전원을 켜고 첫 페이지가 뜨기까지](/posts/first-page-from-power-on)에 패킷 단위로 있다. 이 글은 그 흐름을 다시 설명하지 않고, 서비스가 아주 커졌을 때 무엇이 달라지는지만 본다. 이름 하나에 답이 여러 개인 DNS, 엣지에서 끝나는 TLS, HTTP/3로 넘어가는 두 번째 방문, 껍데기 HTML과 API, 그리고 다른 호스트에서 조각으로 오는 영상이다.

## 이 글에서 직접 잰 것과 못 잰 것

먼저 실제 유튜브를 재 보려 했다. 실습 환경은 Ubuntu 24.04, curl 8.5.0, OpenSSL 3.0.13, Node 22.22, Chromium 141이다.

```bash
# 유튜브 이름을 직접 풀어 본다
dig www.youtube.com

# 페이지를 HTTP/2로 요청해 본다 (이 환경은 바깥 연결이 프록시를 거친다)
curl -sv -o /dev/null --http2 https://www.youtube.com/
```

```text
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 44713
;; Query time: 0 msec
;; SERVER: 8.8.8.8#53(8.8.8.8) (UDP)

> CONNECT www.youtube.com:443 HTTP/1.1
< HTTP/1.1 403 Forbidden
* CONNECT tunnel failed, response 403
```

두 결과 모두 유튜브가 아니라 이 환경에 대한 이야기다. 8.8.8.8까지 갔다 왔다면 0ms일 수 없으니 중간에서 누군가 대신 답한 것이고, 프록시는 터널을 열기 전에 403으로 막았다. 그래서 이 글에 나오는 유튜브의 IP, 호스트 이름, 헤더 값은 공개된 자료와 개발자 도구에서 흔히 보이는 모양을 줄인 예시이고, 그때마다 예시라고 적었다. 대신 같은 구조를 로컬에 작게 만들어 Chromium으로 띄웠다. `www.yt.test`(페이지)와 `media.yt.test`(영상)를 Chromium의 `--host-resolver-rules`로 127.0.0.1에 묶고, Node의 `http2` 모듈로 서버 셋을 띄웠다. 이 부분의 출력은 모두 실제로 돌린 결과다.

이 두 줄은 그 자체로 쓸모가 있다. 회사망에서 "유튜브만 안 된다"는 신고가 오면 처음 확인할 게 이것이다. DNS 답이 0ms로 오거나, curl이 `CONNECT ... 403`에서 멈추면 서버까지 가지도 않았다. 서비스가 아니라 중간 장비의 정책을 봐야 한다.

## 주소창이 https 주소를 만들기까지

`youtube.com`을 치면 브라우저는 https를 붙여 먼저 시도한다. 사용자가 `http://`를 직접 쳤더라도 서버는 301로 https로 보내고, 응답의 `Strict-Transport-Security` 헤더가 브라우저에 "앞으로는 http로 오지 말라"고 남긴다. 아래는 로컬 서버로 같은 일을 한 결과다.

```bash
# 80번 역할을 하는 17900번: 무조건 https로 보낸다
curl -sI http://www.yt.test:17900/watch?v=Xq3vT9bLk2A

# https 쪽 응답 헤더 (실습용 인증서를 --cacert로 믿게 했다)
curl -sI --cacert cert.pem --resolve www.yt.test:17901:127.0.0.1 \
  "https://www.yt.test:17901/watch?v=Xq3vT9bLk2A"
```

```text
HTTP/1.1 301 Moved Permanently
location: https://www.yt.test:17901/watch?v=Xq3vT9bLk2A
Date: Wed, 21 Oct 2026 12:35:20 GMT
Connection: keep-alive
Keep-Alive: timeout=5

HTTP/2 200
content-type: text/html; charset=utf-8
strict-transport-security: max-age=31536000; includeSubDomains
alt-svc: h3=":17901"; ma=2592000
cache-control: no-cache
date: Wed, 21 Oct 2026 12:36:39 GMT
```

301 응답은 HTTP/1.1이고 https 응답은 HTTP/2다. 평문 쪽은 ALPN이 없어 HTTP/2를 고를 길이 없기 때문이다. HSTS가 있으면 두 번째부터는 이 301 왕복이 아예 사라진다. 첫 방문의 301조차 없애려는 게 HSTS 프리로드 목록이다. 브라우저에 박혀 나오는 목록이라 첫 요청부터 https로 간다. 어떤 도메인이 목록에 있는지는 hstspreload.org에서 확인할 수 있고, 이 글에서는 유튜브 도메인이 지금 목록에 있는지 직접 확인하지 못했다. 큰 서비스가 HSTS에 `includeSubDomains`를 붙일 때는 조심해야 한다. 하위 도메인 중 하나라도 https를 못 하면 그 이름은 브라우저에서 영영 열리지 않는다.

`alt-svc` 줄은 아래 QUIC 이야기에서 다시 쓴다. 주소의 나머지 조각은 이렇다.

## 이름 하나에 답이 여러 개

작은 서비스라면 `dig`의 답은 IP 하나다. 큰 서비스는 다르다. 같은 이름을 서울에서 물으면 서울 근처 엣지의 주소가, 런던에서 물으면 런던 근처 주소가 온다. 아래는 그런 서비스에서 흔히 보이는 답의 모양이다. 형식은 실제 dig 출력 그대로이고, 이름과 주소는 문서용 예시 값으로 바꿨다.

```text
;; ANSWER SECTION:   (예시)
www.youtube.com.        300   IN  CNAME  youtube-ui.l.google.com.
youtube-ui.l.google.com. 60   IN  A      203.0.113.10
youtube-ui.l.google.com. 60   IN  A      203.0.113.11
youtube-ui.l.google.com. 60   IN  A      203.0.113.12
youtube-ui.l.google.com. 60   IN  A      203.0.113.13
```

세 가지를 읽는다. CNAME으로 서비스 이름을 운영용 이름에 붙여 두면, 엣지를 바꿀 때 서비스 이름은 건드리지 않아도 된다. 마지막 단계의 TTL이 짧은 건 엣지 하나가 문제일 때 사용자를 빨리 다른 곳으로 옮기려는 것이다. A 레코드가 여럿이면 클라이언트는 하나가 안 붙을 때 다음 주소로 넘어간다. AAAA(IPv6)도 함께 오면 브라우저는 IPv6와 IPv4를 거의 동시에 시도해서 먼저 붙는 쪽을 쓴다(Happy Eyeballs, RFC 8305).

엣지를 고르는 방법은 두 가지다. DNS가 묻는 쪽의 위치를 보고 가까운 엣지 주소를 골라 주는 방식(GeoDNS)과, 여러 지점이 같은 IP를 광고해 라우팅이 가까운 곳으로 보내는 방식(애니캐스트)이다. 두 방식의 차이, EDNS Client Subnet, 회사 리졸버가 멀리 있을 때 엉뚱한 지역으로 가는 문제는 [CDN 엣지와 애니캐스트](/posts/cdn-edge-anycast)에서 직접 재현했다. 여기서 가져올 건 하나다. 사람마다, 장소마다, 몇 분마다 답이 다르니 "유튜브 IP"라는 고정된 값은 없다. 방화벽에 IP를 적어 막거나 풀려는 시도가 잘 안 되는 이유다.

## 두 번째 방문은 QUIC으로 간다

위 헤더의 `alt-svc: h3=":17901"; ma=2592000`은 "같은 호스트의 UDP 17901번에서 HTTP/3도 받는다, 이 정보를 30일 기억해도 된다"는 뜻이다. 실제 서비스는 보통 `h3=":443"`이다. 브라우저는 첫 응답을 받은 뒤에야 HTTP/3를 알게 되니, 첫 방문의 첫 요청은 TCP 위 HTTP/2이고 그 뒤부터 QUIC을 시도한다. Alt-Svc와 DNS HTTPS 레코드, QUIC이 TCP와 무엇이 다른지는 [HTTP 버전의 역사](/posts/http-versions)와 [UDP와 QUIC](/posts/udp-and-quic)에서 다뤘다. 여기서는 영상 서비스에서 이게 왜 중요한지만 본다.

세션 재개는 로컬에서 바로 확인할 수 있다. 첫 접속에서 받은 티켓을 파일로 저장하고, 두 번째 접속에서 내민다.

```bash
# 첫 접속: 세션 티켓을 sess.pem에 저장한다
sleep 1 | openssl s_client -connect 127.0.0.1:17901 -servername www.yt.test \
  -alpn h2 -sess_out sess.pem 2>/dev/null | grep -aE "^(New|Reused)|ALPN"

# 두 번째 접속: 저장한 티켓을 내민다
sleep 1 | openssl s_client -connect 127.0.0.1:17901 -servername www.yt.test \
  -alpn h2 -sess_in sess.pem 2>/dev/null | grep -aE "^(New|Reused)|ALPN"

# 티켓에 적힌 수명
openssl sess_id -in sess.pem -noout -text | grep -aE "Protocol|lifetime"
```

```text
New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
ALPN protocol: h2
Reused, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
ALPN protocol: h2
    Protocol  : TLSv1.3
    TLS session ticket lifetime hint: 7200 (seconds)
```

두 번째 줄의 `Reused`가 재개다. 인증서를 다시 받고 검증하는 일이 빠진다. `sleep 1`을 앞에 둔 이유가 있다. TLS 1.3에서 티켓은 핸드셰이크가 끝난 뒤 따로 오기 때문에, `echo |`로 바로 끊으면 티켓을 받기 전에 연결이 닫혀 `-sess_out` 파일이 쓸모없어진다. 직접 재 보다가 "재개가 안 된다"고 오해하기 쉬운 부분이다.

큰 서비스에는 여기에 함정이 하나 더 있다. 엣지 서버가 수천 대인데 티켓을 서버마다 다른 키로 암호화하면, 다음 접속이 다른 서버로 가는 순간 재개가 실패한다. 그래서 티켓 암호화 키를 서버들끼리 공유하고 주기적으로 바꾼다. 키를 오래 안 바꾸면 그 키가 새는 순간 지난 세션까지 위험해지니, 공유하되 짧게 돌리는 게 보통이다. 0-RTT 요청이 재전송될 수 있다는 위험은 [HTTPS와 TLS](/posts/https-tls)에서 다뤘다.

## HTML은 껍데기이고 내용은 API로 온다

엣지 뒤에서 오는 첫 HTML에는 영상이 없다. 큰 화면 틀과 스크립트, 그리고 첫 화면에 필요한 데이터 정도다. 유튜브는 첫 HTML 안에 초기 데이터를 JSON으로 넣어 보내고(`ytInitialData` 같은 이름으로 알려져 있다), 그다음 영상으로 넘어갈 때는 페이지를 새로 받지 않고 API만 부른다. 이건 개발자 도구에서 보이는 모양을 기준으로 한 설명이고 구현은 언제든 바뀔 수 있다. 로컬 데모도 같은 모양으로 만들었다. HTML에 초기 데이터를 넣고, 스크립트가 재생 정보를 API로 받고, 미디어 호스트로 조각을 요청한다. Chromium의 개발자 도구 프로토콜(CDP)로 요청마다 프로토콜과 상태 코드를 찍었다.

```text
NET +   14ms http/1.1 301 www.yt.test:17900/watch -> https://www.yt.test:17901/watch?v=Xq3vT9bLk2A
NET +   28ms h2       200 www.yt.test:17901/watch?v=Xq3vT9bLk2A
NET +   45ms h2       200 www.yt.test:17901/app.js
NET +   51ms h2       200 www.yt.test:17901/api/player?v=Xq3vT9bLk2A
NET +   57ms h2       204 www.yt.test:17901/favicon.ico
PAGE seg00 240p   100000B 206   306ms  measured  2612kbps  buffer 0.0s -> 2.0s
```

순서가 그대로 의존 관계다. HTML이 와야 스크립트를 알고, 스크립트가 돌아야 API를 부르고, API 답이 와야 미디어 호스트와 화질 목록을 안다. 영상 첫 조각은 HTML로부터 세 단계 뒤에 출발한다. 로컬이라 몇십 밀리초지만, 왕복이 100ms인 모바일 망이라면 단계마다 왕복이 붙는다. 큰 서비스가 첫 HTML에 초기 데이터를 넣고, 스크립트를 미리 받게 힌트를 주고, 미디어 호스트에 미리 연결해 두는(`preconnect`) 이유가 이 사슬을 짧게 만들려는 것이다. 빈 HTML에서 화면이 되기까지의 일반론은 [CSR과 SPA](/posts/rendering-csr-spa)에, 서버가 그린 HTML에 스크립트가 이벤트를 붙이는 과정은 [하이드레이션](/posts/hydration)에 있다.

이름이 엣지 앞단과 다르다는 게 장애를 나눌 때 가장 중요한 단서다. 페이지와 API는 `www.youtube.com`으로, 썸네일은 `i.ytimg.com` 같은 이미지 호스트로, 영상은 `*.googlevideo.com`으로 간다. 이름이 다르면 DNS 조회, TCP·QUIC 연결, TLS 핸드셰이크가 모두 따로다. 그래서 하나만 막혀도 나머지는 멀쩡하다.

조각을 받는 방법은 두 가지다. HLS처럼 조각마다 파일을 따로 만드는 방식과, 화질별로 파일 하나를 두고 바이트 구간을 잘라 받는 방식이다. 조각 파일과 목록 파일의 구조는 [동영상 스트리밍과 CDN 비용](/posts/sd-video-streaming-cost)에서 HLS로 봤으니, 여기서는 두 번째 방식을 쓴다. HTTP의 Range 요청이다.

```bash
# 240p 파일의 첫 100,000바이트만 달라고 한다
curl -s -o /dev/null -D - --cacert cert.pem --resolve media.yt.test:17903:127.0.0.1 \
  -r 0-99999 https://media.yt.test:17903/v/400.bin

# 파일 크기를 넘는 구간을 달라고 한다
curl -s -o /dev/null -D - --cacert cert.pem --resolve media.yt.test:17903:127.0.0.1 \
  -r 99999999-99999999 https://media.yt.test:17903/v/400.bin
```

페이지와 미디어 호스트가 다르니 브라우저 입장에서는 교차 출처 요청이다. 미디어 서버가 `access-control-allow-origin`을 안 주면 바이트는 왔는데 스크립트가 못 읽는다. `Range` 헤더는 크롬 계열 최근 버전에서 단순한 `bytes=시작-끝` 형태면 사전 요청(OPTIONS) 없이 나간다. 실제로 이 데모의 서버 로그에도 OPTIONS가 한 번도 찍히지 않았다. 다만 모든 브라우저와 모든 버전이 그렇지는 않으니, 주소의 파라미터로 구간을 넘기는 방식이 더 안전하다. ## 화질은 처리량과 버퍼가 같이 정한다

조각마다 화질을 고르는 게 ABR(적응형 비트레이트)이다. 기본 원리, 즉 잰 속도의 일정 비율 안에서 가장 높은 화질을 고르고 버퍼가 충격을 흡수한다는 이야기는 [동영상 스트리밍과 CDN 비용](/posts/sd-video-streaming-cost)에서 HLS 데모로 봤다. 여기서는 같은 회선에서 규칙을 조금 바꾸면 결과가 얼마나 달라지는지를 실제 브라우저로 잰다.

데모 플레이어의 규칙은 셋이다. 처리량은 최근 세 조각의 조화 평균으로 추정한다. 산술 평균보다 낮은 값에 끌려서, 한 번 튄 값에 속지 않는다. 버퍼가 4초 미만이면 추정치의 50%, 10초 미만이면 80%, 그 이상이면 100%까지 쓴다. 버퍼가 넉넉할 때만 과감해지는 것이다. 마지막으로 화질은 한 번에 한 칸만 올린다. 내릴 때는 바로 내린다.

```js
// abr.js: 처리량(kbps 목록)과 버퍼(초)로 다음 화질 인덱스를 고른다
function pickQuality(ladder, samples, buffer, current) {
  if (samples.length === 0) return 0;
  const recent = samples.slice(-3);
  const est = recent.length / recent.reduce((s, x) => s + 1 / x, 0); // 조화 평균
  const safety = buffer < 4 ? 0.5 : buffer < 10 ? 0.8 : 1.0;
  let pick = 0;
  for (let i = 0; i < ladder.length; i++) if (ladder[i] <= est * safety) pick = i;
  return Math.min(pick, current + 1); // 올릴 때는 한 칸씩
}
```

미디어 서버는 첫 조각 요청부터 8초 동안 3,000kbps, 18초까지 700kbps, 그 뒤로 6,000kbps로 보내도록 속도를 제한했다. 조각 하나는 2초 분량이고 사다리는 240p 400k, 360p 800k, 480p 1.5M, 720p 2.5M, 1080p 4.5M이다. 바이트는 실제로 오가고 시간도 실제 브라우저의 `performance.now()`로 쟀다. 영상을 디코딩하지는 않고, 재생은 버퍼에서 흐른 시간만큼 빼는 것으로 흉내 냈다.

## 영상만 안 나올 때와 페이지가 안 뜰 때

이름이 여럿이라는 걸 알면 장애를 나누는 첫 질문이 생긴다. "어느 이름에서 막혔나." 로컬 데모에서 미디어 호스트만 풀리지 않게 바꿔 돌렸다. Chromium의 `--host-resolver-rules`에서 `media.yt.test`를 `~NOTFOUND`로 두면 그 이름만 DNS 실패가 된다.

```bash
# www는 127.0.0.1로, media는 일부러 풀리지 않게
node run.cjs "MAP www.yt.test 127.0.0.1, MAP media.yt.test ~NOTFOUND"
```

```text

NET +   83ms h2       200 www.yt.test:17901/watch?v=Xq3vT9bLk2A
NET +  145ms h2       200 www.yt.test:17901/app.js
NET +  157ms h2       200 www.yt.test:17901/api/player?v=Xq3vT9bLk2A
NET +  157ms h2       204 www.yt.test:17901/favicon.ico
PAGE Failed to load resource: net::ERR_NAME_NOT_RESOLVED
NET FAIL net::ERR_NAME_NOT_RESOLVED Fetch
```

HTML, 스크립트, API는 전부 200이다. 화면에 제목도 떴다. 영상 조각 요청 하나만 DNS에서 죽었다. 사용자가 보는 건 "영상만 안 나온다"이고, 페이지 서버의 로그에는 아무 문제도 없다. 실제 현장에서 이런 모양이 나오는 경우를 증상별로 나누면 이렇다.

페이지 자체가 안 뜨면 `www` 이름 쪽이다. 크롬의 에러 화면 코드가 단계를 알려 준다. `ERR_NAME_NOT_RESOLVED`면 DNS, `ERR_CONNECTION_TIMED_OUT`이나 `ERR_CONNECTION_RESET`이면 연결 단계, `ERR_CERT_*`면 TLS다. 회사망이라면 프록시가 막았는지부터 본다. 이 글 처음의 `CONNECT ... 403`이 그 모양이다. 회사가 TLS를 중간에서 풀어 보는 장비를 쓰면 인증서 발급자가 회사 CA로 바뀌어 있다.

페이지는 뜨는데 영상만 돌면 미디어 이름 쪽이다. 개발자 도구 Network 탭에서 `videoplayback`으로 거르면 영상 요청만 남는다. 상태가 `(failed)`면 DNS나 연결이 막힌 것이다. 학교나 회사 필터가 `youtube.com`은 허용하고 `googlevideo.com`은 막은 경우가 흔한 예다. `403`이 보이면 서명이나 만료 시각 문제일 가능성이 높으니 새로고침으로 새 주소를 받는다. 요청은 계속 `200`·`206`인데 느리게 오면 회선이나 그 지역 미디어 캐시 문제다. 유튜브 플레이어를 오른쪽 클릭하면 나오는 "전문가용 통계"(Stats for nerds)에서 연결 속도와 버퍼 상태가 실시간으로 보인다. 버퍼 값이 0 근처에서 맴돌면 위 실행의 두 번째 결과와 같은 상황이다.

어느 쪽이든 Protocol 열을 켜 두면 `h3`인지 `h2`인지 보인다. 다른 사람은 되는데 한 사무실만 느리다면 거기서만 `h2`로 떨어져 있는지 확인한다. UDP 443이 막힌 망이다. 기능에는 문제가 없지만 왕복이 하나 늘고 손실에 약해진다.

브라우저 안쪽은 크롬 계열의 내부 페이지로 본다. `chrome://net-internals/#dns`에서 호스트 캐시를 비우고, `#sockets`에서 연결 풀을 비우고, `#hsts`에서 HSTS 기록을 조회한다. 예전에는 net-internals에서 이벤트 로그를 바로 봤지만, 최근 버전은 `chrome://net-export`로 로그 파일을 떠서 따로 연 뷰어에서 읽는다. 메뉴 이름과 위치는 버전마다 자주 바뀌니, 안 보이면 그 버전의 문서를 확인한다. 계층별로 더 아래까지 내려가는 순서는 [계층별로 장애 좁히기](/posts/network-troubleshooting-by-layer)에, 패킷으로 직접 보는 법은 [tcpdump로 패킷 캡처하기](/posts/packet-capture-tcpdump)에 있다.

## 큰 서비스가 바꾸는 것

같은 DNS, TCP, TLS, HTTP라도 서비스가 커지면 각 단계의 목표가 "사용자 가까이에서 끝내기"로 바뀐다. DNS는 가까운 엣지를 골라 주고, TLS는 그 엣지에서 끝나고, 두 번째 방문은 QUIC과 세션 재개로 왕복을 줄인다. 페이지는 껍데기와 API로 나뉘고, 영상은 다른 이름의 미디어 캐시에서 바이트 구간으로 오며, 플레이어가 처리량과 버퍼를 보고 조각마다 화질을 고른다. 이름이 나뉘어 있으니 장애를 볼 때도 "어느 이름에서 막혔나"를 먼저 묻는다.

## 면접에서 나올 만한 질문

### 유튜브 주소를 입력하고 영상이 나오기까지 무슨 일이 일어나나요?

기본 흐름은 다른 사이트와 같지만 길이 두 갈래다. 브라우저가 https 주소를 만들고 DNS로 가까운 엣지 주소를 받아 연결하면, 엣지가 TLS를 끝내고 안쪽 서버에서 껍데기 HTML과 초기 데이터를 받아 준다. 스크립트가 API로 재생 정보를 받으면 거기 적힌 별도 미디어 호스트로 새 연결을 맺고, 영상을 바이트 구간 단위로 받으며 조각마다 화질을 고른다. 두 번째 방문부터는 HTTP/3와 세션 재개로 연결이 더 빨리 열린다.

### 같은 이름인데 사람마다 받는 IP가 다른 이유는요?

DNS가 묻는 쪽의 위치를 보고 가까운 엣지의 주소를 골라 주거나(GeoDNS), 여러 지점이 같은 IP를 광고해 라우팅이 가까운 곳으로 보내기(애니캐스트) 때문이다. GeoDNS는 사용자가 아니라 리졸버의 위치를 보니 ECS로 사용자 대역을 함께 실어 보내기도 한다. TTL을 짧게 둬서 엣지 장애 때 사용자를 빨리 옮긴다. 그래서 큰 서비스를 IP로 막거나 허용하는 방화벽 규칙은 금방 틀어진다.

### TLS를 엣지에서 끝내면 무엇이 좋고 무엇을 조심해야 하나요?

핸드셰이크 왕복이 가까운 거리에서 끝나 첫 바이트가 빨라지고, 인증서와 키 관리가 한 계층에 모이며, 공격 트래픽을 안쪽까지 들이지 않는다. 대신 엣지에서 요청이 평문이 되니 그 계층이 가장 중요한 보안 경계가 되고, 엣지와 안쪽 사이를 다시 암호화하는 경우가 많다. 서버마다 세션 티켓 키가 다르면 다른 엣지로 갈 때 재개가 실패하니, 키를 공유하되 자주 바꾼다. 앱 서버는 사용자 IP를 앞단이 넣어 준 헤더로만 알 수 있다.

### 첫 방문은 HTTP/2인데 새로고침하면 HTTP/3가 되는 이유는요?

브라우저는 연결하기 전에는 서버가 HTTP/3를 하는지 모른다. 첫 응답의 `Alt-Svc: h3=":443"` 헤더를 보고 나서야 다음 요청부터 QUIC을 시도한다. DNS의 HTTPS 레코드에 alpn이 있으면 첫 요청부터 h3를 쓸 수 있다. UDP가 막힌 망에서는 QUIC이 실패하고 조용히 h2로 남으니, 한 곳에서만 계속 h2라면 UDP 443 차단을 의심한다.

### 영상은 왜 페이지와 다른 호스트에서 받나요?

트래픽의 성격이 완전히 달라서다. 페이지와 API는 작고 사람마다 다르며 안쪽 서비스를 불러야 하고, 영상은 크고 모두에게 같은 바이트라 통신사 안 캐시처럼 사용자에게 아주 가까운 곳에 두는 게 유리하다. 호스트를 나누면 미디어 서버를 따로 배치하고 확장하고 캐시 정책을 따로 둘 수 있다. 그 대가로 DNS, 연결, TLS가 한 번 더 일어나고 CORS 설정이 필요하다. 장애 때는 "페이지는 되는데 영상만 안 된다"처럼 증상이 갈린다.

### Range 요청은 무엇이고 영상에서 어떻게 쓰나요?

파일의 일부 바이트 구간만 달라는 요청이다. `Range: bytes=0-99999`를 보내면 서버가 `206 Partial Content`와 `Content-Range: bytes 0-99999/전체크기`로 답하고, 범위를 벗어나면 `416`을 준다. 플레이어는 파일 앞의 색인으로 시간을 바이트 위치로 바꿔, 화질별 파일 하나에서 필요한 구간만 받는다. 탐색(seek)할 때도 그 시간의 구간부터 받으면 된다. 교차 출처라면 `Content-Range`를 스크립트가 읽게 `Access-Control-Expose-Headers`를 열어야 한다.

### 회선이 갑자기 느려지면 플레이어는 어떻게 화질을 고르나요?

최근 조각들의 처리량으로 회선을 추정하고, 남은 버퍼에 따라 그 추정치를 얼마나 믿을지 정한다. 조화 평균을 쓰면 느린 값에 빨리 반응하고 한 번 튄 빠른 값에는 덜 속는다. 버퍼가 적으면 보수적으로 고르고, 올릴 때는 한 칸씩, 내릴 때는 바로 내린다. 직접 돌려 보니 직전 속도만 보고 버퍼를 무시한 규칙은 같은 회선에서 두 번 멈췄고, 버퍼를 함께 본 규칙은 한 번도 멈추지 않았다.

### "유튜브가 안 된다"는 신고를 받으면 어디부터 보나요?

어느 이름에서 막혔는지 먼저 나눈다. 페이지가 안 뜨면 `www` 쪽의 DNS, 연결, TLS를 크롬 에러 코드로 구분하고, 회사망이면 프록시가 CONNECT를 막는지 본다. 페이지는 뜨는데 영상만 돌면 Network 탭에서 영상 요청만 걸러 실패인지, 403인지, 느린 206인지 본다. 실패면 미디어 도메인 차단, 403이면 만료되거나 서명이 틀린 주소, 느리면 회선이나 지역 캐시 문제다. 특정 망에서만 느리면 h3에서 h2로 떨어졌는지도 확인한다.
