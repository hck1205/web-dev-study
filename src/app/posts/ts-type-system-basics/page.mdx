  사용자 번호와 주문 번호를 받는 함수에 둘의 순서를 바꿔 넣었는데 TypeScript가 아무 말도 하지 않는다. 둘 다 그냥 글자 묶음이라 검사기 눈에는 같은 것으로 보이기 때문이다.

  흔히 헷갈리는 점은 이 검사가 프로그램을 만들 때만 일어난다는 것이다. 실행할 때는 타입이 모두 지워지니, 서버에서 들어오는 값은 입구에서 직접 확인해야 한다.

주문 취소 API를 부르는 함수가 있다. 사용자 ID와 주문 ID를 받는데, 둘 다 문자열이라 타입 별칭을 하나씩 붙여 두었다.

```ts
type UserId = string;
type OrderId = string;

function cancelOrder(userId: UserId, orderId: OrderId) {
  console.log(`user=${userId} order=${orderId}`);
}

const userId: UserId = "u_42";
const orderId: OrderId = "o_9001";
cancelOrder(orderId, userId); // 순서를 바꿔 넘겼다
```

`tsc --strict`는 아무 말도 하지 않는다. 실행하면 인자가 뒤바뀐 채로 요청이 나간다.

```text
user=o_9001 order=u_42
```

이름을 따로 붙였는데 왜 막지 못했을까. TypeScript가 타입을 이름이 아니라 모양으로 비교하기 때문이다. `UserId`와 `OrderId`는 둘 다 `string`이라는 같은 모양이고, 별칭은 같은 타입에 붙은 다른 이름일 뿐이다.

이 글은 TypeScript 시리즈의 첫 글로, 타입 검사기가 "이 값을 저 자리에 넣어도 되나"를 판단하는 기본 규칙을 다룬다. 구조적 타이핑, 객체 리터럴의 초과 속성 검사, `any`·`unknown`·`never`, 리터럴 타입과 넓히기, 추론, `type`과 `interface`다. 이어지는 글은 [제네릭](/posts/ts-generics), [타입 좁히기](/posts/ts-narrowing), [유틸리티·매핑 타입](/posts/ts-utility-mapped-types), [tsconfig strict 옵션](/posts/tsconfig-strict), [React에서 TypeScript 쓰기](/posts/typescript-in-react)이고, 전체 순서는 [TypeScript 로드맵](/posts/typescript-roadmap)에 모았다. 예제는 모두 TypeScript 5.9와 `--strict`로 검사했다.

## 이름이 달라도 모양이 같으면 같은 타입이다

Java나 C#은 타입을 선언한 이름으로 구분한다. `class Celsius`와 `class Fahrenheit`는 필드가 똑같아도 서로 다른 타입이다. 이런 방식을 명목적 타이핑(nominal typing)이라고 한다. TypeScript는 반대로 구조적 타이핑(structural typing)을 쓴다. 받는 쪽이 요구하는 속성이 값에 모두 있고 그 속성의 타입이 맞으면 통과한다.

```ts
interface Point2D { x: number; y: number }
interface Point3D { x: number; y: number; z: number }

function length2D(p: Point2D) { return Math.hypot(p.x, p.y); }

const p3: Point3D = { x: 3, y: 4, z: 12 };
console.log(length2D(p3)); // Point3D를 Point2D 자리에 넣었다

const p2: Point2D = { x: 1, y: 2 };
const bad: Point3D = p2;   // 반대 방향
```

```text
shape.ts(10,7): error TS2741: Property 'z' is missing in type 'Point2D' but required in type 'Point3D'.
```

첫 호출은 통과하고 실행 결과는 `5`다. `Point3D`는 `x`와 `y`를 모두 가지고 있으니 `Point2D`가 필요한 자리에 들어갈 수 있다. 반대로 `Point2D`에는 `z`가 없어서 `Point3D` 자리에 못 들어간다. 속성이 더 많은 쪽이 더 적은 쪽에 들어간다. 집합으로 보면 `Point3D` 값들은 `Point2D` 값들의 부분집합이다.

아래 그림은 검사기가 `length2D(p3)`를 볼 때 하는 일을 순서대로 보여 준다. 받는 쪽(`Point2D`)이 요구하는 속성을 하나씩 찾고, 남는 속성은 따지지 않는다.

이 규칙은 자바스크립트를 생각하면 자연스럽다. 자바스크립트 함수는 받은 객체가 어느 클래스에서 왔는지 묻지 않고 필요한 속성만 꺼내 쓴다. 객체 리터럴을 아무 데서나 만들어 넘기는 코드가 대부분이라, 이름으로 비교하면 기존 코드 대부분이 타입 오류가 된다. TypeScript는 이미 있는 자바스크립트 코드에 타입을 입히려고 만든 언어라서 이 관습을 그대로 따랐다.

### 클래스도 모양으로 비교한다

클래스도 예외가 아니다. 이름이 다른 두 클래스라도 공개 멤버가 같으면 서로 바꿔 넣을 수 있다.

```ts
class Celsius { constructor(public value: number) {} }
class Fahrenheit { constructor(public value: number) {} }

const boil: Celsius = new Fahrenheit(212); // 오류 없음
console.log(boil instanceof Celsius);
```

```text
false
```

타입 검사는 통과했는데 런타임에 `instanceof`로 물어보면 `false`다. 검사기는 모양을 보고, `instanceof`는 프로토타입 체인을 본다. 둘이 다른 질문을 하고 있다는 걸 보여 주는 예다. 단, `private`이나 `#` 필드가 있으면 이야기가 달라진다. private 멤버는 "같은 선언에서 왔는가"까지 비교한다.

```ts
class Celsius { private readonly kind = "C"; constructor(public value: number) {} }
class Fahrenheit { private readonly kind = "F"; constructor(public value: number) {} }
const boil: Celsius = new Fahrenheit(212);
```

```text
priv.ts(3,7): error TS2322: Type 'Fahrenheit' is not assignable to type 'Celsius'.
  Types have separate declarations of a private property 'kind'.
```

## 문자열 두 개를 구분하는 브랜드 타입

처음의 ID 문제로 돌아가자. `string`끼리는 모양이 같으니, 모양을 일부러 다르게 만들면 된다. 실제로는 없는 속성을 타입에만 하나 붙이는 방법이다. 이걸 브랜드 타입(branded type)이라고 부른다.

```ts
type UserId = string & { readonly __brand: "UserId" };
type OrderId = string & { readonly __brand: "OrderId" };

const toUserId = (s: string) => s as UserId;
const toOrderId = (s: string) => s as OrderId;

function cancelOrder(userId: UserId, orderId: OrderId) {
  console.log(`user=${userId} order=${orderId}`);
}

const userId = toUserId("u_42");
const orderId = toOrderId("o_9001");
cancelOrder(orderId, userId);   // 순서를 바꿨다
cancelOrder("u_42", "o_9001");  // 그냥 문자열
cancelOrder(userId, orderId);   // 올바른 호출
console.log(userId.toUpperCase(), typeof userId);
```

```text
brand.ts(13,13): error TS2345: Argument of type 'OrderId' is not assignable to parameter of type 'UserId'.
  Type 'OrderId' is not assignable to type '{ readonly __brand: "UserId"; }'.
    Types of property '__brand' are incompatible.
      Type '"OrderId"' is not assignable to type '"UserId"'.
brand.ts(14,13): error TS2345: Argument of type 'string' is not assignable to parameter of type 'UserId'.
  Type 'string' is not assignable to type '{ readonly __brand: "UserId"; }'.
```

오류를 무시하고 그대로 실행하면 이렇게 나온다.

```text
user=o_9001 order=u_42
user=u_42 order=o_9001
user=u_42 order=o_9001
U_42 string
```

검사기는 앞의 두 호출을 막았다. 순서를 바꾸면 오류가 난다. 오류 메시지는 들여쓰기된 줄이 이유를 한 단계씩 파고드는 모양이다. 맨 아래 줄 `'"OrderId"' is not assignable to '"UserId"'`가 진짜 원인이다. 긴 오류는 마지막 줄부터 읽는 편이 빠르다.

## 객체 리터럴에만 걸리는 검사

구조적 타이핑대로라면 속성이 남는 건 괜찮아야 한다. 그런데 이런 코드는 오류가 난다.

```ts
interface ButtonProps { label: string; color?: "primary" | "danger"; onClick?: () => void }
function renderButton(p: ButtonProps) { return `<button class="${p.color ?? "primary"}">${p.label}</button>`; }

renderButton({ label: "삭제", colour: "danger" });
```

```text
excess.ts(4,29): error TS2561: Object literal may only specify known properties, but 'colour' does not exist in type 'ButtonProps'. Did you mean to write 'color'?
```

`colour`라는 오타를 잡아 줬다. 초과 속성 검사(excess property check)라는 별도 규칙이다. 방금 만든 객체 리터럴(검사기 용어로 fresh object literal)을 타입이 정해진 자리에 바로 넣을 때만 동작한다. 같은 객체를 변수에 담았다가 넘기면 검사가 꺼진다.

```ts
const props = { label: "삭제", colour: "danger" };
console.log(renderButton(props)); // 오류 없음
```

```text
<button class="primary">삭제</button>
```

빨간 버튼을 만들려던 의도는 사라지고 기본색 버튼이 나왔다. 아무 오류도 없이. 이 비대칭에는 이유가 있다. 리터럴을 그 자리에서 만들었다면 다른 곳에서 그 객체를 쓸 일이 없으니, 받는 쪽이 모르는 속성은 거의 확실히 실수다. 반면 변수로 넘긴 객체는 다른 용도로도 쓰이는 값일 수 있다. 위의 `p3`가 그랬다.

초과 속성 검사와 비슷한 규칙이 하나 더 있다. 모든 속성이 선택적인 타입(약한 타입, weak type)에 겹치는 속성이 하나도 없는 값을 넣으면 변수로 넘겨도 오류가 난다.

```ts
interface Options { retries?: number; timeoutMs?: number }
const opts = { retry: 3 };       // retries를 retry로 잘못 썼다
function request(o: Options) { return o; }
request(opts);
```

```text
excess.ts(15,9): error TS2559: Type '{ retry: number; }' has no properties in common with type 'Options'.
```

옵션 객체를 미리 만들어 두고 넘기는 코드가 많은데, 속성 하나만 오타가 나고 다른 하나는 맞으면 이 검사에도 걸리지 않는다. 옵션은 가능하면 호출하는 자리에서 리터럴로 쓰거나, 변수에 담을 때 `const opts: Options = { ... }`처럼 타입을 적어 그 자리에서 검사를 받는다. 뒤에서 볼 `satisfies`도 같은 목적에 쓴다.

`unknown`은 맨 위, 모든 값의 집합이다. 무엇이든 `unknown`에 넣을 수 있다. 대신 꺼내 쓸 때는 아무것도 할 수 없다. 이 값이 무엇인지 모르니 속성을 읽거나 호출하려면 먼저 확인해야 한다.

`never`는 맨 아래, 공집합이다. 들어갈 값이 하나도 없으니 어디에든 넣을 수 있다(빈 집합은 모든 집합의 부분집합이다). 항상 예외를 던지는 함수의 반환 타입, 모든 경우를 다 처리하고 남은 자리, `string & number`처럼 동시에 만족할 수 없는 교차 타입이 `never`다. 유니온에 섞인 `never`는 사라진다. `string | never`는 그냥 `string`이다.

`any`는 이 그림 밖에 있다. 어디에서 와도 받고 어디로든 넘어간다. 집합이 아니라 "이 값은 검사하지 마"라는 표시다. 두 타입을 같은 JSON에 써 보면 차이가 바로 드러난다.

```ts
const raw = '{"user":{"name":"kim"}}';

const a = JSON.parse(raw);        // JSON.parse는 any를 돌려준다
console.log(a.usr.name);          // 오타인데 통과

const u: unknown = JSON.parse(raw);
console.log(u.user.name);         // 확인 없이 쓰면 오류
```

```text
anyunk.ts(7,13): error TS18046: 'u' is of type 'unknown'.
```

검사기는 `unknown` 줄만 막았다. `any` 줄은 통과해서 실행하면 터진다.

```text
TypeError: Cannot read properties of undefined (reading 'name')
```

`any`는 한 곳에서 끝나지 않고 퍼진다. `any`의 속성을 읽으면 `any`, `any`를 돌려주는 함수의 반환 타입도 `any`가 된다. 선언 파일을 뽑아 보면 보인다.

```ts
const anyRes: any = { total: "100" };
export const total = anyRes.total * 2;              // 곱셈 결과는 number로 정해진다
export function getTotal() { return anyRes.total; } // 반환 타입이 any로 새어 나간다
```

```text
export declare const total: number;
export declare function getTotal(): any;
```

`getTotal()`을 쓰는 모든 곳이 검사 밖으로 나간다. 그래서 외부에서 들어오는 값(`JSON.parse`, `fetch().json()`, `localStorage`, `postMessage`)은 `unknown`으로 받고, 확인한 다음 구체적인 타입으로 좁힌다. `strict`에 포함된 `useUnknownInCatchVariables`(TypeScript 4.4부터)가 `catch (e)`의 `e`를 `unknown`으로 만드는 것도 같은 생각이다. 던져진 값이 `Error`라는 보장이 없기 때문이다.

```ts
try { JSON.parse("{"); } catch (e) { console.log(e.message); }                          // 오류
try { JSON.parse("{"); } catch (e) { if (e instanceof Error) console.log(e.message); }  // 통과
```

```text
catchu.ts(1,50): error TS18046: 'e' is of type 'unknown'.
```

`unknown`을 확인하는 방법(`typeof`, `in`, 사용자 정의 타입 가드)은 [타입 좁히기 글](/posts/ts-narrowing)에서 이어 간다. 하나만 덧붙이면, `never`에는 `any`도 넣을 수 없다. `let x: never = 1 as any`는 `Type 'any' is not assignable to type 'never'`로 막힌다. 모든 걸 받아 주는 `any`도 공집합 앞에서는 멈춘다.

## let은 넓히고 const는 좁힌다

`"GET"`이라는 값의 타입은 `string`일 수도, 오직 `"GET"` 하나만 들어가는 리터럴 타입 `"GET"`일 수도 있다. 검사기는 변수가 나중에 바뀔 수 있는지를 보고 둘 중 하나를 고른다. 이걸 넓히기(widening)라고 한다.

```ts
type Method = "GET" | "POST";
function send(url: string, method: Method) { return `${method} ${url}`; }

let m1 = "GET";
const m2 = "GET";
send("/a", m1);
send("/a", m2);

const req = { url: "/a", method: "GET" };
send(req.url, req.method);
```

```text
lit.ts(6,12): error TS2345: Argument of type 'string' is not assignable to parameter of type 'Method'.
lit.ts(10,15): error TS2345: Argument of type 'string' is not assignable to parameter of type 'Method'.
```

`let`은 나중에 다른 문자열을 넣을 수 있으니 `string`으로 넓혔다. `const`는 바뀔 수 없으니 `"GET"`으로 남았다. 객체의 속성은 `const`로 선언한 객체라도 속성 자체는 바꿀 수 있어서 `string`이 된다. 객체 설정값을 따로 빼 두면 이 오류를 자주 만난다. 고치는 방법은 세 가지가 있고, 결과 타입이 각각 다르다. 선언 파일로 뽑아 비교해 봤다.


```text

    readonly url: "/a";
    readonly method: "GET";
};
export declare const req3: {
    url: string;
    method: "GET";
};
export declare const req4: {
    url: string;
    method: "GET" | "POST";
};
```

`req4`처럼 타입을 직접 적으면 변수 타입이 적은 타입 그대로(`method: "GET" | "POST"`)가 된다. 셋의 차이는 이렇다. 타입 표기는 "이 변수는 이 타입이다"라고 못 박아서 값에서 알아낼 수 있던 더 좁은 정보를 버린다. `as const`는 값을 최대한 좁게 고정하지만 형식 검사는 하지 않는다. `satisfies`(TypeScript 4.9부터)는 "이 모양에 맞는지 검사만 해 줘, 타입은 값에서 추론해"라는 뜻이라 오타는 잡고 좁은 타입은 남긴다. 설정 객체, 라우트 표, 색 팔레트처럼 키를 나중에 정확히 꺼내 써야 하는 상수에 `satisfies`가 잘 맞는다. 활용은 [유틸리티·매핑 타입 글](/posts/ts-utility-mapped-types)에서 더 다룬다.

배열도 같다. `["sm", "md"]`는 `string[]`, `["sm", "md"] as const`는 `readonly ["sm", "md"]`라는 튜플이 된다. 리터럴 유니온을 배열에서 뽑아 쓰고 싶을 때 `as const`가 필요한 이유다.

## 추론에 맡길 곳과 적어 줄 곳

TypeScript는 많은 곳에서 타입을 알아서 정한다. 초기값에서 변수 타입을, `return` 문들에서 반환 타입을, 콜백이 들어갈 자리에서 매개변수 타입을 정한다. 마지막 것을 문맥적 타이핑(contextual typing)이라고 한다. `[1, 2, 3].map(n => n * 2)`에서 `n`에 타입을 적지 않아도 `number`인 이유다.

```ts
export const nums = [1, 2, 3].map(n => n * 2);
export function add(a: number, b: number) { return a + b > 10 ? "big" : a + b; }
export const el = [1, null];
```

```text
export declare const nums: number[];
export declare function add(a: number, b: number): number | "big";
export declare const el: (number | null)[];
```

`add`의 반환 타입이 `number | "big"`으로 추론됐다. 의도한 것일 수도, 실수로 문자열을 섞은 것일 수도 있다. 추론은 코드가 하는 일을 그대로 받아 적을 뿐, 의도를 알지 못한다. 그래서 적어 주는 곳의 기준은 "의도를 검사받고 싶은 경계"다.

- 함수 매개변수는 항상 적는다. 매개변수는 추론할 근거가 없으니 적지 않으면 `noImplicitAny`에 걸린다.
- 다른 모듈이 쓰는 함수의 반환 타입은 적는 편이 낫다. 구현을 고치다 반환 타입이 바뀌면 호출하는 쪽이 아니라 함수 안에서 오류가 난다.
- 빈 값으로 시작하는 변수는 적는다. 추론할 재료가 없기 때문이다.
- 지역 변수와 콜백 매개변수는 맡긴다. 적어 봐야 소음이다.

세 번째가 React에서 가장 자주 부딪히는 곳이다.

```tsx
const [todos, setTodos] = useState([]);
const add = () => setTodos([{ id: 1, title: "장보기" }]);
const [user, setUser] = useState(null);
const login = () => setUser({ name: "kim" });
```

```text
ust.tsx(5,31): error TS2322: Type '{ id: number; title: string; }' is not assignable to type 'never'.
ust.tsx(7,33): error TS2353: Object literal may only specify known properties, and 'name' does not exist in type '(prevState: null) => null'.
```

`useState([])`는 빈 배열에서 추론해 `never[]`, `useState(null)`은 `null`만 들어가는 상태가 된다. `useState<Todo[]>([])`, `useState<User | null>(null)`처럼 제네릭 인자로 적어 준다. 이 꺾쇠 안의 인자가 무엇인지는 [제네릭 글](/posts/ts-generics)에서, 컴포넌트 props와 이벤트 타입은 [React에서 TypeScript 쓰기](/posts/typescript-in-react)에서 다룬다.

## type과 interface 중 무엇을 쓰나

객체 모양을 적을 때는 `type`과 `interface` 둘 다 된다. 대부분의 경우 결과가 같아서 팀 규칙으로 하나를 고르면 된다. 차이가 드러나는 곳만 짚어 둔다.

```ts
interface User { id: string }
interface User { name: string }     // 같은 이름 interface는 합쳐진다
const u: User = { id: "1" };

type Account = { id: string };
type Account = { name: string };    // type은 다시 선언할 수 없다
```

```text
tvi.ts(3,7): error TS2741: Property 'name' is missing in type '{ id: string; }' but required in type 'User'.
tvi.ts(5,6): error TS2300: Duplicate identifier 'Account'.
tvi.ts(6,6): error TS2300: Duplicate identifier 'Account'.
```

첫째, 같은 이름의 `interface`는 선언 병합(declaration merging)으로 하나가 된다. 라이브러리 타입에 속성을 더할 때(`Window`에 전역 값 추가, Express `Request`에 `user` 추가) 이 기능을 쓴다. 반대로 내 코드에서는 다른 파일에서 같은 이름을 우연히 선언해 모르게 합쳐질 수도 있다.

둘째, 확장하다 충돌할 때 반응이 다르다.

```ts
interface Base { id: string }
interface Admin extends Base { id: number }

type BaseT = { id: string };
type AdminT = BaseT & { id: number };
const ad: AdminT = { id: 1 };
```

```text
tvi.ts(9,11): error TS2430: Interface 'Admin' incorrectly extends interface 'Base'.
  Types of property 'id' are incompatible.
    Type 'number' is not assignable to type 'string'.
tvi.ts(13,22): error TS2322: Type 'number' is not assignable to type 'never'.
```

`extends`는 선언하는 순간 충돌을 알려 준다. `&`는 선언은 받아 주고 `id`를 `string & number`, 곧 `never`로 만든다. 오류는 값을 넣는 곳에서야 나고, 메시지도 `never`라서 원인을 찾기 어렵다. 공통 필드를 물려받는 구조라면 `extends`가 진단이 더 친절하다.

셋째, 암묵적 인덱스 시그니처다. `type`으로 만든 객체 타입은 `Record<string, string>` 자리에 들어가는데, 같은 모양의 `interface`는 안 들어간다.

```ts
type Row = { id: string };
interface IRow { id: string }
const t: Row = { id: "1" };
const i: IRow = { id: "1" };
const rec1: Record<string, string> = t;   // 통과
const rec2: Record<string, string> = i;   // 오류
```

```text
idx.ts(6,7): error TS2322: Type 'IRow' is not assignable to type 'Record<string, string>'.
  Index signature for type 'string' is missing in type 'IRow'.
```

`interface`는 나중에 병합으로 다른 속성이 붙을 수 있어서, 지금 모양만 보고 "모든 값이 문자열"이라고 보장하지 않는다.

그리고 유니온(`"idle" | "loading"`), 튜플, 매핑 타입, 조건부 타입은 `type`으로만 만든다. 그래서 흔한 규칙은 "객체 모양, 특히 확장되는 공개 API는 `interface`, 나머지는 `type`"이거나 "전부 `type`, 병합이 필요할 때만 `interface`"다. 어느 쪽이든 섞어 쓰는 기준만 분명하면 된다.

## 컴파일이 끝나면 타입은 사라진다

지금까지의 검사는 모두 컴파일할 때 일어난다. `tsc`가 내놓는 자바스크립트에는 타입이 한 글자도 남지 않는다.

```ts
interface User { id: string; name: string }
type Role = "admin" | "member";

export function greet(user: User, role: Role): string {
  return `${role}:${user.name}`;
}
```

```text
export function greet(user, role) {
    return `${role}:${user.name}`;
}
```

이걸 타입 지우기(type erasure)라고 한다. 그래서 타입만으로는 런타임에 들어오는 값을 막을 수 없다. 서버가 `name` 대신 `nickname`을 보내도 `fetch().json()`은 `any`를 돌려주고, 그 값을 `User`라고 적어 두면 검사기는 그 말을 믿는다. 아래 그림은 같은 응답이 `any`, `unknown`, 검증 함수를 거칠 때 각각 어디까지 가는지 보여 준다.

타입이 사라진다는 사실은 반대로 장점도 된다. 타입은 실행 속도나 번들 크기에 영향을 주지 않는다. Node 22의 `--experimental-strip-types`나 esbuild·SWC 같은 도구가 타입을 검사하지 않고 지우기만 해서 빠르게 실행하는 것도 이 성질 덕분이다. 대신 그런 도구로 돌리면 타입 오류가 있어도 그냥 실행되니, `tsc --noEmit`을 CI에서 따로 돌린다. 이 블로그의 아래 연습 칸도 타입을 지우기만 하고 실행한다.

## JSX 속성도 같은 규칙으로 검사한다

React 컴포넌트에 넘기는 JSX 속성은 객체 리터럴처럼 검사된다. 그래서 초과 속성 검사가 그대로 적용된다.

```tsx
type ButtonProps = { label: string; color?: "primary" | "danger" };
function Button({ label, color = "primary" }: ButtonProps) {
  return <button className={color}>{label}</button>;
}
export const A = <Button label="삭제" colour="danger" />;

const rest = { label: "삭제", colour: "danger" };
export const B = <Button {...rest} />;  // 오류 없음
```

```text
button.tsx(5,37): error TS2322: Type '{ label: string; colour: string; }' is not assignable to type 'IntrinsicAttributes & ButtonProps'.
  Property 'colour' does not exist on type 'IntrinsicAttributes & ButtonProps'. Did you mean 'color'?
```

직접 쓴 속성의 오타는 잡히지만, 객체를 펼쳐 넘긴 `{...rest}`는 잡히지 않는다. 상위 컴포넌트가 받은 props를 그대로 아래로 펼쳐 넘기는 코드에서 오타나 이름이 바뀐 속성이 조용히 사라지는 이유다. 펼칠 때는 넘길 속성을 구조 분해로 골라 내거나, 펼칠 객체의 타입을 `ButtonProps`로 적어 둔다. `IntrinsicAttributes`는 `key`처럼 모든 컴포넌트가 받는 속성을 담은 타입이라, 메시지에 함께 나온다고 신경 쓸 필요는 없다.

## 직접 해 보기: unknown을 숫자로 바꾸기

경계에서 값을 확인하는 함수를 하나 만들어 보자. 장바구니 가격이 어떤 때는 숫자, 어떤 때는 `"2,000"` 같은 문자열, 어떤 때는 엉뚱한 값으로 들어온다. `unknown`을 받아 쓸 수 있는 숫자면 그 숫자를, 아니면 `null`을 돌려준다. 처음 코드는 `input as number`로 우기고 있다. `tsc`는 이 코드를 통과시키지만 테스트 대부분이 실패한다. `as`가 검사를 대신하지 못한다는 걸 직접 확인해 보자.

## 모양, 집합, 경계

TypeScript의 할당 규칙은 "받는 쪽이 요구하는 모양을 갖췄는가" 하나로 거의 설명된다. 그 위에 리터럴에만 걸리는 초과 속성 검사가 오타를 잡고, `unknown`과 `never`는 모든 값과 빈 집합으로 양 끝을 막고, `any`는 그 규칙을 꺼 버린다. 그리고 이 모든 검사는 컴파일이 끝나면 사라지니, 밖에서 들어오는 값은 경계에서 직접 확인해야 한다. 다음 글 [제네릭](/posts/ts-generics)에서는 이 모양을 매개변수로 받아 재사용하는 방법을 본다.

## 면접에서 나올 만한 질문

### TypeScript의 구조적 타이핑이란

타입을 선언한 이름이 아니라 가진 속성의 모양으로 호환성을 판단하는 방식이다. 받는 쪽이 요구하는 속성을 모두 갖고 타입이 맞으면, 이름이 다르거나 속성이 더 있어도 할당할 수 있다. 자바스크립트가 객체 리터럴을 자유롭게 만들어 넘기는 언어라서 그 관습을 따른 설계다. 다만 private·`#` 필드가 있는 클래스는 같은 선언에서 왔는지도 비교한다.

### 이름은 다르지만 둘 다 string인 ID를 구분하려면

타입 별칭은 같은 타입의 다른 이름일 뿐이라 구분되지 않는다. 실제 값에는 없는 속성을 교차 타입으로 붙인 브랜드 타입(`string & { __brand: "UserId" }`)을 쓰면 모양이 달라져서 서로 바꿔 넣으면 오류가 난다. 브랜드는 런타임에 없으니 값을 만드는 생성 함수 한 곳에서 형식을 검사하고 `as`로 붙인다.

### 구조적 타이핑인데 객체 리터럴에 속성을 더 넣으면 왜 오류가 나나

방금 만든 객체 리터럴을 타입이 정해진 자리에 바로 넣을 때만 동작하는 초과 속성 검사 때문이다. 그 자리에서 만든 객체는 다른 곳에서 쓰일 일이 없으니 모르는 속성은 오타일 가능성이 높다고 본다. 같은 객체를 변수에 담아 넘기거나 JSX에서 `{...rest}`로 펼치면 검사가 꺼진다. 모든 속성이 선택적인 약한 타입은 겹치는 속성이 하나도 없으면 변수로 넘겨도 TS2559로 막는다.

### any와 unknown의 차이는

둘 다 모든 값을 받지만 `unknown`은 확인하기 전에는 속성 접근이나 호출을 막고, `any`는 검사 자체를 끈다. `any`는 속성을 읽거나 반환하면서 다른 타입으로 퍼지기 때문에 한 곳에서 시작한 구멍이 넓어진다. 외부 입력은 `unknown`으로 받아 좁힌 다음 쓰고, `catch`의 변수가 `strict`에서 `unknown`인 것도 같은 이유다.

### never는 어디에 쓰나

값이 하나도 없는 타입, 집합으로는 공집합이다. 항상 예외를 던지거나 끝나지 않는 함수의 반환 타입, 동시에 만족할 수 없는 교차 타입의 결과, 유니온의 모든 경우를 처리하고 남은 자리의 타입으로 나타난다. 마지막 성질을 이용해 `switch`에서 빠진 경우를 컴파일 오류로 잡는 완전성 검사를 만든다.

### let과 const로 선언한 문자열의 타입이 다른 이유는

다시 할당할 수 있는 `let`은 `string`으로 넓히고, 바뀌지 않는 `const`는 리터럴 타입으로 남긴다. 객체 속성은 `const` 객체 안에서도 고칠 수 있어 `string`으로 넓어진다. 리터럴로 고정하려면 `as const`(readonly까지 붙음)를, 모양 검사와 좁은 타입을 함께 원하면 `satisfies`를 쓴다.

### type과 interface는 언제 무엇을 쓰나

객체 모양에는 둘 다 쓸 수 있고 결과도 대부분 같다. `interface`는 같은 이름끼리 병합되고 `extends` 충돌을 선언 시점에 알려 주며, 암묵적 인덱스 시그니처가 없어 `Record<string, …>` 자리에 바로 들어가지 않는다. 유니온·튜플·매핑·조건부 타입은 `type`으로만 만든다. 팀이 기준을 하나 정해 일관되게 쓰는 것이 차이보다 더 중요하다.

### 타입을 다 적었는데 런타임에 undefined 오류가 나는 이유는

타입은 컴파일 후 지워져서 런타임 값을 검사하지 않는다. `fetch().json()`이나 `JSON.parse`가 `any`를 돌려주고 그 값에 `as User`를 붙이면 검사기는 그 선언을 믿을 뿐이다. 외부 값은 `unknown`으로 받아 경계에서 타입 가드나 스키마 검증으로 확인하고, 그 뒤에만 구체적인 타입으로 쓴다.
