<EasyIntro>
  Next.js App Router에서는 폴더를 하나 만들면 그 이름이 주소가 되고, 폴더 안에 page라는 파일을 두면 그 주소에서 볼 수 있는 화면이 생긴다.

  화면은 여러 조각이 겹쳐서 만들어진다. 학교 건물로 치면 복도와 교실 같다. 교실을 옮겨 다녀도 복도는 그대로이고, 복도에 붙여 둔 게시물도 그대로 남는다.

  layout이라는 파일이 이 복도 역할을 해서, 페이지를 옮겨도 그 안에 적어 둔 값이 유지된다. template이라는 파일은 교실을 옮길 때마다 새로 칠하는 칸이라 안의 값이 처음으로 돌아간다.

  링크를 누르면 Next.js는 바뀐 교실만 받아서 끼워 넣는다. 그래서 이동이 빠르고 복도에 있던 값이 사라지지 않는다.
</EasyIntro>

대시보드에 검색 필터를 하나 붙였다. 필터 입력창을 `app/dash/layout.js`에 두었더니 다른 탭으로 옮겨도 입력해 둔 검색어가 그대로 남았다. 기획자는 탭을 옮기면 필터가 비워져야 한다고 했다. 그래서 같은 컴포넌트를 `template.js`로 옮기자 이번에는 원하는 대로 비워졌는데, 왜 그렇게 되는지는 설명하지 못했다.

이 차이를 눈으로 보려고 Next.js 16.4.1로 작은 앱을 만들었다. `dash/layout.js`와 `dash/template.js`에 똑같은 카운터 버튼을 넣고, 각 버튼이 마운트·언마운트될 때 콘솔에 찍게 했다. Playwright로 `/dash/a`에서 layout 버튼을 두 번, template 버튼을 한 번 누른 뒤 `Link`로 `/dash/b`에 갔다.

```text
console: mount layout
console: mount template
on /dash/a:             layout: 2 | template: 1 | page a
console: unmount template
console: mount template
after Link to /dash/b:  layout: 2 | template: 0 | page b
console: mount layout
console: mount template
after reload:           layout: 0 | template: 0 | page b
```

링크로 옮겼을 때 layout의 숫자는 2로 남았고 template만 언마운트됐다가 다시 마운트되어 0이 됐다. 새로고침하면 둘 다 0이다. 이 글은 이 결과를 출발점으로 App Router가 폴더를 어떻게 주소로 바꾸는지, 파일들이 어떤 순서로 겹쳐서 화면을 만드는지, 링크를 누르면 무엇을 받아 오는지를 차례로 본다. 렌더링이 정적인지 동적인지 정해지는 과정은 [App Router의 정적·동적 렌더링](/posts/nextjs-static-dynamic-rendering)에, 서버 컴포넌트가 무엇을 보내는지는 [React 서버 컴포넌트](/posts/react-server-components)에 따로 정리했다.

## 폴더가 주소가 되는 규칙

App Router는 `app` 폴더 아래의 폴더 하나를 URL의 한 조각으로 본다. 이 조각을 세그먼트(segment)라고 부른다. `app/dash/a/page.js`는 `dash`, `a` 두 세그먼트를 거쳐 `/dash/a`가 된다.

폴더만 있다고 주소가 열리지는 않는다. 그 폴더에 `page.js`나 `route.js`가 있어야 바깥에서 접근할 수 있다. 그래서 컴포넌트, 유틸, 테스트 파일을 라우트 폴더 안에 같이 둬도 주소가 생기지 않는다. 같은 자리에 둔다고 해서 이걸 colocation이라고 부른다.

실험 앱의 폴더 구조와 빌드 출력이다.

```text
app
├── layout.js
├── page.js
├── (marketing)/about/page.js
├── _lib/page.js
├── blog/[slug]/page.js        # generateStaticParams로 hello 하나만 미리 만든다
├── docs/[...slug]/page.js
├── shop/[[...slug]]/page.js
└── dash
    ├── layout.js
    ├── template.js
    ├── a/page.js
    └── b/page.js
```

```text
Route (app)
┌ ○ /
├ ○ /_not-found
├ ○ /about
├   /blog/[slug]
│ └ ● /blog/hello
├ ○ /dash/a
├ ○ /dash/b
├ ƒ /docs/[...slug]
└ ƒ /shop/[[...slug]]
```

`(marketing)` 폴더는 주소에서 사라지고 `/about`만 남았다. `_lib` 폴더에는 `page.js`를 넣었는데도 표에 아예 없다. 이 두 규칙은 아래에서 따로 본다. 기호 `○ ● ƒ`의 뜻은 [정적·동적 렌더링 글의 첫 절](/posts/nextjs-static-dynamic-rendering)에 있다.

한 세그먼트에 `page.js`와 `route.js`를 같이 둘 수는 없다. 둘 다 그 주소의 모든 HTTP 메서드를 가져가기 때문이다. API가 필요하면 `app/api/...`처럼 다른 세그먼트에 둔다. `route.js`는 [Route Handler와 Proxy](/posts/nextjs-route-handlers-proxy)에서 다룬다.

## 대괄호 세 가지

주소 일부가 바뀌는 페이지는 폴더 이름을 대괄호로 감싼다. 대괄호 모양이 세 가지이고, 받는 주소의 범위가 다르다. 서버를 띄우고 직접 요청해 페이지가 받은 `params`를 찍었다.

```bash
# 각 주소로 요청하고 상태 코드와 페이지가 받은 params를 본다
for p in /blog/hello /blog/new /docs/a /docs/a/b/c /docs /shop /shop/x/y; do
  curl -s -o page.html -w "$p %{http_code} " "localhost:3922$p"
  grep -o '<pre>[^<]*</pre>' page.html | sed 's/&quot;/"/g'
done
```

```text
/blog/hello 200 <pre>{"slug":"hello"}</pre>
/blog/new 200 <pre>{"slug":"new"}</pre>
/docs/a 200 <pre>{"slug":["a"]}</pre>
/docs/a/b/c 200 <pre>{"slug":["a","b","c"]}</pre>
/docs 404
/shop 200 <pre>{}</pre>
/shop/x/y 200 <pre>{"slug":["x","y"]}</pre>
```

`[slug]`는 세그먼트 정확히 하나를 문자열로 받는다. `[...slug]`(catch-all)는 하나 이상을 배열로 받고, 하나도 없으면 404다. `[[...slug]]`(optional catch-all)는 없어도 받는다. 그때 `params`는 빈 객체라서 `slug`가 `undefined`다. 문서 사이트의 `/docs/getting-started/install` 같은 깊은 경로는 catch-all로, 상품 목록 `/shop`과 카테고리 `/shop/men/shoes`를 한 페이지로 그릴 때는 optional catch-all로 받는다.

`/blog/new`는 `generateStaticParams` 목록에 없었는데 200이 났다. 목록 밖 주소를 첫 요청 때 만드는 게 기본값(`dynamicParams = true`)이라서다. 목록 밖을 404로 막으려면 `export const dynamicParams = false`를 쓴다.

Next 15부터 `params`는 Promise다. 페이지와 레이아웃에서 `await params`로 꺼낸다. 15에서는 동기로 읽어도 경고만 내고 동작했지만 16에서는 그 호환 동작이 빠졌다. 14 버전 코드를 옮길 때 가장 먼저 걸리는 곳이다.

```tsx
// app/docs/[...slug]/page.tsx
export default async function DocPage({
  params,
}: {
  params: Promise<{ slug: string[] }>;
}) {
  const { slug } = await params; // ["a", "b", "c"]
  return <h1>{slug.join(" / ")}</h1>;
}
```

규칙을 손으로 짜 보면 경계가 분명해진다. 아래 함수는 라우트 패턴과 실제 주소를 받아 `params`를 돌려주고, 맞지 않으면 `null`을 돌려준다. 괄호 폴더는 주소에서 빼고, 밑줄 폴더는 라우트가 아니라고 본다. 테스트의 기대값은 위 실험 앱이 실제로 낸 결과와 같다.

## 주소에 나오지 않는 폴더

괄호로 감싼 폴더 `(marketing)`은 라우트 그룹이다. 주소에는 나오지 않고, 파일을 묶고 레이아웃을 나누는 데만 쓴다. 마케팅 페이지와 쇼핑 페이지가 헤더 모양이 전혀 다르다면 이렇게 나눈다.

```text
app
├── (marketing)
│   ├── layout.js        # 큰 히어로 헤더
│   ├── about/page.js    # /about
│   └── page.js          # /
└── (shop)
    ├── layout.js        # 장바구니 헤더
    └── cart/page.js     # /cart
```

이렇게 두면 최상위 `app/layout.js` 없이 그룹마다 루트 레이아웃을 둘 수 있다. 조심할 점이 둘 있다. 서로 다른 루트 레이아웃 사이를 이동하면 소프트 내비게이션이 아니라 전체 새로고침이 일어난다. `/about`에서 `/cart`로 갈 때 화면이 한 번 하얗게 깜빡이는 건 버그가 아니라 규칙이다. 그리고 두 그룹이 같은 주소를 만들면 안 된다. `(marketing)/about`과 `(shop)/about`이 둘 다 `/about`이 되면 빌드 에러다.

밑줄로 시작하는 `_lib`는 private 폴더다. 안에 `page.js`가 있어도 라우트로 보지 않는다. 실험에서 `/_lib`은 404였다. 컴포넌트와 유틸을 라우트 폴더 안에 두면서 실수로 주소가 열리는 일을 막고 싶을 때 쓴다. 정말 밑줄로 시작하는 주소가 필요하면 폴더 이름을 `%5Fname`으로 쓴다.

프로젝트가 커지면 이 두 폴더 규칙으로 구조를 잡는다. 흔한 선택은 둘이다. 하나는 라우트 폴더 안에 그 화면만 쓰는 컴포넌트를 `_components`로 같이 두는 방식이다. 화면을 지우면 관련 코드가 같이 지워져서 정리가 쉽다. 다른 하나는 `app`에는 라우트 파일만 두고 나머지는 `src/features` 같은 곳에 모으는 방식이다. 이 블로그가 그렇게 한다. 여러 화면이 같은 코드를 나눠 쓰는 일이 많으면 이쪽이 낫다. 어느 쪽이든 라우트 그룹으로 팀이나 영역별 경계를 그어 두면, 레이아웃을 따로 줄 수 있고 코드 소유자를 정하기도 쉽다.

## 화면 조각이 겹치는 순서

한 세그먼트 폴더에 둘 수 있는 특수 파일은 `layout`, `template`, `error`, `loading`, `not-found`, `page`다. Next는 이 파일들을 정해진 순서로 감싸서 하나의 React 트리를 만든다. `loading`은 Suspense 경계가 되고, `error`와 `not-found`는 에러 경계가 된다.

코드로 풀면 이런 모양이다. 하위 세그먼트는 `page` 자리에 다시 같은 모양으로 들어간다.

```tsx
<Layout>
  <Template key={segmentKey}>
    <ErrorBoundary fallback={<Error />}>
      <Suspense fallback={<Loading />}>
        <NotFoundBoundary fallback={<NotFound />}>
          <Page />
        </NotFoundBoundary>
      </Suspense>
    </ErrorBoundary>
  </Template>
</Layout>
```

이 순서에서 실무 규칙 몇 개가 그대로 나온다.

`error.js`는 같은 세그먼트의 `layout.js`를 감싸지 않는다. 그래서 `dash/layout.js`가 던진 에러는 `dash/error.js`가 잡지 못하고 한 단계 위 세그먼트의 `error.js`로 올라간다. 레이아웃에서 데이터를 가져오다 실패할 수 있다면 부모 폴더에 `error.js`를 둔다. 루트 레이아웃의 에러는 잡아 줄 부모가 없어서 `app/global-error.js`가 따로 있다. 이 파일은 루트 레이아웃을 통째로 대신하므로 `<html>`과 `<body>`를 직접 그려야 하고, 전역 스타일도 따라오지 않는다.

직접 확인했다. `err-layout/layout.js`가 에러를 던지게 하고 같은 폴더와 루트에 각각 `error.js`를 두었다. 비교하려고 `err-page`에는 page가 던지게 했다. 둘 다 `connection()`으로 동적 라우트로 만들어 빌드 때가 아니라 요청 때 던지게 했다.

```text
/err-layout 500 | root error.js: digest 358391924
/err-page   500 | err-page/error.js
```

layout이 던진 에러는 같은 폴더의 `error.js`를 지나쳐 루트의 `error.js`가 받았고, page가 던진 에러는 같은 폴더의 `error.js`가 받았다. 둘 다 응답 상태는 500이다. 에러 화면이 그려졌다고 200이 되지는 않는다. 그리고 빌드 때 렌더링되는 정적 라우트에서 레이아웃이 던지면 에러 화면이 아니라 빌드 실패(`Error occurred prerendering page`)로 나타난다.

`error.js`는 반드시 클라이언트 컴포넌트다(`"use client"`). 에러 경계가 브라우저에서 동작해야 하기 때문이다. 서버 컴포넌트에서 난 에러는 프로덕션에서 메시지가 가려지고 `error.digest`만 온다. 서버 로그에서 같은 digest를 찾아 원인을 본다. 16.3부터 `error.js`가 받는 `retry()`는 경계 안을 서버에서 다시 받아 렌더링하고, `reset()`은 다시 받지 않고 상태만 지운다. 일시적인 네트워크 오류라면 `retry()`가 맞다.

`loading.js`는 그 세그먼트의 `page`를 Suspense로 감싼다. 레이아웃은 바깥에 있어서 로딩 중에도 그대로 보인다. 스트리밍이 실제로 어떻게 조각을 흘려보내는지는 [스트리밍 SSR과 Suspense](/posts/streaming-ssr-suspense)에, 에러 경계 자체의 동작은 [Suspense와 Error Boundary](/posts/react-suspense-error-boundary)에 있다.

`not-found.js`는 `notFound()`를 부르면 보인다. `/docs`처럼 아무 라우트에도 안 맞는 주소는 루트의 `not-found.js`(없으면 기본 404)가 처리한다.

## 레이아웃은 남고 템플릿은 다시 태어난다

처음 실험으로 돌아가면, layout의 카운터가 남은 이유는 React가 그 컴포넌트를 같은 자리의 같은 컴포넌트로 보고 그대로 두었기 때문이다. 링크 이동은 페이지 전체를 다시 그리지 않고 바뀐 세그먼트 아래만 바꾼다. `dash` 레이아웃은 `/dash/a`와 `/dash/b`에 공통이라 바뀌지 않았다.

template은 Next가 세그먼트마다 고유한 `key`를 붙여 렌더링한다. React는 `key`가 바뀌면 이전 컴포넌트를 버리고 새로 만든다. 그래서 상태가 0으로 돌아가고 `useEffect`가 다시 돈다. `key`로 상태를 초기화하는 원리는 [재조정과 key](/posts/react-reconciliation-keys)와 같다.

template이 다시 마운트되는 조건은 생각보다 좁다. 문서에 적힌 규칙과 실험을 합치면 이렇다.

- 그 template이 있는 세그먼트 바로 아래가 바뀔 때 다시 마운트된다. `dash/template.js`는 `/dash/a`에서 `/dash/b`로 갈 때 바뀐다.
- 더 깊은 세그먼트만 바뀌면 위쪽 template은 그대로다. `/dash/a/1`에서 `/dash/a/2`로 가도 `dash/template.js`는 남는다.
- 검색어(`?q=`)만 바뀌는 이동에서는 다시 마운트되지 않는다.

그래서 "탭을 옮기면 필터 비우기"는 template으로 풀리지만, "검색어가 바뀔 때마다 비우기"는 template으로 풀리지 않는다. 그때는 필터 컴포넌트에 `key={searchParams.toString()}`처럼 직접 `key`를 주거나, 필터 값을 URL에 두고 URL에서 읽는다.

template을 남발하면 손해도 있다. 그 아래 DOM이 매번 새로 만들어지고 클라이언트 컴포넌트 상태가 모두 날아간다. 페이지 진입 애니메이션, 페이지별 로그 이벤트, 입력 초기화처럼 "매번 새로"가 목적일 때만 쓴다. 문서에도 적혀 있듯 레이아웃 안의 Suspense 경계는 첫 로딩에만 fallback을 보여 주는데, template 안에 두면 이동할 때마다 fallback을 보여 준다.

## 링크를 누르면 일어나는 일

`next/link`의 `Link`는 평범한 `<a>`를 그리지만 클릭을 가로챈다. 브라우저가 새 HTML 문서를 받는 대신 Next 라우터가 필요한 세그먼트의 RSC payload만 받아 현재 트리에 끼워 넣는다. 이걸 소프트 내비게이션이라고 부른다. 주소창에 직접 치거나 새로고침하는 건 하드 내비게이션이다. 아래 그림에서 단계를 넘겨 보자.

받아 둔 payload를 얼마나 다시 쓰는지는 클라이언트 캐시 이야기다. 뒤로 가기에서는 다시 쓰고, 동적 페이지를 링크로 다시 들어가면 기본으로 다시 받는다. 이 동작과 바꾸는 법은 [Next.js 캐시 네 겹](/posts/nextjs-caching-layers)에서 실험으로 확인한다.

## 이동이 느리거나 상태가 이상할 때 보는 곳

증상별로 먼저 볼 곳이 다르다.

링크를 눌렀는데 한참 아무 반응이 없다가 화면이 바뀐다. 대개 동적 라우트에 `loading.js`가 없는 경우다. 미리 받기가 로딩 화면까지밖에 못 받는데 로딩 화면이 없으니, 라우터는 서버 응답이 올 때까지 기다린다. 해당 세그먼트에 `loading.js`를 두면 클릭 즉시 로딩 화면으로 바뀐다. 사용자가 누른 걸 알 수 있게 링크 자체에 표시를 하고 싶으면 `useLinkStatus()`가 `pending`을 알려 준다.

링크마다 페이지 전체가 새로고침된다. 서로 다른 루트 레이아웃 사이를 오가는지 본다. `pages` 디렉터리 라우트와 `app` 라우트 사이를 오가는 것도 하드 내비게이션이다. 일반 `<a href>`로 링크를 걸었는지도 본다. 마크다운 렌더러가 만든 링크가 흔히 그렇다.

페이지를 옮겨도 이전 페이지의 입력값이나 스크롤 위치, 열린 메뉴가 남는다. 그 상태를 가진 컴포넌트가 layout 쪽에 있는지 본다. 모바일 메뉴가 열린 채로 다음 페이지에 가는 버그가 대표적이다. `usePathname()`이 바뀔 때 메뉴를 닫거나, 그 부분만 template로 옮긴다.

에러 화면이 엉뚱한 곳에서 뜬다. 에러를 던진 파일이 layout인지 page인지 본다. layout이면 같은 폴더의 `error.js`가 아니라 부모의 `error.js`가 뜬다.

확인은 브라우저 개발자 도구 네트워크 탭에서 `_rsc`로 거르면 된다. 클릭했을 때 문서(`Doc`) 요청이 나가면 하드 내비게이션이고, `_rsc` 요청만 나가면 소프트 내비게이션이다.

## Pages Router에서 넘어올 때

같은 Next.js 안에 라우터가 둘 있다. `pages` 디렉터리를 쓰는 Pages Router와 `app` 디렉터리를 쓰는 App Router다. 둘은 한 프로젝트에 같이 둘 수 있고, 같은 주소를 두 곳에 만들면 충돌한다.

가장 큰 차이는 데이터를 가져오는 자리다. Pages Router는 페이지 파일 밖의 특수 함수에서 가져와 props로 넘긴다.

```tsx
// pages/products/[id].tsx — Pages Router
export async function getServerSideProps({ params }) {
  const product = await db.product.find(params.id); // 요청마다 서버에서
  return { props: { product } };
}
export default function Product({ product }) {
  return <h1>{product.name}</h1>;
}
```

App Router는 서버 컴포넌트가 직접 `await`한다. 페이지만이 아니라 레이아웃이나 깊은 자식 컴포넌트도 자기 데이터를 가져온다.

```tsx
// app/products/[id]/page.tsx — App Router
export default async function Product({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const product = await db.product.find(id);
  return <h1>{product.name}</h1>;
}
```

나머지 대응은 이렇다. `getStaticProps`는 캐시되는 fetch나 `"use cache"`로, `getStaticPaths`는 `generateStaticParams`로, `_app`과 `_document`는 루트 `layout.js` 하나로, `next/router`의 `useRouter`는 `next/navigation`의 `useRouter`·`usePathname`·`useSearchParams`로 바뀐다. `pages/api/*`는 Route Handler(`route.js`)가 된다.

옮길지 말지는 얻는 것과 치르는 것을 같이 본다. 얻는 것은 중첩 레이아웃, 스트리밍, 서버 컴포넌트로 줄어드는 클라이언트 JS, 세그먼트 단위 로딩과 에러 처리다. 치르는 것은 서버·클라이언트 경계를 새로 배워야 한다는 점, 캐시 동작이 달라서 생기는 "값이 안 바뀐다" 류의 버그, 그리고 브라우저 전역 객체에 기대는 라이브러리들의 호환성이다.

한 번에 다 옮길 필요는 없다. 새 페이지를 `app`에 만들고 기존 페이지는 `pages`에 두는 식으로 섞어 쓸 수 있다. 다만 두 라우터 사이의 이동은 하드 내비게이션이고 `Link`가 서로를 미리 받지 않는다. 사용자가 자주 오가는 화면 묶음(예: 상품 목록과 상세)은 같은 라우터로 함께 옮겨야 체감 속도가 떨어지지 않는다.

## 다시 대시보드 필터로

처음 질문의 답은 트리 구조에 있다. layout은 그 아래 세그먼트가 바뀌어도 같은 자리에 그대로 있어서 상태가 남는다. template은 세그먼트마다 다른 `key`를 받아 새로 만들어진다. 링크 이동은 바뀐 세그먼트만 서버에서 받아 바꾸기 때문에 이 차이가 드러난다. 폴더는 주소의 조각이고, 특수 파일은 그 조각 안에서 레이아웃, 템플릿, 에러 경계, Suspense 경계, 페이지 순으로 겹친다. 이 순서를 머릿속에 두면 상태가 남는 이유, 에러 화면이 뜨는 위치, 로딩 화면이 보이는 시점을 모두 같은 그림으로 설명할 수 있다. 같은 레이아웃 안에 여러 페이지를 동시에 띄우는 방법은 [병렬 라우트와 가로채는 라우트](/posts/nextjs-parallel-intercepting-routes)에서 이어 본다.

## 면접에서 나올 만한 질문

### App Router에서 폴더와 파일은 주소와 어떻게 대응하나요?

`app` 아래 폴더 하나가 URL 세그먼트 하나다. 폴더에 `page.js`나 `route.js`가 있어야 그 주소가 공개된다. 그래서 라우트 폴더 안에 컴포넌트나 테스트 파일을 같이 둬도 주소가 생기지 않는다. 괄호 폴더는 주소에서 빠지는 라우트 그룹이고, 밑줄 폴더는 라우트에서 제외되는 private 폴더다.

### [slug], [...slug], [[...slug]]는 어떻게 다른가요?

`[slug]`는 세그먼트 하나를 문자열로, `[...slug]`는 하나 이상을 배열로 받고 0개면 404다. `[[...slug]]`는 0개도 받아서 `/shop`과 `/shop/men/shoes`를 한 페이지로 처리할 수 있다. 같은 위치에 고정 폴더가 있으면 고정 폴더가 우선한다. Next 15부터 `params`는 Promise라 `await`해서 읽는다.

### layout과 template의 차이는 무엇인가요?

layout은 아래 세그먼트가 바뀌어도 다시 마운트되지 않아 상태와 DOM이 유지된다. template은 세그먼트마다 고유한 key로 렌더링되어 이동할 때마다 새로 마운트되고, 상태가 초기화되고 effect가 다시 돈다. 다만 template은 자기 바로 아래 세그먼트가 바뀔 때만 다시 마운트되고, 검색어만 바뀔 때는 그대로다. 매번 초기화가 목적일 때만 template을 쓴다.

### error.js가 같은 폴더의 layout에서 난 에러를 못 잡는 이유는요?

파일이 감싸는 순서가 layout, template, error, loading, page라서 error 경계가 layout 안쪽에 있기 때문이다. 같은 세그먼트 layout의 에러는 부모 세그먼트의 `error.js`로 올라간다. 루트 layout의 에러는 `global-error.js`가 처리하며, 이 파일은 루트 레이아웃을 대신하므로 html과 body를 직접 그린다.

### 소프트 내비게이션과 하드 내비게이션은 무엇이 다른가요?

소프트 내비게이션은 `Link`나 `router.push`로 이동할 때 새 HTML 문서를 받지 않고, 바뀌는 세그먼트의 RSC payload만 받아 현재 트리에 끼워 넣는 방식이다. 공통 레이아웃과 그 상태가 유지된다. 하드 내비게이션은 새로고침이나 주소창 입력처럼 문서 전체를 새로 받는 것이고, 다른 루트 레이아웃이나 Pages Router 라우트로 가는 이동도 여기에 속한다.

### Link의 prefetch는 언제 무엇을 받나요?

프로덕션에서 링크가 화면에 들어오면 받는다. 기본값에서 정적 라우트는 전체를, 동적 라우트는 가장 가까운 `loading.js`까지만 받는다. 그래서 동적 라우트에 `loading.js`가 없으면 클릭 뒤 서버 응답까지 화면이 멈춘 것처럼 보인다. 개발 서버에서는 미리 받지 않으니 이동 속도는 프로덕션 빌드로 확인한다.

### Pages Router에서 App Router로 옮길 때 무엇을 고려하나요?

`getServerSideProps`·`getStaticProps`가 서버 컴포넌트의 직접 `await`와 캐시 설정으로, `_app`·`_document`가 루트 layout으로, `next/router`가 `next/navigation`으로 바뀐다. 두 디렉터리를 섞어 단계적으로 옮길 수 있지만 두 라우터 사이 이동은 하드 내비게이션이라, 자주 오가는 화면은 같이 옮긴다. 캐시 기본값과 서버·클라이언트 경계가 달라서 생기는 버그를 테스트로 먼저 잡아 둔다.
