<EasyIntro>
  TypeScript 클래스에는 private, protected, readonly 같은 표시를 붙일 수 있다. 이 표시는 "이 값은 밖에서 만지지 마"라는 규칙이다. 그런데 이 규칙을 지키는 건 코드를 검사하는 컴파일러이고, 프로그램이 실제로 돌 때는 대부분 사라진다.

결제 모듈의 `PaymentClient` 클래스에 API 키를 `private apiKey`로 넣었다. 밖에서 `client.apiKey`라고 쓰면 빨간 줄이 그어지니 안전하다고 생각했다. 그런데 에러 수집 도구에 올라온 로그를 열어 보니 `{"apiKey":"sk_live_...","baseUrl":"..."}`가 그대로 찍혀 있다. 에러가 났을 때 클라이언트 객체를 통째로 로그에 남긴 코드 한 줄 때문이다.

TypeScript의 접근 제한자는 대부분 컴파일할 때만 있는 규칙이다. 이 글은 그 규칙이 정확히 무엇을 막고 무엇을 못 막는지에서 시작해, 생성자 매개변수 속성, `readonly`, `abstract`, `override`, 생성자 오버로드를 TypeScript 5.9 컴파일러로 직접 돌려 보며 따라간다. 마지막에는 클래스 상속을 쓸 자리와 합성을 쓸 자리를 가른다. 자바스크립트 클래스 자체가 프로토타입 위에서 어떻게 돌아가는지는 [클래스와 상속](/posts/js-classes)에 있으니, 여기서는 TypeScript가 그 위에 얹은 것만 본다.

## private는 컴파일러에게 하는 약속이다

먼저 위 상황을 그대로 만들어 컴파일하고 실행했다.

```ts
class Account {
  private balance = 0;
  #pin: string;
  constructor(pin: string) { this.#pin = pin; }
  deposit(n: number) { this.balance += n; }
}
const acc = new Account("1234");
acc.deposit(100);
// acc.balance;                         // 여기는 컴파일 에러
console.log((acc as any).balance);      // 100
console.log(acc["balance"]);            // 괄호 표기는 통과
console.log(JSON.stringify(acc));
console.log(Object.keys(acc));
```

```text
100
100
{"balance":100}
[ 'balance' ]
```

`(acc as any)`로 타입을 지우면 그냥 읽힌다. 눈여겨볼 것은 두 번째 줄이다. `acc["balance"]`처럼 문자열 리터럴로 괄호 접근을 하면 TypeScript는 에러를 내지 않는다. 테스트 코드에서 내부 값을 확인할 때 쓰라고 일부러 열어 둔 탈출구다. 그리고 `JSON.stringify`와 `Object.keys`에는 평범한 속성으로 나온다. 컴파일 결과를 보면 이유가 분명하다.

```js
class Account {
    balance = 0;
    #pin;
    constructor(pin) { this.#pin = pin; }
    deposit(n) { this.balance += n; }
}
```

`private` 단어만 지워졌다. 반면 `#pin`은 그대로 남았다. `#`은 자바스크립트 엔진이 지키는 진짜 비공개 필드라서 직렬화에도 키 목록에도 나오지 않는다. 그래서 로그나 응답으로 새어 나가면 안 되는 값은 `#`으로 둔다. 처음 장면의 API 키가 여기에 해당한다.

`#`을 쓰면 컴파일 대상이 오래된 경우의 비용도 알아 둔다. `target`을 ES2017로 낮춰 같은 코드를 컴파일하면 `#` 필드가 `WeakMap`과 도우미 함수로 바뀐다.

```js
var _Token_raw;
class Token {
    constructor(raw) {
        _Token_raw.set(this, void 0);
        __classPrivateFieldSet(this, _Token_raw, raw, "f");
    }
    get masked() { return __classPrivateFieldGet(this, _Token_raw, "f").slice(0, 4) + "****"; }
}
_Token_raw = new WeakMap();
```

동작은 같지만 읽을 때마다 함수 호출을 한 번 더 거치고 디버거에서 값이 잘 안 보인다. 지금 브라우저와 Node는 모두 `#`을 직접 지원하니 `target`을 ES2022 이상으로 두면 이 변환은 생기지 않는다.

정리하면 기준은 하나다. 같은 코드베이스 안에서 실수로 건드리는 것을 막고 싶으면 `private`, 실행 중에도 정말 숨겨야 하면 `#`이다. `#`은 `Proxy`로 감싼 객체에서 메서드가 깨지는 부작용이 있는데, 이 부분은 [클래스와 상속](/posts/js-classes)의 "정말로 숨기는 #private"에서 실제 에러로 보여 준다.

## private는 인스턴스가 아니라 클래스의 것이다

`private`이 "이 객체만 볼 수 있다"는 뜻이라고 생각하기 쉽다. 아니다. 같은 클래스 안의 코드라면 다른 인스턴스의 `private`도 읽을 수 있다.

```ts
class Money {
  private amount: number;
  constructor(amount: number) { this.amount = amount; }
  equals(other: Money) {
    return this.amount === other.amount;   // 다른 인스턴스의 private, 에러 없음
  }
}
```

`equals`, `compareTo`, 복사 생성자처럼 같은 종류의 객체끼리 내부를 비교하는 메서드를 쉽게 짜라고 이렇게 정했다. 자바와 C#도 같다.

`private` 멤버가 있으면 구조적 타입 검사의 규칙도 바뀐다. 모양이 똑같은 두 클래스라도 `private` 멤버가 서로 다른 선언에서 왔으면 호환되지 않는다.

```ts
class Won { private amount = 0; get value() { return this.amount; } }
class Usd { private amount = 0; get value() { return this.amount; } }
const w: Won = new Usd();
```

```text
d.ts(3,7): error TS2322: Type 'Usd' is not assignable to type 'Won'.
  Types have separate declarations of a private property 'amount'.
```

`private`을 지우고 공개 필드로 바꾸면 같은 코드가 통과한다. 원화와 달러를 섞지 못하게 하는 효과를 공짜로 얻는 셈이다. 이 성질을 이용한 브랜드 타입은 [TypeScript 타입 시스템 기초](/posts/ts-type-system-basics)의 "문자열 두 개를 구분하는 브랜드 타입"에서 이어진다.

## protected는 내 쪽 계보에서만

`protected`는 하위 클래스에 열어 준다. 그런데 하위 클래스 안이라고 아무 인스턴스의 `protected`나 읽을 수 있는 건 아니다.

```ts
class P { protected secret = 1; }
class Q extends P {
  peek(other: P, q: Q) {
    return [q.secret, other.secret];
  }
}
```

```text
c.ts(24,50): error TS2446: Property 'secret' is protected and only accessible through an instance of class 'Q'. This is an instance of class 'P'.
```

`q.secret`은 되고 `other.secret`은 안 된다. `P`를 상속한 다른 클래스 `R`의 인스턴스가 `other`로 들어올 수 있기 때문이다. `Q`가 `R`의 내부를 들여다볼 권리는 없다. 같은 부모를 둔 형제 클래스끼리는 `protected`를 공유하지 않는다는 규칙이다.

`protected`를 많이 쓸수록 상위 클래스의 내부 구현이 하위 클래스에 새어 나간다. 하위 클래스가 `protected` 필드를 직접 고치기 시작하면 상위 클래스는 그 필드의 의미를 바꿀 수 없게 된다. 열어 줄 게 있다면 필드보다 메서드로 연다. 이 문제는 글 끝의 합성 이야기와 이어진다.

## 생성자 매개변수 속성

`constructor` 매개변수 앞에 접근 제한자나 `readonly`를 붙이면 필드 선언과 대입이 한 번에 된다.

```ts
class User {
  constructor(
    public readonly id: string,
    private name: string,
    protected role = "member",
  ) {}
  greet() { return `hi ${this.name}`; }
}
```

컴파일하면 필드 선언과 대입 코드가 생긴다.

```js
class User {
    id;
    name;
    role;
    constructor(id, name, role = "member") {
        this.id = id;
        this.name = name;
        this.role = role;
    }
    greet() { return `hi ${this.name}`; }
}
```

같은 내용을 손으로 쓰면 세 번씩 반복해야 하니 짧고 편하다. 의존성 주입을 쓰는 Angular나 NestJS 코드에서 `constructor(private readonly repo: UserRepository) {}` 모양이 흔한 이유다. 그런데 이 문법에는 요즘 문제가 둘 생겼다.

첫째는 타입만 지우는 도구다. 매개변수 속성은 타입을 지우는 것만으로는 안 되고 대입 코드를 새로 만들어야 한다. Node.js 22의 타입 제거 실행에 그대로 넣었다.

```bash
# Node 22.22에서 .ts 파일을 바로 실행
node b2.ts
```

```text
SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript parameter property is not supported in strip-only mode
```

TypeScript 5.8의 `erasableSyntaxOnly`를 켜면 같은 자리가 컴파일 에러(TS1294)가 된다. `enum`, `namespace`도 같은 부류다. 이 흐름은 [TypeScript enum과 유니온](/posts/ts-enum-vs-union)에서 자세히 다뤘다. 타입 제거 실행이나 그런 번들러를 쓸 계획이면 매개변수 속성 대신 필드를 직접 선언한다.

둘째는 필드 초기화 순서다. 이건 실제 버그로 이어진다.

## 필드가 매개변수 속성보다 먼저 돈다

매개변수 속성 값을 다른 필드의 초기값에서 쓰는 코드는 흔하다.

```ts
class Base {
  kind = (console.log("1 Base 필드"), "base");
  constructor() { console.log("2 Base 생성자 본문"); }
}
class Child extends Base {
  label = (console.log("4 Child 필드, id =", this.id), `item-${this.id}`);
  constructor(public id: number) {
    super();
    console.log("5 Child 생성자 본문");
  }
}
console.log(JSON.stringify(new Child(7)));
```

`useDefineForClassFields`를 켜고 끄며 두 번 컴파일해 실행했다. 이 옵션은 `target`이 ES2022 이상이면 기본으로 켜진다.

```text

1 Base 필드
2 Base 생성자 본문
4 Child 필드, id = undefined
5 Child 생성자 본문
{"kind":"base","id":7,"label":"item-undefined"}
== useDefine=false
1 Base 필드
2 Base 생성자 본문
4 Child 필드, id = 7
```

옵션 하나로 `label`이 `item-7`에서 `item-undefined`로 바뀌었다. 켜진 쪽은 TypeScript가 TS2729로 경고해 주지만, 옛 설정에서 `target`만 ES2022로 올린 프로젝트라면 이 경고가 갑자기 수십 개 쏟아지거나 `skipLibCheck`와 함께 묻힌다. 아래 그림에서 `new Child(7)`이 객체를 채우는 순서를 단계별로 본다.

고치는 방법은 둘이다. `label`을 생성자 본문에서 대입하거나, getter로 바꿔 읽을 때 계산한다. 매개변수 속성에 기대는 필드 초기값은 옵션 하나에 따라 결과가 바뀌는 코드라 피하는 게 좋다.

같은 옵션이 만드는 또 하나의 함정이 있다. 부모가 채워 준 필드를 하위 클래스에서 타입만 좁히려고 다시 적는 경우다.

```ts
class Base { name = "base"; }
class Derived extends Base { declare name: string; }
class Derived2 extends Base { name!: string; }
console.log(new Derived().name, new Derived2().name);
```

```text

useDefine=false  →  base base
```

`name!: string`은 "초기값은 없지만 걱정 마"라는 뜻으로 쓴 것인데, 표준 필드 의미에서는 필드 선언 자체가 `undefined`로 다시 정의하는 동작이다. 타입만 다시 적고 싶을 때는 `declare`를 붙인다. `declare` 필드는 컴파일 결과에 아무것도 남기지 않는다. 부모 setter가 무시되는 경우까지 포함한 필드 정의 의미 전체는 [클래스와 상속](/posts/js-classes)의 "필드 선언은 대입이 아니다"에 있다.

## readonly는 얕고 컴파일 때만이다

```ts
class Cfg {
  readonly tags: string[] = ["a"];
  readonly opts = { retry: 3 };
}
const c = new Cfg();
c.tags.push("b");
c.opts.retry = 5;
c.tags = [];
```

```text
g.ts(5,3): error TS2540: Cannot assign to 'tags' because it is a read-only property.
```

에러는 마지막 줄 하나다. `readonly`는 속성 자리를 다시 대입하는 것만 막고, 그 안의 배열이나 객체를 고치는 건 그대로 둔다. 안쪽까지 막으려면 타입을 `readonly string[]`이나 `Readonly<...>`로 적는다. 그래도 컴파일 시점뿐이다. 실행 중에도 막아야 한다면 `Object.freeze`를 쓰는데, 그것도 한 단계만 얼린다.

## abstract 클래스와 interface 사이

`abstract` 클래스는 직접 만들 수 없고, 하위 클래스가 채워야 할 메서드를 선언해 둘 수 있다.

```ts
abstract class Shape {
  abstract area(): number;
  describe() { return `${this.constructor.name}: ${this.area().toFixed(2)}`; }
}
class Circle extends Shape {
  constructor(private r: number) { super(); }
  area() { return Math.PI * this.r ** 2; }
}
class Square extends Shape {}
new Shape();
```

```text
c.ts(9,7): error TS2515: Non-abstract class 'Square' does not implement inherited abstract member area from class 'Shape'.
c.ts(10,1): error TS2511: Cannot create an instance of an abstract class.
```

비슷한 일을 `interface`와 `implements`로도 할 수 있다. 둘 중 무엇을 고를지는 세 가지 차이로 정한다.

`abstract` 클래스는 실행 중에도 남는다. `instanceof Shape`가 되고, 의존성 주입 컨테이너가 이 클래스를 토큰으로 쓸 수 있다. `interface`는 컴파일 뒤에 흔적이 없어서 `instanceof`도, 값으로 쓰는 것도 안 된다.

`abstract` 클래스는 구현을 물려준다. 위의 `describe()`처럼 공통 흐름을 상위 클래스가 쥐고 단계만 하위 클래스에 맡기는 템플릿 메서드 패턴이 이 자리다. `implements`는 아무것도 물려주지 않는다. "이 모양을 지키겠다"는 검사일 뿐이라 메서드를 전부 직접 써야 한다.

클래스는 하나만 상속할 수 있지만 `interface`는 여러 개를 `implements`할 수 있다. 캐시도 되고 직렬화도 되는 객체처럼 역할이 여러 개면 `interface`가 맞다.

그래서 공유할 구현이 있고 계층이 단순하면 `abstract`, 계약만 정하고 구현은 제각각이면 `interface`가 기본이다. 실무에서는 둘을 함께 쓰는 일이 많다. 외부에는 `interface`로 계약을 공개하고, 내부에 그걸 `implements`하는 `abstract` 기반 클래스를 둬서 공통 구현을 나눈다. 이렇게 하면 테스트에서는 `interface`만 맞춘 가짜 객체를 넣을 수 있다.

`abstract` 메서드와 생성자가 만나면 조심할 점도 하나 있다. 상위 생성자에서 `abstract` 메서드를 부르면 하위 클래스의 필드가 아직 초기화되지 않은 상태로 그 메서드가 돈다. 앞 절의 초기화 순서와 같은 문제다. 이 함정과 템플릿 메서드 전체는 [템플릿 메서드 패턴](/posts/pattern-template-method)의 "생성자에서 단계를 부르면 생기는 일"에 있다.

## override와 noImplicitOverride

상위 클래스의 `save()`를 하위 클래스가 덮어쓰고 있었다. 어느 날 누군가 상위 클래스의 `save()`를 `persist()`로 이름을 바꿨다. 하위 클래스의 `save()`는 에러 없이 그냥 새 메서드가 되고, 덮어쓰던 동작은 조용히 사라진다. `override` 키워드와 `noImplicitOverride` 옵션은 이걸 막으려고 TypeScript 4.3에 들어왔다.

```ts
class Base { save() {} protected log(msg: string) {} }
class Child extends Base {
  save() {}           // override 없이 덮어씀
  override sav() {}   // 오타
}
```

```bash
# noImplicitOverride를 켜고 검사
npx tsc --noEmit --strict --noImplicitOverride c.ts
```

```text
c.ts(14,3): error TS4114: This member must have an 'override' modifier because it overrides a member in the base class 'Base'.
c.ts(15,12): error TS4117: This member cannot have an 'override' modifier because it is not declared in the base class 'Base'. Did you mean 'save'?
```

두 방향을 다 잡는다. 덮어쓰면서 `override`를 안 쓰면 에러, `override`를 썼는데 상위에 그런 멤버가 없으면 에러다. 상위 메서드 이름이 바뀌면 하위의 `override save()`가 바로 TS4117로 빨갛게 변한다. `noImplicitOverride`는 `strict`에 포함되지 않으니 따로 켠다. 클래스 상속을 쓰는 코드베이스라면 켜 두는 비용이 거의 없다. 어떤 검사 옵션이 `strict`에 묶여 있는지는 [tsconfig와 strict 옵션](/posts/tsconfig-strict)에 정리했다.

`override`가 시그니처까지 엄격하게 맞춰 주지는 않는다. 덮어쓰는 메서드의 매개변수를 상위보다 좁히고, 반환 타입을 바꿔 봤다.

```ts
class Animal { feed(food: string | number): void {} }
class Dog extends Animal { override feed(food: string): void {} }      // 매개변수를 좁혔다
class Base2 { get(): string { return ""; } }
class D2 extends Base2 { override get(): number { return 1; } }        // 반환 타입을 바꿨다
```

```text
j.ts(10,35): error TS2416: Property 'get' in type 'D2' is not assignable to the same property in base type 'Base2'.
  Type '() => number' is not assignable to type '() => string'.
```

반환 타입은 잡았지만 매개변수를 좁힌 `Dog`는 통과했다. `strictFunctionTypes`를 켜도 메서드 문법으로 선언한 매개변수는 양방향(bivariant)으로 비교하기 때문이다. `Animal` 자리에 `Dog`를 넣고 `feed(1)`을 부르면 `Dog`는 숫자를 받을 준비가 안 된 채로 실행된다. 다형성이 기대하는 것은 "상위 타입 자리에 하위 인스턴스를 넣어도 깨지지 않는다"는 약속이고, 컴파일러는 그중 타입으로 표현되는 부분만 검사한다. 상위 메서드가 "음수를 넣으면 예외"라고 약속했는데 하위가 조용히 0을 돌려주는 식의 의미 변화는 여전히 사람이 막아야 한다.

## 생성자 오버로드보다 이름 있는 생성 함수

생성자 하나로 여러 모양의 인자를 받고 싶을 때 오버로드 시그니처를 쓴다.

```ts
class Span {
  start: number; end: number;
  constructor(end: number);
  constructor(start: number, end: number);
  constructor(a: number, b?: number) {
    if (b === undefined) { this.start = 0; this.end = a; }
    else { this.start = a; this.end = b; }
  }
}
new Span(5); new Span(2, 5); new Span();
new Span(1, 2, 3);
```

```text
h.ts(9,30): error TS2554: Expected 1-2 arguments, but got 0.
h.ts(10,16): error TS2554: Expected 1-2 arguments, but got 3.
```

밖에서는 위의 두 시그니처만 보이고 마지막 구현 시그니처(`a, b?`)는 보이지 않는다. 구현은 하나뿐이라 본문에서 인자 모양을 직접 가려야 한다. 오버로드가 셋, 넷으로 늘면 본문의 분기가 복잡해지고, `new Span(2, 5)`만 보고는 2가 시작인지 길이인지 알기 어렵다.

이럴 때는 이름 있는 정적 생성 함수가 낫다.

```ts
class Span {
  private constructor(readonly start: number, readonly end: number) {}
  static upTo(end: number) { return new Span(0, end); }
  static between(start: number, end: number) {
    if (start > end) throw new RangeError("start > end");
    return new Span(start, end);
  }
}
Span.between(2, 5);
// new Span(2, 5);  // private constructor라 밖에서 못 만든다
```

생성자를 `private`으로 막고 의도가 드러나는 이름으로만 만들게 했다. 검증도 각 생성 함수에 둘 수 있다. 오버로드는 `Date`처럼 이미 굳은 API를 타입으로 옮길 때나, 인자 모양이 둘 정도로 분명할 때 쓴다.

## 상속보다 합성을 고르는 순간

상속은 "B는 A의 한 종류다"를 코드로 적는 일이다. 문제는 하위 클래스가 상위 클래스의 공개 API뿐 아니라 구현 세부(어떤 메서드가 어떤 메서드를 부르는지, `protected` 필드의 의미)에도 기대게 된다는 점이다. 상위 클래스를 고치면 알지 못하는 하위 클래스가 깨진다. 흔히 깨지기 쉬운 상위 클래스 문제라고 부른다.

합성은 "B는 A를 가지고 있다"로 적는다. 바뀌는 부분을 객체로 받아 끼운다.

```ts
interface Formatter {
  separator: string;
  escape(cell: string): string;
}

const csv: Formatter = {
  separator: ",",
  escape: (c) => (/[",\n]/.test(c) ? '"' + c.replace(/"/g, '""') + '"' : c),
};

class TableExporter {
  constructor(
    private readonly formatter: Formatter,
    private readonly options: { header?: boolean; bom?: boolean } = {},
  ) {}
  export(columns: string[], rows: Record<string, unknown>[]) {
    const line = (cells: string[]) => cells.map(this.formatter.escape).join(this.formatter.separator);
    const lines = rows.map((r) => line(columns.map((c) => String(r[c] ?? ""))));
    if (this.options.header !== false) lines.unshift(line(columns));
    return (this.options.bom ? "﻿" : "") + lines.join("\n");
  }
}

new TableExporter(csv, { bom: true }); // 엑셀용 CSV. 새 클래스가 필요 없다
```

형식과 옵션이 따로 늘어나도 조합마다 클래스를 만들 필요가 없다. 테스트에서는 `Formatter`만 가짜로 바꿔 끼우면 된다. 이 모양이 전략 패턴이다. 자세한 비교는 [전략 패턴](/posts/pattern-strategy)과 [디자인 패턴 개요](/posts/design-patterns-overview)에 있다.

그렇다고 상속이 늘 틀린 건 아니다. 다음 경우에는 상속이 자연스럽다. 계층이 얕고(한두 단계) 상위 클래스가 거의 바뀌지 않을 때, 프레임워크가 상속을 요구할 때(`Error`를 상속한 도메인 에러, React의 에러 경계 클래스, Node의 `Transform` 스트림), 공통 흐름이 정말로 하나이고 하위 클래스는 단계만 채우는 템플릿 메서드일 때. 반대로 상속 단계가 셋을 넘거나, 하위 클래스가 상위의 메서드를 덮어쓴 뒤 `super`를 부를지 말지 고민하거나, 기능 조합마다 클래스가 생기기 시작하면 합성으로 옮길 신호다. React가 컴포넌트 재사용을 상속이 아니라 `props`와 `children`, 훅으로 하는 것도 같은 판단이다.

```ts
// 도메인 에러는 상속이 맞는 자리다
class PaymentDeclinedError extends Error {
  override readonly name = "PaymentDeclinedError";
  constructor(readonly code: string, options?: ErrorOptions) {
    super(`결제 거절: ${code}`, options);
  }
}
```

`override readonly name`은 상위 `Error`의 `name`을 덮어쓴다는 표시다. `noImplicitOverride`를 켠 채로 `override`를 빼 봤더니 메서드가 아닌 속성에도 TS4114가 났다. `name`을 정해 두면 로그와 에러 수집 도구에서 `Error` 대신 이 이름으로 묶인다.

## 다시 로그에 찍힌 API 키로

처음 장면의 API 키는 `private`이라서 샌 게 아니라, `private`이 실행 중에는 평범한 속성이라서 샜다. 실행 중에도 숨겨야 하면 `#`을 쓰고, 같은 코드베이스 안의 실수를 막는 데는 `private`으로 충분하다. 매개변수 속성은 짧지만 타입 제거 도구에서 안 돌고, `useDefineForClassFields`가 켜지면 필드 초기값이 그 값을 `undefined`로 본다. `readonly`는 얕고, `abstract`는 실행 중에도 남는 계약이며, `override`와 `noImplicitOverride`는 상위 클래스가 바뀌는 순간을 잡아 준다. 그리고 하위 클래스가 조합마다 늘기 시작하면 상속을 멈추고 바뀌는 부분을 객체로 받아 끼운다.

## 면접에서 나올 만한 질문

### TypeScript의 private과 자바스크립트의 #private은 무엇이 다른가

`private`은 컴파일 때만 검사하고 결과 코드에서는 지워져서, 실행 중에는 `JSON.stringify`, `Object.keys`, `(obj as any).x`로 그대로 보인다. `obj["x"]` 괄호 접근은 컴파일러도 일부러 허용한다. `#private`은 엔진이 지키는 진짜 비공개 필드라 직렬화와 키 목록에 나오지 않고 밖에서 접근할 방법이 없다. 로그나 응답으로 새면 안 되는 값은 `#`을 쓴다.

### private 멤버는 다른 인스턴스에서 읽을 수 있나

같은 클래스 안의 코드라면 읽을 수 있다. `private`은 인스턴스 단위가 아니라 클래스 단위 규칙이라 `equals(other)`에서 `other.amount`를 읽는 게 허용된다. 또 `private` 멤버가 있는 클래스는 모양이 같아도 다른 선언에서 온 클래스와 호환되지 않아서, 명목적 타입처럼 동작한다.

### protected 멤버를 하위 클래스에서 다른 인스턴스로 읽으면 왜 에러가 나나

하위 클래스 `Q`는 자기 계열(`Q`나 그 하위) 인스턴스를 통해서만 `protected`에 접근할 수 있다. 상위 타입 `P`로 받은 값은 형제 클래스의 인스턴스일 수 있는데, `Q`가 형제의 내부를 볼 권리는 없기 때문이다. 그래서 TS2446 에러가 난다.

### 생성자 매개변수 속성을 쓸 때 주의할 점은

필드 초기값에서 매개변수 속성을 읽으면 `useDefineForClassFields`가 켜진 경우(target ES2022 이상의 기본값) `undefined`를 본다. 표준 필드 정의가 `super()` 직후에 돌고 매개변수 속성 대입은 그 뒤에 돌기 때문이다. TypeScript가 TS2729로 알려 주니 생성자 본문이나 getter로 옮긴다. 또 매개변수 속성은 타입만 지우는 실행 환경(Node의 타입 제거)에서 돌지 않고 `erasableSyntaxOnly`에서 에러가 된다.

### abstract 클래스와 interface는 언제 각각 쓰나

공유할 구현이 있고 계층이 단순하면 `abstract` 클래스, 계약만 정하고 구현은 제각각이면 `interface`다. `abstract` 클래스는 실행 중에도 남아 `instanceof`와 의존성 주입 토큰으로 쓸 수 있고 구현을 물려주지만 하나만 상속할 수 있다. `interface`는 흔적 없이 사라지고 여러 개를 구현할 수 있다. 외부에는 `interface`로 계약을 공개하고 내부에 `abstract` 기반 클래스를 두는 조합도 흔하다.

### override 키워드와 noImplicitOverride는 무엇을 막나

상위 클래스 메서드 이름이 바뀌거나 하위 클래스에서 오타가 나서, 덮어쓰던 메서드가 조용히 새 메서드가 되는 사고를 막는다. 옵션을 켜면 덮어쓰면서 `override`를 빼면 TS4114, 상위에 없는데 `override`를 붙이면 TS4117이 난다. `strict`에 포함되지 않아 따로 켜야 한다.

### readonly 배열 속성에 push를 하면 막히나

막히지 않는다. 속성의 `readonly`는 그 자리를 다시 대입하는 것만 막고 안의 배열이나 객체 변경은 허용한다. 안쪽까지 막으려면 타입을 `readonly string[]`이나 `Readonly`로 적어야 하고, 그것도 컴파일 시점 검사다. 실행 중에 막으려면 `Object.freeze`를 쓰는데 한 단계만 얼린다.

### 상속 대신 합성을 고르는 기준은

상속 단계가 깊어지거나, 기능 조합마다 하위 클래스가 생기거나, 하위 클래스가 상위의 구현 세부와 `protected` 필드에 기대기 시작하면 합성으로 옮긴다. 바뀌는 부분을 인터페이스로 정의해 객체로 받아 끼우면 조합이 늘어도 클래스가 늘지 않고, 테스트에서 그 부분만 바꿔 끼울 수 있다. 계층이 얕고 상위가 안정적이거나 `Error`처럼 프레임워크가 상속을 요구할 때는 상속이 자연스럽다.
