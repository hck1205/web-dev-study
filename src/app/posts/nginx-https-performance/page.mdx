[앞 글](/posts/nginx-reverse-proxy)에서 nginx 뒤에 Node 앱을 붙였다. 이제 도메인도 연결했으니 HTTPS를 붙여야 한다. 그런데 막상 시작하면 할 일이 줄줄이 따라온다. 인증서는 어디서 받고 90일마다 어떻게 갱신하나, HTTP/2는 켜야 하나, 브라우저 개발자 도구를 보니 JS 파일이 압축 없이 300KB씩 내려가고, 앱의 상품 목록 API는 1초에 수백 번 같은 결과를 계산하고 있다. 로그를 보면 로그인 API를 1초에 수십 번 두드리는 IP도 있다.

이 글은 그 목록을 위에서부터 처리한다. certbot으로 인증서를 받고, HTTP를 HTTPS로 돌리고, TLS와 HTTP/2를 설정하고, 압축과 정적 파일 캐시 헤더를 붙이고, 업스트림 응답을 nginx에 캐시하고, 요청 수를 제한하고, 보안 헤더를 붙인다. 마지막엔 curl과 openssl로 결과를 확인한다. TLS가 어떻게 동작하는지는 [HTTPS와 TLS 글](/posts/https-tls)에서, 캐시 헤더의 의미는 [HTTP 캐시와 CDN 글](/posts/http-caching-cdn)에서 다뤘으니 여기서는 nginx 설정으로 옮기는 데 집중한다.

기준은 [첫 글](/posts/nginx-basics)과 같이 Ubuntu 24.04 LTS와 Ubuntu 저장소의 nginx 1.24다. 버전에 따라 문법이 달라지는 곳(HTTP/2)은 따로 적는다. 도메인 `example.com`의 A 레코드가 이 서버를 가리키고, 방화벽에서 80과 443이 열려 있다고 가정한다.

## 인증서는 certbot에게 맡긴다

Let's Encrypt는 무료로 도메인 인증서를 발급하는 인증 기관이고, certbot은 그 발급과 갱신을 자동으로 하는 클라이언트다. certbot 공식 문서는 Ubuntu에서 snap으로 설치하는 방법을 권한다. apt의 `certbot` 패키지는 배포판 버전에 묶여 갱신이 늦기 때문이다. apt로 이미 깔았다면 먼저 지운다.

```bash
# 시작 전 상태: 80, 443을 누가 듣는지
sudo ss -ltnp | grep -E ':80|:443'

# apt로 설치된 certbot이 있으면 제거 (snap 버전과 섞이지 않게)
sudo apt remove -y certbot

# snap으로 certbot 설치
sudo snap install --classic certbot

# certbot 명령을 PATH에서 찾을 수 있게 링크
sudo ln -s /snap/bin/certbot /usr/bin/certbot

# 설정 파일 백업 (certbot이 사이트 설정을 고치기 때문)
sudo tar czf ~/nginx-backup-$(date +%F-%H%M).tgz -C /etc nginx
```

nginx 플러그인을 쓰면 certbot이 인증서를 받은 뒤 nginx 설정까지 고쳐 준다. 그 전에 `server_name example.com www.example.com;`인 server 블록이 `sites-enabled`에 있어야 한다. certbot은 이 이름으로 고칠 블록을 찾는다.

```bash
# 인증서 발급 + nginx 설정 수정 (도메인 여러 개는 -d를 반복)
sudo certbot --nginx -d example.com -d www.example.com
```

처음 실행하면 이메일 주소와 약관 동의를 묻는다. 끝나면 이렇게 나온다.


### certbot이 고친 설정

certbot이 사이트 파일에 넣은 줄에는 `# managed by Certbot` 주석이 붙는다.

```nginx
# /etc/nginx/sites-available/app (certbot 실행 후)
server {
    server_name example.com www.example.com;
    root /var/www/app/public;

    location /api/ {
        proxy_pass http://app;
        include snippets/proxy-headers.conf;
    }

    listen [::]:443 ssl ipv6only=on; # managed by Certbot
    listen 443 ssl; # managed by Certbot
    ssl_certificate /etc/letsencrypt/live/example.com/fullchain.pem; # managed by Certbot
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem; # managed by Certbot
    include /etc/letsencrypt/options-ssl-nginx.conf; # managed by Certbot
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem; # managed by Certbot
}

server {
    if ($host = www.example.com) {
        return 301 https://$host$request_uri;
    } # managed by Certbot

    if ($host = example.com) {
        return 301 https://$host$request_uri;
    } # managed by Certbot

    listen 80;
    listen [::]:80;
    server_name example.com www.example.com;
    return 404; # managed by Certbot
}
```

원래 `listen 80`이던 블록이 443으로 바뀌었고, 80을 받는 블록이 새로 생겼다. `ssl_certificate`에는 `cert.pem`이 아니라 중간 인증서까지 이어 붙인 `fullchain.pem`을 쓴다. `cert.pem`만 쓰면 크롬처럼 중간 인증서를 알아서 받아 오는 브라우저에서는 되고, curl이나 안드로이드 앱, 다른 서버의 HTTP 클라이언트에서는 `unable to get local issuer certificate`로 실패한다. 중간 인증서가 왜 필요한지는 TLS 글의 인증서 체인 부분에 있다.

`options-ssl-nginx.conf`에는 certbot이 관리하는 TLS 설정(프로토콜, 암호 스위트, 세션 캐시)이 들어 있다. 이 파일과 같은 지시어를 같은 컨텍스트에 또 쓰면 `nginx -t`가 이렇게 거부한다.

```text
nginx: [emerg] "ssl_session_cache" directive is duplicate in /etc/letsencrypt/options-ssl-nginx.conf:7
```

TLS 설정을 직접 관리하고 싶으면 이 include 줄을 지우고 아래에 나오는 설정을 쓴다. 둘 중 하나만 쓴다.

### 자동 갱신 확인하기

snap 버전 certbot은 systemd 타이머를 등록해 하루 두 번 갱신을 확인한다. 만료가 가까운 인증서만 실제로 갱신하고, 갱신하면 nginx를 reload한다.

```bash
# 갱신 타이머가 등록돼 있는지 확인
systemctl list-timers | grep certbot

# 실제로 발급하지 않고 갱신 과정만 시험 (스테이징 서버 사용)
sudo certbot renew --dry-run

# 가진 인증서와 만료일 목록
sudo certbot certificates
```

```text
Fri 2026-10-16 22:41:00 UTC 9h left  Fri 2026-10-16 07:12:03 UTC 6h ago  snap.certbot.renew.timer  snap.certbot.renew.service
```

```text
Congratulations, all simulated renewals succeeded:
  /etc/letsencrypt/live/example.com/fullchain.pem (success)
```

`--dry-run`이 실패하면 지금 고쳐야 한다. 석 달 뒤 실제 갱신도 같은 이유로 실패한다. 흔한 원인은 80을 막았거나, 80 블록에서 `/.well-known/`까지 다른 곳으로 리다이렉트하거나, 처음 발급 이후 `server_name`을 바꾼 경우다. 갱신 기록은 `/var/log/letsencrypt/letsencrypt.log`에 있다.

## HTTP는 HTTPS로 돌려보낸다

certbot이 만든 80 블록은 `if`가 도메인마다 붙어 읽기 불편하다. 직접 관리한다면 이렇게 줄인다.

```nginx
# HTTP 요청은 모두 같은 주소의 HTTPS로
server {
    listen 80;
    listen [::]:80;
    server_name example.com www.example.com;

    # 갱신용 검증 경로는 리다이렉트하지 않고 그대로 둔다 (webroot 방식일 때)
    location /.well-known/acme-challenge/ {
        root /var/www/letsencrypt;
    }

    location / {
        return 301 https://$host$request_uri;
    }
}
```

`$request_uri`는 쿼리 문자열까지 포함한 원래 요청 경로라서 `/search?q=nginx`도 그대로 옮겨 간다. 301은 브라우저가 기억하는 영구 이동이다. 처음 붙일 땐 302로 시험하고 확인한 뒤 301로 바꾸면, 잘못 설정했을 때 브라우저 캐시에 남는 걸 피할 수 있다. POST 본문까지 유지해야 하는 API 주소라면 308을 쓴다. 301은 오래된 클라이언트가 POST를 GET으로 바꿔 다시 보낼 수 있다.

`www.example.com`과 `example.com` 중 하나로 합치려면 443 쪽에 server 블록을 하나 더 두고 `return 301 https://example.com$request_uri;`를 쓴다. 이때도 그 이름이 인증서에 들어 있어야 한다. 인증서에 없는 이름으로 HTTPS 접속이 오면 리다이렉트를 보내기도 전에 브라우저가 인증서 오류를 띄운다.

## TLS 버전과 암호, HTTP2 켜기

certbot의 기본 설정을 쓰지 않고 직접 관리한다면, Mozilla SSL Configuration Generator의 intermediate 설정을 기준으로 잡는 게 무난하다. TLS 1.2와 1.3만 허용하고, 1.2에서는 전방향 안전성이 있는 ECDHE 계열 AEAD 암호만 쓴다.

```nginx
# /etc/nginx/snippets/tls.conf
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;
ssl_prefer_server_ciphers off;   # 위 목록은 모두 안전하니 클라이언트가 고르게 둔다

# 재접속 때 핸드셰이크를 줄이는 세션 재사용
ssl_session_cache shared:TLS:10m;   # 1MB에 세션 약 4000개
ssl_session_timeout 1d;
ssl_session_tickets off;
```

`ssl_ciphers`는 TLS 1.2에만 적용된다. TLS 1.3의 암호 스위트는 다섯 개뿐이고 모두 안전해서 따로 정하지 않는다. TLS 1.0·1.1은 주요 브라우저가 2020년에 지원을 끊었으니 열어 둘 이유가 없다. 아주 오래된 안드로이드(4.x)나 윈도 7의 IE를 지원해야 하는 서비스가 아니라면 이 설정에서 막히는 사용자는 거의 없다.

Ubuntu의 `/etc/nginx/nginx.conf` http 블록에도 `ssl_protocols` 줄이 있다. 패키지 버전에 따라 TLSv1, TLSv1.1까지 적혀 있기도 하니 열어 보고, server 블록에서 다시 정하거나 거기서 고친다. server에 쓴 값이 http 값을 덮어쓴다.

HTTP/2는 하나의 TCP 연결 위에서 요청 여러 개를 동시에 주고받게 해 준다(멀티플렉싱). 브라우저는 HTTPS에서만 HTTP/2를 쓰니 TLS 설정과 같이 켠다. 여기서 nginx 버전에 따라 문법이 다르다.

```nginx
# nginx 1.25.1 미만 (Ubuntu 24.04의 1.24, 22.04의 1.18)
server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    # ...
}
```

```nginx
# nginx 1.25.1 이상 (nginx.org 저장소의 최신 버전 등)
server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;
    # ...
}
```

새 버전에서 예전 문법을 쓰면 동작은 하되 `nginx -t`가 `the "listen ... http2" directive is deprecated, use the "http2" directive instead` 경고를 낸다. 1.24에서 새 문법을 쓰면 `unknown directive "http2"`로 거부한다. `nginx -v`로 버전을 먼저 본다. 같은 IP·포트를 듣는 server 중 하나에만 `http2`를 붙여도 그 포트 전체에 적용된다는 점도 알아 둔다. HTTP/3(QUIC)은 1.25.0부터 `listen 443 quic;`으로 쓸 수 있지만 UDP 443을 열어야 하고 아직 다룰 게 많아 이 글에서는 넘어간다. HTTP 버전별 차이는 [HTTP 버전 글](/posts/http-versions)에 있다.

### HSTS로 브라우저에게 약속하기

HTTP를 HTTPS로 리다이렉트해도 첫 요청은 평문 http로 나간다. 공용 와이파이에서 누군가 그 첫 요청을 가로채면 리다이렉트 전에 가짜 페이지를 보여 줄 수 있다. HSTS(HTTP Strict Transport Security)는 "앞으로 이 도메인은 https로만 접속하라"고 브라우저에게 기억시키는 헤더다. 한 번 받은 브라우저는 그 기간 동안 사용자가 `http://`를 쳐도 내부에서 https로 바꿔 보낸다.

```nginx
# 443 server 블록에서. always는 에러 응답(4xx, 5xx)에도 붙이라는 뜻
add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;
```

`max-age=63072000`은 2년이다. 처음에는 `max-age=300` 정도로 짧게 걸어 문제가 없는지 본 뒤 늘린다. 한 번 긴 값이 퍼지면 되돌릴 방법이 사실상 없다. 인증서 갱신에 실패하거나 HTTPS를 끄면 그 도메인은 브라우저에서 아예 열리지 않고, 사용자가 경고를 무시하고 들어가는 버튼도 사라진다. `includeSubDomains`는 모든 하위 도메인에도 적용하니, 내부용 `http://intranet.example.com` 같은 게 남아 있다면 넣지 않는다.

### OCSP stapling은 이제 따로 챙기지 않는다

예전 설정 예제에는 `ssl_stapling on; ssl_stapling_verify on;`이 거의 빠짐없이 들어 있다. 브라우저 대신 서버가 인증서 폐기 여부(OCSP 응답)를 받아 핸드셰이크에 붙여 주는 기능이다. 그런데 Let's Encrypt는 2025년에 OCSP 지원을 끝내고 인증서에서 OCSP 주소를 뺐다. 그 인증서에 stapling을 켜 두면 nginx가 `"ssl_stapling" ignored, no OCSP responder URL in the certificate` 경고를 내고 아무 일도 하지 않는다. 다른 인증 기관의 인증서라면 아직 의미가 있을 수 있으니, 인증서에 OCSP 주소가 있는지 보고 정한다.

```bash
# 인증서에 OCSP 주소가 있는지 확인 (아무것도 안 나오면 없다)
sudo openssl x509 -in /etc/letsencrypt/live/example.com/fullchain.pem -noout -ocsp_uri
```

## 압축은 텍스트에만

JS, CSS, JSON, SVG 같은 텍스트는 gzip으로 보통 원래 크기의 20~30%까지 줄어든다. 모바일 회선에서는 전송 시간이 그대로 준다. Ubuntu의 `nginx.conf`에는 `gzip on;`만 켜져 있고 나머지는 주석이다. 문제는 `gzip_types`의 기본값이 `text/html` 하나라는 점이다. 그래서 `gzip on`만 보고 압축이 되고 있다고 믿기 쉬운데, JS와 CSS는 압축되지 않는다. 글머리에서 300KB짜리 JS가 그대로 내려간 이유다.

```nginx
# /etc/nginx/conf.d/gzip.conf (http 컨텍스트)
gzip on;
gzip_vary on;            # Vary: Accept-Encoding을 붙여 캐시가 압축본과 원본을 나눠 저장하게
gzip_proxied any;        # 프록시(CDN)를 거쳐 온 요청에도 압축
gzip_comp_level 5;       # 1~9. 5 근처가 CPU 대비 효율이 좋다
gzip_min_length 1024;    # 1KB보다 작은 응답은 압축하지 않는다
gzip_types
    text/plain text/css text/xml
    application/javascript application/json application/xml
    application/rss+xml application/manifest+json
    image/svg+xml;
```

Ubuntu 기본 `nginx.conf`의 주석 처리된 gzip 줄들과 겹치므로, 그쪽 주석을 풀었다면 이 파일을 쓰지 않는다. 같은 컨텍스트에 `gzip_types`를 두 번 쓰면 `nginx -t`가 `directive is duplicate`로 거부한다.

이미 압축된 형식(JPEG, PNG, WebP, MP4, WOFF2)은 목록에 넣지 않는다. 다시 압축해도 거의 줄지 않고 CPU만 쓴다. `gzip_comp_level`을 9로 올리면 5보다 몇 % 더 줄지만 CPU는 몇 배 든다. 요청마다 실시간으로 압축하는 구조라 레벨을 올리는 이득이 작다. 빌드 때 미리 `.gz` 파일을 만들어 두고 `gzip_static on;`을 쓰면 nginx가 압축본을 그대로 보내니, 정적 파일은 최고 레벨로 미리 압축해도 비용이 없다.

Brotli는 gzip보다 텍스트를 15~20% 정도 더 줄이고, 현재 주요 브라우저가 모두 HTTPS에서 지원한다. 다만 nginx 본체에는 없고 ngx_brotli 모듈이 필요하다. 배포판에 따라 모듈 패키지(`libnginx-mod-http-brotli-filter` 같은 이름)가 있기도 하고 직접 빌드해야 하기도 하니 `apt search brotli`로 먼저 찾아본다. 앞에 CDN이 있다면 CDN이 Brotli 압축을 대신해 주는 경우가 많다.

압축과 보안이 얽히는 경우도 하나 있다. HTTPS 응답 안에 비밀 값(CSRF 토큰)과 사용자가 넣은 값이 함께 있으면, 압축된 크기 변화로 비밀 값을 한 글자씩 알아내는 BREACH 공격이 이론적으로 가능하다. 대부분의 사이트에서는 토큰을 요청마다 바꾸는 식으로 앱에서 막고, 압축은 그대로 둔다.

## 정적 파일 캐시 헤더

빌드 도구가 `app.3f9a1c.js`처럼 내용의 해시를 파일 이름에 넣는다면, 이 파일은 내용이 바뀌면 이름도 바뀐다. 같은 이름의 내용은 영원히 같다. 그래서 브라우저가 1년 동안 서버에 묻지도 않고 써도 된다. 반대로 `index.html`은 이름이 그대로인 채 내용이 바뀌니 매번 확인해야 한다. 이 차이를 location으로 나눈다.

```nginx
server {
    # ... listen 443, 인증서 ...
    root /var/www/app/public;

    # 해시가 붙은 빌드 산출물: 1년, 다시 확인하지 않음
    location /assets/ {
        try_files $uri =404;
        add_header Cache-Control "public, max-age=31536000, immutable";
        include snippets/security-headers.conf;
    }

    # HTML: 쓰기 전에 매번 서버에 확인 (ETag가 맞으면 304로 본문 없이 끝난다)
    location / {
        try_files $uri $uri/ /index.html;
        add_header Cache-Control "no-cache";
        include snippets/security-headers.conf;
    }
}
```

`immutable`은 사용자가 새로고침을 눌러도 다시 확인하지 말라는 뜻이다. 해시가 없는 파일에 이걸 붙이면 사용자는 1년 동안 옛 파일을 본다. 배포 후 "어떤 사용자는 아직 예전 화면이 보인다"는 문제는 대개 해시 없는 파일에 긴 캐시를 준 데서 나온다. `no-cache`는 "캐시하지 말라"가 아니라 "쓰기 전에 확인하라"다. 저장 자체를 막는 건 `no-store`다.

`expires 1y;` 지시어도 같은 일을 한다. `Expires` 헤더와 `Cache-Control: max-age=31536000`을 함께 만들어 준다. 다만 `expires`와 `add_header Cache-Control`을 같은 곳에 쓰면 `Cache-Control` 헤더가 두 줄 나가니 하나만 쓴다. 위에서 location마다 `include snippets/security-headers.conf;`를 반복한 이유는 [첫 글](/posts/nginx-basics)에서 본 `add_header` 상속 규칙 때문이다. location에 `add_header`가 하나라도 있으면 server에 쓴 `add_header`는 그 location에 하나도 내려오지 않는다. 캐시 헤더와 보안 헤더를 함께 쓰려면 안쪽에서 다시 넣어야 한다.

## 업스트림 응답을 nginx에 저장하기

상품 목록 API처럼 모든 사용자에게 같은 결과를 주는 응답은 nginx가 저장해 뒀다가 앱에 묻지 않고 내줄 수 있다. 앱이 같은 계산을 초당 수백 번 반복하던 게 10초에 한 번으로 준다. `proxy_cache_path`로 저장소를 정의하고, location에서 그 저장소를 쓴다.

```bash
# 캐시 디렉터리를 만들고 worker 사용자에게 준다
sudo mkdir -p /var/cache/nginx/app
sudo chown www-data:www-data /var/cache/nginx/app
```

```nginx
# /etc/nginx/conf.d/proxy-cache.conf (http 컨텍스트)
proxy_cache_path /var/cache/nginx/app
    levels=1:2              # 파일을 하위 디렉터리 두 단계로 나눠 저장
    keys_zone=app_cache:10m # 키 목록을 둘 공유 메모리. 1MB에 키 약 8000개
    max_size=1g             # 디스크 사용 상한. 넘으면 오래 안 쓴 것부터 지운다
    inactive=60m            # 60분 동안 아무도 안 찾은 항목은 지운다
    use_temp_path=off;      # 임시 파일을 캐시 디렉터리에 바로 써서 복사를 줄인다
```

```nginx
# 사이트 설정
location /api/products {
    proxy_pass http://app;
    include snippets/proxy-headers.conf;

    proxy_cache app_cache;
    proxy_cache_valid 200 301 10s;   # 200·301은 10초 동안 저장된 걸 쓴다
    proxy_cache_valid 404 1s;
    proxy_cache_key $scheme$host$request_uri;

    # 로그인한 사용자(세션 쿠키가 있음)는 캐시를 읽지도 쓰지도 않는다
    proxy_cache_bypass $cookie_session;
    proxy_no_cache     $cookie_session;

    # 같은 키로 동시에 몰리면 하나만 앱에 보내고 나머지는 기다린다
    proxy_cache_lock on;
    # 앱이 죽었거나 갱신 중이면 만료된 것이라도 준다
    proxy_cache_use_stale error timeout updating http_502 http_503 http_504;
    proxy_cache_background_update on;

    add_header X-Cache-Status $upstream_cache_status always;
}
```

`inactive`와 `proxy_cache_valid`는 다르다. `valid`가 지나면 항목은 "만료"돼 다음 요청 때 앱에 다시 묻지만 디스크에는 남아 있고, `inactive` 동안 아무도 안 찾으면 그때 지워진다. 만료된 항목이 남아 있어서 `proxy_cache_use_stale`로 앱 장애 때 대신 내줄 수 있다.

`proxy_cache_lock`은 캐시가 비어 있을 때 같은 요청이 한꺼번에 몰려 모두 앱으로 가는 일(캐시 스탬피드)을 막는다. `updating`과 `background_update`를 함께 쓰면 만료된 순간에도 사용자는 기다리지 않는다. nginx가 옛 응답을 바로 주고 뒤에서 앱에 새로 묻는다.

캐시가 동작하는지는 응답 헤더로 확인한다.

```bash
# 두 번 연속 요청해서 X-Cache-Status 변화를 본다
curl -s -o /dev/null -D - https://example.com/api/products | grep -i x-cache
curl -s -o /dev/null -D - https://example.com/api/products | grep -i x-cache

# 쿠키를 붙이면 BYPASS가 나와야 한다
curl -s -o /dev/null -D - -b "session=abc" https://example.com/api/products | grep -i x-cache
```

```text
x-cache-status: MISS
x-cache-status: HIT
x-cache-status: BYPASS
```

HTTP/2로 받으면 curl이 헤더 이름을 소문자로 보여 준다. 값은 MISS, HIT, BYPASS 말고도 EXPIRED(만료돼 앱에 다시 물음), STALE, UPDATING, REVALIDATED(앱이 304로 그대로라고 답함)가 있다.

가장 무서운 실수는 사용자마다 다른 응답을 캐시하는 것이다. 내 장바구니가 다른 사람에게 보인다. 그래서 nginx는 기본으로 `Set-Cookie`가 있는 응답이나 `Cache-Control: private`, `no-store`, `no-cache`가 붙은 응답을 저장하지 않는다. 하지만 앱이 이런 헤더 없이 사용자별 응답을 주면 nginx는 구분하지 못한다. 위 설정의 `proxy_cache_bypass`와 `proxy_no_cache`가 그 안전장치다. 세션 쿠키 이름이 `session`이 아니라면 실제 이름으로 바꾼다. 캐시는 공개 데이터만 나오는 경로에만 켠다. 캐시를 비워야 할 때는 디렉터리 안을 지우고 reload하면 된다. 특정 키만 지우는 `proxy_cache_purge`는 상용 버전이나 서드파티 모듈 기능이다.

```bash
# 캐시 전체 비우기 (디렉터리 자체는 남긴다)
sudo find /var/cache/nginx/app -type f -delete
sudo systemctl reload nginx
```

## 요청 수를 제한한다

로그인 API를 1초에 수십 번 두드리는 IP를 막는 게 `limit_req`다. 원리는 바닥에 구멍이 난 양동이(leaky bucket)다. 요청이 오면 양동이에 물을 한 칸 붓고, 물은 정해진 속도(`rate`)로 빠져나간다. 양동이 크기(`burst`)를 넘게 부으면 넘친 요청을 거절한다. 설정은 두 줄이다.

```nginx
# http 컨텍스트: IP별 상태를 저장할 공간과 속도
limit_req_zone $binary_remote_addr zone=login:10m rate=2r/s;
limit_req_status 429;   # 기본값 503 대신 429 Too Many Requests
```

```nginx
# 사이트 설정
location = /api/login {
    limit_req zone=login burst=3 nodelay;
    proxy_pass http://app;
    include snippets/proxy-headers.conf;
}
```

### 제한을 걸 때 놓치기 쉬운 것

nginx 앞에 로드 밸런서나 CDN이 있으면 `$binary_remote_addr`는 그 장비의 IP다. 모든 사용자가 한 IP로 세어져 사이트 전체가 2r/s로 묶인다. [앞 글](/posts/nginx-reverse-proxy)에서 본 realip 모듈(`set_real_ip_from`, `real_ip_header`)로 진짜 클라이언트 IP를 먼저 복원해야 한다. 반대로 회사나 학교처럼 많은 사람이 NAT 뒤에서 IP 하나를 쓰는 곳은 정상 사용자끼리 서로의 한도를 쓴다. 로그인 같은 민감한 경로는 IP 제한과 함께 앱에서 계정별 실패 횟수를 센다.

동시에 열린 연결 수는 `limit_conn`으로 따로 제한한다. 큰 파일을 여러 연결로 쪼개 받는 다운로드 도구나, 연결을 열어 두고 아주 느리게 보내는 공격(slowloris)을 막는다.

```nginx
# http 컨텍스트
limit_conn_zone $binary_remote_addr zone=perip_conn:10m;
limit_conn_status 429;

# server 또는 location
limit_conn perip_conn 20;   # IP 하나당 동시 연결 20개까지
```

HTTP/2에서는 연결 하나에 요청 여러 개가 흐르니, `limit_conn`은 요청 수가 아니라 스트림 단위로 센다는 걸 기억한다. 429를 줄 때는 앱 쪽에서처럼 `Retry-After` 헤더를 붙여 주면 클라이언트가 언제 다시 시도할지 안다. nginx에서는 `error_page 429 /429.json;`으로 거절 응답 본문을 JSON으로 바꾸고 그 location에서 헤더를 붙인다.

## 보안 헤더와 숨길 것

응답 헤더 몇 줄로 브라우저 쪽 공격 몇 가지를 막을 수 있다. 앞에서 말한 상속 문제 때문에 파일 하나로 묶고 필요한 곳마다 include한다.

```nginx
# /etc/nginx/snippets/security-headers.conf
add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;
add_header X-Content-Type-Options    "nosniff" always;
add_header X-Frame-Options           "SAMEORIGIN" always;
add_header Content-Security-Policy   "frame-ancestors 'self'" always;
add_header Referrer-Policy           "strict-origin-when-cross-origin" always;
```

`X-Content-Type-Options: nosniff`는 브라우저가 `Content-Type`을 무시하고 내용을 보고 형식을 짐작하지 못하게 한다. 사용자가 올린 텍스트 파일이 스크립트로 실행되는 일을 막는다. `mime.types`에 없는 확장자는 `application/octet-stream`으로 나가니, 새 형식(`.webmanifest`, `.mjs`)을 쓰면 `mime.types`에 있는지 확인한다.

`X-Frame-Options`와 CSP의 `frame-ancestors`는 다른 사이트가 내 페이지를 iframe에 넣지 못하게 한다. 투명한 iframe 위에 가짜 버튼을 얹어 클릭을 훔치는 클릭재킹을 막는다. `frame-ancestors`가 표준이고 더 세밀하게(허용할 출처 목록) 정할 수 있으며, 둘 다 있으면 지원하는 브라우저는 `frame-ancestors`를 따른다. 오래된 브라우저를 위해 둘 다 둔다. CSP 전체(script-src 등)는 앱이 쓰는 스크립트 출처를 알아야 정할 수 있어서 nginx보다 앱에서 관리하는 경우가 많다. 앱이 이미 CSP 헤더를 보낸다면 nginx가 하나 더 붙이지 않게 한다. 둘 다 있으면 브라우저는 두 정책을 모두 만족해야 통과시킨다.

`Referrer-Policy: strict-origin-when-cross-origin`은 다른 사이트로 이동할 때 경로와 쿼리를 빼고 도메인만 보낸다. 주소에 토큰이나 검색어가 들어 있어도 밖으로 새지 않는다. 지금 브라우저 대부분의 기본값이기도 하지만 명시해 두면 확실하다.

서버 정보와 파일도 숨긴다.

```nginx
# http 컨텍스트: Server 헤더와 에러 페이지에서 버전을 뺀다
server_tokens off;
```

```nginx
# server 블록: .git, .env 같은 점 파일은 막되 .well-known은 연다
location ~ /\.(?!well-known) {
    deny all;
    access_log off;
    log_not_found off;
}
```

`server_tokens off`를 하면 `Server: nginx/1.24.0 (Ubuntu)`가 `Server: nginx`가 된다. 버전을 숨긴다고 취약점이 없어지진 않지만, 특정 버전을 노리는 자동 스캐너의 표적 목록에서는 빠진다. 헤더 자체를 지우려면 headers-more 같은 서드파티 모듈이 필요하다.

점 파일 차단은 생각보다 자주 필요하다. 배포를 `git pull`로 하면 웹 루트에 `.git/`이 생기고, `https://example.com/.git/config`가 열리면 저장소 전체를 내려받을 수 있다. `.env`에는 DB 비밀번호가 들어 있다. 정규식에서 `(?!well-known)`으로 예외를 둔 건 certbot의 HTTP-01 검증 경로가 `/.well-known/`이기 때문이다. 이걸 막으면 인증서 갱신이 실패한다. 이 location은 정규식이라 같은 server의 `^~` 접두사 location이 먼저 고르는 경로에는 적용되지 않는다는 점도 앞 글의 location 순서대로 확인한다. 애초에 웹 루트를 저장소 루트가 아니라 빌드 결과 폴더(`public/`, `dist/`)로 잡는 게 근본적인 해결이다.

`Verification: OK`가 핵심이다. 체인이 빠졌으면 여기에 `unable to get local issuer certificate`가 나온다. `-servername`은 SNI 값으로, 한 IP에 사이트가 여럿이면 이게 없을 때 다른 사이트의 인증서가 나온다. certbot 2.0부터는 기본으로 ECDSA 키를 만들어서 `Signature type: ECDSA`로 나온다. <Callout kind="warning" title="HSTS와 리다이렉트는 짧게 시험하고 늘린다">
`Strict-Transport-Security`의 긴 `max-age`와 301 리다이렉트는 브라우저가 기억한다. 서버 설정을 되돌려도 이미 받은 사용자에게는 남는다. 처음에는 `max-age=300`, 302로 걸어 확인하고, 문제없으면 늘린다. 되돌릴 때는 `max-age=0`을 보내야 브라우저가 기록을 지운다(헤더를 빼기만 하면 남은 기간 동안 유지된다). 설정 자체는 백업(`sudo tar xzf ~/nginx-backup-날짜.tgz -C /etc`) 후 `sudo nginx -t && sudo systemctl reload nginx`로 되돌린다. certbot이 고친 사이트 파일만 되돌리면 인증서 경로가 사라지니, 다시 `sudo certbot --nginx`로 넣거나 `sudo certbot install --cert-name example.com`으로 설치만 다시 한다.
</Callout>

## HTTPS를 붙인 뒤에 걸려 오는 전화

설정을 다 끝내고 몇 주 지나 생기는 문제는 대개 둘 중 하나다. 앞단을 바꾼 날 사이트가 안 열리거나, 인증서는 갱신됐다는데 브라우저에 만료 경고가 뜬다. 아래 출력은 Ubuntu 24.04의 nginx 1.24로 같은 구성을 만들어 돌려 본 것이다.

### 로드 밸런서를 앞에 두자 `ERR_TOO_MANY_REDIRECTS`

클라우드 로드 밸런서(또는 Cloudflare 같은 CDN)에 인증서를 올리고 TLS를 거기서 끝내게 바꿨다. 로드 밸런서는 nginx의 80으로 평문을 넘긴다. 그날부터 크롬이 "리디렉션한 횟수가 너무 많습니다"와 `ERR_TOO_MANY_REDIRECTS`를 띄운다. 개발자 도구 Network 탭을 보면 같은 주소로 301이 줄줄이 찍혀 있다. curl로 따라가 보면 바로 보인다.

```bash
# 리다이렉트를 5번까지만 따라간다
curl -sSL --max-redirs 5 -o /dev/null https://example.com/login

# 첫 응답만 본다
curl -sI https://example.com/login
```

```text
curl: (47) Maximum (5) redirects followed
```

```text
HTTP/1.1 301 Moved Permanently
Server: nginx/1.24.0 (Ubuntu)
Date: Sun, 18 Oct 2026 11:03:08 GMT
Content-Type: text/html
Content-Length: 178
Connection: keep-alive
Location: https://example.com/login
```

`Location`이 지금 요청한 주소와 똑같다. 사용자는 https로 들어왔지만 nginx가 받은 건 로드 밸런서가 보낸 평문 요청이라서, 80 블록의 `return 301 https://...`이 매번 다시 걸린다. 원래 스킴은 로드 밸런서가 붙여 주는 `X-Forwarded-Proto`에만 남아 있다. 80 블록에서 그 값을 보고 판단한다.

```nginx
server {
    listen 80;
    server_name example.com;

    location / {
        # 로드 밸런서가 https로 받은 요청이면 리다이렉트하지 않는다
        if ($http_x_forwarded_proto != "https") {
            return 301 https://$host$request_uri;
        }
        proxy_pass http://app;
        include snippets/proxy-headers.conf;
    }
}
```

고친 뒤 같은 `curl -sI`는 `HTTP/1.1 200 OK`로 끝나고, 로드 밸런서를 거치지 않은 평문 요청에만 301이 나간다. 이 구성에서는 앱에 넘기는 `X-Forwarded-Proto`도 `$scheme`(지금은 늘 http)이 아니라 받은 값 그대로여야 한다. 공용 snippet의 그 줄을 `proxy_set_header X-Forwarded-Proto $http_x_forwarded_proto;`로 바꾼 snippet을 이 server용으로 따로 둔다. 같은 location에 한 줄을 더 쓰면 헤더가 두 번 나가니 덮어쓰기가 되지 않는다. 그대로 두면 이번엔 앱이 http 주소로 리다이렉트를 만든다. 그리고 이 헤더는 누구나 붙일 수 있으니, nginx의 80은 보안 그룹이나 [iptables](/posts/iptables-basics)로 로드 밸런서 주소에서 오는 것만 받게 묶는다. Cloudflare라면 SSL 모드가 Flexible(엣지까지만 HTTPS)일 때 같은 루프가 나고, Full(strict)로 바꾸는 게 정석이다.

### 갱신은 됐다는데 만료 경고가 뜬다

모니터링에서 "인증서 만료 7일 전" 알림이 왔다. `certbot certificates`를 보면 이미 갱신돼 89일 남았다고 나온다. 디스크의 파일과 nginx가 실제로 내보내는 인증서를 나란히 본다.

```bash
# 디스크에 있는 인증서의 만료일
sudo openssl x509 -in /etc/letsencrypt/live/example.com/fullchain.pem -noout -enddate

# nginx가 지금 내보내는 인증서의 만료일
openssl s_client -connect 127.0.0.1:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -enddate
```

```text
notAfter=Jan 16 11:03:20 2027 GMT
notAfter=Oct 25 11:03:03 2026 GMT
```

날짜가 다르면 nginx가 옛 인증서를 메모리에 들고 있는 것이다. nginx는 시작하거나 reload할 때만 인증서 파일을 읽는다. `sudo nginx -t && sudo systemctl reload nginx` 뒤에 다시 보면 두 번째 줄도 `Jan 16 11:03:20 2027 GMT`로 바뀐다.

`certbot --nginx`로 받았다면 갱신 뒤 reload까지 알아서 한다. 이 일이 생기는 건 `certonly --webroot`나 `--standalone`처럼 설치 플러그인 없이 받은 경우다. `sudo grep -E "authenticator|installer" /etc/letsencrypt/renewal/example.com.conf`에 `installer = nginx`가 없으면 갱신만 하고 reload는 안 한다. 갱신될 때마다 실행되는 훅을 하나 둔다.

```bash
# 갱신에 성공할 때마다 실행된다
sudo tee /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh > /dev/null <<'EOF'
#!/bin/sh
nginx -t && systemctl reload nginx
EOF
sudo chmod +x /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh
```

같은 인증서를 로드 밸런서나 메일 서버에 복사해서 쓰는 경우도 같은 증상이 난다. 복사도 이 훅에서 한다. 만료 모니터링은 디스크가 아니라 바깥에서 받은 인증서로 해야 이런 경우를 잡는다. 앞의 `openssl s_client` 줄을 그대로 쓰면 된다. 인증서 문제가 아니라 TLS 연결 자체가 안 맺어진다면 어느 계층에서 끊겼는지부터 [계층별로 장애 좁히기](/posts/network-troubleshooting-by-layer)의 순서로 본다.

## 앞단에서 한 번에 처리한다

nginx 앞단에서 할 일은 결국 "모든 요청이 반드시 지나가는 자리"라는 점을 이용하는 것이다. 인증서는 certbot이 HTTP-01로 받아 자동 갱신하고, 80은 HTTPS로 돌리고, TLS 1.2·1.3과 HTTP/2(버전에 맞는 문법)를 켜고, HSTS는 짧게 시험한 뒤 늘린다. 텍스트는 `gzip_types`를 채워 압축하고, 해시 붙은 파일엔 `immutable`, HTML엔 `no-cache`를 준다. 공개 API 응답은 `proxy_cache`로 몇 초만 저장해도 앱 부하가 크게 준다. `limit_req`로 IP별 속도를 묶고, 보안 헤더는 `add_header` 상속 규칙 때문에 snippet으로 묶어 include한다. 확인은 언제나 `curl -I`와 `openssl s_client`로 바깥에서 한다.

## 면접에서 나올 만한 질문

### Let's Encrypt 인증서는 어떻게 발급되고 갱신되나요?

ACME 프로토콜로 발급한다. nginx 플러그인은 HTTP-01 방식이라 인증 기관이 `http://도메인/.well-known/acme-challenge/` 아래 토큰을 직접 가져가 도메인 제어를 확인하고, 그 뒤 CSR에 서명해 인증서를 준다. 인증서가 90일짜리라 snap 버전 certbot이 등록한 systemd 타이머가 하루 두 번 만료 임박 인증서를 갱신하고 nginx를 reload한다. 80 포트를 막으면 갱신이 실패하니 `certbot renew --dry-run`으로 미리 확인한다.

### ssl_certificate에 fullchain.pem을 써야 하는 이유는요?

클라이언트가 서버 인증서를 루트까지 이어 검증하려면 중간 인증서가 필요한데, 서버가 보내 줘야 한다. `cert.pem`만 쓰면 중간 인증서를 알아서 받아 오는 일부 브라우저에서는 되지만 curl, 모바일 앱, 서버 간 HTTP 클라이언트는 `unable to get local issuer certificate`로 실패한다. `openssl s_client`의 `Verification: OK`로 확인한다.

### HSTS는 무엇을 막고, 도입할 때 무엇을 조심하나요?

HTTP에서 HTTPS로 리다이렉트되기 전 첫 평문 요청을 가로채는 공격(SSL 스트리핑)을 막으려고, 브라우저가 정해진 기간 동안 그 도메인을 무조건 https로만 접속하게 한다. 긴 `max-age`가 퍼지면 인증서 문제나 HTTPS 중단 때 사이트가 아예 열리지 않고 되돌리기 어려우니 짧게 시험하고 늘린다. `includeSubDomains`는 http로만 도는 하위 도메인이 없을 때만 넣는다.

### gzip을 켰는데 JS가 압축되지 않습니다. 왜 그럴까요?

`gzip_types` 기본값이 `text/html` 하나라서 `gzip on`만으로는 HTML만 압축된다. `application/javascript`, `text/css`, `application/json`, `image/svg+xml` 같은 텍스트 형식을 추가하고, `gzip_vary on`으로 캐시가 압축본과 원본을 나눠 저장하게 한다. 이미 압축된 이미지나 폰트는 넣지 않고, 레벨은 5 근처가 CPU 대비 효율이 좋다.

### 정적 파일 캐시 헤더는 어떻게 나누나요?

내용 해시가 파일 이름에 들어간 빌드 산출물은 내용이 바뀌면 이름도 바뀌니 `max-age=31536000, immutable`로 1년 동안 묻지 않고 쓰게 한다. 이름이 그대로인 채 내용이 바뀌는 HTML은 `no-cache`로 매번 ETag 확인을 하게 해서 배포가 바로 반영되게 한다. 해시 없는 파일에 긴 캐시를 주면 사용자가 옛 버전을 계속 본다.

### proxy_cache를 쓸 때 사용자별 응답이 섞이지 않게 하려면요?

nginx는 기본으로 `Set-Cookie`나 `Cache-Control: private`·`no-store`가 있는 응답을 저장하지 않지만, 앱이 그런 헤더 없이 사용자별 응답을 주면 구분하지 못한다. 그래서 세션 쿠키가 있는 요청은 `proxy_cache_bypass`와 `proxy_no_cache`로 캐시를 건너뛰게 하고, 캐시는 공개 데이터 경로에만 켠다. `$upstream_cache_status`를 헤더로 내보내 HIT·MISS·BYPASS를 확인한다.

### limit_req의 burst와 nodelay는 각각 무엇을 하나요?

`rate`는 양동이에서 물이 빠지는 속도이고 `burst`는 넘친 요청을 몇 개까지 받아 줄지다. nodelay가 없으면 받아 준 요청을 rate에 맞춰 늦게 보내서 사용자가 이유 없이 기다리고, nodelay면 바로 보내고 칸만 차지한다. 2r/s, burst=3, nodelay에서 동시에 6개가 오면 4개가 통과하고 2개가 거절된다. 거절 코드는 기본 503이라 `limit_req_status 429`로 바꾼다.

### nginx 앞에 로드 밸런서가 있으면 속도 제한에서 무엇이 문제가 되나요?

`$binary_remote_addr`가 로드 밸런서의 IP가 되어 모든 사용자가 한 키로 세어지고, 사이트 전체가 한 사람 몫의 한도에 묶인다. realip 모듈의 `set_real_ip_from`으로 믿을 수 있는 로드 밸런서 대역을 지정하고 `real_ip_header X-Forwarded-For`로 진짜 클라이언트 IP를 복원한 뒤 제한한다. 신뢰 대역을 넓게 잡으면 클라이언트가 위조한 헤더로 제한을 피할 수 있으니 정확한 대역만 적는다.
