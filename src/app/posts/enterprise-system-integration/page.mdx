주문 시스템에서 배송 요청을 벤더 API로 보냈다. 응답이 800ms 안에 오지 않아 타임아웃으로 처리하고 한 번 더 보냈다. 다음 날 아침 물류 담당자가 묻는다. "같은 주문으로 배송 접수가 두 건 들어왔는데 어느 걸 취소하나요?" 우리 로그에는 첫 요청이 실패로 찍혀 있다. 벤더 쪽에서는 첫 요청도 성공이었다.

회사 시스템은 대부분 혼자 돌지 않는다. 결제, 배송, 회계(ERP), 고객 관리(CRM), 재고, 정산 같은 남의 시스템이나 오래된 사내 시스템과 데이터를 주고받는다. 이 글은 그 연동을 어떤 방식으로 붙이고, 경계에서 무엇을 번역하고, 실패와 중복을 어떻게 다루고, 매일 밤 무엇으로 어긋남을 찾는지를 본다. 실습은 Node 22.22.0으로 일부러 말썽을 부리는 벤더 서버와 어댑터를 직접 짜서 돌렸다.

이 주제의 다른 글: [새 나라에 서비스를 열 때](/posts/global-rollout-localization), [SIT와 UAT](/posts/sit-uat-testing), [컷오버와 하이퍼케어](/posts/release-cutover-hypercare).

## 붙이는 방법은 세 가지로 갈린다

연동 방식은 데이터가 언제, 어떤 모양으로 건너가느냐로 나뉜다. 지금 바로 답이 필요하면 동기 API를 부른다. 상대가 나중에 처리해도 되면 메시지로 넘긴다. 상대가 하루에 한 번 파일로만 받는다면 파일 배치다. 실무에서 세 번째가 생각보다 흔하다. 오래된 ERP나 은행, 물류사는 지금도 SFTP 서버에 CSV나 고정 길이 텍스트 파일을 올려 두는 방식을 쓰는 경우가 많다.

세 방식은 서로 대체재가 아니라 함께 쓰는 경우가 많다. 주문 접수는 메시지로 보내고, 상태 변화는 웹훅으로 받고, 하루치 전체 목록은 파일로 받아 맞춰 본다. 고를 때 따지는 것을 표로 모으면 이렇다.

| | 동기 API | 메시지 | 파일 배치 |
|---|---|---|---|
| 결과를 아는 시점 | 바로 | 나중에(웹훅·폴링) | 다음 배치 |
| 벤더가 죽으면 | 우리 요청도 실패 | 큐에 쌓였다가 다시 | 다음 날 다시 올림 |
| 한 번에 보내는 양 | 한 건 | 한 건씩, 많이 | 수만~수백만 건 |
| 순서 | 호출 순서 | 파티션·키에 따라 | 파일 안의 줄 순서 |
| 흔한 사고 | 타임아웃 뒤 중복 | 중복 소비, 순서 뒤바뀜 | 파일 반쪽 읽기, 인코딩 |

웹훅을 받는 쪽에서 챙길 것(서명 확인, 먼저 응답하고 나중에 처리하기, 순서가 보장되지 않는다는 점)은 [웹훅](/posts/webhooks) 글에 있다. 여기서는 그 앞뒤, 우리가 벤더를 부르는 쪽과 결과를 맞춰 보는 쪽을 본다.

파일 배치에는 따로 적어 둘 함정이 있다. 벤더가 파일을 다 쓰기 전에 우리가 읽기 시작하면 반쪽짜리 파일을 처리한다. 그래서 보통 `.tmp`로 올린 뒤 이름을 바꾸거나, 데이터 파일 뒤에 `.done` 같은 빈 표시 파일을 올리는 약속을 한다. 파일 끝에 건수와 합계를 적은 트레일러(trailer) 줄을 두면 읽은 쪽이 다 받았는지 스스로 확인할 수 있다. 인코딩도 확인한다. 오래된 국내 시스템은 UTF-8이 아니라 CP949(EUC-KR 확장)로 파일을 내는 경우가 있어서, 그대로 읽으면 한글이 깨진다. 배치 작업 자체를 잘게 나누고 다시 시작하는 방법은 [배치 처리](/posts/batch-processing)에서 다뤘다.

## 벤더의 말은 경계에서 우리 말로 바꾼다

벤더 API의 필드는 대개 이렇게 생겼다. `STAT_CD: "02"`, `DLV_DT: "20261023"`, `QTY: "0003"`. 상태는 코드표의 번호이고, 날짜는 구분자 없는 문자열이고, 수량은 앞을 0으로 채운 문자열이다. 이 모양이 주문 서비스 안까지 들어오면 곤란해진다. `if (order.status === "02")` 같은 코드가 여기저기 생기고, 벤더를 바꾸거나 벤더가 코드표를 바꾸는 순간 온 코드를 뒤져야 한다.

그래서 연동 지점에 번역 계층을 둔다. 바깥 시스템의 모델이 우리 도메인을 오염시키지 않게 막는다는 뜻에서 부패 방지 계층이라고 부른다. 개념과 어댑터 패턴으로 짜는 법은 [어댑터 패턴](/posts/pattern-adapter)과 [헥사고날 아키텍처](/posts/hexagonal-architecture)에서 다뤘으니, 여기서는 연동에서 실제로 번역하는 것들을 본다. 아래 조각을 하나씩 눌러 보면 벤더가 밤마다 주는 CSV 한 줄에 무엇이 숨어 있는지 보인다.

번역 계층이 맡는 일은 이름 바꾸기보다 넓다.

- 코드표: 상태, 사유, 배송 방식 같은 코드를 우리 열거형으로 바꾼다. 모르는 코드는 기본값으로 뭉개지 않는다. 벤더가 새 상태를 추가했다는 신호이기 때문이다.
- 형식: 날짜, 시간대, 금액 단위, 0 채움, 공백 채움, 인코딩. 벤더 시각이 현지 시각인지 UTC인지는 문서에 없으면 직접 확인한다.
- 의미: 벤더의 "완료"가 우리의 "배송 완료"인지 "출고 완료"인지. 같은 단어가 다른 뜻인 경우가 가장 위험하다. [바운디드 컨텍스트](/posts/ddd-bounded-context)가 말하는 문제가 시스템 사이에서 그대로 일어난다.
- 마스터 데이터: 상품 코드, 매장·센터 코드, 단위(EA, BOX) 같은 기준 정보는 양쪽이 서로 다른 번호를 쓴다. 매핑 테이블을 따로 두고, 누가 그 표를 고치는지 주인을 정한다.

마스터 데이터 매핑은 코드가 아니라 데이터라서 사고가 잘 숨는다. 새 상품이 우리 쪽에 등록됐는데 매핑 표에 없으면 그 상품의 주문만 벤더로 못 간다. 매핑이 없을 때는 주문 전체를 실패시키지 말고 그 건만 보류 상태로 두고 알림을 보낸다. 매핑 표에도 유효 기간(언제부터 언제까지 이 코드가 이 코드에 대응하는지)을 두면, 벤더가 센터 코드를 바꾸는 날 옛 주문과 새 주문을 모두 바르게 읽을 수 있다.

의존 방향을 그림으로 보면 이렇다. 주문 서비스는 "배송을 요청한다"는 우리 말로 된 인터페이스만 알고, 벤더 코드표와 CSV 형식은 어댑터 안에만 있다.

## 타임아웃은 실패가 아니라 모른다는 뜻이다

처음 이야기로 돌아가자. 이걸 재현하려고 벤더 서버를 하나 짰다(포트 18050). `ORD-1002`의 첫 요청은 저장까지 마친 뒤 1.5초 늦게 응답하고, `ORD-1003`은 처음 두 번 `503`을 돌려주고, 우편번호가 다섯 자리가 아닌 `ORD-1004`는 `400`으로 거절한다. 어댑터는 800ms 타임아웃을 걸고, 타임아웃과 `5xx`는 최대 네 번까지 다시 보내고, `4xx`는 바로 포기한다. 먼저 멱등 키 없이 돌렸다.

```js
// adapter.mjs (줄임) — 타임아웃과 5xx는 다시, 4xx는 바로 포기
for (let n = 0; n < 4; n++) {
  try {
    const res = await fetch(`${BASE}/v1/orders`, {
      method: "POST",
      headers: { "content-type": "application/json", ...(mode === "safe" ? { "idempotency-key": order.idemKey } : {}) },
      body: JSON.stringify(toVendor(order)),
      signal: AbortSignal.timeout(800),
    });
    const body = await res.json();
    if (res.status >= 400 && res.status < 500) throw new Permanent(`${res.status} ${body.code}`);
    if (res.status >= 500) throw new Error(`${res.status} ${body.code}`);
    return body.VND_ORD_ID;
  } catch (e) {
    if (e instanceof Permanent) throw e;   // DLQ로 간다
    await sleep(backoff(n));               // full jitter, 상한 1초
  }
}
```


타임아웃이 났을 때 우리가 아는 것은 "답을 못 받았다"뿐이다. 요청이 아예 안 갔을 수도, 가서 처리됐는데 답만 늦었을 수도 있다. 그래서 타임아웃 뒤 재시도는 상대가 중복을 걸러 줄 때만 안전하다. 같은 실험을 멱등 키를 붙여 다시 돌렸다. 키는 주문을 만들 때 한 번 생성해 저장해 두고, 재시도할 때 같은 값을 보낸다.

```text
== mode=safe
  [adapter] ORD-1001 ok -> V7001 (10ms)
  [adapter] ORD-1002 timeout(800ms), retry in 58ms
  [adapter] ORD-1002 ok -> V7002 (3ms)
  [adapter] ORD-1003 503 BUSY, retry in 52ms
  [adapter] ORD-1003 503 BUSY, retry in 183ms
  [adapter] ORD-1003 ok -> V7003 (3ms)
  [adapter] ORD-1004 -> DLQ (400 E_ZIP)
```

이번에는 재시도가 `V7002`, 즉 첫 요청이 만든 번호를 돌려받았다. 벤더가 키를 보고 저장해 둔 첫 응답을 내줬기 때문이다. 키를 받는 쪽이 어떻게 선점하고 응답을 저장하는지는 [멱등성 키](/posts/idempotency-key)에서 다뤘다.

문제는 모든 벤더가 멱등 키를 받아 주지 않는다는 점이다. 그럴 때 고를 수 있는 길은 몇 가지다.

- 다시 보내기 전에 먼저 묻는다. 벤더가 우리 참조 번호로 조회하는 API(`GET /orders?ref=ORD-1002`)를 준다면, 타임아웃 뒤에는 재전송 대신 조회부터 한다. 있으면 그 번호를 쓰고, 없을 때만 다시 보낸다. 조회와 재전송 사이에 첫 요청이 늦게 처리되는 틈은 남는다.
- 참조 번호를 유일하게 지켜 달라고 요청한다. 벤더 DB에 우리 참조 번호의 유니크 제약이 있으면 두 번째 요청은 "이미 있음" 오류로 돌아온다. 이 오류를 성공으로 해석하는 처리를 어댑터에 둔다.
- 다시 보내지 않고 사람에게 넘긴다. 돈이 오가는 요청인데 위 둘 다 안 되면, 자동 재시도는 연결 실패(요청이 확실히 안 간 경우)에만 하고 타임아웃은 보류 상태로 둔 뒤 대사로 확정한다.

여기서 타임아웃 값도 중요하다. 벤더가 평소 1.2초 걸리는데 800ms로 끊으면 정상 요청까지 모두 "모름"으로 만든다. 벤더의 p99 지연을 재 보고 그보다 넉넉하게 잡는다. 값을 고르는 순서는 [타임아웃](/posts/timeouts)에 정리했다.

## 들어오는 쪽은 버전을 보고 덮어쓴다

반대 방향도 있다. 벤더가 웹훅이나 파일로 상태를 보내 주면 우리는 그걸 저장한다. 이때 같은 사건이 두 번 오고, 늦게 생긴 사건이 먼저 오는 일이 생긴다. 웹훅은 재전송되고, 파일은 다시 올라오고, 폴링은 겹치는 구간을 다시 읽는다. 받는 쪽 저장을 멱등하게 만드는 방법은 "벤더가 그 상태를 정한 시각"보다 새 것일 때만 덮어쓰는 것이다. PostgreSQL 16에서 확인했다.

```sql
create table vendor_orders (
  vendor_order_id   text primary key,
  order_ref         text not null,
  status            text not null,
  vendor_updated_at timestamptz not null
);

-- 사건마다 같은 문장을 돌린다
prepare apply_event(text, text, text, timestamptz) as
insert into vendor_orders values ($1, $2, $3, $4)
on conflict (vendor_order_id) do update
  set status = excluded.status, vendor_updated_at = excluded.vendor_updated_at
  where vendor_orders.vendor_updated_at < excluded.vendor_updated_at;  -- 더 새 것만

execute apply_event('V7002', 'ORD-1002', 'SHIPPED',  '2026-10-23 10:05+09');
execute apply_event('V7002', 'ORD-1002', 'ACCEPTED', '2026-10-23 10:00+09'); -- 늦게 온 옛 사건
execute apply_event('V7002', 'ORD-1002', 'SHIPPED',  '2026-10-23 10:05+09'); -- 중복
select * from vendor_orders;
```

```text
INSERT 0 1
INSERT 0 0
INSERT 0 0
 vendor_order_id | order_ref | status  |   vendor_updated_at
-----------------+-----------+---------+------------------------
 V7002           | ORD-1002  | SHIPPED | 2026-10-23 01:05:00+00
```

두 번째와 세 번째 문장은 `INSERT 0 0`, 아무것도 바꾸지 않았다. 늦게 온 `ACCEPTED`가 `SHIPPED`를 덮지 않았고, 중복도 그냥 지나갔다. 결과의 시각이 `01:05+00`으로 보이는 건 이 서버의 시간대가 UTC라서다. 같은 순간이다. 벤더가 시각을 주지 않고 순번(sequence)만 준다면 그 순번으로 비교하고, 둘 다 없다면 상태 전이 규칙(`SHIPPED`에서 `ACCEPTED`로는 못 간다)으로 막는다.

이 방법은 벤더가 보낸 시각이 믿을 만하다는 가정 위에 있다. 벤더 서버 여러 대의 시계가 어긋나 있으면 같은 주문에서 시각이 거꾸로 찍힐 수 있다. 사건마다 유일한 id가 온다면 처리한 사건 id를 저장해 두는 인박스 테이블이 더 단단하다. 그 방식은 [메시지 전달 보장](/posts/message-delivery-semantics)의 인박스 테이블 부분에 있다.

## 다시 보낼 것과 포기할 것

어댑터의 재시도 규칙은 실패의 종류로 정한다. 위 실험의 규칙을 정리하면 이렇다.

- 연결 실패, `502`, `503`, `504`, 타임아웃: 일시적일 수 있다. 간격을 늘리고 지터를 섞어 다시 보낸다. 타임아웃은 멱등이 보장될 때만.
- `429`: 벤더가 그만 보내라고 한 것이다. `Retry-After`가 있으면 따른다.
- `400`, `422`: 내용이 틀렸다. 몇 번을 보내도 같다. 바로 DLQ로 보내고 원인을 고친다.
- `401`, `403`: 대개 우리 쪽 인증서나 키가 만료됐다. 모든 요청이 동시에 실패하므로 재시도보다 알림이 먼저다.

## 매일 밤 두 장부를 맞춰 본다

멱등 키와 재시도를 다 갖춰도 어긋남은 생긴다. 벤더 담당자가 화면에서 직접 주문을 취소하고, 웹훅 하나가 사라지고, 누군가 DB를 손으로 고친다. 그래서 정해진 주기로 양쪽 전체 목록을 받아 한 줄씩 비교하는 대사(reconciliation)를 돌린다. 실험에서는 벤더 담당자가 `V7001`을 직접 취소했다고 치고, 벤더가 내려 주는 CSV와 우리 장부를 비교했다. 먼저 멱등 키 없이 돌렸던 날의 결과다.

```text
== vendor export
VND_ORD_ID,ORD_REF,STAT_CD,QTY
V7001,ORD-1001,99,0002
V7002,ORD-1002,01,0001
V7003,ORD-1002,01,0001
V7004,ORD-1003,01,0005

== reconcile
  ORD-1001 status_diff ours=ACCEPTED vendor=CANCELLED
  ORD-1002 duplicate   vendor=V7002+V7003
  ORD-1003 match
  ORD-1004 ours_only   (ours=PENDING)

DLQ: [{"id":"ORD-1004","reason":"400 E_ZIP"}]
```

어긋남이 네 종류로 갈린다. 아래 그림에서 하나씩 따라가 보자.

대사를 운영할 때 챙기는 것들이 있다.

- 날짜 경계: 23시 59분에 보낸 요청이 벤더의 다음 날 파일에 실린다. 하루 창으로만 비교하면 매일 밤 몇 건이 "우리에게만 있음"으로 뜨고, 다음 날엔 "벤더에게만 있음"으로 뜬다. 앞뒤로 겹치는 구간을 두고 비교하거나, 하루 늦게 한 번 더 비교한다.
- 결과를 테이블에 남긴다: 몇 건이 어긋났고 몇 건이 해결됐는지를 지표로 본다. 같은 종류의 어긋남이 매일 나오면 그건 운영 이슈가 아니라 버그다.
- 고치는 규칙을 나눈다: 원인과 처리가 정해진 것(벤더 쪽 취소를 우리 쪽에 반영)은 자동으로, 판단이 필요한 것(중복 접수 중 어느 쪽을 살릴지)은 담당자에게 보낸다.

결제처럼 돈이 걸린 대사를 함수로 짜 보는 연습은 [결제 시스템 설계 ②](/posts/sd-payment-reliability)에 있다. 원리는 같다. 양쪽 모두를 남기는 조인을 하고, 한쪽에만 있거나 값이 다른 줄을 종류별로 센다.

## 벤더가 계약을 바꿀 때

연동이 깨지는 날은 대개 우리 코드가 아니라 상대가 바뀐 날이다. 벤더가 CSV에 열 하나를 추가하거나, 상태 코드를 하나 늘리거나, 날짜 형식을 바꾼다. 미리 알려 주면 다행이고, 모르는 채로 오는 경우도 많다.

- 열 순서가 아니라 헤더 이름으로 읽는다. 열이 끝에 추가되면 버티고, 중간에 끼어들어도 버틴다.
- 모르는 필드는 무시하고, 모르는 코드 값은 오류로 세운다. 필드 추가는 대개 안전하지만 코드 값 추가는 의미가 바뀐 것이다.
- 벤더 응답 원본을 그대로 보관한다. 번역 전의 원문이 있어야 "벤더가 이상한 값을 보냈다"와 "우리가 잘못 번역했다"를 가를 수 있다. 개인정보가 섞이면 보관 기간과 마스킹을 함께 정한다.
- 벤더 샌드박스에 계약 테스트를 매일 돌린다. 샌드박스와 운영이 다르게 동작하는 벤더가 있어서 완벽하지 않지만, 형식이 바뀐 것은 대개 잡힌다. 이 이야기는 [SIT와 UAT](/posts/sit-uat-testing)에서 이어진다.

우리가 제공하는 쪽이 될 때 버전을 어떻게 나누고 끝내는지는 [API 버전 관리](/posts/api-versioning)에서 다뤘다.

## 연동이 이상할 때 보는 순서

"벤더로 안 넘어간다"는 문의가 오면 이 순서로 본다.

1. 그 주문이 아웃박스나 큐에 들어갔나. 안 들어갔다면 연동 이전 문제다.
2. 어댑터 로그에 그 주문 번호로 요청이 찍혔나, 응답 상태 코드는 무엇이었나. 요청 하나마다 주문 번호, 시도 횟수, 상태, 걸린 시간을 한 줄로 남겨 두면 여기서 바로 답이 나온다.
3. DLQ에 있나. 있다면 사유(`400 E_ZIP`)가 원인을 말해 준다.
4. 벤더 쪽에서는 받았나. 벤더 조회 API나 담당자에게 우리 참조 번호로 묻는다. 우리는 실패, 벤더는 성공이라면 타임아웃 뒤 상황이다.
5. 특정 상품이나 매장만 안 넘어가나. 그렇다면 마스터 데이터 매핑이 빠진 것이다.

모든 요청이 한꺼번에 실패하기 시작했다면 순서가 다르다. 인증서·키 만료, 벤더 쪽 IP 허용 목록, 벤더 점검 공지를 먼저 확인한다. 그 시각에 우리가 배포한 것이 있는지도 본다.

## 남의 시스템은 우리 말로 감싸고, 매일 맞춰 본다

연동은 방식(동기, 메시지, 파일)을 고르는 데서 시작하지만, 오래 버티게 하는 건 그다음이다. 벤더의 코드표와 형식은 어댑터 안에 가두고, 타임아웃은 "모름"으로 다루고, 다시 보낼 때는 중복을 걸러 줄 장치를 확인하고, 받은 것은 더 새 것만 덮어쓴다. 그래도 남는 어긋남은 대사가 잡는다. 이 연동이 새 나라로 넓어질 때 무엇이 더 붙는지는 [다음 글](/posts/global-rollout-localization)에서 본다.

## 면접에서 나올 만한 질문

### 외부 시스템과 연동할 때 동기 API, 메시지, 파일 배치 중 무엇을 고르나요?

결과가 그 자리에서 필요한지와 상대가 무엇을 지원하는지로 고른다. 사용자가 기다리는 요청이면 동기 API, 나중에 처리돼도 되면 메시지로 넘겨 벤더 장애가 우리 요청으로 번지지 않게 한다. 대량이거나 상대가 파일만 받으면 파일 배치를 쓰고, 실무에서는 접수는 메시지, 상태는 웹훅, 하루치 전체는 파일로 받아 맞춰 보는 식으로 섞어 쓴다.

### 부패 방지 계층은 연동에서 구체적으로 무엇을 하나요?

벤더의 코드표, 날짜·금액 형식, 단어의 의미를 경계에서 우리 모델로 번역해서 도메인 코드가 벤더 형식을 모르게 한다. 모르는 코드 값은 기본값으로 뭉개지 않고 오류로 세운다. 상품·매장 코드 같은 마스터 데이터 매핑도 여기서 다루고, 덕분에 벤더를 바꾸거나 형식이 바뀌어도 어댑터만 고친다.

### 벤더 API가 타임아웃 났을 때 다시 보내도 되나요?

벤더가 중복을 걸러 줄 때만 된다. 타임아웃은 요청이 처리됐는지 모른다는 뜻이라, 걸러 주는 장치 없이 다시 보내면 중복 접수가 생긴다. 멱등 키를 받는 벤더면 같은 키로 다시 보내고, 아니면 참조 번호로 먼저 조회하거나 참조 번호 유니크 제약을 요청하고, 둘 다 안 되면 보류 상태로 두고 대사로 확정한다.

### 벤더가 보낸 상태 이벤트가 순서가 뒤바뀌어 오면 어떻게 저장하나요?

벤더가 상태를 정한 시각이나 순번을 같이 저장하고, 더 새 것일 때만 덮어쓴다. PostgreSQL이라면 `ON CONFLICT DO UPDATE ... WHERE` 조건으로 한 문장에 처리할 수 있고, 중복은 아무 변화 없이 지나간다. 벤더 시계를 믿기 어렵거나 사건마다 id가 오면 처리한 사건 id를 저장하는 인박스 테이블이 더 단단하다.

### 재시도를 잘 갖췄는데 대사는 왜 필요한가요?

재시도로는 막을 수 없는 어긋남이 있기 때문이다. 벤더 담당자가 화면에서 직접 바꾼 것, 사라진 웹훅, 사람이 DB를 고친 것은 재시도 경로를 거치지 않는다. 정해진 주기로 양쪽 전체를 비교해서 한쪽에만 있거나 값이 다른 건을 종류별로 찾고, 결과를 지표로 남겨 같은 종류가 반복되면 버그로 다룬다.

### 대사에서 매일 밤 몇 건씩 같은 어긋남이 나왔다가 다음 날 사라집니다. 무엇을 의심하나요?

날짜 경계를 먼저 의심한다. 자정 직전 건이 벤더의 다음 날 파일에 실리거나, 한쪽은 UTC, 한쪽은 현지 시각으로 하루를 자르면 그 시간대의 건이 매일 한쪽에만 있는 것처럼 보인다. 비교 구간을 앞뒤로 겹치게 하거나 하루 늦게 한 번 더 비교하고, 양쪽이 하루를 어느 시간대로 자르는지 확인한다.

### 벤더가 예고 없이 CSV 형식을 바꾸면 어떻게 버티나요?

열 순서가 아니라 헤더 이름으로 읽어서 열 추가에는 버티게 하고, 모르는 코드 값은 오류로 세워 의미 변화를 놓치지 않게 한다. 번역 전 원문을 보관해 벤더 문제인지 우리 번역 문제인지 가를 수 있게 하고, 트레일러의 건수·합계로 파일이 온전한지 확인한다. 벤더 샌드박스에 매일 계약 테스트를 돌리면 운영 파일이 바뀌기 전에 잡히는 경우도 많다.
