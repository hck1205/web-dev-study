<EasyIntro>
  Git 훅은 Git이 일을 하는 특정 순간마다 저절로 불러 주는 작은 프로그램이다. 커밋하기 직전, 커밋 메시지를 적은 직후, 다른 컴퓨터로 올리기 직전 같은 순간이다. 이 프로그램이 "안 된다"고 답하면 Git은 하던 일을 멈춘다.

  학교 정문에 선 선생님을 떠올리면 쉽다. 교실 문 앞에서 내가 스스로 하는 복장 점검은 편하지만, 마음만 먹으면 건너뛸 수 있다. 정문에 선 선생님의 점검은 누구도 건너뛸 수 없다.

  내 컴퓨터에서 도는 훅이 교실 문 앞 점검이다. 실수를 빨리 알려 주지만 한 줄 명령으로 꺼진다. 게다가 훅 파일은 저장소에 같이 올라가지 않아서, 친구들 컴퓨터에는 없을 수도 있다.

  서버에서 도는 훅이 정문 점검이다. 팀이 꼭 지켜야 하는 규칙은 결국 서버와 자동 검사 쪽에 한 번 더 둔다. 내 컴퓨터의 훅은 빨리 알려 주는 도우미로, 서버 쪽 검사는 최종 판정으로 나눠 쓰는 게 요령이다.

팀에서 커밋 전에 줄 끝 공백과 비밀 키를 검사하는 pre-commit 훅을 만들었다. 내 컴퓨터에서는 잘 막힌다. 그런데 다음 주 리뷰에 올라온 PR에 AWS 키가 그대로 들어 있었다. 올린 사람에게 물어보니 훅이 뭔지 모른다고 했다. 그 사람 컴퓨터의 `.git/hooks`에는 `.sample` 파일만 있었다.

훅을 만들어 두기만 하면 모두에게 적용될 거라고 생각하기 쉽다. 실제로는 그렇지 않다. 이 글은 Git 훅이 어디에 있고 언제 도는지, 왜 저장소에 같이 올라가지 않는지, 팀이 같은 훅을 쓰게 하는 방법(`core.hooksPath`, husky, pre-commit 프레임워크), 그리고 클라이언트 훅으로는 끝까지 막을 수 없어서 서버 훅과 CI가 필요한 이유를 차례로 본다. 실습은 Ubuntu 24.04의 Git 2.43으로 했다. bisect나 worktree 같은 다른 도구는 [알아 두면 편한 Git 기능](/posts/git-tips-advanced)에서 다뤘다.

## 훅은 정해진 이름의 실행 파일일 뿐이다

`git init`을 하면 `.git/hooks/` 폴더에 예제가 들어 있다.

```bash
# 새 저장소를 만들고 훅 폴더를 본다
git init -q -b main app && cd app
ls .git/hooks
```

```text
applypatch-msg.sample
commit-msg.sample
fsmonitor-watchman.sample
post-update.sample
pre-applypatch.sample
pre-commit.sample
pre-merge-commit.sample
pre-push.sample
pre-rebase.sample
pre-receive.sample
prepare-commit-msg.sample
push-to-checkout.sample
sendemail-validate.sample
update.sample
```

`.sample`을 뗀 이름의 실행 파일이 있으면 Git은 그 시점에 그 파일을 실행한다. 언어는 상관없다. 첫 줄의 shebang(`#!/bin/sh`, `#!/usr/bin/env python3`)대로 돈다. 규칙은 몇 가지뿐이다.

- 이름이 정확해야 한다. `pre-commit.sh`처럼 확장자를 붙이면 Git은 찾지 못한다.
- 실행 권한이 있어야 한다. 없으면 `hint: The '.git/hooks/pre-commit' hook was ignored because it's not set as executable.`라는 안내만 내고 건너뛴다.
- 이름이 `pre-`로 시작하는 훅 대부분은 종료 코드로 결과를 정한다. 0이 아니면 Git이 하던 일을 멈춘다. `post-`로 시작하는 훅은 일이 끝난 뒤에 돌아서 결과를 바꾸지 못한다.
- 비 bare 저장소에서는 작업 트리 맨 위 폴더에서 실행된다. 그래서 훅 안에서 상대 경로를 써도 된다.

```bash
# 가장 단순한 훅. 커밋할 때마다 한 줄을 찍는다
cat > .git/hooks/pre-commit <<'EOF'
#!/bin/sh
echo "local hook ran"
EOF
chmod +x .git/hooks/pre-commit
echo hi > a.txt && git add a.txt && git commit -m "init"
```

```text
local hook ran
[main (root-commit) 5049509] init
 1 file changed, 1 insertion(+)
 create mode 100644 a.txt
```

## .git/hooks는 왜 같이 올라가지 않나

방금 훅 파일을 만들었지만 `git status --short`는 아무것도 보여 주지 않는다. `.git/` 폴더 안은 Git이 관리하는 데이터라서 추적 대상이 아니다. 커밋에도, 푸시에도, clone에도 들어가지 않는다.

일부러 그렇게 만들었다. 훅은 내 컴퓨터에서 내 권한으로 도는 임의의 프로그램이다. clone만 했는데 남이 넣어 둔 스크립트가 자동으로 실행된다면, 저장소 하나 받는 일이 낯선 실행 파일을 더블클릭하는 일과 같아진다. 그래서 Git은 훅을 "각자 자기 컴퓨터에 직접 설치하는 것"으로 둔다.

처음 장면의 원인이 이거다. 내가 만든 훅은 내 `.git/hooks`에만 있었다. 팀원이 clone한 저장소에는 예제 파일만 있었다. 훅을 공유하려면 저장소 안 일반 폴더에 훅을 두고, 각자 그 폴더를 훅 폴더로 쓰겠다고 한 번 설정해야 한다. 방법은 뒤에서 본다.

## pre-commit은 스테이징된 것만 본다

pre-commit은 커밋 메시지를 묻기 전에 돈다. 인자가 없어서 "무엇을 검사할지"는 훅이 직접 정한다. 이때 작업 폴더 파일을 그대로 읽으면 안 된다. 커밋에 들어가는 건 스테이징 영역(인덱스)의 내용이고, 작업 폴더에는 아직 `git add`하지 않은 변경이 섞여 있을 수 있다. 그래서 `git diff --cached`로 인덱스와 HEAD의 차이만 본다. 스테이징 영역이 무엇인지는 [스테이징 영역 글](/posts/git-staging-area)에 있다.

훅 폴더를 저장소 안에 만들고 두 가지를 검사해 본다. 하나는 Git이 기본으로 주는 공백 검사(`--check`)이고, 다른 하나는 AWS 액세스 키 모양의 문자열이다.

```bash
# 저장소 안에 훅 폴더를 만든다 (커밋해서 공유할 폴더)
mkdir -p .githooks
cat > .githooks/pre-commit <<'EOF'
#!/bin/sh
# pre-commit: 스테이징된 변경만 검사한다
# 1) 줄 끝 공백, 충돌 표시(<<<<<<<) 같은 실수
if ! git diff --cached --check; then
  echo "pre-commit: 공백 오류나 충돌 표시가 있다" >&2
  exit 1
fi
# 2) 비밀 키처럼 보이는 문자열 (새로 더한 줄만)
if git diff --cached -U0 | grep -qE '^\+.*AKIA[0-9A-Z]{16}'; then
  echo "pre-commit: AWS 액세스 키처럼 보이는 값이 있다" >&2
  exit 1
fi
EOF
chmod +x .githooks/pre-commit
git config core.hooksPath .githooks   # 이 저장소는 .githooks를 훅 폴더로 쓴다
```

줄 끝에 공백이 있는 파일을 커밋하면 이렇게 막힌다.

```text
b.js:1: trailing whitespace.
+const a = 1;   
pre-commit: 공백 오류나 충돌 표시가 있다
```

공백을 지우고 키를 넣으면 두 번째 검사에 걸린다.

```text
pre-commit: AWS 액세스 키처럼 보이는 값이 있다
```

둘 다 종료 코드 1이고 커밋은 만들어지지 않았다. 볼 곳은 훅이 표준 에러로 찍은 마지막 줄이다. Git 자체는 "훅이 실패했다"는 말을 따로 하지 않아서, 훅이 이유를 직접 적어 줘야 사용자가 무엇을 고칠지 안다.

여기서 흔히 하는 실수가 둘 있다. 하나는 린터를 `eslint .`처럼 프로젝트 전체에 돌리는 것이다. 파일이 많아지면 커밋마다 수십 초가 걸리고, 그 순간부터 사람들이 훅을 끄기 시작한다. 바뀐 파일만 넘기면 된다(`git diff --cached --name-only --diff-filter=ACM`). 다른 하나는 일부만 스테이징한 파일을 작업 폴더 기준으로 검사하는 것이다. `git add -p`로 절반만 올린 파일을 포매터가 고치고 다시 `git add`하면, 올리지 않으려던 절반까지 커밋에 들어간다. JavaScript 쪽의 lint-staged는 스테이징되지 않은 변경을 잠시 숨겨 두고 스테이징된 내용만 검사·수정한 뒤 되돌려 놓는 방식으로 이 문제를 피한다.

## commit-msg는 메시지 파일 하나를 받는다

commit-msg는 메시지를 저장한 뒤에 돈다. 인자는 메시지가 담긴 파일 경로 하나다.

```bash
# 인자로 무엇이 오는지 찍어 본다
cat > .githooks/commit-msg <<'EOF'
#!/bin/sh
echo "commit-msg: 메시지 파일은 $1" >&2
EOF
chmod +x .githooks/commit-msg
git commit -qam "fix: z"
```

```text
commit-msg: 메시지 파일은 .git/COMMIT_EDITMSG
```

훅이 이 파일을 고쳐 쓰면 고친 내용이 커밋 메시지가 된다. 이슈 번호를 브랜치 이름에서 뽑아 붙이는 훅이 이 방식이다. 메시지 틀을 미리 채우는 일은 그보다 앞에 도는 prepare-commit-msg가 맡는다. Conventional Commits 형식을 검사하는 셸 훅은 [알아 두면 편한 Git 기능](/posts/git-tips-advanced)에 실제 출력과 함께 있으니, 여기서는 검사 규칙 자체를 직접 짜 본다. 실무 규칙에는 예외가 꼭 붙는다. `git merge`가 만드는 "Merge branch …", `git revert`의 "Revert "…"", `git commit --fixup`의 "fixup! …"까지 막으면 평소 쓰는 명령이 다 깨진다.

## pre-push는 무엇을 어디로 올리는지 표준 입력으로 받는다

pre-push는 원격과 통신하기 직전에 돈다. 인자 두 개(원격 이름, URL)와 함께, 올릴 ref마다 한 줄씩 표준 입력이 들어온다. 형식은 `<로컬 ref> <로컬 SHA> <원격 ref> <원격 SHA>`이고, 원격에 아직 없는 브랜치면 원격 SHA가 0 40개다.

```bash
# main으로 직접 푸시하는 것을 막는 pre-push
cat > .githooks/pre-push <<'EOF'
#!/bin/sh
remote="$1"; url="$2"
echo "pre-push: remote=$remote url=$url" >&2
while read local_ref local_sha remote_ref remote_sha; do
  echo "pre-push: $local_ref $local_sha -> $remote_ref $remote_sha" >&2
  if [ "$remote_ref" = "refs/heads/main" ]; then
    echo "pre-push: main에는 직접 푸시하지 않는다. PR을 연다" >&2
    exit 1
  fi
done
exit 0
EOF
chmod +x .githooks/pre-push
git push origin main
```

```text
pre-push: remote=origin url=../server.git
pre-push: refs/heads/main 30fbdd845756130d5fefa92b09f1fb617f5d883f -> refs/heads/main 0000000000000000000000000000000000000000
pre-push: main에는 직접 푸시하지 않는다. PR을 연다
error: failed to push some refs to '../server.git'
```

pre-push는 커밋보다 드물게 돌기 때문에 단위 테스트나 타입 검사처럼 몇 초 걸리는 일을 두기 좋다. pre-commit에 다 넣으면 커밋이 무거워지고, pre-push에 다 넣으면 실수를 늦게 안다. 빠른 검사(포매팅, 비밀 값)는 pre-commit, 느린 검사(테스트)는 pre-push, 전체 검사는 CI로 나누는 게 무난하다.

## post-checkout은 결과를 바꾸지 못한다

post-checkout은 `git checkout`이나 `git switch`가 끝난 뒤 돈다. 인자는 이전 HEAD, 새 HEAD, 그리고 브랜치를 바꿨으면 1, 파일만 꺼냈으면 0이다. 이미 체크아웃이 끝났으니 종료 코드로 되돌릴 수 없고, 알림이나 뒷정리를 맡는다. 잠금 파일이 바뀐 브랜치로 넘어가면 의존성을 다시 깔라고 알려 주는 훅을 만들어 본다.

```bash
cat > .githooks/post-checkout <<'EOF'
#!/bin/sh
# 인자: <이전 HEAD> <새 HEAD> <1=브랜치 전환, 0=파일 체크아웃>
prev="$1"; new="$2"; is_branch="$3"
[ "$is_branch" = "1" ] || exit 0
if git diff --quiet "$prev" "$new" -- package-lock.json; then exit 0; fi
echo "post-checkout: package-lock.json이 바뀌었다. npm ci를 다시 돌린다" >&2
EOF
chmod +x .githooks/post-checkout
# 이 훅과 잠금 파일은 feat/x 브랜치에만 커밋했다
git checkout main
git checkout feat/x
git checkout -- a.txt
```

```text
Switched to branch 'main'
Switched to branch 'feat/x'
post-checkout: package-lock.json이 바뀌었다. npm ci를 다시 돌린다
```

세 명령 중 두 번째에서만 메시지가 나왔다. 세 번째는 파일 체크아웃이라 세 번째 인자가 0이어서 바로 끝났다. 첫 번째가 조용한 이유는 더 흥미롭다. 이 훅 파일은 `feat/x`에만 커밋돼 있었고, `main`으로 넘어가는 순간 작업 폴더의 `.githooks/post-checkout`이 사라졌다. Git은 체크아웃이 끝난 뒤의 훅 폴더를 보므로 실행할 파일이 없었다. 훅을 저장소 안에 두면 브랜치마다 훅이 달라질 수 있다는 뜻이다. 훅 변경은 기본 브랜치에 먼저 넣고, 오래된 브랜치에서는 훅이 다르게 돌 수 있다는 걸 염두에 둔다.

## 팀이 같은 훅을 쓰게 하는 방법

공유 방법은 결국 "저장소 안 폴더에 훅을 두고, 각자 Git이 그 폴더를 보게 만든다"로 같다. 차이는 그 마지막 설정을 누가 해 주느냐와, 훅 안에서 무엇을 실행하느냐다. 아래 그림의 점은 설정이 흘러가는 방향이다.

가장 단순한 방법은 앞에서 쓴 `git config core.hooksPath .githooks`(Git 2.9부터)다. 의존성이 없고 어떤 언어 프로젝트에서도 된다. 대신 clone할 때마다 각자 한 번 실행해야 한다. README에 적어 두거나 `make setup` 같은 준비 스크립트에 넣는다. 잊는 사람이 반드시 생긴다.

husky는 이 한 줄을 `npm install`에 묶는다. husky 9.1.7로 해 보면(`npx husky init`이 만드는 `.husky/pre-commit`의 기본 내용은 `npm test` 한 줄이다) 무엇을 하는지 바로 보인다.

```bash
# husky를 깔고 초기화한다
npm i -D husky
npx husky init
git config core.hooksPath      # 무엇으로 바뀌었나
ls .husky
ls .husky/_ | head -6
grep '"prepare"' package.json
```

```text
.husky/_
_
pre-commit
applypatch-msg
commit-msg
h
husky.sh
post-applypatch
post-checkout
    "prepare": "husky"
```

`core.hooksPath`가 `.husky/_`로 바뀌었고, 그 안에 모든 훅 이름의 작은 파일이 생겼다. 각 파일은 공용 스크립트 `h`를 부르고, `h`는 같은 이름의 `.husky/pre-commit` 같은 사용자 파일이 있으면 그걸 `sh -e`로 실행한다. `.husky/_`는 자체 `.gitignore`로 커밋에서 빠지고, 팀이 커밋하는 건 `.husky/pre-commit` 같은 사용자 파일뿐이다. `package.json`의 `prepare` 스크립트가 `npm install` 때마다 `husky`를 실행해 이 설정을 되살린다. 그래서 clone 후 `npm install`만 하면 된다. `h` 스크립트를 열어 보면 `HUSKY=0`이면 아무것도 하지 않고 끝나는 줄이 있다. CI나 배포 이미지에서 훅 설치를 끄는 스위치다.

pre-commit 프레임워크(Python 패키지 이름도 `pre-commit`이다)는 언어와 상관없이 쓰인다. `.pre-commit-config.yaml`에 "어느 저장소의 어느 검사를 몇 버전으로 쓸지"를 적고, `pre-commit install`이 `.git/hooks/pre-commit`에 진입 스크립트를 깐다. 검사 도구를 각자 설치할 필요 없이 프레임워크가 버전을 고정해 받아 오는 게 장점이고, `pre-commit run --all-files`로 CI에서도 같은 검사를 그대로 돌릴 수 있다. 다만 `pre-commit install`도 각자 한 번 해야 한다는 점은 `core.hooksPath`와 같다.

```yaml
# .pre-commit-config.yaml 예시: 버전을 rev로 고정한다
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: trailing-whitespace
      - id: check-merge-conflict
      - id: detect-private-key
```

lefthook처럼 YAML 하나로 여러 검사를 병렬로 돌리는 도구도 있다. 어느 것을 고르든 하는 일은 훅 폴더를 채우는 것이고, 고르는 기준은 프로젝트에 이미 있는 런타임이다. Node 프로젝트면 husky와 lint-staged, Python이나 여러 언어가 섞인 저장소면 pre-commit 프레임워크, 의존성을 하나도 늘리고 싶지 않으면 `core.hooksPath`다.

## --no-verify 한 줄이면 끝난다

공유를 아무리 잘해도 로컬 훅은 개발자가 끌 수 있다.

```bash
# 키가 든 커밋을 훅을 건너뛰고 만든다
git commit --no-verify -m "feat: add b"
```

```text
[main 1dc58be] feat: add b
 1 file changed, 2 insertions(+)
 create mode 100644 b.js
```

`--no-verify`(줄여서 `-n`)는 커밋에서 pre-commit과 commit-msg를, 푸시에서는 pre-push를 건너뛴다. husky 환경이면 `HUSKY=0 git commit`도 된다. `core.hooksPath`를 지우거나, Git 클라이언트가 훅을 지원하지 않거나, 다른 컴퓨터에서 커밋하면 애초에 돌지 않는다. GitHub 웹에서 파일을 고쳐 커밋하는 경우도 로컬 훅과는 무관하다.

이건 결함이 아니라 설계다. 급한 핫픽스, 훅 자체가 망가졌을 때, 작업 중간 저장 같은 상황에서 개발자가 탈출할 길이 있어야 한다. 그래서 로컬 훅은 빨리 알려 주는 장치로 보고, 반드시 지켜야 할 규칙은 같은 검사를 CI에서 다시 돌린 뒤 브랜치 보호 규칙에서 그 결과를 필수로 건다. 훅과 CI가 같은 스크립트를 부르게 해 두면 규칙이 두 곳에서 따로 놀지 않는다. 비밀 키처럼 "한 번 올라가면 끝"인 값은 서버 쪽 푸시 보호까지 켠다. 이미 올라간 뒤 대응은 [커밋에 들어가면 안 되는 것](/posts/git-large-files-secrets)에 있다.

## 서버 훅: 건너뛸 수 없는 마지막 문

서버 훅은 푸시를 받는 저장소(보통 bare 저장소)의 `hooks/` 폴더에서 돈다. 클라이언트는 이 훅을 끌 수 없다. 실험을 위해 로컬에 bare 저장소를 만들고 세 훅을 넣었다.

- pre-receive: 푸시 한 번에 한 번 돈다. 표준 입력으로 ref마다 `<이전 SHA> <새 SHA> <ref>`가 들어온다. 0이 아니면 그 푸시의 ref가 하나도 반영되지 않는다.
- update: ref마다 한 번 돈다. 인자는 `<ref> <이전 SHA> <새 SHA>`다. 0이 아니면 그 ref만 거절된다.
- post-receive, post-update: 반영이 끝난 뒤 돈다. post-receive는 pre-receive와 같은 표준 입력을, post-update는 바뀐 ref 이름들을 인자로 받는다. 둘 다 결과를 바꾸지 못한다.

```bash
git init -q --bare -b main server.git
# pre-receive: 새로 들어오는 커밋 제목이 규칙에 맞는지 본다
cat > server.git/hooks/pre-receive <<'EOF'
#!/bin/sh
zero=0000000000000000000000000000000000000000
while read old new ref; do
  [ "$new" = "$zero" ] && continue          # 브랜치 삭제는 건너뛴다
  if [ "$old" = "$zero" ]; then range="$new"; else range="$old..$new"; fi
  for c in $(git rev-list "$range" --not --all); do   # 서버에 처음 들어오는 커밋만
    subject=$(git log -1 --format=%s "$c")
    if ! echo "$subject" | grep -qE '^(feat|fix|docs|refactor|test|chore)(\(.+\))?: .+'; then
      echo "pre-receive: $c 제목이 규칙에 맞지 않는다: \"$subject\"" >&2
      exit 1
    fi
  done
done
EOF
# update: main의 강제 푸시를 막는다
cat > server.git/hooks/update <<'EOF'
#!/bin/sh
ref="$1"; old="$2"; new="$3"
zero=0000000000000000000000000000000000000000
if [ "$ref" = "refs/heads/main" ] && [ "$old" != "$zero" ]; then
  if ! git merge-base --is-ancestor "$old" "$new"; then
    echo "update: main은 강제 푸시할 수 없다" >&2
    exit 1
  fi
fi
EOF
chmod +x server.git/hooks/pre-receive server.git/hooks/update
```

`--no-verify`로 로컬 pre-push를 건너뛰고 규칙에 맞지 않는 커밋을 올렸다.

```text
remote: pre-receive: 8c044ed1ea8bcc6f80b6b96c906fef206ba64b5d 제목이 규칙에 맞지 않는다: "update a"        
To ../server.git
 ! [remote rejected] main -> main (pre-receive hook declined)
error: failed to push some refs to '../server.git'
```

서버 훅이 표준 에러로 찍은 글은 `remote:`가 붙어 클라이언트 화면에 그대로 나온다. 로컬 우회는 여기서 소용이 없다. 다음은 강제 푸시 하나와 새 브랜치 하나를 한 번에 올린 결과다.

```bash
git push --no-verify --force origin feat/z feat/y:main
```

```text
remote: update: main은 강제 푸시할 수 없다        
remote: error: hook declined to update refs/heads/main        
remote: post-receive: refs/heads/feat/z 가 668a2e2 로 바뀌었다. 배포 알림을 보낸다        
remote: post-update: refs/heads/feat/z        
To ../server.git
 * [new branch]      feat/z -> feat/z
 ! [remote rejected] feat/y -> main (hook declined)
error: failed to push some refs to '../server.git'
```

`update`가 거절한 `main`만 빠지고 `feat/z`는 들어갔다. pre-receive에서 거절했다면 둘 다 들어가지 않았을 것이다. "이 푸시는 통째로 받거나 통째로 버린다"가 필요하면 pre-receive, "규칙에 걸린 브랜치만 막는다"면 update를 쓴다. post-receive와 post-update는 반영된 ref에 대해서만 돌았다. post-update는 원래 정적 HTTP로 저장소를 내보낼 때 `git update-server-info`를 돌리는 용도로 쓰였고, 요즘은 표준 입력으로 SHA까지 받는 post-receive를 주로 쓴다.

GitHub.com과 GitLab.com 같은 호스팅 서비스에서는 이 폴더에 직접 스크립트를 넣을 수 없다. GitHub Enterprise Server와 자체 운영 GitLab은 관리자가 pre-receive 계열 훅을 등록할 수 있다. 호스팅 서비스에서는 같은 역할을 브랜치 보호 규칙과 룰셋(강제 푸시 금지, 리뷰 필수, 필수 상태 검사), 비밀 값 푸시 보호, 웹훅이 나눠 맡는다. 저장소 권한과 보호 규칙 설계는 [저장소 운영 규칙 글](/posts/github-repo-governance)에서 다뤘다.

## 훅이 미움받지 않게 운영하기

훅은 사람이 매일 부딪치는 장치라서, 느리거나 엉뚱하게 실패하면 바로 꺼진다. 현장에서 자주 보는 증상과 원인은 이렇다.

"내 컴퓨터에서만 훅이 안 돈다"는 거의 설정 문제다. `git config core.hooksPath`로 어디를 보는지 먼저 확인하고, 그 폴더의 파일에 실행 권한이 있는지(`ls -l`), 커밋된 권한이 `100755`인지 본다. 앞의 실행 권한 hint는 `advice.ignoredHook` 설정을 꺼 두면 안 보이기도 한다.

"터미널에서는 되는데 IDE나 GUI 클라이언트에서 커밋하면 `command not found`가 난다"는 PATH 문제다. GUI 앱은 셸 설정 파일을 읽지 않고 시작해서 nvm으로 깐 `node`나 `npx`를 찾지 못한다. husky는 이런 경우를 위해 `~/.config/husky/init.sh`를 먼저 읽는다. 앞의 `h` 스크립트에 그 줄이 있다.

"커밋이 10초씩 걸린다"면 검사 범위를 본다. 바뀐 파일만 검사하고, 테스트는 pre-push나 CI로 옮긴다. `time git commit`으로 재 보면 훅이 빈 커밋에도 얼마를 쓰는지 바로 나온다.

"훅이 파일을 고쳤는데 커밋에 안 들어갔다"는 pre-commit 안에서 포매터를 돌리고 `git add`를 하지 않은 경우다. 반대로 `git add .`를 하면 스테이징하지 않으려던 파일까지 들어간다. 바뀐 파일 목록만 다시 add하거나 lint-staged에 맡긴다.

윈도에서는 Git for Windows가 함께 주는 sh로 훅을 돌리므로 `#!/bin/sh` 스크립트가 대체로 그대로 돈다. 다만 저장소를 CRLF로 체크아웃하면 shebang 줄 끝에 `\r`이 붙어 실행이 안 될 수 있다. 훅 파일은 `.gitattributes`에서 `eol=lf`로 고정한다.

## 로컬 훅은 도우미, 판정은 서버가 한다

훅은 Git이 정해진 순간에 부르는 실행 파일이고, `.git/hooks`는 보안상 저장소와 함께 퍼지지 않는다. 팀이 공유하려면 훅을 저장소 안 폴더에 두고 `core.hooksPath`, husky, pre-commit 프레임워크 중 하나로 각자 연결한다. 그래도 로컬 훅은 `--no-verify` 한 번에 꺼지므로 빠른 피드백용으로 쓰고, 지켜야 하는 규칙은 서버 훅이나 브랜치 보호 규칙과 CI에서 다시 검사한다. 처음 장면의 AWS 키는 로컬 훅이 아니라 서버 쪽 푸시 보호와 CI 검사가 막았어야 했다.

## 면접에서 나올 만한 질문

### Git 훅은 무엇이고 어떻게 동작하나요?

Git이 커밋, 푸시, 체크아웃 같은 특정 시점에 실행하는 스크립트다. 훅 폴더(기본 `.git/hooks`)에 정해진 이름의 실행 파일을 두면 된다. `pre-`로 시작하는 훅은 종료 코드가 0이 아니면 그 작업을 멈추고, `post-` 훅은 작업이 끝난 뒤 알림이나 뒷정리를 한다. 언어는 shebang으로 정하므로 셸이든 Python이든 상관없다.

### .git/hooks에 넣은 훅이 왜 팀원에게 적용되지 않나요?

`.git/` 안은 추적 대상이 아니라서 커밋·푸시·clone에 포함되지 않기 때문이다. clone만으로 남의 스크립트가 자동 실행되면 위험하니 일부러 그렇게 설계됐다. 공유하려면 훅을 저장소 안 일반 폴더에 커밋하고 각자 `core.hooksPath`로 연결하거나, husky처럼 `npm install` 때 자동으로 설정해 주는 도구를 쓴다.

### pre-commit, commit-msg, pre-push에는 각각 어떤 검사를 두나요?

빨리 끝나는 것부터 앞에 둔다. pre-commit에는 스테이징된 파일의 포매팅, 린트, 비밀 값 검사를 두고, commit-msg에는 메시지 형식 검사를 둔다. pre-push에는 단위 테스트나 타입 검사처럼 몇 초 걸리는 검사를 둔다. 전체 테스트는 CI가 맡는다. pre-commit이 느려지면 사람들이 훅을 끄기 시작한다.

### pre-commit 훅에서 작업 폴더 파일을 그대로 검사하면 무엇이 문제인가요?

커밋되는 건 인덱스의 내용인데 작업 폴더에는 스테이징하지 않은 변경이 섞여 있어서, 검사 결과와 실제 커밋이 어긋난다. `git add -p`로 일부만 올린 파일을 포매터가 고치고 다시 add하면 올리지 않으려던 부분까지 커밋된다. `git diff --cached`로 스테이징된 것만 보거나, 스테이징되지 않은 변경을 잠시 숨기고 검사하는 lint-staged 같은 도구를 쓴다.

### 클라이언트 훅만으로 규칙을 강제할 수 있나요?

없다. `git commit --no-verify`로 pre-commit과 commit-msg를, `git push --no-verify`로 pre-push를 건너뛸 수 있고, 설정을 안 했거나 다른 클라이언트를 쓰면 애초에 돌지 않는다. 반드시 지켜야 할 규칙은 같은 검사를 CI에서 다시 돌리고 브랜치 보호 규칙에서 필수 상태 검사로 걸거나, 서버 훅에서 막는다.

### pre-receive와 update 훅은 어떻게 다른가요?

pre-receive는 푸시 한 번에 한 번 돌며 표준 입력으로 모든 ref 변경을 받고, 실패하면 그 푸시의 ref가 하나도 반영되지 않는다. update는 ref마다 한 번 돌며 인자로 ref와 이전·새 SHA를 받고, 실패하면 그 ref만 거절된다. 푸시 전체를 원자적으로 판단해야 하면 pre-receive, 브랜치별 규칙(예: main 강제 푸시 금지)은 update가 편하다.

### GitHub.com처럼 서버 훅을 넣을 수 없는 곳에서는 어떻게 강제하나요?

브랜치 보호 규칙이나 룰셋으로 강제 푸시 금지, 리뷰 필수, 필수 상태 검사를 걸고, 그 상태 검사를 CI가 채운다. 비밀 값은 푸시 보호와 비밀 값 스캐닝으로 막는다. post-receive가 하던 알림은 웹훅이 맡는다. 자체 운영하는 GitHub Enterprise Server나 GitLab이라면 관리자가 pre-receive 훅을 직접 등록할 수도 있다.

### husky는 내부적으로 무엇을 하나요?

husky 9 기준으로 `core.hooksPath`를 `.husky/_`로 바꾸고, 그 안에 모든 훅 이름의 작은 진입 스크립트를 만든다. 진입 스크립트는 `.husky/pre-commit` 같은 사용자 파일이 있으면 그걸 실행한다. `package.json`의 `prepare` 스크립트가 `npm install` 때마다 이 설정을 되살리고, `HUSKY=0`이면 훅을 건너뛴다. 결국 Git의 훅 폴더 설정을 자동화하는 도구다.
