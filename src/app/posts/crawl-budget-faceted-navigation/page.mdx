## 상품은 1만 개인데 주소는 수백만 개

의류 쇼핑몰에 상품이 1만 개쯤 있다. 지난주 올린 신상품 300개가 2주째 구글에 나오지 않는다. Search Console의 페이지 색인 생성 보고서를 열어 보니 신상품 주소 대부분이 "발견됨 - 현재 색인이 생성되지 않음"이다. 구글이 주소는 알지만 아직 가져가지 않았다는 뜻이다.

크롤링 통계 보고서(설정 아래에 있다)를 보면 구글봇은 하루에 꽤 많이 오고 있다. 그런데 서버 접근 로그에서 구글봇 요청만 골라 보면 이야기가 다르다. 이 상황을 흉내 낸 예시 로그 14줄(구글봇 13줄, 일반 사용자 1줄)을 만들어 아래 명령으로 세 봤다. 실제 로그에도 그대로 쓸 수 있는 명령이다.

```bash
# 구글봇 요청 중 쿼리 파라미터가 붙은 주소의 비율
grep 'Googlebot' access.log | awk '{print $7}' \
  | awk '{ if ($0 ~ /\?/) p++; else s++ } END { printf "parameter URLs: %d / %d (%.0f%%)\n", p, p+s, 100*p/(p+s) }'

# 어떤 파라미터가 많이 붙는지
grep 'Googlebot' access.log | awk '{print $7}' | grep -o '[?&][a-z_]*=' | tr -d '?&=' | sort | uniq -c | sort -rn
```

```text
parameter URLs: 9 / 13 (69%)
      8 color
      7 size
      3 sort
      3 brand
      2 price
      1 sessionid
      1 page
```

구글봇이 가져간 13개 중 9개가 `/coats?color=gray&size=m` 같은 필터 주소다. 상품 상세(`/products/10482`)는 3개뿐이다. 필터 버튼마다 `<a href>`로 주소가 붙어 있으니, 구글봇은 그걸 전부 새 페이지로 보고 따라간다.

이 글은 이 상황을 푼다. 크롤 예산이 무엇인지, 패싯 내비게이션과 파라미터가 중복 주소를 얼마나 만드는지 직접 계산하고, canonical·noindex·robots.txt·링크 없애기 중 무엇을 언제 쓰는지, 페이지네이션과 무한 스크롤, 색인 비대와 콘텐츠 정리, 품절·단종 상품 처리까지 본다. canonical과 noindex의 기본, sitemap 규칙은 [SPA와 SEO](/posts/seo-for-spa)에 있으니 여기서는 그 도구들을 큰 사이트에서 고르는 판단을 다룬다. 크롤러를 만드는 쪽에서 본 같은 문제(스파이더 트랩, robots.txt 해석)는 [웹 크롤러 설계 ②](/posts/sd-web-crawler-politeness-dedup)에 있다.

## 크롤 예산은 두 가지로 정해진다

크롤 예산(crawl budget)은 검색 엔진이 한 사이트에서 일정 기간 동안 가져갈 주소의 양이다. 구글 문서는 이걸 두 가지의 조합으로 설명한다.

크롤 용량 한도(crawl capacity limit). 서버를 힘들게 하지 않고 동시에 몇 개를 얼마나 자주 가져갈 수 있느냐다. 응답이 빠르고 오류가 없으면 늘고, 느려지거나 5xx가 늘면 줄어든다. 구글봇은 서버 상태를 보고 스스로 속도를 조절한다. Search Console에 있던 크롤링 속도 제한 도구는 2024년 1월에 없어졌다.

크롤 수요(crawl demand). 가져갈 가치가 있느냐다. 인기 있는 주소(많이 링크되고 많이 검색되는), 오래돼서 다시 볼 때가 된 주소, 그리고 사이트에 있다고 알려진 주소의 양(인지된 재고)이 영향을 준다. 마지막이 중요하다. 중복이나 쓸모없는 주소가 많으면 구글이 아는 "재고"가 부풀어 오르고, 크롤링 시간이 그쪽에 쓰인다.

예산은 대부분의 사이트에는 신경 쓸 문제가 아니다. 구글은 이 주제를 주로 큰 사이트(고유 페이지 100만 개 이상이면서 주 단위로 바뀌는 곳)나, 중간 규모 이상(1만 개 이상)이면서 내용이 매일 바뀌는 사이트, 그리고 "발견됨 - 현재 색인이 생성되지 않음"이 많은 사이트를 위한 것이라고 안내한다. 글 200개짜리 블로그가 새 글이 늦게 색인된다면 원인은 예산이 아니라 품질이나 링크 쪽일 가능성이 크다.

패싯 내비게이션이 있는 쇼핑몰은 상품 수가 적어도 주소 수가 많아 이 범위에 쉽게 들어간다. 다음 절에서 얼마나 많은지 세어 보자.

## 필터 조합을 세어 보면

패싯 내비게이션(faceted navigation)은 상품 목록을 여러 속성(패싯)으로 거르는 UI다. 색, 크기, 브랜드, 가격대 같은 것이다. 사용자에게는 편하지만, 선택마다 주소가 생기면 주소 수는 조합으로 늘어난다.

# 파라미터를 이름순으로 정렬해 같은 조합끼리 묶고, 두 번 이상 크롤링된 것만 본다
grep 'Googlebot' access.log | awk '{print $7}' | grep '?' \
  | perl -ne 'chomp; my ($p,$q)=split /\?/; print "$p?", join("&", sort split /&/, $q), "\n"' \

## 중복 주소가 생기는 다른 길

패싯이 가장 크지만 혼자는 아니다. 같은 내용이 다른 주소로 퍼지는 경로는 대략 이렇다.

- 호스트와 프로토콜: `http`와 `https`, `www`가 있고 없고
- 경로 표기: 끝의 `/`, 대소문자(`/Coats`와 `/coats`), `index.html`
- 추적 파라미터: `utm_*`, `gclid`, 제휴사 ID
- 세션 ID와 장바구니 토큰이 주소에 붙는 오래된 구현
- 정렬과 보기 방식(`view=grid`, `per_page=60`)
- 인쇄용, AMP, 앱 웹뷰용 별도 주소
- 상품 변형: 색만 다른 같은 상품이 각자 주소를 가질 때
- 다른 사이트에 배포한 같은 글(신디케이션)

중복 콘텐츠 자체로 벌을 받지는 않는다. 구글은 속이려는 의도가 없는 중복에 페널티가 없다고 여러 번 밝혔다. 문제는 벌이 아니라 낭비와 분산이다. 같은 페이지를 여러 번 크롤링하느라 예산을 쓰고, 외부 링크와 내부 링크가 여러 주소로 흩어지고, 구글이 대표 주소를 우리 뜻과 다르게 고를 수 있다. Search Console에서 "중복, 사용자가 표시한 표준이 없음"이나 "중복, Google에서 사용자와 다른 표준을 선택함"이 그 신호다.

## 네 가지 도구는 하는 일이 다르다

중복 주소를 다루는 도구는 네 가지다. 헷갈리는 이유는 각자 막는 단계가 다르기 때문이다. 크롤링(가져가기), 색인(검색 결과에 넣기), 신호 합치기(링크 점수를 대표로 모으기) 중 무엇에 작용하는지로 나눠 보면 정리된다.

canonical. "이 페이지의 대표는 저쪽이다"라는 힌트다. 신호를 대표 주소로 모으고 대표만 색인되게 한다. 하지만 구글은 canonical을 읽으려면 그 페이지를 가져와야 한다. 그래서 크롤링은 줄지 않는다. 시간이 지나면 덜 자주 가져가긴 하지만, 수백만 개 주소가 있다면 그 "덜 자주"도 많다. 그리고 내용이 크게 다르면(필터로 상품이 3개만 남은 목록을 전체 목록의 사본이라고 하면) 무시될 수 있다.

noindex. "이 페이지는 검색 결과에 넣지 말라"는 지시다. 확실히 색인에서 빠진다. 하지만 역시 가져가야 읽을 수 있으니 크롤링은 계속된다. 신호를 다른 주소로 모아 주지도 않는다. 그리고 오랫동안 noindex인 페이지는 결국 그 안의 링크도 따라가지 않는 것처럼 다뤄진다고 구글 직원이 설명한 적이 있다. noindex 페이지를 다른 페이지로 가는 통로로 쓰면 안 된다.

robots.txt Disallow. "가져가지 말라"는 요청이다. 크롤링을 줄이는 유일하게 직접적인 도구다. 대신 가져가지 않으니 그 페이지의 canonical도 noindex도 읽지 못한다. 막힌 주소도 외부 링크가 많으면 내용 없이 주소만 색인될 수 있다. 그 주소로 들어온 링크 신호는 대표 주소로 모이지 않는다.

링크를 만들지 않기. 애초에 크롤러가 따라올 `<a href>`를 만들지 않는 것이다. 사이즈 필터를 링크가 아니라 체크박스와 `button`으로 만들고, 결과는 자바스크립트로 그리거나 주소의 해시(`#size=xl`) 뒤에 둔다. 구글은 링크를 따라갈 때 `<a>`의 `href`만 보고 `#` 뒤는 무시하므로, 이런 상태는 새 주소로 보이지 않는다. 다만 사용자가 그 상태를 공유하거나 뒤로 가기로 돌아올 수 있게 하려면 히스토리 처리를 따로 해야 한다.

네 도구가 어느 단계에 작용하는지 그림으로 모아 보면 이렇다. 실선은 그 단계를 확실히 바꾸는 것, 점선은 힌트로만 작용하거나 간접적인 것이다.

그래서 도구를 고를 때 질문은 "무엇을 아끼고 싶은가"다.

- 크롤링을 아끼고 싶고, 그 주소의 신호를 모을 필요가 없으면 robots.txt로 막는다. 내부 정렬·사이즈 필터처럼 외부에서 링크할 일이 거의 없는 주소가 그렇다.
- 이미 색인된 주소를 빼고 싶으면 먼저 noindex를 두고 크롤링을 허락해 빠지는 걸 확인한 뒤, 필요하면 그다음에 robots.txt로 막는다. 순서를 거꾸로 하면 noindex를 영영 못 읽는다.
- 내용이 거의 같고 신호를 대표로 모으고 싶으면 canonical을 쓴다. 추적 파라미터, 색만 다른 상품 변형이 그렇다.
- 크롤러가 알 필요가 없는 상태라면 처음부터 링크를 만들지 않는다. 가장 깔끔하다.

robots.txt의 와일드카드(`*`, `$`)와 가장 긴 규칙이 이기는 해석 규칙은 [웹 크롤러 설계 ②](/posts/sd-web-crawler-politeness-dedup)에서 직접 돌려 봤다. 패턴을 넣기 전에 Search Console의 robots.txt 보고서나 같은 해석기로 상품 상세가 실수로 막히지 않는지 확인한다. `Disallow: /*?`처럼 넓게 쓰면 `?page=2`까지 막혀 2페이지 이후 상품이 발견되지 않는다.

## 필요한 패싯만 색인 대상으로 남긴다

모든 패싯을 막을 필요는 없다. "acme 코트", "남색 코트"처럼 검색 수요가 있는 조합은 오히려 좋은 착륙 페이지다. 구글이 2024년 말에 낸 패싯 내비게이션 안내도 두 갈래로 나눈다. 색인할 필요가 없는 필터 주소는 robots.txt로 크롤링을 막거나 해시(`#`)로 상태를 표현하고, 색인이 필요한 필터 주소는 크롤러가 다루기 좋게 만들라는 것이다. 후자의 요령은 이렇다.

파라미터 구분자는 표준대로 `&`와 `=`를 쓴다. 쉼표나 세미콜론으로 이어 붙이는 자체 형식은 크롤러가 구조를 알아보기 어렵다.

순서를 고정한다. 사용자가 어떤 순서로 눌렀든 서버나 라우터에서 파라미터를 정해진 순서로 정렬해 링크를 만든다. 앞의 계산에서 본 18배가 여기서 사라진다.

```ts
// 필터 상태 → 링크 주소. 항상 같은 순서, 빈 값과 기본값은 뺀다
const FACET_ORDER = ["brand", "color", "price"] as const; // 색인 대상 패싯만, 정해진 순서로

export function facetHref(base: string, state: Record<string, string | undefined>) {
  const params = new URLSearchParams();
  for (const key of FACET_ORDER) {
    const v = state[key];
    if (v) params.set(key, v);
  }
  const qs = params.toString();
  return qs ? `${base}?${qs}` : base;
}

// size, sort는 링크를 만들지 않는다. 버튼으로 상태만 바꾼다
```

색인 대상 깊이를 정한다. 패싯 하나(`/coats?brand=acme`)나 검색량이 확인된 두 개 조합까지만 링크로 만들고, 그보다 깊은 조합은 링크 대신 버튼으로 둔다. 이 기준은 검색어 도구와 Search Console의 실제 검색어로 정한다.

결과가 없는 조합은 404를 준다. 초록색 acme XL 코트가 없는데 "상품이 없습니다" 화면을 200으로 주면 소프트 404가 되고, 그런 주소가 수만 개 생긴다. 결과가 0개인 필터는 아예 링크를 만들지 않고, 직접 들어왔다면 404를 준다.

색인 대상 패싯 페이지에는 고유한 내용을 둔다. 브랜드 페이지라면 브랜드 소개, 고유한 title과 h1이 있어야 목록만 있는 수많은 비슷한 페이지 중 하나로 묻히지 않는다.

Search Console에 있던 "URL 매개변수" 도구로 파라미터별 처리를 지정하던 방법은 2022년에 없어졌다. 지금은 주소 설계와 위의 도구들로 직접 다뤄야 한다.

## Next.js에서 주소 규칙을 강제하기

규칙을 정해도 코드 곳곳에서 링크를 만들다 보면 금방 어긋난다. 그래서 요청이 들어오는 입구에서 한 번 더 정리한다. Next.js 16에서는 요청이 페이지에 닿기 전에 지나가는 `proxy.ts`에서 할 수 있다(15까지는 `middleware.ts`). 동작 순서와 함정은 [Route Handler와 Proxy](/posts/nextjs-route-handlers-proxy)에 있다.

```ts
// proxy.ts — 목록 주소의 파라미터를 정리해 대표 주소로 영구 이동시킨다
import { NextResponse, type NextRequest } from "next/server";

const KEEP = ["brand", "color", "price", "size", "sort", "page"]; // 앱이 아는 파라미터만
const DROP = /^(utm_|gclid$|fbclid$|sessionid$)/;

export function proxy(request: NextRequest) {
  const url = request.nextUrl;
  const entries = [...url.searchParams].filter(([k, v]) => v !== "" && !DROP.test(k) && KEEP.includes(k));
  entries.sort(([a], [b]) => KEEP.indexOf(a) - KEEP.indexOf(b)); // 순서 고정
  if (entries.find(([k, v]) => k === "page" && v === "1")) {
    entries.splice(entries.findIndex(([k]) => k === "page"), 1); // page=1은 기본값이라 뺀다
  }

  const normalized = new URLSearchParams(entries).toString();
  if (normalized === url.searchParams.toString()) return NextResponse.next();

  const target = url.clone();
  target.search = normalized;
  return NextResponse.redirect(target, 301);
}

export const config = { matcher: ["/coats/:path*", "/shoes/:path*"] };
```

이렇게 하면 `?size=m&color=gray&utm_source=x`로 들어온 요청은 `?color=gray&size=m`으로 301 된다. 순서만 다른 주소와 추적 파라미터가 붙은 주소가 크롤러에게 같은 주소로 모인다. 분석 도구가 `utm_` 값을 읽어야 한다면 리디렉션 전에 서버에서 기록하거나, 클라이언트 분석 스크립트가 첫 요청의 주소를 읽게 한다. 리디렉션하면 그 값은 주소에서 사라진다.

남은 파라미터 중 무엇을 색인할지는 페이지의 메타데이터에서 정한다.

```tsx
// app/coats/page.tsx
import type { Metadata } from "next";

type Props = { searchParams: Promise<Record<string, string | undefined>> };

export async function generateMetadata({ searchParams }: Props): Promise<Metadata> {
  const { brand, color, size, sort, page } = await searchParams;
  const facetCount = [brand, color].filter(Boolean).length;
  const indexable = !size && !sort && facetCount <= 1; // 색인 대상: 패싯 하나까지, 사이즈·정렬 없음

  const params = new URLSearchParams();
  if (brand) params.set("brand", brand);
  if (color) params.set("color", color);
  if (page) params.set("page", page);
  const qs = params.toString();

  return {
    alternates: { canonical: `https://shop.example.com/coats${qs ? `?${qs}` : ""}` },
    robots: indexable ? undefined : { index: false, follow: true },
  };
}
```

정렬이나 사이즈가 붙은 주소는 noindex가 되고, canonical은 정렬·사이즈를 뺀 주소를 가리킨다. 다만 이 둘은 앞에서 본 대로 크롤링을 줄이지 않는다. 크롤링까지 줄이려면 정렬·사이즈 필터를 링크 대신 버튼으로 만들거나 `app/robots.ts`에서 막는다. 막는다면 이미 색인된 주소가 noindex로 빠진 걸 확인한 다음에 막는다.

## 페이지네이션은 각자 자기 주소다

목록이 길면 페이지를 나눈다. 여기서 실수가 잦다.

예전에는 `<link rel="next">`와 `rel="prev"`로 페이지 묶음을 알려 주라는 안내가 있었다. 구글은 2019년에 이 태그를 몇 년 전부터 색인에 쓰지 않고 있었다고 밝혔다. 넣어서 해가 되진 않고 다른 검색 엔진이나 브라우저가 쓸 수는 있지만, 구글 기준으로는 아무 일도 하지 않는다. 지금 구글이 권하는 방식은 단순하다.

- 각 페이지에 고유한 주소를 준다(`/coats?page=2`). 해시(`#page=2`)는 쓰지 않는다. 구글은 `#` 뒤를 무시한다.
- 페이지끼리 일반 `<a href>`로 잇는다. 1페이지에서 2페이지로, 2페이지에서 1·3페이지로.
- 각 페이지는 자기 자신을 canonical로 가진다. 2페이지의 canonical을 1페이지로 걸면, 2페이지 이후에만 있는 상품으로 가는 길이 약해진다.
- 정렬·필터 파라미터는 위의 규칙대로 다루고, `page`만 남긴 주소를 기본으로 한다.

전체 상품을 한 페이지에 보여 주는 "전체 보기" 페이지가 빠르게 뜬다면 그 페이지를 대표로 삼는 방법도 있다. 상품이 수천 개라 느려진다면 쓰지 않는다.

무한 스크롤은 사람에게는 편하지만 크롤러에게는 1페이지만 있는 목록이 되기 쉽다. 구글의 렌더러는 스크롤하거나 "더 보기"를 누르지 않는다. 세로로 아주 긴 화면으로 렌더링해서 처음 일부가 더 보일 수는 있지만 그걸 믿고 설계하지 않는다. 그래서 무한 스크롤 뒤에도 페이지 주소가 있어야 한다.

```tsx
// "더 보기"는 실제 다음 페이지 주소를 가진 링크다.
// 자바스크립트가 있으면 가로채서 이어 붙이고, 없거나 크롤러면 다음 페이지로 이동한다
<a
  href={`/coats?page=${page + 1}`}
  onClick={(e) => {
    e.preventDefault();
    loadMore(page + 1);
    history.replaceState(null, "", `/coats?page=${page + 1}`); // 지금 보는 위치를 주소에 반영
  }}
>
  더 보기
</a>
```

이렇게 하면 사람은 끊김 없이 스크롤하고, 크롤러는 `?page=2`, `?page=3`을 링크로 따라간다. 각 페이지 주소로 직접 들어오면 그 페이지의 상품이 서버 렌더링으로 보여야 한다. 화면에 들어온 순간 다음 페이지를 불러오는 센티널 구현은 [IntersectionObserver](/posts/scroll-triggered-intersection-observer)에 있다.

## 색인이 부풀었을 때 정리하는 법

크롤링 문제를 고치다 보면 반대편 문제도 보인다. 색인에 들어가 있는데 아무도 검색으로 찾지 않는 페이지가 많은 상태, 색인 비대(index bloat)다. 태그 페이지 수천 개, 결과가 한두 개인 검색 결과 페이지, 내용이 거의 없는 오래된 공지, 상품이 다 빠진 기획전 페이지 같은 것이다.

이런 페이지가 많으면 크롤 수요가 분산되고, 사이트 전체의 품질 판단에도 좋지 않을 수 있다. 정리는 페이지마다 네 갈래 중 하나로 보낸다.

- 고친다: 검색 수요가 있는데 내용이 부족하면 내용을 채운다.
- 합친다: 같은 주제의 비슷한 페이지 여러 개는 가장 나은 하나로 합치고 나머지는 거기로 301을 건다. 링크 신호와 북마크가 따라간다.
- 색인에서 뺀다: 사용자에게는 필요하지만 검색으로 들어올 일은 없는 페이지(내부 검색 결과, 얇은 태그 페이지)는 noindex.
- 지운다: 아무 가치가 없으면 404나 410을 준다. 구글은 둘을 거의 같게 다루고, 410이 조금 더 빨리 빠지는 정도다.

판단 근거는 데이터로 잡는다. Search Console 실적 보고서에서 지난 12개월 노출이 0인 주소, 분석 도구에서 자연 검색 유입이 0인 주소, 외부 링크가 있는 주소를 함께 놓고 본다. 외부 링크가 있는 페이지는 지우지 말고 합쳐서 301로 보낸다. 링크가 그대로 사라지기 때문이다.

Search Console의 "삭제" 도구는 정리 도구가 아니다. 검색 결과에서 약 6개월 동안 임시로 숨길 뿐이고, 그동안 noindex나 404로 실제 처리를 해야 한다.

## 품절과 단종은 다르게 처리한다

쇼핑몰에서 매일 생기는 결정이다. 상품이 팔리지 않게 됐을 때 그 페이지를 어떻게 할까.

잠깐 품절이면 페이지를 그대로 두고 200을 준다. "품절, 11월 둘째 주 입고 예정"처럼 알리고, 재입고 알림 신청을 받는다. 구조화 데이터의 `availability`를 `https://schema.org/OutOfStock`으로 바꾸면 검색 결과에도 반영될 수 있다. 품절마다 페이지를 지우면 그동안 쌓은 순위와 링크를 매번 버리게 된다.

영구 단종이면 갈래가 나뉜다. 바로 대체할 후속 모델이 있으면 그 상품으로 301을 건다. 대체품이 없으면 404나 410을 주고, 그 페이지에 비슷한 상품과 카테고리 링크를 보여 준다. 외부 링크가 많이 걸린 인기 상품이었다면, 단종 안내와 대체 추천을 담은 페이지를 200으로 남겨 두는 것도 방법이다.

흔한 실수는 단종 상품 수천 개를 홈이나 카테고리로 일괄 301 하는 것이다. 내용이 전혀 다른 곳으로의 리디렉션은 구글이 소프트 404로 판단할 수 있고, 사용자도 찾던 상품 대신 홈을 보고 떠난다.

블랙 프라이데이, 시즌 기획전처럼 해마다 돌아오는 페이지는 연도를 주소에 넣지 않는다. `/sale/black-friday` 하나를 해마다 다시 쓰면 작년에 쌓은 링크와 순위를 올해도 쓴다. 행사가 없는 기간에는 지난 행사 안내와 다음 일정을 보여 주는 200 페이지로 둔다.

## 바꾼 뒤 확인하는 순서

이런 변경은 효과가 몇 주에 걸쳐 나타나서, 무엇이 먹혔는지 확인하는 순서를 정해 두는 게 좋다.

1. 바꾸기 전에 기준을 남긴다. 접근 로그에서 구글봇 요청 중 파라미터 주소 비율, Search Console의 "발견됨 - 현재 색인이 생성되지 않음" 개수, 크롤링 통계의 하루 요청 수와 평균 응답 시간.
2. 로그의 구글봇이 진짜인지 확인한다. User-Agent는 아무나 흉내 낼 수 있다. IP를 역방향 DNS로 조회해 `googlebot.com`이나 `google.com`으로 끝나는지 보고, 그 이름을 다시 정방향으로 조회해 같은 IP가 나오는지 본다. 구글 문서에 나오는 형식은 이렇다. 구글은 크롤러 IP 대역도 JSON으로 공개하니 대량 로그는 그 목록과 대조하는 편이 빠르다.

```bash
# 역방향 조회: 이름이 googlebot.com 으로 끝나야 한다
host 66.249.66.1
# 1.66.249.66.in-addr.arpa domain name pointer crawl-66-249-66-1.googlebot.com.

# 정방향 조회: 같은 IP가 나와야 한다
host crawl-66-249-66-1.googlebot.com
# crawl-66-249-66-1.googlebot.com has address 66.249.66.1
```

3. robots.txt와 링크를 바꾼다. robots.txt는 배포 전에 해석기로 상품 상세, `?page=`, 색인 대상 패싯이 허용되는지 확인한다.
4. 일주일, 한 달 뒤 같은 지표를 다시 본다. 파라미터 주소 비율이 내려가고, 상품 상세와 신상품 요청이 늘고, "발견됨" 개수가 줄어야 한다.
5. 되돌릴 준비를 한다. robots.txt는 파일 하나라 이전 버전을 커밋에 남겨 두면 바로 되돌릴 수 있다. 실수로 넓게 막았을 때 피해가 가장 빨리 커지는 곳이 여기다.

서버가 감당을 못 할 만큼 크롤링이 몰리면 응급 처치로 503이나 429를 잠깐 돌려줄 수 있다. 구글봇은 이 응답을 보고 속도를 줄인다. 다만 하루이틀을 넘기면 그 주소들이 색인에서 빠지기 시작할 수 있으니, 그 사이에 위의 근본 처리를 한다.

## 다시 신상품 300개로

처음 장면의 원인은 크롤 예산이 필터 주소에 새고 있던 것이었다. 상품 1만 개에 필터 4개와 정렬 5가지만으로 카테고리마다 16만 개 넘는 주소가 생겼고, 순서와 세션 ID가 그걸 더 불렸다. 고치는 방법은 주소마다 무엇을 원하는지 정하는 데서 시작한다. 검색 수요가 있는 패싯은 정해진 순서의 깔끔한 주소로 색인 대상으로 남기고, 정렬과 사이즈 같은 필터는 링크를 만들지 않거나 robots.txt로 막고, 추적 파라미터는 canonical로 모은다. robots.txt로 막은 주소의 canonical과 noindex는 읽히지 않는다는 것, 페이지 번호마다 자기 주소와 자기 canonical을 준다는 것, 품절은 남기고 단종은 대체품이나 404로 보낸다는 것을 기억하면 된다. 그 결과 남은 예산은 신상품 상세 페이지로 간다. 순위가 정해지는 그다음 단계는 [검색 엔진은 순위를 어떻게 매기나](/posts/search-engine-ranking-pagerank)에 있다.

## 면접에서 나올 만한 질문

### 크롤 예산이란 무엇이고 언제 신경 써야 하나요?

검색 엔진이 한 사이트에서 일정 기간 가져가는 주소의 양이고, 서버가 감당할 수 있는 크롤 용량 한도와 가져갈 가치를 뜻하는 크롤 수요의 조합으로 정해진다. 수요는 인기, 오래된 정도, 사이트에 있다고 알려진 주소의 양에 영향을 받는다. 구글은 고유 페이지가 수십만에서 수백만 개인 큰 사이트나 내용이 매일 바뀌는 중간 규모 사이트, "발견됨 - 현재 색인이 생성되지 않음"이 많은 사이트에서 신경 쓰라고 안내한다. 작은 블로그의 색인 지연은 대개 예산 문제가 아니다.

### 패싯 내비게이션은 왜 SEO 문제가 되나요?

필터 조합마다 주소가 생겨 주소 수가 곱으로 늘기 때문이다. 패싯 4개와 정렬 5가지만으로 카테고리 하나에 16만 개가 넘고, 다중 선택이나 파라미터 순서까지 더하면 수천만 개가 된다. 크롤러가 이 주소들을 따라가느라 새 상품이 늦게 크롤링되고, 비슷한 목록 페이지가 대량으로 생겨 신호도 흩어진다.

### canonical, noindex, robots.txt Disallow는 각각 무엇을 막나요?

canonical은 신호를 대표 주소로 모으고 대표만 색인되게 하는 힌트지만 페이지를 가져가야 읽으니 크롤링은 줄지 않는다. noindex는 색인에서 확실히 빼지만 역시 크롤링은 계속되고 신호를 모아 주지 않는다. Disallow는 크롤링을 직접 줄이는 유일한 도구지만, 가져가지 않으니 그 안의 canonical과 noindex를 읽지 못하고 링크가 많으면 주소만 색인될 수 있다.

### robots.txt로 막은 페이지에 noindex를 넣으면 어떻게 되나요?

noindex가 읽히지 않는다. 크롤러가 페이지를 가져가지 않으니 그 안의 메타 태그를 볼 수 없다. 이미 색인된 주소를 빼고 싶으면 먼저 크롤링을 허락한 채 noindex로 빠지는 걸 확인하고, 그다음에 필요하면 robots.txt로 막는다.

### 색인이 필요한 패싯 페이지는 어떻게 설계하나요?

검색 수요가 확인된 패싯과 얕은 조합만 링크로 만들고 나머지는 버튼으로 둔다. 파라미터는 표준 `&` 구분자를 쓰고 항상 같은 순서로 정렬해 링크를 만든다. 결과가 없는 조합은 링크하지 않고 직접 들어오면 404를 준다. 색인 대상 페이지에는 고유한 title, h1, 소개 내용을 둔다.

### rel=prev/next는 아직 써야 하나요? 페이지네이션은 어떻게 하나요?

구글은 2019년에 이 태그를 이미 몇 년 전부터 색인에 쓰지 않았다고 밝혔다. 지금은 페이지마다 `?page=2` 같은 고유 주소를 주고, 일반 `a href` 링크로 잇고, 각 페이지가 자기 자신을 canonical로 갖게 한다. 2페이지 이후의 canonical을 1페이지로 걸면 뒤쪽 상품으로 가는 길이 약해진다.

### 무한 스크롤 목록은 크롤러에게 어떻게 보이나요?

구글의 렌더러는 스크롤하거나 버튼을 누르지 않으므로, 페이지 주소가 없으면 첫 묶음만 있는 목록으로 보이기 쉽다. "더 보기"를 실제 다음 페이지 주소를 가진 링크로 만들고, 자바스크립트가 있으면 가로채서 이어 붙이며 주소를 갱신한다. 각 페이지 주소로 직접 들어와도 그 페이지 상품이 서버에서 렌더링돼야 한다.

### 품절 상품과 단종 상품 페이지는 어떻게 처리하나요?

일시 품절이면 페이지를 200으로 남기고 품절과 입고 예정을 알리며 구조화 데이터의 availability를 바꾼다. 영구 단종이면 후속 모델이 있을 때 301, 없으면 404나 410을 주고 비슷한 상품을 안내한다. 단종 상품을 홈으로 일괄 리디렉션하면 소프트 404로 처리될 수 있고 사용자 경험도 나쁘다.
