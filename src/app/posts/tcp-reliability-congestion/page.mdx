1Gbps 회선이 깔린 서버에서 바다 건너 리전으로 백업 파일을 올린다고 해 보자. 같은 도시의 서버로 올릴 때는 회선 끝까지 속도가 나오는데, 멀리 있는 서버로는 몇십 Mbps에서 멈춘다. 회선도 서버도 같은데 거리만 다르다. 또 어떤 API는 응답이 몇 바이트짜리인데도 요청마다 정확히 40ms쯤 늦다. 두 증상 모두 TCP가 "빠짐없이, 넘치지 않게" 보내려고 쓰는 장치에서 나온다.

[TCP 연결의 일생 글](/posts/tcp-connection-lifecycle)에서는 연결을 맺고 끊는 과정을 봤다. 이 글은 연결이 ESTABLISHED인 동안 일어나는 일을 본다. 번호와 확인으로 잃어버린 조각을 찾아 다시 보내는 법, 받는 쪽이 넘치지 않게 속도를 맞추는 흐름 제어, 길 중간이 넘치지 않게 조절하는 혼잡 제어, 그리고 이 장치들이 만드는 지연과 그걸 `ss -ti`로 읽는 법까지다.

기준은 Ubuntu 24.04다. 출력은 Ubuntu 24.04 컨테이너(커널 6.18)의 루프백에서 Python으로 서버와 클라이언트를 띄우고, iptables로 패킷을 일부러 버려 가며 찍었다. 루프백은 지연이 수십 마이크로초라 RTT 숫자는 실제 망보다 훨씬 작다.

## 번호는 바이트마다, 확인은 다음 번호로

TCP는 보내는 데이터를 바이트 단위로 센다. 3바이트를 보내면 `seq 1:4`, 다음 100바이트는 `seq 4:104`처럼 번호 구간이 붙는다. 받는 쪽은 "몇 번까지 받았다"가 아니라 "다음엔 몇 번을 줘"를 ACK로 알려 준다.

```text
22:57:40.122872 IP 127.0.0.1.35384 > 127.0.0.1.7000: Flags [P.], seq 1:4, ack 1, win 64, length 3
22:57:40.122875 IP 127.0.0.1.7000 > 127.0.0.1.35384: Flags [.], ack 4, win 64, length 0
```

1~3번 바이트를 받았으니 `ack 4`다. 이 ACK는 누적이다. `ack 4`는 "3번까지는 빈틈없이 다 받았다"는 뜻이라, 중간 ACK 하나가 사라져도 다음 ACK가 앞의 것을 모두 대신해 준다. 반대로 말하면 중간에 빈 곳이 있으면 그 뒤를 아무리 많이 받아도 ACK 번호는 빈 곳에서 멈춘다.

보내는 쪽은 ACK가 올 때까지 보낸 데이터를 버리지 않고 송신 버퍼에 들고 있다. 확인이 오면 그만큼 지우고, 안 오면 다시 보낸다. TCP의 신뢰성은 이 단순한 규칙 위에 있다.

## 확인이 안 오면 기다렸다가 다시 보낸다

ACK가 일정 시간 안에 안 오면 잃어버린 것으로 보고 다시 보낸다. 이 시간이 재전송 타임아웃(RTO)이다. 실제로 재현해 봤다. 연결을 맺은 뒤 iptables로 데이터가 든 패킷만 버리게 하고 `hello` 5바이트를 보냈다.

```bash
# 7030번으로 가는 데이터 패킷(PSH 플래그)만 버린다. 실험 뒤 -D로 지운다
sudo iptables -I INPUT -i lo -p tcp --dport 7030 --tcp-flags PSH PSH -j DROP
```

```text

22:59:08.189205 IP 127.0.0.1.36868 > 127.0.0.1.7030: Flags [P.], seq 101:106, ack 1, win 64, length 5
22:59:08.397210 IP 127.0.0.1.36868 > 127.0.0.1.7030: Flags [P.], seq 101:106, ack 1, win 64, length 5
22:59:08.821234 IP 127.0.0.1.36868 > 127.0.0.1.7030: Flags [P.], seq 101:106, ack 1, win 64, length 5
22:59:09.653264 IP 127.0.0.1.36868 > 127.0.0.1.7030: Flags [P.], seq 101:106, ack 1, win 64, length 5

22:59:14.773274 IP 127.0.0.1.7030 > 127.0.0.1.36868: Flags [.], ack 106, win 64, length 0
```

같은 `seq 101:106`이 일곱 번 나갔다. 간격을 계산하면 204, 208, 424, 832, 1664, 3456ms다. 첫 재전송은 리눅스의 꼬리 손실 탐침(TLP, 마지막 조각이 사라졌을 때 빨리 찾으려는 장치)으로 보이고, 그 뒤로는 RTO가 약 200ms에서 시작해 두 배씩 늘었다. 규칙을 지운 뒤 나간 일곱 번째가 도착하자 `ack 106`이 바로 돌아왔다. 그 사이 `ss -ti`는 이렇게 보였다(긴 줄은 필요한 부분만 남겼다).

```bash
# 7030번 연결의 내부 상태(-i)와 타이머(-o)
ss -tnio state established '( dport = :7030 )'
```

```text
0      5          127.0.0.1:36868    127.0.0.1:7030 timer:(on,644ms,2)
	 ts sack bbr wscale:10,10 rto:816 backoff:2 rtt:0.03/0.016 mss:32768 ... cwnd:1 ... unacked:1 retrans:1/3 lost:1 ...
```

`Send-Q`의 5가 ACK를 못 받은 5바이트이고, `timer:(on,644ms,2)`는 644ms 뒤에 다시 보내며 지금까지 두 번 물러섰다(backoff)는 뜻이다. `rto:816`은 처음 204ms에서 두 번 두 배가 된 값이다. `cwnd:1`은 뒤에서 볼 혼잡 윈도가 타임아웃 때문에 1까지 떨어진 것이다. 재전송 타임아웃은 TCP가 겪는 가장 큰 벌이다.

RTO를 얼마로 잡을지는 연결마다 다르다. 커널은 ACK가 돌아오는 시간을 계속 재서 평균 왕복 시간(SRTT)과 그 흔들림(RTTVAR)을 구하고, RFC 6298의 식대로 대략 SRTT + 4 × RTTVAR로 정한다. RFC는 최솟값을 1초로 권하지만 리눅스는 200ms를 하한으로 쓴다(`tcp_rto_min_us`). 그래서 루프백처럼 RTT가 0.03ms여도 RTO는 204ms였다. 데이터센터 안에서는 이 200ms가 꼬리 지연의 주범이 되기도 한다. 패킷 하나가 사라지면 그 요청은 최소 200ms 늦는다.

## 같은 ACK가 세 번 오면 기다리지 않는다

RTO까지 기다리는 건 너무 느리다. 데이터를 계속 보내는 중이라면 더 빠른 신호가 있다. 중간 조각 하나가 빠지면 받는 쪽은 그 뒤 조각이 올 때마다 "아직 그 번호를 기다린다"는 같은 ACK를 다시 보낸다. 보내는 쪽은 같은 ACK가 세 번 더 오면 타이머를 기다리지 않고 바로 그 조각을 다시 보낸다. 이게 빠른 재전송(fast retransmit)이다.

SACK(선택 확인)가 켜져 있으면 받는 쪽은 "3번은 없지만 4~6번은 받았다"를 ACK에 함께 적어 보낸다. 그래서 보내는 쪽은 빠진 3번만 골라 보낸다. SACK가 없으면 3번 뒤를 전부 다시 보내야 할 수도 있다. 앞의 SYN에서 본 `sackOK`가 이 기능을 쓰겠다는 약속이다.

마지막 단계가 줄 막힘(head-of-line blocking)이다. #4~#6은 이미 도착했는데도 #3이 올 때까지 앱에 넘어가지 못했다. TCP는 바이트 순서를 지키는 걸 약속했기 때문이다. 하나의 TCP 연결에 여러 요청을 섞어 보내는 HTTP/2에서 이 기다림이 상관없는 요청까지 붙잡는 문제가 되고, 그래서 HTTP/3는 TCP를 떠났다. 이 이야기는 [HTTP 버전 글](/posts/http-versions)에 자세히 있다. 빠른 재전송은 뒤에 보낼 데이터가 있을 때만 통한다는 점도 기억해 둔다. 응답의 마지막 조각이 사라지면 중복 ACK를 만들어 줄 뒷조각이 없어서, 앞에서 본 TLP나 RTO를 기다리게 된다.

## 받는 쪽이 넘치지 않게 하는 흐름 제어

받는 쪽 커널은 도착한 데이터를 수신 버퍼에 쌓아 두고, 앱이 `read()`로 꺼내 가면 비운다. 앱이 꺼내 가는 속도보다 빨리 들어오면 버퍼가 찬다. 그래서 받는 쪽은 모든 ACK에 "지금 이만큼 더 받을 수 있다"를 적어 보낸다. tcpdump의 `win` 값이 그 수신 윈도다. 보내는 쪽은 ACK를 받지 못한 데이터가 이 값을 넘지 않게 보낸다.

`win` 필드는 16비트라 최대 65535다. 요즘 망에서는 너무 작아서, SYN에서 윈도 배율(`wscale`)을 정하고 그 뒤로는 `win` 값에 2의 배율 제곱을 곱해 읽는다. 앞의 캡처에서 `wscale 10`이었으니 `win 64`는 64 × 1024 = 65536바이트다. 배율은 SYN에서만 정하기 때문에, tcpdump를 연결 중간부터 뜨면 배율을 몰라서 `win 64`를 그대로 64바이트로 오해하기 쉽다.

받는 쪽 앱이 아예 읽지 않으면 어떻게 될까. 수신 버퍼를 8KB로 줄인 서버가 `read()`를 한 번도 부르지 않게 하고, 클라이언트가 계속 보내게 했다.

```bash
# 양쪽 소켓의 큐를 본다
ss -tn '( sport = :7040 or dport = :7040 )'
```

```text
State Recv-Q Send-Q  Local Address:Port  Peer Address:Port Process
ESTAB 12288  0           127.0.0.1:7040     127.0.0.1:58474
ESTAB 0      3272704     127.0.0.1:58474    127.0.0.1:7040
```

```text
22:59:25.397160 IP 127.0.0.1.7040 > 127.0.0.1.58474: Flags [.], ack 12289, win 0, options [nop,nop,TS val 3202020645 ecr 4033774111,nop,nop,sack 1 {8193:12289}], length 0
22:59:25.609179 IP 127.0.0.1.58474 > 127.0.0.1.7040: Flags [.], ack 1, win 64, options [nop,nop,TS val 4033774366 ecr 3202020645], length 0
22:59:25.609191 IP 127.0.0.1.7040 > 127.0.0.1.58474: Flags [.], ack 12289, win 0, options [nop,nop,TS val 3202020857 ecr 4033774111], length 0
```

받는 쪽(7040)의 `Recv-Q`에 앱이 읽지 않은 12288바이트가 쌓였고, `win 0`으로 "더는 못 받는다"고 알렸다. 보내는 쪽은 데이터를 멈추고, 가끔 빈 탐침 패킷(zero window probe)을 보내 윈도가 열렸는지 묻는다. 둘째 줄이 그 탐침이다. 보내는 쪽 앱이 `send()`로 넘긴 3272704바이트는 송신 버퍼(`Send-Q`)에 그대로 쌓여 있다.

이 모양은 현장에서 그대로 보인다. 받는 쪽의 `Recv-Q`가 계속 크다면 네트워크가 아니라 받는 앱이 느린 것이다. 로그 수집기나 메시지 소비자가 처리를 못 따라가는 경우가 대표적이다. 반대로 보내는 쪽의 `Send-Q`만 크고 상대 `Recv-Q`는 0이라면 데이터가 길에서 막히고 있다. 어느 쪽 큐가 쌓였는지만 봐도 어디를 봐야 할지가 갈린다.

## 길이 넘치지 않게 하는 혼잡 제어

흐름 제어는 받는 쪽을 지키지만, 그 사이의 길은 지켜 주지 못한다. 서버가 10Gbps로 보내도 중간 어딘가 100Mbps 구간이 있으면 그 앞의 라우터 큐가 넘쳐 패킷이 버려진다. 1980년대 인터넷은 실제로 이렇게 무너졌다. 모두가 잃어버린 패킷을 서둘러 다시 보내면서 길은 더 막히고, 쓸모 있는 데이터는 거의 지나가지 못했다(혼잡 붕괴). 그 뒤로 TCP에 혼잡 제어가 들어갔다.

보내는 쪽은 길의 사정을 직접 볼 수 없다. 그래서 스스로 혼잡 윈도(cwnd)라는 한도를 두고, ACK를 받지 못한 데이터가 cwnd와 수신 윈도 중 작은 쪽을 넘지 않게 보낸다. cwnd는 세그먼트 개수로 센다.

연결을 막 맺은 뒤에는 길이 얼마나 넓은지 모르니 작게 시작한다. 지금 리눅스의 첫 cwnd는 10세그먼트(RFC 6928)다. 그리고 ACK가 돌아올 때마다 그만큼 늘려서, 왕복 한 번마다 두 배가 된다. 이름은 느린 시작(slow start)인데 실제로는 빠르게 커진다. 커지다가 임계값(ssthresh)에 닿으면 왕복마다 1씩만 늘리는 혼잡 회피로 넘어간다. 그러다 손실이 보이면 줄인다.

## CUBIC과 BBR

손실이 나면 얼마나 줄이고 어떻게 다시 늘릴지는 알고리즘마다 다르다. 리눅스는 이 부분을 모듈로 바꿔 끼울 수 있다.

```bash
# 지금 쓰는 혼잡 제어와 쓸 수 있는 목록
sysctl net.ipv4.tcp_congestion_control net.ipv4.tcp_available_congestion_control
```

```text
net.ipv4.tcp_congestion_control = bbr
net.ipv4.tcp_available_congestion_control = reno bbr cubic
```

이 글을 찍은 환경은 BBR이 기본으로 설정돼 있었다. 기본 설치 Ubuntu 24.04는 `cubic`이 나온다. CUBIC은 리눅스 2.6.19부터 기본값이다. 손실이 나면 cwnd를 0.7배로 줄이고, 마지막으로 손실이 난 시점부터 흐른 시간의 3차 함수로 다시 늘린다. 잃었던 크기 근처까지는 빠르게 회복하고, 그 근처에서는 머뭇거리다가, 넘어서면 다시 빠르게 늘린다. 왕복 횟수가 아니라 시간에 따라 늘어나서, RTT가 긴 연결도 짧은 연결과 비슷한 속도로 회복한다.

CUBIC까지의 알고리즘은 손실을 혼잡의 신호로 본다. 문제는 손실이 늘 혼잡 때문은 아니라는 것이다. 무선 구간이나 오래된 장비에서는 혼잡 없이도 패킷이 조금씩 사라지고, 그때마다 cwnd를 깎으면 회선을 다 쓰지 못한다. 반대로 라우터 큐가 아주 크면 손실이 나기 전까지 큐가 꽉 차서 지연만 늘어난다(bufferbloat). 이 큐를 직접 재고 줄이는 방법은 [트래픽 셰이핑 글](/posts/traffic-shaping-qos)에서 다룬다.

BBR은 Google이 2016년에 내놓았고 리눅스 4.9부터 들어 있다. 손실 대신 두 값을 잰다. 지금까지 본 가장 높은 전달 속도(병목 대역폭)와 가장 짧은 왕복 시간이다. 그 곱만큼만 길 위에 데이터를 두고, 그 속도로 고르게 흘려보낸다(pacing). 손실이 조금 있는 먼 거리 연결에서 CUBIC보다 훨씬 빠를 수 있다. 대신 CUBIC 연결과 같은 병목을 나눌 때 몫이 한쪽으로 쏠리는 공정성 문제가 지적돼 왔고, 개선판(BBRv2, v3)은 아직 리눅스 본선에 들어가지 않았다.

```bash
# BBR로 바꿔 보기 (재부팅하면 원래대로 돌아간다)
sudo modprobe tcp_bbr
sudo sysctl -w net.ipv4.tcp_congestion_control=bbr

# 영구로 바꾸려면 설정 파일에 적는다
echo "net.ipv4.tcp_congestion_control=bbr" | sudo tee /etc/sysctl.d/90-bbr.conf

# 되돌리기
sudo sysctl -w net.ipv4.tcp_congestion_control=cubic
sudo rm /etc/sysctl.d/90-bbr.conf
```

혼잡 제어는 보내는 쪽 알고리즘이라 서버에서 바꾸면 서버가 보내는 방향(다운로드)에만 적용된다. 큰 파일을 내려주는 서버나 먼 지역으로 복제하는 서버에서 효과가 크고, 바꾼 뒤에는 실제 트래픽에서 재전송률과 속도를 비교해 본다.

## 멀리 갈수록 느린 이유는 대역폭과 지연의 곱이다

처음의 질문으로 돌아가자. 1Gbps로 RTT 100ms인 곳에 보내려면, 첫 바이트의 ACK가 돌아오기 전까지 100ms 동안 계속 보내고 있어야 회선을 다 쓴다. 그 양은 1Gbps × 0.1초 = 12.5MB다. 이 값을 대역폭 지연 곱(BDP)이라 한다. ACK를 받지 못한 데이터가 12.5MB까지 날아다닐 수 있어야 한다는 뜻이고, 그러려면 cwnd도 수신 윈도도 송신 버퍼도 모두 그만큼 커야 한다.

수신 윈도가 64KB에 묶여 있다면 왕복마다 64KB만 보낼 수 있다. 65535바이트 ÷ 0.1초 = 약 5.2Mbps다. 1Gbps 회선이 5Mbps처럼 동작한다. 윈도 배율을 지워 버리는 오래된 방화벽을 지나는 연결에서 실제로 나오는 증상이다. 같은 계산으로 수신 버퍼가 6MB면 약 503Mbps, 128KB면 약 10.5Mbps가 상한이다. RTT가 10ms인 같은 도시 서버라면 1.25MB만 있어도 1Gbps가 나오니, 같은 설정이 가까운 곳에서는 멀쩡하다.

리눅스는 수신 버퍼를 연결 상황에 맞게 자동으로 늘리고(autotuning), 그 범위를 `tcp_rmem`의 세 값(최소, 기본, 최대)으로 정한다.

```bash
# 수신·송신 버퍼의 최소, 기본, 최대 (바이트)
sysctl net.ipv4.tcp_rmem net.ipv4.tcp_wmem
```

```text
net.ipv4.tcp_rmem = 4096	131072	33554432
net.ipv4.tcp_wmem = 4096	16384	4194304
```

이 환경은 수신 최대가 32MB로 크게 잡혀 있었다. 기본 설치 Ubuntu에서는 메모리 크기에 따라 정해지는데, 보통 6MB(6291456) 언저리다. 먼 거리로 큰 데이터를 보내는 서버라면 BDP를 계산해 최대값을 그 이상으로 올린다. 앱에서 `SO_RCVBUF`를 직접 지정하면 그 소켓은 자동 조정이 꺼지니, 작은 값을 박아 둔 설정이 없는지도 확인한다.

손실률도 속도를 크게 깎는다. 손실 기반 알고리즘의 처리량은 대략 MSS ÷ RTT × 1.22 ÷ √손실률로 어림한다(Mathis 식, Reno 기준). MSS 1460, RTT 100ms에서 손실률 0.01%면 약 14.3Mbps, 1%면 약 1.4Mbps다. 같은 손실률이라도 RTT가 10ms면 열 배인 약 142Mbps다. 먼 곳일수록 작은 손실에도 민감하다는 게 숫자로 보인다. BBR이 먼 거리에서 강한 이유가 여기 있다.

## 작은 패킷 두 개가 40ms를 만든다

이번엔 대역폭이 아니라 지연의 문제다. 클라이언트가 요청을 10바이트짜리 두 번의 `send()`로 나눠 보내고, 서버는 20바이트가 다 모이면 짧은 응답을 보낸다. 이걸 20번 반복하는 데 걸린 시간을 쟀다.

```text
TCP_NODELAY=0: 20회 왕복 878.5 ms
TCP_NODELAY=1: 20회 왕복 0.6 ms
```

루프백인데 왕복 한 번에 약 44ms가 걸렸다. 두 장치가 서로를 기다린 결과다.

Nagle 알고리즘은 작은 조각을 너무 많이 보내지 않으려고, 아직 ACK를 못 받은 데이터가 있으면 다음 작은 조각을 모아 두고 기다린다. 지연 ACK는 ACK를 바로 보내지 않고 함께 실어 보낼 응답이 생길 때까지 잠깐 기다린다. 리눅스의 최소 지연은 40ms다. 클라이언트의 두 번째 `send()`는 첫 조각의 ACK를 기다리고, 서버는 첫 조각만으로는 응답할 수 없어 ACK를 미루다가 40ms 타이머가 끝나서야 ACK를 보낸다. 그제야 두 번째 조각이 나간다. 앞서 본 연결 종료 캡처에서 FIN에 대한 ACK가 42ms 뒤에 나간 것도 같은 지연 ACK다.

고치는 방법은 둘이다. 소켓에 `TCP_NODELAY`를 켜서 Nagle을 끄거나, 애초에 요청을 한 번의 쓰기로 모아서 보낸다. 지연에 민감한 구현은 대부분 `TCP_NODELAY`를 켜 둔다. nginx는 `tcp_nodelay on`이 기본값이고, Redis와 gRPC 같은 RPC 라이브러리도 켠다. 직접 소켓 프로토콜을 짜는데 "요청마다 정확히 40ms 늦다"면 이 조합부터 의심한다. 다만 `TCP_NODELAY`만 켜고 작은 쓰기를 남발하면 패킷 수가 늘어 처리량이 떨어지니, 한 번에 모아 쓰는 습관이 먼저다.

이 연결은 `rwnd_limited`가 100%다. 받는 쪽이 광고한 윈도 때문에 더 못 보낸 것이라, 보내는 쪽 혼잡 제어를 바꿔 봐야 소용없고 받는 쪽 버퍼나 앱의 읽기 속도를 봐야 한다. 이렇게 한 줄이 어느 쪽을 고쳐야 할지 알려 준다.

연결 하나가 아니라 서버 전체의 손실을 보려면 커널 카운터를 본다.

```bash
# 재전송한 세그먼트와 타임아웃 횟수 (누적값). 몇 초 간격으로 두 번 찍어 차이를 본다
nstat -az TcpRetransSegs TcpOutSegs TcpExtTCPTimeouts
```

`TcpRetransSegs`를 `TcpOutSegs`로 나누면 재전송률이다. 데이터센터 안에서 0.1%를 넘게 꾸준히 나오면 경로 어딘가(NIC, 스위치 포트, 과부하 걸린 가상 네트워크)를 의심한다. 특정 목적지로만 느리면 `ss -ti dst 그주소`로 그 연결들의 `rtt`와 `retrans`를 비교한다. 경로 자체를 확인하는 순서는 [계층별 장애 좁히기 글](/posts/network-troubleshooting-by-layer)에 있다.

흔한 실수도 몇 가지 있다. 속도 테스트를 연결 하나로 짧게 해서 느린 시작 구간만 재고 "느리다"고 결론 내는 것, 수신 쪽 문제를 보내는 쪽 혼잡 제어로 고치려는 것, 방화벽에서 ICMP를 모두 막아 경로 MTU를 못 찾게 만들고는 재전송 폭주를 보는 것이다. 마지막 경우는 [MTU 글](/posts/layer-mtu-fragmentation)에서 재현한다.

## 믿을 만하다는 것의 값

TCP는 바이트마다 번호를 붙이고 다음 번호로 확인받는다. 확인이 안 오면 RTO를 두 배씩 늘리며 다시 보내고, 같은 ACK가 세 번 오면 바로 다시 보낸다. 받는 쪽의 수신 윈도로 넘치지 않게 맞추고, 스스로 정한 혼잡 윈도로 길이 넘치지 않게 맞춘다. 이 장치들 덕분에 앱은 빠짐없이 순서대로 받지만, 그 대가로 손실 하나가 줄 전체를 세우고, 먼 곳에서는 BDP만큼 버퍼가 없으면 회선을 다 못 쓴다. 다음 글에서는 이 보장을 모두 내려놓고 빨리 보내는 쪽, [UDP와 QUIC](/posts/udp-and-quic)을 본다.

## 면접에서 나올 만한 질문

### TCP는 어떻게 데이터가 빠짐없이 순서대로 도착하게 하나요?

바이트마다 시퀀스 번호를 붙이고, 받는 쪽은 다음에 받을 번호를 누적 ACK로 알려 준다. 보내는 쪽은 ACK가 올 때까지 데이터를 버퍼에 들고 있다가, RTO 안에 확인이 없거나 중복 ACK가 세 번 오면 다시 보낸다. 받는 쪽은 번호로 순서를 맞추고 중복을 버린 뒤 빈틈없는 부분만 앱에 넘긴다.

### 흐름 제어와 혼잡 제어는 어떻게 다른가요?

흐름 제어는 받는 쪽 버퍼가 넘치지 않게 하는 것으로, 받는 쪽이 ACK마다 수신 윈도를 알려 준다. 혼잡 제어는 중간 경로가 넘치지 않게 하는 것으로, 보내는 쪽이 손실이나 지연을 보고 혼잡 윈도를 스스로 조절한다. 실제로 보낼 수 있는 양은 둘 중 작은 값이다.

### 느린 시작은 이름과 달리 왜 빠르게 늘어나나요?

ACK 하나를 받을 때마다 cwnd를 하나씩 늘리니 왕복마다 두 배가 된다. 처음엔 길의 폭을 모르니 작게 시작하되, 빨리 찾아가려고 지수적으로 늘린다. ssthresh에 닿으면 왕복마다 1씩 늘리는 혼잡 회피로 넘어가고, 손실이 나면 줄인다. 첫 cwnd가 10이라 새 연결의 첫 왕복에는 약 14KB만 보낼 수 있다.

### 빠른 재전송과 타임아웃 재전송의 차이는요?

타임아웃 재전송은 RTO 동안 ACK가 없을 때 하는 것으로, 최소 200ms를 기다리고 cwnd를 1로 떨어뜨리는 큰 벌을 받는다. 빠른 재전송은 같은 ACK가 세 번 더 오면 타이머를 기다리지 않고 빠진 조각만 다시 보내며 cwnd도 덜 줄인다. 다만 뒤에 보낼 데이터가 있어야 중복 ACK가 생기니, 응답의 마지막 조각 손실은 빠른 재전송으로 못 잡는다.

### 1Gbps 회선인데 먼 리전으로는 속도가 안 나옵니다. 왜죠?

한 연결이 낼 수 있는 속도는 대략 윈도 ÷ RTT라서, RTT가 길면 대역폭 지연 곱만큼 윈도와 버퍼가 커야 한다. 1Gbps, 100ms면 12.5MB가 필요한데 수신 버퍼가 6MB면 500Mbps 언저리, 윈도 배율이 막혀 64KB면 5Mbps 정도가 상한이다. 손실 기반 혼잡 제어는 RTT가 길수록 작은 손실에도 크게 느려진다. `ss -ti`로 rwnd_limited와 retrans를 보고 버퍼를 올리거나 BBR, 병렬 연결을 검토한다.

### CUBIC과 BBR은 어떻게 다른가요?

CUBIC은 손실을 혼잡 신호로 보고 0.7배로 줄인 뒤 시간의 3차 함수로 회복하며, 리눅스 기본값이다. BBR은 손실 대신 병목 대역폭과 최소 RTT를 재서 그 곱만큼만 길 위에 두고 일정한 속도로 보낸다. 그래서 손실이 조금 있는 먼 경로나 큐가 큰 경로에서 유리하지만, CUBIC과 섞일 때의 공정성 문제가 있다.

### 요청마다 40ms씩 늦는 현상은 왜 생기나요?

Nagle 알고리즘과 지연 ACK가 서로를 기다릴 때 생긴다. 작은 쓰기 두 번으로 요청을 보내면 두 번째 조각은 첫 조각의 ACK를 기다리고, 받는 쪽은 응답할 거리가 없어 ACK를 최대 40ms 미룬다. 요청을 한 번에 모아 쓰거나 `TCP_NODELAY`로 Nagle을 끄면 사라진다.
