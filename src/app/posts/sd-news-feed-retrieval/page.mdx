이 시리즈에서 이 글의 자리: [㉔ 뉴스 피드 ①: 글 하나를 팔로워 피드에 나눠 넣기](/posts/sd-news-feed-publishing)에서 글을 쓸 때 팔로워마다 피드 목록에 글 ID를 넣어 두는 법을 봤다. 이 글은 그 목록을 읽는 쪽이다. ID를 화면에 보일 글로 바꾸고, 스크롤에 맞춰 다음 페이지를 주고, 목록이 비어 있는 사용자의 피드를 다시 만든다. 다음 글은 [㉖ 채팅 ①](/posts/sd-chat-connections)이다.

피드를 내리다 보면 방금 지나간 글이 다시 나온다. 다섯 개가 연달아 겹친다. 반대로 친구가 분명히 올린 글이 내 피드에서만 빠져 있기도 하다. 둘 다 서버가 고장 난 게 아니라 "다음 페이지"를 정하는 방식 때문에 생긴다.

앞 글 덕분에 피드 캐시에는 이미 내 피드의 글 ID가 최신순으로 들어 있다. 그런데 ID만으로는 화면을 그릴 수 없다. 작성자 이름과 사진, 본문, 좋아요 수, 내가 좋아요를 눌렀는지까지 붙여야 한다. 이 글은 피드 한 페이지가 만들어지는 길을 따라가며 어디서 느려지고 어디서 글이 겹치거나 빠지는지 직접 재 본다.

## 캐시를 바뀌는 속도로 나눈다

- 피드 캐시는 사용자마다 하나, 글이 써질 때마다 바뀐다. 크기를 상한으로 묶는다.
- 글 캐시는 글마다 하나다. 한 번 쓰면 거의 바뀌지 않으니 오래 둔다. 많이 읽히는 글만 남도록 메모리가 차면 오래 안 쓴 것부터 내보낸다.
- 관계 캐시는 팔로우 목록과 차단 목록이다. 팬아웃 작업자도 이것을 읽는다.
- 행동 캐시는 "사용자 42가 글 7301에 좋아요를 눌렀나" 같은 사람별 상태다.
- 숫자 캐시는 좋아요·댓글·팔로워 수다. 가장 자주 바뀌고, 유명인 글 하나에 수십만 명이 동시에 좋아요를 누르면 키 하나에 쓰기가 몰린다. 이런 핫 키를 나눠 받는 방법은 [캐시 전략](/posts/caching-strategies)에 있다.

나눠 두면 각 칸의 만료 시간과 무효화 규칙을 따로 정할 수 있다. 좋아요 수는 몇 초 늦어도 괜찮지만 차단 목록은 바로 반영돼야 한다. 대신 한 페이지를 만들 때 들를 곳이 늘어난다. 그 비용을 줄이는 게 다음 절이다.

## 하나씩 물으면 왕복이 스물한 번

ID 20개를 받아 본문을 하나씩 `GET`하면 피드 캐시 1번, 글 캐시 20번, 모두 21번 왕복한다. 목록 하나를 가져온 뒤 항목마다 다시 묻는 이 모양을 N+1 문제라고 부른다. `MGET`(여러 키를 한 명령으로)이나 파이프라인(여러 명령을 한 번에 보내고 답을 한 번에 받기)으로 묶으면 2번이 된다. 로컬 Redis 7.0에 글 500개(본문 358바이트)를 넣고 한 페이지를 500번 만들어 평균을 냈다.

```js
// hydrate.mjs 일부: 같은 페이지를 세 방식으로 만든다
const ids = async () => r.cmd("ZRANGE", "feed:me", 0, 19, "REV");
await bench("GET one by one (1+20 trips)", async () => { for (const id of await ids()) await r.cmd("GET", `post:${id}`); });
await bench("MGET (1+1 trips)", async () => r.cmd("MGET", ...(await ids()).map((id) => `post:${id}`)));
await bench("pipeline GET x20 (1+1 trips)", async () => r.pipeline((await ids()).map((id) => ["GET", `post:${id}`])));
```

```text
GET one by one (1+20 trips)  1.114 ms/page
MGET (1+1 trips)             0.176 ms/page
pipeline GET x20 (1+1 trips) 0.207 ms/page
```

같은 컴퓨터 안이라 왕복 한 번이 수십 µs밖에 안 되는데도 6배 차이가 났다. 캐시 서버가 다른 기계에 있으면 같은 데이터센터 안에서도 왕복마다 보통 수백 µs가 붙으니 21번과 2번의 차이는 몇 ms로 벌어진다. 왕복 시간의 대략적인 크기는 [⑨ 지연 시간 숫자](/posts/sd-latency-numbers)에 정리해 두었다. 글 캐시, 사용자 캐시, 숫자 캐시를 차례로 묶어 물으면 한 페이지에 왕복 4번 정도로 끝난다. 사용자 캐시와 숫자 캐시는 서로 기다릴 필요가 없으니 동시에 보내면 더 줄어든다.

`MGET`은 없는 키 자리에 빈 값(nil)을 돌려준다. 그 글들만 모아 DB에서 한 번에 읽고 캐시에 넣는다. 캐시를 먼저 보고 없으면 원본에서 채우는 이 방식이 cache-aside다. 지워진 글이나 차단한 사람의 글은 이 단계에서 빠지므로 20개를 달라고 했는데 17개만 남을 수 있다. 그래서 피드 캐시에서는 처음부터 25개쯤 꺼내 걸러 낸 뒤 20개를 채운다. 그래도 모자라면 한 번 더 꺼낸다.

## 피드 하나가 쓰는 메모리

피드 캐시는 사용자 수만큼 있으니 한 개의 크기가 전체 비용을 정한다. 앞 글에서는 정렬된 셋을 썼는데, 같은 ID 500개를 리스트에 넣을 때와 비교해 봤다. 사용자 1만 명의 피드에 19자리 글 ID를 500개씩 넣고 `INFO memory`의 증가량을 쟀다.

```text
zset: 10,000 feeds x 500 ids = 606.5 MiB, 127.2 bytes/entry, encoding=skiplist
list: 10,000 feeds x 500 ids = 50.5 MiB, 10.6 bytes/entry, encoding=quicklist
```

정렬된 셋이 리스트의 12배다. Redis는 정렬된 셋이 작을 때는 항목을 빽빽하게 이어 붙인 listpack이라는 형식으로 두고, 항목 수가 `zset-max-listpack-entries`(기본 128)를 넘으면 검색용 구조(skiplist와 해시 테이블)로 바꾼다. 500개는 기준을 넘어서 항목마다 포인터와 해시 칸이 붙었다. 기준을 512로 올리고 다시 쟀다.

```text
zset: 10,000 feeds x 500 ids = 98.4 MiB, 20.6 bytes/entry, encoding=listpack
```

메모리가 6분의 1로 줄었다. 공짜는 아니다. listpack은 중간에 넣을 때 뒤쪽을 밀어야 해서 항목이 많을수록 느리다. 서버 쪽 처리 시간(`INFO commandstats`의 `usec_per_call`)을 비교했다.

```text
listpack-entries=128 encoding=skiplist
  zadd: 10000 calls, usec_per_call=0.55
  zremrangebyrank: 10000 calls, usec_per_call=0.26
  zrange: 10000 calls, usec_per_call=1.11
listpack-entries=512 encoding=listpack
  zadd: 10000 calls, usec_per_call=14.37
  zremrangebyrank: 10000 calls, usec_per_call=0.36
  zrange: 10000 calls, usec_per_call=1.94
```

`ZADD`가 0.55µs에서 14.37µs로 26배 느려졌다. 읽기는 거의 같다. 팬아웃 쓰기가 많은 서비스라면 이 차이가 Redis 한 대가 받을 수 있는 쓰기 양을 바로 줄인다. 한 사람에 500개를 두면 1,000만 명이면 skiplist로 약 640GB, listpack으로 약 100GB다. 그래서 실제로는 상한 자체를 줄이거나(앞 몇 페이지면 충분하다), 활성 사용자에게만 피드를 두거나, 메모리가 적은 리스트를 쓰고 읽을 때 중복을 거른다. 어느 쪽이든 숫자를 재 보고 고른다.

## 스크롤하는 동안 새 글이 들어오면

이제 처음의 증상, 글이 겹치는 문제를 보자. 페이지를 가장 쉽게 나누는 방법은 offset이다. 1페이지는 0번째부터 20개, 2페이지는 20번째부터 20개. 그런데 피드는 맨 앞에 계속 새 글이 들어오는 목록이다.

Node 22로 작은 피드 캐시를 만들고, 1페이지를 읽은 뒤 새 글 5개가 들어오고 2페이지에 있던 글 하나가 지워지는 상황을 재현했다.

```js
// cursor.mjs 일부: 커서는 마지막으로 본 ID다. 그보다 작은 첫 글부터 이어 준다
byOffset(offset, limit) { return this.ids.slice(offset, offset + limit); }
byCursor(cursor, limit) {
  const start = cursor === null ? 0 : this.ids.findIndex((x) => x < cursor);
  const items = start < 0 ? [] : this.ids.slice(start, start + limit);
  return { items, next: items.length === limit ? items[items.length - 1] : null };
}
```

```text
page1: 1100 ... 1081 | cursor next = 1081
offset page2: 1085 ... 1065 | duplicates: 1085,1084,1083,1082,1081
cursor page2: 1080 ... 1060 | duplicates: 0 | next = 1060
offset saw 35 unique of 40 rows; cursor saw 40 unique of 40
```

offset 방식의 2페이지는 1085부터 시작해 1페이지 끝의 다섯 개를 다시 보여 줬다. 새 글 다섯 개가 앞에 끼면서 모든 글이 다섯 칸씩 뒤로 밀렸기 때문이다. 반대로 글이 지워지면 한 칸씩 앞으로 당겨져 한 개를 건너뛴다. 이 실험에서는 두 효과가 겹쳐 40줄 중 35개만 서로 달랐다.

## Redis 점수에 64비트 ID를 넣으면

커서 방식을 정렬된 셋으로 그대로 옮기면 이렇게 된다. 점수와 멤버를 모두 글 ID로 두고, 다음 페이지는 "커서보다 점수가 작은 것"을 `BYSCORE`로 가져온다. 2026년 10월 22일 09:00:00(UTC)에 쓰인 글 두 개와 몇 ms 뒤의 글 두 개를 Snowflake 형식 ID로 만들어 넣었다. 앞의 둘은 같은 밀리초에 생겨 순번만 0과 1로 다르다.

```text
127.0.0.1:6420> ZADD feed:me 2113193641374646272 2113193641374646272 2113193641374646273 2113193641374646273 2113193641395617792 2113193641395617792 2113193641412395008 2113193641412395008
(integer) 4
127.0.0.1:6420> ZRANGE feed:me +inf -inf BYSCORE REV LIMIT 0 3 WITHSCORES
1) "2113193641412395008"
2) "2.113193641412395e+18"
3) "2113193641395617792"
4) "2.1131936413956178e+18"
5) "2113193641374646273"
6) "2.1131936413746463e+18"
127.0.0.1:6420> ZRANGE feed:me (2113193641374646273 -inf BYSCORE REV LIMIT 0 3
(empty array)
```

1페이지는 세 개를 잘 줬다. 마지막 글 `…273`을 커서로 2페이지를 달라고 했더니 빈 배열이 왔다. 남은 글 `…272`가 사라졌다.

Redis 점수는 배정밀도 실수(double)라서 2의 53제곱(약 9×10^15)까지만 정수를 정확히 담는다. 19자리 Snowflake ID는 그보다 훨씬 커서 점수로 바뀌는 순간 반올림된다. 이 범위에서는 이웃한 실수 사이 간격이 256이라, 1밖에 차이 나지 않는 `…272`와 `…273`은 같은 점수가 됐다. "`…273`보다 작은 점수"를 찾으니 같은 점수의 `…272`도 함께 빠졌다. 같은 밀리초에 글이 두 개 이상 쓰일 때만 생기므로 테스트에서는 잘 안 보이고 트래픽이 많을 때 가끔 글이 사라진다. 가장 찾기 어려운 종류의 버그다.

고치는 방법은 점수와 멤버의 역할을 나누는 것이다. 점수는 ID에서 꺼낸 밀리초 시각(13자리, 2의 53제곱보다 작다)으로 두고, 멤버는 ID 문자열 그대로 둔다. 같은 점수끼리는 멤버를 사전순으로 정렬하는데, 자릿수가 같은 숫자 문자열은 사전순과 크기순이 같다. 커서는 마지막 멤버로 두고, 다음 페이지는 그 멤버의 순위를 찾아 그 뒤부터 준다.

```text
127.0.0.1:6420> ZADD feed:me 1792659600000 2113193641374646272 1792659600000 2113193641374646273 1792659600005 2113193641395617792 1792659600009 2113193641412395008
(integer) 4
127.0.0.1:6420> ZRANGE feed:me 0 1 REV
1) "2113193641412395008"
2) "2113193641395617792"
127.0.0.1:6420> ZADD feed:me 1792659660000 2113193893032886272
(integer) 1
127.0.0.1:6420> ZREVRANK feed:me 2113193641395617792
(integer) 2
127.0.0.1:6420> ZRANGE feed:me 3 4 REV
1) "2113193641374646273"
2) "2113193641374646272"
```

1페이지 두 개를 읽는 사이 새 글이 하나 들어왔다. 커서 멤버 `…792`의 순위를 `ZREVRANK`로 다시 찾으니 2가 나왔고(새 글 때문에 1에서 2로 밀렸다), 그 다음 칸부터 가져와 같은 밀리초의 두 글을 모두 받았다. 순위를 매번 커서 멤버로 다시 찾으니 offset처럼 밀리지 않는다.

커서로 쓴 글이 그사이 지워졌거나 상한 500개 밖으로 밀려나면 `ZREVRANK`가 nil을 돌려준다. 그때는 ID에서 시각을 꺼내 그 시각 이하를 `BYSCORE`로 가져오고, 멤버가 커서 이상인 것을 버린다. 이 규칙은 아래 연습 문제에서 직접 짜 볼 수 있다.

## 500개 너머로 내려가면

## 피드가 이상하다는 문의가 오면

피드 문의는 증상별로 보는 곳이 정해져 있다.

- 같은 글이 연달아 두 번 나온다. 페이지를 offset으로 나누고 있는지 먼저 본다. 커서를 쓰는데도 겹친다면 피드를 리스트로 두고 팬아웃이 재시도된 경우다. 피드 캐시에서 그 사용자의 목록을 직접 꺼내 같은 ID가 두 번 있는지 확인한다.
- 친구 글 하나가 내 피드에서만 빠졌다. 그 글 ID와 바로 위 글 ID의 시각이 같은 밀리초인지 본다. 점수 정밀도 문제라면 커서 경계에서만 빠진다. 아니라면 팬아웃이 아직 안 끝났거나 내 피드가 그 시각에 활성 대상이 아니었는지 본다.
- 지운 글이 아직 보인다. 글 캐시의 만료 시간과 삭제 시 캐시를 지우는지 확인한다. 피드 캐시에 ID가 남아 있는 건 정상이고, 본문을 붙이는 단계에서 걸러야 한다.
- 피드가 느리다. 한 페이지를 만들 때 캐시 왕복이 몇 번인지 추적(트레이스)으로 센다. 항목마다 묻는 코드가 숨어 있으면 왕복 수가 페이지 크기만큼 늘어나 있다. 왕복 수가 정상이면 숫자 캐시의 핫 키를 의심한다.

## 커서로 페이지 넘기기

커서 페이지를 직접 짜 보자. `ids`는 최신순(큰 수가 앞)으로 정렬된 글 ID 배열, `cursor`는 마지막으로 본 ID 또는 첫 페이지면 `null`, `limit`은 페이지 크기다. `{ items, next }`를 돌려준다. `items`는 커서보다 작은 ID 중 앞에서부터 `limit`개, `next`는 뒤에 글이 더 남아 있으면 `items`의 마지막 ID이고 없으면 `null`이다. 커서가 가리키던 글이 지워져 배열에 없어도 동작해야 한다.

## 다음에 읽을 글

읽는 쪽은 이렇게 정리된다. 피드 캐시에서 ID를 꺼내고, 글·사용자·숫자 캐시에서 내용을 묶음으로 가져와 붙인다. 캐시는 바뀌는 속도로 나누고, 항목마다 따로 묻지 않는다. 페이지는 칸 번호가 아니라 마지막으로 본 글로 넘긴다. Redis 점수에 64비트 ID를 넣으면 같은 밀리초의 글이 사라지니 점수는 시각, 멤버는 ID로 나눈다. 캐시 밖의 오래된 글과 돌아온 사용자의 빈 피드는 읽기 시점 팬아웃으로 채운다.

뉴스 피드 두 편은 여기까지다. 다음 장은 [㉖ 채팅 ①](/posts/sd-chat-connections)이다. 피드는 새 글이 있는지 앱이 물어보는 구조였는데, 채팅은 서버가 메시지를 즉시 밀어 줘야 해서 연결을 붙잡아 두는 서버라는 다른 문제가 생긴다.

## 면접에서 나올 만한 질문

### 피드를 읽을 때 서버에서는 무슨 일이 일어나나요?

피드 캐시에서 내 글 ID를 최신순으로 꺼내고, 팔로우한 유명인의 최근 글을 당겨 와 합친다. 그 ID들로 글 캐시에서 본문을, 사용자 캐시에서 작성자 정보를, 숫자 캐시에서 좋아요 수와 내 반응을 한 번에 가져와 붙인다. 캐시에 없는 글은 DB에서 모아 읽어 채우고, 지워진 글과 차단한 사람의 글은 거른 뒤 다음 페이지 커서와 함께 돌려준다.

### 피드 캐시에 글 본문까지 넣지 않는 이유는요?

글을 팔로워 수만큼 복사하면 메모리가 수백 배로 늘고, 글을 고치거나 좋아요가 늘 때마다 모든 사본을 고쳐야 하기 때문이다. ID만 넣으면 본문은 글 캐시 한 곳에서 관리하고, 바뀌는 속도가 다른 데이터를 칸별로 나눠 만료와 무효화를 따로 정할 수 있다. 대신 읽을 때 여러 캐시를 묶음 요청으로 들른다.

### offset 대신 커서로 페이지를 나누는 이유는요?

피드는 맨 앞에 계속 새 글이 들어오는 목록이라, offset으로 자르면 새 글만큼 이미 본 글이 다음 페이지에 다시 나오고 글이 지워지면 건너뛴다. 커서는 마지막으로 본 글을 기억해 그보다 오래된 글부터 주므로 앞에서 무슨 일이 생겨도 겹치거나 빠지지 않는다. 깊은 페이지에서 앞부분을 세며 건너뛰는 비용도 없다.

### Redis 정렬된 셋의 점수에 Snowflake ID를 넣으면 어떤 문제가 있나요?

점수가 배정밀도 실수라 2의 53제곱이 넘는 64비트 ID는 반올림되고, 같은 밀리초에 생긴 ID들이 같은 점수가 된다. 그러면 "커서보다 작은 점수"로 다음 페이지를 찾을 때 같은 점수의 글이 함께 빠진다. 점수는 ID에서 꺼낸 밀리초 시각으로, 멤버는 ID 문자열로 두고, 커서 멤버의 순위로 다음 페이지를 찾는다.

### 피드 캐시 메모리가 너무 큽니다. 무엇을 줄일 수 있나요?

먼저 사용자당 상한을 줄인다. 대부분의 사용자가 앞 몇 페이지만 보니 그보다 깊은 부분은 DB에서 모아 오면 된다. 활성 사용자에게만 피드를 두고, 정렬된 셋이 listpack 형식에 들어가도록 상한과 설정을 맞추거나 리스트로 바꾼다. 측정에서 500개 기준 skiplist는 항목당 127바이트, listpack은 21바이트, 리스트는 11바이트였지만 listpack은 쓰기가 느려지므로 쓰기 양과 함께 따진다.

### 피드 캐시가 비어 있는 사용자는 어떻게 처리하나요?

팔로우 목록을 읽고 작성자별 타임라인을 모아 합쳐 피드를 다시 만든 뒤 캐시에 넣는다. 같은 사용자의 재구성이 동시에 여러 번 돌지 않게 짧은 락을 걸고, 캐시 장애 뒤처럼 많은 사용자가 한꺼번에 비면 재구성 작업 수를 제한해 DB를 보호한다.

### 트래픽이 10배가 되면 읽기 쪽에서 무엇이 먼저 버거워지나요?

캐시 왕복 수와 핫 키다. 한 페이지에 들르는 캐시를 묶음 요청과 병렬 요청으로 최소화하고, 캐시를 샤드로 나눠 늘린다. 유명인 글의 본문과 좋아요 수처럼 모두가 읽는 키는 복제본을 두거나 서버 메모리에 아주 짧게 한 번 더 캐시한다. 피드 캐시가 비는 사용자가 늘면 재구성이 DB로 몰리니 그 경로의 제한도 함께 본다.
