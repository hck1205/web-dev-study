## 클릭은 1,200인데 세션은 800이다

주간 회의에 숫자 두 개가 올라왔다. Search Console은 지난주 구글 검색 클릭이 1,200이라고 하고, GA4의 "Organic Search" 세션은 800이다. 누군가 묻는다. "400명은 어디 갔어요?"

어느 한쪽이 고장 난 게 아니다. 두 도구는 다른 곳에서, 다른 단위로, 다른 규칙으로 센다. Search Console은 구글 쪽에서 검색 결과의 링크가 눌린 순간을 센다. GA4는 내 페이지에서 자바스크립트 태그가 실행되고, 그 방문이 어디서 왔는지 판단해 채널을 붙인 다음 센다. 그 사이에 사람이 빠지기도 하고, 채널이 바뀌기도 한다.

이 글은 그 틈을 하나씩 본다. 노출·클릭·CTR·평균 게재순위가 정확히 무엇을 세는지, 방문이 "오가닉"이 되는 원리, 직접 유입으로 새는 트래픽, AI 답변에서 오는 유입과 클릭 없이 끝나는 검색까지. 구글이 페이지를 크롤하고 색인하는 쪽은 [접근 로그와 Search Console](/posts/seo-log-file-analysis-search-console)에서 다뤘다. 여기는 색인된 다음, 사람이 실제로 오는지를 재는 이야기다.

## 숫자가 다른 이유를 하나씩 맞춘다

틈은 사람이 빠지는 것 말고도 집계 규칙에서 생긴다. 숫자를 맞춰 볼 때 확인하는 순서다.

단위가 다르다. 클릭은 클릭이고 세션은 방문이다. 한 사람이 검색 결과에서 같은 페이지를 두 번 누르고 30분 안에 돌아다니면 클릭 2, 세션 1이다. 반대로 한 번 들어와 탭을 띄워 두고 한 시간 뒤 다시 보면 클릭 1, 세션 2가 될 수 있다.

시간대가 다르다. Search Console의 날짜는 미국 태평양 시간 기준이고, GA4는 속성에 설정한 시간대(한국이면 보통 서울)다. 하루 단위로 비교하면 16~17시간이 어긋난다. 일 단위가 아니라 주 단위로 맞춘다.

검색 유형이 다르다. Search Console 실적 보고서는 웹, 이미지, 동영상, 뉴스 같은 검색 유형을 나눠 보여 주고, Discover와 Google 뉴스는 별도 보고서다. GA4의 Organic Search에는 구글 이외의 검색 엔진(네이버, 빙, 다음)도 다 들어 있다. 국내 서비스는 이 차이가 크다.

주소가 다르다. Search Console은 클릭과 노출을 구글이 고른 대표 주소(canonical)에 몰아서 기록한다. `?utm_source=` 같은 파라미터 주소로 들어온 방문이 GA4에는 따로 보이는데 Search Console에서는 한 주소로 합쳐진 것처럼 보인다.

데이터가 늦다. Search Console은 보통 이틀쯤 늦게 채워지고, 최근 데이터는 나중에 조금 바뀔 수 있다. 어제 숫자를 비교하면 거의 늘 Search Console이 적다.

이걸 다 맞추고도 남는 틈은 태그가 실행되지 않은 방문과, 출처를 잃어 다른 채널로 간 방문이다. 두 숫자를 같게 만들려고 애쓰기보다는 그 비율이 갑자기 바뀌는지를 본다. 평소 클릭 대비 세션이 65% 근처였는데 배포 뒤 40%로 떨어졌다면, 페이지가 느려졌거나 태그가 깨졌다는 신호다.

## 구글 바깥의 검색

국내 서비스라면 구글 숫자만으로는 반쪽이다. GA4의 Organic Search에는 네이버, 다음, 빙 검색 유입이 다 들어 있는데 Search Console은 구글만 보여 준다. 클릭 1,200과 세션 800을 비교하기 전에 GA4에서 세션 소스를 google로 좁혀야 같은 범위의 비교가 된다. 이걸 빼먹으면 반대로 GA4가 Search Console보다 많아 보이기도 한다.

네이버는 서치어드바이저, 빙은 Bing Webmaster Tools에서 같은 종류의 보고서를 준다. 수집 현황, 노출과 클릭 같은 숫자가 있지만 항목 이름과 집계 기준은 서비스마다 다르니 구글 숫자와 바로 더하지 않는다. 검색 엔진마다 따로 추세를 보고, 비중이 큰 쪽을 먼저 챙긴다. 빙의 색인은 Copilot 같은 서비스의 답변 출처로도 쓰이니 AI 쪽 노출을 신경 쓴다면 빙도 함께 등록해 둔다.

## 노출, 클릭, CTR, 평균 게재순위가 세는 것

Search Console 실적 보고서의 네 숫자를 정확히 읽어 두자. 구글 문서의 정의를 줄이면 이렇다.

노출은 내 사이트의 링크가 사용자가 본 검색 결과 페이지에 실린 횟수다. 결과 페이지의 아래쪽에 있어 스크롤하지 않았어도, 그 페이지가 로드됐으면 센다. 다만 2쪽에 있는 결과는 사용자가 2쪽을 열어야 노출이 된다. 이미지 묶음이나 펼쳐야 보이는 결과처럼 예외 규칙이 있는 요소도 있다.

클릭은 검색 결과에서 내 사이트로 나가는 링크를 누른 횟수다. 결과 안에서 다른 구글 검색으로 이어지는 링크는 세지 않는다.

CTR은 클릭을 노출로 나눈 값이다.

평균 게재순위는 노출이 생길 때마다 내 사이트의 결과 중 가장 위에 있던 위치를 기록하고 노출 수로 평균 낸 값이다. 한 결과 페이지에 내 사이트 링크가 3위와 7위에 함께 나오면 그 노출의 위치는 3이다.

여기서 집계 단위가 하나 더 있다. 보고서를 속성(사이트) 단위로 보면 한 결과 페이지에 내 링크가 둘 나와도 노출 1이다. 페이지 단위로 보면 두 페이지가 각각 노출 1이다. 그래서 페이지 탭의 노출 합계가 위쪽 총계보다 클 수 있다. 숫자가 안 맞는다고 느껴질 때 먼저 확인할 것 중 하나다.

## 평균 게재순위가 나빠졌는데 클릭은 늘었다

평균 게재순위는 가장 많이 오해받는 숫자다. 쿼리 두 개로 시작해 보자.

```text
쿼리            클릭   노출   위치
examshop 코트    300   1000   1.2
울 코트 추천      40   2000   6.5
```

사이트 전체 평균 게재순위는 노출로 가중한 평균이다. (1.2×1000 + 6.5×2000) / 3000 = 4.7. CTR은 340/3000 = 11.3%다.

다음 달, 새로 쓴 글이 "겨울 코트"라는 큰 쿼리에서 28위로 노출되기 시작했다. 노출 5,000에 클릭 15다. 세 쿼리를 합치면 평균 게재순위는 19.3, CTR은 4.4%가 된다. 그래프만 보면 순위가 4.7에서 19.3으로 무너지고 CTR은 반 토막이 났다. 실제로는 아무것도 떨어지지 않았고 클릭은 340에서 355로 늘었다. 새로 노출되기 시작한 깊은 순위가 평균을 끌어내렸을 뿐이다.

아래에서 직접 계산해 보자. 쿼리 행 목록을 받아 합계와 CTR(%, 소수 첫째 자리), 노출 가중 평균 게재순위(소수 첫째 자리)를 돌려준다.

  let clicks = 0, impressions = 0, posSum = 0;
  for (const r of rows) {
    clicks += r.clicks;
    impressions += r.impressions;
    posSum += r.position * r.impressions;
  }

    clicks,
    impressions,
    ctr: Math.round((clicks / impressions) * 1000) / 10,
    position: Math.round((posSum / impressions) * 10) / 10,
  };

위치를 그냥 산술 평균하면 (1.2 + 6.5 + 28) / 3 = 11.9가 나온다. 노출이 1,000인 쿼리와 5,000인 쿼리를 똑같이 취급한 틀린 값이다. 쿼리 행을 내려받아 대시보드에서 다시 합칠 때 자주 하는 실수다.

그래서 평균 게재순위는 쿼리나 페이지를 좁혀서 본다. 사이트 전체의 평균은 "노출 구성이 바뀌었다"는 신호 정도로만 쓰고, 중요한 쿼리 몇 개를 정해 그 쿼리의 위치 추이를 따로 본다.

## 표에 안 나오는 쿼리

쿼리 탭의 클릭을 다 더해도 위쪽 총 클릭보다 작다. 이것도 정상이다. 구글은 아주 적은 수의 사용자만 검색한 쿼리를 익명화 쿼리로 처리해 표에서 뺀다. 개인 정보를 지키기 위해서다. 총계에는 포함되고 쿼리 표에는 없다. 롱테일 쿼리가 많은 사이트는 클릭의 상당 부분이 이렇게 표 밖에 있다.

이 동작은 필터를 걸 때 한 번 더 숫자를 흔든다. 쿼리 조건으로 필터를 걸면(예: "코트"를 포함하는 쿼리) 익명화 쿼리는 어느 조건에도 맞는지 알 수 없으니 결과에서 빠진다. 그래서 "코트 포함"과 "코트 미포함"을 더해도 전체가 되지 않는다. 브랜드·비브랜드 비율을 낼 때 이 빈칸을 잊으면 두 쪽 모두 실제보다 작게 잡힌다.

페이지 필터는 다르다. 페이지 조건으로만 거르면 익명화 쿼리의 클릭도 그 페이지의 숫자에 들어간다. 쿼리를 모르는 클릭까지 보고 싶다면 페이지 단위로 보고, 쿼리 단위 분석은 표에 보이는 부분에 대한 이야기라고 적어 둔다.

화면 표는 1,000행까지만 보여 준다는 한계도 겹친다. API로 더 많은 행을 받거나 BigQuery 내보내기를 쓰면 익명화 쿼리가 `is_anonymized_query` 같은 표시와 함께 집계 행으로 들어와 "표 밖에 얼마나 있는지"를 셀 수 있다. API와 내보내기 설정은 [접근 로그와 Search Console](/posts/seo-log-file-analysis-search-console)에 있다.

## 브랜드 검색과 비브랜드 검색을 나눈다

"examshop 코트"를 검색한 사람은 이미 우리를 안다. 이 쿼리의 클릭은 SEO를 잘해서라기보다 브랜드가 알려져서 생긴다. TV 광고를 한 주에 브랜드 쿼리 클릭이 두 배가 되면 "SEO 성과"가 두 배로 보인다. 그래서 브랜드 쿼리와 비브랜드 쿼리를 나눠서 본다.

Search Console의 쿼리 필터는 정규 표현식(RE2 문법)을 지원한다. 브랜드 이름과 흔한 오타, 영문·한글 표기를 하나의 식으로 묶는다.

```text
쿼리 필터 → 맞춤(정규식) → 다음과 일치하지 않는 검색어
(?i)(examshop|exam shop|이그잼샵|이그젬샵)
```

일치하는 쪽이 브랜드, 일치하지 않는 쪽이 비브랜드다.

앞의 세 쿼리 예로 나눠 보면 이렇다.

```text
구분       클릭   노출
브랜드      300   1000   (examshop 코트)
비브랜드     55   7000   (울 코트 추천, 겨울 코트)
```

클릭 355 중 300, 약 84.5%가 브랜드다. 사이트 전체 클릭이 늘어도 그게 브랜드 쪽이라면 SEO가 잘된 게 아니라 이름이 알려진 것이다. 비브랜드 55를 따로 추적해야 새 글과 구조 개선이 효과가 있었는지 보인다. SEO 작업의 효과는 비브랜드 쪽에서 본다. 브랜드 쿼리에서 순위가 떨어지는 건 다른 문제(사칭 사이트, 리뷰 사이트가 위로 올라옴)의 신호다. 익명화 쿼리는 어느 쪽인지 모르니 비율 계산에서는 "모름"으로 따로 둔다.

## 방문이 오가닉이 되는 원리

GA4는 방문마다 소스(source)와 매체(medium)를 정하고, 그 둘을 규칙에 맞춰 기본 채널 그룹으로 묶는다. 근거는 두 가지다.

하나는 주소의 UTM 파라미터다. 링크를 만든 쪽이 직접 출처를 적어 둔 것이라 가장 우선한다.

<UrlAnatomy

  ]}
/>

다른 하나는 UTM이 없을 때 쓰는 Referer, 즉 브라우저가 알려 주는 직전 페이지의 출처다. 출처가 `www.google.com`이면 소스는 google, 매체는 organic이 되고, GA4의 규칙상 "소스가 검색 사이트 목록에 있거나 매체가 organic"이면 Organic Search다. 광고 클릭은 구글 애즈의 자동 태깅(`gclid`)이나 `cpc` 같은 매체 값으로 유료 채널로 간다. 소스가 `(direct)`이고 매체가 `(none)`이면 Direct다. 출처를 알려 주는 정보가 아무것도 없을 때 남는 곳이다.

여기서 흔한 실수가 둘 있다. 사이트 안의 링크에 UTM을 붙이는 것이다. 홈 배너에 `?utm_source=banner`를 달면, 검색으로 들어와 배너를 누른 사람의 세션 출처가 배너로 바뀌어 오가닉 성과가 줄어든다. UTM은 외부에서 들어오는 링크에만 쓴다. 다른 하나는 UTM 값을 대소문자 섞어 쓰는 것이다. GA4는 값을 그대로 구분한다.

## Direct로 새는 트래픽

Direct는 "주소를 직접 쳤다"가 아니라 "출처를 모른다"에 가깝다. 실제로는 다른 곳에서 왔는데 출처가 지워져 Direct에 쌓이는 방문이 적지 않다.

Referrer-Policy가 출처를 지운다. 링크를 건 쪽 페이지가 `Referrer-Policy: no-referrer`를 쓰거나 링크에 `rel="noreferrer"`가 있으면 브라우저는 Referer를 보내지 않는다. 최신 브라우저의 기본 정책은 `strict-origin-when-cross-origin`이라 다른 사이트로 갈 때 출처(도메인)만 보내고, HTTPS 페이지에서 HTTP 페이지로 갈 때는 아무것도 보내지 않는다. 우리 사이트의 일부가 아직 HTTP라면 거기로 들어오는 방문은 출처를 잃는다. 헤더 자체의 의미는 [웹 보안 헤더](/posts/web-security-headers)에 있다.

앱이 출처를 지운다. 메신저, SNS 앱의 내장 브라우저나 이메일 앱은 Referer를 보내지 않거나 앱 자체를 출처로 남기지 못하는 경우가 많다. 카카오톡 대화방에 공유된 링크로 들어온 방문은 대개 Direct다. 공유되는 링크를 우리가 만든다면(공유 버튼) UTM을 붙여 둔다.

문서와 복사가 출처를 지운다. PDF, 사내 문서, 메모 앱의 링크, 주소창에 붙여 넣은 링크는 Referer가 없다.

Direct가 이유 없이 늘고 오가닉이 같은 만큼 줄었다면, 사람이 바뀐 게 아니라 출처가 바뀐 것일 수 있다. 랜딩 페이지별로 Direct 세션을 보면 힌트가 나온다. 사람이 주소를 외워서 칠 리 없는 깊은 상세 페이지에 Direct가 많다면 대부분 출처를 잃은 다른 유입이다.

## 서버 로그로 세 번째 숫자를 만든다

Search Console과 GA4가 계속 어긋나면 서버 접근 로그를 세 번째 기준으로 쓴다. 로그는 자바스크립트 태그와 상관없이 요청이 오면 남으니 광고 차단기와 동의 거부의 영향을 받지 않는다. 대신 봇이 섞이고(사람만 남기는 법은 [접근 로그 분석](/posts/seo-log-file-analysis-search-console)에 있다), 세션 개념이 없으며, 캐시된 응답은 원본 서버에 남지 않는다.

아래는 글을 위해 만든 사람 방문 로그 2,206줄에서 Referer의 호스트만 뽑아 센 것이다. Nginx `combined` 형식에서 따옴표로 자르면 네 번째 칸이 Referer다.

```bash
# Referer 칸($4)에서 호스트만 꺼내 센다. 우리 사이트 안에서 온 요청은 뺀다
awk -F'"' '$4 !~ /shop\.example\.com/ {
  split($4, u, "/"); host = (u[3] == "" ? "(none)" : u[3]); print host
}' human.log | sort | uniq -c | sort -rn
```

```text
    520 www.google.com
    400 (none)
    310 search.naver.com
     30 m.facebook.com
     22 www.bing.com
     18 chatgpt.com
      6 www.perplexity.ai
```

`(none)`이 Referer가 `-`인 요청, 즉 GA4라면 Direct로 갈 방문이다. 이 숫자에는 태그가 막힌 방문도 들어 있으니 GA4의 같은 채널과 비교하면 태그가 놓친 비율을 대략 짐작할 수 있다. 로그에서 구글 Referer 요청이 Search Console 클릭과 비슷하고 GA4 오가닉만 크게 적다면 태그 쪽 문제, 로그도 같이 적다면 클릭 뒤 페이지에 닿기 전에 떠난 사람이 많은 것이다.

## AI 답변에서 오는 유입을 따로 센다

ChatGPT, Perplexity, Copilot, Gemini 같은 AI 답변에서 출처 링크를 눌러 오는 방문이 생겼다. 이 방문은 기본 채널 그룹에서 대개 Referral로 들어간다. 소스가 `chatgpt.com`, `perplexity.ai`, `copilot.microsoft.com`, `gemini.google.com` 같은 값으로 찍힌다. ChatGPT는 답변의 링크에 `utm_source=chatgpt.com`을 붙이는 경우가 있어서 Referer가 없는 앱 환경에서도 출처가 남는다. 다만 이런 동작은 서비스마다, 시기마다 바뀌니 실제 소스 값 목록을 보고 규칙을 만든다.

수가 아직 작아도 따로 떼어 둘 이유가 있다. Referral 안에 섞이면 추세를 볼 수 없다. GA4 관리 화면에서 맞춤 채널 그룹을 만들고, 기본 Referral 규칙보다 위에 "AI" 채널을 둔다.

```text
채널 이름: AI Assistants
조건: 세션 소스가 다음 정규식과 일치
(?i)^(chatgpt\.com|chat\.openai\.com|perplexity\.ai|.*\.perplexity\.ai|copilot\.microsoft\.com|gemini\.google\.com|claude\.ai)$
순서: Referral보다 위
```

규칙의 순서가 중요하다. 채널 그룹은 위에서부터 처음 맞는 규칙을 고른다. 아래 그림은 소스가 `chatgpt.com`이고 매체가 `referral`인 세션 하나가 규칙을 차례로 지나가는 모습이다.

구글의 AI 개요(AI Overviews)는 다르다. 구글 검색 결과 안의 일부라서 거기서 누른 링크는 Referer가 `www.google.com`이고 GA4에서는 일반 Organic Search와 구분되지 않는다. Search Console 쪽에서는 웹 검색 실적에 함께 집계된다. 구글 문서는 AI 개요 안의 링크들이 모두 AI 개요 자체의 위치 하나를 공유한다고 설명한다. AI 개요가 맨 위에 뜨면 그 안의 내 링크는 위치 1로 기록되는 것이다. 그래서 AI 개요가 생긴 쿼리에서 "순위는 올랐는데 클릭은 줄었다"는 모양이 나오기도 한다. AI 답변이 어떤 출처를 고르는지는 [AI 검색과 그라운딩](/posts/ai-search-grounding-geo)에서 다룬다.

## 클릭 없이 끝나는 검색

검색 결과 화면에서 답을 다 얻고 아무것도 누르지 않는 검색을 제로 클릭 검색이라고 부른다. 날씨, 환율, 영업시간, 단위 변환 같은 질문은 원래 그랬고, 추천 스니펫과 AI 개요가 늘면서 설명형 질문에서도 늘었다.

측정 쪽에서 이게 뜻하는 건 하나다. 노출은 생기는데 클릭이 없다. CTR이 떨어지는 게 순위가 떨어져서인지, 결과 화면이 답을 대신 줘서인지를 구분해야 한다. 쿼리별로 보면 구분이 된다. 위치는 그대로인데 CTR만 떨어진 쿼리가 "~란", "~ 차이" 같은 정의형 질문에 몰려 있으면 후자일 가능성이 크다.

귀속도 어렵다. 결과 화면에서 우리 브랜드 이름을 보고, 며칠 뒤 주소를 직접 쳐서 들어오면 그 방문은 Direct이고 처음 검색과 이어지지 않는다. 이런 효과를 정확히 재는 방법은 없다. 브랜드 쿼리 노출 추이, Direct 신규 사용자 추이처럼 간접 지표를 같이 보는 정도가 현실적이다.

## AI 답변에서 얼마나 인용되나

AI 답변은 로그인과 대화 맥락에 따라 답이 달라지고 노출 수를 알려 주는 보고서도 없다. 그래서 "얼마나 보이는가"는 직접 표본을 떠서 잰다. 방법은 순위 추적과 비슷하다.

1. 우리 분야에서 사람이 실제로 물을 만한 질문 목록을 정한다(예: 50개). 브랜드 질문과 비브랜드 질문을 나눈다.
2. 정해 둔 서비스들에 같은 질문을 주기적으로 묻고 답을 저장한다. 같은 질문도 여러 번 물어 본다. 답이 매번 다르기 때문이다.
3. 답마다 우리 사이트가 출처로 인용됐는지(인용률), 출처 목록에서 몇 번째인지, 링크 없이 이름만 언급됐는지, 경쟁 사이트는 얼마나 인용됐는지(답변 점유율)를 기록한다.

이 숫자는 표본이라 오차가 크다. 질문 목록을 바꾸면 숫자가 크게 흔들리니 목록은 고정하고 추세만 본다. 서비스 쪽 모델이 바뀌면 하루 사이에 크게 달라질 수 있다는 점도 함께 적어 둔다. 실제 방문으로 이어졌는지는 앞의 AI 채널 세션으로 확인한다.

## 측정을 깨뜨리는 흔한 배포

숫자가 갑자기 바뀌었는데 검색 쪽에는 아무 일이 없었다면, 측정 자체가 바뀐 경우가 많다. 개발자가 만드는 실수들이다.

리다이렉트가 쿼리스트링을 버린다. 옛 주소에서 새 주소로 301을 걸면서 쿼리를 붙여 넘기지 않으면 `?utm_source=newsletter`가 사라진다. 뉴스레터 방문이 출처를 잃고 Direct나 앞 세션의 출처로 잡힌다. 리다이렉트 규칙은 쿼리를 보존하는지 `curl -sI`로 `Location` 헤더를 확인한다.

결제 도메인이 출처를 덮어쓴다. 결제를 외부 PG 도메인에서 하고 우리 사이트로 돌아오면, 돌아오는 요청의 Referer가 PG 도메인이라 새 세션의 출처가 PG가 된다. 검색으로 들어와 산 사람의 전환이 PG Referral로 잡힌다. GA4의 "원치 않는 추천 목록"에 PG 도메인을 넣는다.

태그가 두 번 붙는다. `gtag.js`를 직접 넣은 상태에서 태그 관리자(GTM)로 같은 측정 ID를 또 넣으면 페이지뷰가 두 배가 된다. 세션 수는 비슷한데 페이지뷰와 이벤트만 두 배로 뛰면 이걸 의심한다.

SPA에서 페이지뷰가 안 잡히거나 두 번 잡힌다. GA4의 향상된 측정은 기본으로 브라우저 기록이 바뀔 때 페이지뷰를 보낸다. 여기에 라우터 이벤트에서 직접 `page_view`를 보내는 코드를 더하면 중복이고, 향상된 측정을 끈 상태에서 직접 보내는 코드도 없으면 첫 화면만 잡힌다.

배포 체크리스트에 "UTM을 붙인 주소로 들어가 GA4 실시간 보고서에서 소스가 맞게 보이는지"를 한 줄 넣어 두면 이런 일은 대부분 배포 당일에 잡힌다.

## 순위 추적 도구와 변동 읽기

검색 점유율(share of search)이라는 말도 같은 맥락이다. 우리 분야의 키워드 묶음에서 우리 브랜드와 경쟁 브랜드가 받는 검색량이나 예상 클릭을 나눠 비율로 본다. 절대 숫자보다 경쟁 속 위치가 바뀌는지를 볼 때 쓴다.

순위 추적 도구는 정해 둔 키워드를 정해 둔 위치와 기기에서 매일 검색해 순위를 기록한다. 경쟁사 순위와 "가시성 점수"(키워드별 검색량에 순위별 예상 CTR을 곱해 더한 값)를 보여 주는 게 장점이다. 하지만 한 장소, 한 기기, 로그인하지 않은 상태의 한 번 검색이다. 실제 사용자가 보는 결과는 위치, 기기, 검색 기록에 따라 다르다. 그래서 도구의 순위와 Search Console의 평균 게재순위는 맞지 않는다. 도구는 경쟁 비교와 일일 변동 감지에, Search Console은 실제 노출과 클릭에 쓴다.

순위가 크게 흔들린 주가 있다면 먼저 바깥을 본다. 구글은 핵심 업데이트(core update)를 1년에 몇 번 내놓고, 반영에 보통 2주 안팎이 걸린다. Google Search Status Dashboard에 시작과 끝이 공지된다. 업데이트 기간 중의 숫자는 오르내림이 크니, 끝난 뒤 업데이트 전과 같은 길이, 같은 요일 구성의 기간을 비교한다. 업데이트 하나로 떨어진 사이트가 무엇을 고칠 수 있고 무엇은 아닌지는 [검색 스팸 정책과 개발자의 실수](/posts/search-spam-policies-cloaking)에서 다룬다.

바깥에 이유가 없다면 안을 본다. 배포 기록과 날짜를 맞춘다. 떨어진 게 특정 디렉터리나 특정 템플릿에 몰렸는지, 노출이 떨어졌는지(색인·순위 문제) 노출은 그대로인데 클릭만 떨어졌는지(제목·스니펫·결과 화면 변화)부터 가른다.

## CTR이 낮은 페이지부터 손본다

숫자를 읽었으면 고칠 곳을 고른다. 가장 손이 덜 가는 곳은 이미 노출이 많은데 클릭이 적은 페이지다. 페이지 탭을 노출 순으로 정렬하고 평균 게재순위가 3~10 사이인데 CTR이 같은 위치의 다른 페이지보다 눈에 띄게 낮은 줄을 찾는다. 순위를 올리는 것보다 결과 화면에서 더 눌리게 만드는 게 빠르다.

이때 먼저 확인할 것은 구글이 실제로 보여 주는 제목과 설명이다. 구글은 `title`이 너무 길거나, 모든 페이지에 같은 문구가 붙어 있거나, 내용과 맞지 않으면 제목을 페이지의 `h1`이나 다른 텍스트로 바꿔 보여 준다. 설명(`meta description`)은 더 자주 바뀐다. 검색어에 맞는 본문 문장을 골라 보여 주기 때문이다. 그래서 내가 쓴 제목을 고치기 전에 그 쿼리로 직접 검색해 실제 결과 화면을 본다.

제목을 고친 효과는 같은 쿼리, 같은 위치 범위에서 CTR이 바뀌었는지로 본다. 위치가 함께 바뀌었다면 CTR 변화는 위치 때문일 수 있다. 바꾸기 전 4주와 바꾼 뒤 4주를 같은 요일 구성으로 비교하고, 그 기간에 핵심 업데이트가 끼어 있지 않은지 확인한다.

## SEO 변경은 페이지 묶음으로 실험한다

일반 A/B 테스트는 사용자를 둘로 나눈다. 같은 주소에 사람마다 다른 내용을 주는 방식이다. SEO 변경은 이렇게 실험할 수 없다. 구글봇은 한 명이고, 같은 주소에 다른 내용을 주면 구글은 둘 중 하나만 본다. 봇에게만 다른 내용을 주는 건 클로킹에 가까워진다.

그래서 SEO 실험은 페이지를 나눈다. 템플릿이 같은 상품 상세 2,000개가 있다면 비슷한 트래픽을 가진 두 묶음으로 나누고, 한 묶음에만 제목 형식이나 구조화 데이터를 바꾼다. 그리고 바꾸기 전 기간의 두 묶음 클릭 비율과 바꾼 뒤의 비율을 비교한다. 두 묶음이 원래 같이 움직였다면, 바꾼 뒤 벌어진 만큼이 변경의 효과로 추정된다. 계절이나 업데이트처럼 사이트 전체에 오는 변화는 두 묶음에 함께 오니 상쇄된다.

이 방식에는 조건이 있다. 묶음마다 페이지와 클릭이 충분해야 하고(페이지 수십 개로는 잡음이 효과보다 크다), 묶음을 무작위로 나누되 트래픽 분포가 비슷해야 하며, 반영에 몇 주가 걸리니 기간을 길게 잡는다. 사용자 단위 실험의 표본 크기와 판단 방법은 [A/B 테스트](/posts/ab-testing)에 있다.

## 클릭이 줄었을 때 좁혀 가는 순서

"검색 유입이 20% 줄었다"는 보고를 받으면 Search Console 실적 보고서에서 범위를 하나씩 좁힌다. 날짜 필터의 "비교"를 켜고 줄기 전과 후를 같은 길이로 놓은 다음 탭을 차례로 본다.

1. 검색 유형. 웹만 줄었는지, 이미지나 동영상, Discover가 줄었는지 본다. Discover는 변동이 원래 크고 검색 순위와 다른 이야기다.
2. 노출과 클릭 중 무엇이 줄었나. 노출이 같이 줄었으면 색인이나 순위 문제다. 노출은 그대로인데 클릭만 줄었으면 결과 화면이 바뀌었거나(AI 개요, 새 결과 형태) 제목이 바뀐 것이다.
3. 페이지. 줄어든 클릭이 몇 개 페이지에 몰렸는지, 특정 디렉터리나 템플릿에 몰렸는지 본다. 한 템플릿에 몰렸으면 그 템플릿의 최근 배포를 의심한다.
4. 쿼리. 그 페이지들의 어떤 쿼리가 줄었는지 본다. 브랜드 쿼리면 브랜드 쪽 사정, 비브랜드 정의형 질문이면 제로 클릭 쪽을 의심한다.
5. 국가와 기기. 모바일만 줄었다면 모바일 화면이나 속도 문제일 수 있다. 특정 국가만 줄었다면 `hreflang`이나 지역 리다이렉트를 본다.
6. 색인 쪽 확인. 그 페이지들이 페이지 색인 보고서에서 빠졌는지, URL 검사에서 구글이 고른 대표 주소가 바뀌지 않았는지 본다.

이 순서를 거꾸로, 즉 "쿼리부터" 보면 수천 줄 속에서 길을 잃는다. 큰 칸에서 작은 칸으로 내려간다. 범위가 잡힌 뒤에야 순위 추적 도구나 로그를 열어 원인을 확인한다.

## 무엇을 목표 숫자로 둘까

검색 성과를 숫자 하나로 말해 달라는 요청을 자주 받는다. 숫자 하나는 위험하다. 평균 게재순위는 앞에서 본 것처럼 구성에 따라 흔들리고, 총 클릭은 브랜드 광고에 끌려간다. 그래서 몇 개를 같이 둔다.

- 비브랜드 쿼리 클릭. SEO 작업의 효과에 가장 가까운 숫자다.
- 핵심 페이지 묶음의 노출. 상품 상세, 분류 페이지처럼 사업에 중요한 템플릿별로 나눠 본다.
- 오가닉 랜딩 세션의 전환. 들어온 사람이 가입하거나 구매했는지다. 클릭만 늘고 전환이 그대로면 검색 의도가 맞지 않는 쿼리가 늘었을 수 있다.
- 클릭 대비 세션 비율. 측정이 건강한지 보는 숫자다. 갑자기 떨어지면 성과가 아니라 측정이 깨진 것이다.
- AI 채널 세션과 인용 표본. 아직 작아도 추세를 남겨 둔다.

숫자마다 "어디서 가져왔고 어떤 규칙으로 셌는지"를 대시보드 옆에 적어 둔다. 석 달 뒤 누군가 같은 숫자를 다시 뽑으려 할 때, 시간대나 필터 하나가 달라 숫자가 안 맞는 일을 줄인다.

## 보고서는 한곳에 모은다

Search Console, GA4, 순위 도구, AI 인용 표본을 따로 보면 회의마다 숫자 맞추기로 시간이 간다. Looker Studio(예전 이름 Google Data Studio)는 Search Console과 GA4를 데이터 소스로 바로 붙일 수 있어 한 화면에 놓기 쉽다. 데이터가 크면 Search Console의 BigQuery 내보내기와 GA4의 BigQuery 내보내기를 같은 프로젝트에 두고 랜딩 페이지 주소로 조인한다. 이때 Search Console의 주소는 canonical 기준이고 GA4의 랜딩 페이지에는 파라미터가 붙어 있으니, 조인 전에 파라미터를 지우고 끝 슬래시와 대소문자를 맞춘다.

```sql
-- GA4 BigQuery 내보내기: 지난 7일 세션 시작 이벤트를 수동 소스 기준으로 센다
-- collected_traffic_source에는 이벤트에 실린 UTM과 gclid가 들어 있다
SELECT
  IFNULL(collected_traffic_source.manual_source, '(referrer 기반)') AS utm_source,
  COUNT(*) AS sessions
FROM `my-project.analytics_123456789.events_*`
WHERE _TABLE_SUFFIX BETWEEN FORMAT_DATE('%Y%m%d', DATE_SUB(CURRENT_DATE(), INTERVAL 7 DAY))
                        AND FORMAT_DATE('%Y%m%d', DATE_SUB(CURRENT_DATE(), INTERVAL 1 DAY))
  AND event_name = 'session_start'
GROUP BY utm_source
ORDER BY sessions DESC;
```

내보내기 표의 출처 필드는 여러 개다. `traffic_source`는 사용자를 처음 데려온 출처라 세션 채널과 다르고, `collected_traffic_source`는 이벤트에 실린 UTM 값이다. GA4 화면의 세션 채널과 같은 기준으로 보고 싶으면 세션 단위 출처 필드를 쓰거나 화면의 숫자와 한 번 맞춰 본 뒤 쓴다. 필드 이름은 내보내기 스키마가 바뀌면서 늘어 왔으니 자기 데이터 세트의 스키마를 먼저 확인한다.

숫자 다음에는 행동을 본다. Microsoft Clarity 같은 무료 세션 녹화·히트맵 도구는 검색으로 들어온 사람이 첫 화면에서 무엇을 하고 어디서 나가는지 보여 준다. 클릭은 많은데 바로 나간다면 검색 의도와 페이지가 맞지 않는 것이고, 이건 순위 보고서에서는 보이지 않는다.

## 400명은 사라지지 않았다

클릭 1,200과 세션 800의 차이는 대부분 설명된다. 구글은 링크가 눌린 순간을 세고, GA4는 태그가 실행되고 출처가 남은 방문을 센다. 그 사이에 태그가 실행되지 않은 방문, 출처를 잃고 Direct로 간 방문, 다른 시간대와 다른 주소 집계가 있다. 평균 게재순위는 노출 가중 평균이라 새 쿼리가 들어오면 순위가 나빠진 것처럼 보이고, 표에 없는 익명화 쿼리와 브랜드 쿼리를 나눠야 SEO의 효과가 보인다. AI 답변 유입은 맞춤 채널로 떼어 내고, 클릭 없이 끝나는 검색은 쿼리별 CTR 변화로 읽는다.

## 면접에서 나올 만한 질문

### Search Console 클릭과 GA4 오가닉 세션이 다른 이유는요?

세는 곳과 단위가 다르다. Search Console은 구글에서 링크가 눌린 횟수를 세고, GA4는 내 페이지의 태그가 실행된 방문을 세션 단위로 센다. 태그 전 이탈, 광고 차단, 동의 거부, 출처를 잃은 Direct 분류에서 차이가 생기고, 시간대(태평양 시간과 속성 시간대), canonical 주소 집계, 다른 검색 엔진 포함 여부도 다르다. 차이를 없애기보다 그 비율이 갑자기 변하는지를 본다.

### 평균 게재순위는 어떻게 계산되고 왜 조심해서 읽어야 하나요?

노출마다 내 사이트의 가장 높은 결과 위치를 기록해 노출 수로 평균 낸다. 노출 가중 평균이라 깊은 순위의 큰 쿼리가 새로 노출되기 시작하면 클릭이 늘어도 평균 순위는 나빠진다. 쿼리 행을 다시 합칠 때 산술 평균을 쓰는 것도 흔한 실수다. 중요한 쿼리나 페이지로 좁혀서 추이를 본다.

### GA4는 어떻게 방문을 Organic Search로 분류하나요?

UTM 파라미터가 있으면 그것으로, 없으면 Referer로 소스와 매체를 정한다. 소스가 검색 엔진 목록에 있거나 매체가 organic이면 Organic Search다. 광고는 gclid 자동 태깅이나 cpc 같은 매체로 유료 채널에 가고, 출처 정보가 하나도 없으면 Direct다. 구글은 Referer에 출처만 넘겨서 GA4는 검색어를 알 수 없다.

### Direct 트래픽이 갑자기 늘었다면 무엇을 의심하나요?

사람이 주소를 쳐서 들어왔다기보다 출처를 잃은 방문일 가능성을 먼저 본다. 링크한 쪽의 `no-referrer` 정책, HTTPS에서 HTTP로 가는 링크, 메신저·SNS 앱 내장 브라우저, 문서와 복사한 링크가 출처를 지운다. 깊은 상세 페이지의 Direct 세션이 늘었다면 거의 확실하다. 내가 만드는 공유 링크에는 UTM을 붙인다.

### AI 서비스에서 오는 유입은 어떻게 측정하나요?

GA4에서 chatgpt.com, perplexity.ai 같은 소스를 정규식으로 묶은 맞춤 채널을 만들고, Referral보다 위에 둔다. 채널 규칙은 위에서부터 처음 맞는 것을 고르기 때문이다. 구글 AI 개요의 클릭은 구글 검색 Referer라 일반 오가닉과 구분되지 않는다. 인용 여부는 고정한 질문 목록으로 주기적으로 표본을 떠서 인용률과 점유율 추세로 본다.

### 핵심 업데이트 기간에 순위가 떨어지면 어떻게 판단하나요?

업데이트 반영 중에는 변동이 크니 Search Status Dashboard에서 끝난 것을 확인하고, 업데이트 전과 같은 길이·같은 요일 구성의 기간을 비교한다. 떨어진 범위가 사이트 전체인지 특정 디렉터리·템플릿인지, 노출이 떨어졌는지 클릭만 떨어졌는지를 나눈다. 배포 기록과 날짜를 맞춰 내부 원인부터 배제한다.

### SEO 변경의 효과는 어떻게 실험하나요?

사용자를 나누는 A/B 테스트는 쓸 수 없다. 구글봇은 한 명이라 같은 주소에 다른 내용을 주면 하나만 보고, 봇에게만 다르게 주면 클로킹에 가까워진다. 대신 같은 템플릿의 페이지를 트래픽이 비슷한 두 묶음으로 나눠 한쪽만 바꾸고, 바꾸기 전과 후의 두 묶음 클릭 비율을 비교한다. 사이트 전체에 오는 계절·업데이트 영향은 두 묶음에 함께 와서 상쇄된다.

### 검색 유입이 줄었다는 보고를 받으면 어디부터 보나요?

Search Console에서 기간 비교를 켜고 큰 칸에서 작은 칸으로 좁힌다. 검색 유형, 노출과 클릭 중 무엇이 줄었는지, 어느 페이지·템플릿에 몰렸는지, 어떤 쿼리인지, 국가·기기 순서다. 노출이 함께 줄었으면 색인·순위 문제, 클릭만 줄었으면 결과 화면이나 제목 변화를 의심하고, 마지막으로 배포 기록과 측정 설정이 바뀌지 않았는지 확인한다.
