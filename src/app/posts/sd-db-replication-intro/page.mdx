이 시리즈에서 이 글의 자리: [③ 로드 밸런서와 무상태 웹](/posts/sd-load-balancer-stateless)에서 웹 계층을 여러 대로 늘린 다음 단계다. 다음 글은 [⑤ 캐시와 CDN](/posts/sd-cache-and-cdn-tier)이다. 같은 장의 글은 [① 서버 한 대](/posts/sd-start-single-server), [② 웹과 DB 나누기](/posts/sd-split-web-and-db), [⑥ 데이터 센터 여러 곳](/posts/sd-multi-datacenter), [⑦ 큐, 로그, 자동화](/posts/sd-queue-logging-automation), [⑧ 샤딩 입문](/posts/sd-sharding-intro)이다.

맛집 리뷰 앱의 웹 서버는 이제 로드 밸런서 뒤에 여러 대가 있다. 한 대가 죽어도 나머지가 받는다. 그런데 그 웹 서버들이 묻는 DB는 여전히 한 대다. 저녁 시간이 되면 DB CPU가 90%를 넘는다. 들여다보면 거의 다 읽기다. 식당 목록, 리뷰 목록, 별점 평균. 리뷰를 새로 쓰는 요청은 읽기 수백 건에 한 건꼴이다.

그리고 그 DB가 멈추면 웹 서버가 몇 대든 아무것도 못 한다. 이 글은 DB를 여러 대로 만드는 첫 번째 방법, 복제(replication)를 다룬다. 쓰기는 한 대가 받고, 그 내용을 다른 서버들이 그대로 따라 쓰게 해서 읽기를 나눠 받는다. 그리고 그 서버들 중 하나가 죽으면 무슨 일이 생기는지 직접 꺼 보며 확인한다.

실습은 Redis 7.0 세 대로 했다. 서버를 띄우고 끄는 데 몇 초면 충분해서 복제의 동작을 손으로 확인하기 좋다. Redis의 복제도 PostgreSQL과 MySQL의 기본 설정처럼 비동기 방식이라 원리는 같다. PostgreSQL에서 스탠바이를 실제로 붙이고 지연을 재는 실습은 [DB 복제와 복제 지연 글](/posts/db-replication-sharding)에 있다.

## 읽기는 많고 쓰기는 적다

대부분의 서비스는 읽기가 쓰기보다 훨씬 많다. 맛집 앱에서 리뷰 하나가 써지면 그 리뷰는 수백, 수천 번 읽힌다. [⑩ 용량 추정](/posts/sd-capacity-estimation)에서 계산한 예시에서는 읽기와 쓰기가 600 대 1이었다.

이 비율이 해법을 정한다. 쓰기는 한 곳에서 받아 순서를 지키고, 그 결과를 여러 대에 복사해서 읽기를 나눠 받으면 된다. 쓰기를 받는 서버를 주 DB(primary, 예전 이름은 master), 복사본을 들고 읽기만 받는 서버를 복제본(replica, 예전 이름은 slave)이라고 한다. Redis는 지금도 출력에 옛 이름을 쓴다.

## 복제본은 주 DB의 기록을 따라 쓴다

복제본이 어떻게 같은 내용을 유지하는지 조금만 들여다보자. DB는 데이터를 바꿀 때마다 "무엇을 어떻게 바꿨는지"를 순서대로 로그에 먼저 적는다. PostgreSQL은 이것을 WAL(Write-Ahead Log), MySQL은 binlog라고 부른다. 원래는 서버가 갑자기 꺼졌을 때 복구하려고 쓰는 로그인데, 이 로그를 다른 서버에 보내 그대로 다시 적용하면 복제가 된다.

여기서 중요한 사실이 하나 있다. 기본 설정에서 주 DB는 복제본이 받았는지 기다리지 않는다. 자기 디스크에 쓰면 바로 "성공"이라고 답하고, 로그는 그 뒤에 복제본으로 간다. 이 방식을 비동기 복제라고 한다. 빠르지만, 아주 짧은 순간이라도 복제본은 주 DB보다 뒤처진다. 이 뒤처짐을 복제 지연(replication lag)이라고 한다.

## 세 대로 복제를 걸어 보기

Redis를 7301(주), 7302, 7303(복제본) 포트로 세 개 띄우고, 두 복제본에게 7301을 따라가라고 했다.

```bash
# 세 서버를 띄우고, 7302와 7303에 "7301의 복제본이 되라"고 한다
for p in 7301 7302 7303; do
  redis-server --port $p --save "" --appendonly no --repl-diskless-sync-delay 0 \
    --daemonize yes --pidfile $PWD/r$p.pid
done
redis-cli -p 7302 REPLICAOF 127.0.0.1 7301
redis-cli -p 7303 REPLICAOF 127.0.0.1 7301
# 주 서버에서 복제 상태를 본다
redis-cli -p 7301 INFO replication
```

```text
# Replication
role:master
connected_slaves:2
slave0:ip=127.0.0.1,port=7302,state=online,offset=98,lag=0
slave1:ip=127.0.0.1,port=7303,state=online,offset=98,lag=1
```

`connected_slaves:2`는 복제본 두 대가 붙었다는 뜻이다. 줄마다 `state=online`이면 처음 전체 복사를 마치고 실시간으로 따라오는 중이다. `offset`은 복제본이 지금까지 받은 로그의 위치(바이트 수)다. 주 서버의 위치와 같으면 다 따라온 것이다. 이 숫자를 뒤에서 계속 본다.

주 서버에 쓰고 복제본에서 읽어 본다. 복제본에 직접 쓰는 것도 시도해 본다.

```bash
redis-cli -p 7301 SET review:41 '{"restaurant":"망원 만두","stars":5}'   # 주 서버에 쓴다
redis-cli -p 7302 GET review:41                                           # 복제본에서 읽는다
redis-cli -p 7303 SET review:99 x                                         # 복제본에 쓰려고 하면?
```

```text
OK
{"restaurant":"망원 만두","stars":5}
READONLY You can't write against a read only replica.
```

복제본은 읽기 전용이다. 쓰기를 받으면 주 서버와 내용이 달라지기 때문이다. PostgreSQL 스탠바이도 쓰기를 거절한다(`cannot execute INSERT in a read-only transaction`). 그래서 웹 앱이 쓰기와 읽기를 구분해서 보내야 한다.

## 웹 앱이 읽을 곳과 쓸 곳을 고른다

쓰기와 읽기를 어디로 보낼지는 누군가 정해야 한다. 웹 앱 안의 코드가 정할 수도 있고, 중간의 프록시(PgBouncer 앞단, ProxySQL, 클라우드 DB의 읽기 전용 엔드포인트)가 정할 수도 있다. 처음에는 웹 앱에 연결을 두 개 두는 방법이 가장 단순하다. 쓰기용 연결은 주 DB로, 읽기용 연결은 복제본들로 간다.

작은 라우터를 만들어 돌렸다. 쓰기는 7301로 보내고, 읽기는 7302와 7303에 번갈아 보낸다. 복제본이 응답하지 않으면 다음 복제본으로, 모두 죽으면 주 서버에서 읽는다.

```bash
# 쓰기 한 번, 읽기 네 번. 그다음 복제본을 하나씩 PID로 끄면서 읽는다
node router.mjs
```

```text
write review:50 -> 7301
read  review:50 <- 7302 5
read  review:50 <- 7303 5
read  review:50 <- 7302 5
read  review:50 <- 7303 5
# kill 7302 (pid 10007)
        7302 failed, marked down
read  review:50 <- 7303 5
read  review:50 <- 7303 5
read  review:50 <- 7303 5
# kill 7303 (pid 10013)
        7303 failed, marked down
read  review:50 <- 7301 (primary fallback) 5
read  review:50 <- 7301 (primary fallback) 5
```

복제본 하나가 죽으면 남은 복제본이 읽기를 다 받는다. 둘 다 죽으면 주 서버가 읽기까지 받는다. 서비스는 계속 돈다. 다만 이 구조에서 조심할 점이 있다. 주 서버로 읽기를 넘기는 것은 임시방편이다. 평소 복제본들이 나눠 받던 읽기가 한꺼번에 주 서버로 오면 주 서버가 쓰기까지 못 하게 될 수 있다. 그래서 복제본은 한 대가 죽어도 나머지가 감당할 만큼 두고, 죽은 복제본은 새 서버로 바로 바꾼다.

## 방금 쓴 리뷰가 안 보인다

복제본으로 읽기를 보내면 피할 수 없는 문제가 있다. 앞에서 본 복제 지연이다. 실습에서 7303으로 가는 복제 회선을 일부러 붙잡아 두고 리뷰를 하나 썼다. 이를 위해 7303은 7301을 직접 따라가지 않고, 복제 데이터를 원할 때 멈춰 둘 수 있는 작은 Node.js 중계 프로그램(7399)을 거쳐 따라가게 했다(`REPLICAOF 127.0.0.1 7399`). 네트워크가 막히거나 복제본이 바빠서 늦어지는 상황을 흉내 낸 것이다.

```bash
redis-cli -p 7301 SET review:42 '{"restaurant":"성수 버거","stars":4}'   # 주 서버에 쓴다
redis-cli -p 7302 GET review:42                                           # 잘 따라온 복제본
redis-cli -p 7303 GET review:42                                           # 회선이 막힌 복제본
redis-cli -p 7301 INFO replication | grep ^slave                          # 누가 어디까지 받았나
```

```text
OK
{"restaurant":"성수 버거","stars":4}

slave0:ip=127.0.0.1,port=7302,state=online,offset=196,lag=0
slave1:ip=127.0.0.1,port=7303,state=online,offset=98,lag=0
```

7303은 빈 줄, 그러니까 "그런 리뷰 없음"을 돌려줬다. 오류가 아니다. 7303 입장에서는 정말 아직 없는 것이다. `offset`을 보면 7302는 196까지, 7303은 98에서 멈춰 있다. 98바이트만큼 뒤처졌다.

`lag=0`이라고 안심하면 안 된다는 것도 보인다. Redis의 `lag`는 복제본이 "나 여기까지 받았다"고 마지막으로 알려 온 뒤 몇 초가 지났는지다. 여기서는 복제본이 보내는 확인 신호는 막지 않아서 0으로 나온다. 얼마나 뒤처졌는지는 offset의 차이로 본다. PostgreSQL에서는 `pg_stat_replication`의 `replay_lag`, MySQL에서는 `SHOW REPLICA STATUS`의 `Seconds_Behind_Source`가 같은 역할을 한다.

회선을 풀어 주자 7303도 곧 따라잡았다.

```text
{"restaurant":"성수 버거","stars":4}
```

시간 축으로 펼쳐 보면 이렇다.

- 쓴 사람의 읽기는 잠깐 주 DB로 보낸다. 리뷰를 쓴 뒤 몇 초 동안은 그 사용자의 요청만 주 DB에서 읽는다.
- 쓴 결과를 화면에 바로 그린다. 서버가 돌려준 리뷰를 목록 맨 위에 붙이고, 목록은 나중에 다시 불러온다.
- 정확해야 하는 읽기는 처음부터 주 DB로 보낸다. 결제 상태, 재고, 잔액이 그렇다.

## 주 DB가 죽으면 누가 이어받나

복제본이 죽는 것은 비교적 쉽다. 읽기를 다른 곳으로 돌리면 된다. 어려운 것은 쓰기를 받는 주 DB가 죽을 때다. 쓰기를 받을 곳이 없으니 리뷰 작성, 회원 가입, 좋아요가 모두 멈춘다.

해법은 복제본 하나를 새 주 DB로 올리는 것이다. 이것을 승격(promotion)이라고 한다. 그런데 어느 복제본을 올려야 할까. 실습으로 보자. 다시 7303 회선을 막은 상태에서 리뷰 43을 쓰고, 곧바로 주 서버를 PID로 껐다. 막혀 있던 복제 데이터는 버렸다. 회선이 끊긴 채 주 서버가 죽은 상황이다.

```bash
redis-cli -p 7301 SET review:43 '{"restaurant":"을지로 국수","stars":3}'
kill 9227                                          # 주 서버(7301)를 PID로 끈다
redis-cli -p 7302 INFO replication | grep -E "^role|master_link_status|slave_repl_offset"
redis-cli -p 7303 INFO replication | grep -E "^role|master_link_status|slave_repl_offset"
```

```text
OK
role:slave
master_link_status:down
slave_repl_offset:325
role:slave
master_link_status:down
slave_repl_offset:210
```

두 복제본 모두 `master_link_status:down`, 주 서버를 잃었다. `slave_repl_offset`이 다르다. 7302는 325까지, 7303은 210까지 받았다. 리뷰 43은 어디에 있을까.

```bash
redis-cli -p 7302 GET review:43
redis-cli -p 7303 GET review:43
```

```text
{"restaurant":"을지로 국수","stars":3}

```

7302에는 있고 7303에는 없다. 사용자는 리뷰 43을 쓰고 "성공"을 받았다. 7303을 승격하면 그 리뷰는 사라진다. 그래서 승격할 복제본은 offset이 가장 앞선 것으로 고른다. 7302를 주 서버로 올리고, 7303이 7302를 따라가게 했다.

```bash
redis-cli -p 7302 REPLICAOF NO ONE                 # 7302를 주 서버로 승격
redis-cli -p 7303 REPLICAOF 127.0.0.1 7302         # 7303은 새 주 서버를 따라간다
redis-cli -p 7302 INFO replication
redis-cli -p 7303 GET review:43                    # 7303도 따라잡았나
```

```text
OK
OK
# Replication
role:master
connected_slaves:1
slave0:ip=127.0.0.1,port=7303,state=online,offset=325,lag=1
{"restaurant":"을지로 국수","stars":3}
```

7302가 `role:master`가 됐고, 7303은 새 주 서버에서 빠진 부분을 받아 리뷰 43까지 갖게 됐다. 이제 웹 앱의 쓰기 주소를 7302로 바꾸면 쓰기가 다시 돈다.

이번에는 운이 좋았다. 복제본 하나가 리뷰 43을 받아 둔 상태였다. 만약 두 복제본 모두 리뷰 43을 받기 전에 주 DB가 죽었다면, 누구를 올려도 리뷰 43은 사라진다. 비동기 복제에서는 "성공이라고 답한 쓰기를 잃을 수 있다". 이것이 비동기 복제의 대가다.

이것을 막으려면 동기 복제를 쓴다. 주 DB가 복제본 하나 이상이 받았다고 확인한 뒤에야 성공이라고 답한다. 대신 쓰기마다 복제본까지의 왕복 시간이 붙고, 그 복제본이 멈추면 쓰기도 멈출 수 있다. 그래서 흔히 복제본 여러 대 중 하나만 동기로 기다리게 하거나, 결제처럼 잃으면 안 되는 데이터에만 동기 확인을 건다. PostgreSQL의 `synchronous_commit`과 `synchronous_standby_names`가 그 설정이다.

## 장애 조치를 사람이 하면 늦다

위에서 손으로 한 일을 정리하면 이렇다. 주 DB가 죽었는지 판단하고, 가장 앞선 복제본을 고르고, 승격하고, 나머지를 새 주 DB에 붙이고, 웹 앱의 쓰기 주소를 바꾼다. 새벽 3시에 사람이 이걸 하면 수십 분이 걸린다.

그래서 이 과정을 자동으로 하는 도구를 쓴다. PostgreSQL은 Patroni, Redis는 Sentinel이 대표적이고, AWS RDS의 Multi-AZ 같은 관리형 DB는 제공자가 대신 해 준다. 자동화하면 수십 초 안에 끝나지만 새로운 위험이 생긴다.

옛 주 DB가 진짜 죽은 게 아니라 네트워크만 잠깐 끊겼다면 어떻게 될까. 복제본이 승격된 뒤 옛 주 DB가 돌아오면 주 DB가 두 대가 된다. 웹 서버 일부는 옛 주 DB에, 일부는 새 주 DB에 쓰면서 데이터가 갈라진다. 이 상태를 스플릿 브레인(split-brain)이라고 한다. 그래서 장애 조치 도구는 승격하기 전에 옛 주 DB를 확실히 차단하는 장치(펜싱)를 함께 둔다. 이 과정의 시간을 재고 펜싱을 거는 방법은 [장애 조치 글](/posts/failover)에서, Redis Sentinel이 판단하는 과정은 [Redis 복제와 Sentinel 글](/posts/redis-replication-sentinel)에서 본다.

## 복제본은 몇 대가 필요할까

복제본을 늘리면 읽기는 계속 늘릴 수 있다. 하지만 쓰기는 늘지 않는다. 오히려 복제본마다 주 DB의 모든 쓰기를 똑같이 다시 적용해야 한다. 복제본 한 대가 초당 2,000개의 일을 할 수 있는데 쓰기가 초당 1,000개라면, 그중 1,000개는 쓰기를 따라가는 데 쓰고 읽기에 쓸 수 있는 것은 1,000개뿐이다.

아래 함수를 완성해 보자. 계산을 단순하게 하려고 복제본이 쓰기 하나를 적용하는 비용을 읽기 하나와 같다고 잡는다. 복제본 한 대가 읽기에 쓸 수 있는 여유는 `nodeQps - writeQps`다. 필요한 복제본 수는 `readQps`를 그 여유로 나눠 올림한다. 여유가 0 이하면 복제본으로는 답이 없으니 둘 다 `-1`로 돌려준다. `withSpare`는 한 대가 죽어도 버티도록 한 대를 더한 수다.

<CodePlayground
  caption="읽기를 감당할 복제본 수"
  functionName="replicasNeeded"
  initialCode={`function replicasNeeded(readQps, writeQps, nodeQps) {
  // 복제본 한 대가 읽기에 쓸 수 있는 여유 = nodeQps - writeQps
  // replicas = 올림(readQps / 여유), withSpare = replicas + 1
  // 여유가 0 이하면 { replicas: -1, withSpare: -1 }
  return { replicas: 0, withSpare: 0 };
}`}
  solution={`function replicasNeeded(readQps, writeQps, nodeQps) {
  const spare = nodeQps - writeQps;
  if (spare <= 0) return { replicas: -1, withSpare: -1 };
  const replicas = Math.ceil(readQps / spare);
  return { replicas, withSpare: replicas + 1 };
}`}
  tests={[

같은 초당 6,000 읽기라도 쓰기가 200이면 복제본 4대, 1,800이면 30대가 필요하다. 쓰기가 한 대의 한계에 가까워질수록 복제본을 늘리는 효과가 사라진다. 쓰기가 한 대를 넘으면 복제로는 아예 풀 수 없다. 그때가 데이터를 여러 DB로 쪼개는 [⑧ 샤딩 입문](/posts/sd-sharding-intro)으로 넘어갈 때다.

## 현장에서 복제를 의심하는 순간

"방금 쓴 게 안 보인다", "새로고침하면 보였다 안 보였다 한다"는 문의가 들어오면 복제 지연부터 본다. 복제본별 지연 지표(PostgreSQL `replay_lag`, MySQL `Seconds_Behind_Source`, Redis offset 차이)를 대시보드에 두고, 평소보다 늘었는지 본다. 쓰기 직후 읽기를 어디로 보내는지 코드도 확인한다.

"특정 복제본 하나만 지연이 계속 는다"면 그 복제본에서 긴 분석 쿼리가 돌고 있거나, 디스크가 느리거나, 네트워크가 혼잡한 경우가 많다. 지연이 기준(예: 5초)을 넘은 복제본은 라우터나 로드 밸런서에서 자동으로 빼는 규칙을 둔다. 늦은 복제본에서 읽는 것보다 주 DB나 다른 복제본에서 읽는 편이 낫다.

"장애 조치 후 몇 건의 주문이 사라졌다"면 비동기 복제의 대가다. 잃으면 안 되는 쓰기가 무엇인지 정하고, 그 쓰기에 동기 확인을 걸지 결정한다.

"주 DB 디스크가 갑자기 찬다"면 PostgreSQL에서 죽은 복제본의 복제 슬롯이 WAL을 붙잡고 있는 경우가 있다. 복제본을 버릴 때는 슬롯도 함께 지운다.

## 이어서 읽을 글

다음 글 [⑤ 캐시와 CDN](/posts/sd-cache-and-cdn-tier)에서는 복제본까지 가지 않고 읽기를 끝내는 방법을 붙인다. 같은 답을 매번 다시 계산하지 않게 캐시를 두고, 사진과 JS 파일은 사용자 가까이의 CDN에 맡긴다.

복제는 쓰기를 한 곳에서 받고, 그 기록을 여러 대가 따라 쓰게 해서 읽기를 나누고 장애에 대비하는 방법이다. 대가는 복제본이 조금 늦을 수 있다는 점이다. 그래서 방금 쓴 것은 주 DB에서 읽고, 주 DB가 죽으면 가장 앞선 복제본을 올리고, 비동기 복제가 응답한 쓰기를 잃을 수 있음을 알고 설계한다.

## 면접에서 나올 만한 질문

### DB 복제는 왜 하고, 어떻게 동작하나요?

읽기를 여러 대로 나누고 서버 장애에 대비하기 위해서다. 쓰기는 주 DB 한 대가 받아 변경 내용을 로그(PostgreSQL WAL, MySQL binlog)에 적고, 복제본들은 그 로그를 받아 같은 순서로 다시 적용한다. 대부분의 서비스는 읽기가 쓰기보다 훨씬 많아서 복제본을 늘리는 것만으로 큰 효과를 본다.

### 복제본에서 읽으면 어떤 문제가 생기나요?

복제 지연 때문에 방금 쓴 데이터가 안 보일 수 있다. 기본 설정인 비동기 복제는 주 DB가 복제본을 기다리지 않고 답하기 때문이다. 쓴 사용자의 읽기를 잠깐 주 DB로 보내거나, 쓴 결과를 화면에 바로 그리거나, 정확해야 하는 읽기는 처음부터 주 DB로 보내는 식으로 read-your-writes를 보장한다.

### 복제본 하나가 죽으면 어떻게 되나요?

읽기를 다른 복제본으로 돌리고, 복제본이 하나도 없으면 임시로 주 DB에서 읽는다. 서비스는 계속 돌지만 남은 서버가 늘어난 읽기를 버텨야 하므로, 복제본 수는 한 대가 빠져도 감당할 만큼 잡는다. 죽은 복제본은 새 서버로 교체해 주 DB에서 다시 복사받게 한다.

### 주 DB가 죽으면 어떻게 하나요?

복제본 중 하나를 새 주 DB로 승격하고, 나머지 복제본이 새 주 DB를 따라가게 한 뒤 웹 앱의 쓰기 주소를 바꾼다. 승격할 복제본은 로그를 가장 많이 받은 것, 즉 offset이나 LSN이 가장 앞선 것으로 고른다. 사람이 하면 느리기 때문에 Patroni, Sentinel, 관리형 DB의 자동 장애 조치를 쓴다.

### 비동기 복제에서 데이터를 잃을 수 있나요? 막으려면요?

잃을 수 있다. 주 DB가 성공이라고 답했지만 로그가 어느 복제본에도 가기 전에 죽으면, 누구를 승격해도 그 쓰기는 없다. 막으려면 동기 복제로 최소 한 복제본이 받았음을 확인한 뒤 답하게 한다. 대신 쓰기 지연이 늘고 그 복제본이 멈추면 쓰기도 멈출 수 있어서, 복제본 하나만 동기로 두거나 중요한 쓰기에만 거는 식으로 절충한다.

### 자동 장애 조치에서 가장 조심해야 할 것은 무엇인가요?

스플릿 브레인이다. 옛 주 DB가 네트워크만 끊겼다가 돌아오면 주 DB가 둘이 되어 서로 다른 쓰기를 받는다. 그래서 승격 전에 옛 주 DB를 확실히 차단하는 펜싱을 하고, 과반의 판단이 있을 때만 승격하게 한다. 너무 민감하게 감지하면 멀쩡한 주 DB를 잘못 넘기는 일도 생기므로 감지 시간과 오탐을 함께 조정한다.

### 트래픽이 10배가 되면 복제본만 늘리면 되나요?

읽기가 늘어난 것이라면 복제본과 캐시로 대부분 풀린다. 하지만 복제본은 쓰기를 전혀 덜어 주지 못하고, 오히려 모든 복제본이 같은 쓰기를 다시 적용한다. 쓰기가 주 DB 한 대의 한계에 가까워지면 복제본을 늘려도 효과가 줄고, 넘으면 샤딩으로 데이터를 여러 주 DB에 나눠야 한다.

### 복제본이 있으면 백업은 필요 없나요?

필요하다. 복제는 서버 고장에 대비하는 것이고, 실수로 지운 데이터는 복제본에서도 함께 지워진다. 백업과 WAL 보관으로 특정 시점으로 되돌릴 수 있어야 한다.
