로그 뷰어에 검색 하이라이트를 붙이면서 문자열 찾기를 이중 반복문으로 직접 짰다. 평소 로그에서는 아무 문제가 없었다. 그런데 어떤 요청 본문이 `a`로 100만 자 채워져 들어왔고, 누군가 그 위에서 `a` 999개 뒤에 `b`가 붙은 문자열을 검색했다. 탭이 10초 동안 멈췄다.

Node.js 22에서 같은 입력을 네 가지 방법으로 찾아봤다.

```text
naive    idx=-1 comparisons=999001000 10239.8ms
kmp      idx=-1 comparisons=2999000 29.4ms
includes result=false 4.5ms
indexOf  result=-1 4.4ms
regex result=false 5205.8ms
```

직접 짠 반복문은 글자 비교를 약 10억 번 했다. 같은 일을 KMP는 300만 번에 끝냈고, 엔진에 들어 있는 `indexOf`는 4ms였다. `/a{999}b/` 정규식은 5초가 걸렸다. 같은 질문에 답하는데 1000배 넘게 차이가 난다.

이 글은 그 차이가 어디서 오는지 따라간다. 이미 맞힌 글자를 다시 보지 않는 KMP, 글자 대신 숫자로 먼저 비교하는 라빈-카프, 뒤에서부터 비교해 크게 건너뛰는 보이어-무어를 하나씩 본다. 그다음 같은 텍스트에서 여러 번 찾을 때 쓰는 접미사 배열, 찾을 단어가 많을 때 쓰는 아호-코라식까지 가서 언제 무엇을 고르는지 정리한다. 실행 결과는 모두 Node.js 22에서 직접 돌린 값이다. 복잡도 표기는 [Big O 표기법](/posts/big-o-notation)을 따른다.

## 한 칸 밀 때마다 처음부터 다시 비교한다

텍스트 길이를 n, 찾는 패턴 길이를 m이라 하자. 가장 단순한 방법은 패턴을 텍스트의 0번 칸에 대 보고, 글자가 하나라도 다르면 한 칸 밀어서 처음부터 다시 대 보는 것이다.

```js
function naive(text, pattern) {
  for (let i = 0; i + pattern.length <= text.length; i++) {
    let j = 0;
    while (j < pattern.length && text[i + j] === pattern[j]) j++; // 맞는 동안 오른쪽으로
    if (j === pattern.length) return i;                           // 끝까지 맞았다
  }
  return -1;
}
```

시작 위치가 n - m + 1개, 위치마다 최대 m번 비교하니 최악은 O(n·m)이다. 위 실험의 999,001,000번은 (1,000,000 - 1000 + 1) × 1000을 그대로 센 값이다. 매번 999글자를 맞히고 마지막 `b`에서 틀린 다음, 한 칸 밀어서 방금 맞힌 999글자를 또 읽었다.

그렇다고 이 방법이 늘 느린 건 아니다. 평범한 텍스트에서는 첫 글자나 둘째 글자에서 대부분 틀리기 때문이다. `error`, `timeout`, `session` 같은 단어를 섞어 만든 500만 자 로그에서 `connection refused`를 찾으면 글자당 비교 횟수가 이렇게 나온다.

```text
naive -1 cmp/char 1.029 60.7ms
kmp -1 cmp/char 1.029 52.1ms
```

글자 하나를 평균 1.03번 본다. KMP와 똑같다. 단순 탐색이 위험한 건 같은 글자가 길게 반복되는 입력, 이를테면 0으로 채운 바이너리, `AAAA`로 이어지는 염기 서열, 패딩이 긴 base64 같은 데이터다. 그리고 사용자가 텍스트와 패턴을 모두 고를 수 있다면 누군가는 그런 입력을 일부러 만든다.

## 이미 맞힌 글자는 다시 보지 않는다

999글자를 맞힌 뒤 마지막에서 틀렸다면, 우리는 방금 본 999글자가 무엇이었는지 정확히 안다. 패턴과 똑같았으니까. 그러면 한 칸 밀고 처음부터 다시 볼 필요가 없다. "지금까지 맞힌 부분의 끝이 패턴의 앞부분과 얼마나 겹치는가"만 알면 그 지점부터 이어서 비교할 수 있다.

1977년에 크누스, 모리스, 프랫이 정리한 KMP 알고리즘이 이 생각이다. 패턴 `ABABC`로 텍스트 `ABABABC`를 찾는 과정을 따라가 보자. 아래 그림에서 다음을 누르면 텍스트를 읽는 위치(i)가 한 번도 왼쪽으로 돌아가지 않는 걸 볼 수 있다. 오른쪽의 k는 "지금까지 패턴 앞에서부터 몇 글자를 맞혔나"다.

넷째 단계가 KMP의 전부다. 틀린 순간 텍스트 포인터는 4번 칸에 그대로 있고, k만 4에서 2로 줄었다. "ABAB의 끝 두 글자는 패턴의 처음 두 글자와 같다"는 사실을 미리 알고 있었기 때문이다. 이 정보를 패턴만 보고 미리 계산해 둔 표가 실패 함수(failure function)다. 문헌에 따라 pi 배열, 접두사 함수, LPS(longest proper prefix which is also suffix) 배열이라고도 부른다.

## 실패 함수는 패턴이 자기 자신과 겹치는 길이다

실패 함수의 i번 칸에는 "패턴의 0부터 i까지 중에서, 앞부분(접두사)이면서 동시에 뒷부분(접미사)인 가장 긴 문자열의 길이"가 들어간다. 단, 자기 자신 전체는 빼고 센다. 전체를 허용하면 늘 자기 길이가 답이 되어 쓸모가 없다.

`ABABC`라면 이렇게 된다.

- `A`: 자기 자신을 빼면 겹치는 게 없다. 0
- `AB`: 앞 `A`, 뒤 `B`. 0
- `ABA`: 앞 `A`와 뒤 `A`가 같다. 1
- `ABAB`: 앞 `AB`와 뒤 `AB`가 같다. 2
- `ABABC`: C로 끝나는 접미사와 같은 접두사가 없다. 0

이 표를 만드는 코드는 검색 코드와 거의 같다. 패턴을 텍스트 삼아 자기 자신을 찾는 셈이다.

```js
function failure(p) {
  const f = new Array(p.length).fill(0);
  for (let i = 1, k = 0; i < p.length; i++) {
    while (k > 0 && p[i] !== p[k]) k = f[k - 1]; // 틀리면 더 짧은 겹침으로 물러난다
    if (p[i] === p[k]) k++;                      // 맞으면 겹침이 한 글자 늘어난다
    f[i] = k;
  }
  return f;
}
console.log("failure(ABABC) =", failure("ABABC"));
console.log("failure(AABAAA) =", failure("AABAAA"));
```

```text
failure(ABABC) = [ 0, 0, 1, 2, 0 ]
failure(AABAAA) = [ 0, 1, 0, 1, 2, 2 ]
```

`AABAAA`의 마지막 칸을 보면 `while`의 역할이 보인다. 다섯째 글자까지 `AABAA`에서 겹침은 2(`AA`)였다. 여섯째 글자 `A`를 붙이면 겹침을 3으로 늘리고 싶지만, 패턴의 셋째 글자는 `B`라 맞지 않는다. 그래서 `f[1] = 1`로 물러나 `A` 하나짜리 겹침에서 다시 시도하고, 패턴의 둘째 글자 `A`가 맞아 2가 된다.

`while` 안에서 여러 번 물러날 수 있는데도 전체가 O(m)인 이유는 k의 움직임에 있다. k는 한 바퀴에 많아야 1 늘고, `while`은 k를 줄이기만 한다. 늘어난 총량이 m을 넘지 않으니 줄어드는 총량도 m을 넘지 못한다. 검색도 같은 논리로 O(n)이라, KMP 전체는 O(n + m)이다. 위 실험의 299만 번은 글자당 약 세 번으로, 텍스트 길이에 비례해서만 늘었다.

KMP가 실무에서 그 자체로 많이 쓰이지는 않는다. 평범한 텍스트에서는 단순 탐색과 속도가 같고, 아래에서 볼 보이어-무어 계열이 대개 더 빠르다. 그래도 KMP의 장점은 분명하다. 텍스트를 앞에서 뒤로 한 번만, 되돌아가지 않고 읽는다. 그래서 네트워크로 흘러 들어오는 스트림처럼 지나간 데이터를 다시 볼 수 없는 곳에서도 쓸 수 있고, 최악의 시간이 보장된다. 실패 함수라는 생각은 뒤의 아호-코라식에서 다시 나온다.

## 글자 대신 숫자를 먼저 비교한다

다른 방향의 생각도 있다. 패턴과 텍스트의 한 구간을 글자 단위로 비교하는 대신, 각각을 숫자 하나(해시)로 바꿔 숫자부터 비교한다. 숫자가 다르면 글자를 볼 필요가 없다. 숫자가 같을 때만 글자를 확인한다.

문제는 구간마다 해시를 새로 계산하면 결국 m글자를 다 읽는다는 점이다. 1987년에 카프와 라빈이 발표한 라빈-카프 알고리즘은 해시를 굴린다(rolling hash). 구간을 한 칸 밀 때 빠지는 글자 몫을 빼고 들어오는 글자 몫을 더해, 새 해시를 O(1)에 얻는다.

숫자로 된 텍스트라면 이해가 쉽다. 다섯 자리 구간 `67399`를 수 67399로 보고 13으로 나눈 나머지를 해시로 쓴다. 한 칸 밀어 `73993`이 되면 맨 앞 6의 몫(6 × 10⁴)을 빼고, 10을 곱해 자리를 올린 다음, 새로 들어온 3을 더한다. 모든 계산을 13으로 나눈 나머지 위에서 하면 수가 커지지 않는다.

```js
const t = "6739931415", p = "31415", q = 13, B = 10, m = p.length;
const h = s => [...s].reduce((a, c) => (a * B + +c) % q, 0);
let hp = h(p), ht = h(t.slice(0, m));
const hi = B ** (m - 1) % q;               // 맨 앞자리의 무게 10^4 mod 13
console.log("pattern hash", hp, "hi", hi);
for (let i = 0; i + m <= t.length; i++) {
  const tag = ht === hp ? (t.slice(i, i + m) === p ? "MATCH" : "SPURIOUS") : "";
  console.log(i, t.slice(i, i + m), ht, tag);
  if (i + m < t.length)                    // 앞 글자 빼고, 자리 올리고, 새 글자 더하기
    ht = ((ht - +t[i] * hi % q + q) % q * B + +t[i + m]) % q;
}
```

```text
pattern hash 7 hi 3
0 67399 7 SPURIOUS
1 73993 10 
2 39931 8 
3 99314 7 SPURIOUS
4 93141 9 
5 31415 7 MATCH
```

가짜 일치가 이렇게 잦은 건 법(modulus)을 13으로 작게 잡았기 때문이다. 해시 값이 q가지뿐이면 무작위 구간이 패턴과 같은 해시를 가질 확률은 대략 1/q다. 그래서 실제로는 10⁹ + 7 같은 큰 소수를 법으로 쓰고, 기수(base)는 글자 종류보다 큰 수(바이트라면 256 이상)를 쓴다. 가짜 일치가 드물면 기대 시간은 O(n + m)이다. 다만 가짜 일치마다 m글자를 확인하므로 최악은 여전히 O(n·m)이다.

자바스크립트에서 큰 법을 쓸 때는 곱셈 넘침을 조심해야 한다. 해시 값이 10⁹ 근처일 때 기수 256을 곱하면 약 2.6 × 10¹¹로 아직 안전하지만, 법을 2⁶¹ - 1처럼 키우면 곱이 2⁵³을 넘어 Number로는 정확히 계산되지 않는다. BigInt를 쓰면 정확하지만 몇 배 느리다. 그래서 흔히 법 10⁹ 근처 두 개로 해시를 두 번 계산하는 이중 해시를 쓴다. 정수 넘침과 2⁵³ 한계는 [비트 연산 글](/posts/bit-manipulation)에서 자세히 본다.

보안 쪽 엣지 케이스도 있다. 법과 기수가 고정되어 있고 상대가 그 값을 안다면, 같은 해시를 내는 문자열을 일부러 대량으로 만들 수 있다. 그러면 모든 창에서 가짜 일치가 나서 최악으로 떨어진다. 해시 테이블을 노린 [해시 플러딩](/posts/ds-hash-map)과 같은 공격이다. 외부 입력을 받는 곳이라면 기수를 실행할 때마다 무작위로 고른다.

라빈-카프가 진짜로 빛나는 곳은 "한 문자열 찾기"가 아니다. 길이가 같은 패턴 여러 개의 해시를 집합에 넣어 두고 창 하나를 밀며 집합에 있는지 보면, 여러 패턴을 한 번에 찾을 수 있다. 두 문서에서 겹치는 구간을 찾는 표절 검사, 바뀐 블록만 보내는 [rsync의 굴리는 체크섬](/posts/rsync-algorithm), 데이터를 내용 기준으로 자르는 중복 제거 저장소도 같은 굴리는 해시를 쓴다.

## 뒤에서부터 비교하면 크게 건너뛴다

지금까지의 방법은 모두 텍스트의 글자를 적어도 한 번씩은 봤다. 1977년에 보이어와 무어가 발표한 방법은 패턴을 텍스트에 대고 패턴의 끝 글자부터 비교한다. 이 순서가 큰 차이를 만든다.

패턴 `EXAMPLE`을 대 보았는데 텍스트의 끝 칸 글자가 `S`라고 하자. `S`는 `EXAMPLE` 안에 아예 없다. 그러면 이 `S`를 덮는 어떤 위치에 패턴을 놓아도 맞을 수 없다. 패턴 길이 7만큼 한 번에 건너뛴다. 끝 칸이 `P`라면 패턴 안의 `P`가 그 칸에 오도록 2칸만 민다. 이 규칙을 나쁜 문자 규칙(bad character rule)이라 한다.

보이어-무어 원래 알고리즘은 규칙이 하나 더 있다. 뒤쪽 몇 글자를 맞히고 틀렸을 때, 맞힌 꼬리가 패턴의 다른 곳에 또 나오는지를 보고 미는 좋은 접미사 규칙(good suffix rule)이다. 두 규칙 중 더 멀리 가는 쪽을 고른다. 1980년에 호스풀은 좋은 접미사 규칙을 빼고, 창의 마지막 칸 글자로만 미는 단순한 판(Boyer-Moore-Horspool)을 냈다. 표 하나로 끝나서 구현이 짧고, 보통 텍스트에서는 거의 같은 속도가 난다.

```js
function horspool(t, p) {
  const m = p.length, shift = new Map();
  for (let i = 0; i < m - 1; i++) shift.set(p[i], m - 1 - i); // 글자마다 끝에서 떨어진 거리
  let i = 0;
  while (i + m <= t.length) {
    let j = m - 1;
    while (j >= 0 && t[i + j] === p[j]) j--;  // 끝에서 앞으로 비교
    if (j < 0) return i;
    i += shift.get(t[i + m - 1]) ?? m;        // 창의 마지막 글자로 민다. 패턴에 없으면 m칸
  }
  return -1;
}
```

`EXAMPLE`의 이동 표는 `E: 6, X: 5, A: 4, M: 3, P: 2, L: 1`이고, 표에 없는 글자는 7이다. 마지막 `E`는 표를 만들 때 빼는데, 넣으면 이동 거리가 0이 되어 제자리에 멈추기 때문이다. `HERE-IS-A-SIMPLE-EXAMPLE`에서 찾는 과정을 그림으로 보자.

## 언어와 도구는 이미 섞어 쓴다

처음 실험에서 `indexOf`가 4ms에 끝난 이유가 여기 있다. V8의 문자열 검색 구현(`src/strings/string-search.h`)을 보면 패턴이 아주 짧을 때는 단순 탐색을 쓰고, 길어지면 단순 탐색으로 시작했다가 비용이 커지면 보이어-무어-호스풀로, 그래도 비용이 크면 좋은 접미사 규칙까지 쓰는 보이어-무어로 옮겨 간다. 다른 엔진의 구현은 다를 수 있지만, 표준 라이브러리 검색은 대개 이렇게 입력을 보며 방법을 바꾼다. 그러니 단일 문자열 하나를 찾을 때는 직접 KMP를 짜기보다 `indexOf`나 `includes`를 쓰는 쪽이 빠르다.

GNU grep이 빠른 이유도 비슷하다. grep 원저자 중 한 명인 마이크 하어텔이 2010년 메일링 리스트에 남긴 설명이 유명하다. 보이어-무어로 바이트 대부분을 건너뛰고, 그 안쪽 반복문을 아주 짧게 만들고, 입력을 줄 단위로 나누지 않은 채 통째로 훑다가 찾은 뒤에야 줄 경계를 찾는다는 내용이다. 고정 문자열 여러 개(`grep -F -f words.txt`)를 찾을 때는 아래의 아호-코라식 계열 자동자를 쓴다. 세부 구현은 버전마다 바뀌어 왔다.

정규식은 사정이 다르다. 처음 실험에서 `/a{999}b/`가 5초나 걸린 건 자바스크립트 정규식이 백트래킹 엔진이라서다. 시작 위치마다 `a`를 999개까지 따라가다 틀리면 다음 위치에서 다시 시작하니, 단순 탐색과 같은 O(n·m)이 된다. 패턴이 더 나쁘면 지수 시간까지 간다. 엔진 구조와 ReDoS는 [정규식과 glob](/posts/regex-and-globbing) 글에서 다뤘다. 사용자가 입력한 검색어를 정규식으로 바꿔 쓰고 있다면, 특수 문자를 이스케이프하는 것만으로는 이 비용을 막지 못한다. 고정 문자열 검색이면 `indexOf`로 바꾼다.

## 같은 텍스트에서 여러 번 찾을 때

지금까지는 텍스트 하나에 질문 하나였다. 그런데 텍스트가 고정되어 있고 질문이 계속 들어온다면 어떨까. 게놈 서열에 수백만 개의 짧은 조각을 맞춰 보거나, 같은 문서에서 사용자가 이것저것 검색하는 경우다. 질문마다 O(n)씩 쓰지 말고, 텍스트를 한 번 손질해 두고 질문마다 패턴 길이에 가까운 시간으로 답하고 싶다.

접미사 배열(suffix array)이 그 손질이다. 텍스트의 모든 접미사(어느 위치부터 끝까지)를 사전 순으로 정렬하고, 그 시작 위치만 배열로 저장한다. `banana`라면 이렇다. 마지막 열은 바로 위 접미사와 앞에서부터 몇 글자가 같은지를 적은 LCP(longest common prefix) 배열이다.

```js
const s = "banana";
const sa = [...s].map((_, i) => i).sort((a, b) => (s.slice(a) < s.slice(b) ? -1 : 1));
const lcp = sa.map((x, k) => {
  if (k === 0) return 0;
  const a = s.slice(sa[k - 1]), b = s.slice(x);
  let l = 0;
  while (l < a.length && a[l] === b[l]) l++;
  return l;
});
sa.forEach((x, k) => console.log(k, x, s.slice(x).padEnd(7), lcp[k]));
```

```text
0 5 a       0
1 3 ana     1
2 1 anana   3
3 0 banana  0
4 4 na      0
5 2 nana    2
```

패턴이 텍스트 어딘가에 나온다는 말은 어떤 접미사가 그 패턴으로 시작한다는 뜻이다. 정렬되어 있으니 그 접미사들은 배열에서 한 덩어리로 붙어 있다. `ana`로 시작하는 접미사는 1번, 2번 줄에 모여 있고 시작 위치는 3과 1이다. 덩어리의 처음과 끝은 [이분 탐색](/posts/binary-search)으로 찾는다. 비교 한 번에 최대 m글자를 보니 질문 하나가 O(m log n)이다.

```text
ana -> [ 1, 3 ] na -> [ 2, 4 ] nab -> []
LRS ana
distinct substrings 15
```

LCP 배열은 덤으로 다른 질문에도 답한다. LCP의 최댓값 3은 `anana`와 `ana`가 세 글자를 공유한다는 뜻이고, 그래서 두 번 이상 나오는 가장 긴 부분 문자열은 `ana`다. 서로 다른 부분 문자열의 개수도 전체 부분 문자열 수 n(n+1)/2 = 21에서 LCP 합 6을 빼면 15다. 로그에서 반복되는 긴 덩어리를 찾거나 압축 사전을 만들 때 이런 계산을 쓴다.

위 코드는 `slice`로 접미사를 만들어 비교 정렬하니 O(n² log n)이고 메모리도 많이 쓴다. 설명용이다. 실제로는 접미사의 앞 2ᵏ글자 순위로 정렬을 반복하는 접두사 배가법이 기수 정렬과 함께 쓰면 O(n log n)이고, SA-IS 같은 알고리즘은 O(n)에 만든다. LCP는 카사이 알고리즘으로 O(n)에 구한다.

접미사 트리(suffix tree)는 같은 정보를 모든 접미사를 넣은 압축 트라이로 저장한다. 패턴 찾기가 O(m)이고 우코넨 알고리즘으로 O(n)에 만들 수 있지만, 노드마다 자식 포인터를 들고 있어서 메모리가 흔히 글자당 수십 바이트까지 커진다. 접미사 배열은 정수 배열 하나(글자당 4~8바이트)라 훨씬 가볍고 캐시에도 잘 맞는다. 그래서 실무에서는 접미사 배열과 LCP로 접미사 트리가 하던 일을 대신하는 경우가 많다. 더 줄여야 하면 BWT와 FM 인덱스로 간다. 생물정보학의 서열 정렬 도구들이 이 계열을 쓴다.

텍스트가 하나의 긴 문자열이 아니라 문서 수백만 개이고, 질문이 "이 글자들이 이어서 나오는 곳"이 아니라 "이 단어가 든 문서"라면 접미사 배열보다 [역색인](/posts/elasticsearch-inverted-index)이 맞다. 단어 단위로 쪼개 두고 단어에서 문서 목록으로 가는 표를 만든다. 접미사 배열은 단어 경계가 없는 데이터나 임의 부분 문자열 검색이 필요할 때 고른다.

## 찾을 단어가 수천 개일 때

금칙어 5천 개를 채팅 메시지마다 걸러야 한다고 해 보자. 단어마다 `includes`를 부르면 메시지 하나에 5천 번 훑는다. 1975년에 아호와 코라식이 발표한 알고리즘은 단어를 모두 [트라이](/posts/ds-trie)에 넣고, 텍스트를 한 번만 읽으며 모든 단어를 찾는다. 시간은 O(n + 단어 길이 합 + 찾은 개수)다.

트라이만으로는 부족하다. `she`를 따라가다 다음 글자에서 막히면, 그동안 읽은 글자의 꼬리(`he`)가 다른 단어의 앞부분일 수 있다. 그래서 노드마다 "여기서 막히면 갈 곳"을 미리 이어 둔다. 지금까지 읽은 문자열의 가장 긴 접미사이면서 트라이에 있는 노드다. KMP의 실패 함수를 트라이로 넓힌 것이고, 이름도 실패 링크(failure link)다. 실패 링크는 트라이를 BFS로 돌며 얕은 노드부터 채운다. 깊은 노드의 링크가 더 얕은 노드의 링크로 정해지기 때문이다.

```js
function build(words) {
  const next = [new Map()], fail = [0], out = [[]];
  for (const w of words) {                       // 1. 단어를 트라이에 넣는다
    let s = 0;
    for (const c of w) {
      if (!next[s].has(c)) { next.push(new Map()); fail.push(0); out.push([]); next[s].set(c, next.length - 1); }
      s = next[s].get(c);
    }
    out[s].push(w);
  }
  const q = [...next[0].values()];               // 2. BFS로 실패 링크를 채운다
  while (q.length) {
    const s = q.shift();
    for (const [c, t] of next[s]) {
      let f = fail[s];
      while (f && !next[f].has(c)) f = fail[f];
      fail[t] = next[f].has(c) && next[f].get(c) !== t ? next[f].get(c) : 0;
      out[t].push(...out[fail[t]]);              // 실패 링크 쪽에서 끝나는 단어도 함께 보고한다
      q.push(t);
    }
  }
  return { next, fail, out };
}
function search(text, words) {
  const { next, fail, out } = build(words), hits = [];
  let s = 0;
  for (let i = 0; i < text.length; i++) {
    while (s && !next[s].has(text[i])) s = fail[s]; // 막히면 실패 링크를 탄다
    s = next[s].get(text[i]) ?? 0;
    for (const w of out[s]) hits.push([i - w.length + 1, w]);
  }
  return hits;
}
console.log(search("ushers", ["he", "she", "his", "hers"]));
```

```text
[ [ 1, 'she' ], [ 2, 'he' ], [ 2, 'hers' ] ]
```

`ushers`를 한 번 읽으면서 `she`, `he`, `hers`를 모두 찾았다. `she`의 끝 노드에 도착한 순간, 그 실패 링크가 `he`의 끝 노드를 가리키므로 `he`도 같이 보고된다. 이 출력 합치기를 빠뜨리면 다른 단어 안에 숨은 짧은 단어를 놓친다. 아호-코라식을 직접 짤 때 가장 흔한 버그다.

금칙어 필터, 침입 탐지 시스템의 시그니처 매칭, 바이러스 검사, `grep -F -f`가 이 계열이다. 한국어 금칙어 필터라면 띄어쓰기나 특수 문자를 끼워 넣는 우회(`바 보`, `바.보`)가 문제가 되니, 검색 전에 텍스트를 정규화하는 단계가 알고리즘보다 더 중요해진다.

## 상황별로 고르는 알고리즘 한 표

조건마다 고르는 기준을 한 표에 모으면 이렇다.

| 상황 | 고를 것 | 이유 |
|---|---|---|
| 문자열 하나에서 한 번 찾기 | 언어 내장 `indexOf`·`includes` | 이미 보이어-무어 계열을 섞어 쓴다 |
| 최악 시간을 보장해야 함, 스트림 | KMP | 되돌아가지 않고 O(n + m) |
| 길이가 같은 패턴 여러 개, 문서끼리 겹침 찾기 | 라빈-카프 | 해시 집합 하나로 창마다 O(1) 확인 |
| 긴 패턴, 글자 종류가 많은 텍스트 | 보이어-무어·호스풀 | 글자 대부분을 건너뛴다 |
| 패턴 수천 개를 한 번에 | 아호-코라식 | 텍스트를 한 번만 읽는다 |
| 고정 텍스트에 질문이 계속 옴 | 접미사 배열 + LCP | 질문당 O(m log n) |
| 문서 집합에서 단어 찾기 | 역색인 | 단어 단위 질문에 맞다 |

면접에서는 "KMP를 짜 보라"가 많이 나오지만, 실무에서 직접 짜는 일은 드물다. 실무에서 더 자주 만나는 건 표의 맨 윗줄과 아랫줄이다. 내장 함수를 쓰면 되는 곳에 정규식을 쓰거나, 역색인이 필요한 곳에 `LIKE '%검색어%'`를 쓰는 실수다.

## 현장에서 검색이 느려질 때 보는 곳

증상별로 보면 대개 이렇게 좁혀진다.

검색창에 특정 입력을 넣었을 때만 서버 CPU가 100%로 붙는다면 정규식부터 의심한다. 입력을 정규식으로 바꾸는 코드가 있는지, 백트래킹이 폭발하는 패턴인지 본다. Node 서버라면 요청 하나가 이벤트 루프를 붙잡아 다른 요청까지 멈춘다. 고정 문자열이면 `indexOf`로 바꾸고, 정규식이 꼭 필요하면 입력 길이를 제한하거나 선형 시간 엔진(RE2 계열)을 쓴다.

DB에서 `WHERE body LIKE '%timeout%'`이 느리다면 알고리즘 문제가 아니라 인덱스 문제다. 앞에 `%`가 붙으면 B-tree 인덱스를 쓰지 못해 표 전체를 훑는다. PostgreSQL이라면 `pg_trgm` 확장의 트라이그램 인덱스(GIN)가 부분 문자열 검색을 받쳐 주고, 단어 단위 검색이면 전문 검색이나 별도 검색 엔진으로 간다.

찾는 글자가 분명히 있는데 못 찾는다면 유니코드 정규화를 본다. 같은 `é`도 한 글자(NFC)로 올 수도, `e` 뒤에 결합 부호가 붙은 두 글자(NFD)로 올 수도 있다.

```js
const a = "café", b = "cafe\u0301";
console.log(a.length, b.length, a === b, b.includes("é"), b.normalize("NFC").includes("é"));
console.log("한글".normalize("NFD").length);
```

```text
4 5 false false true
6
```

눈에는 똑같은데 `includes`가 `false`다. 한글도 NFD로 바꾸면 두 글자가 자모 여섯 개가 된다. macOS에서 만든 파일 이름처럼 NFD로 들어오는 데이터가 있으니, 검색 전에 텍스트와 검색어를 같은 형식으로 `normalize`한다. 이모지 같은 보조 평면 문자는 자바스크립트 문자열에서 두 칸을 차지해서 `length`와 인덱스가 눈에 보이는 글자 수와 다르다는 점도 함께 기억해 둔다.

## KMP를 직접 짜 보기

실패 함수를 만들고, 그걸로 텍스트에서 패턴이 나오는 모든 위치를 찾는 함수를 짜 보자. 겹치는 위치도 모두 찾아야 한다(`aaaaa`에서 `aa`는 0, 1, 2, 3). 하나를 찾은 뒤에 k를 어디로 돌릴지가 마지막 관문이다. 패턴 길이는 1 이상이라고 가정한다.

  for (let i = 1, k = 0; i < m; i++) {

문자열 검색 알고리즘들은 결국 "이미 본 글자에서 얼마나 많은 정보를 짜내느냐"의 차이다. KMP는 맞힌 부분의 모양을, 라빈-카프는 숫자로 줄인 요약을, 보이어-무어는 패턴에 없는 글자라는 사실을 쓴다. 텍스트를 미리 손질할 수 있으면 접미사 배열로, 패턴이 많으면 아호-코라식으로 간다. 어느 쪽이든 고르기 전에 텍스트 길이, 질문 수, 패턴 수, 그리고 입력을 누가 고르는지를 먼저 본다.

## 면접에서 나올 만한 질문

### 단순 문자열 검색의 시간 복잡도는 얼마이고 언제 문제가 되나요?

최악은 O(n·m)이다. 위치마다 패턴을 거의 끝까지 맞히고 마지막에서 틀리면, 한 칸 밀 때마다 방금 본 글자를 다시 읽기 때문이다. 평범한 텍스트에서는 대부분 첫 한두 글자에서 틀려서 실제로는 선형에 가깝다. 같은 글자가 길게 반복되는 입력이나, 공격자가 텍스트와 패턴을 모두 고를 수 있는 경우에 문제가 된다.

### KMP는 어떻게 O(n + m)을 보장하나요?

패턴의 실패 함수를 미리 만들어 두고, 틀리면 텍스트 포인터는 그대로 둔 채 맞힌 길이만 실패 함수 값으로 줄인다. 실패 함수는 패턴 앞부분 각각에서 접두사이면서 접미사인 가장 긴 길이다. 맞힌 길이는 글자마다 많아야 1 늘고 물러날 때는 줄기만 하므로, 물러나는 횟수의 합이 n을 넘지 못한다. 그래서 검색 O(n), 실패 함수 O(m)이다.

### 라빈-카프에서 해시 충돌은 어떻게 다루고, 법은 어떻게 고르나요?

해시가 같으면 반드시 글자를 직접 비교해 확인한다. 가짜 일치 확률은 대략 1/법이라서 10⁹ + 7 같은 큰 소수를 쓰고, 기수는 글자 종류보다 크게 잡는다. 자바스크립트는 곱이 2⁵³을 넘으면 정확도가 깨지니 법을 10⁹ 근처로 두거나 이중 해시를 쓴다. 외부 입력이면 기수를 무작위로 골라 일부러 충돌을 만드는 공격을 막는다.

### 보이어-무어가 보통 텍스트에서 KMP보다 빠른 이유는 무엇인가요?

패턴의 끝부터 비교해서, 창 끝의 텍스트 글자가 패턴에 없으면 패턴 길이만큼 한 번에 건너뛰기 때문이다. KMP는 모든 글자를 적어도 한 번 보지만 보이어-무어는 많은 글자를 아예 보지 않는다. 로그 텍스트로 재 보면 글자당 비교가 KMP 1.03번, 호스풀 0.14번이었다. 패턴이 길수록 빨라지고, DNA처럼 글자 종류가 적으면 효과가 줄어든다.

### 그럼 자바스크립트에서 includes 대신 KMP를 직접 짜야 하나요?

대부분은 아니다. V8 같은 엔진은 패턴 길이와 진행 상황을 보며 단순 탐색, 보이어-무어-호스풀, 보이어-무어를 바꿔 쓰고 네이티브 코드로 돈다. 위 실험에서도 KMP 29ms, `indexOf` 4ms였다. 직접 짤 이유는 스트림처럼 되돌아갈 수 없는 입력, 여러 패턴 동시 검색, 같은 텍스트에 질문이 많은 경우처럼 내장 함수가 답하지 못하는 질문일 때다.

### 접미사 배열은 무엇이고 접미사 트리와 비교하면 어떤가요?

텍스트의 모든 접미사를 사전 순으로 정렬해 시작 위치만 저장한 배열이다. 패턴으로 시작하는 접미사가 한 덩어리로 모여 있어서 이분 탐색으로 O(m log n)에 찾는다. 접미사 트리는 O(m) 검색이 되지만 포인터가 많아 글자당 수십 바이트를 쓴다. 접미사 배열은 정수 배열 하나라 가볍고, LCP 배열을 더하면 가장 긴 반복 부분 문자열 같은 트리의 질문에도 답한다.

### 금칙어 수천 개를 걸러야 하면 어떻게 하나요?

아호-코라식을 쓴다. 금칙어를 트라이에 넣고 노드마다 실패 링크를 BFS로 이어 두면, 메시지를 한 번만 읽으며 모든 금칙어를 찾는다. 노드에 도착했을 때 실패 링크를 따라 끝나는 단어까지 함께 보고해야 `she` 안의 `he` 같은 단어를 놓치지 않는다. 실제 서비스에서는 띄어쓰기·특수 문자 우회가 많아 검색 전 정규화가 같이 필요하다.

### 사용자 검색어로 정규식을 만들면 무엇이 위험한가요?

자바스크립트를 비롯한 대부분의 정규식 엔진은 백트래킹 방식이라 패턴과 입력에 따라 O(n·m)이나 지수 시간까지 갈 수 있다. 특수 문자를 이스케이프해도 반복이 많은 입력에서는 단순 탐색과 같은 최악이 남는다. Node 서버라면 요청 하나가 이벤트 루프를 붙잡아 전체가 멈춘다. 고정 문자열이면 `indexOf`로 바꾸고, 정규식이 필요하면 입력 길이 제한이나 선형 시간 엔진을 쓴다.
