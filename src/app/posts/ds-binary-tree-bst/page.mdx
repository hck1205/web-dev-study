주문 id로 빨리 찾으려고 이진 탐색 트리(BST)를 직접 만든다고 해 보자. 교과서대로 재귀로 짠 `insert`에, DB에서 id 순서로 읽어 온 주문 10만 건을 차례로 넣는 상황을 그대로 흉내 내 봤다.

```js
class Node {
  constructor(key) { this.key = key; this.left = null; this.right = null; }
}
function insertRec(node, key) {
  if (node === null) return new Node(key);
  if (key < node.key) node.left = insertRec(node.left, key);
  else if (key > node.key) node.right = insertRec(node.right, key);
  return node;
}

let root = null;
for (let id = 1; id <= 100_000; id++) root = insertRec(root, id);
```

```bash
node orders.js
```

## 노드 하나에 자식 두 개

이진 트리(binary tree)는 노드마다 자식이 많아야 둘인 트리다. 맨 위 노드를 루트(root), 자식이 없는 노드를 잎(leaf)이라고 한다. 루트에서 어떤 노드까지 내려가는 간선 수가 그 노드의 깊이(depth)이고, 가장 깊은 잎까지의 단계 수가 트리의 높이(height)다. 이 글에서 높이는 노드 수로 센다. 노드 하나짜리 트리는 높이 1이다.

JS에서 트리는 보통 객체와 참조로 만든다. 노드 하나가 키와 왼쪽·오른쪽 자식을 가리키는 참조 두 개를 들고 있다. 배열처럼 연속된 메모리가 아니라, 힙 메모리 여기저기 흩어진 객체가 참조로 이어진 모양이다.

```js
// 노드 100만 개를 만들고 늘어난 힙 크기를 잰다 (node --expose-gc)
global.gc(); const before = process.memoryUsage().heapUsed;
const nodes = new Array(1_000_000);
for (let i = 0; i < nodes.length; i++) nodes[i] = new Node(i);
global.gc(); const after = process.memoryUsage().heapUsed;
console.log("bytes per node (incl. array slot):", ((after - before) / nodes.length).toFixed(1));
```

```text
bytes per node (incl. array slot): 56.0
```

정수 키 하나를 담는데 노드 하나가 56바이트다(노드를 담아 둔 배열 칸 포함). 객체 머리와 필드 세 개가 붙어서 그렇다. 같은 정수 100만 개를 정렬된 배열에 담으면 `Int32Array`로 4MB인데 트리는 56MB다. 노드가 흩어져 있어서 내려갈 때마다 캐시 미스가 날 수 있는 것도 비용이다. 트리는 이 비용을 내고 "정렬된 순서를 유지하면서 중간에 넣고 빼기"를 산다. 배열은 정렬을 유지하며 중간에 넣으려면 뒤의 원소를 모두 밀어야 한다.

## 왼쪽은 작고 오른쪽은 크다

이진 탐색 트리는 이진 트리에 규칙 하나를 더한다. 모든 노드에서 왼쪽 서브트리의 키는 전부 그 노드보다 작고, 오른쪽 서브트리의 키는 전부 크다. "왼쪽 자식이 작다"가 아니라 "왼쪽 서브트리 전체가 작다"인 게 중요하다. 이 차이가 뒤에서 검증 문제의 함정이 된다.

이 규칙 덕분에 찾기는 루트에서 시작해 비교 한 번마다 한쪽 서브트리를 통째로 버린다. 배열의 이진 탐색을 포인터로 옮긴 셈이다. 아래 트리는 `[8, 3, 10, 1, 6, 14, 4, 7, 13]`을 이 순서로 넣은 결과다.

넣기는 찾기와 같은 길을 가다가 빈자리에 노드를 단다. 그래서 찾기, 넣기, 지우기 모두 비용이 트리 높이 h에 비례하는 O(h)다. 노드 n개가 고르게 퍼져 있으면 h ≈ log₂ n이라 100만 개에서 20단계 남짓이다. 한 줄로 늘어서면 h = n이다. BST의 성능은 "몇 개가 들어 있나"보다 "어떤 모양인가"가 정한다.

재귀 없이 반복문으로 쓰면 깊이가 깊어도 콜 스택을 쓰지 않는다. 처음의 에러를 피하는 첫걸음이다.

```js
function insert(root, key) {
  const n = new Node(key);
  if (root === null) return n;
  let cur = root;
  while (true) {
    if (key < cur.key) { if (cur.left === null) { cur.left = n; break; } cur = cur.left; }
    else if (key > cur.key) { if (cur.right === null) { cur.right = n; break; } cur = cur.right; }
    else break; // 같은 키는 무시한다
  }
  return root;
}
```

같은 키를 어떻게 할지는 미리 정해야 한다. 무시하거나, 값만 덮어쓰거나, 노드에 개수를 두는 방법이 흔하다. "같으면 오른쪽"처럼 중복 노드를 허용하면 지우기와 검증 규칙이 모두 복잡해진다.

## 네 가지 순서로 훑기

트리의 모든 노드를 한 번씩 방문하는 순서는 네 가지가 기본이다. 앞의 셋은 깊이 우선(DFS)이고, "자기 자신을 언제 처리하나"만 다르다.

```js
const pre = [], ino = [], post = [];
function walk(n) {
  if (!n) return;
  pre.push(n.key);   // 전위: 내려가기 전에
  walk(n.left);
  ino.push(n.key);   // 중위: 왼쪽을 다 본 뒤에
  walk(n.right);
  post.push(n.key);  // 후위: 양쪽을 다 본 뒤에
}
walk(root);

const level = [], q = [root]; // 레벨 순서: 큐로 한 층씩
for (let i = 0; i < q.length; i++) {
  const n = q[i];
  level.push(n.key);
  if (n.left) q.push(n.left);
  if (n.right) q.push(n.right);
}
```

```text
pre   8 3 1 6 4 7 10 14 13
in    1 3 4 6 7 8 10 13 14
post  1 4 7 6 3 13 14 10 8
level 8 3 10 1 6 14 4 7 13
```

중위 순회 결과가 정렬되어 있다. BST에서만 생기는 성질이고, 뒤의 검증 문제에서 그대로 쓴다. 순서마다 쓰임이 다르다.

- 전위: 부모를 먼저 적으니 트리를 복사하거나 직렬화할 때 쓴다. 이 순서로 다시 넣으면 같은 모양의 BST가 나온다.
- 중위: BST의 정렬된 순회, k번째로 작은 값.
- 후위: 자식을 먼저 끝내니 폴더 크기 합산, 트리 지우기, 수식 트리 계산처럼 "아래 결과로 위를 계산"할 때 쓴다.
- 레벨: 루트에서 가까운 순이라 "가장 얕은 잎", 층별 출력, 최단 거리에 쓴다. 그래프의 BFS와 같다. [그래프 글](/posts/ds-graph-bfs-dfs)에서 더 넓게 다룬다.

화면 쪽에서도 같은 순서를 만난다. DOM 트리의 `querySelectorAll`은 문서 순서, 즉 전위 순서로 결과를 돌려주고, React도 컴포넌트 트리를 자식부터 내려갔다가 형제로 넘어가는 깊이 우선 순서로 훑는다. DOM 구조는 [DOM 글](/posts/dom-basics)에 있다.

재귀 없이 중위 순회를 하려면 콜 스택이 하던 일을 배열 스택이 대신한다. 왼쪽 끝까지 내려가며 쌓고, 하나 꺼내 방문하고, 그 오른쪽으로 옮겨 가서 다시 왼쪽 끝까지 쌓는다.

```js
function inorderIter(root) {
  const out = [], stack = [];
  let cur = root;
  while (cur || stack.length) {
    while (cur) { stack.push(cur); cur = cur.left; } // 왼쪽 끝까지 쌓는다
    cur = stack.pop();
    out.push(cur.key);                               // 방문
    cur = cur.right;                                 // 오른쪽으로 옮겨 간다
  }
  return out;
}
```

아래 그림의 칸은 방문하는 순서(정렬 순서)이고, 오른쪽은 그 순간의 스택이다. 실제로 스택 상태를 찍은 출력 그대로 옮겼다.

## 재귀는 깊이만큼 스택을 먹는다

트리 코드는 재귀로 쓰면 짧고 읽기 쉽다. 대신 호출 하나가 콜 스택에 프레임 하나를 쌓는다. 처음 예제에서는 1만 3,945단계에서 넘쳤다. 이 숫자는 함수의 지역 변수와 인자 수, Node 버전, 플랫폼에 따라 달라진다. Node 22의 V8 기본 스택은 1MB 안팎이고 `node --stack-size`로 바꿀 수 있지만, OS 스레드 스택보다 크게 잡으면 `RangeError` 대신 프로세스가 세그폴트로 죽을 수 있어서 해결책으로 쓰지 않는다.

고르는 기준은 이렇다. 균형이 보장된 트리(높이가 log n)라면 재귀로 써도 100만 개에서 깊이 20~40이라 안전하다. 입력이 사용자나 외부 데이터이고 모양을 보장할 수 없다면 반복문과 명시적 스택으로 쓴다. JSON을 재귀로 훑는 코드도 같은 문제를 안고 있다. 수만 단계로 중첩된 JSON을 일부러 보내면 재귀 파서나 재귀 `deepClone`이 넘친다.

## 지우기는 자식 수에 따라 세 갈래

지울 노드를 찾은 다음, 그 노드의 자식 수에 따라 처리가 갈린다.

- 자식이 없다: 그냥 떼어 낸다.
- 자식이 하나다: 그 자식을 내 자리에 올린다.
- 자식이 둘이다: 오른쪽 서브트리에서 가장 작은 키(후계자, in-order successor)를 찾아 내 자리에 복사하고, 후계자를 원래 자리에서 지운다. 후계자는 오른쪽 서브트리의 왼쪽 끝이라 왼쪽 자식이 없으니, 그 지우기는 앞의 두 경우로 끝난다.

```js
function remove(node, key) {
  if (!node) return null;
  if (key < node.key) node.left = remove(node.left, key);
  else if (key > node.key) node.right = remove(node.right, key);
  else {
    if (!node.left) return node.right;   // 자식 0개 또는 오른쪽만
    if (!node.right) return node.left;   // 왼쪽만
    let s = node.right;                  // 자식 2개: 후계자를 찾는다
    while (s.left) s = s.left;
    node.key = s.key;
    node.right = remove(node.right, s.key);
  }
  return node;
}

root = remove(root, 3);  // 자식 2개
root = remove(root, 14); // 자식 1개 (13)
root = remove(root, 7);  // 자식 0개
```

```text
remove 7 → pre 8 4 1 6 10 13
```

## 정렬된 키를 넣으면 리스트가 된다

처음 사고를 숫자로 다시 보자. 키 2만 개를 무작위 순서로 넣은 트리와 1부터 차례로 넣은 트리를 반복문 `insert`로 만들고, 모든 키를 한 번씩 찾았다. 무작위 순서는 시드를 고정한 셔플이다.

```text
random  height     32 | build     6.3ms | search all     4.4ms | avg steps 18.3
sorted  height  20000 | build   771.1ms | search all   795.0ms | avg steps 10000.5
log2(20000) = 14.3
```

무작위로 넣으면 높이 32, 찾기 한 번에 평균 18.3단계다. 무작위 BST에서 찾기 한 번의 평균 비교 횟수는 이론상 2(1 + 1/n)Hₙ − 3(Hₙ은 조화수)이고, 2만 개면 약 18이라 측정과 맞는다. 대략 1.39 log₂ n이다. 정렬해서 넣으면 높이가 정확히 2만, 평균 1만 단계를 걷는다. 만들기와 찾기 모두 120배 이상 느리다. 실제 데이터는 무작위가 아니다. id, 시각, 일련번호처럼 거의 정렬된 채로 들어오는 키가 흔하다.

해결책은 트리가 스스로 균형을 잡게 하는 것이다. 넣거나 지울 때 회전(rotation)으로 높이를 고쳐서 항상 O(log n)을 보장하는 트리를 균형 이진 탐색 트리라고 부른다.

- AVL 트리: 모든 노드에서 좌우 높이 차를 1 이하로 지킨다. 높이가 더 낮아 찾기가 빠르고, 대신 넣기·지우기 때 회전이 잦다.
- 레드-블랙 트리: 규칙을 느슨하게 해서 높이가 최악 약 2 log₂ n이다. 회전이 적어 쓰기가 많을 때 유리하다. 자바 `TreeMap`, C++ `std::map`(주요 구현), 리눅스 커널의 CFS 스케줄러 실행 대기열이 이걸 썼다.
- B-tree: 노드 하나에 키를 수백 개 담아 높이를 3~4로 낮춘다. 디스크 페이지 단위로 읽는 DB 인덱스의 기본 구조다. [인덱스 글](/posts/db-index)에서 실행 계획과 함께 다뤘다.
- 스킵 리스트: 트리 대신 여러 층의 연결 리스트에 확률로 균형을 맞춘다. Redis의 정렬된 셋이 이 구조다([리더보드 글](/posts/sd-leaderboard-sorted-set)).

JS에는 정렬된 맵이 내장되어 있지 않다. 자바의 `TreeMap` 같은 걸 기대하고 찾으면 없다. 선택지는 몇 가지다. 키가 한 번에 다 주어지고 잘 안 바뀌면 정렬된 배열에 이진 탐색이 가장 빠르고 작다. 정렬된 배열에서 가운데를 루트로 삼아 재귀로 만들면 균형 트리가 바로 나오는데, 2만 개로 만들면 높이 15(= ⌈log₂ 20001⌉)였다. 넣고 빼기가 계속 섞이면 검증된 라이브러리의 레드-블랙 트리나 B+ 트리를 쓴다. 대부분의 웹 서비스에서는 순서가 필요한 데이터를 DB 인덱스나 Redis 정렬된 셋에 맡기고, 애플리케이션 메모리에서는 해시맵을 쓴다. BST를 직접 짤 일은 생각보다 적지만, 그 아래에서 무슨 일이 일어나는지는 알아야 인덱스와 정렬된 셋의 비용을 설명할 수 있다.

## BST가 맞는지 검증하기

면접 단골인 "이 트리가 BST인가" 문제는 거의 모두가 한 번은 같은 함정에 빠진다. 부모와 직접 자식만 비교하는 것이다.

```js
function wrongValid(n) { // 부모와 자식만 비교한다
  if (!n) return true;
  if (n.left && n.left.val >= n.val) return false;
  if (n.right && n.right.val <= n.val) return false;
  return wrongValid(n.left) && wrongValid(n.right);
}
```

`[5, 3, 8, null, null, 4, 9]`(레벨 순서, `null`은 빈자리)는 루트 5의 오른쪽 8 아래 왼쪽에 4가 있는 트리다. 4 < 8이라 지역 비교는 통과한다. 그런데 4는 5의 오른쪽 서브트리에 있으니 5보다 커야 한다. BST가 아니다.

바르게 하려면 각 노드가 들어갈 수 있는 범위를 들고 내려간다. 왼쪽으로 가면 상한이 부모 값으로 줄고, 오른쪽으로 가면 하한이 부모 값으로 오른다.

## 두 노드의 가장 가까운 공통 조상

최소 공통 조상(LCA, lowest common ancestor)은 두 노드를 모두 자손으로 가진 노드 중 가장 깊은 것이다. 조직도에서 두 사람의 가장 가까운 공통 상사, 파일 경로 두 개의 공통 상위 폴더, git에서 두 브랜치가 갈라진 커밋(merge-base)이 모두 같은 질문이다.

BST라면 값만 보고 내려가면 된다. 두 값이 모두 현재 노드보다 작으면 왼쪽, 모두 크면 오른쪽, 그렇지 않으면 두 값이 여기서 갈라지니 현재 노드가 답이다.

BST가 아닌 일반 이진 트리라면 값으로 방향을 정할 수 없다. 후위 순회로 양쪽 서브트리에 물어본다. 왼쪽과 오른쪽에서 하나씩 찾았다면 내가 답이고, 한쪽에서만 찾았다면 그 결과를 위로 올린다.

```js
function lcaBST(root, p, q) { // O(h), 반복문
  let cur = root;
  while (cur) {
    if (p < cur.val && q < cur.val) cur = cur.left;
    else if (p > cur.val && q > cur.val) cur = cur.right;
    else return cur.val;
  }
  return null;
}
function lca(n, p, q) { // 일반 이진 트리, O(n)
  if (!n || n.val === p || n.val === q) return n;
  const L = lca(n.left, p, q), R = lca(n.right, p, q);
  return L && R ? n : L || R;
}
```

```text
lcaBST(4,7) 6 lcaBST(4,13) 8 lcaBST(1,3) 3
lca(4,7) 6 lca(1,7) 3 lca(13,8) 8
```

일반 트리 풀이는 두 노드가 모두 트리에 있다고 가정한다. 하나만 있으면 그 노드를 답으로 돌려주는데, 면접에서 이 가정을 먼저 확인하면 좋다. 한 트리에 LCA 질문이 수십만 번 들어온다면 매번 O(n)은 비싸다. 노드마다 깊이와 2^k번째 조상을 미리 계산해 두는 이진 리프팅(binary lifting)으로 질문 하나를 O(log n)에 답한다.

## 트리를 꺼낼 때와 넣어 둘 때

BST를 고르는 이유는 하나다. 순서가 필요한데 데이터가 계속 바뀐다. "이 값 이상 중 가장 작은 것", "구간 안의 모든 키", "k번째로 작은 값"을 넣고 빼기와 섞어서 물어야 할 때다. 순서가 필요 없으면 [해시맵](/posts/ds-hash-map)이 빠르고, 가장 작은 것 하나만 반복해서 꺼내면 [힙](/posts/ds-heap)이 더 단순하고 빠르다. 데이터가 거의 안 바뀌면 정렬된 배열이 메모리도 적고 캐시에도 유리하다.

트리 코드에서 실제로 자주 보는 실수는 이렇다.

- 정렬된 입력을 균형 없는 BST에 넣는다. 처음 예제처럼 리스트가 되고, 재귀면 스택이 넘친다.
- 검증할 때 부모와 자식만 비교한다. 범위를 들고 내려가야 한다.
- 레벨 순회에 `shift()`를 쓴다. 큰 트리에서 O(n²)이 된다.
- 중복 키 규칙을 정하지 않는다. 넣기는 오른쪽, 찾기는 왼쪽처럼 어긋나면 있는 키를 못 찾는다.
- 지우기에서 부모의 참조를 갱신하지 않는다. 위 `remove`처럼 "서브트리의 새 루트를 돌려받아 다시 단다"로 쓰면 부모 포인터 없이도 깔끔하다.

트리 문제는 결국 "이 노드에서 할 일을 정하고 자식에게 같은 일을 맡긴다"로 푼다. 할 일을 언제 하느냐가 순회 순서를 정하고, 무엇을 들고 내려가느냐(범위, 깊이, 경로)가 문제를 푼다. 그 틀 위에서 높이가 곧 비용이라는 것만 기억하면 BST, 균형 트리, B-tree가 한 줄로 이어진다.

## 면접에서 나올 만한 질문

### BST의 찾기, 넣기, 지우기 시간 복잡도는 어떻게 되나요?

모두 트리 높이 h에 비례하는 O(h)다. 균형이 잡혀 있으면 h가 log n이라 O(log n)이지만, 정렬된 키를 차례로 넣는 식으로 한쪽으로 기울면 h가 n이 되어 O(n)이다. 실제로 키 2만 개를 무작위로 넣으면 평균 18단계였고 정렬해서 넣으면 1만 단계였다. 그래서 최악을 보장해야 하면 AVL이나 레드-블랙 같은 균형 트리를 쓴다.

### 전위, 중위, 후위, 레벨 순회는 각각 언제 쓰나요?

전위는 부모를 먼저 처리하니 트리 복사나 직렬화에, 중위는 BST에서 정렬된 순서가 나오니 정렬 순회나 k번째 원소에 쓴다. 후위는 자식 결과로 부모를 계산하는 폴더 크기 합이나 트리 해제에 쓴다. 레벨 순회는 큐로 루트에서 가까운 순서대로 보니 층별 처리나 가장 얕은 노드 찾기에 쓴다.

### 재귀 대신 반복문으로 트리를 순회해야 하는 이유는 무엇인가요?

재귀는 깊이만큼 콜 스택 프레임을 쌓아서 한쪽으로 긴 트리에서는 스택이 넘친다. Node 22에서 재귀 insert가 깊이 1만 4천 정도에서 RangeError를 냈다. 반복문과 배열 스택을 쓰면 같은 정보를 힙에 쌓으니 넘치지 않는다. 트리 모양을 보장할 수 없는 외부 입력이면 반복문이 안전하다.

### 자식이 둘인 노드는 어떻게 지우나요?

오른쪽 서브트리에서 가장 작은 노드(후계자)를 찾아 그 키를 지울 자리에 복사하고, 후계자 노드를 원래 위치에서 지운다. 후계자는 왼쪽 자식이 없으니 그 지우기는 자식이 0개나 1개인 쉬운 경우로 끝난다. 왼쪽 서브트리의 가장 큰 노드(선행자)를 써도 같다.

### 이 트리가 BST인지 어떻게 검증하나요? 흔한 실수는요?

각 노드가 들어갈 수 있는 하한과 상한을 들고 내려가며 확인한다. 왼쪽으로 가면 상한이 부모 값이 되고 오른쪽으로 가면 하한이 부모 값이 된다. 흔한 실수는 부모와 직접 자식만 비교하는 것인데, 손자 노드가 조상의 범위를 어기는 경우를 놓친다. 중위 순회 결과가 엄격하게 증가하는지 보는 방법도 같은 답을 준다.

### BST가 한쪽으로 기우는 걸 어떻게 막나요?

넣고 지울 때 회전으로 높이를 고치는 균형 트리를 쓴다. AVL은 좌우 높이 차를 1 이하로 엄격하게 지켜 찾기가 빠르고, 레드-블랙은 느슨한 대신 회전이 적어 쓰기가 많은 곳에 맞다. 데이터를 한 번에 다 안다면 정렬한 뒤 가운데를 루트로 삼아 재귀로 만들면 바로 균형 트리가 나온다.

### DB 인덱스는 왜 이진 트리가 아니라 B-tree를 쓰나요?

디스크나 페이지 캐시는 한 번에 수 KB 페이지 단위로 읽기 때문이다. 이진 트리는 노드 하나에 키 하나라 100만 개면 20번 가까이 페이지를 읽어야 하지만, B-tree는 노드 하나(페이지 하나)에 키를 수백 개 담아 높이를 3~4로 낮춘다. 읽는 페이지 수가 곧 비용이라 가지를 넓게 펴는 쪽이 유리하다.

### 일반 이진 트리에서 두 노드의 최소 공통 조상은 어떻게 찾나요?

후위 순회로 왼쪽과 오른쪽 서브트리에 두 노드를 찾게 하고, 양쪽에서 하나씩 찾았으면 현재 노드가 답이다. 한쪽에서만 찾았으면 그 결과를 위로 올린다. 시간은 O(n)이고 두 노드가 모두 트리에 있다는 가정이 필요하다. BST라면 값만 보고 갈라지는 지점을 찾으면 되니 O(h)다.
