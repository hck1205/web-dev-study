[LeetCode 162. Find Peak Element](https://leetcode.com/problems/find-peak-element/)는 정렬되지 않은 배열에서 이분 탐색을 하는 문제다. 이분 탐색은 정렬된 배열에서만 쓴다고 배웠다면 처음엔 말이 안 되는 것처럼 보인다. 나도 처음 보고 "정렬도 안 됐는데 절반을 어떻게 버리지?"부터 생각했다. 답은 이 문제가 찾는 게 "아무 봉우리 하나"라는 데 있다. 가장 높은 봉우리를 찾으라고 했다면 O(n)보다 빠른 방법은 없다.

문제를 내 말로 풀면 이렇다. 정수 배열 `nums`에서 봉우리 하나의 인덱스를 돌려준다. 봉우리는 양옆 이웃보다 큰 칸이다. 배열 바깥(`nums[-1]`과 `nums[n]`)은 음의 무한대로 본다. 그래서 첫 칸은 오른쪽 이웃보다만 크면 봉우리고, 끝 칸은 왼쪽 이웃보다만 크면 봉우리다. 봉우리가 여러 개면 아무거나 돌려줘도 된다.

풀이를 정하는 조건은 이렇다.

- 이웃한 두 칸의 값은 항상 다르다(`nums[i] != nums[i + 1]`). 이 조건이 없으면 O(log n)이 불가능하다. 뒤에서 왜 그런지 본다.
- 길이는 1 이상 1000 이하다. O(n)도 통과하지만 문제가 O(log n)을 요구한다.
- 값은 `int` 전체 범위(-2^31 이상 2^31 - 1 이하)다. 자바에서 음의 무한대를 `Integer.MIN_VALUE`로 흉내 내면 틀리는 이유가 된다.

이분 탐색의 구간 다루기는 [LeetCode 704 글](/posts/leetcode-binary-search)에서, 이분 탐색이 정렬이 아니라 "참거짓이 한 번만 바뀌는 조건"에 쓰는 도구라는 이야기는 [이분 탐색 글](/posts/binary-search)에서 다뤘다. 그 글의 "정렬이 반쯤 깨진 배열에서" 절에 이 문제가 짧게 나온다. 여기서는 그게 왜 맞는지, 다른 풀이와 무엇이 다른지를 끝까지 판다. 실행 결과는 Node.js 22, Python 3.13, OpenJDK에서 돌린 값이다.

## 양옆보다 높은 칸

예시 하나로 끝까지 간다.

```text
번호 :   0  1  2  3  4  5  6  7
값   :   1  3  2  4  6  5  2  7
```

칸마다 양옆과 비교해 보자. 배열 밖은 음의 무한대다.

- 1번(값 3): 왼쪽 1, 오른쪽 2보다 크다. 봉우리.
- 4번(값 6): 왼쪽 4, 오른쪽 5보다 크다. 봉우리.
- 7번(값 7): 왼쪽 2보다 크고 오른쪽은 배열 밖이다. 봉우리.
- 나머지는 적어도 한쪽 이웃이 더 크다. 예를 들어 3번(값 4)은 오른쪽 6보다 작다.

봉우리가 세 곳이라 1, 4, 7 중 무엇을 돌려줘도 정답이다. 이 "아무거나"가 이 문제를 빠르게 풀 수 있게 해 준다.

봉우리는 항상 하나 이상 있다. 가장 큰 값이 있는 칸을 떠올려 보면 된다. 그 칸은 양옆보다 크거나(이웃이 다르다는 조건 덕분에 같을 수는 없다) 배열 끝이다. 어느 경우든 봉우리다.

## 칸마다 양옆과 비교한다

정의 그대로 옮기면 첫 풀이다. 배열 밖은 `-Infinity`로 둔다.

```js
function findPeakElement(nums) {
  for (let i = 0; i < nums.length; i++) {
    const left = i === 0 ? -Infinity : nums[i - 1];               // 배열 밖은 음의 무한대
    const right = i === nums.length - 1 ? -Infinity : nums[i + 1];
    if (nums[i] > left && nums[i] > right) return i;              // 처음 만난 봉우리
  }
  return -1; // 봉우리는 반드시 있으니 여기까지 오지 않는다
}
```

예시에서는 0번(1 < 3)을 지나 1번에서 멈춘다. 시간은 O(n), 공간은 O(1)이다. 비교를 칸마다 두 번씩 하는데, 사실 한 번이면 된다.

## 처음으로 내려가는 곳

왼쪽 끝 바깥이 음의 무한대라서, 0번 칸은 "왼쪽보다 크다"를 공짜로 만족한다. 그러면 오른쪽으로 가면서 처음으로 `nums[i] > nums[i + 1]`이 되는 i가 봉우리다. 거기까지는 계속 올라왔으니 왼쪽보다 크고, 오른쪽보다 크다는 건 방금 확인했다. 끝까지 내려가는 곳이 없으면 계속 올라온 것이니 마지막 칸이 봉우리다.

```js
function findPeakElement(nums) {
  for (let i = 0; i < nums.length - 1; i++) {
    if (nums[i] > nums[i + 1]) return i; // 여기까지 올라왔고, 다음 칸이 낮다
  }
  return nums.length - 1;                // 끝까지 오르막이었다
}
```

비교가 칸마다 한 번으로 줄었다. 이 생각이 이분 탐색 풀이의 씨앗이다. "오르막이 이어지다 처음 내리막이 나오는 곳"이 봉우리라는 것, 그리고 오르막 위에 서 있으면 오른쪽 어딘가에 봉우리가 반드시 있다는 것이다.

시간은 여전히 O(n)이다. 배열이 계속 오르막이면 끝까지 간다.

## 가장 높은 칸은 언제나 봉우리다

앞에서 봉우리가 반드시 있다는 걸 보일 때 쓴 성질을 그대로 풀이로 쓸 수도 있다.

```js
function findPeakElement(nums) {
  let best = 0;
  for (let i = 1; i < nums.length; i++) {
    if (nums[i] > nums[best]) best = i; // 가장 큰 값의 자리
  }
  return best;
}
```

파이썬이면 `nums.index(max(nums))` 한 줄이다. 예시에서는 7번(값 7)이 나온다. 틀리지 않고 짧아서 면접에서 첫 답으로 내기 좋다.

하지만 이 풀이는 이 문제가 준 자유를 쓰지 않았다. 문제는 아무 봉우리나 달라고 했는데, 이 코드는 가장 높은 봉우리를 찾는다. 가장 높은 봉우리는 어디든 있을 수 있어서 배열 전체를 봐야 하고, 그래서 입력과 상관없이 항상 O(n)이다. 앞의 두 풀이는 앞쪽에 봉우리가 있으면 일찍 멈추는데, 이 풀이는 늘 끝까지 간다. 질문을 약하게 줄 때는 그 약함을 써야 빨라진다.

## 오르막에 서 있으면 오른쪽에 봉우리가 있다

가운데 칸 `mid` 하나와 그 오른쪽 이웃 `mid + 1`만 본다. 이웃끼리 값이 다르니 경우는 둘이다.

- `nums[mid] < nums[mid + 1]`: 오르막 위에 서 있다. mid에서 오른쪽으로 걸어가면 계속 오르다가 언젠가 처음으로 내려가는 곳이 나오고, 그 직전이 봉우리다. 끝까지 내려가지 않으면 마지막 칸이 봉우리다(오른쪽 밖이 음의 무한대라서). 어느 쪽이든 `mid + 1`부터 끝 사이에 봉우리가 있다. 왼쪽 절반은 버린다.
- `nums[mid] > nums[mid + 1]`: 내리막이 시작된다. 이번엔 mid에서 왼쪽으로 걸어가면 같은 논리로 처음부터 mid 사이에 봉우리가 있다. mid 자신이 봉우리일 수도 있으니 mid는 남기고 오른쪽 절반을 버린다.

정렬은 없지만, 매번 "이 절반에는 봉우리가 반드시 있다"고 말할 수 있는 절반이 있다. 이분 탐색에 필요한 건 그것뿐이다. 버린 쪽에 봉우리가 있을 수도 있지만 상관없다. 아무거나 하나면 되니까.

```js
function findPeakElement(nums) {
  let lo = 0, hi = nums.length - 1; // 봉우리가 반드시 있는 구간 [lo, hi]
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;          // lo < hi라 mid + 1 ≤ hi, 배열 안이다
    if (nums[mid] < nums[mid + 1]) lo = mid + 1; // 오르막: 오른쪽에 봉우리가 있다
    else hi = mid;                               // 내리막: mid를 포함한 왼쪽에 있다
  }
  return lo; // 구간이 한 칸으로 줄었다. 그 칸이 봉우리다
}
```

구간 `[lo, hi]`는 "이 안에 봉우리가 반드시 있다"는 약속이다. 처음엔 배열 전체라 약속이 성립하고, 매번 위의 두 경우 중 하나로 약속을 지키며 줄인다. 한 칸이 남으면 그 칸이 봉우리다.

이 코드는 [이분 탐색 글](/posts/binary-search)에서 본 lower bound와 모양이 똑같다. 조건이 `nums[mid] < x`에서 `nums[mid] < nums[mid + 1]`로 바뀌었을 뿐이다. 다만 lower bound와 달리 "오르막인가"는 배열 전체에서 F, T가 한 번만 바뀌는 조건이 아니다. 예시에서 오르막인 자리는 0, 2, 3, 6번이라 들쭉날쭉하다. 그래도 맞는 이유는 위에서 본 "구간 안에 봉우리가 있다"는 약속이 매번 지켜지기 때문이다. 단조성이 아니라 이 약속이 정당성의 근거다.

### 두 칸, 세 칸짜리 배열을 손으로

경계에서 실수가 나기 쉬우니 작은 배열을 손으로 따라가 보자.

```text
[5]        lo 0, hi 0 → 루프를 안 돈다 → 0
[2, 1]     mid 0: 2 > 1 내리막, hi = 0 → 0
[1, 2]     mid 0: 1 < 2 오르막, lo = 1 → 1
[1, 3, 2]  mid 1: 3 > 2 내리막, hi = 1 → mid 0: 1 < 3 오르막, lo = 1 → 1
[3, 2, 1]  mid 1: 2 > 1 내리막, hi = 1 → mid 0: 3 > 2 내리막, hi = 0 → 0
```

원소 하나면 그 칸이 봉우리다. 배열 밖이 양쪽 모두 음의 무한대이기 때문이다. `[2, 1]`의 0번은 왼쪽 밖보다 크고 오른쪽 1보다 크니 봉우리이고, `[1, 2]`의 1번도 같은 이유로 봉우리다. 이 경우들에서 `mid + 1`이 배열 밖으로 나가는 일은 없다. `lo < hi`일 때 아래쪽 가운데 `mid`는 `hi`보다 작아서 `mid + 1`이 많아야 `hi`다.

### 비교가 몇 번 일어나는지 세어 보면

계속 오르막인 배열과 계속 내리막인 배열에서 비교 횟수를 셌다.

```text
n         오르막  내리막
1            0      0
2            1      1
3            1      2
1000         9     10
1000000     19     20
```

1000칸이면 많아야 10번, 100만 칸이면 20번이다. ⌈log₂ n⌉과 같다. 내리막에서 한 번씩 더 많은 건 `hi = mid`가 mid를 남겨 구간이 `lo = mid + 1`보다 조금 덜 줄기 때문이다. 오르막이든 내리막이든 봉우리가 배열 끝에 하나뿐인 최악의 경우인데도 이 정도다.

### 파이썬과 자바로 옮기면

```python
from typing import List

class Solution:
    def findPeakElement(self, nums: List[int]) -> int:
        lo, hi = 0, len(nums) - 1
        while lo < hi:
            mid = (lo + hi) // 2
            if nums[mid] < nums[mid + 1]:   # 오르막 위: 오른쪽으로 오르면 봉우리가 있다
                lo = mid + 1
            else:                           # 내리막 시작: mid를 포함한 왼쪽에 있다
                hi = mid
        return lo
```

```java
class Solution {
    public int findPeakElement(int[] nums) {
        int lo = 0, hi = nums.length - 1;
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] < nums[mid + 1]) lo = mid + 1; // 값끼리만 비교하니 경계값 걱정이 없다
            else hi = mid;
        }
        return lo;
    }
}
```

예시에서 세 언어 모두 4를 돌려준다. `[5]`는 0, `[2, 1]`은 0, `[1, 2]`는 1이다.

자바에서 짚을 곳은 첫 번째 풀이(칸마다 양옆과 비교)를 옮길 때다. 자바에는 `int`의 음의 무한대가 없어서 `Integer.MIN_VALUE`로 대신하기 쉽다. 그런데 이 문제는 값이 `int` 전체 범위라 `MIN_VALUE` 자체가 배열에 들어올 수 있다.

```text
                     [MIN]  [MIN, MIN+1, MIN]  [MIN+5, MIN]
binary search          0          1                0
MIN_VALUE 경계값       -1          1                0
long 경계값            0          1                0
```

`[Integer.MIN_VALUE]` 하나짜리 배열에서 `MIN_VALUE > MIN_VALUE`가 거짓이라 봉우리를 못 찾고 -1을 냈다. 경계값을 `long`의 `Long.MIN_VALUE`로 넓히거나, 이분 탐색처럼 배열 안의 값끼리만 비교하면 이 문제가 사라진다. 이분 탐색 풀이는 `mid + 1`이 항상 배열 안이라 경계값을 쓸 일이 없다. 자바스크립트와 파이썬은 `-Infinity`, `float('-inf')`가 있어서 이 함정이 없다.

### 재귀로 쓰면

같은 생각을 재귀로 쓰면 "봉우리가 있는 구간"을 인자로 넘기는 모양이 된다.

```js
function findPeakElement(nums, lo = 0, hi = nums.length - 1) {
  if (lo === hi) return lo;                     // 한 칸이면 그 칸이 봉우리
  const mid = (lo + hi) >>> 1;
  return nums[mid] < nums[mid + 1]
    ? findPeakElement(nums, mid + 1, hi)        // 오르막: 오른쪽 구간
    : findPeakElement(nums, lo, mid);           // 내리막: mid 포함 왼쪽 구간
}
```

시간은 같은 O(log n)이고, 호출 스택이 log n 깊이만큼 쌓여 공간이 O(log n)이다. 길이 1000이면 깊이 10이라 파이썬 기본 재귀 한도(1000)에도 한참 못 미친다. 분할 정복으로 설명할 때 이 모양이 자연스럽지만, 반복문 버전이 공간도 적고 함수 호출 비용도 없다.

## 100만 칸에서 재 보면

LeetCode 크기(1000)는 어느 풀이든 순식간이다. 길이 100만 배열 두 개로 풀이마다 100번씩 돌린 평균을 쟀다.

- 오르막: 0, 1, 2, …, 999999. 봉우리는 맨 끝 하나뿐이다.
- 무작위: 이웃끼리 다른 무작위 값 100만 개. 봉우리가 아주 많다.

```text
오르막 argMax           idx 999999  1.8519 ms
```

오르막에서는 앞의 세 풀이가 모두 100만 칸을 다 보고, 이분 탐색은 20번 비교로 끝나 천 배 안팎으로 빠르다. 무작위 배열에서는 재미있는 일이 생긴다. 앞에서부터 보는 두 풀이는 0번이 이미 봉우리라 바로 멈춰서 이분 탐색보다도 빠르다. 반면 가장 큰 값을 찾는 풀이는 봉우리가 아무리 많아도 끝까지 간다.

같은 O(n)이라도 "일찍 멈출 수 있는 O(n)"과 "항상 끝까지 가는 O(n)"은 다르다. 그래도 최악을 보장하는 건 이분 탐색뿐이다. 그리고 세 풀이가 돌려준 봉우리가 서로 다르다는 것(0, 6378, 923897)도 눈여겨볼 만하다. 모두 정답이다.

### 여섯 풀이가 정말 봉우리를 주는지

봉우리는 여러 개일 수 있어서 "정답과 같은가"로는 채점할 수 없다. 대신 돌려준 자리가 봉우리인지 정의대로 확인한다. 이웃끼리 다른 0~7 사이 값으로 길이 1~10 배열 2만 개를 만들고, 뒤에서 볼 삼분 탐색까지 여섯 풀이를 넣었다.

```js
const { isPeak, checkAll, firstDrop, argMax, findPeakElement, recur, ternary } = require("./sol.js");

const wrong = { checkAll: 0, firstDrop: 0, argMax: 0, findPeakElement: 0, recur: 0, ternary: 0 };
for (let it = 0; it < 20000; it++) {
  const n = 1 + Math.floor(Math.random() * 10);
  const nums = [];
  while (nums.length < n) {
    const v = Math.floor(Math.random() * 8);
    if (nums.length === 0 || nums[nums.length - 1] !== v) nums.push(v); // 이웃끼리 다르게
  }
  for (const f of [checkAll, firstDrop, argMax, findPeakElement, recur, ternary]) {
    if (!isPeak(nums, f(nums))) wrong[f.name]++; // 돌려준 자리가 봉우리가 아니면 오답
  }
}
console.log(wrong);
```

```text
{ checkAll: 0, firstDrop: 0, argMax: 0, findPeakElement: 0, recur: 0, ternary: 8 }
```

다섯 풀이는 한 번도 틀리지 않았고, 삼분 탐색만 8번 봉우리가 아닌 칸을 돌려줬다. 다시 돌리면 6번이 나오기도 했다. 2만 개 중 몇 개라 손으로 고른 테스트 몇 개로는 거의 안 걸린다. "아무거나 정답"인 문제는 이렇게 정답 대신 조건을 검사하는 채점관을 만들어 두면 편하다. 아래 연습 칸의 `checkPeak`도 같은 생각이다.

## 봉우리 찾기 다섯 가지

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 칸마다 양옆과 비교 | O(n) | O(1) | 정의를 그대로 확인할 때. 채점관 |
| 처음 내려가는 곳 | O(n) | O(1) | 봉우리가 앞쪽에 많다고 알 때 |
| 가장 큰 값의 자리 | O(n), 항상 끝까지 | O(1) | 가장 높은 봉우리가 필요할 때 |
| 오르막 쪽 이분 탐색 | O(log n) | O(1) | 기본 답 |
| 재귀 분할 정복 | O(log n) | O(log n) | 분할 정복으로 설명할 때 |

가장 큰 값 풀이만 다른 질문(가장 높은 봉우리)에 답한다는 게 이 표에서 눈여겨볼 점이다. 그 질문에는 O(n)보다 빠른 방법이 없다. 값이 어디에 숨어 있을지 모르니 모든 칸을 봐야 한다.

## 삼분 탐색과 위쪽 가운데가 틀리는 이유

### 삼분 탐색을 쓴다

"봉우리를 찾는 이분 탐색"이라는 말에 삼분 탐색(구간을 셋으로 나눠 두 점을 비교하고 한쪽 3분의 1을 버리는 방법)을 떠올리기 쉽다. 삼분 탐색은 봉우리가 하나뿐인 산(오르다가 내리기만 하는 배열)에서만 맞다. 봉우리가 여러 개면 두 점을 비교한 결과가 봉우리가 있는 쪽을 알려 주지 않는다. 앞에서 본 대로 이웃끼리 다른 무작위 배열 2만 개에서 6~8번 틀렸다. 그중 하나다.

```text
[1, 2, 6, 5, 4, 3, 7, 4, 2] → 3번 (값 5, 왼쪽 6보다 작아 봉우리가 아니다)
```

처음에 2번(6)과 6번(7)을 비교해 6이 작으니 0~2번을 버렸다. 2번이 봉우리였는데 함께 버려졌다. 그 뒤 4번(4)과 7번(4), 4번(4)과 5번(3)을 비교하며 줄이다가 `[3, 4]`만 남았는데, 이 구간은 6에서 내려오는 내리막 한가운데라 봉우리가 없다. 이분 탐색이 맞는 이유는 mid와 mid + 1처럼 "바로 옆" 두 칸을 비교해서다. 바로 옆이라야 오르막인지 내리막인지가 정해지고, 그 방향으로 가면 봉우리가 있다는 논증이 성립한다. 멀리 떨어진 두 점 사이에서는 그 논증이 안 된다. 삼분 탐색이 맞는 산(봉우리 하나)은 아래 852번에서 다시 나온다.

### 위쪽 가운데를 쓴다

`mid = (lo + hi + 1) >>> 1`로 위쪽 가운데를 쓰면 두 가지가 틀린다. `lo = n - 2`, `hi = n - 1`이면 mid가 `n - 1`이라 `nums[mid + 1]`이 배열 밖이다. 그리고 `hi = mid`가 구간을 줄이지 못한다.

```text
[1, 3, 2, 4, 6, 5, 2, 7] → lo 3, hi 4에서 끝나지 않음
[1, 2]                   → lo 0, hi 1에서 끝나지 않음
```

자바스크립트에서 `nums[n]`은 `undefined`라 `x < undefined`가 거짓이 되어 `hi = mid`로 가고, 같은 자리를 영원히 돈다. `hi = mid`와 짝이 되는 건 아래쪽 가운데다. 아래쪽 가운데는 `lo < hi`일 때 항상 `hi`보다 작아서 `mid + 1`이 배열 안이고, `hi = mid`가 구간을 반드시 줄인다.

### `lo <= hi`로 돈다

닫힌 구간 습관으로 `while (lo <= hi)`를 쓰면 lo와 hi가 같아진 다음에도 돈다. `hi = mid`는 구간을 더 줄이지 못한다.

```text
[1, 3, 2, 4, 6, 5, 2, 7] → lo 4, hi 4에서 끝나지 않음
[5]                      → lo 0, hi 0에서 끝나지 않음
```

원소 하나짜리 배열에서 바로 멈춘다. 이 문제의 구간은 "봉우리가 반드시 있는 곳"이라 한 칸이 남으면 일이 끝난 것이다. `lo < hi`로 돌고 `lo`를 돌려준다.

### mid를 mid - 1과 비교하며 경계를 놓친다

`nums[mid - 1] < nums[mid]`로 비교하는 거울 버전도 가능하다. 그때는 오르막이면 mid를 남기고(`lo = mid`), 내리막이면 `hi = mid - 1`이다. `lo = mid`는 위쪽 가운데와 짝이어야 무한 루프가 없다. 비교 방향을 바꾸면 가운데 방향과 갱신식을 함께 바꿔야 한다. 처음 짤 때는 mid와 mid + 1 버전 하나만 손에 익히는 게 낫다.

## 같은 값이 붙거나 2차원이 되면

### 이웃끼리 같은 값이 있어도 된다면

`nums[i] != nums[i + 1]` 조건이 빠지면 `nums[mid] === nums[mid + 1]`일 때 어느 쪽이 오르막인지 알 수 없다. 위 코드는 이 경우를 내리막처럼 다루는데, 실제로 틀린다.

```text
[1, 1, 1, 2, 1, 1, 1] → 0번 (값 1, 오른쪽도 1이라 봉우리가 아니다)
```

진짜 봉우리는 3번 하나뿐인데, 평평한 칸만 보고 왼쪽으로 가다 끝에 닿았다. 이건 코드를 고쳐서 해결되는 문제가 아니다. `[1, 1, …, 1, 2, 1, …, 1]`처럼 평평한 바닥 어딘가에 봉우리 하나가 숨어 있으면, 그 2가 어디 있는지 알려 주는 정보가 모든 1에 똑같이 없다. 결국 칸을 하나씩 봐야 하니 최악 O(n)이다. 같은 값을 만나면 그 칸을 건너뛰고 계속 찾는 식으로 짤 수는 있지만 최악은 피할 수 없다. 이웃이 다르다는 조건이 이 문제의 O(log n)을 가능하게 한 바탕이다.

### 봉우리가 하나뿐인 산 (852. Peak Index in a Mountain Array)

배열이 오르다가 내리기만 한다면 봉우리는 정확히 하나다. 이때는 "오르막인가"가 F, T가 아니라 T, T, …, T, F, F처럼 한 번만 바뀌는 진짜 단조 조건이 되고, 위 코드가 그대로 답이다. 이 경우에는 삼분 탐색도 맞다. 다만 이분 탐색이 비교를 더 적게 한다. 852번은 이 글의 코드를 그대로 내면 된다.

### 산에서 값 찾기 (1095. Find in Mountain Array)

산 모양 배열에서 target의 가장 앞 인덱스를 찾는다. 먼저 이 글의 방법으로 봉우리를 찾고, 왼쪽 오르막은 오름차순 이분 탐색, 오른쪽 내리막은 내림차순 이분 탐색으로 찾는다. 이분 탐색 세 번, O(log n)이다. 배열에 직접 접근하지 못하고 `get(i)` 호출 횟수가 100번으로 제한돼 있어서 O(n)은 처음부터 안 된다.

```js
// 1095. get 호출 수를 세는 가짜 MountainArray
class MountainArray {
  constructor(a) { this.a = a; this.calls = 0; }
  get(i) { this.calls++; return this.a[i]; }
  length() { return this.a.length; }
}

function findInMountainArray(target, arr) {
  const n = arr.length();
  // 1) 봉우리: 이 글의 이분 탐색 그대로
  let lo = 0, hi = n - 1;
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;
    if (arr.get(mid) < arr.get(mid + 1)) lo = mid + 1;
    else hi = mid;
  }
  const peak = lo;
  // 2) 왼쪽 오르막에서 오름차순 이분 탐색 (가장 앞 인덱스가 우선이라 먼저 본다)
  lo = 0; hi = peak;
  while (lo <= hi) {
    const mid = (lo + hi) >>> 1, v = arr.get(mid);
    if (v === target) return mid;
    if (v < target) lo = mid + 1; else hi = mid - 1;
  }
  // 3) 오른쪽 내리막에서 내림차순 이분 탐색 (부등호 방향이 반대)
  lo = peak + 1; hi = n - 1;
  while (lo <= hi) {
    const mid = (lo + hi) >>> 1, v = arr.get(mid);
    if (v === target) return mid;
    if (v > target) lo = mid + 1; else hi = mid - 1;
  }
  return -1;
}
```

`get` 호출 수를 세는 가짜 `MountainArray`로 돌려 봤다.

```text
[1, 4, 6, 9, 7, 6, 3]에서
target 6 → 2   get 호출 8
target 3 → 6   get 호출 10
target 9 → 3   get 호출 9
target 5 → -1  get 호출 10
길이 9999 산, target 2500 → 2500   get 호출 38
```

6은 2번과 5번 두 곳에 있는데, 왼쪽 오르막을 먼저 찾으니 더 앞인 2번이 나온다. 길이 1만에 가까운 산에서도 호출이 38번이라 제한 100번에 넉넉하다. 봉우리 찾기에서 한 번에 `get`을 두 번 부르니, 같은 칸을 다시 읽지 않게 값을 저장해 두면 호출을 더 줄일 수 있다. 내리막 쪽 탐색에서 부등호 방향을 뒤집는 걸 빠뜨리는 실수가 가장 흔하다.

### 2차원 격자에서 봉우리 (1901. Find a Peak Element II)

상하좌우 이웃보다 큰 칸을 찾는다. 가운데 열을 하나 골라 그 열에서 가장 큰 칸을 찾고, 그 칸의 좌우 이웃과 비교해 더 큰 쪽 절반의 열로 간다. 열 하나를 훑는 데 O(m), 열을 반씩 줄이니 O(m log n)이다. 1차원에서 "mid와 mid + 1 비교"가 2차원에서는 "열 최댓값과 옆 열 비교"가 된 것이다. 열 최댓값을 고르는 이유는, 그 칸이 같은 열의 위아래보다 이미 크니 좌우만 보면 되기 때문이다.

```js
// 1901. 가운데 열의 최댓값을 보고 더 큰 이웃이 있는 쪽 열 절반으로 간다
function findPeakGrid(mat) {
  const m = mat.length, n = mat[0].length;
  let lo = 0, hi = n - 1;                       // 봉우리가 있는 열 구간
  while (lo <= hi) {
    const mid = (lo + hi) >>> 1;
    let r = 0;
    for (let i = 1; i < m; i++) if (mat[i][mid] > mat[r][mid]) r = i; // 이 열에서 가장 큰 칸
    const left = mid > 0 ? mat[r][mid - 1] : -1;  // 값은 1 이상이라 -1이 바깥 역할
    const right = mid < n - 1 ? mat[r][mid + 1] : -1;
    if (mat[r][mid] > left && mat[r][mid] > right) return [r, mid];
    if (right > mat[r][mid]) lo = mid + 1;       // 오른쪽이 더 크다: 오른쪽 열들로
    else hi = mid - 1;                            // 왼쪽이 더 크다: 왼쪽 열들로
  }
  return [-1, -1];
}
```

`[[10, 20, 15], [21, 30, 14], [7, 16, 32]]`에서는 가운데 열 최댓값 30이 상하좌우(20, 16, 21, 14)보다 커서 바로 `[1, 1]`이 나온다. `[[1, 4], [3, 2]]`는 0번 열의 최댓값 3이 오른쪽 2보다 커서 `[1, 0]`이다. 모든 값이 서로 다른 무작위 격자 5000개에서 돌려준 칸이 봉우리가 아닌 경우는 0건이었다. 1차원과 달리 열이 하나 남을 때까지 줄이지 않고, 찾자마자 돌려주는 닫힌 구간 모양으로 짰다. 매번 그 열의 최댓값이 봉우리인지 바로 확인할 수 있어서다.

### 봉우리 대신 골짜기를 찾으라면

양옆보다 작은 칸(지역 최솟값)은 부호만 뒤집으면 된다. `nums[mid] > nums[mid + 1]`이면 내리막이니 오른쪽으로 가면 골짜기가 있다. 배열 밖을 양의 무한대로 보는 조건도 같이 뒤집는다.

## 정렬이 없어도 버릴 절반은 있다

이분 탐색에 필요한 건 정렬이 아니라 "남긴 절반에 답이 반드시 있다"는 보장이다. 이 문제에서는 바로 옆 칸과 비교해 오르막이면 오른쪽, 내리막이면 mid를 포함한 왼쪽에 봉우리가 반드시 있고, 배열 밖이 음의 무한대라서 끝까지 올라가도 끝 칸이 봉우리가 된다. "아무 봉우리나"라는 약한 질문이 이 보장을 만들었다. 가장 높은 봉우리를 묻거나, 이웃끼리 같은 값을 허용하면 보장이 깨지고 O(n)으로 돌아간다.

## 면접에서 나올 만한 질문

### 정렬되지 않은 배열에서 왜 이분 탐색이 되나요?

이분 탐색에 필요한 건 정렬이 아니라 "남긴 절반에 답이 반드시 있다"는 보장이기 때문이다. `nums[mid] < nums[mid + 1]`이면 오른쪽으로 오르다 처음 내려가는 곳이나 마지막 칸이 봉우리라 오른쪽 절반에 봉우리가 있다. 반대면 같은 논리로 mid를 포함한 왼쪽에 있다. 매번 이 보장을 지키며 구간을 절반으로 줄이니 O(log n)이다.

### 왜 mid를 mid + 1과 비교하나요? 멀리 떨어진 두 점을 비교하면 안 되나요?

바로 옆 칸이라야 mid가 오르막 위인지 내리막 위인지가 정해지고, 그 방향으로 가면 봉우리가 있다는 논증이 성립한다. 멀리 떨어진 두 점 사이에는 봉우리와 골짜기가 여러 번 있을 수 있어서 어느 쪽에 봉우리가 있는지 알 수 없다. 그래서 삼분 탐색은 봉우리가 여럿인 배열에서 틀린다. 실제로 무작위 배열 2만 개 중 6~8개에서 봉우리가 아닌 칸을 돌려줬다.

### 가장 높은 봉우리를 찾으라면 어떻게 되나요?

O(n)보다 빠를 수 없다. 가장 큰 값은 어느 칸에든 있을 수 있어서 모든 칸을 봐야 확신할 수 있다. 이 문제가 O(log n)인 건 "아무 봉우리나"라는 약한 질문 덕분이고, 가장 큰 값의 자리가 봉우리라는 사실은 봉우리가 반드시 있다는 증명에만 쓴다.

### 이웃한 값이 같을 수 있다면 어떻게 되나요?

`nums[mid] === nums[mid + 1]`이면 어느 쪽에 봉우리가 있는지 알 수 없어 O(log n)이 깨진다. `[1, 1, 1, 2, 1, 1, 1]`에서 위 코드는 봉우리가 아닌 0번을 돌려준다. 평평한 바닥 어딘가에 봉우리 하나가 숨은 배열은 결국 칸을 다 봐야 하니 최악 O(n)이다.

### `while (lo < hi)`와 `hi = mid`를 쓰는 이유는 무엇인가요?

구간 `[lo, hi]`가 "봉우리가 반드시 있는 곳"이라 한 칸이 남으면 그게 답이고, 내리막일 때 mid 자신이 봉우리일 수 있어 mid를 남겨야 하기 때문이다. `lo < hi`이고 아래쪽 가운데를 쓰면 `mid + 1`이 항상 배열 안이고 `hi = mid`가 구간을 반드시 줄인다. `lo <= hi`나 위쪽 가운데를 쓰면 무한 루프에 빠진다.

### 자바로 칸마다 양옆을 비교할 때 조심할 점은 무엇인가요?

배열 밖의 음의 무한대를 `Integer.MIN_VALUE`로 흉내 내면, 값이 `int` 전체 범위라서 `[Integer.MIN_VALUE]` 같은 입력에서 봉우리를 못 찾는다. `long`으로 넓혀 `Long.MIN_VALUE`를 쓰거나, 이분 탐색처럼 배열 안의 값끼리만 비교하면 된다. 이분 탐색 풀이는 `mid + 1`이 항상 배열 안이라 이 문제가 없다.

### 2차원 격자에서 봉우리를 찾으려면 어떻게 하나요?

가운데 열에서 가장 큰 칸을 고르고, 그 칸을 좌우 이웃과 비교해 더 큰 쪽 절반의 열로 간다. 열 최댓값이라 위아래보다는 이미 크니 좌우만 보면 되고, 1차원의 "옆 칸과 비교" 논증이 열 단위로 그대로 성립한다. 열 하나를 훑는 O(m)을 log n번 하니 O(m log n)이다. 1901번이 이 문제다.
