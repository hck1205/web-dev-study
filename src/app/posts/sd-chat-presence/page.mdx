이 시리즈에서 이 글의 자리: 채팅 시스템 세 편의 마지막이다. [㉖ 채팅 시스템 ①: 연결](/posts/sd-chat-connections)에서 WebSocket과 상태 있는 채팅 서버를, [㉗ 채팅 시스템 ②: 메시지 저장과 기기 동기화](/posts/sd-chat-message-storage)에서 메시지 번호와 기기별 커서를 정했다. 이 글은 친구 이름 옆 초록 점, 접속 상태를 다룬다. 다음 글은 [㉙ 검색어 자동완성 ①](/posts/sd-autocomplete-trie)이다.

친구 목록에서 준호 이름 옆에 초록 점이 떠 있다. 메시지를 보냈는데 10분째 읽지 않는다. 알고 보니 준호는 지하철에서 휴대폰이 터널에 들어간 뒤로 앱을 보지도 않았다. 반대로 서연은 접속해 있는데도 점이 켜졌다 꺼졌다를 반복한다. 접속 상태는 기능 목록에서 한 줄짜리지만, 틀리게 보이면 사용자가 바로 알아챈다.

이 글은 "연결이 있으면 온라인"이라는 가장 단순한 규칙에서 출발한다. 그 규칙이 어디서 틀리는지 보고, 하트비트로 고치고, 바뀐 상태를 친구들에게 알리는 비용을 계산한다.

## 연결이 있으면 온라인이라는 규칙

앞 글들에서 채팅 앱은 켜져 있는 동안 채팅 서버와 WebSocket 연결을 하나 유지한다. 그러면 접속 상태도 쉽게 만들 수 있을 것 같다. 연결이 열리면 온라인으로 적고, 닫히면 오프라인으로 적는다. 앱이 정상적으로 닫히면 이 규칙은 정확하다. 문제는 연결이 정상적으로 닫히지 않는 경우다.

첫째, 죽은 연결은 스스로 알려 주지 않는다. 휴대폰이 터널에 들어가거나 와이파이에서 LTE로 넘어가면 TCP 연결의 한쪽이 그냥 사라진다. 끊겼다는 신호(FIN이나 RST)를 보낼 기회가 없었으니 서버는 그 연결이 아직 살아 있다고 믿는다. 소켓에 TCP keepalive를 켜 두면 운영체제가 결국 알아채지만, 리눅스 기본값(`tcp_keepalive_time` 7200초)으로는 연결이 2시간 동안 조용해야 확인을 시작한다. 그동안 준호는 초록 점이다.

둘째, 모바일 네트워크는 자주 잠깐씩 끊긴다. 엘리베이터에서 3초 끊겼다가 다시 붙을 때마다 오프라인과 온라인을 오가면, 친구들 화면에서 점이 깜빡이고 그때마다 상태 변경 알림이 친구 수만큼 퍼진다.

셋째, 기기가 여러 대다. 휴대폰을 닫아도 노트북이 켜져 있으면 온라인이어야 한다. 연결 하나가 닫혔다고 사람을 오프라인으로 만들면 안 된다.

## 살아 있다고 주기적으로 알리기

해결책은 앱이 "나 아직 여기 있다"는 짧은 신호를 일정한 간격으로 보내는 것이다. 이 신호를 하트비트(heartbeat)라고 한다. 서버는 사람마다 마지막 하트비트 시각을 적어 두고, 정해 둔 시간 동안 하트비트가 없으면 오프라인으로 바꾼다. 연결이 닫히는 신호가 오면 기다리지 않고 바로 오프라인으로 바꾼다.

Node로 접속 상태 서버를 만들어 네 사람을 붙였다. 기다리기 지루하니 실제로 흔히 쓰는 5초 간격, 30초 기준을 1초와 3초로 줄였다. 서버는 250ms마다 마지막 하트비트가 3초를 넘은 사람을 찾는다.

```js
// presence.mjs 일부: 하트비트가 오면 시각을 갱신하고, 연결이 닫히면 바로, 조용하면 기준 시간 뒤에 오프라인
ws.on("message", () => { last.set(user, Date.now()); set(user, "online", "하트비트"); });
ws.on("close", () => { last.delete(user); set(user, "offline", "연결 종료"); });
setInterval(() => {
  for (const [user, t] of last) if (Date.now() - t > TIMEOUT_MS) set(user, "offline", `${((Date.now() - t) / 1000).toFixed(1)}초 동안 하트비트 없음`);
}, 250);

client("minji", {});                                          // 계속 보낸다
client("junho", { mute: (ms) => ms > 2000 });                 // 2초부터 아무것도 못 보낸다 (연결은 열린 채)
client("seoyeon", { closeAt: 3000 });                         // 3초에 앱을 닫는다
client("doyun", { mute: (ms) => ms > 1500 && ms < 2600 });    // 하트비트 하나를 놓치고 돌아온다
```

```text
 0.1s  minji   → online  (연결)
 0.1s  junho   → online  (연결)
 0.1s  seoyeon → online  (연결)
 0.1s  doyun   → online  (연결)
 3.1s  seoyeon → offline (연결 종료)
 4.3s  junho   → offline (3.2초 동안 하트비트 없음)
 7.1s  최종: {"minji":"online","junho":"offline","seoyeon":"offline","doyun":"online"}
```

서연은 앱을 닫는 순간 바로 오프라인이 됐다. 준호는 연결이 열린 채 신호만 끊겼는데, 마지막 하트비트가 1.1초였으니 3초가 지난 4.3초에 오프라인이 됐다. 도윤은 하트비트를 하나 놓쳤지만 기준 시간 안에 다시 보냈기 때문에 한 번도 오프라인이 되지 않았다. 잠깐 끊긴 사람을 오프라인으로 만들지 않는 것, 이것이 기준 시간을 간격보다 길게 잡는 이유다.

하트비트는 따로 HTTP 요청을 만들 필요가 없다. 이미 열려 있는 채팅 WebSocket 연결로 작은 메시지를 보내면 된다. WebSocket 규약의 ping, pong 프레임을 하트비트로 쓰기도 하는데, 이 경우 서버가 보낸 ping에 브라우저가 자동으로 pong을 돌려준다. 다만 그건 "연결이 살아 있다"는 뜻이지 "사용자가 앱을 보고 있다"는 뜻은 아니다. 연결 수준의 생존 확인은 [WebSocket 깊게 보기](/posts/websocket-deep-dive)에서 다뤘다.

## 간격과 기준 시간을 고르는 법

간격을 짧게 잡으면 상태가 정확해지지만 비용이 커진다. 동시 접속 200만 명이 5초마다 보내면 초당 40만 개, 30초마다면 약 6만 7천 개다. 모바일에서는 배터리도 문제다. 휴대폰 무선 모듈은 데이터를 보낼 때마다 잠깐 깨어나서 전력을 쓰니, 짧은 간격의 하트비트는 배터리를 갉아먹는다.

기준 시간은 보통 간격의 몇 배로 잡는다. 하트비트 하나쯤은 늦거나 빠질 수 있으니 간격과 같게 잡으면 잠깐의 지연에도 오프라인이 된다. 간격 5초에 기준 30초면 여섯 번 연속 빠져야 오프라인이다. 대신 실제로 떠난 사람이 최대 30초 동안 온라인으로 보인다. 정확도와 깜빡임 사이에서 고르는 값이다.

모바일 운영체제도 고려해야 한다. iOS는 앱이 백그라운드로 가면 곧 실행을 멈추고, 안드로이드도 절전 상태에서 네트워크 사용을 제한한다. 그래서 앱은 백그라운드로 갈 때 "자리 비움"이나 오프라인을 직접 알리고 연결을 닫는 경우가 많다. 하트비트 기준 시간은 이렇게 알릴 틈도 없이 사라진 경우를 위한 마지막 그물이다.

## 상태를 어디에 적어 두나

접속 상태는 사람마다 `{ status, last_active_at }` 정도의 작은 값이다. 자주 바뀌고, 잃어도 하트비트가 금방 다시 채우니 오래 보관할 필요가 없다. 그래서 디스크 DB보다 Redis 같은 메모리 키-값 저장소에 둔다. 만료 시간(TTL)을 쓰면 "기준 시간 동안 하트비트가 없으면 오프라인"을 저장소가 대신해 준다. 하트비트마다 키를 다시 쓰면서 만료 시간을 30초로 되돌리고, 하트비트가 끊기면 키가 저절로 사라진다.

따로 띄운 Redis(포트 6391)에서 기준 시간을 3초로 줄여 확인했다. 키가 만료될 때 알림을 받도록 키스페이스 알림을 켜고, 다른 창에서 만료 이벤트를 구독해 뒀다.

```bash
# 만료(expired) 이벤트를 알림으로 내보내게 한다 (이 실험용 인스턴스에서만)
redis-cli -p 6391 CONFIG SET notify-keyspace-events Ex
# 다른 창에서: 만료된 키 이름을 받아 본다
redis-cli -p 6391 SUBSCRIBE __keyevent@0__:expired
# 하트비트가 올 때마다 하는 일: 키를 쓰고 만료를 3초로 되돌린다
redis-cli -p 6391 SET presence:junho online EX 3
```

```text
127.0.0.1:6391> CONFIG SET notify-keyspace-events Ex
OK
127.0.0.1:6391> SET presence:junho online EX 3
OK
127.0.0.1:6391> TTL presence:junho
(integer) 3
```

4초 뒤에 다시 읽으면 키가 없고, 구독하던 창에는 만료된 키 이름이 왔다.

```text
127.0.0.1:6391> GET presence:junho
(nil)
```

```text
1) "message"
2) "__keyevent@0__:expired"
3) "presence:junho"
```

편하지만 두 가지를 알고 써야 한다. Redis는 만료된 키를 누군가 읽거나 백그라운드 정리가 그 키를 찾을 때 지우고, 만료 알림도 그때 나온다. 그래서 TTL이 0이 된 순간과 알림 사이에 지연이 생길 수 있다. 그리고 PUB/SUB 알림은 그 순간 구독 중인 쪽에만 가니, 구독하던 서버가 재시작하는 사이 만료된 사람은 알림 없이 사라진다. 접속 상태 정도면 감당할 오차지만, 만료 알림만 믿고 "오프라인 처리 후 정산" 같은 중요한 일을 걸면 안 된다.

쓰기 양도 줄일 수 있다. 하트비트는 채팅 서버가 받으니, 채팅 서버가 메모리에 마지막 시각을 들고 있다가 상태가 바뀔 때와 일정 주기에만 Redis에 쓴다. 200만 명의 5초 하트비트를 그대로 쓰면 초당 40만 번이지만, 15초마다 한 번 TTL을 갱신하면 약 13만 번이다.

## 친구들에게 바뀐 상태 알리기

준호가 오프라인이 되면 준호를 친구로 둔 사람들의 화면에서 점이 꺼져야 한다. 방법은 [발행·구독](/posts/pub-sub)이다. 사람마다 `presence:준호` 같은 채널을 하나 두고, 준호의 상태가 바뀌면 그 채널에 발행한다. 민지가 접속하면 민지가 붙은 채팅 서버가 민지 친구들의 채널을 구독하고, 받은 알림을 민지의 WebSocket으로 내려보낸다.

Redis에서 `PUBLISH`는 그 채널을 지금 구독 중인 연결 수를 돌려준다. 민지 채널에 구독자 둘을 붙여 두고 발행했다.

```text
127.0.0.1:6391> PUBLISH presence:minji online
(integer) 2
127.0.0.1:6391> PUBLISH presence:doyun online
(integer) 0
```

`presence:minji`는 두 곳이 받았고, 아무도 구독하지 않은 `presence:doyun`은 0이다. 0이 나왔다고 실패가 아니다. 도윤의 친구 중 지금 접속한 사람이 없을 뿐이다. 오프라인 친구에게는 보낼 필요가 없으니, 구독은 접속한 사람의 서버만 하는 게 맞다.

채널을 사람마다 하나 두는 대신 친구 쌍마다 하나씩 두는 설계도 있다. 준호와 민지 사이에 채널 하나, 준호와 서연 사이에 또 하나. 친구 관계마다 공개 범위를 다르게 하기 쉽지만 채널 수가 친구 관계 수만큼 늘어난다. 어느 쪽이든 상태 하나가 바뀌면 접속 중인 친구 수만큼 알림이 나간다는 점은 같다.

## 친구가 5,000명이거나 방이 10만 명이면

이 팬아웃은 친구 수에 비례한다. 접속 200만 명이 시간당 네 번 상태가 바뀌고, 친구 100명 중 20%가 접속해 있다면 초당 약 2,222번 바뀌고 알림은 약 44,444개다. 감당할 만하다. 하지만 평균 친구 수가 5,000명인 서비스라면 같은 계산으로 초당 220만 개가 넘는다. 회사 메신저의 10만 명 전체 공지 채널에서 멤버 모두의 접속 상태를 실시간으로 보여 주려 하면 한 사람이 들어올 때마다 10만 개다.

## 여러 기기와 마지막 접속 시각

기기가 여러 대면 사람의 상태는 기기 상태를 합친 값이다. 기기 하나라도 온라인이면 온라인이다. 그래서 상태 키를 사람마다 하나 두기보다 기기마다 하나씩 두고(`presence:junho:phone`, `presence:junho:laptop`), 사람의 상태는 남은 키가 하나라도 있는지로 정한다. 휴대폰 키가 만료돼도 노트북 키가 남아 있으면 친구들에게 아무것도 알리지 않는다. 상태가 실제로 바뀌는 건 마지막 기기 키가 사라질 때다.

## 접속 상태가 틀리게 보일 때

"모두 초록인데 아무도 답이 없다"면 오프라인 처리가 안 되고 있는 것이다. 채팅 서버가 연결 종료와 하트비트 기준 시간을 모두 처리하는지 본다. Redis를 쓴다면 상태 키에 만료가 붙어 있는지 `TTL presence:<id>`로 확인한다. `-1`이 나오면 만료 없이 영원히 남는 키다. `SET`할 때 `EX`를 빠뜨렸거나, 다른 코드가 `EX` 없이 덮어쓴 것이다.

"점이 깜빡깜빡한다"면 기준 시간이 하트비트 간격에 너무 가깝거나, 앱이 연결을 끊고 다시 붙을 때마다 연결 종료를 바로 오프라인으로 처리하는 것이다. 연결 종료 뒤에도 몇 초 기다렸다가, 그사이 같은 사람의 다른 연결이 붙지 않았을 때만 오프라인을 발행한다.

"배포할 때마다 모두 오프라인으로 보였다가 돌아온다"면 채팅 서버가 내려가며 끊긴 연결을 모두 오프라인으로 발행하고, 재연결 뒤 다시 온라인을 발행하는 것이다. 연결이 몰리는 순간 팬아웃이 두 배로 터진다. 서버를 내릴 때는 상태 발행을 멈추고 키의 만료에 맡기면, 기준 시간 안에 다른 서버로 다시 붙은 사람은 상태가 한 번도 바뀌지 않는다. 재연결 지터는 [㉖ 채팅 시스템 ①](/posts/sd-chat-connections)에서 다뤘다.

## 다음에 읽을 글

접속 상태는 연결이 닫혔다는 신호만으로 만들 수 없다. 죽은 연결은 말이 없고, 모바일 연결은 자주 잠깐 끊기기 때문이다. 앱이 몇 초마다 하트비트를 보내고, 기준 시간 동안 없으면 오프라인으로 본다. 상태는 만료가 붙은 메모리 키-값에 두고, 바뀔 때만 접속 중인 친구에게 발행한다. 친구나 멤버가 너무 많으면 보이는 사람만 구독하고 나머지는 열 때 가져온다.

이걸로 채팅 시스템 세 편이 끝났다. 연결을 붙잡는 서버, 방마다 번호를 매기는 저장소, 하트비트로 정하는 접속 상태가 한 앱 안에서 함께 돈다. 다음 장은 검색창에 글자를 칠 때마다 추천어를 보여 주는 [㉙ 검색어 자동완성 ①: 트라이](/posts/sd-autocomplete-trie)다. 친구 위치를 실시간으로 퍼뜨리는 [㊱ 주변 친구](/posts/sd-nearby-friends)도 이 글의 팬아웃 구조를 그대로 키운다.

## 면접에서 나올 만한 질문

### 접속 상태는 어떻게 판단하나요?

앱이 몇 초마다 하트비트를 보내고, 서버는 사람마다 마지막 하트비트 시각을 적어 둔다. 기준 시간 동안 하트비트가 없으면 오프라인으로 바꾸고, 연결이 정상적으로 닫히면 바로 오프라인으로 바꾼다. 연결 여부만 보면 터널에 들어가 사라진 연결을 한참 동안 온라인으로 보게 된다.

### 하트비트 간격과 기준 시간은 어떻게 정하나요?

간격은 정확도와 비용 사이에서 고른다. 짧으면 상태가 정확하지만 하트비트 양과 모바일 배터리 소모가 늘어난다. 기준 시간은 간격의 몇 배로 잡아 하트비트 한두 개가 빠져도 오프라인이 되지 않게 한다. 5초 간격에 30초 기준이면 잠깐 끊긴 사람은 깜빡이지 않고, 떠난 사람은 최대 30초 늦게 오프라인이 된다.

### 접속 상태는 어디에 저장하나요?

Redis 같은 메모리 키-값 저장소에 만료 시간을 붙여 둔다. 하트비트마다 만료를 되돌리면 하트비트가 끊길 때 키가 저절로 사라진다. 잃어도 하트비트가 금방 다시 채우는 값이라 디스크 DB에 오래 보관할 필요가 없다. 만료 알림은 지연되거나 구독자가 없을 때 사라질 수 있으니 중요한 처리에 쓰지 않는다.

### 바뀐 상태는 친구들에게 어떻게 알리나요?

사람마다 상태 채널을 두고, 접속한 사람의 채팅 서버가 그 사람 친구들의 채널을 구독한다. 상태가 바뀔 때만 발행하고 하트비트마다 발행하지 않는다. 구독자는 접속 중인 친구의 서버뿐이니 오프라인 친구에게는 아무것도 가지 않는다.

### 친구가 수천 명이거나 10만 명 방이면 어떻게 하나요?

상태 하나가 바뀔 때 알림이 접속 중인 친구 수만큼 나가니, 밀어 주기를 줄인다. 화면에 보이는 사람만 구독하고, 큰 방은 멤버 목록을 열 때 그 순간의 상태를 한 번에 가져온다. 같은 사람의 잦은 변경은 짧게 모아 마지막 값만 보낸다.

### 휴대폰은 닫고 노트북은 켜져 있으면요?

기기마다 상태 키를 따로 두고, 하나라도 남아 있으면 온라인으로 본다. 휴대폰 키가 만료돼도 노트북 키가 있으면 친구들에게 아무것도 알리지 않는다. 사람의 상태가 바뀌는 건 마지막 기기 키가 사라질 때다.

### 채팅 서버를 배포할 때 모두 오프라인으로 깜빡인다면요?

내려가는 서버가 끊긴 연결마다 오프라인을 발행하고, 재연결 뒤 다시 온라인을 발행해서 생긴다. 서버를 내릴 때는 상태 발행을 멈추고 상태 키의 만료에 맡긴다. 기준 시간 안에 다른 서버로 다시 붙은 사람은 키가 갱신되니 상태가 한 번도 바뀌지 않는다. 재연결에 지터를 넣어 몰림도 줄인다.

### 접속자가 10배가 되면 어디부터 손대나요?

하트비트 양이 먼저 커지니 채팅 서버가 마지막 시각을 메모리에 들고 있다가 상태가 바뀔 때와 일정 주기에만 저장소에 쓰게 한다. 상태 저장소와 발행·구독 채널은 사용자 ID로 샤딩한다. 팬아웃은 구독 대상을 화면에 보이는 사람으로 줄이고, 하트비트 간격을 늘리는 것도 선택지다.
