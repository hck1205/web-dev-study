## 13px, 15px, 18px가 섞인 화면

설정 화면 하나의 CSS를 열었다. 카드 안쪽 여백이 15px, 제목 아래가 13px, 목록 사이가 18px, 버튼 위가 20px이다. 다른 화면의 같은 카드는 안쪽 여백이 16px이다. 누가 틀린 것도 아니다. 각자 디자인 파일을 재서 가장 가까워 보이는 숫자를 넣었다. 그런데 화면을 나란히 놓으면 미묘하게 어긋나 보이고, 리뷰 때마다 "여기 2px 더 띄워 주세요"가 반복된다.

이걸 숫자 체계로 바꾸는 게 이 글의 주제다. 기본 단위를 정하고, 그 위에 간격과 크기와 글자 단계를 쌓고, 줄 높이와 아이콘까지 같은 단위에 맞춘다. 토큰을 기본값, 의미, 컴포넌트 세 층으로 나누는 구조는 [디자인 시스템 만들기](/posts/design-system-building)에, rem과 단위 없는 `line-height`처럼 글자 CSS 자체는 [CSS 글자 다루기](/posts/css-typography)에, `clamp()` 공식을 두 점에서 끌어내는 과정은 [반응형 디자인](/posts/responsive-design#글자-크기를-clamp로-부드럽게)에 있으니, 여기서는 그 위에서 "어떤 숫자를 고르나"에 답한다.

## 기본 단위 하나를 정한다: 4pt와 8pt

체계의 출발점은 기본 단위 하나다. 거의 모든 디자인 시스템이 4 또는 8을 고른다. 디자인 도구에서 pt라고 부르지만 웹에서는 CSS 픽셀로 보면 된다.

왜 하필 4와 8일까. 첫째, 나누기 쉽다. 8은 반으로, 다시 반으로 나눠도 정수(4, 2)가 남는다. 10을 고르면 반은 5, 그 반은 2.5가 된다. 둘째, 화면 밀도와 잘 맞는다. 기기 픽셀 비율(DPR)이 1.5인 화면에서 8px은 기기 픽셀 12개로 딱 떨어지지만 5px은 7.5개가 되어 경계가 픽셀 중간에 걸린다. 테두리나 구분선이 흐릿하게 번지는 원인이 이것이다. 2배, 3배 화면에서는 어떤 정수도 정수로 떨어지니, 1.5배 같은 애매한 비율에서 4의 배수가 특히 안전하다.

8을 기본으로 하되 4를 반 단위로 허용하는 방식이 가장 흔하다. 큰 여백은 8의 배수로, 아이콘과 글자 사이처럼 촘촘한 곳은 4로 맞춘다. 처음 사례의 15px은 16px로, 13px은 12px로, 18px은 16px이나 20px으로 옮긴다. 어느 쪽으로 옮길지 고민될 때는 같은 화면의 다른 간격과의 관계를 본다. 이 이야기는 아래에서 다시 한다.

## 간격 스케일은 점점 벌어진다

기본 단위를 정했다고 모든 배수를 쓰면 4, 8, 12, 16, 20, 24, 28, 32… 고를 것이 너무 많아서 다시 13px과 15px의 고민으로 돌아간다. 그래서 쓸 값만 골라 스케일을 만든다.

```css
:root {
  /* 기본 단위 0.25rem(4px). 작은 쪽은 촘촘하게, 큰 쪽은 성글게 */
  --space-1: 0.25rem; /*  4px */
  --space-2: 0.5rem;  /*  8px */
  --space-3: 0.75rem; /* 12px */
  --space-4: 1rem;    /* 16px */
  --space-6: 1.5rem;  /* 24px */
  --space-8: 2rem;    /* 32px */
  --space-12: 3rem;   /* 48px */
  --space-16: 4rem;   /* 64px */
}
```

작은 값은 4px 간격으로 촘촘하고, 큰 값은 16px씩 성글게 벌어진다. 사람 눈은 차이를 비율로 느끼기 때문이다. 4px과 8px은 두 배 차이라 확실히 다르게 보이지만, 56px과 60px은 7% 차이라 거의 같아 보인다. 큰 쪽에 촘촘한 값을 두면 쓰는 사람만 헷갈린다.

이름은 두 가지 방식이 있다. 위처럼 숫자가 단위의 배수를 뜻하게 하면(`--space-4`는 4 × 4px) 값을 외우기 쉽고, 사이에 새 값을 끼워 넣어도 이름이 꼬이지 않는다. Tailwind CSS v4가 이 방식으로 `--spacing: 0.25rem` 하나를 두고 `p-4`를 그 네 배로 계산한다. `xs`, `sm`, `md`처럼 옷 치수 이름은 읽기 쉽지만 `sm`과 `md` 사이에 하나를 넣으려면 `smd` 같은 이름을 지어야 한다.

그리고 이 기본값 위에 의미 토큰을 얹는다. `--space-inset-card: var(--space-4)`, `--space-stack-section: var(--space-12)` 같은 이름이다. 그러면 "카드 안쪽 여백을 모두 20px로 바꾸자"는 결정이 왔을 때 숫자를 찾아 바꾸는 대신 의미 토큰 하나만 고친다.

## 안쪽 여백은 바깥 여백보다 작게

스케일이 있어도 어느 값을 어디에 쓸지는 관계로 정한다. 가장 쓸모 있는 규칙은 "안쪽 여백은 바깥 여백보다 작거나 같다"다. 카드 안의 제목과 본문 사이가 16px인데 카드와 카드 사이가 12px이면, 눈은 카드 경계보다 간격을 먼저 읽어서 위 카드의 본문과 아래 카드의 제목을 한 덩어리로 본다. 가까운 것끼리 묶어 보는 근접성 원리 때문이다.

그래서 간격은 위계를 따라 커진다. 글자와 아이콘 사이 4~8px, 한 항목 안의 줄 사이 8px, 항목 사이 16px, 묶음 사이 24~32px, 섹션 사이 48~64px. 처음 사례에서 제목 아래 13px과 목록 사이 18px을 어디로 옮길지도 이걸로 정해진다. 제목과 그 아래 목록은 한 묶음이니 제목 아래는 목록 항목 사이보다 작거나 같아야 한다. 그러면 제목 아래 12px, 목록 사이 16px이 된다.

레이아웃 그리드도 같은 단위를 쓴다. 열 사이 간격(gutter)과 화면 가장자리 여백(margin)을 간격 스케일에서 고른다. 모바일 4열에 16px, 태블릿 8열에 24px, 데스크톱 12열에 24~32px 같은 조합이 흔하다. CSS Grid의 `gap`에 같은 토큰을 넣으면 그리드 간격과 컴포넌트 간격이 자연스럽게 맞는다.

## 컴포넌트 크기와 손가락이 누를 자리

간격과 별도로 크기 토큰을 둔다. 버튼, 입력칸, 선택 상자처럼 한 줄에 나란히 서는 컨트롤은 높이를 같은 단계에서 고른다.

```css
:root {
  --size-control-sm: 2rem;   /* 32px: 표 안, 밀도 높은 도구 화면 */
  --size-control-md: 2.5rem; /* 40px: 데스크톱 기본 */
  --size-control-lg: 3rem;   /* 48px: 모바일 기본 */
  --size-icon-sm: 1rem;      /* 16px */
  --size-icon-md: 1.25rem;   /* 20px */
  --size-icon-lg: 1.5rem;    /* 24px */
}
```

입력칸 40px 옆에 버튼 38px이 서 있으면 2px 차이가 바로 보인다. 크기를 토큰으로 묶으면 검색창과 검색 버튼, 필터 선택 상자가 같은 단계로 맞춰진다.

모바일에서는 손가락이 기준이다. 애플의 휴먼 인터페이스 가이드라인은 44 × 44pt를, 머티리얼 디자인은 48 × 48dp를 터치 대상의 최소로 권한다. WCAG 2.2의 2.5.8(최소 대상 크기, AA)은 24 × 24 CSS 픽셀이거나 그만큼 떨어져 있으면 통과로 보고, 2.5.5(AAA)는 44 × 44를 요구한다. AA 기준은 넘기 쉬운 바닥일 뿐이라, 실제 모바일 화면은 44~48px을 목표로 잡는다.

아이콘 버튼처럼 겉모양은 작아야 하는 경우에는 보이는 크기와 누르는 크기를 나눈다.

```css
.icon-button {
  position: relative;
  inline-size: var(--size-icon-lg); /* 보이는 크기 24px */
  block-size: var(--size-icon-lg);
}
.icon-button::after {
  content: "";
  position: absolute;
  inset: -10px; /* 사방으로 10px씩 넓혀 누르는 영역을 44px로 */
}
```

가상 요소로 넓힌 영역도 클릭과 터치를 받는다. 다만 옆 버튼과 넓힌 영역이 겹치면 엉뚱한 쪽이 눌리니, 버튼 사이 간격도 같이 확인한다.

## 글자 크기를 비율의 계단으로

글자 크기도 간격처럼 고를 값을 정해 둔다. 모듈러 타입 스케일(modular type scale)은 기본 크기에 같은 비율을 거듭 곱해 단계를 만든다. 기본 16px, 비율 1.25라면 16 × 1.25 = 20, 20 × 1.25 = 25, 25 × 1.25 = 31.25… 식이다. 비율마다 음악 음정 이름이 붙어 있다. 1.2는 단3도, 1.25는 장3도, 1.333은 완전4도다.

두 비율로 계산하면 이렇다(소수 둘째 자리).

```text
단계     -1      0      1      2      3      4      5
1.2    13.33  16.00  19.20  23.04  27.65  33.18  39.81
1.25   12.80  16.00  20.00  25.00  31.25  39.06  48.83
```

비율이 작으면 단계 사이 차이가 작아서 제목 단계를 여러 개 둬도 화면이 차분하다. 글이 길고 제목 위계가 깊은 문서, 정보가 빽빽한 도구 화면에 맞다. 비율이 크면 단계가 금방 커져서 5단계 만에 49px에 이른다. 제목이 몇 개 없고 큰 제목으로 시선을 끄는 화면에 맞다. 모바일은 화면이 좁아 큰 비율의 제목이 두세 줄로 넘어가기 쉬우니 작은 비율을 쓰고, 넓은 화면에서 비율을 키우는 방법이 아래에 나온다.

계산값은 반올림해서 쓴다. 27.65px을 그대로 쓰면 브라우저가 소수 픽셀로 그려 글자마다 미세하게 흐려질 수 있고, 무엇보다 사람이 기억하기 어렵다. 그리고 스케일은 출발점일 뿐이다. 계산된 값이 실제 글꼴에서 너무 붙어 보이면 한 단계를 빼거나 손으로 고친다.

## 줄 높이를 그리드에 붙인다

글자 크기를 정하면 줄 높이(line-height)가 따라온다. 본문은 글자 크기의 1.5배 안팎, 큰 제목은 1.2~1.25배가 보통이다. 제목은 글자가 커서 같은 비율이면 줄 사이가 너무 벌어져 보이기 때문이다.

여기서 줄 높이를 4px의 배수로 맞추면 글이 몇 줄이 되든 블록 높이가 그리드에 떨어진다. 16px 본문에 1.5배면 24px로 이미 4의 배수다. 20px 글자에 1.5배면 30px인데, 가까운 4의 배수인 32px으로 올린다. 아래 그림은 1.2 비율 스케일을 따라가며 각 단계의 줄 높이를 4px에 맞춘다. 24px 이상은 1.25배, 그 아래는 1.5배를 쓴다.

마지막 단계가 보여 주듯 규칙으로 뽑은 값도 결국 눈으로 다듬는다. 직접 규칙을 바꿔 가며 표를 뽑아 보자. 아래 함수는 기본 크기, 비율, 단계 범위, 그리드 단위를 받아 각 단계의 반올림한 글자 크기와 그리드에 맞춘 줄 높이를 돌려준다.

  // lineHeight = size × 비율을 grid 배수로 반올림
  // [{ step, size, lineHeight }] 를 돌려준다

  solution={`function typeScale(base, ratio, from, to, grid) {
  const out = [];
  for (let n = from; n <= to; n++) {
    const size = Math.round(base * Math.pow(ratio, n));
    const lhRatio = size >= 24 ? 1.25 : 1.5;
    const lineHeight = Math.round((size * lhRatio) / grid) * grid;
    out.push({ step: n, size, lineHeight });
  }
  return out;
}`}
  tests={[
    {
      label: "16px, 1.2, -1~5단계, 4px",
      args: [16, 1.2, -1, 5, 4],
      expected: [
        { step: -1, size: 13, lineHeight: 20 },
        { step: 0, size: 16, lineHeight: 24 },
        { step: 1, size: 19, lineHeight: 28 },
        { step: 2, size: 23, lineHeight: 36 },
        { step: 3, size: 28, lineHeight: 36 },
        { step: 4, size: 33, lineHeight: 40 },
        { step: 5, size: 40, lineHeight: 52 },
      ],
    },
    {
      label: "16px, 1.25, -1~5단계, 4px",
      args: [16, 1.25, -1, 5, 4],
      expected: [
        { step: -1, size: 13, lineHeight: 20 },
        { step: 0, size: 16, lineHeight: 24 },
        { step: 1, size: 20, lineHeight: 32 },
        { step: 2, size: 25, lineHeight: 32 },
        { step: 3, size: 31, lineHeight: 40 },
        { step: 4, size: 39, lineHeight: 48 },
        { step: 5, size: 49, lineHeight: 60 },
      ],
    },
    {
      label: "8px 그리드로 맞추면",
      args: [16, 1.25, 0, 2, 8],
      expected: [
        { step: 0, size: 16, lineHeight: 24 },
        { step: 1, size: 20, lineHeight: 32 },
        { step: 2, size: 25, lineHeight: 32 },
      ],
    },
  ]}
/>

8px 그리드로 줄 높이를 맞추면 20px 글자와 25px 글자가 모두 32px이 된다. 8은 작은 글자에서 너무 거칠다. 그래서 간격은 8 기준이라도 줄 높이는 4 기준으로 맞추는 시스템이 많다.

CSS로 직접 맞출 수도 있다. `round()` 함수는 값을 정한 단위의 배수로 반올림한다.

```css
p {
  /* 글자 크기의 1.5배를 4px 배수로 올린다 */
  line-height: round(up, 1.5em, 4px);
}
```

`round()`는 크롬 125, 파이어폭스 118, 사파리 15.4부터 지원한다. 지원하지 않는 브라우저는 선언 전체를 무시하니, 앞줄에 `line-height: 1.5`를 먼저 써 두면 그쪽으로 떨어진다. 다만 토큰으로 크기와 줄 높이를 짝지어 두면 이 함수 없이도 같은 결과가 나온다.

줄 높이를 그리드에 맞춰도 글자의 눈에 보이는 윗선과 아랫선은 줄 상자 안에서 위아래로 남는 여백(half-leading) 때문에 그리드에 붙지 않는다. 버튼 안 글자가 살짝 아래로 처져 보이는 것도 글꼴의 위아래 여백이 다르기 때문이다. `text-box: trim-both cap alphabetic`은 이 여백을 잘라 대문자 윗선과 기준선에 맞춘다. 크롬 133, 사파리 18.2부터 들어왔고 파이어폭스는 지원 여부를 확인해야 해서, 아직은 보조 수단으로 쓴다.

## 아이콘 상자를 줄 높이에 맞춘다

아이콘은 그림 자체보다 바깥 상자가 중요하다. 머티리얼 아이콘은 24px 상자 안에 실제 그림이 들어가는 영역을 20px로 두고 사방 2px을 비운다. 그래서 모든 아이콘이 같은 상자 크기로 정렬되고, 원처럼 꽉 찬 모양과 가는 화살표처럼 얇은 모양이 시각적으로 비슷한 무게를 갖는다.

글자 옆 아이콘은 아이콘 상자 높이를 그 글자의 줄 높이와 같게 두면 계산이 끝난다. 14px 글자에 줄 높이 20px이면 아이콘 상자도 20px으로 두고 그 안에 16px 아이콘을 놓는다. 위아래로 2px씩 남아서 글자 줄과 가운데가 맞는다. 16px 본문에 줄 높이 24px이면 24px 상자에 20px 아이콘이다.

```css
.label {
  display: inline-flex;
  align-items: center;      /* 아이콘 상자와 글자 줄 상자를 가운데로 */
  gap: var(--space-1);      /* 아이콘과 글자 사이 4px */
  font-size: 0.875rem;      /* 14px */
  line-height: 1.25rem;     /* 20px */
}
.label svg {
  inline-size: 1rem;        /* 그림 16px */
  block-size: 1rem;
  margin-block: 0.125rem;   /* 위아래 2px, 상자 20px */
}
```

`inline-flex` 없이 `img`나 `svg`를 글자 사이에 그냥 두면 기본 `vertical-align: baseline` 때문에 아이콘 아래가 기준선에 붙어서 위로 떠 보인다. 기준선 아래 글자 꼬리(g, y) 자리만큼 아래가 비기 때문이다. 버튼 높이도 같은 방식으로 계산한다. 40px 버튼에 20px 줄 높이면 위아래 안쪽 여백은 10px이다.

## 화면 폭에 따라 스케일 자체를 바꾼다

모바일에서는 1.2, 데스크톱에서는 1.25가 어울린다면 두 스케일을 브레이크포인트에서 갈아 끼울 수도 있지만, 그러면 경계에서 제목이 툭 바뀐다. 대신 각 단계를 "작은 화면 값"과 "큰 화면 값" 두 점으로 정하고 그 사이를 `clamp()`로 잇는다. 두 점에서 `clamp()`를 만드는 공식은 [반응형 디자인](/posts/responsive-design#글자-크기를-clamp로-부드럽게)에 정리했다.

390px에서 기본 16px·비율 1.2, 1280px에서 기본 18px·비율 1.25로 정하고 각 단계를 계산하면 이렇다.

```text
단계   390px    1280px   clamp()
0      16.00    18.00    clamp(1rem, 0.9452rem + 0.2247vw, 1.125rem)
2      23.04    28.13    clamp(1.44rem, 1.3007rem + 0.5713vw, 1.7578rem)
5      39.81    54.93    clamp(2.4883rem, 2.0743rem + 1.6987vw, 3.4332rem)
```

820px 태블릿에서 계산하면 본문은 16.97px, 5단계 제목은 47.12px이다. 본문은 2px만 움직이고 큰 제목은 15px 넘게 움직인다. 큰 단계일수록 많이 변하는 게 이 방식의 핵심이고, 그래서 넓은 화면에서 위계가 더 또렷해진다.

간격도 같은 방식으로 쌍을 만든다. `--space-section`을 390px에서 24px, 1280px에서 40px으로 잡으면 `clamp(1.5rem, 1.0618rem + 1.7978vw, 2.5rem)`이 된다. 다만 모든 간격을 유동으로 만들 필요는 없다. 버튼 안쪽 여백이나 아이콘과 글자 사이처럼 컴포넌트 안의 간격은 고정값이 낫다. 화면 폭에 따라 버튼 모양이 달라지면 오히려 이상하다. 유동 간격은 섹션 사이, 페이지 가장자리처럼 레이아웃 층에만 쓴다.

## 브레이크포인트 토큰은 따로 둔다

간격과 글자 토큰은 CSS 변수로 두면 되지만, 브레이크포인트는 그렇게 안 된다. 미디어 쿼리 조건에는 CSS 변수를 쓸 수 없다. `@media (min-width: var(--bp-tablet))`은 동작하지 않는다. 변수는 요소에 붙는 값인데, 미디어 쿼리는 요소와 상관없이 문서 전체에서 판단하기 때문이다.

Media Queries Level 5 명세의 `@custom-media`가 이 문제를 풀려고 만들어졌지만, 아직 주요 브라우저에서 기본으로 쓸 수 있는 상태가 아니라 PostCSS 플러그인으로 빌드 때 펼쳐 쓴다. CSS-in-JS를 쓴다면 브레이크포인트를 TypeScript 상수로 두고 미디어 쿼리 문자열을 만들어 내보내는 게 가장 단순하다.

```ts
// breakpoints.ts: 브레이크포인트는 빌드 때 문자열이 되는 상수로 둔다
const bp = { tablet: 768, desktop: 1024 } as const;

export const media = {
  tablet: `@media (min-width: ${bp.tablet}px)`,
  desktop: `@media (min-width: ${bp.desktop}px)`,
};
```

브레이크포인트 개수는 적을수록 좋다. 유동 글자와 간격, 그리고 컴포넌트가 자기 자리 폭에 반응하는 컨테이너 쿼리를 쓰면, 화면 폭 브레이크포인트는 레이아웃의 열 수가 바뀌는 두세 곳이면 충분하다.

## 한 줄에 몇 글자가 들어가나

글자 크기와 간격을 다 정해도 한 줄이 너무 길면 읽기 어렵다. 줄 끝에서 다음 줄 처음으로 눈을 옮길 때 줄을 놓치기 때문이다. 영문 타이포그래피에서는 한 줄 45~75자를 편한 범위로 보고 66자 안팎을 이상적인 값으로 자주 든다.

CSS에서는 `max-width`를 `ch`로 막는다. `ch`는 그 글꼴의 숫자 0의 폭이다. 영문 소문자 평균 폭과 비슷해서 `max-width: 65ch`면 영문 기준 대략 65자 안팎이 된다. 한글은 사정이 다르다. 한글 글자는 대개 0보다 넓어서 1em에 가까운 폭을 차지하니, 같은 `65ch` 안에 들어가는 한글은 그보다 훨씬 적다. 한글 본문은 `em`이나 `rem`으로 폭을 잡고 실제 글꼴로 한 줄 글자 수를 세어 확인하는 편이 정확하다. 16px 본문이라면 40~45rem 폭에 한 줄 40자 안팎이 들어간다. 이 블로그의 본문 폭(44rem)도 이 근처다.

줄 길이와 줄 높이는 함께 움직인다. 줄이 길수록 다음 줄을 찾기 어려우니 줄 높이를 조금 키우고, 줄이 짧은 모바일 카드에서는 줄 높이를 조금 줄여도 된다. 본문 색 대비, 굵기, 문단 사이 간격(보통 줄 높이 하나 정도)도 가독성에 함께 영향을 준다.

## 있는 코드를 스케일로 옮기는 순서

처음 사례의 화면을 실제로 옮긴다면 숫자부터 모은다. 여백 속성에 직접 쓴 px 값을 세어 본다.

```bash
# margin·padding·gap에 직접 쓴 px 값(단축 속성은 첫 값만)을 세기
grep -rhoE '(margin|padding|gap)[a-z-]*: *[0-9]+px' src | grep -oE '[0-9]+px' | sort -n | uniq -c
```

설정 화면 CSS 한 파일에서 돌린 결과다.

```text
      1 2px
      1 8px
      1 12px
      2 13px
      1 15px
      1 16px
      1 18px
      1 20px
```

여덟 가지 값 중 13px, 15px, 18px은 스케일에 없다. 각각을 가장 가까운 단계로 그냥 옮기지 말고, 앞에서 본 관계 규칙으로 정한다. 제목 아래 13px은 묶음 안 간격이라 12px, 카드 안쪽 15px은 16px, 목록 사이 18px은 항목 사이라 16px이다. 2px은 배지 안쪽처럼 아주 촘촘한 곳이라 예외로 남기거나 4px으로 올린다. 이 정규식은 `padding: 2px 6px` 같은 단축 속성에서 첫 값만 잡으니, 정확히 세려면 CSS 파서를 쓰는 편이 낫다.

옮긴 뒤에는 다시 늘지 않게 막는다. stylelint의 `declaration-property-value-allowed-list` 규칙으로 여백 속성에는 토큰 변수와 0만 허용하게 하면, 새 코드에 15px이 들어오는 순간 린트가 잡는다. 이 경고 수를 매달 세어 지표로 보는 방법은 [디자인 시스템 운영](/posts/design-system-adoption-governance)에 있다.

```json
{
  "rules": {
    "declaration-property-value-allowed-list": {
      "/^(margin|padding|gap)/": ["0", "auto", "/var\\(--space-/"]
    }
  }
}
```

화면이 1~2px씩 움직이는 변경이라 눈으로 다 확인하기 어렵다. 시각 회귀 테스트로 바꾸기 전과 후의 스크린샷을 비교하고, 의도한 차이만 났는지 본다. 한 번에 전부 옮기기보다 화면 단위로 나눠 옮겨야 리뷰할 수 있다.

## rem으로 정할까 px로 정할까

토큰 값의 단위는 사용자가 브라우저 기본 글자 크기를 키웠을 때 무엇이 함께 커져야 하는가로 정한다. 글자 크기는 당연히 `rem`이다. `px`로 고정하면 기본 글자 크기를 20px로 올린 사용자에게도 16px로 보인다.

간격은 의견이 갈린다. `rem`으로 두면 글자가 커질 때 여백도 같은 비율로 커져서 화면 비율이 유지된다. 글자만 커지고 여백은 그대로면 큰 글자가 좁은 상자에 꽉 끼어 답답해진다. 대신 좁은 화면에서 여백까지 커져서 내용이 들어갈 자리가 준다. 대부분의 시스템은 간격과 크기도 `rem`으로 두고, 테두리 두께, 구분선, 그림자 오프셋처럼 커질 이유가 없는 값만 `px`로 둔다. 1px 선이 기본 글자 크기를 따라 1.25px이 되면 오히려 흐려진다.

토큰 이름에는 단위를 넣지 않는다. `--space-16px`이라고 지었다가 rem으로 바꾸면 이름이 거짓말이 된다. 디자인 도구에는 px로, 코드에는 rem으로 보이게 변환 도구에서 내보내면 된다.

## 8pt 그리드를 깨야 하는 순간

규칙을 지키는 게 목적은 아니다. 깨야 하는 순간이 몇 가지 있고, 그때는 이유를 알고 깬다.

테두리가 대표적이다. 40px 버튼에 1px 테두리가 있으면 안쪽 내용 영역은 38px이고, 20px 줄 높이를 가운데 두려면 위아래 여백이 9px이 된다. 여기서 10px을 고집하면 버튼이 42px이 되어 옆 입력칸과 어긋난다. 바깥 크기를 그리드에 맞추고 안쪽 숫자는 어긋나게 둔다. `box-sizing: border-box`를 쓰면 이 계산을 브라우저가 대신 한다.

시각 보정(optical adjustment)도 있다. 재생 버튼의 삼각형은 수학적으로 가운데 두면 왼쪽으로 치우쳐 보여서 1~2px 오른쪽으로 민다. 둥근 아이콘은 같은 상자 안의 네모 아이콘보다 작아 보여서 살짝 키운다. 대문자만 있는 버튼 글자는 아래 꼬리가 없어서 위로 떠 보인다.

정보 밀도가 높은 표나 개발 도구 화면은 행 높이 28px, 안쪽 여백 6px처럼 4의 배수 사이를 쓰기도 한다. 이럴 때는 밀도 단계를 따로 토큰으로 두고(`--density-compact`) 그 화면에서만 쓴다. 한 화면 안에서 예외를 하나씩 손으로 넣기 시작하면 다시 처음의 13px, 15px으로 돌아간다. 예외도 체계 안에 이름을 붙여 둔다.

## 면접에서 나올 만한 질문

### 간격 체계를 4pt나 8pt로 잡는 이유는요?

나누기 쉬워서 반 단위가 정수로 남고, 1.5배 같은 화면 밀도에서도 기기 픽셀로 정수가 떨어져 선과 경계가 흐려지지 않는다. 8을 기본으로 하고 촘촘한 곳에 4를 반 단위로 허용하는 방식이 흔하다. 무엇보다 고를 값을 줄여서 13px과 15px 같은 근거 없는 숫자가 들어오지 않게 하는 게 목적이다.

### 간격 스케일을 등간격이 아니라 점점 벌어지게 만드는 이유는요?

사람은 차이를 비율로 느끼기 때문이다. 4px과 8px은 두 배라 확실히 구분되지만 56px과 60px은 거의 같아 보인다. 그래서 작은 쪽은 4px씩 촘촘하게, 큰 쪽은 16px 이상씩 성글게 두고, 쓸 값만 골라 이름을 붙인다. 그 위에 카드 안쪽 여백 같은 의미 토큰을 얹어 결정을 한곳에서 바꾼다.

### 모듈러 타입 스케일의 비율은 어떻게 고르나요?

1.2처럼 작은 비율은 단계 차이가 작아 제목 위계가 깊은 문서나 밀도 높은 화면에 맞고, 1.25나 1.333처럼 큰 비율은 몇 단계 만에 크게 자라서 제목이 적고 시선을 끌어야 하는 화면에 맞다. 모바일은 큰 제목이 줄을 넘기 쉬워 작은 비율을 쓰고, 넓은 화면에서 비율을 키워 두 점을 `clamp()`로 잇는 방식을 많이 쓴다. 계산값은 반올림하고 실제 글꼴로 보고 다듬는다.

### 줄 높이를 그리드 단위에 맞추면 무엇이 좋은가요?

글이 몇 줄이 되든 블록 높이가 그리드 배수로 떨어져서 주변 간격과 컴포넌트 높이가 맞는다. 글자 크기 × 비율을 4px 배수로 반올림해 크기와 짝지은 토큰으로 두거나, 지원 범위가 맞으면 `round(up, 1.5em, 4px)`로 계산한다. 8px로 맞추면 작은 글자에서 너무 거칠어서 줄 높이는 4px 기준이 흔하다.

### 글자 옆 아이콘이 위로 떠 보이는 이유와 해결은요?

인라인 `svg`나 `img`는 기본 `vertical-align: baseline`이라 아래가 기준선에 붙고, 기준선 아래 꼬리 자리만큼 아래가 비어 떠 보인다. 아이콘 상자 높이를 글자 줄 높이와 같게 두고 `inline-flex`와 `align-items: center`로 가운데를 맞춘다. 14px 글자, 20px 줄 높이라면 20px 상자에 16px 아이콘을 둔다.

### 디자인 토큰을 rem과 px 중 무엇으로 정하나요?

사용자가 기본 글자 크기를 키웠을 때 같이 커져야 하는 값은 rem으로 둔다. 글자 크기는 반드시 rem이고, 간격과 컨트롤 크기도 rem으로 두면 글자와 여백의 비율이 유지된다. 테두리, 구분선, 그림자 오프셋처럼 커질 이유가 없는 값만 px로 둔다. 토큰 이름에는 단위를 넣지 않는다.

### 브레이크포인트를 CSS 변수 토큰으로 두지 않는 이유는요?

미디어 쿼리 조건에는 CSS 변수를 쓸 수 없다. 변수는 요소에 붙는 값이고 미디어 쿼리는 문서 전체에서 판단하기 때문이다. `@custom-media`는 아직 브라우저에서 바로 쓰기 어려워 빌드 도구로 펼치거나, 브레이크포인트를 TypeScript 상수로 두고 미디어 쿼리 문자열을 만들어 쓴다.

### 8pt 그리드를 깨도 되는 때는 언제인가요?

1px 테두리 때문에 안쪽 여백이 9px이 되는 경우처럼, 바깥 크기를 그리드에 맞추느라 안쪽 숫자가 어긋날 때다. 재생 삼각형을 오른쪽으로 밀거나 둥근 아이콘을 살짝 키우는 시각 보정도 그렇다. 밀도 높은 표처럼 예외가 반복되면 그때그때 손으로 넣지 말고 밀도 토큰처럼 이름 붙은 예외로 체계 안에 둔다.
