"구글로 계속하기" 버튼은 하루에도 몇 번씩 누른다. 그런데 그 버튼 뒤에서 무슨 일이 일어나는지는 막연하게만 알고 있었다. 리다이렉트가 몇 번 오가고, 어딘가에서 토큰이 생긴다는 정도. 이번에 흐름을 처음부터 끝까지 한 단계씩 따라가 보면서 정리했다.

## 비밀번호를 넘기면 안 되는 이유

일정 정리 앱이 내 구글 캘린더를 읽어야 한다고 해 보자. 가장 단순한 방법은 앱에 구글 비밀번호를 알려 주는 것이다. 당연히 위험하다. 비밀번호를 받은 앱은 캘린더뿐 아니라 메일도, 드라이브도 열 수 있다. 앱이 해킹당하면 내 계정도 같이 털린다. 이제 그만 쓰고 싶어도 비밀번호를 바꾸는 것 말고는 방법이 없다.

발렛 파킹을 떠올리면 쉽다. 차를 맡길 때 마스터 키를 주는 대신 발렛 키를 준다. 발렛 키로는 시동은 걸려도 트렁크는 안 열린다. OAuth는 이 발렛 키를 만들어 주는 규칙이다. 비밀번호(마스터 키) 대신 **할 수 있는 일과 쓸 수 있는 시간이 정해진 열쇠**, 즉 액세스 토큰을 앱에 넘긴다. 열쇠가 필요 없어지면 그 열쇠만 없애면 된다.

## 등장하는 네 주체

OAuth 문서를 읽으면 리소스 소유자, 클라이언트, 인가 서버, 리소스 서버 같은 이름이 계속 나온다. 이름은 딱딱해도 하는 일은 단순하다. 리소스 소유자는 계정 주인인 나, 클라이언트는 내 정보를 쓰려는 앱이다. 인가 서버는 열쇠를 발급하는 곳(구글 로그인 서버), 리소스 서버는 실제 정보를 가진 곳(구글 캘린더 API)이다.

## 토큰은 두 개가 온다

9번 응답을 다시 보면 토큰이 두 개 있다. 액세스 토큰은 API를 부를 때마다 내미는 출입증이고, 수명이 짧다. 리프레시 토큰은 출입증이 만료됐을 때 새 출입증을 받는 데만 쓴다. 수명이 길고, 인가 서버에만 보낸다.

수명을 일부러 짧게 잡는 이유는 도난 대비다. 액세스 토큰은 요청마다 네트워크를 타니 새어 나갈 기회가 많다. 짧게 살면 훔쳐 가도 금방 쓸모가 없어진다. 그렇다고 한 시간마다 다시 로그인시킬 수는 없으니, 리프레시 토큰으로 사용자 모르게 새 출입증을 받는다.

## 비밀을 숨길 수 없는 앱: PKCE

위 흐름은 앱이 client_secret을 안전하게 숨길 수 있다는 전제에 기대고 있다. 서버에서 도는 웹 앱이라면 괜찮다. 그런데 모바일 앱이나 브라우저에서 도는 SPA는 코드가 사용자 기기에 그대로 내려가기 때문에 비밀을 숨길 곳이 없다.

PKCE(픽시라고 읽는다)는 이 문제를 미리 정해 둔 비밀 대신 **요청할 때마다 새로 만드는 비밀**로 푼다. 앱은 무작위 문자열(code_verifier)을 만들고, 거기서 되돌릴 수 없는 지문(code_challenge)을 계산한다. 지문은 처음 요청에 실어 보내고, 원래 문자열은 코드를 토큰으로 바꿀 때 처음 꺼낸다.

  ]}
/>

요즘은 비밀을 숨길 수 있는 서버 앱에도 PKCE를 같이 쓰는 걸 권장한다. 코드가 새는 경로는 생각보다 다양해서, 방어선이 하나 더 있는 편이 낫다.

## 구현하면서 놓치기 쉬운 것

라이브러리를 쓰면 대부분 알아서 처리되지만, 직접 붙이다 보면 몇 군데서 구멍이 생긴다. state를 만들어 보내기만 하고 돌아왔을 때 비교하지 않는 경우가 생각보다 흔하다. redirect_uri를 앞부분만 비교하는 것도 위험하다. `https://app.example.com.evil.com` 같은 주소가 통과할 수 있다.

예전에 SPA에서 쓰던 암시적 흐름(Implicit Flow)은 토큰을 주소창에 바로 실어 보낸다. 앞에서 코드를 한 번 거치는 이유를 생각하면 왜 위험한지 알 수 있다. 지금은 쓰지 않고, SPA도 인가 코드 흐름에 PKCE를 붙인다.

<Callout kind="warning" title="OAuth는 로그인 규칙이 아니다">
  OAuth가 답하는 질문은 "이 앱이 내 정보를 써도 되는가"(인가)다. "이 사람이 누구인가"(인증)는 OAuth 위에 얹은 OpenID Connect가 맡는다. "구글로 로그인"은 보통 둘을 함께 쓴다.
</Callout>

## 인가 코드 말고 다른 방식들

OAuth에는 토큰을 받는 방식(grant type)이 몇 가지 더 있다. 사람이 끼지 않는 서버끼리의 통신에는 클라이언트 자격 증명(Client Credentials) 방식을 쓴다. 서버가 자기 client_id와 client_secret으로 바로 토큰을 받는다. 키보드 입력이 불편한 TV나 CLI 도구는 기기 코드(Device Code) 방식을 쓴다. 화면에 짧은 코드를 띄우고, 사용자가 휴대폰으로 그 코드를 입력해 승인하는 방식이다.

반대로 지금은 쓰지 않는 방식도 있다. 앞에서 본 암시적 흐름과, 앱이 사용자 비밀번호를 직접 받아 토큰으로 바꾸는 비밀번호 방식(Resource Owner Password Credentials)이다. 비밀번호를 앱에 넘기지 않으려고 OAuth를 쓰는 건데, 비밀번호 방식은 그 목적 자체를 거스른다. 이런 정리를 반영한 OAuth 2.1 초안은 인가 코드 흐름에 PKCE를 기본으로 두고 이 두 방식을 뺐다.

## 로그인까지 하려면: OpenID Connect

앞에서 OAuth는 인가 규칙이라고 했다. 액세스 토큰은 "이 앱이 이 범위의 API를 불러도 된다"는 증명일 뿐, 토큰을 든 사람이 누구인지 말해 주지 않는다. 액세스 토큰으로 사용자 정보 API를 불러서 로그인에 쓰는 방식도 가능하지만, 그 토큰이 내 앱을 위해 발급된 건지 확인할 표준 방법이 없다.

OpenID Connect(OIDC)는 인가 코드 흐름 위에 이걸 얹는다. scope에 `openid`를 넣으면 토큰 응답에 액세스 토큰과 함께 ID 토큰이 온다. ID 토큰은 JWT이고 누가(`sub`), 어느 발급자가(`iss`), 어느 앱을 위해(`aud`) 언제 로그인했는지가 서명되어 담겨 있다. 앱은 이 토큰을 검증해서 로그인 처리를 한다. 정리하면 ID 토큰은 앱이 읽는 "로그인 증명서"이고, 액세스 토큰은 API 서버에 내미는 "출입증"이다. 앱이 액세스 토큰을 디코딩해서 사용자를 판단하면 안 되는 이유가 여기 있다.

인가 요청에는 `nonce`도 함께 보낸다. state가 "이 응답이 내가 보낸 요청에 대한 것인가"를 확인한다면, nonce는 ID 토큰 안에 그대로 담겨 돌아와서 "이 ID 토큰이 이번 로그인을 위해 발급된 것인가"를 확인해 재사용(replay)을 막는다.

## 콜백에서 막히는 세 가지

소셜 로그인을 처음 붙이면 흐름 그림의 순서대로 막힌다. 인가 서버가 아예 돌려보내 주지 않거나, 돌아왔는데 앱이 state를 못 찾거나, 코드를 토큰으로 바꾸다 실패한다. 규칙대로 동작하는 연습용 인가 서버를 Node.js로 만들어 curl로 재현해 봤다. 이 서버에 등록한 주소는 `https://app.example.com/callback` 하나다.

첫 번째는 redirect_uri다. 끝에 `/`가 하나 더 붙은 주소와 `http`로 시작하는 주소로 인가 요청을 보냈다.

```bash
A='http://127.0.0.1:3301/authorize?response_type=code&client_id=my-app&state=xK3f9&redirect_uri='
curl -si "${A}https%3A%2F%2Fapp.example.com%2Fcallback%2F"   # 끝에 /가 붙었다
curl -si "${A}http%3A%2F%2Fapp.example.com%2Fcallback"       # https가 아니다
curl -si "${A}https%3A%2F%2Fapp.example.com%2Fcallback"      # 등록한 그대로
```

```text
HTTP/1.1 400 Bad Request
{"error":"invalid_request","error_description":"redirect_uri is not registered for this client"}
HTTP/1.1 400 Bad Request
{"error":"invalid_request","error_description":"redirect_uri is not registered for this client"}
HTTP/1.1 302 Found
Location: https://app.example.com/callback?code=Ooe4AC5NA9-AD4c7&state=xK3f9
```

글자 하나만 달라도 인가 서버는 브라우저를 돌려보내지 않고 자기 화면에 에러를 띄운다. 돌려보냈다가 공격자 주소로 코드가 샐 수 있어서다. 구글이라면 `Error 400: redirect_uri_mismatch` 화면이 뜬다. 끝 슬래시, `www` 유무, 포트 번호는 눈으로 찾기 쉽다. 찾기 어려운 건 `http`다. 앱이 TLS를 끝내는 로드 밸런서 뒤에 있으면 자기가 받은 요청이 `http`라고 생각해서 `http://.../callback`으로 주소를 만든다. 인가 요청 주소를 로그로 찍어 실제로 보낸 `redirect_uri`를 확인하고, 프레임워크가 `X-Forwarded-Proto`를 믿게 하거나 콜백 주소를 설정값으로 고정한다.

두 번째는 돌아왔는데 앱이 "state가 맞지 않는다"며 거절하는 경우다. state는 보통 세션 쿠키에 묶어 두는데, 그 세션 쿠키가 `SameSite=Strict`이면 문제가 된다. 인가 서버에서 앱으로 돌아오는 이동은 다른 사이트에서 시작된 이동이라, `Strict` 쿠키는 이 요청에 실리지 않는다. 앱은 세션을 못 찾고 state도 못 찾는다. 콜백을 받는 쿠키는 `Lax`로 둔다. `Lax`는 이런 최상위 GET 이동에는 쿠키를 붙여 준다. 같은 증상이 탭을 두 개 열고 로그인 버튼을 각각 눌렀을 때도 생긴다. 두 번째 요청의 state가 첫 번째 것을 덮어써서 먼저 돌아온 탭이 실패한다. state를 하나만 저장하지 말고 여러 개를 짧은 수명으로 들고 있으면 된다.

세 번째는 코드를 토큰으로 바꿀 때의 `invalid_grant`다. 같은 코드로 토큰 교환을 두 번 해 봤다.

```bash
curl -s -X POST http://127.0.0.1:3301/token \
  -d "grant_type=authorization_code&code=$CODE&redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback&client_id=my-app&client_secret=s3cret"
# 같은 명령을 한 번 더
```

```text
{"access_token":"bd8cb37be351d48c087a2120f906353f","token_type":"Bearer","expires_in":3600}
{"error":"invalid_grant"}
```

인가 코드는 한 번만 쓸 수 있고 수명도 보통 몇 분 안쪽이다. 두 번째 교환은 `invalid_grant`로 거절된다. 실제로는 이런 장면에서 만난다. 사용자가 콜백 페이지에서 새로고침을 했다. SPA에서 개발 모드의 React `StrictMode`가 effect를 두 번 실행해서 교환 요청이 두 번 나갔다. 콜백 처리가 느려서 사용자가 버튼을 다시 눌렀다. 토큰 교환 때 보내는 `redirect_uri`가 인가 요청 때와 다를 때, 코드가 만료됐을 때도 같은 `invalid_grant`가 온다(RFC 6749가 정한 에러 이름이라 대부분의 인가 서버가 같은 이름을 쓴다). 그래서 이 에러를 보면 교환 요청이 몇 번 나갔는지, 두 요청의 `redirect_uri`가 같은지, 콜백부터 교환까지 몇 초 걸렸는지를 차례로 본다. 교환이 끝나면 주소창에서 `code`를 지우고 다른 화면으로 넘겨서 새로고침해도 다시 교환하지 않게 한다.

브라우저 개발자 도구로 볼 때는 Network 패널의 "Preserve log"를 켠다. 리다이렉트가 오가며 페이지가 바뀌어도 기록이 남아서, 302 응답의 `Location`에 실린 `code`와 `state`, 콜백 요청에 쿠키가 실렸는지를 한 화면에서 따라갈 수 있다.

## 정리

OAuth는 결국 "누가, 무엇을, 얼마 동안" 할 수 있는지를 토큰에 담아 넘기는 규칙이다. 비밀번호 대신 범위와 수명이 정해진 열쇠를 준다. 그 열쇠가 브라우저 주소창을 지나가지 않도록 코드를 한 번 거친다. 비밀을 숨길 수 없는 앱은 PKCE로 그때그때 비밀을 만든다. 로그인까지 필요하면 그 위에 OpenID Connect를 얹어 ID 토큰을 함께 받는다.

## 면접에서 나올 만한 질문

### OAuth 2.0은 무엇이고 왜 쓰나요?

사용자가 비밀번호를 넘기지 않고, 다른 앱에 자기 자원에 대한 제한된 권한을 위임하는 표준이다. 앱은 비밀번호 대신 범위(scope)와 수명이 정해진 액세스 토큰을 받는다. 권한이 필요 없어지면 그 토큰만 폐기하면 되고, 앱이 해킹당해도 비밀번호는 안전하다.

### 인가 코드를 한 번 거쳐서 토큰을 받는 이유는요?

브라우저 주소창을 지나는 값은 방문 기록, 리퍼러, 확장 프로그램 등으로 새어 나가기 쉽다. 그래서 브라우저로는 짧게 살고 한 번만 쓸 수 있는 인가 코드만 보내고, 토큰 교환은 앱 서버와 인가 서버가 client_secret으로 직접 한다. 코드가 새도 secret 없이는 토큰으로 바꿀 수 없다.

### PKCE는 무엇을 막나요?

client_secret을 숨길 수 없는 모바일 앱이나 SPA에서 인가 코드를 가로채 토큰으로 바꾸는 공격을 막는다. 앱이 요청마다 무작위 code_verifier를 만들고, 그 해시(code_challenge)를 인가 요청에 보낸다. 토큰 교환 때 원본 verifier를 보내야 하므로, 코드만 훔친 공격자는 토큰을 받지 못한다. 지금은 서버 앱에도 함께 쓰는 걸 권장한다.

### state와 nonce는 각각 무엇을 막나요?

state는 앱이 보낸 인가 요청과 돌아온 응답을 짝지어 CSRF를 막는다. 공격자가 자기 인가 코드를 내 앱 콜백에 밀어 넣는 걸 막는 것이다. nonce는 OIDC에서 ID 토큰 안에 담겨 돌아와, 그 ID 토큰이 이번 로그인을 위해 발급된 것인지 확인해 재사용을 막는다.

### OAuth와 OpenID Connect는 어떻게 다른가요?

OAuth는 인가, 즉 "이 앱이 이 API를 불러도 되는가"를 다루고 액세스 토큰을 준다. OIDC는 그 위에 인증, 즉 "이 사용자가 누구인가"를 얹어 ID 토큰(JWT)을 추가로 준다. 소셜 로그인은 보통 OIDC를 쓴다.

### 액세스 토큰과 ID 토큰은 무엇이 다른가요?

액세스 토큰은 리소스 서버(API)에 보여 주는 출입증이고, 앱은 그 내용을 해석하지 않는 게 원칙이다. 형식도 JWT일 수도, 아무 의미 없는 문자열일 수도 있다. ID 토큰은 앱이 직접 검증하고 읽는 로그인 증명서로, 반드시 JWT이며 `aud`가 자기 앱인지 확인해야 한다. API 호출에 ID 토큰을 쓰거나 로그인 판단에 액세스 토큰을 쓰면 안 된다.

### 서버 간 통신에는 어떤 방식을 쓰나요?

사용자가 개입하지 않으니 클라이언트 자격 증명(Client Credentials) 방식을 쓴다. 서버가 자기 client_id와 secret으로 바로 토큰을 받는다. 리프레시 토큰은 보통 주지 않고, 만료되면 다시 요청한다.
