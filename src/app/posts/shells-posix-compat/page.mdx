<EasyIntro>
  셸은 사람이 친 명령을 컴퓨터에게 전해 주는 통역사다. 통역사는 한 명만 있는 게 아니라 bash, dash, zsh처럼 여러 명이 있다.

  이 통역사들은 모두 같은 기본 말을 알아듣는다. 하지만 각자 자기만 아는 사투리도 쓴다. bash에게 사투리로 말하면 잘 알아듣지만, 같은 말을 dash에게 하면 못 알아듣거나 엉뚱하게 옮긴다.

  내 노트북에서는 bash가 통역하던 스크립트가, 서버나 컨테이너에서는 다른 통역사에게 맡겨지는 일이 흔하다. 그러면 어제까지 되던 스크립트가 갑자기 이상하게 돈다.

  해결 방법은 두 가지다. 누구나 아는 기본 말로만 쓰거나, 첫 줄에 "이 글은 bash가 읽어 주세요"라고 분명히 적는 것이다. 이 글은 통역사들이 어떻게 다른지, 그리고 내가 쓴 말에 사투리가 섞였는지 검사하는 법을 다룬다.
</EasyIntro>

로컬에서 잘 돌던 배포 스크립트를 CI의 Alpine 컨테이너에 올렸더니 첫 줄부터 문법 오류가 난다. 같은 스크립트를 Ubuntu 서버에서 `sh deploy.sh`로 돌리면 이번엔 오류는 덜 나는데 `prod` 분기를 안 탄다. 스크립트는 한 글자도 안 바꿨다. 바뀐 건 그 스크립트를 읽은 셸이다.

```bash
#!/bin/sh
files=(a.txt b.txt)
if [[ "$1" == prod* ]]; then echo "prod"; fi
for i in {1..3}; do echo "n=$i"; done
echo "first=${files[0]}"
```

```text
== bash
prod
n=1
n=2
n=3
first=a.txt
exit=0
== dash (sh)
deploy.sh: 2: Syntax error: "(" unexpected
exit=2
== busybox ash
deploy.sh: line 2: syntax error: unexpected "("
exit=2
```

첫 줄에 `#!/bin/sh`라고 적어 놓고 bash 문법을 썼다. 노트북(macOS의 `/bin/sh`는 bash를 POSIX 모드로 띄운다)이나 `bash deploy.sh`로 돌릴 때는 bash가 읽으니 문제가 없었다. Ubuntu의 `/bin/sh`는 dash, Alpine의 `/bin/sh`는 BusyBox의 ash다. 둘 다 배열을 모른다. 기준은 Ubuntu 24.04이고, 이 글의 출력은 그 위의 bash 5.2.21, dash 0.5.12, BusyBox 1.36.1, zsh 5.9, ksh93u+m 1.0.8로 직접 돌린 것이다.

## 누가 스크립트를 읽을지는 실행하는 방법이 정한다

`./deploy.sh`로 실행하면 커널이 파일 첫 두 바이트 `#!`를 보고 그 뒤에 적힌 프로그램을 띄워 파일을 넘긴다. 이걸 shebang이라고 한다. 반면 `sh deploy.sh`나 `bash deploy.sh`처럼 셸 이름을 앞에 적으면 커널은 그 셸을 띄울 뿐이고, shebang 줄은 그 셸에게 주석 한 줄일 뿐이다. shebang과 실행 권한의 기본은 [셸 환경과 시작 파일](/posts/shell-environment-startup) 글에서 다뤘다. 여기서는 그 결과 누가 읽게 되는지만 본다.

그래서 규칙은 하나다. bash 문법을 쓰면 첫 줄을 `#!/bin/bash`나 `#!/usr/bin/env bash`로 쓰고, 실행할 때 `sh`를 앞에 붙이지 않는다. crontab과 Dockerfile의 `RUN`(셸 형식)과 `make`의 레시피는 모두 `/bin/sh -c`로 명령을 돌린다는 것도 같이 기억해 둔다. 거기 적은 한 줄은 bash가 아니라 dash가 읽는다.

## 같은 줄이 셸마다 다르게 깨진다

배열처럼 문법 단계에서 바로 멈추는 경우는 차라리 낫다. 더 곤란한 건 실행 중에 조용히 다른 값을 내는 경우다. 다섯 줄짜리 스크립트를 다섯 셸로 돌렸다.

```bash
#!/bin/sh
if [[ "$1" == prod* ]]; then echo "prod"; fi
for i in {1..3}; do echo "n=$i"; done
echo -e "a\tb"
x=hello; echo "${x^^}"
source ./lib.sh 2>/dev/null || echo "no source"
```

```text
== bash
prod
n=1
n=2
n=3
a	b
HELLO

exit=0
== dash

-e a	b

exit=2
== busybox sh

a	b

exit=2
== zsh

n=2

exit=1
== ksh
```

가장 위험한 건 첫 줄이다. `[[`가 없다는 메시지가 한 줄 찍히고 스크립트는 계속 간다. `if`가 거짓으로 처리됐으니 운영 배포 분기를 건너뛰고 기본 분기로 간다. 로그를 보지 않으면 "배포는 성공했는데 설정이 개발용이다" 같은 증상으로만 나타난다. `set -e`를 켜도 `if` 조건 자리의 실패는 멈추지 않는다는 점은 [bash 스크립트 글](/posts/bash-scripting)의 "set -e가 멈추지 않는 자리"에서 봤다.

zsh와 ksh도 bash가 아니다. 둘 다 `[[ ]]`와 `{1..3}`은 알지만 `${x^^}`는 모른다. 대화형으로 zsh를 쓰는 사람이 `zsh deploy.sh`로 시험해 보고 "된다"고 하는 경우가 그래서 믿을 게 못 된다. zsh는 더 근본적인 차이도 있다.

```bash
f="my file.txt"
for w in $f; do echo "word=[$w]"; done
arr=(a b c); echo "first=${arr[1]}"
```

```text
== bash
word=[my]
word=[file.txt]
first=b
== zsh
word=[my file.txt]
first=a
```

zsh는 따옴표 없는 변수를 공백에서 쪼개지 않고, 배열 번호가 1부터 시작한다. bash에서 따옴표를 빼먹어 생기던 버그가 zsh에서는 안 보이니, zsh로 시험하고 bash로 돌리면 거꾸로 깨진다.

## POSIX sh가 약속하는 것

이 혼란 아래에 공통 언어가 있다. POSIX(IEEE 1003.1) 표준의 "Shell Command Language"다. 변수, `if`·`case`·`while`·`for`, 함수, 리다이렉션, `$(...)`, `$((...))` 산술, `${var:-기본값}` 같은 매개변수 확장이 여기에 들어 있다. dash, BusyBox ash, bash, zsh, ksh 모두 이걸 지킨다(zsh는 `emulate sh`나 `sh` 이름으로 띄울 때 가장 가깝게 지킨다).

위 스크립트를 POSIX 문법만으로 다시 썼다.

```bash
#!/bin/sh
set -eu
case "${1:-}" in prod*) echo "prod" ;; esac         # [[ == 패턴 ]] 대신 case
i=1; while [ "$i" -le 3 ]; do echo "n=$i"; i=$((i+1)); done   # {1..3} 대신
printf 'a\tb\n'                                      # echo -e 대신 printf
x=hello; printf '%s\n' "$x" | tr '[:lower:]' '[:upper:]'      # ${x^^} 대신
. ./lib.sh                                           # source 대신 .
set -- a.txt b.txt                                   # 배열 대신 위치 매개변수
echo "first=$1 count=$#"
```

```text
== bash
prod n=1 n=2 n=3 a	b HELLO lib first=a.txt count=2
== dash
prod n=1 n=2 n=3 a	b HELLO lib first=a.txt count=2
== busybox sh
prod n=1 n=2 n=3 a	b HELLO lib first=a.txt count=2
== zsh
prod n=1 n=2 n=3 a	b HELLO lib first=a.txt count=2
== ksh
prod n=1 n=2 n=3 a	b HELLO lib first=a.txt count=2
```

다섯 셸이 같은 결과를 낸다. 바꾼 것들은 대부분 기계적이다. `[[ ]]` 대신 `[ ]`와 `case`, `==` 대신 `=`, `echo -e` 대신 `printf`, `source` 대신 `.`, `function f` 대신 `f()`. 배열은 POSIX에 하나뿐인 배열인 위치 매개변수(`set --`)로 버틸 수 있지만, 두 개 이상 필요해지면 bash로 가는 게 맞다. `pipefail`은 POSIX 2024판에 들어갔지만 Ubuntu 24.04의 dash 0.5.12는 아직 모른다.

POSIX로 쓰는 게 늘 정답은 아니다. 고르는 기준은 "이 스크립트가 어디서 돌 것인가"다.

- Alpine·distroless에 가까운 작은 이미지, initramfs, 임베디드 장비, 여러 유닉스에 배포하는 설치 스크립트: bash가 없을 수 있다. POSIX sh로 쓴다.
- 우리 팀 Ubuntu 서버와 CI에서만 도는 운영 스크립트: bash는 늘 있다. `#!/usr/bin/env bash`로 못박고 배열, `[[ ]]`, `pipefail`을 마음껏 쓴다. 억지로 POSIX에 맞추면 오히려 따옴표 실수가 늘어난다.

## 셸 가족을 한 장에

셸은 크게 두 계보에서 나왔다. 1979년 유닉스 V7의 Bourne shell(`sh`) 계보와, 같은 시기 BSD의 C shell(`csh`) 계보다. 아래 그림의 화살표는 "문법을 물려받았다"는 뜻이다. 점이 흐르는 방향으로 따라가면 된다.

각 셸의 성격을 짧게 적는다.

- bash: GNU 프로젝트의 셸이고 대부분 리눅스 배포판의 기본 로그인 셸이다. POSIX 위에 배열, 연관 배열, `[[ ]]`, 프로세스 치환 같은 확장을 얹었다. macOS는 라이선스(GPLv3) 문제로 bash 3.2에 멈춰 있어서, 연관 배열(bash 4)이나 `${x^^}`가 macOS 기본 bash에서는 안 된다.
- dash: Debian Almquist shell. 작고 빠르게 만든 POSIX 셸이다. Debian과 Ubuntu가 부팅 스크립트를 빨리 돌리려고 `/bin/sh`로 바꿨다.
- ash·BusyBox sh: dash와 같은 뿌리의 Almquist 셸이다. Alpine과 임베디드 장비의 `/bin/sh`다.
- ksh: Korn shell. `[[ ]]`, 배열 같은 확장을 bash보다 먼저 만들었다. AIX 같은 상용 유닉스와 오래된 금융권 배치 스크립트에서 아직 만난다.
- zsh: 탭 완성, 플러그인(oh-my-zsh), 맞춤법 교정이 강해서 대화형으로 인기가 많다. macOS는 10.15 Catalina부터 기본 로그인 셸이 zsh다. 위에서 본 것처럼 bash와 단어 쪼개기, 배열 번호가 다르다.
- fish: 처음부터 쓰기 편하게 만든 셸이다. 자동 제안과 문법 강조가 기본이다. 대신 POSIX 문법이 아니다(`set x 1`, `if test ...; end`). 대화형으로만 쓰고 스크립트는 다른 셸로 쓰는 게 보통이다.
- tcsh: C shell 계보다. 문법이 sh와 아예 다르다(`setenv`, `if (...) then`). FreeBSD의 root 기본 셸이 오랫동안 tcsh였다. 스크립트 언어로는 권하지 않는다는 오래된 글("Csh Programming Considered Harmful")이 있을 정도다.

## 대화형 셸과 스크립트 셸은 따로 고른다

여기서 실무 규칙이 하나 나온다. 내가 터미널에서 쓰는 셸과 스크립트를 쓰는 셸은 서로 상관이 없다. 대화형 셸은 손에 편한 것을 고르면 된다. zsh나 fish를 써도 된다. 스크립트는 그 스크립트가 돌 곳에 맞춰 bash나 POSIX sh로 쓰고 shebang으로 못박는다. 그러면 fish 사용자가 `./deploy.sh`를 실행해도 커널이 bash를 띄운다.

로그인 셸을 바꾸는 방법은 이렇다.

```bash
cat /etc/shells          # 로그인 셸로 쓸 수 있게 등록된 셸 목록
echo "$SHELL"            # 지금 내 로그인 셸
chsh -s /usr/bin/zsh     # 다음 로그인부터 zsh (목록에 있어야 한다)
```

`$SHELL`은 로그인 셸일 뿐 "지금 이 스크립트를 읽는 셸"이 아니다. 스크립트 안에서 지금 셸을 알고 싶으면 `ps -p $$ -o comm=`이나 bash라면 `$BASH_VERSION`이 비었는지를 본다.

왜 데비안은 `/bin/sh`를 굳이 dash로 바꿨을까. 시작 시간과 크기가 다르다. 빈 명령을 1000번 띄워 봤다.

```bash
for s in dash bash; do echo "== $s"; time (for i in $(seq 1000); do $s -c ':'; done); done
ls -l /usr/bin/dash /usr/bin/bash
```

```text
== dash
real	0m1.499s
== bash
real	0m1.951s

```

바이너리는 11분의 1이고, 한 번 띄울 때마다 0.45ms쯤 덜 든다. 사람이 느낄 차이는 아니지만 부팅이나 패키지 설치처럼 짧은 `sh -c`를 수천 번 띄우는 곳에서는 쌓인다. 이 머신은 다른 작업과 함께 돌고 있어서 절대값보다 비율만 본다.

## 사투리를 기계에게 찾게 한다

눈으로 찾는 건 한계가 있다. 도구가 둘 있다. `checkbashisms`(Debian의 devscripts 패키지)는 `#!/bin/sh` 스크립트에서 bash 전용 문법을 찾는다. `shellcheck`는 더 넓게 버그를 찾는데, `--shell=sh`(또는 shebang)를 보고 그 셸 기준으로 검사한다.

```bash
sudo apt install shellcheck devscripts   # devscripts는 꽤 크다. checkbashisms만 필요하면 이 패키지 하나를 받는다
checkbashisms deploy.sh
shellcheck --shell=sh -f gcc deploy.sh build.sh
```

`checkbashisms`는 2번 줄의 배열 대입 `files=(a.txt b.txt)`를 놓쳤고(dash를 멈춘 바로 그 줄이다), shellcheck는 잡았다. shellcheck 0.9 기준으로 SC3로 시작하는 경고가 "POSIX sh에 없는 문법" 묶음이다. POSIX로 고친 스크립트는 shellcheck에서 `lib.sh`를 따라가지 않았다는 안내(SC1091) 하나만 남았고, `checkbashisms`는 아무것도 찍지 않고 0으로 끝났다.

## PowerShell과 cmd는 텍스트가 아니라 다른 것을 넘긴다

윈도 서버나 Azure를 만지면 PowerShell을 만난다. 문법보다 큰 차이는 파이프로 흐르는 것이다. 유닉스 셸의 파이프에는 바이트(텍스트)가 흐른다. 그래서 `ps aux | awk '$3 > 50 {print $11}'`처럼 출력 모양을 보고 칸 번호로 자른다. 출력 형식이 바뀌면 스크립트가 깨진다. 텍스트를 자르는 도구들은 [grep·awk·sed 글](/posts/linux-grep-awk-sed)에 있다.

PowerShell 파이프에는 .NET 객체가 흐른다.

```powershell
# CPU 시간이 100초 넘는 프로세스의 이름과 CPU (칸 번호가 아니라 속성 이름으로)
Get-Process | Where-Object CPU -gt 100 | Select-Object Name, CPU
# 결과를 JSON으로 바로 바꾼다
Get-Process | Select-Object -First 3 Name, Id | ConvertTo-Json
```

`CPU`, `Name`은 화면에 찍힌 글자가 아니라 객체의 속성이다. 출력 모양과 상관없이 같은 코드가 돈다. 대신 외부 프로그램(`git`, `kubectl`)의 출력은 결국 문자열 줄로 들어오니, 그쪽은 `--output json`으로 받아 `ConvertFrom-Json`으로 바꿔 쓴다. PowerShell 7(`pwsh`)은 리눅스와 macOS에서도 돈다.

cmd(`cmd.exe`)는 MS-DOS의 `COMMAND.COM`을 이은 옛 셸이다. 변수는 `%VAR%`, 실패 확인은 `if errorlevel 1`처럼 쓴다. 새로 쓸 스크립트라면 윈도에서도 PowerShell로 쓰고, cmd는 오래된 `.bat` 파일을 읽을 때만 만난다. 셸마다 줄 끝(CRLF와 LF)도 다르다. 윈도에서 편집한 스크립트를 리눅스에서 돌리면 shebang 줄 끝의 `\r` 때문에 `/bin/bash^M: bad interpreter` 같은 오류가 난다. `.gitattributes`에 `*.sh text eol=lf`를 두면 막힌다.

## 스크립트를 셸에 두기로 했다면

정리하면, 같은 스크립트가 셸마다 다르게 도는 건 "누가 읽느냐"가 실행 방법과 shebang으로 정해지고, 각 셸이 POSIX라는 공통 언어 위에 서로 다른 사투리를 얹었기 때문이다. bash를 쓸 거면 `#!/usr/bin/env bash`로 못박고, 어디서든 돌아야 하면 POSIX로 쓰고 shellcheck `--shell=sh`로 검사한 뒤 그 이미지에서 직접 돌려 본다. 셸 스크립트가 길어질 때 어디서 언어를 바꿀지는 아래 꼬리 질문에서 다룬다. 같은 Linux 토픽의 다른 글로 [패키지 관리자](/posts/linux-package-management)와 [tar와 압축, 파일 옮기기](/posts/linux-archive-transfer)가 있다.

## 면접에서 나올 만한 질문

### #!/bin/sh로 시작하는 스크립트가 Ubuntu에서만 깨집니다. 왜인가요?

Ubuntu와 Debian의 `/bin/sh`가 bash가 아니라 dash이기 때문이다. dash는 POSIX 셸이라 배열, `[[ ]]`, `{1..3}`, `${x^^}` 같은 bash 확장을 모른다. macOS나 `bash script.sh`로 돌릴 때는 bash가 읽어서 숨어 있던 문제다. bash 문법을 쓰면 shebang을 `#!/usr/bin/env bash`로 바꾸고, `sh script.sh`로 부르지 않는다.

### shebang은 누가 읽나요? `sh script.sh`로 실행하면 어떻게 되나요?

`./script.sh`처럼 파일을 실행하면 커널이 첫 줄의 `#!` 뒤 경로를 해석기로 띄운다. `sh script.sh`처럼 셸을 직접 지정하면 커널은 sh만 띄우고, sh에게 shebang 줄은 주석이다. 그래서 같은 파일이 실행 방법에 따라 다른 셸에서 돈다. crontab, Dockerfile의 셸 형식 RUN, make 레시피는 `/bin/sh -c`로 돌린다는 점도 같은 함정이다.

### POSIX sh로 쓰는 것과 bash로 쓰는 것, 어떻게 고르나요?

스크립트가 돌 곳으로 고른다. Alpine 같은 작은 이미지, 임베디드, 여러 유닉스에 배포하는 설치 스크립트처럼 bash가 없을 수 있는 곳이면 POSIX로 쓴다. 우리 서버와 CI에서만 돌면 bash로 못박고 배열과 `pipefail`을 쓰는 편이 오히려 안전하다. 억지 POSIX는 따옴표와 위치 매개변수 묘기 때문에 버그가 늘어난다.

### dash에서 `[[ ... ]]`를 쓰면 어떻게 되나요? 왜 위험한가요?

dash에게 `[[`는 문법이 아니라 명령 이름이라 "not found"(127)로 실패하고 스크립트는 계속 간다. `if` 조건이 거짓으로 처리되어 조용히 다른 분기로 간다. 배열처럼 문법 오류로 바로 멈추는 경우보다 찾기 어렵다. `set -e`도 if 조건 자리의 실패에는 멈추지 않는다.

### zsh에서 시험한 스크립트를 bash에서 돌렸더니 결과가 다릅니다. 무엇부터 의심하나요?

단어 쪼개기와 배열 번호다. zsh는 따옴표 없는 `$var`를 공백에서 쪼개지 않고 배열이 1부터 시작한다. bash는 쪼개고 0부터 시작한다. 그래서 zsh에서 안 보이던 따옴표 누락 버그가 bash에서 나타난다. 스크립트는 대화형 셸이 아니라 shebang에 적은 셸로 시험한다.

### 이식성은 어떻게 검사하나요?

`shellcheck --shell=sh`가 POSIX에 없는 문법을 SC3 계열 경고로 알려 준다. Debian의 `checkbashisms`도 비슷한 일을 하지만 배열 대입처럼 놓치는 것이 있었다. CI에서 shellcheck를 경고 수준으로 걸고, 마지막에는 실제로 돌 이미지(예: `alpine`)에서 스크립트를 직접 돌려 본다.

### PowerShell 파이프는 bash 파이프와 무엇이 다른가요?

bash 파이프에는 텍스트가 흘러서 출력 모양을 보고 칸을 잘라야 한다. PowerShell 파이프에는 객체가 흘러서 `Where-Object CPU -gt 100`처럼 속성 이름으로 고른다. 출력 형식이 바뀌어도 코드가 깨지지 않는다. 대신 외부 프로그램의 출력은 문자열로 들어오니 JSON으로 받아 변환해 쓴다.

### 셸 스크립트는 언제 Python 같은 언어로 넘기나요?

명령을 잇고 파일을 옮기고 종료 코드로 흐름을 가르는 일이면 셸이 맞다. JSON을 고쳐 다시 보내거나, 재시도와 타임아웃을 계산하거나, 자료 구조가 배열 몇 개를 넘거나, 테스트를 붙여야 할 만큼 로직이 커지면 넘길 때다. 셸마다 사투리를 맞추는 비용이 커지는 것도 신호다. Python도 서버마다 버전이 다르니 그때는 런타임을 이미지로 고정한다.
