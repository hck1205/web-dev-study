크론에 걸어 둔 정리 스크립트가 가끔 실패한다는데 로그 파일에는 아무 오류가 없다. 크론 줄을 보니 이렇게 적혀 있다.

```bash
0 3 * * * /opt/jobs/cleanup.sh 2>&1 > /var/log/cleanup.log
```

옆 서버의 같은 작업은 `> /var/log/cleanup.log 2>&1`로 적혀 있고, 거기는 오류가 로그에 잘 남는다. 차이는 두 조각의 순서뿐이다. stdout과 stderr를 한 줄씩 찍는 작은 스크립트로 확인했다.

```bash
cat > cmd.sh <<'EOF'
#!/bin/bash
echo "out"
echo "err" >&2
EOF
chmod +x cmd.sh
./cmd.sh > log1 2>&1;  echo "[log1]"; cat log1
./cmd.sh 2>&1 > log2;  echo "[log2]"; cat log2
```

```text
[log1]
out
err
err
[log2]
out
```

`2>&1 > log2` 쪽은 `err`가 로그로 가지 않고 터미널에 찍혔다. 크론에서는 터미널이 없으니 그 줄은 메일로 가거나 버려진다. 왜 순서가 결과를 바꾸는지는 리다이렉션이 "무엇을 하는 명령"인지 알면 바로 보인다. 이 글은 파일 디스크립터 표에서 시작해 리다이렉션이 그 표를 어떻게 고치는지, 파이프가 두 프로세스를 어떻게 잇고 버퍼가 차면 무슨 일이 생기는지, tee와 here document, 프로세스 치환까지 따라간다.

기준은 Ubuntu 24.04의 bash 5.2다. 출력은 모두 직접 돌린 것이다. 파이프의 종료 코드와 `pipefail`, 스크립트에서 stdout과 stderr를 나눠 쓰는 습관은 [bash 스크립트 글](/posts/bash-scripting)에서 다뤘으니 여기서는 짧게만 짚는다.

## 프로세스는 번호 붙은 구멍 세 개로 시작한다

프로세스가 파일, 터미널, 파이프, 소켓에 읽고 쓸 때는 이름이 아니라 작은 정수를 쓴다. 이게 파일 디스크립터(fd)다. 프로세스마다 "번호 → 열린 대상" 표가 있고, 0번은 표준 입력(stdin), 1번은 표준 출력(stdout), 2번은 표준 오류(stderr)로 약속되어 있다. `echo`는 1번에 쓰고, 오류 메시지는 2번에 쓰고, `read`는 0번에서 읽는다. 어디에 이어져 있는지는 프로그램이 모른다.

이 표는 `/proc/PID/fd/`에서 직접 볼 수 있다. 자기 0, 1, 2번이 어디를 가리키는지 찍는 스크립트를 만들었다. 결과는 9번 fd로 따로 내보내서, 1번과 2번을 아무리 바꿔도 화면에서 볼 수 있게 했다.

```bash
cat > fds.sh <<'EOF'
#!/bin/bash
for fd in 0 1 2; do printf '%s -> %s\n' "$fd" "$(readlink /proc/$$/fd/$fd)" >&9; done
EOF
chmod +x fds.sh
./fds.sh 9>&1
```

```text
0 -> /dev/pts/0
1 -> /dev/pts/0
2 -> /dev/pts/0
```

세 칸 모두 지금 터미널(`/dev/pts/0`)이다. 터미널에서 명령을 치면 셸이 자기 표를 그대로 물려주기 때문이다. 셸은 명령을 실행할 때 자신을 복제(fork)하고, 복제본에서 표를 고친 뒤 그 명령으로 갈아탄다(exec). 리다이렉션은 이 "표를 고치는" 단계에서 일어난다. 명령은 고쳐진 표를 받아 그대로 1번에 쓸 뿐이다.

## 리다이렉션은 왼쪽부터 표의 칸을 바꾼다

`> app.log`는 "app.log를 쓰기용으로 열고 그걸 1번 칸에 넣어라"다. `2>&1`은 "지금 1번 칸에 들어 있는 것을 2번 칸에도 넣어라"다. 시스템 호출로 쓰면 `dup2(1, 2)`이고, 핵심은 "지금"이다. 1번이 나중에 바뀌어도 2번은 따라가지 않는다. 셸은 리다이렉션을 왼쪽에서 오른쪽으로 하나씩 처리한다. 아래 그림에서 단계를 넘기며 표가 바뀌는 모습을 보자.

실제 프로세스의 표로 확인했다.

```bash
./fds.sh 9>&1 > app.log 2>&1
./fds.sh 9>&1 2>&1 > app.log
```

```text
0 -> /dev/pts/0
1 -> /srv/demo/app.log
2 -> /srv/demo/app.log
0 -> /dev/pts/0
1 -> /srv/demo/app.log
2 -> /dev/pts/0
```

그림과 같다. 그래서 "stdout과 stderr를 같은 파일에"는 언제나 `> 파일 2>&1` 순서다. bash에서는 이걸 줄여 `&> 파일`로도 쓴다. 다만 `&>`는 bash 전용이라 `#!/bin/sh`로 도는 스크립트(Ubuntu의 sh는 dash다)나 크론의 기본 셸에서는 "백그라운드 실행 + 빈 리다이렉션"으로 엉뚱하게 해석된다. 크론 줄에는 길게 쓰는 편이 안전하다.

같은 원리로 fd 두 개를 맞바꿀 수도 있다. 3번을 임시 칸으로 쓴다.

```bash
# stdout은 out.log로 보낸 뒤, 1번과 2번을 맞바꾼다
./fds.sh 9>&1 > out.log 3>&1 1>&2 2>&3
```

```text
0 -> /dev/pts/0
1 -> /dev/pts/0
2 -> /srv/demo/out.log
```

3번에 out.log를 맡겨 두고, 1번에 2번(터미널)을 넣고, 2번에 3번(out.log)을 넣었다. 이 순서를 머리로 따라가는 연습은 글 끝의 코드로 해 볼 수 있다.

## 출력 리다이렉션은 명령보다 먼저 파일을 연다

`>`는 파일이 없으면 만들고, 있으면 길이를 0으로 자른 뒤 연다. `>>`는 자르지 않고 끝에 덧붙인다. 이 일이 명령을 실행하기 전에 일어난다는 점이 함정을 만든다.

```bash
printf 'c\na\nb\n' > list.txt
sort list.txt > list.txt      # 정렬해서 같은 파일에 쓰려고 했다
wc -c list.txt
nosuch > out.txt 2>/dev/null  # 없는 명령
ls -l out.txt
```

```text
0 list.txt
-rw-r--r-- 1 root root 0 Oct 23 19:23 out.txt
```

셸이 `list.txt`를 먼저 0바이트로 잘라 놓고 `sort`를 실행했으니 `sort`는 빈 파일을 읽었다. 명령이 없어서 실패해도 `out.txt`는 이미 생겼다. 같은 파일을 읽고 쓰려면 `sort -o list.txt list.txt`처럼 명령 스스로 다 읽은 뒤 쓰게 하거나, 임시 파일에 쓰고 `mv`로 바꾼다. 실수로 중요한 파일을 `>`로 덮는 걸 막고 싶으면 `set -o noclobber`를 켠다.

```bash
set -o noclobber
echo x > app.log;  echo "exit=$?"
echo x >| app.log; echo "exit=$?"    # 정말 덮어쓰려면 >| 로 쓴다
```

```text
bash: line 1: app.log: cannot overwrite existing file
exit=1
exit=0
```

`/dev/null`은 쓰면 버리고 읽으면 바로 끝(EOF)인 특수 파일이다. `2>/dev/null`은 오류를 버리는 흔한 방법이지만, 진짜 장애의 단서도 같이 버린다. 크론과 배치에서는 버리지 말고 따로 모으는 편이 낫다. 뒤에서 그 방법을 본다.

## 입력 리다이렉션은 0번을 바꾼다

`< 파일`은 파일을 읽기용으로 열어 0번에 넣는다.

```bash
./fds.sh 9>&1 < /etc/hostname
printf 'c\na\nb\n' > list.txt
wc -l list.txt
wc -l < list.txt
```

```text
0 -> /etc/hostname
1 -> /dev/pts/0
2 -> /dev/pts/0
3 list.txt
3
```

`wc -l list.txt`는 `wc`가 직접 파일을 열어서 이름을 알고, `wc -l < list.txt`는 셸이 열어 0번으로 준 거라 `wc`는 이름을 모른다. 그래서 숫자만 필요할 때는 `<`를 쓴다. 파일 이름에 `-`로 시작하는 이상한 이름이 와도 옵션으로 오해받지 않는 장점도 있다.

## here document와 here string

여러 줄을 0번으로 넣을 때는 here document를 쓴다. `<<끝표시`부터 그 표시만 있는 줄까지가 입력이 된다.

```bash
name=shop
cat <<EOF
server_name $name.example.com;
root \$document_root;
EOF
cat <<'EOF'
server_name $name.example.com;
EOF
```

```text
server_name shop.example.com;
root $document_root;
server_name $name.example.com;
```

끝표시를 따옴표 없이 쓰면 안에서 변수와 명령 치환이 펼쳐진다. nginx 설정처럼 `$`가 많은 글을 쓸 때 하나하나 `\$`로 막기 번거로우면 `<<'EOF'`처럼 끝표시에 따옴표를 붙인다. 그러면 아무것도 펼쳐지지 않는다. `<<-EOF`로 쓰면 각 줄 앞의 탭(공백은 아니다)을 지워 줘서 들여쓴 함수 안에서도 쓸 수 있다.

한 줄만 넣을 때는 here string `<<<`이 짧다.

```bash
read -r host port <<< "10.0.0.5 8080"; echo "host=$host port=$port"
tr a-z A-Z <<< "$name"
wc -c <<< "abc"
printf abc | wc -c
```

```text
host=10.0.0.5 port=8080
SHOP
4
3
```

here string은 끝에 줄바꿈을 하나 붙인다. 그래서 `abc`가 4바이트다. 해시나 서명을 계산할 때 `sha256sum <<< "$secret"`로 하면 줄바꿈까지 들어간 값이 나와서 다른 시스템의 결과와 맞지 않는다. 그런 자리는 `printf '%s' "$secret" | sha256sum`으로 쓴다.

## 파이프는 두 프로세스를 동시에 띄운다

`a | b`는 커널에 파이프 하나를 만들고, a의 1번을 파이프의 쓰는 쪽에, b의 0번을 읽는 쪽에 꽂은 뒤 둘을 동시에 실행한다.

```bash
./fds.sh 9>&1 | cat
```

```text
0 -> /dev/pts/0
1 -> pipe:[105638]
2 -> /dev/pts/0
```

1번만 파이프로 바뀌고 2번은 그대로 터미널이다. 그래서 `cmd | grep error`는 stderr에 찍힌 오류를 거르지 못한다. stderr까지 파이프로 보내려면 `cmd 2>&1 | grep error` 또는 bash의 `cmd |& grep error`를 쓴다. 이번에는 `2>&1`이 파이프 연결 뒤에 처리되어서 2번도 파이프를 받는다.

파이프는 파일이 아니라 커널 안의 작은 버퍼다. 리눅스의 기본 크기는 64KiB다. 쓰는 쪽이 버퍼를 채우면 읽는 쪽이 비울 때까지 멈추고, 읽는 쪽은 버퍼가 비면 쓰는 쪽이 채울 때까지 멈춘다. 1KiB씩 쓰면서 몇 KiB를 썼는지 stderr로 알리는 프로그램을, 아무것도 읽지 않는 `sleep` 앞에 붙였다.

```bash
cat > writer.py <<'EOF'
import os, sys
n = 0
while True:
    os.write(1, b"x" * 1024)          # stdout(파이프)에 1KiB씩 쓴다
    n += 1
    print(f"{n} KiB written", file=sys.stderr, flush=True)
EOF
# 2초 뒤 끊는다. stderr는 파일로 받아 마지막 줄만 본다
timeout 2 sh -c 'python3 writer.py | sleep 5' 2> err.txt; echo "exit=$?"
tail -1 err.txt
```

```text
exit=124
64 KiB written
```

64KiB를 쓰고 멈췄다. 2초 동안 CPU를 쓰지도 않고 그냥 잠들어 있다가 `timeout`에 끊겼다(124). 아래 그림은 이 장면과, 읽는 쪽이 먼저 끝날 때를 이어서 보여 준다.


`yes`는 끝없이 쓰는 프로그램인데 `head`가 두 줄을 읽고 끝나자 SIGPIPE로 멈췄다. 이 덕분에 `big_command | head`가 전체를 다 만들지 않고 일찍 끝난다. 대신 `set -o pipefail`을 켠 스크립트에서는 이 141이 실패로 잡힌다. 그 처리는 [bash 스크립트 글](/posts/bash-scripting)에 있다.

버퍼가 찬다는 사실은 실무에서 두 가지 증상으로 나타난다. 첫째, 자식 프로세스의 stdout과 stderr를 파이프로 받는 프로그램이 한쪽만 읽고 다른 쪽은 끝날 때 읽으려 하면, 자식이 안 읽히는 쪽 버퍼 64KiB를 채우는 순간 서로 기다리며 멈춘다. 둘째, 로그를 받아 가는 쪽(수집기, `tee` 뒤의 느린 디스크)이 느려지면 앱의 `write`가 막혀 요청 처리까지 느려진다. "로그 수집기가 죽었더니 앱이 멈췄다"가 이 경로다.

### 파이프의 오른쪽은 서브셸이다

bash에서 파이프로 이은 명령은 각자 별도 프로세스에서 돈다. 그래서 파이프 안에서 바꾼 변수는 밖에 남지 않는다.

```bash
count=0
printf 'a\nb\nc\n' | while read -r l; do count=$((count+1)); done
echo "pipe: count=$count"
count=0
while read -r l; do count=$((count+1)); done < <(printf 'a\nb\nc\n')
echo "procsub: count=$count"
```

```text
pipe: count=0
procsub: count=3
```

첫 번째 `while`은 서브셸에서 3까지 셌지만 그 서브셸과 함께 사라졌다. 두 번째는 `while`이 현재 셸에서 돌고 입력만 다른 곳에서 받는다. 이 `< <(...)`가 다음에 볼 프로세스 치환이다. 스크립트라면 `shopt -s lastpipe`(작업 제어가 꺼져 있을 때만 동작)로 파이프의 마지막 명령을 현재 셸에서 돌게 할 수도 있다. `while read`가 틀리는 다른 경우(IFS, 마지막 줄의 줄바꿈)는 [조건문과 함수 글](/posts/bash-control-flow-functions)에서 다뤘다.

## sudo echo가 Permission denied를 내는 이유

`/etc`에 설정 한 줄을 쓰려고 sudo를 붙였는데 거절당했다. 일반 사용자 dev로 돌렸다.

```bash
sudo echo "vm.swappiness=10" > /etc/sysctl.d/99-demo.conf; echo "exit=$?"
echo "vm.swappiness=10" | sudo tee /etc/sysctl.d/99-demo.conf; echo "exit=$?"
echo "fs.file-max=100000" | sudo tee -a /etc/sysctl.d/99-demo.conf > /dev/null
sudo sh -c 'echo net.core.somaxconn=4096 >> /etc/sysctl.d/99-demo.conf'
cat /etc/sysctl.d/99-demo.conf
```

```text
-bash: line 1: /etc/sysctl.d/99-demo.conf: Permission denied
exit=1
vm.swappiness=10
exit=0
vm.swappiness=10
fs.file-max=100000
net.core.somaxconn=4096
```

오류를 낸 것이 `sudo`나 `echo`가 아니라 `-bash`라는 점을 보자. `> /etc/...`는 dev 권한의 셸이 sudo를 실행하기 전에 처리한다. 앞 절에서 본 "리다이렉션은 명령보다 먼저"와 같은 이야기다. root가 되는 건 `echo`뿐이고, 파일을 여는 셸은 여전히 dev다.

고치는 방법은 파일을 여는 쪽을 root로 만드는 것이다. `tee`는 stdin을 받아 stdout과 파일 양쪽에 쓰는 명령이라, `sudo tee`로 띄우면 파일을 root가 연다. 덧붙이려면 `-a`, 화면에 다시 찍히는 게 싫으면 `> /dev/null`을 붙인다. 리다이렉션째로 root 셸에게 맡기는 `sudo sh -c '...'`도 되지만 따옴표가 한 겹 더 생겨 변수가 섞이면 헷갈린다. 여러 줄은 here document와 `tee`를 합친다.

```bash
sudo tee /etc/sysctl.d/99-web.conf > /dev/null <<'EOF'
net.core.somaxconn = 4096
net.ipv4.ip_local_port_range = 10240 65535
EOF
```

이 값들이 무엇을 바꾸는지는 [네트워크 한도 글](/posts/linux-network-tuning)에서 다뤘다.

## tee로 화면과 파일에 동시에

`tee`는 파이프 중간에서 흐름을 복사한다. 긴 배포 명령의 출력을 보면서 파일로도 남기고 싶을 때 쓴다.

```bash
./deploy.sh 2>&1 | tee -a deploy-$(date +%F).log
```

이때 종료 코드는 `tee`의 것이라 `deploy.sh`가 실패해도 0이다. 스크립트에서 쓴다면 `pipefail`을 켜거나 `${PIPESTATUS[0]}`을 본다. `tee`도 파이프의 한쪽이라 디스크가 느리면 앞 명령까지 느려진다.

## 프로세스 치환은 출력을 파일 이름처럼 쓴다

어떤 명령은 stdin 하나가 아니라 파일 이름을 여러 개 받는다. `diff`가 대표적이다. 두 서버의 패키지 목록을 비교하려고 임시 파일을 두 개 만드는 대신 프로세스 치환을 쓴다.

```bash
echo <(true)
diff <(printf 'a\nb\n') <(printf 'a\nc\n'); echo "diff exit=$?"
# 실무: 두 서버의 설치 패키지 비교
diff <(ssh web1 dpkg-query -W) <(ssh web2 dpkg-query -W)
```

```text
/dev/fd/63
2c2
< b
---
> c
diff exit=1
```

`<(명령)`은 그 명령을 백그라운드로 띄워 출력을 파이프에 연결하고, 그 파이프를 `/dev/fd/63` 같은 이름으로 바꿔 끼운다. `diff`는 파일 두 개를 연 줄 안다. 반대 방향인 `>(명령)`은 "여기에 쓰면 그 명령의 stdin으로 간다"는 이름을 만든다. bash와 zsh에는 있고 POSIX sh(dash)에는 없다.

## stderr만 따로 모으는 패턴

배치 작업에서 원하는 건 보통 "정상 출력은 로그 파일에, 오류는 로그 파일에도 남기고 따로도 모아서 알림에 쓰기"다. 앞에서 본 것들을 합치면 된다.

stderr만 파이프로 보내고 stdout은 버리려면 순서가 중요하다.

```bash
./cmd.sh 2>&1 > /dev/null | sed 's/^/ERR: /'
```

```text
ERR: err
```

앞의 AlgoTrace를 떠올리면 된다. `2>&1`이 먼저 2번에 파이프를 복사하고, 그다음 1번만 `/dev/null`로 바꿨다. 처음 장면에서 버그였던 순서가 여기서는 의도한 동작이다.

스크립트 전체에 적용하려면 맨 위에서 `exec`로 셸 자신의 표를 바꾼다. `exec`에 명령 없이 리다이렉션만 주면 현재 셸의 fd가 바뀌고 이후 모든 명령이 물려받는다.

```bash
cat > job.sh <<'EOF'
#!/bin/bash
# 이 줄 아래의 stdout은 화면과 job.log에, stderr는 화면과 job.err에 남긴다
exec > >(tee -a job.log) 2> >(tee -a job.err >&2)
echo "start"
ls /nope
echo "done"
EOF
chmod +x job.sh && ./job.sh
cat job.log; echo ---; cat job.err
```

```text
start
ls: cannot access '/nope': No such file or directory
done
start
done
---
ls: cannot access '/nope': No such file or directory
```

`>(tee ...)`가 백그라운드 프로세스라서, 스크립트가 끝난 직후 파일을 읽으면 마지막 줄이 아직 안 써졌을 수 있다. 스크립트 끝에서 바로 그 파일을 메일로 보내야 한다면 프로세스 치환 대신 `{ ...; } > job.log 2> job.err`처럼 블록 단위 리다이렉션을 쓴다.

systemd 서비스나 쿠버네티스 컨테이너로 도는 프로그램은 이런 리다이렉션을 하지 않는 편이 낫다. systemd는 stdout과 stderr를 저널로 받아 우선순위까지 구분해 주고, 쿠버네티스는 컨테이너의 1번과 2번을 노드의 로그 파일로 모은다. 앱이 직접 파일에 쓰면 로테이션과 수집을 따로 챙겨야 한다. 저널에서 읽는 법은 [systemd 글](/posts/linux-systemd-systemctl)에 있다.

## 구멍 세 개와 왼쪽부터

모든 프로세스는 0, 1, 2번 fd를 물려받고, 리다이렉션은 명령이 돌기 전에 셸이 그 표를 왼쪽부터 고치는 일이다. `2>&1`은 그 순간 1번이 가리키는 곳을 복사할 뿐이라 순서가 결과를 바꾼다. 파이프는 1번과 0번을 64KiB 버퍼로 잇고 두 프로세스를 동시에 돌린다. 이 두 문장으로 `sudo echo >`가 실패하는 이유, `cmd | grep`이 오류를 못 거르는 이유, 로그 수집기가 앱을 멈추는 이유가 모두 설명된다. 셸이 명령 줄의 변수와 따옴표를 펼치는 순서는 [bash 확장 글](/posts/bash-expansions-variables)에서 이어진다.

## 면접에서 나올 만한 질문

### stdin, stdout, stderr는 무엇이고 왜 stderr를 따로 두나?

프로세스가 물려받는 0, 1, 2번 파일 디스크립터다. 결과는 stdout으로, 진단 메시지는 stderr로 나눠 두면 `cmd > result.txt`처럼 결과만 파일이나 다음 명령으로 넘기면서 오류는 화면에 볼 수 있다. 둘이 섞이면 파이프 뒤의 프로그램이 오류 메시지를 데이터로 읽어 버린다.

### cmd > log 2>&1과 cmd 2>&1 > log는 무엇이 다른가?

리다이렉션은 왼쪽부터 적용되고 `2>&1`은 그 순간 1번이 가리키는 곳을 2번에 복사한다. 앞의 것은 1번을 log로 바꾼 뒤 복사하니 둘 다 log로 간다. 뒤의 것은 2번이 먼저 터미널을 복사해 가고 1번만 log로 바뀌어서 stderr는 터미널에 남는다.

### sudo echo "x" > /etc/파일이 Permission denied가 나는 이유와 해결책은?

리다이렉션은 sudo가 실행되기 전에 일반 사용자 권한의 셸이 처리하기 때문이다. root로 도는 건 echo뿐이고 파일을 여는 건 일반 사용자다. `echo x | sudo tee /etc/파일`(덧붙이기는 `tee -a`)처럼 파일을 여는 프로그램을 root로 띄우거나, `sudo sh -c '...'`로 리다이렉션째 root 셸에 맡긴다.

### 파이프는 어떻게 동작하나? 버퍼가 차면 무슨 일이 생기나?

커널이 파이프를 만들어 앞 명령의 1번과 뒤 명령의 0번에 꽂고 두 프로세스를 동시에 실행한다. 리눅스 기본 버퍼는 64KiB이고, 차면 쓰는 쪽의 write가 막혀 잠들고 비면 읽는 쪽이 잠든다. 읽는 쪽이 먼저 닫히면 쓰는 쪽은 SIGPIPE를 받아 141로 끝난다. 그래서 느린 로그 수집기가 앱의 쓰기를 막을 수 있다.

### 파이프 안의 while 루프에서 바꾼 변수가 밖에서 사라지는 이유는?

bash는 파이프의 각 명령을 별도 프로세스(서브셸)에서 실행하기 때문이다. 루프가 끝나면 그 서브셸과 함께 변수도 사라진다. `while ... done < <(명령)`처럼 프로세스 치환으로 입력만 받게 하면 루프가 현재 셸에서 돈다. 스크립트에서는 `shopt -s lastpipe`도 쓸 수 있다.

### here document에서 끝표시에 따옴표를 붙이면 무엇이 달라지나?

따옴표 없는 `<<EOF`는 안에서 변수, 명령 치환, 산술 확장이 펼쳐지고, `<<'EOF'`는 한 글자도 펼치지 않고 그대로 넘긴다. `$`가 많은 nginx 설정이나 다른 스크립트를 파일로 쓸 때 따옴표를 붙인다. `<<-`는 줄 앞의 탭을 지워 준다.

### 프로세스 치환 `<(...)`은 언제 쓰나?

명령이 stdin 하나가 아니라 파일 이름을 받을 때 다른 명령의 출력을 넘기려고 쓴다. `diff <(cmd1) <(cmd2)`처럼 임시 파일 없이 두 출력을 비교할 수 있다. bash가 출력을 파이프에 연결하고 `/dev/fd/63` 같은 이름을 넘겨 준다. `>(...)`는 반대로 쓰기용 이름을 만들어 `exec 2> >(tee err.log >&2)` 같은 로그 분기에 쓴다.

### 스크립트에서 stderr만 따로 모으려면?

stderr만 다음 명령으로 보내려면 `cmd 2>&1 > /dev/null | 처리`처럼 2번에 파이프를 먼저 복사하고 1번을 바꾼다. 스크립트 전체라면 맨 위에서 `exec 2> >(tee -a err.log >&2)`로 셸 자신의 2번을 바꾼다. systemd나 쿠버네티스에서 도는 프로그램은 직접 파일로 돌리지 말고 stdout과 stderr에 쓰게 두면 플랫폼이 모아 준다.
