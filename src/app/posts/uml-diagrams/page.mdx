## 말로 하던 설계 리뷰가 길어질 때

주문 취소 기능을 리뷰하는 자리였다. "결제가 끝난 주문을 취소하면 바로 취소가 아니라 환불 대기로 가고, 환불이 끝나야 취소 상태가 되는데, 배송이 시작된 주문은 취소가 안 되고 반품으로 가야 한다"는 설명이 세 번째 반복될 즈음 누군가 화이트보드에 동그라미 다섯 개와 화살표 여섯 개를 그렸다. 질문이 바로 바뀌었다. "배송 중에서 취소로 가는 화살표가 없는 게 맞아요?" 말로는 30분 동안 나오지 않던 질문이다.

그림이 빠른 이유는 빠진 것이 보이기 때문이다. 문장은 있는 것만 말하지만, 상자와 화살표는 없는 화살표를 드러낸다. UML(Unified Modeling Language)은 이런 그림을 누가 그려도 같은 뜻으로 읽히게 모양을 정해 둔 표기법이다. 1990년대 중반 부치(Booch), 럼바우(Rumbaugh), 야콥슨(Jacobson)이 각자의 표기법을 합쳐 만들었고, 지금은 OMG가 표준으로 관리한다. 현재 판은 2.5.1이다.

UML 2.5.1에는 다이어그램이 14종 있다. 구조를 그리는 7종(클래스, 객체, 컴포넌트, 복합 구조, 패키지, 배포, 프로파일)과 행동을 그리는 7종(유스케이스, 활동, 상태 머신, 그리고 상호작용 계열의 시퀀스, 커뮤니케이션, 타이밍, 상호작용 개요)이다. 실무에서 자주 꺼내는 건 그중 다섯 개다. 클래스, 시퀀스, 상태 머신, 유스케이스, 활동. 이 글은 같은 쇼핑몰 주문 예제를 이 다섯 그림으로 차례로 그린다.

시스템 전체를 확대 단계로 나눠 그리는 C4 모델과 결정을 남기는 ADR은 [아키텍처 문서: C4 모델과 ADR](/posts/architecture-docs-c4-adr)에서 다뤘다. C4가 "무엇을 어느 확대 단계에서 그릴지"를 정한다면 UML은 "상자와 화살표가 무슨 뜻인지"를 정한다. 둘은 겹치지 않고 함께 쓴다.

## 클래스 다이어그램은 누가 누구를 아는지 그린다

클래스 다이어그램은 상자 하나가 클래스 하나다. 상자는 세 칸으로 나뉜다. 맨 위에 이름, 가운데 속성, 아래에 연산(메서드)이 들어간다. 이름 앞의 기호는 접근 범위다. `+`는 public, `-`는 private, `#`은 protected, `~`는 package다.

```text
┌──────────────────────────┐
│ Order                    │
├──────────────────────────┤
│ - id: OrderId            │
│ - status: OrderStatus    │
│ - lines: OrderLine[1..*] │
├──────────────────────────┤
│ + addLine(p, qty): void  │
│ + total(): Money         │
│ + cancel(): void         │
└──────────────────────────┘
```

상자보다 중요한 건 상자 사이의 선이다. 선 모양이 여섯 가지쯤 되는데, 실선이냐 점선이냐, 끝에 무엇이 달렸냐로 뜻이 갈린다. 아래 그림은 주문 도메인의 클래스 관계다. 실선 화살표에는 점이 흐르고, 점선은 "알기만 하는" 약한 관계라 멈춰 있다.

선 여섯 개를 하나씩 보면 이렇다.

- 연관(association): 실선. 한 클래스가 다른 클래스를 필드로 들고 있어 언제든 찾아갈 수 있다는 뜻이다. 끝에 열린 화살표가 있으면 그 방향으로만 찾아갈 수 있다(navigability). 선 끝에 `1`, `0..1`, `*`, `1..*` 같은 다중성을 적는다. `Customer 1 — * Order`는 고객 한 명에 주문이 0개 이상이라는 말이다.
- 집합(aggregation): 전체 쪽 끝에 빈 마름모가 달린 실선. "전체와 부분"이지만 부분이 전체 없이도 살아 있다.
- 합성(composition): 전체 쪽 끝에 채운 마름모. 부분의 수명을 전체가 쥐고 있다.
- 의존(dependency): 점선에 열린 화살표. 필드로 들고 있지는 않고 메서드 인자나 지역 변수로 잠깐 쓴다.
- 일반화(generalization): 실선에 빈 삼각형. 상속이다. 삼각형이 부모를 가리킨다.
- 실현(realization): 점선에 빈 삼각형. 인터페이스를 구현한다는 뜻이다.

코드로 옮기면 차이가 더 분명해진다.

```ts
interface Payment {
  pay(amount: number): Promise<void>;
}

class CardPayment implements Payment {          // 실현: 점선 + 빈 삼각형
  async pay(amount: number) {
    const client = new PgClient();              // 의존: 메서드 안에서만 잠깐 쓴다
    await client.approve(amount);
  }
}

class Order {
  private readonly lines: OrderLine[] = [];     // 합성: Order가 만들고 Order와 함께 사라진다
  private coupon?: Coupon;                      // 집합: 쿠폰은 밖에서 받아 오고 다른 주문과 공유될 수 있다

  constructor(private readonly customerId: string) {}  // 연관: 고객을 id로 안다

  addLine(product: Product, qty: number) {
    this.lines.push(new OrderLine(product, qty)); // 줄은 Order 안에서만 생긴다
  }

  applyCoupon(coupon: Coupon) {
    this.coupon = coupon;
  }
}
```

화살표 방향은 "누가 누구를 아는가"다. `Order`는 `OrderLine`을 알지만 `OrderLine`은 `Order`를 모른다면 화살표는 Order 쪽에서 나간다. 양방향 연관은 코드에서도 서로가 서로를 필드로 들고 있다는 뜻이라, 그림에서 양방향 선이 많으면 결합이 강하다는 신호로 읽는다. 결합을 줄이는 원칙은 [결합도와 응집도](/posts/coupling-cohesion-principles)에서, 상속과 인터페이스 자체는 [객체 지향의 네 기둥](/posts/oop-four-pillars)에서 다뤘다.

## 합성과 집합은 수명으로 가른다

면접에서 클래스 다이어그램이 나오면 거의 반드시 묻는 게 이 둘의 차이다. 둘 다 "전체-부분" 관계라 헷갈리는데, 기준은 하나다. 전체가 사라질 때 부분도 같이 사라지느냐.

주문 줄(`OrderLine`)은 주문 밖에서 의미가 없다. 주문을 지우면 줄도 지워진다. 한 줄이 두 주문에 동시에 속할 수도 없다. 이게 합성이다. UML 명세도 합성을 이렇게 정한다. 부분 인스턴스는 한 번에 최대 하나의 합성 객체에만 속하고, 합성 객체가 삭제되면 그 부분도 함께 삭제된다.

쿠폰은 다르다. 주문을 취소해도 쿠폰은 남아서 다른 주문에 다시 쓸 수 있다. 여러 주문이 같은 쿠폰 정의를 가리킬 수도 있다. 이건 집합이다.

재미있는 건 UML 명세가 집합(명세 용어로 shared aggregation)의 정확한 뜻을 정하지 않는다는 점이다. 명세는 "공유 집합의 정확한 의미는 적용 분야와 모델러에 따라 다르다"고 적어 둔다. 그래서 팀마다 집합을 다르게 쓰고, 일부 팀은 아예 집합을 쓰지 않고 연관과 합성만 쓴다. 이 사실을 알고 있으면 면접에서 한 단계 더 깊은 답이 된다.

가비지 컬렉터가 있는 언어에서는 "삭제"가 코드에 드러나지 않으니 차이가 흐려 보인다. 그래도 설계에서는 차이가 실제로 생긴다.

- 저장: 합성인 주문 줄은 주문과 같은 트랜잭션에서 저장하고 지운다. JPA라면 `cascade = ALL`, `orphanRemoval = true`가 어울리는 자리다. 집합인 쿠폰에 cascade 삭제를 걸면 주문 하나 지울 때 다른 고객의 쿠폰까지 사라진다.
- 생성: 합성 부분은 전체가 직접 만든다(`addLine` 안의 `new OrderLine`). 집합 부분은 밖에서 받아 온다(`applyCoupon(coupon)`).
- 경계: DDD에서 애그리거트 하나는 합성으로 묶인 덩어리와 거의 겹친다. 애그리거트 밖의 것은 id로만 참조한다. 이 이야기는 [DDD 전술 패턴](/posts/ddd-tactical-patterns)에 이어진다.

## 시퀀스 다이어그램은 시간을 아래로 흘린다

클래스 다이어그램은 구조를 보여 주지만 "주문 버튼을 누르면 무슨 일이 어떤 순서로 일어나나"는 보여 주지 못한다. 그건 시퀀스 다이어그램의 몫이다. 참여자를 가로로 늘어놓고 각자 아래로 점선(생명선, lifeline)을 내린다. 시간은 위에서 아래로 흐르고, 메시지는 생명선 사이의 화살표다.

이 그림에서 읽어야 할 표기는 세 가지다.

화살촉 모양이 동기와 비동기를 가른다. 동기 호출은 실선에 채운 삼각형 화살촉, 비동기 메시지는 실선에 열린 화살촉, 응답은 점선에 열린 화살촉이다. 위 그림의 결제 승인은 동기, `OrderPaid`는 비동기다. 이 둘을 섞어 그리면 "결제 서비스가 느려지면 주문 API도 느려지나"라는 질문에 그림이 엉뚱한 답을 준다.

생명선 위의 가는 직사각형은 활성 막대(activation, 명세 용어로 execution specification)다. 그 참여자가 일하고 있는 구간이다. 결제 승인을 기다리는 동안 주문 API의 막대가 길게 이어지면, 그 구간 동안 스레드나 커넥션 하나를 붙잡고 있다는 뜻으로 읽는다. 막대가 길고 깊게 겹친 그림은 타임아웃과 연쇄 장애를 먼저 의심할 자리다.

조건과 반복은 결합 조각(combined fragment)으로 감싼다. 왼쪽 위에 연산자 이름이 붙은 상자다. `alt`는 if/else, `opt`는 else 없는 if, `loop`는 반복, `par`는 병렬이다. 결제 실패 경로를 그리고 싶다면 결제 승인부터 응답까지를 `alt` 상자로 감싸고 "승인" 칸과 "거절" 칸을 나눈다.

시퀀스 다이어그램은 장애 회고에서 특히 쓸모가 있다. 로그의 타임스탬프를 생명선 위에 그대로 옮기면 "누가 누구를 기다리다 끊겼는지"가 한눈에 보인다. 서비스 사이의 호출을 자동으로 이런 모양으로 보여 주는 도구가 분산 추적이다([분산 추적](/posts/distributed-tracing)).

## 상태 머신 다이어그램은 가능한 길만 그린다

처음 장면의 화이트보드 그림이 바로 이것이다. 상태 머신 다이어그램은 객체 하나가 거쳐 가는 상태와 그 사이의 전이를 그린다. 둥근 사각형이 상태, 화살표가 전이, 채운 원이 시작점, 테두리 있는 채운 원(과녁 모양)이 끝이다.

전이 화살표에는 `이벤트 [가드] / 동작` 순서로 라벨을 붙인다. 이벤트는 전이를 일으키는 신호, 가드는 참일 때만 전이가 일어나는 조건, 동작은 전이하면서 하는 일이다. 예를 들어 `pay [결제액 = 주문액] / 영수증 발행`은 "결제 이벤트가 왔고 금액이 맞으면 결제됨으로 가면서 영수증을 낸다"는 뜻이다.

상태가 많아지면 복합 상태로 묶는다. "배송" 상태 안에 "포장", "출고", "배송중"을 넣고, 배송 전체에서 나가는 "반품" 화살표를 바깥 테두리에서 한 번만 그린다. 안의 상태 셋에 화살표를 하나씩 그릴 필요가 없다.

## 유스케이스 다이어그램은 시스템의 바깥 경계를 그린다

유스케이스 다이어그램은 가장 단순해 보이고 가장 자주 잘못 쓰이는 그림이다. 막대 인형이 액터(시스템을 쓰는 사람이나 바깥 시스템), 타원이 유스케이스(액터가 시스템으로 이루려는 목표), 큰 사각형이 시스템 경계다.

```text
            ┌──────────── 쇼핑몰 ────────────┐
  고객 ───── │ (주문하기) ──include──▶ (결제하기) │ ───── 결제대행사
            │      ▲                          │
            │      └──extend── (쿠폰 적용)     │
  운영자 ─── │ (주문 취소 승인)                 │
            └─────────────────────────────────┘
```

화살표 두 개가 헷갈린다. `<<include>>`는 기본 유스케이스가 늘 포함하는 공통 단계다. 주문하기는 항상 결제하기를 거친다. 화살표는 기본(주문하기)에서 포함되는 쪽(결제하기)으로 간다. `<<extend>>`는 조건이 맞을 때만 끼어드는 선택 단계다. 쿠폰이 있을 때만 쿠폰 적용이 붙는다. 화살표는 확장하는 쪽(쿠폰 적용)에서 기본(주문하기)으로 간다. 방향이 서로 반대라는 점을 외워 두면 면접에서 덜 당황한다.

흔한 실수는 유스케이스를 기능 목록이나 화면 목록으로 쓰는 것이다. "주문 테이블 조회", "버튼 클릭" 같은 타원이 수십 개 생기면 그건 순서도의 조각이지 목표가 아니다. 유스케이스 이름은 액터가 시스템을 쓰는 이유가 되도록 "동사 + 목적어"로 짓고, 그림에는 경계와 액터만 분명하게 남긴다. 실제 내용은 그림이 아니라 유스케이스 명세(주 흐름, 대안 흐름, 사전·사후 조건)에 글로 쓴다. 그림은 목차 역할만 한다.

이 그림이 값을 하는 건 기획 초반, "이번 범위에 운영자 기능이 들어가나", "결제대행사 쪽 연동은 누가 맡나" 같은 경계 질문을 정리할 때다.

## 활동 다이어그램은 일의 흐름과 갈래를 그린다

활동 다이어그램은 순서도와 닮았다. 둥근 사각형이 행동, 마름모가 분기와 합류, 굵은 막대가 병렬의 시작(fork)과 끝(join)이다. 순서도와 다른 점은 두 가지다. 병렬을 그릴 수 있고, 세로 칸(파티션, 흔히 swimlane이라 부른다)으로 "누가" 하는지를 나눌 수 있다.

주문이 결제된 뒤 창고와 고객센터가 각자 하는 일을 그려 보면 이렇다. 아래는 PlantUML의 활동 다이어그램 문법이다.

```text
@startuml
|주문 API|
start
:결제 승인 확인;
if (재고 있음?) then (예)
  fork
    |창고|
    :포장;
    :출고;
  fork again
    |고객센터|
    :주문 확인 문자;
  end fork
  |주문 API|
  :배송중으로 변경;
else (아니오)
  :환불 요청;
endif
stop
@enduml
```

`fork`와 `end fork` 사이는 동시에 진행된다. `end fork`는 양쪽이 모두 끝나야 다음으로 간다. 그래서 "문자가 늦게 나가면 배송중 변경도 늦어지나"라는 질문에 그림이 예라고 답한다. 정말 기다릴 필요가 없다면 그건 join이 아니라 비동기 이벤트로 그려야 하고, 그 차이를 발견하는 게 이 그림을 그린 값이다.

시퀀스 다이어그램과 헷갈리면 질문을 바꿔 보면 된다. "누가 누구에게 메시지를 보내나"가 궁금하면 시퀀스, "일이 어떤 갈래로 흘러가고 어디서 기다리나"가 궁금하면 활동이다. 활동 다이어그램은 업무 프로세스나 배치 작업처럼 참여자보다 단계가 중요한 곳에 맞는다.

## 그림을 코드처럼 관리한다

그림 도구로 그린 PNG는 코드가 바뀌면 바로 낡는다. 누가 마지막으로 고쳤는지도, 무엇이 바뀌었는지도 알 수 없다. 그래서 요즘은 텍스트로 그림을 쓰고 저장소에 함께 둔다. 많이 쓰는 건 둘이다.

Mermaid는 마크다운 코드 블록 안에 쓰면 GitHub, GitLab, Notion 같은 곳이 바로 그림으로 그려 준다. 별도 설치가 필요 없다는 게 가장 큰 장점이다. 클래스, 시퀀스, 상태 다이어그램을 지원한다.

```text
classDiagram
  Customer "1" --> "*" Order : places
  Order "1" *-- "1..*" OrderLine : contains
  Order o-- Coupon
  CardPayment ..|> Payment
  CardPayment ..> PgClient
```

Mermaid 클래스 문법의 화살표는 위에서 본 선과 일대일로 맞는다. `-->`가 연관, `*--`가 합성, `o--`가 집합, `..>`가 의존, `..|>`가 실현, `<|--`가 상속이다. 상태 다이어그램은 이렇게 쓴다.

```text
stateDiagram-v2
  [*] --> Pending
  Pending --> Paid : pay [amount ok]
  Pending --> Cancelled : cancel
  Paid --> Refunding : cancel
  Refunding --> Cancelled : refunded
  Paid --> Shipped : ship [stock > 0]
  Shipped --> Delivered : deliver
  Delivered --> [*]
  Cancelled --> [*]
```

PlantUML은 자바로 돌아가는 렌더러가 필요하지만 UML 표기를 더 충실하게 지원한다. 위에서 본 활동 다이어그램의 파티션, 유스케이스의 `<<include>>`·`<<extend>>`처럼 Mermaid에 없거나 약한 표기가 있다. Mermaid에는 유스케이스 다이어그램 전용 문법이 없어서, 그 그림이 필요하면 PlantUML을 쓰거나 Mermaid 순서도로 흉내 낸다.

고르는 기준은 간단하다. 문서가 GitHub이나 위키에서 읽히고 표기가 엄격하지 않아도 되면 Mermaid, 표기가 정확해야 하고 CI에서 이미지를 만들어 낼 수 있으면 PlantUML이다. 어느 쪽이든 그림 소스는 그 그림이 설명하는 코드 근처에 두고, 코드를 바꾸는 PR에서 그림도 같이 고친다. 리뷰에 묶어 두는 방법은 C4·ADR 글의 마지막 부분과 같다.

## 다섯 개 중 무엇을 그릴까

다섯 그림은 서로 다른 질문에 답한다. 어떤 질문을 받았는지 먼저 정하면 그림은 따라 나온다.

- "이 시스템은 누가 쓰고 범위가 어디까지인가" → 유스케이스
- "이 클래스들은 서로 얼마나 엮여 있나, 무엇이 무엇을 소유하나" → 클래스
- "요청 하나가 어떤 순서로 누구를 거치고, 어디서 기다리나" → 시퀀스
- "이 객체는 어떤 상태가 될 수 있고, 어디서 어디로는 못 가나" → 상태 머신
- "일이 어떤 갈래로 흐르고, 무엇이 동시에 일어나나" → 활동

실무에서 가장 자주, 그리고 가장 값있게 쓰는 건 시퀀스와 상태 머신이다. 둘 다 코드만 읽어서는 보이지 않는 것(시간 순서와 막힌 길)을 보여 주기 때문이다. 클래스 다이어그램은 IDE가 만들어 주는 경우가 많고, 손으로 그린다면 클래스 전체가 아니라 리뷰할 관계 몇 개만 그린다.

UML을 배우다 보면 표기를 전부 지켜야 할 것 같은 압박이 생기고, 화살촉 모양 하나 틀릴까 봐 그림을 미루게 된다. 그런데 화이트보드 그림의 목적은 질문을 끌어내는 것이라, 표기가 조금 틀려도 범례 한 줄이면 충분하다. 표기를 엄격하게 지켜야 하는 건 그림이 계약 문서처럼 오래 남거나 코드 생성에 쓰일 때 정도다.

## 그림이 거짓말하는 순간

그림은 코드가 아니라서 틀려도 컴파일 에러가 나지 않는다. 자주 보는 실수를 모아 두면 이렇다.

- 모든 클래스를 한 장에 넣는다. 상자가 30개를 넘으면 아무도 읽지 않는다. 질문 하나에 그림 하나로 나눈다.
- 동기와 비동기를 같은 화살표로 그린다. 시퀀스 다이어그램에서 메시지 큐를 거치는 흐름을 채운 화살촉으로 그리면, 큐가 막혀도 API가 멀쩡한 이유를 그림으로 설명할 수 없다.
- 합성을 남발한다. 다른 애그리거트의 객체를 합성으로 그리고 그대로 cascade 삭제를 걸면, 그림대로 구현했는데 데이터가 사라진다.
- 상태 머신에서 예외 경로를 빼먹는다. 결제 타임아웃, 환불 실패처럼 드문 이벤트가 오면 어디로 가는지 그리지 않으면, 코드에서도 그 경로가 비어 있을 확률이 높다.
- 그린 날짜가 없다. 그림 아래에 기준 커밋이나 날짜를 적어 두면 낡은 그림을 믿는 일이 줄어든다.

## 면접에서 나올 만한 질문

### UML이 무엇이고 실무에서 어떤 다이어그램을 주로 쓰나요?

UML은 소프트웨어 구조와 행동을 그리는 표준 표기법으로, OMG가 관리하고 2.5.1 기준 14종의 다이어그램이 있다. 구조 계열 7종, 행동 계열 7종으로 나뉜다. 실무에서는 클래스, 시퀀스, 상태 머신, 유스케이스, 활동 다섯 개를 주로 쓰고, 그중에서도 시간 순서를 보여 주는 시퀀스와 가능한 전이를 보여 주는 상태 머신이 리뷰와 장애 분석에서 가장 자주 쓰인다.

### 클래스 다이어그램에서 연관, 의존, 실현은 어떻게 구분하나요?

연관은 실선으로, 한 클래스가 다른 클래스를 필드로 들고 계속 참조하는 관계다. 의존은 점선에 열린 화살표로, 메서드 인자나 지역 변수로 잠깐 쓰는 약한 관계다. 실현은 점선에 빈 삼각형으로, 인터페이스를 구현한다는 뜻이다. 실선에 빈 삼각형은 상속(일반화)이다.

### 합성과 집합의 차이는 무엇인가요?

부분의 수명을 전체가 쥐고 있으면 합성, 부분이 전체 없이도 살아 있고 공유될 수 있으면 집합이다. 주문을 지우면 주문 줄도 지워지니 합성이고, 쿠폰은 주문이 사라져도 남으니 집합이다. 합성은 채운 마름모, 집합은 빈 마름모를 전체 쪽에 붙인다. UML 명세는 집합의 정확한 의미를 모델러에게 맡겨 두어서, 팀에 따라 집합을 쓰지 않고 연관과 합성만 쓰기도 한다.

### 합성과 집합의 차이가 코드에서는 어떻게 드러나나요?

가비지 컬렉터가 있는 언어에서도 생성과 저장에서 차이가 난다. 합성 부분은 전체가 직접 만들고 같은 트랜잭션에서 저장·삭제하며, JPA라면 cascade와 orphanRemoval이 어울린다. 집합 부분은 밖에서 받아 오고 id로 참조하며 cascade 삭제를 걸지 않는다. 이 구분을 틀리면 주문 하나를 지울 때 공유된 쿠폰까지 지워지는 버그가 생긴다.

### 시퀀스 다이어그램에서 동기 메시지와 비동기 메시지는 어떻게 다르게 그리나요?

동기 호출은 실선에 채운 화살촉, 비동기 메시지는 실선에 열린 화살촉, 응답은 점선으로 그린다. 동기 호출 동안에는 보낸 쪽의 활성 막대가 이어져서 그동안 자원을 붙잡고 있다는 걸 보여 준다. 메시지 큐를 거치는 흐름을 동기로 그리면 장애 전파 경로를 잘못 읽게 된다.

### 상태 머신 다이어그램의 전이 라벨은 어떻게 읽나요?

`이벤트 [가드] / 동작` 순서로 읽는다. 이벤트가 오고 가드 조건이 참일 때만 전이가 일어나며, 전이하면서 동작을 실행한다. 가드가 거짓이면 상태는 그대로다. 그림에 없는 전이는 일어날 수 없다는 뜻이라, 막아야 할 길이 정말 막혀 있는지 리뷰할 때 쓴다.

### 유스케이스의 include와 extend는 어떻게 다른가요?

include는 기본 유스케이스가 항상 포함하는 공통 단계이고, 화살표가 기본에서 포함되는 쪽으로 간다. extend는 조건이 맞을 때만 끼어드는 선택 단계이고, 화살표가 확장하는 쪽에서 기본으로 간다. 주문하기가 결제하기를 항상 거치면 include, 쿠폰이 있을 때만 쿠폰 적용이 붙으면 extend다.

### UML과 C4 모델은 어떤 관계인가요? 그림은 어떻게 관리하나요?

UML은 상자와 화살표의 뜻을 정하는 표기법이고, C4는 무엇을 어느 확대 단계에서 그릴지 정하는 방법이라 함께 쓴다. C4의 코드 단계는 UML 클래스 다이어그램으로, 컨테이너 사이의 복잡한 흐름은 UML 시퀀스로 보충한다. 그림은 Mermaid나 PlantUML 같은 텍스트로 써서 코드 옆에 두고, 코드를 바꾸는 PR에서 같이 고쳐 낡지 않게 한다.
