## 가입 버튼을 바꿨는데 아무도 답하지 못한다

지난달 가입 버튼 문구를 "무료로 시작"에서 "30초 만에 가입"으로 바꿨다. 회의에서 누군가 묻는다. "그래서 효과 있었어요?" 대시보드를 열어 보니 `signup_click`, `SignUpClicked`, `btn_signup` 세 이벤트가 있다. 하나는 웹, 하나는 iOS 앱, 하나는 작년에 인턴이 넣은 것이다. 셋을 더해야 하는지, 겹치는지 아무도 모른다. 가입 완료 이벤트는 아예 없어서 "버튼을 누른 사람"만 셀 수 있다.

이런 상태에서는 실험을 해도 판정할 숫자가 없다. A/B 테스트에서 표본을 어떻게 나누고 언제 판정하는지는 [A/B 테스트와 피처 플래그](/posts/ab-testing)에 정리했다. 이 글은 그보다 앞 단계를 다룬다. 무엇을 잴지 정하고, 그걸 이벤트로 어떻게 남기고, 남은 이벤트로 퍼널과 리텐션을 어떻게 계산하는지. 그리고 그 숫자에서 무엇이 빠져 있는지.

## 결과, 행동, 행위자를 먼저 적는다

"가입을 늘리자"는 목표가 아니라 바람이다. 재려면 세 가지를 먼저 적어야 한다.

목표 결과(target outcome)는 비즈니스가 실제로 원하는 변화다. 가입 수가 아니라 "가입하고 7일 안에 첫 프로젝트를 만든 사람의 비율"처럼, 서비스가 가치를 준 순간에 가깝게 잡는다. 가입만 늘고 아무도 안 쓰면 서버 비용만 는다.

목표 행동(target action)은 그 결과를 만들려면 사용자가 해야 하는 구체적인 행동이다. "가입 폼 제출", "템플릿 선택", "첫 프로젝트 저장". 이 행동 하나하나가 나중에 이벤트가 된다.

행위자(target actor)는 그 행동을 하는 사람이 누구인지다. 광고를 보고 처음 온 사람과 동료에게 초대 링크를 받고 온 사람은 같은 가입 화면에서도 전혀 다르게 행동한다. 초대받은 사람은 이미 팀이 있어서 첫 프로젝트를 만들 필요가 없다. 둘을 섞어서 재면 개선이 상쇄되어 보이지 않는다. 그래서 행위자를 구분할 속성(유입 경로, 초대 여부, 기기)을 이벤트에 같이 남긴다.

이렇게 적고 나면 버튼 문구 실험의 질문이 바뀐다. "클릭이 늘었나"가 아니라 "광고로 온 신규 방문자 중 7일 안에 첫 프로젝트를 만든 비율이 늘었나"다. 클릭은 중간 지표일 뿐이다. 문구를 과장하면 클릭은 늘고 가입 완료는 줄 수도 있다.

이름 규칙은 무엇을 고르든 하나로 정하고 지키는 게 전부다. 널리 쓰이는 방식은 "대상 + 과거형 동사"다. Segment가 공개한 전자상거래 명세가 `Product Viewed`, `Order Completed` 같은 이름을 쓴다. 표기는 `Signup Completed`처럼 띄어 쓰든 `signup_completed`처럼 스네이크 표기를 쓰든 상관없지만, 섞이면 도구가 대소문자와 공백까지 다른 이벤트로 본다. 처음 사례의 세 이름이 바로 그렇게 생겼다.

흔한 실수가 몇 가지 있다. 화면 이름을 이벤트에 넣는 것(`Signup Page Button Clicked`)은 화면이 바뀌면 이름도 바꿔야 해서 기록이 끊긴다. 화면은 속성(`screen: "signup"`)으로 뺀다. 값을 이름에 넣는 것(`Plan Pro Selected`, `Plan Free Selected`)도 피한다. 요금제가 늘 때마다 이벤트가 늘어난다. `Plan Selected`에 `plan: "pro"` 속성을 둔다. 반대로 성격이 다른 행동을 하나로 뭉치는 것(`Button Clicked`에 `name` 속성)도 곤란하다. 모든 분석이 속성 필터부터 시작해야 하고, 버튼 이름이 바뀌면 또 끊긴다.

## 트래킹 플랜을 코드보다 먼저 쓴다

트래킹 플랜(tracking plan)은 "어떤 이벤트를, 어떤 속성과 함께, 언제 보내는지"를 적은 목록이다. 스프레드시트로 시작해도 되지만, 커지면 코드가 읽는 데이터로 두는 편이 낫다.

| 이벤트 | 언제 보내나 | 속성 | 보내는 곳 |
|---|---|---|---|
| `Signup Started` | 가입 폼이 처음 보일 때 | `source`, `variant` | 클라이언트 |
| `Signup Completed` | 계정이 실제로 만들어졌을 때 | `method`, `source` | 서버 |
| `Project Created` | 첫 저장이 성공했을 때 | `template`, `isFirst` | 서버 |
| `Template Previewed` | 템플릿 미리보기를 열 때 | `templateId` | 클라이언트 |

"언제 보내나" 칸이 가장 중요하다. `Signup Completed`를 가입 버튼을 누를 때 보내면, 서버에서 이메일 중복으로 실패한 사람까지 가입한 것으로 센다. 성공이 확정되는 곳, 즉 서버에서 계정을 저장한 뒤에 보낸다.

플랜을 타입으로 바꾸면 오타와 빠진 속성을 컴파일러가 잡는다.

```ts
// tracking-plan.ts: 트래킹 플랜을 타입으로 둔다
type TrackingPlan = {
  "Signup Started": { source: "ad" | "organic" | "invite"; variant: string };
  "Template Previewed": { templateId: string };
};

export function track<E extends keyof TrackingPlan>(
  event: E,
  properties: TrackingPlan[E],
) {
  analytics.track(event, properties); // 실제 수집 SDK 호출은 한곳에서만
}

track("Signup Started", { source: "ad", variant: "B" }); // 통과
// track("Signup Start", { source: "ad" }); // 이름 오타와 빠진 variant를 컴파일 에러로 잡는다
```

SDK를 컴포넌트마다 직접 부르지 않고 이 함수 하나로 모으면, 나중에 수집 도구를 바꾸거나 동의 여부를 확인하는 코드를 넣을 자리도 하나가 된다. 서버 쪽에서는 같은 플랜을 JSON 스키마로 만들어 수집 단계에서 검사하고, 플랜에 없는 이벤트는 버리지 않고 따로 모아 경고한다. 버리면 누가 무엇을 잘못 넣었는지 모른다.

이벤트를 바꿀 때도 규칙이 필요하다. 이름을 바꾸면 그 날짜를 기준으로 그래프가 끊긴다. 의미가 바뀌는 수정(가입 완료를 "이메일 인증까지"로 바꾸기)은 이름을 새로 짓고 옛 이벤트와 한동안 같이 보낸다. 같은 이름으로 의미만 바꾸면 지난 숫자와 비교할 수 없는데, 아무도 그 사실을 모른다.

나눠 보면 원칙이 생긴다. 돈, 계정, 저장처럼 결과가 확정되는 이벤트는 서버에서 보낸다. 서버는 차단기의 영향을 받지 않고, 실패를 성공으로 셀 일도 없다. 미리보기를 열었다, 스크롤을 끝까지 내렸다처럼 서버가 모르는 화면 안의 행동만 클라이언트에서 보낸다. 그리고 클라이언트 숫자는 "실제보다 적게 잡힌 숫자"라는 걸 전제로 본다. 서버 가입 수 대비 클라이언트 `Signup Started` 수의 비율을 주기적으로 보면 유실이 갑자기 늘었는지 알 수 있다.

탭을 닫을 때 큐에 남은 이벤트는 `visibilitychange`에서 `document.visibilityState === "hidden"`일 때 보낸다. 모바일 브라우저는 앱을 전환하면 `unload`를 부르지 않고 탭을 정리하는 일이 많아서 `unload`는 믿을 수 없다. 이때 일반 `fetch`는 페이지와 함께 끊길 수 있으니 `navigator.sendBeacon`이나 `fetch`의 `keepalive` 옵션을 쓴다. 두 API의 차이와 크기 제한은 [브라우저에서 HTTP 요청 보내기](/posts/browser-fetch)에 있다.

```ts
// 화면이 가려지는 순간 남은 이벤트를 비운다
document.addEventListener("visibilitychange", () => {
  if (document.visibilityState !== "hidden" || queue.length === 0) return;
  const body = JSON.stringify(queue.splice(0)); // 큐를 비우면서 꺼낸다
  navigator.sendBeacon("/e/collect", body); // 페이지가 닫혀도 브라우저가 대신 보낸다
});
```

시간도 어긋난다. 사용자 기기 시계는 틀릴 수 있다. 수집 서버는 받은 시각을 따로 기록해 두고, 기기 시각이 받은 시각보다 미래이거나 며칠씩 과거면 보정하거나 표시해 둔다. 하루 단위로 자르는 리텐션 계산에서 이 차이가 숫자를 흔든다.

## 퍼널은 단계를 어떻게 정의하느냐가 반이다

퍼널(funnel)은 목표 행동을 순서대로 늘어놓고 각 단계까지 온 사람 수를 센 것이다. 가입 퍼널을 이렇게 잡았다고 하자.

```text
랜딩 페이지 조회     10,000명
가입 폼 시작          2,400명   (이전 단계 대비 24.0%)
가입 완료             1,500명   (62.5%)
첫 프로젝트 생성        600명   (40.0%)
전체 전환율                      6.0%  (600 / 10,000)
```

단계별 전환율을 보면 어디서 사람이 많이 빠지는지 보인다. 여기서는 랜딩에서 폼 시작까지가 24%로 가장 낮다. 버튼 문구가 영향을 줄 수 있는 곳이 바로 이 단계다. 반대로 가입 완료 뒤 첫 프로젝트까지 40%라는 건, 가입한 사람의 절반 이상이 아무것도 만들지 않고 떠난다는 뜻이다. 목표 결과가 "7일 안에 첫 프로젝트"라면 버튼보다 이쪽이 더 큰 일거리일 수 있다.

같은 이벤트로도 정의에 따라 숫자가 달라진다. 결정할 것이 세 가지 있다.

첫째, 세는 단위. 사람 단위로 셀지 세션 단위로 셀지다. 한 사람이 세 번 방문해서 세 번째에 가입했다면, 사람 단위로는 전환 1명이지만 세션 단위로는 3번 중 1번이다. 가입처럼 한 번 하는 행동은 사람 단위가 맞고, 장바구니 담기처럼 반복되는 행동은 세션 단위가 더 맞을 때가 있다.

둘째, 순서. 앞 단계를 거친 뒤에 다음 단계를 해야 센다. 다른 탭에서 폼을 먼저 열어 두고 나중에 랜딩을 본 사람은 "랜딩 → 폼"으로 세지 않는다. 도구마다 "정해진 순서대로"와 "순서 상관없이" 옵션이 있는데, 기본값이 무엇인지 확인하지 않으면 두 팀이 같은 퍼널을 보고 다른 숫자를 말한다.

셋째, 전환 기간(conversion window). 첫 단계 뒤 얼마 안에 끝내야 전환으로 볼지다. 24시간으로 잡으면 이틀 뒤에 돌아와 가입한 사람은 빠진다. 기간을 너무 길게 잡으면 실험 직후에는 아직 기간이 안 끝난 사람이 많아서 최근 날짜의 전환율이 낮게 보인다. 실험 비교에서는 두 무리 모두 같은 기간이 다 지난 사람만 센다.

## 처음 온 날로 묶어 리텐션을 본다

퍼널은 한 번의 여정을 본다. 서비스가 정말 쓸모 있는지는 사람들이 다시 오는지로 본다. 이걸 리텐션(retention)이라고 하고, 같은 시기에 가입한 사람을 한 무리(코호트, cohort)로 묶어서 시간이 지나며 몇 %가 남는지 센다.

왜 묶어야 할까. 전체 주간 활성 사용자 수만 보면 신규 가입이 계속 들어오는 한 숫자가 올라간다. 밑으로 사람이 줄줄 새고 있어도 위에서 더 많이 부으면 수위가 유지되는 것과 같다. 가입 주별로 나눠야 새는 속도가 보인다.

```text
가입 주         가입자   1주 뒤          2주 뒤          3주 뒤
10월 1주        1,200    456 (38.0%)     372 (31.0%)     348 (29.0%)
10월 2주        1,500    645 (43.0%)     540 (36.0%)
10월 3주        1,350    581 (43.0%)
```

읽는 법은 두 방향이다. 가로로 읽으면 한 코호트가 시간에 따라 어떻게 줄어드는지 보인다. 10월 1주 코호트는 1주 뒤 38%에서 3주 뒤 29%로 내려가는데, 2주에서 3주 사이에는 2%p만 줄었다. 곡선이 평평해지기 시작한다는 뜻이고, 이렇게 평평해지는 지점이 있어야 "남는 사람"이 있는 서비스다. 끝까지 0을 향해 내려가면 신규 유입을 계속 사 와야 유지된다.

세로로 읽으면 같은 시점(1주 뒤)을 코호트끼리 비교한다. 10월 2주부터 38%에서 43%로 올랐다. 그 주에 바꾼 게 온보딩이었다면 그 효과를 의심해 볼 수 있다. 다만 이건 시간 비교라서 같은 주에 있었던 다른 일과 섞인다. 원인으로 확정하려면 [A/B 테스트](/posts/ab-testing)로 같은 기간에 나눠야 한다.

"N일째 리텐션"도 정의가 둘이다.

- N일째 정확히(classic): 가입 후 정확히 N일째에 활동한 사람의 비율. 매일 쓰는 서비스(메신저, 게임)에 맞다.
- N일째 이후 언제든(unbounded, rolling): N일째나 그 뒤에 한 번이라도 돌아온 비율. 가끔 쓰는 서비스(여행 예약, 세금 신고)에 맞다.

여섯 명의 활동일이 `[0,1,2,7]`, `[0,1]`, `[0,8]`, `[0]`, `[0,3,7,14]`, `[0,1,30]`이라면, 7일째 정확히 리텐션은 7일째에 온 두 명이라 33.3%다. 7일째 이후 언제든으로 세면 7일, 8일, 14일, 30일에 온 네 명이라 66.7%다. 같은 데이터에서 두 배 차이가 난다. 보고서에 "7일 리텐션 40%"라고만 쓰면 어느 쪽인지 알 수 없으니 정의를 같이 적는다.

"활동"을 무엇으로 볼지도 정한다. 앱을 열기만 한 것까지 세면 푸시 알림을 많이 보낼수록 리텐션이 오른다. 목표 결과와 이어진 행동(프로젝트를 열어 수정했다)을 활동으로 잡아야 숫자가 가치와 같이 움직인다.

## 다변량 테스트는 표본을 몇 배로 먹는다

가입 화면에서 바꾸고 싶은 게 셋이다. 버튼 문구 두 가지, 버튼 색 두 가지, 소셜 로그인 버튼 위치 두 가지. 하나씩 A/B 테스트하면 세 번 돌려야 하니, 한 번에 모든 조합을 시험하고 싶어진다. 이게 다변량 테스트(multivariate test, MVT)다. 2 × 2 × 2 = 8가지 조합을 동시에 나눠 보여 준다.

문제는 표본이다. 기존 전환율 5%에서 5.5%로 오르는 차이를 유의수준 0.05(양측), 검정력 80%로 잡으려면 두 비율 비교 공식으로 한 무리에 31,234명이 필요하다. A/B 테스트는 두 무리니까 모두 62,468명이다.

8가지 조합을 각각 대조군과 비교하면 사정이 달라진다.

```text
설계                     무리 수   비교 횟수   비교 1번의 기준   무리당 인원   전체 인원
A/B                      2         1           0.05              31,234        62,468
조합 8개, 보정 없음      8         7           0.05              31,234        249,872
조합 8개, 본페로니 보정  8         7           0.05 / 7          49,636        397,088
```

보정 없이도 네 배다. 그런데 일곱 번을 비교하면서 매번 기준 0.05를 쓰면, 실제로 아무 효과가 없어도 일곱 중 하나쯤은 우연히 "이겼다"고 나올 확률이 높아진다. 비교마다 기준을 0.05 / 7로 엄격하게 잡는 본페로니(Bonferroni) 보정을 하면 무리당 49,636명이 필요하고, 전체는 A/B의 약 6.4배인 397,088명이 된다. 하루 가입 화면 방문자가 5,000명인 서비스라면 A/B는 2주 안에 끝나지만 이 설계는 80일 가까이 걸린다.

조합을 하나하나 비교하지 않고 요인별 효과만 볼 수도 있다. 문구 효과는 "문구 A가 들어간 네 조합"과 "문구 B가 들어간 네 조합"을 비교하면 되니, 전체 인원을 반씩 쓰는 셈이라 A/B와 비슷한 인원으로 세 요인을 한 번에 본다. 이게 요인 설계(factorial design)의 장점이다. 다만 이건 요인끼리 서로 영향을 주지 않는다는 가정 위에서다. "초록 버튼은 짧은 문구와 함께일 때만 효과가 있다" 같은 상호작용을 잡으려면 차이의 차이를 봐야 해서, 같은 크기의 효과라도 2 × 2 설계 기준으로 주효과보다 네 배의 표본이 필요하다.

그래서 다변량 테스트는 트래픽이 아주 많은 페이지에서, 요인끼리 영향을 주고받을 것 같을 때 고른다. 트래픽이 적다면 효과가 클 것 같은 요인 하나를 먼저 A/B로 보고, 이긴 쪽 위에서 다음 요인을 본다. 모든 조합을 다 돌리지 않고 일부 조합만 골라 주효과를 추정하는 부분 요인 설계(fractional factorial)도 있지만, 어떤 상호작용을 포기할지 미리 정해야 한다. 판정 방법과 엿보기 문제는 A/B와 같으니 [A/B 테스트와 피처 플래그](/posts/ab-testing)를 따른다.

## 동의 배너가 숫자를 바꾼다

유럽 사용자가 있다면 필수가 아닌 쿠키나 기기 저장소를 쓰기 전에 동의를 받아야 한다(ePrivacy 지침과 GDPR). 분석용 쿠키는 보통 필수가 아니다. 그래서 동의 배너에서 거절한 사람의 클라이언트 이벤트는 아예 오지 않거나, 기기를 구분하지 못하는 형태로만 온다. 국내 서비스도 개인정보 보호법에 따라 수집 항목과 목적을 알리고, 맞춤형 광고에 쓰는 행태정보는 따로 다뤄야 한다. 규정 쪽 이야기는 [개인정보와 규정](/posts/data-privacy-compliance)에 정리했다.

분석에 미치는 영향은 두 가지다.

먼저 숫자가 비어 있다. 동의율이 70%면 클라이언트 퍼널의 모든 단계가 대략 30%씩 적게 잡힌다. 단계별 전환율은 비율이라 덜 흔들리지만, 서버에서 센 가입 수와 클라이언트에서 센 폼 시작 수를 섞어 전환율을 만들면 분모만 줄어서 전환율이 부풀려진다. 한 퍼널 안에서는 같은 출처, 같은 동의 상태의 이벤트끼리 계산한다.

다음으로 치우친다. 동의한 사람과 거절한 사람은 같은 사람들이 아니다. 기술에 익숙하고 개인정보에 민감한 사용자가 더 많이 거절할 수 있다. 그러니 동의한 70%의 리텐션이 전체 리텐션이라고 단정할 수 없다. 배너 디자인을 바꿔 동의율이 바뀌면, 제품은 그대로인데 지표가 움직인다. 배너 변경 날짜를 대시보드에 표시해 두는 이유다.

```ts
// 동의 상태를 확인하는 자리를 track 하나로 모은다
export function track<E extends keyof TrackingPlan>(event: E, properties: TrackingPlan[E]) {
  if (!consent.has("analytics")) return; // 동의 전에는 보내지 않는다
  analytics.track(event, properties);
}
```

속성에 개인정보를 넣지 않는 것도 같은 맥락이다. 이메일을 해시해서 넣으면 익명처럼 보이지만, 같은 이메일은 항상 같은 해시가 나오니 다른 데이터와 맞춰 보면 사람을 다시 찾을 수 있다. 법적으로도 가명 정보이지 익명 정보가 아니다. URL에 이메일이나 토큰이 쿼리로 붙는 화면이 있으면 페이지 조회 이벤트가 그 URL을 그대로 수집하니, 수집 전에 쿼리를 걸러 낸다.

## 숫자가 이상할 때 먼저 보는 곳

대시보드의 가입 전환율이 어느 날 반으로 떨어졌다. 제품이 망가졌을 수도 있지만, 측정이 망가졌을 가능성부터 확인한다. 순서는 대개 이렇다.

1. 이벤트 양을 본다. 이벤트별 하루 건수 그래프에서 특정 날짜부터 0이 되거나 절반이 된 게 있는지 본다. 배포 날짜와 겹치면 누군가 이벤트를 지웠거나 이름을 바꿨을 가능성이 크다.
2. 서버 기준값과 비교한다. DB의 실제 가입 수와 `Signup Completed` 수가 같은지 본다. 서버 이벤트가 DB와 다르면 수집 파이프라인 문제, 같은데 클라이언트 이벤트만 줄었으면 브라우저 쪽(SDK 로딩 실패, 차단, 동의 배너 변경) 문제다.
3. 플랫폼별로 나눠 본다. iOS 앱만 줄었다면 앱 업데이트를 의심한다. 한 브라우저만 줄었다면 그 브라우저의 추적 방지 정책 변화나 그 브라우저에서만 나는 스크립트 오류를 본다.
4. 브라우저 개발자 도구 Network 탭에서 수집 요청을 직접 본다. 요청이 아예 없으면 SDK가 안 불렸거나 차단된 것이고, 400 응답이면 스키마 검사에 걸린 것이다.
5. 플랜에 없는 이벤트 모음을 본다. 누군가 `signup_completed`를 소문자로 새로 보내기 시작했다면 거기에 쌓여 있다.

자주 만나는 함정도 있다. 사파리의 추적 방지(ITP)는 자바스크립트로 쓴 쿠키의 수명을 최대 7일로 줄인다. 일주일 넘게 안 온 사람은 다시 오면 새 익명 id를 받으니, 신규 방문자가 실제보다 많아지고 로그인 전 리텐션이 낮게 잡힌다. 로그인한 사용자는 userId로 이어지니 리텐션은 로그인 기준으로 보는 편이 덜 흔들린다. 같은 사람이 휴대폰과 노트북을 쓰면 로그인 전에는 두 사람으로 잡히는 것도 같은 문제다.

## 배운 것을 모아 다음 순서를 정한다

숫자를 다 모았다고 끝이 아니다. 실험 하나가 끝날 때마다 무엇을 바꿨고, 어떤 지표가 얼마나 움직였고, 왜 그렇다고 생각하는지를 짧게 남긴다. 진 실험도 남긴다. 반년 뒤 누군가 같은 문구 실험을 다시 제안할 때 이 기록이 시간을 아낀다.

다음에 무엇을 할지는 퍼널에서 가장 많이 빠지는 단계와 기대 효과, 드는 품을 같이 놓고 고른다. 영향(Impact), 확신(Confidence), 쉬움(Ease)에 점수를 매기는 ICE나 도달 범위(Reach)까지 곱하는 RICE 같은 틀이 있다. 점수 자체가 정답은 아니고, 팀이 같은 기준으로 이야기하게 만드는 도구다. 처음 사례로 돌아가면, 버튼 문구는 24% 단계를 건드리지만 가입 뒤 첫 프로젝트 40% 단계가 목표 결과에 더 가깝다. 이렇게 숫자가 있으면 "버튼부터 고칠까, 온보딩부터 고칠까"를 감이 아니라 근거로 다툰다.

정리하면, 재고 싶은 결과와 행동과 행위자를 먼저 적고, 이름 규칙과 트래킹 플랜으로 이벤트를 한 가지 말로 남기고, 확정된 결과는 서버에서 보낸다. 퍼널과 리텐션은 정의(단위, 순서, 기간, 활동)를 숫자와 함께 적는다. 그리고 그 숫자에는 차단기와 동의 거절로 빠진 사람이 있다는 걸 잊지 않는다.

## 면접에서 나올 만한 질문

### 기능 개선의 효과를 재고 싶을 때 무엇부터 정하나요?

목표 결과, 목표 행동, 행위자를 먼저 정한다. 결과는 클릭 수가 아니라 "가입 7일 안에 첫 프로젝트를 만든 비율"처럼 가치에 가까운 숫자로 잡고, 그 결과로 가는 행동을 이벤트로 정의한다. 행위자를 구분할 속성(유입 경로, 초대 여부)을 함께 남겨야 서로 다른 사용자 집단의 효과가 섞여 상쇄되지 않는다.

### 이벤트 이름은 어떤 규칙으로 짓나요?

"대상 + 과거형 동사"(`Signup Completed`)처럼 하나의 규칙을 정하고 트래킹 플랜으로 관리한다. 화면 이름이나 값을 이벤트 이름에 넣지 않고 속성으로 뺀다. 그래야 화면이 바뀌거나 선택지가 늘어도 이벤트가 끊기거나 늘어나지 않는다. 플랜을 타입이나 스키마로 만들어 오타와 빠진 속성을 개발 중과 수집 단계에서 잡는다.

### 같은 이벤트를 클라이언트와 서버 중 어디서 보내야 하나요?

결제, 가입, 저장처럼 결과가 확정되는 이벤트는 서버에서 보낸다. 서버만 성공 여부를 확실히 알고, 광고 차단기나 탭 닫기로 유실되지 않는다. 화면 안의 행동처럼 서버가 모르는 것만 클라이언트에서 보내고, 클라이언트 숫자는 실제보다 적게 잡힌다는 전제로 본다. 양쪽에서 보낼 때는 eventId를 맞춰 중복을 제거한다.

### 클라이언트 이벤트가 유실되는 이유와 줄이는 방법은요?

광고 차단기가 알려진 분석 도메인을 막고, 큐에 쌓인 이벤트가 전송 전에 탭과 함께 사라지고, 동의하지 않은 사용자는 아예 보내지 않는다. 화면이 숨겨지는 `visibilitychange`에서 `sendBeacon`이나 `keepalive` fetch로 남은 큐를 비우고, 자기 도메인 경로로 수집하면 일부 줄어든다. 그래도 완전히 없앨 수 없으니 서버 기준값과의 비율을 주기적으로 본다.

### 퍼널 전환율이 도구마다 다르게 나오는 이유는요?

정의가 달라서다. 사람 단위인지 세션 단위인지, 단계 순서를 강제하는지, 전환 기간이 얼마인지에 따라 같은 이벤트로도 숫자가 달라진다. 전환 기간이 다 지나지 않은 최근 사용자를 포함하면 최근 전환율이 낮게 보이기도 한다. 그래서 퍼널을 보고할 때는 숫자와 함께 이 정의를 적는다.

### 리텐션을 코호트로 봐야 하는 이유는요?

전체 활성 사용자 수는 신규 유입이 계속되면 사람이 빠르게 빠져나가도 유지되어 보인다. 가입 시기별로 묶으면 한 무리가 시간에 따라 얼마나 남는지(가로)와 개선 전후 코호트의 같은 시점 비교(세로)가 보인다. N일째 정확히와 N일째 이후 언제든은 같은 데이터에서 두 배 가까이 다를 수 있어서 어느 정의인지 함께 밝힌다.

### 다변량 테스트는 A/B보다 표본이 얼마나 더 필요한가요?

조합 수만큼 무리가 늘어나서, 2 × 2 × 2 조합 8개를 각각 대조군과 비교하면 보정 없이도 A/B의 네 배, 본페로니 보정까지 하면 전환율 5%에서 5.5%를 잡는 조건으로 약 6.4배가 필요하다. 요인별 주효과만 보면 A/B와 비슷한 인원으로 되지만 요인끼리 독립이라는 가정이 필요하고, 상호작용을 잡으려면 같은 효과 크기 기준 네 배가 더 든다. 그래서 트래픽이 아주 많은 페이지에서만 고른다.

### 쿠키 동의 배너가 분석 결과에 주는 영향은요?

거절한 사람의 클라이언트 이벤트가 빠져서 숫자가 작아지고, 동의하는 사람과 거절하는 사람의 성향이 달라 결과가 치우친다. 서버 이벤트와 클라이언트 이벤트를 섞어 전환율을 만들면 분모만 줄어서 부풀려질 수 있다. 배너 디자인이 바뀌면 제품 변화 없이 지표가 움직이니 변경 날짜를 기록해 둔다.
