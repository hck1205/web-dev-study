관리자 화면의 주문 목록이 느리다는 이야기가 들어온다. 첫 페이지는 괜찮은데 뒤로 넘길수록 느려지고, 목록 하나를 여는 동안 DB에 쿼리가 수십 개 날아간다. 그런데 어느 쿼리가 문제인지는 아무도 모른다. 응용 코드에는 ORM 호출만 보이고, 실제로 어떤 SQL이 몇 번 나가는지는 숨어 있다.

느린 쿼리를 고치는 일은 순서가 정해져 있다. 먼저 어떤 쿼리가 시간을 먹는지 찾고, 그 쿼리의 실행 계획을 읽고, 원인에 맞게 고친 다음, 고친 뒤의 실행 계획으로 확인한다. 이 글은 그 순서대로 간다.

예제는 [인덱스 글](/posts/db-index)과 같은 쇼핑몰 테이블을 그대로 쓴다. 회원 `users` 10만 명, 상품 `products` 1,000개, 주문 `orders` 100만 건이고, 인덱스는 그 글 끝의 상태에서 출발한다. 기본 키 셋에 `orders (user_id)`, `orders (status, created_at)`, `orders (product_id)`, `users (lower(email))` 유니크 인덱스가 있다. 기준은 Ubuntu 24.04의 PostgreSQL 16이고, 실행 계획은 모두 이 환경에서 실제로 돌린 출력이다. 시간은 장비마다 다르니 자릿수와 `Buffers`(읽은 페이지 수)를 보면 된다.

## 어떤 쿼리가 시간을 먹는지부터 찾는다

PostgreSQL에는 `pg_stat_statements`라는 확장이 있다. 서버가 실행한 쿼리를 모양별로 묶어서 몇 번 돌았는지, 모두 합쳐 얼마나 걸렸는지 세어 둔다. `WHERE id = 42`와 `WHERE id = 43`은 값만 다른 같은 쿼리라서 `WHERE id = $1` 한 줄로 묶인다. 운영 DB라면 가장 먼저 켜 둘 확장이다.

Ubuntu의 PostgreSQL 16 패키지에는 이 확장이 이미 들어 있다. 서버가 시작할 때 미리 올려야 하는 라이브러리라서 재시작이 한 번 필요하다.

```bash
# 지금 미리 올리는 라이브러리 확인 (다른 값이 있으면 아래 명령에 쉼표로 이어 붙인다)
sudo -u postgres psql -c "SHOW shared_preload_libraries;"

# 설정을 바꾼다 (postgresql.auto.conf에 저장된다)
sudo -u postgres psql -c "ALTER SYSTEM SET shared_preload_libraries = 'pg_stat_statements';"

# 라이브러리는 재시작해야 올라온다
sudo systemctl restart postgresql

# 확인
sudo -u postgres psql -c "SHOW shared_preload_libraries;"

# 통계를 볼 DB에서 확장(조회용 뷰)을 만든다
sudo -u postgres psql -d shop -c "CREATE EXTENSION pg_stat_statements;"
```

```text
 shared_preload_libraries
--------------------------
 pg_stat_statements
(1 row)
```

되돌리려면 `ALTER SYSTEM RESET shared_preload_libraries;` 후 다시 재시작한다. 이제 관리자 화면을 이것저것 열어 본다. 주문 목록을 여러 페이지에 걸쳐 50번 열고, 전체 개수와 날짜별 결제 목록도 몇 번 본 다음, 모두 합친 실행 시간이 큰 순서로 본다.

```sql
SELECT calls,                                         -- 실행 횟수
       round(total_exec_time::numeric, 1) AS total_ms, -- 합친 시간
       round(mean_exec_time::numeric, 2)  AS mean_ms,  -- 한 번 평균
       rows,                                          -- 돌려준 행 수 합계
       left(query, 60) AS query
FROM pg_stat_statements
WHERE dbid = (SELECT oid FROM pg_database WHERE datname = current_database())
ORDER BY total_exec_time DESC
LIMIT 5;
```

```text
 calls | total_ms | mean_ms | rows |                            query
-------+----------+---------+------+--------------------------------------------------------------
    50 |    816.1 |   16.32 | 1000 | SELECT id, user_id, product_id, amount, created_at FROM orde
     5 |    109.8 |   21.96 |    5 | SELECT count(*) FROM orders
     3 |    106.0 |   35.33 | 1211 | SELECT id, amount FROM orders WHERE status = $1 AND created_
  1000 |      7.7 |    0.01 | 1000 | SELECT id, email FROM users WHERE id = $1
  1000 |      4.1 |    0.00 | 1000 | SELECT id, name FROM products WHERE id = $1
(5 rows)
```

맨 위의 주문 목록 쿼리가 50번에 816ms를 썼다. 정렬 기준은 `mean_ms`가 아니라 `total_ms`로 잡는다. 한 번에 2초 걸리지만 하루에 한 번 도는 쿼리보다, 16ms씩 초당 수백 번 도는 쿼리가 DB를 더 바쁘게 만든다.

아래 두 줄도 봐야 한다. 회원과 상품을 id 하나로 찾는 쿼리가 각각 1,000번 돌았다. 합친 실행 시간은 7.7ms라 시간 순으로는 맨 아래다. 하지만 이 숫자는 DB 안에서 쓴 시간만 센 것이다. 쿼리 하나마다 응용 서버와 DB 사이를 한 번씩 왕복하는 시간은 여기에 없다. `calls`가 유독 큰 쿼리는 N+1의 흔적이다. 뒤에서 다시 본다.

`ORDER BY calls DESC`, 그리고 `shared_blks_read`(디스크에서 읽은 페이지 수) 순으로도 한 번씩 정렬해 본다. 통계를 새로 모으고 싶을 때는 `SELECT pg_stat_statements_reset();`을 실행한다.

## 느린 쿼리를 로그에 남긴다

`pg_stat_statements`는 모양별 합계라서 "어제 오후 3시에 이 값으로 돈 쿼리" 같은 개별 사례는 남기지 않는다. 그건 로그가 맡는다. 일정 시간을 넘긴 쿼리만 로그에 쓰게 할 수 있다.

```bash
# 100ms 넘게 걸린 쿼리를 로그에 남긴다. 재시작 없이 다시 읽기만 하면 된다
sudo -u postgres psql -c "ALTER SYSTEM SET log_min_duration_statement = '100ms';"
sudo -u postgres psql -c "SELECT pg_reload_conf();"

# Ubuntu의 기본 로그 파일을 따라 읽는다
sudo tail -f /var/log/postgresql/postgresql-16-main.log
```

```text

```

로그에 실행 계획까지 남기고 싶으면 `auto_explain` 확장을 쓴다. `auto_explain.log_min_duration`을 넘긴 쿼리의 계획을 자동으로 로그에 쓴다. 다만 `log_analyze`까지 켜면 모든 쿼리에 시간 측정이 붙어 서버가 느려지니 조심해서 켠다.

MySQL 8에서는 슬로 쿼리 로그가 같은 일을 한다. `SET PERSIST`는 재시작 후에도 값을 유지한다.

```bash
# 100ms 넘는 쿼리를 슬로 쿼리 로그에 남긴다 (MySQL 8)
sudo mysql -e "SET PERSIST slow_query_log = 'ON'; SET PERSIST long_query_time = 0.1;"

# 로그 파일 위치 확인
sudo mysql -e "SHOW VARIABLES LIKE 'slow_query_log_file';"

# 모양별로 묶어 합친 시간 순으로 요약한다
LOG=$(sudo mysql -NBe "SELECT @@slow_query_log_file;")
sudo mysqldumpslow -s t "$LOG" | head -30
```

`long_query_time`을 바꾸면 새로 연결한 세션부터 적용된다. `pg_stat_statements`에 해당하는 것은 `performance_schema.events_statements_summary_by_digest` 테이블이다. 쿼리 모양(digest)별로 횟수와 시간을 모아 둔다.

## 실행 계획은 안쪽부터 읽는다

찾은 쿼리 앞에 `EXPLAIN (ANALYZE, BUFFERS)`를 붙인다. `EXPLAIN`만 쓰면 계획만 보여 주고, `ANALYZE`를 붙이면 실제로 실행해서 시간과 행 수를 함께 보여 준다.

<Callout kind="warning" title="EXPLAIN ANALYZE는 쿼리를 실제로 실행한다">
`UPDATE`, `DELETE`, `INSERT`에 `EXPLAIN ANALYZE`를 붙이면 데이터가 정말로 바뀐다. 계획만 보려면 `EXPLAIN`만 쓰고, 실제 수치가 필요하면 `BEGIN; EXPLAIN ANALYZE UPDATE ...; ROLLBACK;`처럼 트랜잭션으로 감싸 되돌린다. 되돌려도 그동안 잡은 행 잠금은 실제로 걸리니 운영 DB에서는 조용한 시간에 한다.
</Callout>

읽는 순서는 두 가지만 기억하면 된다. 들여쓰기가 깊은 노드가 먼저 실행되고, 결과를 한 단계 바깥 노드로 올린다. 같은 깊이에 노드가 둘이면(조인의 양쪽) 위쪽이 바깥 입력, 아래쪽이 안쪽 입력이다. 그래서 맨 안쪽부터 바깥으로 읽어 나오면서, 노드마다 세 가지를 본다.

어디서 시간이 늘었나. `actual time`의 뒤 숫자가 그 노드까지 걸린 누적 시간이다. 바깥 노드와 안쪽 노드의 차이가 그 노드가 쓴 시간이다. `loops`가 2 이상이면 한 번의 평균이니 곱해서 본다.

어디서 페이지를 많이 읽었나. `Buffers`의 `hit`(메모리에서)과 `read`(디스크에서)를 합친 값이 그 노드가 읽은 페이지 수다. 시간은 캐시 상태에 따라 오르내리지만 페이지 수는 데이터가 같으면 그대로라서, 고치기 전과 후를 비교할 때 더 믿을 만하다.

예상과 실제가 맞나. `rows`가 두 번 나온다. 앞 괄호의 `rows`는 플래너의 예상, `actual` 괄호의 `rows`는 실제다. 열 배 넘게 차이 나면 플래너가 데이터를 잘못 알고 있다는 뜻이다. 아래는 최근 1만 건의 주문을 회원 이메일과 함께 가져오는 쿼리다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, u.email, o.amount
FROM orders AS o
JOIN users AS u ON u.id = o.user_id
WHERE o.id > 990000                        -- 최근 주문 1만 건
  AND o.created_at >= '2026-10-09 18:00';  -- 같은 1만 건을 날짜로도 거른다
```

```text
                                                             QUERY PLAN
-------------------------------------------------------------------------------------------------------------------------------------
 Nested Loop  (cost=0.72..1239.98 rows=109 width=33) (actual time=0.039..18.912 rows=10000 loops=1)
   Buffers: shared hit=30125
   ->  Index Scan using orders_pkey on orders o  (cost=0.42..426.19 rows=109 width=20) (actual time=0.011..2.249 rows=10000 loops=1)
         Index Cond: (id > 990000)
         Filter: (created_at >= '2026-10-09 18:00:00+09'::timestamp with time zone)
         Buffers: shared hit=125
   ->  Index Scan using users_pkey on users u  (cost=0.29..7.47 rows=1 width=29) (actual time=0.001..0.001 rows=1 loops=10000)
         Index Cond: (id = o.user_id)
         Buffers: shared hit=30000
 Planning:
   Buffers: shared hit=165
 Planning Time: 0.513 ms
 Execution Time: 19.609 ms
(13 rows)
```

안쪽부터 본다. `orders` 쪽 `Index Scan`의 예상은 `rows=109`인데 실제는 `rows=10000`이다. 90배 넘게 틀렸다. 이유는 두 조건이 사실 같은 행을 고르기 때문이다. 주문은 시간 순으로 쌓여서 `id > 990000`인 주문이 바로 10월 9일 18시 이후 주문이다. 플래너는 기본적으로 조건끼리 서로 관계없다고 가정하고 확률을 곱한다. 각각 1%씩이니 1% × 1% = 0.01%, 100만 건의 0.01%인 100건 남짓으로 예상했다.

틀린 예상은 계획 선택으로 이어진다. 100건이면 회원을 하나씩 찾아가는 Nested Loop가 싸 보인다. 실제로는 1만 번을 반복했다(`loops=10000`). 회원 인덱스를 1만 번 내려가느라 3만 페이지를 읽었다. 이번엔 회원 테이블이 다 메모리에 있어서 19ms로 끝났지만, 바깥 행이 100만이거나 안쪽이 디스크를 읽어야 했다면 수십 초가 된다. 불필요한 날짜 조건을 빼면 예상이 `rows=10438`로 맞아지고, 플래너는 Hash Join을 고른다.

예상이 틀리는 흔한 원인은 이렇다. 통계가 낡았거나(대량 변경 직후, `ANALYZE`로 해결), 위처럼 컬럼끼리 관련이 있거나, 컬럼에 함수를 씌워 통계를 못 쓰거나(`lower(email)`의 기본 추정 0.5%), 값을 바인딩 파라미터로 넘겨 플래너가 값을 모르는 일반 계획을 쓰는 경우다. `city`와 `zip_code`처럼 같다로 비교하는 컬럼끼리 관련이 있다면 `CREATE STATISTICS ... (dependencies) ON city, zip_code FROM ...`로 그 관계를 알려 줄 수 있다.

## 조인을 처리하는 세 가지 방법

위에서 Nested Loop와 Hash Join이 나왔다. PostgreSQL이 두 테이블을 조인하는 방법은 세 가지이고, 플래너는 양쪽 행 수와 인덱스, 정렬 상태를 보고 고른다.

Nested Loop는 바깥 행 하나마다 안쪽을 한 번씩 찾는다. 바깥이 작고 안쪽 조인 컬럼에 인덱스가 있을 때 가장 빠르다. 결제 대기 주문 213건에 회원 이메일을 붙이면 이렇게 나온다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, u.email, o.amount
FROM orders AS o
JOIN users AS u ON u.id = o.user_id
WHERE o.status = 'pending' AND o.created_at >= '2026-10-06';
```

```text
                                                                   QUERY PLAN
-------------------------------------------------------------------------------------------------------------------------------------------------
 Nested Loop  (cost=0.72..2106.91 rows=214 width=33) (actual time=0.065..3.212 rows=213 loops=1)
   Buffers: shared hit=438 read=338
   ->  Index Scan using orders_status_created_idx on orders o  (cost=0.42..648.57 rows=214 width=20) (actual time=0.041..0.378 rows=213 loops=1)
         Index Cond: ((status = 'pending'::text) AND (created_at >= '2026-10-06 00:00:00+09'::timestamp with time zone))
         Buffers: shared hit=135 read=2
   ->  Index Scan using users_pkey on users u  (cost=0.29..6.81 rows=1 width=29) (actual time=0.013..0.013 rows=1 loops=213)
         Index Cond: (id = o.user_id)
         Buffers: shared hit=303 read=336
 Planning:
   Buffers: shared hit=312
 Planning Time: 0.853 ms
 Execution Time: 3.314 ms
(13 rows)
```

안쪽 `users_pkey` 노드에 `loops=213`이 찍혀 있다. 바깥에서 올라온 213행마다 한 번씩 기본 키로 찾았다. 안쪽에 인덱스가 없다면 213번 모두 `users` 전체를 훑어야 해서, Nested Loop는 바깥이 작아도 재앙이 된다.

Hash Join은 작은 쪽을 통째로 읽어 메모리에 해시 테이블을 만들고(build), 큰 쪽을 한 줄씩 읽으며 해시 테이블에서 짝을 찾는다(probe). 같다(`=`) 조건에만 쓸 수 있고, 양쪽이 크고 정렬돼 있지 않을 때 나온다. 아래 그림은 인덱스 글의 작은 예제 데이터, 주문 5건과 상품 3개로 그 과정을 보여 준다.

`Hash` 노드가 회원 10만 명으로 7MB짜리 해시 테이블을 만들었다. 여기서 볼 줄은 `Batches: 1`이다. 해시 테이블이 `work_mem`(정렬·해시에 쓰는 메모리 한도, 기본 4MB)에 해시 배수(`hash_mem_multiplier`, 기본 2.0)를 곱한 한도 안에 들어가서 한 번에 처리됐다는 뜻이다. 한도를 넘으면 `Batches`가 2, 4, 8로 늘면서 일부를 임시 파일에 썼다 다시 읽는다. 정렬도 같아서, `Sort Method: external merge  Disk: ...`가 보이면 메모리가 모자랐다는 신호다. 그 쿼리를 돌리는 세션에서만 `SET work_mem = '64MB';`처럼 올려 본다. 서버 전체 값을 크게 올리면 연결 수 × 쿼리 안의 정렬·해시 노드 수만큼 메모리를 쓸 수 있어 위험하다.

이 쿼리에 Nested Loop를 강제하면(`SET enable_hashjoin = off; SET enable_mergejoin = off;`) 회원 인덱스를 1만 7천 번 내려가느라 5만 2천 페이지를 읽는다. 이 장비에서는 모든 페이지가 메모리에 있어서 워커 병렬로 28ms가 나왔지만, 읽은 양은 Hash Join(2,140페이지)의 25배다. `enable_*` 설정은 이렇게 다른 계획과 비교해 볼 때만 쓰고, 운영 설정으로 남기지 않는다.

Merge Join은 양쪽을 조인 키 순서로 정렬해 두고 지퍼를 잠그듯 나란히 훑는다. 양쪽이 이미 인덱스로 정렬돼 있거나, 결과를 그 키로 정렬해야 할 때 나온다.

## 뒤 페이지로 갈수록 느려지는 OFFSET

관리자 주문 목록은 최신 주문부터 20건씩 보여 준다. 흔히 이렇게 짠다.

```sql
-- 1페이지
SELECT id, user_id, amount, created_at FROM orders ORDER BY id DESC LIMIT 20 OFFSET 0;
-- 45001페이지
SELECT id, user_id, amount, created_at FROM orders ORDER BY id DESC LIMIT 20 OFFSET 900000;
```

두 번째 계획의 `Index Scan Backward`가 `rows=900020`을 내놓았다. `OFFSET 900000`은 "90만 건을 건너뛰라"는 뜻이지만, DB는 90만 건이 어디서 끝나는지 모른다. 인덱스를 처음부터 90만 20건 읽고, 앞의 90만 건을 버리고, 20건을 준다. 4페이지가 13,333페이지가 됐다.

해결은 "몇 번째부터"가 아니라 "어디부터"로 묻는 것이다. 앞 페이지의 마지막 행 id를 기억했다가 그보다 작은 것부터 20건을 달라고 한다. 이걸 키셋 페이지네이션(keyset pagination) 또는 커서 페이지네이션이라고 부른다. 위의 `OFFSET 900000` 결과의 마지막 행은 id 99981이었다. 그 앞 페이지의 마지막이 100001이었으니 이렇게 쓴다.

OFFSET에는 속도 말고 문제가 하나 더 있다. 사용자가 1페이지를 보는 사이에 새 주문이 3건 들어오면, 2페이지를 `OFFSET 20`으로 가져올 때 1페이지 끝의 3건이 다시 나온다. 반대로 지워지면 건너뛰는 행이 생긴다. 키셋은 "이 id보다 작은 것"이라 새로 들어온 행에 영향을 받지 않는다.

정렬 기준이 유일하지 않은 컬럼이면 동점을 끊는 컬럼을 하나 더 붙인다. 같은 시각에 들어온 주문이 여러 건일 수 있으니 `created_at`만으로는 경계가 모호하다. `(created_at, id)`로 정렬하고, 같은 순서의 복합 인덱스를 만들고, 행 비교로 묻는다.

```sql
CREATE INDEX orders_created_id_idx ON orders (created_at, id);

-- 지난 페이지 마지막 행: created_at = 2025-12-04 17:10:30+09, id = 99981
SELECT id, user_id, amount, created_at FROM orders
WHERE (created_at, id) < ('2025-12-04 17:10:30+09', 99981)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

실행 계획을 보면 `Index Cond: (ROW(created_at, id) < ROW(...))`로 인덱스 안에서 바로 시작점을 찾고 6페이지만 읽었다. 행 비교를 지원하지 않는 DB나 쿼리 빌더라면 같은 뜻을 `created_at < $1 OR (created_at = $1 AND id < $2)`로 풀어 쓴다.

키셋의 대가는 "45001페이지로 바로 가기"를 못 한다는 점이다. 다음, 이전, 더 보기(무한 스크롤)만 된다. 대부분의 목록 화면은 그걸로 충분하다. 페이지 번호가 꼭 필요하면 OFFSET을 쓰되 갈 수 있는 페이지 수에 상한을 둔다. API에서는 마지막 행의 값을 그대로 노출하지 않고 base64 같은 불투명한 커서 문자열로 감싸 주는 경우가 많다.

PostgreSQL은 `IN (...)` 목록을 `= ANY(배열)`로 바꿔 인덱스에서 한 번에 찾는다. 쿼리는 목록, 회원, 상품 세 번이다. 조인은 쿼리가 하나지만 한쪽에 여러 행이 붙는 일대다 관계(주문 하나에 상품 여러 개)면 결과 행이 곱해져 중복 데이터가 많아진다. 그럴 때는 IN 방식이 낫다. IN 목록이 수천 개로 길어지면 SQL 자체가 커지니, 응용에서 배열 하나를 파라미터로 넘기는 `WHERE id = ANY($1)`을 쓰면 쿼리 모양도 하나로 고정된다.

응용 서버의 쿼리 로그에서 N+1을 찾는 함수를 직접 만들어 보자. 쿼리 문자열 목록과 기준 횟수를 받아서, 값만 다르고 모양이 같은 쿼리가 기준 이상 반복되면 그 모양과 횟수를 돌려준다. 문자열과 숫자 값은 `?`로 바꾸고, `IN (?, ?, ?)`처럼 개수만 다른 목록은 `IN (?)` 하나로 본다. `pg_stat_statements`가 쿼리를 묶는 방식을 흉내 낸 것이다.

## EXISTS, IN, JOIN 중 무엇을 쓰나

"상품 7번을 한 번이라도 산 회원"을 찾는다. 세 가지로 쓸 수 있다.

```sql
-- 1. EXISTS: 주문이 하나라도 있으면 참
SELECT u.id, u.email FROM users AS u
WHERE EXISTS (SELECT 1 FROM orders AS o WHERE o.user_id = u.id AND o.product_id = 7);

-- 2. IN: 상품 7번 주문의 user_id 목록에 들어 있으면 참
SELECT u.id, u.email FROM users AS u
WHERE u.id IN (SELECT o.user_id FROM orders AS o WHERE o.product_id = 7);

-- 3. JOIN: 주문과 짝지은 뒤 중복을 없앤다
SELECT DISTINCT u.id, u.email FROM users AS u
JOIN orders AS o ON o.user_id = u.id
WHERE o.product_id = 7;
```

PostgreSQL에서 1과 2는 똑같은 계획이 나온다. 둘 다 세미 조인(semi join: 짝이 하나라도 있으면 왼쪽 행을 한 번만 내보내는 조인)으로 바뀌기 때문이다.


`HashAggregate`가 user_id의 중복을 먼저 없애서(1015 → 1011), 회원 한 명이 한 번만 나온다. JOIN으로 쓰면 상품 7번을 두 번 산 회원이 두 행으로 나오니(1015행) `DISTINCT`가 필요하고, 계획 맨 위에 `Sort`와 `Unique`가 붙는다. 이 데이터에서는 32ms로 세미 조인보다 느렸다. "있는지"만 묻는 거라면 EXISTS나 IN으로 쓰는 게 뜻도 분명하고 계획도 낫다. 오른쪽 테이블의 컬럼이 결과에 필요할 때 JOIN을 쓴다.

부정형에서는 차이가 커진다. "한 번도 주문하지 않은 회원"을 `NOT IN`으로 쓰면 NULL 때문에 함정이 생긴다.

```sql
SELECT 'found' AS result WHERE 3 NOT IN (1, 2, NULL);
```

```text
 result
--------
(0 rows)
```

3은 1도 2도 아닌데 결과가 없다. `3 <> NULL`은 참도 거짓도 아닌 "알 수 없음"이라, 목록에 NULL이 하나라도 있으면 `NOT IN` 전체가 참이 될 수 없다. 서브쿼리 결과에 NULL이 섞이면 결과가 통째로 사라진다. 그리고 이 의미를 지키느라 PostgreSQL은 `NOT IN`을 안티 조인으로 바꾸지 못한다.

```sql
EXPLAIN SELECT count(*) FROM users AS u
WHERE u.id NOT IN (SELECT o.user_id FROM orders AS o);

EXPLAIN SELECT count(*) FROM users AS u
WHERE NOT EXISTS (SELECT 1 FROM orders AS o WHERE o.user_id = u.id);
```

## 한 줄씩 넣지 말고 묶어서 넣는다

쓰기도 같은 원리다. 주문 1만 건을 넣는 방법 네 가지를 같은 서버 안에서 psql로 재 봤다. 인덱스 없는 연습용 테이블을 하나 만들어 쓴다.

```sql
-- orders와 같은 컬럼, 기본값, id 자동 증가만 복사한다 (인덱스는 없다)
CREATE TABLE orders_staging (LIKE orders INCLUDING DEFAULTS INCLUDING IDENTITY);

-- 1. 한 줄씩, 각각 자동 커밋 (1만 번 커밋)
INSERT INTO orders_staging (user_id, product_id, status, amount, created_at) VALUES (1, 1, 'paid', 1000, now());
INSERT INTO orders_staging (user_id, product_id, status, amount, created_at) VALUES (2, 2, 'paid', 2000, now());
-- ... 1만 줄

-- 2. 같은 1만 줄을 BEGIN ... COMMIT 하나로 감싼다 (커밋 1번)

-- 3. 여러 행을 한 문장에 (문장 1개)
INSERT INTO orders_staging (user_id, product_id, status, amount, created_at) VALUES
  (1, 1, 'paid', 1000, now()),
  (2, 2, 'paid', 2000, now()),
  -- ... 1만 행
  (10000, 1000, 'paid', 100000, now());

-- 4. COPY로 CSV 파일을 흘려 넣는다 (psql의 \copy는 클라이언트 쪽 파일을 읽는다)
\copy orders_staging (user_id, product_id, status, amount, created_at) FROM 'orders.csv' WITH (FORMAT csv)
```

```text
1. 한 줄씩 자동 커밋   약 2.7~3.5초
2. 트랜잭션 하나       약 0.75초
3. 여러 행 INSERT      약 0.13초
4. COPY               약 0.06초
```

1과 2의 차이는 커밋 횟수다. 커밋할 때마다 WAL(변경 기록)을 디스크에 확실히 써야(fsync) 해서, 1만 번 커밋은 1만 번 디스크를 기다린다. 2와 3의 차이는 문장 수다. 문장마다 파싱, 계획, 실행 준비를 반복한다. 여기에 응용 서버와 DB 사이의 왕복이 문장마다 붙는다. 위 숫자는 같은 서버 안이라 왕복이 거의 없는 경우이고, 네트워크를 건너면 1번은 왕복 1만 번이 더해진다.

배치는 1,000건 안팎으로 끊어서 넣는다. 한 문장이 너무 크면 파라미터 개수 한도(PostgreSQL 프로토콜은 한 문장에 65,535개)에 걸리고, 실패했을 때 전부 다시 해야 한다. ORM에도 bulk insert 기능이 있는데, JPA의 IDENTITY 키 생성 방식처럼 행마다 id를 받아 와야 하는 설정에서는 배치가 조용히 꺼지기도 하니 실제로 나가는 SQL을 로그로 확인한다.

반대로 큰 UPDATE와 DELETE는 잘게 나눈다. 오래된 주문 1,000만 건을 한 문장으로 지우면, 끝날 때까지 그 행들의 잠금을 쥐고, WAL이 한꺼번에 쏟아져 복제본이 뒤처지고, 실패하면 처음부터 되돌린다. PostgreSQL의 `DELETE`에는 `LIMIT`이 없어서 서브쿼리로 묶음을 고른다.

```sql
-- 5,000건씩 지운다. 0건이 나올 때까지 응용이나 스크립트에서 반복한다
DELETE FROM orders_staging
WHERE id IN (
  SELECT id FROM orders_staging
  WHERE status = 'paid'
  ORDER BY id
  LIMIT 5000
);
```

```text
DELETE 5000
```

묶음 사이에 잠깐 쉬어 주면 autovacuum과 복제가 따라올 시간이 생긴다. MySQL은 `DELETE ... LIMIT 5000`을 바로 쓸 수 있다. 행마다 다른 값으로 바꿔야 하는 UPDATE는 `VALUES` 목록과 조인해서 한 문장으로 만든다.

```sql
-- 주문 세 건의 상태를 한 번에 바꾼다
UPDATE orders AS o
SET status = v.status
FROM (VALUES (6, 'delivered'), (7, 'delivered'), (8, 'cancelled')) AS v(id, status)
WHERE o.id = v.id;
```

```text
UPDATE 3
```

## 오래 열린 트랜잭션은 청소를 막는다

느린 쿼리만 문제가 되는 건 아니다. 아무것도 안 하면서 열려 있는 트랜잭션도 문제다. 응용 코드가 `BEGIN`을 하고 외부 API를 부르거나 사용자 입력을 기다리는 동안 트랜잭션이 열려 있는 경우다.

PostgreSQL의 UPDATE와 DELETE는 옛 버전의 행(dead tuple)을 남긴다. 이걸 치우는 게 VACUUM인데, 아직 옛 버전을 볼 수도 있는 트랜잭션이 하나라도 열려 있으면 못 치운다. 다른 세션에서 `BEGIN; SELECT txid_current();`만 해 두고 가만히 둔 상태에서, 1만 행을 고치고 VACUUM을 돌려 봤다.

```sql
UPDATE orders_staging SET amount = amount + 1;  -- 1만 행 수정 → 옛 버전 1만 개
VACUUM (VERBOSE) orders_staging;
```

```text
INFO:  vacuuming "shop.public.orders_staging"
INFO:  finished vacuuming "shop.public.orders_staging": index scans: 0
pages: 0 removed, 281 remain, 188 scanned (66.90% of total)
tuples: 0 removed, 24405 remain, 10000 are dead but not yet removable
removable cutoff: 31379, which was 2 XIDs old when operation ended
```

`10000 are dead but not yet removable`가 그 줄이다. 옛 버전 1만 개가 남았고, 하나도 못 치웠다(`0 removed`). 이 상태가 몇 시간 이어지면 테이블과 인덱스가 계속 부풀고, 쿼리가 읽어야 할 페이지가 늘어난다. 범인은 `pg_stat_activity`에서 찾는다.

```sql
-- 트랜잭션이 열린 지 오래된 순서
SELECT pid, state, now() - xact_start AS xact_age, backend_xid, left(query, 30) AS query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL AND pid <> pg_backend_pid()
ORDER BY xact_start;
```

```text
 pid  |        state        |    xact_age    | backend_xid |         query
------+---------------------+----------------+-------------+------------------------
 4718 | idle in transaction | 00:00:05.02598 |       31379 | SELECT txid_current();
(1 row)
```

`idle in transaction`은 트랜잭션을 열어 둔 채 아무 쿼리도 안 하고 있다는 뜻이다. `query` 열은 지금 실행 중인 쿼리가 아니라 마지막으로 실행한 쿼리다. 급하면 `SELECT pg_terminate_backend(4718);`로 그 연결을 끊는다. 이런 트랜잭션은 잠금도 쥐고 있어서, 그 행을 고치려는 다른 요청이 줄줄이 기다리게 만든다.

근본 해결은 트랜잭션 안에서 DB 일만 하는 것이다. 외부 API 호출, 파일 업로드, 메일 발송은 트랜잭션 밖으로 뺀다. 그리고 안전장치로 한도를 건다. 이건 바로 다음 이야기다.

## 끝나지 않는 쿼리에 한도를 건다

PostgreSQL은 기본으로 쿼리 시간에 제한이 없다. 실수로 만든 무거운 쿼리가 30분씩 돌며 연결과 CPU를 잡아도 아무도 끊지 않는다. 응용이 쓰는 계정에 한도를 걸어 둔다.

```sql
-- 이 계정의 쿼리는 3초 넘으면 취소한다
ALTER ROLE app SET statement_timeout = '3s';
-- 잠금을 5초 넘게 기다리면 포기한다
ALTER ROLE app SET lock_timeout = '5s';
-- 트랜잭션을 연 채 60초 넘게 놀면 연결을 끊는다
ALTER ROLE app SET idle_in_transaction_session_timeout = '60s';
```

역할에 건 설정은 새로 연결할 때부터 적용된다. 실제로 걸리면 이렇게 나온다.

```sql
SET statement_timeout = '100ms';
SELECT id, user_id, amount FROM orders ORDER BY id DESC LIMIT 20 OFFSET 900000;
```

```text
ERROR:  canceling statement due to statement timeout
```

```text
FATAL:  terminating connection due to idle-in-transaction timeout
server closed the connection unexpectedly
	This probably means the server terminated abnormally
	before or while processing the request.
```

두 번째는 `idle_in_transaction_session_timeout`이 놀고 있던 연결을 끊은 뒤, 그 연결로 다음 쿼리를 보냈을 때 psql이 받은 메시지다. 응용 쪽 커넥션 풀은 끊긴 연결을 버리고 새로 맺으면 된다.

배치 작업이나 마이그레이션처럼 오래 걸리는 게 정상인 일은 별도 계정을 쓰거나, 그 세션에서만 `SET statement_timeout = 0;`으로 푼다. 한도는 응용의 요청 타임아웃보다 짧게 잡는다. 응용이 5초 만에 포기한 요청의 쿼리가 DB에서 계속 돌면 아무도 받지 않을 결과를 계산하는 셈이다. MySQL에서는 `max_execution_time`(밀리초, SELECT에만 적용)과 `innodb_lock_wait_timeout`(초)이 비슷한 역할을 한다.

## 연결은 풀로 나눠 쓴다

PostgreSQL은 연결 하나마다 서버 프로세스 하나를 띄운다. 연결을 맺을 때 프로세스를 만들고 인증하는 비용이 들고, 프로세스마다 메모리를 따로 쓴다. 기본 `max_connections`는 100이다. 응용 서버 20대가 각자 풀을 20개씩 잡으면 400개가 되어 연결이 거부되거나, 허용치를 올려도 코어 수보다 훨씬 많은 프로세스가 CPU를 두고 다투느라 전체가 느려진다.

그래서 응용과 DB 사이에 PgBouncer 같은 연결 풀러를 둔다. 응용은 PgBouncer에 수백 개를 연결하고, PgBouncer는 실제 DB 연결 수십 개를 돌려 가며 쓴다.

```bash
# Ubuntu에 설치한다
sudo apt install -y pgbouncer

# 설정 파일
sudo nano /etc/pgbouncer/pgbouncer.ini
```

```text
[databases]
shop = host=127.0.0.1 port=5432 dbname=shop

[pgbouncer]
listen_addr = 127.0.0.1
listen_port = 6432
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt
pool_mode = transaction
default_pool_size = 20
max_client_conn = 1000
```

`pool_mode = transaction`은 트랜잭션이 끝나면 DB 연결을 풀에 돌려준다. 가장 효율이 좋지만, 같은 클라이언트의 다음 트랜잭션이 다른 DB 연결로 갈 수 있다. 그래서 세션에 남는 상태가 깨진다. 트랜잭션 밖에서 건 `SET`, 세션 단위 advisory lock, `LISTEN`, 임시 테이블 같은 것들이다. prepared statement는 PgBouncer 1.21부터 `max_prepared_statements` 설정으로 트랜잭션 모드에서도 쓸 수 있다. 응용은 `6432` 포트로 접속하게 바꾸고, 응용 쪽 풀 크기와 PgBouncer의 `default_pool_size`를 함께 맞춘다. 풀 크기는 크다고 좋은 게 아니라, DB 코어 수의 몇 배 정도 작은 값에서 시작해 대기 시간을 보며 조정한다.

## 느린 쿼리를 고치는 순서

`pg_stat_statements`를 합친 시간과 호출 횟수로 정렬해 범인을 고르고, 그 쿼리에 `EXPLAIN (ANALYZE, BUFFERS)`를 붙여 안쪽부터 읽는다. 예상 행 수와 실제가 크게 다르면 통계와 조건부터 보고, `Rows Removed by Filter`가 크면 인덱스나 sargable하지 않은 조건을, `loops`가 크면 조인 방법이나 N+1을, 버리는 행이 많은 OFFSET이면 키셋을 의심한다. 고친 뒤에는 같은 명령으로 `Buffers`가 줄었는지 확인한다. 쿼리 하나하나보다 왕복 수, 커밋 수, 트랜잭션 길이 같은 바깥쪽 비용이 더 클 때가 많다는 것도 같이 기억해 둔다.

## 면접에서 나올 만한 질문

### 느린 쿼리는 어떻게 찾나요?

PostgreSQL이면 `pg_stat_statements`로 쿼리 모양별 호출 수와 누적 실행 시간을 보고, 누적 시간이 큰 순서로 고른다. 개별 사례는 `log_min_duration_statement`로 일정 시간을 넘긴 쿼리를 로그에 남겨 찾고, 필요하면 `auto_explain`으로 계획까지 남긴다. MySQL은 슬로 쿼리 로그와 `performance_schema`의 digest 요약을 쓴다. 호출 수가 비정상적으로 많은 짧은 쿼리는 N+1 신호라서 횟수로도 정렬해 본다.

### EXPLAIN ANALYZE 출력에서 무엇을 보나요?

안쪽 노드부터 바깥으로 읽으면서 어느 노드에서 시간과 `Buffers`가 크게 늘었는지 본다. 예상 `rows`와 실제 `rows`가 열 배 넘게 다르면 통계가 낡았거나 조건 사이에 상관관계가 있다는 뜻이고, 틀린 예상은 잘못된 조인 방법으로 이어진다. `Rows Removed by Filter`가 크면 인덱스가 없거나 조건이 인덱스를 못 쓰는 형태다. `loops`가 크면 시간에 곱해서 본다. DML에 쓸 때는 실제로 실행되니 트랜잭션으로 감싸 롤백한다.

### Nested Loop, Hash Join, Merge Join은 언제 쓰이나요?

Nested Loop는 바깥 행 하나마다 안쪽을 찾는 방식이라, 바깥이 작고 안쪽 조인 컬럼에 인덱스가 있을 때 가장 빠르다. Hash Join은 작은 쪽으로 해시 테이블을 만들고 큰 쪽으로 찾는 방식으로, 양쪽이 크고 같다 조건일 때 쓰이며 `work_mem`을 넘으면 디스크로 나뉜다(`Batches`). Merge Join은 양쪽이 조인 키로 정렬돼 있을 때 나란히 훑는다. 플래너가 행 수를 잘못 예상하면 큰 입력에 Nested Loop를 고르는 사고가 난다.

### OFFSET 페이지네이션은 왜 느려지고, 어떻게 고치나요?

`OFFSET n`은 앞의 n행을 실제로 읽고 버리기 때문에 페이지가 뒤로 갈수록 읽는 양이 늘어난다. 예제에서 `OFFSET 900000`은 90만 20행을 읽어 13,333페이지를 썼다. 앞 페이지 마지막 행의 키를 기억해 `WHERE id < 마지막 id ORDER BY id DESC LIMIT 20`처럼 묻는 키셋 페이지네이션으로 바꾸면 어느 페이지든 몇 페이지만 읽는다. 정렬 키가 유일하지 않으면 `(created_at, id)`처럼 동점을 끊는 컬럼을 붙이고 같은 순서의 인덱스를 만든다. 대신 임의 페이지로 바로 가는 기능은 포기한다.

### N+1 문제가 무엇이고 어떻게 해결하나요?

목록을 쿼리 하나로 가져온 뒤, 행마다 연관 데이터를 다시 쿼리해서 1 + N번 왕복하는 문제다. ORM의 지연 로딩에서 흔하고, 개별 쿼리는 빨라 슬로 로그에 안 잡히지만 왕복 시간이 행 수만큼 쌓인다. 조인으로 한 번에 가져오거나, id를 모아 `WHERE id = ANY($1)` 한 번으로 가져오는 eager loading으로 고친다. 일대다 관계를 조인하면 결과 행이 곱해지니 그때는 IN 방식이 낫다.

### 큰 테이블에서 COUNT(*)가 느린 이유와 대안은요?

PostgreSQL과 InnoDB는 MVCC 때문에 트랜잭션마다 보이는 행이 달라서, 행 수를 따로 저장해 두지 못하고 매번 센다. 인덱스만 훑어도 100만 행이면 수십 ms다. 정확한 값이 필요 없으면 `pg_class.reltuples`나 `EXPLAIN`의 예상 행 수를 쓰고, 다음 페이지 여부만 필요하면 `LIMIT n+1`로 판단한다. 정확한 값이 자주 필요하면 별도 집계 테이블을 두되 갱신 경합을 고려한다.

### NOT IN 대신 NOT EXISTS를 쓰라는 이유는요?

서브쿼리 결과에 NULL이 하나라도 있으면 `x NOT IN (...)`은 참이 될 수 없어 결과가 통째로 사라진다. 이 의미 때문에 PostgreSQL은 `NOT IN`을 안티 조인으로 바꾸지 못하고, 결과가 메모리에 안 들어가면 행마다 서브쿼리를 훑는 계획이 된다. 예제에서 예상 비용이 6억 4천만 대 2만 2천으로 갈렸다. `NOT EXISTS`는 NULL 문제가 없고 안티 조인으로 바뀐다.

### 운영 DB에서 오래 열린 트랜잭션이 왜 문제인가요?

열린 트랜잭션이 볼 수 있는 옛 버전의 행은 VACUUM이 치우지 못해서 테이블과 인덱스가 계속 부푼다. 그 트랜잭션이 쥔 잠금 때문에 다른 쓰기가 줄줄이 기다리기도 한다. `pg_stat_activity`에서 `idle in transaction` 상태와 `xact_start`로 찾고, `idle_in_transaction_session_timeout`과 `statement_timeout`으로 한도를 건다. 근본적으로는 트랜잭션 안에서 외부 API 호출 같은 DB 밖의 일을 하지 않는다.
