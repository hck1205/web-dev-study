문자열 두 개를 받았다. 짧은 쪽 글자를 아무렇게나 섞은 것 중 하나가 긴 쪽 안에 이어 붙어 있는지 묻는다. 순열(글자 순서를 바꾼 것)이라는 말 때문에 순열을 다 만들어 보고 싶어지는데, 그 길로 가면 길이 10만 넘어도 끝나지 않는다. 이 문제는 "순서는 상관없고 글자 개수만 같으면 된다"를 알아채는 순간 길이가 정해진 창 문제로 바뀐다.

창을 미는 기본 틀과 글자별 개수 배열은 [슬라이딩 윈도 패턴](/posts/sliding-window-pattern)의 "길이가 정해진 창"에서 다뤘다. 거기서 본 애너그램 위치 찾기(438번)와 이 문제는 사실상 같은 문제라, 이 글은 그 틀을 반복하지 않고 그 위에서 할 수 있는 것들을 끝까지 판다. 순열을 모두 만드는 풀이부터 창마다 정렬, 창마다 다시 세기, 26칸 비교 창, 일치 칸 수 하나로 끝내는 창, 그리고 빚을 갚는 가변 창까지 여섯 가지다. 문제 원문은 [LeetCode 567](https://leetcode.com/problems/permutation-in-string/)이다. 코드는 Node.js 22, Python 3.13, Java로 모두 돌려 봤다.

## 섞은 s1이 s2 안에 붙어 있나

소문자로만 된 문자열 `s1`, `s2`가 주어진다. `s1`의 글자 순서를 바꿔서 만들 수 있는 문자열 가운데 하나라도 `s2`의 부분 문자열(이어진 구간)로 나타나면 `true`, 아니면 `false`를 돌려준다.

풀이 선택에 영향을 주는 조건만 추리면 이렇다.

- 두 문자열 길이는 1 이상 1만 이하다. `s1`이 길면 순열 수가 길이의 팩토리얼이라 순열을 만드는 풀이는 바로 탈락이다.
- 글자는 소문자 26종뿐이다. 개수를 길이 26짜리 배열에 담을 수 있고, "26칸을 매번 비교해도 되나"가 풀이를 가르는 기준이 된다.
- `s1`이 `s2`보다 길 수도 있다. 그럼 볼 것도 없이 `false`다.

예를 들어 `s1 = "abc"`, `s2 = "cbdbcae"`면 `s2`의 3번부터 5번까지가 `"bca"`이고, 이건 `"abc"`의 순열이라 답은 `true`다. `s1 = "ab"`, `s2 = "eidboaoo"`면 a와 b가 붙어 있는 곳이 없어서 `false`다. b와 a가 둘 다 있긴 하지만 사이에 o가 끼어 있다.

## 순서가 아니라 개수를 본다

두 문자열이 서로의 순열이라는 건 글자 구성이 같다는 뜻이다. a가 몇 개, b가 몇 개, 이런 개수 목록이 똑같으면 순열이고 하나라도 다르면 아니다. `"bca"`와 `"abc"`는 둘 다 a 1, b 1, c 1이다.

그리고 `s2` 안에서 `s1`의 순열이 될 수 있는 구간은 길이가 반드시 `s1`의 길이 m과 같다. 그러니 볼 곳은 `s2`의 길이 m짜리 구간들뿐이다. 길이 n인 `s2`에는 그런 구간이 n − m + 1개 있다.

예시 `s1 = "abc"`, `s2 = "cbdbcae"`에서 길이 3 구간을 손으로 대 본다.

```text
시작  구간   a b c d   abc와 같나
 0    cbd   0 1 1 1   아니다 (a가 없고 d가 있다)
 1    bdb   0 2 0 1   아니다
 2    dbc   0 1 1 1   아니다
 3    bca   1 1 1 0   같다
 4    cae   1 0 1 0   (3에서 이미 찾았다)
```

이 표를 보면 다음 풀이가 보인다. 0번 구간 `cbd`에서 1번 구간 `bdb`로 갈 때 바뀐 건 앞의 c가 빠지고 뒤에 b가 들어온 것뿐이다. 나머지 두 글자는 그대로다. 개수 목록도 c가 1 줄고 b가 1 느는 것 말고는 같다. 이 "두 글자만 바뀐다"를 얼마나 잘 써먹느냐가 아래 여섯 풀이의 차이다.

## 순열을 전부 만들어 찾아본다

문제 문장을 그대로 코드로 옮기면 이렇다. `s1`의 순열을 [백트래킹](/posts/recursion-backtracking)으로 하나씩 만들고, 만들 때마다 `s2`에 들어 있는지 본다.

```js
function permBrute(s1, s2) {
  const seen = new Set(); // 같은 순열을 두 번 확인하지 않게
  const used = new Array(s1.length).fill(false);
  let found = false;
  const build = (cur) => {
    if (found) return;
    if (cur.length === s1.length) {
      if (!seen.has(cur)) {
        seen.add(cur);
        if (s2.includes(cur)) found = true; // 부분 문자열로 들어 있나
      }
      return;
    }
    for (let i = 0; i < s1.length; i++) {
      if (used[i]) continue;
      used[i] = true;
      build(cur + s1[i]);
      used[i] = false;
    }
  };
  build("");
  return found;
}
```

순열이 m!개이고, 하나마다 `includes`로 O(n·m)을 쓰니 최악 O(m! · n · m)이다. `s2`를 1만 자로 두고 재 보니 m = 7에서 6ms, 8에서 36ms, 9에서 456ms였다. 한 글자 늘 때마다 열 배씩 뛰고, m = 12쯤이면 몇 시간이다. 제약의 m 최댓값이 1만이라 말할 것도 없다.

`seen`으로 같은 순열을 거르는 건 `s1 = "aab"`처럼 글자가 겹칠 때 쓸데없는 `includes`를 줄이려는 것이다. 그래도 `build` 호출 수 자체는 m!에 비례해서 근본적인 해결은 아니다. 순서를 만들어 보는 접근을 버려야 한다.

## 창마다 정렬해서 맞대 본다

순서를 무시하는 가장 쉬운 방법은 정렬이다. 두 문자열을 정렬했을 때 같으면 서로의 순열이다. `s1`을 한 번 정렬해 두고, `s2`의 길이 m 구간마다 잘라서 정렬한 뒤 비교한다.

```js
function permSort(s1, s2) {
  const m = s1.length;
  const key = [...s1].sort().join(""); // "bca" → "abc"
  for (let i = 0; i + m <= s2.length; i++) {
    const part = [...s2.slice(i, i + m)].sort().join("");
    if (part === key) return true;
  }
  return false;
}
```

구간이 n − m + 1개, 구간마다 정렬이 O(m log m)이라 O((n − m) · m log m)이다. 공간은 잘라 낸 구간 하나만큼 O(m)이다.

m이 작으면 충분히 빠르다. 문제는 m이 n의 절반쯤일 때다. `s1`을 3,001자, `s2`를 1만 자로 두고 쟀더니 4.5초가 걸렸다. 구간 7,000개를 매번 3,000자씩 정렬한 셈이다. 이웃한 구간은 두 글자만 다른데 매번 처음부터 정렬하는 게 낭비다.

## 창마다 글자를 처음부터 센다

정렬 대신 개수를 센다. 소문자 26종이니 길이 26 배열 하나면 된다. 정렬의 log가 빠진다.

```js
function permRecount(s1, s2) {
  const m = s1.length;
  const need = new Array(26).fill(0); // s1의 글자별 개수
  for (const c of s1) need[c.charCodeAt(0) - 97]++; // 'a'의 코드가 97
  for (let i = 0; i + m <= s2.length; i++) {
    const win = new Array(26).fill(0); // 이 구간의 글자별 개수
    for (let j = i; j < i + m; j++) win[s2.charCodeAt(j) - 97]++;
    if (win.every((v, t) => v === need[t])) return true;
  }
  return false;
}
```

O((n − m) · (m + 26))이고 공간은 O(26)이다. 같은 입력에서 74ms로 정렬보다 60배 빨라졌다. 그래도 m이 n의 절반이면 여전히 O(n²) 꼴이다. 구간마다 m글자를 다시 세는 일이 남아 있다.

## 한 칸 밀 때 두 글자만 고친다

앞에서 본 대로 구간을 한 칸 밀면 들어오는 글자 하나, 나가는 글자 하나만 바뀐다. 개수 배열 `win`을 구간마다 새로 만들지 말고 계속 들고 다니면서 그 두 칸만 고친다. 이게 고정 길이 슬라이딩 윈도다. 틀 자체는 [슬라이딩 윈도 패턴](/posts/sliding-window-pattern)의 438번 코드와 같다.

```js
function permWindow26(s1, s2) {
  const m = s1.length;
  if (m > s2.length) return false;
  const need = new Array(26).fill(0), win = new Array(26).fill(0);
  for (const c of s1) need[c.charCodeAt(0) - 97]++;
  for (let r = 0; r < s2.length; r++) {
    win[s2.charCodeAt(r) - 97]++;                   // 들어오는 글자
    if (r >= m) win[s2.charCodeAt(r - m) - 97]--;   // 나가는 글자
    if (r >= m - 1 && win.every((v, t) => v === need[t])) return true; // 창이 다 찼을 때만 비교
  }
  return false;
}
```

한 칸 밀 때 고치는 건 O(1)이고, 비교가 26칸이다. 전체 O(26n), 공간 O(26)이다. 같은 입력에서 4.9ms였다. 26은 상수라 보통 이걸 O(n)이라고 부르고, 실전에서는 여기까지만 짜도 통과한다.

면접에서는 "매번 26칸을 비교하는 걸 없앨 수 있나요?"가 이어서 나온다. 알파벳이 26개면 괜찮지만, 글자 종류가 유니코드처럼 수만 개면 비교 비용이 그만큼 커진다. 다음 풀이가 그 답이다.

## 26칸 비교를 matches 하나로 줄인다

26칸을 다 비교하는 대신 "지금 개수가 맞는 칸이 몇 개인가"를 숫자 하나 `matches`로 들고 다닌다. `matches`가 26이면 모든 글자 개수가 같다는 뜻이니 순열이다.

창을 밀 때 바뀌는 칸은 두 개뿐이라, `matches`도 그 두 칸의 상태 변화만 반영하면 된다. 한 칸의 개수가 1 늘었을 때 생각할 경우는 셋이다.

- 늘어서 `need`와 같아졌다: 안 맞던 칸이 맞게 됐다. `matches`를 1 늘린다.
- 늘기 전에 `need`와 같았는데 이제 1 많다: 맞던 칸이 깨졌다. `matches`를 1 줄인다.
- 그 밖: 원래도 안 맞았고 지금도 안 맞는다. 그대로 둔다.

1 줄었을 때도 방향만 반대로 같다. 같아졌으면 늘리고, `need`보다 1 적어졌으면(직전엔 같았다는 뜻) 줄인다.

```js
function checkInclusion(s1, s2) {
  const m = s1.length, n = s2.length;
  if (m > n) return false; // s1이 더 길면 들어갈 수 없다
  const need = new Array(26).fill(0), win = new Array(26).fill(0);
  for (let i = 0; i < m; i++) {
    need[s1.charCodeAt(i) - 97]++;
    win[s2.charCodeAt(i) - 97]++; // 첫 창을 미리 채운다
  }
  let matches = 0; // need와 win의 값이 같은 칸 수 (0~26)
  for (let t = 0; t < 26; t++) if (need[t] === win[t]) matches++;

  for (let r = m; r < n; r++) {
    if (matches === 26) return true; // 직전 창이 순열이다

    const a = s2.charCodeAt(r) - 97; // 들어오는 글자
    win[a]++;
    if (win[a] === need[a]) matches++;           // 맞게 됐다
    else if (win[a] === need[a] + 1) matches--;  // 맞던 게 깨졌다

    const b = s2.charCodeAt(r - m) - 97; // 나가는 글자
    win[b]--;
    if (win[b] === need[b]) matches++;
    else if (win[b] === need[b] - 1) matches--;
  }
  return matches === 26; // 마지막 창도 확인한다
}
```

`"abc"`를 `"cbdbcae"`에서 찾는 과정을 따라가 본다. 메모리 칸은 a부터 d까지 "창 안 개수/필요 개수"와 `matches`다. e부터 z까지는 창에도 `s1`에도 없어서 처음부터 끝까지 맞는 칸이다.

두 번째 단계를 눈여겨볼 만하다. b는 1개에서 2개로 늘면서 맞던 칸이 깨졌고, c는 1개에서 0개로 줄면서 깨졌다. 들어오는 쪽과 나가는 쪽을 따로 따지니 두 칸이 동시에 깨지는 것도 정확히 반영된다.

들어오는 글자와 나가는 글자가 같을 때도 맞을까. `a`에서 `win[a]`를 1 늘렸다가 바로 `b`(같은 칸)에서 1 줄이니, 늘릴 때 `matches`가 바뀌었다면 줄일 때 반대로 되돌아간다. 결과는 아무 일도 없던 것과 같다.

시간은 첫 창 준비 O(m + 26), 미는 동안 칸마다 O(1)이라 O(n + 26)이다. 공간은 배열 두 개로 O(26)이다. 같은 입력에서 4.2ms로 26칸 비교와 거의 같았다. 알파벳 26자에서는 비교 비용이 원래 작아서 차이가 잘 안 보인다. 차이가 나는 건 글자 종류 k가 클 때다. 26칸 비교는 O(k·n)이 되고, 이 풀이는 처음에 한 번 O(k)를 쓴 뒤로는 O(n)이다. 글자 종류가 정해져 있지 않으면 배열 대신 `Map`을 쓰고 `matches` 대신 "아직 개수가 다른 글자 종류 수"를 세면 된다.

이 "일치 개수" 변수는 [Minimum Window Substring](/posts/leetcode-minimum-window-substring)에서 그대로 다시 쓰인다. 거기서는 창 길이가 정해져 있지 않을 뿐이다.

## 빚을 갚는 가변 창

창 길이를 고정하지 않고도 풀 수 있다. `need` 배열을 "아직 받아야 할 글자 수"라고 보고, 창에 글자가 들어오면 그 글자의 `need`를 1 줄인다. `need`가 음수가 되면 `s1`이 허락한 것보다 많이 받았다는 뜻, 곧 빚이다. 빚이 생기면 왼쪽에서 글자를 빼서 돌려준다. 그 글자의 빚이 0으로 돌아올 때까지.

이렇게 하면 창 안의 어떤 글자도 `s1`보다 많이 들어 있지 않다는 상태가 늘 유지된다. 그런 창의 길이가 m에 닿으면, 모든 글자가 많아야 필요한 만큼 있으면서 합이 m이니 정확히 필요한 만큼 있는 것이다. 그래서 길이 m이 되는 순간이 곧 순열을 찾은 순간이다.

```js
function permDebt(s1, s2) {
  const m = s1.length;
  const need = new Array(26).fill(0); // 아직 받아야 할 개수. 음수면 빚
  for (const c of s1) need[c.charCodeAt(0) - 97]++;
  let l = 0;
  for (let r = 0; r < s2.length; r++) {
    const c = s2.charCodeAt(r) - 97;
    need[c]--;                     // 들어온 글자를 받는다
    while (need[c] < 0) {          // 너무 많이 받았으면
      need[s2.charCodeAt(l) - 97]++; // 왼쪽 글자를 돌려준다
      l++;
    }
    if (r - l + 1 === m) return true; // 빚 없이 m글자를 채웠다
  }
  return false;
}
```

`l`과 `r`이 각각 한 방향으로 많아야 n번 움직이니 `for` 안에 `while`이 있어도 O(n)이다(왜 그런지는 [허브 글](/posts/sliding-window-pattern)의 "안쪽에 while이 있어도 O(n)인 이유"). 공간은 O(26)이다. 같은 입력에서 3.4ms로 여섯 풀이 중 가장 빨랐다. 26칸 비교도 `matches` 관리도 없어서 코드가 가장 짧다는 것도 장점이다.

다만 이 풀이는 "길이 m에 닿으면 순열"이라는 논리가 한 번 더 필요하다. 면접에서 쓰려면 위의 "많아야 필요한 만큼 있고 합이 m이면 정확히 필요한 만큼"을 말로 설명할 수 있어야 한다. 설명이 자신 없으면 `matches` 풀이가 안전하다.

## matches 풀이의 Python·Java 판

코딩 테스트용으로는 고정 창 + `matches` 풀이를 세 언어로 맞춰 두는 걸 권한다. 고정 창이라 438번(위치 모두 찾기)으로 바꿀 때 `return true`를 `push`로만 바꾸면 되기 때문이다.

```python
class Solution:
    def checkInclusion(self, s1: str, s2: str) -> bool:
        m, n = len(s1), len(s2)
        if m > n:
            return False
        need, win = [0] * 26, [0] * 26
        for i in range(m):
            need[ord(s1[i]) - 97] += 1
            win[ord(s2[i]) - 97] += 1
        matches = sum(need[t] == win[t] for t in range(26))  # 개수가 같은 글자 칸 수
        for r in range(m, n):
            if matches == 26:
                return True
            a = ord(s2[r]) - 97          # 들어오는 글자
            win[a] += 1
            if win[a] == need[a]:
                matches += 1
            elif win[a] == need[a] + 1:
                matches -= 1
            b = ord(s2[r - m]) - 97      # 나가는 글자
            win[b] -= 1
            if win[b] == need[b]:
                matches += 1
            elif win[b] == need[b] - 1:
                matches -= 1
        return matches == 26
```

```java
class Solution {
    public boolean checkInclusion(String s1, String s2) {
        int m = s1.length(), n = s2.length();
        if (m > n) return false;
        int[] need = new int[26], win = new int[26];
        for (int i = 0; i < m; i++) {
            need[s1.charAt(i) - 'a']++;
            win[s2.charAt(i) - 'a']++;
        }
        int matches = 0;
        for (int t = 0; t < 26; t++) if (need[t] == win[t]) matches++;
        for (int r = m; r < n; r++) {
            if (matches == 26) return true;
            int a = s2.charAt(r) - 'a';      // 들어오는 글자
            win[a]++;
            if (win[a] == need[a]) matches++;
            else if (win[a] == need[a] + 1) matches--;
            int b = s2.charAt(r - m) - 'a';  // 나가는 글자
            win[b]--;
            if (win[b] == need[b]) matches++;
            else if (win[b] == need[b] - 1) matches--;
        }
        return matches == 26;
    }
}
```

`("abc", "bdcabe")`, `("ab", "eidboaoo")`, `("ab", "ba")`, `("a", "a")`, `("abc", "ab")`, `("aab", "abab")`, `("adc", "dcda")`, `("aa", "ab")`를 넣어 세 언어 모두 true, false, true, true, false, true, true, false가 나왔다. 여섯 JS 풀이가 서로 같은 답을 내는지는 a·b·c로 만든 무작위 입력 5,000쌍으로 확인했다.

언어마다 짚을 점이 있다.

- Python은 `collections.Counter`를 쓰면 `Counter(s2[i:i+m]) == Counter(s1)`처럼 한 줄로 끝나는 유혹이 있다. 구간마다 새로 세니 "창마다 다시 세기"와 같은 O(n·m)이다. 창을 밀면서 `Counter`의 값을 고치는 식으로 쓸 수는 있는데, 그때는 Python 버전을 봐야 한다. 3.10부터는 `Counter` 비교에서 값이 0인 키를 없는 키로 친다. 3.9 이하에서는 개수가 0이 된 키를 지우지 않으면 `==`가 False를 낸다.
- Java의 `s.charAt(i) - 'a'`는 바로 `int`다. JS는 `charCodeAt(i) - 97`이 필요하다. JS에서 `s[i] - "a"`라고 쓰면 `NaN`이 되고, `win[NaN]++`은 오류 없이 배열에 `"NaN"` 속성을 만든다. 틀린 답이 조용히 나온다.
- `m > n` 검사를 빼면 Java는 첫 창을 채울 때 `s2.charAt(i)`가 범위를 벗어나 `StringIndexOutOfBoundsException`을 던진다. JS는 `charCodeAt`이 `NaN`을 돌려줄 뿐이라 예외가 나지 않는다. 운 좋게 답이 맞을 수도 있지만 믿을 코드는 아니다.

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 순열 전부 만들기 | O(m! · n · m) | O(m) | m이 한 자릿수일 때 정답 확인용 |
| 창마다 정렬 | O((n − m) · m log m) | O(m) | 개수 배열이 떠오르지 않을 때 |

| 고정 창 + matches | O(n + 26) | O(26) | 글자 종류가 많거나 비교를 없애라고 할 때 |

## matches가 어긋나는 코드들

`matches` 갱신을 "같으면 늘리고 아니면 줄인다"로 줄여 쓰는 경우가 많다. 짧아 보이지만 틀린다.

```js
win[a]++;
if (win[a] === need[a]) matches++;
else matches--; // 원래 안 맞던 칸이 계속 안 맞아도 줄여 버린다
```

`("c", "aac")`에서 이 코드는 false를 낸다. 첫 창 `a`에서 a는 이미 안 맞는 칸이다. 다음 a가 들어와 a가 2가 돼도 여전히 안 맞는 칸일 뿐인데 `matches`를 하나 줄이고, 나갈 때 또 줄인다. 이렇게 깎인 `matches`는 마지막 창 `c`가 정답인데도 26에 닿지 못한다. 줄이는 건 "직전에 맞았던 칸"일 때뿐이고, 그걸 알려 주는 조건이 `win[a] === need[a] + 1`이다.

반복문 안에서만 확인하고 끝에 `return false`를 쓰는 실수도 있다.

```js
for (let r = m; r < n; r++) {
  if (matches === 26) return true; // 직전 창을 확인한다
  // ... 창을 민다 ...
}
return false; // 마지막 창은 아무도 확인하지 않았다
```

반복문은 매번 "민 다음"이 아니라 "밀기 전"에 직전 창을 확인한다. 그래서 마지막으로 민 창은 반복문 안에서 확인받지 못한다. `("c", "c")`처럼 m과 n이 같으면 반복문이 한 번도 돌지 않아 첫 창조차 보지 않는다. 끝을 `return matches === 26`으로 써야 한다. 확인을 밀고 난 뒤로 옮기는 방법도 있는데, 그럼 첫 창을 반복문 앞에서 따로 확인해야 한다. 어느 쪽이든 창이 n − m + 1개 모두 확인되는지 세어 보는 습관이 이 실수를 막는다.

빚 창에서 `while`을 `if`로 바꾸면 이렇게 된다.

```js
need[c]--;
if (need[c] < 0) { need[s2.charCodeAt(l) - 97]++; l++; } // 한 글자만 돌려준다
if (r - l + 1 === m) return true;
```

`("ad", "dca")`에서 true를 낸다. 정답은 false다. c가 들어와 빚이 생겼을 때 맨 앞의 d 하나만 돌려주는데, 빚을 진 글자는 c라서 빚이 그대로다. 그 상태로 a가 들어오면 창 `ca`의 길이가 2라 순열로 착각한다. 빚은 진 글자가 빠질 때까지 갚아야 하니 `while`이다.

마지막으로, `s1`이 `s2`보다 길 때를 따로 처리하지 않으면 언어마다 다르게 망가진다는 점은 위에서 봤다. 맨 처음 한 줄로 막는 게 가장 깔끔하다.

## 조건을 비틀면 바뀌는 곳

### 시작 위치를 모두 구하라면 (LeetCode 438)

`s2` 안에서 `s1`의 순열이 시작하는 위치를 전부 돌려주는 문제가 438번 Find All Anagrams in a String이다. 고정 창 풀이에서 `return true`를 `out.push(r - m + 1)`로 바꾸고 끝까지 훑는다. 코드는 [슬라이딩 윈도 패턴](/posts/sliding-window-pattern)에 있다. 빚 창도 길이가 m에 닿을 때 위치를 넣고, 다음 칸으로 가기 전에 왼쪽 글자 하나를 돌려주면(`need[s2[l]]++`, `l++`) 계속 찾을 수 있다.

### 대문자, 숫자, 한글이 섞이면

길이 26 배열을 `Map`으로 바꾼다. `matches`의 기준이 "26칸 중 맞는 칸"이 아니라 "`s1`에 나온 글자 종류 가운데 개수가 맞는 종류 수"가 된다. `s1`에 없는 글자는 창에 들어오는 순간 어차피 그 창이 답이 될 수 없으니, 빚 창 쪽이 특히 깔끔하다. `need`에 없는 글자는 0으로 보고 빼면 바로 음수가 되어 창이 비워진다.

### 글자가 하나씩 흘러 들어온다면

`s2`가 통째로 주어지지 않고 로그처럼 한 글자씩 들어온다고 하자. 들어올 때마다 "방금까지의 마지막 m글자가 `s1`의 순열인가"를 답해야 한다. 고정 창은 나가는 글자를 알아야 하니 최근 m글자를 원형 버퍼(길이 m 배열을 돌려 쓰는 큐)에 들고 있으면 된다. 메모리는 `s2` 길이와 상관없이 O(m + 26)이다.

```js
function makeWatcher(s1) {
  const m = s1.length;
  const need = new Array(26).fill(0), win = new Array(26).fill(0);
  for (const c of s1) need[c.charCodeAt(0) - 97]++;
  const buf = new Array(m); // 최근 m글자만 담는 원형 버퍼
  let count = 0, matches = 0;
  for (let t = 0; t < 26; t++) if (need[t] === win[t]) matches++;
  const bump = (x, d) => {
    if (win[x] === need[x]) matches--; // 바꾸기 전에 맞았으면 일단 뺀다
    win[x] += d;
    if (win[x] === need[x]) matches++; // 바꾼 뒤 맞으면 다시 더한다
  };
  return (ch) => {
    const a = ch.charCodeAt(0) - 97;
    if (count >= m) bump(buf[count % m], -1); // 가장 오래된 글자를 내보낸다
    buf[count % m] = a;
    bump(a, +1);
    count++;
    return count >= m && matches === 26;
  };
}
const push = makeWatcher("abc");
console.log([..."cbdbcae"].map(push).join(" "));
```

```text
false false false false false true false
```

여섯 번째 글자 a가 들어온 순간에만 true다. 여기 쓴 `bump`는 `matches` 갱신을 다르게 적은 것이다. "바꾸기 전에 맞았으면 하나 빼고, 바꾼 뒤에 맞으면 하나 더한다." 경우를 셋으로 나누는 대신 앞뒤 상태만 보니 1씩 바뀌지 않는 경우(한 번에 여러 개를 넣고 빼는 경우)에도 그대로 맞는다. 본문의 `+ 1`, `- 1` 조건이 헷갈리면 이 모양으로 외워 두는 쪽이 실수가 적다.

### 순서까지 같아야 한다면

순열이 아니라 `s1` 그대로를 찾는 문제는 문자열 검색이다. JS의 `s2.includes(s1)`이고, 직접 짜면 KMP나 라빈-카프(롤링 해시)다. 롤링 해시도 "한 칸 밀 때 들어온 것과 나간 것만 반영한다"는 점에서 이 글의 창과 생각이 같다.

### 가장 짧은 창에 s1의 글자가 모두 들어 있으면 되는 경우 (LeetCode 76)

`s1`의 글자를 "포함"만 하면 되고 다른 글자가 끼어도 되는 가장 짧은 구간을 찾으면 [Minimum Window Substring](/posts/leetcode-minimum-window-substring)이다. 창 길이가 정해지지 않아 가변 창이 되고, 이 글의 `matches`가 "필요한 종류를 다 채웠나"로 바뀐다.

### 단어들을 이어 붙인 순열이라면 (LeetCode 30)

글자 대신 같은 길이의 단어 여러 개를 아무 순서로 이어 붙인 구간을 찾는 30번 Substring with Concatenation of All Words는 이 문제의 단어 판이다. 창이 한 번에 단어 길이만큼 움직이고, 시작 위치를 단어 길이로 나눈 나머지별로 창을 따로 돌린다. 개수 배열은 단어를 키로 하는 `Map`이 된다.

비슷한 연습으로는 같은 묶음의 [Longest Substring Without Repeating Characters](/posts/leetcode-longest-substring-without-repeating)(빚 창과 같은 "넘치면 줄인다" 모양), 정렬 대신 개수로 순열을 판정하는 [Valid Anagram](/posts/leetcode-valid-anagram), 그 판정을 키로 묶는 [Group Anagrams](/posts/leetcode-group-anagrams)가 있다.

## 면접에서 나올 만한 질문

### 왜 순열을 만들지 않고 개수를 비교하나요?

두 문자열이 서로의 순열인지는 글자별 개수가 같은지와 정확히 같은 질문이기 때문이다. 순열을 만들면 m!개라 길이 10만 넘어도 감당이 안 되지만, 개수는 소문자 26칸 배열로 O(m)에 끝난다. 그리고 `s2`에서 볼 곳은 길이 m 구간뿐이라 고정 길이 창이 된다.

### 고정 창 풀이의 시간 복잡도는요?

창을 한 칸 밀 때 들어오고 나가는 두 칸만 고치니 O(1)이고, 매번 26칸을 비교하면 O(26n)이다. 26이 상수라 O(n)이라고 해도 된다. 비교까지 없애고 싶으면 맞는 칸 수 `matches`를 들고 다녀 O(n + 26)으로 만든다.

### matches를 늘리고 줄이는 조건을 설명해 보세요.

한 칸의 값이 바뀐 뒤 `need`와 같아졌으면 안 맞던 칸이 맞게 된 것이라 늘린다. 1 늘었는데 `need`보다 1 많거나, 1 줄었는데 `need`보다 1 적으면 직전에 맞던 칸이 깨진 것이라 줄인다. 그 밖은 안 맞던 칸이 계속 안 맞는 것이라 그대로 둔다. "같지 않으면 줄인다"로 쓰면 이미 안 맞던 칸을 또 깎아서 틀린다.

### 가변 창으로도 풀 수 있나요?

된다. `need`를 받아야 할 개수로 보고, 들어온 글자의 `need`가 음수가 되면 그 글자가 0이 될 때까지 왼쪽을 뺀다. 그러면 창 안의 모든 글자가 많아야 필요한 만큼만 있으니, 창 길이가 m이 되는 순간 정확히 필요한 만큼 있는 것이고 그게 순열이다. `s1`에 없는 글자를 만나면 창을 한 번에 비우는 효과도 있다.

### 글자 종류가 유니코드 전체라면 무엇이 달라지나요?

배열 대신 `Map`을 쓰고, 26칸 비교는 글자 종류 수만큼 커지니 버린다. 대신 `s1`에 나온 글자 종류 가운데 개수가 맞는 종류 수를 세서 그게 종류 수와 같아지는지 본다. 빚 창은 `s1`에 없는 글자가 들어오면 바로 음수가 되어 자연스럽게 처리된다.

### 반복문이 끝난 뒤 한 번 더 확인하는 이유는요?

반복문이 "창을 밀기 전에 직전 창"을 확인하도록 짜면 마지막 창은 반복문 안에서 확인받지 못한다. m과 n이 같으면 반복문이 아예 돌지 않는다. 그래서 끝에 `return matches === 26`이 있어야 n − m + 1개 창이 모두 확인된다.

### 시작 위치를 모두 구하라고 하면요?

438번 문제다. 고정 창에서 `return true` 대신 위치 `r - m + 1`을 결과에 넣고 끝까지 훑으면 된다. 시간은 그대로 O(n)이고, 결과 배열만큼 공간이 더 든다.
