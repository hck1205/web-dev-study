카운터 모듈 하나를 두 가지 방식으로 불러 봤다. 코드는 거의 같다. `count`를 내보내고, `increment`를 두 번 부른 다음 다시 읽는다.

```js
// counter.mjs
export let count = 0;
export function increment() { count++; }

// main.mjs
import { count, increment } from "./counter.mjs";
console.log("ESM 처음:", count);
increment();
increment();
console.log("ESM 두 번 뒤:", count);
```

```js
// counter.cjs
let count = 0;
function increment() { count++; }
module.exports = { count, increment };

// main.cjs
const { count, increment } = require("./counter.cjs");
console.log("CJS 처음:", count);
increment();
increment();
console.log("CJS 두 번 뒤:", count);
console.log("CJS 모듈 객체:", require("./counter.cjs").count);
```

```text
ESM 처음: 0
ESM 두 번 뒤: 2
CJS 처음: 0
CJS 두 번 뒤: 0
CJS 모듈 객체: 0
```

ES 모듈(ESM)에서는 2가 됐고 CommonJS(CJS)에서는 0에 머물렀다. 모듈 객체를 다시 꺼내 봐도 0이다. 두 시스템은 "내보낸다"의 뜻부터 다르다. 이 글은 그 차이에서 출발해 import가 변수를 어떻게 연결하는지, 모듈이 어떤 순서로 읽히고 실행되는지, 브라우저와 Node에서 두 시스템이 만나는 자리에서 어떤 오류가 나는지 따라간다. Node 22.22와 Chromium(Playwright)에서 돌린 출력이고, 긴 파일 경로는 `/work`로 줄였다.

모듈 이전 시대에 함수 스코프로 모듈을 흉내 내던 방법은 [IIFE와 모듈 패턴 글](/posts/js-iife-module-pattern)에서, 번들을 쪼개고 안 쓰는 코드를 빼는 이야기는 [코드 스플리팅 글](/posts/code-splitting)에서 다룬다. 이 글은 그 사이, 모듈 시스템 자체의 동작을 본다.

## 내보낸 것은 값이 아니라 변수다

CJS의 `module.exports = { count, increment }`는 그 순간 `count`의 값 `0`을 새 객체의 속성에 복사한다. 이후 `increment`가 바꾸는 것은 모듈 안의 지역 변수 `count`이지 객체의 속성이 아니다. 받는 쪽에서 구조 분해하면 그 복사본을 한 번 더 복사한다.

ESM의 `export let count`는 값을 복사하지 않는다. 모듈의 환경 레코드에 있는 `count`라는 변수 칸 자체를 내보낸다. `import { count }`는 그 칸에 연결된 이름을 만든다. 명세는 이것을 간접 바인딩(indirect binding)이라고 부르고, 흔히 라이브 바인딩(live binding)이라고 한다. 읽을 때마다 원래 칸의 현재 값을 본다.

연결은 한 방향이다. import한 이름에 대입하면 오류가 난다.

```js
import { count } from "./counter.mjs";
try { count = 10; } catch (e) { console.log(e.constructor.name + ": " + e.message); }
```

```text
TypeError: Assignment to constant variable.
```

`let`으로 내보냈어도 받는 쪽에서는 `const`처럼 보인다. 값을 바꾸는 권한은 내보낸 모듈에만 있다. 그래서 바꿀 수 있는 상태를 모듈로 공유할 때는 `increment` 같은 함수를 함께 내보낸다. 이 성질 덕분에 "누가 이 값을 바꾸나"를 찾을 때 그 모듈 파일 하나만 보면 된다.

라이브 바인딩이 필요한 상황은 생각보다 드물다. 실무에서 이 차이를 체감하는 건 대개 반대 방향이다. CJS 시절에 `require`로 받아 둔 설정 값이 "나중에 바뀌지 않는다"고 믿던 코드를 ESM으로 옮겼더니, 초기화 순서에 따라 다른 값이 보이는 경우다.

## default는 이름이 default인 내보내기일 뿐이다

ESM의 내보내기는 이름 있는 내보내기(named export)와 기본 내보내기(default export)로 나뉜다. 그런데 명세에서 default는 특별한 종류가 아니다. 이름이 `"default"`인 내보내기다. 아래 import 한 줄을 조각으로 눌러 보자.

default가 "이름이 default인 변수"라는 사실은 라이브 바인딩에서 차이를 만든다. `export default 식`은 그 식의 값을 `*default*`라는 숨은 변수에 담는다. 원래 변수와 연결되지 않는다.

```js
// theme.mjs
let theme = "light";
export default theme;          // 이 순간의 값을 default에 담는다
export { theme as current };   // theme 변수 자체를 내보낸다
export function setTheme(t) { theme = t; }

// main.mjs
import theme, { current, setTheme } from "./theme.mjs";
import * as ns from "./theme.mjs";
setTheme("dark");
console.log(theme, current, ns.default, ns.current);
console.log(Object.keys(ns), Object.prototype.toString.call(ns));
try { ns.extra = 1; } catch (e) { console.log(e.message); }
```

```text
light dark light dark
[ 'current', 'default', 'setTheme' ] [object Module]
Cannot add property extra, object is not extensible
```

`theme`(default)는 `light`에 머물고, `current`는 `dark`로 따라왔다. `import * as ns`로 받은 네임스페이스 객체에는 `default`도 그냥 속성 하나로 들어 있고, 새 속성을 붙일 수 없다. `export function f`나 `export default function f() {}`처럼 함수 선언을 내보내면 그 함수 이름의 바인딩이 그대로 연결된다.

`export *`는 default를 다시 내보내지 않는다.

```js
// reexport.mjs
export * from "./theme.mjs";
```

```text
[ 'current', 'setTheme' ]
SyntaxError: The requested module './reexport.mjs' does not provide an export named 'default'
```

모든 것을 모아 내보내는 `index.js`(배럴 파일)에서 default를 쓰던 컴포넌트가 사라지는 이유다. `export { default } from "./theme.mjs"`나 `export { default as Theme } from ...`을 따로 적어야 한다.

이름 있는 내보내기와 default 중 무엇을 쓸지는 팀 규칙의 문제지만, 이름 있는 내보내기 쪽이 실수가 적다. 이름이 틀리면 링크 단계에서 바로 오류가 나고, 편집기의 자동 import와 전체 이름 바꾸기가 정확하게 동작한다. default는 받는 쪽마다 다른 이름을 붙일 수 있어 검색이 어려워진다. 반대로 `React.lazy`나 Next.js의 `page.tsx`처럼 프레임워크가 default를 요구하는 자리에서는 default를 쓴다.

## 실행하기 전에 연결부터 한다

`import`와 `export`는 파일의 최상위에만 쓸 수 있고, 모듈 지정자는 문자열 리터럴이어야 한다. `if` 안에서 import하거나 변수로 경로를 만들 수 없다. 이 제약 덕분에 엔진은 코드를 실행하기 전에 모든 모듈의 import와 export를 읽어 그래프를 만들고, 이름끼리 연결까지 끝낼 수 있다. 명세는 이 과정을 세 단계로 나눈다.

평가 단계의 순서를 직접 보자. `main`이 `a`와 `b`를 import하고, 둘 다 `c`를 import한다. 각 파일은 자기 이름만 찍는다. `main`은 import 문보다 `console.log`를 위에 썼다.

```js
// main.mjs
console.log("main 본문");
import "./a.mjs";
import "./b.mjs";
// a.mjs: import "./c.mjs"; console.log("a 본문");
// b.mjs: import "./c.mjs"; console.log("b 본문");
// c.mjs: console.log("c 본문");
```

```text
c 본문
a 본문
b 본문
main 본문
```

같은 구조를 CJS의 `require`로 바꾸면 이렇게 나온다.

```text
main 본문
c 본문
a 본문
b 본문
```

ESM에서는 `main 본문`이 맨 마지막이다. import는 위치와 상관없이 본문보다 먼저 처리되고, 의존성 그래프를 깊이 우선으로 내려가서 가장 깊은 모듈부터 실행한다. `c`는 두 번 import됐지만 한 번만 실행됐다. CJS의 `require`는 그 줄에 닿았을 때 동기로 파일을 읽어 실행하는 함수 호출이라 코드 순서를 그대로 따른다.

모듈이 "한 번만 실행된다"는 기준은 경로가 아니라 해석된 주소(URL)다. 같은 파일이라도 `./a.mjs`와 `./a.mjs?v=2`는 다른 모듈로 두 번 실행된다. 같은 패키지가 `node_modules`에 두 벌 깔리거나, ESM 빌드와 CJS 빌드가 함께 로드되면 모듈 상태가 둘로 갈라진다. 이 문제는 [싱글턴 패턴 글](/posts/pattern-singleton)에서 자세히 다뤘다.

의존성이 순환하면 어떻게 될까. `a`가 `b`를, `b`가 `a`를 import하면 평가 중인 `a`를 만났을 때 다시 들어가지 않고 넘어간다. 그래서 `b`가 먼저 실행되는데, 이때 `a`의 `let`·`const`·`class`는 아직 초기화 전이라 읽으면 ReferenceError다. 이 장면은 [호이스팅과 TDZ 글의 순환 import 부분](/posts/js-hoisting-tdz#순환-import가-tdz를-부른다)에서 실제 오류와 함께 다뤘다.

## 브라우저는 import를 만날 때마다 한 번 더 요청한다

브라우저에서는 `<script type="module">`로 모듈을 불러온다. 모듈 스크립트는 기본으로 `defer`처럼 동작해서 HTML 파싱을 막지 않고, 문서 파싱이 끝난 뒤 실행된다. 그리고 파일마다 HTTP 요청이 하나씩 생긴다. 파일 하나를 받을 때마다 서버가 100ms씩 늦게 응답하게 만들고, Chromium에서 요청 순서를 찍어 봤다. `main.js`가 `a.js`, `b.js`를, 둘이 `c.js`를 import하는 앞의 그래프 그대로다.

```text
  24ms 요청  /
 145ms 요청  /main.js
 146ms 콘솔  classic script: DOM 파싱 중 loading
 250ms 요청  /a.js
 251ms 요청  /b.js
 355ms 요청  /c.js
 463ms 콘솔  main 실행 interactive
화면: AcBc
```

`main.js`를 받아 파싱해야 `a.js`와 `b.js`가 필요하다는 것을 알고, 그걸 받아야 `c.js`를 안다. 그래프의 깊이만큼 왕복이 쌓이는 워터폴이다. 모듈 스크립트 아래에 둔 일반 스크립트가 먼저 실행된 것(`loading`)도 보인다. 모듈은 `interactive`, 즉 파싱이 끝난 뒤에 돌았다.

HTML에 `<link rel="modulepreload">`로 필요한 모듈을 미리 알려 주면 이렇게 바뀐다.

```html
<link rel="modulepreload" href="./a.js">
<link rel="modulepreload" href="./b.js">
<link rel="modulepreload" href="./c.js">
<script type="module" src="./main.js"></script>
```

```text
  28ms 요청  /
 165ms 요청  /a.js
 165ms 요청  /b.js
 166ms 요청  /c.js
 166ms 요청  /main.js
 167ms 콘솔  classic script: DOM 파싱 중 loading
 263ms 콘솔  main 실행 interactive
화면: AcBc
```

모듈 스크립트에는 몇 가지 규칙이 더 있다. 항상 엄격 모드로 실행되고, 최상위 `this`가 `undefined`다(CJS 파일에서는 `module.exports`다). 다른 출처에서 받으면 CORS 검사를 거친다. 그래서 HTML 파일을 더블클릭해 `file://`로 열면 모듈이 로드되지 않는다.

## Node에서 두 시스템이 만나는 자리

Node는 CJS로 시작했고 지금도 두 시스템을 함께 지원한다. 파일이 어느 쪽인지는 확장자와 가장 가까운 `package.json`의 `"type"`이 정한다. `.mjs`는 ESM, `.cjs`는 CJS, `.js`는 `"type": "module"`이면 ESM이고 아니면 CJS다.

`"type"`이 없는 패키지에서 `.js`에 import 문을 쓰면, 예전에는 문법 오류였다. Node 22.7부터는 모듈 문법을 감지해 ESM으로 다시 읽는다. 대신 경고를 남긴다.

```text
3
(node:1999) [MODULE_TYPELESS_PACKAGE_JSON] Warning: Module type of file:///work/esm/interop/app.js is not specified and it doesn't parse as CommonJS.
Reparsing as ES module because module syntax was detected. This incurs a performance overhead.
To eliminate this warning, add "type": "module" to /work/esm/interop/package.json.
```

한 번 CJS로 파싱했다가 실패하고 다시 파싱하니 비용이 든다. 경고 문구대로 `"type": "module"`을 적는다.

ESM으로 옮기면 CJS에서 당연하던 것들이 사라진다. 실제로 마주치는 오류는 이렇다.

```text
# 확장자 없는 상대 경로: import { add } from "./util";
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '/work/esm/interop/util' imported from /work/esm/interop/noext.mjs
Did you mean to import "./util.js"?

# ESM 파일에서 __dirname 사용
__dirname is not defined

# JSON을 그냥 import: import cfg from "./config.json";
TypeError [ERR_IMPORT_ATTRIBUTE_MISSING]: Module "file:///work/esm/interop/config.json" needs an import attribute of "type: json"
```

ESM은 브라우저와 같은 규칙으로 주소를 해석해서 확장자를 추측하지 않는다. TypeScript 소스에서도 `import "./util.js"`처럼 출력될 파일의 확장자를 적는다. `__dirname`과 `__filename` 대신 `import.meta.dirname`과 `import.meta.filename`(Node 20.11부터)을, 그 전 버전에서는 `fileURLToPath(import.meta.url)`를 쓴다. JSON은 `import cfg from "./config.json" with { type: "json" }`으로 "이건 JSON이니 실행하지 마라"를 명시해야 한다. 서버가 JSON이라던 파일이 사실 스크립트일 때 실행되는 것을 막으려는 장치다.

### ESM에서 CJS를 부를 때

ESM에서 CJS 모듈을 import하면 `module.exports` 전체가 default로 들어온다. 이름 있는 import도 되는데, Node가 CJS 코드를 실행하지 않고 정적으로 훑어서(cjs-module-lexer) `exports.이름 = ...` 모양만 찾아내기 때문이다. 실행해 봐야 알 수 있는 내보내기는 못 찾는다.

```js
// legacy.cjs
exports.parse = (s) => s.split(",");
module.exports.version = "1.0";
const extra = {};
extra.dynamicHelper = () => "x";
Object.assign(module.exports, extra);

// use-legacy.mjs
import legacy, { parse, version } from "./legacy.cjs";
console.log(parse("a,b"), version, Object.keys(legacy));
```

```text
[ 'a', 'b' ] 1.0 [ 'parse', 'version', 'dynamicHelper' ]
```

```text
SyntaxError: Named export 'dynamicHelper' not found. The requested module './legacy.cjs' is a CommonJS module, which may not support all module.exports as named exports.
CommonJS modules can always be imported via the default export, for example using:

import pkg from './legacy.cjs';
const { dynamicHelper } = pkg;
```

`Object.assign`으로 붙인 `dynamicHelper`는 default 객체에는 있지만 이름 있는 import로는 못 받는다. 오류 문구가 해결책까지 알려 준다. 오래된 CJS 라이브러리에서 이름 있는 import가 안 될 때 이 경우가 많다.

### CJS에서 ESM을 부를 때

반대 방향은 오랫동안 막혀 있었다. `require`는 동기 함수인데 ESM 평가는 최상위 await 때문에 비동기일 수 있어서다. Node 22.12부터는 플래그 없이 `require(esm)`이 된다. 22.22에서 돌려 보니 경고 없이 불러왔다.

```js
// lib.mjs
export const version = "2.0.0";
export default function greet() { return "hi"; }

// use.cjs
const lib = require("./lib.mjs");
console.log(lib, typeof lib.default);
```

```text
[Module: null prototype] {
  __esModule: true,
  default: [Function: greet],
  version: '2.0.0'
} function
```

네임스페이스 객체가 통째로 오고, default는 `.default`로 꺼낸다. 다만 그래프 어딘가에 최상위 await가 있으면 동기로 끝낼 수 없으니 실패한다.

```text
Error [ERR_REQUIRE_ASYNC_MODULE]: require() cannot be used on an ESM graph with top-level await. Use import() instead. To see where the top-level await comes from, use --experimental-print-required-tla.
```

이때는 오류 문구대로 `await import()`를 쓴다. 최상위 await 자체는 [async/await 글](/posts/js-async-await)에서 다뤘다.

### 패키지의 exports가 문을 정한다

라이브러리는 `package.json`의 `"exports"`로 어떤 경로를 공개할지, import와 require에 각각 어떤 파일을 줄지 정한다.

```json
{
  "name": "tiny-date",
  "type": "module",
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  }
}
```

```text
esm 빌드
cjs 빌드
Error [ERR_PACKAGE_PATH_NOT_EXPORTED]: Package subpath './dist/internal.js' is not defined by "exports" in /work/esm/pkg/node_modules/tiny-date/package.json imported from /work/esm/pkg/c.mjs
```

같은 `"tiny-date"`가 `import`에서는 ESM 빌드, `require`에서는 CJS 빌드로 갔다. `"exports"`에 적지 않은 내부 파일은 깊은 경로로 불러도 막힌다. 라이브러리를 올렸더니 `ERR_PACKAGE_PATH_NOT_EXPORTED`가 나면, 내부 경로를 직접 import하던 코드가 새로 생긴 `"exports"`에 막힌 것이다. 이 구성은 편하지만 한 앱에서 두 빌드가 함께 로드되면 상태가 두 벌이 된다.

## TypeScript와 번들러가 바꿔 쓰는 코드

TypeScript를 CJS로 출력하면 import가 어떻게 바뀌는지 보면 두 시스템의 차이가 더 분명해진다. `--module commonjs --esModuleInterop`으로 컴파일했다.

```ts
import express from "express";
import { readFile } from "node:fs/promises";
export const app = express();
export const load = () => readFile("a.txt");
```

```js
"use strict";
var __importDefault = (this && this.__importDefault) || function (mod) {
    return (mod && mod.__esModule) ? mod : { "default": mod };
};
Object.defineProperty(exports, "__esModule", { value: true });
exports.load = exports.app = void 0;
const express_1 = __importDefault(require("express"));
const promises_1 = require("node:fs/promises");
exports.app = (0, express_1.default)();
const load = () => (0, promises_1.readFile)("a.txt");
exports.load = load;
```

세 가지가 보인다. 첫째, default import는 `__importDefault`를 거친다. CJS 모듈에는 default가 없으니 `module.exports` 전체를 `{ default: ... }`로 감싸고, ESM에서 변환된 모듈(`__esModule: true` 표시가 있는)이면 그대로 쓴다. `esModuleInterop`이 꺼져 있던 시절에 `import express from "express"`가 `undefined`를 주던 이유가 이것이다. 둘째, `readFile`을 지역 변수로 꺼내 두지 않고 `promises_1.readFile`로 부를 때마다 읽는다. 라이브 바인딩을 흉내 내는 방법이다. 셋째, `(0, fn)()`은 `this`가 모듈 객체로 묶이지 않게 하려는 장치다.

TypeScript 5.0부터는 `verbatimModuleSyntax`를 켜면 `import type`이 아닌 import를 그대로 남긴다. 타입만 쓰는 import는 `import type`으로 적으라는 규칙이 생기고, 출력에서 import가 몰래 사라지는 일이 없어진다.

번들러가 안 쓰는 export를 빼는 트리 셰이킹도 이 정적 구조 위에서 동작한다. 실행하지 않고도 누가 무엇을 import하는지 알 수 있으니 쓰이지 않는 export를 지운다. `require`는 실행 중에 무엇이든 꺼낼 수 있어서 이 분석이 어렵다. 자세한 조건과 배럴 파일 문제는 [코드 스플리팅 글](/posts/code-splitting)에 있다.

## React 코드에서 모듈 경계를 만나는 순간

`React.lazy`는 동적 `import()`가 돌려주는 모듈 네임스페이스에서 `default`를 꺼내 컴포넌트로 쓴다. 이름 있는 내보내기만 있는 파일을 그대로 넘기면 깨진다. React 19.3의 서버 렌더러(`prerenderToNodeStream`)로 확인했다.

```js
// chart.mjs
export function Chart() { return <svg data-chart="" />; }

const LazyChart = React.lazy(() => import("./chart.mjs"));
const LazyChartFixed = React.lazy(() =>
  import("./chart.mjs").then((m) => ({ default: m.Chart })),
);
```

```text
lazy: Expected the result of a dynamic import() call. Instead received: [Module: null prototype] { Chart: [Function: Chart] }

Your code should look like: 
  const MyComponent = lazy(() => import('./MyComponent'))
onError: Element type is invalid: expected a string (for built-in components) or a class/function (for composite components) but got: undefined. You likely forgot to export your component from the file it's defined in, or you might have mixed up default and named imports.
```

고친 쪽은 `<svg data-chart=""></svg>`를 그렸다. 첫 번째는 서버 렌더링에 실패하고 fallback을 남긴 채 클라이언트 렌더링으로 넘겼다. "mixed up default and named imports"라는 문구를 보면 default와 이름 있는 내보내기가 어긋난 곳을 찾는다. 같은 오류는 일반 import에서도 `import Button from "./button"`인데 파일은 `export function Button`일 때 난다.

두 번째는 모듈 스코프의 상태다. 모듈은 한 번만 평가되니 모듈 최상위 변수는 그 모듈을 import한 모든 곳이 공유한다. 브라우저에서는 사용자 한 명이니 캐시로 쓰기 좋지만, 서버 렌더링에서는 모든 요청이 같은 변수를 본다. 요청마다 달라야 할 사용자 정보를 모듈 변수에 두면 다른 사람 화면에 섞인다. 이 사고는 [SSR 글](/posts/rendering-ssr)에서 재현했다.

세 번째는 모듈 그래프 자체가 경계가 되는 경우다. Next.js App Router의 `"use client"`는 그 파일부터 아래로 이어지는 import 그래프를 클라이언트 번들로 보낸다. 서버 컴포넌트가 배럴 `index.ts`를 import하면, 배럴이 다시 내보내는 모든 모듈이 그래프에 들어와 평가된다. 이 블로그의 규칙이 컴포넌트 `index.ts`에서 클라이언트 전용 훅을 다시 내보내지 말라고 하는 이유도 이것이다. 그 훅 하나 때문에 서버 쪽에서 jotai나 react-query 모듈이 평가되어 빌드가 깨진다.

## 모듈 오류를 만났을 때 읽는 순서

모듈 오류는 메시지에 원인이 거의 다 들어 있다. 증상별로 정리하면 이렇다.

- `Cannot use import statement outside a module` 또는 `MODULE_TYPELESS_PACKAGE_JSON` 경고: 파일이 CJS로 취급되고 있다. 확장자와 가장 가까운 `package.json`의 `"type"`을 본다.
- `ERR_MODULE_NOT_FOUND`에 `Did you mean ...js`: ESM에서 확장자를 빠뜨렸다.
- `does not provide an export named ...`: 이름 있는 import와 default가 어긋났거나, `export *`가 default를 빠뜨렸거나, CJS 모듈이 정적 분석으로 찾을 수 없는 방식으로 내보냈다.
- `ERR_REQUIRE_ASYNC_MODULE`: `require`한 ESM 그래프 어딘가에 최상위 await가 있다.
- `ERR_PACKAGE_PATH_NOT_EXPORTED`: 패키지의 `"exports"`가 막은 내부 경로를 불렀다.
- 값이 가끔 `undefined`이거나 `Cannot access ... before initialization`: 순환 import를 의심한다. 번들러의 순환 감지 플러그인이나 `madge --circular`로 그래프를 그려 본다.
- 같은 싱글턴이 두 개 있다: 패키지 중복 설치나 ESM·CJS 빌드가 함께 로드됐는지 `npm ls 패키지명`으로 확인한다.

아래 칸에서 모듈 평가 순서를 계산하는 함수를 만들어 보자. `graph`는 모듈 이름마다 import하는 모듈 이름의 배열이다. `entry`부터 시작해 본문이 실행되는 순서를 돌려준다. 지금 코드는 CJS처럼 위에서부터 실행한다고 가정해서 순서가 틀리고, 공통 의존성을 두 번 넣고, 순환에서 끝나지 않는다. 기대값은 모두 같은 그래프를 실제 `.mjs` 파일로 만들어 Node 22에서 돌린 순서다.

순환 테스트에서는 `b`가 `a`보다 먼저 실행된다. `b`가 실행되는 순간 `a`의 본문은 아직 돌지 않았다. 순환 import에서 TDZ 오류가 나는 이유가 이 순서다.

## 정적인 그래프가 주는 것

ES 모듈은 값을 복사하지 않고 변수 칸을 연결하며, import와 export가 파일 최상위에 고정되어 있어서 실행하기 전에 그래프 전체를 만들고 연결할 수 있다. 그 덕분에 없는 이름은 실행 전에 잡히고, 의존성은 깊은 곳부터 한 번씩만 평가되고, 번들러는 안 쓰는 코드를 지울 수 있다. 대신 브라우저에서는 그래프의 깊이만큼 요청이 쌓이고, Node에서는 동기로 동작하던 CJS와 만나는 자리마다 규칙이 생긴다. 오류 메시지가 어느 단계(파싱, 링크, 평가, 해석)에서 났는지 보면 대부분 원인이 바로 보인다.

## 면접에서 나올 만한 질문

### CommonJS와 ES 모듈의 가장 큰 차이는

ESM은 정적이고 CJS는 동적이다. ESM의 import와 export는 파일 최상위에 고정되어 실행 전에 그래프를 만들고 이름을 연결하며, CJS의 `require`는 실행 중에 불리는 동기 함수다. 그래서 ESM은 실행 전에 없는 이름을 잡고 트리 셰이킹이 쉽다. 또 ESM은 변수 자체를 연결하는 라이브 바인딩이고, CJS는 `module.exports`에 담긴 값을 받는다.

### 라이브 바인딩이란 무엇인가

import한 이름이 내보낸 모듈의 변수 칸에 직접 연결되어, 읽을 때마다 현재 값을 본다는 뜻이다. 내보낸 모듈이 값을 바꾸면 import한 쪽에서도 바뀐 값이 보인다. 받는 쪽에서는 대입할 수 없어서 `const`처럼 동작한다. 단 `export default 식`은 그 순간의 값을 숨은 변수에 담기 때문에 원래 변수와 연결되지 않는다.

### 모듈 코드는 어떤 순서로 실행되나

엔진은 파싱, 링크, 평가 세 단계를 거친다. 평가는 의존성 그래프를 깊이 우선으로 내려가 가장 깊은 모듈부터 실행하고, 한 번 평가한 모듈은 다시 실행하지 않는다. import 문은 위치와 상관없이 본문보다 먼저 처리되어서, import 위에 쓴 코드도 의존성 실행이 끝난 뒤에 돈다. 같은 모듈인지는 해석된 URL로 판단한다.

### 순환 import가 있으면 어떻게 되나

평가 중인 모듈을 다시 만나면 들어가지 않고 넘어가서, 나중에 import된 쪽이 먼저 실행된다. 그 시점에 상대 모듈의 `let`, `const`, `class`는 초기화 전이라 읽으면 ReferenceError다. 함수 선언은 호이스팅되어 있어서 부를 수 있다. 공통 부분을 별도 모듈로 빼서 순환을 끊는 것이 근본 해결이다.

### 이름 있는 내보내기와 default 중 무엇을 쓰나

이름 있는 내보내기가 실수가 적다. 이름이 틀리면 링크 단계에서 바로 오류가 나고, 자동 import와 이름 바꾸기가 정확하다. default는 받는 쪽이 아무 이름이나 붙일 수 있고 `export *`로 다시 내보내지지도 않는다. `React.lazy`나 프레임워크의 페이지 파일처럼 default를 요구하는 자리에만 쓴다.

### Node에서 ESM과 CJS를 섞어 쓸 때 주의할 점은

ESM에서 CJS를 import하면 `module.exports`가 default로 오고, 이름 있는 import는 정적 분석으로 찾을 수 있는 것만 된다. CJS에서 ESM은 Node 22.12부터 `require`로 부를 수 있지만 최상위 await가 있으면 안 되고 `import()`를 써야 한다. 패키지가 ESM과 CJS 빌드를 함께 주면 한 앱에서 두 벌이 로드되어 상태가 갈라질 수 있다. ESM에서는 확장자, `__dirname`, JSON import 방식도 다르다.

### 브라우저에서 모듈을 번들 없이 쓰면 무엇이 느린가

import를 파싱해야 다음 파일을 알 수 있어서 그래프 깊이만큼 요청이 순서대로 쌓인다. 실험에서는 깊이 3인 그래프가 파일마다 왕복을 기다려 실행이 늦어졌고, `modulepreload`로 미리 알려 주자 네 파일이 동시에 출발해 200ms가 줄었다. 번들러는 그래프를 미리 펼쳐 파일 수를 줄이고 preload를 넣어 준다.

### React.lazy에 이름 있는 내보내기만 있는 모듈을 넘기면

`lazy`는 모듈의 `default`를 컴포넌트로 쓰기 때문에 `undefined`를 렌더링하려다 "Element type is invalid"로 실패한다. `import("./chart").then((m) => ({ default: m.Chart }))`처럼 default 모양으로 감싸서 넘긴다. 오류 문구의 "mixed up default and named imports"가 같은 원인을 가리킨다.
