층 하나를 맡은 라우터가 펌웨어 업데이트로 재부팅됐다. 3분 정도였는데, 그동안 그 층의 PC와 서버는 같은 층끼리만 통하고 바깥으로는 아무 데도 못 나갔다. 옆에 예비 라우터가 꽂혀 있었는데도 그랬다. 모든 호스트의 기본 게이트웨이가 재부팅 중인 라우터의 IP 하나로 적혀 있었기 때문이다.

라우터끼리는 [OSPF 같은 라우팅 프로토콜](/posts/routing-protocols-ospf-rip-eigrp)로 서로 끊긴 길을 알아채고 돌아간다. 그런데 호스트는 라우팅 프로토콜을 하지 않는다. DHCP로 받은 게이트웨이 주소 하나만 들고 있다가, 그 주소가 답하지 않으면 그냥 멈춘다. 이 글은 이 첫 번째 홉을 이중화하는 FHRP(First Hop Redundancy Protocol)인 VRRP, HSRP, GLBP를 보고, keepalived로 게이트웨이를 넘길 때 실제로 몇 초가 걸리는지 잰다. 그 다음 서버와 스위치 사이 선을 묶는 LACP와 리눅스 bonding, 그리고 묶어도 한 흐름은 한 선만 쓰는 이유를 본다.

로드 밸런서 두 대가 VIP를 주고받는 기본 모습은 [로드 밸런서 기본 글](/posts/load-balancer-basics)에서, 여러 부품을 나란히 둘 때의 가용성 계산은 [고가용성 글](/posts/high-availability)에서 다뤘다. 여기서는 게이트웨이와 링크 자체의 이중화에 집중한다. 실습은 Ubuntu 24.04에서 네트워크 네임스페이스와 리눅스 브리지로 같은 L2 망을 만들고 keepalived 2.2.8을 올려 했다. 출력은 모두 이 실습 망에서 받은 것이다.

## 호스트는 게이트웨이를 하나만 안다

호스트의 라우팅 테이블은 보통 두 줄이다. 내 망은 직접, 나머지는 전부 기본 게이트웨이로.

```bash
# 일반 서버의 라우팅 테이블
ip route
```

```text
default via 192.168.10.1 dev eth0
192.168.10.0/24 dev eth0 proto kernel scope link src 192.168.10.50
```

게이트웨이를 두 개 적어 두면 되지 않을까 싶지만, 호스트는 게이트웨이가 죽었는지 판단할 방법이 마땅치 않다. 리눅스는 기본 경로 두 개를 metric을 달리해 넣을 수 있지만, 앞 게이트웨이의 인터페이스가 살아 있는 한 계속 그쪽을 쓴다. 게이트웨이 라우터만 죽고 스위치 포트는 살아 있는 흔한 경우를 못 잡는다. 수백 대의 호스트에 라우팅 데몬을 깔 수도 없다.

옛날에는 다른 방법도 있었다. 라우터가 남의 망 주소에 대신 ARP 응답을 하는 proxy ARP, 라우터가 "다른 게이트웨이로 가라"고 알려 주는 ICMP redirect, 호스트가 라우터 광고를 엿듣는 IRDP 같은 것이다. 모두 호스트 쪽 동작에 기대거나 전환이 느려서 지금은 거의 쓰지 않는다.

그래서 생각을 바꿨다. 호스트는 그대로 두고, 게이트웨이 주소를 특정 장비에서 떼어 낸다. 라우터 두 대가 가상 IP 하나를 나눠 갖고, 그 순간 살아 있는 쪽이 그 IP의 주인 노릇을 한다. 호스트 입장에서는 게이트웨이가 한 번도 바뀌지 않는다. FHRP가 다 이 방식이다.

## 가상 IP와 가상 MAC을 나눠 갖는다

VRRP(Virtual Router Redundancy Protocol)는 IETF 표준이다. IPv4용 VRRPv2가 RFC 3768이고, IPv6까지 다루는 VRRPv3이 RFC 5798이다. 라우터 여러 대가 같은 VRID(가상 라우터 번호, 1~255)로 한 그룹을 만들고, 그중 하나가 마스터가 되어 가상 IP를 맡는다. 마스터는 1초(기본값)마다 224.0.0.18로 "내가 마스터다"라는 광고를 보내고, 나머지 백업은 듣기만 한다. VRRP는 IP 프로토콜 번호 112로 바로 실린다.

표준 VRRP는 가상 MAC도 정해 둔다. IPv4는 `00:00:5e:00:01:{VRID}`라서, VRID 10이면 `00:00:5e:00:01:0a`다. 가상 IP의 ARP 응답에 이 MAC을 쓰면 마스터가 바뀌어도 호스트의 ARP 표는 그대로다. 스위치만 그 MAC이 다른 포트 뒤로 옮겼다는 걸 배우면 된다.

HSRP(Hot Standby Router Protocol)는 시스코가 먼저 만든 같은 생각이다. RFC 2281로 공개됐지만 정보성 문서이고 사실상 시스코 장비 전용이다. 역할 이름이 Active와 Standby이고, Hello 3초·Hold 10초가 기본이라 VRRP보다 느긋하다. 가상 MAC은 HSRPv1이 `0000.0c07.acXX`, HSRPv2가 `0000.0c9f.fXXX`(XX는 그룹 번호) 꼴이다. 시스코만 쓰는 망이라면 HSRP, 장비가 섞이면 VRRP를 쓰는 것이 보통이다.

리눅스에서 VRRP를 구현한 대표가 keepalived다. 설정은 짧다.

```text
vrrp_instance GW {
  state BACKUP
  interface eth0
  virtual_router_id 10
  priority 150          # gw2는 100
  advert_int 1
  virtual_ipaddress {
    192.168.10.1/24
  }
}
```

두 대 다 `state BACKUP`으로 시작하게 두고 우선순위로 마스터를 정하게 하는 것이 흔한 방식이다. 한 대를 `MASTER`로 박아 두면 그 장비가 재시작할 때마다 일단 마스터를 주장하고 본다. 이 설정으로 gw1(192.168.10.2)과 gw2(192.168.10.3)를 띄우면 gw1 로그에 이렇게 남는다.

```text
Fri Oct 23 19:07:21 2026: (GW) Entering BACKUP STATE (init)
Fri Oct 23 19:07:25 2026: (GW) Entering MASTER STATE
```

```bash
# 마스터에 가상 IP가 붙었는지 확인
ip -br addr show eth0
```

```text
eth0@if3         UP             192.168.10.2/24 192.168.10.1/24
```

eth0에 원래 주소와 가상 IP가 함께 붙었다. 하나 알아 둘 것은 keepalived가 기본으로는 가상 MAC을 쓰지 않는다는 점이다. 가상 IP에 대한 ARP 응답에 gw1의 실제 MAC이 나간다. 표준의 가상 MAC을 쓰려면 `use_vmac`을 켜는데, 그러면 keepalived가 macvlan 인터페이스를 따로 만들어 그 위에 가상 IP를 붙인다. 가상 MAC을 안 쓰면 전환 때 호스트의 ARP 표가 바뀌어야 하므로, 새 마스터가 알리는 단계가 더 중요해진다.

## 누가 주인이 되나: 우선순위와 선점

마스터는 우선순위로 정한다. VRRP의 우선순위는 1~254를 설정할 수 있고 기본은 100이다. 255는 가상 IP를 자기 인터페이스의 실제 주소로 가진 "주소 주인"에게만 쓰이는 값이고, 0은 마스터가 "나 그만둔다"고 알릴 때 쓰는 특별한 값이다. 우선순위가 같으면 IP 주소가 큰 쪽이 이긴다.

선점(preempt)은 우선순위가 더 높은 장비가 나중에 살아났을 때 마스터 자리를 도로 가져갈지를 정한다. VRRP는 기본이 선점 켜짐이고, HSRP는 기본이 꺼짐이다. 선점이 켜져 있으면 고장 났던 gw1이 부팅되자마자 다시 마스터가 된다. 아래 실습에서 링크가 살아난 gw1이 1초 만에 자리를 되찾은 로그다.

```text
==> gw1.log <==
Fri Oct 23 19:08:02 2026: (GW) received lower priority (100) advert from 192.168.10.3 - discarding
Fri Oct 23 19:08:03 2026: (GW) Entering MASTER STATE

==> gw2.log <==
Fri Oct 23 19:08:03 2026: (GW) Master received advert from 192.168.10.2 with higher priority 150, ours 100
Fri Oct 23 19:08:03 2026: (GW) Entering BACKUP STATE
```

이 실습에서는 선점 순간에 0.05초 간격 ping이 하나도 빠지지 않았다. 문제는 실제 라우터는 "부팅 끝"과 "일할 준비 끝"이 다르다는 점이다. VRRP가 먼저 올라오고 OSPF 이웃이나 업링크가 아직 안 붙었는데 선점해 버리면, 호스트 트래픽을 받아 놓고 바깥으로 보낼 길이 없다. 그래서 선점을 켤 때는 선점 지연(VRRP의 preempt delay, keepalived의 `preempt_delay`)을 함께 걸어 라우팅이 안정된 뒤에 자리를 가져가게 한다. 아예 선점을 끄면 전환이 한 번으로 끝나는 대신, 마스터가 어느 장비인지 시간이 지나면서 뒤섞인다.

```bash
# 클라이언트에서 VRRP(프로토콜 112)와 ARP만 잡는다
sudo tcpdump -nn -e -i eth0 'arp or ip proto 112'
```

```text
19:07:43.964758 f6:bf:79:f4:80:9a > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42: Request who-has 192.168.10.1 (ff:ff:ff:ff:ff:ff) tell 192.168.10.1, length 28
19:07:43.964773 f6:bf:79:f4:80:9a > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42: Request who-has 192.168.10.1 (ff:ff:ff:ff:ff:ff) tell 192.168.10.1, length 28
(같은 GARP가 세 번 더)
19:07:48.964909 f6:bf:79:f4:80:9a > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42: Request who-has 192.168.10.1 (ff:ff:ff:ff:ff:ff) tell 192.168.10.1, length 28
```

gw1의 마지막 광고가 40.355초, gw2의 첫 광고와 GARP가 43.964초다. 3.609초 차이로, 표준이 정한 Master_Down_Interval과 정확히 맞는다. VRRPv2에서 이 값은 `3 × 광고 간격 + (256 − 우선순위) / 256`이다. 우선순위 100이면 스큐 시간이 156/256 = 0.609초라 합이 3.609초가 된다. 스큐 시간은 우선순위가 높은 백업일수록 짧아서, 백업이 여럿이면 우선순위가 높은 쪽이 먼저 손을 든다.

GARP(Gratuitous ARP)는 아무도 묻지 않았는데 "192.168.10.1은 나다"를 알리는 ARP다. 보낸 쪽 MAC이 gw2의 것(`f6:bf:...`)이라, 이걸 받은 클라이언트는 ARP 표를 고친다. keepalived는 마스터가 된 순간 다섯 번, 5초 뒤에 다시 다섯 번 보낸다(48.96초 줄). 첫 묶음을 놓친 장비를 위한 것이다. 클라이언트의 ARP 표가 실제로 바뀌었다.

```bash
# 클라이언트의 ARP 표에서 가상 IP 항목 (전환 전, 전환 후)
ip neigh show 192.168.10.1
```

```text
192.168.10.1 dev eth0 lladdr fe:6d:e1:ad:04:02 REACHABLE
192.168.10.1 dev eth0 lladdr f6:bf:79:f4:80:9a REACHABLE
```

ping은 30개가 빠졌다. 약 3.1초다. 링크를 내린 시점이 마지막 광고 0.45초 뒤였으니 3.609 − 0.45 ≈ 3.16초, 계산과 맞는다.

이번에는 gw1을 정상 종료(SIGTERM)해 본다. 점검 때문에 일부러 내리는 경우다.

```text
19:08:05.316135 IP 192.168.10.2 > 224.0.0.18: VRRPv2, Advertisement, vrid 10, prio 150, authtype none, intvl 1s, length 20
19:08:05.620231 IP 192.168.10.2 > 224.0.0.18: VRRPv2, Advertisement, vrid 10, prio 0, authtype none, intvl 1s, length 20
19:08:06.229790 IP 192.168.10.3 > 224.0.0.18: VRRPv2, Advertisement, vrid 10, prio 100, authtype none, intvl 1s, length 20
```

gw1이 떠나면서 우선순위 0 광고를 보냈다. 표준에 따라 백업은 이걸 받으면 3배 간격을 기다리지 않고 스큐 시간만 기다린다. 05.620에서 06.230까지 0.61초, 계산한 스큐 시간 그대로다. 0.05초 간격 ping은 9개, 약 0.45초 빠졌다. 계획된 점검이라면 이렇게 keepalived를 먼저 정상 종료하고 장비를 내리면 끊김이 3초대에서 0.5초대로 준다.

더 줄이려면 광고 간격을 줄인다. VRRPv3은 센티초 단위로 간격을 줄 수 있다. 다만 라우팅 프로토콜의 Hello와 마찬가지로, 마스터 CPU가 잠깐 바빠서 광고가 늦으면 멀쩡한 마스터를 두고 전환이 일어난다. 1초 간격, 3초대 전환이 많은 망의 기본으로 쓰이는 이유다.

## 살아 있어도 쓸모없는 마스터

VRRP 광고는 마스터 장비가 살아 있는지만 알려 준다. 마스터의 업링크가 끊겨 바깥으로 갈 길이 없어도, 안쪽 인터페이스로는 광고가 잘 나가니 계속 마스터다. 호스트 트래픽은 마스터까지 와서 버려진다.

그래서 FHRP에는 추적(tracking)이 있다. 지정한 인터페이스나 경로, 스크립트 결과가 나빠지면 자기 우선순위를 깎는다. 깎인 우선순위가 백업보다 낮아지면 선점이 켜진 백업이 마스터를 가져간다. keepalived에서는 이렇게 쓴다.

```text
vrrp_script chk_uplink {
  script "/usr/bin/ping -c1 -W1 10.0.0.1"   # 업링크 너머 라우터에 닿는지
  interval 2
  fall 2                                      # 두 번 연속 실패하면 실패로
  rise 2
  weight -60                                  # 실패하면 우선순위 150 → 90
}

vrrp_instance GW {
  ...
  track_interface {
    eth1 weight -60                           # 업링크 인터페이스가 내려가도 -60
  }
  track_script {
    chk_uplink
  }
}
```

깎는 폭은 "깎인 마스터가 백업보다 낮아지는" 만큼이어야 한다. 150에서 40만 깎으면 110이라 여전히 백업(100)보다 높아서 아무 일도 안 일어난다. 반대로 추적 대상을 너무 많이 걸면, 두 장비가 같은 외부 상태를 보는 경우 둘 다 깎여서 결국 아무것도 바뀌지 않는다. 추적은 "이 장비에만 해당하는 고장"을 잡는 데 쓴다.

## 둘 다 마스터가 되면

VRRP는 광고가 안 들리면 상대가 죽었다고 판단한다. 그런데 광고가 안 들리는 이유가 상대의 죽음이 아니라 둘 사이 길의 문제일 수도 있다. 실습에서 gw2가 VRRP 패킷만 버리게 해 봤다.

```bash
# gw2가 VRRP 광고만 못 듣게 만든다
sudo ip netns exec gw2 iptables -A INPUT -p vrrp -j DROP
```

```text
Fri Oct 23 19:08:24 2026: (GW) Entering BACKUP STATE
Fri Oct 23 19:08:27 2026: (GW) Entering MASTER STATE
```

```bash
# 두 장비에서 각각 주소 확인 (위가 gw1, 아래가 gw2)
ip -br addr show eth0
```

```text
eth0@if3         UP             192.168.10.2/24 192.168.10.1/24
eth0@if4         UP             192.168.10.3/24 192.168.10.1/24
```

같은 가상 IP가 두 장비에 동시에 붙었다. 이걸 스플릿 브레인(split brain)이라고 한다. 둘 다 GARP를 보내고 ARP에 답하니, 호스트의 ARP 표와 스위치의 MAC 표가 둘 사이를 오간다. 어떤 호스트는 gw1로, 어떤 호스트는 gw2로 가고, 상태를 들고 있는 방화벽이나 NAT라면 연결이 반쯤 끊긴다. 가상 MAC을 쓰는 경우에는 같은 MAC이 두 포트에서 나타나 스위치가 MAC 이동(flapping) 경고를 쏟아낸다.

현장에서 이걸 만드는 원인은 대개 사소하다. 한쪽에만 방화벽 규칙을 넣으면서 프로토콜 112를 빠뜨렸거나, VLAN 설정이 한쪽 트렁크에서만 빠졌거나, 멀티캐스트를 막는 스위치 설정이 들어갔다. 막는 방법은 광고가 지나는 길을 하나로 두지 않는 것(광고를 여러 인터페이스로 보내거나 유니캐스트 피어를 함께 두기), 그리고 양쪽에서 같은 VRID·같은 인증·같은 방화벽 정책을 설정 관리 도구로 함께 배포하는 것이다. keepalived는 `unicast_peer`로 상대 주소를 직접 지정해 멀티캐스트 없이 광고를 보낼 수 있다. 같은 L2 망에 다른 팀이 같은 VRID를 쓰는 VRRP를 올려도 서로의 광고를 자기 그룹 것으로 착각한다. VRID는 망 안에서 겹치지 않게 관리한다.

리더 선출에서 같은 문제를 다루는 방식, 즉 다수결과 임대(lease)로 "둘 다 리더"를 막는 법은 [리더 선출 글](/posts/leader-election)에 있다. VRRP는 장비 두 대만으로 판단하기 때문에 다수결을 할 수 없다. 그래서 길을 여러 개 두는 것이 사실상 유일한 방어다.

## 한 대만 일하는 게 아깝다면

VRRP와 HSRP에서 백업은 평소에 아무 일도 하지 않는다. 라우터 두 대를 사 놓고 한 대 몫만 쓰는 셈이다. 이걸 피하는 고전적인 방법은 그룹을 두 개 만드는 것이다. 그룹 1은 gw1이 마스터, 그룹 2는 gw2가 마스터가 되게 우선순위를 엇갈리게 주고, DHCP로 호스트 절반에게는 그룹 1의 가상 IP를, 나머지 절반에게는 그룹 2의 가상 IP를 게이트웨이로 준다. 둘 다 일하고, 한쪽이 죽으면 남은 쪽이 두 가상 IP를 모두 맡는다. 대신 DHCP 범위를 둘로 나눠 관리해야 하고, 부하가 정확히 반반이 되지는 않는다.

GLBP(Gateway Load Balancing Protocol)는 시스코가 이걸 프로토콜 안에서 푼 것이다. 그룹의 가상 IP는 하나인데, 대표 장비(AVG, Active Virtual Gateway)가 ARP 요청에 답할 때마다 서로 다른 가상 MAC을 돌려준다. 각 가상 MAC은 그룹 안의 다른 라우터(AVF, Active Virtual Forwarder)가 맡는다. 호스트 A는 가상 IP의 MAC을 gw1 것으로, 호스트 B는 gw2 것으로 알게 되어 같은 게이트웨이 주소로 서로 다른 라우터를 쓴다. 한 그룹에 AVF는 넷까지 둘 수 있고, 한 AVF가 죽으면 다른 AVF가 그 가상 MAC까지 맡는다. 시스코 전용이고, 호스트 단위로 나뉘기 때문에 트래픽이 많은 서버 몇 대가 한쪽에 몰리면 고르게 나뉘지 않는다.

데이터 센터처럼 라우터 여러 대가 모두 같은 게이트웨이 MAC으로 동시에 답하는 방식(애니캐스트 게이트웨이, EVPN의 분산 게이트웨이)도 있다. 이건 [망 구조 설계 글](/posts/network-design-three-tier-spine-leaf)의 스파인-리프 구조에서 리프마다 게이트웨이를 두는 모양으로 이어진다.

## 선 두 가닥을 하나로: 링크 묶기와 LACP

게이트웨이를 이중화해도 서버와 스위치를 잇는 선이 하나면 그 선이 단일 장애 지점이다. 선을 두 가닥 꽂으면 해결될 것 같지만, 스위치 둘 사이에 선을 두 개 그냥 꽂으면 L2 고리가 생기고 STP가 하나를 막아 버린다([라우터와 스위치 글](/posts/router-vs-switch)). 원하는 것은 두 선을 동시에 쓰면서 하나가 끊겨도 버티는 것이다.

링크 묶기(link aggregation, LAG)는 여러 물리 포트를 하나의 논리 포트로 만든다. STP와 MAC 학습은 논리 포트 하나만 보니 고리가 없고, 대역폭은 묶은 선만큼 늘어난다. 시스코는 EtherChannel, 리눅스는 bonding, 다른 장비는 port-channel이나 trunk라고 부른다.

묶는 방법은 둘이다. 양쪽에 그냥 "이 포트들은 한 묶음"이라고 설정하는 정적 LAG와, 양쪽이 LACP(Link Aggregation Control Protocol)로 대화해서 묶는 동적 LAG다. LACP는 IEEE 802.3ad로 시작해 지금은 802.1AX에 정리되어 있다. 각 포트로 LACPDU를 주고받으며 "나는 어느 장비의 몇 번 묶음이다"를 확인하고, 상대도 같은 묶음이라고 답한 포트만 묶음에 넣는다.

정적 LAG가 위험한 이유가 여기 있다. 케이블 하나를 엉뚱한 스위치 포트에 꽂아도 정적 LAG는 그 포트로 트래픽을 보낸다. 상대 쪽은 그 포트를 묶음으로 모르니 프레임이 엉뚱한 곳으로 가거나 버려진다. LACP는 상대 정보를 확인하므로 잘못 꽂힌 포트는 묶음에 들어가지 않는다. 또 선은 살아 있는데 상대 장비의 그 포트가 멈춘 경우도 LACPDU가 끊기는 것으로 알아챈다.

LACP 세부 중 실무에서 고르는 것은 두 가지다. 하나는 active와 passive다. active는 먼저 LACPDU를 보내고, passive는 받으면 답만 한다. 둘 다 passive면 아무도 말을 걸지 않아 묶음이 안 생기니 적어도 한쪽은 active로 둔다. 다른 하나는 속도(rate)다. slow는 30초, fast는 1초마다 LACPDU를 보내고, 3번 못 받으면 그 포트를 뺀다. slow면 조용한 장애를 90초 동안 모를 수 있어서 서버 쪽에서는 fast를 많이 쓴다. 묶는 포트들은 속도와 듀플렉스가 같아야 하고, 한 묶음은 보통 같은 두 장비 사이에서만 만들어진다(예외는 뒤의 MLAG).

## 리눅스 bonding 모드

리눅스 bonding 드라이버에는 일곱 가지 모드가 있다. 현장에서 쓰는 것은 대부분 두 가지다.

active-backup(mode 1)은 한 번에 한 포트만 쓰고 나머지는 대기한다. 스위치 쪽에 아무 설정도 필요 없고, 서로 다른 스위치 두 대에 하나씩 꽂아도 된다. 대역폭은 늘지 않지만 가장 단순하고 안전하다. 802.3ad(mode 4)는 LACP로 스위치와 묶음을 맺고 모든 포트를 쓴다. 스위치에도 LACP 묶음 설정이 있어야 한다.

나머지는 이렇다. balance-rr(mode 0)는 패킷을 포트에 번갈아 보내 한 흐름도 여러 선을 쓰지만, 순서가 뒤바뀐 패킷 때문에 TCP 성능이 오히려 떨어질 수 있다. balance-xor(mode 2)는 해시로 포트를 고르는 정적 LAG, broadcast(mode 3)는 모든 포트로 똑같이 보낸다. balance-tlb(mode 5)와 balance-alb(mode 6)는 스위치 설정 없이 송신(alb는 ARP를 조작해 수신까지) 부하를 나눈다.

Ubuntu 서버에서는 netplan으로 설정한다.

```yaml
# /etc/netplan/60-bond.yaml
network:
  version: 2
  ethernets:
    eno1: {}
    eno2: {}
  bonds:
    bond0:
      interfaces: [eno1, eno2]
      addresses: [10.0.0.10/24]
      routes:
        - to: default
          via: 10.0.0.1
      parameters:
        mode: 802.3ad
        lacp-rate: fast
        mii-monitor-interval: 100
        transmit-hash-policy: layer3+4
```

```bash
# 원격 접속 중이면 try로 먼저 적용해 본다 (확인하지 않으면 120초 뒤 되돌아간다)
sudo netplan try
# 묶음 상태 보기
cat /proc/net/bonding/bond0
```

`/proc/net/bonding/bond0`에서 볼 곳은 정해져 있다. 맨 위 `Bonding Mode`와 `Transmit Hash Policy`가 의도한 값인지, 포트마다 `MII Status: up`인지, 802.3ad라면 포트마다 `Aggregator ID`가 모두 같은지, `Partner Mac Address`가 0이 아닌 스위치 MAC인지다. Aggregator ID가 포트마다 다르면 스위치가 그 포트들을 한 묶음으로 받아들이지 않은 것이고, 파트너 MAC이 `00:00:00:00:00:00`이면 스위치에서 LACPDU가 오지 않는 것이다. 이 글의 실습 환경 커널에는 bonding 모듈이 없어서 실제 출력은 싣지 않았다.

`mii-monitor-interval: 100`은 100ms마다 포트의 링크 상태를 확인하라는 뜻이다. 이걸 0으로 두면(기본값) 포트가 내려가도 bonding이 모르는 경우가 있으니 꼭 넣는다.

## 한 흐름은 한 링크만 쓴다

10Gbps 선 두 개를 묶었는데, 백업 서버 한 대에서 스토리지로 파일 하나를 복사하면 10Gbps에서 멈춘다. 묶음이 고장 난 게 아니다. LAG는 패킷마다 포트를 고르지 않고, 흐름(같은 출발지·목적지 쌍)마다 포트를 고른다. 같은 TCP 연결의 패킷이 서로 다른 선으로 가면 도착 순서가 뒤바뀔 수 있고, TCP는 순서가 뒤바뀐 패킷을 손실로 오해해 속도를 줄인다. 그래서 헤더 몇 개를 해시해 포트를 정하고, 같은 흐름은 언제나 같은 포트로 보낸다.

어떤 헤더를 해시할지가 해시 정책이다. 리눅스 bonding의 `xmit_hash_policy` 기본값은 layer2로, 출발지와 목적지 MAC만 본다. 서버가 게이트웨이 하나와만 통신하면 목적지 MAC이 언제나 같아서 모든 트래픽이 한 포트로 몰린다. layer2+3은 IP를 더하고, layer3+4는 포트 번호까지 더해서 같은 두 호스트 사이의 연결들도 서로 다른 선으로 나뉜다. 스위치 쪽 해시 정책은 스위치에서 따로 정한다. 서버에서 나가는 방향과 들어오는 방향의 분배는 각자의 해시가 정한다.

## 스위치 두 대에 걸친 묶음: MLAG

LACP 묶음은 원래 같은 두 장비 사이에서만 만든다. 그런데 서버가 스위치 한 대에만 두 선을 꽂으면 그 스위치가 죽을 때 둘 다 끊긴다. 스위치 두 대에 하나씩 꽂고 싶다. active-backup bonding이면 그냥 되지만 한 선만 쓴다. 두 선을 다 쓰면서 스위치도 이중화하려면 스위치 두 대가 서버에게 "우리는 한 대"인 척해야 한다.

MLAG(Multi-Chassis LAG)가 그 일을 한다. 시스코 Nexus는 vPC, 다른 회사는 MC-LAG 같은 이름을 쓴다. 두 스위치가 피어 링크로 이어져 서로의 MAC 표와 묶음 상태를 동기화하고, 서버에게는 같은 시스템 ID로 LACPDU를 보낸다. 서버는 평범한 802.3ad 묶음 하나로 보고, 실제로는 두 스위치에 걸쳐 있다.

MLAG에도 스플릿 브레인이 있다. 피어 링크가 끊겼는데 두 스위치가 모두 살아 있으면, 둘 다 자기가 묶음의 주인이라고 생각하고 따로 움직인다. 그래서 MLAG는 피어 링크와 별개로 관리망 같은 다른 길로 상대 생존을 확인하는 keepalive를 둔다. 피어 링크만 끊기고 상대가 살아 있다고 확인되면 한쪽(보통 secondary)이 자기 쪽 묶음 포트를 내려서 둘이 동시에 일하는 것을 막는다. VRRP의 스플릿 브레인과 같은 문제를 길을 하나 더 둬서 푸는 것이다.

MLAG는 같은 회사 스위치 두 대만 짝이 될 수 있고, 두 스위치의 소프트웨어 버전과 설정이 엇갈리면 이상하게 동작한다. 요즘 데이터 센터는 EVPN의 멀티호밍(ESI-LAG)으로 같은 일을 표준 방식으로, 두 대 이상의 스위치에 걸쳐 하기도 한다.

## 현장에서 이중화를 의심하는 순간

게이트웨이 이중화 장애는 증상으로 갈린다. 몇 초 동안 끊겼다가 살아났다면 전환이 일어난 것이다. 두 장비의 VRRP 로그에서 `Entering MASTER STATE`와 `BACKUP STATE`가 언제 찍혔는지 보고, 끊긴 시간이 Master_Down_Interval과 비슷한지 본다. 이유 없이 전환이 반복되면 광고가 가끔씩 늦거나 빠지는 것이다. 마스터 CPU 사용률, 그 인터페이스의 드롭 카운터, 광고가 지나는 스위치의 멀티캐스트 설정을 본다.

일부 호스트만 바깥으로 못 나가는 경우는 GARP를 못 받았거나 무시한 호스트다. 그 호스트의 ARP 표에서 게이트웨이 MAC이 현재 마스터의 MAC인지 확인한다. 리눅스는 `ip neigh`, 윈도우는 `arp -a`다. 일부 보안 장비나 오래된 OS는 GARP를 무시하도록 설정되어 있어서, ARP 항목이 만료될 때까지(수십 초~몇 분) 죽은 MAC으로 보낸다. 가상 MAC을 쓰면 이 문제는 없어진다.

전환은 됐는데 연결이 끊긴다면 상태를 들고 있는 장비다. 게이트웨이가 NAT나 상태 방화벽을 겸하면 새 마스터는 기존 연결의 상태를 모른다. 리눅스에서는 conntrackd로 연결 상태를 두 장비 사이에 동기화한다.

묶음 쪽은 대역폭 증상이 많다. 묶음 전체 사용률은 50%인데 선 하나는 100%라면 해시 분배가 기울었다. 포트별 카운터를 따로 본다.

```bash
# 포트별 송수신 바이트와 드롭을 따로 본다
ip -s link show eno1
ip -s link show eno2
```

해시 정책이 layer2로 남아 있지 않은지 먼저 확인하고, 그래도 기울면 소수의 큰 흐름이 원인이다. LACP 묶음이 아예 안 올라오면 `/proc/net/bonding/bond0`의 파트너 정보와 Aggregator ID를 보고, 스위치에서 해당 포트들이 같은 port-channel에 들어 있는지, 한쪽만 fast rate인지 확인한다. 한 포트가 계속 묶음에 들어갔다 나갔다 하면(flapping) 케이블이나 광 모듈을 의심한다.

클라우드에서는 이 글의 대부분이 그대로 되지 않는다. 가상 네트워크가 멀티캐스트와 GARP를 막거나 무시하기 때문에 VRRP로 IP를 옮길 수 없다. 대신 클라우드 API로 보조 IP나 Elastic IP를 다른 인스턴스로 옮기거나, 라우트 테이블의 대상을 바꾸거나, 처음부터 관리형 로드 밸런서와 NAT 게이트웨이를 쓴다. 물리 링크 묶기는 클라우드가 대신 해 준다.

## 주소는 그대로, 주인만 바뀐다

FHRP는 호스트가 아는 게이트웨이 주소를 장비에서 떼어 내 살아 있는 쪽이 맡게 한다. 백업은 광고가 3번 간격과 스큐 시간만큼 끊기면 가상 IP를 가져가고 GARP로 알리니, 기본 설정에서 끊김은 3초 남짓이고 정상 종료면 1초 아래다. 마스터가 살아 있어도 쓸모없는 경우는 추적으로, 둘 다 마스터가 되는 경우는 광고 길을 여러 개 두는 것으로 막는다. 링크 묶기는 선을 이중화하면서 대역폭도 늘리지만 흐름 단위로 해시하기 때문에 한 흐름은 선 하나를 넘지 못한다. 이 게이트웨이와 링크들이 모여 어떤 모양의 망이 되는지는 [망 구조 설계 글](/posts/network-design-three-tier-spine-leaf)에서 이어진다.

## 면접에서 나올 만한 질문

### FHRP는 왜 필요한가요?

호스트는 라우팅 프로토콜을 하지 않고 기본 게이트웨이 IP 하나만 들고 있어서, 그 라우터가 죽으면 예비 라우터가 있어도 바깥으로 못 나간다. FHRP는 라우터 여러 대가 가상 IP 하나를 나눠 갖고, 살아 있는 쪽이 그 IP의 주인 노릇을 하게 만든다. 호스트 설정을 바꾸지 않고 게이트웨이를 이중화하는 것이 목적이다. VRRP는 표준, HSRP와 GLBP는 시스코 전용이다.

### VRRP에서 백업이 마스터가 되기까지 얼마나 걸리나요?

마스터의 광고가 Master_Down_Interval 동안 오지 않으면 전환된다. VRRPv2에서 이 값은 3 × 광고 간격 + (256 − 우선순위)/256초라, 기본 1초 간격에 우선순위 100이면 3.609초다. 실습에서도 마지막 광고와 새 마스터의 첫 광고 사이가 정확히 3.609초였다. 마스터가 정상 종료하면 우선순위 0 광고를 보내서 백업은 스큐 시간(0.61초)만 기다린다.

### 전환 뒤 호스트는 새 마스터를 어떻게 알게 되나요?

새 마스터가 가상 IP에 대한 Gratuitous ARP를 브로드캐스트한다. 스위치는 그 MAC이 어느 포트 뒤에 있는지 다시 배우고, 호스트는 ARP 표를 고친다. 표준 VRRP처럼 가상 MAC을 쓰면 호스트의 ARP 표는 바뀔 필요가 없고 스위치만 고치면 된다. keepalived는 기본으로 실제 MAC을 쓰기 때문에 GARP가 더 중요하고, GARP를 무시하는 호스트는 ARP 항목이 만료될 때까지 끊긴다.

### 선점은 켜는 게 좋나요?

우선순위 높은 장비가 돌아왔을 때 자리를 되찾게 하려면 켠다. 다만 라우터가 부팅 직후 VRRP만 먼저 올라오고 라우팅이 아직 안정되지 않았을 때 선점하면 트래픽을 받아 버리는 문제가 있어서 선점 지연을 함께 건다. 선점을 끄면 전환이 한 번으로 끝나는 대신 시간이 지나며 어느 장비가 마스터인지 뒤섞인다. VRRP는 기본이 켜짐, HSRP는 꺼짐이다.

### VRRP에서 스플릿 브레인은 어떻게 생기고 어떻게 막나요?

두 장비가 모두 살아 있는데 광고만 서로 못 들으면 둘 다 마스터가 되어 같은 가상 IP를 주장한다. 한쪽 방화벽에서 프로토콜 112를 막았거나 VLAN이 한쪽에서만 빠진 경우가 흔하다. 호스트 ARP 표와 스위치 MAC 표가 둘 사이를 오가고 상태 방화벽의 연결이 깨진다. 광고가 지나는 길을 여러 개 두거나 유니캐스트 피어를 추가하고, 두 장비의 설정을 함께 배포해서 막는다.

### LACP로 10G 두 개를 묶었는데 파일 복사가 10G를 넘지 않는 이유는 무엇인가요?

LAG는 패킷이 아니라 흐름 단위로 포트를 고르기 때문이다. 같은 연결의 패킷이 여러 선으로 나뉘면 순서가 뒤바뀌고 TCP가 이를 손실로 보고 속도를 줄이니, 헤더를 해시해 한 흐름은 한 선에 고정한다. 그래서 연결 하나의 상한은 선 하나의 속도다. 여러 연결로 나눠 보내거나 더 빠른 선을 써야 한다.

### 정적 LAG 대신 LACP를 쓰는 이유는 무엇인가요?

LACP는 포트마다 상대가 같은 묶음인지 LACPDU로 확인해서, 케이블을 엉뚱한 포트에 꽂아도 그 포트를 묶음에 넣지 않는다. 링크는 살아 있는데 상대 포트가 멈춘 경우도 LACPDU가 끊기는 것으로 잡는다. 정적 LAG는 이런 확인 없이 트래픽을 보내 프레임이 사라진다. fast rate면 1초 간격, 3번 놓치면 3초 안에 포트를 뺀다.

### MLAG는 무엇이고 무엇을 조심해야 하나요?

스위치 두 대가 피어 링크로 상태를 동기화하고 서버에게 한 대인 것처럼 LACP로 답해서, 서버가 두 스위치에 걸친 묶음 하나를 쓰게 하는 기술이다. 스위치 이중화와 두 선 동시 사용을 함께 얻는다. 피어 링크만 끊기고 둘 다 살아 있으면 스플릿 브레인이 되므로, 다른 길로 상대를 확인하는 keepalive를 두고 한쪽이 묶음 포트를 내리게 한다. 같은 회사 장비끼리만 짝이 된다.
