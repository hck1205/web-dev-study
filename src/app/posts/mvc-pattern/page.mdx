주문 화면에 쿠폰 입력칸 하나를 추가해 달라는 요청을 받았다고 하자. 코드를 열어 보면 `OrderController`에 메서드 하나가 300줄이다. 요청 파라미터를 꺼내고, 재고를 SQL로 직접 조회하고, 할인율을 계산하고, 메일을 보내고, 마지막에 템플릿에 넘길 값을 만든다. 쿠폰 할인을 어디에 끼워 넣어야 할지 감이 안 온다. 같은 계산이 모바일 API 컨트롤러에도 복사돼 있다는 걸 나중에 알게 된다.

이 프로젝트도 처음에는 MVC로 시작했을 것이다. 폴더도 `controllers`, `models`, `views`로 잘 나뉘어 있다. 그런데 역할은 나뉘지 않았다. MVC가 무엇을 나누자는 약속인지, 웹에서 그 약속이 어떻게 변했는지부터 보면 이런 코드가 왜 생기는지 보인다.

## 원래 MVC는 웹을 위한 게 아니었다

MVC는 1979년 무렵 트뤼그베 린스쿠그(Trygve Reenskaug)가 제록스 PARC에서 Smalltalk로 GUI를 만들면서 정리한 생각이다. 웹이 나오기 10년도 더 전이다.

그때 풀려던 문제는 이랬다. 같은 데이터를 표로도 보고 그래프로도 보는 프로그램이 있다. 표에서 숫자를 고치면 그래프도 바로 바뀌어야 한다. 데이터를 화면 코드 안에 넣어 두면 화면마다 데이터가 따로 놀고, 화면을 하나 추가할 때마다 다른 화면 코드를 고쳐야 한다.

그래서 데이터와 규칙을 모델로 떼어 냈다. 뷰는 모델을 그리기만 하고, 컨트롤러는 마우스·키보드 입력을 받아 모델을 바꾼다. 모델이 바뀌면 자신을 지켜보는 뷰들에게 알린다(옵서버 패턴). 뷰는 알림을 받고 모델을 다시 읽어 그린다.

## HTTP 위로 옮기면서 생긴 변화

1990년대 후반 자바 진영에서 JSP로 웹을 만들 때, 처음에는 JSP 파일 하나가 요청을 받고 DB를 읽고 HTML까지 만들었다(Model 1이라고 불렀다). 화면 코드와 SQL이 한 파일에 섞이니 금방 엉켰다. 그래서 요청은 서블릿이 받아 처리하고, JSP는 결과를 그리기만 하는 구조가 나왔다. 이걸 Model 2라고 불렀고, 사람들이 Smalltalk의 MVC 이름을 빌려 붙였다. Struts, Spring MVC, Rails, Django가 모두 이 계열이다.

이름은 같지만 몇 가지가 크게 다르다.

먼저 알림이 없다. HTTP는 요청 하나에 응답 하나로 끝난다. 서버의 모델이 바뀌었다고 이미 받아 간 브라우저 화면을 다시 그리게 할 방법이 없다. 그래서 웹 MVC의 흐름은 원래의 삼각형이 아니라 컨트롤러 → 모델 → 컨트롤러 → 뷰의 일직선이 된다. 뷰는 모델을 지켜보지 않고, 컨트롤러가 건네준 값을 한 번 그리고 끝난다.

다음으로 컨트롤러의 뜻이 바뀌었다. Smalltalk에서는 위젯 하나마다 컨트롤러가 붙어 키 입력을 해석했다. 웹에서는 URL 하나, HTTP 요청 하나를 받는 곳이 컨트롤러다. 입력 해석의 단위가 키 입력에서 HTTP 요청으로 커진 셈이다.

마지막으로 "모델"이라는 말이 두 가지를 가리키게 됐다. Spring의 `Model` 객체처럼 뷰에 넘길 값 꾸러미를 모델이라 부르기도 하고, 주문·회원 같은 도메인 객체와 규칙 전체를 모델이라 부르기도 한다. 면접에서 "모델에 뭐가 들어가냐"는 질문을 받으면 이 둘을 나눠서 답하는 편이 정확하다.

## 컨트롤러가 뚱뚱해지는 이유

처음 장면으로 돌아가 보자. 컨트롤러가 비대해지는 건 게을러서라기보다 컨트롤러가 가장 손 닿기 쉬운 곳이라서다. 요청 값도 여기 있고, 응답도 여기서 만든다. 새 요구 사항이 오면 여기에 한 줄 넣는 게 제일 빠르다. Express로 쓰면 이런 모양이 된다.

```js
app.post("/orders", async (req, res) => {
  const { productId, quantity, couponCode } = req.body;
  if (!quantity || quantity < 1) return res.status(400).send("수량 오류");

  const product = await db.query("SELECT * FROM products WHERE id = $1", [productId]);
  if (product.stock < quantity) return res.status(409).send("재고 부족");

  let price = product.price * quantity;
  if (couponCode === "WELCOME10") price = Math.floor(price * 0.9);
  if (price < 30000) price += 3000; // 배송비

  await db.query("UPDATE products SET stock = stock - $1 WHERE id = $2", [quantity, productId]);
  const order = await db.query("INSERT INTO orders ...", [/* ... */]);
  await mailer.send(req.user.email, "주문 완료", `${price}원`);

  res.render("order-complete", { order, price });
});
```

이 코드의 문제는 길이가 아니다. 할인과 배송비 규칙이 HTTP 핸들러 안에 갇혀 있다는 게 문제다. 앱용 JSON API를 만들면 이 계산을 복사해야 하고, 두 곳 중 한 곳만 고치는 순간 웹과 앱의 결제 금액이 달라진다. 규칙을 테스트하려 해도 HTTP 요청을 흉내 내고 DB를 띄워야 한다. 재고를 빼는 쿼리와 주문을 넣는 쿼리 사이에 트랜잭션이 없어서, 중간에 실패하면 재고만 줄어든 채로 남는 것도 덤이다.

## 업무 규칙은 서비스와 모델에 둔다

고치는 방향은 컨트롤러를 HTTP 번역기로 줄이는 것이다. 컨트롤러는 요청을 검증하고 서비스를 부르고 결과를 응답으로 바꾼다. 무엇이 주문 가능한지, 금액이 얼마인지는 서비스 계층과 도메인 모델이 안다.

```js
// controller: HTTP만 안다
app.post("/orders", async (req, res) => {
  const command = parsePlaceOrder(req.body); // 형식 검증만
  const order = await orderService.place(req.user.id, command);
  res.render("order-complete", { order });
});

// service: HTTP를 모른다. 트랜잭션 경계와 흐름을 맡는다
async place(userId, { productId, quantity, couponCode }) {
  return db.transaction(async (tx) => {
    const product = await products.findForUpdate(tx, productId);
    const order = Order.create(product, quantity, coupons.find(couponCode));
    await products.decreaseStock(tx, productId, quantity);
    await orders.save(tx, order);
    events.publish("order.placed", order); // 메일은 이벤트를 받아 따로 보낸다
    return order;
  });
}
```

할인과 배송비 계산은 `Order.create` 안으로 들어갔다. 이제 JSON API 컨트롤러도, 관리자 화면도, 배치 작업도 같은 `orderService.place`를 부른다. 금액 규칙은 DB 없이 `Order`만 만들어서 테스트할 수 있다.

여기서 반대쪽 함정이 하나 있다. 서비스를 만들고 나니 모든 로직이 서비스로 몰리고, 도메인 객체는 getter와 setter만 있는 데이터 상자가 되는 경우다. 마틴 파울러는 이걸 빈약한 도메인 모델(anemic domain model)이라고 부르며 안티패턴으로 꼽았다. `order.setStatus("CANCELED")`를 서비스 다섯 군데에서 부르면, "배송이 시작된 주문은 취소할 수 없다"는 규칙도 다섯 군데에 흩어진다. 규칙이 데이터와 붙어 있으면 `order.cancel()` 하나가 그 검사를 책임진다.

그렇다고 모든 걸 풍부한 도메인 모델로 짜야 하는 건 아니다. 규칙이 거의 없는 CRUD 화면이라면 서비스 메서드 하나가 한 트랜잭션을 처음부터 끝까지 처리하는 방식(트랜잭션 스크립트)이 더 읽기 쉽다. 기준은 규칙의 양이다. 같은 규칙을 두 군데 이상에서 검사하기 시작하면 그 규칙을 도메인 객체로 옮길 때가 됐다는 신호다. 정리하면 이렇게 나뉜다.

- 컨트롤러: 요청 파싱, 형식 검증, 인증 정보 꺼내기, 응답 형식(HTML·JSON·상태 코드) 결정
- 서비스: 유스케이스 흐름, 트랜잭션 경계, 여러 도메인 객체와 리포지토리 조율, 권한 확인
- 도메인 모델: 그 객체 자체의 규칙과 상태 변화(취소 가능 여부, 금액 계산)
- 뷰: 받은 값으로 그리기. 조건문은 표시용(빈 목록이면 안내 문구)까지만

반대로 Rails 쪽에서는 한동안 "컨트롤러는 날씬하게, 모델은 뚱뚱하게(skinny controller, fat model)"가 구호였다. 그 결과 `User` 모델 하나가 수천 줄이 되는 일이 생겨서, 지금은 서비스 객체나 폼 객체로 다시 쪼개는 방식도 널리 쓴다. 어디에 두든 HTTP와 업무 규칙을 섞지 않는다는 원칙은 같다.

## MVP와 MVVM은 무엇을 바꿨나

MVC가 GUI 쪽에서 계속 쓰이면서 불편한 점이 드러났다. 뷰가 모델을 직접 지켜보니 뷰를 테스트하기 어렵고, 뷰 안에 "이 버튼을 언제 비활성화할지" 같은 화면 로직이 쌓였다. 그래서 두 가지 변형이 나왔다.

MVP(Model-View-Presenter)는 뷰를 최대한 멍청하게 만든다. 뷰는 인터페이스 뒤에 숨고, 입력이 들어오면 프레젠터에 그대로 넘긴다. 프레젠터가 모델을 읽고 `view.showError("재고 부족")`처럼 뷰의 메서드를 직접 부른다. 뷰와 모델은 서로 모른다. 프레젠터는 뷰 인터페이스만 알면 되니, 가짜 뷰를 넣어 화면 로직을 단위 테스트할 수 있다. 데이터 바인딩이 없던 시절의 안드로이드 앱에서 많이 쓰였다. 대신 화면 요소 하나마다 뷰 인터페이스 메서드가 늘어나는 수고가 든다.

MVVM(Model-View-ViewModel)은 2005년 무렵 마이크로소프트가 WPF용으로 정리했다. 뷰모델은 화면에 필요한 상태를 속성으로 들고 있고(`isSubmitDisabled`, `totalText`), 뷰는 그 속성에 바인딩된다. 프레젠터처럼 뷰를 직접 부르지 않는다. 뷰모델 값이 바뀌면 바인딩이 화면을 고치고, 입력칸을 고치면 바인딩이 뷰모델 값을 고친다.

## 브라우저로 옮겨 온 MVC와 양방향 바인딩의 한계

2010년 전후로 화면 로직이 브라우저로 넘어오면서 MVC도 따라왔다. Backbone.js는 모델과 컬렉션, 뷰를 나누고 모델의 `change` 이벤트를 뷰가 구독하게 했다. Smalltalk의 알림 구조가 브라우저에서 다시 살아난 셈이다. AngularJS는 한발 더 나가 양방향 바인딩을 줬다. 입력칸과 스코프 변수를 `ng-model`로 묶으면 둘이 알아서 같아졌다.

화면이 작을 때는 마법 같았다. 화면이 커지자 문제가 생겼다. 모델 A가 바뀌면 그걸 보는 뷰가 모델 B를 고치고, B를 보는 다른 뷰가 다시 A를 고친다. 값 하나가 왜 이렇게 바뀌었는지 추적하려면 이벤트 사슬을 전부 따라가야 한다. AngularJS는 바뀐 값을 찾으려고 등록된 감시자(watcher)를 값이 더 이상 바뀌지 않을 때까지 반복해서 돌리는 다이제스트 루프를 썼는데, 감시자가 많아지면 입력 한 번에도 화면이 느려졌다.

페이스북이 2014년에 Flux를 발표하면서 든 예가 이런 종류였다. 메시지를 읽었는데 상단의 안 읽은 메시지 숫자가 다시 살아나는 버그가 고쳐도 계속 돌아왔다고 했다. 데이터가 여러 방향으로 흐르니 어디서 값을 덮어쓰는지 찾기 어려웠다. 그래서 데이터가 한 방향으로만 흐르게 만들었다.

React가 이 흐름과 잘 맞았다. 데이터는 props로 부모에서 자식으로만 내려가고, 자식은 콜백을 불러 변경을 요청한다. 입력칸도 상태에서 값을 받고 `onChange`로 상태를 바꾸는 제어 컴포넌트로 만든다. 양방향 바인딩을 손으로 펼쳐 쓰는 셈이라 코드는 조금 길어지지만, 값이 바뀌는 길이 늘 하나라서 디버깅할 때 따라갈 곳이 분명하다. 2015년에 나온 Redux는 Flux를 스토어 하나와 순수 함수 리듀서로 단순하게 다듬었다.

그렇다고 MVC가 사라진 건 아니다. React 컴포넌트는 MVC로 치면 뷰이고, 스토어나 서버 상태 캐시(TanStack Query 같은 것)가 모델 자리에 앉는다. 화면과 규칙을 떼어 낸다는 원칙은 그대로이고, 둘을 잇는 방식만 알림에서 단방향 흐름으로 바뀌었다. Vue처럼 `v-model`로 양방향 바인딩을 주는 프레임워크도 컴포넌트 안쪽의 입력칸에만 쓰게 하고, 컴포넌트 사이에서는 props와 이벤트로 한 방향을 지킨다.

## 서비스가 커지면 계층보다 기능으로 나눈다

MVC 프로젝트가 작을 때는 `controllers/`, `services/`, `repositories/`, `views/`처럼 계층별 폴더가 깔끔하다. 그런데 기능이 50개를 넘으면 주문 기능 하나를 고치려고 네 폴더를 오가야 한다. 계층 폴더 안에서 파일끼리 서로를 마음대로 import해서, 주문 서비스가 회원 리포지토리를 직접 부르는 식의 의존이 쌓인다.

그래서 큰 MVC 서비스는 보통 기능(도메인) 단위로 먼저 나누고, 그 안에서 계층을 나눈다.

```
order/
  OrderController   // 웹
  OrderApiController // 앱용 JSON
  OrderService
  Order, OrderRepository
member/
  ...
```

여기에 두 가지 규칙을 더한다. 첫째, 의존 방향은 컨트롤러 → 서비스 → 도메인·리포지토리로만 흐르고 거꾸로 가지 않는다. 서비스가 `HttpServletRequest`를 받거나 도메인 객체가 뷰 템플릿 이름을 알면 규칙 위반이다. 둘째, 다른 모듈은 그 모듈의 서비스(공개 API)로만 부른다. 주문 모듈이 회원 테이블을 직접 조회하지 않고 `memberService.getGrade(id)`를 부른다. 자바라면 ArchUnit 같은 도구로 이 규칙을 테스트에 넣어 빌드에서 막을 수 있다.

모듈 경계가 지켜지면 그다음 선택지가 생긴다. 트래픽이 몰리는 모듈만 떼어 별도 서비스로 만들 수 있고, 화면 쪽은 서버 템플릿 대신 SPA나 프론트엔드 전용 서버(BFF)로 옮겨 서버는 JSON API만 내보내게 할 수도 있다. 이때 서버의 뷰 자리는 JSON 직렬화가 차지하고, 브라우저 안에서 다시 컴포넌트·상태 관리라는 작은 MVC가 하나 더 생긴다. 반대로 경계 없이 자란 코드는 무엇을 떼어 내려 해도 전부 엮여 나온다. 처음 장면의 300줄 컨트롤러가 그런 상태다.

## 경계가 무너진 코드는 장애 문의로 돌아온다

계층을 어떻게 나눴는지는 코드 리뷰보다 운영에서 먼저 드러난다. 처음 장면 같은 코드가 실제로 만드는 문의 두 가지와, 그때 확인하는 방법이다. SQL 출력은 PostgreSQL 16에서 재현한 것이다.

### 웹과 앱의 결제 금액이 다르다

"같은 운동화를 같은 쿠폰으로 샀는데 앱이 1,600원 더 비싸다"는 문의가 온다. 금액 규칙이 컨트롤러마다 복사돼 있으면 이런 일이 생긴다. 규칙에 쓰이는 값으로 저장소를 찾아본다.

```bash
# 쿠폰 코드와 배송비 기준 금액이 어디어디 적혀 있는지
grep -rnE 'WELCOME10|< 30000' src/
```

```text
src/web/order-controller.js:3:  if (couponCode === "WELCOME10") price = Math.floor(price * 0.85);
src/web/order-controller.js:4:  if (price < 30000) price += 3000;
src/api/order-api-controller.js:3:  if (couponCode === "WELCOME10") price = Math.floor(price * 0.9);
src/api/order-api-controller.js:4:  if (price < 30000) price += 3000;
```

지난달 프로모션 때 웹 컨트롤러만 15% 할인으로 바꿨다. 32,000원짜리를 사면 웹은 27,200원이 돼서 배송비가 붙어 30,200원, 앱은 28,800원에 배송비를 더해 31,800원이다. 버그를 고치는 건 숫자 하나지만, 원인은 같은 규칙이 두 곳에 있다는 데 있다. 규칙을 `Order`의 금액 계산 한 곳으로 옮기고, 두 컨트롤러는 그걸 부르게 바꾼다. 그리고 "32,000원, WELCOME10 → 얼마"를 HTTP 없이 `Order`만으로 확인하는 테스트를 하나 붙인다. grep 결과가 두 줄 이상 나오는 업무 상수는 대개 같은 문제를 품고 있다.

### 주문 API가 가끔 몇 초씩 멈춘다

평소 50ms인 주문 API의 p99가 가끔 몇 초로 튄다. 같은 상품에 주문이 몰릴 때만 그렇다. 이럴 땐 DB에서 누가 누구를 기다리는지 본다.

```sql
SELECT pid, application_name, state, wait_event_type, wait_event,
       date_trunc('second', now() - xact_start) AS xact_age,
       left(query, 50) AS query
FROM pg_stat_activity
WHERE datname = current_database() AND pid <> pg_backend_pid()
ORDER BY xact_start;
```

```text
 pid  | application_name |        state        | wait_event_type |  wait_event   | xact_age |                       query
------+------------------+---------------------+-----------------+---------------+----------+----------------------------------------------------
 2390 | order-api-1      | idle in transaction | Client          | ClientRead    | 00:00:04 | UPDATE products SET stock = stock - 1 WHERE id = 7
 2394 | order-api-2      | active              | Lock            | transactionid | 00:00:02 | UPDATE products SET stock = stock - 1 WHERE id = 7
(2 rows)
```

첫 줄이 범인이다. `idle in transaction`은 트랜잭션을 열고 재고 행을 잠근 채 DB에 아무것도 안 보내고 있다는 뜻이다. `query` 열은 지금 실행 중인 게 아니라 마지막으로 보낸 쿼리다. 둘째 줄은 같은 행을 고치려다 `Lock`에서 기다리는 중이다. 누가 막고 있는지는 `SELECT pid, pg_blocking_pids(pid) FROM pg_stat_activity WHERE wait_event_type = 'Lock';`로 확인하면 `{2390}`이 나온다.

애플리케이션 쪽을 보면 서비스 메서드가 트랜잭션 안에서 재고를 줄인 뒤 메일 서버나 결제사 API를 부르고 있는 경우가 많다. 외부 호출이 3초 걸리면 그 3초 동안 재고 행이 잠겨 있다. 트랜잭션 경계를 서비스에 두라는 건 "서비스 메서드 전체를 트랜잭션으로 감싸라"가 아니다. DB 일만 트랜잭션 안에 두고, 메일은 앞의 서비스 코드처럼 이벤트로 넘기되, 이벤트가 커밋된 뒤에 나가게 한다(Spring이라면 `@TransactionalEventListener`의 기본 단계가 커밋 후다). 결제처럼 결과가 필요하면 결제를 먼저 하고 짧은 트랜잭션으로 반영한다. 안전장치로 `ALTER ROLE app SET idle_in_transaction_session_timeout = '10s';`를 걸어 두면 그보다 오래 쉬는 트랜잭션은 세션째 끊긴다. 잠금 대기를 더 깊게 보는 법은 [락과 데드락](/posts/db-locking-deadlock) 글에 있다.

Spring Boot로 이 구조를 만들었다면 시작 로그의 경고 하나도 같이 본다. `spring.jpa.open-in-view is enabled by default. Therefore, database queries may be performed during view rendering.`로 시작하는 줄이다. 기본값이 켜져 있어서 뷰를 그리는 동안에도 DB 연결을 쥐고 지연 로딩 쿼리를 보낼 수 있다는 뜻이다. 템플릿에서 `order.items`를 돌다가 쿼리가 수십 번 나가는 일이 여기서 생긴다. `spring.jpa.open-in-view=false`로 끄고, 뷰에 필요한 값은 서비스가 트랜잭션 안에서 다 채워 넘기게 하면 "뷰는 받은 값을 그리기만 한다"는 원칙이 설정으로도 지켜진다.

## 다시 쿠폰 입력칸으로

쿠폰 하나 추가하는 일이 막막했던 건 업무 규칙이 HTTP 처리 코드 안에 흩어져 있어서였다. MVC는 폴더 이름 세 개가 아니라 화면과 입력 처리에서 업무 규칙을 떼어 내자는 약속이다. 웹에서는 컨트롤러가 HTTP를 번역하고, 서비스와 도메인 모델이 규칙을 맡고, 뷰가 그린다. 쿠폰 할인은 `Order`의 금액 계산에 들어가야 하고, 그러면 웹과 앱이 같은 금액을 낸다.

## 면접에서 나올 만한 질문

### MVC 패턴을 설명해 주세요.

애플리케이션을 데이터와 업무 규칙을 담는 모델, 화면을 그리는 뷰, 입력을 받아 모델과 뷰를 잇는 컨트롤러로 나누는 패턴이다. 모델이 화면을 모르게 해서 같은 규칙을 여러 화면에서 쓰고, 화면을 바꿔도 규칙이 흔들리지 않게 하는 게 목적이다. 원래는 Smalltalk GUI에서 나왔고, 웹에서는 요청 하나를 컨트롤러가 받아 모델을 거쳐 뷰로 HTML을 만드는 형태로 바뀌었다.

### Spring MVC에서 요청이 처리되는 순서는요?

필터를 지나 DispatcherServlet이 요청을 받고, HandlerMapping으로 담당 컨트롤러 메서드를 찾아 HandlerAdapter로 호출한다. 컨트롤러는 서비스를 불러 결과를 Model에 담고 뷰 이름을 돌려주며, ViewResolver가 템플릿을 찾아 렌더링한다. 인터셉터가 컨트롤러 앞뒤에 끼고, `@RestController`라면 뷰 대신 메시지 컨버터가 객체를 JSON으로 바꾼다.

### 원래의 MVC와 웹 MVC는 무엇이 다른가요?

원래 MVC는 모델이 바뀌면 옵서버로 뷰에 알리고 뷰가 다시 그리는 구조다. HTTP는 요청 하나에 응답 하나로 끝나서 서버가 이미 보낸 화면에 알릴 방법이 없으니, 웹 MVC는 컨트롤러가 모델을 부르고 결과를 뷰에 넘기는 일직선 흐름이 된다. 컨트롤러의 단위도 위젯의 입력 처리에서 HTTP 요청 처리로 커졌다.

### 비즈니스 로직은 컨트롤러, 서비스, 모델 중 어디에 두나요?

컨트롤러에는 두지 않는다. 컨트롤러는 요청 파싱과 형식 검증, 응답 형식 결정만 하고, 유스케이스 흐름과 트랜잭션 경계는 서비스가, 객체 자체의 규칙(취소 가능 여부, 금액 계산)은 도메인 모델이 맡는다. 컨트롤러에 두면 웹과 앱 API가 규칙을 복사하게 되고, HTTP 없이는 테스트할 수 없다.

### 빈약한 도메인 모델은 왜 문제인가요?

도메인 객체가 getter·setter만 있고 규칙은 전부 서비스에 있으면, 같은 규칙을 여러 서비스가 각자 검사하게 되어 하나라도 빠뜨리면 잘못된 상태가 저장된다. 규칙을 데이터 옆의 메서드(`order.cancel()`)에 두면 한 곳에서 지킨다. 다만 규칙이 거의 없는 CRUD라면 서비스 하나가 처리하는 트랜잭션 스크립트가 더 단순하니, 규칙이 중복되기 시작할 때 옮기는 게 현실적이다.

### MVC, MVP, MVVM의 차이는요?

셋 다 모델이 화면을 모른다는 점은 같고, 화면과 그 뒤 객체를 잇는 방식이 다르다. MVC는 뷰가 모델 변경을 지켜보고, MVP는 프레젠터가 뷰 인터페이스의 메서드를 직접 불러 갱신해서 가짜 뷰로 테스트하기 쉽다. MVVM은 뷰모델이 화면 상태를 속성으로 들고 데이터 바인딩이 뷰와 자동으로 동기화한다. 바인딩을 주는 플랫폼이면 MVVM, 아니면 MVP를 고르는 경우가 많다.

### 양방향 바인딩이 큰 앱에서 어려워진 이유와 React의 접근은요?

양방향 바인딩에서는 뷰와 모델이 서로를 고치면서 변경이 연쇄되어, 값이 왜 바뀌었는지 추적하기 어렵고 AngularJS 같은 감시 방식은 감시자가 늘수록 느려졌다. Flux와 React는 상태가 위에서 아래로만 흐르고 변경은 액션이나 콜백 한 길로만 올라가게 했다. 코드는 조금 길어지지만 변경 경로가 하나라서 디버깅과 예측이 쉽다.

### 큰 MVC 프로젝트는 어떻게 구조를 잡나요?

계층별 폴더보다 기능(도메인) 모듈로 먼저 나누고 그 안에서 컨트롤러·서비스·도메인을 나눈다. 의존 방향은 컨트롤러 → 서비스 → 도메인으로만 흐르게 하고, 다른 모듈은 그 모듈의 서비스로만 부르게 해서 경계를 지킨다. 경계가 지켜지면 특정 모듈을 별도 서비스로 떼거나 화면을 SPA·BFF로 옮기는 선택을 나중에 할 수 있다.
