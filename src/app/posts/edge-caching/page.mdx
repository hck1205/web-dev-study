CDN을 붙였는데 오리진 요청이 생각만큼 줄지 않았다. 콘솔의 캐시 히트율은 50%대에 머문다. 상품 페이지는 사람마다 다르지 않고, `Cache-Control`도 `public`으로 잘 나가고 있다. 로그를 열어 보니 같은 상품 URL 뒤에 `utm_campaign=...`이 수백 가지로 붙어 있었다. CDN 눈에는 그 수백 개가 전부 다른 페이지였다.

엣지 캐시가 일을 하는지는 헤더 규칙만으로 정해지지 않는다. 무엇을 같은 요청으로 볼지(캐시 키), 만료된 사본을 언제까지 내줄지(stale), 히트율을 어떻게 셀지, 사람마다 다른 응답을 어디서 가를지가 함께 맞아야 한다. 이 글은 nginx 1.24의 `proxy_cache`로 작은 엣지를 직접 띄우고, `X-Cache-Status` 헤더와 접근 로그로 그 네 가지를 하나씩 확인한다. 실습은 Ubuntu 24.04에서 했고, 오리진은 응답을 300ms 걸려 만드는 Node 서버다.

이 주제의 다른 글: `Cache-Control`, `ETag`, `Vary` 같은 HTTP 캐시 규칙 자체는 [HTTP 캐시와 CDN](/posts/http-caching-cdn)에서, 엣지가 어디에 있고 사용자가 어떻게 가까운 엣지로 가는지는 [CDN 엣지와 애니캐스트](/posts/cdn-edge-anycast)에서 다뤘다. 캐시에 든 사본을 지우는 방법은 [캐시 무효화](/posts/cache-invalidation)로 이어진다.

## 엣지 하나를 직접 띄운다

CDN의 엣지 서버는 결국 캐시를 가진 리버스 프록시다. nginx로 같은 모양을 만들 수 있다. 오리진은 상품 JSON에 엣지용 수명 5초(`s-maxage=5`)와 상한 사본 규칙을 붙여 보낸다.

```text
Cache-Control: public, max-age=0, s-maxage=5, stale-while-revalidate=30, stale-if-error=300
```

```nginx
# nginx.conf의 http 블록: 디스크 캐시 영역 정의
proxy_cache_path /var/cache/edge levels=1:2 keys_zone=edge:10m max_size=100m inactive=10m use_temp_path=off;
log_format edge '$request_uri $upstream_cache_status $body_bytes_sent $request_time';

server {
  listen 19431;
  access_log /var/log/nginx/edge.log edge;
  location / {
    proxy_pass http://127.0.0.1:19432;                      # 오리진
    proxy_cache edge;                                       # 위의 캐시 영역 사용
    add_header X-Cache-Status $upstream_cache_status always; # 히트 여부를 응답에 표시
  }
}
```

```bash
# 같은 URL을 세 번 요청하고 캐시 상태와 오리진이 센 요청 번호를 본다
for i in 1 2 3; do curl -s -o /dev/null -D - http://127.0.0.1:19431/product/42 | grep -iE "x-cache|x-origin"; done
```

```text
X-Origin-Hit: 1
X-Cache-Status: MISS
X-Origin-Hit: 1
X-Cache-Status: HIT
X-Origin-Hit: 1
X-Cache-Status: HIT
```

첫 요청은 MISS로 오리진에 갔고, 나머지 둘은 엣지가 저장한 사본(오리진의 1번 응답)을 받았다. `$upstream_cache_status`가 내놓는 값은 이 글 내내 나온다. MISS(사본 없음), HIT(신선한 사본), EXPIRED(만료돼서 오리진에 다시 받음), STALE(만료됐지만 상한 사본을 줌), UPDATING(누군가 갱신 중이라 상한 사본을 줌), REVALIDATED(오리진이 304로 사본이 맞다고 확인), BYPASS(규칙에 따라 캐시를 건너뜀)다. CDN도 이름만 다를 뿐 같은 정보를 응답 헤더로 준다. CloudFront는 `X-Cache: Hit from cloudfront`, Cloudflare는 `cf-cache-status`, Fastly는 `X-Cache`다.

## 캐시 키에 무엇을 넣을까

처음 장면을 재현했다. 기본 키(`$scheme$proxy_host$request_uri`)는 쿼리 문자열 전체를 키에 넣는다.

```bash
# 같은 상품, 같은 색인데 광고 파라미터만 다르다
for q in "?color=red" "?color=red&utm_source=mail" "?color=red&utm_source=insta" "?utm_source=mail&color=red"; do
  printf "%-40s " "/product/7$q"
  curl -s -o /dev/null -D - "http://127.0.0.1:19431/product/7$q" | grep -i x-cache-status
done
```

```text
/product/7?color=red                     X-Cache-Status: MISS
/product/7?color=red&utm_source=mail     X-Cache-Status: MISS
/product/7?color=red&utm_source=insta    X-Cache-Status: MISS
/product/7?utm_source=mail&color=red     X-Cache-Status: MISS
```

오리진의 응답은 넷 다 같은데 엣지는 네 번 모두 오리진에 갔다. 광고 파라미터의 값이 다르거나 순서만 바뀌어도 다른 키다. 그래서 응답을 실제로 바꾸는 쿼리만 골라 키를 직접 만들었다.

```nginx
# 응답을 바꾸는 쿼리(color, size)만 정해진 순서로 키에 넣는다
proxy_cache_key "norm:$host$uri|color=$arg_color|size=$arg_size";
```

```text
/product/7?color=red                     X-Cache-Status: MISS
/product/7?color=red&utm_source=mail     X-Cache-Status: HIT
/product/7?color=red&utm_source=insta    X-Cache-Status: HIT
/product/7?utm_source=mail&color=red     X-Cache-Status: HIT
/product/7?color=blue                    X-Cache-Status: MISS
```

광고 파라미터가 붙든 순서가 바뀌든 같은 키로 모였고, 색이 다른 요청만 따로 MISS가 났다. nginx는 키의 MD5를 파일 이름으로 디스크에 사본을 두고, 파일 앞쪽에 키 원문을 적어 둔다. 키가 무엇으로 만들어졌는지 확인할 때 이걸 본다.

```bash
# 캐시 파일마다 저장된 키 원문을 꺼낸다
for f in $(find /var/cache/edge -type f); do grep -a -m1 "^KEY:" "$f"; done | sort
# 파일 이름은 키의 MD5. levels=1:2면 끝 한 글자/그 앞 두 글자 디렉터리에 들어간다
echo -n "norm:127.0.0.1/product/7|color=red|size=" | md5sum
```

KEY: http://127.0.0.1:19432/product/7?color=red&utm_source=insta
KEY: http://127.0.0.1:19432/product/7?color=red&utm_source=mail
KEY: http://127.0.0.1:19432/product/7?utm_source=mail&color=red

키에 넣을 것을 정하는 기준은 하나다. 오리진의 응답을 바꾸는 입력은 모두 넣고, 바꾸지 않는 입력은 모두 뺀다. 넣어야 하는데 빼면 잘못된 응답이 나가고(한국어 페이지가 영어 사용자에게), 빼야 하는데 넣으면 히트율이 떨어진다. 그 사이에서 자주 고민하는 것들이 있다.

- 언어, 통화, 국가: 응답이 바뀌면 넣는다. 다만 `Accept-Language` 헤더를 통째로 넣으면 `ko-KR,ko;q=0.9,en;q=0.8` 같은 조합이 수백 가지라서, 지원하는 언어 몇 개로 줄인 값을 넣는다.
- 기기: `User-Agent`를 그대로 넣으면 사실상 캐시가 안 된다. 모바일과 데스크톱처럼 응답이 정말 달라지는 단위로 줄여 넣거나, 응답을 반응형으로 만들어 아예 뺀다.
- 쿠키: 키에 넣으면 사용자마다 키가 달라진다. 필요한 쿠키 하나(예: A/B 실험 그룹)만 골라 넣는다.
- 압축: `Accept-Encoding`도 값 조합이 많다. CDN은 보통 이 값을 gzip, br 정도로 정규화해서 다룬다.

CloudFront는 이 결정을 캐시 정책(cache policy)으로 하고, 키에는 넣지 않되 오리진에는 넘길 값은 오리진 요청 정책(origin request policy)으로 따로 정한다. 키와 오리진에 넘기는 값을 나눠 생각하는 습관이 중요하다. 오리진이 로그를 위해 utm 값을 받아야 해도, 그게 키에 들어갈 이유는 없다.

## 히트율은 로그에서 센다

콘솔의 히트율 하나만 보면 무엇이 문제인지 모른다. 접근 로그에 캐시 상태를 남기면 직접 쪼개 볼 수 있다. 상품 500개에 인기 순으로 몰리는(지프 분포) 요청 2만 건을 초당 400건씩 보냈다. 30%에는 무작위 `utm_campaign`이 붙는다. 같은 트래픽을 기본 키 엣지와, 키를 정규화하고 상한 사본 설정(뒤에서 설명)을 켠 엣지에 각각 흘렸다.

```bash
# 로그의 둘째 칸이 $upstream_cache_status. 상태별 개수와 비율, 그리고 히트율
awk '{c[$2]++; n++} END {for (k in c) printf "%-9s %6d  %5.1f%%\n", k, c[k], c[k]*100/n;
     h=c["HIT"]+c["STALE"]+c["UPDATING"]; printf "hit ratio (HIT+STALE+UPDATING) = %.1f%%\n", h*100/n}' edge.log
```

```text
== 기본 키
UPDATING     544    2.7%
HIT        11000   55.0%
EXPIRED     6059   30.3%
MISS        2397   12.0%
hit ratio (HIT+STALE+UPDATING) = 57.7%
== 정규화한 키 + 상한 사본
UPDATING     761    3.8%
HIT        16588   82.9%
MISS         469    2.3%
STALE       2180   10.9%
hit ratio (HIT+STALE+UPDATING) = 97.7%
```

상태를 쪼개 보면 두 가지 개선이 따로 보인다. MISS가 12.0%에서 2.3%로 줄어든 건 키 정규화 덕이다. 기본 키에서 MISS를 다시 나눠 보면 원인이 바로 나온다.

```bash
# MISS 중 utm이 붙은 요청과 아닌 요청
awk '$2=="MISS"{ if ($1 ~ /utm_/) u++; else p++ } END {print "with utm_:", u, " without:", p}' edge.log
# 서로 다른 캐시 키 수와, 쿼리를 뗀 경로 수
awk '{print $1}' edge.log | sort -u | wc -l
awk '{split($1,a,"?"); print a[1]}' edge.log | sort -u | wc -l
```

```text
with utm_: 1876  without: 521
2313
469
```

MISS 2,397건 중 1,876건이 utm 때문이었다. 실제 상품은 469개인데 키는 2,313개로 쪼개져 있었다. EXPIRED 30.3%가 사라지고 STALE·UPDATING으로 바뀐 건 상한 사본 설정 덕이다. 만료된 사본을 버리고 오리진을 기다리는 대신, 상한 사본을 주면서 뒤에서 갱신했다.

그런데 여기서 숫자 하나를 더 봐야 한다. 오리진이 실제로 받은 요청 수다.

```text
origin hits: start=9259 after_raw=17715 after_norm=20366
```

기본 키 엣지 뒤의 오리진은 8,456건을 받았다. 히트율 57.7%와 정확히 맞는다(2만 건의 42.3%). 정규화 엣지 뒤의 오리진은 2,651건을 받았는데, 엣지 히트율 97.7%로 계산하면 460건 정도여야 한다. 차이는 뒤에서 일어난 갱신이다. STALE을 준 요청마다 엣지는 오리진에 갱신 요청을 하나씩 보냈고, 그건 사용자 요청의 MISS로 세지지 않는다. 그래서 히트율은 세 가지로 나눠 본다.

- 요청 히트율: 엣지에서 끝난 사용자 요청의 비율. 사용자가 느끼는 속도와 관계있다.
- 오리진 오프로드: 1 − (오리진이 받은 요청 ÷ 사용자 요청). 오리진 용량과 비용에 관계있다. 이 실험에서는 86.7%였다.
- 바이트 히트율: 엣지에서 나간 바이트의 비율. 큰 파일(이미지, 동영상)이 많으면 요청 히트율과 크게 다르다. 로그의 `$body_bytes_sent`를 상태별로 더하면 된다.

CDN 콘솔이 보여 주는 "캐시 히트율"이 이 중 무엇인지 확인하고 비교해야 한다. CDN에 따라 엣지 미스가 오리진 실드에서 잡힌 경우를 히트로 셀 수도 있다.

## 상한 사본을 내주면 오리진이 쉰다

수명이 5초인 사본이 만료된 직후의 요청을 두 엣지에서 비교했다. 기본 엣지에는 아무 설정이 없고, 다른 엣지에는 다음을 넣었다.

```nginx
proxy_cache_background_update on;   # 만료된 사본을 주고 갱신은 뒤에서
proxy_cache_use_stale updating error timeout http_500 http_502 http_503 http_504;
proxy_cache_lock on;                # 같은 키의 미스는 하나만 오리진으로
```

```bash
# 요청하고 6초 기다렸다가(s-maxage=5 만료) 두 번 더 요청한다
curl -s -o /dev/null -w "%{http_code} %{time_total}s " -D h.txt http://127.0.0.1:19431/product/55; grep -iE "x-cache|x-origin" h.txt
```

```text
== 기본 엣지
200 0.303086s X-Origin-Hit: 33 X-Cache-Status: MISS
(6s later, s-maxage=5 expired)
200 0.302718s X-Origin-Hit: 34 X-Cache-Status: EXPIRED
200 0.000501s X-Origin-Hit: 34 X-Cache-Status: HIT
== background_update 엣지
200 0.302974s X-Origin-Hit: 35 X-Cache-Status: MISS
(6s later, s-maxage=5 expired)
200 0.000414s X-Origin-Hit: 35 X-Cache-Status: STALE
200 0.000533s X-Origin-Hit: 36 X-Cache-Status: HIT
```

기본 엣지는 만료 뒤 첫 요청이 오리진을 300ms 기다렸다(EXPIRED). 오리진이 `stale-while-revalidate=30`을 보냈지만, 이 nginx에서 그 헤더는 다른 요청이 갱신 중일 때 기다리던 요청에게 상한 사본을 주게 할 뿐이고, 갱신을 시작한 요청 자신은 기다린다. `proxy_cache_background_update`를 켜자 만료 뒤 첫 요청도 0.4ms 만에 상한 사본(35번 응답)을 받았고, 바로 다음 요청은 뒤에서 받아 온 새 사본(36번)을 받았다.

오리진이 망가졌을 때도 비교했다. 먼저 오리진이 500을 돌려주게 한 뒤 사본이 만료되기를 기다렸다.

```text
== 기본 엣지 (origin returns 500)
500 0.003256s X-Cache-Status: EXPIRED
== use_stale http_500 엣지 (origin returns 500)
200 0.000692s X-Origin-Hit: 36 X-Cache-Status: STALE
```

오리진의 헤더에 `stale-if-error=300`이 있었는데도 기본 엣지는 500을 그대로 내보냈다. 오리진 프로세스를 아예 내려 연결이 거부되게 하자 결과가 달라졌다.

```text
== origin process stopped (connection refused)
200 0.000413s X-Origin-Hit: 34 X-Cache-Status: STALE
200 0.000570s X-Origin-Hit: 36 X-Cache-Status: STALE
```

이번에는 기본 엣지도 상한 사본을 줬다. nginx 1.24에서 헤더의 `stale-if-error`는 연결 실패나 타임아웃 같은 "오류"에 적용되고, 오리진이 정상적으로 돌려준 500 응답은 `proxy_cache_use_stale`에 `http_500`을 적어야 오류로 다룬다. 실제 장애에서 오리진은 죽기보다 500이나 502를 내는 경우가 많으니, 응답 코드까지 명시하는 쪽이 안전하다. CDN마다 이 동작(첫 요청이 기다리는지, 어떤 상태 코드에서 상한 사본을 주는지)이 다르므로, 설정 문서를 볼 때 이 두 질문을 들고 본다.

상한 사본에는 대가가 있다. 오리진이 데이터를 고쳐도 최대 `stale-while-revalidate`만큼 옛 값이 보일 수 있고, 장애 중에는 `stale-if-error`만큼 옛 값이 보인다. 가격처럼 틀리면 곤란한 값은 이 시간을 짧게 두거나 결제 단계에서 오리진 값을 다시 확인한다. 지금 당장 바꿔야 하는 값이라면 기다리지 말고 지운다. 그 방법은 [캐시 무효화](/posts/cache-invalidation)에서 다룬다.

## 같은 키의 미스를 하나로 모은다

인기 상품이 처음 요청되거나 만료되는 순간 같은 키로 요청이 몰리면, 엣지가 각자 오리진에 갈 수 있다. 사본이 없는 키에 동시에 50개를 보냈다.

```bash
# 사본이 없는 키에 동시에 50개, 앞뒤로 오리진이 센 요청 수를 비교
for i in $(seq 50); do curl -s -o /dev/null http://127.0.0.1:19431/product/90019431 & done; wait
```

```text
port 19431 lock=off: origin hits before={"hits":7} after={"hits":31}
port 19433 lock=on: origin hits before={"hits":31} after={"hits":32}
```

`proxy_cache_lock`이 꺼진 엣지는 오리진에 24번 갔고(나머지 26개는 그 사이 저장된 사본을 받았다), 켜진 엣지는 한 번 갔다. 나머지 49개는 첫 응답이 저장되기를 기다렸다가 HIT로 받았다. 이걸 요청 병합(request collapsing)이라고 한다. 스탬피드가 오리진을 쓰러뜨리는 원리는 [HTTP 캐시와 CDN](/posts/http-caching-cdn) 글에 있다. nginx의 잠금은 기본 5초(`proxy_cache_lock_timeout`)를 넘기면 기다리던 요청도 오리진으로 보내니, 오리진 응답이 느린 경로는 이 값도 함께 본다.

## 사람마다 다른 응답과 공유 캐시

엣지 캐시에서 가장 비싼 사고는 개인 응답이 공유 사본이 되는 것이다. 오리진이 실수로 로그인 응답에 `public, max-age=60`을 붙이고 `Set-Cookie`로 세션을 굽는 상황을 만들었다.

```bash
# 기본 엣지 두 번, Set-Cookie를 무시하게 설정한 엣지 두 번
curl -s -D - http://127.0.0.1:19431/me | grep -iE "set-cookie|x-cache-status|^\{"
```

```text
== 기본 엣지 /me
Set-Cookie: sid=u1; HttpOnly
X-Cache-Status: MISS
{"user":"u1"}
== 기본 엣지 /me
Set-Cookie: sid=u2; HttpOnly
X-Cache-Status: MISS
{"user":"u2"}
== proxy_ignore_headers Set-Cookie 엣지 /me
Set-Cookie: sid=u3; HttpOnly
X-Cache-Status: MISS
{"user":"u3"}
== proxy_ignore_headers Set-Cookie 엣지 /me
Set-Cookie: sid=u3; HttpOnly
X-Cache-Status: HIT
{"user":"u3"}
```

nginx는 기본적으로 `Set-Cookie`가 붙은 응답을 저장하지 않는다. 그래서 기본 엣지는 매번 MISS였고 사용자마다 자기 세션을 받았다. 그런데 히트율을 올리겠다고 `proxy_ignore_headers Set-Cookie`를 넣은 엣지에서는 두 번째 방문자가 첫 방문자의 응답과 세션 쿠키(`sid=u3`)를 그대로 받았다. 다른 사람으로 로그인된 것이다. 이 안전장치는 엣지 제품마다 다르고, HTTP 캐시 명세는 `Set-Cookie`가 있다고 캐시를 막지 않는다. 그러니 기본 동작에 기대지 않고 오리진이 개인 응답에 `private`나 `no-store`를 붙인다.

<Callout kind="warning" title="Set-Cookie를 무시하는 설정은 경로를 좁혀서">
`proxy_ignore_headers Set-Cookie`나 CDN의 "쿠키 무시" 옵션은 정적 파일처럼 절대 개인 응답이 나갈 수 없는 경로에만 건다. 잘못 걸었다면 그 설정을 빼고, 이미 저장된 사본을 지우고(퍼지), 노출됐을 수 있는 세션을 서버에서 모두 만료시킨다. 설정만 되돌리면 이미 퍼진 사본과 세션은 그대로 남는다.
</Callout>

캐시 키를 정규화하고(추적 파라미터 제거, 쿼리 정렬, 언어 값 줄이기), A/B 실험 그룹을 정해 쿠키와 키에 넣고, 토큰이 유효한지 엣지에서 먼저 확인하고, 응답 헤더를 고친다. 이런 일은 오리진까지 가지 않고 사용자 가까이에서 끝난다는 게 장점이다.

한계도 분명하다. 실행 시간과 메모리 한도가 작고(CloudFront Functions는 1ms 안쪽의 가벼운 일만 맡는다), 데이터베이스는 대개 멀리 있어서 엣지 코드가 DB를 부르면 지연이 오히려 는다. 요청마다 요금이 붙으니 트래픽이 큰 경로에서는 비용도 따진다. 그리고 코드가 키를 바꾸는 순간 캐시 동작을 추론하기가 어려워진다. 엣지 코드는 키와 헤더를 다듬는 얇은 층으로 두고, 업무 로직은 오리진에 두는 쪽이 운영하기 쉽다.

## 히트율이 낮을 때 보는 순서

"CDN을 붙였는데 오리진 부하가 그대로다"라는 말이 들어오면 이 순서로 본다.

먼저 응답 헤더를 본다. `curl -sI`로 같은 URL을 두 번 요청해 캐시 상태 헤더와 `Age`(엣지에 들어간 지 몇 초인가), `Cache-Control`을 확인한다. 두 번째도 MISS라면 저장이 안 되는 것이다. `Set-Cookie`가 붙어 있지 않은지, `private`나 `no-store`가 붙지 않았는지, `Vary`에 `User-Agent`나 `Cookie`가 있지 않은지 본다.

```bash
# 두 번 요청해서 캐시 관련 헤더만 본다
for i in 1 2; do curl -sI https://example.com/product/7 | grep -iE "x-cache|cf-cache-status|age|cache-control|vary|set-cookie"; echo; done
```

저장은 되는데 히트율이 낮다면 키가 쪼개진 것이다. 접근 로그(CDN이라면 실시간 로그나 로그 내보내기)에서 위처럼 서로 다른 키 수와 실제 경로 수를 비교한다. 경로는 수백 개인데 키가 수천 개면 쿼리, 헤더, 쿠키 중 무엇이 키를 쪼개는지 찾는다.

키도 괜찮다면 수명이 짧은 것이다. EXPIRED 비율이 높으면 `s-maxage`를 늘리거나 상한 사본 설정을 켠다. 수명이 짧을 수밖에 없는 데이터라면, 수명은 길게 두고 바뀔 때 지우는 쪽으로 설계를 바꾼다.

그래도 오리진 요청이 많다면 엣지가 너무 많아 캐시가 흩어진 것이다. PoP 수백 곳이 각자 미스를 내면 오리진에 가는 요청도 그만큼 많다. [CDN 엣지와 애니캐스트](/posts/cdn-edge-anycast) 글의 오리진 실드가 이 문제를 푼다.

## 키, 수명, 사람

엣지 캐시가 일하게 만드는 건 세 가지 결정이다. 무엇을 같은 요청으로 볼지(응답을 바꾸는 입력만 키에), 만료된 사본을 얼마나 더 내줄지(stale-while-revalidate와 stale-if-error, 그리고 그걸 엣지가 실제로 어떻게 처리하는지), 사람마다 다른 응답을 어디서 가를지(껍데기와 개인 데이터 나누기)다. 그리고 결과는 콘솔의 숫자 하나가 아니라 로그의 상태별 개수와 오리진이 받은 요청 수로 확인한다.

## 면접에서 나올 만한 질문

### CDN 캐시 히트율이 낮을 때 가장 먼저 의심하는 것은 무엇인가요?

캐시 키가 쪼개졌는지다. 기본 키에는 쿼리 문자열 전체가 들어가서 utm 같은 추적 파라미터가 붙을 때마다 다른 키가 된다. 실험에서 상품 469개가 키 2,313개로 쪼개졌고 MISS의 78%가 utm 때문이었다. 응답을 바꾸는 쿼리만 허용 목록으로 골라 정해진 순서로 키를 만들면 같은 사본으로 모인다.

### 캐시 키에 넣을 값은 어떤 기준으로 고르나요?

오리진의 응답을 바꾸는 입력은 넣고, 바꾸지 않는 입력은 뺀다. 빼야 할 것을 넣으면 히트율이 떨어지고, 넣어야 할 것을 빼면 다른 사람에게 잘못된 응답이 나간다. 언어나 기기처럼 값이 많은 헤더는 몇 가지 값으로 줄여서 넣고, User-Agent나 쿠키 전체는 넣지 않는다. 키에 넣는 값과 오리진에 넘기는 값은 따로 정한다.

### stale-while-revalidate를 쓰면 무엇이 좋아지고 무엇을 감수하나요?

만료된 사본을 바로 주고 갱신은 뒤에서 하니, 만료 직후의 사용자가 오리진을 기다리지 않는다. 실험에서 만료 뒤 첫 요청이 300ms에서 0.4ms로 줄었다. 대신 그 시간만큼 옛 데이터가 보일 수 있고, 뒤에서 하는 갱신 요청이 오리진에 가므로 엣지 히트율만큼 오리진 요청이 줄지는 않는다. 엣지 제품마다 첫 요청이 기다리는지가 달라서 동작을 직접 확인한다.

### 엣지 히트율이 97%인데 오리진 요청은 13%였습니다. 왜 차이가 나나요?

상한 사본을 주면서 뒤에서 갱신하는 요청이 오리진으로 가기 때문이다. 사용자 요청은 STALE이나 UPDATING으로 엣지에서 끝나 히트로 세지만, 그때마다 갱신 요청이 하나씩 오리진에 간다. 그래서 요청 히트율, 오리진 오프로드, 바이트 히트율을 따로 보고, 오리진 용량은 오리진이 실제로 받은 요청 수로 판단한다.

### 오리진이 500을 내면 엣지가 옛 사본을 주나요?

설정에 따라 다르다. nginx 1.24에서 헤더의 stale-if-error는 연결 실패에는 적용됐지만 오리진이 돌려준 500 응답에는 적용되지 않았고, proxy_cache_use_stale에 http_500을 적어야 옛 사본을 줬다. 실제 장애는 500이나 502로 나타나는 경우가 많으니 어떤 상태 코드에서 상한 사본을 줄지 명시한다.

### 로그인한 사용자의 페이지는 CDN에 캐시하면 안 되나요?

사람마다 같은 부분은 캐시하고 다른 부분만 따로 받으면 된다. 페이지 껍데기는 공유 사본으로 두고 이름, 장바구니 같은 개인 데이터는 private 응답의 API로 받아 끼운다. 로그인 여부나 국가처럼 몇 가지 무리로 키를 나누거나, ESI나 엣지 컴퓨팅으로 엣지에서 조각을 조립하는 방법도 있다. 개인 응답에는 반드시 private나 no-store를 붙인다.

### Set-Cookie가 있는 응답을 캐시하게 설정하면 어떤 일이 생기나요?

첫 사용자의 응답과 세션 쿠키가 공유 사본이 되어 다음 사용자에게 그대로 나간다. 실험에서 Set-Cookie를 무시하게 한 엣지는 두 번째 방문자에게 첫 방문자의 sid를 줬다. nginx는 기본적으로 이런 응답을 저장하지 않지만 제품마다 다르고 명세가 막아 주지도 않는다. 이미 사고가 났다면 설정을 되돌리고 사본을 퍼지하고 노출된 세션을 만료시킨다.
