4Sum은 [3Sum](/posts/leetcode-3sum)을 푼 사람에게 "그럼 네 개는요?"라고 묻는 문제다. 반복문 하나를 더 두르면 끝날 것 같고, 실제로 그렇게 짜면 대부분 통과한다. 그런데 Java로 제출하면 `[1000000000, 1000000000, 1000000000, 1000000000]`, 목표 `-294967296`이라는 이상한 테스트에서 틀린다. 네 수의 합이 `int`를 넘어 음수로 돌아가 버리기 때문이다. 이 문제가 3Sum에 더하는 건 반복문 하나와, 이 정수 넘침 하나다.

[LeetCode 18. 4Sum](https://leetcode.com/problems/4sum/)은 정렬, 수 고정, 양 끝 투 포인터, 중복 건너뛰기가 모두 3Sum과 같다. 그 설명은 3Sum 글에 자세히 있으니 여기서는 반복하지 않는다. 3Sum 글 끝의 "네 수, k개의 수라면"에서 k개 일반화 코드도 이미 봤다. 이 글은 4Sum에서 새로 생기는 것들을 본다. 다섯 가지 풀이를 실제로 재서 n이 200일 때와 1000일 때 순위가 어떻게 바뀌는지, 두 수 합을 해시맵에 담는 "반씩 나눠 만나기" 풀이가 왜 어떤 입력에서는 30초 가까이 걸리는지, 가지치기 두 줄이 얼마나 줄여 주는지, 그리고 언어별 정수 넘침이다. 패턴 전체는 [투 포인터 패턴 글](/posts/two-pointers-pattern)에 있다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 네 수의 합이 target인 조합을 한 번씩

문제를 내 말로 줄이면 이렇다. 정수 배열 `nums`와 정수 `target`이 주어진다. 서로 다른 네 칸의 값을 더해 `target`이 되는 조합을 모두 찾는다. 값이 같은 조합은 한 번만 낸다. 순서는 상관없다.

```text
nums = [2, -1, 0, -2, 1, 1, -1], target = 1

-2 + 0 + 1 + 2   = 1
-1 + -1 + 1 + 2  = 1
-1 + 0 + 1 + 1   = 1

답: [[-2, 0, 1, 2], [-1, -1, 1, 2], [-1, 0, 1, 1]]
```

`1`이 두 칸에 있어서 `-1 + 0 + 1 + 1`처럼 1을 두 번 쓰는 조합이 된다. 1이 한 칸뿐이었다면 안 된다. 칸이 달라야 하기 때문이다. 반대로 `-1`도 두 칸에 있지만, `-2 + 0 + 1 + 2`에 어느 칸의 1을 쓰든 값이 같은 조합은 하나로 친다. 이 "칸은 달라야 하고 값 조합은 한 번만"이 3Sum과 같은 난이도의 원천이다.

풀이에 영향을 주는 제약은 이렇다. 길이는 최대 200이다. 네 수 조합은 약 6470만 개라 O(n⁴)도 어떻게든 돌기는 한다. O(n³)이면 800만 정도로 넉넉하다. 값과 `target`은 ±10^9다. 네 수를 더하면 최대 4 × 10^9로, Java `int`의 최댓값(약 2.1 × 10^9)을 넘는다. JavaScript의 수는 2^53 − 1(약 9 × 10^15)까지 정확하니 문제없고, Python 정수는 크기 제한이 없다.

## 네 겹으로 다 골라 본다

정의를 그대로 옮긴다. 중복 조합은 네 수를 정렬해 문자열 키로 만들어 집합으로 거른다.

```js
// 풀이 1: 네 겹 반복 + 키 집합
function fourSum(nums, target) {
  const n = nums.length, seen = new Set(), out = [];
  for (let a = 0; a < n; a++)
    for (let b = a + 1; b < n; b++)
      for (let c = b + 1; c < n; c++)
        for (let d = c + 1; d < n; d++) {
          if (nums[a] + nums[b] + nums[c] + nums[d] !== target) continue;
          const t = [nums[a], nums[b], nums[c], nums[d]].sort((x, y) => x - y);
          const key = t.join(",");                   // "-2,0,1,2" 같은 키
          if (!seen.has(key)) { seen.add(key); out.push(t); }
        }
  return out;
}
```

시간 O(n⁴)이다. n = 200에서 재 봤다.

```text
값 ±10^9 무작위   402.6ms
값 ±50 무작위     891.6ms
모두 0           25686.6ms
```

값이 넓으면 0.4초로 버틴다. 그런데 모두 0인 배열에서는 25초가 넘었다. 답은 `[[0, 0, 0, 0]]` 하나뿐인데, 6470만 개 조합이 모두 합 0이라 매번 배열을 만들고 정렬하고 문자열 키를 만들었기 때문이다. 중복을 "나중에 거르는" 방식은 같은 답이 많이 나오는 입력에서 비용이 터진다. 처음부터 중복을 만들지 않아야 한다.

## 셋을 고르고 넷째는 이진 탐색으로

정렬하면 두 가지가 생긴다. 같은 값이 붙어 있어서 "바로 앞과 같으면 건너뛴다"로 중복을 막을 수 있고, 넷째 수를 [이진 탐색](/posts/binary-search)으로 찾을 수 있다. 세 수를 고르면 넷째는 `target - (a + b + c)`로 정해지니, 남은 범위에 그 값이 있는지만 본다.

```js
// 풀이 2: 정렬 + 세 수 고정 + 이진 탐색
function fourSum(nums, target) {
  nums.sort((a, b) => a - b);
  const n = nums.length, out = [];
  const has = (lo, x) => {                       // nums[lo..]에 x가 있나
    let hi = n - 1;
    while (lo <= hi) {
      const m = (lo + hi) >> 1;
      if (nums[m] === x) return true;
      if (nums[m] < x) lo = m + 1; else hi = m - 1;
    }
    return false;
  };
  for (let a = 0; a < n; a++) {
    if (a > 0 && nums[a] === nums[a - 1]) continue;          // 같은 첫 수
    for (let b = a + 1; b < n; b++) {
      if (b > a + 1 && nums[b] === nums[b - 1]) continue;    // 같은 둘째 수
      for (let c = b + 1; c < n; c++) {
        if (c > b + 1 && nums[c] === nums[c - 1]) continue;  // 같은 셋째 수
        const need = target - nums[a] - nums[b] - nums[c];
        if (need >= nums[c] && has(c + 1, need)) out.push([nums[a], nums[b], nums[c], need]);
      }
    }
  }
  return out;
}
```

셋째 수까지 같은 값을 건너뛰었으니 같은 `(a, b, c)` 값 조합은 한 번만 나오고, 넷째는 그 셋으로 정해지니 결과도 한 번씩만 나온다. `need >= nums[c]` 검사는 넷째가 셋째보다 작은 경우를 버린다. 정렬된 순서로만 조합을 만들기 위해서다.

시간은 O(n³ log n)이다. 모두 0인 입력이 0.0ms로 바뀐 게 눈에 띈다. 같은 값을 건너뛰니 반복이 거의 돌지 않는다.

```text
값 ±10^9 무작위   19.1ms
값 ±50 무작위     3.1ms
모두 0           0.0ms
```

이 풀이의 한계는 log n이다. 넷째 수를 매번 처음부터 이진 탐색하는데, 셋째 수가 커지면 넷째 수는 작아져야 한다는 단조성을 쓰지 않는다. 셋째와 넷째를 함께 양 끝에서 좁히면 log n이 사라진다.

## 둘을 고정하고 나머지 둘은 양 끝에서

3Sum에서 하나를 고정하고 Two Sum II를 돌렸듯이, 4Sum은 둘을 고정하고 Two Sum II를 돌린다.

1. 정렬한다.
2. `a`를 고정한다. 바로 앞과 같은 값이면 건너뛴다.
3. `b`를 `a + 1`부터 고정한다. 바로 앞과 같은 값이면 건너뛰는데, 비교는 `b > a + 1`일 때만 한다.
4. `l = b + 1`, `r = n - 1`에서 네 수의 합을 본다. 작으면 `l++`, 크면 `r--`.
5. 같으면 담고, `l`과 `r` 쪽의 같은 값을 건너뛴 뒤 한 칸씩 좁힌다.

3번의 `b > a + 1`이 3Sum에 없던 부분이다. `b`의 중복은 "이번 `a`에서 고른 둘째 수 중에서" 따져야 한다. `b`가 `a + 1`이면 그게 이번 `a`에서 처음 고르는 둘째 수라 건너뛸 이유가 없다. `nums[b] === nums[b - 1]`이어도 그 `b - 1`은 `a` 자신이다. 이걸 `b > 0`으로 쓰면 무슨 일이 생기는지는 뒤의 "건너뛰기 기준을 잘못 잡는 자리"에서 돌려 본다.

```js
// 풀이 3: 정렬 + 두 수 고정 + 투 포인터
function fourSum(nums, target) {
  nums.sort((a, b) => a - b);                          // 비교 함수 필수
  const n = nums.length, out = [];
  for (let a = 0; a < n - 3; a++) {
    if (a > 0 && nums[a] === nums[a - 1]) continue;    // 같은 첫 수
    for (let b = a + 1; b < n - 2; b++) {
      if (b > a + 1 && nums[b] === nums[b - 1]) continue; // 이번 a에서 같은 둘째 수
      let l = b + 1, r = n - 1;
      while (l < r) {
        const sum = nums[a] + nums[b] + nums[l] + nums[r];
        if (sum < target) l++;
        else if (sum > target) r--;
        else {
          out.push([nums[a], nums[b], nums[l], nums[r]]);
          while (l < r && nums[l] === nums[l + 1]) l++; // 같은 셋째 수
          while (l < r && nums[r] === nums[r - 1]) r--; // 같은 넷째 수
          l++;
          r--;
        }
      }
    }
  }
  return out;
}
```

시간 O(n³)이다. 바깥 두 반복이 O(n²), 안쪽 투 포인터가 O(n)이다. 공간은 결과를 빼면 포인터와 정렬 보조 공간뿐이다.

### 두 줄로 가지치기

정렬돼 있으니 "지금 고른 수로 만들 수 있는 가장 작은 합"과 "가장 큰 합"을 바로 안다. 가장 작은 합이 `target`보다 크면 이 `a`(또는 `b`)뿐 아니라 그 뒤도 모두 볼 필요가 없다. 가장 큰 합이 `target`보다 작으면 이 `a`만 건너뛰고 다음으로 간다. 그림의 마지막 단계(a = 0에서 가장 작은 합 4)가 앞의 경우다.

```js
// 풀이 3에 가지치기 추가 (a 반복의 맨 앞)
if (nums[a] + nums[a + 1] + nums[a + 2] + nums[a + 3] > target) break;    // 가장 작은 합도 크다
if (nums[a] + nums[n - 3] + nums[n - 2] + nums[n - 1] < target) continue; // 가장 큰 합도 작다
// b 반복의 맨 앞
if (nums[a] + nums[b] + nums[b + 1] + nums[b + 2] > target) break;
if (nums[a] + nums[b] + nums[n - 2] + nums[n - 1] < target) continue;
```

```text
                  가지치기 없음   있음
n200 값 ±10^9      7.3ms         3.4ms
n1000 값 ±10^9     1091.0ms      705.4ms
```

시간 복잡도는 그대로지만 실제로는 절반 가까이 줄었다. 값이 넓게 퍼진 무작위 입력에서 양 끝 쪽 `a`, `b`는 대부분 가지치기에 걸린다.

`break`와 `continue`를 바꿔 쓰면 틀린다. 가장 작은 합이 크다면 `a`가 커질수록 더 커지니 끝내도 되지만(`break`), 가장 큰 합이 작다면 `a`가 커지면 커질 수 있으니 다음 `a`는 봐야 한다(`continue`). 그리고 3Sum에서 쓰던 "`nums[a] > 0`이면 끝" 같은 짧은 조건을 `nums[a] > target`으로 옮기면 음수 `target`에서 틀린다. 이것도 뒤에서 돌려 본다.

### Python과 Java에서 달라지는 것은 정수 넘침

```python
from typing import List

def four_sum(nums: List[int], target: int) -> List[List[int]]:
    nums.sort()
    n, out = len(nums), []
    for a in range(n - 3):
        if a > 0 and nums[a] == nums[a - 1]:
            continue                                         # 같은 첫 수는 한 번만
        for b in range(a + 1, n - 2):
            if b > a + 1 and nums[b] == nums[b - 1]:
                continue                                     # 같은 둘째 수는 한 번만
            l, r = b + 1, n - 1
            while l < r:
                s = nums[a] + nums[b] + nums[l] + nums[r]    # Python 정수는 넘치지 않는다
                if s < target:
                    l += 1
                elif s > target:
                    r -= 1
                else:
                    out.append([nums[a], nums[b], nums[l], nums[r]])
                    while l < r and nums[l] == nums[l + 1]:
                        l += 1
                    while l < r and nums[r] == nums[r - 1]:
                        r -= 1
                    l += 1
                    r -= 1
    return out
```

Python 정수는 필요한 만큼 자릿수를 늘리니 넘침이 없다. 대신 같은 O(n³)이라도 인터프리터라 느리다. n = 200이면 문제없지만 가지치기 두 줄을 넣어 두는 게 좋다.

```java
class Solution {
    public List<List<Integer>> fourSum(int[] nums, int target) {
        Arrays.sort(nums);
        int n = nums.length;
        List<List<Integer>> out = new ArrayList<>();
        for (int a = 0; a < n - 3; a++) {
            if (a > 0 && nums[a] == nums[a - 1]) continue;
            for (int b = a + 1; b < n - 2; b++) {
                if (b > a + 1 && nums[b] == nums[b - 1]) continue;
                int l = b + 1, r = n - 1;
                while (l < r) {
                    long s = (long) nums[a] + nums[b] + nums[l] + nums[r]; // 첫 항을 long으로
                    if (s < target) l++;
                    else if (s > target) r--;
                    else {
                        out.add(Arrays.asList(nums[a], nums[b], nums[l], nums[r]));
                        while (l < r && nums[l] == nums[l + 1]) l++;
                        while (l < r && nums[r] == nums[r - 1]) r--;
                        l++;
                        r--;
                    }
                }
            }
        }
        return out;
    }
}
```

`(long) nums[a] + ...`의 캐스트 위치가 핵심이다. 덧셈은 왼쪽부터 하니, 첫 항이 `long`이면 나머지 덧셈이 모두 `long`으로 된다. `long s = nums[a] + nums[b] + nums[l] + nums[r]`처럼 변수만 `long`으로 선언하면 오른쪽이 `int`로 다 더해져 넘친 뒤에 `long`으로 바뀐다. 직접 돌려 보면 이렇다.

```text
[[-2, 0, 1, 2], [-1, -1, 1, 2], [-1, 0, 1, 1]]
[[2, 2, 2, 2]]
[]
[]
```

위의 네 줄은 `long` 캐스트를 한 풀이에 `[2, -1, 0, -2, 1, 1, -1]`(목표 1), `[2, 2, 2, 2, 2]`(목표 8), 10억 네 개(목표 -294967296), `[1, 2, 3]`(목표 6)을 넣은 결과다. 세 번째가 빈 배열이라 맞다. 10억 네 개의 합 40억은 `int`에서 2^32를 빼고 -294967296이 되는데, `int`로 더하는 코드는 이걸 목표와 같다고 판단한다(다섯째 줄의 `matches 1`). 변수만 `long`으로 선언한 코드도 같은 값이 나왔다(여섯째 줄). ## 두 수 합을 해시맵에 모아 만나게 하기

네 수를 두 쌍으로 나누면 다른 길이 보인다. 두 수의 합을 모두 해시맵에 담아 두고, 다른 두 수의 합을 만들 때마다 `target - 합`이 맵에 있는지 본다. 반씩 나눠 가운데서 만나는(meet in the middle) 방법이다. 두 수 쌍은 O(n²)개니 잘 되면 O(n²)이다.

칸이 겹치지 않게 하는 게 까다롭다. 맵에는 `i < j < k`인 쌍 `(i, j)`만 들어 있도록, `k`를 옮겨 가며 "`k`보다 앞의 칸으로 만든 쌍"만 넣는다. 그러면 `(i, j)`와 `(k, l)`을 붙인 네 칸은 `i < j < k < l`로 겹치지 않는다.

```js
// 풀이 4: 두 수 합 해시맵 (meet in the middle)
function fourSum(nums, target) {
  const n = nums.length, bySum = new Map(), seen = new Set(), out = [];
  for (let k = 0; k < n; k++) {
    for (let l = k + 1; l < n; l++) {                    // 뒤쪽 쌍 (k, l)
      const list = bySum.get(target - nums[k] - nums[l]); // 앞쪽 쌍 중 합이 맞는 것
      if (!list) continue;
      for (const [i, j] of list) {
        const t = [nums[i], nums[j], nums[k], nums[l]].sort((x, y) => x - y);
        const key = t.join(",");
        if (!seen.has(key)) { seen.add(key); out.push(t); }
      }
    }
    for (let i = 0; i < k; i++) {                         // k를 끝으로 하는 앞쪽 쌍을 넣는다
      const s = nums[i] + nums[k];
      if (!bySum.has(s)) bySum.set(s, []);
      bySum.get(s).push([i, k]);
    }
  }
  return out;
}
```

같은 입력들로 재 봤다.

```text
n200 값 ±10^9 무작위   18.1ms
n200 값 ±50 무작위     265.4ms
n200 모두 0            28820.5ms
n1000 값 ±10^9 무작위  576.2ms     (풀이 3은 1091.0ms)
```

결과가 극단적이다. 값이 넓게 퍼져 같은 합이 거의 없는 n = 1000 입력에서는 투 포인터 O(n³)보다 두 배 빨랐다. 그런데 모두 0인 n = 200 입력에서는 29초 가까이 걸렸다. 모든 쌍의 합이 0이라 맵의 한 칸에 쌍 19900개가 몰리고, 뒤쪽 쌍마다 그 목록을 다 돌면서 네 수 배열과 키를 만들었기 때문이다. 이때 실제 비용은 "합이 맞는 (앞쪽 쌍, 뒤쪽 쌍) 짝의 수"라서 최악 O(n⁴)이다. 값이 ±500인 n = 1000 입력은 2분이 넘도록 첫 실행조차 끝나지 않아 멈췄다. 답이 433만 개인 입력이라 짝의 수도 그만큼 폭발한다.

이 풀이는 "답을 모두 나열하라"는 이 문제와 잘 맞지 않는다. 대신 답의 개수만 세라면 이야기가 달라진다. 뒤의 "네 배열에서 하나씩 고르면"에서 본다.

## 다섯 풀이의 순위는 입력이 정한다

## 건너뛰기 기준을 잘못 잡는 자리

### 둘째 수 중복을 b > 0으로 거른다

3Sum의 `i > 0 && nums[i] === nums[i - 1]`을 둘째 수에 그대로 옮기면 이렇게 된다.

```js
if (b > 0 && nums[b] === nums[b - 1]) continue; // 틀림: b > a + 1이어야 한다
```

```text
bBug [] [[-2,0,1,2],[-1,0,1,1]]
```

`[2, 2, 2, 2, 2]`(목표 8)에서 답이 사라졌고, 예시 입력에서는 `[-1, -1, 1, 2]`가 빠졌다. `a = 0`일 때 `b = 1`이 `nums[0]`과 같은 2라서 건너뛰었다. 하지만 `nums[0]`은 첫 수로 쓰고 있는 칸이지 이번 `a`에서 고른 둘째 수가 아니다. 같은 값을 첫 수와 둘째 수로 동시에 쓰는 조합을 통째로 잃는다. 건너뛰기의 기준은 "이 층에서 처음 고르는 칸인가"이고, 둘째 수 층은 `a + 1`에서 시작한다.

### 3Sum의 조기 종료를 그대로 옮긴다

3Sum은 목표가 0이라 "첫 수가 양수면 끝"이 맞았다. 이걸 `nums[a] > target`으로 일반화하면 그럴듯해 보인다.

```js
if (nums[a] > target) break; // 틀림: target이 음수면 성립하지 않는다
```

```text
prBug [] correct [[-4,-3,-2,-1]]
```

`[-1, -2, -3, -4, -5]`, 목표 -10이다. 정렬하면 첫 수가 -5인데, -5는 -10보다 크니 바로 끝내 버렸다. 음수를 더하면 합이 작아지니 "첫 수가 목표보다 크면 합도 크다"는 음수가 섞이면 틀린다. 가장 작은 네 수의 합과 비교하는 위의 가지치기는 부호와 상관없이 맞는다.

### 넷째 수를 찾을 때 셋째 수 칸을 다시 쓴다

이진 탐색 풀이에서 `has(c + 1, need)` 대신 `has(c, need)`로 쓰면 셋째 수의 칸에서부터 넷째 수를 찾는다.

```text
[[1,2,3,3]]   ← [1, 2, 3, 4], target 9
```

`[1, 2, 3, 4]`에는 합이 9인 네 칸이 없다(네 칸을 다 써도 10이다). 그런데 3이 한 칸뿐인데도 `[1, 2, 3, 3]`이 나왔다. 셋째 수로 쓴 3을 넷째로 또 찾았기 때문이다. 탐색 범위의 시작은 언제나 "마지막으로 고른 칸 + 1"이다. 투 포인터 풀이의 `l = b + 1`도 같은 규칙이다.

## 네 배열에서 하나씩 고르면

LeetCode 454(4Sum II)는 길이가 같은 네 배열 A, B, C, D에서 하나씩 골라 합이 0이 되는 경우의 수를 센다. 조합을 나열하지 않고 개수만 세며, 같은 값이어도 칸이 다르면 다른 경우로 센다. 이때는 풀이 4가 빛난다. A + B의 합마다 몇 번 나왔는지 세어 두고, C + D의 합마다 `-(c + d)`가 몇 번 나왔는지 더하면 된다.

```js
function fourSumCount(A, B, C, D) {
  const m = new Map();
  for (const a of A) for (const b of B) m.set(a + b, (m.get(a + b) || 0) + 1); // 앞 두 배열의 합 개수
  let cnt = 0;
  for (const c of C) for (const d of D) cnt += m.get(-(c + d)) || 0;          // 뒤 두 배열이 맞추는 수
  return cnt;
}
```

```text
454 2 1
```

`[1, 2]`, `[-2, -1]`, `[-1, 2]`, `[0, 2]`에서 2가지, 모두 `[0]`이면 1가지다. 나열 대신 개수만 쓰니 목록을 돌 일이 없고, 같은 합이 아무리 많아도 정확히 O(n²)이다. 18번에서 29초 걸리던 바로 그 구조가 454번에서는 최선이 되는 건 "답을 모두 내라"와 "개수만 내라"의 차이 때문이다. 정렬 투 포인터로 454번을 풀면 O(n³)이라 오히려 느리다.

같은 생각으로 한 배열에서 칸이 다른 네 수 조합의 개수(값이 같아도 칸이 다르면 따로)를 셀 수도 있다. 풀이 4의 쌍 목록 대신 쌍의 개수만 담으면 된다.

```js
function countQuads(nums, target) {
  const pairCnt = new Map();     // 합 → k보다 앞의 칸으로 만든 쌍의 개수
  let cnt = 0;
  for (let k = 0; k < nums.length; k++) {
    for (let l = k + 1; l < nums.length; l++) cnt += pairCnt.get(target - nums[k] - nums[l]) || 0;
    for (let i = 0; i < k; i++) {
      const s = nums[i] + nums[k];
      pairCnt.set(s, (pairCnt.get(s) || 0) + 1);
    }
  }
  return cnt;
}
```

```text
5 6
64684950 3.0ms
```

`[0, 0, 0, 0, 0]`, 목표 0이면 C(5, 4) = 5가지, 이 글의 예시는 값 조합으로는 3개지만 칸 조합으로는 6가지다(1이 두 칸, -1이 두 칸이라). 마지막 줄은 모두 0인 200칸 배열이다. 풀이 4가 29초 걸린 바로 그 입력에서, 6468만 4950가지를 3ms에 셌다. 목록을 돌지 않으니 같은 합이 아무리 몰려도 O(n²)이다.

## 더 넓히는 꼬리 질문

### k가 입력으로 주어진다면

수 하나를 고정할 때마다 k가 줄어드는 재귀로 짠다. 바닥은 2Sum 투 포인터다. 시간은 O(n^(k−1))이다. 각 층에서 중복 건너뛰기는 그 층의 시작점(`i > start`)을 기준으로 하고, 가지치기도 층마다 "남은 k개의 가장 작은 합과 가장 큰 합"으로 일반화한다. 코드는 3Sum 글에 있다.

### 답이 아니라 target에 가장 가까운 네 수의 합이라면

3Sum Closest(16번)를 한 층 넓힌 것이다. 풀이 3의 틀에서 답을 모으는 대신 `|sum − target|`이 가장 작은 합을 기억한다. 정확히 같은 합이 나오면 바로 끝낸다.

```js
function fourSumClosest(nums, target) {
  nums.sort((a, b) => a - b);
  const n = nums.length;
  let best = nums[0] + nums[1] + nums[2] + nums[3];
  for (let a = 0; a < n - 3; a++)
    for (let b = a + 1; b < n - 2; b++) {
      let l = b + 1, r = n - 1;
      while (l < r) {
        const s = nums[a] + nums[b] + nums[l] + nums[r];
        if (Math.abs(s - target) < Math.abs(best - target)) best = s; // 더 가까우면 갱신
        if (s === target) return s;
        if (s < target) l++; else r--;
      }
    }
  return best;
}
```

```text
4 0
```

이 글의 예시에 목표 10을 주면 만들 수 있는 가장 큰 합 4가 가장 가깝고, `[5, -4, 3, 1, -2]`에 목표 0을 주면 `5 − 4 + 1 − 2 = 0`이 정확히 맞는다. 값 하나만 돌려주니 중복 건너뛰기는 빼도 결과가 같다. 넣으면 같은 계산을 조금 줄일 뿐이다.

## 한 층 더 두른 3Sum

4Sum은 정렬한 뒤 두 수를 고정하고 나머지 둘을 양 끝 투 포인터로 찾는 O(n³) 문제다. 3Sum과 달라지는 건 셋이다. 둘째 수 중복은 `b > a + 1`일 때만 따진다. 그 층의 첫 칸은 건너뛸 이유가 없기 때문이다. 조기 종료는 "첫 수가 크면"이 아니라 "가장 작은 네 수의 합이 크면"으로 써야 음수에서도 맞는다. 그리고 네 수의 합은 ±4 × 10^9까지 가니 Java에서는 첫 항을 `long`으로 캐스트해야 한다. 두 수 합을 해시맵에 모으는 방법은 같은 합이 드물면 빠르지만 답을 나열할 때는 최악 O(n⁴)이고, 개수만 세는 4Sum II에서 제 몫을 한다.

## 면접에서 나올 만한 질문

### 4Sum의 시간 복잡도는 얼마이고 더 줄일 수 있나요?

정렬 후 두 수를 고정하고 투 포인터를 돌리면 O(n³)이다. 두 수 합을 해시맵에 담는 방법은 같은 합이 드물면 O(n²) 근처지만, 답을 모두 나열해야 하니 같은 합이 몰리면 O(n⁴)까지 간다. 모두 0인 200칸 배열에서 해시맵이 29초, 투 포인터가 0.0ms였다. 나열 문제에서는 O(n³) 투 포인터가 최악을 보장하는 답이다.

### 둘째 수 중복을 왜 b > a + 1일 때만 검사하나요?

중복은 "같은 층에서 이미 고른 값"을 다시 고를 때만 생기기 때문이다. `b = a + 1`은 이번 `a`에서 처음 고르는 둘째 수라 앞 칸 `b - 1`은 첫 수 자신이다. `b > 0`으로 쓰면 `[2, 2, 2, 2, 2]`에서 첫 수와 둘째 수를 같은 2로 쓰는 조합을 잃어 빈 배열이 나온다.

### Java로 풀 때 주의할 점은요?

네 수의 합이 최대 4 × 10^9라 `int`를 넘는다. 10억 네 개를 `int`로 더하면 -294967296이 되어 목표가 그 값인 테스트에서 오답이 나온다. `long s = (long) nums[a] + nums[b] + nums[l] + nums[r]`처럼 첫 항을 캐스트해야 하고, 변수만 `long`으로 선언하면 오른쪽이 이미 `int`로 넘친 뒤라 소용없다.

### 가지치기는 어떻게 하고 얼마나 효과가 있나요?

정렬돼 있으니 고정한 수로 만들 수 있는 가장 작은 합과 가장 큰 합을 바로 안다. 가장 작은 합이 목표보다 크면 `break`, 가장 큰 합이 목표보다 작으면 `continue`다. 복잡도는 같지만 n = 1000 무작위 입력에서 1091ms가 705ms로 줄었다. `nums[a] > target`처럼 줄여 쓰면 음수 목표에서 틀린다.

### 해시맵으로 두 수 합을 모으는 방법은 언제 쓰나요?

답의 개수만 세는 문제에서 쓴다. 4Sum II처럼 네 배열에서 하나씩 고르는 경우는 앞 두 배열의 합 개수를 세어 두고 뒤 두 배열로 맞추면 정확히 O(n²)이다. 답을 나열해야 하는 18번에서는 같은 합의 쌍 목록을 매번 돌아야 해서 최악 O(n⁴)이 된다. 같은 구조가 문제의 요구에 따라 최선도 최악도 된다.

### kSum으로 일반화하면 어떻게 짜나요?

수 하나를 고정할 때마다 k를 하나 줄이는 재귀로 짜고 바닥인 2Sum에서 투 포인터를 쓴다. 시간은 O(n^(k−1))이다. 중복 건너뛰기는 그 층의 시작 칸 기준(`i > start`)이고, 가지치기는 남은 k개의 가장 작은 합과 가장 큰 합으로 한다. 4Sum의 `b > a + 1`이 k = 4일 때의 `i > start`다.
