사진을 올리면 썸네일을 만드는 기능을 Lambda로 짰다. S3 버킷에 파일이 올라오면 알림이 함수를 부르고, 함수는 줄인 이미지를 같은 버킷에 `thumb-` 이름으로 저장한다. 배포하고 사진 한 장을 올렸다. 다음 날 아침 결제 알림이 왔다. 썸네일의 썸네일의 썸네일이 밤새 만들어지고 있었다. 썸네일을 저장한 것도 "버킷에 파일이 올라왔다"는 사건이었기 때문이다.

서버리스 아키텍처는 서버 프로세스 하나가 요청을 기다리는 구조가 아니라, 관리형 서비스에서 일어난 사건마다 함수가 하나씩 불려 반응하는 구조다. 함수를 부르는 건 내 코드가 아니라 S3, SQS, API Gateway, 스케줄러 같은 트리거다. 그래서 "누가, 어떻게 부르고, 실패하면 누가 다시 부르나"를 트리거마다 알아야 한다. 위의 사고도 트리거가 어떻게 동작하는지를 몰라서 생겼다.

이 주제의 다른 글: 시간·크기·동시성·DB 연결 같은 플랫폼의 벽은 [서버리스의 한계](/posts/serverless-limits)에, 첫 요청이 느린 이유는 [콜드 스타트](/posts/cold-starts)에, SNS 뒤에 SQS를 하나씩 두는 팬아웃은 [발행·구독](/posts/pub-sub)에 있다. 이 글은 그 위에서 구조를 짜는 쪽, 트리거의 호출 방식과 재시도, 배치 실패, 여러 단계를 잇는 법, 비용이 어떻게 계산되는지를 본다. AWS Lambda 기준이고 숫자와 기본값은 2026년 10월 공개 문서 기준이다. 로컬 실험은 Node 22에서 Lambda의 동작을 흉내 낸 하네스로 돌린 출력이고(실제 AWS가 아니다), AWS CLI 출력은 계정 없이 실제 형식대로 쓴 예시다.

## 함수는 사건 하나에 반응한다

서버리스라는 말에는 두 가지가 섞여 있다. 하나는 코드를 함수 단위로 올리고 호출될 때만 실행되는 FaaS(Lambda, Cloud Functions, Vercel Functions)다. 다른 하나는 직접 운영하지 않는 관리형 서비스들이다. 저장소(S3), 큐(SQS), DB(DynamoDB), 인증(Cognito), 이벤트 버스(EventBridge). 서버리스 아키텍처는 이 둘을 엮는다. 함수는 짧게 돌고, 상태는 관리형 서비스에 둔다.

처음의 썸네일 기능을 그림으로 그리면 이렇다. 다음을 누르면 업로드 한 번이 어떤 길을 타는지, 그리고 어디서 고리가 생기는지 나온다.

고리를 로컬에서 흉내 내 봤다. 알림 설정에 접두사 필터가 없을 때와, 함수가 다른 접두사(`thumbnails/`)에 쓰고 알림은 `uploads/`만 받게 했을 때다. 하네스는 다섯 번째에서 강제로 멈춘다.

```js
function simulate(label, filterPrefix, outKey) {
  const queue = ["uploads/cat.jpg"]; let invocations = 0;
  while (queue.length && invocations < 5) {
    const key = queue.shift();
    if (!key.startsWith(filterPrefix)) continue;   // 알림 설정의 접두사 필터
    invocations++;
    const out = outKey(key);
    console.log(`  #${invocations} got ${key} -> put ${out}`);
    queue.push(out);                               // 저장이 다시 알림을 만든다
  }
  console.log(`${label}: ${invocations} invocations${invocations === 5 ? " (stopped by harness)" : ""}`);
}
simulate("same prefix", "", (k) => k.replace(/([^/]+)$/, "thumb-$1"));
simulate("separate prefix", "uploads/", (k) => k.replace("uploads/", "thumbnails/"));
```

```text
  #3 got uploads/thumb-thumb-cat.jpg -> put uploads/thumb-thumb-thumb-cat.jpg
  #4 got uploads/thumb-thumb-thumb-cat.jpg -> put uploads/thumb-thumb-thumb-thumb-cat.jpg
```

실제 AWS에는 이 하네스의 "다섯 번에서 멈춤"이 없다. Lambda는 2023년부터 SQS, SNS를 거치는 재귀 고리를 감지해 16번쯤에서 끊기 시작했고 감지하는 경로를 넓혀 왔지만, 모든 경로를 다 잡아 주리라고 기대하면 안 된다. 고리는 설계로 막는다. 입력과 출력을 다른 버킷이나 다른 접두사로 나누고, 알림에 접두사 필터를 걸고, 함수 안에서도 "이미 썸네일인 파일이면 바로 끝낸다"를 한 번 더 확인한다. 예약 동시성을 작게 걸어 두면 고리가 생겨도 동시에 도는 수가 묶여서 청구서가 덜 커진다.

## 트리거마다 부르는 방식이 다르다

Lambda를 부르는 방식은 세 가지다. 같은 함수라도 어떤 트리거에 연결되느냐에 따라 실패했을 때의 동작이 완전히 다르다.

| 방식 | 대표 트리거 | 누가 기다리나 | 실패하면 |
|---|---|---|---|
| 동기 호출 | API Gateway, ALB, 함수 URL | 부른 쪽이 응답을 기다린다 | Lambda는 다시 부르지 않는다. 부른 쪽(브라우저, SDK)이 알아서 재시도한다 |
| 비동기 호출 | S3 알림, SNS, EventBridge | 아무도 기다리지 않는다. Lambda 내부 큐에 들어간다 | 기본 2번 더 시도한다(총 3번). 끝내 실패하면 실패 목적지나 DLQ로, 없으면 버려진다 |
| 폴링(이벤트 소스 매핑) | SQS, Kinesis, DynamoDB Streams, Kafka | Lambda가 직접 꺼내 와 배치로 부른다 | SQS는 메시지가 다시 보이고, 스트림은 그 샤드가 성공할 때까지 막힌다 |

동기 호출은 평범한 서버와 같다. 부른 쪽이 에러를 보고 판단한다. 시간 한도(API Gateway의 29초 같은)는 [서버리스의 한계](/posts/serverless-limits)에서 다룬다.

비동기 호출은 처음 보면 헷갈린다. S3는 Lambda 서비스에 사건을 넘기고 바로 "202 받았다"를 듣는다. 실제 실행은 그 뒤 Lambda가 자기 큐에서 꺼내 한다. 함수가 에러를 내면 1분쯤 뒤, 그다음 2분쯤 뒤에 다시 부른다. 아래 그림에서 다음을 누르면 그 과정이 나온다.

마지막 단계의 "조용히 버려진다"가 비동기 트리거에서 가장 흔한 사고다. 에러 로그는 CloudWatch에 남지만, 그 사건을 다시 처리할 방법은 없다. 그래서 비동기로 불리는 함수에는 실패 목적지를 꼭 붙인다.

```bash
# 재시도 횟수, 사건을 붙잡아 둘 최대 시간, 실패 목적지를 정한다
aws lambda put-function-event-invoke-config \
  --function-name thumbnailer \
  --maximum-retry-attempts 1 \
  --maximum-event-age-in-seconds 3600 \
  --destination-config '{"OnFailure":{"Destination":"arn:aws:sqs:ap-northeast-2:123456789012:thumbnailer-failed"}}'
```

```text
{
    "LastModified": "2026-10-21T14:05:40.118000+09:00",
    "FunctionArn": "arn:aws:lambda:ap-northeast-2:123456789012:function:thumbnailer:$LATEST",
    "MaximumRetryAttempts": 1,
    "MaximumEventAgeInSeconds": 3600,
    "DestinationConfig": {
        "OnSuccess": {},
        "OnFailure": {
            "Destination": "arn:aws:sqs:ap-northeast-2:123456789012:thumbnailer-failed"
        }
    }
}
```

(예시 출력이다.) `MaximumEventAgeInSeconds`는 60초부터 6시간(21600초)까지다. 함수가 거절(throttle)되거나 Lambda 쪽 오류로 실행조차 못 하면, 사건은 이 시간 동안 내부 큐에서 기다리며 다시 시도된다. 썸네일처럼 늦어도 되는 일은 길게, "5분 안에 안 가면 의미 없는 알림"은 짧게 둔다.

## 배치에서 하나만 실패했을 때

SQS에 연결된 함수는 메시지를 한 번에 여러 개(배치) 받는다. 배치 크기를 10으로 잡으면 호출 한 번에 메시지 열 개가 온다. 여기서 하나만 실패하면 어떻게 될까. 함수가 그 실패를 어떻게 알리느냐에 따라 세 가지 결과가 나온다. 핸들러는 실패한 메시지의 ID를 `batchItemFailures`로 돌려준다.

```js
const processed = new Set();   // 실제로는 DynamoDB 같은 바깥 저장소
export async function handler(event) {
  const batchItemFailures = [];
  for (const record of event.Records) {
    try {
      const order = JSON.parse(record.body);
      if (processed.has(order.orderId)) continue;      // 다시 와도 한 번만 처리한다
      if (order.amount < 0) throw new Error(`bad amount ${order.amount}`);
      processed.add(order.orderId);
      console.log(`  ok   ${record.messageId} order ${order.orderId}`);
    } catch (err) {
      console.log(`  fail ${record.messageId} ${err.message}`);
      batchItemFailures.push({ itemIdentifier: record.messageId });
    }
  }
  return { batchItemFailures };
}
```

하네스는 메시지 다섯 개 중 세 번째(`amount: -1`)가 항상 실패하게 하고, 세 가지 경우를 세 바퀴씩 돌렸다. `throw`는 실패가 하나라도 있으면 호출 전체를 에러로 끝낸 경우, `no-setting`은 `batchItemFailures`를 돌려주지만 매핑에 그 설정을 켜지 않은 경우, `setting`은 켠 경우다.

```text
[no-setting]

```

`throw`에서는 멀쩡한 네 개까지 매번 다시 왔다. 15번 전달됐고, 다섯 개 모두 `receiveCount=3`이다. 두 번째 바퀴부터 `ok` 줄이 안 찍힌 건 핸들러가 처리한 주문 ID를 기억해 건너뛰었기 때문이다. 이 장치가 없었다면 주문 네 개가 세 번씩 처리됐다. 큐의 `maxReceiveCount`가 3이었다면 멀쩡한 메시지 넷까지 DLQ로 갔을 것이다.

`no-setting`이 가장 위험하다. 핸들러는 실패를 보고했지만 매핑이 응답을 읽지 않으니 호출은 성공으로 끝났고, 실패한 `m3`까지 다섯 개 모두 지워졌다. 에러 로그 한 줄만 남고 주문 하나가 사라진다. `setting`에서는 실패한 `m3`만 남아 다시 오고, 나머지는 첫 바퀴에 지워졌다. 아래 그림이 `setting`의 첫 두 바퀴다.

## 사건 하나를 여러 곳에 나눠 보낸다

주문이 들어오면 메일을 보내고, 배송 흐름을 시작하고, 통계에 넣어야 한다. 주문 함수가 셋을 차례로 부르면 함수 하나가 모든 후속 처리를 알게 된다. 서버리스에서는 이벤트 버스에 사건을 하나 남기고, 규칙(rule)이 그걸 대상마다 나눠 보낸다. SNS 토픽 뒤에 서비스마다 SQS 큐를 두는 구성은 [발행·구독](/posts/pub-sub)에서 봤으니, 여기서는 EventBridge로 같은 일을 하는 모양을 본다.

## 여러 단계는 함수끼리 부르지 않는다

배송 흐름은 재고 예약 → 고객이 취소할 수 있는 30분 대기 → 출고 요청이고, 재고가 없으면 주문을 취소한다. 이걸 함수 A가 함수 B를 동기로 부르고, B가 C를 부르게 짜면 A는 C가 끝날 때까지 돈을 내며 기다린다. 중간에 실패하면 어디까지 했는지 아는 곳이 없다.

Step Functions 같은 워크플로 서비스는 단계와 분기, 재시도, 보상을 상태 머신 정의로 적게 한다. 각 단계의 함수는 자기 일만 하고 끝난다. "30분 기다렸다가 출고한다" 같은 대기도 함수를 띄워 둔 채가 아니라 워크플로가 상태로 들고 있으니, 기다리는 동안 함수 요금이 나가지 않는다.

## 비용은 호출 수와 실행 시간으로 계산된다

Lambda 요금은 두 부분이다. 호출 100만 번에 0.20달러, 그리고 실행 시간 × 메모리(GB-초)에 GB-초당 0.0000166667달러다(미국 동부 버지니아 리전, x86 기준. Arm은 GB-초가 20% 싸다. 리전마다 조금씩 다르고 무료 사용량은 빼고 계산했다). 실행 시간은 1ms 단위로 올림한다. 메모리를 올리면 CPU도 비례해서 늘어서(1,769MB에서 vCPU 하나에 해당한다), 계산이 많은 함수는 메모리를 올려 시간이 줄어 오히려 싸지는 경우도 있다.

하루 100만 건, 한 달 3000만 건이 평균 200ms, 512MB로 돈다면 요청 6달러에 실행 50달러, 한 달 56달러다. 같은 일을 0.5 vCPU, 1GB짜리 컨테이너 두 대(Fargate, 버지니아 기준 시간당 vCPU 0.04048달러, GB 0.004445달러)로 상시 돌리면 한 달 약 36달러다. 단순 비교로는 컨테이너가 싸다. 손익분기점을 계산하면 요청당 약 0.0000018667달러이니 한 달 약 1930만 건, 평균 초당 7.5건쯤에서 두 쪽이 같아진다.

하지만 이 비교에는 빠진 것이 많다. 컨테이너 두 대는 트래픽이 0인 새벽에도 돈이 나가고, 초당 수백 건으로 몰리는 순간을 받으려면 더 많이 띄워 둬야 한다. Lambda 앞에 API Gateway를 두면 HTTP API 기준 100만 건에 1달러가 더 붙어 3000만 건이면 30달러가 늘어난다. 서버리스는 트래픽이 적거나 들쭉날쭉할 때 싸고, 꾸준히 많을 때 비싸다. 비용을 줄이는 방법은 [클라우드 비용 줄이기](/posts/cloud-cost-optimization)에서 다룬다.

직접 계산해 보자. 한 달 호출 수, 평균 실행 시간(ms), 메모리(MB)를 받아 x86 기준 요금을 센트 단위로 반올림해 돌려준다. 무료 사용량은 빼지 않는다.

## 상태는 함수 밖에 둔다

함수 인스턴스는 언제 새로 뜨고 언제 사라질지 모른다. 같은 사용자의 두 번째 요청이 같은 인스턴스로 간다는 보장도 없다. 그래서 메모리에 세션이나 장바구니를 두면 안 되고, `/tmp`도 캐시로만 쓴다. 상태는 DynamoDB, ElastiCache, S3 같은 바깥 저장소에 둔다. 앞의 배치 핸들러에서 처리한 주문 ID를 `Set`에 둔 것도 하네스라서 그렇게 했을 뿐, 실제로는 DynamoDB에 조건부 쓰기(`attribute_not_exists`)로 남겨야 인스턴스가 바뀌어도 중복을 거른다. AWS Lambda Powertools의 멱등성 유틸리티가 이 일을 해 준다. 멱등성 키 저장소를 설계하는 법은 [멱등성 키](/posts/idempotency-key)에 있다.

트리거는 대부분 "적어도 한 번" 부른다. S3 알림도, SQS도, EventBridge도 같은 사건을 두 번 줄 수 있다. 서버리스 함수는 처음부터 같은 사건을 두 번 받아도 결과가 같게 짠다. 이게 서버리스 아키텍처에서 가장 먼저 몸에 익혀야 하는 습관이다.

같은 이야기가 Next.js에도 있다. Vercel에 배포한 Next.js의 Route Handler와 서버 렌더링은 함수로 돈다. 이 블로그도 Vercel에 있어서, 코드 규칙에 "파일시스템 저장과 WebSocket에 의존하지 않는다"가 들어 있다. 함수 인스턴스의 디스크는 배포 사이에, 심지어 요청 사이에 남는다는 보장이 없고, 오래 붙잡는 연결은 함수가 끝나면 끊기기 때문이다. 페이지를 언제 정적으로, 언제 함수로 만들지는 [Next.js의 정적·동적 렌더링](/posts/nextjs-static-dynamic-rendering)에서 다룬다.

## 서버리스가 맞지 않는 일

계속 바쁜 일은 비싸다. 앞의 계산처럼 평균 트래픽이 높고 일정하면 상시 컨테이너가 싸다. 한 번에 15분을 넘는 작업, 연결을 오래 붙잡는 WebSocket 서버, GPU가 필요한 추론은 Lambda에 맞지 않는다(API Gateway의 WebSocket API처럼 연결 관리를 플랫폼이 맡는 방식은 있다). p99 지연이 엄격한 API는 콜드 스타트를 감당할 비용(프로비저닝된 동시성)까지 계산에 넣는다.

묶이는 것도 비용이다. 트리거, 권한(IAM), 이벤트 형식이 모두 그 클라우드의 것이라 다른 곳으로 옮기기 어렵다. 업무 로직을 핸들러에서 떼어 순수한 함수로 두고 핸들러는 이벤트를 풀어서 넘기기만 하게 짜면, 옮길 때 다시 쓸 부분이 핸들러로 줄어든다. 로컬에서 테스트하기도 쉬워진다.

## 사건이 사라졌다는 문의가 오면

"사진을 올렸는데 썸네일이 안 생긴다"는 문의가 오면 트리거의 종류부터 확인하고, 그 방식의 실패 경로를 따라간다.

```bash
# 어떤 비동기 설정이 걸려 있나: 재시도 횟수와 실패 목적지
aws lambda get-function-event-invoke-config --function-name thumbnailer

# 어떤 이벤트 소스 매핑이 있고 켜져 있나
aws lambda list-event-source-mappings --function-name order-worker \
  --query 'EventSourceMappings[].{state:State,batch:BatchSize,types:FunctionResponseTypes}'

# 실패 목적지 큐에 쌓인 사건 수
aws sqs get-queue-attributes --queue-url https://sqs.ap-northeast-2.amazonaws.com/123456789012/thumbnailer-failed \
  --attribute-names ApproximateNumberOfMessages
```

비동기 트리거라면 함수의 `Errors`와 `Throttles` 지표, 비동기 사건이 내부 큐에서 기다린 시간인 `AsyncEventAge`, 실패 목적지로 보내다 실패한 `DestinationDeliveryFailures`를 본다. 실패 목적지가 비어 있는데 사건이 없어졌다면, 목적지 설정이 없거나 S3 알림 자체가 오지 않은 것이다. S3 알림 설정의 접두사·접미사 필터가 업로드 경로와 맞는지 본다.

SQS 매핑이라면 큐의 `ApproximateAgeOfOldestMessage`가 커지는지 본다. 커지는데 함수 에러가 없다면 `MaximumConcurrency`나 예약 동시성이 너무 작아 따라가지 못하는 것이다. 메시지가 DLQ로 계속 가는데 함수 로그에는 일부만 실패가 찍힌다면, 앞의 `throw` 경우처럼 배치 전체가 다시 오고 있는지, `ReportBatchItemFailures`가 꺼져 있는지 확인한다. 스트림 매핑이라면 `IteratorAge` 하나만 봐도 막힌 샤드가 있는지 보인다.

## 트리거가 곧 구조다

서버리스 아키텍처에서 구조를 정하는 건 함수보다 트리거다. 동기, 비동기, 폴링 중 무엇으로 불리느냐가 재시도와 실패의 행방을 정하고, 그래서 비동기 함수에는 실패 목적지를, 배치 함수에는 부분 실패 보고를, 모든 함수에는 중복을 견디는 처리를 붙인다. 출력이 다시 입력이 되지 않게 경로를 나누고, 여러 단계는 함수끼리 부르지 않고 워크플로에 맡긴다. 비용은 호출 수와 GB-초로 직접 계산해서, 트래픽이 들쭉날쭉한 일에 쓴다.

## 면접에서 나올 만한 질문

### 서버리스 아키텍처가 무엇인가요?

서버 프로세스를 직접 띄워 두지 않고, 관리형 서비스에서 일어난 사건마다 함수가 불려 짧게 실행되는 구조다. 함수(FaaS)는 상태를 갖지 않고, 저장소·큐·DB·인증 같은 관리형 서비스에 상태를 둔다. 호출된 만큼만 요금을 내고 확장은 플랫폼이 맡는 대신, 시간·크기·동시성 한도와 콜드 스타트, 특정 클라우드에 묶이는 비용을 받아들인다.

### Lambda의 동기, 비동기, 폴링 호출은 실패 처리가 어떻게 다른가요?

동기 호출은 Lambda가 다시 부르지 않고 부른 쪽이 에러를 받아 판단한다. 비동기 호출은 Lambda 내부 큐에 들어가 기본 두 번 더 시도하고, 끝내 실패하면 실패 목적지나 DLQ로 보내며 없으면 버린다. 폴링 방식에서 SQS는 실패한 메시지가 가시성 타임아웃 뒤 다시 보이고, Kinesis나 DynamoDB Streams는 순서 때문에 그 샤드가 성공하거나 레코드가 만료될 때까지 막힌다.

### SQS 배치에서 메시지 하나만 실패하면 어떻게 되나요?

함수가 에러를 던지면 배치 전체가 다시 와서 멀쩡한 메시지도 다시 처리된다. ReportBatchItemFailures를 켜고 실패한 메시지 ID만 batchItemFailures로 돌려주면 그것만 남는다. 설정을 켜지 않은 채 batchItemFailures만 돌려주면 호출이 성공으로 처리돼 실패한 메시지까지 지워지니, 매핑의 FunctionResponseTypes를 꼭 확인한다.

### S3 트리거 함수가 자기 자신을 계속 부르는 문제는 어떻게 막나요?

함수의 출력이 다시 트리거 조건에 걸리지 않게 경로를 나눈다. 입력과 출력을 다른 버킷이나 다른 접두사에 두고, 알림에 접두사 필터를 걸고, 함수 안에서도 이미 처리된 파일이면 바로 끝낸다. Lambda가 일부 경로의 재귀를 감지해 끊어 주지만 모든 경로를 잡지는 않으니, 예약 동시성을 작게 걸어 피해 범위를 묶어 두는 것도 함께 한다.

### 여러 단계의 처리를 함수끼리 직접 부르면 안 되는 이유는?

앞 함수가 뒤 함수가 끝날 때까지 실행 시간 요금을 내며 기다리고, 중간에 실패했을 때 어디까지 했는지 아는 곳이 없기 때문이다. Step Functions 같은 워크플로에 단계, 재시도, 실패 시 보상을 정의하면 각 함수는 자기 일만 하고 끝나며, 긴 대기도 함수 요금 없이 워크플로 상태로 들고 있는다. 오래 걸리고 정확히 한 번이 중요하면 Standard, 짧고 많은 흐름은 Express를 고른다.

### 서버리스가 컨테이너보다 비싸지는 때는 언제인가요?

트래픽이 꾸준히 많을 때다. Lambda는 호출 수와 GB-초로 요금을 내니 요청이 늘수록 선형으로 커지고, 상시 컨테이너는 바쁘든 한가하든 시간으로 낸다. 예제 조건(200ms, 512MB)에서는 0.5 vCPU 컨테이너 두 대와 평균 초당 약 7.5건에서 같아졌고, 그보다 꾸준히 많으면 컨테이너가 싸다. 들쭉날쭉하거나 적은 트래픽, 새벽에 0이 되는 일은 서버리스가 유리하다.

### 서버리스 함수를 멱등하게 만들어야 하는 이유는?

S3 알림, SQS, EventBridge 같은 트리거 대부분이 같은 사건을 한 번 이상 전달하고, 비동기 재시도와 배치 재전달도 같은 사건을 다시 준다. 함수 인스턴스는 언제든 바뀌니 처리 기록은 메모리가 아니라 DynamoDB 같은 바깥 저장소에 조건부 쓰기로 남겨 중복을 거른다.
