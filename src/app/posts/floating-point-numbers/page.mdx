정산 배치를 돌렸더니 주문 합계와 결제 합계가 1원 차이 난다. 둘 다 같은 주문 100만 건을 더했는데 하나는 DB의 `SUM`으로, 하나는 애플리케이션에서 반복문으로 더했다. 다른 날에는 해외 결제 모듈에서 19.99달러에 100을 곱해 센트로 바꿨더니 1999가 아니라 1998이 나왔다는 보고가 올라온다. 할인율 계산 결과를 `0.3`과 비교하는 `if`는 테스트에서 한 번도 참이 된 적이 없다.

원인은 하나다. 대부분의 언어가 소수를 IEEE 754 부동소수점으로 저장하는데, 이 형식은 0.1을 정확히 담지 못한다. 이 글에서는 64비트 부동소수점의 부호·지수·가수 비트를 실제로 쪼개 보고, 0.1이 왜 2진수로 끝나지 않는지, 오차가 어디서 생기고 어떻게 쌓이는지 따라간다. 그다음 비교는 어떻게 해야 하는지, 2의 53제곱을 넘는 정수가 왜 틀어지는지, NaN과 -0이 무엇인지 보고, 돈을 정수와 decimal로 다루는 법과 반올림 방식, 합산 순서에 따른 오차까지 정리한다. 실험은 Node 22, Python 3.13, OpenJDK 21, PostgreSQL 16으로 했다. 부동소수점은 언어와 상관없이 같은 하드웨어 규칙을 따르므로 결과도 같다.

## 0.1 + 0.2를 여러 언어에 물어보면

먼저 증상부터 확인하자.

```bash
node -e 'console.log(0.1 + 0.2, (0.1 + 0.2) === 0.3)'   # 자바스크립트
python3 -c 'print(0.1 + 0.2, 0.1 + 0.2 == 0.3)'          # 파이썬
psql -c "SELECT 0.1::float8 + 0.2::float8 AS f, 0.1::numeric + 0.2::numeric AS n, (0.1::float8 + 0.2::float8) = 0.3::float8 AS f_eq"
```

```text
0.30000000000000004 false
0.30000000000000004 False
          f          |  n  | f_eq
---------------------+-----+------
 0.30000000000000004 | 0.3 | f
```

자바스크립트만의 문제가 아니다. 10진수를 그대로 저장하는 `numeric`만 0.3을 냈다. 파이썬도, PostgreSQL의 `float8`(`double precision`)도, 자바의 `double`도, C의 `double`도 같은 답을 낸다. 전부 CPU가 하드웨어로 계산하는 IEEE 754 배정밀도(64비트) 부동소수점을 쓰기 때문이다. 증상이 같으니 원인도 한곳에 있다.

## 64비트를 셋으로 나눈다

자바스크립트에서 안전한 정수 범위, BigInt, JSON의 큰 정수처럼 이 구조가 만드는 언어별 함정은 [자바스크립트 숫자](/posts/js-numbers-bigint) 글에 모았다.

IEEE 754는 1985년에 정해진 부동소수점 표준이다. 그 전에는 컴퓨터 회사마다 소수를 저장하는 방법이 달라서, 같은 프로그램이 기계마다 다른 답을 냈다. 지금은 거의 모든 CPU가 이 표준을 따른다.

부동소수점은 수를 과학적 표기법처럼 적는다. 10진수로 1234.5를 1.2345 × 10³으로 적듯이, 2진수로 1.xxxx × 2ᵉ 꼴로 적는다. 소수점이 지수에 따라 "떠다닌다"고 해서 부동(浮動)소수점이다. 64비트는 세 부분으로 나뉜다.

- 부호(sign) 1비트: 0이면 양수, 1이면 음수.
- 지수(exponent) 11비트: 2의 몇 제곱인지. 음수 지수도 적어야 해서 실제 지수에 1023을 더해 저장한다(바이어스).
- 가수(fraction, mantissa) 52비트: 1.xxxx의 소수점 아래 xxxx 부분. 맨 앞의 1은 언제나 1이라 저장하지 않고 공짜로 얻는다. 그래서 정밀도는 53비트다.

0.1을 실제로 쪼개 보자. 아래 그림에서 조각을 누르면 각 부분이 무엇을 뜻하는지 볼 수 있다.

## 오차는 더할수록 쌓인다

한 번의 오차는 10의 -17제곱 수준이라 대부분 문제가 되지 않는다. 문제는 쌓일 때다. 0.1을 열 번 더하면 1이 안 된다. 100만 번 더하면 차이가 눈에 보인다.

```bash
node -e 'let s = 0; for (let i = 0; i < 10; i++) s += 0.1; console.log(s)'
python3 -c '
s = 0.0
for _ in range(1_000_000): s += 0.1   # 하나씩 그냥 더한다
print(s)'
```

```text
0.9999999999999999
100000.00000133288
```

처음 상황의 정산 배치가 이것이다. DB에서도 `float8` 컬럼을 `SUM`하면 같은 일이 생긴다. 주문 100만 건에 0.1씩 넣고 `float8` 컬럼과 `numeric(12,2)` 컬럼을 각각 더했다.

```sql
CREATE TABLE orders (id int PRIMARY KEY, amount_f float8, amount_n numeric(12,2));
INSERT INTO orders SELECT g, 0.1, 0.1 FROM generate_series(1, 1000000) g;  -- 100만 건
SELECT sum(amount_f) AS float_sum, sum(amount_n) AS numeric_sum FROM orders;
```

```text
     float_sum     | numeric_sum
-------------------+-------------
 99999.99999938629 |   100000.00
```

`numeric`은 10진수를 그대로 저장하니 정확히 100000.00이다. `float8`은 0.0006만큼 모자란다. 애플리케이션 반복문의 오차(0.0013 초과)와 방향도 크기도 다르다. 더하는 방식이 달랐기 때문이다. 둘 다 반올림해서 보여 주면 1원 차이가 나는 것이 당연하다.

곱셈도 마찬가지다. 19.99에 100을 곱해 정수로 바꾸는 코드가 가장 흔한 사고다.

```bash
node -e 'console.log(19.99 * 100, Math.floor(19.99 * 100), Math.round(19.99 * 100))'
python3 -c 'print(19.99 * 100, int(19.99 * 100), round(19.99 * 100))'
```

```text
1998.9999999999998 1998 1999
1998.9999999999998 1998 1999
```

19.99는 진짜 값보다 조금 작게 저장되어 있어서 100을 곱하면 1998.9999…가 된다. 정수로 자르면(`Math.floor`, 파이썬 `int`, 자바의 `(int)` 캐스팅) 1998이 된다. 1센트가 사라졌다. 소수를 정수로 바꿀 때는 자르지 말고 반올림해야 하고, 더 나은 방법은 처음부터 소수를 거치지 않는 것이다. 금액은 문자열 `"19.99"`로 받아 decimal로 바로 파싱하거나, 처음부터 정수 센트로 주고받는다.

## 같은지 비교하는 법

부동소수점 값을 `==`로 비교하면 0.1 + 0.2 == 0.3처럼 수학적으로는 같은데 거짓이 나온다. 그래서 "충분히 가까우면 같다"로 비교한다. 문제는 얼마나 가까워야 하느냐다.

자바스크립트의 `Number.EPSILON`(약 2.22 × 10⁻¹⁶)은 1과 그다음 double 사이의 간격이다. 2의 -52제곱이다. 이걸 그대로 문턱으로 쓰는 코드가 많다.

```javascript
Math.abs((0.1 + 0.2) - 0.3) < Number.EPSILON   // true. 1 근처에서는 맞는다
```

하지만 double 사이의 간격은 수의 크기에 비례해서 커진다. 1 근처에서는 2.22 × 10⁻¹⁶이지만, 1만 근처에서는 약 1.8 × 10⁻¹², 10¹⁶ 근처에서는 2다. 큰 수에서 `Number.EPSILON`으로 비교하면 바로 옆 칸인 두 수도 다르다고 나오고, 아주 작은 수(10⁻²⁰ 같은)에서는 전혀 다른 두 수가 같다고 나온다. 그래서 상대 오차로 비교한다.

```javascript
function nearlyEqual(a, b, rel = 1e-9, abs = 1e-12) {
  // 두 수 중 큰 쪽에 비례한 허용치, 그리고 0 근처를 위한 절대 허용치
  return Math.abs(a - b) <= Math.max(rel * Math.max(Math.abs(a), Math.abs(b)), abs);
}
```

파이썬의 `math.isclose(a, b, rel_tol=1e-09, abs_tol=0.0)`이 정확히 이 방식이고 기본 상대 허용치도 1e-9다. 허용치는 정답이 없다. 그 값이 어떤 계산을 몇 번 거쳤는지에 따라 오차가 다르니, 도메인에 맞게 고른다. 테스트 프레임워크의 `toBeCloseTo`(Jest, 소수점 자릿수 기준)나 JUnit의 `assertEquals(expected, actual, delta)`도 같은 생각이다. 그리고 돈에는 이런 비교를 쓰지 않는다. 돈은 애초에 정확해야 하니 정확한 타입으로 바꾼다.

## 2의 53제곱 너머의 정수

가수가 53비트라는 건 정수도 2⁵³(9,007,199,254,740,992)까지만 빠짐없이 담을 수 있다는 뜻이다. 그 위로는 칸 사이 간격이 2, 4, 8로 벌어져서 홀수를 담지 못한다.

```bash
node -e 'console.log(2**53, 2**53 + 1, 9007199254740993, Number.MAX_SAFE_INTEGER, 1e16 + 1)'
python3 -c 'print(float(2**53 + 1), 2**53 + 1)'   # float로 바꾸면 틀어지고, 파이썬 int는 정확하다
```

```text
9007199254740992 9007199254740992 9007199254740992 9007199254740991 10000000000000000
9007199254740992.0 9007199254740993
```

`2**53 + 1`이 `2**53`과 같게 나온다. 소스 코드에 9007199254740993이라고 적어도 읽는 순간 ...992가 된다. `Number.MAX_SAFE_INTEGER`가 2⁵³ - 1인 이유가 이것이다. 그 이하의 정수는 모두 정확하고 서로 구별된다.

실무에서 이게 터지는 곳은 ID다. DB의 `bigint` ID나 트위터(X)의 스노플레이크 ID 같은 64비트 정수를 JSON 숫자로 보내면, 자바스크립트를 비롯해 JSON 숫자를 double로 읽는 클라이언트에서 끝자리가 바뀐다. 다른 주문을 조회하는 버그가 된다. 그래서 64비트 ID는 JSON에 문자열로 싣는다. 언어 쪽에서는 파이썬의 `int`, 자바의 `long`, 자바스크립트의 `BigInt`가 정확한 정수를 다룬다.

## 0이 둘, 자기 자신과 다른 값

IEEE 754에는 수가 아닌 값도 있다. 지수 비트가 전부 1이면 특별한 값이다. 가수가 0이면 무한대(`Infinity`, `-Infinity`), 가수가 0이 아니면 NaN(Not a Number)이다. 지수와 가수가 모두 0이면 0인데, 부호 비트가 따로 있으니 +0과 -0이 둘 다 있다.

```bash
node -e 'console.log(1/0, 1/-0, -0 === 0, Object.is(-0, 0), 0/0, NaN === NaN, Number.isNaN(0/0), Math.sqrt(-1))'
```

```text
Infinity -Infinity true false NaN false true NaN
```

-0과 0은 `===`로는 같지만 1을 나누면 다른 무한대가 나온다. 아주 작은 음수가 반올림되어 0이 되면 부호를 기억해 두는 셈이라, 극한 계산에서 방향 정보를 지킨다. 대부분의 코드에서는 신경 쓸 일이 없고, 화면에 "-0"이 찍히거나 `Object.is`로 비교할 때만 드러난다.

NaN은 자기 자신과도 같지 않다. `x !== x`가 참이면 NaN이다. 그래서 NaN 검사는 `Number.isNaN`이나 파이썬 `math.isnan`으로 한다. 더 골치 아픈 건 전파다. NaN이 한 번 생기면 그 뒤의 모든 계산 결과가 NaN이 된다. 평균을 내는 배열에 NaN 하나가 끼면 평균이 NaN이 되고, 정렬 비교 함수에 NaN이 들어가면 정렬 결과가 엉망이 된다. 0으로 나누기나 음수의 제곱근이 예외 없이 조용히 NaN을 내는 언어가 많아서, 원인 지점과 증상 지점이 멀리 떨어진다. DB에서는 PostgreSQL이 `float8`의 NaN을 허용하고 정렬 시 모든 수보다 크다고 본다. `numeric` 열에도 NaN을 넣을 수 있으니 입력 검증에서 막는다.

## 반올림에는 방법이 여러 개다

"반올림"이라는 말은 하나지만 방법은 여럿이다. 정확히 절반(2.5)일 때 어느 쪽으로 가느냐가 다르다.

```bash
python3 -c 'print(round(2.5), round(3.5), round(0.125, 2), round(2.675, 2))'
node -e 'console.log(Math.round(2.5), Math.round(-2.5), (2.5).toFixed(0), (1.005).toFixed(2))'
psql -c "SELECT round(2.5::float8) AS f25, round(3.5::float8) AS f35, round(2.5::numeric) AS n25, round(-2.5::numeric) AS nm25"
```

```text
2 4 0.12 2.67
3 -2 3 1.00
 f25 | f35 | n25 | nm25
-----+-----+-----+------
   2 |   4 |   3 |   -3
```

파이썬의 `round`와 PostgreSQL의 `float8` `round`는 절반일 때 짝수 쪽으로 간다(2.5 → 2, 3.5 → 4). 이것을 은행가 반올림(round half to even)이라고 부르고, IEEE 754의 기본 반올림 방식이기도 하다. 절반을 언제나 올리면 많이 더할수록 결과가 위로 치우치는데, 짝수 쪽으로 보내면 올림과 내림이 반반이라 치우침이 사라진다. PostgreSQL의 `numeric` `round`는 학교에서 배운 대로 0에서 멀어지는 쪽으로 간다(2.5 → 3, -2.5 → -3). 자바스크립트의 `Math.round`는 언제나 +무한대 쪽으로 가서 -2.5가 -2가 된다. 자바의 `Math.round`도 같다.

`round(2.675, 2)`가 2.68이 아니라 2.67이고 `(1.005).toFixed(2)`가 1.01이 아니라 1.00인 건 반올림 방식 문제가 아니다. 2.675와 1.005가 이미 진짜 값보다 조금 작게 저장되어 있어서 "절반"이 아니라 "절반보다 조금 작은 값"을 반올림한 것이다. 여기서도 결국 소수가 정확하지 않다는 문제로 돌아온다.

## 돈은 정수로 세거나 decimal로 다룬다

이제 처음 상황의 해법이다. 돈은 두 가지 방법 중 하나로 다룬다.

첫째, 가장 작은 단위의 정수로 센다. 원화는 원, 달러는 센트, 비트코인은 사토시 단위 정수로 저장하고 계산한다. 정수 덧셈과 뺄셈은 2⁵³(자바스크립트) 또는 2⁶³(64비트 정수) 안에서는 오차가 없다. 화면에 보여 줄 때만 소수점을 찍는다. 통화마다 최소 단위가 다르다는 점을 챙긴다. ISO 4217 기준으로 원화와 엔화는 소수점이 없고, 달러와 유로는 2자리, 바레인 디나르는 3자리다. "모든 금액에 100을 곱한다"는 가정은 통화가 늘어나는 순간 깨진다.

둘째, 10진수를 그대로 담는 decimal 타입을 쓴다. PostgreSQL의 `numeric(p, s)`, MySQL의 `DECIMAL(p, s)`, 자바의 `BigDecimal`, 파이썬의 `Decimal`, C#의 `decimal`이 있다. 0.1을 2진수 근삿값이 아니라 "1 × 10⁻¹"로 저장하니 0.1 + 0.2가 정확히 0.3이다. 대신 하드웨어가 아니라 소프트웨어로 계산하니 double보다 훨씬 느리다. 금액 계산에서는 상관없는 수준이다. DB에서 금액 컬럼 타입을 고르는 이야기는 [PostgreSQL 데이터 타입 글](/posts/postgres-data-types)에도 있다. PostgreSQL의 `money` 타입은 출력 형식이 서버 로캘(`lc_monetary`)에 따라 바뀌고 소수 자릿수도 로캘이 정해서, PostgreSQL 위키의 "Don't Do This" 문서가 쓰지 말라고 하는 타입 중 하나다.

decimal에도 함정이 있다. 자바로 확인했다.

```java
System.out.println(new BigDecimal(0.1));                                   // double에서 만들면
System.out.println(new BigDecimal("0.1").add(new BigDecimal("0.2")));      // 문자열에서 만들면
System.out.println(BigDecimal.valueOf(0.1));                                // valueOf는 double의 짧은 표기를 쓴다
System.out.println(new BigDecimal("2.0").equals(new BigDecimal("2.00"))
    + " " + new BigDecimal("2.0").compareTo(new BigDecimal("2.00")));
System.out.println(new BigDecimal("2.5").setScale(0, RoundingMode.HALF_EVEN)
    + " " + new BigDecimal("2.5").setScale(0, RoundingMode.HALF_UP));
new BigDecimal("10000").divide(new BigDecimal("3"));                        // 나누어떨어지지 않으면?
```

```text
0.1000000000000000055511151231257827021181583404541015625
0.3
0.1
false 0
2 3
Non-terminating decimal expansion; no exact representable decimal result.
```

`new BigDecimal(0.1)`은 이미 오차가 들어간 double을 그대로 옮겨 와서 소용이 없다. 문자열이나 `BigDecimal.valueOf`로 만든다. `equals`는 자릿수(scale)까지 비교해서 2.0과 2.00이 다르다고 하니 값 비교는 `compareTo`로 한다. `HashMap` 키나 `HashSet`에 `BigDecimal`을 넣으면 이 차이 때문에 같은 금액이 두 번 들어간다. 반올림 방식은 `RoundingMode`로 명시한다. 그리고 1만 원을 3으로 나누는 것처럼 끝나지 않는 나눗셈은 자릿수와 반올림 방식을 주지 않으면 예외가 난다.

## 나누고 남은 1원은 어디로

마지막 예외가 실무의 진짜 문제를 보여 준다. 1만 원을 세 명이 나눠 내면 3333.33…원이다. 원 단위로 반올림하면 3333원씩, 합이 9999원이라 1원이 사라진다. 올림하면 3334원씩, 1만 2원이라 2원이 생긴다. 정밀도가 무한한 decimal을 써도 이 문제는 그대로다. 결국 어딘가에서 끊어야 하기 때문이다.

정답은 "나머지를 누군가에게 몰아 주는 규칙"을 정하는 것이다. 몫을 내림으로 구하고, 남은 원을 앞사람부터 1원씩 더 준다. 그러면 합계가 언제나 원래 금액과 같다. 할인을 상품 여러 개에 나눠 적용하거나, 수수료를 정산 대상별로 나눌 때도 같은 방식을 쓴다. 남은 몫을 누구에게 줄지는 비즈니스 규칙(금액이 큰 항목, 첫 항목 등)으로 정해 문서에 남긴다.

## 더하는 순서가 결과를 바꾼다

부동소수점 덧셈은 결합 법칙이 성립하지 않는다. (a + b) + c와 a + (b + c)가 다를 수 있다. 큰 수에 작은 수를 더하면, 작은 수의 아랫자리가 큰 수의 53비트 밖으로 밀려나 사라지기 때문이다.

```bash
python3 -c '
s = 0.0
for x in [1e16, 1.0, -1e16]: s += x   # 큰 수에 1을 더하면 1이 사라진다
print(s)
import math; print(sum([1e16, 1.0, -1e16]), math.fsum([1e16, 1.0, -1e16]))'
```

```text
0.0
1.0 1.0
```

반복문으로 더하면 1이 사라져 0이 된다. 10¹⁶ 근처의 double 간격이 2라서 10¹⁶ + 1은 10¹⁶으로 반올림된다. 그런데 파이썬 내장 `sum`은 1을 살려 냈다. 파이썬 3.12부터 `sum`이 float을 더할 때 보정 합산(Neumaier 방식)을 쓰기 때문이다. 3.11 이하에서는 `sum`도 0.0을 낸다. `math.fsum`은 그보다 더 나아가 정확히 반올림된 합을 보장한다.

보정 합산의 원조는 카한(Kahan) 합이다. 더할 때마다 잃어버린 아랫자리를 따로 모아 두었다가 다음 덧셈에 돌려준다.

```javascript
function kahanSum(xs) {
  let sum = 0, c = 0;          // c: 지금까지 잃어버린 아랫자리
  for (const x of xs) {
    const y = x - c;           // 지난번에 잃은 만큼 보정해서 더할 값
    const t = sum + y;         // 더한다. 여기서 y의 아랫자리가 잘린다
    c = (t - sum) - y;         // 실제로 더해진 양과 더하려던 양의 차이 = 이번에 잃은 것
    sum = t;
  }
  return sum;
}
```

`(t - sum) - y`는 수학적으로는 0이지만 부동소수점에서는 잘려 나간 부분이 된다. 컴파일러가 "수학적으로 0이니 지우자"고 최적화하면 망가지므로, C에서 `-ffast-math`를 켜면 카한 합이 그냥 합으로 바뀔 수 있다. 보정 없이 오차를 줄이는 쉬운 방법도 있다. 작은 수부터 더하거나(정렬 비용이 든다), 배열을 반으로 나눠 각각 더한 뒤 합치는 쌍별 합산(pairwise summation)이다. NumPy의 `sum`이 쌍별 합산을 쓴다.

[여러 스레드로 나눠 계산](/posts/process-vs-thread)하면 이 성질이 재현성 문제로 나타난다. 스레드 수나 GPU 블록 배치가 바뀌면 더하는 순서가 바뀌고, 결과의 마지막 몇 자리가 실행마다 달라진다. 분산 집계에서 "같은 데이터인데 어제와 오늘 합계 끝자리가 다르다"는 문의가 오면 이것을 의심한다. 앞의 정산 배치에서 DB 합계와 애플리케이션 합계가 달랐던 것도 같은 이유다.

## 실무에서 고르는 기준

정리하면 고르는 기준은 이렇다. 돈, 수량, 정확히 맞아야 하는 회계 값은 정수(최소 단위)나 decimal로 다루고, DB 컬럼은 `numeric`/`DECIMAL`, 주고받을 때는 문자열이나 정수로 싣는다. 측정값, 좌표, 통계, 그래픽, 머신러닝처럼 원래 오차가 있는 값은 double을 그대로 쓰고, 비교는 상대 허용치로 한다. 64비트 정수 ID는 JSON에 문자열로 보낸다. 큰 배열을 더할 때는 보정 합산이나 쌍별 합산을 쓰고, 합계를 비교하는 테스트는 끝자리 차이를 허용한다. 그리고 소수를 정수로 바꿀 때는 자르지 말고 반올림 방식을 명시한다.

머신러닝 쪽에서는 반대 방향의 선택도 있다. 정밀도를 더 줄인 16비트 형식(`float16`, 지수 8비트를 유지한 `bfloat16`)으로 메모리와 계산량을 아낀다. 정밀도와 표현 범위를 무엇과 바꿀지는 결국 도메인이 정한다.

## 면접에서 나올 만한 질문

### 0.1 + 0.2가 0.3이 아닌 이유는 무엇인가요?

0.1과 0.2는 2진수로 끝나지 않는 소수라서 IEEE 754 double의 53비트 가수에 담을 때 반올림된 근삿값으로 저장된다. 두 근삿값을 더한 결과를 다시 반올림하면 0.3에 가장 가까운 double이 아니라 그 바로 옆 칸이 된다. 언어 문제가 아니라 하드웨어 표준의 성질이라 자바스크립트, 파이썬, 자바, PostgreSQL `float8`이 모두 같은 답을 낸다.

### IEEE 754 배정밀도는 어떻게 생겼나요?

64비트를 부호 1비트, 지수 11비트, 가수 52비트로 나눈다. 값은 (-1)^부호 × 1.가수 × 2^(지수 - 1023)이고, 앞의 1은 저장하지 않아 정밀도는 53비트, 10진수로 15~17자리다. 지수가 전부 1이면 무한대나 NaN, 전부 0이면 0과 아주 작은 비정규 수를 나타낸다.

### 부동소수점을 비교할 때는 어떻게 하나요?

`==` 대신 허용치 안에 있는지 본다. 이때 `Number.EPSILON` 같은 고정 절대값은 1 근처에서만 의미가 있고, double 간격은 수의 크기에 비례하므로 큰 수에서는 너무 엄격하고 작은 수에서는 너무 느슨하다. 두 수 중 큰 쪽에 비례한 상대 허용치에 0 근처를 위한 절대 허용치를 더해 비교하고, 파이썬 `math.isclose`가 이 방식이다. 돈처럼 정확해야 하는 값은 비교 방법이 아니라 타입을 바꾼다.

### 돈은 어떤 타입으로 다뤄야 하나요?

가장 작은 단위의 정수(원, 센트)로 세거나, PostgreSQL `numeric`, 자바 `BigDecimal` 같은 decimal 타입을 쓴다. double은 0.01조차 정확히 담지 못해 더하거나 곱할 때 오차가 쌓인다. 정수로 셀 때는 통화마다 소수 자릿수가 다르다는 점을, decimal을 쓸 때는 double에서 만들지 말고 문자열로 만들어야 한다는 점과 나눗셈에 반올림 방식을 명시해야 한다는 점을 챙긴다.

### 은행가 반올림은 무엇이고 왜 쓰나요?

정확히 절반일 때 짝수 쪽으로 보내는 반올림이다. 2.5는 2, 3.5는 4가 된다. 절반을 항상 올리면 많은 값을 반올림해 더할 때 결과가 위로 치우치는데, 짝수 쪽으로 보내면 올림과 내림이 반반이 되어 치우침이 없다. IEEE 754의 기본 방식이고 파이썬 `round`가 이렇게 동작하며, PostgreSQL `numeric`의 `round`는 0에서 멀어지는 쪽이라 DB와 애플리케이션의 반올림 결과가 다를 수 있다.

### 1만 원을 세 명이 나누면 1원은 어떻게 처리하나요?

decimal을 써도 결국 원 단위에서 끊어야 하니 정밀도 문제가 아니라 규칙 문제다. 몫을 내림으로 구하고 남은 원을 정해진 순서대로 1원씩 더 배정해서 합계가 언제나 원래 금액과 같게 만든다. 누구에게 더 줄지는 비즈니스 규칙으로 정해 두고, 그 규칙을 정산 쪽과 맞춘다.

### 2의 53제곱보다 큰 정수는 왜 문제가 되나요?

double의 가수가 53비트라서 2⁵³을 넘으면 칸 간격이 2 이상이 되어 홀수 같은 정수를 담지 못한다. 그래서 `Number.MAX_SAFE_INTEGER`가 2⁵³ - 1이다. 64비트 DB ID를 JSON 숫자로 보내면 double로 읽는 클라이언트에서 끝자리가 바뀌므로 문자열로 보낸다.

### 같은 데이터를 더했는데 실행마다 합계 끝자리가 다릅니다. 왜 그런가요?

부동소수점 덧셈은 결합 법칙이 성립하지 않아 더하는 순서가 바뀌면 결과가 달라진다. 병렬 집계는 스레드 수나 데이터 분할에 따라 순서가 바뀌니 마지막 몇 자리가 흔들린다. 정확해야 하는 값이면 decimal이나 정수로 바꾸고, 오차를 줄이려면 카한 합 같은 보정 합산이나 쌍별 합산을 쓰고, 테스트는 끝자리 차이를 허용한다.
