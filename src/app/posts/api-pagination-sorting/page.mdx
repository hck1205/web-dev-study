쇼핑몰 상품 목록에서 "낮은 가격순"을 누르고 2페이지로 넘어가면 1페이지에서 본 키보드가 또 나온다는 제보가 들어온다. 그사이 상품이 추가되거나 지워졌으면 이해가 가는데, 확인해 보니 새벽이라 상품 테이블은 그대로였다. 데이터가 하나도 안 바뀌었는데 페이지가 겹친 것이다. 원인은 페이지를 자르는 방식이 아니라 정렬에 있었다.

새 글이 끼어들 때 OFFSET이 밀리는 이유와 커서의 기본 모양은 [REST API 설계](/posts/rest-api-design)에서, 뒤 페이지로 갈수록 OFFSET이 느려지는 실행 계획은 [SQL 쿼리 고쳐 쓰기](/posts/sql-query-rewrite)에서 봤다. 이 글은 그다음 질문을 다룬다. 정렬이 흔들리지 않으려면 무엇이 필요한가, 정렬 방향이 섞이거나 NULL이 있으면 키셋 조건을 어떻게 쓰는가, 커서 안에는 무엇을 담고 어떻게 지키는가. 상품 100만 개짜리 테이블을 PostgreSQL 16에 만들어 직접 돌렸다.

```sql
CREATE TABLE products (
  id         bigint PRIMARY KEY,
  name       text    NOT NULL,
  price      int     NOT NULL,          -- 1000원 단위라 같은 값이 많다
  rating     numeric(2,1),              -- 리뷰가 없으면 NULL
  created_at timestamptz NOT NULL
);
-- 가격은 1000원부터 30만 원까지 300가지, 평점은 다섯 개 중 하나가 NULL이다
INSERT INTO products
SELECT g, 'product-' || g,
       (1 + (hashint4(g) & 2147483647) % 300) * 1000,
       CASE WHEN g % 5 = 0 THEN NULL
            ELSE round((1 + ((hashint4(g * 7) & 2147483647) % 41) / 10.0)::numeric, 1) END,
       timestamptz '2026-01-01' + (g || ' seconds')::interval * 25
FROM generate_series(1, 1000000) g;
VACUUM ANALYZE products;
```

가격이 300가지뿐이라 같은 가격의 상품이 평균 3,333개씩 있다. 실제 쇼핑몰도 9,900원, 19,900원처럼 가격이 몰린다.

SQL 표준도 PostgreSQL도 `ORDER BY`에 적은 값이 같은 행끼리의 순서는 보장하지 않는다. 실행 계획을 보면 이유가 보인다.

```sql

```

```text

 Limit (actual time=64.530..68.731 rows=20 loops=1)
   ->  Gather Merge (actual time=64.524..68.725 rows=40 loops=1)
         Workers Planned: 2
         Workers Launched: 2
         ->  Sort (actual time=62.351..62.354 rows=40 loops=3)
               Sort Key: price

               Worker 0:  Sort Method: top-N heapsort  Memory: 27kB
               Worker 1:  Sort Method: top-N heapsort  Memory: 27kB

(12 rows)
```

작업자 프로세스 셋이 테이블을 나눠 읽고(`Parallel Seq Scan`), 각자 상위 40개만 힙으로 추린 뒤(`top-N heapsort`) 합친다(`Gather Merge`). 힙 정렬은 같은 값끼리의 순서를 지키지 않고, 어느 작업자가 어느 블록을 먼저 읽을지도 그때그때 다르다. `LIMIT`이 바뀌면 힙의 크기도 바뀐다. 1페이지(상위 5개)와 2페이지(상위 10개)는 서로 다른 계산이라 동점끼리의 순서가 맞을 이유가 없다. 이 밖에도 행이 UPDATE로 다른 위치로 옮겨지거나, 통계가 바뀌어 실행 계획이 달라지면 순서가 바뀐다.

50페이지(1000행)를 연달아 받아 세어 봤다.

```bash
# 20개씩 50페이지를 OFFSET으로 받아 중복을 센다
node unstable.js
```

```text
ORDER BY price      50페이지(1000행) 받음: 중복 455행, 서로 다른 행 545개
ORDER BY price, id  50페이지(1000행) 받음: 중복 0행, 서로 다른 행 1000개
```

정렬에 `id` 하나를 덧붙이자 중복이 사라졌다. 앞 줄의 숫자는 돌릴 때마다 조금씩 달랐다(한 번은 416행). 결과가 매번 다르다는 것 자체가 순서가 정해져 있지 않다는 증거다.

## 정렬 키 끝에는 유일한 열을 붙인다

정렬 키 전체가 행 하나를 가리켜야 페이지 경계가 하나로 정해진다. 그래서 정렬 키 맨 끝에 기본 키 같은 유일한 열을 붙인다. 이걸 동점 처리 열(tie-breaker)이라고 한다. 사용자에게 보이는 정렬 옵션이 "가격순" 하나여도 SQL은 `ORDER BY price, id`다.

정렬 옵션을 클라이언트가 고르게 할 때는 받은 문자열을 SQL에 끼워 넣지 않고 허용 목록에서 꺼내 쓴다. 옵션마다 동점 처리 열이 붙은 정렬과, 그 정렬에 맞는 인덱스를 함께 정해 둔다.

```js
// sort 파라미터 → SQL 정렬. 목록에 없는 값은 400
const SORTS = {
  "price":      { orderBy: "price ASC, id ASC",   index: "products_price_id_idx" },
  "-price":     { orderBy: "price DESC, id ASC",  index: "products_price_desc_id_idx" },
  "-createdAt": { orderBy: "created_at DESC, id DESC", index: "products_created_id_idx" },
};
```

이 규칙은 OFFSET에도, 키셋(커서)에도 똑같이 필요하다. 커서 방식에서 동점 처리 열이 없으면 "가격이 1000원보다 큰 것"으로 다음 페이지를 찾게 되고, 1000원짜리 3천 개 중 첫 페이지에 못 든 나머지는 통째로 건너뛴다.

## 인덱스 순서와 테이블 순서가 다르면 OFFSET은 더 비싸다

`(price, id)` 인덱스를 만들고 50만 번째 근처 페이지를 두 방식으로 받았다. 키셋 쪽 커서는 OFFSET 499999 자리의 행 `(150000, 906589)`다.

```sql
CREATE INDEX products_price_id_idx ON products (price, id);

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, name, price FROM products ORDER BY price, id LIMIT 20 OFFSET 500000;

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, name, price FROM products
WHERE (price, id) > (150000, 906589)
ORDER BY price, id LIMIT 20;
```

OFFSET 쪽은 `rows=500020`을 읽고 버렸는데, 버퍼(8KB 페이지)를 42만 번 건드렸다. [SQL 쿼리 고쳐 쓰기](/posts/sql-query-rewrite)에서 id 순서로 90만 행을 건너뛸 때는 1만 3천 번이었다. 차이는 인덱스 순서와 테이블에 행이 놓인 순서가 얼마나 닮았느냐다. id 순서는 행이 들어간 순서와 같아서 같은 테이블 페이지를 연달아 읽는다. 가격 순서는 테이블 여기저기에 흩어져 있어서 행 하나마다 다른 페이지를 찾아간다. 가격, 평점, 이름처럼 사용자가 고르는 정렬일수록 OFFSET이 이렇게 더 비싸진다. 키셋은 정렬과 상관없이 `Index Cond`로 시작점에 바로 내려가 19번 만에 끝났다.

## 정렬 방향이 섞이면 행 비교를 못 쓴다

이번에는 "높은 가격순, 같은 가격이면 먼저 등록한 순"이다. `ORDER BY price DESC, id ASC`. 행 비교 `(price, id) < (150000, 906589)`는 두 열을 같은 방향으로 비교하니 이 정렬의 "다음"을 뜻하지 않는다. 뜻대로 풀어 쓰면 "가격이 더 낮거나, 가격이 같고 id가 더 큰 것"이다.

```sql
CREATE INDEX products_price_desc_id_idx ON products (price DESC, id ASC);

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT id, name, price FROM products
WHERE price < 150000 OR (price = 150000 AND id > 906589)
ORDER BY price DESC, id ASC LIMIT 20;
```

```text
                                                  QUERY PLAN                                                  
--------------------------------------------------------------------------------------------------------------
 Limit (actual time=261.186..261.200 rows=20 loops=1)
   Buffers: shared hit=422388 read=1928
   ->  Index Scan using products_price_desc_id_idx on products (actual time=261.185..261.196 rows=20 loops=1)
         Filter: ((price < 150000) OR ((price = 150000) AND (id > 906589)))
         Rows Removed by Filter: 502655
         Buffers: shared hit=422388 read=1928
 Planning:
   Buffers: shared hit=119 read=1
 Planning Time: 0.440 ms
 Execution Time: 261.227 ms
(10 rows)
```

방향이 맞는 인덱스를 탔는데도 261ms다. 조건이 `Index Cond`가 아니라 `Filter`에 있다. OR로 묶인 조건은 인덱스의 시작점으로 쓰지 못해서, 인덱스 맨 앞(가장 비싼 상품)부터 읽으며 50만 행을 걸러 냈다(`Rows Removed by Filter: 502655`). 고치는 방법이 두 가지 있다.

첫째, 뜻은 같지만 인덱스가 쓸 수 있는 조건을 하나 덧붙인다. "가격이 15만 원 이하"는 OR 두 갈래에 모두 참이니 결과가 바뀌지 않는다.

```sql
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT id, name, price FROM products
WHERE price <= 150000 AND (price < 150000 OR id > 906589)
ORDER BY price DESC, id ASC LIMIT 20;
```

```text
                                                QUERY PLAN                                                
----------------------------------------------------------------------------------------------------------
 Limit (actual time=5.776..5.818 rows=20 loops=1)
   Buffers: shared hit=2519 read=1
   ->  Index Scan using products_price_desc_id_idx on products (actual time=5.775..5.814 rows=20 loops=1)
         Index Cond: (price <= 150000)
         Filter: ((price < 150000) OR (id > 906589))
         Rows Removed by Filter: 2969
         Buffers: shared hit=2519 read=1
 Planning:
   Buffers: shared hit=134
 Planning Time: 0.423 ms
 Execution Time: 5.845 ms
(11 rows)
```

`Index Cond: (price <= 150000)`로 15만 원 자리로 바로 내려갔다. 남은 낭비는 같은 15만 원짜리 중 커서보다 앞에 있던 2,969행이다. 동점이 많을수록 이 낭비가 커진다.

둘째, 방향을 하나로 맞춘다. 숫자라면 `-price`로 뒤집은 식 인덱스를 만들면 두 열 모두 오름차순이 되어 행 비교를 그대로 쓸 수 있다.

```sql
CREATE INDEX products_negprice_id_idx ON products ((-price), id);

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT id, name, price FROM products
WHERE (-price, id) > (-150000, 906589)
ORDER BY -price, id LIMIT 20;
```

```text

--------------------------------------------------------------------------------------------------------

   Buffers: shared hit=16 read=3

         Index Cond: (ROW((- price), id) > ROW('-150000'::integer, 906589))
         Buffers: shared hit=16 read=3
 Planning:
   Buffers: shared hit=130 read=1
 Planning Time: 0.468 ms
 Execution Time: 0.114 ms
(9 rows)
```

0.1ms, 19버퍼다. 문자열처럼 뒤집을 수 없는 값은 첫째 방법을 쓴다. 세 쿼리가 인덱스를 어떻게 읽었는지 그림으로 보면 이렇다.

## NULL이 섞인 열로 정렬하면 행이 사라진다

"평점 높은 순"을 만들었다. 평점은 리뷰가 없는 상품이 NULL이다. 그냥 내림차순으로 정렬하면 이렇게 나온다.

```sql
SELECT id, rating FROM products ORDER BY rating DESC, id DESC LIMIT 3;
```

```text
   id    | rating
```

PostgreSQL은 NULL을 어떤 값보다 크다고 보고 정렬한다. 그래서 내림차순이면 NULL이 맨 앞(`NULLS FIRST`)에 온다. 리뷰 없는 상품이 "평점 높은 순" 맨 위에 뜨니 `NULLS LAST`를 붙였다. 그다음 키셋으로 페이지를 넘기다 평점 있는 마지막 상품(1.0점, id 48)에서 다음 페이지를 요청했다.

```sql
-- 평점 있는 상품의 끝과 NULL의 시작
SELECT id, rating FROM products ORDER BY rating DESC NULLS LAST, id DESC LIMIT 3 OFFSET 799998;
-- 그 자리를 커서로 다음 페이지를 찾는다
SELECT count(*) FROM products WHERE (rating, id) < (1.0, 48);
-- 아직 남은 행
SELECT count(*) FROM products WHERE rating IS NULL;
```

고치는 방법은 NULL을 정렬 가능한 값으로 바꾸는 것이다. 평점은 0.0보다 작을 수 없으니 NULL을 -1로 바꾼 식으로 정렬하고, 같은 식으로 인덱스를 만든다.

```sql
CREATE INDEX products_rating_sort_idx ON products ((coalesce(rating, -1)) DESC, id DESC);

EXPLAIN (ANALYZE, COSTS OFF)
SELECT id, rating FROM products
WHERE (coalesce(rating, -1), id) < (1.0, 48)
ORDER BY coalesce(rating, -1) DESC, id DESC LIMIT 3;
```

MySQL 8은 NULL을 가장 작은 값으로 보아 오름차순에서 맨 앞, 내림차순에서 맨 뒤에 두고 `NULLS LAST` 문법이 없다. DB를 옮길 때 목록 순서가 바뀌는 흔한 원인이다.

## 이전 페이지로 돌아가기

```sql
  ORDER BY price DESC, id DESC LIMIT 3
```

## 직접 짜 보는 커서 비교

메모리 캐시에 올려 둔 목록이나 여러 저장소에서 모은 결과를 앱에서 페이지로 자를 때는 SQL 대신 코드로 "커서 뒤에 오는가"를 판단해야 한다. 정렬 정의(`[["price", "desc"], ["id", "asc"]]` 같은 배열)를 받아서 `row`가 `cursor`보다 엄밀히 뒤에 오면 `true`를 돌려주는 함수를 짜 보자. 앞 열부터 비교하고, 같으면 다음 열로 넘어간다.

## 전체 개수와 페이지 번호가 꼭 필요할 때

관리자 화면처럼 "총 36,481건, 1,825페이지 중 3페이지"를 보여 줘야 하는 화면도 있다. 정확한 `COUNT(*)`가 비싼 이유는 [SQL 쿼리 고쳐 쓰기](/posts/sql-query-rewrite)에서 봤다. 대략이면 되는 곳은 통계 추정치를 쓴다.

## 목록이 이상하다는 문의가 오면

"같은 항목이 두 페이지에 나온다"는데 데이터 변경이 없었다면 정렬 키에 동점 처리 열이 있는지부터 본다. 실행 계획에 병렬 작업자나 `top-N heapsort`가 보이면 거의 확실하다. 데이터가 계속 바뀌는 목록이면 OFFSET이 밀리는 경우다.

"목록 끝까지 갔는데 항목 수가 모자란다"면 NULL이 있는 열로 키셋을 거는지, 커서에 동점 처리 열이 빠졌는지 본다. 커서를 해독해서 `k`에 정렬 키가 몇 개 들어 있는지 세어 보면 바로 보인다.

"뒤 페이지로 갈수록 느리다"는 OFFSET이다. 가격·평점처럼 테이블 순서와 다른 정렬이면 같은 깊이라도 훨씬 느리다. 실행 계획의 `rows`와 `Buffers`를 본다.

"정렬을 바꿨더니 이상한 결과가 나온다"면 앱이 이전 정렬의 커서를 그대로 붙여 보내는 경우가 많다. 서버가 커서의 정렬과 요청의 정렬을 비교해서 거절하게 만들면 이 버그가 조용히 넘어가지 않는다.

"방향이 섞인 정렬만 느리다"면 조건이 `Index Cond`가 아니라 `Filter`에 있는지 본다. OR 조건만 있으면 인덱스 시작점을 못 찾는다.

## 페이지는 정렬이 정해져야 잘린다

페이지를 자르는 방법보다 먼저 정렬이 행 하나하나의 자리를 정해야 한다. 정렬 키 끝에 유일한 열을 붙이고, 방향이 섞이면 인덱스가 쓸 수 있는 조건으로 풀고, NULL은 정렬 가능한 값으로 바꾼다. 커서에는 정렬 키 전부와 정렬 이름, 필터, 방향을 담고 서명한다. 커서와 OFFSET의 기본은 [REST API 설계](/posts/rest-api-design)와 [SQL 쿼리 고쳐 쓰기](/posts/sql-query-rewrite)에 있다.

## 면접에서 나올 만한 질문

### 데이터가 바뀌지 않았는데 OFFSET 페이지에 중복이 생기는 이유는 무엇인가요?

정렬 값이 같은 행끼리의 순서를 DB가 보장하지 않기 때문이다. 페이지마다 별개의 쿼리라서 병렬 스캔, top-N 힙 정렬, 실행 계획 변화에 따라 동점끼리의 순서가 달라진다. 정렬 키 끝에 기본 키 같은 유일한 열을 붙이면 순서가 하나로 정해져 중복이 사라진다.

### 키셋 페이지네이션에서 정렬 방향이 섞이면 어떻게 하나요?

행 비교는 모든 열을 같은 방향으로 비교하니 쓸 수 없고, "앞 열이 더 작거나, 같고 뒤 열이 더 큰" OR 조건으로 풀어 쓴다. OR 조건은 인덱스 시작점으로 못 쓰니 `price <= 값` 같은 범위 조건을 덧붙이거나, 숫자 열이면 -price 식 인덱스로 방향을 맞춰 행 비교를 쓴다. 실제로 OR만 쓴 쿼리는 261ms, 범위를 덧붙이면 5.8ms, 식 인덱스는 0.1ms였다.

### NULL이 있는 열로 키셋 페이지네이션을 하면 어떤 문제가 있나요?

NULL과의 비교는 참이 아니라 NULL이라서 WHERE를 통과하지 못하고, NULLS LAST로 정렬하면 NULL 구간이 통째로 사라진다. coalesce로 NULL을 정렬 가능한 값으로 바꾼 식으로 정렬하고 같은 식 인덱스를 만들거나, NULL 구간에서는 IS NULL 조건 쿼리로 갈아탄다. PostgreSQL은 NULL을 가장 큰 값으로, MySQL은 가장 작은 값으로 다룬다는 차이도 있다.

### 커서에는 무엇을 담나요?

경계 행의 정렬 키 값 전부(동점 처리 열 포함), 커서를 만든 정렬 이름, 필터 해시, 방향, 형식 버전을 담고 서버 비밀로 서명한다. 받은 커서는 서명과 정렬, 필터가 지금 요청과 맞는지 먼저 확인하고 다르면 400을 돌려준다. base64는 암호화가 아니니 노출되면 안 되는 값은 넣지 않는다.

### 키셋으로 이전 페이지는 어떻게 가져오나요?

현재 페이지 첫 행을 기준으로 비교 방향과 정렬 방향을 모두 뒤집어 LIMIT만큼 읽은 뒤, 결과를 다시 원래 순서로 뒤집는다. 안쪽 정렬을 뒤집지 않으면 커서 가까이가 아니라 목록 맨 처음 행들이 온다. 응답에는 첫 행으로 만든 prev 커서와 마지막 행으로 만든 next 커서를 함께 준다.

### 가격순 OFFSET이 id순 OFFSET보다 훨씬 느린 이유는 무엇인가요?

인덱스 순서와 테이블에 행이 놓인 순서가 다르기 때문이다. id 순서는 입력 순서와 같아 같은 테이블 페이지를 연달아 읽지만, 가격 순서는 행마다 다른 페이지를 찾아가야 해서 같은 50만 행을 건너뛰는 데 버퍼를 42만 번 건드렸다. 키셋은 정렬과 상관없이 시작점으로 바로 내려가니 이 차이가 없다.

### 전체 개수를 꼭 보여 줘야 하면 어떻게 하나요?

정확한 COUNT가 비싸면 pg_class.reltuples나 EXPLAIN의 rows 추정치를 쓰고 화면에 어림이라는 걸 드러낸다. 페이지 번호 이동이 필요하면 OFFSET을 쓰되 깊이에 상한을 둔다. 수백만 행을 일관되게 읽어야 하는 내보내기는 트랜잭션 하나의 서버 쪽 커서나 결과 스냅샷으로 따로 처리한다.
