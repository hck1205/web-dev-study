프론트엔드를 `http://localhost:3000`에 띄우고, 백엔드 API를 `http://localhost:8080`에 띄운 다음 `fetch("http://localhost:8080/api/me")`를 호출했다. 콘솔에 빨간 줄이 찍힌다.

```
Access to fetch at 'http://localhost:8080/api/me' from origin 'http://localhost:3000'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present
on the requested resource.
```

그런데 서버 로그를 보면 `GET /api/me 200`이 멀쩡히 찍혀 있다. 서버는 요청을 받았고 응답도 보냈다. 막힌 건 요청이 아니라 응답을 읽는 쪽이다. 나도 처음엔 이 부분이 제일 헷갈렸다. CORS를 이해하려면 이 장면에서 출발하는 게 가장 빠르다.

## 남의 응답을 읽지 못하게 하는 이유

브라우저에는 같은 출처 정책(Same-Origin Policy, SOP)이 있다. 한 출처에서 온 스크립트는 다른 출처의 응답을 읽지 못한다는 규칙이다.

이게 없으면 어떻게 되는지 생각해 보면 이유가 바로 보인다. 내가 은행 사이트에 로그인해 둔 채로 아무 블로그에 들어갔다. 그 블로그의 스크립트가 `fetch("https://bank.example.com/accounts")`를 부른다. 브라우저는 은행 쿠키를 가지고 있으니 요청에 붙여 보낼 수 있고, 은행은 내 계좌 목록을 돌려준다. 그 응답을 블로그 스크립트가 읽어서 자기 서버로 보내면 끝이다. 공격자는 내 비밀번호를 몰라도 내 권한으로 데이터를 읽어 간다.

그래서 SOP는 읽기를 막는다. 다른 출처로 요청을 보내는 것 자체는 원래 웹이 하던 일이라 막지 않는다. `<img src>`로 다른 서버의 이미지를 띄우고, `<script src>`로 CDN의 스크립트를 불러오고, `<form>`으로 다른 사이트에 POST를 보내는 건 모두 SOP 이전부터 되던 일이다. 막는 건 `fetch`나 `XMLHttpRequest`로 받은 응답을 스크립트가 들여다보는 것, 다른 출처 iframe의 DOM을 만지는 것 같은 읽기 쪽이다.

그런데 요즘은 프론트엔드와 API를 다른 출처에 두는 구성이 흔하다. 읽기를 무조건 막으면 이런 구조를 만들 수가 없다. 그래서 서버가 "이 출처는 내 응답을 읽어도 된다"고 허락할 수 있는 규칙을 만들었다. 그게 CORS(Cross-Origin Resource Sharing, 교차 출처 리소스 공유)다. CORS는 SOP를 강화하는 장치가 아니라, SOP에 구멍을 뚫는 공식 절차다.

## 응답 헤더로 허락을 받는다

허락하는 방법은 응답 헤더다. 처음 장면의 서버가 응답에 이 한 줄만 붙였으면 에러가 나지 않았다.

```
Access-Control-Allow-Origin: http://localhost:3000
```

브라우저는 요청의 `Origin`과 응답의 `Access-Control-Allow-Origin`을 비교해서 같으면 응답을 페이지 코드에 넘긴다. 값으로는 출처 하나 또는 `*`(누구나)만 쓸 수 있다. 쉼표로 여러 출처를 나열하는 건 안 된다. 여러 출처를 허락하려면 서버가 허락 목록을 들고 있다가, 요청의 `Origin`이 목록에 있을 때 그 값을 그대로 돌려줘야 한다.

여기까지가 단순 요청(simple request)의 경우다. 요청은 일단 보내고, 응답이 오면 읽어도 되는지 검사한다.

## 먼저 물어보는 요청 (preflight)

단순 요청은 SOP 이전부터 `<form>`으로도 보낼 수 있던 요청들이다. 서버들은 이미 이런 요청이 다른 사이트에서 날아올 수 있다는 걸 전제로 만들어져 있다. 그래서 일단 보내도 새로 생기는 위험이 없다.

반대로 `PUT`, `DELETE`, `Content-Type: application/json`, `Authorization` 헤더 같은 요청은 예전에는 다른 출처에서 보낼 방법이 없었다. 오래된 서버는 "이런 요청은 우리 페이지에서만 온다"고 믿고 있을 수 있다. 이런 요청을 덜컥 보내 버리면 그 믿음이 깨진다. 그래서 브라우저는 실제 요청을 보내기 전에 `OPTIONS` 메서드로 먼저 물어본다. 이걸 예비 요청, preflight라고 한다.

단순 요청이 되려면 아래 조건을 모두 만족해야 한다. 하나라도 벗어나면 preflight가 먼저 간다.

- 메서드가 `GET`, `HEAD`, `POST` 중 하나
- 직접 넣은 헤더가 `Accept`, `Accept-Language`, `Content-Language`, `Content-Type` 같은 안전 목록(CORS-safelisted) 안에 있다. `Authorization`이나 `X-Request-Id` 같은 커스텀 헤더는 하나만 있어도 탈락이다
- `Content-Type`이 `application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain` 중 하나

JSON API를 만들면 `Content-Type: application/json` 때문에 POST도 거의 항상 preflight를 거친다. 아래 그림은 글 수정 API를 `PUT`으로 부르는 경우다.

실무에서 preflight가 실패하는 가장 흔한 이유는 인증 미들웨어다. preflight에는 `Authorization`도 쿠키도 실리지 않는데, 서버가 모든 요청에 인증을 요구하면 `OPTIONS`에 401을 돌려준다. 브라우저는 preflight 응답이 2xx가 아니면 실패로 본다. CORS 처리는 인증보다 앞에 두고, `OPTIONS`는 인증 없이 통과시켜야 한다.

직접 헤더를 적기보다는 프레임워크의 CORS 설정을 쓰는 게 보통이다. Express라면 `cors` 미들웨어에 허락 목록을 넘긴다. 목록으로 넘기면 맞는 출처만 돌려주고 `Vary: Origin`도 붙여 준다.

```js
import cors from "cors";

app.use(
  cors({
    origin: ["https://app.example.com", "https://admin.example.com"],
    credentials: true,
    maxAge: 600,
  }),
);
```

## 쿠키까지 보내려면

`fetch`는 다른 출처로 요청할 때 기본으로 쿠키를 싣지 않는다. 쿠키 세션으로 로그인하는 API라면 요청 쪽에서 명시해야 한다.

```js
fetch("https://api.example.com/me", { credentials: "include" });
// XMLHttpRequest라면 xhr.withCredentials = true
```

이렇게 credentials를 포함한 요청에는 규칙이 더 엄격해진다. 응답에 `Access-Control-Allow-Credentials: true`가 있어야 하고, `Access-Control-Allow-Origin`은 `*`이면 안 되고 정확한 출처여야 한다. `Allow-Headers`, `Allow-Methods`, `Expose-Headers`의 `*`도 와일드카드가 아니라 글자 `*`로 취급된다.

`*`를 막은 이유는 앞의 은행 예시를 다시 떠올리면 된다. `*`와 쿠키를 같이 허락한다는 건 "세상 모든 사이트가 내 사용자의 쿠키로 내 응답을 읽어도 된다"는 뜻이다. SOP가 없던 것과 같아진다. 스펙은 이 조합을 아예 금지해서, 쿠키를 쓰는 API는 허락할 출처를 하나하나 고르도록 만들었다.

쿠키가 실제로 실리는지는 CORS와 별개로 쿠키 자신의 규칙도 통과해야 한다. 프론트엔드와 API가 다른 사이트(`app.foo.com`과 `api.bar.com`)라면 쿠키는 `SameSite=None; Secure`여야 하고, 그래도 서드파티 쿠키를 기본으로 막는 브라우저(사파리 등)에서는 안 실릴 수 있다. 그래서 API를 `api.example.com`처럼 같은 사이트의 하위 도메인에 두는 구성이 흔하다. 이 구성을 로컬에서도 똑같이 재현하는 방법은 [localhost 대신 내 도메인으로 개발하기](/posts/local-custom-domain)에 정리했다.

## 열어 두다가 뚫리는 경우

CORS 설정에서 생기는 보안 문제는 대부분 "일단 에러부터 없애자"에서 나온다.

가장 위험한 건 요청의 `Origin`을 검사 없이 그대로 `Access-Control-Allow-Origin`에 되돌려 주면서 `Allow-Credentials: true`를 붙이는 것이다. 브라우저가 `*`와 credentials 조합을 막아 두니 그걸 피하려고 이렇게 짜는 경우가 있다. 결과는 `*`와 credentials를 허락한 것과 똑같다. 어느 사이트든 로그인한 사용자의 응답을 읽을 수 있다.

<Callout kind="warning" title="Origin을 그대로 되돌려 주지 않는다">
쿠키를 쓰는 API에서 `res.setHeader("Access-Control-Allow-Origin", req.headers.origin)`처럼 받은 값을 그대로 돌려주면 CORS를 꺼 둔 것과 같다. 허락할 출처를 목록으로 정해 두고, 목록에 있을 때만 돌려준다.
</Callout>

목록 대신 패턴으로 검사할 때도 구멍이 잘 생긴다. `origin.endsWith("example.com")`은 `https://evilexample.com`도 통과시킨다. 정규식에서 점을 이스케이프하지 않으면 `https://appXexample.com` 같은 주소가 통과한다. 하위 도메인을 허락하려면 `.example.com`으로 끝나는지를 점까지 포함해 보고, 스킴도 함께 확인한다.

`null`을 허락 목록에 넣는 것도 위험하다. `Origin: null`은 `file://`로 연 페이지, `sandbox` 속성이 붙은 iframe, 일부 리다이렉트에서 나온다. 개발 중에 로컬 HTML 파일로 테스트하다가 `null`을 열어 두는 경우가 있는데, 공격자도 자기 페이지에 sandbox iframe을 하나 넣으면 `null` 출처를 만들 수 있다. 결국 아무나 허락한 것과 같다.

반대 방향의 실수도 있다. 공개 API처럼 쿠키 없이 누구나 읽어도 되는 데이터라면 `*`가 맞는 선택이다. 이때는 굳이 출처를 하나하나 관리할 필요가 없다. `*`가 위험한 건 credentials와 엮일 때다.

## CORS는 브라우저가 지킨다

그래서 curl이나 Postman으로 부르면 똑같은 API가 멀쩡히 응답한다. 서버에서 다른 서버를 부르는 것도 마찬가지다. 브라우저가 아니니 SOP도 CORS도 없다. "Postman에서는 되는데 브라우저에서는 안 된다"는 말이 나오면 거의 CORS 문제다.

이 사실에서 두 가지가 따라 나온다. 하나, CORS는 API를 보호하는 접근 제어가 아니다. `Access-Control-Allow-Origin`을 좁게 잡아도 curl로는 누구나 부를 수 있다. 데이터를 지키는 건 인증과 인가다. 둘, CORS가 지키는 대상은 서버가 아니라 사용자다. 사용자의 브라우저에 있는 쿠키와 사내망 접근 권한 같은 걸 다른 사이트가 빌려 쓰지 못하게 하는 장치다.

## CORS는 CSRF를 막지 못한다

CORS를 잘 설정했으니 CSRF도 막혔다고 생각하기 쉽다. 그렇지 않다.

CSRF는 다른 사이트가 사용자의 브라우저로 내 서버에 요청을 보내게 해서, 쿠키가 붙은 그 요청으로 무언가를 바꾸는 공격이다. 공격자는 응답을 읽을 필요가 없다. 송금이 실행되기만 하면 된다. 그런데 처음 장면에서 봤듯이 단순 요청은 CORS 에러가 나도 서버에서 이미 처리된다. 숨겨진 `<form>`으로 보내는 POST는 아예 CORS 검사 대상도 아니다. CORS는 읽기를 막을 뿐이라, 쓰기를 노리는 CSRF와는 겨냥하는 곳이 다르다.

다만 간접적인 효과는 있다. API가 `Content-Type: application/json`만 받고 다른 형식은 거절한다면, 다른 출처의 스크립트가 그런 요청을 만들려면 preflight를 거쳐야 하고 거기서 막힌다. 커스텀 헤더를 요구하는 방식도 같은 원리다. 하지만 서버가 `text/plain`이나 폼 형식을 실수로 받아 주는 순간 무너지는 방어라서 주된 대책으로 삼지 않는다. CSRF는 쿠키의 `SameSite`와 CSRF 토큰으로 막는다. 자세한 흐름은 [쿠키와 세션으로 로그인 유지하기](/posts/cookie-session-login)에서 다뤘다.

## 개발할 때는 프록시로 돌아간다

개발 환경에서 처음 장면을 피하는 가장 흔한 방법은 브라우저가 다른 출처로 요청할 일 자체를 없애는 것이다. 프론트엔드 개발 서버가 `/api`로 들어온 요청을 백엔드로 대신 전달하게 하면, 브라우저 입장에서는 같은 출처로만 요청한다. 개발 서버와 백엔드 사이는 서버 간 통신이라 CORS가 없다.

Next.js는 `next.config.ts`의 `rewrites`로 한다.

```ts
const nextConfig = {
  async rewrites() {
    return [{ source: "/api/:path*", destination: "http://localhost:8080/api/:path*" }];
  },
};

export default nextConfig;
```

Vite는 `server.proxy`다. `changeOrigin: true`는 백엔드로 넘길 때 `Host` 헤더를 대상 주소로 바꿔 준다. 백엔드가 호스트 이름을 확인한다면 필요하다.

```ts
export default defineConfig({
  server: {
    proxy: {
      "/api": { target: "http://localhost:8080", changeOrigin: true },
    },
  },
});
```

편하지만 대가가 있다. 개발 중에는 CORS가 한 번도 일어나지 않으니, 배포 환경에서 프론트엔드와 API의 출처가 다르면 그때 처음 CORS 에러를 만난다. 배포에서도 같은 방식(nginx나 CDN이 `/api`를 백엔드로 넘기는 구성)을 쓸 거라면 문제가 없다. 배포에서 출처가 갈린다면 개발에서도 출처를 갈라 두고 서버의 CORS 설정을 그대로 시험해 보는 편이 안전하다. 크롬을 보안 옵션을 끈 채로 띄우거나 CORS 해제 확장 프로그램을 쓰는 방법도 돌아다니는데, 문제를 숨길 뿐이고 실제 사용자 브라우저에서는 그대로 깨진다.

## 평소엔 되다가 가끔만 나는 CORS 에러

CORS 설정을 마치고 한동안 잘 쓰다가, 어느 날 특정 요청에서만 콘솔에 CORS 에러가 찍힐 때가 있다. 이럴 때 콘솔 메시지는 진짜 원인을 가린다. 브라우저 대신 curl로 `Origin` 헤더를 붙여 보내면, 브라우저가 무엇을 보고 막았는지 그대로 볼 수 있다. 아래는 Ubuntu 24.04의 nginx 1.24(`localhost:18611`)에서 nginx가 허락 헤더를 붙이게 한 구성으로 재현한 것이다.

첫 번째는 에러 응답에만 허락 헤더가 빠지는 경우다. nginx의 `add_header`는 기본으로 200, 201, 204, 206, 301, 302, 303, 304, 307, 308 응답에만 헤더를 붙인다. 4xx·5xx에는 안 붙는다.

```nginx
location /api/ {
    add_header Access-Control-Allow-Origin "https://app.example.com";
    proxy_pass http://app;
}
```

```bash
# 정상 요청
curl -s -i -H 'Origin: https://app.example.com' http://localhost:18611/api/me | grep -iE '^HTTP|^access-control'

# 본문이 너무 큰 요청 (client_max_body_size 1m 에 2MB를 보낸다)
head -c 2000000 /dev/urandom > photo.jpg
curl -s -i -H 'Origin: https://app.example.com' --data-binary @photo.jpg http://localhost:18611/api/me | grep -iE '^HTTP|^access-control'
```

```text
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.example.com
HTTP/1.1 413 Request Entity Too Large
```

두 번째 응답에는 허락 헤더가 없다. 브라우저는 응답을 페이지에 넘기지 않으니, 프론트엔드 코드는 413을 모르고 `TypeError: Failed to fetch`만 받는다. 콘솔에는 대개 "No 'Access-Control-Allow-Origin' header" 메시지가 찍힌다. 그래서 "업로드할 때만 CORS 에러가 난다", "서버가 죽을 때만 CORS 에러가 난다" 같은 신고가 들어온다. 실제 원인은 413, 500, 502다. 크롬 Network 탭의 Status 열에도 대개 `CORS error`로만 보여서, 진짜 상태 코드는 같은 요청을 curl로 보내야 확인된다. `always`를 붙이면 모든 응답에 붙는다.

```nginx
add_header Access-Control-Allow-Origin "https://app.example.com" always;
```

```text
HTTP/1.1 413 Request Entity Too Large
Access-Control-Allow-Origin: https://app.example.com
```

앱 프레임워크에서 CORS를 처리할 때도 같은 문제가 생긴다. 에러 핸들러가 CORS 미들웨어보다 먼저 응답을 끝내면 에러 응답에만 헤더가 빠진다. 에러 응답에도 헤더가 붙는지 curl로 한 번은 확인해 둔다.

두 번째는 preflight가 인증에 막히는 경우다. `Authorization` 헤더를 붙인 요청은 preflight를 거치는데, 브라우저는 preflight에 그 헤더를 싣지 않는다. 인증 미들웨어가 OPTIONS까지 검사하면 이렇게 된다.

```bash
# 브라우저가 보내는 preflight를 그대로 흉내 낸다
curl -s -i -X OPTIONS \
  -H 'Origin: https://app.example.com' \
  -H 'Access-Control-Request-Method: PATCH' \
  -H 'Access-Control-Request-Headers: authorization, content-type' \
  http://localhost:18611/api/me | grep -iE '^HTTP|^access-control|^\{'
```

```text
HTTP/1.1 401 Unauthorized
{"error":"unauthorized"}
```

preflight가 2xx가 아니면 브라우저는 본 요청을 아예 보내지 않는다. 서버 로그에는 `OPTIONS /api/me 401`만 남고 PATCH는 없다. OPTIONS는 인증 검사보다 앞에서 받아 허락 헤더와 204로 끝내도록 순서를 바꾼다.

세 번째는 앞단 캐시가 다른 출처의 허락을 저장해 버리는 경우다. 요청의 `Origin`을 보고 허락 헤더를 고르는 서버라면 응답이 출처마다 다르다. 그런데 `Vary: Origin`이 없으면 캐시는 그 응답을 출처와 상관없이 하나로 저장한다. nginx `proxy_cache`를 앞에 두고 두 출처로 번갈아 보내 봤다.

```bash
for o in https://a.example.com https://b.example.com; do
  curl -s -i -H "Origin: $o" http://localhost:18611/cached/x | grep -iE '^access-control|^x-cache'
done
```

```text
Access-Control-Allow-Origin: https://a.example.com
X-Cache-Status: MISS
Access-Control-Allow-Origin: https://a.example.com
X-Cache-Status: HIT
```

b가 받은 응답에 a의 출처가 적혀 있다. 브라우저에서 b 사이트만 CORS 에러가 나고, 캐시가 만료되면 이번엔 a가 막힌다. 배포 직후나 캐시가 비는 시간마다 어느 쪽이 깨질지 바뀌니 재현이 어렵다. 출처별로 허락 헤더를 고른다면 `Vary: Origin`을 반드시 함께 보낸다. CDN 쪽 캐시 키는 [HTTP 캐시와 CDN](/posts/http-caching-cdn)에서 다뤘다.

세 경우 모두 확인 순서는 같다. 콘솔 메시지만 믿지 말고, Network 탭에서 실패한 요청을 Copy as cURL로 꺼내 `-i`를 붙여 다시 보낸다. 상태 코드와 응답 헤더가 그대로 보인다. 어느 층에서 헤더가 빠졌는지가 보이면 고칠 곳이 정해진다.

## 다시 처음 장면으로

서버 로그에 200이 찍혔는데 콘솔이 빨갛던 이유는 이제 한 줄로 말할 수 있다. 요청은 갔지만, 서버가 `localhost:3000`이 응답을 읽어도 된다고 허락하지 않아서 브라우저가 응답을 넘겨주지 않았다. CORS는 같은 출처 정책이 막아 둔 읽기를 서버가 출처 단위로 풀어 주는 규칙이고, 그 규칙을 지키는 건 브라우저다. 쿠키가 얽히면 출처를 정확히 지정해야 하고, 쓰기를 노리는 CSRF는 따로 막아야 한다.

## 면접에서 나올 만한 질문

### CORS가 무엇이고 왜 필요한가요?

브라우저의 같은 출처 정책은 다른 출처의 응답을 스크립트가 읽지 못하게 막는다. CORS는 서버가 응답 헤더로 "이 출처는 읽어도 된다"고 허락해서 그 제한을 풀어 주는 규칙이다. 프론트엔드와 API를 다른 출처에 두는 구조가 흔해지면서, 안전하게 교차 출처 읽기를 허용할 표준 방법이 필요해서 생겼다.

### 같은 출처 정책은 왜 있나요?

브라우저가 사용자의 쿠키를 자동으로 붙이기 때문이다. 이 정책이 없으면 아무 사이트의 스크립트가 사용자가 로그인한 은행이나 메일 서비스에 요청을 보내고, 사용자 권한으로 받은 응답을 읽어 갈 수 있다. 그래서 요청을 보내는 건 허용하되 응답을 읽는 건 막는다.

### 출처가 같다는 건 정확히 무슨 뜻인가요?

스킴, 호스트, 포트가 모두 같다는 뜻이다. 경로와 쿼리는 상관없고, 포트를 안 적으면 스킴의 기본 포트로 본다. 그래서 `localhost:3000`과 `localhost:8080`은 다른 출처이고, `app.example.com`과 `api.example.com`도 다른 출처다. 다만 둘은 같은 사이트라서 SameSite 쿠키 기준으로는 같은 편이다.

### preflight는 언제 발생하고 무엇을 확인하나요?

GET·HEAD·POST가 아닌 메서드, 안전 목록 밖의 헤더(`Authorization`이나 커스텀 헤더), 폼·text/plain이 아닌 Content-Type 중 하나라도 있으면 발생한다. 브라우저가 `OPTIONS`로 출처와 쓰려는 메서드·헤더를 먼저 알리고, 서버가 Allow-Origin·Allow-Methods·Allow-Headers로 허락해야 실제 요청을 보낸다. preflight에는 인증 정보가 실리지 않으니 서버는 `OPTIONS`를 인증 없이 통과시켜야 하고, `Max-Age`로 결과를 캐시하게 해서 요청 수를 줄인다.

### 서버 로그에는 200이 찍혔는데 브라우저에서 CORS 에러가 나는 이유는요?

CORS를 검사하는 주체가 브라우저이기 때문이다. 단순 요청은 일단 서버로 가서 처리되고, 응답이 돌아온 뒤 브라우저가 허락 헤더가 없다는 걸 보고 페이지 코드에 넘기지 않는다. 같은 이유로 curl이나 서버 간 호출은 CORS와 상관없이 성공한다. 그래서 CORS는 API 접근 제어 수단이 아니다.

### credentials를 쓸 때 `Access-Control-Allow-Origin: *`을 쓸 수 없는 이유는요?

`*`와 쿠키를 함께 허락하면 모든 사이트가 로그인한 사용자 권한으로 응답을 읽을 수 있게 되어 같은 출처 정책이 의미를 잃는다. 그래서 스펙이 이 조합을 금지하고, 정확한 출처와 `Allow-Credentials: true`를 요구한다. 이걸 피하려고 요청의 Origin을 검사 없이 되돌려 주면 같은 구멍이 다시 생기므로, 허락 목록과 비교해야 한다.

### 동적으로 Allow-Origin을 정할 때 `Vary: Origin`을 붙이는 이유는요?

응답이 Origin 헤더에 따라 달라진다는 걸 캐시에 알리기 위해서다. 없으면 CDN이나 브라우저가 A 출처를 위해 만든 응답을 B 출처 요청에 재사용해서, 정상 요청이 간헐적으로 CORS 에러를 내거나 허락하지 않은 출처에 허락 헤더가 나가는 문제가 생긴다.

### CORS를 잘 설정하면 CSRF도 막히나요?

막히지 않는다. CORS는 응답을 읽는 걸 막을 뿐이고, CSRF는 응답을 읽지 않고 요청이 실행되게만 하면 된다. 폼 전송 같은 단순 요청은 CORS와 상관없이 서버에서 처리된다. JSON만 받거나 커스텀 헤더를 요구하면 preflight 때문에 부수 효과는 있지만, CSRF 대책은 SameSite 쿠키와 CSRF 토큰으로 따로 세운다.
