`CLAUDE.md`에 배포 절차 40줄과 "끝내기 전에 테스트를 돌려라"를 적어 두었다. 배포는 한 달에 몇 번 하는데 그 40줄은 매 세션 컨텍스트를 먹는다. 테스트 규칙은 대화가 길어지면 가끔 건너뛴다. 코드 리뷰를 시키면 diff와 로그가 대화에 쏟아져 정작 하던 작업의 맥락이 밀려난다.

세 문제는 해결 도구가 다르다. 가끔 쓰는 절차는 스킬로, 반드시 일어나야 하는 검사는 훅으로, 결과만 필요한 곁가지 작업은 서브에이전트로 옮긴다. 이 글은 `.claude/` 아래의 `commands/`, `skills/`, `agents/`, 훅이 각각 언제 불려서 무엇을 할 수 있는지, 그리고 한 요청 안에서 어떻게 맞물리는지를 실제 파일과 실행 결과로 본다. 파일이 어디에 놓이고 어떤 순서로 읽히는지, 권한 규칙과 `.mcp.json`은 [Claude Code 프로젝트 구조 글](/posts/claude-code-project-structure)에서 먼저 다뤘다. 컨텍스트 창이 차고 압축되는 과정은 [컨텍스트 창 글](/posts/claude-code-context-window)에 있다.

기준은 Claude Code 2.1.306(Ubuntu 24.04, bash)과 2026년 10월의 [공식 문서](https://code.claude.com/docs/en/skills)다. 훅 스크립트는 jq 1.7과 bash로 돌렸다.

## 누가 방아쇠를 당기나

네 가지 확장은 "누가 부르느냐"로 나누면 덜 헷갈린다. 스킬과 명령은 내가 `/이름`으로 부르거나, Claude가 설명을 보고 필요하다고 판단할 때 불린다. 서브에이전트는 Claude가 일을 넘길 때 생긴다. 훅은 아무도 부르지 않는다. 도구 호출 직전, 응답이 끝날 때 같은 사건이 일어나면 Claude Code가 매번 실행한다. MCP 서버의 도구는 Claude가 다른 도구처럼 부른다.

이 구분이 실무에서 중요한 이유는 "확실히 일어나느냐"가 여기서 갈리기 때문이다. 스킬과 서브에이전트는 모델의 판단을 거친다. 설명을 잘 써도 안 불릴 수 있다. 훅만이 사건이 일어날 때마다 돈다. 공식 문서도 스킬 안의 규칙을 Claude가 건너뛰면 그 규칙을 훅으로 옮기라고 안내한다.

## commands 폴더는 스킬로 합쳐졌다

구조도에 흔히 나오는 `.claude/commands/review.md`, `fix-issue.md`는 옛 형식이다. 지금 문서는 "사용자 정의 명령이 스킬로 합쳐졌다"고 적는다. `.claude/commands/deploy.md`와 `.claude/skills/deploy/SKILL.md`는 둘 다 `/deploy`를 만들고 똑같이 동작한다. 명령 파일은 계속 쓸 수 있지만 `name`, `paths` 필드를 못 쓰고 보조 파일을 둘 폴더가 없다. 새로 만든다면 스킬이 낫다.

```markdown
---
description: GitHub 이슈 번호를 받아 고친다
argument-hint: [issue-number]
disable-model-invocation: true
---

GitHub 이슈 #$ARGUMENTS 를 고친다.

1. `gh issue view $ARGUMENTS`로 이슈를 읽는다.
2. 원인을 찾고 고친다.
3. 실패하던 테스트를 먼저 추가하고 `pnpm test`로 통과를 확인한다.
```

`/fix-issue 123`을 치면 `$ARGUMENTS` 자리에 `123`이 들어간다. 인자를 나눠 받으려면 `$0`, `$1`(0부터 센다)이나 `arguments` 필드로 이름을 붙인다. 하위 폴더 `.claude/commands/frontend/component.md`는 `/frontend:component`가 된다.

이름 충돌은 미리 피한다. 같은 이름이면 명령 파일보다 스킬이, 프로젝트보다 개인(`~/.claude/skills/`)이, 개인보다 관리형이 이긴다. 내장 명령과 이름이 같으면 로컬 터미널에서는 내 스킬이 내장 명령을 대신하지만 별칭까지 가져가지는 못한다. 그런데 구조도의 `review.md`는 공교롭게도 `/review`라는 이름을 쓴다. 지금 `/review`는 내장 스킬 `/code-review`의 별칭이다. 문서는 `code-review` 스킬을 직접 만들면 `/code-review`는 바뀌지만 `/review`는 계속 내장 쪽을 부른다고 적는데, `review`라는 이름의 프로젝트 명령이 별칭과 부딪칠 때 어느 쪽이 도는지는 문서에서 찾지 못했다. `project-review`처럼 겹치지 않는 이름이 안전하다.

## SKILL.md 한 장 뜯어보기

스킬은 폴더 하나다. `SKILL.md`는 필수고, 참고 문서나 스크립트를 곁에 둘 수 있다. 데모 저장소의 배포 스킬이다.

```text
.claude/skills/deploy/
├── SKILL.md
└── scripts/
    └── deploy.sh
```

```markdown
---
name: deploy
description: 스테이징이나 프로덕션에 배포한다. 사용자가 배포를 요청할 때만 쓴다.
disable-model-invocation: true
argument-hint: [staging|production]
allowed-tools: Bash(${CLAUDE_SKILL_DIR}/scripts/deploy.sh *)
---

## 지금 브랜치

!`git branch --show-current`

## 순서

1. `pnpm test`가 통과하는지 확인한다. 실패하면 멈추고 알린다.
2. `${CLAUDE_SKILL_DIR}/scripts/deploy.sh $ARGUMENTS`를 실행한다.
3. 배포가 끝나면 헬스 체크 결과를 한 줄로 보고한다.
```

앞머리의 필드를 하나씩 보면 이렇다. 아래 조각을 눌러 보면 각 필드가 무엇을 바꾸는지 나온다.

### 설명은 늘 있고, 본문은 불릴 때 들어온다

보통 세션에서는 모든 스킬의 이름과 `description`만 컨텍스트에 올라가 있다. 본문은 내가 부르거나 Claude가 고를 때 한 번 들어와서, 그 뒤로 계속 대화에 남는다. 파일을 다시 읽지 않으니 "테스트를 돌려라"보다 "편집할 때마다 테스트를 돌린다"처럼 작업 전체에 걸리게 써야 한다. 앞머리의 두 필드가 이 흐름을 바꾼다.

- `disable-model-invocation: true`: 설명도 컨텍스트에 없고, 내가 부를 때만 본문이 들어온다. Claude가 굳이 부르려 하면 Claude Code가 막는다.
- `user-invocable: false`: 반대로 `/` 메뉴에서 숨기고 Claude만 부른다. 오래된 시스템 설명처럼 배경지식에 쓴다.

자동 압축이 일어나면 불린 스킬은 가장 최근 호출 것만, 스킬마다 앞 5,000토큰까지, 합쳐 25,000토큰 안에서 다시 붙는다. 스킬을 많이 부른 긴 세션에서는 오래된 스킬이 통째로 빠질 수 있다. 중요한 지시를 `SKILL.md` 위쪽에 두는 이유다. 아래 그림은 한 세션에서 컨텍스트에 무엇이 쌓이는지를 따라간다.

### 느낌표 명령은 Claude보다 먼저 돈다

본문의 `` !`git branch --show-current` `` 줄은 동적 컨텍스트 주입이다. Claude Code가 스킬을 렌더링할 때 이 명령을 먼저 실행하고 출력으로 줄을 바꾼 뒤에 Claude에게 넘긴다. Claude는 명령이 아니라 결과(`main` 같은 글자)를 본다. 그래서 몇 가지 규칙이 따른다.

- 명령 하나가 실패하면(0이 아닌 종료 코드) 스킬 호출 전체가 취소된다. 문제를 찾으면 1로 끝나는 검사 스크립트라면 `|| true`를 붙인다.
- 주입 명령은 렌더링 중에 묻지 않는다. 권한 규칙에 먼저 대 보고, deny에 걸리면 취소, auto 모드가 아닐 때 allow가 아니면 역시 취소다. 읽기 전용 `git` 명령은 기본으로 허용되는 집합에 들어 있어 위 예제는 그대로 돈다. 다른 명령을 쓰려면 `allowed-tools`로 미리 허용한다.
- 작업 디렉터리는 세션 셸의 현재 위치다. 스킬 폴더의 파일을 가리킬 때는 `${CLAUDE_SKILL_DIR}`, 저장소 루트는 `${CLAUDE_PROJECT_DIR}`를 쓴다.

스킬 앞머리 YAML이 깨지면 스킬은 필드 없이 로드된다. `/deploy`로는 불리지만 Claude가 설명을 못 보니 자동으로는 안 불린다. 세션 밖에서 확인할 수 있다.

```bash
# 프로젝트 스킬의 SKILL.md 앞머리 검사 (2.1.233 이상)
claude plugin validate .claude/skills
```

```text
Validating components in: …/demo/.claude/skills

√ Validation passed
```

## 서브에이전트는 따로 쓰는 작업 공간

정의는 `.claude/agents/`(프로젝트)나 `~/.claude/agents/`(개인)에 마크다운으로 쓴다. 앞머리 `name`과 `description`만 필수고, 본문이 시스템 프롬프트가 된다.

```markdown
---
name: code-reviewer
description: 코드 변경을 리뷰한다. 변경을 마친 직후 먼저 나서서 쓴다.
tools: Read, Grep, Glob, Bash
model: sonnet
---

너는 이 저장소의 코드 리뷰어다. `git diff`로 바뀐 부분만 읽는다.
버그, 빠진 에러 처리, 테스트 누락을 심각한 것부터 적는다.
파일을 고치지 않는다. 찾은 것을 파일:줄 형식으로 요약해 돌려준다.
```

문서에서 짚어 둘 동작은 이렇다.

- 시스템 프롬프트는 본문과 환경 정보뿐이다. Claude Code의 시스템 프롬프트를 받지 않는다. 대신 `CLAUDE.md` 계층과 git 상태는 받는다. 내장 Explore와 Plan만 빠르게 돌려고 이 둘을 건너뛴다. 메인 대화의 자동 메모리와 출력 스타일은 넘어가지 않는다.
- `tools`를 생략하면 쓸 수 있는 도구를 모두 물려받는다. 역할을 좁히려면 `tools`에 목록을 쓰거나 `disallowedTools`로 뺀다. 권한 모드는 `permissionMode` 필드로 따로 정할 수 있다.
- 같은 이름이면 관리형 > `--agents` 플래그 > 프로젝트 > 개인 > 플러그인 순이다. 파일 이름이 아니라 `name`으로 구분한다.
- 지금 버전은 메인 대화에서 띄운 서브에이전트가 기본으로 백그라운드에서 돈다. 서브에이전트가 또 서브에이전트를 부르는 것은 메인 아래 3단계까지고, 동시에 20개가 돌면 더 띄우지 못한다.
- 설명을 보고 Claude가 알아서 넘기지만 확실하지 않다. "use proactively" 같은 말을 넣으면 더 자주 넘긴다고 문서가 적는다. 내가 직접 "code-reviewer로 리뷰해"라고 말해도 된다.

언제 넘기지 말아야 하는지도 문서가 적어 둔다. 주고받기가 잦은 작업, 계획·구현·테스트가 맥락을 많이 공유하는 작업, 금방 끝나는 수정은 메인 대화가 낫다. 서브에이전트는 맥락을 새로 모으느라 시작이 느리다. 결과가 장황하고 요약만 필요할 때, 도구를 제한하고 싶을 때 쓴다.

## 훅은 매번 실행된다

훅은 정해진 사건에 셸 명령, HTTP 요청, MCP 도구, 프롬프트, 에이전트를 거는 기능이다. 사건은 서른 개가 넘지만 자주 쓰는 것은 몇 개다.

- `PreToolUse`: 도구 호출 직전. 막을 수 있다.
- `PostToolUse`: 도구가 성공한 뒤. 이미 실행됐으니 되돌리지는 못하고 Claude에게 피드백을 준다.
- `UserPromptSubmit`: 프롬프트가 Claude에게 가기 전. 막거나 컨텍스트를 덧붙인다.
- `Stop`: Claude가 응답을 마칠 때. 막으면 Claude가 이어서 일한다.
- `SessionStart`, `PreCompact`, `SubagentStart`처럼 세션 흐름에 걸리는 것들.

훅은 `settings.json`의 `hooks` 키에 사건 → 매처 묶음 → 핸들러 세 단계로 적는다. 스킬이나 서브에이전트의 앞머리에도 같은 모양으로 쓸 수 있다. 스크립트 파일은 어디 있어도 되고, 관례로 `.claude/hooks/`에 둔다.

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/validate-bash.sh"
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/require-tests.sh",
            "timeout": 300
          }
        ]
      }
    ]
  }
}
```

`$CLAUDE_PROJECT_DIR`는 세션을 시작한 프로젝트 루트다. Claude가 `cd`를 해도 훅이 같은 스크립트를 찾게 해 준다. 셸 형식에서는 경로를 큰따옴표로 감싼다. `"args": []`를 함께 주면 셸 없이 바로 실행하는 exec 형식이 되어 따옴표 걱정이 없어진다.

### 종료 코드가 판정이다

명령 훅은 사건 정보를 JSON으로 stdin에 받고, 종료 코드와 stdout으로 답한다.

| 종료 코드 | 뜻 | PreToolUse에서 |
|---|---|---|
| 0 | 성공. stdout이 JSON이면 그 필드를 적용한다 | 평소 권한 흐름대로 간다 |
| 2 | 막는 오류. stderr가 이유가 된다 | 도구 호출을 막고 stderr를 Claude에게 보여 준다 |
| 그 밖(1 포함) | 막지 않는 오류 | 호출은 그대로 진행되고 hook error 알림만 뜬다 |

세 번째 줄이 가장 위험하다. 유닉스 관례대로 실패를 1로 알리면 Claude Code는 막지 않는다. 정책 훅은 반드시 2로 끝내야 한다. 스크립트 경로를 틀려서 훅이 아예 못 뜰 때도 막지 않는 오류라 모든 명령이 그대로 통과한다. 2.1.295부터는 핸들러에 `"onFailure": "block"`을 주면 훅이 실패하거나 시간을 넘길 때 호출을 막는다.

종료 코드 대신 JSON으로 더 세밀하게 답할 수도 있다. `PreToolUse`는 `hookSpecificOutput.permissionDecision`에 `allow`, `deny`, `ask`, `defer`를 쓰고, `updatedInput`으로 도구 인자를 바꿔 넣을 수 있다. 다만 훅의 `allow`도 `settings.json`의 deny·ask 규칙을 이기지 못한다. 반대로 훅의 `deny`는 `bypassPermissions` 모드에서도 막는다.

### validate-bash.sh를 직접 만들어 보기

구조도에 있는 `validate-bash.sh`를 실제로 써 봤다. rm의 재귀·강제 삭제, force push, `--no-verify` 커밋, 내려받은 스크립트를 셸로 바로 넘기는 것을 막는다.

```bash
#!/usr/bin/env bash
# PreToolUse(Bash) 훅: 위험한 명령을 실행 전에 막는다.
# 입력: stdin으로 들어오는 훅 JSON. 막을 때는 stderr에 이유를 쓰고 exit 2.

if ! command -v jq >/dev/null 2>&1; then
  echo "validate-bash: jq가 없어 검사할 수 없다. 명령을 막는다." >&2
  exit 2
fi

input=$(cat)
if ! cmd=$(jq -er '.tool_input.command' <<<"$input" 2>/dev/null); then
  echo "validate-bash: 입력 JSON에서 command를 읽지 못했다." >&2
  exit 2
fi

block() {
  echo "Blocked: $1" >&2
  exit 2
}

# 명령 경계: 줄 처음, 공백, ; & | ( 뒤
b='(^|[;&|(]|[[:space:]])'

if [[ $cmd =~ ${b}rm[[:space:]]+-[a-zA-Z]*([rR][a-zA-Z]*f|f[a-zA-Z]*[rR]) ]]; then
  block "rm -rf는 쓰지 않는다. 지울 경로를 하나씩 지정하거나 사용자에게 맡긴다."
fi

if [[ $cmd =~ ${b}git[[:space:]]+push([[:space:]].*)?[[:space:]](--force|-f)([[:space:]]|$) ]]; then
  block "force push 금지. 꼭 필요하면 --force-with-lease를 쓰고 사용자에게 먼저 묻는다."
fi

if [[ $cmd =~ ${b}git[[:space:]]+commit([[:space:]].*)?[[:space:]](--no-verify|-n)([[:space:]]|$) ]]; then
  block "--no-verify로 pre-commit 훅을 건너뛰지 않는다. 훅이 실패한 원인을 고친다."
fi

if [[ $cmd =~ (curl|wget)[^|]*\|[[:space:]]*(sudo[[:space:]]+)?(ba|z)?sh([[:space:]]|$) ]]; then
  block "내려받은 스크립트를 바로 셸에 넘기지 않는다. 파일로 받아 내용을 먼저 보여 준다."
fi

exit 0
```

jq가 없거나 입력을 못 읽으면 2로 끝낸다. 검사를 못 하면 막는 쪽(fail closed)을 고른 것이다. 반대로 하면 jq가 빠진 새 컴퓨터에서 훅이 조용히 모든 것을 통과시킨다. 그리고 실행 권한이 있어야 Claude Code가 띄울 수 있다.

```bash
# 실행 권한을 주고, 문서가 권하는 방식으로 샘플 JSON을 넣어 본다
chmod +x .claude/hooks/validate-bash.sh
echo '{"tool_name":"Bash","tool_input":{"command":"git push --force origin main"}}' \
  | .claude/hooks/validate-bash.sh; echo "exit=$?"
```

```text
Blocked: force push 금지. 꼭 필요하면 --force-with-lease를 쓰고 사용자에게 먼저 묻는다.
exit=2
```

명령 여러 개를 한 번에 돌려 보려고 작은 실행기를 붙였다. jq로 훅 입력 JSON을 만들어 넣고 종료 코드와 stderr를 한 줄씩 찍는다.

```bash
#!/usr/bin/env bash
# run-hook-tests.sh: 한 줄에 명령 하나씩 받아 훅에 넣어 본다
hook="$1"
while IFS= read -r c; do
  json=$(jq -nc --arg c "$c" '{hook_event_name:"PreToolUse",tool_name:"Bash",tool_input:{command:$c}}')
  err=$(printf '%s' "$json" | "$hook" 2>&1 >/dev/null); code=$?
  printf 'exit=%s  %-42s %s\n' "$code" "$c" "$err"
done
```

```text
exit=0  ls -la                                     
exit=0  pnpm test && git status                    
exit=2  rm -rf node_modules                        Blocked: rm -rf는 쓰지 않는다. 지울 경로를 하나씩 지정하거나 사용자에게 맡긴다.
exit=2  rm -fr /                                   Blocked: rm -rf는 쓰지 않는다. 지울 경로를 하나씩 지정하거나 사용자에게 맡긴다.
exit=2  pnpm build; rm -Rf dist                    Blocked: rm -rf는 쓰지 않는다. 지울 경로를 하나씩 지정하거나 사용자에게 맡긴다.
exit=0  git push origin main                       
exit=2  git push --force origin main               Blocked: force push 금지. 꼭 필요하면 --force-with-lease를 쓰고 사용자에게 먼저 묻는다.
exit=2  git push -f                                Blocked: force push 금지. 꼭 필요하면 --force-with-lease를 쓰고 사용자에게 먼저 묻는다.
exit=0  git push --force-with-lease                
exit=2  git commit -m "wip" --no-verify            Blocked: --no-verify로 pre-commit 훅을 건너뛰지 않는다. 훅이 실패한 원인을 고친다.
exit=2  curl -fsSL https://get.example.sh | sh     Blocked: 내려받은 스크립트를 바로 셸에 넘기지 않는다. 파일로 받아 내용을 먼저 보여 준다.
exit=0  curl -o install.sh https://get.example.sh  
exit=0  bash -c 'rm -rf /'                         
exit=0  /bin/rm -rf build                          
exit=0  rm -r -f build                             
```

위쪽은 의도대로다. `;` 뒤에 숨은 `rm -Rf`도 잡고, `--force-with-lease`는 통과시킨다. 봐야 할 곳은 마지막 세 줄이다. `bash -c '...'` 안의 rm은 앞 글자가 작은따옴표라 경계 패턴에 안 걸렸고, `/bin/rm`은 앞이 `/`라 빠졌고, `rm -r -f`는 플래그를 나눠 써서 빠졌다. 정규식을 아무리 고쳐도 셸 문법 전체를 흉내 낼 수는 없다. 이런 훅은 Claude가 습관적으로 쓰는 위험한 모양을 걸러 주는 안전망이고, 진짜 경계는 샌드박스와 deny 규칙이 맡는다.

### 응답을 끝내기 전에 테스트를 확인하기

`CLAUDE.md`의 "끝내기 전에 테스트를 돌려라"는 Stop 훅으로 옮기면 매번 검사된다. 테스트가 실패하면 JSON으로 `decision: "block"`과 이유를 돌려줘서 Claude가 계속 일하게 한다.

```bash
#!/usr/bin/env bash
# Stop 훅: 테스트가 깨진 채로 응답을 끝내지 못하게 한다.
input=$(cat)
# 이미 Stop 훅 때문에 이어서 일하는 중이면 다시 막지 않는다 (무한 반복 방지)
if [[ $(jq -r '.stop_hook_active' <<<"$input") == "true" ]]; then
  exit 0
fi
if out=$(${TEST_CMD:-pnpm test} 2>&1); then
  exit 0
fi
jq -n --arg tail "$(tail -n 5 <<<"$out")" \
  '{decision: "block", reason: ("테스트가 실패한다. 고친 뒤에 끝낸다.\n" + $tail)}'
```

데모에는 테스트가 없어서, `TEST_CMD` 자리에 실패 메시지를 찍고 1로 끝나는 가짜 스크립트를 넣어 돌렸다.

```text
--- 테스트 실패, stop_hook_active=false
{
  "decision": "block",
  "reason": "테스트가 실패한다. 고친 뒤에 끝낸다.\nFAIL src/cart.test.ts > total() 할인 적용\nTests  1 failed | 23 passed"
}
exit=0
--- 테스트 실패, stop_hook_active=true
exit=0
--- 테스트 통과
exit=0
```

JSON으로 판정할 때는 0으로 끝낸다. 2로 끝내도 막기는 하지만, 그때는 JSON 필드가 판정을 바꾸지 못한다. `stop_hook_active` 검사도 빼면 안 된다. 고칠 수 없는 실패면 Claude가 끝없이 되돌아온다. Claude Code도 연속 8번 이어 붙이면 강제로 끝내는 상한을 두지만, 그때까지도 시간과 토큰이 든다. Stop은 작업이 끝날 때가 아니라 응답이 끝날 때마다 불린다. 질문에 한 줄 답할 때도 테스트가 돈다.

### 매처는 문자에 따라 다르게 읽힌다

`matcher`는 쓴 글자에 따라 해석이 달라진다. 비어 있거나 `*`면 전부, 영문·숫자·`_`·`-`·공백·`,`·`|`만 있으면 정확히 같은 이름(목록은 `|`나 `,`로), 그 밖의 글자가 하나라도 있으면 앞뒤가 고정되지 않은 JavaScript 정규식이다. 대소문자도 구분한다. 아래에서 직접 구현해 보면 `Edit.*`가 `NotebookEdit`에도 맞는 이유가 보인다.

마지막 테스트가 함정이다. 권한 규칙에서 `mcp__github`는 그 서버의 모든 도구를 뜻하지만, 훅 매처에서는 글자가 정확히 같아야 하는 이름이라 아무 도구에도 안 맞는다. 훅에서 서버 전체를 잡으려면 `mcp__github__.*`처럼 정규식으로 쓴다.

## 한 요청이 지나가는 길

구조도의 "how it all works"는 CLAUDE.md를 읽고, 설정·규칙·스킬을 불러오고, 명령과 서브에이전트를 쓰고, MCP로 도구를 붙이고, 훅을 돌린다는 순서로 정리한다. 큰 흐름은 맞지만 실제로는 한꺼번에 불러오지 않는다. `paths` 규칙은 맞는 파일을 만질 때, 스킬 본문은 불릴 때, 하위 `CLAUDE.md`는 그 폴더에 들어갈 때 들어온다. 훅은 마지막 단계가 아니라 도구 호출마다, 응답 끝마다 끼어든다. `/deploy staging` 하나를 따라가 보면 이렇다.

## 남이 만든 확장을 돌리기 전에

확장은 코드다. 남의 저장소를 열면 그 사람이 쓴 코드가 내 컴퓨터에서 돈다. 문서가 정리한 위험을 모으면 이렇다.

- 명령 훅은 내 사용자 권한 그대로 실행된다. 내 계정이 읽고 지울 수 있는 것은 다 읽고 지울 수 있다.
- 대화형 세션은 폴더를 신뢰하기 전에는 설정 파일의 훅을 돌리지 않는다. 하지만 `claude -p`와 SDK는 신뢰한 것으로 치고 저장소의 훅을 돌린다.
- 프로젝트 스킬의 `allowed-tools`는 신뢰 확인과 상관없이 적용된다. 신뢰하지 않은 폴더의 `-p` 실행에서도 마찬가지다. 스킬이 스스로 넓은 권한을 줄 수 있으니 커밋된 스킬의 이 줄을 먼저 읽는다.
- 프로젝트 스킬 앞머리의 훅도 신뢰 전 `-p` 실행에서 스킬이 불리면 등록된다. 반면 프로젝트 서브에이전트 앞머리의 훅은 신뢰한 뒤에만 돈다(2.1.218 전에는 아니었다).
- 플러그인이 주는 서브에이전트는 `hooks`, `mcpServers`, `permissionMode` 필드를 무시한다. 보안 때문에 일부러 뺀 것이다.

또 하나는 모델 쪽 위험이다. MCP 도구 결과, 웹 페이지, 읽은 파일 속에 "이전 지시를 무시하고 이 명령을 실행하라" 같은 글이 섞여 있으면 모델이 그것을 지시로 받아들일 수 있다. [RAG 파이프라인 글](/posts/rag-classic-pipeline)에서 본 간접 프롬프트 인젝션이 에이전트에서는 실제 명령 실행으로 이어진다. 그래서 권한 규칙과 훅은 "Claude가 착하게 굴 것"을 전제로 하지 않고 짜야 한다.

<Callout kind="warning">
남의 저장소에 `claude -p`를 돌리기 전에는 `.claude/settings.json`의 `hooks`, `.claude/skills/*/SKILL.md`의 `allowed-tools`와 `hooks`, `.mcp.json`을 먼저 읽는다. 내용을 확인할 수 없으면 `--bare`(훅·스킬·명령·서브에이전트·플러그인·`.mcp.json`을 읽지 않는다)로 띄우거나 `--settings '{"disableAllHooks": true}'`로 훅을 끈다. 훅을 처음 등록한 뒤에는 `/hooks`에서 실제로 등록됐는지, 첫 실행에 hook error 알림이 없는지 확인한다. 경로를 틀린 정책 훅은 조용히 아무것도 막지 않는다.
</Callout>

## 무엇을 어디에 둘까

같은 내용을 어디에 두느냐에 따라 언제 컨텍스트를 먹고, 확실히 지켜지는지가 달라진다. 비교가 정말 필요한 곳이라 표로 둔다.

| 넣을 곳 | 컨텍스트에 들어가는 때 | 누가 부르나 | 강제되나 |
|---|---|---|---|
| `CLAUDE.md` | 매 세션 시작 | 자동 | 아니다 |
| `.claude/rules/` + `paths` | 맞는 파일을 만질 때 | 자동 | 아니다 |
| 스킬 | 설명은 항상, 본문은 불릴 때 | 나 또는 Claude | 아니다 |
| 서브에이전트 | 메인에는 요약만 | Claude(내가 요청 가능) | 도구 목록은 강제된다 |
| 훅 | 출력이나 막은 이유만 | 사건 | 그렇다 |
| 권한 규칙 | 들어가지 않는다 | 클라이언트 | 그렇다 |

판단 기준을 말로 하면 이렇다. 매번 필요한 짧은 사실은 `CLAUDE.md`, 특정 파일에만 필요한 규칙은 rules, 가끔 쓰는 긴 절차는 스킬, 결과만 필요한 무거운 조사는 서브에이전트, 어기면 안 되는 검사는 훅과 권한 규칙이다. 스킬이 두 군데 이상의 프로젝트에서 반복되면 `~/.claude/skills/`로 올리거나 플러그인으로 묶는다.

## 면접에서 나올 만한 질문

### 스킬과 슬래시 명령은 어떻게 다른가?

지금은 같은 기능이다. `.claude/commands/x.md`와 `.claude/skills/x/SKILL.md`는 둘 다 `/x`를 만들고, 명령 파일은 옛 형식으로 계속 동작한다. 스킬은 보조 파일을 둘 폴더, `name`과 `paths` 필드, Claude가 설명을 보고 자동으로 부르는 기능이 더 있어서 새로 만들 때는 스킬을 쓴다.

### 스킬은 언제 컨텍스트에 들어가나?

기본으로는 이름과 설명만 항상 들어가 있고, 본문은 내가 부르거나 Claude가 고를 때 들어와 대화에 남는다. `disable-model-invocation: true`면 설명도 빠지고 내가 부를 때만 들어온다. 자동 압축 뒤에는 최근 호출의 앞 5,000토큰씩, 합쳐 25,000토큰 안에서만 다시 붙어서 중요한 지시는 위에 둔다.

### 서브에이전트를 쓰는 이유는? 단점은?

곁가지 작업의 긴 출력이 메인 컨텍스트를 채우지 않게 하려고 쓴다. 서브에이전트는 자기 컨텍스트에서 읽고 돌린 뒤 요약만 돌려주고, `tools`로 역할을 강제할 수 있다. 대신 대화 이력을 모른 채 새로 시작해 맥락을 다시 모으느라 느리고, 주고받기가 잦은 작업에는 맞지 않는다.

### 서브에이전트는 메인 대화의 무엇을 물려받나?

대화 이력은 받지 않고 Claude가 쓴 위임 메시지로 시작한다. `CLAUDE.md` 계층과 git 상태는 받지만 Claude Code의 시스템 프롬프트, 자동 메모리, 출력 스타일은 받지 않는다. 내장 Explore와 Plan은 가볍게 돌려고 `CLAUDE.md`와 git 상태도 건너뛴다.

### PreToolUse 훅에서 막으려면 exit 1이면 되나?

안 된다. 막는 종료 코드는 2이고, 1을 포함한 다른 코드는 막지 않는 오류라 도구 호출이 그대로 진행된다. 스크립트 경로를 틀려 훅이 못 떠도 같아서 정책 훅은 첫 실행을 확인하고, 2.1.295 이상이면 `onFailure: "block"`을 준다.

### 훅의 allow는 권한 규칙을 우회하나?

못 한다. 훅이 `permissionDecision: "allow"`를 돌려줘도 설정의 deny와 ask 규칙은 그대로 평가된다. 반대로 훅의 `deny`나 exit 2는 allow 규칙보다 먼저 막고 `bypassPermissions` 모드에서도 유효하다. 그래서 훅은 권한을 좁히는 데는 쓸 수 있지만 넓히는 데는 한계가 있다.

### Bash 명령을 검사하는 훅만 있으면 위험한 명령을 다 막을 수 있나?

아니다. 정규식 검사는 `bash -c '...'`, `/bin/rm`, 플래그를 나눠 쓴 `rm -r -f`처럼 모양이 다른 명령을 놓친다. 실제로 만든 훅도 이 셋을 통과시켰다. 훅은 흔한 실수를 거르는 안전망으로 두고, 꼭 지켜야 하는 경계는 샌드박스와 deny 규칙, 최소한의 도구 허용으로 만든다.

### 남의 저장소에서 Claude Code를 돌릴 때 확장 쪽 위험은?

훅은 내 권한으로 셸 명령을 실행하고, `claude -p`는 신뢰 확인 없이 저장소 설정의 훅을 돌린다. 프로젝트 스킬의 `allowed-tools`는 신뢰와 상관없이 적용된다. 먼저 `.claude/`와 `.mcp.json`을 읽고, 확인할 수 없으면 `--bare`나 `disableAllHooks`로 띄우며, 도구 결과에 섞인 프롬프트 인젝션까지 전제하고 권한을 좁힌다.
