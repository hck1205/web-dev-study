## 반경 500m 식당을 테이블 하나로 찾으면

가장 단순한 버전은 가게마다 위도와 경도를 적은 테이블 하나다. 위도(latitude)는 적도에서 남북으로 얼마나 떨어졌는지, 경도(longitude)는 기준 자오선에서 동서로 얼마나 떨어졌는지를 나타내는 각도다.

```sql
-- 가게 테이블: 이름과 좌표만 둔다
CREATE TABLE businesses (
  id   bigint PRIMARY KEY,
  name text NOT NULL,
  lat  double precision NOT NULL,
  lng  double precision NOT NULL
);

-- 내 위치(37.4979, 127.0276) 주변을 위도·경도 범위로 자른다
SELECT id, name
FROM businesses
WHERE lat BETWEEN 37.4979 - 0.00449 AND 37.4979 + 0.00449
  AND lng BETWEEN 127.0276 - 0.00566 AND 127.0276 + 0.00566;
```

0.00449도와 0.00566도는 500m를 각도로 바꾼 값이다. 위도 1도는 어디서나 약 111km지만, 경도 1도는 북쪽으로 갈수록 짧아진다. 서울 위도에서는 약 88km라서 같은 500m가 경도로는 더 큰 각도가 된다. 이 쿼리는 원이 아니라 네모를 자르니, 마지막에 실제 거리로 한 번 더 걸러야 한다.

가게가 몇천 곳이면 이걸로 충분하다. 문제는 가게가 늘어날 때 생긴다.

## 위도 인덱스와 경도 인덱스는 따로 논다

인덱스는 값을 정렬해 둔 목차다. `lat`에 인덱스를 걸면 "위도가 이 범위인 행"은 빨리 찾는다. 그런데 그 행들은 지구를 가로로 한 바퀴 두른 띠 전체다. `lng` 인덱스도 마찬가지로 세로 띠를 준다. 둘 다 걸어도 DB는 띠 두 개를 각각 읽고 겹치는 부분을 찾아야 한다. 서울 크기 상자에 가게 20만 곳을 무작위로 뿌리고, 각 띠에 몇 곳이 걸리는지 세 봤다.

```js
// prox1.js: 위도 인덱스, 경도 인덱스를 따로 걸면 각각 얼마나 넓은 띠를 읽나
const N = 200_000;                                   // 서울 상자 안 가게 20만 곳
const biz = Array.from({ length: N }, (_, i) => ({ id: i + 1, lat: 37.43 + rand() * 0.27, lng: 126.80 + rand() * 0.38 }));
const me = { lat: 37.4979, lng: 127.0276 }, R = 500; // 강남역 근처, 반경 500m
const dLat = R / 111320, dLng = R / (111320 * Math.cos(me.lat * Math.PI / 180));
const latBand = biz.filter((b) => Math.abs(b.lat - me.lat) <= dLat);
const lngBand = biz.filter((b) => Math.abs(b.lng - me.lng) <= dLng);
const box = latBand.filter((b) => Math.abs(b.lng - me.lng) <= dLng);
const circle = box.filter((b) => haversine(me.lat, me.lng, b.lat, b.lng) <= R);
```

```text
dLat=0.00449°  dLng=0.00566°
latitude band rows : 6611
longitude band rows: 6018
both (box)         : 189
inside 500m circle : 149
```

원 안에 든 가게는 149곳인데, 한쪽 인덱스만 쓰면 6천 곳 넘게 읽는다. 40배를 더 읽는 셈이다. 가게가 2억 곳인 전 세계 서비스라면 띠 하나가 수십만 행이 된다. B-tree 같은 보통의 인덱스는 한 줄로 늘어선 값에 강하다. 2차원 범위는 그대로는 못 다룬다.

그래서 2차원 좌표를 1차원 값으로 접는 공간 색인을 쓴다. 지도를 칸으로 나누고 칸마다 번호를 붙이면, "이 칸에 든 가게"는 번호 하나로 찾을 수 있다. 칸을 어떻게 나누느냐에 따라 지오해시, 쿼드트리, S2 같은 이름이 붙는다.

## 요구 사항과 숫자부터

설계하기 전에 범위를 정한다. 이 글에서 정한 가상의 서비스는 이렇다.

- 위치와 반경(기본 500m, 최대 20km)을 주면 그 안의 가게를 가까운 순으로 준다.
- 가게 상세(이름, 주소, 사진, 영업시간)를 볼 수 있다.
- 사장님은 가게를 등록·수정·삭제한다. 바뀐 내용은 다음 날 검색에 반영돼도 된다.
- 하루 사용자(DAU) 2,000만 명, 한 명이 하루 6번 검색, 가게 500만 곳.

마지막 줄로 부하를 어림한다. 하루 검색은 2,000만 × 6 = 1억 2,000만 번이다. 하루는 86,400초니까 평균 약 1,389 QPS(초당 요청 수)다. 점심·저녁에 몰리는 걸 평균의 3배로 잡으면 약 4,167 QPS다. 쓰기는 사장님이 가게 정보를 고칠 때뿐이라 읽기에 비하면 거의 없다. 이 서비스는 읽기가 압도적으로 많은 서비스다.

아래에서 직접 계산해 볼 수 있다. 세 번째 값은 칸 색인 테이블의 크기다. 행 하나가 칸 번호와 가게 ID라서 40바이트 정도로 잡는다.

가게 CRUD는 평범하다. `GET /v1/businesses/:id`로 상세를 읽고, `POST`, `PUT`, `DELETE`로 사장님이 고친다. 응답에는 상세 정보 전체가 아니라 목록에 필요한 이름, 거리, 대표 사진 정도만 담는다. 사용자가 하나를 누르면 그때 상세를 부른다.

두 API는 성격이 정반대라서 서비스를 나눈다. 검색을 맡는 쪽을 위치 기반 서비스(LBS, Location-Based Service)라고 부른다. LBS는 쓰기가 없고, 요청마다 독립적이다. 서버가 요청 사이에 기억하는 상태가 없다는 뜻에서 무상태(stateless)라고 한다. 무상태 서버는 붐비면 대수만 늘리면 된다. 이 성질은 [③ 로드 밸런서와 무상태 웹 계층](/posts/sd-load-balancer-stateless)에서 봤다. 가게 서비스는 읽기도 있지만 쓰기를 받는 유일한 곳이다.

DB는 주 DB 하나와 복제본 여럿으로 둔다. 쓰기는 주 DB가 받고, 읽기는 복제본들이 나눠 받는다. 복제본은 주 DB를 몇십 밀리초에서 몇 초 늦게 따라온다. 그 사이 검색에는 옛 영업시간이 보일 수 있다. 다음 날 반영해도 된다고 정했으니 이 늦음은 문제가 안 된다. 복제의 기본은 [④ DB 복제 입문](/posts/sd-db-replication-intro)에 있다.

DB 종류는 관계형으로 충분하다. 가게 정보는 구조가 정해져 있고, 읽기가 많으며, 복제본으로 읽기를 늘리는 방법이 잘 알려져 있다. PostgreSQL이라면 PostGIS 확장의 GiST 색인처럼 공간 색인을 DB 안에서 바로 쓰는 길도 있다.

## 칸 색인은 무엇으로 고를까

공간 색인 후보는 크게 셋이다. 내부 동작은 각 글에 미루고, 이 서비스 관점에서 무엇이 다른지만 본다.

[지오해시](/posts/geohash)는 지도를 반씩 접어 칸마다 문자열 번호를 붙인다. 번호가 그냥 문자열이라 보통의 B-tree 인덱스나 Redis 키로 바로 쓸 수 있다. 가게 하나를 고치면 그 가게의 행 하나만 바뀐다. 대신 칸 크기가 글자 수로 고정돼 있어서, 강남처럼 붐비는 칸과 시골의 텅 빈 칸이 같은 크기다.

[쿼드트리](/posts/quadtree)는 꽉 찬 칸만 넷으로 쪼갠다. 붐비는 곳은 칸이 작고 한적한 곳은 크다. "가장 가까운 10곳"처럼 개수로 묻는 질문에 잘 맞는다. 보통 서버 메모리에 트리를 올려 두는데, 서버가 뜰 때 가게 전체를 읽어 트리를 만드는 시간이 걸린다. 가게 수가 억 단위면 몇 분이 걸릴 수 있어서, 배포할 때 서버를 한꺼번에 내리면 검색이 멈춘다. 일부씩 바꿔 끼워야 한다.

S2는 구를 정육면체에 감싸 펼친 뒤 힐베르트 곡선으로 칸에 번호를 붙인다. 칸 크기를 여러 단계로 섞어 임의 모양의 구역을 덮을 수 있어서, 배달 구역처럼 다각형 구역을 다루는 지오펜스(가상의 울타리)에 강하다. 다만 직접 구현하기는 어렵고 라이브러리에 기댄다. S2와 H3의 차이는 지오해시 글의 마지막 부분에서 다뤘다.

반경 검색이 주 기능이고 가게 정보가 하루 한 번 바뀌는 이 서비스에는 지오해시가 무난하다. 구현이 쉽고, 칸 번호를 캐시 키로 쓰기 좋다. 이 글은 지오해시로 간다. 붐비는 정도가 지역마다 크게 다르고 "가까운 k곳"이 주 질문이라면 쿼드트리 쪽으로 기운다.

## 아홉 칸에서 후보를 모아 거리로 거른다

같은 일을 가게 20만 곳에 실제로 돌려 봤다. `encode`, `neighbors`, `haversine`은 지오해시 글의 방식대로 직접 짠 작은 함수다. 하버사인(haversine) 공식은 지구를 구로 보고 두 좌표 사이의 대원 거리를 구한다.

```js
// prox2.js 일부: 지오해시 칸 + 이웃 8칸으로 반경 검색하기
const LEN = 6, index = new Map();            // 색인: 칸 번호 → 그 칸의 가게들
for (const b of biz) { const h = encode(b.lat, b.lng, LEN); if (!index.has(h)) index.set(h, []); index.get(h).push(b); }

const myCell = encode(me.lat, me.lng, LEN);
const own = (index.get(myCell) || []).filter((b) => haversine(me.lat, me.lng, b.lat, b.lng) <= R);
let candidates = [];
for (const c of neighbors(myCell)) candidates = candidates.concat(index.get(c) || []);
const hits = candidates
  .map((b) => ({ ...b, d: haversine(me.lat, me.lng, b.lat, b.lng) }))
  .filter((b) => b.d <= R)
  .sort((a, b) => a.d - b.d);
const brute = biz.filter((b) => haversine(me.lat, me.lng, b.lat, b.lng) <= R).length;  // 정답 확인용
```

## 칸 길이는 반경으로 정한다

위 결과에서 6글자 칸은 서울 위도에서 가로 약 969m, 세로 약 611m였다. 9칸이 반경을 빠짐없이 덮으려면, 내가 칸 어디에 있든 원이 이웃 칸 너머로 나가지 않아야 한다. 원은 내 칸 경계에서 최대 반경만큼 넘친다. 그러니 칸의 짧은 변이 반경보다 길면 이웃 한 줄 안에 원이 다 들어간다. 611m는 500m보다 기니 6글자면 된다.

반경이 2km면 6글자 칸으로는 이웃 한 줄을 넘어간다. 한 글자 줄여 5글자로 가면 칸이 대략 가로 3.9km, 세로 4.9km가 된다. 짧은 변이 2km보다 기니 다시 9칸으로 덮인다. 그래서 서버는 반경별 글자 수 표를 들고 있다가 요청의 반경으로 길이를 고른다. 칸 크기를 글자 수별로 정리한 표는 지오해시 글에 있다.

길이를 하나만 쓰면 안 되니 색인 테이블에는 같은 가게를 길이별로 여러 행 넣거나, 가장 긴 6글자만 저장하고 짧은 칸은 접두사로 찾는다. 지오해시는 짧은 칸의 번호가 긴 칸의 접두사라서 `geohash LIKE 'wydm6%'`처럼 B-tree로 찾을 수 있다.

```sql
-- 칸 색인 테이블: 가게 하나가 한 행. 칸과 가게 ID를 묶어 기본 키로 쓴다
CREATE TABLE geo_index (
  geohash     varchar(6) NOT NULL,
  business_id bigint     NOT NULL,
  PRIMARY KEY (geohash, business_id)
);

-- 6글자 칸 9개를 한 번에 읽는다
SELECT business_id FROM geo_index
WHERE geohash IN ('wydm67','wydm6e','wydm6g','wydm66','wydm6d','wydm6f','wydm63','wydm69','wydm6c');

-- 반경이 커서 5글자 칸을 쓸 땐 접두사로 읽는다. varchar_pattern_ops 색인이나 C 콜레이션이어야 B-tree를 탄다
SELECT business_id FROM geo_index WHERE geohash LIKE 'wydm6%';
```

칸 하나에 가게 ID 목록을 배열로 한 행에 담는 방식도 떠올릴 수 있다. 그러면 가게 하나를 추가할 때 그 칸의 긴 배열 전체를 고쳐 써야 하고, 같은 칸에 동시에 쓰면 잠금을 기다린다. 가게 하나를 한 행으로 두면 추가와 삭제가 행 하나로 끝난다.

## 색인 테이블은 작아서 나누지 않는다

데이터가 커지면 샤딩(데이터를 여러 DB에 나눠 담기)을 떠올린다. 두 테이블은 사정이 다르다.

가게 테이블은 사진 주소, 영업시간, 설명까지 담아 한 행이 1KB쯤 된다. 500만 곳이면 5GB, 전 세계 2억 곳이면 200GB다. 언젠가 한 대를 넘을 수 있으니 가게 ID로 샤딩할 수 있다. ID로 나누면 고르게 퍼지고, 상세 조회는 늘 ID 하나로 오니 샤드 하나만 찾아간다. 샤딩 기초는 [⑧ 샤딩 입문](/posts/sd-sharding-intro)에 있다.

칸 색인은 앞의 계산대로 200MB, 커져도 몇 GB다. 메모리에 다 올라가는 크기를 굳이 나누면 얻는 것보다 잃는 게 많다. 칸 번호로 나누면 강남 칸이 든 샤드에 검색이 몰리고, 9칸이 서로 다른 샤드에 걸치면 한 검색이 여러 샤드를 돌아야 한다. 대신 복제본을 늘려 읽기를 나눈다. 읽기 부하는 복제본으로, 데이터 크기는 샤딩으로 푸는 것이다.

## 좌표 대신 칸 번호를 캐시 키로

QPS가 수천이면 DB 앞에 캐시를 둔다. 처음 떠오르는 캐시 키는 요청 좌표 그대로다. 그런데 GPS는 가만히 서 있어도 몇 미터씩 흔들리고, 사람은 걷는다. 같은 자리에서 세 번 검색해도 좌표가 매번 달라서 캐시가 한 번도 맞지 않는다. 칸 번호를 키로 쓰면 몇 미터 흔들려도 같은 칸에 떨어진다.

캐시는 두 종류로 둔다. 칸 번호를 키로 그 칸의 가게 목록을 담는 캐시, 가게 ID를 키로 상세를 담는 캐시다. Redis를 비표준 포트 6397에 띄우고 가게 20만 곳을 넣어 봤다. 아래 클라이언트는 라이브러리 없이 RESP 명령을 보내는 50줄짜리다.

```js
// prox3.js 일부: 지오해시 칸을 캐시 키로 쓰기 (Redis 7.0, 포트 6397)
jobs.push(r.cmd("SADD", `geo6:${encode(lat, lng, 6)}`, i));                        // 칸 → 가게 ID 목록
jobs.push(r.cmd("HSET", `biz:${i}`, "name", `가게${i}`, "lat", lat.toFixed(6), "lng", lng.toFixed(6)));  // 가게 상세

// 검색 한 번: 9칸의 ID를 한꺼번에 받고, 후보 상세를 한꺼번에 받는다
const lists = await Promise.all(neighbors(encode(me.lat, me.lng, 6)).map((c) => r.cmd("SMEMBERS", `geo6:${c}`)));
const rows = await Promise.all(lists.flat().map((id) => r.cmd("HMGET", `biz:${id}`, "name", "lat", "lng")));
```

시간 줄을 보면 칸 9개를 읽는 데는 1ms, 후보 1,050곳의 상세를 읽는 데 11ms가 걸렸다. 같은 컨테이너 안의 루프백에서 잰 값이라 돌릴 때마다 조금씩 다르지만, 비율은 비슷했다. 거리를 재려고 상세를 다 읽은 게 낭비다. 칸 캐시의 값에 ID와 함께 좌표를 넣어 두면 9칸만 읽고 거리를 잰 뒤, 첫 페이지 20곳의 상세만 읽으면 된다. 마지막 줄이 그렇게 한 결과로, 2ms 안에 끝났다. 칸 값은 3.6KB로 커지지만 보내는 명령이 1,059개에서 29개로 준다.

캐시를 고쳐 쓰지 않고 지우는 이유가 있다. 지우면 다음 읽기가 DB의 최신 값으로 채운다. 고쳐 쓰려면 캐시 안의 목록을 읽고 바꿔 쓰는 사이에 다른 갱신이 끼어들 수 있다. 지우는 쪽이 단순하고 틀릴 일이 적다. 자세한 함정은 [캐시 무효화](/posts/cache-invalidation)에 있다.

폐업처럼 바로 내려야 하는 변경도 있다. 그런 건 밤을 기다리지 않고, 가게 서비스가 상세 캐시를 바로 지우고 검색 결과에서 "폐업" 표시가 된 가게를 거르게 한다. 하루 지연을 허용한다고 해서 모든 변경을 하루 늦출 필요는 없다.

## 결과가 비거나 너무 많을 때

시골에서 반경 500m를 검색하면 아무것도 안 나올 수 있다. 빈 화면을 주는 대신 반경을 넓혀 다시 찾는다. 6글자에서 비면 5글자로, 그래도 비면 4글자로 칸을 키운다. 몇 단계까지 넓혔는지 응답에 담아 앱이 "2km 안의 결과"라고 보여 주게 한다.

반대로 강남 한복판에서 반경 20km를 주면 후보가 수십만 곳이 된다. 그래서 반경에 상한을 두고, 결과도 한 번에 다 주지 않고 20개씩 나눠 준다. 다음 페이지는 오프셋보다 커서가 낫다. "앞 페이지 마지막 가게의 거리와 ID보다 뒤"로 이어 받으면, 그 사이 가게가 추가돼도 같은 가게가 두 번 나오지 않는다.

거리 말고 다른 기준을 섞기도 한다. 평점이나 지금 영업 중인지로 순위를 매기려면, 칸에서 후보를 넉넉히 모은 뒤 LBS 안에서 점수를 매겨 정렬한다. 칸 색인은 후보를 좁히는 일만 하고, 순위는 그 뒤의 일이다.

## 움직이지 않는 가게에서 움직이는 친구로

주변 검색은 "가게가 거의 움직이지 않는다"는 사실 위에 서 있다. 그래서 칸 색인을 밤에 고치고, 칸 캐시를 오래 둘 수 있었다. 2차원 범위를 1차원 칸 번호로 바꿔 9칸만 읽고, 그 번호를 캐시 키로 다시 썼다. 색인은 작아서 나누지 않고 복제본으로 읽기를 받았다.

다음 글 [㊱ 주변 친구 설계](/posts/sd-nearby-friends)는 이 전제를 뒤집는다. 찾는 대상이 가게가 아니라 걸어 다니는 친구라서 위치가 30초마다 바뀐다. 밤에 고치는 색인으로는 안 되고, 바뀔 때마다 친구에게 밀어 줘야 한다.

## 면접에서 나올 만한 질문

### 위도와 경도에 각각 인덱스를 걸면 안 되나요?

걸어도 느리다. 인덱스 하나는 지구를 두른 띠 하나를 줄 뿐이라서, 두 띠를 각각 읽고 겹치는 부분을 찾아야 한다. 가게 20만 곳으로 재 보니 원 안에 149곳인데 위도 띠 하나에만 6,611곳이 걸렸다. 2차원 좌표를 칸 번호 하나로 접는 공간 색인을 써야 한 번에 좁힌다.

### 지오해시와 쿼드트리 중 무엇을 고르나요?

반경 검색이 주 기능이고 데이터가 자주 안 바뀌면 지오해시를 고른다. 칸 번호가 문자열이라 DB 인덱스와 캐시 키로 바로 쓰고, 가게 하나를 고치면 행 하나만 바뀐다. 지역마다 밀도가 크게 다르거나 "가장 가까운 k곳"이 주 질문이면 쿼드트리가 낫다. 대신 메모리에 트리를 올리느라 서버 기동이 느려서 배포를 나눠 해야 한다.

### 왜 이웃 8칸까지 보나요?

칸 가장자리에 서 있으면 반경 원이 옆 칸으로 넘치기 때문이다. 내 칸만 보면 바로 옆 가게를 놓친다. 실제로 돌려 보니 내 칸만 볼 때 149곳 중 90곳만 찾았다. 칸의 짧은 변이 반경보다 길도록 칸 길이를 고르면 9칸이 원을 빠짐없이 덮는다.

### 트래픽이 10배가 되면 어디부터 늘리나요?

LBS는 무상태라 대수만 늘린다. 칸 캐시와 상세 캐시는 읽기 전용에 가까우니 복제본을 늘리고, DB도 복제본을 더 붙인다. 칸 색인은 몇 GB 안이라 샤딩하지 않는다. 쓰기 경로는 그대로라 영향이 없다.

### 칸 색인 테이블도 샤딩해야 하나요?

보통은 아니다. 가게 500만 곳이면 200MB, 2억 곳이어도 수 GB라 한 대에 들어간다. 칸 번호로 나누면 붐비는 칸이 든 샤드에 검색이 몰리고, 9칸이 여러 샤드에 걸쳐 한 요청이 여러 곳을 돈다. 크기가 아니라 읽기 부하가 문제라서 복제본으로 푼다. 가게 상세 테이블은 커질 수 있으니 가게 ID로 샤딩한다.

### 캐시 키를 요청 좌표로 하면 왜 안 되나요?

GPS가 몇 미터씩 흔들리고 사람이 움직여서 같은 자리의 검색도 좌표가 매번 달라지기 때문이다. 좌표가 키면 캐시가 거의 맞지 않는다. 칸 번호를 키로 쓰면 몇 미터 흔들려도 같은 칸에 떨어진다. 칸 값에 좌표를 함께 넣어 두면 거리 계산까지 캐시 안에서 끝난다.

### 캐시 서버가 죽으면 어떻게 되나요?

검색이 DB 복제본으로 쏟아진다. 평소 캐시가 받던 수천 QPS가 그대로 내려가면 복제본이 못 버틸 수 있다. 캐시를 복제본과 함께 여러 대로 두고, 캐시가 빈 칸을 채울 때 같은 칸은 한 요청만 DB에 가게 묶는다. LBS 메모리에 몇 초짜리 로컬 캐시를 한 겹 더 두면 충격이 줄어든다.

### 가게가 옮기면 검색에 언제 반영되나요?

이 설계에서는 다음 날이다. 가게 테이블은 바로 고치고, 밤에 바뀐 가게를 모아 칸 색인에서 옛 칸을 빼고 새 칸에 넣은 뒤 두 칸의 캐시를 지운다. 폐업처럼 바로 내려야 하는 변경은 상세 캐시를 즉시 지우고 검색 단계에서 거른다. 실시간 반영이 필요하면 변경 이벤트를 큐로 받아 바로 색인을 고치는 쪽으로 간다.
