사번으로 사원 한 명을 찾는 쿼리가 운영 DB에서 갑자기 느려졌다. 인덱스도 있고, 쿼리도 `WHERE emp_code = 7369` 한 줄뿐이다. 실행 계획을 열어 보니 인덱스 대신 테이블 전체를 읽고 있다. `emp_code`가 `'007369'`처럼 문자로 저장된 컬럼인데 숫자와 비교했기 때문이다. 사용자는 함수를 쓴 적이 없는데 DB가 컬럼에 몰래 함수를 씌웠다.

반대로 함수를 일부러 써서 생기는 실수도 있다. 시각을 `'HH:MM:SS'`로 찍었더니 분 자리에 월이 들어갔는데 에러는 나지 않는다. 둘 다 값의 타입을 바꾸는 형 변환에서 생긴다. SQLD 시험은 `TO_CHAR` 형식 문자열과 암시적 형 변환의 방향을 묻고, 현장에서는 같은 일이 인덱스를 못 타는 느린 쿼리로 나타난다.

문자, 숫자, 날짜 함수는 [단일행 함수 글](/posts/sqld-single-row-functions)에서 봤다. 이 글은 `TO_CHAR`, `TO_DATE`, `TO_NUMBER` 형식 문자열을 조각으로 읽고, 암시적 형 변환이 왜 인덱스를 막는지 PostgreSQL 16의 실행 계획으로 확인한다. SQL은 Oracle 문법을 먼저 쓰고 PostgreSQL 16과 SQL Server에서 다른 부분을 옆에 적었다. 결과 표는 PostgreSQL 16.15에서 실제로 돌린 출력이다.

```sql
SELECT ename,
       TO_CHAR(hiredate, 'YYYY-MM-DD')             AS a,
       TO_CHAR(hiredate, 'YYYY"년" MM"월" DD"일"') AS b,
       TO_CHAR(hiredate, 'DY')                     AS c,
       TO_CHAR(hiredate, 'MON')                    AS d,
       TO_CHAR(hiredate, 'Q')                      AS q
FROM emp WHERE deptno = 10 ORDER BY empno;

SELECT TO_CHAR(TIMESTAMP '2026-10-17 14:05:09', 'YYYY-MM-DD HH24:MI:SS') AS ok,
       TO_CHAR(TIMESTAMP '2026-10-17 14:05:09', 'YYYY-MM-DD HH:MM:SS')   AS wrong,
       TO_CHAR(TIMESTAMP '2026-10-17 14:05:09', 'HH12:MI AM')            AS h12;
```

숫자에도 형식이 있다. `9`는 숫자 한 자리, `0`은 빈자리를 0으로 채우는 자리, `,`는 천 단위 구분자다. 형식만 주면 부호 자리로 앞에 공백이 하나 붙는데, `FM`을 앞에 붙이면 공백을 뗀다.

```sql
SELECT TO_DATE('19811203', 'YYYYMMDD') AS d,
       TO_NUMBER('1,250', '9,999')     AS n,
       TO_CHAR(1250, '9,999')          AS c1,   -- 앞에 공백 한 칸
       TO_CHAR(1250, 'FM9,999')        AS c2;
```

```text
     d      |  n   |   c1   |  c2
------------+------+--------+-------
 1981-12-03 | 1250 |  1,250 | 1,250
(1 row)
```

SQL Server는 `TO_CHAR` 대신 `CONVERT(VARCHAR, hiredate, 23)`처럼 스타일 번호를 쓰거나 `FORMAT(hiredate, 'yyyy-MM-dd')`를 쓴다. `FORMAT`의 형식은 .NET 규칙이라 월이 대문자 `MM`, 분이 소문자 `mm`이다.

## 형 변환은 직접 적는다

`TO_CHAR`, `TO_DATE`, `TO_NUMBER`, `CAST`처럼 함수로 타입을 바꾸는 것이 명시적 형 변환이다. 함수를 안 써도 DB가 알아서 타입을 맞춰 주는 경우가 있는데, 이것이 암시적 형 변환이다. Oracle에서 `WHERE empno = '7369'`는 문자 `'7369'`를 숫자로 바꿔서 비교하니 문제없이 돈다.

문제는 반대 방향이다. Oracle은 문자와 숫자를 비교하면 문자 쪽을 숫자로 바꾼다. 문자가 상수면 상관없지만, 문자가 컬럼이면 컬럼 전체에 `TO_NUMBER`가 씌워진다. 인덱스는 컬럼에 저장된 원래 값으로 정렬돼 있어서, 함수를 거친 값으로는 인덱스를 찾을 수 없다. 사번 코드를 `'007369'` 같은 문자열 컬럼에 담은 테이블을 생각해 보자. 아래 그림에서 다음을 누르면 Oracle이 이 쿼리를 어떻게 처리하는지 나온다.

PostgreSQL은 이 상황에서 아예 변환해 주지 않고 에러를 낸다. 20만 행짜리 테이블에 실험했다.

```sql
CREATE TABLE emp_big AS
SELECT i AS empno,
       lpad(i::text, 6, '0')::varchar(6) AS emp_code,   -- '000001' ~ '200000'
       date '1980-01-01' + (i % 15000) AS hiredate
FROM generate_series(1, 200000) AS i;
CREATE INDEX emp_big_code_idx ON emp_big (emp_code);
CREATE INDEX emp_big_hire_idx ON emp_big (hiredate);
VACUUM ANALYZE emp_big;

SELECT * FROM emp_big WHERE emp_code = 7369;
```

날짜도 같다. [단일행 함수 글](/posts/sqld-single-row-functions)에서 본 `TRUNC(created) = DATE '...'`나 `TO_CHAR(hiredate, 'YYYYMMDD') = '19811203'`도 컬럼에 함수를 씌운 모양이다.

SQL Server는 타입 우선순위 표를 따라 낮은 쪽을 높은 쪽으로 바꾼다. `int`가 `varchar`보다 높아서 `varchar` 컬럼과 숫자를 비교하면 역시 컬럼 쪽이 바뀌고, 인덱스를 제대로 못 쓴다.

## 현장에서 파라미터 타입이 인덱스를 막는 순간

쿼리에 상수를 직접 쓰는 경우보다 애플리케이션이 파라미터로 값을 넘기는 경우가 훨씬 많다. 이때 파라미터의 타입은 코드 쪽에서 정해진다. 자바에서 `BigDecimal`이나 다른 언어의 십진수 타입으로 값을 넘기면 드라이버가 `numeric`으로 보내고, 정수 컬럼과 비교하는 순간 컬럼 쪽이 바뀐다. 위의 `emp_big`에 `empno` 유니크 인덱스를 하나 더 만들고 실험했다.

```sql
CREATE UNIQUE INDEX emp_big_empno_idx ON emp_big (empno);
VACUUM ANALYZE emp_big;

-- 숫자 상수에 소수점이 붙었다
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM emp_big WHERE empno = 7369.0;
```

```text
                                                      QUERY PLAN
----------------------------------------------------------------------------------------------------------------------
 Gather  (cost=1000.00..3952.71 rows=1000 width=15) (actual time=0.939..14.498 rows=1 loops=1)
   Workers Planned: 1
   Workers Launched: 1
   Buffers: shared hit=1088
   ->  Parallel Seq Scan on emp_big  (cost=0.00..2852.71 rows=588 width=15) (actual time=4.572..9.941 rows=0 loops=2)
         Filter: ((empno)::numeric = 7369.0)
         Rows Removed by Filter: 100000

```

`Filter: ((empno)::numeric = 7369.0)`가 범인이다. 컬럼에 `::numeric`이 붙었다. 드라이버가 파라미터를 보내는 모양은 `PREPARE`로 똑같이 재현할 수 있다. 같은 값을 `bigint`로 보낼 때와 `numeric`으로 보낼 때를 비교한다.

```sql
-- 정수 파라미터 (bigint)
PREPARE by_big(bigint) AS SELECT * FROM emp_big WHERE empno = $1;
EXPLAIN (ANALYZE, BUFFERS) EXECUTE by_big(7369);

-- 십진수 파라미터 (numeric)
PREPARE by_num(numeric) AS SELECT * FROM emp_big WHERE empno = $1;
EXPLAIN (ANALYZE, BUFFERS) EXECUTE by_num(7369);
```

```text
 Index Scan using emp_big_empno_idx on emp_big  (cost=0.42..8.44 rows=1 width=15) (actual time=0.051..0.052 rows=1 loops=1)
   Index Cond: (empno = '7369'::bigint)
   Buffers: shared hit=4 read=3
 Execution Time: 0.064 ms

   ->  Parallel Seq Scan on emp_big  (cost=0.00..2852.71 rows=588 width=15) (actual time=4.996..10.562 rows=0 loops=2)
         Filter: ((empno)::numeric = '7369'::numeric)
         Rows Removed by Filter: 100000
         Buffers: shared hit=1088
 Execution Time: 15.115 ms
```

`bigint`는 `integer` 컬럼과 바로 비교하는 연산자가 있어서 `Index Cond`로 들어갔다. `numeric`은 그런 연산자가 없어 컬럼을 바꿨고, 7페이지 대신 1,088페이지를 읽었다. 값은 똑같이 7369인데 넘긴 타입 하나로 200배 넘게 느려졌다.

이런 쿼리는 코드만 봐서는 찾기 어렵다. 느린 쿼리 로그나 `pg_stat_statements`에서 걸린 쿼리를 `EXPLAIN`으로 열고, `Filter` 줄의 컬럼에 `::타입`이 붙어 있는지 본다. 붙어 있으면 코드에서 파라미터 타입을 컬럼에 맞춘다(정수 컬럼이면 `Long`·`Integer`로). ORM의 엔티티 필드 타입이 컬럼 타입과 다를 때 자주 생기니, 스키마를 바꾼 뒤에는 엔티티도 함께 맞춘다. 인덱스와 실행 계획을 읽는 법은 [인덱스 글](/posts/db-index)에 더 있다.

## SQLD 시험 포인트

- 분은 `MI`, 월은 `MM`이다. `HH:MM:SS`로 쓰면 에러 없이 분 자리에 월이 들어간다. 24시간제는 `HH24`다.
- `TO_CHAR`는 날짜·숫자를 문자로, `TO_DATE`는 문자를 날짜로, `TO_NUMBER`는 문자를 숫자로 바꾼다. 숫자 형식의 `9`는 자리, `0`은 0 채움, `FM`은 앞 공백 제거다.
- 문자 컬럼을 숫자 상수와 비교하면 컬럼이 변환돼 인덱스를 못 쓴다. 숫자 컬럼을 문자 상수와 비교하면 상수가 바뀌어서 괜찮다.
- 컬럼에 함수를 씌우면(`TRUNC(created)`, `TO_CHAR(hiredate, ...)`) 인덱스를 못 쓴다. 범위 조건으로 바꾸거나 함수 기반 인덱스를 만든다.
- SQL Server 대응: `CONVERT`, `CAST`, `FORMAT`(월 `MM`, 분 `mm`).

## 면접에서 나올 만한 질문

### 암시적 형 변환이 왜 성능 문제가 되나요?

Oracle은 문자와 숫자를 비교하면 문자 쪽을 숫자로 바꾸는데, 그 문자가 컬럼이면 `TO_NUMBER(컬럼)`이 씌워진다. 인덱스는 원래 값 순서로 정렬돼 있어서 함수를 거친 값으로는 탐색할 수 없고, 전체 스캔으로 바뀐다. 예제에서 20만 행 테이블이 4페이지 대신 1,082페이지를 읽었다. 숫자가 아닌 값이 섞여 있으면 ORA-01722 에러까지 난다. 상수를 컬럼 타입에 맞춰 쓰는 게 기본이다.

### 컬럼에 함수를 꼭 써야 하면 인덱스는 포기해야 하나요?

두 가지 방법이 있다. 하나는 조건을 컬럼이 그대로 남게 다시 쓰는 것이다. `TRUNC(created) = 날짜`는 `created >= 날짜 AND created < 날짜 + 1`로, `TO_CHAR(hiredate, 'YYYY') = '1981'`은 1981년 1월 1일부터 1982년 1월 1일 전까지의 범위로 바꾼다. 다른 하나는 `UPPER(ename)`처럼 식 자체로 함수 기반 인덱스를 만드는 것이다. 다만 쿼리의 식이 인덱스 식과 정확히 같아야 쓰이고 쓰기 비용이 늘어난다.

### TO_CHAR에서 HH:MM:SS로 쓰면 어떻게 되나요?

에러 없이 분 자리에 월이 찍힌다. 형식 문자열에서 `MM`은 월이고 분은 `MI`이기 때문이다. 오후 2시 5분 9초를 `HH:MM:SS`로 찍으면 `HH`가 12시간제라 02, `MM`이 10월이라 10이 들어가 `02:10:09`가 된다. 시각은 `HH24:MI:SS`로 쓰고, 에러가 안 나는 실수라서 결과를 눈으로 확인하는 테스트가 필요하다.

### Oracle과 PostgreSQL은 문자와 숫자를 비교할 때 어떻게 다르게 동작하나요?

Oracle은 문자 쪽을 숫자로 암시적으로 바꿔서 비교를 진행한다. 문자가 컬럼이면 `TO_NUMBER(컬럼)`이 되어 인덱스를 못 쓰고, 숫자가 아닌 값이 있으면 ORA-01722로 멈춘다. PostgreSQL은 `varchar = integer` 연산자가 없어서 바로 에러를 내고 명시적 변환을 요구한다. 대신 integer와 numeric처럼 숫자끼리는 넓은 쪽으로 맞추느라 컬럼이 바뀔 수 있다.

### 애플리케이션에서 넘긴 파라미터 타입 때문에 인덱스를 못 쓸 수도 있나요?

그렇다. PostgreSQL에서 integer 컬럼을 numeric 파라미터와 비교하면 컬럼이 `::numeric`으로 바뀌어 전체 스캔이 된다. 예제에서 같은 7369를 bigint로 넘기면 Index Scan으로 7페이지, numeric으로 넘기면 Seq Scan으로 1,088페이지를 읽었다. 실행 계획의 `Filter` 줄에서 컬럼에 캐스팅이 붙었는지 보고, 코드의 파라미터 타입을 컬럼에 맞춘다.
