실패하면 1초 쉬고 다시 시도하는 `retry` 함수를 만들고 테스트를 짰다. 실제로 1초씩 기다리면 테스트가 느려지니 가짜 타이머로 시간을 앞으로 돌린다. Node.js 22에 들어 있는 `node:test`의 mock timers를 썼다(22에서는 아직 실험 기능이라 경고가 한 줄 찍힌다).

```js
import { test, mock } from "node:test";
import assert from "node:assert/strict";

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function retry(fn, times, delay) {
  for (let i = 0; ; i++) {
    try {
      return await fn();
    } catch (e) {
      if (i >= times) throw e;
      await sleep(delay);
    }
  }
}

test("두 번 실패하고 세 번째에 성공한다", () => {
  mock.timers.enable({ apis: ["setTimeout"] });
  let calls = 0;
  const fn = async () => {
    calls++;
    if (calls < 3) throw new Error("일시 장애");
    return "ok";
  };
  retry(fn, 3, 1000);
  mock.timers.tick(1000);
  mock.timers.tick(1000);
  assert.equal(calls, 3);
  mock.timers.reset();
});
```

```text
not ok 1 - 두 번 실패하고 세 번째에 성공한다
  ...
  error: |-
    Expected values to be strictly equal:

    1 !== 3
```

시간을 2초나 돌렸는데 `fn`은 한 번만 불렸다. 코드는 맞다. 실제 시간으로 돌리면 세 번 불린다. 틀린 건 테스트가 상상한 "순서"다. 첫 실패를 `catch`로 받아 `sleep`을 부르는 일은 마이크로태스크에서 일어나는데, 테스트는 동기 코드 안에서 그걸 기다리지 않고 바로 시계를 돌렸다. 시계를 돌리는 순간 예약된 타이머가 아직 하나도 없었다.

## 매크로태스크라는 말은 명세에 없다

용어부터 정리하자. 흔히 매크로태스크(macrotask)라고 부르는 것을 HTML 명세는 그냥 태스크(task)라고 부른다. 매크로태스크는 마이크로태스크와 대비하려고 개발자들이 붙인 별명이다. 그리고 태스크 큐는 하나가 아니다. 타이머, 사용자 입력, 네트워크, `postMessage`처럼 태스크 소스(task source)마다 큐가 따로 있고, 브라우저가 다음에 어느 큐에서 꺼낼지 고른다.

마이크로태스크 쪽은 이름이 두 개다. ECMAScript 명세는 Promise 반응을 잡(job)이라 부르고 "호스트가 정한 큐에 넣으라"고만 적는다(HostEnqueuePromiseJob). 브라우저(HTML 명세)와 Node.js는 이 잡을 마이크로태스크 큐에 넣는다. 그래서 `then` 콜백이 마이크로태스크라는 건 자바스크립트 언어 자체가 아니라 실행 환경이 정한 것이다. 실무에서 차이가 날 일은 거의 없지만 면접에서 "job queue와 microtask queue는 같은가"라는 꼬리 질문이 나오면 이렇게 답하면 된다.

```js
queueMicrotask(() => out.push("micro"));
setTimeout(() => console.log(out.join(" ")), 100);
```

## 장부를 적으며 푸는 법

퍼즐을 감으로 풀면 틀린다. 칸 세 개짜리 장부를 적으면 기계적으로 풀린다. 콜 스택에서 지금 도는 것, 마이크로태스크 큐, 태스크 큐다. 규칙은 넷이다.

1. 동기 코드는 스택에서 바로 실행한다.
2. `then`은 앞의 Promise가 이미 정해졌으면 콜백을 마이크로태스크 큐 뒤에 넣는다. 아직이면 Promise에 걸어 두었다가 정해지는 순간 넣는다.
3. 스택이 비면 마이크로태스크 큐 맨 앞에서 하나 꺼내 실행한다. 실행하면서 새로 넣은 건 큐 맨 뒤로 간다. 큐가 빌 때까지 반복한다.
4. 그다음에야 태스크 하나를 꺼낸다.

규칙 2가 함정이다. `then`을 이어 붙인 체인은 한 번에 큐에 들어가지 않는다. 첫 콜백만 들어가고, 두 번째 콜백은 첫 콜백이 끝나 그 결과 Promise가 정해질 때 들어간다. 그래서 체인 두 개는 번갈아 실행된다.

```js
const out = [];
Promise.resolve()
  .then(() => out.push("a1"))
  .then(() => out.push("a2"))
  .then(() => out.push("a3"));
Promise.resolve()
  .then(() => out.push("b1"))
  .then(() => out.push("b2"));
setTimeout(() => console.log(out.join(" ")), 0);
```

```text
a1 b1 a2 b2 a3
```

```js
const out = [];

  .then(() => {
    out.push("a1");
    Promise.resolve().then(() => out.push("inner"));
  })
```

## await 하나는 한 틱이다

`async` 함수도 같은 장부로 푼다. `await` 앞까지는 동기로 돌고, `await` 뒷부분은 기다리는 값이 정해지면 마이크로태스크로 들어간다. Promise가 아닌 값(`null`, 숫자)을 `await`해도 한 틱은 쉰다.

```js
const out = [];
async function slow() {
  out.push("s1");
  await null;
  out.push("s2");
  await null;
  out.push("s3");
}
async function fast() {
  out.push("f1");
  await null;
  out.push("f2");
}
slow();
fast();
Promise.resolve().then(() => out.push("p"));
out.push("sync");
setTimeout(() => console.log(out.join(" ")), 0);
```

```text
s1 f1 sync s2 f2 p s3
```

여기서 실무 감각 하나를 얻는다. `await`가 많은 함수는 그만큼 다른 마이크로태스크에 자리를 내준다. 그래서 두 `async` 흐름이 같은 변수를 읽고 쓰면, `await` 개수만 바뀌어도 순서가 바뀐다. 리팩터링으로 `await` 하나를 지웠더니 동작이 달라졌다면 이 경우다. 순서가 중요한 일은 틱 수에 기대지 말고 한쪽이 다른 쪽을 명시적으로 `await`하게 짠다.

이미 이행된 Promise를 `then` 콜백에서 `return`하면 틱이 두 번 더 든다는 규칙도 있다. 그건 [Promise 글의 resolve에 Promise를 넘기는 절](/posts/js-promises#resolve에-promise를-넘기면-늦어진다)에서 봤고, 아래 연습 문제에서 직접 굴려 본다.

고치는 방법은 시계를 돌리기 전에 마이크로태스크를 비우는 것이다. 가짜로 만들지 않은 진짜 태스크 하나를 기다리면 된다. 태스크가 돌기 전에는 마이크로태스크가 전부 비워진다는 규칙 3, 4를 그대로 이용한다.

```js
// 가짜로 만들지 않은 setImmediate는 진짜 태스크다.
// 이걸 기다리면 그 전에 쌓인 마이크로태스크가 전부 비워진다.
const flush = () => new Promise((r) => setImmediate(r));

test("두 번 실패하고 세 번째에 성공한다", async () => {
  mock.timers.enable({ apis: ["setTimeout"] });
  let calls = 0;
  const fn = async () => {
    calls++;
    if (calls < 3) throw new Error("일시 장애");
    return "ok";
  };
  const result = retry(fn, 3, 1000);
  await flush(); // 첫 실패 처리 → 타이머 예약까지
  mock.timers.tick(1000);
  await flush();
  mock.timers.tick(1000);
  assert.equal(await result, "ok");
  assert.equal(calls, 3);
  mock.timers.reset();
});
```

```text
ok 1 - 두 번 실패하고 세 번째에 성공한다
```

`await Promise.resolve()` 한 번으로 비우려는 코드를 자주 본다. 우연히 통과할 수는 있다. 하지만 기다려야 할 틱 수는 `retry` 안의 `await` 개수에 달려 있어서, 구현이 조금만 바뀌어도 다시 깨진다. 태스크 하나를 기다리는 쪽이 튼튼하다. Jest(29.5부터)와 Vitest에는 이 일을 대신 하는 `advanceTimersByTimeAsync`가 있다. 시간을 돌리는 사이사이 마이크로태스크를 비워 준다. 가짜 타이머 테스트가 이유 없이 실패하면 동기 `tick`/`advanceTimersByTime`을 비동기 버전으로 바꿔 보는 게 첫 번째 확인이다.

반대 방향의 함정도 있다. `setImmediate`까지 가짜로 바꾸는 설정(Jest의 기본 가짜 타이머가 그렇다)에서는 위의 `flush`가 시계를 돌리기 전까지 끝나지 않는다. 어떤 API를 가짜로 바꿨는지 먼저 확인한다.

## Node.js 11에서 바뀐 순서

Node.js에서 같은 시각에 만료된 타이머 두 개가 각자 마이크로태스크를 예약하면 어떻게 될까.

```js
setTimeout(() => {
  console.log("t1");
  Promise.resolve().then(() => console.log("p1"));
}, 0);
setTimeout(() => {
  console.log("t2");
  Promise.resolve().then(() => console.log("p2"));
}, 0);
```

## 마이크로태스크에서 던진 에러는 어디로 가나

같은 마이크로태스크라도 무엇으로 만들었느냐에 따라 에러가 가는 곳이 다르다. 크롬 141에서 확인했다.

```js
window.addEventListener("error", (e) => console.log("error 이벤트:", e.message));
window.addEventListener("unhandledrejection", (e) => console.log("unhandledrejection:", e.reason.message));

queueMicrotask(() => { throw new Error("A"); });
queueMicrotask(() => console.log("다음 마이크로태스크는 돈다"));
Promise.resolve().then(() => { throw new Error("B"); });
```

```text
error 이벤트: Uncaught Error: A
다음 마이크로태스크는 돈다
unhandledrejection: B
```

`queueMicrotask` 콜백에서 던진 에러는 잡히지 않은 예외로 바로 보고된다(`error` 이벤트). `then` 콜백에서 던진 에러는 예외가 아니라 그 `then`이 돌려준 Promise의 거부가 되고, 아무도 처리하지 않으면 마이크로태스크를 다 비운 뒤에 `unhandledrejection`으로 보고된다. 그리고 한 마이크로태스크가 던져도 큐의 나머지는 계속 돈다.

Node.js에서는 결과가 훨씬 무겁다. `queueMicrotask`의 예외는 `uncaughtException`이 되어 기본으로 프로세스를 끝낸다. 처리되지 않은 거부도 Node.js 15부터 기본으로 프로세스를 끝낸다([Promise 글](/posts/js-promises#아무도-받지-않은-거부) 참고). 라이브러리를 만들며 콜백을 "나중에" 부르려고 `queueMicrotask`를 쓸 때, 사용자 콜백을 `try`/`catch` 없이 부르면 사용자의 실수가 서버를 내린다.

## DOM 변경은 마이크로태스크로 묶인다

`MutationObserver`가 마이크로태스크를 쓰는 이유를 보면 마이크로태스크가 왜 있는지 감이 온다. DOM을 세 번 바꿨을 때 콜백이 세 번 불리면 낭비이고, 다음 태스크까지 미루면 그 사이에 화면이 그려져 버린다. 마이크로태스크는 "지금 하는 일이 끝나자마자, 그러나 렌더링보다는 먼저"라는 자리다.

```js
const box = document.getElementById("box");
new MutationObserver((records) => console.log("observer 호출, 기록", records.length, "개"))
  .observe(box, { childList: true, attributes: true });
box.setAttribute("data-a", "1");
box.append("x");
box.setAttribute("data-b", "2");
Promise.resolve().then(() => console.log("then"));
console.log("동기 코드 끝");
```

```text
동기 코드 끝
observer 호출, 기록 3 개
then
```

## React가 업데이트를 묶는 자리

React 18부터는 이벤트 핸들러든 `setTimeout`이든 `await` 뒤든 `setState`를 여러 번 부르면 한 번만 렌더링한다(자동 배칭). 무엇이 언제 묶이는지는 [리렌더링 글](/posts/react-rerender#여러-번-바꿔도-렌더링은-한-번)에서 봤다. 여기서는 그게 어느 큐를 쓰는지만 본다.

React 19의 `react-dom` 소스를 보면 `setState`가 불렸을 때 바로 렌더링하지 않고 `queueMicrotask`로 "루트 일정 정리"를 예약한다. 그래서 같은 동기 코드 안에서 부른 `setState`는 몇 번이든 그 마이크로태스크 하나에서 함께 처리된다. 그 마이크로태스크에서 클릭 같은 이산 이벤트의 업데이트는 바로 렌더링하고, 덜 급한 업데이트는 React의 스케줄러에 넘긴다. 스케줄러는 브라우저에서 `MessageChannel`로 태스크를 만들어 5ms 단위로 일을 끊는다.

장부로 보면 이렇게 정리된다. `setState` 다음 줄에서 DOM을 읽으면 아직 옛 화면이다. 렌더링은 내 코드가 끝난 뒤의 마이크로태스크나 다음 태스크에서 일어나기 때문이다. 핸들러 중간에 `await`가 있으면, 그 앞에서 부른 `setState`가 잡아 둔 React 마이크로태스크가 `await` 뒷부분보다 먼저 줄에 서 있다. 그래서 `await` 앞뒤의 업데이트는 서로 다른 묶음이 된다. 꼭 그 자리에서 DOM에 반영해야 한다면(스크롤 위치를 재야 할 때 등) `flushSync`로 감싼다. 렌더링 비용을 바로 치르는 거라 꼭 필요한 곳에만 쓴다.

## 순서 버그를 현장에서 좁히는 법

순서 문제의 증상은 대개 "가끔"이다. 테스트가 가끔 실패한다, 상태가 가끔 옛값으로 덮인다, 로그 순서가 환경마다 다르다. 이렇게 좁힌다.

- 같은 종류 안의 순서인지 다른 종류 사이의 순서인지 본다. 마이크로태스크끼리, 같은 타이머끼리의 순서는 보장된다. `setTimeout`과 `MessageChannel`, `setTimeout(0)`과 `setImmediate`처럼 서로 다른 태스크 소스 사이의 순서에 기대고 있다면 그게 원인이다.
- 틱 수에 기대고 있지 않은지 본다. "`await` 두 번이면 저쪽보다 늦다" 같은 가정이 있으면, 한쪽 구현이 바뀔 때 깨진다. 기다려야 할 대상을 직접 `await`하게 바꾼다.
- 테스트라면 가짜 타이머 설정을 본다. 무엇을 가짜로 바꿨는지, 시계를 돌리는 함수가 마이크로태스크를 비워 주는 비동기 버전인지 확인한다.
- 크롬 개발자 도구 Performance 패널에서 한 태스크 아래에 "Run Microtasks"가 길게 붙어 있으면 마이크로태스크가 쌓여 태스크를 늘리고 있다는 뜻이다. `await`를 수천 번 도는 반복문이 흔한 원인이다.

## 연습: 체인 여러 개의 출력 순서

`Promise.resolve()`에서 시작하는 `then` 체인 여러 개를 동시에 만들었을 때의 출력 순서를 계산하는 함수를 짜 보자. `chains`는 체인마다 콜백 이름을 담은 배열이다. 이름이 `~`로 시작하면 그 콜백은 이미 이행된 Promise(`Promise.resolve()`)를 `return`한다. 그러면 다음 고리는 틱 두 번을 더 기다린 뒤에 큐에 선다. 출력에는 `~`를 뗀 이름을 넣는다.

## 다시 retry 테스트로

테스트가 틀린 건 시간을 몰라서가 아니라 순서를 몰라서였다. 동기 코드가 다 끝나야 마이크로태스크가 돌고, 마이크로태스크가 다 비워져야 다음 태스크가 돈다. 체인의 고리 하나, `await` 하나가 각각 한 틱이고 큐는 공정하게 줄을 세운다. 이 장부만 적을 줄 알면 퍼즐도, 가짜 타이머 테스트도, React의 배칭도 같은 그림으로 읽힌다. 시간 쪽 이야기, 즉 타이머가 정해진 시각보다 늦게 울리는 이유는 [타이머는 왜 늦게 울리나](/posts/js-timers-accuracy)에서 이어진다.

## 면접에서 나올 만한 질문

### 마이크로태스크와 매크로태스크는 무엇이 다른가요?

태스크(흔히 매크로태스크)는 이벤트 루프가 한 번에 하나씩 꺼내는 일이고, 마이크로태스크는 콜 스택이 빌 때마다 큐가 빌 때까지 전부 실행하는 일이다. `setTimeout`, 입력 이벤트, `postMessage`는 태스크이고, Promise 콜백, `await` 뒷부분, `queueMicrotask`, `MutationObserver`는 마이크로태스크다. 그래서 같은 시점에 예약하면 마이크로태스크가 항상 먼저 돈다.

### then 체인 두 개를 동시에 만들면 왜 번갈아 실행되나요?

체인의 다음 콜백은 앞 콜백이 끝나 그 결과 Promise가 정해질 때 비로소 큐에 들어가기 때문이다. 처음에는 체인마다 첫 콜백만 큐에 있고, 하나가 끝날 때마다 다음 고리가 큐 맨 뒤에 선다. 그래서 a1 b1 a2 b2처럼 한 칸씩 엇갈린다.

### await null처럼 Promise가 아닌 값을 await해도 비동기인가요?

그렇다. 값은 `Promise.resolve`로 감싸지고 함수의 나머지는 마이크로태스크로 예약된다. 그래서 `await null`도 한 틱을 쉬고, 그 사이에 이미 큐에 있던 다른 마이크로태스크가 먼저 돈다. 다만 태스크를 거치지 않으니 렌더링이나 입력에 메인 스레드를 양보하는 효과는 없다.

### 가짜 타이머로 시간을 돌렸는데 콜백이 안 불립니다. 왜 그런가요?

타이머를 예약하는 코드가 `await`나 `then` 뒤, 즉 마이크로태스크에 있는데 테스트가 동기 코드 안에서 바로 시계를 돌렸기 때문이다. 시계를 돌리는 순간에는 아직 타이머가 예약되지 않았다. 시계를 돌리기 전에 진짜 태스크 하나를 기다려 마이크로태스크를 비우거나, `advanceTimersByTimeAsync` 같은 비동기 버전을 쓴다.

### queueMicrotask에서 던진 에러와 then에서 던진 에러는 어떻게 다른가요?

`queueMicrotask`의 에러는 잡히지 않은 예외로 바로 보고된다. 브라우저는 `error` 이벤트, Node.js는 `uncaughtException`이고 Node.js에서는 기본으로 프로세스가 끝난다. `then`에서 던진 에러는 그 `then`이 돌려준 Promise의 거부가 되고, 처리하는 쪽이 없으면 `unhandledrejection`으로 보고된다. 둘 다 큐의 나머지 마이크로태스크는 계속 실행된다.

### ECMAScript의 job queue와 HTML의 microtask queue는 같은 건가요?

같은 일을 서로 다른 명세가 부르는 이름이다. ECMAScript는 Promise 반응을 job으로 만들어 호스트에게 넣어 달라고만 하고, 브라우저와 Node.js가 그걸 마이크로태스크 큐에 넣는다. 그래서 Promise 콜백이 언제 도는지는 실행 환경의 이벤트 루프가 정한다.

### Node.js와 브라우저의 이벤트 루프 순서는 어떻게 다른가요?

마이크로태스크를 비우는 시점은 Node.js 11부터 브라우저와 같아서, 타이머 콜백 하나가 끝날 때마다 비운다. 다른 점은 Node.js에 `process.nextTick` 큐가 마이크로태스크보다 앞에 있고, 태스크 쪽이 타이머, I/O, `setImmediate` 같은 단계로 나뉜다는 것이다. 메인 모듈에서 `setTimeout(0)`과 `setImmediate`의 순서는 정해지지 않지만 I/O 콜백 안에서는 `setImmediate`가 먼저다.

### React에서 setState 직후 DOM을 읽으면 왜 옛값인가요?

`setState`는 바로 렌더링하지 않고 업데이트를 모아 두었다가 마이크로태스크나 스케줄러 태스크에서 한 번에 처리하기 때문이다. React 19 소스 기준으로 `setState`는 `queueMicrotask`로 일정을 잡고, 급하지 않은 업데이트는 `MessageChannel` 태스크로 넘긴다. 그 자리에서 DOM 반영이 꼭 필요하면 `flushSync`를 쓰고, 보통은 effect에서 읽는다.
