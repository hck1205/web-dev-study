</EasyIntro>

주문 테이블의 열 타입을 바꾸는 `ALTER TABLE`을 프라이머리에서 돌렸다. 9초 만에 끝났고 에러도 없었다. 그런데 그 직후부터 주문 상세 화면이 "주문을 찾을 수 없습니다"를 띄운다. 방금 들어온 주문이 읽기용 레플리카에 없다. 모니터링의 `Seconds_Behind_Source`는 조금 전까지 0이었다가 갑자기 9, 10, 11로 올라간다.

이 글은 이 장면을 따라 MySQL 복제가 어떻게 돌아가는지, 그리고 큰 테이블의 구조를 바꿀 때 무엇이 막히는지 본다. binlog에 무엇이 적히는지, 레플리카 안에서 어떤 스레드가 그걸 받아 적용하는지, GTID가 왜 필요한지, 반동기 복제가 무엇을 지켜 주는지, 복제 지연 숫자를 어디까지 믿을지를 실제 서버 두 대로 확인한다. 뒤쪽에서는 온라인 DDL의 세 가지 방식과 메타데이터 잠금, gh-ost와 pt-online-schema-change를 다룬다.

InnoDB 안쪽(redo, undo, 잠금)은 [MySQL InnoDB 기초](/posts/mysql-innodb-basics)에서 다뤘다. 복제 일반론과 PostgreSQL 스트리밍 복제는 [DB 한 대로 버티지 못할 때](/posts/db-replication-sharding)에, 잠금 큐와 PostgreSQL의 무중단 스키마 변경은 [무중단 스키마 변경](/posts/zero-downtime-migrations)에 있다. 여기서는 그 내용을 반복하지 않고 MySQL에서 실제로 돌려 본 것만 쓴다.

## 프라이머리에선 9초에 끝난 ALTER가 레플리카에선 그때부터 시작됐다

장면을 그대로 재현했다. 100만 행 `orders_big`의 `memo` 열 타입을 바꾸고, 끝나자마자 주문을 하나 넣은 뒤, 레플리카에 그 주문이 언제 보이는지 1초마다 확인했다.

```sql
-- 프라이머리
ALTER TABLE orders_big MODIFY memo CHAR(120) NOT NULL DEFAULT '', ALGORITHM=COPY;
INSERT INTO orders (user_id, amount, status) VALUES (20, 7000, 'ready');  -- id 6
```

```text
18:41:11 ALTER start
18:41:20 ALTER done
18:41:20 insert done
18:41:29 order 6 visible on replica
```

레플리카 쪽에서는 1초마다 `SHOW REPLICA STATUS`의 `Seconds_Behind_Source`와 적용 스레드의 상태를 찍었다.

```text
18:41:10 Seconds_Behind_Source=0
18:41:19 Seconds_Behind_Source=0
18:41:20 Seconds_Behind_Source=9 copy to tmp table
18:41:21 Seconds_Behind_Source=10 copy to tmp table
18:41:24 Seconds_Behind_Source=13 copy to tmp table
18:41:27 Seconds_Behind_Source=16 copy to tmp table
18:41:28 Seconds_Behind_Source=17
18:41:29 Seconds_Behind_Source=0
```

프라이머리가 ALTER를 돌리는 9초 동안 레플리카는 아무것도 모르고 지연 0이었다. ALTER는 끝나야 binlog에 기록되기 때문이다. 18:41:20에 binlog를 받은 레플리카는 같은 ALTER를 처음부터 다시 돌리기 시작했고(`copy to tmp table`), 그 9초 동안 뒤에 들어온 주문 6은 ALTER 뒤에서 기다렸다. 지연이 0에서 바로 9로 뛴 이유도 binlog에 있다. 이벤트에는 프라이머리에서 문장이 시작된 시각이 적힌다.

```text
#261021 18:41:11 server id 1  end_log_pos 24106572 CRC32 0x5a647001 	Query	thread_id=17	exec_time=9	error_code=0	Xid = 51
ALTER TABLE orders_big MODIFY memo CHAR(120) NOT NULL DEFAULT '', ALGORITHM=COPY
```

이벤트 시각은 18:41:11, 프라이머리에서 걸린 시간은 `exec_time=9`다. 레플리카는 "지금 적용 중인 이벤트가 언제 만들어졌나"로 지연을 계산하니, 받자마자 9초 늦은 것으로 보인다.

## 프라이머리와 레플리카 두 대를 띄운다

실험 환경은 Ubuntu 24.04 패키지의 MySQL 8.0.46 두 대다. 같은 장비에서 포트만 다르게(프라이머리 17950, 레플리카 17951) 띄웠다. 이 글의 출력은 모두 이 두 대에서 실제로 돌린 것이다. 1초마다 찍은 기록은 필요한 줄만 골랐고, 스크립트로 돌릴 때 에러 뒤에 붙는 `at line 1`은 지웠다. 프라이머리는 binlog와 GTID를 켠다. 8.0은 binlog가 기본으로 켜져 있지만 GTID는 꺼져 있다.

```ini
# 프라이머리 my.cnf (레플리카는 server-id=2, port만 다르다)
[mysqld]
server-id                = 1
log-bin                  = binlog
gtid_mode                = ON
enforce_gtid_consistency = ON
```

프라이머리에 복제 전용 계정을 만들고, 레플리카에서 그 계정으로 붙는다.

```sql
-- 프라이머리: 복제 계정
CREATE USER 'repl'@'127.0.0.1' IDENTIFIED BY 'replpw';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'127.0.0.1';

-- 레플리카: 어디서 받을지 정하고 시작한다
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = '127.0.0.1', SOURCE_PORT = 17950,
  SOURCE_USER = 'repl', SOURCE_PASSWORD = 'replpw',
  SOURCE_AUTO_POSITION = 1,      -- binlog 파일 위치 대신 GTID로 이어 받는다
  GET_SOURCE_PUBLIC_KEY = 1;     -- caching_sha2_password를 TLS 없이 쓸 때 필요
START REPLICA;
SET GLOBAL super_read_only = ON; -- 레플리카에 실수로 쓰지 못하게
```

```text
           Replica_IO_Running: Yes
          Replica_SQL_Running: Yes
        Seconds_Behind_Source: 0
                  Source_UUID: e9e49837-cd4b-11f1-a341-02fc00000001
           Retrieved_Gtid_Set: e9e49837-cd4b-11f1-a341-02fc00000001:1-2
            Executed_Gtid_Set: e9e49837-cd4b-11f1-a341-02fc00000001:1-2
                Auto_Position: 1
```

`SHOW REPLICA STATUS\G`에서 처음 볼 줄은 두 개의 `Running: Yes`다. 하나라도 `No`면 복제가 멈춘 것이고, `Last_IO_Error`나 `Last_SQL_Error`에 이유가 적힌다. 실제 운영에서는 `SOURCE_SSL = 1`로 복제 연결도 암호화한다. 이미 데이터가 있는 프라이머리에 레플리카를 붙일 때는 먼저 `mysqldump --source-data`나 클론 플러그인, 물리 백업으로 같은 시점의 사본을 만들고 거기서부터 받게 한다.

8.0.22~8.0.23에서 명령 이름이 `SHOW SLAVE STATUS` → `SHOW REPLICA STATUS`, `CHANGE MASTER TO` → `CHANGE REPLICATION SOURCE TO`로 바뀌었다. 옛 이름도 아직 동작하지만 문서와 출력은 새 이름을 쓴다.

## binlog에는 바뀐 행의 전후가 적힌다

복제는 프라이머리의 binlog를 레플리카가 받아 그대로 다시 실행하는 일이다. binlog는 InnoDB의 redo와 다르다. redo는 "어느 페이지의 몇 바이트"라서 그 장비의 파일 배치에 묶여 있고, binlog는 "어느 테이블의 어떤 행이 어떻게"라는 논리적인 기록이다. 그래서 버전이 조금 달라도, 저장 엔진이 달라도 받아 적용할 수 있다.

주문 6을 `paid`로 바꾼 트랜잭션 하나를 `mysqlbinlog`로 풀어 보면 이렇다.

```bash
# 행 이벤트를 읽을 수 있는 형태로 푼다
mysqlbinlog -vv --base64-output=DECODE-ROWS /var/lib/mysql/binlog.000001
```

```text
#261021 18:42:06 server id 1  end_log_pos 24106960 CRC32 0x30da12c4 	GTID	last_committed=12	sequence_number=13	rbr_only=yes	original_committed_timestamp=1792608126621014	immediate_commit_timestamp=1792608126621014	transaction_length=345
SET @@SESSION.GTID_NEXT= 'e9e49837-cd4b-11f1-a341-02fc00000001:13'/*!*/;
BEGIN
#261021 18:42:06 server id 1  end_log_pos 24107106 CRC32 0x723f277a 	Table_map: `shop`.`orders` mapped to number 148
#261021 18:42:06 server id 1  end_log_pos 24107195 CRC32 0xbe0a10a1 	Update_rows: table id 148 flags: STMT_END_F
### UPDATE `shop`.`orders`
### WHERE
###   @1=6 /* LONGINT meta=0 nullable=0 is_null=0 */
###   @2=20 /* LONGINT meta=0 nullable=0 is_null=0 */
###   @3=7000 /* INT meta=0 nullable=0 is_null=0 */
###   @4='ready' /* VARSTRING(40) meta=40 nullable=0 is_null=0 */
### SET
###   @1=6 /* LONGINT meta=0 nullable=0 is_null=0 */
###   @2=20 /* LONGINT meta=0 nullable=0 is_null=0 */
###   @3=7000 /* INT meta=0 nullable=0 is_null=0 */
###   @4='paid' /* VARSTRING(40) meta=40 nullable=0 is_null=0 */
#261021 18:42:06 server id 1  end_log_pos 24107226 CRC32 0x2c9fc8ce 	Xid = 58
COMMIT/*!*/;
```

트랜잭션 하나가 GTID 이벤트, `BEGIN`, 테이블 맵, 행 이벤트, `Xid`(커밋) 순으로 적혀 있다. `### WHERE` 아래가 바뀌기 전 행 전체, `### SET` 아래가 바뀐 뒤 행 전체다. 열 이름 대신 `@1`, `@2`처럼 위치로 적혀 있다는 점도 눈여겨본다. 레플리카의 테이블 열 순서가 다르면 엉뚱한 열에 들어간다. GTID 줄의 `last_committed`와 `sequence_number`는 뒤에서 볼 병렬 적용에 쓰인다.

이 형식이 `binlog_format = ROW`(5.7.7부터 기본값)다. 다른 형식도 있다. `STATEMENT`는 SQL 문장을 그대로 적는다. binlog가 작지만, 실행할 때마다 결과가 달라질 수 있는 문장은 레플리카에서 다른 행을 바꾼다.

```sql
SET SESSION binlog_format = 'STATEMENT';
UPDATE orders SET status = 'hold' WHERE status = 'ready' LIMIT 1;
SHOW WARNINGS\G
```

```text
Query OK, 1 row affected, 1 warning (0.01 sec)
Rows matched: 1  Changed: 1  Warnings: 1

  Level: Note
   Code: 1592
Message: Unsafe statement written to the binary log using statement format since BINLOG_FORMAT = STATEMENT. The statement is unsafe because it uses a LIMIT clause. This is unsafe because the set of rows included cannot be predicted.
```

`ORDER BY` 없는 `LIMIT 1`은 어느 행이 걸릴지 정해져 있지 않다. 프라이머리와 레플리카가 서로 다른 행을 `hold`로 바꾸면 두 서버의 데이터가 조용히 갈라진다. `UUID()`, `SYSDATE()` 같은 함수도 같은 문제가 있다. `MIXED`는 평소에는 문장으로 적다가 이런 위험한 문장만 행으로 적는다. 실무에서는 `ROW`를 쓰고, 위의 `SET SESSION binlog_format` 자체도 8.0.34부터 경고(`'@@binlog_format' is deprecated`)가 나온다. 앞으로는 `ROW`만 남는 방향이다.

`ROW`의 약점은 크기다. `UPDATE orders_big SET amount = 0` 한 문장이 100만 행의 전후 값을 모두 binlog에 쓴다. `binlog_row_image = MINIMAL`로 바꾸면 기본 키와 바뀐 열만 적어서 줄어든다. 대신 binlog를 읽어 변경을 다른 시스템으로 흘리는 CDC 도구나 gh-ost는 보통 `FULL`(기본값)을 요구한다. 대량 변경은 binlog 크기와 레플리카 지연을 함께 키우니 잘게 나눠서 돌린다.

## 레플리카 안의 받는 스레드와 적용하는 스레드

레플리카 안에서는 일이 두 단계로 나뉜다. 받는 스레드(receiver, 예전 이름은 IO thread)가 프라이머리의 dump 스레드에서 binlog를 받아 레플리카의 relay log 파일에 그대로 쓴다. 적용 스레드(applier, 예전 이름은 SQL thread)가 relay log를 읽어 실행한다. 8.0.27부터는 적용 쪽이 코디네이터 하나와 워커 여러 개(`replica_parallel_workers = 4`가 기본)로 나뉜다.

```sql
-- 레플리카에서
SELECT id, user, command, state
FROM information_schema.processlist
WHERE user = 'system user' ORDER BY id;
```

```text
+----+-------------+---------+----------------------------------------------------------+
| id | user        | command | state                                                    |
+----+-------------+---------+----------------------------------------------------------+
| 10 | system user | Connect | Waiting for source to send event                         |
| 11 | system user | Query   | Replica has read all relay log; waiting for more updates |
| 12 | system user | Query   | Waiting for an event from Coordinator                    |
| 13 | system user | Connect | Waiting for an event from Coordinator                    |
| 14 | system user | Connect | Waiting for an event from Coordinator                    |
| 15 | system user | Connect | Waiting for an event from Coordinator                    |
+----+-------------+---------+----------------------------------------------------------+
```

10번이 받는 스레드, 11번이 코디네이터, 12~15번이 워커 넷이다. 아래 그림에서 다음을 누르면 커밋 하나가 이 경로를 따라간다.

지연이 생길 때 어느 쪽인지 가르는 법은 간단하다. `Retrieved_Gtid_Set`(받은 것)이 프라이머리의 `gtid_executed`를 따라가는데 `Executed_Gtid_Set`(적용한 것)만 뒤처지면 적용 쪽 문제다. 큰 트랜잭션, 레플리카의 느린 디스크, 레플리카에서 도는 무거운 읽기 쿼리, 기본 키 없는 테이블(행 이벤트 하나마다 전체 스캔을 한다)을 의심한다. 받은 것부터 뒤처지면 네트워크나 프라이머리 쪽이다.

병렬 적용은 프라이머리에서 동시에 커밋 준비가 된 트랜잭션끼리는 서로 겹치지 않는다는 표시(`last_committed`, `sequence_number`)를 보고 워커에게 나눈다. `replica_preserve_commit_order = ON`(8.0.27부터 기본)이라 커밋 순서는 프라이머리와 같게 맞춘다. 8.0에서는 `binlog_transaction_dependency_tracking`을 `WRITESET`으로 바꾸면 건드린 행이 겹치지 않는 트랜잭션까지 병렬로 돌릴 수 있고, 8.4에서는 이 방식이 기본이 됐다(정확한 기본값은 버전 문서로 확인한다). 어떤 설정이든 DDL 하나, 거대한 트랜잭션 하나는 쪼갤 수 없다. 처음 장면의 ALTER가 그런 경우다.

## GTID는 트랜잭션마다 붙는 주소다

GTID(Global Transaction ID)는 `서버UUID:번호` 꼴의 트랜잭션 이름이다. 위 binlog의 `e9e49837-…:13`은 그 서버가 만든 13번째 트랜잭션이다. 각 서버는 지금까지 적용한 GTID 집합(`gtid_executed`)을 들고 있고, 레플리카는 프라이머리에 "나는 이 집합까지 있다"고 말하고 나머지만 받는다. 이게 `SOURCE_AUTO_POSITION = 1`이다.

GTID가 없던 시절에는 "binlog.000123 파일의 4567890 바이트부터"처럼 위치로 이어 받았다. 프라이머리가 죽고 레플리카 B가 새 프라이머리가 되면, 다른 레플리카 C는 B의 binlog 어디부터 받아야 하는지 사람이 계산해야 했다. 파일 이름도 위치도 서버마다 다르기 때문이다. GTID에서는 C가 B에게 자기 집합을 말하면 끝난다.

  solution={`function gtidSubtract(a, b) {
  const parse = (s) => {
    const m = {};
    for (const part of s.split(",").map((x) => x.trim()).filter(Boolean)) {
      const [uuid, ...ranges] = part.split(":");
      m[uuid] = m[uuid] || [];
      for (const r of ranges) {
        const [lo, hi] = r.split("-").map(Number);
        m[uuid].push([lo, hi ?? lo]);
      }
    }
    return m;
  };
  const A = parse(a), B = parse(b);
  const out = [];
  for (const uuid of Object.keys(A)) {
    let cur = A[uuid].slice().sort((x, y) => x[0] - y[0]);
    for (const [blo, bhi] of B[uuid] || []) {
      const next = [];
      for (const [lo, hi] of cur) {
        if (bhi < lo || blo > hi) { next.push([lo, hi]); continue; }
        if (blo > lo) next.push([lo, blo - 1]);
        if (bhi < hi) next.push([bhi + 1, hi]);
      }
      cur = next;
    }
    if (cur.length) {
      out.push(uuid + ":" + cur.map(([lo, hi]) => (lo === hi ? String(lo) : lo + "-" + hi)).join(":"));
    }
  }
  return out.join(",");
}`}

## 레플리카에 직접 쓴 한 줄이 복제를 멈춘다

레플리카는 `super_read_only`로 막아 두었다. 그래서 실수로 쓰면 이렇게 거절된다.

```text
ERROR 1290 (HY000) at line 1: The MySQL server is running with the --super-read-only option so it cannot execute this statement
```

급한 데이터 수정을 하려고 이 설정을 잠깐 끄고 레플리카에 주문 한 줄을 넣었다고 해 보자. 그 트랜잭션은 레플리카 자신의 UUID로 GTID를 받는다.

```sql
-- 레플리카에서 (하면 안 되는 일)
SET GLOBAL super_read_only = OFF;
INSERT INTO orders (user_id, amount, status) VALUES (30, 1000, 'ready');   -- id 7
SET GLOBAL super_read_only = ON;

-- 레플리카의 집합에서 프라이머리의 집합을 뺀다
SELECT GTID_SUBTRACT(@@global.gtid_executed, '<프라이머리의 gtid_executed>') AS errant;
```

```text
+----------------------------------------+
| errant                                 |
+----------------------------------------+
| cc823d06-cd7e-11f1-a3e4-02fc00000001:1 |
+----------------------------------------+
```

프라이머리에는 없고 레플리카에만 있는 이런 트랜잭션을 errant transaction이라고 부른다. 피해는 두 가지로 온다. 먼저 지금 당장, 프라이머리에서 다음 주문이 들어오면 같은 id 7을 받는다.

```text
           Replica_IO_Running: Yes
          Replica_SQL_Running: No
        Seconds_Behind_Source: NULL
               Last_SQL_Errno: 1062

-- performance_schema.replication_applier_status_by_worker
last_error_message: Worker 1 failed executing transaction 'e9e49837-cd4b-11f1-a341-02fc00000001:16' at source log binlog.000001, end_log_pos 24108200; Could not execute Write_rows event on table shop.orders; Duplicate entry '7' for key 'orders.PRIMARY', Error_code: 1062; handler error HA_ERR_FOUND_DUPP_KEY; the event's source log binlog.000001, end_log_pos 24108200
```

적용 스레드가 멈췄다(`Replica_SQL_Running: No`). 받는 스레드는 계속 받으니 relay log만 쌓이고, 레플리카의 데이터는 그 시점에 멈춘다. `SHOW REPLICA STATUS`의 `Last_SQL_Error`는 "워커에서 에러가 났다"까지만 말하고, 진짜 이유는 `replication_applier_status_by_worker`에 있다.

두 번째 피해는 나중에 온다. 이 레플리카가 장애 조치로 프라이머리가 되면, 다른 레플리카들이 AUTO_POSITION으로 붙으면서 이 GTID를 받아 간다. 오래전에 지워진 binlog에 있던 errant GTID라면 다른 레플리카가 붙지도 못한다.

이번에는 레플리카의 엉뚱한 행을 binlog 없이 지우고, 프라이머리에 같은 GTID로 빈 트랜잭션을 넣어 "이 GTID는 이미 있다"고 표시해서 정리했다.

```sql
-- 레플리카: 엉뚱한 행을 binlog에 남기지 않고 지운 뒤 적용을 다시 시작
SET GLOBAL super_read_only = OFF;
SET SESSION sql_log_bin = 0;
DELETE FROM orders WHERE id = 7;
SET GLOBAL super_read_only = ON;
START REPLICA SQL_THREAD;

-- 프라이머리: errant GTID를 빈 트랜잭션으로 채워 둔다
SET GTID_NEXT = 'cc823d06-cd7e-11f1-a3e4-02fc00000001:1';
BEGIN; COMMIT;
SET GTID_NEXT = 'AUTOMATIC';
```

```text
-- 이후 두 서버의 gtid_executed가 같아졌다
cc823d06-cd7e-11f1-a3e4-02fc00000001:1,
e9e49837-cd4b-11f1-a341-02fc00000001:1-16
```

데이터가 실제로 달라졌을 때는 이걸로 끝이 아니다. 어느 쪽이 맞는지 확인하고, 필요하면 pt-table-checksum 같은 도구로 전체를 비교한다. 예방이 훨씬 싸다. 레플리카에는 항상 `super_read_only = ON`을 걸고, 앱의 쓰기 연결이 레플리카로 가지 않게 연결 설정을 분리한다.

## 반동기 복제는 기다리다 혼자 비동기로 내려간다

지금까지는 비동기 복제다. 프라이머리는 커밋을 binlog에 쓰면 바로 앱에 OK를 준다. 그 직후 프라이머리가 디스크째 사라지면, 아직 레플리카로 가지 않은 커밋은 앱이 성공으로 알고 있는데도 없어진다.

반동기(semi-synchronous) 복제는 레플리카 한 대 이상이 "받아서 relay log에 썼다"고 답할 때까지 앱에 OK를 미룬다. 플러그인으로 켠다(8.0.26부터 이름이 `rpl_semi_sync_source` / `rpl_semi_sync_replica`).

```sql
-- 프라이머리
INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';
SET GLOBAL rpl_semi_sync_source_enabled = 1;
SET GLOBAL rpl_semi_sync_source_timeout = 3000;   -- 기본 10000ms, 실험을 위해 3초로

-- 레플리카 (적용 후 받는 스레드를 다시 시작해야 반동기로 붙는다)
INSTALL PLUGIN rpl_semi_sync_replica SONAME 'semisync_replica.so';
SET GLOBAL rpl_semi_sync_replica_enabled = 1;
STOP REPLICA IO_THREAD; START REPLICA IO_THREAD;
```

기다리는 지점은 `rpl_semi_sync_source_wait_point`로 정하고 기본값은 `AFTER_SYNC`다. binlog를 디스크에 쓴 뒤, InnoDB에 커밋하기 전에 기다린다. 그래서 레플리카가 받기 전에는 다른 세션도 이 변경을 볼 수 없다. 예전 방식 `AFTER_COMMIT`은 InnoDB 커밋 뒤에 기다려서, 다른 세션은 이미 본 데이터가 장애 조치 뒤에 사라질 수 있었다.

```text

Query OK, 1 row affected (0.01 sec)

-- STOP REPLICA IO_THREAD 뒤
INSERT INTO orders (user_id, amount, status) VALUES (20, 3700, 'ready')
Query OK, 1 row affected (3.00 sec)
```

```text
+------------------------------+-------+
| Variable_name                | Value |
+------------------------------+-------+
| Rpl_semi_sync_source_no_tx   | 1     |
| Rpl_semi_sync_source_status  | OFF   |
+------------------------------+-------+

[Warning] [MY-011153] [Repl] Timeout waiting for reply of binlog (file: binlog.000001, pos: 24111090), semi-sync up to file binlog.000001, position 24110781.
[Note] [MY-011155] [Repl] Semi-sync replication switched OFF.
```

두 번째 커밋이 정확히 timeout만큼(3.00초) 기다렸고, 에러 없이 성공했다. 그리고 `Rpl_semi_sync_source_status`가 `OFF`가 됐다. 이 순간부터는 비동기다. `no_tx`는 레플리카의 답 없이 커밋된 트랜잭션 수다. 받는 스레드를 다시 켜고 레플리카가 따라잡자 에러 로그에 `Semi-sync replication switched ON`이 찍히고 상태가 `ON`으로 돌아왔다.

그래서 반동기 복제는 "데이터를 절대 잃지 않는다"가 아니다. 레플리카가 살아 있고 timeout 안에 답하는 동안만 지켜 준다. `Rpl_semi_sync_source_status`가 `OFF`인 동안은 비동기와 같으니 이 값에 알림을 건다. 커밋마다 레플리카까지 왕복 한 번이 더해지니, 레플리카는 같은 리전의 가까운 존에 둔다. 여러 대 중 몇 대의 답을 기다릴지는 `rpl_semi_sync_source_wait_for_replica_count`(기본 1)로 정한다. 장애 조치까지 자동으로 묶고 싶으면 Group Replication(InnoDB Cluster)처럼 합의 기반 방식으로 넘어간다.

## Seconds_Behind_Source가 말해 주지 않는 것

`Seconds_Behind_Source`는 "지금 적용 중인 이벤트가 프라이머리에서 언제 만들어졌나"와 현재 시각의 차이다. 그래서 처음 장면처럼 9초짜리 DDL을 받는 순간 0에서 9로 뛴다. 이 정의에서 몇 가지 함정이 나온다.

적용 스레드가 멈추면 `NULL`이 된다. 앞의 중복 키 에러 때도 그랬다. 알림 규칙을 "값이 30보다 크면"으로만 걸어 두면 `NULL`은 숫자 비교에서 빠져서, 복제가 완전히 멈춘 가장 나쁜 상황에 알림이 울리지 않는다.

적용할 것이 relay log에 없으면 0이다. 받는 스레드가 네트워크 문제로 프라이머리에서 한참 뒤처져 있어도, 받은 것을 다 적용했다면 0으로 보일 수 있다. 숫자는 레플리카가 이미 받은 것 기준이다.

실제로 확인할 때는 프라이머리가 1초마다 현재 시각을 쓰는 하트비트 테이블을 두고, 레플리카에서 그 값과 현재 시각을 비교한다. pt-heartbeat가 이 방식이다. 레플리카의 적용 스레드를 6초 동안 멈추고 둘을 나란히 찍었다.

```sql
-- 프라이머리: 1초마다
UPDATE heartbeat SET ts = NOW(6) WHERE id = 1;

-- 레플리카: 실제로 몇 초 전 데이터를 보고 있나
SELECT ROUND(TIMESTAMPDIFF(MICROSECOND, ts, NOW(6)) / 1e6, 1) AS lag_s FROM heartbeat WHERE id = 1;
```

```text
18:44:53 SQL thread stopped
18:44:53 Seconds_Behind_Source=NULL heartbeat_lag_s=1
18:44:55 Seconds_Behind_Source=NULL heartbeat_lag_s=3.1
18:44:57 Seconds_Behind_Source=NULL heartbeat_lag_s=5.1
18:44:58 Seconds_Behind_Source=NULL heartbeat_lag_s=6.1
18:44:59 SQL thread started
18:45:00 Seconds_Behind_Source=0 heartbeat_lag_s=0.8
```

하트비트는 멈춘 동안에도 "6초 전 데이터"라고 정확히 말한다. 1초마다 쓰니 평소에도 0~1초 사이 값이 나오는 건 감안한다. 하트비트는 두 서버의 시계가 맞아야 의미가 있으니 NTP를 확인한다. 8.0에서는 `performance_schema.replication_applier_status_by_worker`의 `LAST_APPLIED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP`와 `..._END_APPLY_TIMESTAMP`로 트랜잭션별 지연을 계산할 수도 있다. 운영에서는 이 숫자와 함께 `Replica_IO_Running`, `Replica_SQL_Running`을 각각 감시한다.

## 방금 쓴 주문을 레플리카에서 읽으려면

복제가 늦으면 처음 장면처럼 "방금 쓴 것이 안 보이는" 일이 생긴다. 쓴 사용자에게는 일정 시간 프라이머리에서 읽게 하는 방법, 세션에 마지막 쓰기 시각을 기억하는 방법 같은 일반적인 해법은 [복제 글](/posts/db-replication-sharding)에 정리돼 있다. MySQL은 GTID 덕분에 더 정확한 방법이 있다. 쓴 트랜잭션의 GTID를 받아 두고, 레플리카에서 읽기 전에 그 GTID가 적용될 때까지 기다린다.

```sql
-- 프라이머리: 자기 트랜잭션의 GTID를 OK 응답에 실어 달라고 한다
SET SESSION session_track_gtids = OWN_GTID;
INSERT INTO orders (user_id, amount, status) VALUES (10, 9900, 'ready');
-- 드라이버가 지원하면 OK 패킷에서 'e9e49837-…:43'을 꺼낼 수 있다

-- 레플리카: 그 GTID가 적용될 때까지 최대 2초 기다린다
SELECT WAIT_FOR_EXECUTED_GTID_SET('e9e49837-cd4b-11f1-a341-02fc00000001:1-43', 2) AS waited;
```

적용 스레드를 멈춰 둔 상태와 다시 켠 상태에서 각각 실행했다.

```text
-- 적용이 멈춘 레플리카: 2초 기다리고 1(시간 초과)
+--------+
| waited |
+--------+
|      1 |
+--------+
1 row in set (2.00 sec)

-- 적용 중인 레플리카: 바로 0(적용됨)
+--------+
| waited |
+--------+
|      0 |
+--------+
1 row in set (0.00 sec)
```

0이면 그 레플리카에서 읽어도 방금 쓴 주문이 보인다. 1이면 프라이머리로 읽기를 돌리거나 다른 레플리카를 시도한다. 기다리는 시간이 곧 사용자 응답 시간이니 timeout은 짧게 잡는다. ProxySQL처럼 이 GTID 추적을 프록시가 대신 해 주는 구성도 있다. 모든 읽기에 이걸 붙이면 레플리카를 둔 의미가 줄어드니, 결제 직후 주문 상세처럼 "방금 쓴 것"을 읽는 화면에만 쓴다.

## ALTER TABLE은 세 가지 방식으로 돈다

이제 처음 장면의 다른 절반, 스키마 변경이다. InnoDB의 `ALTER TABLE`은 세 방식 중 하나로 돈다. 개념은 [무중단 스키마 변경 글의 MySQL 절](/posts/zero-downtime-migrations#mysql은-어떻게-다른가)에 있으니 여기서는 100만 행 `orders_big`에서 실제 시간과 에러를 본다.

```sql
-- 1) 맨 뒤에 열 추가: 메타데이터만 바꾼다
ALTER TABLE orders_big ADD COLUMN coupon VARCHAR(20) NULL, ALGORITHM=INSTANT;

-- 2) 열 타입 변경을 INSTANT, INPLACE로 시도
ALTER TABLE orders_big MODIFY amount BIGINT NOT NULL, ALGORITHM=INSTANT;
ALTER TABLE orders_big MODIFY amount BIGINT NOT NULL, ALGORITHM=INPLACE, LOCK=NONE;

-- 3) 보조 인덱스 추가: 테이블을 복사하지 않고, 도는 동안 쓰기를 허용
ALTER TABLE orders_big ADD INDEX idx_amount (amount), ALGORITHM=INPLACE, LOCK=NONE;

-- 4) 열 타입 변경: 새 테이블로 복사
ALTER TABLE orders_big MODIFY amount BIGINT NOT NULL, ALGORITHM=COPY;
```

```text
-- 1) INSTANT
Query OK, 0 rows affected (0.12 sec)

-- 2) 지원하지 않는 방식은 에러로 거절된다
ERROR 1846 (0A000): ALGORITHM=INSTANT is not supported. Reason: Need to rebuild the table to change column type. Try ALGORITHM=COPY/INPLACE.
ERROR 1846 (0A000): ALGORITHM=INPLACE is not supported. Reason: Cannot change column type INPLACE. Try ALGORITHM=COPY.

-- 3) INPLACE 인덱스 추가, 1.5초 뒤 다른 세션의 INSERT
   다른 세션: Query OK, 1 row affected (0.01 sec)
Query OK, 0 rows affected (2.22 sec)

-- 4) COPY, 1.5초 뒤 다른 세션의 INSERT
Query OK, 1000001 rows affected (13.31 sec)
   다른 세션: Query OK, 1 row affected (11.81 sec)
```

세 방식의 차이가 숫자로 보인다. INSTANT는 행 수와 상관없이 0.12초다. INPLACE 인덱스 추가는 2.22초가 걸렸지만 도중에 들어온 `INSERT`는 0.01초에 끝났다. COPY는 13.31초 동안 쓰기를 막았고, 1.5초에 들어온 `INSERT`가 11.81초를 기다렸다. 이게 API 타임아웃으로 나타난다.

`ALGORITHM`을 적어 두는 이유가 2)번이다. 적어 두면 원하는 방식이 불가능할 때 에러로 멈춘다. 적지 않으면 MySQL은 가능한 가장 빠른 방식을 고르고, 그게 COPY여도 말없이 진행한다.

INSTANT에도 한계가 있다. 8.0.29부터 아무 위치에 열을 추가하고 열을 지우는 것도 INSTANT로 되는데, 테이블마다 이런 행 형식 변경을 64번까지만 쌓을 수 있다. 작은 테이블에서 열 추가와 삭제를 번갈아 반복했다.

```text
add 33: ERROR 4092 (HY000): Maximum row versions reached for table shop/t_instant. No more columns can be added or dropped instantly. Please use COPY/INPLACE.

+----------------+--------------------+
| name           | total_row_versions |
+----------------+--------------------+
| shop/t_instant |                 64 |
+----------------+--------------------+
```

`information_schema.innodb_tables`의 `total_row_versions`가 64에 닿으면 더는 INSTANT가 안 된다. 이때 `ALGORITHM` 없이 `ADD COLUMN`을 하면 조용히 테이블을 다시 만들고 버전을 0으로 되돌린다. 작은 테이블이라 0.04초였지만 큰 테이블이라면 COPY와 같은 시간이 걸린다. 마이그레이션 도구로 열을 자주 붙였다 떼는 테이블이라면 배포 전에 이 값을 확인한다.

그리고 어떤 방식이든 복제는 처음 장면처럼 간다. INPLACE든 COPY든 프라이머리에서 끝난 뒤 레플리카에서 같은 시간을 다시 쓰고, 그동안 뒤의 트랜잭션은 줄을 선다. 프라이머리에서 쓰기를 막지 않는 INPLACE라도 레플리카 지연은 피하지 못한다.

## 열 추가도 줄을 서서 기다린다

INSTANT는 0.12초면 끝나니 아무 때나 돌려도 될까. 아니다. 모든 `ALTER TABLE`은 시작이나 끝에 그 테이블의 메타데이터 잠금(MDL)을 배타적으로 잡는다. 일반 `SELECT`도 테이블을 읽는 동안, 트랜잭션 안이라면 트랜잭션이 끝날 때까지 공유 MDL을 쥔다. 세 세션으로 재현했다.

```sql
-- A: 트랜잭션을 열고 orders를 읽은 채 멈춰 있다 (앱이 커밋을 잊었다)
START TRANSACTION;
SELECT COUNT(*) FROM orders;

-- B: 열 하나 추가 (INSTANT)
ALTER TABLE orders ADD COLUMN memo VARCHAR(50) NULL, ALGORITHM=INSTANT;

-- C: 평범한 조회
SELECT * FROM orders WHERE id = 1;
```

```text
+-----+---------+------+---------------------------------+--------------------------------------------------------------+
| id  | command | time | state                           | info                                                         |
+-----+---------+------+---------------------------------+--------------------------------------------------------------+
| 147 | Sleep   |    2 |                                 | NULL                                                         |
| 148 | Query   |    2 | Waiting for table metadata lock | ALTER TABLE orders ADD COLUMN memo VARCHAR(50) NULL, ALGORIT |
| 149 | Query   |    1 | Waiting for table metadata lock | SELECT * FROM orders WHERE id = 1                            |
+-----+---------+------+---------------------------------+--------------------------------------------------------------+
```

A(147)는 `Sleep`이라 아무 일도 안 하는 것처럼 보인다. B(148)는 A의 공유 MDL이 풀리기를 기다리고, C(149)는 A와는 충돌하지 않는데도 B 뒤에 줄을 섰다. 배타 잠금을 기다리는 요청이 있으면 그 뒤의 공유 잠금 요청도 기다리게 해서 B가 영원히 굶지 않게 하는 규칙 때문이다. 운영에서는 C 같은 쿼리가 초당 수백 개 쌓이고 커넥션 풀이 바닥난다.

누가 막고 있는지는 `sys.schema_table_lock_waits`가 보여 준다.

```text
               object_name: orders
               waiting_pid: 154
         waiting_lock_type: EXCLUSIVE
             waiting_query: ALTER TABLE orders ADD COLUMN  ... AR(50) NULL, ALGORITHM=INSTANT
              blocking_pid: 153
        blocking_lock_type: SHARED_READ

```

이 뷰는 기다리는 쪽과 쥔 쪽의 조합을 모두 늘어놓아서 줄이 여러 개 나온다. 가장 오래 쥐고 있는 pid(여기서는 153)를 찾는 게 먼저다. `information_schema.innodb_trx`에서 그 연결의 `trx_started`를 보면 얼마나 오래 열려 있었는지 알 수 있다.

해법은 ALTER 쪽이 먼저 물러나게 하는 것이다. MySQL의 `lock_wait_timeout` 기본값은 31,536,000초(1년)라서 사실상 무한히 기다린다. 마이그레이션 세션에서는 몇 초로 낮춘다.

```sql
SET SESSION lock_wait_timeout = 3;
ALTER TABLE orders ADD COLUMN memo VARCHAR(50) NULL, ALGORITHM=INSTANT;
```

```text
-- B
ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction
-- C: B가 물러나자 실행됐다
1 row in set (2.49 sec)
```

B는 3초 뒤 포기했고, 그 뒤에 서 있던 C가 바로 실행됐다. 마이그레이션 도구는 이렇게 짧게 실패하고 잠시 뒤 다시 시도하게 만든다. 그 전에 오래 열린 트랜잭션이 없는지(`innodb_trx`) 먼저 확인하는 게 더 좋다.

## 테이블을 복사해야 할 때는 gh-ost와 pt-osc

열 타입 변경처럼 COPY가 필요한 변경을 큰 테이블에 직접 돌리면, 프라이머리에서는 쓰기가 몇 시간 막히고 레플리카는 그만큼 뒤처진다. 그래서 테이블 복사를 MySQL에 맡기지 않고 도구가 조금씩 한다. 대표가 gh-ost와 pt-online-schema-change(pt-osc)다. 둘 다 이 글에서 직접 돌리지는 않았고, 공식 문서의 동작을 정리한다.

pt-osc는 같은 일을 트리거로 한다. 원래 테이블에 `INSERT`, `UPDATE`, `DELETE` 트리거를 걸어 변경을 새 테이블에도 쓰게 하고, 나머지는 같다. 트리거는 앱의 쓰기 트랜잭션 안에서 함께 돌아서 쓰기마다 비용이 붙고, 도중에 멈추거나 속도를 줄이기 어렵다. gh-ost는 binlog를 읽는 별도 프로세스라 쓰기 경로에 끼어들지 않고, 실행 중에 속도를 바꾸거나 멈출 수 있다. 대신 binlog를 읽을 권한과 ROW 형식이 필요하고, 외래 키가 있는 테이블은 지원하지 않는다. pt-osc도 외래 키는 별도 옵션으로 조심스럽게 다뤄야 한다.

두 도구의 공통점이 중요하다. 복사가 행 묶음 단위의 작은 트랜잭션들이라 레플리카도 따라오면서 같이 진행한다. 처음 장면처럼 레플리카가 거대한 DDL 하나를 붙잡고 있는 일이 없고, 지연이 기준(`--max-lag-millis` 같은 옵션)을 넘으면 도구가 스스로 쉰다. 대가는 시간과 공간이다. 테이블이 잠시 두 벌 있으니 디스크가 그만큼 필요하고, 원래 COPY보다 몇 배 오래 걸린다.

## 큰 스키마 변경 전에 확인하는 순서

지금까지 본 것을 배포 전 점검으로 묶으면 이렇다.

1. 원하는 변경이 INSTANT로 되는지 `ALGORITHM=INSTANT`를 붙여 스테이징에서 먼저 돌려 본다. 에러가 나면 INPLACE, 그것도 안 되면 COPY 대상이다. INSTANT라면 `total_row_versions`도 본다.
2. INPLACE나 COPY라면 테이블 크기와 스테이징 소요 시간으로 레플리카 지연을 예상한다. 몇 분을 넘길 것 같으면 gh-ost나 pt-osc로 돌린다.
3. 직전에 `information_schema.innodb_trx`에서 오래 열린 트랜잭션이 없는지 보고, 마이그레이션 세션에 `SET SESSION lock_wait_timeout = 3`처럼 짧은 값을 건다.
4. 도는 동안 레플리카의 하트비트 지연과 `Replica_SQL_Running`, 프라이머리의 `Waiting for table metadata lock` 개수를 지켜본다.
5. 읽기를 레플리카로 보내는 서비스라면, 지연이 길어지는 동안 쓴 사용자에게 보여 줄 화면이 어디서 읽는지 미리 정해 둔다.

## 복제는 binlog를 따라 하는 일이고 DDL도 그 줄에 선다

처음 장면을 다시 읽으면, 9초짜리 ALTER는 끝난 뒤에야 binlog에 실렸고 레플리카는 그걸 처음부터 다시 돌리는 동안 뒤의 주문을 적용하지 못했다. `Seconds_Behind_Source`가 0에서 9로 뛴 건 이벤트에 시작 시각이 적히기 때문이다. 복제를 안다는 건 binlog에 무엇이 어떤 순서로 적히고, 레플리카가 그걸 어떤 스레드로 받아 적용하며, 그 줄이 어디서 막히는지를 아는 일이다. 그 위에 GTID로 위치를 잃지 않고, 반동기로 잃을 수 있는 범위를 줄이고, 큰 DDL은 레플리카가 함께 따라올 수 있는 작은 조각으로 나눈다.

## 면접에서 나올 만한 질문

### MySQL 복제는 어떤 순서로 동작하나

프라이머리가 커밋하면 변경이 binlog에 기록되고, dump 스레드가 레플리카로 보낸다. 레플리카의 받는 스레드가 그걸 relay log에 쓰고, 적용 스레드(8.0.27부터는 코디네이터와 워커 4개)가 relay log를 읽어 실행한다. 기본은 비동기라서 프라이머리는 레플리카를 기다리지 않고 앱에 응답한다. 받은 것은 `Retrieved_Gtid_Set`, 적용한 것은 `Executed_Gtid_Set`으로 구분해서 본다.

### binlog 형식 STATEMENT, ROW, MIXED의 차이와 무엇을 쓰나

STATEMENT는 SQL 문장을, ROW는 바뀐 행의 전후 값을, MIXED는 평소엔 문장을 쓰다 위험한 문장만 행으로 적는다. STATEMENT는 작지만 `ORDER BY` 없는 `LIMIT`이나 `UUID()`처럼 결과가 정해지지 않은 문장에서 프라이머리와 레플리카의 데이터가 갈라질 수 있다. ROW가 5.7.7부터 기본이고 8.0.34부터 `binlog_format` 설정 자체가 폐기 예정이다. ROW는 대량 변경에서 binlog가 커지니 작업을 잘게 나누고 필요하면 `binlog_row_image=MINIMAL`을 검토한다.

### GTID를 쓰면 무엇이 좋아지나

트랜잭션마다 `서버UUID:번호`가 붙어서, 레플리카가 binlog 파일 이름과 위치 대신 "가진 GTID 집합"으로 이어 받는다. 장애 조치 뒤 다른 레플리카를 새 프라이머리에 붙일 때 위치 계산이 필요 없다. 레플리카에만 있는 errant GTID를 `GTID_SUBTRACT`로 찾을 수 있다는 것도 장점이다. 대신 레플리카에 직접 쓰면 errant 트랜잭션이 생겨 중복 키로 복제가 멈추거나 장애 조치가 꼬이니 `super_read_only`로 막는다.

### 반동기 복제를 켜면 데이터 유실이 없어지나

레플리카가 답하는 동안만 줄어든다. AFTER_SYNC 방식은 레플리카가 relay log에 썼다고 답할 때까지 InnoDB 커밋과 앱 응답을 미루니, 그사이 프라이머리가 죽어도 그 트랜잭션은 레플리카에 있다. 하지만 `rpl_semi_sync_source_timeout`(기본 10초) 안에 답이 없으면 에러 없이 비동기로 내려간다. 실험에서도 커밋 하나가 timeout만큼 기다린 뒤 성공했고 상태가 OFF가 됐다. 그래서 `Rpl_semi_sync_source_status`에 알림을 건다.

### Seconds_Behind_Source를 지연 지표로 쓸 때 주의할 점은

적용 중인 이벤트의 생성 시각과 현재 시각의 차이라서, 큰 DDL을 받는 순간 갑자기 뛰고 적용할 것이 없으면 받는 쪽이 늦어도 0이다. 적용 스레드가 멈추면 `NULL`이 되어 숫자 비교 알림에서 빠진다. 프라이머리가 1초마다 시각을 쓰는 하트비트 테이블을 레플리카에서 읽어 실제 지연을 재고, 두 스레드의 Running 상태를 따로 감시한다.

### 쓰자마자 레플리카에서 읽으면 안 보이는 문제를 MySQL에서는 어떻게 푸나

쓴 사용자의 읽기를 잠시 프라이머리로 보내는 일반적인 방법 외에, MySQL은 GTID로 정확하게 기다릴 수 있다. `session_track_gtids=OWN_GTID`로 커밋한 트랜잭션의 GTID를 받아 두고, 레플리카에서 `WAIT_FOR_EXECUTED_GTID_SET(gtid, timeout)`을 부른다. 0이면 적용된 것이고 1이면 시간 초과라 프라이머리로 돌린다. 기다리는 시간이 응답 시간이 되니 방금 쓴 데이터를 읽는 화면에만 쓴다.

### INSTANT, INPLACE, COPY의 차이와 ALGORITHM을 명시하는 이유는

INSTANT는 메타데이터만 바꿔 행 수와 무관하게 끝나고, INPLACE는 테이블을 복사하지 않고 작업하며 대개 쓰기를 허용하고, COPY는 새 테이블로 복사하는 동안 쓰기를 막는다. 실험에서 100만 행 기준 INSTANT 0.12초, INPLACE 인덱스 추가 2.22초(동시 INSERT 0.01초), COPY 13.31초(동시 INSERT 11.81초 대기)였다. `ALGORITHM`을 적으면 원하는 방식이 불가능할 때 에러로 멈추고, 안 적으면 말없이 COPY로 갈 수 있다. INSTANT 열 변경은 테이블당 64번까지라는 한계도 있다.

### 0.1초짜리 INSTANT ALTER가 서비스를 멈출 수 있는 이유는

모든 ALTER가 메타데이터 잠금을 배타적으로 잡아야 하는데, 커밋하지 않은 트랜잭션이 그 테이블의 공유 MDL을 쥐고 있으면 ALTER가 기다리고, 그 뒤의 일반 SELECT까지 모두 줄을 서기 때문이다. `lock_wait_timeout` 기본값이 1년이라 사실상 끝없이 기다린다. 마이그레이션 세션에 짧은 `lock_wait_timeout`을 걸고 재시도하게 만들고, 시작 전에 `innodb_trx`로 오래 열린 트랜잭션을 확인한다. 막는 쪽은 `sys.schema_table_lock_waits`로 찾는다.
