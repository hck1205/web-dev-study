<EasyIntro>
  새 버전을 내보냈는데 에러가 나면 가장 먼저 하는 일은 옛 버전으로 되돌리는 것, 롤백이다. 원인을 찾고 고치는 것보다 이미 잘 돌던 버전으로 돌아가는 편이 훨씬 빠르다. 그런데 되돌렸는데도 에러가 계속되는 일이 생긴다.

  컴퓨터로 편지를 쓰는 일과 비슷하다. 화면에 쓴 글자는 실행 취소로 지울 수 있지만, 이미 우체통에 넣은 편지는 돌아오지 않는다. 프로그램 코드는 화면 속 글자라 쉽게 돌아가지만, 새 버전이 바꿔 놓은 데이터 구조나 고객에게 이미 보낸 메일과 결제는 부친 편지다.

  그래서 되돌리기 버튼이 안전하려면 배포 전에 준비가 필요하다. 새 버전은 옛 버전과 함께 돌아가도록 데이터 구조를 더하기만 하고, 지우는 일은 한참 뒤로 미룬다. 부친 편지는 되돌리는 대신 정정 편지를 보내는 식으로 수습한다.

새 버전을 내보내고 10분 뒤 결제 에러가 오르기 시작했다. 망설임 없이 `kubectl rollout undo`를 쳤고, Pod는 1분 만에 옛 이미지로 돌아왔다. 그런데 에러가 줄지 않는다. 이번에는 다른 에러다. `column "amount" of relation "orders" does not exist`. 새 버전과 함께 나간 마이그레이션이 컬럼 이름을 바꿔 놓았고, 옛 코드는 그 컬럼을 찾고 있었다. 되돌리기 버튼은 코드만 되돌렸다.

롤백은 "이전 상태로 돌아가기"지만 시스템의 모든 부분이 같은 방식으로 돌아가지는 않는다. 코드는 쉽게 돌아가고, 설정은 기록이 있어야 돌아가고, 데이터와 바깥으로 나간 부작용은 돌아가지 않는다. 이 글은 무엇을 어떻게 되돌릴지, 되돌릴 수 없으면 무엇을 할지, 그리고 사람이 판단하기 전에 기계가 되돌리게 하는 방법을 다룬다. `rollout undo`의 리비전 동작과 두 번 치면 생기는 일은 [Deployment와 롤링 업데이트](/posts/k8s-deployment)와 [push에서 EKS까지 배포 파이프라인](/posts/k8s-deploy-pipeline-eks)에서, `helm rollback`은 [업그레이드와 롤백](/posts/helm-release-lifecycle)에서 다뤘다.

이 주제의 다른 글: [CI/CD의 뼈대](/posts/ci-cd-basics), [빌드 캐시](/posts/build-caching), [피처 플래그 운영](/posts/feature-flags).

실습은 Ubuntu 24.04에서 했다. 쿠버네티스는 kwok(v0.6.1) 가짜 클러스터와 kubectl 1.31.4, DB는 PostgreSQL 16.15다. kwok은 실제 컨테이너를 띄우지 않으므로 Pod가 Ready가 되는 시간은 실제 클러스터보다 훨씬 짧다.

## 롤백할까, 고쳐서 내보낼까

문제가 생긴 버전 앞에서 고를 수 있는 길은 둘이다. 롤백(rollback)은 마지막으로 잘 돌던 버전으로 돌아가는 것이고, 롤 포워드(roll forward)는 고친 새 버전을 앞으로 내보내는 것이다. 둘 다 목표는 같다. 사용자가 겪는 피해를 가장 빨리 멈추는 것이다.

롤백이 기본값이어야 하는 이유는 시간이다. 롤백은 이미 검증된 결과물을 다시 까는 일이라 몇 분이면 끝난다. 롤 포워드는 원인을 찾고, 고치고, 리뷰받고, 파이프라인을 다시 도는 시간이 다 들어간다. 원인을 정확히 모르는 상태에서 급하게 만든 수정은 두 번째 장애를 부르기도 한다. 그래서 흔한 규칙은 "원인을 찾기 전에 먼저 되돌린다"다.

롤 포워드를 고르는 경우도 분명히 있다. 롤백이 불가능하거나 더 위험할 때다. 되돌릴 버전이 바뀐 스키마나 메시지 형식을 견디지 못하면 롤백이 두 번째 장애가 된다. 버그가 이번 배포가 아니라 몇 주 전부터 있던 것이면 되돌려도 소용없다. 수정이 한 줄이고 파이프라인이 10분 안에 돈다면 고쳐서 내보내는 편이 빠를 수도 있다. 이때도 먼저 확인할 것은 "더 빠르게 피해를 멈추는 방법이 있나"다. [피처 플래그](/posts/feature-flags) 뒤에 숨겨 둔 기능이라면 플래그를 끄는 게 둘 다보다 빠르다.

코드와 이미지는 결과물이 남아 있으면 돌아간다. 이미지 태그를 커밋 SHA로 붙이고 레지스트리 수명 주기 정책이 옛 이미지를 너무 빨리 지우지 않게 해 두는 게 전제다. 설정은 git에 있거나 버전 기록이 있어야 돌아간다. 쿠버네티스의 ConfigMap과 Secret은 리비전 기록이 없어서 `rollout undo`가 되돌려 주지 않는다.

스키마부터는 조건부다. 컬럼을 더하기만 했다면 옛 코드는 새 컬럼을 무시하고 돌아간다. 이름을 바꾸거나 지웠다면 옛 코드는 돌아오자마자 실패한다. 그 아래는 되돌릴 수 없다. 새 버전이 새 형식으로 쓴 데이터, 고객에게 이미 나간 메일과 푸시, 결제 대행사에 이미 들어간 승인, 다른 팀의 큐로 이미 나간 메시지. 앱 스토어에 올라간 모바일 앱도 여기에 가깝다. 사용자 기기에 깔린 버전을 회수할 방법은 없어서, 서버는 옛 앱 버전을 계속 받아 줘야 한다.

이 경계를 알면 원칙 하나가 나온다. 모든 릴리스는 바로 이전 릴리스와 함께 돌아갈 수 있어야 한다. 새 코드는 옛 스키마를, 옛 코드는 새 스키마를 견딘다. 메시지 형식, 캐시에 저장된 객체의 직렬화 형식, 세션 쿠키 형식도 마찬가지다. 이걸 지키면 롤백은 언제나 안전한 선택지로 남는다.

## 롤백했더니 DB가 맞지 않는다

처음 장면을 PostgreSQL로 그대로 재현했다. v2 배포와 함께 `amount` 컬럼 이름을 `total_amount`로 바꾸는 마이그레이션이 나갔다.

```sql
CREATE TABLE orders (
  id         bigserial PRIMARY KEY,
  user_id    int NOT NULL,
  amount     int NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
INSERT INTO orders (user_id, amount) VALUES (1, 32000), (2, 15000), (3, 8900);

-- v2 배포와 함께 나간 마이그레이션: 이름을 바로 바꿨다
ALTER TABLE orders RENAME COLUMN amount TO total_amount;
-- v2 앱이 넣는 주문
INSERT INTO orders (user_id, total_amount) VALUES (4, 12000);
-- 앱만 v1로 롤백했다. v1은 여전히 amount에 쓴다
INSERT INTO orders (user_id, amount) VALUES (5, 9000);
```

```text
ERROR:  column "amount" of relation "orders" does not exist
LINE 1: INSERT INTO orders (user_id, amount) VALUES (5, 9000);
                                     ^
```

롤백한 v1이 주문을 한 건도 받지 못한다. 같은 변경을 두 단계로 나누면 결과가 다르다. 먼저 새 컬럼을 더하기만 하고(확장), 새 코드가 두 컬럼에 모두 쓰게 한다. 옛 컬럼은 모든 코드가 새 컬럼으로 옮겨 가고 롤백할 일이 없어진 뒤에 지운다(수축).

```sql
-- 확장(expand): 새 컬럼을 더하기만 한다. 옛 컬럼은 그대로 둔다
ALTER TABLE orders ADD COLUMN total_amount int;
UPDATE orders SET total_amount = amount WHERE total_amount IS NULL;
-- v2 앱: 두 컬럼에 모두 쓴다
INSERT INTO orders (user_id, amount, total_amount) VALUES (4, 12000, 12000);
-- 앱만 v1로 롤백: 옛 컬럼이 있으니 그대로 동작한다
INSERT INTO orders (user_id, amount) VALUES (5, 9000);
SELECT id, user_id, amount, total_amount FROM orders ORDER BY id;
```

```text
 id | user_id | amount | total_amount 
----+---------+--------+--------------
  1 |       1 |  32000 |        32000
  2 |       2 |  15000 |        15000
  3 |       3 |   8900 |         8900
  4 |       4 |  12000 |        12000
  5 |       5 |   9000 |             
```

롤백한 v1이 정상으로 주문을 받는다. 5번 행의 `total_amount`가 비어 있는 것을 보자. 롤백 중에 옛 코드가 쓴 행은 새 컬럼을 채우지 않는다. 그래서 다시 v2로 올라갈 때 빈 값을 채우는 백필을 한 번 더 돌리거나, 트리거로 두 컬럼을 맞춰 두는 장치가 필요하다. 이런 단계를 어떻게 쪼개고 언제 수축하는지는 [무중단 마이그레이션](/posts/zero-downtime-migrations)에서, 마이그레이션 도구의 버전 관리는 [DB 마이그레이션 도구](/posts/db-migration-tools)에서 다룬다.

## down 마이그레이션이 지우는 것

마이그레이션 도구 대부분은 up과 down을 짝으로 쓰게 한다. down은 롤백용으로 보이지만, 운영에서 down을 돌리는 것은 대개 데이터를 지우는 일이다. 선물 메시지 기능을 추가한 v2를 롤백하면서 down을 돌려 봤다.

```sql
-- v2에서 선물 메시지 기능을 추가했다
ALTER TABLE orders ADD COLUMN gift_message text;
UPDATE orders SET gift_message = '생일 축하해' WHERE id = 4;
INSERT INTO orders (user_id, amount, total_amount, gift_message) VALUES (6, 21000, 21000, '늦었지만 축하');
SELECT count(*) AS orders_with_gift FROM orders WHERE gift_message IS NOT NULL;
-- 롤백하면서 down 마이그레이션도 돌렸다
ALTER TABLE orders DROP COLUMN gift_message;
-- 문제를 고쳐 다시 v2로 올라가며 up 마이그레이션을 돌린다
ALTER TABLE orders ADD COLUMN gift_message text;
SELECT count(*) AS orders_with_gift FROM orders WHERE gift_message IS NOT NULL;
```

```text
 orders_with_gift 
------------------
                2

 orders_with_gift 
------------------
                0
```

v2가 떠 있던 동안 고객이 쓴 메시지 두 건이 사라졌다. 컬럼을 더한 마이그레이션은 옛 코드가 무시하면 그만이라 되돌릴 필요가 없다. 그래서 많은 팀이 운영에서는 down을 돌리지 않고, 스키마는 앞으로만 간다(forward-only)는 규칙을 둔다. 되돌려야 할 스키마 변경이 생기면 그 변경을 취소하는 새 마이그레이션을 리뷰를 거쳐 앞으로 내보낸다.

<Callout kind="warning" title="운영 DB에서 down을 돌리기 전에">
down 마이그레이션의 `DROP COLUMN`, `DROP TABLE`은 그 사이 쌓인 데이터를 함께 지우고, 트랜잭션이 끝나면 되돌릴 수 없다. 꼭 돌려야 한다면 먼저 해당 컬럼이나 테이블을 따로 덤프해 두고(`pg_dump -t orders --data-only`처럼), 시점 복구(PITR)가 가능한 백업이 있는지 확인한다. 복구는 덤프한 데이터를 다시 넣거나 백업에서 그 시점으로 복원하는 방법뿐이다.
</Callout>

## 큐에 남은 새 형식의 메시지

DB만 문제가 아니다. v2가 메시지 형식을 바꿔 큐에 넣었다면, 롤백한 v1 소비자는 큐에 남은 v2 메시지를 읽어야 한다. 금액을 숫자에서 `{ value, currency }` 객체로 바꾼 경우를 node로 흉내 냈다.

```js
// v1 소비자: amount를 숫자로 안다
function v1Consume(raw) {
  const m = JSON.parse(raw);
  const vat = Math.round(m.amount * 0.1);
  if (Number.isNaN(vat)) throw new Error(`order ${m.orderId}: amount is not a number`);
  return `order ${m.orderId}: vat=${vat}`;
}
```

```text
ok    order 101: vat=3200
fail  order 102: amount is not a number
fail  order 103: amount is not a number
```

검사 없이 계산했다면 실패 대신 `NaN`이 저장되는 더 나쁜 결과가 났을 것이다. 실패한 메시지는 재시도를 반복하다 [데드 레터 큐](/posts/dead-letter-queue)로 가고, 다시 v2를 올린 뒤 재처리해야 한다. 막는 방법은 스키마와 같다. 새 필드를 더하되 옛 필드를 남기거나(`amount`와 `amount_v2`를 같이 싣기), 메시지에 버전을 싣고 소비자를 먼저 배포해 두 형식을 모두 읽게 만든 뒤 생산자를 바꾼다. 소비자가 먼저, 생산자가 나중이다.

## 쿠버네티스에서 되돌리기

코드 층의 롤백은 도구가 해 준다. 쿠버네티스 Deployment는 Pod 템플릿이 바뀔 때마다 리비전을 남기고, `rollout undo`가 이전 템플릿으로 다시 롤링 업데이트를 한다. 실습 클러스터에 두 버전을 배포하고 기록을 봤다.

```bash
# 배포할 때마다 변경 이유를 annotation으로 남긴다
kubectl -n shop apply -f deploy.yaml
kubectl -n shop annotate deploy/order-api kubernetes.io/change-cause="1.8.0 정기 배포" --overwrite
kubectl -n shop set image deploy/order-api app=registry.example/order-api:1.9.0
kubectl -n shop annotate deploy/order-api kubernetes.io/change-cause="1.9.0 결제 금액 계산 변경" --overwrite
kubectl -n shop rollout history deploy/order-api
```

```text
deployment.apps/order-api 
REVISION  CHANGE-CAUSE
1         1.8.0 정기 배포
2         1.9.0 결제 금액 계산 변경
```

`CHANGE-CAUSE`가 비어 있으면 장애 중에 어느 리비전이 무엇이었는지 `rollout history --revision=N`으로 하나씩 열어 봐야 한다. 배포 스크립트에서 annotation을 남기는 습관이 그 시간을 줄인다. 되돌리는 명령의 조각을 보자.

## 사람보다 먼저 되돌리게 하기

사람이 알림을 받고, 노트북을 열고, 상황을 파악하고, 되돌리기로 결정하기까지 대개 10분은 넘게 걸린다. 배포 직후는 무엇이 바뀌었는지 분명한 유일한 순간이라, 이때 지표가 나빠지면 기계가 먼저 되돌리게 할 수 있다.

기준은 에러 예산을 태우는 속도(burn rate)로 잡는 게 흔하다. SLO가 99.9%면 허용되는 에러율은 0.1%다. 지금 에러율이 1%면 예산을 10배 속도로 쓰고 있는 것이다. 구글 SRE 워크북은 한 달 예산의 2%를 1시간 안에 태우는 속도, 즉 14.4배를 "바로 사람을 깨울 만한" 기준으로 든다. 개념은 [SLI와 SLO](/posts/sli-slo), [에러 예산](/posts/error-budgets)에서 자세히 다룬다.

배포 직후 지표를 보다가 기준을 넘으면 되돌리는 스크립트를 짜서 실습 클러스터에 돌렸다. 지표는 Prometheus 대신 호출할 때마다 지난 1분의 요청·에러 수를 돌려주는 가짜 서버에서 받았다. 한 번 튄 값에 반응하지 않도록 세 번 연속 넘어야 되돌린다.

```bash
# 배포 직후 burn rate를 보고 기준을 넘으면 직전 리비전으로 되돌린다
node auto-rollback.mjs
kubectl -n shop rollout history deploy/order-api
kubectl -n shop get deploy order-api -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
```


## 되돌리기가 실패하는 자리

롤백이 필요한 순간에 롤백이 안 되는 이유는 대개 미리 알 수 있는 것들이다.

되돌릴 이미지가 없다. 레지스트리 수명 주기 정책이 "최근 10개만 남김"인데 하루에 배포를 20번 하면 어제 버전은 이미 지워졌다. `revisionHistoryLimit`을 0으로 두면 쿠버네티스 쪽 기록도 없다. 이미지는 운영에 나간 적이 있는 것만이라도 넉넉히 보관한다.

설정이 같이 바뀌었다. 새 버전이 새 환경 변수를 요구해서 ConfigMap을 바꿨는데, 롤백은 Pod 템플릿만 되돌린다. 옛 코드가 바뀐 설정을 견디지 못하면 실패한다. 설정 이름에 내용 해시를 붙여 새 ConfigMap을 만드는 방식(`configMapGenerator`)이면 템플릿이 다른 ConfigMap을 가리키게 되어 롤백이 설정까지 같이 되돌린다.

캐시와 세션이 새 형식이다. v2가 Redis에 새 직렬화 형식으로 객체를 저장했다면, 롤백한 v1은 그 값을 읽다가 실패한다. 캐시 키에 형식 버전을 넣어 두면(`user:v2:42`) 옛 코드는 옛 키만 읽는다.

연습한 적이 없다. 롤백 절차를 장애 때 처음 해 보면 권한이 없거나, 명령을 모르거나, 스크립트가 낡아 있다. 스테이징에서 정기적으로 배포 직후 롤백을 실제로 해 보고 걸린 시간을 잰다. 그 시간이 [DORA 지표](/posts/ci-cd-basics)의 복구 시간을 정한다.

## 되돌릴 수 있게 만드는 것이 먼저다

롤백은 버튼 하나처럼 보이지만, 그 버튼이 안전하려면 배포 전에 정해 둘 것이 많다. 모든 릴리스가 이전 릴리스와 함께 돌아가도록 스키마는 확장부터, 메시지는 소비자부터 바꾼다. 운영에서 down 마이그레이션 대신 앞으로 가는 마이그레이션을 쓴다. 이미지와 설정의 기록을 남기고, 바깥으로 나가는 부작용은 플래그 뒤에 둔다. 그러면 장애 앞에서 "되돌릴까"는 고민이 아니라 기본값이 되고, 판단까지 기계에 맡길 수 있다. 실제 장애를 어떻게 지휘하고 기록하는지는 [장애 대응](/posts/production-incidents)과 [포스트모템](/posts/postmortems)으로 이어진다.

## 면접에서 나올 만한 질문

### 롤백과 롤 포워드 중 무엇을 먼저 고려하나요?

롤백을 먼저 고려한다. 이미 검증된 결과물로 돌아가는 일이라 몇 분이면 끝나고, 원인을 몰라도 피해를 멈출 수 있다. 롤 포워드는 원인 파악, 수정, 리뷰, 파이프라인 시간이 다 들어간다. 다만 스키마나 메시지 형식이 호환되지 않아 롤백이 더 위험하거나, 버그가 이번 배포 이전부터 있었다면 고쳐서 내보낸다. 플래그로 끌 수 있으면 그게 가장 빠르다.

### 배포 후 롤백할 수 없는 것에는 무엇이 있나요?

새 버전이 쓴 데이터와 바깥으로 나간 부작용이다. 고객에게 보낸 메일과 푸시, 결제 승인, 다른 시스템으로 나간 메시지, 지운 데이터, 사용자 기기에 깔린 모바일 앱 버전이 그렇다. 이런 것은 되돌리는 대신 정정 메일이나 결제 취소 같은 보상으로 처리한다. 그래서 바깥으로 무언가를 보내는 기능은 플래그 뒤에 두고 작게 시작한다.

### 컬럼 이름을 바꾸는 배포는 어떻게 해야 롤백이 안전한가요?

한 번에 RENAME하지 않고 확장과 수축으로 나눈다. 새 컬럼을 더하고 백필한 뒤 새 코드가 두 컬럼에 모두 쓰게 하고, 롤백할 일이 없어진 뒤에 옛 컬럼을 지운다. 실습에서 RENAME 뒤에는 롤백한 옛 코드가 `column "amount" does not exist`로 실패했고, 확장만 한 경우에는 정상으로 동작했다. 롤백 중 옛 코드가 쓴 행은 새 컬럼이 비므로 다시 올라갈 때 백필한다.

### 운영에서 down 마이그레이션을 돌리면 왜 위험한가요?

down은 대개 DROP이라 그 사이 쌓인 데이터를 함께 지운다. 실습에서도 v2가 떠 있던 동안 쓴 선물 메시지 두 건이 down 한 번에 사라졌다. 컬럼을 더한 변경은 옛 코드가 무시하면 되므로 되돌릴 필요가 없다. 그래서 스키마는 앞으로만 가게 하고, 취소가 필요하면 새 마이그레이션을 리뷰를 거쳐 내보낸다.

### kubectl rollout undo를 했는데도 문제가 남는다면 무엇을 의심하나요?

undo는 Pod 템플릿만 되돌린다는 점부터 본다. 함께 바뀐 ConfigMap과 Secret, DB 스키마, 큐에 남은 새 형식 메시지, 캐시의 새 직렬화 형식은 그대로다. 그리고 git에 나쁜 버전이 남아 있으면 다음 apply나 GitOps 동기화가 다시 내보내므로 git도 되돌려야 한다.

### 자동 롤백의 기준은 어떻게 정하나요?

SLO 대비 에러 예산을 태우는 속도로 잡는 게 흔하다. SLO 99.9%에서 에러율 1.44%면 burn rate 14.4로, 한 달 예산의 2%를 한 시간에 태우는 속도다. 한 번 튄 값에 반응하지 않도록 연속 횟수나 두 개의 시간 창을 함께 보고, 트래픽이 적은 구간은 판단에서 뺀다. 전체 서비스가 아니라 새 버전의 요청만 따로 보고 옛 버전과 비교해야 외부 원인에 엉뚱하게 되돌리지 않는다.

### 자동 롤백을 켜면 안 되는 배포는 어떤 것인가요?

롤백 자체가 안전하지 않은 배포다. 스키마를 호환되지 않게 바꾸거나 메시지 형식을 바꾼 배포에서 자동으로 옛 버전을 띄우면 두 번째 장애가 난다. 또 감시자가 지표를 받지 못하는 상황에서는 되돌리지도 통과시키지도 말고 배포를 멈춰 사람에게 넘긴다.

### 롤백이 필요할 때 실패하지 않게 평소에 무엇을 해 두나요?

되돌릴 이미지를 넉넉히 보관하고, 배포마다 변경 이유를 기록으로 남긴다. 설정은 내용 해시를 붙인 새 이름으로 만들어 템플릿과 함께 되돌아가게 하고, 캐시 키에는 형식 버전을 넣는다. 그리고 스테이징에서 배포 직후 롤백을 정기적으로 실제로 해 보며 걸린 시간을 잰다.
