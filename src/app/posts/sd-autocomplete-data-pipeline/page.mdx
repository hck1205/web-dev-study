이 시리즈에서 이 글의 자리: [㉙ 검색어 자동완성 ①: 트라이와 노드마다 미리 고른 상위 5개](/posts/sd-autocomplete-trie)에서 접두사로 추천 다섯 개를 마이크로초 안에 찾는 트라이를 만들었다. 이 글은 그 트라이를 어디서 무엇으로 만드는지, 검색 기록을 모으고 세고 저장하고 여러 서버로 나누는 쪽을 다룬다. 다음 장은 [㉛ 동영상 업로드와 변환](/posts/sd-video-upload-transcoding)이다.

앞 글의 트라이에는 한 가지가 빠져 있었다. 횟수는 어디서 왔을까. 데모에서는 가짜 빈도표를 넣었지만 실제 서비스에서는 사람들이 검색한 기록이 그 숫자가 된다. 그리고 앞 글 끝에서 봤듯 노드마다 상위 목록을 둔 트라이는 검색이 올 때마다 고치기가 어렵다.

그래서 자동완성은 두 갈래로 나뉜다. 사용자가 글자를 칠 때 답하는 질의 쪽과, 검색 기록을 모아 트라이를 새로 만드는 데이터 쪽이다. 이 글은 하루치 검색 로그 100만 줄을 직접 만들어 집계하고, 접두사 표로 바꿔 Redis에 올리고, 서비스를 멈추지 않고 새 버전으로 바꿔 끼우기까지 따라간다.

## 검색할 때마다 트라이를 고치면

가장 단순한 생각부터 해 보자. 누가 `redis json`을 검색하면 그 자리에서 트라이의 횟수를 하나 올리고, 지나는 노드의 상위 목록을 고친다.

검색은 글자 입력보다 훨씬 적다. 앞 글의 가정(하루 활성 사용자 500만 명, 한 사람 하루 8번 검색)이면 실제로 검색 버튼을 누르는 것은 초당 약 463번이다. 숫자는 작아 보이지만 검색 하나가 검색어 길이만큼, 평균 15개 노드의 목록을 고친다. 초당 7천 번 가까운 목록 수정이 같은 트라이를 읽는 초당 수천~수만 번의 질의와 부딪힌다. 여러 질의 서버가 같은 트라이를 들고 있으니 수정을 모든 서버에 똑같이 퍼뜨려야 하고, 순서가 엇갈리면 서버마다 추천이 달라진다.

게다가 대부분의 수정은 결과를 바꾸지 않는다. `re`의 1등 `render`가 검색 한 번으로 바뀌지는 않는다. 상위 목록은 몇 시간, 며칠에 걸쳐 천천히 움직인다. 그래서 검색은 기록만 남기고, 트라이는 모아 둔 기록으로 주기적으로 새로 굽는다.

## 검색 로그는 덧붙이기만 한다

검색 API는 검색이 들어올 때마다 한 줄을 남긴다. 이 로그는 나중에 처음부터 끝까지 한 번에 읽기만 하니 인덱스를 두지 않고 파일 끝에 덧붙이기만 한다. 덧붙이기는 디스크가 가장 잘하는 일이라 검색 API를 느리게 하지 않는다. 실제로는 로그를 [메시지 큐](/posts/sd-queue-logging-automation)나 [Kafka](/posts/kafka-basics) 같은 곳으로 보내 모으는 경우가 많다.

Node 22로 하루치 로그 100만 줄을 만들었다. 앞 글의 가짜 검색어 20만 개를 인기 순 확률로 뽑고, 사람이 치는 것처럼 일부는 대문자로, 일부는 공백을 섞었다. 20줄마다 한 번은 봇 계정 하나가 같은 검색어를 친다. 파일은 44MB다.

## 같은 검색어를 하나로 센다

집계는 로그를 줄 단위로 읽으며 검색어마다 숫자를 올린다. 먼저 친 그대로 세고, 다음에 정규화(소문자로 바꾸고, 앞뒤 공백을 지우고, 여러 칸 공백을 한 칸으로)를 한 뒤 세고, 마지막으로 검색어마다 서로 다른 사용자 수를 셌다.

```js
// aggregate.mjs 일부: 로그를 한 줄씩 읽어 세 가지로 센다
const normalize = (q) => q.trim().toLowerCase().replace(/\s+/g, " ");
for await (const line of createInterface({ input: createReadStream("search.log") })) {
  const [, user, q] = line.split("\t");
  raw.set(q, (raw.get(q) ?? 0) + 1);                       // 친 그대로
  const n = normalize(q);
  norm.set(n, (norm.get(n) ?? 0) + 1);                     // 정규화한 뒤
  let set = users.get(n); if (!set) users.set(n, (set = new Set())); set.add(user);  // 서로 다른 사용자
}
```

```text
distinct raw=170858 normalized=115647
top by count: [["ssl",75223],["buy cheap followers",50000],["json",37735]]
top by users: [["ssl",66356],["json",35430],["spring",23971]]

```

세 줄을 차례로 보자. 친 그대로 세면 서로 다른 검색어가 17만 개인데, 정규화하면 11만 6천 개로 줄었다. 마지막 줄처럼 `json`, `JSON`, `Json`과 공백 섞인 것들이 따로 세졌다가 정규화 뒤에 37,735 하나로 합쳐졌다. 정규화를 빼먹으면 같은 검색어가 추천에 두 번 뜨거나 표가 갈려 순위가 낮아진다. 정규화 규칙은 앞 글의 질의 서버가 쓰는 규칙과 똑같아야 한다. 한글이라면 자모로 푸는 것까지 같은 함수를 쓴다.

## 몇 번이 아니라 몇 명이 찾았나

`top by count` 줄에서 `buy cheap followers`가 2등이다. 봇 하나가 5만 번 친 결과다. 횟수로만 세면 누구든 같은 검색어를 반복해서 추천 목록에 올릴 수 있다. `top by users`, 즉 서로 다른 사용자 수로 세면 이 검색어는 1명이라 목록에서 사라지고 `json`과 `spring`이 올라온다. 하루 안에 같은 사람이 같은 검색어를 여러 번 친 것은 한 번으로 친다.

사람 수로 세면 한 가지를 더 막을 수 있다. 개인 정보다. 누군가 자기 집 주소나 다른 사람의 이름과 전화번호를 검색했다면 그 검색어를 친 사람은 한두 명뿐이다. 그런 검색어가 남의 추천에 뜨면 안 된다. 그래서 최소 사람 수를 정해 그보다 적은 검색어는 버린다. 위 결과에서 2명 이상만 남기면 11만 5,647개 중 6만 473개가, 5명 이상이면 1만 8,423개가 남았다. 이 데이터에서는 기준을 2명에서 5명으로 올리자 검색어가 3분의 1로 줄었다. 기준이 높을수록 안전하지만 드문 검색어에 대한 추천이 사라지니 서비스 성격에 맞춰 정한다.

사용자 집합을 검색어마다 통째로 들고 있으면 메모리가 많이 든다. 이 데모는 100만 줄에 158MB를 썼다. 하루 수억 줄이면 한 대에서 어렵다. 정확한 사람 수 대신 HyperLogLog처럼 고정 크기로 개수를 어림하는 구조를 쓰기도 한다. 하루치를 "사용자, 검색어" 쌍의 중복 제거로 먼저 줄이고 나서 세는 것도 방법이다.

## 한 대로 안 되면 조각으로 나눠 센다

로그가 커지면 한 대가 다 읽을 수 없다. 여러 대가 나눠 세고 합친다. 이때 무엇으로 나눌지가 중요하다. 로그를 시간순으로 4등분해 각자 세면, 같은 `json`이 네 조각에 다 나와서 마지막에 네 숫자를 더하고 사용자 집합까지 합쳐야 한다. 대신 검색어의 해시로 조각을 정하면 같은 검색어는 늘 같은 조각으로 간다. 그러면 조각마다 센 결과를 이어 붙이기만 하면 된다.

```js
// build.mjs 일부: 검색어 해시로 4조각에 나눠 센다. 같은 검색어는 늘 같은 조각으로 간다
const part = (q) => createHash("md5").update(q).digest()[0] % P;
const m = parts[part(n)]; let s = m.get(n); if (!s) m.set(n, (s = new Set())); s.add(user);
// 조각끼리 검색어가 겹치지 않으니 합치기는 이어 붙이기만 하면 된다
for (const m of parts) for (const [q, s] of m) if (s.size >= MIN_USERS) freq.push([q, s.size]);
```

```text
map: 4749ms, partition sizes=28689/29069/28922/28967
reduce: 60473 queries with >= 2 users
```

이 데모는 네 조각을 한 프로세스에서 차례로 돌려서 해시 계산만큼 오히려 느려졌다. 보여 주려는 것은 시간이 아니라 모양이다. 조각 크기가 2만 8,689~2만 9,069로 고르게 나뉘었고, 합친 결과 6만 473개는 한 번에 센 결과와 같다. 실제로는 조각마다 다른 기계가 맡는다. 이렇게 나눠서 세고(map) 모아서 합치는(reduce) 일은 Spark 같은 배치 처리 도구가 해 주는 일이고, 배치 작업을 운영하는 법은 [배치 처리](/posts/batch-processing)에 정리해 두었다.

## 얼마나 자주 굽나

트라이를 굽는 주기는 서비스가 얼마나 빨리 바뀌느냐로 정한다. 백과사전이나 쇼핑몰의 상품 검색처럼 인기 검색어가 천천히 바뀌면 일주일에 한 번도 충분하다. 뉴스나 SNS처럼 몇 시간 만에 새 검색어가 쏟아지는 곳에서는 일주일은 너무 길다. 새 게임이 발표된 날 그 이름이 다음 주에야 추천에 뜨면 늦는다.

주기를 줄이는 데는 비용이 따른다. 굽는 데 드는 계산이 주기마다 반복되고, 집계 창(몇 시간 또는 며칠치를 세는지)이 짧아지면 그 순간 튀는 검색어가 쉽게 올라온다. 그래서 둘을 겹쳐 쓴다. 긴 창(예컨대 최근 4주)으로 구운 큰 트라이를 기본으로 두고, 최근 한 시간처럼 짧은 창에서 급히 뜨는 검색어만 작은 목록으로 따로 센다. 질의 서버는 둘을 합쳐 답한다. 짧은 창에서 "많이 나온 것만" 고정된 메모리로 찾는 방법은 [Lossy Counting](/posts/lossy-counting)과 [Count-Min Sketch](/posts/count-min-sketch)에서 다뤘고, 오래된 기록의 무게를 줄이는 시간 감쇠도 Lossy Counting 글에 있다.

왼쪽은 트라이를 파일 하나로 직렬화해 문서 저장소나 객체 저장소에 둔다. 질의 서버는 시작할 때 통째로 내려받아 메모리에 트라이를 다시 세운다. 앞 글의 구조 그대로다. 오른쪽은 트라이의 노드마다 "접두사 → 상위 목록"을 키와 값으로 펼쳐 키-값 저장소에 둔다. 질의는 접두사를 키로 `GET` 한 번이면 끝나고, 트라이를 따라 내려갈 필요도 없다. 노드마다 목록을 미리 적어 두었으니 사실 트라이의 연결 구조는 답을 만들 때만 필요했던 셈이다.

오른쪽 모양을 만들어 봤다. 2명 이상이 찾은 검색어 6만 473개의 앞 20글자까지 접두사를 모두 키로 만들고, 키마다 상위 5개를 계산했다.

```text
prefix table: 307784 keys, ~15.8MB as JSON, built in 822ms
re -> [["render",5256],["rest",2179],["redis",1134],["react",843],["replica deno",394]]
```

키가 30만 7,784개다. 접두사를 20글자에서 자른 덕분에 긴 검색어가 키를 끝없이 늘리지 않는다. `re`의 목록이 앞 글의 가짜 빈도표 결과와 같은 순서로 나왔다. 이번 숫자는 횟수가 아니라 사람 수다.

이것을 Redis에 올렸다. 키 이름 앞에 버전을 붙인 것이 다음 절의 준비다.

```js
// load.mjs 일부: 새 버전 이름(ac:v43:*)으로 5,000개씩 묶어 올린다. 값은 검색어 목록만
await r.pipeline(table.slice(i, i + 5000).map(([p, arr]) => ["SET", `ac:v43:${p}`, JSON.stringify(arr.map(([q]) => q))]));
```

```text
loaded 307784 keys in 814ms, +42.3MB
```

JSON 크기는 15.8MB였는데 Redis에서는 42.3MB가 늘었다. 키마다 붙는 관리 정보가 있어서다. 키-값 모양은 질의가 단순하고 여러 서버가 같은 저장소를 함께 읽을 수 있지만, 질의마다 네트워크 왕복이 하나 생긴다. 스냅숏 모양은 질의가 메모리 안에서 끝나지만 서버마다 전체를 들고 있어야 하고 새 버전을 받을 때 시간이 걸린다. 큰 서비스에서는 키-값 저장소를 원본으로 두고, 질의 서버가 그 앞에 많이 쓰는 접두사를 메모리에 캐시하는 식으로 둘을 섞는다.

## 새 버전으로 한 번에 바꾼다

새 표를 올리는 동안에도 질의는 계속 들어온다. 기존 키를 하나씩 덮어쓰면 올리는 몇 초 동안 `re`는 새 버전, `red`는 옛 버전인 상태가 된다. 한 글자 칠 때마다 추천이 들쭉날쭉해진다. 그래서 새 버전은 다른 이름으로 다 올리고, 마지막에 "지금 쓰는 버전"을 가리키는 포인터 하나만 바꾼다.

```text
127.0.0.1:6420> GET ac:current
"v42"
127.0.0.1:6420> GET ac:v42:re
"[\"react\",\"rest\",\"redis\",\"render\",\"regex\"]"
127.0.0.1:6420> SET ac:current v43
OK
127.0.0.1:6420> GET ac:v43:re
"[\"render\",\"rest\",\"redis\",\"react\",\"replica deno\"]"
127.0.0.1:6420> GET ac:v43:redis
"[\"redis\",\"redis kubernetes\",\"redis json\",\"redis trie\",\"redis https\"]"
127.0.0.1:6420> EXISTS ac:v43:zzzz
(integer) 0
```

질의 서버는 `ac:current`로 버전을 읽고 `ac:{버전}:{접두사}`를 찾는다. 포인터는 매 요청마다 읽지 않고 몇 초마다 확인해 메모리에 둔다. `SET ac:current v43` 한 줄 전에는 모두 v42를, 그 뒤에는 모두 v43을 본다. 없는 접두사(`zzzz`)는 키가 없으니 빈 추천을 준다.

검사 단계가 생각보다 중요하다. 집계 작업이 로그 일부만 읽고 끝났거나 정규화 규칙이 바뀌어 검색어가 반으로 줄었는데 그대로 바꿔 끼우면, 모든 사용자의 추천이 한꺼번에 이상해진다. 키 수, 상위 접두사의 답, 지난 버전과 겹치는 비율 같은 숫자로 미리 걸러 낸다. 이 방식은 코드 배포의 블루-그린 전환과 같은 생각이다. 버전을 둘 다 갖고 있다가 가리키는 곳만 바꾼다.

## 접두사로 나눠 여러 서버에

검색어가 수억 개로 늘면 접두사 표가 저장소 한 대에 들어가지 않는다. 키를 나눠야 하는데, 키-값 모양이라면 [안정 해시](/posts/consistent-hashing)로 접두사 키를 고르게 흩는 것이 가장 쉽다. 키마다 질의가 독립이라 어느 서버에 있든 상관없다.

스냅숏 모양처럼 질의 서버가 트라이 일부를 통째로 들고 있어야 한다면 접두사의 첫 글자로 나누는 방법이 자연스럽다. `a`부터 `m`은 1번, `n`부터 `z`는 2번. 질의가 `re`로 오면 첫 글자 `r`을 보고 2번으로 보낸다. 문제는 글자마다 검색어 수가 다르다는 것이다. 위 데이터로 첫 글자별 비중(사람 수 합)을 계산했다.

```text
a-m: 51.4%, n-z: 48.6%
top letters: s=17.9% j=9.2% r=7.5% p=7.0% d=6.7%
4 shards by load, cut after: g(26.5%), m(51.4%), s(90.5%)
```

둘로 나누면 51.4%와 48.6%로 우연히 고르다. 하지만 넷으로 나누려고 누적 비중이 25%, 50%, 75%를 넘는 글자에서 잘랐더니 경계가 `g`, `m`, `s`가 됐고, 세 번째 조각(`n`~`s`)은 39.1%, 네 번째(`t`~`z`)는 9.5%다. `s` 하나가 17.9%라서 글자 단위로는 더 고르게 자를 수 없다. 그래서 무거운 글자는 두 번째 글자로 한 번 더 나눈다. `sa`~`sl`과 `sm`~`sz`처럼. 이 데이터는 가짜라 비중 자체는 의미가 없지만, 실제 검색어도 첫 글자가 고르지 않다는 점은 같다. 실제 비중을 재서 경계를 정해야 한다.

## 파이프라인이 고장 나면 보이는 것

데이터 쪽의 장애는 질의 쪽처럼 바로 에러로 드러나지 않는다. 추천이 조용히 낡거나 이상해진다.

- 추천이 몇 주째 그대로다. 굽는 작업이 실패하고 있는데 포인터는 옛 버전을 가리키니 서비스는 멀쩡해 보인다. 현재 버전이 만들어진 시각을 지표로 남기고, 정해진 주기의 두 배를 넘으면 알림을 건다.
- 어느 날 추천이 텅 비거나 엉뚱해졌다. 검사 없이 포인터를 바꾼 경우다. 바로 이전 버전으로 포인터를 되돌리고, 그 버전의 집계가 로그를 얼마나 읽었는지(입력 줄 수)부터 본다.
- 특정 검색어가 갑자기 1등이다. 사람 수가 아니라 횟수로 세고 있거나, 봇이 계정을 여러 개 쓰고 있다. 그 검색어를 친 계정들의 가입 시점과 검색 간격을 본다. 급하면 앞 글의 거르기 단계에 넣는다.
- 같은 검색어가 추천에 두 번 뜬다. 집계와 질의의 정규화 규칙이 어긋났다. 한쪽만 고친 배포가 있었는지 본다.

## 검색 로그 집계하기

집계 함수를 직접 짜 보자. `logs`는 `[사용자, 친 그대로의 검색어]` 배열이다. 검색어를 정규화(앞뒤 공백 제거, 소문자, 여러 칸 공백을 한 칸으로)하고, 정규화 결과가 빈 문자열이면 버린다. 검색어마다 서로 다른 사용자 수를 세어 `minUsers` 이상인 것만 `[검색어, 사람 수]`로 돌려준다. 사람 수가 많은 순, 같으면 사전순이다.

## 다음에 읽을 글

데이터 쪽은 이렇게 정리된다. 검색은 트라이를 직접 고치지 않고 로그에 한 줄을 덧붙인다. 로그는 정규화해서 검색어별로 서로 다른 사람 수를 세고, 너무 적은 사람이 찾은 검색어는 버린다. 크면 검색어 해시로 나눠 세고 이어 붙인다. 결과는 접두사마다 상위 목록을 적은 표로 펼쳐 새 버전 이름으로 올리고, 검사한 뒤 포인터 하나만 바꾼다. 커지면 접두사 범위나 해시로 나누되 글자마다 무게가 다르니 실제 비중을 재서 경계를 정한다.

자동완성 두 편은 여기까지다. 다음 장 [㉛ 동영상 업로드와 변환](/posts/sd-video-upload-transcoding)에서는 이번처럼 무거운 일을 뒤로 돌리는 구조가 훨씬 큰 규모로 나온다. 몇 GB짜리 파일을 받아 여러 화질로 바꾸는 일이다.

## 면접에서 나올 만한 질문

### 검색할 때마다 트라이를 바로 고치지 않는 이유는요?

노드마다 상위 목록을 둔 트라이는 검색어 하나의 횟수가 바뀌면 그 경로의 노드 목록을 모두 다시 계산해야 해서, 실시간으로 고치면 질의와 부딪히고 여러 질의 서버의 상태를 맞추기 어렵다. 게다가 상위 목록은 천천히 바뀌어 대부분의 수정이 결과를 바꾸지 않는다. 그래서 검색은 로그만 남기고 주기적으로 새 트라이를 구워 통째로 바꾼다.

### 검색 횟수 대신 사용자 수로 세는 이유는요?

봇이나 한 사람이 같은 검색어를 반복해서 추천 순위를 올리는 것을 막기 위해서다. 실험에서 봇 하나가 5만 번 친 검색어가 횟수로는 2등이었지만 사람 수로는 1명이라 사라졌다. 최소 사람 수 기준을 두면 한두 사람만 친 주소나 이름 같은 개인 정보가 남의 추천에 뜨는 것도 막는다.

### 로그가 너무 커서 한 대로 집계할 수 없으면요?

검색어 해시로 조각을 나눠 여러 대가 센다. 같은 검색어는 늘 같은 조각으로 가므로 조각마다 센 결과를 이어 붙이기만 하면 되고, 사용자 집합을 조각 사이에 합칠 필요가 없다. 시간순으로 나누면 같은 검색어가 모든 조각에 흩어져 합치는 단계가 무거워진다.

### 트라이를 얼마나 자주 새로 만드나요?

인기 검색어가 얼마나 빨리 바뀌는지로 정한다. 천천히 바뀌는 서비스는 주 단위로도 충분하고, 뉴스처럼 빠른 곳은 긴 창으로 구운 기본 트라이에 최근 한 시간 정도의 급상승 목록을 따로 세어 합친다. 주기를 줄이면 계산 비용이 늘고 순간적으로 튀는 검색어가 쉽게 올라오는 대가가 있다.

### 새 트라이로 바꾸는 순간 추천이 섞이지 않게 하려면요?

새 버전을 다른 키 이름으로 모두 올리고 검사한 뒤, 현재 버전을 가리키는 포인터 하나만 바꾼다. 그 순간 전에는 모두 옛 버전을, 뒤에는 모두 새 버전을 본다. 옛 버전을 한동안 남겨 두면 문제가 있을 때 포인터만 되돌려 몇 초 안에 복구한다.

### 트라이를 접두사 첫 글자로 샤딩하면 어떤 문제가 있나요?

글자마다 검색어 수와 질의 양이 달라 샤드 부하가 고르지 않다. 실험에서 s 하나가 17.9%를 차지해 글자 단위 경계로는 넷으로 고르게 나눌 수 없었다. 무거운 글자는 둘째 글자까지 보고 더 나누고, 경계는 실제 비중을 재서 정해 샤드 지도로 관리한다. 키-값 모양이라면 접두사 키를 해시로 흩는 것이 더 단순하다.

### 굽는 작업이 몇 주째 실패하고 있다는 걸 어떻게 알아채나요?

포인터가 옛 버전을 계속 가리켜서 서비스는 정상처럼 보이니 에러로는 알 수 없다. 현재 버전이 만들어진 시각을 지표로 남겨 주기의 두 배를 넘으면 알림을 걸고, 집계 작업의 입력 줄 수와 결과 검색어 수도 함께 기록해 갑자기 줄었는지 본다.
