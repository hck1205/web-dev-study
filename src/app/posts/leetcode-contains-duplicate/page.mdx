[Contains Duplicate](https://leetcode.com/problems/contains-duplicate/)는 LeetCode 217번이다. 배열에 같은 값이 두 번 이상 나오는지만 묻는다. 너무 쉬워 보여서 그냥 지나치기 쉬운데, 이 문제에는 "같은 것을 찾을 때 쓸 수 있는 도구"가 거의 다 들어 있다. 이중 반복, 정렬, 해시 집합, 그리고 범위가 붙으면 슬라이딩 윈도와 버킷까지 간다. 면접에서도 이 문제를 열어 두고 "값 범위가 작다면", "k칸 안에서만 본다면"으로 계속 넓혀 간다.

[Two Sum](/posts/leetcode-two-sum)이 "짝이 되는 값을 본 적 있나"를 물었다면, 이 문제는 "같은 값을 본 적 있나"를 묻는다. 장부에 인덱스를 적을 필요가 없어서 해시맵 대신 해시 집합이면 충분하다. 해시 집합이 왜 평균 O(1)에 찾는지는 [해시맵 글](/posts/ds-hash-map)에서 다뤘다. 코드는 Node.js 22, Python 3.13, Java 21에서 직접 돌렸다.

## 같은 값이 두 번 나오는지만 본다

정수 배열 `nums`가 주어진다. 어떤 값이든 두 번 이상 나오면 `true`, 모든 값이 서로 다르면 `false`를 돌려준다. 어느 값이 중복인지, 몇 번 나왔는지는 묻지 않는다.

제약 중 풀이를 정하는 건 두 가지다.

- 배열 길이가 1 이상 10^5 이하다. 모든 쌍을 비교하면 최대 약 50억 번이라 시간 안에 못 끝낸다.
- 값은 -10^9 이상 10^9 이하다. 값 범위가 20억 개쯤 되니 "값마다 칸 하나짜리 배열"을 만들 수는 없다.

첫 번째가 O(n²)를 막고, 두 번째가 "값을 그대로 인덱스로 쓰는" 가장 빠른 방법을 막는다. 남는 건 정렬 O(n log n)과 해시 집합 O(n)이다.

## 손으로 해 보면 무엇을 기억하게 되나

예시 하나를 정해 두고 끝까지 쓴다.

```text
인덱스   0   1   2   3   4
nums     7   3   9   3   1
```

눈으로 보면 3이 두 번 나온다는 걸 금방 안다. 그런데 손가락으로 하나씩 짚으면서 확인한다고 해 보자. 7을 짚고, 3을 짚고, 9를 짚고, 다시 3을 짚는 순간 "아까 봤다"를 떠올린다. 머릿속에 지금까지 본 값의 목록을 들고 다니는 셈이다.

그 목록을 어떻게 들고 다니느냐가 풀이를 가른다. 목록을 매번 처음부터 훑으면 이중 반복이다. 목록을 정렬된 상태로 들고 다니거나, 처음부터 배열 전체를 정렬해 두면 정렬 풀이다. 목록을 "값으로 바로 찾을 수 있는" 집합으로 들고 다니면 해시 풀이다.

## 모든 쌍을 비교하는 풀이

```js
function containsDuplicate(nums) {
  for (let i = 0; i < nums.length; i++) {
    // i보다 뒤에 있는 칸만 본다. 같은 쌍을 두 번 보지 않는다.
    for (let j = i + 1; j < nums.length; j++) {
      if (nums[i] === nums[j]) return true;
    }
  }
  return false;
}

console.log(containsDuplicate([7, 3, 9, 3, 1]), containsDuplicate([4, 8, 2, 6]));
```

```text
true false
```

시간은 O(n²), 공간은 O(1)이다. 이 문제에서 최악은 중복이 없을 때다. 중복이 있으면 찾는 순간 끝나지만, 없으면 n(n-1)/2개의 쌍을 전부 확인해야 "없다"고 말할 수 있다. 실제로 서로 다른 값 10만 개를 넣었더니 3초가 넘게 걸렸다(뒤의 측정 절).

이 풀이의 문제는 안쪽 반복이 "nums[i]와 같은 값이 뒤에 있나"를 매번 처음부터 찾는다는 점이다. 찾기를 빠르게 하는 방법은 두 갈래다. 같은 값끼리 모이게 만들거나(정렬), 값으로 바로 찾게 만들거나(해시).

## 정렬하면 같은 값이 옆에 붙는다

정렬된 배열에서 같은 값은 반드시 연속해서 놓인다. 그 사이에 다른 값이 끼어 있다면 그 값은 둘보다 크거나 작아야 하는데, 정렬돼 있으니 둘 사이에 들어갈 수 없다. 그러니 정렬한 뒤 바로 옆 칸끼리만 비교하면 된다.

```js
function containsDuplicate(nums) {
  // 입력을 망가뜨리지 않으려고 복사해서 정렬한다
  const a = [...nums].sort((x, y) => x - y);
  for (let i = 1; i < a.length; i++) {
    if (a[i] === a[i - 1]) return true; // 같은 값은 반드시 이웃한다
  }
  return false;
}

console.log(containsDuplicate([7, 3, 9, 3, 1]), containsDuplicate([4, 8, 2, 6]));
```

```text
true false
```

시간은 정렬 O(n log n)과 훑기 O(n)을 합쳐 O(n log n)이다. 공간은 무엇을 쓰느냐에 따라 다르다. 위 코드처럼 복사하면 O(n)이다. 입력 배열을 그대로 정렬해도 된다면 추가 공간이 정렬 구현이 쓰는 만큼만 든다. V8의 배열 정렬(TimSort)은 최악 O(n)의 임시 공간을 쓰고, Java의 `int[]` 정렬(듀얼 피벗 퀵정렬)은 재귀 스택 정도인 O(log n)이다.

입력을 그대로 정렬하는 건 면접에서 한 번 짚고 넘어갈 일이다. 함수가 받은 배열의 순서를 바꾸면, 함수를 부른 쪽이 그 배열을 다시 쓸 때 놀란다. `const orig = [3, 1, 2]; orig.sort((a, b) => a - b);` 뒤에 `orig`를 찍으면 `[1, 2, 3]`이다. "입력을 바꿔도 되나요?"라고 먼저 묻고, 안 된다고 하면 복사하거나 다른 풀이를 고른다.

JavaScript에서 정수만 다룬다면 `Int32Array`로 바꿔 정렬하는 방법도 있다. 타입 배열의 `sort`는 비교 함수 없이도 숫자 순서로 정렬하고, 일반 배열보다 빠르다. 10만 개에서 일반 배열 정렬 풀이가 19.85ms, `Int32Array.from(nums).sort()`를 쓴 풀이가 6.40ms였다. 값이 -2^31 이상 2^31 미만이어야 하는데 이 문제의 범위는 거기에 들어간다.

한 가지 재미있는 점이 있다. 일반 배열에서 비교 함수를 빼먹으면 값이 문자열로 정렬돼 `[10, 9, 1, 10, 2].sort()`가 `[1, 10, 10, 2, 9]`가 된다. 순서는 엉망인데, 같은 숫자는 같은 문자열이 되니 여전히 이웃한다. 그래서 이 문제에서는 우연히 답이 맞는다. 다른 문제에서 이 버릇이 그대로 나오면 틀리니 기대지 않는다.

정렬 풀이의 한계는 중복이 맨 앞 두 칸에 있어도 정렬은 끝까지 해야 한다는 점이다. 일찍 끝낼 수가 없다.

## 본 값을 집합에 적어 두기

머릿속의 "본 값 목록"을 해시 집합(`Set`)으로 들고 다닌다. 집합은 값이 있는지 없는지만 기억하는 해시 테이블이다. 칸마다 두 가지만 한다.

1. 지금 값이 집합에 있나 본다. 있으면 `true`로 끝낸다.
2. 없으면 집합에 넣는다.

```js
function containsDuplicate(nums) {
  const seen = new Set(); // 지금 칸보다 앞에서 본 값들
  for (const x of nums) {
    if (seen.has(x)) return true; // 본 적 있다 → 중복
    seen.add(x);
  }
  return false; // 끝까지 다 봤는데 겹친 적이 없다
}

console.log(containsDuplicate([7, 3, 9, 3, 1]), containsDuplicate([4, 8, 2, 6]), containsDuplicate([5]));
```

```text
true false false
```

아래 그림에서 다음을 누르면 한 칸씩 넘어가며 집합이 쌓인다. 3번 칸의 3을 볼 때 집합에 이미 3이 있다.

시간은 평균 O(n)이다. 칸마다 집합 조회 한 번과 삽입 한 번이고, 둘 다 평균 O(1)이다. 공간은 최악 O(n)이다. 중복이 없으면 값을 전부 집합에 넣기 때문이다.

정렬 풀이와 비교하면 두 가지가 낫다. 등급이 O(n log n)에서 O(n)으로 내려가고, 중복을 찾는 순간 멈출 수 있다. 중복이 앞쪽에 있으면 거의 바로 끝난다. 대신 메모리를 쓴다. 얼마나 쓰는지 직접 재 봤다. `node --expose-gc`로 가비지 컬렉션을 강제로 돌린 뒤 힙 사용량을 비교했다.

```js
const nums = Array.from({ length: 100000 }, (_, i) => i * 7 - 300000);
gc(); const before = process.memoryUsage().heapUsed;
const s = new Set(nums);
gc(); const after = process.memoryUsage().heapUsed;
console.log(((after - before) / 1024 / 1024).toFixed(2), "MB", s.size);
```

```text
2.50 MB 100000
```

10만 개에 약 2.5MB, 값 하나에 26바이트 정도다. 같은 값을 `Int32Array`에 담으면 값 하나에 4바이트라 0.38MB다. 해시 집합은 빈칸과 연결 정보를 함께 들고 있어서 원래 데이터보다 몇 배 크다. 이 문제 크기에서는 상관없지만 값이 수억 개면 이야기가 달라진다. 그 경우는 뒤의 변형 절에서 본다.

## 집합 크기를 세는 한 줄 풀이

집합은 같은 값을 한 번만 담는다. 그러니 배열 전체를 집합으로 만든 뒤 크기를 배열 길이와 비교하면 된다. 크기가 줄었으면 어딘가에서 겹친 것이다.

```js
const containsDuplicate = (nums) => new Set(nums).size !== nums.length;

console.log(containsDuplicate([7, 3, 9, 3, 1]), containsDuplicate([4, 8, 2, 6]));
```

```text
true false
```

시간과 공간은 앞 풀이와 같은 O(n)이다. 코드가 짧고 읽기 쉬워서 실무에서는 이쪽을 더 자주 쓴다. 다만 일찍 끝나지 않는다. 0번 칸과 1번 칸이 같은 10만 개 배열에서 한 칸씩 보는 풀이는 0.002ms, 한 줄 풀이는 5.21ms가 걸렸다. 중복이 없을 때는 둘이 거의 같다(5.59ms와 5.92ms).

면접에서 한 줄 풀이를 먼저 쓰는 것도 괜찮다. 다만 "일찍 멈출 수 있나요?"가 나오면 바로 반복문 풀이로 바꿀 수 있어야 한다. 두 풀이의 차이를 스스로 먼저 말하면 더 좋다.

## Python과 Java로 옮기기

```python
from typing import List

class Solution:
    def containsDuplicate(self, nums: List[int]) -> bool:
        seen = set()
        for x in nums:
            if x in seen:   # set의 in은 평균 O(1)
                return True
            seen.add(x)
        return False

    def containsDuplicateShort(self, nums: List[int]) -> bool:
        return len(set(nums)) != len(nums)

s = Solution()
print(s.containsDuplicate([7, 3, 9, 3, 1]), s.containsDuplicate([4, 8, 2, 6]), s.containsDuplicate([5]))
print(s.containsDuplicateShort([7, 3, 9, 3, 1]), s.containsDuplicateShort([4, 8, 2, 6]))
```

```text
True False False
True False
```

Python에서는 한 줄 풀이가 반복문보다 빠른 경우가 많다. `set(nums)`는 C로 구현된 내부 반복을 한 번에 돌지만, `for` 반복문은 칸마다 파이썬 바이트코드를 실행하기 때문이다. 중복 없는 10만 개에서 반복문이 10.0ms, 한 줄 풀이가 3.1ms였다. 중복이 앞쪽에 몰려 있다는 보장이 없으면 한 줄 풀이를 쓰는 편이 현실적이다. 리스트에 `in`을 쓰면 O(n)이니 `seen = []`로 시작하는 실수는 피한다. 그러면 전체가 다시 O(n²)가 된다.

```java
import java.util.*;

class Solution {
    public boolean containsDuplicate(int[] nums) {
        Set<Integer> seen = new HashSet<>(nums.length * 2); // 다시 늘리는 일을 줄이려고 넉넉히 잡는다
        for (int x : nums) {
            if (!seen.add(x)) return true; // add는 이미 있으면 false를 돌려준다
        }
        return false;
    }

    public boolean containsDuplicateSort(int[] nums) {
        int[] a = nums.clone();   // 입력을 망가뜨리지 않는다
        Arrays.sort(a);           // int[]는 듀얼 피벗 퀵정렬
        for (int i = 1; i < a.length; i++) if (a[i] == a[i - 1]) return true;
        return false;
    }

    public static void main(String[] args) {
        Solution s = new Solution();
        System.out.println(s.containsDuplicate(new int[] { 7, 3, 9, 3, 1 }) + " " + s.containsDuplicate(new int[] { 4, 8, 2, 6 }) + " " + s.containsDuplicate(new int[] { 5 }));
        System.out.println(s.containsDuplicateSort(new int[] { 7, 3, 9, 3, 1 }) + " " + s.containsDuplicateSort(new int[] { 4, 8, 2, 6 }));
    }
}
```

```text
true false false
true false
```

Java의 `Set.add`는 새로 넣었으면 `true`, 이미 있었으면 `false`를 돌려준다. 그래서 `contains`와 `add`를 따로 부르지 않고 한 번에 확인과 삽입을 한다. 해시 계산도 한 번으로 줄어든다.

`new HashSet<>(nums.length * 2)`처럼 초기 용량을 주는 이유는 다시 넣기(rehash)를 줄이기 위해서다. `HashSet`은 기본 적재율 0.75를 넘으면 칸 수를 두 배로 늘리고 모든 값을 다시 넣는다. 들어갈 개수를 알면 처음부터 크게 잡아 그 비용을 없앤다. 적재율과 다시 넣기는 [해시맵 글](/posts/ds-hash-map#얼마나-채우면-느려지나)에 있다.

`int[]`를 정렬할 때 `Arrays.sort`는 기본형 전용 퀵정렬을 쓴다. `Integer[]` 같은 객체 배열이면 TimSort를 쓴다. 기본형 배열에서는 같은 값끼리의 순서가 의미가 없으니 안정 정렬이 아니어도 된다.

| 정렬 후 이웃 비교 | O(n log n) | O(1)~O(n) | 정렬은 끝까지 | 메모리를 아껴야 하거나 입력이 이미 정렬돼 있을 때 |
| 집합에 하나씩 넣기 | O(n) | O(n) | 멈춘다 | 기본 답. 중복이 일찍 나올 수 있을 때 |
| 집합 크기 비교 | O(n) | O(n) | 끝까지 | 짧고 읽기 쉬운 코드가 필요할 때 |

서로 다른 값을 무작위로 섞어 중복이 없는 배열을 만들고, 각 풀이를 다섯 번 돌린 가장 빠른 시간을 쟀다. 모든 쌍 비교는 한 번만 돌렸다.

## 헷갈리기 쉬운 입력과 실수

### 원소가 하나뿐인 배열

`[5]`는 `false`다. 정렬 풀이의 반복문은 `i = 1`부터 시작하니 한 번도 돌지 않고 `false`를 돌려준다. `i = 0`부터 `a[i] === a[i + 1]`로 쓰면 마지막 칸에서 `a[n]`을 읽는다. JavaScript는 `undefined`라 우연히 넘어가지만 Java는 `ArrayIndexOutOfBoundsException`이 난다.

```java
for (int i = 0; i < a.length; i++) if (a[i] == a[i + 1]) return true; // i = a.length - 1에서 범위를 넘는다
```

### 음수, 0, 그리고 -0

해시 집합과 정렬은 부호를 신경 쓰지 않는다. `[-2, -2]`는 `true`, `[1000000000, -1000000000]`은 `false`다. JavaScript만의 함정이 하나 있는데, `Set`은 `0`과 `-0`을 같은 값으로 본다. `[0, -0]`을 넣으면 `true`가 나온다. 정수 배열 문제에서는 상관없지만, 실수 계산 결과를 집합에 넣는 코드라면 알아 둘 일이다.

### 객체에 값을 적으면서 참거짓으로 확인하기

`seen[x] = true`로 적고 `if (seen[x])`로 확인하는 건 이 문제에서는 맞다. 값이 `true`라서 0 문제가 없다. 하지만 Two Sum처럼 인덱스를 적는 순간 0번 칸이 사라진다. [Two Sum 글](/posts/leetcode-two-sum#틀리기-쉬운-입력들)에서 실제로 틀리는 모습을 봤다. 습관처럼 `Set`이나 `Map.has`를 쓰면 이 차이를 신경 쓸 필요가 없다.

### 리스트로 "본 값"을 들고 다니기

```js
const seen = [];
for (const x of nums) {
  if (seen.includes(x)) return true; // includes는 O(n)이다
  seen.push(x);
}
```

모양은 집합 풀이와 똑같은데 `includes`가 처음부터 훑기 때문에 전체는 O(n²)다. 모든 쌍 비교를 다르게 쓴 것뿐이다. Python의 `x in list`, Java의 `List.contains`도 같다.

## 범위가 붙으면 문제가 달라진다

### k칸 안에서 겹치는지 보라면

LeetCode 219. Contains Duplicate II는 "같은 값이 인덱스 차이 k 이하로 두 번 나오나"를 묻는다. 멀리 떨어진 중복은 세지 않는다. 집합을 배열 전체가 아니라 최근 k칸만 담는 창으로 바꾸면 된다. 새 값을 넣고, 창이 k칸을 넘으면 가장 오래된 값을 뺀다. [슬라이딩 윈도](/posts/sliding-window-pattern)의 가장 단순한 형태다.

```js
function containsNearbyDuplicate(nums, k) {
  const window = new Set(); // 최근 k칸의 값
  for (let i = 0; i < nums.length; i++) {
    if (window.has(nums[i])) return true; // 창 안에 같은 값 → 거리 k 이하
    window.add(nums[i]);
    if (window.size > k) window.delete(nums[i - k]); // 창 밖으로 밀려난 값을 뺀다
  }
  return false;
}

console.log(containsNearbyDuplicate([4, 1, 2, 4, 3, 4], 2));
```

### 값도 비슷하면 중복으로 치라면

LeetCode 220. Contains Duplicate III는 한 걸음 더 간다. 인덱스 차이가 `indexDiff` 이하이고 값 차이가 `valueDiff` 이하인 두 칸이 있나. 값이 정확히 같지 않아도 되니 집합의 `has`로는 못 찾는다.

생각할 수 있는 길은 둘이다. 창 안의 값을 정렬된 상태로 들고 다니며(균형 이진 탐색 트리, Java의 `TreeSet`) 지금 값 이상 중 가장 작은 값을 찾는 방법이 O(n log k)다. 더 빠른 건 버킷이다. 값을 폭 `valueDiff + 1`인 구간으로 나눠 구간 번호를 키로 쓴다. 같은 구간에 든 두 값은 차이가 `valueDiff` 이하일 수밖에 없고, 차이가 그 이하인 값은 같은 구간이거나 바로 옆 구간에만 있다.

```js
function containsNearbyAlmostDuplicate(nums, indexDiff, valueDiff) {
  const w = valueDiff + 1;
  const id = (x) => Math.floor(x / w); // 음수도 아래로 내려 같은 폭을 유지한다
  const bucket = new Map();            // 구간 번호 → 그 구간에 든 값 (창 안에 하나뿐)
  for (let i = 0; i < nums.length; i++) {
    const x = nums[i], b = id(x);
    if (bucket.has(b)) return true;                                        // 같은 구간
    if (bucket.has(b - 1) && x - bucket.get(b - 1) <= valueDiff) return true; // 왼쪽 이웃
    if (bucket.has(b + 1) && bucket.get(b + 1) - x <= valueDiff) return true; // 오른쪽 이웃
    bucket.set(b, x);
    if (i >= indexDiff) bucket.delete(id(nums[i - indexDiff])); // 창 밖으로 나간 값
  }
  return false;
}

console.log(containsNearbyAlmostDuplicate([10, 14, 12], 2, 2));
console.log(containsNearbyAlmostDuplicate([1, 5, 9, 1, 5, 9], 2, 3));
```

```text
true
false
```

구간 번호에 `Math.floor`를 쓰는 게 중요하다. `Math.trunc`나 정수 나눗셈은 0 쪽으로 자르기 때문에, 폭이 2일 때 -1과 1이 둘 다 0번 구간에 들어간다. 0번 구간만 폭이 두 배가 되어 차이가 2인 두 값을 중복으로 잘못 센다. Java의 `/`가 바로 이렇게 동작하니 Java로 풀 때는 `Math.floorDiv`를 쓴다. 이 함수는 무작위 배열 2만 개를 모든 쌍 비교와 대조해 결과가 하나도 다르지 않은 걸 확인했다.

버킷이 낯설면 정렬된 창으로 시작해도 된다. Java라면 `TreeSet`의 `ceiling`이 "어떤 값 이상 중 가장 작은 값"을 O(log k)에 찾아 준다. 지금 값을 `x`라 하면 `x - valueDiff` 이상 중 가장 작은 값이 `x + valueDiff` 이하인지만 보면 된다.

```java
static boolean containsNearbyAlmostDuplicate(int[] nums, int indexDiff, int valueDiff) {
    TreeSet<Long> window = new TreeSet<>(); // 최근 indexDiff칸의 값, 정렬된 상태
    for (int i = 0; i < nums.length; i++) {
        long x = nums[i];
        Long ceil = window.ceiling(x - valueDiff); // x - valueDiff 이상 중 가장 작은 값
        if (ceil != null && ceil <= x + valueDiff) return true;
        window.add(x);
        if (i >= indexDiff) window.remove((long) nums[i - indexDiff]);
    }
    return false;
}
// [10, 14, 12], 2, 2 → true
// [1, 5, 9, 1, 5, 9], 2, 3 → false
// [-2147483648, 2147483647], 1, 1 → false
```

값을 `long`으로 바꾼 데는 이유가 있다. `int`로 `x - valueDiff`를 계산하면 `x`가 `-2147483648`일 때 아래로 넘쳐 아주 큰 양수가 된다. 마지막 예시가 그 경우인데, `long`으로 계산하니 제대로 `false`가 나왔다. 시간은 O(n log k)로 버킷보다 느리지만 코드가 덜 까다롭다.

### 어떤 값이 몇 번 겹쳤는지 알려 달라면

질문이 "있나"에서 "무엇이 몇 번"으로 바뀌면 집합 대신 값별 횟수를 세는 해시맵을 쓴다. 이때는 일찍 멈출 수 없다. 끝까지 봐야 횟수가 확정되기 때문이다.

```js
function duplicates(nums) {
  const count = new Map(); // 값 → 나온 횟수
  for (const x of nums) count.set(x, (count.get(x) ?? 0) + 1);
  return [...count].filter(([, c]) => c > 1).map(([v, c]) => `${v}x${c}`);
}
console.log(duplicates([7, 3, 9, 3, 1, 7, 3]));
```

```text
[ '7x2', '3x3' ]
```

`Map`은 넣은 순서를 기억하니 결과도 처음 나온 순서(7, 3)로 나온다. 이렇게 값별 횟수를 세는 장부는 [Valid Anagram](/posts/leetcode-valid-anagram)과 [Top K Frequent Elements](/posts/leetcode-top-k-frequent-elements)에서도 첫 단계로 그대로 쓴다.

### 값 범위가 좁다면

값이 0 이상 10^6 이하처럼 좁게 정해져 있으면 해시가 필요 없다. 값을 그대로 칸 번호로 쓰는 배열(또는 비트 하나씩 쓰는 비트맵)을 만든다.

```js
function containsDuplicateSmallRange(nums) {
  const seen = new Uint8Array(1_000_001); // 값 0..10^6 전용
  for (const x of nums) {
    if (seen[x]) return true;
    seen[x] = 1;
  }
  return false;
}
console.log(containsDuplicateSmallRange([5, 1000000, 0, 5]), containsDuplicateSmallRange([0, 1, 2]));
```

```text
true false
```

시간은 해시와 같은 O(n)이지만 해시 계산과 충돌이 없어 상수가 훨씬 작다. 대신 공간이 값 범위 크기만큼 든다. 원래 문제처럼 범위가 20억이면 비트맵으로도 약 250MB라 쓰지 않는다.

### 데이터가 메모리에 다 안 들어간다면

수억 개의 ID에서 중복을 찾아야 한다면 두 가지 길이 있다. 하나는 해시 값으로 파일을 여러 조각으로 나누는 것이다. 같은 값은 같은 해시를 가지니 반드시 같은 조각에 들어가고, 조각 하나는 메모리에 올려 집합으로 확인한다. 다른 하나는 외부 정렬 후 이웃 비교다.

조금 틀려도 되는 상황이라면 블룸 필터를 쓴다. 비트 배열과 해시 함수 몇 개로 "확실히 없다" 또는 "아마 있다"를 답하는 구조라, 메모리를 아주 적게 쓰는 대신 가끔 없는 값을 있다고 한다(거짓 양성). "아마 있다"가 나온 값만 정확한 저장소에서 다시 확인하는 식으로 쓴다.

비슷한 생각을 쓰는 다른 문제로는, 같은 글자 구성을 키로 바꿔 묶는 [Valid Anagram](/posts/leetcode-valid-anagram)과 [Group Anagrams](/posts/leetcode-group-anagrams), 배열 안에서 값의 범위를 이용해 중복을 찾는 LeetCode 287. Find the Duplicate Number가 있다. 287번은 배열을 고치지 않고 O(1) 공간으로 풀라고 해서, 인덱스를 연결 리스트처럼 따라가는 [사이클 찾기](/posts/leetcode-linked-list-cycle)로 이어진다.

## 면접에서 나올 만한 질문

### 정렬 풀이와 해시 집합 풀이 중 무엇을 고르나요?

기본은 해시 집합이다. 평균 O(n)이고 중복을 찾는 즉시 멈출 수 있다. 메모리를 아껴야 하거나 입력이 이미 정렬돼 있으면 정렬 풀이를 고른다. 정렬은 O(n log n)이지만 입력을 그대로 정렬해도 된다면 추가 공간이 거의 없다.

### `new Set(nums).size !== nums.length`와 반복문 풀이의 차이는요?

시간과 공간 등급은 둘 다 O(n)으로 같다. 차이는 일찍 멈추는지다. 반복문은 중복을 찾는 순간 끝나지만, 한 줄 풀이는 항상 배열 전체를 집합에 넣는다. 0번과 1번 칸이 같은 10만 개 배열에서 0.002ms와 5ms 정도로 차이가 났다.

### 중복이 없을 때와 있을 때 어느 쪽이 최악인가요?

중복이 없을 때가 최악이다. 없다는 걸 확인하려면 모든 값을 다 봐야 하기 때문이다. 해시 풀이는 값 n개를 전부 집합에 넣어 공간도 가장 많이 쓴다. 반대로 중복이 앞쪽에 있으면 집합 풀이는 거의 바로 끝난다.

### 공간을 O(1)로 할 수 있나요?

입력을 고쳐도 된다면 제자리 정렬 후 이웃 비교로 추가 공간을 정렬 구현이 쓰는 만큼(Java `int[]`면 O(log n))으로 줄일 수 있다. 시간은 O(n log n)이 된다. 입력을 고치면 안 되고 값 범위에 특별한 성질도 없으면, O(n²) 비교 말고는 O(1) 공간 방법이 없다.

### 인덱스 차이가 k 이하인 중복만 찾으라면 어떻게 바꾸나요?

집합을 최근 k칸만 담는 슬라이딩 윈도로 바꾼다. 새 값을 보기 전에 창에 있는지 확인하고, 넣은 뒤 창이 k칸을 넘으면 `nums[i - k]`를 뺀다. 시간 O(n), 공간 O(k)다. 값 차이까지 허용하면 값을 폭 `t + 1` 구간으로 나눈 버킷을 써서 같은 구간과 양옆 구간만 확인한다.

### 값 범위가 작다고 하면 무엇이 달라지나요?

해시 대신 값을 그대로 인덱스로 쓰는 배열이나 비트맵을 쓴다. 해시 계산과 충돌이 없어서 같은 O(n)이라도 훨씬 빠르다. 공간은 값 범위에 비례하니 범위가 n보다 아주 크면 오히려 손해다.

### 이 문제의 해시 풀이가 느려질 수 있는 입력이 있나요?

있다. 해시 조회는 평균 O(1)이지 최악 O(1)이 아니라서, 일부러 같은 칸에 떨어지는 값만 넣으면 조회가 느려진다. 정수 해시가 값 그대로인 언어에서 특히 그렇다. 최악을 보장해야 하는 서비스라면 정렬 풀이나, 충돌 칸을 트리로 바꾸는 구현(Java 8 이후 `HashMap`)을 고려한다. 해시 플러딩은 [해시맵 글](/posts/ds-hash-map#일부러-충돌을-만드는-공격)에 있다.
