지금까지의 창 문제는 "가장 긴" 또는 "가장 짧은" 구간 하나를 찾았다. 이 문제는 조건을 만족하는 구간이 몇 개인지 센다. 구간이 많으면 수억 개라 하나씩 셀 수는 없다. 창을 미는 틀은 [슬라이딩 윈도 패턴](/posts/sliding-window-pattern)과 같지만, 오른쪽 끝이 한 칸 갈 때마다 창 길이만큼을 한꺼번에 더하는 세는 요령이 새로 나온다. 이 요령은 허브 글의 "정확히 K개는 많아야 K개 둘의 차로"에서도 쓰였고, 개수를 묻는 창 문제 대부분이 이 모양이다.

곱이라서 생기는 문제도 있다. 합은 빼면 되지만 곱은 나눠야 하고, 곱은 금방 커져서 오버플로가 난다. 곱을 로그의 합으로 바꿔 [이분 탐색](/posts/binary-search)으로 푸는 풀이도 있는데, 부동소수점 오차 때문에 그대로 쓰면 틀린다. 출발점마다 곱하기, 로그 누적 합과 이분 탐색, 창 세 가지를 보고, 각각에서 언제 틀리는지 실제 입력으로 확인한다. 문제 원문은 [LeetCode 713](https://leetcode.com/problems/subarray-product-less-than-k/)이다. 코드는 Node.js 22, Python 3.13, Java로 모두 돌렸다.

## 곱이 k보다 작은 구간은 몇 개인가

양의 정수 배열 `nums`와 정수 `k`가 주어진다. 원소를 모두 곱한 값이 `k`보다 작은 연속 부분 배열의 개수를 센다.

풀이에 영향을 주는 조건은 이렇다.

- 길이는 1 이상 3만 이하다. 구간이 약 4.5억 개라 하나씩 세면 안 된다. 답 자체도 4.5억까지 갈 수 있지만 Java `int`(약 21억)에 들어간다.
- 원소는 1 이상 1,000 이하다. 1이 있어서 곱이 늘지 않고 그대로일 수 있다. 0은 없다. 0이 있으면 나눌 수 없어서 창이 깨진다.
- `k`는 0 이상 100만 이하다. `k`가 0이나 1이면 곱이 1 이상이라 어떤 구간도 통과하지 못한다. 답은 0이고, 이 경우를 따로 막지 않으면 창 코드가 이상하게 동작한다.

## 다섯 칸에서 열한 개를 세어 보기

예시는 `nums = [4, 2, 5, 1, 3]`, `k = 20`이다. 길이별로 곱을 구해 20 미만인 것을 센다.

```text
길이  구간과 곱                                  20 미만
 1    4, 2, 5, 1, 3                              5개
 2    4·2=8, 2·5=10, 5·1=5, 1·3=3                4개
 3    4·2·5=40, 2·5·1=10, 5·1·3=15               2개
 4    4·2·5·1=40, 2·5·1·3=30                     0개
 5    4·2·5·1·3=120                              0개
```

모두 11개다. 표에서 길이 3짜리 `4·2·5`가 40으로 탈락하니 그걸 품은 길이 4, 5짜리 `4·2·5·1`과 `4·2·5·1·3`도 당연히 탈락한다. 원소가 1 이상이라 구간을 넓히면 곱이 줄지 않기 때문이다. 거꾸로 통과한 구간 안에 든 더 짧은 구간은 모두 통과한다.

이번엔 같은 11개를 "어디서 끝나나"로 나눠 보자.

```text
끝나는 칸  그 칸에서 끝나는 통과 구간          개수
 0 (4)    [4]                                  1
 1 (2)    [2], [4,2]                           2
 2 (5)    [5], [2,5]                           2
 3 (1)    [1], [5,1], [2,5,1]                  3
 4 (3)    [3], [1,3], [5,1,3]                  3
```

1 + 2 + 2 + 3 + 3 = 11이다. 각 줄의 통과 구간은 언제나 "끝 칸 하나, 끝 두 칸, 끝 세 칸…"처럼 끝에서부터 이어지다가 어느 길이에서 끊긴다. 끊기는 자리만 알면 개수가 나온다. 아래 창 풀이는 이 끊기는 자리를 왼쪽 끝 `l`로 들고 다닌다.

## 출발점마다 곱하다가 넘치면 멈춘다

출발점 `i`를 고정하고 오른쪽으로 곱해 가며 `k` 미만인 동안 센다. 한 번 `k` 이상이 되면 더 길게 가도 곱이 줄지 않으니 멈춘다.

```js
function prodBrute(nums, k) {
  let count = 0;
  for (let i = 0; i < nums.length; i++) {
    let p = 1;
    for (let j = i; j < nums.length; j++) {
      p *= nums[j];
      if (p >= k) break; // 더 길게 가도 k 미만이 될 수 없다
      count++;           // 구간 i..j는 통과
    }
  }
  return count;
}
```

최악 O(n²), 공간 O(1)이다. 원소가 1~1000 무작위면 곱이 금방 커져 일찍 멈추니 3만 개에서 0.16ms였다. 하지만 1이 대부분인 배열, 예를 들어 1,000개 중 하나만 2이고 `k`가 100만인 3만 개짜리 입력에서는 출발점마다 수천 칸을 곱해 496ms가 걸렸다. 길이 제한이 더 크거나 테스트가 여러 개면 위험하다.

`break`는 속도만이 아니라 정확성에도 중요하다. 아래 "곱 창의 Python·Java 판"에서 보겠지만, Java에서 `break` 없이 `int`로 계속 곱하면 곱이 오버플로해서 음수나 작은 수가 되고, 그게 `k` 미만으로 잘못 세어진다.

## 곱을 로그의 합으로 바꾸면

곱은 다루기 불편하다. 로그를 씌우면 곱이 합으로 바뀐다. `log(a·b) = log a + log b`이고 로그는 증가 함수라 `a·b < k`와 `log a + log b < log k`가 같은 말이다.

합이 되면 누적 합을 쓸 수 있다. `pre[i]`를 앞에서 i칸의 로그 합으로 두면 구간 i..j − 1의 곱이 `k` 미만인지는 `pre[j] - pre[i] < log k`로 판정된다. 원소가 1 이상이라 로그는 0 이상이고, `pre`는 줄지 않는 순서다. 그래서 출발점 i마다 이 조건을 만족하는 가장 큰 j를 이분 탐색으로 찾으면, i에서 출발하는 통과 구간 수가 j − i다.

```js
function prodLog(nums, k) {
  if (k <= 1) return 0;
  const n = nums.length;
  const pre = new Array(n + 1).fill(0); // pre[i] = 앞에서 i칸의 log 합
  for (let i = 0; i < n; i++) pre[i + 1] = pre[i] + Math.log(nums[i]);
  const limit = Math.log(k) - 1e-9;    // 오차를 감안해 기준을 살짝 낮춘다
  let count = 0;
  for (let i = 0; i < n; i++) {
    // pre[j] - pre[i] < limit 인 가장 큰 j (j = i면 빈 구간이라 늘 성립)
    let lo = i, hi = n;
    while (lo < hi) {
      const mid = (lo + hi + 1) >> 1;  // lo = mid로 좁히니 올림
      if (pre[mid] - pre[i] < limit) lo = mid;
      else hi = mid - 1;
    }
    count += lo - i; // i..i, i..i+1, ..., i..lo-1
  }
  return count;
}
```

시간 O(n log n), 공간 O(n)이다. 1이 대부분인 입력에서 8ms로 브루트포스의 60분의 1이었다. 원소가 무작위인 입력에서는 2.6ms로 오히려 브루트포스(0.16ms)보다 느렸다. 출발점마다 이분 탐색을 하니 구간이 짧을 때는 손해다.

이 풀이의 장점은 곱을 실제로 계산하지 않아 오버플로가 없다는 것이다. 단점은 이 코드의 `- 1e-9` 한 줄에 숨어 있다.

## 로그에 여유를 두지 않으면 생기는 일

위 코드에서 `limit`를 `Math.log(k)` 그대로 두면 어떻게 될까. 무작위로 작은 입력 2만 개를 넣어 브루트포스와 비교했더니 215개에서 답이 달랐다. 가장 짧은 예가 `nums = [7, 2]`, `k = 2`다. 정답은 0이다. 2는 2보다 작지 않다. 그런데 여유 없는 판은 1을 낸다.

```js
const b = (Math.log(7) + Math.log(2)) - Math.log(7); // 구간 [2]의 로그 합
console.log(b, Math.log(2), b < Math.log(2));
const a = Math.log(2) + Math.log(5) + Math.log(3);   // 구간 [2, 5, 3]의 로그 합
console.log(a, Math.log(30), a < Math.log(30));
```

```text
0.6931471805599452 0.6931471805599453 true
3.401197381662155 3.4011973816621555 true
```

`log 7 + log 2`를 더하는 순간 반올림이 일어나고, 거기서 `log 7`을 다시 빼면 원래의 `log 2`보다 아주 조금 작은 값이 남는다. 그 아주 작은 차이 때문에 "2 < 2"가 참이 된다. 두 번째 줄은 `[2, 5, 3]`의 곱이 정확히 30인데, 로그 세 개를 더한 값이 `log 30`보다 4.4 × 10^-16만큼 작게 나와서 `k = 30`일 때 통과로 세어진다. `[2, 5, 3, 10]`, `k = 30`에서 정답 6 대신 7이 나온다.

곱이 정확히 `k`와 같은 경계에서만 틀린다는 게 고약하다. 예시 몇 개로는 거의 드러나지 않는다. 기준을 `log k - 1e-9`처럼 살짝 낮추면 경계에 걸린 구간이 확실히 탈락한다. 원소가 1000 이하 정수라 곱이 `k`보다 작은 경우와 같은 경우의 로그 차이는 `log(k) - log(k - 1)`, 곧 약 1/k(최소 10^-6쯤) 이상 벌어지니 10^-9 정도의 여유로는 진짜 통과 구간을 잘못 떨어뜨리지 않는다. 경계 근처의 구간은 곱이 100만 미만이라 1이 아닌 원소가 많아야 스무 개쯤(2^20이 100만을 넘는다)이고, 1의 로그 0을 더하는 건 오차가 없다. 그래서 그 구간의 로그 합에 쌓이는 오차는 10^-10 정도로 이 여유 안에 들어간다. 1이 70%인 길이 3만 무작위 배열 스무 개에 여러 `k`를 넣어 창 풀이와 비교해도 차이가 없었다.

Python도 같은 IEEE 754 배정밀도 실수를 쓰니 사정이 같다. 다만 버전에 따라 결과가 달라지는 자리가 하나 있다.

```python
import math
print(math.log(2) + math.log(5) + math.log(3) < math.log(30))   # + 로 차례로 더한다
print(sum(math.log(x) for x in [2, 5, 3]) < math.log(30))      # 내장 sum
```

```text
True
False
```

Python 3.13에서 `+`로 더하면 JS와 똑같이 참(틀린 판정)이 나오고, 내장 `sum`으로 더하면 거짓이 나온다. Python 3.12부터 `sum`이 실수를 더할 때 오차를 보정하는 합산(Neumaier 방식)을 쓰기 때문이다. 그렇다고 문제가 풀린 건 아니다. 누적 합은 `itertools.accumulate`나 `+`로 만들 테니 보정이 적용되지 않고, 보정을 해도 각 `math.log` 값 자체가 이미 반올림된 값이라 경계에서 틀릴 가능성은 남는다. 어느 언어든 여유값이 필요하다.

그래도 면접에서는 이 풀이를 마지막 답으로 내지 않는 편이 좋다. 여유를 얼마로 둘지가 입력 범위에 따라 달라지고, 그걸 설명해야 한다. 정수만으로 계산하는 창 풀이가 있으니 그쪽이 안전하다. 로그 풀이는 "곱을 합으로 바꿔 누적 합과 이분 탐색을 쓸 수 있다"는 생각을 보여 주는 용도로 기억해 두면 된다.

## 오른쪽 끝마다 창 길이만큼 더한다

앞의 "어디서 끝나나" 표를 다시 보자. 끝나는 칸이 오른쪽으로 갈 때 통과 구간이 끊기는 자리(가장 왼쪽 출발점)는 뒤로 가지 않았다. 그렇다면 창 `[l, r]`을 "곱이 `k` 미만인 가장 긴, r에서 끝나는 구간"으로 유지할 수 있다. 오른쪽 칸을 곱하고, 곱이 `k` 이상이면 왼쪽 칸을 나눠 내며 `l`을 당긴다.

창이 정해지면 r에서 끝나는 통과 구간은 `[r, r]`, `[r-1, r]`, …, `[l, r]`이고 그 개수가 `r - l + 1`이다. 창보다 짧은 구간은 곱이 더 작거나 같으니 모두 통과하고, 창보다 긴 구간(`l - 1`에서 시작)은 방금 나눠 낸 이유 그대로 탈락한다.

```js
function numSubarrayProductLessThanK(nums, k) {
  if (k <= 1) return 0;       // 곱은 1 이상이라 통과하는 구간이 없다
  let l = 0, prod = 1, count = 0;
  for (let r = 0; r < nums.length; r++) {
    prod *= nums[r];           // 오른쪽 칸을 곱한다
    while (prod >= k) {        // k 이상이면
      prod /= nums[l++];       // 왼쪽 칸을 나눠 낸다
    }
    count += r - l + 1;        // r에서 끝나는 통과 구간 수
  }
  return count;
}
```

`l`과 `r`이 각각 한 방향으로 많아야 n번 움직이니 전체 O(n), 공간 O(1)이다. 1이 대부분인 입력에서 1.8ms, 무작위 입력에서 0.37ms로 두 경우 모두 빠르다. 곱을 정수로만 다루니 로그 풀이의 오차 걱정도 없다. `prod /= nums[l]`은 `prod`가 `nums[l]`을 곱해서 만든 값이라 언제나 나누어떨어진다. JS에서는 실수 나눗셈이지만 결과가 정확한 정수로 나온다.

이 "오른쪽 끝마다 `r - l + 1`을 더한다"는 세는 요령은 창이 단조로운 조건(구간을 줄이면 계속 만족)일 때 쓸 수 있다. 서로 다른 값이 많아야 K개인 부분 배열 수, 합이 `k` 미만인 양수 부분 배열 수가 모두 같은 코드 모양이다.

## 출발점을 기준으로 세는 창

같은 개수를 출발점 기준으로 셀 수도 있다. 이번엔 `l`을 바깥 반복문으로 두고, `r`을 "곱이 `k` 미만인 동안" 늘린다. 창을 반열린 구간 `[l, r)`로 두면 l에서 출발하는 통과 구간은 `[l, l]`부터 `[l, r - 1]`까지 `r - l`개다.

```js
function leftAnchored(nums, k) {
  if (k <= 1) return 0;
  const n = nums.length;
  let r = 0, prod = 1, count = 0; // 창은 [l, r) 반열린 구간
  for (let l = 0; l < n; l++) {
    if (r < l) { r = l; prod = 1; }  // 창이 비었으면 l에서 다시 시작
    while (r < n && prod * nums[r] < k) prod *= nums[r++]; // 곱해도 k 미만이면 늘린다
    count += r - l;                  // l에서 출발하는 통과 구간 수
    if (r > l) prod /= nums[l];      // 다음 출발점으로 가기 전에 l을 뺀다
  }
  return count;
}
console.log(leftAnchored([4, 2, 5, 1, 3], 20), leftAnchored([10, 5, 2, 6], 100), leftAnchored([5], 5));
```

```text
11 8 0
```

앞의 "어디서 끝나나" 표 대신 "어디서 시작하나"로 나눈 셈이다. 예시에서는 0번 출발 2개(`[4]`, `[4,2]`), 1번 출발 3개, 2번 출발 3개, 3번 출발 2개, 4번 출발 1개로 11개다. 이 판은 곱하기 전에 "곱해도 되나"를 먼저 보니 창의 곱이 언제나 `k` 미만으로 유지되고, `k` 이상인 값이 `prod`에 잠깐이라도 들어가는 일이 없다. 곱이 넘칠 수 있는 큰 수에서는 이 점이 장점이다.

대신 `[5]`, `k = 5`처럼 원소 하나만으로 `k` 이상이면 창이 비어 `r < l`이 되는 경우를 따로 처리해야 한다. 위 코드의 첫 `if`와 마지막 `if`가 그 일을 한다. 오른쪽 끝 기준 판은 그런 처리가 없어도 `r - l + 1`이 0이 되어 저절로 맞으니, 코드가 짧은 쪽은 오른쪽 끝 기준이다. 무작위 입력 5,000개로 두 판이 같은 답을 내는지 확인했다.

## k가 1 이하일 때 창이 뒤집힌다

창 코드 맨 앞의 `if (k <= 1) return 0`이 왜 필요한지 빼고 돌려 보면 안다.

```js
function noGuard(nums, k) {
  let l = 0, prod = 1, count = 0;
  for (let r = 0; r < nums.length; r++) {
    prod *= nums[r];
    while (prod >= k) prod /= nums[l++];
    count += r - l + 1;
  }
  return count;
}
console.log(noGuard([1, 2, 3], 1), noGuard([1, 2, 3], 0), noGuard([2, 3], 1));
```

```text
-3 -6 -2
```

개수가 음수로 나온다. `k = 1`이면 창을 다 비워 곱이 1(빈 곱)이 돼도 여전히 `1 >= 1`이라 `while`이 멈추지 않는다. `l`이 `r`을 넘어 배열 밖까지 가고, `nums[l]`이 `undefined`라 `prod`가 `NaN`이 되고 나서야 비교가 거짓이 되어 빠져나온다. 그때 `r - l + 1`이 음수다. Java라면 `nums[l]`에서 `ArrayIndexOutOfBoundsException`이 나고, Python이면 `IndexError`다. 언어마다 다르게 망가지지만 셋 다 틀렸다.

원인은 "빈 창은 조건을 만족한다"는 창의 기본 전제가 깨진 것이다. 빈 구간의 곱은 1인데 `k`가 1 이하면 빈 창조차 조건(`곱 < k`)을 만족하지 못한다. 그래서 줄이기가 끝날 자리가 없다. 맨 앞에서 0을 돌려주거나, `while (l <= r && prod >= k)`처럼 창이 비면 멈추게 막는다. 후자로 막아도 빈 창의 개수 `r - l + 1 = 0`이 더해지니 답은 0으로 맞다.

## 곱 창의 Python·Java 판

```python
from typing import List

class Solution:
    def numSubarrayProductLessThanK(self, nums: List[int], k: int) -> int:
        if k <= 1:                     # 곱은 1 이상이라 1 미만이 될 수 없다
            return 0
        l, prod, count = 0, 1, 0
        for r, x in enumerate(nums):
            prod *= x                  # 오른쪽 칸을 곱한다
            while prod >= k:           # k 이상이면 왼쪽을 나눠 낸다
                prod //= nums[l]       # 정수 나눗셈. 나누어떨어지니 정확하다
                l += 1
            count += r - l + 1         # r에서 끝나는 구간 개수
        return count
```

```java
class Solution {
    public int numSubarrayProductLessThanK(int[] nums, int k) {
        if (k <= 1) return 0;
        int l = 0, count = 0;
        long prod = 1; // k 미만 × 1000 이하라 int로도 되지만 여유를 둔다
        for (int r = 0; r < nums.length; r++) {
            prod *= nums[r];
            while (prod >= k) prod /= nums[l++];
            count += r - l + 1; // 최대 n(n+1)/2 = 약 4.5억이라 int에 들어간다
        }
        return count;
    }
}
```

`([4,2,5,1,3], 20)`, `([10,5,2,6], 100)`, `([1,2,3], 0)`, `([1,2,3], 1)`, `([1,1,1], 2)`, `([5], 5)`, `([5], 6)`, `([2,5,3,10], 30)`을 넣어 세 언어 모두 11, 8, 0, 0, 6, 0, 1, 6이 나왔다. 세 JS 풀이(로그 풀이는 여유를 둔 판)가 같은 답을 내는지는 원소 1~12, 길이 8 이하, `k` 0~199 무작위 입력 2만 개로 확인했다.

언어별로 짚을 점이다.

- Python은 `/`가 실수 나눗셈이라 `prod /= nums[l]`로 쓰면 `prod`가 `float`가 된다. 이 문제 크기에서는 값이 정확하게 남지만, 정수로 계속 다루려면 `//=`를 쓴다. 나누어떨어지니 `//`도 정확하다.
- Java에서 창 안의 곱은 `k`(100만 미만)보다 작은 상태에서 1,000 이하를 곱하니 많아야 10억 미만이라 `int`에 들어간다. 그래도 제약이 바뀌면 바로 넘치는 자리라 `long`으로 두는 습관이 낫다.
- 브루트포스를 `break` 없이 Java `int`로 짜면 오버플로가 답을 틀리게 한다. `[1000, 1000, 1000, 1000, 1000]`, `k = 100`이면 정답은 0인데, `break` 없이 돌린 판은 3을 냈다. 1000을 네 번 곱한 10^12가 `int`에서 −727,379,968로 감겨 `k` 미만이 됐기 때문이다. JS는 곱이 커지면 `Infinity`까지 가지만 정수 오버플로로 감기지는 않는다.

## 세 풀이의 시간과 한계

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 출발점마다 곱하기 | O(n²) | O(1) | 정답 확인용. 곱이 빨리 커지면 실제로는 빠르다 |
| 로그 누적 합 + 이분 탐색 | O(n log n) | O(n) | 곱을 합으로 바꾸는 생각을 보여 줄 때. 오차 여유가 필요하다 |
| 곱 창, 끝마다 r − l + 1 | O(n) | O(1) | 기본 답 |

길이 3만, `k` = 100만에서 잰 시간이다.

```text
                       1이 대부분인 입력   1~1000 무작위
출발점마다 곱하기          496.31 ms          0.16 ms
로그 + 이분 탐색             8.04 ms          2.63 ms
곱 창                        1.79 ms          0.37 ms
```

1이 대부분인 입력의 답은 340,141,588개였다. 답이 3억이 넘어도 창은 2ms가 안 걸린다. 구간을 하나씩 세지 않고 오른쪽 끝마다 한꺼번에 더하기 때문이다. 브루트포스는 이 3억 개를 하나씩 세느라 느리다.

## 개수를 잘못 세는 코드들

창을 찾는 데 익숙하면 창 하나를 하나로 센다.

```js
while (prod >= k) prod /= nums[l++];
count++; // 창 하나를 하나로 센다
```

`([4,2,5,1,3], 20)`에서 5가 나온다. 정답은 11이다. 이건 "오른쪽 끝마다 가장 긴 창"의 개수, 곧 n을 센 것이다. 각 창 안에는 r에서 끝나는 더 짧은 구간들이 함께 들어 있다.

가장 긴 창이 끝날 때마다 그 길이 L로 L(L + 1)/2를 더하는 방법도 떠올리기 쉽다. 길이 L 구간 안의 연속 부분 배열 수가 L(L + 1)/2라서다.

```js
// 창이 막히기 직전마다 L(L+1)/2를 더한다
if (prod >= k) { const L = r - l; count += L * (L + 1) / 2; /* 그다음 줄인다 */ }
```

예시에서 15가 나온다. 첫 창 `[4, 2]`(3개)와 다음 창 `[2, 5, 1]`(6개), 마지막 창 `[5, 1, 3]`(6개)을 더하면 15인데, `[2]`, `[5]`, `[1]`, `[2, 5]`, `[5, 1]`이 두 창에 겹쳐 두 번 세어졌다. 겹친 부분을 빼 주면 맞출 수는 있지만 복잡하다. 오른쪽 끝을 기준으로 세면 각 구간이 정확히 한 번, 자기 끝 칸에서만 세어지니 겹칠 일이 없다.

비교를 `prod > k`로 쓰면 곱이 정확히 `k`인 구간을 통과로 센다. 문제는 "`k`보다 작다"라 `>=`일 때 줄여야 한다. `([2,5,3,10], 30)`에서 6 대신 7이 나온다. 로그 풀이에서 여유를 두지 않을 때와 같은 증상인데, 원인은 오차가 아니라 부등호다.

`k <= 1` 처리를 빠뜨리면 음수가 나온다는 건 위에서 봤다.

## 곱 대신 다른 조건이라면

### 합이 k 미만인 구간의 개수

원소가 양수면 곱을 합으로, 곱셈을 덧셈으로, 나눗셈을 뺄셈으로 바꾸면 끝이다.

```js
function sumLess(nums, k) {
  let l = 0, sum = 0, count = 0;
  for (let r = 0; r < nums.length; r++) {
    sum += nums[r];
    while (l <= r && sum >= k) sum -= nums[l++]; // 빈 합 0도 k 이상이면 멈춘다
    count += r - l + 1;
  }
  return count;
}
console.log(sumLess([4, 2, 5, 1, 3], 8));
```

```text
9
```

빈 구간의 합은 0이라 `k`가 0 이하일 때 곱 문제의 `k <= 1`과 같은 일이 생긴다. 여기서는 `l <= r`로 막았다. 같은 묶음의 [Minimum Size Subarray Sum](/posts/leetcode-minimum-size-subarray-sum)에서 본 "합이 target 이상인 구간 개수"는 전체 구간 수에서 이 개수를 빼도 나온다. 전체는 n(n + 1)/2다. 양수가 아니면 창 대신 누적 합 위에서 정렬된 구조나 병합 정렬로 센다(LeetCode 327 Count of Range Sum).

### 원소에 0이 있다면

0이 하나라도 들어간 구간의 곱은 0이라 `k`가 1 이상이면 무조건 통과한다. 그런데 0을 `prod`에 곱하면 그 뒤로 나눠 낼 방법이 없어서 창이 깨진다. 0을 창에 넣지 않고, "가장 최근 0의 위치" `lastZero`만 기억해 둔다. r에서 끝나는 구간 가운데 `lastZero` 이하에서 출발하는 것은 0을 품어 모두 통과하고, 그 뒤에서 출발하는 것은 0 없는 창으로 센다.

```js
function withZeros(nums, k) {
  if (k <= 0) return 0;               // 곱은 0 이상이라 0 미만이 될 수 없다
  let lastZero = -1, l = 0, prod = 1, count = 0;
  for (let r = 0; r < nums.length; r++) {
    if (nums[r] === 0) {
      lastZero = r;                   // 이 0을 품은 구간은 곱이 0이라 모두 통과
      l = r + 1; prod = 1;            // 0 뒤에서 창을 새로 시작한다
      count += r + 1;                 // 0..r에서 출발해 r에서 끝나는 구간
      continue;
    }
    prod *= nums[r];
    while (l <= r && prod >= k) prod /= nums[l++]; // 창은 0 뒤에서만, 비면 멈춘다
    count += (lastZero + 1) + (r - l + 1); // 0을 품은 구간 + 창 안에서 출발한 구간
  }
  return count;
}
console.log(withZeros([4, 0, 5, 1, 3], 20), withZeros([0, 0], 1), withZeros([3, 0, 7], 5));
```

```text
15 3 5
```

`[3, 0, 7]`, `k = 5`에서는 `[7]`만 탈락하고 나머지 다섯 개가 통과한다. 처음 짠 판은 "0이 있으면 줄이지 않는다"로 썼다가 0이 창에서 빠져나가는 순간을 처리하지 못해 틀렸다. 0을 창 밖의 위치 하나로 따로 들고 가는 쪽이 깔끔하다. `k = 1`이면 0 없는 구간은 하나도 통과하지 못해 창이 늘 비는데, `l <= r` 조건이 그때 줄이기를 멈춘다. 0이 25% 섞인 무작위 입력 5,000개로 이중 반복문과 같은 답을 내는지 확인했다.

### 음수가 있다면

곱의 부호가 오락가락해서 "구간을 넓히면 곱이 커진다"가 성립하지 않는다. 창은 쓸 수 없다. 개수를 세는 문제는 거의 브루트포스로 가야 하고, 곱의 최댓값을 묻는 152번 [Maximum Product Subarray](/posts/leetcode-maximum-product-subarray)는 "지금까지의 최대 곱과 최소 곱"을 함께 들고 가는 [동적 계획법](/posts/dynamic-programming)으로 푼다. 음수를 곱하면 최소가 최대로 뒤집히기 때문이다.

### 곱이 k 이하라면

부등호만 바꾼다. 줄이는 조건이 `prod > k`가 되고, 빈 창의 곱 1이 조건을 만족하지 못하는 경우는 `k`가 0일 때뿐이니 맨 앞의 처리를 `k < 1`로 바꾼다.

### 곱이 k 이상인 구간을 세라면

전체 구간 수에서 빼는 게 가장 간단하다. 길이 n 배열의 연속 구간은 n(n + 1)/2개다.

```js
function atLeast(nums, k) {
  const n = nums.length;
  return n * (n + 1) / 2 - numSubarrayProductLessThanK(nums, k); // 전체 - 미만
}
console.log(atLeast([4, 2, 5, 1, 3], 20), atLeast([1, 2, 3], 1));
```

```text
4 6
```

예시에서 곱이 20 이상인 구간은 `4·2·5`, `4·2·5·1`, `2·5·1·3`, `4·2·5·1·3` 네 개다. `k = 1`이면 모든 구간이 1 이상이라 6개 전부다. Java라면 n(n + 1)/2를 `int`로 계산할 때 n이 3만이면 n(n + 1)이 9억이라 괜찮지만, n이 46,341 이상이면 곱셈 단계에서 `int`를 넘는다. `long`으로 계산하는 습관을 들인다.

### 곱이 정확히 k인 구간을 세라면

원소가 정수라 "곱이 정확히 k"는 "곱이 k + 1 미만"에서 "곱이 k 미만"을 뺀 것이다. 허브 글의 "정확히 K개는 많아야 K개 둘의 차로"와 같은 요령이다.

```js
const exactly = (nums, k) =>
  numSubarrayProductLessThanK(nums, k + 1) - numSubarrayProductLessThanK(nums, k);
console.log(exactly([4, 2, 5, 1, 3], 10), exactly([2, 5, 3, 10], 30), exactly([1, 1, 1], 1));
```

```text
2 2 6
```

곱이 정확히 10인 구간은 `[2, 5]`와 `[2, 5, 1]` 두 개다. 1이 끼면 곱이 같은 구간이 여러 개 생긴다는 게 보인다. 무작위 입력 5,000개로 이중 반복문과 같은 개수가 나오는지 확인했다. 창을 직접 "정확히 k"로 맞추려고 하면 1 때문에 줄여도 곱이 그대로인 경우가 생겨 언제 줄일지가 한 방향으로 정해지지 않는다. 차로 바꾸는 이유가 그것이다.

### 숫자가 하나씩 흘러 들어온다면

스트림으로 원소가 오고, 올 때마다 "방금 원소로 끝나는 통과 구간 수"를 답해야 한다면 오른쪽 끝 기준 창이 그대로 맞는다. 다만 왼쪽을 나눠 내려면 창 안의 원소를 기억해야 하니 창을 큐로 들고 있어야 한다. 원소가 1이 대부분이면 창이 아주 길어질 수 있어 메모리가 창 길이만큼 든다. 1은 곱에 영향이 없으니 "1이 몇 개 이어졌나"만 묶어서 큐에 넣으면 1이 아닌 원소 수(많아야 log₂k개쯤)로 줄일 수 있다.

### 구간 목록을 모두 돌려 달라면

답이 수억 개일 수 있으니 시간과 메모리가 답의 크기에 비례할 수밖에 없다. 창은 그대로 두고, r마다 `l`부터 `r`까지 출발점을 돌며 구간을 만든다. 면접에서 이걸 물으면 "출력 크기가 O(n²)일 수 있다"는 걸 먼저 말하는 게 요점이다.

## 면접에서 나올 만한 질문

### 오른쪽 끝마다 r − l + 1을 더하는 이유는요?

창 `[l, r]`은 r에서 끝나면서 곱이 k 미만인 가장 긴 구간이다. 원소가 1 이상이라 그보다 짧은 `[l+1, r]`, …, `[r, r]`도 모두 곱이 k 미만이다. 그래서 r에서 끝나는 통과 구간은 정확히 r − l + 1개이고, 각 구간은 자기 끝 칸에서 한 번만 세어진다.

### 왜 창이 O(n)인가요?

`l`과 `r` 모두 앞으로만 움직이고 각각 많아야 n번 움직인다. 곱하기와 나누기가 칸마다 한 번씩이니 전체가 O(n)이다. 답이 수억 개여도 하나씩 세지 않고 끝마다 한꺼번에 더하므로 시간은 답의 크기와 상관없다.

### k가 0이나 1이면 어떻게 되나요?

원소가 1 이상이라 어떤 곱도 1 이상이니 답은 0이다. 이 처리를 빼면 빈 창의 곱 1조차 조건을 만족하지 못해 줄이는 `while`이 `l`을 r 너머로 보낸다. JS는 음수 개수가 나오고, Java와 Python은 인덱스 예외가 난다.

### 오버플로는 괜찮나요?

창 안의 곱은 k 미만에서 1,000 이하를 곱한 값이라 10억 미만이고, 넘치는 즉시 나눠 낸다. 그래서 Java `int`로도 된다. 위험한 건 브루트포스를 `break` 없이 짠 경우로, `int`가 감겨 작은 값이 되면 틀린 구간이 세어진다.

### 로그로 바꾸는 풀이의 문제는 무엇인가요?

곱을 로그 합으로 바꾸면 누적 합과 이분 탐색으로 O(n log n)에 풀 수 있다. 하지만 부동소수점 반올림 때문에 곱이 정확히 k인 구간이 `log k`보다 아주 조금 작게 계산되어 통과로 세어질 수 있다. 기준을 `log k - 1e-9`처럼 낮춰야 하고, 그 여유를 입력 범위로 정당화해야 한다. 정수만 쓰는 창이 더 안전하다.

### 원소에 0이 있으면요?

0으로는 나눌 수 없어 창에서 0을 빼낼 수 없다. 창 안의 0 개수를 따로 세고 0이 아닌 원소의 곱만 들고 다니거나, 배열을 0에서 잘라 조각마다 풀고 0을 품은 구간 수를 따로 더한다.

### 곱이 k 이상인 구간의 개수는요?

전체 구간 수 n(n + 1)/2에서 이 문제의 답을 빼면 된다. 직접 세려면 창을 "곱이 k 미만"으로 유지하면서 r마다 l개(0부터 l − 1까지 출발한 구간)를 더한다.
