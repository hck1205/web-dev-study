스프링 부트로 만든 마이크로서비스를 쿠버네티스로 옮기는 회의에서 자주 나오는 질문이 있다. "Eureka랑 Config Server는 이제 빼도 되나?" 반대 의견도 나온다. "그래도 서킷 브레이커는 필요하지 않나?" 둘 다 맞는 말이다. Spring Cloud가 풀던 문제의 절반은 쿠버네티스가 플랫폼 수준에서 풀어 주고, 나머지 절반은 여전히 애플리케이션 안에서 풀어야 한다.

이 글은 그 경계를 가른다. Spring Cloud의 각 부품이 어떤 문제를 풀려고 생겼는지, 쿠버네티스의 무엇이 같은 일을 하는지, 그리고 남겨야 하는 것은 무엇인지를 본다. 남는 쪽의 대표인 서킷 브레이커는 주문 서비스가 재고 서비스 두 대를 부르는 작은 데모로 직접 돌려 봤다. 마이크로서비스 자체의 장단점은 [모놀리스에서 마이크로서비스로](/posts/microservices)에, 서비스 디스커버리의 일반론은 [서비스 디스커버리](/posts/service-discovery)에 있으니 여기서는 스프링과 쿠버네티스 사이의 선택에 집중한다.

데모는 JDK 21, Spring Boot 4.1.1, Spring Cloud 2025.1.3, `resilience4j-spring-boot4` 2.4.0으로 돌렸다. 주문 서비스는 19210 포트, 재고 서비스는 19211과 19212 포트다. 쿠버네티스 클러스터는 이 환경에 없어서 매니페스트와 `kubectl` 출력은 예시로 적었고, 그 밖의 스프링 출력은 모두 실제로 돌린 결과다.

## Spring Cloud가 처음 풀던 문제

2010년대 중반 마이크로서비스를 VM 위에 올리던 시절을 떠올리면 Spring Cloud의 부품들이 왜 그렇게 생겼는지 보인다. 인스턴스는 오토스케일링으로 생기고 사라지는데 IP가 매번 바뀐다. 그래서 각 인스턴스가 시작할 때 자기 주소를 레지스트리(Eureka)에 올리고, 호출하는 쪽이 목록을 받아 직접 골랐다(Ribbon, 지금은 Spring Cloud LoadBalancer). 서비스마다 설정 파일을 들고 다니기 싫어서 설정 서버(Config Server)가 Git 저장소의 설정을 나눠 줬다. 바깥 요청을 받아 서비스로 나누는 문은 Zuul, 지금은 Spring Cloud Gateway가 맡았다. 한 서비스가 느려지면 부르는 쪽 스레드가 다 묶이니 Hystrix로 회로를 끊었다.

이 부품들은 모두 라이브러리다. 자바 애플리케이션 안에 들어가 같은 JVM에서 돈다. 장점은 플랫폼이 무엇이든 동작한다는 것이고, 단점은 모든 서비스가 자바와 스프링이어야 같은 기능을 누린다는 것이다. 쿠버네티스는 같은 일 중 상당수를 플랫폼으로 끌어내렸다. 아래 그림에서 다음을 누르며 같은 요청이 두 세계에서 어떻게 흘러가는지 비교해 보자.

등록과 조회는 거의 완전히 넘어간다. 쿠버네티스에서는 Pod가 스스로 등록하지 않는다. kubelet이 Pod 상태를 API 서버에 올리고, 컨트롤러가 Service의 셀렉터에 맞고 readiness가 통과한 Pod의 IP만 EndpointSlice에 넣는다. 호출하는 쪽은 `inventory`라는 DNS 이름만 안다. Eureka에서는 인스턴스가 하트비트를 멈춰야 목록에서 빠졌지만(기본 갱신 30초, 만료 90초), 쿠버네티스는 프로브 실패나 종료 시작 순간에 엔드포인트에서 뺀다. 자세한 흐름은 [Kubernetes Service 타입](/posts/k8s-service-types)과 [CoreDNS](/posts/k8s-coredns) 글에 있다.

인스턴스 고르기도 넘어간다. ClusterIP Service로 가는 연결은 노드의 kube-proxy 규칙(또는 eBPF 기반 CNI)이 Pod 하나로 바꿔 보낸다. 다만 여기서 하나를 알고 있어야 한다. 분산은 연결 단위다. HTTP 연결을 재사용하는 클라이언트는 한 Pod에 계속 붙어 있고, gRPC처럼 연결 하나에 요청을 몰아 보내는 경우 새 Pod가 늘어나도 트래픽이 가지 않는다. 요청 단위로 고르고 싶으면 Spring Cloud LoadBalancer를 남기거나 서비스 메시를 쓴다.

## 이름으로 부르는 두 가지 방법

데모에서 Spring Cloud LoadBalancer를 써 봤다. 레지스트리 서버 없이 인스턴스 목록을 설정에 직접 적는 `SimpleDiscoveryClient`를 썼다.

```properties
spring.cloud.discovery.client.simple.instances.inventory[0].uri=http://127.0.0.1:19211
spring.cloud.discovery.client.simple.instances.inventory[1].uri=http://127.0.0.1:19212
```

```java
@Bean
@LoadBalanced                  // 이 빌더로 만든 RestClient는 호스트 이름을 서비스 ID로 읽는다
RestClient.Builder lbRestClientBuilder() {
  var http = HttpClient.newBuilder().connectTimeout(Duration.ofMillis(500)).build();
  var factory = new JdkClientHttpRequestFactory(http);
  factory.setReadTimeout(Duration.ofSeconds(1));
  return RestClient.builder().requestFactory(factory);
}

// InventoryClient
this.http = lb.baseUrl("http://inventory").build();
```

## 호출 코드는 Feign에서 HTTP 인터페이스로

디스커버리를 바꾸는 김에 호출 코드도 같이 보게 된다. Spring Cloud로 MSA를 짠 프로젝트에는 대개 OpenFeign이 있다. 인터페이스에 `@FeignClient(name = "inventory")`를 붙이고 `@GetMapping`을 적으면 구현이 생기고, `name`이 서비스 ID라 LoadBalancer와 바로 묶인다.

```java
@FeignClient(name = "inventory")
interface InventoryFeign {
  @GetMapping("/stock/{sku}")
  Stock stock(@PathVariable String sku);
}
```

Spring Cloud 팀은 2022.0 릴리스 때 Spring Cloud OpenFeign을 기능 완료로 보고 버그 수정 위주로만 관리하겠다고 밝혔고, 문서에서도 스프링 자체의 HTTP 인터페이스로 옮기라고 권한다. 옮기는 이유는 유지 보수 상태만이 아니다. Feign은 인코더·디코더, 재시도(`Retryer`), 에러 변환(`ErrorDecoder`), 타임아웃 설정을 자기 방식으로 따로 갖는다. 그래서 같은 앱 안에서 `RestClient`에 붙인 인터셉터, 메시지 변환기, 관찰(observation) 설정이 Feign 호출에는 따로 걸린다. 동기 호출만 되는 것도 한계다.

HTTP 인터페이스는 Spring Framework 6부터 들어 있는 같은 생각의 구현이다. `@HttpExchange`로 인터페이스를 쓰면 프레임워크가 프록시를 만들고, 실제 요청은 그 아래의 `RestClient`(블로킹)나 `WebClient`(리액티브)가 보낸다. 클라이언트 설정이 한 벌로 모인다.

```java
@HttpExchange("/stock")
interface InventoryApi {
  @GetExchange("/{sku}")
  Stock stock(@PathVariable String sku);
}

@Bean
InventoryApi inventoryApi(RestClient.Builder builder) {
  // 쿠버네티스에서는 Service 이름, 아직 Eureka라면 @LoadBalanced 빌더에 서비스 ID
  RestClient http = builder.baseUrl("http://inventory:8080").build();
  return HttpServiceProxyFactory.builderFor(RestClientAdapter.create(http))
      .build()
      .createClient(InventoryApi.class);
}
```

인터페이스 모양이 거의 같아서 옮기는 일은 어노테이션 바꾸기와 빈 등록이 대부분이다. Boot 4에서는 `@ImportHttpServices`로 이 빈 등록마저 설정 키로 대신하는데, 그 모습은 [Spring Boot 4 마이그레이션](/posts/spring-boot-4-migration)에서 돌려 봤다. 옮길 때 놓치기 쉬운 것은 실패 처리다. Feign은 4xx·5xx를 `FeignException`으로 던지고 `ErrorDecoder`로 바꿔 왔는데, `RestClient`는 `HttpClientErrorException`·`HttpServerErrorException`을 던지고 바꾸려면 `defaultStatusHandler`를 쓴다. 서킷 브레이커의 `recordExceptions`나 `@ControllerAdvice`가 Feign 예외 이름으로 걸려 있으면, 옮긴 뒤 실패가 실패로 세어지지 않는다. 타임아웃도 Feign 설정 키에서 위 데모처럼 요청 팩토리의 연결·읽기 타임아웃으로 옮긴다. Feign은 따로 주지 않아도 연결 10초, 읽기 60초가 기본이었지만, 옮긴 뒤에는 쓰는 HTTP 클라이언트 라이브러리의 기본값을 따르니 값을 명시해 둔다.

## 설정은 파일로 받는다

Config Server가 하던 일은 ConfigMap과 Secret이 대부분 가져간다. 스프링 부트는 둘 다 그대로 읽는다. 환경 변수로 넣으면 `ORDER_MAXQTY` 같은 이름이 relaxed binding으로 `order.max-qty`에 묶이고([Spring Boot 자동 구성](/posts/spring-boot-auto-configuration) 참고), 볼륨으로 마운트하면 파일 이름이 키, 내용이 값이 된다. 후자를 읽는 방법이 `configtree`다. 쿠버네티스가 볼륨을 만드는 것과 같은 모양의 디렉터리를 로컬에 만들어 확인했다.

```bash
mkdir -p cfg
printf '25' > cfg/order.max-qty        # ConfigMap 키 하나 = 파일 하나
printf '가을 세일' > cfg/order.banner
CONFIG_DIR=$PWD/cfg java -jar order/target/order-0.0.1.jar
```

```properties
# 디렉터리가 없어도 시작은 하도록 optional
spring.config.import=optional:configtree:${CONFIG_DIR:/nonexistent}/
```

```bash
curl -s localhost:19210/config
```

```text
{"banner":"가을 세일","maxQty":25}
```

여기서 실행 중에 `cfg/order.max-qty`를 `30`으로 바꾸고 다시 불렀다.

```text
{"banner":"가을 세일","maxQty":25}
```

그대로 25다. 쿠버네티스도 마운트된 ConfigMap 파일은 잠시 뒤 바꿔 주지만, 스프링은 시작할 때 읽은 값을 들고 있다. 환경 변수로 넣은 값은 Pod를 다시 만들어야 바뀐다. 언제 파일이 바뀌고 `subPath`면 왜 안 바뀌는지는 [ConfigMap](/posts/k8s-configmap) 글에 있다. 쿠버네티스에서 가장 흔한 답은 설정이 바뀌면 롤링 재시작하는 것이다. ConfigMap 내용의 해시를 Deployment의 Pod 템플릿 어노테이션에 넣어 두면 설정이 바뀔 때 새 Pod가 뜬다. 재시작 없이 바꿔야 하는 값(기능 플래그, 할인율)이 있다면 그건 설정이 아니라 데이터에 가깝다. Spring Cloud Config의 `@RefreshScope`나 Spring Cloud Kubernetes의 설정 리로드를 쓸 수도 있지만, 인스턴스마다 바뀌는 시점이 다르다는 점을 감안해야 한다.

Config Server가 여전히 쓸모 있는 경우도 있다. 설정 이력을 Git 커밋으로 남기고 여러 클러스터·VM에 같은 설정을 나눠야 할 때다. 다만 쿠버네티스에서는 이 역할을 GitOps가 대신하는 경우가 많다. 매니페스트와 ConfigMap을 Git에 두고 Argo CD가 맞춰 주면 이력과 배포가 한곳에 모인다([Argo CD](/posts/argocd-basics)). 비밀값은 ConfigMap이 아니라 Secret으로, 더 나아가 외부 비밀 저장소로 보낸다([Secret](/posts/k8s-secret), [비밀 관리](/posts/secrets-management)).

## 게이트웨이는 겹친다

바깥 문은 깔끔하게 나뉘지 않는다. Ingress나 Gateway API는 호스트·경로·헤더로 나누고, TLS를 끝내고, 가중치로 트래픽을 쪼개는 일을 잘한다([게이트웨이](/posts/gateway), [Gateway API](/posts/k8s-gateway-api)). 여기까지라면 Spring Cloud Gateway를 따로 둘 이유가 없다.

Spring Cloud Gateway를 남기는 건 라우팅이 애플리케이션 지식을 필요로 할 때다. 토큰을 풀어 사용자 등급에 따라 다른 서비스로 보내거나, 여러 서비스의 응답을 모아 하나로 돌려주는 BFF를 만들거나, 요청 본문을 고쳐야 하는 경우다. 이때도 구조는 Ingress → Spring Cloud Gateway Pod → 서비스가 된다. 홉이 하나 늘고 게이트웨이 Pod의 스케일과 장애도 직접 챙겨야 하니, 규칙이 단순해지면 다시 Ingress로 내리는 걸 검토한다.

## 서킷 브레이커가 앱에 남는 이유

쿠버네티스는 "이 Pod가 살아 있나, 요청을 받을 준비가 됐나"를 본다. "재고 서비스가 지금 3초씩 걸리는데 주문 서비스는 그걸 기다려야 하나"는 보지 않는다. 그건 부르는 쪽만 아는 사정이다. 타임아웃, 재시도, 서킷 브레이커, 폴백은 그래서 앱(또는 서비스 메시의 사이드카)에 남는다. 원리는 [장애가 번지지 않게](/posts/resilience-patterns)와 [서킷 브레이커 안쪽](/posts/circuit-breaker)에서 다뤘으니, 여기서는 스프링에 붙였을 때 실제로 어떻게 움직이는지 본다.

Spring Cloud CircuitBreaker라는 추상화 모듈도 있지만, 지금은 Resilience4j의 스프링 부트 모듈을 바로 쓰는 경우가 많다. Boot 4용은 `resilience4j-spring-boot4`이고, 어노테이션이 동작하려면 AOP 스타터(Boot 4에서는 `spring-boot-starter-aspectj`)가 필요하다.

```java
@CircuitBreaker(name = "inventory", fallbackMethod = "fallback")
Map<String, Object> stock(String sku) {
  return http.get().uri("/stock/{sku}", sku).retrieve().body(Map.class);
}

Map<String, Object> fallback(String sku, Throwable t) {
  return Map.of("sku", sku, "stock", "unknown", "fallback", t.getClass().getSimpleName());
}
```

## 느려지면 타임아웃이 먼저다

이번에는 두 인스턴스 모두 3초씩 걸리게 했다. RestClient의 읽기 타임아웃은 1초다.

```text
 1 {"ms":1009,"result":{"stock":"unknown","sku":"C-3003","fallback":"ResourceAccessException"},"cb":"CLOSED","failureRate":-1.0,"slowRate":-1.0}
 2 {"ms":1006,"result":{"stock":"unknown","sku":"C-3003","fallback":"ResourceAccessException"},"cb":"CLOSED","failureRate":-1.0,"slowRate":-1.0}
 3 {"ms":1003,"result":{"stock":"unknown","sku":"C-3003","fallback":"ResourceAccessException"},"cb":"CLOSED","failureRate":-1.0,"slowRate":-1.0}
 4 {"ms":1006,"result":{"stock":"unknown","sku":"C-3003","fallback":"ResourceAccessException"},"cb":"OPEN","failureRate":80.0,"slowRate":80.0}
 5 {"ms":1,"result":{"stock":"unknown","sku":"C-3003","fallback":"CallNotPermittedException"},"cb":"OPEN","failureRate":80.0,"slowRate":80.0}
```

닫힌 직후 성공한 1건과 타임아웃 4건으로 다섯 건이 차자 실패율 80%로 열렸다. 타임아웃이 없었다면 각 요청이 3초씩 톰캣 스레드를 붙잡았을 것이다. 서킷 브레이커는 실패를 세는 장치일 뿐이고, 기다리는 시간을 줄이는 건 타임아웃이다. 순서를 지켜 건다. 타임아웃을 먼저, 그 다음 서킷 브레이커, 재시도는 멱등한 호출에만 짧게. Resilience4j 어노테이션을 함께 쓰면 기본 적용 순서가 정해져 있다(재시도가 가장 바깥). 그 의미는 [서킷 브레이커 안쪽](/posts/circuit-breaker)의 "재시도와 타임아웃 사이 어디에 끼우나"에 있다. 계층별 타임아웃 값을 맞추는 법은 [타임아웃](/posts/timeouts)에서 다뤘다. Spring Framework 7에는 `@Retryable`과 `@ConcurrencyLimit`이 프레임워크에 들어왔는데([Spring Boot 4 마이그레이션](/posts/spring-boot-4-migration)), 서킷 브레이커는 아직 없어서 Resilience4j가 남는다.

## 회로가 열렸다고 Pod를 빼면 안 된다

Resilience4j는 브레이커 상태를 헬스 지표로 내놓는다. 기본 설정에서 회로가 열렸을 때 `/actuator/health`를 보면 이렇다.

```text
UP UNKNOWN CIRCUIT_OPEN    # 전체 상태, circuitBreakers 컴포넌트, inventory 브레이커
```

`allow-health-indicator-to-fail=true`를 주고 같은 상황을 만들면 달라진다.

```text
HTTP503 DOWN DOWN
readiness 200
```

전체 헬스가 503 DOWN이 됐다. 다행히 `/actuator/health/readiness`는 기본 그룹이라 200 그대로다. 문제는 누군가 "의존성이 죽으면 트래픽을 받지 말아야 한다"며 readiness 그룹에 `circuitBreakers`를 넣을 때 생긴다.

## 직접 세어 보는 실패율

Resilience4j의 건수 기반 창을 그대로 흉내 내 보자. 결과 목록(`"ok"` 또는 `"fail"`)을 차례로 넣으며, 창 크기만큼만 기억하고, 최소 건수가 차기 전에는 -1, 그 뒤에는 실패율(소수 첫째 자리 반올림)을 기록한다. 임계값 이상이 되면 그 호출 번호(1부터)를 `openedAt`으로 돌려주고 멈춘다. 첫 테스트는 위 데모의 순서 그대로이고, 기대값은 데모에서 본 실패율과 같다.

## 옮길 때 실제로 하는 일

정리하면 쿠버네티스로 옮기는 스프링 MSA에서 손대는 순서는 대략 이렇다. Eureka 클라이언트를 빼고 호출 주소를 Service 이름으로 바꾼다. 이때 두 디스커버리가 섞인 기간을 짧게 잡는다. Config Server의 설정을 ConfigMap·Secret으로 옮기고, 설정이 바뀌면 롤링 재시작되게 한다. 게이트웨이는 단순 라우팅이면 Ingress나 Gateway API로 내리고, 앱 지식이 필요한 라우팅만 Spring Cloud Gateway에 남긴다. 타임아웃, 서킷 브레이커, 폴백은 그대로 둔다. 그리고 액추에이터 프로브를 켜고 readiness에서 외부 의존성을 뺀다.

옮긴 뒤 자주 보는 증상도 정해져 있다. 배포 중에만 503이 몇 건 섞이면 종료 순서와 엔드포인트 제거 사이의 틈을 본다([Spring Boot를 쿠버네티스에서](/posts/spring-boot-on-kubernetes)). 새 Pod를 늘렸는데 부하가 기존 Pod에 몰려 있으면 연결 재사용과 kube-proxy의 연결 단위 분산을 의심한다. 서킷 브레이커가 자주 열리는데 재고 서비스 지표는 멀쩡해 보이면 인스턴스별 오류율부터 본다. 위 데모처럼 한 대가 회로 전체를 끌어내리고 있을 수 있다.

## 플랫폼이 할 일과 호출자가 할 일

쿠버네티스는 "어디에 있나"와 "살아 있나"를 맡는다. 등록, 조회, 연결 분산, 설정 배포, 바깥 문이 여기에 든다. "지금 저쪽을 믿고 기다려도 되나"는 부르는 쪽만 판단할 수 있다. 그래서 Eureka와 Config Server는 대개 빠지고, Resilience4j는 남는다. 경계에 있는 게이트웨이와 요청 단위 분산은 규칙이 앱 지식을 필요로 하는지에 따라 고른다. 같은 원리가 모델 API를 부르는 앱에도 그대로 적용된다는 이야기는 [Spring AI로 에이전트 만들기](/posts/spring-ai-agents)에 있다.

## 면접에서 나올 만한 질문

### 쿠버네티스를 쓰면 Spring Cloud는 필요 없나요?

전부 필요 없어지지는 않고, 역할이 겹치는 것만 빠진다. 서비스 등록·조회(Eureka), 인스턴스 고르기(LoadBalancer), 설정 배포(Config Server)는 Service·DNS, kube-proxy, ConfigMap·Secret이 대신한다. 타임아웃, 서킷 브레이커, 폴백처럼 호출하는 쪽의 판단이 필요한 것은 앱(Resilience4j)이나 서비스 메시에 남는다. 게이트웨이는 단순 라우팅이면 Ingress나 Gateway API로 내리고, 인증 정보에 따른 라우팅이나 BFF처럼 앱 지식이 필요하면 Spring Cloud Gateway를 남긴다.

### 쿠버네티스 위에서 Eureka를 계속 쓰면 무엇이 문제인가요?

인스턴스 목록이 두 벌이 되어 서로 어긋난다. 쿠버네티스는 Pod가 종료를 시작하거나 readiness가 실패하면 바로 엔드포인트에서 빼지만, Eureka에서는 등록 취소나 리스 만료(기본 90초)까지 남아 있어서 이미 내려가는 Pod로 요청이 간다. 레지스트리 서버 자체도 운영해야 할 대상이 된다. 옮길 때는 한쪽으로 정하고, 스프링 API가 꼭 필요하면 쿠버네티스 API를 감싼 Spring Cloud Kubernetes를 쓴다.

### ConfigMap을 바꿨는데 스프링 앱의 값이 안 바뀝니다. 왜인가요?

스프링은 시작할 때 읽은 값을 들고 있기 때문이다. 환경 변수로 넣었다면 Pod를 다시 만들어야 바뀌고, 볼륨으로 넣었다면 파일은 잠시 뒤 바뀌어도(subPath면 그것도 안 됨) 바인딩된 값은 그대로다. 실제로 configtree로 읽은 값을 실행 중에 바꿔 봐도 25가 그대로였다. 보통은 ConfigMap 해시를 Pod 템플릿 어노테이션에 넣어 설정이 바뀌면 롤링 재시작되게 하고, 실행 중에 바꿔야 하는 값은 리로드 기능이나 별도 저장소로 다룬다.

### 인스턴스 하나만 고장 났는데 서킷 브레이커가 열렸습니다. 어떻게 봐야 하나요?

서비스 단위 브레이커에 인스턴스 단위 문제를 맡겼기 때문이다. 두 대 중 한 대가 실패하면 라운드 로빈으로 실패율이 50%로 올라가고, 임계값이 50%면 회로가 열려 멀쩡한 인스턴스까지 차단된다. 고장 난 인스턴스를 빼는 일은 readiness 프로브, 로드 밸런서의 헬스 체크, 서비스 메시의 아웃라이어 감지가 먼저 해야 한다. 브레이커는 서비스 전체가 아플 때를 위한 장치로 두고, 인스턴스별 오류율 지표를 같이 본다.

### 반열림 상태에서 회로가 왜 다시 열리나요?

반열림에서 허용한 시험 호출의 실패율로 다시 판정하기 때문이다. 시험 2건이 라운드 로빈으로 정상 인스턴스와 고장 인스턴스에 하나씩 가면 실패율 50%가 되어 다시 OPEN이 된다. 원인 인스턴스가 빠지기 전까지는 이 고리가 반복된다. 또 Resilience4j는 기본으로 대기 시간이 지나도 다음 호출이 올 때 상태를 바꾸므로, 트래픽이 없으면 OPEN이 길게 보일 수 있다.

### 서킷 브레이커 상태를 readiness 프로브에 넣으면 안 되는 이유는?

외부 의존성 장애가 모든 Pod를 한꺼번에 서비스에서 빼 버리기 때문이다. 같은 재고 서비스를 부르는 주문 Pod들은 거의 동시에 회로가 열리고, readiness가 실패하면 Service 뒤가 비어 재고와 무관한 기능까지 죽는다. readiness는 그 Pod 혼자만의 문제를 보는 곳이고, 의존성 장애는 폴백과 메트릭 알림으로 다룬다. Resilience4j도 기본값으로는 열린 회로를 DOWN이 아니라 UNKNOWN으로 보고한다.

### 서킷 브레이커만 있으면 느린 의존성 문제가 해결되나요?

아니고, 타임아웃이 먼저 있어야 한다. 브레이커는 실패를 세어 판정할 뿐이라, 타임아웃이 없으면 판정에 필요한 호출마다 스레드가 수 초씩 묶인다. 데모에서는 읽기 타임아웃 1초 덕분에 각 호출이 1초에 끝났고, 5건이 차자 회로가 열려 이후 응답은 1ms가 됐다. 재시도는 멱등한 호출에만 짧게 걸고, 브레이커의 느린 호출 기준은 타임아웃보다 작게 잡는다.

### 쿠버네티스 Service로 부르는데 새로 늘린 Pod에 트래픽이 안 갑니다. 왜인가요?

kube-proxy의 분산이 요청이 아니라 연결 단위이기 때문이다. HTTP keep-alive나 gRPC처럼 연결을 오래 재사용하는 클라이언트는 처음 붙은 Pod에 계속 요청을 보낸다. 연결 수명을 제한하거나, 클라이언트 측 요청 단위 분산(Spring Cloud LoadBalancer, gRPC의 클라이언트 LB)을 쓰거나, 서비스 메시의 L7 분산을 쓴다. HPA로 Pod를 늘렸는데 CPU가 기존 Pod에만 몰려 있다면 이걸 먼저 의심한다.
