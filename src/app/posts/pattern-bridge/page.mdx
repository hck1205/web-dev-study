<EasyIntro>
  매출 차트가 막대, 꺾은선, 상위 몇 개 막대로 늘어나는 사이, 그리는 방식도 그림, 글자, 빠른 캔버스 세 가지로 늘었다. 둘을 한데 묶어 만들다 보니 파일이 아홉 개가 됐고, 막대 높이 계산 하나를 고치려면 세 파일을 고쳐야 했다.

  브리지 패턴은 무엇을 그릴지와 어떻게 그릴지를 강 양쪽의 두 마을로 떼어 놓고, 그 사이에 다리 하나만 놓는다. 차트 쪽은 어디에 무엇을 그릴지만 계산해서 다리 건너편에 그려 달라고 부탁한다. 그리는 쪽은 차트가 무엇인지 모른 채 받은 대로 그린다.

  그러면 새 차트나 새 그리는 방식이 생겨도 자기 마을에 하나씩만 더하면 되고, 개수가 곱이 아니라 덧셈으로 늘어난다. 다만 아직 그리는 방식이 하나뿐이고 늘 계획도 없다면 다리는 한 번 더 건너야 하는 길일 뿐이다.

관리자 화면에 매출 차트를 넣었다. 처음에는 SVG 막대 차트 하나였다. 그다음 요청은 접근성 때문에 표처럼 읽히는 텍스트 버전, 그다음은 대량 데이터를 위한 Canvas 버전이었다. 그사이 차트 종류도 막대, 꺾은선, 상위 N개 막대로 늘었다. 파일 목록을 열어 보니 이렇다.

막대 높이를 계산하는 코드가 세 파일에 복사돼 있고, 반올림 버그를 하나 고치면 세 파일을 고쳐야 한다. PDF 내보내기가 들어오면 파일이 세 개 더 생긴다. 차트 종류와 그리는 방식, 두 가지가 서로 상관없이 바뀌는데 그걸 상속 하나로 표현하려니 곱셈이 된다. 이 둘을 서로 다른 계층으로 떼어 놓고 사이를 객체 참조 하나로 잇는 것이 브리지 패턴이다. 구조 패턴 전체의 지도는 [디자인 패턴 개요](/posts/design-patterns-overview)에 있다.

## 두 방향으로 갈라지는 상속

클래스 이름에 단어 두 개가 붙어 있다는 게 신호다. `SvgBarChart`의 `Svg`는 그리는 방식이고 `Bar`는 차트 종류다. 이 두 축은 바뀌는 이유가 다르다. 차트 종류는 기획 요구로 늘고, 그리는 방식은 플랫폼과 성능 요구로 는다. 상속으로 둘을 함께 표현하면 축 하나가 늘 때마다 다른 축의 개수만큼 클래스가 생긴다.

## 무엇을 그릴지와 어떻게 그릴지를 떼어 놓는다

GoF(1994)는 브리지의 의도를 "추상을 구현에서 분리해 둘이 독립적으로 변할 수 있게 한다"고 적었다. 등장인물은 넷이다. 클라이언트가 쓰는 Abstraction(`Chart`)과 그걸 확장한 RefinedAbstraction(`BarChart`, `TopNBarChart`), 그리고 Abstraction이 들고 있는 Implementor(`Renderer`)와 그 구현들(`SvgRenderer`, `AsciiRenderer`)이다. 두 계층을 잇는 화살표 하나가 다리다.

Implementor 쪽부터 보자. 렌더러는 사각형과 글자를 그리는 법만 안다. 막대 차트가 무엇인지 모른다.

```ts
// Implementor: 그리는 방법. 차트가 무엇인지 모른다
export interface Renderer {
  rect(x: number, y: number, w: number, h: number): void;
  text(x: number, y: number, s: string): void;
  output(): string;
}

export class SvgRenderer implements Renderer {
  private parts: string[] = [];
  constructor(private readonly width: number, private readonly height: number) {}
  rect(x: number, y: number, w: number, h: number) {
    this.parts.push(`<rect x="${x}" y="${y}" width="${w}" height="${h}"/>`);
  }
  text(x: number, y: number, s: string) {
    this.parts.push(`<text x="${x}" y="${y}">${s}</text>`);
  }
  output() {
    return `<svg viewBox="0 0 ${this.width} ${this.height}">${this.parts.join("")}</svg>`;
  }
}

// 터미널과 테스트용: 한 칸 = 글자 하나
export class AsciiRenderer implements Renderer {
  private grid: string[][];
  constructor(width: number, private readonly height: number) {
    this.grid = Array.from({ length: height }, () => Array(width).fill(" "));
  }
  rect(x: number, y: number, w: number, h: number) {
    for (let r = y; r < y + h; r++) for (let c = x; c < x + w; c++) this.grid[r][c] = "█";
  }
  text(x: number, y: number, s: string) {
    [...s].forEach((ch, i) => (this.grid[y][x + i] = ch));
  }
  output() {
    return this.grid.map((row) => row.join("").trimEnd()).join("\n");
  }
}
```

Abstraction 쪽은 무엇을 어디에 그릴지 계산하고, 실제로 그리는 일은 들고 있는 렌더러에 맡긴다.

```ts
// Abstraction: 무엇을 그릴지. 어떻게 그리는지는 renderer에 맡긴다
export abstract class Chart {
  constructor(protected readonly renderer: Renderer) {}
  abstract draw(data: { label: string; value: number }[]): string;
}

// Refined Abstraction: 막대 차트
export class BarChart extends Chart {
  draw(data: { label: string; value: number }[]) {
    const max = Math.max(...data.map((d) => d.value));
    const chartH = 6;
    data.forEach((d, i) => {
      const h = Math.round((d.value / max) * chartH);
      this.renderer.rect(i * 4, chartH - h, 3, h);
      this.renderer.text(i * 4, chartH, d.label);
    });
    return this.renderer.output();
  }
}

// Refined Abstraction: 큰 순서로 상위 n개만
export class TopNBarChart extends BarChart {
  constructor(renderer: Renderer, private readonly n: number) {
    super(renderer);
  }
  draw(data: { label: string; value: number }[]) {
    return super.draw([...data].sort((a, b) => b.value - a.value).slice(0, this.n));
  }
}
```

막대 높이 계산은 이제 `BarChart` 한곳에만 있다. `TopNBarChart`는 데이터를 골라 넘길 뿐이고, 어떤 렌더러와도 조합된다. 아래 그림에서 다음을 누르면 상위 2개 차트가 렌더러에게 그리기를 맡기는 순서가 나온다.

## 여기서 말하는 구현은 implements가 아니다

브리지 설명에서 가장 헷갈리는 말이 "추상과 구현의 분리"다. 여기서 추상은 `abstract class`가 아니고, 구현은 `implements` 키워드가 아니다. 추상은 클라이언트가 보고 쓰는 고수준의 개념(차트, 로거, DB 연결)이고, 구현은 그걸 실제로 해내는 저수준의 수단(SVG, 표준 출력, PostgreSQL 프로토콜)이다. 보통의 인터페이스와 구현 클래스 관계라면 추상 쪽은 하나이고 구현 쪽만 여럿이다. 브리지에서는 추상 쪽도 따로 계층을 이루며 늘어난다. 앞의 `BarChart`와 `TopNBarChart`처럼.

C++에서 쓰는 pimpl(pointer to implementation) 관용구도 같은 계보다. 헤더에 공개되는 클래스는 구현 객체를 가리키는 포인터 하나만 들고, 실제 필드와 로직은 소스 파일 안의 구현 클래스에 둔다. 구현을 바꿔도 헤더가 바뀌지 않아 그 헤더를 쓰는 코드를 다시 컴파일하지 않아도 된다. GoF 책도 브리지의 다른 이름으로 Handle/Body를 적어 두었다.

## Go의 slog가 나눠 놓은 두 쪽

## 렌더러를 바꿔 끼우는 프레임워크들

리액트가 큰 예다. 컴포넌트, 훅, 재조정 알고리즘은 `react`와 `react-reconciler` 쪽에 있고, 실제 화면에 노드를 만들고 붙이는 일은 렌더러가 한다. `react-dom`은 DOM 노드를, React Native는 네이티브 뷰를, ink는 터미널 글자를 만든다. 렌더러는 `createInstance`, `appendChild`, `commitUpdate` 같은 함수를 담은 host config를 재조정기에 넘긴다. 같은 컴포넌트 코드가 브라우저와 모바일과 터미널에서 도는 이유가 이 다리다. 재조정이 무엇을 비교하는지는 [리렌더링](/posts/react-rerender) 글에 있다.

Go의 `database/sql`도 같은 구조다. 앱이 쓰는 `sql.DB`는 커넥션 풀, 트랜잭션, `QueryRow` 같은 편의 기능을 가진 추상 쪽이고, 각 DB 드라이버는 `database/sql/driver` 패키지의 `Driver`, `Conn`, `Stmt` 인터페이스를 구현한다. 커넥션 풀 기능이 좋아지면 모든 드라이버가 덕을 보고, 새 드라이버는 풀을 다시 만들 필요가 없다. 자바의 JDBC도 `DriverManager`와 `Connection` 인터페이스 아래에 벤더 드라이버를 두는 같은 모양이다.

쿠버네티스의 kubelet은 컨테이너를 직접 띄우지 않고 CRI(Container Runtime Interface)라는 gRPC 인터페이스로 containerd나 CRI-O에 맡긴다. 저장소는 CSI, 네트워크는 CNI가 같은 역할을 한다. kubelet의 Pod 관리 기능과 런타임 구현이 서로를 고치지 않고 따로 발전한다.

## 가짜 렌더러로 차트 로직만 테스트하기

브리지로 나누면 테스트도 둘로 나뉜다. 차트 쪽은 "어떤 좌표에 무엇을 그려 달라고 했는가"만 확인하면 된다. 그리지 않고 호출만 적어 두는 렌더러를 끼우면 SVG 문자열을 비교하는 깨지기 쉬운 테스트가 필요 없다.

```ts
// 그리지 않고 호출만 적어 두는 가짜 구현
class RecordingRenderer implements Renderer {
  calls: string[] = [];
  rect(x: number, y: number, w: number, h: number) { this.calls.push(`rect ${x},${y} ${w}x${h}`); }
  text(x: number, y: number, s: string) { this.calls.push(`text ${s}`); }
  output() { return ""; }
}

test("상위 2개만 큰 순서로 그린다", () => {
  const r = new RecordingRenderer();
  new TopNBarChart(r, 2).draw([
    { label: "Mon", value: 12 },
    { label: "Tue", value: 30 },
    { label: "Thu", value: 24 },
  ]);
  assert.deepEqual(r.calls, ["rect 0,0 3x6", "text Tue", "rect 4,1 3x5", "text Thu"]);
});
```

렌더러 쪽은 반대로 "사각형 하나를 주면 올바른 SVG 태그가 나오는가"만 확인한다. 상속 구조였다면 차트 종류 3개 × 방식 3개, 9개 클래스마다 높이 계산과 출력 형식을 함께 검사해야 했다. 나누면 차트 3개, 렌더러 3개를 각자 검사하고 조합은 몇 개만 통합 테스트로 확인한다.

## 전략, 어댑터와 무엇이 다른가

코드만 보면 브리지는 [전략 패턴](/posts/pattern-strategy)과 거의 같다. 둘 다 객체가 인터페이스 타입의 필드를 들고 일을 위임한다. 차이는 의도와 수명이다. 전략은 알고리즘 하나를 갈아 끼우는 것이 목적이라 실행 중에도 바꾸곤 하고, 전략을 쓰는 쪽은 보통 계층이 없다. 브리지는 두 계층이 각자 확장되는 구조를 처음부터 설계하는 것이 목적이고, 한 번 묶으면 객체가 사는 동안 잘 바꾸지 않는다. "쓰는 쪽도 하위 클래스로 늘어나는가"를 물어보면 대체로 갈린다.

[어댑터](/posts/pattern-adapter)와는 시점이 다르다. 어댑터는 이미 있는 두 인터페이스가 맞지 않을 때 나중에 끼운다. 브리지는 아직 구현이 하나뿐이라도 두 축이 따로 늘어날 것을 알고 미리 나눈다. 실제로는 둘이 함께 쓰인다. 렌더러 인터페이스를 정해 둔 뒤, 외부 차트 라이브러리를 그 인터페이스에 맞추는 어댑터를 렌더러 구현 중 하나로 넣는 식이다.

[추상 팩토리](/posts/pattern-abstract-factory)는 브리지를 조립할 때 쓰인다. GoF 책도 둘의 관계를 그렇게 적었다. 실행 환경에 맞는 렌더러를 고르는 팩토리를 두면, 차트를 만드는 코드는 어떤 렌더러가 붙는지 몰라도 된다.

## 미리 나눴다가 후회하는 경우

가장 흔한 실수는 축이 하나뿐인데 나누는 것이다. 렌더러가 SVG 하나뿐이고 늘 계획도 없다면 `Renderer` 인터페이스는 읽는 사람이 한 번 더 건너가야 하는 다리일 뿐이다. 클래스 이름이 두 단어의 곱으로 늘기 시작하거나, 한쪽을 고칠 때마다 같은 수정이 여러 파일에 복사되는 걸 본 뒤에 나눠도 늦지 않다. 앞의 클래스 수 그림에서 보듯 축이 둘 다 두 개 이상이 되기 전까지는 상속 쪽이 더 단순하다.

더 어려운 건 Implementor 인터페이스를 정하는 일이다. 첫 렌더러가 SVG라서 인터페이스를 SVG 기능에 맞춰 만들면, 나중에 들어온 텍스트 렌더러는 그라데이션이나 투명도를 표현할 방법이 없다. 반대로 모든 렌더러가 할 수 있는 것만 남기면 SVG의 장점을 못 쓴다. 인터페이스는 구현 하나의 기능 목록이 아니라 추상 쪽이 실제로 필요로 하는 동작(`rect`, `text`처럼 차트가 요구하는 것)으로 정한다. 특정 구현만 할 수 있는 일은 그 구현의 옵션으로 둔다.

성능은 거의 걱정할 일이 없다. 호출 하나에 간접 참조가 한 번 더 붙을 뿐이다. 차트처럼 그릴 것이 수만 개라면 `rect`를 하나씩 부르는 대신 `rects(batch)`처럼 묶어서 넘기는 메서드를 인터페이스에 두는 편이 렌더러 쪽에서 최적화할 여지를 준다.

처음의 파일 아홉 개로 돌아가면, 브리지가 한 일은 클래스 이름에 붙어 있던 두 단어를 두 계층으로 떼어 놓은 것이다. 그 뒤로 차트 종류는 차트 쪽에서, 그리는 방식은 렌더러 쪽에서 각자 늘어난다.

## 면접에서 나올 만한 질문

### 브리지 패턴은 어떤 문제를 푸나요?

두 가지 축이 서로 상관없이 바뀌는데 상속 하나로 표현하면 클래스가 곱으로 느는 문제를 푼다. 추상 쪽(무엇을 할지)과 구현 쪽(어떻게 할지)을 별도 계층으로 나누고, 추상이 구현을 참조로 들게 한다. 그러면 한쪽에 클래스를 더해도 다른 쪽은 고치지 않고, 클래스 수가 곱이 아니라 합으로 는다.

### 여기서 말하는 추상과 구현은 abstract class와 implements를 뜻하나요?

아니다. 추상은 클라이언트가 쓰는 고수준 개념이고, 구현은 그걸 실제로 해내는 저수준 수단이다. 차트와 렌더러, slog의 Logger와 Handler, database/sql의 DB와 드라이버가 그 예다. 보통의 인터페이스 구현과 달리 추상 쪽도 하위 클래스로 따로 확장된다.

### 브리지와 전략 패턴은 어떻게 다른가요?

구조는 거의 같고 의도가 다르다. 전략은 알고리즘 하나를 바꿔 끼우는 게 목적이라 실행 중에도 교체하고, 쓰는 쪽은 보통 계층이 없다. 브리지는 추상과 구현 두 계층이 각자 확장되는 구조를 처음부터 설계하는 것이고, 묶은 조합은 잘 바꾸지 않는다.

### 브리지와 어댑터는 어떻게 다른가요?

어댑터는 이미 있는 맞지 않는 인터페이스를 나중에 맞추는 패턴이고, 브리지는 두 축이 따로 늘어날 것을 알고 미리 나누는 패턴이다. 둘을 함께 쓰는 경우도 많다. 브리지의 구현 인터페이스를 정해 두고, 외부 라이브러리를 그 인터페이스에 맞추는 어댑터를 구현 중 하나로 넣는다.

### 실제로 쓰이는 예를 들어 주세요.

리액트는 컴포넌트와 재조정을 한쪽에 두고, react-dom, React Native, ink 같은 렌더러가 host config로 실제 노드를 만든다. Go의 slog는 Logger와 Handler를, database/sql은 sql.DB와 드라이버 인터페이스를 나눴다. 쿠버네티스 kubelet이 CRI로 containerd나 CRI-O에 컨테이너 실행을 맡기는 것도 같은 구조다.

### 브리지를 쓰지 말아야 할 때는요?

축이 하나뿐이거나 구현이 하나뿐이고 늘 계획이 없을 때다. 이때는 인터페이스가 한 번 더 건너가야 하는 간접 계층만 만든다. 클래스 이름이 두 단어의 곱으로 늘거나 같은 수정이 여러 파일에 복사되는 걸 본 뒤에 나눠도 늦지 않다.

### 구현 쪽 인터페이스는 어떻게 정해야 하나요?

첫 구현의 기능 목록이 아니라 추상 쪽이 실제로 필요로 하는 동작으로 정한다. 첫 구현에 맞추면 나중 구현이 표현할 수 없는 메서드가 생기고, 모든 구현의 공통분모만 남기면 좋은 구현의 장점을 못 쓴다. 특정 구현만 가능한 기능은 그 구현의 옵션으로 두고, 호출이 많다면 묶어서 넘기는 메서드를 둬 구현 쪽이 최적화할 여지를 준다.
