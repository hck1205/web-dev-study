</EasyIntro>

환승 경로를 찾는 기능을 만든다고 해 보자. 역을 정점, 역 사이 구간을 간선으로 두고 [BFS](/posts/ds-graph-bfs-dfs)를 돌리면 정거장 수가 가장 적은 길이 나온다. 처음엔 그걸로 충분해 보인다. 그런데 구간마다 걸리는 분이 붙는 순간 답이 틀리기 시작한다. 정거장 두 개짜리 완행이 25분, 세 개짜리 급행이 12분이면 BFS는 25분짜리를 고른다.

BFS가 맞는 이유는 "한 겹 넓힐 때마다 거리가 정확히 1씩 늘어난다"는 데 있었다. 간선에 무게가 붙으면 그 전제가 사라진다. 그 자리를 채우는 알고리즘이 셋 있다. 음수가 없을 때의 다익스트라, 음수가 있을 때의 벨만-포드, 목적지를 알 때의 A\*다. 모든 쌍의 거리가 필요하면 플로이드-워셜, 무게가 0과 1뿐이면 0-1 BFS가 붙는다.

이 글은 다섯 가지를 같은 질문으로 비교한다. 무엇을 가정하고, 그 가정이 깨지면 어떻게 틀리고, 얼마나 걸리는가. 예제는 모두 Node 22에서 직접 돌린 출력이다. 다익스트라를 쓰는 지도 서비스의 큰 그림은 [지도와 길 찾기](/posts/sd-maps-tiles-routing)에, 다익스트라가 그리디인 이유는 [그리디 알고리즘](/posts/greedy-algorithms)에 있다. 여기서는 그 사이의 구현 세부와 대안을 판다.

## 가장 가까운 곳부터 확정한다

다익스트라의 생각은 하나다. 아직 확정하지 않은 정점 중 출발점에서 가장 가까운 것을 꺼내면, 그 거리는 더 줄어들 수 없다. 다른 길로 돌아오려면 이미 그보다 먼 정점을 거쳐야 하고, 간선 무게가 음수가 아니니 돌아오면서 거리가 줄 리 없다.

그래서 순서는 이렇다. 출발점 거리를 0, 나머지를 무한대로 둔다. 가장 가까운 정점을 꺼내 확정하고, 그 정점에서 나가는 간선마다 "이 정점을 거쳐 가면 더 짧아지나"를 본다. 짧아지면 값을 고친다. 이 "고치기"를 완화(relaxation)라고 부른다. 가장 가까운 정점을 빨리 꺼내려고 [힙](/posts/ds-heap)을 쓴다.

```js
function dijkstra(adj, start) {
  const dist = new Array(adj.length).fill(Infinity);
  const prev = new Array(adj.length).fill(-1);
  dist[start] = 0;
  const heap = new MinHeap();           // [거리, 정점]을 거리 순으로 꺼낸다
  heap.push([0, start]);
  while (heap.size) {
    const [d, u] = heap.pop();
    if (d > dist[u]) continue;          // 이미 더 짧은 값으로 확정됐다. 낡은 후보다
    for (const [v, w] of adj[u]) {
      if (d + w < dist[v]) {            // u를 거치면 더 짧다 → 완화
        dist[v] = d + w;
        prev[v] = u;                    // 어디서 왔는지 적어 둔다 (경로 복원용)
        heap.push([dist[v], v]);
      }
    }
  }
  return { dist, prev };
}
```

정점 여섯 개짜리 무방향 그래프에 돌려 봤다. 간선은 S-A 4, S-B 1, B-A 2, A-C 1, B-C 5, C-D 3, D-T 1, C-T 6, B-D 8이다. 꺼낼 때와 고칠 때마다 한 줄씩 찍었다.

```text
pop S(0) settle
  relax S->A: inf -> 4
  relax S->B: inf -> 1
pop B(1) settle
  relax B->A: 4 -> 3
  relax B->C: inf -> 6
  relax B->D: inf -> 9
pop A(3) settle
  relax A->C: 6 -> 4
pop A(4) stale, skip
pop C(4) settle
  relax C->D: 9 -> 7
  relax C->T: inf -> 10
pop C(6) stale, skip
pop D(7) settle
  relax D->T: 10 -> 8
pop T(8) settle
pop D(9) stale, skip
pop T(10) stale, skip
dist S=0 A=3 B=1 C=4 D=7 T=8
path S->B->A->C->D->T pops 10 stale 4
```

S에서 바로 가는 A는 4지만 B를 거치면 3이다. B를 꺼낸 순간 A의 값이 4에서 3으로 고쳐졌다. 힙 안에는 `A(4)`라는 옛 후보가 그대로 남아 있다가 나중에 꺼내지고, `d > dist[u]` 검사에 걸려 버려진다. 아래 그림에서 힙이 어떻게 차고 빠지는지 따라가 보자.

## 힙에 낡은 후보가 쌓여도 괜찮다

교과서의 다익스트라는 "decrease-key", 힙 안에 이미 있는 원소의 값을 줄이는 연산을 쓴다. 그러려면 정점마다 힙의 몇 번째 칸에 있는지 따로 적어 둬야 한다. 위 코드는 그 대신 새 후보를 그냥 하나 더 넣고, 꺼낼 때 낡은 것을 버린다. 이걸 lazy deletion이라고 부른다. 코드가 짧아서 실무와 코딩 테스트에서 대부분 이쪽을 쓴다.

대신 힙이 커진다. 최악이면 간선 하나마다 후보가 하나씩 들어가 힙 크기가 E까지 간다. 그래도 log E는 많아야 2 log V라서 복잡도는 O((V + E) log V) 그대로다. 정점 20만 개, 간선 100만 개 무작위 그래프에서 재 봤다.

```text
V=200000 E=1000000  1170ms  pops=203384 stale=3384 maxHeap=34018 farthest=1128
```

꺼낸 횟수 20만 3,384번 중 낡은 후보는 3,384개였다. 힙은 가장 클 때 3만 4천 개였다. 무작위 그래프에서는 걱정할 만큼 쌓이지 않는다. 1.2초는 `[거리, 정점]` 배열을 원소로 쓰는 단순한 힙이라 걸린 시간이고, 거리와 정점을 따로 담은 타입 배열 힙으로 바꾸면 줄어든다.

정점이 적고 간선이 꽉 찬 그래프라면 힙이 오히려 손해다. E가 V²에 가까우면 O(E log V)가 O(V² log V)가 된다. 이때는 힙 없이 매번 배열을 훑어 가장 가까운 정점을 찾는 O(V²) 구현이 더 빠르다. 피보나치 힙을 쓰면 이론상 O(E + V log V)지만 상수가 커서 실제로 쓰는 경우는 드물다.

## 지나온 길을 거꾸로 따라가기

거리만 묻는 면접 문제는 드물다. "그래서 어떤 길로 가나"가 꼬리 질문으로 온다. 완화할 때 `prev[v] = u`로 "v에 가장 짧게 오려면 u를 거친다"를 적어 두면 된다. 끝나고 나서 목적지에서 `prev`를 따라 출발점까지 거슬러 올라간 뒤 뒤집는다.

```js
function restorePath(prev, target) {
  const path = [];
  for (let v = target; v !== -1; v = prev[v]) path.push(v); // 목적지에서 거꾸로
  return path.reverse();                                     // 출발점부터 읽게 뒤집는다
}
```

위 예제에서 이렇게 얻은 길이 `S->B->A->C->D->T`다. 경로 전체를 정점마다 배열로 들고 다니면 메모리가 O(V²)까지 늘 수 있지만, `prev` 하나면 O(V)다. 거리가 같은 길이 여럿이면 `prev`는 먼저 찾은 쪽 하나만 기억한다. 같은 거리의 모든 길이 필요하면 `prev`를 목록으로 두고 같은 값일 때도 추가해야 한다.

`dist[target]`이 끝까지 무한대라면 닿을 수 없는 정점이다. 이걸 확인하지 않고 경로를 복원하면 목적지 하나짜리 배열이 나온다. 응답에 그대로 내보내면 "출발지와 목적지가 같은 경로"처럼 보이는 버그가 된다.

## 음수 간선 하나가 확정을 깬다

다익스트라의 확정은 "돌아와도 더 짧아질 수 없다"는 가정에 기대고 있다. 음수 간선은 바로 그 가정을 깬다. [그리디 알고리즘 글](/posts/greedy-algorithms)에서 정점 네 개로 한 번 보였는데, 여기서는 확정이 틀리면 그 뒤로 어떻게 번지는지 본다.

방향 그래프 S→A 2, A→C 2, S→B 4, B→A -3, C→T 1이다. 포인트 적립이나 환급처럼 거치면 비용이 줄어드는 구간이 B→A다. 정답은 S→B→A→C→T, 4 - 3 + 2 + 1 = 4다. 확정한 정점을 다시 보지 않는 다익스트라를 돌렸다.

```text
dijkstra settle order S(0) A(2) B(4) C(4) T(5)
dijkstra dist S=0 A=2 B=4 C=4 T=5
```

A를 2로 확정한 뒤 B를 꺼내 B→A를 보면 4 - 3 = 1이 나온다. 하지만 A는 이미 확정이라 고치지 않는다. 틀린 건 A 하나가 아니다. A를 거치는 C와 T도 같이 1씩 틀렸다. 확정 하나가 틀리면 그 정점 뒤의 모든 값이 따라 틀린다.

앞의 코드처럼 `done` 배열 없이 `d > dist[u]`만 검사하는 버전은 사정이 다르다. A가 1로 줄면 새 후보가 들어가고, A를 다시 꺼내 C와 T도 고친다. 음수 사이클만 없으면 답은 맞는다. 대신 한 정점이 여러 번 다시 꺼내질 수 있어서, 일부러 만든 그래프에서는 지수 시간까지 늘어난다. "음수가 있어도 lazy 다익스트라는 맞던데요"라는 말이 나오면 답은 맞아도 시간 보장이 없다고 짚으면 된다.

## 모든 간선을 V-1번 다시 본다

벨만-포드는 확정이라는 개념을 버린다. 대신 모든 간선을 한 바퀴 돌며 완화하는 일을 V - 1번 되풀이한다. 왜 V - 1번이면 충분할까. 사이클이 없는 최단 경로는 정점을 많아야 V개, 간선을 많아야 V - 1개 지난다. 한 바퀴를 돌 때마다 최단 경로의 간선이 적어도 하나씩 앞에서부터 맞춰지니, V - 1바퀴면 모두 맞는다.

```js
function bellmanFord(n, edges, start) {
  const dist = new Array(n).fill(Infinity);
  dist[start] = 0;
  for (let round = 1; round < n; round++) {     // V-1바퀴
    let changed = false;
    for (const [u, v, w] of edges) {
      if (dist[u] !== Infinity && dist[u] + w < dist[v]) {
        dist[v] = dist[u] + w;
        changed = true;
      }
    }
    if (!changed) return { dist, negativeCycle: false }; // 한 바퀴 동안 아무것도 안 바뀌면 끝
  }
  for (const [u, v, w] of edges) {              // V번째 바퀴에도 줄어들면 음수 사이클
    if (dist[u] !== Infinity && dist[u] + w < dist[v]) return { dist, negativeCycle: true };
  }
  return { dist, negativeCycle: false };
}
```

같은 음수 간선 그래프에 돌렸다. 간선은 S→A, A→C, S→B, B→A, C→T 순서로 넣었다.

```text
round 1: S=0 A=1 B=4 C=4 T=5
round 2: S=0 A=1 B=4 C=3 T=4
round 3: S=0 A=1 B=4 C=3 T=4 (no change, stop)
BF neg cycle false
```

첫 바퀴에서 A가 1로 줄었지만 C는 A가 줄기 전에 이미 계산돼 4로 남았다. 둘째 바퀴에서 C가 3, T가 4로 맞춰지고, 셋째 바퀴에서 아무것도 바뀌지 않아 일찍 멈췄다. 정점이 5개라 최대 4바퀴인데 3바퀴에 끝났다. 바퀴 수는 간선을 넣은 순서에 따라 달라진다. 운이 좋으면 한 바퀴, 나쁘면 V - 1바퀴다. 시간은 O(VE)라 정점 1만, 간선 10만이면 10억 번 완화까지 갈 수 있다.

`dist[u] !== Infinity` 검사를 빠뜨리면 생기는 버그가 있다. 자바스크립트에서는 `Infinity + (-3)`이 여전히 `Infinity`라 티가 안 나지만, 자바나 C++에서 무한대를 `Integer.MAX_VALUE` 같은 큰 정수로 두면 음수 간선을 더할 때 닿지도 않은 정점의 값이 줄어든다. 양수 간선을 더하면 넘침(overflow)으로 음수가 된다. 무한대를 `1e18`처럼 여유 있게 두고 닿지 않은 정점은 건너뛰는 습관이 필요하다.

## 고리를 돌수록 줄어드는 길: 음수 사이클

간선 무게를 다 더하면 음수인 고리가 있으면 최단 경로라는 말 자체가 성립하지 않는다. 고리를 한 바퀴 돌 때마다 더 짧아지니까 끝이 없다. 벨만-포드는 이걸 찾아낸다. V - 1바퀴 뒤에도 줄어드는 간선이 있다면, 그건 V개 넘는 간선을 지나는 길, 즉 고리를 도는 길이 더 짧다는 뜻이다.

이게 실제로 쓰이는 곳이 환율 차익 찾기다. 달러를 원으로, 원을 엔으로, 엔을 달러로 바꿨을 때 처음보다 많아지면 차익이 난다. 곱해서 1을 넘는지를 묻는 문제인데, 로그를 씌우면 곱이 합이 된다. 환율 r마다 무게를 -log r로 두면 "곱이 1보다 크다"가 "무게 합이 0보다 작다", 즉 음수 사이클이 된다.

```js
const rates = [["USD", "KRW", 1380], ["KRW", "JPY", 0.108], ["JPY", "USD", 0.0068]];
const edges = rates.map(([a, b, r]) => [idx[a], idx[b], -Math.log(r)]); // 곱 → 합, 크다 → 작다
```

```text
product 1.0135
USD->KRW w=-7.2298

```

세 환율을 곱하면 1.0135, 한 바퀴에 1.35%가 남는다. 무게 합은 -0.0134로 음수이고 벨만-포드가 음수 사이클을 찾았다. 예제의 환율은 차익이 나도록 일부러 맞춘 값이다. 실제 시장에서는 수수료와 호가 차이 때문에 이런 고리가 거의 바로 사라진다.

네트워크 라우팅에도 같은 두 갈래가 있다. 링크 상태 방식(OSPF)은 라우터마다 전체 지도를 받아 다익스트라를 돌린다. 거리 벡터 방식(RIP)은 이웃과 거리표를 주고받으며 조금씩 고치는데, 그 과정이 벨만-포드를 여러 라우터가 나눠 돌리는 모양이다. 라우터가 하는 일은 [라우터와 스위치](/posts/router-vs-switch)에 있다.

## 목적지 쪽으로 기울이는 A\*

다익스트라는 목적지를 모른다. 출발점을 중심으로 원을 넓혀 가듯 모든 방향을 똑같이 뒤진다. 목적지가 동쪽에 있어도 서쪽 정점까지 확정한다. A\*는 힙의 순서를 바꾼다. 지금까지 온 거리 g에 "여기서 목적지까지 남은 거리의 추정" h를 더한 f = g + h가 작은 것부터 꺼낸다. 코드로는 힙에 넣는 값 한 곳만 다르다.

```js
heap.push([dist[v] + h(v), v]); // 다익스트라는 h(v) = 0인 A*다
```

h를 어떻게 잡느냐가 전부다. 두 가지 성질을 본다.

허용성(admissible)은 h가 실제 남은 거리보다 절대 크지 않다는 성질이다. 지도라면 직선거리가 그렇다. 직선보다 짧은 길은 없으니까. 허용성이 있으면 A\*도 최단 경로를 보장한다. 일관성(consistent)은 더 강한 조건으로, 간선 u→v마다 h(u) ≤ w(u, v) + h(v)가 성립하는 것이다. 한 걸음 갈 때 추정이 그 걸음의 비용보다 많이 줄지 않는다는 뜻이다. 일관성이 있으면 다익스트라처럼 한 번 꺼낸 정점을 다시 볼 일이 없다. 허용적이지만 일관적이지 않은 h라면 이미 꺼낸 정점을 다시 열어야 최단 경로가 보장된다. 직선거리, 격자의 맨해튼 거리는 둘 다 일관적이다.

정점 11개짜리 그래프에서 세 가지를 비교했다. 간선 무게는 두 점 사이 직선거리를 올림한 값이라 직선거리 h는 허용적이다. 세 번째는 h에 3을 곱해 일부러 부풀렸다.

```text

astar settled 5 S E D F G | path S-D-F-G cost 295

```

정점이 많을수록 차이가 벌어진다. 100×100 격자 한가운데 세로 벽을 세우고, 벽 왼쪽에서 오른쪽으로 가는 길을 찾았다. 벽은 위아래 끝이 열려 있어서 돌아가야 한다. 한 칸 이동 비용은 1, h는 맨해튼 거리다.

```text

A* manhattan     settled  4427 of 10000  cost 162  12.5ms
A* 2x manhattan  settled  3300 of 10000  cost 162  19.7ms
A* 5x manhattan  settled  2522 of 10000  cost 162  8.6ms
```

다익스트라는 격자 1만 칸 중 9,822칸을 확정했다. 맨해튼 A\*는 절반 아래인 4,427칸이다. 부풀린 h는 더 줄었고 이 격자에서는 길이도 162로 같았다. 앞의 작은 그래프에서 봤듯 늘 같지는 않다. 시간은 돌릴 때마다 출렁이니 확정한 칸 수를 보면 된다.

h가 0이면 다익스트라와 같고, h가 실제 남은 거리와 정확히 같으면 최단 경로 위의 정점만 꺼낸다. 좋은 h는 실제에 가깝되 넘지 않는 값이다. 대각선 이동이 되는 격자에 맨해튼 거리를 쓰면 실제보다 커져서 허용성이 깨진다. 이때는 옥타일 거리나 체비쇼프 거리를 쓴다.

## 무게가 0과 1뿐이면 덱으로

벽을 부수면 비용 1, 그냥 지나가면 0인 미로처럼 무게가 두 가지뿐인 문제가 있다. 힙 없이 [덱](/posts/ds-stack-queue-deque) 하나로 다익스트라와 같은 답을 낸다. 무게 0인 간선으로 간 정점은 덱의 앞에, 1인 간선으로 간 정점은 뒤에 넣는다. 그러면 덱 안의 거리가 늘 앞에서 뒤로 많아야 1 차이로 정렬된 상태가 유지되고, 앞에서 꺼내는 것이 곧 가장 가까운 것을 꺼내는 일이 된다.

```js
function zeroOneBfs(adj, start) {
  const dist = new Array(adj.length).fill(Infinity);
  dist[start] = 0;
  const deque = [start];                 // 예시용. 실제로는 링 버퍼 덱을 쓴다
  while (deque.length) {
    const u = deque.shift();
    for (const [v, w] of adj[u]) {       // w는 0 또는 1
      if (dist[u] + w < dist[v]) {
        dist[v] = dist[u] + w;
        if (w === 0) deque.unshift(v);   // 거리가 그대로면 앞에
        else deque.push(v);              // 1 늘면 뒤에
      }
    }
  }
  return dist;
}
```

시간은 O(V + E)다. 예시의 `shift`와 `unshift`는 배열 전체를 밀어서 O(n)이니 큰 입력에서는 [링 버퍼](/posts/ds-stack-queue-deque)로 바꿔야 한다. 무게가 0부터 작은 정수 k까지라면 거리별 통을 두는 Dial 알고리즘으로 넓힐 수 있다.

## 모든 쌍이 필요하면 플로이드-워셜

배송 거점 수십 곳 사이의 거리표가 통째로 필요할 때가 있다. 출발점마다 다익스트라를 V번 돌려도 되고, 플로이드-워셜로 한 번에 구해도 된다. 플로이드-워셜은 "중간에 0번부터 k번 정점까지만 거쳐도 될 때의 최단 거리"를 k를 하나씩 늘리며 채우는 [동적 계획법](/posts/dynamic-programming)이다.

```js
for (let k = 0; k < n; k++)          // 거쳐도 되는 정점을 하나씩 늘린다. k가 맨 바깥이어야 한다
  for (let i = 0; i < n; i++)
    for (let j = 0; j < n; j++)
      if (d[i][k] + d[k][j] < d[i][j]) d[i][j] = d[i][k] + d[k][j];
```

방향 그래프 A→B 3, A→D 7, B→A 8, B→C 2, C→A 5, C→D 1, D→A 2에 돌린 결과다.

```text
      A  B  C  D
A     0  3  5  6
B     5  0  2  3
C     3  6  0  1
D     2  5  7  0
```

A에서 D로 바로 가면 7이지만 A→B→C→D로 3 + 2 + 1 = 6이다. B에서 A는 바로 가는 8보다 B→C→D→A의 5가 짧다. 세 겹 반복문이라 O(V³), 정점 400개에서 225ms가 걸렸다. 1,000개면 대략 15배라 몇 초, 1만 개면 쓸 수 없다. 메모리도 V² 칸이다.

자주 하는 실수는 반복문 순서다. k를 안쪽에 두면 아직 다 채우지 않은 값을 근거로 계산해서 틀린다. 음수 간선도 다루고, 끝난 뒤 `d[i][i]`가 음수인 i가 있으면 음수 사이클이 있다는 뜻이다. 간선이 적은 큰 그래프에서 모든 쌍이 필요하면 다익스트라를 V번 돌리는 O(V(V + E) log V)가 더 빠르고, 음수 간선이 섞여 있으면 벨만-포드로 무게를 한 번 고친 뒤 다익스트라를 V번 돌리는 Johnson 알고리즘을 쓴다.

## 현장에서 최단 경로가 틀리는 순간

길 찾기 API가 가끔 엉뚱한 경로를 낸다는 문의가 오면 먼저 무게부터 본다. 무게를 계산하는 식이 할인이나 보정을 넣다가 음수를 만들고 있지 않은지, 결측값이 0으로 들어가 공짜 구간이 생기지 않았는지다. 다익스트라 자체가 틀리는 경우보다 입력이 가정을 어기는 경우가 훨씬 많다. 서비스 코드라면 그래프를 만들 때 `w >= 0`을 검사해 어기면 바로 실패시키는 편이 낫다.

두 번째로 흔한 건 확정 시점 버그다. 힙에 넣을 때 `visited`를 표시하면 나중에 더 짧은 값이 와도 무시해서 틀린다. BFS에서는 넣을 때 표시하는 게 맞았기 때문에 그 습관이 그대로 넘어온다. 다익스트라에서는 꺼낼 때 확정한다. 비교 함수를 거꾸로 써서 최대 힙이 되는 실수도 테스트가 작으면 우연히 통과한다.

세 번째는 규모다. 도로망 전체 같은 큰 그래프에서 질의마다 다익스트라를 처음부터 돌리면 수백 ms에서 초 단위가 걸린다. 실제 지도 엔진은 지름길 간선을 미리 계산해 두는 Contraction Hierarchies 같은 전처리로 질의를 ms 단위로 줄인다. 대신 교통 정보로 무게가 바뀌면 전처리를 다시 해야 한다. 그 구조는 [지도와 길 찾기](/posts/sd-maps-tiles-routing)에서 다룬다. 출발점과 목적지 양쪽에서 동시에 퍼뜨리는 양방향 다익스트라도 탐색 범위를 줄이는 흔한 방법이다.

마지막으로 재현이다. 같은 거리의 길이 여럿이면 힙의 동점 처리에 따라 매번 다른 길이 나올 수 있다. 테스트가 경로를 비교하다 가끔 깨진다면 거리만 비교하거나, 동점일 때 정점 번호로 순서를 고정한다.

## 직접 짜 보기

## 면접에서 나올 만한 질문

### 다익스트라 알고리즘은 어떻게 동작하나요?

아직 확정하지 않은 정점 중 출발점에서 가장 가까운 것을 꺼내 확정하고, 그 정점에서 나가는 간선으로 이웃의 거리를 고치는 일을 반복한다. 가장 가까운 정점을 빨리 꺼내려고 최소 힙을 쓴다. 간선 무게가 음수가 아니면 꺼낸 순간의 거리가 최단 거리라는 게 보장된다. 다른 길로 돌아오려면 더 먼 정점을 거쳐야 하기 때문이다.

### 시간 복잡도는요? 힙을 안 쓰면요?

이진 힙을 쓰면 O((V + E) log V)다. lazy deletion으로 힙에 후보가 E개까지 쌓여도 log E가 2 log V 이하라 같다. 힙 없이 매번 배열을 훑으면 O(V²)인데, 간선이 V²에 가까운 밀집 그래프에서는 이쪽이 더 빠르다. 피보나치 힙은 이론상 O(E + V log V)지만 상수가 커서 잘 쓰지 않는다.

### 왜 음수 간선이 있으면 틀리나요?

꺼낸 정점을 확정하는 근거가 "돌아와도 더 짧아질 수 없다"인데, 음수 간선은 나중에 꺼낸 정점을 거쳐 이미 확정한 정점을 더 짧게 만든다. 확정이 하나 틀리면 그 정점을 거치는 뒤쪽 정점도 모두 틀린다. 확정 표시 없이 다시 넣는 lazy 버전은 음수 사이클만 없으면 답은 맞지만 시간이 지수까지 늘 수 있다. 음수 간선이 있으면 벨만-포드를 쓴다.

### 벨만-포드는 왜 V-1번 반복하나요? 음수 사이클은 어떻게 찾나요?

사이클이 없는 최단 경로는 간선을 많아야 V - 1개 지나고, 모든 간선을 한 바퀴 완화할 때마다 최단 경로의 간선이 적어도 하나씩 맞춰지기 때문이다. V - 1바퀴 뒤 한 바퀴 더 돌았을 때 아직 줄어드는 간선이 있으면 고리를 돌수록 짧아지는 음수 사이클이 있다는 뜻이다. 시간은 O(VE)이고, 한 바퀴에 아무것도 안 바뀌면 일찍 멈출 수 있다.

### A\*는 다익스트라와 무엇이 다르고, 휴리스틱은 어떻게 고르나요?

힙의 기준을 지금까지 온 거리 g에서 g + h로 바꾼 것이다. h는 남은 거리의 추정이고, 실제보다 크지 않으면(허용성) 최단 경로를 보장한다. 간선마다 h(u) ≤ w + h(v)인 일관성까지 있으면 정점을 한 번만 꺼내도 된다. 지도는 직선거리, 4방향 격자는 맨해튼 거리를 쓴다. h를 부풀리면 더 빨리 끝나지만 더 긴 길을 고를 수 있다. 본문 예제에서 3배로 키우자 295 대신 308짜리 길이 나왔다.

### 경로 자체는 어떻게 복원하나요?

완화할 때 `prev[v] = u`로 어디서 왔는지 적어 두고, 끝나면 목적지에서 `prev`를 따라 출발점까지 올라간 뒤 뒤집는다. 메모리는 O(V)다. 목적지 거리가 무한대면 닿을 수 없는 것이니 복원하기 전에 확인한다. 같은 거리의 모든 경로가 필요하면 `prev`를 목록으로 둔다.

### 모든 쌍의 최단 거리는 어떻게 구하나요?

정점이 수백 개 이하면 플로이드-워셜로 O(V³)에 구한다. 중간에 거쳐도 되는 정점을 하나씩 늘려 가는 DP라 k 반복문이 맨 바깥에 있어야 한다. 간선이 적은 큰 그래프는 다익스트라를 V번 돌리는 편이 빠르고, 음수 간선이 있으면 무게를 한 번 고친 뒤 다익스트라를 돌리는 Johnson 알고리즘을 쓴다.

### 실제 지도 서비스도 다익스트라를 질의마다 돌리나요?

그대로 돌리면 대륙 규모 도로망에서 너무 느리다. Contraction Hierarchies처럼 지름길 간선을 미리 계산해 두는 전처리를 하고, 질의 때는 양방향 탐색으로 아주 적은 정점만 본다. 대신 교통 상황으로 무게가 바뀌면 전처리를 다시 해야 해서, 무게 변화를 빨리 반영하는 변형 기법을 함께 쓴다.
