<EasyIntro>

  VPN은 고속도로 위를 달리는 잠긴 화물 트럭과 같다. 고속도로인 인터넷은 모두가 함께 쓰지만, 트럭 안의 짐인 원래 데이터는 밖에서 볼 수도 바꿀 수도 없고, 트럭 겉면에는 출발 창고와 도착 창고 주소만 적혀 있다. 오래된 방식인 IPsec은 트럭을 띄우기 전에 어떤 자물쇠를 쓸지와 어떤 짐을 실을지를 양쪽이 하나하나 협상해서, 하나라도 어긋나면 출발하지 못한다. 새 방식인 WireGuard는 자물쇠를 하나로 정해 두고 서로의 열쇠 모양만 적어 두면 바로 출발한다.

재택 근무 날, VPN을 켜고 사내 위키는 잘 열리는데 사내 DB(`192.168.60.20`)에는 접속이 안 된다. 옆자리 동료는 된다고 한다. 같은 날 인프라 팀은 IDC와 AWS 사이에 IPsec 터널을 새로 놓았는데, 로그에 `NO_PROPOSAL_CHOSEN`만 반복해서 찍힌다. 두 장면 모두 VPN이 무엇을 터널로 보낼지 정하는 규칙과, 터널을 맺는 협상 과정을 알면 바로 원인이 보인다.

이 글은 VPN이 왜 필요한지에서 출발해, 패킷을 다른 패킷 안에 넣어 나르는 원리, IPsec이 IKE로 열쇠를 나누고 ESP로 암호화하는 과정, WireGuard가 이걸 훨씬 단순하게 다시 짠 방식을 차례로 본다. 실제로 터널을 두 개 만들어 패킷을 캡처했다. 기준 OS는 Ubuntu 24.04다. 실습 컨테이너의 커널에는 WireGuard 모듈과 IPsec(XFRM ESP)이 빠져 있어서, WireGuard는 공식 사용자 공간 구현인 wireguard-go로, IPsec은 strongSwan 5.9.13의 사용자 공간 ESP(kernel-libipsec 플러그인)로 돌렸다. 프로토콜과 패킷 모양, 명령 출력은 커널 구현과 같다. 다른 점은 그때그때 적는다.

터널이 MTU를 깎아 큰 패킷만 사라지는 문제는 [MTU 글](/posts/layer-mtu-fragmentation)에서 자세히 다뤘으니 여기서는 짧게만 짚는다. 패킷을 감싸는 다른 방식인 VXLAN은 [오버레이 글](/posts/sdn-vxlan-overlay)에서 본다.

## 남의 길 위에 내 전용 통로를 낸다

회사 두 곳을 잇는 가장 확실한 방법은 전용 회선이다. 통신사가 두 건물 사이에 남과 섞이지 않는 회선을 깔아 준다. 안전하고 품질도 좋지만 비싸고, 개통에 몇 주가 걸리고, 직원 노트북마다 깔아 줄 수는 없다.

VPN(Virtual Private Network)은 누구나 쓰는 인터넷 위에 전용 회선을 흉내 낸다. 이 글에서는 VPN을 "고속도로 위를 달리는 잠긴 화물 트럭"으로 생각하겠다. 고속도로(인터넷)는 모두가 쓰지만, 트럭(바깥 패킷) 안의 짐(원래 패킷)은 밖에서 볼 수도 바꿀 수도 없다. 트럭 겉면에는 출발 창고와 도착 창고 주소만 적혀 있다.

VPN은 쓰임새로 두 가지로 나뉜다.

- 사이트 간 VPN(site-to-site): 사무실과 IDC, IDC와 클라우드처럼 망과 망을 잇는다. 양 끝의 게이트웨이 장비가 터널을 맺고, 망 안의 서버들은 VPN이 있는지도 모른다. 주로 IPsec을 쓴다. AWS Site-to-Site VPN, GCP Cloud VPN이 이쪽이다.
- 원격 접속 VPN(remote access): 직원 노트북 하나가 회사 망에 붙는다. 노트북에 클라이언트를 깔고 회사의 VPN 게이트웨이에 접속한다. IPsec(IKEv2), TLS 기반(OpenVPN, 상용 SSL VPN), WireGuard가 모두 쓰인다.

어느 쪽이든 하는 일은 같다. 원래 패킷을 암호화해서 새 패킷 안에 넣고, 반대편 게이트웨이가 꺼내서 원래 목적지로 보낸다.

## IPsec은 두 단계로 나뉜다

IPsec은 1990년대에 IPv6와 함께 설계된, IP 계층에서 암호화하는 표준 묶음이다. 장비 제조사와 클라우드가 모두 지원해서 사이트 간 VPN의 사실상 표준이다. 부품이 여럿이라 처음엔 헷갈리는데, 두 단계로 나눠 보면 정리된다.

1. 열쇠를 나누는 단계: IKE(Internet Key Exchange). 서로 누구인지 확인하고, 어떤 암호 방식을 쓸지 합의하고, 암호 키를 만든다. UDP 500번(NAT가 있으면 4500번)으로 대화한다. 지금은 IKEv2(RFC 7296)를 쓴다.
2. 실제 데이터를 보내는 단계: ESP(Encapsulating Security Payload). IKE가 만든 키로 패킷을 암호화하고 무결성 검사값을 붙인다. ESP는 TCP나 UDP가 아니라 IP 프로토콜 번호 50번을 쓰는 별도 프로토콜이다.

IKE가 합의한 결과를 SA(Security Association)라고 부른다. IKE 자체를 보호하는 IKE SA가 하나 있고, 그 안에서 데이터용 CHILD SA(ESP SA)를 만든다. CHILD SA는 방향마다 하나씩, 각자 SPI라는 32비트 번호를 갖는다. 받는 쪽은 ESP 패킷의 SPI를 보고 어느 키로 풀지 찾는다.

옛 글에 자주 나오는 AH(Authentication Header, 프로토콜 51)는 암호화 없이 무결성만 보장하고, 바깥 IP 헤더까지 검사해서 NAT를 지나면 깨진다. 지금은 거의 쓰지 않는다.

모드도 두 가지다. 터널 모드는 원래 IP 패킷 전체를 암호화하고 새 IP 헤더를 씌운다. 게이트웨이끼리 망을 잇는 사이트 간 VPN이 이걸 쓴다. 전송 모드는 원래 IP 헤더는 두고 그 뒤의 내용만 암호화한다. 서버 두 대가 직접 암호화할 때 쓴다.

### IKEv2 협상을 따라가 본다

게이트웨이 두 대(`gw-a` 198.51.100.1, `gw-b` 198.51.100.2)를 네임스페이스로 만들고, 뒤에 각각 `10.1.0.0/24`, `10.2.0.0/24` 사내망을 붙였다. 설정은 strongSwan의 swanctl 형식이다.

```text
connections {
  site-a-to-b {
    version = 2
    local_addrs = 198.51.100.1
    remote_addrs = 198.51.100.2
    proposals = aes256gcm16-prfsha256-x25519
    local { auth = psk
            id = gw-a }
    remote { auth = psk
             id = gw-b }
    children {
      lan-a-to-b {
        local_ts = 10.1.0.0/24
        remote_ts = 10.2.0.0/24
        esp_proposals = aes256gcm16-x25519
      }
    }
  }
}
```

`proposals`는 IKE SA의 암호 조합(AES-256-GCM, PRF는 SHA-256, 키 교환은 X25519), `esp_proposals`는 데이터용 조합이다. `local_ts`와 `remote_ts`는 트래픽 셀렉터, 즉 "어떤 출발지에서 어떤 목적지로 가는 패킷을 이 터널에 넣을지"다. 아래 그림이 터널을 여는 메시지 흐름이다.

```text
13:26:25.818102 IP 198.51.100.2.4500 > 198.51.100.1.4500: UDP-encap: ESP(spi=0x10773fa4,seq=0x1), length 120
```

다섯째 줄부터가 사내망 ping이다. 가는 쪽은 SPI `0x721a4fef`, 오는 쪽은 `0x10773fa4`로 방향마다 다르다. `seq`는 재전송 공격을 막는 일련번호다. 안의 84바이트 ICMP 패킷이 ESP 헤더 8, IV 8, 패딩을 더한 암호문 88, 무결성 태그 16바이트를 붙여 120바이트가 됐다. 같은 포트 4500에서 IKE와 ESP를 가르는 게 `NONESP-encap` 표시다. IKE 패킷 앞에는 4바이트 0을 붙여 ESP가 아님을 표시한다.

협상이 끝난 상태는 `--list-sas`로 본다.

```bash

sudo swanctl --list-sas
```

```text
  local  'gw-a' @ 198.51.100.1[4500]

  established 12s ago, rekeying in 14204s
  lan-a-to-b: #1, reqid 1, INSTALLED, TUNNEL-in-UDP, ESP:AES_GCM_16-256
```

장애를 볼 때는 `in`과 `out` 카운터가 핵심이다. `out`만 늘고 `in`이 0이면 터널은 맺어졌는데 상대가 응답을 터널로 돌려보내지 않는 것이다. 상대의 라우팅이나 방화벽, 또는 UDP 4500이 중간에서 막힌 경우다.

암호 조합이 겹치지 않으면 첫 메시지에서 끝난다. gw-b의 IKE 조합을 `aes128-sha256-modp2048`로 바꿨다.

```text
[NET] received packet: from 198.51.100.2[500] to 198.51.100.1[500] (36 bytes)
[ENC] parsed IKE_SA_INIT response 0 [ N(NO_PROP) ]
[IKE] received NO_PROPOSAL_CHOSEN notify error
```

처음 장면의 인프라 팀 로그가 이것이다. 클라우드 VPN과 붙일 때 흔하다. AWS 같은 클라우드는 기본으로 여러 조합을 받아 주지만, 사내 장비가 옛 조합(예: 3DES, DH 그룹 2) 하나만 고집하면 겹치는 게 없다. 양쪽이 제안하는 목록을 로그에서 비교하고, 한쪽에 맞춰 준다.

사전 공유 키(PSK)가 다르면 두 번째 왕복에서 끝난다.

```text
[ENC] parsed IKE_AUTH response 1 [ N(AUTH_FAILED) ]
[IKE] received AUTHENTICATION_FAILED notify error
```

키가 다른 경우 말고도, 한쪽이 기대하는 ID(`id = gw-b`)와 상대가 보낸 ID가 다를 때 같은 메시지가 나온다. 기본 ID가 IP 주소인데 상대가 NAT 뒤에 있어서 사설 IP를 ID로 보내는 경우가 대표적이다.

트래픽 셀렉터가 어긋나면 IKE SA는 맺어지는데 CHILD SA가 안 생긴다. gw-b의 `remote_ts`를 `10.1.1.0/24`로 바꿨다.

```text
[IKE] IKE_SA site-a-to-b[4] established between 198.51.100.1[gw-a]...198.51.100.2[gw-b]
[IKE] received TS_UNACCEPTABLE notify, no CHILD_SA built
[IKE] failed to establish CHILD_SA, keeping IKE_SA
```

이게 가장 헷갈린다. 상태 화면에는 터널이 `ESTABLISHED`로 보이는데 사내망 트래픽이 안 흐른다. 한쪽은 `/24` 전체, 다른 쪽은 `/24` 중 일부만 적었거나, 서브넷을 하나 추가하면서 한쪽만 고친 경우다. 양쪽의 `local_ts`와 `remote_ts`가 서로 거울처럼 맞는지 본다.

## NAT를 지나는 법

ESP에는 포트 번호가 없다. 집 공유기나 클라우드의 NAT는 포트로 연결을 구분하는데, 포트가 없으니 ESP 패킷을 어느 내부 기기로 보낼지 모른다. 그래서 IKE가 첫 메시지에서 NAT가 있는지 확인하고(NATD 해시), NAT가 있으면 ESP를 UDP 4500번 안에 넣어 보낸다. 이게 NAT-T(NAT Traversal, RFC 3948)다. 위 캡처의 `UDP-encap: ESP`가 그 모양이다.

NAT 장비는 한동안 패킷이 없는 UDP 연결을 금방 잊는다([UDP 글](/posts/udp-and-quic)에서 다뤘다). 그래서 NAT 뒤의 쪽은 20초 정도마다 1바이트짜리 NAT-T keepalive를 보내 연결 기록을 살려 둔다. 방화벽 담당자에게 IPsec을 열어 달라고 할 때는 UDP 500, UDP 4500, 그리고 NAT가 없을 때 쓰는 IP 프로토콜 50(ESP)을 함께 말해야 한다. 프로토콜 50을 "포트 50"으로 잘못 알아들어 TCP 50을 여는 실수도 실제로 있다.

## WireGuard는 설정할 게 거의 없다

IPsec은 강력하지만 고를 게 너무 많다. 암호 조합만 수십 가지, 인증 방식, 모드, 수명, 셀렉터까지 양쪽이 다 맞아야 한다. 코드도 크다. WireGuard는 2016년 Jason Donenfeld가 이걸 정반대로 다시 짰다. 리눅스 커널에는 5.6(2020년)부터 들어가 있고, Ubuntu 20.04 이후 커널은 모두 쓸 수 있다.

설계 원칙은 "고를 게 없다"다.

- 암호 방식이 고정이다. 키 교환은 Curve25519, 암호화는 ChaCha20-Poly1305, 해시는 BLAKE2s, 핸드셰이크는 Noise 프로토콜의 IKpsk2 패턴이다. 협상 단계가 없으니 `NO_PROPOSAL_CHOSEN` 같은 실패도 없다. 약점이 발견되면 프로토콜 버전을 통째로 올린다.
- 신원은 공개 키 하나다. SSH처럼 서로의 공개 키를 설정 파일에 적는다. 사용자 이름, 인증서, PSK 없이도 된다(PSK는 양자 내성용 선택 사항이다).
- UDP 하나만 쓴다. IKE와 ESP처럼 둘로 나뉘지 않고, NAT 통과가 처음부터 기본이다.
- 연결 상태가 거의 없다. 보낼 게 없으면 아무것도 보내지 않는다. 모르는 키로 온 패킷에는 응답하지 않아서 포트 스캔에 걸리지도 않는다.

설정 파일은 이 정도다. 노트북 쪽 `/etc/wireguard/wg0.conf` 예시다.

```ini
[Interface]
PrivateKey = <노트북 개인 키>
Address = 10.8.0.2/24
DNS = 192.168.60.53

[Peer]
PublicKey = <게이트웨이 공개 키>
Endpoint = vpn.example.com:51820
AllowedIPs = 10.8.0.0/24, 192.168.60.0/24
PersistentKeepalive = 25
```

```bash
# 키 한 쌍 만들기 (개인 키는 남이 못 읽게)
umask 077
wg genkey | tee privatekey | wg pubkey > publickey
# wg0.conf대로 인터페이스를 만들고 주소, 경로까지 잡는다
sudo wg-quick up wg0
# 부팅할 때 자동으로 올린다
sudo systemctl enable wg-quick@wg0
```

## AllowedIPs가 라우팅과 방화벽을 겸한다

WireGuard에서 가장 중요한 설정은 `AllowedIPs`다. 한 줄이 두 가지 일을 한다.

- 나갈 때: 목적지가 어느 피어의 AllowedIPs에 들어가는지 보고 그 피어로 암호화해 보낸다. 여러 피어가 겹치면 더 긴 프리픽스가 이긴다. 라우팅 테이블과 같은 규칙이다(최장 일치는 [라우팅 글](/posts/layer-ip-routing-icmp)에서 다뤘다). 어느 피어에도 안 맞으면 보내지 않는다.
- 들어올 때: 복호화한 패킷의 출발지 IP가 보낸 피어의 AllowedIPs에 들어 있는지 본다. 아니면 버린다.

## 무엇을 터널로 보낼 것인가

VPN을 켰을 때 모든 트래픽을 터널로 보내면 전체 터널(full tunnel), 사내 대역만 보내면 스플릿 터널(split tunnel)이다. WireGuard에서는 AllowedIPs에 `0.0.0.0/0, ::/0`을 넣으면 전체 터널이다.

전체 터널은 카페 Wi-Fi 같은 믿을 수 없는 망에서도 모든 트래픽을 보호하고, 회사가 인터넷 트래픽까지 검사할 수 있다. 대신 화상 회의와 동영상까지 회사 게이트웨이를 돌아 나가 느려지고, 게이트웨이 대역폭이 모자라기 쉽다. 스플릿 터널은 빠르지만, 노트북이 회사망과 인터넷에 동시에 걸쳐 있는 셈이라 보안 정책상 금지하는 회사도 있다.

둘 다 놓치기 쉬운 게 DNS다. 사내 도메인(`db.corp.internal`)은 사내 DNS만 안다. 스플릿 터널인데 DNS는 집 공유기를 쓰면 사내 이름이 안 풀린다. 반대로 전체 터널인데 DNS 질의만 집 회선으로 새면(DNS 누출) 어떤 사이트에 가는지 그대로 드러난다. wg-quick의 `DNS =` 줄이나 systemd-resolved의 도메인별 라우팅으로 맞춘다.

`PersistentKeepalive = 25`는 NAT 뒤의 피어가 25초마다 빈 패킷을 보내 NAT 기록을 살려 두는 설정이다. 게이트웨이처럼 고정 주소가 있는 쪽에는 필요 없고, NAT 뒤에 있으면서 밖에서 먼저 연결을 받아야 하는 쪽에 둔다. 이게 없으면 "한동안 조용하다가 서버 쪽에서 먼저 보내면 안 닿는다"는 증상이 생긴다.

## 무엇을 고를까

| | IPsec (IKEv2) | WireGuard | OpenVPN·SSL VPN |
|---|---|---|---|
| 동작 계층 | IP (커널) | IP (커널, 가상 인터페이스) | 사용자 공간, TLS 위 |
| 협상 | 암호 조합·셀렉터를 협상 | 없음 (고정) | TLS 협상 |
| 쓰는 포트 | UDP 500·4500, ESP(50) | UDP 하나 (보통 51820) | UDP 1194 또는 TCP 443 |
| 장비·클라우드 호환 | 거의 모든 방화벽·클라우드 | 늘고 있지만 장비 지원은 적다 | 상용 SSL VPN 제품군 |
| 사용자 인증 | 인증서, PSK, EAP(ID·비밀번호) | 공개 키뿐 (계정 연동은 별도) | 인증서, ID·비밀번호, SSO 연동 |

사이트 간 연결, 특히 상대가 클라우드나 방화벽 장비라면 IPsec이 거의 유일한 선택이다. AWS Site-to-Site VPN은 연결 하나에 터널 두 개를 주고 BGP로 경로를 주고받게 한다. 한쪽 터널이 점검으로 내려가도 다른 쪽으로 넘어가게 하려는 것이니, 두 터널을 모두 올려 두지 않으면 AWS 정기 점검 때 연결이 끊긴다.

서버끼리, 또는 개발팀의 원격 접속이라면 WireGuard가 설정과 운영 모두 단순하다. 다만 계정 관리(입사·퇴사 때 키 추가·삭제), SSO 연동, 접속 기록 같은 기능은 기본으로 없어서, Tailscale처럼 WireGuard 위에 관리 기능을 얹은 제품을 쓰거나 직접 만들어야 한다. TCP 443 하나만 열린 호텔 망에서 붙어야 한다면 TCP를 쓰는 SSL VPN이 유리하다. 다만 TCP 위에 TCP를 실으면 손실이 났을 때 재전송이 겹쳐 느려진다.

VPN 자체가 "사내망에 들어오면 다 믿는다"는 모델이라는 점도 기억해 두자. 노트북 하나가 감염되면 VPN을 타고 사내망 전체에 닿는다. 사용자와 기기를 요청마다 확인하는 방향은 [제로 트러스트 글](/posts/zero-trust-architecture)에서 다룬다.

### 터널에 라우팅 프로토콜을 태우려면: GRE와 GRE over IPsec

IPsec 터널 모드에는 오래된 약점이 하나 있다. 트래픽 셀렉터에 맞는 유니캐스트 IP 패킷만 싣는다. OSPF 같은 라우팅 프로토콜은 이웃을 찾을 때 멀티캐스트(OSPF는 224.0.0.5)를 쓰니, 정책 기반 IPsec만으로는 양쪽 라우터가 터널 너머 이웃을 만나지 못한다. 지점이 늘 때마다 셀렉터와 정적 경로를 손으로 맞춰야 한다.

GRE(Generic Routing Encapsulation, IP 프로토콜 번호 47)가 이 빈칸을 메운다. GRE는 어떤 패킷이든 4바이트짜리 GRE 헤더와 새 IP 헤더로 감싸서 보내는 단순한 터널이다. 멀티캐스트도, IPv6도, 라우팅 프로토콜도 그대로 싣고, 양 끝에 일반 인터페이스(`gre1`)가 생기니 라우팅 테이블에서 보통 링크처럼 다룬다. 대신 암호화도, 인증도 없다. 새 IP 20바이트와 GRE 4바이트, 모두 24바이트가 붙으니 1500 링크 위의 GRE 터널 MTU는 1476이다.

```bash
# 리눅스에서 GRE 터널 하나 (ip_gre 커널 모듈 필요). 양쪽에서 local과 remote를 바꿔 실행한다
sudo ip tunnel add gre1 mode gre local 198.51.100.1 remote 203.0.113.2 ttl 64
sudo ip addr add 172.31.255.1/30 dev gre1   # 터널 안쪽 주소. 라우팅 이웃은 이 주소로 맺는다
sudo ip link set gre1 up
ip -d link show gre1                        # mtu 1476과 gre remote 203.0.113.2가 보이면 된다
```

그래서 둘을 겹쳐 쓴다. GRE로 멀티캐스트와 라우팅 프로토콜을 감싸고, 그 GRE 패킷(두 게이트웨이 공인 IP 사이의 프로토콜 47)을 IPsec으로 암호화한다. 이것이 GRE over IPsec이다. GRE가 "무엇이든 싣는 통로"를, IPsec이 "엿보거나 고치지 못하게"를 맡는다. 헤더가 두 겹이라 MTU가 더 줄어드니, 바로 다음 절에서 다룰 MSS 클램핑을 꼭 함께 건다.

요즘 장비와 클라우드는 같은 목적을 경로 기반 VPN으로 푼다. IPsec 위에 가상 터널 인터페이스(VTI)를 만들고, 셀렉터를 0.0.0.0/0으로 넓혀 둔 뒤 무엇을 보낼지는 라우팅 테이블이 정한다. 그 인터페이스 위에서 BGP를 맺으면 멀티캐스트가 없어도 경로를 주고받는다. 앞에서 말한 AWS Site-to-Site VPN이 이 모양이다. 연결 하나에 서로 다른 AWS 엔드포인트로 가는 IPsec 터널 둘을 주고, 각 터널 안쪽에 `169.254.x.x/30` 주소를 붙여 BGP 세션을 하나씩 맺는다. 한쪽이 점검으로 내려가면 BGP가 경로를 거두고 다른 터널로 넘어간다. 터널 하나의 대역폭에는 상한이 있어서(AWS는 터널당 최대 1.25Gbps로 안내한다), 더 필요하면 Transit Gateway에서 VPN 연결 여러 개를 ECMP로 묶는다. GRE 자체는 AWS의 관리형 VPN에서는 쓰지 않지만, Transit Gateway Connect가 SD-WAN 장비와 GRE 터널 위에서 BGP를 맺는 방식으로 다시 등장한다. BGP가 경로를 고르는 원리는 [BGP 글](/posts/bgp-basics)에 있다.

## 현장에서 VPN을 들여다보는 순서

VPN 장애는 "터널이 안 맺어진다"와 "맺어졌는데 트래픽이 안 흐른다"로 먼저 나눈다. 앞쪽은 협상 문제, 뒤쪽은 라우팅과 방화벽 문제다.

터널이 안 맺어진다. 바깥 패킷이 오가는지부터 본다. 핸드셰이크 패킷이 나가기만 하고 돌아오지 않으면 중간 방화벽이나 상대 설정이다.

```bash
# IPsec: IKE(500, 4500)와 날것의 ESP가 오가는지
sudo tcpdump -n -i eth0 'udp port 500 or udp port 4500 or esp'
# WireGuard: 핸드셰이크(148바이트)가 나가고 92바이트 응답이 오는지
sudo tcpdump -n -i eth0 udp port 51820
# strongSwan 로그 (Ubuntu는 charon-systemd를 쓰면 journal로 간다)
sudo journalctl -u strongswan -f
```

IPsec이면 로그의 notify 이름으로 좁힌다. `NO_PROPOSAL_CHOSEN`은 암호 조합, `AUTHENTICATION_FAILED`는 키나 ID, `TS_UNACCEPTABLE`은 트래픽 셀렉터다. WireGuard는 실패해도 아무 메시지를 보내지 않으니 `wg show`의 `latest handshake`가 갱신되는지만 볼 수 있다. 공개 키를 반대로 넣었거나(내 공개 키를 내 피어 항목에), 엔드포인트 포트가 다르면 핸드셰이크가 영영 안 된다.

터널은 맺어졌는데 안 흐른다. 카운터로 방향을 가른다. `swanctl --list-sas`의 `in`/`out`, `wg show`의 `transfer`가 한쪽만 늘면 반대 방향이 문제다. 그다음 경로를 본다.

```bash
# 이 목적지가 정말 터널 인터페이스로 가는지
ip route get 192.168.60.20
# WireGuard 피어별 AllowedIPs만 모아 본다
sudo wg show wg0 allowed-ips
# 반대편 사내 라우터에 VPN 대역(10.8.0.0/24)으로 돌아올 경로가 있는지 확인한다
```

작은 요청은 되는데 큰 응답이나 업로드만 멈춘다. 터널 오버헤드 때문에 MTU를 넘는 것이다. WireGuard는 기본 1420, IPsec은 조합에 따라 50~70바이트를 깎는다. 터널 인터페이스의 MTU를 낮추거나 게이트웨이에서 MSS를 클램핑한다. 방법은 [MTU 글](/posts/layer-mtu-fragmentation)에 있다.

몇 시간에 한 번씩 몇 초간 끊긴다. 키를 갱신(rekey)할 때 양쪽 수명 설정이 크게 다르거나, 양쪽이 동시에 갱신을 시작해 충돌하는 경우다. IPsec 로그에서 끊긴 시각의 `rekeying` 줄을 찾는다.

## 결국 감싸고, 열쇠를 나누고, 무엇을 넣을지 정한다

VPN은 원래 패킷을 암호화해 새 패킷 안에 넣는 터널이다. IPsec은 IKE로 열쇠와 조건을 협상하고 ESP로 데이터를 나르며, 협상할 게 많은 만큼 양쪽 설정이 어긋나는 장애가 많다. WireGuard는 암호를 고정하고 공개 키로 신원을 정해 협상을 없앴고, AllowedIPs 한 줄로 라우팅과 출발지 검사를 함께 한다. 어느 쪽이든 장애를 볼 때는 "터널이 맺어졌나", "어떤 트래픽을 넣기로 했나", "돌아오는 길이 있나" 세 가지를 차례로 확인하면 된다.

## 면접에서 나올 만한 질문

### VPN은 어떤 원리로 동작하나요?

원래 패킷을 암호화하고 무결성 검사값을 붙여 새 IP·UDP 패킷 안에 넣어 보내고, 반대편 게이트웨이가 꺼내 원래 목적지로 라우팅하는 터널이다. 인터넷 구간에서는 바깥 헤더의 게이트웨이 주소만 보인다. 사이트 간 VPN은 망과 망을, 원격 접속 VPN은 기기 하나를 망에 잇는다.

### IPsec에서 IKE와 ESP는 각각 무슨 일을 하나요?

IKE는 상대를 인증하고 암호 조합과 트래픽 셀렉터를 합의해 키를 만드는 제어용 프로토콜로, UDP 500과 NAT가 있으면 4500을 쓴다. ESP는 그 키로 실제 데이터를 암호화해 나르는 IP 프로토콜 50번이다. IKEv2는 IKE_SA_INIT과 IKE_AUTH 두 번의 왕복으로 IKE SA와 첫 CHILD SA를 함께 만들고, 받는 쪽은 ESP 패킷의 SPI로 어느 SA인지 찾는다.

### IPsec 터널이 ESTABLISHED인데 트래픽이 안 흐릅니다. 무엇을 보나요?

IKE SA만 맺어지고 CHILD SA가 안 생겼을 수 있으니 로그에서 TS_UNACCEPTABLE을 찾고, 양쪽 트래픽 셀렉터가 거울처럼 맞는지 본다. CHILD SA가 있다면 in/out 카운터로 어느 방향이 끊겼는지 가르고, 반대편 사내망에 터널 쪽으로 돌아오는 경로가 있는지, 방화벽이 ESP나 UDP 4500을 막는지 확인한다.

### NAT-T는 왜 필요한가요?

ESP에는 포트 번호가 없어서 포트로 연결을 구분하는 NAT가 ESP 패킷을 어느 내부 기기로 보낼지 모르기 때문이다. IKE가 첫 메시지의 NATD 해시로 NAT를 감지하면 ESP를 UDP 4500 안에 넣어 보내고, NAT 기록이 사라지지 않게 주기적으로 keepalive를 보낸다.

### WireGuard가 IPsec보다 단순하다는 건 구체적으로 무엇인가요?

암호 방식이 고정이라 협상 단계가 없고, 신원은 서로의 공개 키로 정해서 인증서나 계정 설정이 필요 없다. 핸드셰이크는 한 번 왕복이고 UDP 포트 하나만 쓴다. 대신 암호를 바꾸려면 프로토콜 버전을 올려야 하고, 사용자 계정 연동이나 접속 기록 같은 관리 기능은 기본으로 없어 따로 갖춰야 한다.

### WireGuard의 AllowedIPs는 어떤 역할을 하나요?

나갈 때는 목적지 주소를 최장 일치로 비교해 어느 피어로 암호화해 보낼지 정하는 라우팅 표 역할을 하고, 들어올 때는 복호화한 패킷의 출발지가 그 피어의 AllowedIPs에 있는지 확인하는 필터 역할을 한다. 그래서 피어 하나가 다른 주소를 사칭해 패킷을 넣을 수 없다. 0.0.0.0/0을 넣으면 모든 트래픽을 보내는 전체 터널이 된다.

### 전체 터널과 스플릿 터널은 어떻게 고르나요?

믿을 수 없는 망에서 모든 트래픽을 보호하고 회사가 인터넷 트래픽까지 검사해야 하면 전체 터널, 성능과 게이트웨이 부하가 중요하면 스플릿 터널을 고른다. 어느 쪽이든 DNS를 함께 설계해야 한다. 스플릿 터널에서는 사내 도메인을 사내 DNS로 보내야 하고, 전체 터널에서는 DNS 질의가 터널 밖으로 새지 않게 해야 한다.

### VPN을 켜면 큰 파일 업로드만 멈춥니다. 원인은요?

터널 헤더만큼 실을 수 있는 크기가 줄었는데 그보다 큰 패킷이 경로 어딘가에서 버려지는 MTU 문제다. 특히 ICMP Fragmentation Needed가 막혀 있으면 경로 MTU 탐색이 실패해 큰 패킷만 사라진다. 터널 인터페이스의 MTU를 오버헤드만큼 낮추거나(WireGuard 기본 1420) 게이트웨이에서 TCP MSS를 클램핑해서 고친다.
