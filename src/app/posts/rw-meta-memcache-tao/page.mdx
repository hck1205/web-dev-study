## 페이지 하나에 521개를 꺼낸다

Meta 엔지니어링 블로그의 [Scaling memcache at Facebook](https://engineering.fb.com/2013/04/15/core-infra/scaling-memcache-at-facebook/)(2013년 4월)에 따르면 Facebook은 2005년 8월에 memcached를 처음 썼다. 페이지를 열 때마다 DB 질의가 커지면서 로딩 시간이 눈에 띄게 늘던 때였다. 같은 글은 소셜 그래프가 "1조 개가 넘는 객체와 연결"로 촘촘히 엮여 있어 나누기 어렵고, 어떤 객체는 평균보다 몇 자릿수 더 인기가 많아 서버 쪽에 요청이 몰린다고 적었다.

같은 달 NSDI에 실린 논문 [Scaling Memcache at Facebook](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)이 숫자를 준다. 시스템은 초당 수십억 건 요청을 처리하고 수조 개 항목을 담는다. 인기 페이지 하나를 그리는 데 memcache에서 평균 521개의 서로 다른 항목을 꺼내고, 95번째 백분위로는 1,740개다. 페이지 하나에 DB 질의 수백 개를 날리는 기능은 너무 느리고 비싸서 시제품 단계를 못 벗어났을 거라고 논문은 썼다.

기본 구조는 단순한 look-aside 캐시다. 웹 서버가 키로 memcache에 묻고, 없으면 DB에서 읽어 채운다. 쓸 때는 DB에 SQL을 보낸 뒤 memcache에서 그 키를 지운다. 고치지 않고 지우는 이유를 논문은 한 줄로 적었다. 삭제는 멱등이라서다. 같은 삭제가 두 번 가도 결과가 같다. 이것이 [캐싱 전략 글](/posts/caching-strategies)의 cache-aside와 같은 구조다.

논문은 설계 목표 두 가지도 밝혔다. 하나는 사용자나 운영에 닿는 문제를 고치는 변경만 한다는 것이다. 다른 하나가 이 글 전체를 관통한다. 잠깐 낡은 데이터를 읽을 확률을 응답 속도처럼 "조절할 값"으로 다룬다. 백엔드 저장소를 과부하에서 지킬 수 있다면 조금 낡은 데이터를 보여 주는 것을 감수하겠다고 했다.

## 클러스터 안: 모두가 모두에게 묻는다

클러스터 하나에는 memcached 서버가 수백 대 있고, 항목은 [일관된 해싱](/posts/consistent-hashing)으로 서버에 흩어진다. 그래서 웹 서버 한 대가 요청 하나를 처리하려면 많은 memcached 서버와 이야기해야 하고, 짧은 시간 안에 모든 웹 서버가 모든 memcached 서버에 닿는다. 논문은 이 모두-대-모두 통신이 인캐스트 혼잡(응답이 한꺼번에 몰려 스위치 버퍼가 넘치는 현상)을 만들거나 서버 한 대를 여러 웹 서버의 병목으로 만든다고 적었다.

지연은 주로 클라이언트 쪽에서 줄였다. memcached 서버끼리는 서로 통신하지 않고, 복잡한 일은 상태 없는 클라이언트에 넣었다. 클라이언트는 앱에 넣는 라이브러리이거나, memcached와 같은 인터페이스를 흉내 내는 독립 프록시 mcrouter다.

- 데이터 의존성을 DAG로 그려 한 번에 꺼낼 수 있는 키를 묶는다. 묶음 하나는 평균 24개 키다.
- 읽기(get)는 UDP로 바로 보낸다. 연결을 맺지 않아 웹 서버의 스레드마다 memcached에 직접 말할 수 있다. 피크 때 get의 0.25%가 버려지는데, 그중 80% 정도가 늦거나 잃은 패킷이고 나머지는 순서가 바뀐 패킷이다. 클라이언트는 이걸 캐시 미스로 치되, DB에서 읽은 뒤 캐시에 다시 넣지는 않는다. 이미 과부하일 수 있는 네트워크와 서버에 일을 더 얹지 않으려는 것이다.
- 쓰기(set, delete)는 같은 기계에서 도는 mcrouter를 거쳐 TCP로 보낸다. 상태 변경은 확인이 필요하니 UDP에 재시도를 따로 짜는 대신 TCP에 맡겼다. 웹 스레드마다 TCP 연결을 열면 메모리가 너무 들어서 mcrouter가 연결을 모아 준다.

논문 그림 3은 UDP로 읽을 때가 mcrouter를 거친 TCP보다 지연이 약 20% 낮다고 보여 준다. 인캐스트는 TCP 혼잡 제어처럼 성공하면 천천히 늘고 응답이 없으면 줄어드는 슬라이딩 윈도로 막았다. 창이 작으면 요청을 여러 번에 나눠 보내 느려지고, 크면 인캐스트로 오류가 나 DB로 떨어진다. 그 사이의 균형점을 찾는 문제다.

## 낡은 set과 몰려드는 무리를 리스 하나로

논문이 "리스(lease)"를 소개한 이유는 두 가지 문제였다. 하나는 낡은 set(stale set)이다. 동시에 일어난 갱신의 순서가 뒤바뀌어, 웹 서버가 최신이 아닌 값을 캐시에 넣는 경우다. 다른 하나는 썬더링 허드(thundering herd)다. 특정 키에 읽기와 쓰기가 몰릴 때, 쓰기가 방금 넣은 값을 계속 지우니 많은 읽기가 비싼 DB 경로로 떨어진다.

리스는 둘을 함께 푼다. 클라이언트가 캐시 미스를 겪으면 memcached가 그 키에 묶인 64비트 토큰을 준다. 클라이언트는 값을 채울 때 이 토큰을 함께 내고, memcached는 토큰을 보고 저장할지 정한다. 그사이 그 키에 삭제가 오면 토큰이 무효가 되어, 삭제 전에 읽은 낡은 값은 들어가지 못한다. 논문은 load-link/store-conditional과 비슷한 방식이라고 했다.

썬더링 허드는 토큰을 주는 속도로 막는다. 기본 설정은 키마다 10초에 한 번만 토큰을 준다. 토큰을 준 뒤 10초 안에 같은 키를 묻는 요청은 "잠깐 기다렸다 다시 물어보라"는 특별한 응답을 받는다. 토큰을 받은 클라이언트는 보통 몇 ms 안에 값을 채우니, 기다린 클라이언트가 다시 물을 때는 캐시에 값이 있는 경우가 많다. 아래 그림은 두 웹 서버가 같은 키를 거의 동시에 놓친 상황이다.

논문의 표현으로는, DB를 피크 부하 기준으로 증설하니 피크를 1만 7천에서 1,300으로 줄인 것이 "상당한 효율 향상"으로 이어진다. 기다리는 시간도 더 줄였다. 지운 값을 곧바로 버리지 않고 최근 삭제 항목을 담는 자료 구조에 잠깐 두었다가, get에 "낡았다고 표시한 값"을 돌려줄 수 있게 했다. 낡은 값으로도 일을 계속할 수 있는 앱은 DB에서 최신 값을 기다리지 않는다. 논문은 캐시 값이 대개 DB의 단조 증가 스냅숏이라 대부분의 앱이 코드를 고치지 않고도 낡은 값을 쓸 수 있었다고 적었다.

Redis로 같은 동작을 재현하는 방법은 [캐시 무효화 글](/posts/cache-invalidation)에 있다. 그 글의 토큰은 `SET NX`로 흉내 낸 것이고, Facebook은 이 기능을 memcached 서버 안에 직접 넣었다.

## 키를 나누지 않고 복제한 이유

memcache를 범용 캐시로 쓰면 접근 패턴, 메모리 크기, 서비스 품질 요구가 서로 다른 일들이 한 인프라를 나눠 쓴다. 논문은 이것이 서로 적중률을 깎아 먹는다고 보고, 클러스터의 memcached 서버를 여러 풀(pool)로 나눴다. 기본 풀 이름은 wildcard이고, 자주 읽히지만 미스 비용이 싼 키를 위한 작은 풀, 드물게 읽히지만 미스 비용이 아주 큰 키를 위한 큰 풀을 따로 둔다. 값어치 있는 저회전 키가 더는 안 읽히는 고회전 키보다 먼저 쫓겨나는 일을 막으려는 것이다.

일부 풀 안에서는 키를 더 잘게 나누는 대신 복제했다. 조건은 셋이다. 앱이 키를 여러 개 한꺼번에 꺼내고, 데이터 전체가 memcached 서버 한두 대에 들어가고, 요청률이 서버 한 대가 감당할 수준을 훨씬 넘을 때다. 논문의 예가 직관적이다. 항목 100개를 들고 초당 50만 요청을 받을 수 있는 서버가 있고, 요청마다 키 100개를 묻는다. 초당 100만 요청으로 늘리려고 서버를 한 대 더 두고 키를 반씩 나누면, 클라이언트는 요청을 50개씩 둘로 쪼개 보내야 하니 두 서버 모두 여전히 초당 100만 요청을 받는다. 키 100개를 두 서버에 모두 복제하면 요청 하나는 아무 복제본에나 가면 되니 서버당 50만이 된다.

직접 계산해 보자. 키가 고르게 흩어져 있고 요청 하나가 키를 여러 개 묻는다고 할 때, 서버 한 대가 받는 초당 요청 수를 돌려주는 함수다.

## 서버가 죽으면 Gutter로

memcache에서 못 읽으면 그 부하가 백엔드로 넘어가 연쇄 장애가 날 수 있다. 클러스터 전체를 내려야 할 만큼 큰 장애는 사용자 요청을 다른 클러스터로 돌린다. 문제는 서버 몇 대가 죽는 작은 장애다. 자동 복구 시스템이 처리하지만 몇 분까지 걸리고, 그 몇 분이면 연쇄 장애가 나기에 충분하다.

그래서 Gutter라는 작은 서버 묶음을 따로 둔다. 클러스터 memcached 서버의 약 1%다. 클라이언트는 get에 응답이 없으면 그 서버가 죽었다고 보고 Gutter 풀에 다시 묻는다. 거기서도 미스면 DB에서 읽어 Gutter에 넣는다. Gutter 항목은 빨리 만료돼서 무효화를 따로 보내지 않아도 된다. 대가는 조금 낡은 데이터다.

죽은 서버의 키를 남은 서버들에 다시 해싱하지 않은 이유도 적혀 있다. 키마다 접근 빈도가 고르지 않아서, 키 하나가 서버 요청의 20%를 차지할 수도 있다. 그 뜨거운 키를 넘겨받은 서버가 다시 과부하에 걸리면 연쇄 장애가 된다. 놀고 있는 Gutter로 보내면 그 위험이 줄어든다. 논문은 Gutter가 클라이언트에 보이는 실패율을 99% 줄이고, 매일 실패의 10~25%를 히트로 바꾼다고 했다. memcached 서버 한 대가 완전히 죽으면 Gutter 풀의 적중률은 보통 4분 안에 35%를 넘고 50%에 가까워진다.

## 리전 안: 삭제는 DB가 커밋 로그로 보낸다

클러스터를 계속 키우면 문제가 사라지지 않는다. 웹 서버가 늘수록 인기 항목은 더 인기가 많아지고, memcached 서버가 늘수록 인캐스트는 나빠진다. 그래서 웹 서버와 memcached 서버를 여러 프런트엔드 클러스터로 나누고, 이 클러스터들과 DB가 있는 저장소 클러스터 하나를 묶어 리전(region)이라고 불렀다. 데이터 복제를 감수하고 더 작은 장애 영역과 다루기 쉬운 네트워크를 얻은 것이다.

그러면 같은 데이터가 여러 프런트엔드 클러스터 캐시에 복제된다. 무효화를 누가 보내느냐가 문제가 된다. Facebook은 데이터를 바꾸는 SQL 문에 커밋 뒤 무효화할 memcache 키를 함께 적고, DB마다 mcsqueal이라는 데몬을 둬서 커밋된 SQL에서 삭제를 뽑아 리전의 모든 프런트엔드 클러스터에 뿌렸다. 데이터를 고친 웹 서버도 자기 클러스터에는 직접 삭제를 보낸다. 같은 요청 안에서 쓴 값을 바로 읽게 하고 낡은 데이터가 머무는 시간을 줄이려는 것이다. 논문은 실제로 캐시 데이터를 지우는 삭제가 전체 삭제의 4%뿐이라고 적었다.

mcsqueal이 memcached 서버에 바로 보내면 클러스터 경계를 넘는 패킷이 너무 많아진다. 그래서 삭제를 묶어 각 프런트엔드 클러스터의 mcrouter 서버들에 보내고, mcrouter가 풀어서 맞는 memcached로 보낸다. 묶음으로 패킷당 삭제 수 중앙값이 18배 좋아졌다.

웹 서버가 모든 클러스터에 직접 무효화를 뿌리는 방법을 버린 이유도 둘이다. 웹 서버는 mcsqueal만큼 잘 묶지 못하고, 설정 실수로 삭제가 엉뚱한 곳에 가는 식의 시스템 문제가 생기면 되돌릴 방법이 없다. 예전에는 그럴 때마다 memcache 전체를 차례로 재시작해야 했다. SQL 문에 담아 DB 로그에 남긴 무효화는 잃거나 잘못 보낸 것을 다시 재생하면 된다. 일반적인 변경 데이터 캡처 방식은 [CDC 글](/posts/cdc-change-data-capture)에 있다.

메모리를 아끼는 장치도 있다. 크고 드물게 읽히는 항목은 모든 클러스터에 복제할 필요가 없어서, 여러 프런트엔드 클러스터가 memcached 서버 한 벌을 나눠 쓰는 리전 풀(regional pool)에 둔다. 대신 클러스터 경계를 넘으면 지연이 늘고, 논문 기준 경계를 넘는 평균 가용 대역폭은 클러스터 안보다 40% 적다. 논문 표 1의 예로, 클러스터마다 복제한 A 항목군은 사용자 수 중앙값 30, 초당 get 326만, 값 크기 중앙값 10.7kB였고, 리전 풀로 옮긴 B 항목군은 각각 1, 45만 8천, 4.34kB였다. B는 접근이 한 자릿수 적어 클러스터 사이 대역폭을 해치지 않고, 그대로 두면 각 클러스터 wildcard 풀의 25%를 차지했을 것이다.

새 클러스터를 띄우거나 점검하면 캐시가 비어 DB를 지키지 못한다. Cold Cluster Warmup은 빈 클러스터의 클라이언트가 DB 대신 정상 클러스터의 캐시에서 읽게 해서, 며칠 걸리던 복구를 몇 시간으로 줄였다. 경쟁 조건이 있다. 빈 클러스터에서 DB를 고쳤는데, 무효화가 정상 클러스터에 닿기 전에 다른 클라이언트가 정상 클러스터에서 옛 값을 가져와 넣으면 그 값이 계속 남는다. 그래서 빈 클러스터에 보내는 삭제에는 2초의 보류 시간을 줘서 그동안의 add를 거절하게 했다. 삭제가 2초 넘게 늦으면 여전히 틀릴 수 있지만, 논문은 운영상의 이득이 드문 불일치 비용보다 훨씬 크다고 판단했다.

## 리전을 넘으면: 복제 지연과 원격 마커

웹 서버를 사용자 가까이 두고, 자연재해나 대규모 정전에 대비하려고 리전을 여러 개로 늘렸다. 한 리전에 마스터 DB를 두고 나머지 리전은 읽기 전용 복제본을 MySQL 복제로 따라가게 했다. 이때 어려움은 하나로 모인다. 복제본 DB가 마스터보다 늦을 수 있다.

마스터 리전에서 쓴 경우는 mcsqueal 덕분에 안전하다. 복제본 리전의 삭제가 그 리전의 DB 복제 스트림에서 나오니, 데이터가 복제되기 전에 무효화가 먼저 닿는 경쟁이 생기지 않는다. 논문은 이 이유 때문에 mcsqueal을 여러 리전으로 늘린 뒤에 만들었다고 적었다.

까다로운 건 마스터가 아닌 리전에서 쓴 경우다. 복제 지연이 클 때 사용자가 방금 고친 내용이 다음 요청에서 사라져 보이면 혼란스럽다. 그래서 원격 마커(remote marker)를 쓴다. 아래 그림에서 순서대로 볼 수 있다.

무효화가 얼마나 제때 닿는지는 직접 쟀다. 삭제 100만 건 중 1건을 골라 언제 보냈는지 적고, 주기적으로 모든 프런트엔드 클러스터의 캐시를 조회해 지워졌어야 할 항목이 남아 있으면 오류로 기록했다. 30일 측정에서 마스터 리전 안의 삭제는 1초 안에 네 개의 9(99.99%), 1시간 뒤 다섯 개의 9에 닿았다. 복제본 리전에서 다른 복제본 리전으로 가는 삭제는 1초 안에 세 개의 9, 10분 안에 네 개의 9였다. 몇 초 뒤에도 무효화가 안 됐다면 대개 첫 시도가 실패한 것이고 재시도가 해결한다고 했다. 이 측정 방식은 그대로 가져다 쓸 만하다. 아래 "내 서비스라면" 부분에서 다시 다룬다.

## 서버 한 대도 다시 짰다

모두-대-모두 통신에서는 서버 한 대가 클러스터 전체의 병목이 된다. 그래서 memcached 자체도 고쳤다. 처음엔 고정 크기 해시 테이블을 쓰는 단일 스레드였는데, 해시 테이블 자동 확장과 전역 잠금을 쓴 다중 스레드화를 오픈소스에 돌려줬다. 그 뒤 잠금을 잘게 나누자 히트 처리량이 초당 60만에서 180만 항목으로 세 배가 됐고, 미스는 270만에서 450만이 됐다. 같은 실험에서 UDP는 TCP보다 단일 get에서 13%, 10키 다중 get에서 8% 빨랐다.

만료가 짧은 키를 위한 Transient Item Cache도 붙였다. memcached는 만료된 항목을 읽힐 때나 LRU 끝에 닿을 때에야 지우는데, 잠깐 쓰이고 끝나는 키가 그동안 메모리를 차지한다. 만료까지 남은 초로 색인한 원형 버퍼에 넣고 매초 맨 앞 칸을 비우게 하자, 그런 키 묶음이 풀에서 차지하던 비율이 적중률 변화 없이 6%에서 0.3%로 줄었다.

소프트웨어 업그레이드도 문제였다. memcached 서버 한 대가 최고 적중률의 90%에 닿는 데 몇 시간이 걸려서, DB 부하를 조심스럽게 관리하며 서버 묶음을 업그레이드하는 데 12시간이 넘게 걸렸다. 캐시 값과 주요 자료 구조를 System V 공유 메모리에 두어 업그레이드 중에도 살아 있게 고쳤다.

## look-aside의 한계와 TAO

memcache를 늘리는 동안 다른 문제가 쌓였다. Meta 엔지니어링 블로그의 [TAO: The power of the graph](https://engineering.fb.com/2013/06/25/core-infra/tao-the-power-of-the-graph/)(2013년 6월)는 이렇게 설명한다. memcache와 MySQL 조합을 제대로 쓰려면 제품 엔지니어가 시스템 내부를 꽤 알아야 했고, 실수가 버그와 사용자에게 보이는 불일치, 성능 문제로 이어졌다. 2007년에 몇몇 엔지니어가 그래프 모델을 바탕으로 한 Objects and Associations API를 PHP로 만들었고, 좋아요, 페이지, 이벤트 같은 기능이 memcache나 MySQL을 직접 부르지 않고 이 API만으로 만들어졌다.

그런데 클라이언트 쪽 구현에는 한계가 있었다. 같은 해 USENIX ATC에 실린 [TAO: Facebook's Distributed Data Store for the Social Graph](https://www.usenix.org/system/files/conference/atc13/atc13-bronson.pdf)는 look-aside 캐시의 근본 문제 셋을 든다.

- 간선 목록에 키-값 캐시가 맞지 않는다. 목록 전체를 늘 가져와야 하고, 간선 하나만 바뀌어도 목록 전체를 다시 읽어야 한다.
- 제어 로직이 서로 대화하지 않는 클라이언트들에 흩어져 있다. 실패 유형이 늘고 썬더링 허드를 피하기 어렵다. 논문은 리스가 일반적인 해법이라고 인정하면서도, API가 고정돼 있으면 그 로직을 캐시 안으로 옮겨 더 효율적으로 풀 수 있다고 봤다.
- 쓴 것을 바로 읽게 하는 비용이 크다. MySQL을 비동기 마스터-슬레이브로 복제하니 복제본 리전 캐시에 문제가 생기고, 원격 마커는 리전을 넘는 통신을 요구한다.

블로그에 따르면 2009년 초에 인프라 엔지니어 팀이 TAO("The Associations and Objects")를 만들기 시작했다. 데이터 모델은 둘뿐이다. 객체는 64비트 id로 식별되는 타입 있는 노드이고, 연관(association)은 (id1, atype, id2)로 식별되는 타입 있는 방향 간선이다. 연관마다 32비트 time 필드가 있고, (id1, atype)의 연관 목록은 time 내림차순으로 정렬된다. "이 체크인에 달린 최근 댓글 50개"는 `assoc_range(632, COMMENT, 0, 50)` 하나로 끝난다. 데이터 대부분은 오래됐지만 질의는 최신 부분에 몰린다는 "생성 시각 지역성"을 API에 그대로 담은 것이다. 한 번에 돌려주는 개수에는 타입마다 상한(보통 6,000)이 있다.

논문은 뺀 것도 적었다. 객체 API에는 compare-and-set이 없다. 최종 일관성 아래서는 쓸모가 크게 줄기 때문이다. 친구 관계처럼 양방향인 간선은 연관 두 개로 저장하고 역방향을 자동으로 만들어 주지만, 두 갱신 사이에 원자성은 없다. 중간에 실패하면 정방향만 남고, 이런 "매달린 연관"은 비동기 작업이 고친다.

## 리더 티어, 팔로워 티어, 그리고 마스터 리전

TAO는 MySQL을 그대로 영구 저장소로 쓰되 접근을 가로막고 자기 그래프 캐시를 둔다. 데이터는 논리 샤드로 나누고, 객체 id에 샤드 id가 들어 있어 객체는 평생 한 샤드에 묶인다. 연관은 id1의 샤드에 저장되니 연관 질의 하나가 서버 한 대에서 끝난다. 샤드는 일관된 해싱으로 캐시 서버에 배치된다.

캐시는 두 층이다. 클라이언트는 가장 가까운 팔로워 티어에만 말하고, 팔로워는 미스와 쓰기를 리더 티어로 넘기며, 리더만 DB를 읽고 쓴다. 샤드마다 리더는 하나라 쓰기가 자연스럽게 한 줄로 서고, 리더는 DB에 겹치는 질의를 동시에 보내지 않아 썬더링 허드를 막는다. 논문은 티어 하나를 키우면 핫스폿이 늘고 모두-대-모두 연결이 제곱으로 늘어서 두 층으로 나눴다고 설명했다.

리전을 넘을 때 TAO는 팔로워의 읽기 미스가 쓰기보다 25배 잦다는 측정을 근거로 마스터-슬레이브 구조를 골랐다. 쓰기는 마스터 리전으로 보내고 읽기 미스는 로컬에서 처리한다. 마스터 리전은 샤드마다 따로 정하고, DB가 죽으면 자동으로 바뀐다. 아래 그림은 논문 그림 2의 흐름이다.

무효화와 refill 메시지는 DB 복제 스트림에 실어 보낸다. 트랜잭션이 슬레이브 DB에 복제된 직후에 그 리전에 닿게 하려는 것이다. 더 일찍 보내면 로컬 DB를 읽은 캐시가 낡은 값을 다시 담는다. 논문은 TAO와 memcache가 같은 전달 파이프라인을 쓴다고 적었다. 앞에서 본 mcsqueal의 생각이 그대로 이어진 것이다.

간선을 지우면 캐시해 둔 목록 앞부분이 잘려 나가니, 리더는 연관을 쓸 때 무효화 대신 refill 메시지를 보내 팔로워가 리더에게 목록을 다시 묻게 한다. 쓴 팔로워 자신은 리더가 돌려준 변경 내용(changeset)으로 바로 갱신되고, 캐시와 DB에 있는 버전 번호로 나중에 도착한 메시지를 무시할지 판단한다. 그래서 장애가 하나 이하일 때는 한 티어 안에서 내가 쓴 것을 바로 읽을 수 있다. 강한 일관성이 꼭 필요한 소수의 읽기는 "critical"로 표시해 마스터 리전으로 보낸다. 논문은 인증 과정에서 복제 지연 때문에 낡은 자격 증명이 쓰이지 않게 하는 경우를 예로 들었다.

## TAO의 숫자

논문이 40일 동안 무작위로 뽑은 요청 650만 건을 분석한 결과는 이렇다. 쓰기는 전체 요청의 0.2%였다. 연관 읽기는 대부분 빈 결과였다. `assoc_get`은 19.6%만 연관을 찾았고, `assoc_range`는 31.0%, `assoc_time_range`는 1.9%만 결과가 있었다. `assoc_count`는 45%가 0을 돌려줬다. "이 사용자가 이 글을 좋아했나"의 답이 대부분 "아니다"라는 뜻이다. 블로그도 같은 이유로 MySQL의 블록 캐시가 이 작업 부하에 맞지 않는다고 설명했다. 없다는 답을 하려고 몇 KB 블록을 끌어오면 캐시만 더럽힌다.

읽기 전체 적중률은 96.4%였다. 90일 동안 웹 서버에서 잰 TAO 질의 실패 비율은 4.9 × 10⁻⁶이다. 쓰기는 마스터 DB에 동기로 하니, 평균 왕복 58.1ms 떨어진 두 데이터센터에서 잰 평균 쓰기 지연은 마스터 리전 안에서 12.1ms, 먼 리전에서 74.4ms(58.1 + 16.3)였다. 슬레이브 DB의 복제 지연은 측정 기간의 85%에서 1초 미만, 99%에서 3초 미만, 99.8%에서 10초 미만이었다. 리더가 없어서 팔로워가 DB에 직접 간 경우는 팔로워 미스의 0.15%였다.

당시 TAO는 Facebook 전체에 하나뿐인 인스턴스였다. 리전마다 DB 한 벌, 리더 티어 하나, 팔로워 티어 최소 둘이 있었고, 초당 읽기 10억 건과 쓰기 수백만 건을 처리했다. 리전 안의 지연이 보통 1ms 미만이 되게 데이터센터를 몇 개 리전으로 묶고, 리전마다 소셜 그래프 전체 사본을 한 벌만 둔 것도 비용 때문이다. 그래프가 촘촘해서 사용자를 묶어 나눌 수 없으니 팔로워 근처에 전체 사본이 있어야 하고, 데이터센터마다 두기엔 너무 비쌌다고 논문은 적었다.

## 그 뒤에 공개된 것

mcrouter는 2014년 9월 15일에 오픈소스로 공개됐다. 지금의 [facebook/mcrouter 저장소 README](https://raw.githubusercontent.com/facebook/mcrouter/main/README.md)는 mcrouter를 Facebook과 Instagram 캐시 인프라의 핵심 부품으로 소개하고, 피크 때 초당 거의 50억 건을 처리한다고 적었다. 저장소 위키는 연결 풀링, 복제 풀, 콜드 캐시 워밍업, 신뢰할 수 있는 삭제 스트림 같은 기능을 나열하는데, 2013년 논문에 나온 장치들이 프록시 기능으로 정리된 모습이다.

TAO 블로그 글에는 나중에 붙은 문장이 하나 있다. 언어를 더 포용적으로 바꾸려고 "master"와 "slave"를 "primary"와 "secondary"로 고쳤다는 안내다. 이 글에서는 논문 원문을 따라 마스터와 슬레이브를 썼다. 2013년 이후 TAO와 memcache 구조가 어떻게 바뀌었는지는 이 글이 참고한 자료에 자세히 나오지 않으니, 위의 숫자와 구조는 2013년 시점의 것으로 읽어야 한다.

## 논문이 보여 주지 않는 쪽

두 논문 모두 Facebook이 고른 성공 사례다. memcache 논문은 리스와 Gutter의 효과를 숫자로 보여 주지만, 그 장치를 만들기 전에 어떤 장애가 있었는지, 장애가 얼마나 길었는지는 거의 쓰지 않았다. 리전 풀로 옮길지 여부는 "접근률, 데이터 크기, 사용자 수에 기반한 수동 휴리스틱"으로 정한다고만 했다. TAO 논문은 TAO로 옮기지 않은 데이터 종류가 얼마나 남았는지, 옮기는 데 얼마나 걸렸는지를 말하지 않는다. 실패율 4.9 × 10⁻⁶도 논문 스스로 해석에 조심하라고 붙였다. 질의 하나가 실패하면 그 결과에 의존하는 다음 질의는 아예 보내지 않으니 실패가 적게 세어질 수 있고, 다른 시스템의 장애와 함께 일어나기도 한다.

## 수천 대가 아니어도 쓸 수 있는 것

Facebook이 이 장치들을 만든 조건을 다시 보면, 읽기가 쓰기보다 한 자릿수 이상 많고, 페이지 하나가 키 수백 개를 꺼내며, 같은 데이터가 여러 클러스터와 리전에 복제되고, 그 규모가 수천 대였다. 이 조건이 아니라면 대부분은 필요 없다. 캐시 서버 몇 대짜리 서비스에 Gutter 풀이나 리전 풀, 별도 무효화 파이프라인을 처음부터 만들면 운영할 부품만 늘어난다. TAO처럼 캐시가 쓰기까지 맡는 그래프 저장소를 직접 만드는 건 더 말할 필요가 없다.

규모와 상관없이 지금 가져올 수 있는 건 세 가지다. 첫째, 쓸 때는 캐시를 고치지 말고 지운다. 삭제는 멱등이라 재시도와 재생이 안전하다. 둘째, 인기 키의 미스에는 채울 권리를 하나만 준다. Redis라면 `SET NX`로 짧은 락을 잡고 나머지는 잠깐 기다리게 하면 된다. 방법은 [캐시 무효화 글](/posts/cache-invalidation)에 있다. 셋째, 무효화가 실제로 닿았는지 표본으로 잰다. Facebook처럼 삭제 일부를 골라 몇 초 뒤 캐시에 아직 남았는지 조회해 지표로 남기면, "고쳤는데 안 바뀐다"는 문의가 오기 전에 문제를 안다.

DB의 복제본을 읽는 구조라면 원격 마커의 생각도 쓸모 있다. 방금 쓴 사용자의 다음 요청 몇 초 동안은 복제본 대신 주 DB에서 읽게 하는 것이다. 세션이나 쿠키에 마지막 쓰기 시각을 남기는 식으로 더 가볍게 구현할 수도 있다. 일반적인 방법은 [DB 복제 글](/posts/sd-db-replication-intro)에서 다룬다.

비슷한 증상을 만나면 볼 곳도 이 사례에서 나온다. 캐시를 지운 직후 DB 부하가 튄다면 같은 키에 미스가 몇 번 겹쳤는지부터 센다. 캐시 서버 한 대가 죽었을 때 나머지가 줄줄이 느려진다면 재해싱이 뜨거운 키를 옆 서버로 옮긴 건 아닌지 본다. 페이지 응답이 키를 많이 묻는 요청에서만 느리다면 서버당 요청 수를 보고, 키를 더 나누는 대신 복제가 맞는 경우인지 위의 계산으로 확인한다.

## 면접에서 나올 만한 질문

### Facebook은 캐시 값을 쓸 때 왜 고치지 않고 지웠나요?

삭제는 멱등이라서다. 같은 삭제가 여러 번 가거나 재생돼도 결과가 같아서 재시도와 무효화 재전송이 안전하다. 값을 고치는 방식은 두 쓰기의 순서가 뒤바뀌면 낡은 값이 남는다. memcache는 원본이 아니라 쫓겨나도 되는 캐시이니, 지우고 다음 읽기가 DB에서 채우게 했다.

### 리스는 무엇을 막고 어떻게 동작하나요?

낡은 set과 썬더링 허드를 막는다. 캐시 미스가 나면 memcached가 그 키에 묶인 64비트 토큰을 주고, 채울 때 토큰을 함께 내야 저장된다. 그사이 삭제가 오면 토큰이 무효가 되어 삭제 전에 읽은 값은 못 들어간다. 토큰은 키마다 10초에 한 번만 줘서 나머지 요청은 잠깐 기다렸다 다시 묻는다. 논문 측정에서 DB 질의 피크가 초당 1만 7천에서 1,300으로 줄었다.

### memcached 서버가 죽었을 때 남은 서버로 재해싱하지 않은 이유는요?

키마다 인기가 고르지 않아서, 키 하나가 서버 요청의 20%를 차지하기도 하기 때문이다. 그 키를 넘겨받은 서버가 다시 과부하에 걸리면 연쇄 장애가 난다. 그래서 클러스터의 약 1%인 Gutter 풀로 보내고 그 항목은 빨리 만료시켰다. 클라이언트에 보이는 실패율이 99% 줄었다.

### 키를 더 잘게 나누는 대신 복제한 건 언제인가요?

요청 하나가 키를 많이 묻고, 데이터 전체가 서버 한두 대에 들어가며, 요청률이 한 대를 크게 넘을 때다. 이때 키를 나누면 요청이 서버마다 쪼개져 가서 서버당 요청 수가 줄지 않는다. 복제하면 요청 하나가 아무 복제본에나 가니 서버당 부하가 서버 수만큼 준다. 대신 무효화를 모든 복제본에 보내야 한다.

### 무효화를 웹 서버가 아니라 DB 쪽 데몬(mcsqueal)이 보낸 이유는요?

DB 커밋 로그에 남은 SQL에서 삭제를 뽑으면 잃거나 잘못 보낸 무효화를 다시 재생할 수 있기 때문이다. 웹 서버가 직접 뿌리면 묶음 효율이 떨어지고, 설정 실수로 삭제가 엉뚱한 곳에 가면 되돌릴 방법이 없어 memcache 전체를 재시작해야 했다. 여러 리전에서는 복제 스트림을 따라 무효화가 가니 데이터보다 무효화가 먼저 닿는 경쟁도 사라진다.

### 왜 memcache 위에 TAO를 따로 만들었나요?

look-aside 캐시가 그래프 데이터에 맞지 않았기 때문이다. 간선 목록은 하나만 바뀌어도 전체를 다시 읽어야 했고, 제어 로직이 서로 대화하지 않는 클라이언트에 흩어져 썬더링 허드와 일관성을 다루기 어려웠으며, 복제본 리전에서 쓴 것을 바로 읽게 하는 비용이 컸다. TAO는 객체와 연관이라는 고정된 API를 두고 캐시가 쓰기까지 맡아, 그 로직을 캐시 안으로 옮겼다.

### TAO에서 쓴 직후 다른 리전에서 읽으면 낡은 값이 보이나요?

보일 수 있다. TAO는 기본이 최종 일관성이고, 같은 팔로워 티어 안에서만 장애가 하나 이하일 때 내가 쓴 값을 바로 읽게 해 준다. 슬레이브 DB 복제 지연은 측정 기간의 99%에서 3초 미만이었다. 인증처럼 강한 일관성이 꼭 필요한 읽기는 critical로 표시해 마스터 리전으로 보낸다.

### 우리 서비스가 Facebook의 100분의 1 규모라면 무엇을 따라 하나요?

장치 자체보다 습관을 가져온다. 쓸 때는 캐시를 지우고, 인기 키의 미스에는 채울 권리를 하나만 주고, 무효화가 실제로 닿았는지 표본으로 잰다. Gutter 풀, 리전 풀, 별도 무효화 파이프라인, TAO 같은 그래프 캐시는 캐시 서버가 수천 대이고 리전 사이 복제가 있을 때 값어치가 생긴다. 그 전에 만들면 운영할 부품만 늘어난다.
