로그를 더 보고 싶어서 ConfigMap의 `LOG_LEVEL`을 `info`에서 `debug`로 바꿨다. `kubectl patch`는 `configmap/api-config patched`라고 답했다. 그런데 몇 분을 기다려도 로그는 그대로다. 같은 ConfigMap을 파일로 마운트한 다른 앱은 1분쯤 뒤에 바뀐 값을 읽었다. 또 다른 앱은 파일로 마운트했는데도 끝까지 옛 값이다.

세 앱의 차이는 ConfigMap을 Pod에 넣은 방법뿐이다. 환경 변수로 넣었는지, 볼륨으로 마운트했는지, 볼륨을 `subPath`로 꽂았는지. 이 글은 ConfigMap이 Pod 안으로 들어가는 길을 따라가면서 값이 언제 읽히고 언제 바뀌는지, 바뀐 설정을 확실히 반영하려면 무엇을 해야 하는지 본다. 크기 제한과 `immutable`처럼 운영에서 부딪히는 규칙도 함께 본다.

`kubectl` 출력은 [Namespace 글](/posts/k8s-namespace)처럼 kwok로 띄운 실습 클러스터(Kubernetes 1.30)에서 받았다. API 서버, 컨트롤러, 검증 규칙은 진짜다. 노드와 컨테이너는 흉내만 내기 때문에 컨테이너 안에서 본 파일 목록과 kubelet이 남기는 오류는 실제 형식대로 쓴 예시로 표시했다.

## 이미지 하나를 여러 환경에서 쓰려면

같은 이미지를 개발, 스테이징, 운영에 그대로 올리고 싶다. 이미지를 환경마다 따로 빌드하면 "스테이징에서 시험한 이미지"와 "운영에 올라간 이미지"가 달라진다. 그래서 바뀌는 값, 즉 DB 주소, 로그 수준, 기능 플래그, 외부 API 주소 같은 것을 이미지 밖으로 뺀다. 쿠버네티스에서 그 값을 담는 객체가 ConfigMap이다.

ConfigMap은 문자열 키와 값의 묶음일 뿐이다. 안에 무엇이 들었는지 쿠버네티스는 해석하지 않는다. `LOG_LEVEL: info` 같은 한 줄짜리 값일 수도 있고, `nginx.conf` 파일 전체가 값 하나일 수도 있다. 네임스페이스에 속하는 객체라서 Pod는 같은 네임스페이스의 ConfigMap만 읽는다.

비밀번호나 토큰은 ConfigMap에 넣지 않는다. ConfigMap은 `kubectl get -o yaml` 한 번에 평문으로 보이고, 읽기 권한도 보통 넓게 준다. 비밀 값은 [Secret](/posts/k8s-secret)에 둔다. Secret도 기본 상태로는 암호화되지 않는데, 그 이야기는 그 글에서 따로 본다.

## ConfigMap을 만드는 세 가지 방법

명령으로 만들 때는 값을 어디서 가져오느냐에 따라 옵션이 셋이다.

```bash
# 키와 값을 직접 적는다
kubectl create configmap api-config -n shop \
  --from-literal=LOG_LEVEL=info \
  --from-literal=DB_HOST=postgres.shop.svc.cluster.local

# 파일 하나가 키 하나가 된다 (키 이름은 파일 이름)
kubectl create configmap api-files -n shop --from-file=app.properties

# KEY=VALUE 줄로 된 파일을 줄마다 키로 나눈다
kubectl create configmap api-envfile -n shop --from-env-file=app.env

# 만든 것을 본다
kubectl get configmap -n shop
```

```text
configmap/api-config created
configmap/api-files created
configmap/api-envfile created
NAME               DATA   AGE
api-config         2      0s
api-envfile        2      0s
api-files          1      0s
kube-root-ca.crt   1      78s
```

DATA 칸은 키 개수다. 만든 적 없는 `kube-root-ca.crt`가 보이는데, 컨트롤러가 모든 네임스페이스에 자동으로 넣는 클러스터 CA 인증서다. Pod가 API 서버의 인증서를 검증할 때 쓴다.

`--from-file`과 `--from-env-file`은 이름이 비슷해서 자주 헷갈린다. 둘의 결과를 나란히 보면 차이가 분명하다.

```bash
# 파일 하나가 통째로 값 하나가 된 모습
kubectl get configmap api-files -n shop -o yaml
```

```text
apiVersion: v1
data:
  app.properties: |
    feature.newCheckout=true
    cache.ttlSeconds=300
kind: ConfigMap
metadata:
  creationTimestamp: "2026-10-20T13:56:37Z"
  name: api-files
  namespace: shop
  resourceVersion: "428"
  uid: ab2a8e69-6f55-468b-8594-573d776b6ba3
```

```bash
# 줄마다 키로 나뉜 모습
kubectl get configmap api-envfile -n shop -o yaml | head -4
```

```text
apiVersion: v1
data:
  LOG_LEVEL: info
  PAYMENT_TIMEOUT_MS: "3000"
```

`--from-file`은 파일을 볼륨으로 마운트해 앱이 파일로 읽을 때, `--from-env-file`은 환경 변수로 넣을 때 맞는 모양이다. `PAYMENT_TIMEOUT_MS`에 따옴표가 붙은 데 주목한다. ConfigMap의 값은 모두 문자열이라서, YAML로 직접 쓸 때 `3000`이나 `true`를 따옴표 없이 쓰면 숫자와 불리언으로 읽혀 거절된다. 문자열이 아닌 바이트가 필요하면 `binaryData`에 base64로 넣는다.

아래 그림은 운영에서 많이 쓰는 형태다. 클러스터에 바로 만들지 않고 YAML만 뽑아서 git에 둔다. 조각을 눌러 보면 각 옵션이 무엇을 정하는지 나온다.

## Pod에 넣는 두 가지 길

ConfigMap을 Pod에 넣는 길은 크게 둘이다. 환경 변수로 넣거나, 볼륨으로 마운트해 파일로 보이게 한다. 컨테이너의 `command`나 `args`에 `$(LOG_LEVEL)`처럼 환경 변수를 펼쳐 쓰는 방법도 있지만, 이건 환경 변수 길의 한 갈래다.

매니페스트로 쓰면 이렇다. 키 하나를 고르는 `env.valueFrom`, ConfigMap 전체를 쏟아 넣는 `envFrom`, 파일로 마운트하는 `volumes`를 한 Pod에 다 넣었다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: shop
spec:
  replicas: 2
  selector:
    matchLabels: {app: api}
  template:
    metadata:
      labels: {app: api}
    spec:
      containers:
        - name: api
          image: shop/api:1.4.2
          env:
            - name: DATABASE_HOST         # 컨테이너 안에서 쓸 이름
              valueFrom:
                configMapKeyRef:
                  name: api-config        # 어느 ConfigMap의
                  key: DB_HOST            # 어느 키를
          envFrom:
            - configMapRef:
                name: api-config          # 모든 키를 그대로 환경 변수로
            - configMapRef:
                name: api-envfile
              prefix: APP_                # APP_LOG_LEVEL처럼 앞에 붙인다
          volumeMounts:
            - name: files
              mountPath: /etc/shop        # 키마다 파일이 하나씩 생긴다
              readOnly: true
      volumes:
        - name: files
          configMap:
            name: api-files
            items:                        # 생략하면 모든 키를 파일로
              - key: app.properties
                path: app.properties
```

`envFrom`은 편하지만 키가 겹칠 때 누가 이기는지 알아 둬야 한다. 같은 이름이 여러 `envFrom` 소스에 있으면 목록에서 뒤에 온 소스가 이긴다. `env`에 직접 적은 값은 `envFrom`보다 우선한다. 아래에서 직접 규칙을 구현해 보면 헷갈리지 않는다.

`envFrom`으로 쏟아 넣으면 ConfigMap에 키를 하나 더하는 것만으로 앱의 환경이 바뀐다. 다른 팀이 같은 ConfigMap에 `PATH`나 `HOME` 같은 키를 넣으면 컨테이너가 이상하게 동작할 수 있다. 앱이 읽는 키가 정해져 있다면 `valueFrom`으로 하나씩 고르는 쪽이 안전하고, 매니페스트만 봐도 앱이 어떤 설정을 쓰는지 드러난다.

## 없는 ConfigMap을 가리키면 Pod가 뜨지 않는다

ConfigMap 이름이나 키에 오타가 있으면 Pod는 뜨지 않는다. 환경 변수와 볼륨은 막히는 단계가 달라서 보이는 상태도 다르다. 아래 두 출력은 kubelet이 남기는 실제 형식대로 쓴 예시다.

```bash
# 상태와 이벤트를 본다
kubectl get pod -n shop
kubectl describe pod api-7c4754bf9c-x2k8p -n shop | tail -3
```

```text
NAME                   READY   STATUS                       RESTARTS   AGE
api-7c4754bf9c-x2k8p   0/1     CreateContainerConfigError   0          14s
api-7c4754bf9c-q9n4d   0/1     ContainerCreating            0          14s

  Warning  Failed       3s (x3 over 14s)  kubelet  Error: couldn't find key LOG_LEVL in ConfigMap shop/api-config
  Warning  FailedMount  2s (x6 over 14s)  kubelet  MountVolume.SetUp failed for volume "files" : configmap "api-file" not found
```

환경 변수 쪽은 컨테이너를 만들 설정을 꾸리다 실패해서 `CreateContainerConfigError`가 된다. 볼륨 쪽은 마운트 단계에서 막혀 `ContainerCreating`에 머문다. 둘 다 재시작 횟수가 오르지 않는다. 컨테이너가 한 번도 뜨지 않았기 때문이다. ConfigMap을 나중에 만들면 kubelet이 다시 시도해서 Pod가 뜬다.

ConfigMap이 없어도 떠야 하는 경우, 예를 들어 선택적인 기능 플래그라면 `optional: true`를 단다. 키나 ConfigMap이 없으면 그 환경 변수는 빠지고, 볼륨은 빈 디렉터리로 마운트된다. 반대로 꼭 있어야 하는 설정에 `optional`을 달면 오타가 조용히 묻힌다.

## 환경 변수는 컨테이너가 뜰 때 한 번만 읽힌다

처음 상황으로 돌아간다. 환경 변수는 리눅스 프로세스가 시작할 때 부모에게서 받는 값이다. 실행 중인 프로세스의 환경을 밖에서 바꾸는 방법은 없다. 그래서 ConfigMap을 고쳐도 이미 떠 있는 컨테이너의 `LOG_LEVEL`은 그대로다. 실습 클러스터에서 확인해 본다.

```bash
# ConfigMap을 env로 쓰는 Deployment를 띄우고 ReplicaSet을 본다
kubectl apply -f deploy.yaml
kubectl get rs -n shop -l app=api

# ConfigMap 값만 바꾼다
kubectl patch configmap api-config -n shop --type merge -p '{"data":{"LOG_LEVEL":"debug"}}'

# ReplicaSet과 롤아웃 기록이 그대로인지 본다
kubectl get rs -n shop -l app=api
kubectl rollout history deploy/api -n shop
```

```text
deployment.apps/api created
NAME            DESIRED   CURRENT   READY   AGE
api-f8c4cb756   2         2         2       4s
configmap/api-config patched
NAME            DESIRED   CURRENT   READY   AGE
api-f8c4cb756   2         2         2       8s
deployment.apps/api
REVISION  CHANGE-CAUSE
1         <none>
```

ReplicaSet 이름 끝의 `f8c4cb756`은 Pod 템플릿으로 계산한다. Pod 템플릿에는 "api-config라는 ConfigMap을 읽어라"라는 참조만 있고 값은 없다. 값이 바뀌어도 템플릿은 같으니 Deployment는 바뀐 게 없다고 본다. 롤아웃도 재시작도 없다.

여기서 흔한 오해가 생긴다. Pod 하나가 죽어서 다시 뜨면 그 Pod만 새 값을 읽는다. 컨테이너 재시작이나 노드 장애로 몇 개만 다시 뜨면 같은 Deployment 안에서 `info`와 `debug`가 섞인다. 장애가 몇몇 Pod에서만 재현된다면 이걸 의심한다.

## 마운트한 파일은 늦게 바뀐다

볼륨으로 마운트한 파일은 바뀐다. kubelet이 Pod를 주기적으로 다시 맞출 때 마운트한 ConfigMap이 최신인지 보고 파일을 새로 쓰기 때문이다. 다만 즉시는 아니다. 아래 그림은 값을 바꾼 순간부터 앱이 읽기까지의 순서다.

공식 문서의 표현으로는 지연이 "kubelet 동기화 주기 + 캐시 전파 지연"까지 갈 수 있다. 동기화 주기는 kubelet 설정 `syncFrequency`(기본 1m)이고, 캐시 방식은 `configMapAndSecretChangeDetectionStrategy`(기본 Watch)가 정한다. 기본 설정이면 길게는 1분 남짓이다. 배포 스크립트에서 ConfigMap을 고치고 바로 다음 단계로 넘어가면 앱은 아직 옛 값을 읽고 있을 수 있다.

이 구조 때문에 앱이 파일 변경을 감시하는 방식이 중요하다. `app.properties` 파일 자체에 inotify를 걸면 링크가 가리키는 대상이 통째로 바뀌는 순간을 놓칠 수 있다. 디렉터리나 `..data`를 감시하거나, 일정 간격으로 파일을 다시 읽는 편이 확실하다. nginx처럼 설정을 시작할 때만 읽는 프로그램은 파일이 바뀌어도 `nginx -s reload`를 받기 전까지 옛 설정으로 돈다. 그래서 사이드카가 파일을 감시하다가 메인 프로세스에 reload 신호를 보내는 구성이 흔하다. 한 Pod에 컨테이너를 붙이는 방법은 [멀티 컨테이너 글](/posts/k8s-pod-multicontainer)에서 다룬다.

## subPath로 꽂은 파일은 끝까지 그대로다

`/etc/nginx` 디렉터리에 이미 이미지가 넣어 둔 파일이 여럿 있는데 `nginx.conf` 하나만 바꾸고 싶다. 볼륨을 `/etc/nginx`에 그대로 마운트하면 디렉터리 전체가 가려져서 다른 파일이 안 보인다. 그래서 `subPath`로 파일 하나만 꽂는다.

```yaml
          volumeMounts:
            - name: nginx-conf
              mountPath: /etc/nginx/nginx.conf   # 파일 하나 자리에
              subPath: nginx.conf                # 볼륨 안의 이 파일만 꽂는다
```

이렇게 꽂은 파일은 ConfigMap을 고쳐도 영영 바뀌지 않는다. 공식 문서도 subPath로 마운트한 ConfigMap은 업데이트를 받지 않는다고 적어 둔다. 앞에서 본 링크 교체 방식과 관련이 있다. subPath는 컨테이너가 뜰 때 그 순간의 실제 파일을 컨테이너 경로에 바인드 마운트한다. 나중에 kubelet이 `..data`를 새 디렉터리로 돌려도, 컨테이너에 꽂힌 것은 예전 디렉터리 안의 파일이다.

방법은 셋이다. 파일이 바뀔 때 재시작해도 괜찮다면 subPath를 그대로 두고 다음 절의 롤아웃 방법을 쓴다. 실시간 반영이 필요하면 ConfigMap을 다른 빈 디렉터리(예: `/etc/nginx/conf.d`)에 통째로 마운트하고, 메인 설정 파일이 그 디렉터리를 `include`하게 만든다. 앱 설정이라면 앱이 읽는 경로를 환경 변수로 받아 `/etc/shop/app.properties`처럼 ConfigMap 전용 디렉터리를 가리키게 한다.

## 설정이 바뀌면 Pod를 다시 띄우게 하기

환경 변수든 subPath든, 결국 확실한 방법은 Pod를 새로 띄우는 것이다. 다만 한 번에 다 죽이면 안 되니 Deployment의 롤링 업데이트에 태운다. 롤아웃이 일어나려면 Pod 템플릿이 바뀌어야 한다. 방법은 세 가지다.

첫째는 손으로 재시작하는 것이다. `kubectl rollout restart`는 템플릿에 시각 어노테이션을 넣어 템플릿을 바꾼다.

```bash
# 템플릿에 restartedAt을 넣어 롤아웃을 일으킨다
kubectl rollout restart deploy/api -n shop

# 새 ReplicaSet이 생겼는지, 템플릿에 무엇이 들어갔는지 본다
kubectl get rs -n shop -l app=api
kubectl get deploy api -n shop -o jsonpath='{.spec.template.metadata.annotations}'; echo
```

```text
deployment.apps/api restarted
NAME             DESIRED   CURRENT   READY   AGE
api-6d5684b459   2         2         2       5s
api-f8c4cb756    0         0         0       13s
{"kubectl.kubernetes.io/restartedAt":"2026-10-20T14:06:02Z"}
```

사람이 잊으면 끝이라는 게 약점이다. 그래서 둘째 방법, ConfigMap 내용의 해시를 Pod 템플릿 어노테이션에 넣는 방법을 많이 쓴다. 손으로 해 보면 원리가 보인다.

```bash
# ConfigMap 내용으로 해시를 만든다
H=$(kubectl get configmap api-config -n shop -o jsonpath='{.data}' | sha256sum | cut -c1-16)
echo $H

# 해시를 Pod 템플릿 어노테이션에 넣는다
kubectl patch deploy api -n shop -p "{\"spec\":{\"template\":{\"metadata\":{\"annotations\":{\"checksum/config\":\"$H\"}}}}}"
kubectl get rs -n shop -l app=api
```

```text

deployment.apps/api patched
NAME             DESIRED   CURRENT   READY   AGE
api-6d5684b459   0         0         0       10s
api-b85c64b6     2         2         2       5s
api-f8c4cb756    0         0         0       18s
```

해시가 바뀌면 템플릿이 바뀌고, 템플릿이 바뀌면 새 ReplicaSet으로 롤아웃한다. 내용이 같으면 해시도 같아서 쓸데없는 재시작이 없다. Helm 차트에서는 템플릿 한 줄로 이 일을 한다. 그 방법은 [차트 템플릿 글](/posts/helm-chart-templates)의 "설정이 바뀌면 Pod를 다시 띄우게 하기"에 있다. 아래 그림은 이 과정을 객체 사이의 움직임으로 본 것이다.

셋째 방법이 이 문제를 푼다. ConfigMap 이름 자체에 내용의 해시를 붙이는 것이다. Kustomize의 `configMapGenerator`가 이렇게 한다.

```bash
# configMapGenerator로 만든 ConfigMap 이름과 그걸 참조하는 곳을 본다
kubectl kustomize . | grep -E "name: api-config"

# 값을 바꾸고 다시 렌더링한다
sed -i 's/LOG_LEVEL=info/LOG_LEVEL=debug/' kustomization.yaml
kubectl kustomize . | grep -E "name: api-config"
```

  name: api-config-mhd58dhdg6
            name: api-config-mhd58dhdg6

값이 바뀌면 ConfigMap 이름이 바뀌고, Deployment가 참조하는 이름도 같이 바뀐다. 템플릿이 바뀌니 롤아웃이 일어난다. 옛 ConfigMap `api-config-82986htdd9`는 그대로 남아 있어서, 롤백하면 옛 ReplicaSet이 옛 이름의 ConfigMap을 다시 읽는다. 대신 쓰지 않는 ConfigMap이 쌓이니 `kubectl apply --prune`이나 ArgoCD의 정리 기능으로 지워야 한다.

재시작 없이 설정을 반영하고 싶은 앱이라면 다른 길도 있다. Spring Cloud Kubernetes처럼 앱이 API 서버를 직접 watch하거나, Reloader 같은 컨트롤러가 ConfigMap 변경을 보고 Deployment를 대신 재시작하게 한다. 어느 쪽이든 "설정 변경도 배포다"라는 원칙은 같다. 리뷰 없이 운영 ConfigMap을 `kubectl edit`으로 고치면 git과 클러스터가 어긋나고, 다음 배포 때 그 수정이 덮어써진다.

## immutable로 잠그기

ConfigMap에 `immutable: true`를 달면 그 뒤로 `data`를 바꿀 수 없다. 1.21부터 정식 기능이다.

```bash
# 잠근 ConfigMap을 만든다
kubectl apply -f flags.yaml

# 값을 바꿔 본다
kubectl patch configmap feature-flags-v3 -n shop --type merge -p '{"data":{"NEW_CHECKOUT":"false"}}'

# 잠금을 풀어 본다
kubectl patch configmap feature-flags-v3 -n shop --type merge -p '{"immutable":false}'

# 라벨은 바꿀 수 있다
kubectl patch configmap feature-flags-v3 -n shop --type merge -p '{"metadata":{"labels":{"team":"checkout"}}}'
```

```text
configmap/feature-flags-v3 created
The ConfigMap "feature-flags-v3" is invalid: data: Forbidden: field is immutable when `immutable` is set
The ConfigMap "feature-flags-v3" is invalid: immutable: Forbidden: field is immutable when `immutable` is set
configmap/feature-flags-v3 patched
```

한 번 잠그면 풀 수도 없다. 바꾸려면 지우고 다시 만들어야 한다. 그래서 잠그는 ConfigMap은 `feature-flags-v3`처럼 이름에 버전을 넣고, 바꿀 때는 `v4`를 새로 만들어 Deployment가 가리키는 이름을 바꾼다. 앞의 Kustomize 해시 방식과 잘 맞는다.

잠그는 이유는 둘이다. 하나는 사고 방지다. 누군가 운영 ConfigMap을 손으로 고쳐 일부 Pod만 새 값을 읽는 일을 막는다. 다른 하나는 성능이다. kubelet은 마운트한 ConfigMap마다 watch를 건다. Pod가 수만 개인 클러스터에서는 이 watch들이 API 서버에 부담이 된다. immutable인 ConfigMap은 바뀔 일이 없으니 kubelet이 watch를 걸지 않는다.

## 1MiB를 넘으면 만들어지지 않는다

ConfigMap 하나는 1MiB(1048576바이트)를 넘을 수 없다. etcd에 객체 하나로 들어가기 때문이다. 1.1MB 파일을 넣어 본다.

```bash
# 1100000바이트짜리 파일로 ConfigMap을 만든다
kubectl create configmap big -n shop --from-file=big.txt
```

```text
error: failed to create configmap: ConfigMap "big" is invalid: []: Too long: must have at most 1048576 bytes
```

그런데 그보다 훨씬 작은 크기에서 먼저 막히는 경우가 있다. Grafana 대시보드 JSON처럼 300KB쯤 되는 ConfigMap을 `kubectl apply`로 올리면 이렇게 된다.

```bash
# 300KB 남짓한 ConfigMap 매니페스트를 apply한다
kubectl apply -f dash.yaml

# 서버 쪽 apply로 다시 올린다
kubectl apply --server-side -f dash.yaml
```

```text
The ConfigMap "dashboards" is invalid: metadata.annotations: Too long: must have at most 262144 bytes
configmap/dashboards serverside-applied
```

`kubectl apply`는 기본으로 적용한 내용을 통째로 `kubectl.kubernetes.io/last-applied-configuration` 어노테이션에 저장한다. 어노테이션은 전부 합쳐 256KiB를 넘을 수 없으니 그 전에 걸린다. `--server-side`로 적용하면 이 어노테이션을 쓰지 않아서 통과한다. `kubectl create`나 `replace`도 어노테이션을 남기지 않는다.

설정이 1MiB에 가까워진다면 ConfigMap이 맞는 그릇인지부터 다시 본다. 큰 정적 파일은 이미지에 넣거나, 오브젝트 스토리지에 두고 init 컨테이너가 받아 오게 하는 편이 낫다. ConfigMap 여러 개로 쪼갠 뒤 `projected` 볼륨으로 한 디렉터리에 모으는 방법도 있다.

명령으로는 이렇게 확인한다. 먼저 매니페스트에서 값이 어느 길로 들어갔는지 본다.

```bash
# 이 Deployment가 ConfigMap을 env로 쓰는지, 볼륨으로 쓰는지, subPath인지 본다
kubectl get deploy api -n shop -o yaml | grep -n -E "configMapRef|configMapKeyRef|configMap:|subPath"

# 컨테이너가 실제로 받은 환경 변수를 본다
kubectl exec -n shop deploy/api -- printenv LOG_LEVEL

# 마운트된 파일의 실제 내용을 본다
kubectl exec -n shop deploy/api -- cat /etc/shop/app.properties

# Pod마다 언제 떴는지 본다 (ConfigMap을 바꾼 시각보다 이전이면 옛 값일 수 있다)
kubectl get pod -n shop -l app=api -o custom-columns=NAME:.metadata.name,START:.status.startTime
```

길에 따라 처방이 다르다. 환경 변수와 subPath라면 롤아웃이 필요하다. 볼륨이라면 1분쯤 기다려 본 뒤에도 파일이 그대로인지, 파일은 바뀌었는데 앱이 다시 안 읽는 건지를 나눈다. 파일까지 바뀌었다면 남은 건 앱의 reload 문제다.

같은 Deployment의 Pod끼리 동작이 다르면 시작 시각을 비교한다. ConfigMap을 바꾼 뒤에 다시 뜬 Pod만 새 값을 읽었을 가능성이 크다. 이럴 때 롤아웃을 한 번 일으켜 모든 Pod를 같은 값으로 맞추고 나서 원인을 본다.

## ConfigMap은 언제 무엇을 읽나

ConfigMap은 이미지 밖에 둔 문자열 묶음이다. 환경 변수로 넣은 값은 컨테이너가 뜰 때 한 번 읽히고, 볼륨으로 넣은 파일은 kubelet이 1분 안팎의 지연을 두고 링크를 바꿔 갱신하며, subPath로 꽂은 파일은 갱신되지 않는다. 확실하게 반영하려면 해시 어노테이션이나 이름에 해시를 붙이는 방식으로 롤아웃을 일으키고, 롤백까지 생각하면 이름에 해시를 붙이는 쪽이 낫다. 비밀 값을 담는 [Secret](/posts/k8s-secret)은 같은 방식으로 Pod에 들어가지만 지켜야 할 것이 더 많다. 데이터를 Pod보다 오래 남기는 일은 [PV와 PVC](/posts/k8s-pv-pvc)가 맡는다.

## 면접에서 나올 만한 질문

### ConfigMap을 수정했는데 Pod에 반영되지 않습니다. 왜 그런가요?

어떻게 넣었는지에 달렸다. 환경 변수로 넣었다면 프로세스가 시작할 때만 읽으니 Pod를 다시 띄워야 한다. 볼륨으로 마운트했다면 kubelet 동기화 주기(기본 1분)와 캐시 지연만큼 늦게 파일이 바뀌고, 앱이 파일을 다시 읽어야 반영된다. subPath로 마운트한 파일은 아예 갱신되지 않는다.

### ConfigMap 변경 시 Pod를 자동으로 재시작하게 하려면 어떻게 하나요?

Pod 템플릿을 바꾸는 게 핵심이다. ConfigMap 내용의 해시를 템플릿 어노테이션에 넣으면 내용이 바뀔 때만 롤아웃이 일어난다. Kustomize의 configMapGenerator처럼 이름에 해시를 붙이면 롤백할 때 옛 ConfigMap도 함께 돌아간다는 장점이 있다. Reloader 같은 컨트롤러를 두는 방법도 있다.

### 볼륨으로 마운트한 ConfigMap 파일은 어떻게 원자적으로 바뀌나요?

kubelet은 시각이 이름인 새 디렉터리에 파일을 다 쓴 뒤 `..data` 심볼릭 링크를 새 디렉터리로 바꾼다. 키 이름의 파일은 `..data/키`를 가리키는 링크라서, 링크 교체 한 번으로 모든 파일이 동시에 바뀐다. 그래서 앱은 반쯤 쓰인 파일을 보지 않지만, 파일 하나에 inotify를 걸면 교체를 놓칠 수 있다.

### subPath로 마운트한 ConfigMap은 왜 갱신되지 않나요?

subPath는 컨테이너가 뜰 때 볼륨 안의 그 파일을 컨테이너 경로에 바인드 마운트한다. 나중에 kubelet이 `..data` 링크를 새 디렉터리로 바꿔도 컨테이너에 꽂힌 것은 옛 디렉터리의 파일이다. 갱신이 필요하면 디렉터리째 마운트하고 include하거나, 바뀔 때 롤아웃한다.

### immutable ConfigMap은 왜 쓰나요?

실수로 운영 설정을 고치는 일을 막고, kubelet이 그 ConfigMap에 watch를 걸지 않게 해서 큰 클러스터의 API 서버 부담을 줄인다. 한 번 잠그면 data도 immutable 필드도 바꿀 수 없으니, 이름에 버전을 넣어 새로 만들고 Deployment의 참조를 바꾸는 방식으로 쓴다.

### ConfigMap의 크기 제한은 얼마이고, 넘으면 어떻게 하나요?

1MiB다. etcd에 객체 하나로 저장되기 때문이다. 다만 `kubectl apply`는 last-applied 어노테이션에 전체를 복사해서 256KiB 어노테이션 한도에 먼저 걸릴 수 있고, 이건 `--server-side`로 피한다. 1MiB에 가까운 데이터라면 이미지나 오브젝트 스토리지에 두고 init 컨테이너로 받는 편이 낫다.

### envFrom과 env에 같은 키가 있으면 어느 값이 쓰이나요?

env에 직접 적은 값이 이긴다. envFrom 소스끼리 겹치면 목록에서 뒤에 오는 소스가 이긴다. 그래서 envFrom으로 큰 ConfigMap을 통째로 넣으면 다른 사람이 추가한 키가 앱 환경을 바꿀 수 있으니, 필요한 키만 valueFrom으로 고르거나 prefix를 붙인다.
