<EasyIntro>
  ArgoCD는 클러스터 안에서 돌면서 저장소에 적힌 모습과 실제 클러스터를 계속 비교하고, 다르면 저장소 쪽으로 맞추는 도구다. 그래서 급해서 손으로 서버 수를 늘려도 몇 초 만에 원래대로 돌아가는 일이 생긴다. 저장소가 정답지이고 손으로 바꾼 것은 오답으로 취급되기 때문이다.

장애 중에 급해서 `kubectl scale deploy shop-api --replicas 5`를 쳤다. 1초도 안 돼 Pod가 다시 2개로 줄었다. 다시 쳐도 마찬가지였다. 누군가 되돌리고 있는 것 같은데 터미널에는 아무도 없다. 범인은 클러스터 안에서 도는 ArgoCD였다. git에 `replicas: 2`가 적혀 있고, 자동 동기화에 selfHeal이 켜져 있었다.

반대 경우도 있다. git에서 ConfigMap 파일을 지웠는데 클러스터에는 그대로 남아 있다. 고친 커밋을 올렸는데 ArgoCD는 몇 분째 예전 커밋으로 재시도만 한다. 화면에는 `Synced`인데 서비스는 안 뜬다. ArgoCD를 쓰면 이런 장면을 한 번씩은 만난다. 이 글은 ArgoCD가 무엇을 언제 비교하고 언제 적용하는지를 따라가며 이 장면들을 하나씩 풀어 본다.

출력은 kwok 실습 클러스터(Kubernetes 1.30)에 ArgoCD v3.1.8의 repo-server와 application-controller, applicationset-controller를 클러스터 밖 프로세스로 띄워 받았다. git 저장소는 같은 머신의 로컬 저장소(`file://`)를 썼고, 대상 클러스터는 `kwok`이라는 이름으로 등록했다. 그래서 출력에 `kubernetes.default.svc` 대신 `kwok`이 보인다. kwok은 Pod를 실제로 실행하지 않고 상태만 흉내 내지만, ArgoCD가 하는 비교와 적용은 API 서버를 상대로 하는 일이라 실제 클러스터와 같다.

밀어 넣는 배포(push)와 끌어오는 배포(pull)의 차이는 [EKS 배포 파이프라인](/posts/k8s-deploy-pipeline-eks)에서, ArgoCD가 Helm 차트를 렌더링만 하는 이유는 [차트 배포 흐름](/posts/helm-dependencies-oci-gitops)에서 다뤘다. ArgoCD와 Flux를 고르는 문제는 [GitOps 도구 비교](/posts/gitops-argocd-vs-flux)에 따로 적었다.

## ArgoCD는 세 부품이 나눠서 일한다

ArgoCD를 설치하면 Deployment가 여럿 생긴다. 이름만 보면 헷갈리는데 하는 일은 분명히 나뉜다.

- repo-server: git을 받아 와서 매니페스트를 만든다. 순수 YAML이면 읽기만 하고, Kustomize나 Helm이면 `kustomize build`, `helm template`을 돌린다. 클러스터에 접근하지 않는다.
- application-controller: Application마다 "git에서 만든 매니페스트"와 "클러스터에 있는 실제 객체"를 비교하고, 동기화를 실행한다. 클러스터의 객체는 watch로 계속 받아 캐시해 둔다.
- argocd-server: 웹 UI와 CLI가 붙는 API다. 비교나 적용을 직접 하지 않는다.
- redis: repo-server가 만든 매니페스트와 앱 상태를 캐시한다. 지워져도 다시 만들 수 있는 값만 둔다.

이 구분이 장애를 볼 때 바로 쓸모가 있다. 매니페스트가 안 만들어지면 repo-server 로그를, 비교 결과가 이상하거나 적용이 안 되면 controller 로그를 본다. UI가 안 열리는 건 argocd-server 문제고 배포와는 상관이 없다. 아래 그림에서 다음을 누르면 git 변경과 클러스터 변경이 각각 어떤 길로 controller에 닿는지 보인다.

여기서 나온 두 단어를 구분해 둔다. 새로 고침(refresh)은 git과 클러스터를 다시 비교하는 일이다. 결과로 상태 표시만 바뀌고 클러스터는 건드리지 않는다. 동기화(sync)는 비교 결과에 따라 클러스터를 실제로 바꾸는 일이다. UI의 Refresh 버튼과 Sync 버튼이 따로 있는 이유다.

새로 고침에도 두 가지가 있다. 보통 새로 고침은 캐시된 매니페스트를 쓰고, 강한 새로 고침(hard refresh)은 repo-server 캐시를 무시하고 다시 렌더링한다. 차트 저장소의 같은 버전 차트를 덮어썼거나, Helm values 파일을 다른 저장소에서 가져오는 경우처럼 "커밋은 같은데 결과가 달라지는" 상황에서만 강한 새로 고침이 필요하다.

```bash
# 보통 새로 고침 (UI의 Refresh와 같다)
kubectl -n argocd annotate application shop-api argocd.argoproj.io/refresh=normal --overwrite

# 강한 새로 고침: repo-server 캐시를 무시하고 다시 렌더링한다
kubectl -n argocd annotate application shop-api argocd.argoproj.io/refresh=hard --overwrite
```

git 변화를 3분까지 기다리기 싫으면 git 서버에 ArgoCD 웹훅을 건다(`/api/webhook`). 푸시 이벤트를 받으면 해당 저장소를 쓰는 Application을 바로 새로 고친다. 웹훅이 빠지면 "머지했는데 배포가 안 된다"는 문의가 3분짜리 미스터리로 돌아온다.

## Application 한 장과 AppProject 한 장

ArgoCD에게 일을 시키는 단위는 Application이라는 커스텀 리소스다. "어느 저장소의 어느 경로를, 어느 클러스터의 어느 네임스페이스에"를 적는다. 실습에 쓴 것은 이렇다.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: shop-api
  namespace: argocd          # Application은 기본적으로 argocd 네임스페이스에 둔다
spec:
  project: shop              # 어떤 규칙 안에서 움직일지
  source:
    repoURL: https://github.com/acme/shop-deploy.git
    targetRevision: main     # 브랜치, 태그, 커밋 SHA 모두 된다
    path: apps/shop
  destination:
    server: https://kubernetes.default.svc
    namespace: shop
```

`project`가 가리키는 AppProject는 울타리다. 이 프로젝트의 Application이 어느 저장소에서 가져오고, 어느 클러스터와 네임스페이스에 배포하고, 어떤 종류의 리소스를 만들 수 있는지를 정한다. 팀마다 프로젝트를 나누면 결제팀 Application이 실수로 `kube-system`에 배포하는 일을 막을 수 있다.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: shop
  namespace: argocd
spec:
  sourceRepos:
    - https://github.com/acme/shop-deploy.git
  destinations:
    - server: https://kubernetes.default.svc
      namespace: shop
  clusterResourceWhitelist: []        # 클러스터 범위 리소스는 하나도 못 만든다
  namespaceResourceBlacklist:
    - group: ""
      kind: ResourceQuota             # 쿼터는 플랫폼팀만 바꾼다
```

울타리를 넘으면 어떻게 되는지 직접 봤다. 같은 Application을 `kube-system`으로 보내게 바꾸고, git에 Namespace 리소스도 하나 넣었다.

```text
NAME           SYNC STATUS   HEALTH STATUS
shop-api       Synced        Healthy
shop-api-sys   Unknown       Unknown
InvalidSpecError: application destination server 'kwok' and namespace 'kube-system' do not match any of the allowed destinations in project 'shop'
```

```text
Sync	Namespace/shop-tools	SyncFailed	resource :Namespace is not permitted in project shop
```

목적지가 틀리면 비교조차 하지 않고 `Unknown`에 머문다. 리소스 종류가 막히면 그 리소스만 `SyncFailed`가 된다. 아래 그림은 두 가지 막힘이 어디서 일어나는지 보여 준다.

AppProject는 사람의 권한이 아니라 Application의 권한을 정한다. "누가 이 Application을 동기화할 수 있나"는 ArgoCD RBAC(`argocd-rbac-cm`)과 프로젝트의 `roles`가 맡는다. 그리고 controller 자신은 대개 클러스터 관리자에 가까운 권한으로 돈다. 울타리를 AppProject로 치지 않으면 git에 쓸 수 있는 사람은 사실상 클러스터 관리자가 된다. 쿠버네티스 쪽 권한 모델은 [RBAC 글](/posts/k8s-rbac)에 있다.

## Synced와 Healthy는 다른 질문이다

ArgoCD 화면의 두 상태를 섞어 읽으면 장애를 놓친다.

- 동기화 상태(sync status): git에서 만든 매니페스트와 클러스터 객체가 같은가. `Synced`, `OutOfSync`, `Unknown`.
- 건강 상태(health status): 그 객체가 제 역할을 하고 있나. `Healthy`, `Progressing`, `Degraded`, `Suspended`, `Missing`, `Unknown`.

Synced는 "적힌 대로 들어갔다"는 뜻이지 "잘 돌고 있다"는 뜻이 아니다. 실습에서 스케줄될 수 없는 Deployment(존재하지 않는 `pool: gpu` 노드를 요구하고 `progressDeadlineSeconds: 20`)를 git에 올렸다.

```text
01:42:40 shop-api   OutOfSync   Missing
01:42:46 shop-api   Synced   Progressing
01:43:05 shop-api   Synced   Degraded
```

```bash
# ArgoCD가 Degraded라고 판단한 근거는 Deployment의 조건에 있다
kubectl -n shop get deploy shop-worker -o jsonpath='{range .status.conditions[*]}{.type}{"\t"}{.status}{"\t"}{.reason}{"\n"}{end}'
```

```text
Available	False	MinimumReplicasUnavailable
Progressing	False	ProgressDeadlineExceeded
```

적용은 6초 만에 끝나서 `Synced`가 됐다. Pod가 Pending에 머무는 동안 `Progressing`이었고, Deployment가 기한을 넘겨 `ProgressDeadlineExceeded`를 세우자 `Degraded`로 바뀌었다. ArgoCD는 건강 상태를 스스로 재지 않는다. 리소스 종류마다 정해진 판단 규칙이 있고, Deployment는 쿠버네티스가 남긴 조건을 그대로 읽는다. Pod 하나하나의 readiness는 [Pod 프로브 글](/posts/k8s-pod-probes)의 이야기다.

그래서 배포 성공 여부를 볼 때는 둘 다 본다. 알림도 `OutOfSync`가 오래 가는 것과 `Degraded`가 되는 것을 따로 건다. controller가 내놓는 지표에 두 상태가 레이블로 들어 있다.

```text
argocd_app_info{autosync_enabled="true",dest_namespace="shop",health_status="Healthy",name="shop-api",project="shop",sync_status="Synced",...} 1
argocd_app_sync_total{name="shop-api",phase="Failed",project="shop",...} 2
argocd_app_sync_total{name="shop-api",phase="Succeeded",project="shop",...} 8
```

이 지표를 Prometheus로 모으는 방법은 [Prometheus 내부 구조](/posts/prometheus-basics)에 있다.

## 손으로 고친 것을 되돌리는 selfHeal

처음 장면으로 돌아간다. 자동 동기화(`automated`)를 켜면 OutOfSync를 발견할 때 ArgoCD가 알아서 동기화한다. 그런데 자동 동기화만으로는 git이 바뀔 때만 동작한다. 클러스터 쪽을 누가 바꾼 것까지 되돌리려면 `selfHeal: true`가 필요하다.

```yaml
spec:
  syncPolicy:
    automated:
      selfHeal: true   # 클러스터에서 바뀐 것도 git으로 되돌린다
      prune: false     # git에서 지운 리소스를 클러스터에서도 지울지
```

같은 앱을 계속 되돌리는 경우를 대비해 selfHeal에는 지수 백오프가 있다. v3.1의 controller 플래그 기본값은 처음 2초, 3배씩 늘려 최대 300초다(`--self-heal-backoff-*`). 누가 계속 고치는데 ArgoCD가 계속 되돌리는 싸움이 무한히 빠르게 돌지는 않는다는 뜻이다.

장애 중에 손으로 늘려야 한다면 방법은 셋이다. git에 replicas를 고쳐 커밋한다. 그게 느리면 Application의 자동 동기화를 잠시 끈다. 아니면 replicas를 ArgoCD가 보지 않게 만든다(다음 다음 절의 ignoreDifferences). `kubectl rollout undo`도 같은 이유로 몇 초 뒤 되돌아간다. 되돌리기는 git revert가 기본이다. 되돌리기 전략 전반은 [롤백 전략](/posts/rollback-strategy)에 있다.

## git에서 지운 것은 prune이 있어야 지워진다

git에서 `cm.yaml`을 지우고 새로 고쳤다. selfHeal은 켜져 있고 prune은 꺼져 있다.

```text
NAME       SYNC STATUS   HEALTH STATUS
shop-api   OutOfSync     Healthy
ConfigMap	shop-config	OutOfSync	true
Service	shop-api	Synced
Deployment	shop-api	Synced
```

```text
{"application":"shop-api","level":"info","msg":"Skipping auto-sync: need to prune extra resources only but automated prune is disabled","project":"shop"}
```

세 번째 칸의 `true`는 `requiresPruning`이다. 지워야 할 리소스가 있다는 것까지는 알지만, 자동으로 지우지는 않는다. 로그가 그 이유를 그대로 적는다. prune을 켜고 새로 고치자 지워졌다.

```text
Sync	ConfigMap/shop-config	Pruned	pruned
Sync	Service/shop-api	Synced	service/shop-api unchanged
Sync	Deployment/shop-api	Synced	deployment.apps/shop-api unchanged
```

prune을 켜지 않으면 지운 리소스가 쌓인다. 켜면 경로를 잘못 바꾼 커밋 하나로 리소스가 통째로 지워질 수 있다. 실무에서 쓰는 안전장치는 이렇다.

- 지우면 안 되는 리소스(PVC, 운영 DB의 Secret)에는 `argocd.argoproj.io/sync-options: Prune=false`를 붙인다. 이 리소스는 prune 대상에서 빠지고 OutOfSync로만 표시된다.
- 한 번에 많이 지우는 것을 막으려면 동기화 옵션 `PruneLast=true`로 지우기를 맨 뒤로 미룬다. 새 리소스가 다 건강해진 뒤에 옛 것을 지운다.
- Application 자체를 지울 때 리소스를 같이 지울지는 Application의 finalizer(`resources-finalizer.argocd.argoproj.io`)가 정한다. finalizer가 있으면 Application을 지우는 순간 그 앱이 만든 리소스도 모두 지워진다.

마지막 항목이 뒤에서 ApplicationSet과 엮여 사고를 만든다.

## 순서가 필요할 때: sync wave와 hook

DB 마이그레이션을 먼저 돌리고, ConfigMap을 만든 다음 Deployment를 바꾸고, 다 뜨면 스모크 테스트를 돌리고 싶다. ArgoCD는 이 순서를 두 가지 어노테이션으로 정한다.

- hook: `argocd.argoproj.io/hook: PreSync | Sync | PostSync | SyncFail`. 동기화의 특정 단계에만 실행되는 리소스다. 주로 Job이다.
- wave: `argocd.argoproj.io/sync-wave: "-1"`. 같은 단계 안의 순서다. 숫자가 작은 것부터, 기본값은 0이다.

실습에 쓴 파일의 요점만 옮기면 이렇다.

```yaml
# migrate-job.yaml: 본 리소스보다 먼저 한 번 돈다
metadata:
  name: db-migrate
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: BeforeHookCreation  # 다음 동기화 직전에 지운다
---
# cm.yaml
metadata:
  name: shop-config
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
---
# deploy.yaml, svc.yaml
metadata:
  name: shop-api
  annotations:
    argocd.argoproj.io/sync-wave: "1"
---
# smoke-job.yaml: 다 건강해진 뒤에 돈다
metadata:
  name: smoke-test
  annotations:
    argocd.argoproj.io/hook: PostSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded       # 성공하면 지운다
```

커밋하고 새로 고친 뒤 1초마다 상태를 찍었다.

01:41:21 Synced   Healthy   Running   waiting for completion of hook batch/Job/smoke-test

## 고친 커밋을 올렸는데 예전 커밋만 재시도한다

앞의 worker 사고 중에 겪은 일이다. Degraded를 보고 worker를 지우는 커밋을 바로 올렸다. 그런데 ArgoCD는 몇 분 동안 계속 worker를 넣었던 커밋으로 재시도했다.

```text
01:44:50 OutOfSync   Degraded   a002cf1b3d0ec4909b11511be2ae3d95cbdca2a4   Running   ... Retrying attempt #4 at 1:45AM.
01:45:56 OutOfSync   Degraded   a002cf1b3d0ec4909b11511be2ae3d95cbdca2a4   Running   ... Retrying attempt #5 at 1:47AM.
01:48:33 OutOfSync   Degraded   44cda7b366ae4712cb1774d11050b17915217aac   Running   ... Retrying attempt #1 at 1:48AM.
```

세 번째 칸이 동기화 중인 커밋이다. 이미 시작한 동기화 작업(operation)은 그 커밋에 묶여 있다. 실패하면 재시도하고, 재시도가 다 끝나야 새 커밋으로 넘어간다. 이 버전에서는 spec에 `retry`를 적지 않았는데도 자동 동기화 작업에 `{"limit":5}`가 붙어 있었고, 간격이 점점 늘어서 다섯 번을 다 쓰는 데 4분 가까이 걸렸다. 급할 때는 진행 중인 작업을 끊는다(`argocd app terminate-op shop-api`, UI의 Terminate). 실습에서는 같은 일을 Application의 `status.operationState.phase`를 `Terminating`으로 바꿔서 했다.

끊고 나면 다른 함정이 기다린다. 자동 동기화는 한 번 실패한 커밋을 다시 시도하지 않는다.

```text
"msg":"Skipping auto-sync: failed previous sync attempt to be1f91b24a684d8331c0511d2a77ebc0fc031523"
```

이 커밋을 고치려고 git 밖의 설정(AppProject 권한 등)을 바꿨다면 새 커밋이 올 때까지 ArgoCD는 가만히 있는다. 손으로 한 번 동기화하거나 빈 커밋이라도 하나 올려야 한다. "고쳤는데 왜 안 움직이지"의 상당수가 이 두 가지다.

## 남이 바꾸는 필드는 ignoreDifferences로 비켜 준다

HPA를 붙인 Deployment를 생각해 보자. HPA가 replicas를 4로 늘리면 git의 `replicas: 2`와 달라져 OutOfSync가 되고, selfHeal이 켜져 있으면 다시 2로 되돌린다. HPA와 ArgoCD가 싸운다. 가장 깔끔한 해결은 git의 Deployment에서 `replicas`를 아예 빼는 것이다. 이미 적혀 있거나, 다른 컨트롤러(웹훅이 주입하는 사이드카, cert-manager가 채우는 `caBundle`)가 바꾸는 필드라면 비교에서 뺀다.

```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      name: shop-api
      jsonPointers:
        - /spec/replicas
```

이걸 넣고 replicas를 4로 바꾸자 `Synced`가 유지됐다. 그런데 git에 다른 변경(ConfigMap 한 줄)을 커밋해 동기화가 일어나자 결과가 달라졌다.

```text
after scale: shop-api   Synced   Healthy replicas=4
after git sync: shop-api   Synced   Healthy replicas=2 rev=422f5e5
```

ignoreDifferences는 비교에서만 빼 준다. 동기화할 때는 git의 매니페스트를 통째로 적용하니 replicas가 다시 2가 된다. 적용할 때도 그 필드를 건드리지 않게 하려면 동기화 옵션을 하나 더 켠다.

```yaml
spec:
  syncPolicy:
    syncOptions:
      - RespectIgnoreDifferences=true   # 동기화할 때도 무시한 필드는 live 값을 유지한다
```

```text
after git sync: shop-api   Synced   Healthy replicas=4 rev=df128e5
```

이번에는 4가 유지됐다. 여러 리소스에 공통으로 적용할 규칙은 `argocd-cm`의 `resource.customizations.ignoreDifferences.<group>_<kind>`에 둔다. 필드 주인을 API 서버가 기억하는 서버 쪽 apply(`ServerSideApply=true`)를 켜면 이런 충돌 일부를 다른 방식으로 풀 수 있다. 필드 주인 개념은 [kubectl apply와 서버 쪽 apply](/posts/kubectl-apply-ssa)에 있다. HPA 자체는 [HPA 글](/posts/k8s-hpa)에서 다뤘다.

ArgoCD가 어떤 리소스를 자기 것으로 보는지도 이 맥락에서 알아 두면 좋다. v3의 기본은 어노테이션 추적이다. 적용한 리소스마다 아래 한 줄을 남긴다.

## 앱이 많아지면: app-of-apps와 ApplicationSet

서비스가 30개, 환경이 셋이면 Application이 90장이다. 손으로 만들기 시작하면 Application 자체가 git 밖의 수작업이 된다. 이걸 푸는 방법이 둘 있다.

app-of-apps는 Application YAML을 담은 폴더를 가리키는 Application 하나를 만드는 방식이다. 루트 앱을 동기화하면 그 안의 Application들이 생기고, 각각이 자기 서비스를 배포한다. 단순하고 Application마다 설정을 다르게 쓰기 쉽다. 대신 비슷한 YAML을 복사해 늘리게 된다.

ApplicationSet은 생성기(generator)가 변수를 만들고 템플릿에 대입해 Application을 찍어 낸다. git 폴더 생성기를 써 봤다.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: shop-envs
  namespace: argocd
spec:
  goTemplate: true
  generators:
    - git:
        repoURL: https://github.com/acme/shop-deploy.git
        revision: main
        directories:
          - path: envs/*            # envs 아래 폴더마다 Application 하나
  template:
    metadata:
      name: 'shop-{{.path.basename}}'
    spec:
      project: envs
      source:
        repoURL: https://github.com/acme/shop-deploy.git
        targetRevision: main
        path: '{{.path.path}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: 'shop-{{.path.basename}}'
      syncPolicy:
        automated: {}
        syncOptions: ["CreateNamespace=true"]
```

```text
{"allPaths":["apps","apps/shop","envs","envs/dev","envs/prod"],"msg":"applications result from the repo service",...}
{"applicationset":{"Namespace":"argocd","Name":"shop-envs"},"msg":"generated 2 applications"}
NAME        SYNC STATUS   HEALTH STATUS
shop-api    Synced        Healthy
shop-dev    OutOfSync     Missing
shop-prod   OutOfSync     Missing
```

폴더 둘에서 Application 둘이 생겼다. 그런데 동기화가 안 됐다. 이유는 앞의 AppProject였다.

```text
Namespace/shop-dev SyncFailed resource :Namespace is not permitted in project envs
```

`CreateNamespace=true`는 Namespace 리소스를 만드는 일이라, 프로젝트의 `clusterResourceWhitelist`에 Namespace가 있어야 한다. 화이트리스트에 `{group: "", kind: Namespace}`를 넣고 다시 동기화하자 둘 다 `Synced Healthy`가 됐다. 이때도 앞 절의 "실패한 커밋은 다시 시도하지 않는다"가 걸려서 손으로 한 번 동기화해야 했다.

ApplicationSet이 만든 Application에는 finalizer가 자동으로 붙는다.

```text
["resources-finalizer.argocd.argoproj.io"]
```

그래서 git에서 `envs/dev` 폴더를 지우면 ApplicationSet이 `shop-dev` Application을 지우고, finalizer 때문에 그 안의 리소스까지 지워진다. 실습에서도 폴더를 지운 지 몇 초 만에 `shop-dev`의 ConfigMap이 사라졌다(Namespace는 ArgoCD가 추적하는 리소스가 아니라 남았다). 생성기가 클러스터 목록이나 외부 API를 보고 있다면, 그 목록이 일시적으로 비는 것만으로 모든 환경이 지워질 수 있다. 운영에서는 ApplicationSet에 `syncPolicy.preserveResourcesOnDeletion: true`를 두거나, 컨트롤러를 `--policy create-update`로 띄워 ApplicationSet이 Application을 지우지 못하게 막는다.

<Callout kind="warning" title="ApplicationSet의 생성기가 비면 앱이 지워진다">
git 폴더 이름을 바꾸거나, 클러스터 생성기의 라벨 셀렉터를 고치거나, 외부 생성기(SCM, Pull Request)가 잠깐 빈 목록을 돌려주면 그만큼의 Application과 리소스가 지워진다. 처음 도입할 때는 `preserveResourcesOnDeletion: true`를 켜 두고, 지우는 동작은 사람이 확인한 뒤 따로 한다. 이미 지워졌다면 git을 되돌리고 ApplicationSet을 다시 동기화하면 Application은 다시 생기지만, PVC에 있던 데이터는 스토리지 클래스의 reclaimPolicy에 따라 돌아오지 않을 수 있다.
</Callout>

어느 쪽을 고를지는 앱들의 모양이 얼마나 같은지로 정한다. 환경마다, 클러스터마다 같은 구조가 반복되면 ApplicationSet이 맞다. 서비스마다 설정이 제각각이고 수가 적으면 app-of-apps가 읽기 쉽다. 둘을 섞어서 루트 앱이 ApplicationSet 몇 개를 배포하는 구성도 흔하다.

## ArgoCD가 이상할 때 보는 순서

현장에서 증상별로 어디부터 보는지 정리한다.

"머지했는데 배포가 안 된다"면 먼저 Application이 그 커밋을 봤는지 확인한다.

```bash
# 지금 비교한 커밋과 상태
kubectl -n argocd get application shop-api -o jsonpath='{.status.sync.revision}{"  "}{.status.sync.status}{"\n"}'
# 진행 중이거나 마지막 동기화 작업의 커밋과 메시지
kubectl -n argocd get application shop-api -o jsonpath='{.status.operationState.syncResult.revision}{"  "}{.status.operationState.phase}{"  "}{.status.operationState.message}{"\n"}'
```

첫 줄의 커밋이 옛것이면 새로 고침이 안 된 것이다(웹훅, 3분 주기, repo-server 접근). 두 번째 줄이 옛 커밋으로 `Running`이면 앞에서 본 재시도에 묶인 것이다.

"Synced인데 안 뜬다"면 건강 상태와 리소스 목록을 본다. `Progressing`에 오래 머무는 리소스가 범인이다. Deployment라면 `kubectl rollout status`와 Pod 이벤트로 넘어간다. 이 단계부터는 [Pod 문제 해결](/posts/k8s-pod-troubleshooting)의 영역이다.

"계속 OutOfSync인데 diff가 없어 보인다"면 기본값을 채우는 필드나 다른 컨트롤러가 바꾸는 필드가 원인이다. UI의 diff에서 그 필드를 확인하고 ignoreDifferences나 서버 쪽 apply로 푼다.

"아무것도 안 하는데 리소스가 바뀐다"면 selfHeal이 켜진 Application이 그 리소스를 관리하고 있는지 tracking-id 어노테이션부터 본다.

```bash
# 이 리소스를 어느 Application이 관리하나
kubectl -n shop get deploy shop-api -o jsonpath='{.metadata.annotations.argocd\.argoproj\.io/tracking-id}{"\n"}'
```

로그는 controller 쪽을 본다. `Skipping auto-sync:`로 시작하는 줄이 자동 동기화가 왜 안 움직였는지를 그대로 적어 준다. 실습에서 본 이유만 해도 `application status is Synced`, `need to prune extra resources only but automated prune is disabled`, `another operation is in progress`, `failed previous sync attempt to …` 넷이었다.

## git이 원본이라는 말의 범위

ArgoCD는 git에서 만든 매니페스트와 클러스터를 비교하는 controller 하나와 그 비교 대상을 만들어 주는 repo-server로 움직인다. 새로 고침은 비교를, 동기화는 적용을 한다. selfHeal은 클러스터 쪽 변화를, prune은 git에서 사라진 것을 맡는다. Synced는 적힌 대로 들어갔다는 뜻일 뿐이고, 잘 도는지는 건강 상태가 말한다. 그리고 git이 원본이라는 말은 "git에 없는 손 작업은 언제든 되돌려진다"는 뜻이기도 하다. 다음으로는 같은 일을 다른 방식으로 하는 Flux와 비교한 [GitOps 도구 비교](/posts/gitops-argocd-vs-flux)를 이어서 보면 좋다.

## 면접에서 나올 만한 질문

### ArgoCD의 refresh와 sync는 무엇이 다른가요?

refresh는 git과 클러스터를 다시 비교해 상태 표시만 바꾸고, sync는 그 차이를 클러스터에 실제로 적용한다. 기본적으로 git은 120초 주기에 최대 60초 지터를 더해 읽고, 웹훅을 걸면 푸시 즉시 새로 고친다. hard refresh는 repo-server의 매니페스트 캐시까지 무시하고 다시 렌더링하는 것으로, 같은 커밋인데 결과가 달라질 수 있을 때만 쓴다.

### Synced인데 서비스가 안 뜨는 건 어떻게 설명하나요?

동기화 상태와 건강 상태가 다른 질문이기 때문이다. Synced는 git의 매니페스트대로 객체가 들어갔다는 뜻이고, 그 객체가 제 역할을 하는지는 Healthy, Progressing, Degraded 같은 건강 상태가 말한다. Deployment라면 쿠버네티스가 남긴 Progressing·Available 조건을 읽어 판단하므로, 기한을 넘기면 Synced이면서 Degraded가 된다.

### selfHeal을 켜 두면 장애 중에 무엇을 조심해야 하나요?

kubectl로 replicas를 늘리거나 rollout undo를 하면 watch로 바로 감지되어 몇 초 안에 git 값으로 되돌아간다. 그래서 장애 대응은 git 커밋이나 git revert로 하고, 급하면 해당 Application의 자동 동기화를 잠시 끈다. HPA처럼 계속 바뀌는 필드는 git에서 빼거나 ignoreDifferences로 비켜 준다.

### ignoreDifferences만 넣었는데 동기화 때 값이 되돌아가는 이유는요?

ignoreDifferences는 비교에서만 그 필드를 빼고, 동기화할 때는 git의 매니페스트를 통째로 적용하기 때문이다. 실제로 replicas를 무시하게 해 둬도 다른 변경으로 동기화가 일어나자 2로 돌아갔다. 적용할 때도 live 값을 지키려면 `RespectIgnoreDifferences=true` 동기화 옵션을 함께 켠다.

### sync wave와 hook은 각각 언제 쓰나요?

hook은 동기화의 특정 단계에만 실행되는 리소스로, 마이그레이션 Job을 PreSync에, 스모크 테스트를 PostSync에 두는 식으로 쓴다. wave는 같은 단계 안의 순서로, 숫자가 작은 것부터 적용하고 앞 wave가 건강해질 때까지 기다린다. hook Job은 `hook-delete-policy`를 정해 두지 않으면 다음 동기화가 이름 충돌로 실패하고, 본 리소스 하나가 건강해지지 않으면 PostSync가 시작하지 않는다는 점을 같이 말한다.

### 고친 커밋을 올렸는데 ArgoCD가 계속 예전 커밋을 재시도하면 어떻게 하나요?

이미 시작한 동기화 작업은 그 커밋에 묶여 있어서 재시도를 다 쓸 때까지 새 커밋으로 넘어가지 않는다. 급하면 terminate-op으로 작업을 끊고 다시 동기화한다. 또 자동 동기화는 한 번 실패한 커밋을 다시 시도하지 않으므로, git 밖의 설정만 고쳤다면 손으로 한 번 동기화하거나 새 커밋을 올려야 한다.

### app-of-apps와 ApplicationSet은 어떻게 고르나요?

같은 구조가 환경이나 클러스터마다 반복되면 생성기로 찍어 내는 ApplicationSet이, 서비스마다 설정이 제각각이고 수가 적으면 Application YAML을 폴더에 두는 app-of-apps가 맞다. ApplicationSet이 만든 Application에는 리소스 finalizer가 붙어서, 생성기 결과에서 빠지면 리소스까지 지워진다. 그래서 운영에서는 `preserveResourcesOnDeletion`이나 `create-update` 정책으로 지우는 동작을 막아 둔다.

### AppProject는 무엇을 막아 주나요?

Application이 가져올 수 있는 저장소, 배포할 수 있는 클러스터와 네임스페이스, 만들 수 있는 리소스 종류를 제한한다. controller가 넓은 권한으로 돌기 때문에 이 울타리가 없으면 git에 쓸 수 있는 사람이 사실상 클러스터 관리자가 된다. 목적지가 어긋나면 Application 전체가 InvalidSpecError가 되고, 리소스 종류가 막히면 그 리소스만 SyncFailed가 된다.
