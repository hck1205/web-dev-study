캐시 서버가 4대였는데 메모리가 모자라 1대를 늘렸다. 배포가 끝나자마자 캐시 적중률이 95%에서 20%대로 떨어지고, 뒤에 있던 DB의 CPU가 100%를 찍었다. 캐시에 있던 데이터는 하나도 지워지지 않았다. 다만 대부분의 키가 "다른 서버에 있어야 한다"고 계산되면서, 앱이 엉뚱한 서버에 물어보고 비어 있으니 DB로 갔다. 서버를 늘렸을 뿐인데 캐시를 통째로 비운 것과 같은 일이 생겼다.

키를 서버에 나누는 방법으로서 일관된 해싱(consistent hashing)이 무엇이고, 해시 링 위에서 키가 시계 방향 첫 노드로 간다는 기본 그림은 [샤딩 글](/posts/db-sharding)에서 봤다. 이 글은 그 다음의 설계 질문을 다룬다. 가상 노드는 몇 개를 찍어야 하나, 링 말고 점프 해시나 랑데부 해싱은 언제 고르나, 로드 밸런서에서는 어떻게 쓰나, 운영하다 무엇이 깨지나. 숫자는 모두 이 글을 쓰면서 노드로 10만 개 키를 직접 나눠 잰 값이고, Nginx 예시는 Nginx 1.24에서 실제로 돌린 결과다.

## 나머지 연산이 키를 흩어 버린다

처음 장면의 앱은 `hash(key) % 서버 수`로 서버를 골랐다. 서버가 4대에서 5대가 되면 나누는 수가 바뀌니, 같은 키라도 나머지가 달라진다. 아래 그림은 키 여덟 개를 MD5로 해시해서 실제로 계산한 결과다. 칸을 따라가며 4대일 때와 5대일 때 서버가 어떻게 바뀌는지 보자.

키 10만 개로 재면 더 분명하다. 4대에서 5대로 늘리면 79.9%가, 10대에서 11대로 늘리면 90.7%가 다른 서버로 계산됐다. 새 서버가 맡아야 할 몫은 1/5(20%), 1/11(9.1%)뿐인데 나머지 이사는 기존 서버끼리 쓸데없이 주고받은 것이다. 서버가 하나 죽어서 빠질 때도 똑같다. 캐시라면 그만큼 미스가 나고, 샤딩된 DB라면 그만큼 데이터를 옮겨야 한다.

일관된 해싱의 목표는 하나다. 서버가 n대에서 n+1대가 되면 새 서버가 맡을 1/(n+1)만큼만 옮기고, 그 키는 모두 새 서버로 가게 하는 것. 해시 링은 이 목표를 이루는 여러 방법 중 첫 번째였을 뿐이다.

## 가상 노드는 몇 개를 찍나

링에 서버마다 점을 하나만 찍으면 구간 길이가 제각각이라 부하가 크게 갈린다. 그래서 서버 하나를 링 위 여러 자리에 찍는 가상 노드(vnode)를 쓴다는 것까지는 [샤딩 글](/posts/db-sharding)에서 봤다. 그럼 몇 개를 찍어야 할까. 서버 10대에 키 10만 개를 놓고 가상 노드 수만 바꿔 쟀다. 해시는 MD5 앞 4바이트다.

```text
vnodes   가장 적은 서버  가장 많은 서버  최대/평균  변동계수(CV)
     1          1,281          22,960      2.296       69.1%
    10          7,047          15,055      1.506       27.2%
   100          8,526          11,806      1.181        8.6%
  1000          9,790          10,329      1.033        1.6%
```

가상 노드가 하나면 가장 바쁜 서버가 평균의 2.3배를 받았다. 서버 용량은 가장 바쁜 서버에 맞춰 잡아야 하니, 10대를 사 놓고 4대 남짓의 값어치만 쓰는 셈이다. 100개면 최대가 평균의 1.18배, 1,000개면 1.03배까지 내려갔다. 변동계수가 대략 1/√(가상 노드 수)에 비례해서 줄어든다. 10배 찍으면 편차는 약 3분의 1이 된다.

공짜는 아니다. 링은 정렬된 배열이라 가상 노드가 많을수록 메모리를 더 먹고, 서버 목록이 바뀔 때마다 다시 만들고 정렬해야 한다. 서버 10대 × 1,000개는 1만 칸이라 문제가 안 되지만, 서버 수천 대 × 1,000개를 클라이언트마다 들고 있으면 이야기가 다르다. 그래서 실무 기본값은 100~200 언저리가 많다. Nginx의 `hash ... consistent`는 서버 가중치 1당 160개 점을 찍는다(ketama 방식). Cassandra는 노드마다 토큰을 여러 개 갖는 `num_tokens`가 있는데, 3.x까지 기본 256이었고 4.0부터 16으로 줄이면서 토큰 배치 알고리즘을 바꿨다. 토큰이 적으면 노드를 넣고 뺄 때 스트리밍 상대가 적어지고 복구 작업이 가벼워지기 때문이다.

가상 노드는 서버 성능 차이를 표현하는 손잡이이기도 하다. 메모리가 두 배인 서버에 가상 노드를 두 배로 찍으면 키도 두 배 받는다. Nginx에서 `server ... weight=2`가 바로 점을 320개 찍는 것이다.

서버를 더하고 뺄 때 옮긴 양도 쟀다.

```text
링(vnodes 1)    10 → 11대   14.0% 이사, 이사한 키의 100%가 새 서버로
링(vnodes 100)  10 → 11대   10.2% 이사, 이사한 키의 100%가 새 서버로
링(vnodes 100)  10 → 9대     9.5% 이사, 이사한 키의 100%가 빠진 서버의 것
이상적인 값     10 → 11대    1/11 = 9.1%
```

가상 노드가 하나일 때 14%가 옮긴 건 새 서버가 우연히 긴 구간에 떨어져 제 몫보다 많이 가져갔기 때문이다. 100개면 이론값 9.1%에 가깝다. 어느 경우든 기존 서버끼리 주고받은 키는 하나도 없다. 그리고 가상 노드에는 덜 알려진 장점이 하나 더 있다. 서버 하나가 빠지면, 점이 하나뿐인 링에서는 그 서버의 키가 전부 시계 방향 다음 서버 한 대에 몰린다. 가뜩이나 장애 상황인데 한 서버의 부하가 두 배가 된다. 가상 노드를 찍어 두면 빠진 서버의 구간들이 링 곳곳에 흩어져 있으니 남은 서버들이 나눠 받는다.

## 복제본은 링을 따라 다음 서버에 둔다

키를 한 서버에만 두면 그 서버가 죽을 때 데이터도 사라진다. Amazon Dynamo 논문 계열의 저장소(Cassandra, Riak 등)는 링에서 키의 자리부터 시계 방향으로 걸으며 만나는 서로 다른 서버 N대에 복제본을 둔다. 가상 노드가 있으면 같은 서버의 점을 연달아 만날 수 있으니 "서로 다른" 서버만 센다. 더 나아가 같은 랙이나 같은 가용 영역에 복제본이 몰리지 않게 건너뛰기도 한다(Cassandra의 `NetworkTopologyStrategy`).

## 링 말고 다른 방법들

링은 1997년 논문에서 웹 캐시 분산을 위해 나왔고 지금도 가장 흔하다. 하지만 가상 노드를 많이 찍어야 고르게 나뉘고 메모리를 쓴다는 약점 때문에 다른 방법들이 나왔다. 같은 조건(서버 10대, 키 10만 개)에서 쟀다.

점프 해시(jump consistent hash)는 2014년 구글이 낸 방법이다. 메모리를 전혀 안 쓰고 코드가 다섯 줄이다. 키를 시드로 난수를 뽑아, "버킷 수가 1, 2, 3, …으로 늘어날 때 이 키가 새 버킷으로 점프하는 순간"만 빠르게 건너뛰며 계산한다. 버킷이 b+1개가 될 때 키가 새 버킷으로 옮길 확률이 정확히 1/(b+1)이 되도록 만들어서, 고르게 나뉘고 옮기는 양도 최소다.

그림의 값은 `user:42`의 MD5 앞 8바이트로 실제 계산한 것이다. 버킷 수를 1부터 12까지 바꿔 가며 계산하면 이 키는 0, 1, 2, 2, 2, 5, 5, 5, 5, 9, 9, 11로 바뀐다. 바뀔 때는 항상 막 생긴 새 버킷으로만 간다. 측정 결과는 최대/평균 1.021, 10대에서 11대로 늘릴 때 9.3% 이사, 이사한 키는 전부 새 서버로 갔다.

코드는 논문의 C++ 다섯 줄을 그대로 옮기면 이렇다. 64비트 곱셈이 필요해서 자바스크립트에서는 `BigInt`를 쓴다.

```js
// key: 키를 64비트로 해시한 값(BigInt), n: 버킷 수 → 0..n-1
function jumpHash(key, n) {
  let k = BigInt.asUintN(64, key), b = -1, j = 0;
  while (j < n) {
    b = j;
    k = BigInt.asUintN(64, k * 2862933555777941757n + 1n);       // 선형 합동 난수
    j = Math.floor((b + 1) * (2 ** 31 / Number((k >> 33n) + 1n))); // 다음 점프 지점
  }
  return b;
}
```

루프는 점프 지점마다 한 번 돈다. 점프 지점 사이 간격이 갈수록 넓어져서, 버킷이 n개일 때 평균 ln n번쯤 돈다. 버킷 수가 1,000개여도 7번 남짓이다. 저장하는 게 없으니 서버 목록을 클라이언트에 나눠 줄 필요도 없고, 버킷 수 하나만 맞으면 어디서 계산해도 같은 답이 나온다.

네 방법의 분배를 한 표로 모으면 이렇다. 같은 키 10만 개, 서버 10대다.

```text
방법               가장 적은 서버  가장 많은 서버  최대/평균  10→11대 이사
hash % n                   -               -          -        90.7%
링(vnodes 100)          8,526          11,806      1.181        10.2%
링(vnodes 1000)         9,790          10,329      1.033            -
점프 해시               9,775          10,207      1.021         9.3%
랑데부                  9,896          10,110      1.011         9.1%
```

점프 해시의 제약은 버킷이 0부터 n−1까지 번호여야 한다는 것이다. 끝 번호를 늘리거나 줄이는 것만 된다. 중간의 4번 서버가 죽었다고 목록에서 빼면 뒤 번호가 한 칸씩 당겨지면서 69.1%가 이사했다. 마지막 서버를 뺄 때는 9.9%였다. 그래서 점프 해시는 서버가 아니라 "샤드 번호"를 고를 때 쓴다. 샤드 0~n−1은 고정이고, 각 샤드는 복제로 살아 있게 하는 구조(저장소 샤딩)에 잘 맞는다. 임의의 서버가 들고 나는 캐시 클러스터에는 맞지 않는다.

랑데부 해싱(rendezvous hashing, 최고 무작위 가중치 HRW)은 1996년에 나왔다. 키마다 서버 하나하나의 `hash(서버, 키)` 점수를 매기고 가장 높은 서버를 고른다. 서버가 빠지면 그 서버가 1등이던 키만 각자의 2등에게 가고, 서버가 들어오면 그 서버가 1등이 된 키만 옮긴다. 점수 순서대로 위에서 r개를 고르면 복제본 자리도 바로 나온다. 측정에서는 최대/평균 1.011로 가장 고르게 나뉘었고, 10대에서 11대는 9.1%, 중간 서버 하나를 빼도 10.0%만 옮겼다. 약점은 키마다 서버 수만큼 해시를 계산해야 한다는 것이다.

```text
조회 한 번에 걸린 시간 (노드 22, MD5 해시, 이 컨테이너 기준)
             서버 10대     서버 1,000대
링(vnode 100)  2.17 µs       1.82 µs
점프 해시      2.64 µs       2.68 µs
랑데부        23.20 µs     1688.69 µs
```

링과 점프 해시는 서버 수와 거의 상관없고, 랑데부는 서버 수에 정비례한다. 숫자 자체보다 기울기를 보면 된다. 서버가 수십 대 이하면 랑데부의 비용은 무시할 만하고 코드가 가장 단순하다. 서버가 수천 대면 서버를 묶어 계층을 만들거나 다른 방법을 쓴다.

로드 밸런서 쪽에는 Maglev 해싱도 있다. 구글이 자사 L4 로드 밸런서를 위해 만든 방법으로, 서버마다 정해진 순서로 칸을 채워 고정 크기 조회표(기본 65,537칸 같은 소수 크기)를 만든다. 조회는 표 한 칸 읽기라 아주 빠르고 고르게 나뉘지만, 서버가 바뀔 때 링보다 조금 더 많은 키가 옮긴다. Envoy는 `RING_HASH`와 `MAGLEV`를 둘 다 제공한다. 로드 밸런서에서의 선택은 [로드 밸런싱 알고리즘 글](/posts/load-balancing-algorithms)에서 다른 알고리즘들과 함께 비교한다.

## 로드 밸런서에서 같은 요청을 같은 서버로

일관된 해싱은 저장소만의 이야기가 아니다. 로드 밸런서가 같은 URL을 같은 백엔드로 보내면 백엔드의 로컬 캐시 적중률이 올라간다. 이미지 리사이저, 렌더링 캐시, 사용자별 세션을 메모리에 두는 서버가 그렇다. Nginx로 해 봤다. 백엔드 세 대 앞에 `hash $request_uri consistent;`를 두고 `/products/1`부터 `/products/1000`까지 요청한 뒤, 네 번째 백엔드를 넣고 설정을 다시 읽어 같은 요청을 반복했다.

```nginx
upstream app {
    hash $request_uri consistent;   # 같은 URI는 같은 서버로, ketama 링
    server 127.0.0.1:9101;
    server 127.0.0.1:9102;
    server 127.0.0.1:9103;
    server 127.0.0.1:9104;          # 두 번째 실행에서 추가
}
```

## 해시가 고르게 나눠도 남는 문제

일관된 해싱은 키 개수를 고르게 나눌 뿐, 요청량을 고르게 나누지는 않는다. 키 하나가 전체 요청의 30%를 받는 핫 키(인기 상품, 유명인의 프로필)는 어떤 해시 함수로도 한 서버에 간다. 그 서버만 CPU와 네트워크가 터진다. 핫 키는 해시가 아니라 다른 방법으로 다룬다. 앱 안에 몇 초짜리 로컬 캐시를 두거나, 키 뒤에 번호를 붙여(`product:7#0`~`#7`) 여러 서버에 복제해 두고 읽을 때 아무 데서나 읽는다. Redis에서 핫 키를 찾는 방법은 `redis-cli --hotkeys`(LFU 정책일 때)로 본다.

부하가 몰린 서버를 피하는 변형도 있다. 2016년 구글 연구진이 낸 consistent hashing with bounded loads는 서버마다 "평균의 1.25배" 같은 상한을 두고, 키가 간 서버가 상한을 넘으면 링의 다음 서버로 넘긴다. 요청 수가 고르게 맞춰지는 대신 같은 키가 늘 같은 서버로 가지는 않는다. HAProxy의 `hash-balance-factor`가 이 방식이다.

운영하다 실제로 깨지는 건 해시 자체보다 "모두가 같은 링을 보고 있나"다. 클라이언트 쪽에서 링을 계산하는 구조(예: memcached 클라이언트 라이브러리)에서 서비스 A는 서버 목록을 `cache-1, cache-2, cache-3`으로, 서비스 B는 IP 주소로 적었다면 둘의 링이 다르다. A가 쓴 키를 B는 다른 서버에서 찾는다. 해시 함수(MD5, CRC32, MurmurHash)나 가상 노드 수, 키 문자열 형식(`user:7`과 `user/7`)이 다른 라이브러리끼리도 마찬가지다. 언어가 다른 서비스가 같은 캐시를 쓴다면 같은 알고리즘인지 키 몇 개로 직접 맞춰 본다. 해시 함수나 가상 노드 수를 바꾸는 것도 사실상 전체 재배치라, 서버를 늘리는 것보다 훨씬 크게 흔들린다.

서버를 넣는 순간의 미스도 계획해야 한다. 옮긴 몫(10대에서 11대면 약 9%)만큼은 새 서버에서 미스가 나고 DB로 간다. 피크 시간을 피해 넣고, 한 번에 여러 대를 넣지 말고 하나씩 넣으며 DB 부하를 본다. 넣기 전에 새 서버를 미리 데우는 방법(옮겨 갈 키를 계산해 복사)도 있다. 처음 장면처럼 나머지 연산을 쓰고 있었다면, 일관된 해싱으로 바꾸는 그 배포 자체가 전체 재배치라는 점도 잊지 않는다.

Redis Cluster는 이 문제를 링 대신 16,384개 고정 슬롯과 슬롯 지도로 푼다. 키는 늘 같은 슬롯에 있고, 서버를 늘리면 슬롯 몇 개를 통째로 옮긴다. 어느 키가 옮기는지 사람이 정할 수 있다는 점이 링과 다르다. 이 방식은 [Redis Cluster 글](/posts/redis-cluster)에 있다.

## 옮길 키를 최소로

일관된 해싱은 서버가 n대에서 n+1대가 될 때 새 서버가 맡을 1/(n+1)만 옮기고 나머지는 건드리지 않는 성질이다. 해시 링은 그걸 가상 노드 수로 고르게 맞추고(100개면 최대가 평균의 1.18배, 1,000개면 1.03배), 점프 해시는 메모리 없이 번호형 샤드에, 랑데부는 서버가 많지 않을 때 가장 단순하게 같은 성질을 얻는다. 어느 쪽이든 핫 키와 "모든 클라이언트가 같은 링을 보는가"는 따로 챙긴다. 샤드 설계 전체에서 이 선택이 어디에 들어가는지는 [샤딩 글](/posts/db-sharding)을 다시 보면 된다.

## 면접에서 나올 만한 질문

### 일관된 해싱은 왜 필요한가요?

`hash % n`은 서버 수가 바뀌면 나누는 수가 바뀌어 키 대부분이 다른 서버로 계산된다. 실제로 4대에서 5대로 늘리면 79.9%, 10대에서 11대로 늘리면 90.7%가 옮겼다. 캐시라면 그만큼 미스가 나서 DB가 쓰러지고, 저장소라면 그만큼 데이터를 옮겨야 한다. 일관된 해싱은 새 서버가 맡을 1/(n+1)만 옮기고, 옮긴 키는 모두 새 서버로 가게 한다.

### 가상 노드는 왜 쓰고 몇 개가 적당한가요?

서버마다 점을 하나만 찍으면 구간 길이가 제각각이라 부하가 크게 갈린다. 10대에서 가장 바쁜 서버가 평균의 2.3배였고, 100개씩 찍으면 1.18배, 1,000개면 1.03배로 줄었다. 편차는 대략 1/√(가상 노드 수)로 줄고, 대가는 링 메모리와 재계산 비용이다. 보통 100~200개를 쓰고, 서버가 빠질 때 그 부하가 다음 서버 한 대에 몰리지 않고 흩어진다는 장점도 있다.

### 점프 해시와 해시 링은 어떻게 다른가요?

점프 해시는 메모리 없이 키와 버킷 수만으로 계산하고, 링보다 고르게 나뉜다. 대신 버킷이 0부터 n−1 번호라서 끝 번호를 늘리고 줄이는 것만 된다. 중간 서버를 빼면 번호가 당겨져 69%가 옮겼다. 그래서 고정된 샤드 번호를 고를 때 쓰고, 임의의 서버가 들고 나는 캐시에는 링이나 랑데부를 쓴다.

### 랑데부 해싱은 언제 고르나요?

서버가 수십 대 이하이고 단순한 구현을 원할 때다. 키마다 모든 서버의 점수를 매겨 1등을 고르니, 서버가 빠지면 그 서버가 1등이던 키만 2등에게 가고, 점수 순서대로 r개를 고르면 복제본 자리도 나온다. 조회 비용이 서버 수에 비례해서, 서버 1,000대에서는 링보다 수백 배 느렸다.

### 일관된 해싱을 써도 한 서버에 부하가 몰리는 이유는요?

키 개수는 고르게 나뉘어도 키마다 요청량이 다르기 때문이다. 핫 키 하나는 어떤 해시로도 한 서버에 간다. 로컬 캐시를 두거나 키를 여러 개로 복제해 읽기를 흩는다. 요청량 자체를 맞추려면 서버마다 상한을 두고 넘치면 다음 서버로 넘기는 bounded loads 방식을 쓴다.

### 로드 밸런서에서 일관된 해싱은 어디에 쓰나요?

같은 URL이나 같은 사용자를 같은 백엔드로 보내 백엔드의 로컬 캐시를 살릴 때 쓴다. Nginx는 `hash $request_uri consistent;`로 ketama 링을 쓰고, 백엔드를 하나 추가했을 때 1,000개 요청 중 224개만 옮겼다. `consistent`를 빼면 753개가 옮겼다. Envoy는 `RING_HASH`와 `MAGLEV`를 제공한다.

### 운영 중에 일관된 해싱이 깨지는 흔한 경우는요?

클라이언트마다 다른 링을 볼 때다. 서버 목록을 이름과 IP로 다르게 적거나, 해시 함수나 가상 노드 수가 다른 라이브러리를 섞으면 같은 키를 다른 서버에서 찾는다. 해시 함수나 가상 노드 수를 바꾸는 것 자체도 전체 재배치다. 언어가 다른 서비스끼리는 키 몇 개로 같은 서버가 나오는지 직접 맞춰 본다.
