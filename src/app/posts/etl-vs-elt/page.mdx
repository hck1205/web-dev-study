## 밤마다 통째로 복사하던 작업이 6시간을 넘겼다

처음에는 간단했다. 매일 새벽 1시에 운영 DB의 `orders` 테이블을 통째로 읽어 분석용 DB에 덮어썼다. 주문이 몇십만 건일 때는 10분이면 끝났다. 2년이 지나 행이 수억 건이 되자 작업이 6시간을 넘겼고, 아침 9시 리포트가 전날이 아니라 그 전날 숫자를 보여 주기 시작했다. 복사하는 동안 운영 DB의 디스크 읽기가 치솟아 새벽 주문 API도 느려졌다.

이 장면에 데이터 파이프라인의 기본 질문이 다 들어 있다. 무엇을 가져올지(추출), 어디서 모양을 바꿀지(변환), 어떻게 넣을지(적재), 그리고 실패했을 때 다시 돌려도 숫자가 맞는지. 이 글은 PostgreSQL 16을 원본, DuckDB 1.5를 분석용 저장소로 두고 이 네 가지를 직접 돌려 본다. 실험은 Ubuntu 24.04에서 했고, 주문 200만 건을 만들어 썼다.

```sql
-- 원본(PostgreSQL 16): 운영 서비스의 주문 테이블
CREATE TABLE orders (
  id          bigint PRIMARY KEY,
  user_id     bigint NOT NULL,
  status      text   NOT NULL,          -- paid / shipped / cancelled / refunded
  amount      numeric(12,2) NOT NULL,
  created_at  timestamptz NOT NULL,
  updated_at  timestamptz NOT NULL
);
CREATE INDEX orders_updated_at_idx ON orders (updated_at);
```

```text
  count  |          min           |          max
---------+------------------------+------------------------
 2000000 | 2026-01-01 00:00:10+00 | 2026-08-20 11:33:20+00
```

파이프라인 전체에서 이 글이 맡는 자리는 "원본 DB에서 분석 저장소까지 한 번 옮기는 일"이다. 옮긴 뒤의 대용량 처리는 [Spark 기초](/posts/spark-basics), 옮길 곳인 레이크는 [데이터 레이크와 HDFS](/posts/data-lake-hdfs), 매일 돌리는 순서와 백필은 [Airflow](/posts/airflow-orchestration), 이벤트 스트림을 실시간으로 쌓는 길은 [Kafka에서 레이크까지](/posts/kafka-to-lake-pipeline)에서 다뤘다.

## 추출, 변환, 적재를 어디서 하나

ETL(Extract, Transform, Load)은 원본에서 꺼내고, 별도 서버에서 모양을 바꾼 뒤, 웨어하우스에 넣는 순서다. 2000년대의 웨어하우스는 비싼 전용 장비였다. 저장 공간도 계산 능력도 아까워서, 깨끗하게 다듬은 결과만 넣고 지저분한 원본은 넣지 않았다. 변환은 Informatica 같은 ETL 도구나 직접 짠 스크립트가 웨어하우스 바깥에서 했다.

ELT는 순서만 바꾼다. 꺼낸 원본을 거의 그대로 웨어하우스에 먼저 넣고, 변환은 웨어하우스 안에서 SQL로 한다. BigQuery, Snowflake, Redshift 같은 클라우드 웨어하우스가 이걸 가능하게 했다. 저장은 객체 저장소라 싸고, 계산은 쓸 때만 빌리며, 컬럼 저장이라 큰 집계가 빠르다(컬럼 저장이 빠른 이유는 [컬럼형 분석 DB](/posts/db-type-columnar-olap)에 있다). 원본을 다 들고 있으니 변환 규칙이 바뀌면 다시 계산하면 된다. 변환 SQL은 dbt 같은 도구로 버전 관리하고 테스트한다.

아래 그림에서 두 길의 차이는 변환 상자가 어디 있느냐다. 점이 흐르는 방향이 데이터가 가는 방향이다.

ELT가 기본이 됐어도 ETL이 사라지지는 않았다. 웨어하우스에 들어가면 안 되는 값이 있으면 넣기 전에 걸러야 한다. 주민등록번호나 카드 번호처럼 분석에 필요 없는 개인정보는 추출 단계에서 빼거나 가린다. 일단 웨어하우스에 들어가면 접근 권한, 백업, 스냅샷까지 모두 그 값을 품게 된다([개인정보와 규정](/posts/data-privacy-compliance)). 이미지·로그처럼 SQL로 다루기 어려운 데이터, 웨어하우스로 보내기 전에 크기를 크게 줄여야 하는 데이터도 앞에서 처리한다. 실제 파이프라인은 대개 섞여 있다. 가볍게 가리고 형식만 맞춰(작은 T) 넣은 다음, 무거운 변환은 안에서 한다.

## 바뀐 것만 가져오기

통째로 복사하는 전체 추출은 단순하고 틀릴 일이 적다. 그 대신 테이블 크기에 비례해 느려진다. 바뀐 행만 가져오는 증분 추출은 "지난번에 어디까지 가져왔나"를 기억해 두고 그 뒤만 읽는다. 기억해 두는 값을 워터마크라고 부르고, 가장 흔한 기준은 `updated_at`이다.

하루 동안 주문 5000건이 환불됐다고 치고 두 방식으로 CSV를 내려 봤다.

```sql
-- 하루치 변경: 400건에 1건꼴로 환불 처리
UPDATE orders
SET status = 'refunded',
    updated_at = timestamptz '2026-08-21 09:00+00' + (id % 3600 || ' seconds')::interval
WHERE id % 400 = 0;
```

```bash
# 전체 추출: 테이블 전부
psql -d shop -c "\copy (SELECT id,user_id,status,amount,created_at,updated_at FROM orders) TO 'full.csv' CSV HEADER"
# 증분 추출: 지난 워터마크 이후만
psql -d shop -c "\copy (SELECT id,user_id,status,amount,created_at,updated_at FROM orders WHERE updated_at > '2026-08-21 00:00+00') TO 'inc.csv' CSV HEADER"
ls -la full.csv inc.csv   # 파일 크기 비교
```

```text
COPY 2000000
Time: 3332.695 ms (00:03.333)
COPY 5000
Time: 8.306 ms

-rw-r--r-- 1 root root 149784703 Oct 24 09:57 full.csv
-rw-r--r-- 1 root root    381073 Oct 24 09:57 inc.csv
```

같은 서버 안이라 3.3초와 8밀리초였다. 네트워크를 건너 수억 건이면 앞쪽이 몇 시간이 되고 뒤쪽은 그대로 몇 초다. 증분 추출이 빠른 이유는 `updated_at` 인덱스 덕분이다.

```sql
EXPLAIN SELECT id,user_id,status,amount,created_at,updated_at
FROM orders WHERE updated_at > '2026-08-21 00:00+00';
```

```text
                                        QUERY PLAN
------------------------------------------------------------------------------------------
 Index Scan using orders_updated_at_idx on orders  (cost=0.43..100.79 rows=2535 width=45)
   Index Cond: (updated_at > '2026-08-21 00:00:00+00'::timestamp with time zone)
```

`Index Scan`과 `Index Cond` 줄을 본다. 이 줄이 `Seq Scan`으로 바뀌어 있으면 인덱스가 없거나 조건이 인덱스를 못 타는 모양이다(`updated_at::date > ...`처럼 컬럼을 감싸면 그렇게 된다). `rows=2535`는 추정치고 실제로는 5000건이다. 방금 고친 행이라 통계가 아직 따라오지 못했다.

증분 추출에는 전제가 셋 있다. 모든 쓰기가 `updated_at`을 빠짐없이 갱신해야 한다(앱 코드 한 곳이라도 빼먹으면 그 변경은 영영 안 온다. 트리거로 강제하는 편이 안전하다). 행을 물리적으로 지우지 않아야 한다. 그리고 "지난번 워터마크 이후"가 정말로 지난번 이후의 변경을 다 담아야 한다. 마지막 전제가 생각보다 쉽게 깨진다.

## 늦게 커밋된 주문이 빠진다

PostgreSQL의 `now()`는 트랜잭션이 시작한 시각을 돌려준다. 오래 걸리는 트랜잭션이 `updated_at = now()`로 행을 고치면, 커밋은 나중에 해도 값은 시작 시각으로 남는다. 그 사이에 추출이 돌아 워터마크를 더 뒤로 올려 버리면 그 행은 다음 추출에서도 안 잡힌다. 두 세션으로 재현했다.

```bash
W=$(psql -d shop -Atc "select now()")            # 이번 추출의 시작 워터마크
# 세션 A: 주문 7을 고치고 4초 뒤에 커밋하는 긴 트랜잭션
psql -d shop -c "BEGIN; UPDATE orders SET status='shipped', updated_at=now() WHERE id=7; SELECT pg_sleep(4); COMMIT;" &
sleep 1
# 세션 B: 주문 8을 고치고 바로 커밋
psql -d shop -c "UPDATE orders SET status='shipped', updated_at=now() WHERE id=8"
sleep 1
# 1회차 추출
psql -d shop -c "SELECT id, status, updated_at FROM orders WHERE updated_at > '$W' ORDER BY updated_at"
```

```text
 id | status  |          updated_at
----+---------+-------------------------------
  8 | shipped | 2026-10-24 09:57:40.435763+00
(1 row)
```

1회차는 주문 8만 봤고, 워터마크를 40.435초로 올렸다. A가 커밋한 뒤의 2회차와 실제 테이블은 이렇다.

```text
--- 2회차: updated_at > '2026-10-24 09:57:40.435763+00'
 id | status | updated_at
----+--------+------------
(0 rows)

--- 실제 테이블
 id | status  |          updated_at
----+---------+-------------------------------
  7 | shipped | 2026-10-24 09:57:39.456823+00
  8 | shipped | 2026-10-24 09:57:40.435763+00
```

주문 7은 39.456초로 적혀 있어 2회차 워터마크보다 작다. 이 행은 다음 날에도, 그다음 날에도 안 온다. 웨어하우스에는 주문 7이 계속 `paid`로 남는다. 같은 구멍을 CDC 쪽에서 순서도로 그린 그림은 [CDC 글](/posts/cdc-change-data-capture)에 있다.

메우는 방법은 두 가지를 같이 쓴다. 하나는 겹쳐 읽기다. 다음 추출을 `updated_at > 워터마크 - 10분`처럼 조금 앞에서 시작한다. 2회차를 이렇게 바꾸면 주문 7과 8이 둘 다 나온다. 8은 두 번째로 오지만, 뒤에서 볼 upsert로 적재하면 중복이 생기지 않는다.

```text
 id | status  |          updated_at
----+---------+-------------------------------
  7 | shipped | 2026-10-24 09:57:39.456823+00
  8 | shipped | 2026-10-24 09:57:40.435763+00
(2 rows)
```

겹치는 폭을 몇 분으로 할지는 감으로 정하기 어렵다. 그래서 다른 하나로, 워터마크를 올릴 상한을 "지금"이 아니라 "아직 열려 있는 가장 오래된 트랜잭션의 시작 시각"으로 묶는다. 그보다 앞의 변경은 모두 커밋됐거나 롤백됐으니 안전하다.

```sql
-- 이번 추출이 워터마크를 어디까지 올려도 되나
SELECT now() AS now,
       (SELECT min(xact_start) FROM pg_stat_activity
         WHERE backend_type = 'client backend'
           AND xact_start IS NOT NULL
           AND pid <> pg_backend_pid()) AS oldest_open_xact;
```

```text
              now              |       oldest_open_xact
-------------------------------+-------------------------------
 2026-10-24 10:00:31.873158+00 | 2026-10-24 10:00:30.875855+00
```

추출은 `updated_at > 지난 워터마크 AND updated_at <= least(now, oldest_open_xact)` 구간만 읽고, 다음 워터마크를 그 상한으로 둔다. 이 방법은 원본에 `pg_stat_activity`를 볼 권한이 있어야 하고, 읽기 복제본에서 추출하면 주 DB의 열린 트랜잭션이 보이지 않는다는 한계가 있다. 그래서 실무에서는 겹쳐 읽기와 upsert를 기본으로 깔고, 상한 묶기는 할 수 있으면 더한다. `updated_at`을 DB의 `now()`가 아니라 앱 서버 시계로 채우는 경우는 더 나쁘다. 서버마다 시계가 몇 초씩 어긋나서([시계 차이](/posts/clock-skew)) 같은 구멍이 더 넓게 열린다.

## 지워진 행은 updated_at으로 못 찾는다

증분 추출의 두 번째 구멍은 삭제다. `DELETE`된 행은 테이블에서 사라지니 어떤 `WHERE`로도 찾을 수 없다. 웨어하우스에는 지워진 주문이 계속 남아 매출에 더해진다.

선택지는 세 가지다. 원본에서 행을 지우지 않고 `deleted_at`을 채우는 소프트 삭제로 바꾸면 삭제도 `updated_at`이 바뀌는 수정이 된다. 원본을 바꿀 수 없으면 주기적으로 키 목록만 통째로 비교해 웨어하우스에서 사라진 키를 지운다. 키만 읽으니 전체 추출보다 훨씬 가볍다. 셋째가 CDC(Change Data Capture)다. DB가 이미 적고 있는 변경 로그(PostgreSQL의 WAL, MySQL의 binlog)를 읽으니 삭제도, 늦게 커밋된 변경도, 한 행이 1분에 세 번 바뀐 중간 상태도 놓치지 않는다. 그 대신 복제 슬롯 관리와 스키마 변경 대응 같은 운영 부담이 생긴다.

정리하면 추출 방식은 이렇게 고른다. 작은 테이블(수십만 행 이하)이나 코드 테이블은 매번 전체 추출이 가장 단순하고 안전하다. 큰 테이블이고 몇 시간 늦어도 되면 `updated_at` 증분에 겹쳐 읽기, 그리고 가끔 키 비교를 더한다. 삭제와 중간 상태가 중요하거나 몇 초 안에 따라와야 하면 CDC로 간다.

## 스테이징에 원본 그대로 내려놓는다

꺼낸 데이터는 바로 최종 테이블에 넣지 않는다. 먼저 스테이징(staging)이라는 중간 칸에 원본 모양 그대로 내려놓는다. 이렇게 하면 적재가 실패해도 원본 DB를 다시 읽을 필요가 없고, 변환 규칙이 바뀌면 스테이징부터 다시 계산하면 된다. 레이크를 쓰면 날짜별 경로(`raw/orders/dt=2026-08-21/`)에 파일로 두는 것이 스테이징이다.

스테이징에서 가장 흔한 실수는 타입을 추측에 맡기는 것이다. DuckDB에 CSV를 그냥 읽히면 컬럼 타입을 알아서 정한다.

```sql
-- DuckDB: 타입 추측에 맡겨 읽기
DESCRIBE SELECT * FROM read_csv('full.csv');
```

```text
┌─────────────┬──────────────────────────┐
│ column_name │       column_type        │
├─────────────┼──────────────────────────┤
│ id          │ BIGINT                   │
│ user_id     │ BIGINT                   │
│ status      │ VARCHAR                  │
│ amount      │ DOUBLE                   │
│ created_at  │ TIMESTAMP WITH TIME ZONE │
│ updated_at  │ TIMESTAMP WITH TIME ZONE │
└─────────────┴──────────────────────────┘
```

원본에서 `numeric(12,2)`였던 금액이 `DOUBLE`이 됐다. 이 상태로 하루 매출을 더하면 이렇게 나온다.

```text
┌───────────┬───────────────────┐
│  status   │      revenue      │
│  varchar  │      double       │
├───────────┼───────────────────┤
│ cancelled │         4345884.8 │
│ paid      │         4347825.6 │
│ refunded  │           31780.0 │
│ shipped   │ 4345855.199999999 │
└───────────┴───────────────────┘
```

`4345855.199999999`는 부동소수점 오차다. 리포트에서 반올림하면 안 보이지만, 정산 시스템과 원 단위로 맞춰 보는 날 차이가 난다. 금액은 스키마를 직접 적어 `DECIMAL`로 받는다.

```sql
-- 타입을 명시해서 스테이징에 올린다
CREATE OR REPLACE TABLE ods_orders AS
SELECT * FROM read_csv('full.csv', header = true, columns = {
  'id': 'BIGINT', 'user_id': 'BIGINT', 'status': 'VARCHAR',
  'amount': 'DECIMAL(12,2)', 'created_at': 'TIMESTAMPTZ', 'updated_at': 'TIMESTAMPTZ'
});
ALTER TABLE ods_orders ADD PRIMARY KEY (id);
```

시간대도 같은 종류의 함정이다. `CAST(created_at AS DATE)`는 세션 시간대 기준으로 날짜를 자른다. 같은 테이블, 같은 쿼리를 시간대만 바꿔 돌렸다.

```sql
SET TimeZone = 'UTC';         -- 다음엔 'Asia/Seoul'로 바꿔서 한 번 더
SELECT count(*) AS orders, sum(amount) AS revenue
FROM ods_orders WHERE CAST(created_at AS DATE) = DATE '2026-03-01';
```

```text
-- TimeZone = 'UTC'
┌────────┬───────────────┐
│ orders │    revenue    │
├────────┼───────────────┤
│   8640 │   13071345.60 │
└────────┴───────────────┘
-- TimeZone = 'Asia/Seoul'
┌────────┬───────────────┐
│ orders │    revenue    │
├────────┼───────────────┤
│   8640 │   12965713.60 │
└────────┴───────────────┘
```

주문이 10초에 하나씩 고르게 생겨서 건수는 같지만 날짜 경계가 9시간 밀려 매출이 10만 원 넘게 다르다. 한국 서비스의 "3월 1일 매출"은 보통 한국 시각 기준이다. 변환 SQL의 시간대를 고정하고, 날짜 컬럼을 만들 때 어느 시간대 기준인지 이름이나 문서에 남긴다(`order_date_kst`).

## 다시 돌려도 숫자가 같게 적재하기

파이프라인은 반드시 다시 돈다. 네트워크가 끊겨 재시도하고, 버그를 고쳐 지난주를 다시 계산하고, 위에서 본 겹쳐 읽기 때문에 같은 행이 두 번 온다. 몇 번을 돌려도 결과가 같은 성질을 멱등성이라고 하고, 적재 방식이 이걸 정한다.

가장 단순한 추가(append)는 받은 것을 뒤에 붙인다. 같은 증분 파일을 두 번 넣으면 이렇게 된다.

```sql
CREATE OR REPLACE TABLE raw_append AS SELECT * FROM read_csv('inc.csv', ...);
INSERT INTO raw_append SELECT * FROM read_csv('inc.csv', ...);   -- 재시도로 한 번 더
SELECT count(*) AS rows, count(DISTINCT id) AS ids FROM raw_append;
```

```text
┌───────┬───────┐
│ rows  │ ids   │
├───────┼───────┤
│ 10000 │  5000 │
└───────┴───────┘
```

추가는 원본 이벤트 로그처럼 "받은 기록 자체"를 남기는 칸에만 쓴다. 대신 읽는 쪽에서 키별로 최신 한 줄만 고르는 변환을 둔다.

현재 상태를 담는 테이블은 upsert로 넣는다. 키가 있으면 고치고 없으면 넣는다. 여기서 조건 하나가 중요하다. 더 새로운 버전일 때만 덮어써야 한다. 겹쳐 읽기와 재처리 때문에 오래된 버전이 나중에 도착할 수 있다.

```sql
-- DuckDB 1.5. PostgreSQL도 같은 문법이다
INSERT INTO ods_orders SELECT * FROM stg
ON CONFLICT (id) DO UPDATE SET
  status = excluded.status,
  amount = excluded.amount,
  updated_at = excluded.updated_at
WHERE excluded.updated_at > ods_orders.updated_at;   -- 더 새로울 때만
```

같은 증분 파일로 두 번 돌려도 `ods_orders`는 200만 건 그대로였다. MySQL 8은 `INSERT ... ON DUPLICATE KEY UPDATE`를 쓰고 `WHERE`를 붙일 수 없어서 `status = IF(VALUES(updated_at) > updated_at, VALUES(status), status)`처럼 컬럼마다 조건을 건다(8.0.20부터는 `VALUES()` 대신 행 별칭을 권한다). BigQuery·Snowflake에서는 `MERGE` 문이 같은 일을 한다.

아래에서 직접 짜 볼 수 있다. 대상 테이블과 새 묶음을 받아, 같은 `id`면 `updatedAt`이 더 클 때만 바꾸고 결과를 `id` 순으로 돌려준다. 같은 묶음을 두 번 넣어도, 오래된 버전이 뒤늦게 와도 결과가 같아야 한다.

넷째 테스트가 실제로 자주 걸린다. 한 묶음 안에 같은 키가 여러 번 있으면 SQL의 `MERGE`는 "대상 한 행에 원본 여러 행이 맞는다"며 실패하는 경우가 많다(BigQuery, Snowflake 기본 설정이 그렇다). 그래서 적재 전에 스테이징에서 키별 최신 한 줄만 남기는 `ROW_NUMBER() OVER (PARTITION BY id ORDER BY updated_at DESC) = 1` 단계를 둔다.

집계 테이블처럼 날짜별로 다시 계산하는 결과는 파티션 덮어쓰기로 넣는다. 그날 것을 지우고 새로 넣는 일을 한 트랜잭션으로 묶는다.

```sql
BEGIN;
DELETE FROM fct_daily_sales WHERE dt = DATE '2026-08-19';
INSERT INTO fct_daily_sales
SELECT CAST(created_at AS DATE), status, count(*), sum(amount)
FROM ods_orders
WHERE CAST(created_at AS DATE) = DATE '2026-08-19'
GROUP BY ALL;
COMMIT;
```

같은 날짜로 세 번 돌렸고 세 번 모두 `4행, 주문 8640건, 매출 12780905.60`이 나왔다. 지우고 넣는 사이에 읽는 쪽이 빈 날짜를 보지 않으려면 트랜잭션이 필요하다. 레이크의 파일 테이블이라면 Delta Lake·Iceberg의 `replaceWhere`나 동적 파티션 덮어쓰기가 같은 역할을 한다. Airflow에서 실행 하나가 자기 데이터 구간만 지우고 다시 쓰게 만드는 것도 이 방식이다.

## 원본 스키마가 바뀐 날

원본 팀이 `orders`에 `coupon_code` 컬럼을 추가했다. PostgreSQL의 `ADD COLUMN`은 맨 끝에 붙으니 `SELECT *`로 내린 CSV에 컬럼이 하나 늘었다. 적재 SQL이 어떻게 반응하는지 몇 가지 써 봤다.

```text
INSERT INTO ods_orders SELECT * FROM read_csv('new.csv')
→ Binder Error: table ods_orders has 6 columns but 7 values were supplied

INSERT INTO ods_orders BY NAME SELECT * FROM read_csv('new.csv')
→ Binder Error: Table "ods_orders" does not have a column with name "coupon_code"
```

시끄럽게 실패하는 쪽은 차라리 낫다. 새벽에 알림이 오고 고치면 된다. 위험한 쪽은 조용히 틀리는 경우다. 원본 팀이 `amount`를 `total_amount`로 이름을 바꿨고, 레이크의 날짜별 파일을 이름 기준으로 합쳐 읽는다고 해 보자.

```sql
-- d1.csv는 옛 이름(amount), d2.csv는 새 이름(total_amount)
SELECT * FROM read_csv('lake/*.csv', union_by_name = true) ORDER BY id;
```

```text
┌───────┬─────────┬──────────────┐
│  id   │ amount  │ total_amount │
│ int64 │ double  │    double    │
├───────┼─────────┼──────────────┤
│     1 │ 1000.37 │         NULL │
│     2 │ 1000.74 │         NULL │
│     3 │    NULL │      1001.11 │
│     4 │    NULL │        999.0 │
└───────┴─────────┴──────────────┘
```

오류는 없다. `sum(amount)`는 새 파일의 금액을 전부 빼고 2001.11 남짓을 돌려준다. 다음 날 매출이 반토막인데 파이프라인은 초록불이다. 이런 종류는 적재 뒤의 품질 검사(행 수, 금액 합, 널 비율이 평소와 비슷한가)로 잡는다. 어떤 검사를 어디에 두는지는 [데이터 품질 검사](/posts/data-quality-checks)에서 따로 다룬다.

스키마 변경에 덜 깨지려면 이렇게 한다. 추출은 `SELECT *`가 아니라 컬럼 이름을 적는다. 그러면 이름이 바뀐 날 원본 쪽에서 "column does not exist"로 바로 실패한다. 컬럼 추가는 받아들이되(스테이징은 넓게, 이벤트라면 스키마 레지스트리의 호환성 규칙으로, [스키마 버전 관리](/posts/schema-versioning)), 이름 변경과 타입 변경은 원본 팀과 미리 약속한 절차로만 한다. 이 약속을 문서와 검사로 만든 것이 데이터 계약이다.

## 끌어오기와 밀어 넣기

지금까지는 적재 작업이 원본에 가서 데이터를 끌어왔다(pull). 수집 구조는 반대 방향도 있다. 원본 서비스가 변경이 생길 때마다 이벤트를 내보내고(push), 수집 쪽은 받아서 쌓는다. 웹훅, 서비스가 Kafka에 직접 쓰는 이벤트, CDC 커넥터가 Kafka로 내보내는 변경 로그가 여기 속한다.

끌어오기는 수집 쪽이 주도권을 쥔다. 언제 얼마나 읽을지 정하고, 실패하면 같은 구간을 다시 읽으면 된다. 원본 서비스 팀은 아무것도 안 해도 된다. 그 대신 원본 DB에 조회 부하를 주고(그래서 읽기 복제본에서 읽는다), 실행 간격만큼 늦고, 앞에서 본 삭제·늦은 커밋 구멍이 있다.

밀어 넣기는 변경이 생긴 순간 나가니 늦지 않고, 원본 DB를 따로 조회하지 않는다. 그 대신 받는 쪽이 멈추면 보낸 이벤트를 어딘가에 쌓아 둬야 해서 Kafka 같은 버퍼가 사이에 들어간다. 같은 이벤트가 두 번 오거나 순서가 바뀌어 오는 일도 받는 쪽이 처리해야 한다. 이벤트 형식은 원본 팀이 정하니 형식을 바꿀 때의 약속이 더 중요해진다. 이 길은 [Kafka에서 레이크까지](/posts/kafka-to-lake-pipeline)에서 따라갔다.

현장에서는 둘이 섞인다. 주문·회원 같은 핵심 테이블은 CDC로 밀어 넣고, 광고 플랫폼이나 결제사 같은 외부 SaaS는 그쪽 API를 주기적으로 끌어온다(Fivetran, Airbyte 같은 관리형 수집 도구가 이 커넥터들을 대신 만들어 둔다). 앱 클릭 로그는 SDK가 수집 서버로 밀어 넣는다.

## 웨어하우스 안에서 변환하면 드는 비용

ELT가 편해진 만큼 다른 비용이 생긴다. 먼저 돈이다. 클라우드 웨어하우스는 쿼리가 읽은 양이나 쓴 계산 시간으로 요금을 매긴다. 변환 SQL 하나가 원본 전체를 매일 다시 읽게 짜여 있으면, 데이터가 늘수록 청구서가 조용히 커진다. 변환도 증분으로 만들고(dbt의 incremental 모델처럼 바뀐 날짜 파티션만 다시 계산), 날짜 파티션과 클러스터링으로 읽는 범위를 줄인다.

다음은 거버넌스다. 원본을 다 넣어 두니 누가 무엇을 볼 수 있는지 관리할 범위가 넓어진다. 개인정보 컬럼이 raw 칸에 그대로 있으면 raw 테이블 접근 권한 하나로 전부 열린다. 그래서 추출 단계에서 가리거나, raw 칸은 파이프라인 계정만 읽게 하고 분석가는 정제된 칸만 보게 나눈다. 변환 SQL이 수백 개가 되면 어느 테이블이 어디서 왔는지(데이터 계보) 추적하는 일도 따로 필요하다.

마지막은 SQL로 하기 어려운 변환이다. 복잡한 파싱, 외부 API 호출, 머신러닝 전처리는 웨어하우스 SQL로 억지로 쓰기보다 Spark나 Python 작업으로 빼는 편이 낫다. "ELT냐 ETL이냐"보다 "이 변환은 어디서 하는 게 싸고 다시 돌리기 쉬운가"를 변환마다 따지는 게 실제 판단에 가깝다.

## 재처리를 미리 설계해 둔다

변환 버그가 발견됐다. 지난 3주 동안 환불 주문을 매출에서 빼지 않았다. 이때 할 수 있는 일은 파이프라인이 처음에 어떻게 설계됐느냐로 정해진다.

스테이징에 원본이 남아 있으면 변환만 고쳐서 3주치 날짜를 다시 계산하면 된다. 각 날짜가 파티션 덮어쓰기로 적재되니 몇 번 돌려도 숫자가 같고, Airflow의 백필로 날짜 범위를 한 번에 돌린다. 원본을 보관하지 않았다면 운영 DB를 다시 읽어야 하는데, 운영 DB에는 지금 모습만 있어서 3주 전 그날의 상태는 이미 없다.

그래서 처음부터 세 가지를 지킨다. 원본은 지우지 않고 날짜별로 보관한다(용량이 걱정되면 오래된 것은 싼 저장 등급으로 옮긴다). 모든 적재 단계를 날짜 구간을 받아 그 구간만 다시 쓰는 멱등한 단위로 만든다. 변환 코드 버전과 실행 기록을 남겨, 어느 날짜가 어느 버전으로 계산됐는지 안다.

## 새벽 적재가 늦거나 숫자가 비면

알림이 오면 단계 순서대로 좁혀 간다.

먼저 추출이 돌았는지, 몇 건을 가져왔는지 본다. 평소 5000건인데 0건이면 원본 쪽 문제(권한, 접속, 워터마크가 미래로 튄 경우)다. 워터마크가 이상하게 크면 앱 서버 시계로 `updated_at`을 채운 행이 섞였는지 본다.

```sql
-- 원본에서: 미래 시각으로 찍힌 행이 있나
SELECT count(*), max(updated_at) FROM orders WHERE updated_at > now();
```

추출 건수가 평소의 수십 배면 원본에서 대량 백필이나 일괄 수정이 있었던 것이다. 이때 적재가 몇 시간씩 늘어나니, 원본 팀의 일괄 작업 일정을 미리 공유받는 편이 낫다.

추출은 정상인데 웨어하우스 숫자가 이상하면 적재 방식을 본다. 중복이면 append로 재시도된 흔적이 있는지(`count(*)`와 `count(DISTINCT id)` 비교), 일부 날짜가 비었으면 덮어쓰기가 지우기만 하고 넣기 전에 실패한 것은 아닌지 본다. 특정 주문만 상태가 틀리면 늦은 커밋이나 삭제 구멍을 의심하고, 원본과 웨어하우스의 키 목록을 그 날짜 범위로 비교한다.

## 어디서 바꾸든, 다시 돌릴 수 있게

ETL과 ELT의 차이는 변환을 웨어하우스 바깥에서 하느냐 안에서 하느냐다. 클라우드 웨어하우스가 싸고 빨라지면서 원본을 먼저 넣고 안에서 SQL로 바꾸는 쪽이 기본이 됐다. 어느 쪽이든 오래 버티는 파이프라인은 같은 모양이다. 바뀐 것만 겹쳐서 가져오고, 원본 그대로 스테이징에 남기고, 더 새로울 때만 덮어쓰거나 날짜 단위로 통째로 다시 써서 몇 번을 돌려도 숫자가 같게 만든다. 이렇게 옮긴 데이터를 어떤 칸으로 나눠 쌓을지는 [데이터 웨어하우스 설계](/posts/data-warehouse-architecture)에서 이어 간다.

## 면접에서 나올 만한 질문

### ETL과 ELT는 무엇이 다르고, 요즘 ELT가 많이 쓰이는 이유는?

변환을 적재 전에 웨어하우스 바깥에서 하면 ETL, 원본을 먼저 넣고 웨어하우스 안에서 SQL로 하면 ELT다. 클라우드 웨어하우스가 저장과 계산을 분리해 저장은 싸고 계산은 필요할 때만 빌리게 됐고, 컬럼 저장이라 큰 변환도 빠르다. 원본을 다 갖고 있으니 규칙이 바뀌면 다시 계산하면 된다. 다만 개인정보처럼 웨어하우스에 들어가면 안 되는 값은 여전히 적재 전에 처리한다.

### updated_at 기반 증분 추출에서 데이터가 빠지는 경우는?

두 가지가 대표적이다. 하나는 늦게 커밋된 트랜잭션이다. PostgreSQL의 `now()`는 트랜잭션 시작 시각이라, 긴 트랜잭션이 고친 행은 커밋 시점보다 이른 시각으로 남고 그 사이 워터마크가 올라가면 다음 추출에서 빠진다. 다른 하나는 물리 삭제로, 지운 행은 어떤 조건으로도 찾을 수 없다. 앱이 `updated_at`을 갱신하지 않는 경로가 있어도 빠진다.

### 늦은 커밋 문제는 어떻게 막나?

겹쳐 읽기와 멱등한 적재를 같이 쓴다. 지난 워터마크보다 몇 분 앞에서 읽기 시작하고, 다시 온 행은 더 새로울 때만 덮어쓰는 upsert로 넣는다. 더 정확하게는 워터마크 상한을 열려 있는 가장 오래된 트랜잭션의 시작 시각으로 묶는다. 근본적으로는 커밋 순서대로 변경 로그를 읽는 CDC로 간다.

### 적재를 멱등하게 만드는 방법은?

현재 상태 테이블은 키 기준 upsert로, 그리고 더 새로운 버전일 때만 덮어쓰게 조건을 건다. 날짜별 집계처럼 다시 계산하는 결과는 그 구간을 지우고 다시 넣는 파티션 덮어쓰기를 한 트랜잭션으로 한다. 단순 append는 재시도하면 중복이 생기니 원본 기록 보관용에만 쓰고, 읽는 쪽에서 키별 최신 행을 고른다. 워터마크는 적재가 성공한 뒤에 올린다.

### 원본 스키마가 바뀌면 파이프라인의 어디가 깨지나?

컬럼 추가는 `SELECT *`로 위치 기반 적재를 하면 컬럼 수가 안 맞아 실패한다. 이름 변경은 이름 기준으로 합쳐 읽으면 오류 없이 옛 컬럼이 NULL이 되어 숫자가 조용히 틀린다. 타입 변경은 형 변환에서 실패하거나 정밀도를 잃는다. 추출은 컬럼을 명시해 시끄럽게 실패하게 하고, 적재 뒤에 행 수·합계·널 비율 검사를 둬서 조용한 실패를 잡는다.

### ELT의 단점은?

쿼리 스캔량이나 계산 시간으로 과금되니 변환이 매번 전체를 다시 읽으면 비용이 데이터 크기만큼 커진다. 원본을 다 넣으니 개인정보와 접근 권한을 관리할 범위가 넓어지고, 변환 SQL이 늘면 계보 추적이 어려워진다. SQL로 표현하기 어려운 변환은 오히려 복잡해진다. 증분 변환, 파티션 설계, 칸별 권한 분리로 완화한다.

### 끌어오는(pull) 수집과 밀어 넣는(push) 수집은 언제 고르나?

pull은 수집 쪽이 주도하니 단순하고 재처리가 쉽지만, 원본에 부하를 주고 실행 간격만큼 늦으며 삭제를 놓치기 쉽다. push는 변경 즉시 나가 지연이 짧지만, 중간 버퍼와 중복·순서 처리, 원본 팀과의 형식 약속이 필요하다. 외부 SaaS나 몇 시간 늦어도 되는 테이블은 pull, 핵심 테이블의 변경을 빨리 따라가야 하면 CDC 같은 push를 고른다.

### 3주치 변환 버그를 고쳐 재처리해야 한다면?

원본이 스테이징이나 레이크에 날짜별로 남아 있다면 변환을 고친 뒤 그 날짜 범위를 백필로 다시 돌린다. 각 날짜 적재가 파티션 덮어쓰기라 몇 번 돌려도 결과가 같다. 원본을 보관하지 않았다면 운영 DB에는 현재 상태만 있어 과거 상태를 복원할 수 없다. 그래서 원본 보관, 날짜 단위 멱등 적재, 변환 버전 기록을 처음부터 설계에 넣는다.
