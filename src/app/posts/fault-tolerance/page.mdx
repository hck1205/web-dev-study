검색 서버 세 대가 1초 안에 전부 죽었다. 트래픽이 몰린 것도 아니고 배포를 한 것도 아니다. 로그를 거꾸로 따라가 보니 세 서버가 마지막으로 받은 요청이 똑같았다. 검색창에 `c:\`를 친 사용자 한 명의 요청이었다. 앞단 프록시가 "첫 서버가 죽었으니 다음 서버에 보내자"를 두 번 한 결과, 버그 하나가 서버 세 대로 옮겨 갔다.

서버를 여러 대 둔 이유는 한 대가 고장 나도 서비스가 버티게 하려는 것이었다. 그런데 고장의 원인이 서버가 아니라 요청 안에 있으면, 여러 대는 같은 고장을 여러 번 겪을 뿐이다. 내결함성(fault tolerance)은 부품 안에서 생긴 결함이 서비스 전체의 장애로 번지지 않게 하는 성질이다. 이 글은 고장을 종류별로 나누고, 그 고장을 가리는 법과 가두는 법을 직접 재현하면서 따라간다.

실험은 Ubuntu 24.04에서 네트워크 네임스페이스로 만든 작은 구성(클라이언트, Node로 짠 프록시, 검색 서버 세 대)과 Node 22 스크립트로 한다. 네임스페이스를 엮는 방법은 [고가용성](/posts/high-availability) 글의 실험실과 같다.

이 주제의 다른 글: 서버를 몇 대 두고 어떻게 나란히 세우는지는 [고가용성](/posts/high-availability), 타임아웃·재시도·서킷 브레이커·벌크헤드·폴백을 하나씩 붙이는 법은 [장애가 번지지 않게](/posts/resilience-patterns)에서 다룬다. 서킷 브레이커의 내부는 [서킷 브레이커 안쪽](/posts/circuit-breaker), 고장을 일부러 넣어 보는 실험은 [카오스 엔지니어링](/posts/chaos-engineering)에 있다.

## 검색어 하나가 서버 세 대를 차례로 죽였다

검색 서버의 토크나이저에는 버그가 하나 있다. 역슬래시 다음 글자를 이스케이프로 읽는데, 검색어가 역슬래시로 끝나면 "다음 글자"가 없다.

```js
// search-backend.js 일부
function tokenize(q) {
  const out = []; let cur = "";
  for (let i = 0; i < q.length; i++) {
    if (q[i] === "\\") { const next = q[i + 1]; cur += next.toLowerCase(); i++; continue; } // q가 "\"로 끝나면 next는 undefined
    if (q[i] === " ") { out.push(cur); cur = ""; } else cur += q[i].toLowerCase();
  }
  out.push(cur);
  return out;
}
http.createServer((req, res) => {
  const q = new URL(req.url, "http://x").searchParams.get("q") ?? "";
  setImmediate(() => { const t = tokenize(q); res.end(`${name} ${t.join(",")}`); }); // 콜백 안에서 던진 예외는 프로세스를 죽인다
}).listen(8080);
```

앞단 프록시는 백엔드가 실패하면 다음 백엔드로 다시 보낸다. 실패의 종류는 가리지 않는다. 클라이언트는 100ms마다 정상 검색(`red shoes`)을 보내고, 1.5초에 `c:\`를 한 번, 3초에 한 번 더 보낸다.

```bash
# 검색 서버 세 대 (10.71.0.11, .12, .13)
sudo ip netns exec sd1a node search-backend.js a &
sudo ip netns exec sd1b node search-backend.js b &
sudo ip netns exec sd1x node search-backend.js c &
# 프록시 (10.71.0.2): 실패하면 종류와 상관없이 다음 서버로
sudo ip netns exec sd1lb node proxy.js retry-all &
# 클라이언트
sudo ip netns exec sd1c node qclient.js
```

## 결함이 장애가 되기까지

이 사고를 설명하려면 말을 셋으로 나눠야 한다. 신뢰성 분야에서 오래 쓰여 온 구분(Avižienis, Laprie 등의 분류)이다.

- 결함(fault): 고장의 원인. 여기서는 토크나이저의 경계 검사 누락이다. 코드에 들어 있어도 그 줄이 실행되기 전까지는 아무 일도 없다.
- 오류(error): 결함이 실행되어 생긴 잘못된 상태. `next`가 `undefined`인 채로 메서드를 부른 순간이다.
- 장애(failure): 바깥에서 본 서비스가 약속한 동작을 벗어난 사건. 사용자가 502를 받은 것이다.

이 사슬은 층을 따라 올라간다. 검색 서버 a의 장애는 검색 서비스 입장에서는 결함 하나다. 서비스가 그 결함을 가리지 못하면 서비스의 장애가 되고, 검색을 부르는 상품 페이지 입장에서는 또 하나의 결함이 된다.

이 구분이 쓸모 있는 이유는, 끊을 수 있는 자리가 화살표마다 다르기 때문이다. 결함 자체를 없애는 건 테스트와 리뷰의 몫이다. 결함이 실행돼도 오류로 번지지 않게 하는 건 입력 검증의 몫이다. 오류가 생겨도 그 요청 하나에서 멈추게 하는 건 격리의 몫이다. 부품의 장애가 서비스의 장애가 되지 않게 하는 건 이중화와 우회의 몫이다. 내결함성은 마지막 두 화살표, 즉 "결함은 언젠가 실행된다"를 받아들이고 그다음을 설계하는 일이다.

## 무엇이 어떻게 고장 나는지 먼저 정한다

"고장에 강하다"는 말은 어떤 고장을 견디는지 정해야 뜻이 생긴다. 분산 시스템에서는 이것을 장애 모델(failure model)이라고 부르고, 흔히 이렇게 나눈다. 아래로 갈수록 다루기 어렵다.

- 크래시 정지(crash-stop): 멈추고 다시 돌아오지 않는다. 멈추기 전까지는 올바르게 동작한다.
- 크래시 복구(crash-recovery): 멈췄다가 다시 돌아온다. 메모리는 잃고 디스크에 남긴 것만 남는다. 재시작한 프로세스가 이 경우다.
- 누락(omission): 살아 있지만 일부 메시지를 보내지 않거나 받지 않는다. 패킷 손실, 꽉 찬 큐가 그렇다.
- 타이밍(timing): 답은 맞는데 너무 늦다. GC 멈춤, 디스크 지연, 과부하가 그렇다. 바깥에서는 누락과 구별이 안 된다.
- 비잔틴(Byzantine): 틀린 답을 낸다. 거짓말을 하거나, 사람마다 다른 말을 한다. 메모리 비트가 뒤집힌 서버, 버그가 있는 버전, 악의적인 노드가 이 경우다.

이 구분이 바로 "몇 대가 필요한가"를 정한다. 결함 f개를 견디려면 대략 이렇다.

- 크래시만 있고 죽은 걸 확실히 알 수 있다면 f+1대. 하나라도 살아 있으면 된다. 프라이머리와 스탠바이 구성이 이 가정을 쓴다.
- 크래시에 네트워크 분할까지 있으면 2f+1대. 죽음과 끊김을 구분할 수 없으니 과반이 동의해야 결정한다. Raft와 etcd가 3대로 1대, 5대로 2대를 견디는 이유다([Raft 합의](/posts/raft-consensus), [네트워크 분할](/posts/network-partitions)).
- 비잔틴까지 견디는 합의는 3f+1대. 거짓말하는 f대가 정직한 쪽을 둘로 갈라 놓지 못하게 하려면 그만큼 필요하다는 것이 1982년 Lamport 등의 결과다. 블록체인 합의와 항공기 제어 같은 곳 말고는 비용 때문에 잘 쓰지 않는다.

실무에서 흔한 실수는 크래시 정지를 가정하고 설계한 시스템이 타이밍 장애를 만나는 경우다. 느린 서버는 죽은 서버처럼 빠지지 않고, 요청을 계속 받아 붙잡고 있는다. 앞의 사고는 반대 방향의 실수다. 프록시는 "백엔드가 죽었다"를 서버의 크래시로 해석했지만, 실제로는 모든 서버에 똑같이 들어 있는 결함, 일종의 공통 원인 고장이었다.

## 같은 것을 여러 벌 두는 세 가지 방법

결함을 가리는(masking) 방법은 결국 여분을 두는 것이다. 무엇을 여러 벌 두느냐에 따라 셋으로 나뉜다.

- 공간 여분: 같은 부품을 여러 대 둔다. 서버, 디스크(RAID), 복제본.
- 시간 여분: 같은 일을 한 번 더 한다. 재시도와 재전송이다. 일시적인 결함(패킷 하나 손실, 잠깐의 과부하)에만 통한다.
- 정보 여분: 데이터에 검사용 정보를 덧붙인다. 체크섬, 패리티, ECC 메모리, 오류 정정 부호.

정보 여분은 비잔틴 결함 중 가장 흔한 것, 즉 조용히 바뀐 데이터를 잡는 유일한 방법이다. 주문 레코드의 비트 하나를 뒤집어 봤다.

```js
// redundancy.js: 같은 레코드 세 벌, 그중 하나의 비트 하나를 뒤집는다
const record = Buffer.from(JSON.stringify({ orderId: 1042, amount: 39000, currency: "KRW" }));
const copies = [Buffer.from(record), Buffer.from(record), Buffer.from(record)];
const at = record.indexOf("39000"); copies[1][at] ^= 0b00000100; // "3"(0x33) -> "7"(0x37)
const sum = (b) => zlib.crc32(b).toString(16).padStart(8, "0");   // Node 22의 zlib.crc32
```


비트 하나가 39,000원을 79,000원으로 바꿨다. JSON은 여전히 올바른 형식이라 파서는 아무 말도 하지 않는다. 체크섬이 없었다면 이 값은 그대로 결제로 넘어갔을 것이다. 체크섬은 어느 사본이 틀렸는지 알려 주고(검출), 세 벌 중 다수결은 맞는 값을 골라 준다(정정). 아래 그림에서 다음을 누르면 사본을 하나씩 검사한다.

같은 원리가 여러 층에 있다. ECC 메모리는 워드마다 여분 비트를 붙여 비트 하나가 뒤집히면 고치고 둘이 뒤집히면 알린다. TCP 체크섬은 16비트라 약해서, 중요한 데이터는 응용 계층에서 따로 해시를 붙여 검증하는 일이 많다. 저장소 쪽에서는 블록마다 체크섬을 두고 읽을 때 검사하는 파일 시스템과 DB가 있고, 복제본끼리 해시를 비교해 어긋난 곳을 찾는 방법은 [머클 트리](/posts/merkle-tree)에서 다룬다.

공간 여분과 다수결을 섞은 고전적인 구성이 삼중 모듈 이중화(TMR)다. 같은 계산을 세 대가 하고 다수결로 결과를 고른다. 한 대가 틀린 답을 내도 가려진다. 대신 세 대가 같은 코드를 돌리면 앞의 검색 사고처럼 셋이 똑같이 틀린다. 소프트웨어 결함을 가리려면 사본끼리 다르게 만들어야 하는데(다른 구현, 다른 버전, 다른 입력 순서), 비용이 커서 일반 서비스에서는 거의 하지 않는다. 대신 다음 두 절의 방법, 즉 빨리 멈추게 하기와 가두기를 쓴다.

## 고장 난 것은 빨리, 조용히 멈추게

틀린 답을 내며 계속 도는 서버보다 아예 멈춘 서버가 다루기 쉽다. 멈춘 서버는 헬스 체크가 잡아내고 로드 밸런서가 빼지만, 틀린 답을 내는 서버는 아무도 모른다. 그래서 내결함성 설계는 비잔틴 결함을 크래시 결함으로 바꾸려고 한다. 이것을 빠른 실패(fail-fast)라고 한다. 상태가 이상하다고 판단되면 그 자리에서 멈춘다.

- 시작할 때 설정을 검증하고, 틀리면 기동하지 않는다. 틀린 설정으로 반쯤 도는 것보다 낫다.
- 불변식이 깨지면(재고가 음수, 잔액 합이 안 맞음) 예외를 던지고 그 작업을 멈춘다.
- 메모리가 한도에 닿거나 이벤트 루프가 오래 막히면 스스로 죽는다.

빨리 멈추게 했으면 다시 띄우는 쪽이 있어야 한다. Erlang이 "let it crash"라는 말로 퍼뜨린 구조로, 일하는 프로세스와 감시하는 프로세스(슈퍼바이저)를 나눈다. 일하는 쪽은 예외를 다 처리하려 애쓰지 않고 죽고, 슈퍼바이저가 깨끗한 상태로 다시 띄운다. 크래시 복구 결함으로 바꾸는 셈이다. 쿠버네티스의 kubelet, systemd의 `Restart=on-failure`, Node의 PM2가 같은 역할이다.

그런데 재시작은 일시적인 결함에만 통한다. 고장의 원인이 설정이나 데이터에 있다면 몇 번을 띄워도 같은 자리에서 죽는다. 그래서 슈퍼바이저는 "얼마 동안 몇 번까지 다시 띄울지"를 정해 두고, 그걸 넘으면 포기하고 위로 알린다. 직접 짜서 두 가지 결함을 넣어 봤다. 5초 안에 3번까지 다시 띄우는 설정이다.

```js
// supervisor.js 일부
const MAX = 3, WINDOW = 5000;
child.on("exit", (code) => {
  if (code === 0) return console.log(`${t()} pid=${child.pid} finished normally`);
  const now = Date.now();
  restarts.push(now);
  while (restarts.length && now - restarts[0] > WINDOW) restarts.shift();
  if (restarts.length > MAX) return console.log(`${t()} ${restarts.length} crashes within ${WINDOW}ms > ${MAX}: give up, escalate`);
  setTimeout(start, 200);
});
```

## 직접 짜 보기: 언제 재시작을 포기하나

## 결함을 가두는 칸

빨리 멈추게 하는 것만으로는 앞의 검색 사고를 못 막는다. 멈춘 범위가 너무 넓었기 때문이다. 검색어 하나의 결함이 요청 하나가 아니라 프로세스 전체를 멈췄고, 그 프로세스에 들어 있던 다른 요청들까지 함께 실패했다. 결함이 퍼질 수 있는 범위를 결함 격리 영역(fault containment region)이라 하고, 이것을 얼마나 작게 자르느냐가 피해 반경을 정한다.

가장 작은 칸은 요청 하나다. 검색 서버가 요청마다 예외를 잡아 그 요청만 500으로 끝내게 바꿨다. 프록시는 뒤 절에서 볼 `retry-connect` 설정, 즉 연결을 맺지 못한 경우에만 다른 서버로 다시 보내는 설정이다.

```js
// search-backend.js safe 모드
setImmediate(() => {
  try { const t = tokenize(q); res.end(`${name} ${t.join(",")}`); }
  catch (e) { console.log(`${name} request failed: ${e.message}`); res.statusCode = 500; res.end(`${name} error`); }
});
```

```text
normal+poison summary ok=49 fail=2
```

결함은 그대로인데 장애의 크기가 달라졌다. `c:\` 요청 두 개만 실패하고(프록시가 백엔드의 500을 502로 바꿔 돌려준다), 정상 검색 49건은 전부 성공했다. 서버는 하나도 죽지 않았다.

칸은 여러 크기로 자를 수 있다. 큰 칸일수록 격리가 확실하지만 비용이 크다.

- 요청: try/catch, Promise 거부 처리, 요청별 타임아웃. 가장 싸지만 메모리 오염이나 무한 루프는 못 막는다. Node에서 이벤트 루프를 막는 무한 루프는 같은 프로세스의 모든 요청을 멈춘다.
- 프로세스와 스레드 풀: 일을 종류별로 다른 프로세스나 풀에 나눠, 한 종류가 자원을 다 써도 다른 종류는 돈다. 이것이 벌크헤드(bulkhead)다([장애가 번지지 않게](/posts/resilience-patterns)).
- 컨테이너와 노드: 메모리와 CPU 한도를 cgroup으로 건다. 한 파드의 메모리 누수가 노드의 다른 파드를 OOM으로 끌고 가지 않게 한다.
- 셀: 서비스 전체를 작은 사본(셀) 여러 벌로 나누고 사용자를 셀에 나눠 담는다. 한 셀이 망가져도 그 셀의 사용자만 겪는다([멀티 리전](/posts/multi-region)의 셀 기반 구조).

셀처럼 고객을 나눠 담을 때 쓰는 영리한 방법이 셔플 샤딩(shuffle sharding)이다. 고정된 칸에 나누는 대신, 고객마다 일꾼 중 몇 개를 무작위로 골라 준다. AWS가 Route 53 같은 서비스에서 쓴다고 Amazon Builders' Library에 공개한 방법이다. 일꾼 8개, 고객 1000명에서 독이 든 요청을 보내는 고객 하나가 자기 일꾼을 모두 죽인다고 하고 피해를 세어 봤다.

```js
// shuffle.js 일부: 고정 샤드는 일꾼 2개씩 4묶음, 셔플 샤드는 고객마다 일꾼 2개를 무작위로
const tenants = Array.from({ length: T }, (_, i) => ({ id: i, shard: i % 4, pair: pick2() }));
```

```text
$ node shuffle.js
no isolation : 999/999 other tenants fully down
fixed shards : 249/999 fully down (24.9%)
shuffle shard: 30/999 fully down (3.0%), 417 lost one of two workers
theory: C(8,2)=28, fully down 1/28=3.6%, partial 12/28=42.9%
```

격리가 없으면 모두가 죽는다. 고정 샤드면 같은 묶음에 든 4분의 1이 죽는다. 셔플 샤드면 일꾼 두 개를 정확히 똑같이 받은 고객만, 이론상 28분의 1(시뮬레이션 3.0%)만 완전히 멈춘다. 일꾼 하나만 겹친 42% 남짓은 남은 일꾼 하나로 계속 돌아간다. 이 효과를 보려면 클라이언트가 자기 일꾼 중 하나가 실패할 때 다른 하나로 다시 보낼 수 있어야 한다. 그런데 바로 그 재시도가 앞의 사고를 만들었다. 다음 절이 그 이야기다.

## 다시 보내는 것이 결함을 퍼뜨릴 때

재시도는 시간 여분이다. 패킷이 하나 사라졌거나 서버가 잠깐 바빴다면, 다시 보내면 된다. 하지만 결함이 요청 안에 있으면 다시 보내는 건 결함을 다른 서버에 배달하는 일이다. 그래서 재시도 전에 "이 실패가 어디서 났나"를 가려야 한다.

- 연결을 맺지 못했다(`ECONNREFUSED`, connect 타임아웃): 요청이 서버에 닿지 않았다. 다른 서버로 보내도 안전하다.
- 요청을 보낸 뒤 연결이 끊겼다(`ECONNRESET` after send): 서버가 요청을 받고 죽었을 수 있다. 요청이 원인일 수 있고, 일부가 실행됐을 수도 있다.
- 서버가 5xx로 답했다: 서버는 살아 있고 그 요청을 처리하지 못했다.

프록시를 연결 단계 실패만 다시 보내게(`retry-connect`) 바꾸고, 같은 실험을 다시 했다. 그다음엔 "요청을 받은 서버를 죽인 요청"을 기억해 두고 같은 요청이 다시 오면 백엔드에 보내지 않고 바로 거절하는 격리(`quarantine`)를 더했다.

```text
# node proxy.js retry-connect
$ awk 'NR<=4 || /summary/' client.log
08:08:37.955 POISON 502 bad gateway
08:08:39.462 POISON again 502 bad gateway
normal+poison summary ok=49 fail=2
$ grep -v "red%20shoes" proxy.log
proxy retry-connect
08:08:37.953 /search?q=c%3A%5C -> c failed: ECONNRESET (after send)
08:08:39.461 /search?q=c%3A%5C -> a failed: ECONNRESET (after send)
$ for f in be-a be-b be-c; do kill -0 $(cat $f.pid) 2>/dev/null && echo "$f alive" || echo "$f dead"; done
be-a dead
be-b alive
be-c dead

# node proxy.js quarantine
$ awk 'NR<=4 || /summary/' client.log
08:08:47.608 POISON 502 bad gateway
08:08:49.095 POISON again 422 quarantined
normal+poison summary ok=48 fail=2
$ grep -v "red%20shoes" proxy.log
proxy quarantine
08:08:47.606 /search?q=c%3A%5C -> b failed: ECONNRESET (after send)
08:08:49.094 /search?q=c%3A%5C quarantined -> 422
$ for f in be-a be-b be-c; do kill -0 $(cat $f.pid) 2>/dev/null && echo "$f alive" || echo "$f dead"; done
be-a alive
be-b dead
be-c alive
```

연결 단계만 재시도하자 독이 든 요청 하나가 서버 하나만 죽였다. 정상 검색은 모두 성공했다. 죽은 서버로 가던 정상 요청은 연결 거절을 받고 살아 있는 서버로 다시 갔기 때문이다. 다만 같은 사용자가 같은 검색어를 다시 치자 또 한 대(a)가 죽었다. 격리를 더하자 두 번째 요청은 백엔드에 닿기 전에 422로 끝났고, 서버는 한 대만 잃었다.

이 격리는 단순화한 것이다. 실제로는 요청 전체가 아니라 특징(경로, 특정 파라미터, 사용자)으로 묶어야 하고, 정상 요청이 우연히 서버가 죽는 순간에 걸렸을 수도 있으니 한 번이 아니라 여러 서버에서 반복될 때 격리하는 편이 안전하다. 그리고 격리는 시간 제한을 두고 풀어야 한다. 원인을 고친 배포가 나간 뒤에도 그 검색어를 영원히 막으면 안 된다. 근본 해결은 물론 토크나이저를 고치는 것이다. 격리는 고치기 전까지 버티는 장치다.

재시도의 나머지 조건, 즉 멱등성과 재시도 예산, 지수 백오프는 [재시도는 공짜가 아니다](/posts/retries)와 [지수 백오프와 지터](/posts/exponential-backoff-jitter)에서 자세히 다룬다.

## 다 못 하면 덜 한다

모든 결함을 가릴 수는 없다. 가릴 수 없을 때 남은 선택지는 서비스 전체를 멈추는 것과 일부 기능만 포기하는 것이다. 뒤쪽을 우아한 성능 저하(graceful degradation)라고 부른다. 검색이 죽었을 때 상품 페이지 전체가 500을 내는 대신, 검색창만 회색으로 두고 카테고리 탐색은 그대로 보여 주는 식이다.

이 결정은 장애가 나기 전에 해 둬야 한다. 기능마다 "이게 없으면 서비스가 의미 없나"를 묻고 등급을 나눈다. 결제와 로그인은 핵심이고, 추천과 리뷰 개수와 최근 본 상품은 없어도 된다. 핵심이 아닌 의존성은 실패했을 때 빈 값이나 캐시된 옛 값, 기본값을 돌려주도록 미리 짜 둔다. 그리고 그 경로를 평소에 실제로 타 봐야 한다. 한 번도 실행된 적 없는 폴백 코드는 그 자체가 결함일 가능성이 크다.

부하가 원인일 때도 같은 원리다. 서버가 감당할 수 있는 양을 넘으면 비싼 기능부터 끈다. 기능 플래그로 추천 호출을 끄고([기능 플래그](/posts/feature-flags)), 넘치는 요청은 빨리 거절해 남은 요청이라도 제시간에 처리한다([백프레셔](/posts/backpressure)). 폴백과 부하 차단을 코드로 붙이는 방법은 [장애가 번지지 않게](/posts/resilience-patterns)의 "안 되면 덜 보여 주기"에 있다.

## 서버들이 줄줄이 재시작할 때 보는 순서

여러 서버가 짧은 간격으로 차례로 죽거나 재시작한다면, 원인이 서버 밖에서 들어오고 있다는 신호다. 서버 하나하나의 결함이라면 동시에 일어날 이유가 없다.

먼저 죽은 시각을 나란히 놓는다. 쿠버네티스라면 재시작 횟수와 마지막 종료 사유를 본다.

```bash
# 파드별 재시작 횟수와 마지막 종료 사유
kubectl get pods -l app=search -o custom-columns='NAME:.metadata.name,RESTARTS:.status.containerStatuses[0].restartCount,REASON:.status.containerStatuses[0].lastState.terminated.reason,AT:.status.containerStatuses[0].lastState.terminated.finishedAt'
# 죽기 직전 로그 (이전 컨테이너)
kubectl logs search-7c9f-abcde --previous --tail=50
```

간격이 수 ms에서 수 초라면 같은 요청이 옮겨 다니는 경우를 의심한다. 다음으로 각 서버가 죽기 직전에 받은 요청을 찾는다. 요청을 받을 때 한 줄, 끝날 때 한 줄을 찍어 두면, "시작은 있는데 끝이 없는 요청"이 범인 후보다. 앞단 프록시나 LB의 접근 로그에서 같은 요청 ID가 여러 백엔드로 간 기록이 있으면 재시도가 결함을 옮긴 것이다.

```bash
# 시작 로그는 있고 끝 로그가 없는 요청 ID (로그 형식은 서비스마다 다르다)
comm -23 <(grep -o 'start req=[0-9a-f]*' app.log | cut -d= -f2 | sort) \
         <(grep -o 'end req=[0-9a-f]*' app.log | cut -d= -f2 | sort)
```

범인을 찾았으면 순서대로 막는다. 앞단 재시도를 연결 단계로 줄이고, 그 요청 유형을 WAF나 게이트웨이에서 잠시 막고, 그다음 코드를 고친다. 반대로 재시작 간격이 일정하고(예: 정확히 몇 분마다) 서버마다 따로 논다면 메모리 누수나 주기 작업이 원인일 가능성이 크다. 이때는 [메모리 누수](/posts/js-memory-leak)나 OOM 기록부터 본다.

<Callout kind="warning">
독이 든 요청을 재현하려고 운영 서버에 그 요청을 다시 보내면 서버를 또 하나 죽인다. 재현은 격리된 환경에서 하고, 운영에서는 해당 요청을 먼저 막은 뒤 로그로만 확인한다.
</Callout>

## 결함은 막는 게 아니라 가둔다

결함은 언젠가 실행된다. 내결함성은 그 결함이 어떤 모양으로 나타날지(크래시, 누락, 지연, 틀린 값) 먼저 정하고, 그 모양에 맞는 여분을 둔 뒤, 결함이 퍼질 수 있는 칸을 작게 자르는 일이다. 틀린 값은 체크섬과 다수결로 잡고, 이상한 상태는 빨리 멈춰서 크래시로 바꾸고, 재시작은 한도를 둬서 고쳐지지 않는 결함을 위로 올리고, 재시도는 결함이 요청 안에 있을 수 있다는 걸 의심한다. 여기까지 와도 남는 결함은 기능을 덜어 내서 버틴다. 이 장치들이 실제로 동작하는지는 고장을 일부러 넣어 봐야 안다([카오스 엔지니어링](/posts/chaos-engineering)).

## 면접에서 나올 만한 질문

### 결함, 오류, 장애는 어떻게 다른가요?

결함은 원인(코드의 버그, 뒤집힌 비트), 오류는 결함이 실행되어 생긴 잘못된 내부 상태, 장애는 바깥에서 본 서비스가 약속한 동작을 벗어난 사건이다. 아래 부품의 장애는 위 시스템의 결함이 된다. 내결함성은 결함이 장애로 이어지는 사슬을 중간에서 끊는 설계다.

### 고가용성과 내결함성은 어떻게 다른가요?

고가용성은 쓸 수 있는 시간의 비율이라는 결과이고, 내결함성은 부품이 고장 나도 서비스가 올바르게 동작하는 성질이다. 빠른 장애 조치로 몇 초 멈췄다 돌아오는 구성은 가용성은 높지만 그 몇 초 동안은 결함을 가리지 못했다. 반대로 내결함성이 높아도 결함이 모두 같은 원인에서 오면(같은 버그) 가용성이 무너진다.

### 장애 모델에 따라 필요한 노드 수가 왜 달라지나요?

크래시만 있고 죽은 걸 확실히 안다면 f+1대 중 하나만 살아도 된다. 네트워크 분할이 있으면 죽음과 끊김을 구분할 수 없어 과반이 동의해야 하므로 2f+1대가 필요하다. 거짓말하는 비잔틴 노드까지 견디는 합의는 3f+1대가 필요하다. 그래서 Raft 클러스터는 3대로 1대, 5대로 2대의 크래시를 견딘다.

### 요청 하나가 서버 여러 대를 연달아 죽였습니다. 원인과 대책은요?

결함이 서버가 아니라 요청 안에 있고, 앞단의 재시도가 그 요청을 다른 서버로 옮긴 경우다. 대책은 요청을 보낸 뒤의 실패는 재시도하지 않게 줄이고, 서버를 죽인 요청을 기억해 다시 오면 문 앞에서 거절하는 것이다. 서버 안에서는 요청마다 예외를 잡아 그 요청만 실패시켜 결함의 범위를 요청 하나로 줄인다.

### 슈퍼바이저가 재시작 한도를 두는 이유는 뭔가요?

재시작은 일시적인 결함에만 통하고, 설정이나 데이터에 원인이 있는 결함은 몇 번을 띄워도 같은 자리에서 죽는다. 한도 없이 다시 띄우면 자원과 로그를 태우면서 문제를 감춘다. 일정 시간 안에 몇 번 넘게 죽으면 포기하고 위 층에 알려, 배포를 되돌리는 것 같은 다른 조치를 하게 한다. 쿠버네티스는 포기 대신 대기를 늘리는 백오프를 쓴다.

### 체크섬은 어떤 결함을 막나요? TCP에도 체크섬이 있는데 왜 또 두나요?

조용히 바뀐 데이터, 즉 형식은 멀쩡한데 값이 틀린 결함을 잡는다. 비트 하나가 금액 39000을 79000으로 바꿔도 JSON은 유효하니 파서는 모른다. TCP 체크섬은 16비트라 약하고 구간마다 끝나므로, 저장과 전송 전체를 지나는 데이터에는 응용 계층에서 해시를 따로 붙여 끝에서 끝까지 검증한다. 사본이 셋 있으면 다수결로 맞는 값을 골라 고칠 수도 있다.

### 셔플 샤딩은 무엇이고 왜 고정 샤딩보다 낫나요?

고객마다 일꾼 몇 개를 무작위 조합으로 주는 격리 방법이다. 고정 샤드는 같은 묶음의 고객이 모두 같이 죽지만, 셔플 샤딩은 조합이 정확히 같은 고객만 완전히 멈춘다. 일꾼 8개 중 2개씩이면 28분의 1이다. 대신 클라이언트가 자기 일꾼 중 실패한 쪽을 피해 다시 보낼 수 있어야 하고, 그 재시도가 독이 든 요청을 퍼뜨리지 않게 해야 한다.

### 우아한 성능 저하를 설계할 때 무엇을 먼저 정하나요?

기능마다 없으면 서비스가 의미 없는지 등급을 나누는 것부터다. 핵심이 아닌 기능의 의존성은 실패할 때 빈 값, 캐시된 값, 기본값을 돌려주게 짜고, 기능 플래그로 끌 수 있게 한다. 폴백 경로는 평소에 실제로 실행해 봐야 하고, 장애 중에 처음 실행되는 폴백은 그 자체가 새 결함이 되기 쉽다.
