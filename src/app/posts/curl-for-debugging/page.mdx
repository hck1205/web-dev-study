배포 스크립트 끝에 헬스 체크를 넣었다. `curl http://api.internal/healthz`가 성공하면 다음 단계로 넘어간다. 그런데 서버가 503을 돌려줬는데도 스크립트는 그냥 지나갔다. curl은 HTTP 응답을 받기만 하면 상태 코드와 상관없이 종료 코드 0을 낸다. `-f`를 빠뜨린 것이다.

curl은 옵션이 250개가 넘는다. 장애를 볼 때 쓰는 건 그중 스무 개 남짓인데, 그 스무 개도 기본값이 직관과 다른 것들이 많다. 이 글은 그 옵션들을 하나씩 실제로 돌려 보며 기본 동작과 함정을 정리한다. 응답 헤더만 보는 법, 단계별 시간을 재는 법, DNS를 건드리지 않고 특정 서버로 보내는 세 가지 방법, 인증서 검사, HTTP 버전 고르기, 리다이렉트와 재시도, 종료 코드, 그리고 쿠버네티스 Pod 안에서 curl을 치는 법까지 간다.

이 주제의 다른 글: 접속 장애를 링크부터 HTTP까지 아래층에서 위로 좁히는 순서는 [계층별로 장애 좁히기](/posts/network-troubleshooting-by-layer)에 있고, 그 글이 `curl -v` 출력 읽는 법과 `-w`의 기본 다섯 값을 다룬다. HTTP 메시지 자체의 모양은 [HTTP 메시지는 어떻게 생겼나](/posts/http-message)에 있다. 여기서는 그 위에서 curl이라는 도구를 깊게 판다.

실습은 Ubuntu 24.04의 기본 curl 8.5.0에서 했다. 상대는 직접 띄운 Node 서버 하나다. 127.0.0.1의 18080(HTTP/1.1과 h2c 업그레이드), 18081(h2c 전용), 18443(TLS, h2와 HTTP/1.1)에서 듣고, 실습용 CA로 서명한 `shop.lab.test`, `api.lab.test` 인증서를 쓴다.

## 헤더만 볼 때 HEAD를 조심한다

응답 헤더만 보려고 `-I`를 쓴다. `-I`는 HEAD 메서드로 요청하고, 본문이 없다는 걸 알고 헤더만 읽고 끝낸다. 그런데 HEAD를 막아 둔 서버가 꽤 있다. 실습 서버의 `/head`도 HEAD에는 405를, GET에는 200을 준다.

```bash
# HEAD로 요청한다
curl -sS -I http://127.0.0.1:18080/head

# GET으로 요청하되 본문은 버리고 헤더만 stdout에 찍는다
curl -sS -o /dev/null -D - http://127.0.0.1:18080/head
```

```text
HTTP/1.1 405 Method Not Allowed
content-type: text/plain
allow: GET
Date: Wed, 21 Oct 2026 00:40:10 GMT
Connection: keep-alive
Keep-Alive: timeout=5

HTTP/1.1 200 OK
content-type: text/plain
Date: Wed, 21 Oct 2026 00:40:10 GMT
Connection: keep-alive
Keep-Alive: timeout=5
Transfer-Encoding: chunked
```

`-I`가 405를 보여 줬다고 해서 서비스가 죽은 게 아니다. 실제 사용자는 GET을 보내니, 진짜 응답이 궁금하면 `-o /dev/null -D -`(헤더를 파일 `-`, 즉 stdout에 덤프)를 쓴다. 로드 밸런서의 헬스 체크가 HEAD로 설정되어 있으면 같은 이유로 멀쩡한 서버가 빠진다. `-i`는 GET 응답의 헤더와 본문을 함께 찍는다.

`-I` 대신 `-X HEAD`를 쓰면 다른 문제가 생긴다.

```bash
# 메서드 이름만 HEAD로 바꾼다. 3초 한도를 걸었다
curl -X HEAD -m 3 http://127.0.0.1:18080/
```

```text
Warning: Setting custom HTTP method to HEAD with -X/--request may not work the 
Warning: way you want. Consider using -I/--head instead.
curl: (28) Operation timed out after 3002 milliseconds with 0 bytes received
```

`-X`는 요청 줄의 메서드 글자만 바꾸고 curl의 동작은 바꾸지 않는다. curl은 여전히 GET처럼 본문을 기다리고, 서버는 HEAD라서 본문을 안 보낸다. 한도가 없었다면 영원히 멈췄을 것이다. `-X`는 curl이 따로 옵션을 주지 않는 메서드(PATCH, DELETE 같은)에만 쓴다. `-d`를 주면 이미 POST라서 `-X POST`도 필요 없다. 뒤에 리다이렉트에서 이게 다시 문제가 된다.

## 단계별 시간을 원하는 모양으로 찍는다

`-w`는 요청이 끝난 뒤 찍을 내용을 정한다. 시간 변수는 모두 요청을 시작한 순간부터의 누적 초다. 자주 쓰는 형식은 파일로 만들어 두고 `-w @파일`로 부른다.

```text
     dns:  %{time_namelookup}\n
 connect:  %{time_connect}\n
     tls:  %{time_appconnect}\n
     pre:  %{time_pretransfer}\n
redirect:  %{time_redirect}\n
    ttfb:  %{time_starttransfer}\n
   total:  %{time_total}\n
    code:  %{http_code} (http/%{http_version}) %{remote_ip}:%{remote_port}\n
```

```bash
# 1.5초 뒤에 답하는 /slow를 HTTPS로 부르고 단계별 시각을 찍는다
curl -sS -o /dev/null --cacert ca.crt --resolve shop.lab.test:18443:127.0.0.1 \
  -w @timing.txt https://shop.lab.test:18443/slow
```

```text
     dns:  0.000018
 connect:  0.000124
     tls:  0.004176
     pre:  0.004300
redirect:  0.000000
    ttfb:  1.507370
   total:  1.507457
    code:  200 (http/2) 127.0.0.1:18443
```

`-L`로 리다이렉트를 따라가면 `time_redirect`가 생긴다. 앞선 모든 리다이렉트에 쓴 시간의 합이고, 나머지 값은 마지막 요청 기준이 아니라 여전히 맨 처음부터의 누적이다.

```bash
# 301을 한 번 따라가는 요청
curl -sS -o /dev/null -L -w @timing.txt http://localhost:18080/old
```

```text
     dns:  0.000033
 connect:  0.000146
     tls:  0.000000
     pre:  0.000194
redirect:  0.000741
    ttfb:  0.000915
   total:  0.000972
    code:  200 (http/1.1) 127.0.0.1:18080
```

평문 HTTP라 `tls`가 0이다. 단계별 시간을 `tls - connect`로 계산하면 음수가 나온다. 이럴 때 `pre`를 기준으로 삼으면 HTTP와 HTTPS를 같은 식으로 다룰 수 있다. 모든 값을 한꺼번에 받으려면 `-w '%{json}'`(curl 7.70 이상)을 쓴다.

```bash
# 전부 JSON으로 받고 필요한 키만 고른다
curl -sS -o /dev/null --cacert ca.crt --resolve shop.lab.test:18443:127.0.0.1 -w '%{json}' https://shop.lab.test:18443/ \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); print({k: d[k] for k in ["http_code","http_version","num_connects","time_appconnect","time_total","size_download","ssl_verify_result","exitcode","errormsg"]})'
```

```text
{'http_code': 200, 'http_version': '2', 'num_connects': 1, 'time_appconnect': 0.00358, 'time_total': 0.005978, 'size_download': 44, 'ssl_verify_result': 0, 'exitcode': 0, 'errormsg': None}
```

`num_connects`는 새로 맺은 연결 수다. 같은 curl 명령에서 URL 여러 개를 부르면 연결을 재사용해 0이 나오기도 한다. 이 JSON을 줄마다 파일에 쌓으면 간단한 외부 감시가 된다.

## 직접 해 보기: 누적 시각을 단계 시간으로 바꾸기

`-w`의 누적 시각을 단계별 시간(ms)으로 바꾸고 가장 오래 걸린 단계를 고르는 함수를 짜 본다. 평문 HTTP는 `appconnect`가 0이다. 서버 시간은 `starttransfer - pretransfer`로 잡는다.

## 특정 서버 한 대로 보내는 세 가지 방법

로드 밸런서 뒤의 서버 한 대만 확인하고 싶을 때, 또는 DNS를 바꾸기 전에 새 서버를 미리 두드려 보고 싶을 때 쓰는 방법이 셋 있다. 결과가 미묘하게 다르다.

```bash
# 1) --resolve: 이름:포트를 IP에 묶는다
curl -sS --cacert ca.crt --resolve shop.lab.test:18443:127.0.0.1 https://shop.lab.test:18443/

# 2) --connect-to: 이름:포트로 가는 연결을 다른 호스트:포트로 돌린다
curl -sS --cacert ca.crt --connect-to shop.lab.test:443:127.0.0.1:18443 https://shop.lab.test/

# 3) IP로 붙고 Host 헤더만 바꾼다
curl -sS -H 'Host: shop.lab.test' http://127.0.0.1:18080/
curl -sS --cacert ca.crt -H 'Host: shop.lab.test' https://127.0.0.1:18443/
```

```text
hello from shop.lab.test:18443 via HTTP/2.0
hello from shop.lab.test via HTTP/2.0
hello from shop.lab.test via HTTP/1.1
curl: (60) SSL: no alternative certificate subject name matches target host name '127.0.0.1'
```

`--resolve`는 URL을 그대로 두고 IP만 바꾼다. 그래서 포트가 URL과 같아야 하고, Host 헤더에 `:18443`이 붙어 간다. `--connect-to`는 URL을 `https://shop.lab.test/`(443) 그대로 두고 연결만 다른 포트로 돌린다. 서버가 받는 Host가 `shop.lab.test`로 운영과 똑같다. 운영 서버가 443이 아닌 포트로 열린 새 인스턴스나 포트 포워딩 끝을 확인할 때 이쪽이 맞다.

`-H Host`는 평문 HTTP에서는 잘 된다. HTTPS에서는 실패했다. Host 헤더는 TLS가 끝난 뒤에 가는데, curl은 그 전에 URL의 이름(127.0.0.1)으로 SNI를 보내고 인증서를 검사한다. 아래 그림에서 세 방법이 가는 길을 비교한다.

## 인증서 검사는 끄지 말고 믿을 곳을 더한다

사내 CA나 자체 서명 인증서를 쓰는 서버에 붙으면 이런 오류가 난다.

```bash
# 시스템 CA 목록만으로 붙는다
curl -sS --resolve shop.lab.test:18443:127.0.0.1 https://shop.lab.test:18443/; echo "exit=$?"
```

```text
curl: (60) SSL certificate problem: unable to get local issuer certificate
More details here: https://curl.se/docs/sslcerts.html

curl failed to verify the legitimacy of the server and therefore could not
establish a secure connection to it. To learn more about this situation and
how to fix it, please visit the web page mentioned above.
exit=60
```

`-k`(`--insecure`)를 주면 통과한다. 하지만 `-k`는 체인 검사와 이름 검사를 모두 끈다. 중간에서 누가 가짜 인증서를 내밀어도 그대로 믿는다. 같은 요청에 `--cacert ca.crt`를 주면 그 CA를 신뢰 목록에 더해서, 검사는 그대로 하면서 통과한다. 이름이 틀리면 여전히 잡는다.

```bash
# 실습 CA를 믿되 인증서에 없는 이름(www.lab.test)으로 붙는다
curl -sS --cacert ca.crt --resolve www.lab.test:18443:127.0.0.1 https://www.lab.test:18443/; echo "exit=$?"
```

```text
curl: (60) SSL: no alternative certificate subject name matches target host name 'www.lab.test'
More details here: https://curl.se/docs/sslcerts.html

curl failed to verify the legitimacy of the server and therefore could not
establish a secure connection to it. To learn more about this situation and
how to fix it, please visit the web page mentioned above.
exit=60
```

종료 코드는 같은 60이지만 메시지가 다르다. "unable to get local issuer certificate"는 체인을 믿을 CA까지 잇지 못했다는 뜻이다. 서버가 중간 인증서를 빠뜨렸거나 내 쪽 CA 목록에 그 루트가 없다. "no alternative certificate subject name matches"는 체인은 믿을 만한데 이름이 다르다. 인증서 SAN에 그 도메인을 넣거나 맞는 이름으로 붙어야 한다. 원인 구분과 고치는 법은 [HTTPS는 무엇을 지켜 주나](/posts/https-tls)의 인증서 오류 절에 있다.

<Callout kind="warning" title="-k가 스크립트에 남으면">
디버깅 때 쓴 `-k`가 배포 스크립트나 헬스 체크, Dockerfile에 그대로 남는 일이 흔하다. 그 순간부터 그 요청은 아무 인증서나 믿는다. `-k`가 필요했다면 원인은 CA 목록이나 이름이니 `--cacert`나 `--capath`, 시스템 CA 저장소(`/usr/local/share/ca-certificates/`에 넣고 `sudo update-ca-certificates`)로 고친다. 코드 리뷰에서 `-k`, `--insecure`를 검색해 걸러 내는 것도 방법이다.
</Callout>

## HTTP 버전은 묻는 방식이 셋이다

HTTPS에서는 TLS 핸드셰이크 안의 ALPN으로 버전을 고른다. curl 8.5는 기본으로 `h2,http/1.1`을 제안하고 서버가 고른다. 평문 HTTP는 사정이 다르다.

```bash
# 같은 HTTPS 서버에 기본값, --http1.1, --http2로 묻는다
R="--cacert ca.crt --resolve shop.lab.test:18443:127.0.0.1"
for o in "" "--http1.1" "--http2"; do
  curl -sS $R $o -o /dev/null -w "[$o] -> %{http_version}\n" https://shop.lab.test:18443/
done

# 평문 HTTP에 --http2: Upgrade 헤더로 h2c를 청한다
curl -sS --http2 -v -o /dev/null http://127.0.0.1:18080/ 2>&1 | grep -iE 'upgrade|HTTP2-Settings|< HTTP'

# h2c 전용 포트: 처음부터 HTTP/2로 말하기, 그리고 그냥 묻기
curl -sS --http2-prior-knowledge -o /dev/null -w "[prior-knowledge] -> %{http_version}\n" http://127.0.0.1:18081/
curl -sS -o /dev/null -w "[plain] -> %{http_version}\n" http://127.0.0.1:18081/; echo "exit=$?"
```

```text
[] -> 2
[--http1.1] -> 1.1
[--http2] -> 2
> Connection: Upgrade, HTTP2-Settings
> Upgrade: h2c
> HTTP2-Settings: AAMAAABkAAQAoAAAAAIAAAAA
< HTTP/1.1 200 OK
[prior-knowledge] -> 2
curl: (1) Received HTTP/0.9 when not allowed
[plain] -> 0
exit=1
```

18080 서버는 업그레이드를 받아 주지 않아서 HTTP/1.1로 답했다. `--http2`는 "가능하면"이라는 뜻이라 오류 없이 1.1로 내려간다. 버전 때문에 생기는 문제를 재현할 때는 `-w '%{http_version}'`로 실제 버전을 꼭 찍는다. h2c 전용 서버에 HTTP/1.1로 물으면 서버가 HTTP/2 프레임을 돌려주고, curl은 그걸 HTTP/0.9 응답으로 오해해 거부한다. gRPC 서버나 사이드카 프록시 포트에 그냥 curl을 쳤을 때 보는 메시지다. 그런 포트는 `--http2-prior-knowledge`로 부른다. HTTP/3은 `--http3`로 고르는데 Ubuntu 24.04의 curl 패키지는 HTTP/3 없이 빌드되어 있어서 `curl --version`의 Features에 `HTTP3`가 있는지 먼저 본다. 버전 차이 자체는 [HTTP/1.1에서 HTTP/2, HTTP/3까지](/posts/http-versions)를 본다.

## 리다이렉트를 따라가면 메서드와 인증이 바뀐다

`-L`을 주면 3xx 응답의 Location을 따라간다(기본 최대 50번, `--max-redirs`로 바꾼다). 따라가면서 curl은 메서드를 바꿀 수 있다. 규칙은 상태 코드마다 다르다.

```bash
# -d로 POST한 요청이 301(/old)과 307(/temp)을 따라갈 때 /new가 받은 메서드
curl -sS -d 'a=1' -L http://127.0.0.1:18080/old
curl -sS -d 'a=1' -L http://127.0.0.1:18080/temp

# -X POST를 함께 주면
curl -sS -X POST -d 'a=1' -L http://127.0.0.1:18080/old
```

```text
GET /new
POST /new
POST /new
```

301, 302, 303은 따라갈 때 POST를 GET으로 바꾸고 본문을 버린다. 브라우저가 오래전부터 그렇게 해 와서 명세도 그 동작을 허용한다. 307과 308은 메서드와 본문을 그대로 유지하라는 코드다. 그래서 API에 POST를 보내는데 http에서 https로 301 리다이렉트가 걸려 있으면, 최종 서버는 본문 없는 GET을 받고 엉뚱하게 405나 목록 응답을 준다. `-X POST`를 주면 curl이 메서드를 고정해서 301 뒤에도 POST를 보낸다. 이건 테스트를 통과시키지만 브라우저나 다른 클라이언트의 실제 동작과 달라서 문제를 숨긴다. 상태 코드별 의미는 [HTTP 상태 코드](/posts/http-status-codes)에 있다.

리다이렉트가 다른 호스트로 가면 인증 정보가 떨어진다.

```bash
# shop.lab.test/away는 api.lab.test로 302를 준다. 두 이름 모두 127.0.0.1로 묶는다
R="--resolve shop.lab.test:18080:127.0.0.1 --resolve api.lab.test:18080:127.0.0.1"
curl -sS $R -u admin:secret http://shop.lab.test:18080/whoami
curl -sS $R -u admin:secret -L http://shop.lab.test:18080/away
curl -sS $R -H 'Authorization: Bearer tok123' -L http://shop.lab.test:18080/away
curl -sS $R -u admin:secret -L --location-trusted http://shop.lab.test:18080/away
```

```text
host=shop.lab.test:18080 auth=Basic YWRtaW46c2VjcmV0
host=api.lab.test:18080 auth=-
host=api.lab.test:18080 auth=-
host=api.lab.test:18080 auth=Basic YWRtaW46c2VjcmV0
```

`-u`로 준 인증과 `-H`로 직접 넣은 `Authorization` 헤더 모두 다른 호스트로는 보내지 않았다. 리다이렉트 한 번으로 자격 증명이 남의 서버로 새는 걸 막으려는 동작이다(직접 넣은 헤더까지 거르는 건 curl 7.58부터다). 리다이렉트 뒤에서 401이 나면 이걸 의심한다. `--location-trusted`는 이 보호를 끈다. 정말 믿을 수 있는 호스트 사이에서만 쓴다.

## 재시도는 무엇을 다시 하는가

`--retry N`은 "일시적인" 실패만 다시 한다. curl이 일시적이라고 보는 건 타임아웃, 그리고 HTTP 408, 429, 500, 502, 503, 504다. 서버가 `Retry-After`를 주면 그만큼 기다리고, 아니면 1초부터 두 배씩 늘린다(`--retry-delay`로 고정할 수 있다). 실습 서버의 `/flaky`는 세 번에 한 번만 200을 준다.

```bash
# 재시도 없이, 그리고 --retry 3으로
curl -sS -w 'code=%{http_code}\n' http://127.0.0.1:18080/flaky
curl --no-progress-meter --retry 3 -o out.txt http://127.0.0.1:18080/flaky; cat out.txt
```

```text
busy
code=503
Warning: Problem : HTTP error. Will retry in 1 seconds. 3 retries left.
Warning: Problem : HTTP error. Will retry in 1 seconds. 2 retries left.
ok after 3 tries
```

아래 그림은 이 세 번의 시도가 어떻게 흘러갔는지다.

함정이 몇 개 있다. 먼저 `-sS`를 쓰면 위의 Warning 줄이 사라져서 재시도가 일어났는지 보이지 않는다. 재시도를 디버깅할 때는 `--no-progress-meter`를 쓴다. 다음으로 stdout으로 받으면 실패한 시도의 본문도 그대로 이어 붙는다. 실습에서 `-o` 없이 `--retry 3`을 줬더니 `busy`, `busy`, `ok after 3 tries` 세 줄이 이어서 나왔다. 파이프로 `jq`에 넘기는 스크립트라면 JSON이 깨진다.

연결 거부는 기본으로 다시 하지 않는다. 막 뜨는 서버를 기다리는 스크립트에서 자주 걸린다.

```bash
# 아무도 듣지 않는 포트. --retry만으로는 한 번에 끝난다
curl -sS --retry 2 --retry-delay 1 http://127.0.0.1:18099/; echo "exit=$?"

# --retry-connrefused를 더하면 거부도 다시 한다
curl --no-progress-meter --retry 2 --retry-delay 1 --retry-connrefused http://127.0.0.1:18099/; echo "exit=$?"
```

```text
curl: (7) Failed to connect to 127.0.0.1 port 18099 after 0 ms: Couldn't connect to server
exit=7
curl: (7) Failed to connect to 127.0.0.1 port 18099 after 0 ms: Couldn't connect to server
Warning: Problem : connection refused. Will retry in 1 seconds. 2 retries left.
curl: (7) Failed to connect to 127.0.0.1 port 18099 after 0 ms: Couldn't connect to server
Warning: Problem : connection refused. Will retry in 1 seconds. 1 retries left.
curl: (7) Failed to connect to 127.0.0.1 port 18099 after 0 ms: Couldn't connect to server
exit=7
```

`--retry-all-errors`(7.71 이상)는 404를 포함해 모든 실패를 다시 한다. `-f`와 함께 써야 HTTP 오류가 실패로 잡힌다. 마지막으로 재시도는 같은 요청을 다시 보낸다는 뜻이다. POST로 결제나 주문을 만드는 요청에 `--retry`를 걸면 503 직전에 서버가 이미 처리했을 경우 두 번 만들어진다. 이 위험과 멱등성 키 이야기는 [재시도](/posts/retries)와 [멱등성 키](/posts/idempotency-key)에 있다.

## 한도를 안 걸면 curl은 기다린다

curl의 기본 시간 한도는 연결 단계 300초뿐이고, 응답 전체에는 한도가 없다. 응답을 안 주는 서버에 curl을 치면 스크립트가 그대로 멈춘다. 한도는 둘로 나뉜다.

```bash
# 응답을 영영 주지 않는 /hang에 전체 한도 2초
curl -sS -m 2 http://127.0.0.1:18080/hang; echo "exit=$?"

# SYN을 버리는 주소(실습 netns에서 iptables DROP)에 연결 한도 2초, 그리고 전체 한도 3초
curl -sS --connect-timeout 2 http://10.99.0.2/; echo "exit=$?"
curl -sS -m 3 http://10.99.0.2/; echo "exit=$?"
```

```text
curl: (28) Operation timed out after 2002 milliseconds with 0 bytes received
exit=28
curl: (28) Failed to connect to 10.99.0.2 port 80 after 2001 ms: Timeout was reached
exit=28
curl: (28) Connection timed out after 3002 milliseconds
exit=28
```

종료 코드는 모두 28이지만 메시지가 어디서 멈췄는지 말해 준다. "Failed to connect … Timeout"이면 SYN에 답이 없는 것이라 방화벽이나 보안 그룹, 라우팅을 본다. "0 bytes received"면 연결은 됐는데 서버가 답을 안 하는 것이라 애플리케이션이나 그 뒤의 DB를 본다. 연결 거부(7)는 그 주소까지는 갔지만 포트를 아무도 듣지 않는다는 뜻이다. 패킷 수준에서 이 셋을 가르는 법은 [tcpdump로 계층을 눈으로 보기](/posts/packet-capture-tcpdump)에 있다.

스크립트에는 `--connect-timeout`을 짧게(2~5초), `-m`을 그 요청이 정상일 때 걸리는 시간의 몇 배로 준다. 재시도와 함께 쓰면 `-m`은 시도 한 번의 한도이고, 전체를 묶으려면 `--retry-max-time`을 더한다. 타임아웃 값을 계층마다 맞추는 이야기는 [타임아웃](/posts/timeouts)에서 이어진다.

## 종료 코드로 스크립트를 짠다

처음의 헬스 체크로 돌아간다. curl의 종료 코드는 어디서 실패했는지를 숫자로 알려 준다.

```bash
# 각 실패를 일부러 만들어 종료 코드를 본다
curl -sS http://no-such-host.invalid/; echo "exit=$?"     # 이름 풀이 실패
curl -sS http://127.0.0.1:18082/; echo "exit=$?"          # 연결하자마자 끊는 서버
curl -sS -f http://127.0.0.1:18080/nope; echo "exit=$?"   # 404를 -f로
curl -sS --fail-with-body http://127.0.0.1:18080/nope; echo "exit=$?"
```

```text
curl: (6) Could not resolve host: no-such-host.invalid
exit=6
curl: (52) Empty reply from server
exit=52
curl: (22) The requested URL returned error: 404
exit=22
curl: (22) The requested URL returned error: 404
not found
exit=22
```

현장에서 자주 보는 번호를 묶으면 이렇다. 6은 DNS, 7은 연결 거부, 28은 시간 초과, 35는 TLS 핸드셰이크 실패, 60은 인증서 검사 실패, 52는 응답 없이 끊김(앞단 프록시가 백엔드 연결을 잃었을 때 흔하다), 56은 받다가 끊김, 22는 `-f`로 잡은 4xx·5xx, 47은 리다이렉트 한도 초과다. `-f`가 없으면 HTTP 오류는 전부 0이니, 헬스 체크는 이렇게 쓴다.

```bash
# 연결 2초, 전체 5초, 일시적 실패와 거부를 5번까지 다시, HTTP 오류는 실패로
curl -fsS --connect-timeout 2 -m 5 --retry 5 --retry-connrefused --retry-max-time 60 \
  -o /dev/null -w '%{http_code} %{time_total}\n' http://127.0.0.1:18080/ || { echo "health check failed: $?"; exit 1; }
```

스크립트가 이상하게 동작하면 환경도 본다. curl은 `https_proxy`, `http_proxy` 환경 변수가 있으면 그 프록시로 보낸다. 사내 프록시가 설정된 셸에서 내부 주소에 curl을 치면 엉뚱한 곳으로 간다.

```bash
# 듣지 않는 프록시를 환경 변수로 주고 요청한다
https_proxy=http://127.0.0.1:18099 curl -sS -v --cacert ca.crt --resolve shop.lab.test:18443:127.0.0.1 https://shop.lab.test:18443/ 2>&1 | grep -iE 'proxy|Trying'

# no_proxy에 도메인을 넣으면 직접 간다
https_proxy=http://127.0.0.1:18099 no_proxy=.lab.test curl -sS --cacert ca.crt --resolve shop.lab.test:18443:127.0.0.1 https://shop.lab.test:18443/
```

```text
* Uses proxy env variable https_proxy == 'http://127.0.0.1:18099'
*   Trying 127.0.0.1:18099...
hello from shop.lab.test:18443 via HTTP/2.0
```

`-v`의 첫 줄이 프록시를 쓴다고 알려 준다. 한 번만 피하려면 `--noproxy '*'`를 준다. 홈 디렉터리의 `~/.curlrc`도 옵션을 몰래 더할 수 있어서, 남의 서버에서 결과가 이상하면 `curl -q`(첫 옵션이어야 한다)로 설정 파일 없이 다시 쳐 본다.

## Pod 안에서 curl을 친다

클러스터 안에서 치는 가장 간단한 방법은 curl 이미지로 일회용 Pod를 띄우는 것이다.

```bash
# curl 이미지로 임시 Pod를 띄워 한 번 치고, 끝나면 지운다
kubectl run curl-tmp --rm -it --restart=Never --image=curlimages/curl:8.10.1 --command -- \
  curl -sS -m 5 -w '\n%{http_code} %{remote_ip}\n' http://web.shop.svc.cluster.local/
```

`--` 뒤의 내용은 기본으로 컨테이너의 `args`가 되어 이미지의 ENTRYPOINT 뒤에 붙는다. `--command`를 주면 `command`로 들어가 ENTRYPOINT를 대신한다. 어느 쪽으로 들어가는지는 `--dry-run=client -o yaml`로 확인할 수 있다(이 부분은 kwok 클러스터에서 실제로 찍었다).

```bash
# 위 명령에서 --rm -it를 빼고 --dry-run=client -o yaml로 바꿔 스펙만 본다
kubectl run curl-tmp --image=curlimages/curl:8.10.1 --restart=Never --dry-run=client -o yaml \
  --command -- curl -sS http://web.shop.svc.cluster.local/ | sed -n '/containers:/,/name: curl-tmp/p'
```

```text
  containers:
  - command:
    - curl
    - -sS
    - http://web.shop.svc.cluster.local/
    image: curlimages/curl:8.10.1
    name: curl-tmp
```

임시 Pod는 다른 Pod라서 앱 Pod의 `localhost`에는 닿지 않는다. 앱 Pod 안에서 보려면 앱 이미지에 curl이 있어야 하는데, distroless나 scratch 이미지에는 셸조차 없다. 그때는 `kubectl debug`로 같은 Pod에 도구 컨테이너를 붙인다. 디버그 컨테이너는 Pod의 net namespace를 함께 써서 `localhost:8080`이 앱이다. `--target`을 주면 앱의 PID namespace에도 들어간다. 붙이는 과정과 제약은 [Pod가 안 뜰 때 상태별로 보는 순서](/posts/k8s-pod-troubleshooting)에, namespace에 합류한다는 게 커널에서 무슨 뜻인지는 [네임스페이스와 cgroup](/posts/linux-namespaces-cgroups)에 있다.

```bash
# 앱 Pod에 netshoot 컨테이너를 붙이고 localhost로 친다 (예시: 이 실습의 kwok 클러스터는 컨테이너를 실제로 돌리지 않는다)
kubectl debug -it pod/web-7d9c -n shop --image=nicolaka/netshoot --target=web -- \
  curl -sS -m 3 -w '\n%{http_code}\n' http://localhost:8080/healthz
```

Pod 안에서 칠 때 흔한 실수가 둘 있다. 이름을 짧게 `web`이라고만 쓰면 Pod가 속한 네임스페이스 기준으로 풀린다. 다른 네임스페이스의 Service면 `web.shop`이나 FQDN을 쓴다([CoreDNS](/posts/k8s-coredns)). 그리고 사이드카 프록시(서비스 메시)가 있는 Pod에서는 curl도 그 프록시를 지나간다. 앱이 아니라 프록시가 503을 줄 수 있으니 응답의 `server` 헤더를 `-D -`로 같이 본다.

## 기본값을 알고 쓰면 거짓말을 안 한다

curl은 기본으로 HTTP 오류를 성공으로 보고, 응답을 끝없이 기다리고, 리다이렉트를 따라가지 않고, 연결 거부는 다시 하지 않는다. 디버깅과 스크립트에서 믿을 만한 결과를 얻으려면 `-f`, `--connect-timeout`과 `-m`, 필요한 만큼의 `--retry`를 명시하고, `-w`로 실제 버전과 IP와 단계별 시간을 찍는다. 특정 서버를 고를 때는 `--resolve`나 `--connect-to`를, 인증서 문제는 `-k`가 아니라 `--cacert`를 쓴다. 이 글에서 정리한 옵션으로 어디서 멈췄는지 알았다면, 그다음 칸을 좁히는 순서는 [계층별로 장애 좁히기](/posts/network-troubleshooting-by-layer)에서 이어진다.

## 면접에서 나올 만한 질문

### 헬스 체크 스크립트가 503인데도 성공으로 넘어갔습니다. 왜 그런가요?

curl은 HTTP 응답을 받기만 하면 상태 코드와 상관없이 종료 코드 0을 낸다. `-f`를 줘야 4xx·5xx가 종료 코드 22로 실패가 된다. 본문의 오류 메시지까지 보고 싶으면 `--fail-with-body`를 쓴다.

### curl -I와 curl -X HEAD는 무엇이 다른가요?

`-I`는 HEAD로 요청하면서 본문을 기다리지 않도록 curl의 동작까지 바꾼다. `-X HEAD`는 요청 줄의 메서드 글자만 바꿔서 curl이 GET처럼 본문을 기다리다 멈춘다. 또 HEAD를 막은 서버는 -I에 405를 주니, 실제 GET 응답의 헤더는 `-o /dev/null -D -`로 본다.

### --resolve, --connect-to, -H Host는 어떻게 고르나요?

`--resolve`는 이름:포트를 특정 IP에 묶어 URL과 SNI, 인증서 검사를 그대로 유지한다. `--connect-to`는 연결만 다른 호스트:포트로 돌려서 Host 헤더에 포트가 붙지 않는다. `-H Host`는 평문 HTTP에서만 쓸 만하고, HTTPS에서는 SNI와 인증서 검사가 URL의 이름으로 이뤄져 실패한다.

### -k를 쓰면 안 되는 이유와 대신 무엇을 쓰나요?

`-k`는 체인 검사와 이름 검사를 모두 꺼서 중간자 공격을 막지 못한다. 사내 CA라면 `--cacert`로 그 CA를 신뢰 목록에 더하거나 시스템 CA 저장소에 등록해, 검사는 유지한 채 통과시킨다. 오류 메시지가 issuer 문제인지 이름 문제인지 보고 원인을 고친다.

### POST 요청에 -L을 줬는데 서버가 GET을 받았습니다. 왜 그런가요?

301, 302, 303을 따라갈 때 curl은 POST를 GET으로 바꾸고 본문을 버린다. 브라우저와 같은 동작이다. 메서드를 유지하려면 서버가 307이나 308을 줘야 하고, `-X POST`로 고정하면 curl에서만 통과해 실제 클라이언트의 문제를 숨긴다.

### curl --retry는 무엇을 다시 하나요? 조심할 점은요?

타임아웃과 408, 429, 500, 502, 503, 504 같은 일시적 실패만 다시 하고, Retry-After가 있으면 그만큼 기다린다. 연결 거부는 `--retry-connrefused`, 그 밖의 오류는 `--retry-all-errors`가 있어야 다시 한다. 같은 요청을 다시 보내는 것이라 멱등하지 않은 POST에 걸면 중복 처리가 생기고, stdout으로 받으면 실패한 시도의 본문이 이어 붙는다.

### curl 종료 코드 7, 28, 52는 각각 무엇을 뜻하나요?

7은 연결 거부라 주소까지는 갔지만 포트를 듣는 프로세스가 없다. 28은 시간 초과인데, 메시지가 "Failed to connect"면 SYN에 답이 없는 방화벽·라우팅 문제이고 "0 bytes received"면 연결 뒤 서버가 답을 안 하는 문제다. 52는 응답 없이 연결이 끊긴 것으로, 앞단 프록시가 백엔드를 잃었을 때 흔하다.

### Pod 안에서 curl이 필요한데 이미지에 curl이 없습니다. 어떻게 하나요?

Service 경로를 보려면 curl 이미지로 임시 Pod를 띄워 Service DNS 이름으로 친다. 앱 Pod의 localhost를 봐야 하면 `kubectl debug`로 도구 컨테이너를 같은 Pod에 붙여 net namespace를 공유한다. 노드 접근이 된다면 nsenter로 Pod의 net namespace에 들어가 호스트의 curl을 쓰는 방법도 있다.
