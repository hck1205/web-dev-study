지사가 서른 곳인 회사의 네트워크 담당자가 됐다. 지사마다 통신사 MPLS 회선이 하나씩 들어와 있고, 매달 회선비 청구서가 꽤 두툼하다. 요즘 불만은 따로 있다. 지사에서 Teams 화상 회의가 자주 끊기고 Microsoft 365가 느리다. traceroute를 떠 보면 지사에서 나간 트래픽이 MPLS를 타고 본사로 갔다가, 본사 방화벽을 거쳐 인터넷으로 나간다. 서울 지사에서 바로 옆 데이터센터에 있는 SaaS로 가는데 부산 본사를 돌아오는 셈이다.

예전에는 이게 맞는 구조였다. 업무 시스템은 전부 본사 전산실에 있었고, 인터넷은 본사 한곳에서 검사하면 됐다. 지금은 업무의 절반이 SaaS와 클라우드에 있다. 이 글은 그 변화를 따라 WAN 기술을 본다. 통신사 망 안에서 패킷이 라벨로 옮겨지는 MPLS, 한 장비에서 고객마다 경로표를 나누는 VRF, 인터넷 위에 터널을 놓는 GRE over IPsec, 여러 회선을 앱 단위로 골라 쓰는 SD-WAN, 그리고 클라우드와 이어지는 지점까지 다룬다.

명령 예시는 Ubuntu 24.04의 iproute2 기준이다. 실습 컨테이너 커널에는 VRF·GRE·MPLS 모듈이 없어 명령을 실제로 돌리지 못했다. 그래서 출력 예시는 싣지 않고 명령과 확인할 지점만 적는다. 터널 자체의 원리는 [VPN 글](/posts/vpn-ipsec-wireguard)에서, 통신사끼리 경로를 주고받는 BGP는 [BGP 글](/posts/bgp-basics)에서 다뤘다.

## 멀리 떨어진 망을 잇는 세 가지 길

WAN(Wide Area Network)은 건물 밖, 도시와 나라를 건너는 망이다. 회사가 직접 선을 깔 수 없으니 결국 통신사 망을 빌린다. 빌리는 방식은 크게 세 가지다.

전용선(leased line)은 두 지점 사이에 남과 섞이지 않는 회선을 통째로 빌린다. 대역폭이 보장되고 지연이 일정하다. 대신 거리와 속도에 따라 비싸고, 지사가 n곳이면 서로 다 이으려면 회선이 n(n-1)/2개 필요하다. 지사 서른 곳이면 435개다. 그래서 보통 본사를 중심으로 별 모양(hub-and-spoke)으로만 잇는다.

MPLS VPN은 통신사의 MPLS 망 하나에 모든 지사를 붙이고, 통신사가 그 안에서 회사별로 망을 나눠 준다. 지사마다 회선은 하나(통신사까지)만 있으면 되고, 지사끼리는 통신사 망 안에서 바로 통한다. 통신사가 지연과 손실을 계약(SLA)으로 보장한다. 이 글의 첫 장면이 이 구성이다.

인터넷 VPN은 지사마다 일반 인터넷 회선을 놓고, 그 위에 암호화한 터널을 친다. 회선비가 훨씬 싸고 개통도 빠르다. 대신 인터넷 구간의 품질은 아무도 보장하지 않는다. SD-WAN은 이 인터넷 회선과 MPLS를 섞어 쓰는 방식이다.

## 통신사 망 안에서는 라벨만 본다

MPLS(Multiprotocol Label Switching)는 패킷 앞에 4바이트짜리 라벨을 붙이고, 망 안의 라우터가 IP 주소 대신 그 라벨만 보고 패킷을 넘기는 기술이다. 라벨은 20비트 값(0~15는 예약)과 우선순위 3비트, 스택의 마지막인지 표시하는 1비트, TTL 8비트로 이뤄진다. IP 헤더와 이더넷 헤더 사이에 끼워 넣어서 흔히 2.5계층이라고 부른다.

역할은 위치에 따라 나뉜다. 고객 쪽 장비가 CE(Customer Edge), 통신사 망의 가장자리 라우터가 PE(Provider Edge), 망 안쪽 라우터가 P(Provider)다. PE가 들어온 IP 패킷에 라벨을 붙이고(push), P는 라벨을 다음 라벨로 바꿔 넘기고(swap), 마지막에 라벨을 뗀다(pop). 라우터마다 "이 라벨로 들어오면 저 라벨로 바꿔 이 포트로"라는 표(LFIB)를 갖고 있고, 이 표는 LDP 같은 프로토콜로 이웃끼리 라벨을 나눠 만든다.

처음 MPLS가 나왔을 때는 "긴 IP 주소를 최장 일치로 찾는 것보다 고정 길이 라벨을 찾는 게 빠르다"는 속도 이점이 이유였다. 지금은 라우터 칩이 IP 조회도 충분히 빨리 해서 그 이점은 거의 없다. MPLS가 아직 쓰이는 진짜 이유는 둘이다. 라벨로 경로를 미리 정해 둘 수 있어서 특정 트래픽을 덜 붐비는 길로 돌리는 트래픽 엔지니어링이 된다. 그리고 라벨을 두 겹 쌓으면 한 망 위에 고객별 VPN을 얹을 수 있다. 다음 절이 그 이야기다.

### 리눅스로 라벨 표를 만들어 보면

리눅스 커널도 MPLS 전달을 지원한다(`mpls_router`·`mpls_iptunnel` 모듈). 장비 없이 원리를 확인할 때 쓸 만하다. Ubuntu 24.04 기준으로 PE와 P 역할은 이렇게 흉내 낸다. 이 실습 컨테이너에는 모듈이 없어 돌리지 못했으니, 출력 대신 확인할 명령만 적는다.

```bash
# MPLS 전달을 켠다: 모듈을 올리고, 쓸 라벨 범위와 라벨을 받을 인터페이스를 정한다
sudo modprobe mpls_router
sudo modprobe mpls_iptunnel   # IP 경로에 라벨을 붙이는(encap mpls) 기능
sudo sysctl -w net.mpls.platform_labels=1000
sudo sysctl -w net.mpls.conf.eth1.input=1

# PE 역할(push): 10.9.0.0/24로 가는 IP 패킷에 라벨 17을 붙여 P(10.0.12.2)로 보낸다
sudo ip route add 10.9.0.0/24 encap mpls 17 via 10.0.12.2 dev eth1

# P 역할(swap): 라벨 17로 들어오면 22로 바꿔 다음 라우터로 넘긴다
sudo ip -f mpls route add 17 as 22 via inet 10.0.23.3 dev eth2

# 라벨 표(LFIB)를 확인한다
ip -f mpls route show
```

장비에서는 이 표를 손으로 만들지 않는다. LDP가 이웃끼리 "이 목적지로 가려면 나한테 이 라벨로 보내라"를 주고받아 채운다. 요즘 새로 짓는 통신사 망은 LDP 대신 세그먼트 라우팅(SR-MPLS)을 쓰는 경우가 늘었다. 라벨을 라우터마다 따로 나누지 않고, 출발지가 지나갈 경로를 라벨 목록으로 패킷에 미리 적어 보낸다. 경로 정보는 OSPF나 IS-IS가 함께 퍼뜨려서 LDP라는 프로토콜 하나가 줄어든다.

### 라벨의 우선순위 비트와 통신사 QoS

라벨 안의 3비트 TC(Traffic Class, 예전 이름 EXP)는 우선순위다. 통신사 MPLS VPN 상품은 보통 "실시간", "업무", "일반" 같은 서너 개의 등급을 팔고, PE가 고객 패킷의 DSCP 값을 보고 TC를 정한다. 음성에 흔히 쓰는 DSCP EF(46)는 실시간 등급으로, 나머지는 일반 등급으로 가는 식이다. 망 안의 P 라우터는 IP 헤더를 보지 않으니 이 3비트만 보고 큐를 고른다.

여기서 두 가지 실수가 자주 나온다. 하나는 고객 장비가 DSCP를 아예 찍지 않아서, 비싼 실시간 등급을 계약해 놓고 모든 트래픽이 일반 등급으로 가는 경우다. 다른 하나는 계약한 실시간 대역(예를 들어 회선의 20%)을 넘겨 찍어서, 넘친 만큼이 통신사 입구에서 버려지는 경우다. 통화가 많은 시간에만 음성이 깨진다면 이쪽을 본다. 큐와 셰이핑 자체는 [트래픽 셰이핑 글](/posts/traffic-shaping-qos)에서 다뤘다.

## 같은 사설 대역을 쓰는 두 회사

통신사 입장에서 보자. A사도 B사도 지사 대역으로 `10.1.0.0/24`를 쓴다. 사설 대역이니 겹치는 게 당연하다. PE1 라우터 하나에 A사 서울 지사와 B사 서울 지사가 함께 붙어 있다. 경로표가 하나라면 `10.1.0.0/24`가 어느 회사 것인지 구분할 수 없다.

VRF(Virtual Routing and Forwarding)가 이걸 푼다. 라우터 안에 경로표를 여러 개 두고, 인터페이스마다 어느 경로표에 속하는지 정한다. A사 회선이 들어오는 포트는 `VRF A`, B사 포트는 `VRF B`에 넣는다. 같은 `10.1.0.0/24`라도 서로 다른 표에 있으니 부딪히지 않는다. 한 VRF의 패킷은 다른 VRF의 경로를 아예 보지 못한다.

PE가 여러 대이니 VRF 경로도 PE끼리 나눠야 한다. 이때 MP-BGP를 쓰고, 두 가지 값을 붙인다.

- RD(Route Distinguisher): 경로 앞에 붙이는 8바이트 값이다. `65000:1` + `10.1.0.0/24`와 `65000:2` + `10.1.0.0/24`는 서로 다른 경로가 된다. 겹치는 주소를 BGP 안에서 구분하는 용도일 뿐 누가 받을지는 정하지 않는다.
- RT(Route Target): 경로에 붙이는 꼬리표(BGP 확장 커뮤니티)다. 각 VRF는 "이 RT를 붙여 내보내고(export), 이 RT가 붙은 경로를 받는다(import)"를 설정한다. 어느 VRF가 어느 경로를 보는지는 RT가 정한다.

MP-BGP는 경로와 함께 VPN 라벨도 알려 준다. 그래서 패킷에는 라벨이 두 겹 붙는다. 바깥 라벨은 "어느 PE로 가나"(앞 절의 전송 라벨), 안쪽 라벨은 "그 PE의 어느 VRF로 가나"(VPN 라벨)다. 이 구성을 MPLS L3VPN(RFC 4364)이라고 부른다. 아래 그림에서 다음을 누르면 A사와 B사의 패킷이 같은 주소로 출발해 섞이지 않고 각자의 본사에 닿는 과정이 보인다.

## VRF는 VLAN과 무엇이 다른가

둘 다 "한 장비를 여러 망으로 나눈다"라서 자주 헷갈린다. 나누는 계층이 다르다.

[VLAN](/posts/vlan-basics)은 2계층을 나눈다. 스위치 포트를 묶어 브로드캐스트 도메인을 가르고, 다른 VLAN끼리는 라우터를 거쳐야 통신한다. 하지만 그 라우터의 경로표가 하나라면 VLAN 10과 VLAN 20은 라우터에서 바로 이어진다. VRF는 3계층을 나눈다. 라우터 안의 경로표 자체를 여러 개로 나눠서, 같은 라우터를 지나도 VRF가 다르면 서로 경로가 없다. 주소가 겹쳐도 된다는 점도 VLAN에는 없는 성질이다.

실무에서는 둘을 함께 쓴다. 스위치에서 VLAN으로 나눈 망을 라우터의 서브인터페이스로 받고, 그 서브인터페이스를 VRF에 넣는다. VLAN 10은 VRF 영업, VLAN 20은 VRF 개발 하는 식이다. MPLS 없이 한 장비 안에서만 VRF를 쓰는 것을 VRF-lite라고 부른다. 데이터센터에서 관리망과 서비스망을 나누거나, 고객별로 망을 가르는 데 흔하다.

리눅스 커널에도 VRF가 있다(4.3부터 기본 기능, 여러 배포판 커널에 포함). Ubuntu 24.04라면 이렇게 만든다. 앞에서 말했듯 실습 컨테이너에서는 `vrf` 장치 종류가 없다는 오류(`Unknown device type`)가 나서 돌리지 못했다.

```bash
# VRF 장치를 만들고 경로표 10번에 연결한다
sudo ip link add vrf-sales type vrf table 10
sudo ip link set vrf-sales up

# eth1(영업망 쪽 포트)을 VRF에 넣는다. 이 포트의 경로는 이제 표 10에만 생긴다
sudo ip link set eth1 master vrf-sales

# VRF 안의 경로표만 본다
ip route show vrf vrf-sales

# VRF 안에서 명령을 실행한다 (VRF를 지정하지 않으면 기본 경로표로 나가서 안 닿는다)
sudo ip vrf exec vrf-sales ping -c 3 10.20.0.1
```

마지막 줄이 현장에서 자주 헷갈리는 부분이다. VRF가 있는 장비에서 그냥 `ping`을 치면 기본 경로표로 나간다. 대상이 VRF 안에만 있으면 실패한다. 망은 멀쩡한데 확인하는 방법이 틀린 것이다. 네트워크 장비도 마찬가지로 `ping vrf 이름 주소`처럼 VRF를 지정하는 문법이 따로 있다.

## 인터넷 위에 터널을 놓는다: GRE over IPsec

MPLS가 비싸니 인터넷 회선으로 지사를 잇고 싶다. 인터넷 위로 사설 주소 패킷을 보내려면 [VPN 글](/posts/vpn-ipsec-wireguard)에서 본 것처럼 터널에 넣어야 한다. 여기서 GRE와 IPsec이 함께 등장한다.

GRE(Generic Routing Encapsulation)는 패킷을 다른 IP 패킷 안에 넣는 가장 단순한 터널이다. IP 프로토콜 47번을 쓰고, 바깥 IP 헤더 20바이트와 GRE 헤더 4바이트, 합쳐 24바이트를 덧씌운다. 암호화는 전혀 하지 않는다. 대신 무엇이든 넣는다. 멀티캐스트도, OSPF 같은 라우팅 프로토콜 패킷도 그대로 실어 나른다. 터널이 평범한 인터페이스처럼 보이니 그 위에서 동적 라우팅을 돌릴 수 있다.

IPsec은 그 반대다. 암호화와 무결성을 주지만, 정책 기반 IPsec은 "이 대역에서 저 대역으로 가는 유니캐스트"만 정해진 대로 넣는다. 멀티캐스트를 쓰는 OSPF가 터널을 넘지 못하고, 경로가 바뀔 때마다 양쪽 정책을 고쳐야 한다.

그래서 둘을 겹친다. 먼저 GRE로 감싸 라우팅 프로토콜까지 담을 수 있는 터널을 만들고, 그 GRE 패킷 전체를 IPsec으로 암호화한다. 이게 GRE over IPsec이다. 지사가 많을 때는 지사끼리 필요할 때 직접 터널을 여는 DMVPN 같은 방식으로 넓힌다. 지금은 IPsec 자체에 가상 터널 인터페이스(VTI)를 두는 라우트 기반 VPN으로도 같은 효과를 내서, GRE 없이 쓰는 경우도 많다.

```bash
# 지사 쪽: 본사 공인 IP와 GRE 터널을 만든다 (암호화는 IPsec이 따로 맡는다)
sudo ip link add gre-hq type gre local 198.51.100.10 remote 203.0.113.1 ttl 64
sudo ip addr add 172.16.0.2/30 dev gre-hq
# GRE 24바이트 + IPsec 오버헤드를 감안해 MTU를 낮춘다
sudo ip link set gre-hq mtu 1400 up

# 본사 대역을 터널로 보낸다 (실무에서는 이 경로를 OSPF나 BGP가 대신 넣는다)
sudo ip route add 10.9.0.0/16 via 172.16.0.1 dev gre-hq
```

여기서 가장 흔한 장애가 MTU다. 1500바이트 회선에 GRE 24바이트와 IPsec ESP 오버헤드(암호 방식에 따라 수십 바이트)가 붙으면 원래 패킷이 실을 수 있는 크기가 1400바이트 언저리로 줄어든다. 터널 MTU를 낮추지 않으면 ping은 되는데 큰 파일 전송이나 HTTPS 일부가 멈추는 증상이 나온다. 터널 MTU를 1400으로, TCP MSS를 1360 정도로 고정(clamping)하는 게 흔한 시작점이다. 원리는 [MTU 글](/posts/layer-mtu-fragmentation)에 자세히 있다.

## SD-WAN은 회선을 앱 단위로 고른다

인터넷 터널로 지사를 이으면 회선비는 줄지만 품질이 들쭉날쭉하다. 저녁 시간 가정용 회선처럼 손실이 몇 퍼센트씩 튀면 화상 회의가 깨진다. SD-WAN(Software-Defined WAN)은 여기서 출발한다. 회선 하나에 기대지 말고 여러 회선을 동시에 쓰면서, 지금 가장 나은 회선으로 앱마다 골라 보내자는 생각이다.

구성은 이렇다. 지사마다 SD-WAN 엣지 장비(실물 또는 가상 머신)를 둔다. 엣지에는 MPLS, 일반 인터넷, LTE·5G처럼 서로 다른 회선(언더레이)이 여러 개 붙는다. 엣지끼리는 각 회선 위에 IPsec 터널(오버레이)을 쳐 둔다. 그리고 중앙의 컨트롤러가 모든 엣지에 같은 정책을 내려보낸다.

엣지는 두 가지 일을 계속한다. 하나는 측정이다. 터널마다 작은 프로브 패킷을 보내 지연, 손실, 지터(지연의 흔들림)를 초 단위로 잰다. 다른 하나는 분류다. 들어오는 트래픽이 어떤 앱인지 첫 패킷이나 TLS의 SNI, 알려진 주소 목록으로 판별한다. 그리고 정책을 대조한다. "음성·화상은 지연 150ms, 손실 1%, 지터 30ms 이하인 회선으로", "백업은 가장 싼 회선으로", "SaaS는 본사를 거치지 말고 지사 인터넷으로 바로 내보낸다(local breakout)" 같은 규칙이다.

넷째 테스트를 보면 최선 노력 점수가 결과를 정한다. 인터넷은 180 + 200 = 380점, LTE는 90 + 400 = 490점이라 지연이 큰 인터넷이 손실이 큰 LTE를 이긴다. 손실에 무게를 얼마나 줄지는 앱 성격에 따라 다르다. 실제 제품도 이런 가중치와, 회선을 너무 자주 바꾸지 않도록 하는 판정 횟수·유지 시간을 정책으로 둔다. 회선이 기준선 근처에서 오르내릴 때 흐름이 왔다 갔다 하면(flapping) 오히려 통화 품질이 나빠진다.

몇 가지 장치가 더 있다. 손실이 잦은 회선에서는 패킷 몇 개마다 복구용 패킷을 덧붙이는 FEC(Forward Error Correction)나, 중요한 흐름을 두 회선에 동시에 보내는 패킷 복제를 쓴다. 대역폭을 더 쓰는 대신 손실을 숨긴다.

### 터널을 몇 개 칠 것인가

오버레이 모양도 정해야 한다. 지사끼리 모두 직접 터널을 치는 풀 메시는 지사 간 통화가 가장 빠르지만 터널 수가 빠르게 는다. 지사 서른 곳이면 쌍이 435개이고, 지사마다 회선이 둘(MPLS, 인터넷)이고 회선 조합마다 터널을 치면 쌍마다 최대 네 개, 합쳐 1,740개다. 엣지마다 다른 지사 29곳과 키를 교환하고 프로브를 돌려야 한다.

그래서 보통은 허브 앤 스포크로 시작한다. 지사는 본사나 지역 허브 두 곳에만 터널을 치고, 지사 간 트래픽은 허브를 거친다. 지사 간 트래픽이 많은 쌍(예를 들어 서울 지사와 판교 연구소)만 직접 터널을 열고, 일부 제품은 트래픽이 생길 때 지사끼리 터널을 동적으로 열었다가 닫는다. 지사 간 화상 회의가 많지 않다면 허브 앤 스포크로 충분하다. 요즘 화상 회의는 대개 SaaS 서버를 거치니 지사끼리 직접 오가는 트래픽이 생각보다 적다.

## 클라우드와 이어지는 지점

트래픽이 클라우드로 옮겨 가면서 WAN의 반대편 끝도 바뀌었다. 본사 전산실이 아니라 AWS VPC나 SaaS가 목적지다.

통신사 회선으로 클라우드에 바로 붙는 길은 AWS Direct Connect, Azure ExpressRoute, GCP Cloud Interconnect 같은 전용 연결이다. 많은 통신사가 MPLS VPN에 이 연결을 붙여, 고객 VRF에서 클라우드로 가는 경로를 BGP로 내준다. 인터넷 위로 가는 길은 사이트 간 IPsec VPN이다. 둘 다 클라우드 쪽에서는 Transit Gateway 같은 허브에 붙는다. AWS Transit Gateway Connect는 GRE 터널과 BGP로 SD-WAN 장비를 붙이는 연결 방식을 따로 제공한다. VPC를 허브로 잇는 이야기는 [VPC 잇기 글](/posts/vpc-peering-transit-privatelink)에서 다뤘다.

SD-WAN 업체들은 클라우드 리전에 가상 엣지를 띄워 두는 방식도 쓴다. 지사 엣지는 가까운 클라우드 엣지까지만 터널을 치고, 그다음은 클라우드 사업자의 백본을 탄다. 여기서 한 걸음 더 나가면 보안 검사까지 클라우드로 옮긴 SASE가 된다. 지사 인터넷을 바로 내보내면(local breakout) 본사 방화벽을 거치지 않으니, 그 검사를 어딘가에서 해 줘야 하기 때문이다. 사용자와 기기 단위로 접근을 정하는 쪽은 [제로 트러스트 글](/posts/zero-trust-architecture)과 이어진다.

## 무엇을 고르나: MPLS를 다 걷어 낼까

SD-WAN이 나오면서 "이제 MPLS는 필요 없다"는 말이 돌았다. 실제 선택은 그렇게 단순하지 않다.

인터넷만으로 충분한 경우가 많아졌다. 직원 열 명 남짓한 영업 지사, 업무가 대부분 SaaS인 지사는 일반 인터넷 두 회선(서로 다른 통신사)과 LTE 백업에 SD-WAN을 얹으면 MPLS보다 싸고 SaaS도 빠르다. 개통도 며칠이면 된다.

MPLS가 남는 경우도 분명하다. 공장 제어망이나 금융 거래처럼 지연과 손실을 계약으로 보장받아야 하는 곳, 인터넷 품질이 나쁜 지역의 거점, 규제 때문에 공중망 경유 자체를 피해야 하는 곳이다. 그래서 흔한 결론은 혼합이다. 큰 거점은 MPLS를 유지하되 대역을 줄이고 인터넷 회선을 더해 SD-WAN으로 묶고, 작은 지사는 인터넷만 쓴다. 회선비가 줄어든 만큼 SD-WAN 장비와 라이선스 비용이 생긴다는 점도 계산에 넣는다.

설계할 때 자주 놓치는 점도 있다. 두 인터넷 회선이 결국 같은 통신사, 같은 관로로 건물에 들어오면 굴착 공사 한 번에 둘 다 끊긴다. 회선 다중화는 통신사와 물리 경로까지 나눠야 의미가 있다. 그리고 SD-WAN은 흐름을 회선 사이로 옮기니, 가는 길과 오는 길이 달라지는 비대칭 경로가 생기기 쉽다. 중간에 상태를 기억하는 방화벽이 있으면 돌아오는 패킷을 모르는 연결로 보고 버린다.

## 지사가 느리다는 전화를 받으면

첫 장면처럼 "지사에서 SaaS가 느리다"는 전화가 오면 이 순서로 좁힌다.

```bash
# 1. 트래픽이 어디로 나가는지 본다. 본사 방화벽 주소가 중간에 보이면 백홀 중이다
traceroute -n outlook.office365.com

# 2. 경로 MTU를 본다. 터널 구간에서 pmtu 값이 1500보다 작게 떨어지는지 확인한다
tracepath -n 10.9.0.5

# 3. 큰 패킷이 지나가는지 직접 본다 (DF 비트를 켜고 1372바이트 + 헤더 28 = 1400)
ping -M do -s 1372 -c 3 10.9.0.5

# 4. VRF가 있는 장비라면 VRF를 지정해서 확인한다
ip route show vrf vrf-sales
sudo ip vrf exec vrf-sales ping -c 3 10.9.0.5
```

traceroute에 본사 주소가 보이면 local breakout 정책이 그 앱에 걸리지 않은 것이다. SaaS 주소 목록이 낡았거나, 앱 판별이 실패했을 수 있다. 작은 ping은 되는데 3번이 실패하면 MTU다. 터널 MTU와 MSS 클램핑을 확인한다. VRF를 지정하면 되고 안 하면 안 되는 건 장애가 아니라 확인 방법의 문제다. 특정 시간대에만 느리다면 SD-WAN 컨트롤러에서 그 지사 회선의 손실·지터 그래프를 먼저 본다. 회선이 기준을 넘었는데도 흐름이 옮겨지지 않았다면 정책의 판정 기준이나 앱 분류를 의심한다.

## 표를 나누고, 라벨을 붙이고, 길을 고른다

WAN은 통신사 망을 빌려 먼 곳을 잇는 일이다. MPLS는 망 안에서 라벨만 보고 패킷을 넘기고, 라벨을 두 겹 쌓아 고객별 VPN을 얹는다. VRF는 라우터 안의 경로표를 나눠 겹치는 주소를 가르고, RD는 경로를 구분하고 RT는 누가 받을지 정한다. 인터넷 위에서는 GRE로 무엇이든 담고 IPsec으로 암호화한 터널을 친다. SD-WAN은 그 터널들을 회선마다 재서 앱 단위로 고르고, 정책을 중앙에서 내린다. 트래픽이 클라우드로 옮겨 간 만큼 본사를 돌아가는 구조를 줄이는 게 요즘 WAN 설계의 방향이다.

## 면접에서 나올 만한 질문

### MPLS는 어떻게 패킷을 전달하나요?

PE 라우터가 들어온 IP 패킷에 4바이트 라벨을 붙이고, 망 안의 P 라우터는 IP 헤더 대신 라벨만 보고 LFIB에 따라 다음 라벨로 바꿔 넘깁니다. 라벨 표는 LDP 같은 프로토콜로 이웃끼리 나눠 만듭니다. 출구 PE 바로 앞 라우터가 라벨을 떼는 PHP 덕에 출구 PE는 IP 조회만 하면 됩니다. 지금은 속도보다 트래픽 엔지니어링과 VPN을 위해 씁니다.

### MPLS L3VPN에서 겹치는 고객 주소는 어떻게 구분하나요?

PE에 고객마다 VRF를 두어 경로표를 나누고, PE끼리 MP-BGP로 경로를 나눌 때 RD를 앞에 붙여 같은 프리픽스를 서로 다른 경로로 만듭니다. 어느 VRF가 그 경로를 받을지는 RT의 import/export로 정합니다. 데이터는 바깥 전송 라벨과 안쪽 VPN 라벨 두 겹을 달고 가고, 출구 PE는 VPN 라벨로 어느 VRF인지 압니다.

### RD와 RT는 무엇이 다른가요?

RD는 BGP 안에서 겹치는 주소를 유일하게 만드는 구분자일 뿐이고, 경로를 누가 받을지는 정하지 않습니다. RT는 경로에 붙는 확장 커뮤니티로, VRF가 어떤 RT의 경로를 가져오고 어떤 RT를 붙여 내보낼지 정해 VPN의 연결 모양을 만듭니다. 새 지사가 본사와 안 통하면 RT import 설정부터 봅니다.

### VRF와 VLAN은 어떻게 다른가요?

VLAN은 2계층에서 브로드캐스트 도메인을 나누고, VRF는 3계층에서 라우터의 경로표를 나눕니다. 경로표가 하나인 라우터에서는 다른 VLAN끼리 바로 라우팅되지만, VRF가 다르면 같은 라우터를 지나도 서로 경로가 없고 주소가 겹쳐도 됩니다. 실무에서는 VLAN 서브인터페이스를 VRF에 넣어 함께 씁니다.

### GRE over IPsec은 왜 쓰나요?

GRE는 암호화가 없지만 멀티캐스트와 라우팅 프로토콜까지 담을 수 있고, IPsec은 암호화하지만 정책 기반이면 정해진 유니캐스트만 넣습니다. 그래서 GRE로 감싸 그 위에서 OSPF나 BGP를 돌리고, GRE 패킷 전체를 IPsec으로 암호화합니다. 오버헤드가 커서 터널 MTU와 TCP MSS를 낮춰야 하고, 요즘은 IPsec VTI 같은 라우트 기반 VPN으로 대신하기도 합니다.

### SD-WAN은 어떤 원리로 회선을 고르나요?

지사 엣지가 MPLS, 인터넷, LTE 같은 여러 회선 위에 터널을 치고, 프로브로 터널마다 지연·손실·지터를 계속 잽니다. 트래픽을 앱 단위로 분류한 뒤 중앙 컨트롤러가 내려 준 정책의 SLA 기준과 비교해, 기준을 지키는 회선 중 우선순위가 높거나 싼 쪽으로 보냅니다. SaaS는 지사에서 바로 인터넷으로 내보내고, 회선이 나빠지면 그 앱 흐름만 다른 회선으로 옮깁니다.

### SD-WAN이 MPLS를 완전히 대체하나요?

작은 지사나 SaaS 위주 지사는 인터넷 두 회선과 LTE에 SD-WAN만으로 충분한 경우가 많습니다. 하지만 지연·손실을 계약으로 보장받아야 하는 거점, 인터넷 품질이 나쁜 지역, 규제상 공중망을 피해야 하는 곳은 MPLS를 남깁니다. 그래서 큰 거점은 MPLS와 인터넷을 SD-WAN으로 묶고 작은 지사는 인터넷만 쓰는 혼합이 흔합니다.

### SD-WAN을 도입한 뒤 일부 연결만 간헐적으로 끊깁니다. 무엇을 의심하나요?

흐름이 회선 사이로 옮겨지면서 가는 길과 오는 길이 달라진 비대칭 경로를 먼저 의심합니다. 중간의 상태 기반 방화벽이 돌아오는 패킷을 모르는 연결로 보고 버립니다. 회선이 SLA 기준 근처에서 오르내려 흐름이 자주 바뀌는 flapping도 확인하고, 판정 횟수와 유지 시간을 늘려 안정시킵니다.
