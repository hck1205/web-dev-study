`race`와 `car`를 붙이면 `racecar`가 된다. 앞에서 읽어도 뒤에서 읽어도 같은 회문이다. 단어 목록에서 이렇게 붙였을 때 회문이 되는 순서쌍을 모두 찾는 것이 [LeetCode 336. Palindrome Pairs](https://leetcode.com/problems/palindrome-pairs/)다.

Hard 문제이고, 처음 보면 "모든 쌍을 붙여 본다" 말고는 떠오르지 않는다. 열쇠는 회문의 모양을 쪼개 보는 데 있다. `racecar`를 `race` + `car`로 보면, `car`를 뒤집은 `rac`가 `race`의 앞부분이고 남은 `e`가 회문이다. 이 관찰 하나로 쌍을 찾는 문제가 "뒤집은 단어를 찾는" 문제로 바뀐다. 이 글은 모든 쌍을 붙여 보는 풀이부터, 단어를 잘라 해시맵에 묻는 풀이, 뒤집은 단어의 트라이를 내려가는 풀이 두 가지까지 네 가지를 본다. 재 보면 해시맵 풀이가 트라이보다 빠른데, 그 이유도 따져 본다. 트라이 자체는 [Implement Trie](/posts/leetcode-implement-trie)에서 만들었다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 붙였을 때 회문이 되는 순서쌍

입력은 서로 다른 단어의 배열 `words`다. `i`와 `j`가 다르고 `words[i] + words[j]`가 회문인 쌍 `[i, j]`를 모두 돌려준다. 순서쌍이라 `[i, j]`와 `[j, i]`는 다른 쌍이고, 답의 순서는 상관없다.

- 단어 수 n은 5,000 이하, 단어 길이 k는 300 이하. 모두 소문자.
- 빈 문자열도 단어로 나올 수 있다.

n이 5,000이면 순서쌍이 약 2,500만 개다. 쌍마다 최대 600글자를 붙여 회문인지 보면 150억 번까지 간다. 반대로 k는 300으로 작다. 단어 하나를 자를 수 있는 자리가 301개뿐이라는 뜻이다. 풀이는 n² 대신 n·k²을 노린다.

이 글에서 쓸 예시다.

```text
words = [ab, ba, aba, b]
답    = [0,1] [1,0] [0,2] [2,1] [1,3] [3,0]
```

손으로 붙여 보자.

- `ab` + `ba` = `abba`, `ba` + `ab` = `baab`. 서로 뒤집은 단어라 양쪽 순서 모두 회문이다.
- `ab` + `aba` = `ababa`. 길이가 다른데도 된다.
- `aba` + `ba` = `ababa`. 같은 회문이 다른 쌍으로 만들어진다.
- `ba` + `b` = `bab`, `b` + `ab` = `bab`.

`ab`와 `b`는 `abb`, `bab` 중 `bab` 한쪽만 된다. 두 단어 길이가 같지 않아도 되고, 한쪽 순서만 될 수도 있다는 게 이 문제를 어렵게 만든다.

## 모든 쌍을 붙여 보기

정의 그대로 모든 순서쌍을 붙여서 확인한다.

```js
// s[lo..hi]가 회문인지 양 끝에서 좁혀 오며 확인한다
const isPal = (s, lo = 0, hi = s.length - 1) => {
  while (lo < hi) if (s[lo++] !== s[hi--]) return false;
  return true;
};

function palindromePairs(words) {
  const res = [];
  for (let i = 0; i < words.length; i++)
    for (let j = 0; j < words.length; j++)
      if (i !== j && isPal(words[i] + words[j])) res.push([i, j]);
  return res;
}
```

쌍이 n²개, 쌍마다 붙이고 확인하는 데 O(k)라 O(n²·k)다. 공간은 붙인 문자열 하나 O(k)와 답이다.

5,000개 무작위 단어로 재 보았다. 길이 1~10이면 1,433ms, 길이 1~300이면 2,614ms가 걸렸다. 무작위 단어는 첫 글자와 끝 글자부터 다른 경우가 많아 `isPal`이 바로 끝나서 이 정도다. 그래도 문자열을 2,500만 번 붙이는 비용은 피할 수 없고, LeetCode는 이 풀이를 시간 초과로 막는다.

이 풀이에는 짝을 "찾는" 생각이 없다. 단어 하나를 정했을 때 짝이 어떤 모양이어야 하는지 알면, 그 모양을 바로 찾아갈 수 있다.

## 회문을 가운데에서 쪼개 보면

`A + B`가 회문이라고 하자. 두 경우로 나뉜다.

A가 B보다 길거나 같다면, A를 `왼쪽 + 오른쪽`으로 자를 수 있다. 여기서 `왼쪽`은 B를 뒤집은 것이고, `오른쪽`은 그 자체로 회문이다. `race` + `car`라면 `race` = `rac` + `e`이고, `rac`는 `car`를 뒤집은 것, `e`는 회문이다.

```text
A = [ 뒤집은 B ][ 회문 ]
B =                    [ B ]
```

A가 B보다 짧다면 반대로 B를 `회문 + 오른쪽`으로 자를 수 있고, `오른쪽`이 A를 뒤집은 것이다. `dcb` + `abcd`라면 `abcd` = `a` + `bcd`이고, `bcd`는 `dcb`를 뒤집은 것, `a`는 회문이다.

그러니 단어 `w` 하나를 정하면, `w`를 자르는 자리마다 두 가지를 확인하면 된다.

1. `w[0..cut)`이 회문이면, `w[cut..]`를 뒤집은 단어가 목록에 있는지 본다. 있으면 그 단어가 `w` 앞에 붙는다. 쌍은 `[그 단어, w]`.
2. `w[cut..]`가 회문이면, `w[0..cut)`를 뒤집은 단어가 목록에 있는지 본다. 있으면 그 단어가 `w` 뒤에 붙는다. 쌍은 `[w, 그 단어]`.

1번은 `w`가 B 역할(뒤에 붙는 긴 쪽), 2번은 `w`가 A 역할(앞에 오는 긴 쪽)이다. "뒤집은 단어가 목록에 있나"는 뒤집은 단어를 미리 해시맵에 넣어 두면 O(k)에 답한다.

## 단어를 자르는 자리마다 해시맵에 묻기

```js
function palindromePairs(words) {
  // 뒤집은 단어 -> 원래 위치. "이걸 뒤집은 단어가 있나"를 바로 묻는다
  const index = new Map();
  words.forEach((w, i) => index.set([...w].reverse().join(""), i));

  const res = [];
  words.forEach((w, i) => {
    for (let cut = 0; cut <= w.length; cut++) {
      // 1. 왼쪽 w[0..cut)이 회문이면, 오른쪽을 뒤집은 단어가 w 앞에 붙는다
      if (isPal(w, 0, cut - 1)) {
        const j = index.get(w.slice(cut));
        if (j !== undefined && j !== i) res.push([j, i]);
      }
      // 2. 오른쪽 w[cut..]가 회문이면, 왼쪽을 뒤집은 단어가 w 뒤에 붙는다
      //    cut === w.length는 1번의 cut === 0과 같은 쌍을 다시 만드니 뺀다
      if (cut < w.length && isPal(w, cut, w.length - 1)) {
        const j = index.get(w.slice(0, cut));
        if (j !== undefined && j !== i) res.push([i, j]);
      }
    }
  });
  return res;
}
```

아래 그림에서 다음을 누르면 `aba`(위치 2)를 자르는 자리가 하나씩 옮겨 간다. 해시맵에는 뒤집은 단어 `ba → 0`, `ab → 1`, `aba → 2`, `b → 3`이 들어 있다. 강조된 칸이 왼쪽 조각이다.

단어 n개 × 자르는 자리 k + 1개 × (회문 확인 O(k) + 부분 문자열과 해시 O(k))라 시간은 O(n·k²)이다. 5,000 × 300² = 4.5억이 최악이지만, 회문이 아닌 쪽은 `isPal`이 첫 글자에서 끝나고 해시맵에 묻지도 않으니 실제로는 훨씬 적다. 공간은 해시맵 O(n·k)와 답이다.

### 두 번 세지 않으려면 한쪽 끝을 뺀다

2번 확인에서 `cut < w.length`를 빼면 어떻게 될까. `cut = w.length`에서 2번은 "오른쪽(빈 문자열)이 회문, 왼쪽(`w` 전체)을 뒤집은 단어가 있나"를 묻는다. 이건 `w`와 `w`를 뒤집은 단어 `v`의 쌍 `[w, v]`다. 그런데 `v`를 볼 때 1번의 `cut = 0`이 "왼쪽(빈 문자열)이 회문, 오른쪽(`v` 전체)을 뒤집은 단어(`w`)가 있나"로 같은 `[w, v]`를 또 만든다.

```js
// cut < w.length를 빼면
// [ab, ba] -> [[1,0],[0,1],[0,1],[1,0]] (정답은 [[0,1],[1,0]])
```

서로 뒤집은 단어 쌍이 모두 두 번씩 들어간다. 빈 문자열 조각을 한쪽에서만 허락하면 된다.

### 빈 문자열은 따로 다루지 않아도 된다

목록에 `""`가 있으면 모든 회문 단어와 양쪽으로 짝이 된다. `aba` + `""`도, `""` + `aba`도 회문이다. 위 코드는 이걸 따로 처리하지 않아도 잡는다. `""`를 뒤집어도 `""`라 해시맵에 들어 있기 때문이다. 회문 단어 `w`를 볼 때 1번의 `cut = w.length`에서는 왼쪽이 `w` 전체(회문)이고 오른쪽이 `""`라 `[""의 위치, w]`가 나온다. 2번의 `cut = 0`에서는 오른쪽이 `w` 전체이고 왼쪽이 `""`라 `[w, ""의 위치]`가 나온다. `["a", ""]`에 `[[0,1],[1,0]]`이 나온다.

빈 문자열 자신을 볼 때는 `cut = 0` 하나뿐이고, 1번에서 오른쪽 `""`를 물으면 자기 자신이라 빠진다. 2번은 `cut < 0`이 거짓이라 하지 않는다.

### Python과 Java로 쓰면

Python은 슬라이스와 뒤집기 `[::-1]`로 짧게 쓴다.

```python
from typing import List

class Solution:
    def palindromePairs(self, words: List[str]) -> List[List[int]]:
        index = {w[::-1]: i for i, w in enumerate(words)}  # 뒤집은 단어 -> 위치
        res = []
        for i, w in enumerate(words):
            n = len(w)
            for cut in range(n + 1):
                left, right = w[:cut], w[cut:]
                if left == left[::-1]:  # 왼쪽이 회문이면 오른쪽을 뒤집은 단어를 앞에
                    j = index.get(right)
                    if j is not None and j != i:
                        res.append([j, i])
                if cut < n and right == right[::-1]:  # 오른쪽이 회문이면 왼쪽을 뒤집은 단어를 뒤에
                    j = index.get(left)
                    if j is not None and j != i:
                        res.append([i, j])
        return res
```

`left == left[::-1]`은 뒤집은 복사본을 만들어 비교하니 양 끝에서 좁혀 오는 것보다 일을 더 한다. 그래도 C로 짠 내장 연산이라 Python에서는 반복문으로 한 글자씩 비교하는 것보다 대개 빠르다. 같은 5,000개 무작위 단어(길이 1~300)에서 347ms였다. `j != i`를 `if j`로 줄이면 위치 0이 거짓으로 읽혀 빠진다. `is not None`으로 쓴다.

Java는 `substring`과 `HashMap`이다.

```java
import java.util.*;

class Solution {
    private static boolean isPal(String s, int lo, int hi) {
        while (lo < hi) if (s.charAt(lo++) != s.charAt(hi--)) return false;
        return true;
    }

    public List<List<Integer>> palindromePairs(String[] words) {
        Map<String, Integer> index = new HashMap<>();
        for (int i = 0; i < words.length; i++)
            index.put(new StringBuilder(words[i]).reverse().toString(), i);
        List<List<Integer>> res = new ArrayList<>();
        for (int i = 0; i < words.length; i++) {
            String w = words[i];
            int n = w.length();
            for (int cut = 0; cut <= n; cut++) {
                if (isPal(w, 0, cut - 1)) {
                    Integer j = index.get(w.substring(cut));
                    if (j != null && j != i) res.add(List.of(j, i));
                }
                if (cut < n && isPal(w, cut, n - 1)) {
                    Integer j = index.get(w.substring(0, cut));
                    if (j != null && j != i) res.add(List.of(i, j));
                }
            }
        }
        return res;
    }
}
```

`j != i`에서 `j`는 `Integer`, `i`는 `int`라 `j`가 풀려서 값으로 비교된다. 둘 다 `Integer`였다면 `!=`가 객체 비교가 되어 127을 넘는 값에서 틀린다. 실제로 `Integer` 두 개에 1000을 넣고 `==`로 비교하면 `false`가 나왔다. 단어가 5,000개라 이 함정이 그대로 걸린다.

세 언어 모두 예시에 같은 여섯 쌍을 냈다(순서는 언어마다 다르다).

## 뒤집은 단어의 트라이를 내려가기

해시맵 풀이는 자르는 자리마다 부분 문자열을 새로 만들어 해시를 계산한다. 트라이로 바꾸면 `w`를 한 글자씩 읽으며 "지금까지 읽은 앞부분을 뒤집은 단어가 있나"를 한 칸씩 이어서 확인할 수 있다. 모든 단어를 뒤집어 트라이에 넣는다.

`w`를 앞에서부터 읽으며 트라이를 내려갈 때 두 가지 일이 생긴다.

1. 내려가는 도중 어떤 뒤집은 단어 `v`의 끝 표시를 만났다. `w`의 지금까지 읽은 부분이 `v`를 뒤집은 것이다. `w`의 남은 부분이 회문이면 `[w, v]`가 짝이다. 앞 절의 2번(`w`가 더 긴 쪽)이다.
2. `w`를 끝까지 읽었는데 그 아래에 뒤집은 단어가 더 이어진다. 그 단어의 남은 부분이 회문이면 `[w, 그 단어]`가 짝이다. `w`가 더 짧은 쪽이다.

[ab, ba, aba, b]를 뒤집어 넣은 트라이다. 노드 아래 글자는 "여기서 끝나는 뒤집은 단어"다.

### 끝까지 읽은 뒤 아래를 전부 뒤지기

2번을 가장 단순하게 하는 방법은, `w`를 다 읽은 노드에서 아래를 DFS로 전부 뒤지며 끝 표시마다 남은 글자가 회문인지 확인하는 것이다.

```js
function palindromePairs(words) {
  const root = { next: {}, word: -1 };
  words.forEach((w, j) => {
    let node = root;
    for (let k = w.length - 1; k >= 0; k--) node = node.next[w[k]] ??= { next: {}, word: -1 };
    node.word = j; // 뒤집은 w가 여기서 끝난다
  });
  const res = [];
  words.forEach((w, i) => {
    let node = root;
    for (let k = 0; k < w.length; k++) {
      // 1. 뒤집은 단어가 여기서 끝났고, w의 남은 부분이 회문이다
      if (node.word !== -1 && node.word !== i && isPal(w, k, w.length - 1)) res.push([i, node.word]);
      node = node.next[w[k]];
      if (!node) return; // 이 앞부분을 뒤집은 단어가 없다
    }
    // 2. w를 다 읽었다. 아래에서 남은 글자가 회문인 단어를 찾는다
    const dfs = (nd, rest) => {
      if (nd.word !== -1 && nd.word !== i && isPal(rest)) res.push([i, nd.word]);
      for (const ch in nd.next) dfs(nd.next[ch], rest + ch);
    };
    dfs(node, "");
  });
  return res;
}
```

1번에서 `w`를 끝까지 읽은 자리(`k === w.length`)는 확인하지 않는다는 점을 보자. 그 자리는 2번의 DFS 시작 노드라서 거기서 `rest = ""`로 잡힌다. 해시맵 풀이에서 `cut < w.length`로 한쪽을 뺀 것과 같은 이유다.

문제는 DFS다. `w`가 짧고 그 아래 가지가 크면, 예를 들어 `w = "a"`이고 `a`로 끝나는 단어가 수천 개면 매번 그 가지 전체를 걷고 `rest`를 이어 붙인다. 무작위 단어에서는 해시맵보다 9배(길이 1~300에서 657ms), `a`와 `b` 두 글자로만 된 단어에서는 21배(2,044ms) 느렸다. 두 글자 단어는 가지가 덜 갈라져서 DFS가 걷는 양이 커진다.

### 남은 부분이 회문인 단어를 노드에 미리 적어 두기

DFS가 매번 확인하는 "이 노드 아래에서 남은 부분이 회문인 단어"는 `w`와 상관없이 노드마다 정해져 있다. 그러니 트라이를 만들 때 한 번만 계산해 노드에 목록 `pal`로 적어 둔다.

뒤집은 단어 `r`을 넣을 때, 깊이 `d`의 노드에 서서 아직 넣지 않은 나머지 `r[d..]`가 회문이면 이 노드의 `pal`에 단어 위치를 넣는다. 원래 단어 `w`로 말하면 `r[d..]`는 `w[0..len-d)`, 곧 `w`의 앞부분이다. 끝 노드에는 나머지가 빈 문자열이니 언제나 넣는다.

| 노드 | 여기서 끝나는 뒤집은 단어 | pal (남은 부분이 회문인 단어) |
|---|---|---|
| 뿌리 | 없음 | aba(2), b(3) |
| b | b(3) | ab(0), b(3) |
| ba | ab(0) | ab(0) |
| a | 없음 | ba(1) |
| ab | ba(1) | ba(1), aba(2) |
| aba | aba(2) | aba(2) |

예를 들어 노드 `b`의 `pal`에 `ab(0)`가 있는 건, 뒤집은 `ab` = `ba`를 `b`까지 넣었을 때 남은 `a`가 회문이기 때문이다.

```js
function palindromePairs(words) {
  const root = { next: {}, word: -1, pal: [] };
  words.forEach((w, j) => {
    let node = root;
    for (let k = w.length - 1; k >= 0; k--) {
      // 뒤집은 단어의 남은 부분 = w[0..k]. 회문이면 이 노드에 적어 둔다
      if (isPal(w, 0, k)) node.pal.push(j);
      node = node.next[w[k]] ??= { next: {}, word: -1, pal: [] };
    }
    node.word = j;
    node.pal.push(j); // 남은 부분이 빈 문자열
  });

  const res = [];
  words.forEach((w, i) => {
    let node = root;
    for (let k = 0; k < w.length; k++) {
      // 1. 뒤집은 단어가 여기서 끝났다. w의 남은 부분이 회문이면 짝이다
      if (node.word !== -1 && node.word !== i && isPal(w, k, w.length - 1)) res.push([i, node.word]);
      node = node.next[w[k]];
      if (!node) return;
    }
    // 2. w를 다 읽었다. 남은 부분이 회문인 단어가 이미 적혀 있다
    for (const j of node.pal) if (j !== i) res.push([i, j]);
  });
  return res;
}
```

아래 그림은 네 단어를 차례로 트라이에 내려 보낸다. 기억 칸은 지금까지 찾은 쌍이다.

Python과 Java로도 같은 구조를 짜서 예시에 같은 여섯 쌍이 나오는 것을 확인했다. Java는 노드에 `Node[] next = new Node[26]`, `int word = -1`, `List<Integer> pal`을 두면 위 코드를 그대로 옮길 수 있다.

## 트라이가 해시맵보다 느린 이유

복잡도는 같은데 잰 값은 반대로 나왔다. 5,000개 단어, Node.js 22다.

```text
                       길이 1~10   길이 1~300   a·b만, 길이 1~300
모든 쌍                 1433ms      2614ms       3651ms
해시맵 + 자르기           30ms        74ms         97ms
트라이 + DFS              65ms       657ms        2044ms
트라이 + pal 목록         40ms      1131ms         791ms
```

길이 1~300 무작위 단어에서 pal 목록 트라이(1,131ms)가 해시맵(74ms)보다 15배 느리다. 두 가지 이유다.

첫째, 노드를 만드는 비용이다. 단어 5,000개 × 평균 150글자 = 노드 약 75만 개를 만들고, 노드마다 객체가 셋(노드, `next`, `pal`)이다. 해시맵 풀이는 뒤집은 단어 5,000개만 넣는다. 무작위 긴 단어는 서로 앞부분을 거의 공유하지 않으니 트라이가 아끼는 것도 없다.

둘째, 해시맵 풀이의 `O(n·k²)`는 최악일 뿐이다. 회문이 아닌 조각에서는 `isPal`이 첫 비교에서 끝나고, 회문인 조각에서만 부분 문자열을 만든다. 무작위 단어에서 회문인 조각은 아주 드물다.

Python에서도 같은 무작위 입력에서 해시맵 347ms, pal 목록 트라이 1,424ms로 같은 순서였다. 그러니 실무나 코딩 테스트에서는 해시맵 풀이를 먼저 쓰는 게 맞다. 트라이 풀이는 "뒤집은 단어의 앞부분을 한 글자씩 이어서 확인한다"는 생각을 보여 주는 데 의미가 있고, 면접관이 트라이 패턴으로 내면 이쪽을 말하면 된다.

## 네 풀이가 드는 비용

n은 단어 수, k는 단어 최대 길이다.

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 모든 쌍 붙이기 | O(n²·k) | O(k) | n이 수백 이하일 때. 정답 확인용 |
| 해시맵 + 자르는 자리마다 묻기 | O(n·k²) | O(n·k) | 실전 기본 답. 재 보면 가장 빠르다 |
| 뒤집은 단어 트라이 + DFS | 최악 O(n²·k) | O(n·k) | 트라이 풀이를 떠올리는 첫 단계 |
| 뒤집은 단어 트라이 + pal 목록 | O(n·k²) | O(n·k) | 트라이 패턴으로 물을 때. 단어가 앞부분을 많이 공유할 때 |

## 자기 자신과 짝짓거나 통째로만 뒤집으면 틀린다

가장 먼저 걸리는 실수는 `j !== i`를 빼먹는 것이다.

```js
// j !== i 확인이 없으면
// [aba, x] -> [[0, 0], [1, 1]] (정답은 [])
```

회문 단어는 뒤집어도 자기 자신이라 해시맵에서 자기를 찾는다. `aba` + `aba`도 회문이긴 하지만 문제는 서로 다른 두 단어를 원한다. 한 글자 단어 `x`도 회문이라 같은 이유로 걸린다.

두 번째는 단어를 통째로 뒤집은 짝만 찾는 것이다.

```js
// index.get(w)만 묻는다
words.forEach((w, i) => {
  const j = index.get(w);
  if (j !== undefined && j !== i) res.push([i, j]);
});
// [ab, ba, aba, b] -> [[0,1],[1,0]] (정답은 여섯 쌍)
```

`bat`/`tab` 같은 예시만 보고 짜면 이렇게 된다. 길이가 다른 쌍(`ab` + `aba`, `ba` + `b`)을 모두 놓친다. 자르는 자리를 돌아야 하는 이유가 이것이다.

그 밖에 조심할 것들이다.

- 2번 확인에 `cut < w.length`를 빼면 서로 뒤집은 쌍이 두 번 들어간다(위의 "한쪽 끝을 뺀다" 절).
- `isPal(w, 0, cut - 1)`에서 `cut = 0`이면 `hi`가 -1이라 빈 범위다. 반복문이 바로 끝나 참을 돌려주니 맞다. 이 경계를 `cut`부터 시작하는 코드로 바꾸다가 빈 조각을 빠뜨리기 쉽다.
- 해시맵 키로 `w.split("").reverse().join("")`을 쓰면 서로게이트 쌍(이모지 등)이 반으로 갈린다. 이 문제는 소문자뿐이라 상관없지만, 일반 문자열이면 `[...w]`로 코드 포인트 단위로 뒤집는다.

## 개수만 세거나 단어가 늘어나면

### 쌍의 개수만 세라면

같은 풀이에서 `res.push` 대신 개수를 더한다. 답이 최악 O(n²)개라 목록을 만드는 것 자체가 비쌀 때 의미가 있다. 예를 들어 `a`, `aa`, `aaa`, …처럼 모두 같은 글자인 단어 300개면 모든 순서쌍 89,700개가 답이다.

### 단어가 계속 추가된다면

새 단어 `x`를 자르는 자리마다 해시맵에 물으면 `x`가 긴 쪽(또는 길이가 같은 쪽)인 쌍은 모두 찾는다. 하지만 `x`가 짧은 쪽인 쌍은 기존의 긴 단어를 잘라야 나오니, 해시맵만으로는 기존 단어를 다 다시 봐야 한다. 여기서 트라이가 강하다. 뒤집은 단어의 트라이에서 `x`를 끝까지 읽은 노드의 `pal`이 곧 `[x, 긴 단어]` 쌍이다. `[긴 단어, x]` 쪽은 원래 단어로 만든 트라이를 하나 더 두고 뒤집은 `x`로 내려가면 같은 방식으로 찾는다. 새 단어는 두 트라이에 넣으며 지나는 노드의 `pal`을 갱신하면 된다.

### 회문 확인을 더 빠르게 하려면

단어마다 "앞부분 `w[0..cut)`이 회문인가"와 "뒷부분이 회문인가"를 모든 `cut`마다 합쳐서 O(k)에 미리 구할 수 있다. Manacher 알고리즘이나 `w + "#" + 뒤집은 w`에 KMP 실패 함수를 쓰는 방법이다. 그러면 회문 확인이 O(1)이 되고, 남는 비용은 부분 문자열 해시뿐이다. 롤링 해시까지 쓰면 전체 O(n·k)까지 내려간다. Manacher는 [Longest Palindromic Substring](/posts/leetcode-longest-palindromic-substring)에서 다룬다.

### 세 단어를 붙인다면

경우가 크게 늘어 이 방식을 그대로 넓히기 어렵다. 가운데 단어를 정하고 양옆을 찾는 식으로 O(n²·k) 정도가 현실적인 출발점이다. 면접에서는 "두 단어의 구조(뒤집은 단어 + 회문)를 세 조각으로 일반화하기 어렵다"고 말하고 브루트포스부터 줄여 가는 방향을 보여 주면 된다.

## 뒤집은 짝과 남는 회문으로 쪼갠다

`A + B`가 회문이면 긴 쪽이 "짧은 쪽을 뒤집은 것 + 회문"으로 쪼개진다. 그래서 단어마다 자르는 자리를 돌며, 회문인 쪽은 그대로 두고 반대쪽을 뒤집은 단어가 있는지 해시맵이나 뒤집은 단어의 트라이에 묻는다. 빈 조각을 한쪽에서만 허락해 두 번 세지 않고, 자기 자신을 빼면 O(n·k²)으로 끝난다. 재 보면 해시맵이 트라이보다 빠르다는 것도 기억해 둘 만하다.

## 면접에서 나올 만한 질문

### 모든 쌍을 확인하는 것보다 어떻게 빠르게 하나요?

`A + B`가 회문이면 긴 쪽을 "짧은 쪽을 뒤집은 것"과 "회문"으로 자를 수 있다. 그래서 단어마다 자르는 자리 k + 1개를 돌며, 한쪽이 회문이면 다른 쪽을 뒤집은 단어가 있는지 해시맵에 묻는다. 쌍 n²개 대신 단어 n개 × 자리 k개라 O(n·k²)이고, n이 5,000, k가 300인 제약에서 이쪽이 맞다.

### 왜 한쪽에서는 cut === w.length를 빼나요?

서로 뒤집은 두 단어 `w`, `v`의 쌍 `[w, v]`가 `w`의 끝 자르기와 `v`의 처음 자르기에서 한 번씩, 두 번 나오기 때문이다. 빈 조각을 한쪽 확인에서만 허락하면 한 번만 센다. 빼지 않으면 `[ab, ba]`에 네 쌍이 나온다.

### 빈 문자열이 있으면 어떻게 되나요?

모든 회문 단어와 양쪽 순서로 짝이 된다. 따로 처리하지 않아도 빈 문자열을 뒤집은 빈 문자열이 해시맵에 들어 있어서, 회문 단어를 자르는 양 끝 자리에서 자연스럽게 잡힌다. 빈 문자열 자신은 자기와 짝이 되지 않게 `j !== i`가 막는다.

### 트라이로는 어떻게 푸나요?

모든 단어를 뒤집어 트라이에 넣고, 단어 `w`를 앞에서부터 읽으며 내려간다. 도중에 끝 표시를 만나면 `w`의 남은 부분이 회문인지 보고, `w`를 다 읽으면 그 노드 아래에서 남은 부분이 회문인 단어들을 짝으로 얻는다. 이 목록을 트라이를 만들 때 노드마다 미리 적어 두면 DFS가 필요 없다.

### 트라이와 해시맵 중 무엇이 빠른가요?

복잡도는 둘 다 O(n·k²)인데, 재 보면 해시맵이 빨랐다. 길이 300까지인 무작위 단어 5,000개에서 해시맵 74ms, pal 목록 트라이 1,131ms였다. 트라이는 노드 75만 개와 목록을 만드는 비용이 크고, 해시맵은 회문인 조각에서만 부분 문자열을 만들어 실제 일이 적다.

### 시간 복잡도를 더 줄일 수 있나요?

회문 확인이 O(k)라서 생긴 k²이다. Manacher나 KMP 실패 함수로 모든 앞부분과 뒷부분의 회문 여부를 O(k)에 미리 구하면 확인이 O(1)이 되고, 롤링 해시로 부분 문자열 해시까지 이어서 구하면 O(n·k)까지 내려간다. 다만 해시 충돌을 감수해야 한다.

### 답이 몇 개까지 나올 수 있나요?

최악 O(n²)이다. 모든 단어가 같은 글자로만 되어 있으면(`a`, `aa`, `aaa`, …) 어떤 두 단어를 붙여도 회문이라 모든 순서쌍이 답이다. 그래서 출력 크기까지 생각하면 어떤 풀이도 O(n²)보다 빨라질 수 없는 입력이 있다.
