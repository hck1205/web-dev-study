해외 리전에 둔 API가 느리다는 말을 듣고 회선을 100Mbps에서 1Gbps로 올렸다. 대용량 백업은 확실히 빨라졌는데, 정작 API 응답 시간은 그대로였다. 같은 "빠르다"라는 말이 전혀 다른 숫자를 가리키고 있었다.

네트워크가 빠르다는 말에는 세 가지 숫자가 섞여 있다. 지연(latency), 대역폭(bandwidth), 처리량(throughput)이다. 이 글은 셋이 각각 무엇이고 서로 어떻게 묶여 있는지, 어떤 일에는 어느 숫자가 결정적인지를 직접 재 보며 정리한다. TCP가 창을 키우고 줄이는 원리와 대역폭 지연 곱의 계산은 [TCP 신뢰성과 혼잡 제어 글](/posts/tcp-reliability-congestion)에 있으니 여기서는 그 결과가 실제 전송 시간에 어떻게 나타나는지를 본다. 병목에서 줄을 관리하고 트래픽을 나누는 일은 [트래픽 셰이핑 글](/posts/traffic-shaping-qos)로 이어진다.

## 실험 망: 지연과 대역폭을 따로 돌리는 장치

셋을 떼어서 보려면 지연과 대역폭을 각자 마음대로 바꿀 수 있어야 한다. Ubuntu 24.04 컨테이너에 network namespace 세 개로 클라이언트 — 중간 — 서버를 이었다. 대역폭은 중간이나 서버의 나가는 문에 커널의 `tbf`(토큰 버킷 필터)를 걸어 제한했다.

지연은 원래 `tc qdisc ... netem delay 50ms`로 만든다. 그런데 이 실습 커널에는 netem 모듈이 빠져 있어서, 중간 namespace에 TUN 장치 두 개를 두고 그 사이에서 패킷을 붙잡았다가 정해진 시간 뒤에 놓아주는 Go 프로그램(약 70줄)을 끼웠다. 커널이 아니라 프로그램이 지연을 만든다는 점만 다르고, 양 끝의 TCP가 보는 왕복 시간은 진짜다. 보통의 Ubuntu에서 따라 할 때는 netem을 쓰면 된다.

```bash
# 일반 Ubuntu에서 같은 조건 만들기: 나가는 쪽에 50ms 지연과 1% 손실
sudo tc qdisc add dev eth0 root netem delay 50ms loss 1%
# 지연에 대역폭 제한까지 겹치기 (netem 아래에 tbf를 단다)
sudo tc qdisc replace dev eth0 root handle 1: netem delay 50ms
sudo tc qdisc add dev eth0 parent 1:1 handle 10: tbf rate 100mbit burst 64kb latency 50ms
# 되돌리기
sudo tc qdisc del dev eth0 root
```

## 세 숫자가 가리키는 것

비유를 하나만 쓰자. 네트워크를 고속도로라고 하면, 대역폭은 차선 수다. 1초에 최대 몇 대가 지나갈 수 있는지를 정한다. 지연은 한 대가 출발해서 도착할 때까지 걸리는 시간이다. 도로 길이와 톨게이트, 정체가 정한다. 처리량은 실제로 1초 동안 도착한 차의 수다. 차선이 넓어도 차를 띄엄띄엄 보내면 처리량은 작다.

- 대역폭은 길의 성질이다. 단위는 초당 비트(bps)다. 회선 계약서와 NIC 사양에 적힌 숫자가 이것이다.
- 지연은 한 조각이 끝에서 끝까지 가는 시간이다. 네트워크에서는 대개 왕복 시간(RTT)으로 잰다. ping이 보여 주는 값이다.
- 처리량은 실제로 옮겨진 양이다. 대역폭을 넘을 수 없고, 프로토콜과 지연, 손실, 양 끝의 처리 능력에 따라 그보다 작아진다. 처리량 가운데 재전송과 헤더를 뺀 쓸모 있는 데이터만 센 것을 goodput이라고 부른다.

단위에서 자주 틀린다. 네트워크는 비트, 파일은 바이트로 센다. 100Mbps 회선에서 내려받기 창에 12MB/s가 찍히면 정상이다(100 ÷ 8 = 12.5). iperf3 출력에 `MBytes`와 `Mbits/sec`가 한 줄에 같이 나오는 것도 그래서다. 그리고 회선 제조사는 1Mbps를 100만 bps로 세지만, 운영체제는 1MB를 1048576바이트로 셀 때가 많아서 숫자가 몇 % 더 어긋난다.

네 조각은 성질이 다르다. 전파 지연은 거리로 정해지는 바닥이라서 돈을 써도 줄지 않는다. 서울에서 미국 서부까지 직선으로 약 9000km라면 광섬유로 한 방향 45ms, 왕복 90ms가 물리적인 최소다. 실제 케이블은 직선이 아니고 중간에 장비도 많아서 보통은 이보다 꽤 길게 나온다. 이 바닥을 줄이는 방법은 서버를 사용자 가까이 두는 것뿐이고, CDN과 엣지가 존재하는 이유다([CDN과 애니캐스트 글](/posts/cdn-edge-anycast)).

직렬화 지연은 대역폭으로 줄어든다. 대역폭을 열 배로 늘리면 이 조각만 10분의 1이 된다. 패킷 하나에 1.2ms이던 것이 0.12ms가 되는 정도라서, 작은 요청 하나의 전체 시간에서는 티가 거의 안 난다. 처음 장면에서 회선을 올려도 API가 그대로였던 이유가 이것이다. 바뀐 조각이 원래 작았다.

줄 서기 지연은 가장 변덕스럽다. 평소엔 0인데 누군가 큰 파일을 올리기 시작하면 수백 ms가 된다. 평균 지연은 괜찮은데 가끔 튀는 지연은 대부분 이 조각에서 나온다. [트래픽 셰이핑 글](/posts/traffic-shaping-qos)에서 이 줄을 직접 재고 줄인다.

## 작은 파일은 왕복 횟수가, 큰 파일은 대역폭이 정한다

실험 망에서 대역폭(10Mbps, 100Mbps)과 왕복 시간(약 2ms, 약 100ms)을 바꿔 가며 10KB 파일과 10MB 파일을 HTTP로 받았다. TLS 없는 평문 HTTP다.

```bash
# 조건마다 curl의 단계별 시간 측정
curl --noproxy '*' -s -o /dev/null \
  -w 'connect=%{time_connect}s ttfb=%{time_starttransfer}s total=%{time_total}s speed=%{speed_download}B/s\n' \
  http://10.10.2.2:8080/small.bin
```

10KB 파일부터 보자. 대역폭을 10Mbps에서 100Mbps로 열 배 올려도 6.4ms가 6.8ms로, 203ms가 204ms로, 사실상 그대로다. 반면 왕복 시간을 2ms에서 100ms로 늘리자 30배 넘게 느려졌다. 100ms 줄을 읽어 보면 `connect`가 0.101초, `ttfb`가 0.203초다. TCP 연결에 왕복 한 번, 요청을 보내고 첫 바이트를 받는 데 왕복 한 번, 합해서 두 번이다. 파일을 싣는 시간은 그 뒤 0.00005초뿐이다. 작은 요청의 시간은 거의 전부가 "몇 번 왕복하느냐 × 왕복 시간"이다.

10MB 파일은 반대다. 왕복 2ms에서 대역폭을 열 배 올리자 8.7초가 0.88초가 됐다. 이 크기에서는 데이터를 싣는 시간이 전부다. 그런데 100Mbps에 왕복 100ms 줄은 1.67초로, 계산상 최소(왕복 두 번 0.2초 + 10MB 싣기 0.84초 = 약 1.04초)보다 0.6초 더 걸렸다. TCP가 처음에 작게 보내다가 왕복마다 창을 두 배씩 키우는 느린 시작 때문이다. 왕복이 길면 창이 커지는 데도 오래 걸린다.

HTTPS라면 여기에 TLS 왕복이 더해진다. TLS 1.3은 한 번, TLS 1.2는 두 번이다. 처음 접속이라면 DNS 조회도 붙는다. 왕복 100ms 거리에서 새 HTTPS 연결로 작은 API 하나를 부르면 이렇게 쌓인다.

그래서 지연을 줄이는 일은 대개 왕복 횟수를 줄이는 일이다. keep-alive로 연결을 재사용하고([HTTP 버전 글](/posts/http-versions)), TLS 1.3과 세션 재개를 쓰고, 여러 번 나눠 부르던 API를 한 번으로 묶고, 리다이렉트를 없앤다. 각각이 왕복 하나씩을 지운다.

아래 함수는 이 관찰을 아주 단순한 식으로 만든 것이다. 연결을 여는 데 드는 왕복 수(`setupRtts`, TCP만이면 1, TCP와 TLS 1.3이면 2)에 요청·응답 왕복 1을 더하고, 데이터를 싣는 시간을 더한다. 느린 시작은 무시한다. 0.1ms 단위로 반올림해 돌려주게 만들어 보자.

## 창이 작으면 넓은 길도 좁게 쓴다

TCP는 상대의 확인(ACK)을 받지 못한 데이터를 창 크기만큼만 띄워 둘 수 있다. 그래서 한 연결의 처리량은 "창 ÷ 왕복 시간"을 넘지 못한다. 길이 아무리 넓어도 창이 작고 길이 길면 차를 띄엄띄엄 보내게 된다. 이 계산과 리눅스 버퍼 자동 조정은 [TCP 글](/posts/tcp-reliability-congestion)에서 다뤘으니, 여기서는 실제로 재 본다. 대역폭 100Mbps에 소켓 버퍼를 64KB로 묶고(`iperf3 -w 64K`) 왕복 시간만 바꿨다.

```bash
# 서버가 보내는 방향(-R)으로 6초, 소켓 버퍼 64KB
iperf3 -c 10.10.2.2 -t 6 -R -w 64K
```

```text
== one-way 0ms, -w 64K
[  5]   0.00-6.00   sec  68.4 MBytes  95.6 Mbits/sec                  receiver
== one-way 25ms, -w 64K
[  5]   0.00-6.00   sec  7.88 MBytes  11.0 Mbits/sec                  receiver
== one-way 50ms, -w 64K
[  5]   0.00-6.00   sec  4.00 MBytes  5.59 Mbits/sec                  receiver
```

계산으로 맞춰 보면 64KB(524288비트) ÷ 0.05초 = 10.5Mbps, ÷ 0.1초 = 5.2Mbps다. 실측 11.0과 5.59가 거의 그대로 맞는다. 왕복 0.3ms에서는 64KB로도 100Mbps를 다 채웠다. 같은 설정이 가까운 곳에서는 멀쩡하고 먼 곳에서만 느려지는 이유다. 반대로 버퍼 제한을 풀면 왕복 100ms에서도 84.7Mbps가 나왔다.

```text
== one-way 50ms (버퍼 자동 조정)
[  5]   0.00-6.00   sec  60.6 MBytes  84.7 Mbits/sec                  receiver
```

연결을 넷으로 나누면 창도 넷이 되니 처리량이 네 배 가까이 된다.

```bash
# 같은 64KB 제한으로 연결 4개를 동시에
iperf3 -c 10.10.2.2 -t 6 -R -w 64K -P 4
```

```text
[SUM]   0.00-6.00   sec  15.5 MBytes  21.7 Mbits/sec                  receiver
```

다운로드 가속기와 `aws s3 cp`의 멀티파트, 병렬 rsync가 빠른 이유가 이것이다. 다만 병렬 연결은 원인을 고치는 게 아니라 우회하는 방법이다. 버퍼를 작게 박아 둔 설정(`SO_RCVBUF` 직접 지정, 오래된 프록시)이 있으면 그걸 먼저 찾는다.

## 보낸 양과 받은 양이 다르다

처리량을 잴 때는 어느 쪽에서 셌는지 본다. 왕복 50ms에 손실 1%를 걸고 100Mbps 길에서 혼잡 제어만 바꿔 보냈다.

```bash
# 혼잡 제어를 지정해서 8초 전송
iperf3 -c 10.10.2.2 -t 8 -R -C cubic
iperf3 -c 10.10.2.2 -t 8 -R -C bbr
```


`sender` 줄은 보낸 쪽이 내보낸 양이고 `Retr`는 다시 보낸 세그먼트 수다. `receiver` 줄이 실제로 받은 쓸모 있는 데이터, goodput에 가깝다. CUBIC은 손실을 볼 때마다 창을 줄여서 100Mbps 길에서 3.15Mbps밖에 못 썼다. 손실 기반 처리량을 어림하는 Mathis 식(1460바이트 × 8 ÷ 0.05초 × 1.22 ÷ √0.01 ≈ 2.85Mbps)과 비슷한 수준이다. BBR은 손실을 혼잡 신호로 보지 않아 89.6Mbps를 냈지만 625번을 다시 보냈다. 둘의 차이는 TCP 글에서 다뤘다.

손실이 없어도 처리량과 goodput은 다르다. 1500바이트 패킷에서 IP와 TCP 헤더(타임스탬프 옵션 포함 52바이트)를 빼면 데이터는 1448바이트, 약 96.5%다. tbf는 이더넷 헤더까지 포함한 1514바이트를 세니 1448 ÷ 1514 ≈ 95.6%이고, 실험 첫 줄의 95.6Mbps와 그대로 맞는다. 실제 회선은 프레임 앞뒤의 프리앰블과 간격(약 24바이트)까지 쓰니 100Mbps에서 TCP로 받을 수 있는 건 약 94Mbps다. 회선 속도를 정확히 다 받는 측정값은 없다고 보면 된다.

## 평균은 꼬리를 숨긴다

지연은 평균으로 보면 안 된다. 왕복 50ms 길에서 10KB 파일을 300번 받고, 손실 1%를 건 다음 다시 300번 받았다. 정렬해서 백분위를 뽑았다.

```bash
# 300번 받아 걸린 시간을 정렬하고 p50, p90, p99, 최댓값
for i in $(seq 300); do
  curl --noproxy '*' -s -o /dev/null -w '%{time_total}\n' http://10.10.2.2:8080/small.bin
done | sort -n | awk '{a[NR]=$1} END{printf "p50=%.0fms p90=%.0fms p99=%.0fms max=%.0fms\n", a[int(NR*0.5)]*1000, a[int(NR*0.9)]*1000, a[int(NR*0.99)]*1000, a[NR]*1000}'
```

```text
loss=0 n=300 p50=104ms p90=105ms p99=109ms max=128ms
loss=0.01 n=300 p50=104ms p90=154ms p99=1177ms max=2141ms
```

손실 1%에서 p50은 104ms로 그대로다. 대부분의 요청은 아무 일도 겪지 않았다. 그런데 p99는 1.2초, 최댓값은 2.1초다. 백 번에 한 번꼴로 연결을 여는 SYN이 사라지면, 리눅스는 1초를 기다렸다가 다시 보낸다(첫 재전송 타임아웃 1초, RFC 6298). 두 번 연속 사라지면 그 두 배를 더 기다린다. 데이터 패킷이 사라지면 빠른 재전송이나 최소 200ms의 타임아웃이 붙는다. 평균을 내면 이 몇 개가 나머지에 묻혀서 "평균은 괜찮다"는 결론이 나온다.

꼬리는 요청이 여러 서버를 거칠수록 커진다. 페이지 하나가 뒤에서 서버 100개에 동시에 묻고 모두 답해야 끝난다면, 각 서버의 p99가 1초여도 페이지 전체가 1초를 넘길 확률은 1 − 0.99¹⁰⁰ ≈ 63%다. 서버 하나에서는 드문 일이 사용자에게는 흔한 일이 된다. 그래서 SLO는 평균이 아니라 p95, p99로 정하고, 꼬리를 줄이는 장치(타임아웃 뒤 다른 서버에 다시 묻는 hedged request, 가장 느린 몇 개를 기다리지 않는 설계)를 따로 둔다.

## 지연이 늘면 처리량도 줄어든다

지연과 처리량은 따로 노는 숫자가 아니다. 줄을 서는 모든 시스템에는 리틀의 법칙이 성립한다. 안에 머무는 평균 개수(L) = 들어오는 속도(λ) × 머무는 평균 시간(W)이다.

이게 실무에서 어떻게 나오냐면, 동시에 처리할 수 있는 개수가 정해진 곳에서 지연이 곧 처리량의 천장이 된다. DB 커넥션 풀이 20개이고 쿼리 하나가 커넥션을 50ms 잡고 있으면, 그 풀로 낼 수 있는 최대는 20 ÷ 0.05초 = 초당 400개다. DB가 다른 리전으로 옮겨 가서 왕복 시간이 150ms 늘면 커넥션을 잡는 시간이 200ms가 되고, 같은 풀의 최대는 초당 100개로 떨어진다. 대역폭은 그대로인데 처리량이 4분의 1이 된다. 같은 원리로 스레드 풀, HTTP 클라이언트의 연결 수 상한, Kafka 컨슈머의 동시 처리 수가 모두 지연을 처리량으로 바꾼다. 풀 크기를 정하는 방법은 [커넥션 풀 글](/posts/connection-pool)에서 다룬다.

반대 방향도 있다. 처리량을 한계 가까이 밀어붙이면 지연이 폭발한다. 요청 하나에 10ms가 걸리는 서버 하나(초당 100개 처리)에 요청이 무작위 간격으로 들어온다고 하면, 단순한 대기열 모형(M/M/1)에서 평균 응답 시간은 1 ÷ (100 − 들어오는 속도)초다. 초당 50개면 20ms, 80개면 50ms, 90개면 100ms, 95개면 200ms다. 사용률 50%에서 95%로 가는 동안 지연은 열 배가 된다. 서버 사용률 목표를 100%가 아니라 60~70%로 잡는 이유가 이 곡선이다. [로드 밸런싱 알고리즘 글](/posts/load-balancing-algorithms)에서 느린 서버 앞에 줄이 끝없이 쌓인 것도 같은 현상이다.

## "느리다"를 숫자 셋으로 쪼개기

느리다는 보고를 받으면 셋 중 무엇이 문제인지부터 가른다. 처음 할 일은 curl의 단계별 시간이다. 실험 망에서 왕복 100ms를 걸고 받은 결과다.

```bash
# 단계별 누적 시간 (초)
curl --noproxy '*' -s -o /dev/null -w 'namelookup:    %{time_namelookup}\nconnect:       %{time_connect}\nappconnect:    %{time_appconnect}\npretransfer:   %{time_pretransfer}\nstarttransfer: %{time_starttransfer}\ntotal:         %{time_total}\nsize:          %{size_download} bytes\n' http://10.10.2.2:8080/small.bin
```

```text
namelookup:    0.000028
connect:       0.101103
appconnect:    0.000000
pretransfer:   0.101244
starttransfer: 0.203804
total:         0.203880
size:          10240 bytes
```

각 값은 요청 시작부터의 누적이다. `namelookup`이 크면 DNS, `connect − namelookup`이 크면 네트워크 왕복, `appconnect − connect`가 크면 TLS(여기선 평문이라 0), `starttransfer − pretransfer`가 크면 서버 처리, `total − starttransfer`가 크면 데이터 크기나 대역폭이다. 이 결과는 `connect`와 `starttransfer − pretransfer`가 같은 100ms라서 서버 처리는 거의 없고 왕복이 전부라는 걸 보여 준다. 서버 처리 시간이 따로 궁금하면 앱 로그의 처리 시간이나 `Server-Timing` 헤더와 비교한다.

그다음은 숫자마다 맞는 도구로 따로 잰다.

```bash
# 지연: 왕복 시간과 흔들림 (mdev가 크면 줄 서기를 의심)
ping -c 20 api.example.com
# 경로 위 어느 구간에서 지연이나 손실이 생기는지
mtr -rwc 50 api.example.com
# 대역폭: 서버에 iperf3 -s를 띄우고, 양방향을 따로 잰다
iperf3 -c server.example.com -t 10        # 클라이언트 → 서버
iperf3 -c server.example.com -t 10 -R     # 서버 → 클라이언트
# 열려 있는 연결의 실제 RTT, 창, 재전송
ss -tni dst server.example.com
```

현장에서 자주 보는 실수도 정리해 둔다.

- 작은 파일 하나로 대역폭을 잰다. 10KB 다운로드는 왕복 시간을 잴 뿐이다. 대역폭은 최소 몇 초 이상 이어지는 전송으로 잰다.
- 지연을 평균으로 보고 끝낸다. p99와 최댓값, 손실률을 같이 본다.
- 한 방향만 잰다. 집 회선과 클라우드 NAT는 업로드와 다운로드가 다르고, 병목도 방향마다 다르다.
- 같은 리전 안에서 재고 사용자도 그럴 거라고 생각한다. 사용자 쪽 왕복 시간은 RUM(실제 사용자 측정)이나 지역별 합성 모니터링으로 따로 본다.
- Mbps와 MB/s를 섞어 보고 "8배 느리다"고 오해한다.

## 처음 질문으로 돌아가면

회선을 열 배 올렸을 때 빨라진 건 데이터를 싣는 시간, 직렬화 지연뿐이었다. API 응답 하나는 왕복 몇 번이 시간의 거의 전부라서 그대로였다. 큰 백업은 대역폭이, 작은 요청은 왕복 횟수와 거리가, 동시성이 정해진 시스템의 처리량은 지연이 정한다. 그리고 지연은 평균이 아니라 꼬리로 본다. 다음 글에서는 이 셋이 한 병목에서 부딪힐 때, 큰 전송이 작은 요청의 지연을 망치지 않게 줄을 관리하는 법을 본다.

## 면접에서 나올 만한 질문

### 지연, 대역폭, 처리량은 어떻게 다른가요?

대역폭은 길이 1초에 실을 수 있는 최대 비트 수, 지연은 한 조각이 끝에서 끝까지 가는 시간, 처리량은 실제로 옮겨진 양이다. 처리량은 대역폭을 넘을 수 없고, 지연과 손실, 창 크기, 양 끝의 처리 능력 때문에 그보다 작아진다. 재전송과 헤더를 뺀 쓸모 있는 데이터만 센 것을 goodput이라고 한다.

### 대역폭을 올렸는데 API 응답이 빨라지지 않습니다. 왜 그런가요?

작은 응답의 시간은 대부분 왕복 횟수 × 왕복 시간이기 때문이다. 실험에서 10KB 파일은 대역폭을 열 배 올려도 그대로였고, 왕복 시간을 2ms에서 100ms로 늘리자 30배 느려졌다. 대역폭은 데이터를 싣는 시간만 줄인다. 연결 재사용, TLS 1.3, 요청 묶기, 서버를 가까이 두기처럼 왕복을 줄이는 쪽이 효과가 크다.

### 지연은 어떤 요소로 이루어지나요?

직렬화, 전파, 줄 서기, 처리 네 가지다. 전파는 거리로 정해져 광섬유에서 1km에 약 5µs이고 대역폭으로 줄지 않는다. 직렬화는 패킷 크기 ÷ 대역폭이라 대역폭으로 줄어든다. 줄 서기는 병목 큐에 쌓인 양에 따라 0에서 수백 ms까지 흔들려 지연 튐의 주범이고, 처리는 장비와 앱이 패킷과 요청을 다루는 시간이다.

### 1Gbps 회선인데 먼 곳으로 한 연결이 수 Mbps밖에 안 나옵니다. 무엇을 확인하나요?

창 크기 ÷ RTT가 그 연결의 상한이니 창이 작게 묶여 있는지 본다. 실험에서 64KB 버퍼는 RTT 100ms에서 5.6Mbps에 그쳤다. `ss -tni`로 실제 창과 RTT, 재전송을 보고, 소켓 버퍼를 직접 작게 지정한 설정이나 `tcp_rmem` 최대값, 윈도 배율을 지우는 중간 장비를 찾는다. 손실이 있다면 손실 기반 혼잡 제어의 한계도 함께 본다.

### 응답 시간을 평균으로 보면 왜 안 되나요?

꼬리를 숨기기 때문이다. 손실 1% 실험에서 p50은 104ms로 그대로였지만 p99는 SYN 재전송 때문에 1.2초였다. 요청 하나가 여러 서버를 거치면 꼬리를 겪는 사용자 비율은 더 커져서, 서버 100개를 기다리는 페이지는 각 서버 p99를 넘길 확률이 약 63%다. 그래서 p95, p99로 목표를 정하고 본다.

### 지연과 처리량은 어떤 관계인가요?

리틀의 법칙(L = λW)으로 묶여 있다. 동시 처리 수가 정해진 곳에서는 지연이 늘면 처리량의 상한이 그만큼 줄어서, 커넥션 20개 풀에서 요청 하나가 50ms면 초당 400개, 200ms면 100개가 최대다. 반대로 사용률을 한계 가까이 올리면 대기열 때문에 지연이 급격히 커져서, 처리 시간 10ms 서버는 사용률 50%에서 평균 20ms, 95%에서 200ms가 된다.

### 측정한 처리량이 회선 속도보다 항상 조금 낮은 이유는?

헤더와 프레임 오버헤드 때문이다. 1500바이트 패킷에서 IP·TCP 헤더를 빼면 데이터는 약 96%이고, 이더넷 프리앰블과 프레임 간격까지 치면 100Mbps에서 TCP로 받을 수 있는 건 약 94Mbps다. 여기에 손실이 있으면 재전송이 더해져 보낸 양과 받은 양이 벌어진다. iperf3의 sender와 receiver 줄을 비교하면 그 차이가 보인다.
