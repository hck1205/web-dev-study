<EasyIntro>
  회사 하나가 여러 고객에게 같은 프로그램을 빌려줄 때, 고객마다 컴퓨터를 따로 사 주면 돈이 너무 많이 든다. 그래서 보통은 한 시스템에 여러 고객을 함께 담는다. 이렇게 고객 여럿이 한 시스템을 같이 쓰는 방식을 멀티 테넌시라고 부르고, 고객 하나하나를 테넌트라고 부른다.

  아파트를 떠올리면 쉽다. 건물과 엘리베이터와 수도관은 함께 쓰지만, 집마다 현관문이 있어서 남의 집에는 들어갈 수 없다. 그런데 윗집이 밤새 공사를 하면 아랫집까지 시끄럽고, 한 집이 물을 엄청 쓰면 다른 집 수압이 떨어진다.

  그래서 두 가지를 챙겨야 한다. 하나는 남의 집 물건을 볼 수 없게 현관문을 단단히 다는 일이다. 다른 하나는 한 집이 너무 많이 쓰더라도 다른 집이 불편하지 않게 쓰는 양에 한도를 두는 일이다. 아주 큰 집은 아예 옆 동으로 옮겨 주기도 한다. 이 글은 이 현관문과 한도를 프로그램과 데이터베이스에서 어떻게 만드는지 다룬다.
</EasyIntro>

월요일 오전 10시, 모든 고객의 API 응답이 한꺼번에 느려졌다. 평소 p99가 180ms인데 3초를 넘는다. 배포도 없었고 트래픽 총량도 평소와 비슷하다. 원인을 찾아 보니 고객사 하나가 연말 정산용으로 3년 치 주문을 CSV로 내보내는 작업을 50개 동시에 걸어 두었다. 내보내기 워커가 DB 커넥션을 다 잡았고, 큰 순차 읽기가 버퍼 캐시를 밀어내서 다른 고객의 평범한 조회까지 디스크로 내려갔다.

여러 고객을 한 시스템에 담는 SaaS에서는 이런 일이 흔하다. 고객 하나를 테넌트(tenant, 세입자)라고 부르고, 여러 테넌트가 같은 코드와 인프라를 나눠 쓰는 구조를 멀티 테넌시라고 한다. 멀티 테넌시에는 두 가지 숙제가 따라온다. 데이터 격리(다른 테넌트의 데이터를 절대 못 보게)와 성능 격리(한 테넌트가 다른 테넌트를 느리게 만들지 못하게)다. 이 글은 이 두 숙제를 어느 층에서 어떤 도구로 푸는지, 그리고 섞어 둔 테넌트를 나중에 어떻게 떼어 내는지 따라간다. SQL은 PostgreSQL 16에서 직접 돌렸다.

이 주제의 다른 글: 역할과 권한, RLS의 기본 문법은 [역할과 권한](/posts/postgres-roles-security)에서, 리전 단위로 나누는 셀 구조는 [멀티 리전](/posts/multi-region)에서, 요청 수 제한 자체는 [요청 수 제한을 API에 붙이기](/posts/rate-limiting-in-practice)에서 다룬다. 느린 서버에서 자주 보이는 다른 모양들은 [성능 안티패턴](/posts/performance-antipatterns)에 모았다.

## 한 고객의 배치가 모두를 느리게 만든 아침

먼저 그날 무엇을 함께 쓰고 있었는지 적어 본다. 웹 서버, 내보내기 워커, DB 커넥션 풀, DB의 버퍼 캐시와 디스크 IOPS, 그리고 그 앞의 요청 큐. 테넌트마다 따로인 것은 하나도 없었다. 공유 자원에 한도가 없으면 가장 많이 요청하는 테넌트가 가장 많이 가져간다. 이렇게 한 테넌트가 공유 자원을 차지해 이웃을 느리게 만드는 현상을 노이지 네이버(noisy neighbor, 시끄러운 이웃)라고 부른다.

## 무엇을 나눠 쓰고 무엇을 따로 두나

격리 수준은 보통 세 가지 모델로 나눠 말한다. AWS의 SaaS 설계 문서에서 쓰는 이름이 널리 퍼졌다.

- 사일로(silo) 모델: 테넌트마다 스택을 따로 띄운다. DB도, 앱도, 때로는 클라우드 계정도 따로다. 격리는 가장 강하고 비용과 운영 부담도 가장 크다.
- 풀(pool) 모델: 모든 테넌트가 같은 앱과 같은 DB 테이블을 나눠 쓰고, 행마다 `tenant_id`로 구분한다. 가장 싸고 온보딩이 빠르지만 격리를 코드와 정책으로 지켜야 한다.
- 브리지(bridge) 모델: 층마다 다르게 고른다. 웹 계층은 함께 쓰고 DB만 테넌트별로 두거나, 일반 고객은 풀에 두고 큰 고객만 사일로로 빼는 식이다.

고르는 기준은 대개 숫자와 계약에서 나온다. 테넌트가 수만 개인 무료 요금제를 사일로로 돌리면 빈 DB 수만 개의 기본 비용을 내야 한다. 반대로 금융 고객이 "우리 데이터는 다른 회사와 같은 DB에 두지 말 것"을 계약서에 넣으면 그 고객만큼은 사일로가 된다. 그래서 실무에서 가장 흔한 답은 요금제별 브리지다. 무료와 소규모는 풀, 엔터프라이즈는 전용 DB나 전용 셀로 간다.

사일로가 공짜로 주는 것도 기억해 둔다. 테넌트별 백업과 복원(한 고객만 어제 시점으로 되돌리기), 테넌트별 데이터 위치(유럽 고객은 유럽 리전), 테넌트별 비용 계산이 거의 저절로 된다. 풀에서는 이걸 하나하나 직접 만들어야 한다. 반면 사일로에서는 스키마 변경 하나를 배포할 때도 DB 수만큼 마이그레이션을 돌려야 하고, 몇 개만 실패한 상태를 관리해야 한다.

## 데이터를 나누는 세 가지 방법

DB 층만 놓고 보면 선택지가 셋이다.

| 방법 | 격리 | 테넌트가 많아지면 | 흔한 쓰임 |
|---|---|---|---|
| 테넌트마다 DB | DB 경계 | 커넥션·마이그레이션·백업이 테넌트 수만큼 | 엔터프라이즈, 규제 고객 |
| 테넌트마다 스키마 | `search_path` | 카탈로그가 커진다(테넌트 × 테이블 수) | 수백 개 이하 |
| 공유 테이블 + `tenant_id` | 행 단위 | 큰 테이블 하나, 인덱스와 파티션 설계가 중요 | 대부분의 SaaS |

스키마 방식은 중간처럼 보이지만 숫자를 한 번 계산해 볼 만하다. 테이블이 50개인 서비스에 테넌트가 5,000개면 테이블이 25만 개다. 인덱스까지 치면 PostgreSQL 카탈로그(`pg_class`)에 수십만 줄이 생기고, 마이그레이션은 스키마마다 돌아야 하며, 커넥션마다 `search_path`를 바꾸는 코드가 풀링과 부딪친다. 테넌트 수가 작고 거의 늘지 않을 때 고르는 방법이다.

이 글의 나머지는 가장 흔한 공유 테이블 방식으로 간다. 예제 테이블은 이렇다.

```sql
-- 테넌트(고객사) 목록
CREATE TABLE tenants (
  id   bigint PRIMARY KEY,
  name text NOT NULL,
  plan text NOT NULL            -- free / pro / enterprise
);

-- 모든 테넌트의 주문이 한 테이블에 들어간다
CREATE TABLE orders (
  tenant_id  bigint NOT NULL REFERENCES tenants(id),
  id         bigint GENERATED ALWAYS AS IDENTITY,
  amount     int NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, id)   -- 기본 키에 tenant_id를 앞에 둔다
);

INSERT INTO tenants VALUES (1, 'acme', 'enterprise'), (2, 'blue', 'free'), (3, 'cobalt', 'pro');
INSERT INTO orders (tenant_id, amount) VALUES (1, 12000), (1, 8000), (2, 3000), (3, 45000), (3, 1500);
```

기본 키를 `(tenant_id, id)`로 둔 데는 이유가 셋 있다. 테넌트 안의 조회가 인덱스 앞부분을 바로 탄다. 나중에 테넌트를 다른 DB로 옮길 때 행을 고르기 쉽다. 그리고 외래 키를 `(tenant_id, order_id)`로 걸면 "A 테넌트의 주문에 B 테넌트의 결제가 붙는" 실수를 DB가 막아 준다.

## 공유 테이블의 경계를 DB가 지키게 하기

가장 큰 위험은 코드 어딘가에서 `WHERE tenant_id = ?`를 빠뜨리는 것이다. 쿼리가 수백 개면 언젠가 하나는 빠진다. PostgreSQL의 행 수준 보안(RLS)은 이 조건을 DB가 모든 쿼리에 대신 붙이게 한다.

앱은 요청마다 "지금 누구의 요청인지"를 세션 변수로 알려 주고, 정책은 그 변수와 행의 `tenant_id`를 비교한다.

```sql
-- 테이블 주인(app_owner)과 앱이 쓰는 계정(app_user)을 나눈다
GRANT SELECT, INSERT, UPDATE, DELETE ON orders TO app_user;

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- USING: 읽기·수정·삭제할 수 있는 행, WITH CHECK: 새로 쓰는 행이 지켜야 할 조건
CREATE POLICY tenant_isolation ON orders
  USING      (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::bigint)
  WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::bigint);
```

`app_user`로 붙어서 확인해 본다.

```sql
SET ROLE app_user;

SELECT count(*) FROM orders;          -- 테넌트를 정하지 않았다

SET app.tenant_id = '1';
SELECT tenant_id, id, amount FROM orders ORDER BY id;

INSERT INTO orders (tenant_id, amount) VALUES (2, 999);   -- 남의 테넌트로 쓰기
```

```text
 count
-------
     0

 tenant_id | id | amount
-----------+----+--------
         1 |  1 |  12000
         1 |  2 |   8000

ERROR:  new row violates row-level security policy for table "orders"
```

테넌트를 정하지 않으면 0줄, 정하면 자기 행만, 남의 `tenant_id`로 쓰면 에러다. 실수로 조건을 빠뜨린 쿼리가 다른 고객 데이터를 내보내는 대신 빈 결과를 낸다.

정책에 들어간 `NULLIF(..., '')`는 직접 돌려 보다가 붙였다. 처음에는 `current_setting('app.tenant_id', true)::bigint`만 썼다. 두 번째 인자 `true`는 변수가 없으면 에러 대신 NULL을 돌려 달라는 뜻이다. 그런데 한 세션에서 변수를 한 번 설정했다가 `RESET`하거나, `SET LOCAL`로 설정한 트랜잭션이 끝나면 그 변수는 NULL이 아니라 빈 문자열이 된다. 그래서 다음 쿼리가 이렇게 터졌다.

```text
ERROR:  invalid input syntax for type bigint: ""
```

빈 문자열을 NULL로 바꿔 주면 "정하지 않음"이 언제나 0줄로 끝난다.

### 인덱스는 tenant_id부터

RLS 조건은 결국 모든 쿼리에 붙는 `WHERE tenant_id = ...`다. 그러니 인덱스도 `tenant_id`로 시작해야 한다. 주문을 20만 줄로 늘리고 `app_user`로 "테넌트 2의 최근 하루 주문 20개"를 물었다. 처음에는 기본 키 인덱스만 있었다.

```sql
SET app.tenant_id = '2';
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
SELECT id, amount FROM orders
WHERE created_at > now() - interval '1 day'
ORDER BY created_at DESC LIMIT 20;
```

```text
 Limit (actual rows=20 loops=1)
   ->  Gather Merge (actual rows=20 loops=1)
         ->  Sort (actual rows=20 loops=2)
               Sort Key: created_at DESC
               ->  Parallel Bitmap Heap Scan on orders (actual rows=33334 loops=2)
                     Recheck Cond: (tenant_id = (NULLIF(current_setting('app.tenant_id'::text, true), ''::text))::bigint)
                     Filter: (created_at > (now() - '1 day'::interval))
                     ->  Bitmap Index Scan on orders_pkey (actual rows=66668 loops=1)
 Execution Time: 42.621 ms
```

테넌트 2의 행 6만 6천여 개를 다 읽고 정렬해서 20개를 고른다. `(tenant_id, created_at)` 인덱스를 만들고 같은 쿼리를 다시 돌리면 이렇다.

```sql
CREATE INDEX orders_tenant_created ON orders (tenant_id, created_at);
```

```text
 Limit (actual rows=20 loops=1)
   ->  Index Scan Backward using orders_tenant_created on orders (actual rows=20 loops=1)
         Index Cond: ((tenant_id = (NULLIF(current_setting('app.tenant_id'::text, true), ''::text))::bigint) AND (created_at > (now() - '1 day'::interval)))
 Execution Time: 0.073 ms
```

`Index Cond`에 RLS 조건과 날짜 조건이 함께 들어갔고, 인덱스를 거꾸로 20줄만 읽고 끝났다. 42ms에서 0.07ms다. RLS가 붙은 테이블에서 느린 쿼리를 보면 `Filter`나 `Recheck Cond`에 정책 조건이 있는지부터 본다.

## 행 수준 보안만 믿으면 안 되는 이유

RLS는 좋은 안전망이지만, 직접 해 보면 구멍이 여러 군데 보인다.

첫째, 주인과 슈퍼유저는 정책을 건너뛴다. 같은 데이터를 테이블 주인 `app_owner`로 읽으면 다섯 줄이 다 나왔고, 슈퍼유저 `postgres`도 마찬가지였다. 주인까지 정책을 받게 하려면 `ALTER TABLE orders FORCE ROW LEVEL SECURITY`가 필요하다. 그래도 슈퍼유저와 `BYPASSRLS` 속성을 가진 역할은 여전히 건너뛴다. 앱이 마이그레이션 계정으로 붙어 있다면 RLS는 아무 일도 하지 않는다.

둘째, 커넥션 풀에서 세션 변수가 남는다. 같은 커넥션에서 요청 하나가 `SET app.tenant_id = '1'`을 하고 끝났는데, 다음 요청이 설정을 빠뜨리면 이렇게 된다.

```text
-- 다음 요청이 같은 커넥션에서 테넌트를 정하지 않고 조회
 tenant_id | id | amount
-----------+----+--------
         1 |  1 |  12000
         1 |  2 |   8000
```

0줄이 아니라 앞 요청의 테넌트 데이터가 나온다. 정책은 "지금 변수 값"을 믿을 뿐, 그 값이 이번 요청에서 나온 것인지는 모른다. 그래서 세션 단위 `SET` 대신 트랜잭션 단위로 설정한다.

```sql
BEGIN;
SELECT set_config('app.tenant_id', '3', true);   -- 세 번째 인자 true = 이 트랜잭션에서만
SELECT tenant_id, id, amount FROM orders ORDER BY id;
COMMIT;                                          -- 끝나면 변수가 사라진다(빈 문자열)
```

PgBouncer를 트랜잭션 모드로 쓰면 이 방식이 사실상 유일한 선택이다. 트랜잭션마다 다른 서버 커넥션이 붙을 수 있어서 세션 `SET`은 엉뚱한 클라이언트에게 넘어간다. 이 문제는 [커넥션 풀](/posts/connection-pool) 글에서 더 자세히 다룬다.

셋째, RLS는 PostgreSQL 안에서만 지킨다. 테넌트 데이터는 DB 밖에도 있다. Redis 캐시, 검색 인덱스, S3 같은 객체 저장소, 메시지 큐, 로그, 분석용 데이터 웨어하우스. 실제 유출 사고는 이쪽에서 더 자주 난다. 캐시 키를 `order:42`로 만들면 테넌트 1과 테넌트 3의 주문 42가 같은 칸을 쓴다. 키에 테넌트를 넣어 `t:1:order:42`로 만들고, 객체 저장소 경로는 `tenants/1/...`로 시작하게 해서 IAM 정책도 그 접두사로 자른다.

넷째, 관리용 경로가 우회한다. 배치 작업, 관리자 화면, 고객 지원 도구는 흔히 모든 테넌트를 봐야 해서 RLS를 건너뛰는 계정을 쓴다. 이 경로에서 테넌트를 섞는 버그가 나면 RLS는 막지 못한다. 이런 경로는 계정을 따로 두고 접근 기록을 남긴다.

<Callout kind="warning">
RLS 정책을 켰다고 끝난 게 아니다. 앱이 붙는 계정이 테이블 주인이나 슈퍼유저가 아닌지, `SELECT rolname, rolbypassrls, rolsuper FROM pg_roles`로 먼저 확인한다. 주인 계정으로 붙어 있으면 정책은 그대로 있는데 모든 테넌트가 다 보인다.
</Callout>

그래서 실무에서는 겹으로 막는다. 앱 코드의 저장소 계층이 모든 쿼리에 테넌트 조건을 붙이고, RLS가 그 아래에서 빠진 것을 잡고, 테스트가 "테넌트 A로 만든 주문을 테넌트 B로 조회하면 404"를 API마다 확인한다.

## 테넌트 ID가 요청을 따라가게 하기

정책이 믿는 값은 결국 앱이 넣어 준 테넌트 ID다. 이 값을 어디서 가져와서 어디까지 실어 나르는지가 격리의 나머지 절반이다.

출발점은 인증이다. 클라이언트가 보낸 `X-Tenant-Id` 헤더나 요청 본문의 값을 그대로 믿으면 숫자 하나만 바꿔서 남의 테넌트로 들어갈 수 있다. 서버가 검증한 토큰의 클레임(예: JWT의 `tenant_id`)이나 세션에서 꺼내고, 사용자가 그 테넌트의 구성원인지 한 번 더 확인한다. 서브도메인(`acme.example.com`)은 화면을 고르는 힌트일 뿐 권한의 근거가 아니다.

그다음은 요청이 지나가는 모든 곳에 같은 값을 들고 가는 일이다. 아래 그림은 주문 내보내기 요청이 API에서 큐를 거쳐 워커까지 가는 길이다.

Node에서는 `AsyncLocalStorage`로 요청 범위를 만들고, DB 접근을 감싸는 함수 하나에서 테넌트 설정을 강제한다.

```ts
import { AsyncLocalStorage } from "node:async_hooks";
import type { Pool, PoolClient } from "pg";

type TenantContext = { tenantId: string };
export const tenantStore = new AsyncLocalStorage<TenantContext>();

// 미들웨어: 검증된 토큰에서 꺼낸 값만 넣는다
export function withTenant<T>(tenantId: string, fn: () => Promise<T>) {
  return tenantStore.run({ tenantId }, fn);
}

// 모든 쿼리는 이 함수를 거친다. 테넌트가 없으면 쿼리를 보내지 않는다
export async function tenantTx<T>(pool: Pool, fn: (c: PoolClient) => Promise<T>) {
  const ctx = tenantStore.getStore();
  if (!ctx) throw new Error("tenant context missing");
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    await client.query("SELECT set_config('app.tenant_id', $1, true)", [ctx.tenantId]);
    const result = await fn(client);
    await client.query("COMMIT");
    return result;
  } catch (e) {
    await client.query("ROLLBACK");
    throw e;
  } finally {
    client.release();
  }
}
```

테넌트가 없을 때 조용히 넘어가지 않고 예외를 던지는 게 요점이다. "테넌트 없음"을 전체 조회로 해석하는 코드가 사고의 가장 흔한 출발점이다.

테넌트 ID는 로그와 지표에도 실린다. 로그 줄마다 `tenant_id` 필드를 넣어 두면 "느리다는 고객사의 요청만" 걸러 볼 수 있다. 지표는 조심한다. Prometheus 라벨에 테넌트 ID를 넣으면 테넌트 수만큼 시계열이 곱해진다. 테넌트가 수천 개면 상위 몇 개만 라벨로 두고 나머지는 `other`로 묶거나, 테넌트별 분석은 로그와 트레이스에 맡긴다.

## 시끄러운 이웃을 묶어 두는 한도

처음 장면으로 돌아가면, 막아야 할 것은 "A가 많이 쓰는 것"이 아니라 "A가 많이 써서 B가 못 쓰는 것"이다. 그래서 한도는 공유 자원마다 테넌트 단위로 건다.

- 들어오는 요청 수: API 게이트웨이에서 테넌트별 토큰 버킷. 키를 IP가 아니라 테넌트로 잡는다. 알고리즘은 [요청 수 제한 알고리즘](/posts/rate-limiting-algorithms)에 있다.
- 동시 실행 수: 무거운 작업(내보내기, 리포트)은 요청 수보다 동시에 몇 개 돌아가는지가 중요하다. 테넌트별 세마포어로 "동시에 2개"를 건다. 요청 수 제한만으로는 1분에 5개짜리 30분 작업을 막지 못한다.
- 작업 큐: 큐 하나에 모든 테넌트 작업을 넣으면 먼저 50개를 넣은 테넌트가 앞을 다 차지한다. 테넌트별로 줄을 나누고 돌아가며 꺼내거나, 공정 몫(fair share)으로 워커를 나눈다.
- DB: 배치용 계정을 따로 두고 `ALTER ROLE export_worker SET statement_timeout = '60s'`처럼 한도를 건다. 배치 전용 커넥션 풀을 작게 따로 두면 배치가 커넥션을 다 가져가는 일이 사라진다. 큰 읽기는 읽기 복제본으로 보낸다.
- 저장 공간과 개수: 테넌트별 행 수, 파일 용량, 사용자 수 같은 쿼터는 요금제와 함께 정한다.

공정 몫을 나누는 대표적인 규칙이 최대-최소 공정(max-min fairness)이다. 적게 원하는 테넌트는 원하는 만큼 다 주고, 남은 몫을 나머지에게 똑같이 나눈다. 워커 100개를 세 테넌트가 10, 50, 80개씩 원하면 10을 먼저 주고, 남은 90을 둘이 45씩 나눈다. 아래에서 직접 짜 볼 수 있다.

<CodePlayground
  caption="최대-최소 공정 몫 나누기"
  functionName="fairShare"
  initialCode={`// capacity: 나눌 총량, demands: 테넌트별 원하는 양
// 적게 원하는 테넌트부터 다 채워 주고, 남은 몫을 나머지에게 똑같이 나눈다
function fairShare(capacity, demands) {
  return demands.map(() => 0);
}`}
  solution={`function fairShare(capacity, demands) {
  const alloc = demands.map(() => 0);
  let left = capacity;
  let active = demands.map((_, i) => i);
  while (active.length > 0 && left > 0) {
    const share = left / active.length;
    const next = [];
    for (const i of active) {
      const need = demands[i] - alloc[i];
      if (need <= share) { alloc[i] += need; left -= need; }
      else next.push(i);
    }
    if (next.length === active.length) {
      for (const i of next) alloc[i] += share;
      left = 0;
    }
    active = next;
  }
  return alloc;
}`}

    { label: "모두 넘친다", args: [90, [100, 100, 100]], expected: [30, 30, 30] },
    { label: "큰 테넌트 하나", args: [100, [5, 90, 10]], expected: [5, 85, 10] },

요금제를 반영하려면 몫을 똑같이 나누는 대신 가중치를 곱한다(엔터프라이즈 2, 프로 1처럼). 중요한 성질은 그대로다. 아무리 많이 원해도 남의 최소 몫을 빼앗지 못한다.

한도에 걸린 테넌트에게는 무엇이 막혔는지 알려 준다. 요청 수 한도는 429와 `Retry-After`, 동시 실행 한도는 202로 받아 두고 큐에서 기다리게 하는 편이 고객 경험이 낫다. 이 흐름은 [큐로 부하 받아 내기](/posts/queue-based-load-leveling)에서 이어서 다룬다.

## 테넌트마다 비용을 잰다

풀 모델의 숨은 숙제는 "이 고객 하나에 돈이 얼마 드는가"에 답하는 것이다. 무료 테넌트 하나가 서버비의 30%를 쓰고 있어도 재지 않으면 모른다. 요금제를 설계하고 한도를 정하는 근거도 이 숫자다.

측정 단위는 층마다 다르다. API는 테넌트별 요청 수와 처리 시간 합계, 워커는 작업 수와 실행 초, DB는 저장 용량과 쿼리 시간이다. 저장 용량은 공유 테이블에서도 대략 셀 수 있다.

```sql
-- 테넌트별 행 수와 대략의 데이터 크기(행 크기 합, 인덱스 제외)
SELECT tenant_id, count(*) AS rows,
       pg_size_pretty(sum(pg_column_size(o.*))) AS approx_size
FROM orders o
GROUP BY tenant_id ORDER BY tenant_id;
```

```text
 tenant_id | rows  | approx_size
-----------+-------+-------------
         1 | 66668 | 3646 kB
         2 | 66668 | 3646 kB
         3 | 66669 | 3646 kB
```

큰 테이블에서 이 쿼리는 전체를 읽으니 밤에 한 번 돌려 집계 테이블에 쌓는다. 쿼리 시간은 DB 쪽 통계(`pg_stat_statements`)가 테넌트를 구분하지 못하니, 앱이 트랜잭션마다 걸린 시간을 테넌트 ID와 함께 기록하는 쪽이 현실적이다. 쿠버네티스에서 테넌트별 네임스페이스나 라벨을 쓰면 비용 도구가 그 단위로 나눠 준다. 클라우드 요금이 붙는 단위는 [클라우드 비용 줄이기](/posts/cloud-cost-optimization)에 정리돼 있다.

## 큰 고객을 따로 떼어 내기

풀에서 시작한 서비스도 언젠가 혼자 전체 트래픽의 40%를 쓰는 고객이 생긴다. 한도로 묶기엔 너무 중요한 고객이고, 그 고객의 배치가 매일 다른 고객을 흔든다. 이때 그 고객을 따로 떼어 낸다.

떼어 내는 단위로 셀(cell)을 쓴다. 셀은 앱과 DB를 포함한 완전한 스택 하나이고, 테넌트 여러 개를 담는다. 앞단의 라우터가 "테넌트 1 → 셀 3"이라는 표를 보고 요청을 보낸다. 셀 하나가 죽어도 그 셀의 테넌트만 영향을 받는다. 큰 고객은 셀 하나를 혼자 쓰고, 작은 고객은 여러 명이 한 셀을 나눈다.

테넌트를 셀 사이에서 옮기는 순서는 이렇다.

PostgreSQL 15부터 발행(publication)에 행 필터를 걸 수 있어서 테넌트 하나만 복제하는 게 쉬워졌다. 16에서 위 명령을 돌리면 필터가 등록된다(실습 DB는 `wal_level`이 기본값이라 경고가 함께 나왔다).

```text
WARNING:  wal_level is insufficient to publish logical changes
HINT:  Set wal_level to "logical" before creating subscriptions.
CREATE PUBLICATION

    pubname    | tablename |    rowfilter
---------------+-----------+-----------------
 move_tenant_1 | orders    | (tenant_id = 1)
```

UPDATE와 DELETE까지 복제하려면 필터에 쓰는 열이 복제 식별자(보통 기본 키)에 들어 있어야 한다. 기본 키를 `(tenant_id, id)`로 잡아 둔 덕을 여기서 본다.

### 섞어 둔 테넌트를 나중에 나누는 일

처음부터 테넌트를 염두에 두지 않은 서비스를 나누려면 이사보다 공사가 먼저다. 실제로 걸리는 것은 대개 이런 것들이다.

- `tenant_id`가 없는 테이블. 주문에는 있는데 주문 항목, 첨부 파일, 감사 로그에는 없다. 부모를 따라가 채우는(backfill) 작업과 NOT NULL 전환을 먼저 한다. 큰 테이블의 NOT NULL 전환은 잠금이 길어지니 [무중단 마이그레이션](/posts/zero-downtime-migrations) 방식으로 한다.
- 전역 순번 ID. DB마다 시퀀스가 따로면 옮긴 뒤 새 셀에서 만든 주문 번호가 다른 셀의 번호와 겹친다. 고객에게 보이는 번호라면 문제가 된다. 옮기기 전에 UUID나 전역 ID 생성기로 바꾸거나, 셀마다 번호 범위를 나눠 둔다.
- 테넌트를 넘나드는 쿼리. 관리자 통계, 전체 검색, 테넌트 사이의 공유 기능은 셀로 나누면 한 번의 SQL로 안 된다. 분석용 저장소로 모아 따로 계산하게 바꾼다.
- 테넌트를 넘나드는 유일 제약. 이메일이 전역에서 유일해야 한다면 셀로 나눈 뒤에는 따로 확인할 곳이 필요하다.

그래서 풀로 시작하더라도 처음부터 지킬 것이 있다. 모든 테이블에 `tenant_id`, 기본 키와 외래 키에 `tenant_id`, 테넌트 밖으로 새는 순번 ID를 쓰지 않기. 이 셋만 지켜 두면 나중의 분리는 공사 없이 이사로 끝난다.

## 현장에서 테넌트 문제를 좁히는 순서

"전체가 느리다"는 제보가 오면 먼저 테넌트별로 쪼개 본다. 대시보드에서 요청 수와 처리 시간을 테넌트별 상위 10개로 정렬하면, 한 테넌트의 몫이 갑자기 커진 그래프가 바로 보인다. 그날 아침이라면 A의 내보내기 요청이 평소의 수십 배였을 것이다.

DB 쪽에서는 지금 누가 무엇을 돌리는지 본다. 커넥션마다 `application_name`에 테넌트와 작업 종류를 넣어 두면 `pg_stat_activity`에서 바로 보인다.

```sql
-- 워커가 트랜잭션 시작 때 SET application_name = 'api tenant=1 export' 처럼 넣어 둔다
SELECT pid, application_name, state, now() - query_start AS running_for, left(query, 30) AS query
FROM pg_stat_activity
WHERE datname = current_database() AND application_name LIKE 'api%';
```

```text
 pid  |  application_name   | state  |   running_for   |        query
------+---------------------+--------+-----------------+---------------------
 6007 | api tenant=1 export | active | 00:00:01.082151 | SELECT pg_sleep(4);
```

같은 테넌트의 긴 쿼리가 여러 줄 보이면 원인이 거의 정해진다. 급하면 `pg_cancel_backend(pid)`로 그 쿼리만 끊고, 그 테넌트의 동시 실행 한도를 낮춘다.

데이터 유출이 의심될 때는 반대로 본다. 어느 경로에 테넌트 조건이 빠졌는지 찾는 일이다. 캐시 키, 검색 인덱스 질의, 객체 저장소 경로, 관리자 도구처럼 RLS 밖에 있는 곳부터 의심한다. 재발을 막는 가장 싼 장치는 교차 테넌트 테스트다. 테스트 데이터에 테넌트를 둘 이상 두고, 모든 조회 API에서 다른 테넌트의 ID로 요청해 404가 나오는지 확인한다.

## 같이 쓰되 서로 모르게

멀티 테넌시는 비용 때문에 같이 쓰고, 신뢰 때문에 서로 모르게 만드는 일이다. 데이터 격리는 토큰에서 꺼낸 테넌트 ID를 트랜잭션, 큐, 캐시 키까지 빠짐없이 들고 가고, 빠졌을 때 RLS가 0줄로 막게 하는 겹 구조로 지킨다. 성능 격리는 공유 자원마다 테넌트 단위 한도를 두고, 그래도 안 되는 큰 고객은 셀로 옮긴다. 처음부터 모든 키에 `tenant_id`를 넣어 두면 그 이사가 쉬워진다.

## 면접에서 나올 만한 질문

### 멀티 테넌시에서 사일로, 풀, 브리지 모델은 어떻게 다른가요?

사일로는 테넌트마다 스택을 따로 두는 방식이고, 풀은 모든 테넌트가 같은 앱과 테이블을 나눠 쓰는 방식이며, 브리지는 층마다 둘을 섞는 방식이다. 사일로는 격리와 테넌트별 복원이 쉽지만 비용과 배포 횟수가 테넌트 수만큼 늘고, 풀은 싸고 온보딩이 빠르지만 격리를 코드와 정책으로 지켜야 한다. 실무에서는 무료·소규모는 풀, 규제나 대형 고객은 전용 DB나 셀로 빼는 요금제별 브리지가 흔하다.

### 시끄러운 이웃 문제는 어떻게 막나요?

공유 자원마다 테넌트 단위 한도를 둔다. 게이트웨이에서 테넌트별 요청 수 제한, 무거운 작업은 테넌트별 동시 실행 한도, 작업 큐는 테넌트별로 나누고 공정 몫으로 꺼내기, DB는 배치 전용 계정과 풀, `statement_timeout`으로 묶는다. 요청 수 제한만으로는 오래 도는 작업을 못 막아서 동시 실행 한도가 함께 필요하다. 그래도 한 고객이 너무 크면 그 고객을 별도 셀로 옮긴다.

### 공유 테이블에서 테넌트 데이터를 어떻게 격리하나요?

모든 테이블에 `tenant_id`를 두고 기본 키와 외래 키에 포함시킨 뒤, 저장소 계층이 모든 쿼리에 테넌트 조건을 붙인다. 그 아래에 PostgreSQL 행 수준 보안을 걸어, 조건이 빠진 쿼리도 세션 변수에 설정된 테넌트의 행만 보게 한다. 인덱스는 `tenant_id`로 시작하게 만들어야 RLS 조건이 인덱스를 탄다.

### 행 수준 보안만 믿으면 안 되는 이유는 뭔가요?

RLS는 DB 안에서만, 그리고 정책을 받는 역할에만 작동한다. 테이블 주인은 `FORCE`를 걸지 않으면 건너뛰고, 슈퍼유저와 `BYPASSRLS` 역할은 항상 건너뛴다. 세션 변수를 커넥션 풀에서 `SET`으로 걸면 다음 요청에 앞 테넌트 값이 남아서 남의 데이터가 보인다. 캐시, 검색 인덱스, 객체 저장소, 로그는 RLS가 보지 못하니 앱 계층의 테넌트 전파와 교차 테넌트 테스트가 함께 있어야 한다.

### 커넥션 풀을 쓸 때 테넌트 세션 변수는 어떻게 설정하나요?

트랜잭션마다 `set_config('app.tenant_id', $1, true)`로 설정한다. 세 번째 인자가 true면 트랜잭션이 끝날 때 값이 사라져서 다음 요청으로 새지 않는다. PgBouncer 트랜잭션 모드에서는 세션 `SET`이 다른 클라이언트에게 넘어갈 수 있어서 이 방식이 사실상 필수다. 끝난 뒤 변수는 빈 문자열이 되니 정책에서 `NULLIF`로 NULL로 바꿔 둬야 형 변환 에러가 나지 않는다.

### 테넌트 ID는 어디서 가져와야 하나요?

서버가 검증한 인증 정보, 예를 들어 서명된 토큰의 클레임이나 서버 세션에서 가져오고 사용자가 그 테넌트 구성원인지 확인한다. 클라이언트가 보낸 헤더나 본문 값을 믿으면 숫자만 바꿔 남의 테넌트로 들어갈 수 있다. 가져온 값은 요청 컨텍스트에 넣고 큐 메시지, 로그, 캐시 키까지 함께 실어 나르며, 컨텍스트가 없으면 쿼리를 보내지 않고 예외를 던진다.

### 섞여 있던 테넌트를 다른 DB로 떼어 내려면 무엇이 필요한가요?

먼저 모든 테이블에 `tenant_id`를 채우고 키에 포함시키는 공사가 필요하다. 그다음 테넌트 하나만 걸러 복제하고(PostgreSQL 15 이상은 발행에 행 필터를 걸 수 있다), 변경분을 따라잡은 뒤 그 테넌트의 쓰기만 잠깐 멈추고 건수와 합계를 대조하고 라우팅을 바꾼다. DB마다 따로 도는 시퀀스 ID가 겹치는 문제, 테넌트를 넘나드는 쿼리와 전역 유일 제약도 미리 정리해야 한다.

### 테넌트별 비용은 어떻게 측정하나요?

층마다 테넌트를 붙여 센다. API와 워커는 요청 수와 처리 시간을 테넌트 ID와 함께 기록하고, DB는 테넌트별 행 수와 용량을 밤마다 집계하며, 쿼리 시간은 DB 통계가 테넌트를 모르니 앱이 트랜잭션 시간을 기록한다. 지표 라벨에 테넌트를 다 넣으면 시계열이 폭증하니 상위 테넌트만 라벨로 두고 나머지는 로그에서 분석한다.
