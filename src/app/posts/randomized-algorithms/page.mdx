정렬 API를 하나 열어 두었다고 하자. 사용자가 숫자 배열을 보내면 정렬해서 돌려준다. 직접 짠 퀵 정렬이고, 기준값은 가운데 칸으로 골랐다. 정렬된 입력에서 첫 칸 기준값이 무너진다는 이야기를 들어서다. 그런데 누군가 이 코드를 읽고, 가운데 칸이 매번 가장 작은 값이 되도록 배열을 짜서 보낸다. 요청 하나가 CPU를 몇 초씩 붙잡는다. 같은 요청을 수십 개 보내면 서버가 멈춘다.

이건 상상이 아니다. 1999년 더글러스 매킬로이는 "A Killer Adversary for Quicksort"에서 비교 함수를 가로채 기준값 규칙이 정해진 거의 모든 퀵 정렬을 O(n²)으로 만드는 입력을 자동으로 찾아냈다. 기준값을 첫 칸, 가운데 칸, 세 값의 중앙값 중 무엇으로 고르든 규칙이 고정되어 있으면 상대가 그 규칙을 거꾸로 이용한다.

막는 방법은 규칙을 숨기는 게 아니라 규칙에 동전을 넣는 것이다. 기준값을 무작위로 고르면 어떤 입력을 보내도 기대 시간이 O(n log n)이다. 이 글은 이렇게 알고리즘 안에 무작위를 넣는 방법들을 본다. 무작위 기준값이 무엇을 보장하는지, 공정한 셔플과 흔한 잘못된 셔플, 길이를 모르는 스트림에서 표본을 뽑는 저수지 샘플링, 라스베이거스와 몬테카를로의 차이, 해시 테이블을 노리는 공격, 그리고 `Math.random`을 믿으면 안 되는 자리까지 간다. 퀵 정렬 자체와 정렬된 입력에서의 실측은 [정렬 알고리즘 글](/posts/sorting-algorithms)에, 퀵셀렉트와 분할 정복의 복잡도는 [분할 정복 글](/posts/divide-and-conquer)에 있다. 실행 결과는 모두 Node.js 22에서 직접 돌린 값이다.

## 무작위 기준값이 약속하는 것

"무작위로 고르면 빠르다"를 정확하게 말하면 이렇다. 어떤 입력이 와도, 알고리즘이 던지는 동전에 대한 기대 시간이 O(n log n)이다.

여기서 확률이 어디에 붙는지가 중요하다. "평균적인 입력에서 빠르다"는 입력이 무작위라는 가정이다. 공격자가 입력을 고르면 그 가정은 깨진다. 무작위 기준값은 확률을 입력에서 빼서 알고리즘 쪽으로 옮긴다. 공격자가 아무리 입력을 잘 골라도 내가 굴릴 주사위 결과는 미리 모른다. 그래서 최악의 입력이 따로 없다. 운이 나쁜 실행만 있을 뿐이고, 그 확률은 n이 커질수록 빠르게 작아진다.

입력을 먼저 무작위로 섞고 첫 칸을 기준값으로 써도 같은 효과다. 섞은 배열의 첫 칸은 무작위로 고른 원소이기 때문이다. 다만 섞는 데 O(n)이 한 번 더 들고, 섞는 방법이 치우쳐 있으면 보장도 사라진다. 그 섞는 방법이 다음 이야기다.

무작위가 못 막는 것도 있다. 같은 값이 많으면 어떤 값을 기준값으로 골라도 한쪽에 같은 값이 몰린다. 이건 분할 방식(3-way 분할)으로 풀어야 한다. 그리고 공격자가 내 난수 생성기의 다음 값을 맞힐 수 있다면 무작위가 아니다. 이건 뒤에서 `Math.random`을 보며 다시 다룬다.

## 공정하게 섞는 피셔-예이츠

배열을 섞는다는 건 n!가지 순서가 모두 같은 확률로 나오게 만드는 일이다. 피셔-예이츠(Fisher–Yates) 셔플은 이렇게 한다. 맨 뒤 칸부터 앞으로 오면서, 지금 칸과 그 앞의 칸들(자기 자신 포함) 중 하나를 무작위로 골라 바꾼다.

```js
function shuffle(arr) {
  const a = arr.slice();
  for (let i = a.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1)); // 0 ~ i 중 하나
    [a[i], a[j]] = [a[j], a[i]];
  }
  return a;
}
```

왜 공정한지는 선택지의 수를 세면 보인다. 맨 뒤 칸에 올 원소를 n개 중 하나로 고르고, 그다음 칸은 남은 n−1개 중 하나로 고른다. 전체 경우의 수는 n × (n−1) × … × 1 = n!이고, 각 경우가 정확히 하나의 순서를 만든다. n!가지 경우가 n!가지 순서에 하나씩 대응하니 모든 순서의 확률이 같다. 시간은 O(n)이고 추가 메모리도 없다.

`[1, 2, 3]`을 60만 번 섞어 여섯 가지 순서가 나온 비율을 셌다.

```text
fisher-yates 123 16.7%  132 16.7%  213 16.7%  231 16.7%  312 16.6%  321 16.6%
```

1/6 = 16.67%에 고르게 붙는다.

## 그럴듯하지만 치우친 셔플

자바스크립트에서 자주 보이는 한 줄 셔플이 있다.

```js
arr.sort(() => Math.random() - 0.5);
```

비교할 때마다 동전을 던져 앞뒤를 정하니 섞일 것 같다. 같은 조건으로 재 봤다.

```text
sort-random 123 37.4%  132 6.3%  213 12.5%  231 6.3%  312 6.3%  321 31.3%
```

원래 순서 `123`이 37.4%, 뒤집힌 `321`이 31.3%다. 공정하다면 16.7%여야 한다. 원소 10개로 늘려서 0이 어디에 떨어지는지도 봤다(왼쪽부터 0번 자리).

```text
sort-random n=10, where 0 ends: 19.4 13.7 9.0 7.4 6.9 7.5 8.1 8.5 9.3 10.3
```

공정하다면 모든 자리가 10%다. 0번 자리에 19.4%로 몰리고 가운데는 7% 아래로 빠진다. 이유는 두 가지다. 정렬 알고리즘은 비교 결과가 일관된다고 가정하고 비교 횟수를 줄이도록 짜여 있다. a가 b보다 작다고 했다가 다음엔 크다고 하는 비교 함수는 그 가정을 깨고, 결과는 엔진이 쓰는 정렬 알고리즘의 모양을 따라간다. V8의 TimSort는 짧은 배열을 삽입 정렬로 처리하는데, 삽입 정렬은 비교 결과에 따라 원소를 옮길지 말지를 정하니 원래 자리 근처에 머무르는 결과가 더 자주 나온다. 엔진과 배열 길이가 바뀌면 치우침의 모양도 바뀐다. 둘째로 동전 k번의 결과는 2^k가지인데 n!은 2의 거듭제곱으로 나누어떨어지지 않는다(3! = 6만 해도 3이 들어 있다). 동전 결과를 순서에 고르게 나눠 줄 수가 없다.

피셔-예이츠를 반쯤 기억해서 짠 버전도 흔하다. 매번 배열 전체에서 j를 고르는 코드다.

```js
for (let i = 0; i < a.length; i++) {
  const j = Math.floor(Math.random() * a.length); // 0 ~ n-1 전체에서
  [a[i], a[j]] = [a[j], a[i]];
}
```

```text
naive swap 123 14.8%  132 18.5%  213 18.5%  231 18.5%  312 14.8%  321 14.9%
```

이번엔 덜 눈에 띄지만 여전히 치우쳤다. 경우의 수가 n^n = 27인데 순서는 6가지라 27을 6으로 나눌 수 없다. 어떤 순서는 4번, 어떤 순서는 5번 나와서 4/27 = 14.8%, 5/27 = 18.5%가 된다. 셔플은 결과를 눈으로 봐서는 섞여 보여서 테스트에서 잘 안 걸린다. 퀴즈 보기 순서, 추첨, 카드 게임처럼 공정함이 중요한 곳에서는 분포를 직접 세어 보는 게 확실하다.

## 끝을 모르는 줄에서 k개 뽑기

로그가 끝없이 흘러오는데 그중 1,000줄을 공평하게 뽑아 보관하고 싶다. 전체가 몇 줄인지 모르고, 다 저장할 수도 없다. "줄마다 1% 확률로 뽑기"는 전체 개수를 알아야 정확히 1,000개가 되고, 몇 개가 뽑힐지도 들쭉날쭉하다.

저수지 샘플링(reservoir sampling)은 크기 k짜리 저수지만 들고 다닌다. 처음 k개는 그냥 넣는다. i번째(1부터 센다) 원소가 오면 k/i 확률로 저수지에 넣고, 넣을 때는 저수지 안의 하나를 무작위로 골라 내보낸다. 아래 그림은 k = 2로 여섯 개짜리 스트림을 지나간다. 다음을 누르면 원소가 하나씩 오고, 저수지에 들어가거나 그냥 지나간다.

코드로는 몇 줄이다.

```js
function reservoir(stream, k) {
  const r = [];
  let i = 0;
  for (const x of stream) {
    if (i < k) r.push(x);
    else {
      const j = Math.floor(Math.random() * (i + 1)); // 0 ~ i
      if (j < k) r[j] = x;                            // k/(i+1) 확률로 들어간다
    }
    i++;
  }
  return r;
}
```

모든 원소가 끝에 남을 확률이 똑같이 k/n이라는 건 곱셈으로 확인된다. i번째 원소는 k/i 확률로 들어온다. 그 뒤 j번째 원소가 올 때마다 쫓겨날 확률은 (k/j) × (1/k) = 1/j이니, 살아남을 확률은 (1 − 1/j) = (j−1)/j다. i+1부터 n까지 곱하면 i/n이 되고, 처음 들어올 확률 k/i와 곱하면 k/n이다. 10개 중 3개를 20만 번 뽑아 원소마다 뽑힌 비율을 셌다.

```text
reservoir k=3 of 10: 29.9 30.0 30.0 29.8 30.0 30.1 30.0 30.3 29.9 29.9
```

3/10 = 30%에 고르게 붙는다. 전체 개수를 몰라도 되고, 메모리는 k개, 한 번만 훑는다. 스트림 처리에서 표본을 남기거나, 분산된 여러 서버에서 각자 뽑은 뒤 합치는 데 쓴다. 원소마다 가중치가 다르면 각 원소에 `u^(1/w)`(u는 0~1 난수, w는 가중치)라는 열쇠를 붙여 가장 큰 k개를 남기는 가중 버전(Efraimidis–Spirakis)이 있다.

DB에서 무작위 표본을 뽑을 때도 같은 고민을 한다. `ORDER BY random() LIMIT 10`은 모든 행에 난수를 붙이고 정렬하니 큰 테이블에서 느리다. PostgreSQL은 `TABLESAMPLE SYSTEM (1)`(페이지 단위로 1%, 빠르지만 덩어리져 뽑힌다)과 `TABLESAMPLE BERNOULLI (1)`(행 단위로 1%, 고르지만 전체를 읽는다)을 제공한다. 정확히 k개가 필요한지, 대충 1%면 되는지로 고른다.

## 답이 늘 맞는 무작위, 가끔 틀리는 무작위

무작위 알고리즘은 무작위가 무엇에 영향을 주느냐로 두 갈래로 나눈다.

라스베이거스 알고리즘은 답이 늘 맞고, 걸리는 시간이 무작위다. 무작위 퀵 정렬과 퀵셀렉트가 여기 속한다. 운이 나쁘면 오래 걸리지만 틀린 답은 내지 않는다.

몬테카를로 알고리즘은 시간이 정해져 있고, 답이 작은 확률로 틀린다. 밀러-라빈 소수 판정은 한 번 돌릴 때 합성수를 소수라고 잘못 말할 확률이 1/4 이하이고, 서로 다른 무작위 밑으로 k번 돌리면 4^(−k) 이하로 줄어든다. 40번이면 사실상 틀리지 않는다. 블룸 필터는 "있다"고 할 때 가끔 틀리고, HyperLogLog는 고유 개수를 오차 범위 안에서 추정한다. 이름의 유래가 된 계산도 있다. 정사각형 안에 점을 무작위로 찍고 사분원 안에 든 비율로 원주율을 구한다.

```text
n=1000 pi≈3.11600
n=100000 pi≈3.14284
n=10000000 pi≈3.14161
```

점을 100배 늘릴 때마다 오차가 대략 10분의 1로 준다. 몬테카를로 추정의 오차는 표본 수의 제곱근에 반비례하기 때문이다. 정밀도 한 자리를 더 얻으려면 표본이 100배 필요하다.

둘은 오갈 수 있다. 몬테카를로의 답을 빠르게 검증할 수 있으면 맞을 때까지 반복해서 라스베이거스로 바꾼다. 라스베이거스 알고리즘은 시간 제한을 두고 넘으면 "모름"을 내게 하면 몬테카를로가 된다. 면접에서 "랜덤 알고리즘을 쓰면 답이 틀릴 수도 있지 않나"라는 질문이 나오면 이 구분으로 답한다.

## 해시 테이블을 노리는 입력

## Math.random을 믿으면 안 되는 자리

`Math.random()`은 빠르고 고르게 퍼진 수를 주지만, 예측 불가능하다는 약속은 없다. 명세는 알고리즘을 정하지 않고, V8은 2015년부터 xorshift128+를 쓴다. 이 계열 생성기는 내부 상태가 128비트뿐이라, 연속으로 나온 출력 몇 개로 상태를 거꾸로 풀고 다음 값을 예측하는 방법이 공개되어 있다. 셔플이나 화면 효과에는 문제없지만 비밀번호 재설정 토큰, 세션 ID, 초대 코드, 추첨처럼 상대가 맞히면 안 되는 값에 쓰면 안 된다.

그런 값은 운영체제의 암호학적 난수 생성기(CSPRNG)를 쓴다. 브라우저와 Node 모두 `crypto.getRandomValues()`가 있고, UUID가 필요하면 `crypto.randomUUID()`, Node에서 범위 안의 정수가 필요하면 `crypto.randomInt()`를 쓴다.

```js
// 브라우저, Node 19+ (globalThis.crypto)
const bytes = crypto.getRandomValues(new Uint8Array(32)); // 토큰용 32바이트
const id = crypto.randomUUID();                            // v4 UUID

// Node
const { randomInt } = require("node:crypto");
const code = randomInt(0, 1_000_000);                      // 0 ~ 999999, 치우침 없음
```

난수 원천이 튼튼해도 범위를 줄이는 방법에서 치우침이 생길 수 있다. 바이트 하나(0~255)를 `% 100`으로 줄이면 0~55는 세 번(0, 100, 200), 56~99는 두 번(56, 156)씩 나온다. 256만 바이트로 재 봤다.

```text
byte%100  value 0: 1.170% value 55: 1.170% value 56: 0.780% value 99: 0.780%
randomInt(100) value 0: 1.001% value 99: 1.018%
```

3/256 = 1.17%, 2/256 = 0.78%로 정확히 갈린다. 인증 코드라면 앞쪽 숫자가 1.5배 잘 나오는 셈이다. `randomInt`는 범위를 넘는 값을 버리고 다시 뽑는 방식(거절 표본 추출)으로 이 치우침을 없앤다. 직접 구현해야 한다면 256을 범위로 나눈 몫 × 범위(여기서는 200) 이상인 바이트를 버리고 다시 뽑는다.

반대로 무작위가 오히려 해로운 자리도 있다. A/B 테스트에서 요청마다 `Math.random()`으로 그룹을 정하면 같은 사용자가 새로고침할 때마다 다른 화면을 본다. 이럴 때는 사용자 ID를 해시해 그룹을 정해서, 무작위처럼 고르게 나뉘되 같은 사용자는 늘 같은 그룹에 들게 한다. 재시도 간격에 무작위 지터를 넣는 건 여러 클라이언트가 한꺼번에 몰리지 않게 하려는 것이고, 이 경우엔 `Math.random()`으로 충분하다.

## 동전을 어디에 던질까

무작위는 상대가 고를 수 있는 것을 내가 굴리는 것으로 바꾼다. 기준값을 무작위로 고르면 최악의 입력이 사라지고, 해시 시드를 무작위로 두면 미리 계산한 충돌이 사라진다. 섞고 뽑을 때는 결과가 고르게 나오는지가 전부라서 피셔-예이츠나 저수지 샘플링처럼 확률을 셀 수 있는 방법을 쓰고, 결과 분포를 직접 세어 확인한다. 그리고 상대가 맞히면 안 되는 값에는 `Math.random` 대신 운영체제의 난수를 쓴다.

## 면접에서 나올 만한 질문

### 퀵 정렬에서 기준값을 무작위로 고르면 무엇이 좋아지나요?

어떤 입력이 와도 기대 시간이 O(n log n)이 된다. 고정된 규칙(첫 칸, 가운데, 세 값의 중앙값)은 그 규칙을 아는 사람이 최악의 입력을 만들 수 있지만, 무작위 기준값은 확률이 입력이 아니라 알고리즘의 동전에 붙어서 최악의 입력이 따로 없다. 운이 나쁜 실행은 있지만 그 확률은 n이 커질수록 급격히 작아진다. 같은 값이 많은 경우는 무작위로도 못 막아서 3-way 분할을 함께 쓴다.

### 피셔-예이츠 셔플은 왜 공정한가요?

맨 뒤 칸부터 앞의 칸들(자기 포함) 중 하나와 바꾸니 선택지가 n, n−1, …, 1개로 줄어 전체 경우의 수가 n!이다. 이 경우들이 n!가지 순서에 하나씩 대응해서 모든 순서의 확률이 같다. O(n) 시간에 추가 메모리 없이 끝난다. j를 매번 배열 전체에서 고르면 경우의 수가 n^n이 되어 n!로 나누어떨어지지 않으니 치우친다.

### 정렬 함수에 무작위 비교 함수를 넘겨 섞으면 안 되는 이유는요?

결과가 치우친다. V8에서 `[1, 2, 3]`을 60만 번 섞으면 원래 순서가 37.4%, 뒤집힌 순서가 31.3%로, 공정한 16.7%와 크게 다르다. 정렬 알고리즘은 비교 결과가 일관되다고 가정하는데 매번 바뀌는 비교 함수가 그 가정을 깨고, 결과가 엔진의 정렬 구현 모양을 따라간다. 동전 결과 2^k가지를 n!가지 순서에 고르게 나눌 수도 없다.

### 크기를 모르는 스트림에서 k개를 공평하게 뽑으려면요?

저수지 샘플링을 쓴다. 처음 k개는 넣고, i번째 원소는 k/i 확률로 저수지의 무작위 칸을 대신한다. i번째가 끝까지 남을 확률은 k/i에 이후 살아남을 확률 i/n을 곱한 k/n으로 모두 같다. 메모리는 k개, 한 번만 훑으면 되고 전체 개수를 몰라도 된다.

### 라스베이거스 알고리즘과 몬테카를로 알고리즘의 차이는요?

라스베이거스는 답이 늘 맞고 시간이 무작위다(무작위 퀵 정렬, 퀵셀렉트). 몬테카를로는 시간이 정해져 있고 답이 작은 확률로 틀린다(밀러-라빈 소수 판정, 블룸 필터, HyperLogLog). 밀러-라빈은 한 번에 틀릴 확률이 1/4 이하라 k번 반복하면 4^(−k) 이하로 줄일 수 있다. 답을 빠르게 검증할 수 있으면 몬테카를로를 맞을 때까지 반복해 라스베이거스로 바꿀 수 있다.

### 해시 테이블에 무작위 시드를 쓰는 이유는요?

해시 함수가 고정되면 공격자가 같은 칸에 떨어지는 키를 미리 계산해 보내 삽입을 O(n²)으로 만들 수 있다. 2011년 폼 파라미터에 충돌 키를 실어 웹 서버 CPU를 묶는 공격이 여러 언어에서 시연됐다. 프로세스마다 시드를 바꾸면 미리 계산한 충돌이 통하지 않는다. 파이썬은 시드 무작위화와 SipHash, PHP는 파라미터 개수 제한, 자바 8은 충돌이 많은 칸을 트리로 바꾸는 방법을 더했다.

### Math.random으로 비밀번호 재설정 토큰을 만들면 왜 안 되나요?

`Math.random`은 예측 불가능하다는 보장이 없다. V8의 xorshift128+는 상태가 작아 연속 출력 몇 개로 다음 값을 예측하는 방법이 알려져 있다. 토큰, 세션 ID, 추첨처럼 상대가 맞히면 안 되는 값은 `crypto.getRandomValues`, `crypto.randomUUID`, Node의 `crypto.randomInt` 같은 CSPRNG를 쓴다. 범위를 줄일 때 `% n`을 쓰면 치우침이 생기니 `randomInt`나 거절 표본 추출을 쓴다.
