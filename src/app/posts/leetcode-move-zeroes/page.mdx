배열에서 0을 뒤로 보내라는 말을 들으면 `splice`로 0을 빼서 `push`로 뒤에 붙이는 코드가 먼저 나온다. 짧고 읽기 쉽다. 그런데 길이가 10만인 배열에서 그 코드는 5초가 넘게 걸렸다. 같은 일을 1ms에 하는 코드가 있다. 둘의 차이는 반복문 안에서 배열을 한 칸씩 당기느냐, 두 포인터로 한 번에 자리를 정하느냐다.

[LeetCode 283. Move Zeroes](https://leetcode.com/problems/move-zeroes/)는 같은 방향으로 달리는 투 포인터의 가장 작은 문제다. [투 포인터 패턴 글](/posts/two-pointers-pattern)의 "같은 방향으로 달리는 두 포인터"에서 읽기 포인터와 쓰기 포인터라는 틀을 봤다. 이 글은 그 틀을 이 문제에 맞춰 다섯 가지 풀이로 펼쳐 보고, "쓰기 횟수를 줄여라"는 후속 질문까지 간다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 0이 아닌 값은 순서를 지키고 0만 뒤로

문제를 내 말로 줄이면 이렇다. 정수 배열 `nums`의 모든 0을 맨 뒤로 옮긴다. 0이 아닌 값들은 원래 순서를 그대로 지켜야 한다. 새 배열을 만들지 말고 `nums`를 제자리에서 고친다.

```text
nums = [4, 0, 0, 5, 0, 7]
→ [4, 5, 7, 0, 0, 0]

4, 5, 7의 순서는 그대로
0 세 개는 뒤로
```

조건 두 개가 이 문제를 만든다. 하나는 "순서 유지"다. 순서가 상관없다면 양 끝에서 0과 0 아닌 값을 바꾸는 더 쉬운 방법이 있다(뒤의 "0의 순서도 상관없다면"). 다른 하나는 "제자리"다. 새 배열을 써도 되면 그냥 0 아닌 값을 모으고 0을 붙이면 끝난다. 길이는 최대 10^4이고, 문제 끝에 "연산 횟수를 최소로 줄일 수 있나"라는 후속 질문이 붙어 있다.

## 새 배열에 골라 담고 다시 옮긴다

제자리 조건을 잠깐 무시하면 가장 자연스러운 풀이가 나온다. 0이 아닌 값을 차례로 새 배열에 담고, 0의 개수만큼 뒤에 0을 붙인 다음, 그 결과를 `nums`에 다시 복사한다.

```js
// 풀이 1: 보조 배열
function moveZeroes(nums) {
  const keep = [];
  let zeros = 0;
  for (const x of nums) {
    if (x !== 0) keep.push(x);   // 0이 아닌 값은 순서대로 담는다
    else zeros++;
  }
  for (let i = 0; i < zeros; i++) keep.push(0);
  for (let i = 0; i < nums.length; i++) nums[i] = keep[i]; // 원래 배열에 다시 쓴다
}
```

시간 O(n), 공간 O(n)이다. 결과를 `nums`에 다시 써야 하는 이유는 LeetCode가 함수의 반환값이 아니라 넘긴 배열 자체를 채점하기 때문이다. 이걸 잊고 `nums = keep`이라고 쓰면 함수 안의 변수 이름만 새 배열을 가리킬 뿐, 호출한 쪽의 배열은 그대로다. 이 실수는 뒤의 "자리를 잘못 정하면 생기는 일"에서 직접 돌려 본다.

이 풀이의 한계는 공간이다. 제자리 조건을 지키려면 보조 배열 없이 같은 배열 안에서 값을 옮겨야 한다.

## 0을 하나씩 빼서 뒤에 붙인다

보조 배열 없이 가장 먼저 떠오르는 건 "0을 찾으면 빼서 뒤에 붙인다"를 그대로 옮긴 코드다.

```js
// 풀이 2: splice + push
function moveZeroes(nums) {
  let n = nums.length;               // 아직 정리하지 않은 앞부분의 길이
  for (let i = 0; i < n; ) {
    if (nums[i] === 0) {
      nums.splice(i, 1);             // i 칸을 빼면 뒤의 값들이 한 칸씩 당겨진다
      nums.push(0);                  // 맨 뒤에 0을 붙인다
      n--;                           // 뒤에 붙인 0은 다시 보지 않는다
    } else {
      i++;                           // 0을 뺐을 때는 i를 그대로 둔다
    }
  }
}
```

0을 뺐을 때 `i`를 그대로 두는 게 중요하다. 뒤의 값이 당겨져 와서 `i` 자리에 새 값이 들어왔기 때문이다. 이걸 놓친 코드가 아주 흔하다(뒤의 "자리를 잘못 정하면 생기는 일"에서 본다).

결과는 맞지만 느리다. `splice(i, 1)`은 i 뒤의 모든 값을 한 칸씩 당기므로 한 번에 O(n)이다. 0이 n/2개면 그걸 n/2번 하니 O(n²)이다. 0과 0 아닌 값이 반반 섞인 배열로 재 봤다.

```text
10000  splice  106.37ms
100000 splice  5621.70ms
```

길이를 열 배 늘렸더니 시간이 50배 넘게 늘었다. 제곱으로 늘어나는 코드의 전형적인 모습이다. LeetCode 제한(10^4)에서는 통과하지만, 실무에서 같은 코드를 10만 개짜리 목록에 쓰면 화면이 5초 멈춘다.

이 풀이에서 가져갈 생각은 "당기는 일을 매번 하지 말고, 0이 아닌 값이 최종적으로 갈 자리를 바로 계산하자"다.

## 안정 정렬에 맡기기

0이 아닌 값은 순서를 지키고 0만 뒤로 보내는 건, "0이면 1, 아니면 0"이라는 키로 안정 정렬(같은 키끼리 원래 순서를 지키는 정렬)을 하는 것과 같다.

```js
// 풀이 3: 0인지 여부를 키로 안정 정렬
function moveZeroes(nums) {
  nums.sort((a, b) => (a === 0) - (b === 0)); // true - false = 1이라 0이 뒤로 간다
}
```

`(a === 0) - (b === 0)`은 불리언을 빼서 -1, 0, 1을 만든다. a만 0이면 1이라 a가 뒤로, b만 0이면 -1이라 a가 앞으로 간다. 둘 다 0이 아니거나 둘 다 0이면 0이라 순서를 바꾸지 않는다. 여기서 순서가 지켜지는 건 `Array.prototype.sort`가 안정 정렬이기 때문이다. ES2019부터 명세가 안정성을 요구하고, V8은 TimSort를 쓴다. 그보다 오래된 엔진에서는 보장되지 않았다.

한 줄이라 깔끔하지만 O(n log n)이고 정렬의 보조 공간도 든다. 비교 결과가 두 종류뿐인 문제에 비교 정렬 전체를 돌리는 건 과하다. 실제로 10만 칸에서 10.56ms로, 아래의 투 포인터보다 열 배 느렸다. 면접에서는 "안정 정렬로도 되지만 O(n)이 있다"고 말하고 넘어가는 용도다.

## 읽는 손과 쓰는 손

이제 투 포인터다. 포인터를 두 개 둔다.

- `r`(읽기)은 매번 한 칸씩 간다.
- `w`(쓰기)는 "다음에 0이 아닌 값을 놓을 자리"다. 0이 아닌 값을 하나 놓을 때만 한 칸 간다.

`w`는 지금까지 읽은 0 아닌 값의 개수와 같다. 그러니 r번째 칸의 값이 0이 아니면 그 값이 최종적으로 갈 자리는 정확히 `w`다. 풀이 2가 매번 당기며 찾던 자리를 덧셈 한 번으로 안다.

### 두 번 훑기: 앞을 채우고 뒤를 0으로

가장 단순한 형태는 두 번 훑는다. 첫 번째에 0이 아닌 값을 `w` 자리에 차례로 덮어쓰고, 두 번째에 `w`부터 끝까지 0으로 채운다.

```js
// 풀이 4: 쓰기 포인터 + 뒤를 0으로 채우기
function moveZeroes(nums) {
  let w = 0;
  for (let r = 0; r < nums.length; r++)
    if (nums[r] !== 0) nums[w++] = nums[r]; // 0 아닌 값을 앞에서부터 덮어쓴다
  while (w < nums.length) nums[w++] = 0;    // 남은 칸은 모두 0
}
```

덮어써도 안전한 이유는 `w`가 언제나 `r` 이하라는 데 있다. `w`는 `r`보다 앞서 갈 수 없으니(0 아닌 값의 개수는 읽은 칸 수를 넘지 않는다) 아직 읽지 않은 칸을 덮어쓰는 일이 없다. 덮어쓰는 칸은 이미 읽은 칸이고, 그 칸의 값은 이미 앞쪽 어딘가에 옮겨 놨거나 0이라 버려도 되는 값이다.

시간 O(n), 공간 O(1)이다. 쓰기 횟수는 항상 n번이다. 앞쪽에 0 아닌 값 수만큼, 뒤쪽에 0의 수만큼 쓴다.

### 한 번 훑기: 바꾸면 0이 저절로 밀린다

두 번째 훑기를 없애려면 덮어쓰는 대신 바꾼다. `nums[r]`이 0이 아니면 `nums[w]`와 자리를 바꾼다. 그러면 `w` 자리에 있던 값(0이거나 자기 자신)이 `r` 자리로 간다.

이게 맞는 이유는 구간으로 보면 분명하다. 반복할 때마다 이 성질이 유지된다.

```text
[0, w)    0이 아닌 값, 원래 순서 그대로
[w, r)    전부 0
[r, 끝]   아직 안 읽은 칸
```

`[w, r)`가 전부 0이니, `w < r`일 때 `nums[w]`는 0이다. 그러니 바꾸기는 "0 아닌 값을 `w`로, 0을 `r`로" 보내는 일이 된다. 0 구간이 통째로 한 칸 오른쪽으로 굴러가는 모양이라 눈덩이(snowball)에 빗대기도 한다. `w === r`이면 자기 자신과 바꾸는 것이라 아무 일도 없다.

아래 그림에서 다음을 누르면 `[4, 0, 0, 5, 0, 7]`을 이 규칙으로 따라간다. ▼는 읽기 포인터 `r`, 색칠한 칸은 0이 아닌 값이 확정된 `[0, w)` 구간이다. 칸 위 숫자는 처음 값이고, 바꾼 뒤의 배열은 오른쪽에 적었다.

```js
// 풀이 5: 쓰기 포인터 + 바꾸기 (한 번 훑기)
function moveZeroes(nums) {
  let w = 0;                                   // [0, w)는 0 아닌 값, [w, r)는 0
  for (let r = 0; r < nums.length; r++) {
    if (nums[r] !== 0) {
      [nums[w], nums[r]] = [nums[r], nums[w]]; // 0 아닌 값은 앞으로, 0은 r 자리로
      w++;
    }
  }
}
```

시간 O(n), 공간 O(1)이다. 0 아닌 값의 순서가 지켜지는 이유도 구간에서 나온다. 0 아닌 값은 읽은 순서대로 `w` 자리에 하나씩 놓이고, 한 번 `[0, w)`에 들어간 값은 다시 움직이지 않는다.

### 쓰기 횟수를 줄이라는 후속 질문

문제의 후속 질문은 "연산 횟수를 최소로"다. 배열 칸에 값을 쓰는 횟수를 세어 비교해 봤다. 바꾸기 한 번은 두 칸을 쓰니 2로 셌다.

```text
입력              두 번 훑기  바꾸기  같은 칸이면 건너뛰기
[4,0,0,5,0,7]     6          6       4
[1,2,3,4,0]       5          8       0
[0,0,0,0,9]       5          2       2
[1,2,3,4,5]       5          10      0
```

두 번 훑기는 언제나 n번을 쓴다. 바꾸기는 0 아닌 값 하나당 2번이라 0이 거의 없을 때 오히려 많다. `[1, 2, 3, 4, 5]`처럼 0이 하나도 없으면 바꿀 필요가 전혀 없는데 10번을 쓴다. 모두 자기 자신과 바꾸기 때문이다.

그래서 `w !== r`일 때만 옮긴다. 이때 `nums[w]`는 0이 확실하니 바꾸기 대신 대입 두 번으로 충분하다.

```js
// 풀이 5를 다듬기: 같은 칸이면 아무것도 하지 않는다
function moveZeroes(nums) {
  let w = 0;
  for (let r = 0; r < nums.length; r++) {
    if (nums[r] !== 0) {
      if (w !== r) {         // w < r이면 nums[w]는 0이다
        nums[w] = nums[r];
        nums[r] = 0;
      }
      w++;
    }
  }
}
```

이 버전의 쓰기 횟수는 "자리를 옮겨야 하는 0 아닌 값의 수 × 2"다. 이미 제자리인 앞부분은 건드리지 않는다. 면접에서 "최소"를 물으면 이 표를 근거로 "0이 적으면 이 버전, 두 번 훑기는 항상 n번"이라고 답할 수 있다. 엄밀한 최솟값은 아니다. 0 아닌 값 하나가 옮겨 갈 때 그 자리를 0으로 비우는 쓰기가 다른 값이 그 자리를 다시 채우면 헛일이 되기 때문이다. 그래도 실무에서 의미 있는 차이는 "이미 제자리인 값을 다시 쓰지 않는다" 하나다.

`w !== r` 조건을 빼고 대입 두 번만 남기면 틀린다. `w === r`일 때 `nums[w] = nums[r]`은 아무 일도 안 하지만, 이어지는 `nums[r] = 0`이 방금 놓은 값을 지운다.

```text
badAssign [0,5,7,0,0,0] [0,0,0]
```

`[1, 2, 3]`이 `[0, 0, 0]`이 됐다. 바꾸기는 같은 칸이어도 안전했지만, 대입 두 개로 쪼개면 같은 칸일 때를 따로 막아야 한다.

### Python과 Java로

```python
from typing import List

def move_zeroes(nums: List[int]) -> None:
    w = 0                                  # 다음에 0이 아닌 값을 놓을 자리
    for r in range(len(nums)):
        if nums[r] != 0:
            nums[w], nums[r] = nums[r], nums[w]
            w += 1
```

Python에서는 한 줄짜리 리스트 컴프리헨션이 끌린다. 그대로 대입하면 틀리고, 슬라이스에 대입해야 원래 리스트가 바뀐다.

```python
a = [4, 0, 0, 5, 0, 7]
b = a
b = [x for x in b if x != 0] + [0] * b.count(0)   # b가 새 리스트를 가리킬 뿐
print("rebind", a)
b = a
b[:] = [x for x in b if x != 0] + [0] * b.count(0) # a가 가리키는 리스트를 고친다
print("slice", a)
```

```text
rebind [4, 0, 0, 5, 0, 7]
slice [4, 5, 7, 0, 0, 0]
```

슬라이스 대입은 맞지만 새 리스트를 만들었다가 복사하는 것이라 O(n) 추가 공간을 쓴다. 제자리 조건을 엄격하게 따지면 투 포인터가 답이다.

```java
class Solution {
    public void moveZeroes(int[] nums) {
        int w = 0;                                 // 다음에 0이 아닌 값을 놓을 자리
        for (int r = 0; r < nums.length; r++) {
            if (nums[r] != 0) {
                int t = nums[w]; nums[w] = nums[r]; nums[r] = t;
                w++;
            }
        }
    }
}
```

Java의 `int[]`는 참조로 넘어가서 메서드 안에서 칸을 바꾸면 호출한 쪽 배열이 바뀐다. 다만 `nums = new int[n]`처럼 변수에 새 배열을 대입하면 JavaScript, Python과 똑같이 호출한 쪽에는 반영되지 않는다. 세 언어 모두 같은 결과를 냈다.

```text
[4, 5, 7, 0, 0, 0]
[0]
[1, 0, 0]
[-3, 2, -1, 0, 0]
```

`[4, 0, 0, 5, 0, 7]`, `[0]`, `[0, 0, 1]`, `[-3, 0, 2, 0, -1]`을 넣은 결과다. 음수가 섞여도 0인지만 보니 상관없다.

## 같은 일을 다섯 가지로 하면

| 풀이 | 시간 | 추가 공간 | 쓰기 횟수 | 언제 고르나 |
|---|---|---|---|---|
| 1. 보조 배열 | O(n) | O(n) | 2n | 제자리 조건이 없을 때. 가장 읽기 쉽다 |
| 2. splice + push | O(n²) | O(1) | 0마다 O(n) | 쓰지 않는다. 짧은 목록의 일회성 스크립트 정도 |
| 3. 안정 정렬 | O(n log n) | 정렬 보조 공간 | - | 한 줄이 필요할 때. 순서 보장은 안정 정렬 덕분 |
| 4. 쓰기 포인터 + 0 채우기 | O(n) | O(1) | 항상 n | 가장 단순한 O(n) 제자리 풀이 |
| 5. 쓰기 포인터 + 바꾸기 | O(n) | O(1) | 옮길 값 × 2 | 한 번 훑기. 같은 칸 건너뛰기를 붙이면 쓰기가 가장 적다 |

10만 칸, 0이 반쯤 섞인 배열에서 잰 시간은 이렇다.

```text

100000 splice      5621.70ms
100000 안정 정렬   10.56ms
100000 0 채우기    1.10ms
100000 바꾸기      1.02ms
```

풀이 4와 5는 이 크기에서 차이가 없다. 둘 중 무엇을 내도 된다. 면접에서는 풀이 4로 시작해서 "쓰기를 줄이려면" 질문에 풀이 5로 넘어가는 흐름이 자연스럽다.

## 0의 순서도 상관없다면

조건을 하나 풀어 "0 아닌 값의 순서도 상관없다"면 양 끝 투 포인터로 쓰기를 더 줄일 수 있다. 왼쪽 포인터는 0을 찾고, 오른쪽 포인터는 0이 아닌 값을 찾고, 찾으면 오른쪽 값을 왼쪽에 놓고 오른쪽을 0으로 비운다.

```js
function moveZeroesUnordered(nums) {
  let l = 0, r = nums.length - 1;
  while (l < r) {
    if (nums[l] !== 0) { l++; continue; } // 왼쪽은 0을 찾는다
    if (nums[r] === 0) { r--; continue; } // 오른쪽은 0 아닌 값을 찾는다
    nums[l] = nums[r];                    // 뒤의 값을 앞의 빈자리로
    nums[r] = 0;
    l++;
    r--;
  }
}
```

```text
[4,7,5,0,0,0] 쓰기 4
[4,1,2,3,0] 쓰기 2
```

`[4, 0, 0, 5, 0, 7]`이 `[4, 7, 5, 0, 0, 0]`이 됐다. 5와 7의 순서가 뒤집혔다. 대신 0 하나당 많아야 한 번만 옮기니 쓰기가 적다. `[0, 1, 2, 3, 4]`는 0이 하나라 4를 앞으로 가져오는 두 번으로 끝났는데, 순서 유지 버전(같은 칸 건너뛰기)은 1, 2, 3, 4를 모두 한 칸씩 당겨 8번을 쓴다. 순서 유지가 공짜가 아니라는 걸 보여 주는 숫자다. [Sort Colors](/posts/leetcode-sort-colors)의 세 포인터가 안정적이지 않은 이유도 같다. 뒤에서 값을 끌어오면 순서가 섞인다.

## 같은 틀로 푸는 다른 문제

### 0을 앞으로 보내라면

뒤에서 앞으로 훑으면 된다. 쓰기 포인터를 맨 뒤에서 시작해 0이 아닌 값을 만날 때마다 바꾸고 한 칸 당긴다.

```js
function zerosFront(nums) {
  let w = nums.length - 1;
  for (let r = nums.length - 1; r >= 0; r--)
    if (nums[r] !== 0) { [nums[w], nums[r]] = [nums[r], nums[w]]; w--; }
  return nums;
}
```

```text
front [0,0,0,4,5,7] [0,0,1]
```

### 조건이 0이 아니라 아무 조건이라면

"남길 값"의 조건만 함수로 받으면 안정 분할(stable partition)의 절반이 된다. 남길 값의 순서는 지켜지지만 버릴 값의 순서는 섞인다.

```js
function partition(a, keep) {
  let w = 0;
  for (let r = 0; r < a.length; r++)
    if (keep(a[r])) { [a[w], a[r]] = [a[r], a[w]]; w++; }
  return w; // 남긴 값의 개수
}
```

```text
partition 3 [8,6,2,3,5,1]
```

`[3, 8, 1, 6, 5, 2]`에서 짝수를 앞으로 보냈다. 8, 6, 2는 원래 순서대로지만 홀수는 3, 1, 5에서 3, 5, 1로 바뀌었다. 0을 뒤로 보내는 문제에서는 버릴 값이 모두 0이라 순서가 섞여도 티가 나지 않았던 것이다. 양쪽 순서를 모두 지켜야 하면 보조 배열이 필요하다.

### 남길 조건만 바꾼 이웃 문제

- LeetCode 27(Remove Element): 특정 값을 지우고 남은 개수를 돌려준다. 풀이 4의 첫 번째 훑기 그대로다. 뒤를 채울 필요도 없다. 아래 코드 블록에 옮겨 두었다.
- [Remove Duplicates from Sorted Array](/posts/leetcode-remove-duplicates-from-sorted-array): "남길지"의 조건이 "바로 앞에 쓴 값과 다른가"로 바뀐다.
- LeetCode 905(Sort Array By Parity): 짝수를 앞으로. 순서 조건이 없어 양 끝 포인터로도 된다.
- LeetCode 2460(Apply Operations to an Array): 이웃한 같은 값을 합친 뒤 0을 뒤로 보낸다. 뒷부분이 이 문제다. `[2, 2, 0, 4, 4, 1]`은 `[4, 8, 1, 0, 0, 0]`이 된다.
- [Sort Colors](/posts/leetcode-sort-colors): 두 구역이 세 구역으로 늘어난다.

```js
function removeElement(nums, val) {
  let w = 0;
  for (let r = 0; r < nums.length; r++) if (nums[r] !== val) nums[w++] = nums[r];
  return w; // 앞 w칸만 채점한다
}
// [3, 1, 3, 3, 2]에서 3을 지운다
```

```text
2 [1,2] [1,2,3,3,2]
```

돌려준 개수는 2이고 앞 두 칸이 `[1, 2]`다. 뒤의 `3, 3, 2`는 옛 값이 남은 것이고 채점하지 않는다. Move Zeroes와 달리 뒤를 정리하라는 조건이 없어서 두 번째 훑기가 통째로 빠진다.

## 목록에서 지운 항목을 걸러 낼 때

이 문제의 쓰기 포인터는 실무 코드에서 "목록에서 조건에 맞는 항목을 지운다"는 모양으로 자주 나온다. 게임의 총알 목록에서 화면 밖으로 나간 것을 지우거나, 메모리에 들고 있는 작업 큐에서 끝난 작업을 지우는 식이다. 이때 흔히 쓰는 코드가 셋이다.

```js
// 1. 뒤에서 앞으로 splice: 인덱스 밀림 버그는 없지만 지울 때마다 뒤를 당긴다
for (let i = items.length - 1; i >= 0; i--) if (items[i].dead) items.splice(i, 1);

// 2. filter: 새 배열을 만든다
items = items.filter(x => !x.dead);

// 3. 쓰기 포인터로 제자리 압축: 이 문제의 풀이 4와 같다
let w = 0;
for (let r = 0; r < items.length; r++) if (!items[r].dead) items[w++] = items[r];
items.length = w;  // 뒤에 남은 칸을 잘라 낸다
```

절반이 지울 대상인 객체 배열로 재 봤다.

```text
10000  뒤에서 splice  50.13ms
10000  압축           0.10ms
10000  filter         0.46ms
100000 뒤에서 splice  2274.57ms
100000 압축           0.74ms
100000 filter         2.36ms
```

뒤에서 앞으로 도는 `splice`는 앞에서 도는 버전의 인덱스 버그를 피하려고 쓰는 코드인데, 시간은 여전히 O(n²)이다. 10만 개에서 2초가 넘었다. `filter`는 O(n)이고 읽기 쉬워서 대부분은 이걸로 충분하다. 다만 새 배열을 만들기 때문에, 그 배열을 다른 곳에서도 참조하고 있으면 그쪽은 옛 목록을 계속 본다. 같은 배열 객체를 유지해야 하거나 매 프레임 할당을 줄여야 할 때는 압축을 쓴다. 마지막의 `items.length = w`가 Move Zeroes에서 뒤를 0으로 채우던 줄에 해당한다. 성능 문제가 "목록이 커질수록 점점 느려진다"는 증상으로 나타나면 반복문 안의 `splice`, `shift`, `indexOf`부터 찾아본다.

## 자리를 계산하면 당길 필요가 없다

Move Zeroes는 "0이 아닌 값이 최종적으로 갈 자리"가 지금까지 읽은 0 아닌 값의 개수라는 걸 알아채는 문제다. 그 개수를 쓰기 포인터 `w`로 들고 다니면 `splice`처럼 매번 배열을 당길 필요 없이 한 번 훑기로 끝난다. `w`가 `r`을 앞지르지 않으니 덮어써도 안전하고, `[w, r)`가 모두 0이라는 불변식 덕분에 바꾸기 한 번으로 0이 저절로 밀린다. 쓰기를 줄이라는 질문에는 같은 칸일 때 건너뛰는 한 줄로 답한다. 같은 쓰기 포인터에 "바로 앞에 쓴 값과 비교" 조건을 붙이면 [Remove Duplicates from Sorted Array](/posts/leetcode-remove-duplicates-from-sorted-array)가 된다.

## 면접에서 나올 만한 질문

### 이 문제를 O(n), O(1) 공간으로 어떻게 푸나요?

읽기 포인터 `r`과 쓰기 포인터 `w`를 둔다. `r`이 0 아닌 값을 만날 때마다 `nums[w]`와 바꾸고 `w`를 한 칸 민다. `[0, w)`에는 0 아닌 값이 원래 순서대로, `[w, r)`에는 0만 있다는 불변식이 유지되어 끝나면 0이 모두 뒤에 모인다. 한 번 훑기라 O(n), 포인터 두 개라 O(1)이다.

### splice로 0을 빼고 push하면 왜 안 되나요?

`splice(i, 1)`이 i 뒤의 모든 값을 한 칸씩 당기는 O(n) 연산이라 0이 많으면 전체가 O(n²)이 된다. 10만 칸에서 5.6초가 걸렸고 투 포인터는 1ms였다. 그리고 뺀 뒤에 인덱스를 올리면 당겨 온 0을 건너뛰는 버그가 생기기 쉽다.

### 덮어써도 아직 안 읽은 값이 사라지지 않는 이유는요?

`w`는 지금까지 읽은 0 아닌 값의 개수라 항상 `r` 이하다. 그래서 덮어쓰는 칸은 이미 읽은 칸이고, 그 칸의 값은 이미 앞쪽에 옮겼거나 0이다. 같은 방향 투 포인터로 제자리 수정을 할 때 가장 먼저 확인할 성질이 이 "쓰기 포인터가 읽기 포인터를 앞지르지 않는다"다.

### 쓰기 횟수를 최소로 줄이려면 어떻게 하나요?

`w !== r`일 때만 `nums[w] = nums[r]; nums[r] = 0`을 한다. 이미 제자리인 앞부분은 건드리지 않아서 0이 없는 배열이면 한 번도 쓰지 않는다. 0 채우기 방식은 언제나 n번을 쓰고, 조건 없는 바꾸기는 0 아닌 값마다 두 칸을 써서 0이 적을 때 오히려 많다. 조건 없이 대입 두 개로 쪼개면 같은 칸일 때 값을 지우니 조건이 꼭 필요하다.

### 순서를 지키지 않아도 된다면 무엇이 달라지나요?

양 끝 포인터로 바꾼다. 왼쪽은 0을, 오른쪽은 0 아닌 값을 찾아 오른쪽 값을 왼쪽에 놓는다. 0 하나당 많아야 한 번만 옮기니 쓰기가 더 적다. `[0, 1, 2, 3, 4]`가 순서 유지 버전은 8번, 이 버전은 2번이었다. 대신 0 아닌 값의 순서가 섞인다.

### 정렬로 풀 수는 없나요?

"0이면 1, 아니면 0"을 키로 안정 정렬하면 된다. `nums.sort((a, b) => (a === 0) - (b === 0))` 한 줄이다. 0 아닌 값의 순서가 지켜지는 건 ES2019부터 `Array.prototype.sort`가 안정 정렬로 정해졌기 때문이다. 다만 O(n log n)이라 O(n) 풀이가 있는 문제에서 답으로 내지는 않는다.

### LeetCode에서 결과를 반환하지 않는데 어떻게 채점되나요?

넘긴 배열 자체를 고쳤는지 본다. 그래서 함수 안에서 `nums = 새 배열`이라고 쓰면 호출한 쪽 배열은 그대로라 틀린다. JavaScript, Python, Java 모두 변수에 새 배열을 대입하는 건 그 이름이 가리키는 대상을 바꿀 뿐이다. Python에서 꼭 한 줄로 쓰려면 `nums[:] = ...`로 슬라이스에 대입한다.
