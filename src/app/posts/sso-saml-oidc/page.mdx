퇴사한 사람의 계정이 사내 위키에 석 달째 살아 있었다는 이야기는 보안 점검에서 흔히 나온다. 메일과 메신저는 퇴사일에 막았는데, 위키와 대시보드와 배포 도구는 각자 따로 계정을 만들어 썼으니 누가 일일이 지우지 않으면 그대로 남는다. 반대로 입사자는 첫 주 내내 도구마다 계정을 신청한다.

SSO(Single Sign-On)는 이 문제를 "로그인은 한 곳에서만 한다"로 푼다. 회사의 신원 공급자(IdP)에 한 번 로그인하면 연결된 앱들이 그 결과를 믿는다. IdP에서 계정을 막으면 모든 앱의 새 로그인이 막힌다. 이 글은 기업 SSO에서 쓰는 두 규약, SAML 2.0과 OpenID Connect(OIDC)를 비교하고, 앱(SP) 쪽에서 무엇을 확인해야 하는지를 Node로 직접 서명하고 검증해 본 결과로 따라간다. 로그아웃과 계정 자동 생성·삭제(JIT, SCIM)까지 다룬다.

OIDC가 얹혀 있는 OAuth 인가 코드 흐름은 [OAuth 2.0](/posts/oauth)에, ID 토큰의 서명 키를 바꾸는 이야기는 [JWT 서명 키 교체](/posts/jwt-key-rotation)에 있다. 여기서는 그 위에서 "여러 앱이 한 IdP를 믿는 구조"를 본다.

## 로그인을 한곳에 모으면

SSO에는 두 역할이 있다. 로그인을 받아 주고 "이 사람은 누구다"를 증명해 주는 IdP(Identity Provider, Okta·Microsoft Entra ID·Google Workspace·Keycloak 같은 것), 그리고 그 증명을 믿고 자기 서비스에 들여보내는 쪽이다. SAML에서는 후자를 SP(Service Provider), OIDC에서는 RP(Relying Party)라고 부른다. 이름만 다르고 하는 일은 같다.

로그인을 모으면 좋은 점이 분명하다. 비밀번호 정책과 MFA, 기기 확인을 IdP 한곳에서 강하게 걸 수 있다. 앱은 비밀번호를 저장하지 않는다. 퇴사 처리는 IdP 계정 하나를 막는 일이 된다. 대신 IdP가 단일 장애점이 된다. IdP가 멈추면 모든 앱의 새 로그인이 멈추고, IdP 관리자 계정이 털리면 모든 앱이 열린다. IdP 관리자 계정에는 [패스키](/posts/passkeys-webauthn) 같은 피싱 저항 인증을 먼저 건다.

여기서 하나 구분해 둔다. 세션이 두 겹이다. IdP에 로그인된 IdP 세션이 있고, 각 앱이 자기 쿠키로 들고 있는 앱 세션이 따로 있다. 위키에 들어갈 때 IdP 세션이 살아 있으면 비밀번호를 다시 묻지 않고 바로 돌려보내 준다. 사용자가 "한 번만 로그인했다"고 느끼는 건 이 IdP 세션 덕분이다. 이 두 겹이 뒤에서 볼 로그아웃을 어렵게 만든다.

## Assertion 한 장 뜯어보기

IdP가 서명하는 핵심 덩어리가 Assertion이다. "이 IdP가, 언제, 누구를, 어느 SP를 위해, 이런 속성을 증명한다"는 문서다. Node의 `xml-crypto`로 RSA-SHA256 서명을 붙여 만든 실제 Assertion에서 서명값을 줄이고 주요 부분을 남겼다.

```xml
<saml:Assertion xmlns:saml="urn:oasis:names:tc:SAML:2.0:assertion" ID="_a1" Version="2.0" IssueInstant="2026-10-25T01:00:00Z">
<saml:Issuer>https://idp.example.com</saml:Issuer>
<Signature xmlns="http://www.w3.org/2000/09/xmldsig#">
<SignedInfo>
<CanonicalizationMethod Algorithm="http://www.w3.org/2001/10/xml-exc-c14n#"/>
<SignatureMethod Algorithm="http://www.w3.org/2001/04/xmldsig-more#rsa-sha256"/>
<Reference URI="#_a1">
...
<DigestValue>1nZXJzlpDRanwyiWik0iQZ3rsOfSEGqqtH3n4yGejPc=</DigestValue>
</Reference>
</SignedInfo>
<SignatureValue>PmMpzAGMHP58FCdvV3888RPniKaM5weA...</SignatureValue>
</Signature>
<saml:Subject>
<saml:NameID Format="urn:oasis:names:tc:SAML:1.1:nameid-format:emailAddress">mina@example.com</saml:NameID>
<saml:SubjectConfirmation Method="urn:oasis:names:tc:SAML:2.0:cm:bearer">
<saml:SubjectConfirmationData InResponseTo="_req123" Recipient="https://app.example.com/saml/acs" NotOnOrAfter="2026-10-25T01:05:00Z"/>
</saml:SubjectConfirmation>
</saml:Subject>
<saml:Conditions NotBefore="2026-10-25T00:59:55Z" NotOnOrAfter="2026-10-25T01:05:00Z">
<saml:AudienceRestriction>
<saml:Audience>https://app.example.com/saml/metadata</saml:Audience>
</saml:AudienceRestriction>
</saml:Conditions>
<saml:AttributeStatement>
<saml:Attribute Name="groups">
<saml:AttributeValue>engineering</saml:AttributeValue>
</saml:Attribute>
</saml:AttributeStatement>
</saml:Assertion>
```

필드가 많아 보이지만 SP가 볼 곳은 정해져 있다. 조각을 눌러 보자.

## 서명이 맞아도 확인할 것이 남는다

SP 검증 코드를 만들어 경우마다 넣어 봤다. 서명 하나만 보는 게 아니라는 걸 결과가 보여 준다.

```text
1 valid                : ACCEPT NameID=mina@example.com groups=engineering
2 NameID tampered      : REJECT signature invalid
3 after 10 minutes     : REJECT expired at 2026-10-25T01:05:00Z (now 2026-10-25T01:10:00Z)
4 SP sent _req456       : REJECT InResponseTo "_req123" expected "_req456"
4b IdP-initiated        : REJECT InResponseTo "(none)" expected "_req123"
5 assertion for other SP: REJECT audience "https://other-app.example.com"
6 signature removed     : REJECT no signature
```

2번은 NameID를 `admin@example.com`으로 바꿨더니 다이제스트가 어긋나 서명이 깨졌다. 5번은 서명이 멀쩡하다. 같은 IdP가 다른 앱용으로 정상 발급한 Assertion이다. 한 IdP에 연결된 앱이 수십 개라면, 그중 하나의 앱(또는 그 앱의 로그)에서 Assertion을 얻은 사람이 그걸 내 앱에 들고 올 수 있다. Audience를 안 보면 그대로 들어온다. 6번은 서명이 아예 없는 응답이다. "서명이 있으면 검증한다"로 짜 두면 서명을 지운 응답이 통과한다. 서명은 있으면 보는 게 아니라 반드시 있어야 하는 것이다.

## 서명은 맞는데 다른 사람으로 들어온다

목록의 두 번째 칸, "서명 대상"을 왜 따로 뒀는지가 SAML에서 가장 유명한 함정이다. XML 서명은 문서 전체가 아니라 ID로 가리킨 요소 하나를 서명한다. 검증 코드가 "서명이 맞다"를 확인한 뒤 사용자 정보를 "문서의 첫 번째 Assertion"에서 읽으면, 서명된 Assertion은 그대로 두고 서명 없는 Assertion을 앞에 끼운 응답이 통과한다. 이걸 XML 서명 감싸기(XML Signature Wrapping)라고 부른다. 두 가지 검증 코드에 같은 응답을 넣었다.

```text
7 wrapped, naive SP     : ACCEPT NameID=admin@example.com groups=engineering
7 wrapped, safe SP      : ACCEPT NameID=mina@example.com groups=engineering
```

둘 다 서명 검증은 통과했다. 서명은 정말로 `mina`의 Assertion을 덮고 있으니까. 차이는 사용자 정보를 어디서 읽었느냐다. 첫 번째 코드는 문서에서 처음 만난 Assertion을 읽어 `admin`으로 로그인시켰다. 두 번째 코드는 `xml-crypto`의 `getSignedReferences()`로 서명이 실제로 덮은 요소만 꺼내 읽었다.

여기서 얻을 교훈은 "직접 짜지 말라"에 가깝다. XML 정규화, 네임스페이스, 파서마다 다른 해석이 얽혀서, 널리 쓰이는 SAML 라이브러리에서도 이 계열 취약점이 여러 번 나왔다(2025년 ruby-saml의 파서 차이 문제가 한 예다). 관리가 잘 되는 라이브러리를 쓰고, 보안 업데이트를 빨리 따라가고, 라이브러리가 돌려준 "검증된 Assertion" 객체에서만 값을 읽는다. 응답 XML을 다시 파싱해서 값을 꺼내는 코드가 있다면 그게 구멍이다.

## OIDC로 하면 같은 일이 이렇게 보인다

OIDC는 [OAuth 인가 코드 흐름](/posts/oauth) 위에 ID 토큰을 얹은 규약이다. SAML의 Assertion 자리에 JWT로 된 ID 토큰이 오고, 브라우저로는 짧은 인가 코드만 지나가며 토큰은 RP 서버가 IdP에 직접 받는다. 확인할 것도 거의 1:1로 대응한다. `iss`는 Issuer, `aud`는 Audience, `nonce`는 InResponseTo, `exp`는 NotOnOrAfter다. `jose`로 ID 토큰을 만들어 RP 검증에 넣어 봤다.

```text
payload: {"nonce":"n-7Fq2","email":"mina@example.com","groups":["engineering"],"iss":"https://idp.example.com","sub":"248289761001","aud":"app-web","iat":1792629198,"exp":1792629498}
1 valid          : ACCEPT sub=248289761001 email=mina@example.com
2 other client   : REJECT ERR_JWT_CLAIM_VALIDATION_FAILED: unexpected "aud" claim value
3 other issuer   : REJECT ERR_JWT_CLAIM_VALIDATION_FAILED: unexpected "iss" claim value
4 expired        : REJECT ERR_JWT_EXPIRED: "exp" claim timestamp check failed
5 replayed (nonce): REJECT nonce "n-7Fq2" expected "n-NEW9"
6 payload edited : REJECT ERR_JWS_SIGNATURE_VERIFICATION_FAILED: signature verification failed
```

`jwtVerify`에 `issuer`와 `audience`를 넘기면 2~4번은 라이브러리가 걸러 준다. `nonce`는 라이브러리가 모르는 값이라 5번처럼 직접 비교해야 한다. 계정은 `email`이 아니라 `iss`와 `sub`의 쌍으로 묶는다. OIDC 명세가 보장하는 고유 식별자는 이 쌍뿐이고, 이메일은 바뀌거나 다른 IdP에서 같은 값이 나올 수 있다.

둘 중 무엇을 고를지는 대개 상대가 정한다. 연동할 IdP나 SaaS가 지원하는 쪽을 쓴다. 둘 다 된다면 비교는 이렇다.

| | SAML 2.0 | OIDC |
|---|---|---|
| 증명서 형식 | 서명된 XML Assertion | 서명된 JWT(ID 토큰) |
| 브라우저를 지나는 것 | Assertion 전체(POST) | 짧은 인가 코드 |
| 서명 키 배포 | 메타데이터 XML의 인증서, 교체 시 다시 등록 | discovery 문서와 JWKS 주소, 자동으로 갱신 |
| 모바일 앱·SPA | 맞지 않는다 | PKCE와 함께 쓴다 |
| API 호출 권한 | 따로 없다 | 같은 흐름에서 액세스 토큰을 받는다 |
| 주로 쓰는 곳 | 사내 SSO, 기업용 SaaS 연동 | 새로 만드는 서비스, 소셜 로그인, 모바일 |

새로 만드는 앱이라면 OIDC가 다루기 쉽다. JSON과 JWT라 라이브러리가 많고, 키 교체가 JWKS로 자동화된다. 다만 기업 고객이 "우리 IdP는 SAML만 된다"고 하면 SAML도 받아야 한다. 그래서 많은 서비스가 두 규약을 받아 주는 브로커(Keycloak 같은 것)를 앞에 두고, 앱 자신은 OIDC 하나만 구현한다.

## 로그아웃은 로그인보다 어렵다

로그인은 한 번으로 끝나는데, 로그아웃은 세션이 여러 곳에 있다는 문제를 그대로 드러낸다. 위키에서 로그아웃 버튼을 누르면 위키 쿠키는 지워진다. 그런데 IdP 세션이 살아 있으면 위키에 다시 들어갈 때 비밀번호 없이 바로 로그인된다. 대시보드와 배포 도구의 앱 세션은 아예 그대로다.

브라우저를 통하는 프런트채널 로그아웃은 IdP 로그아웃 페이지가 각 앱의 로그아웃 주소를 숨은 iframe으로 불러서 앱 쿠키를 지우게 하는 방식이다. 서버 간 통신이 필요 없어 붙이기 쉽지만, 요즘 브라우저가 iframe 안의 제3자 쿠키를 막으면서 앱 쿠키가 실리지 않아 조용히 실패하는 일이 늘었다. SAML의 단일 로그아웃(SLO)도 브라우저 리다이렉트를 앱마다 차례로 거치는 방식이 많아 중간 하나가 실패하면 나머지가 남는다.

현실적인 설계는 로그아웃 알림을 믿되 그것만 믿지 않는 것이다. 앱 세션 수명을 몇 시간 단위로 짧게 두고, 끝나면 IdP에 조용히 다시 물어 확인한다. 계정을 막는 일이 급하면 로그아웃 알림이 아니라 다음 절의 SCIM 비활성화로 한다.

## 계정은 누가 만들고 누가 지우나

SSO는 로그인만 모은다. 앱 안의 사용자 레코드(역할, 소속 팀, 개인 설정)는 여전히 각 앱에 있다. 이 레코드를 만드는 방법이 두 가지다.

JIT(Just-In-Time) 프로비저닝은 처음 로그인할 때 Assertion이나 ID 토큰의 속성으로 계정을 만든다. 구현이 간단하다. 대신 로그인할 때만 동작하니 지우는 일을 못 한다. 퇴사자는 다시 로그인하지 않으니 앱 안의 계정과 API 토큰, 이미 열린 세션이 그대로 남는다. 처음 장면의 위키가 그랬다.

SCIM(RFC 7643·7644)은 IdP가 앱의 사용자 API를 직접 부르는 표준이다. 입사하면 POST로 만들고, 정보가 바뀌면 PATCH, 퇴사하면 `active: false`로 바꾼다. 앱 쪽 SCIM 엔드포인트를 최소한으로 만들어 curl로 IdP 역할을 해 봤다.

```bash
H='Authorization: Bearer scim-demo-token'; B=http://localhost:18910/scim/v2/Users
# 입사: 사용자를 만들고 응답에서 앱이 매긴 id를 꺼낸다
ID=$(curl -s -X POST $B -H "$H" -H 'Content-Type: application/scim+json' \
  -d '{"schemas":["urn:ietf:params:scim:schemas:core:2.0:User"],"externalId":"00u1a2b3","userName":"mina@example.com","name":{"givenName":"Mina","familyName":"Kim"},"active":true}' \
  | tee c.json | node -e 'let s="";process.stdin.on("data",d=>s+=d).on("end",()=>console.log(JSON.parse(s).id))')
grep -E '"(id|userName|active)"' c.json
# 같은 사람을 또 만들면 상태 코드만 본다
curl -s -o /dev/null -w '%{http_code}\n' -X POST $B -H "$H" -d '{"userName":"mina@example.com"}'
# 퇴사: 비활성화
curl -s -X PATCH $B/$ID -H "$H" \
  -d '{"schemas":["urn:ietf:params:scim:api:messages:2.0:PatchOp"],"Operations":[{"op":"replace","path":"active","value":false}]}' \
  | grep -E '"(userName|active)"'
```

```text
  "id": "f47f1536-c6bc-4671-a939-2756cfe111b8",
  "userName": "mina@example.com",
  "active": true,
409
  "userName": "mina@example.com",
  "active": false,
```

`id`는 앱이 매긴 값이고, `externalId`는 IdP 쪽 id다. IdP는 이후 이 `id`로 PATCH를 보낸다. 같은 `userName`을 다시 만들려 하면 RFC 7644대로 409와 `scimType: "uniqueness"`를 돌려준다. IdP는 이 응답을 보고 기존 사용자를 찾아 연결한다.

앱 서버 로그에는 비활성화와 함께 열려 있던 세션 두 개를 끊은 기록이 남았다.

```text
CREATE mina@example.com
DEACTIVATE mina@example.com: revoked 2 sessions
```

## SSO를 붙인 뒤 걸려 오는 문의

"로그인하면 IdP에서 돌아오는데 '요청을 찾을 수 없다'며 실패한다." SAML에서 가장 흔한 문의다. IdP가 ACS로 보내는 건 다른 사이트에서 시작된 POST다. 앱의 세션 쿠키가 `SameSite=Lax`(요즘 브라우저의 기본값)면 교차 사이트 POST에는 실리지 않아서, 앱은 처음 저장한 요청 ID를 찾지 못한다. ACS를 위한 상태 쿠키는 `SameSite=None; Secure`로 따로 두거나, 요청 ID를 쿠키가 아닌 RelayState와 서버 저장소로 짝짓는다. 크롬은 SameSite를 적지 않은 쿠키에 한해 만든 지 2분 안의 POST는 보내 주는 예외를 둔 적이 있어서, 개발 중엔 되다가 운영에서 안 되는 식으로 헷갈리기 쉽다. 쿠키 옵션 자체는 [CSRF 글](/posts/csrf)에 정리해 두었다.

"어느 날 아침 모든 SAML 로그인이 서명 오류로 실패한다." IdP가 서명 인증서를 교체했는데 SP에 새 인증서를 등록하지 않았다. SAML은 OIDC의 JWKS처럼 자동으로 따라가지 않는 경우가 많다. 메타데이터 주소를 주기적으로 다시 읽게 하거나, IdP가 새 인증서를 미리 게시하는 기간에 두 인증서를 함께 믿도록 등록한다. 겹쳐서 교체하는 순서는 [JWT 서명 키 교체](/posts/jwt-key-rotation)와 같다.

"NotBefore 때문에 가끔 실패한다." IdP와 SP의 시계가 몇 초 어긋나면 막 발급된 Assertion이 아직 유효하지 않다고 나온다. 검증에 30초 안팎의 오차를 허용하고 서버 시계를 NTP로 맞춘다.

"이름을 바꾼 직원이 새 계정으로 들어왔다." 계정을 이메일 NameID로 묶어 두면 이메일이 바뀔 때 새 사람처럼 보인다. SAML은 persistent NameID나 바뀌지 않는 직원 id 속성으로, OIDC는 `iss`와 `sub`로 묶는다.

"로드 밸런서 뒤에서 Recipient가 안 맞는다." 앱이 자기 주소를 `http://`로 알고 있으면 ACS 주소 비교가 어긋난다. OAuth 콜백 주소에서 생기는 문제와 같은 원인이라, 앱이 기대하는 ACS 주소를 설정값으로 고정한다.

## 정리하며

SSO는 로그인을 IdP 한곳으로 모으고, 앱은 IdP가 서명한 증명서를 검증해 믿는다. SAML이든 OIDC든 앱이 볼 것은 같다. 누가 발급했나, 내 앱을 위한 것인가, 내가 보낸 요청에 대한 것인가, 아직 유효한가, 처음 보는가. SAML에서는 여기에 "서명이 덮은 그 요소를 읽는가"가 더해진다. 로그인만 모으고 계정 수명은 모으지 않으면 퇴사자 계정이 남으니, 로그아웃 알림과 SCIM 비활성화, 짧은 앱 세션을 함께 둔다.

## 면접에서 나올 만한 질문

### SSO는 무엇이고 무엇이 좋아지나요?

한 번의 로그인으로 여러 앱에 들어가게 하는 구조로, IdP가 로그인을 대신하고 앱은 IdP의 서명된 증명을 믿는다. 비밀번호와 MFA 정책을 한곳에서 관리하고, 앱은 비밀번호를 저장하지 않으며, 퇴사 처리가 IdP 계정 하나로 모인다. 대신 IdP가 단일 장애점이자 가장 중요한 공격 대상이 된다.

### SAML과 OIDC는 어떻게 다른가요?

둘 다 IdP가 서명한 신원 증명을 앱에 전달하는 규약이다. SAML은 XML Assertion을 브라우저 POST로 보내고 인증서를 메타데이터로 등록하며 사내 SSO에서 주로 쓴다. OIDC는 OAuth 인가 코드 흐름 위에서 JWT ID 토큰을 서버가 직접 받고, JWKS로 키를 자동 갱신하며 모바일과 SPA에도 맞는다.

### SP는 SAML 응답에서 무엇을 검증해야 하나요?

서명이 반드시 있는지와 등록된 IdP 인증서로 맞는지, 그리고 그 서명이 덮은 Assertion에서만 값을 읽는지를 먼저 본다. 그다음 Issuer, Audience가 내 entityID인지, Recipient가 내 ACS인지, InResponseTo가 내가 보낸 요청인지, NotBefore·NotOnOrAfter를 오차 범위로 확인하고, Assertion ID를 저장해 재사용을 막는다.

### XML 서명 감싸기 공격은 무엇인가요?

XML 서명이 ID로 가리킨 요소 하나만 덮는다는 점을 이용한다. 서명된 Assertion은 그대로 두고 서명 없는 가짜 Assertion을 문서에 끼우면, 서명 검증은 통과하는데 코드가 가짜를 읽어 다른 사용자로 로그인시킨다. 라이브러리가 돌려준 서명된 요소에서만 값을 읽고, 직접 XML을 다시 파싱하지 않으며, 라이브러리를 최신으로 유지해 막는다.

### SP 주도와 IdP 주도 흐름은 어떻게 다르고, IdP 주도는 왜 조심하나요?

SP 주도는 앱이 AuthnRequest를 보내고 응답의 InResponseTo로 짝을 맞춘다. IdP 주도는 요청 없이 응답이 와서 이 브라우저의 의도인지 확인할 수 없고, 남의 응답을 밀어 넣는 로그인 CSRF나 재사용에 약하다. 받아야 한다면 Assertion ID 캐시와 짧은 유효 시간, RelayState 허용 목록을 두고, 가능하면 포털 링크를 SP 로그인 시작 주소로 바꾼다.

### SSO 환경에서 로그아웃이 어려운 이유는요?

세션이 IdP와 각 앱에 따로 있어서 한 곳을 지워도 다른 곳이 남기 때문이다. OIDC 백채널 로그아웃은 IdP가 앱 서버에 서명된 logout_token을 보내 sid로 세션을 지우게 하고, 프런트채널 방식은 제3자 쿠키 차단으로 조용히 실패할 수 있다. 그래서 앱 세션을 짧게 두고 IdP에 주기적으로 다시 확인하는 방식을 함께 쓴다.

### JIT 프로비저닝과 SCIM은 어떻게 다른가요?

JIT는 첫 로그인 때 증명서의 속성으로 앱 계정을 만드는 방식이라 간단하지만, 로그인하지 않는 퇴사자를 지우지 못한다. SCIM은 IdP가 앱의 표준 사용자 API를 불러 생성·수정·비활성화를 밀어 넣는다. 퇴사 처리가 앱까지 닿게 하려면 SCIM이 필요하고, 비활성화할 때 세션과 API 토큰도 함께 끊어야 한다.

### 사용자 계정은 어떤 값으로 IdP 신원과 연결하나요?

바뀌지 않는 식별자로 연결한다. OIDC는 `iss`와 `sub`의 쌍이 명세가 보장하는 고유 식별자이고, SAML은 persistent NameID나 직원 고유 id 속성을 쓴다. 이메일로 묶으면 이름이나 도메인이 바뀔 때 새 계정이 생기거나, 다른 IdP의 같은 이메일이 남의 계정에 붙는 사고가 난다.
