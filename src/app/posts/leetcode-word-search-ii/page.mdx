보글(Boggle)이라는 단어 게임이 있다. 글자가 적힌 격자판에서 위아래 양옆으로 붙은 칸을 이어 단어를 만든다. 게임 판정 프로그램을 짠다면 사전의 단어 하나하나가 판에 있는지 확인해야 하는데, 사전에는 단어가 수만 개 있다. 단어 하나를 찾는 일은 [Word Search](/posts/leetcode-word-search)에서 백트래킹으로 풀었다. 그걸 단어 수만큼 반복하면 될까?

[LeetCode 212. Word Search II](https://leetcode.com/problems/word-search-ii/)가 이 질문이다. Hard 문제지만 새 아이디어는 하나뿐이다. 단어마다 판을 뒤지지 말고, 판을 한 번 뒤지면서 모든 단어를 함께 맞춰 본다. 그러려면 "지금까지 밟은 글자로 시작하는 단어가 있나"를 빨리 물어볼 수 있어야 하고, 그게 [Implement Trie](/posts/leetcode-implement-trie)의 `startsWith`다. 이 글은 단어마다 찾는 풀이부터 시작해 접두사 집합, 트라이, 트라이 가지치기까지 다섯 가지를 보고, 일부러 고약한 입력을 만들어 시간을 재어 본다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 판 하나에 단어 여러 개

입력은 글자 격자 `board`와 단어 목록 `words`다. 판에서 만들 수 있는 단어를 모두 찾아 돌려준다. 순서는 상관없다.

- 단어는 위아래 양옆으로 붙은 칸을 차례로 이어 만든다. 대각선은 안 된다.
- 한 단어 안에서 같은 칸을 두 번 쓸 수 없다. 다른 단어끼리는 같은 칸을 써도 된다.
- 판은 최대 12 × 12, 단어는 최대 3 × 10^4개, 단어 길이는 1 이상 10 이하, 모두 소문자이고 단어끼리 중복은 없다.

단어 길이가 10 이하라는 조건이 중요하다. 한 칸에서 출발하는 길은 첫 걸음에 4방향, 그 뒤로는 왔던 칸을 빼고 3방향이라 길이 10짜리 길이 4 · 3^9, 약 8만 개다. 칸이 144개니 판 전체에서 길이 10 이하의 길은 천만 개 단위다. 이걸 단어 3만 개마다 반복할 수는 없다.

이 글에서 쓸 예시는 3 × 3 판이다.

```text
o a t
h e a
t r e

words = [oat, eat, heat, tea, hot, tree]
답    = [oat, heat, eat]  (순서는 상관없다)
```

손으로 찾아보자. `oat`는 맨 윗줄을 왼쪽에서 오른쪽으로 읽으면 된다. `eat`는 가운데 `e`에서 위 `a`, 오른쪽 위 `t`로 간다. `heat`는 왼쪽 가운데 `h`에서 `e`로 간 뒤 `eat`과 같은 길을 탄다. `hot`는 `h` 위의 `o`까지는 가지만 `o` 옆에 `t`가 없다. `tea`는 `t`가 두 개인데 어느 쪽 옆에도 `e`가 없다. `tree`는 왼쪽 아래 `t`에서 `r`, `e`까지 가지만 그 `e` 옆에 다른 `e`가 없다.

## 단어마다 Word Search를 돌리면

가장 먼저 떠오르는 건 이미 아는 풀이를 단어마다 돌리는 것이다. [Word Search](/posts/leetcode-word-search)의 `exist(board, word)`는 판의 칸마다 출발해서 단어의 다음 글자와 맞는 옆 칸으로 DFS(깊이 우선 탐색, 한 길을 끝까지 가 본 뒤 돌아오는 탐색)를 한다. 지나온 칸은 `#`로 덮어 다시 밟지 않게 하고, 돌아올 때 원래 글자로 되돌린다. 이 "덮었다가 되돌리기"가 백트래킹이다([재귀와 백트래킹 글](/posts/recursion-backtracking)).

```js
const DIRS = [[1, 0], [-1, 0], [0, 1], [0, -1]];

function findWords(board, words) {
  const m = board.length, n = board[0].length;
  const exist = (word) => {
    const dfs = (r, c, i) => {
      if (board[r][c] !== word[i]) return false; // 글자가 다르거나 이미 쓴 칸(#)
      if (i === word.length - 1) return true;    // 마지막 글자까지 맞췄다
      const saved = board[r][c];
      board[r][c] = "#";                          // 이 길에서 쓴 칸 표시
      for (const [dr, dc] of DIRS) {
        const nr = r + dr, nc = c + dc;
        if (nr >= 0 && nr < m && nc >= 0 && nc < n && dfs(nr, nc, i + 1)) {
          board[r][c] = saved;
          return true;
        }
      }
      board[r][c] = saved;                        // 돌아오면서 되돌린다
      return false;
    };
    for (let r = 0; r < m; r++) {
      for (let c = 0; c < n; c++) if (dfs(r, c, 0)) return true;
    }
    return false;
  };
  return words.filter(exist);
}
```

판이 m × n, 단어가 W개, 가장 긴 단어가 L글자라면 단어 하나에 O(m · n · 4 · 3^(L-1)), 전체는 그 W배다. 공간은 재귀 깊이 O(L)뿐이다.

이 풀이의 낭비는 단어들이 앞부분을 나눠 쓸 때 드러난다. `heat`와 `hot`는 둘 다 `h`에서 출발한다. 단어마다 따로 돌리면 `h`가 있는 칸을 찾고 옆 칸을 둘러보는 일을 두 번 한다. 단어가 `aaaaaaa`로 시작하는 1만 개라면 같은 `aaaaaaa` 길을 1만 번 걷는다. 뒤의 측정에서 이런 입력에 이 풀이는 100초를 넘겼다.

## 판에 없는 글자부터 걸러 낸다

단어마다 돌리는 틀은 그대로 두고, 돌려 볼 필요도 없는 단어를 먼저 버릴 수 있다. 판의 글자 개수를 세어 두고, 단어에 필요한 글자가 판에 모자라면 DFS를 하지 않는다. `tree`는 `e`가 두 개 필요한데 판에 `e`가 하나뿐이라면 바로 탈락이다. 단어 길이가 칸 수보다 길어도 탈락이다.

```js
function findWords(board, words) {
  const m = board.length, n = board[0].length;
  const have = new Array(26).fill(0); // 판의 글자별 개수
  for (const row of board) for (const ch of row) have[ch.charCodeAt(0) - 97]++;
  const enough = (w) => {
    const need = new Array(26).fill(0);
    for (const ch of w) {
      const k = ch.charCodeAt(0) - 97;
      if (++need[k] > have[k]) return false; // 판에 이 글자가 모자라다
    }
    return true;
  };
  const candidates = words.filter((w) => w.length <= m * n && enough(w));
  return findWordsEach(board, candidates); // 앞의 풀이를 남은 단어에만 돌린다
}
```

거르는 데는 단어 글자 수 합만큼, O(W · L)이 든다. 판에 없는 글자가 섞인 단어가 많을 때는 효과가 크다. 판 글자가 `a`와 `b`뿐인데 단어에 `c`가 섞여 있으면 DFS를 아예 하지 않는다.

비슷한 요령으로, 단어의 첫 글자가 판에 많고 끝 글자가 적으면 단어를 뒤집어서 찾는 방법도 있다. 출발 칸이 줄어든다. 하지만 둘 다 "운 좋은 입력"에서만 이긴다. 판에 필요한 글자가 다 있는데 길이 이어지지 않는 단어, 앞부분이 같은 단어가 많은 입력에서는 첫 풀이와 똑같이 느리다. 단어를 하나씩 따로 본다는 틀 자체를 바꿔야 한다.

## 판을 한 번만 걷고 단어를 함께 맞춘다

방향을 뒤집어 보자. 단어마다 판을 걷지 말고, 판 위의 길을 한 번만 걷는다. 걸으면서 "지금까지 밟은 글자들"을 들고 다니고, 이 문자열이 어떤 단어의 접두사도 아니면 그 길은 더 갈 필요가 없으니 돌아선다. 접두사이면서 단어 자체이면 결과에 넣는다.

여기에 필요한 질문은 두 개다. "이 문자열로 시작하는 단어가 있나"와 "이 문자열이 단어인가". [Implement Trie](/posts/leetcode-implement-trie)에서 본 접두사 집합 풀이로 둘 다 해시 조회 한 번에 답할 수 있다.

```js
function findWords(board, words) {
  const m = board.length, n = board[0].length;
  const wordSet = new Set(words);
  const prefixes = new Set(); // 모든 단어의 모든 접두사
  for (const w of words) for (let i = 1; i <= w.length; i++) prefixes.add(w.slice(0, i));
  const found = new Set();    // 같은 단어를 여러 길에서 찾을 수 있으니 집합
  const dfs = (r, c, path) => {
    const ch = board[r][c];
    if (ch === "#") return;          // 이 길에서 이미 쓴 칸
    const next = path + ch;
    if (!prefixes.has(next)) return; // 이 길로는 어떤 단어도 못 만든다
    if (wordSet.has(next)) found.add(next);
    board[r][c] = "#";
    for (const [dr, dc] of DIRS) {
      const nr = r + dr, nc = c + dc;
      if (nr >= 0 && nr < m && nc >= 0 && nc < n) dfs(nr, nc, next);
    }
    board[r][c] = ch;
  };
  for (let r = 0; r < m; r++) for (let c = 0; c < n; c++) dfs(r, c, "");
  return [...found];
}
```

이제 `heat`와 `hot`는 `h` 칸에서 출발하는 길 하나 위에서 함께 확인된다. 걷는 길의 수는 단어 수 W와 상관없고, 단어들의 접두사가 허락하는 길만 걷는다. 최악은 O(m · n · 4 · 3^(L-1))번 걸음이다.

남은 문제는 걸음마다 드는 비용이다. 걸음마다 `path + ch`로 새 문자열을 만들고 해시를 계산하니 걸음 하나에 O(L)이 든다. 접두사 집합을 만드는 데도 O(W · L²) 시간과 공간이 든다. 그리고 `oat`를 이미 찾았어도 다음 칸에서 출발할 때 `oat` 길을 다시 확인한다. 찾은 단어를 목록에서 뺄 방법이 마땅치 않다.

## 트라이를 판 위의 길과 함께 내려간다

접두사 집합 대신 트라이를 쓰면 걸음마다 문자열을 만들 필요가 없다. 트라이는 단어를 글자 하나씩 내려가는 나무로 저장한 것이고, 노드 하나가 접두사 하나를 뜻한다. 판에서 한 칸 걸을 때 트라이에서도 그 글자의 자식으로 한 칸 내려가면, "지금까지 밟은 글자들"이 곧 지금 트라이 노드다. 자식이 없으면 그 접두사로 시작하는 단어가 없다는 뜻이니 돌아선다. 걸음 하나가 자식 조회 한 번, O(1)이다.

끝 표시는 `true`/`false` 대신 단어 문자열 자체를 노드에 들고 있게 한다. 그러면 단어를 찾았을 때 길을 따라 문자열을 다시 조립할 필요가 없다.

```js
function findWords(board, words) {
  const m = board.length, n = board[0].length;
  const root = { children: new Map(), word: null };
  for (const w of words) {
    let node = root;
    for (const ch of w) {
      if (!node.children.has(ch)) node.children.set(ch, { children: new Map(), word: null });
      node = node.children.get(ch);
    }
    node.word = w; // 끝 표시 대신 단어를 들고 있는다
  }
  const found = new Set();
  const dfs = (r, c, node) => {
    const ch = board[r][c];
    const child = node.children.get(ch); // '#'은 자식에 없으니 쓴 칸도 여기서 걸러진다
    if (!child) return;
    if (child.word !== null) found.add(child.word);
    board[r][c] = "#";
    for (const [dr, dc] of DIRS) {
      const nr = r + dr, nc = c + dc;
      if (nr >= 0 && nr < m && nc >= 0 && nc < n) dfs(nr, nc, child);
    }
    board[r][c] = ch;
  };
  for (let r = 0; r < m; r++) for (let c = 0; c < n; c++) dfs(r, c, root);
  return [...found];
}
```

트라이를 만드는 데 O(W · L), 판을 걷는 데 O(m · n · 4 · 3^(L-1)), 공간은 트라이 노드 O(W · L)와 재귀 깊이 O(L)이다. 접두사 집합 풀이와 걷는 길은 같고 걸음 하나가 싸졌다.

그런데 이 풀이에도 접두사 집합 풀이와 같은 낭비가 남아 있다. `oat`를 찾은 뒤에도 트라이에는 `o → a → t` 가지가 그대로 있어서, 판의 다른 `o`에서 출발하면 다시 그 길을 끝까지 걷는다. 판이 `a`와 `b`로만 채워지고 단어가 그 둘로 된 길이 10짜리 1,024개(가능한 조합 전부)라면, 단어를 다 찾은 뒤에도 판의 모든 칸에서 길이 10까지의 모든 길을 걷는다. 측정해 보니 이 입력에서 이 풀이는 213ms, 단어마다 찾는 첫 풀이는 9ms였다. 단어마다 찾기는 단어를 찾는 순간 멈추지만, 이 풀이는 멈출 줄을 모른다.

## 찾은 단어는 트라이에서 떼어 낸다

해결은 두 줄이다.

1. 단어를 찾으면 결과에 넣고 그 노드의 `word`를 `null`로 지운다. 같은 단어를 두 번 넣지 않으니 결과용 `Set`도 필요 없다.
2. DFS에서 돌아올 때, 지금 노드에 자식도 없고 `word`도 없으면 부모에서 이 노드를 떼어 낸다. 더 찾을 단어가 없는 가지라서다.

이렇게 하면 찾은 단어만 쓰던 가지가 트라이에서 사라지고, 다음 출발에서는 그 길을 첫 글자부터 걷지 않는다. 트라이가 판을 걸을수록 작아진다. 뿌리의 자식이 다 없어지면 남은 칸은 볼 필요도 없다.

```js
function findWords(board, words) {
  const m = board.length, n = board[0].length;
  const root = { children: new Map(), word: null };
  for (const w of words) {
    let node = root;
    for (const ch of w) {
      if (!node.children.has(ch)) node.children.set(ch, { children: new Map(), word: null });
      node = node.children.get(ch);
    }
    node.word = w;
  }
  const result = [];
  const dfs = (r, c, parent) => {
    const ch = board[r][c];
    const node = parent.children.get(ch); // 쓴 칸(#)이거나 이어지는 단어가 없으면 undefined
    if (!node) return;
    if (node.word !== null) {
      result.push(node.word);
      node.word = null;                   // 찾은 단어는 지운다
    }
    board[r][c] = "#";
    for (const [dr, dc] of DIRS) {
      const nr = r + dr, nc = c + dc;
      if (nr >= 0 && nr < m && nc >= 0 && nc < n) dfs(nr, nc, node);
    }
    board[r][c] = ch;
    if (node.children.size === 0 && node.word === null) {
      parent.children.delete(ch);         // 더 찾을 게 없는 가지는 잘라 낸다
    }
  };
  for (let r = 0; r < m; r++) {
    for (let c = 0; c < n; c++) {
      if (root.children.size === 0) return result; // 단어를 다 찾았다
      dfs(r, c, root);
    }
  }
  return result;
}
```

### Python과 Java로 쓰면

Python은 노드에 `word`를 두고, 가지를 잘라 낼 때는 `del parent.children[ch]`를 쓴다. 재귀 깊이는 단어 길이(최대 10)를 넘지 않는다.

```python
from typing import List


class TrieNode:
    __slots__ = ("children", "word")

    def __init__(self):
        self.children = {}
        self.word = None  # 여기서 끝나는 단어 자체를 들고 있는다


def find_words(board: List[List[str]], words: List[str]) -> List[str]:
    root = TrieNode()
    for w in words:
        node = root
        for ch in w:
            node = node.children.setdefault(ch, TrieNode())
        node.word = w

    m, n = len(board), len(board[0])
    result = []

    def dfs(r: int, c: int, parent: TrieNode) -> None:
        ch = board[r][c]
        node = parent.children.get(ch)  # '#'이면 None
        if node is None:
            return
        if node.word is not None:
            result.append(node.word)
            node.word = None  # 같은 단어를 두 번 넣지 않는다
        board[r][c] = "#"  # 이 길에서 쓴 칸
        for nr, nc in ((r + 1, c), (r - 1, c), (r, c + 1), (r, c - 1)):
            if 0 <= nr < m and 0 <= nc < n:
                dfs(nr, nc, node)
        board[r][c] = ch
        if not node.children and node.word is None:
            del parent.children[ch]  # 더 찾을 게 없는 가지는 잘라 낸다

    for r in range(m):
        for c in range(n):
            dfs(r, c, root)
    return result


board = [list("oat"), list("hea"), list("tre")]
print(find_words(board, ["oat", "eat", "heat", "tea", "hot", "tree"]))
print(board)
```

두 번째 줄은 판이 원래대로 돌아왔는지 확인한 것이다. `#`로 덮은 칸을 되돌리지 않으면 다음 출발에서 그 칸을 못 쓴다. Python에서는 이 문제가 시간 제한에 자주 걸리는데, 가지치기를 빼면 통과가 어렵다. 노드를 클래스 대신 딕셔너리 하나로 두고 단어를 `"$"` 키에 넣는 짧은 버전도 많이 쓰지만, 가지치기에서 `"$"` 키를 빼고 세어야 해서 실수하기 쉽다.

Java는 자식을 26칸 배열로 두는데, 배열은 `size`가 없으니 살아 있는 자식 수를 따로 센다. 판의 `#`를 `ch - 'a'`로 바꾸면 음수 인덱스가 되므로 `#` 검사를 먼저 한다.

```java
import java.util.*;

class Solution {
    private static class Node {
        Node[] children = new Node[26];
        String word;    // 여기서 끝나는 단어, 없으면 null
        int size;       // 살아 있는 자식 수 (가지 잘라 내기용)
    }

    private char[][] board;
    private List<String> result;

    public List<String> findWords(char[][] board, String[] words) {
        Node root = new Node();
        for (String w : words) {
            Node node = root;
            for (int i = 0; i < w.length(); i++) {
                int c = w.charAt(i) - 'a';
                if (node.children[c] == null) {
                    node.children[c] = new Node();
                    node.size++;
                }
                node = node.children[c];
            }
            node.word = w;
        }
        this.board = board;
        this.result = new ArrayList<>();
        for (int r = 0; r < board.length; r++)
            for (int c = 0; c < board[0].length; c++)
                dfs(r, c, root);
        return result;
    }

    private void dfs(int r, int c, Node parent) {
        char ch = board[r][c];
        if (ch == '#') return;                 // 이 길에서 이미 쓴 칸
        Node node = parent.children[ch - 'a'];
        if (node == null) return;
        if (node.word != null) {
            result.add(node.word);
            node.word = null;
        }
        board[r][c] = '#';
        if (r > 0) dfs(r - 1, c, node);
        if (r + 1 < board.length) dfs(r + 1, c, node);
        if (c > 0) dfs(r, c - 1, node);
        if (c + 1 < board[0].length) dfs(r, c + 1, node);
        board[r][c] = ch;
        if (node.size == 0 && node.word == null) {   // 빈 가지 잘라 내기
            parent.children[ch - 'a'] = null;
            parent.size--;
        }
    }
}
```

```text
[oat, heat, eat]
```

다섯 풀이를 12 × 12 판에서 네 가지 입력으로 돌렸다. Node.js 22에서 잰 값이다.

①은 26글자 무작위 판과 무작위 단어 3만 개(중복을 빼면 29,624개)다. 단어 대부분이 두세 글자 만에 막혀서 어느 풀이든 빠르다. ②는 앞에서 말한 "모든 단어를 찾을 수 있는" 입력이다. 가지치기 없는 트라이와 접두사 집합은 단어를 다 찾은 뒤에도 모든 길을 끝까지 걸어서 느리다. ③은 `b`가 판 양 끝에 하나씩 있어서 글자 개수 검사는 통과하지만 어떤 단어도 만들 수 없는 입력이다. 가지치기가 일어나지 않아서 두 트라이 풀이가 비슷하다.

④가 트라이를 쓰는 이유다. 판은 거의 `a`이고 아래 두 줄에 `b`부터 `y`까지 한 번씩 있다. 단어는 `aaaaaaa` 뒤에 그 글자 셋을 붙인 13,824개다. 단어마다 찾으면 같은 `aaaaaaa` 길을 13,824번 걸어서 100초가 넘게 걸렸다. 글자 개수 검사도 거의 소용이 없다. 세 글자가 서로 다른 단어 12,144개는 필요한 글자가 판에 다 있어서 걸러지지 않는다. 트라이 풀이들은 `aaaaaaa` 길을 한 번만 걷고 그 끝에서 세 글자만 갈라 보니 40ms 안팎이다. 2,500배 넘는 차이다. 접두사 집합도 같은 이유로 빠르지만 ②에서 보듯 문자열을 만드는 비용이 쌓인다.

네 입력을 모두 무난하게 넘기는 건 트라이 + 가지치기 하나뿐이다. 면접에서 이 풀이를 기본 답으로 내는 이유가 이 표에 다 있다.

## 다섯 풀이를 나란히 놓으면

판은 m × n, 단어는 W개, 가장 긴 단어는 L글자다. 걷는 길의 수 m · n · 4 · 3^(L-1)을 P라고 줄여 쓴다.

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 단어마다 Word Search | O(W · P) | O(L) | 단어가 몇 개뿐일 때 |
| 글자 개수로 거르기 | O(W · L + 남은 단어 수 · P) | O(1) 추가 | 판에 없는 글자가 섞인 단어가 많을 때. 다른 풀이 앞에 붙여도 된다 |
| 접두사 집합 + 판 DFS | O(W · L² + P · L) | O(W · L²) | 트라이를 짜기 싫을 때의 중간 단계 |
| 트라이 + 판 DFS | O(W · L + P) | O(W · L) | 모든 단어를 찾는 입력에 약하다 |
| 트라이 + 가지치기 | O(W · L + P), 실제로는 훨씬 적게 | O(W · L) | 기본 답 |

## 같은 단어가 두 번 나오고, 판이 망가진다

가장 흔한 실수는 같은 단어를 결과에 여러 번 넣는 것이다. 판에 `aa`를 만들 수 있는 길이 여러 개면, 단어를 찾을 때마다 넣는 코드는 같은 단어를 여러 번 넣는다.

```js
if (child.word !== null) result.push(child.word); // 지우지 않고 넣기만 한다
// board [["a","a"],["a","a"]], words ["aa"] -> ["aa","aa","aa","aa","aa","aa","aa","aa"]
```

2 × 2 판에서 `aa`는 칸 넷에서 각각 옆 칸 둘로 갈 수 있어서 여덟 번 나온다. 찾은 순간 `word`를 `null`로 지우거나, 결과를 `Set`으로 모은다. 위 테스트의 "여러 곳에서 찾아도 한 번만"이 이걸 잡는다.

두 번째는 단어를 찾았다고 바로 `return`하는 것이다.

```js
if (node.word !== null) { result.push(node.word); node.word = null; return; } // 여기서 멈춘다
// board [["c","a","t"],["x","x","s"]], words ["ca","cat","cats"] -> ["ca"]
```

`ca`를 찾고 돌아서 버려서 그 아래의 `cat`, `cats`를 못 찾는다. 단어 하나를 찾는 Word Search I에서는 찾으면 멈추는 게 맞지만, 여기서는 단어가 다른 단어의 접두사일 수 있다. 결과에 넣고 계속 내려가야 한다.

세 번째는 `return` 하나 때문에 판이 망가지는 것이다. 칸을 `#`로 덮은 뒤 중간에 `return`하면 되돌리는 줄을 건너뛴다. 그러면 다음 출발에서 그 칸이 영원히 `#`로 남는다. 덮기와 되돌리기 사이에는 `return`을 두지 않거나, 되돌린 뒤에 돌아간다.

그 밖에 이 문제에서 조심할 것들이다.

- 가지를 잘라 낼 때 `node.word === null` 확인을 빼면, 아직 못 찾은 단어로 끝나는 잎 노드까지 잘라서 그 단어를 영영 못 찾는다.
- 칸을 덮지 않고 `visited` 배열을 따로 둬도 되지만, 출발 칸마다 새로 만들면 O(m · n)이 매번 붙는다. 같은 배열을 덮고 되돌리며 다시 쓴다.
- 결과를 정렬해서 돌려줄 필요는 없다. LeetCode는 순서를 무시하고 채점한다.

## 면접관이 이어서 묻는 것

### 판은 그대로이고 단어 목록이 계속 바뀐다면

지금 풀이는 단어로 트라이를 만들고 판을 걷는다. 판이 고정이고 질문이 단어 하나씩 들어온다면, 반대로 판에서 만들 수 있는 길이 L 이하의 모든 문자열을 한 번 모아 두는 쪽이 낫다. 다만 12 × 12 판에서도 천만 단위라 메모리가 문제다. 실제로는 단어마다 Word Search I을 돌리되, 같은 단어 결과를 캐시해 두는 정도가 현실적이다.

### 대각선 이동도 된다면

방향 배열에 대각선 네 개를 더하면 끝이다. 대신 걷는 길의 수가 8 · 7^(L-1)로 늘어나서, 가지치기의 효과가 더 중요해진다. 보글 게임은 실제로 대각선을 허용한다.

### 단어를 찾은 길(칸 좌표)도 돌려 달라면

DFS에 지금까지의 칸 좌표를 담는 배열을 들고 다니다가, 단어를 찾는 순간 그 배열을 복사해 결과에 넣는다. 들어갈 때 넣고 나올 때 빼는, 백트래킹의 같은 틀이다. 같은 단어를 만드는 길이 여러 개라면 하나만 돌려줄지 전부 돌려줄지를 먼저 정해야 한다.

### 판이 아주 커서 여러 대에 나눠 돌린다면

판을 행 단위로 잘라 기계마다 출발 칸을 나눠 준다. 길은 경계를 넘어갈 수 있으니 각 기계는 판 전체를 읽을 수 있어야 하고, 출발 칸만 나눈다. 가지치기는 기계마다 따로 일어나서 효과가 줄어든다. 결과는 합집합으로 모은다.

## 판을 한 번만 걷고, 찾은 가지는 버린다

단어마다 판을 뒤지면 같은 접두사의 길을 단어 수만큼 다시 걷는다. 단어 목록을 트라이로 묶으면 판을 걷는 한 걸음이 트라이를 내려가는 한 걸음이 되고, 트라이에 없는 글자를 밟는 순간 그 길에서 만들 수 있는 모든 단어를 한꺼번에 포기한다. 여기에 찾은 단어를 지우고 빈 가지를 잘라 내면 트라이가 걸을수록 작아져서, 단어를 다 찾은 뒤에도 헛걸음하는 문제가 사라진다. 판의 칸을 `#`로 덮었다가 되돌리는 백트래킹, 찾아도 멈추지 않고 계속 내려가기, 같은 단어 한 번만 넣기. 이 세 가지를 지키면 답이 맞는다.

## 면접에서 나올 만한 질문

### 단어마다 Word Search를 돌리면 왜 느린가요?

같은 접두사를 가진 단어들이 같은 길을 단어 수만큼 다시 걷기 때문이다. 단어 하나에 O(m · n · 4 · 3^(L-1))이고 단어가 3만 개면 그 3만 배다. `aaaaaaa`로 시작하는 단어 1만 3천 개를 넣은 입력에서 이 풀이는 100초를 넘겼다. 트라이로 묶으면 같은 길은 한 번만 걷는다.

### 트라이가 이 문제에서 정확히 무슨 일을 하나요?

판 위에서 지금까지 밟은 글자들이 어떤 단어의 접두사인지를 걸음마다 O(1)로 알려 준다. 판에서 한 칸 걸을 때 트라이에서도 그 글자의 자식으로 한 칸 내려가고, 자식이 없으면 그 길에서는 어떤 단어도 만들 수 없으니 바로 돌아선다. 노드에 단어 문자열을 들고 있게 하면 찾은 순간 바로 결과에 넣을 수 있다.

### 찾은 단어를 트라이에서 지우는 이유는요?

두 가지다. 같은 단어를 여러 길에서 찾아도 한 번만 넣게 되고, 빈 가지를 잘라 내면 다음 출발에서 그 길을 다시 걷지 않는다. 모든 단어를 찾을 수 있는 입력에서 가지치기가 없으면 단어를 다 찾은 뒤에도 모든 길을 끝까지 걷는다. 직접 재 보면 이 입력에서 213ms가 9ms로 줄었다.

### 시간 복잡도는 어떻게 말하나요?

트라이를 만드는 데 O(W · L), 판을 걷는 데 최악 O(m · n · 4 · 3^(L-1))이다. 첫 걸음은 네 방향, 그 뒤는 왔던 칸을 빼고 세 방향이라 3의 거듭제곱이 된다. 단어 수 W가 판 탐색 쪽 식에 없다는 게 단어마다 찾는 풀이와의 차이다. 가지치기는 최악을 바꾸지 않지만 실제 걷는 길을 크게 줄인다.

### 방문 표시를 visited 배열 대신 판에 직접 하는 이유는요?

메모리를 따로 쓰지 않고, 트라이 조회와 방문 검사를 한 번에 할 수 있어서다. 칸을 `#`로 덮으면 `#`는 트라이 자식에 없으니 자식 조회 한 번으로 걸러진다. 대신 돌아올 때 반드시 원래 글자로 되돌려야 하고, 그 사이에 `return`을 두면 판이 망가진다. 입력을 바꾸면 안 되는 상황이라면 `visited` 배열 하나를 덮고 되돌리며 다시 쓴다.

### 단어를 찾았을 때 return하면 왜 틀리나요?

단어가 다른 단어의 접두사일 수 있기 때문이다. `ca`, `cat`, `cats`가 모두 목록에 있으면 `ca`를 찾고 멈추는 순간 나머지 둘을 놓친다. 결과에 넣고 단어 표시만 지운 뒤 계속 내려가야 한다. 단어 하나만 찾는 Word Search I과 다른 점이다.
