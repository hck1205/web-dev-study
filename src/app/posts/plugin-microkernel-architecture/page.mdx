에디터에 확장을 하나 깔았더니 저장할 때마다 1초씩 멈춘다. 확장을 끄면 멀쩡하다. 그런데 VS Code 자체는 멈추지 않고 "확장 호스트가 응답하지 않는다"는 알림만 뜬다. 같은 확장이 에디터와 한 몸이었다면 화면 전체가 굳었을 것이다.

VS Code, ESLint, webpack, Babel, Vite는 공통점이 있다. 사람들이 쓰는 기능 대부분이 본체가 아니라 플러그인에 있다. ESLint 본체는 파일을 파싱해 규칙을 돌리는 틀이고, React 규칙도 TypeScript 규칙도 플러그인이다. webpack은 내부 기능까지 상당 부분을 자기 플러그인 시스템 위에 올려 두었다. 이렇게 작고 오래 안 바뀌는 코어와, 그 위에 꽂는 확장으로 나누는 구조를 마이크로커널 아키텍처, 또는 플러그인 아키텍처라고 부른다.

이 글은 작은 플러그인 호스트를 Node 22로 직접 만들어 보면서 코어와 플러그인 사이의 계약, 발견과 로딩, 버전 호환, 격리를 따라간다. 코드를 층으로 나누는 [레이어드 아키텍처](/posts/layered-architecture)나 업무 규칙을 바깥 기술에서 떼어 내는 [헥사고날 아키텍처](/posts/hexagonal-architecture)와 무엇이 다른지는 뒤에서 나란히 놓고 본다.

## 코어가 하는 일은 생각보다 적다

마이크로커널 구조는 두 부분으로 이뤄진다. 코어 시스템과 플러그인 모듈이다.

코어는 "모든 플러그인이 공통으로 필요한 최소한"만 가진다. 에디터라면 파일 열기, 버퍼, 화면 그리기, 명령 실행 틀이다. 린터라면 파일을 읽고 AST로 바꾸고, 노드를 하나씩 방문하며 등록된 규칙을 부르는 루프다. 언어별 문법 강조, 특정 프레임워크 규칙, 회사 고유 정책 같은 건 코어에 없다.

플러그인은 코어가 열어 둔 구멍, 즉 확장점(extension point)에 자기 코드를 끼운다. 이 둘을 잇는 것이 세 가지다.

- 계약: 플러그인이 지켜야 할 모양. 이름, 어느 API 판을 따르는지, `activate` 같은 진입 함수
- 레지스트리: 코어가 "지금 누가 무엇을 맡았나"를 적어 두는 표. 명령 이름 → 함수, 파일 확장자 → 처리기
- 훅: 코어가 특정 시점에 "여기 끼어들 사람?" 하고 부르는 자리. 렌더 전, 저장 직후, 빌드 산출물을 쓰기 직전

아래 그림은 이 관계를 그린 것이다. 플러그인은 코어를 알지만 서로는 모른다. 점이 흐르는 방향이 의존 방향이다.

이 구조를 고르는 이유는 변경의 속도가 둘로 갈리기 때문이다. 코어는 몇 년에 한 번 크게 바뀌고, 플러그인은 매주 생기고 사라진다. 둘을 한 코드베이스에 두면 자주 바뀌는 쪽이 드물게 바뀌는 쪽을 계속 흔든다. 떼어 두면 코어 팀은 계약만 지키면 되고, 플러그인은 코어 릴리스를 기다리지 않는다.

## 작은 마크다운 도구로 만들어 보기

마크다운을 변환하는 작은 도구를 만든다고 하자. 코어는 텍스트를 받아 렌더 훅을 차례로 통과시키고, 이름으로 명령을 부를 수 있게 한다. 이모지 치환과 목차 생성은 플러그인으로 뺀다.

```js
// core.mjs
import { readdir } from "node:fs/promises";
import { pathToFileURL } from "node:url";
import path from "node:path";

export const CORE_API = 2; // 코어가 지금 제공하는 플러그인 API 판

export function createCore() {
  const hooks = { "markdown:render": [], command: new Map() };
  const loaded = [];
  // 플러그인이 받는 건 이 객체뿐이다. 코어 내부(hooks, loaded)는 직접 못 만진다
  const api = {
    apiVersion: CORE_API,
    onRender(fn) { hooks["markdown:render"].push(fn); },
    registerCommand(name, fn) {
      if (hooks.command.has(name)) throw new Error(`command "${name}" already registered`);
      hooks.command.set(name, fn);
    },
  };
  return {
    async loadFrom(dir) {
      for (const file of (await readdir(dir)).sort()) {
        const p = (await import(pathToFileURL(path.join(dir, file)).href)).default;
        if (p.apiVersion !== CORE_API) {
          console.log(`skip ${p.name}: needs api ${p.apiVersion}, core has ${CORE_API}`);
          continue;
        }
        try { p.activate(api); loaded.push(p.name); }
        catch (e) { console.log(`skip ${p.name}: ${e.message}`); }
      }
      console.log("loaded:", loaded.join(", "));
    },
    // 렌더 훅은 앞 플러그인의 결과를 다음 플러그인이 받는 폭포수 방식이다
    render(text) { return hooks["markdown:render"].reduce((acc, fn) => fn(acc), text); },
    run(name, ...args) {
      const fn = hooks.command.get(name);
      if (!fn) throw new Error(`unknown command ${name}`);
      return fn(...args);
    },
  };
}
```

플러그인은 계약 모양의 객체 하나를 내보낸다.

```js
// plugins/emoji.mjs
export default { name: "emoji", apiVersion: 2,
  activate(api) { api.onRender((t) => t.replaceAll(":ok:", "[OK]")); } };

// plugins/toc.mjs
export default { name: "toc", apiVersion: 2,
  activate(api) {
    api.registerCommand("toc", (t) =>
      t.split("\n").filter((l) => l.startsWith("## ")).map((l) => "- " + l.slice(3)).join("\n"));
  } };
```

여기에 일부러 문제 있는 플러그인 둘을 섞었다. API 1판을 기대하며 코어에 없는 `addLinter`를 부르는 `old-lint`, 그리고 이미 있는 `toc` 명령을 또 등록하려는 `toc-fancy`다. 돌려 보면 이렇다.

```text
skip old-lint: needs api 1, core has 2
skip toc-fancy: command "toc" already registered
loaded: emoji, toc
## 시작 [OK]
본문
## 끝
- 시작
- 끝
```

이 짧은 예제에 이 구조의 고민이 거의 다 들어 있다. 코어는 플러그인 폴더를 훑어 찾고(발견), 계약 판을 확인하고(호환성), `activate`를 불러 레지스트리에 등록하게 하고(로딩), 등록 충돌을 막는다. 그리고 플러그인이 만지는 건 `api` 객체뿐이라 코어 내부 구조를 바꿔도 플러그인은 모른다. 이 `api` 객체가 곧 계약이다.

한 가지 함정도 보인다. `toc-fancy`가 `registerCommand`를 부르기 전에 렌더 훅을 먼저 등록했다면, 활성화는 실패했는데 훅은 남는다. 실제 호스트들은 플러그인별로 등록한 것을 따로 모아 두었다가 실패하거나 끌 때 한꺼번에 걷어 낸다. VS Code가 `context.subscriptions`에 등록 해제 함수를 넣게 하는 게 이 이유다.

## 훅은 부르는 방식이 여러 가지다

위 예제의 렌더 훅은 결과를 이어 붙이는 방식이었다. 훅에는 몇 가지 모양이 있고, 무엇을 고르느냐에 따라 플러그인끼리 서로를 얼마나 신경 써야 하는지가 달라진다.

- 알림형: 이벤트만 알리고 반환값은 버린다. 순서가 상관없어 플러그인끼리 얽히지 않는다
- 폭포수형: 앞 플러그인의 반환값을 다음 플러그인이 받는다. 순서가 결과를 바꾼다
- 먼저 답한 쪽이 이기는 형: 누가 값을 돌려주면 거기서 멈춘다. "이 파일을 누가 처리하나" 같은 질문에 쓴다
- 비동기 직렬·병렬형: 플러그인이 비동기 작업을 할 때 기다릴지, 동시에 돌릴지

webpack의 tapable 라이브러리가 이걸 클래스로 나눠 둔 대표적인 예다. `SyncHook`, `SyncWaterfallHook`, `SyncBailHook`, `AsyncSeriesHook`, `AsyncParallelHook` 같은 이름이 그대로 위 분류다. 플러그인은 `compiler.hooks.emit.tapAsync("MyPlugin", ...)`처럼 이름을 붙여 끼어든다. 이름을 붙이는 건 디버깅과 순서 조정을 위해서다.

폭포수형은 편하지만 위험하다. 이모지 플러그인과 "코드 블록 안은 건드리지 않는" 플러그인이 둘 다 렌더 훅에 있으면, 누가 먼저 도느냐에 따라 결과가 달라진다. 이걸 코어가 정하지 않으면 사용자가 플러그인 설치 순서로 버그를 고치게 된다. 그래서 많은 호스트가 단계(phase)를 나눈다. Vite와 Rollup 플러그인의 `enforce: "pre" | "post"`, PostCSS의 플러그인 배열 순서처럼 순서를 드러난 설정으로 만든다.

## 발견하고, 늦게 깨운다

코어가 플러그인을 어떻게 찾느냐도 설계다. 크게 세 가지다.

- 폴더나 패키지 이름 규칙: 예전 ESLint는 설정에 `"plugins": ["react"]`라고 쓰면 `eslint-plugin-react` 패키지를 찾아 불렀다
- 명시적 import: ESLint 9의 기본 설정 방식(flat config)은 `eslint.config.js`에서 플러그인 객체를 직접 import해서 넘긴다
- 매니페스트: VS Code 확장은 `package.json`의 `contributes`에 명령, 설정, 언어를 선언하고 `activationEvents`로 언제 깨울지 적는다

이름 규칙은 편하지만 "어느 node_modules에서 찾았나"가 흐려진다. ESLint가 flat config로 옮기면서 내세운 이유 중 하나가 이 해석 규칙의 혼란이었다. 명시적 import는 번들러와 타입 검사기가 플러그인을 보통 모듈처럼 다룰 수 있어 추적이 쉽다.

매니페스트 방식의 진짜 장점은 늦게 깨우기(lazy activation)다. 확장이 수십 개 깔린 에디터에서 시작할 때마다 모두의 코드를 실행하면 느리다. VS Code는 매니페스트만 읽어 메뉴와 명령 목록을 먼저 그리고, 사용자가 그 명령을 누르거나 해당 언어 파일을 열 때 확장 코드를 처음 불러온다. 아래 순서로 일어난다.

## 계약의 판을 어떻게 올리나

예제에서 `old-lint`는 API 1판을 기대했다. 코어가 2판으로 올리면서 `addLinter`를 없앴기 때문에 그대로 불렀다면 `TypeError`로 죽었을 것이다. 계약 판을 확인하는 이유가 이것이다.

실제 생태계는 판 번호 하나보다 정교하다. VS Code 확장은 `engines.vscode`에 `^1.90.0` 같은 범위를 적고, 마켓은 그보다 낮은 에디터에 그 판을 설치하지 않는다. npm 플러그인은 `peerDependencies`로 "나는 eslint 8 이상 9 이하와 맞는다"를 선언한다. peer로 적는 이유는 플러그인이 자기만의 eslint 사본을 갖는 게 아니라, 사용자 프로젝트에 깔린 바로 그 코어에 끼워져야 하기 때문이다. 플러그인이 코어를 일반 dependency로 들고 오면 코어가 두 벌 깔리고, `instanceof` 검사나 싱글턴 레지스트리가 서로 다른 사본을 보게 된다. 이건 [의존성 지옥](/posts/dependency-hell)에서 다룬 중복 설치 문제의 한 모습이다.

코어 쪽에서 계약을 오래 살리는 방법도 있다.

- 넓히기만 하고 좁히지 않는다. 새 메서드는 더하고, 있던 메서드는 지우지 않는다
- 지울 때는 한 판 동안 경고를 낸다. ESLint는 규칙 형식을 바꿀 때 예전 형식을 한동안 경고와 함께 받아 줬다
- 플러그인에 넘기는 객체를 좁게 유지한다. 코어 내부 객체를 통째로 넘기면 플러그인이 아무 필드나 만지기 시작하고, 그 필드가 사실상 공개 API가 된다

마지막 항목이 가장 중요하다. 내부를 그대로 노출한 플러그인 시스템은 코어를 리팩터링할 때마다 생태계가 깨진다. 예제에서 `hooks` 대신 `api`만 넘긴 건 이 때문이다.

## 플러그인이 다른 플러그인을 필요로 할 때

계약대로라면 플러그인은 서로 몰라야 한다. 현실에서는 그렇지 않다. Git 기록을 보여 주는 확장은 Git 확장이 이미 떠 있어야 하고, React 규칙 묶음은 TypeScript 파서 설정을 기대한다. VS Code는 매니페스트에 `extensionDependencies`를 적게 해서, 의존하는 확장을 먼저 깨운다.

이렇게 되면 코어가 로딩 순서를 계산해야 한다. 의존하는 쪽이 의존받는 쪽보다 뒤에 와야 하고, 서로가 서로를 요구하면 순서를 정할 수 없으니 거부해야 한다. 그래프에서 위상 정렬이라고 부르는 일이다. 아래에서 직접 짜 볼 수 있다. 규칙은 이렇다.

- 의존하는 플러그인보다 의존받는 플러그인이 먼저 온다
- 동시에 올릴 수 있는 것들은 이름 ABC 순으로 고른다(결과가 매번 같도록)
- 없는 플러그인에 의존하거나 순환이 있으면 `null`을 돌려준다

    }

두 번째 테스트를 보면 `prettier`가 `typescript`보다 먼저 온다. `eslint`가 올라간 순간 `prettier`가 준비되고, 이름순으로 `prettier`가 `typescript`보다 앞이기 때문이다. 순서가 결과에 영향을 주는 시스템이라면 이런 규칙까지 문서에 적어 둬야 한다.

순서 계산보다 더 큰 문제는 의존 자체가 계약을 우회한다는 점이다. 플러그인 B가 플러그인 A의 내부 함수를 직접 부르면, A의 작은 수정이 B를 깨뜨린다. 그래서 VS Code는 확장이 `activate`에서 돌려준 값만 다른 확장이 `getExtension(...).exports`로 받게 한다. A가 공개할 것을 스스로 정하는 작은 계약이다. 플러그인끼리 의존이 많아지기 시작하면 공통 부분을 코어의 확장점으로 올릴 때가 됐다는 신호이기도 하다.

## 느린 플러그인 하나가 전체를 멈춘다

처음의 증상으로 돌아가 보자. 플러그인이 코어와 같은 프로세스, 같은 스레드에서 돌면 플러그인의 무한 루프나 무거운 계산이 곧 코어의 정지다. 렌더 훅에서 400ms 동안 CPU를 쓰는 플러그인을 만들고, 10ms 뒤에 울려야 할 타이머를 같이 걸어 봤다.

```js
// slow-plugin.mjs: 렌더 훅 안에서 400ms 동안 CPU를 쓴다
export function render(text) {
  const end = Date.now() + 400;
  while (Date.now() < end) {}
  return text.toUpperCase();
}
```

```text
render: HELLO
timer(10ms) fired at 410ms
```

10ms짜리 타이머가 410ms에 울렸다. 그동안 코어는 키 입력도, 네트워크 응답도 처리하지 못했다. Node의 이벤트 루프가 한 스레드라 생기는 일이고, 그 원리는 [이벤트 루프](/posts/event-loop)에서 자세히 봤다.

같은 플러그인을 `worker_threads`의 워커에서 돌리고, 시간 제한을 넘기면 워커를 종료하게 바꿨다.

```js
import { Worker } from "node:worker_threads";

function callPlugin(file, input, timeoutMs) {
  return new Promise((resolve) => {
    const w = new Worker(new URL("./plugin-runner.mjs", import.meta.url), {
      workerData: { file, input },
      resourceLimits: { maxOldGenerationSizeMb: 64 }, // 메모리도 묶어 둔다
    });
    const timer = setTimeout(() => { w.terminate(); resolve({ ok: false, reason: `timeout ${timeoutMs}ms` }); }, timeoutMs);
    w.once("message", (out) => { clearTimeout(timer); w.terminate(); resolve({ ok: true, out }); });
    w.once("error", (e) => { clearTimeout(timer); resolve({ ok: false, reason: e.message }); });
  });
}
```

```text
timer(10ms) fired at 10ms
{ ok: true, out: 'HELLO' }
{ ok: false, reason: 'timeout 200ms' }
```

이제 타이머는 제시간에 울리고, 200ms 제한을 준 호출은 플러그인을 끊고 실패로 돌아온다. 코어는 멈추지 않았다.

격리는 공짜가 아니다. 같은 컨테이너(Node 22, 4코어)에서 쟀더니 같은 프로세스 안의 함수 호출은 한 번에 0.13us였고, 호출마다 워커를 새로 띄우면 중간값이 67ms였다. 워커 하나를 띄워 두고 메시지만 주고받으면 왕복 중간값이 24us로 줄었다. 그래서 실제 호스트는 플러그인용 프로세스나 워커를 오래 살려 두고 메시지로 대화한다. VS Code의 확장 호스트가 그런 구조다. 대신 넘기는 값은 복사 가능한 데이터여야 하고, 함수나 DOM 객체는 넘길 수 없다. 플러그인 API가 비동기 메시지 모양이 되는 이유가 여기 있다.

격리 수준은 신뢰의 정도에 따라 고른다.

| 격리 | 막아 주는 것 | 비용 | 쓰는 곳 |
|---|---|---|---|
| 같은 스레드 | 없음. 계약으로만 지킨다 | 가장 싸다 | ESLint 규칙, webpack 플러그인 |
| 워커 스레드 | 코어 멈춤, 메모리 폭주 일부 | 메시지 복사 | 무거운 변환 작업 |
| 별도 프로세스 | 크래시, 멈춤 | 프로세스 기동, IPC | VS Code 확장 호스트, 브라우저 확장 |
| 샌드박스(WASM, V8 isolate, 권한 제한) | 파일·네트워크 접근까지 | 제공하는 API만 쓸 수 있다 | Figma 플러그인, 엣지 함수, Envoy WASM 필터 |

워커나 프로세스로 떼어도 권한은 그대로다. 같은 사용자 권한으로 도는 확장 호스트는 홈 디렉터리 파일을 읽고 네트워크로 보낼 수 있다. 확장 마켓에서 악성 확장이 문제가 되는 이유다. 멈춤을 막는 격리와 권한을 막는 격리는 다른 문제이고, 후자는 샌드박스나 권한 모델이 필요하다.

## 운영체제의 마이크로커널과 같은 이름인 이유

이 구조의 이름은 운영체제에서 왔다. 마이크로커널 OS(MINIX 3, QNX, seL4 같은 L4 계열)는 커널에 프로세스 간 통신, 스케줄링, 주소 공간 관리처럼 꼭 필요한 것만 남기고, 파일 시스템과 장치 드라이버는 사용자 공간의 별도 프로세스로 뺀다. 드라이버가 죽어도 커널은 살아 있고, 드라이버를 다시 띄우면 된다.

반대편이 리눅스 같은 모놀리식 커널이다. 리눅스도 모듈을 실행 중에 넣고 뺄 수 있어서 플러그인처럼 보이지만, 모듈은 커널과 같은 주소 공간에서 돈다. 잘못된 드라이버 하나가 커널 전체를 멈출 수 있다. 앞의 표로 말하면 리눅스 모듈은 "같은 스레드" 칸이고, 마이크로커널의 드라이버는 "별도 프로세스" 칸이다.

그리고 OS에서 있었던 논쟁이 애플리케이션에서도 똑같이 반복된다. 마이크로커널은 경계를 넘을 때마다 메시지를 주고받아야 해서 느리다는 비판을 오래 받았다. 워커 왕복 24us와 함수 호출 0.13us의 차이가 바로 그 이야기다. 그래서 대부분의 애플리케이션 플러그인 시스템은 기본은 같은 프로세스로 두고, 믿을 수 없거나 멈추면 곤란한 것만 떼어 낸다.

## 레이어드, 헥사고날과 나란히 놓으면

세 구조 모두 코드를 나누지만, 나누는 기준이 다르다.

레이어드 아키텍처는 기술적 역할로 층을 쌓는다. 화면, 업무, 저장 순서로 위에서 아래로 부른다. 한 기능을 추가하면 보통 모든 층에 손을 댄다.

헥사고날 아키텍처는 업무 규칙과 바깥 기술 사이에 포트를 둔다. 결제사를 바꾸거나 DB를 바꿀 때 어댑터만 갈아 끼운다. 어댑터도 "꽂는다"는 점에서 플러그인과 닮았지만, 어댑터는 이미 정해진 역할(저장소, 결제)을 다른 기술로 구현하는 것이고 보통 하나만 고른다.

마이크로커널은 기능 자체를 꽂는다. 플러그인은 코어가 모르는 새 기능을 여러 개 동시에 더한다. 코어 개발자가 상상하지 못한 기능을 남이 만들게 하는 것이 목적이다.

그래서 셋은 함께 쓰인다. ESLint의 코어 내부를 레이어로 나눌 수도 있고, 코어가 파일 시스템 접근을 포트로 감쌀 수도 있다. 질문이 다를 뿐이다. 이런 축 나누기는 [아키텍처 패턴 지도](/posts/architecture-patterns-overview)에서 더 넓게 정리했다.

## 이 구조가 맞지 않는 곳

플러그인 시스템은 만드는 데도 유지하는 데도 비용이 든다. 공개 계약은 한 번 내보내면 거둬들이기 어렵고, 문서와 예제, 판 관리가 따라와야 한다. 다음 조건이 아니면 보통 과하다.

- 코어를 만드는 팀 바깥에서 확장을 만들 사람이 있다(사용자, 다른 팀, 고객사)
- 고객마다 다른 규칙이 붙는 제품이다. 보험료 계산, 세금 규칙, 결제 수단처럼 지역·고객별로 갈리는 로직
- 기능을 켜고 끄는 단위가 배포 단위보다 작아야 한다

사내 서비스 하나에 "나중에 확장할지도 모르니" 플러그인 레지스트리를 만들면, 플러그인은 하나뿐이고 간접 호출만 늘어난다. 확장점이 두 번째로 필요해질 때 만들어도 늦지 않다.

흔한 실수도 정리해 둔다. 코어 내부 객체를 그대로 넘겨 리팩터링을 막는다. 훅 순서를 정하지 않아 설치 순서가 결과를 바꾼다. 활성화 실패 때 등록한 것을 걷어 내지 않는다. 같은 스레드에서 돌리면서 시간 제한이 없다. 플러그인이 코어를 일반 dependency로 들고 와 코어가 두 벌 깔린다.

## 마무리

마이크로커널 아키텍처는 오래 안 바뀌는 작은 코어와, 그 코어가 열어 둔 확장점에 꽂히는 플러그인으로 나누는 구조다. 설계의 중심은 플러그인에 넘기는 계약이다. 무엇을 공개하고 어떻게 판을 올릴지, 훅을 어떤 순서로 부를지, 플러그인을 언제 깨우고 얼마나 떼어 놓을지가 결정할 일이다. 격리를 늘릴수록 안전해지지만 경계를 넘는 비용이 붙는다는 점은 OS의 마이크로커널 논쟁과 똑같다.

## 면접에서 나올 만한 질문

### 마이크로커널(플러그인) 아키텍처를 설명해 달라

작은 코어 시스템과, 코어가 정한 계약에 맞춰 기능을 더하는 플러그인으로 나누는 구조다. 코어는 공통 실행 틀, 레지스트리, 훅만 갖고 기능 대부분은 플러그인이 맡는다. 코어는 드물게 바뀌고 플러그인은 자주 바뀌니, 둘을 떼어 서로의 릴리스를 기다리지 않게 하는 게 목적이다. VS Code, ESLint, webpack이 대표적이다.

### 플러그인 API를 설계할 때 가장 신경 쓸 점은

플러그인에 넘기는 객체를 좁게 유지하는 것이다. 코어 내부를 그대로 넘기면 플러그인이 아무 필드나 쓰기 시작하고, 그게 사실상 공개 API가 되어 코어를 고칠 수 없게 된다. 넓히기만 하고 지울 때는 경고 기간을 두며, 판 범위를 매니페스트나 peerDependencies로 선언하게 한다. 활성화 실패나 비활성화 때 등록한 것을 한꺼번에 걷어 낼 수 있게 해제 함수를 모으는 장치도 필요하다.

### 느린 플러그인이 전체를 멈추게 하는 문제는 어떻게 막나

같은 스레드에서 돌면 막을 방법이 시간 측정과 경고 정도뿐이다. 멈추면 곤란한 플러그인은 워커나 별도 프로세스로 떼고, 시간 제한을 넘기면 종료한다. 이때 호출마다 새로 띄우면 기동 비용이 크니 오래 사는 호스트 프로세스를 두고 메시지로 주고받는다. VS Code가 확장을 확장 호스트라는 별도 프로세스에서 돌리는 이유가 이것이다.

### 플러그인끼리 의존이 생기면 어떻게 하나

매니페스트에 의존을 선언하게 하고, 코어가 위상 정렬로 로딩 순서를 정한다. 순환이나 없는 의존은 로딩 전에 거부한다. 의존하는 쪽은 상대의 내부가 아니라 상대가 공개한 값만 쓰게 해야 한다. 의존이 많아지면 그 공통 기능을 코어의 확장점으로 올릴 신호로 본다.

### 플러그인이 코어 패키지를 peerDependencies로 두는 이유는

플러그인은 사용자 프로젝트에 깔린 바로 그 코어에 끼워져야 하기 때문이다. 일반 dependency로 두면 코어 사본이 하나 더 깔릴 수 있고, 그러면 레지스트리나 `instanceof` 검사가 서로 다른 사본을 보게 된다. peer로 두면 "이 범위의 코어와 맞는다"는 선언만 하고 실제 코어는 사용자 쪽 것을 쓴다.

### OS의 마이크로커널과 애플리케이션의 마이크로커널 아키텍처는 무슨 관계인가

이름과 생각이 같다. OS 마이크로커널은 IPC, 스케줄링, 메모리 관리만 커널에 두고 드라이버와 파일 시스템을 사용자 공간 프로세스로 뺀다. 리눅스 모듈은 실행 중 꽂을 수 있지만 커널과 같은 주소 공간에서 돌아 격리가 없다. 경계를 넘는 메시지 비용과 격리의 안전성 사이의 트레이드오프가 애플리케이션 플러그인에서도 그대로 나타난다.

### 헥사고날 아키텍처의 어댑터와 플러그인은 무엇이 다른가

어댑터는 코어가 이미 정한 역할(저장소, 결제)을 특정 기술로 구현하고 보통 하나를 골라 조립한다. 플러그인은 코어가 모르는 새 기능을 여러 개 동시에 더하고, 코어 팀 바깥 사람이 만드는 경우가 많다. 레이어드는 기술 역할로 층을 쌓는 것이라 질문 자체가 다르다. 셋은 배타적이지 않아 한 시스템에서 함께 쓴다.
