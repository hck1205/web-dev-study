<EasyIntro>
  서버가 한 대라면 10초마다 컴퓨터가 얼마나 바쁜지 적어 두는 작은 프로그램 하나로 충분하다. 그런데 서버가 1만 대가 되면 프로그램을 일일이 깔기도 힘들고, 숫자를 한곳에 모으는 쪽 한 대가 그 많은 숫자를 다 받지 못한다.

  숫자를 모으는 방법은 두 가지다. 모으는 쪽이 서버마다 찾아가 읽어 오거나, 서버가 알아서 보내 온다. 찾아가는 방식은 서버 목록을 들고 있는 곳에 물어 갈 곳을 정하고, 모으는 쪽을 여러 대로 늘려 서버를 나눠 맡긴다. 모은 숫자는 바로 저장하지 않고 줄 서서 기다리는 대기열에 먼저 넣어서, 저장소가 잠깐 멈춰도 숫자를 잃지 않게 한다.

  이 시스템은 숫자 몇 개쯤 빠져도 그래프에 작은 틈이 생길 뿐이라 큰일이 아니다. 다만 몇 분치가 통째로 사라지면 알림이 울리지 않으니 그건 막아야 한다.
</EasyIntro>

이 시리즈에서 이 글의 자리: 앞 글은 [㊶ 복제와 acks](/posts/sd-mq-replication)로, 분산 메시지 큐 장을 마쳤다. 이 글부터 두 편에 걸쳐 지표 모니터링 시스템을 설계한다. 이 글은 수만 대의 서버에서 숫자를 어떻게 모아 저장소 앞까지 가져오는지 정한다. 다음 글 [㊸ 저장과 다운샘플링, 알림](/posts/sd-metrics-storage-alerting)이 그 숫자를 쌓고 묻고 울리는 쪽을 맡는다. 그 뒤에는 [㊹ 광고 클릭 집계 ①](/posts/sd-ad-click-stream-windows)으로 넘어간다.

서버가 한 대일 때 "CPU가 얼마나 바쁜가"를 지켜보는 건 쉽다. 10초마다 `/proc/loadavg`를 읽어 파일 끝에 한 줄 적는 셸 스크립트 하나면 된다. 그래프가 필요하면 그 파일을 열어 그리면 된다. 서버가 열 대가 되면 스크립트를 열 군데에 깔고, 파일을 한곳으로 모으는 일이 생긴다. 이 글은 서버가 1만 대, 시계열이 1,000만 개가 될 때까지 이 수집 쪽이 어떻게 자라야 하는지 따라간다.

면접에서는 "지표 모니터링과 알림 시스템을 설계하라"는 문제로 나온다. 지표의 종류(카운터, 게이지, 히스토그램)는 [지표 타입](/posts/metrics-types)에, 무엇을 잴지는 [모니터링 기본](/posts/monitoring-basics)에, Prometheus 한 대의 내부는 [Prometheus 내부 구조](/posts/prometheus-basics)에 정리해 뒀다. 여기서는 그 위에서 "이걸 회사 전체 규모로 직접 만든다면"을 묻는다.

## 서버 한 대를 지켜볼 때는 스크립트 하나면 된다

가장 작은 버전부터 보자. 서버 한 대, 스크립트 하나, 파일 하나다.

```bash
# loadavg.sh: 10초마다 1분 평균 부하를 한 줄씩 남긴다
while true; do
  echo "$(date +%s) $(cut -d' ' -f1 /proc/loadavg)" >> /var/log/loadavg.log
  sleep 10
done
```

이 구조에는 지표 모니터링 시스템의 부품이 이미 다 들어 있다. `/proc/loadavg`가 숫자가 나오는 곳(출처)이고, 스크립트가 숫자를 집어 오는 수집기, 파일이 저장소다. 파일을 열어 눈으로 보는 게 시각화이고, "부하가 4를 넘으면 메일을 보내라"는 한 줄을 더하면 알림이 된다.

서버가 1만 대가 되면 무엇부터 깨질까. 순서대로 적어 보면 이렇다.

- 1만 대에 스크립트를 깔고 고치는 일 자체가 일이다. 새 서버가 생기고 없어질 때마다 목록을 손으로 고칠 수는 없다.
- 1만 개의 파일을 한곳으로 모아야 "전체 웹 서버의 평균 부하" 같은 질문에 답할 수 있다.
- 모으는 쪽 한 대가 1만 대의 숫자를 다 받지 못한다.
- 저장소가 잠깐 멈추면 그동안의 숫자가 사라진다.

이 글은 이 넷을 하나씩 푼다. 그 전에 얼마나 큰 걸 만드는지부터 정한다.

## 무엇을 모으고 무엇은 안 모으나

면접관과 범위를 먼저 좁힌다. 이 문제에서 흔히 합의하는 범위는 이렇다.

- 회사 안에서 쓰는 시스템이다. 남에게 파는 SaaS가 아니다.
- 모으는 건 운영 지표다. CPU, 메모리, 디스크, 초당 요청 수, 큐에 쌓인 메시지 수 같은 것. 매출 같은 비즈니스 지표는 뺀다.
- 로그 수집과 분산 추적은 범위 밖이다. 로그는 [구조화 로그](/posts/structured-logging)가 다루는 다른 문제이고, 요청 하나를 따라가는 건 [분산 추적](/posts/distributed-tracing)이다.
- 1년 보관한다. 최근 7일은 원본 해상도, 그 뒤 30일은 1분 단위, 그 뒤는 1시간 단위로 줄여도 된다.
- 알림은 메일, 전화, PagerDuty 같은 호출 서비스, 웹훅으로 보낸다.

규모는 서버 풀 1,000개에 풀마다 100대, 서버마다 지표 100개로 잡는다. 곱하면 시계열이 1,000만 개다. 시계열(time series)은 "web-17 서버의 CPU 부하"처럼 이름과 라벨이 정해진 한 줄의 숫자 흐름을 말한다. 10초마다 한 점씩 찍는다면 초당 100만 점이 들어온다.

점 하나를 압축 없이 저장하면 시각 8바이트, 값 8바이트로 16바이트다. 하루면 얼마일까. 아래 함수를 채워서 직접 계산해 보자.

## 점 하나에 담기는 것

1,000만 개의 시계열을 서로 구분하려면 점마다 "누구의 무엇인지"가 붙어야 한다. 흔히 쓰는 모양은 지표 이름, 라벨 묶음, 값, 시각이다. Prometheus의 텍스트 형식이나 InfluxDB의 줄 프로토콜이 모두 이 네 조각을 한 줄에 담는다. 구두점만 조금 다르다. Prometheus 형식으로 쓰면 `cpu_load{host="web-17",region="ap-ne-2"} 0.62 1792483200000`이다(시각은 밀리초). 아래 그림은 같은 줄을 조각이 잘 보이게 띄어 쓴 것이다. 조각별로 눌러 보자.

라벨은 질문을 쉽게 만든다. "ap-ne-2 지역 웹 서버의 지난 10분 평균 부하"는 `region=ap-ne-2`인 시계열을 모두 골라 지난 10분 값을 평균 내면 된다. 대신 라벨 값의 가짓수가 그대로 시계열 수가 된다. 라벨에 사용자 ID나 요청 ID를 넣으면 시계열이 순식간에 수백만 개로 불어난다. 이 함정은 [지표 타입](/posts/metrics-types)의 실험에서 숫자로 확인했다. 설계 면접에서는 "라벨에는 값의 가짓수가 작은 것만 넣는다"는 한 줄을 꼭 말한다.

이 데이터는 성질이 독특하다. 쓰기는 쉬지 않고 쏟아지는데, 읽기는 평소엔 적다가 장애가 나면 한꺼번에 몰린다. 그래서 일반 관계형 DB보다 시계열에 맞춘 저장소를 고른다. 저장소 이야기는 다음 글에서 한다.

## 다섯 부품으로 나눠 그린다

스크립트 하나에 뭉쳐 있던 일을 다섯으로 나눈다. 출처에서 숫자를 집는 수집, 수집한 것을 저장소까지 나르는 전송, 쌓아 두는 저장, 규칙을 보고 사람을 부르는 알림, 그래프로 보여 주는 시각화다. 전체 모양은 이렇다.

이 시스템에 고유한 성질이 하나 있다. 숫자 몇 개쯤 잃어도 큰일이 아니다. 10초마다 찍히는 CPU 부하에서 한 점이 빠지면 그래프에 작은 틈이 생길 뿐이다. 결제와 다르게 "보내고 잊기"가 허용된다. 이 여유가 뒤에서 UDP를 쓸지, 큐를 둘지 같은 선택을 가볍게 만든다. 다만 알림이 의존하는 숫자가 통째로 사라지는 건 안 된다. 잃어도 되는 건 점 몇 개지, 몇 분이 아니다.

## 가지러 가거나, 보내 오거나

수집 방식은 둘이다. 수집기가 각 서버의 `/metrics` 주소로 가서 읽어 오는 pull, 서버 옆의 에이전트가 수집기로 보내는 push다. Prometheus가 pull, Graphite나 CloudWatch가 push를 쓴다. pull이 대상의 생사를 공짜로 알려 주는 `up` 지표와, 짧게 사는 작업을 위한 Pushgateway는 [모니터링 기본](/posts/monitoring-basics)에서 실제로 돌려 봤다. 여기서는 두 방식이 설계에서 어떻게 다르게 깨지는지에 집중한다.

같은 앱 세 대를 두 방식으로 모아 보는 Node 22 스크립트를 짰다. 앱은 0.1초마다 요청 7개를 받았다고 세고, `/metrics`에 지금까지 센 값을 적는다. pull 수집기는 0.5초마다 읽으러 가고, 두 번째 바퀴 전에 web-3가 죽는다. 그사이 0.2초만 살다 끝나는 배치 작업도 하나 떴다 사라진다.

```js
// pull-push.js 일부: pull 수집기는 목록을 돌며 읽어 온다
function scrape(target) {
  return new Promise((resolve) => {
    const req = http.get({ host: "127.0.0.1", port: target.port, path: "/metrics", timeout: 200 }, (res) => {
      let body = ""; res.on("data", (c) => (body += c)); res.on("end", () => resolve({ ok: true, body: body.trim() }));
    });
    req.on("timeout", () => req.destroy(new Error("timeout")));
    req.on("error", (e) => resolve({ ok: false, err: e.code || e.message }));
  });
}
// push 쪽: 에이전트는 UDP로 한 줄을 던지고 끝이다
const send = (line) => new Promise((r) => agent.send(line, cport, "127.0.0.1", (err) => r(err ? err.code : "sent")));
```


출력에서 볼 곳이 셋이다. pull에서 web-3가 죽자 바로 다음 바퀴에 `up=0`이 찍혔다. 수집기가 직접 가서 실패했으니 "대상이 죽었다"는 사실을 수집기가 안다. 반면 배치 작업은 두 바퀴 사이에 떴다 사라져서 pull은 그 숫자를 한 번도 보지 못했다. push에서는 배치 작업이 끝나기 직전에 보낸 한 줄이 그대로 도착했다.

세 번째가 가장 중요하다. push 수집기를 내린 뒤 다섯 번 보냈는데 다섯 번 모두 `sent`였다. UDP는 받는 쪽이 있는지 확인하지 않는다. 보내는 쪽은 숫자가 버려진 걸 모른다. push 방식에서 수집기가 조용하다면 그게 "서버가 죽어서"인지 "네트워크가 막혀서"인지 "할 일이 없어서"인지 수집기만 봐서는 구분이 안 된다. 그래서 push 시스템은 "이 서버에서 마지막으로 숫자가 온 시각"을 따로 지켜보는 장치를 둔다.

## 수집 목록은 서비스 디스커버리가 들고 있다

## 수집기 한 대가 다 못 읽는다

초당 100만 점을 수집기 한 대가 다 읽을 수는 없다. 여러 대로 나눠야 한다. 그런데 그냥 여러 대를 띄우면 같은 서버를 두 수집기가 읽어 점이 두 번 들어간다. 대상마다 담당 수집기를 하나씩 정해야 한다.

가장 쉬운 규칙은 `hash(대상 주소) % 수집기 수`다. 문제는 수집기 수가 바뀔 때다. 3대에서 4대로 늘리면 나머지가 거의 다 바뀐다. 담당이 바뀐 대상은 새 수집기가 처음 읽기 시작할 때까지 틈이 생기고, 카운터의 변화율을 계산하던 상태도 처음부터 다시 쌓아야 한다. 대상 1만 개로 직접 세 봤다.

```js
// shard.js 일부: 대상 1만 개, 수집기 3대 -> 4대
const byMod = (n) => (t) => `c${h32(t) % n}`;
function ring(collectors) {                 // 수집기마다 가상 노드 100개를 링에 놓는다
  const points = [];
  for (const c of collectors) for (let v = 0; v < 100; v++) points.push([h32(`${c}#${v}`), c]);
  points.sort((a, b) => a[0] - b[0]);
  return (t) => { /* 대상 해시보다 크거나 같은 첫 점의 주인을 이분 탐색으로 찾는다 */ };
}
```

```text
== 수집기 3대 -> 4대
mod N          moved  7534 / 10000 (75.3%)  load after: c0=2577 c1=2497 c2=2478 c3=2448
hash ring      moved  2431 / 10000 (24.3%)  load after: c0=2705 c1=2381 c2=2483 c3=2431
```

나머지 방식은 75%가 담당이 바뀌었다. [안정 해시](/posts/consistent-hashing)의 링을 쓰면 24%만 옮겨 간다. 새 수집기 c3가 가져가야 하는 몫이 4분의 1이니, 꼭 옮겨야 하는 것만 옮긴 셈이다. 가상 노드 덕분에 넷의 부하도 2,381~2,705로 고르다. 아래 그림은 수집기가 늘 때 어떤 대상만 자리를 옮기는지 보여 준다.

## push는 수집기를 로드 밸런서 뒤에 둔다

push에서는 문제가 거꾸로다. 누가 누구를 읽을지 정할 필요가 없다. 에이전트가 알아서 보낸다. 대신 1만 대가 한꺼번에 보내는 양을 받아 내야 한다. 그래서 수집기를 [로드 밸런서](/posts/load-balancer-basics) 뒤의 오토스케일링 그룹으로 둔다. 수집기는 상태가 없으니 몇 대든 늘릴 수 있다.

에이전트를 서버마다 두면 좋은 점이 하나 더 있다. 보내기 전에 미리 합칠 수 있다. 요청 하나마다 "1"을 보내는 대신, 에이전트가 10초 동안 세어 합계 하나만 보낸다. 서버가 초당 200건을 받는다면 보내는 줄이 10초에 2,000개에서 1개로 준다. 쿠버네티스에서는 이런 에이전트를 노드마다 하나씩 띄우는 [DaemonSet](/posts/k8s-daemonset)으로 돌린다.

UDP로 보내면 연결을 맺지 않아 가볍다. 대신 앞에서 본 것처럼 잃어도 모른다. 받는 쪽이 잠깐 바쁘기만 해도 버려진다. 받기 버퍼를 64KB로 잡은 수집기가 1초 동안 다른 일로 바쁜 사이에 에이전트가 2,000줄을 보내 봤다. 리눅스 커널의 UDP 카운터는 `nstat`으로 본다.

```bash
# 카운터 기준점을 잡고, 실험을 돌리고, 그사이 늘어난 UDP 카운터만 본다
nstat -n
node udp-drop.js
nstat 'Udp*'
```

```text
send callbacks: ok=2000 error=0
collector received=157
#kernel
UdpInDatagrams                  157                0.0
UdpInErrors                     1843               0.0
UdpOutDatagrams                 2000               0.0
UdpRcvbufErrors                 1843               0.0
```

보내는 쪽 콜백은 2,000번 모두 성공했다. 수집기가 받은 건 157줄뿐이다. 나머지 1,843줄은 `UdpRcvbufErrors`, 즉 받기 버퍼가 꽉 차서 커널이 버린 개수로 잡혔다. push 수집기의 그래프가 이유 없이 듬성듬성하다면 수집기 서버에서 이 카운터부터 본다. 늘고 있다면 받기 버퍼(`net.core.rmem_max`와 소켓의 버퍼 크기)를 키우거나, 수집기를 늘리거나, TCP로 바꾼다. TCP와 UDP의 차이 자체는 [UDP와 QUIC](/posts/udp-and-quic)에 있다.

push에는 보안 문제도 하나 붙는다. 아무나 수집기에 숫자를 보낼 수 있다. 잘못 설정된 테스트 서버가 운영 지표 이름으로 숫자를 보내면 대시보드가 오염된다. 허용 목록이나 인증 토큰으로 받을 출처를 제한한다. pull은 수집기가 고른 주소만 읽으니 이 문제가 적다.

## 둘 중 하나를 고르는 기준

여기까지의 차이를 한자리에 모으면 이렇다. 정답은 없고, 큰 조직은 보통 둘 다 쓴다.

| 따질 것 | pull | push |
|---|---|---|
| 대상이 죽었나 | 읽으러 가서 실패하면 바로 안다 | 조용하면 이유를 구분하기 어렵다 |
| 몇 초만 사는 작업 | 읽기 전에 끝나면 놓친다 (Pushgateway로 보완) | 끝나기 전에 보내면 된다 |
| 방화벽, 다른 데이터 센터 | 수집기가 모든 대상에 닿아야 한다 | 대상이 수집기 주소 하나에만 닿으면 된다 |
| 디버깅 | 노트북에서 `curl /metrics`로 바로 본다 | 에이전트와 네트워크를 함께 의심해야 한다 |
| 가짜 숫자 | 정해진 주소만 읽어서 적다 | 받을 출처를 인증해야 한다 |
| 늘리는 법 | 대상을 수집기에 나눠 배정한다 | 로드 밸런서 뒤에 수집기를 늘린다 |

설계 면접에서는 표를 외우기보다 이 시스템에 무엇이 많은지로 고른다. 오래 사는 서버가 대부분이고 같은 네트워크 안에 있다면 pull이 편하다. 서버리스 함수나 짧은 배치 작업이 많고, 모니터링 대상이 여러 데이터 센터나 고객 네트워크에 흩어져 있다면 push가 편하다. 에이전트를 깔 수 없는 장비(네트워크 스위치, 매니지드 DB)는 바깥에서 읽어 오는 수밖에 없다.

## 저장소가 멈추면 수집한 것도 사라진다

이제 수집기가 모은 점을 저장소로 보낸다. 수집기가 시계열 DB에 바로 쓰면 구조는 단순하다. 그런데 DB가 30초 멈추면 그 30초의 점은 갈 곳이 없다. 수집기 메모리에 쌓아 두면 수집기가 터진다.

그래서 수집기와 DB 사이에 [Kafka](/posts/kafka-basics) 같은 큐를 둔다. 수집기는 큐에 쓰고, 소비자가 큐에서 꺼내 DB에 쓴다. DB가 멈춰도 큐에는 계속 쌓이고, DB가 돌아오면 소비자가 밀린 걸 따라잡는다. 얼마나 걸리는지 숫자로 보자. 초당 1,000점이 들어오고, 소비자는 초당 1,500점까지 쓸 수 있으며, DB가 10초부터 40초까지 멈춘다고 했다.

```text
t=  9s backlog=0
t= 10s backlog=1000
t= 39s backlog=30000
t= 40s backlog=29500
t= 60s backlog=19500
t= 99s backlog=0
t=100s backlog=0
direct write lost: 30000
queue lost: 0, peak backlog: 30000, caught up at t=99s
```

바로 쓰면 3만 점을 잃는다. 큐를 두면 잃지 않지만, 따라잡는 데 DB가 돌아온 뒤로 약 1분이 더 걸렸다. 소비자의 여유가 초당 500점뿐이라 3만 점을 비우는 데 60초가 든다. 이 1분 동안 대시보드와 알림은 늦은 숫자를 본다. 소비자 처리량을 평소의 1.5배로만 잡으면 복구가 느리다는 뜻이다. 장애 뒤 따라잡는 시간을 줄이려면 소비자를 넉넉히 둔다. 큐에 남은 양(컨슈머 랙)을 지켜보는 법은 [Kafka 기초](/posts/kafka-basics)에 있다.

  ]}
/>

큐는 공짜가 아니다. Kafka 클러스터를 하나 더 운영해야 한다. 이 부담 때문에 큐 없이 수집기가 원격 저장소로 직접 보내되, 보내지 못한 것을 수집기 디스크에 잠시 쌓아 두는 방식도 많이 쓴다. Prometheus의 `remote_write`가 이런 식으로 WAL을 읽으며 재시도한다. Facebook의 Gorilla처럼 처음부터 메모리에 받도록 만든 대규모 저장소를 쓰는 길도 있다. 면접에서는 "큐를 두면 잃지 않지만 운영할 것이 하나 늘어난다"는 맞바꿈을 말하면 된다.

## 파티션 키를 이름으로만 고르면

큐를 Kafka로 정했다면 어떤 점을 어느 파티션에 넣을지 정해야 한다. 같은 지표 이름을 한 파티션에 모으면 소비자가 이름별로 합치기 편하다. 그런데 지표 이름마다 시계열 수가 크게 다르다. 대상 1만 대에서 지표 네 가지가 내는 점을 파티션 12개에 나눠 봤다. CPU는 코어마다 하나씩 8개, 응답 시간 히스토그램은 경로 5개 × 칸 12개로 60개의 시계열을 대상마다 낸다.

```text
== 1만 대가 10초마다 보내는 샘플을 파티션 12개에 나누기
key = name           max 600000 min 0 empty 8
key = name + labels  max 59738 min 58729 empty 0
```

이름만 키로 쓰면 이름이 넷이라 파티션 12개 중 8개가 비고, 히스토그램이 들어간 파티션 하나에 60만 점이 몰린다. 소비자를 아무리 늘려도 그 파티션 하나를 맡은 소비자가 병목이다. 이름과 라벨을 함께 해시하면 12개가 5만 9천 개 안팎으로 고르게 나뉜다. 대신 같은 이름의 점이 여러 파티션에 흩어지니, 이름별 합계가 필요하면 저장소나 조회 쪽에서 합친다. 몰리는 시계열이 특정 이름에 있다는 걸 알면 그 이름만 라벨까지 넣어 나누는 절충도 있다. 같은 문제를 키-값 저장소 쪽에서 본 이야기는 [⑧ 샤딩](/posts/sd-sharding-intro)의 핫스팟이다.

## 어디서 미리 합칠까

마지막으로 합치기다. 1,000만 개의 원본을 다 저장할지, 어딘가에서 미리 합쳐 줄일지 정해야 한다. 합칠 수 있는 곳은 세 군데다.

에이전트에서 합치면 보내는 양이 가장 크게 준다. 대신 서버 한 대 안에서 할 수 있는 단순한 것만 된다. "10초 동안 센 요청 수" 정도다. 여러 서버를 합친 평균은 에이전트가 알 수 없다.

큐 뒤의 스트림 처리(Flink 같은 엔진)에서 합치면 여러 서버를 묶은 합계를 만들어 저장할 수 있다. 쓰기 양이 크게 준다. 대신 원본을 버리면 나중에 다른 방식으로 묶어 볼 수 없다. "지역별로 합쳐 뒀는데 이제 서버별로 보고 싶다"는 요구가 오면 답이 없다.

조회할 때 합치면 원본을 다 갖고 있으니 어떤 질문에도 답한다. 대신 질문할 때마다 많은 점을 읽어야 해서 느리다. 대시보드가 30개 패널을 띄울 때마다 수백만 점을 합치면 장애 중에 대시보드가 멈춘다.

실제로는 섞는다. 에이전트에서는 카운터를 가볍게 합치고, 원본은 짧게 보관하며, 자주 묻는 합계는 미리 계산해 둔다. 미리 계산하는 방법과 오래된 데이터를 줄이는 방법은 [다음 글](/posts/sd-metrics-storage-alerting)의 몫이다.

## 현장에서 수집이 새는 자리

그래프에 틈이 생겼다는 문의가 오면 수집 경로를 앞에서부터 하나씩 본다.

pull이라면 먼저 그 대상의 `up`이 0이었는지 본다. 0이면 대상이 죽었거나 수집기가 닿지 못한 것이다. 1인데 점이 빠졌다면 읽는 데 걸린 시간을 본다. Prometheus는 대상마다 `scrape_duration_seconds`를 남긴다. 이 값이 타임아웃 근처라면 `/metrics`가 너무 커졌거나 앱이 느린 것이다. 라벨을 잘못 넣어 응답이 수십 MB가 된 경우가 흔하다.

push라면 수집기 서버의 UDP 카운터를 본다. 앞에서처럼 `UdpRcvbufErrors`가 늘고 있으면 받는 쪽이 못 따라오는 것이다. 에이전트 쪽에서는 보낸 줄 수를 세는 지표를 에이전트 스스로 내게 해 두면 "보냈는데 안 왔다"와 "아예 안 보냈다"를 가를 수 있다.

큐를 두었다면 소비자 랙을 본다. 랙이 계속 늘면 소비자가 DB에 쓰는 속도가 들어오는 속도를 못 따라오는 것이다. 그래프의 최근 몇 분이 비어 있고 조금 지나면 채워진다면 데이터를 잃은 게 아니라 늦게 도착하는 중이다.

흔한 실수 하나를 더 적어 둔다. 수집기 인스턴스를 늘렸는데 대상 배정을 바꾸지 않으면 모든 수집기가 같은 대상을 읽는다. 점이 두세 배로 들어가고, 합계 지표가 두세 배로 부풀어 보인다. 수집기를 늘릴 때는 담당 나누기를 함께 바꾼다.

## 다음에 읽을 글

수집 쪽은 서비스 디스커버리로 목록을 받고, 대상을 링으로 수집기에 나누거나 push 수집기를 로드 밸런서 뒤에 늘리는 것으로 자랐다. 저장소가 멈춰도 잃지 않게 큐를 두었고, 큐의 파티션 키는 라벨까지 넣어 고르게 나눴다. 잃어도 되는 건 점 몇 개뿐이라는 성질이 이 모든 선택을 가볍게 했다.

다음 글 [㊸ 저장과 다운샘플링, 알림](/posts/sd-metrics-storage-alerting)은 큐 뒤쪽을 맡는다. 1년치를 어떻게 줄여 담는지, 조회 서비스가 어느 해상도를 읽을지 어떻게 고르는지, 알림이 두 번 울리지도 빠지지도 않게 하는 법을 다룬다. 지표 하나하나의 의미가 궁금하면 [지표 타입](/posts/metrics-types)을 먼저 읽어도 좋다.

## 면접에서 나올 만한 질문

### pull과 push 중 무엇을 고르겠나요?

정답은 없고, 대상의 성격으로 고른다. 오래 사는 서버가 한 네트워크 안에 있으면 pull이 대상의 생사를 바로 알려 주고 디버깅도 쉽다. 짧게 사는 작업이 많거나 대상이 여러 네트워크에 흩어져 있으면 push가 편하다. 큰 조직은 보통 둘 다 쓰고, pull 쪽의 짧은 작업은 Pushgateway로 보완한다.

### pull 방식에서 수집기 한 대가 1만 대를 못 읽으면 어떻게 하나요?

수집기를 여러 대 두고 대상마다 담당 수집기를 하나 정한다. 나머지 연산으로 나누면 수집기 수가 바뀔 때 대부분의 담당이 바뀌니 안정 해시 링을 쓴다. 대상 1만 개를 3대에서 4대로 늘렸을 때 나머지 방식은 75%가, 링은 24%가 옮겨 갔다. 대상 목록은 서비스 디스커버리에서 받는다.

### 수집기 한 대가 죽으면 어떻게 되나요?

링에서 그 수집기의 몫이 다음 수집기로 넘어가고, 넘어가는 동안 한두 바퀴의 점이 빠진다. 지표는 점 몇 개를 잃어도 되는 데이터라 대개 이 정도는 받아들인다. 알림이 걸린 중요한 대상은 수집기 두 대가 같이 읽게 하고 저장할 때 중복을 하나로 줄이는 식으로 이중화한다.

### 시계열 DB가 30초 멈추면 그동안의 지표는요?

수집기가 DB에 바로 쓰면 그 30초가 사라진다. 수집기와 DB 사이에 Kafka 같은 큐를 두면 큐에 쌓였다가 DB가 돌아온 뒤 소비자가 따라잡는다. 소비자의 여유 처리량이 작으면 따라잡는 시간이 길어지니 넉넉히 둔다. 큐 운영 부담이 싫으면 수집기가 디스크에 잠시 쌓아 두고 재시도하는 방식도 쓴다.

### 트래픽이 10배가 되면 어디가 먼저 막히나요?

수집 쪽에서는 수집기 처리량, 큐 파티션, 소비자의 DB 쓰기 속도 순으로 본다. 수집기는 상태가 없어 늘리기 쉽지만 파티션 수는 나중에 바꾸기 어려우니 미리 넉넉히 만든다. 파티션 키를 지표 이름만으로 잡았다면 히스토그램 같은 큰 지표가 한 파티션에 몰려 먼저 막힌다. 근본적으로는 에이전트에서 미리 합쳐 들어오는 양을 줄인다.

### push 방식에서 UDP를 쓰면 어떤 위험이 있나요?

받는 쪽이 없거나 바빠도 보내는 쪽은 성공으로 안다. 실험에서 2,000줄을 보냈는데 157줄만 도착했고, 나머지는 수집기 커널의 받기 버퍼 오류로 버려졌다. 그래서 수집기의 UdpRcvbufErrors를 지켜보고, 받기 버퍼를 키우거나 수집기를 늘리고, 잃으면 안 되는 지표는 TCP로 보낸다.

### 지표를 어디서 미리 합치나요?

에이전트, 스트림 처리, 조회 시점 세 곳이 있다. 에이전트는 양을 크게 줄이지만 서버 하나 안의 단순한 합계만 된다. 스트림 처리에서 합치면 쓰기가 줄지만 원본을 버리면 다른 방식으로 다시 묶을 수 없다. 조회 시점에 합치면 유연하지만 느려서, 보통은 원본을 짧게 두고 자주 묻는 합계를 미리 만들어 둔다.

### 라벨에 사용자 ID를 넣으면 왜 안 되나요?

라벨 값의 가짓수만큼 시계열이 곱으로 늘어난다. 사용자가 100만 명이면 지표 하나가 시계열 100만 개가 되고, 저장소의 색인과 메모리가 버티지 못한다. 수집 쪽에서는 `/metrics` 응답이 커져 수집 시간이 타임아웃을 넘긴다. 사용자별로 봐야 하는 정보는 로그나 추적으로 남긴다.
