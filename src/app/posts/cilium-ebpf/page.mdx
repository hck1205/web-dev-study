Cilium으로 바꾼 클러스터의 노드에서 습관처럼 `iptables-save | grep KUBE-SVC`를 쳤다. 아무것도 안 나온다. kube-proxy Pod도 없다. 그런데 Service는 잘 된다. ClusterIP로 보낸 요청이 Pod에 닿으려면 어디선가 주소가 바뀌어야 하는데, 그 일을 하는 규칙이 보이지 않는다. 장애가 나면 무엇을 들여다봐야 할지부터 막막해진다.

규칙은 eBPF 프로그램과 맵의 형태로 커널 안에 있다. 이 글은 eBPF가 무엇인지(검증기, 맵, 훅)를 작은 프로그램을 직접 커널에 올려 보며 확인하고, 그 위에서 Cilium이 kube-proxy를 대신하는 방식, IP 대신 identity로 정책을 거는 방식, Hubble로 흐름을 보는 방법까지 이어 간다.

이 주제의 다른 글과 나눈 범위가 있다. kube-proxy의 iptables·nftables 모드가 규칙을 어떻게 쓰는지와 conntrack 문제는 [kube-proxy 모드 글](/posts/k8s-kube-proxy-modes)에, 표준 NetworkPolicy의 규칙과 한계는 [NetworkPolicy 글](/posts/k8s-network-policy)에, 사이드카 프록시와 mTLS는 [서비스 메시 글](/posts/service-mesh)에 있다. 여기서는 그 설명을 반복하지 않고 eBPF가 같은 일을 다르게 푸는 지점만 본다.

실습 환경은 Ubuntu 24.04 사용자 공간(clang 18.1.3, Ubuntu `linux-tools-6.8.0-147` 패키지의 bpftool v7.4.0)과 리눅스 6.18 커널이다. 네트워크 네임스페이스 두 개를 veth로 잇고 그 사이에 프로그램을 걸었다. Cilium 자체는 실제 노드가 없어 띄우지 못했다. Cilium 명령의 출력은 Cilium v1.20.3 문서에 실린 것을 옮기고 예시로 표시했다.

## 커널에 작은 프로그램을 끼워 넣는다

패킷 처리를 바꾸고 싶을 때 예전에는 두 길밖에 없었다. 커널이 이미 가진 기능(iptables, tc 큐 규칙)을 조합하거나, 커널 모듈을 짜서 넣는 것이다. 앞의 것은 규칙이 수만 개가 되면 느리고 표현이 제한된다. 뒤의 것은 버그 하나가 커널 전체를 죽인다.

eBPF는 그 사이의 길이다. 커널이 정해 둔 길목(훅)에 작은 프로그램을 끼워 넣는데, 넣기 전에 커널의 검증기(verifier)가 그 프로그램이 커널을 망가뜨릴 수 없는지 증명한다. 통과한 프로그램은 JIT 컴파일러가 기계어로 바꿔서 거의 네이티브 속도로 돈다. 프로그램은 상태를 갖지 않고, 패킷 수나 Service 목록 같은 상태는 맵(map)이라는 커널 안의 키-값 저장소에 둔다. 사용자 공간 프로그램(Cilium 에이전트 같은)은 맵을 읽고 써서 프로그램의 동작을 바꾼다. 프로그램을 다시 올리지 않아도 된다.

## 검증기가 먼저 읽는다

받은 패킷의 IP 프로토콜 번호별로 수를 세고, ICMP는 버리는 XDP 프로그램을 썼다. 눈여겨볼 곳은 `data_end`와 비교하는 두 `if`다.

```c
// xdp_count.c — IP 프로토콜별 패킷 수를 세고, ICMP는 버린다
#include <linux/bpf.h>
#include <linux/if_ether.h>
#include <linux/ip.h>
#include <linux/in.h>
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_endian.h>

struct {
    __uint(type, BPF_MAP_TYPE_ARRAY);   // 키 0~255, 값 u64 카운터
    __uint(max_entries, 256);
    __type(key, __u32);
    __type(value, __u64);
} proto_count SEC(".maps");

SEC("xdp")
int xdp_count(struct xdp_md *ctx)
{
    void *data = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;
    struct ethhdr *eth = data;
    if ((void *)(eth + 1) > data_end)        // 이더넷 헤더 14바이트가 있나
        return XDP_PASS;
    if (eth->h_proto != bpf_htons(ETH_P_IP))
        return XDP_PASS;
    struct iphdr *ip = (void *)(eth + 1);
    if ((void *)(ip + 1) > data_end)         // IP 헤더 20바이트가 있나
        return XDP_PASS;
    __u32 key = ip->protocol;
    __u64 *val = bpf_map_lookup_elem(&proto_count, &key);
    if (val)
        __sync_fetch_and_add(val, 1);
    if (ip->protocol == IPPROTO_ICMP)
        return XDP_DROP;
    return XDP_PASS;
}

char LICENSE[] SEC("license") = "GPL";
```

```bash
# BPF 오브젝트로 컴파일한다 (libbpf-dev 헤더와 asm 헤더 경로가 필요하다)
clang -O2 -g -target bpf -I/usr/include/x86_64-linux-gnu -c xdp_count.c -o xdp_count.o
file xdp_count.o
```

```text
xdp_count.o: ELF 64-bit LSB relocatable, eBPF, version 1 (SYSV), with debug_info, not stripped
```

검증기가 까다로운 만큼 eBPF 프로그램에는 제약이 많다. 스택은 512바이트, 루프는 끝이 증명돼야 하고(5.3 이후 경계가 정해진 루프 허용), 검사하는 명령 수에도 상한(로그의 `limit 1000000`)이 있다. Cilium 같은 큰 프로그램은 기능을 여러 프로그램으로 쪼개 tail call로 잇는다. 대신 검증을 통과한 프로그램은 커널을 멈추게 할 수 없다. 커널 모듈과 가장 크게 다른 점이다.

## 맵에 상태를 두고 바깥에서 읽는다

이제 제대로 된 프로그램을 veth 한쪽에 건다. 네임스페이스 두 개를 만들고 r12b 쪽 장치에 XDP 프로그램을 붙였다.

```bash
# 네임스페이스 두 개를 veth로 잇는다
sudo ip netns add r12a && sudo ip netns add r12b
sudo ip link add r12va type veth peer name r12vb
sudo ip link set r12va netns r12a && sudo ip link set r12vb netns r12b
sudo ip -n r12a addr add 10.12.0.1/24 dev r12va && sudo ip -n r12a link set r12va up
sudo ip -n r12b addr add 10.12.0.2/24 dev r12vb && sudo ip -n r12b link set r12vb up
# r12b 쪽 장치에 XDP 프로그램을 건다 (xdpgeneric: 드라이버 지원 없이 도는 모드)
sudo ip -n r12b link set dev r12vb xdpgeneric obj xdp_count.o sec xdp
sudo ip -n r12b link show r12vb
```

```text
18: r12vb@if19: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 xdpgeneric qdisc noqueue state UP mode DEFAULT group default qlen 1000
    link/ether da:b4:7b:c3:9c:b0 brd ff:ff:ff:ff:ff:ff link-netns r12a
    prog/xdp id 19 name xdp_count tag 5ada26aa4282c1d0 jited 
```

`xdpgeneric`과 `prog/xdp id 19 ... jited`가 붙었다. 이제 ping은 버려지고 HTTP는 지나가야 한다. r12b에서 `python3 -m http.server 8080`을 띄우고 r12a에서 보냈다.

```bash
# ICMP는 XDP에서 버려지고, TCP는 지나간다
sudo ip netns exec r12a ping -c3 -W1 10.12.0.2
sudo ip netns exec r12a curl -s -o /dev/null -w '%{http_code}\n' http://10.12.0.2:8080/
# 프로그램과 맵이 커널에 어떻게 올라가 있나
sudo bpftool prog show
sudo ip netns exec r12b bpftool net show
# 맵에서 프로토콜 1(ICMP)과 6(TCP)의 수를 읽는다 (키는 4바이트 리틀 엔디언)
sudo bpftool map lookup name proto_count key 1 0 0 0

```

이 구조가 Cilium의 기본이다. 프로그램은 노드에 한 번 올리고, Service나 정책이 바뀌면 에이전트가 맵의 항목만 고친다. iptables처럼 규칙 목록 전체를 다시 쓰지 않으니 Service가 수만 개여도 갱신이 가볍고, 맵 조회는 해시라서 항목 수와 상관없이 일정하다. 맵 종류는 해시, 배열, LRU 해시, CPU별 해시, 주소 대역용 LPM trie, 이벤트를 보내는 ring buffer 등이 있고, 쓰임에 맞게 고른다.

## 패킷이 지나는 길목: XDP, tc, 소켓

eBPF를 걸 수 있는 네트워크 훅은 여러 층에 있다. 어디에 거느냐에 따라 볼 수 있는 정보와 할 수 있는 일이 다르다.

- XDP: 네트워크 드라이버가 패킷을 받자마자, 커널이 `sk_buff` 구조체를 만들기도 전에 돈다. 가장 빠르고 버리기(DDoS 방어)나 다른 장치로 바로 보내기에 좋다. 받는 방향에만 있다. 드라이버가 지원하면 native, 아니면 위처럼 generic 모드로 돈다(generic은 느리다).
- tc(clsact): `sk_buff`가 만들어진 뒤 들어오는 쪽과 나가는 쪽 모두에 건다. 주소를 바꾸거나 다른 장치로 넘기기 좋다. Cilium은 Pod의 veth와 노드 장치에 주로 여기에 건다.
- 소켓과 cgroup: 패킷이 아니라 `connect()`, `sendmsg()` 같은 시스템 콜에 건다. 연결을 맺는 순간 목적지 주소를 바꿀 수 있다.

나가는 쪽(tc egress)에서 TCP 8080을 막는 프로그램도 걸어 봤다. 반환값이 `TC_ACT_SHOT`이면 버린다.

sudo ip netns exec r12a tc filter add dev r12va egress bpf da obj tc_port.o sec tc

## kube-proxy 없이 Service를 푸는 법

Cilium을 kube-proxy 대체 모드로 깔면 Service 처리를 eBPF가 맡는다. kube-proxy가 없으니 Cilium 에이전트가 API 서버를 `kubernetes` Service의 ClusterIP로 찾을 수 없다. 그래서 설치할 때 API 서버 주소를 직접 알려 준다. Cilium v1.20.3 문서의 Helm 설정이다.

```bash
# Cilium 차트 저장소를 추가한다
helm repo add cilium https://helm.cilium.io/
# kube-proxy 없이 Cilium을 설치한다 (kubeadm이면 kube-proxy 애드온을 건너뛰고 클러스터를 만든다)
helm install cilium cilium/cilium --namespace kube-system \
  --set kubeProxyReplacement=true \
  --set k8sServiceHost=${API_SERVER_IP} \
  --set k8sServicePort=${API_SERVER_PORT}
# 대체 모드로 도는지 확인한다
kubectl -n kube-system exec ds/cilium -- cilium-dbg status --verbose
```

## IP 대신 identity로 정책을 건다

표준 NetworkPolicy를 iptables로 구현하면 "role=frontend Pod들의 IP 목록"을 노드마다 규칙으로 들고 있어야 한다. frontend Pod가 하나 뜰 때마다 backend가 있는 모든 노드의 규칙을 고쳐야 하고, 고치기 전에 새 Pod가 보낸 연결은 잘못 막힐 수 있다. Pod가 자주 바뀌는 큰 클러스터에서는 이 갱신이 병목이 된다.

Cilium은 주소와 보안을 떼어 놓는다. 같은 라벨 묶음을 가진 Pod들은 같은 숫자 identity를 받는다. 정책 맵에는 IP가 아니라 identity가 들어간다. frontend Pod가 100개로 늘어도 identity는 하나라서 backend 쪽 정책 맵은 그대로다. 새 Pod는 자기 identity만 알면 된다. 숫자 몇 개는 예약돼 있다. Cilium 문서 기준으로 `reserved:host`는 1, 클러스터 밖 전부를 뜻하는 `reserved:world`는 2, 헬스 체크는 4, 다른 노드는 `reserved:remote-node` 6이다.

```yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: api-ingress
spec:
  endpointSelector:
    matchLabels: {app: api}
  ingress:
  - fromEndpoints:
    - matchLabels: {app: frontend}
    toPorts:
    - ports: [{port: "8080", protocol: TCP}]
      rules:
        http:
        - {method: GET, path: "/v1/.*"}   # GET /v1/... 만 허용한다
---
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: api-egress-payments
spec:
  endpointSelector:
    matchLabels: {app: api}
  egress:
  - toEndpoints:                          # toFQDNs는 DNS 응답을 봐야 하니 DNS 허용과 검사가 함께 필요하다
    - matchLabels: {k8s:io.kubernetes.pod.namespace: kube-system, k8s-app: kube-dns}
    toPorts:
    - ports: [{port: "53", protocol: ANY}]
      rules:
        dns:
        - matchPattern: "*"
  - toFQDNs:
    - matchName: api.payments.example.com
    toPorts:
    - ports: [{port: "443", protocol: TCP}]
```

L7 규칙에는 대가가 있다. 그 포트의 트래픽이 커널에서 끝나지 않고 노드의 프록시를 한 번 지나니 지연과 CPU가 는다. 꼭 필요한 Service에만 건다.

## Hubble로 흐름을 본다

패킷이 eBPF 안에서 처리되면 tcpdump로는 "왜 버려졌는지"를 알 수 없다. Cilium의 프로그램은 판정할 때마다 이벤트를 남기고, Hubble이 이를 모아 흐름(flow)으로 보여 준다. 정책 문제를 볼 때 가장 먼저 여는 도구다.

```bash
# 버려진 흐름만 본다
hubble observe --pod deathstar --verdict DROPPED
# HTTP 수준으로 본다 (L7 정책이 걸린 포트)
hubble observe --pod deathstar --protocol http
```

## 언제 Cilium을 고르나

Cilium이 유리한 곳은 Service와 Pod가 많고 자주 바뀌는 클러스터, 표준 NetworkPolicy로 부족한 L7·도메인 정책이 필요한 곳, 흐름 단위 관측이 필요한 곳이다. 서비스 메시의 일부 기능(mTLS, L7 관측)을 사이드카 없이 노드 단위로 가져가려는 경우에도 후보가 된다.

비용도 분명하다.

- 커널 의존성이 생긴다. 커널 버전과 설정에 따라 쓸 수 있는 기능이 다르고, 노드 이미지를 바꿀 때마다 확인해야 한다. 오래된 커널을 오래 쓰는 환경이면 걸림돌이 된다.
- 디버깅 도구가 바뀐다. `iptables-save`, `conntrack -L` 대신 `cilium-dbg`, `hubble`, `bpftool`을 익혀야 한다. 장애 대응 문서와 사람의 습관이 같이 바뀌어야 한다.
- 맵은 크기가 정해져 있다. Service, 백엔드, 연결 추적 항목이 맵 크기를 넘으면 새 항목이 들어가지 못한다. 큰 클러스터는 맵 크기 설정과 사용률 지표를 함께 본다.
- 에이전트 업그레이드가 데이터패스 업그레이드다. 프로그램이 바뀌는 순간이 있으니 노드를 순서대로 올린다.

iptables 기반 kube-proxy와 Calico(또는 Flannel) 조합은 여전히 무난한 선택이다. 노드 수백 대, Service 수천 개 정도면 iptables로도 버티고, 많은 사람이 디버깅법을 안다. Calico도 eBPF 데이터패스 모드를 갖고 있어서 "eBPF냐 아니냐"와 "Cilium이냐 아니냐"는 따로 따질 문제다.

## 현장에서 eBPF 데이터패스를 의심할 때

Cilium 클러스터에서 연결이 안 될 때는 판정을 먼저 본다. 버려졌는지, 어디서 버려졌는지를 알면 나머지는 빨리 좁혀진다.

```bash
# 1. 에이전트가 건강한가, kube-proxy 대체가 켜져 있나
kubectl -n kube-system exec ds/cilium -- cilium-dbg status --brief
# 2. 버려진 흐름이 있나 (정책 때문인지, 다른 이유인지)
hubble observe --namespace <ns> --verdict DROPPED --last 50
# 3. 노드에서 실시간으로 drop 이벤트를 본다
kubectl -n kube-system exec ds/cilium -- cilium-dbg monitor --type drop
# 4. Service 백엔드가 맵에 들어 있나
kubectl -n kube-system exec ds/cilium -- cilium-dbg service list | grep <ClusterIP>
# 5. 그 노드의 장치에 어떤 BPF 프로그램이 걸려 있나
sudo bpftool net show
```

증상별로 자주 만나는 원인은 이렇다.

- 새로 뜬 Pod가 처음 몇 초간 연결이 안 된다. identity가 아직 정해지지 않은 `reserved:init` 상태이거나, 상대 노드의 ipcache에 새 Pod IP가 아직 퍼지지 않았다. Hubble에서 출발지 identity가 숫자로 찍히는지 본다.
- 정책을 걸었더니 외부 도메인 호출이 다 죽었다. `toFQDNs`를 쓰면서 DNS 허용과 DNS 검사 규칙을 같이 넣지 않았다. Cilium이 DNS 응답을 못 보면 도메인을 IP로 바꿀 수 없다.
- kube-proxy를 지운다고 했는데 노드에 KUBE-SVC 체인이 남아 있다. kube-proxy DaemonSet은 지웠지만 노드의 규칙이 그대로 남았다. 둘이 같이 Service를 처리하면 증상이 이상해진다. 노드를 새로 띄우거나 kube-proxy의 `--cleanup` 모드로 규칙을 지운다.
- 큰 패킷만 안 간다. 터널 모드(VXLAN, Geneve)의 헤더만큼 MTU가 줄어든다. 이 내용은 [CNI와 Pod 네트워크 글](/posts/k8s-cni-pod-network)에서 재현했다.
- Service가 가끔 응답을 안 한다. 연결 추적 맵이나 NAT 맵이 꽉 찼을 수 있다. 에이전트의 맵 사용률 지표와 `cilium-dbg` 로그의 맵 관련 경고를 본다.

## 규칙 목록에서 프로그램과 맵으로

eBPF는 커널 길목에 검증된 작은 프로그램을 끼워 넣고, 상태는 맵에 두어 바깥에서 고치는 방식이다. XDP는 받자마자, tc는 들어오고 나갈 때, 소켓 훅은 연결을 여는 순간 동작한다. Cilium은 이 위에서 Service를 소켓 단계에서 풀어 kube-proxy를 대신하고, Pod 라벨로 만든 identity로 정책을 판정하고, 판정마다 남긴 이벤트를 Hubble로 보여 준다. 그 대가로 커널 버전과 새 디버깅 도구에 익숙해져야 한다. Service와 NetworkPolicy가 iptables 위에서 어떻게 생겼는지는 [kube-proxy 모드 글](/posts/k8s-kube-proxy-modes)과 [NetworkPolicy 글](/posts/k8s-network-policy)에서 비교해 볼 수 있다.

## 면접에서 나올 만한 질문

### eBPF는 커널 모듈과 무엇이 다른가요?

eBPF 프로그램은 커널에 올리기 전에 검증기가 모든 경로를 따라가며 범위 밖 메모리 접근, 끝나지 않는 루프 같은 위험이 없는지 증명한다. 통과해야만 JIT로 기계어가 되어 훅에 걸리니, 버그가 있어도 커널을 멈추게 할 수 없다. 커널 모듈은 이런 검사 없이 커널 권한으로 돌아서 실수 하나가 커널 패닉이 된다. 대신 eBPF는 스택 크기, 명령 수, 쓸 수 있는 헬퍼 함수에 제약이 있다.

### 검증기가 패킷 접근을 거절하는 대표적인 이유는요?

`data_end`와 비교해 길이를 확인하지 않고 패킷을 읽었기 때문이다. 검증기는 레지스터마다 패킷 시작에서 몇 바이트까지 안전한지를 추적하고, 비교가 끝난 경로에서만 그 범위를 늘린다. 이더넷 헤더만 확인하고 IP 헤더의 필드를 읽으면 `invalid access to packet`으로 거절된다.

### XDP와 tc 훅은 어떻게 다르고, 언제 무엇을 쓰나요?

XDP는 드라이버가 패킷을 받자마자 `sk_buff`를 만들기 전에 돌아서 가장 빠르지만 받는 방향에만 있고 볼 수 있는 정보가 적다. 대량 차단이나 로드 밸런서 앞단 처리에 쓴다. tc는 `sk_buff`가 생긴 뒤 들어오고 나가는 양쪽에 걸 수 있어 주소 변환이나 Pod 단위 정책처럼 더 많은 문맥이 필요한 일에 쓴다. Cilium은 Pod의 veth에는 tc를, NodePort 가속에는 XDP를 쓴다.

### Cilium은 kube-proxy 없이 Service를 어떻게 처리하나요?

cgroup에 건 소켓 훅이 앱의 `connect()`를 가로채 LB 맵에서 백엔드를 골라 목적지를 Pod 주소로 바꿔 쓴다. 연결을 여는 순간 한 번만 바꾸니 패킷마다 DNAT하지 않고 conntrack 항목도 덜 생긴다. 소켓 단계가 아닌 경로(외부에서 오는 NodePort 등)는 tc나 XDP 프로그램이 패킷 단위로 처리한다. kube-proxy가 없으니 설치할 때 `k8sServiceHost`로 API 서버 주소를 직접 알려 줘야 한다.

### identity 기반 정책이 IP 기반보다 나은 점은요?

같은 라벨 묶음의 Pod들이 하나의 숫자 identity를 공유해서, Pod가 늘거나 바뀌어도 받는 쪽 노드의 정책 맵을 고칠 필요가 없다. IP 기반이면 Pod가 뜰 때마다 관련된 모든 노드의 IP 목록을 고쳐야 하고, 갱신 전에 보낸 연결이 잘못 막힐 수 있다. 터널 모드에서는 identity를 캡슐화 헤더에 실어 보내 받는 쪽이 IP를 해석하지 않아도 된다.

### Cilium 클러스터에서 Pod 사이 연결이 안 되면 무엇부터 보나요?

판정을 먼저 본다. `hubble observe --verdict DROPPED`로 버려졌는지와 이유(Policy denied 등)를 확인하고, 정책 문제가 아니면 `cilium-dbg monitor --type drop`으로 노드에서 drop 이유를 본다. Service 문제면 `cilium-dbg service list`에 백엔드가 들어 있는지 본다. `iptables-save`는 Cilium이 Service와 정책을 eBPF로 처리하니 거의 쓸모가 없다.

### Cilium을 도입할 때 주의할 트레이드오프는요?

커널 버전에 의존하고(v1.20 기준 5.10 이상), 디버깅 도구와 운영 습관이 바뀌고, 맵 크기라는 새 한계가 생긴다. L7 정책은 노드 프록시를 거치니 그 포트의 지연과 CPU가 는다. Service와 Pod가 적고 팀이 iptables 디버깅에 익숙하면 기존 kube-proxy 조합이 더 단순할 수 있다.
