병원 상담 기록을 요약하는 기능을 만든다고 해 보자. 기획은 간단했는데 보안 검토에서 막힌다. 환자 기록을 외부 모델 API로 보낼 수 없다는 것이다. 공급사가 학습에 쓰지 않는다고 약관에 적어 두어도, 데이터가 회사 망을 떠나는 것 자체가 규정 위반인 조직이 있다. 남은 길은 모델을 직접 띄우는 것이다.

막상 해 보려고 하면 질문이 줄줄이 나온다. 어떤 모델을 받아야 하나, 라이선스는 상업적으로 써도 되나, 노트북에서 돌려 보던 Ollama를 그대로 서버에 올려도 되나, GPU는 몇 GB짜리가 필요한가, 사용자 50명이 동시에 쓰면 느려지지 않나, 그리고 이게 API를 쓰는 것보다 싼가.

이 글은 그 순서대로 간다. 모델 고르기와 라이선스, 노트북용 도구와 서버용 추론 엔진의 차이, GPU 메모리 계산과 양자화, 처리량을 올리는 연속 배칭과 PagedAttention, OpenAI 호환 엔드포인트로 노출하기, 비용 손익분기, 브라우저에서 돌리는 작은 모델까지다. 토큰과 생성 루프의 기본은 [LLM 기초 글](/posts/llm-basics-for-developers)에, 모델 API를 서비스에 붙이는 코드는 [LLM API 연동 글](/posts/llm-api-integration)에 있다. 띄운 모델이 API 모델만큼 답하는지 재는 방법은 [LLM 평가 글](/posts/llm-evals)로 넘긴다.

## 데이터를 밖으로 보낼 수 없을 때

모델을 직접 띄우는 이유는 보통 셋 중 하나다. 첫째는 위의 장면처럼 데이터가 망을 떠날 수 없는 경우다. 의료, 금융, 공공, 사내 소스 코드가 흔한 예다. 둘째는 비용이다. 하루 수억 토큰을 쓰는 일괄 처리(문서 분류, 요약)는 GPU를 꽉 채워 돌리면 API보다 싸질 수 있다. 셋째는 통제다. 모델 버전이 내 허락 없이 바뀌지 않고, 공급사 장애나 속도 제한에 묶이지 않고, 필요하면 내 데이터로 파인튜닝한 모델을 올릴 수 있다.

반대로 잃는 것도 분명하다. 가장 강한 상용 모델은 가중치를 공개하지 않으니, 직접 띄울 수 있는 건 공개 가중치(open-weight) 모델뿐이다. 같은 일을 시켰을 때 품질 차이가 있을 수 있고, 그 차이가 이 일에서 문제가 되는지는 평가로 확인해야 한다. GPU를 사고(혹은 빌리고), 드라이버와 엔진을 올리고, 장애가 나면 새벽에 일어나는 일도 우리 몫이 된다.

## 모델은 Hugging Face Hub에서 고른다

공개 가중치 모델은 대부분 Hugging Face Hub에 올라온다. 모델마다 페이지(모델 카드)가 있고, 여기서 봐야 할 것이 정해져 있다.

- 크기(파라미터 수): 8B, 70B처럼 적힌다. GPU 메모리를 정하는 첫 숫자다.
- 종류: 같은 이름에 base와 instruct(또는 chat)가 따로 있다. 대화나 지시를 따르게 하려면 instruct를 받는다. base는 문장 이어 쓰기만 배운 상태다.
- 컨텍스트 길이: 학습 때 다룬 최대 길이. 긴 문서 요약이라면 중요하다.
- 라이선스: 아래에서 따로 본다.
- 파일 형식: 원본은 보통 safetensors 파일 여러 개로 나뉘어 있다. GGUF는 llama.cpp 계열(Ollama, LM Studio)이 쓰는 양자화된 단일 파일 형식으로, 보통 원본과 다른 저장소에 따로 올라온다.
- 태스크: Hub는 모델을 text-generation, feature-extraction(임베딩), automatic-speech-recognition 같은 태스크로 분류한다. 요약이라면 꼭 생성 모델이 아니어도 된다는 것을 이 분류에서 떠올리게 된다.

일부 모델은 게이트(gated)가 걸려 있어서 페이지에서 약관에 동의하고, 접근 토큰으로 내려받아야 한다.

```bash
# Hugging Face CLI 설치 (huggingface_hub 패키지에 들어 있다)
pip install -U "huggingface_hub[cli]"

# 접근 토큰으로 로그인한다. 토큰은 Hub 설정 페이지에서 읽기 권한으로 만든다
hf auth login

# 모델 파일을 내려받는다. 서버에서는 캐시 위치를 큰 디스크로 잡아 둔다
HF_HOME=/data/hf hf download meta-llama/Llama-3.1-8B-Instruct
```

CLI 이름은 버전에 따라 `huggingface-cli`(예전)와 `hf`(새 버전)로 다르니, 설치된 버전의 도움말을 확인한다. 8B 모델도 원본은 16GB 정도라서, 서버마다 따로 내려받지 말고 공유 스토리지나 사내 미러에 한 번 받아 두는 게 낫다. Hub에 접속할 수 없는 폐쇄망이라면 이 단계가 반입 절차가 된다.

### 라이선스는 모델마다 다르다

"공개 모델"이 곧 "아무렇게나 써도 되는 모델"은 아니다. Apache 2.0이나 MIT처럼 널리 쓰이는 오픈소스 라이선스로 풀린 모델이 있고, 공급사가 직접 만든 라이선스로 풀린 모델이 있다. Meta의 Llama 계열은 자체 커뮤니티 라이선스를 쓰는데, 월간 활성 사용자가 7억 명을 넘는 서비스는 별도 허가를 받아야 한다는 조항과 허용 사용 정책이 붙어 있다. Google의 Gemma도 자체 이용 약관이 있다. 같은 회사의 모델이라도 크기마다 라이선스가 다른 경우가 있다.

확인할 것은 상업적 사용 가능 여부, 사용자 수나 매출 조건, 금지된 용도, 모델 출력으로 다른 모델을 학습시키는 것을 막는지, 파인튜닝한 모델을 배포할 때의 조건이다. 법무 검토를 받을 때는 모델 카드가 아니라 저장소에 있는 LICENSE 파일 원문을 넘긴다.

## 노트북의 Ollama와 서버의 vLLM은 하는 일이 다르다

처음 모델을 띄워 볼 때 가장 쉬운 건 Ollama다. 설치하고 명령 하나면 모델을 내려받아 대화가 된다.

```bash
# Ollama 설치 (Linux 공식 설치 스크립트)
curl -fsSL https://ollama.com/install.sh | sh

# 4비트로 양자화된 8B 모델을 받아 대화를 시작한다
ollama run llama3.1:8b

# 지금 메모리에 올라온 모델과, GPU/CPU 중 어디에 올라갔는지 본다
ollama ps
```

Ollama는 내부적으로 llama.cpp를 쓰고 GGUF 형식 모델을 받는다. `localhost:11434`에서 자체 API와 OpenAI 호환 API를 함께 연다. LM Studio는 같은 계열의 엔진을 GUI로 감싼 데스크톱 앱이다. 모델을 검색해 받고, 슬라이더로 설정을 바꾸고, 로컬 서버(기본 1234 포트)를 켤 수 있다. 둘 다 "내 컴퓨터에서 한 사람이 쓰기"에 맞춰져 있다. GPU가 없거나 모자라면 일부 층을 CPU로 돌리고, 애플 실리콘 맥의 통합 메모리를 잘 쓴다.

서버에서 여러 사용자를 받을 때는 vLLM, SGLang, Hugging Face의 TGI(Text Generation Inference) 같은 추론 엔진을 쓴다. 이 엔진들은 GPU 한 장으로 동시에 수십~수백 개의 요청을 처리하도록 만들어졌다. 차이는 아래 "주방" 이야기에서 나온다.

```bash
# vLLM을 설치하고 OpenAI 호환 서버를 띄운다 (NVIDIA GPU, CUDA 드라이버 필요)
pip install vllm

# --max-model-len: 요청 하나의 최대 길이. KV 캐시 계산에 쓰인다
# --gpu-memory-utilization: GPU 메모리의 몇 %를 쓸지 (기본 0.9)
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90 \
  --port 8000
```

Docker로 띄우면 이렇다. 공식 이미지가 `vllm/vllm-openai`로 올라와 있다.

```bash
# GPU를 컨테이너에 넘기려면 NVIDIA Container Toolkit이 먼저 설치되어 있어야 한다
# -v: 내려받은 모델을 재사용한다 / -e HF_TOKEN: 게이트 모델이면 필요하다
docker run --gpus all -p 8000:8000 \
  -v /data/hf:/root/.cache/huggingface \
  -e HF_TOKEN="$HF_TOKEN" \
  vllm/vllm-openai:latest \
  --model meta-llama/Llama-3.1-8B-Instruct --max-model-len 8192
```

`latest` 태그는 실습에서만 쓰고, 운영에서는 버전 태그를 고정한다. 엔진 버전이 바뀌면 같은 모델이라도 기본값과 성능이 달라진다.

흔한 실수는 Ollama를 그대로 서버에 올려 사내 서비스로 쓰는 것이다. 사용자가 몇 명일 때는 잘 돌다가 동시 요청이 늘면 대기열이 길어진다. Ollama도 동시 처리 수(`OLLAMA_NUM_PARALLEL`)를 설정할 수 있지만, 많은 동시 요청을 처리하도록 설계된 엔진은 아니다. 또 하나는 Ollama의 기본 컨텍스트 길이다. 모델이 지원하는 길이보다 훨씬 짧게(버전에 따라 2048이나 4096 토큰) 잡혀 있어서, 긴 상담 기록을 넣으면 앞부분이 조용히 잘린다. 요약이 이상하면 `num_ctx` 설정부터 본다.

## GPU 메모리는 가중치와 KV 캐시로 나뉜다

GPU 메모리를 얼마나 쓰는지는 두 덩어리로 계산된다.

첫째는 가중치다. 파라미터 수 × 파라미터 하나의 크기다. 8B 모델을 16비트(FP16, BF16)로 올리면 80억 × 2바이트 = 16GB다. 70B면 140GB로, 80GB GPU 한 장에 안 들어간다.

둘째는 KV 캐시다. 모델은 다음 토큰을 만들 때마다 앞의 모든 토큰을 다시 보는데, 앞 토큰들의 중간 계산 결과(키와 값)를 저장해 두고 재사용한다. 이게 KV 캐시다. 토큰 하나당 크기는 2(키와 값) × 층 수 × KV 헤드 수 × 헤드 차원 × 값 하나의 바이트 수다. Llama 3.1 8B는 32층, KV 헤드 8개, 헤드 차원 128이라 2 × 32 × 8 × 128 × 2바이트 = 131,072바이트, 토큰당 128KiB다. 같은 계열 70B는 80층이라 토큰당 320KiB다.

KV 캐시는 요청마다, 토큰마다 쌓인다. 8,192토큰 요청 하나에 약 1.1GB, 그런 요청 16개가 동시에 돌면 17GB가 넘는다. 가중치만 보고 "16GB 모델이니 24GB GPU면 넉넉하다"고 판단하면, 동시 사용자가 늘어나는 순간 KV 캐시가 들어갈 자리가 없다. 직접 계산해 보자.

  return { weightsGB: r(weights), kvGB: r(kv), totalGB: r(weights + kv) };

세 번째 테스트가 눈여겨볼 곳이다. 가중치를 4비트로 줄이면 16GB가 4.5GB가 되지만, KV 캐시 17.2GB는 그대로다. 동시 요청이 많은 서비스에서는 KV 캐시가 가중치보다 커진다. 그래서 KV 캐시 자체를 8비트로 저장하는 옵션(vLLM의 `--kv-cache-dtype fp8` 같은 것)이 따로 있다. 네 번째 테스트처럼 KV 캐시가 반으로 준다.

실제로는 이 계산에 더해 활성값(중간 계산), CUDA 런타임, 엔진의 작업 공간이 수 GB 더 든다. vLLM은 `--gpu-memory-utilization`만큼 GPU 메모리를 미리 잡고, 가중치를 올린 뒤 남은 공간을 전부 KV 캐시 블록으로 나눠 둔다. 그래서 띄우자마자 GPU 메모리가 90% 찬 것으로 보이는 건 정상이다. 같은 GPU에 다른 프로세스를 함께 올리면 메모리가 모자라 시작이 실패한다.

70B를 FP16으로 올리려면 140GB가 넘으니 GPU 여러 장에 나눠 올린다. 층 안의 행렬을 GPU 여러 장에 쪼개는 텐서 병렬(`--tensor-parallel-size 2` 같은 설정)이 흔하다. GPU끼리 매 층마다 결과를 주고받아서 GPU 사이 연결(NVLink 같은 고속 연결이 있는지)에 따라 속도가 크게 달라진다. GPU를 Kubernetes에서 나눠 쓰는 방법은 [Kubernetes GPU 글](/posts/k8s-gpu-dra)에 있다.

## 4비트로 줄이면 무엇을 잃나

양자화(quantization)는 가중치를 더 적은 비트로 적는 것이다. 16비트 실수 대신 8비트나 4비트 정수로 적고, 정수를 실수로 되돌릴 배율(scale)을 함께 저장한다. 4비트 정수는 −8부터 7까지 16개 값만 쓸 수 있으니, 원래 값들을 그 16칸에 맞춰 반올림하는 셈이다.

중요한 건 배율을 얼마나 잘게 두느냐다. 가중치 전체에 배율 하나를 쓰면 한 칸의 폭이 "가장 큰 값 ÷ 7"로 정해진다. 큰 값이 하나라도 있으면 칸이 넓어져서 작은 값들은 전부 0으로 뭉개진다. 그래서 가중치를 32개나 128개씩 묶어(그룹) 묶음마다 배율을 따로 둔다. numpy로 재 봤다. 평균 0, 표준편차 0.02인 가중치 약 100만 개를 4비트로 줄였다가 되돌려서, 원래 값 대비 평균 오차를 쟀다.

```python
# quant.py: 그룹 크기별 4비트 양자화 오차 (numpy 2.5)
import numpy as np
rng = np.random.default_rng(0)
w = rng.normal(0, 0.02, 4096 * 256).astype(np.float32)

def quantize(w, group, bits=4):
    w2 = w.reshape(-1, group)
    qmax = 2 ** (bits - 1) - 1                     # 4비트면 7
    scale = np.abs(w2).max(axis=1, keepdims=True) / qmax  # 묶음마다 배율 하나
    q = np.clip(np.round(w2 / scale), -qmax - 1, qmax)
    return (q * scale).reshape(-1)                 # 다시 실수로 되돌린 값

def rel_err(w, d):
    return np.abs(d - w).mean() / np.abs(w).mean()

for g in [len(w), 128, 32]:
    print(g, round(float(rel_err(w, quantize(w, g))), 4))

w[5] = 0.5   # 아주 큰 값(이상치) 하나를 넣는다
for g in [len(w), 32]:
    print("outlier", g, round(float(rel_err(w, quantize(w, g))), 4))
```

```text
1048576 0.2236
128 0.1257
32 0.1017
outlier 1048576 0.9257
outlier 32 0.1018
```

전체에 배율 하나(첫 줄)면 평균 오차가 22%인데, 128개 묶음이면 13%, 32개 묶음이면 10%로 준다. 이상치 하나를 넣으니 차이가 극적이다. 배율 하나짜리는 오차가 93%로 치솟는다. 거의 모든 가중치가 0으로 반올림되었기 때문이다. 32개 묶음은 이상치가 든 묶음 하나만 망가지고 나머지는 그대로라 10%를 지킨다. 실제 LLM 가중치에는 이런 이상치가 있다고 알려져 있어서, 실무 양자화 방식은 모두 묶음 배율을 쓰고, AWQ나 GPTQ처럼 중요한 가중치를 골라 더 조심스럽게 다루는 방식도 쓰인다.

묶음 배율에는 공간이 든다. 32개마다 16비트 배율 하나면 가중치 하나당 0.5비트가 더 붙어 4.5비트가 된다. 위 계산기에서 4비트 모델을 4.5비트로 넣은 이유다. GGUF의 Q4_K_M 같은 이름은 이런 묶음 구조와 비트 배분 방식을 가리키며, 같은 "4비트"라도 실제 파일 크기는 방식마다 조금씩 다르다.

이 오차가 답의 품질에 얼마나 영향을 주는지는 가중치 오차로 바로 알 수 없다. 모델은 오차에 꽤 강해서, 8비트는 대부분의 일에서 차이를 느끼기 어렵고 4비트는 작은 하락이 있다는 보고가 많다. 다만 숫자 계산, 코드, 긴 추론처럼 정밀함이 필요한 일에서 차이가 더 크게 나타나는 경향이 있고, 작은 모델일수록 양자화에 약하다. 결국 우리 일의 평가 세트로 FP16과 4비트를 나란히 돌려 보고 정한다. "70B 4비트 vs 8B FP16"처럼 같은 메모리에서 큰 모델을 줄여 넣을지 작은 모델을 그대로 넣을지도 같은 방법으로 고른다.

## 한 요청씩 처리하면 GPU가 논다

토큰을 하나 만들 때마다 모델은 가중치 전체를 GPU 메모리에서 읽어 와야 한다. 8B FP16이면 토큰 하나에 16GB를 읽는 셈이다. 계산보다 이 읽기가 병목이라, 요청 하나만 처리할 때 초당 토큰 수의 상한은 대략 "메모리 대역폭 ÷ 가중치 크기"다. 대역폭이 3.35TB/s인 GPU(H100 SXM의 공개 사양)라면 3.35TB ÷ 16GB ≈ 초당 209토큰이 이론 상한이다. 4비트(4.5GB)로 줄이면 약 744토큰까지 올라간다. 양자화가 메모리만이 아니라 속도에도 도움이 되는 이유다.

여기서 핵심 관찰이 나온다. 가중치를 한 번 읽어 올 때 요청 하나의 토큰만 계산하든 요청 32개의 토큰을 한꺼번에 계산하든 읽는 양은 같다. 그러니 여러 요청을 묶어(배칭) 한 번에 계산하면, 요청 하나의 속도는 거의 그대로인데 전체 처리량은 몇 배로 늘어난다.

문제는 요청마다 길이가 다르다는 것이다. 예전 방식(정적 배칭)은 요청 4개를 묶어 시작하면 4개가 모두 끝날 때까지 새 요청을 받지 않았다. 짧은 답은 일찍 끝났는데 그 자리는 가장 긴 답이 끝날 때까지 비어 있고, 새 요청은 문 앞에서 기다린다. 식당 주방에 비유하면, 한 테이블의 요리가 다 나갈 때까지 다음 주문을 받지 않는 주방이다.

연속 배칭(continuous batching)은 토큰 한 단계마다 묶음을 다시 짠다. 어떤 요청이 끝나면 그 자리에 대기열의 다음 요청을 바로 넣는다. 화구가 비는 즉시 다음 주문을 올리는 주방이다. 아래 그림에서 다음을 누르며 자리 네 개가 어떻게 채워지는지 보자.

자리 수는 고정이 아니다. 실제 엔진에서는 KV 캐시가 들어갈 공간이 허락하는 만큼 자리를 늘린다. 그래서 KV 캐시를 얼마나 알뜰하게 쓰느냐가 곧 동시 처리 수가 된다.

### PagedAttention은 KV 캐시를 페이지로 나눈다

예전 방식은 요청이 들어오면 그 요청이 쓸 수 있는 최대 길이만큼 KV 캐시 공간을 통째로 미리 잡았다. 최대 8,192토큰을 잡아 두었는데 실제 답이 300토큰에서 끝나면 나머지는 그동안 아무도 못 쓴다. 이렇게 낭비되는 공간이 컸다.

vLLM이 들고 나온 PagedAttention은 운영체제의 가상 메모리 페이징과 같은 생각이다. KV 캐시를 작은 블록(기본 16토큰)으로 나누고, 요청이 토큰을 만들 때마다 필요한 만큼만 블록을 붙여 준다. 블록은 GPU 메모리 곳곳에 흩어져 있어도 되고, 요청마다 블록 테이블로 순서를 기억한다. vLLM 논문은 기존 시스템이 KV 캐시 메모리의 60~80%를 낭비하던 것을 4% 미만으로 줄였다고 보고했다. 남는 공간만큼 동시 요청을 더 받으니 처리량이 오른다.

블록 단위로 나눠 두면 덤도 있다. 여러 요청이 같은 시스템 프롬프트로 시작하면, 그 부분의 KV 블록을 복사하지 않고 함께 가리킬 수 있다. 이게 프리픽스 캐싱(prefix caching)이다. 긴 시스템 프롬프트나 같은 문서를 여러 번 묻는 RAG에서 첫 토큰 시간이 크게 준다.

KV 캐시가 꽉 차면 어떻게 될까. 엔진은 새 요청을 대기열에 두고, 그래도 모자라면 진행 중인 요청 일부를 잠시 내려놓는다(preemption). 내려놓은 요청은 나중에 KV 캐시를 다시 계산하거나 CPU 메모리에서 되돌려 와야 해서 그만큼 느려진다. 로그에 preemption 경고가 자주 보이면 동시 처리 수에 비해 KV 캐시가 모자란 것이다.

## 동시 사용자와 지연은 맞바꾼다

배칭은 처리량을 올리지만 공짜는 아니다. 묶음이 커질수록 한 단계의 계산이 무거워져서 요청 하나가 토큰을 받는 간격(토큰 간 지연)이 조금씩 늘어난다. 새 요청의 긴 프롬프트를 처리하는 단계(prefill)가 끼어들면, 그 단계 동안 다른 요청들의 토큰 생성이 잠깐 멈칫하기도 한다. 엔진들은 prefill을 잘게 나눠 끼워 넣는 기능(chunked prefill)으로 이 멈칫을 줄인다.

그래서 운영에서는 두 숫자를 같이 본다. 사용자가 느끼는 지연(첫 토큰 시간 p95, 토큰 간 지연)과 GPU가 내는 전체 처리량(초당 총 토큰 수)이다. 동시 처리 수 상한(vLLM의 `--max-num-seqs`)을 올리면 처리량이 오르다가 어느 지점부터 지연만 늘어난다. 이 지점은 모델, GPU, 입력·출력 길이 분포에 따라 달라서 문서의 숫자로 정할 수 없다. 실제 요청 분포를 흉내 낸 부하 테스트로 동시 사용자 수를 올려 가며 두 숫자를 그려 보고, 지연 목표(예: 첫 토큰 p95 1초)를 지키는 가장 높은 처리량을 고른다. vLLM 저장소에 벤치마크 스크립트가 들어 있다.

대화형 채팅과 밤에 도는 일괄 요약은 목표가 다르다. 채팅은 지연이 우선이고, 일괄 처리는 처리량이 우선이다. 같은 GPU에서 둘을 섞으면 일괄 작업이 채팅의 지연을 망친다. 따로 띄우거나, 일괄 작업은 사람이 없는 시간에 돌린다.

## OpenAI 호환 엔드포인트로 연다

vLLM, SGLang, Ollama, LM Studio 모두 OpenAI의 Chat Completions API와 같은 모양의 엔드포인트를 연다. 그래서 OpenAI SDK의 `baseURL`만 바꾸면 기존 코드가 그대로 돈다.

```ts
import OpenAI from "openai";

// 사내 vLLM 서버를 가리킨다. 키는 게이트웨이에서 검사하는 사내 키
const client = new OpenAI({
  baseURL: "http://llm-gateway.internal:8000/v1",
  apiKey: process.env.INTERNAL_LLM_KEY!,
});

const stream = await client.chat.completions.create({
  model: "meta-llama/Llama-3.1-8B-Instruct", // vLLM은 띄운 모델 이름을 그대로 쓴다
  messages: [
    { role: "system", content: "상담 기록을 세 문장으로 요약한다." },
    { role: "user", content: record },
  ],
  max_tokens: 300,
  stream: true,
});
```

호환은 "대부분"이라는 점은 알아 둔다. 기본 요청·응답과 스트리밍은 맞지만, 도구 호출이나 구조화 출력은 엔진 버전과 모델의 채팅 템플릿에 따라 지원 범위가 다르다. vLLM은 도구 호출을 쓰려면 모델에 맞는 파서를 옵션으로 지정해야 하고, 구조화 출력은 자체 방식(guided decoding)으로 지원한다. 공급사 API에서 쓰던 기능을 옮길 때는 하나씩 확인한다.

운영에서는 엔진 앞에 게이트웨이를 둔다. 엔진은 GPU를 잘 쓰는 데 집중하고, 인증, 팀별 한도, 요청 로그, 모델별 라우팅은 앞단이 맡는다. vLLM은 `/metrics`로 Prometheus 지표(실행 중 요청 수, 대기 중 요청 수, KV 캐시 사용률, 첫 토큰 시간 분포)를 내놓으니, 대기 중 요청 수가 계속 0보다 크면 GPU를 늘릴 신호로 쓴다.

## API보다 싸지는 지점

직접 띄우는 게 싼지는 사용량에 달려 있다. 계산 틀은 단순하다. GPU 시간당 비용을, 그 GPU가 한 시간에 만드는 토큰 수로 나눈다.

가정을 하나 놓고 계산해 보자. GPU 한 장을 시간당 2달러에 빌리고, 연속 배칭으로 꽉 채웠을 때 초당 1,500토큰을 만든다고 치자. 한 시간에 540만 토큰이니 백만 토큰당 약 0.37달러다. 같은 GPU가 하루 대부분 놀아서 평균 초당 150토큰밖에 안 만든다면 백만 토큰당 3.70달러가 된다. GPU는 놀아도 돈이 나간다. 사용량이 적고 들쭉날쭉한 서비스는 쓴 만큼만 내는 API가 거의 항상 싸고, 하루 종일 꽉 채울 수 있는 일괄 처리일수록 직접 띄우는 쪽이 유리해진다. 위 숫자는 가정이니, 실제로는 내 모델과 GPU로 잰 처리량과 실제 GPU 가격을 넣는다.

빠뜨리기 쉬운 비용도 있다. 사람의 시간(엔진 업그레이드, 드라이버 문제, 장애 대응), 여분 GPU(한 장이 죽으면 서비스가 멈추니 두 장 이상), 모니터링, 그리고 품질 차이다. 공개 모델이 이 일에서 상용 모델보다 정확도가 낮아서 사람이 검토할 양이 늘어난다면 그것도 비용이다. 반대로 데이터가 밖으로 나갈 수 없다면 이 계산은 의미가 없다. API라는 선택지 자체가 없기 때문이다.

## 아주 작은 모델은 브라우저에서 돌린다

모든 모델이 GPU 서버에 있어야 하는 건 아니다. Transformers.js(`@huggingface/transformers` 패키지)는 ONNX로 바꾼 모델을 브라우저와 Node.js에서 돌린다. WebGPU를 지원하는 브라우저에서는 GPU를, 아니면 WebAssembly로 CPU를 쓴다.

```ts
import { pipeline } from "@huggingface/transformers";

// 처음 한 번 모델 파일을 내려받고, 이후에는 브라우저 캐시에서 읽는다
const embed = await pipeline("feature-extraction", "Xenova/all-MiniLM-L6-v2", {
  device: "webgpu", // 지원하지 않는 브라우저면 "wasm"
});

const vectors = await embed(["배포가 실패했다", "deploy failed"], {
  pooling: "mean",
  normalize: true,
});
```

맞는 일은 수십~수백 MB짜리 작은 모델로 되는 일이다. 문장 임베딩, 분류, 짧은 텍스트의 감정 분석, 음성 인식 작은 모델, 이미지 분류 같은 것들이다. 데이터가 사용자 기기를 아예 떠나지 않고, 서버 비용이 없고, 오프라인에서도 된다. 대신 첫 방문 때 모델 파일을 내려받아야 해서 처음 쓸 때까지 시간이 걸리고, 사용자 기기마다 성능이 크게 다르며, 수 GB짜리 생성 모델은 대부분의 기기에서 현실적이지 않다. 모델 파일을 받는 동안 진행률을 보여 주고, 기능을 쓰기 직전이 아니라 미리 받아 두는 식으로 다룬다.

Hugging Face는 서버 쪽 호출도 SDK(`@huggingface/inference`의 InferenceClient)로 준다. Hub의 모델을 여러 추론 제공자를 통해 API로 부르는 방식이라, 직접 띄우기 전에 후보 모델 몇 개를 빠르게 비교해 볼 때 쓸 만하다. 다만 이것은 결국 외부 API이니 처음 장면처럼 데이터가 나갈 수 없는 경우의 답은 아니다.

## 직접 띄운 서버에서 받는 제보

"처음 요청이 30초 걸린다"면 모델 로딩이다. 엔진이 시작할 때 수십 GB를 디스크에서 읽어 GPU에 올리고, 일부 엔진은 그래프 컴파일까지 한다. Ollama는 일정 시간(기본 5분) 요청이 없으면 모델을 메모리에서 내린다(`OLLAMA_KEEP_ALIVE`로 바꾼다). 서버라면 엔진을 미리 띄워 두고, 준비 완료 후에만 트래픽을 받도록 헬스 체크를 건다.

"평소엔 빠른데 점심시간에만 느리다"면 대기 중 요청 수와 KV 캐시 사용률을 본다. 대기열이 쌓이고 KV 캐시가 100% 근처면 GPU가 모자란 것이다. GPU를 늘리거나, `--max-model-len`을 실제로 필요한 길이로 줄여 요청당 차지하는 공간을 줄이거나, KV 캐시를 FP8로 바꾼다.

"Ollama로 테스트할 땐 잘 요약하더니 vLLM에 올리니 답이 이상하다"면 같은 모델이 아닐 가능성부터 본다. Ollama의 `llama3.1:8b`는 4비트 GGUF이고 vLLM은 원본 BF16을 올렸을 수 있다. 채팅 템플릿(시스템·사용자 메시지를 모델이 학습한 형식으로 감싸는 규칙)이 다르거나, 기본 샘플링 값(temperature 등)이 엔진마다 달라서 생기기도 한다. 비교할 때는 모델 파일, 템플릿, 샘플링 값을 맞춘다.

"GPU 메모리가 부족하다며 엔진이 안 뜬다"면 같은 GPU에 다른 프로세스가 있는지 `nvidia-smi`로 보고, `--max-model-len`을 줄이거나 `--gpu-memory-utilization`을 조정한다. 모델이 지원하는 최대 길이(예: 128K)로 기본값이 잡히면, 요청 하나도 KV 캐시에 못 들어간다며 시작을 거부할 수 있다.

## 직접 띄운다는 건 GPU 메모리를 관리하는 일이다

모델을 직접 띄우는 일은 결국 GPU 메모리를 나눠 쓰는 일로 모인다. 가중치는 양자화로 줄이고, 나머지 공간을 KV 캐시로 알뜰하게 쪼개 쓸수록 동시에 더 많은 요청을 받는다. 연속 배칭과 PagedAttention이 그 일을 하고, 우리는 지연 목표 안에서 처리량이 가장 높은 지점을 부하 테스트로 찾는다. 비용은 GPU를 얼마나 꽉 채우느냐에 달려 있고, 품질 차이는 평가 세트로 확인한다. 띄운 모델로 이미지나 음성까지 다루려면 [멀티모달 글](/posts/multimodal-llm-apps)을 이어서 보면 된다.

## 면접에서 나올 만한 질문

### 언제 모델을 직접 띄우고, 언제 API를 쓰나요?

데이터가 조직 밖으로 나갈 수 없거나, GPU를 하루 종일 꽉 채울 만큼 사용량이 많거나, 모델 버전과 가용성을 직접 통제해야 할 때 직접 띄운다. 사용량이 적고 들쭉날쭉하면 GPU가 노는 시간에도 돈이 나가니 API가 싸다. 직접 띄우면 쓸 수 있는 건 공개 가중치 모델뿐이라 품질 차이를 평가로 확인해야 하고, 운영 인력과 여분 GPU도 비용에 넣어야 한다.

### 8B 모델을 서비스하려면 GPU 메모리가 얼마나 필요한가요?

가중치와 KV 캐시를 따로 계산한다. 8B를 FP16으로 올리면 가중치가 16GB이고, Llama 3.1 8B 구조라면 KV 캐시가 토큰당 128KiB라 8K 토큰 요청 하나에 약 1.1GB, 16개가 동시에 돌면 17GB가 넘는다. 여기에 활성값과 런타임 여유가 더 든다. 가중치만 보고 GPU를 고르면 동시 사용자가 늘 때 KV 캐시 자리가 없어 대기열과 preemption이 생긴다.

### 양자화는 무엇이고 무엇을 잃나요?

가중치를 16비트 대신 8비트나 4비트 정수와 배율로 적어 메모리와 대역폭을 줄이는 것이다. 배율을 32~128개 묶음마다 따로 두는 이유는 큰 값 하나가 전체 칸 폭을 넓혀 작은 값들을 0으로 뭉개는 걸 막기 위해서다. 8비트는 대부분 차이가 작고 4비트는 작은 하락이 있으며, 계산·코드·긴 추론이나 작은 모델에서 더 드러나는 경향이 있다. 결국 우리 평가 세트로 비교해 정한다.

### 연속 배칭은 왜 처리량을 올리나요?

토큰 생성은 매 단계 가중치 전체를 읽는 메모리 대역폭이 병목이라, 여러 요청을 묶어 한 번 읽을 때 같이 계산하면 처리량이 몇 배로 는다. 정적 배칭은 묶음의 가장 긴 요청이 끝날 때까지 빈자리를 못 채우지만, 연속 배칭은 토큰 단계마다 끝난 요청을 빼고 대기 요청을 넣어 GPU를 계속 채운다. 대신 묶음이 커질수록 토큰 간 지연이 조금씩 늘어난다.

### PagedAttention은 어떤 문제를 푸나요?

KV 캐시를 요청의 최대 길이만큼 통째로 미리 잡던 방식의 낭비를 없앤다. KV 캐시를 16토큰 같은 작은 블록으로 나누고 필요할 때마다 붙여 주며, 블록 테이블로 순서를 기억하는 운영체제 페이징 방식이다. 남는 메모리만큼 동시 요청을 더 받을 수 있고, 같은 프롬프트 앞부분의 블록을 여러 요청이 공유하는 프리픽스 캐싱도 가능해진다.

### 동시 사용자 수는 어떻게 정하나요?

문서 숫자로 정하지 않고 부하 테스트로 정한다. 실제 입력·출력 길이 분포를 흉내 낸 요청으로 동시 수를 올려 가며 첫 토큰 시간 p95, 토큰 간 지연, 전체 처리량을 함께 그린다. 지연 목표를 지키는 가장 높은 처리량 지점이 운영 상한이 된다. 대화형과 일괄 처리는 목표가 달라 분리하는 편이 낫다.

### Ollama를 그대로 사내 서비스로 써도 되나요?

한두 명이 쓰는 개발·시연에는 충분하지만, 많은 동시 요청을 처리하도록 설계된 엔진은 아니라서 사용자가 늘면 대기열이 길어진다. 기본 컨텍스트 길이가 짧게 잡혀 긴 문서가 조용히 잘리는 함정도 있다. 서비스로는 vLLM이나 SGLang 같은 엔진을 쓰고, 앞에 인증·한도·로그를 맡는 게이트웨이를 둔다. 테스트한 모델과 올린 모델의 양자화·채팅 템플릿이 같은지도 확인한다.

### 브라우저에서 모델을 돌리는 건 언제 맞나요?

임베딩, 분류, 작은 음성 인식처럼 수십~수백 MB 모델로 되는 일에 맞는다. 데이터가 기기를 떠나지 않고 서버 비용이 없으며 오프라인에서도 된다. 대신 첫 사용 때 모델 다운로드 시간이 있고 기기마다 성능 차이가 크며, 큰 생성 모델은 대부분의 기기에서 현실적이지 않다. Transformers.js는 WebGPU가 있으면 GPU를, 없으면 WebAssembly로 CPU를 쓴다.
