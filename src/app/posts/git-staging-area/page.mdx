<EasyIntro>
  파일에 함수를 추가하고 git add를 한 다음, 한 줄이 더 생각나서 마저 고치고 저장했다. 그런데 확인 삼아 git diff를 쳐 보니 방금 추가한 함수는 안 보이고 마지막 한 줄만 나온다. Git이 이상한 게 아니라 정확히 시킨 대로 한 것이다.

  Git에는 파일이 머무는 구역이 셋이다. 내가 고치는 실제 파일(작업 트리), 다음 커밋에 들어갈 사진의 초안(인덱스, 스테이징 영역), 그리고 이미 찍어 둔 사진들(저장소)이다. 단체 사진을 찍기 전에 사람들을 자리에 세우는 것과 같아서, git add는 "이 파일을 찍을 대상으로 표시해"가 아니라 "지금 이 순간의 파일 내용을 자리에 세워 둬"라는 명령이고, 그 뒤에 파일을 또 고치면 자리에 선 사람과 지금 내 앞의 사람이 달라진다.

  git diff는 자리에 선 것과 실제 파일의 차이를 보여 주니 마지막 한 줄만 나온 것이고, 옵션을 붙이면 자리에 선 것과 마지막 사진의 차이를 볼 수 있다. git status가 보여 주는 두 글자가 이 두 가지 차이를 한 번에 알려 준다. 커밋 직전에 "지금 자리에 뭐가 서 있나"를 보는 습관이 이런 실수를 막는다.
</EasyIntro>

`app.js`에 함수 하나를 추가하고 `git add app.js`를 쳤다. 커밋하기 전에 한 줄이 더 생각나서 `module.exports`를 붙이고 저장했다. 이제 커밋만 하면 된다고 생각하고 확인 삼아 `git diff`를 쳤는데, 방금 추가한 함수는 안 보이고 마지막에 쓴 한 줄만 나온다. `git status`에는 같은 파일이 "커밋할 변경"과 "커밋하지 않은 변경" 양쪽에 두 번 나온다. 이 상태에서 `git commit`을 치면 마지막 한 줄은 커밋에 들어가지 않는다.

이상해 보이지만 Git은 정확히 시킨 대로 했다. `git add`는 "이 파일을 커밋 대상으로 표시해"가 아니라 "지금 이 순간의 파일 내용을 따로 떠 둬"라는 명령이다. 그 뒤에 파일을 고치면 떠 둔 것과 디스크의 파일이 따로 논다. 이걸 이해하려면 Git이 파일을 어디에, 어떤 모양으로 저장하는지부터 봐야 한다.

Git이 파일 내용을 blob으로, 폴더를 tree로, 스냅샷을 commit으로 저장한다는 건 [앞 글](/posts/git-internals-basics)에서 객체를 직접 열어 보며 확인했다. 이 글은 그 객체들이 만들어지는 길을 따라간다. 작업 트리·인덱스·저장소라는 세 구역 사이에서 파일이 어떻게 옮겨 다니는지 보고, `git status`의 두 글자를 읽는 법, 변경 일부만 커밋하는 `git add -p`, 커밋한 뒤 히스토리를 읽는 명령까지 정리한다. 끝에서는 커밋 직전에 인덱스를 확인하는 습관이 현장에서 어떤 실수를 막는지 본다.

명령과 출력은 Ubuntu 24.04 LTS의 기본 패키지인 Git 2.43.0에서 실행한 것이다. 예제는 앞 글과 같은 `todo-app` 저장소이고, 첫 커밋까지는 이렇게 만든다.

```bash
# todo-app이라는 새 저장소를 만든다
git init todo-app
cd todo-app

# 파일 두 개를 만든다
printf "# todo-app\n" > README.md
printf "function add(a, b) {\n  return a + b;\n}\n" > app.js

# 두 파일을 인덱스에 올리고 커밋한다
git add README.md app.js
git commit -m "첫 커밋: README와 app.js"
```

```text
Initialized empty Git repository in /tmp/git-demo-1/todo-app/.git/
[main (root-commit) 2a8cce0] 첫 커밋: README와 app.js
 2 files changed, 4 insertions(+)

```

이 커밋에서 app.js의 blob은 `86eb6d1`, README.md의 blob은 `3a928f9`다. 앞 글에서 `git cat-file`로 열어 본 그 객체들이고, 아래 그림과 출력에 계속 나온다.

## 파일은 세 구역을 오간다

이제 처음 상황으로 돌아간다. Git에는 파일이 머무는 구역이 세 개 있다.

- 작업 트리(working tree): 에디터로 열어 고치는 실제 파일들.
- 인덱스(index): 다음 커밋에 들어갈 스냅샷의 초안. 스테이징 영역(staging area)이라고도 부른다. `.git/index` 파일 하나다.
- 저장소(repository): 커밋된 스냅샷들. HEAD가 가리키는 커밋이 마지막으로 찍은 사진이다.

`git add`는 작업 트리의 파일 내용을 blob으로 저장하고, 인덱스의 그 파일 항목이 새 blob을 가리키게 바꾼다. `git commit`은 인덱스를 그대로 tree로 만들어 커밋을 찍는다. 작업 트리는 쳐다보지도 않는다. 아래 그림에서 다음을 누르면 명령마다 세 구역의 app.js가 어느 blob을 가리키는지 바뀌는 게 보인다.

같은 상황을 명령으로 재현하면 이렇다.

```bash
# sub 함수를 추가하고 인덱스에 올린다
printf "function add(a, b) {\n  return a + b;\n}\n\nfunction sub(a, b) {\n  return a - b;\n}\n" > app.js
git add app.js

# 인덱스에 올린 뒤에 한 줄을 더 쓴다
printf "function add(a, b) {\n  return a + b;\n}\n\nfunction sub(a, b) {\n  return a - b;\n}\n\nmodule.exports = { add, sub };\n" > app.js

# 상태를 본다
git status
```

```text
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	modified:   app.js

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   app.js
```

`Changes to be committed`는 인덱스와 HEAD가 다르다는 뜻이고, `Changes not staged for commit`은 작업 트리와 인덱스가 다르다는 뜻이다. 한 파일이 양쪽에 다 나올 수 있다. 세 가지 diff로 각각을 확인한다.

```bash
# 작업 트리 ↔ 인덱스: 아직 add하지 않은 변경
git diff

# 인덱스 ↔ HEAD: 지금 커밋하면 들어갈 변경 (--cached와 같다)
git diff --staged
```

```text

--- a/app.js
+++ b/app.js
@@ -5,3 +5,5 @@ function add(a, b) {
```

두 출력의 `index` 줄을 보면 그림과 똑같다. 첫 번째는 `80cae42..4b52f4f`(인덱스 → 작업 트리), 두 번째는 `86eb6d1..80cae42`(HEAD → 인덱스)다. `@@ -5,3 +5,5 @@`는 원래 파일의 5번째 줄부터 3줄이 새 파일에서 5번째 줄부터 5줄이 됐다는 뜻이다.

인덱스 안을 직접 보는 명령도 있다. `git ls-files -s`는 인덱스에 들어 있는 파일마다 모드, blob 해시, 스테이지 번호, 경로를 보여 준다. 스테이지 번호는 평소엔 0이고, 병합 충돌 중에만 1·2·3이 나온다.

```bash
# 인덱스의 내용
git ls-files -s

# 인덱스에 올라간 버전의 파일 내용 (콜론 앞이 비면 인덱스)
git show :app.js
```

```text

100644 80cae42e4faff29c6ff21dcea21369e0fbe6cdb1 0	app.js

  return a + b;
}

```

인덱스는 "바뀐 파일 목록"이 아니라 다음 커밋의 전체 파일 목록이다. 바뀌지 않은 README.md도 들어 있다. 그래서 `git commit`은 작업 트리를 다시 훑을 필요 없이 인덱스만 보고 tree를 만든다.

처음 상황의 해결법은 둘 중 하나다. 마지막 한 줄까지 커밋에 넣고 싶으면 `git add app.js`를 한 번 더 하고 커밋한다. 수정한 파일 전체를 넣을 거라면 `git commit -a`(추적 중인 파일을 모두 add하고 커밋)를 쓴다. `-a`는 새로 만든 파일(untracked)은 넣지 않는다.

```bash
# 마지막 변경까지 인덱스에 올리고 커밋
git add app.js
git commit -m "모듈로 내보내기"
```

## 파일의 상태는 두 글자로 읽는다

`git status`의 긴 출력은 안내 문구가 많아서 매일 보기엔 길다. `-s`(short)를 붙이면 파일마다 두 글자로 줄여 준다. 첫 글자는 인덱스와 HEAD의 차이, 둘째 글자는 작업 트리와 인덱스의 차이다.

```bash
# 짧은 형식
git status -s

# 브랜치 정보까지 한 줄 더 (원격보다 앞섰는지, 뒤처졌는지)
git status -sb
```

```text
MM app.js

## main
 M app.js
```

자주 보는 조합은 이렇다.

- `??`: 추적하지 않는(untracked) 새 파일. Git이 아직 모른다.
- `A `: 새 파일을 인덱스에 올렸다.
- ` M`: 고쳤지만 아직 add하지 않았다.
- `M `: 고친 것을 add했다. 이대로 커밋하면 들어간다.
- `MM`: add한 뒤에 또 고쳤다. 처음 상황이 이것이다.
- `D ` / ` D`: 삭제를 인덱스에 반영했다 / 파일만 지웠다.
- `UU`: 병합 충돌 중인 파일.

파일 하나의 일생으로 보면 untracked → staged → committed(깨끗함) → modified → staged → committed를 오간다. `.gitignore`에 걸린 파일은 이 목록에 아예 나오지 않는다(ignored).

변경 중 일부만 커밋하고 싶을 때는 `git add -p`(patch)를 쓴다. 바뀐 덩어리(hunk)마다 넣을지 물어본다.

```bash
# 바뀐 덩어리마다 y(넣기) / n(건너뛰기) / s(더 잘게 쪼개기) / q(그만)를 고른다
git add -p app.js
```

`y`로 이 덩어리를 넣으면 app.js만 인덱스에 올라가고, 같이 고친 README.md는 작업 트리에 남는다. `git status -s`가 `M  app.js`와 ` M README.md`로 갈린다. 디버깅용 `console.log`는 빼고 기능만 커밋하거나, 한 파일에 섞인 두 가지 변경을 두 커밋으로 나눌 때 쓴다. 덩어리가 붙어 있어 `s`로 안 쪼개지면 `e`로 직접 고칠 수 있다.

## 커밋하고 히스토리를 읽는 명령

새 프로젝트는 `git init`, 이미 있는 저장소는 `git clone`으로 시작한다. 클론하면 원격 저장소가 `origin`이라는 이름으로 등록되고, 원격의 기본 브랜치가 로컬 브랜치로 체크아웃된다.

```bash
# 원격 저장소 복제 (보통은 https나 ssh 주소. 여기서는 로컬 경로)
git clone todo-app todo-clone
cd todo-clone

# 원격과 비교한 상태
git status -sb

# 로컬과 원격 추적 브랜치 목록
git branch -a

# 다시 원래 저장소로
cd ../todo-app
```

```text
Cloning into 'todo-clone'...
done.

## main...origin/main

* main
  remotes/origin/HEAD -> origin/main
  remotes/origin/feature/div
  remotes/origin/main
```

`remotes/origin/...`는 원격 브랜치가 마지막으로 어디 있었는지 기억해 둔 사본이다. 원격과 주고받는 이야기는 [원격 협업 글](/posts/git-remote-collaboration)에서 다룬다.

커밋 메시지는 `-m`으로 바로 쓰거나, 빼면 에디터가 열린다. `-v`를 붙이면 에디터 아래에 이번 커밋의 diff가 함께 나와서 무엇을 커밋하는지 보면서 메시지를 쓸 수 있다. 방금 한 커밋을 고치는 `--amend`는 [.gitignore 글](/posts/git-ignore-config)에서 직접 써 본다.

히스토리를 볼 때는 `git log`에 옵션을 붙여 필요한 것만 본다.

```bash
# 한 줄씩, 브랜치 갈래와 이름표까지, 모든 브랜치
git log --oneline --graph --decorate --all

# 마지막 커밋에서 바뀐 파일과 줄 수
git log --stat -1
```

```text
* d953796 (HEAD -> main) 라이선스 추가
| * deb48d4 (feature/div) div 함수
|/  
* b490154 mul 함수와 README 설명 추가
* 0cb225b 모듈로 내보내기
* 06e8251 sub 함수 추가
* 2a8cce0 첫 커밋: README와 app.js

commit d9537965efb063fab0b30321fc2052806082379a

Date:   Sat Oct 17 10:06:00 2026 +0900

    라이선스 추가

 LICENSE | 1 +
 1 file changed, 1 insertion(+)
```

`--graph`는 위가 최신이다. `*`는 커밋, `|`는 이어지는 갈래, `|/`는 옆 갈래가 그 아래 커밋에서 갈라져 나왔다는 표시다. `(HEAD -> main)`은 HEAD가 main을 가리키고 main이 이 커밋에 있다는 뜻이다. 매번 치기 길어서 별칭으로 등록해 두는 경우가 많다. 별칭은 [설정 글](/posts/git-ignore-config)에서 다룬다.

경로를 붙이면 그 파일을 바꾼 커밋만 보고, `-p`를 더하면 변경 내용까지 나온다. `--` 뒤에 경로를 쓰는 건 브랜치 이름과 파일 이름이 겹칠 때 헷갈리지 않게 하려는 것이다.

```bash
# README.md를 바꾼 마지막 커밋과 그 diff
git log -p -1 -- README.md
```

```text

Author: Jane <jane@example.com>
Date:   Sat Oct 17 10:04:00 2026 +0900

    mul 함수와 README 설명 추가

diff --git a/README.md b/README.md
index 3a928f9..fcb755c 100644
--- a/README.md
+++ b/README.md
@@ -1 +1,3 @@

+
+계산 함수 모음
```

무언가를 찾을 때 쓰는 옵션도 알아 두면 좋다.

```bash
# 코드에 "mul("이 처음 생기거나 없어진 커밋 (pickaxe)
git log --oneline -S"mul("

# 작성자로 거르기 (부분 일치)
git log --oneline --author=Jane

# 날짜로 거르기. "2 weeks ago" 같은 표현도 된다
git log --oneline --since="2026-10-17 10:03"

# 원하는 형식으로 출력
git log --format="%h %an %ad %s" --date=short
```

`-S`는 그 문자열이 나오는 횟수가 바뀐 커밋만 찾는다. "이 함수는 언제 생겼지", "이 설정값은 누가 지웠지"를 찾을 때 가장 빠르다. 줄 안에서 값만 바뀐 경우까지 찾으려면 정규식으로 diff를 훑는 `-G`를 쓴다. 특정 줄을 누가 마지막으로 바꿨는지는 `git blame -L 5,8 app.js`로 본다.

`git show`는 커밋 하나를 자세히 보거나, 특정 시점의 파일을 꺼낼 때 쓴다. `HEAD~1`은 HEAD의 부모, `HEAD~3`은 부모를 세 번 거슬러 간 커밋이다.

```bash
# 한 커밋의 메타데이터와 바뀐 파일
```

## git diff에 무엇과 무엇을 넣느냐

앞에서 본 세 diff는 인자가 없거나 하나였다. 인자가 없으면 작업 트리와 인덱스, `--staged`면 인덱스와 HEAD, 커밋을 하나 주면 작업 트리와 그 커밋이다. 커밋을 둘 주면 작업 트리와 인덱스는 빠지고 두 스냅샷만 비교한다. PR 리뷰 전에 "이 브랜치가 main과 무엇이 다른가"를 볼 때 쓰는 게 이 형태인데, 여기서 점 두 개와 세 개가 갈린다.

예제는 add 함수만 있는 커밋에서 갈라져, `feature/div`는 app.js에 div 함수를 넣었고 main은 그 사이 README.md에 라이선스 줄을 넣은 상태다.

```bash
# 두 브랜치 끝을 그대로 비교한다 (git diff main feature/div와 같다)
git diff --stat main..feature/div

# 갈라진 지점(merge base)부터 feature/div 끝까지만 비교한다
git diff --stat main...feature/div
```

```text
 README.md | 2 --
 app.js    | 6 +++++-
 2 files changed, 5 insertions(+), 3 deletions(-)

 app.js | 6 +++++-
 1 file changed, 5 insertions(+), 1 deletion(-)
```

`..`에서 README.md 두 줄이 지워진 것처럼 나온다. 브랜치에서 README를 건드린 적은 없다. main이 그 뒤에 넣은 줄이 feature/div 끝에는 없으니 끝과 끝을 비교하면 "지웠다"로 보일 뿐이다. `...`는 `git merge-base main feature/div`로 찾은 공통 조상과 feature/div 끝을 비교해서 브랜치가 실제로 한 일만 보여 준다. GitHub PR의 Files changed 탭이 보여 주는 것도 이쪽이다. 리뷰 전에 로컬에서 볼 때는 `...`를 쓴다.

헷갈리는 건 `git log`에서는 뜻이 다르다는 점이다.

```bash
# feature/div에는 있고 main에는 없는 커밋
git log --oneline main..feature/div

# 어느 한쪽에만 있는 커밋 (<는 왼쪽 main, >는 오른쪽 feature/div)
git log --oneline --left-right main...feature/div
```

```text
1027514 div 함수

< dc048ae 라이선스 표기
> 1027514 div 함수
```

log의 `..`는 "B에서 닿고 A에서 안 닿는 커밋", `...`는 양쪽 중 한쪽에서만 닿는 커밋이다. diff의 `..`는 두 끝 비교, `...`는 merge base부터라서 결과적으로 `git log A..B`와 짝이 맞는 건 `git diff A...B`다. 점 개수만 같다고 같은 뜻으로 외우면 틀린다.

출력 모양을 바꾸는 옵션은 범위와 함께 쓴다. `--stat`은 파일별 바뀐 줄 수, `--name-only`는 파일 이름만, `--name-status`는 이름 앞에 `M`·`A`·`D`를 붙인다. 스크립트로 바뀐 파일을 넘길 때는 `--name-only`가 편하다. 한 줄 안에서 몇 단어만 바뀌었다면 `--word-diff`가 줄 전체를 지우고 다시 쓴 것처럼 보여 주는 대신 바뀐 단어만 표시한다.

```bash
# 바로 앞 커밋과 비교하되 단어 단위로
git diff --word-diff HEAD~1 HEAD

# 두 커밋 사이에서 app.js만
git diff HEAD~2 HEAD -- app.js
```

```text
diff --git a/app.js b/app.js
index 3637735..b75c99e 100644
--- a/app.js
+++ b/app.js
@@ -3,7 +3,7 @@ function add(a, b) {
}

function div(a, b) {
  return {+b === 0 ? NaN :+} a / b;
}

module.exports = { add, div };
```

`{+...+}`가 새로 들어간 단어, `[-...-]`가 지워진 단어다. 문서나 긴 설정 줄을 고친 커밋을 볼 때 특히 편하다. 커밋 두 개 사이는 `HEAD~2 HEAD`처럼 해시나 상대 이름을 그대로 두 개 주면 되고, `--` 뒤에 경로를 붙이면 그 파일만 본다.

## 커밋 직전에 인덱스를 보는 습관

세 구역을 알면 현장에서 자주 나는 실수 하나가 설명된다. "분명 지웠는데 PR에 올라갔다"는 종류다. 디버깅하려고 `console.log`를 넣고 add해 둔 뒤, 에디터에서 그 줄을 지우고 저장했다. 다시 add하지 않으면 인덱스에는 여전히 `console.log`가 있고, 커밋은 그 인덱스를 찍는다. 에디터 화면만 보고는 절대 알 수 없다.

그래서 커밋 직전에는 작업 트리가 아니라 인덱스를 본다. 두 명령이면 충분하다. 아래는 새 파일 new.js를 add하고, todo.js를 add한 뒤 한 줄을 더 고친 상태에서 본 것이다.

```bash
# 브랜치 상태와 파일별 두 글자
git status -sb

# 지금 커밋하면 들어갈 파일과 줄 수
git diff --staged --stat
```

```text
## main
A  new.js
MM todo.js

 new.js  | 1 +
 todo.js | 1 +
 2 files changed, 2 insertions(+)
```

`MM`이 보이면 멈춘다. add한 뒤에 또 고쳤다는 뜻이라, 커밋에 들어갈 내용과 지금 에디터의 내용이 다르다. `git diff --staged`로 들어갈 내용을 직접 읽고, 맞으면 커밋하고 아니면 다시 add한다.

팀에서는 이 확인을 pre-commit 훅으로 자동화한다. 이때 훅이 무엇을 검사하는지가 중요하다. 아래 훅은 작업 트리 파일이 아니라 인덱스에 올라간 변경(`--cached`)에서 새로 추가된 줄을 본다.

```bash
# .git/hooks/pre-commit (실행 권한 필요: chmod +x)
#!/bin/sh
# 인덱스에 올라간 변경 중 새로 추가한 줄에 console.log가 있으면 커밋을 막는다
if git diff --cached -U0 | grep -q '^+.*console\.log'; then
  echo "pre-commit: 스테이징된 변경에 console.log가 있다"
  exit 1
fi
```

`console.log`가 든 app.js를 add한 다음 에디터에서 그 줄을 지우고 커밋하면 이렇게 된다.

```bash
# 작업 트리의 app.js에는 console.log가 없다
grep -c console.log app.js
git status -s

# 커밋을 시도한다
git commit -m "add 정리"

# 인덱스에 올라간 버전
git show :app.js
```

```text
0
MM app.js
pre-commit: 스테이징된 변경에 console.log가 있다
function add(a, b) {
  console.log(a, b);
  return a + b;
}
```

디스크의 파일만 검사하는 린트였다면 통과했을 커밋이다. 실제로 커밋될 내용은 `git show :app.js`의 것이다. lint-staged 같은 도구가 훅을 돌리기 전에 add하지 않은 변경을 잠시 치워 두고 인덱스 내용만 남기는 이유가 이것이다. 훅을 직접 짤 때 검사할 파일 목록은 인덱스에서 가져온다.

```bash
# 스테이징된 파일 중 추가(A)·복사(C)·수정(M)된 것만. 지운 파일은 검사할 필요가 없다
git diff --cached --name-only --diff-filter=ACM
```

```text
new.js
todo.js
```

훅을 저장소에 공유하고 관리하는 법은 [Git 훅 글](/posts/git-hooks)에서 다룬다. 훅은 `--no-verify`로 건너뛸 수 있으니 같은 검사를 CI에서도 한 번 더 돌린다.

## 커밋은 작업 트리가 아니라 인덱스를 찍는다

작업 트리에서 고친 내용은 `git add`로 인덱스에 떠 두어야 커밋에 들어가고, 커밋은 작업 트리가 아니라 인덱스를 찍는다. 처음의 `git diff`가 마지막 한 줄만 보여 준 이유는 그 명령이 작업 트리와 인덱스를 비교했기 때문이다. `git status -s`의 첫 글자는 인덱스와 HEAD, 둘째 글자는 작업 트리와 인덱스의 차이라서 `MM`을 보면 커밋될 내용과 화면의 내용이 다르다는 걸 바로 안다. 다음 글에서는 무엇을 아예 커밋하지 않을지 정하는 `.gitignore`와 설정을 본다.

## 면접에서 나올 만한 질문

### 스테이징 영역(인덱스)은 왜 있나요?

다음 커밋의 스냅샷을 미리 조립하는 곳이다. 작업 트리에 여러 변경이 섞여 있어도 `git add -p`로 일부만 골라 의미 있는 단위로 커밋을 나눌 수 있다. 내부적으로는 다음 커밋의 전체 파일 목록과 blob 해시, 파일 시각을 담은 `.git/index` 파일이라, 커밋할 때 작업 트리를 다시 해시하지 않고 바로 tree를 만들고 status도 빠르게 판단한다. 병합 충돌 중에는 파일마다 base·ours·theirs 세 버전을 스테이지 1·2·3으로 담는 역할도 한다.

### git add 후에 파일을 또 수정하면 커밋에는 어떤 내용이 들어가나요?

add한 시점의 내용만 들어간다. add는 그 순간의 내용을 blob으로 저장하고 인덱스가 그걸 가리키게 할 뿐이고, 커밋은 인덱스를 찍는다. 이후 수정은 작업 트리에만 있어서 `git status`에 같은 파일이 staged와 unstaged 양쪽에 나오고, `git diff`는 그 나중 수정만, `git diff --staged`는 커밋될 내용을 보여 준다. 다 넣으려면 다시 add하거나 `commit -a`를 쓴다.

### git diff, git diff --staged, git diff HEAD는 각각 무엇을 비교하나요?

`git diff`는 작업 트리와 인덱스, 즉 아직 add하지 않은 변경을 보여 준다. `git diff --staged`(`--cached`)는 인덱스와 HEAD, 즉 지금 커밋하면 들어갈 변경이다. `git diff HEAD`는 작업 트리와 HEAD를 바로 비교해서 add 여부와 상관없이 마지막 커밋 이후의 모든 변경을 보여 준다. 커밋 직전에는 `--staged`로 들어갈 내용을 확인하는 습관이 실수를 줄인다.

### git status -s에서 MM은 무슨 뜻인가요?

첫 글자는 인덱스와 HEAD의 차이, 둘째 글자는 작업 트리와 인덱스의 차이다. MM은 고친 것을 add한 뒤에 또 고쳤다는 뜻이라, 지금 커밋하면 add한 시점의 내용만 들어가고 나중 수정은 빠진다. `git diff --staged`로 들어갈 내용을, `git diff`로 빠질 내용을 확인한다.

### pre-commit 훅은 작업 트리를 검사해야 하나요, 인덱스를 검사해야 하나요?

인덱스다. 커밋은 인덱스를 찍으니 작업 트리 파일만 검사하면 add한 뒤 지운 디버그 코드가 그대로 커밋될 수 있다. 훅에서는 `git diff --cached`나 `git diff --cached --name-only --diff-filter=ACM`으로 스테이징된 변경을 보고, lint-staged처럼 add하지 않은 변경을 잠시 치워 두는 도구를 쓰기도 한다. 훅은 `--no-verify`로 건너뛸 수 있어서 CI에서 한 번 더 검사한다.

### git log -S와 -G는 어떻게 다른가요?

`-S문자열`은 그 문자열이 나오는 횟수가 바뀐 커밋, 즉 처음 생기거나 사라진 커밋만 찾는다. 함수가 언제 생겼는지, 설정값을 누가 지웠는지 찾을 때 빠르다. `-G정규식`은 diff에서 바뀐 줄이 정규식에 맞으면 다 찾아서, 줄 안에서 값만 바뀐 경우까지 잡는다.

### git diff A..B와 A...B는 어떻게 다른가요?

`A..B`는 두 끝 스냅샷을 그대로 비교하고, `A...B`는 두 브랜치의 merge base와 B를 비교한다. 그래서 A가 그 사이에 따로 바꾼 내용이 `..`에서는 B가 되돌린 것처럼 보이고, `...`에서는 B가 실제로 한 변경만 남는다. PR의 Files changed가 `...` 쪽이다. `git log`에서는 `A..B`가 B에만 있는 커밋, `A...B`가 한쪽에만 있는 커밋이라 뜻이 엇갈린다.
