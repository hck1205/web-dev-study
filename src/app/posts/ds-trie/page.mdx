단어 10만 개를 `Set`에 넣어 두었다. `words.has("apple")`은 눈 깜짝할 새 답한다. 그런데 "`pre`로 시작하는 단어가 하나라도 있나"를 물으니 방법이 없다. 해시 집합은 단어를 통째로 해시해서 흩어 놓기 때문에, 앞 세 글자가 같은 단어끼리 가까이 있지 않다. 결국 10만 개를 하나씩 꺼내 `startsWith`를 돌려야 한다.

이 글은 그 질문에 답하려고 만든 자료구조, 트라이(trie)를 면접 문제 쪽에서 본다. 트라이를 자동완성 서비스에 써서 노드마다 상위 k개를 적어 두는 이야기는 [검색어 자동완성 ①](/posts/sd-autocomplete-trie)에서 이미 했다. 여기서는 그보다 한 걸음 아래, 트라이를 직접 짜고 지우고, 와일드카드 검색과 Word Search II를 풀고, 메모리를 해시 집합·정렬 배열과 재어 비교한다. 자료구조 전체 지도는 [자료구조 한눈에 고르기](/posts/data-structures-overview)에 있다.

## 해시 집합이 대답하지 못하는 질문

먼저 숫자부터 본다. Node 22에서 영어 비슷한 가짜 단어 10만 개(평균 11.1글자)를 만들고, 접두사 여섯 개로 "이걸로 시작하는 단어가 있나"를 세 가지 방법으로 물었다.

```js
// 접두사로 시작하는 단어가 하나라도 있나
const viaSet = (p) => { for (const w of set) if (w.startsWith(p)) return true; return false; };
const viaTrie = (p) => { let n = trie; for (const ch of p) { n = n.c.get(ch); if (!n) return false; } return true; };
const viaSorted = (p) => {           // 정렬된 배열에서 p 이상인 첫 자리를 이진 탐색
  let lo = 0, hi = sorted.length;
  while (lo < hi) { const m = (lo + hi) >> 1; if (sorted[m] < p) lo = m + 1; else hi = m; }
  return lo < sorted.length && sorted[lo].startsWith(p);
};
```

```text
trie           0.36us/query [false,true,true,false,true,true]
sorted+binary  0.63us/query [false,true,true,false,true,true]
```

답은 셋 다 같다. 걸린 시간은 Set을 훑는 쪽이 질의당 1.4ms, 트라이가 0.36µs다. 3,800배쯤 차이가 난다. 없는 접두사(`zz`)일 때 Set은 끝까지 다 봐야 해서 특히 느리다.

눈여겨볼 줄은 세 번째다. 단어를 정렬해 두고 이진 탐색으로 접두사 자리를 찾으면 트라이와 거의 같은 속도가 나온다. 트라이가 접두사 질문의 유일한 답은 아니라는 뜻이다. 둘의 차이는 메모리와 "단어가 계속 바뀌는가"에서 갈리는데, 뒤에서 잰다.

## 넣고, 찾고, 접두사 묻기

면접에 가장 자주 나오는 형태가 LeetCode 208번 Implement Trie다. `insert`, `search`, `startsWith` 세 개를 만든다.

```js
class TrieNode {
  constructor() {
    this.children = new Map(); // 글자 → 자식 노드
    this.isEnd = false;        // 여기서 끝나는 단어가 있나
  }
}

class Trie {
  root = new TrieNode();
  insert(word) {
    let node = this.root;
    for (const ch of word) {
      if (!node.children.has(ch)) node.children.set(ch, new TrieNode()); // 없는 길만 새로 만든다
      node = node.children.get(ch);
    }
    node.isEnd = true;                                                   // 마지막 노드에 끝 표시
  }
  #walk(s) {                          // s를 따라 내려가 도착한 노드, 길이 끊기면 null
    let node = this.root;
    for (const ch of s) {
      node = node.children.get(ch);
      if (!node) return null;
    }
    return node;
  }
  search(word) { return this.#walk(word)?.isEnd === true; } // 끝 표시까지 있어야 단어
  startsWith(prefix) { return this.#walk(prefix) !== null; } // 길만 있으면 된다
}

const t = new Trie();
for (const w of ["apple", "app", "apply", "bat"]) t.insert(w);
console.log(t.search("app"), t.search("appl"), t.startsWith("appl"), t.search("ba"), t.startsWith("c"));
```

```text
true false true false false
```

`appl`은 길은 있지만 끝 표시가 없어서 `search`는 `false`, `startsWith`는 `true`다. 두 메서드의 차이는 이 끝 표시 하나다.

## 해시 집합도 사실 O(L)이다

여기서 꼬리 질문이 자주 온다. "그럼 트라이 `search`가 해시 집합의 `has`보다 빠른가요?"

아니다. `Set.has(word)`도 단어 전체를 읽어 해시를 계산해야 하니 문자열 길이 L에 비례한다. 둘 다 O(L)이다. 실제로는 해시 쪽이 대개 더 빠르다. 연속된 메모리의 문자열을 한 번 훑는 일이, 노드 L개를 포인터로 건너 다니는 일보다 CPU 캐시에 훨씬 잘 맞는다. 정확히 일치하는 단어 찾기만 필요하면 트라이를 고를 이유가 없다.

트라이가 이기는 곳은 질문이 접두사 모양일 때다. "이걸로 시작하는 단어가 있나", "이걸로 시작하는 단어를 전부 다오", "이 문자열의 접두사 중 사전에 있는 가장 긴 것은", "한 글자씩 읽어 가며 사전과 맞춰 보기". 마지막 두 가지는 해시 집합으로 하려면 접두사를 하나하나 잘라서 다 물어봐야 한다. 트라이는 한 번 내려가면서 전부 답한다.

## 끝 표시를 잊으면 생기는 일

가장 흔한 실수는 `search`를 `startsWith`처럼 짜는 것이다. 경로만 있으면 단어라고 답해 버린다.

```js
// isEnd를 보지 않은 search: 경로만 있으면 단어라고 답한다
class BrokenTrie extends Trie { search(w) { return this.startsWith(w); } }
const b = new BrokenTrie();
b.insert("apple");
console.log("broken search('app'):", b.search("app"));
```

```text
broken search('app'): true
```

`apple`만 넣었는데 `app`이 있다고 한다. 금칙어 목록이라면 멀쩡한 단어를 막고, 사전이라면 없는 단어를 맞다고 한다. 반대 방향의 실수도 있다. 끝 표시를 "자식이 없는 노드"로 판단하면, `apple`이 들어간 뒤의 `app`처럼 중간에서 끝나는 단어를 놓친다. 끝은 자식 유무와 상관없이 따로 기록해야 한다.

## 점 하나가 길을 여러 개로 가른다

LeetCode 211번 Add and Search Word는 검색어에 `.`을 허용한다. `.`은 아무 글자 하나다. `.ad`는 `bad`, `dad`, `mad` 무엇이든 맞는다.

일반 글자는 자식 하나로 내려가면 되지만, `.`을 만나면 그 노드의 자식 전부를 시도해야 한다. 그래서 재귀 DFS(깊이 우선 탐색, 한 갈래를 끝까지 가 본 뒤 돌아오는 방식)로 짠다.

```js
search(word) {
  this.visits = 0;
  const dfs = (n, i) => {
    this.visits++;
    if (i === word.length) return n.end;          // 다 읽었으면 끝 표시를 본다
    const ch = word[i];
    if (ch !== ".") { const nx = n.c.get(ch); return nx ? dfs(nx, i + 1) : false; }
    for (const nx of n.c.values()) if (dfs(nx, i + 1)) return true; // 갈림길: 자식 전부 시도
    return false;
  };
  return dfs(this.root, 0);
}
```

`bad`, `dad`, `mad`, `pad` 네 개를 넣고 여러 검색어로 방문한 노드 수를 셌다.

```text
pad   true visits=4
bad   true visits=4
.ad   true visits=4
b..   true visits=4
..d   true visits=4
b.    false visits=3
...   true visits=4
....  false visits=13
```

맞는 단어가 있으면 첫 갈래에서 바로 찾아 방문이 4로 끝난다. 마지막 줄 `....`가 문제다. 네 글자 단어가 없으니 모든 갈래를 끝까지 가 보고서야 `false`를 낸다. 13개 노드를 다 돌았다.

```js
  if (!node) return;                          // 이 글자로 이어지는 단어가 없다: 가지치기
  if (node.word) { out.push(node.word); node.word = null; } // 찾은 단어는 지워 중복을 막는다
  board[r][c] = "#";                          // 지금 밟은 칸 표시
  for (const [dr, dc] of [[1,0],[-1,0],[0,1],[0,-1]]) {
    const nr = r + dr, nc = c + dc;
    if (nr >= 0 && nr < R && nc >= 0 && nc < C && board[nr][nc] !== "#") dfs(nr, nc, node);
  }
  board[r][c] = ch;                           // 돌아올 때 되돌린다
  if (Object.keys(node.c).length === 0 && !node.word) delete parent.c[ch]; // 다 찾은 가지는 잘라 낸다
};
for (let r = 0; r < R; r++) for (let c = 0; c < C; c++) dfs(r, c, root);
```

끝 노드에 `true` 대신 단어 문자열을 적어 두는 게 요령이다. 그러면 지나온 글자를 따로 모으지 않아도 된다. 찾은 단어를 `null`로 지우는 건 같은 단어가 판 여러 곳에서 만들어질 때 결과에 두 번 들어가지 않게 하려는 것이다.

예제 판과, 무작위 12×12 판에 단어 5,000개를 넣은 경우를 단어마다 따로 찾는 방식과 비교했다.

```text
{ out: [ 'oath', 'eat' ], calls: 41 }
{ out: [ 'oath', 'eat' ], calls: 57 }
trie   found=64 dfsCalls=1811 31.4ms
naive  found=64 dfsCalls=889993 30.1ms
trie   warm avg 6.7ms
naive  warm avg 16.6ms
```

DFS 호출 수는 1,811번과 88만 9,993번으로 490배 차이다. 그런데 시간은 첫 실행에서 거의 같고, 데운 뒤에도 6.7ms와 16.6ms로 2.5배다. 트라이를 만드는 시간만 따로 재 보니 5.4ms였다. 판이 작으면 탐색보다 트라이 만들기가 더 비싸다. 판이 커지거나 같은 단어 목록으로 판을 여러 번 검사하면 트라이를 한 번 만들고 재사용하는 쪽이 크게 이긴다. 복잡도와 함께 이런 고정 비용이 어디서 드는지까지 말할 수 있어야 한다.

마지막 줄 `delete parent.c[ch]`가 꼬리 질문으로 자주 나온다. 단어를 다 찾은 가지를 트라이에서 잘라 내면, 이후 다른 칸에서 출발한 DFS가 같은 접두사로 들어오지 않는다. 남은 단어가 적어질수록 탐색이 빨라진다.

## 단어를 지울 때는 빈 가지까지 치운다

삭제는 면접에서 덜 나오지만, 나오면 많이 막힌다. 끝 표시만 내리면 동작은 맞는다. 하지만 아무 단어에도 쓰이지 않는 노드가 남아 메모리를 계속 차지하고, `startsWith`가 사라진 단어의 접두사에 `true`를 답한다.

그래서 재귀로 내려갔다가 올라오면서, 자식도 없고 끝 표시도 없는 노드를 부모에서 떼어 낸다.

```js
// 지운 뒤 자식도 없고 단어 끝도 아닌 노드는 부모에서 떼어 낸다
function remove(n, w, i = 0) {
  if (i === w.length) { if (!n.end) return false; n.end = false; return n.c.size === 0; }
  const nx = n.c.get(w[i]);
  if (!nx) return false;                                   // 없는 단어
  if (remove(nx, w, i + 1)) { n.c.delete(w[i]); return !n.end && n.c.size === 0; }
  return false;
}
```

```text
remove app nodes= 1
```

## 노드 하나가 생각보다 무겁다

트라이의 대가는 메모리다. 단어 10만 개(글자 합 110만 개)로 세 가지 구조를 만들고 `--expose-gc`로 가비지 컬렉션을 돌린 뒤 늘어난 힙을 쟀다. 단어 문자열 자체는 이미 메모리에 있으니, 그 위에 구조가 더 쓰는 양이다.

```text

trie(Map)          build=600ms heap=+125.8MB
trie(Array 26)     build=520ms heap=+165.5MB
```

`Set`은 단어 문자열을 가리키는 칸만 더 쓰니 2.6MB다. 트라이는 노드가 58만 6,247개 생겼고 126MB를 썼다. 노드 하나에 200바이트쯤이다. 노드마다 객체 하나와 `Map` 하나가 붙고, `Map`은 비어 있어도 내부 해시 테이블을 갖는다. 글자 하나를 저장하려고 그만큼을 쓰는 셈이다.

자식을 길이 26짜리 배열로 두는 고전적인 방법은 더 무겁다. 165MB다. 글자를 `charCodeAt(i) - 97`로 바로 칸 번호로 바꿔 찾으니 해시 계산이 없어 빠르지만, 대부분의 노드는 자식이 한두 개뿐이라 나머지 24칸이 `null`로 비어 있다. C나 Java로 푸는 코딩 테스트에서는 이 방식이 흔한데, 자바스크립트에서는 `Map`이나 객체가 더 낫다.

이 숫자를 보면 처음의 정렬 배열이 다시 보인다. 0.8MB로 트라이와 비슷한 접두사 속도를 냈다. 단어 목록이 한 번 만들고 잘 바뀌지 않는다면(사전, 금칙어 목록, 배포 때 굽는 라우트 목록) 정렬 배열과 이진 탐색이 더 싸다. 단어가 계속 들어오고 빠진다면 정렬 배열은 끼워 넣을 때마다 뒤를 밀어야 해서 O(n)이고, 트라이는 O(L)이다.

## 글자를 어떻게 자르느냐

자식 키를 정할 때 "글자 하나"가 생각보다 단순하지 않다. 자바스크립트 문자열의 `length`와 `str[i]`는 UTF-16 코드 단위 기준이라, 이모지처럼 기본 다국어 평면 밖의 문자는 두 칸으로 쪼개진다.

```js
const w = "cat😺";
console.log(w.length, [...w].length);
const byIndex = []; for (let i = 0; i < w.length; i++) byIndex.push(w[i]);
console.log(JSON.stringify(byIndex));
console.log(JSON.stringify([...w]));
console.log("Z".charCodeAt(0) - 97, "é".charCodeAt(0) - 97);
```

```text
["c","a","t","\ud83d","\ude3a"]
["c","a","t","😺"]

```

인덱스로 자르면 😺가 짝 없는 반쪽 두 개로 들어간다. 넣을 때와 찾을 때 같은 방식으로 자르면 검색은 맞지만, 트라이 안의 단어를 다시 꺼내 보여 주거나 접두사를 잘라 응답에 실을 때 깨진 문자가 나온다. `for...of`나 스프레드는 코드 포인트 단위라 안전하다.

마지막 줄은 26칸 배열 트라이가 영어 소문자 밖의 입력을 만났을 때다. `Z`는 -7, `é`는 136이 된다. 자바스크립트 배열에 `arr[-7] = node`를 하면 에러 없이 `"-7"`이라는 속성으로 들어가 버려서, 버그가 조용히 숨는다. 입력 범위를 정했으면 넣기 전에 소문자로 바꾸고 범위를 검사해야 한다. 한글을 다루는 트라이라면 음절과 자모 중 무엇을 키로 쓸지부터 정해야 하는데, 그 이야기는 자동완성 글의 한글 절에 있다.

## 트라이를 고를 때와 고르지 않을 때

정확히 일치하는지만 보면 해시 집합이 메모리도 적고 빠르다. 단어 목록이 고정이고 접두사 범위만 찾으면 정렬 배열과 이진 탐색이 메모리를 100분의 1로 쓴다. 트라이는 접두사 질문이 많고 목록이 계속 바뀔 때, 또는 Word Search II처럼 탐색 도중 매 글자마다 "아직 가망이 있나"를 물어야 할 때 고른다.

글 여러 개를 한 번에 거르는 금칙어 필터처럼, 긴 본문에서 사전 단어 수천 개가 어디 나오는지 한 번에 찾으려면 트라이에 실패 링크를 더한 아호-코라식(Aho-Corasick) 알고리즘을 쓴다. 본문을 한 번만 읽으면서 모든 단어를 찾는다. 이 글의 범위는 넘어서니 이름만 알아 둔다.

트라이 다음으로는 같은 "나무를 따라 내려가는" 구조인 [이진 탐색 트리](/posts/ds-binary-tree-bst)와, 트라이 위에서 돌린 DFS를 일반 그래프로 넓힌 [그래프와 BFS·DFS](/posts/ds-graph-bfs-dfs)를 이어서 보면 좋다.

## 면접에서 나올 만한 질문

### 트라이는 무엇이고 언제 쓰나요?

문자열을 글자 단위 경로로 저장하는 나무로, 같은 접두사를 가진 단어가 길을 공유한다. 접두사로 시작하는 단어가 있는지, 그런 단어를 전부 꺼내기, 가장 긴 접두사 찾기처럼 질문이 접두사 모양일 때 쓴다. 정확히 일치만 확인하면 해시 집합이 더 낫다.

### insert, search, startsWith의 시간 복잡도는요?

셋 다 단어 길이가 L일 때 O(L)이고, 저장된 단어 수와는 상관없다. 글자마다 자식 하나로 내려가고 자식 찾기는 해시 맵이나 배열 인덱스라 상수 시간이다. search와 startsWith의 차이는 마지막 노드에 끝 표시가 있어야 하느냐 하나다.

### 해시 집합의 has도 O(1)인데 트라이가 왜 필요한가요?

해시 집합의 has도 문자열 전체를 해시해야 하니 실제로는 O(L)이고, 연속 메모리를 읽어서 트라이보다 대개 빠르다. 대신 해시는 단어를 흩어 놓기 때문에 접두사 질문에 답하려면 전부 훑어야 한다. 10만 단어에서 접두사 확인이 Set 훑기로 1.4ms, 트라이로 0.36µs였다.

### 트라이의 공간 복잡도와 줄이는 방법은요?

최악에 글자 수 합만큼 노드가 생기고, 노드마다 자식 컨테이너가 붙어 무겁다. Node에서 10만 단어가 노드 58만 개, 126MB를 썼고 Set은 2.6MB였다. 자식이 하나뿐인 길을 합치는 래딕스 트리로 노드를 줄이거나, 목록이 고정이면 정렬 배열과 이진 탐색으로 바꾼다.

### '.' 와일드카드 검색은 어떻게 하고, 최악의 복잡도는요?

일반 글자는 자식 하나로, 점은 자식 전부로 갈라지는 DFS로 찾는다. 점이 k개면 최악에 알파벳 크기의 k제곱만큼 갈래가 생겨 영어 소문자는 26^k다. 맞는 단어가 없을 때가 가장 느리므로 입력에 점 개수나 길이 제한을 두는 게 안전하다.

### Word Search II에서 트라이가 왜 유리한가요?

단어마다 판 전체를 DFS하는 대신, 단어 목록을 트라이 하나로 묶고 판을 한 번 훑으며 지금 경로가 어떤 단어의 접두사인지 동시에 확인한다. 접두사가 아니면 즉시 갈래를 버린다. 측정에서 DFS 호출이 89만 번에서 1,811번으로 줄었고, 다 찾은 가지를 트라이에서 잘라 내면 더 줄어든다.

### 트라이에서 단어를 지울 때 주의할 점은요?

끝 표시만 내리면 쓰이지 않는 노드가 남아 메모리를 차지하고 startsWith가 틀린 답을 낸다. 재귀로 내려갔다 올라오면서 자식도 없고 끝 표시도 없는 노드를 부모에서 떼어 내고, 다른 단어의 끝이거나 다른 자식이 있는 노드에서 멈춘다.
