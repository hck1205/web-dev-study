배송 예정일을 보여 주던 앱이 어느 날 주문 상세 화면에 들어가자마자 꺼진다. 앱은 2주 동안 배포한 적이 없다. 원인은 백엔드에 있었다. 응답 필드 이름을 정리하는 PR이 `deliveryEta`를 `estimatedDelivery`로 바꿨고, 앱은 `order.deliveryEta.split("-")`를 하다가 `undefined`에서 터졌다.

양쪽 다 테스트는 있었다. 백엔드의 단위 테스트는 필드 이름을 함께 고쳐서 통과했다. 앱의 테스트는 미리 저장해 둔 응답 JSON 파일을 썼으니 예전 이름 그대로 통과했다. 각자는 맞았고, 둘이 만나는 자리에서 틀렸다. 이 자리를 확인하는 게 API 테스트다.

이 글은 API 테스트가 단위·통합·E2E 사이에서 맡는 자리, 응답에서 무엇을 확인할지, Postman 컬렉션을 Newman으로 CI에서 돌리는 법, JSON Schema로 응답 모양을 고정하는 법, REST Assured·Karate 같은 코드 기반 도구, 테스트끼리 데이터를 넘기지 않는 법, 인증 토큰과 외부 API 다루기, 그리고 배포 전에 호환성을 확인하는 소비자 주도 계약 테스트를 다룬다. 예제는 Node 22.22로 띄운 작은 주문 API에 Newman 6.2와 Ajv 8.17로 돌렸다.

## API 테스트가 서는 자리

[테스트 피라미드](/posts/test-pyramid-unit-tests#피라미드와-트로피가-다투는-것)로 보면 API 테스트는 통합 테스트 층의 위쪽, E2E 바로 아래다. 서버를 실제로 띄우고 HTTP로 부른다. 화면은 거치지 않는다.

이 층이 따로 값을 하는 이유는 단위 테스트가 못 보는 것이 여기서 처음 진짜가 되기 때문이다. 라우팅, 인증 미들웨어, 요청 본문 파싱, 응답 직렬화(날짜가 문자열로 어떻게 나가는지, `BigInt`나 `undefined` 필드가 어떻게 되는지), 상태 코드와 헤더. 필드 이름 변경 사고도 직렬화된 응답을 보는 이 층에서 잡힌다.

E2E보다 나은 점은 속도와 원인 찾기다. 브라우저를 띄우지 않으니 요청 하나에 수십 밀리초면 끝나고, 실패하면 어떤 요청의 어떤 필드가 틀렸는지 바로 보인다. 화면이 바뀌어도 깨지지 않는다. 그래서 업무 규칙의 조합(쿠폰 경계값, 권한별 응답)은 API 층에서 넓게 돌리고, E2E는 화면을 꼭 거쳐야 하는 핵심 흐름 몇 개로 줄이는 구성이 흔하다.

한계도 분명하다. API 테스트는 우리 서버를 기준으로 쓴다. 앱이 그 응답에서 무엇을 쓰는지는 모른다. 백엔드가 자기 API 테스트에서 `estimatedDelivery`를 확인하도록 고치면 그 테스트도 통과한다. 그래서 이 글 뒷부분의 계약 테스트가 필요해진다.

## 응답에서 무엇을 확인하나

"200이 오면 통과"인 API 테스트가 많다. 사고 난 응답도 200이었다. 확인할 것을 층으로 나눠 보면 이렇다.

상태 코드는 기본이다. 정상 경로만이 아니라 실패 경로도 확인한다. 잘못된 본문에 400(또는 422), 토큰이 없으면 401, 남의 주문이면 403이나 404, 없는 주문이면 404. 실패 경로가 500을 내면 그게 버그다. 남의 주문을 403으로 막을지 404로 숨길지는 정책인데, 어느 쪽이든 테스트로 못 박아 둔다. 정상 응답은 맞는데 권한 검사가 빠진 API가 운영에서 가장 비싼 버그다.

헤더는 `Content-Type`, 캐시 헤더(`Cache-Control`), 페이지네이션 링크, CORS 헤더, 그리고 새로 만든 자원의 `Location` 같은 것이다. 본문은 값과 모양을 따로 본다. 값은 "주문 금액이 24,000원"처럼 업무 규칙을, 모양은 "필수 필드가 있고 타입이 맞다"를 본다. 모양은 다음 절의 JSON Schema가 맡는다.

응답 시간도 확인할 수 있지만 조심해서 쓴다. CI 러너는 공유 자원이라 같은 요청도 매번 다르게 걸린다. 500ms 같은 넉넉한 상한으로 "갑자기 몇 초씩 걸리는 사고"만 잡고, 실제 성능 판단은 부하 테스트와 운영 지표로 한다. 빡빡한 시간 단언은 플레이키 테스트를 만드는 지름길이다.

마지막으로 부작용이다. POST가 201을 돌려줬다고 주문이 저장된 건 아니다. 같은 API로 다시 조회해서 확인하거나, 그레이박스로 DB를 들여다본다. 같은 요청을 두 번 보냈을 때 주문이 하나만 생기는지(멱등성)도 결제·주문 API라면 꼭 넣는다.

## Postman 컬렉션을 CI에서 돌린다

Postman은 API를 손으로 불러 보는 도구로 시작하지만, 요청을 묶은 컬렉션에 테스트 스크립트를 붙이면 그대로 자동화가 된다. Newman은 그 컬렉션을 명령줄에서 돌리는 실행기다. Postman에서 컬렉션과 환경을 JSON으로 내보내 저장소에 넣고, CI에서 Newman으로 돌린다.

주문 조회 요청에 붙인 테스트 스크립트다. Postman의 `pm` 객체로 쓴다.

```js
// "주문 조회" 요청의 Tests 탭
const schema = {
  type: "object",
  required: ["id", "status", "amount", "deliveryEta"],
  properties: {
    id: { type: "string" }, status: { type: "string" }, deliveryEta: { type: "string" },
    amount: { type: "object", required: ["value", "currency"],
              properties: { value: { type: "number" }, currency: { type: "string" } } },
  },
};
pm.test("200 OK", () => pm.response.to.have.status(200));
pm.test("JSON 응답이다", () => pm.response.to.have.header("Content-Type", "application/json"));
pm.test("스키마를 지킨다", () => pm.response.to.have.jsonSchema(schema));
pm.test("500ms 안에 응답한다", () => pm.expect(pm.response.responseTime).to.be.below(500));
```

컬렉션에는 요청이 셋 있다. 주문을 만들고, 만든 주문을 조회하고, 토큰 없이 조회해서 401을 확인한다. 토큰은 컬렉션 단위의 사전 스크립트에서 받아 온다(뒤에서 다시 본다).

## 스키마로 응답의 모양을 고정한다

필드마다 `pm.expect(...).to.be.a("string")`를 쓰면 금방 지친다. JSON Schema는 응답의 모양을 선언으로 적는다. 필수 필드, 타입, 허용 값, 형식(날짜, 이메일), 숫자 범위. Postman도 내부에서 Ajv라는 검증기를 쓴다. 코드 테스트에서는 Ajv를 직접 쓴다.

```js
import Ajv from "ajv";
import addFormats from "ajv-formats";

const ajv = new Ajv({ allErrors: true });   // 첫 오류에서 멈추지 않고 모두 모은다
addFormats(ajv);                             // "date" 같은 format 검사를 켠다

const orderSchema = {
  type: "object",
  required: ["id", "status", "amount", "deliveryEta"],
  properties: {
    id: { type: "string", pattern: "^ord_" },
    status: { enum: ["PAID", "SHIPPED", "CANCELLED"] },
    amount: {
      type: "object",
      required: ["value", "currency"],
      properties: { value: { type: "integer", minimum: 0 }, currency: { const: "KRW" } },
    },
    deliveryEta: { type: "string", format: "date" },
  },
};

const validate = ajv.compile(orderSchema);
const res = { id: "ord_1000", status: "PAID",
              amount: { value: "24000", currency: "KRW" }, estimatedDelivery: "2026-10-25" };
console.log(validate(res));
console.log(validate.errors.map((e) => `${e.instancePath || "/"} ${e.message}`).join("\n"));
```

```text
false
/ must have required property 'deliveryEta'
/amount/value must be integer
```

`allErrors: true`라서 두 문제가 함께 나왔다. 금액이 문자열로 바뀐 것도 앱을 깨뜨리는 변경이다. JavaScript 앱에서 `"24000" + 3000`은 `"240003000"`이 된다.

스키마를 쓸 때 정할 게 하나 있다. 모르는 필드를 허용할까. `additionalProperties: false`를 걸면 새 필드가 하나만 생겨도 테스트가 깨진다. 제공자 쪽에서 "문서에 없는 필드를 실수로 내보내지 않는다"를 확인할 때는 쓸 만하다. 하지만 소비자 쪽 테스트라면 걸지 않는다. 응답에 필드가 추가되는 건 안전한 변경이고, 소비자는 자기가 쓰는 필드만 보고 나머지는 무시하는 게 오래 버티는 방식(관대한 독자, tolerant reader)이다. 어떤 변경이 안전하고 어떤 게 깨는지는 [API 버전 관리](/posts/api-versioning#추가했을-뿐인데-깨지는-이유)에 정리했다.

스키마를 손으로 따로 쓰면 문서와 어긋난다. OpenAPI 명세가 있다면 응답 스키마를 거기서 가져온다. OpenAPI 3.1의 스키마는 JSON Schema 2020-12와 맞춰져 있어 그 버전을 읽는 검증기(Ajv라면 `ajv/dist/2020`)에 넣을 수 있다. 3.0은 `nullable` 같은 자체 문법이 있어 변환이 필요하다. 명세가 원천이 되면 "문서는 이렇게 말하는데 서버는 다르게 준다"가 테스트에서 걸린다.

## 직접 해 보기: 응답 모양 검사기

스키마 검증기가 하는 일의 뼈대를 직접 만들어 본다. `shape`는 기대하는 모양이다. 값이 `"string"`, `"number"` 같은 타입 이름이면 그 타입이어야 하고, 객체면 그 안의 키를 하나씩 확인하고, `[모양]`처럼 원소가 하나인 배열이면 배열의 모든 원소가 그 모양이어야 한다. 오류는 `$.amount.value: expected number, got string`이나 `$.deliveryEta: missing` 형식의 문자열 배열로 돌려준다. `shape`에 없는 필드는 무시한다(관대한 독자). `null`은 `null`, 배열은 `array`로 부른다.

<CodePlayground
  caption="응답이 기대한 모양인지 확인하기"
  functionName="checkShape"
  initialCode={`function checkShape(shape, value, path = "$") {
  // 오류 메시지 배열을 돌려준다. 문제가 없으면 []
  return [];
}`}
  solution={`function checkShape(shape, value, path = "$") {
  const kind = (v) => (v === null ? "null" : Array.isArray(v) ? "array" : typeof v);
  if (typeof shape === "string") {
    return kind(value) === shape ? [] : [path + ": expected " + shape + ", got " + kind(value)];
  }
  if (Array.isArray(shape)) {
    if (!Array.isArray(value)) return [path + ": expected array, got " + kind(value)];
    return value.flatMap((item, i) => checkShape(shape[0], item, path + "[" + i + "]"));
  }
  if (kind(value) !== "object") return [path + ": expected object, got " + kind(value)];
  return Object.keys(shape).flatMap((key) =>
    value[key] === undefined
      ? [path + "." + key + ": missing"]
      : checkShape(shape[key], value[key], path + "." + key)
  );
}`}

## 코드로 쓰는 API 테스트

테스트가 많아지고 개발자가 주로 쓴다면 코드 기반 도구가 낫다. 리뷰가 쉽고, 공통 코드를 함수로 빼고, 서버 코드와 같은 저장소에서 같이 고친다.

JVM 진영에서는 REST Assured가 오래 쓰였다. given-when-then 모양의 체이닝으로 쓴다.

```java
// REST Assured + JUnit 5
import static io.restassured.RestAssured.given;
import static io.restassured.module.jsv.JsonSchemaValidator.matchesJsonSchemaInClasspath;
import static org.hamcrest.Matchers.*;

@Test
void 주문_상세를_조회한다() {
    given()
        .auth().oauth2(token)
    .when()
        .get("/orders/{id}", orderId)
    .then()
        .statusCode(200)
        .contentType("application/json")
        .body("amount.value", equalTo(24000))
        .body(matchesJsonSchemaInClasspath("schemas/order.json"))
        .time(lessThan(500L));
}
```

Karate는 테스트를 Gherkin 비슷한 문법으로 쓰는 도구다. Java 위에서 돌지만 테스트 작성자는 Java를 몰라도 된다. 응답 모양을 `#string`, `#number` 같은 표기로 바로 비교하는 게 특징이다.

```gherkin
Feature: 주문 조회

  Background:
    * url baseUrl
    * header Authorization = 'Bearer ' + token

  Scenario: 주문 상세는 약속한 모양으로 온다
    Given path 'orders', orderId
    When method get
    Then status 200
    And match response == { id: '#string', status: '#string', deliveryEta: '#string', amount: { value: '#number', currency: 'KRW' } }
```

Karate의 `match ==`는 기본적으로 응답 전체가 같아야 해서 모르는 필드가 생기면 실패한다. 소비자 입장의 검사라면 `match response contains`로 쓰는 쪽이 관대한 독자에 맞는다.

Node 진영이라면 전용 도구 없이 테스트 러너에 `fetch`와 Ajv를 붙이는 것만으로 충분한 경우가 많다. [스모크 테스트](/posts/smoke-sanity-regression-testing#연기가-나는지부터-본다)에서 쓴 방식 그대로다. 서버를 테스트 안에서 직접 띄우는 통합 테스트라면 supertest처럼 포트 없이 앱 객체에 요청을 보내는 도구도 쓴다. 도구 선택은 누가 테스트를 쓰고 고치느냐로 정한다. QA가 GUI로 관리한다면 Postman, 개발자가 서버 코드 옆에서 고친다면 서버와 같은 언어의 코드 기반 도구가 오래 간다.

## 테스트끼리 데이터를 넘기지 않는다

위 Postman 컬렉션에는 사실 냄새가 하나 있다. "주문 생성"이 만든 주문 id를 컬렉션 변수에 넣고, "주문 조회"가 그걸 꺼내 쓴다.

```js
// "주문 생성"의 Tests 탭
pm.collectionVariables.set("orderId", pm.response.json().id);
```

Postman에서 흔히 쓰는 방식이고, 위에서 아래로 한 번 도는 시나리오라면 편하다. 문제는 테스트가 서로에게 기대게 된다는 것이다. 주문 생성이 실패하면 뒤의 조회 테스트들이 모두 엉뚱한 이유로 실패한다(빨간불 여러 개 중 진짜 원인은 하나다). 조회 테스트만 따로 돌릴 수 없고, 순서를 바꾸거나 병렬로 돌릴 수도 없다.

기준은 "이 테스트 하나만 돌려도 통과하나"다. 조회를 확인하는 테스트라면 자기가 쓸 주문을 자기가 준비한다. 앞의 API로 만들든, 테스트 데이터 API나 DB 시드로 넣든.

```js
// node:test로 쓴 API 테스트. 각 테스트가 자기 데이터를 만든다
async function createOrder(items = [{ sku: "A-1", price: 12000, qty: 2 }]) {
  const res = await api("POST", "/orders", { items });
  assert.equal(res.status, 201);
  return res.json();
}

test("주문 상세는 약속한 모양으로 온다", async () => {
  const order = await createOrder();
  const res = await api("GET", `/orders/${order.id}`);
  assert.equal(res.status, 200);
  assert.ok(validate(await res.json()), ajv.errorsText(validate.errors));
});
```

공유 환경(스테이징)에서 돌린다면 데이터 이름도 겹치지 않게 한다. 고정된 `test@example.com` 대신 실행마다 다른 접미사를 붙이고(`qa+<실행 id>@example.com`), 테스트가 끝나면 지우거나, 지우지 못하는 환경이라면 테스트 데이터에 표시를 달아 주기적으로 청소한다. 같은 계정을 여러 파이프라인이 동시에 쓰면 한쪽이 바꾼 상태 때문에 다른 쪽이 실패하는 플레이키가 생긴다. 진짜 DB에 붙여 테스트마다 되돌리는 방법은 [실제 DB로 도는 통합 테스트](/posts/integration-tests-real-db#테스트마다-트랜잭션을-열고-되돌린다)에서 다뤘다.

## 토큰이 필요한 API

인증이 걸린 API는 테스트도 토큰이 있어야 한다. 사람 로그인 흐름(비밀번호, 2단계 인증)을 테스트가 흉내 내면 느리고 깨지기 쉽다. 테스트 전용 클라이언트를 따로 등록하고 OAuth의 client credentials 방식처럼 사람 없이 토큰을 받는 길을 쓰는 게 보통이다. 사용자 단위 권한을 확인해야 한다면, 테스트 환경에만 있는 토큰 발급 API나 미리 만든 테스트 사용자를 쓴다.

토큰을 받는 사전 스크립트는 이렇다.

```js
// 컬렉션의 Pre-request Script: 토큰이 없을 때만 한 번 받는다
if (pm.environment.get("accessToken")) return;
pm.sendRequest({
  url: pm.environment.get("baseUrl") + "/token", method: "POST",
  header: { "Content-Type": "application/json" },
  body: { mode: "raw", raw: JSON.stringify({ client_id: "qa-bot", client_secret: pm.environment.get("clientSecret") }) },
}, (err, res) => { pm.environment.set("accessToken", res.json().access_token); });
```

인증 쪽에서 확인할 실패 경로도 정해 둔다. 토큰 없음(401), 만료된 토큰(401), 서명이 틀린 토큰(401), 권한이 모자란 토큰(403), 다른 사용자의 자원(403 또는 404). 401과 403의 구분은 "누군지 모른다"와 "누군지는 아는데 안 된다"다. 그리고 테스트 클라이언트의 권한은 최소로 준다. 테스트용 비밀값이 새도 운영 데이터를 지울 수 없게.

## 바깥 API는 어떻게 다루나

우리 서버가 결제사나 배송사 API를 부른다면, CI의 API 테스트에서 그걸 진짜로 부르면 안 된다. 느리고, 돈이 들고, 상대 샌드박스가 죽으면 우리 테스트가 빨개진다. 테스트 환경에서는 바깥 API 자리에 스텁 서버를 세운다. WireMock(요청 패턴에 따라 정해 둔 응답을 주는 서버)이나, OpenAPI 명세를 읽어 예시 응답을 돌려주는 Prism 같은 도구를 쓴다. 바깥 API의 실패(타임아웃, 500, 이상한 응답)는 스텁으로만 재현할 수 있으니, 오히려 스텁이 있어야 테스트할 수 있는 것들이 있다.

스텁의 약점은 상대가 바뀌어도 모른다는 것이다. 스텁은 우리가 마지막으로 본 상대의 모습이다. 그래서 상대의 샌드박스에 대고 "스텁과 진짜가 같은 모양인지"만 확인하는 작은 검사를 따로, 덜 자주 돌린다. 이 검사가 실패해도 우리 배포를 막지는 않고 알림을 보낸다. 벤더 샌드박스에서 확인하는 법은 [SIT와 UAT](/posts/sit-uat-testing#벤더-샌드박스에도-계약을-확인한다)에서 더 다뤘다.

녹화·재생 방식(실제 응답을 한 번 녹화해 두고 이후엔 재생)도 많이 쓴다. 편하지만 녹화 파일에 토큰이나 개인정보가 그대로 들어가기 쉽고, 녹화가 오래되면 스텁과 같은 약점을 가진다. 녹화할 때 민감한 헤더와 필드를 지우는 필터를 꼭 건다.

## 배포 전에 호환성을 확인하는 계약 테스트

여기까지의 API 테스트는 제공자(백엔드)가 자기 기준으로 쓴다. 도입부 사고를 막으려면 소비자(앱)가 무엇을 쓰는지가 제공자의 배포 전에 확인되어야 한다. 소비자 주도 계약 테스트(consumer-driven contract testing)가 그 일을 한다. 원리와 전체 흐름, 작은 검증기로 돌려 본 예는 [API 버전 관리](/posts/api-versioning#소비자가-쓰는-것만-지킨다)에 있으니, 여기서는 Pact로 실제로 짤 때의 모양만 본다.

소비자 쪽 테스트는 Pact가 띄우는 목 서버를 상대로 돈다. 이 테스트가 통과하면 "이 요청을 보내면 이런 모양이 와야 한다"는 계약 파일(pact)이 만들어진다.

```js
// 앱(소비자) 쪽: @pact-foundation/pact의 PactV3
import { PactV3, MatchersV3 } from "@pact-foundation/pact";
const { like } = MatchersV3;

const provider = new PactV3({ consumer: "shop-app", provider: "order-api" });

test("주문 상세에서 배송 예정일을 읽는다", async () => {
  provider
    .given("ord_1000 주문이 있다")
    .uponReceiving("주문 상세 조회")
    .withRequest({ method: "GET", path: "/orders/ord_1000" })
    .willRespondWith({
      status: 200,
      headers: { "Content-Type": "application/json" },
      body: { id: like("ord_1000"), deliveryEta: like("2026-10-25") },   // 앱이 실제로 쓰는 필드만
    });

  await provider.executeTest(async (mock) => {
    const order = await getOrder(mock.url, "ord_1000");   // 앱의 진짜 API 클라이언트 코드
    assert.equal(order.deliveryEta, "2026-10-25");
  });
});
```

`like`는 "이 값 그대로가 아니라 이 타입이면 된다"는 뜻이다. 계약에는 앱이 쓰는 `id`와 `deliveryEta`만 들어간다. `status`나 `amount`는 앱의 이 화면이 안 쓰니 넣지 않는다. 그래야 제공자가 안 쓰이는 필드를 자유롭게 바꿀 수 있다.

계약 파일은 Pact Broker(또는 PactFlow)에 올라간다. 제공자 쪽 CI는 PR마다 브로커에서 계약을 받아, 진짜 서버를 띄우고 계약의 요청을 재생해 응답을 대 본다. `given`에 적힌 상태("ord_1000 주문이 있다")는 제공자 쪽의 상태 핸들러가 테스트 데이터를 넣어 맞춘다. 사고 난 PR이었다면 여기서 `shop-app`의 계약이 깨졌다고 실패했을 것이다.

마지막 관문은 배포 직전의 질문이다. "지금 운영에 있는 소비자 버전들과 이 버전이 호환되나." 브로커는 어떤 버전끼리 검증이 통과했는지 기록하고 있으니 그걸 묻는다.

```bash
# 이 버전의 order-api를 production에 배포해도 되는지 브로커에 묻는다
pact-broker can-i-deploy --pacticipant order-api --version "$GIT_SHA" --to-environment production
```

계약 테스트는 통합 테스트를 대신하지 않는다. 계약 테스트는 "모양이 맞나"를 서로 떨어진 채로 빠르게 확인하고, 통합 테스트는 "진짜끼리 붙여서 동작하나"를 확인한다. 계약 테스트는 두 서비스를 동시에 띄우지 않아도 되니 서비스가 많을수록 값을 하고, 대신 소비자 팀들이 계약을 써 줘야 한다. 불특정 다수가 쓰는 공개 API라면 소비자를 모으기 어려워 스키마 비교와 사용량 로그로 간다.

## SOAP과 운영 중인 API 확인

REST가 아닌 API도 아직 많다. 은행, 공공, 오래된 사내 시스템에는 SOAP이 남아 있다. SOAP은 WSDL이라는 명세 파일에 연산과 메시지 모양이 XML 스키마로 정의되어 있어서, SoapUI 같은 도구가 WSDL을 읽어 요청 틀을 만들어 준다. 확인은 XPath로 XML 응답의 특정 노드를 짚어서 한다. 상태 코드보다 응답 본문 안의 SOAP Fault를 봐야 하는 경우가 많다는 점이 REST와 다르다. SOAP 서비스는 실패도 HTTP 500에 Fault 본문으로 주거나, 시스템에 따라 200에 오류 코드를 담아 주기도 해서 "HTTP 200이면 통과"가 더 위험하다.

CI에서 도는 API 테스트와 운영 API 모니터링은 질문이 다르다. CI 테스트는 "이 빌드가 약속을 지키나"를 배포 전에 묻는다. 모니터링은 "지금 운영에서 이 API가 동작하나"를 몇 분마다 묻는다. Runscope 같은 API 모니터링 서비스나 Postman Monitors, Checkly가 이 자리에 있다. 운영 모니터링에는 읽기 전용 요청과 테스트 계정만 쓰고, 실패하면 테스트 결과가 아니라 장애 알림으로 보낸다. 바깥 API(결제사, 지도 API)를 우리가 직접 모니터링해 두면, 상대가 먼저 공지하기 전에 "응답 형식이 바뀌었다"를 알 수 있다.

## API 테스트가 거짓말하는 순간

- 테스트는 통과하는데 앱이 깨진다: 제공자 기준으로만 확인하고 있다. 앱이 쓰는 필드가 계약이나 스키마의 `required`에 들어 있는지 본다. 앱 쪽 테스트의 고정 응답 JSON이 언제 만들어졌는지도 본다.
- 스테이징에서만 가끔 실패한다: 공유 데이터다. 다른 파이프라인이 같은 계정, 같은 주문을 쓰고 있지 않은지, 테스트가 앞 테스트의 데이터에 기대고 있지 않은지 본다.
- 긴 테스트 묶음의 뒤쪽에서만 401이 난다: 토큰 만료다. 사전 스크립트가 만료 시간을 보지 않고 처음 받은 토큰을 계속 쓴다.
- 응답 시간 단언이 가끔 실패한다: CI 러너의 흔들림이다. 상한을 넉넉히 하고, 성능은 별도 부하 테스트로 판단한다.
- 바깥 API 스텁으로는 다 통과하는데 운영에서 연동이 깨진다: 스텁이 오래됐다. 샌드박스 대조 검사를 돌리고 있는지, 실패 알림을 누가 받는지 본다.
- 스키마 검사가 너무 자주 깨져서 다들 고치기만 한다: 소비자 쪽 검사에 `additionalProperties: false`나 전체 일치 비교를 쓰고 있다. 쓰는 필드만 확인하도록 바꾼다.

## 둘이 만나는 자리를 확인한다

API 테스트는 화면 없이 진짜 HTTP와 직렬화를 거쳐 상태 코드, 헤더, 값, 모양, 응답 시간, 부작용을 확인한다. 모양은 JSON Schema로 선언하고, 소비자 쪽에서는 모르는 필드를 허용한다. Postman 컬렉션은 Newman으로 CI에서 돌릴 수 있고, 테스트가 커지면 코드 기반 도구가 리뷰와 재사용에서 유리하다. 테스트마다 자기 데이터를 만들고, 토큰은 한 번 받아 재사용하며 비밀값은 실행할 때 넣고, 바깥 API는 스텁으로 바꾸되 스텁이 진짜와 같은지 따로 확인한다. 그리고 제공자의 테스트로는 소비자가 무엇을 쓰는지 모르니, 소비자가 남긴 계약을 제공자가 배포 전에 확인한다. 테스트 케이스를 뽑는 법은 [테스트 케이스 설계](/posts/test-design-techniques)에, 이 테스트들이 배포 길목에서 언제 도는지는 [스모크, 새니티, 회귀 테스트](/posts/smoke-sanity-regression-testing)에 있다.

## 면접에서 나올 만한 질문

### API 테스트는 단위·통합·E2E 사이에서 어떤 자리인가요?

서버를 실제로 띄우고 HTTP로 부르되 화면은 거치지 않는 층이라 통합 테스트의 위쪽, E2E 아래에 선다. 라우팅, 인증 미들웨어, 본문 파싱, 응답 직렬화처럼 단위 테스트가 못 보는 것이 여기서 처음 진짜가 된다. E2E보다 빠르고 실패 원인이 바로 보여서 업무 규칙의 조합은 이 층에서 넓게 돌리는 편이다. 다만 제공자 기준이라 소비자가 무엇을 쓰는지는 모른다.

### API 응답에서 무엇을 검증하나요?

상태 코드(실패 경로 포함), 헤더(Content-Type, 캐시, Location), 본문의 값과 모양, 넉넉한 상한의 응답 시간, 그리고 부작용이다. 200만 보는 테스트는 필드 이름이 바뀐 응답도 통과시킨다. 모양은 JSON Schema로 필수 필드와 타입을 선언해 확인하고, 생성 API는 다시 조회해 저장됐는지, 같은 요청을 두 번 보내도 하나만 생기는지까지 본다.

### Postman 컬렉션을 CI에서 어떻게 돌리나요?

컬렉션과 환경을 JSON으로 내보내 저장소에 넣고 Newman으로 돌린다. 비밀값은 환경 파일이 아니라 CI 비밀 변수에서 `--env-var`로 넣고, `--reporters cli,junit`으로 JUnit XML을 남겨 CI가 결과를 보여 주게 한다. 실패하면 종료 코드 1이라 파이프라인이 멈춘다. 다만 스크립트가 JSON 문자열로 들어가 리뷰와 재사용이 어려우니, 테스트가 커지고 개발자가 주로 관리한다면 코드 기반 도구가 낫다.

### 테스트 간 데이터 의존은 왜 문제이고 어떻게 끊나요?

앞 테스트가 만든 id를 뒤 테스트가 쓰면, 앞이 실패할 때 뒤가 모두 엉뚱한 이유로 실패하고 하나만 따로 돌리거나 병렬로 돌릴 수 없다. 기준은 그 테스트 하나만 돌려도 통과하느냐다. 각 테스트가 자기 데이터를 API나 시드로 만들고, 공유 환경에서는 실행마다 다른 이름을 붙이고 끝나면 지운다. 같은 계정을 여러 파이프라인이 동시에 쓰면 플레이키가 생긴다.

### 인증 토큰이 필요한 API 테스트는 어떻게 구성하나요?

사람 로그인 흐름을 흉내 내지 않고 테스트 전용 클라이언트로 client credentials 같은 방식으로 토큰을 받는다. 토큰은 묶음 시작에 한 번 받아 재사용하고 만료가 가까우면 다시 받는다. 비밀값은 실행 시점에 CI 비밀 변수로 넣고, 테스트 클라이언트 권한은 최소로 준다. 토큰 없음, 만료, 위조, 권한 부족, 남의 자원 같은 실패 경로도 테스트로 둔다.

### 외부 의존 API는 테스트에서 어떻게 다루나요?

CI에서는 진짜를 부르지 않고 WireMock이나 OpenAPI 기반 목 서버 같은 스텁을 세운다. 스텁이 있어야 타임아웃이나 500 같은 상대의 실패도 재현할 수 있다. 대신 스텁은 상대가 바뀌어도 모르니, 상대 샌드박스에 대고 스텁과 같은 모양인지 확인하는 검사를 덜 자주 따로 돌리고 실패하면 알림을 보낸다. 녹화·재생을 쓴다면 토큰과 개인정보를 지우는 필터를 건다.

### 계약 테스트와 통합 테스트는 무엇이 다른가요?

계약 테스트는 소비자가 실제로 쓰는 요청과 응답 모양을 계약으로 남기고, 제공자가 두 서비스를 함께 띄우지 않고도 배포 전에 그 계약을 만족하는지 확인한다. 통합 테스트는 진짜끼리 붙여서 동작하는지 본다. 계약은 빠르고 서비스가 많을수록 값을 하지만 동작 전체를 보장하지 않고, 소비자 팀의 협조가 필요하다. Pact라면 브로커의 `can-i-deploy`로 운영 중인 소비자 버전과의 호환을 배포 직전에 묻는다.

### 스키마 검사에서 모르는 필드는 허용해야 하나요?

소비자 쪽 검사라면 허용한다. 필드 추가는 안전한 변경이고, 소비자는 자기가 쓰는 필드만 보고 나머지를 무시해야 오래 버틴다(관대한 독자). `additionalProperties: false`나 전체 일치 비교를 걸면 새 필드 하나에도 테스트가 깨져 다들 고치기만 하게 된다. 제공자가 문서에 없는 필드를 실수로 내보내지 않는지 확인할 때만 엄격하게 쓴다.
