## 파이프라인은 초록불인데 어제 매출이 0원이다

금요일 아침 대시보드에 목요일 매출이 0원으로 찍혔다. Airflow 화면은 전부 초록불이다. 추출, 적재, 변환이 모두 성공했고 적재된 행도 6168건으로 평소와 비슷하다. 원인을 찾는 데 두 시간이 걸렸다. 결제 팀이 목요일에 배포하면서 주문 상태 값 `paid`를 `payment_completed`로 바꿨고, 매출 집계는 `status = 'paid'`인 행만 더하고 있었다.

```sql
SELECT order_date, count(*) AS orders,
       coalesce(sum(amount) FILTER (WHERE status = 'paid'), 0) AS revenue
FROM (SELECT * FROM orders WHERE order_date >= '2026-10-21'
      UNION ALL
      SELECT * FROM stg_orders) t          -- 목요일 묶음은 아직 스테이징에 있다
GROUP BY 1 ORDER BY 1;
```

```text
 order_date | orders |   revenue
------------+--------+--------------
 2026-10-21 |   6147 | 299810360.00
 2026-10-22 |   6154 | 301475940.00
 2026-10-23 |   6168 |            0
(3 rows)
```

이 글은 이런 "조용히 틀린 숫자"를 사람보다 먼저 잡는 법을 다룬다. 실험은 Ubuntu 24.04의 PostgreSQL 16에서 회원 2만 명, 2주치 주문 7만 5천 건을 만들어 했다. 원본에서 데이터를 옮기는 과정(증분 추출, 멱등한 적재)은 [ETL과 ELT](/posts/etl-vs-elt)에서, 검사 결과를 남길 칸(브론즈·실버·골드)은 [데이터 웨어하우스 설계](/posts/data-warehouse-architecture)에서 다뤘다.

## 틀린 데이터는 오류를 내지 않는다

애플리케이션 버그는 대개 예외를 던진다. 데이터 문제는 다르다. 상태 값이 바뀌어도, 금액 단위가 원에서 센트로 바뀌어도, 컬럼 하나가 통째로 NULL이 돼도 SQL은 문법적으로 멀쩡히 돈다. 결과가 틀렸을 뿐이다. 그래서 데이터 품질 검사는 "작업이 성공했나"가 아니라 "결과가 말이 되나"를 따로 물어야 한다.

작업 성공 여부조차 믿기 어려운 경우가 있다. 검사가 실패하면 예외를 던지게 짠 SQL 파일을 psql로 돌렸다.

```bash
psql -d dq -f publish.sql;  echo "exit=$?"     # 기본 설정
psql -d dq -v ON_ERROR_STOP=1 -f publish.sql;  echo "exit=$?"
```

```text
BEGIN
psql:publish.sql:10: ERROR:  accepted_status failed: 5549 rows
CONTEXT:  PL/pgSQL function inline_code_block line 7 at RAISE
psql:publish.sql:12: ERROR:  current transaction is aborted, commands ignored until end of transaction block
ROLLBACK
exit=0

BEGIN
psql:publish.sql:10: ERROR:  accepted_status failed: 5549 rows
CONTEXT:  PL/pgSQL function inline_code_block line 7 at RAISE
exit=3
```

psql은 기본값으로 오류가 나도 다음 문장으로 넘어가고, 파일을 끝까지 읽으면 종료 코드 0을 돌려준다. 이걸 `BashOperator`로 부르면 Airflow는 성공으로 본다. 검사가 실패를 외쳤는데 오케스트레이터는 초록불을 켠 셈이다. psql로 SQL 파일을 돌리는 작업에는 `-v ON_ERROR_STOP=1`을 항상 붙인다. 종료 코드 3은 스크립트 실행 중 오류로 멈췄다는 뜻이다.

## 품질을 다섯 갈래로 나눠 묻는다

"데이터가 좋다"는 말은 너무 넓어서 검사로 바꾸기 어렵다. 보통 몇 가지 차원으로 쪼개 묻는다. 책마다 이름과 개수가 조금씩 다르지만 실무에서 자주 쓰는 것은 이렇다.

유일성은 같은 키가 두 번 있지 않은지 묻는다. 재시도로 같은 묶음이 두 번 들어오면 깨진다. 완전성은 있어야 할 값과 행이 다 있는지 묻는다. 꼭 필요한 컬럼의 NULL, 빠진 날짜, 평소보다 적은 행 수가 여기 걸린다. 유효성(정확성)은 값이 약속한 범위와 형식 안에 있는지 묻는다. 상태 값 목록, 금액 범위, 이메일 형식 같은 것이다. 일관성은 다른 데이터와 맞는지 묻는다. 주문이 가리키는 회원이 실제로 있는지, 주문 합계와 결제사 정산 합계가 맞는지. 신선도는 데이터가 제때 들어왔는지 묻는다. 어제 데이터가 오늘 아침 9시 전에 와야 한다는 식이다.

각 검사를 "실패한 행을 돌려주는 SQL"로 쓰면 다루기 쉽다. 0행이면 통과다. dbt의 테스트도 이 방식이다. 목요일 데이터가 들어온 스테이징 테이블에 여섯 개를 한 번에 돌렸다.

```sql
-- 1. 유일성: 같은 id가 두 번 이상
SELECT 'unique_id' AS check_name, count(*) AS failing
FROM (SELECT id FROM stg_orders GROUP BY id HAVING count(*) > 1) t
UNION ALL
-- 2. 완전성: 꼭 있어야 하는 값이 비었다
SELECT 'not_null_amount', count(*) FROM stg_orders WHERE amount IS NULL
UNION ALL
-- 3. 유효성: 약속한 상태 값만
SELECT 'accepted_status', count(*) FROM stg_orders
WHERE status NOT IN ('paid', 'shipped', 'cancelled', 'refunded')
UNION ALL
-- 4. 유효성: 금액 범위
SELECT 'amount_range', count(*) FROM stg_orders WHERE amount <= 0 OR amount > 10000000
UNION ALL
-- 5. 일관성: 없는 회원을 가리키는 주문
SELECT 'fk_user', count(*) FROM stg_orders o
WHERE NOT EXISTS (SELECT 1 FROM users u WHERE u.id = o.user_id)
UNION ALL
-- 6. 신선도: 마지막 적재가 26시간보다 오래됐다 (재현을 위해 기준 시각을 고정)
SELECT 'freshness', CASE WHEN max(loaded_at) < timestamptz '2026-10-24 09:00+09' - interval '26 hours'
                         THEN 1 ELSE 0 END
FROM stg_orders;
```

```text
   check_name    | failing
-----------------+---------
 unique_id       |       7
 not_null_amount |       0
 accepted_status |    5549
 amount_range    |       0
 fk_user         |      12
 freshness       |       0
(6 rows)
```

`accepted_status`가 5549건으로 처음 장면의 원인을 정확히 짚었다. 그 밖에 두 가지가 더 나왔다. 재시도로 7건이 두 번 들어왔고(`unique_id`), 12건은 회원 테이블에 없는 회원을 가리킨다(`fk_user`). 이 셋은 무게가 다르다. 상태 값이 틀리면 매출 전체가 틀리니 막아야 하고, 중복 7건은 적재 단계에서 키별 최신 한 줄만 남기면 사라진다. 없는 회원 12건은 회원 테이블이 주문보다 늦게 적재되는 날 흔히 생기는 일이라, 알리기만 하고 다음 날 다시 확인하면 된다.

이 판단을 검사마다 미리 정해 둔다. dbt는 이걸 `severity: error` / `warn`으로 적는다. 검사가 실패했을 때 무엇을 할지 정하지 않은 검사는 결국 무시당한다.

## 행 수는 맞았다

처음 장면에서 행 수 검사는 통과했다. 6168건은 평소 금요일과 비슷하다. 행 수는 가장 싸고 가장 많이 쓰는 검사지만, 행은 다 왔는데 값이 틀린 경우는 못 잡는다.

그래서 행 수와 함께 "결과 지표"도 본다. 하루 매출, 결제 완료 비율, 회원당 주문 수처럼 비즈니스가 실제로 보는 숫자가 평소 범위 안인지 확인한다. 상태 값 목록을 미리 알지 못해도 결제 완료 비율이 89%에서 0%로 떨어진 것은 잡힌다.

```sql
-- 요일이 같은 지난 두 주의 결제 완료 비율
SELECT order_date, to_char(order_date, 'Dy') AS dow, count(*) AS orders,
       round(100.0 * count(*) FILTER (WHERE status = 'paid') / count(*), 1) AS paid_pct
FROM orders WHERE order_date IN ('2026-10-09', '2026-10-16')
GROUP BY 1, 2 ORDER BY 1;
```

```text
 order_date | dow | orders | paid_pct
------------+-----+--------+----------
 2026-10-09 | Fri |   6063 |     89.7
 2026-10-16 | Fri |   6112 |     89.5
(2 rows)
```

널 비율도 같은 종류의 지표다. 원본 쪽에서 컬럼 이름이 바뀌면 받는 쪽 컬럼이 오류 없이 NULL로 채워지는 일이 있다([ETL과 ELT](/posts/etl-vs-elt)에서 이름 기준 합치기로 재현했다). `NOT NULL`을 걸기 어려운 선택 컬럼이라도 "평소 널 비율 2%가 오늘 100%"는 이상하다.

## 다른 장부와 합계를 맞춰 본다

일관성 검사 가운데 가장 힘이 센 것은 같은 사건을 따로 기록한 다른 장부와 합계를 맞춰 보는 대사(reconciliation)다. 주문 DB의 결제 완료 금액과 결제사가 보내 주는 정산 파일의 금액은 같아야 한다. 둘은 서로 다른 회사가 다른 시스템으로 적으니, 한쪽 파이프라인의 버그가 다른 쪽에 똑같이 생길 가능성이 낮다.

정산 파일을 `pg_settlements` 테이블로 올렸다고 하고 날짜별로 비교했다.

```sql
SELECT o.order_date,
       sum(o.amount)                          AS our_paid,
       coalesce(s.settled, 0)                 AS pg_settled,
       sum(o.amount) - coalesce(s.settled, 0) AS diff
FROM orders o
LEFT JOIN (SELECT settled_date, sum(paid_amount) AS settled
           FROM pg_settlements GROUP BY 1) s ON s.settled_date = o.order_date
WHERE o.status = 'paid' AND o.order_date BETWEEN '2026-10-20' AND '2026-10-22'
GROUP BY o.order_date, s.settled ORDER BY 1;
```

```text
 order_date |   our_paid   |  pg_settled  |   diff
------------+--------------+--------------+-----------
 2026-10-20 | 300707060.00 | 300707060.00 |      0.00
 2026-10-21 | 299810360.00 | 299613580.00 | 196780.00
 2026-10-22 | 301475940.00 | 301475940.00 |      0.00
(3 rows)
```

21일에 19만 6780원이 비었다. 합계가 다르면 그다음은 키로 내려가 어떤 주문이 한쪽에만 있는지 찾는다.

```sql
SELECT count(*) AS missing, sum(o.amount) AS missing_amount
FROM orders o
WHERE o.status = 'paid' AND o.order_date = '2026-10-21'
  AND NOT EXISTS (SELECT 1 FROM pg_settlements s WHERE s.order_id = o.id);
```

```text
 missing | missing_amount
---------+----------------
       5 |      196780.00
(1 row)
```

실제 대사는 이렇게 깔끔하지 않다. 결제사는 자정 근처 결제를 다음 날로 정산하기도 하고, 부분 환불과 수수료가 섞이고, 시간대가 다르다. 그래서 "차이가 0이어야 한다"보다 "차이가 합계의 0.1% 이하이고, 차이 나는 주문 목록이 사흘 안에 사라져야 한다"처럼 허용 폭과 기간을 함께 정한다. 대사 검사는 보통 막지 않고 알린다. 원인이 우리 쪽인지 상대 쪽인지 사람이 봐야 알기 때문이다.

## 어제와 비교하면 토요일마다 알림이 온다

평소 범위를 어떻게 정하느냐가 이상 탐지 검사의 전부다. 가장 쉬운 방법은 어제와 비교하는 것이다. "어제보다 30% 넘게 줄면 알림"을 걸었더니 토요일마다 알림이 왔다. 실험 데이터는 평일 6000건 안팎, 주말 3500건 안팎이다. 토요일은 금요일보다 40% 적은 게 정상이다.

기준을 잡을 때 쓰는 요령은 이렇다. 계절성이 있으면 같은 주기끼리 비교한다(요일, 월초·월말, 시간대). 평균 대신 중앙값을 쓰면 지난번 장애 날 하나가 기준을 끌어내리지 않는다. 허용 폭은 처음엔 넓게 잡고, 실제로 놓친 사고와 거짓 알림을 보면서 좁힌다. 명절, 대형 할인 행사처럼 미리 아는 날은 검사를 끄거나 따로 기준을 준다.

아래에 같은 요일 기록의 중앙값과 비교하는 검사를 직접 짜 볼 수 있다. 기록이 없으면 판단할 수 없다는 뜻으로 `"unknown"`을 돌려준다.

  if (ratio > 1 + tolerance) return "high";

마지막 테스트가 어제 비교의 거짓 알림이다. 같은 3619건이 금요일 기록과 비교되면 `"low"`가 된다. 더 정교하게는 추세와 계절성을 함께 학습하는 시계열 모델을 쓰기도 하고, Monte Carlo나 Elementary 같은 데이터 관측 도구가 테이블마다 이런 기준을 자동으로 잡는다. 그래도 원리는 같다. 비교할 대상을 잘 고르는 것이 모델보다 먼저다.

## 적재 전에 막을까, 적재 후에 알릴까

검사를 파이프라인 어디에 두느냐에 따라 할 수 있는 일이 다르다.

적재 후 경보는 데이터를 일단 최종 테이블에 넣고 나서 검사한다. 파이프라인이 멈추지 않으니 데이터는 늦지 않는다. 그 대신 틀린 숫자가 검사보다 먼저 대시보드에 나가고, 그걸 본 사람이 이미 결정을 내렸을 수 있다.

적재 전 차단은 데이터를 스테이징에 쓰고, 검사하고, 통과했을 때만 최종 테이블로 넘긴다. 이 순서를 Write-Audit-Publish(WAP)라고 부른다. 틀린 데이터는 밖으로 안 나가지만, 검사가 실패하면 그날 데이터가 늦는다. 아래 그림에서 다음을 누르면 목요일 데이터가 어디서 멈추는지 보인다.

PostgreSQL에서는 검사와 넘기기를 한 트랜잭션에 넣으면 간단하다. 검사가 예외를 던지면 넘기기까지 함께 롤백된다.

```sql
BEGIN;
DO $$
DECLARE bad bigint;
BEGIN
  SELECT count(*) INTO bad FROM stg_orders
  WHERE status NOT IN ('paid', 'shipped', 'cancelled', 'refunded');
  IF bad > 0 THEN
    RAISE EXCEPTION 'accepted_status failed: % rows', bad;   -- error 등급 검사
  END IF;
END $$;
INSERT INTO orders                                           -- 통과했을 때만 넘긴다
SELECT DISTINCT ON (id) * FROM stg_orders ORDER BY id, loaded_at DESC;
COMMIT;
```

실행 결과는 앞의 `exit=3` 출력 그대로고, 그 뒤 `orders`에 10월 23일 행은 0건이었다. 레이크의 테이블 포맷이라면 Iceberg의 브랜치나 Delta Lake의 별도 테이블에 쓰고 검사 후 바꿔 끼우는 식으로 같은 일을 한다.

어디에 둘지는 틀린 숫자의 비용과 늦은 숫자의 비용을 비교해서 정한다. 정산·과금·외부 보고처럼 틀리면 되돌리기 어려운 곳은 막는다. 내부 탐색용 대시보드처럼 조금 틀려도 곧 고치면 되는 곳은 알린다. 한 파이프라인 안에서도 검사마다 다르게 둔다. 원본 바로 뒤(브론즈 → 실버)에는 스키마와 키 검사를, 골드 직전에는 지표 범위 검사를 둔다. 원인에 가까운 곳에서 잡을수록 고치기 쉽다.

## 검사를 도구로 옮기면

검사가 수십 개가 되면 SQL 파일로 관리하기 어렵다. 많이 쓰는 도구는 두 가지다.

dbt는 변환 SQL 옆에 검사를 적는다. `unique`, `not_null`, `accepted_values`, `relationships` 네 가지가 기본으로 들어 있고, 나머지는 실패 행을 돌려주는 SQL로 직접 만든다. 아래는 dbt 1.8 이후 문법이다(이전 버전은 `data_tests` 대신 `tests`, 최근 버전은 인자를 `arguments` 아래에 두도록 바뀌는 중이라 쓰는 버전 문서를 확인한다).

```yaml
# models/staging/stg_orders.yml
version: 2
models:
  - name: stg_orders
    columns:
      - name: id
        data_tests: [unique, not_null]
      - name: status
        data_tests:
          - accepted_values:
              values: ["paid", "shipped", "cancelled", "refunded"]
      - name: user_id
        data_tests:
          - relationships:
              to: ref('stg_users')
              field: id
              config:
                severity: warn        # 알리기만 하고 막지 않는다
```

`dbt build`는 모델을 만들고 바로 그 모델의 테스트를 돌린 뒤, error 등급 테스트가 실패하면 그 모델에 의존하는 다음 모델을 건너뛴다. 앞에서 본 WAP와 비슷한 효과가 기본으로 생긴다.

Great Expectations(GX)는 Python 쪽 도구다. "이 컬럼 값은 이 집합 안에 있다(`ExpectColumnValuesToBeInSet`)", "행 수는 이 범위다" 같은 기대값 묶음을 정의해 pandas, Spark, SQL 데이터 원본에 돌리고, 결과를 HTML 문서로 남긴다. Spark 작업 중간이나 레이크 파일처럼 dbt가 닿지 않는 곳에 쓰기 좋다. 도구는 달라도 같은 질문을 던진다. 무엇을, 어느 단계에서, 실패하면 막을지 알릴지.

## 원본 팀과 맺는 데이터 계약

처음 장면을 다시 보자. 검사가 아무리 좋아도 목요일 데이터를 막는 데서 끝난다. 결제 팀이 상태 값을 바꾸기 전에 알았다면 일이 아예 안 생겼다. 결제 팀은 자기 서비스 DB의 값을 바꿨을 뿐이고, 그 값을 누가 읽는지 몰랐다.

데이터 계약은 데이터를 내보내는 쪽(생산자)과 받는 쪽(소비자)이 이 경계를 문서와 검사로 만든 것이다. 형식은 팀마다 다르고 Open Data Contract Standard 같은 표준도 있지만, 담는 내용은 비슷하다.

```yaml
# 예시: orders 데이터 계약 (형식은 팀마다 다르다)
dataset: payments.orders
owner: payments-team            # 바꿀 때 누구에게 물어야 하나
schema:
  - { name: id,      type: bigint,        required: true, unique: true }
  - { name: status,  type: text,          required: true,
      allowed: [paid, shipped, cancelled, refunded] }
  - { name: amount,  type: numeric(12,2), required: true, unit: KRW }
freshness: "전날 데이터는 다음 날 06:00 KST까지"
changes: "컬럼 삭제·이름 변경·허용 값 변경은 2주 전 공지, 추가는 자유"
```

중요한 것은 이 문서를 생산자 쪽 배포 과정에서 검사한다는 점이다. 결제 팀의 CI가 마이그레이션이나 이벤트 스키마를 계약과 비교해, 허용 값에서 `paid`가 빠지면 배포 전에 실패시킨다. 이벤트 스트림이라면 스키마 레지스트리의 호환성 검사가 이 역할을 한다([스키마 버전 관리](/posts/schema-versioning)). dbt의 모델 계약(`contract: enforced: true`)은 반대 방향, 즉 데이터팀이 내보내는 골드 테이블의 컬럼과 타입을 고정해 소비자를 지킨다.

계약이 푸는 문제는 기술보다 소유권이다. 운영 DB 테이블을 데이터팀이 몰래 읽는 구조에서는 원본 팀이 무엇을 바꿔도 책임이 없다. 계약을 맺으면 원본 팀이 "우리 데이터를 바깥에 내보내는 인터페이스"를 API처럼 관리하게 된다. 그 대신 원본 팀의 일이 늘어나니, 모든 테이블이 아니라 매출·회원처럼 여러 팀이 기대는 핵심 데이터부터 계약을 맺는다. 운영 DB 테이블을 직접 열지 않고 원본 팀이 정한 이벤트나 뷰만 내보내는 방식도 계약을 지키기 쉽게 만든다.

## 틀린 숫자가 이미 나갔을 때

검사가 놓쳐서 틀린 숫자가 이미 대시보드와 리포트에 나갔다면, 순서대로 영향 범위를 좁힌다.

먼저 더 퍼지지 않게 한다. 문제가 된 테이블을 갱신하는 작업을 멈추고, 그 테이블을 읽는 대시보드 위에 "확인 중" 안내를 띄운다. 다음으로 처음 틀린 지점을 찾는다. 칸마다 날짜별 행 수와 지표를 남겨 뒀다면 어느 날짜, 어느 칸에서 숫자가 달라졌는지 바로 보인다. 처음 장면이라면 10월 23일, 실버의 `status` 컬럼이다.

그다음 하류를 센다. dbt의 계보 그래프나 웨어하우스의 계보 기능으로 그 테이블에 의존하는 테이블, 대시보드, 머신러닝 특성, 외부로 나간 보고서를 목록으로 만든다. 사람에게 알리는 범위는 이 목록이 정한다. 마지막으로 원인을 고치고 영향받은 날짜만 다시 계산한다. 적재가 날짜 단위로 멱등하면 그 날짜 범위를 백필로 다시 돌리면 끝난다([Airflow](/posts/airflow-orchestration)).

사고가 끝나면 그 사고를 잡았을 검사를 하나 추가한다. 이번에는 상태 값 목록 검사와 결제 완료 비율 검사였다. 검사 목록은 이렇게 실제 사고를 따라 자란다.

## 검사 결과도 테이블에 쌓는다

검사가 통과했는지 실패했는지만 알림으로 보내고 버리면, "이 검사가 지난달에 몇 번 울렸나", "회원 없는 주문이 늘고 있나" 같은 질문에 답할 수 없다. 검사 결과를 날짜별로 테이블에 남긴다.

```sql
CREATE TABLE dq_results (
  run_date   date        NOT NULL,   -- 검사한 데이터의 날짜
  table_name text        NOT NULL,
  check_name text        NOT NULL,
  severity   text        NOT NULL,   -- error / warn
  failing    bigint      NOT NULL,   -- 실패한 행 수
  checked_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (run_date, table_name, check_name)   -- 다시 돌리면 덮어쓴다
);
```

21일과 22일 값은 예시로 넣고, 23일은 앞의 검사 결과를 넣은 뒤 최근 사흘을 한 줄로 펼쳐 봤다.

```sql
SELECT check_name, severity,
       string_agg(failing::text, ' → ' ORDER BY run_date) AS last_3_days
FROM dq_results
WHERE run_date > date '2026-10-23' - 3
GROUP BY 1, 2 ORDER BY 1;
```

```text
   check_name    | severity | last_3_days
-----------------+----------+--------------
 accepted_status | error    | 0 → 0 → 5549
 fk_user         | warn     | 9 → 11 → 12
(2 rows)
```

`accepted_status`는 갑자기 튀었으니 사고고, `fk_user`는 매일 조금씩 있으니 회원 적재가 늦는 평소 모습이다. 숫자가 서서히 늘어나는 쪽이 오히려 놓치기 쉬운 문제라, 이 테이블 자체에 다시 추세 검사를 걸기도 한다. 기본 키를 `(run_date, table_name, check_name)`으로 잡은 이유는 재처리로 같은 날짜를 다시 검사하면 덮어써서 이력이 두 줄이 되지 않게 하려는 것이다.

## 검사를 너무 많이 걸면

검사를 열심히 거는 팀이 빠지는 함정은 알림 피로다. 모든 컬럼에 `not_null`을 걸고, 모든 테이블에 행 수 경보를 걸면 하루에 알림이 수십 개 온다. 그중 대부분이 무시해도 되는 것이면 사람들은 알림 채널 자체를 안 보게 되고, 진짜 사고가 묻힌다.

몇 가지 원칙으로 줄인다. 검사마다 주인을 정한다. 실패하면 누가 보는지 모르는 검사는 지운다. warn 등급이 한 달 내내 울리면 기준을 고치거나 error로 올리거나 지운다. 계속 울리는데 아무도 행동하지 않는 warn은 소음이다. 골드와 외부로 나가는 테이블에 검사를 집중하고, 중간 테이블은 키와 스키마 검사만 둔다. 그리고 거짓 알림이 났을 때 기준을 고친 기록을 남겨 다음 사람이 같은 실수를 반복하지 않게 한다.

## 성공한 작업과 맞는 숫자는 다르다

데이터 품질 검사는 "작업이 끝났나"와 "숫자가 맞나"를 따로 묻는 일이다. 유일성, 완전성, 유효성, 일관성, 신선도로 쪼개 실패 행을 돌려주는 SQL로 쓰고, 행 수와 함께 결제 완료 비율 같은 결과 지표를 같은 요일 기준과 비교한다. 틀리면 되돌리기 어려운 곳은 스테이징에서 검사하고 통과한 것만 넘기고, 나머지는 알린다. 그리고 원인은 대개 원본 쪽 변경이니, 데이터 계약으로 생산자가 바꾸기 전에 알게 만드는 것이 가장 싸다.

## 면접에서 나올 만한 질문

### 데이터 품질은 어떤 차원으로 나눠 검사하나?

유일성(같은 키 중복), 완전성(필수 값의 NULL, 빠진 날짜·행), 유효성(허용 값, 범위, 형식), 일관성(참조 무결성, 다른 시스템과 합계 일치), 신선도(제때 도착)로 나눈다. 각 검사는 실패한 행을 돌려주는 SQL로 쓰고 0행이면 통과로 본다. 검사마다 실패했을 때 막을지 알릴지 등급을 정해 둔다.

### 파이프라인이 성공했는데 숫자가 틀리는 이유는?

데이터 문제는 대개 오류를 내지 않기 때문이다. 상태 값 변경, 단위 변경, 컬럼 이름 변경으로 생긴 NULL은 SQL을 문법적으로 깨지 않는다. psql처럼 기본값으로 오류 뒤에도 종료 코드 0을 돌려주는 도구도 있어서, `ON_ERROR_STOP` 같은 설정 없이는 실패한 검사도 성공으로 보인다. 그래서 작업 성공과 별도로 결과를 검사한다.

### 품질 검사를 파이프라인 어디에 두나?

틀린 숫자가 나가는 비용과 데이터가 늦는 비용을 비교해 정한다. 정산·과금처럼 되돌리기 어려운 곳은 스테이징에 쓰고 검사한 뒤 통과한 것만 넘기는 Write-Audit-Publish로 막고, 내부 탐색용은 적재 후 알린다. 원본 바로 뒤에는 스키마·키 검사를, 골드 직전에는 지표 범위 검사를 둬서 원인에 가까운 곳에서 잡는다.

### 행 수 이상 탐지에서 거짓 알림을 줄이려면?

어제와 비교하지 않고 같은 요일이나 같은 주기끼리 비교한다. 평균 대신 중앙값을 써서 지난 장애 날 하나가 기준을 흔들지 않게 한다. 허용 폭은 넓게 시작해 실제 사고와 거짓 알림을 보며 좁히고, 명절·행사처럼 미리 아는 날은 따로 다룬다. 행 수만으로는 값이 틀린 경우를 못 잡으니 결과 지표도 같이 본다.

### 데이터 계약은 어떤 문제를 푸나?

원본 팀이 자기 DB를 바꿨는데 누가 그 데이터를 읽는지 몰라서 하류가 조용히 깨지는 문제를 푼다. 스키마, 허용 값, 단위, 신선도, 변경 절차, 주인을 적고 생산자 쪽 CI에서 검사해 깨지는 변경을 배포 전에 막는다. 기술보다 소유권의 문제라서, 여러 팀이 기대는 핵심 데이터부터 계약을 맺는다.

### dbt 테스트와 Great Expectations는 어떻게 다른가?

dbt는 웨어하우스 안의 변환 SQL 옆에 테스트를 적고, `dbt build`가 모델을 만든 직후 테스트를 돌려 실패하면 하류 모델을 건너뛴다. Great Expectations는 Python에서 기대값 묶음을 정의해 pandas, Spark, SQL에 돌리고 결과 문서를 남겨서, 웨어하우스 밖의 데이터에도 쓸 수 있다. 무엇을 어느 단계에서 검사하고 실패하면 어떻게 할지는 도구와 상관없이 정해야 한다.

### 틀린 데이터가 이미 대시보드에 나갔다면 어떻게 대응하나?

먼저 그 테이블의 갱신을 멈추고 대시보드에 확인 중임을 알린다. 칸별 날짜별 지표로 처음 틀린 날짜와 칸을 찾고, 계보로 하류 테이블·대시보드·보고서 목록을 만들어 알릴 범위를 정한다. 원인을 고친 뒤 영향받은 날짜만 멱등한 적재로 다시 계산하고, 그 사고를 잡았을 검사를 추가한다.
