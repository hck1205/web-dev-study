  한 번 검사를 통과한 주소라도 중간에 다른 곳으로 넘겨 버리거나 뒤늦게 번호가 바뀔 수 있으니, 검사한 그 번호로만 연결하고 넘어갈 때마다 다시 검사한다.

"이미지 URL을 붙여넣으면 썸네일을 만들어 주는" 기능을 만들었다. 사용자가 준 주소를 서버가 `fetch`해서 이미지를 받아 온다. 누군가 이미지 주소 대신 `http://169.254.169.254/latest/meta-data/iam/security-credentials/`를 넣었다. 서버가 그 주소로 요청을 보냈고, 클라우드가 발급한 임시 자격증명이 응답으로 돌아왔다. 그 키로 공격자는 우리 클라우드 계정에서 할 수 있는 일을 한다.

이게 SSRF(Server-Side Request Forgery), 서버 측 요청 위조다. 공격자가 직접 못 가는 내부 주소를, 그 내부에 있는 **우리 서버를 시켜** 대신 요청하게 만든다. 서버는 외부에서 못 닿는 사설망·메타데이터·내부 API에 닿을 수 있다는 점이 핵심이다. OWASP Top 10에서 SSRF는 2021년에 A10으로 독립 항목이 됐다. 클라우드가 퍼지면서 메타데이터 엔드포인트 탈취 같은 피해가 커진 것이 반영됐다.

이 글은 컨테이너 안에서 가짜 메타데이터 서버를 실제 링크로컬 IP에 띄우고, URL을 받아 `fetch`하는 취약한 서버를 공격한 뒤, resolved-IP 검사와 `net.BlockList`로 막는 과정을 실제 출력으로 본다. 보내는 쪽(서버가 외부를 부를 때) 관점은 [웹훅](/posts/webhooks)에서도 짧게 다룬다. 이 글은 그 위험을 깊게 판다.

## 못 가는 곳을 서버가 대신 간다

SSRF가 왜 위험한지는 네트워크 위치로 이해하면 빠르다. 공격자는 인터넷에 있고, 우리 앱 서버는 사설망 안에 있다. 사설망 안에는 외부에서 못 닿는 것들이 있다. 클라우드 메타데이터(`169.254.169.254`), 내부 DB, 관리용 API 같은 것들이다. 앱 서버가 사용자 URL을 그대로 받아 요청하면, 공격자는 앱 서버의 네트워크 위치를 빌려 그것들에 닿는다.

실제로 가짜 메타데이터 서버를 `169.254.169.254:80`에 띄우고(리눅스 루프백에 그 IP를 붙였다), URL을 받아 `fetch`하는 취약한 서버에 그 주소를 넘겼다.

```text
=== 1. IMDSv1 SSRF: fetch attacker-supplied metadata URL ===
   {"AccessKeyId":"ASIA...FAKE","SecretAccessKey":"wJal...FAKE","Token":"FwoG...FAK
```

자격증명(값은 가짜다)이 그대로 응답에 실려 나왔다. 클라우드 환경이라면 이 키로 S3를 읽거나 다른 자원을 만질 수 있다. 메타데이터 엔드포인트가 SSRF의 1순위 표적인 이유다.

## IMDSv2는 한 겹을 더 둔다

AWS는 이 공격 때문에 메타데이터 접근 방식을 바꿨다. 예전 방식(IMDSv1)은 그냥 GET하면 자격증명을 줬다. SSRF로 GET 한 번이면 끝이었다. IMDSv2는 먼저 `PUT`으로 토큰을 받고, 이후 요청마다 그 토큰을 헤더에 실어야 한다. 가짜 서버로 이 흐름을 재현했다.

```text
=== 2. IMDSv2 needs a PUT token first ===
   PUT token minted = TOKEN-179252...  (IMDSv2는 이 PUT이 필요하다)
```

여기서 SSRF 방어의 핵심 포인트가 나온다. 많은 SSRF는 **GET만** 보낼 수 있다(이미지 URL, 리다이렉트 등). `PUT`과 커스텀 헤더를 자유롭게 넣지 못하는 SSRF는 IMDSv2 토큰을 만들 수 없다. 게다가 IMDSv2는 응답의 홉 제한(TTL)도 1로 둬서, 여러 홉을 거친 프록시성 요청을 걸러 낸다. 그래서 IMDSv2를 강제하면(인스턴스 설정에서 IMDSv1을 끈다) SSRF로 메타데이터를 터는 경로 상당수가 막힌다. 다만 이것만 믿으면 안 된다. 메타데이터 말고도 내부 DB·관리 API 같은 표적이 남아 있다.

## 문자열 차단 목록은 거의 다 뚫린다

"그럼 `169.254.169.254`랑 `localhost`를 URL에서 막으면 되지 않나" 싶다. 이게 흔한 실수다. 같은 IP를 적는 방법이 너무 많다. 10진수, 16진수, 8진수, IPv6 표기까지 섞으면 문자열 매칭은 전부 샌다. 각 표기가 실제로 어디로 해석되는지 `dns.lookup`으로 확인했다.

## 해석한 IP를 검사하고 그 IP로 고정한다

제대로 된 방어는 문자열이 아니라 **해석된 IP**를 본다. 순서가 중요하다. 호스트 이름을 IP로 해석하고(DNS lookup), 그 IP가 사설·루프백·링크로컬 대역이면 거부하고, 통과하면 그 해석한 IP로 연결을 고정한다. 노드의 `net.BlockList`로 내부 대역을 등록해 검사했다.

같은 공격 URL들을 이 `safeFetch`에 넣어 봤다.

```text
=== 4. Defense: resolve host, check resolved IP, then fetch ===
   http://169.254.169.254/latest/meta-data/  -> REJECT: blocked internal IP 169.254.169.254
   http://2130706433/                        -> REJECT: blocked internal IP 127.0.0.1 (host 127.0.0.1)
   file:///etc/passwd                        -> REJECT: scheme not allowed: file:
   8.8.8.8                                    -> blocked? false
```

메타데이터 IP는 직접 표기로도, 10진수 `2130706433`으로도 막혔다. 10진수는 해석 단계에서 `127.0.0.1`로 드러나 거부됐다. `file:` 스킴도 막혔고, 공개 IP `8.8.8.8`은 통과했다. 문자열이 아니라 해석된 IP를 보는 게 차이를 만든다.

## 리다이렉트와 DNS 리바인딩이라는 뒷문

해석한 IP를 검사해도 두 가지 우회가 남는다. 첫째는 **리다이렉트**다. 공격자가 허용될 법한 주소를 주되, 그 주소가 `302`로 메타데이터 IP로 넘긴다. `fetch`는 기본적으로 리다이렉트를 따라가므로, 처음 URL만 검사하면 뚫린다.

실제로 리다이렉트를 따라가니 자격증명이 돌아왔고, `redirect: "manual"`로 바꿔 각 홉을 다시 검사하니 막혔다.

```text
=== 5. Redirect-based SSRF ===
   following redirects (fetch default):
   final url = http://169.254.169.254/latest/meta-data/iam | body = {"AccessKeyId":"ASIA...FAKE",...
   fix: redirect:"manual" and re-validate each hop
   hop -> http://169.254.169.254/latest/meta-data/iam  resolves 169.254.169.254  BLOCKED
```

둘째는 **DNS 리바인딩**이다. 검사할 때 호스트를 해석하면 공개 IP가 나와 통과하고, 잠시 뒤 실제로 연결할 때 다시 해석하면 그 사이 공격자가 DNS 레코드를 내부 IP로 바꿔 둔다. "검사한 IP"와 "연결한 IP"가 달라지는 시점 차이(TOCTOU) 공격이다.

```text
=== 6. DNS rebinding (TOCTOU) ===
   check-time resolve = 8.8.8.8 (passes), connect-time resolve = 127.0.0.1 (internal!)
   fix: resolve ONCE, validate, then connect to that pinned IP
```

막는 법은 하나다. 호스트를 **한 번만** 해석하고, 그 IP를 검사한 뒤, 바로 그 IP로 연결을 고정한다(드라이버의 lookup 옵션이나 커스텀 에이전트로 IP를 박는다). 리다이렉트도 홉마다 같은 검사를 반복한다.

## 네트워크로 한 겹 더 가둔다

## 실제로 SSRF를 만나는 순간

SSRF가 있는 기능은 패턴이 있다. 사용자가 준 URL·호스트·IP를 서버가 요청하는 곳이다. 썸네일 생성, 웹훅 등록, 문서 가져오기, 오픈 그래프 미리보기, PDF 렌더러, 파일 import URL 같은 기능을 먼저 본다. 이런 엔드포인트에서 서버의 아웃바운드 로그에 사설 대역(`10.`, `192.168.`, `169.254.`)이나 `127.0.0.1`로 나간 요청이 보이면 SSRF를 의심한다.

확인 순서는 이렇다. 먼저 그 기능이 URL을 어떻게 가져오는지 코드에서 본다(문자열 블랙리스트만 있으면 취약). 다음으로 리다이렉트를 따라가는지, 해석한 IP를 검사하는지, IP를 고정하는지 본다. 마지막으로 인스턴스의 메타데이터가 IMDSv2 강제인지, egress 정책이 있는지 확인한다. 가장 흔한 실수는 문자열 차단만 해 두고 10진수·리다이렉트·IPv6 우회를 놓치는 것, 그리고 `fetch`의 리다이렉트 자동 추적을 그대로 둔 것이다.

정리하면 SSRF는 "서버에게 대신 요청시키는" 공격이고, 막는 방법은 문자열이 아니라 해석된 IP를 검사하고 그 IP로 연결을 고정하는 것이다. 메타데이터는 IMDSv2로, 네트워크는 egress 정책으로 한 겹씩 더 가둔다. 사용자 URL을 서버가 부르는 모든 기능에서 이걸 챙긴다.

## 면접에서 나올 만한 질문

### SSRF는 무엇이고 왜 위험한가

공격자가 직접 닿지 못하는 내부 주소를, 그 내부에 있는 우리 서버를 시켜 대신 요청하게 만드는 공격이다. 앱 서버는 사설망 안에 있어 메타데이터 엔드포인트, 내부 DB, 관리 API 같은 외부 차단 자원에 닿을 수 있다. 특히 클라우드 메타데이터에서 임시 자격증명을 빼내 계정을 장악할 수 있어 위험하다. 실험에서도 사용자 URL을 그대로 fetch하자 169.254.169.254의 자격증명이 응답에 실려 나왔다.

### 왜 문자열로 169.254.169.254나 localhost를 막는 건 부족한가

같은 IP를 적는 방법이 너무 많아서다. 10진수 2130706433, 16진수 0x7f000001, 8진수 0177.0.0.1, IPv6 [::1]이 모두 루프백으로 해석되지만 문자열로는 안 걸린다. 실험에서 이 표기들이 전부 127.0.0.1로 해석됐다. 그래서 문자열이 아니라 DNS로 해석한 실제 IP를 보고 사설·루프백·링크로컬 대역이면 거부해야 한다.

### IMDSv2는 SSRF를 어떻게 줄이나

메타데이터 접근 전에 PUT으로 토큰을 받고 이후 요청마다 그 토큰을 헤더에 싣게 한다. 많은 SSRF는 GET만 보낼 수 있어 PUT과 커스텀 헤더로 토큰을 만들지 못하고, 응답 홉 제한(TTL 1)이 프록시성 요청도 걸러 낸다. 그래서 IMDSv1을 끄고 IMDSv2를 강제하면 메타데이터를 터는 경로 상당수가 막힌다. 다만 내부 DB·관리 API 같은 다른 표적은 남으니 이것만 믿으면 안 된다.

### 해석한 IP를 검사했는데도 뚫리는 경우는

두 가지다. 리다이렉트는 처음 URL만 검사하면, fetch가 302를 따라가다 내부 IP에 닿는다. 실험에서 공개 호스트가 메타데이터 IP로 리다이렉트하자 자격증명이 돌아왔고, redirect를 수동 처리해 각 홉을 재검사하니 막혔다. DNS 리바인딩은 검사 시점엔 공개 IP, 연결 시점엔 내부 IP로 레코드를 바꾸는 시점 차이 공격이다. 호스트를 한 번만 해석해 검사하고 그 IP로 연결을 고정하면 둘 다 막힌다.

### 애플리케이션 코드 외에 네트워크로 SSRF를 막는 방법은

서버의 egress(바깥으로 나가는 트래픽)를 네트워크에서 차단한다. 쿠버네티스라면 NetworkPolicy로 Pod egress를 좁혀 169.254.169.254/32와 사설 대역행 연결을 막고, 클라우드 VPC라면 보안 그룹·네트워크 ACL의 아웃바운드 규칙으로 같은 일을 한다. 코드에 빈틈이 있어도 패킷이 내부에 못 닿게 하는 2차 방어다.

### 어떤 기능에서 SSRF를 먼저 의심하나

사용자가 준 URL·호스트·IP를 서버가 요청하는 기능이다. 썸네일 생성, 웹훅 등록, 문서 가져오기, 오픈 그래프 미리보기, PDF 렌더러, import URL 같은 곳을 먼저 본다. 서버 아웃바운드 로그에 10., 192.168., 169.254. 같은 사설 대역이나 127.0.0.1로 나간 요청이 보이면 SSRF 신호다. 그 기능이 문자열 블랙리스트만 쓰는지, 리다이렉트를 따라가는지부터 확인한다.

### SSRF와 CSRF는 어떻게 다른가

둘 다 "요청을 위조"하지만 주체가 다르다. CSRF는 사용자의 브라우저를 속여 피해 사이트로 요청을 보내게 하고, 사용자의 쿠키가 실린다. SSRF는 우리 서버를 속여 내부 주소로 요청을 보내게 하고, 서버의 네트워크 위치와 권한이 쓰인다. CSRF 방어는 토큰·SameSite 같은 브라우저 축, SSRF 방어는 해석된 IP 검사·egress 정책 같은 서버·네트워크 축이다.
