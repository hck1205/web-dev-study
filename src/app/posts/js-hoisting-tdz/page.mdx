<EasyIntro>
  자바스크립트는 코드를 한 줄씩 읽어 나가기 전에 그 안에 어떤 이름이 선언돼 있는지 먼저 명단에 적어 둔다. 그래서 선언보다 위에 있는 줄에서도 그 이름을 알아본다. 이걸 호이스팅이라고 부르는데, 코드가 실제로 위로 옮겨지는 게 아니라 이름을 미리 적어 두는 것뿐이다.

  다만 명단에 적을 때 값까지 채우느냐가 선언 종류마다 다르다. 함수 선언은 함수까지 채워 두니 아래에 써도 위에서 부를 수 있고, var는 일단 비어 있다는 뜻의 undefined로 채운다. let과 const와 class는 이름만 적고 값은 비워 두기 때문에, 선언 줄이 실행되기 전에 읽으면 오류가 난다.

  이름은 있는데 아직 값이 없는 그 시간을 TDZ라고 부른다. 코드의 위치가 아니라 실행되는 순서가 기준이라서, 같은 코드라도 언제 불리느냐에 따라 되기도 하고 안 되기도 한다.
</EasyIntro>

유틸 파일을 정리하면서 함수 선언을 화살표 함수로 바꿨다. 코드 모양만 바꾼 건데 바로 오류가 났다.

```js
// 바꾸기 전
console.log(formatPrice(1200));
function formatPrice(n) {
  return n.toLocaleString("ko-KR") + "원";
}
```

```text
1,200원
```

```js
// 바꾼 뒤
console.log(formatPrice(1200));
const formatPrice = (n) => n.toLocaleString("ko-KR") + "원";
```

```text
h2.js:1
console.log(formatPrice(1200));
            ^

ReferenceError: Cannot access 'formatPrice' before initialization
```

Node 22에서 돌린 결과다. 함수 선언은 아래에 있어도 위에서 부를 수 있었는데, `const`로 바꾸자 "초기화 전에는 접근할 수 없다"는 오류가 났다. 흥미로운 건 오류 문구다. "`formatPrice`가 없다"가 아니라 "아직 초기화되지 않았다"고 한다. 엔진은 이 줄을 실행할 때 이미 `formatPrice`라는 이름을 알고 있었다는 뜻이다.

이 글은 그 "미리 안다"가 무엇인지, 그리고 왜 `var`, 함수, `let`이 각자 다르게 대답하는지 따라간다. 범위 자체는 [var, let, const 글](/posts/js-var-let-const)과 [스코프 글](/posts/js-scope-lexical)에서 다뤘으니, 여기서는 시간 순서에 집중한다.

## 실행 전에 이름부터 등록한다

자바스크립트 엔진은 함수(또는 스크립트, 모듈)를 실행하기 전에 그 범위 안의 선언을 먼저 훑는다. 명세에서는 이 단계를 `FunctionDeclarationInstantiation`, 전역이면 `GlobalDeclarationInstantiation`이라고 부른다. 여기서 선언된 이름이 모두 환경 레코드에 등록되고, 그다음에 첫 줄부터 실행이 시작된다.

선언이 코드 위로 끌어올려진 것처럼 보인다고 해서 이걸 호이스팅(hoisting)이라고 부른다. 명세에 정의된 용어는 아니다. 실제로 코드가 움직이는 일은 없고, 실행 전에 이름을 등록하는 단계가 있을 뿐이다. 이 단계가 실행 컨텍스트, 콜 스택과 어떻게 이어지는지는 [실행 컨텍스트 글](/posts/js-execution-context)에서 다룬다.

등록할 때 초기화하는 방식이 선언 종류마다 다르다. 이 코드로 확인해 보자.

```js
console.log(a);
console.log(hello());
console.log(b);
var a = 1;
let b = 2;
function hello() {
  return "hi";
}
```

```text
undefined
hi
two.js:3
console.log(b);
            ^

ReferenceError: Cannot access 'b' before initialization
```

## 선언마다 초기화하는 시점이 다르다

정리하면 이름 하나는 세 상태를 거친다. 등록됨, 초기화됨, 값이 바뀜. 선언 종류마다 어느 상태에서 실행을 시작하는지가 다르다.

- `var`는 등록과 동시에 `undefined`로 초기화된다. 선언 줄보다 먼저 읽으면 오류 없이 `undefined`가 나온다.
- 함수 선언(`function f() {}`)은 등록과 동시에 함수 객체로 초기화된다. 그래서 아래에 써도 위에서 부를 수 있다.
- `let`, `const`, `class`는 등록만 되고 초기화되지 않는다. 선언 줄이 실행돼야 초기화된다. 등록부터 초기화까지의 구간을 TDZ(Temporal Dead Zone, 일시적 사각지대)라고 부르고, 이 구간에 이름에 닿으면 `ReferenceError`다.

함수 표현식은 함수 선언이 아니다. `var g = function () {}`는 `var` 규칙을 따르니 등록 단계에서 `g`는 `undefined`다. 처음 예제의 `const formatPrice = () => {}`도 함수처럼 보이지만 `const` 규칙을 따른다.

```js
try { new Cart(); } catch (e) { console.log(e.name + ": " + e.message); }
class Cart {}
try { g(); } catch (e) { console.log(e.name + ": " + e.message); }
var g = function () {};
```

```text
ReferenceError: Cannot access 'Cart' before initialization
TypeError: g is not a function
```

같은 이름에 `var`와 함수 선언이 둘 다 있으면 등록 단계에서는 함수가 이긴다. `var`는 이미 있는 이름을 `undefined`로 덮지 않는다. 대입 줄이 실행되면 그때 바뀐다.

```js
console.log(typeof f);
var f = 1;
function f() {}
console.log(typeof f);
```

```text
function
number
```

등록 단계의 규칙을 함수로 직접 써 보자. 선언 목록을 받아서 실행을 시작하는 순간 각 이름이 어떤 상태인지 돌려준다.

크롬 계열과 Node.js(V8)의 문구다. 파이어폭스는 `can't access lexical declaration 'x' before initialization`처럼 다르게 쓰니, 오류 수집 도구에서 묶을 때는 둘 다 고려한다.

## TDZ는 위치가 아니라 시간이다

TDZ의 T는 Temporal, 시간이다. 코드에서 선언보다 위에 적혔느냐가 아니라 선언 줄이 실행되기 전에 읽었느냐가 기준이다.

```js
function readLimit() {
  return limit;
}
try { readLimit(); } catch (e) { console.log("before:", e.message); }
let limit = 10;
console.log("after:", readLimit());
```

```text
before: Cannot access 'limit' before initialization
after: 10
```

`readLimit` 안의 `return limit`은 글자로는 선언보다 위에 있다. 그래도 두 번째 호출은 성공한다. 그때는 `let limit = 10`이 이미 실행됐기 때문이다. 아래 그림은 같은 함수가 언제 불리느냐에 따라 결과가 갈리는 과정이다.

이 성질이 실무에서 중요한 이유는 버그가 실행 경로에 따라 나타났다 사라진다는 데 있다. 모듈 최상위에서 초기화 코드가 어떤 함수를 먼저 부르는지, 이벤트가 언제 들어오는지에 따라 같은 코드가 어떤 때는 되고 어떤 때는 안 된다.

TDZ에는 몇 가지 덜 알려진 모서리가 있다.

```js
console.log(typeof notDeclared);
try { console.log(typeof b); } catch (e) { console.log(e.name + ": " + e.message); }
let b = 2;
```

```text
undefined
ReferenceError: Cannot access 'b' before initialization
```

`typeof`는 선언되지 않은 이름에는 오류 없이 `"undefined"`를 주지만, TDZ에 있는 이름에는 오류를 던진다. "`typeof`는 안전하다"는 오래된 습관이 `let` 앞에서는 통하지 않는다.

```js
try { let x = x; } catch (e) { console.log(e.name + ": " + e.message); }
function f(a = b, b = 1) { return [a, b]; }
try { f(); } catch (e) { console.log(e.name + ": " + e.message); }
console.log(f(5));
```

```text
ReferenceError: Cannot access 'x' before initialization
ReferenceError: Cannot access 'b' before initialization
[ 5, 1 ]
```

`let x = x`의 오른쪽 `x`는 바깥 `x`가 아니라 지금 선언 중인 `x`다. 초기화는 오른쪽을 다 계산한 뒤라서 TDZ에 걸린다. 매개변수 기본값도 왼쪽부터 차례로 초기화되므로 `a`의 기본값에서 아직 초기화 전인 `b`를 읽으면 실패한다. `a`를 직접 넘기면 `b`를 읽지 않으니 통과한다.

## 바깥 이름이 있어도 TDZ가 이긴다

TDZ가 바깥 변수를 가리는 방식도 기억해 둘 만하다.

```js
let theme = "light";
function render() {
  console.log(theme);
  let theme = "dark";
}
render();
```

```text
shadow.js:3
  console.log(theme);
              ^

ReferenceError: Cannot access 'theme' before initialization
```

`console.log(theme)`가 바깥의 `"light"`를 읽을 것 같지만 그렇지 않다. 함수 범위에 `theme`가 등록된 순간부터 그 범위 전체에서 `theme`는 안쪽 이름을 가리킨다. 아직 초기화 전이니 오류다.

왜 이렇게 만들었을까. TDZ가 없다면 두 가지 선택지가 있었다. `var`처럼 `undefined`로 초기화하면 `const`가 `undefined`였다가 값이 되는, 상수인데 두 값을 갖는 순간이 생긴다. 선언 줄 전까지 바깥 `theme`를 보게 하면 한 블록 안에서 같은 이름이 줄마다 다른 변수를 가리킨다. ES2015는 둘 다 버리고 "초기화 전에 읽으면 오류"를 골랐다. 선언 전 사용을 실수로 보고 일찍 알려 주는 쪽이다. 클래스도 같은 규칙을 따라, 상속 관계의 클래스가 정의되기 전에 쓰이는 일을 막는다.

## 블록 안의 함수 선언은 모드마다 다르다

함수 선언을 `if` 블록 안에 쓰면 엄격 모드 여부에 따라 결과가 달라진다. 느슨한 모드에서는 웹 호환성 때문에 명세 부록(Annex B)의 특별 규칙이 적용된다.

```js
console.log(typeof inner);
if (true) {
  function inner() {}
}
console.log(typeof inner);
```

```text
undefined
function
```

느슨한 모드에서는 바깥 함수 범위에 `var`처럼 `inner`가 `undefined`로 등록되고, 블록이 실행될 때 함수가 복사된다. 맨 위에 `"use strict";`를 붙이면 이렇게 바뀐다.

```text
undefined
undefined
```

엄격 모드에서는 `inner`가 블록 범위에만 있어서 블록 밖에서 보이지 않는다. ES 모듈과 클래스는 자동으로 엄격 모드라서 번들러를 쓰는 코드는 대부분 아래쪽 동작이다. 같은 코드를 레거시 스크립트로 옮기면 동작이 바뀐다는 뜻이기도 하다. 블록 안에서는 함수 선언 대신 `const fn = () => {}`를 쓰면 모드와 상관없이 동작이 하나로 정해진다. 엄격 모드 차이는 [strict mode 글](/posts/js-strict-mode)에 더 있다.

## 순환 import가 TDZ를 부른다

실무에서 `Cannot access 'X' before initialization`를 가장 자주 만나는 곳은 내가 쓴 한 파일이 아니라 모듈 사이다. 개발 서버에서는 멀쩡했는데 빌드한 번들에서 이 오류가 나는 경우, 순환 import부터 의심한다.

파일 세 개로 재현해 봤다.

```js
// main.mjs
import { formatPrice } from "./format.mjs";
console.log(formatPrice(1200));

// format.mjs
import { CURRENCY } from "./config.mjs";
export const formatPrice = (n) => n.toLocaleString("ko-KR") + CURRENCY;

// config.mjs
import { formatPrice } from "./format.mjs";
export const CURRENCY = "원";
export const SAMPLE = formatPrice(1000); // 설정 파일에서 미리 계산해 두려 했다
```

```text
config.mjs:3
export const SAMPLE = formatPrice(1000); // 설정 파일에서 미리 계산해 두려 했다
                      ^

ReferenceError: Cannot access 'formatPrice' before initialization
    at config.mjs:3:23
```

ES 모듈은 실행 전에 import 문을 모두 따라가 모듈 그래프를 만들고 이름을 연결한다. import가 파일 중간에 있어도 맨 위로 끌어올려진 것처럼 동작하는 이유다. 그다음 의존 관계의 가장 깊은 곳부터 실행한다. 아래 그림에서 그 순서를 따라가 보자.

import로 받은 이름은 값의 복사가 아니라 내보낸 모듈의 칸에 연결된 라이브 바인딩이다. 그래서 내보낸 쪽의 `const`가 TDZ면 가져온 쪽도 TDZ다. 라이브 바인딩 이야기는 [ES 모듈 글](/posts/js-es-modules)에서 더 다룬다.

CommonJS로 같은 구조를 만들면 증상이 다르다.

```text
config.js:3
exports.SAMPLE = format.formatPrice(1000); // 설정 파일에서 미리 계산해 두려 했다
                        ^

TypeError: format.formatPrice is not a function
    at Object.<anonymous> (config.js:3:25)
```

CommonJS의 `require`는 순환을 만나면 아직 다 채워지지 않은 `exports` 객체를 그대로 돌려준다. 이름이 없으니 TDZ가 아니라 `undefined`를 호출한 `TypeError`다. 번들러가 ESM을 CommonJS 비슷한 코드로 바꿔 내보내는 설정이라면 운영 오류가 이쪽 모양으로 나오기도 한다.

순환은 도구로 찾는다. madge 8로 위 폴더를 검사했다.

```bash
npx madge --circular --extensions mjs main.mjs
```

```text
Processed 3 files (551ms)

✖ Found 1 circular dependency!

1) config.mjs > format.mjs
```

고치는 방법은 세 가지 중에서 고른다. 가장 확실한 건 순환을 끊는 것이다. 두 파일이 서로 필요로 하는 부분(여기서는 `CURRENCY`)을 세 번째 파일로 빼면 그래프가 한 방향이 된다. 순환을 당장 끊기 어렵다면 최상위에서 호출하지 말고 호출을 함수 안으로 미룬다.

```js
// config.mjs
import { formatPrice } from "./format.mjs";
export const CURRENCY = "원";
export const sample = () => formatPrice(1000); // 호출을 나중으로 미룬다
```

```text
1,200원
```

`sample`이 실제로 불릴 때는 `format.mjs`가 이미 실행된 뒤라서 TDZ가 끝나 있다. TDZ가 시간 기준이라는 성질을 이용한 셈이다. 다만 순환 자체는 남아 있으니, 나중에 누가 최상위 호출을 다시 넣으면 같은 오류가 돌아온다. 세 번째 방법인 import 순서 바꾸기는 진입점이 바뀌면 다시 깨지므로 피한다.

<Callout kind="tip" title="배럴 파일이 순환을 숨긴다">
`index.ts`에서 폴더의 모든 것을 다시 내보내는 배럴 파일을 쓰면, 같은 폴더 안 파일끼리 배럴을 거쳐 import하다가 보이지 않는 순환이 생기기 쉽다. 폴더 안에서는 배럴 대신 옆 파일을 직접 import한다.
</Callout>

## React 파일에서 만나는 경우

컴포넌트를 `const`로 정의하는 게 보통이라 React 코드에서도 TDZ를 만난다. 경계선은 "모듈을 읽는 순간 실행되는가, 렌더링할 때 실행되는가"다.

```js
function App() {
  return "<div>" + Button() + "</div>";
}
const Button = () => "<button>ok</button>";
console.log(App());
```

```text
<div><button>ok</button></div>
```

`App` 본문은 `App()`이 불릴 때 실행되고, 그때는 `Button`이 초기화된 뒤다. JSX로 쓴 실제 컴포넌트도 마찬가지라서 파일 아래쪽에 정의한 자식 컴포넌트를 위쪽 컴포넌트에서 써도 된다. 반대로 모듈 최상위에서 즉시 평가되는 값은 문제가 된다.

```js
const ICONS = { home: HomeIcon };
const HomeIcon = () => "home";
```

```text
h9.js:1
const ICONS = { home: HomeIcon };
                      ^

ReferenceError: Cannot access 'HomeIcon' before initialization
```

라우트 설정 배열, 아이콘 맵, `styled(Button)`처럼 다른 컴포넌트를 감싸는 코드는 모듈을 읽는 순간 실행된다. 이런 값은 참조하는 컴포넌트 정의 아래에 둔다. 컴포넌트 함수 안에서도 같다. 렌더링 중에 `const total = calc(items)`를 `const calc = ...`보다 위에 쓰면 매 렌더 TDZ에 걸린다. `useEffect` 콜백 안에서 아래에 정의한 함수를 부르는 건 이펙트가 렌더 이후에 실행되니 괜찮다.

## 도구로 미리 잡기

TDZ 오류는 실행해 봐야 나는 런타임 오류지만, 정적 분석으로 상당 부분 미리 잡힌다. TypeScript 5.9로 같은 범위의 사용을 검사했다.

```ts
console.log(formatPrice(1200));
const formatPrice = (n: number) => n.toLocaleString("ko-KR") + "원";

new Cart();
class Cart {}

function readLimit() {
  return limit;
}
readLimit();
let limit = 10;
```

```text
t.ts(1,13): error TS2448: Block-scoped variable 'formatPrice' used before its declaration.
t.ts(1,13): error TS2454: Variable 'formatPrice' is used before being assigned.
t.ts(4,5): error TS2449: Class 'Cart' used before its declaration.
```

같은 범위에서 바로 쓰는 경우는 잡지만 `readLimit()`처럼 함수 안에서 읽고 그 함수를 일찍 부르는 경우는 잡지 못한다. 실행 순서까지 따라가야 알 수 있기 때문이다.

ESLint의 `no-use-before-define`은 기본값이 엄격하다. 기본 설정으로 `limit.js`, `icons.js`, 앞의 `App`/`Button` 예제(`app.js`)를 검사하면 셋 다 오류로 잡는다. 문제없이 도는 `app.js`까지 걸리는 셈이다. `{ variables: false }` 옵션을 주면 안쪽 함수에서 바깥 변수를 참조하는 경우는 넘어가고 같은 범위의 사용만 잡는다.

```text
icons.js
  1:23  error  'HomeIcon' was used before it was defined  no-use-before-define

✖ 1 problem (1 error, 0 warnings)
```

(파일 경로 줄은 이름만 남겼다.) 모듈 최상위에서 즉시 실행되는 진짜 위험만 남는다. 컴포넌트를 아래에 정의하는 스타일을 쓰는 React 프로젝트에서 현실적인 설정이다.

## 다시 formatPrice로

처음 코드에서 함수 선언 `formatPrice`는 등록 단계에서 함수 객체까지 들어가 있었으니 위에서 불러도 됐다. `const formatPrice`로 바꾸자 이름만 등록되고 선언 줄이 실행되기 전까지 비어 있게 됐고, 첫 줄은 그 비어 있는 시간에 이름을 읽었다. 고치려면 호출을 선언 아래로 내리거나, 함수 선언으로 되돌린다. 모든 선언은 실행 전에 등록되고, `var`는 `undefined`로, 함수는 함수로, `let`·`const`·`class`는 비어 있는 채로 출발한다. 그 비어 있는 시간이 TDZ이고, 모듈 사이에서는 순환 import가 그 시간을 늘린다.

## 면접에서 나올 만한 질문

### 호이스팅이 무엇인가요?

실행 전에 범위 안의 선언을 먼저 등록하는 동작을 부르는 말이다. 코드가 실제로 위로 옮겨지는 게 아니라 명세의 선언 초기화 단계에서 이름이 환경 레코드에 미리 만들어진다. 그래서 선언보다 위에서도 이름에 닿을 수 있고, 무엇이 나오는지는 선언 종류에 따라 다르다. `var`는 `undefined`, 함수 선언은 함수 객체, `let`·`const`·`class`는 초기화 전 상태다.

### let과 const는 호이스팅되지 않나요?

호이스팅된다. 이름은 실행 전에 등록되지만 초기화되지 않을 뿐이다. 그 증거로 바깥에 같은 이름이 있어도 선언 전에 읽으면 바깥 값을 보지 않고 `ReferenceError`가 난다. 그 이름이 이미 범위 전체를 차지하고 있기 때문이다.

### TDZ란 무엇이고 왜 존재하나요?

`let`, `const`, `class`의 이름이 등록된 시점부터 선언 줄이 실행돼 초기화될 때까지의 구간이고, 이때 접근하면 `ReferenceError`가 난다. `var`처럼 `undefined`로 시작하면 `const`가 두 값을 갖는 순간이 생기고, 바깥 이름을 보게 하면 한 블록 안에서 같은 이름이 줄마다 다른 변수를 가리킨다. 선언 전 사용을 일찍 오류로 알려 주는 쪽을 택한 것이다.

### TDZ에서 Temporal이 의미하는 것은 무엇인가요?

코드의 위치가 아니라 실행 시점이 기준이라는 뜻이다. 함수 안에서 아래쪽 `let`을 참조해도, 그 함수를 선언 줄 실행 뒤에 부르면 문제없다. 선언 줄 전에 부르면 같은 코드가 실패한다. 그래서 TDZ 버그는 실행 경로에 따라 나타났다 사라질 수 있다.

### 함수 선언과 함수 표현식의 호이스팅 차이는?

함수 선언은 등록 단계에서 함수 객체까지 초기화되어 선언 위에서도 호출할 수 있다. 함수 표현식은 담는 변수의 규칙을 따른다. `var`에 담으면 선언 전에는 `undefined`라 호출하면 `TypeError: is not a function`, `const`에 담으면 TDZ라서 `ReferenceError`다.

### 빌드한 번들에서만 Cannot access 'X' before initialization이 납니다. 어디부터 보나요?

순환 import부터 의심한다. ES 모듈은 의존 관계의 깊은 쪽부터 실행하는데, 순환이 있으면 한 모듈이 아직 실행되지 않은 모듈의 `const`를 최상위에서 읽게 되고 라이브 바인딩이라 TDZ 오류가 난다. 개발 서버와 번들은 모듈 실행 순서가 달라질 수 있어서 한쪽에서만 드러나기도 한다. madge 같은 도구로 순환을 찾고, 공통 부분을 별도 모듈로 빼거나 최상위 호출을 함수 안으로 미뤄서 고친다.

### typeof는 항상 안전한가요?

선언되지 않은 이름에는 오류 없이 `"undefined"`를 주지만 TDZ에 있는 이름에는 `ReferenceError`를 던진다. 그래서 `let`이나 `const`로 선언될 이름을 선언 전에 `typeof`로 확인하는 코드는 깨진다. 전역 기능 감지를 할 때는 `typeof window !== "undefined"`처럼 선언하지 않은 전역 이름에만 쓴다.
