[LeetCode 78. Subsets](https://leetcode.com/problems/subsets/)가 그 함수를 짜는 문제다. 백트래킹 패턴의 첫 문제로 자주 나오고, 여기서 익힌 틀이 [Combination Sum](/posts/leetcode-combination-sum), [Permutations](/posts/leetcode-permutations), [N-Queens](/posts/leetcode-n-queens)까지 그대로 이어진다. 이 글은 한 개씩 불려 가는 반복문, 넣는다/안 넣는다 재귀, 시작 위치를 넘기는 백트래킹, 비트마스크, 재귀 없는 스택 다섯 가지 풀이를 비교한다. 재귀와 백트래킹의 일반적인 틀은 [재귀와 백트래킹 글](/posts/recursion-backtracking)에 있고, 여기서는 이 문제에 맞춰 더 깊게 본다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 원소마다 넣을지 말지 정하는 문제

서로 다른 정수가 담긴 배열 `nums`가 주어진다. 이 원소들로 만들 수 있는 부분집합을 모두 돌려준다. 빈 집합도 부분집합이고, 배열 전체도 부분집합이다. 같은 부분집합이 두 번 나오면 안 되고, 답의 순서와 부분집합 안의 순서는 상관없다.

제약은 두 가지가 풀이를 정한다.

- 길이는 1 이상 10 이하다. 부분집합은 2^10 = 1024개가 최대라서 전부 만들어도 금방 끝난다.
- 원소는 서로 다르다. 같은 값이 섞이면 같은 부분집합이 두 번 나올 수 있는데, 이 문제는 그 걱정을 덜어 줬다. 섞인 버전은 [Subsets II](/posts/leetcode-subsets-ii)다.

부분집합의 개수가 왜 2^n인지부터 짚자. 원소 하나마다 "넣는다"와 "안 넣는다" 두 가지가 있고, 원소끼리의 선택은 서로 영향을 주지 않는다. 그래서 2를 n번 곱한다. 이 문제에서 출력 크기 자체가 2^n이니 어떤 풀이도 2^n보다 빨라질 수 없다. 이 문제의 "빠른 풀이"는 쓸데없는 일을 덜 하는 풀이라는 뜻이다.

## 손으로 [1, 2, 3]을 적어 보면

빠뜨리지 않으려면 규칙이 있어야 한다. 크기별로 적어 보자.

```text
크기 0: []
크기 1: [1] [2] [3]
크기 2: [1,2] [1,3] [2,3]
크기 3: [1,2,3]
```

1 + 3 + 3 + 1 = 8개다. 크기 k인 부분집합의 개수는 n개 중 k개를 고르는 조합 수 C(n, k)이고, 이걸 k = 0부터 n까지 더하면 2^n이 된다. 손으로 적을 때 쓴 규칙도 하나 있다. 부분집합 안에서는 늘 원래 배열 순서대로 적었다. `[2,1]`을 따로 적지 않은 이유다. 순서를 정해 두면 같은 부분집합을 두 번 적지 않는다. 이 규칙이 뒤에서 나올 "시작 위치" 풀이의 출발점이다.

다른 규칙으로도 적을 수 있다. 1이 없는 부분집합을 먼저 다 적고, 그 각각에 1을 붙이면 1이 있는 부분집합이 된다. 이 관찰은 첫 번째 풀이가 된다.

## 원소를 하나씩 들이며 답을 두 배로

빈 집합 하나에서 시작한다. 원소 하나를 들일 때마다, 지금까지 만든 부분집합 각각에 그 원소를 붙인 복사본을 더한다. 원래 것은 "그 원소를 안 넣은" 경우, 복사본은 "넣은" 경우다. 원소 하나마다 답이 정확히 두 배가 된다.

```js
function subsets(nums) {
  const res = [[]]; // 빈 집합 하나에서 시작
  for (const x of nums) {
    const size = res.length; // 이번 원소를 들이기 전의 개수를 고정한다
    for (let i = 0; i < size; i++) {
      res.push([...res[i], x]); // 기존 부분집합에 x를 붙인 복사본
    }
  }
  return res;
}
```

`[1, 2, 3]`에서 `res`가 늘어나는 모습을 따라가 보자. 칸은 들이는 원소이고, 기억 장소가 지금까지 만든 부분집합 목록이다.

```text
1 들인 뒤: [[],[1]]
```

재귀가 없어서 읽기 쉽고, 결과 순서도 깔끔하다. 시간은 O(n · 2^n)이다. 부분집합이 2^n개이고, 각각을 만들 때 평균 n/2개 원소를 복사하기 때문이다. 공간은 출력 말고는 거의 쓰지 않는다.

이 풀이에서 가장 흔한 실수는 `size`를 고정하지 않는 것이다.

```js
for (const x of nums) {
  for (let i = 0; i < res.length; i++) { // res.length가 계속 늘어난다
    res.push([...res[i], x]);
  }
}
```

방금 넣은 `[1]`에 또 1을 붙이고, 그 `[1,1]`에 또 붙인다. 20번만 돌리고 멈춰서 보니 앞쪽이 `[], [1], [1,1], [1,1,1], …`이었다. 멈추지 않고 두면 `JavaScript heap out of memory`로 죽었다. 반복문 안에서 자기 자신을 늘리는 배열을 돌 때는 시작할 때의 길이를 따로 잡는다.

한계도 분명하다. 모든 부분집합을 메모리에 들고 있어야 다음 원소를 붙일 수 있다. "크기가 2인 것만", "합이 10인 것만"처럼 조건이 붙으면, 조건에 안 맞는 중간 결과도 다 만들어 둬야 해서 낭비가 커진다. 원하는 것만 골라 만들려면 한 부분집합씩 끝까지 만들어 보는 탐색이 필요하다.

## 넣는다, 안 넣는다 두 갈래로 내려가기

원소를 앞에서부터 하나씩 보며 "넣는다"와 "안 넣는다" 두 갈래로 나누면 이진 트리가 생긴다. 깊이 n까지 내려가면 잎에 도착하고, 잎 하나가 부분집합 하나다. `[1, 2]`로 그려 보면 이렇다.

코드는 그림을 그대로 옮긴다. 만드는 중인 부분집합 `path` 하나를 들고 다니면서, 넣는 갈래에서는 push하고 돌아오면 pop한다.

```js
function subsets(nums) {
  const res = [];
  const path = [];

  function go(i) {
    if (i === nums.length) {   // 모든 원소를 정했으면 잎이다
      res.push([...path]);     // 지금 모습을 복사해서 기록
      return;
    }
    path.push(nums[i]);        // nums[i]를 넣는 갈래
    go(i + 1);
    path.pop();                // 되돌려 놓고
    go(i + 1);                 // 안 넣는 갈래
  }

  go(0);
  return res;
}
```

`[1, 2, 3]`이면 `[1,2,3] [1,2] [1,3] [1] [2,3] [2] [3] []` 순서로 나온다. 넣는 갈래를 먼저 가서 큰 것부터 나온다. 두 줄의 순서를 바꾸면 `[]`부터 나온다.

호출 횟수를 세 보면 n = 3에서 15번, n = 10에서 2047번이다. 완전 이진 트리의 마디 수 2^(n+1) - 1이다. 그중 잎이 2^n개라 답 하나에 호출이 두 번꼴이다. 시간은 잎마다 복사하는 비용까지 O(n · 2^n), 재귀 깊이는 n + 1이라 추가 공간은 O(n)이다.

이 풀이의 장점은 원소마다 무슨 결정을 했는지 코드에 그대로 보인다는 것이다. "넣을 때 합이 target을 넘으면 그 갈래는 가지 않는다" 같은 가지치기를 붙이기 쉽다. [0/1 배낭 문제](/posts/dynamic-programming)를 재귀로 짤 때의 모양과도 같다.

아쉬운 점은 답이 잎에서만 나온다는 것이다. 안쪽 마디 `[1]`(2를 볼 차례)은 답이 아니라 지나가는 길이다. 그래서 마디가 답의 두 배 가까이 된다. 마디 하나하나가 곧 답이 되게 트리를 다시 짤 수 있다.

## 시작 위치를 넘기면 모든 마디가 답이다

손으로 적을 때의 규칙을 떠올리자. 부분집합 안에서는 늘 배열 순서대로 적었다. 그렇다면 "다음에 넣을 원소는 마지막에 넣은 원소보다 뒤에 있는 것 중 하나"라고 정할 수 있다. 재귀 함수에 "여기부터 고를 수 있다"는 시작 위치 `start`를 넘기고, `start`부터 끝까지 하나씩 골라 본다.

이렇게 짜면 재귀 호출 하나하나가 서로 다른 부분집합이다. 들어오자마자 `path`를 기록하면 된다. `[1, 2, 3]`에서 `path`가 쌓이고 빠지는 모습을 따라가 보자. 칸은 원래 배열이고, 초록 칸이 지금 `path`에 들어 있는 원소다.

```js
function subsets(nums) {
  const res = [];
  const path = [];

  function go(start) {
    res.push([...path]);                   // 이 호출 자체가 부분집합 하나
    for (let i = start; i < nums.length; i++) {
      path.push(nums[i]);                  // 고른다
      go(i + 1);                           // i보다 뒤에서만 이어서 고른다
      path.pop();                          // 되돌린다
    }
  }

  go(0);
  return res;
}
```

결과는 `[] [1] [1,2] [1,2,3] [1,3] [2] [2,3] [3]`이다. 사전순(앞 원소부터 비교한 순서)과 같다. `go(i + 1)`에 `start + 1`이 아니라 `i + 1`을 넘기는 게 포인트다. `start + 1`을 넘기면 `[1,3]` 다음에 3이 또 후보로 남아서 `[1,3,3]` 같은 게 나온다.

호출 횟수는 n = 3에서 8번, n = 10에서 1024번이다. 정확히 답의 개수다. 앞 풀이보다 호출이 절반으로 줄었다. 그래도 시간 복잡도는 같은 O(n · 2^n)이다. 복사 비용이 그대로이기 때문이다. n = 20(약 105만 개)으로 재 보니 이 풀이가 374ms, 넣는다/안 넣는다 풀이가 346ms였다. 호출 수 차이보다 배열 복사와 메모리 할당이 시간을 정한다는 뜻이다.

이 모양이 백트래킹의 표준 틀이다. "고른다, 들어간다, 되돌린다" 세 줄이 for문 안에 있고, for문의 범위가 "다음에 무엇을 고를 수 있나"를 정한다. 범위를 바꾸면 다른 문제가 된다.

- 크기 k만: `path.length === k`일 때만 기록하고 돌아간다. LeetCode 77 Combinations다.
- 같은 원소를 또 써도 되면: `go(i)`를 넘긴다. [Combination Sum](/posts/leetcode-combination-sum)이다.
- 순서가 다르면 다른 답이면: `start` 대신 `used` 배열을 쓴다. [Permutations](/posts/leetcode-permutations)다.

### Python과 Java로 쓰면

Python은 리스트 복사를 `path[:]`로 쓴다. 재귀 깊이는 n + 1이 최대라 기본 한도 1000과 거리가 멀다.

```python
from typing import List

def subsets(nums: List[int]) -> List[List[int]]:
    res = []
    path = []

    def go(start: int) -> None:
        res.append(path[:])            # 지금 모습을 복사해 기록
        for i in range(start, len(nums)):
            path.append(nums[i])
            go(i + 1)
            path.pop()

    go(0)
    return res
```

라이브러리를 쓰면 `itertools.combinations`로 크기별 조합을 이어 붙여도 된다.

```python
from itertools import combinations

def subsets_lib(nums):
    return [list(c) for k in range(len(nums) + 1) for c in combinations(nums, k)]
```

`[1, 2, 3]`에서 `[[], [1], [2], [3], [1, 2], [1, 3], [2, 3], [1, 2, 3]]`로 크기순으로 나온다. 면접에서는 직접 짜는 걸 보여 주고, "실무라면 이걸 쓴다"고 한 줄 덧붙이는 정도가 좋다.

Java는 `List<List<Integer>>`를 돌려준다. 기록할 때 `new ArrayList<>(path)`로 복사한다.

```java
import java.util.ArrayList;
import java.util.List;

class Solution {
    public List<List<Integer>> subsets(int[] nums) {
        List<List<Integer>> res = new ArrayList<>();
        go(nums, 0, new ArrayList<>(), res);
        return res;
    }

    private void go(int[] nums, int start, List<Integer> path, List<List<Integer>> res) {
        res.add(new ArrayList<>(path)); // 복사본을 넣는다
        for (int i = start; i < nums.length; i++) {
            path.add(nums[i]);
            go(nums, i + 1, path, res);
            path.remove(path.size() - 1); // 인덱스로 지운다
        }
    }
}
```

Java에서 되돌리기를 `path.remove(nums[i])`로 쓰면 안 된다. `nums[i]`가 `int`라서 `remove(int index)`가 불린다. "값 5를 지워라"가 아니라 "5번 칸을 지워라"가 된다. 실제로 길이 1인 리스트에서 `path.remove(5)`를 부르면 이렇게 죽는다.

```text
Exception in thread "main" java.lang.IndexOutOfBoundsException: Index 5 out of bounds for length 1
```

값으로 지우려면 `path.remove(Integer.valueOf(x))`인데, 그건 맨 앞의 같은 값을 지우니 백트래킹에는 맞지 않다. 늘 마지막 칸을 `size() - 1`로 지운다.

세 언어 모두 `[1, 2, 3]`에서 같은 8개를, `[0]`에서 `[[], [0]]`을 낸다.

## 0부터 2^n - 1까지 세면 끝난다

넣는다/안 넣는다를 n번 고르는 건 n자리 이진수 하나를 정하는 것과 같다. i번째 비트가 1이면 `nums[i]`를 넣고 0이면 안 넣는다. 그러니 0부터 2^n - 1까지 정수를 세면서 비트를 읽으면 모든 부분집합이 한 번씩 나온다. 비트 연산이 낯설면 [비트 조작 글](/posts/bit-manipulation)을 먼저 보자.

```text
mask  비트  부분집합
 0    000   []
 1    001   [1]
 2    010   [2]
 3    011   [1,2]
 4    100   [3]
 5    101   [1,3]
 6    110   [2,3]
 7    111   [1,2,3]
```

비트는 오른쪽이 0번째다. mask 5 = `101`은 0번째와 2번째 비트가 켜져 있어서 `nums[0]`과 `nums[2]`, 곧 `[1,3]`이다.

```js
function subsets(nums) {
  const n = nums.length;
  const res = [];
  for (let mask = 0; mask < (1 << n); mask++) {  // 2^n가지 선택
    const sub = [];
    for (let i = 0; i < n; i++) {
      if (mask & (1 << i)) sub.push(nums[i]);    // i번째 비트가 켜졌으면 넣는다
    }
    res.push(sub);
  }
  return res;
}
```

재귀도 `path`도 없다. 부분집합 하나를 만드는 데 비트 n개를 다 보니 시간은 O(n · 2^n)이다. 다른 풀이는 짧은 부분집합을 빨리 만드는데, 이 풀이는 빈 집합에도 n번 검사한다. n = 20에서 527ms로 백트래킹보다 조금 느렸다.

비트마스크의 진짜 장점은 부분집합을 정수 하나로 다룰 수 있다는 점이다. 정수는 배열 인덱스나 해시 키가 되니 "부분집합마다 값을 기억해 두는" 동적 계획법(외판원 문제의 비트마스크 DP 같은)으로 이어진다. 두 부분집합의 교집합이 `a & b`, 합집합이 `a | b` 한 번이라 집합 연산도 빠르다.

한계는 정수 폭이다. JavaScript의 `<<`는 32비트 정수로 계산해서 `1 << 31`이 `-2147483648`, `1 << 32`가 `1`이다. 그래서 n = 31이면 `mask < (1 << 31)`이 처음부터 거짓이라 반복이 0번 돈다. 답이 빈 배열로 나온다. 이 문제는 n이 10 이하라 괜찮지만, 큰 n에서 비트마스크를 쓰려면 `2 ** n`과 `Math.floor(mask / 2 ** i) % 2`로 바꾸거나 `BigInt`를 써야 한다. Java는 `1 << n`이 `int`라 같은 문제가 있고 `1L << n`으로 피한다. 물론 n이 31이면 부분집합이 21억 개라 어차피 다 만들 수 없다.

## 재귀를 스택 하나로 바꾸면

시작 위치 백트래킹을 재귀 없이 쓸 수도 있다. 재귀 호출이 콜 스택에 쌓던 `(지금까지 고른 것, 시작 위치)`를 배열 스택에 직접 넣고 꺼낸다. 재귀 깊이 한도가 걱정되는 환경이나, 탐색을 중간에 멈췄다가 이어 가야 할 때 이렇게 바꾼다.

```js
function subsets(nums) {
  const res = [];
  const stack = [[[], 0]]; // [지금까지 고른 부분집합, 다음에 고를 수 있는 시작 위치]
  while (stack.length) {
    const [sub, start] = stack.pop();
    res.push(sub);
    // 나중에 넣은 것이 먼저 나오니 뒤쪽 후보부터 넣어야 사전순이 된다
    for (let i = nums.length - 1; i >= start; i--) {
      stack.push([[...sub, nums[i]], i + 1]);
    }
  }
  return res;
}
```

`[1, 2, 3]`에서 재귀 풀이와 똑같은 `[] [1] [1,2] [1,2,3] [1,3] [2] [2,3] [3]`이 나온다. 후보를 넣는 순서를 뒤에서 앞으로 뒤집은 게 포인트다. 앞에서부터 넣으면 3으로 시작하는 것부터 꺼내져서 순서가 바뀐다. 답의 집합은 같다.

재귀 풀이는 `path` 하나를 고쳐 쓰다가 기록할 때만 복사했다. 이 풀이는 스택에 넣을 때마다 새 배열을 만든다. 되돌리기를 따로 하지 않으려고 상태를 통째로 들고 다니는 것이다. 그래서 n = 20에서 1604ms로, 재귀 풀이(374ms)보다 네 배 느렸다. 스택이 가장 컸을 때 칸 수는 n = 10에서 46칸이었다. 깊이마다 아직 안 꺼낸 형제들이 쌓이기 때문이다. 이 문제처럼 n이 10 이하면 재귀가 더 낫고, 스택 버전은 "재귀 없이 짤 수 있나요"라는 꼬리 질문의 답으로 알아 두면 된다.

## 다섯 풀이를 나란히 놓으면

n = 20(1,048,576개)에서 세 번 돌린 평균이다.

```text
하나씩 들이며 두 배로     685ms
넣는다/안 넣는다 재귀     346ms
시작 위치 백트래킹        374ms
비트마스크               527ms
명시적 스택              1604ms
```

하나씩 불리는 풀이는 재귀가 없는데도 느렸다. 원소를 들일 때마다 기존 부분집합을 펼쳐 복사하니, 긴 부분집합일수록 같은 앞부분을 여러 번 복사한다. 시간 차이는 대부분 배열을 몇 번 새로 만드느냐에서 나온다.

| 풀이 | 시간 | 추가 공간 | 언제 고르나 |
|---|---|---|---|
| 하나씩 들이며 두 배로 | O(n · 2^n) | 출력뿐 | 재귀 없이 짧게 짤 때 |
| 넣는다/안 넣는다 재귀 | O(n · 2^n) | O(n) 재귀 | 원소마다 결정에 조건을 붙일 때(배낭형 가지치기) |
| 시작 위치 백트래킹 | O(n · 2^n) | O(n) 재귀 | 기본 답. 조합·순열·Combination Sum으로 바꾸기 쉽다 |
| 비트마스크 | O(n · 2^n) | O(n) | 부분집합을 정수 키로 다뤄야 할 때(비트마스크 DP) |
| 명시적 스택 | O(n · 2^n) | O(n²) 스택 | 재귀를 쓸 수 없거나 탐색을 멈췄다 이어야 할 때 |

다섯 풀이 모두 복잡도가 같다. 출력이 n · 2^n 크기라서 그보다 빠를 수 없다. 면접에서는 "개수가 2^n이라 출력만으로 O(n · 2^n)이다"를 먼저 말하고, 확장하기 좋은 시작 위치 백트래킹을 짜는 흐름이 무난하다. 시간이 남으면 비트마스크를 덧붙인다.

## 결과가 전부 빈 배열로 나온다면

가장 흔한 버그는 `path`를 복사하지 않고 그대로 넣는 것이다.

```js
function go(start) {
  res.push(path); // 복사하지 않았다
  for (let i = start; i < nums.length; i++) {
    path.push(nums[i]); go(i + 1); path.pop();
  }
}
```

`[1, 2, 3]`에서 결과가 `[[],[],[],[],[],[],[],[]]`로 나왔다. 개수는 8개로 맞다. `res`의 여덟 칸이 모두 같은 배열 `path`를 가리키고 있고, 탐색이 끝나면 `path`는 pop으로 비어 있다. 기록하는 순간의 모습을 `[...path]`, `path[:]`, `new ArrayList<>(path)`로 새로 만들어 넣어야 한다. [재귀와 백트래킹 글](/posts/recursion-backtracking)도 이 버그로 시작한다.

`go(i + 1)` 자리에 `go(start + 1)`을 쓰면 같은 원소가 두 번 들어간 부분집합이 생긴다. 반대로 `go(i)`를 쓰면 같은 원소를 무한히 다시 고를 수 있어서 끝나지 않는다. 재귀 깊이가 계속 늘다가 `Maximum call stack size exceeded`로 죽는다. 다음 후보 범위를 정하는 이 인자 하나가 부분집합, 조합, 중복 조합을 가른다.

결과 배열을 함수 밖에 두는 실수도 있다. LeetCode는 같은 프로세스에서 여러 테스트를 돌리니 앞 테스트의 답이 남는다. `res`와 `path`는 함수 안에서 만든다.

입력에 같은 값이 있으면 이 코드는 같은 부분집합을 또 만든다. `[1, 2, 2]`를 넣으면 `[1,2]`와 `[2]`가 두 번씩 나와 8개가 된다. 이 문제는 원소가 서로 다르다고 했으니 괜찮지만, 면접관이 이걸 바로 꼬리 질문으로 묻는다.

## 면접관이 조건을 바꾸면

### 같은 값이 섞여 있다면

LeetCode 90 [Subsets II](/posts/leetcode-subsets-ii)다. 정렬해서 같은 값을 붙여 놓고, 같은 for문 안에서 바로 앞과 같은 값이면 건너뛴다.

```js
function subsetsWithDup(nums) {
  nums = [...nums].sort((a, b) => a - b);  // 같은 값을 붙여 놓는다
  const res = [], path = [];
  function go(start) {
    res.push([...path]);
    for (let i = start; i < nums.length; i++) {
      if (i > start && nums[i] === nums[i - 1]) continue; // 이 자리에 같은 값은 한 번만
      path.push(nums[i]); go(i + 1); path.pop();
    }
  }
  go(0);
  return res;
}
```

`[1, 2, 2]`에서 `[[],[1],[1,2],[1,2,2],[2],[2,2]]` 6개가 나온다. 조건이 `i > 0`이 아니라 `i > start`인 이유가 중요하다. 같은 자리(같은 깊이)에서 2를 두 번 고르는 것만 막고, 깊이 들어가서 두 번째 2를 이어 고르는 `[2,2]`는 살려야 한다. `i > 0`으로 쓰면 `[2,2]`와 `[1,2,2]`가 사라진다. 결과를 `Set`에 문자열로 넣어 지우는 방법도 있지만, 그건 같은 가지를 두 번 탐색한 뒤라 느리다.

### 크기가 k인 것만 달라면

`path.length === k`일 때만 기록하고 바로 돌아간다. 더 나아가 남은 원소가 모자라면 들어가지 않는 가지치기를 붙인다. `i`의 상한을 `nums.length - (k - path.length)`로 두면 끝까지 가도 k개를 못 채우는 갈래를 건너뛴다. `[1, 2, 3, 4]`에서 k = 2면 `[1,2] [1,3] [1,4] [2,3] [2,4] [3,4]`다. LeetCode 77 Combinations가 이 변형이다.

### 합이 target인 부분집합만 세라면

넣는다/안 넣는다 재귀에 합을 들고 다니면 된다. `[1, 2, 3, 4]`에서 합 5는 `[1,4]`, `[2,3]` 두 개다. 원소가 모두 양수면 합이 target을 넘는 순간 그 갈래를 끊을 수 있다. 개수만 필요하고 값의 범위가 작으면 `dp[s] = 합 s를 만드는 방법 수`로 바꿔 O(n · target)에 끝낸다. 백트래킹에서 [동적 계획법](/posts/dynamic-programming)으로 넘어가는 대표적인 지점이다. [Partition Equal Subset Sum](/posts/leetcode-partition-equal-subset-sum)이 이 계산을 쓴다.

### 메모리가 부족하다면

답을 전부 모으지 말고 하나 만들 때마다 처리한다. 비트마스크는 mask 하나로 부분집합 하나를 바로 만들 수 있어서, 반복문 안에서 쓰고 버리면 추가 메모리가 O(n)이다. 제너레이터로 감싸면 호출하는 쪽이 원할 때 하나씩 꺼낼 수 있다. 다만 n이 30만 넘어도 10억 개라, 메모리보다 시간이 먼저 문제다. 그때는 "정말 다 봐야 하나"부터 다시 묻는다.

### k번째 부분집합 하나만 달라면

비트마스크 순서라면 계산이 필요 없다. k번째(1부터 셈)는 mask = k - 1이라 비트 n개를 읽으면 O(n)에 끝난다. `[1, 2, 3]`에서 6번째는 mask 5 = `101`이라 `[1,3]`이다. 시작 위치 백트래킹의 사전순으로 k번째를 원하면, "이 원소로 시작하는 부분집합이 몇 개인가"를 세어 건너뛴다. `nums[i]`를 고른 뒤 남은 원소가 r개면 그 아래 부분집합이 2^r개라서, k가 그보다 크면 그만큼 빼고 다음 후보로 넘어간다. [Generate Parentheses](/posts/leetcode-generate-parentheses)의 k번째 문자열 구하기와 같은 방식이다.

### 이웃한 두 부분집합이 원소 하나만 다르게 하라면

그레이 코드(Gray code) 순서다. `i ^ (i >> 1)`로 mask를 만들면 이웃한 두 값이 비트 하나만 다르다. 3비트에서 `000 001 011 010 110 111 101 100`, 부분집합으로는 `[] [1] [1,2] [2] [2,3] [1,2,3] [1,3] [3]` 순서다. 원소 하나를 넣거나 빼는 비용만 들여 다음 부분집합으로 넘어갈 수 있어서, 부분집합마다 합을 다시 계산하지 않고 고쳐 나갈 때 쓴다. LeetCode 89 Gray Code가 이 수열을 만드는 문제다.

[Letter Combinations of a Phone Number](/posts/leetcode-letter-combinations-of-a-phone-number)는 칸마다 후보가 여러 개인 결정 트리다. ## 옵션 조합 테스트를 만들 때

처음 이야기로 돌아가면, 켜고 끄는 옵션 세 개의 조합은 부분집합 8개다. 이 함수 결과를 테스트 러너의 매개변수 테스트(Jest의 `test.each`, pytest의 `parametrize`)에 그대로 넘기면 빠뜨린 조합 없이 테스트가 생긴다.

```js
const options = ["gift", "engraving", "express"];
const cases = subsets(options); // 8가지 조합
// test.each(cases)("옵션 %j로 주문한다", (...picked) => { ... })
console.log(cases.length, JSON.stringify(cases[3])); // 8 ["gift","engraving","express"]
```

옵션이 늘면 이야기가 달라진다. 10개면 1024개, 20개면 104만 개다. 테스트 하나가 0.1초만 걸려도 20개 옵션은 하루를 넘긴다. 이때 "모든 부분집합"은 정답이 아니다. 실무에서는 옵션 두 개씩의 모든 조합만 한 번 이상 나오게 줄이는 페어와이즈(pairwise) 테스트나, 서로 영향을 주는 옵션끼리만 묶어 부분집합을 만드는 방식을 쓴다. 2^n이 얼마나 빨리 커지는지 알면 이 판단을 미리 할 수 있다.

## 고른 순서를 정하면 겹치지 않는다

부분집합은 원소마다 넣을지 말지 정하는 문제라 2^n개이고, 출력만으로 O(n · 2^n)이 든다. 빠짐없이, 겹치지 않게 만들려면 고르는 순서를 정한다. 원래 배열 순서대로만 고르게 `start`를 넘기면 호출 하나가 곧 부분집합 하나가 되고, for문의 범위를 바꾸면 조합, 중복 조합, 순열로 넘어간다. 기록할 때 `path`를 복사하는 것만 잊지 않으면 된다.

## 면접에서 나올 만한 질문

### 시간 복잡도가 왜 O(n · 2^n)인가요?

부분집합이 2^n개이고, 각각의 평균 길이가 n/2라 답을 적는 데만 n · 2^n에 비례하는 시간이 든다. 백트래킹은 호출 하나가 답 하나라 탐색 비용이 출력 크기를 넘지 않는다. 그래서 어떤 풀이든 이보다 빠를 수 없고, 풀이 사이의 차이는 상수 배다.

### 공간 복잡도는요?

출력을 빼면 재귀 깊이 n과 `path` 길이 n이라 O(n)이다. 출력까지 세면 O(n · 2^n)이다. 면접에서는 둘을 나눠서 말하는 게 좋다. 비트마스크와 하나씩 불리는 반복문은 재귀 스택이 없다.

### 결과를 넣을 때 왜 복사하나요?

`path`는 탐색 내내 하나의 배열을 고쳐 쓴다. 그대로 넣으면 결과의 모든 칸이 같은 배열을 가리키고, 탐색이 끝나 `path`가 비면 답이 전부 빈 배열로 보인다. 기록하는 순간의 모습을 새 배열로 만들어 넣어야 한다.

### 넣는다/안 넣는다 재귀와 시작 위치 백트래킹은 무엇이 다른가요?

앞의 것은 원소마다 두 갈래로 나누는 이진 트리라 잎에서만 답이 나오고, 마디가 2^(n+1) - 1개다. 시작 위치 방식은 "다음에 고를 원소"로 갈래를 나눠서 모든 마디가 답이고 마디가 2^n개다. 복잡도는 같지만 시작 위치 방식이 조합·순열로 바꾸기 쉽다.

### 비트마스크 풀이에서 n이 커지면 무엇이 문제인가요?

JavaScript의 `<<`는 32비트로 계산해서 `1 << 31`이 음수, `1 << 32`가 1이다. n = 31이면 반복이 한 번도 돌지 않는다. Java도 `int`라 `1L << n`을 써야 한다. 다만 그 크기면 부분집합이 수십억 개라 다 만드는 것 자체가 현실적이지 않다.

### 입력에 중복이 있으면 어떻게 바꾸나요?

정렬해서 같은 값을 붙이고, 같은 for문 안에서 `i > start`이면서 바로 앞과 같은 값이면 건너뛴다. 같은 깊이에서 같은 값을 두 번 고르는 것만 막고, 더 깊이 들어가 같은 값을 이어 고르는 건 허용한다. `i > 0`으로 쓰면 `[2,2]` 같은 답이 빠진다.

### 합이 target인 부분집합의 개수만 필요하면요?

목록이 필요 없으면 백트래킹 대신 동적 계획법으로 바꾼다. `dp[s]`를 합 s를 만드는 방법 수로 두고 원소마다 큰 s부터 갱신하면 O(n · target)이다. 원소가 모두 양수라면 백트래킹에서도 합이 target을 넘는 갈래를 끊을 수 있지만, 최악은 여전히 2^n이다.
