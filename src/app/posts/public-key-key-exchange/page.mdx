[대칭 암호](/posts/symmetric-encryption-aes) 글에서는 열쇠를 이미 나눠 가졌다고 치고 시작했다. 그런데 처음 만나는 서버와 브라우저는 그 열쇠를 어떻게 똑같이 갖게 되는가. 열쇠를 그냥 네트워크로 보내면 중간에서 엿보는 사람이 그대로 복사해 간다.

이 문제를 직접 눈으로 보려고 X25519 키 교환을 양쪽에서 돌려 봤다. 두 사람이 서로 공개 값만 주고받았는데 똑같은 비밀 32바이트를 얻었다.

```text
A가 계산한 공유 비밀: e8c658aedbc5a3e80d7f46fb2fc7f07eec5e414d2768ff4410cfe5770e6d6d76
B가 계산한 공유 비밀: e8c658aedbc5a3e80d7f46fb2fc7f07eec5e414d2768ff4410cfe5770e6d6d76
```

중간에서 두 공개 값을 다 본 사람도 이 비밀은 계산하지 못한다. 어떻게 이게 되는지, 그리고 왜 RSA로 키를 직접 보내지 않고 요즘은 전부 이 방식(ECDHE)을 쓰는지 작은 숫자로 따라가 본다. 이 글의 openssl·node 출력은 이 컨테이너(OpenSSL 3.0.13, Node 22)에서 실제로 돌린 값이다. 이렇게 맞춘 열쇠로 [HTTPS가 연결을 맺는 전체 흐름](/posts/https-tls)과 [내부망 mTLS](/posts/encryption-in-transit)는 이어지는 글에서 다룬다.

## 한쪽으로만 쉬운 자물쇠

공개 키 암호의 바탕은 "한 방향으로는 쉽지만 되돌리기는 어려운" 계산이다. 자물쇠를 잠그는 건 누구나 할 수 있지만 여는 건 열쇠 가진 사람만 하는 것과 같다. 공개 키는 자물쇠, 개인 키는 그 열쇠다. 자물쇠는 아무에게나 나눠 줘도 되고, 열쇠는 나만 쥔다.

수학에서 이런 "한쪽으로만 쉬운" 계산이 두 종류 쓰인다. 하나는 큰 수를 소인수분해하는 어려움(RSA), 다른 하나는 이산 로그를 푸는 어려움(디피-헬먼, 타원곡선)이다. 곱하는 건 쉽지만 다시 소수 두 개로 쪼개는 건 어렵고, `g^a`를 계산하는 건 쉽지만 결과에서 `a`를 되찾는 건 어렵다. 이 비대칭이 공개 키 암호를 떠받친다.

## 소수 두 개로 시작하는 RSA

RSA는 큰 소수 두 개를 곱한 수 `n`을 공개하되, 그 두 소수는 숨긴다. 교과서 예제를 작은 수로 끝까지 계산해 보면 구조가 보인다. 소수 `p=61`, `q=53`을 골랐다.

```text
n = p*q = 3233
phi = (p-1)*(q-1) = 3120
e = 17            (phi와 서로소인 공개 지수)
d = 2753          (e*d ≡ 1 mod phi 를 푼 개인 지수)
```

공개 키는 `(n=3233, e=17)`, 개인 키는 `d=2753`이다. 메시지 `m=65`를 공개 키로 암호화하면 `c = m^e mod n`, 개인 키로 복호화하면 `m = c^d mod n`이다.

```text
c = 65^17 mod 3233 = 2790
back = 2790^2753 mod 3233 = 65
```

공개 키만 아는 사람은 `n=3233`을 `61×53`으로 쪼개야 `d`를 구할 수 있다. 3233은 암산으로도 쪼개지지만, 실제로 쓰는 RSA의 `n`은 2048비트(십진 600여 자리)라서 지금까지 알려진 어떤 방법으로도 현실적인 시간 안에 못 쪼갠다. 방향을 바꿔 `m^d`를 먼저 하고 공개 키로 `^e`를 하면 전자 서명이 된다. 이 서명·인증서 이야기는 [전자 서명과 인증서](/posts/digital-signatures-certificates) 글에서 openssl로 이어 간다.

## 큰 데이터는 RSA로 직접 암호화하지 않는다

RSA로 긴 본문을 통째로 암호화하지는 않는다. RSA는 느리고, 한 번에 다룰 수 있는 크기가 키 길이보다 작다(2048비트 키면 한 번에 200바이트 남짓). 그래서 실무는 하이브리드 방식을 쓴다. 본문은 빠른 AES로 암호화하고, 그 AES 키(DEK)만 RSA 공개 키로 감싸서 함께 보낸다. 받는 쪽은 개인 키로 DEK를 풀고, 그 DEK로 본문을 연다.

```js
import { generateKeyPairSync, randomBytes, createCipheriv, createDecipheriv,
  publicEncrypt, privateDecrypt } from "node:crypto";
const { publicKey, privateKey } = generateKeyPairSync("rsa", { modulusLength: 2048 });
const dek = randomBytes(32), iv = randomBytes(12);
const ci = createCipheriv("aes-256-gcm", dek, iv);
const body = Buffer.concat([ci.update("주문 10만 건 CSV ...", "utf8"), ci.final()]);
const tag = ci.getAuthTag();
const wrapped = publicEncrypt({ key: publicKey, oaepHash: "sha256" }, dek); // DEK만 RSA로 감쌈
```

```text
감싼 DEK 길이: 256 바이트 (RSA-2048 OAEP)
본문 암호문 길이: 24 바이트
복원: 주문 10만 건 CSV ...
DEK 복원 일치: true
```

이 "작은 키만 공개 키로 감싸고 본문은 대칭키로"라는 구조는 [저장 데이터 암호화의 봉투 암호화](/posts/encryption-at-rest#봉투-암호화-데이터-키와-마스터-키)와 똑같은 생각이다. 거기서는 마스터 키가 KMS 안에 있을 뿐이다.

## 열쇠를 보내지 않고 같은 열쇠를 만든다

하이브리드에도 약점이 하나 있다. 공격자가 오늘의 트래픽을 전부 녹화해 두고 1년 뒤 서버의 RSA 개인 키를 훔치면, 녹화본 속 `wrapped DEK`를 전부 풀어 과거 통신을 모두 복호화할 수 있다. 과거가 미래의 유출에 묶여 있다. 이걸 끊으려면 키를 아예 "보내지" 않아야 한다.

디피-헬먼(Diffie-Hellman) 키 교환이 그 답이다. 모두가 아는 큰 소수 `p`와 밑 `g`를 두고, A는 비밀 수 `a`로 `g^a mod p`를, B는 비밀 수 `b`로 `g^b mod p`를 보낸다. A는 받은 값을 `a`제곱, B는 받은 값을 `b`제곱한다. 둘 다 `g^(ab) mod p`가 된다. 열쇠 자체는 선을 타고 간 적이 없다.

작은 수로 보면 확실하다. `p=23`, `g=5`, A의 비밀 `a=6`, B의 비밀 `b=15`라 하자. A가 보내는 값은 `5^6 mod 23 = 8`, B가 보내는 값은 `5^15 mod 23 = 19`다. 선 위에 보이는 건 `8`과 `19`뿐이다. A는 `19^6 mod 23 = 2`, B는 `8^15 mod 23 = 2`. 둘 다 `2`를 얻는다. `8`과 `19`에서 `6`이나 `15`를 되찾으려면 이산 로그를 풀어야 하는데, 수가 크면 손들린다.

## 타원곡선으로 더 짧고 빠르게

맨 앞의 X25519가 바로 이 디피-헬먼을 정수 대신 타원곡선 위에서 하는 것이다(ECDH). 같은 안전성을 훨씬 짧은 키로 얻는다. X25519의 공개 값은 32바이트다. RSA-2048과 대략 비슷한 안전성을 주는 타원곡선 키가 256비트 정도다.

ECDH가 요즘 기본이 된 결정적 이유는 키를 연결마다 새로 버릴 수 있을 만큼 싸다는 점이다. 이 컨테이너에서 키 쌍 생성 시간을 재 봤다.

```text
RSA-2048 keygen x5: 211 ms 총
X25519 keygen x5:   0 ms 총  (측정 분해능 아래)
```

RSA 키 생성은 느려서 연결마다 새로 만들 수 없다. X25519는 사실상 공짜라 매 연결마다 새 `a`, `b`를 만들고 핸드셰이크가 끝나면 버린다. 이게 ECDHE의 마지막 `E`(ephemeral, 일회용)다.

일회용이라 전방향 안전성이 생긴다. 서버 개인 키(인증서 키)는 "내가 그 서버가 맞다"는 서명에만 쓰이고, 세션 키 계산에는 그 연결에서만 살았다 사라진 `a`, `b`가 쓰인다. 그래서 1년 뒤 인증서 키가 털려도 과거 녹화본은 계속 잠겨 있다. TLS 1.3이 RSA 키 교환을 아예 빼 버린 이유이고, 그 효과를 [HTTPS 글](/posts/https-tls#키를-보내지-않고-같은-키를-만든다)에서 프로토콜 흐름으로 본다.

하지만 ECDH만으로는 중간자 공격을 못 막는다. A가 받은 "B의 공개 값"이 정말 B의 것인지 보장이 없기 때문이다. 공격자가 양쪽과 각각 키 교환을 하면 두 구간을 다 복호화할 수 있다. 그래서 키 교환의 공개 값에 서버가 **인증서 개인 키로 서명**을 붙인다. 공개 값은 숨기지 않고, 그 값이 진짜 그 서버에서 왔다는 것만 서명으로 묶는다. 키 교환(ECDHE)과 신원 확인(인증서 서명)은 이렇게 역할이 나뉜다.

## 모듈러 거듭제곱을 손으로 따라가기

디피-헬먼의 심장은 `g^a mod p`를 큰 수에서도 빠르게 계산하는 것이다. `a`를 이진수로 보고 제곱을 반복하면 곱셈 횟수가 지수가 아니라 비트 수에 비례한다(square-and-multiply). `5^6 mod 23`을 이 방법으로 밟아 보면 이렇다. `6`은 이진수 `110`이다.

## 양자 컴퓨터가 깨는 것과 그 대비

RSA와 (EC)DH가 어려운 이유인 소인수분해·이산 로그는, 충분히 큰 양자 컴퓨터가 나오면 쇼어 알고리즘으로 풀린다. 아직 그런 기계는 없지만, 오늘 녹화한 트래픽을 보관해 두고 미래에 푸는 "지금 수집하고 나중에 복호화"(harvest now, decrypt later) 위협 때문에 전환이 이미 시작됐다.

대비책은 격자 기반 같은 양자 내성 알고리즘으로 바꾸는 것인데, 이들은 아직 실전 검증이 짧다. 그래서 과도기에는 하이브리드로 간다. 기존 X25519와 새 ML-KEM(격자 기반 키 캡슐화)을 함께 돌려 두 공유 비밀을 섞는다. 둘 중 하나만 안전해도 전체가 안전하다. 크롬 계열과 일부 서버는 이미 X25519MLKEM768이라는 하이브리드 그룹을 쓴다.

다만 지원 범위는 빠르게 바뀌는 중이다. 이 컨테이너의 OpenSSL 3.0.13에는 ML-KEM이 없어서(키 교환 알고리즘 목록에 X25519·X448·ECDH·DH까지만 나온다), X25519 단독까지만 실제로 돌릴 수 있었다. ML-KEM 하이브리드는 OpenSSL 3.5 이후와 최신 브라우저에서 켜지는 것으로 알려져 있으니, 실제 지원 여부는 쓰는 버전에서 확인해야 한다.

## 보내지 말고, 같이 만들라

열쇠 문제의 핵심은 "비밀을 어떻게 안 보내고 공유하느냐"다. RSA는 자물쇠(공개 키)로 작은 키를 감싸 보내는 방식이고, 디피-헬먼은 아예 보내지 않고 양쪽이 같은 값을 계산해 낸다. 후자가 연결마다 일회용 키로 돌릴 만큼 싸고(ECDHE), 그래서 과거 트래픽을 미래 유출로부터 지킨다. 오늘의 TLS는 ECDHE로 비밀을 만들고 인증서 서명으로 상대를 확인한 뒤, 그 비밀에서 뽑은 대칭키로 본문을 나른다. 그 서명과 인증서 이야기가 [다음 글](/posts/digital-signatures-certificates)이다.

## 면접에서 나올 만한 질문

### 공개 키 암호에서 공개 키와 개인 키의 역할은 각각 무엇인가요?

공개 키는 자물쇠처럼 누구에게나 나눠 줄 수 있고, 그걸로 암호화하거나 서명을 검증한다. 개인 키는 그 짝이 되는 열쇠로 나만 쥐고, 그걸로 복호화하거나 서명을 만든다. 둘은 수학적으로 짝이지만, 공개 키에서 개인 키를 계산해 내는 것은 소인수분해나 이산 로그처럼 현실적으로 불가능한 문제에 기대고 있다.

### RSA로 큰 데이터를 직접 암호화하지 않고 하이브리드 방식을 쓰는 이유는?

RSA는 연산이 느리고 한 번에 다룰 수 있는 크기가 키 길이보다 작아서(2048비트면 200바이트 남짓) 긴 본문에 맞지 않는다. 그래서 본문은 빠른 AES로 암호화하고, 그 AES 키만 RSA 공개 키로 감싸 함께 보낸다. 받는 쪽은 개인 키로 AES 키를 풀고 본문을 복호화한다. 봉투 암호화와 같은 구조다.

### 디피-헬먼은 열쇠를 어떻게 네트워크로 보내지 않고 공유하나요?

양쪽이 공개 값 `g^a`, `g^b`만 주고받고, 각자 받은 값을 자기 비밀로 거듭제곱해 `g^(ab)`라는 같은 값을 얻는다. 공유할 비밀 자체는 선을 타고 간 적이 없다. 중간에서 두 공개 값을 다 봐도 `a`나 `b`를 알아내려면 이산 로그를 풀어야 해서 비밀을 재현할 수 없다.

### TLS 1.3이 RSA 키 교환을 버리고 ECDHE를 쓰는 이유는?

ECDHE는 연결마다 일회용 키 쌍을 만들고 버려서 전방향 안전성을 준다. 그래서 나중에 서버의 인증서 개인 키가 유출돼도 과거에 녹화된 트래픽은 복호화되지 않는다. RSA 키 교환은 세션 키를 서버 공개 키로 감싸 보내므로 개인 키 하나가 과거 전체를 푸는 열쇠가 되고, 키 생성이 비싸 연결마다 새로 만들 수도 없다.

### ECDH만으로 중간자 공격을 막을 수 없는 이유와 보완책은?

ECDH는 양쪽이 같은 비밀을 만들게 해 줄 뿐, 받은 공개 값이 진짜 상대의 것인지는 보장하지 못한다. 공격자가 양쪽과 각각 키 교환을 하면 두 구간을 모두 복호화할 수 있다. 그래서 서버가 키 교환의 공개 값에 인증서 개인 키로 서명을 붙이고, 클라이언트는 인증서 체인을 검증해 그 값이 진짜 그 서버에서 왔음을 확인한다.

### 타원곡선 키 교환(X25519)이 같은 안전성에 키가 더 짧고 빠른 점이 왜 중요한가요?

X25519의 공개 값은 32바이트로 RSA-2048 수준 안전성을 훨씬 작게 얻고, 키 생성이 사실상 공짜라 연결마다 새 키를 만들어 버릴 수 있다. 이 컨테이너에서도 RSA-2048 키 생성은 다섯 번에 200밀리초가 넘었지만 X25519는 측정 분해능 아래였다. 이 저렴함이 매 연결 일회용 키(ephemeral)를 현실화해 전방향 안전성을 가능하게 한다.

### 양자 컴퓨터를 대비한 포스트 양자 하이브리드 키 교환은 무엇인가요?

큰 양자 컴퓨터는 쇼어 알고리즘으로 RSA·ECDH의 바탕인 소인수분해와 이산 로그를 풀 수 있어, 지금 녹화한 트래픽을 미래에 복호화하는 위협이 있다. 그래서 과도기에는 기존 X25519와 격자 기반 ML-KEM을 함께 돌려 두 공유 비밀을 섞는 하이브리드(X25519MLKEM768 등)를 쓴다. 둘 중 하나만 안전해도 전체가 안전하지만, 지원 범위가 빠르게 바뀌는 중이라 쓰는 버전에서 확인해야 한다.
