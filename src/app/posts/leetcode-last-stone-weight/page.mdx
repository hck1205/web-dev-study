[Last Stone Weight](https://leetcode.com/problems/last-stone-weight/)는 LeetCode 1046번이고 난이도는 Easy다. 문제 자체는 시키는 대로 흉내 내면 끝나는 시뮬레이션이다. 그래서 이 문제의 질문은 "어떻게 푸나"보다 "가장 큰 두 개를 반복해서 꺼낼 때 어떤 자료구조가 맞나"다. 최대 힙을 처음 연습하기에 좋은 문제다.

이 글은 매번 정렬하기, 정렬 없이 두 번 훑기, 정렬된 배열에 조각 끼우기, 최대 힙, 무게별 칸까지 다섯 풀이를 본다. 입력이 작아서 어느 풀이든 통과하지만, 입력을 키워 보면 각자 어디서 무너지는지가 드러난다. 힙의 넣기와 꺼내기가 어떻게 동작하는지는 [힙 글](/posts/ds-heap#넣으면-올라가고-꺼내면-내려간다)에 있어서 여기서는 반복하지 않는다. 코드는 Node.js 22, Python 3.13, Java 21에서 돌렸다.

## 가장 무거운 두 돌을 계속 부딪친다

양의 정수 배열 `stones`가 주어진다. 각 값이 돌 하나의 무게다. 한 번의 차례에 이렇게 한다.

1. 가장 무거운 돌 y와 그다음으로 무거운 돌 x를 고른다. x는 y보다 작거나 같다.
2. x와 y가 같으면 둘 다 없어진다.
3. 다르면 x는 없어지고, y는 무게가 `y - x`가 되어 남는다.

돌이 하나 남으면 그 무게를, 하나도 안 남으면 0을 돌려준다.

제약은 작다. 돌은 1개 이상 30개 이하이고, 무게는 1 이상 1000 이하다. 돌 30개면 O(n² log n)도 순식간이다. 그래서 면접에서는 보통 "n이 10^6이라면?"으로 판을 키운다. 이 글도 그 질문을 따라간다. 무게가 1000 이하라는 제약은 마지막 풀이에서 쓴다.

한 가지는 미리 짚어 둔다. 한 차례마다 돌이 최소 하나는 줄어든다. 둘이 같으면 두 개가, 다르면 한 개가 사라진다. 그래서 차례는 많아야 n - 1번이고 시뮬레이션은 반드시 끝난다.

## 여섯 개의 돌을 손으로 부숴 본다

이 글 내내 쓰는 예시는 `[6, 4, 9, 2, 5, 3]`이다. 매 차례 남은 돌을 큰 순서로 늘어놓고 앞의 두 개를 부딪친다.

```text
차례  남은 돌(큰 순)     부딪치는 두 돌   결과
1     9 6 5 4 3 2        9와 6           3이 남는다
2     5 4 3 3 2          5와 4           1이 남는다
3     3 3 2 1            3과 3           둘 다 사라진다
4     2 1                2와 1           1이 남는다
끝    1                                  답은 1
```

표를 보면 매 차례 쓰인 건 앞의 두 칸뿐이다. 그런데 새로 생긴 조각(3, 1)이 줄의 중간 어딘가로 들어간다. 1차례에서 생긴 3은 원래 있던 3과 나란히 서서 3차례에 함께 사라졌다. 조각이 들어갈 자리를 매번 정확히 맞춰야 하는지, 아니면 맨 앞만 맞으면 되는지가 풀이를 가른다.

## 매번 정렬하고 뒤의 두 개를 꺼낸다

시키는 대로 흉내 내는 첫 번째 방법이다. 차례마다 배열을 오름차순으로 정렬하고, 맨 뒤 두 개를 꺼낸다.

```js
function lastStoneWeight(stones) {
  const a = [...stones];
  while (a.length > 1) {
    a.sort((x, y) => x - y);          // 매 차례 전부 정렬
    const y = a.pop(), x = a.pop();   // 가장 무거운 돌, 두 번째로 무거운 돌
    if (y !== x) a.push(y - x);       // 다르면 깎인 조각이 남는다
  }
  return a.length ? a[0] : 0;
}
```

차례가 최대 n - 1번이고 정렬이 O(n log n)이라 전체는 O(n² log n)이다. 공간은 복사한 배열 O(n)이다.

여기서도 `sort`의 비교 함수가 중요하다. `sort()`만 쓰면 문자열 순서라서 `[10, 9]`가 그대로 `[10, 9]`로 남고, 맨 뒤의 9를 가장 무겁다고 착각한다. `[10, 9, 2]`라면 9와 2를 먼저 부딪친다.

이미 거의 정렬된 배열을 다시 정렬하는 일은 엔진이 빨리 끝내 주지만, 그래도 차례마다 n칸을 다 본다. 필요한 건 가장 큰 두 개뿐인데 전체 순서를 다시 맞추는 게 낭비다.

## 정렬 없이 가장 큰 두 개만 찾는다

정렬을 버리고 배열을 두 번 훑는다. 첫 번째로 훑어 가장 큰 값을 찾아 빼고, 두 번째로 훑어 그다음으로 큰 값을 찾아 뺀다. 빼는 방법은 그 칸에 맨 끝 값을 옮기고 끝을 줄이는 것이다. 순서를 지킬 필요가 없으니 O(1)에 뺄 수 있다.

```js
function lastStoneWeight(stones) {
  const a = [...stones];
  const takeMax = () => {
    let i = 0;
    for (let t = 1; t < a.length; t++) if (a[t] > a[i]) i = t; // 가장 큰 칸을 찾는다
    const v = a[i];
    a[i] = a[a.length - 1];           // 맨 끝 값을 그 자리로 옮기고
    a.pop();                          // 끝을 줄인다
    return v;
  };
  while (a.length > 1) {
    const y = takeMax(), x = takeMax();
    if (y !== x) a.push(y - x);
  }
  return a.length ? a[0] : 0;
}
```

차례마다 O(n)이라 전체는 O(n²)이고, 추가 공간은 O(1)이다. 돌 30개에서는 이 풀이가 다섯 풀이 중 가장 빨랐다. 1만 번 반복해 10ms였고, 힙은 32ms였다. 칸이 몇 개 안 되면 단순한 반복문이 힙의 자리 바꾸기보다 싸다. 원래 제약에서는 이게 가장 좋은 답이라고 말해도 틀리지 않는다.

하지만 n이 커지면 n²이 바로 드러난다. 돌 2000개에서 2.7ms로, 힙의 0.7ms보다 네 배 가까이 느렸다. 10만 개라면 차례마다 10만 칸을 두 번씩 훑는다.

## 정렬된 줄을 유지하고 조각만 끼운다

처음에 한 번만 정렬하고, 그다음부터는 정렬 상태를 지킨다. 가장 큰 두 개는 맨 뒤에 있으니 `pop` 두 번이면 된다. 새로 생긴 조각만 [이분 탐색](/posts/binary-search)으로 자리를 찾아 끼운다.

```js
function lastStoneWeight(stones) {
  const a = [...stones].sort((x, y) => x - y); // 처음 한 번만 정렬
  while (a.length > 1) {
    const y = a.pop(), x = a.pop();            // 맨 뒤 두 개가 가장 무겁다
    if (y !== x) {
      const d = y - x;
      let lo = 0, hi = a.length;
      while (lo < hi) {                        // d 이상인 첫 자리
        const m = (lo + hi) >> 1;
        if (a[m] < d) lo = m + 1;
        else hi = m;
      }
      a.splice(lo, 0, d);                      // 그 자리에 끼운다
    }
  }
  return a.length ? a[0] : 0;
}
```

꺼내기는 O(1), 자리 찾기는 O(log n), 끼우기는 뒤를 미느라 O(n)이다. 전체는 최악 O(n²)이다. 실제로는 꽤 빠르다. 조각 `y - x`는 두 돌보다 가벼워서 배열 앞쪽에 들어가는 일이 많지만, 미는 작업이 메모리 블록 복사라 빠르다. 돌 20만 개에서 99ms였다.

이 풀이는 조각이 들어갈 정확한 자리를 매번 맞춘다. 손으로 풀 때 본 것처럼 실제로 필요한 건 맨 앞(여기서는 맨 뒤) 두 칸뿐이다. 나머지 칸의 순서까지 맞추는 비용을 덜어 낸 것이 힙이다.

## 최대 힙에서 두 번 꺼내고 한 번 넣는다

필요한 연산을 다시 적으면 "가장 큰 값 꺼내기"와 "값 넣기" 두 가지다. 이 둘이 O(log n)인 자료구조가 최대 힙이다. 최대 힙은 부모가 자식보다 크거나 같다는 규칙만 지켜서, 맨 위가 늘 가장 큰 값이다.

1. 돌 전부를 최대 힙으로 만든다. 한꺼번에 만들면 O(n)이다.
2. 힙에 돌이 두 개 이상 있는 동안 두 번 꺼낸다. 처음 꺼낸 것이 y, 다음이 x다.
3. 둘이 다르면 `y - x`를 힙에 넣는다.
4. 힙이 비었으면 0, 아니면 맨 위를 돌려준다.

```js
class MaxHeap {
  constructor(a = []) {
    this.a = a;
    for (let i = (a.length >> 1) - 1; i >= 0; i--) this.down(i); // 한꺼번에 힙으로 만든다
  }
  get size() { return this.a.length; }
  push(x) {
    const a = this.a;
    a.push(x);
    let i = a.length - 1;
    while (i > 0) {                       // 부모보다 크면 올라간다
      const p = (i - 1) >> 1;
      if (a[p] >= a[i]) break;
      [a[p], a[i]] = [a[i], a[p]];
      i = p;
    }
  }
  down(i) {
    const a = this.a;
    for (;;) {                            // 더 큰 자식과 바꾸며 내려간다
      const l = 2 * i + 1, r = l + 1;
      let m = i;
      if (l < a.length && a[l] > a[m]) m = l;
      if (r < a.length && a[r] > a[m]) m = r;
      if (m === i) break;
      [a[m], a[i]] = [a[i], a[m]];
      i = m;
    }
  }
  pop() {
    const a = this.a, top = a[0], last = a.pop();
    if (a.length) { a[0] = last; this.down(0); }
    return top;
  }
}

function lastStoneWeight(stones) {
  const h = new MaxHeap([...stones]);
  while (h.size > 1) {
    const y = h.pop();                    // 가장 무거운 돌
    const x = h.pop();                    // 두 번째로 무거운 돌
    if (y !== x) h.push(y - x);           // 깎인 조각을 다시 넣는다
  }
  return h.size ? h.a[0] : 0;
}
```

예시를 넣고 차례마다 힙 배열을 찍어 봤다. 힙 배열은 정렬된 순서가 아니다. 맨 앞만 가장 크고, 나머지는 부모가 자식보다 크다는 규칙만 지킨다.

```text
start   [9,5,6,2,4,3]
9 vs 6  [5,4,3,2,3]
5 vs 4  [3,2,3,1]
3 vs 3  [2,1]
2 vs 1  [1]
```

1차례 뒤 배열 `[5,4,3,2,3]`의 맨 끝 3이 새로 들어온 조각이다. 정렬된 줄이었다면 원래 있던 3 옆에 나란히 서야 하지만, 힙은 그 자리를 정확히 맞추지 않고 맨 끝에 둔 채 부모 4보다 작으니 멈췄다. 맨 위만 맞으면 되기 때문이다.

### 첫 차례를 한 칸씩 들여다본다

힙을 처음 보는 사람에게는 배열이 왜 저렇게 바뀌는지가 가장 궁금하다. 인덱스 i의 자식은 `2i + 1`과 `2i + 2`, 부모는 `(i - 1) >> 1`이라는 규칙만 기억하고 첫 차례를 따라가 본다.

```text
한꺼번에 만들기  [6,4,9,2,5,3]
  i = 2: 9의 자식은 3뿐, 9가 더 커서 그대로
  i = 1: 4의 자식 2와 5 중 5가 더 크다 → 바꾼다   [6,5,9,2,4,3]
  i = 0: 6의 자식 5와 9 중 9가 더 크다 → 바꾼다   [9,5,6,2,4,3]
첫 번째 pop     맨 위 9를 꺼내고 맨 끝 3을 맨 위로  [3,5,6,2,4]
  3의 자식 5와 6 중 6이 더 크다 → 바꾼다          [6,5,3,2,4]
두 번째 pop     맨 위 6을 꺼내고 맨 끝 4를 맨 위로  [4,5,3,2]
  4의 자식 5와 3 중 5가 더 크다 → 바꾼다          [5,4,3,2]
push 3          맨 끝에 3을 붙인다                [5,4,3,2,3]
  부모 4가 3보다 커서 그대로 멈춘다
```

내려가거나 올라가는 길이는 트리의 높이, 즉 log n을 넘지 않는다. 돌이 6개면 높이가 2라 자리 바꾸기가 많아야 두 번이다. 100만 개여도 20번 정도다. 이게 힙 연산이 O(log n)인 이유다.

### 처음에 하나씩 넣어도 되나

돌을 빈 힙에 하나씩 `push`하면 O(n log n)이다. 한꺼번에 만드는 O(n)과 결과는 같다. 전체가 어차피 O(n log n)이라 이 문제에서는 어느 쪽도 괜찮다. 한꺼번에 만들기가 왜 O(n)인지는 [힙 글](/posts/ds-heap#한꺼번에-만들면-on이다)에 있다. 면접에서 "더 줄일 수 있나"를 물으면 꺼낼 만한 이야기다.

## 무게가 1000을 넘지 않으니 무게별로 센다

무게가 1 이상 1000 이하라는 제약을 쓴다. 무게마다 돌이 몇 개인지 세는 칸 `cnt`를 만들고, 무거운 칸에서 가벼운 칸으로 손가락 `w`를 내리며 돌을 고른다.

- 들고 있는 돌 `y`가 없을 때 `w` 칸에 돌이 있으면, 같은 무게 두 개끼리는 부딪쳐 사라지니 개수를 2로 나눈 나머지만 남긴다. 하나가 남으면 그 돌을 `y`로 든다.
- `y`를 들고 있을 때 `w` 칸에 돌이 있으면, 그 돌이 두 번째로 무거운 돌 x다. 둘을 부딪쳐 `y - w` 칸에 조각을 하나 더한다. 조각이 `w`보다 무거우면 손가락을 조각 위치로 올린다.
- 칸이 비었으면 손가락을 한 칸 내린다.

```js
function lastStoneWeight(stones) {
  let max = 0;
  for (const s of stones) if (s > max) max = s;
  const cnt = new Array(max + 1).fill(0);   // 무게마다 돌 개수
  for (const s of stones) cnt[s]++;
  let w = max, y = 0;                       // 손가락, 들고 있는 돌(0이면 없음)
  while (w > 0) {
    if (cnt[w] === 0) { w--; continue; }    // 빈 칸은 지나간다
    if (y === 0) {
      cnt[w] %= 2;                          // 같은 무게 두 개씩은 서로 사라진다
      if (cnt[w] === 1) { y = w; cnt[w] = 0; } // 하나 남으면 그 돌을 든다
      w--;
    } else {
      cnt[w]--;                             // 두 번째로 무거운 돌 x = w
      const d = y - w;
      y = 0;
      cnt[d]++;                             // 조각을 제 무게 칸에 넣는다
      if (d > w) w = d;                     // 조각이 더 무거우면 손가락을 올린다
    }
  }
  return y;
}
```

## 돌 30개와 돌 100만 개에서 갈리는 선택

| 풀이 | 시간 | 추가 공간 | 언제 고르나 |
|---|---|---|---|
| 매번 정렬 | O(n² log n) | O(n) | 코드를 가장 빨리 쓰고 싶을 때. n이 작으면 충분하다 |
| 두 번 훑기 | O(n²) | O(1) | 원래 제약(n이 30 이하). 실제로 가장 빨랐다 |
| 정렬된 배열에 조각 끼우기 | O(n²) | O(n) | 남은 돌의 순서를 계속 봐야 할 때 |
| 최대 힙 | O(n log n) | O(n) | n이 커질 수 있는 일반적인 답. 면접의 기본 |
| 무게별 칸 | O(n + W²) | O(W) | 무게 범위 W가 작고 돌이 아주 많을 때 |

측정은 같은 Node.js에서 했다. 돌 30개를 1만 번 돌리면 정렬 179ms, 두 번 훑기 10ms, 조각 끼우기 27ms, 힙 32ms, 무게별 칸 36ms였다. 무게별 칸은 1001칸짜리 배열을 매번 새로 만드느라 작은 입력에서 손해를 본다. 돌 20만 개에서는 조각 끼우기 99ms, 힙 69ms, 무게별 칸 1ms였다.

정리하면 원래 문제의 크기에서는 무엇을 써도 되고, 제일 단순한 반복문이 가장 빠르다. 면접에서 힙을 기대하는 건 "n이 커지면"을 염두에 둔 것이다. 이 차이를 먼저 말하고 힙을 쓰면 크기에 맞춰 자료구조를 고른다는 인상을 준다.

## Python은 부호를 뒤집고 Java는 비교자를 뒤집는다

최대 힙 풀이를 옮긴다.

```python
import heapq

def lastStoneWeight(stones: list[int]) -> int:
    h = [-s for s in stones]     # 부호를 뒤집어 최소 힙을 최대 힙처럼 쓴다
    heapq.heapify(h)
    while len(h) > 1:
        y = -heapq.heappop(h)    # 가장 무거운 돌
        x = -heapq.heappop(h)    # 두 번째로 무거운 돌
        if y != x:
            heapq.heappush(h, -(y - x))
    return -h[0] if h else 0

print(lastStoneWeight([6, 4, 9, 2, 5, 3]))
print(lastStoneWeight([3, 3]), lastStoneWeight([1]), lastStoneWeight([10, 1]))
```

```text
1
0 1 9
```

Python의 `heapq`는 최소 힙 함수만 공개해 왔다. 그래서 값에 `-`를 붙여 넣고, 꺼낼 때 다시 `-`를 붙인다. 넣는 줄의 `-(y - x)`에서 괄호를 빼먹으면 `-y - x`가 되어 엉뚱한 값이 들어간다. 부호를 뒤집는 곳이 네 군데라 하나하나 짝을 맞춰 본다. Python 3.14부터는 `heapq`에 `heappush_max` 같은 최대 힙 함수가 공개 API로 들어왔다. 코딩 테스트 환경의 버전이 그보다 낮은 경우가 많으니 부호 뒤집기를 기본으로 익혀 둔다.

```java
import java.util.*;

class Solution {
    public int lastStoneWeight(int[] stones) {
        PriorityQueue<Integer> h = new PriorityQueue<>(Collections.reverseOrder()); // 최대 힙
        for (int s : stones) h.offer(s);
        while (h.size() > 1) {
            int y = h.poll();      // 가장 무거운 돌
            int x = h.poll();      // 두 번째로 무거운 돌
            if (y != x) h.offer(y - x);
        }
        return h.isEmpty() ? 0 : h.peek();
    }
}
```

```text
1
0 1 9
```

Java의 `PriorityQueue`는 기본이 최소 힙이라 `Collections.reverseOrder()`를 줘서 최대 힙으로 만든다. 직접 비교자를 쓴다면 `(a, b) -> b - a` 대신 `(a, b) -> Integer.compare(b, a)`를 쓰는 버릇을 들인다. 이 문제는 무게가 1000 이하라 괜찮지만, 뺄셈 비교자는 값이 크면 넘친다. `Integer.MIN_VALUE`, 1, `Integer.MAX_VALUE`를 넣고 맨 위를 봤더니 `b - a`는 -2147483648을, `Integer.compare`는 2147483647을 내놓았다. 최대 힙의 맨 위가 가장 작은 값이 된 것이다.

`y`와 `x`를 `int`로 받은 것도 일부러다. `Integer y = h.poll()`처럼 받고 `y != x`로 비교하면 객체끼리 비교가 되어, 128 이상의 같은 무게를 다르다고 판정할 수 있다. 실제로 무게 1000인 돌 두 개를 `Integer`로 꺼내 `y != x`를 찍었더니 `true`였다. 둘이 사라지지 않고 0짜리 조각이 남는다. 답은 우연히 맞아도 규칙과 다르게 움직인다.

## 돌이 하나도 안 남는 경우를 빼먹는다

### 빈 힙의 맨 위를 읽는다

`[3, 3]`처럼 마지막에 둘이 함께 사라지면 힙이 빈다. 이때 `h.a[0]`을 그대로 돌려주면 JavaScript는 `undefined`, Python은 `IndexError`, Java는 `peek()`이 `null`을 줘서 `int`로 풀다가 `NullPointerException`이 난다. 끝에서 비었는지 먼저 본다.

### 같은 무게일 때 0을 넣는다

```js
const y = h.pop(), x = h.pop();
h.push(y - x);              // 같을 때도 0을 넣는다
```

0은 부딪쳐도 상대를 깎지 않아서 마지막 답은 그대로 맞는다. 무작위 입력 2만 개로 대조해도 답이 다른 경우가 없었다. 대신 차례가 늘어난다. `[3, 3, 1]`이면 원래는 3과 3이 사라지고 1이 남아 한 차례로 끝나는데, 이 코드는 0이 들어가서 1과 0을 한 번 더 부딪친다. 답이 맞으니 테스트로는 잡히지 않고, "끝날 때까지 몇 번 부딪치나"나 "남은 돌이 몇 개인가"를 묻는 변형에서 틀린다. 문제의 규칙대로 같으면 넣지 않는다.

### 두 번째 돌을 꺼내기 전에 크기를 보지 않는다

`while (h.size > 0)`으로 반복하면 돌이 하나 남았을 때 `pop`을 두 번 한다. 두 번째 `pop`은 빈 힙에서 `undefined`를 꺼내고, `y - undefined`는 `NaN`이다. `NaN`이 힙에 들어가면 크기가 다시 1이 되어 같은 일이 끝없이 되풀이된다. 실제로 돌려 보니 멈추지 않았다. 반복 조건은 "둘 이상 있을 때"다.

### 입력 배열을 그대로 힙으로 쓴다

`new MaxHeap(stones)`처럼 복사 없이 넘기면 힙이 `stones` 배열 자체를 바꾸고 줄인다. 함수가 끝나면 호출한 쪽의 배열이 `[1]`이나 빈 배열로 변해 있다. 예시 `[6, 4, 9, 2, 5, 3]`을 그렇게 넘겼다가 같은 배열로 다른 풀이를 돌리면, 두 번째 풀이는 `[1]`을 받아 1을 낸다. 답이 같아 보여서 더 헷갈린다. 공간을 아끼려고 일부러 그 자리에서 쓴다면 "입력을 바꾼다"고 면접관에게 먼저 말한다.

Python의 `heapq.heapify(stones)`도 같은 일을 한다. 위 코드는 부호를 뒤집으면서 새 리스트를 만들어서 이 문제를 피했다.

## 돌 문제를 바꿔 묻는다면

### 돌의 순서를 마음대로 정할 수 있다면

LeetCode 1049번 Last Stone Weight II는 매번 아무 두 돌이나 골라 부딪칠 수 있고, 남는 무게의 최솟값을 묻는다. 겉보기는 비슷하지만 전혀 다른 문제다. 부딪치는 과정을 끝까지 펼치면 각 돌 앞에 더하기나 빼기를 붙인 합이 된다. 그래서 돌을 두 무리로 나눠 무게 차를 최소로 만드는 문제가 되고, [동적 계획법](/posts/dynamic-programming)의 부분집합 합으로 푼다. [Partition Equal Subset Sum](/posts/leetcode-partition-equal-subset-sum)과 같은 틀이다.

### 마지막 돌이 아니라 차례마다 남은 무게 합을 달라면

힙 풀이에 합계 하나를 들고 다니면 된다. 부딪칠 때마다 합에서 `2x`를 뺀다. y는 `y - x`로 줄고 x는 사라지니 합이 정확히 `2x`만큼 준다.

### 가장 가벼운 두 돌을 합치는 문제라면

부딪치는 대신 합쳐서 비용을 내는 문제는 최소 힙으로 같은 틀을 쓴다. 가장 가벼운 두 개를 꺼내 합친 값을 다시 넣는다. 허프만 부호화가 이 방식으로 트리를 만든다.

### 꺼낸 값을 일정 시간 뒤에 다시 넣는다면

꺼낸 작업을 바로 넣지 않고 기다렸다 넣는 문제는 힙과 대기열을 함께 쓴다. [Task Scheduler](/posts/leetcode-task-scheduler)가 그렇다. "가장 큰 것부터 꺼낸다"는 이 문제와 같고, "언제 다시 넣나"가 더해진다.

같은 "가장 큰 것을 반복해서 꺼낸다" 생각은 [Reorganize String](/posts/leetcode-reorganize-string)에도 나온다. 거기서는 가장 많이 남은 글자 두 개를 꺼내 하나씩 쓰고 다시 넣는다. 힙의 크기를 k로 묶어 두는 쓰임은 [Kth Largest Element in a Stream](/posts/leetcode-kth-largest-element-in-a-stream)에서 본다.

## 면접에서 나올 만한 질문

### 왜 최대 힙을 쓰나요?

차례마다 필요한 연산이 가장 큰 값 꺼내기와 새 값 넣기 두 가지이고, 최대 힙은 둘 다 O(log n)에 한다. 정렬된 배열은 꺼내기는 O(1)이지만 조각을 끼울 때 O(n)이 들고, 정렬 없이 훑으면 꺼내기가 O(n)이다. 나머지 돌의 순서는 필요 없어서 맨 위만 맞추는 힙이 딱 맞다.

### 전체 시간 복잡도는 어떻게 되나요?

O(n log n)이다. 힙을 한꺼번에 만드는 데 O(n), 차례는 돌이 최소 하나씩 줄어서 많아야 n - 1번, 차례마다 힙 연산 세 번이 O(log n)이다. 공간은 힙 O(n)이다.

### 제약이 n 30 이하인데 힙이 꼭 필요한가요?

아니다. 실제로 돌 30개에서는 배열을 두 번 훑는 O(n²) 풀이가 가장 빨랐다. 1만 번 반복에 10ms, 힙은 32ms였다. 그래도 n이 커지면 n²이 바로 드러나기 때문에, 크기에 따라 답이 바뀐다는 점을 말하고 힙을 쓰는 게 좋다.

### 시뮬레이션이 반드시 끝난다고 어떻게 말할 수 있나요?

한 차례마다 돌이 적어도 하나 사라지기 때문이다. 무게가 같으면 둘, 다르면 가벼운 하나가 없어진다. 그래서 차례는 많아야 n - 1번이다. 같을 때 0짜리 돌을 넣는 코드는 이 성질이 흐려지니 넣지 않는다.

### 무게 범위가 작다는 걸 쓸 수 있나요?

무게마다 개수를 세는 칸을 두고 무거운 쪽부터 손가락을 내리며 돌을 고른다. 같은 무게 두 개는 개수를 2로 나눈 나머지로 한 번에 지운다. 부딪친 뒤 남는 돌은 늘 이전에 든 돌보다 가벼워서 부딪치는 횟수가 W번을 넘지 않고, 전체는 O(n + W²)이다. 돌 100만 개에서 힙의 562ms가 20ms로 줄었다.

### Python과 Java로 짤 때 주의할 점은요?

Python의 `heapq`는 최소 힙이라 부호를 뒤집어 넣고 꺼낼 때 다시 뒤집는다. `-(y - x)`의 괄호를 빼먹기 쉽다. Java는 `Collections.reverseOrder()`로 최대 힙을 만들고, 직접 쓸 때는 뺄셈 대신 `Integer.compare`를 쓴다. 꺼낸 값을 `Integer`로 받아 `!=`로 비교하면 128 이상에서 같은 무게를 다르다고 볼 수 있다.

### 아무 두 돌이나 골라도 된다면 어떻게 달라지나요?

그러면 Last Stone Weight II가 되고 힙 문제가 아니다. 부딪치는 과정은 결국 각 돌에 더하기나 빼기를 붙인 합이라서, 돌을 두 무리로 나눠 무게 차를 최소로 만드는 부분집합 합 DP로 푼다. 가장 무거운 것부터 고르는 탐욕이 최적이 아니기 때문이다.
