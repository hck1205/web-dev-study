## 검색 결과에 상품 이름 대신 Shop이 뜬다

React로 만든 쇼핑몰을 오픈하고 한 달이 지났다. 구글에서 상품 이름을 검색해 보니 우리 페이지가 나오긴 하는데, 제목이 "Shop"이고 설명은 비어 있거나 푸터 문구다. 몇몇 상품 페이지는 아예 검색되지 않는다. 브라우저로 열면 상품 이름과 가격이 다 보이는데 왜 이럴까.

이 상품 페이지를 로컬에 같은 모양으로 띄우고, 서버가 처음 보내는 HTML을 `curl`로 받아 봤다.

```bash
# 자바스크립트를 실행하지 않고, 서버가 보낸 HTML에서 제목과 루트만 본다
curl -s localhost:4300/csr/products/42 | grep -o -E '<title>[^<]*</title>|<div id="root">[^<]*</div>'
```

```text
<title>Shop</title>
<div id="root"></div>
```

같은 주소를 Chromium으로 열어 네트워크가 잠잠해질 때까지 기다린 뒤 다시 읽었다.

```text
title: 회색 울 코트 | Shop
root:  <h1>회색 울 코트</h1><p>89,000원</p>
```

사람이 보는 페이지와 서버가 보낸 HTML이 다르다. 제목과 내용은 자바스크립트가 상품 API를 부른 뒤에야 생긴다. 검색 엔진이 이 페이지를 어떻게 읽느냐는 "언제 HTML을 보고, 언제 자바스크립트를 돌리느냐"의 문제다. SPA가 빈 HTML에서 화면을 만드는 과정은 [CSR과 SPA](/posts/rendering-csr-spa)에 있고, 이 글은 그 페이지를 검색 엔진 최적화(SEO) 관점에서 본다. 구글봇이 렌더링하는 순서, 첫 HTML에 꼭 있어야 하는 태그, 같은 페이지가 여러 주소로 퍼지는 문제, 렌더링 방식을 고르는 기준, Next.js에서 쓰는 법, Search Console로 확인하는 법까지 따라간다.

몇 가지가 중요하다.

렌더러는 최신 크롬이다. 구글은 2019년부터 렌더러(Web Rendering Service)를 늘 최신 안정판 크롬에 맞추고 있어서, 최신 자바스크립트 문법 때문에 렌더링이 실패하는 일은 드물다. 문제는 실행 환경이 사람의 브라우저와 다르다는 점이다. 구글봇은 버튼을 누르거나 입력하지 않는다. "더 보기"를 눌러야 불러오는 상품은 보지 못한다. 페이지를 열 때마다 쿠키, `localStorage`, `sessionStorage`를 비운 새 상태로 시작하고, 위치나 알림 같은 권한 요청은 거절한다. 첫 방문 팝업이나 로그인 여부에 따라 내용이 바뀌는 페이지는 늘 "처음 온 비로그인 사용자" 화면으로 보인다.

렌더링은 나중이다. 구글은 렌더 큐에서 기다리는 시간이 대부분 짧다고 설명해 왔다(2019년 발표 기준 중앙값 5초 정도). 하지만 꼬리가 길고, 사이트가 크면 크롤 예산 안에서 렌더링에 쓰는 자원도 더 든다. 자주 바뀌는 가격이나 재고처럼 빨리 반영돼야 하는 정보를 자바스크립트로만 그리면, 검색 결과에 옛 값이 오래 남는다.

첫 HTML이 먼저 읽힌다. 그림의 세 번째 단계가 실수의 대부분이 생기는 곳이다. 첫 HTML에 `noindex`가 있으면 구글은 렌더링하지 않는다. 자바스크립트로 나중에 `noindex`를 지워도 소용없다. 반대로 자바스크립트로 `noindex`를 추가하는 건 렌더링 뒤에 반영된다. 첫 HTML과 렌더된 DOM에서 `canonical`이 다르면 어느 쪽이 쓰일지 장담할 수 없다.

구글만 있는 것도 아니다. 빙도 자바스크립트를 렌더링하지만 범위가 좁다고 알려져 있고, 메신저와 SNS의 링크 미리보기 봇(페이스북, 슬랙, 카카오톡 등)은 자바스크립트를 실행하지 않는다. 생성형 검색 서비스들의 크롤러도 대부분 HTML만 가져간다. 구글이 렌더링해 준다고 첫 HTML을 비워 두면, 나머지는 모두 "Shop"과 빈 `div`를 본다.

## 첫 HTML에 있어야 하는 것

결국 기준은 하나다. 검색과 공유에 필요한 정보는 자바스크립트를 돌리기 전의 HTML에 있어야 한다. 상품 페이지라면 서버가 처음 보내는 `head`가 이 정도는 갖춰야 한다.

```html
<head>
  <meta charset="utf-8">
  <title>회색 울 코트 | Shop</title>
  <meta name="description" content="울 70% 회색 코트. 95~110 사이즈.">
  <link rel="canonical" href="https://shop.example.com/products/42">
  <meta property="og:title" content="회색 울 코트">
  <meta property="og:image" content="https://shop.example.com/img/42-1200x630.jpg">
  <script type="application/ld+json">…</script>
</head>
```

본문(`h1`, 상품 설명, 다른 페이지로 가는 `a href`)도 첫 HTML에 있으면 가장 좋다. 구글이 렌더링으로 채울 수는 있지만 늦고, 다른 봇은 못 채운다. 서버에서 HTML을 만드는 페이지는 `curl`로 바로 확인된다.

```bash
curl -s localhost:4300/ssr/products/42 | grep -o -E '<title>[^<]*</title>|<meta name="description"[^>]*>|<link rel="canonical"[^>]*>'
```

```text
<title>회색 울 코트 | Shop</title>
<meta name="description" content="울 70% 회색 코트. 95~110 사이즈.">
<link rel="canonical" href="https://shop.example.com/products/42">
```

링크는 `a href`여야 크롤러가 따라간다. 구글은 `href`가 있는 `a` 태그만 링크로 본다고 명시해 두었다. `onClick`으로 `router.push`를 부르는 `div`나 `button`은 사람에게는 링크지만 크롤러에게는 끝이 막힌 길이다. 이 차이는 [시맨틱 HTML](/posts/html-semantics)의 "눌리는 것은 button과 a 중 하나다"와 같은 이야기다.

## title과 meta description

`title`은 검색 결과의 파란 제목줄과 브라우저 탭 이름이 된다. 페이지마다 달라야 하고, 앞쪽에 그 페이지만의 말을 둔다. "Shop | 회색 울 코트"보다 "회색 울 코트 | Shop"이 낫다. 검색 결과에서 잘리는 길이는 글자 수가 아니라 화면 폭으로 정해져서 정해진 숫자는 없지만, 핵심이 앞에 있으면 잘려도 남는다. 스크린리더도 페이지를 열 때 `title`을 먼저 읽고, Next.js는 화면 전환 때 이 값을 읽어 준다([ARIA와 키보드·포커스](/posts/aria-keyboard-focus)). 같은 `title`이 수백 페이지에 붙어 있는 건 검색에도 접근성에도 나쁘다.

`meta description`은 순위에 쓰이지 않는다. 검색 결과 제목 아래 설명(스니펫)의 후보일 뿐이다. 구글은 검색어에 더 맞는 문장이 본문에 있으면 그걸 쓰고, `title`도 너무 길거나 내용과 맞지 않으면 다시 써서 보여 준다. 그래도 설명을 쓰는 이유는 쓴 문장이 그대로 쓰일 때가 많고, 공유 미리보기의 기본 설명으로도 쓰이기 때문이다. 상품이라면 가격, 소재, 사이즈처럼 검색한 사람이 고르는 데 필요한 사실을 넣는다.

구글이 `title`을 다시 쓰는 경우는 문서에 꽤 구체적으로 나와 있다. 비어 있거나 "| Shop"처럼 반만 있는 제목, 작년 연도가 남은 낡은 제목, 내용과 맞지 않는 제목, 여러 페이지가 똑같이 쓰는 상투 제목, 키워드를 늘어놓은 제목, 너무 긴 제목이다. 그럴 때 구글은 페이지의 `h1`, 눈에 띄는 큰 글자, `og:title`, 다른 페이지가 이 페이지를 가리키는 링크 문구에서 제목을 새로 만든다. 그러니 `title`과 `h1`이 같은 내용을 말하게 두면 다시 쓰여도 크게 달라지지 않는다. 키워드는 사람들이 실제로 검색할 말을 `title` 앞쪽, `h1`, 첫 문단, URL 경로, 이미지 `alt`에 자연스럽게 한 번씩 둔다. 같은 말을 여러 번 반복한다고 순위가 오르지 않고, 반복이 심하면 스팸 신호가 된다.

`meta keywords`는 구글이 오래전부터 읽지 않는다. 넣어도 해가 되진 않지만 쓸 이유도 없다.

## 같은 페이지, 여러 주소

같은 상품 페이지는 생각보다 많은 주소로 들어온다. 광고 링크의 `utm_` 파라미터, 클릭 추적용 `gclid`, 정렬 순서만 다른 쿼리, 끝에 붙은 `/`, 대문자 섞인 호스트, 리뷰 탭을 여는 `#reviews`. 아래 주소를 조각별로 눌러 보면 검색 엔진이 각 조각을 어떻게 다루는지 나온다.

검색 엔진은 이런 주소들을 모아 같은 내용이라고 판단하면 하나를 대표로 고른다. 그 대표를 우리가 알려 주는 것이 `canonical`이다.

```html
<link rel="canonical" href="https://shop.example.com/products/42">
```

`canonical`은 명령이 아니라 강한 힌트다. 구글은 이 값 외에도 리디렉션, sitemap에 넣은 주소, 내부 링크가 가리키는 주소, HTTPS 여부를 함께 보고 고른다. 그래서 신호를 서로 맞춰 둔다. 내부 링크는 대표 주소로 걸고, sitemap에도 대표 주소만 넣고, 끝의 `/`나 `http`처럼 아예 쓰지 않을 주소는 301로 보낸다. 값은 절대 주소로 쓴다. 상대 주소를 쓰면 스테이징 도메인을 대표로 가리키는 사고가 난다.

대표 주소를 만드는 규칙을 함수로 써 보자. 호스트는 소문자, 기본 포트와 프래그먼트는 빼고, 추적용 파라미터(`utm_`로 시작하는 것, `gclid`, `fbclid`)를 지우고, 남은 파라미터는 이름 순으로 정렬하고, 루트가 아닌 경로 끝의 `/`는 뗀다. 같은 내용이 늘 같은 주소가 되면 서버의 캐시 키, 분석 도구의 페이지 집계에도 그대로 쓸 수 있다.

// URL과 URLSearchParams를 쓰면 호스트 소문자, 기본 포트 제거는 알아서 된다.
function canonicalize(input) {
  const url = new URL(input);
  return url.toString();
}`}
  solution={`function canonicalize(input) {
  const url = new URL(input);
  url.hash = "";
  const drop = (k) => k.startsWith("utm_") || k === "gclid" || k === "fbclid";
  const kept = [...url.searchParams].filter(([k]) => !drop(k));
  kept.sort((a, b) => (a[0] < b[0] ? -1 : a[0] > b[0] ? 1 : 0));
  url.search = new URLSearchParams(kept).toString();
  if (url.pathname.length > 1 && url.pathname.endsWith("/")) {
    url.pathname = url.pathname.slice(0, -1);
  }
  return url.toString();

  tests={[

      args: ["HTTPS://Shop.Example.com:443/products/42/?utm_source=kakao&color=gray&size=m#reviews"],

    },
    { args: ["https://shop.example.com/?gclid=abc"], expected: "https://shop.example.com/", label: "루트의 / 는 남긴다" },
    {
      args: ["https://shop.example.com/search?q=%EC%BD%94%ED%8A%B8&page=2&fbclid=x"],
      expected: "https://shop.example.com/search?page=2&q=%EC%BD%94%ED%8A%B8",
      label: "파라미터 정렬",
    },
    { args: ["https://shop.example.com/products/42"], expected: "https://shop.example.com/products/42", label: "이미 대표 주소" },
    { args: ["http://shop.example.com:8080/a/?b=2&a=1"], expected: "http://shop.example.com:8080/a?a=1&b=2", label: "기본이 아닌 포트는 남는다" },
  ]}
/>

실제로는 `color` 같은 파라미터를 남길지가 설계 판단이다. 색마다 검색량이 있고 사진과 설명이 다르면 각각을 대표 주소로 두고, 색만 다르고 나머지가 같으면 기본 상품 주소를 `canonical`로 가리킨다. 페이지 번호(`page=2`)는 다른 상품 목록이니 첫 페이지로 `canonical`을 걸지 않는다. 걸면 2페이지 이후 상품이 색인되기 어렵다.

## 색인하지 말라는 두 가지 방법

검색에 나오면 안 되는 페이지(장바구니, 내 주문, 검색 결과 페이지, 스테이징 환경)는 `noindex`로 막는다.

```html
<meta name="robots" content="noindex">
```

HTML이 아닌 파일(PDF, 이미지)이나 환경 전체를 막을 때는 응답 헤더로 같은 뜻을 보낸다.

```bash
curl -sI localhost:4300/preview | grep -i robots
```

```text
x-robots-tag: noindex
```

`robots.txt`의 `Disallow`는 뜻이 다르다. "가져가지 말라"이지 "색인하지 말라"가 아니다. `Disallow`로 막은 주소도 다른 사이트에서 링크되면 내용 없이 주소만 색인될 수 있고, Search Console에 "Indexed, though blocked by robots.txt"로 뜬다. 더 나쁜 건 막아 버리면 크롤러가 페이지를 가져오지 못하니 그 안의 `noindex`도 읽지 못한다는 점이다. 색인에서 빼려면 크롤링은 허락하고 `noindex`를 보여 줘야 한다. `robots.txt`의 해석 규칙은 [웹 크롤러 설계 ②](/posts/sd-web-crawler-politeness-dedup)에 있다.

SPA에서는 `robots.txt`가 렌더링을 깨뜨리기도 한다. `/static/`이나 `/api/`를 `Disallow`로 막아 두면 구글의 렌더러가 번들과 상품 API를 가져오지 못해, 렌더된 페이지도 빈 `div`가 된다. 렌더링에 필요한 JS, CSS, API는 막지 않는다.

## sitemap은 지도일 뿐이다

sitemap은 "이 사이트에 이런 주소가 있다"고 알려 주는 XML 목록이다. 링크로 닿기 어려운 페이지가 많거나, 새 페이지가 자주 생기거나, 사이트가 클 때 도움이 된다. 넣는다고 색인이 보장되지는 않는다.

```xml
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://shop.example.com/products/42</loc>
    <lastmod>2026-10-20</lastmod>
  </url>
</urlset>
```

규칙은 많지 않다. 파일 하나에 주소 5만 개, 압축 전 50MB까지이고, 넘으면 여러 파일로 나누고 sitemap 인덱스 파일로 묶는다. 대표 주소만 넣는다. `noindex`나 리디렉션되는 주소를 넣으면 신호가 서로 부딪친다. 구글은 `priority`와 `changefreq`를 무시하고, `lastmod`는 값이 꾸준히 정확한 사이트에서만 쓴다. 배포할 때마다 모든 주소의 `lastmod`를 오늘로 찍으면 결국 무시된다. 내용이 실제로 바뀐 날짜를 넣는다.

sitemap 위치는 Search Console에 제출하거나 `robots.txt`에 `Sitemap: https://shop.example.com/sitemap.xml` 한 줄로 알린다.

sitemap 인덱스는 sitemap 파일들의 목록이고, 인덱스 하나에도 sitemap 5만 개까지 넣는다. 상품이 수십만 개면 `/sitemaps/products-1.xml`처럼 나눠 만들고 인덱스의 각 항목에 그 파일의 `lastmod`를 적는다. 바뀐 상품이 든 파일만 날짜가 바뀌니 구글이 어디를 다시 읽어야 할지 안다. 예전에는 `google.com/ping?sitemap=` 주소로 갱신을 알렸지만 구글이 이 방식을 2023년에 폐기했다. 지금은 정확한 `lastmod`가 그 역할을 한다.

새 글이나 바뀐 상품을 바로 알리고 싶다면 IndexNow도 있다. Bing과 Yandex가 2021년에 내놓은 규약으로, 사이트 루트에 키 파일을 올려 소유를 보이고 바뀐 URL 목록을 `https://api.indexnow.org/indexnow`에 POST로 보낸다. 참여한 검색 엔진끼리 알림을 나눠 받는다. Bing, Yandex, 네이버 등이 받고 구글은 받지 않는다. 그래서 구글에는 sitemap과 Search Console, 다른 검색 엔진에는 IndexNow를 함께 쓰는 식이 된다. 같은 URL을 계속 보내도 크롤링이 빨라지지는 않으니 실제로 바뀐 것만 보낸다.

```bash
# 바뀐 URL 두 개를 IndexNow에 알린다. key 값은 사이트 루트의 {key}.txt 내용과 같아야 한다
curl -X POST "https://api.indexnow.org/indexnow" \
  -H "Content-Type: application/json; charset=utf-8" \
  -d '{"host":"shop.example.com","key":"YOUR_INDEXNOW_KEY","urlList":["https://shop.example.com/products/42","https://shop.example.com/products/43"]}'
```

뉴스 사이트라면 일반 sitemap과 별도로 News sitemap을 둔다. 최근 2일 안에 낸 기사만 넣고, 파일 하나에 1,000개까지다. 기사마다 매체 이름과 언어(`news:publication`), 발행 시각(`news:publication_date`), 제목(`news:title`)을 적는다. 기사 페이지에는 `NewsArticle` 구조화 데이터로 제목, 대표 이미지, 발행·수정 시각, 글쓴이를 함께 알린다. 구글 문서는 내용을 크게 고치지 않고 날짜만 새로 찍어 최신 기사처럼 보이게 하지 말라고 한다. 검색어 없이 뜨는 구글 디스커버의 대표 이미지 조건은 [이미지 최적화 글](/posts/image-optimization#검색-결과에-이미지가-나오려면)에 있다.

## 링크 미리보기와 Open Graph

상품 링크를 카카오톡이나 슬랙에 붙였을 때 뜨는 카드는 검색과 다른 경로로 만들어진다. 각 서비스의 봇이 주소를 가져가서 Open Graph 메타 태그를 읽는다. 이 봇들은 자바스크립트를 실행하지 않는다.

```html
<meta property="og:type" content="website">
<meta property="og:title" content="회색 울 코트">
<meta property="og:description" content="울 70% 회색 코트. 89,000원">
<meta property="og:image" content="https://shop.example.com/img/42-1200x630.jpg">
<meta property="og:url" content="https://shop.example.com/products/42">
<meta name="twitter:card" content="summary_large_image">
```

`og:image`는 절대 주소여야 하고, 봇이 실제로 받아 갈 수 있어야 한다(로그인이 필요한 CDN 주소, 서명이 만료되는 주소는 안 된다). 페이스북 기준 권장 크기는 1200×630이다. 미리보기는 서비스마다 오래 캐시된다. 태그를 고친 뒤에도 옛 카드가 뜨면 페이스북의 공유 디버거나 카카오 개발자 사이트의 공유 디버거로 캐시를 지운다.

## 구조화 데이터로 내용을 설명한다

검색 결과에 별점, 가격, 재고, 이동 경로가 붙은 것을 리치 결과(rich result)라고 한다. 이걸 받으려면 페이지 내용을 기계가 읽는 형식으로 따로 적어 둔다. 이게 구조화 데이터다. schema.org 어휘를 쓰고, 구글은 형식 셋(JSON-LD, Microdata, RDFa) 중 JSON-LD를 권한다. 마크업에 섞지 않고 `script` 하나에 따로 쓰니 관리하기 쉽다.

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "회색 울 코트",
  "image": ["https://shop.example.com/img/42-1200x630.jpg"],
  "offers": {
    "@type": "Offer",
    "price": "89000",
    "priceCurrency": "KRW",
    "availability": "https://schema.org/InStock"
  }
}
</script>
```

구조화 데이터는 화면에 보이는 내용과 같아야 한다. 화면에는 품절인데 `InStock`이라고 쓰거나, 없는 리뷰 별점을 넣으면 구글의 구조화 데이터 정책 위반으로 리치 결과가 빠지고 수동 조치를 받을 수 있다. 넣는다고 반드시 리치 결과가 나오지도 않는다. 구글은 2023년 8월부터 FAQ 리치 결과를 정부·보건 분야의 일부 권위 있는 사이트에만 보여 주고, HowTo 리치 결과는 없앴다. 어떤 유형이 지금 지원되는지는 구글 검색 센터의 구조화 데이터 문서를 확인한다.

JSON-LD를 자바스크립트로 넣어도 구글은 렌더링한 뒤 읽는다. 하지만 다른 봇까지 생각하면 서버에서 넣는 편이 낫다. 검증은 구글의 리치 결과 테스트와 schema.org의 Schema Markup Validator로 한다.

## 언어마다 다른 페이지

같은 상품을 한국어, 영어, 일본어 페이지로 따로 낸다면 검색 엔진이 사용자 언어에 맞는 페이지를 보여 주도록 서로의 존재를 알린다. 이게 `hreflang`이다.

```html
<link rel="alternate" hreflang="ko" href="https://shop.example.com/ko/products/42">
<link rel="alternate" hreflang="en" href="https://shop.example.com/en/products/42">
<link rel="alternate" hreflang="ja" href="https://shop.example.com/ja/products/42">
<link rel="alternate" hreflang="x-default" href="https://shop.example.com/products/42">
```

아래 그림처럼 세 페이지가 서로를 가리켜야 한다. 한쪽만 가리키면 무시된다.

실수가 나는 지점은 정해져 있다.

- 모든 언어 페이지가 자기 자신을 포함한 전체 목록을 똑같이 가져야 한다. 한국어 페이지에도 `hreflang="ko"` 줄이 있어야 한다.
- 언어 코드는 ISO 639-1, 지역은 ISO 3166-1이다. 영국 영어는 `en-GB`이지 `en-UK`가 아니다. 지역만 쓰는 `kr`은 틀린 값이다.
- 각 언어 페이지의 `canonical`은 자기 자신이어야 한다. 영어 페이지의 `canonical`이 한국어 페이지를 가리키면 "영어 페이지는 한국어 페이지의 사본"이라고 말하는 셈이라 `hreflang`과 부딪친다.
- `x-default`는 어느 언어에도 맞지 않는 사용자에게 보여 줄 페이지다. 언어 선택 페이지나 기본 언어 페이지를 둔다.
- 구글은 `html`의 `lang` 속성으로 언어 버전을 묶지 않는다. `lang`은 스크린리더와 번역기를 위한 값이고, 언어 버전 연결은 `hreflang`이 한다.

언어를 IP나 `Accept-Language` 헤더로 자동 리디렉션하면 곤란하다. 구글봇은 주로 미국 IP에서 `Accept-Language` 헤더 없이 크롤링하니 다른 언어 페이지를 영영 보지 못할 수 있다. 자동으로 보내지 말고 언어 제안 배너를 띄운다.

## 해시 라우팅은 주소가 하나다

오래된 SPA나 정적 호스팅에서 새로고침 404를 피하려고 해시 라우팅을 쓰는 경우가 있다. `https://shop.example.com/#/products/42` 같은 주소다. `#` 뒤는 서버로 가지 않으니 서버는 늘 `index.html` 하나만 주면 되고, 라우팅은 브라우저 안에서 끝난다.

검색 쪽에서는 치명적이다. 구글은 색인할 때 `#` 뒤를 무시하므로, 모든 상품이 `https://shop.example.com/` 한 주소가 된다. 상품 1만 개가 검색 결과에 한 줄로 합쳐진다. 2009년쯤 구글이 `#!`(해시뱅) 주소를 따로 크롤링해 주는 방식을 제안했지만 2015년에 폐기했고, 지금은 지원하지 않는다.

History API(`pushState`)로 진짜 경로를 쓰고, 서버는 모르는 경로에도 `index.html`을 주는 폴백을 둔다. 이 설정과 폴백이 만드는 문제는 [CSR과 SPA](/posts/rendering-csr-spa)에 있다. 같은 페이지 안의 위치를 가리키는 `#reviews` 같은 프래그먼트는 원래 용도대로 써도 괜찮다.

## 렌더링 방식은 페이지마다 고른다

지금까지의 결론은 "검색과 공유에 필요한 정보는 첫 HTML에"였다. 그 HTML을 언제 어디서 만들지가 렌더링 방식의 선택이다. 방식마다 비용과 신선도가 다르고, 자세한 비교는 [CSR, SSR, SSG, ISR, 스트리밍](/posts/rendering-strategies)에 있다. SEO 관점만 추리면 이렇게 고른다.

- 검색으로 들어와야 하고 내용이 잘 안 바뀐다: 블로그 글, 도움말, 상품 소개. 빌드할 때 HTML을 만드는 SSG가 가장 단순하고 빠르다([SSG와 ISR](/posts/rendering-ssg-isr)).
- 검색으로 들어와야 하고 내용이 자주 바뀐다: 가격·재고가 있는 상품 상세, 목록. 일정 시간마다 다시 만드는 ISR이나, 요청마다 만드는 SSR([SSR](/posts/rendering-ssr))을 쓴다. 가격이 몇 분마다 바뀌어도 대부분의 정보(이름, 설명, 사진)는 고정이니, 고정 부분은 미리 만들고 가격만 따로 받아도 된다.
- 검색에 나올 필요가 없다: 장바구니, 마이페이지, 관리자 화면, 로그인 뒤의 대시보드. CSR로 충분하고, `noindex`를 건다.

한 사이트 안에서 페이지마다 다르게 고르는 게 보통이다. 전체를 SSR로 바꾸는 건 SEO가 필요한 페이지가 대부분일 때의 선택이고, 서버 비용과 운영 부담이 따라온다. 렌더러에게 맡기는 방법(봇에게만 미리 렌더링한 HTML을 주는 동적 렌더링)은 구글이 이제 권하지 않는 임시방편이라고 문서에 적어 두었다.

## Next.js에서 메타데이터 쓰기

Next.js App Router는 `metadata` 객체나 `generateMetadata` 함수를 export하면 `head`에 태그를 만들어 준다. 서버 컴포넌트(`page.tsx`나 `layout.tsx`)에서만 export할 수 있다. `"use client"` 파일에서는 안 된다.

```tsx
// app/products/[id]/page.tsx
import type { Metadata } from "next";
import { notFound } from "next/navigation";

export async function generateMetadata({ params }: { params: Promise<{ id: string }> }): Promise<Metadata> {
  const { id } = await params;
  const product = await getProduct(id);
  if (!product) return { title: "상품 없음", robots: { index: false } };
  return {
    title: `${product.name} | Shop`,
    description: product.summary,
    alternates: {
      canonical: `/products/${id}`,
      languages: { ko: `/ko/products/${id}`, en: `/en/products/${id}` },
    },
    openGraph: { title: product.name, images: [product.ogImage], type: "website" },
  };
}

export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const product = await getProduct(id);
  if (!product) notFound();
  // …
}
```

```tsx
// app/layout.tsx: 상대 주소를 절대 주소로 바꿀 기준
export const metadata: Metadata = {
  metadataBase: new URL("https://shop.example.com"),
};
```

`metadataBase`가 있으면 `canonical`, `og:image` 같은 상대 주소가 절대 주소로 바뀐다. 이 값을 환경마다 다르게 두면 스테이징이 프로덕션을 가리키는 일을 막을 수 있지만, 반대로 프로덕션 빌드에 스테이징 주소가 들어가는 사고도 이 한 줄에서 난다.

`app/sitemap.ts`와 `app/robots.ts`를 만들면 `/sitemap.xml`과 `/robots.txt`가 생긴다. 구조화 데이터는 페이지 안에 `script type="application/ld+json"`을 직접 그린다. 이때 Next.js 문서는 `JSON.stringify(data).replace(/</g, "\\u003c")`처럼 `<`를 이스케이프하라고 권한다. 상품 이름에 `</script>`가 들어 있으면 스크립트가 끊기고 그 뒤가 HTML로 해석되기 때문이다([XSS](/posts/xss)).

Next.js 15.2부터는 `generateMetadata`가 느릴 때 페이지를 먼저 보내고 메타데이터를 나중에 흘려보내는 스트리밍 메타데이터가 기본이다. 이때 태그는 `head`가 아니라 `body` 쪽에 붙는다. 구글봇처럼 자바스크립트를 실행하는 봇은 문제없이 읽는다고 Next.js 문서가 밝히고 있고, 페이스북 미리보기 봇 같은 "HTML만 읽는 봇"은 User-Agent로 구분해 예전처럼 `head`에 넣어 준다. 이 목록은 `next.config.ts`의 `htmlLimitedBots`로 바꿀 수 있다. 미리보기 카드가 이상하면 이 경계부터 본다.

존재하지 않는 상품에서 `notFound()`를 부르면 스트리밍이 시작되기 전에는 404 상태 코드가 나간다. 스트리밍이 이미 시작된 뒤(`Suspense` 경계 안에서 부른 경우)에는 상태 코드를 바꿀 수 없어서 200이 나가고, 대신 `<meta name="robots" content="noindex">`가 들어간다. 상태 코드를 정확히 주고 싶으면 상품 존재 여부를 경계 바깥, 렌더링 앞에서 확인한다.

## Search Console로 구글이 본 화면 확인하기

추측하지 말고 구글에게 직접 묻는다. Google Search Console에 사이트를 등록하면 구글이 내 페이지를 어떻게 봤는지 확인할 수 있다.

URL 검사(URL Inspection)에 상품 주소를 넣으면 지금 색인 상태가 나온다. "실제 URL 테스트(Test live URL)"를 누르면 구글봇이 그 자리에서 페이지를 가져가 렌더링하고, "테스트한 페이지 보기(View tested page)"에서 세 가지를 보여 준다.

- HTML: 렌더링이 끝난 DOM이다. 여기에 상품 이름과 `h1`이 있으면 렌더링은 됐다. 없으면 렌더링 단계에서 막힌 것이다.
- 스크린샷: 구글봇 화면 크기로 찍은 첫 화면이다. 빈 화면이나 로딩 스피너만 보이면 렌더러가 기다리는 동안 내용이 안 나온 것이다.
- 추가 정보: 가져오지 못한 리소스 목록과 자바스크립트 콘솔 메시지다. `robots.txt`에 막힌 API, 렌더러에서만 나는 오류(구글봇은 `localStorage`가 비어 있어서 나는 예외 같은 것)가 여기 찍힌다.

페이지 색인 생성(Page indexing) 보고서는 사이트 전체에서 색인되지 않은 페이지를 이유별로 묶어 준다. 자주 보는 이유를 영어 화면의 이름으로 적으면 이렇다.

- "Excluded by 'noindex' tag": 의도한 것인지 확인한다. 의도하지 않았다면 아래 실수 목록의 첫 번째다.
- "Soft 404": 200을 줬지만 내용이 "없음" 페이지처럼 보인다.
- "Duplicate, Google chose different canonical than user": 내가 준 `canonical`과 구글이 고른 대표 주소가 다르다. 내부 링크와 sitemap이 어느 주소를 가리키는지 맞춰 본다.
- "Crawled - currently not indexed", "Discovered - currently not indexed": 가져갔거나 알고는 있지만 아직 넣지 않았다. 내용이 빈약하거나 비슷한 페이지가 많을 때 흔하다.

고친 뒤에는 URL 검사에서 "색인 생성 요청(Request indexing)"을 눌러 다시 가져가게 하고, 페이지 보고서의 "수정 결과 확인(Validate fix)"으로 묶음 단위 재검사를 시작한다. 반영은 며칠에서 몇 주가 걸린다.

## 배포하고 나서 터지는 실수

검색 유입이 갑자기 줄었을 때 먼저 보는 것들이다.

스테이징의 `noindex`가 프로덕션에 나갔다. 스테이징을 막으려고 넣은 `<meta name="robots" content="noindex">`나 `X-Robots-Tag` 헤더가 환경 변수 실수로 프로덕션에 그대로 나가는 경우다. 페이지 색인 생성 보고서에서 "Excluded by 'noindex' tag"가 하루 만에 수천 개로 뛴다. Vercel 같은 플랫폼은 미리보기 배포에 `X-Robots-Tag: noindex`를 자동으로 붙인다. 이건 정상이지만, 프로덕션 도메인이 미리보기 배포를 가리키고 있으면 프로덕션도 막힌다. 배포 파이프라인에 프로덕션 주소를 `curl -sI`로 찔러 `noindex`가 없는지 보는 단계를 넣어 두면 싸게 막을 수 있다.

```bash
# 프로덕션 배포 직후: 헤더와 HTML 양쪽에서 noindex가 없어야 한다
curl -sI https://shop.example.com/products/42 | grep -i x-robots-tag
curl -s https://shop.example.com/products/42 | grep -o '<meta name="robots"[^>]*>'
```

없는 상품이 200을 준다(소프트 404). SPA는 서버가 모든 경로에 `index.html`과 200을 주니, 없는 상품도 "상품이 없습니다"라는 화면과 함께 200이 된다. 앞의 로컬 서버로 재 보면 차이가 그대로 보인다.

```bash
curl -s -o /dev/null -w "%{http_code}\n" localhost:4300/csr/products/999
curl -s -o /dev/null -w "%{http_code}\n" localhost:4300/ssr/products/999
```

```text
200
404
```

CSR 쪽은 렌더링하면 제목이 "상품 없음 | Shop"이고 본문이 "상품이 없습니다"인 200 페이지다. 구글은 이런 페이지를 소프트 404로 분류하지만, 그 판단이 늦거나 틀리면 빈 페이지가 색인되고 크롤 예산을 쓴다. 서버에서 판단할 수 있으면 404를 주고, CSR에서 어쩔 수 없으면 자바스크립트로 `noindex` 메타 태그를 추가하거나 404를 주는 주소로 이동시킨다. 품절은 없는 상품이 아니다. 품절 상품은 200으로 두고 구조화 데이터의 `availability`를 `OutOfStock`으로 바꾼다.

모든 페이지의 `canonical`이 홈을 가리킨다. 레이아웃에 `canonical: "/"`를 한 번 넣고 페이지에서 덮어쓰지 않으면, 모든 페이지가 "나는 홈의 사본"이라고 말한다. 구글이 무시해 주기도 하지만 색인이 크게 줄어든다. `canonical`은 페이지마다 만든다.

렌더러가 API를 못 부른다. API를 `robots.txt`로 막았거나, 봇 차단 방화벽 규칙이 구글봇 IP를 막았거나, API가 로그인 쿠키를 요구한다. URL 검사의 "추가 정보"에 실패한 요청이 찍힌다.

`title`이 모두 같다. 클라이언트에서 `document.title`을 바꾸는 코드가 라우트 전환에서만 돌고 첫 로드에서는 안 돌면, 구글이 렌더링한 페이지도 사이트 이름만 남는다. 이건 처음 장면의 "Shop"이다.

## 다시 Shop으로

검색 결과에 "Shop"이 뜬 이유는 제목과 내용이 자바스크립트를 돌린 뒤에야 생겼기 때문이다. 구글은 그 페이지를 나중에 렌더링해서 읽을 수 있지만 늦고, 실행 환경이 사람과 다르며, 다른 봇은 렌더링하지 않는다. 상품 상세를 SSG나 ISR로 바꿔 첫 HTML에 `title`, `description`, `canonical`, Open Graph, JSON-LD, `h1`, `a href` 링크를 넣으면 `curl` 한 줄로도 상품 이름이 보인다. 그다음은 Search Console의 URL 검사로 구글이 본 화면을 확인하고, 페이지 보고서로 `noindex`와 소프트 404, 대표 주소 충돌을 지켜보는 일이다.

## 면접에서 나올 만한 질문

### CSR 페이지도 구글에 색인되나요?

된다. 구글봇은 HTML을 크롤링한 뒤 200 응답 페이지를 렌더 큐에 넣고 최신 크롬으로 자바스크립트를 실행해 렌더된 DOM을 색인한다. 다만 렌더링이 나중에 일어나 반영이 늦고, 클릭·입력을 하지 않으며 저장소와 쿠키가 빈 상태로 실행된다. 빙 일부와 SNS 미리보기 봇은 렌더링하지 않으니 중요한 정보는 첫 HTML에 넣는다.

### 첫 HTML에 noindex가 있고 자바스크립트로 지우면 어떻게 되나요?

색인되지 않는다. 구글은 렌더링 전에 첫 HTML의 robots 메타를 먼저 읽고, `noindex`가 있으면 렌더링 자체를 하지 않는다. 그래서 자바스크립트로 지우는 코드는 실행될 기회가 없다. 반대로 자바스크립트로 `noindex`를 추가하는 건 렌더링 뒤에 반영된다.

### canonical은 무엇이고 어떻게 정하나요?

같은 내용이 여러 주소로 존재할 때 대표 주소를 검색 엔진에 알리는 힌트다. 추적 파라미터, 끝 슬래시, 대소문자, 정렬 파라미터처럼 내용이 같은 주소는 하나로 모은다. 강제가 아니라 힌트라서 내부 링크, sitemap, 301 리디렉션을 같은 주소로 맞춰야 구글이 그대로 따른다. 절대 주소로 쓰고 페이지마다 자기 주소를 넣는다.

### robots.txt로 막으면 검색 결과에서 빠지나요?

아니다. `Disallow`는 가져가지 말라는 뜻이라, 다른 곳에서 링크된 주소는 내용 없이 색인될 수 있다. 게다가 페이지를 가져오지 못하니 그 안의 `noindex`도 읽지 못한다. 색인에서 빼려면 크롤링은 허락하고 `noindex` 메타나 `X-Robots-Tag` 헤더를 준다. SPA에서는 JS나 API를 막으면 렌더링까지 깨진다.

### 해시 라우팅이 SEO에 불리한 이유는 무엇인가요?

`#` 뒤는 서버로 가지 않고, 구글은 색인할 때 프래그먼트를 무시한다. 그래서 `/#/products/42`와 `/#/products/43`이 모두 같은 주소 `/`로 취급되어 상품 페이지가 따로 색인되지 않는다. 해시뱅 크롤링 방식은 이미 폐기됐다. History API로 실제 경로를 쓰고 서버에 SPA 폴백을 둔다.

### 소프트 404는 무엇이고 어떻게 막나요?

없는 페이지가 404가 아니라 200과 "없음" 화면을 주는 경우다. SPA는 모든 경로에 `index.html`과 200을 주니 쉽게 생긴다. 서버에서 판단할 수 있으면 404를 주고, CSR에서만 알 수 있으면 `noindex`를 추가하거나 404 주소로 보낸다. Next.js의 `notFound()`는 스트리밍 전이면 404를, 이미 스트리밍 중이면 200과 `noindex`를 준다. 품절은 404가 아니라 재고 상태로 표현한다.

### hreflang을 쓸 때 흔한 실수는 무엇인가요?

서로 가리키지 않거나 자기 자신을 빼먹는 것, `en-UK`처럼 틀린 코드를 쓰는 것, 언어 페이지의 `canonical`을 한 언어로 몰아 `hreflang`과 부딪치게 하는 것이다. 모든 언어 페이지가 자신을 포함한 같은 목록을 갖고, 각자 자기 자신을 `canonical`로 둔다. 구글봇은 주로 미국 IP에서 언어 헤더 없이 크롤링하니 언어 자동 리디렉션도 피한다.

### SEO가 필요한 페이지의 렌더링 방식은 어떻게 고르나요?

페이지마다 고른다. 검색 유입이 중요하고 잘 안 바뀌면 SSG, 자주 바뀌면 ISR이나 SSR, 검색이 필요 없는 로그인 뒤 화면은 CSR과 `noindex`다. 목표는 검색과 공유에 필요한 정보가 첫 HTML에 있는 것이고, 고른 뒤에는 `curl`로 첫 HTML을, Search Console의 URL 검사로 구글이 렌더링한 결과를 확인한다.
