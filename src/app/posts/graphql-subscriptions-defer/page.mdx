주문 상세 화면에 배송 상태가 있다. 지금은 사용자가 새로고침해야 바뀐다. "배송 출발" 알림 푸시를 받고 앱을 열었는데 화면에는 아직 "결제 완료"가 떠 있다는 문의가 들어왔다. 상태가 바뀌면 화면도 바로 바뀌게 하고 싶다.

방법은 여럿이다. 몇 초마다 같은 쿼리를 다시 보내는 폴링, 서버가 이벤트를 밀어 주는 구독(subscription), 쿼리 결과가 바뀔 때마다 서버가 새 결과를 보내는 라이브 쿼리. 그리고 이것과 헷갈리기 쉬운 `@defer`·`@stream`이 있다. 이 글은 넷을 직접 돌려 보며 무엇이 다른지, 운영에서 무엇을 떠안는지 정리한다. 데모는 Node.js 22, graphql-js 16.14, graphql-ws 6.4, Redis 7.0으로 만들었고 `@defer`·`@stream`만 graphql-js 17.0.2로 돌렸다.

연결을 오래 쥐는 전송 계층 자체(WebSocket 프레임, 하트비트, 프록시 타임아웃)는 [WebSocket 깊게 보기](/posts/websocket-deep-dive)와 [HTTP 스트리밍](/posts/http-streaming-sse)에, 폴링·롱 폴링·SSE·WebSocket을 고르는 일반적인 기준은 [실시간 통신](/posts/realtime-communication)에 있다. 여기서는 그 위에 GraphQL이 얹는 것만 본다.

## 구독은 이벤트를 응답으로 바꾼다

구독은 스키마의 세 번째 루트 타입이다.

```graphql
type Subscription {
  orderStatusChanged(id: ID!): Order!
}
```

쿼리는 요청 하나에 응답 하나다. 구독은 요청 하나에 응답이 여러 번 온다. 그 사이에서 실행기가 하는 일은 두 단계다. 먼저 최상위 필드의 `subscribe` 함수를 불러 이벤트 원천(source stream)을 만든다. 보통 비동기 이터레이터다. 그다음 이벤트가 하나 올 때마다 그 이벤트를 루트 값으로 삼아 선택 집합을 평소처럼 실행하고 결과 하나를 내보낸다. 이벤트를 응답으로 바꾸는 이 두 번째 단계 덕분에 클라이언트는 쿼리와 똑같이 필요한 필드만 고른다.

```js
const roots = {
  orderStatusChanged: {
    // 1) 이벤트 원천: bus에 'order' 이벤트가 오면 이 주문 것만 흘려보낸다
    subscribe: async function* ({ id }) {
      for await (const [o] of on(bus, "order")) {
        if (o.id === id) yield { orderStatusChanged: o };
      }
    },
  },
  // 쓰기가 일어난 곳에서 이벤트를 낸다
  setStatus: ({ id, status }) => {
    bus.emit("order", { id, status });
    return { id, status };
  },
};
```

구독이 "주문 객체가 바뀐 것을 서버가 알아서 감지하는" 기능이 아니라는 점을 짚어 두자. 이벤트를 내는 것은 서버 코드다. `setStatus` 뮤테이션이 `bus.emit`을 부르지 않으면 구독자는 아무것도 받지 못한다. 배치 작업이나 다른 서비스가 DB를 직접 바꾸면 그 변경도 이벤트로 이어 줘야 한다. 그래서 구독은 "이벤트 기반"이다. 어떤 이벤트를 언제 낼지는 서버가 정한다.

구독 작업은 최상위 필드를 하나만 가질 수 있다. 이벤트 원천을 하나로 정해야 하기 때문이다. 검증 규칙 `SingleFieldSubscriptionsRule`이 이걸 막는다. 실행기가 이벤트마다 선택 집합을 돌리는 과정은 [GraphQL 실행 엔진 안쪽](/posts/graphql-execution-validation)의 구독 부분에 있다.

## WebSocket 위에서 오가는 메시지

GraphQL 명세는 구독 결과를 어떻게 실어 나를지 정하지 않는다. 실무에서 가장 많이 쓰는 것은 WebSocket 위의 `graphql-transport-ws` 하위 프로토콜이고, 이를 구현한 라이브러리가 graphql-ws다. 예전에 널리 쓰던 `subscriptions-transport-ws`(하위 프로토콜 이름 `graphql-ws`)는 관리가 끝난 별개의 프로토콜이라, 이름이 비슷해도 서로 붙지 않는다. 서버와 클라이언트의 하위 프로토콜이 맞는지부터 본다.

graphql-ws 서버에 원시 WebSocket 클라이언트로 붙어 오가는 프레임을 그대로 찍었다. 화살표 `->`는 클라이언트가 보낸 것, `<-`는 받은 것이다.

```text
A -> {"type":"connection_init","payload":{"token":"secret"}}
A <- {"type":"connection_ack"}
A -> {"id":"1","type":"subscribe","payload":{"query":"subscription($id: ID!) { orderStatusChanged(id: $id) { id status } }","variables":{"id":"42"}}}
A <- {"id":"1","type":"next","payload":{"data":{"orderStatusChanged":{"id":"42","status":"SHIPPED"}}}}
A <- {"id":"1","type":"next","payload":{"data":{"orderStatusChanged":{"id":"42","status":"DELIVERED"}}}}
A -> {"id":"1","type":"complete"}
A -> {"type":"ping"}
A <- {"type":"pong"}
```

`SHIPPED`와 `DELIVERED` 사이에 주문 7번의 이벤트도 버스에 흘렸는데, `subscribe` 함수가 걸러서 오지 않았다. 아래 그림에서 단계별로 메시지가 무슨 일을 하는지 보자.

인증이 틀리거나 순서를 어기면 서버는 WebSocket 닫기 코드로 답한다.

```text
B -> {"type":"connection_init","payload":{"token":"bad"}}
B closed 4403 Forbidden

C -> {"id":"1","type":"subscribe","payload":{"query":"subscription { orderStatusChanged(id: 1) { id } }"}}
C closed 4401 Unauthorized

(D는 연결만 열고 아무것도 보내지 않았다)
D closed 4408 Connection initialisation timeout
```

B는 `onConnect`가 거절해서 4403, C는 `connection_init` 없이 구독부터 보내서 4401, D는 3초(graphql-ws의 기본 `connectionInitWaitTimeout`) 안에 인사하지 않아서 4408로 닫혔다. 클라이언트 로그에 4400번대 코드가 찍히면 이 표를 먼저 본다. 4403에 재연결을 무한히 반복하는 클라이언트는 서버를 괴롭히기만 하니, graphql-ws 클라이언트의 `shouldRetry`로 인증 실패에서는 다시 붙지 않게 한다.

### 토큰은 연결이 열릴 때 한 번 본다

HTTP 요청은 매번 토큰을 싣지만 WebSocket 연결은 처음 한 번만 인증한다. 연결이 몇 시간 살아 있으면 그 사이에 토큰이 만료되거나 권한이 바뀌어도 연결은 그대로다. 서버는 연결마다 토큰 만료 시각을 기억해 두고, 지나면 연결을 4403으로 닫는다. 클라이언트는 `connectionParams`를 함수로 넘겨 다시 붙을 때마다 새 토큰을 꺼내게 한다.

```ts
import { createClient } from "graphql-ws";

const client = createClient({
  url: "wss://api.example.com/graphql",
  // 다시 연결할 때마다 불린다: 갱신된 토큰을 싣는다
  connectionParams: async () => ({ token: await getAccessToken() }),
  retryAttempts: 5,
});
```

권한 검사는 연결 때 한 번으로 끝나지 않는다. "주문 42번을 구독할 수 있는가"는 `subscribe` 함수에서 보고, "이 이벤트를 이 사람에게 보내도 되는가"는 이벤트마다 본다. 구독한 뒤에 주문의 주인이 바뀌는 경우도 있기 때문이다. 쿠키로 인증하는 WebSocket이 다른 사이트에서 열리는 문제(CSWSH)는 [WebSocket 깊게 보기](/posts/websocket-deep-dive)에 있다.

### SSE로 실어 나르기

WebSocket 대신 SSE(Server-Sent Events)로 구독을 나를 수도 있다. graphql-sse 라이브러리가 이 방식이고, 구독을 보통의 HTTP POST로 보내면 응답이 `text/event-stream`으로 열려 `next` 이벤트가 이어서 온다. HTTP 위라서 기존 인증 헤더, 프록시, 로드 밸런서 설정을 그대로 쓰고, WebSocket이 막힌 사내망에서도 통한다. 대신 서버에서 클라이언트로만 흐르므로 구독을 끝낼 때는 요청을 끊거나 따로 요청을 보낸다. HTTP/1.1에서는 브라우저가 출처마다 동시 연결을 6개쯤으로 제한해서 탭을 여러 개 열면 막힐 수 있다. HTTP/2를 쓰면 연결 하나에 여러 스트림이 실려 이 문제가 거의 사라진다. SSE 자체의 동작은 [HTTP 스트리밍](/posts/http-streaming-sse)에 있다.

## 서버가 두 대가 되면 이벤트가 반만 간다

데모의 이벤트 버스는 서버 프로세스 안의 `EventEmitter`다. 서버가 한 대일 때는 잘 돈다. 같은 서버를 두 대 띄우고, 클라이언트는 A에 구독을 열고, 뮤테이션은 한 번은 A로 한 번은 B로 보냈다. 로드 밸런서 뒤에서는 이렇게 갈리는 것이 보통이다.

```text
== 1) in-memory bus per server
client@A got {"orderStatusChanged":{"id":"42","status":"SHIPPED"}}
mutation SHIPPED sent to :18321
mutation DELIVERED sent to :18322
```

B로 간 `DELIVERED`는 오지 않았다. B의 `EventEmitter`에 낸 이벤트는 B 안에서만 돈다. A에 붙은 구독자는 그 이벤트를 알 길이 없다. 화면은 "배송 중"에 멈춰 있고 에러는 어디에도 없다. 서버 한 대로 개발할 때는 절대 안 보이는 장애다.

이벤트를 서버 바깥의 공용 채널로 내보내면 풀린다. Redis pub/sub를 다리로 놓았다. 각 서버는 이벤트를 Redis 채널에 발행하고, 같은 채널을 구독해서 받은 메시지를 자기 버스에 다시 흘린다.

```js
function redisBus() {
  const bus = new EventEmitter();
  const pub = new Redis(16399), sub = new Redis(16399); // 구독용 연결은 따로 둔다
  sub.subscribe("order");
  sub.on("message", (_ch, msg) => EventEmitter.prototype.emit.call(bus, "order", JSON.parse(msg)));
  bus.emit = (ev, payload) => { pub.publish(ev, JSON.stringify(payload)); return true; };
  return bus;
}
```

```text
== 2) redis pub/sub bridge
client@A got {"orderStatusChanged":{"id":"42","status":"SHIPPED"}}
mutation SHIPPED sent to :18331
client@A got {"orderStatusChanged":{"id":"42","status":"DELIVERED"}}
mutation DELIVERED sent to :18332
redis NUMSUB ["order",2]
```

이번에는 B로 간 뮤테이션도 A의 구독자에게 도착했다. `NUMSUB`의 2는 두 서버가 모두 `order` 채널을 듣고 있다는 뜻이다. 아래 그림에서 두 경우의 이벤트 경로를 비교해 보자.

Redis pub/sub에는 짚어 둘 성질이 있다. 메시지를 저장하지 않는다. 발행하는 순간 듣고 있지 않던 서버는 그 메시지를 영영 못 받는다. 서버가 재시작하는 몇 초, Redis 연결이 끊긴 사이의 이벤트는 사라진다. 그래서 구독은 "놓칠 수 있는 알림"으로 다루고, 클라이언트는 다시 연결될 때 쿼리로 현재 상태를 한 번 다시 받는다. 놓치면 안 되는 이벤트라면 Redis Streams나 Kafka처럼 오프셋을 가진 저장소를 두고 "마지막으로 받은 위치부터"를 구현한다. 메시지 큐 쪽 이야기는 [메시지 큐 기초](/posts/message-queue-basics)에 있다.

모든 서버가 모든 이벤트를 받는다는 점도 비용이다. 서버 20대, 초당 주문 변경 1,000건이면 서버마다 초당 1,000개를 받아 대부분 걸러 버린다. 채널을 `order:42`처럼 잘게 나누면 구독자가 있는 서버만 받는다. 대신 채널 수가 늘고 구독·해지가 잦아진다.

### 연결 수가 곧 비용이다

구독 하나는 연결 하나를 오래 쥔다. 동시 접속 10만 명이면 서버들이 WebSocket 10만 개를 들고 있어야 한다. 연결마다 메모리(소켓 버퍼, 이터레이터, 인증 정보)가 들고, 배포할 때 서버를 내리면 그 서버의 연결이 한꺼번에 끊겨 다른 서버로 재연결이 몰린다. graphql-ws 클라이언트의 재시도 간격에 무작위 지연(jitter)을 두는 이유다. 로드 밸런서의 유휴 타임아웃, 하트비트, 느린 수신자 처리는 [WebSocket 깊게 보기](/posts/websocket-deep-dive)에서 실험했다.

그래서 무엇을 구독으로 만들지 고른다. "지금 보고 있는 주문의 상태"처럼 사용자가 화면 앞에서 기다리고, 바뀌는 빈도가 낮고, 바로 보여야 가치가 있는 것만 구독으로 만든다. 목록 전체의 실시간 반영이나 몇 분 늦어도 되는 값은 폴링이나 다음 화면 진입 때 다시 받기로 충분하다.

## 이벤트 하나에 실행은 구독자 수만큼

구독의 비용에는 연결 말고도 하나가 더 있다. 이벤트가 오면 실행기는 그 이벤트를 구독자마다 따로 실행한다. 구독자마다 고른 필드가 다를 수 있고, 권한에 따라 결과가 다를 수 있기 때문이다. 같은 주문을 구독한 사람이 1,000명, 10,000명일 때 이벤트 하나를 흘려 봤다. 네트워크 없이 프로세스 하나 안에서 graphql-js의 `subscribe()` 이터레이터만 만들어 쟀다. `buyer` 필드에는 호출 수를 세는 리졸버를 달았다.

```js
// 같은 문서로 구독 n개를 만들고, 이벤트 하나를 흘려 n개가 모두 받을 때까지 잰다
const doc = parse(`subscription { orderStatusChanged(id: "42") { id status buyer { name } } }`);
for (let i = 0; i < n; i++) its.push(await subscribe({ schema, document: doc, rootValue }));
bus.emit("order", { id: "42", status: "SHIPPED" });
```

```text
subscribers=1000 delivered=1000 buyerResolverCalls=1000 time=55.2ms listeners=1000
subscribers=10000 delivered=10000 buyerResolverCalls=10000 time=689.8ms listeners=10000
```

이벤트는 하나인데 `buyer` 리졸버가 구독자 수만큼 불렸다. 10,000명이면 이벤트 하나를 나눠 주는 데만 0.7초 가까이 걸렸고, 그동안 이 프로세스는 다른 요청을 거의 처리하지 못한다. `buyer`가 DB를 부르는 리졸버였다면 이벤트 하나에 쿼리 1만 개다. 요청 단위로 만드는 DataLoader는 구독자 사이에서 공유되지 않으니 이걸 묶어 주지 못한다.

그래서 구독 페이로드에는 이벤트에 이미 들어 있는 값만 담고, 리졸버가 추가로 DB를 부르는 깊은 관계는 넣지 않는 편이 안전하다. 구독자가 많은 공개 이벤트(경기 점수, 공지)라면 같은 문서·같은 권한의 구독자를 묶어 결과를 한 번만 만들고 나눠 주는 방식을 쓴다. 일부 GraphQL 게이트웨이나 서버 제품이 이런 중복 제거를 제공하지만, graphql-js와 graphql-ws만으로는 직접 만들어야 한다.

## 이벤트에는 무엇을 담을까

구독이 돌려주는 타입을 정할 때 두 갈래가 있다. 바뀐 객체를 통째로 담거나(`orderStatusChanged: Order!`), "바뀌었다"는 신호만 담고 클라이언트가 쿼리로 다시 받게 하는 방식(`orderChanged: ID!`)이다.

객체를 담는 쪽은 정규화 캐시와 잘 맞는다. 구독 결과에 `__typename`과 `id`가 들어 있으면 Apollo Client나 urql은 그 결과를 캐시의 `Order:42` 항목에 합친다. 그러면 같은 주문을 보여 주던 다른 쿼리의 화면도 별도 코드 없이 바뀐다. 구독으로 받은 데이터를 화면마다 손으로 반영하는 코드가 거의 필요 없어진다. 대신 앞에서 본 대로 구독자마다 실행 비용을 치른다.

신호만 담는 쪽은 서버가 싸다. 이벤트를 받은 클라이언트가 필요할 때 쿼리를 보내니, 화면에 없는 구독자는 아무것도 하지 않는다. 대신 이벤트가 몰리면 쿼리도 몰린다. 신호를 받은 1만 명이 동시에 쿼리를 보내는 상황을 막으려면 클라이언트가 짧은 무작위 지연을 두고 다시 받게 한다.

어느 쪽이든 순서와 중복을 생각한다. 이벤트는 서버 여러 대와 pub/sub를 거치며 순서가 뒤바뀌어 올 수 있다. `DELIVERED` 뒤에 늦게 도착한 `SHIPPED`가 화면을 되돌리면 안 된다. 주문에 `version`(또는 `updatedAt`)을 두고, 클라이언트는 가진 것보다 오래된 이벤트를 버린다. 재연결 뒤 같은 이벤트를 두 번 받아도 결과가 같도록 "상태를 이 값으로 바꾼다"는 식의 멱등한 이벤트로 설계한다. "수량을 1 늘린다" 같은 이벤트는 두 번 받으면 틀린다.

## 느린 필드를 나중에 보내는 @defer와 @stream

이번에는 다른 문제다. 주문 상세 화면의 주문 정보는 10ms면 나오는데, 아래쪽 "함께 사면 좋은 상품"은 추천 서비스를 거쳐 80ms가 걸린다. 쿼리 하나로 받으면 화면 전체가 80ms를 기다린다. 쿼리를 둘로 나누면 요청이 둘이 된다. `@defer`는 쿼리 하나로 보내되 응답을 나눠 받게 한다.

```graphql
query OrderPage {
  order(id: "42") {
    id
    status
    ... @defer(label: "recs") { recommendations { name } }
    reviews @stream(initialCount: 1)
  }
}
```

`@defer`는 프래그먼트에 붙어 "이 부분은 나중에 보내도 된다"고 알린다. `@stream`은 목록 필드에 붙어 "처음 `initialCount`개만 먼저 주고 나머지는 하나씩 흘려 달라"고 알린다. 이 둘은 2026년 현재 GraphQL 명세에 들어가지 않은 제안(RFC) 단계다. graphql-js 17은 이를 `experimentalExecuteIncrementally`라는 이름으로 따로 둔다. 실행기 이름에 붙은 experimental이 그 상태를 말해 준다. 17.0.2로 돌린 결과다.

```text
+ 44ms initial {"data":{"order":{"id":"42","status":"SHIPPED","reviews":["좋다"]}},"pending":[{"id":"0","path":["order"],"label":"recs"},{"id":"1","path":["order","reviews"]}],"hasNext":true}
+ 77ms subsequent {"hasNext":true,"incremental":[{"id":"1","items":["빠르다"]}]}
+108ms subsequent {"hasNext":true,"incremental":[{"id":"1","items":["튼튼하다"]}],"completed":[{"id":"1"}]}
+127ms subsequent {"hasNext":false,"incremental":[{"id":"0","data":{"recommendations":[{"name":"펜"},{"name":"공책"}]}}],"completed":[{"id":"0"}]}
```

첫 결과에는 주문 정보와 리뷰 첫 개가 들어 있고, `pending`에 "아직 오지 않은 조각" 두 개가 경로와 함께 적혀 있다. 이어지는 결과의 `incremental`이 조각을 채운다. `items`는 스트림에 원소를 더하고, `data`는 그 경로의 객체에 필드를 합친다. `completed`가 오면 그 조각은 끝났고, `hasNext: false`면 응답 전체가 끝났다. 클라이언트는 첫 결과로 화면을 그리고, 조각이 올 때마다 그 부분을 채운다.

이 결과 형식은 제안이 다듬어지면서 여러 번 바뀌었다. 예전 형식에는 `pending`과 `completed`가 없고 조각마다 `path`가 직접 붙어 있었다. 서버와 클라이언트가 같은 형식을 쓰는지 꼭 확인한다. Apollo Client와 Relay는 `@defer`를 지원하지만 지원하는 형식의 판이 정해져 있다. HTTP 위에서는 이 결과들이 `multipart/mixed` 응답의 파트 하나에 하나씩 실려 온다. 응답이 한 번에 끝나지 않으니 중간 프록시가 응답을 모아서 버퍼링하면 효과가 사라진다.

### 조각을 받아 합치는 일

클라이언트가 하는 일을 직접 짜 보자. 첫 결과와 이어지는 결과 배열을 받아 최종 data를 만들고, 아직 끝나지 않은 조각이 있는지(`done`) 돌려준다. 첫 테스트는 위에서 graphql-js 17이 실제로 낸 결과 그대로다.

### @defer는 언제 쓰나

`@defer`가 줄여 주는 것은 첫 화면까지의 시간이다. 서버가 하는 일의 총량은 그대로이거나 조금 늘어난다. 느린 부분이 화면 아래쪽에 있고, 그걸 기다리느라 위쪽까지 늦게 그려지는 경우에 맞다. 반대로 느린 필드가 화면 맨 위에 있으면 먼저 보낼 것이 없다. 모든 필드가 빠르면 응답을 나누는 비용(조각마다 직렬화, 클라이언트 합치기)만 는다.

서버가 지원하지 않으면 어떻게 될까. 명세 제안은 서버가 `@defer`를 무시하고 한 번에 돌려줘도 되게 했다. 그래서 `@defer`는 "나중에 보내도 된다"는 허락이지 "나중에 보내라"는 명령이 아니다. 클라이언트 코드는 조각이 한 번에 와도 동작해야 한다.

`@defer`는 구독과 목적이 다르다. 구독은 시간이 지나며 바뀌는 값을 계속 받는 것이고, `@defer`는 한 번의 답을 준비된 순서대로 나눠 받는 것이다. `hasNext: false`가 오면 끝난다. React 서버 컴포넌트나 스트리밍 SSR에서 느린 부분을 Suspense로 감싸 나중에 흘려보내는 것과 생각이 같다([스트리밍 SSR과 Suspense](/posts/streaming-ssr-suspense)).

## 라이브 쿼리와 폴링

구독은 "어떤 이벤트가 났다"를 받는다. 화면이 정말 원하는 것은 대개 "이 쿼리의 결과가 지금 무엇인가"다. 주문 상태 이벤트를 받으면 화면은 그 이벤트를 캐시에 반영해야 하고, 이벤트 종류가 늘 때마다 반영 코드도 는다. 라이브 쿼리는 이걸 뒤집는다. 쿼리 자체를 등록해 두면, 서버가 그 결과가 바뀔 때마다 새 결과(또는 바뀐 부분)를 보낸다.

라이브 쿼리는 GraphQL 명세에 없다. `@live` 디렉티브를 쓰는 graphql-live-query 같은 라이브러리나 Hasura처럼 DB 변경을 감지하는 제품이 각자 구현한다. 서버는 "어떤 쿼리 결과가 바뀌었는가"를 알아야 하므로, 쓰기가 일어날 때 어떤 리소스가 무효가 됐는지 알리거나(`Order:42` 무효화) DB를 주기적으로 다시 조회해 비교한다. 구현이 무거워지는 자리가 서버로 옮겨 간 것이다.

가장 단순한 방법은 여전히 폴링이다. Apollo Client는 `useQuery(ORDER, { pollInterval: 10000 })`처럼 간격만 주면 같은 쿼리를 다시 보낸다. 연결을 쥐지 않으니 서버를 그대로 늘릴 수 있고, HTTP 캐시와 기존 모니터링이 그대로 통한다. 대신 바뀐 것이 없어도 요청이 나가고, 반영이 최대 한 간격만큼 늦다. 사용자 1만 명이 10초마다 폴링하면 초당 1,000건이다. 화면이 보이지 않을 때(탭이 백그라운드일 때) 폴링을 멈추면 이 숫자가 크게 준다.

고르는 기준을 정리하면 이렇다. 바뀌는 빈도가 낮고 몇 초 늦어도 되면 폴링으로 시작한다. 바뀐 순간 보여야 하고 이벤트가 분명하면(채팅 메시지, 주문 상태) 구독을 쓴다. 화면이 보는 데이터가 여러 이유로 바뀌고 이벤트를 일일이 다루기 어려우면 라이브 쿼리를 검토하되, 서버가 변경을 감지하는 비용을 함께 본다. 그리고 응답 하나가 느린 부분 때문에 늦다면 그건 실시간 문제가 아니라 `@defer`의 문제다.

## 앱에서 구독을 붙이는 모양

클라이언트에서는 보통 쿼리와 뮤테이션은 HTTP로, 구독만 WebSocket으로 보낸다. 연결을 오래 쥐는 전송은 꼭 필요한 곳에만 쓰기 위해서다. Apollo Client에서는 작업 종류를 보고 링크를 가르는 `split`을 쓴다. 아래 코드는 Apollo Client 3 기준이다. 4에서는 React 훅이 `@apollo/client/react`로 옮겨 가는 등 import 경로가 바뀌었으니 쓰는 판의 문서를 확인한다.

```ts
import { ApolloClient, HttpLink, InMemoryCache, split } from "@apollo/client";
import { GraphQLWsLink } from "@apollo/client/link/subscriptions";
import { getMainDefinition } from "@apollo/client/utilities";
import { createClient } from "graphql-ws";

const http = new HttpLink({ uri: "/graphql" });
const ws = new GraphQLWsLink(createClient({
  url: "wss://api.example.com/graphql",
  connectionParams: async () => ({ token: await getAccessToken() }),
}));

// 구독 작업만 WebSocket으로, 나머지는 HTTP로 보낸다
const link = split(
  ({ query }) => {
    const def = getMainDefinition(query);
    return def.kind === "OperationDefinition" && def.operation === "subscription";
  },
  ws,
  http,
);

export const client = new ApolloClient({ link, cache: new InMemoryCache() });
```

화면에서는 쿼리로 현재 상태를 먼저 그리고, 구독으로 바뀐 것을 받는다. 구독 결과에 `id`가 있으니 캐시의 같은 주문이 바뀌고, 쿼리 쪽 화면이 따라 바뀐다.

```tsx
"use client";
import { gql, useQuery, useSubscription } from "@apollo/client";

const ORDER = gql`query OrderStatus($id: ID!) { order(id: $id) { id status } }`;
const CHANGED = gql`subscription OrderStatusChanged($id: ID!) { orderStatusChanged(id: $id) { id status } }`;

export function OrderStatus({ id }: { id: string }) {
  const { data } = useQuery(ORDER, { variables: { id } });
  // 결과는 캐시의 Order:{id}에 합쳐져 위 useQuery가 다시 그린다
  useSubscription(CHANGED, { variables: { id } });
  return <p>{data?.order?.status ?? "불러오는 중"}</p>;
}
```

컴포넌트가 화면에서 사라지면 `useSubscription`이 `complete`를 보내 구독을 정리한다. 직접 graphql-ws 클라이언트의 `subscribe`를 쓸 때는 돌려받은 해지 함수를 `useEffect`의 정리 함수에서 꼭 부른다. 빠뜨리면 페이지를 오갈 때마다 같은 구독이 하나씩 늘어, 서버에는 아무도 보지 않는 구독이 쌓이고 화면에는 같은 이벤트가 여러 번 반영된다.

## 운영에서 실시간이 조용히 멈출 때

"가끔 화면이 안 바뀐다"는 신고는 서버가 여러 대인지부터 본다. 개발 환경에서는 늘 되고, 운영에서 확률적으로 안 된다면 앞에서 본 프로세스 안 버스가 원인일 가능성이 높다. 이벤트를 낸 서버와 구독 연결을 쥔 서버의 로그를 함께 본다.

"배포 직후 한동안 안 바뀐다"는 재연결과 놓친 이벤트다. 서버가 내려가면 연결이 끊기고, 다시 붙는 사이의 pub/sub 메시지는 사라진다. 클라이언트가 재연결 후 현재 상태를 다시 받는지 본다. graphql-ws 클라이언트의 `on("connected")` 이벤트에서 관련 쿼리를 다시 부르면 된다.

연결 수와 구독 수를 지표로 남긴다. 서버마다 열린 WebSocket 수, 활성 구독 수, 초당 보낸 `next` 수, 4400번대 닫기 코드의 비율이다. 구독 수가 연결 수보다 훨씬 빨리 늘면 화면을 떠나도 `complete`를 보내지 않는 클라이언트 버그를 의심한다. 서버의 이터레이터와 버스 리스너가 쌓여 메모리가 샌다.

`@defer`가 효과가 없다면 응답이 정말 나눠져 오는지 본다. 브라우저 개발자 도구에서 응답이 한꺼번에 도착하면 중간의 프록시나 CDN이 `multipart/mixed`를 버퍼링하고 있다. 스트리밍이 끊기는 지점을 좁히는 순서는 [HTTP 스트리밍](/posts/http-streaming-sse)에 있다.

## 계속 받을 것인가, 나눠 받을 것인가

GraphQL의 구독은 서버가 낸 이벤트를 클라이언트가 고른 모양의 응답으로 바꿔 연결 위로 계속 보내는 방식이다. 전송은 명세 밖이라 graphql-ws(WebSocket)나 graphql-sse를 쓰고, 인증은 연결을 열 때 한 번 보니 만료와 이벤트별 권한을 따로 챙긴다. 서버가 여러 대면 이벤트를 Redis 같은 공용 채널로 나눠야 하고, 그 채널은 메시지를 저장하지 않으니 재연결 때 상태를 다시 받는다. `@defer`·`@stream`은 실시간이 아니라 한 번의 응답을 준비된 순서대로 나눠 받는 아직 제안 단계의 기능이다. 라이브 쿼리는 결과 자체를 구독하는 라이브러리 수준의 방식이고, 많은 경우 폴링이 가장 싼 출발점이다.

## 면접에서 나올 만한 질문

### GraphQL 구독은 어떻게 동작하나요?

구독 작업의 최상위 필드 하나가 이벤트 원천(보통 비동기 이터레이터)을 만들고, 이벤트가 올 때마다 실행기가 그 이벤트를 루트 값으로 선택 집합을 실행해 결과 하나를 내보낸다. 그래서 클라이언트는 쿼리처럼 필요한 필드만 고른다. 이벤트를 내는 것은 뮤테이션 같은 서버 코드라서, 데이터가 바뀌어도 이벤트를 내지 않으면 구독자는 모른다. 전송 방식은 명세에 없고 graphql-ws나 graphql-sse를 쓴다.

### graphql-ws 프로토콜의 흐름을 설명해 주세요.

WebSocket을 `graphql-transport-ws` 하위 프로토콜로 연 뒤 클라이언트가 `connection_init`에 토큰을 실어 보내고 서버가 `connection_ack`로 받아들인다. 그다음 `subscribe` 메시지로 id를 붙여 구독을 시작하고, 서버는 이벤트마다 같은 id로 `next`를 보낸다. 끝낼 때는 `complete`를 보내고, `ping`/`pong`으로 연결을 확인한다. 인증 실패는 4403, init 없이 구독하면 4401, init이 늦으면 4408로 닫힌다.

### 구독 서버를 여러 대로 늘리면 무엇이 문제인가요?

구독 연결을 쥔 서버와 이벤트를 낸 서버가 다를 수 있어서, 프로세스 안의 이벤트 버스를 쓰면 다른 서버의 구독자에게 이벤트가 가지 않는다. 데모에서 B로 간 뮤테이션은 A의 구독자에게 도착하지 않았고 에러도 없었다. Redis pub/sub 같은 공용 채널에 이벤트를 발행하고 모든 서버가 그 채널을 들으면 해결된다. 다만 Redis pub/sub는 메시지를 저장하지 않으니 재연결 때 현재 상태를 다시 받아야 한다.

### WebSocket 구독에서 인증은 어떻게 하나요?

브라우저 WebSocket은 헤더를 자유롭게 붙이지 못하므로 보통 `connection_init`의 payload(connectionParams)에 토큰을 싣고 서버의 onConnect에서 검사한다. 연결 때 한 번만 보니, 서버가 토큰 만료 시각을 기억했다가 지나면 연결을 닫고, 클라이언트는 connectionParams를 함수로 넘겨 재연결 때마다 새 토큰을 싣는다. 구독 대상 권한은 subscribe 함수에서, 이벤트별 권한은 이벤트마다 확인한다.

### @defer와 @stream은 무엇이고, 구독과 어떻게 다른가요?

`@defer`는 프래그먼트를 나중에 보내도 된다고 표시하고, `@stream`은 목록을 처음 몇 개만 먼저 주고 나머지를 흘려보내게 한다. 응답은 첫 결과와 이어지는 결과들로 나뉘고, `pending`, `incremental`, `completed`, `hasNext`로 조각을 맞춘다. 구독은 시간이 지나며 바뀌는 값을 계속 받는 것이고, `@defer`는 한 번의 응답을 준비된 순서로 나눠 받는 것이라 `hasNext: false`면 끝난다. 2026년 현재 명세 제안 단계라 graphql-js 17도 experimental 실행 함수로 따로 두고, 결과 형식이 바뀌어 왔으니 서버와 클라이언트의 판을 맞춰야 한다.

### 폴링, 구독, 라이브 쿼리 중 무엇을 고르나요?

몇 초 늦어도 되고 바뀌는 빈도가 낮으면 폴링으로 시작한다. 연결을 쥐지 않아 확장과 운영이 쉽고 HTTP 캐시도 통한다. 바뀐 순간 보여야 하고 이벤트가 분명하면 구독을 쓰되, 연결 수, 공용 이벤트 채널, 재연결 처리를 떠안는다. 결과가 여러 이유로 바뀌어 이벤트를 일일이 다루기 어려우면 라이브 쿼리를 검토하는데, 명세 밖이라 라이브러리마다 다르고 서버가 변경을 감지하는 비용이 크다.

### 구독이 가끔 화면에 반영되지 않는다면 무엇부터 보나요?

서버가 여러 대인데 이벤트 버스가 프로세스 안에 있는지 먼저 본다. 그다음 배포나 네트워크 끊김 뒤 재연결하면서 pub/sub 메시지를 놓쳤는지, 클라이언트가 재연결 후 상태를 다시 받는지 확인한다. 연결 수, 활성 구독 수, 4400번대 닫기 코드 비율을 지표로 남기고, 구독 수가 연결 수보다 빨리 늘면 complete를 보내지 않는 클라이언트 버그를 의심한다.
