사무실 세 곳을 라우터 세 대로 묶은 작은 사내망이 있었다. 처음 만든 사람은 경로를 손으로 넣었다. 본사 라우터에는 "지사 대역은 지사로 바로 가는 선으로"라고 적었고, 반대쪽도 똑같이 적었다. 예비로 다른 지점을 거쳐 가는 선도 깔아 두었다. 그러다 본사와 지사를 잇는 선 하나가 끊겼다. 예비 선은 멀쩡히 살아 있는데 아무도 그쪽으로 돌아가지 않았다. 라우팅 테이블에는 여전히 끊긴 선 너머의 주소가 다음 칸으로 적혀 있었기 때문이다.

정적 경로는 사람이 적은 것이라 사람이 고치기 전까지는 바뀌지 않는다. 이 문제를 라우터끼리 대화해서 스스로 풀게 하는 것이 동적 라우팅 프로토콜이다. 이 글은 거리만 주고받는 RIP, 지도를 나눠 갖는 OSPF, 예비 경로를 미리 계산해 두는 EIGRP가 길을 배우는 방식을 비교하고, 여러 프로토콜이 같은 목적지를 두고 다툴 때 누가 이기는지, 링크가 끊긴 뒤 다시 길을 찾기까지 시간이 어디에 쓰이는지를 실습으로 잰다.

라우팅 테이블을 읽는 법과 최장 접두사 일치는 [라우팅과 ICMP 글](/posts/layer-ip-routing-icmp)에서, 라우터가 패킷을 넘기는 방식은 [라우터와 스위치 글](/posts/router-vs-switch)에서 다뤘다. 다익스트라와 벨만-포드 알고리즘 자체는 [최단 경로 알고리즘 글](/posts/shortest-path-algorithms)에 있다. 여기서는 그 알고리즘을 라우터 여러 대가 나눠 돌릴 때 생기는 일에 집중한다. 실습은 Ubuntu 24.04에서 네트워크 네임스페이스로 라우터 세 대를 만들고 FRR 8.4.4(우분투 기본 패키지)를 올려 했다. 출력은 모두 이 실습 망에서 받은 것이다.

## 손으로 적은 길은 스스로 바뀌지 않는다

정적 경로가 나쁜 것은 아니다. 길이 하나뿐인 곳에서는 오히려 정적 경로가 낫다. 지점 라우터 뒤에 망이 하나 있고 밖으로 나가는 선도 하나라면, "모르는 곳은 전부 본사로" 하는 기본 경로 한 줄이면 끝난다. 라우터끼리 대화할 필요가 없으니 CPU도 안 쓰고, 이웃이 엉뚱한 경로를 알려 줄 위험도 없다. 이렇게 출구가 하나뿐인 망을 스텁(stub) 망이라고 부른다.

정적 경로가 버거워지는 신호는 셋이다. 갈 수 있는 길이 둘 이상이고, 그중 하나가 끊기면 다른 길로 돌아가야 하고, 망이 자주 늘어난다. 라우터가 열 대만 되어도 새 대역 하나를 추가할 때마다 열 대에 경로를 넣어야 하고, 한 대를 빠뜨리면 그 대역은 한쪽 방향으로만 통한다.

정적 경로로도 예비 길을 만들 수는 있다. 같은 목적지에 경로를 두 개 넣되, 예비 쪽 관리 거리(뒤에서 다룬다)를 크게 주면 평소에는 숨어 있다가 주 경로가 사라질 때 나타난다. 이걸 플로팅 정적 경로라고 한다. 다만 주 경로가 "사라지는" 조건이 인터페이스가 내려가는 것뿐이다. 선은 살아 있는데 건너편 장비가 멈춘 경우, 중간에 스위치가 있어 내 쪽 포트는 계속 올라와 있는 경우에는 정적 경로가 끝까지 죽은 곳을 가리킨다. 처음 장면이 정확히 이 경우였다.

```bash
# 플로팅 정적 경로: 주 경로는 거리 1(기본), 예비는 거리 200
sudo ip route add 192.168.3.0/24 via 10.0.13.2 metric 10          # 리눅스는 metric으로 순서를 정한다
sudo ip route add 192.168.3.0/24 via 10.0.12.2 metric 200
# FRR(vtysh)에서는 끝에 관리 거리를 붙인다
# ip route 192.168.3.0/24 10.0.12.2 200
```

## 이웃에게 거리표만 건네는 RIP

동적 라우팅의 가장 오래된 모양은 거리 벡터(distance vector)다. 라우터는 자기가 아는 목적지와 그곳까지의 거리를 이웃에게 통째로 보낸다. 이웃은 받은 거리에 자기와 보낸 라우터 사이 거리를 더하고, 지금 아는 것보다 짧으면 표를 고친다. 각 라우터가 아는 것은 "어느 이웃에게 넘기면 몇 칸 걸린다"뿐이고, 망 전체가 어떻게 생겼는지는 모른다.

RIP(Routing Information Protocol)는 이 방식을 가장 단순하게 구현했다. 거리는 홉 수, 즉 라우터를 몇 개 건너는지다. 30초마다 표 전체를 이웃에게 보내고, 180초 동안 소식이 없는 경로는 쓸 수 없다고 표시한다. 홉 수 16은 "갈 수 없음"이라는 뜻이라 RIP 망은 15홉을 넘을 수 없다. RIPv2는 서브넷 마스크를 함께 실어 보내고(RIPv1은 클래스 단위로만 다뤘다), 멀티캐스트 224.0.0.9로 보낸다.

실습 망에서 RIP를 켜면 표가 이렇게 보인다. 라우터 r1, r2, r3이 삼각형으로 이어져 있고 r3 뒤에 192.168.3.0/24가 있다.

```bash
# r1에서 RIP가 배운 경로 보기 (FRR)
sudo vtysh -c "show ip rip"
```

```text
     Network            Next Hop         Metric From            Tag Time
C(i) 10.0.12.0/30       0.0.0.0               1 self              0
C(i) 10.0.13.0/30       0.0.0.0               1 self              0
R(n) 10.0.23.0/30       10.0.12.2             2 10.0.12.2         0 02:59
C(i) 192.168.1.0/24     0.0.0.0               1 self              0
R(n) 192.168.3.0/24     10.0.13.2             2 10.0.13.2         0 02:59
```

`Metric` 열이 홉 수다. 직접 붙은 망이 1이고, r3을 하나 건너는 192.168.3.0/24는 2다. `Time` 열은 그 경로가 만료되기까지 남은 시간인데, 이웃이 30초마다 다시 알려 줄 때마다 3분으로 돌아간다. 이웃이 조용히 죽으면 이 숫자가 0이 될 때까지 기다려야 한다는 뜻이기도 하다.

홉 수만 보는 것도 한계다. 1Gbps 선 세 개를 건너는 길보다 10Mbps 선 하나를 건너는 길을 더 좋다고 판단한다. 아래 실습에서 OSPF와 나란히 놓으면 이 차이가 그대로 드러난다.

## 나쁜 소식은 천천히 퍼진다

RIP는 이걸 몇 가지 규칙으로 막는다. 분할 수평(split horizon)은 "어떤 이웃에게서 배운 경로는 그 이웃에게 다시 광고하지 않는다"는 규칙이다. A는 X를 B에게서 배웠으니 B에게 X 이야기를 하지 않는다. 독 역전(poison reverse)은 한 발 더 나가 그 이웃에게 "나를 거쳐서는 X에 못 간다(16)"고 적극적으로 알린다. 경로를 잃은 라우터는 곧바로 16을 광고하고(triggered update), 일정 시간 동안 더 나쁜 소식을 무시하는 hold-down 타이머도 둔다.

이 규칙들은 두 라우터 사이의 고리는 막지만, 셋 이상이 고리를 이루는 망에서는 여전히 잠깐씩 엉뚱한 경로가 생길 수 있다. 각 라우터가 이웃의 말만 믿고 망의 모양을 모르기 때문이다. 홉 수 15 제한도 사실 이 문제의 피해를 줄이려고 무한대를 작게 잡은 결과다. 그래서 요즘 RIP는 작은 실습 망이나 오래된 장비 사이에서나 보고, 회사 망의 IGP(한 조직 안에서 쓰는 라우팅 프로토콜)로는 거의 쓰지 않는다.

## 모두가 같은 지도를 갖는 OSPF

링크 상태(link state) 방식은 생각을 뒤집는다. 거리를 전하지 말고 사실을 전한다. 라우터마다 "나는 누구와 어떤 비용의 선으로 이어져 있다"는 정보만 만들어서 망 전체에 뿌린다. 이 정보 한 장을 LSA(Link State Advertisement)라고 하고, 모든 라우터가 모은 LSA 묶음을 LSDB(링크 상태 데이터베이스)라고 한다. 같은 영역 안의 라우터는 모두 같은 LSDB를 갖게 되고, 각자 자기를 뿌리로 놓고 다익스트라(SPF, Shortest Path First)를 돌려 최단 경로 나무를 만든다.

OSPF(Open Shortest Path First)가 대표다. IETF 표준(OSPFv2는 RFC 2328, IPv6용 OSPFv3는 RFC 5340)이라 어느 회사 장비끼리도 통한다. 프로토콜 번호 89로 IP 위에 바로 실리고, 224.0.0.5(모든 OSPF 라우터)로 Hello를 보낸다.

FRR로 세 라우터에 OSPF를 켜고 r1에서 이웃과 LSDB를 보면 이렇게 나온다. 링크마다 `ip ospf network point-to-point`를 줘서 대표 라우터(DR) 선출을 생략했다. 이더넷처럼 여럿이 붙는 망에서는 모두가 서로 이웃을 맺으면 관계가 너무 많아지니 DR 하나를 뽑아 그와만 지도를 맞추는데, 라우터 두 대만 잇는 선에서는 필요 없다.

```bash
# r1의 OSPF 이웃, LSDB 요약 보기
sudo vtysh -c "show ip ospf neighbor"
sudo vtysh -c "show ip ospf database"
```

`State`가 `Full`이어야 지도가 맞춰진 것이다. 뒤의 `-`는 DR/BDR 역할이 없다는 뜻이다(point-to-point라서). `Dead Time`은 이웃의 Hello가 이 시간 안에 다시 오지 않으면 이웃을 지운다는 카운트다운이다. LSDB에는 라우터마다 Router LSA가 한 장씩, 모두 세 장 있고 세 라우터 모두에서 같은 내용이 나온다. `Seq#`는 새 LSA가 나올 때마다 오르는 번호라, 두 라우터의 같은 LSA 번호가 계속 다르면 지도가 안 맞는다는 신호다.

라우팅 테이블에는 두 갈래가 동시에 들어간 줄도 보인다.

```text
O>* 10.0.23.0/30 [110/20] via 10.0.12.2, to-r2, weight 1, 00:00:00
  *                       via 10.0.13.2, to-r3, weight 1, 00:00:00
O>* 192.168.3.0/24 [110/20] via 10.0.13.2, to-r3, weight 1, 00:00:00
```

r2와 r3 사이 선(10.0.23.0/30)은 r1에서 보면 r2를 거치든 r3을 거치든 비용이 20으로 같다. OSPF는 비용이 같은 길을 모두 테이블에 넣어 트래픽을 나눠 보낸다. 이걸 ECMP(Equal-Cost Multi-Path)라고 하고, 데이터 센터 설계가 이걸 전제로 한다([망 구조 설계 글](/posts/network-design-three-tier-spine-leaf)에서 다시 나온다). 대괄호 안 `[110/20]`의 앞 숫자는 관리 거리, 뒤 숫자는 비용이다.

## 비용은 대역폭에서 나온다

OSPF의 비용(cost)은 링크마다 붙는 숫자고, 경로의 비용은 지나는 링크의 비용을 더한 값이다. 사람이 직접 줄 수도 있고, 주지 않으면 장비가 "기준 대역폭 ÷ 링크 대역폭"으로 계산한다. 기준 대역폭의 기본값은 100Mbps라서 100Mbps 링크는 1, 10Mbps 링크는 10이 된다.

함정은 100Mbps보다 빠른 링크다. 1Gbps도 10Gbps도 100Gbps도 계산하면 1보다 작아서 모두 1로 올림된다. 그러면 OSPF는 1Gbps 길과 100Gbps 길을 구별하지 못한다. 그래서 실무에서는 기준 대역폭을 망의 가장 빠른 링크 이상으로 올려 둔다. 이 값은 모든 라우터에서 같아야 한다. 한 대만 바꾸면 그 라우터만 다른 잣대로 비용을 매겨 경로가 비대칭이 된다.

```text
router ospf
 auto-cost reference-bandwidth 100000   ! 단위 Mbps, 100Gbps를 1로
```

이 실습에서는 FRR이 veth 링크마다 비용 10을 주었다. 이제 r1과 r3 사이 링크를 느린 선이라고 치고 비용을 100으로 올려 본다. 같은 r1에서 RIP도 함께 돌리고 있으니, 두 프로토콜이 같은 목적지에 어떤 답을 내는지 나란히 볼 수 있다.

```bash
# r1-r3 링크 비용을 100으로 (FRR)
sudo vtysh -c "conf t" -c "interface to-r3" -c "ip ospf cost 100"
sudo vtysh -c "show ip route" | grep 192.168.3
```

```text
O>* 192.168.3.0/24 [110/30] via 10.0.12.2, to-r2, weight 1, 00:00:00
R   192.168.3.0/24 [120/2] via 10.0.13.2, to-r3, weight 1, 00:00:11
```

OSPF는 비용 100짜리 직통 대신 10+10+10=30인 r2 경유를 골랐다. RIP는 여전히 홉 수 2인 r3 직통을 고집한다. 대역폭을 모르는 거리 벡터의 한계가 이 두 줄에 다 들어 있다. 그리고 실제로 쓰이는 것은 `>*` 표시가 붙은 OSPF 줄이다. 왜 OSPF가 이겼는지는 아래 관리 거리에서 본다.

## 영역을 나누는 이유

라우터가 수십 대를 넘어가면 모두가 같은 지도를 갖는 방식이 부담이 된다. 어디선가 링크 하나가 오르내릴 때마다 LSA가 망 전체로 퍼지고, 모든 라우터가 SPF를 다시 돌린다. 링크가 자주 흔들리는 지점이 하나만 있어도 망 전체 라우터의 CPU가 같이 흔들린다. LSDB도 라우터 수와 링크 수에 비례해 커진다.

OSPF는 망을 영역(area)으로 나눠서 이 문제를 푼다. 모든 영역은 백본인 영역 0에 붙어야 하고, 영역 사이의 경로는 영역 0을 거친다. 두 영역에 걸친 라우터를 ABR(Area Border Router)이라고 하는데, ABR은 한쪽 영역의 상세 지도를 다른 쪽에 넘기지 않는다. 대신 "이 영역 안에는 이런 대역들이 있고 내게서 비용이 얼마다"라는 요약(Summary LSA, type 3)만 넘긴다. 영역 바깥의 라우터 입장에서 이건 다시 거리 벡터와 비슷한 정보다. 지도는 영역 안에서만 정확하고, 영역 밖은 "저쪽 문으로 가면 얼마"만 안다.

그래서 영역 1에서 링크가 흔들려도 SPF를 전부 다시 돌리는 건 영역 1 안의 라우터뿐이다. 영역 0과 다른 영역은 요약 정보의 비용이 바뀌었다는 소식만 받는다. 거기에 ABR이 영역 1의 대역들을 큰 블록 하나로 묶어 광고하면(아래 "경로 요약"), 영역 1 안의 작은 대역이 생기고 사라지는 것은 바깥에서 아예 보이지 않는다.

LSA 종류는 면접에서 자주 나오지만 외울 것은 몇 개면 된다. Router LSA(type 1)는 라우터 자신의 링크, Network LSA(type 2)는 DR이 만드는 다중 접속 망 정보, 둘 다 영역 안에서만 퍼진다. Summary LSA(type 3)는 ABR이 다른 영역에 넘기는 요약, External LSA(type 5)는 OSPF 바깥(정적 경로, BGP 등)에서 들여온 경로다. 바깥으로 나가는 출구가 하나뿐인 영역은 stub 영역으로 지정해 type 5를 막고 기본 경로 하나로 대신할 수 있다.

영역을 몇 개로 나눌지는 정답이 없다. 라우터 수십 대 정도면 영역 0 하나로도 충분하다. 영역을 나누면 요약 덕분에 안정성이 오르지만, 영역 사이 경로가 최단이 아닐 수 있고(요약이 세부를 가리니까) 설계와 장애 분석이 복잡해진다. 지점이나 건물처럼 물리적으로 자연스럽게 갈리는 경계, 그리고 요약하기 좋은 주소 블록 경계에 맞춰 자른다.

## EIGRP는 예비 경로를 미리 들고 있다

EIGRP(Enhanced Interior Gateway Routing Protocol)는 시스코가 만든 프로토콜이다. 2016년에 RFC 7868로 기본 동작이 공개되긴 했지만 정보성 문서이고, 실제로는 거의 시스코 장비끼리만 쓴다. 이웃에게 거리를 알려 주는 점은 거리 벡터와 같지만, 표 전체를 주기적으로 보내지 않고 바뀐 것만 보내며, 루프를 수학적으로 막는 DUAL(Diffusing Update Algorithm)을 쓴다. 그래서 "고급 거리 벡터"라고 부른다.

DUAL의 아이디어는 이렇다. 각 이웃은 목적지까지 자기가 얼마 걸리는지(보고된 거리, RD)를 알려 준다. 나는 그 이웃을 거쳐 가는 전체 거리를 계산하고, 가장 짧은 것을 쓴다. 이게 successor이고 그 거리가 FD(feasible distance)다. 그리고 다른 이웃 중 "자기가 보고한 거리가 내 FD보다 작은" 이웃은 feasible successor로 따로 적어 둔다.

```text
feasibility condition:  RD(이웃) < FD(나)
```

이 조건을 만족하는 이웃은 나보다 목적지에 확실히 더 가깝다. 그러니 그 이웃의 경로가 나를 거쳐 돌아올 수 없다. 앞의 count to infinity가 생긴 이유는 A가 "2홉"이라고 했을 때 B가 그 길이 자기를 거친다는 걸 몰랐기 때문이다. DUAL에서 B의 FD는 1이었고 A의 RD는 2라서, A는 처음부터 feasible successor가 될 수 없다. B는 A의 말을 믿지 않는다.

successor 쪽 링크가 끊기면, feasible successor가 있는 경우 계산 없이 곧바로 그쪽으로 바꾼다. 없으면 이웃들에게 질의(Query)를 보내 새 길을 묻고 답(Reply)이 모두 올 때까지 그 목적지를 "계산 중(active)"으로 둔다. 큰 망에서 이 질의가 끝없이 퍼지다 답을 못 받으면 SIA(Stuck In Active)라는 이름난 장애가 된다. 그래서 EIGRP 망도 요약과 stub 설정으로 질의가 퍼지는 범위를 잘라 둔다.

메트릭은 기본으로 경로상 가장 느린 링크의 대역폭과 지연의 합으로 계산한다(K값으로 부하·신뢰도도 넣을 수 있지만 기본은 끈다). OSPF와 마찬가지로 대역폭을 반영하고, 비용이 다른 경로 사이에도 트래픽을 나누는 unequal-cost 분산(variance)을 지원한다는 점이 특징이다. FRR에도 eigrpd가 있지만 기능이 제한적이라, 실무에서 EIGRP를 만나는 건 시스코 장비만 쓰는 오래된 사내망이 대부분이다.

## 같은 목적지를 여러 프로토콜이 말할 때

앞의 실습에서 r1은 192.168.3.0/24를 OSPF와 RIP에게서 동시에 들었다. 둘의 메트릭은 비교할 수 없다. 비용 30과 홉 수 2 중 무엇이 더 좋은지는 의미가 없는 질문이다. 그래서 라우터는 먼저 "어느 출처를 더 믿을지"를 정하는 숫자를 본다. 이게 관리 거리(administrative distance)다. 작을수록 믿는다.

```bash
# 한 목적지에 대해 출처별 후보를 모두 보기 (FRR)
sudo vtysh -c "show ip route 192.168.3.0/24"
```

```text
Routing entry for 192.168.3.0/24
  Known via "ospf", distance 110, metric 20, best
  Last update 00:00:01 ago
  * 10.0.13.2, via to-r3, weight 1

Routing entry for 192.168.3.0/24
  Known via "rip", distance 120, metric 2
  Last update 00:00:05 ago
    10.0.13.2, via to-r3, weight 1
```

OSPF는 110, RIP는 120이라 OSPF가 `best`가 된다. 시스코와 FRR이 쓰는 기본값은 직접 연결 0, 정적 1, eBGP 20, EIGRP 내부 90, OSPF 110, IS-IS 115, RIP 120, iBGP 200이다. 다른 회사 장비는 숫자가 다를 수 있다(주니퍼는 OSPF 내부를 10으로 둔다). 같은 망에서 회사가 다른 장비를 섞을 때 이 차이로 경로가 엇갈린다.

순서를 정리하면 이렇다. 라우터는 먼저 가장 길게 맞는 접두사를 고르고([라우팅과 ICMP 글](/posts/layer-ip-routing-icmp)), 같은 접두사 후보가 여럿이면 관리 거리가 작은 출처를 고르고, 출처가 같으면 그 프로토콜의 메트릭을 비교한다. 관리 거리는 같은 접두사끼리만 비교한다는 점을 놓치면 안 된다. RIP가 192.168.3.0/25를 광고하면, OSPF의 /24보다 더 길게 맞으니 그 절반은 RIP 경로로 간다.

먼저 인터페이스를 내리는 경우다. 케이블이 뽑혀서 포트 불이 꺼지는 상황과 같다.

```bash
# h1에서 0.1초 간격 ping을 돌려 둔 채, r1과 r3 양쪽 인터페이스를 내린다
sudo ip netns exec h1 ping -i 0.1 -c 60 -O 192.168.3.10 > ping1.txt &
sudo ip -n r1 link set to-r3 down
sudo ip -n r3 link set to-r1 down
```

```text
--- 192.168.3.10 ping statistics ---
60 packets transmitted, 60 received, 0% packet loss, time 6179ms
```

하나도 잃지 않았다. 인터페이스가 내려가면 커널이 그 인터페이스로 가는 경로를 바로 지우고, OSPF도 그 이벤트를 받아 즉시 LSA를 새로 만든다. 감지에 걸리는 시간이 거의 0이다. 경로를 확인하면 이제 r2를 거친다.

```text
Routing entry for 192.168.3.0/24
  Known via "ospf", distance 110, metric 30, best
  Last update 00:00:05 ago
  * 10.0.12.2, via to-r2, weight 1
```

현실의 장애는 이렇게 친절하지 않다. 중간에 스위치나 광 변환기가 있으면 건너편이 죽어도 내 포트는 계속 올라와 있다. 이번에는 인터페이스는 살려 두고 iptables로 그 링크의 패킷을 모두 버려서 "선은 살아 있는데 아무것도 안 지나가는" 상태를 만들었다.

```bash
# 링크는 up인 채로 그 인터페이스의 모든 패킷을 버린다 (r1, r3 양쪽)
sudo ip netns exec r1 iptables -A INPUT -i to-r3 -j DROP
sudo ip netns exec r1 iptables -A OUTPUT -o to-r3 -j DROP
sudo ip netns exec r1 iptables -A FORWARD -i to-r3 -j DROP
sudo ip netns exec r1 iptables -A FORWARD -o to-r3 -j DROP
# r3 쪽도 to-r1에 같은 규칙

# 끝난 뒤: 응답 없던 패킷 수, 첫 무응답과 마지막 무응답의 타임스탬프(-D로 찍힌 값)
tail -2 ping2.txt
grep -n "no answer" ping2.txt | sed -n '1p;$p'
```

```text
260 packets transmitted, 70 received, 73.0769% packet loss, time 52990ms
12:[1792782290.521511] no answer yet for icmp_seq=11
201:[1792782329.197526] no answer yet for icmp_seq=200
```

0.2초 간격 ping에서 190개가 빠졌고, 첫 무응답과 마지막 무응답의 타임스탬프 차이가 약 38.7초다. 기본 Hello 10초, Dead 40초라서, 마지막 Hello를 받은 뒤 40초가 지나야 이웃을 지운다. 끊긴 시점이 마지막 Hello 직후가 아니었으니 40초보다 조금 짧게 나왔다. 이 40초 동안 r1은 죽은 길로 열심히 패킷을 보냈다.

Hello를 1초, Dead를 4초로 줄이면 어떨까. 이 값은 양쪽이 같아야 이웃이 맺어진다.

```text
interface to-r3
 ip ospf hello-interval 1
 ip ospf dead-interval 4
```

같은 실험에서 0.1초 간격 ping이 36개 빠졌다. 약 3.7초다. 그런데 Hello를 더 줄이는 데는 한계가 있다. Hello는 라우팅 데몬이 만들고 받으니, 라우터 CPU가 바쁜 순간 몇 초 늦으면 멀쩡한 이웃을 죽었다고 판단해 오히려 망이 흔들린다.

그래서 링크가 살아 있는지 보는 일은 BFD(Bidirectional Forwarding Detection)에게 따로 맡긴다. BFD는 아주 작은 패킷을 수백 밀리초 간격으로 주고받는 것만 하는 프로토콜이고(RFC 5880), 장비에 따라 하드웨어에서 처리한다. BFD가 끊김을 알리면 OSPF는 Dead 간격을 기다리지 않고 바로 이웃을 내린다. FRR에서 300ms 간격, 3번 놓치면 끊김으로 설정했다.

```text
interface to-r3
 ip ospf bfd
 ip ospf bfd profile fast
bfd
 profile fast
  receive-interval 300
  transmit-interval 300
  detect-multiplier 3
```

```text
20:[1792782390.813488] no answer yet for icmp_seq=19
32:[1792782391.521531] no answer yet for icmp_seq=31
```

0.05초 간격 ping이 13개 빠졌다. 약 0.7초다. 300ms × 3 = 0.9초 안에 감지하고, 나머지는 LSA 교환과 SPF, FIB 설치에 쓰인다. 같은 장애가 38.7초에서 0.7초로 줄었다.

## 수렴 시간은 대부분 감지에 쓰인다

수렴(convergence)은 장애 뒤 모든 라우터가 같은 새 지도로 경로를 다시 만들기까지의 과정이다. 시간을 쪼개 보면 감지, 전파, 계산, 설치 네 단계다. 위 실습이 보여 준 것처럼 작은 망에서 시간을 잡아먹는 건 압도적으로 감지다. 전파와 계산은 라우터 몇 대짜리 망에서는 밀리초 단위다.

전파와 계산에도 일부러 넣은 지연이 있다. 링크가 1초에 몇 번씩 오르내리면 그때마다 SPF를 돌릴 수 없으니, 장비는 첫 변화 뒤 잠깐 기다렸다가 계산하고, 변화가 계속되면 대기 시간을 늘린다(SPF throttle, FRR에서는 `timers throttle spf`). 큰 망에서 이 값을 너무 공격적으로 줄이면 흔들리는 링크 하나 때문에 모든 라우터가 쉬지 않고 계산한다.

설치 단계는 장비가 클수록 눈에 띈다. 경로 수십만 개를 하드웨어 테이블에 다시 쓰는 데 시간이 걸린다. 그래서 상용 장비에는 예비 경로를 미리 하드웨어에 넣어 두었다가 바로 바꾸는 기능(LFA, Loop-Free Alternate, FRR이라는 같은 약자를 쓰는 Fast Reroute)이 있다. EIGRP의 feasible successor와 같은 생각이다.

RIP의 수렴은 이 모든 것과 차원이 다르다. 이웃이 조용히 죽으면 경로 만료까지 180초, 그 뒤에도 count to infinity를 막는 hold-down이 붙는다. 처음 장면 같은 사내망에 RIP를 넣었다면 몇 분짜리 장애가 됐을 것이다.

## 경로 요약으로 흔들림을 가둔다

경로 요약(summarization)은 여러 작은 대역을 큰 블록 하나로 묶어 광고하는 것이다. 지점 하나가 10.20.0.0/24부터 10.20.15.0/24까지 열여섯 개 대역을 쓴다면, 지점 바깥에는 10.20.0.0/20 한 줄만 알려 주면 된다. 라우팅 테이블이 작아지는 것도 좋지만 더 중요한 효과는 안정성이다. 지점 안에서 /24 하나가 생기고 사라져도 /20 요약은 그대로라, 바깥 라우터는 아무것도 다시 계산하지 않는다.

OSPF에서 요약은 영역 경계(ABR)에서만 할 수 있다. 같은 영역 안의 라우터는 모두 같은 지도를 가져야 하므로 중간에서 정보를 줄일 수 없기 때문이다. 외부 경로는 그 경로를 들여오는 라우터(ASBR)에서 요약한다.

```text
router ospf
 area 1 range 10.20.0.0/20        ! 영역 1의 대역들을 /20 하나로 내보낸다
```

요약에는 대가가 있다. 바깥에서는 /20 전체가 살아 있는 것처럼 보이니, 그 안의 /24 하나가 실제로 죽어도 패킷은 계속 그 지점으로 들어온다. 그래서 요약을 만드는 라우터는 요약 블록에 대한 null 경로(버리는 경로)를 함께 둬서, 모르는 하위 대역 패킷이 기본 경로를 타고 다시 밖으로 나가 고리를 만들지 않게 한다. FRR과 시스코는 요약을 걸면 이걸 자동으로 넣는다. 또 이중으로 연결된 지점에서 두 ABR이 똑같이 요약하면, 한쪽 ABR이 안쪽과 끊겨도 요약을 계속 광고해 트래픽 일부가 블랙홀로 빠질 수 있다. 요약은 주소를 처음부터 묶기 좋게 나눠 둬야 쓸 수 있다는 점에서 설계 문제이기도 하다.

## IGP와 BGP는 맡은 일이 다르다

지금까지 본 RIP, OSPF, EIGRP, 그리고 통신사가 많이 쓰는 IS-IS는 모두 IGP다. 한 조직 안에서 "가장 빠른 길"을 찾는 것이 목적이고, 망 안의 모든 라우터를 믿는다. 인터넷처럼 서로 다른 조직의 망(AS, 자율 시스템)을 잇는 곳에서는 사정이 다르다. 남의 망을 믿을 수 없고, 가장 빠른 길보다 "돈을 내는 회선으로", "경쟁사 망은 거치지 않게" 같은 정책이 먼저다.

그 자리를 맡은 것이 BGP다. BGP는 링크 비용 대신 경로가 지나온 AS 번호 목록(AS_PATH)과 여러 속성을 보고 고르며, TCP 179번 포트 위에서 이웃과 명시적으로 세션을 맺는다. 수십만 개의 인터넷 경로를 들고도 버티도록 만들어졌고, 대신 수렴은 IGP보다 느리다. 같은 IP를 여러 곳에서 광고해 가까운 곳이 답하게 만드는 일도 BGP로 한다([CDN과 애니캐스트 글](/posts/cdn-edge-anycast)).

회사 망에서 둘은 보통 층을 이룬다. IGP는 내부 라우터의 루프백과 링크 주소처럼 "망의 뼈대"만 실어 나르고, 고객 대역과 인터넷 경로는 BGP가 실어 나른다. IGP에 인터넷 경로를 통째로 재분배(redistribute)하는 건 흔한 사고다. OSPF가 수십만 장의 External LSA를 뿌리다가 작은 라우터들의 메모리가 먼저 무너진다.

요즘 큰 데이터 센터는 내부에서도 IGP 대신 BGP를 쓰는 경우가 많다. 스위치마다 AS 번호를 따로 주고 eBGP로 이어 단순한 규칙으로 큰 망을 다룬다(RFC 7938). 이 구조는 [망 구조 설계 글](/posts/network-design-three-tier-spine-leaf)의 스파인-리프와 함께 본다.

## 현장에서 라우팅 프로토콜을 의심하는 순간

라우팅 프로토콜 장애는 대부분 "이웃이 안 맺어진다"와 "이웃은 맺어졌는데 경로가 이상하다" 둘로 나뉜다. 먼저 이웃 상태부터 본다.

```bash
# 이웃 상태, 인터페이스별 OSPF 설정 확인 (FRR)
sudo vtysh -c "show ip ospf neighbor"
sudo vtysh -c "show ip ospf interface to-r3"
```

```text
to-r3 is up
  ifindex 4, MTU 1500 bytes, BW 10000 Mbit <UP,BROADCAST,RUNNING,MULTICAST>
  Internet Address 10.0.13.1/30, Broadcast 10.0.13.3, Area 0.0.0.0
  MTU mismatch detection: enabled
  Router ID 1.1.1.1, Network Type POINTOPOINT, Cost: 10
  Transmit Delay is 1 sec, State Point-To-Point, Priority 1
  No backup designated router on this network
  Multicast group memberships: OSPFAllRouters
  Timer intervals configured, Hello 10s, Dead 40s, Wait 40s, Retransmit 5
```

이웃 목록이 비어 있으면 Hello가 아예 오가지 않는 것이다. 방화벽이 프로토콜 89나 멀티캐스트 224.0.0.5를 막고 있거나, 그 인터페이스가 `passive`로 설정되어 있거나, `network` 문이 인터페이스 대역을 포함하지 않는 경우다. 서버 쪽 망을 OSPF에 광고만 하고 Hello는 보내지 않으려고 걸어 둔 passive를 정작 라우터 사이 링크에도 걸어 버리는 실수가 흔하다.

상태가 `Init`에 멈춰 있으면 내 Hello는 상대에게 안 가고 상대 Hello만 온다는 뜻이다. 한쪽 방향만 막는 ACL이나 보안 그룹을 의심한다. `2-Way`에서 멈추는 건 DR이 있는 망에서 DR이 아닌 라우터끼리는 정상이다. `ExStart`나 `Exchange`에서 멈추면 십중팔구 MTU가 다르다. 위 출력의 `MTU mismatch detection: enabled`가 이 검사를 켠 것이고, 터널이나 VLAN 때문에 한쪽 MTU만 다를 때 이 상태로 멈춘다. Hello·Dead 간격, 영역 번호, 인증, 망 마스크, 네트워크 타입(한쪽은 broadcast, 한쪽은 point-to-point)이 다르면 아예 이웃이 안 된다.

이웃은 `Full`인데 경로가 이상하면 LSDB와 라우팅 테이블을 비교한다. LSDB에 목적지가 있는데 테이블에 없으면 관리 거리가 더 작은 다른 출처(정적 경로가 대표적)가 이기고 있는지, 더 길게 맞는 접두사가 다른 쪽으로 끌고 가는지 본다. 경로가 몇 초마다 바뀌면 흔들리는 링크(flapping)가 있다. `Last update`와 LSA의 `Seq#`가 계속 오르는 라우터를 찾아가면 그 근처에 문제 링크가 있다. 비대칭 경로는 기준 대역폭이 라우터마다 다르거나 한쪽에만 비용을 손으로 넣었을 때 생긴다. 이건 [traceroute](/posts/layer-ip-routing-icmp)를 양쪽에서 돌려 보면 드러난다.

처음 장면 같은 증상, 즉 장애 뒤 수십 초 동안 끊겼다가 저절로 살아나는 패턴이 보이면 감지 시간을 의심한다. 끊긴 시간이 Dead 간격과 비슷한지 보고, 중간에 포트를 살려 두는 장비가 있는지 확인한 뒤 BFD를 건다.

## 거리를 전하느냐, 지도를 나누느냐

RIP는 이웃에게 거리만 건네서 간단하지만 망의 모양을 몰라 나쁜 소식이 느리게 퍼진다. OSPF는 모두가 같은 지도를 갖고 각자 다익스트라를 돌려 빠르고 정확하며, 커지면 영역으로 나눠 지도를 잘게 만든다. EIGRP는 거리 벡터를 쓰면서도 "나보다 확실히 가까운 이웃"만 예비로 믿어 루프를 막는다. 어떤 프로토콜을 쓰든 장애 뒤 멈춘 시간의 대부분은 끊김을 알아채는 데 쓰이니, 수렴을 줄이려면 타이머보다 BFD 같은 감지부터 본다. 이 라우터들을 어떤 모양으로 이을지는 [망 구조 설계 글](/posts/network-design-three-tier-spine-leaf)에서, 라우터 자체가 죽었을 때 호스트가 게이트웨이를 잃지 않게 하는 법은 [게이트웨이와 링크 이중화 글](/posts/gateway-link-redundancy-fhrp-lacp)에서 이어진다.

## 면접에서 나올 만한 질문

### 정적 라우팅과 동적 라우팅은 언제 각각 쓰나요?

출구가 하나뿐인 스텁 망이나 경로가 거의 바뀌지 않는 작은 망에는 정적 경로가 낫다. CPU를 쓰지 않고, 이웃이 잘못된 경로를 퍼뜨릴 위험도 없다. 길이 여럿이고 장애 때 다른 길로 돌아가야 하거나 망이 자주 커지면 동적 라우팅이 필요하다. 정적 경로는 인터페이스가 내려갈 때만 사라지기 때문에, 건너편 장비만 죽은 경우에는 끝까지 죽은 길을 가리킨다.

### 거리 벡터와 링크 상태 방식은 어떻게 다른가요?

거리 벡터(RIP)는 이웃에게 목적지별 거리만 전하고, 각 라우터는 망의 모양을 모른 채 이웃의 말을 믿는다. 링크 상태(OSPF)는 각 라우터가 자기 링크 정보를 LSA로 망 전체에 뿌리고, 모두가 같은 LSDB를 갖고 각자 다익스트라로 최단 경로를 계산한다. 거리 벡터는 가볍지만 count to infinity처럼 나쁜 소식이 느리게 퍼지는 문제가 있고, 링크 상태는 메모리와 계산을 더 쓰는 대신 빠르고 루프 없이 수렴한다.

### count to infinity는 왜 생기고 어떻게 막나요?

경로를 잃은 라우터가, 사실은 자기를 거쳐 가는 이웃의 경로를 새 길로 믿어 버려서 생긴다. 둘이 서로를 가리키며 거리를 하나씩 올리다가 무한대(RIP는 16)에 닿아야 멈춘다. 배운 이웃에게 다시 광고하지 않는 분할 수평, 그 이웃에게 갈 수 없다고 알리는 독 역전, 잃은 경로를 즉시 알리는 triggered update, 잠깐 나쁜 소식을 무시하는 hold-down으로 줄인다. 다만 셋 이상이 고리를 이루면 완전히 막지 못한다.

### OSPF 이웃이 ExStart 상태에서 넘어가지 않으면 무엇을 보나요?

가장 먼저 양쪽 인터페이스 MTU가 같은지 본다. ExStart와 Exchange는 LSA 목차(DBD)를 주고받는 단계인데, DBD에 인터페이스 MTU가 들어 있어서 다르면 여기서 멈춘다. 터널이나 VLAN 서브인터페이스 때문에 한쪽만 MTU가 작아진 경우가 흔하다.

### OSPF에서 영역을 나누는 이유는 무엇인가요?

LSA의 범람과 SPF 재계산을 영역 안으로 가두기 위해서다. 영역이 하나면 어디서든 링크가 흔들릴 때 모든 라우터가 SPF를 다시 돌리지만, 영역을 나누면 ABR이 다른 영역에 요약 정보만 넘기므로 바깥 라우터는 비용 변화만 받는다. ABR에서 대역을 요약하면 하위 대역의 변화는 아예 보이지 않는다. 대가로 영역 사이 경로가 최단이 아닐 수 있고, 모든 영역은 영역 0에 붙어야 한다는 제약이 생긴다.

### 관리 거리와 메트릭은 어떻게 다르게 쓰이나요?

메트릭은 한 프로토콜 안에서 경로끼리 비교하는 값이고, 관리 거리는 서로 다른 출처(정적, OSPF, RIP, BGP)가 같은 접두사를 말할 때 어느 출처를 믿을지 정하는 값이다. 작은 쪽이 이기며 시스코·FRR 기본값은 정적 1, eBGP 20, OSPF 110, RIP 120이다. 둘 다 같은 길이의 접두사 사이에서만 쓰이고, 더 길게 맞는 접두사가 있으면 관리 거리와 상관없이 그쪽이 먼저다.

### 링크 장애 후 수렴을 빠르게 하려면 무엇을 바꾸나요?

수렴 시간의 대부분은 감지에 쓰이므로 BFD를 먼저 건다. 기본 OSPF는 Dead 간격 40초를 기다리는데, 실습에서 같은 장애가 Hello 1초·Dead 4초로 약 3.7초, BFD 300ms×3으로 약 0.7초까지 줄었다. Hello만 아주 짧게 줄이면 CPU가 바쁠 때 멀쩡한 이웃을 끊는 부작용이 있다. 그 다음으로 SPF throttle 같은 계산 지연과 예비 경로를 미리 설치하는 LFA를 본다.

### IGP와 BGP의 역할은 어떻게 다른가요?

IGP(OSPF, IS-IS 등)는 한 조직 안에서 모든 라우터를 믿고 가장 빠른 길을 빨리 찾는 것이 목적이다. BGP는 서로 믿지 않는 조직(AS) 사이에서 AS_PATH와 속성, 정책으로 경로를 고르고, 인터넷 경로 수십만 개를 견디도록 만들어졌다. 보통 IGP는 망의 뼈대인 루프백과 링크 주소만, BGP는 고객 대역과 외부 경로를 맡는다. IGP에 인터넷 경로를 재분배하면 작은 라우터의 메모리부터 무너진다.
