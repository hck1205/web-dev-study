<EasyIntro>
  "쿠폰은 한 사람이 한 번만"이라고 코드를 짰는데 할인이 두 번 들어간 주문이 나온다. 사용자가 버튼을 두 번 눌러 요청 두 개가 거의 같은 순간에 들어왔고, 둘 다 "아직 쓴 기록이 없다"고 확인한 뒤 각자 할인을 적용했기 때문이다.

  이렇게 누가 먼저 도착하느냐에 따라 결과가 달라지는 버그를 경쟁 상태라고 한다. 확인하고 행동하기까지 두 걸음 이상이 걸리면, 그 사이의 틈에 다른 요청이 끼어들 수 있다. 숫자를 하나 올리는 일조차 컴퓨터에게는 읽고, 더하고, 다시 쓰는 세 걸음이라 같은 틈이 생긴다.

  고치는 방법은 틈을 없애는 것이다. 확인과 행동을 한 동작으로 합치거나, 틈 동안 아무도 못 들어오게 잠그거나, 틈 사이에 바뀌었는지 알아채고 다시 한다. 테스트에서는 요청을 하나씩 보내니 늘 통과하고 부하가 몰릴 때만 드러나서, 찾기 어려운 버그로 유명하다.

신규 가입 쿠폰은 한 사람이 한 번만 쓸 수 있다. 코드도 그렇게 짰다. 이미 쓴 기록이 있는지 조회하고, 없으면 기록을 남기고 할인한다. 그런데 정산 담당자가 같은 사용자에게 할인이 두 번 들어간 주문을 찾아왔다. 로그를 보면 두 요청이 3ms 간격으로 들어왔다. 사용자가 결제 버튼을 두 번 눌렀거나, 탭 두 개에서 동시에 결제했다.

조회한 순간에는 분명히 기록이 없었다. 두 요청 모두에게. 이렇게 여러 실행 흐름이 같은 데이터를 다루고, 누가 먼저 도착하느냐에 따라 결과가 달라지는 버그를 경쟁 상태(race condition)라고 한다. 이 글은 경쟁 상태가 생기는 세 가지 모양(읽고 고치고 쓰기, 확인하고 행동하기, 파일의 TOCTOU)을 직접 재현하고, 싱글 스레드인 자바스크립트와 워커 스레드, DB에서 각각 어떻게 나타나는지, 찾는 법과 고치는 법을 고르는 기준까지 따라간다. 환경은 Ubuntu 24.04, Node 22, Go 1.24, Python 3.13, PostgreSQL 16이다.

이 주제의 다른 글: 락끼리 서로 기다리다 멈추는 문제는 [데드락 글](/posts/deadlocks), 여러 스레드가 같은 객체를 써도 깨지지 않게 만드는 법과 메모리 가시성은 [스레드 안전 글](/posts/thread-safety)에서 다룬다.

## 결과가 실행 순서에 달려 있으면

경쟁 상태의 정의는 단순하다. 프로그램의 결과가 여러 실행 흐름의 상대적인 순서나 타이밍에 따라 달라지고, 그중 일부 순서에서 틀린 결과가 나오는 상태다. 실행 흐름은 스레드일 수도, 프로세스일 수도, 서버 여러 대일 수도, 자바스크립트의 비동기 콜백 두 개일 수도 있다.

필요한 재료는 세 가지다. 공유하는 무언가(메모리, 파일, DB 행, 외부 API의 상태), 그것을 바꾸는 쓰기, 그리고 여러 단계로 나뉜 작업이다. 작업이 한 걸음에 끝나면 끼어들 틈이 없다. 두 걸음 이상이면 그 사이에 다른 흐름이 들어올 수 있다. 이 글 전체에서 이 사이 공간을 "틈"이라고 부르겠다.

순서가 맞으면 멀쩡히 동작한다는 점이 이 버그를 고약하게 만든다. 테스트는 한 요청씩 보내니 늘 통과한다. 부하가 적으면 틈에 무언가 들어올 확률이 낮다. 로그를 찍어 보려고 `console.log`를 넣으면 타이밍이 바뀌어 사라지기도 한다. 관찰하려고 하면 숨는 버그라 하이젠버그(Heisenbug)라는 별명이 붙었다.

## 읽고 더하고 쓰는 세 걸음 (read-modify-write)

가장 흔한 모양은 값을 읽어서 고친 다음 다시 쓰는 것이다. 조회수 `count++` 한 줄이 대표적이다. 코드는 한 줄이지만 CPU에게는 세 걸음이다. gcc 13으로 최적화 없이(`-O0`) 컴파일한 결과를 보자.

```bash
gcc -O0 -c inc.c -o inc.o           # void inc(void) { count++; } 를 컴파일한다
objdump -d --no-show-raw-insn inc.o # 기계어를 사람이 읽는 명령으로 풀어 본다
```

```text
0000000000000000 <inc>:
   0:	endbr64
   4:	push   %rbp
   5:	mov    %rsp,%rbp
   8:	mov    0x0(%rip),%eax        # e <inc+0xe>
   e:	add    $0x1,%eax
  11:	mov    %eax,0x0(%rip)        # 17 <inc+0x17>
  17:	nop
  18:	pop    %rbp
  19:	ret
```

8번 줄이 메모리에서 레지스터로 읽고, e번 줄이 레지스터에서 더하고, 11번 줄이 메모리에 쓴다.

`-O2`로 최적화하면 `addl $1, count(%rip)` 한 줄이 된다. 그래도 안전하지 않다. 명령은 하나지만 CPU 안에서는 여전히 읽고 쓰는 두 번의 메모리 접근이고, 다른 코어가 그 사이에 끼어들 수 있다. 원자적으로 하려면 `lock addl $1, count(%rip)`처럼 `lock` 접두사가 붙어야 한다. gcc에서 `__atomic_fetch_add`를 쓰면 실제로 그렇게 나온다.

두 스레드 A와 B가 0에서 한 번씩 올리면 2가 되어야 한다. 그런데 아래 순서로 섞이면 1이 된다.

스레드 두 개가 한 번씩만 올려도 가능한 실행 순서가 6가지이고, 그중 결과가 2인 것은 2가지뿐이다. 각자 두 번씩이면 70가지, 세 번씩이면 924가지로 늘어난다. 직접 세어 보자. 아래 함수는 스레드 수와 스레드마다 올리는 횟수를 받아, 가능한 모든 실행 순서를 따라가며 마지막에 남을 수 있는 count 값을 모은다. 각 증가는 "읽기"와 "쓰기" 두 걸음으로 본다.

<CodePlayground
  caption="섞이는 순서마다 남는 값 모으기"
  functionName="outcomes"
  initialCode={`function outcomes(threads, increments) {
  // 스레드마다 [읽기, 쓰기]를 increments번 반복한다
  // 읽기: 레지스터 = 메모리, 쓰기: 메모리 = 레지스터 + 1
  // 가능한 모든 순서를 따라가서, 끝났을 때의 메모리 값을 오름차순 배열로 돌려준다
  return [];
}`}
  solution={`function outcomes(threads, increments) {
  const results = new Set();
  const total = increments * 2;
  function dfs(pc, regs, mem) {
    let moved = false;
    for (let t = 0; t < threads; t++) {
      if (pc[t] === total) continue;
      moved = true;
      const nextPc = pc.slice();
      nextPc[t]++;
      if (pc[t] % 2 === 0) {
        const r = regs.slice();
        r[t] = mem;
        dfs(nextPc, r, mem);
      } else {
        dfs(nextPc, regs, regs[t] + 1);
      }
    }
    if (!moved) results.add(mem);
  }
  dfs(Array(threads).fill(0), Array(threads).fill(0), 0);
  return [...results].sort((a, b) => a - b);
}`}
  tests={[

    { label: "2개 스레드, 2번씩", args: [2, 2], expected: [2, 3, 4] },
    { label: "3개 스레드, 1번씩", args: [3, 1], expected: [1, 2, 3] },
    { label: "2개 스레드, 3번씩", args: [2, 3], expected: [2, 3, 4, 5, 6] },
  ]}

2개 스레드가 3번씩 올리면 정답 6 말고도 2부터 5까지 다 나올 수 있다. 횟수가 늘수록 최솟값은 2에 머물고 정답과의 거리는 벌어진다. 여러 번 올릴수록 틀릴 수 있는 폭이 커진다는 뜻이다.

Go로 실제로 돌려 봤다. 고루틴 두 개가 `views++`를 10만 번씩 한다.

```bash
go run .   # 고루틴 2개가 views++를 100,000번씩, 기대값 200,000
```

```text
views = 113027
views = 168110
views = 156265
```

세 번 돌려 세 번 다 다르고, 셋 다 20만에 한참 못 미친다. 반대로 반복을 1,000번으로 줄이면 몇 번을 돌려도 2,000이 정확히 나왔다. 고루틴 하나가 다른 하나가 시작되기 전에 끝나 버려서 섞일 틈이 없었기 때문이다. 결과가 맞았다고 경쟁 상태가 없는 게 아니다.

## 확인한 사실은 행동할 때 이미 낡았다 (check-then-act)

두 번째 모양은 조건을 확인하고, 그 결과를 믿고 행동하는 것이다. 처음의 쿠폰이 이 모양이다. "기록이 없으면 넣는다", "재고가 있으면 판다", "파일이 없으면 만든다", "인스턴스가 null이면 만든다(지연 초기화 싱글턴)" 모두 같다.

읽고 고치고 쓰기와 다른 점은 값이 아니라 판단이 틀어진다는 것이다. 확인한 순간에는 참이었던 조건이 행동하는 순간에는 거짓일 수 있다. 확인과 행동 사이가 1ms든 1분이든 똑같이 위험하다. 길수록 자주 터질 뿐이다.

틈을 메우는 방법은 두 가지다. 확인과 행동을 한 동작으로 합치거나(쿠폰이라면 `UNIQUE` 제약과 `INSERT ... ON CONFLICT DO NOTHING`), 확인부터 행동까지 다른 흐름이 못 들어오게 막는다(락). 앞의 사용자 42를 고유 제약이 있는 테이블로 다시 돌리면 이렇다.

```text
unique: [ 'already', 'ok' ]
23505 duplicate key value violates unique constraint "redemptions2_coupon_user_id_key"
```

두 요청 중 하나만 `ok`다. 제약을 둔 채 그냥 `INSERT`를 한 번 더 하면 `23505`(unique_violation) 에러가 난다. 확인을 앱이 아니라 저장소가 하니, 서버가 몇 대든 판정은 한 곳에서 난다.

## 파일 시스템의 TOCTOU

파일에서 확인하고 행동하기는 따로 이름이 있다. TOCTOU(Time Of Check to Time Of Use), 확인한 시점과 쓰는 시점이 다르다는 뜻이다. 크론 작업이 겹치지 않게 락 파일을 쓰는 흔한 코드로 재현해 봤다. 두 프로세스가 동시에 출발하고, 틈을 잘 보이게 하려고 확인과 생성 사이에 1ms를 넣었다.

```python
# naive: 확인과 생성이 따로다
if not os.path.exists(LOCK):        # 확인 (check)
    time.sleep(0.001)               # 확인과 생성 사이의 틈을 1ms로 벌렸다
    with open(LOCK, "w") as f:      # 사용 (use)
        f.write(name)

# excl: O_CREAT | O_EXCL은 "없으면 만들고, 있으면 실패"를 커널이 한 번에 한다
fd = os.open(LOCK, os.O_CREAT | os.O_EXCL | os.O_WRONLY, 0o644)
```

```text
--- naive
cron-a: 락을 잡았다, 작업 시작
cron-b: 락을 잡았다, 작업 시작
--- excl
cron-a: 락을 잡았다, 작업 시작
cron-b: FileExistsError(17, 'File exists')
```

`O_EXCL`은 존재 확인과 생성을 커널 안에서 한 번에 처리한다. 크론 작업이라면 셸에서 `flock`을 쓰는 게 더 간단하다. 파일에 커널 잠금을 걸고, 프로세스가 죽으면 잠금도 같이 풀려서 락 파일이 남아 다음 실행을 영원히 막는 일이 없다.

```bash
# A가 1초 동안 잠금을 쥐고 있는 사이 B가 -n(기다리지 않음)으로 시도한다
(flock -n ./report.lock -c 'echo "A 시작"; sleep 1; echo "A 끝"'; echo "A exit=$?") &
sleep 0.2; flock -n ./report.lock -c 'echo "B 시작"'; echo "B exit=$?"
```

```text
A 시작
B exit=1
A 끝
A exit=0
```

B는 실행되지 않고 종료 코드 1로 끝났다. 크론탭에는 `flock -n /var/lock/report.lock /opt/jobs/report.sh`처럼 쓴다. 서버가 여러 대면 파일 잠금은 서버 한 대 안에서만 통하니 [크론 작업 글](/posts/cron-jobs)의 방법으로 넘어가야 한다.

TOCTOU가 보안 문제로 바뀌는 건 권한이 높은 프로그램이 경로를 확인하고 나서 여는 경우다. root로 도는 프로그램이 "이 경로는 사용자 소유의 일반 파일이다"를 확인하고, 그다음 같은 경로를 연다고 하자. 공격자는 그 틈에 경로를 `/etc/passwd`를 가리키는 심볼릭 링크로 바꾼다.

막는 원칙은 이름이 아니라 열어 둔 파일 디스크립터로 확인하는 것이다. 먼저 열고(`O_NOFOLLOW`로 심볼릭 링크를 거부하고), 열린 fd에 `fstat`을 해서 확인한다. 링크를 거부하면 실제로 이렇게 실패한다.

```bash

python3 -c 'import os; os.open("evil.txt", os.O_WRONLY | os.O_NOFOLLOW)'
```

```text
OSError(40, 'Too many levels of symbolic links')
```

`O_NOFOLLOW`는 마지막 경로 조각만 검사한다. 중간 디렉터리까지 링크를 막으려면 리눅스 5.6부터 있는 `openat2`의 `RESOLVE_NO_SYMLINKS`를 쓴다. 임시 파일은 이름을 짐작할 수 없게 `mkstemp`로 만들고, 설정 파일을 바꿀 때는 임시 파일에 다 쓴 뒤 `rename`으로 바꿔치기한다. 같은 파일 시스템 안의 `rename`은 원자적이라 읽는 쪽은 옛 파일 아니면 새 파일만 본다. 컨테이너 도구에서도 이런 심볼릭 링크 바꿔치기 경쟁이 취약점으로 보고된 적이 있다(`docker cp`의 CVE-2018-15664).

## 스레드가 하나인 자바스크립트에서도 생긴다

Node는 자바스크립트를 스레드 하나에서 돌린다. 그래서 `count++`가 중간에 끊길 일은 없다. 함수 하나가 실행되는 동안 다른 자바스크립트는 끼어들지 못한다([이벤트 루프 글](/posts/event-loop)). 그런데 `await`를 만나면 함수는 거기서 멈추고 다른 콜백이 돌 수 있다. `await`가 틈이다.

```js
const used = new Set();
async function redeem(user, coupon) {
  if (used.has(coupon)) return `${user}: 이미 쓴 쿠폰`;   // 확인
  await sleep(5);                                          // 결제 API 호출 같은 I/O
  used.add(coupon);                                        // 기록
  return `${user}: 할인 적용`;
}
```

```text
[ 'tab-1: 할인 적용', 'tab-2: 할인 적용' ] discounts = 2
[ 'tab-1: 할인 적용', 'tab-2: 이미 쓴 쿠폰' ] discounts = 1
```

첫 줄은 위 코드를 두 번 동시에 부른 결과다. 둘 다 할인받았다. 둘째 줄은 `await` 전에 "처리 중" 표시를 동기적으로 남기도록 고친 결과다. 확인과 표시 사이에 `await`가 없으니 다른 콜백이 끼어들 수 없다. 단, 이 방법은 프로세스 하나 안에서만 통한다. PM2나 클러스터 모드로 프로세스를 여러 개 띄우면 앞의 그림과 같은 상황이 되니 결국 DB 제약으로 가야 한다.

브라우저에서는 두 가지 모양이 자주 나온다. 하나는 늦게 온 옛 응답이 새 응답을 덮는 것이다. 검색어를 "re", "rea", "react"로 바꾸는 동안 요청 세 개가 나가고, "re"의 응답이 가장 늦게 오면 화면에는 "react"를 쳤는데 "re"의 결과가 남는다. 이 경우는 [브라우저 fetch 글](/posts/browser-fetch)에서 `AbortController`와 요청 번호로 막는 방법까지 다뤘다. 다른 하나는 중복 제출이다. 버튼을 막는 건 사용자 경험을 위한 것이고, 네트워크 재시도나 새로 고침으로 같은 요청이 두 번 오는 것까지 막으려면 서버가 [멱등성 키](/posts/idempotency-key)로 판정해야 한다.

## 워커 스레드가 같은 메모리를 만질 때

Node에서도 진짜 스레드끼리 메모리를 나누는 방법이 있다. `worker_threads`에 `SharedArrayBuffer`를 넘기면 여러 워커가 같은 메모리를 본다. 워커 4개가 같은 칸을 100만 번씩 올리게 했다. 한 번은 그냥 `view[0]++`로, 한 번은 `Atomics.add`로.

```js
// 워커 안에서
if (mode === "plain") for (let i = 0; i < N; i++) view[0]++;
else for (let i = 0; i < N; i++) Atomics.add(view, 0, 1);
```

```bash
node sab.js   # 워커 4개 x 1,000,000번, 기대값 4,000,000
```

```text
plain    expected 4000000  got 3356336  (124 ms)
atomics  expected 4000000  got 4000000  (343 ms)
plain    expected 4000000  got 3327039  (135 ms)
atomics  expected 4000000  got 4000000  (308 ms)
plain    expected 4000000  got 2832637  (105 ms)
atomics  expected 4000000  got 4000000  (244 ms)
```

`view[0]++`는 매번 30만~110만 번을 잃었다. `Atomics.add`는 매번 정확했고, 대신 2~3배 느렸다. 원자적 연산은 코어끼리 캐시 줄을 주고받으며 줄을 서기 때문이다. 이 비용이 아까워서 워커마다 따로 세고 마지막에 더하는 방식이 더 빠를 때가 많다. 공유를 줄이는 쪽이다. 워커끼리 `postMessage`로 주고받는 일반 객체는 복사되어 넘어가니 이런 문제가 없다. 공유는 `SharedArrayBuffer`를 넘길 때만 생긴다. 왜 `Atomics`가 필요한지, 쓴 값이 다른 스레드에 언제 보이는지는 [스레드 안전 글](/posts/thread-safety)에서 이어서 본다.

## DB에서는 갱신 손실로 나타난다

읽고 고치고 쓰기가 DB 위에서 일어나면 갱신 손실(lost update)이다. 앱에서 `SELECT views`로 읽고 1을 더해 `UPDATE ... SET views = $1`로 쓰는 코드를, 요청 200개가 100ms에 걸쳐 흩어져 들어오게 해서 돌렸다. 같은 200번을 `SET views = views + 1` 한 문장으로도 돌렸다.

```js
// 앱에서 읽고 더해 쓰기
const { rows } = await pool.query("SELECT views FROM posts WHERE id = $1", [id]);
await pool.query("UPDATE posts SET views = $1 WHERE id = $2", [rows[0].views + 1, id]);
// DB가 한 문장 안에서 읽고 더해 쓰기
await pool.query("UPDATE posts SET views = views + 1 WHERE id = $1", [id]);
```

```text
┌─────────┬────┬───────┐
│ (index) │ id │ views │
├─────────┼────┼───────┤
│ 0       │ 1  │ 4     │
│ 1       │ 2  │ 200   │
└─────────┴────┴───────┘
```

앱에서 더한 1번 글은 200번 중 4번만 남았다(다시 돌리면 3, 4). 커넥션 10개가 거의 같은 값을 읽고 같은 값을 써서 대부분이 덮였다. 2번 글은 정확히 200이다. PostgreSQL은 `UPDATE`가 행을 고치기 전에 행 잠금을 잡고, 기다렸다면 최신 행으로 `views + 1`을 다시 계산한다. 읽기와 쓰기가 한 문장 안에서 잠금 아래 일어나니 틈이 없다.

계산이 SQL 한 문장으로 안 되는 경우(외부 API 결과를 반영해야 하는 경우 등)에는 버전 열로 덮어쓰기를 알아채는 [낙관적 잠금](/posts/optimistic-locking)이나 `SELECT ... FOR UPDATE`의 [비관적 잠금](/posts/pessimistic-locking)으로 간다. 격리 수준이 이 현상을 어디까지 막는지는 [트랜잭션 격리 수준 글](/posts/db-transaction-isolation)에 정리했다. 기본값인 READ COMMITTED는 앱에서 읽고 쓰는 갱신 손실을 막지 않는다.

## 경쟁 상태를 찾아내는 법

경쟁 상태는 코드 리뷰로 찾는 게 먼저다. 공유하는 것이 무엇이고, 그것을 읽은 뒤 쓰기 전에 `await`, 네트워크 호출, 락 해제, 다른 문장이 있는지 본다. 그 사이가 틈이다.

도구로는 데이터 경합 탐지기가 있다. Go는 `-race` 플래그를 붙이면 메모리 접근마다 기록을 남겨서, 동기화 없이 두 고루틴이 같은 주소를 만지고 그중 하나가 쓰기면 알려 준다. 앞의 1,000번짜리 코드는 결과가 2,000으로 맞게 나왔지만 탐지기는 바로 잡았다(경로는 줄였다).

```bash
go run -race .   # 데이터 경합 탐지기를 켜고 실행한다
```

```text
==================
WARNING: DATA RACE
Read at 0x00c00011a078 by goroutine 7:
  main.main.func1()
      .../gorace/main.go:16 +0x99

Previous write at 0x00c00011a078 by goroutine 8:
  main.main.func1()
      .../gorace/main.go:16 +0xab

Goroutine 7 (running) created at:
  main.main()
      .../gorace/main.go:13 +0x78

Goroutine 8 (finished) created at:
  main.main()
      .../gorace/main.go:13 +0x78
==================
views = 2000
Found 1 data race(s)
exit status 66
```

읽는 순서는 이렇다. `Read at ... by goroutine 7`과 `Previous write at ... by goroutine 8`이 같은 주소(`0x00c00011a078`)를 가리킨다. 둘 다 16번 줄 `views++`다. 아래쪽의 `created at`은 그 고루틴을 누가 만들었는지(13번 줄의 `go func()`)다. 경합이 발견되면 종료 코드가 66이 되어 CI가 실패한다. `views`를 `atomic.Int64`로 바꾸고 `views.Add(1)`로 고치니 `-race`로 돌려도 경고 없이 `views = 200000`, 종료 코드 0이었다.

탐지기에는 한계가 있다. 실행 중에 실제로 일어난 접근만 보니, 테스트가 그 경로를 동시에 지나가야 잡힌다. Go 문서는 메모리를 5~10배, 실행 시간을 2~20배 더 쓴다고 안내해서 운영 서버에 상시로 켜 두지는 않고, `go test -race`를 CI에 넣고 부하 테스트 환경에서 한동안 돌린다. C와 C++은 `-fsanitize=thread`(ThreadSanitizer)가 같은 일을 한다. 그리고 탐지기가 잡는 것은 메모리의 데이터 경합이다. 쿠폰처럼 DB나 파일을 사이에 둔 경쟁 상태는 메모리 접근이 아니라서 못 잡는다. 이런 건 같은 요청을 동시에 수십 개 보내는 테스트로 재현한다. 앞의 `coupon2.js`처럼 `Promise.all`로 같은 사용자의 요청을 두 개씩 묶어 보내는 것만으로도 대부분 드러난다.

한 동작으로 바꿀 수 있으면 그게 제일이다. CPU의 원자적 명령, SQL 한 문장, `O_EXCL`, `rename`, Redis의 `INCR`이나 `SET NX`가 여기 든다. 락을 잡고 푸는 코드가 없으니 푸는 걸 잊거나 순서를 틀릴 일도 없다.

저장소가 규칙을 알 수 있으면 제약에 맡긴다. "쿠폰은 사람당 한 번"은 고유 제약 하나로 표현된다. "잔액은 0 이상"은 `UPDATE accounts SET balance = balance - 100 WHERE id = 1 AND balance >= 100`처럼 조건을 `WHERE`에 넣고 바뀐 행 수를 확인한다. 확인과 행동이 한 문장이 된다.

여러 단계가 꼭 필요하면 두 갈래다. 충돌이 드물면 잠그지 않고 진행하다가 쓰는 순간 "내가 읽은 뒤로 바뀌었나"를 확인하고, 바뀌었으면 다시 한다(CAS, 버전 열). 충돌이 잦으면 재시도가 일을 잡아먹으니 처음부터 락으로 줄을 세운다. 락은 확실하지만 기다리는 시간이 생기고, 락을 둘 이상 쓰는 순간 서로 기다리다 멈추는 [데드락](/posts/deadlocks)의 위험이 생긴다.

마지막은 아예 여러 명이 같은 것을 쓰지 않게 구조를 바꾸는 것이다. 사용자 ID로 파티션을 나눈 큐에서 소비자 하나가 그 사용자의 요청을 차례로 처리하면, 같은 사용자의 요청끼리는 경쟁할 일이 없다. 대신 처리량은 파티션 수에 묶인다.

## 현장에서 경쟁 상태를 의심하는 순간

이런 증상이면 경쟁 상태부터 의심한다.

- 한 번만 일어나야 하는 일이 가끔 두 번 일어났다. 중복 주문, 이중 할인, 알림 두 번, 크론 작업 두 번.
- 숫자가 조금씩 맞지 않는다. 조회수, 재고, 포인트 잔액이 로그로 계산한 값보다 적다.
- 부하가 높을 때만 나고, 같은 요청을 하나씩 다시 보내면 재현되지 않는다. 디버그 로그를 켜면 사라진다.
- 배포로 서버 대수를 늘렸거나 워커 동시성을 올린 직후부터 생겼다.

확인은 시간과 키로 한다. 중복된 두 건의 생성 시각과 요청 ID를 나란히 놓고, 두 요청의 처리 구간이 겹쳤는지 본다. 겹쳤다면 그 코드 경로에서 "읽고 판단하고 쓰는" 구간을 찾는다. DB라면 같은 키로 중복이 있는지 바로 셀 수 있다.

```sql
-- 같은 사용자가 같은 쿠폰을 두 번 쓴 기록 찾기
SELECT user_id, count(*) AS uses, min(created_at), max(created_at)
FROM redemptions
WHERE coupon = 'WELCOME10'
GROUP BY user_id
HAVING count(*) > 1;
```

`max - min`이 수 ms에서 수백 ms면 동시 요청이 겹친 것이다. 고칠 때는 기존 중복 데이터를 먼저 정리해야 고유 제약을 만들 수 있다는 점도 잊지 않는다. 중복이 남아 있으면 `CREATE UNIQUE INDEX`가 `could not create unique index` 에러로 실패한다.

흔한 실수도 몇 가지 있다. 앱 서버 메모리의 락으로 고쳤는데 서버가 두 대라서 그대로인 경우, 트랜잭션으로 감쌌으니 안전하다고 생각했는데 READ COMMITTED라서 갱신 손실이 그대로인 경우, 버튼만 막고 서버 쪽 판정을 빼먹은 경우가 많다. 트랜잭션은 경쟁 상태를 저절로 막아 주지 않는다. 어떤 격리 수준에서 어떤 현상을 막는지 알고 써야 한다.

경쟁 상태는 결국 "확인한 사실이 행동하는 순간에도 참인가"의 문제다. 확인과 행동을 한 동작으로 붙이거나, 그사이를 아무도 못 들어오게 하거나, 그사이에 바뀌었으면 알아채게 하면 된다. 셋 중 무엇을 고를지는 서버가 몇 대인지, 충돌이 얼마나 잦은지가 정한다. 락을 고른 다음에 생기는 문제는 [데드락 글](/posts/deadlocks)에서, 스레드끼리 나누는 객체를 처음부터 안전하게 설계하는 법은 [스레드 안전 글](/posts/thread-safety)에서 이어진다.

## 면접에서 나올 만한 질문

### 경쟁 상태가 무엇인가요?

여러 실행 흐름이 공유 자원을 다룰 때, 실행 순서나 타이밍에 따라 결과가 달라지고 그중 일부 순서에서 틀린 결과가 나오는 상태다. 공유 자원, 쓰기, 여러 단계로 나뉜 작업이 함께 있을 때 생긴다. 대표적인 모양은 읽고 고치고 쓰기(`count++`)와 확인하고 행동하기(없으면 만들기)다.

### count++ 한 줄이 왜 스레드에서 안전하지 않나요?

CPU에서는 메모리에서 읽기, 레지스터에서 더하기, 메모리에 쓰기의 세 단계라서 그 사이에 다른 스레드가 끼어들 수 있기 때문이다. 두 스레드가 같은 값을 읽으면 한쪽의 증가가 덮인다. 최적화로 명령 하나가 되어도 `lock` 접두사가 없으면 원자적이지 않다. Go로 10만 번씩 두 번 올렸을 때 실제로 11만~16만 정도만 남았고, 원자적 연산이나 뮤텍스로 고친다.

### 자바스크립트는 싱글 스레드인데 경쟁 상태가 생기나요?

생긴다. 동기 코드 한 덩어리는 끊기지 않지만 `await`에서 함수가 멈추고 다른 콜백이 돌 수 있어서, `await`를 사이에 둔 확인과 행동은 틈이 된다. 늦게 온 옛 응답이 새 응답을 덮는 UI 버그, 중복 제출도 같은 모양이다. 프로세스 안이라면 `await` 전에 동기적으로 자리를 잡아 두면 되지만, 프로세스가 여러 개면 DB 제약이나 멱등성 키 같은 바깥 판정이 필요하다.

### 서버가 여러 대일 때 쿠폰 중복 사용은 어떻게 막나요?

DB의 고유 제약으로 판정을 저장소에 맡기는 게 가장 단단하다. `(coupon, user_id)`에 `UNIQUE`를 걸고 `INSERT ... ON CONFLICT DO NOTHING`의 결과 행 수로 성공 여부를 안다. 서버 메모리의 뮤텍스는 다른 서버의 요청을 막지 못한다. 제약으로 표현이 안 되는 규칙이면 행 잠금이나 분산 락을 쓴다.

### TOCTOU가 무엇이고 어떻게 막나요?

확인한 시점과 사용하는 시점 사이에 대상이 바뀌는 경쟁 상태다. 파일 경로를 검사한 뒤 같은 경로를 여는 사이에 공격자가 심볼릭 링크로 바꾸면 권한 있는 프로그램이 엉뚱한 파일을 쓰게 된다. 이름 대신 열린 파일 디스크립터로 확인하고(`open` 후 `fstat`), `O_NOFOLLOW`나 `openat2`의 `RESOLVE_NO_SYMLINKS`로 링크를 거부하고, 생성은 `O_CREAT | O_EXCL`로 한 번에 한다.

### 테스트에서는 안 나오는 경쟁 상태를 어떻게 찾나요?

먼저 코드에서 읽은 뒤 쓰기 전에 `await`, 네트워크 호출, 락 해제가 끼어 있는 구간을 찾는다. 메모리 경합은 Go의 `-race`나 ThreadSanitizer 같은 탐지기를 CI에서 돌려 잡는다. 결과가 맞게 나와도 경합을 잡아 주는 게 장점이다. DB나 파일을 사이에 둔 경쟁은 탐지기가 못 잡으니 같은 요청을 동시에 여러 개 보내는 테스트로 재현한다.

### 락 말고 경쟁 상태를 없애는 방법은 무엇이 있나요?

연산 자체를 원자적으로 만드는 방법(`UPDATE ... SET x = x + 1`, `INCR`, `Atomics.add`), 저장소의 제약에 맡기는 방법, 버전을 비교해 바뀌었으면 다시 하는 CAS나 낙관적 잠금, 키별로 한 명만 쓰게 구조를 바꾸는 방법이 있다. 충돌이 드물면 CAS가, 잦으면 락이나 단일 작성자가 낫다. 락은 기다림과 데드락 위험을 함께 가져온다.

### 트랜잭션으로 감싸면 경쟁 상태가 사라지나요?

자동으로 사라지지 않는다. PostgreSQL 기본값인 READ COMMITTED에서는 두 트랜잭션이 같은 값을 읽고 각자 계산해 쓰면 갱신 손실이 그대로 생긴다. 한 문장 안에서 계산하거나, `FOR UPDATE`로 읽을 때부터 잠그거나, 버전 열을 쓰거나, SERIALIZABLE로 올리고 직렬화 실패를 재시도해야 한다.
