  이 작업대가 영속성 컨텍스트다. 작업대에 올라온 데이터는 바뀐 걸 알아서 저장해 주지만, 작업대에서 내려온 데이터는 아무리 고쳐도 아무도 비교해 주지 않는다. 이 글은 데이터가 작업대에 오르고 내리는 순간, 사서가 장부에 옮겨 적는 시점, 아직 꺼내지 않은 책을 펼치려다 나는 에러까지 실제 SQL 로그로 따라간다.

## save()를 부르지 않았는데 UPDATE가 나간다

회원 이름을 바꾸는 메서드를 짰다. 조회하고, 필드를 바꾸고, 끝이다. `save()`를 부르는 걸 잊었다.

```java
tx.executeWithoutResult(s -> {
  Member m = em.find(Member.class, id);
  System.out.println("found " + m.name + ", changing name");
  m.name = "lee";
  System.out.println("method end (no save call)");
});
```

SQL 로그를 켜고 돌렸더니 UPDATE가 나갔다. 그것도 메서드 본문이 다 끝난 뒤에.

```text
SQL: select m1_0.id,m1_0.name from members m1_0 where m1_0.id=?
found kim, changing name
method end (no save call)
SQL: update members set name=? where id=?
```

반대 경우도 있다. 컨트롤러에서 받은 엔티티를 고치고 서비스에서 트랜잭션을 열었는데 아무것도 저장되지 않는다. 지연 로딩 필드를 읽다가 `LazyInitializationException`이 나기도 한다. 모두 같은 장치에서 나온다. JPA의 영속성 컨텍스트(persistence context)다.

이 글은 엔티티가 영속성 컨텍스트에 들어가고 나오는 상태, 1차 캐시와 동일성, 더티 체킹과 flush 시점, 쓰기 지연과 배치, 프록시와 지연 로딩, OSIV를 실제 SQL 로그로 따라간다. 지연 로딩이 쿼리 수백 개로 번지는 N+1 문제는 [N+1 쿼리 깊이 보기](/posts/n-plus-one-queries)에서 다뤘다. 엔티티 사이의 관계를 매핑하는 법은 [JPA 연관관계 매핑](/posts/jpa-entity-relationships)에서 이어 간다.

예제는 JDK 21, Spring Boot 4.1.1(Hibernate 7.4.5, Spring Data JPA 4.1.1), H2 메모리 DB로 돌렸다. 트랜잭션 경계를 눈에 보이게 하려고 `@Transactional` 대신 `TransactionTemplate`을 썼다. SQL은 이 설정으로 찍었다.

```properties
# 실행되는 SQL을 로거로 찍는다 (show-sql보다 이쪽을 권한다)
logging.level.org.hibernate.SQL=DEBUG
# 바인딩되는 파라미터 값까지 본다 (Hibernate 6 이상의 로거 이름)
logging.level.org.hibernate.orm.jdbc.bind=TRACE
```

`spring.jpa.show-sql=true`는 표준 출력에 바로 찍어서 로그 레벨이나 형식을 따르지 않는다. 운영 로그에 섞여도 끌 방법이 설정 파일뿐이다. 로거로 켜면 파라미터까지 볼 수 있다.

```text
SQL: update members set name=? where id=?
BIND: binding parameter (1:VARCHAR) <- [lee]
BIND: binding parameter (2:BIGINT) <- [1]
```

## 영속성 컨텍스트는 트랜잭션 동안의 작업 공간이다

영속성 컨텍스트는 "엔티티를 식별자로 관리하는 메모리 공간"이다. Hibernate에서는 `Session`이 그 구현이고, JPA 코드에서는 `EntityManager`로 다룬다. 스프링에서는 기본으로 트랜잭션 하나에 영속성 컨텍스트 하나가 열리고, 트랜잭션이 끝나면 닫힌다. 주입받은 `EntityManager`는 실제 객체가 아니라 "지금 스레드의 트랜잭션에 묶인 진짜 EntityManager"를 찾아 주는 프록시다. 트랜잭션 매니저가 커넥션을 스레드에 묶는 방식은 [@Transactional 깊게](/posts/spring-transactional-propagation)에서 로그로 봤다.

이 공간이 하는 일은 넷이다.

- 같은 id의 엔티티는 한 트랜잭션 안에서 같은 객체로 돌려준다(1차 캐시).
- 처음 읽어 온 상태를 스냅숏으로 보관하고, 끝날 때 비교해 바뀐 것을 UPDATE한다(더티 체킹).
- INSERT, UPDATE, DELETE를 바로 보내지 않고 모았다가 flush 때 보낸다(쓰기 지연).
- 연관된 엔티티를 쓸 때 가져온다(지연 로딩).

## 엔티티의 네 가지 상태

엔티티 객체는 영속성 컨텍스트와의 관계에 따라 상태가 넷이다. `new`로 막 만든 객체는 비영속(transient)이다. 컨텍스트는 이 객체를 모른다. `persist()`하거나 `find()`로 읽어 오면 영속(managed)이 된다. 컨텍스트가 추적하는 상태다. 트랜잭션이 끝나 컨텍스트가 닫히거나 `detach()`, `clear()`를 하면 준영속(detached)이 된다. id는 있지만 아무도 추적하지 않는다. `remove()`하면 삭제(removed) 상태가 되고, flush 때 DELETE가 나간다.

아래 그림이 상태와 그 사이를 오가는 메서드다. 화살표를 따라 점이 흐른다.

상태를 하나씩 바꿔 가며 로그를 찍었다. 회원 하나를 만들어 저장하고, 트랜잭션이 끝난 뒤 그 객체를 고치고, `merge()`했다.

```java
Member t = new Member("choi");                           // 비영속
Member detached = tx.execute(s -> { em.persist(t); return t; });  // 영속 → 트랜잭션 끝나면 준영속
tx.executeWithoutResult(s -> {
  System.out.println("contains detached? " + em.contains(detached));
  detached.name = "changed-detached";                    // 준영속을 고친다
});
tx.executeWithoutResult(s -> {
  Member merged = em.merge(detached);                    // 다시 영속으로
  System.out.println("merged == detached ? " + (merged == detached));
});
```

```text
transient contains? -> (no tx) id=null
SQL: select next value for members_seq
after persist id=2 contains=true
SQL: insert into members (name,id) values (?,?)
tx ended
contains detached? false
changed detached, method end
SQL: select m1_0.id,m1_0.name from members m1_0 where m1_0.id=?
merged == detached ? false, contains merged=true
SQL: update members set name=? where id=?
SQL: select m1_0.id,m1_0.name from members m1_0 where m1_0.id=?
removed, contains=false
SQL: delete from members where id=?
```

읽을 곳이 몇 군데 있다.

- `persist()` 직후 id가 2로 채워졌지만 INSERT는 아직 없다. 시퀀스에서 번호만 받아 왔다. INSERT는 트랜잭션이 끝날 때 나갔다.
- 준영속 객체를 고친 두 번째 트랜잭션에서는 SQL이 하나도 나가지 않았다. 컨텍스트가 그 객체를 모르니 비교할 스냅숏도 없다. "컨트롤러에서 받은 엔티티를 고쳤는데 저장이 안 된다"의 정체가 이것이다.
- `merge()`는 준영속 객체를 영속으로 바꾸지 않는다. 같은 id를 DB에서 읽어 새 영속 객체를 만들고, 준영속 객체의 값을 그 위에 복사한 뒤, 그 영속 객체를 돌려준다. `merged == detached`가 `false`다. merge 뒤에도 원래 `detached`를 계속 고치면 저장되지 않는다. 돌려받은 객체를 써야 한다.

Spring Data의 `save()`가 이 둘 사이에서 고른다. `SimpleJpaRepository.save()`는 엔티티가 새것이면 `persist()`, 아니면 `merge()`를 부른다. 새것인지는 기본으로 id가 `null`인지(원시 타입이면 0인지)로 판단한다. 그래서 id를 직접 넣는 엔티티(주문 번호를 앱에서 만드는 경우)는 `save()`할 때마다 `merge()`로 가서 SELECT부터 날린다. 이럴 때는 `Persistable`을 구현해 `isNew()`를 직접 알려 주거나, `@Version` 필드를 두어 판단하게 한다.

## 같은 id는 같은 객체다: 1차 캐시

한 트랜잭션에서 같은 회원을 세 번 꺼냈다. 두 번은 `find()`로, 한 번은 JPQL로.

```java
Member a = em.find(Member.class, id);
Member b = em.find(Member.class, id);
System.out.println("a == b : " + (a == b));
Member c = em.createQuery("select m from Member m where m.id = :id", Member.class)
    .setParameter("id", id).getSingleResult();
System.out.println("a == c : " + (a == c));
```

```text
SQL: select m1_0.id,m1_0.name from members m1_0 where m1_0.id=?
a == b : true
SQL: select m1_0.id,m1_0.name from members m1_0 where m1_0.id=?
a == c : true
```

두 번째 `find()`는 SQL 없이 1차 캐시에서 돌려줬다. JPQL은 달랐다. JPQL은 항상 DB에 SQL을 보낸다. 컨텍스트는 JPQL이 어떤 행을 돌려줄지 미리 알 수 없어서다. 그래도 결과 행의 id가 이미 컨텍스트에 있으면, 새 객체를 만들지 않고 이미 있는 객체를 돌려준다. 그래서 `a == c`도 `true`다. 이때 DB에서 막 읽어 온 값은 버린다. 다른 트랜잭션이 그 사이에 이름을 바꿨어도 `c.name`은 처음 읽은 값이다. 한 트랜잭션 안에서는 같은 행을 다시 읽어도 같은 값이 보이는, 반복 읽기 비슷한 성질이 앱 쪽에서 생긴다.

1차 캐시를 성능 캐시로 생각하면 안 된다. 트랜잭션 하나 동안만 살고, 다른 요청과 공유되지 않는다. 요청 사이에 공유하는 캐시는 2차 캐시나 Redis 같은 별도 캐시의 일이다. 1차 캐시의 진짜 쓸모는 "한 트랜잭션 안에서 같은 행은 객체 하나"라는 동일성 보장이다. 이게 있어야 더티 체킹이 성립한다. 같은 행을 가리키는 객체가 둘이면 어느 쪽 변경을 저장할지 정할 수 없다.

## 더티 체킹: 스냅숏과 비교한다

처음 장면의 UPDATE로 돌아간다. 컨텍스트는 엔티티를 영속 상태로 만들 때 그 순간의 필드 값을 복사해 스냅숏으로 둔다. flush 때 지금 값과 스냅숏을 필드마다 비교해, 다른 엔티티가 있으면 UPDATE를 만든다. 이걸 더티 체킹(dirty checking)이라고 한다. 아래 그림에서 다음을 누르며 UPDATE가 언제 만들어지는지 따라가 보자.

Hibernate의 기본 UPDATE는 바뀐 필드만이 아니라 모든 컬럼을 SET한다. 위 예에서는 컬럼이 `name` 하나뿐이라 그렇게 보이지 않았다. 컬럼이 열 개면 하나만 바꿔도 열 개를 다 쓴다. 엔티티마다 SQL 모양이 하나로 고정돼 미리 준비해 두고 재사용하기 좋아서다. 바뀐 컬럼만 쓰게 하려면 엔티티에 `@DynamicUpdate`를 붙인다. 컬럼이 아주 많거나, 다른 컬럼을 동시에 고치는 트랜잭션과 덮어쓰기 충돌을 줄이고 싶을 때 쓴다. 동시에 고칠 때 덮어쓰기를 확실히 막는 건 [낙관적 잠금](/posts/optimistic-locking)의 `@Version`이 할 일이다.

더티 체킹에는 비용이 있다. flush마다 컨텍스트의 모든 영속 엔티티를 필드 단위로 비교한다. 배치 작업에서 엔티티 10만 개를 한 트랜잭션에 읽어 두면 스냅숏 10만 벌이 메모리에 있고, flush 한 번이 수십만 번의 비교가 된다. 큰 작업은 일정 개수마다 `flush()`와 `clear()`로 컨텍스트를 비우거나, 바꿀 필요가 없는 조회는 읽기 전용 트랜잭션에서 한다. 읽기 전용이면 Hibernate가 스냅숏을 만들지 않는다.

## flush는 언제 일어나나

flush는 컨텍스트에 쌓인 변경을 SQL로 DB에 보내는 일이다. 커밋이 아니다. flush된 SQL도 롤백하면 사라진다. 기본 flush 모드(AUTO)에서 flush가 일어나는 시점은 셋이다.

1. 트랜잭션 커밋 직전.
2. `em.flush()`를 직접 부를 때.
3. JPQL이나 네이티브 쿼리를 실행하기 직전, 그 쿼리가 아직 보내지 않은 변경의 영향을 받을 수 있을 때.

세 번째가 헷갈린다. 이름을 바꾸고 아직 flush하지 않은 상태에서 그 이름으로 세는 JPQL을 날렸다.

```java
Member m = em.find(Member.class, id);
m.name = "park";
System.out.println("before JPQL");
long n = em.createQuery("select count(m) from Member m where m.name = 'park'", Long.class).getSingleResult();
System.out.println("count park = " + n);
```

```text
SQL: select m1_0.id,m1_0.name from members m1_0 where m1_0.id=?
before JPQL
SQL: update members set name=? where id=?
SQL: select count(m1_0.id) from members m1_0 where m1_0.name='park'
count park = 1
```

JPQL 직전에 UPDATE가 끼어들었다. flush하지 않았다면 DB에는 아직 `kim`이라 결과가 0이었을 것이다. Hibernate는 쿼리가 `members` 테이블을 건드리고 그 테이블에 보내지 않은 변경이 있으니 먼저 flush했다. 덕분에 결과는 맞다. 대신 "조회만 했는데 UPDATE 로그가 찍힌다"는 장면이 생기고, 그 UPDATE가 행 잠금을 잡은 채 다음 쿼리로 넘어간다. 트랜잭션 초반에 엔티티를 고치고 무거운 조회를 오래 하면 그 행이 조회 내내 잠겨 있다.

## 쓰기 지연과 배치

`persist()`도 SQL을 바로 보내지 않는다. 컨텍스트 안의 작업 목록(action queue)에 INSERT를 쌓아 두고 flush 때 한꺼번에 보낸다. 이걸 쓰기 지연(transactional write-behind)이라고 한다. 시퀀스 방식 엔티티 셋과 IDENTITY 방식 엔티티 둘을 차례로 저장했다.

```java
@Entity class Member { @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id; ... }
@Entity class LogLine { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) Long id; ... }

for (int i = 0; i < 3; i++) { em.persist(new Member("m" + i)); System.out.println("persist m" + i); }
for (int i = 0; i < 2; i++) { em.persist(new LogLine("l" + i)); System.out.println("persist log l" + i); }
System.out.println("method end");
```

```text
SQL: select next value for members_seq
persist m0
persist m1
persist m2
SQL: insert into members (name,id) values (?,?)
SQL: insert into members (name,id) values (?,?)
SQL: insert into members (name,id) values (?,?)
SQL: insert into logs (text,id) values (?,default)
persist log l0
SQL: insert into logs (text,id) values (?,default)
persist log l1
method end
```

`Member` 셋은 `persist` 로그가 먼저 찍히고 INSERT가 나중에 나갔다. 시퀀스 값은 한 번만 받아 왔다. Hibernate는 기본으로 시퀀스를 50씩 미리 할당받는다(`allocationSize=50`). `LogLine`은 `persist` 로그보다 INSERT가 먼저다. IDENTITY는 DB가 INSERT를 실행해야 id를 만들어 주니, id가 필요한 `persist()` 순간 바로 INSERT할 수밖에 없다. 그 INSERT 앞에 쌓여 있던 `Member` 셋도 순서를 지키려고 함께 밀려 나갔다.

여기서 IDENTITY의 대가가 하나 더 보인다. IDENTITY 엔티티는 `persist()` 순간 INSERT해야 하니 Hibernate가 INSERT 배치를 할 수 없다. MySQL에서 `AUTO_INCREMENT`에 맞춰 IDENTITY를 고르는 경우가 많은데, 대량 INSERT가 중요한 테이블이라면 이 차이를 알고 고른다. PostgreSQL이면 시퀀스를 쓰는 편이 배치에 유리하다. 여러 엔티티를 섞어 저장할 때는 `hibernate.order_inserts=true`로 같은 테이블의 INSERT를 모아야 배치가 끊기지 않는다.

## 벌크 UPDATE는 영속성 컨텍스트를 모른다

모든 회원 이름을 대문자로 바꾸는 쿼리를 Spring Data의 `@Modifying @Query`로 날렸다. 그 전에 회원 하나를 읽어 둔 상태다.

```java
interface MemberRepo extends JpaRepository<Member, Long> {
  @Modifying @Query("update Member m set m.name = upper(m.name)")
  int upperAll();
}

Member m = em.find(Member.class, id);
int n = members.upperAll();
System.out.println("updated rows=" + n + ", in-memory name=" + m.name);
em.clear();
System.out.println("after clear name=" + em.find(Member.class, id).name);
```

```text
SQL: select m1_0.id,m1_0.name from members m1_0 where m1_0.id=?
SQL: update members m1_0 set name=upper(m1_0.name)
updated rows=1, in-memory name=kim
SQL: select m1_0.id,m1_0.name from members m1_0 where m1_0.id=?
after clear name=KIM
```

DB는 `KIM`인데 메모리의 객체는 `kim`이다. 벌크 쿼리는 영속성 컨텍스트를 거치지 않고 DB로 바로 가기 때문이다. 이 상태에서 `m`의 다른 필드를 고치면 더티 체킹이 모든 컬럼을 SET하면서 `name`을 다시 `kim`으로 덮어쓴다. 벌크 쿼리 뒤에는 컨텍스트를 비운다. `@Modifying(clearAutomatically = true)`가 쿼리 직후 `clear()`를 해 준다. 비우기 전에 보내지 않은 변경이 날아가지 않도록 `flushAutomatically = true`도 함께 쓴다.

## 프록시와 LazyInitializationException

`@ManyToOne(fetch = FetchType.LAZY)`로 둔 연관 필드나 `getReference()`는 진짜 엔티티 대신 프록시를 돌려준다. 프록시는 엔티티 클래스를 상속한 빈 껍데기로, id만 알고 있다가 다른 값을 처음 읽을 때 SELECT를 보내 자신을 채운다. 컬렉션 연관(`@OneToMany`)은 Hibernate의 지연 컬렉션 객체가 같은 일을 한다.

프록시를 꺼내 트랜잭션 안과 밖에서 써 봤다.

```java
Member ref = tx.execute(s -> {
  Member r = em.getReference(Member.class, id);
  System.out.println("ref class=" + r.getClass().getName());
  System.out.println("ref field id=" + r.id + ", getId()=" + r.getId());
  return r;
});
ref.getName();                                     // 트랜잭션 밖
Member viaFind = tx.execute(s -> em.find(Member.class, id));
viaFind.getOrders().size();                        // 트랜잭션 밖에서 지연 컬렉션
```

```text
ref class=demo.jpa.Member$HibernateProxy
ref field id=null, getId()=1
org.hibernate.LazyInitializationException: Could not initialize proxy [demo.jpa.Member#1] - no session
SQL: select m1_0.id,m1_0.name from members m1_0 where m1_0.id=?
org.hibernate.LazyInitializationException: Cannot lazily initialize collection of role 'demo.jpa.Member.orders' with key '1' (no session)
```

첫 줄의 클래스 이름이 `Member$HibernateProxy`다. 둘째 줄이 의외다. 필드를 직접 읽은 `r.id`는 `null`이고, 메서드로 읽은 `getId()`는 1이다. 프록시는 메서드 호출을 가로채 진짜 객체로 넘기는 방식이라, 프록시 객체 자신의 필드는 비어 있다. 같은 패키지 안에서 필드를 직접 읽는 코드, 특히 `equals()`에서 `other.id`를 읽는 코드가 이 함정에 빠진다. 이 이야기는 [JPA 연관관계 매핑](/posts/jpa-entity-relationships)의 equals 절에서 다시 본다.

트랜잭션이 끝난 뒤 프록시에서 이름을 읽으면 `LazyInitializationException`이 난다. SELECT를 보낼 영속성 컨텍스트(세션)가 이미 닫혔다. 컬렉션도 같다. 고치는 방법은 세 갈래다.

- 트랜잭션 안에서 필요한 걸 다 읽는다. 서비스가 엔티티 대신 화면에 필요한 값만 담은 DTO를 돌려주면 경계가 분명해진다.
- 처음부터 함께 가져온다. JPQL의 `join fetch`나 `@EntityGraph`로 한 쿼리에 붙여 읽는다. 어떤 걸 고를지는 N+1 글에서 다뤘다.
- 영속성 컨텍스트를 요청 끝까지 열어 둔다. 이게 다음 절의 OSIV다.

`FetchType.EAGER`로 바꾸는 건 답이 아니다. 그 연관을 쓰지 않는 모든 조회에서도 끌려오고, JPQL에서는 결과마다 추가 쿼리가 나가 N+1이 생긴다.

## OSIV를 끌지 말지

Spring Boot는 JPA를 쓰면 OSIV(Open Session In View)를 기본으로 켠다. 앱을 띄우면 이 경고가 나온다.

```text
WARN ... JpaBaseConfiguration$JpaWebConfiguration : spring.jpa.open-in-view is enabled by default. Therefore, database queries may be performed during view rendering. Explicitly configure spring.jpa.open-in-view to disable this warning
```

OSIV는 인터셉터 하나(`OpenEntityManagerInViewInterceptor`)로 요청이 시작될 때 영속성 컨텍스트를 열고 응답이 끝날 때 닫는다. 트랜잭션은 서비스에서 끝나도 컨텍스트는 살아 있으니, 컨트롤러나 JSON 직렬화 중에 지연 로딩이 동작한다. 트랜잭션 없이 주문의 회원 이름을 읽는 컨트롤러로 비교했다.

```java
@GetMapping("/orders/{id}/member-name")
String memberName(@PathVariable long id) {
  Order o = orders.findById(id).orElseThrow();   // 리포지토리 안에서만 트랜잭션
  return o.getMember().getName();               // 트랜잭션 밖에서 지연 로딩
}
```

```text
# spring.jpa.open-in-view=true (기본)
HTTP/1.1 200
kim
SQL: select o1_0.id,o1_0.member_id,o1_0.status from orders o1_0 where o1_0.id=?
SQL: select m1_0.id,m1_0.name from members m1_0 where m1_0.id=?

# spring.jpa.open-in-view=false
HTTP/1.1 500
SQL: select o1_0.id,o1_0.member_id,o1_0.status from orders o1_0 where o1_0.id=?
org.hibernate.LazyInitializationException: Could not initialize proxy [demo.jpa.Member#1] - no session
```

켜 두면 편하다. 대신 대가가 있다.

- 커넥션을 요청 끝까지 쥘 수 있다. 컨텍스트가 지연 로딩을 위해 커넥션을 잡으면 응답을 다 쓸 때까지 놓지 않는다. 컨트롤러에서 외부 API를 부르거나 큰 응답을 천천히 내보내면, 그동안 DB 커넥션이 묶인다. 트랜잭션 안의 외부 호출이 풀을 고갈시킨 실험과 같은 그림이 트랜잭션 밖에서도 생긴다.
- 쿼리가 어디서 나가는지 흐려진다. JSON 직렬화 중에 연관을 따라가며 쿼리가 나가 N+1이 컨트롤러 밖에서 생긴다. 직렬화 대상에 양방향 연관이 있으면 끝없이 따라간다.
- 트랜잭션 밖에서 엔티티를 고쳐도 저장되지 않는데, 영속 상태처럼 보여서 헷갈린다. 그 뒤에 다른 트랜잭션이 열리면 그때 flush되어 엉뚱한 곳에서 저장되기도 한다.

API 서버라면 끄고 시작하는 쪽을 권한다. 서비스가 트랜잭션 안에서 DTO를 만들어 돌려주면 OSIV가 할 일이 없다. 이미 켜진 채로 운영 중인 서비스를 끄면 숨어 있던 지연 로딩이 `LazyInitializationException`으로 한꺼번에 드러난다. 통합 테스트를 `open-in-view=false`로 먼저 돌려 터지는 곳을 찾고, 그 화면들을 fetch join이나 DTO로 바꾼 뒤 끈다.

## 더티 체킹을 직접 만들어 본다

flush가 하는 비교를 함수로 옮겨 보자. `flush(snapshot, current, dynamicUpdate)`의 `snapshot`과 `current`는 id에서 필드 객체로 가는 맵이다. `snapshot`에 있는 엔티티마다 `current`와 비교해, 값이 다르면 `"update members set name=?, grade=? where id=1"` 형식의 문자열을 만든다. `dynamicUpdate`가 `false`면 모든 컬럼을, `true`면 바뀐 컬럼만 SET한다. `current`에서 사라진 엔티티는 `remove()`된 것으로 보고 `"delete from members where id=2"`를 만든다. Hibernate처럼 UPDATE를 먼저, DELETE를 나중에 둔다. 스냅숏에 없는 엔티티는 이 함수가 다루지 않는다.

실제 Hibernate는 여기에 INSERT, 컬렉션 변경, 외래 키 순서 맞추기가 더해진다. 그래도 뼈대는 같다. 비교할 스냅숏이 있는 엔티티만 저장된다.

## 작업 공간이라는 한 가지 생각

영속성 컨텍스트는 트랜잭션 동안 엔티티를 id로 하나씩 들고 있는 작업 공간이다. 그 안에 있는 엔티티는 스냅숏과 비교되어 바뀐 만큼 저장되고, 밖으로 나온 엔티티는 고쳐도 아무도 보지 않는다. SQL은 바로 나가지 않고 flush 때 모여 나가며, JPQL 앞에서 끼어들기도 한다. 벌크 쿼리는 이 공간을 건너뛰고, 지연 로딩은 공간이 닫히면 실패한다. "이 코드가 실행될 때 컨텍스트가 열려 있고, 이 엔티티가 그 안에 있나"를 물으면 대부분의 이상한 동작이 설명된다. 다음 글 [JPA 연관관계 매핑](/posts/jpa-entity-relationships)에서는 엔티티 둘이 서로를 가리킬 때 어느 쪽이 외래 키를 쓰는지 본다.

## 면접에서 나올 만한 질문

### 영속성 컨텍스트란 무엇이고 왜 필요한가요?

엔티티를 식별자로 관리하는 트랜잭션 범위의 메모리 공간이다. 스프링에서는 기본으로 트랜잭션 하나에 하나씩 열린다. 한 트랜잭션 안에서 같은 id는 같은 객체로 돌려주고, 처음 읽은 상태를 스냅숏으로 두었다가 바뀐 것을 UPDATE하며, 쓰기를 모아 flush 때 보낸다. 객체를 고치는 것만으로 DB에 반영되는 프로그래밍 모델이 이 공간 덕분에 가능하다.

### 엔티티의 생명주기 상태를 설명해 주세요.

`new`로 만든 비영속, `persist`나 조회로 컨텍스트가 추적하는 영속, 컨텍스트가 닫히거나 `detach`된 준영속, `remove`된 삭제 상태가 있다. 영속 상태만 더티 체킹 대상이라, 준영속 엔티티를 고치면 저장되지 않는다. `merge`는 준영속 객체를 영속으로 바꾸는 게 아니라 값을 복사한 새 영속 객체를 돌려주므로, 돌려받은 객체를 써야 한다.

### save()를 부르지 않았는데 UPDATE가 나가는 이유는 무엇인가요?

더티 체킹 때문이다. 영속 엔티티는 읽어 올 때 스냅숏이 함께 저장되고, 커밋 직전 flush에서 지금 값과 비교해 달라진 엔티티의 UPDATE를 만든다. Hibernate 기본은 모든 컬럼을 SET하고, `@DynamicUpdate`를 붙이면 바뀐 컬럼만 쓴다. 엔티티가 많으면 이 비교가 비싸서 큰 작업은 `flush`와 `clear`로 나눈다.

### flush는 언제 일어나고 커밋과 무엇이 다른가요?

flush는 쌓인 변경을 SQL로 DB에 보내는 것이고, 커밋은 그걸 확정하는 것이다. flush된 SQL도 롤백하면 사라진다. 기본 AUTO 모드에서는 커밋 직전, `flush()`를 직접 부를 때, 그리고 보내지 않은 변경에 영향받을 JPQL·네이티브 쿼리 직전에 일어난다. 그래서 조회만 했는데 UPDATE가 먼저 찍히는 장면이 생긴다.

### IDENTITY 전략을 쓰면 배치 INSERT가 안 되는 이유는 무엇인가요?

IDENTITY는 DB가 INSERT를 실행해야 id를 만들어 준다. 영속 상태가 되려면 id가 있어야 하니 Hibernate는 `persist` 순간 바로 INSERT하고, 쓰기 지연과 JDBC 배치를 쓸 수 없다. 시퀀스 전략은 번호를 미리 할당받아 두고 INSERT를 flush 때 모아 `hibernate.jdbc.batch_size`로 묶을 수 있다.

### LazyInitializationException은 왜 나고 어떻게 해결하나요?

지연 로딩 프록시나 컬렉션을 영속성 컨텍스트가 닫힌 뒤에 처음 읽으면, SELECT를 보낼 세션이 없어서 난다. 트랜잭션 안에서 필요한 값을 다 읽어 DTO로 돌려주거나, fetch join이나 `@EntityGraph`로 함께 가져온다. `EAGER`로 바꾸면 쓰지 않는 조회에서도 끌려오고 JPQL에서 N+1이 생겨서 해결책이 아니다.

### OSIV는 무엇이고 끄는 게 좋은가요?

요청 시작부터 응답이 끝날 때까지 영속성 컨텍스트를 열어 두어 컨트롤러나 직렬화 중에도 지연 로딩이 되게 하는 장치로, Spring Boot는 기본으로 켠다. 편한 대신 커넥션을 응답 끝까지 쥘 수 있고, 쿼리가 직렬화 중에 흩어져 나가 N+1이 숨는다. API 서버는 끄고 서비스에서 DTO를 만들어 돌려주는 구조를 권한다. 운영 중에 끌 때는 테스트에서 먼저 꺼서 숨은 지연 로딩을 찾는다.

### 벌크 UPDATE 뒤에 주의할 점은 무엇인가요?

JPQL 벌크 UPDATE·DELETE는 영속성 컨텍스트를 거치지 않고 DB로 바로 가서, 이미 읽어 둔 엔티티는 옛값을 들고 있다. 그 상태에서 다른 필드를 고치면 더티 체킹이 옛값으로 덮어쓸 수 있다. 벌크 쿼리 뒤에는 컨텍스트를 비우고, Spring Data에서는 `@Modifying(clearAutomatically = true, flushAutomatically = true)`를 쓴다.
