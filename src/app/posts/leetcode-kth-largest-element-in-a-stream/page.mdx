[Kth Largest Element in a Stream](https://leetcode.com/problems/kth-largest-element-in-a-stream/)은 LeetCode 703번이고 난이도는 Easy다. 숫자가 하나씩 계속 들어오고, 들어올 때마다 "지금까지 들어온 수 중 k번째로 큰 값"을 답한다. 게임 순위표에서 "커트라인 점수"를 실시간으로 보여 주는 것과 같은 일이다.

같은 질문을 배열 하나에 한 번만 던지는 문제가 [Kth Largest Element in an Array](/posts/leetcode-kth-largest-element-in-an-array)다. 그 글에서는 퀵셀렉트가 힙과 겨뤘지만, 여기서는 값이 계속 들어와서 사정이 다르다. 이 글은 매번 정렬하기, 정렬된 배열에 끼워 넣기, 위쪽 k개만 정렬해 두기, 크기 k인 최소 힙, 값의 범위를 이용한 개수 칸까지 다섯 풀이를 본다. 힙의 기본 동작과 "상위 k개만 남기기"의 일반론은 [힙 글](/posts/ds-heap#상위-k개만-남기기)에 있어서, 여기서는 스트림이라는 조건이 무엇을 바꾸는지에 집중한다. 코드는 Node.js 22, Python 3.13, Java 21에서 돌렸다.

## 점수가 들어올 때마다 커트라인을 묻는다

`KthLargest` 클래스를 만든다.

- `KthLargest(k, nums)`: k와 처음부터 있던 수들의 배열 `nums`로 만든다.
- `add(val)`: `val`을 넣고, 지금까지의 모든 수 중 k번째로 큰 값을 돌려준다.

"k번째로 큰 값"은 큰 순서로 줄을 세웠을 때 k번째 자리의 값이다. 같은 값이 여러 개면 각각 한 자리씩 차지한다. 예를 들어 `[8, 8, 5]`에서 2번째로 큰 값은 8이다.

풀이 선택에 영향을 주는 제약은 이렇다.

- `nums`의 길이와 `add` 호출 수가 각각 최대 10^4다. 전체 값은 최대 2 × 10^4개다.
- k는 1 이상 10^4 이하다. 처음 `nums`가 k개보다 하나 적을 수 있다. 그래도 `add`를 부를 때는 값이 k개 이상 모여 있다고 보장한다.
- 값은 -10^4 이상 10^4 이하다. 범위가 좁다는 사실은 마지막 풀이에서 쓴다.

두 번째 줄이 은근히 중요하다. 처음에는 값이 k개가 안 될 수 있다는 뜻이고, 이걸 놓치면 틀리는 코드가 나온다. 뒤에서 실제로 틀리는 예를 본다.

## 손으로 3등을 지켜 본다

이 글 내내 쓰는 예시다. k는 3이고, 처음 수는 `[5, 1, 8, 3]`이다. 그다음 4, 9, 2, 7, 10을 차례로 넣는다.

```text
넣은 값   큰 순서로 세운 전체            3번째
(처음)    8 5 3 1                      3
4         8 5 4 3 1                    4
9         9 8 5 4 3 1                  5
2         9 8 5 4 3 2 1                5
7         9 8 7 5 4 3 2 1              7
10        10 9 8 7 5 4 3 2 1           8
```

`add`의 답은 차례로 4, 5, 5, 7, 8이다.

표를 다시 보면 3번째 값을 정할 때 쓰인 건 늘 앞의 세 칸뿐이었다. 4번째 이후로 밀려난 값(3, 2, 1 같은)은 다시는 앞 세 칸에 들어오지 못한다. 값이 들어오기만 하고 빠지지 않으니, 한 번 3등 밖으로 밀린 값은 영영 3등 안에 못 든다. 이 관찰이 이 문제의 모든 빠른 풀이를 떠받친다. 그 전에 느린 풀이부터 본다.

## 들어올 때마다 전부 다시 줄 세운다

가장 먼저 떠오르는 방법이다. 값을 배열에 모두 쌓아 두고, `add`마다 큰 순서로 정렬해 k번째를 읽는다.

```js
class KthLargest {
  constructor(k, nums) {
    this.k = k;
    this.a = [...nums];
  }
  add(val) {
    this.a.push(val);
    const b = [...this.a].sort((x, y) => y - x); // 큰 순서로 전부 정렬
    return b[this.k - 1];                         // k번째는 인덱스 k - 1
  }
}
```

`add` 한 번에 O(n log n)이고, n은 지금까지 들어온 값의 수다. 처음 1만 개에 1만 번을 넣으면 정렬 1만 번이 2만 개 근처 배열에서 돈다. 실제로 재 보니 43.6초가 걸렸다. 맞기는 하지만 시간 초과다.

`sort`에 비교 함수를 꼭 줘야 한다. `sort()`만 쓰면 값을 문자열로 바꿔 비교해서 10이 9보다 앞에 오고, -1이 -10보다 앞에 온다. 값에 음수와 두 자리 수가 섞이면 답이 틀린다.

## 정렬된 줄에 끼워 넣는다

매번 처음부터 정렬하는 건 낭비다. 배열을 늘 오름차순으로 들고 있으면 새 값은 들어갈 자리만 찾아 끼우면 된다. 자리는 [이분 탐색](/posts/binary-search)으로 찾는다. k번째로 큰 값은 오름차순 배열의 뒤에서 k번째 칸, 즉 인덱스 `length - k`다.

```js
class KthLargest {
  constructor(k, nums) {
    this.k = k;
    this.a = [...nums].sort((x, y) => x - y); // 오름차순
  }
  add(val) {
    const a = this.a;
    let lo = 0, hi = a.length;
    while (lo < hi) {                // val 이상인 첫 자리를 찾는다
      const m = (lo + hi) >> 1;
      if (a[m] < val) lo = m + 1;
      else hi = m;
    }
    a.splice(lo, 0, val);            // 뒤의 값을 한 칸씩 밀고 끼운다
    return a[a.length - this.k];
  }
}
```

자리 찾기는 O(log n)이지만 `splice`가 뒤의 값을 밀어서 `add`는 O(n)이다. 제약 크기에서는 13.7ms로 충분히 빨랐다. 메모리를 통째로 옮기는 작업이 빠르기 때문이다. 하지만 `add`를 20만 번으로 늘렸더니 5.9초가 걸렸다. 그리고 이 풀이는 밀려난 값까지 전부 들고 있다. 앞에서 본 관찰대로라면 그 값들은 다시 쓸 일이 없다.

## 위쪽 k개만 줄에 남긴다

그래서 배열에 k개만 남긴다. 오름차순으로 k개를 들고 있으면 맨 앞 `a[0]`이 그 k개 중 가장 작은 값이고, 그게 바로 k번째로 큰 값이다.

새 값이 `a[0]`보다 작거나 같으면 k등 안에 못 드니 버린다. 크면 제자리에 끼우고, 길이가 k를 넘으면 맨 앞을 뺀다.

```js
class KthLargest {
  constructor(k, nums) {
    this.k = k;
    this.a = [];                     // 오름차순, 길이는 최대 k
    for (const x of nums) this.insert(x);
  }
  insert(val) {
    const a = this.a;
    if (a.length === this.k && val <= a[0]) return; // k등 밖이면 버린다
    let lo = 0, hi = a.length;
    while (lo < hi) {
      const m = (lo + hi) >> 1;
      if (a[m] < val) lo = m + 1;
      else hi = m;
    }
    a.splice(lo, 0, val);
    if (a.length > this.k) a.shift(); // k + 1개가 되면 가장 작은 값을 뺀다
  }
  add(val) {
    this.insert(val);
    return this.a[0];
  }
}
```

공간이 O(k)로 줄었고, 버려지는 값은 비교 한 번에 끝난다. 값이 무작위로 들어오면 대부분 버려져서 20만 번 넣기가 9.8ms였다.

문제는 끼울 때다. `splice`와 `shift`가 k칸을 밀어서 최악에 `add` 한 번이 O(k)다. 값이 계속 커지는 입력이 최악이다. 새 값마다 맨 끝에 들어가고 맨 앞이 빠져서 매번 k칸이 움직인다. k를 10만으로 두고 커지는 값 10만 개를 넣었더니 29초가 걸렸다. k가 작으면 좋은 풀이지만, k가 크면 다음 풀이가 필요하다.

## 문지기 하나만 보는 최소 힙

위 풀이에서 실제로 필요한 연산은 두 가지뿐이었다. 가장 작은 값을 보기, 그리고 가장 작은 값을 빼고 새 값을 넣기. 나머지 k - 1개의 순서는 아무도 묻지 않는다. 이 두 연산만 빠른 자료구조가 최소 힙이다. 맨 위 보기는 O(1), 넣기와 빼기는 O(log k)다. 힙이 배열로 트리를 표현하는 방식은 [힙 글](/posts/ds-heap#배열-하나에-트리를-접어-넣는다)에 있다.

힙 맨 위는 "k등 안에 드는 값 중 가장 작은 값"이라서, 새 값이 k등 안에 들어올 수 있는지 판정하는 문지기 노릇을 한다.

1. 힙에 k개가 안 차 있으면 새 값을 무조건 넣는다.
2. 다 차 있으면 새 값을 맨 위와 비교한다. 새 값이 더 크면 맨 위를 빼고 새 값을 넣는다. 작거나 같으면 버린다.
3. 맨 위가 답이다.

```js
class MinHeap {
  constructor() { this.a = []; }
  get size() { return this.a.length; }
  peek() { return this.a[0]; }
  push(x) {
    const a = this.a;
    a.push(x);
    let i = a.length - 1;
    while (i > 0) {                          // 부모보다 작으면 올라간다
      const p = (i - 1) >> 1;
      if (a[p] <= a[i]) break;
      [a[p], a[i]] = [a[i], a[p]];
      i = p;
    }
  }
  pop() {
    const a = this.a, top = a[0], last = a.pop();
    if (a.length) {
      a[0] = last;                           // 마지막 값을 맨 위로 올리고
      let i = 0;
      for (;;) {                             // 더 작은 자식과 바꾸며 내려간다
        const l = 2 * i + 1, r = l + 1;
        let m = i;
        if (l < a.length && a[l] < a[m]) m = l;
        if (r < a.length && a[r] < a[m]) m = r;
        if (m === i) break;
        [a[m], a[i]] = [a[i], a[m]];
        i = m;
      }
    }
    return top;
  }
}

class KthLargest {
  constructor(k, nums) {
    this.k = k;
    this.h = new MinHeap();
    for (const x of nums) this.add(x);       // 처음 수도 같은 규칙으로 넣는다
  }
  add(val) {
    const h = this.h;
    if (h.size < this.k) h.push(val);        // 1. 덜 찼으면 무조건 넣는다
    else if (val > h.peek()) {               // 2. 문지기보다 크면 교체
      h.pop();
      h.push(val);
    }
    return h.peek();                         // 3. 맨 위가 k번째로 큰 값
  }
}
```

예시를 넣으며 힙의 배열 상태를 찍어 봤다. 힙 배열은 정렬된 순서가 아니라 "부모가 자식보다 작거나 같다"만 지킨 순서라서 `[3, 8, 5]`처럼 보인다.

```text
넣은 값  힙 배열      맨 위(답)
5        [5]          5
1        [1,5]        1
8        [1,5,8]      1
3        [3,8,5]      3     ← 처음 nums 끝. 1이 밀려났다
4        [4,8,5]      4
9        [5,8,9]      5
2        [5,8,9]      5     ← 문지기 5보다 작아서 버렸다
7        [7,9,8]      7
10       [8,9,10]     8
```

`add` 한 번은 힙 연산 최대 두 번이라 O(log k)다. 생성자는 n개를 하나씩 넣어 O(n log k)다. 공간은 힙의 k칸이라 O(k)다. 앞에서 29초 걸린 "k = 10만, 계속 커지는 값 10만 개" 입력에서 74ms였다. 무작위 값 20만 번은 17ms로, 위쪽 k개 정렬 풀이보다 조금 느렸다. 값 대부분이 비교 한 번에 버려지는 입력에서는 두 풀이가 거의 같고, 끼울 일이 많아질수록 힙이 이긴다.

### 왜 최대 힙이 아니라 최소 힙인가

"큰 값을 찾는데 최소 힙"이 처음엔 어색하다. 나도 처음엔 최대 힙에 모두 넣고 k번 꺼내는 쪽을 먼저 떠올렸다. 그러면 `add`마다 k번 꺼냈다가 다시 넣어야 해서 O(k log n)이고, 밀려난 값까지 모두 들고 있어 공간도 O(n)이다.

최소 힙을 쓰는 이유는 답이 "k개 안에서 가장 작은 값"이기 때문이다. k등 안의 값 중 쫓겨날 후보는 늘 가장 작은 값 하나다. 쫓겨날 후보를 맨 위에 두는 힙이 최소 힙이다. [힙 글](/posts/ds-heap#상위-k개만-남기기)에서 상위 k개를 구할 때 최소 힙을 쓰는 것과 같은 이유다.

### 처음 nums를 한꺼번에 정리하는 방법

생성자에서 n개를 하나씩 넣으면 O(n log k)다. 다른 방법도 있다. n개를 한꺼번에 힙으로 만들고(heapify, O(n)) n - k번 꺼내면 O(n + (n - k) log n)이다. Python의 `heapq.heapify`가 이 방식이다. heapify가 왜 O(n)인지는 [힙 글](/posts/ds-heap#한꺼번에-만들면-on이다)에 있다.

n이 k보다 훨씬 크면 하나씩 넣는 쪽이 낫다. 버려지는 값은 비교만 하고 지나가서 힙이 k칸을 넘지 않기 때문이다. n과 k가 비슷하면 heapify가 조금 유리하다. 이 문제의 크기에서는 어느 쪽이든 차이가 거의 없다.

## 값의 범위가 좁다는 점을 쓰는 개수 칸

값이 -10^4 이상 10^4 이하라는 제약을 다시 본다. 가능한 값이 20001가지뿐이다. 그러면 값마다 몇 번 나왔는지 세는 칸을 만들 수 있다.

여기에 손으로 풀 때 본 관찰을 하나 더한다. 값이 빠지지 않으니 k번째로 큰 값은 절대 작아지지 않는다. 새 값이 들어오면 k번째 값은 그대로이거나 커진다. 그래서 "지금 답" 위치를 가리키는 손가락 `cur`를 하나 두고, 위로만 옮긴다.

- `ge`: `cur` 이상인 값의 개수.
- 손가락이 맞는 자리라면 `cur`보다 큰 값은 k개보다 적고, `cur` 이상인 값은 k개 이상이다.
- 새 값이 `cur` 이상이면 개수 칸을 늘리고 `ge`도 늘린다. `cur`보다 작은 값은 다시 답이 될 일이 없으니 세지도 않는다.
- `ge`에서 `cur` 칸 개수를 빼도 k개 이상이면 `cur`가 답이 아니다. `cur`를 한 칸 올린다. 이걸 조건이 깨질 때까지 반복한다.

```js
const OFF = 10000;                           // 값 -10000을 칸 0에 둔다
class KthLargest {
  constructor(k, nums) {
    this.k = k;
    this.cnt = new Int32Array(2 * OFF + 1);  // 값마다 개수
    this.cur = -OFF;                         // 손가락은 가장 작은 값에서 시작
    this.ge = 0;                             // cur 이상인 값의 개수
    for (const x of nums) this.add(x);
  }
  add(val) {
    if (val >= this.cur) {
      this.cnt[val + OFF]++;
      this.ge++;
    }
    while (this.ge - this.cnt[this.cur + OFF] >= this.k) { // cur보다 큰 값만으로 k개가 차면
      this.ge -= this.cnt[this.cur + OFF];
      this.cur++;                            // 손가락을 위로 옮긴다
    }
    return this.cur;
  }
}
```

값이 k개보다 적은 동안에는 손가락이 맨 아래에 머문다. 그때의 `cur`는 의미 없는 값이지만, 문제는 그 상태에서 답을 묻지 않는다.

그림에 20001칸은 안 들어가니 값이 0부터 9까지인 작은 경우로 줄였다. k는 2이고 3, 7, 5, 1, 8, 8을 차례로 넣는다. 칸 아래 숫자는 값이고, 손가락이 가리키는 칸이 지금 답이다.

손가락은 전체를 통틀어 최대 20001칸만 오른다. 그래서 `add` 한 번은 상각 O(1)이다. 상각은 "어떤 호출은 오래 걸려도 전체를 호출 수로 나누면 상수"라는 뜻이다. 전체 비용은 O(n + R)이고 R은 값의 범위 20001이다. 공간도 O(R)이다. 무작위 20만 번에서 9.5ms였다.

이 풀이는 값의 범위가 좁고 값이 빠지지 않는다는 두 조건에 기대고 있다. 범위가 10^9이면 칸을 만들 수 없고, 값을 지우는 연산이 생기면 손가락이 아래로도 움직여야 해서 상각 분석이 깨진다. 면접에서 "범위가 좁다면 더 빠르게 할 수 있나"로 이어질 때 꺼낼 카드다.

## 다섯 방법을 재 보니

| 풀이 | add | 공간 | 언제 고르나 |
|---|---|---|---|
| 매번 전체 정렬 | O(n log n) | O(n) | 답을 묻는 일이 한두 번뿐일 때 |
| 정렬된 배열에 끼우기 | O(n) | O(n) | 모든 값의 순서가 따로 필요할 때 |
| 위쪽 k개만 정렬 | O(k), 버리는 값은 O(1) | O(k) | k가 작고 코드를 짧게 쓰고 싶을 때 |
| 크기 k 최소 힙 | O(log k) | O(k) | 범위 제한이 없는 일반적인 답. 면접의 기본 |
| 개수 칸 + 손가락 | 상각 O(1) | O(R) | 값의 범위 R이 좁고 지우기가 없을 때 |

측정은 모두 같은 Node.js에서 했다. 제약 크기(처음 1만 개, `add` 1만 번)에서는 매번 정렬만 43.6초로 시간 초과였고, 나머지는 모두 14ms 아래였다. 차이는 크기를 키워야 드러난다. 무작위 값 20만 번에서는 끼우기가 5.9초로 떨어져 나갔다. k = 10만에 커지는 값 10만 개에서는 위쪽 k개 정렬이 29초, 힙이 74ms였다.

## Python의 heapreplace와 Java의 PriorityQueue

최소 힙 풀이를 옮긴다. Python은 처음 수를 heapify로 한꺼번에 정리했다.

```python
import heapq

class KthLargest:
    def __init__(self, k: int, nums: list[int]):
        self.k = k
        self.h = nums[:]            # 복사해서 쓴다
        heapq.heapify(self.h)       # O(n)에 최소 힙으로 만든다
        while len(self.h) > k:      # 작은 값부터 버려 k개만 남긴다
            heapq.heappop(self.h)

    def add(self, val: int) -> int:
        if len(self.h) < self.k:
            heapq.heappush(self.h, val)
        elif val > self.h[0]:
            heapq.heapreplace(self.h, val)  # 맨 위를 빼고 val을 넣는다. 한 번에 내려보낸다
        return self.h[0]

kl = KthLargest(3, [5, 1, 8, 3])
print([kl.add(v) for v in [4, 9, 2, 7, 10]])
kl2 = KthLargest(1, [])
print([kl2.add(v) for v in [-3, -5, 2]])
```

```text
[4, 5, 5, 7, 8]
[-3, -3, 2]
```

`heapq`는 최소 힙이라 부호를 바꿀 필요가 없다. `heapreplace`는 맨 위를 꺼내고 새 값을 넣는 일을 한 번의 내려보내기로 한다. `heappop` 뒤 `heappush`를 하는 것보다 일이 적다. 비슷한 이름의 `heappushpop`은 순서가 반대라서 먼저 넣고 꺼낸다. 새 값이 맨 위보다 작으면 새 값이 그대로 나온다. 그래서 `heappushpop`을 쓰면 `val > self.h[0]` 비교 없이도 맞는 결과가 나온다. 비교를 해 두면 버릴 값에서 힙을 아예 건드리지 않는다.

`nums[:]`로 복사한 데도 이유가 있다. 복사하지 않고 `heapify(nums)`를 하면 호출한 쪽의 리스트가 바뀐다. LeetCode에서는 상관없지만 실무 코드에서는 남의 리스트를 몰래 바꾸는 버그가 된다.

```java
import java.util.*;

class KthLargest {
    private final int k;
    private final PriorityQueue<Integer> h = new PriorityQueue<>(); // 최소 힙

    public KthLargest(int k, int[] nums) {
        this.k = k;
        for (int x : nums) add(x);
    }

    public int add(int val) {
        if (h.size() < k) h.offer(val);
        else if (val > h.peek()) {
            h.poll();
            h.offer(val);
        }
        return h.peek();
    }
}
```

```text
4 5 5 7 8
```

같은 예시를 넣은 `main`의 출력이다. Java의 `PriorityQueue`는 기본이 최소 힙이다. 최대 힙이 필요할 때만 `Collections.reverseOrder()`를 준다.

Java에서 조심할 곳은 `peek()`이 `int`가 아니라 `Integer`를 돌려준다는 점이다. `val > h.peek()`은 `Integer`가 `int`로 풀려서 괜찮다. 하지만 두 `Integer`를 `==`로 비교하면 값이 아니라 객체가 같은지를 본다. -128부터 127까지는 캐시된 객체를 써서 우연히 맞고, 그 밖에서는 틀린다. 실제로 `Integer a = 1000, b = 1000`에서 `a == b`는 `false`, `a.equals(b)`는 `true`였다. 힙의 맨 위를 다른 힙의 맨 위와 `==`로 비교하는 코드에서 자주 터진다.

## 힙이 덜 찬 순간을 놓치면 틀린다

### 크기 확인 없이 문지기와 비교한다

생성자에서는 크기를 챙기고 `add`에서는 바로 비교하는 코드가 흔하다.

```js
add(val) {
  if (val > this.h.peek()) {   // 힙이 k개보다 적을 때도 교체해 버린다
    this.h.pop();
    this.h.push(val);
  }
  return this.h.peek();
}
```

k가 3이고 처음 수가 `[5, 1]`이면 힙은 `[1, 5]`로 아직 덜 찼다. 여기에 3을 넣으면 3이 1보다 커서 1을 빼고 3을 넣는다. 힙은 `[3, 5]`가 되고 3을 답한다. 실제 세 값은 5, 3, 1이라 3번째로 큰 값은 1이다. 이어서 0을 넣으면 정답은 1인데 이 코드는 3을 답했다. 1이 사라진 채로 계속 틀린다. 덜 찼으면 무조건 넣는 분기가 꼭 있어야 한다.

### 최대 힙으로 착각해 맨 위를 답한다

최소 힙 대신 최대 힙을 만들면 맨 위가 가장 큰 값이라 k = 1일 때만 맞는다. 예시에서 k = 3이면 처음부터 8을 답한다. 언어마다 기본 힙이 다른 것이 원인이 되기도 한다. Java의 `PriorityQueue`와 Python의 `heapq`는 최소 힙이지만, C++의 `priority_queue`는 기본이 최대 힙이다.

### 같은 값을 하나로 친다

`[8, 8, 5]`에서 2번째로 큰 값은 8이다. 값을 `Set`에 넣어 중복을 없애고 순위를 매기면 5가 나온다. 이 문제의 순위는 값의 종류가 아니라 값의 개수로 센다. 힙 풀이는 같은 값을 따로 넣으니 자연스럽게 맞다. 교체 조건은 `val > peek`이든 `val >= peek`이든 답이 같다. 같은 값끼리 바꿔 넣어도 힙의 내용이 같기 때문이다. `>`를 쓰면 쓸데없는 교체를 하지 않는다.

### 생성자 안에서 add를 부르는 순서

JavaScript에서 생성자가 `this.add`를 부르려면 `this.k`와 `this.h`를 먼저 만들어야 한다. 순서를 바꾸면 `this.h`가 `undefined`라 바로 오류가 난다. 단순한 실수지만 면접 화이트보드에서 자주 보인다.

## 커트라인 문제를 비틀면

### k번째로 작은 값을 묻는다면

방향만 뒤집는다. 크기 k인 최대 힙을 두고, 새 값이 맨 위보다 작으면 교체한다. 맨 위는 "작은 쪽 k개 중 가장 큰 값"이다.

### 값을 지우는 연산이 생긴다면

힙은 맨 위가 아닌 값을 빨리 지우지 못한다. 그런데 지워진 값이 k등 안에 있었다면, 밀려났던 값이 다시 k등으로 올라와야 한다. 이미 버린 값이 필요해지니 크기 k 힙만으로는 안 된다. 모든 값을 순서대로 들고 있는 구조가 필요하다. Java의 `TreeMap`에 값과 개수를 담거나, 두 힙에 지연 삭제를 붙인다. 지연 삭제는 [Sliding Window Median](/posts/leetcode-sliding-window-median)에서 자세히 본다.

### k가 아니라 위쪽 k개 전부를 달라면

힙에 든 k개가 그 답이다. 큰 순서로 달라고 하면 힙을 복사해 정렬하거나 하나씩 꺼낸다. O(k log k)다. 순위표를 보여 주는 화면이라면 이 방식이다.

### 여러 서버에 값이 흩어져 들어온다면

서버마다 크기 k인 힙을 따로 두고, 물을 때 각 서버의 k개를 모아 다시 크기 k 힙으로 거른다. 어떤 서버의 k등 밖에 있는 값은 전체에서도 k등 안에 못 들기 때문에 정확하다. 서버가 m대면 모으는 값은 m × k개다.

### 중앙값을 계속 묻는다면

k가 고정이 아니라 "전체의 절반"으로 계속 바뀌는 셈이다. 크기 k인 힙 하나로는 안 되고, 작은 절반과 큰 절반을 두 힙에 나눠 담는다. [Find Median from Data Stream](/posts/leetcode-find-median-from-data-stream)이다.

같은 "상위 k개를 힙으로 거른다" 생각을 쓰는 문제로는 [K Closest Points to Origin](/posts/leetcode-k-closest-points-to-origin), [Top K Frequent Elements](/posts/leetcode-top-k-frequent-elements)가 있다. 맨 위 두 개를 계속 꺼내는 [Last Stone Weight](/posts/leetcode-last-stone-weight)는 같은 힙을 다르게 쓴다.

## 면접에서 나올 만한 질문

### 왜 크기 k인 최소 힙을 쓰나요?

답이 "큰 값 k개 중 가장 작은 값"이고, 새 값이 들어올 때 쫓겨날 후보도 그 가장 작은 값 하나이기 때문이다. 최소 힙은 그 값을 맨 위에 두어 O(1)에 보고 O(log k)에 바꾼다. k등 밖으로 밀려난 값은 값이 빠지지 않는 한 다시 들어올 수 없어서 버려도 된다. 그래서 공간도 O(k)로 끝난다.

### add 한 번의 시간 복잡도는 어떻게 되나요?

O(log k)다. 버릴 값이면 맨 위와 비교 한 번으로 끝나고, 교체할 값이면 꺼내기와 넣기를 한 번씩 한다. 전체 입력 크기 n이 아니라 k에만 기대므로 스트림이 아무리 길어져도 느려지지 않는다. 생성자는 처음 n개를 넣느라 O(n log k)다.

### 정렬된 배열로 위쪽 k개만 들고 있으면 안 되나요?

k가 작으면 괜찮다. 버리는 값은 비교 한 번이라 무작위 입력에서는 힙만큼 빠르다. 하지만 끼울 때 k칸을 밀어서 최악에 O(k)이고, 계속 커지는 값이 들어오면 매번 최악이 된다. k = 10만에서 실제로 29초와 74ms로 갈렸다.

### 처음 nums가 k개보다 적을 때 무엇을 조심하나요?

힙이 덜 찬 동안에는 비교 없이 무조건 넣어야 한다. 이 분기를 빼면 k = 3, 처음 `[5, 1]`에 3을 넣을 때 1을 쫓아내 버려서 답이 3으로 나온다. 정답은 1이다. 한 번 잃은 값은 되돌릴 수 없어서 그 뒤로도 계속 틀린다.

### 값의 범위가 좁다면 더 빠르게 할 수 있나요?

값마다 개수를 세는 칸을 두고, 답을 가리키는 손가락을 위로만 옮긴다. 값이 빠지지 않으니 k번째로 큰 값은 줄지 않아서 손가락이 아래로 갈 일이 없다. 손가락이 범위 전체를 한 번만 지나므로 `add`는 상각 O(1)이고 공간은 범위 크기만큼이다. 범위가 넓거나 지우기가 생기면 쓸 수 없다.

### 값을 지우는 연산이 추가되면 어떻게 하나요?

크기 k 힙은 밀려난 값을 버렸기 때문에 지우기를 감당하지 못한다. 지워진 값 대신 올라올 값이 이미 없기 때문이다. 모든 값을 순서대로 들고 있는 `TreeMap` 같은 균형 이진 탐색 트리로 바꾸거나, 두 힙으로 경계를 나누고 지연 삭제를 붙인다. 어느 쪽이든 연산은 O(log n)이고 공간은 O(n)이 된다.

### 배열에서 k번째로 큰 값을 한 번만 구하는 문제와는 무엇이 다른가요?

한 번만 구하면 퀵셀렉트가 평균 O(n)으로 가장 빠르다. 스트림에서는 값이 들어올 때마다 답해야 하는데, 퀵셀렉트는 매번 전체를 다시 나눠야 해서 쓸 수 없다. 이전 상태를 이어 쓸 수 있는 힙이 스트림에 맞는 이유다.
