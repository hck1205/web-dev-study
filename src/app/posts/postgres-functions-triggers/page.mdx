책 정보가 바뀐 순서대로 검색 색인을 다시 만드는 작업이 있다. `updated_at`이 마지막 실행 시각보다 큰 책만 가져가는 방식이다. 어느 날 가격이 바뀐 책이 검색 결과에 옛 가격으로 남아 있다는 문의가 왔다. 찾아보니 가격을 일괄로 바꾸는 배치 서비스가 `UPDATE books SET price = ...`만 하고 `updated_at`은 건드리지 않았다. API 서버 코드는 꼬박꼬박 `updated_at = now()`를 넣고 있었는데, 테이블을 고치는 프로그램이 하나 더 있다는 걸 아무도 생각하지 못했다.

"이 테이블을 고치면 반드시 이 일도 일어나야 한다"는 규칙을 각 서비스가 지키게 두면 언젠가 하나가 빠진다. PostgreSQL은 이런 규칙을 DB 안에 둘 수 있게 함수, 프로시저, 트리거를 제공한다. 이 글은 그 셋을 만들어 보고, 어디까지 DB에 맡기는 게 맞는지까지 본다. 기준은 Ubuntu 24.04의 PostgreSQL 16.15이고, 출력은 모두 실제로 돌린 결과다. 앞 글 [PostgreSQL다운 SQL](/posts/postgres-advanced-sql)의 서점 예제를 그대로 쓴다.

## updated_at이 멈춰 있는 책

시리즈의 `shop` 테이블(`users`, `books`, `orders`, `order_items`)에 `books.updated_at`을 더한다. 테이블을 만드는 SQL은 [앞 글의 첫 섹션](/posts/postgres-advanced-sql)과 같다.

```sql
SET timezone = 'Asia/Seoul';
ALTER TABLE books ADD COLUMN updated_at timestamptz NOT NULL DEFAULT now();
UPDATE books SET updated_at = '2026-10-01 09:00+09';     -- 모두 같은 시각에서 시작

-- API 서버: 잊지 않고 updated_at을 넣는다
UPDATE books SET price = 19000, updated_at = now() WHERE id = 1;
-- 배치 서비스: 잊었다
UPDATE books SET price = 27000 WHERE id = 2;

SELECT id, title, price, updated_at FROM books ORDER BY id;
```

```text
 id |        title        | price |          updated_at
----+---------------------+-------+-------------------------------
  1 | 데이터베이스 첫걸음 | 19000 | 2026-10-18 01:17:53.682102+09
  2 | SQL 레시피          | 27000 | 2026-10-01 09:00:00+09
  3 | PostgreSQL 인사이드 | 32000 | 2026-10-01 09:00:00+09
(3 rows)
```

2번 책은 가격이 바뀌었는데 `updated_at`은 10월 1일 그대로다. 이걸 트리거로 고치는 게 이 글의 목표지만, 트리거는 함수로 만들기 때문에 함수부터 본다.

## SQL로 쓰는 함수와 plpgsql로 쓰는 함수

함수는 두 가지 언어로 많이 쓴다. `LANGUAGE sql`은 SQL 문장 하나(또는 몇 개)를 이름 붙여 둔 것이다. 계산이 간단하면 이쪽이 낫다. 플래너가 함수 본문을 호출한 쿼리 안에 녹여 넣을(인라인) 수 있어서 함수 호출 비용이 거의 없다.

```sql
-- 부가세 10%를 더한 가격. 14부터는 본문을 RETURN으로 바로 쓸 수 있다
CREATE FUNCTION price_with_vat(price integer) RETURNS integer
LANGUAGE sql IMMUTABLE
RETURN price + price / 10;

SELECT title, price, price_with_vat(price) FROM books ORDER BY id;
```

```text
        title        | price | price_with_vat
---------------------+-------+----------------
 데이터베이스 첫걸음 | 19000 |          20900
 SQL 레시피          | 27000 |          29700
 PostgreSQL 인사이드 | 32000 |          35200
(3 rows)
```

행을 여러 개 돌려주는 함수는 `RETURNS TABLE(...)`이나 `RETURNS SETOF 테이블`로 만든다. FROM 절에서 테이블처럼 쓰고, 앞 글의 `LATERAL`과 함께 쓰면 회원마다 호출할 수도 있다.

```sql
CREATE FUNCTION user_orders(p_user_id bigint)
RETURNS TABLE (order_id bigint, status text, total integer)
LANGUAGE sql STABLE
BEGIN ATOMIC                          -- 14+: 만들 때 본문을 미리 해석해 둔다
  SELECT id, status, total FROM orders WHERE user_id = p_user_id ORDER BY id;
END;

SELECT * FROM user_orders(1);
SELECT u.name, o.* FROM users u CROSS JOIN LATERAL user_orders(u.id) o WHERE u.id = 2;
```

```text
 order_id |  status   | total
----------+-----------+-------
        1 | paid      | 18000
        2 | paid      | 57000
        4 | cancelled | 32000
        6 | paid      | 25000
(4 rows)

 name | order_id | status  | total
------+----------+---------+-------
 lee  |        3 | pending | 25000
 lee  |        5 | paid    | 32000
(2 rows)
```

`BEGIN ATOMIC`이나 `RETURN`으로 쓴 본문은 만들 때 해석되고, 참조하는 테이블과 의존 관계가 기록된다. 그래서 함수가 쓰는 컬럼을 지우려고 하면 막아 준다. 예전 방식인 `AS $$ ... $$` 문자열 본문은 실행할 때야 해석해서, 오타나 사라진 컬럼을 호출하는 순간에 알게 된다.

변수, `IF`, 반복문, 예외 처리가 필요하면 PL/pgSQL을 쓴다. 주문 하나를 만드는 함수를 예로 든다. 재고를 줄이고, 재고가 모자라면 오류를 내고, 주문과 항목을 넣고, 주문 id를 돌려준다.

```sql
CREATE FUNCTION place_order(p_user_id bigint, p_book_id bigint, p_qty integer DEFAULT 1)
RETURNS bigint
LANGUAGE plpgsql
AS $$
DECLARE
  v_price    integer;                       -- 변수 선언
  v_order_id bigint;
BEGIN
  UPDATE books SET stock = stock - p_qty
  WHERE id = p_book_id AND stock >= p_qty
  RETURNING price INTO v_price;             -- 결과를 변수에 담는다

  IF NOT FOUND THEN                         -- 바로 앞 문장이 0행이면 참
    RAISE EXCEPTION '재고 부족: book_id=%, 요청 수량=%', p_book_id, p_qty
      USING ERRCODE = 'P0001', HINT = '재고를 확인하세요';
  END IF;

  INSERT INTO orders (user_id, status, total)
  VALUES (p_user_id, 'pending', v_price * p_qty)
  RETURNING id INTO v_order_id;

  INSERT INTO order_items (order_id, book_id, qty, price)
  VALUES (v_order_id, p_book_id, p_qty, v_price);

  RETURN v_order_id;
END;
$$;

SELECT place_order(3, 3, 2);                                     -- 위치로 넘기기
SELECT place_order(p_user_id => 3, p_book_id => 3, p_qty => 5);  -- 이름으로 넘기기
```

```text
 place_order
-------------
           7
(1 row)

ERROR:  재고 부족: book_id=3, 요청 수량=5
HINT:  재고를 확인하세요
CONTEXT:  PL/pgSQL function place_order(bigint,bigint,integer) line 11 at RAISE
```

`RAISE EXCEPTION`은 오류를 내고 함수가 한 일을 모두 되돌린다. `ERRCODE`를 주면 애플리케이션이 메시지 문자열 대신 SQLSTATE 코드로 분기할 수 있다. `p_qty integer DEFAULT 1`처럼 기본값을 주고, `=>`로 이름을 붙여 넘기면 인자가 많아도 헷갈리지 않는다. 함수는 같은 이름에 인자 타입만 다르게 여러 개 만들 수 있어서(오버로딩), 지우거나 권한을 줄 때 `place_order(bigint, bigint, integer)`처럼 인자 타입까지 적는다.

## 함수에 붙이는 약속, 변동성

함수를 만들 때 붙이는 `IMMUTABLE`, `STABLE`, `VOLATILE`은 "같은 인자를 넣으면 같은 결과가 나오는가"에 대한 약속이다. 플래너는 이 약속을 믿고 실행 계획을 바꾼다.

`IMMUTABLE`은 언제 불러도 같은 인자면 같은 결과다(`lower`, 숫자 계산). `STABLE`은 한 문장 안에서는 같은 결과다(`now()`, 테이블을 읽는 함수). `VOLATILE`은 매번 다를 수 있다(`random()`, `clock_timestamp()`, 데이터를 바꾸는 함수). 아무것도 적지 않으면 `VOLATILE`이다.

차이를 보려고 주문을 20만 건으로 늘리고 `created_at`에 인덱스를 만든 뒤, 본문이 똑같은 함수 두 개를 변동성만 다르게 만들었다. SQL 함수는 인라인되면서 변동성 표시가 무시될 수 있어서 PL/pgSQL로 만들었다.

```sql
INSERT INTO users (email, name)
SELECT 'user' || i || '@example.com', 'user' || i FROM generate_series(4, 20000) i;
SELECT setseed(0.42);
INSERT INTO orders (user_id, status, total, created_at)
SELECT 1 + floor(random() * 20000)::bigint, 'paid', (1 + floor(random() * 50)::int) * 1000,
       timestamptz '2025-10-17 00:00+09' + random() * interval '365 days'
FROM generate_series(1, 200000);
CREATE INDEX orders_created_idx ON orders (created_at);
VACUUM ANALYZE;

CREATE FUNCTION recent_cutoff_volatile() RETURNS timestamptz
LANGUAGE plpgsql VOLATILE
AS $$ BEGIN RETURN timestamptz '2026-10-17 00:00+09' - interval '1 day'; END $$;

CREATE FUNCTION recent_cutoff_stable() RETURNS timestamptz
LANGUAGE plpgsql STABLE
AS $$ BEGIN RETURN timestamptz '2026-10-17 00:00+09' - interval '1 day'; END $$;

EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders WHERE created_at >= recent_cutoff_volatile();
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders WHERE created_at >= recent_cutoff_stable();
```

```text
-- VOLATILE
   ->  Seq Scan on orders  (cost=0.00..54168.84 rows=66669 width=0) (actual time=0.139..75.375 rows=572 loops=1)
         Filter: (created_at >= recent_cutoff_volatile())
         Rows Removed by Filter: 199435
         Buffers: shared hit=1684
 Execution Time: 75.555 ms

-- STABLE
   ->  Index Only Scan using orders_created_idx on orders  (cost=0.67..28.40 rows=899 width=0) (actual time=0.031..0.077 rows=572 loops=1)
         Index Cond: (created_at >= recent_cutoff_stable())
         Heap Fetches: 0
         Buffers: shared hit=6
 Execution Time: 0.197 ms
```

본문은 같은데 하나는 Seq Scan으로 20만 행을 읽으며 행마다 함수를 불렀고(`Filter`), 다른 하나는 함수를 한 번 불러 그 값으로 인덱스를 탔다(`Index Cond`). `VOLATILE`이면 행마다 결과가 다를 수 있으니 인덱스 탐색의 기준값으로 쓸 수 없다. 함수를 만들고 변동성을 안 적으면 이런 일이 생긴다.

`IMMUTABLE`은 한 단계 더 나간다. 식 인덱스와 generated column에는 `IMMUTABLE`만 쓸 수 있다. `timestamptz`를 `date`로 바꾸는 것은 세션 시간대에 따라 결과가 달라지니 `STABLE`이라서 인덱스가 안 된다. 시간대를 고정하면 된다.

```sql
CREATE INDEX ON orders ((created_at::date));                                   -- 시간대에 따라 달라진다
CREATE INDEX ON orders (((created_at AT TIME ZONE 'Asia/Seoul')::date));       -- 시간대를 고정했다
```

```text
ERROR:  functions in index expression must be marked IMMUTABLE
CREATE INDEX
```

거꾸로 거짓말을 하면 위험하다. 테이블을 읽는 함수를 `IMMUTABLE`로 표시하면 플래너가 계획을 만들 때 한 번 계산한 값을 상수처럼 박아 넣거나, 그 함수로 만든 인덱스가 데이터가 바뀐 뒤 틀린 값을 가리킨다. 오류는 나지 않고 결과만 조용히 틀린다. 확실하지 않으면 한 단계 느슨하게 적는다.

## 실패를 붙잡는 EXCEPTION 블록

PL/pgSQL의 `BEGIN ... EXCEPTION WHEN ... THEN ... END`는 그 블록 안에서 난 오류를 붙잡는다. 이메일이 이미 있으면 기존 회원 id를 돌려주는 함수를 만든다.

```sql
CREATE FUNCTION add_user(p_email text, p_name text) RETURNS bigint
LANGUAGE plpgsql
AS $$
DECLARE
  v_id bigint;
BEGIN
  INSERT INTO users (email, name) VALUES (p_email, p_name) RETURNING id INTO v_id;
  RETURN v_id;
EXCEPTION
  WHEN unique_violation THEN                  -- SQLSTATE 23505
    RAISE NOTICE '이미 있는 이메일: %', p_email;
    SELECT id INTO v_id FROM users WHERE email = p_email;
    RETURN v_id;
END;
$$;

SELECT add_user('kim@example.com', 'kim');
SELECT add_user('jung@example.com', 'jung');
```

```text
NOTICE:  이미 있는 이메일: kim@example.com
 add_user
----------
        1
(1 row)

 add_user
----------
    20002
(1 row)
```

두 번째 결과가 20001이 아니라 20002인 것은 첫 호출에서 실패한 `INSERT`가 시퀀스 값 하나를 쓰고 되돌렸기 때문이다. 오류의 자세한 내용은 `GET STACKED DIAGNOSTICS`로 꺼낸다.

```sql
DO $$                                        -- 이름 없는 일회용 블록
DECLARE
  v_state text; v_msg text; v_detail text;
BEGIN
  INSERT INTO order_items (order_id, book_id, qty, price) VALUES (999999, 1, 1, 1000);
EXCEPTION WHEN OTHERS THEN
  GET STACKED DIAGNOSTICS v_state = RETURNED_SQLSTATE, v_msg = MESSAGE_TEXT, v_detail = PG_EXCEPTION_DETAIL;
  RAISE NOTICE 'state=% msg=% detail=%', v_state, v_msg, v_detail;
END $$;
```

```text
NOTICE:  state=23503 msg=insert or update on table "order_items" violates foreign key constraint "order_items_order_id_fkey" detail=Key (order_id)=(999999) is not present in table "orders".
DO
```

`EXCEPTION`이 붙은 블록은 들어갈 때마다 서브트랜잭션(세이브포인트)을 하나 연다. 오류가 나면 그 블록에서 한 일만 되돌리기 위해서다. 공짜가 아니라서 수십만 번 도는 반복문 안에 넣으면 눈에 띄게 느려진다. 그리고 `WHEN OTHERS THEN NULL`처럼 모든 오류를 삼키면 문제가 숨는다. 붙잡을 오류만 이름으로 적는다. 사실 이 함수는 앞 글의 `INSERT ... ON CONFLICT`로 바꾸는 편이 더 싸다.

## 트랜잭션을 나눠 커밋하는 프로시저

함수는 호출한 쪽의 트랜잭션 안에서 돈다. 그래서 함수 안에서는 `COMMIT`을 할 수 없다. 1년 지난 주문 수십만 건을 보관 테이블로 옮기는 작업을 함수 하나로 하면, 끝날 때까지 트랜잭션 하나가 열려 있어 잠금과 죽은 행이 쌓인다. 11부터 생긴 프로시저(`CREATE PROCEDURE`, `CALL`)는 안에서 `COMMIT`을 할 수 있어서 이런 일을 조각내 처리한다.

```sql
CREATE TABLE orders_archive (LIKE orders);

CREATE PROCEDURE archive_old_orders(p_before timestamptz, p_batch integer DEFAULT 10000)
LANGUAGE plpgsql
AS $$
DECLARE
  v_moved integer;
BEGIN
  LOOP
    WITH batch AS (                               -- 한 번에 p_batch건만
      DELETE FROM orders
      WHERE id IN (
        SELECT id FROM orders
        WHERE created_at < p_before
          AND NOT EXISTS (SELECT 1 FROM order_items i WHERE i.order_id = orders.id)
        LIMIT p_batch
      )
      RETURNING *
    )
    INSERT INTO orders_archive SELECT * FROM batch;
    GET DIAGNOSTICS v_moved = ROW_COUNT;          -- 방금 옮긴 행 수
    RAISE NOTICE '% rows moved', v_moved;
    EXIT WHEN v_moved = 0;
    COMMIT;                                       -- 조각마다 커밋한다
  END LOOP;
END;
$$;

CALL archive_old_orders('2025-11-01', 2000);
```

```text
NOTICE:  2000 rows moved
NOTICE:  2000 rows moved
NOTICE:  2000 rows moved
NOTICE:  1919 rows moved
NOTICE:  0 rows moved
CALL
```

중간에 끊겨도 커밋한 조각까지는 남고, 다시 `CALL`하면 남은 것부터 이어서 한다. 단, 바깥에서 이미 트랜잭션을 열고 `CALL`하면 안쪽의 `COMMIT`이 실패한다. 드라이버나 ORM이 자동으로 `BEGIN`을 보내는 환경에서 흔히 만나는 오류다.

```sql
BEGIN;
CALL archive_old_orders('2025-11-05', 2000);
```

```text
NOTICE:  2000 rows moved
ERROR:  invalid transaction termination
CONTEXT:  PL/pgSQL function archive_old_orders(timestamp with time zone,integer) line 20 at COMMIT
```

정리하면 값을 돌려주고 쿼리 안에서 쓰는 건 함수, 트랜잭션을 직접 나눠야 하는 긴 작업은 프로시저다. 프로시저는 `SELECT` 안에서 부를 수 없다.

## 테이블이 바뀔 때 끼어드는 트리거

트리거는 테이블에 `INSERT`, `UPDATE`, `DELETE`(그리고 `TRUNCATE`)가 일어날 때 자동으로 실행되는 함수다. 처음 문제였던 `updated_at`을 고친다. 트리거 함수는 `RETURNS trigger`로 만들고, 안에서 `NEW`(바뀔 행)와 `OLD`(바뀌기 전 행)를 쓴다.

```sql
CREATE FUNCTION set_updated_at() RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  NEW.updated_at := now();     -- 저장될 행의 값을 고친다
  RETURN NEW;                  -- 고친 행을 저장하라고 돌려준다
END;
$$;

CREATE TRIGGER books_set_updated_at
BEFORE UPDATE ON books         -- 행을 쓰기 전에
FOR EACH ROW                   -- 바뀌는 행마다
EXECUTE FUNCTION set_updated_at();

BEGIN;
SELECT now();
UPDATE books SET price = 28000 WHERE id = 2;                               -- updated_at을 안 넣어도
UPDATE books SET price = 33000, updated_at = '2000-01-01' WHERE id = 3;    -- 엉뚱한 값을 넣어도
SELECT id, price, updated_at FROM books ORDER BY id;
COMMIT;
```

```text
              now
-------------------------------
 2026-10-18 01:18:44.332428+09
(1 row)

 id | price |          updated_at
----+-------+-------------------------------
  1 | 19000 | 2026-10-18 01:17:53.682102+09
  2 | 28000 | 2026-10-18 01:18:44.332428+09
  3 | 33000 | 2026-10-18 01:18:44.332428+09
(3 rows)
```

이제 어느 서비스가 고치든 `updated_at`이 따라 바뀐다. 2번과 3번의 시각이 마이크로초까지 같은 것은 `now()`가 트랜잭션이 시작된 시각을 돌려주기 때문이다. 문장마다 실제 시각이 필요하면 `clock_timestamp()`를 쓴다.

`BEFORE ... FOR EACH ROW` 트리거는 `NEW`를 고쳐서 저장될 값을 바꿀 수 있고, `NULL`을 돌려주면 그 행의 변경을 조용히 건너뛴다. 아래 그림은 이 트리거가 끼어드는 자리다. 단계를 넘기며 `NEW`가 어떻게 바뀌는지 보자.

값이 하나도 안 바뀐 `UPDATE`에도 `updated_at`이 바뀌는 게 싫다면 `WHEN` 조건을 붙인다. 조건이 거짓이면 함수를 아예 부르지 않아서 함수 안에서 검사하는 것보다 싸다.

```sql
DROP TRIGGER books_set_updated_at ON books;
CREATE TRIGGER books_set_updated_at
BEFORE UPDATE ON books
FOR EACH ROW
WHEN (OLD.* IS DISTINCT FROM NEW.*)    -- 실제로 뭔가 바뀌었을 때만
EXECUTE FUNCTION set_updated_at();
```

`EXECUTE FUNCTION`은 11부터의 문법이고, 그 전에는 `EXECUTE PROCEDURE`라고 썼다. MySQL은 `updated_at`만큼은 트리거 없이 `ON UPDATE CURRENT_TIMESTAMP` 컬럼 속성으로 해결한다.

## 누가 무엇을 바꿨는지 남기는 감사 로그

가격이 언제 누가 얼마에서 얼마로 바꿨는지 묻는 일이 생긴다. `AFTER` 트리거로 바뀐 행을 이력 테이블에 남긴다. 행 전체를 `to_jsonb()`로 바꿔 두면 컬럼이 추가돼도 트리거를 고칠 필요가 없다.

```sql
CREATE TABLE book_history (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  book_id    bigint NOT NULL,
  op         text NOT NULL,                              -- INSERT, UPDATE, DELETE
  changed    jsonb,                                      -- 바뀐 컬럼만 {"컬럼": [전, 후]}
  old_row    jsonb,
  new_row    jsonb,
  changed_by text NOT NULL DEFAULT current_user,
  changed_at timestamptz NOT NULL DEFAULT now()
);

CREATE FUNCTION audit_books() RETURNS trigger
LANGUAGE plpgsql
AS $$
DECLARE
  v_old jsonb := CASE WHEN TG_OP <> 'INSERT' THEN to_jsonb(OLD) END;   -- TG_OP: 어떤 작업인지
  v_new jsonb := CASE WHEN TG_OP <> 'DELETE' THEN to_jsonb(NEW) END;
  v_changed jsonb;
BEGIN
  IF TG_OP = 'UPDATE' THEN
    SELECT jsonb_object_agg(n.key, jsonb_build_array(v_old -> n.key, n.value))
    INTO v_changed
    FROM jsonb_each(v_new) AS n                            -- 새 행의 (컬럼, 값)마다
    WHERE v_old -> n.key IS DISTINCT FROM n.value;         -- 옛 값과 다른 것만
  END IF;
  INSERT INTO book_history (book_id, op, changed, old_row, new_row)
  VALUES (coalesce(NEW.id, OLD.id), TG_OP, v_changed, v_old, v_new);
  RETURN NULL;                                             -- AFTER 트리거의 반환값은 무시된다
END;
$$;

CREATE TRIGGER books_audit
AFTER INSERT OR UPDATE OR DELETE ON books
FOR EACH ROW
EXECUTE FUNCTION audit_books();

UPDATE books SET price = 26000, stock = 4 WHERE id = 2;
INSERT INTO books (isbn, title, price, stock) VALUES ('978-89-0004', '인덱스 설계', 28000, 7);
DELETE FROM books WHERE id = 4;
SELECT id, book_id, op, changed FROM book_history ORDER BY id;
```

```text
 id | book_id |   op   |                                                              changed
----+---------+--------+------------------------------------------------------------------------------------------------------------------------------------
  1 |       2 | UPDATE | {"price": [28000, 26000], "stock": [5, 4], "updated_at": ["2026-10-18T01:18:44.332428+09:00", "2026-10-18T01:18:44.349568+09:00"]}
  2 |       4 | INSERT |
  3 |       4 | DELETE |
(3 rows)
```

`changed`에 `updated_at`도 들어 있다. `BEFORE` 트리거가 먼저 `updated_at`을 고친 뒤 `AFTER` 트리거가 최종 행을 봤기 때문이다. 지워진 책도 `old_row`에 전체가 남아 있어서 복구할 수 있다.

같은 비교를 직접 해 보자. 옛 행과 새 행을 받아 바뀐 컬럼만 `[컬럼, 전, 후]`로 돌려주는 함수다. 트리거 안의 `IS DISTINCT FROM`처럼 한쪽에만 있는 컬럼은 NULL로 보고, 배열 같은 값도 내용으로 비교한다. 결과는 컬럼 이름순으로 정렬한다.

## 트리거가 실행되는 순서

트리거는 시점(`BEFORE`, `AFTER`, 뷰에는 `INSTEAD OF`)과 단위(`FOR EACH ROW`, `FOR EACH STATEMENT`)로 나뉜다. 같은 시점, 같은 단위의 트리거가 여러 개면 만든 순서가 아니라 이름의 알파벳 순서로 실행된다. 이름만 출력하는 트리거 네 개를 붙여서 두 행을 고쳐 봤다.

```sql
CREATE FUNCTION trg_note() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN RAISE NOTICE '% % % %', TG_NAME, TG_WHEN, TG_LEVEL, TG_OP; RETURN COALESCE(NEW, OLD); END $$;

CREATE TRIGGER b_note BEFORE UPDATE ON books FOR EACH ROW EXECUTE FUNCTION trg_note();
CREATE TRIGGER a_note BEFORE UPDATE ON books FOR EACH ROW EXECUTE FUNCTION trg_note();  -- 나중에 만들었지만
CREATE TRIGGER z_stmt AFTER UPDATE ON books FOR EACH STATEMENT EXECUTE FUNCTION trg_note();
CREATE TRIGGER s_stmt BEFORE UPDATE ON books FOR EACH STATEMENT EXECUTE FUNCTION trg_note();

UPDATE books SET stock = stock + 1 WHERE id IN (1, 2);
UPDATE books SET stock = stock + 1 WHERE id = 999;      -- 0행
```

```text
NOTICE:  s_stmt BEFORE STATEMENT UPDATE
NOTICE:  a_note BEFORE ROW UPDATE
NOTICE:  b_note BEFORE ROW UPDATE
NOTICE:  a_note BEFORE ROW UPDATE
NOTICE:  b_note BEFORE ROW UPDATE
NOTICE:  z_stmt AFTER STATEMENT UPDATE
UPDATE 2
NOTICE:  s_stmt BEFORE STATEMENT UPDATE
NOTICE:  z_stmt AFTER STATEMENT UPDATE
UPDATE 0
```

`a_note`가 나중에 만들어졌는데 먼저 돈다. 문장 단위 트리거는 0행을 고쳐도 한 번씩 돈다. 아래 그림은 `UPDATE` 한 문장 안에서 일어나는 일을 순서대로 보여 준다.

## 행 20만 개를 고칠 때 트리거가 치르는 값

행 트리거는 행마다 함수를 부른다. 주문 19만 2천 건의 금액을 한 번에 바꾸면서 감사 로그를 남겨 봤다. 먼저 행 단위 트리거다.

```sql
CREATE TABLE order_history (
  order_id bigint NOT NULL, old_total integer, new_total integer,
  changed_at timestamptz NOT NULL DEFAULT now()
);

CREATE FUNCTION audit_orders_row() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO order_history (order_id, old_total, new_total) VALUES (OLD.id, OLD.total, NEW.total);
  RETURN NULL;
END $$;
CREATE TRIGGER orders_audit_row AFTER UPDATE ON orders
FOR EACH ROW EXECUTE FUNCTION audit_orders_row();

EXPLAIN (ANALYZE, COSTS OFF) UPDATE orders SET total = total + 100;
```

10부터는 문장 단위 트리거가 전이 테이블(transition table)을 받을 수 있다. `REFERENCING OLD TABLE AS ... NEW TABLE AS ...`로 이름을 붙이면 이 문장이 바꾼 행 전체를 테이블처럼 읽는다. `INSERT ... SELECT` 한 번으로 로그를 남기는 셈이다.

```sql
DROP TRIGGER orders_audit_row ON orders;

CREATE FUNCTION audit_orders_stmt() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO order_history (order_id, old_total, new_total)
  SELECT o.id, o.total, n.total
  FROM old_rows o JOIN new_rows n ON n.id = o.id      -- 바뀌기 전과 후를 id로 짝짓는다
  WHERE o.total IS DISTINCT FROM n.total;
  RETURN NULL;
END $$;
CREATE TRIGGER orders_audit_stmt AFTER UPDATE ON orders
REFERENCING OLD TABLE AS old_rows NEW TABLE AS new_rows
FOR EACH STATEMENT EXECUTE FUNCTION audit_orders_stmt();

EXPLAIN (ANALYZE, COSTS OFF) UPDATE orders SET total = total + 100;
```

```text
-- 트리거 없음
 Update on orders (actual time=2470.442..2470.443 rows=0 loops=1)
 Execution Time: 2470.533 ms

-- 행 단위 트리거
 Trigger orders_audit_row: time=864.764 calls=192088
 Execution Time: 3877.324 ms

-- 문장 단위 트리거 + 전이 테이블
 Trigger orders_audit_stmt: time=518.917 calls=1
 Execution Time: 3156.681 ms
```

`EXPLAIN ANALYZE`는 트리거마다 걸린 시간과 호출 횟수를 맨 아래에 따로 적는다. 행 트리거는 19만 번 불려 865ms, 문장 트리거는 한 번 불려 519ms였다. 같은 테이블을 여러 번 고친 뒤라 `UPDATE` 자체 시간은 실행마다 오르내리니 트리거 줄을 비교한다. 대량 변경이 잦은 테이블이면 전이 테이블 쪽이 낫다. 다만 `BEFORE` 트리거나 `NEW`를 고치는 일은 행 단위로만 된다.

트리거를 잠깐 끄고 대량 적재를 하고 싶을 때가 있다. `ALTER TABLE ... DISABLE TRIGGER`는 테이블 잠금을 잡고 모든 세션에 적용되니 운영 중에는 위험하다. 세션 하나에서만 일반 트리거를 건너뛰려면 슈퍼유저가 `SET session_replication_role = replica`를 쓴다. 이 설정은 외래 키 검사(내부 트리거)까지 건너뛰니 데이터가 맞는다는 확신이 있을 때만 쓴다.

```sql
SELECT count(*) FROM book_history;            -- 지금 몇 건인지 본다 (7)
SET session_replication_role = replica;
UPDATE books SET stock = stock + 1 WHERE id = 1;
RESET session_replication_role;
SELECT count(*) FROM book_history;            -- 여전히 7: 감사 트리거가 안 돌았다
```

## 커밋할 때 검사하는 제약 트리거

"주문에는 항목이 하나 이상 있어야 한다" 같은 규칙은 행을 넣는 순간에는 검사할 수 없다. 주문을 먼저 넣고 항목을 나중에 넣기 때문이다. 제약 트리거(`CREATE CONSTRAINT TRIGGER`)는 `AFTER ... FOR EACH ROW`만 되는 대신 `DEFERRABLE INITIALLY DEFERRED`로 검사를 커밋 시점까지 미룰 수 있다.

```sql
CREATE FUNCTION check_order_has_items() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM order_items WHERE order_id = NEW.id) THEN
    RAISE EXCEPTION '주문 %에 항목이 없다', NEW.id;
  END IF;
  RETURN NULL;
END $$;

CREATE CONSTRAINT TRIGGER orders_need_items
AFTER INSERT ON orders
DEFERRABLE INITIALLY DEFERRED           -- COMMIT할 때 검사한다
FOR EACH ROW EXECUTE FUNCTION check_order_has_items();

BEGIN;
INSERT INTO orders (user_id, total) VALUES (1, 18000);
COMMIT;                                  -- 항목 없이 커밋
```

```text
BEGIN
INSERT 0 1
ERROR:  주문 200009에 항목이 없다
CONTEXT:  PL/pgSQL function check_order_has_items() line 4 at RAISE
```

같은 트랜잭션 안에서 항목까지 넣고 커밋하면 통과한다. 다만 트리거로 만든 검사는 동시에 도는 트랜잭션끼리 서로의 커밋 안 된 행을 못 봐서, 다른 행과 비교하는 규칙(중복 금지 등)은 경쟁에 약하다. 그런 규칙은 가능하면 유니크 제약이나 배제 제약으로 만든다.

## 트리거가 만드는 함정

트리거는 코드를 읽어서는 안 보인다. `UPDATE books SET price = 26000` 한 줄이 이력 테이블에 행을 넣고, 알림을 보내고, 다른 테이블을 고칠 수 있다. 새로 온 사람은 쿼리가 왜 느린지, 이력 테이블은 누가 채우는지 모른다. 그래서 트리거는 적게, 이름은 하는 일이 드러나게 짓고, 마이그레이션 파일에 함께 둔다. 붙어 있는 트리거는 psql의 `\d books` 아래쪽 `Triggers:`에서 확인한다.

자기 테이블을 다시 고치는 트리거는 끝없이 자기를 부른다. `AFTER UPDATE` 트리거 안에서 같은 테이블을 `UPDATE`하면 이렇게 된다.

```sql
CREATE FUNCTION touch_book() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  UPDATE books SET updated_at = now() WHERE id = NEW.id;   -- 또 UPDATE → 또 트리거
  RETURN NULL;
END $$;
CREATE TRIGGER books_touch AFTER UPDATE ON books FOR EACH ROW EXECUTE FUNCTION touch_book();
UPDATE books SET stock = stock + 1 WHERE id = 1;
```

```text
ERROR:  stack depth limit exceeded
HINT:  Increase the configuration parameter "max_stack_depth" (currently 2048kB), after ensuring the platform's stack depth limit is adequate.
```

같은 행의 값을 바꾸는 일은 `AFTER`에서 `UPDATE`하지 말고 `BEFORE`에서 `NEW`를 고친다. 정말 필요하면 `WHEN (pg_trigger_depth() < 1)`로 트리거 안에서 일어난 변경에는 다시 돌지 않게 막는다.

그 밖에도 알아 둘 것이 있다. `TRUNCATE`는 `DELETE` 트리거를 부르지 않는다(`ON TRUNCATE` 문장 트리거가 따로 있다). `COPY`로 넣는 행에도 행 트리거가 돈다. 논리 복제로 받은 쪽에서는 기본적으로 일반 트리거가 돌지 않는다. 트리거가 다른 테이블의 행을 고치면 잠금 범위가 넓어져서 교착 상태가 생기기 쉬워진다([트랜잭션과 격리 수준](/posts/db-transaction-isolation) 참고).

## 만든 사람 권한으로 도는 SECURITY DEFINER

함수는 기본적으로 부른 사람의 권한으로 돈다(`SECURITY INVOKER`). `SECURITY DEFINER`를 붙이면 함수를 만든 사람(소유자)의 권한으로 돈다. 애플리케이션 계정에 테이블 권한은 주지 않고 "이 함수로만 기록해라"를 강제할 때 쓴다. 앞 글 [역할과 권한](/posts/postgres-roles-security)의 권한 모델 위에 얹는 기능이다.

조회 기록을 남기는 함수를 슈퍼유저가 만들고, 앱 계정 `pg2_app`에는 함수 실행 권한만 줬다.

```sql
CREATE TABLE access_log (book_id bigint NOT NULL, viewer text NOT NULL, at timestamptz NOT NULL DEFAULT now());

CREATE FUNCTION log_view(p_book_id bigint) RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
AS $$
BEGIN
  INSERT INTO access_log (book_id, viewer) VALUES (p_book_id, session_user);  -- 스키마를 안 적었다
END;
$$;
REVOKE ALL ON FUNCTION log_view(bigint) FROM PUBLIC;       -- 함수는 기본으로 PUBLIC이 실행할 수 있다
GRANT EXECUTE ON FUNCTION log_view(bigint) TO pg2_app;
```

`pg2_app`으로 접속해서 테이블에 직접 쓰면 막히고, 함수로는 기록된다. 여기까지는 의도대로다. 그런데 `pg2_app`이 같은 이름의 임시 테이블을 만들고 함수를 부르면 어떻게 될까.

```sql
-- pg2_app으로 접속한 세션
INSERT INTO access_log (book_id, viewer) VALUES (1, 'me');   -- 직접 쓰기
SELECT log_view(1);                                          -- 함수로 쓰기
CREATE TEMP TABLE access_log (book_id bigint, viewer text);  -- 같은 이름의 임시 테이블
SELECT log_view(2);
SELECT * FROM access_log;                                    -- 임시 테이블을 본다
```

```text

----------

(1 row)

CREATE TABLE

----------

(1 row)

 book_id | viewer
---------+---------
       2 | pg2_app
(1 row)
```

진짜 `public.access_log`에는 1번만 남았고, 2번 기록은 공격자의 임시 테이블로 들어갔다. 스키마를 적지 않은 이름은 `search_path` 순서대로 찾는데, 임시 스키마(`pg_temp`)는 따로 적지 않으면 맨 앞에서 찾기 때문이다. 감사 기록을 피한 정도로 끝났지만, 함수가 이름으로 다른 함수나 연산자를 부르는 경우라면 소유자 권한으로 공격자 코드를 실행시키는 데까지 갈 수 있다. 15부터는 `public` 스키마에 아무나 객체를 만들 수 없게 기본값이 바뀌어서 그쪽 길은 좁아졌지만, 임시 스키마는 여전히 남아 있다.

<Callout kind="warning" title="SECURITY DEFINER에는 search_path를 고정한다">
`SECURITY DEFINER` 함수에는 `SET search_path`를 붙이고 `pg_temp`를 맨 뒤에 명시한다. 함수 안의 테이블 이름에 스키마를 적으면 더 안전하다. 실행 권한은 `PUBLIC`에서 회수하고 필요한 역할에만 준다.
</Callout>

```sql
ALTER FUNCTION log_view(bigint) SET search_path = public, pg_temp;
-- 같은 공격을 다시 하면 기록은 public.access_log로 간다
```

## 바뀌었다고 알려 주는 LISTEN과 NOTIFY

API 서버들이 책 정보를 메모리에 캐시하고 있다. 가격이 바뀌면 캐시를 지워야 하는데, 어느 서비스가 바꿨든 모든 서버가 알아야 한다. PostgreSQL에는 간단한 발행 구독 기능이 있다. `LISTEN 채널`로 구독하고, `NOTIFY 채널, '내용'`이나 `pg_notify()`로 알린다. 트리거와 묶으면 "books가 바뀌면 알린다"가 된다.

```sql
CREATE FUNCTION notify_book_changed() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  PERFORM pg_notify('book_changed', json_build_object('id', NEW.id, 'price', NEW.price)::text);
  RETURN NULL;
END $$;
CREATE TRIGGER books_notify AFTER UPDATE ON books
FOR EACH ROW EXECUTE FUNCTION notify_book_changed();
```

psql 두 개로 실제로 돌렸다. 세션 A는 구독하고 기다린다. 세션 B는 트랜잭션 안에서 가격을 바꾸고, 같은 내용의 `NOTIFY`를 두 번 직접 보낸 뒤 2초 있다가 커밋한다.

```sql
-- 세션 A (구독자)
LISTEN book_changed;
SELECT pg_sleep(1.5);
SELECT 'before commit' AS t;      -- B가 아직 커밋 전
SELECT pg_sleep(2);
SELECT 'after commit' AS t;       -- B가 커밋한 뒤

-- 세션 B (변경하는 쪽)
BEGIN;
UPDATE books SET price = 31000 WHERE id = 3;
NOTIFY book_changed, 'dup';
NOTIFY book_changed, 'dup';
SELECT pg_sleep(2);
COMMIT;
```

편하지만 한계가 분명하다. 알림은 저장되지 않는다. 구독자가 재시작하는 동안 온 알림은 사라지니, 다시 연결하면 캐시를 통째로 비우고 시작해야 한다. 내용은 기본 설정에서 8000바이트 미만이어야 한다. 구독하려면 연결을 계속 붙잡고 있어야 해서 PgBouncer의 트랜잭션 풀링 모드에서는 쓸 수 없고, 구독용 연결은 DB에 직접 붙는다. 알림이 많아지거나 놓치면 안 되는 이벤트라면 아웃박스 테이블과 메시지 큐로 간다([규모별 DB 아키텍처](/posts/db-architecture-by-scale) 참고). MySQL에는 이런 기능이 없다.

## 로직을 DB에 둘까 애플리케이션에 둘까

DB에 두면 좋은 것은 "어느 경로로 바꾸든 지켜져야 하는 데이터 규칙"이다. `updated_at`, 감사 로그, 파생 값, 커밋 시점 검사가 그렇다. 서비스가 여럿이고 사람이 SQL로 직접 고치기도 하는 테이블이라면 더 그렇다. 데이터 가까이에서 돌아 왕복이 줄어드는 대량 처리도 DB가 잘한다.

애플리케이션에 두는 편이 나은 것은 업무 흐름이다. 결제 승인, 할인 정책, 외부 API 호출, 메일 발송은 자주 바뀌고, 테스트와 배포, 로그, 모니터링 도구가 애플리케이션 쪽에 다 갖춰져 있다. DB 안의 코드는 버전 관리와 배포를 마이그레이션 도구에 맡겨야 하고, 디버깅이 어렵고, DB CPU는 늘리기 가장 비싼 자원이다. 그리고 트리거는 트랜잭션 안에서 돌아서 느린 일을 넣으면 그만큼 잠금을 오래 잡는다.

내 기준은 이렇다. 데이터의 정합성을 지키는 짧고 단순한 규칙은 DB에, 그 밖의 판단은 애플리케이션에 둔다. DB에 둔 것은 이름과 주석으로 드러내고, 마이그레이션과 테스트에 포함한다.

## DB 안에 둔 코드도 코드다

함수의 변동성은 성능 문제고, `SECURITY DEFINER`의 `search_path`는 보안 문제고, 트리거의 순서와 재귀는 정확성 문제다. 셋 다 "DB 안에 둔 코드도 결국 코드"라서 생긴다. 다음 글 [JSONB와 전문 검색](/posts/postgres-jsonb-search)에서는 오늘 감사 로그에 쓴 `jsonb`를 제대로 파고, 검색까지 DB 안에서 해 본다.

## 면접에서 나올 만한 질문

### 함수와 프로시저는 무엇이 다른가요?

함수는 값을 돌려주고 `SELECT` 안에서 쓸 수 있으며, 호출한 쪽의 트랜잭션 안에서 돌아서 `COMMIT`을 할 수 없다. 프로시저(11부터)는 `CALL`로만 부르고 안에서 `COMMIT`, `ROLLBACK`을 할 수 있어서, 대량 작업을 조각내 커밋할 때 쓴다. 단 바깥에서 트랜잭션을 연 채로 `CALL`하면 안쪽 `COMMIT`이 "invalid transaction termination"으로 실패한다.

### IMMUTABLE, STABLE, VOLATILE은 왜 중요한가요?

플래너가 함수 결과를 얼마나 믿고 최적화할지 정하는 약속이다. `VOLATILE`이면 행마다 다시 불러야 해서 인덱스 조건으로 쓸 수 없고, 예제에서 같은 본문이 VOLATILE이면 Seq Scan 75ms, STABLE이면 Index Only Scan 0.2ms였다. 식 인덱스와 generated column에는 IMMUTABLE만 쓸 수 있다. 적지 않으면 VOLATILE이고, 반대로 테이블을 읽는 함수를 IMMUTABLE로 속이면 결과가 조용히 틀린다.

### updated_at을 트리거로 관리하는 이유와 방법은요?

테이블을 고치는 경로가 여러 개면 애플리케이션 코드 하나가 빠뜨리는 순간 값이 틀어지기 때문이다. `BEFORE UPDATE ... FOR EACH ROW` 트리거에서 `NEW.updated_at := now()`를 하고 `NEW`를 돌려주면 어느 경로든 같다. `WHEN (OLD.* IS DISTINCT FROM NEW.*)`로 실제 변경에만 돌게 할 수 있다. `now()`는 트랜잭션 시작 시각이라 같은 트랜잭션 안의 행은 같은 값을 가진다.

### BEFORE와 AFTER, ROW와 STATEMENT 트리거는 언제 쓰나요?

값을 고치거나 행을 막아야 하면 `BEFORE ROW`, 최종 결과를 기록하거나 다른 테이블에 반영하면 `AFTER ROW`다. 대량 변경에서 감사 로그를 남긴다면 `AFTER STATEMENT`에 전이 테이블(`REFERENCING OLD TABLE ... NEW TABLE`)을 쓰면 함수 호출이 한 번으로 줄어든다. 예제의 19만 행에서 트리거 시간이 865ms에서 519ms로 줄었다. 같은 종류의 트리거는 이름 알파벳 순서로 실행된다.

### 트리거를 쓸 때 주의할 점은요?

코드에서 안 보이는 로직이라 동작과 성능을 추적하기 어렵다. 자기 테이블을 다시 고치면 무한 재귀로 "stack depth limit exceeded"가 나니 `BEFORE`에서 `NEW`를 고치거나 `pg_trigger_depth()`로 막는다. 행 트리거는 대량 변경을 느리게 하고, 트리거 안의 느린 작업은 잠금을 오래 잡는다. `TRUNCATE`는 `DELETE` 트리거를 부르지 않는다.

### SECURITY DEFINER 함수는 왜 위험하고 어떻게 막나요?

소유자 권한으로 돌기 때문에, 함수 안에서 스키마 없이 쓴 이름을 호출자가 바꿔치기하면 권한이 새어 나간다. `pg_temp`는 명시하지 않으면 맨 앞에서 검색돼서, 예제에서는 같은 이름의 임시 테이블로 감사 기록이 빠져나갔다. `SET search_path = public, pg_temp`처럼 고정하고 `pg_temp`를 맨 뒤에 두며, 실행 권한은 `PUBLIC`에서 회수한다.

### LISTEN/NOTIFY로 캐시 무효화를 할 때 한계는요?

알림은 커밋할 때만 전달되고, 같은 트랜잭션의 중복은 합쳐지며, 저장되지 않아서 구독자가 끊겨 있던 동안의 알림은 사라진다. 그래서 재연결하면 캐시를 전부 비워야 한다. 내용은 8000바이트 미만이고 연결을 계속 붙잡아야 해서 PgBouncer 트랜잭션 풀링과 맞지 않는다. 놓치면 안 되는 이벤트는 아웃박스와 메시지 큐를 쓴다.

### 비즈니스 로직을 DB에 두는 건 어떻게 보나요?

경로와 상관없이 지켜야 하는 짧은 데이터 규칙(`updated_at`, 감사 로그, 커밋 시점 검사)은 DB에 두는 편이 안전하다. 자주 바뀌는 업무 흐름이나 외부 호출은 테스트, 배포, 관측 도구가 갖춰진 애플리케이션에 둔다. DB CPU는 늘리기 비싸고 트리거는 트랜잭션 안에서 돌아 잠금을 늘리기 때문이다. DB에 둔 코드는 마이그레이션으로 버전 관리한다.
