상품 2,000개짜리 표에서 정렬 버튼을 눌렀더니 화면이 0.3초쯤 굳는다. 크롬 개발자 도구의 Performance 패널로 녹화하면 노란 막대 하나가 길게 늘어져 있고, 펼쳐 보면 React 함수 이름이 층층이 쌓여 있다. `performWorkOnRoot` 아래 `renderRootSync`, 그 아래 `workLoopSync`, 그 아래 `performUnitOfWork`가 수천 번 반복되고, 끝에 `commitRoot`가 한 번 붙어 있다.

같은 표를 `startTransition` 안에서 정렬하게 바꾸면 그림이 달라진다. 긴 막대 하나 대신 5ms 남짓한 짧은 막대가 수십 개 늘어서고, 그 사이사이에 클릭이나 키 입력 처리가 끼어든다. 이번에는 `workLoopSync` 대신 `workLoopConcurrentByScheduler`가 보인다.

이 차이를 읽으려면 React가 렌더링 작업을 어떤 단위로 쪼개고, 언제 멈추고, 언제 DOM을 바꾸는지 알아야 한다. 이 글은 그 구조인 Fiber 아키텍처를 따라간다. 함수 이름은 React 19 소스(`react-reconciler` 패키지)에 실제로 있는 것만 쓰고, 측정은 React 19.3.1을 Node 22와 jsdom 위에서 돌려서 했다. 렌더와 커밋이 무엇인지부터 필요하면 [React는 언제 다시 그리나](/posts/react-rerender)를, 이전 트리와 새 트리를 짝짓는 규칙은 [재조정과 key](/posts/react-reconciliation-keys)를 먼저 보면 좋다.

## 재귀로는 중간에 멈출 수 없었다

React 15까지의 재조정자는 지금 흔히 스택 재조정자(stack reconciler)라고 부른다. 컴포넌트를 렌더링하고, 그 결과의 자식을 렌더링하고, 또 그 자식을 렌더링하는 일을 함수 재귀로 했다. 트리를 걷는 위치가 JavaScript 엔진의 콜 스택에 쌓여 있었다는 뜻이다.

콜 스택은 개발자가 마음대로 저장해 두었다가 나중에 꺼낼 수 없다. 함수 중간에서 "여기까지 하고 브라우저에게 양보한 뒤 다음 태스크에서 이어 하자"고 하려면 지금까지 쌓인 스택 프레임을 어딘가에 보관해야 하는데, 재귀로는 그 방법이 없다. 결국 업데이트 하나가 시작되면 트리 끝까지 가야 끝났고, 그동안 메인 스레드는 다른 일을 못 했다. 메인 스레드가 50ms 넘게 막히면 사용자 입력이 눈에 띄게 늦어지는 긴 작업이 된다. 이 기준과 브라우저가 태스크 사이에서만 화면을 그리는 이유는 [이벤트 루프](/posts/event-loop)에서 다뤘다.

React 16(2017)은 재조정자를 새로 썼다. 콜 스택 대신 React가 직접 관리하는 자료 구조 위에서 트리를 걷는다. 걷는 위치를 변수 하나(`workInProgress`)에 들고 있으니, 아무 때나 멈췄다가 그 변수부터 다시 시작할 수 있다. 이 자료 구조의 노드가 Fiber다. 16에서는 구조만 바뀌었고, 실제로 작업을 쪼개 양보하는 동시성 렌더링이 기본 API(`createRoot`)로 쓰이기 시작한 건 React 18부터다.

## Fiber 노드 하나가 들고 있는 것

Fiber는 컴포넌트 인스턴스 하나, DOM 요소 하나, Fragment나 Suspense 같은 특수 노드 하나마다 만들어지는 평범한 JavaScript 객체다. 엘리먼트(`<Item />`가 만드는 객체)는 렌더링할 때마다 새로 만들어지고 버려지지만, Fiber는 렌더링을 넘어 살아남는다. 상태와 effect, 실제 DOM 노드에 대한 참조가 여기 붙어 있다. 주요 필드를 조각으로 보자.

## 재귀 대신 포인터를 따라 걷는다

렌더 단계의 작업 단위는 Fiber 하나다. 작업 루프는 놀랄 만큼 짧다. React 19.3.1 빌드에서 그대로 옮기면 이렇다.

```js
function workLoopSync() {
  for (; null !== workInProgress; ) performUnitOfWork(workInProgress);
}
function workLoopConcurrentByScheduler() {
  for (; null !== workInProgress && !shouldYield(); )
    performUnitOfWork(workInProgress);
}
```

둘의 차이는 `shouldYield()` 하나다. 이 질문을 Fiber마다 던질 수 있게 된 것이 Fiber 아키텍처의 전부라고 해도 지나치지 않다.

`performUnitOfWork`는 Fiber 하나에 `beginWork`를 부른다. `beginWork`는 내려가는 쪽 일이다. 함수 컴포넌트라면 함수를 호출하고, 돌려받은 엘리먼트를 이전 자식 Fiber들과 비교해(`reconcileChildFibers`) 새 자식 Fiber를 만들거나 다시 쓴다. 그리고 첫째 자식을 돌려준다. 자식이 있으면 그게 다음 `workInProgress`가 된다.

자식이 없으면 `completeUnitOfWork`로 넘어가 올라가는 쪽 일을 한다. 그 Fiber에 `completeWork`를 부르고, 형제가 있으면 형제로 가서 다시 내려가고, 없으면 `return`을 따라 부모로 올라가 부모를 완료한다. `completeWork`는 DOM 태그 Fiber라면 처음 마운트할 때 DOM 노드를 만들어 자식 DOM을 붙여 두고(아직 문서에는 붙이지 않는다), 업데이트라면 props가 바뀌었을 때 Update 표시를 붙인다. React 18까지는 여기서 바뀐 속성 목록까지 계산했고, 19는 그 비교를 커밋 단계의 `commitUpdate`로 옮겼다.

## 트리는 두 벌이다

React는 Fiber 트리를 두 벌 들고 있다. 지금 화면에 반영된 트리가 `current`, 렌더 단계에서 만들고 있는 트리가 `workInProgress`다. 같은 자리의 두 Fiber는 `alternate`로 서로를 가리킨다. 그래픽에서 다음 프레임을 보이지 않는 버퍼에 그린 뒤 한 번에 바꿔 보여 주는 더블 버퍼링과 같은 생각이다.

렌더 단계에서 Fiber를 처리할 때 `createWorkInProgress`가 `current.alternate`를 본다. 비어 있으면 새 Fiber를 만들고, 이미 있으면 지난번에 쓰고 남은 그 객체를 다시 쓰면서 필드만 덮어쓴다. 렌더링마다 Fiber를 수천 개씩 새로 할당하지 않아도 되는 이유다.

두 벌이 있기 때문에 렌더 단계를 버리는 비용이 싸다. `workInProgress` 트리는 아직 아무 데도 연결되지 않은 초안이다. 중간에 더 급한 업데이트가 오면 React는 초안을 그냥 두고 `current`에서 다시 시작한다(`prepareFreshStack`). 화면에는 아무 흔적도 남지 않는다.

맞바꾸는 시점은 커밋 안에 있다. React 소스에서 `root.current = finishedWork`는 DOM을 바꾸는 mutation 단계가 끝난 직후, layout 단계 직전에 있다. 그래서 `componentWillUnmount`처럼 mutation 단계에서 도는 코드는 이전 트리를 보고, `componentDidMount`·`componentDidUpdate`와 `useLayoutEffect`처럼 layout 단계에서 도는 코드는 새 트리를 본다.

## 일을 쪼개고 브라우저에 양보한다

`shouldYield()`는 React가 아니라 `scheduler` 패키지의 함수다. 스케줄러는 작업을 시작한 시각을 기억해 두고, 지난 시간이 `frameInterval`을 넘으면 양보하라고 답한다. `scheduler` 0.28의 기본값은 5ms다. 양보한 뒤 이어서 할 일은 브라우저에서 `MessageChannel` 메시지로 다음 태스크에 예약한다. `setTimeout(fn, 0)`은 중첩되면 최소 4ms로 늘어나지만 `MessageChannel`에는 그런 지연이 없다. Node처럼 `setImmediate`가 있는 환경에서는 그걸 쓴다.

정말 5ms마다 끊기는지 재 봤다. 한 번 렌더링에 0.3ms씩 일부러 시간을 쓰는 `Item` 300개를 두고, 업데이트를 일반 `setState`와 `startTransition`으로 각각 일으켰다. 다른 태스크가 끼어들 때마다 그 사이에 렌더링된 `Item` 수를 셌다.

```text
default    slices: 1   items per slice: 300 total 300
transition slices: 19  items per slice: 12,17,16,17,16,16,17,17 total 300
```

일반 업데이트는 300개를 한 번에 렌더링했다. 약 90ms 동안 다른 태스크가 하나도 끼어들지 못했다. transition은 열아홉 조각으로 나뉘었고, 조각마다 16~17개, 0.3ms씩 곱하면 5ms 남짓이다. 조각 사이에 클릭이나 키 입력 같은 태스크가 들어올 수 있다.

어떤 업데이트를 쪼갤지는 우선순위(lane)가 정한다. 클릭·키 입력에서 나온 업데이트(SyncLane), 드래그·스크롤 같은 연속 입력(InputContinuousLane), 이벤트 밖에서 생긴 일반 업데이트(DefaultLane)는 막는(blocking) 업데이트로 보고 `renderRootSync`로 끝까지 한 번에 렌더링한다. transition, Suspense 재시도, idle 업데이트일 때만 `renderRootConcurrent`로 쪼갠다. 그래서 `createRoot`를 쓴다고 모든 렌더링이 쪼개지는 건 아니다. 우선순위가 어떻게 정해지고, 쪼개진 렌더링이 급한 업데이트에 밀려 버려지는 과정은 [동시성 렌더링과 transition](/posts/react-concurrent-transitions)에서 자세히 본다.

양보는 Fiber와 Fiber 사이에서만 일어난다. 컴포넌트 함수 하나가 혼자 80ms를 쓰면 그 80ms는 쪼갤 수 없다. 시간 쪼개기는 "가벼운 컴포넌트가 많은" 트리에 듣고, 한 컴포넌트 안의 무거운 계산에는 `useMemo`로 다시 계산하지 않게 하거나 Web Worker로 옮기는 수밖에 없다.

## render 단계에서 부작용이 금지되는 이유

여기까지 오면 "렌더링은 순수해야 한다"는 규칙이 취향이 아니라 구조에서 나온 요구라는 게 보인다. 렌더 단계의 컴포넌트 함수 호출은 다음 중 어떤 일이든 겪을 수 있다.

중간에 멈췄다가 나중에 이어진다. 그 사이 바깥 값(전역 변수, `ref.current`, 외부 저장소)이 바뀌면 트리의 앞부분과 뒷부분이 서로 다른 값을 보고 렌더링된다. 이 문제가 tearing이고, 외부 저장소는 그래서 `useSyncExternalStore`로 읽어야 한다.

통째로 버려진다. 앞의 실험을 조금 바꿔, transition으로 `Item` 300개를 렌더링하는 도중 클릭을 한 번 넣었더니 `Item`이 358번 렌더링됐다. 58번은 클릭 업데이트에 밀려 버려진 렌더링이다. 그 58번 안에서 서버로 로그를 보냈거나 배열에 push를 했다면, 화면에 반영되지 않은 렌더링의 부작용만 남는다.

같은 입력으로 여러 번 불린다. 개발 모드의 `StrictMode`는 컴포넌트 함수를 일부러 두 번 부르고 결과 하나를 버린다. 에러가 나면 React가 한 번 더 렌더링해 보기도 한다.

그래서 부작용은 커밋 이후에 실행되는 곳에 둔다. 사용자 동작에 반응하는 코드는 이벤트 핸들러에, 화면이 반영된 뒤 바깥 세상과 맞추는 일은 effect에 둔다. effect는 커밋된 렌더링에서만, 커밋마다 한 번 실행된다는 보장이 있다.

## flags는 위로 모인다

렌더 단계가 끝나면 커밋 단계는 "어느 Fiber에 할 일이 있는지"를 알아야 한다. 트리 전체를 다시 걸으며 모든 Fiber를 확인하면 렌더링이 줄어든 의미가 없다.

React 17까지는 할 일이 있는 Fiber만 따로 이은 연결 리스트(effect list, `firstEffect`·`nextEffect`)를 만들어 커밋에서 그 리스트만 돌았다. React 18부터는 이 리스트를 없애고 `subtreeFlags`를 쓴다. `completeWork` 끝에서 부르는 `bubbleProperties`가 자식들의 `flags`와 `subtreeFlags`를 OR로 합쳐 부모의 `subtreeFlags`에 넣는다. 자식이 부모보다 먼저 완료되니, 루트까지 올라오면 루트의 `subtreeFlags`에 트리 전체의 할 일 종류가 모인다.

커밋 단계는 루트부터 내려가며 `subtreeFlags`를 본다. 어떤 서브트리의 `subtreeFlags`에 이번 단계에서 할 종류(예를 들어 mutation 단계라면 Placement, Update, ChildDeletion 등)가 없으면 그 아래로 내려가지 않는다. 바뀐 곳이 한 줄이면 커밋은 그 줄까지 가는 경로만 걷는다.

## useEffect는 언제 도나

"useEffect는 화면이 그려진 뒤에 돈다"는 설명은 대부분 맞지만 예외가 있다. layout effect 안에서 마이크로태스크와 `setTimeout(0)`을 하나씩 예약해 두고, 업데이트 종류만 바꿔 가며 순서를 찍었다.

```text
== click (discrete)
  layout v=1
  passive v=1
  microtask (from layout) v=1
  setTimeout0 (from layout) v=1
== setTimeout setState (default)
  layout v=2
  microtask (from layout) v=2
  passive v=2
  setTimeout0 (from layout) v=2
== startTransition
  layout v=3
  microtask (from layout) v=3
  passive v=3
  setTimeout0 (from layout) v=3
```

클릭으로 생긴 업데이트에서는 passive effect가 마이크로태스크보다도 먼저, 커밋이 끝나자마자 동기로 실행됐다. React 18부터 클릭·키 입력 같은 discrete 입력의 결과는 passive effect까지 동기로 비운다. 다음 입력이 들어오기 전에 앞 입력의 effect가 끝나 있어야 결과가 일관되기 때문이다. 일반 업데이트와 transition에서는 passive effect가 별도 태스크로 미뤄졌다. 이 실험은 Node라서 스케줄러가 `setImmediate`를 썼고, 브라우저라면 `MessageChannel` 태스크로 예약되어 보통 그 사이에 화면이 그려진다.

이걸 알면 실무에서 두 가지 판단이 쉬워진다. 첫째, 깜빡임 없이 처리해야 하는 일(요소 크기를 재서 툴팁 위치를 고치는 것)은 `useLayoutEffect`에 둔다. `useEffect`에 두면 일반 업데이트에서는 엉뚱한 위치가 한 프레임 그려졌다가 고쳐진다. 둘째, `useLayoutEffect`와 클릭에서 나온 `useEffect`는 그리기 전에 돌아서, 무거운 일을 넣으면 그대로 INP가 늘어난다. 데이터 요청이나 로그 전송은 그리는 것을 막을 이유가 없다.

새 렌더링이 시작되기 전에 React는 남은 passive effect를 먼저 비운다. React 19 소스에서는 스케줄러 태스크가 렌더링을 시작하기 전에 `flushPendingEffects`를 부르고, 그 안에서 `flushPassiveEffects`가 돈다. 이전 커밋의 effect가 아직 안 돌았는데 다음 업데이트가 오면, 그 effect를 먼저 실행하고 렌더링을 시작한다. effect가 "언젠가는 반드시, 다음 렌더링 전에는" 실행된다는 보장이 여기서 나온다.

## 프로파일에서 이 이름들을 읽는 법

처음의 Performance 녹화로 돌아가면 이제 막대를 읽을 수 있다. 개발 빌드나 압축하지 않은 React 빌드에서는 함수 이름이 그대로 보인다. 번들러가 압축한 프로덕션 빌드에서는 이름이 한두 글자로 바뀌니, 이름을 보려면 개발 빌드로 녹화한다. 개발 빌드는 검사 코드 때문에 느리니 절대 시간보다 어디에 시간이 몰렸는지를 본다.

`renderRootSync`와 `workLoopSync`가 길게 하나로 이어져 있으면 막는 우선순위의 렌더링이 쪼개지지 않고 돈 것이다. 그 안에서 `performUnitOfWork` 아래의 넓은 막대를 찾으면 시간을 많이 쓴 컴포넌트 함수 이름이 보인다. `workLoopConcurrentByScheduler`가 짧게 여러 번 반복되면 시간 쪼개기가 일하고 있는 것이다. 그런데도 입력이 늦다면 조각 하나 안의 특정 컴포넌트가 5ms를 혼자 넘기고 있지 않은지 본다.

`commitRoot` 아래가 길면 커밋 쪽 문제다. `commitMutationEffectsOnFiber`가 넓으면 DOM 변경이 많고, 그 직후에 브라우저의 Recalculate Style·Layout이 길게 붙는다. `commitLayoutEffectOnFiber` 아래에 내 `useLayoutEffect`가 넓게 보이면 그리기 전에 너무 많은 일을 하고 있다. `flushPassiveEffects`가 클릭 핸들러와 같은 태스크 안에 붙어 있으면 앞 절의 discrete 입력 경우다.

React 19.2부터는 개발 빌드에서 크롬 Performance 패널에 React 전용 트랙이 생긴다. Scheduler 트랙에는 Blocking, Transition, Suspense, Idle 우선순위별로 Render, Commit, Remaining Effects 구간이 표시되고, 버려진 렌더링은 Interrupted Render로 찍힌다. Components 트랙에는 컴포넌트별 렌더링 시간과 Mount·Update 같은 표시가 보인다. 함수 이름을 일일이 펼치지 않아도 "어느 우선순위의 렌더링이 버려지고 다시 시작됐는지"를 바로 볼 수 있다. 컴포넌트 단위로 왜 렌더링됐는지까지 보려면 React DevTools의 Profiler가 낫다. 그 사용법은 [React는 언제 다시 그리나](/posts/react-rerender)에 있다.

## 끊을 수 있는 계산과 끊을 수 없는 반영

React 15의 재귀는 시작하면 끝까지 가야 했다. Fiber는 트리의 각 자리를 `child`·`sibling`·`return`으로 이은 객체로 만들고 걷는 위치를 `workInProgress` 하나에 담아서, Fiber 하나마다 `shouldYield()`를 물을 수 있게 했다. 렌더 단계는 `current`와 짝을 이룬 두 번째 트리에서 일어나니 멈추고, 이어 가고, 버려도 화면에 흔적이 없다. 그 대가로 렌더링은 순수해야 한다. 커밋은 `subtreeFlags`를 따라 바뀐 곳만 내려가며 before mutation, mutation, layout을 동기로 끝내고, `useEffect`는 그 뒤에 돈다. 이 구조 위에서 우선순위를 나누고 낡은 렌더링을 버리는 이야기는 [동시성 렌더링과 transition](/posts/react-concurrent-transitions)에서 이어진다.

## 면접에서 나올 만한 질문

### Fiber는 무엇이고 왜 도입됐나요?

React 16에서 바꾼 재조정 엔진이자, 컴포넌트나 DOM 요소 하나마다 만들어지는 작업 단위 객체다. 예전 스택 재조정자는 트리를 재귀로 걸어서 시작하면 끝까지 멈출 수 없었다. Fiber는 `child`·`sibling`·`return` 포인터로 트리를 잇고 걷는 위치를 변수 하나에 들고 있어서, 작업을 Fiber 단위로 쪼개 멈추고 이어 가고 버릴 수 있다.

### current 트리와 workInProgress 트리는 어떻게 다른가요?

`current`는 지금 화면에 반영된 트리이고, `workInProgress`는 렌더 단계에서 만들고 있는 초안이다. 같은 자리의 두 Fiber가 `alternate`로 서로를 가리키고, `createWorkInProgress`가 이전 객체를 재사용한다. 커밋의 mutation 단계가 끝나면 `root.current`를 초안으로 바꾼다. 초안이 따로 있으니 렌더링을 중간에 버려도 화면에 흔적이 남지 않는다.

### render 단계와 commit 단계의 차이는요?

render 단계는 컴포넌트 함수를 부르고 이전 트리와 비교해 바꿀 내용을 계산한다. 순수해야 하고, 동시성 렌더링에서는 중단되거나 버려지거나 다시 실행될 수 있다. commit 단계는 계산 결과를 DOM에 반영하고 ref와 effect를 처리하며, before mutation, mutation, layout 순서로 동기로 끝낸다. 반쯤 바뀐 화면이 그려지지 않게 하려고 커밋은 끊지 않는다.

### useLayoutEffect와 useEffect는 정확히 언제 실행되나요?

`useLayoutEffect`는 커밋의 layout 단계에서 DOM을 바꾼 직후, 브라우저가 그리기 전에 동기로 실행된다. `useEffect`는 보통 커밋 뒤 별도 태스크로 미뤄져 그린 뒤에 돈다. 다만 클릭·키 입력 같은 discrete 입력에서 나온 업데이트는 React 18부터 커밋 끝에 passive effect까지 동기로 비운다. 둘 다 effect는 자식부터 부모 순서로 실행된다.

### 렌더링 중에 부작용을 일으키면 왜 안 되나요?

렌더 단계의 함수 호출은 커밋된다는 보장이 없다. 동시성 렌더링에서는 급한 업데이트에 밀려 버려지거나 중간에 멈췄다 이어지고, `StrictMode`는 일부러 두 번 부른다. 렌더 중 요청이나 전역 변경은 화면에 반영되지 않은 렌더링에서도 일어나고, 멈춘 사이 바깥 값이 바뀌면 화면 일부가 다른 값을 보는 tearing이 생긴다. 부작용은 이벤트 핸들러나 effect에 둔다.

### React는 렌더 작업을 얼마나 쪼개서 양보하나요?

`scheduler`가 작업 시작 후 `frameInterval`(기본 5ms)이 지나면 `shouldYield`에 참을 돌려주고, 이어서 할 일을 `MessageChannel` 태스크로 예약한다. 실측에서 0.3ms짜리 컴포넌트가 조각마다 16~17개씩 렌더링됐다. 다만 쪼개는 건 transition, Suspense 재시도, idle 같은 낮은 우선순위뿐이고 클릭이나 일반 업데이트는 끝까지 한 번에 렌더링한다. 컴포넌트 하나가 혼자 오래 걸리면 그 안은 쪼갤 수 없다.

### 커밋 단계는 바뀐 Fiber를 어떻게 찾나요?

React 18부터 `completeWork`의 `bubbleProperties`가 자식들의 flags를 부모의 `subtreeFlags`로 모은다. 커밋은 루트부터 내려가며 `subtreeFlags`에 해당 단계의 표시가 없는 서브트리는 건너뛴다. 17까지는 할 일이 있는 Fiber만 이은 effect list를 따로 만들었다.
