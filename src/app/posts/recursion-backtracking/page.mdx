옵션 조합을 미리 만들어 두려고 배열의 모든 부분집합을 구하는 함수를 짰다. 하나 고르고, 그 뒤를 재귀로 처리하고, 고른 걸 다시 빼는 익숙한 모양이다.

```js
function subsetsBuggy(nums) {
  const result = [], path = [];
  function dfs(start) {
    result.push(path);              // 지금까지 고른 것을 답에 넣는다
    for (let i = start; i < nums.length; i++) {
      path.push(nums[i]);           // 고른다
      dfs(i + 1);                   // 들어간다
      path.pop();                   // 되돌린다
    }
  }
  dfs(0);
  return result;
}
console.log(subsetsBuggy([1, 2, 3]));
```

```text
[

  [], [], [], []
]
```

개수는 2³ = 8개로 맞는데 전부 비어 있다. 중간에 `console.log(path)`를 찍어 보면 `[1]`, `[1, 2]`, `[1, 2, 3]`이 차례로 잘 만들어진다. 만들 때는 맞았는데 다 끝나고 보니 비어 있다. 원인은 한 줄이고, 고치는 것도 한 줄이다. 그런데 이 한 줄을 이해하려면 백트래킹이 상태 하나를 들고 어떻게 들어갔다 나오는지 봐야 한다.

이 글은 재귀를 "같은 모양의 작은 문제에 맡기기"로 보고, 그 위에 백트래킹(고르고, 들어가고, 되돌리기)을 쌓는다. 부분집합·조합·순열을 한 틀로 짜고, 같은 값이 섞일 때와 가지치기, N-Queens, 답이 폭발적으로 많을 때의 메모리 문제, 정규식 엔진 안의 백트래킹까지 따라간다. 재귀가 콜 스택을 얼마나 쓰고 언제 넘치는지는 [실행 컨텍스트와 콜 스택 글](/posts/js-execution-context)에서, 같은 계산을 기억해 두는 방법은 [메모이제이션 글](/posts/js-memoization)에서 다뤘다. 실행 결과는 모두 Node.js 22에서 돌린 값이다.

## 더 작은 같은 문제에 맡긴다

재귀 함수는 문제를 조금 줄여서 자기 자신에게 맡긴다. 배열의 합이라면 "첫 원소 + 나머지의 합"이고, 나머지의 합은 같은 함수가 구한다. 더 줄일 수 없을 만큼 작아지면(빈 배열) 바로 답을 낸다. 이 두 부분을 재귀 단계와 기저 조건(base case)이라고 한다.

```js
function sum(nums, i = 0) {
  if (i === nums.length) return 0;      // 기저 조건: 남은 게 없다
  return nums[i] + sum(nums, i + 1);    // 재귀 단계: 하나 떼고 나머지를 맡긴다
}
```

재귀를 짤 때 확인할 건 세 가지다. 기저 조건이 정말 도달 가능한가(`i + 1`이 아니라 `i`를 넘기면 끝나지 않는다). 매번 문제가 기저 조건 쪽으로 줄어드는가. 그리고 함수가 "자기 몫"만 하고 나머지는 믿고 맡기는가. 마지막이 가장 중요하다. 재귀 호출 안에서 무슨 일이 일어나는지 끝까지 따라가려 하면 머리가 터진다. "sum(nums, i + 1)은 i + 1부터의 합을 돌려준다"고 믿고, 지금 단계가 맞는지만 본다.

호출이 하나 일어날 때마다 콜 스택에 실행 컨텍스트가 하나 쌓인다. 위 `sum`은 원소 수만큼 깊어져서 수천~수만 개에서 `RangeError`가 난다. 이렇게 한 줄로 길게 내려가는 재귀는 반복문으로 바꾸는 게 맞다. 이 글의 백트래킹은 사정이 다르다. 깊이는 고르는 횟수(보통 n 이하)라 얕고, 대신 옆으로 가지가 엄청나게 많이 뻗는다. 문제는 스택이 아니라 시간이다.

## 고르고, 들어가고, 되돌린다

백트래킹은 답을 한 조각씩 만들어 가는 탐색이다. 지금까지 고른 조각(`path`)을 들고, 다음 조각의 후보를 하나씩 시도한다. 하나를 고르면 그 상태로 한 단계 더 들어가고, 거기서 할 수 있는 걸 다 하고 돌아오면 고른 걸 되돌려 다음 후보를 시도한다. 길 찾기에 비유하면 갈림길마다 한쪽 길로 끝까지 가 보고, 막히거나 다 봤으면 갈림길로 돌아와 다른 길로 가는 것이다.

## 기록한 답이 전부 같은 배열이었다

이제 처음 버그가 보인다. `result.push(path)`는 path의 지금 모습을 넣는 게 아니라, path라는 배열 하나를 가리키는 참조를 넣는다. 트리를 도는 동안 path는 하나뿐이고, 그 배열에 넣었다 뺐다를 반복한다. 결과 배열의 여덟 칸은 모두 같은 path를 가리키고, 탐색이 끝나 path가 비면 여덟 칸이 다 빈 배열로 보인다.

## 다음 후보를 고르는 규칙만 다르다

부분집합, 조합, 순열은 모두 같은 뼈대에서 후보를 고르는 규칙만 바꾼 것이다.

```js
// 조합: 1..n 중 k개. 순서가 상관없으니 뒤쪽 수만 후보다
function combine(n, k) {
  const result = [], path = [];
  (function dfs(start) {
    if (path.length === k) { result.push([...path]); return; }
    for (let i = start; i <= n; i++) { path.push(i); dfs(i + 1); path.pop(); }
  })(1);
  return result;
}

// 순열: 순서가 다르면 다른 답이다. 아직 안 쓴 것이 모두 후보다
function permute(nums) {
  const result = [], path = [], used = new Array(nums.length).fill(false);
  (function dfs() {
    if (path.length === nums.length) { result.push([...path]); return; }
    for (let i = 0; i < nums.length; i++) {
      if (used[i]) continue;
      used[i] = true; path.push(nums[i]);
      dfs();
      path.pop(); used[i] = false;
    }
  })();
  return result;
}
```

## 답의 개수가 곧 걸리는 시간이다

모든 답을 다 만드는 탐색은 답의 개수보다 빨라질 수 없다. 답 하나를 쓰는 데만 길이만큼 시간이 들고, 답의 개수는 n이 늘면 무섭게 커진다.

```text
permute n=8      40320      18ms
permute n=9     362880     157ms
permute n=10    3628800    1703ms
subsets n=20    1048576      14ms
subsets n=25   33554432     312ms
combine 20C10   184756      68ms
```

부분집합은 2ⁿ, 순열은 n!이다. n이 1 늘 때 부분집합은 두 배, 순열은 n배가 된다. 순열을 n = 10에서 11로 늘리면 시간이 11배가 되는 데서 끝나지 않는다. 같은 코드를 n = 11로 돌리자 이렇게 죽었다.

```text
FATAL ERROR: Ineffective mark-compacts near heap limit Allocation failed - JavaScript heap out of memory
```

11! = 39,916,800개의 배열을 모두 `result`에 담으려다 힙(이 환경에서 약 2GB)을 다 썼다. 답을 전부 모아서 돌려주는 API는 답이 많아지면 메모리부터 터진다. 실무에서 "모든 조합"을 다뤄야 한다면 답을 모으지 말고 하나 만들 때마다 처리하고 버린다. 같은 11!을 모으지 않고 세는 방법 두 가지를 따로 돌려 비교했다. 하나는 답마다 콜백을 부르고, 다른 하나는 제너레이터로 하나씩 꺼낸다.

```js
function forEachPermutation(nums, visit) {
  const path = [], used = new Array(nums.length).fill(false);
  (function dfs() {
    if (path.length === nums.length) { visit(path); return; } // 복사하지 않고 보여 주기만 한다
    for (let i = 0; i < nums.length; i++) {
      if (used[i]) continue;
      used[i] = true; path.push(nums[i]);
      dfs();
      path.pop(); used[i] = false;
    }
  })();
}
```

```js
function* permutations(nums) {
  const path = [], used = new Array(nums.length).fill(false);
  function* dfs() {
    if (path.length === nums.length) { yield path.slice(); return; }
    for (let i = 0; i < nums.length; i++) {
      if (used[i]) continue;
      used[i] = true; path.push(nums[i]);
      yield* dfs(); // 깊이마다 제너레이터가 한 겹씩 쌓인다
      path.pop(); used[i] = false;
    }
  }
  yield* dfs();
}
```

```text
callback n=11 count 39916800 3163ms heapUsed 4MB
generator n=11 count 39916800 37412ms heapUsed 35MB
```

콜백으로 넘기면 3.2초, 메모리 4MB였다. `function*`와 `yield*`로 만든 제너레이터는 필요할 때 하나씩 꺼낼 수 있어 우아하지만 37초가 걸렸다. 답 하나가 나올 때마다 깊이만큼 쌓인 제너레이터를 한 겹씩 거쳐 올라오기 때문이다. 답이 수천 개라면 제너레이터의 편함이 낫고, 수천만 개라면 콜백이나 반복문이 낫다. 어느 쪽이든 `visit`에 넘긴 path를 보관하려면 그때 복사해야 한다는 점은 처음 버그와 같다.

## 같은 값이 섞이면 같은 답이 또 나온다

`[1, 1, 2]`의 순열을 위 코드로 만들면 같은 답이 두 번씩 나온다. 첫 번째 1과 두 번째 1을 다른 원소로 보기 때문이다.

```text
naive  112 121 112 121 211 211
unique 112 121 211
```

`Set`에 문자열로 넣어 중복을 지울 수도 있지만, 그건 이미 같은 가지를 두 번 탐색한 뒤다. 탐색 자체를 막으려면 입력을 정렬해서 같은 값을 붙여 놓고, 같은 자리에서 같은 값을 두 번 고르지 않게 한다.

```js
function permuteUnique(nums) {
  nums = nums.slice().sort((a, b) => a - b); // 같은 값을 붙여 놓는다
  const result = [], path = [], used = [];
  (function dfs() {
    if (path.length === nums.length) { result.push([...path]); return; }
    for (let i = 0; i < nums.length; i++) {
      if (used[i]) continue;
      // 바로 앞의 같은 값이 아직 안 쓰였다면, 이 자리는 이미 그 값으로 시도했다
      if (i > 0 && nums[i] === nums[i - 1] && !used[i - 1]) continue;
      used[i] = true; path.push(nums[i]); dfs(); path.pop(); used[i] = false;
    }
  })();
  return result;
}
```

`!used[i - 1]` 조건이 하는 일은 이렇다. 같은 값이 여러 개면 늘 앞의 것부터 쓰도록 순서를 강제해서, 같은 값끼리 자리를 바꾼 경우를 한 번만 만든다. 조합과 부분집합에서는 `i > start && nums[i] === nums[i - 1]`이면 건너뛴다. 같은 단계(같은 for문) 안에서만 중복을 막고, 깊이 들어가서 같은 값을 또 고르는 건 허용한다는 뜻이다. 면접에서 `i > 0`과 `i > start`를 헷갈리면 답이 빠진다.

## 가망 없는 가지는 들어가지 않는다

백트래킹의 속도는 들어가지 않은 가지에서 나온다. 후보 `[2, 3, 6, 7]`에서 같은 수를 여러 번 써서 합 7을 만드는 조합(Combination Sum)을 찾아보자. 남은 합보다 큰 후보는 골라 봐야 음수가 될 뿐이다. 후보를 정렬해 두면 그런 후보를 만난 순간 그 뒤도 전부 크니 반복을 끝낼 수 있다.

```js
for (let i = start; i < cands.length; i++) {
  if (prune && cands[i] > remain) break; // 정렬돼 있으니 뒤는 더 크다
  path.push(cands[i]); dfs(i, remain - cands[i]); path.pop();
}
```

공격 확인을 매번 판 전체를 훑어서 하면 느리다. 열과 두 방향의 대각선을 집합으로 들고 있으면 O(1)에 확인된다. 같은 `↘` 대각선 위의 칸은 `row - col`이 같고, 같은 `↙` 대각선 위의 칸은 `row + col`이 같다.

```js
function nQueens(n) {
  const cols = new Set(), d1 = new Set(), d2 = new Set(), place = [];
  let solutions = 0, nodes = 0;
  (function dfs(row) {
    if (row === n) { solutions++; return; }
    for (let c = 0; c < n; c++) {
      nodes++;
      if (cols.has(c) || d1.has(row - c) || d2.has(row + c)) continue; // 공격받는 칸은 들어가지 않는다
      cols.add(c); d1.add(row - c); d2.add(row + c); place.push(c);
      dfs(row + 1);
      cols.delete(c); d1.delete(row - c); d2.delete(row + c); place.pop();
    }
  })(0);
  return { solutions, nodes };
}
```

```text
n  solutions      nodes   time
4          2         60    0.2ms
6          4        894    0.5ms
8         92      15720    5.1ms
10       724     348150   40.7ms
12     14200   10103868  855.0ms
brute n=8 solutions=92 leaves=16777216 192.7ms
```

`nodes`는 칸을 확인한 횟수다. 8-Queens의 답은 92개이고 15,720번 확인으로 찾았다. 가지치기 없이 행마다 아무 열에나 놓은 뒤 끝에서 검사하면 8⁸ = 16,777,216가지 배치를 다 만들어야 한다. 그래도 n이 2 늘 때마다 확인 횟수가 스무 배 넘게 늘었다(10에서 12로 갈 때 35만 번에서 1천만 번). 모든 답을 세는 일은 n이 조금만 커져도 금방 감당할 수 없게 된다.

답이 하나만 필요하다면 이야기가 다르다. 첫 답을 찾는 즉시 `true`를 돌려 모든 단계에서 빠져나오게 하면 된다.

```text
first only n=12: nodes=3066 0.3ms placement=0,2,4,7,9,11,5,10,1,6,8,3
first only n=20: nodes=3992510 371.8ms placement=0,2,4,1,3,12,14,11,17,19,16,8,15,18,7,9,6,13,5,10
```

12-Queens의 모든 답은 1천만 번 확인이 필요했지만 첫 답은 3,066번이면 나온다. 실무의 백트래킹(일정 배치, 좌석 배정, 설정 조합 검증)은 대부분 "되는 배치 하나"가 필요하다. 이럴 때는 유망한 후보부터 시도하는 순서가 성능을 크게 바꾼다. 스도쿠라면 후보가 가장 적은 칸부터 채우는 식이다.

## 같은 계산을 또 하는 재귀

백트래킹과 헷갈리기 쉬운 경우가 있다. 피보나치를 재귀로 그대로 짜면 `fib(n - 1)`과 `fib(n - 2)`가 같은 아래 문제를 몇 번이고 다시 푼다.

```text
fib(35)=9227465 calls=29860703 119ms
memo fib(35)=9227465 calls=69 0.19ms
```

호출이 3천만 번이다. 결과를 `Map`에 기억해 두면 69번으로 끝난다. 이건 백트래킹이 아니다. 백트래킹은 path가 달라서 같은 상태를 두 번 방문하는 일이 거의 없고, 그래서 기억해 둘 게 없다. 반대로 피보나치처럼 같은 인자로 같은 계산을 반복한다면(겹치는 부분 문제) 기억해 두는 게 답이고, 이게 [동적 계획법](/posts/dynamic-programming)의 출발점이다. 기억하는 방법과 캐시 키 고르는 법은 [메모이제이션 글](/posts/js-memoization)에 있다.

구분하는 질문은 이렇다. "재귀 함수의 인자만으로 결과가 정해지고, 같은 인자가 여러 번 나오나?" 그렇다면 기억한다. "결과가 지금까지 고른 경로 전체에 달려 있나?" 그렇다면 백트래킹이고, 줄일 방법은 가지치기다. 단어 쪼개기(Word Break)처럼 처음엔 백트래킹으로 보였는데 "i번째 글자부터 쪼갤 수 있나"라는 인자 하나로 답이 정해지는 문제는 기억하는 순간 지수 시간이 다항 시간으로 떨어진다.

## 정규식 엔진 안의 백트래킹

백트래킹은 면접 문제에만 있는 게 아니다. 자바스크립트를 포함한 대부분의 정규식 엔진은 백트래킹으로 동작한다. `/^(a+)+$/`로 `"aaaa!"`를 검사하면, 엔진은 a 네 개를 `(a+)` 묶음으로 나누는 방법을 하나 고르고, 끝의 `!` 때문에 실패하면 되돌아가 다른 방법을 고른다. 나누는 방법의 수를 직접 세 봤다.

```js
// "a"가 n개인 문자열을 (a+)+ 로 나누는 방법의 수
function ways(n) {
  if (n === 0) return 1;
  let s = 0;
  for (let k = 1; k <= n; k++) s += ways(n - k); // 첫 묶음에 k개를 쓰고 나머지를 맡긴다
  return s;
}
```

```text
n=1:1  n=2:2  n=3:4  n=4:8  n=10:512  n=20:524288
backtracking n=20 6.6ms
backtracking n=22 34.4ms
backtracking n=24 165.0ms
backtracking n=26 516.0ms
```

2ⁿ⁻¹가지다. 실패할 문자열에서는 엔진이 이 가지를 다 시도한 뒤에야 "안 맞는다"고 답한다. 글자 몇 개마다 시간이 몇 배씩 뛰는 게 위 측정이다. 이게 ReDoS이고, 운영에서 미치는 영향과 방어(입력 길이 제한, 중첩 반복 피하기)는 [Big O 글](/posts/big-o-notation)의 마지막 부분에서 다뤘다. 여기서 볼 점은 원인이 이 글의 탐색 트리와 같다는 것이다. 가지치기 없는 백트래킹이 지수 개의 가지를 다 돈다.

V8에는 백트래킹 없이 선형 시간에 도는 실험적인 정규식 엔진도 있다. Node 22에서는 플래그를 켜야 `l` 플래그를 쓸 수 있다.

```bash
# 실험 기능이라 운영 기본값으로 쓰지 않는다
node --enable-experimental-regexp-engine redos.js
```

```text
linear engine n=26 0.0ms
linear engine n=10000 0.6ms
```

플래그 없이 `new RegExp("^(a+)+$", "l")`을 만들면 `Invalid flags supplied to RegExp constructor 'l'` 에러가 난다. 역참조나 전후방 탐색처럼 백트래킹이 필요한 문법은 이 엔진에서 쓸 수 없다. 실무에서는 문제가 되는 패턴을 고치는 쪽이 먼저다.

## 깊은 트리를 만났을 때

재귀가 자연스러운 곳은 트리다. 댓글과 대댓글, 메뉴, 폴더, JSON처럼 자기 안에 같은 모양을 품은 데이터는 재귀로 짜면 코드가 데이터 모양을 그대로 따른다. React에서도 댓글 트리를 `Comment`가 자식 댓글마다 `Comment`를 다시 렌더링하는 재귀 컴포넌트로 많이 짠다.

```jsx
function Comment({ node }) {
  return (
    <li>
      {node.text}
      {node.replies.length > 0 && (
        <ul>{node.replies.map((r) => <Comment key={r.id} node={r} />)}</ul>
      )}
    </li>
  );
}
```

이런 재귀는 백트래킹과 반대로 가지는 적고 깊이가 데이터에 달려 있다. 사용자가 만든 데이터라면 깊이가 수천 단계일 수 있다. 렌더링도, 트리를 펼치는 함수도 그 깊이만큼 스택을 쓰니, 깊이에 상한을 두거나(대댓글은 몇 단계까지만) 명시적인 스택을 쓰는 반복문으로 바꾼다. 재귀를 반복문으로 바꾸는 방법은 [실행 컨텍스트 글](/posts/js-execution-context)의 "깊이를 스택에서 빼내는 방법"에, 트리 순회의 반복문 구현은 [이진 트리 글](/posts/ds-binary-tree-bst)에, 그래프에서의 DFS는 [BFS·DFS 글](/posts/ds-graph-bfs-dfs)에 있다.

## 되돌릴 수 있어서 다 볼 수 있다

재귀는 문제를 같은 모양의 작은 문제에 맡기는 방법이고, 백트래킹은 그 위에서 상태 하나를 고쳐 쓰며 고르고, 들어가고, 되돌리는 탐색이다. 부분집합·조합·순열은 후보를 고르는 규칙만 다르고, 답을 기록할 때는 복사해야 하며, 같은 값은 정렬한 뒤 같은 단계에서 한 번만 고른다. 걸리는 시간은 답의 개수와 들어간 가지 수가 정하니, 가지치기로 헛걸음을 줄이고 답이 많으면 모으지 말고 흘려보낸다. 같은 인자의 계산이 반복된다면 백트래킹이 아니라 기억할 차례다.

## 면접에서 나올 만한 질문

### 재귀 함수를 짤 때 꼭 확인할 것은 무엇인가요?

기저 조건에 실제로 도달하는지, 호출마다 문제가 기저 조건 쪽으로 줄어드는지 본다. 그리고 재귀 호출이 더 작은 문제를 맞게 푼다고 믿고 지금 단계만 맞게 짠다. 깊이가 입력 크기에 비례하면 수천~수만 단계에서 콜 스택이 넘치니, 그럴 때는 반복문이나 명시적 스택으로 바꾼다.

### 백트래킹이 무엇이고 완전 탐색과 어떻게 다른가요?

답을 한 조각씩 고르며 만들다가, 더 갈 수 없거나 다 봤으면 마지막 선택을 되돌리고 다음 후보를 시도하는 탐색이다. 모든 경우를 끝까지 만든 뒤 검사하는 완전 탐색과 달리, 중간에 답이 될 수 없다고 판단되면 그 아래 가지를 통째로 건너뛴다. 8-Queens에서 완전 탐색은 1,677만 가지를 만들지만 백트래킹은 칸 확인 15,720번으로 92개 답을 모두 찾았다.

### 부분집합을 구했는데 결과가 전부 빈 배열입니다. 왜 그런가요?

답을 기록할 때 path 배열의 참조를 넣었기 때문이다. 탐색 내내 path는 하나뿐이라 결과의 모든 칸이 같은 배열을 가리키고, 탐색이 끝나 path가 비면 전부 빈 배열로 보인다. `result.push([...path])`처럼 기록하는 순간의 사본을 넣는다.

### 부분집합, 조합, 순열의 개수와 구현 차이는 무엇인가요?

부분집합은 2ⁿ, k개 조합은 nCk, 순열은 n!개다. 조합과 부분집합은 앞에서 고른 것보다 뒤의 원소만 후보로 삼아 같은 묶음이 두 번 나오지 않게 하고, 순열은 매번 처음부터 보되 이미 쓴 원소를 `used`로 건너뛴다. 실제로 순열은 n = 11에서 결과를 다 모으다 힙 메모리가 부족해 프로세스가 죽었다.

### 입력에 중복 값이 있을 때 같은 답이 나오지 않게 하려면 어떻게 하나요?

정렬해서 같은 값을 붙여 놓고, 같은 단계에서 같은 값을 두 번 고르지 않는다. 조합·부분집합은 `i > start && nums[i] === nums[i - 1]`이면 건너뛰고, 순열은 `nums[i] === nums[i - 1] && !used[i - 1]`이면 건너뛴다. 결과를 `Set`으로 거르는 방법은 같은 가지를 이미 탐색한 뒤라 느리다.

### 가지치기를 넣었는데 답이 줄었다면 무엇이 잘못된 건가요?

답이 있는 가지까지 잘랐다는 뜻이다. 가지치기는 헛걸음만 줄이고 답은 바꾸지 않아야 한다. 예를 들어 `cands[i] > remain`일 때 `break`하려면 후보가 오름차순으로 정렬돼 있어야 하고, 정렬하지 않았다면 뒤쪽의 작은 후보를 놓친다. 가지치기 전후로 답의 개수가 같은지 테스트로 확인한다.

### 백트래킹과 동적 계획법은 어떻게 구분하나요?

재귀 함수의 결과가 인자 몇 개만으로 정해지고 같은 인자가 반복해서 나오면 동적 계획법(메모이제이션)으로 줄일 수 있다. 피보나치 35는 호출이 3천만 번에서 기억해 두니 69번이 됐다. 결과가 지금까지 고른 경로 전체에 달려 있어 같은 상태가 거의 반복되지 않으면 백트래킹이고, 그때 줄이는 수단은 가지치기다.

### 정규식이 특정 입력에서 서버를 멈추게 하는 이유는 무엇인가요?

자바스크립트 정규식 엔진이 백트래킹으로 동작해서, 중첩 반복 같은 패턴은 실패할 입력에서 지수 개의 분할을 다 시도하기 때문이다. `/^(a+)+$/`는 a가 n개면 2ⁿ⁻¹가지를 시도하고, 26글자에 0.5초가 걸렸다. 중첩 반복을 없애고 입력 길이를 제한하는 게 먼저이고, V8의 선형 시간 엔진은 아직 실험 플래그 뒤에 있다.
