이 글은 "실제 서비스 사례" 시리즈에서 우버가 만든 워크플로 엔진 Cadence를 다룬다. 같은 회사의 다른 글로는 지도를 육각형으로 나눈 [Uber H3](/posts/rw-uber-h3-geospatial), MySQL 위에 쌓은 저장소 [Uber Schemaless와 Docstore](/posts/rw-uber-schemaless-docstore), 마이크로서비스를 도메인으로 묶은 [Uber DOMA](/posts/rw-uber-doma)가 있다. 여러 서비스에 걸친 일을 단계와 보상으로 나누는 일반 원리는 [사가 패턴 글](/posts/saga-pattern)에, 상태 대신 사건을 쌓는 원리는 [이벤트 소싱 글](/posts/event-sourcing)과 [지갑을 이벤트 소싱으로 만들기](/posts/sd-wallet-event-sourcing)에 있다. 같은 문제를 서비스 안에 박아 넣는 라이브러리로 푼 사례는 [Airbnb Skipper](/posts/rw-airbnb-skipper)에 있다.

2019년 11월 우버 엔지니어링 블로그는 Cadence 커뮤니티 행사의 발표 넷을 소개하면서, 첫 발표에서 Maxim Fateev가 한 말을 옮겼다. 우버의 비동기 마이크로서비스 구조에서는 "단순한 코드가 콜백의 늪이 된다." 가입 흐름, 주문 처리, 머신러닝 파이프라인처럼 요청 하나로 끝나지 않는 일은 서비스 여러 개를 부르고, 실패하면 다시 부르고, 몇 시간이나 며칠을 기다려야 한다. 그 일을 콜백과 큐와 상태 표로 엮다 보면 원래 업무가 무엇이었는지 코드에서 읽을 수 없게 된다.

## 이 글이 기대는 자료

우버와 Cadence 프로젝트가 직접 낸 자료를 썼다. 우버 블로그 글 두 편([Conducting Better Business with Uber's Open Source Orchestration Tool, Cadence](https://www.uber.com/blog/open-source-orchestration-tool-cadence-overview/), 2019년 11월 / [Cadence Workflow Joins the Cloud Native Computing Foundation](https://www.uber.com/blog/cadence-workflow-joins-the-cloud-native-computing-foundation/), 2025년 10월), [cadence-workflow/cadence 저장소](https://github.com/cadence-workflow/cadence)의 README와 비결정성 오류 문서(2020년 1월 작성, 2024년 11월 수정), [Cadence 공식 문서 저장소](https://github.com/cadence-workflow/Cadence-Docs)의 개념 문서와 프로젝트 블로그 글(2023~2025년)이다. Cadence 공동 창시자들이 세운 Temporal은 Temporal이 직접 낸 회사 소개와 공식 문서만 봤다.

## 콜백의 늪과 상태 표 훑기

Cadence 문서의 워크플로 개념 페이지는 문제를 예 하나로 보여 준다. 고객이 체험 기간이 있는 서비스에 가입한다. 체험이 끝날 때까지 해지하지 않으면 매달 요금을 청구하고, 청구할 때마다 메일을 보내고, 고객은 언제든 해지할 수 있어야 한다. 업무 규칙은 수십 줄이면 쓸 수 있다. 어려운 건 이걸 장애에 강하고 확장되게 만드는 일이다.

문서는 흔한 두 방법을 차례로 짚는다. 첫째는 DB 중심이다. 애플리케이션이 주기적으로 표를 훑어 특정 상태의 고객을 찾아 처리하고 상태를 갱신한다. 문서는 고객 상태 기계가 금세 아주 복잡해진다고 적었다. 카드 청구나 메일 발송은 하류 시스템이 멈추면 실패하니 오래, 이상적으로는 지수적으로 재시도해야 하고, 외부 시스템이 넘치지 않게 속도를 줄여야 하고, 처리할 수 없는 레코드 하나가 전체를 막지 않게 해야 한다. 특정 상태의 레코드를 계속 물어보는 일은 DB에도 비효율적이다.

둘째는 타이머 서비스와 큐다. 갱신을 큐에 넣고 워커가 꺼내 DB를 고치고 다음 큐에 또 넣는다. DB를 계속 훑지 않으니 더 잘 확장된다. 하지만 문서는 프로그래밍 모델이 더 복잡하고 오류가 나기 쉽다고 적었다. 큐 시스템과 DB 사이에 트랜잭션으로 묶인 갱신이 대개 없기 때문이다. 이 틈이 [트랜잭셔널 아웃박스](/posts/transactional-outbox)가 메우려는 바로 그 틈이다.

Cadence의 답은 이 업무를 함수 하나로 쓰는 것이다. 청구 서비스가 하루 동안 멈춰 있으면 청구 호출에서 하루 동안 막혀 있어도 되고, 30일을 자는 것도 평범한 동작이다. 문서는 이 함수를 "장애를 모르는 상태 있는(fault-oblivious stateful) 워크플로"라고 부르고, 지역 변수와 그 안에서 만든 스레드까지 프로세스나 Cadence 서비스의 장애에 영향을 받지 않는다고 적었다. 워커가 죽으면 어떻게 하느냐는 질문에 문서의 답은 "하지 않는다"다.

## 코드는 일꾼이 돌리고, 상태는 서버가 쥔다

Cadence 서버는 워크플로 코드를 직접 돌리지 않는다. 토폴로지 문서에 따르면 사용자의 워크플로 코드는 서버 바깥의 워커 프로세스에 있다. 서버는 워크플로가 처리해야 할 이벤트를 결정 작업(decision task)에 담아 워커에 주고, 워커는 코드를 돌려 다음에 무엇을 할지(결정)를 서버에 돌려준다. 외부 세계와 하는 모든 일, 즉 서비스 호출, DB 갱신, 파일 다운로드는 액티비티(activity)로 감싸고, 액티비티 워커가 액티비티 작업을 받아 실행한다.

서버 쪽은 서비스 넷으로 나뉜다. 워커의 요청을 받는 무상태 Front End, 워크플로 단계를 조율하는 핵심 로직이 있는 History Service, 실행할 작업을 그 작업을 처리할 수 있는 워커와 짝지어 주는 Matching Service, 그리고 보관(archival) 같은 내부 작업을 하는 Internal Worker Service다. 저장소로는 Cassandra, MySQL, PostgreSQL이 일급 플러그인으로 지원되고, 복잡한 조건으로 워크플로를 찾는 고급 검색에는 Elasticsearch, OpenSearch, Pinot을 Kafka와 함께 쓴다. 2019년 우버 블로그가 소개한 Samar Abbas의 아키텍처 발표도 Front End, History, Matching과 Cassandra 백엔드 구조를 다뤘다.

Cadence 서비스는 여러 사용자가 같이 쓴다. 문서에 따르면 우버에서는 서비스 하나를 100개가 넘는 애플리케이션이 쓰고, 어떤 외부 사용자는 애플리케이션마다 Cadence 서비스를 따로 띄운다. 워크플로 수에도 사실상 확장 한계가 없다고 적었다. 막혀 있는 워크플로는 워커에서 안전하게 내렸다가 필요할 때 같은 워커나 다른 워커에서 되살릴 수 있어서, 워커 하나가 열린 워크플로 수백만 개를 다룰 수 있다는 것이다. 2025년 7월 프로젝트 블로그는 우버가 수명이 몇 초에서 몇 년까지인 워크플로를 수십억 개 관리한다고 적었다.

## 27줄짜리 일지

워크플로가 장애를 모를 수 있는 비결은 기록이다. 저장소의 비결정성 오류 문서는 Cadence가 이벤트 소싱으로 설계됐다고 설명한다. 워크플로 상태 기계 전체를 저장하는 대신, 상태를 바꾼 사건 하나하나를 히스토리 이벤트(history event)로 저장한다. 같은 문서가 든 예는 이렇다(옵션 부분만 줄였다). 액티비티 A를 실행하고, 1분 자고, A의 결과로 액티비티 B를 실행하고, 1시간 자고 끝나는 Go 워크플로다.

```go
func Workflow(ctx workflow.Context) error {
	ao := workflow.ActivityOptions{ /* 시한 등 */ }
	ctx = workflow.WithActivityOptions(ctx, ao)
	var a int
	if err := workflow.ExecuteActivity(ctx, activityA).Get(ctx, &a); err != nil {
		return err
	}
	workflow.Sleep(time.Minute)          // time.Sleep이 아니다
	if err := workflow.ExecuteActivity(ctx, activityB, a).Get(ctx, nil); err != nil {
		return err
	}
	workflow.Sleep(time.Hour)
	return nil
}
```

아무 문제 없이 돌면 히스토리는 27개 이벤트가 된다. 문서에 실린 그대로 옮긴다.

```text

ID:2		DecisionTaskScheduled : first decision triggered by server
ID:3		DecisionTaskStarted
ID:4		DecisionTaskCompleted
ID:5		ActivityTaskScheduled : activityA is scheduled by decision
ID:6		ActivityTaskStarted   : started by worker
ID:7		ActivityTaskCompleted : completed with result of var a
ID:8		DecisionTaskScheduled : triggered by ActivityCompleted
ID:9		DecisionTaskStarted
ID:10		DecisionTaskCompleted
ID:11		TimerStarted : decision scheduled a timer for 1 minute
ID:12		TimerFired : fired after 1 minute
ID:13		DecisionTaskScheduled : triggered by TimerFired
ID:14		DecisionTaskStarted
ID:15		DecisionTaskCompleted
ID:16		ActivityTaskScheduled: activityB scheduled by decision with param a
ID:17		ActivityTaskStarted : started by worker
ID:18		ActivityTaskCompleted : completed with nil as error
ID:19		DecisionTaskScheduled : triggered by ActivityCompleted
ID:20		DecisionTaskStarted
ID:21		DecisionTaskCompleted
ID:22		TimerStarted : decision scheduled a timer for 1 hour
ID:23		TimerFired : fired after 1 hour
ID:24		DecisionTaskScheduled : triggered by TimerFired
ID:25		DecisionTaskStarted
ID:26		DecisionTaskCompleted
ID:27		WorkflowCompleted     : completed by decision
```

읽는 법은 이렇다. 결정 작업은 늘 예약(Scheduled), 시작(Started), 완료(Completed) 세 줄로 나온다. 첫 결정 작업은 서버가 만들고, 그 뒤로는 워크플로가 기다릴 만한 사건이 다음 결정 작업을 만든다. 액티비티 완료(7, 18), 타이머 만료(12, 23) 다음에 곧바로 결정 작업 예약(8, 13, 19, 24)이 오는 이유다.

문서는 `ActivityTaskStarted` 같은 사건은 결정을 만들지 않는다고 적었다. 그리고 결정 작업이 진행 중인 동안(시작과 완료 사이)에는 다른 이벤트를 히스토리에 쓰지 않는다. 그사이 신호(signal)가 오면 버퍼에 두었다가 결정이 끝난 뒤 쓴다.

## 다른 일꾼이 이어받을 때: 재생

워커가 죽으면 무슨 일이 생길까. 비결정성 오류 문서는 Cadence 워크플로를 "분산 운영체제 위에서 오래 도는 프로세스"에 빗댄다. 프로세스의 상태와 배치는 Cadence 서버가 쥐고, 워커는 코드를 돌릴 CPU와 메모리를 댄다. 대부분의 시간에는 한 워커가 워크플로를 쥐고 보통 프로세스처럼 돌지만, 소유권이 다른 워커로 넘어갈 수 있다. 일반 운영체제와 달리 처음부터 다시 시작하지 않고 이전 상태에서 이어 간다.

이어 가려면 상태 기계를 다시 세워야 한다. 이 과정을 히스토리 재생(history replay)이라 부른다. 새 워커는 워크플로 코드를 처음부터 돌리면서 히스토리를 한 줄씩 맞춰 본다. 문서의 규칙에서 가장 중요한 한 줄은 이것이다.

"히스토리 재생 중에는 액티비티, 타이머, 자식 워크플로를 다시 실행하지 않는다." `ExecuteActivity(A)`에 닿으면 A를 다시 부르지 않고 히스토리 7번에 기록된 결과 a를 돌려준다. `Sleep(1분)`에 닿으면 기다리지 않고 12번에서 이미 만료됐다는 사실을 받는다. 그렇게 히스토리 끝까지 오면 앞 워커가 멈춘 자리, 22번의 1시간 타이머를 기다리는 자리에 서게 된다.

재생은 워커가 죽을 때만 일어나지 않는다. 문서에 따르면 워커는 여러 워크플로의 스택을 메모리에 들고 있는데(이를 sticky cache라 한다), 메모리가 모자라면 오래 안 쓴 것부터 내리고 필요할 때 다시 세운다. 스택이 오류로 낡았을 때도 재생한다. 그래서 운영에서는 sticky 실행을 켜 두는 게 기본이고, 덕분에 매번 전체를 재생하지 않는다. 같은 이유로 sticky 실행은 숨은 비결정성 오류를 가린다. 문서는 문제를 찾을 때 일부 워커만 sticky 실행을 끄고 돌려, 결정 작업마다 히스토리 전체를 재생하게 하라고 권한다.

이게 [이벤트 소싱](/posts/event-sourcing)이 워크플로 엔진에 쓰인 모습이다. [지갑을 이벤트 소싱으로 만들기](/posts/sd-wallet-event-sourcing)에서 사건을 다시 읽어 잔액을 계산했다면, Cadence는 사건을 다시 읽어 함수의 실행 지점과 지역 변수를 되살린다.

## 같은 순서로 같은 일을 시켜야 한다

재생에는 대가가 하나 있다. 문서의 표현으로 워크플로 코드는 결정적이어야 한다. 여러 번 실행해도 정확히 같은 결과를 내야 한다. 그래서 워크플로 코드에서 바깥 API를 부를 수 없다. 바깥 호출은 언제든 실패하거나 다른 값을 줄 수 있기 때문이다. 바깥 세계와의 모든 소통은 액티비티로 하고, 지금 시각을 얻거나, 자거나, 스레드를 만들 때도 Cadence API를 써야 한다.

저장소 문서는 무엇이 비결정성 오류를 일으키는지 목록으로 적었다.

- 액티비티, 타이머, 자식 워크플로, 외부 신호, 취소 요청의 실행 순서를 바꾸기
- 액티비티의 시그니처를 바꾸기
- 타이머 기간을 바꾸기
- `workflow.Now()` 대신 `time.Now()` 쓰기
- `workflow.Go` 대신 Go의 `go`로 고루틴 띄우기
- `workflow.Channel` 대신 Go의 채널 쓰기

반대로 액티비티 입출력 구조체의 세부를 바꾸거나, 로그·지표처럼 히스토리에 영향이 없는 코드를 고치거나, 액티비티의 재시도 정책을 바꾸는 건 괜찮다고 적었다. `time.Sleep()`은 비결정성 오류를 내지는 않지만 동작하지 않는다고 적었다. 서버가 쥔 타이머가 아니라 워커 프로세스만 재우니, 워커가 바뀌면 기다린 사실이 남지 않기 때문으로 보인다(이 이유는 내 해석이다).

오류의 종류는 셋이다. 재생한 코드가 히스토리보다 결정을 적게 내는 "결정 누락(missing decision)", 더 많이 내는 "추가 결정(extra decision)", 다른 결정을 내는 "결정 불일치(decision mismatch)"다. 문서의 예를 그대로 쓰면, 1시간 타이머를 기다리는 중에 `Sleep(time.Hour)` 줄을 지우고 워커를 재시작하면 누락이다. B 하나만 실행하던 자리에서 B와 C를 나란히 실행하게 바꾸면 추가 결정이다. B를 C로 바꾸면 불일치다.

마지막 테스트는 엔진마다 다르다. Cadence 저장소 문서는 타이머 기간 변경을 비결정성 원인으로 꼽았지만, [Temporal 공식 문서](https://docs.temporal.io/workflow-definition)는 타이머 기간을 바꾸는 것을 비결정성 오류를 내지 않는 작은 변경으로 적고, Java·Python·Go에서 0으로 또는 0에서 바꾸는 경우만 예외로 둔다.

같은 계보의 엔진이라도 무엇이 안전한 변경인지는 엔진과 버전마다 문서로 확인해야 한다는 뜻이다. 다섯 번째 테스트도 볼 만하다. 같은 코드 변경이라도 그 변경 지점까지 아직 가지 않은 워크플로에는 문제가 없다. 그래서 비결정성 오류는 배포 직후 모든 워크플로가 아니라 "그 지점을 이미 지난" 오래된 워크플로에서만 터진다.

## 코드를 바꿀 때 쓰는 도구들

몇 년씩 도는 워크플로가 있으니 코드는 바뀔 수밖에 없다. 문서와 프로젝트 블로그에 나온 도구는 이렇다.

`workflow.GetVersion()`이 기본이다. 바뀌는 지점에 버전을 표시해, 그 지점을 이미 옛 코드로 지난 워크플로는 옛 길로, 아직 지나지 않은 워크플로는 새 길로 가게 한다. 앞의 "결정 누락" 예라면 줄을 그냥 지우지 않고 버전으로 감싼다. 문서가 든 코드는 이렇다.

```go
// 1시간 타이머를 지우고 싶을 때: 줄을 그냥 지우지 않고 버전으로 감싼다
v := workflow.GetVersion(ctx, "delete_timer", workflow.DefaultVersion, 1)
if v == workflow.DefaultVersion {
	// 이 지점을 옛 코드로 이미 지난 워크플로: 기록과 맞게 타이머를 그대로 둔다
	workflow.Sleep(time.Hour)
} else {
	// 아직 이 지점에 오지 않은 워크플로: 새 코드대로 타이머 없이 간다
}
```

Go 버전 관리 문서에 따르면 `GetVersion`은 새 실행에서 처음 불릴 때 히스토리에 표시(marker)를 남긴다. 그래서 같은 워크플로를 나중에 재생하면 늘 같은 갈래로 간다. 대신 이 `if`는 옛 버전으로 지난 워크플로가 모두 끝날 때까지 코드에 남아 있어야 한다. 몇 달짜리 워크플로라면 몇 달 동안이다. 버전 갈래가 쌓이는 것이 이 방식의 운영 비용이다.

비슷한 목적으로 결정적이지 않은 값을 히스토리에 한 번만 기록해 두는 `workflow.SideEffect()`가 있다.

버전 표시 없이 깨지는 변경을 배포해 버렸다면 더 곤란하다. 문서는 이 상황을 이렇게 설명한다. 배포 뒤 일부 워크플로는 새 코드로 진행했고 일부는 막혀 있다. 되돌리면 막힌 쪽은 살지만 새 코드로 진행한 쪽이 막힌다. 그래서 되돌릴 수도 없다. 문서의 해법은 결정을 내린 바이너리의 체크섬(`BinaryChecksum`, Git 참조로 설정하길 권한다)과 결정 시각(`workflow.Now()`)으로 갈라, 나쁜 배포 전 바이너리로 결정했거나 배포 시작 전에 결정한 워크플로는 옛 길로 보내는 것이다.

마지막 수단은 리셋이다. 일반 운영체제의 프로세스는 앞으로만 가지만, Cadence는 히스토리를 목록으로 저장하니 이전 상태로 돌아갈 수 있다. 문서에 따르면 리셋은 히스토리를 트리로 다뤄 기존 히스토리에서 새 가지를 뻗고, 새 실행 ID로 다시 시작한다. 보관 기간이 끝나 히스토리가 지워지기 전까지는 여러 번 리셋해도 기록을 잃지 않는다.

배포 전에 잡는 도구도 생겼다. 2023년 8월 프로젝트 블로그는 리플레이어(replayer)와 섀도어(shadower)를 소개했다. 리플레이어는 실제 워크플로의 히스토리를 바뀐 코드로 다시 돌려 보는 테스트 도구이고, 섀도어는 그 위에서 조건에 맞는 운영 워크플로들을 찾아 히스토리를 받아 계속 재생해 본다. 2025년 7월 블로그는 버전 기능의 한계를 짚었다.

버전 변경은 하위 호환이지만 상위 호환이 아니어서, 새 버전으로 진행한 워크플로가 롤백 중에 옛 워커로 다시 배치되면 막히거나 실패한다. 그래서 코드 배포와 새 로직의 활성화를 떼어 놓는 쪽으로 버전 API를 고쳤다고 적었다. 먼저 새 코드를 모든 워커에 깔고, 그 뒤에 새 길을 켠다. [기능 플래그](/posts/feature-flags)로 배포와 출시를 나누는 것과 같은 발상이다.

## 워크플로 하나의 크기에도 끝이 있다

워크플로 수에는 한계가 거의 없지만 워크플로 하나의 크기에는 있다. 문서는 워크플로 하나가 액티비티를 10만 개 실행할 수는 없다고 적었다. 히스토리가 그만큼 길어지고, 재생할 때마다 그 길이를 다시 읽어야 하기 때문이다. 이럴 때 자식 워크플로를 쓴다. 부모 하나가 자식 1,000개를, 자식이 각각 액티비티 1,000개를 실행하면 액티비티 100만 개다.

주기적으로 도는 일은 자식 워크플로가 실행을 이어 가며(continue as new) 반복하게 하면 부모의 히스토리가 불어나지 않는다. 문서는 그래도 크기가 정해진 문제라면 워크플로 하나로 시작하라고 권한다. 자식과 부모는 상태를 나누지 못하고 비동기 신호로만 이야기해서, 오히려 더 복잡해질 수 있다.

워크플로 ID에도 규칙이 있다. 시작할 때 클라이언트가 고객 ID나 주문 ID 같은 업무 ID를 워크플로 ID로 준다. Cadence는 한 도메인 안에서 같은 ID로 열린 워크플로가 동시에 하나만 있게 보장하고, 같은 ID로 또 시작하면 `WorkflowExecutionAlreadyStarted` 오류를 낸다.

이미 끝난 같은 ID의 워크플로가 있을 때의 동작은 재사용 정책으로 고르고, 기본값은 앞의 실행이 실패했을 때만 허용하는 `AllowDuplicateFailedOnly`다. 주문 ID를 워크플로 ID로 쓰면 같은 주문의 결제 흐름이 두 번 시작되지 않는다. 엔진 차원의 [멱등 키](/posts/idempotency-key)인 셈이다.

다만 이 보장은 워크플로 단위이고 액티비티 단위가 아니다. 액티비티는 재시도 정책에 따라 다시 실행되고, 워커가 액티비티를 끝냈다는 보고를 잃으면 다시 실행될 수 있다. [사가 패턴 글](/posts/saga-pattern)이 짚은 대로 엔진을 써도 각 단계는 여전히 멱등해야 한다.

## Cadence에서 Temporal로, 그리고 CNCF로

Temporal 회사 소개 페이지에 따르면 Maxim Fateev와 Samar Abbas는 아마존에서 Simple Workflow Service의 첫 공개판을 함께 냈고, Samar는 그 뒤 마이크로소프트에서 Azure Durable Task Framework를 만들었다.

둘은 2015년 우버에서 다시 만나 Cadence를 함께 만들었다. 2019년 우버 블로그는 Cadence를 2017년에 오픈소스로 공개했다고 적었다. 두 사람은 그 뒤 Temporal을 세웠고, 지금 Samar는 CEO, Maxim은 CTO다. Temporal 소개는 Cadence를 "Temporal의 전신"이라 부른다.

Cadence는 우버에 남아 계속 발전했다. 2024년 11월 프로젝트 블로그에 따르면 `uber`, `uber-go`, `uber-common` 조직에 흩어져 있던 저장소를 모두 `cadence-workflow` 조직으로 모았다. 2025년 10월 우버 블로그는 Cadence가 CNCF에 합류했다고 발표했다. 글에 따르면 Cadence는 우버와 다른 회사에서 수천 개의 쓰임을 돌리고 있고, 생태계가 150개가 넘는 회사에 닿았다. 프로젝트 관리를 사내 도구에서 GitHub로 옮기고, 로드맵을 공개하고, 커뮤니티 회의를 열겠다고 적었다.

결정적 코드와 히스토리 재생이라는 뼈대는 두 프로젝트가 같다. Temporal 문서도 워크플로 코드가 재생을 위해 결정적이어야 하고, API 호출이나 DB 쿼리 같은 비결정적 일은 액티비티에 두라고 적는다. 앞에서 본 타이머 기간처럼 세부 규칙은 갈라졌다.

## 공개 자료가 말하지 않는 것

이 글의 근거는 우버와 Cadence 프로젝트가 고른 자료다. 2019년 블로그는 행사 영상을 소개하는 글이라 깊이가 얕고, 문서는 쓰는 법을 설명하려고 쓴 글이라 우버 안에서 어떤 장애가 있었는지, Cadence 클러스터를 몇 개 몇 대로 운영하는지, 히스토리 저장에 비용이 얼마나 드는지는 말하지 않는다. "수십억 개의 워크플로", "100개가 넘는 애플리케이션" 같은 숫자는 어느 시점의 숫자인지 문서마다 분명하지 않다. Cadence와 Temporal이 왜 따로 가게 됐는지도 두 쪽 모두 공개 자료에서 자세히 말하지 않는다.

## 우리 팀에 워크플로 엔진이 필요할까

Cadence가 맞는 조건은 문서의 예에 있다. 몇 분에서 몇 달 걸리는 업무, 서비스 여러 개를 부르고 실패하면 오래 재시도해야 하는 단계, 사람의 승인이나 외부 신호를 기다리는 대기, 그리고 그 흐름을 코드 한곳에서 읽고 싶은 요구다. 이런 흐름이 서비스마다 여럿이고, 엔진을 운영할 팀이 있다면 상태 표와 큐와 크론으로 직접 엮는 것보다 싸다.

맞지 않는 조건도 분명하다. 요청 하나로 끝나는 일, 단계가 둘셋이고 몇 초 안에 끝나는 흐름은 엔진이 오히려 지연과 복잡도를 더한다. Cadence는 Front End, History, Matching, 저장소(그리고 선택적으로 Kafka와 Elasticsearch)를 운영해야 하는 분산 시스템이다.

엔진이 멈추면 그 위의 모든 워크플로가 시작도 진행도 못 한다. 이 의존을 피하려고 서비스 안에 박아 넣는 라이브러리를 만든 회사도 있다. [Airbnb Skipper](/posts/rw-airbnb-skipper)가 그 예이고, 대가로 언어와 서비스를 넘는 조율을 포기했다.

처음부터 들이면 드는 비용은 "결정적 코드"라는 사고방식이다. 팀 전체가 `time.Now()` 대신 `workflow.Now()`를 쓰고, 순서를 바꾸는 변경마다 버전을 표시하고, 배포 전에 운영 히스토리로 재생 테스트를 돌려야 한다. 한 번 놓치면 몇 달 된 워크플로가 막히고, 되돌리기도 쉽지 않다는 것을 문서가 직접 보여 준다.

작은 팀이 엔진 없이도 지금 가져올 만한 것은 두 가지다. 하나는 업무 ID를 흐름의 ID로 쓰는 습관이다. 주문 ID 하나로 그 주문의 흐름이 하나만 돌게 하면 중복 실행의 대부분을 막는다. 다른 하나는 바깥 호출과 판단 로직을 나누는 습관이다. 결제 호출, 메일 발송처럼 바깥과 이야기하는 부분을 멱등한 함수로 떼어 두면, 나중에 엔진을 들이든 사가를 직접 짜든 그대로 액티비티가 된다.

엔진을 들이기로 했다면 처음 몇 달은 워크플로 하나, 팀 하나로 시작해 버전 표시와 재생 테스트 습관부터 들이는 편이 안전하다. 문서가 권하듯 크기가 정해진 문제는 워크플로 하나로 시작하고, 자식 워크플로는 히스토리가 정말 길어질 때 꺼낸다.

비슷한 신호가 보이면 이 순서로 본다. 상태 표를 훑는 크론이 늘고, 재시도 횟수와 다음 시도 시각을 담는 열이 표마다 생기고, "이 주문이 지금 어디서 멈췄나"를 답하려면 로그 여러 곳을 뒤져야 한다면 워크플로 엔진을 검토할 때다. 엔진을 쓰는 중에 배포 직후 오래된 워크플로만 막힌다면 비결정적 변경을 의심하고, 그 워크플로의 히스토리를 받아 바뀐 코드로 재생해 본다. 워커 수를 늘렸는데 처리량이 오르지 않으면 sticky cache가 넘쳐 재생이 잦아졌는지, 히스토리가 너무 길어져 재생 자체가 무거워졌는지 본다.

## 면접에서 나올 만한 질문

### Cadence는 어떤 문제를 풀려고 만들었나요?

우버의 비동기 마이크로서비스 구조에서 여러 서비스를 부르고, 실패하면 오래 재시도하고, 몇 시간에서 며칠을 기다리는 업무가 콜백과 큐와 상태 표로 흩어져 읽을 수 없게 되는 문제다. Cadence 문서는 DB를 훑는 방식은 상태 기계가 복잡해지고, 큐와 타이머 방식은 큐와 DB 사이 트랜잭션이 없어 오류가 나기 쉽다고 짚는다. Cadence는 그 업무를 함수 하나로 쓰게 하고, 상태와 타이머와 재시도를 서버가 맡는다.

### 워커가 죽으면 워크플로는 어떻게 이어지나요?

Cadence는 워크플로 상태 대신 상태를 바꾼 사건을 히스토리로 저장한다. 다른 워커가 이어받으면 워크플로 코드를 처음부터 다시 돌리면서 히스토리와 맞춰 보는데, 이미 끝난 액티비티와 타이머는 다시 실행하지 않고 기록된 결과를 돌려준다. 히스토리 끝에 닿으면 앞 워커가 멈춘 자리에 서게 된다. 이걸 히스토리 재생이라 한다.

### 워크플로 코드는 왜 결정적이어야 하나요?

재생할 때 코드가 히스토리에 기록된 것과 같은 순서로 같은 결정을 내려야 기록과 맞출 수 있기 때문이다. 그래서 바깥 API 호출은 액티비티로 빼고, 시각·잠자기·스레드도 `workflow.Now`, `workflow.Sleep`, `workflow.Go` 같은 엔진 API를 쓴다. 어기면 결정이 모자라거나, 넘치거나, 달라지는 비결정성 오류가 난다.

### 실행 중인 워크플로가 있는데 코드를 바꿔야 하면 어떻게 하나요?

바뀌는 지점을 `GetVersion`으로 표시해, 그 지점을 이미 옛 코드로 지난 워크플로는 옛 길로 보내고 아직 안 지난 워크플로만 새 길로 보낸다. 배포 전에는 운영 히스토리를 바뀐 코드로 재생하는 리플레이어·섀도어로 확인한다. 이미 깨진 배포를 냈다면 바이너리 체크섬과 결정 시각으로 갈라 주거나 워크플로를 이전 지점으로 리셋한다. 2025년부터는 코드 배포와 새 로직 활성화를 떼어 롤백도 안전하게 만드는 쪽으로 버전 API를 고쳤다.

### 비결정성 오류는 왜 배포 직후 모든 워크플로가 아니라 일부에서만 나나요?

바뀐 지점을 이미 지난 워크플로만 히스토리와 새 코드가 어긋나기 때문이다. 그 지점까지 아직 가지 않은 워크플로는 재생할 때 맞출 기록이 없어 새 코드대로 진행한다. 게다가 sticky cache에 올라 있는 워크플로는 재생 자체를 하지 않으니, 캐시에서 내려가거나 워커가 바뀌는 순간에야 터진다. 그래서 문제를 찾을 때는 일부 워커의 sticky 실행을 끈다.

### 워크플로 엔진을 쓰면 액티비티는 멱등하지 않아도 되나요?

아니다. Cadence가 보장하는 건 같은 워크플로 ID로 열린 워크플로가 하나라는 것이고, 액티비티는 재시도 정책에 따라, 또는 완료 보고를 잃었을 때 다시 실행될 수 있다. 결제 같은 액티비티는 결제사의 멱등 키나 자체 중복 검사를 여전히 가져야 한다. 엔진은 흐름을 이어 줄 뿐, 바깥 세계에 두 번 일어난 일을 되돌려 주지는 않는다.

### Cadence와 Temporal은 어떤 관계인가요?

Cadence는 Maxim Fateev와 Samar Abbas가 2015년 우버에서 함께 만들었고 2017년에 오픈소스가 됐다. 두 사람은 뒤에 Temporal을 세웠고, Temporal은 스스로 Cadence를 전신이라 부른다. Cadence는 우버에서 계속 발전해 2025년 CNCF에 합류했다. 결정적 코드와 히스토리 재생이라는 뼈대는 같지만 타이머 기간 변경을 허용하는지 같은 세부 규칙은 다르다.

### 우리 서비스가 우버의 100분의 1 규모라면 Cadence 같은 엔진을 들이나요?

규모보다 흐름의 모양으로 정한다. 며칠씩 기다리고 여러 서비스를 오래 재시도하는 흐름이 여럿이면 작은 규모에서도 엔진이 상태 표와 크론보다 싸다. 반대로 몇 초짜리 두세 단계 흐름뿐이라면 엔진 운영과 결정적 코드 규칙의 비용이 더 크다. 엔진 클러스터 자체가 새 의존이 된다는 점도 따져야 하고, 그게 싫다면 서비스 안에 박아 넣는 라이브러리 방식도 있다.
