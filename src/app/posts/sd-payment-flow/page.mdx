이 시리즈에서 이 글의 자리: 앞 글 [게임 리더보드 설계 ②](/posts/sd-leaderboard-scaling)로 리더보드 장이 끝났다. 이 글부터 두 편은 면접의 "결제 시스템을 설계해 보세요"를 다룬다. 이 글은 돈이 어디서 어디로 움직이는지, 카드 번호를 만지지 않고 결제를 받는 법, 그리고 모든 돈의 움직임을 적는 복식부기 원장을 맡는다. 같은 장의 다음 글 [결제 시스템 설계 ②: 재시도, 웹훅, 대사로 한 번만 청구하기](/posts/sd-payment-reliability)는 일이 틀어졌을 때를 다룬다. 그다음 장은 [디지털 지갑 설계 ①](/posts/sd-wallet-transfer)이다.

여러 판매자가 입점한 쇼핑몰을 만든다. 구매자는 장바구니에 shop-7의 12,000원짜리 물건과 shop-9의 8,000원짜리 물건을 담고 결제 버튼을 누른다. 우리는 구매자의 카드에서 20,000원을 받아, 수수료를 떼고 판매자들에게 나눠 줘야 한다.

처음 떠오르는 구현은 결제 폼에서 카드 번호를 받아 서버에서 카드사에 청구하는 것이다. 이건 첫 줄부터 막힌다. 카드사와 직접 연결하려면 계약과 인증이 필요하고, 카드 번호를 받는 순간 서버 전체가 카드 정보 보안 규정의 감사 대상이 된다. 그래서 거의 모든 서비스는 결제 대행사를 끼운다. 이 글은 그 구조를 작은 실험으로 직접 돌려 보며 따라간다. 결제 대행사는 흉내 낸 가짜 서버(Node 22)이고, 원장은 PostgreSQL 16에 만들었다.

## 돈은 누구에게서 누구에게 가나

등장인물부터 정리한다.

- 구매자와 카드 발급사: 구매자의 카드를 발급한 은행이나 카드사다. 실제로 돈이 빠져나가는 곳이다.
- 카드 네트워크: Visa, Mastercard처럼 발급사와 가맹점 쪽 은행 사이에서 승인과 정산을 중계한다.
- 결제 대행사(PSP, payment service provider): 우리 대신 카드 네트워크와 연결하고, 카드 정보를 받아 결제를 처리해 준다. 국내에서는 흔히 PG사라고 부른다.
- 우리(플랫폼): 구매자에게 돈을 받아 판매자에게 나눠 준다.
- 판매자: 최종적으로 돈을 받을 사람이다.

돈은 두 방향으로 움직인다. 구매자에게서 우리 쪽으로 들어오는 페이인(pay-in)과, 우리 쪽에서 판매자에게 나가는 페이아웃(pay-out)이다. 둘 사이에는 시간 차가 있다. 결제 버튼을 누른 순간 실제 돈이 오가는 게 아니라, 이 단계에서는 "받을 권리"가 생기고 실제 돈은 며칠 뒤 정산으로 들어온다. 기간은 PSP와의 계약과 결제 수단에 따라 다르다.

## 카드 번호를 만지지 않는 결제 페이지

카드 번호를 직접 받지 않으려면 결제 화면 자체를 PSP에게 맡긴다. PSP가 호스팅하는 결제 페이지로 보내거나, PSP가 주는 위젯을 우리 페이지 안에 띄운다. 카드 번호는 그 화면에서 PSP로 바로 가고, 우리는 결과만 받는다. 카드 정보를 다루는 회사가 지켜야 하는 보안 기준(PCI DSS)의 범위가 이렇게 크게 줄어든다.

## 결제 하나를 두 개의 표로

장바구니 하나에 판매자가 둘이면 PSP에 결제를 두 건으로 등록할 수도, 한 건으로 받고 내부에서 나눌 수도 있다. 여기서는 판매자별로 나눠 등록했다. 데이터도 두 층으로 둔다.

```sql
-- 장바구니 하나 = 결제 이벤트 하나
CREATE TABLE payment_events (
  checkout_id text PRIMARY KEY,
  buyer_id    text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

-- 판매자별로 나뉜 결제 건. id를 PSP에 멱등성 키로 보낸다
CREATE TABLE payment_orders (
  id            text PRIMARY KEY,
  checkout_id   text NOT NULL REFERENCES payment_events,
  seller_id     text NOT NULL,
  amount        bigint NOT NULL CHECK (amount > 0),   -- 원 단위 정수
  currency      char(3) NOT NULL DEFAULT 'KRW',
  status        text NOT NULL DEFAULT 'NOT_STARTED'
                CHECK (status IN ('NOT_STARTED', 'EXECUTING', 'SUCCESS', 'FAILED')),
  psp_intent_id text UNIQUE,
  updated_at    timestamptz NOT NULL DEFAULT now()
);
```

결제 건의 상태는 네 가지다. 만들어졌을 때 `NOT_STARTED`, PSP에 등록하면 `EXECUTING`, PSP가 결과를 알려 주면 `SUCCESS`나 `FAILED`. 상태는 앞으로만 간다. `SUCCESS`가 된 건이 `EXECUTING`으로 돌아가는 일은 없다. 이 규칙이 다음 글에서 웹훅이 두 번 오거나 늦게 올 때 우리를 지켜 준다.

```text
│ 0       │ 'po_2001_a' │ 'shop-7'  │ '12000' │ 'SUCCESS' │ 'pi_1'        │
│ 1       │ 'po_2001_b' │ 'shop-9'  │ '8000'  │ 'FAILED'  │ 'pi_2'        │
```

실험의 결과 표에서 `amount`가 `'12000'`처럼 따옴표 안의 문자열로 나온 게 보인다. Node의 `pg` 드라이버는 `bigint`를 기본으로 문자열로 돌려준다. JavaScript 숫자는 2의 53제곱이 넘는 정수를 정확히 담지 못하니 안전한 선택이다. 이걸 귀찮다고 `parseFloat`로 바꾸는 순간 다음 절의 문제로 돌아간다.

## 금액은 정수로 적는다

장바구니 합계를 실수로 계산하면 이런 일이 생긴다.

```js
console.log(0.1 + 0.2);
let total = 0; for (let i = 0; i < 10; i++) total += 0.1; console.log(total, total === 1);
console.log(Math.round(1.005 * 100) / 100);
console.log(1999 * 3);        // 센트 단위 정수
```

```text
0.30000000000000004
0.9999999999999999 false
1
5997
```

0.1달러 열 번이 1달러가 아니고, 1.005를 소수 둘째 자리에서 반올림했더니 1.01이 아니라 1이 됐다. 이진 실수는 0.1 같은 십진 소수를 정확히 담지 못하기 때문이다. 한 번은 작은 오차지만 하루 수백만 건을 더하고 나누면 장부가 맞지 않는다. PostgreSQL에서도 같다.

```text
     float8_sum      | numeric_sum | float8_mul 
---------------------+-------------+------------
 0.30000000000000004 |         0.3 |      59.97
```

`float8`의 덧셈은 같은 오차가 나고 `numeric`은 정확하다. 그래서 금액은 화폐의 가장 작은 단위의 정수로 적는다. 원화는 1원, 달러는 1센트다. 19.99달러는 1999센트로 저장하고, 화면에 보일 때만 소수점을 찍는다. 정수로 담기 어려운 계산(환율, 이자)이 있으면 `numeric`을 쓰고, 반올림 규칙을 한곳에 정해 둔다. API로 주고받을 때도 JSON 숫자 대신 정수나 문자열로 보내야 받는 쪽 언어의 실수로 바뀌지 않는다. 통화는 `KRW`, `USD` 같은 세 글자 코드(ISO 4217)를 함께 둔다. 통화마다 소수 자릿수가 달라서 금액만으로는 크기를 알 수 없다.

## 돈은 생기지도 사라지지도 않는다

이제 장부다. 결제 서비스의 상태 표만으로는 "지금 판매자 shop-7에게 줄 돈이 얼마인가", "PSP가 아직 안 보낸 돈이 얼마인가"에 답하기 어렵다. 그래서 돈의 움직임을 따로 적는 원장(ledger)을 둔다.

원장의 규칙은 오래된 회계 방식인 복식부기를 따른다. 돈이 움직이면 반드시 두 군데 이상에 적는다. 한쪽이 늘면 다른 쪽이 그만큼 줄고, 한 거래의 모든 줄을 더하면 0이다. 돈이 갑자기 생기거나 사라지는 기록은 구조상 들어갈 수 없다.

계정(account)은 돈이 머무는 칸이다. 이 쇼핑몰에는 다섯 개면 된다.

이 글에서는 한 줄에 금액 하나를 두고, 들어오는 쪽(차변)은 양수, 나가는 쪽(대변)은 음수로 적는다. 그러면 "합이 0"을 숫자 하나로 검사할 수 있다.

```sql
CREATE TABLE ledger_txns (
  id          bigserial PRIMARY KEY,
  kind        text NOT NULL,                  -- 'pay_in', 'settlement', 'pay_out'
  ref         text NOT NULL,                  -- payment_order id 등
  created_at  timestamptz NOT NULL DEFAULT now(),
  UNIQUE (kind, ref)                          -- 같은 결제를 두 번 적지 않는다
);
CREATE TABLE ledger_entries (
  txn_id  bigint NOT NULL REFERENCES ledger_txns,
  account text   NOT NULL REFERENCES accounts,
  amount  bigint NOT NULL CHECK (amount <> 0) -- 차변 +, 대변 -
);

-- 커밋 직전에 거래마다 합이 0인지 검사한다
CREATE CONSTRAINT TRIGGER ledger_balanced
  AFTER INSERT OR UPDATE ON ledger_entries
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION check_txn_balanced();
```

`check_txn_balanced()`는 그 줄의 거래 번호로 합을 구해 0이 아니면 예외를 던지는 함수다. 트리거를 `DEFERRABLE INITIALLY DEFERRED`로 만들어 줄을 하나씩 넣는 중간에는 검사하지 않고, `COMMIT` 직전에 검사하게 했다. 빈 원장에 10,000원 결제(수수료 330원)를 적고, 이어서 일부러 틀린 거래와 같은 결제를 두 번 적는 거래를 시도했다.

```sql
BEGIN;
INSERT INTO ledger_txns (kind, ref) VALUES ('pay_in', 'po_1001_a');
INSERT INTO ledger_entries (txn_id, account, amount) VALUES
  (currval('ledger_txns_id_seq'), 'psp_receivable', 10000),   -- PSP가 우리에게 줄 돈이 늘었다
  (currval('ledger_txns_id_seq'), 'seller:shop-7',  -9670),   -- 판매자에게 줄 돈이 늘었다
  (currval('ledger_txns_id_seq'), 'fee_revenue',     -330);   -- 우리 수수료 수익
COMMIT;

BEGIN;
INSERT INTO ledger_txns (kind, ref) VALUES ('pay_in', 'po_bad');
INSERT INTO ledger_entries (txn_id, account, amount) VALUES
  (currval('ledger_txns_id_seq'), 'psp_receivable', 10000),
  (currval('ledger_txns_id_seq'), 'seller:shop-7',  -9670);   -- 수수료 줄을 빠뜨렸다
COMMIT;

BEGIN;
INSERT INTO ledger_txns (kind, ref) VALUES ('pay_in', 'po_1001_a'); -- 같은 결제 건을 또 적는다
ROLLBACK;
```

수수료 줄을 빠뜨린 거래는 커밋에서 통째로 거부됐고, 같은 결제 건을 다시 적으려던 거래는 `(kind, ref)` 유니크 제약에 걸렸다. 남은 것은 첫 거래뿐이다.


모든 계정의 합이 0이다. 장부 어딘가가 틀리면 이 합이 0이 아니게 되거나, 다음 글에서 볼 대사에서 바깥 기록과 어긋난다. 음수 잔액이 어색하게 보이지만 "판매자에게 줄 돈" 같은 부채 계정은 원래 대변 쪽에 쌓이는 계정이라 이 규칙에서는 음수로 나온다. 화면에 보일 때만 부호를 뒤집는다.

규칙 하나 더. 원장의 줄은 고치거나 지우지 않는다. 잘못 적었으면 반대 방향의 거래를 새로 적어 되돌린다. 환불도 원래 결제를 지우는 게 아니라 반대 방향의 거래다. 그래야 "언제 무엇이 왜 바뀌었는지"가 장부에 그대로 남는다.

## 하루가 지나 돈이 실제로 움직일 때

원장을 비우고 앞 절의 호스티드 페이지 실험(12,000원, 수수료 3.3%인 396원)을 다시 돌린 뒤, 다음 날 PSP가 PSP 수수료 2%인 240원을 떼고 11,760원을 보냈다고 하자. 그리고 판매자 shop-7에게 11,604원을 보낸다.

```sql
-- PSP 정산: 받을 돈이 줄고, 은행 잔고와 PSP 수수료가 생긴다
INSERT INTO ledger_entries (txn_id, account, amount) VALUES
  (currval('ledger_txns_id_seq'), 'bank',           11760),
  (currval('ledger_txns_id_seq'), 'psp_fee',          240),

-- 판매자 지급: 줄 돈이 줄고, 은행 잔고가 준다

```

## 지갑은 원장에서 나온 숫자다

판매자 화면에는 "출금 가능 금액 11,604원"이 보여야 한다. 이 숫자를 매번 원장 전체에서 합산하면 거래가 쌓일수록 느려진다. 그래서 계정별 잔액을 따로 들고 있는 지갑(wallet)을 둔다. 결제가 성공할 때 원장에 줄을 적으면서 지갑 잔액도 함께 바꾼다.

여기서 원칙은 원장이 원본이라는 것이다. 지갑은 원장을 빨리 읽으려고 미리 합쳐 둔 값이다. 둘이 어긋나면 원장을 믿고 지갑을 고친다. 원장과 지갑을 같은 PostgreSQL에 두면 한 [트랜잭션](/posts/acid-transactions)으로 함께 바꿀 수 있어 어긋날 일이 적다. 서비스를 나눠 서로 다른 DB에 두면 그때부터 [분산 트랜잭션](/posts/distributed-transactions-2pc)이나 [사가](/posts/saga-pattern) 같은 문제가 된다. 사용자끼리 돈을 보내는 지갑을 여러 샤드에 두는 경우는 [디지털 지갑 설계 ①](/posts/sd-wallet-transfer)에서 따로 다룬다.

## 결제 서비스 안의 역할 나누기

## 결제가 몇 시간 걸릴 때

대부분의 카드 결제는 몇 초 안에 끝나지만, 늦게 끝나는 경우가 있다. 위험 검사에 걸려 사람이 검토하거나, 카드사가 추가 본인 인증(3D Secure 같은)을 요구하거나, 계좌 이체처럼 결제 수단 자체가 느린 경우다.

이때 결제 건은 `EXECUTING`에 머문다. 화면에는 "결제 확인 중"을 보여 주고, 결과는 PSP의 웹훅으로 받는다. 끝나면 메일이나 앱 알림으로 알린다. 웹훅을 주지 않는 PSP라면 상태 조회 API를 주기적으로 부른다. 웹훅을 주는 PSP라도 웹훅이 사라질 수 있으니, 오래 `EXECUTING`에 머문 건을 찾아 PSP에 직접 물어보는 작업을 함께 둔다. 이 작업은 다음 글에서 실제로 돌려 본다.

## 결제 문의가 들어오면

- "결제했는데 주문이 결제 대기로 나온다." 결제 건 상태가 `EXECUTING`인지 보고, PSP 관리 화면에서 그 등록 번호의 상태를 본다. PSP는 성공인데 우리만 `EXECUTING`이면 웹훅이 오지 않았거나 처리 중 실패한 것이다. 웹훅 수신 로그와 응답 코드를 본다.
- "판매자 정산금이 수수료 계산과 1원 다르다." 수수료를 실수로 계산했거나, 반올림 규칙이 결제할 때와 정산할 때 다른지 본다. 원장의 거래 줄을 그대로 보여 주면 어디서 1원이 생겼는지 설명할 수 있다.
- "장부 합계가 0이 아니다." 합이 0이 되게 막는 장치가 DB에 없고 애플리케이션 코드에만 있으면 생긴다. 특정 거래 번호별로 합을 구해 0이 아닌 거래부터 찾는다.
- 리다이렉트 주소의 결과 값만 보고 주문을 완료하는 코드가 있는지 정기적으로 확인한다. 실패한 결제가 성공으로 기록되는 가장 흔한 길이다.

## 할인 금액을 판매자별로 나누기

장바구니 전체에 3,000원 쿠폰을 썼다면, 판매자별 결제 건에 금액 비율대로 나눠 넣어야 한다. 정수로 나누면 나머지가 생기고, 나눈 합이 정확히 3,000원이 되어야 장부가 맞는다. 흔히 쓰는 방법은 이렇다. 각자 몫을 내림하고, 남은 원을 소수 부분이 큰 순서대로 1원씩 준다(소수 부분이 같으면 앞쪽부터).

`allocate(total, weights)`를 짜 보자. `total`은 나눌 정수 금액, `weights`는 각 결제 건의 금액이다. 정수 배열을 돌려주고, 합은 반드시 `total`이다.

  solution={`function allocate(total, weights) {
  const sum = weights.reduce((a, b) => a + b, 0);
  if (sum === 0) return weights.map(() => 0);
  const raw = weights.map((w) => (total * w) / sum);
  const out = raw.map(Math.floor);
  let left = total - out.reduce((a, b) => a + b, 0);
  // 소수 부분이 큰 순서, 같으면 앞쪽부터 1원씩
  const order = raw
    .map((r, i) => [r - Math.floor(r), i])
    .sort((a, b) => b[0] - a[0] || a[1] - b[1]);
  for (let j = 0; left > 0; j++, left--) out[order[j][1]]++;
  return out;
}`}

각자 반올림하면 셋으로 나눈 1,000원이 333 × 3 = 999원이 되어 1원이 사라진다. 이런 1원이 쌓이면 장부의 합이 맞지 않는다. 어느 규칙을 쓰든 나눈 합이 원래 금액과 같은지를 테스트로 묶어 둔다.

## 다음에 읽을 글

정리하면 이렇다. 카드 번호는 PSP의 결제 화면이 받고, 우리는 결과를 웹훅으로 받는다. 브라우저 리다이렉트는 화면용이지 증거가 아니다. 장바구니는 결제 이벤트, 판매자별 결제는 결제 건으로 나누고, 결제 건 ID를 PSP에 멱등성 키로 보낸다. 금액은 가장 작은 화폐 단위의 정수다. 모든 돈의 움직임은 합이 0인 복식부기 거래로 원장에 적고, 줄은 고치지 않고 반대 거래로 되돌린다. 지갑 잔액은 원장에서 나온 사본이다.

여기까지는 모든 요청이 한 번에 성공하는 이야기였다. 다음 글 [결제 시스템 설계 ②](/posts/sd-payment-reliability)에서는 PSP 응답이 끊기고, 웹훅이 두 번 오거나 아예 안 오고, 우리 장부와 PSP 기록이 어긋나는 상황을 가짜 PSP로 하나씩 재현한다.

## 면접에서 나올 만한 질문

### 결제 시스템에서 PSP를 쓰는 이유는요?

카드 네트워크와 직접 연결하려면 계약과 인증, 보안 감사가 필요하고, 카드 번호를 받으면 그 데이터를 다루는 모든 시스템이 카드 보안 기준(PCI DSS)의 범위에 들어간다. PSP는 카드 네트워크 연결과 카드 정보 처리를 대신해 주고, 호스티드 결제 페이지나 위젯을 쓰면 카드 번호가 우리 서버를 아예 지나지 않는다. 직접 연결은 그 투자를 감당할 큰 회사들의 선택이다.

### 결제 성공은 리다이렉트로 판단하면 안 되나요?

안 된다. 리다이렉트 주소는 사용자의 브라우저를 거쳐서 결과 값을 얼마든지 바꿀 수 있고, 사용자가 창을 닫으면 아예 오지 않는다. 결제 상태는 서명된 웹훅이나 PSP 상태 조회 API로 확정하고, 리다이렉트는 어느 결제의 결과 화면을 보여 줄지 고르는 데만 쓴다.

### 금액을 float로 저장하면 안 되는 이유는요?

이진 실수는 0.1 같은 십진 소수를 정확히 담지 못해서 0.1을 열 번 더해도 1이 아니고, 반올림 결과도 예상과 다르다. 하루 수백만 건이 쌓이면 장부가 맞지 않는다. 금액은 원이나 센트 같은 가장 작은 단위의 정수로 저장하고, 필요하면 `numeric`을 쓰며, API에서도 정수나 문자열로 주고받는다.

### 복식부기 원장을 쓰는 이유는요?

모든 돈의 움직임을 두 계정 이상에 적고 한 거래의 합이 0이 되게 해서, 돈이 근거 없이 생기거나 사라지는 기록을 구조적으로 막는다. 계정별 잔액이 언제 어떤 거래로 바뀌었는지 끝까지 추적할 수 있고, 바깥 기록과 맞춰 보는 대사의 기준이 된다. 합이 0인지는 애플리케이션이 아니라 DB의 지연 제약 트리거처럼 커밋 시점에 검사하는 장치로 지킨다.

### 원장에서 잘못 적은 줄은 어떻게 고치나요?

고치거나 지우지 않고 반대 방향의 거래를 새로 적는다. 환불도 원래 결제를 지우는 게 아니라 반대 거래다. 그래야 감사할 때 무엇이 언제 왜 바뀌었는지 남고, 이미 다른 시스템이 읽어 간 기록과도 어긋나지 않는다.

### 웹훅 처리 안에서 주문 서비스와 메일 서비스를 바로 부르면 어떤 문제가 있나요?

다른 서비스가 느리거나 죽으면 웹훅 응답이 늦어지거나 실패하고, PSP는 실패로 보고 웹훅을 다시 보낸다. 결제 영역 안의 상태 변경, 원장, 지갑은 한 트랜잭션으로 커밋하고, 바깥 알림은 아웃박스에 적었다가 메시지 큐로 넘긴다. 그러면 결제 처리는 바깥 서비스의 상태와 상관없이 끝나고, 알림은 커밋된 결제에만 나간다.

### 결제 결과가 몇 시간 뒤에 나오는 경우는 어떻게 처리하나요?

결제 건을 진행 중 상태로 두고 사용자에게 "확인 중"을 보여 준 뒤, PSP 웹훅으로 결과를 받아 마무리하고 메일이나 알림으로 알린다. 웹훅이 사라질 수 있으니 오래 진행 중에 머문 건을 PSP 상태 조회 API로 직접 확인하는 주기 작업을 함께 둔다.
