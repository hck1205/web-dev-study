## 어제도 공부했는데 연속 1일이라고 나온다

단어 앱에 "연속 학습일"과 매일 알림을 붙여 배포했다. 다음 날 아침 이런 문의가 들어왔다. "어제 오전 10시에 공부하고 오늘 아침 8시에 또 했는데 연속 1일이라고 나온다."

서버 코드를 열어 보니 학습 기록의 타임스탬프를 `86400000`으로 나눠 날짜를 만들고 있었다. 타임스탬프는 UTC 기준이니 날짜도 UTC 기준이 된다. 서울은 UTC보다 9시간 빠르다. 오전 10시(KST)는 UTC로 같은 날 새벽 1시이고, 다음 날 아침 8시(KST)는 UTC로 아직 전날 밤 11시다. 두 기록이 UTC로는 같은 날이라 하루로 세였다.

이 글은 이런 기능들을 만드는 개발자의 시점에서 본다. 연속 기록의 날짜 계산, 진행률과 목표, 보상과 순위표, 리마인더와 실행 의도, 웹 푸시 권한을 묻는 시점과 알림 피로, 첫 실행 온보딩, 그리고 이 모든 게 효과가 있었는지 재는 법까지. 왜 이런 장치가 사람을 움직이는지는 [행동 설계 모델](/posts/behavior-design-models)에서 다뤘다. 포그 행동 모델의 동기·능력·신호, 습관 고리, 손실 회피가 여기서 구현으로 바뀐다. 장치가 지나쳐 다크 패턴이 되는 경계도 그 글에 있다.

## 날짜는 사용자의 하루로 센다

연속 기록(스트릭)의 정의는 간단하다. "오늘 또는 어제부터 거꾸로, 하루도 빠지지 않고 학습한 날의 수". 어려운 건 "하루"가 누구의 하루냐다. 사용자에게 하루는 자기 시간대의 자정부터 자정까지다. 아래 그림은 같은 기록 두 개를 UTC 날짜로 셀 때와 서울 날짜로 셀 때를 차례로 보여 준다.

그래서 날짜를 만들 때 시간대를 명시한다. 시간대는 `+09:00` 같은 고정 오프셋이 아니라 `Asia/Seoul` 같은 IANA 이름으로 저장한다. 오프셋을 저장하면 서머타임이 있는 지역에서 1년에 두 번 날짜가 어긋난다. 뉴욕 사용자의 오프셋을 여름 값 -4시간으로 고정해 두면, 서머타임이 끝난 11월 1일 밤 11시 30분(실제 오프셋 -5시간)의 기록이 11월 2일 0시 30분으로 계산된다.

시간대 이름은 브라우저에서 바로 얻는다.

```ts
// 가입이나 설정 저장 때 서버로 함께 보낸다
const timeZone = Intl.DateTimeFormat().resolvedOptions().timeZone; // "Asia/Seoul"
```

날짜를 셀 때는 "타임스탬프 → 그 시간대의 연-월-일 → 날짜 번호"로 바꾼다. 날짜 번호는 연-월-일을 `Date.UTC`로 다시 묶어 하루 단위로 나눈 값이다. 이렇게 하면 서머타임 날처럼 하루가 23시간이나 25시간인 날에도 이웃한 날짜의 번호 차이가 정확히 1이다. 아래에서 직접 만들어 보자. 테스트에는 서울의 아침 8시 문제와 뉴욕의 서머타임 종료일(2026년 11월 1일)이 들어 있다.

초기 코드는 처음 장면의 버그를 그대로 담고 있다. 첫 테스트가 1을 돌려주며 실패한다. `Intl.DateTimeFormat`의 `en-CA` 로캘은 날짜를 `2026-10-23` 꼴로 찍어 주기 때문에 쪼개기 편해서 자주 쓰는 요령이다. 더 정확하게는 `formatToParts`로 연·월·일 조각을 받아도 된다.

실무에서는 이 계산 말고도 정할 게 몇 개 더 있다.

- 시간대가 바뀌면. 서울에서 뉴욕으로 출장을 가면 하루가 14시간 늘어난다. 기록마다 그때의 시간대를 같이 저장하고 "기록 당시 사용자의 날짜"로 세는 게 가장 정확하다. 간단히 하려면 현재 시간대로 다시 세되, 시간대를 바꾼 날만 하루를 봐준다.
- 서버와 클라이언트가 같은 숫자를 보여 줘야 한다. 계산은 서버 한 곳에서 하고 클라이언트는 결과만 그린다. 둘 다 계산하면 오프라인에서 공부한 기록이 늦게 올라올 때 숫자가 오락가락한다.
- 오프라인 기록은 기록한 시각을 클라이언트가 같이 보낸다. 서버가 받은 시각으로 세면, 밤 11시 50분에 지하철에서 공부하고 자정 넘어 동기화한 사용자의 기록이 다음 날로 넘어간다. 클라이언트 시계를 믿을 수 없을 때를 대비해 받은 시각과 너무 차이 나면(예: 48시간 이상) 받은 시각을 쓴다.
- 자정 직전의 사용자를 위한 여유. 몇몇 앱은 하루의 경계를 자정이 아니라 새벽 4시처럼 옮겨 둔다. 늦게 자는 사람에게 새벽 1시의 공부는 "어제"이기 때문이다. 정했다면 화면에 알려 준다.

## 하루 빠졌다고 30일이 0이 되면

연속 기록은 손실 회피로 작동한다. 쌓을수록 잃기 싫어서 돌아온다. 그런데 바로 그 이유로 끊기는 순간이 위험하다. 30일 기록이 0이 되면 "이제 상관없다"며 앱을 지우는 사람이 생긴다. 쌓은 것이 클수록 무너졌을 때 충격도 크다.

그래서 많은 앱이 완충 장치를 둔다. 하루를 빠져도 기록을 지켜 주는 "기록 보호권"(듀오링고의 streak freeze 같은 것)을 미리 쥐여 주거나, 주 5일 목표처럼 매일이 아닌 주 단위 목표를 쓰거나, 끊긴 뒤 "최고 기록 30일"을 남겨 둔다. 보호권은 데이터로 보면 이렇게 된다.

```ts
type StreakState = {
  current: number;          // 지금 연속 일수
  best: number;             // 최고 기록. 끊겨도 남는다
  freezes: number;          // 남은 보호권 (최대 2개처럼 상한을 둔다)
  lastActiveDay: number;    // 마지막 학습 날짜 번호 (사용자 시간대 기준)
};

// 날짜가 바뀐 뒤 처음 접속하거나, 매일 사용자의 자정 직후 배치에서 부른다
export function settle(state: StreakState, today: number): StreakState {
  const missed = today - state.lastActiveDay - 1; // 빠진 날 수
  if (missed <= 0) return state;
  if (missed <= state.freezes) {
    // 빠진 날만큼 보호권을 쓰고 기록은 지킨다. 보호권을 썼다고 알려 준다
    return { ...state, freezes: state.freezes - missed, lastActiveDay: today - 1 };
  }
  return { ...state, current: 0 };
}
```

보호권을 쓴 날은 꼭 알려 준다. 몰래 지켜 주면 사용자는 기록이 이상하다고 느끼고, 알려 주면 "앱이 나를 봐줬다"고 느낀다. 반대로 "기록이 오늘 밤 끊긴다"는 경고 알림은 효과가 크지만 불안을 파는 장치이기도 하다. 하루 한 번, 사용자가 정한 시간대 안에서만 보낸다.

## 진행 막대는 의미가 있어야 한다

진행률을 보여 주면 사람은 목표에 가까워질수록 더 힘을 낸다. 행동경제학에서는 목표 기울기 효과(goal gradient effect)라고 부른다. 커피 쿠폰 실험(Kivetz 외, 2006)에서 도장이 찰수록 손님이 더 자주 왔다는 결과가 자주 인용된다.

출발점을 주는 것도 효과가 있다. 세차장 쿠폰 실험(Nunes와 Drèze, 2006)에서 도장 8개를 모으는 빈 쿠폰과, 10칸 중 2칸을 미리 찍어 준 쿠폰은 남은 칸 수가 같았다. 그런데 미리 찍어 준 쪽의 완주율이 훨씬 높았다(약 34% 대 19%). 이걸 부여된 진행 효과(endowed progress effect)라고 한다. 온보딩 체크리스트에서 "계정 만들기"를 이미 완료된 첫 칸으로 보여 주는 게 이 원리다. 실제로 끝낸 일을 칸으로 세는 것이지, 하지 않은 일을 완료로 표시하는 게 아니다.

진행 막대를 만들 때 지킬 것은 세 가지 정도다.

막대가 무엇의 진행인지 말한다. "73%"보다 "시험 범위 300단어 중 219단어"가 의미 있다. 숫자를 사용자가 세운 목표와 연결하면 보상이 된다. "이번 주 목표 5일 중 4일. 내일 하면 달성."

끝이 있는 단위로 나눈다. 1만 단어 중 219단어는 2%로, 막대가 거의 움직이지 않아 의욕을 꺾는다. 같은 진행이라도 "레벨 3의 73%"처럼 작은 단위로 쪼개면 막대가 움직이는 게 보인다. 목표 기울기 효과는 끝이 가까울 때 커지니, 끝을 자주 만들어 주는 것이다.

막대가 거꾸로 가지 않게 한다. 범위에 새 단어가 추가되면 분모가 늘어 막대가 줄어든다. 사용자는 뭔가 잃었다고 느낀다. 범위를 바꿀 땐 "새 단어 20개가 추가됐다"고 따로 알리고, 이미 채운 부분은 다른 색으로 유지한다.

접근성도 챙긴다. 시각적인 막대만 있으면 스크린리더 사용자는 진행을 모른다. `progress` 요소를 쓰거나, 직접 만든다면 `role="progressbar"`와 `aria-valuenow`, `aria-valuemax`, 그리고 숫자를 말로 풀어 주는 `aria-valuetext`를 준다.

```tsx
<div
  role="progressbar"
  aria-valuemin={0}
  aria-valuemax={300}
  aria-valuenow={219}
  aria-valuetext="시험 범위 300단어 중 219단어"
>
  <div style={{ width: `${(219 / 300) * 100}%` }} />
</div>
```

## 보상은 드물어야 값이 있다

배지와 업적은 쉽게 남발된다. 첫 로그인 배지, 첫 클릭 배지, 프로필 사진 배지. 무엇이든 주면 아무것도 주지 않는 것과 같다. 보상이 의미를 가지려면 노력에 비례해야 하고 드물어야 한다. 기준을 세우는 방법 하나는 "이 배지를 받은 사용자 비율"을 재는 것이다. 활성 사용자의 80%가 가진 배지는 이미 보상이 아니다.

보상의 종류도 고른다. 행동 직후 바로 주는 작은 피드백(카드를 넘기면 짧은 완료 애니메이션)은 습관 고리를 돌리는 데 쓰고, 드문 이정표(100일, 1,000단어)는 투자로 쌓이게 한다. 매번 다른 보상(랜덤 상자)은 효과가 크지만 도박과 같은 원리라 학습 앱에서는 조심한다. 유료 재화가 섞이면 국가에 따라 확률형 아이템 규제 대상이 될 수도 있다.

## 순위표는 아래쪽 사람을 생각해서 만든다

경쟁은 일부 사용자를 크게 움직인다. 문제는 그 일부 말고 나머지다. 전체 사용자 10만 명 순위표에서 5만 등은 동기가 생기지 않는다. 위로 올라갈 길이 보이지 않기 때문이다. 그래서 순위표는 비교 범위를 좁힌다.

- 비슷한 사람끼리 작은 그룹(리그)으로 묶는다. 수십 명 단위로, 주간으로 초기화한다. 듀오링고 같은 앱이 쓰는 방식이다.
- 내 위아래 몇 명만 보여 준다. 1등과의 거리가 아니라 바로 위 사람과의 거리가 행동을 부른다.
- 친구끼리의 순위를 따로 둔다. 아는 사람과의 비교는 약속의 효과도 있다.

구현은 Redis의 정렬된 집합(sorted set)이 흔하다. 점수 갱신과 순위 조회가 둘 다 로그 시간이다. 주간 리그 하나를 키 하나로 두고 주가 끝나면 키를 바꾼다. 로컬 Redis 7에 사용자 8명짜리 리그를 넣고 돌려 봤다.

```bash
# 주간 리그 키에 점수를 넣는다 (사용자 8명)
redis-cli ZADD league:2026-w43 120 mina 340 jun 95 seo 410 hana 220 dami 180 tae 260 yuri 75 kim
# seo가 카드 15장을 더 풀었다
redis-cli ZINCRBY league:2026-w43 15 seo
# seo의 순위 (0부터 센다)
redis-cli ZREVRANK league:2026-w43 seo
```

```text
(integer) 8
"110"
(integer) 6
```

순위 6은 0부터 센 값이라 7등이다. 화면에는 내 위아래 두 명씩만 보여 준다. 4등부터 8등까지에 해당하는 4~8 범위를 달라고 하면 리그에 사람이 8명뿐이라 있는 만큼만 돌아온다.

```bash
redis-cli ZREVRANGE league:2026-w43 4 8 WITHSCORES
```

```text
1) "tae"
2) "180"
3) "mina"
4) "120"
5) "seo"
6) "110"
7) "kim"
8) "75"
```

바로 위 mina와 10점 차이다. "10점만 더 모으면 6등"이 1등 hana와의 300점 차이보다 훨씬 행동을 부른다. 주가 끝나면 다음 주 키(`league:2026-w44`)를 쓰고 지난 키에는 `EXPIRE`로 만료를 걸어 둔다. 같은 점수끼리는 멤버 이름의 사전순으로 정렬되고(`ZREVRANGE`는 그 역순), 먼저 도달한 사람을 앞에 두려면 점수에 시각을 섞는 요령(점수 × 큰 수 + 남은 시간)을 쓴다.

순위표를 끌 수 있게 하는 것도 잊지 않는다. 경쟁이 스트레스인 사람에게는 순위표가 이탈 이유가 된다.

## 리마인더는 사용자가 정한 계획을 상기시키는 것이다

"공부할 시간이다"라는 알림을 아무 때나 보내는 것보다, 사용자가 직접 정한 계획을 되짚어 주는 알림이 낫다. 심리학자 피터 골위처가 정리한 실행 의도(implementation intention)는 "만약 X 상황이면 Y를 한다"는 구체적인 계획이다. "영어 공부를 열심히 하겠다"는 목표 의도보다 "출근 지하철에 앉으면 카드 10장을 넘긴다"가 실천으로 이어질 가능성이 높다는 연구가 많다.

작은 계획 프롬프트 하나도 효과가 있다는 실험이 있다. 독감 예방 접종 안내문에 "접종할 날짜와 시간을 적어 보세요" 칸을 넣었더니 접종률이 약 4%포인트 올랐다는 연구(Milkman 외, 2011)가 대표적이다. 앱에서는 이렇게 옮긴다.

- 첫 목표를 정할 때 "언제 하실래요?"를 함께 묻는다. 시간대(출근길, 점심 뒤, 자기 전)나 기존 습관(커피 마신 뒤)을 고르게 한다. 그 답이 리마인더 시각이 된다.
- 알림 문구에 그 계획을 넣는다. "출근길 10장, 지금이 그 시간이다." 사용자가 한 약속을 상기시키는 것이라 같은 알림이라도 덜 침입적으로 느낀다.
- 친구와 약속을 걸게 할 수도 있다. 다른 사람에게 한 약속은 지키려는 힘이 크다. 다만 친구에게 실패를 알리는 기능은 꼭 사용자가 켜게 한다.

리마인더 발송은 서버 배치로 돌린다. 사용자마다 "현지 시각 08:10, Asia/Seoul"처럼 저장해 두고, 몇 분마다 지금 그 시각이 된 사용자를 찾는다. 보낼지 말지를 정하는 규칙이 중요하다.

```ts
type ReminderUser = {
  timeZone: string;
  remindAt: string;          // "08:10", 사용자 현지 시각
  studiedToday: boolean;     // 사용자 시간대 기준 오늘 이미 했나
  quietHours: [number, number]; // [22, 8] = 22시부터 다음 날 8시까지 보내지 않는다
  sentThisWeek: number;
};

export function shouldRemind(u: ReminderUser, localHour: number): boolean {
  if (u.studiedToday) return false;                 // 이미 한 사람에게 보내지 않는다
  const [from, to] = u.quietHours;
  const quiet = from > to ? localHour >= from || localHour < to : localHour >= from && localHour < to;
  if (quiet) return false;                          // 방해 금지 시간
  if (u.sentThisWeek >= 5) return false;            // 주간 상한
  return true;
}
```

첫 줄이 가장 중요하다. 이미 공부한 사람에게 "공부할 시간이다"를 보내면 앱이 나를 모른다는 신호가 된다. 시간대 계산은 앞의 연속 기록과 같은 함수를 쓴다. 날짜 기준이 둘로 갈리면 "오늘 이미 했는데 알림이 왔다"는 문의가 생긴다.

"지금 알림 시각이 된 사용자"를 찾는 쿼리는 데이터베이스에서 시간대 변환까지 한 번에 할 수 있다. PostgreSQL 16에서 사용자 세 명으로 돌려 봤다. 배치가 UTC 23시 12분에 돌았다고 치고, 현지 시각이 알림 시각부터 5분 안에 든 사람을 고른다.

```sql
CREATE TABLE reminder_settings (
  user_id   int PRIMARY KEY,
  time_zone text NOT NULL,   -- IANA 이름
  remind_at time NOT NULL    -- 사용자 현지 시각
);
INSERT INTO reminder_settings VALUES
  (1, 'Asia/Seoul',       '08:10'),
  (2, 'America/New_York', '19:10'),
  (3, 'Europe/London',    '09:00');

-- timestamptz AT TIME ZONE 이름 → 그 지역의 현지 시각(timestamp)
SELECT user_id, time_zone, remind_at,
       (timestamptz '2026-10-23 23:12:00+00' AT TIME ZONE time_zone) AS local_now
FROM reminder_settings
WHERE (timestamptz '2026-10-23 23:12:00+00' AT TIME ZONE time_zone)::time
      BETWEEN remind_at AND remind_at + interval '5 minutes';
```

```text
 user_id |    time_zone     | remind_at |      local_now
---------+------------------+-----------+---------------------
       1 | Asia/Seoul       | 08:10:00  | 2026-10-24 08:12:00
       2 | America/New_York | 19:10:00  | 2026-10-23 19:12:00
(2 rows)
```

같은 순간이 서울에서는 24일 아침, 뉴욕에서는 23일 저녁이다. `local_now`의 날짜가 사용자마다 다르다는 게 핵심이고, 이 날짜가 "오늘 이미 공부했나"를 판단하는 기준이 된다. 실제로는 실행 시각에 `now()`를 쓴다. 함정이 두 개 있다. 알림 시각이 23시 58분이면 `remind_at + interval '5 minutes'`가 `00:03`으로 돌아가 `BETWEEN`이 늘 거짓이 된다. 자정을 넘는 창은 따로 처리하거나 알림 시각 선택지를 자정 근처에서 빼 둔다. 그리고 배치가 늦거나 두 번 돌면 같은 사람에게 두 번 간다. `(user_id, 현지 날짜)`에 유니크 제약을 건 발송 기록 테이블에 먼저 넣고, 넣는 데 성공한 사람에게만 보낸다.

## 알림 권한은 한 번밖에 못 묻는다

웹 푸시가 기기에 도착하는 구조(푸시 서비스, VAPID, 서비스 워커)는 [PWA 설치와 오프라인](/posts/pwa-install-offline)에 있다. 여기서는 그 전 단계, 권한을 언제 어떻게 묻는지를 본다.

브라우저 알림 권한은 `default`(아직 안 물음), `granted`, `denied` 세 상태다. 한 번 `denied`가 되면 `Notification.requestPermission()`을 다시 불러도 창이 뜨지 않고 바로 `denied`가 돌아온다. 사용자가 브라우저 설정에 직접 들어가 바꾸기 전까지 끝이다. 그리고 요즘 브라우저는 사용자 동작 없이 페이지가 뜨자마자 묻는 걸 막거나 눈에 덜 띄게 바꾼다. 파이어폭스와 사파리는 클릭 같은 사용자 동작 안에서 부른 요청만 창을 띄우고, 크롬은 허용률이 낮은 사이트나 자주 거절하는 사용자에게 주소창의 조용한 안내로 바꿔 보여 준다.

그래서 한 번뿐인 기회를 동기가 가장 높은 순간에 쓴다. 흔히 쓰는 방법은 브라우저 창 전에 앱 자체의 안내(소프트 애스크)를 먼저 보여 주는 것이다. 아래 그림에서 다음을 누르며 따라가 보자.

React로는 이렇게 쓴다. 권한 요청이 클릭 핸들러 안에서 바로 일어나는 게 핵심이다. `await` 앞에 다른 비동기 작업을 끼우면 일부 브라우저는 사용자 동작으로 보지 않는다.

```tsx
"use client";

import { useState } from "react";

export function ReminderOptIn({ onSubscribe }: { onSubscribe: (at: string) => Promise<void> }) {
  const [dismissed, setDismissed] = useState(false);
  const [state, setState] = useState(() =>
    typeof Notification === "undefined" ? "unsupported" : Notification.permission,
  );

  if (dismissed || state === "unsupported" || state === "granted") return null;
  if (state === "denied") {
    return <p>알림이 꺼져 있다. 주소창 왼쪽 사이트 설정에서 켤 수 있다.</p>;
  }

  async function choose(at: string) {
    const result = await Notification.requestPermission(); // 클릭 안에서 바로 부른다
    setState(result);
    if (result === "granted") await onSubscribe(at);
  }

  return (
    <div role="group" aria-label="내일 알림 받기">
      <button onClick={() => choose("08:10")}>출근길 08:10</button>
      <button onClick={() => choose("13:10")}>점심 뒤 13:10</button>
      <button onClick={() => setDismissed(true)}>나중에</button>
    </div>
  );
}
```

"나중에"를 누른 사람에게 언제 다시 물을지도 정한다. 다음 실행마다 묻는 건 반복 간섭이다. 일주일 뒤, 또는 사용자가 비슷한 가치를 다시 겪은 순간(3일 연속 기록을 세운 날) 한 번만 다시 보여 준다.

## 알림이 많아지면 사람들은 끈다

알림 피로는 조용히 온다. 하루 한 번이던 알림에 마케팅팀의 이벤트 알림, 친구 활동 알림, 순위 변동 알림이 더해지면 어느 날 권한이 `denied`로 바뀌어 있다. 이 신호를 놓치지 않으려면 앱을 열 때마다 권한 상태를 확인해 바뀌었으면 이벤트로 남긴다. 지원하는 브라우저에서는 Permissions API로 변화를 구독할 수도 있다.

```ts
// 앱 시작 시 한 번
const status = await navigator.permissions.query({ name: "notifications" });
track("notification_permission_checked", { state: status.state });
status.onchange = () => track("notification_permission_changed", { state: status.state });
```

이 이벤트의 비율이 알림 정책의 체온계다. 알림 종류를 하나 추가한 주에 해제율이 뛰었다면 그 알림이 범인이다. 실무에서 쓰는 방어선은 몇 가지다.

- 사용자 단위 빈도 상한. 종류와 상관없이 하루 최대 몇 개, 주간 최대 몇 개. 상한을 넘으면 우선순위가 낮은 것부터 버린다. 상한은 발송 서비스 한 곳에서 건다. 팀마다 따로 보내면 상한이 의미가 없다.
- 묶음 발송. 친구 활동 알림 다섯 개는 저녁에 한 번 "오늘 친구 3명이 공부했다"로 모은다.
- 종류별 끄기. 설정에서 학습 리마인더, 친구 소식, 이벤트를 따로 끌 수 있게 한다. 하나만 끄고 싶은 사람이 전체 권한을 끄는 걸 막는다.
- 방해 금지 시간. 사용자 시간대 기준으로 밤에는 보내지 않는다.
- 아무 행동도 부르지 않은 알림을 줄인다. 열지 않은 알림이 몇 번 이어지면 그 사용자에게는 빈도를 스스로 낮춘다.

## 처음 온 사람에게 보여 줄 것

온보딩은 첫 실행에서 사용자가 이 앱의 가치를 처음 겪게 만드는 과정이다. 목표는 설명을 많이 하는 게 아니라 첫 성공을 빨리 맛보게 하는 것이다. 쓸 수 있는 도구는 대략 이렇다.

빈 상태. 처음 연 화면에 단어장이 하나도 없으면 그 빈 화면이 가장 좋은 온보딩 자리다. "단어장이 없다"가 아니라 "첫 단어장 만들기"와 "예시 단어장으로 시작하기" 두 길을 준다. 예시 데이터는 처음 한 번 겪어 보기에 좋지만, 사용자의 진짜 데이터와 섞이지 않게 표시하고 쉽게 지울 수 있게 한다.

튜토리얼. 첫 실행에 넘기는 슬라이드 서너 장(캐러셀)은 대부분 건너뛴다. 읽어도 기억하지 못한다. 대신 실제 동작을 하게 하는 튜토리얼이 낫다. "카드를 오른쪽으로 넘겨 보세요"를 보여 주고 사용자가 실제로 넘기면 다음으로 간다.

코치 마크. 화면 요소를 가리키는 말풍선이다. 처음 그 기능을 쓸 때 한 번만, 하나씩 띄운다. 첫 화면에 다섯 개를 한꺼번에 띄우면 아무것도 읽지 않고 닫는다. 접근성 요건이 많다. 키보드로 닫을 수 있어야 하고(Esc), 포커스를 가두지 않거나 가둔다면 확실히 돌려줘야 하며, 가리키는 요소와 말풍선이 `aria-describedby`로 연결돼야 스크린리더도 같은 설명을 듣는다. 위에 겹치는 레이어는 HTML의 `popover` 속성으로 만들면 맨 위 레이어 처리와 Esc 닫기를 브라우저가 해 준다. 주요 브라우저는 2024년부터 모두 지원한다.

체크리스트. "시작하기 4단계"처럼 할 일을 보여 주고 진행률을 단다. 앞에서 본 부여된 진행 효과가 여기서 쓰인다. 실제로 끝낸 첫 단계(가입)를 완료로 보여 주며 시작한다.

팁과 안내. 기능을 처음 쓸 때 맥락 안에서 짧은 팁을 준다(점진적 온보딩). "길게 누르면 발음을 들을 수 있다"는 단어 카드를 처음 열었을 때 보여 줘야 의미가 있다.

어떤 도구를 쓰든 이미 본 것은 다시 보여 주지 않는다. 본 기록은 로그인 사용자라면 서버에, 아니라면 브라우저 저장소에 둔다. 기기를 바꿀 때마다 같은 코치 마크가 뜨는 건 흔한 불만이다. 그리고 언제든 건너뛸 수 있어야 한다. 건너뛴 사람도 나중에 도움말에서 다시 볼 수 있게 한다.

## 효과는 코호트로, 알림은 홀드아웃으로 잰다

이 기능들이 효과가 있었는지 보려면 가입 주별로 사람을 묶은 리텐션 코호트를 본다. 기능을 넣은 주에 가입한 사람들의 1주, 2주, 4주 뒤 재방문율이 이전 코호트보다 높은지다. 코호트 리텐션의 두 가지 정의와 계산은 [제품 지표를 재는 법](/posts/product-analytics-funnels)에 있다.

알림은 따로 조심해야 한다. "알림을 눌러 들어온 세션"을 알림 효과로 세면 크게 부풀려진다. 그 사람들 중 상당수는 알림이 없어도 그날 들어왔을 것이기 때문이다. 진짜 효과는 알림을 아예 받지 않는 작은 대조군(홀드아웃, 예를 들어 무작위 5~10%)과 비교해야 나온다. 예를 들어(가상의 숫자) 알림을 받은 그룹의 7일 리텐션이 38.0%, 홀드아웃이 34.5%라면 알림의 순효과는 3.5%포인트다. 알림 클릭 세션 수로 본 효과가 이보다 몇 배 크게 보이는 일이 흔하다.

같이 볼 지표도 정해 둔다. 리텐션이 올라도 알림 권한 해제율과 앱 삭제율이 같이 오르면 오래가지 않는다. 연속 기록 기능이라면 "기록이 끊긴 다음 날의 이탈률"을 따로 본다. 끊긴 사람의 이탈이 유독 높다면 보호권이나 주 단위 목표 같은 완충 장치가 필요하다는 뜻이다. 실험 설계와 대조군을 나누는 법은 [A/B 테스트와 피처 플래그](/posts/ab-testing)를 참고한다.

## 다시 연속 1일 문의로

처음 문의의 원인은 UTC로 날짜를 센 것이었고, 고친 방법은 사용자의 시간대 이름으로 날짜를 만드는 것이었다. 그런데 그 버그가 무서운 이유는 숫자가 틀려서가 아니라, 손실 회피로 붙잡아 둔 사용자에게 억울하게 잃는 경험을 줘서다. 연속 기록, 진행 막대, 순위표, 리마인더, 온보딩은 모두 사용자가 이미 원하는 행동을 쉽게 하도록 돕는 도구다. 날짜는 사용자의 하루로 세고, 권한은 가치를 겪은 뒤 한 번만 묻고, 알림은 사용자가 정한 계획을 상기시키는 데 쓰고, 효과는 홀드아웃과 코호트로 잰다. 이 선을 넘으면 같은 기능이 다크 패턴이 된다. 그 경계는 [행동 설계 모델](/posts/behavior-design-models)에서 정리했다.

## 면접에서 나올 만한 질문

### 연속 학습일(스트릭)을 구현할 때 가장 흔한 버그는 무엇인가요?

날짜를 서버의 UTC 기준으로 세는 것이다. 서울 사용자의 아침 8시는 UTC로 전날이라, 이틀 연속 공부해도 하루로 세는 일이 생긴다. 사용자의 IANA 시간대 이름을 저장하고 그 시간대의 연-월-일로 날짜를 만든 뒤, 날짜를 `Date.UTC`로 다시 묶은 번호로 비교한다. 고정 오프셋을 저장하면 서머타임 지역에서 1년에 두 번 어긋난다.

### 시간대 대신 UTC 오프셋을 저장하면 왜 안 되나요?

오프셋은 날짜마다 바뀔 수 있기 때문이다. 뉴욕은 여름에 -4시간, 겨울에 -5시간이라 여름 값을 고정해 두면 서머타임이 끝난 뒤 밤 11시 30분 기록이 다음 날로 넘어간다. `America/New_York` 같은 이름을 저장하면 `Intl`이나 서버의 시간대 데이터베이스가 그 날짜의 규칙을 적용해 준다.

### 알림 권한은 언제 물어야 하나요?

사용자가 알림의 가치를 겪은 직후, 그리고 앱 자체의 안내에서 원한다고 답한 뒤에 묻는다. 브라우저 권한은 한 번 거절되면 다시 물을 수 없고, 사용자 동작 없이 묻는 요청은 브라우저가 막거나 조용한 안내로 바꾼다. 그래서 `requestPermission`은 클릭 핸들러 안에서 바로 부르고, 앱 안내에서 거절하면 브라우저 권한을 아껴 둔다.

### 알림의 효과는 어떻게 재나요?

알림을 받지 않는 무작위 홀드아웃 그룹을 두고 리텐션을 비교한다. 알림을 눌러 들어온 세션을 세면, 알림이 없어도 왔을 사람까지 알림 효과로 세서 크게 부풀려진다. 함께 알림 권한 해제율과 앱 삭제율을 가드레일로 본다.

### 알림 피로를 줄이려면 어떤 장치를 두나요?

발송 서비스 한 곳에서 사용자 단위 빈도 상한을 걸고, 우선순위가 낮은 알림부터 버린다. 친구 활동처럼 잦은 알림은 묶어서 보내고, 종류별로 끌 수 있게 해 전체 권한을 끄는 걸 막는다. 이미 행동한 사용자에게 리마인더를 보내지 않는 규칙이 가장 효과가 크다. 권한 상태 변화를 이벤트로 남겨 어떤 알림이 해제를 부르는지 추적한다.

### 순위표를 설계할 때 주의할 점은요?

전체 순위는 대부분의 사용자에게 동기를 주지 못한다. 수십 명 단위 리그로 묶어 주간으로 초기화하고, 내 위아래 몇 명만 보여 줘서 바로 위 사람과의 거리를 보이게 한다. 구현은 Redis 정렬된 집합으로 주간 키를 쓰고 지난 키에는 만료를 건다. 경쟁이 싫은 사람을 위해 끌 수 있게 한다.

### 연속 기록이 끊기면 이탈하는 문제는 어떻게 다루나요?

연속 기록은 손실 회피로 작동해서, 큰 기록이 0이 되는 순간 오히려 포기하게 만든다. 하루를 지켜 주는 보호권, 매일 대신 주 단위 목표, 끊겨도 남는 최고 기록 같은 완충 장치를 둔다. 보호권을 쓴 사실은 꼭 알려 준다. 효과는 기록이 끊긴 다음 날의 이탈률로 확인한다.

### 온보딩에서 코치 마크를 쓸 때 주의할 점은요?

한꺼번에 여러 개를 띄우지 말고 그 기능을 처음 쓸 때 하나씩 띄운다. Esc로 닫을 수 있어야 하고, 가리키는 요소와 `aria-describedby`로 연결해 스크린리더도 같은 설명을 듣게 한다. 본 기록은 서버에 저장해 기기를 바꿔도 다시 뜨지 않게 하고, 언제든 건너뛸 수 있게 한다.
