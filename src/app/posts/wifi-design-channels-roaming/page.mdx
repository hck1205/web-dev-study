사무실 와이파이가 느리다는 제보에 AP(공유기)를 세 대 더 달았다. 그런데 평균 속도가 더 떨어졌다. 로그를 보니 새 AP들이 모두 2.4GHz 채널 6번을 쓰고 있었고, 서로 신호가 닿는 거리에 있었다. 한 AP가 말하는 동안 옆 AP도 그 채널을 "사용 중"으로 듣고 자기 차례를 기다렸다. AP를 늘렸는데 같은 채널을 공유하는 기기만 늘어난 셈이다.

이게 무선 설계의 핵심 오해다. AP는 많을수록 좋은 게 아니라 겹치지 않게 배치해야 좋다. 이 글은 겹치지 않는 채널을 고르는 법, 신호 세기와 SNR을 읽는 법, 사이트 조사와 AP 배치, 컨트롤러로 묶어 관리하는 법, 그리고 걸어 다니는 기기가 끊기지 않게 옮겨 붙는 로밍까지 본다. 무선 장비 실습 환경이 없어 패킷·스펙트럼 출력은 싣지 않고, 채널·링크 예산 계산은 직접 돌려 본 값만 넣었다.

이 주제의 다른 글: 802.11 규격과 WPA2·WPA3·802.1X 보안은 [Wi-Fi 동작과 보안 글](/posts/wifi-standards-security)에, Wi-Fi가 아닌 무선은 [다른 무선 기술 글](/posts/iot-mobile-wireless-links)에 있다.

## AP를 늘리면 왜 느려질 수 있나

AP는 CSMA/CA로 채널을 나눠 쓴다. 같은 채널을 쓰는 AP와 그 기기들은 하나의 경쟁 영역(contention domain)이 된다. 서로 신호가 닿는 거리에 같은 채널 AP가 둘 있으면, 둘과 거기 붙은 모든 기기가 한 채널을 돌려 쓴다. 이걸 동일 채널 간섭(co-channel interference, CCI)이라고 한다. 겹치기는 하지만 완전히 같지는 않은 채널(예: 2.4GHz의 1번과 3번)을 쓰면 더 나쁘다. 서로를 "사용 중"으로도 인식하지 못해 그냥 잡음으로 부딪친다. 이게 인접 채널 간섭(adjacent channel interference, ACI)이다.

그래서 CCI는 차라리 "질서 있는 느림"이고 ACI는 "무질서한 깨짐"이다. 설계의 첫 목표는 ACI를 없애고 CCI를 최소로 만드는 것이다. 방법은 하나다. 가까운 AP끼리 서로 다른, 겹치지 않는 채널을 주는 것.

## 2.4GHz에 겹치지 않는 채널은 사실상 셋뿐이다

2.4GHz 대역은 채널 번호가 1부터 13(미국은 11)까지 있지만, 한 20MHz 채널이 실제로 차지하는 폭이 약 22MHz라 번호가 5MHz 간격인 채널들은 서로 겹친다. 채널 중심 주파수는 1번이 2412MHz, 그다음 5MHz씩 올라간다. 두 20MHz 채널이 겹치지 않으려면 중심이 최소 25MHz(= 5채널) 떨어져야 한다. 그래서 겹치지 않는 조합은 1, 6, 11뿐이다(13번을 쓰는 지역은 1, 5, 9, 13도 가능하지만 유럽 일부에 한정된다).

아래에서 두 채널이 겹치는지 직접 계산해 보자. 기대값은 node로 같은 식을 돌려 확인했다.

<CodePlayground

  initialCode={`// 20MHz 채널 두 개가 겹치는지 본다.
// 채널 중심(MHz): 14번은 2484, 그 외 n은 2407 + 5*n
// 중심 간격이 25MHz 미만이면 겹친다
function channelOverlap(a, b) {
  return { centerA: 0, centerB: 0, gapMHz: 0, overlap: true };
}`}
  solution={`function center(n) {
  return n === 14 ? 2484 : 2407 + 5 * n;
}

function channelOverlap(a, b) {
  const centerA = center(a);
  const centerB = center(b);
  const gapMHz = Math.abs(centerA - centerB);
  return { centerA, centerB, gapMHz, overlap: gapMHz < 25 };
}`}
  tests={[
    { label: "1번과 6번", args: [1, 6], expected: { centerA: 2412, centerB: 2437, gapMHz: 25, overlap: false } },
    { label: "6번과 11번", args: [6, 11], expected: { centerA: 2437, centerB: 2462, gapMHz: 25, overlap: false } },
    { label: "1번과 5번(흔한 실수)", args: [1, 5], expected: { centerA: 2412, centerB: 2432, gapMHz: 20, overlap: true } },
    { label: "1번과 11번", args: [1, 11], expected: { centerA: 2412, centerB: 2462, gapMHz: 50, overlap: false } },
  ]}
/>

1번과 5번이 겹친다는 결과가 흔한 실수를 보여 준다. "1, 3, 6, 9, 11처럼 많이 쓰면 더 좋지 않나" 싶지만, 3번은 1번·6번 모두와 겹쳐 ACI를 만든다. 2.4GHz에서는 1, 6, 11 셋만 쓰는 게 정답이다. 결국 2.4GHz는 쓸 수 있는 채널이 셋뿐이라 AP가 네 대만 넘어도 어딘가는 채널이 겹친다. 그래서 요즘 설계는 2.4GHz를 "닿아야 하는 옛 기기용"으로만 남기고 용량은 5GHz와 6GHz로 옮긴다.

## 5GHz와 6GHz: 채널은 많지만 넓게 쓰면 줄어든다

5GHz는 20MHz 채널이 20개 넘게 있어 겹치지 않게 배치할 여유가 크다. 대신 채널 폭을 40, 80, 160MHz로 넓히면 쓸 수 있는 채널 수가 반씩 준다. 80MHz를 쓰면 쓸 수 있는 넓은 채널이 몇 개 안 남아, AP가 많은 사무실에서는 오히려 CCI가 늘어난다. 그래서 밀집 환경의 정석은 "채널 폭을 40MHz나 20MHz로 좁혀 채널 수를 확보"하는 것이다. 집처럼 AP가 하나뿐이면 80MHz가 이득이지만, 사무실에서는 좁히는 게 보통 빠르다.

5GHz에는 DFS(동적 주파수 선택) 채널이 있다. 이 대역은 기상·군사 레이더와 공유하므로, AP가 레이더 신호를 감지하면 즉시 그 채널을 비우고 다른 채널로 옮겨야 한다. 공항이나 항만 근처에서 DFS 채널을 쓰면 AP가 갑자기 채널을 바꿔 잠깐 끊기는 일이 생긴다. 그래서 그런 환경에서는 DFS가 아닌 채널만 쓰기도 한다.

6GHz(Wi-Fi 6E/7)는 넓고 깨끗하다. 옛 기기가 아예 없고 20MHz 채널이 59개까지 있어 160MHz를 써도 여유가 있다. 대신 전파가 덜 멀리 가고 벽을 잘 못 뚫어 AP를 더 촘촘히 놓아야 한다. 6GHz는 WPA3나 OWE만 허용한다.

## 신호가 세다고 빠른 게 아니다: SNR을 본다

기기 화면에 뜨는 신호 막대는 수신 세기(RSSI, dBm)다. dBm은 로그 단위라 3dB가 두 배, 10dB가 열 배다. -30dBm은 아주 가까운 상태, -67dBm이 영상 통화가 흔들리기 시작하는 경계, -80dBm 아래면 연결만 겨우 유지된다.

중요한 건 신호 세기 자체가 아니라 신호와 잡음의 비(SNR)다. 잡음 바닥이 -90dBm인 곳에서 신호가 -67dBm이면 SNR은 23dB다. 높은 변조(1024-QAM 같은)는 SNR이 높아야(보통 30dB 이상) 쓸 수 있어서, 신호가 세도 옆 AP와 간섭이 많아 잡음이 높으면 SNR이 낮아 속도가 안 나온다. 처음 장면의 "AP를 늘렸더니 느려진" 현상이 바로 이것이다. 신호는 세졌지만 같은 채널 AP들이 서로 잡음이 되어 SNR이 떨어졌다.

## 신호가 거리와 벽에 따라 얼마나 약해지나 (링크 예산)

AP에서 멀어지고 벽을 지날 때 신호가 얼마나 약해지는지는 대략 계산할 수 있다. 자유 공간 경로 손실(FSPL)은 거리와 주파수로 정해진다. 송신 출력과 안테나 이득에서 경로 손실과 벽 손실을 빼면 기기가 받는 세기(RSSI)가 나온다. 이걸 링크 예산이라고 부른다.

<CodePlayground
  caption="링크 예산: 받는 신호 세기(RSSI) 추정"
  functionName="estimateRssi"
  initialCode={`// txDbm: AP 송신 출력(dBm), gainDbi: 안테나 이득(dBi)
// freqMHz: 주파수, distM: 거리(m), wallLossDb: 벽 손실 합(dB)
// FSPL(dB) = 20*log10(거리km) + 20*log10(주파수MHz) + 32.44
// RSSI = tx + gain - FSPL - wallLoss, 소수 첫째 자리 반올림
function estimateRssi(txDbm, gainDbi, freqMHz, distM, wallLossDb) {
  return 0;
}`}
  solution={`function fspl(distM, freqMHz) {
  return 20 * Math.log10(distM / 1000) + 20 * Math.log10(freqMHz) + 32.44;
}

function estimateRssi(txDbm, gainDbi, freqMHz, distM, wallLossDb) {
  const rssi = txDbm + gainDbi - fspl(distM, freqMHz) - wallLossDb;
  return Math.round(rssi * 10) / 10;
}`}
  tests={[
    { label: "20dBm, 2.4GHz, 10m, 벽 없음", args: [20, 3, 2437, 10, 0], expected: -37.2 },
    { label: "20dBm, 5GHz, 10m, 벽 없음", args: [20, 3, 5500, 10, 0], expected: -44.2 },
    { label: "20dBm, 5GHz, 20m, 벽 12dB", args: [20, 3, 5500, 20, 12], expected: -62.3 },
    { label: "14dBm, 5GHz, 30m, 벽 15dB", args: [14, 3, 5500, 30, 15], expected: -74.8 },
  ]}
/>

같은 거리라도 5GHz가 2.4GHz보다 7dB 더 약하게 들어오는 게 보인다(10m에서 -37.2 대 -44.2). 주파수가 높을수록 FSPL이 크기 때문이다. 그래서 5GHz와 6GHz는 커버리지가 좁고 AP를 더 촘촘히 놓아야 한다. 세 번째 테스트처럼 벽 하나(콘크리트 약 12dB)만 지나도 -62dBm까지 떨어진다. 마지막처럼 출력을 낮추고 거리가 멀고 벽이 여러 개면 -75dBm으로, 실시간 서비스가 흔들리는 영역이다.

실제 실내 감쇠는 벽 재질·가구·사람 몸까지 영향을 받아 이 식보다 더 빠르게 떨어진다(경로 손실 지수가 2보다 커진다). 그래서 계산은 어림이고, 최종 판단은 실측(사이트 조사)으로 한다.

## 설계 전후로 하는 사이트 조사

사이트 조사는 세 종류다. 예측 조사는 도면에 벽 재질과 AP 후보 위치를 넣어 소프트웨어로 커버리지를 시뮬레이션한다. 설계 초안을 잡는 데 쓴다. 능동 조사는 실제 AP를 임시로 켜고 노트북을 들고 돌아다니며 RSSI와 SNR, 속도를 지도에 찍는다. 수동 조사는 지금 깔린 모든 AP(우리 것과 옆 회사 것 모두)의 신호를 수집해 혼잡을 본다.

핵심 지표는 두 가지다. 어디서나 주 대역 신호가 -67dBm 이상 들어오는지(커버리지), 그리고 같은 채널 AP가 몇 dB 차이로 겹치는지(CCI)다. 셀 경계에서 기기가 다음 AP로 넘어갈 수 있게, 이웃 AP의 커버리지를 15~20%쯤 겹치게 설계한다. 너무 많이 겹치면 CCI, 너무 적게 겹치면 로밍 중 끊김이 생긴다.

## AP 배치와 송신 출력: 세게 쏘는 게 능사가 아니다

흔한 실수가 AP 송신 출력을 최대로 올리는 것이다. AP는 세게 쏘는데 기기(특히 휴대폰)는 출력이 약해서, 기기의 응답이 AP까지 못 돌아오는 비대칭이 생긴다. 다운로드는 되는데 업로드가 안 되거나 ACK가 유실돼 재전송이 늘어난다. 그래서 AP 출력을 기기 출력에 맞춰 낮추는 편이 낫다(보통 양방향 균형점은 11~17dBm 근처다).

출력을 낮추면 셀이 작아지는 대신 같은 면적에 AP를 더 촘촘히 놓을 수 있다. 밀집 환경(강당, 사무실)의 정석은 "작은 셀을 촘촘히"다. 셀이 작으면 한 AP에 붙는 기기가 줄어 경쟁이 줄고, 기기가 가까워져 높은 변조를 쓴다. 천장 중앙에 고르게 배치하고, 아주 밀집한 곳은 지향성 안테나로 특정 구역만 덮기도 한다.

## 여러 AP를 한 머리로 묶는다 (컨트롤러)

AP가 수십 대가 되면 채널과 출력을 하나씩 손으로 맞출 수 없다. 그래서 AP들을 묶어 관리한다. 방식은 세 가지다.

- 독립(standalone): AP마다 따로 설정한다. 몇 대까지는 괜찮다.
- 컨트롤러 기반: 전용 WLC(무선 랜 컨트롤러) 장비가 모든 AP의 채널·출력을 자동으로 조정(RRM)하고, 기기 인증과 로밍을 중앙에서 처리한다. 큰 캠퍼스에 맞다. 컨트롤러가 죽으면 전체가 위험하므로 이중화한다.
- 클라우드 관리: 설정은 클라우드 대시보드에서 하고, 기기 트래픽은 AP가 로컬에서 직접 처리한다. 클라우드 연결이 끊겨도 기존 연결은 유지되는 게 보통이다.

RRM(Radio Resource Management)이 자동으로 하는 일이 처음 장면의 문제를 푼다. 새 AP가 켜지면 이웃 AP들의 채널을 보고 겹치지 않는 채널을 고르고, 서로 신호가 세게 닿으면 출력을 낮춰 CCI를 줄인다.

## 작은 사무실 채널 배치를 손으로 짜 보면

AP 네 대짜리 한 층을 예로 든다. 네 모서리에 AP를 두고, 2.4GHz는 1·6·11 세 채널뿐이라 네 대에 1, 6, 11, 1을 준다. 이때 1번을 쓰는 두 AP는 서로 가장 먼 대각선 모서리에 놓아 신호가 약하게 닿게 한다. 같은 채널을 피할 수 없을 때는 "가장 멀리 떨어뜨린다"가 원칙이다.

5GHz는 채널이 많으니 네 대에 36, 44, 149, 157처럼 서로 겹치지 않는 채널을 하나씩 준다. 2.4GHz에서 겹침을 감수한 1번 두 대도 5GHz에서는 완전히 분리된다. 그래서 요즘 설계는 용량을 5GHz로 몰고, 2.4GHz는 커버리지 보조로만 둔다. 채널 폭은 밀집도를 보고 정한다. 이 네 대가 서로 신호가 세게 닿는다면 80MHz로 넓게 쓸 경우 쓸 수 있는 넓은 채널이 몇 개 안 남아 겹치므로, 40MHz로 좁혀 네 채널을 확실히 분리하는 편이 빠르다.

6GHz(Wi-Fi 6E/7)를 쓴다면 PSC(Preferred Scanning Channel)라는, 기기가 우선 스캔하도록 정해진 채널들을 중심으로 배치한다. 기기가 넓은 6GHz 대역을 전부 뒤지지 않고 PSC만 봐도 AP를 빨리 찾게 하기 위해서다.

원칙은 "채널을 돌려 쓰되 같은 채널은 최대한 멀리"다. RRM이 자동으로 해 주더라도, 왜 그런 배치가 나오는지 알아야 로그에서 이상한 배치를 발견하고 고칠 수 있다.

## 클라이언트가 설계를 흔든다

AP 설계를 잘해도 기기(클라이언트) 쪽 사정이 성능을 가른다. 안테나가 하나뿐인 IoT 기기는 아무리 좋은 AP라도 공간 흐름 하나밖에 못 써서 느리고, 그 느린 전송이 공기 시간을 오래 차지해 주변까지 늦춘다. 오래된 2.4GHz 전용 기기는 비좁은 세 채널에 몰려 혼잡을 키운다.

그래서 설계 단계에서 "어떤 기기가 붙는가"를 먼저 조사한다. 바코드 스캐너나 의료 장비처럼 로밍이 굼뜬 기기가 많으면 802.11r을 반드시 켜고 셀을 작게 잡는다. 반대로 노트북 위주의 사무실이면 5GHz·6GHz에 용량을 몰 수 있다. AP 사양표의 최대 속도는 2×2 이상 기기를 가정한 값이므로, 실제 기기가 그만한 안테나를 갖췄는지 확인하지 않으면 설계가 종이 위에서만 빠르다.

## 걸어 다녀도 안 끊기게: 로밍

기기가 AP A에서 B로 옮겨 붙는 로밍의 판단은 사실 기기가 한다. AP는 "더 좋은 데로 가라"고 권할 수 있을 뿐 강제하지 못한다. 기본 로밍은 기기가 다른 AP로 완전히 다시 붙는 과정(스캔, 인증, 결합, 4-way handshake, 802.1X면 RADIUS까지)을 거쳐서 수백 ms가 걸린다. 영상 통화나 바코드 스캐너는 이 틈에 끊긴다. 802.11 연결 과정 자체는 [Wi-Fi 동작 글](/posts/wifi-standards-security)에 있다.

이 틈을 줄이는 표준이 셋이다.

- 802.11k: AP가 "근처에 이런 AP들이 있다(이웃 리포트)"를 알려줘, 기기가 전 채널을 다 스캔하지 않고 후보만 빠르게 본다.
- 802.11v: AP가 기기에게 "더 좋은 AP로 옮겨라(BSS 전환 관리)"를 권한다.
- 802.11r: 빠른 전환(FT). 처음 붙을 때 만든 키 재료를 이웃 AP들과 미리 나눠, 옮길 때 4-way handshake와 802.1X를 다시 안 해도 되게 한다. 로밍 시간을 수십 ms로 줄인다.

밴드 스티어링은 2.4GHz와 5GHz를 둘 다 지원하는 기기를 5GHz로 유도하는 기능이다. AP가 2.4GHz의 probe에 일부러 늦게 답하거나 응답하지 않아 기기가 5GHz를 고르게 만든다. 2.4GHz 혼잡을 줄이는 데 쓴다.

## 먼 AP에 매달리는 sticky client 문제

로밍이 기기 몫이라 생기는 대표 증상이 sticky client다. 기기가 AP A에 붙은 채 사용자가 B 바로 아래로 걸어갔는데도, A의 신호가 아직 "연결 유지 가능"한 -80dBm쯤이면 기기가 굳이 옮기지 않는다. 결과는 느린 속도와 잦은 재전송이다. 특히 배터리를 아끼려 로밍을 게을리하는 기기나 오래된 드라이버에서 자주 보인다.

현장에서 이렇게 좁혀 본다. 사용자가 "특정 자리에서만 느리다"고 하면, 그 기기가 붙은 BSSID와 RSSI를 확인한다. 가까운 AP가 아니라 먼 AP(강한 신호의 다른 BSSID가 있는데도)에 붙어 있으면 sticky client다. 대책은 셀 경계에서 신호가 충분히 약해지도록 출력을 낮춰 기기가 "떠날 결심"을 하게 만들거나(출력이 너무 세면 먼 AP도 "쓸 만하게" 들려 안 떠난다), 802.11k/v로 전환을 권하는 것이다. 일부 컨트롤러는 아주 약하게 붙은 기기를 일부러 끊어 다시 붙게 하는 기능(sticky client 완화)을 제공하지만, 잘못 쓰면 멀쩡한 연결을 끊으니 임계값을 조심해서 정한다.

Ubuntu 24.04 노트북에서 지금 상태는 이렇게 본다. 출력 형식은 드라이버마다 달라 옮기지 않는다.

```bash
# 붙은 AP의 BSSID, 주파수, 신호(dBm), 현재 속도
iw dev wlan0 link
# 주변 AP를 스캔해 BSSID별 신호를 본다(루트 권한)
sudo iw dev wlan0 scan | grep -E "BSS|signal|SSID|freq"
```

`iw ... link`의 `signal`이 약한데(-75dBm 이하) `scan`에 더 강한 같은 SSID의 BSSID가 있으면, 그 기기는 옮겨야 할 때 안 옮기는 상태다.

## 처음 장면을 다시 보면

AP를 늘렸는데 느려진 건 새 AP들이 같은 채널(동일 채널 간섭)을 써서 경쟁 영역만 키웠기 때문이다. 해법은 겹치지 않는 채널로 나누고(2.4GHz는 1·6·11), 출력을 기기에 맞춰 낮춰 셀을 작게 하고, 사이트 조사로 커버리지와 겹침을 실측하고, 컨트롤러의 RRM에 자동 조정을 맡기고, 로밍 표준(11k/v/r)으로 이동 중 끊김을 줄이는 것이다.

## 면접에서 나올 만한 질문

### AP를 늘렸는데 Wi-Fi가 느려지는 이유는?

새 AP들이 서로 신호가 닿는 거리에서 같은 채널을 쓰면 동일 채널 간섭이 생기기 때문이다. 같은 채널 AP와 그 기기들이 하나의 경쟁 영역이 되어 CSMA/CA로 채널을 돌려 쓰므로, AP를 늘린 게 아니라 경쟁자를 늘린 셈이 된다. 겹치지 않는 채널로 나누고 출력을 낮춰야 한다.

### 2.4GHz에서 왜 1, 6, 11만 쓰나?

20MHz 채널이 실제로 약 22MHz를 차지하는데 채널 번호는 5MHz 간격이라, 겹치지 않으려면 중심이 25MHz(5채널) 떨어져야 한다. 그래서 겹치지 않는 조합이 1, 6, 11뿐이다. 1, 3, 6처럼 쓰면 3번이 양쪽과 겹쳐 인접 채널 간섭을 만든다.

### 신호 세기(RSSI)가 센데도 속도가 안 나오는 이유는?

속도는 신호 세기가 아니라 신호 대 잡음비(SNR)로 정해지기 때문이다. 같은 채널 AP들이 서로 잡음이 되면 신호가 세도 SNR이 낮아 높은 변조를 못 쓴다. 신호를 더 세게 하기보다 간섭을 줄여 SNR을 올려야 한다.

### 밀집 환경에서 AP 출력을 낮추는 이유는?

AP는 세게 쏘지만 기기 출력은 약해 응답이 못 돌아오는 비대칭을 막고, 셀을 작게 만들어 한 AP당 기기 수와 경쟁을 줄이기 위해서다. 작은 셀을 촘촘히 놓으면 기기가 가까워져 높은 변조를 쓰고 전체 용량이 는다. 출력을 최대로 올리면 셀이 커져 CCI와 sticky client가 는다.

### 802.11r/k/v는 각각 무엇을 하나?

802.11k는 이웃 AP 목록을 줘 기기가 스캔을 빨리 끝내게 하고, 802.11v는 더 좋은 AP로 옮기라고 권하며, 802.11r은 키 재료를 이웃 AP와 미리 나눠 옮길 때 4-way handshake와 802.1X를 생략해 로밍 시간을 수십 ms로 줄인다. 셋이 함께 쓰일 때 이동 중 끊김이 가장 적다.

### sticky client 문제는 무엇이고 어떻게 푸나?

기기가 가까운 AP를 두고 멀어진 AP에 계속 붙어 있어 느려지는 현상이다. 로밍 판단은 기기가 하는데, 옛 AP 신호가 아직 "연결 가능" 수준이면 배터리를 아끼려 안 옮긴다. 셀 경계에서 신호가 충분히 약해지도록 출력을 낮추고, 802.11k/v로 전환을 권하고, 필요하면 컨트롤러의 완화 기능을 조심스럽게 쓴다.

### 컨트롤러 기반과 클라우드 관리 방식의 차이는?

컨트롤러 기반은 전용 WLC가 기기 트래픽까지 중앙에서 처리하고 RRM으로 채널·출력을 자동 조정하지만 컨트롤러가 단일 장애점이라 이중화한다. 클라우드 관리는 설정만 클라우드에서 하고 트래픽은 AP가 로컬에서 처리해, 클라우드가 끊겨도 기존 연결이 유지되는 게 보통이다. 규모와 운영 방식에 따라 고른다.

### 5GHz의 DFS 채널은 무엇을 조심해야 하나?

DFS 채널은 레이더와 공유하므로 AP가 레이더를 감지하면 즉시 그 채널을 비워야 한다. 공항·항만 근처에서는 AP가 갑자기 채널을 바꿔 잠깐 끊기므로, 그런 환경에서는 비DFS 채널만 쓰거나 채널 전환의 영향을 줄이도록 설계한다.
