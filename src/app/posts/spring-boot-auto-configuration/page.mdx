<EasyIntro>
  의존성 두 줄만 넣고 아무 설정 없이 띄웠는데, 데이터베이스 연결 묶음과 트랜잭션 처리기가 저절로 생겨 있었다. 편하지만 내 설정이 안 먹거나 원하지 않은 부품이 생기면, 이 알아서가 어디서 오는지 알아야 고칠 수 있다.

  Spring Boot의 자동 구성은 새 직원 자리를 꾸며 주는 총무팀의 체크리스트와 같다. 체크리스트에는 항목마다 조건이 붙어 있다. 이 라이브러리가 들어 있으면 연결 묶음을 놓고, 직원이 직접 가져온 게 있으면 놓지 않는다는 식이다. 총무팀은 직원이 가져온 물건을 먼저 확인한 뒤 맨 마지막에 빈자리만 채우므로, 기본값을 바꾸고 싶으면 같은 종류의 부품을 하나 직접 두면 된다.

  왜 켜지고 꺼졌는지는 짐작할 필요가 없다. 시작할 때 디버그 옵션을 주면 항목마다 어떤 조건이 맞고 틀렸는지 적힌 보고서가 나온다. 같은 설정이 여러 곳에 있으면 명령줄, 환경 변수, 설정 파일 순으로 앞쪽이 이긴다는 점도 함께 알아 둔다.
</EasyIntro>

`pom.xml`에 `spring-boot-starter-jdbc`와 H2 한 줄씩을 넣고 아무 설정 없이 띄웠다. `DataSource`를 꺼내 보니 `HikariDataSource`가 들어 있다. 커넥션 풀을 만든 적도, 트랜잭션 매니저를 등록한 적도 없는데 `@Transactional`이 동작한다. 편하다. 그런데 운영에서 커넥션 풀 설정이 안 먹거나, 내가 만든 빈이 무시되거나, 반대로 아무도 원하지 않은 빈이 생기면 그때부터는 이 "알아서"가 어디서 오는지 알아야 고칠 수 있다.

이 글은 Spring Boot 자동 구성(auto-configuration)이 그 빈들을 어떻게 고르는지 따라간다. 스타터가 실제로 무엇인지, 자동 구성 목록이 어디에 적혀 있는지, 조건이 어떻게 평가되는지를 `--debug`의 조건 평가 리포트로 직접 읽는다. 그다음 내 빈으로 덮어쓰는 법, 설정값이 어느 출처에서 이기는지, 프로필, 그리고 자동 구성을 하나 직접 만들어 본다. 빈과 컨테이너 자체는 [IoC 컨테이너와 DI](/posts/spring-ioc-di) 글에서 다뤘고, 4.0에서 자동 구성 jar가 쪼개진 이야기는 [Spring Boot 4 마이그레이션](/posts/spring-boot-4-migration)에서 이어 간다.

예제는 JDK 21, Spring Boot 4.1.1로 돌렸다. 의존성은 `spring-boot-starter-jdbc`, `spring-boot-starter-validation`, H2다. 출력의 클래스 이름과 jar 이름은 4.x 기준이고, 3.x에서는 패키지가 다르다(뒤에서 짚는다).

## 스타터 jar에는 코드가 없다

먼저 스타터를 열어 봤다.

```bash
# 스타터 jar 안에 무엇이 있는지 본다
unzip -l ~/.m2/repository/org/springframework/boot/spring-boot-starter-jdbc/4.1.1/spring-boot-starter-jdbc-4.1.1.jar
```

## 자동 구성 목록은 파일 한 장에 적혀 있다

`@SpringBootApplication`은 어노테이션 세 개를 합친 것이다. `@SpringBootConfiguration`(이 클래스도 설정 클래스다), `@ComponentScan`(이 패키지 아래를 훑는다), `@EnableAutoConfiguration`(자동 구성을 켠다). 자동 구성을 켜면 Boot는 클래스패스의 모든 jar에서 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 파일을 찾아 읽는다. 한 줄에 자동 구성 클래스 하나가 적혀 있다.

```bash
# spring-boot-jdbc jar의 자동 구성 목록
unzip -p spring-boot-jdbc-4.1.1.jar META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

```text
org.springframework.boot.jdbc.autoconfigure.DataSourceAutoConfiguration
org.springframework.boot.jdbc.autoconfigure.DataSourceInitializationAutoConfiguration
org.springframework.boot.jdbc.autoconfigure.DataSourceTransactionManagerAutoConfiguration
org.springframework.boot.jdbc.autoconfigure.JdbcClientAutoConfiguration
org.springframework.boot.jdbc.autoconfigure.JdbcTemplateAutoConfiguration
org.springframework.boot.jdbc.autoconfigure.JndiDataSourceAutoConfiguration
org.springframework.boot.jdbc.autoconfigure.XADataSourceAutoConfiguration
org.springframework.boot.jdbc.autoconfigure.health.DataSourceHealthContributorAutoConfiguration
org.springframework.boot.jdbc.autoconfigure.metrics.DataSourcePoolMetricsAutoConfiguration
```

이 예제의 클래스패스에서 이 파일을 가진 jar를 세어 봤다.

```text
spring-boot-autoconfigure-4.1.1.jar 12
spring-boot-jdbc-4.1.1.jar 9
spring-boot-transaction-4.1.1.jar 3
spring-boot-persistence-4.1.1.jar 1
spring-boot-validation-4.1.1.jar 1
```

목록에 있다고 모두 빈이 되는 건 아니다. 각 클래스에는 조건이 붙어 있고, 조건을 통과한 것만 설정으로 쓰인다. 이 파일 형식은 Boot 2.7에서 생겼고, 그전에 쓰던 `spring.factories`의 `EnableAutoConfiguration` 키는 3.0에서 자동 구성 등록용으로는 더 이상 읽지 않는다. 오래된 사내 스타터를 3.x로 올렸더니 자동 구성이 통째로 사라지는 사고가 여기서 난다.

## 조건 평가 리포트로 "왜"를 읽는다

어떤 자동 구성이 왜 켜졌고 왜 꺼졌는지는 추측할 필요가 없다. `--debug`로 띄우면 Boot가 조건 평가 리포트를 찍는다.

```bash
# 조건 평가 리포트를 찍는다 (debug 플래그는 로그 레벨을 전부 올리지 않고 핵심 로거만 올린다)
java -jar app.jar --debug
# 또는 application.properties에 debug=true
```

출력은 길다. 이 예제에서 321줄이 나왔다. 섹션은 `Positive matches`, `Negative matches`, `Exclusions`, `Unconditional classes` 네 개다. `DataSource` 부분을 옮긴다.

자주 쓰는 조건은 몇 가지로 정리된다. `@ConditionalOnClass`/`@ConditionalOnMissingClass`는 클래스패스에 그 클래스가 있는지 본다. 의존성을 넣는 것만으로 기능이 켜지는 이유가 이것이다. `@ConditionalOnBean`/`@ConditionalOnMissingBean`은 그 타입의 빈이 이미 있는지 본다. `@ConditionalOnProperty`는 설정값을 보고, 3.5부터는 참·거짓 값만 보는 `@ConditionalOnBooleanProperty`가 따로 생겼다(위 리포트의 `AopAutoConfiguration`이 이걸 쓴다). `@ConditionalOnWebApplication`, `@ConditionalOnSingleCandidate`(후보가 하나이거나 `@Primary`가 정해져 있을 때)도 리포트에 자주 보인다.

같은 리포트는 액추에이터의 `/actuator/conditions` 엔드포인트로도 볼 수 있다. 운영 중인 서버를 다시 띄우지 않고 확인할 수 있지만, 내부 구조가 다 드러나니 외부에 열어 두지 않는다.

## 내 빈을 두면 자동 구성이 물러난다

자동 구성 대부분은 `@ConditionalOnMissingBean`을 단다. "사용자가 같은 걸 이미 만들었으면 나는 빠진다"는 약속이다. 그래서 덮어쓰려면 같은 타입의 빈을 하나 두면 된다. 설정을 끄거나 무언가를 상속할 필요가 없다.

아래 그림은 같은 `Greeter` 자리를 두고 세 번 띄운 결과를 따라간다. 조건을 하나씩 통과하거나 걸리는 모습을 본다.

실제 출력이다. `by` 뒤에 누가 만든 빈인지 찍히게 해 뒀다.

```text
[기본]
Greeter    = Hi, 민수  [by auto-config]
[--demo.custom-greeter=true, 내 @Bean을 켠다]
Greeter    = Hi, 민수  [by my @Bean]
[--greeting.enabled=false]
Greeter    = 없음
```

내 빈을 켰을 때 리포트에는 앞에서 조각으로 나눠 본 줄이 `Negative matches`에 나온다.

```text
   GreetingAutoConfiguration#greeter:
      Did not match:
         - @ConditionalOnMissingBean (types: demo.starter.Greeter; SearchStrategy: all) found beans of type 'demo.starter.Greeter' myGreeter (OnBeanCondition)
```

자동 구성 하나를 통째로 빼고 싶을 때는 제외한다.

```bash
# DataSource 자동 구성을 뺀다 (어노테이션으로는 @SpringBootApplication(exclude = ...))
java -jar app.jar --spring.autoconfigure.exclude=org.springframework.boot.jdbc.autoconfigure.DataSourceAutoConfiguration
```

```text
Exclusions:
-----------

    org.springframework.boot.jdbc.autoconfigure.DataSourceAutoConfiguration

DataSource = 없음
```

DB 없이 띄워야 하는 배치 도구나, 의존성은 있지만 DB를 직접 구성하는 앱에서 쓴다. 다만 `exclude`는 마지막 수단이다. 대개는 내 빈을 두거나 속성으로 조정하는 쪽이 의도가 분명하다.

덮어쓸 때 흔히 하는 실수가 둘 있다. 하나는 내 `@Configuration`에 `@ConditionalOnMissingBean`을 다는 것이다. Boot 문서는 이 조건이 "지금까지 처리된 빈 정의"만 보고 판단하므로 자동 구성 클래스에만 쓰라고 권한다. 자동 구성은 사용자 설정이 모두 등록된 뒤에 처리되도록 보장되지만, 사용자 설정끼리는 처리 순서가 정해져 있지 않다. 다른 하나는 `DataSource`를 직접 만들면서 `spring.datasource.hikari.*` 설정이 계속 먹을 거라고 기대하는 것이다. 자동 구성이 물러났으니 그 속성을 읽어 주던 코드도 함께 빠진다. 직접 만든 빈에 속성을 붙이려면 `@ConfigurationProperties("spring.datasource.hikari")`를 그 `@Bean` 메서드에 같이 단다.

## 같은 키가 여러 곳에 있으면 누가 이기나

자동 구성의 조건도, 내 코드도 결국 `Environment`에서 값을 읽는다. 같은 키가 여러 출처에 있으면 우선순위가 높은 쪽이 이긴다. Boot 문서에 적힌 순서는 낮은 것부터 이렇다(뒤에 올수록 앞을 덮는다).

1. `SpringApplication.setDefaultProperties`로 넣은 기본값
2. `@PropertySource`
3. 설정 파일(`application.properties`, YAML)
4. `random.*`
5. OS 환경 변수
6. 자바 시스템 속성(`-D`)
7. JNDI, 서블릿 초기화 파라미터
8. `SPRING_APPLICATION_JSON`
9. 명령줄 인자(`--key=value`)
10. 테스트의 `properties`, `@DynamicPropertySource`, `@TestPropertySource` 등

설정 파일끼리도 순서가 있다. jar 안의 `application.properties` < jar 안의 `application-{profile}.properties` < jar 밖의 `application.properties` < jar 밖의 프로필 파일이다. 같은 자리에 `.properties`와 YAML이 함께 있으면 `.properties`가 이긴다.

외우기보다 직접 덮어 보면 감이 온다. `greeting.prefix`를 `application.properties`에는 `Hi`로, `application-prod.properties`에는 `Hello(prod)`로 두고 출처를 하나씩 더했다.

```bash
java -jar app.jar                                         # 파일만
java -jar app.jar --spring.profiles.active=prod           # 프로필 파일
GREETING_PREFIX=FromEnv java -jar app.jar --spring.profiles.active=prod
GREETING_PREFIX=FromEnv java -jar app.jar --spring.profiles.active=prod --greeting.prefix=FromArgs
GREETING_PREFIX=FromEnv java -Dgreeting.prefix=FromSysProp -jar app.jar
```

```text
Greeter    = Hi, 민수  [by auto-config]
Greeter    = Hello(prod), 민수  [by auto-config]
Greeter    = FromEnv, 민수  [by auto-config]
Greeter    = FromArgs, 민수  [by auto-config]
Greeter    = FromSysProp, 민수  [by auto-config]
```

```text
Greeter    = HI, 민수  [by auto-config]
```

## 설정값을 타입으로 묶고 시작할 때 검사한다

`@Value`로 키를 하나씩 꺼내 쓰면 오타가 런타임까지 숨어 있다. `@ConfigurationProperties`는 접두사 아래의 키를 객체 하나로 묶고, 검증 어노테이션을 달면 시작할 때 검사한다.

```java
@Validated
@ConfigurationProperties("greeting")
public record GreetingProperties(@NotBlank String prefix, boolean shout) { }
```

값을 비워서 띄우면 시작이 멈추고, 어느 출처의 값이 문제인지 알려 준다.

```text
APPLICATION FAILED TO START
***************************

Description:

Binding to target demo.starter.GreetingProperties failed:

    Property: greeting.prefix
    Value: ""
    Origin: "greeting.prefix" from property source "commandLineArgs"
    Reason: must not be blank
```

`Origin`이 중요하다. 운영에서 "설정은 분명히 넣었는데 다른 값이 들어간다"는 일이 생기면, 이 줄이나 액추에이터의 `/actuator/env/{키}`가 그 값이 어느 출처에서 왔는지 보여 준다. 잘못된 설정으로 뜨고 나서 첫 요청에 터지는 것보다, 시작 단계에서 멈추는 쪽이 롤링 배포에서 훨씬 안전하다. 새 파드가 준비되지 않으니 옛 파드가 계속 트래픽을 받는다.

설정 파일 인코딩도 한 번 겪으면 잊지 않는다. 이 예제에서 `application.properties`에 `greeting.prefix=안녕`을 UTF-8로 적었더니 값이 깨져서 들어왔다. Boot는 `.properties` 파일을 기본으로 ISO-8859-1로 읽는다(4.1.1 소스와 문서 기준). 같은 값을 `application-ko.yml`에 두니 정상으로 읽혔다.

```text
Greeter    = 안녕, 민수  [by auto-config]
profiles   = ko
```

한글 값은 YAML에 두거나, `.properties`에서는 `안녕`처럼 이스케이프한다. 4.x 문서에는 `spring.config.import`로 가져오는 파일에 `[encoding=utf-8]`을 붙이는 방법도 적혀 있다.

## 프로필은 설정 묶음을 고르는 스위치다

`spring.profiles.active=prod`를 주면 `application-prod.properties`(또는 `.yml`)가 기본 파일 위에 얹힌다. 빈에도 `@Profile("prod")`를 달아 그 프로필에서만 등록되게 할 수 있다.

프로필을 쓸 때 실무에서 자주 걸리는 건 이런 것들이다.

- 프로필 파일을 환경마다 jar 안에 넣고 `prod`, `stage`, `dev`로 고르는 방식은 비밀번호까지 jar에 들어가기 쉽다. 비밀값은 환경 변수나 시크릿 저장소에서 넣고([시크릿 관리](/posts/secrets-management)), 프로필은 "어떤 기능을 켤지" 정도로만 쓴다. 이미지 하나를 모든 환경에 그대로 올리는 쪽이 배포 사고가 적다.
- 프로필 파일 안에서 `spring.profiles.active`를 다시 지정하면 시작이 실패한다. 2.4부터 프로필별 파일에서는 이 속성을 쓸 수 없다. `application-prod.properties`에 한 줄을 넣고 띄운 결과다.

  ```text
  org.springframework.boot.context.config.InvalidConfigDataPropertyException: Property 'spring.profiles.active' imported from location 'class path resource [application-prod.properties]' is invalid in a profile specific resource [origin: class path resource [application-prod.properties] - 2:24]
  ```

  여러 프로필을 한꺼번에 켜려면 기본 파일에서 `spring.profiles.group.prod=db,metrics`처럼 그룹을 만든다.
- 테스트에서 `@ActiveProfiles("test")`를 쓰는데 실제 운영 설정이 섞이는 경우는 대개 기본 파일에 운영 값을 넣어 둔 탓이다. 기본 파일에는 어디서나 맞는 값만 둔다.

## 자동 구성을 하나 직접 만든다

사내 공통 모듈을 스타터로 만들면 각 서비스가 의존성 하나로 같은 빈을 받는다. 위에서 써 온 `Greeter`가 그런 예다. 필요한 건 세 가지다.

```java
// 1. 자동 구성 클래스
@AutoConfiguration
@ConditionalOnProperty(prefix = "greeting", name = "enabled", havingValue = "true", matchIfMissing = true)
@EnableConfigurationProperties(GreetingProperties.class)
public class GreetingAutoConfiguration {
  @Bean
  @ConditionalOnMissingBean
  Greeter greeter(GreetingProperties props) { return new Greeter(props, "auto-config"); }
}
```

```text
# 2. src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
demo.starter.GreetingAutoConfiguration
```

3. 이 클래스가 쓰는 쪽 애플리케이션의 컴포넌트 스캔에 걸리지 않게 패키지를 분리한다. 예제에서는 앱이 `demo.app`, 자동 구성이 `demo.starter`다. 스캔에 걸리면 자동 구성이 아니라 일반 설정으로 먼저 처리되어 `@ConditionalOnMissingBean`의 순서 보장이 깨진다.

띄우면 리포트에 내 자동 구성이 Boot의 것과 나란히 나온다.

```text
   GreetingAutoConfiguration matched:
      - @ConditionalOnProperty (greeting.enabled=true) matched (OnPropertyCondition)

   GreetingAutoConfiguration#greeter matched:
      - @ConditionalOnMissingBean (types: demo.starter.Greeter; SearchStrategy: all) did not find any beans (OnBeanCondition)
```

공식 문서가 권하는 구조는 자동 구성 코드를 담은 `xxx-autoconfigure` 모듈과, 그것과 라이브러리를 묶기만 하는 `xxx-spring-boot-starter` 모듈을 나누는 것이다. 이름은 `spring-boot-`로 시작하지 않게 짓는다. 그 접두사는 Spring Boot 공식 모듈 몫이다. 다른 자동 구성보다 뒤에 와야 하면 `@AutoConfiguration(after = DataSourceAutoConfiguration.class)`로 순서를 적는다.

아래 그림은 지금까지 나온 조각들의 관계다. 의존성 하나가 빈이 되기까지 어떤 파일을 거치고, 내 빈은 어디서 끼어드는지 본다.

## 3.x와 4.x에서 클래스 이름이 다르다

리포트나 `exclude`에 클래스 이름을 적을 때 버전을 확인한다. 3.x까지는 거의 모든 자동 구성이 `spring-boot-autoconfigure` jar 하나에 `org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration` 같은 이름으로 들어 있었다. 4.0부터는 기술별 모듈(`spring-boot-jdbc` 등)로 나뉘면서 이 예제처럼 `org.springframework.boot.jdbc.autoconfigure.DataSourceAutoConfiguration`이 됐다. 3.x 시절 문자열로 적어 둔 `spring.autoconfigure.exclude`는 4.x에서 그대로 두면 동작하지 않는다. 어떻게 바뀌었고 무엇을 고쳐야 하는지는 [Spring Boot 4 마이그레이션](/posts/spring-boot-4-migration)에서 실제 빌드 오류와 함께 본다.

## 자동 구성이 이상할 때 보는 순서

증상별로 처음 볼 곳을 모아 둔다.

1. 원하지 않는 빈이 생겼다: `--debug`의 `Positive matches`에서 그 빈을 만든 자동 구성을 찾는다. 대개 의존성이 끌고 온 클래스 때문에 `@ConditionalOnClass`가 맞은 것이다. `mvn dependency:tree`로 누가 그 라이브러리를 끌고 왔는지 본다.
2. 기대한 빈이 없다: `Negative matches`에서 `Did not match` 이유를 읽는다. 클래스가 없거나, 속성이 꺼졌거나, 같은 타입 빈이 이미 있다.
3. 설정값이 안 먹는다: `/actuator/env/{키}`나 바인딩 오류의 `Origin`으로 실제로 이긴 출처를 본다. 환경 변수 이름 변환(밑줄, 대시 제거)을 틀린 경우가 많다. 그 빈을 내가 직접 만들어 자동 구성이 물러난 건 아닌지도 본다.
4. 버전을 올렸더니 자동 구성이 사라졌다: 사내 스타터가 아직 `spring.factories`에 등록하고 있지 않은지, 4.x로 오면서 필요한 기술 모듈 스타터가 빠지지 않았는지 본다.

## 알아서 해 주는 것의 정체

자동 구성은 마법이 아니라 "목록 파일에 적힌 설정 클래스를, 조건을 통과한 것만, 내 설정 다음에 등록한다"는 규칙이다. 조건 대부분이 "사용자가 이미 만들었으면 빠진다"는 방향이라, 덮어쓰려면 같은 타입의 빈을 두면 된다. 그리고 왜 켜지고 꺼졌는지는 조건 평가 리포트가 한 줄씩 적어 준다. 설정값은 출처마다 우선순위가 있고, 시작할 때 묶어서 검사하면 잘못된 값이 운영까지 가지 않는다.

## 면접에서 나올 만한 질문

### Spring Boot 자동 구성은 어떻게 동작하나요?

`@EnableAutoConfiguration`이 클래스패스의 모든 jar에서 `META-INF/spring/...AutoConfiguration.imports` 파일을 읽어 자동 구성 클래스 목록을 모은다. 각 클래스에는 `@ConditionalOnClass`, `@ConditionalOnMissingBean`, `@ConditionalOnProperty` 같은 조건이 붙어 있고, 통과한 것만 설정으로 등록된다. 자동 구성은 사용자 설정이 모두 처리된 뒤에 평가되므로 사용자가 만든 빈을 보고 물러날 수 있다.

### 스타터와 자동 구성은 어떻게 다른가요?

스타터는 코드가 없는 의존성 묶음이고, 자동 구성은 그 라이브러리를 언제 어떻게 빈으로 만들지 적은 코드다. 스타터를 넣으면 라이브러리와 자동 구성 모듈이 함께 들어오고, 라이브러리 클래스가 클래스패스에 생기니 `@ConditionalOnClass`가 맞아 기능이 켜진다. 버전은 부모 POM의 BOM이 맞춰 준다.

### Boot가 만든 DataSource 대신 내 것을 쓰려면 어떻게 하나요?

같은 타입의 `@Bean`을 하나 두면 된다. `DataSourceAutoConfiguration`은 `@ConditionalOnMissingBean`이라 내 빈을 보고 물러난다. 이때 `spring.datasource.hikari.*`를 읽어 주던 자동 구성 코드도 함께 빠지므로, 그 속성을 계속 쓰려면 내 `@Bean` 메서드에 `@ConfigurationProperties`를 붙인다. 자동 구성 전체를 빼려면 `exclude`를 쓰지만 마지막 수단이다.

### 특정 자동 구성이 왜 적용됐는지 어떻게 확인하나요?

`--debug`나 `debug=true`로 띄우면 조건 평가 리포트가 찍힌다. `Positive matches`와 `Negative matches`에 클래스마다 어떤 조건이 맞았고 틀렸는지, `@ConditionalOnMissingBean`이면 어떤 이름의 빈 때문에 물러났는지까지 나온다. 운영 중에는 액추에이터의 `/actuator/conditions`로 같은 내용을 볼 수 있지만 외부에 노출하지 않는다.

### 내 설정 클래스에 @ConditionalOnMissingBean을 쓰면 왜 위험한가요?

이 조건은 그 시점까지 등록된 빈 정의만 보고 판단한다. 자동 구성은 사용자 설정 뒤에 처리된다는 보장이 있지만, 사용자 설정 클래스끼리는 처리 순서가 정해져 있지 않다. 그래서 같은 코드가 어떤 날은 빈을 만들고 어떤 날은 안 만드는 식으로 흔들릴 수 있고, Boot 문서도 자동 구성 클래스에만 쓰라고 권한다.

### 같은 설정 키가 application.properties, 환경 변수, 명령줄에 모두 있으면 무엇이 이기나요?

명령줄 인자가 이기고, 그다음이 자바 시스템 속성, 환경 변수, 프로필 파일, 기본 설정 파일 순이다. 환경 변수는 점을 밑줄로 바꾸고 대시를 지우고 대문자로 쓴 이름으로 찾는다. 실제로 어느 값이 이겼는지는 `/actuator/env/{키}`나 바인딩 오류의 `Origin`에서 확인한다.

### 사내 공통 스타터를 만들 때 주의할 점은 무엇인가요?

자동 구성 클래스를 `AutoConfiguration.imports`에 등록하고, 쓰는 쪽의 컴포넌트 스캔에 걸리지 않는 패키지에 둔다. 빈에는 `@ConditionalOnMissingBean`을 달아 서비스가 덮어쓸 수 있게 하고, 설정은 `@ConfigurationProperties`와 검증으로 받는다. 이름은 `spring-boot-` 접두사를 피하고, 3.0 이후에는 `spring.factories` 방식이 자동 구성 등록에 쓰이지 않는다는 점을 확인한다.
