검색 엔진은 `running`, `runs`, `runner`를 모두 `run`으로 묶어서 색인한다. 단어를 어근으로 줄이는 이 작업을 어간 추출(stemming)이라고 한다. 진짜 어간 추출기는 언어 규칙을 쓰지만, 가장 단순한 형태는 어근 목록을 들고 있다가 단어 앞부분이 어근과 맞으면 그 어근으로 바꾸는 것이다.

[LeetCode 648. Replace Words](https://leetcode.com/problems/replace-words/)가 이 단순한 형태다. 문장의 단어마다 "이 단어의 접두사인 어근 중 가장 짧은 것"을 찾는다. [Implement Trie](/posts/leetcode-implement-trie)의 트라이를 거의 그대로 쓰는데, 내려가다가 처음 만나는 끝 표시에서 멈춘다는 점이 다르다. 이 글은 단어마다 모든 어근을 맞춰 보는 풀이부터 문장을 한 글자씩 한 번만 훑는 풀이까지 다섯 가지를 보고, 실제로 재어 보면 해시 집합 풀이가 트라이와 거의 비슷하게 나오는 이유도 함께 본다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 가장 짧은 어근으로 바꾼다

입력은 어근 목록 `dictionary`와 공백 하나로 단어를 나눈 문장 `sentence`다. 문장의 단어마다 그 단어로 시작하는 게 아니라, 그 단어가 어근으로 시작하는지를 본다. 맞는 어근이 여러 개면 가장 짧은 것으로 바꾸고, 하나도 없으면 단어를 그대로 둔다. 바꾼 단어들을 다시 공백으로 이어 돌려준다.

- 어근은 최대 1,000개, 어근 하나의 길이는 100 이하.
- 문장 길이는 10^6 이하, 단어 하나의 길이는 1,000 이하. 모두 소문자.

문장이 100만 글자까지 간다는 게 이 문제의 무게다. 단어마다 어근 1,000개를 다 맞춰 보면 비교가 수억 번까지 갈 수 있다. 어근 길이가 100 이하라는 조건은 반대로 단어 하나에서 볼 앞부분이 100글자를 넘지 않는다는 뜻이라, 뒤에서 풀이 선택에 영향을 준다.

이 글에서 쓸 예시다.

```text
dictionary = [sun, su, moon, star]
sentence   = "sunny moonlight starts super night"
답         = "su moon star su night"
```

손으로 따라가 보자. `sunny`는 `su`로도 `sun`으로도 시작한다. 둘 중 짧은 `su`로 바꾼다. `moonlight`는 `moon`, `starts`는 `star`로 시작한다. `super`는 `su`로 시작한다. `sun`과는 셋째 글자가 다르다. `night`는 어떤 어근으로도 시작하지 않아서 그대로 둔다.

`sunny`에서 볼 수 있듯이 가장 짧은 어근을 고르는 게 요점이다. 목록 순서가 `sun`이 먼저라고 `sun`을 고르면 틀린다.

## 단어마다 어근을 전부 맞춰 보기

가장 먼저 떠오르는 건 단어마다 어근을 하나씩 다 확인하고, 맞는 것 중 가장 짧은 것을 고르는 것이다.

```js
function replaceWords(dictionary, sentence) {
  return sentence
    .split(" ")
    .map((word) => {
      let best = null;
      for (const root of dictionary) {
        // 단어가 이 어근으로 시작하고, 지금까지 찾은 것보다 짧으면 바꾼다
        if (word.startsWith(root) && (best === null || root.length < best.length)) best = root;
      }
      return best ?? word; // 맞는 어근이 없으면 그대로
    })
    .join(" ");
}
```

단어 수를 N, 어근 수를 D, 어근 최대 길이를 R이라 하면 O(N · D · R)이다. 단어마다 어근 D개를 보고, `startsWith` 한 번에 최대 R글자를 비교한다. 공간은 결과 문자열과 쪼갠 단어 배열, O(문장 길이)다.

어근이 1,000개이고 모두 길이 100인데 앞 97글자가 같다면, 단어 하나에 비교가 거의 10만 번이다. 단어가 1,000개면 1억 번이다. 뒤의 측정에서 이런 입력에 0.5초쯤 걸렸다. LeetCode에서는 통과하지만 넉넉하지 않다.

## 짧은 어근부터 정렬해 두기

가장 짧은 어근을 원하니, 어근을 길이 순으로 정렬해 두면 처음 맞는 어근이 곧 답이다. 맞는 걸 찾는 순간 멈출 수 있다.

```js
function replaceWords(dictionary, sentence) {
  const roots = [...dictionary].sort((a, b) => a.length - b.length); // 짧은 것부터
  return sentence
    .split(" ")
    .map((word) => roots.find((r) => word.startsWith(r)) ?? word) // 처음 맞는 것이 가장 짧다
    .join(" ");
}
```

정렬에 O(D log D)가 들고, 나머지는 여전히 최악 O(N · D · R)이다. 맞는 어근이 있는 단어는 일찍 멈추지만, 맞는 어근이 없는 단어는 여전히 1,000개를 다 본다. 실제로 측정해 보면 맞는 어근이 없는 입력에서 첫 풀이와 시간이 같았다.

정렬 비교자를 빼고 `sort()`만 부르면 사전 순이 된다. `b`와 `ab`가 있으면 `ab`, `b` 순서라 길이 순이 아니다. 그런데 직접 돌려 보면 답은 똑같이 맞는다. 무작위 입력 5,000개로 길이 순 풀이와 비교해도 하나도 다르지 않았다. 한 단어와 맞는 어근들은 모두 그 단어의 앞부분이라서, 짧은 어근이 긴 어근의 앞부분이 된다(`su`와 `sun`). 그리고 사전 순에서 앞부분은 언제나 그걸 늘인 문자열보다 앞에 온다. 그래서 맞는 어근끼리만 보면 사전 순과 길이 순이 같다. 면접에서는 길이 순으로 쓰는 쪽이 의도가 분명하지만, 사전 순으로 써도 틀리지 않는 이유를 말할 수 있으면 좋다. 이 성질은 [Longest Common Prefix](/posts/leetcode-longest-common-prefix)의 정렬 풀이에서도 쓴다.

## 앞부분을 잘라서 집합에 물어보기

방향을 바꿔 보자. 어근을 하나씩 맞춰 보는 대신, 단어의 앞부분을 짧은 것부터 잘라서 "이게 어근인가"를 해시 집합에 묻는다. 해시 집합은 값을 해시 함수로 칸 번호로 바꿔 넣어 두는 구조라, 있는지 묻는 데 문자열 길이만큼만 든다. `sunny`라면 `s`, `su`를 차례로 묻고, `su`에서 `있다`가 나오니 멈춘다. 짧은 것부터 묻기 때문에 처음 나온 답이 가장 짧은 어근이다.

어근 길이는 100 이하이니 100글자까지만 잘라 보면 된다. 한 걸음 더 나아가, 실제로 있는 어근 길이만 시도한다. 어근이 모두 길이 3, 4라면 길이 1, 2짜리 앞부분은 물어볼 필요가 없다.

```js
function replaceWords(dictionary, sentence) {
  const roots = new Set(dictionary);
  // 실제로 있는 어근 길이만, 짧은 것부터
  const lengths = [...new Set(dictionary.map((r) => r.length))].sort((a, b) => a - b);
  return sentence
    .split(" ")
    .map((word) => {
      for (const len of lengths) {
        if (len > word.length) break;  // 단어보다 긴 어근은 접두사가 될 수 없다
        const p = word.slice(0, len);
        if (roots.has(p)) return p;    // 처음 맞는 것이 가장 짧다
      }
      return word;
    })
    .join(" ");
}
```

단어 하나에서 길이 k개를 시도하고, 시도마다 앞부분을 잘라 해시하는 데 그 길이만큼 든다. 최악은 길이 1부터 100까지 모두 있을 때로 단어당 1 + 2 + ... + 100, 약 5,000글자다. 전체는 O(N · R²)인데 R이 100으로 묶여 있으니 단어 수에 비례하는 셈이다. 어근 수 D가 식에서 빠졌다는 게 앞의 두 풀이와의 차이다.

이 풀이는 생각보다 훨씬 강하다. 뒤의 측정에서 트라이와 거의 차이가 나지 않았다. 그래도 남는 낭비가 있다. `s`를 묻고, `su`를 물을 때 `s`를 다시 해시한다. 앞부분을 한 글자씩 늘려 가며 묻는 일이 "한 글자씩 내려가기"와 같은 모양인데, 매번 처음부터 다시 계산한다. 이걸 이어서 할 수 있는 구조가 트라이다.

단어를 줄이는 방법은 이렇다.

1. 뿌리에서 시작해 단어의 글자를 하나씩 따라 내려간다.
2. 그 글자의 자식이 없으면, 이 단어로 시작하는 어근이 더는 없다는 뜻이다. 단어를 그대로 둔다.
3. 내려간 노드에 끝 표시가 있으면 거기까지가 가장 짧은 어근이다. 더 내려가지 않고 그때까지 읽은 앞부분을 돌려준다.
4. 단어를 다 읽을 때까지 끝 표시를 못 만났으면 단어를 그대로 둔다.

3번에서 멈추는 이유를 짚어 두자. 트라이를 위에서부터 내려가니, 처음 만나는 끝 표시가 가장 짧은 어근이다. 더 긴 어근(`sun`)은 그 아래에 있어서 볼 필요가 없다. 정렬도, 길이 비교도 필요 없이 내려가는 순서가 곧 짧은 순서다.

같은 이유로 트라이를 만들 때도 아낄 수 있다. 어근을 넣다가 이미 끝 표시가 붙은 노드를 지나게 되면, 지금 넣는 어근은 더 짧은 어근 뒤에 있으니 쓰일 일이 없다. 그 자리에서 넣기를 멈춘다. 그림의 점선 `sun`이 그런 노드인데, `su`가 먼저 들어갔다면 아예 만들어지지 않는다. 이 예시처럼 `sun`이 먼저 들어가면 노드는 생기지만 내려가기가 `u`에서 멈추니 답은 같다.

```js
function replaceWords(dictionary, sentence) {
  const newNode = () => ({ children: new Array(26).fill(null), isEnd: false });
  const root = newNode();
  for (const w of dictionary) {
    let node = root;
    for (let i = 0; i < w.length && !node.isEnd; i++) { // 더 짧은 어근을 지나면 멈춘다
      const c = w.charCodeAt(i) - 97;
      if (node.children[c] === null) node.children[c] = newNode();
      node = node.children[c];
    }
    node.isEnd = true;
  }
  const shorten = (word) => {
    let node = root;
    for (let i = 0; i < word.length; i++) {
      node = node.children[word.charCodeAt(i) - 97];
      if (node === null) return word;              // 이어지는 어근이 없다
      if (node.isEnd) return word.slice(0, i + 1); // 처음 만난 끝 표시가 가장 짧은 어근
    }
    return word;                                    // 단어를 다 읽었는데 어근이 없다
  };
  return sentence.split(" ").map(shorten).join(" ");
}
```

### Python과 Java로 쓰면

Python은 딕셔너리 하나로 노드를 만들고, 끝 표시를 `"$"` 키로 두는 방식이 짧다. 어근에는 소문자만 오니 `$`가 글자 키와 겹칠 일이 없다.

```python
from typing import List


def replace_words(dictionary: List[str], sentence: str) -> str:
    root = {}
    END = "$"  # 이 키가 있으면 여기서 어근이 끝난다
    for w in dictionary:
        node = root
        for ch in w:
            if END in node:  # 더 짧은 어근이 이미 있으면 이 어근은 쓸 일이 없다
                break
            node = node.setdefault(ch, {})
        node[END] = True

    def shorten(word: str) -> str:
        node = root
        for i, ch in enumerate(word):
            node = node.get(ch)
            if node is None:
                return word
            if END in node:
                return word[: i + 1]
        return word

    return " ".join(shorten(w) for w in sentence.split(" "))


print(replace_words(["sun", "su", "moon", "star"], "sunny moonlight starts super night"))
```

```text
su moon star su night
```

넣기 루프에서 `break`한 뒤에도 `node[END] = True`가 실행된다. 이때 `node`는 이미 끝 표시가 있는 더 짧은 어근의 노드라서, 같은 표시를 한 번 더 다는 것뿐이고 해가 없다.

Java는 문자열을 `+`로 이어 붙이면 이어 붙일 때마다 새 문자열을 만들어 문장 길이의 제곱이 될 수 있다. `StringBuilder`에 문장 길이만큼 미리 용량을 잡고 쓴다.

```java
import java.util.*;

class Solution {
    private static class Node {
        Node[] children = new Node[26];
        boolean isEnd;
    }

    public String replaceWords(List<String> dictionary, String sentence) {
        Node root = new Node();
        for (String w : dictionary) {
            Node node = root;
            for (int i = 0; i < w.length() && !node.isEnd; i++) { // 짧은 어근이 있으면 멈춘다
                int c = w.charAt(i) - 'a';
                if (node.children[c] == null) node.children[c] = new Node();
                node = node.children[c];
            }
            node.isEnd = true;
        }
        StringBuilder sb = new StringBuilder(sentence.length());
        for (String word : sentence.split(" ")) {
            if (sb.length() > 0) sb.append(' ');
            Node node = root;
            int cut = -1;
            for (int i = 0; i < word.length(); i++) {
                node = node.children[word.charAt(i) - 'a'];
                if (node == null) break;
                if (node.isEnd) { cut = i + 1; break; }
            }
            sb.append(cut == -1 ? word : word.substring(0, cut));
        }
        return sb.toString();
    }
}
```

```text
su moon star su night
```

`sentence.split(" ")`의 인자는 정규식이다. 공백 하나는 정규식에서도 공백 하나라 문제없지만, 구분자가 `.`이나 `|`였다면 `split("\\.")`처럼 이스케이프해야 한다. 이 문제는 단어 사이가 공백 하나로 보장되어 있어서 빈 문자열이 끼지 않는다.

## 문장을 쪼개지 않고 한 번만 훑기

앞의 풀이들은 모두 `split(" ")`으로 단어 배열을 만든다. 문장이 100만 글자면 단어 배열과 결과 배열이 문장만큼 메모리를 더 쓴다. 문장이 파일이나 네트워크에서 조금씩 들어온다면 다 받기 전에는 쪼갤 수도 없다.

트라이 내려가기는 글자 하나씩 진행되니, 문장을 한 글자씩 읽으면서 상태 두 개만 들고 다닐 수 있다. 지금 단어에서 트라이의 어느 노드까지 왔나(`node`), 그리고 어근을 이미 찾아서 이 단어의 남은 글자를 버리는 중인가(`cut`)다.

```js
function replaceWords(dictionary, sentence) {
  // 트라이는 앞의 풀이와 같다
  const newNode = () => ({ children: new Array(26).fill(null), isEnd: false });
  const root = newNode();
  for (const w of dictionary) {
    let node = root;
    for (let i = 0; i < w.length && !node.isEnd; i++) {
      const c = w.charCodeAt(i) - 97;
      if (node.children[c] === null) node.children[c] = newNode();
      node = node.children[c];
    }
    node.isEnd = true;
  }
  const out = [];
  let node = root;  // 지금 단어에서 트라이의 어디까지 왔나. null이면 맞는 어근이 없다
  let cut = false;  // 어근을 찾아서 이 단어의 남은 글자를 버리는 중
  for (let i = 0; i < sentence.length; i++) {
    const ch = sentence[i];
    if (ch === " ") {               // 단어가 끝났다. 상태를 처음으로
      out.push(" ");
      node = root;
      cut = false;
      continue;
    }
    if (cut) continue;              // 어근 뒤의 글자는 버린다
    out.push(ch);
    if (node !== null) {
      node = node.children[ch.charCodeAt(0) - 97];
      if (node !== null && node.isEnd) cut = true; // 어근 끝. 여기까지만 남긴다
    }
  }
  return out.join("");
}
```

`node`가 `null`이 되면 그 단어에는 맞는 어근이 없다는 뜻이라, 단어 끝까지 글자를 그대로 내보낸다. `cut`이 켜지면 공백을 만날 때까지 글자를 버린다. 문장을 한 번만 읽고 단어 배열을 만들지 않는다. 결과를 바로 파일이나 소켓으로 내보내면 추가 메모리는 트라이뿐이다.

다만 JS에서 재 보면 이 풀이가 `split` 풀이보다 느렸다. 글자 100만 개를 하나씩 배열에 넣고 마지막에 잇는 비용이, 엔진이 C++로 처리하는 `split`과 `slice`보다 비싸기 때문이다. 이 풀이를 고르는 이유는 속도가 아니라 메모리와 스트리밍이다. 속도도 챙기려면 글자를 하나씩 넣지 않고, 단어 시작 위치를 기억해 두었다가 `sentence.slice(start, i)`로 한 번에 잘라 넣는다.

## 다섯 풀이를 재 보면

어근 1,000개를 모두 `a`로 시작하게 만들었다. 길이 2부터 100까지의 `aa...ab` 99개와, `a` 97개 뒤에 세 글자를 붙인 길이 100짜리 901개다. 문장은 `a` 999개짜리 단어 1,000개, 약 100만 글자다. 어떤 단어도 어근과 맞지 않아서 모든 풀이가 최악으로 일한다.

```text

단어마다 전부 맞추기        520ms
짧은 어근부터 정렬          506ms
앞부분 잘라 집합에 묻기      16ms          15ms
```

앞의 두 풀이는 단어마다 어근 1,000개와 97글자씩 비교하느라 느리다. 맞는 어근이 없으니 정렬해도 일찍 멈추지 못한다.

눈여겨볼 건 집합 풀이와 트라이의 차이가 작다는 것이다. 집합 풀이는 단어마다 길이 2부터 100까지 99번 잘라 해시하니 글자로 약 5,000개를 다루고, 트라이는 100글자만 내려간다. 이론으로는 50배 차이인데 실제로는 두 배 안팎이다. 문자열 자르기와 해시가 엔진 안에서 아주 빠르게 돌고, 트라이는 노드 사이를 포인터로 건너뛰느라 메모리 접근이 흩어지기 때문이다. Python에서는 둘이 거의 같았다. 어근 길이 상한이 100이라 집합 풀이의 제곱 항이 커질 수 없다는 조건이 여기서 효과를 낸다.

그래서 이 문제에서는 해시 집합 풀이도 충분히 좋은 답이다. 면접에서 트라이를 기본 답으로 내는 이유는 속도보다 구조다. 처음 만나는 끝 표시가 곧 가장 짧은 어근이라 정렬이나 길이 비교가 필요 없고, 어근 길이에 상한이 없어도 O(문장 길이)가 유지되며, 글자 하나씩 진행되니 스트리밍으로 바꾸기 쉽다.

## 다섯 풀이를 나란히 놓으면

N은 단어 수, D는 어근 수, R은 어근 최대 길이, S는 문장 길이다.

| 풀이 | 시간 | 추가 공간 | 언제 고르나 |
|---|---|---|---|
| 단어마다 전부 맞추기 | O(N · D · R) | O(S) | 어근이 몇 개뿐일 때 |
| 짧은 어근부터 정렬 | O(D log D + N · D · R) | O(D + S) | 대부분의 단어가 짧은 어근과 맞을 때 |
| 앞부분 잘라 집합에 묻기 | O(D · R + N · R²) | O(D · R + S) | 어근 길이 상한이 작을 때. 트라이 없이 짧게 짤 때 |
| 트라이 | O(D · R + S) | O(D · R + S) | 기본 답 |
| 트라이 + 한 번 훑기 | O(D · R + S) | O(D · R) + 출력 | 문장이 스트림으로 들어올 때, 메모리가 빠듯할 때 |

## 끝까지 내려가거나 처음 것을 놓친다

가장 흔한 실수는 끝 표시를 만나도 멈추지 않고, 마지막으로 만난 끝 표시를 답으로 쓰는 것이다.

```js
const shorten = (word) => {
  let node = root, last = -1;
  for (let i = 0; i < word.length; i++) {
    node = node.children[word.charCodeAt(i) - 97];
    if (node === null) break;
    if (node.isEnd) last = i + 1; // 멈추지 않고 계속 갱신한다
  }
  return last === -1 ? word : word.slice(0, last);
};
// dictionary [sun, su], "sunny" -> "sun" (정답은 su)
```

이 코드는 가장 긴 어근을 찾는다. `sun`이 먼저 들어가서 `n` 노드가 있으면 `su`를 지나 `sun`까지 간다. 문제는 가장 짧은 어근을 원한다. 넣을 때 "짧은 어근을 지나면 멈춘다"를 넣어 두면 이 실수를 해도 우연히 맞는 경우가 있어서 더 찾기 어렵다. 위 테스트의 "긴 어근이 목록 앞에 있어도"가 이걸 잡는다.

두 번째는 `startsWith`의 방향을 거꾸로 쓰는 것이다. "단어가 어근으로 시작하나"를 물어야 하는데 "어근이 단어로 시작하나"를 묻는다.

```js
// 단어와 어근의 자리가 바뀌었다
const shorten = (word) => dictionary.find((root) => root.startsWith(word)) ?? word;
// dictionary [cat], "ca cattle" -> "cat cattle" (정답은 "ca cat")
```

`ca`는 어근 `cat`보다 짧은데 `cat`으로 늘어났고, 정작 `cattle`은 줄어들지 않았다. `a.startsWith(b)`는 "a가 b로 시작하나"라서, 읽을 때 주어와 목적어를 헷갈리기 쉽다. `indexOf(...) === 0`으로 바꿔 쓸 때도 자리가 자주 뒤집힌다. 위 테스트의 "어근이 단어보다 길다"가 이걸 잡는다.

그 밖에 이 문제에서 조심할 것들이다.

- 결과를 문자열 `+=`로 이어 붙이는 코드는 JS와 Python에서는 엔진이 최적화해 대개 괜찮지만, Java에서는 문장 길이 제곱이 될 수 있다. `StringBuilder`나 `join`을 쓴다.
- 트라이를 만들 때 끝 표시만 보고 멈추는 최적화를 넣었다면, 같은 트라이를 다른 질문(예: 가장 긴 어근)에 다시 쓰지 않는다. 긴 어근이 빠져 있다.
- 어근 목록에 같은 어근이 두 번 들어와도 트라이와 집합 풀이는 문제없다. 같은 길을 다시 걷고 같은 표시를 다시 붙일 뿐이다.

## 면접관이 이어서 묻는 것

### 가장 긴 어근으로 바꾸라면

내려가다 끝 표시를 만나도 멈추지 않고, 마지막으로 만난 위치를 기억해 두었다가 자식이 끊기면 그 위치를 쓴다. 위의 "실수" 코드가 바로 그 답이다. 넣을 때 짧은 어근에서 멈추는 최적화는 빼야 한다. 네트워크 라우팅의 최장 접두사 일치(longest prefix match)가 이 모양이다. 라우터는 목적지 IP의 비트를 트라이로 내려가며 가장 긴 접두사를 가진 경로를 고른다.

### 어근이 단어 중간이나 끝에 와도 된다면

접미사를 찾는 문제라면 어근과 단어를 모두 뒤집어서 같은 트라이를 쓰면 된다. 단어 중간 어디에서든 찾는 문제라면 시작 위치마다 트라이를 내려가거나, 여러 패턴을 한 번에 찾는 아호-코라식(Aho-Corasick) 자동자를 쓴다. 트라이에 "실패하면 어디로 돌아갈지"를 미리 이어 둔 구조다. [Index Pairs of a String](/posts/leetcode-index-pairs-of-a-string)(1065, 프리미엄 문제)이 시작 위치마다 내려가는 쪽이다.

### 어근 목록이 자주 바뀐다면

트라이는 넣기가 O(R)이라 어근이 추가되어도 다시 만들 필요가 없다. 삭제가 필요하면 끝 표시를 떼고 빈 가지를 정리한다([트라이 글](/posts/ds-trie)). 다만 넣을 때 "짧은 어근에서 멈추기" 최적화를 넣었다면, 짧은 어근을 지울 때 그 아래에 있어야 할 긴 어근이 없어서 결과가 틀린다. 삭제가 있는 상황에서는 이 최적화를 빼고 모든 어근을 온전히 넣는다.

### 문장이 끝없이 들어오는 스트림이라면

위의 한 번 훑기 풀이가 답이다. 상태가 트라이 노드 하나와 플래그 하나라서, 글자가 들어오는 대로 처리하고 바로 내보낼 수 있다. 단어 경계가 청크 사이에 걸쳐도 상태가 이어지니 문제없다.

### 대문자나 다른 언어 글자가 섞인다면

26칸 배열은 `charCodeAt - 97`이 0~25를 벗어나는 순간 쓸 수 없다. 자식을 `Map`(Python은 딕셔너리)으로 바꾸면 글자 종류와 상관없이 같은 코드가 돈다. 대소문자를 구분하지 않아야 한다면 트라이를 만들 때와 내려갈 때 모두 소문자로 바꿔서 내려가되, 결과에는 원래 단어의 앞부분을 잘라 쓴다. 이모지처럼 글자 하나가 UTF-16 코드 단위 두 개로 된 문자를 다룬다면 `for...of`로 코드 포인트 단위로 읽어야 글자가 반으로 갈리지 않는다.

### 어근이 수백만 개로 아주 많다면

노드마다 26칸을 들면 메모리가 먼저 터진다. 자식을 `Map`으로 들거나, 자식이 하나인 사슬을 한 노드로 합친 압축 트라이로 바꾼다. 어근 목록이 고정이라면 정렬된 배열에 두고 단어의 앞부분마다 이진 탐색으로 묻는 방법도 있다. 메모리는 어근 글자 수만큼만 들고, 앞부분 하나에 O(R log D)다. [Implement Trie](/posts/leetcode-implement-trie)에서 잰 것처럼 트라이는 생각보다 무겁다.

## 처음 만나는 끝 표시가 답이다

단어마다 어근을 다 맞추면 어근 수에 비례해 느려진다. 앞부분을 짧은 것부터 잘라 집합에 묻으면 어근 수가 식에서 빠지고, 어근 길이가 100으로 묶인 이 문제에서는 실제로 트라이만큼 빠르다. 트라이는 같은 일을 한 글자에 한 칸씩 이어서 하고, 위에서부터 내려가니 처음 만나는 끝 표시가 곧 가장 짧은 어근이다. 거기서 멈추는 것이 이 문제의 전부이고, 멈추지 않고 끝까지 가면 가장 긴 어근을 찾는 다른 문제가 된다.

## 면접에서 나올 만한 질문

### 트라이에서 처음 만난 끝 표시에서 멈춰도 되는 이유는요?

트라이를 뿌리에서 한 글자씩 내려가니, 지나는 노드의 깊이가 곧 접두사 길이다. 처음 만나는 끝 표시는 그 단어의 접두사인 어근 중 가장 짧은 것이다. 더 긴 어근은 그 아래 깊은 곳에 있으니 볼 필요가 없다. 그래서 정렬이나 길이 비교 없이 내려가는 순서만으로 답이 정해진다.

### 해시 집합으로 풀면 어떻게 되고, 트라이보다 느린가요?

단어의 앞부분을 짧은 것부터 잘라 집합에 묻고, 처음 있는 것을 답으로 쓴다. 단어마다 최악 1 + 2 + ... + R글자를 해시하니 O(N · R²)이다. 이론상으로는 트라이의 O(S)보다 나쁘지만, 이 문제는 R이 100 이하라 실제로 재 보면 거의 차이가 없었다. 어근 길이 상한이 없거나 문장을 스트리밍해야 하면 트라이가 낫다.

### 시간과 공간 복잡도는요?

트라이를 만드는 데 어근 글자 수 합 O(D · R), 문장을 처리하는 데 O(S)다. 단어마다 많아야 min(단어 길이, R)글자만 내려가니 문장 길이를 넘지 않는다. 공간은 트라이 노드 O(D · R)에 결과 문자열이다. 26칸 배열 노드라면 노드마다 26칸이 붙는다.

### 트라이를 만들 때 더 짧은 어근을 지나면 멈추는 이유는요?

그 아래에 넣을 긴 어근은 어떤 단어에서도 쓰일 일이 없기 때문이다. 단어를 줄일 때 짧은 어근의 끝 표시에서 항상 먼저 멈춘다. 그래서 노드를 아낄 수 있다. 다만 어근을 지우거나 가장 긴 어근을 찾는 변형이 생기면 긴 어근이 필요하니 이 최적화를 빼야 한다.

### 가장 긴 어근으로 바꾸라면 무엇을 바꾸나요?

끝 표시를 만나도 멈추지 않고 위치만 기억해 둔 채 계속 내려간다. 자식이 끊기거나 단어가 끝나면 마지막으로 기억한 위치까지 자른다. 넣을 때 짧은 어근에서 멈추는 최적화는 뺀다. 라우터의 최장 접두사 일치가 같은 모양이다.

### 이 풀이가 틀리는 입력을 하나 들어 보세요.

끝 표시를 만나도 멈추지 않는 코드라면 `[sun, su]`와 `sunny`에서 `su`가 아니라 `sun`을 낸다. `startsWith`의 방향을 거꾸로 쓴 코드라면 `[cat]`과 `ca cattle`에서 `cat cattle`을 낸다. 단어가 어근보다 짧은 경우, 긴 어근이 목록 앞에 있는 경우, 맞는 어근이 없는 경우를 테스트에 꼭 넣는다.

### 문장이 100만 글자인데 메모리를 아끼려면요?

`split`으로 단어 배열을 만들지 않고 문장을 한 글자씩 읽는다. 들고 다닐 상태는 지금 트라이 노드와 "어근을 찾아서 남은 글자를 버리는 중"이라는 플래그 두 개뿐이다. 공백에서 상태를 처음으로 돌린다. 결과를 바로 내보내면 추가 메모리는 트라이뿐이고, 입력이 스트림으로 들어와도 그대로 쓸 수 있다.
