페이지 하나에 스크립트 두 개를 붙였다. 장바구니 위젯(`cart.js`)과 알림 위젯(`notice.js`)이다. 각자 따로 만들 때는 잘 돌았는데, 같이 붙이고 장바구니 담기 버튼을 누르니 알림 숫자가 올라간다. 에러도 없다.

```js
// cart.js
var count = 0;
function render() { console.log("cart: " + count + "개"); }
function add() { count += 1; render(); }

// notice.js
var count = 0;
function render() { console.log("notice: 안 읽은 알림 " + count + "개"); }
```

두 파일을 Node의 `vm`으로 같은 전역에서 차례로 돌리고, 버튼 클릭 대신 `add()`를 두 번 불렀다. 브라우저에서 `<script>` 태그 두 개를 붙인 것과 같은 상황이다.

```text
notice: 안 읽은 알림 1개
notice: 안 읽은 알림 2개
```

클래식 스크립트(모듈이 아닌 `<script>`)의 최상위 `var`와 함수 선언은 전부 전역 객체에 붙는다. 파일이 달라도 전역은 하나다. 그래서 `notice.js`가 `count`와 `render`를 덮어썼고, `cart.js`의 `add`는 이름으로 찾다 보니 알림 쪽 `render`를 불렀다.

이 글은 모듈 시스템이 없던 시절 이 문제를 푼 방법인 IIFE(즉시 실행 함수)와 모듈 패턴을 따라간다. 지금 쓰는 코드에 왜 아직 그 흔적이 남아 있는지, 번들러 출력과 React 코드에서 어디에 보이는지도 함께 본다. 출력은 Node.js 22와 크로미움에서 실제로 돌린 결과다.

이 주제의 다른 글: 함수가 태어난 자리의 변수를 기억하는 원리는 [클로저](/posts/js-closures)에서, `var`가 블록을 무시하는 이유는 [var, let, const](/posts/js-var-let-const)에서 먼저 다뤘다. 이 글은 그 둘을 엮어 "파일 하나를 상자에 가두는 법"에 집중한다.

## 만들자마자 부르는 함수

해결책은 함수 스코프를 빌리는 것이다. ES5까지 자바스크립트에서 새 스코프를 만드는 방법은 사실상 함수뿐이었다(`let`과 `const`의 블록 스코프는 ES2015부터다). 그래서 파일 전체를 함수 하나로 감싸고, 그 함수를 바로 불렀다.

```js
// cart.js
var Cart = (function () {
  var count = 0;
  function render() { console.log("cart: " + count + "개"); }
  function add() { count += 1; render(); }
  return { add: add };
})();

// notice.js
var Notice = (function () {
  var count = 0;
  function render() { console.log("notice: 안 읽은 알림 " + count + "개"); }
  return { render: render };
})();

Cart.add(); Cart.add(); Notice.render();
console.log(typeof count, typeof render, Object.keys(Cart));
```

```text
cart: 1개
cart: 2개
notice: 안 읽은 알림 0개
undefined undefined [ 'add' ]
```

이제 전역에 붙는 이름은 `Cart`와 `Notice` 두 개뿐이다. `count`와 `render`는 각 함수 호출의 Environment Record(변수를 담는 상자) 안에 있어서 전역에서는 `undefined`다. 함수는 실행을 마쳤지만 돌려준 `add`가 그 상자를 계속 잡고 있으니 `count`도 살아 있다. 이게 클로저다.

이렇게 정의하자마자 실행하는 함수 표현식을 IIFE(Immediately Invoked Function Expression)라고 부른다. 하는 일은 셋이다. 이름이 바깥으로 새지 않게 막고, 초기화 코드를 한 번만 돌리고, 필요하면 결과를 값으로 돌려준다.

jQuery 플러그인 시절에 흔하던 모양을 조각으로 나눠 보자. 아래 그림에서 조각을 누르면 각 부분이 무슨 일을 하는지 나온다.

## 괄호를 빼면 문법 에러가 난다

괄호가 왜 필요한지는 빼 보면 안다.

```js
function () { console.log("hi"); }()      // 1
function init() { console.log("hi"); }()  // 2
```

```text
SyntaxError: Function statements require a function name
SyntaxError: Unexpected token ')'
```

문장 맨 앞에 `function`이 오면 파서는 함수 선언문으로 읽는다. 1은 선언문인데 이름이 없어서 에러다. 2는 선언문 자체는 맞지만, 뒤의 `()`가 호출이 아니라 비어 있는 괄호 식으로 읽혀서 에러다. 선언문은 값이 아니라서 바로 부를 수 없다.

그래서 `function` 앞에 뭔가를 둬서 파서가 표현식 자리로 읽게 만든다. 방법이 여러 가지다.

```js
(function () { console.log("A 괄호로 감싼다"); })();
(function () { console.log("B 호출까지 감싼다"); }());
!function () { console.log("C 단항 연산자"); }();
void function () { console.log("D void"); }();
(() => { console.log("E 화살표"); })();
const r = (function () { return 42; })();
console.log(r);
```

```text
A 괄호로 감싼다
B 호출까지 감싼다
C 단항 연산자
D void
E 화살표
42
```

동작은 모두 같다. A와 B는 취향 차이고, 압축된 라이브러리에서 `!function(){}()`이 자주 보이는 건 한 글자를 아끼기 때문이다. `!`는 반환값을 뒤집으니 값을 받아 쓸 때는 쓰지 않는다. 화살표 함수는 반드시 A처럼 함수만 괄호로 감싸야 한다. `(() => {}())`는 문법 에러다. 마지막 줄처럼 `=` 오른쪽은 이미 표현식 자리라서 괄호가 없어도 되지만, 읽는 사람이 "이건 함수가 아니라 실행 결과다"를 바로 알게 감싸 두는 게 관례다.

## 세미콜론 하나가 빠졌을 때

IIFE가 괄호로 시작한다는 점이 함정이 되기도 한다. 자바스크립트는 줄 끝에 세미콜론이 없으면 자동으로 넣어 주는데(ASI, 자동 세미콜론 삽입), 다음 줄이 `(`로 시작하면 넣지 않는다. 앞 줄과 이어서 읽는다.

```js
const config = { debug: true }
(function () {
  console.log("초기화");
})()
```

```text
(function () {
^

TypeError: {(intermediate value)} is not a function
```

엔진은 이걸 `{ debug: true }(function () {...})()`로 읽었다. 객체를 함수처럼 부르려 해서 에러가 났다. 앞 줄이 함수라면 더 헷갈린다.

```js
const log = function () { console.log("log 호출됨"); }
(function () {
  console.log("초기화");
})()
```

```text
log 호출됨
})()
  ^

TypeError: (intermediate value)(...) is not a function
```

"log 호출됨"이 찍혔다. 앞 줄의 함수 표현식이 IIFE를 인자로 받아 바로 불렸고, 그 반환값 `undefined`를 다시 부르려다 터졌다. 정작 "초기화"는 한 번도 안 돌았다. 이 에러는 파일을 이어 붙이는 빌드에서 앞 파일의 마지막 줄 때문에 생기기도 해서, 에러 위치가 뒤 파일 첫 줄로 찍힌다. 앞 파일을 의심해야 한다.

## 숨기고 골라서 내보내는 모듈 패턴

IIFE가 객체를 돌려주게 만들면 "공개할 것만 고른 모듈"이 된다. 이걸 모듈 패턴이라고 부른다. 안쪽 함수 중 무엇을 반환 객체에 넣을지가 곧 공개 API다.

```js
var Cart = (function () {
  var items = [];                       // 비공개
  function total() { /* ... */ }        // 공개
  function validate(item) { /* ... */ } // 비공개 도우미
  function add(item) { validate(item); items.push(item); return total(); }
  return { add: add, total: total };    // 고른 것만 내보낸다
})();
```

함수를 안에서 이름으로 다 정의하고 마지막에 이름만 골라 내보내는 이 모양은 따로 revealing module 패턴이라고 부르기도 한다. 어떤 함수가 공개인지 맨 아래만 보면 알 수 있어서 많이 쓰였다.

## 공개한 값은 따라오지 않는다

모듈 패턴에서 흔히 하는 실수 두 가지가 있다. 둘 다 "반환한 객체에 무엇이 들어갔나"를 착각해서 생긴다.

```js
const Cart = (function () {
  let items = [];
  function add(item) { items.push(item); return total(); }
  function total() { return items.reduce((s, i) => s + i.price, 0); }
  return { add, total, items, count: items.length };
})();
Cart.add({ name: "펜", price: 1000 });
Cart.add({ name: "공책", price: 3000 });
console.log("total:", Cart.total());
console.log("count:", Cart.count);
console.log("items:", Cart.items.length);
Cart.items.length = 0;           // 밖에서 배열을 비웠다
console.log("total after:", Cart.total());
```

```text
total: 4000
count: 0
items: 2
total after: 0
```

`count: items.length`는 IIFE가 실행되던 순간의 숫자 0을 복사해 둔 것이다. 원시값은 값이 복사되니 나중에 상품을 넣어도 따라오지 않는다. 반대로 `items`는 배열 참조를 내보냈다. 비공개로 숨겼다고 생각한 배열을 바깥에서 `length = 0`으로 비울 수 있다. 값과 참조가 이렇게 다르게 움직이는 이유는 [원시값과 참조](/posts/js-primitive-vs-reference)에서 다뤘다.

고치는 방법은 상태 대신 상태를 읽는 함수를 내보내는 것이다. `count() { return items.length; }`, `list() { return items.slice(); }`처럼 복사본을 돌려주면 바깥에서 원본을 건드릴 수 없다.

두 번째는 revealing 패턴 특유의 문제다. 공개 메서드를 바깥에서 갈아 끼워도 안쪽 호출은 바뀌지 않는다.

```js
const Price = (function () {
  function format(n) { return n.toLocaleString("ko-KR") + "원"; }
  function label(n) { return "가격: " + format(n); }
  return { format, label };
})();
Price.format = (n) => "$" + (n / 1300).toFixed(2); // 다른 팀이 덮어썼다
console.log(Price.format(13000));
console.log(Price.label(13000));
```

```text
$10.00
가격: 13,000원
```

`label` 안의 `format`은 객체 속성이 아니라 클로저 안의 지역 함수를 가리킨다. 그래서 `Price.format`을 바꿔도 `label`은 옛 함수를 쓴다. 테스트에서 공개 메서드를 스텁(가짜 함수)으로 바꿨는데 내부 호출이 계속 진짜를 부르는 일이 이렇게 생긴다. 안쪽에서도 `api.format(n)`처럼 공개 객체를 거쳐 부르게 하면 갈아 끼운 게 반영된다(`가격: $10.00`). 반대로 외부에서 내부 동작을 못 바꾸게 막고 싶다면 지금 모양이 장점이 된다. 어느 쪽을 원하는지 정하고 쓰면 된다.

## 반복문마다 새 상자가 필요했던 시절

IIFE가 가장 많이 쓰인 곳 중 하나는 `var` 반복문이다. `var`는 블록을 무시하고 함수 단위로 변수 하나만 만든다. 그래서 반복문 안에서 만든 함수들이 모두 같은 `i`를 본다.

```js
var fns = [];
for (var i = 0; i < 3; i++) {
  fns.push(function () { return i; });
}
console.log(fns.map(function (f) { return f(); }));

var fixed = [];
for (var j = 0; j < 3; j++) {
  (function (k) {
    fixed.push(function () { return k; });
  })(j);
}
console.log(fixed.map(function (f) { return f(); }));
```

```text
[ 3, 3, 3 ]
[ 0, 1, 2 ]
```

두 번째 반복문은 매 회차 IIFE를 부른다. 호출마다 새 상자가 생기고, 그 순간의 `j`가 매개변수 `k`로 복사돼 들어간다. 안에서 만든 함수는 자기 회차의 상자를 잡는다.

## 파일 여러 개를 하나의 이름 아래 모으기

위젯이 늘면 전역 이름도 늘어난다. 그래서 전역 이름을 하나만 두고 그 아래에 모듈을 붙이는 네임스페이스 방식이 나왔다. 다른 모듈이 필요하면 IIFE의 인자로 받았다.

```js
// a.js
var App = App || {};
App.cart = (function () {
  var items = [];
  return { add: function (x) { items.push(x); return items.length; } };
})();

// b.js (나중에 로드)
var App = App || {};
App.coupon = (function (cart) {
  return { apply: function (code) { return code + " 적용, 장바구니 " + cart.add("쿠폰상품") + "개"; } };
})(App.cart);

console.log(Object.keys(App));
console.log(App.coupon.apply("WELCOME"));
```

```text
[ 'cart', 'coupon' ]
WELCOME 적용, 장바구니 1개
```

`var App = App || {}`는 "이미 누가 만들었으면 그걸 쓰고 아니면 새로 만든다"는 뜻이다. 어느 파일이 먼저 와도 `App`이 덮어써지지 않는다. 그런데 의존성은 여전히 순서에 묶여 있다. 같은 코드에서 `b.js`가 먼저 로드되면 이렇게 된다.

```text
function
TypeError: Cannot read properties of undefined (reading 'add')
```

`App.cart.add`는 나중에 멀쩡히 생겼다(`function`). 하지만 `b.js`의 IIFE가 실행되던 순간 `App.cart`는 `undefined`였고, 그 값이 `cart` 매개변수로 굳어 버렸다. 에러는 로드할 때가 아니라 쿠폰을 적용할 때 난다. 아래 그림에서 다음을 누르면 순서가 바뀐 경우를 따라간다.

## 어디서나 돌아가는 래퍼, UMD

라이브러리 작성자는 한 파일로 AMD, CommonJS(Node), 브라우저 전역을 모두 지원하고 싶었다. 그래서 IIFE에 "지금 환경에 무엇이 있나"를 묻는 분기를 넣었다. UMD(Universal Module Definition)다.

```js
(function (root, factory) {
  if (typeof define === "function" && define.amd) define([], factory);
  else if (typeof module === "object" && module.exports) module.exports = factory();
  else root.Slugify = factory();
})(typeof self !== "undefined" ? self : this, function () {
  return function slugify(s) { return s.trim().toLowerCase().replace(/\s+/g, "-"); };
});
```

같은 파일을 Node에서 `require`로 읽고, 다시 `vm`으로 브라우저 전역처럼 만든 환경에서 스크립트로 돌렸다.

```text
CommonJS: hello-world
전역 스크립트: iife-module-pattern
```

바깥 IIFE가 환경을 고르고, 안쪽 `factory`가 진짜 모듈이다. npm 패키지의 `dist/*.umd.js` 파일이 이 모양이다. 오래된 페이지에 `<script>`로 라이브러리를 붙이면 `window.라이브러리이름`이 생기는 이유가 마지막 분기다.

## 지금은 모듈 시스템이 같은 일을 한다

모듈 패턴이 손으로 하던 일을 지금은 언어와 런타임이 한다. 먼저 Node의 CommonJS는 내부적으로 진짜 함수로 파일을 감싼다.

```js
// cjs1.cjs
var x = 1;
console.log("CommonJS 파일:", globalThis.x, typeof module, arguments.length);
```

```text
CommonJS 파일: undefined object 5
```

최상위 `var`가 전역에 붙지 않았고, 최상위에서 `arguments`가 있다. Node가 파일을 `function (exports, require, module, __filename, __dirname) { ... }`로 감싸 부르기 때문이다. 인자 다섯 개가 그것이다. CommonJS 모듈 하나가 곧 IIFE 하나인 셈이다.

ES 모듈은 함수로 감싸지 않고 명세에 모듈 스코프가 따로 있다.

```js
// esm1.mjs
var x = 1;
console.log("ES 모듈 파일:", globalThis.x, this);
```

```text
ES 모듈 파일: undefined undefined
```

최상위 `this`도 `undefined`다. ES 모듈은 자동으로 strict mode이고, 몇 번을 import해도 한 번만 평가되며, 의존 관계를 정적으로 분석해서 순서를 엔진이 정한다. 앞에서 본 이름 충돌, 순서 의존, 세미콜론 문제가 모두 사라진다. named/default export와 live binding 이야기는 [ES 모듈](/posts/js-es-modules)에서 이어 간다.

그래도 IIFE가 사라진 건 아니다. 번들러가 결과물을 만들 때 다시 꺼낸다. 아래 두 파일을 esbuild 0.24로 묶었다.

```js
// eb/cart.js
let count = 0;
export function add() { count += 1; return count; }

// eb/main.js
import { add } from "./cart.js";
export const version = "1.0.0";
console.log("added", add());
```

```bash
# 브라우저에 <script>로 붙일 한 파일로 묶는다. 공개 객체 이름은 MyWidget
npx esbuild eb/main.js --bundle --format=iife --global-name=MyWidget
```

```text
var MyWidget = (() => {
  var __defProp = Object.defineProperty;
  ...
  // eb/main.js
  var main_exports = {};
  __export(main_exports, {
    version: () => version
  });

  // eb/cart.js
  var count = 0;
  function add() {
    count += 1;
    return count;
  }

  // eb/main.js
  var version = "1.0.0";
  console.log("added", add());
  return __toCommonJS(main_exports);
})();
```

(중간의 도우미 함수 몇 줄은 줄였다.) 모듈 패턴 그대로다. 파일 두 개가 화살표 IIFE 하나 안에 펼쳐졌고, `let count`는 `var count`로 바뀌었다. 바깥 함수가 스코프를 만들어 주니 블록 스코프가 필요 없어서다. export한 `version`만 반환 객체로 나가고 `add`와 `count`는 숨는다. 광고 태그, 채팅 위젯, 분석 스크립트처럼 남의 페이지에 붙는 코드는 지금도 이 형식으로 배포한다. 남의 전역을 더럽히지 않아야 하기 때문이다.

## React 코드에 남은 즉시 실행 함수

React 코드에서 IIFE를 가장 자주 만나는 곳은 effect 안의 비동기 코드다. effect 함수에 바로 `async`를 붙이면 이렇게 된다.

```jsx
useEffect(async () => {
  const u = await fetchUser(id);
  setUser(u);
}, [id]);
```

React 19.3 개발 빌드는 크로미움 콘솔에 이런 경고를 낸다(앞부분).

```text
useEffect must not return anything besides a function, which is used for clean-up.

It looks like you wrote useEffect(async () => ...) or returned a Promise. Instead, write the async function inside your effect and call it immediately:
```

async 함수는 항상 Promise를 반환한다. React는 effect가 돌려준 값을 정리 함수로 보고 나중에 부르는데, Promise는 함수가 아니다. 프로덕션 빌드에서 `id`를 한 번 바꾸고 컴포넌트를 없애 보니, 경고 대신 그때마다 에러가 났다.

```text
TypeError: destroy_ is not a function
TypeError: destroy_ is not a function
```

경고 문구가 말하는 대로 async 함수를 effect 안에서 만들고 바로 부른다. 이름을 붙여 부르든 IIFE로 부르든 같다.

```jsx
useEffect(() => {
  let ignore = false;
  (async () => {
    const u = await fetchUser(id);
    if (!ignore) setUser(u);
  })();
  return () => { ignore = true; };
}, [id]);
```

effect 자체는 동기 함수로 남고, 정리 함수도 제대로 돌려줄 수 있다. `ignore` 플래그는 `id`가 빨리 바뀌었을 때 늦게 도착한 옛 응답이 화면을 덮지 않게 막는다. 요청 자체를 끊는 방법은 [AbortController](/posts/abort-controller)에서 다룬다. JSX 안에서 조건이 복잡할 때 `{(() => { if (...) return <A />; return <B />; })()}`처럼 IIFE를 쓰는 코드도 가끔 보이는데, 읽기 어려우니 변수나 작은 컴포넌트로 빼는 편이 낫다.

## 모듈 변수는 프로세스에 하나다

모듈 패턴의 상태는 모듈이 한 번만 평가되니 하나뿐이다. 브라우저에서는 탭 하나에 사용자 한 명이라 대개 괜찮다. 서버에서는 다르다. Node 프로세스 하나가 여러 사용자의 요청을 동시에 처리하는데, 모듈 변수는 그 모두가 같이 쓴다.

```js
// session.js
let currentUser = null;
exports.setUser = (u) => { currentUser = u; };
exports.getUser = () => currentUser;

// server.js
const server = http.createServer(async (req, res) => {
  const user = new URL(req.url, "http://x").searchParams.get("user");
  session.setUser(user);
  await wait(user === "alice" ? 100 : 10); // DB 조회를 흉내 낸다
  res.end(`hello ${session.getUser()}\n`);
});
// alice와 bob의 요청을 동시에 보낸다
```

```text
alice 요청 → hello bob
bob 요청   → hello bob
```

alice의 요청이 `await`에서 기다리는 사이 bob의 요청이 `currentUser`를 덮었다. alice는 bob의 화면을 받았다. 개발할 때 혼자 눌러 보면 절대 안 보이고, 사용자가 몰릴 때만 생긴다. Next.js 서버 컴포넌트나 API 라우트에서 모듈 최상단에 요청별 값을 두면 같은 일이 생긴다. 기본값 객체를 고쳐 쓰다 요청끼리 섞이는 비슷한 사례는 [원시값과 참조](/posts/js-primitive-vs-reference)에도 있다.

요청별 값은 인자로 넘기거나, 요청마다 따로 보이는 저장소를 쓴다. Node의 `AsyncLocalStorage`가 그 도구다.

```js
const als = new AsyncLocalStorage(); // 요청마다 따로 보이는 저장소
const getUser = () => als.getStore().user;
const server = http.createServer((req, res) => {
  const user = new URL(req.url, "http://x").searchParams.get("user");
  als.run({ user }, async () => {
    await wait(user === "alice" ? 100 : 10);
    res.end(`hello ${getUser()}\n`);
  });
});
```

```text
alice 요청 → hello alice
bob 요청   → hello bob
```

같은 이유로 모듈 패턴으로 만든 객체는 사실상 싱글턴이다. 테스트끼리 상태가 남아 서로 영향을 주고, 하나 더 만들 방법이 없다. 여러 개가 필요해질 수 있다면 IIFE 대신 팩토리 함수(`createCart()`)로 두고 필요한 곳에서 만든다. 싱글턴을 언제 쓰고 언제 피하는지는 [싱글턴 패턴](/posts/pattern-singleton)에서 다뤘다.

## 연습: 작은 모듈 로더

AMD 로더의 핵심을 만들어 보자. `define`은 모듈을 등록만 하고, `require`는 의존 모듈을 먼저 실행해 factory에 넘긴 뒤 결과를 기억한다. 등록 순서가 거꾸로여도 돌아가야 하고, 같은 모듈은 한 번만 실행해야 한다. 앞에서 본 순서 문제와 "한 번만 평가된다"는 성질을 직접 구현하는 셈이다.

    { label: "없는 모듈은 이름을 알려 준다", args: [["api", "logger"], "api"], expected: { error: "모듈 없음: config", evals: [] } },
  ]}
/>

`api`는 `logger`와 `config`를 둘 다 받는데, `config`는 `logger`가 이미 불러 둔 것을 캐시에서 꺼낸다. 그래서 `evals`에 한 번만 찍힌다. 이 풀이는 순환 의존(a가 b를, b가 a를 요구)이 있으면 끝없이 재귀한다. 실제 로더와 ES 모듈은 평가 중인 모듈을 표시해 두고 덜 만들어진 값을 먼저 넘기는 식으로 이 경우를 처리한다.

## 두 위젯이 다시 따로 세기까지

처음 장바구니 버튼이 알림 숫자를 올린 건 파일마다 스코프가 따로 있다고 착각해서였다. 클래식 스크립트에서 파일은 경계가 아니다. IIFE는 함수 호출 하나로 그 경계를 만들고, 돌려준 객체가 공개 API가 된다. 지금은 ES 모듈과 번들러가 같은 일을 대신하지만, 번들 결과물, UMD 파일, effect 안의 async 호출, 서버의 모듈 변수에서 이 구조를 그대로 다시 만난다. 모듈 상태는 하나뿐이라는 것만 기억해도 서버에서 사용자끼리 값이 섞이는 버그를 피할 수 있다.

## 면접에서 나올 만한 질문

### IIFE는 무엇이고 왜 썼나요?

정의하자마자 바로 실행하는 함수 표현식이다. ES5까지는 블록 스코프가 없어서 새 스코프를 만드는 방법이 함수뿐이었고, 클래식 스크립트의 최상위 변수는 전부 전역에 붙었다. 그래서 파일 전체를 함수로 감싸 바로 불러 이름이 전역으로 새지 않게 하고, 초기화 코드를 한 번만 실행했다.

### `function(){}()`는 왜 문법 에러인가요?

문장 맨 앞의 `function`은 함수 선언문으로 읽히는데, 선언문은 값이 아니라서 바로 호출할 수 없기 때문이다. 이름이 없으면 "이름이 필요하다"는 에러가 나고, 이름이 있으면 뒤의 `()`가 빈 괄호 식으로 읽혀 에러가 난다. 괄호로 감싸거나 `!`, `void`를 앞에 붙여 파서가 표현식으로 읽게 만들면 된다.

### 모듈 패턴은 어떻게 private을 만드나요?

IIFE 안에 변수와 함수를 두고, 공개할 것만 객체에 담아 반환한다. 반환된 함수들은 클로저로 IIFE의 환경을 계속 잡고 있어서 내부 변수에 접근하지만, 바깥에는 그 변수로 가는 이름이 없다. 단, 배열이나 객체를 그대로 반환하면 참조가 나가서 바깥에서 고칠 수 있고, 원시값을 반환하면 그 순간의 복사본이라 갱신되지 않으니 접근 함수를 내보내야 한다.

### revealing module 패턴의 단점은 무엇인가요?

내부 함수끼리는 객체 속성이 아니라 지역 이름으로 서로를 부르기 때문에, 공개 메서드를 바깥에서 바꿔도 내부 호출에는 반영되지 않는다. 테스트에서 메서드를 스텁으로 바꿨는데 다른 공개 메서드가 여전히 진짜를 부르는 문제가 생긴다. 외부 수정을 막는 장점이기도 해서, 갈아 끼울 수 있어야 한다면 내부에서도 공개 객체를 거쳐 호출한다.

### 세미콜론 없는 코드에서 IIFE가 왜 위험한가요?

다음 줄이 `(`로 시작하면 자동 세미콜론 삽입이 일어나지 않아 앞 줄과 이어서 해석되기 때문이다. 앞 줄이 함수 표현식이면 IIFE를 인자로 받아 그 함수가 실행되고, 반환값을 다시 호출하다 `is not a function` 에러가 난다. 에러 위치가 뒤 줄로 찍혀서 원인 찾기가 어렵고, 그래서 `;(function(){})()`처럼 앞에 세미콜론을 붙이거나 포매터에 맡긴다.

### ES 모듈이 있는데 IIFE는 이제 필요 없나요?

직접 쓸 일은 줄었지만 형태는 계속 남아 있다. ES 모듈은 언어 차원의 모듈 스코프, strict mode, 한 번만 평가, 정적 의존성 분석을 주니 이름 충돌과 순서 문제를 IIFE 없이 푼다. 하지만 번들러의 `iife` 출력이나 UMD처럼 `<script>`로 붙이는 배포물, CommonJS의 모듈 래퍼, effect 안에서 async 함수를 바로 부르는 코드에서는 여전히 IIFE를 쓴다.

### `useEffect(async () => ...)`는 왜 안 되나요?

async 함수는 항상 Promise를 반환하는데, React는 effect의 반환값을 정리 함수로 보고 나중에 호출하기 때문이다. 개발 빌드는 경고를 내고, 프로덕션에서는 정리 시점에 함수가 아니라는 에러가 날 수 있다. effect는 동기 함수로 두고 안에서 async 함수를 만들어 바로 부르고, 정리 함수에서 플래그나 AbortController로 늦은 응답을 막는다.

### 모듈 최상위 변수에 요청별 값을 두면 어떤 문제가 생기나요?

모듈은 프로세스에서 한 번만 평가되니 그 변수는 모든 요청이 같이 쓴다. 한 요청이 `await`로 기다리는 사이 다른 요청이 값을 덮으면 다른 사용자의 데이터가 응답에 섞이고, 동시 요청이 있을 때만 재현돼서 찾기 어렵다. 요청별 값은 인자로 넘기거나 Node의 `AsyncLocalStorage`처럼 비동기 흐름마다 따로 보이는 저장소에 둔다.
