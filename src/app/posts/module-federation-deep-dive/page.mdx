추천 영역을 맡은 리모트의 CDN이 응답을 주지 않기 시작했다. 연결을 거부한 게 아니라 요청을 받아 놓고 아무 말도 하지 않는 상태다. 그런데 추천 영역만 비는 게 아니라 셸 전체가 하얗게 남는다. 헤더도, 다른 팀의 결제 화면도 없다. 로컬에서 똑같이 재현해 보니 화면이 뜨기까지 정확히 120초가 걸렸다.

[마이크로 프런트엔드](/posts/micro-frontends) 글에서 셸과 리모트 구조, 버전 스큐, 독립 배포와 롤백을 다뤘다. 이 글은 그 다음 질문을 다룬다. Module Federation 런타임 안에서는 실제로 무슨 일이 일어나기에 리모트 하나가 멈추면 셸까지 멈추는가, 공유 스코프에서 어느 React가 이기는가, 경고 한 줄은 무엇을 말하는가. 화면을 어떤 방식으로 합칠지 고르는 이야기는 [마이크로 프런트엔드 조합 방식](/posts/micro-frontend-integration-patterns)에 따로 정리했다.

## 실험에 쓴 셸 하나와 리모트 둘

모든 출력은 아래 구성을 직접 빌드해서 Chromium 141(Playwright, 헤드리스)로 열어 얻었다. webpack 5.102.1의 내장 `ModuleFederationPlugin`, Node 22, pnpm 워크스페이스다.

- `host`(포트 18550): React 18.3.1과 react-dom 18.3.1을 설치했다. 셸이다.
- `catalog`(18551): React 18.2.0을 설치했고 `./List`를 내보낸다.
- `cart`(18552): 오래된 리모트라는 설정으로 React 17.0.2를 설치했고 `./Badge`를 내보낸다.

```js
// webpack.config.js 중 공유 설정만
// host
new ModuleFederationPlugin({
  name: "host",
  remotes: {
    catalog: "catalog@http://localhost:18551/remoteEntry.js",
    cart: "cart@http://localhost:18552/remoteEntry.js",
  },
  shared: {
    react: { singleton: true, requiredVersion: "^18.3.0" },
    "react-dom": { singleton: true, requiredVersion: "^18.3.0" },
  },
});
// catalog
shared: { react: { singleton: true, requiredVersion: "^18.2.0" } }
// cart
shared: { react: { singleton: true, requiredVersion: "^17.0.0" } }
```

셸의 진입 파일은 `import("./bootstrap")` 한 줄이고, `bootstrap.js`가 `React.lazy(() => import("catalog/List"))`처럼 리모트를 불러 각각 Error Boundary로 감싼다. 리모트 컴포넌트는 자기가 받은 `React.version`을 `data-react` 속성에 적는다. 그래야 화면에서 실제로 어느 React가 쓰였는지 바로 읽을 수 있다.

여기서 쓰인 두 함수가 Module Federation 컨테이너의 전부다. 리모트의 진입 파일은 전역에 `catalog` 같은 이름으로 객체를 하나 만들고, 그 객체는 `init(shareScope)`와 `get(moduleName)` 두 메서드만 가진다. `init`은 공유 스코프에 자기 버전을 등록하고, `get`은 내보낸 모듈의 factory를 Promise로 돌려준다. 이 인터페이스를 알면 뒤에서 볼 런타임 리모트 로딩을 직접 짤 수 있다.

## 공유 스코프를 직접 열어 보기

공유 스코프는 webpack 런타임 안의 평범한 객체 `__webpack_share_scopes__.default`다. 셸 코드에 이 객체를 읽는 함수를 하나 넣고, 화면이 다 그려진 뒤 Playwright로 불러 봤다.

```js
window.__dumpScope = () => {
  const scope = __webpack_share_scopes__.default;
  const out = {};
  for (const [pkg, versions] of Object.entries(scope)) {
    out[pkg] = Object.fromEntries(
      Object.entries(versions).map(([v, e]) => [v, { from: e.from, eager: !!e.eager, loaded: !!e.loaded }]),
    );
  }
  return out;
};
```

결과를 패키지와 버전마다 한 줄로 찍었다.

```text
react-dom  18.3.1  from=host     eager=false loaded=true
react      18.3.1  from=host     eager=false loaded=true
react      17.0.2  from=cart     eager=false loaded=false
react      18.2.0  from=catalog  eager=false loaded=false
```

패키지 이름 아래에 버전별로 칸이 있고, 각 칸에는 누가 올렸는지(`from`)와 실제로 코드를 받아 실행했는지(`loaded`)가 적혀 있다. react 후보는 셋인데 `loaded`는 하나다. 후보가 올라간 순서는 진입 파일이 도착한 순서라서 실행마다 바뀔 수 있다. catalog와 cart는 React 사본을 들고 왔지만 그 청크는 한 번도 내려오지 않았다. 번들에 들어 있다는 것과 사용자에게 내려간다는 것은 다르다.

## 어느 React가 이기는가

singleton 버전을 고르는 규칙은 webpack 런타임 코드(`ConsumeSharedRuntimeModule`)에 짧게 들어 있다. 이미 `loaded`인 버전이 있으면 그걸 계속 쓰고, 아직 아무것도 받지 않았다면 후보 중 가장 높은 버전을 고른다. 누가 셸이고 누가 리모트인지는 따지지 않는다.

이 규칙의 결과를 보려고 버전을 뒤집어 봤다. 셸은 React와 react-dom 18.2.0으로 내리고(범위도 `^18.2.0`으로), catalog는 React 18.3.1로 올렸다.

에러는 cart 모듈을 불러오는 순간(`consumes`)에 나서 셸의 Error Boundary가 잡았다. 셸과 catalog는 그대로다. 실패 범위가 그 리모트 하나로 좁혀진다는 점에서 strictVersion은 생각보다 덜 위험하다. 경계 없이 쓰면 이야기가 달라진다. 셸이 리모트를 Error Boundary로 감싸지 않았다면 같은 에러가 React 트리 전체를 내린다.

## eager가 필요한 순간과 그 값

진입 파일에서 bootstrap을 거치지 않고 바로 앱을 import하면 `Shared module is not available for eager consumption` 에러가 난다는 건 앞 글에서 짚었다. 이유는 앞의 시퀀스에 있다. React는 공유 스코프 초기화가 끝난 뒤에야 어떤 버전을 쓸지 정해지는데, 동기 import는 그걸 기다릴 틈이 없다. 런타임 입장에서는 아직 factory가 준비되지 않은 모듈을 지금 당장 달라는 요청이다. 실제 메시지 끝의 숫자는 모듈 id다.

```text
[pageerror] Shared module is not available for eager consumption: 851
[runner] timeout waiting for render
[dom] (no main)
```

bootstrap 대신 `eager: true`로 고치는 방법도 있다. React를 초기 청크에 바로 넣어서 기다릴 필요를 없애는 옵션이다. 두 방식으로 셸을 빌드해 `wc -c *.js`로 파일 크기를 비교했다. 먼저 `import("./bootstrap")` 방식이다. `59`는 react-dom, `378`은 react, `854`는 bootstrap 청크다.

```text
  6570 378.ea48519b.js
132684 59.01f1f2fd.js
  1230 854.812cc3e9.js
  8334 main.js
148818 total
```

다음은 진입 파일에서 바로 import하고 react, react-dom에 `eager: true`를 준 방식이다. 이 빌드는 에러 없이 떴다.

```text
148431 main.js
```

eager는 진입 파일이 8KB에서 148KB로 커진다. 더 큰 대가는 협상에서 빠진다는 점이다. eager로 넣은 React는 이미 실행된 상태로 시작하니, 리모트가 더 맞는 버전을 들고 와도 고를 여지가 없다. 셸에서는 bootstrap 방식을 쓰고, eager는 리모트를 단독으로 띄울 때나 서버 렌더링 진입처럼 비동기 경계를 만들기 어려운 곳에만 쓰는 편이 낫다.

두 번째 처방은 리모트를 빌드에 적지 않는 것이다. 셸 설정의 `remotes`를 비우고, 앞에서 본 컨테이너의 `init`과 `get`을 직접 부르는 함수를 만든다.

```js
function loadScript(url, timeoutMs) {
  return new Promise((resolve, reject) => {
    const script = document.createElement("script");
    script.src = url;
    const timer = setTimeout(() => { script.remove(); reject(new Error(`timeout ${timeoutMs}ms`)); }, timeoutMs);
    script.onload = () => { clearTimeout(timer); resolve(); };
    script.onerror = () => { clearTimeout(timer); script.remove(); reject(new Error("script error")); };
    document.head.appendChild(script);
  });
}

export async function loadRemote(name, urls, exposed, timeoutMs = 3000) {
  await __webpack_init_sharing__("default");      // 셸 자신의 공유 모듈만 등록한다
  for (const url of urls) {
    try {
      await loadScript(url, timeoutMs);            // 전역에 window[name] 컨테이너가 생긴다
      const container = window[name];
      await container.init(__webpack_share_scopes__.default);
      const factory = await container.get(exposed);
      return factory();
    } catch (e) {
      console.log(`[loadRemote] ${name} ✗ ${url}: ${e.message}`);
    }
  }
  throw new Error(`${name}: 모든 주소 실패`);
}

// bootstrap.js
const remotes = await fetch("/remotes.json").then((r) => r.json());
const List = lazy(() => loadRemote("catalog", remotes.catalog, "./List"));
```

`remotes.json`에는 catalog 주소를 두 개 적었다. 첫 번째는 매달리는 서버, 두 번째는 정상 서버다. 실행 결과다.

```text
[console.warning] Unsatisfied version 18.3.1 from host of shared singleton module react (required ^17.0.0)
[console.log] [loadRemote] cart ← http://localhost:18552/remoteEntry.js (24ms)
[console.log] [loadRemote] catalog ✗ http://localhost:18553/remoteEntry.js: timeout 3000ms (3000ms)
[console.log] [loadRemote] catalog ← http://localhost:18551/remoteEntry.js (27ms)
[runner] main at 144ms, both remotes at 3173ms
```

셸은 144ms에 떴고 cart는 24ms 만에 붙었다. 기다린 건 catalog 자리 하나뿐이다. 예비 주소에 직전 배포 버전을 두면 장애 중에도 한 단계 옛 화면이 나온다. 앞 글의 버전 경로 배포와 합치면 "현재 포인터, 실패하면 직전 포인터"를 셸이 스스로 고르는 구조가 된다.

이 방식의 대가는 타입과 정적 분석을 잃는다는 점이다. `import("catalog/List")`라는 문자열이 사라지니 번들러도 TypeScript도 어떤 리모트를 쓰는지 모른다. 리모트 이름과 노출 모듈을 상수로 한곳에 모으고, 타입은 뒤에서 볼 방법으로 따로 받아야 한다. Module Federation 2.0의 런타임 패키지(`@module-federation/enhanced/runtime`)는 이 일을 `registerRemotes`, `loadRemote` 같은 함수와 `errorLoadRemote` 훅을 가진 런타임 플러그인으로 정리해 둔다. 이 글의 예제는 webpack 내장 플러그인만으로 돌렸고, 2.0 런타임 API는 패키지의 타입 정의에서 이름만 확인했다.

## 요청이 몇 번 왕복하는가

리모트로 나누면 요청 단계가 늘어난다. 얼마나 늘어나는지 재 보려고 같은 화면을 세 가지로 빌드했다. 모든 요청에 80ms 지연을 넣은 로컬 서버에서 열고, 두 리모트 컴포넌트가 모두 DOM에 붙는 시각을 `MutationObserver`로 쟀다.

- 한 번들: Module Federation 없이 셸이 List와 Badge 소스를 직접 import한다(동적 import는 그대로 둔다).
- 정적 리모트: 지금까지의 구성.
- preload 추가: 정적 리모트에 두 진입 파일의 `<link rel="preload" as="script">`를 HTML에 넣었다.

각각 다섯 번씩 열었다. `mono`가 한 번들, `host`가 정적 리모트, `hostpre`가 preload를 더한 것이다.

## 타입과 CSS는 런타임이 챙겨 주지 않는다

공유 스코프가 해결하는 건 자바스크립트 모듈뿐이다. 나머지 두 가지는 따로 챙겨야 한다.

타입부터. 셸의 `import("catalog/List")`는 TypeScript 입장에서 존재하지 않는 모듈이라 보통 `declare module "catalog/List"`로 직접 타입을 적는다. 그러면 리모트가 props를 바꿔도 셸의 타입 검사는 통과한다. `@module-federation/enhanced` 플러그인은 리모트 빌드 때 노출 모듈의 타입 선언을 묶어 내보내고, 셸이 개발 중에 그 묶음을 받아 `@mf-types` 폴더에 풀어 쓰게 하는 기능을 문서에 안내한다. 이 글에서는 돌려 보지 않았다. 어떤 방식이든 받아 온 타입은 "개발할 때 본 리모트 버전"의 타입일 뿐, 운영에서 실제로 뜰 리모트 버전과 같다는 보장은 아니다. 계약 테스트를 리모트 CI에 두는 이유가 여기 있다.

CSS는 리모트 모듈 청크와 함께 따라 들어온다. 리모트가 `import "./list.css"`를 하고 style-loader나 CSS 추출 플러그인을 쓰면, 그 스타일은 셸 문서의 `<head>`에 붙는다. 그래서 리모트가 늦게 뜨면 그 시점에 스타일이 끼어들어 순서가 바뀌고, 같은 명시도의 규칙이라면 나중에 붙은 쪽이 이긴다. 전역 선택자를 쓰지 않는 규칙과 클래스 이름 자동 고유화는 앞 글에서 다뤘다.

## webpack 밖의 Module Federation

webpack 5의 내장 플러그인은 처음 나온 구현이고, 지금은 같은 개념을 이어받은 구현이 여럿이다. 버전과 세부 동작은 빠르게 바뀌니 도입할 때 각 문서를 확인해야 한다.

- `@module-federation/enhanced`: Module Federation 2.0이다. webpack과 Rspack 둘 다에 붙는다. 매니페스트, 타입 공유, 런타임 플러그인, 개발 도구 연동이 이쪽에 있다.
- Rspack: 자체에 webpack 호환 `ModuleFederationPlugin`을 가지고 있고, 2.0 기능은 위 패키지를 붙여 쓰는 방식으로 안내한다.
- Vite: 공식 번들러 기능은 아니고 플러그인으로 쓴다. Module Federation 조직의 `@module-federation/vite`가 있고, 그 전부터 쓰이던 `@originjs/vite-plugin-federation`도 있다. Vite 계열은 리모트를 ES 모듈로 내보내는 경우가 많아서, 앞 글에서 본 CORS 설정이 필수가 된다.

구현이 바뀌어도 이 글에서 본 구조, 즉 진입 파일, 공유 스코프에 버전을 올리는 init, 모듈을 꺼내는 get, singleton 선택 규칙은 그대로 이어진다. 그래서 내부를 한 번 따라가 보면 도구를 바꿔도 장애를 읽는 방법은 같다.

## 직접 골라 보기

singleton 버전을 고르는 규칙을 함수로 옮겨 보자. 입력은 공유 스코프의 한 패키지 칸이다. 키는 버전 문자열, 값은 `loaded` 여부를 가진 객체다. 이미 받은 버전이 고른 값이면 유지하고, 아니면 더 높은 버전으로 바꾼다. 비어 있으면 `null`을 돌려준다. 버전은 `x.y.z` 숫자 세 개만 나온다고 가정한다.

  // versions 예: { "18.3.1": { loaded: false }, "18.2.0": { loaded: true } }
  // 1. 버전 두 개를 숫자로 비교하는 함수를 만든다 (문자열 비교는 틀린다)
  // 2. 키를 차례로 보면서, 고른 값이 없거나
  //    고른 값이 아직 loaded가 아니고 지금 키가 더 높으면 바꾼다
  return null;
}`}
  solution={`function pickSingleton(versions) {
  const lt = (a, b) => {
    const x = a.split(".").map(Number);
    const y = b.split(".").map(Number);
    for (let i = 0; i < 3; i++) {
      if (x[i] !== y[i]) return x[i] < y[i];
    }
    return false;
  };
  let picked = null;
  for (const v of Object.keys(versions)) {
    if (picked === null || (!versions[picked].loaded && lt(picked, v))) picked = v;
  }
  return picked;
}`}
  tests={[

    { args: [{ "18.2.0": { loaded: true }, "18.3.1": { loaded: false } }], expected: "18.2.0", label: "이미 받은 버전이 있을 때" },
    { args: [{ "18.9.2": { loaded: false }, "18.10.0": { loaded: false } }], expected: "18.10.0", label: "문자열 비교 함정" },
    { args: [{ "17.0.2": { loaded: false } }], expected: "17.0.2", label: "후보 하나" },

  ]}

세 번째 테스트에서 `"18.9.2" < "18.10.0"`을 문자열로 비교하면 `false`가 나와 틀린 답을 고른다. webpack 런타임의 `versionLt`도 점으로 나눠 숫자로 비교하고, 프리릴리스 꼬리표까지 다룬다.

## 다시 120초 앞에서

리모트 하나가 매달렸을 때 셸이 같이 멈춘 건, 정적 리모트의 진입 파일이 공유 스코프 초기화의 일부이기 때문이었다. 공유 스코프는 앱들이 버전을 올려 두는 객체이고, singleton은 이미 받은 버전이 없으면 누구 것이든 가장 높은 버전을 고른다. 이 두 가지를 알면 경고 한 줄과 장애 증상을 런타임의 단계에 맞춰 읽을 수 있다. 처방도 그 단계에서 나온다. 리모트가 React를 들고 오지 않게 하는 `import: false`, 실패를 좁히는 `strictVersion`과 Error Boundary, 기다림을 줄이는 `chunkLoadTimeout`과 런타임 로딩, 왕복을 줄이는 preload. 화면을 합치는 방식 자체를 다시 고민한다면 [조합 방식](/posts/micro-frontend-integration-patterns) 글로 이어진다.

## 면접에서 나올 만한 질문

### Module Federation의 리모트 컨테이너는 어떤 인터페이스를 가지나요?

진입 파일(`remoteEntry.js`)이 전역에 만드는 컨테이너 객체는 `init(shareScope)`와 `get(moduleName)` 두 메서드를 가진다. `init`은 셸이 넘긴 공유 스코프 객체에 리모트가 가진 공유 모듈 버전을 등록하고, `get`은 노출한 모듈의 factory를 Promise로 돌려준다. 정적 `remotes` 설정은 이 두 호출을 번들러가 대신 만들어 주는 것이고, 런타임 로딩은 같은 호출을 직접 하는 것이다.

### 리모트 하나가 응답하지 않으면 왜 셸 전체가 안 뜰 수 있나요?

정적으로 적은 리모트의 진입 파일은 공유 스코프 초기화 단계에서 받기 때문이다. 셸의 bootstrap 청크가 React 같은 공유 모듈을 쓰면 런타임은 모든 리모트의 `init`이 끝나야 버전을 고르고 실행한다. 연결 거부는 바로 실패해서 경고만 남기고 넘어가지만, 응답 없이 매달리면 `chunkLoadTimeout` 기본값인 120초를 기다린다. 타임아웃을 줄이거나, 리모트를 런타임에 불러서 그 영역만 기다리게 고친다.

### singleton 공유 모듈은 어떤 버전이 선택되나요?

이미 받아서 실행된 버전이 있으면 그것을 계속 쓰고, 없으면 공유 스코프의 후보 중 가장 높은 버전을 고른다. 셸인지 리모트인지는 따지지 않아서, 리모트가 더 높은 패치 버전을 들고 오면 셸까지 그 리모트의 React를 받아 쓴다. 이걸 막으려면 리모트의 shared 항목에 `import: false`를 줘서 사본을 아예 들고 오지 않게 한다. 대신 리모트를 단독 실행할 설정이 따로 필요하다.

### requiredVersion, strictVersion, singleton은 각각 무엇을 하나요?

`singleton`은 페이지에 그 패키지를 하나만 띄우게 한다. `requiredVersion`은 이 앱이 받아들일 수 있는 범위이고, 생략하면 `package.json`의 의존성 문자열을 쓴다. singleton에서 고른 버전이 범위 밖이면 기본은 콘솔 경고만 내고 그 버전을 쓴다. `strictVersion: true`면 그 모듈을 불러오는 순간 에러를 던져서, Error Boundary가 있으면 그 리모트만 대체 화면으로 바뀐다.

### `Shared module is not available for eager consumption`은 왜 나고 어떻게 고르나요?

공유 모듈은 공유 스코프 초기화가 끝나야 버전이 정해지는데, 진입 파일에서 동기로 import하면 기다릴 틈 없이 바로 달라고 하기 때문이다. 진입 파일에 `import("./bootstrap")`만 두어 비동기 경계를 만들면 해결된다. `eager: true`도 에러는 없애지만 그 모듈이 초기 청크에 들어가 진입 파일이 커지고(실험에서 8KB에서 148KB), 협상 없이 그 버전으로 고정된다. 그래서 셸에는 bootstrap 방식을 쓴다.

### Module Federation이 성능에 주는 비용을 어떻게 재고 줄이나요?

요청 왕복이 늘어나는 게 가장 크다. main.js, 리모트 진입 파일, 고른 공유 모듈, 리모트 모듈이 줄지어 받아진다. 리소스 타이밍으로 각 요청의 시작과 끝을 펼쳐 보면 단계가 보이고, 실험에서는 중앙값 기준 한 번들 412ms, 정적 리모트 533ms였다. 진입 파일을 HTML에서 preload하면 한 단계가 사라져 459ms로 차이가 절반 넘게 줄었다. 리모트마다 붙는 런타임(진입 파일 약 6KB)과 공유하지 않은 라이브러리 중복도 전송량에 더해진다.

### 런타임에 리모트를 불러오면 무엇을 얻고 무엇을 잃나요?

리모트 주소를 빌드에서 떼어 내니 셸 재배포 없이 리모트를 바꾸거나 되돌릴 수 있고, 한 리모트의 장애가 셸 초기화를 막지 않는다. 주소 목록에 예비 주소를 두면 시간 초과 때 직전 버전으로 넘어가는 것도 셸이 직접 한다. 잃는 건 정적 분석이다. 번들러와 TypeScript가 어떤 리모트를 쓰는지 모르니 이름과 타입을 따로 관리하고, 계약 테스트로 실제 리모트 버전과의 호환을 확인해야 한다.
