[Reverse Integer](https://leetcode.com/problems/reverse-integer/)는 LeetCode 7번이다. 정수의 자릿수를 거꾸로 뒤집는다. 여기까지는 쉬운데, 뒤집은 값이 32비트 부호 있는 정수 범위를 벗어나면 0을 돌려줘야 하고, 문제는 "64비트 정수를 쓸 수 없는 환경이라고 가정하라"고 덧붙인다. 그러니 다 뒤집은 뒤에 범위를 확인하는 방법은 반칙이다. 넘치기 전에 알아채야 한다.

이 문제가 비트 연산 패턴에 들어가 있는 건 그래서다. 32비트 정수가 어디서 넘치고 넘치면 어떻게 되는지, 2의 보수 범위가 왜 -2^31부터 2^31 - 1까지로 한쪽이 하나 더 긴지가 풀이 곳곳에 나온다. 32비트가 무엇인지는 [비트 연산 글](/posts/bit-manipulation#숫자-하나에-스위치-아홉-개)에, JavaScript가 비트 연산 앞에서 32비트로 자르는 동작은 [같은 글의 이 절](/posts/bit-manipulation#자바스크립트는-비트-연산-앞에서-32비트로-자른다)에 있다. 이 글은 문자열 풀이부터 넘침 미리 막기, 넘친 뒤 되돌려 보기, 한계값과 문자열 비교까지 다섯 가지로 푼다. 코드는 Node.js 22, Python 3.13, Java 21에서 직접 돌렸다.

## 거꾸로 읽되 32비트 안에서만

정수 `x`가 주어진다. 자릿수를 거꾸로 뒤집은 정수를 돌려준다. 부호는 그대로 둔다. 뒤집은 값이 -2^31(-2147483648) 이상 2^31 - 1(2147483647) 이하가 아니면 0을 돌려준다.

풀이를 고르는 데 영향을 주는 제약은 이것뿐이다.

- `x` 자체는 32비트 범위 안에 있다. 그래서 자릿수는 많아야 10개다.
- 64비트 정수(Java의 `long` 같은 것)를 쓸 수 없다고 가정한다.

자릿수가 10개를 넘지 않으니 어떤 풀이든 시간은 O(10), 사실상 O(1)이다. 이 문제에서 고민할 건 속도가 아니라 넘침이다. 면접관이 보는 것도 "넘침을 어디서, 어떻게 막느냐"다.

## -1230을 손으로 뒤집으면

예시 하나를 정해 두고 끝까지 쓴다. -1230이다.

```text
원래     -  1  2  3  0
부호 떼기   1  2  3  0
뒤집기      0  3  2  1   → 앞의 0은 사라져 321
부호 붙이기 -321
```

손으로 하면 세 가지를 신경 쓴다. 부호는 따로 떼어 둔다. 끝자리 0은 뒤집으면 맨 앞에 와서 사라진다. 결과가 너무 크면 0이다.

넘치는 예시도 하나 정해 둔다. 1563847412를 뒤집으면 2147483651이다. 32비트 최댓값 2147483647보다 4가 크다. 그래서 답은 0이다. 반대로 1463847412를 뒤집은 2147483641은 최댓값보다 6 작아서 그대로 답이 된다. 이 두 수는 앞 아홉 자리가 같아서, 마지막 한 자리에서 운명이 갈린다. 뒤의 그림이 바로 그 순간을 보여 준다.

## 문자열로 바꿔 뒤집기

가장 먼저 떠오르는 건 숫자를 글자로 보는 것이다. 절댓값을 문자열로 바꿔 뒤집고, 다시 수로 읽은 뒤 부호를 붙이고 범위를 본다.

```js
const MAX = 2 ** 31 - 1, MIN = -(2 ** 31);

function reverse(x) {
  // 부호를 떼고 글자 단위로 뒤집는다
  const r = Number(String(Math.abs(x)).split("").reverse().join(""));
  const v = x < 0 ? -r : r;
  return v < MIN || v > MAX ? 0 : v; // 다 뒤집은 뒤에 범위를 본다
}

console.log([-1230, 120, 0, 1463847412, 1563847412, -1563847412, -2147483648].map(reverse).join(" "));
```

```text
-321 21 0 2147483641 0 0 0
```

`"0321"`을 `Number`로 읽으면 앞의 0이 사라져 321이 된다. 끝자리 0 처리를 따로 하지 않아도 되는 이유다.

시간과 공간은 자릿수만큼이라 O(log |x|), 즉 O(10)이다. 동작은 맞지만 문제의 덧붙인 조건을 어긴다. 뒤집은 값 9646324351 같은 수를 일단 담아 두고 나서 범위를 확인하기 때문이다. JavaScript의 수는 2^53까지 정수를 담으니 여기서는 문제가 안 되지만, `int`밖에 없는 환경이라면 담는 순간 이미 넘쳤다. 면접에서 이 풀이로 끝내면 "64비트를 못 쓴다면요?"라는 질문이 바로 온다.

## 끝자리를 떼어 새 수의 끝에 붙인다

문자열 없이 산수로 뒤집을 수 있다. 십진수의 끝자리는 `x % 10`이고, 끝자리를 뗀 나머지는 `x / 10`을 정수로 버린 값이다. 떼어 낸 자리를 새 수 `rev`의 끝에 붙이려면 `rev * 10 + d`를 한다.

```text
x = 123,  rev = 0
d = 3   x = 12   rev = 0 × 10 + 3 = 3
d = 2   x = 1    rev = 3 × 10 + 2 = 32
d = 1   x = 0    rev = 32 × 10 + 1 = 321
```

```js
const MAX = 2 ** 31 - 1, MIN = -(2 ** 31);

function reverse(x) {
  let rev = 0;
  while (x !== 0) {
    const d = x % 10;       // 끝자리. 음수면 d도 음수다
    x = Math.trunc(x / 10); // 끝자리를 뗀다. 0 쪽으로 버린다
    rev = rev * 10 + d;     // 새 수의 끝에 붙인다
  }
  return rev < MIN || rev > MAX ? 0 : rev; // 아직은 다 뒤집고 나서 본다
}

console.log([-1230, 120, 0, 1463847412, 1563847412, -1563847412, -2147483648].map(reverse).join(" "));
```

```text
-321 21 0 2147483641 0 0 0
```

음수를 따로 처리하지 않았는데 맞게 나온다. JavaScript의 `%`는 나머지의 부호를 왼쪽 수에 맞추고(`-1230 % 10`은 -0, `-7 % 10`은 -7), `Math.trunc`는 0 쪽으로 버린다(`Math.trunc(-1230 / 10)`은 -123). 그래서 음수에서는 끝자리 d가 음수로 나오고, `rev`도 음수로 쌓인다. 부호를 떼지 않아도 된다.

넘치면 실제로 어떻게 되는지 `| 0`으로 32비트를 흉내 내 보면 바로 보인다.

```js
function reverseInt32(x) {
  let rev = 0;
  while (x !== 0) {
    const d = x % 10;
    x = (x / 10) | 0;           // | 0은 32비트 정수로 자른다
    rev = (rev * 10 + d) | 0;   // 넘치면 2^32로 돌아 버린다
  }
  return rev;
}
console.log(reverseInt32(1563847412), reverseInt32(-123));
```

양수 1563847412를 뒤집었는데 음수가 나왔다. 2147483651은 최댓값을 4 넘었고, 2^32만큼 돌아서 -2147483645가 됐다. 예외도 경고도 없다. 이 값을 보고 "범위 밖이니 0"이라고 판단할 방법이 없다. 범위 안의 음수이기 때문이다. 그래서 검사는 곱하기 전으로 옮겨야 한다.

## 곱하기 전에 넘칠지 먼저 본다

`rev * 10 + d`가 최댓값 2147483647을 넘는 경우는 두 가지다.

- `rev`가 이미 214748364(최댓값을 10으로 나눈 몫)보다 크다. 그러면 10을 곱하는 것만으로 넘친다.
- `rev`가 정확히 214748364이고 d가 7보다 크다. 2147483640 + d가 2147483647을 넘는다.

음수 쪽도 같다. 최솟값 -2147483648을 10으로 나눈 몫은 -214748364이고, 남는 끝자리는 -8이다. 이 검사를 `rev * 10 + d` 바로 앞에 두면, 넘칠 계산은 아예 하지 않는다.

```js
const MAX = 2 ** 31 - 1, MIN = -(2 ** 31);
const MAX_DIV = Math.trunc(MAX / 10); // 214748364
const MIN_DIV = Math.trunc(MIN / 10); // -214748364

function reverse(x) {
  let rev = 0;
  while (x !== 0) {
    const d = x % 10;
    x = Math.trunc(x / 10);
    // rev * 10 + d가 넘칠 것 같으면 계산하기 전에 멈춘다
    if (rev > MAX_DIV || (rev === MAX_DIV && d > 7)) return 0;
    if (rev < MIN_DIV || (rev === MIN_DIV && d < -8)) return 0;
    rev = rev * 10 + d; // 여기서는 절대 넘치지 않는다
  }
  return rev;
}

console.log([-1230, 120, 0, 1463847412, 1563847412, -1563847412, -2147483648].map(reverse).join(" "));
```


### 7과 -8은 어디서 왔나

2147483647의 끝자리가 7이고, -2147483648의 끝자리가 -8이다. 둘이 다른 건 2의 보수 때문이다. 32비트 2의 보수에서 맨 위 비트는 -2^31의 무게를 가진다. 그래서 음수 쪽은 -2^31까지, 양수 쪽은 2^31 - 1까지라 음수가 하나 더 많다. 0이 양수 쪽 자리를 하나 차지한 셈이다. 이 비대칭이 뒤의 `Math.abs` 함정도 만든다.

### 같을 때의 검사는 실제로 걸리지 않는다

`rev === MAX_DIV && d > 7` 부분은 이 문제에서 한 번도 참이 되지 않는다. `rev`가 214748364(아홉 자리)가 된 뒤 남은 자리가 있다면 x는 열 자리 수였고, 남은 자리는 x의 맨 앞자리다. 32비트 안의 열 자리 수는 1이나 2로 시작한다. 그러니 d는 2 이하라 7을 넘을 수 없다. 무작위 32비트 정수 200만 개로 돌려 봤는데 이 조건에 걸린 경우는 0번이었다.

그래서 `if (rev > MAX_DIV || rev < MIN_DIV) return 0;` 한 줄만 써도 맞다. 하지만 면접에서는 같을 때의 검사까지 쓰고, 왜 생략해도 되는지를 말로 덧붙이는 쪽이 낫다. 입력이 64비트로 바뀌거나, 문자열을 정수로 바꾸는 LeetCode 8번처럼 맨 앞자리가 자유로운 문제에서는 이 검사가 진짜로 필요하다.

### Python과 Java

```python
class Solution:
    def reverse(self, x: int) -> int:
        INT_MAX = 2**31 - 1
        sign = -1 if x < 0 else 1
        x = abs(x)                 # 부호를 떼고 양수로만 다룬다
        rev = 0
        while x:
            x, d = divmod(x, 10)   # 몫과 나머지를 한 번에
            # 부호를 붙였을 때 범위를 넘는지 미리 본다
            limit = INT_MAX if sign > 0 else INT_MAX + 1
            if rev > (limit - d) // 10:
                return 0
            rev = rev * 10 + d
        return sign * rev

s = Solution()
print([s.reverse(x) for x in [-1230, 120, 0, 1463847412, 1563847412, -1563847412, -2**31]])
print(-123 % 10, -123 // 10, int(-123 / 10))
```

```text
[-321, 21, 0, 2147483641, 0, 0, 0]
7 -13 -12
```

Python에서는 부호를 먼저 뗀다. 마지막 줄 출력이 그 이유다. Python의 `%`는 나머지의 부호를 오른쪽 수에 맞춰 `-123 % 10`이 7이고, `//`는 아래로 버려 `-123 // 10`이 -13이다. JavaScript 코드를 그대로 옮기면 음수에서 엉뚱한 자리가 나온다. 양수로만 계산하면 이 차이가 사라진다.

검사는 `rev * 10 + d > limit`을 곱셈 없이 바꾼 `rev > (limit - d) // 10`이다. Python의 정수는 넘치지 않으니 사실 곱한 뒤 비교해도 되지만, 문제의 가정을 따라 미리 본다. 음수의 한계는 2147483648이라 부호에 따라 `limit`을 바꾼다.

```java
class Solution {
    public int reverse(int x) {
        int rev = 0;
        while (x != 0) {
            int d = x % 10;   // Java의 %는 부호를 x에 맞춘다: -123 % 10 == -3
            x /= 10;          // 0 쪽으로 버린다: -123 / 10 == -12
            // rev * 10 + d가 int를 넘기 전에 미리 막는다
            if (rev > Integer.MAX_VALUE / 10 || (rev == Integer.MAX_VALUE / 10 && d > 7)) return 0;
            if (rev < Integer.MIN_VALUE / 10 || (rev == Integer.MIN_VALUE / 10 && d < -8)) return 0;
            rev = rev * 10 + d;
        }
        return rev;
    }

    // 넘친 뒤 되돌려 보고 원래 값이 안 나오면 넘친 것으로 본다
    public int reverseByUndo(int x) {
        int rev = 0;
        while (x != 0) {
            int d = x % 10;
            x /= 10;
            int next = rev * 10 + d;            // 넘치면 조용히 돌아 버린다
            if ((next - d) / 10 != rev) return 0; // 되돌려서 확인한다
            rev = next;
        }
        return rev;
    }

    public static void main(String[] args) {
        Solution s = new Solution();
        int[] xs = { -1230, 120, 0, 1463847412, 1563847412, -1563847412, Integer.MIN_VALUE };
        StringBuilder a = new StringBuilder(), b = new StringBuilder();
        for (int x : xs) { a.append(s.reverse(x)).append(' '); b.append(s.reverseByUndo(x)).append(' '); }
        System.out.println(a.toString().trim());
        System.out.println(b.toString().trim());
    }
}
```

```text
-321 21 0 2147483641 0 0 0
-321 21 0 2147483641 0 0 0
```

Java의 `%`와 `/`는 JavaScript와 같은 규칙(부호는 왼쪽, 0 쪽으로 버림)이라 음수를 따로 처리하지 않아도 된다. 아래의 `reverseByUndo`가 다음 절의 풀이다.

## 넘친 뒤 되돌려 보고 알아채기

미리 막지 않고 일단 계산한 뒤 알아채는 방법도 있다. `next = rev * 10 + d`를 구한 다음 거꾸로 `(next - d) / 10`을 해 본다. 넘치지 않았다면 원래 `rev`가 그대로 나온다. 넘쳤다면 `next`가 2^32만큼 돌아간 값이라 되돌려도 `rev`가 나오지 않는다.

이 방법은 "넘쳐도 프로그램이 죽지 않고 조용히 돈다"는 걸 전제로 한다. Java와 C#의 `int`, JavaScript의 `| 0`이 그렇다. C와 C++에서는 부호 있는 정수의 넘침이 정의되지 않은 동작이라 컴파일러가 이 검사를 지워 버릴 수도 있다. 그래서 C++로 푼다면 앞의 미리 막는 방식을 쓴다.

JavaScript로는 `| 0`으로 32비트 계산을 흉내 낸다.

```js
function reverse(x) {
  let rev = 0;
  while (x !== 0) {
    const d = x % 10;
    x = Math.trunc(x / 10);
    const next = (rev * 10 + d) | 0;               // 32비트로 자른다. 넘치면 돈다
    if (Math.trunc((next - d) / 10) !== rev) return 0; // 되돌려서 rev가 안 나오면 넘쳤다
    rev = next;
  }
  return rev;
}

console.log([-1230, 120, 0, 1463847412, 1563847412, -1563847412, -2147483648].map(reverse).join(" "));
```

```text
-321 21 0 2147483641 0 0 0
```

1563847412의 마지막 단계에서 `rev`는 214748365, `next`는 2147483651이 돌아간 -2147483645다. `(-2147483645 - 1) / 10`은 -214748364.6이고 버리면 -214748364라 `rev`와 다르다. 넘친 걸 알아챈다.

시간과 공간은 앞 풀이와 같다. 코드가 짧고 한계값 상수가 필요 없다는 장점이 있지만, 언어의 넘침 규칙에 기대니 이식성이 떨어진다. 면접에서는 미리 막는 쪽을 기본으로 내고, 이 방법은 "이런 방법도 있다"로 덧붙이는 정도가 좋다.

## 문자열을 한계값과 사전 순으로 비교하기

산수를 쓰지 않고 넘침을 판단할 수도 있다. 뒤집은 숫자 문자열을 `"2147483647"`(음수면 `"2147483648"`)과 비교한다. 자릿수가 더 많으면 넘친 것이고, 자릿수가 같으면 사전 순으로 비교한다. 자릿수가 같은 숫자 문자열은 사전 순과 크기 순이 같기 때문이다.

```js
function reverse(x) {
  // 뒤집고 앞의 0을 지운다 (모두 0이면 "0" 하나는 남긴다)
  const s = String(Math.abs(x)).split("").reverse().join("").replace(/^0+(?=\d)/, "");
  const limit = x < 0 ? "2147483648" : "2147483647";
  // 자릿수가 많거나, 같으면서 사전 순으로 크면 넘친다
  if (s.length > limit.length || (s.length === limit.length && s > limit)) return 0;
  const r = Number(s); // 이제는 범위 안이라 안전하다
  return x < 0 ? -r : r;
}

console.log([-1230, 120, 0, 1463847412, 1563847412, -1563847412, -2147483648].map(reverse).join(" "));
```

```text
-321 21 0 2147483641 0 0 0
```

앞의 0을 지우지 않으면 `"0321"`처럼 자릿수가 부풀어 비교가 틀린다. 정규식의 `(?=\d)`는 숫자 하나는 남기라는 뜻이라 0은 `"0"`으로 남는다.

이 방식은 아주 큰 수(64비트를 넘는 수를 문자열로 받는 경우)에도 그대로 쓸 수 있다는 장점이 있다. 다만 문자열을 만들고 비교하는 비용이 들어 가장 느리다. LeetCode 8. String to Integer (atoi) 같은 파싱 문제에서 참고할 만한 방식이다.

## 부호와 끝자리 0이 만드는 버그

### `Math.floor`로 끝자리를 떼기

```js
function wrongFloor(x) {
  let rev = 0, steps = 0;
```

양수에서는 `Math.floor`와 `Math.trunc`가 같아서 테스트를 양수로만 하면 못 잡는다. 음수에서는 `Math.floor(-1 / 10)`이 0이 아니라 -1이라 x가 영원히 -1에 머문다. 반복을 강제로 끊지 않았다면 무한 루프다. 0 쪽으로 버리는 `Math.trunc`를 쓴다. Python 코드에서 `//`를 그대로 쓰면 같은 일이 생겨서, 앞에서 부호를 먼저 뗐다.

### Java에서 `Math.abs`로 부호 떼기

Python처럼 부호를 떼고 시작하려고 Java에서 `x = Math.abs(x)`를 쓰면 최솟값 하나에서 깨진다.

### 끝자리 0과 0 자체

120을 뒤집으면 021이 아니라 21이다. 산수 풀이는 0을 붙여도 `rev`가 0으로 남아서 자연스럽게 처리된다. 문자열 풀이는 수로 다시 읽을 때 사라진다. 문제는 문자열을 수로 바꾸지 않고 비교하는 풀이다. 앞의 0을 지우지 않으면 자릿수 비교가 틀린다.

x가 0이면 산수 풀이는 반복을 한 번도 돌지 않고 0을 돌려준다. 맞는 답이다. `do ... while`처럼 최소 한 번 도는 반복으로 쓰면 0에서도 한 번 돌지만 결과는 같다.

### 범위 검사를 양수 쪽만 하기

`rev > MAX_DIV`만 쓰고 음수 쪽 검사를 빼면 -1563847412가 -2147483651로 뒤집힌다. JavaScript에서는 이 값이 그대로 나오고, Java에서는 돌아서 2147483645라는 양수가 나온다. 음수를 테스트에 꼭 넣는다.

## 회문 판별, 문자열 파싱, 64비트로 넓히면

### 숫자가 회문인지 묻는다면

LeetCode 9. Palindrome Number는 정수가 앞뒤로 같은지 묻는다. 전부 뒤집어 원래 수와 비교하면 되지만, 뒤집다가 넘칠 수 있다. 그래서 절반만 뒤집는다. 끝자리를 떼어 `rev`에 붙이다가 `rev`가 남은 x 이상이 되면 멈추고, `x === rev`(자릿수가 짝수) 또는 `x === Math.trunc(rev / 10)`(홀수)을 본다. 절반만 뒤집으니 넘칠 일이 없다.

```js
function isPalindrome(x) {
  if (x < 0 || (x % 10 === 0 && x !== 0)) return false; // 음수, 끝이 0인 수는 회문이 아니다
  let rev = 0;
  while (x > rev) {        // 절반까지만 뒤집는다
    rev = rev * 10 + (x % 10);
    x = Math.trunc(x / 10);
  }
  return x === rev || x === Math.trunc(rev / 10); // 홀수 자리면 가운데 자리를 버린다
}
console.log(isPalindrome(12321), isPalindrome(1221), isPalindrome(10), isPalindrome(-121), isPalindrome(0));
```

```text
true true false false true
```

끝이 0인 수를 먼저 거르는 이유는 10 같은 수 때문이다. 거르지 않으면 반복이 끝났을 때 `rev`는 1, x는 0이 되고, `x === Math.trunc(rev / 10)`이 0 === 0으로 참이 되어 10을 회문이라고 답한다. 끝이 0인 양수는 맨 앞이 0일 수 없으니 회문이 될 수 없어서 미리 거른다.

### 문자열을 정수로 바꾼다면

LeetCode 8. String to Integer (atoi)는 같은 넘침 검사를 반대 방향으로 쓴다. 문자열의 앞자리부터 읽어 `num * 10 + d`를 쌓고, 쌓기 전에 `num > MAX_DIV || (num === MAX_DIV && d > 7)`을 본다. 여기서는 맨 앞자리가 어떤 수든 올 수 있어서, 이 글에서 "실제로 걸리지 않는다"고 했던 같을 때의 검사가 진짜로 필요하다. 넘치면 0이 아니라 최댓값이나 최솟값으로 잘라서 돌려주는 것도 다르다.

### 64비트 정수를 뒤집으라면

같은 코드에서 한계만 2^63 - 1(9223372036854775807)로 바꾼다. 한계를 10으로 나눈 몫은 922337203685477580, 끝자리는 7이고 음수는 -8이다. 우연히 32비트와 끝자리가 같다. JavaScript의 `Number`는 2^53을 넘는 정수를 정확히 담지 못해서 이 경우는 BigInt로 풀어야 한다.

## 면접에서 나올 만한 질문

### 넘침을 어떻게 검사하나요?

`rev * 10 + d`를 계산하기 전에 `rev`가 최댓값을 10으로 나눈 몫 214748364보다 큰지 본다. 크면 10을 곱하는 순간 넘친다. 같다면 붙일 자리 d가 7보다 큰지 본다. 음수 쪽은 -214748364와 -8로 같은 검사를 한다. 계산 중 어떤 값도 32비트 밖으로 나가지 않는다.

### 다 뒤집은 다음에 범위를 확인하면 안 되나요?

64비트 정수나 JavaScript의 `Number`처럼 큰 값을 담을 수 있으면 동작은 한다. 하지만 32비트 정수만 쓸 수 있다면 넘친 순간 값이 2^32만큼 돌아서, 범위 안의 엉뚱한 수가 된다. 1563847412를 뒤집으면 -2147483645가 나오는데 이건 범위 안이라 걸러지지 않는다. 그래서 검사는 넘치기 전에 해야 한다.

### 양수 한계는 7, 음수 한계는 -8인 이유는 무엇인가요?

32비트 2의 보수 범위가 -2^31부터 2^31 - 1까지라서다. 맨 위 비트가 -2^31의 무게를 가져 음수가 하나 더 많다. 그래서 최댓값 2147483647의 끝자리는 7, 최솟값 -2147483648의 끝자리는 8이다. 같은 이유로 Java에서 `Math.abs(Integer.MIN_VALUE)`는 양수가 되지 못하고 최솟값 그대로다.

### `rev == 214748364 && d > 7` 검사는 꼭 필요한가요?

이 문제에서는 걸리지 않는다. `rev`가 아홉 자리에 이른 뒤 남은 자리는 입력의 맨 앞자리인데, 32비트 안의 열 자리 수는 1이나 2로 시작하기 때문이다. 그래도 쓰는 게 좋다. 맨 앞자리가 자유로운 atoi 같은 문제나 입력 범위가 바뀌는 경우에는 이 검사가 필요하다.

### 음수는 어떻게 처리하나요?

JavaScript와 Java는 `%`가 왼쪽 수의 부호를 따르고 나눗셈이 0 쪽으로 버리므로, 음수를 그대로 계산하면 자릿수도 음수로 나와 결과가 맞다. Python은 `%`가 오른쪽 수의 부호를 따르고 `//`가 아래로 버려서 부호를 먼저 떼고 양수로 계산한다. Java에서 부호를 떼려고 `Math.abs`를 쓰면 최솟값에서 깨진다.

### 시간 복잡도는 얼마인가요?

자릿수만큼 반복하니 O(log |x|)다. 32비트 정수는 많아야 열 자리라 상수로 보고 O(1)이라 해도 된다. 공간은 산수 풀이가 O(1), 문자열 풀이는 자릿수만큼이다.

### 넘친 뒤에 알아채는 방법도 있나요?

`next = rev * 10 + d`를 구한 뒤 `(next - d) / 10`이 `rev`와 같은지 본다. 넘치면 값이 돌아서 되돌려도 `rev`가 나오지 않는다. 넘침이 정의된 Java에서는 동작하지만, C·C++에서 부호 있는 정수 넘침은 정의되지 않은 동작이라 믿을 수 없다. 그래서 기본은 미리 막는 쪽이다.
