상품 상세 페이지를 빠르게 하려고 Redis에 상품 정보를 캐시해 두었다. 처음에는 단순했다. DB에서 읽은 상품 객체를 JSON 문자열로 바꿔 `SET product:42 '...'`로 넣고, 읽을 때 `GET`해서 파싱한다. 문제는 재고를 Redis에서 바로 줄이기 시작하면서 생겼다. 재고 하나를 줄이려면 문자열 전체를 가져와 파싱하고, 숫자를 바꾸고, 다시 문자열로 만들어 통째로 써야 한다. 그리고 주문이 몰린 날 재고 숫자가 실제 판매량과 맞지 않았다.

Redis 모듈은 이런 일을 서버 안에서 처리하는 명령과 자료형을 더하는 방법이다. 이 글은 문자열 통째 쓰기가 왜 깨지는지 직접 재현하고, 모듈 API가 무엇을 열어 주는지 작은 모듈을 직접 만들어 확인한다. 그다음 JSON(경로로 부분 수정), 검색(보조 인덱스·전문 검색·벡터 검색), 시계열(보존 기간·다운샘플링), 확률적 자료구조(블룸·쿠쿠 필터, Top-K, Count-Min)를 명령으로 보고, Redis 8에서 이것들이 기본 배포에 들어온 변화와 Valkey 쪽의 대응 모듈을 짚는다. 마지막으로 언제 Redis 안에서 끝내고 언제 Elasticsearch나 TimescaleDB 같은 전용 저장소로 가야 하는지 정리한다.

실험 환경을 밝혀 둔다. Ubuntu 24.04의 `redis-server` 패키지(7.0.15)로 실험했고, 이 패키지에는 모듈이 들어 있지 않다. 모듈 소스를 받아 빌드하는 일은 이 환경에서 하지 않기로 해서, JSON·검색·시계열·확률 자료구조 명령은 공식 문서의 형식대로 적고 출력 블록은 넣지 않았다. 출력 블록이 있는 것은 Redis 7.0.15에서 직접 돌린 결과와, 이 글을 위해 C로 직접 짠 작은 모듈의 결과다. Redis가 빠른 이유와 기본 자료구조는 [Redis 기초](/posts/redis-basics)에 있다.

## 통째로 읽고 통째로 쓰면 재고가 맞지 않는다

먼저 처음 장면을 재현했다. 재고 1000개인 상품을 JSON 문자열로 넣고, 프로세스 두 개가 각각 500번씩 "읽고, 고치고, 쓰기"로 재고를 하나씩 줄인다. 다 끝나면 0이어야 한다. Python 3.13과 redis-py 8.1로 돌렸다.

```python
import json, redis
from multiprocessing import Process

r0 = redis.Redis(port=6399)
r0.set("product:42", json.dumps({"id": 42, "name": "keyboard", "price": 59000, "stock": 1000}))

def worker():
    r = redis.Redis(port=6399)
    for _ in range(500):
        p = json.loads(r.get("product:42"))   # 통째로 읽고
        p["stock"] -= 1                        # 앱에서 고치고
        r.set("product:42", json.dumps(p))     # 통째로 다시 쓴다

ps = [Process(target=worker) for _ in range(2)]
[p.start() for p in ps]; [p.join() for p in ps]
print("expected 0, got", json.loads(r0.get("product:42"))["stock"])
```

```text
expected 0, got 312
expected 0, got 413
expected 0, got 340
```

세 번 돌려서 세 번 다 틀렸고, 매번 다르게 틀렸다. 1000번 줄였는데 600번 남짓만 반영됐다. 아래 그림에서 다음을 누르면 한 번의 갱신이 사라지는 순서가 보인다.

Redis는 명령을 한 줄로 세워 하나씩 처리하니 `GET` 하나, `SET` 하나는 원자적이다. 그런데 두 명령 사이에 다른 클라이언트가 끼어들 수 있다. 모듈 없이 고치는 방법은 셋이다.

```bash
# 1. 필드를 해시로 나눈다. 숫자 필드는 서버에서 바로 줄인다
redis-cli -p 6399 HSET product:42:h id 42 name "무선 키보드" price 59000 stock 17
redis-cli -p 6399 HINCRBY product:42:h stock -1
```

```text
4
16
```

해시는 필드가 한 단계뿐이라 `tags` 배열이나 `options.colors[0].stock` 같은 중첩 구조를 담지 못한다. 두 번째는 `WATCH` 후 `MULTI`/`EXEC`로 낙관적 잠금을 거는 것이다. 읽은 뒤 누가 바꿨으면 `EXEC`가 실패하고 다시 시도한다. 경합이 심하면 재시도가 계속 실패한다. 세 번째는 Lua 스크립트로 읽기·파싱·쓰기를 서버 안에서 한 번에 하는 것이다. 원자적이지만 Lua의 `cjson`으로 매번 문자열 전체를 파싱하니, 문서가 크면 그동안 서버 전체가 멈춘다.

JSON 모듈은 이걸 서버 안의 자료형으로 바꾼다. 문서가 문자열이 아니라 트리로 저장되고, 경로로 한 필드만 고치는 명령이 생긴다.

## 모듈은 서버 안에 명령과 자료형을 더한다

모듈은 Redis 4.0에서 들어온 확장 방식이다. C로 만든 공유 라이브러리(`.so`)를 서버가 시작할 때 불러오면, 그 안에서 새 명령과 새 자료형을 등록한다. 모듈이 할 수 있는 일은 대략 이렇다.

얼마나 간단한지 보려고 문자열 값을 서버 안에서 대문자로 바꾸는 명령 하나짜리 모듈을 직접 짰다. 헤더 파일 `redismodule.h`는 Redis 소스에 있는 것을 썼다.

```c
#include "redismodule.h"
#include <ctype.h>

/* HELLO.UPPER key : 서버 안에서 문자열 값을 대문자로 바꾼다 */
int UpperCmd(RedisModuleCtx *ctx, RedisModuleString **argv, int argc) {
  if (argc != 2) return RedisModule_WrongArity(ctx);
  RedisModule_AutoMemory(ctx);
  RedisModuleKey *key = RedisModule_OpenKey(ctx, argv[1], REDISMODULE_READ | REDISMODULE_WRITE);
  if (RedisModule_KeyType(key) != REDISMODULE_KEYTYPE_STRING)
    return RedisModule_ReplyWithError(ctx, "WRONGTYPE not a string");
  size_t len;
  char *buf = RedisModule_StringDMA(key, &len, REDISMODULE_WRITE); // 값의 메모리를 직접 연다
  for (size_t i = 0; i < len; i++) buf[i] = toupper((unsigned char)buf[i]);
  RedisModule_ReplicateVerbatim(ctx);                                // 레플리카와 AOF에도 그대로
  return RedisModule_ReplyWithLongLong(ctx, (long long)len);
}

int RedisModule_OnLoad(RedisModuleCtx *ctx, RedisModuleString **argv, int argc) {
  if (RedisModule_Init(ctx, "hello", 1, REDISMODULE_APIVER_1) == REDISMODULE_ERR) return REDISMODULE_ERR;
  return RedisModule_CreateCommand(ctx, "hello.upper", UpperCmd, "write fast", 1, 1, 1);
}
```

```bash
gcc -fPIC -shared -std=gnu99 -o hello.so hello.c                 # 공유 라이브러리로 빌드
redis-server --port 6399 --daemonize yes --save "" --loadmodule "$PWD/hello.so"
redis-cli -p 6399 SET greet "hi redis"
redis-cli -p 6399 HELLO.UPPER greet
redis-cli -p 6399 GET greet
redis-cli -p 6399 COMMAND INFO hello.upper
```

```text

hello.upper
-1
write
module
fast
1
1
1
```

새 명령이 기본 명령과 똑같이 등록됐다. `COMMAND INFO`는 앞부분만 옮겼는데, 플래그에 `module`이 붙는다. 같은 서버에서 `redis-cli -p 6399 JSON.SET x '$' '{}'`를 부르면 이렇게 나온다. 7.0.15 패키지에 JSON 모듈이 없다는 뜻이다.

```text
ERR unknown command 'JSON.SET', with args beginning with: 'x' '$' '{}'
```

실행 중인 서버에 `MODULE LOAD`로 올리는 것도 되지만, Redis 7.0부터는 `enable-module-command` 설정이 기본으로 `no`라서 막힌다. 설정 없이 시도하면 이렇게 거절된다.

```text
ERR MODULE command not allowed. If the enable-module-command option is set to "local", you can run it from a local connection, otherwise you need to set this option in the configuration file, and then restart the server.
```

이 기본값은 보안 때문이다. 모듈은 서버 프로세스 안에서 도는 네이티브 코드라서, 명령으로 아무 `.so`나 올릴 수 있으면 Redis에 접속한 사람이 서버에서 임의 코드를 실행할 수 있다. 운영에서는 설정 파일의 `loadmodule`로만 올린다. 인증 없이 열린 저장소가 어떻게 털리는지는 [MongoDB 보안](/posts/mongodb-security)의 첫 장면과 같은 이야기다.

모듈을 쓸 때 운영에서 알아 둘 것이 두 가지 있다. 첫째, 모듈이 죽으면 서버가 같이 죽는다. 같은 프로세스이기 때문이다. 둘째, 모듈이 등록한 자료형은 RDB와 AOF에 모듈의 형식으로 저장된다. 그 모듈 없이 서버를 띄우면 그 키가 든 RDB를 읽지 못해 시작에 실패한다. 버전을 올리거나 다른 배포판으로 옮길 때 모듈 버전과 RDB 호환성을 꼭 확인한다. 영속화와 재시작 흐름은 [Redis 영속화와 고가용성](/posts/redis-persistence-ha)에서 다뤘다.

## JSON: 경로로 한 필드만 고친다

JSON 모듈(예전 이름 RedisJSON)은 문서를 트리로 저장하고 JSONPath로 일부만 읽고 쓴다. 경로는 `$`로 시작하는 JSONPath 문법이 2.0부터 기본이고, 예전의 `.`로 시작하는 경로도 받는다. 아래는 공식 문서의 명령 형식이다.

```bash
# 문서를 넣는다
JSON.SET product:42 $ '{"id":42,"name":"무선 키보드","price":59000,"stock":17,"tags":["keyboard"],"options":{"colors":[{"name":"black","stock":10},{"name":"white","stock":7}]}}'

# 필요한 필드만 읽는다. $ 경로는 결과를 배열로 돌려준다
JSON.GET product:42 $.price $.stock

# 숫자를 서버에서 바로 줄인다 (원자적)
JSON.NUMINCRBY product:42 $.stock -1

# 중첩 배열 안의 특정 요소만 고친다
JSON.NUMINCRBY product:42 '$.options.colors[?(@.name=="white")].stock' -1

# 배열에 태그를 붙인다. 문자열 값은 JSON 문자열로 따옴표를 한 번 더 감싼다
JSON.ARRAPPEND product:42 $.tags '"sale"'
```

`JSON.NUMINCRBY`는 명령 하나라서 앞에서 본 갱신 손실이 생기지 않는다. 필터 식(`?(@.name=="white")`)으로 배열 안 요소를 골라 고칠 수 있다는 게 해시와의 큰 차이다. 경로가 여러 곳에 맞으면 맞는 곳마다 적용되고 결과도 배열로 온다. 경로가 하나도 맞지 않으면 오류가 아니라 빈 배열이 오니, 오타 난 경로를 조용히 넘기지 않게 응답을 확인한다.

DB에서 바뀐 필드 몇 개만 캐시에 반영하고 싶을 때는 `JSON.MERGE`(JSON 모듈 2.6부터)가 편하다. 넘긴 객체의 필드만 덮어쓰고 나머지는 그대로 두며, 값을 `null`로 주면 그 필드를 지운다.

```bash
JSON.MERGE product:42 $ '{"price":55000,"badge":"sale","desc":null}'
```

메모리는 공짜가 아니다. 트리로 저장하면 노드마다 포인터와 타입 정보가 붙어서, 같은 내용을 문자열로 넣을 때보다 메모리를 더 쓰는 경우가 많다. 문서를 통째로만 읽고 쓰는 캐시라면 문자열이 더 싸다. 부분 수정과 부분 읽기, 그리고 아래의 검색 인덱스가 필요할 때 JSON을 고른다.

## 검색: 키를 훑지 않고 필드로 찾는다

Redis 키는 이름으로만 찾는다. "가격이 6만 원 이하인 무선 키보드"를 찾으려면 `SCAN`으로 키를 다 훑으며 하나씩 읽어야 한다. 검색 모듈(RediSearch, Redis 8에서는 Redis Query Engine)은 해시나 JSON 키 위에 보조 인덱스를 만든다.

```bash
# product: 로 시작하는 JSON 키를 인덱싱한다
FT.CREATE idx:product ON JSON PREFIX 1 product: SCHEMA
  $.name AS name TEXT
  $.price AS price NUMERIC SORTABLE
  $.tags[*] AS tags TAG

# 태그와 범위로 찾고 가격순 정렬
FT.SEARCH idx:product "@tags:{wireless} @price:[0 60000]" SORTBY price ASC LIMIT 0 10

# 인덱스 상태와 크기
FT.INFO idx:product
```

동작에서 알아 둘 점이 있다. 인덱스는 쓰기와 같은 순간에 갱신된다. `JSON.SET`이 끝나면 바로 다음 `FT.SEARCH`에서 보인다. Elasticsearch처럼 새로고침 주기를 기다리지 않는다. 반대로 이미 키가 많은 상태에서 `FT.CREATE`를 하면 기존 키는 백그라운드에서 훑으며 채우니, 그동안은 결과가 일부만 나온다. `FT.INFO`의 인덱싱 진행률을 보고 끝난 뒤에 쓴다.

필드 종류를 고르는 것도 중요하다. `TEXT`는 토큰으로 쪼개 전문 검색을 하고, `TAG`는 쪼개지 않고 값 그대로 일치만 본다. 상품 코드나 카테고리를 `TEXT`로 만들면 하이픈에서 쪼개져 엉뚱하게 맞는다. 한국어는 형태소 분석기가 없어서, 공백 단위로 쪼개는 것 이상을 기대하기 어렵다. "키보드를"로는 "키보드"가 안 맞는다. 한국어 전문 검색이 중요하면 nori 분석기가 있는 Elasticsearch로 가는 게 맞고, 역색인이 어떻게 동작하는지는 [Elasticsearch와 역색인](/posts/elasticsearch-inverted-index)에 있다.

벡터 검색도 같은 인덱스 안에서 된다. 임베딩을 필드로 넣고 HNSW나 FLAT 인덱스를 만든 뒤 KNN으로 묻는다.

```bash
FT.CREATE idx:doc ON HASH PREFIX 1 doc: SCHEMA
  title TEXT
  category TAG
  vec VECTOR HNSW 6 TYPE FLOAT32 DIM 384 DISTANCE_METRIC COSINE

# category가 manual인 것 중에서 가장 가까운 5개 (vec 파라미터는 float32 바이트열)
FT.SEARCH idx:doc "(@category:{manual})=>[KNN 5 @vec $q AS score]" PARAMS 2 q "<bytes>" SORTBY score DIALECT 2
```

캐시와 벡터 검색을 한 곳에서 하니 RAG 시제품을 빨리 만들 수 있다. 다만 벡터 384차원 float32 하나가 1.5KB이고 HNSW 그래프가 그 위에 더 붙는다. 벡터 100만 개면 원본만 1.5GB다. 모두 메모리에 있어야 한다는 점을 계산에 넣는다. 벡터 인덱스 자체의 원리는 [벡터 DB](/posts/vector-db)에서 다뤘다.

## 시계열: 보존 기간과 다운샘플링

센서 값이나 초당 요청 수를 정렬된 셋에 넣는 경우가 많다. 그러면 오래된 데이터를 지우는 일, 1분 평균을 만드는 일을 앱이 해야 한다. 시계열 모듈(RedisTimeSeries)은 이걸 자료형 안에 넣었다.

```bash
# 원본은 하루(밀리초)만 두고, 같은 타임스탬프가 오면 마지막 값으로 덮는다
TS.CREATE temp:room1 RETENTION 86400000 DUPLICATE_POLICY LAST LABELS room 1 kind temp
# 1시간 평균을 따로 모을 키. 보존 기간은 90일
TS.CREATE temp:room1:1h RETENTION 7776000000 LABELS room 1 kind temp agg 1h
TS.CREATERULE temp:room1 temp:room1:1h AGGREGATION avg 3600000

TS.ADD temp:room1 * 23.5                          # *는 서버 현재 시각
TS.RANGE temp:room1 - + AGGREGATION max 60000     # 1분마다 최댓값
TS.MRANGE - + FILTER kind=temp agg=1h             # 라벨로 여러 키를 한 번에
```

원본은 하루 뒤에 지워지고, 1시간 평균만 90일 남는다. 값은 청크 단위로 압축되어 저장되어 정렬된 셋보다 훨씬 작다. 실수하기 쉬운 곳은 `TS.CREATERULE`이 규칙을 만든 뒤 들어온 값에만 적용된다는 점이다. 이미 쌓인 원본으로 과거 1시간 평균을 채워 주지 않는다. 규칙은 데이터를 넣기 전에 만든다.

## 확률적 자료구조: 블룸, 쿠쿠, Top-K, Count-Min

확률 모듈(RedisBloom)은 조금 틀려도 되는 질문에 아주 적은 메모리로 답하는 구조들을 묶었다.

```bash
BF.RESERVE seen:urls 0.001 1000000     # 거짓 양성 0.1%, 100만 개 예상
BF.ADD seen:urls /posts/redis-modules-stack
BF.EXISTS seen:urls /posts/unknown     # 0이면 확실히 없다, 1이면 아마 있다

CF.RESERVE seen:coupons 1000000        # 쿠쿠 필터: 지울 수 있다
CF.ADD seen:coupons C-1234
CF.DEL seen:coupons C-1234

TOPK.RESERVE hot:products 10 2000 7 0.925   # 상위 10개, 폭 2000, 깊이 7, 감쇠
TOPK.ADD hot:products p42 p7 p42
TOPK.LIST hot:products

CMS.INITBYPROB views 0.001 0.01        # 오차 0.1%, 그 오차를 넘을 확률 1%
CMS.INCRBY views /posts/a 1
CMS.QUERY views /posts/a
```

블룸 필터는 "없다"는 확실하고 "있다"는 가끔 틀리며, 지울 수 없다. 쿠쿠 필터는 지울 수 있는 대신 꽉 차면 넣기가 실패할 수 있다. Count-Min은 개수를 더 세는 쪽으로만 틀리고, Top-K는 그 위에서 자주 나오는 것 몇 개만 추린다. 각 구조의 원리와 크기 고르는 법은 [블룸 필터](/posts/bloom-filter)와 [Count-Min Sketch](/posts/count-min-sketch)에 따로 썼으니, 여기서는 Redis 안에서 키 하나로 쓸 수 있다는 점만 짚는다. 여러 앱 서버가 같은 필터를 공유해야 할 때 특히 쓸모 있다.

## Redis 8에서 달라진 것

예전에는 이 모듈들을 쓰려면 Redis Stack이라는 별도 배포판을 받거나, 모듈을 따로 빌드해 `loadmodule`로 올려야 했다. 모듈들의 라이선스도 Redis 코어와 달랐다. 2025년에 나온 Redis 8은 이걸 정리했다. JSON, 시계열, 확률적 자료구조, 검색(Query Engine)이 Redis Open Source 배포에 기본으로 들어갔고, 벡터 셋(vector set)이라는 새 자료형도 추가됐다. 라이선스는 기존 RSALv2·SSPLv1에 AGPLv3를 고를 수 있는 선택지가 더해졌다. Redis Stack은 7.4가 마지막이고 Redis 8로 흡수됐다.

그래서 이제 "Redis에 JSON이 되나"의 답은 버전과 배포판에 따라 다르다. 공식 Redis 8 이미지나 바이너리에는 들어 있다. 이 글에서 본 것처럼 Ubuntu 24.04 기본 패키지(7.0.15)에는 없다. 관리형 서비스는 서비스마다 지원하는 모듈과 명령이 다르다. 접속해서 `MODULE LIST`(또는 `INFO modules`)로 확인하는 습관을 들인다.

## Valkey로 가면 무엇이 남나

2024년 라이선스 변경으로 갈라진 Valkey는 Redis 7.2.4에서 출발했고, Redis Stack 모듈은 가져오지 않았다. 대신 자체 모듈을 만들고 있다. valkey-json은 RedisJSON의 명령과 호환되도록 만들었고, valkey-bloom은 `BF.*` 명령을 Rust로 다시 구현했고, valkey-search는 벡터 검색부터 시작했다. 이것들을 묶은 valkey-bundle 이미지도 있다. 시계열에 해당하는 공식 모듈은 내가 확인한 범위에서는 아직 없다.

옮길 때 확인할 것은 세 가지다. 쓰는 명령과 옵션이 모두 있는지(특히 `FT.*`의 전문 검색 문법과 집계), 모듈 자료형이 든 RDB를 상대 쪽 모듈이 읽을 수 있는지, 관리형 서비스에서 그 모듈을 켤 수 있는지. 둘 사이의 코어 차이와 옮기는 순서는 [Valkey와 Redis](/posts/valkey-vs-redis)에 따로 정리했다.

## 모듈을 쓰다 만나는 장애

모듈을 붙인 뒤에 생기는 문제는 대개 "한쪽에만 있다"와 "생각보다 크다"에서 온다.

먼저 레플리카와 새 노드다. 프라이머리에만 모듈이 있고 레플리카에는 없으면, 전체 동기화 때 레플리카가 프라이머리의 RDB를 받아 읽다가 모듈 자료형에서 멈춘다. 레플리카 로그에 모듈 자료형을 모른다는 오류가 남고 복제가 계속 다시 시작된다. 모든 노드의 `MODULE LIST` 결과가 같은지(이름과 버전까지) 배포 전에 맞춘다.

```bash
# 노드마다 모듈 이름과 버전을 찍어 비교한다
for h in 10.0.1.11 10.0.1.12 10.0.1.13; do
  echo "== $h"; redis-cli -h "$h" MODULE LIST | paste - - - - - - - - | cut -f1-4
done
```

다음은 메모리다. `INFO memory`의 `used_memory`는 모듈이 잡은 메모리까지 합친 값이라, 키 개수는 그대로인데 메모리만 늘었다면 검색 인덱스를 의심한다. 인덱스별 크기는 `FT.INFO`의 역색인·벡터 인덱스 크기 항목으로 따로 본다. 인덱스에 필드를 하나 더하면 키마다 그만큼 인덱스가 붙으니, 쓰지 않는 필드는 스키마에서 뺀다.

마지막은 느린 질의다. 검색 명령도 이벤트 루프에서 돈다. `FT.SEARCH idx "*"`처럼 모든 문서를 맞추는 질의, 결과가 수십만 건인 `SORTBY`, 큰 `FT.AGGREGATE`는 그동안 다른 명령을 세운다. `SLOWLOG GET`에 `FT.` 명령이 보이면 `LIMIT`을 걸었는지, 필터를 태그·숫자 필드로 먼저 좁혔는지 확인한다. 검색 모듈은 질의를 별도 스레드에서 돌리는 설정도 있지만 버전마다 이름과 기본값이 다르니 문서를 보고 켠다.

## 어디까지 Redis 안에서 끝낼까

모듈 덕분에 Redis 하나로 캐시, 문서 저장소, 검색, 시계열, 중복 거르기를 다 할 수 있다. 그래도 전부 Redis로 하는 게 늘 좋은 건 아니다. 판단 기준은 대개 메모리, 클러스터, 기능 깊이 셋이다.

메모리부터 본다. Redis는 모든 데이터와 인덱스를 메모리에 둔다. 검색 인덱스는 원본 크기에 맞먹거나 더 커질 수 있고, 시계열을 몇 달씩 쌓으면 금방 수십 GB가 된다. 메모리가 차면 [eviction 정책](/posts/redis-memory-eviction)에 따라 키가 지워지는데, 검색 인덱스가 걸린 키가 캐시처럼 지워지면 검색 결과도 사라진다. 원본이 따로 없는 데이터를 이런 정책 아래에 두면 안 된다.

클러스터에서는 키가 해시 슬롯으로 여러 샤드에 흩어진다. 검색 인덱스는 샤드마다 그 샤드에 있는 키만 담는다. 그래서 전체를 대상으로 찾으려면 모든 샤드에 묻고 결과를 합치는 조정 단계가 필요하다. 이 조정 기능을 쓸 수 있는지는 배포판과 버전마다 다르니 도입 전에 확인한다. 여러 키를 한 번에 다루는 명령은 같은 슬롯 안에서만 되는 제약도 그대로 남는다. 슬롯 구조는 [Redis Cluster](/posts/redis-cluster)에서 다뤘다.

기능 깊이도 본다. 한국어 형태소 분석, 복잡한 집계, 관련도 튜닝이 필요하면 Elasticsearch나 OpenSearch가 낫다. 시계열을 몇 년치 보관하면서 SQL로 다른 테이블과 조인해야 하면 TimescaleDB, 지표 수집과 경보가 목적이면 Prometheus 계열이 낫다.

정리하면 이렇게 고른다. 데이터의 원본은 DB에 있고 Redis에는 빠르게 읽을 복사본을 둔다. 그 복사본 위에서 부분 수정, 필드 검색, 짧은 기간 시계열, 중복 거르기를 하는 것까지는 Redis 모듈이 아주 잘 맞는다. 데이터가 메모리에 다 들어가지 않거나, 질의가 점점 복잡해지거나, Redis가 원본이 되어 가기 시작하면 전용 저장소로 옮길 때다.

## 면접에서 나올 만한 질문

### JSON 문자열을 GET/SET으로 고치면 무엇이 문제인가요?

`GET`과 `SET`은 각각 원자적이지만 그 사이에 다른 클라이언트가 끼어들 수 있어서 갱신 손실이 생긴다. 실제로 두 프로세스가 500번씩 재고를 줄였을 때 1000이 아니라 600번 남짓만 반영됐다. 문서가 크면 매번 전체를 주고받는 비용도 크다. 해시와 `HINCRBY`, `WATCH`/`MULTI`, Lua, 또는 JSON 모듈의 `JSON.NUMINCRBY`처럼 서버 안에서 한 번에 고치는 방법을 쓴다.

### Redis 모듈은 무엇이고 어떤 위험이 있나요?

서버 프로세스 안에 불러오는 네이티브 공유 라이브러리로, 새 명령과 자료형, RDB·AOF 저장 콜백, 이벤트 구독을 등록한다. 같은 프로세스라서 모듈이 죽으면 서버도 죽고, 아무 모듈이나 올릴 수 있으면 임의 코드 실행이 되므로 7.0부터 `MODULE LOAD`가 기본으로 막혀 있다. 모듈 자료형이 든 RDB는 그 모듈 없이 읽지 못하니 버전 업과 이전 때 호환성을 확인한다.

### 해시 대신 JSON 모듈을 쓰는 건 언제인가요?

중첩 구조나 배열 안 요소를 부분적으로 읽고 고쳐야 하거나, JSON 필드로 검색 인덱스를 만들 때다. 필드가 한 단계뿐이면 해시가 더 단순하고 메모리도 적다. 문서를 통째로만 읽고 쓰는 캐시라면 문자열이 가장 싸다.

### Redis 검색과 Elasticsearch는 어떻게 고르나요?

Redis 검색은 쓰기와 동시에 인덱스가 갱신되고 지연이 아주 짧지만, 모든 것을 메모리에 두고 한국어 형태소 분석 같은 깊은 기능이 없다. 이미 Redis에 있는 데이터를 필드와 태그, 범위로 빠르게 찾는 데는 잘 맞는다. 데이터가 크거나 한국어 전문 검색, 복잡한 집계, 관련도 튜닝이 필요하면 Elasticsearch로 간다.

### 클러스터에서 검색 인덱스는 어떻게 동작하나요?

키가 해시 슬롯으로 샤드에 흩어지고 인덱스는 샤드마다 그 샤드의 키만 담는다. 전체를 검색하려면 모든 샤드에 묻고 합치는 조정 단계가 필요하고, 이 기능을 쓸 수 있는지는 배포판과 버전에 따라 다르다. 그래서 클러스터 도입 전에 검색이 샤드 전체에 걸쳐 동작하는지 확인해야 한다.

### Redis 8에서 무엇이 바뀌었나요?

Redis Stack으로 따로 나오던 JSON, 시계열, 확률적 자료구조, 검색이 Redis Open Source 기본 배포에 들어갔고 벡터 셋 자료형이 추가됐다. 라이선스에 AGPLv3 선택지도 더해졌다. 다만 배포판 패키지나 관리형 서비스는 그대로가 아닐 수 있어서 `MODULE LIST`로 확인한다.

### Valkey로 옮기면 모듈은 어떻게 되나요?

Valkey는 Redis Stack 모듈을 가져오지 않고 valkey-json, valkey-bloom, valkey-search를 따로 만들었다. 명령은 호환을 목표로 하지만 옵션과 문법이 다 같다고 가정하면 안 되고, 시계열 모듈은 아직 없다. 쓰는 명령 목록, 모듈 자료형 RDB 호환, 관리형 서비스 지원 여부를 먼저 확인한다.
