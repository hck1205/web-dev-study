재고 서비스가 배포 중에 20초쯤 503을 냈다. 배포는 끝났고 인스턴스도 다 떴는데, 대시보드를 보면 재고 서비스로 들어오는 요청이 평소의 수십 배다. 새로 뜬 인스턴스는 그 양을 못 버티고 다시 503을 내고, 503은 또 요청을 부른다. 원인은 이미 사라졌는데 장애가 혼자 굴러간다. 들여다보면 브라우저, 게이트웨이, 주문 서비스가 저마다 "실패하면 세 번까지 다시 보낸다"를 켜 두었다.

재시도는 일시적인 실패를 사용자 몰래 덮어 주는 좋은 도구다. 그런데 어떤 실패를, 몇 번, 어느 계층에서 다시 보낼지를 정하지 않으면 위처럼 장애를 키우는 쪽으로 돈다. 이 글은 다시 보내도 되는 실패를 가르는 기준, 계층이 겹칠 때 재시도가 몇 배로 불어나는지(직접 쟀다), 그걸 막는 재시도 예산, 그리고 실패하기 전에 미리 한 번 더 보내는 헤징까지 다룬다. 실습은 Node 22와 nginx 1.24로 했다.

이 주제의 다른 글: 재시도가 어떤 장애 대응 도구들 사이에 있는지는 [장애가 번지지 않게](/posts/resilience-patterns)에서, 기다리는 시간의 한도는 [타임아웃](/posts/timeouts)에서, 다시 보내기 전에 얼마나 쉴지는 [지수 백오프와 지터](/posts/exponential-backoff-jitter)에서 다룬다.

## 실패했다는 말에는 세 가지 뜻이 있다

클라이언트가 받는 "실패"는 요청이 어디까지 갔는지에 따라 뜻이 다르다. 요청이 서버에 닿지도 못했을 수 있고, 서버가 거절했을 수 있고, 서버는 처리했는데 응답만 못 받았을 수도 있다. 다시 보내도 되는지는 이 셋 중 무엇인지에 달려 있다.

같은 POST를 실패 모양별로 보내 Node `fetch`가 무엇을 던지는지 봤다.

```text
refused (nobody listening)   -> TypeError: fetch failed (cause: ECONNREFUSED)
reset after request sent     -> TypeError: fetch failed (cause: UND_ERR_SOCKET)
timeout 1s                   -> TimeoutError: The operation was aborted due to timeout
503 Retry-After              -> HTTP 503 retry-after=2
```

첫 줄만 확실히 안전하다. 둘째 줄은 서버가 요청을 다 읽은 뒤 연결을 끊은 경우이고, 셋째 줄은 서버가 3초 걸려 처리하는 동안 클라이언트가 1초 만에 포기한 경우다. 둘 다 서버 쪽에서는 일이 끝났을 수 있다. 연결 끊김 에러는 요청을 보내기 전에 끊긴 경우와 보낸 뒤에 끊긴 경우가 같은 모양으로 올 때가 많아서, 에러만 보고 "안 닿았다"고 단정하지 않는다.

## 다시 보내도 되는 실패 고르기

400, 401, 403, 404, 409, 422 같은 4xx는 요청 자체가 잘못된 것이라 백 번 보내도 같다. 예외는 429(너무 많이 보냄)와 408(요청 타임아웃) 정도다. 5xx 중에서도 501(구현 안 됨)은 영구적인 실패다. 500은 애매하다. 일시적인 버그일 수도 있고 특정 입력에서 늘 터지는 버그일 수도 있는데, 후자라면 재시도는 같은 예외 로그만 세 배로 만든다.

멱등성은 HTTP 메서드의 정의에서 출발한다. GET, HEAD, PUT, DELETE, OPTIONS는 여러 번 보내도 한 번 보낸 것과 결과 상태가 같도록 정의돼 있고, POST와 PATCH는 그렇지 않다. 자세한 정의는 [HTTP 메서드](/posts/http-methods) 글에 있다. 다만 정의는 약속일 뿐이다. `GET /coupons/claim`처럼 GET으로 상태를 바꾸는 API를 만들었다면 그 GET은 재시도하면 안 된다.

## 타임아웃 난 POST를 다시 보내면

멱등하지 않은 요청을 재시도하면 어떻게 되는지 직접 봤다. 주문을 받자마자 저장하고 응답은 1.5초 뒤에 주는 서버에, 1초 타임아웃으로 세 번까지 보내는 클라이언트를 붙였다.

```text
  attempt 1: TimeoutError
  attempt 2: TimeoutError
  attempt 3: TimeoutError
without key: gave up
  orders created: 3
```

클라이언트는 실패라고 판단했는데 주문은 세 개가 생겼다. 사용자 화면에는 "주문 실패"가 떴고, 다시 누르면 네 번째 주문이 생긴다. 같은 클라이언트에 `Idempotency-Key` 헤더를 붙이고, 서버가 처음 본 키일 때만 주문을 만들게 하면 이렇게 바뀐다.

```text
  attempt 1: TimeoutError
with Idempotency-Key: attempt 2: 200 {"id":1}
  orders created: 1
```

이 실습의 서버는 키를 메모리 맵에 넣는 가장 단순한 구현이다. 같은 키의 요청 두 개가 동시에 들어올 때, 처리 도중 서버가 죽었을 때, 키 저장과 주문 저장을 한 트랜잭션에 묶는 방법까지는 [멱등성 키 구현](/posts/idempotency-key) 글에서 다룬다. 여기서 가져갈 규칙은 하나다. 결과를 모르는 실패를 다시 보내려면 그 요청이 멱등해야 하고, 멱등하지 않다면 키로 멱등하게 만든 다음에 재시도를 켠다.

## 계층마다 세 번이면 맨 아래는 스물일곱 번

재시도가 위험해지는 건 계층이 겹칠 때다. 브라우저 → 게이트웨이 → 주문 → 재고로 이어지는 사슬에서 각 계층이 "최대 3번 시도"를 켰다고 하자. 맨 아래 재고 서비스가 계속 503을 내면 요청 하나가 재고에 몇 번 닿을까. Node로 네 계층을 띄우고 셌다.

```text
mode=every attempts(client,gateway,order)=3,3,3 -> status 503
requests seen: gateway=3 order=9 inventory=27
```

사용자의 클릭 한 번이 재고 서비스에 27번 닿았다. 계층이 하나 더 있으면 81번이다. 아래 그림에서 다음을 누르면 숫자가 불어나는 순서를 따라간다.

이 증폭이 무서운 이유는 아픈 서비스를 정확히 겨냥한다는 점이다. 재고 서비스가 과부하로 503을 내기 시작하면, 그 503이 27배의 요청을 불러와 과부하를 더 키운다. 원인이 사라져도 재시도 트래픽만으로 처리 용량을 넘는 상태가 이어질 수 있다. 처음 장애를 일으킨 원인 없이 부하만으로 버티는 이런 상태를 준안정 장애(metastable failure)라고 부른다. 글 첫머리의 "배포는 끝났는데 장애가 안 끝난다"가 이 모양이다.

막는 원칙은 재시도를 한 곳에서만 하는 것이다. 보통은 실패한 호출 바로 위, 실패 원인을 가장 잘 아는 계층이다. 다른 계층의 재시도를 끄기 어렵다면 "아래에서 이미 다시 보내 봤다"는 신호를 위로 올린다. 실습에서는 재시도를 다 쓰고 실패한 계층이 응답에 `x-no-retry: 1`을 붙이고, 위 계층은 그 헤더를 보면 다시 보내지 않게 했다. 세 계층 모두 여전히 "3번 시도"로 설정된 상태다.

```text
mode=no-retry-signal attempts(client,gateway,order)=3,3,3 -> status 503
requests seen: gateway=1 order=1 inventory=3
```

27이 3이 됐다. gRPC에는 이 신호가 표준으로 있다. 서버가 응답 트레일러에 `grpc-retry-pushback-ms`를 음수로 넣으면 클라이언트는 다시 보내지 않고, 양수를 넣으면 그만큼 기다렸다가 보낸다.

## 재시도 예산으로 폭주를 막는다

계층을 정리해도 한 계층 안의 문제가 남는다. "요청마다 최대 3번 재시도"는 평소에는 무해하지만, 상대가 완전히 죽으면 모든 요청이 4번씩 나가서 부하가 정확히 4배가 된다. 그래서 횟수 제한에 더해 전체 비율 제한을 건다. 원래 요청의 10%까지만 재시도에 쓴다는 식이다. Google SRE 책이 권하는 방식도 요청당 3회 제한과 클라이언트 전체 10% 비율의 조합이다.

예산은 보통 토큰 통으로 구현한다. 원래 요청이 하나 나갈 때마다 토큰 0.1개를 쌓고, 재시도 하나에 토큰 1개를 쓴다. 토큰이 없으면 재시도하지 않고 바로 실패한다.

이 장치는 이미 여러 도구에 들어 있다. gRPC의 `retryThrottling`(`maxTokens`, `tokenRatio`)이 위와 거의 같은 토큰 통이고, Envoy는 클러스터 설정의 `retry_budget`(`budget_percent`, 기본 20%)로 지금 진행 중인 요청 대비 재시도 비율을 묶는다. AWS SDK의 standard 재시도 모드에도 재시도마다 토큰을 쓰는 할당량이 있다.

## 프록시가 대신 다시 보낼 때

재시도는 코드에만 있지 않다. nginx, Envoy, 서비스 메시, 클라우드 로드 밸런서도 실패하면 다른 백엔드로 다시 보낸다. 앱이 재시도를 끈 줄 알았는데 증폭이 남아 있다면 대개 이쪽이다. nginx는 `proxy_next_upstream error timeout`이 기본값이라, 연결 오류나 타임아웃이 나면 같은 요청을 다음 서버로 넘긴다.

업스트림 두 대를 두고, 첫 번째(a)는 요청을 다 읽은 뒤 응답 없이 연결을 끊게 했다. 두 번째(b)는 정상이다. 로그에 `$upstream_addr`와 `$upstream_status`를 남기면 nginx가 몇 번 시도했는지 보인다.

```nginx
upstream app {
    server 127.0.0.1:18761 max_fails=0;   # a: 요청을 읽고 끊는다 (실습에서 빠지지 않게 max_fails=0)
    server 127.0.0.1:18762;               # b: 정상
}
location / {
    proxy_next_upstream error timeout;    # 기본값과 같다
    proxy_pass http://app;
}
```

```text
GET 200 upstreams="127.0.0.1:18761, 127.0.0.1:18762" statuses="502, 200"
POST 502 upstreams="127.0.0.1:18761" statuses="502"
```

GET은 a에서 끊기자 b로 넘어가 200이 됐다. 사용자는 실패를 모른다. POST는 a에서 끊긴 그대로 502다. nginx 1.9.13부터 POST, LOCK, PATCH처럼 멱등하지 않은 요청은 이미 업스트림에 보낸 뒤라면 다음 서버로 넘기지 않는다. 오류 로그에는 두 경우 모두 같은 줄이 찍힌다.

```text

```

## 느린 요청 하나를 두 번 보내는 헤징

지금까지는 실패한 뒤에 다시 보내는 이야기였다. 헤징(hedging)은 실패를 기다리지 않는다. 요청을 보내고 일정 시간 안에 응답이 없으면 같은 요청을 다른 서버에 한 번 더 보내고, 먼저 온 응답을 쓰고 나머지는 취소한다. 대부분의 요청은 빠른데 일부만 GC 멈춤이나 느린 디스크에 걸려 오래 걸리는 서비스에서, 그 느린 꼬리를 잘라 내는 방법이다.

헤징은 조건이 맞을 때만 쓴다. 요청이 멱등해야 한다(대개 읽기). 느림이 서버 하나의 사정이어야 한다. 모든 서버가 과부하로 느린 상황이라면 헤징은 부하만 늘려 상황을 더 나쁘게 만든다. 그래서 헤징 요청에도 재시도 예산 같은 상한을 둔다. gRPC는 `hedgingPolicy`(`maxAttempts`, `hedgingDelay`)로 이를 설정하고, 재시도 정책과 한 메서드에 함께 쓸 수는 없다.

## 재시도가 장애를 키우고 있다는 신호

재시도 문제는 대시보드의 숫자 차이로 먼저 보인다.

- 하위 서비스가 받는 요청 수가 상위 서비스가 받는 요청 수보다 몇 배 많다. 정상이라면 비율이 거의 일정하다. 장애 때 이 비율이 3배, 9배로 튄다면 계층 재시도가 겹친 것이다.
- 원인을 고쳤는데 에러율이 안 내려간다. 재시도 트래픽만으로 용량을 넘고 있다. 이때는 재시도를 줄이는 쪽이 먼저다. 앞단에서 요청 일부를 버리거나(부하 차단), 기능 플래그로 재시도를 끄거나, 인스턴스를 넉넉히 늘려 한 번 고비를 넘긴다.
- 같은 주문, 같은 결제가 두 번 생겼다는 문의가 온다. 결과를 모르는 실패를 멱등성 없이 재시도한 곳이 있다. 앱 코드뿐 아니라 프록시의 `non_idempotent` 설정, HTTP 클라이언트의 전역 재시도 옵션까지 본다.

재시도는 지표로 남긴다. 요청마다 몇 번째 시도인지를 로그와 트레이스에 붙이고(`attempt=2`), 재시도 비율(재시도 수 / 원래 요청 수)을 그래프로 본다. 평소 이 비율이 1% 안쪽이면 재시도가 일시적 오류를 잘 덮어 주고 있는 것이고, 갑자기 오르면 그 자체가 장애 신호다. 재시도 덕분에 사용자는 에러를 못 봤더라도, 재시도 비율이 오르는 건 하위 서비스가 아프다는 뜻이다.

재시도는 일시적인 실패에만 듣는 약이다. 다시 보내도 결과가 달라질 수 있는 실패인지, 다시 보내도 부작용이 없는지, 그리고 이 재시도가 다른 계층의 재시도와 곱해지지 않는지를 확인하고 켠다. 다시 보내기 전에 얼마나 기다릴지는 다음 글 [지수 백오프와 지터](/posts/exponential-backoff-jitter)에서 이어진다.

## 면접에서 나올 만한 질문

### 어떤 실패를 재시도해야 하나

결과가 달라질 수 있고 부작용이 없는 실패만 다시 보낸다. 연결 거절, 503, 429처럼 서버가 일을 시작하기 전에 실패한 경우는 대개 안전하다. 타임아웃, 연결 끊김, 502·504처럼 처리됐는지 모르는 실패는 멱등한 요청이거나 멱등성 키가 있을 때만 다시 보낸다. 429를 뺀 4xx는 다시 보내도 같으니 재시도하지 않는다.

### POST 요청이 타임아웃 났다. 다시 보내도 되나

그대로는 안 된다. 서버가 이미 처리했는데 응답만 늦은 것일 수 있어서 다시 보내면 주문이나 결제가 두 번 생긴다. 실습에서도 1초 타임아웃으로 세 번 보내자 주문이 세 개 만들어졌다. 클라이언트가 작업마다 멱등성 키를 만들어 같은 키로 재시도하고, 서버가 처음 보는 키일 때만 처리하게 해야 안전하다.

### 여러 계층이 각자 재시도하면 무슨 일이 생기나

시도 횟수가 곱해진다. 세 계층이 각자 세 번씩 시도하면 맨 아래 서비스는 요청 하나에 27번 불리고, 실습에서도 정확히 27번이 나왔다. 하필 아픈 서비스에 부하가 몰려 회복을 막고, 원인이 사라져도 재시도 부하만으로 장애가 이어지는 준안정 상태가 될 수 있다. 재시도는 한 계층에서만 하고, 다른 계층에는 "이미 재시도했다"는 신호를 올려 보낸다.

### 재시도 예산은 무엇이고 횟수 제한과 무엇이 다른가

횟수 제한은 요청 하나에 대한 한도이고, 재시도 예산은 전체 트래픽에서 재시도가 차지할 수 있는 비율의 한도다. 횟수 제한만 있으면 하위 서비스가 완전히 죽었을 때 모든 요청이 최대 횟수만큼 나가 부하가 몇 배가 된다. 예산은 원래 요청마다 토큰을 조금씩 쌓고 재시도마다 토큰을 써서, 장애 때 재시도 양을 원래 요청의 10% 정도로 묶는다. 시뮬레이션에서 성공 건수는 같으면서 장애 중 부하가 4배에서 1.1배로 줄었다.

### nginx 같은 프록시도 재시도를 하나

한다. nginx는 기본으로 연결 오류와 타임아웃이 나면 다음 업스트림 서버로 요청을 넘긴다(`proxy_next_upstream error timeout`). 다만 1.9.13부터는 POST처럼 멱등하지 않은 요청을 이미 보낸 뒤라면 넘기지 않는다. 앱 재시도와 프록시·메시 재시도가 겹치면 증폭이 생기니, 계층별 재시도 설정을 함께 확인해야 한다.

### 요청 헤징은 언제 쓰고 위험은 무엇인가

대부분 빠르고 일부만 서버 사정으로 느린 멱등한 읽기 요청에서, p99 같은 꼬리 지연을 줄이려고 쓴다. 일정 시간(보통 p95 근처) 안에 답이 없으면 다른 서버에 한 번 더 보내고 먼저 온 응답을 쓴 뒤 나머지를 취소한다. 실습에서는 요청을 3% 더 보내고 p99를 301ms에서 36ms로 줄였다. 모든 서버가 과부하로 느릴 때는 부하만 늘리니 상한을 둔다.

### 재시도가 잘 동작하는지는 무엇으로 보나

재시도 비율과 계층 사이 요청 수 비율을 본다. 평소 재시도 비율이 낮게 유지되다가 갑자기 오르면 하위 서비스가 아프다는 신호다. 하위 서비스가 받는 요청이 상위보다 몇 배 많아지면 재시도가 겹친 것이다. 로그와 트레이스에 몇 번째 시도인지 남겨 두면 중복 처리 문의가 왔을 때 원인을 바로 찾을 수 있다.
