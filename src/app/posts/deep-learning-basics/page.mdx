LLM 글을 읽다 보면 "학습", "가중치", "역전파", "GPU 메모리" 같은 말이 계속 나온다. [LLM 기초 글](/posts/llm-basics-for-developers)이나 [트랜스포머 글](/posts/transformer-attention-kv-cache)은 이미 학습이 끝난 모델을 쓰는 쪽에서 출발한다. 그런데 파인튜닝을 해 보려고 하면 이야기가 달라진다. 학습률을 얼마로 줄지, 배치 크기는 몇으로 할지, 왜 추론은 GPU 하나로 되는데 학습은 메모리가 부족하다고 하는지를 알아야 한다.

나도 처음엔 이 단어들이 따로 노는 개념처럼 느껴졌다. 막상 작은 신경망 하나를 직접 짜 보면 전부 한 반복문 안에 들어 있다. 이 글은 손글씨 숫자를 맞히는 아주 작은 신경망을 하나 만들고, 그 반복문을 한 바퀴씩 따라간다. 학습률, 배치 크기, 에폭을 바꿔 가며 실제로 돌린 숫자를 보고, 그다음 GPU가 왜 빠른지, 메모리가 왜 모자라는지, PyTorch와 TensorFlow가 어떻게 다른지를 개발자 입장에서 정리한다.

이 글의 실험 숫자는 scikit-learn에 들어 있는 8×8 손글씨 숫자 데이터(1,797장)로 얻었다. 같은 구조의 신경망을 NumPy로 직접 구현해 CPU에서 돌렸다. PyTorch 코드는 같은 일을 하는 코드로 함께 보여 주지만, 초기값을 정하는 방식이 달라서 숫자가 그대로 같지는 않다.

## 규칙을 적는 대신 숫자를 고친다

8×8 픽셀짜리 숫자 그림 한 장은 0~16 밝기 값 64개다. 이걸 보고 "3"이라고 말하는 규칙을 손으로 적는다고 해 보자. 위쪽에 곡선이 있고, 가운데가 들어가고, 아래에 또 곡선이 있고… 사람마다 쓰는 모양이 다르니 금방 예외투성이가 된다.

신경망은 규칙 대신 숫자 묶음을 둔다. 이 글에서 쓸 신경망은 이렇게 생겼다.

```text
입력 64개 (픽셀 밝기)
  → 은닉층 32개   z1 = x · W1 + b1,  a1 = ReLU(z1)
  → 출력층 10개   z2 = a1 · W2 + b2, p = softmax(z2)
출력: 0~9 각 숫자일 확률 10개
```

`W1`은 64×32 행렬, `W2`는 32×10 행렬이고, `b1`, `b2`는 더해 주는 숫자(편향)다. 가중치와 편향을 합쳐 파라미터라고 부르고, 이 신경망은 64×32 + 32 + 32×10 + 10 = 2,410개를 가진다. "8B 모델"은 이 숫자가 80억 개라는 뜻이다. 구조는 훨씬 복잡하지만 하는 일의 뼈대는 같다.

ReLU는 음수를 0으로 바꾸는 함수다. 이게 없으면 행렬 곱을 몇 번 하든 결국 행렬 곱 하나로 합쳐져서, 층을 쌓는 의미가 없어진다. softmax는 점수 10개를 더해서 1이 되는 확률로 바꾼다.

학습은 이 2,410개 숫자를 "정답에 높은 확률을 주도록" 고치는 일이다. 처음에는 무작위 값으로 시작한다. 학습 전 신경망에 시험 문제 360장을 풀게 하면 정확도가 13.1%다. 10개 중 하나를 찍는 수준이다.

순전파는 계산을 앞으로 한 번 하는 것이다. 추론(서비스에서 예측만 하는 것)은 여기서 끝난다.

손실은 "얼마나 틀렸나"를 숫자 하나로 만든 것이다. 분류 문제에서는 정답 칸 확률에 로그를 씌우고 부호를 뒤집는 교차 엔트로피를 쓴다. 정답에 확률 1을 주면 0, 0.5를 주면 0.69, 0.01을 주면 4.6이 된다. 확신하고 틀릴수록 벌점이 가파르게 커진다.

역전파는 이 손실 하나를 2,410개 파라미터 각각으로 미분하는 방법이다. 하나씩 조금 바꿔 보며 손실 변화를 재면 순전파를 2,410번 더 해야 한다. 역전파는 연쇄 법칙(합성 함수의 미분은 각 단계 미분의 곱)을 이용해서, 출력 쪽에서 구한 값을 재사용하며 거꾸로 한 번 훑는 것으로 끝낸다. 순전파 한 번과 비슷한 비용(보통 두 배 남짓)으로 모든 기울기가 나온다.

그런데 출력 쪽에서 거꾸로 계산하려면 순전파 때의 중간값(z1, a1)이 필요하다. 그래서 학습할 때는 이 값을 메모리에 들고 있어야 한다. 뒤에서 볼 "학습은 추론보다 메모리를 훨씬 많이 먹는다"의 첫 번째 이유가 이거다.

마지막으로 옵티마이저가 기울기를 보고 파라미터를 고친다. 가장 단순한 방식(SGD)은 `파라미터 -= 학습률 × 기울기`다. 기울기는 손실이 커지는 방향을 가리키니, 빼면 손실이 줄어드는 쪽으로 간다. 눈을 가리고 발밑 경사만 느끼며 내리막으로 한 걸음 옮기는 것과 같다.

## 걸음 크기: 학습률

학습률(learning rate)은 한 번에 얼마나 크게 움직일지 정하는 숫자다. 다른 건 그대로 두고 학습률만 바꿔 20에폭씩 돌렸다.

```text
lr 0.001  train_loss 2.1530 test_acc 0.306
lr 0.01   train_loss 0.8837 test_acc 0.831
lr 0.1    train_loss 0.1032 test_acc 0.961
lr 1.0    train_loss 0.0232 test_acc 0.967
lr 5.0    train_loss 2.3759 test_acc 0.100
```

0.001은 너무 조심스럽다. 900번을 움직였는데도 손실이 2.15로, 출발점(2.29)에서 별로 내려오지 못했다. 시간을 훨씬 많이 주면 언젠가는 내려가겠지만 그만큼 GPU 시간을 쓴다.

1.0은 이 작은 문제에서는 오히려 더 잘 됐다. 정답 학습률은 문제와 모델마다 다르다는 뜻이다. 큰 모델일수록 안전한 학습률은 작아지는 경향이 있어서, LLM 파인튜닝에서는 1e-5~1e-4 같은 값을 흔히 본다.

5.0이 재미있다. 손실이 2.38로 출발점보다 나쁘고, 정확도는 정확히 10%다. 무슨 일이 있었는지 처음 몇 걸음을 찍어 보면 이렇다.

```text
step 1 loss 2.997 dead_relu 0.28
step 2 loss 2.634 dead_relu 0.59
step 3 loss 4.633 dead_relu 0.62
step 4 loss 4.820 dead_relu 0.72
step 5 loss 2.829 dead_relu 0.78
step 6 loss 5.093 dead_relu 0.78
step 7 loss 3.101 dead_relu 0.84
step 8 loss 2.854 dead_relu 0.84
```

손실이 내려가지 않고 위아래로 튄다. 골짜기를 넘어 반대편 비탈로 갔다가 다시 넘어오는 것이다. 동시에 dead_relu(어떤 입력에도 0만 내는 은닉 뉴런의 비율)가 빠르게 늘어난다. 큰 걸음 한 번에 편향이 크게 음수로 밀리면, 그 뉴런은 어떤 그림을 넣어도 음수가 되어 ReLU에서 0이 된다. 0이 나오는 뉴런은 기울기도 0이라 다시 살아날 방법이 없다. 20에폭이 끝났을 때 은닉 뉴런 32개가 전부 죽어 있었다(학습률 0.1에서는 32개 중 2개). 은닉층이 아무것도 전하지 못하니 모델은 입력과 상관없이 같은 답을 내고, 정확도가 정확히 10%가 된다.

실무에서 손실이 NaN으로 바뀌거나 갑자기 치솟는 걸 보면 먼저 학습률을 의심한다. 그래서 큰 모델은 처음 몇백~몇천 걸음 동안 학습률을 0에서 천천히 올리는 워밍업과, 후반에 줄여 가는 스케줄(코사인 감쇠 등)을 함께 쓴다. 기울기 크기 자체를 상한으로 자르는 그래디언트 클리핑도 같은 사고를 막는 장치다.

학습률이 결과를 얼마나 바꾸는지는 숫자 하나짜리 문제에서 직접 보는 게 가장 빠르다. 손실이 `(w - 3)²`이면 기울기는 `2(w - 3)`이고, 바닥은 w = 3이다. 아래 함수를 채워서 학습률에 따라 w가 어디에 도착하는지 돌려 보자.

    w = w - lr * grad;
  }
  return Math.round(w * 10000) / 10000;
}`}
  tests={[
    { args: [0, 0.1, 10], expected: 2.6779, label: "lr 0.1, 10걸음" },
    { args: [0, 0.1, 50], expected: 3, label: "lr 0.1, 50걸음" },
    { args: [0, 0.01, 10], expected: 0.5488, label: "lr 0.01, 10걸음 (느림)" },
    { args: [0, 0.5, 1], expected: 3, label: "lr 0.5, 한 걸음에 도착" },
    { args: [0, 1.1, 10], expected: -15.5752, label: "lr 1.1, 발산" },
    { args: [10, 0.1, 10], expected: 3.7516, label: "반대편에서 출발" },
  ]}
/>

lr 1.1이면 한 걸음마다 바닥을 넘어 더 먼 반대편으로 간다. w가 0 → 6.6 → -1.32 …로 커지면서 벌어진다. 이 문제에서는 lr이 1을 넘으면 무조건 발산한다. 실제 신경망의 손실 지형은 이렇게 매끈한 그릇이 아니라 방향마다 경사가 다른 골짜기라서, 가장 가파른 방향이 이 한계를 정한다.

## 한 번에 몇 장 보고 고칠까: 배치 크기

배치 크기는 기울기를 한 번 구할 때 쓰는 샘플 수다. 에폭(20번)은 고정하고 배치만 바꿨다.

```text
batch 1     updates 28740  train_loss 0.0005 test_acc 0.972
batch 32    updates 900    train_loss 0.1032 test_acc 0.961
batch 256   updates 120    train_loss 0.6431 test_acc 0.883
batch 1437  updates 20     train_loss 1.9980 test_acc 0.467
```

같은 20에폭이라도 갱신 횟수가 다르다. 배치 1은 한 장마다 고치니 28,740번, 전체를 한 배치로 쓰면 20번이다. 배치가 클수록 기울기는 정확해지지만(평균 내는 샘플이 많으니) 걸음 수가 줄어든다. 이 실험에서 배치 1437이 46.7%에 그친 건 기울기가 나빠서가 아니라 20걸음밖에 못 걸었기 때문이다.

그럼 배치 1이 최고인가 하면 그렇지 않다. 위 실험은 "에폭을 같게" 놓고 비교한 것이고, 실제로 아끼고 싶은 건 벽시계 시간이다. GPU는 행렬 곱을 크게 할수록 효율이 좋다. 한 장씩 넣으면 GPU 대부분이 놀고, 갱신 한 번마다 생기는 오버헤드가 쌓인다. 그래서 실무에서는 GPU 메모리가 허락하는 선에서 배치를 키우고, 배치를 키운 만큼 학습률도 같이 올리는 것(선형 스케일링 규칙)이 흔한 출발점이다. 다만 배치를 아주 크게 하면 같은 에폭에서 일반화가 나빠질 수 있다는 보고가 많아서, 무한정 키우지는 않는다.

배치 1이 시험에서 97.2%로 가장 좋았던 것도 우연이 아니다. 작은 배치의 기울기는 잡음이 섞여 있고, 이 잡음이 좁고 뾰족한 골짜기에 갇히지 않게 흔들어 주는 효과가 있다고 알려져 있다. 반대로 학습 손실 0.0005는 학습 문제를 거의 외웠다는 뜻이기도 하다.

메모리가 모자라서 배치를 못 키울 때는 그래디언트 누적을 쓴다. 배치 8로 네 번 순전파·역전파하며 기울기를 더해 두었다가 네 번째에 한 번만 갱신하면, 계산 결과는 배치 32와 거의 같다(배치 정규화처럼 배치 통계를 쓰는 층이 있으면 완전히 같지는 않다).

## 몇 바퀴 돌까: 에폭과 멈출 때

```text
epochs 1    train_loss 1.5854 test_loss 1.5980 train_acc 0.630 test_acc 0.656
epochs 5    train_loss 0.3350 test_loss 0.3782 train_acc 0.935 test_acc 0.914
epochs 20   train_loss 0.1032 test_loss 0.1555 train_acc 0.981 test_acc 0.961
epochs 100  train_loss 0.0248 test_loss 0.1191 train_acc 0.997 test_acc 0.967
```

20에폭에서 100에폭으로 다섯 배를 더 돌리면 학습 정확도는 98.1% → 99.7%로 오르는데 시험 정확도는 96.1% → 96.7%로 조금만 오른다. 학습 손실(0.0248)과 시험 손실(0.1191)의 차이도 다섯 배 가까이 벌어졌다. 이 데이터에서는 아직 시험 손실이 내려가고 있어서 더 돌려도 크게 손해는 아니지만, 더 큰 모델이나 더 작은 데이터에서는 어느 순간 시험 손실이 다시 올라간다.

그래서 에폭 수를 미리 정하기보다 검증 손실을 보며 멈춘다. 몇 에폭 동안 검증 손실이 나아지지 않으면 멈추고(조기 종료), 가장 좋았던 시점의 가중치를 체크포인트에서 꺼내 쓴다. 이 기록을 남기고 비교하는 일이 뒤에서 볼 실험 추적이다.

## 깊이 쌓으면 앞쪽 층이 안 배운다: 기울기 소실

층을 깊게 쌓을수록 표현력이 늘어나는데, 예전에는 깊은 신경망이 잘 학습되지 않았다. 역전파가 연쇄 법칙이라는 데서 이유가 나온다. 앞쪽 층의 기울기는 뒤쪽 층들의 미분값을 전부 곱한 것이다. 곱하는 값이 1보다 작으면 층을 지날 때마다 줄어든다.

시그모이드 함수는 미분값이 최대 0.25다. 10층짜리 신경망에 같은 입력을 넣고 층별 가중치 기울기 크기를 재 봤다(L1이 입력에 가장 가까운 층).

```text
sigmoid L1:3.19e-06 L2:6.83e-05 L3:3.17e-04 L4:1.29e-03 L5:5.63e-03 L6:2.53e-02 L7:1.10e-01 L8:4.38e-01 L9:1.92e+00 L10:7.83e+00
relu    L1:1.59e+01 L2:3.69e+01 L3:4.09e+01 L4:4.42e+01 L5:6.47e+01 L6:4.72e+01 L7:5.15e+01 L8:4.76e+01 L9:4.54e+01 L10:4.32e+01
```

시그모이드는 마지막 층(7.83)과 첫 층(0.0000032)의 기울기가 200만 배 넘게 차이 난다. 같은 학습률로 고치면 앞쪽 층은 사실상 움직이지 않는다. 이게 기울기 소실이다. ReLU는 양수 구간의 미분이 1이라 층을 지나도 크기가 비슷하게 유지된다.

지금 쓰는 해결책은 여러 겹이다.

- 활성화 함수: ReLU와 그 변형(GELU 등). 트랜스포머는 GELU 계열을 많이 쓴다.
- 초기화: 층의 입출력 크기에 맞춰 분산을 정하는 He·Xavier 초기화. 위 실험도 ReLU에는 He 방식으로 분산을 2/64로 줬다.
- 정규화 층: 배치 정규화, 레이어 정규화가 층마다 값의 크기를 다시 맞춘다.
- 잔차 연결(residual): 입력을 층 출력에 그대로 더해 주는 지름길. 역전파 때 기울기가 이 지름길로 곱셈 없이 앞쪽까지 간다. 수십~수백 층짜리 모델이 학습되는 가장 큰 이유다.

반대로 곱하는 값이 1보다 크면 기울기가 폭발한다. 손실이 갑자기 NaN이 되는 흔한 원인이고, 위에서 말한 그래디언트 클리핑이 이걸 막는다.

## SGD 대신 Adam을 많이 쓰는 이유

지금까지는 `파라미터 -= 학습률 × 기울기`라는 가장 단순한 갱신(SGD)만 썼다. 이 방식은 모든 파라미터에 같은 걸음 크기를 쓴다. 그런데 어떤 파라미터는 기울기가 늘 크고, 어떤 파라미터는 늘 작다. 같은 학습률이면 한쪽은 튀고 다른 쪽은 움직이지 않는다.

Adam은 파라미터마다 두 가지를 기억한다. 최근 기울기의 이동 평균(1차 모멘트, 방향을 부드럽게 만든다)과 최근 기울기 제곱의 이동 평균(2차 모멘트, 그 파라미터의 기울기가 평소 얼마나 큰지)이다. 갱신할 때 1차 모멘트를 2차 모멘트의 제곱근으로 나누니, 기울기가 늘 작던 파라미터는 상대적으로 크게, 늘 크던 파라미터는 작게 움직인다. 같은 신경망을 Adam으로 20에폭 돌렸다.

```text
adam lr 0.0001 train_loss 1.5594 test_acc 0.697
adam lr 0.001  train_loss 0.1515 test_acc 0.953
adam lr 0.01   train_loss 0.0173 test_acc 0.961
adam lr 0.1    train_loss 0.0754 test_acc 0.942
sgd  lr 0.0001 train_loss 2.2777 test_acc 0.142
sgd  lr 0.001  train_loss 2.1530 test_acc 0.306
sgd  lr 0.01   train_loss 0.8837 test_acc 0.831
```

SGD는 학습률이 0.001일 때 30.6%였는데 Adam은 같은 학습률로 95.3%다. 0.0001에서 0.1까지 천 배 범위에서 Adam은 그럭저럭 학습됐고, SGD는 학습률을 잘못 고르면 거의 배우지 못했다. 학습률을 덜 민감하게 만들어 준다는 게 Adam을 기본값처럼 쓰는 이유다. 트랜스포머 계열은 가중치 감쇠를 분리한 AdamW를 흔히 쓴다.

대가는 메모리다. 파라미터마다 숫자 두 개를 더 들고 있어야 한다. 뒤에서 볼 학습 메모리 계산에서 "Adam 모멘트"가 두 줄을 차지하는 이유다.

## 같은 코드를 PyTorch로

위에서 손으로 짠 역전파는 프레임워크가 대신 해 준다. 같은 신경망을 PyTorch로 쓰면 이렇다.

```python
import torch
from torch import nn
from sklearn.datasets import load_digits
from sklearn.model_selection import train_test_split

d = load_digits()
X = torch.tensor(d.data / 16.0, dtype=torch.float32)
y = torch.tensor(d.target)
Xtr, Xte, ytr, yte = train_test_split(X, y, test_size=0.2, random_state=0, stratify=y)
loader = torch.utils.data.DataLoader(
    torch.utils.data.TensorDataset(Xtr, ytr), batch_size=32, shuffle=True
)

model = nn.Sequential(nn.Linear(64, 32), nn.ReLU(), nn.Linear(32, 10))
loss_fn = nn.CrossEntropyLoss()           # softmax + 교차 엔트로피를 한 번에
opt = torch.optim.SGD(model.parameters(), lr=0.1)

for epoch in range(20):
    model.train()
    for xb, yb in loader:
        logits = model(xb)                # 순전파
        loss = loss_fn(logits, yb)        # 손실
        opt.zero_grad()                   # 지난 배치의 기울기를 지운다
        loss.backward()                   # 역전파: 모든 파라미터의 .grad가 채워진다
        opt.step()                        # 갱신

model.eval()
with torch.inference_mode():              # 추론: 기울기 계산을 끈다
    acc = (model(Xte).argmax(1) == yte).float().mean()
```

`loss.backward()` 한 줄이 위의 역전파 코드를 대신한다. PyTorch는 순전파 때 어떤 연산을 했는지 그래프로 기록해 두고(autograd), backward에서 그 기록을 거꾸로 따라가며 미분한다. 직접 짤 때 중간값을 저장했던 것처럼 여기서도 기록된 중간값이 메모리를 차지한다.

처음 쓸 때 흔히 하는 실수가 몇 가지 있다.

`opt.zero_grad()`를 빠뜨리면 PyTorch는 기울기를 덮어쓰지 않고 더한다. 지난 배치의 기울기가 계속 쌓여서 학습이 이상하게 튄다. 이 "더하는" 동작이 앞에서 말한 그래디언트 누적을 쉽게 만들어 주는 이유이기도 하다.

`model.eval()`을 빠뜨리면 드롭아웃이 추론 때도 뉴런을 무작위로 끄고, 배치 정규화가 배치 통계로 계산한다. 같은 입력에 예측이 매번 달라지거나, 한 장만 넣었을 때 결과가 이상해진다. 반대로 평가 뒤 학습을 이어 갈 때 `model.train()`으로 돌려놓지 않으면 드롭아웃이 꺼진 채 학습된다.

`inference_mode()`(또는 `no_grad()`) 없이 추론하면 autograd가 계속 그래프를 기록해서 메모리를 쓸데없이 잡는다. 서빙 코드에서 메모리가 요청마다 늘어나는 사고가 여기서 나온다.

## GPU가 빠른 이유는 행렬 곱이다

학습에서 시간 대부분은 행렬 곱이다. 위 신경망에서도 순전파의 `xb @ W1`, `a1 @ W2`, 역전파의 `a1.T @ g`, `xb.T @ dz1`이 전부 행렬 곱이다. LLM은 이 행렬이 수천×수천 크기라는 것만 다르다.

행렬 곱은 결과 칸 하나하나가 서로 독립이다. C의 (i, j) 칸은 A의 i행과 B의 j열만 있으면 계산된다. 칸이 백만 개면 백만 개를 동시에 계산해도 된다. CPU는 아주 똑똑한 코어 몇~몇십 개로 복잡한 일을 순서대로 빠르게 하도록 만들어졌고, GPU는 단순한 곱셈·덧셈 유닛 수천 개를 한꺼번에 돌리도록 만들어졌다. 최근 데이터센터 GPU에는 작은 행렬 곱만 전담하는 텐서 코어까지 들어 있다.

CPU 안에서도 차이를 볼 수 있다. 200×200 행렬 곱을 파이썬 반복문으로 한 칸씩 계산하면 2.45초가 걸렸고, NumPy(내부에서 SIMD와 멀티스레드를 쓰는 BLAS 라이브러리)로는 약 8밀리초였다. 2048×2048 float32 행렬 곱은 4코어 CPU에서 0.069초, 초당 약 2,480억 번 연산(248 GFLOPS)이었다. 데이터센터 GPU는 16비트 행렬 곱에서 이보다 수백~수천 배 높은 수치를 내세운다. 같은 모델이라도 CPU로 몇 주 걸릴 학습이 GPU로 며칠이 되는 이유다.

GPU가 빠르려면 조건이 있다. 계산할 일이 충분히 커야 한다(배치가 너무 작으면 유닛 대부분이 논다). 데이터가 GPU 메모리에 있어야 한다(CPU 메모리에서 매번 옮기면 PCIe 대역폭에서 막힌다). 그래서 GPU 사용률이 낮게 나오면 데이터 로더가 GPU를 못 따라오는지부터 본다. `nvidia-smi`의 GPU-Util이 들쭉날쭉하면 대개 이미지 디코딩이나 전처리가 CPU에서 병목이다. DataLoader의 `num_workers`를 늘리고 `pin_memory=True`를 주는 게 첫 조치다.

```bash
# 1초마다 GPU 사용률과 메모리를 본다 (NVIDIA 드라이버가 설치된 서버)
nvidia-smi --query-gpu=utilization.gpu,memory.used,memory.total --format=csv -l 1
```

쿠버네티스에서 GPU를 Pod에 나눠 주는 방식은 [쿠버네티스 GPU 글](/posts/k8s-gpu-dra)에 있다.

## 학습은 추론보다 메모리를 훨씬 많이 먹는다

7B 모델을 16비트로 추론하면 가중치만 14GB(파라미터당 2바이트)다. 그런데 같은 모델을 Adam 옵티마이저로 전체 학습하려면 파라미터 하나마다 이만큼이 필요하다.

```text
fp16/bf16 가중치         2 바이트
fp16/bf16 기울기         2 바이트
fp32 원본 가중치 복사본   4 바이트   (혼합 정밀도에서 갱신은 32비트로 한다)
Adam 1차 모멘트 (fp32)   4 바이트
Adam 2차 모멘트 (fp32)   4 바이트
------------------------------------
합계                    16 바이트 / 파라미터
```

7B × 16바이트 = 112GB다. 여기에 역전파를 위해 저장하는 중간값(활성값)이 배치 크기와 시퀀스 길이에 비례해서 더 붙는다. 추론은 가중치 14GB와 KV 캐시면 되는데(KV 캐시 계산은 [트랜스포머 글](/posts/transformer-attention-kv-cache)), 학습은 GPU 한 장(80GB)에 올라가지도 않는다. LoRA처럼 일부 파라미터만 학습하는 방법이 인기인 이유가 이 계산에 있다. 학습하는 파라미터가 적으면 기울기와 옵티마이저 상태도 그만큼만 필요하다. 계산 예시는 [파인튜닝 글](/posts/fine-tuning-vs-rag-vs-prompting)에 있다.

정리하면 학습과 추론의 자원 차이는 세 가지에서 온다. 기울기와 옵티마이저 상태가 따로 메모리를 잡는다. 역전파를 위해 활성값을 들고 있어야 한다. 계산량도 순전파에 역전파(보통 순전파의 두 배쯤)가 더해져 약 세 배다. 반대로 추론은 요청이 들어오는 대로 지연 시간을 맞춰야 한다는 다른 제약이 생긴다. 이건 [모델 서빙 글](/posts/model-serving)에서 다룬다.

### 메모리가 모자랄 때 손대는 순서

학습 중에 `CUDA out of memory` 오류를 만나면 보통 이 순서로 본다.

1. 배치 크기를 줄이고, 줄인 만큼 그래디언트 누적으로 유효 배치를 맞춘다. 가장 쉽고 결과가 거의 같다.
2. 혼합 정밀도를 켠다. 가중치·활성값을 16비트로 다루면 활성값 메모리가 절반 가까이 줄고 텐서 코어도 쓴다.
3. 활성화 체크포인팅(gradient checkpointing)을 켠다. 활성값을 일부만 저장하고 역전파 때 나머지를 다시 계산한다. 메모리를 크게 줄이는 대신 계산 시간이 20~30%쯤 늘어난다고 흔히 말한다.
4. 옵티마이저 상태와 가중치를 여러 GPU에 나눠 담는다(ZeRO, FSDP). GPU 여러 장이 필요하다.
5. 처음부터 LoRA·QLoRA처럼 학습하는 파라미터 자체를 줄인다.

메모리 사용량은 짐작하지 말고 잰다. PyTorch에서는 `torch.cuda.max_memory_allocated()`로 한 스텝의 최대치를 볼 수 있다. `nvidia-smi`에 보이는 숫자는 PyTorch가 캐시로 잡아 둔 메모리까지 포함해서 실제 사용량보다 크게 나온다.

## 16비트로 학습하기: 혼합 정밀도

32비트(fp32) 대신 16비트로 계산하면 메모리가 줄고 텐서 코어 덕분에 빨라진다. 16비트 형식은 두 가지다.

fp16은 지수 비트가 5개라 표현할 수 있는 가장 작은 수가 크지 않다. 작은 기울기가 0으로 뭉개지는(언더플로) 문제가 생겨서, 손실에 큰 수를 곱해 기울기를 키웠다가 갱신 직전에 다시 나누는 손실 스케일링을 함께 쓴다.

bf16은 지수 비트를 fp32와 같은 8개로 두고 소수 자리를 줄인 형식이다. 범위가 fp32와 같아서 손실 스케일링이 필요 없다. 정밀도는 낮지만 학습에서는 범위가 더 중요해서, 지원하는 GPU(NVIDIA Ampere 세대 이후 등)에서는 bf16을 기본으로 쓰는 경우가 많다. 부동소수점 비트 구조는 [부동소수점 글](/posts/floating-point-numbers)에 있다.

```python
# fp16 혼합 정밀도 (PyTorch 2.x, CUDA)
scaler = torch.amp.GradScaler("cuda")
for xb, yb in loader:
    xb, yb = xb.cuda(), yb.cuda()
    with torch.autocast(device_type="cuda", dtype=torch.float16):
        loss = loss_fn(model(xb), yb)     # 행렬 곱은 16비트, 손실 같은 민감한 연산은 32비트로 자동 선택
    opt.zero_grad()
    scaler.scale(loss).backward()         # 손실을 키워서 역전파
    scaler.step(opt)                      # 기울기를 되돌려 나눈 뒤 갱신, inf/NaN이면 이번 스텝을 건너뛴다
    scaler.update()

# bf16이면 스케일러 없이 autocast만 쓴다
with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
    loss = loss_fn(model(xb), yb)
```

"혼합"인 이유는 모든 걸 16비트로 하지 않아서다. 행렬 곱처럼 16비트로 해도 괜찮은 연산만 16비트로 하고, 합계·소프트맥스·손실처럼 오차가 쌓이기 쉬운 연산과 가중치 갱신은 32비트로 한다. 위 메모리 표에서 fp32 원본 가중치를 따로 들고 있는 게 이 때문이다. 아주 작은 갱신값을 16비트 가중치에 바로 더하면 반올림으로 사라진다.

## PyTorch와 TensorFlow는 어디가 다른가

두 프레임워크 모두 텐서 연산, 자동 미분, GPU 실행을 제공한다. 차이는 코드를 실행하는 방식에서 시작했다.

TensorFlow 1.x는 그래프를 먼저 정의하고 세션에서 나중에 실행했다. 코드를 읽으면 계산이 일어나는 게 아니라 계산 계획이 만들어졌다. 그래프 전체를 미리 알면 최적화하고 다른 기기로 옮기기 좋지만, 중간값을 print로 찍어 보거나 파이썬 if문으로 분기하기 불편했다.

PyTorch는 처음부터 즉시 실행(eager)이었다. 파이썬 한 줄을 실행하면 그 연산이 바로 일어나고, autograd는 실행된 연산을 그때그때 기록한다. 디버거로 멈추고 텐서를 들여다볼 수 있다. 연구자들이 PyTorch로 많이 넘어간 이유가 이 쓰기 편함이었다.

이후 둘은 서로를 닮아 갔다. TensorFlow 2는 즉시 실행을 기본으로 바꾸고, 빠르게 돌릴 함수에 `@tf.function`을 붙이면 그래프로 바꿔 실행한다. PyTorch 2는 `torch.compile(model)`로 즉시 실행 코드를 추적해 그래프로 컴파일하고 연산을 합쳐 빠르게 만든다. 지금은 "즉시 실행으로 개발하고, 필요한 곳만 그래프로 컴파일한다"는 같은 방향에 서 있다.

개발자 입장에서 실제로 갈리는 건 생태계다. 공개된 모델 코드와 LLM 관련 도구(Hugging Face Transformers, vLLM 등)는 PyTorch를 중심으로 돌아가는 경우가 대부분이다. TensorFlow는 기존에 TF로 만든 운영 시스템, TF Serving 같은 배포 도구, 모바일·임베디드용 경량 런타임(TensorFlow Lite, 지금 이름은 LiteRT)에서 여전히 쓰인다. Keras 3는 같은 Keras 코드를 TensorFlow, JAX, PyTorch 중 하나를 골라 돌리게 바뀌었다. 새로 시작하는 프로젝트라면 팀이 가져다 쓸 모델이 어느 쪽 코드로 공개되어 있는지를 먼저 본다.

배포할 때는 학습 프레임워크와 서빙 형식을 떼어 놓는 경우도 많다. ONNX 같은 중립 형식으로 내보내서 다른 런타임으로 돌리면, 서빙 쪽은 PyTorch를 설치하지 않아도 된다. 이 이야기는 [MLOps 글](/posts/what-is-mlops)과 [모델 서빙 글](/posts/model-serving)로 이어진다. 모델이 왜 그렇게 예측했는지 쪼개 보는 방법은 [SHAP과 LIME 글](/posts/explainable-ai-shap-lime)에 있다.

## 다시 반복문 하나로

딥러닝 학습은 순전파로 예측하고, 손실로 틀린 정도를 재고, 역전파로 파라미터마다 기울기를 구하고, 학습률만큼 반대로 움직이는 반복이다. 학습률은 걸음 크기라서 너무 크면 튀거나 뉴런이 죽고 너무 작으면 내려가지 못한다. 배치 크기는 기울기의 정확도와 걸음 수, GPU 효율을 바꾼다. 에폭은 검증 손실을 보며 멈춘다. GPU가 빠른 건 이 반복의 대부분이 서로 독립인 곱셈이라서고, 학습이 추론보다 무거운 건 기울기, 옵티마이저 상태, 저장해 둔 활성값 때문이다.

## 면접에서 나올 만한 질문

### 역전파는 무엇을 계산하고, 왜 효율적인가

손실 하나를 모든 파라미터로 미분한 기울기를 계산한다. 연쇄 법칙을 써서 출력층에서 구한 미분을 입력층 쪽으로 넘기며 재사용하기 때문에, 파라미터가 수십억 개여도 순전파 한두 번 정도의 비용으로 기울기가 전부 나온다. 대신 순전파 때의 중간값을 저장해 두어야 해서 메모리를 쓴다.

### 학습률이 너무 크면 어떤 일이 생기나

손실이 줄지 않고 위아래로 튀거나, 커지다가 NaN이 된다. 골짜기 바닥을 넘어 반대편으로 계속 넘어가기 때문이다. ReLU 신경망에서는 큰 갱신 한 번에 뉴런이 항상 0만 내는 상태가 되어 다시 살아나지 못하기도 한다. 실제로 작은 신경망을 학습률 5.0으로 돌렸더니 은닉 뉴런 32개가 모두 죽어 정확도가 10%가 됐다. 워밍업, 학습률 스케줄, 그래디언트 클리핑으로 막는다.

### 기울기 소실은 왜 생기고 어떻게 해결하나

역전파에서 앞쪽 층의 기울기는 뒤쪽 층 미분값의 곱인데, 시그모이드처럼 미분이 1보다 작은 함수를 쓰면 층마다 줄어들어 앞쪽 층이 거의 학습되지 않는다. 10층 시그모이드 신경망에서 첫 층과 마지막 층의 기울기가 200만 배 넘게 차이 나는 걸 확인했다. ReLU 계열 활성화, He·Xavier 초기화, 배치·레이어 정규화, 기울기가 곱셈 없이 지나가는 잔차 연결로 해결한다.

### 배치 크기를 키우면 무엇이 바뀌나

기울기 추정이 정확해지고 GPU를 더 효율적으로 쓰지만, 같은 에폭에서 갱신 횟수가 줄고 메모리를 더 쓴다. 그래서 배치를 키울 때는 학습률도 함께 올리는 게 보통이다. 너무 크면 일반화가 나빠질 수 있고, 메모리가 부족하면 그래디언트 누적으로 큰 배치를 흉내 낸다.

### GPU가 딥러닝에서 빠른 이유는

학습 시간 대부분이 행렬 곱이고, 행렬 곱의 결과 칸은 서로 독립이라 동시에 계산할 수 있기 때문이다. GPU는 단순한 연산 유닛 수천 개와 행렬 곱 전용 텐서 코어로 이걸 병렬로 처리한다. 대신 일이 충분히 커야 하고 데이터가 GPU 메모리에 있어야 해서, 사용률이 낮으면 배치 크기와 데이터 로더 병목부터 본다.

### 학습과 추론의 자원 차이는

추론은 순전파만 하니 가중치와 KV 캐시 같은 실행 상태면 된다. 학습은 기울기와 옵티마이저 상태가 추가되고, 역전파를 위해 활성값을 저장해야 한다. Adam과 혼합 정밀도로 전체 학습하면 파라미터당 16바이트쯤이 들어서 7B 모델은 활성값을 빼고도 112GB가 필요하다. 계산량도 역전파가 더해져 순전파의 약 세 배다.

### 학습 중 OOM이 나면 무엇부터 하나

배치를 줄이고 그래디언트 누적으로 유효 배치를 유지하는 게 첫 번째다. 그다음 혼합 정밀도, 활성화 체크포인팅(계산을 더 하는 대신 메모리를 줄인다), 여러 GPU에 상태를 나누는 ZeRO·FSDP 순서로 본다. 파인튜닝이라면 LoRA처럼 학습 파라미터를 줄이는 방법을 처음부터 고려한다. 사용량은 `torch.cuda.max_memory_allocated()`로 실제로 잰다.

### PyTorch와 TensorFlow는 무엇이 다른가

출발점이 즉시 실행(PyTorch)과 그래프 먼저 정의(TensorFlow 1.x)로 달랐다. 지금은 둘 다 즉시 실행을 기본으로 하고 `torch.compile`, `tf.function`으로 필요한 부분만 그래프로 컴파일해서 차이가 많이 줄었다. 실제 선택은 생태계로 갈리는데, 공개 모델과 LLM 도구는 PyTorch 중심이고 TensorFlow는 기존 운영 시스템과 모바일 런타임에서 많이 쓰인다.
