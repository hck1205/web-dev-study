응답 시간 로그 100만 건에서 느린 순서로 10번째 값을 뽑아야 했다. 처음 짠 코드는 이랬다.

```js
const tenth = latencies.slice().sort((a, b) => b - a)[9];
```

맞는 답이 나온다. 그런데 이 한 줄이 100만 개를 전부 줄 세운다. 10번째 자리 하나만 필요한데 나머지 999,990개의 순서까지 정한 셈이다. Node 22에서 같은 배열로 재 보면 차이가 꽤 난다.

```text
sort ms 563.9
qs ms 17.5
```

위가 정렬하고 꺼낸 시간, 아래가 퀵셀렉트(quickselect)로 같은 값을 찾은 시간이다(둘 다 배열 복사 포함, 여러 번 돌린 평균). 30배 넘게 빠르다. 퀵셀렉트는 정렬을 하지 않는다. 기준값 하나로 배열을 가르고, 답이 있는 쪽만 다시 가른다. 버리는 쪽은 다시 보지 않는다.

이 글은 퀵셀렉트에서 출발해 분할 정복이라는 생각 자체를 따라간다. 문제를 쪼개는 방식과 걸리는 시간을 점화식으로 적고, 마스터 정리로 병합 정렬·이분 탐색·카라츠바 곱셈의 복잡도를 바로 읽는다. 동적 계획법과 어디서 갈리는지, 퀵셀렉트가 무너지는 입력과 막는 법도 본다. 퀵 정렬과 병합 정렬의 구현은 [정렬 알고리즘 글](/posts/sorting-algorithms)에, 재귀의 기본 뼈대는 [재귀와 백트래킹 글](/posts/recursion-backtracking)에 있다. 실행 결과는 모두 Node.js 22에서 직접 돌린 값이다.

## 쪼개고, 따로 풀고, 합친다

분할 정복(divide and conquer)은 세 단계로 이루어진다.

1. 분할: 문제를 같은 모양의 더 작은 문제 몇 개로 나눈다.
2. 정복: 작은 문제를 재귀로 푼다. 충분히 작아지면 바로 푼다.
3. 결합: 작은 답들을 합쳐 큰 답을 만든다.

병합 정렬로 보면 분명하다. 배열을 반으로 나누고(분할), 양쪽을 각각 정렬하고(정복), 정렬된 두 줄을 머리끼리 비교하며 하나로 합친다(결합). 일이 어디에 몰리는지는 알고리즘마다 다르다. 병합 정렬은 나누기가 공짜고 합치기가 일이다. 퀵 정렬은 반대로 기준값으로 가르는 분할이 일이고 합치기는 할 게 없다. 이분 탐색은 나눈 두 쪽 중 하나를 버리니 정복할 문제가 하나뿐이다.

퀵셀렉트는 퀵 정렬의 분할에 이분 탐색의 "한쪽만 본다"를 붙인 것이다. 아래 그림에서 `[3, 2, 1, 5, 6, 4]`의 2번째로 큰 값을 찾는다. 다음을 누르면 기준값과 비교하는 칸이 차례로 튀어나오고, 작은 쪽과 큰 쪽에 값이 쌓인다.

## 퀵셀렉트를 코드로 옮기면

목표 자리를 정하고, 가르고, 기준값이 선 자리와 목표를 비교해 한쪽 구간으로 좁힌다. 정복할 문제가 하나뿐이라 재귀 대신 반복문으로 쓸 수 있고, 그러면 재귀 깊이 걱정도 없다.

```js
function kthLargest(nums, k) {
  const a = nums.slice();          // 원본을 건드리지 않는다
  const target = a.length - k;     // k번째로 큰 값 = 오름차순 target번 자리
  let lo = 0, hi = a.length - 1;
  while (lo < hi) {
    // 기준값을 무작위로 골라 맨 끝으로 보낸다
    const r = lo + Math.floor(Math.random() * (hi - lo + 1));
    [a[r], a[hi]] = [a[hi], a[r]];
    const pivot = a[hi];
    let s = lo;                    // s 앞은 전부 기준값보다 작다
    for (let i = lo; i < hi; i++) {
      if (a[i] < pivot) { [a[s], a[i]] = [a[i], a[s]]; s++; }
    }
    [a[s], a[hi]] = [a[hi], a[s]]; // 기준값을 제자리(s)에 세운다
    if (s === target) return a[s];
    if (s < target) lo = s + 1;    // 답은 오른쪽에
    else hi = s - 1;               // 답은 왼쪽에
  }
  return a[lo];
}
```

평균이 왜 O(n)인지는 크기만 따라가면 보인다. 기준값이 대충 가운데쯤 서면 남는 구간은 n, n/2, n/4, …로 줄고, 각 단계의 비교 횟수를 다 더하면 n + n/2 + n/4 + … ≈ 2n이다. 정렬은 이 반쪽들을 버리지 않고 양쪽 다 정렬하니 n log n이 된다.

실제로 비교 횟수를 세 봤다. 무작위 정수 100만 개에서 20번씩 돌린 평균이다.

```text
999990 avg 1.89n min 1.16 max 3.33
500000 avg 3.27n min 1.97 max 5.45
```

10번째로 큰 값(목표 자리 999990)을 찾을 때 평균 1.89n번, 가운데 값(목표 자리 500000)을 찾을 때 3.27n번 비교했다. 끝 쪽을 찾을 때는 한 번 가를 때마다 버리는 쪽이 커서 2n에 가깝고, 가운데를 찾을 때는 답이 늘 큰 쪽에 남기 쉬워서 더 든다. 이론값은 가운데일 때 약 3.39n(2(1 + ln 2)n)이니 잰 값과 맞는다. 어느 쪽이든 n에 비례하고, log n이 붙지 않는다.

## 걸리는 시간을 점화식으로 적는다

분할 정복의 시간은 "크기 n짜리를 풀려면 더 작은 것을 몇 번 풀고, 그 밖에 얼마를 더 하나"로 적는다.

```text
T(n) = a·T(n/b) + f(n)
```

`a`는 하위 문제 개수, `n/b`는 하위 문제 하나의 크기, `f(n)`은 나누고 합치는 데 드는 일이다. 몇 가지를 이 꼴로 옮겨 보면 이렇다.

```text
병합 정렬     T(n) = 2T(n/2) + n      반씩 둘, 합치기 n
이분 탐색     T(n) = 1T(n/2) + 1      반 중 하나, 비교 한 번
퀵셀렉트 평균  T(n) = 1T(n/2) + n      한쪽만, 가르기 n
카라츠바 곱셈  T(n) = 3T(n/2) + n      반 길이 곱셈 셋, 덧셈 n
```

이 식을 풀 때는 재귀 호출이 만드는 나무를 그리면 된다. 아래 그림은 병합 정렬이 8칸을 정렬할 때의 나무다. 점이 흐르는 방향으로 문제가 쪼개지고, 층마다 합치는 일이 붙는다.

## 마스터 정리로 복잡도를 바로 읽는다

마스터 정리는 `T(n) = aT(n/b) + f(n)` 꼴의 답을 세 경우로 정리한 것이다. 기준은 `n^(log_b a)`, 곧 잎(가장 작은 문제)의 개수다. 하위 문제가 a개씩 늘어나며 log_b n층을 내려가니 맨 아래 잎은 `a^(log_b n) = n^(log_b a)`개가 된다. 이 값과 `f(n)`을 비교한다.

```text
1. f(n)이 n^(log_b a)보다 다항식만큼 작다  → 잎이 무겁다     T(n) = Θ(n^(log_b a))
2. f(n)이 n^(log_b a)와 같은 크기다       → 층마다 같다     T(n) = Θ(n^(log_b a) · log n)
3. f(n)이 n^(log_b a)보다 다항식만큼 크다  → 뿌리가 무겁다   T(n) = Θ(f(n))
   (3번은 a·f(n/b) ≤ c·f(n), c < 1 이라는 조건이 붙는다)
```

앞의 네 식에 대 보면 이렇다.

```text
병합 정렬     a=2 b=2  n^(log₂2) = n      f = n   같다   → Θ(n log n)
이분 탐색     a=1 b=2  n^(log₂1) = 1      f = 1   같다   → Θ(log n)
퀵셀렉트 평균  a=1 b=2  n^(log₂1) = 1      f = n   크다   → Θ(n)
카라츠바      a=3 b=2  n^(log₂3) ≈ n^1.585 f = n  작다   → Θ(n^1.585)
```

이분 탐색과 병합 정렬이 같은 2번 경우라는 게 재미있다. 둘 다 층마다 하는 일이 같고, 이분 탐색은 그 일이 1이라 층 수 log n만 남는다. 퀵셀렉트 평균은 3번 경우다. 첫 가르기 n이 뒤의 모든 일을 합친 것보다 크니 전체가 첫 층에 지배된다. 조건도 맞는다. `1·f(n/2) = n/2 ≤ (1/2)·n`이다.

마스터 정리로 못 푸는 식도 있다. `T(n) = T(n−1) + n`은 크기가 반이 아니라 하나씩 줄어서 이 꼴이 아니다. 퀵 정렬의 최악이 이 식이고, 그대로 더하면 n + (n−1) + … = O(n²)이다. `T(n) = 2T(n/2) + n log n`은 `f(n)`이 n보다 크지만 다항식만큼 크지는 않아서 기본형 세 경우 사이에 끼고, 확장된 2번 경우로 Θ(n log² n)이 나온다. `T(n) = T(n/3) + T(2n/3) + n`처럼 크기가 다르게 갈라지는 식은 재귀 나무를 직접 그리거나 아크라-바찌(Akra–Bazzi) 정리를 쓴다.

## 곱셈 한 번을 아끼면 지수가 바뀐다

마스터 정리를 외워 두면 좋은 이유가 카라츠바 곱셈에서 드러난다. n자리 수 두 개를 곱하는 학교식 곱셈은 자리마다 다 곱하니 n²번이다. 반으로 쪼개도 그대로 하면 나아지지 않는다.

```text
x = x1·10^m + x0,  y = y1·10^m + y0
x·y = x1y1·10^(2m) + (x1y0 + x0y1)·10^m + x0y0
→ 반 길이 곱셈 4번: T(n) = 4T(n/2) + n  → n^(log₂4) = n²
```

1960년 카라츠바는 가운데 항을 곱셈 하나로 구했다. `(x1 + x0)(y1 + y0)`를 한 번 곱하면 그 안에 x1y1, x0y0, 그리고 원하는 가운데 항이 다 들어 있다. 이미 구한 두 개를 빼면 된다.

```text
1234 × 5678   (x1=12, x0=34, y1=56, y0=78, m=2)
z2 = 12 × 56 = 672
z0 = 34 × 78 = 2652
z1 = (12+34)(56+78) − z2 − z0 = 46 × 134 − 672 − 2652 = 6164 − 3324 = 2840
x·y = 672·10⁴ + 2840·10² + 2652 = 7,006,652
```

곱셈이 4번에서 3번으로 줄었고 덧셈·뺄셈이 몇 번 늘었다. 마스터 정리로는 a가 4에서 3이 된 것이고, 지수가 2에서 log₂3 ≈ 1.585로 내려간다. 1024자리라면 학교식은 한 자리 곱셈 1,048,576번, 카라츠바는 끝까지 쪼갰을 때 3¹⁰ = 59,049번이다. 행렬 곱셈의 스트라센 알고리즘도 같은 생각이다. 2×2 블록 곱셈 8번을 7번으로 줄여 `T(n) = 7T(n/2) + n²`, 곧 n^2.807이 된다.

실제 구현은 작은 크기에서 학교식으로 돌아간다. 쪼개고 더하는 비용이 있어서 몇십 자리 이하에서는 학교식이 더 빠르기 때문이다. 이 "작으면 단순한 방법으로" 전환은 분할 정복을 실무에 쓸 때 거의 언제나 들어간다. V8의 `sort`가 짧은 구간을 삽입 정렬로 처리하는 것도 같은 이유다.

## 합치면서 덤으로 세는 것

결합 단계는 답을 합치는 자리이면서, 두 조각 사이에 걸친 정보를 얻는 자리이기도 하다. 면접에 자주 나오는 "역순 쌍 세기"가 그 예다. 앞에 있는데 더 큰 쌍(i가 j보다 앞이고 `a[i] > a[j]`)이 몇 개인지 센다. 추천 순위 두 개가 얼마나 다른지 잴 때 쓰는 값이다.

모든 쌍을 보면 O(n²)이다. 병합 정렬을 조금 고치면 n log n에 센다. 왼쪽 반과 오른쪽 반이 각각 정렬되어 있을 때, 오른쪽 값을 먼저 꺼내는 순간 왼쪽에 아직 남은 값은 전부 그보다 크다. 그 개수를 한꺼번에 더한다.

```js
function countInversions(a) {
  if (a.length <= 1) return { sorted: a, count: 0 };
  const mid = a.length >> 1;
  const L = countInversions(a.slice(0, mid));
  const R = countInversions(a.slice(mid));
  const out = [];
  let i = 0, j = 0, count = L.count + R.count;   // 각 반쪽 안의 역순 쌍
  while (i < L.sorted.length && j < R.sorted.length) {
    if (L.sorted[i] <= R.sorted[j]) out.push(L.sorted[i++]);
    else {
      out.push(R.sorted[j++]);
      count += L.sorted.length - i;               // 왼쪽에 남은 값은 전부 더 크다
    }
  }
  return { sorted: out.concat(L.sorted.slice(i), R.sorted.slice(j)), count };
}

countInversions([2, 4, 1, 3, 5]).count; // 3: (2,1) (4,1) (4,3)
```

무작위 정수 10만 개에서 이중 반복문과 비교했다.

```text
dc 111ms 2497557790
brute 25672ms 2497557790
```

같은 25억 쌍을 세는데 이중 반복문은 25초, 분할 정복은 0.1초가 걸렸다. 점화식은 병합 정렬과 똑같은 `2T(n/2) + n`이다. 합치는 일에 덧셈 하나를 얹었을 뿐이라 복잡도가 그대로다. 조각 안의 답은 재귀가 주고, 조각 사이에 걸친 답은 결합이 준다. 가장 가까운 점 쌍도 이 틀로 푼다(아래에서 다시 본다).

## 동적 계획법과 갈리는 곳

분할 정복과 동적 계획법은 둘 다 큰 문제를 작은 문제로 푼다. 갈리는 곳은 하위 문제가 겹치느냐다.

병합 정렬의 왼쪽 반과 오른쪽 반은 서로 다른 칸을 다룬다. 한 번 정렬한 구간을 다시 정렬할 일이 없다. 그러니 결과를 저장해 둬도 다시 꺼낼 일이 없다. 피보나치를 그대로 재귀로 쓰면 `fib(5)`가 `fib(4)`와 `fib(3)`을 부르고, `fib(4)`가 또 `fib(3)`을 부른다. 같은 하위 문제가 지수적으로 반복된다. 이렇게 겹칠 때 답을 표에 적어 두는 것이 [동적 계획법](/posts/dynamic-programming)이다.

그래서 문제를 보고 이렇게 고른다. 쪼갠 조각이 서로 독립이면 분할 정복으로 충분하고, 메모를 붙여도 이득이 없다. 조각이 겹치면 메모나 표가 필요하다. 겹치는데 분할 정복으로 짜면 지수 시간이 나오고, 겹치지 않는데 표를 만들면 메모리만 쓴다.

독립이라는 성질에는 덤이 있다. 조각끼리 기다릴 게 없으니 동시에 돌릴 수 있다. 자바의 ForkJoinPool이 큰 작업을 반으로 쪼개 여러 스레드에 나눠 주는 방식, 맵리듀스가 데이터를 조각으로 나눠 각 머신이 처리하고 합치는 방식이 같은 구조다. 메모리에 다 안 들어가는 파일을 정렬하는 외부 정렬도 조각을 각각 정렬해 디스크에 쓰고, 마지막에 k개 줄을 한꺼번에 병합한다.

## 퀵셀렉트가 무너지는 입력

평균 O(n)은 기준값이 "대충 가운데"에 선다는 가정에서 나온다. 기준값이 매번 최솟값이나 최댓값이면 한 번에 하나씩만 줄고 `T(n) = T(n−1) + n`, 곧 O(n²)이 된다. 마지막 칸을 기준값으로 고정하고 이미 정렬된 2만 개에서 가장 작은 값을 찾아 봤다.

```text
sorted last-pivot n=20000 k=n (min)     1974.1ms comps 199990000
sorted random-pivot n=20000 k=n            0.7ms comps 72191
```

비교 횟수가 정확히 n(n−1)/2 = 199,990,000번이다. 무작위로 고르면 7만 번대로 떨어진다. DB에서 정렬된 채로 온 배열, 시간순 로그처럼 이미 정렬된 입력은 실무에서 흔해서, 기준값을 고정 자리에서 고르는 구현은 곧바로 이 함정에 빠진다. 무작위 기준값이 왜 이걸 막는지, 그리고 공격자가 일부러 나쁜 입력을 만들 때는 어떻게 되는지는 [랜덤 알고리즘 글](/posts/randomized-algorithms)에서 이어서 다룬다.

무작위 기준값으로도 못 막는 경우가 하나 있다. 같은 값이 잔뜩 있을 때다. 위 코드는 "기준값보다 작다"만 왼쪽으로 보내니, 전부 7인 배열에서는 기준값과 같은 값이 전부 한쪽에 남는다.

```text
all equal 20000           782ms
3-way all equal 20000     5.2ms
```

같은 값 2만 개에서 782ms가 걸렸다. 같은 값 구역을 따로 두는 3-way 분할로 바꾸면 한 번 가르기로 끝난다. 목표 자리가 같은 값 구역 안에 들어오면 그 값이 답이기 때문이다. 상태 코드, 점수, 날짜처럼 값의 종류가 적은 데이터에서 이 차이가 크다.

최악을 이론적으로 막는 방법도 있다. median of medians는 5개씩 묶어 각 묶음의 중앙값을 구하고, 그 중앙값들의 중앙값을 다시 재귀로 구해 기준값으로 쓴다. 이렇게 고른 기준값의 양쪽에는 적어도 30%쯤의 원소가 있다는 게 보장되어서 식이 `T(n) ≤ T(n/5) + T(7n/10) + n`이 된다. 1/5 + 7/10 = 9/10으로 1보다 작으니 층마다 일이 줄어 최악도 O(n)이다. 대신 상수가 커서 평소에는 무작위 퀵셀렉트보다 느리다. 그래서 라이브러리는 둘을 섞는다. C++의 `std::nth_element`는 보통 인트로셀렉트(평소엔 퀵셀렉트, 너무 깊어지면 최악이 보장된 방법으로 전환)로 구현되고, NumPy의 `partition`도 기본이 인트로셀렉트다.

## 깊이가 얼마나 되나

분할 정복은 재귀로 짜는 게 자연스러워서 호출 스택 깊이를 함께 따져야 한다. Node 22에서 아무것도 안 하는 재귀 함수가 몇 번 들어가다 멈추는지 세 봤다.

```text
max depth 12555 RangeError
```

이 숫자는 함수가 지역 변수를 얼마나 쓰느냐에 따라 달라지고, `node --stack-size`로 바꿀 수도 있다. 대략 만 단위라고 기억해 두면 된다. 반씩 쪼개는 재귀는 100만 개에서도 깊이가 20이라 걱정할 일이 없다. 문제는 쪼개기가 한쪽으로 치우칠 때다. 퀵 정렬 최악은 깊이가 n이라 정렬된 1만 개에서 스택이 넘친다.

막는 방법은 세 가지다. 퀵셀렉트처럼 정복할 문제가 하나면 반복문으로 바꾼다. 퀵 정렬처럼 둘이면 작은 쪽만 재귀로 부르고 큰 쪽은 반복문으로 돌려서 깊이를 log n 안에 묶는다. 깊이 자체를 세다가 일정 값을 넘으면 다른 알고리즘으로 넘어가는 인트로 정렬·인트로셀렉트 방식도 있다.

## 가장 가까운 두 점

분할 정복이 "결합" 단계에서 머리를 써야 하는 예가 가장 가까운 점 쌍 문제다. 평면 위 n개 점 중 거리가 가장 짧은 두 점을 찾는다. 모든 쌍을 재면 n(n−1)/2번, O(n²)이다.

분할 정복으로는 이렇게 푼다. 점을 x좌표로 정렬하고 가운데 세로선으로 반을 나눈다. 왼쪽과 오른쪽에서 각각 가장 가까운 거리를 재귀로 구하고, 둘 중 작은 값을 d라고 하자. 남은 경우는 한 점은 왼쪽, 한 점은 오른쪽에 있는 쌍이다. 그런 쌍이 d보다 가까우려면 두 점 모두 세로선에서 d 안에 있어야 한다. 이 띠 안의 점을 y좌표 순으로 놓으면, 각 점은 위로 몇 개(널리 알려진 증명으로 7개 이하)만 비교하면 된다. d×2d 상자 안에 서로 d 이상 떨어진 점은 몇 개밖에 못 들어가기 때문이다.

결합이 O(n)이 되니 `T(n) = 2T(n/2) + n`, 병합 정렬과 같은 O(n log n)이다. 띠를 매번 y로 새로 정렬하면 결합이 n log n이 되어 전체가 O(n log² n)으로 늘어난다. 처음에 y 순서도 한 번 만들어 두고 재귀 안에서 나눠 쓰거나, 병합 정렬처럼 돌아오면서 y 순서를 합치면 n log n을 지킨다. 지도 서비스에서 가까운 점을 찾는 일은 보통 이 알고리즘보다 공간을 칸으로 나누는 색인으로 푼다. 그 이야기는 [쿼드트리 글](/posts/quadtree)에 있다.

## 현장에서 k번째를 찾을 때

면접 문제로는 퀵셀렉트가 정답이지만, 현장에서 "상위 k개"나 "k번째"를 구할 때는 데이터가 어디 있느냐로 먼저 갈린다.

데이터가 DB에 있으면 DB에 맡긴다. `ORDER BY latency DESC LIMIT 10`에 PostgreSQL은 전체를 정렬하지 않고, k가 작으면 크기 k짜리 힙만 유지하는 방식을 쓴다. `EXPLAIN ANALYZE`의 정렬 노드에 `Sort Method: top-N heapsort`라고 찍히면 그 경우다. 애플리케이션으로 100만 행을 가져와 정렬하는 코드는 대부분 이 한 줄로 바뀐다.

데이터가 스트림으로 흘러오면 크기 k짜리 최소 힙을 둔다. 새 값이 힙의 최솟값보다 크면 바꿔 넣는다. 메모리는 k개, 시간은 O(n log k)이고 전체를 들고 있지 않아도 된다. 힙 자체는 [힙 글](/posts/ds-heap)에서 다뤘다.

배열이 이미 메모리에 다 있고 한 번만 구하면 퀵셀렉트가 가장 빠르다. 대신 배열을 뒤섞으니 원본이 필요하면 복사하고, 같은 배열에서 여러 번 다른 k를 구할 거면 한 번 정렬해 두는 편이 낫다. p50, p95, p99를 한꺼번에 구하는 대시보드라면 정렬 한 번이 퀵셀렉트 세 번보다 단순하다. 응답 시간 분위수 자체를 어떻게 다루는지는 [퍼센타일 지연 글](/posts/percentile-latency)에 있다.

흔한 실수도 정리해 둔다. 기준값을 첫 칸이나 마지막 칸으로 고정해서 정렬된 입력에서 느려진다. 같은 값이 많은 데이터에 2-way 분할을 쓴다. "k번째로 큰"을 오름차순 자리로 바꿀 때 `n − k`와 `k − 1`을 헷갈린다. 원본 배열을 그대로 넘겨서 호출한 쪽의 데이터 순서가 바뀐다.

## 얼마나 쪼개고 얼마나 합치나

분할 정복은 문제를 독립된 작은 조각으로 나누고, 조각의 답을 합친다. 얼마나 걸릴지는 조각이 몇 개인지(a), 얼마나 작아지는지(b), 나누고 합치는 데 얼마가 드는지(f(n))로 정해지고, 마스터 정리는 그중 어느 층이 일을 지배하는지 알려 준다. 퀵셀렉트는 조각을 하나만 남겨서 O(n)이 되고, 카라츠바는 조각 하나를 아껴서 지수를 낮춘다. 조각이 겹치기 시작하면 동적 계획법으로, 쪼개는 지점이 입력에 휘둘리면 무작위로 넘어간다.

## 면접에서 나올 만한 질문

### 분할 정복이 무엇이고 어떤 단계로 이루어지나요?

문제를 같은 모양의 작은 문제로 나누고(분할), 각각 재귀로 풀고(정복), 그 답을 합쳐(결합) 원래 답을 만드는 방법이다. 병합 정렬은 나누기가 공짜고 합치기에 일이 몰리고, 퀵 정렬은 기준값으로 가르는 나누기에 일이 몰린다. 이분 탐색과 퀵셀렉트처럼 나눈 뒤 한쪽만 푸는 경우도 분할 정복으로 본다.

### 정렬 없이 k번째로 큰 수를 어떻게 찾고, 왜 평균 O(n)인가요?

퀵셀렉트를 쓴다. 기준값으로 배열을 가른 뒤 기준값이 선 자리와 목표 자리를 비교해 답이 있는 쪽만 남긴다. 기준값이 대충 가운데에 서면 남는 크기가 n, n/2, n/4로 줄어서 비교 횟수의 합이 약 2n이다. 100만 개에서 재 보면 끝 쪽 k는 평균 1.9n, 가운데는 3.3n번 비교했다. 정렬은 양쪽을 다 처리하니 n log n이 된다.

### 마스터 정리를 설명하고 병합 정렬에 적용해 보세요.

`T(n) = aT(n/b) + f(n)`에서 잎의 개수 `n^(log_b a)`와 `f(n)`을 비교한다. f가 더 작으면 잎이 지배해 `n^(log_b a)`, 같으면 층마다 같은 일이 log n층 있어서 거기에 log n을 곱하고, 더 크면 뿌리가 지배해 `f(n)`이다. 병합 정렬은 a = 2, b = 2라 `n^(log₂2) = n`이고 합치기도 n이라 같은 경우, Θ(n log n)이다.

### 카라츠바 곱셈은 어떻게 n²보다 빨라지나요?

반으로 쪼갠 뒤 필요한 반 길이 곱셈 네 번 중 하나를 `(x1+x0)(y1+y0)`에서 이미 구한 두 곱을 빼는 방식으로 대신해 세 번으로 줄인다. 점화식이 `4T(n/2)+n`에서 `3T(n/2)+n`이 되어 복잡도가 n²에서 n^log₂3 ≈ n^1.585로 내려간다. 덧셈과 뺄셈이 늘어서 작은 수에서는 학교식이 빠르고, 실제 구현은 일정 크기 아래에서 학교식으로 전환한다.

### 분할 정복과 동적 계획법은 무엇이 다른가요?

하위 문제가 겹치는지가 다르다. 병합 정렬의 두 반쪽은 서로 다른 칸을 다뤄 같은 계산이 반복되지 않으니 저장할 이유가 없다. 피보나치처럼 같은 하위 문제가 여러 번 나오면 답을 표에 적어 두는 동적 계획법이 필요하고, 그대로 분할 정복으로 짜면 지수 시간이 된다. 독립된 하위 문제는 병렬로 돌리기도 쉽다.

### 퀵셀렉트의 최악은 언제 생기고 어떻게 막나요?

기준값이 매번 최솟값이나 최댓값이면 한 개씩만 줄어 O(n²)이다. 마지막 칸을 기준값으로 고정하고 정렬된 2만 개에서 최솟값을 찾으면 비교가 정확히 n(n−1)/2번 나왔다. 무작위 기준값으로 평균을 지키고, 같은 값이 많으면 3-way 분할을 쓴다. 최악까지 O(n)으로 보장하려면 median of medians를 쓰는데 상수가 커서, 라이브러리는 평소엔 퀵셀렉트를 쓰다 깊어지면 전환하는 인트로셀렉트를 쓴다.

### median of medians는 왜 최악에도 O(n)인가요?

5개씩 묶어 중앙값을 뽑고, 그 중앙값들의 중앙값을 재귀로 구해 기준값으로 쓰면 양쪽에 각각 최소 30% 정도의 원소가 남는 게 보장된다. 그래서 다음 단계는 많아야 7n/10이고, 중앙값을 구하는 재귀가 n/5라 `T(n) ≤ T(n/5) + T(7n/10) + n`이다. 1/5 + 7/10이 1보다 작으니 층마다 일이 줄어 전체가 O(n)이다.

### 재귀 깊이는 왜 신경 써야 하고 어떻게 줄이나요?

자바스크립트 엔진의 호출 스택은 만 단위 깊이에서 넘친다. Node 22에서 단순 재귀는 12,555번에서 RangeError가 났다. 반씩 쪼개면 깊이가 log n이라 괜찮지만, 퀵 정렬 최악처럼 쪼개기가 치우치면 깊이가 n이 된다. 하위 문제가 하나면 반복문으로 바꾸고, 둘이면 작은 쪽만 재귀로 부르고 큰 쪽은 반복으로 돌려 깊이를 log n 안에 묶는다.
