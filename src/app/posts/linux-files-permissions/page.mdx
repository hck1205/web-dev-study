정적 파일 몇 개를 `/home/alice/site`에 두고 nginx로 띄웠다. 브라우저에는 403 Forbidden이 뜨고, nginx 에러 로그에는 이런 줄이 남는다.

```text
2026/10/20 14:29:29 [error] 1754#1754: *1 "/home/alice/site/index.html" is forbidden (13: Permission denied), client: 127.0.0.1, server: , request: "GET / HTTP/1.1", host: "127.0.0.1:18081"
```

`index.html`은 `-rw-r--r--`라서 누구나 읽을 수 있다. 그런데도 거부된다. 범인은 파일이 아니라 그 위의 디렉터리 `/home/alice`다. Ubuntu 21.04부터 새로 만든 홈 디렉터리는 `750`이라서, nginx 워커가 쓰는 `www-data`는 그 안으로 들어갈 수조차 없다. 나도 처음엔 파일 권한만 들여다보다 시간을 버렸다.

이 글은 이런 `Permission denied`를 만났을 때 커널이 무엇을 어떤 순서로 검사하는지부터 보고, 숫자 권한과 umask, 특수 비트 세 개, ACL, 컨테이너에서 UID가 어긋나는 문제까지 간다. 기준은 Ubuntu 24.04 LTS이고 22.04도 같다. 실습은 `alice`(UID 1001), `bob`(UID 1002), 그룹 `deploy`(GID 1003)를 만들어 놓고 했다.

## ls -l 한 줄 읽기

권한 이야기는 `ls -l`의 한 줄에서 시작한다. 실습용 앱 디렉터리에 DB 비밀번호가 든 `.env`를 두고, 주인은 `alice`, 그룹은 `deploy`로 맞췄다.

```bash
# 소유자와 권한을 한 줄로 본다
```

열 글자 중 뒤의 아홉 글자가 권한이다. 세 글자씩 끊어서 소유자, 그룹, 나머지에게 각각 읽기, 쓰기, 실행을 허락한다. 권한 줄 끝에 `+`가 붙어 있으면 ACL이 걸려 있다는 뜻이고, 뒤에서 다시 본다.

## 커널은 세 칸 중 하나만 고른다

`bob`이 이 파일을 읽으려 하면 어떻게 될까. 많이 하는 오해가 "세 칸을 다 보고 하나라도 허락하면 된다"는 것이다. 실제로는 커널이 요청한 프로세스가 누구인지 보고 세 칸 중 딱 한 칸만 고른다. 고른 칸에 권한이 없으면 다른 칸에 있어도 거부한다.

한 칸만 고른다는 규칙 때문에 이상해 보이는 일도 생긴다. 권한이 `---r--r--`인 파일은 주인만 못 읽고 다른 사람은 다 읽는다. 주인이라서 소유자 칸이 골라졌고, 거기가 비어 있기 때문이다. 실무에서 일부러 쓸 일은 없지만, 권한 칸이 OR가 아니라는 걸 보여 주는 예로 기억해 둘 만하다.

root는 검사를 건너뛴다고 했는데 실행만은 예외다. 읽기와 쓰기는 `000` 파일도 통과하지만, 실행은 세 칸 중 하나라도 `x`가 있어야 한다.

```bash
# 모든 권한을 지운 파일을 root와 alice로 읽어 본다
echo top > /srv/app/zero && sudo chmod 000 /srv/app/zero
sudo cat /srv/app/zero
sudo -u alice cat /srv/app/zero

# x가 하나도 없는 스크립트는 root도 실행하지 못한다
sudo chmod 644 /srv/app/t.sh && sudo /srv/app/t.sh
```

```text
top
cat: /srv/app/zero: Permission denied
/bin/bash: line 1: /srv/app/t.sh: Permission denied
```

root가 통과하는 이유는 UID가 0이라서라기보다 `CAP_DAC_OVERRIDE`라는 능력(capability)을 갖고 있어서다. 컨테이너 런타임이 이 능력을 빼면 컨테이너 안 root도 남의 파일을 못 읽는다.

## 디렉터리의 r, w, x는 뜻이 다르다

처음 403의 원인이 여기 있다. 디렉터리는 "이름 → inode 번호" 목록이 든 파일이라서, 같은 세 글자가 다른 뜻이 된다.

- `r`: 목록을 읽는다. 안에 어떤 이름이 있는지 볼 수 있다.
- `w`: 목록을 고친다. 안에 파일을 만들고, 지우고, 이름을 바꾼다. 지우는 데 파일 자체의 권한은 상관없다.
- `x`: 지나간다. 안에 있는 이름으로 들어가 inode에 닿는다. 그래야 그 아래 파일을 열 수 있다.

`r`만 있고 `x`가 없으면 이름은 보이는데 아무것도 열 수 없다. 반대로 `x`만 있으면 목록은 못 보지만 이름을 알면 열 수 있다.

```bash
# r만 있는 디렉터리: 이름은 보이지만 속성도 내용도 못 본다
sudo chmod 644 /srv/app/nox
sudo -u bob ls -l /srv/app/nox

# x만 있는 디렉터리: 목록은 못 보지만 이름을 알면 연다
sudo chmod 711 /srv/app/nox
sudo -u bob ls /srv/app/nox
sudo -u bob cat /srv/app/nox/f
```

```text
ls: cannot access '/srv/app/nox/f': Permission denied
total 0
-????????? ? ? ? ?            ? f
ls: cannot open directory '/srv/app/nox': Permission denied
hi
```

물음표로 가득한 줄이 "r은 있고 x는 없다"의 모양이다. 이름은 목록에서 읽었지만 inode까지 못 가서 크기도 권한도 모른다. `711`은 홈 디렉터리에서 가끔 쓰는 설정인데, 남이 내 파일 목록은 못 보지만 `~/public_html` 같은 정해진 경로는 열 수 있게 한다.

이렇게 경로 전체를 한 번에 보여 주는 명령이 `namei -l`이다. `Permission denied`가 나오면 `ls -l` 대신 이걸 먼저 친다.

```bash
# 경로의 칸마다 권한과 소유자를 보여 준다
namei -l /home/alice/site/index.html

# nginx 워커와 같은 사용자로 실제로 열어 본다
sudo -u www-data cat /home/alice/site/index.html
```

```text
f: /home/alice/site/index.html
drwxr-xr-x root  root  /
drwxr-xr-x root  root  home
drwxr-x--- alice alice alice
drwxr-xr-x alice alice site
-rw-r--r-- alice alice index.html
cat: /home/alice/site/index.html: Permission denied
```

세 번째 줄 `drwxr-x--- alice alice alice`에서 끝이 `---`다. 고치는 방법은 여럿이다. `chmod o+x /home/alice`가 가장 짧지만 홈 디렉터리를 모두에게 지나갈 수 있게 연다. 더 나은 방법은 사이트를 `/var/www/site`나 `/srv/site`처럼 서비스용 경로로 옮기는 것이다. 홈 아래에 꼭 둬야 하면 `www-data`에게만 지나갈 권한을 주는 ACL(`setfacl -m u:www-data:x /home/alice`)이 범위가 좁다.

## 숫자 세 자리로 쓰는 권한

`chmod 640`의 숫자는 세 칸을 각각 8진수 한 자리로 쓴 것이다. `r`=4, `w`=2, `x`=1을 더한다. `rw-`는 4+2=6, `r--`는 4, `---`는 0이라 `640`이다.

숫자 방식은 세 칸을 한꺼번에 덮어쓴다. 일부만 바꾸고 싶으면 기호 방식을 쓴다. `u`(소유자), `g`(그룹), `o`(나머지), `a`(모두)에 `+`, `-`, `=`를 붙인다.

```bash
# 세 칸을 한 번에 정한다
chmod u=rwx,g=rx,o= /srv/app/deploy.sh && stat -c '%a %A %n' /srv/app/deploy.sh

# 나머지에 읽기를 더하고 그룹 실행만 뺀다. 다른 비트는 그대로 둔다
chmod o+r,g-x /srv/app/deploy.sh && stat -c '%a %A %n' /srv/app/deploy.sh
```

```text
750 -rwxr-x--- /srv/app/deploy.sh
744 -rwxr--r-- /srv/app/deploy.sh
```

`chmod -R 755`를 디렉터리 트리에 거는 실수가 흔하다. 파일까지 실행 가능해지고, 반대로 `chmod -R 644`를 걸면 디렉터리에서 `x`가 빠져 아무도 못 들어간다. 디렉터리와 파일을 나누려면 `find`를 쓰거나, 대문자 `X`(디렉터리이거나 이미 누군가에게 x가 있을 때만 x를 준다)를 쓴다.

```bash
# 디렉터리는 755, 파일은 644로 나눠서 맞춘다
sudo find /srv/app/releases -type d -exec chmod 755 {} +
sudo find /srv/app/releases -type f -exec chmod 644 {} +

# 같은 일을 한 줄로: 읽기는 모두, 디렉터리에만 x
sudo chmod -R u=rwX,go=rX /srv/app/releases
```

    if (x === "t" || x === "T") special += 1;
    digits += n;
  }
  return special ? String(special) + digits : digits;
}`}

## 새 파일의 권한은 umask가 깎는다

`touch`로 만든 파일이 `644`, `mkdir`로 만든 디렉터리가 `755`인 이유는 umask다. 프로그램은 보통 파일을 `666`, 디렉터리를 `777`로 만들어 달라고 요청하고, 커널이 거기서 umask에 켜진 비트를 지운다. Ubuntu의 기본 umask `022`는 그룹과 나머지에서 쓰기를 지운다.

```bash
# 지금 셸의 umask (숫자, 기호)
umask
umask -S

# umask 027로 바꾸고 파일과 디렉터리를 만들어 본다 (이 셸에서만 바뀐다)
umask 027 && touch b.txt && mkdir e && ls -ld b.txt e
```

```text
0022
u=rwx,g=rx,o=rx
-rw-r----- 1 alice alice    0 Oct 20 14:28 b.txt
drwxr-x--- 2 alice alice 4096 Oct 20 14:28 e
```

여기서 "빼기"라고 외우면 틀린다. umask는 비트를 지우는(`요청 & ~umask`) 연산이다. umask `111`이면 `666 - 111 = 555`가 될 것 같지만, 파일 요청에는 원래 x 비트가 없으니 지울 것도 없어서 결과는 `666`이다.

umask는 프로세스 속성이라 셸에서 바꿔도 이미 떠 있는 서비스에는 영향이 없다. Ubuntu에서 로그인 셸의 기본값은 `/etc/login.defs`의 `UMASK 022`를 pam_umask가 적용한 것이다. systemd 서비스는 유닛 파일의 `UMask=0027`로 정한다. 업로드 파일이 다른 사람에게 보이면 안 되는 서비스라면 코드에서 `chmod`를 매번 하기보다 서비스의 umask를 정하는 편이 빠뜨릴 일이 없다.

setuid는 실행 파일에 붙는다. 이 파일을 실행하면 프로세스가 실행한 사람이 아니라 파일 주인의 권한으로 돈다. `passwd`가 일반 사용자에게 root만 쓸 수 있는 `/etc/shadow`를 고치게 해 주는 방법이다.

```bash
# setuid가 붙은 파일 (소유자 칸의 x 자리가 s)
ls -l /usr/bin/passwd /usr/bin/sudo

# 시스템에서 setuid 파일 찾기. 모르는 파일이 있으면 의심한다
sudo find /usr/bin -perm -4000 -type f | sort
```

```text
-rwsr-xr-x 1 root root  64152 May 30  2024 /usr/bin/passwd
-rwsr-xr-x 1 root root 282032 Sep 21 18:37 /usr/bin/sudo
/usr/bin/chfn
/usr/bin/chsh
/usr/bin/gpasswd
/usr/bin/mount
/usr/bin/newgrp
/usr/bin/passwd
/usr/bin/su
/usr/bin/sudo
/usr/bin/umount
```

setuid root 파일은 버그 하나가 곧 root 권한 탈취다. 그래서 목록을 주기적으로 비교하고, 이미지에서는 필요 없는 것을 지운다. 리눅스는 셸 스크립트의 setuid를 무시한다(`#!`로 시작하는 파일은 인터프리터가 실행되기 때문에 경쟁 조건이 생긴다). 스크립트에 `chmod u+s`를 걸어도 아무 일도 일어나지 않는다. 컨테이너에서 `allowPrivilegeEscalation: false`를 켜면 커널의 `no_new_privs`가 걸려 setuid로 권한이 올라가지 않는다.

setgid는 디렉터리에서 자주 쓴다. setgid 디렉터리 안에 만든 파일은 만든 사람의 기본 그룹이 아니라 디렉터리의 그룹을 받는다. 여러 사람이 같이 쓰는 배포 디렉터리에 쓴다.

```bash
# 같은 사용자가 같은 그룹 디렉터리 두 곳에 파일을 만든다. reports만 setgid
sudo chmod 2775 /srv/app/shared/reports
sudo chmod 775 /srv/app/shared/plain
sudo -u alice touch /srv/app/shared/reports/r1.csv /srv/app/shared/plain/r1.csv
ls -l /srv/app/shared/reports/r1.csv /srv/app/shared/plain/r1.csv
```

```text
-rw-r--r-- 1 alice alice  0 Oct 20 14:28 /srv/app/shared/plain/r1.csv
-rw-r--r-- 1 alice deploy 0 Oct 20 14:28 /srv/app/shared/reports/r1.csv
```

`plain` 쪽 파일은 `alice` 그룹이라 `deploy`의 다른 사람이 못 고친다. 협업 디렉터리는 setgid와 umask `002`를 같이 써야 그룹이 쓸 수 있는 파일이 생긴다.

sticky 비트는 누구나 쓸 수 있는 디렉터리에서 남의 파일을 지우지 못하게 한다. 앞에서 디렉터리에 `w`가 있으면 파일 권한과 상관없이 지울 수 있다고 했는데, sticky가 그 규칙에 "파일 주인이거나 디렉터리 주인일 때만"이라는 조건을 붙인다. `/tmp`가 `1777`인 이유다.

```bash
# sticky가 있는 공용 디렉터리에서 bob이 alice의 파일을 지워 본다
sudo -u bob rm -f /srv/app/drop/alice.txt

# sticky를 빼면 같은 명령이 성공한다
sudo chmod 0777 /srv/app/drop && sudo -u bob rm -f /srv/app/drop/alice.txt && ls -l /srv/app/drop
```

```text
rm: cannot remove '/srv/app/drop/alice.txt': Operation not permitted
total 0
```

에러 문구가 `Permission denied`(EACCES)가 아니라 `Operation not permitted`(EPERM)다. 권한 비트가 부족한 게 아니라 규칙상 허용되지 않는 동작이라는 뜻이다. 일반 사용자가 `chown`으로 파일을 남에게 넘기려 할 때도 같은 EPERM이 나온다. 리눅스에서 소유자를 바꾸는 건 root만 할 수 있고, 일반 사용자는 자기가 속한 그룹으로 그룹만 바꿀 수 있다.

대문자 `S`, `T`는 특수 비트는 켜져 있는데 그 자리의 `x`가 꺼져 있다는 뜻이다. `-rwxr-Sr--`를 보면 setgid를 걸고 그룹 실행을 빼 버린 것이라 대개 실수다.

## 한 사람만 더 허락하는 ACL

소유자 한 명, 그룹 하나로는 부족할 때가 있다. 백업 계정 `bob`에게만 `.env` 읽기를 주고 싶은데 `deploy` 그룹에 넣기는 싫다. 이럴 때 ACL(접근 제어 목록)을 쓴다. Ubuntu에서는 `acl` 패키지에 `setfacl`, `getfacl`이 들어 있다.

```bash
# acl 도구 설치
sudo apt install -y acl

# bob에게만 읽기를 더한다
sudo setfacl -m u:bob:r /srv/app/shared/.env
ls -l /srv/app/shared/.env
getfacl /srv/app/shared/.env
```

```text
-rw-r-----+ 1 alice deploy 19 Oct 20 14:28 /srv/app/shared/.env
getfacl: Removing leading '/' from absolute path names
# file: srv/app/shared/.env
# owner: alice
# group: deploy
user::rw-
user:bob:r--
group::r--
mask::r--
other::---
```

권한 끝의 `+`가 ACL이 있다는 표시다. 이제 `bob`이 읽을 수 있다. 문제는 `mask` 줄이다. ACL이 있으면 `ls -l`의 그룹 칸은 더 이상 그룹 권한이 아니라 mask를 보여 주고, mask는 추가한 사용자·그룹 항목의 상한이 된다. 그래서 ACL이 걸린 파일에 누군가 `chmod 600`을 하면 이렇게 된다.

```bash
# 평소처럼 chmod 600으로 "잠근다"
sudo chmod 600 /srv/app/shared/.env
getfacl --omit-header /srv/app/shared/.env
sudo -u bob cat /srv/app/shared/.env
```

```text
user::rw-
user:bob:r--	#effective:---
group::r--	#effective:---
mask::---
other::---

cat: /srv/app/shared/.env: Permission denied
```

`user:bob:r--` 항목은 그대로 남아 있는데 `#effective:---`다. chmod가 그룹 칸 대신 mask를 0으로 바꿨기 때문이다. 배포 스크립트의 `chmod` 한 줄이 백업 작업을 조용히 깨뜨리는 전형적인 경로다. ACL을 쓰는 디렉터리라면 `getfacl`로 effective 값을 같이 본다. 다 걷어낼 때는 `setfacl -b`를 쓴다.

디렉터리에는 기본 ACL(`-d`)을 걸 수 있다. 안에 새로 생기는 파일이 이 ACL을 물려받는다. 하나 알아 둘 점은 기본 ACL이 있는 디렉터리에서는 umask가 적용되지 않는다는 것이다.

```bash
# uploads 아래 새 파일은 deploy 그룹이 읽고 쓸 수 있게
sudo setfacl -d -m g:deploy:rwX /srv/app/shared/uploads

# umask 077로 만들어도 그룹 쓰기가 살아 있다
sudo -u alice bash -c 'umask 077; touch /srv/app/shared/uploads/u1.jpg'
getfacl --omit-header /srv/app/shared/uploads/u1.jpg
```

```text
user::rw-
group::r-x	#effective:r--
group:deploy:rwx	#effective:rw-
mask::rw-
other::r--
```

umask `077`이었다면 `600`이 됐을 파일이 그룹 쓰기와 나머지 읽기까지 받았다. 기본 ACL을 걸 때는 나머지 칸도 같이 정해 둬야 한다(`setfacl -d -m o::- ...`). 그리고 ACL은 파일 시스템이 지원해야 한다. ext4와 XFS는 기본으로 되고, `tar`나 `rsync`로 옮길 때는 `--acls`(`rsync -A`)를 줘야 따라간다.

## 그룹에 넣었는데 여전히 거부된다

`bob`을 `deploy` 그룹에 넣고 바로 다시 시도했는데 여전히 `Permission denied`다. 그룹 목록은 프로세스가 로그인할 때 받아 두는 속성이라, `/etc/group`을 바꿔도 이미 떠 있는 셸과 서비스는 옛 목록을 쓴다.

```bash
# bob의 셸이 떠 있는 상태에서 그룹에 넣는다
sudo usermod -aG deploy bob

# 떠 있는 프로세스가 가진 그룹 목록 (커널이 실제로 쓰는 값)
grep Groups /proc/<bob 셸 PID>/status

# /etc/group 기준의 목록
id bob
```

```text
Groups:	1002 
uid=1002(bob) gid=1002(bob) groups=1002(bob),1003(deploy)
```

`id bob`은 설정 파일을 읽어서 1003이 보이지만, 프로세스의 `Groups`에는 없다. 다시 로그인하거나 `newgrp deploy`로 새 셸을 연다. 서비스라면 재시작해서 프로세스를 새로 띄워야 반영된다(`systemctl restart`). `usermod -G`에서 `-a`를 빼먹으면 기존 보조 그룹이 전부 사라지는 것도 흔한 실수다. `sudo` 그룹이 빠지면 그 계정은 더 이상 관리자가 아니다.

## 컨테이너에서는 숫자가 맞아야 한다

커널은 파일 주인을 숫자로만 저장한다. 컨테이너는 호스트와 커널을 같이 쓰니, 컨테이너 안 `node` 사용자(UID 1000)가 만든 파일은 호스트에서 UID 1000의 주인, Ubuntu라면 `ubuntu` 계정 소유로 보인다. Docker의 바인드 마운트에서 이 문제가 어떻게 보이는지는 [Docker 네트워크와 볼륨](/posts/docker-network-volume)에, `USER`를 바꾼 뒤 이미지 안 경로에서 `EACCES`가 나는 경우는 [Dockerfile과 이미지 레이어](/posts/dockerfile-image-layers)에 있다. 여기서는 쿠버네티스에서 볼륨을 붙일 때를 본다.

새로 만든 볼륨은 대개 `root:root 755`로 시작한다. 이미지가 `USER 1000`이거나 Pod에 `runAsUser: 1000`이 있으면 앱은 거기에 쓰지 못한다. 컨테이너 대신 `setpriv`로 같은 상황을 만들었다.

```bash
# 새 볼륨처럼 root 소유 755 디렉터리
sudo mkdir -p /srv/vol/data && ls -ldn /srv/vol/data

# UID 1000, 보조 그룹 없이 앱을 띄운다 (runAsUser: 1000과 같은 상태)
sudo setpriv --reuid=1000 --regid=1000 --clear-groups \
  node -e "require('fs').writeFileSync('/srv/vol/data/app.log','x')"
```

```text
drwxr-xr-x 2 0 0 4096 Oct 20 14:28 /srv/vol/data
Error: EACCES: permission denied, open '/srv/vol/data/app.log'
    at Object.writeFileSync (node:fs:2437:20)
```

쿠버네티스의 `fsGroup`은 이 문제를 그룹으로 푼다. kubelet이 볼륨을 붙이면서 소유 그룹을 `fsGroup`으로 바꾸고 디렉터리에 setgid를 걸며, 컨테이너 프로세스의 보조 그룹에 그 GID를 넣는다. 앞에서 본 setgid 디렉터리와 그룹 권한을 자동으로 맞춰 주는 셈이다. 아래 그림에서 단계를 넘기면 그 과정이 보인다.

```bash
# 방법 2 (fsGroup 방식): 그룹을 맞추고 setgid, 앱에 그 그룹을 준다
sudo chown 0:2000 /srv/vol/data && sudo chmod 2775 /srv/vol/data
sudo setpriv --reuid=1000 --regid=1000 --groups=2000 \
  node -e "require('fs').writeFileSync('/srv/vol/data/b.log','x'); console.log('ok')"
ls -ln /srv/vol/data
```

```text
ok
total 8
-rw-r--r-- 1 1000 1000 1 Oct 20 14:28 app.log
-rw-r--r-- 1 1000 2000 1 Oct 20 14:28 b.log
```

Pod에는 이렇게 쓴다. `runAsUser`, `fsGroup`, `runAsNonRoot` 같은 보안 설정 전체는 [SecurityContext 글](/posts/k8s-security-context)에서 따로 다룬다.

```yaml
spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 1000
    fsGroup: 2000
    # 볼륨 최상위의 그룹이 이미 맞으면 하위 파일을 다시 훑지 않는다
    fsGroupChangePolicy: OnRootMismatch
```

현장에서 만나는 부작용이 하나 있다. 기본 정책(`Always`)에서 kubelet은 마운트할 때마다 볼륨 안의 모든 파일 그룹을 재귀로 바꾼다. 파일이 수백만 개인 볼륨이면 Pod가 `ContainerCreating`에서 몇 분씩 멈춘다. 이벤트에 특별한 에러가 없는데 큰 볼륨을 붙인 Pod만 느리게 뜬다면 이걸 의심하고 `OnRootMismatch`를 쓴다. 또 `fsGroup`은 볼륨 플러그인이 소유권 변경을 지원할 때만 동작한다. NFS 같은 일부 볼륨에서는 무시되니, 그때는 NFS 서버 쪽 디렉터리 소유자를 앱 UID에 맞추거나 init 컨테이너로 `chown`한다.

## Permission denied를 만났을 때 보는 순서

에러 한 줄만 보고 `chmod 777`을 치기 전에 이 순서로 좁힌다. 777은 문제를 덮을 뿐이고, 비밀 값 파일이면 누구나 읽게 되고 디렉터리면 누구나 파일을 바꿔치기할 수 있다.

1. 누가 열었나. 사람이 아니라 프로세스의 UID와 그룹을 본다. `ps -o user,group,pid,cmd -C nginx`나 `/proc/<PID>/status`의 `Uid`, `Gid`, `Groups` 줄이다. 웹 서버는 대개 마스터가 root, 워커가 `www-data`다.
2. 경로 전체를 본다. `namei -l <경로>`로 칸마다 `x`가 있는지 확인한다. 막힌 칸이 파일이 아니라 상위 디렉터리인 경우가 절반이다.
3. 그 사용자로 직접 해 본다. `sudo -u www-data cat <경로>`나 `sudo -u www-data test -w <디렉터리> && echo ok`. 추측 대신 재현이다.
4. ACL을 본다. `ls -l`에 `+`가 있으면 `getfacl`로 effective 값을 본다.
5. 권한 비트 밖의 원인을 본다. 비트가 다 맞는데도 막히면 읽기 전용 마운트(`findmnt -no OPTIONS <경로>`의 `ro`), `noexec` 마운트(실행만 막힘), 변경 불가 속성(`lsattr`의 `i`), AppArmor·SELinux 거부(`dmesg`나 `journalctl -k`의 `apparmor="DENIED"`)다. RHEL 계열이라면 SELinux 라벨이 가장 흔하고 `ls -Z`와 `ausearch -m avc`로 본다.

`strace`로 실제로 실패한 시스템 콜과 경로를 찍어 보는 것도 빠르다. 프로그램이 에러 메시지에 경로를 안 남길 때 쓴다.

```bash
# 파일 관련 시스템 콜 중 실패한 것만 본다
sudo strace -f -e trace=%file -Z -u www-data cat /home/alice/site/index.html
```

```text
openat(AT_FDCWD, "/home/alice/site/index.html", O_RDONLY) = -1 EACCES (Permission denied)
```

## 칸 하나를 고르고, 경로를 다 지난다

리눅스 권한은 프로세스의 UID와 그룹으로 소유자·그룹·나머지 중 한 칸을 고르고, 경로의 모든 디렉터리에서 `x`를, 마지막 파일에서 요청한 권한을 검사하는 일이다. 새 파일의 권한은 umask가 깎고, setgid와 기본 ACL은 상속을, sticky는 삭제 규칙을 바꾼다. 컨테이너에서는 이름이 아니라 숫자가 맞아야 하고, 쿠버네티스는 그 숫자를 `fsGroup`으로 맞춘다. 프로세스가 누구로 도는지는 [리눅스 프로세스와 시그널](/posts/linux-processes-signals)에서 이어서 본다.

## 면접에서 나올 만한 질문

### 파일 권한 rwxr-x---를 설명해 보세요.

소유자는 읽기·쓰기·실행, 그룹은 읽기·실행, 나머지는 아무것도 못 한다는 뜻이고 숫자로는 750이다. r=4, w=2, x=1을 칸마다 더한다. 커널은 프로세스가 주인이면 소유자 칸, 아니고 그룹에 속하면 그룹 칸, 둘 다 아니면 나머지 칸 중 하나만 골라서 검사한다.

### 디렉터리에서 r과 x의 차이는 무엇인가요?

r은 디렉터리 안의 이름 목록을 읽는 권한이고, x는 그 디렉터리를 지나가 안의 파일에 닿는 권한이다. x 없이 r만 있으면 이름은 보이지만 파일을 열지 못하고, x만 있으면 목록은 못 봐도 이름을 알면 연다. 파일을 열려면 경로의 모든 상위 디렉터리에 x가 있어야 해서, 파일 권한이 644여도 홈 디렉터리가 750이면 웹 서버가 403을 낸다.

### umask 022이면 새 파일 권한은 몇이 되나요? 왜 빼기가 아닌가요?

파일은 644, 디렉터리는 755가 된다. 프로그램이 요청한 666이나 777에서 umask에 켜진 비트를 지우는 `요청 & ~umask` 연산이라서, 요청에 없던 비트는 지울 것도 없다. 그래서 umask 111로 파일을 만들면 555가 아니라 666이다. 서비스의 umask는 systemd 유닛의 `UMask=`로 정한다.

### setuid, setgid, sticky 비트는 각각 무엇인가요?

setuid는 실행 파일을 파일 주인의 권한으로 돌게 하고(`passwd`), setgid는 디렉터리에 걸면 새 파일이 디렉터리의 그룹을 물려받게 한다. sticky는 누구나 쓸 수 있는 디렉터리에서 파일 주인과 디렉터리 주인만 파일을 지울 수 있게 해서 /tmp가 1777이다. setuid root 파일은 공격 표면이라 목록을 관리하고, 컨테이너에서는 `allowPrivilegeEscalation: false`로 막는다.

### 그룹에 사용자를 추가했는데 왜 여전히 권한이 없나요?

그룹 목록은 로그인할 때 프로세스에 들어가는 속성이라 이미 떠 있는 셸이나 서비스에는 반영되지 않는다. `/proc/<PID>/status`의 Groups 줄로 실제 값을 확인하고, 다시 로그인하거나 서비스를 재시작한다. `usermod -G`에 `-a`를 빼먹으면 기존 보조 그룹이 다 지워지는 것도 함께 확인한다.

### ACL을 걸어 둔 파일에 chmod 600을 하면 어떻게 되나요?

ACL이 있으면 ls의 그룹 칸은 mask를 나타내고, chmod는 그 mask를 바꾼다. 그래서 chmod 600을 하면 mask가 ---가 되어 추가한 사용자·그룹 항목이 남아 있어도 effective 권한이 사라진다. getfacl의 `#effective` 표시로 확인하고, ACL을 쓰는 경로에서는 chmod 대신 setfacl로 관리한다.

### 쿠버네티스에서 볼륨에 쓰기가 안 될 때 어떻게 해결하나요?

커널이 숫자 UID·GID로 검사하기 때문에, 볼륨이 root 소유이고 앱이 runAsUser 1000으로 돌면 EACCES가 난다. `fsGroup`을 주면 kubelet이 볼륨의 그룹을 바꾸고 setgid를 걸며 프로세스에 그 그룹을 넣어 준다. 파일이 많은 볼륨은 재귀 변경 때문에 Pod 시작이 느려지니 `fsGroupChangePolicy: OnRootMismatch`를 쓰고, fsGroup을 지원하지 않는 NFS 같은 볼륨은 서버 쪽 소유자나 init 컨테이너로 맞춘다.

### Permission denied가 나면 어떤 순서로 확인하나요?

먼저 실제로 연 프로세스의 UID와 그룹을 확인하고, `namei -l`로 경로의 모든 칸을 본 뒤, 그 사용자로 `sudo -u`를 써서 재현한다. 비트가 맞는데도 막히면 ACL mask, 읽기 전용이나 noexec 마운트, immutable 속성, AppArmor·SELinux 거부를 차례로 본다. chmod 777은 원인을 가리고 보안 구멍을 남기니 쓰지 않는다.
