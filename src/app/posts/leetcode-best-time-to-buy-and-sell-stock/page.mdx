주식 차트를 보다가 "그때 샀다가 그때 팔았으면 얼마 벌었을까"를 계산해 본 적이 있을 것이다. 이 문제가 딱 그 계산이다. 슬라이딩 윈도 패턴의 첫 문제로 자주 나오지만, 실제로 풀어 보면 창(window)보다 "지금까지의 최솟값"이라는 생각이 먼저 떠오른다. 그 둘이 같은 이야기라는 걸 보는 게 이 글의 목표 중 하나다.

이 글에서는 같은 문제를 일곱 가지로 푼다. 모든 쌍을 보는 브루트포스, 반으로 나눠 푸는 분할 정복, 뒤에서부터 최댓값을 쌓는 배열, 한 번 훑기, 두 포인터 창, 하루 변화량에 쓰는 카데인 알고리즘, 상태 DP다. 마지막 상태 DP는 이 문제의 형제들(여러 번 거래, k번 거래, 수수료, 쿨다운)을 한 틀로 푸는 열쇠라 조금 길게 다룬다. 문제 원문은 [LeetCode 121](https://leetcode.com/problems/best-time-to-buy-and-sell-stock/)에 있다. 코드는 모두 Node.js 22, Python 3.13, Java(javac)로 실제로 돌려 본 것이다.

## 한 번 사고 한 번 판다

문제를 내 말로 줄이면 이렇다. 날짜 순서대로 주가가 담긴 배열 `prices`가 주어진다. 어느 하루에 한 주를 사고, 그보다 뒤의 하루에 판다. 거래는 딱 한 번만 할 수 있다. 얻을 수 있는 가장 큰 이익을 구한다. 이익을 낼 방법이 없으면 0을 돌려준다.

풀이 선택에 영향을 주는 제약은 두 가지다.

- 배열 길이는 1 이상 10만 이하다. 모든 쌍을 보면 약 50억 번이라 시간 안에 못 끝난다. O(n) 또는 O(n log n)이 필요하다.
- 가격은 0 이상 1만 이하다. 이익도 1만을 넘지 않으니 어느 언어에서도 정수 오버플로는 걱정하지 않아도 된다.

"사는 날이 파는 날보다 앞"이라는 조건이 이 문제의 전부다. 이 조건이 없으면 그냥 최댓값에서 최솟값을 빼면 된다. 조건이 있기 때문에 순서를 따져야 한다.

## 손으로 먼저 풀어 보기

예시로 `[8, 3, 6, 2, 7, 5]`를 쓴다. 인덱스는 0부터 센다. 0번 날 8원, 1번 날 3원, 2번 날 6원, 3번 날 2원, 4번 날 7원, 5번 날 5원이다.

파는 날을 하나씩 정하고, 그날보다 앞에서 가장 싼 날을 찾아본다.

```text
파는 날   가격   그 앞의 가장 싼 값   이익
  1        3        8               -5 (안 판다)
  2        6        3                3
  3        2        3               -1 (안 판다)
  4        7        2                5   ← 최대
  5        5        2                3
```

답은 5다. 3번 날 2원에 사서 4번 날 7원에 판다. 표의 세 번째 열 "그 앞의 가장 싼 값"이 왼쪽에서 오른쪽으로 가며 8 → 3 → 3 → 2 → 2로 변한다. 이 열은 매번 새로 계산할 필요가 없다. 이전 값과 오늘 값 중 작은 쪽이면 된다. 이 관찰 하나가 O(n) 풀이의 전부다.

함정도 하나 보인다. 전체 최솟값은 2(3번 날), 전체 최댓값은 8(0번 날)이다. 8 − 2 = 6을 답이라고 하면 틀린다. 8원은 2원보다 앞선 날이라 팔 수 없다.

## 모든 짝을 다 해 보기

가장 먼저 떠오르는 방법은 사는 날 `i`와 파는 날 `j`(`i < j`)를 전부 짝지어 보는 것이다. 문제를 그대로 코드로 옮겼으니 틀릴 일이 거의 없다. 다른 풀이를 검증할 정답지로도 쓴다.

```js
function maxProfitBrute(prices) {
  let best = 0; // 거래를 안 하면 0이니 0에서 시작한다
  for (let i = 0; i < prices.length; i++) {       // 사는 날
    for (let j = i + 1; j < prices.length; j++) { // 파는 날은 사는 날 뒤
      best = Math.max(best, prices[j] - prices[i]);
    }
  }
  return best;
}
```

짝의 개수는 n(n − 1)/2라서 시간은 O(n²), 추가 공간은 O(1)이다. 길이 10만인 무작위 배열로 재 보니 이 환경의 Node.js 22에서 약 4초가 걸렸다. LeetCode 제한 시간을 넘긴다.

낭비가 어디서 나는지 보자. 파는 날 `j`를 고정하면 안쪽 반복문은 "`j` 앞에서 가장 싼 값"을 찾는다. 그런데 `j`가 하나 늘어날 때 그 범위는 한 칸만 늘어난다. 매번 처음부터 다시 훑을 이유가 없다. 이 낭비를 없애는 방법이 여러 갈래로 나뉜다.

## 반으로 나눠서 푸는 방법

정렬 알고리즘의 병합 정렬처럼 배열을 반으로 자르면 답은 셋 중 하나다.

1. 왼쪽 절반 안에서 사고판다.
2. 오른쪽 절반 안에서 사고판다.
3. 왼쪽에서 사고 오른쪽에서 판다.

1과 2는 재귀로 구한다. 3은 "왼쪽의 최솟값에서 사서 오른쪽의 최댓값에 판다"가 언제나 최선이다. 왼쪽의 모든 날은 오른쪽의 모든 날보다 앞서니 순서 조건이 저절로 지켜진다. 그래서 재귀 함수가 이익과 함께 구간의 최솟값과 최댓값도 돌려주게 만든다.

```js
function maxProfitDC(prices) {
  // [lo, hi] 구간의 최대 이익, 최솟값, 최댓값을 함께 돌려준다
  function solve(lo, hi) {
    if (lo >= hi) return { best: 0, min: prices[lo], max: prices[lo] };
    const mid = (lo + hi) >> 1;
    const L = solve(lo, mid);
    const R = solve(mid + 1, hi);
    const cross = R.max - L.min; // 왼쪽에서 사고 오른쪽에서 판다
    return {
      best: Math.max(L.best, R.best, cross),
      min: Math.min(L.min, R.min),
      max: Math.max(L.max, R.max),
    };
  }
  if (prices.length === 0) return 0;
  return solve(0, prices.length - 1).best;
}
```

복잡도를 따져 보면 재미있다. 최솟값과 최댓값을 매번 구간을 훑어서 구했다면 한 층에서 O(n), 층이 log n개라 O(n log n)이었을 것이다. 위 코드는 아래에서 올려 준 값을 비교만 하니 각 호출이 O(1)이고, 호출은 모두 2n − 1번이라 시간은 O(n)이다. 공간은 재귀 깊이만큼 O(log n)이다. 10만 개에서 4ms 정도였다.

면접에서 이 풀이를 먼저 꺼낼 필요는 없다. 다만 "O(n²)보다 나은 방법이 있나"에 막혔을 때 분할 정복은 거의 모든 배열 문제에서 한 번쯤 시도해 볼 만한 방향이고, 이 문제에서는 깔끔하게 성립한다. 재귀를 쓰기 때문에 한 번 훑기보다 상수가 크고 코드가 길다.

## 뒤에서부터 최댓값을 쌓아 두기

이번엔 사는 날을 고정해 본다. `i`에 산다면 `i` 뒤에서 가장 비싼 날에 파는 게 최선이다. "`i`부터 끝까지의 최댓값"을 배열 `sufMax`에 미리 만들어 두면 사는 날마다 O(1)로 이익을 구할 수 있다. 접미사(suffix) 최댓값이라고 부른다.

```js
function maxProfitSuffix(prices) {
  const n = prices.length;
  const sufMax = new Array(n);
  // 오른쪽 끝부터 "여기서부터 끝까지의 최댓값"을 채운다
  for (let i = n - 1; i >= 0; i--) {
    sufMax[i] = i === n - 1 ? prices[i] : Math.max(prices[i], sufMax[i + 1]);
  }
  let best = 0;
  for (let i = 0; i < n; i++) {
    best = Math.max(best, sufMax[i] - prices[i]); // i에 사고 그 뒤 최고가에 판다
  }
  return best;
}
```

예시에서 `sufMax`는 `[8, 7, 7, 7, 7, 5]`다. 3번 날에 사면 7 − 2 = 5가 나온다. `sufMax[i]`에 `prices[i]` 자신이 들어가도 괜찮다. 같은 날 사고팔면 이익이 0이고, 답의 하한이 원래 0이기 때문이다.

시간 O(n), 공간 O(n)이다. 앞쪽 최솟값(prefix min) 배열로 똑같이 할 수도 있다. 미리 계산해 두는 이 생각은 [누적 합](/posts/ds-array-matrix)과 같은 뿌리다. 한계는 배열 하나만큼의 메모리다. 그리고 두 번 훑어야 해서, 값이 하나씩 흘러 들어오는 스트림에서는 쓸 수 없다. 끝을 알아야 `sufMax`를 만들 수 있기 때문이다.

## 지금까지의 최저가만 기억한다

`sufMax`를 거꾸로 생각하면 배열이 필요 없어진다. 파는 날을 왼쪽부터 늘려 가면 "그 앞의 가장 싼 값"은 변수 하나로 들고 다닐 수 있다. 손으로 푼 표의 세 번째 열이 바로 이 변수다.

1. `minPrice`를 무한대, `best`를 0으로 둔다.
2. 오늘 가격 `p`가 `minPrice`보다 싸면 `minPrice = p`. 오늘이 새 최저가이니 오늘 팔아서 벌 돈은 없다.
3. 아니면 오늘 팔았을 때의 이익 `p - minPrice`를 `best`와 비교한다.
4. 끝까지 가면 `best`가 답이다.

```js
function maxProfit(prices) {
  let minPrice = Infinity; // 지금까지 본 가장 싼 값
  let best = 0;            // 지금까지 찾은 가장 큰 이익
  for (const p of prices) {
    if (p < minPrice) {
      minPrice = p;                 // 더 싼 날을 찾았다. 앞으로는 여기서 산다
    } else if (p - minPrice > best) {
      best = p - minPrice;          // 오늘 팔면 지금까지보다 더 번다
    }
  }
  return best;
}
```

시간 O(n), 공간 O(1)이다. 모든 원소를 딱 한 번 보고, 기억하는 건 숫자 두 개뿐이다. 10만 개에서 1ms도 걸리지 않았다.

왜 이게 맞는지 한 줄로 말하면 이렇다. 최적의 거래가 `j`번 날에 판다면, 그 거래는 `j` 앞에서 가장 싼 날에 산 것이다. 그런데 반복문이 `j`에 도착했을 때 `minPrice`는 정확히 그 값이다. 모든 `j`에서 그 이익을 한 번씩 계산하니 최적의 `j`도 빠짐없이 본다.

새 최저가를 만났을 때 `best`는 지우지 않는다. 3번 날에 최저가가 2로 바뀌어도, 앞에서 찾은 이익 3은 이미 실제로 가능한 거래였다. 그 기록은 그대로 두고, 앞으로의 거래는 새 최저가를 기준으로 계산한다.

## 창으로 보면 왼쪽 끝은 산 날이다

슬라이딩 윈도(sliding window)는 배열 위에 왼쪽 끝 `l`과 오른쪽 끝 `r`로 이루어진 창을 놓고, `r`을 한 칸씩 늘리면서 조건에 따라 `l`을 당기는 기법이다. 기본 틀과 언제 쓰는지는 [슬라이딩 윈도 패턴 글](/posts/sliding-window-pattern)에서 다뤘다.

이 문제에서 `l`은 사는 날, `r`은 파는 날이다. `prices[r]`이 `prices[l]`보다 작아지면 지금 창은 의미가 없다. `l`보다 더 싸게 살 수 있는 날을 찾았으니 `l`을 `r`로 옮겨 창을 새로 시작한다.

```js
function maxProfitWindow(prices) {
  let l = 0;    // 사는 날 (창의 왼쪽 끝)
  let best = 0;
  for (let r = 1; r < prices.length; r++) { // 파는 날 (창의 오른쪽 끝)
    if (prices[r] < prices[l]) {
      l = r; // 더 싼 날이 나왔다. 창을 여기서 다시 연다
    } else {
      best = Math.max(best, prices[r] - prices[l]);
    }
  }
  return best;
}
```

앞의 한 번 훑기와 비교해 보면 `minPrice`가 `prices[l]`로 바뀌었을 뿐이다. 창의 왼쪽 끝이 늘 "지금까지의 최저가인 날"을 가리킨다. 그래서 두 코드는 같은 일을 한다. 차이는 값 대신 인덱스를 들고 있다는 것 하나인데, 이게 쓸모가 있다. "며칠에 사서 며칠에 팔았나"까지 답해야 할 때 `l`과 `r`을 그대로 기록하면 된다.

이 문제의 창은 다른 슬라이딩 윈도 문제와 성격이 조금 다르다. 보통은 `l`이 한 칸씩 오른쪽으로 기어가며 창을 줄이는데, 여기서는 `l`이 `r`까지 한 번에 점프한다. 창 안의 원소를 하나씩 빼며 상태를 고칠 필요가 없기 때문이다. 창 안에서 필요한 정보가 "왼쪽 끝 값" 하나뿐이라서 가능한 일이다. 다음 문제인 [중복 없는 가장 긴 부분 문자열](/posts/leetcode-longest-substring-without-repeating)부터는 창 안의 내용을 해시맵으로 관리해야 해서 `l`을 조심스럽게 옮긴다.

시간 O(n), 공간 O(1). 두 포인터가 모두 오른쪽으로만 가니 [투 포인터](/posts/two-pointers-pattern)의 같은 방향 형태로 볼 수도 있다.

## 하루치 변화량을 이어 붙인다

관점을 하나 더 바꿔 본다. 3번 날에 사서 4번 날에 판 이익은 `prices[4] - prices[3]`이다. 1번 날에 사서 4번 날에 판 이익은 `prices[4] - prices[1]`인데, 이건 하루씩의 변화량을 더한 것과 같다.

```text
가격      8   3   6   2   7   5
변화량        -5  +3  -4  +5  -2
1일 사서 4일 판다 = (+3) + (-4) + (+5) = 4 = 7 - 3
```

그러면 문제가 "변화량 배열에서 연속한 구간의 합 중 가장 큰 것"으로 바뀐다. 이건 최대 부분 배열 합(LeetCode 53. Maximum Subarray) 문제이고, 카데인(Kadane) 알고리즘이라는 유명한 O(n) 풀이가 있다.

카데인의 생각은 이렇다. "오늘에서 끝나는 구간 중 가장 큰 합" `cur`를 들고 간다. 어제까지의 `cur`에 오늘 변화량을 더했는데 음수가 되면, 그 구간을 이어 가 봤자 손해이니 버리고 0부터 다시 시작한다.

```js
function maxProfitKadane(prices) {
  let cur = 0;  // 오늘 팔면 벌 수 있는 최대 이익 (오늘에서 끝나는 구간 합)
  let best = 0;
  for (let i = 1; i < prices.length; i++) {
    const diff = prices[i] - prices[i - 1];
    cur = Math.max(0, cur + diff); // 음수가 되면 버리고 오늘 다시 산다
    best = Math.max(best, cur);
  }
  return best;
}
```

아래 그림은 변화량 배열 위에서 `cur`가 쌓였다가 0으로 잘리는 모습이다. 칸은 1번 날부터의 하루 변화량이다.

시간 O(n), 공간 O(1). 이 관점의 장점은 "주식"이라는 겉모양을 벗기면 유명한 문제로 바뀐다는 걸 보여 준다는 데 있다. 면접관이 "최대 부분 배열 합과 어떤 관계인가"를 물으면 이 변환으로 답한다.

## 들고 있는가, 비어 있는가

마지막은 상태 기계 DP다. 이 문제 하나만 보면 과하지만, 거래 조건이 바뀌는 변형 문제를 모두 같은 틀로 풀게 해 준다.

하루가 끝났을 때 내 상태는 둘 중 하나다.

- `hold`: 주식을 한 주 들고 있다. 값은 "그 상태에서 내 지갑의 최대 금액"이다. 산 돈만큼 마이너스다.
- `free`: 주식이 없다. 이미 팔았거나 아직 안 샀다.

오늘 가격이 `p`일 때 상태가 바뀌는 길은 이렇다.

- 오늘 `hold`인 경우: 어제도 `hold`였거나, 오늘 처음 샀다(`-p`). 한 번만 거래할 수 있으니 사기 전에는 번 돈이 0이다.
- 오늘 `free`인 경우: 어제도 `free`였거나, 어제 `hold`에서 오늘 팔았다(`hold + p`).

```js
function maxProfitDP(prices) {
  let hold = -Infinity; // 주식을 들고 있을 때의 최대 금액. 처음엔 불가능한 상태
  let free = 0;         // 주식이 없을 때의 최대 금액
  for (const p of prices) {
    hold = Math.max(hold, -p);       // 계속 들고 있거나, 오늘 산다
    free = Math.max(free, hold + p); // 계속 비어 있거나, 오늘 판다
  }
  return free;
}
```

`hold`를 먼저 갱신하고 그 값으로 `free`를 갱신하니 같은 날 사고파는 경우가 생기는데, 이익이 0이라 답에 영향이 없다. `hold = max(hold, -p)`를 보면 `-hold`가 곧 "지금까지의 최저가"다. 여기서도 결국 같은 정보를 들고 다닌다.

시간 O(n), 공간 O(1). 이 틀의 힘은 뒤의 "형제 문제들"에서 보인다. 조건이 하나 바뀌면 점화식 한 줄만 바뀐다.

## 코딩 테스트용 세 언어 코드

가장 많이 쓰는 한 번 훑기 풀이를 Python과 Java로도 옮겼다.

```python
from typing import List

class Solution:
    def maxProfit(self, prices: List[int]) -> int:
        min_price = float("inf")  # 지금까지 본 가장 싼 값
        best = 0
        for p in prices:
            if p < min_price:
                min_price = p
            elif p - min_price > best:
                best = p - min_price
        return best
```

```java
class Solution {
    public int maxProfit(int[] prices) {
        int minPrice = Integer.MAX_VALUE; // 지금까지 본 가장 싼 값
        int best = 0;
        for (int p : prices) {
            if (p < minPrice) {
                minPrice = p;
            } else if (p - minPrice > best) {
                best = p - minPrice;
            }
        }
        return best;
    }
}
```

예시 네 개(`[8,3,6,2,7,5]`, `[9,7,4,1]`, `[5]`, `[1,10,0,8]`)를 넣어 세 언어 모두 5, 0, 0, 9가 나오는 걸 확인했다.

언어마다 짚을 점이 있다.

- Python의 `float("inf")`는 정수와 비교해도 문제없다. 다만 반환값이 실수가 되지 않도록 `best`는 정수 0에서 시작한다. `min_price = prices[0]`으로 시작해도 된다(길이가 1 이상이라는 제약이 있을 때).
- Java에서 `minPrice`를 `Integer.MAX_VALUE`로 두는 건 안전하다. 첫 날에 반드시 `p < minPrice`라서 `p - Integer.MAX_VALUE` 같은 뺄셈이 실행되지 않는다. 만약 비교 순서를 바꿔 `best = Math.max(best, p - minPrice)`를 먼저 계산하면 첫 날에 큰 음수가 나오는데, 가격이 0 이상이라 오버플로까지는 가지 않는다. 가격에 음수가 섞인 변형이라면 `p - Integer.MAX_VALUE`가 넘칠 수 있으니 `prices[0]`으로 시작하는 쪽이 낫다.
- 상태 DP를 Java로 옮길 때 `hold = Integer.MIN_VALUE`로 두고 `hold + p`를 계산하면 가격이 양수라 괜찮지만, 습관적으로 `-hold` 같은 식을 쓰면 `-Integer.MIN_VALUE`가 다시 음수가 된다. `hold = -prices[0]`으로 시작하면 이 걱정이 사라진다.
- 분할 정복을 Python으로 옮기면 재귀 깊이가 log₂(10만) ≈ 17이라 기본 재귀 한도(1000)에 걸리지 않는다.

## 풀이 한눈에 비교

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 모든 짝 | O(n²) | O(1) | 정답 확인용, n이 수천 이하 |
| 분할 정복 | O(n) | O(log n) | 분할 정복 연습, 병렬로 나눠 계산할 때 |
| 접미사 최댓값 배열 | O(n) | O(n) | "i에 사면 얼마"를 여러 번 물을 때 |
| 지금까지의 최저가 | O(n) | O(1) | 면접 기본 답. 스트림에도 그대로 쓴다 |

## 자주 틀리는 코드

전체 최댓값에서 전체 최솟값을 뺀다. 순서 조건을 잊은 코드다.

```js
const wrong = (prices) => Math.max(...prices) - Math.min(...prices);
wrong([7, 9, 1, 3]); // 8. 실제 답은 2 (7→9 또는 1→3)
```

이익이 음수로 나온다. `best`를 `-Infinity`나 `prices[1] - prices[0]`으로 시작하면, 계속 내리는 배열에서 0 대신 음수를 돌려준다. "거래를 안 한다"는 선택지가 있으니 하한은 0이다.

```js
function wrongNeg(prices) {
  let best = -Infinity, m = prices[0];
  for (let i = 1; i < prices.length; i++) {
    best = Math.max(best, prices[i] - m);
    m = Math.min(m, prices[i]);
  }
  return best;
}
wrongNeg([9, 7, 4, 1]); // -2
wrongNeg([5]);          // -Infinity
```

새 최저가를 만났을 때 `best`를 0으로 되돌린다. 앞에서 찾은 거래가 사라진다. `[1, 10, 0, 8]`에서 9가 아니라 8이 나온다.

최저가 갱신과 이익 계산의 순서를 바꿔서 "오늘 사고 오늘 판다"만 남는 경우도 있다. `minPrice = Math.min(minPrice, p)`를 먼저 하고 `best = Math.max(best, p - minPrice)`를 해도 사실 답은 맞는다. 오늘이 새 최저가면 이익이 0으로 계산될 뿐이다. 순서를 바꿔도 되는 이유를 설명할 수 있으면 충분하다.

빈 배열은 LeetCode 제약상 나오지 않지만, 실무 함수라면 `prices[0]`으로 시작하는 코드가 `undefined`를 다룬다. `Infinity`로 시작하는 위 코드는 빈 배열에서 0을 돌려준다.

## 형제 문제들: 거래 조건이 바뀌면

이 문제에는 같은 이름으로 시작하는 형제가 여럿 있다. 면접에서 꼬리 질문으로 그대로 나온다. 상태 DP 틀로 하나씩 바꿔 본다.

### 몇 번이든 사고팔 수 있다면 (LeetCode 122)

들고 있는 동안 주가가 오르는 날은 전부 이익으로 챙기면 된다. 오르는 하루하루의 변화량을 모두 더한다. 1일→2일(+3), 3일→4일(+5)을 더해 예시의 답은 8이다.

```js
function maxProfitII(prices) {
  let sum = 0;
  for (let i = 1; i < prices.length; i++) {
    if (prices[i] > prices[i - 1]) sum += prices[i] - prices[i - 1]; // 오른 날만 챙긴다
  }
  return sum;
}
```

상태 DP로 보면 `hold = max(hold, free - p)`로 한 글자만 바뀐다. 사기 전에 이미 번 돈(`free`)을 들고 다시 살 수 있기 때문이다.

### 최대 k번까지라면 (LeetCode 123, 188)

거래 횟수마다 `hold`와 `free`를 따로 둔다. `buy[j]`는 j번째 매수까지 마친 상태, `sell[j]`는 j번째 매도까지 마친 상태의 최대 금액이다.

```js
function maxProfitK(k, prices) {
  const buy = new Array(k + 1).fill(-Infinity);
  const sell = new Array(k + 1).fill(0);
  for (const p of prices) {
    for (let j = 1; j <= k; j++) {
      buy[j] = Math.max(buy[j], sell[j - 1] - p); // j-1번 팔고 번 돈으로 j번째를 산다
      sell[j] = Math.max(sell[j], buy[j] + p);    // j번째를 판다
    }
  }
  return sell[k];
}
```

예시에서 k = 1이면 5, k = 2면 8이다. 모든 경우를 재귀로 다 해 보는 코드와 길이 8 이하 무작위 배열 3000개로 비교해 일치하는 걸 확인했다. 시간은 O(nk)다. k가 n/2 이상이면 사실상 무제한이라 122번 풀이로 바꾸는 최적화가 188번의 단골 함정이다.

### 수수료나 쿨다운이 붙으면 (LeetCode 714, 309)

수수료가 있으면 팔 때 `free = max(free, hold + p - fee)`로 수수료를 뺀다. 판 다음 날 하루 쉬어야 하는 쿨다운이 있으면 "어제 판 상태"를 하나 더 두거나, 살 때 `free`의 이틀 전 값을 쓴다. 상태를 그림으로 그려 화살표를 하나씩 코드로 옮기면 실수가 적다.

### 사고판 날짜도 알려 달라면

창 풀이에서 `l`과 `r`을 기록한다. 이익이 0이면 거래하지 않는다는 뜻으로 `-1`을 돌려주는 식으로 약속을 정한다.

```js
function maxProfitWithDays(prices) {
  let minIdx = 0, best = 0, buy = -1, sell = -1;
  for (let i = 1; i < prices.length; i++) {
    if (prices[i] < prices[minIdx]) minIdx = i;
    else if (prices[i] - prices[minIdx] > best) {
      best = prices[i] - prices[minIdx];
      buy = minIdx;
      sell = i;
    }
  }
  return { best, buy, sell };
}
maxProfitWithDays([8, 3, 6, 2, 7, 5]); // { best: 5, buy: 3, sell: 4 }
```

### 가격이 실시간으로 들어온다면

한 번 훑기는 원래 스트림 알고리즘이다. 새 가격이 들어올 때마다 `minPrice`와 `best`를 갱신하면 언제든 "지금까지의 최대 이익"을 O(1)에 답한다. 접미사 배열 풀이와 분할 정복은 끝을 알아야 해서 스트림에 쓸 수 없다. "최근 30일 안에서만" 사고팔 수 있다면 창의 길이가 고정되고, 창 안의 최솟값을 빠르게 구해야 한다. 그때는 [Sliding Window Maximum](/posts/leetcode-sliding-window-maximum)의 단조 덱을 최솟값용으로 뒤집어 쓴다.

비슷한 문제로 LeetCode 53(Maximum Subarray), 2016(Maximum Difference Between Increasing Elements)이 있다. 2016번은 이익이 0일 때 -1을 돌려주는 것만 다르다.

## 정리하며

이 문제는 "파는 날마다 그 앞의 최저가를 안다"로 끝난다. 그 최저가를 매번 찾으면 O(n²), 미리 배열로 만들면 공간 O(n), 변수 하나로 들고 다니면 O(n)·O(1)이다. 창으로 보면 왼쪽 끝이 최저가인 날이고, 변화량으로 보면 최대 부분 배열 합이며, 상태로 보면 hold와 free 두 칸짜리 DP다. 마지막 관점이 형제 문제를 모두 푸는 열쇠다. 다음 문제인 [Longest Substring Without Repeating Characters](/posts/leetcode-longest-substring-without-repeating)에서는 창의 왼쪽 끝을 한 칸씩, 조건이 다시 맞을 때까지 당기는 진짜 가변 창을 만난다.

## 면접에서 나올 만한 질문

### 이 문제를 O(n)에 푸는 방법과 그게 맞는 이유는 무엇인가요?

왼쪽부터 한 번 훑으며 지금까지의 최저가와 최대 이익을 들고 간다. 오늘이 최저가보다 싸면 최저가를 바꾸고, 아니면 오늘 팔았을 때의 이익으로 최대 이익을 갱신한다. 최적의 거래가 j번 날에 판다면 산 날은 j 앞의 최저가인 날이고, 반복문이 j에 왔을 때 들고 있는 값이 정확히 그 최저가다. 그래서 최적 거래를 반드시 한 번 계산한다.

### 전체 최댓값에서 전체 최솟값을 빼면 안 되는 이유는 무엇인가요?

사는 날이 파는 날보다 앞이어야 해서다. 최댓값이 최솟값보다 앞에 있으면 그 거래는 불가능하다. `[7, 9, 1, 3]`에서 9 − 1 = 8이지만 9인 날이 이미 지나서 실제 답은 2다.

### 이 문제는 슬라이딩 윈도인가요, 그리디인가요, DP인가요?

셋 다로 설명할 수 있다. 창으로 보면 왼쪽 끝이 사는 날이고, 더 싼 날이 나오면 왼쪽 끝을 거기로 옮긴다. 매 순간 최저가만 고르는 건 그리디이고, "i번 날까지의 최저가"를 이전 칸에서 구하는 건 한 칸짜리 DP를 변수 하나로 줄인 것이다. 들고 다니는 정보는 모두 앞쪽의 최저가로 같다.

### 최대 부분 배열 합(카데인)과 어떤 관계가 있나요?

하루 변화량 배열을 만들면 i에 사서 j에 판 이익은 i+1부터 j까지 변화량의 합이다. 그래서 최대 이익은 변화량 배열의 최대 연속 구간 합과 같고, 카데인 알고리즘으로 O(n)에 구한다. 카데인의 현재 합이 0으로 잘리는 순간이 최저가가 바뀌는 순간과 겹친다.

### 여러 번 거래할 수 있으면 어떻게 바뀌나요?

무제한이면 오른 날의 변화량만 모두 더하면 된다. 들고 있는 동안 오른 구간은 전부 이익으로 챙길 수 있기 때문이다. 최대 k번이면 거래 횟수마다 hold와 free 상태를 두는 DP로 O(nk)에 푼다. k가 n/2 이상이면 무제한과 같아지니 그 경우는 무제한 풀이로 바꾼다.

### 가격이 스트림으로 들어오면 어떻게 하나요?

한 번 훑기 풀이가 그대로 스트림 알고리즘이다. 새 가격마다 최저가와 최대 이익만 갱신하면 언제든 O(1)에 답할 수 있고 메모리도 O(1)이다. 최근 k일 안에서만 거래할 수 있다면 창 안의 최솟값이 필요해서 단조 덱을 쓴다.

### Java로 짤 때 오버플로를 걱정해야 하나요?

이 문제의 제약(가격 0~1만)에서는 걱정하지 않아도 된다. `minPrice = Integer.MAX_VALUE`로 시작해도 첫 날에 바로 최저가가 바뀌어 큰 수끼리의 뺄셈이 일어나지 않는다. 다만 가격에 음수가 섞이거나 상태 DP에서 `Integer.MIN_VALUE`를 부호 반전하면 넘칠 수 있어서, `prices[0]`이나 `-prices[0]`으로 시작하는 습관이 안전하다.
