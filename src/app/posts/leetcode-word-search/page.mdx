보드게임 앱에 "이 판에 이 단어가 있나" 검사를 넣으려고 했다. 처음엔 각 칸에서 시작해 이웃을 따라가며 글자를 이어 붙이고 끝에서 비교하는 함수를 짰다. 3 × 4 판에서는 금방 끝났는데, 6 × 6 판에 같은 글자가 많이 깔린 테스트에서 함수가 돌아오지 않았다.

[LeetCode 79. Word Search](https://leetcode.com/problems/word-search/)가 그 검사를 짜는 문제다. 격자 위의 백트래킹이라 [Number of Islands](/posts/leetcode-number-of-islands) 같은 격자 탐색과 비슷해 보이지만, 칸을 "이 경로에서만" 썼다고 표시하고 물러날 때 지운다는 점이 다르다. 이 글은 끝까지 이어 붙이고 비교하는 풀이에서 시작해, 방문 배열 백트래킹, 판에 직접 표시하기, 글자 수와 뒤집기 가지치기, 재귀 없는 스택 풀이까지 다섯 가지를 비교한다. 백트래킹의 일반적인 틀은 [재귀와 백트래킹 글](/posts/recursion-backtracking)에, 격자를 그래프로 보는 방법은 [그래프 BFS·DFS 글](/posts/ds-graph-bfs-dfs)에 있다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 이웃 칸을 따라 단어를 이어 갈 수 있나

m × n 글자 격자 `board`와 문자열 `word`가 주어진다. 격자에서 상하좌우로 이웃한 칸을 차례로 밟아 `word`를 만들 수 있으면 `true`, 없으면 `false`를 돌려준다. 같은 칸은 한 단어 안에서 두 번 쓸 수 없다. 대각선은 이웃이 아니다.

풀이를 정하는 제약은 이렇다.

- m, n은 1 이상 6 이하다. 칸이 많아야 36개다.
- 단어 길이는 1 이상 15 이하다.
- 글자는 영문 대소문자뿐이고 대소문자를 구분한다.

판이 작아서 "모든 경로를 다 본다"가 가능해 보이지만, 경로의 수는 칸 수보다 단어 길이에 지수적으로 늘어난다. 6 × 6 판이 전부 같은 글자면 길이 15짜리 경로가 수백만 개다. 그래서 이 문제는 헛걸음을 얼마나 일찍 끊느냐의 싸움이다. LeetCode도 문제 끝에 "더 큰 판에서도 빨리 끝나게 가지치기를 해 보라"는 후속 질문을 붙여 뒀다.

## 손으로 DOGS를 찾아 보면

이 글 내내 쓸 판이다.

```text
     0   1   2   3
0    C   A   T   S
1    O   R   E   A
2    D   O   G   S
```

`DOGS`를 찾아보자. 첫 글자 D는 (2,0) 하나뿐이다. D의 이웃은 위쪽 O(1,0)과 오른쪽 O(2,1)이다. 위쪽 O부터 가 보면, 그 이웃은 C(0,0), R(1,1), 이미 밟은 D다. 다음 글자 G가 없으니 막혔다. 한 칸 물러나 D로 돌아오고, 이번엔 오른쪽 O(2,1)로 간다. 그 이웃 중 G(2,2)가 있다. G의 이웃 중 S(2,3)가 있다. 네 글자를 다 이었으니 찾았다.

## 끝까지 이어 붙이고 마지막에 비교하기

각 칸에서 시작해 이웃을 따라가며 글자를 이어 붙이고, 길이가 단어와 같아지면 비교한다. 같은 칸을 두 번 밟지 않으려고 방문 표시는 한다.

```js
function exist(board, word) {
  const m = board.length, n = board[0].length, L = word.length;
  const DIRS = [[-1, 0], [1, 0], [0, -1], [0, 1]];
  const seen = Array.from({ length: m }, () => new Array(n).fill(false));

  function dfs(r, c, s) {
    s += board[r][c];                      // 글자가 맞든 틀리든 이어 붙인다
    if (s.length === L) return s === word; // 길이가 차면 그제야 비교
    seen[r][c] = true;
    for (const [dr, dc] of DIRS) {
      const nr = r + dr, nc = c + dc;
      if (nr >= 0 && nc >= 0 && nr < m && nc < n && !seen[nr][nc] && dfs(nr, nc, s)) {
        seen[r][c] = false;
        return true;
      }
    }
    seen[r][c] = false;
    return false;
  }

  for (let r = 0; r < m; r++)
    for (let c = 0; c < n; c++)
      if (dfs(r, c, "")) return true;
  return false;
}
```

답은 맞다. `DOGS`를 찾는 데 호출이 190번이다. C(0,0)에서 시작한 경로도 길이 4까지 다 만든 뒤에야 "DOGS가 아니다"를 안다. 없는 단어 `CATSAGE`는 1240번이었다. 첫 글자가 이미 다른 경로를 끝까지 키운다. 다음 풀이는 이 낭비를 첫 글자에서 끊는다.

## 글자가 다르면 들어가지 않는다

k번째 글자를 맞추는 중이라면, 지금 칸의 글자가 `word[k]`와 다른 순간 이 경로는 끝났다. 그 자리에서 `false`를 돌려준다. 이렇게 하면 경로를 문자열로 들고 다닐 필요도 없고, 지금 몇 번째 글자인지 `k`만 알면 된다. 방문 표시는 같은 크기의 불리언 격자 `visited`에 한다.

```js
function exist(board, word) {
  const m = board.length, n = board[0].length;
  const visited = Array.from({ length: m }, () => new Array(n).fill(false));
  const DIRS = [[-1, 0], [1, 0], [0, -1], [0, 1]];

  function dfs(r, c, k) {                // (r, c)가 word[k]가 될 수 있나
    if (r < 0 || c < 0 || r >= m || c >= n) return false; // 판 밖
    if (visited[r][c] || board[r][c] !== word[k]) return false; // 밟았거나 글자가 다르다
    if (k === word.length - 1) return true;               // 마지막 글자까지 맞췄다
    visited[r][c] = true;                // 이 경로에서 썼다
    for (const [dr, dc] of DIRS) {
      if (dfs(r + dr, c + dc, k + 1)) {
        visited[r][c] = false;
        return true;
      }
    }
    visited[r][c] = false;               // 물러나며 지운다
    return false;
  }

  for (let r = 0; r < m; r++)
    for (let c = 0; c < n; c++)
      if (dfs(r, c, 0)) return true;
  return false;
}
```

`DOGS`가 25번, `CATSAGE`가 32번으로 줄었다. 25번 중 9번은 D를 만날 때까지 시작 칸을 하나씩 확인하는 호출이다. 판 밖이나 글자가 다른 칸은 들어가자마자 돌아오니, 실제로 경로를 이어 간 건 손풀이에서 본 다섯 걸음뿐이다.

아래 그림은 단어의 글자를 칸으로 놓고, 지금 맞추는 글자 `k`와 경로가 쌓인 모습을 보여 준다.

시간 복잡도는 O(m · n · 3^L)이다(L은 단어 길이). 시작 칸이 m · n개이고, 첫 걸음은 이웃 4개, 그 뒤로는 방금 온 칸을 빼고 3개씩 갈래가 생겨서 경로 수가 많아야 4 · 3^(L-1)이다. 공간은 `visited` 격자 O(m · n)에 재귀 깊이 O(L)이다.

이 풀이로 LeetCode는 통과한다. 하지만 `visited` 격자를 따로 만드는 게 아깝고, 최악의 입력에서는 여전히 느리다. 둘을 하나씩 고친다.

## 판에 직접 표시해 두기

`visited`를 따로 두지 않고, 밟은 칸의 글자를 잠깐 `#`처럼 단어에 나올 수 없는 글자로 바꿔 둔다. 그러면 "밟았나"와 "글자가 맞나"가 비교 한 번으로 합쳐진다. `#`은 어떤 `word[k]`와도 같지 않으니 저절로 막힌다. 물러날 때 원래 글자로 되돌린다.

```js
function exist(board, word) {
  const m = board.length, n = board[0].length;

  function dfs(r, c, k) {
    if (r < 0 || c < 0 || r >= m || c >= n || board[r][c] !== word[k]) return false;
    if (k === word.length - 1) return true;
    const saved = board[r][c];
    board[r][c] = "#";              // 이 경로에서 썼다고 표시
    const found =
      dfs(r - 1, c, k + 1) ||       // 위
      dfs(r + 1, c, k + 1) ||       // 아래
      dfs(r, c - 1, k + 1) ||       // 왼쪽
      dfs(r, c + 1, k + 1);         // 오른쪽
    board[r][c] = saved;            // 찾았든 못 찾았든 되돌린다
    return found;
  }

  for (let r = 0; r < m; r++)
    for (let c = 0; c < n; c++)
      if (dfs(r, c, 0)) return true;
  return false;
}
```

`||`는 앞에서 `true`가 나오면 뒤를 부르지 않는다. 그래서 단어를 찾는 즉시 탐색이 멈추고, 그 다음 줄에서 표시를 되돌린 뒤 `true`가 위로 올라간다. 호출 수는 방문 배열 풀이와 같고, 추가 공간이 재귀 깊이 O(L)로 줄었다. 6 × 6 판이 전부 `A`이고 단어가 `AAAAAAAAAAAAAAB`(A 14개 뒤에 B)인 최악의 입력에서 호출이 9,030,868번, 방문 배열 풀이 187ms, 이 풀이 150ms였다. 격자 하나를 덜 읽는 만큼 빨라졌다.

입력 판을 바꾸는 게 꺼림칙할 수 있다. 이 풀이는 끝날 때 판을 원래대로 돌려놓으니 호출한 쪽에서 보면 바뀐 게 없다. 다만 탐색 도중에 다른 스레드가 판을 읽는다면 `#`을 보게 된다. 공유되는 판이라면 복사본에 표시하거나 방문 배열 풀이를 쓴다.

## 없는 글자가 있으면 탐색하지 않는다

최악의 입력을 다시 보자. 판에 B가 하나도 없는데 A 14개짜리 경로를 900만 번 만들고 나서야 "B가 없다"를 안다. 탐색 전에 글자 개수만 세 봐도 알 수 있는 사실이다. 단어에 필요한 글자가 판에 모자라면 바로 `false`다.

같은 입력에서 판의 한 칸만 B로 바꾸면 개수 검사는 통과한다. 이번엔 다른 낭비가 보인다. A로 시작하는 칸이 35개라 거기서 다 출발한다. 단어를 뒤집어 `BAAA…A`로 찾으면 시작 칸이 B 하나뿐이다. 단어가 판에 있는지는 앞에서 찾든 뒤에서 찾든 같으니, 첫 글자와 끝 글자 중 판에 더 드문 쪽에서 시작한다.

```js
function exist(board, word) {
  const m = board.length, n = board[0].length;
  if (word.length > m * n) return false;          // 칸보다 긴 단어

  const have = new Map();
  for (const row of board) for (const ch of row) have.set(ch, (have.get(ch) || 0) + 1);
  const need = new Map();
  for (const ch of word) need.set(ch, (need.get(ch) || 0) + 1);
  for (const [ch, cnt] of need) {
    if ((have.get(ch) || 0) < cnt) return false;  // 글자가 모자라다
  }

  const first = have.get(word[0]) || 0;
  const last = have.get(word[word.length - 1]) || 0;
  if (first > last) word = [...word].reverse().join(""); // 드문 글자부터 찾는다

  function dfs(r, c, k) {
    if (r < 0 || c < 0 || r >= m || c >= n || board[r][c] !== word[k]) return false;
    if (k === word.length - 1) return true;
    const saved = board[r][c];
    board[r][c] = "#";
    const found = dfs(r - 1, c, k + 1) || dfs(r + 1, c, k + 1) ||
                  dfs(r, c - 1, k + 1) || dfs(r, c + 1, k + 1);
    board[r][c] = saved;
    return found;
  }

  for (let r = 0; r < m; r++)
    for (let c = 0; c < n; c++)
      if (dfs(r, c, 0)) return true;
  return false;
}
```

효과를 재 봤다. 두 번째 판은 전부 A인 6 × 6에서 (0,0)을 C, (5,5)를 B로 바꾼 것이고, 단어는 A 13개 뒤에 `CB`다. C와 B가 이웃하지 않아 답은 `false`인데, 개수 검사는 통과한다.

```text
                                  판에 직접 표시      + 개수 검사와 뒤집기
전부 A, 단어 A×14 + B             9,030,868번 150ms      0번 0ms
C, B 한 칸씩, 단어 A×13 + CB      3,886,228번  47ms     40번 0ms
```

첫 번째는 개수 검사에서 바로 끝났다. 두 번째는 뒤집은 `BCAAA…`로 찾으니 시작 칸 36개를 확인하는 호출과 B 주변 네 칸만 보고 끝났다. 개수를 세는 비용은 O(m · n + L)로, 탐색 한 번보다 훨씬 싸다.

이 가지치기는 최악을 바꾸지 않는다. 판과 단어를 잘 고르면 개수 검사도 통과하고 양 끝 글자도 흔하게 만들 수 있다. 그래도 실제 테스트에서 시간을 잡아먹는 건 대부분 "같은 글자가 잔뜩 깔린 판"이라 효과가 크다. 면접에서 후속 질문에 이 두 가지를 답하면 된다.

### Python과 Java로 쓰면

Python에서는 이 차이가 더 크다. 같은 최악의 입력에서 가지치기 없는 풀이가 1672ms, 가지치기를 넣은 풀이가 0ms였다. LeetCode의 Python 제출이 이 문제에서 시간 초과가 잦은 이유다. 재귀 깊이는 단어 길이 15를 넘지 않아 한도 걱정은 없다.

```python
from collections import Counter
from typing import List

def exist(board: List[List[str]], word: str) -> bool:
    m, n = len(board), len(board[0])
    if len(word) > m * n:
        return False
    have = Counter(ch for row in board for ch in row)
    need = Counter(word)
    if any(have[ch] < cnt for ch, cnt in need.items()):
        return False                          # 글자가 모자라면 탐색할 필요가 없다
    if have[word[0]] > have[word[-1]]:
        word = word[::-1]                     # 드문 글자부터 찾는다

    def dfs(r: int, c: int, k: int) -> bool:
        if r < 0 or c < 0 or r >= m or c >= n or board[r][c] != word[k]:
            return False
        if k == len(word) - 1:
            return True
        saved = board[r][c]
        board[r][c] = "#"                     # 이 경로에서 썼다고 표시
        found = (dfs(r - 1, c, k + 1) or dfs(r + 1, c, k + 1) or
                 dfs(r, c - 1, k + 1) or dfs(r, c + 1, k + 1))
        board[r][c] = saved                   # 되돌린다
        return found

    return any(dfs(r, c, 0) for r in range(m) for c in range(n))
```

Python의 `or`와 `any`도 앞에서 참이 나오면 뒤를 계산하지 않는다. `any`에 넘긴 제너레이터가 첫 `True`에서 멈춰서 나머지 시작 칸을 보지 않는다.

Java는 글자가 영문뿐이라 `Map` 대신 크기 128 배열로 센다. 판과 단어를 필드에 두면 재귀 인자가 줄어든다.

```java
class Solution {
    private char[][] board;
    private char[] word;

    public boolean exist(char[][] board, String word) {
        int m = board.length, n = board[0].length;
        if (word.length() > m * n) return false;
        int[] have = new int[128], need = new int[128]; // 영문 대소문자만 나온다
        for (char[] row : board) for (char ch : row) have[ch]++;
        for (char ch : word.toCharArray()) if (++need[ch] > have[ch]) return false;
        if (have[word.charAt(0)] > have[word.charAt(word.length() - 1)]) {
            word = new StringBuilder(word).reverse().toString(); // 드문 글자부터
        }
        this.board = board;
        this.word = word.toCharArray();
        for (int r = 0; r < m; r++)
            for (int c = 0; c < n; c++)
                if (dfs(r, c, 0)) return true;
        return false;
    }

    private boolean dfs(int r, int c, int k) {
        if (r < 0 || c < 0 || r >= board.length || c >= board[0].length || board[r][c] != word[k]) return false;
        if (k == word.length - 1) return true;
        char saved = board[r][c];
        board[r][c] = '#';
        boolean found = dfs(r - 1, c, k + 1) || dfs(r + 1, c, k + 1)
                     || dfs(r, c - 1, k + 1) || dfs(r, c + 1, k + 1);
        board[r][c] = saved;
        return found;
    }
}
```

세 언어 모두 이 글의 판에서 `DOGS`, `CORE`, `TEAS`는 `true`, `SEA`, `ARA`는 `false`를 낸다. 글자를 `char` 비교 `!=`로 하니 Java에서 문자열 `equals`를 헷갈릴 일이 없다.

## 재귀 없이 스택으로 걷기

재귀를 쓸 수 없는 환경이라면 콜 스택을 직접 만든다. 까다로운 건 "물러날 때 표시를 지우는" 시점이다. 그래서 스택 칸마다 "다음에 볼 방향"을 함께 둔다. 맨 위 칸의 네 방향을 다 봤으면 그때 꺼내면서 표시를 지운다. 스택 깊이가 곧 지금까지 맞춘 글자 수다.

```js
function exist(board, word) {
  const m = board.length, n = board[0].length;
  const DIRS = [[-1, 0], [1, 0], [0, -1], [0, 1]];
  for (let sr = 0; sr < m; sr++) {
    for (let sc = 0; sc < n; sc++) {
      if (board[sr][sc] !== word[0]) continue;
      if (word.length === 1) return true;
      const stack = [[sr, sc, 0]];   // [행, 열, 다음에 볼 방향]. 스택 깊이 = 맞춘 글자 수
      const saved = [board[sr][sc]];
      board[sr][sc] = "#";
      while (stack.length) {
        const top = stack[stack.length - 1];
        const [r, c, d] = top;
        if (d === 4) {                 // 네 방향을 다 봤다. 물러난다
          stack.pop();
          board[r][c] = saved.pop();
          continue;
        }
        top[2]++;                      // 다음에 돌아오면 다음 방향을 본다
        const nr = r + DIRS[d][0], nc = c + DIRS[d][1], k = stack.length;
        if (nr < 0 || nc < 0 || nr >= m || nc >= n || board[nr][nc] !== word[k]) continue;
        if (k === word.length - 1) {   // 마지막 글자까지 맞췄다. 표시를 모두 되돌리고 끝낸다
          while (stack.length) { const [rr, cc] = stack.pop(); board[rr][cc] = saved.pop(); }
          return true;
        }
        saved.push(board[nr][nc]);
        board[nr][nc] = "#";
        stack.push([nr, nc, 0]);
      }
    }
  }
  return false;
}
```

이 판에서 길이 7 이하로 만들 수 있는 1040개 단어와 없는 단어 몇 개를 재귀 풀이와 비교했더니 결과가 모두 같았고, 끝난 뒤 판도 모두 원래대로였다. 최악의 입력(가지치기 없음)에서 315ms로 재귀 풀이의 두 배쯤이다. 칸마다 작은 배열을 만들기 때문이다. 코드가 길고 실수하기 쉬워서, 재귀 깊이가 15를 넘지 않는 이 문제에서는 재귀가 낫다. "재귀 없이 짤 수 있나요"라는 꼬리 질문의 답으로 구조를 설명할 수 있으면 충분하다.

## BFS로는 왜 안 되나

격자 탐색이라 [BFS](/posts/ds-graph-bfs-dfs)를 떠올리기 쉽다. 그런데 BFS는 칸마다 방문 표시를 하나만 둔다. 이 문제의 "밟았다"는 칸의 성질이 아니라 경로의 성질이다. 같은 칸이라도 어떤 경로에서는 밟았고 다른 경로에서는 안 밟았다. 상태를 (칸, 몇 번째 글자)로만 두면 같은 칸을 다시 쓰는 경로를 걸러 내지 못한다.

실제로 방문 표시를 빼면 이 판에서 `ARA`가 `true`로 나온다. A(0,1) → R(1,1) → 다시 A(0,1)로 돌아온 것이다. 경로마다 밟은 칸 집합을 들고 다니면 BFS로도 맞힐 수 있지만, 그 집합이 경로 수만큼 생겨서 메모리가 터진다. 경로 하나를 들고 깊이 들어갔다 나오는 DFS 백트래킹이 이 문제에 맞는 이유다.

## 다섯 풀이를 나란히 놓으면

| 풀이 | 시간 | 추가 공간 | 언제 고르나 |
|---|---|---|---|
| 끝까지 잇고 비교 | O(m · n · 3^L) 그대로 다 돈다 | O(m · n + L) | 출발점일 뿐 |
| 방문 배열 + 글자 확인 | O(m · n · 3^L) | O(m · n) | 판을 바꾸면 안 될 때 |
| 판에 직접 표시 | O(m · n · 3^L) | O(L) | 기본 답 |
| + 개수 검사와 뒤집기 | 최악은 같고 흔한 최악 입력에서 크게 줄어든다 | O(L + 글자 종류) | 후속 질문, Python 제출 |
| 명시적 스택 | O(m · n · 3^L) | O(L) | 재귀를 쓸 수 없을 때 |

면접에서는 판에 직접 표시하는 풀이를 짜고, 복잡도가 왜 3^L인지 설명한 뒤, "글자가 많이 겹치는 판에서는 개수 검사와 뒤집기로 줄인다"고 덧붙이는 흐름이 좋다.

## 표시를 지우지 않으면 있는 단어를 못 찾는다

가장 흔한 실수는 물러날 때 표시를 되돌리지 않는 것이다.

```js
function dfs(r, c, k) {
  if (r < 0 || c < 0 || r >= m || c >= n || board[r][c] !== word[k]) return false;
  if (k === word.length - 1) return true;
  board[r][c] = "#";            // 표시만 하고
  return dfs(r - 1, c, k + 1) || dfs(r + 1, c, k + 1) ||
         dfs(r, c - 1, k + 1) || dfs(r, c + 1, k + 1); // 되돌리지 않는다
}
```

이 판에서 길이 6 이하로 실제로 만들 수 있는 문자열을 모두 넣어 보니 56개를 못 찾았다. 예를 들어 `ASTA`는 A(1,3) → S(0,3) → T(0,2) → A(0,1)로 있다. 그런데 시작 칸을 (0,0)부터 훑다 보면 A(0,1)에서 먼저 출발해 실패하고, 그 칸에 `#`이 남는다. 나중에 올바른 경로가 마지막 글자로 A(0,1)에 오면 이미 `#`이라 막힌다. 한 경로에서 썼다는 표시는 그 경로가 끝나면 지워야 한다.

반대로 표시를 아예 안 하면 같은 칸을 다시 쓴다. 앞에서 본 대로 `ARA`가 `true`가 된다. 표시하고, 들어가고, 지운다. 세 동작이 한 묶음이다.

찾았을 때 바로 `return true`하면서 되돌리기를 건너뛰는 실수도 있다.

```js
board[r][c] = "#";
for (const [dr, dc] of DIRS) {
  if (dfs(r + dr, c + dc, k + 1)) return true; // 표시를 되돌리지 않고 나간다
}
board[r][c] = saved;
```

답은 맞다. 하지만 `DOGS`를 찾은 뒤 판을 열어 보니 맨 아랫줄이 `["#","#","#","S"]`로 망가져 있었다. 마지막 S는 표시하기 전에 `true`를 돌려줘서 남았다. 같은 판으로 다음 단어를 검사하면 틀린 답이 나온다. 앞에서 본 `||` 방식처럼 결과를 변수에 담고, 되돌린 다음 돌려준다.

판의 경계 검사를 글자 비교보다 뒤에 두면 `board[-1]`이 `undefined`라 `undefined[c]`에서 `TypeError`가 난다. Java와 Python은 각각 `ArrayIndexOutOfBoundsException`, 음수 인덱스로 반대편 칸을 읽는 조용한 버그가 된다. Python의 `board[-1]`은 마지막 행이라 오류 없이 엉뚱한 칸으로 이어진다. 경계 검사는 늘 먼저 한다.

## 면접관이 조건을 바꾸면

### 단어가 여러 개라면

[Word Search II](/posts/leetcode-word-search-ii)다. 단어마다 이 함수를 부르면 단어 수만큼 판을 다시 훑는다. 대신 단어들로 [트라이](/posts/ds-trie)를 만들어 두고, 판을 한 번 훑으며 트라이를 같이 따라 내려간다. 지금 경로가 어떤 단어의 접두사도 아니면 그 자리에서 끊는다. 찾은 단어는 트라이에서 지워 같은 단어를 또 찾지 않게 하는 것도 중요한 최적화다.

### 대각선 이웃도 허용한다면

방향 목록에 네 개를 더해 8방향으로 만든다. 갈래가 7개가 되어 복잡도가 O(m · n · 7^L)로 커진다. 보글(Boggle) 게임이 이 규칙이다.

### 같은 칸을 여러 번 써도 된다면

경로의 성질이던 "밟았다"가 없어지니 상태가 (칸, 몇 번째 글자)뿐이다. 이 상태는 m · n · L개라 메모이제이션으로 O(m · n · L)에 끝난다. 앞에서 BFS가 틀렸던 이유가 여기서는 문제가 되지 않는다. 제약 하나가 지수 시간과 다항 시간을 가른다는 걸 보여 주는 좋은 꼬리 질문이다.

### 판이 아주 크고 같은 판에 질문이 많이 온다면

판을 미리 색인해 둔다. 글자마다 위치 목록을 만들어 두면 시작 칸을 찾는 데 판 전체를 훑지 않아도 된다. 단어들이 미리 정해져 있다면 Word Search II처럼 트라이로 묶고, 질문이 실시간으로 온다면 글자 개수 검사를 먼저 해서 대부분의 없는 단어를 탐색 없이 거른다.

### 경로까지 돌려 달라면

`true`를 돌려주는 대신, 찾은 순간의 경로를 복사해 돌려준다. 재귀 풀이라면 들어갈 때 `path.push([r, c])`, 나올 때 `pop`을 넣고, 마지막 글자에서 `[...path]`를 결과로 올린다. `DOGS`라면 `[[2,0],[2,1],[2,2],[2,3]]`이다.

### 비슷한 문제

격자에서 칸을 표시해 가며 퍼지는 문제는 [Number of Islands](/posts/leetcode-number-of-islands), [Max Area of Island](/posts/leetcode-max-area-of-island), [Pacific Atlantic Water Flow](/posts/leetcode-pacific-atlantic-water-flow)가 있다. 이 문제들은 표시를 지우지 않는다. 한 번 센 섬은 다시 셀 필요가 없기 때문이다. 표시를 지우느냐 마느냐가 "경로를 찾는 백트래킹"과 "영역을 세는 탐색"을 가른다. 칸을 채웠다 지우는 백트래킹은 [N-Queens](/posts/leetcode-n-queens)와 [Sudoku Solver](/posts/leetcode-sudoku-solver)로 이어진다.

## 이 경로에서만 밟았다고 표시한다

글자가 다르면 들어가지 않고, 밟은 칸은 그 경로가 끝날 때까지만 표시한다. 표시를 지우지 않으면 있는 단어를 못 찾고, 표시를 안 하면 같은 칸을 두 번 쓴다. 복잡도는 시작 칸 m · n개에 갈래가 3개씩이라 O(m · n · 3^L)이고, 같은 글자가 많이 깔린 판에서는 글자 개수 검사와 단어 뒤집기가 탐색 대부분을 없앤다. 단어가 여러 개가 되면 트라이로 넘어간다.

## 면접에서 나올 만한 질문

### 시간 복잡도가 왜 O(m · n · 3^L)인가요?

시작 칸이 m · n개이고, 첫 걸음은 이웃 4개, 그 뒤로는 방금 온 칸을 빼고 많아야 3개씩 갈래가 생긴다. 그래서 시작 칸 하나에서 경로가 많아야 4 · 3^(L-1)개다. 실제로는 글자가 다르면 바로 끊기니 훨씬 적지만, 판이 전부 같은 글자면 이 상한에 가까워진다.

### 방문 표시를 왜 물러날 때 지우나요?

밟았다는 건 칸이 아니라 경로의 성질이기 때문이다. 실패한 경로가 남긴 표시를 그대로 두면, 나중에 다른 경로가 그 칸을 정당하게 쓰려 할 때 막힌다. 이 판에서 지우지 않으니 `ASTA`처럼 있는 단어 56개를 못 찾았다.

### `visited` 배열 없이 풀 수 있나요?

밟은 칸의 글자를 잠깐 `#`처럼 단어에 나올 수 없는 값으로 바꿔 두고, 물러날 때 원래 글자로 되돌린다. "밟았나"와 "글자가 맞나"를 비교 한 번으로 확인하고 추가 공간이 재귀 깊이 O(L)로 준다. 판을 다른 곳에서 동시에 읽는다면 복사본에 하는 게 안전하다.

### 왜 BFS가 아니라 DFS인가요?

BFS는 칸마다 방문 표시를 하나만 두는데, 이 문제는 같은 칸이 어떤 경로에서는 쓰였고 다른 경로에서는 아니다. 상태를 (칸, 글자 위치)로만 두면 같은 칸을 다시 쓰는 경로를 못 거른다. 경로마다 밟은 칸 집합을 들고 다니면 메모리가 경로 수만큼 든다. 경로 하나를 들고 들어갔다 나오는 DFS 백트래킹이 맞다.

### 더 빠르게 만들 수 있나요?

탐색 전에 글자 개수를 세서 단어에 필요한 글자가 판에 모자라면 바로 `false`를 돌려준다. 그리고 첫 글자와 끝 글자 중 판에 더 드문 쪽에서 시작하도록 단어를 뒤집는다. 전부 A인 6 × 6 판에서 B로 끝나는 단어는 900만 번 호출하던 것이 0번이 됐다. 최악의 상한은 그대로지만 흔한 최악 입력을 대부분 없앤다.

### 단어가 여러 개면 어떻게 하나요?

단어마다 이 함수를 부르지 않고, 단어들로 트라이를 만든 뒤 판을 한 번 훑으며 트라이를 같이 내려간다. 경로가 어떤 단어의 접두사도 아니면 끊고, 찾은 단어는 트라이에서 지운다. Word Search II가 이 풀이다.

### 같은 칸을 여러 번 써도 된다면 무엇이 달라지나요?

경로마다 다른 방문 상태가 사라져서 상태가 (칸, 글자 위치)뿐이 된다. m · n · L개의 상태를 메모이제이션하면 O(m · n · L)에 끝난다. "같은 칸을 한 번만"이라는 제약이 지수 시간 백트래킹을 필요하게 만든 원인이다.
