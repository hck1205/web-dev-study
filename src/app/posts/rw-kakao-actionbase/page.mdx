## 하트 하나에 저장소 세 곳

카카오톡 선물하기에는 위시(wish)가 있다. 받고 싶은 선물을 담아 두는 기능이다. 카카오가 2026년 2월 Actionbase 문서에 올린 [Gift Wish 사례](https://github.com/kakao/actionbase/blob/main/website/src/content/docs/stories/use-cases/kakaotalk-gift-wish.mdx)에 원래 구조가 나온다.

- MySQL이 위시 데이터를 저장하고, 사용자 기준 조회(한 건 조회, 목록, 개수)를 맡았다.
- Spring Batch가 상품별 역방향 개수(이 상품을 몇 명이 찜했나)를 모았다.
- Redis가 그 역방향 개수를 캐시해 빠르게 읽게 했다.

문서는 처음엔 잘 돌았다고 쓴다. 트래픽이 늘면서 두 가지에 막혔다. 테이블이 감당하기 편한 크기를 넘어섰고, MySQL과 Redis 사이를 맞춰 두는 일이 복잡해졌다. MySQL 샤딩도 검토했지만 샤드 키 관리, 샤드를 넘는 쿼리, 운영 부담 때문에 다른 길을 찾았다고 적혀 있다.

이 구조가 어디서 아픈지는 그림으로 보면 바로 보인다. "몇 명이 찜했나"라는 숫자가 MySQL의 행에서 한 번, 배치가 모은 결과에서 한 번, Redis 캐시에서 또 한 번, 모두 세 곳에 산다. 배치가 돌기 전에는 Redis 숫자가 실제와 다르다. 배치가 실패하면 다음 배치까지 다르다. 원본과 사본이 여러 곳에 있을 때 생기는 일반적인 문제는 [캐시 무효화](/posts/cache-invalidation) 글에서 다뤘다.

## 팀마다 다시 만들던 좋아요·최근 본 상품·팔로우

위시 하나만의 문제였다면 그 팀이 MySQL을 샤딩하고 끝났을 수도 있다. 카카오가 공개한 동기는 더 넓다. 2026년 1월 문서 [Path to Open Source](https://github.com/kakao/actionbase/blob/main/website/src/content/docs/project/path-to-open-source.mdx)에 이렇게 적었다. 좋아요, 최근 본 상품, 팔로우 같은 기능이 팀마다 서로 다른 기술 스택, 다른 스키마, 다른 장애 양상으로 거듭 만들어지고 있었고, 트래픽이 늘면 저마다 비슷한 확장의 벽에 부딪혔다. 같은 문제를 열 가지 방식으로 푸는 일을 멈추려 했다는 것이다.

카카오는 이런 데이터를 인터랙션(interaction)이라고 부른다. 누가(source) 무엇을 했고(action) 어떤 대상(target)에 했는가. 출발점과 대상의 조합으로 세 축이 나온다.

- 사용자–사용자(U2U): 팔로우, 팔로워 수, 타임라인
- 사용자–상품(U2I): 좋아요, 찜, 본 기록, 양방향 개수
- 상품–상품(I2I): 연관 상품, 비슷한 콘텐츠

같은 문서의 연표는 짧다. 2023년에 시작해 설계와 구현을 했고, 2024년 초 첫 실서비스로 선물하기 위시에 들어갔다. 2024년 말에는 테넌트별 설정을 분리해 서비스끼리 격리하고 커머스 쪽 여러 기능(최근 본 상품 등)으로 넓혔다. 2025년 초에는 카카오톡 친구에 적용했고, 2025년에 공개를 준비하며 API를 다시 설계했다. 2026년 1월 공개됐다. 공개된 코드는 사내에서 운영하던 그 코드이고, 보안상 민감하거나 조직 고유의 내용만 최소한으로 걷어 냈다고 한다.

## 읽을 때 계산하지 않고 쓸 때 다 해 둔다

Actionbase의 설계 목표는 [Core Concepts 문서](https://github.com/kakao/actionbase/blob/main/website/src/content/docs/design/concepts.mdx)에 두 줄로 나온다. 읽기 구조를 쓰기 시점에 미리 계산해서 읽기를 단순 조회로 만든다. 저장은 검증된 HBase에 맡기고 새로 만들지 않는다.

"쓰기 시점에 미리 계산"은 이 블로그에서 여러 번 나온 생각이다. 뉴스 피드에서 글을 쓸 때 팔로워 피드에 미리 넣어 두는 [쓰기 시점 팬아웃](/posts/sd-news-feed-publishing)이 그렇고, 집계 결과를 테이블로 들고 있는 [머티리얼라이즈드 뷰](/posts/sql-views-materialized)도 그렇다. Actionbase는 이걸 인터랙션 전용으로 일반화했다. 하트가 하나 눌릴 때 세 가지를 같이 만든다.

- State: 이 사용자와 이 상품 사이의 지금 상태(찜했나 안 했나). GET이 이걸 읽는다.
- Index: 속성으로 정렬된 목록(예: `created_at` 내림차순). SCAN이 이걸 훑는다.
- Count: 개수(상품별 찜한 사람 수). COUNT가 이걸 읽는다.

읽는 쪽에서 할 수 있는 일도 그만큼 좁다. 한 건 조회, 개수, 정렬된 목록 훑기, 실시간 집계. FAQ는 Neo4j 같은 범용 그래프 질의를 하지 않는다고 분명히 적는다. 질의를 좁힌 대가로 읽기 비용이 부하가 늘어도 평평하게 유지된다는 것이 문서의 주장이다.

WAL과 CDC가 둘 다 있는 이유가 흥미롭다. WAL은 들어온 요청 그대로라 다시 재생해서 상태를 재구성하는 데 쓰고, CDC는 처리한 뒤의 결과라 쌓아서 현재 스냅숏을 만드는 데 쓴다. 데이터베이스 안쪽의 [WAL](/posts/cdc-change-data-capture)과 바깥으로 변경을 알리는 CDC를 애플리케이션 계층에서 다시 한 번 만든 셈이다.

## 찜, 취소, 다시 찜이 뒤섞여 도착하면

사용자가 빠르게 찜했다가 취소하고 다시 찜했다. 요청이 여러 서버를 거치면 이 셋이 보낸 순서대로 도착한다는 보장이 없다. 재시도 때문에 같은 요청이 두 번 올 수도 있다. 순서가 뒤바뀐 채로 그대로 반영하면 마지막에 찜이 풀려 있거나, 개수가 2가 된다.

Actionbase는 상태 기반 뮤테이션으로 이걸 푼다. 요청을 "개수에 1 더하기" 같은 명령으로 보지 않고, 이벤트로 받아 지금 상태를 다음 상태로 옮긴다. 공개된 구현([`StateExtensions.kt`](https://github.com/kakao/actionbase/blob/main/core/src/main/kotlin/com/kakao/actionbase/core/state/StateExtensions.kt))을 읽어 보면 규칙은 단순하다.

- INSERT가 오면, 그 시각이 지금까지 본 가장 늦은 INSERT 시각보다 같거나 늦을 때만 `createdAt`을 그 시각으로 바꾼다.
- DELETE가 오면, 같은 규칙으로 `deletedAt`을 바꾼다.
- `createdAt`이 있고 `deletedAt`보다 늦으면 활성(찜한 상태)이다.
- 개수는 활성 여부가 바뀔 때만 1 오르거나 내린다.

결국 가장 늦은 시각의 이벤트가 이긴다. 분산 시스템에서 흔히 쓰는 [마지막 쓰기 우선(LWW)](/posts/eventual-consistency)의 한 형태로 읽을 수 있다. 다만 시각을 서버가 아니라 클라이언트가 붙인다는 점이 다르다. 문서의 예시를 그대로 따라가 보자. 사용자는 찜(t=100) → 취소(t=200) → 찜(t=300)을 했는데, 도착은 찜(100) → 찜(300) → 취소(200) 순서였다.

보낸 순서대로 도착했어도 결과는 같다. 같은 이벤트가 두 번 와도 시각이 같으니 상태가 바뀌지 않고 개수도 그대로다. 그래서 WAL을 처음부터 다시 재생해도 같은 결과가 나온다. 문서가 멱등(idempotent)이라고 부르는 성질이다. HTTP API에서 같은 요청을 한 번만 반영하는 [멱등 키](/posts/idempotency-key)와 목적은 같지만, 키를 따로 저장하지 않고 상태와 시각만으로 해낸다.

아래 코드에서 직접 돌려 볼 수 있다. 이벤트 목록을 도착 순서대로 받아 마지막 활성 여부와 개수를 돌려준다. 시각이 같은 INSERT와 DELETE가 오면 나중에 도착한 쪽이 이긴다는 구현의 세부(`shouldOverride`)도 넣었다.

<CodePlayground
  caption="도착 순서와 상관없이 같은 상태가 나오는지 확인하기"
  functionName="replay"
  initialCode={`function replay(events) {
  // events: [{ type: "INSERT" | "DELETE", version: 숫자 }]를 도착 순서대로
  // 1. createdAt, deletedAt, version(지금까지 본 가장 큰 시각)을 들고 간다
  // 2. INSERT: createdAt이 없거나 e.version >= createdAt이면 createdAt = e.version
  //    DELETE: deletedAt이 없거나 e.version >= deletedAt이면 deletedAt = e.version
  //    e.version이 지금까지의 version과 같고 두 값이 같아지면, 반대쪽을 지운다
  // 3. 활성 = createdAt이 있고 (deletedAt이 없거나 createdAt > deletedAt)
  // 4. 활성이 false→true면 count + 1, true→false면 count - 1
  return { active: false, count: 0 };
}`}
  solution={`function replay(events) {
  let createdAt = null, deletedAt = null, version = 0, active = false, count = 0;
  for (const e of events) {
    const override = e.version === version;
    version = Math.max(version, e.version);
    if (e.type === "INSERT") {
      if (createdAt === null || e.version >= createdAt) {
        createdAt = e.version;
        if (override && createdAt === deletedAt) deletedAt = null;
      }
    } else if (e.type === "DELETE") {
      if (deletedAt === null || e.version >= deletedAt) {
        deletedAt = e.version;
        if (override && deletedAt === createdAt) createdAt = null;
      }
    }
    const next = createdAt !== null && (deletedAt === null || createdAt > deletedAt);
    if (next && !active) count += 1;
    if (!next && active) count -= 1;
    active = next;
  }
  return { active, count };
}`}

이 방식에는 전제가 있다. 클라이언트가 붙이는 시각이 믿을 만해야 한다. 서버 여러 대의 시계가 크게 어긋나면 실제로는 나중에 누른 취소가 더 이른 시각을 달고 와서 무시될 수 있다. 공개 문서는 시각을 어떻게 맞추는지, 시계가 어긋날 때 어떻게 하는지는 다루지 않는다. 같은 사용자 한 명의 같은 대상에 대한 이벤트는 대개 같은 서비스 서버를 거칠 테니 실제 위험은 작았을 것이라고 짐작할 수 있지만, 이건 내 추론이다.

## 원자적이라는 문서와 원자적이지 않다는 문서

여기서 공개 자료를 읽을 때 조심할 곳이 하나 나온다. 같은 저장소 안에서 두 문서가 다른 말을 한다.

- Mutation 문서는 6단계에서 "State, 인덱스, 개수가 원자적으로 쓰인다"고 하고, 보장 표에도 "Atomic Writes"를 넣었다. 2025년 12월 첫 커밋부터 있던 문장이다.
- 2026년 2월에 올라온 [HBase Consistency 사례](https://github.com/kakao/actionbase/blob/main/website/src/content/docs/stories/how-we-survived/hbase-consistency.mdx)는 "HBase 배치 연산은 원자적이지 않다"고 쓴다. 리전 서버가 중간에 죽거나 네트워크 문제로 일부만 쓰이면 State는 바뀌었는데 Index는 그대로일 수 있다는 것이다.

HBase는 행 하나 안에서의 변경은 원자적으로 처리하지만, 여러 행에 걸친 배치를 하나의 트랜잭션으로 묶어 주지는 않는다. State, Index, Count는 행 키가 서로 다른 별개의 행이고, 해시에 행 종류 코드까지 들어가니 같은 간선의 세 행이 서로 다른 리전, 다른 서버에 놓일 수 있다. 그러니 운영 경험을 담은 뒤쪽 문서가 실제에 더 가깝다고 보는 게 맞을 것이다. 설계 문서는 의도를, 사례 문서는 겪은 일을 적는다.

카카오가 고른 해법은 막는 것이 아니라 찾아서 고치는 것이다.

1. HBase 스냅숏을 내보낸다.
2. Spark 검증 작업이 State와 Index가 짝이 맞는지, State와 Count가 맞는지 본다.
3. 어긋나면 수리 큐에 넣는다. State가 진실이고, Index와 Count는 State에서 언제든 다시 만든다.
4. 검증 주기는 서비스 SLA에 따라 정한다.

문서의 마지막 줄은 "완벽한 원자성을 기대하지 말라"와 "State가 진실이다"다. 파생 데이터를 원본에서 다시 만들 수 있게 설계하면, 부분 실패를 영원히 막지 못해도 영원히 남겨 두지는 않을 수 있다. [CQRS](/posts/cqrs) 글에서 "읽기 모델은 언제든 버리고 다시 만든다"고 한 것과 같은 생각이다.

## 테스트가 통과했는데도 불안해서 만든 검증 층

[How We Survived](https://github.com/kakao/actionbase/blob/main/website/src/content/docs/stories/how-we-survived/index.mdx) 문서(2026년 2월)는 이렇게 시작한다. 테스트는 통과했지만 "정말 문제가 없나"에 자신 있게 답할 수 없었다. 그래서 단계마다 검증 층을 쌓았다.

개발 단계에는 계약 테스트가 있다. 서비스 팀이 붙을 때 문서를 손으로 쓰지 않고 시나리오 테스트를 같이 쓴다. "사용자의 최근 위시 10개를 시각 내림차순으로" 같은 요구를 스키마, 변경, 질의로 테스트에 박고, 그 테스트에서 문서를 자동으로 만들고, 모든 PR에서 돌린다. 한 팀은 내림차순에, 다른 팀은 배치당 정확히 100개에 기대는 식으로 쓰는 방식이 늘어나니 약속한 동작을 테스트로 묶어 두었다는 설명이다.

배포 전에는 [섀도 테스트](https://github.com/kakao/actionbase/blob/main/website/src/content/docs/stories/how-we-survived/shadow-testing.mdx)가 있다. 운영 Actionbase 앞의 Nginx Ingress가 모든 요청과 응답을 접근 로그로 Kafka에 남기고, 같은 요청을 테스트 환경의 새 버전에 재생해 응답을 비교한다. 다르면 배포를 막는다. 로그 기반이라 실시간 트래픽에는 영향이 없다. [카나리 배포](/posts/canary-release)가 일부 사용자에게 새 버전을 보여 주며 확인하는 것과 달리, 이 방식은 사용자에게 새 버전을 한 번도 보여 주지 않고 확인한다. 대신 쓰기 요청을 재생하면 테스트 환경의 상태가 운영과 갈라질 수 있는데, 이걸 어떻게 맞췄는지는 공개되지 않았다.

이전할 때는 [비교 검증](https://github.com/kakao/actionbase/blob/main/website/src/content/docs/stories/how-we-survived/migration-verification.mdx)이 있다. 비교 대상을 HBase를 직접 읽은 값이 아니라 CDC로 쌓은 스냅숏으로 고른 이유가 적혀 있다. 원본 DB → Actionbase → HBase → CDC → 스냅숏 전체가 제대로 돌아야 둘이 맞으니, 다른 경로로 만든 같은 데이터를 맞대면 파이프라인 전체를 한 번에 검증할 수 있다. 덤프와 CDC의 시각이 정확히 맞지 않는 경계 데이터는 이번 창(예: 전날 00:00~23:59)에서 빼고 다음 창에서 검증한다. 창이 밀려가며 결국 모든 데이터가 검증된다.

운영 중에는 앞에서 본 State·Index·Count 정기 검증이 있다. 네 층이 각각 다른 종류의 문제를 잡는다는 게 문서의 정리다.

## 원천이 아닐 때와 바로 쓰지 않을 때

모든 도입이 위시처럼 원천을 옮기는 일은 아니었다. 2026년 2월에 함께 올라온 두 사례가 다른 모양을 보여 준다.

[카카오톡 친구 사례](https://github.com/kakao/actionbase/blob/main/website/src/content/docs/stories/use-cases/kakaotalk-friends.mdx)에서 친구 관계는 수십 개로 샤딩된 MySQL에 있었고, 읽기가 많은 질의를 위해 HBase 기반 뷰가 이미 있었다. 그 뷰는 특정 접근 패턴에 맞춰 만들어져 새 질의를 붙이기 어려웠다. 카카오는 기존 시스템을 바꾸지 않고 Debezium으로 MySQL 변경을 잡아 Kafka로 흘리고 Actionbase가 받아 반영하게 했다. Actionbase는 원천이 아니라 읽기 전용 뷰다. 이게 [CDC](/posts/cdc-change-data-capture)로 읽기 모델을 채우는 [CQRS](/posts/cqrs)의 전형이다. 쓰기 경로를 전혀 건드리지 않으니 이전 위험이 없다.

[선물하기 최근 본 상품 사례](https://github.com/kakao/actionbase/blob/main/website/src/content/docs/stories/use-cases/kakaotalk-gift-recent-views.mdx)는 쓰기가 아주 잦은 경우다. 상품을 볼 때마다 이벤트가 생기니 찜이나 좋아요보다 쓰기가 훨씬 많다. 이걸 사용자 요청 안에서 동기로 처리하면 응답이 느려지고 몰릴 때 역압이 생긴다. 그래서 요청에 `queue=true`를 붙이면 WAL에 넣고 바로 응답한다. Spark Streaming 작업이 WAL을 읽어 묶고, 몰릴 때는 속도를 줄이고, 실패하면 재시도하며 다시 Actionbase에 변경을 보낸다. 반영까지는 보통 수십 ms라고 적혀 있다. 최근 본 상품은 그 정도 늦어도 괜찮다는 판단이다. 요청을 받는 일과 처리하는 일을 나누는 [메시지 큐](/posts/kafka-basics)의 쓰임새 그대로다.

같은 저장소가 기능마다 원천(위시), 뷰(친구), 비동기 반영(최근 본 상품)이라는 다른 역할을 맡았다. 기능이 데이터 정확도와 지연을 얼마나 견디는지에 따라 역할을 고른 것이다.

## 왜 HBase였나, 무엇을 버렸나

FAQ에는 저장소를 고른 이유가 짧게 있다. 카카오 안에서 이 규모에 인터페이스 요구(get, scan, 원자적 checkAndMutate, batch)를 맞추는 저장소는 HBase와 Redicoke(카카오 사내의 Redis 프로토콜 분산 KV 저장소) 둘이었다. 둘 다 수평 확장, 내구성, 빠른 무작위 읽기·쓰기를 갖췄고, HBase를 고른 이유는 대량 적재로 큰 데이터를 옮기기에 더 맞아서였다. 위시 이전에서 본 "덤프 → 대량 적재 → WAL 재생"이 바로 그 쓰임이다. 2026년 2월 문서 기준으로 대량 적재 파이프라인은 아직 공개되지 않았다.

버린 대안도 문서에 흩어져 있다.

- MySQL 샤딩: 위시 사례에서 검토했다가 샤드 키 관리, 샤드 간 질의, 운영 부담 때문에 택하지 않았다.
- 범용 그래프 DB: FAQ는 Neo4j처럼 임의의 탐색을 하는 범용 그래프 질의를 지원하지 않는다고 못 박는다.
- 저장소 직접 개발: 설계 목표가 "검증된 저장소 위에 짓는다"였다. 저장소 추상화(`Datastore`)는 두었고, HBase 말고 작은 규모용 백엔드는 계획으로 남아 있다.

한 가지 흥미로운 기록이 있다. 2025년 12월 첫 커밋의 README 첫 줄은 Actionbase를 "고성능 그래프 데이터베이스"라고 소개했다. 지금 문서는 "범용 그래프 데이터베이스가 아니다"라고 쓴다. 설계가 바뀌었다기보다 무엇을 하지 않는지를 분명히 하는 쪽으로 소개가 바뀐 것으로 보인다.

## 숫자는 어느 판의 숫자인가

규모 숫자는 판마다 달랐다. 2026년 10월 현재 README는 "카카오에서 분당 100만 건 이상", 모든 축이 "2024년부터 분당 100만 건 이상"으로 운영 중이라고 쓴다. 2026년 1월 19일 이후 Benchmarks 문서는 이렇게 적는다.

- Ingress 9대(6코어, 12GB), Worker 9대(40코어, 64GB), HBase 리전 서버 9대(20코어, 64GB)
- 운영 최대 약 33k RPS(2M RPM), 쓰기 약 15%, 읽기 약 85%
- 지연은 읽기 약 5ms, 쓰기 약 20ms
- 내부 시험에서 60k RPS 이상, 시험한 범위에서 선형 확장

같은 문서의 이전 판은 다르다. 2025년 12월 첫 판은 읽기 "초당 수십만 건", p99 5ms 미만 같은 값을 적었고, 2026년 1월 5일 판은 "60k+ TPS"와 "3개 리전에 3대씩"이라고 썼다. 지금은 60k가 운영이 아니라 내부 시험 값으로 옮겨 갔고 리전 이야기는 빠졌다. 저장소 이력으로 누구나 확인할 수 있는 변화다. 이런 숫자를 면접이나 설계 문서에 인용할 때는 어느 판인지 같이 적어야 한다. 이 문제는 시리즈 입구 글 [실제 서비스 사례를 읽는 법](/posts/rw-reading-engineering-blogs)에서 더 자세히 다룬다.

규모를 가늠해 보면, 최대 33k RPS 중 15%가 쓰기라면 초당 약 5천 건의 쓰기다. 쓰기 하나가 State, 정방향·역방향 인덱스, 개수를 같이 건드리니 HBase가 받는 행 쓰기는 그보다 몇 배 많을 것이다. 정확한 배수는 테이블의 인덱스 수에 따라 달라서 문서로는 알 수 없다.

## 공개된 이야기에서 빠져 있을 수 있는 것

이 자료들은 카카오가 고른 이야기다. Path to Open Source 문서도 스스로 "여기 보이는 건 살아남은 것"이라고 쓰고, 2026년 1월에 올리고 5월에 이슈로 옮긴 [#358](https://github.com/kakao/actionbase/issues/358)의 제목은 아예 "전용 인터랙션 DB가 필요했나, 과하게 만들었나"였다. 정직한 질문이지만 답은 열려 있다.

빠진 것은 이렇다. 실제 장애 사례가 날짜와 영향 범위와 함께 나온 문서가 없다. "사용자가 기다리는 동안 고친 실시간 장애"가 있었다고만 한다. 인덱스 수에 따른 쓰기 증폭, HBase 클러스터 운영 비용, 지연의 백분위 분포(현재 판 기준)도 없다. 대량 적재와 비동기 처리기 같은 핵심 부품은 아직 사내에만 있다. 같은 기능을 따로 만들던 팀들이 실제로 모두 옮겨 왔는지, 옮기지 않은 팀은 왜 그랬는지도 알 수 없다. README가 안내하는 if(kakaoAI) 2024 발표 영상은 이 글을 쓰며 열어 보지 못해서 내용을 인용하지 않았다.

## 우리 서비스의 좋아요 버튼이라면

FAQ에 "Actionbase를 쓰지 말아야 할 때"가 있다. 데이터베이스 인스턴스 하나로 감당될 때, 범용 그래프 질의가 필요할 때, 팀에 HBase 운영 경험이 없을 때, 아직 확장의 벽에 닿지 않았을 때. 그리고 대부분의 팀에는 잘 조정한 관계형 DB로 충분하다고 쓴다. 회사가 스스로 쓴 경고라서 무게가 있다.

이 구조가 맞는 조건은 두 가지가 겹칠 때다. 인터랙션 트래픽이 DB 하나와 캐시 하나로 버티기 어렵고, 여러 팀이 같은 개수·목록·토글 기능을 따로 만들고 있다. 카카오는 둘 다였다. 팀이 하나이고 기능이 하나라면 그 팀의 테이블 설계를 고치는 쪽이 싸다. 처음부터 이런 저장소를 따라 만들면 HBase(또는 비슷한 분산 저장소) 운영, Kafka 운영, 검증 작업, 대량 적재 파이프라인을 모두 떠안는다. 카카오 문서에서 시간과 노력이 가장 많이 들어간 부분은 저장소 코드보다 검증 층이었다.

작은 팀이 지금 가져올 수 있는 것은 저장소가 아니라 습관이다.

```sql
-- PostgreSQL 16: 찜 상태를 (사용자, 상품) 한 줄로 두고, 이벤트 시각으로 순서를 가린다
CREATE TABLE wishes (
  user_id     bigint NOT NULL,
  product_id  bigint NOT NULL,
  created_at  bigint,               -- 가장 늦은 찜 이벤트의 클라이언트 시각
  deleted_at  bigint,               -- 가장 늦은 취소 이벤트의 클라이언트 시각
  PRIMARY KEY (user_id, product_id)
);

-- 찜 이벤트: 더 늦은 시각일 때만 덮어쓴다 (같은 요청이 다시 와도 결과가 같다)
INSERT INTO wishes (user_id, product_id, created_at)
VALUES (1, 456, 300)
ON CONFLICT (user_id, product_id) DO UPDATE
  SET created_at = GREATEST(COALESCE(wishes.created_at, 0), EXCLUDED.created_at);

-- 상품별 개수는 이 상태에서 언제든 다시 셀 수 있다 (캐시가 의심스러울 때 대조용)
SELECT product_id, count(*) AS wish_count
FROM wishes
WHERE created_at IS NOT NULL
  AND (deleted_at IS NULL OR created_at > deleted_at)
GROUP BY product_id;
```

PostgreSQL 16에서 시각 300의 찜을 먼저 넣고, 늦게 도착한 시각 100의 찜을 같은 문장으로 한 번 더 넣은 뒤 테이블과 개수를 봤다. `created_at`은 300 그대로이고 개수는 1이다.

```text
 user_id | product_id | created_at | deleted_at 
---------+------------+------------+------------
       1 |        456 |        300 |           
(1 row)

 product_id | wish_count 
------------+------------
        456 |          1
(1 row)
```

MySQL 8이라면 `ON CONFLICT` 대신 `INSERT ... ON DUPLICATE KEY UPDATE created_at = GREATEST(...)`로 같은 일을 한다.

- 토글 이벤트에 시각을 싣고, "개수 +1" 명령 대신 상태를 저장한다. 재시도와 순서 뒤바뀜이 저절로 해결된다.
- 개수·목록 같은 파생 데이터는 원본에서 다시 만들 수 있게 둔다. 그리고 원본으로 다시 센 값과 캐시 값을 맞대는 작업을 하루 한 번이라도 돌린다. 어긋난 건수가 그대로 지표가 된다.
- 저장소를 바꿀 때는 이중 쓰기 → 비교 → 그림자 읽기 → 전환 → 몇 달 뒤 정리 순서를 지키고, 전환 뒤에도 한동안 옛 저장소에 계속 쓴다.

비슷한 신호가 보이면 무엇부터 볼까. "찜 개수가 화면마다 다르다"는 문의가 오면, 먼저 원본에서 다시 센 값과 캐시 값의 차이를 상품별로 뽑는다. 차이가 배치 주기 직후에 0으로 돌아오면 배치 지연 문제이고, 차이가 계속 쌓이면 이중 쓰기 실패나 재시도 중복이다. 테이블이 커져서 느려졌다면 바로 새 저장소를 찾기 전에 질의가 출발점 하나 안을 훑는 모양인지부터 본다. 그렇다면 [기본 키를 (출발점, 정렬 값)으로 바꾸는 것](/posts/sd-chat-message-storage)만으로 크게 나아질 수 있다.

## 면접에서 나올 만한 질문

### 좋아요 수를 MySQL과 Redis에 나눠 두면 무엇이 문제인가요?

같은 숫자가 두 곳 이상에 살아서 어긋나는 시간이 생긴다는 게 문제다. 카카오 선물하기 위시는 MySQL에 원본을 두고 Spring Batch가 상품별 개수를 모아 Redis에 캐시했는데, 트래픽이 늘면서 테이블 크기와 두 저장소 사이의 정합성이 함께 문제가 됐다. 배치 주기만큼 숫자가 늦고, 배치나 캐시 갱신이 실패하면 다음 주기까지 틀린 채로 남는다.

### 쓰기 시점에 미리 계산하는 설계의 장단점은요?

읽기가 단순 조회가 되어 부하가 늘어도 읽기 지연이 평평하게 유지된다는 게 장점이다. 대신 쓰기 한 번이 상태, 인덱스, 개수 여러 행을 건드려 쓰기 비용이 커지고, 그 행들이 서로 어긋날 수 있다. 그래서 질의 모양을 GET, COUNT, SCAN처럼 미리 정해 둘 수 있는 데이터에 맞고, 질의가 자주 바뀌는 데이터에는 맞지 않는다. Actionbase가 범용 그래프 질의를 지원하지 않는 이유도 여기 있다.

### 순서가 뒤바뀌거나 중복된 이벤트는 어떻게 처리하나요?

명령이 아니라 시각이 붙은 이벤트로 받아 상태를 옮긴다. Actionbase는 INSERT와 DELETE 각각의 가장 늦은 시각을 기억하고, INSERT 시각이 더 늦으면 활성으로 본다. 개수는 활성 여부가 바뀔 때만 움직이니 같은 이벤트가 두 번 와도, 순서가 뒤바뀌어도 결과가 같다. 이 덕분에 WAL을 처음부터 재생해도 같은 상태가 나온다. 전제는 클라이언트 시각을 믿을 수 있어야 한다는 것이다.

### HBase 행 키 앞에 해시를 붙인 이유는요?

HBase는 행 키 순서로 구간을 나눠 서버에 배치해서, 비슷한 키가 몰리면 한 리전만 바빠지는 핫스폿이 생긴다. Actionbase는 출발점의 xxhash32 4바이트를 맨 앞에 붙여 사용자들을 리전 전체에 흩고, 한 사용자의 행은 한곳에 모아 범위 스캔이 되게 했다. 대신 여러 사용자를 가로지르는 전역 정렬 스캔은 이 키로 할 수 없다.

### State, Index, Count가 어긋나면 어떻게 하나요?

막으려 하기보다 찾아서 고친다. HBase의 여러 행 배치는 원자적이지 않아서 부분 실패가 생길 수 있다는 걸 카카오도 운영 사례 문서에 적었다. 그래서 스냅숏을 내보내 Spark로 State와 Index, State와 Count를 대조하고, 어긋나면 State를 기준으로 다시 만든다. 검증 주기는 서비스 SLA로 정한다. 파생 데이터를 원본에서 재생성할 수 있게 설계해 둔 덕분에 가능한 방식이다.

### 저장소를 무중단으로 바꾸려면 어떤 순서로 하나요?

이중 쓰기 → 대량 적재와 로그 재생으로 과거 데이터 채우기 → 비교 검증 → 그림자 읽기 → 읽기 전환 → 몇 달 뒤 정리 순서다. 카카오는 위시 이전에서 비교를 한 달 동안 했고, 전환 뒤에도 기존 시스템에 계속 써서 바로 되돌릴 수 있게 했다. 비교는 새 저장소를 직접 읽지 않고 CDC로 쌓은 스냅숏과 맞대서 파이프라인 전체를 함께 검증했다.

### 왜 카카오는 MySQL을 샤딩하지 않고 새 저장소를 만들었나요?

위시 하나만 보면 샤딩이 더 싼 답이었을 수 있다. 카카오가 밝힌 이유는 샤드 키 관리와 샤드 간 질의, 운영 부담에 더해, 좋아요·최근 본 상품·팔로우를 팀마다 다른 방식으로 거듭 만들고 있었다는 점이다. 한 팀의 문제가 아니라 여러 팀의 같은 문제를 한곳에서 풀려는 선택이었다. 저장소는 새로 만들지 않고 이미 사내에서 운영하던 HBase를 썼다.

### 우리 서비스가 10분의 1 규모라면 같은 구조를 따라야 하나요?

대부분은 아니다. 카카오 FAQ도 DB 하나로 감당되거나 HBase 운영 경험이 없거나 아직 확장의 벽에 닿지 않았다면 쓰지 말라고 쓴다. 대신 가져올 것은 습관이다. 토글을 상태와 이벤트 시각으로 저장하고, 개수 같은 파생 데이터는 원본에서 다시 셀 수 있게 두고, 원본과 캐시를 정기적으로 대조하는 작업을 돌린다. 저장소를 바꿀 일이 생기면 그때 이중 쓰기와 그림자 읽기 순서를 따른다.
