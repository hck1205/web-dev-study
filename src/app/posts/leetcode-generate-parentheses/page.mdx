[괄호 검사 함수](/posts/leetcode-valid-parentheses)를 짜고 나서 테스트를 쓰려는데, 올바른 괄호 문자열을 손으로 몇 개 적다 보니 빠진 게 있는지 자신이 없었다. 3쌍이면 다섯 개쯤일 것 같고, 4쌍이면 몇 개인지 감도 오지 않는다. 길이별로 올바른 문자열을 전부 만들어 주는 함수가 있으면 테스트가 확실해진다.

[LeetCode 22. Generate Parentheses](https://leetcode.com/problems/generate-parentheses/)가 그 함수를 짜는 문제다. 검사가 아니라 생성이고, 답이 하나가 아니라 목록이다. 백트래킹(backtracking)의 입문 문제로 가장 많이 나오고, 답의 개수가 카탈란 수라는 수학과도 이어진다. 이 글은 모두 만들고 검사하는 풀이에서 시작해 백트래킹, 재귀 없는 스택, 동적 계획법, 끼워 넣기까지 다섯 가지를 비교한다. 백트래킹의 일반적인 틀은 [재귀와 백트래킹 글](/posts/recursion-backtracking)에 있다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## n쌍으로 만들 수 있는 올바른 괄호를 전부

정수 `n`이 주어진다. 여는 괄호 `(` n개와 닫는 괄호 `)` n개로 만들 수 있는 올바른 괄호 문자열을 모두 돌려준다. 순서는 상관없다. 괄호는 소괄호 한 종류뿐이다.

올바른 괄호의 조건을 한 종류 괄호에 맞게 다시 쓰면 둘이다.

- 전체에서 `(`와 `)`의 개수가 같다.
- 앞에서부터 어디까지 잘라 봐도, 그 앞부분(접두사)에서 `)`가 `(`보다 많지 않다.

두 번째 조건이 중요하다. `())(`는 개수는 같지만 세 글자까지 잘랐을 때 `)`가 2개, `(`가 1개라서 틀렸다. 앞에서부터 읽으면서 "지금까지 연 개수 - 닫은 개수"를 잔고처럼 세면, 잔고가 한 번도 음수가 되지 않고 끝에 0이어야 한다.

`n`은 1 이상 8 이하다. 작아 보이지만 답의 개수가 빠르게 커져서, n = 8이면 답이 1430개다. 출력 자체가 크기 때문에 어떤 풀이든 답을 다 적는 시간보다 빠를 수는 없다. 그래서 이 문제에서 "빠른 풀이"는 틀린 문자열을 덜 만드는 풀이라는 뜻이다.

## 손으로 n = 3을 적어 보면

빠뜨리지 않으려면 규칙을 정해서 적어야 한다. 왼쪽 글자부터 `(`를 먼저 시도하는 순서로 적어 보자.

```text
((()))   세 번 열고 세 번 닫는다
(()())   두 번 열고, 닫고, 열고, 두 번 닫는다
(())()   두 번 열고 두 번 닫은 뒤, 한 쌍
()(())   한 쌍 뒤에 두 겹
()()()   한 쌍씩 세 번
```

다섯 개다. 적는 동안 머릿속에서 한 일은 이렇다. 매 글자에서 `(`를 놓을 수 있으면 먼저 놓아 보고, 그 뒤를 다 적고 나면 그 자리를 `)`로 바꿔 본다. `(`를 놓을 수 있는 조건은 아직 n개를 다 안 썼을 때, `)`를 놓을 수 있는 조건은 지금까지 닫은 개수가 연 개수보다 적을 때다. 이 손 작업을 그대로 코드로 옮긴 것이 백트래킹 풀이다.

## 일단 다 만들고 검사하기

규칙을 생각하기 전에 떠오르는 방법은 길이 2n짜리 문자열을 `(`와 `)`로 만들 수 있는 모든 경우를 만들고, 하나씩 검사해서 올바른 것만 남기는 것이다. 칸마다 두 가지라 2^(2n)가지다.

```js
function generateParenthesis(n) {
  const res = [];
  const buf = [];

  // 잔고가 음수가 된 적 없고 끝에 0이면 올바르다
  function isValid(s) {
    let balance = 0;
    for (const ch of s) {
      balance += ch === "(" ? 1 : -1;
      if (balance < 0) return false;
    }
    return balance === 0;
  }

  function go() {
    if (buf.length === 2 * n) {
      const s = buf.join("");
      if (isValid(s)) res.push(s);
      return;
    }
    buf.push("("); go(); buf.pop(); // 이 칸에 ( 를 넣어 보고
    buf.push(")"); go(); buf.pop(); // ) 도 넣어 본다
  }

  go();
  return res;
}
```

n = 8이면 2^16 = 65536개를 만들고 검사해서 1430개만 남긴다. 만든 것의 98%를 버린다. 문자열마다 검사가 O(n)이니 전체는 O(2^(2n) · n)이다. n = 8에서 27ms로 LeetCode는 통과하지만, 버리는 비율은 n이 커질수록 더 나빠진다. n = 12면 1677만 개를 만들어 20만 개를 남긴다.

낭비가 어디서 생기는지 보면 다음 풀이가 보인다. `)`로 시작하는 문자열은 첫 글자에서 이미 틀렸다. 그런데 이 풀이는 `)` 뒤의 2n - 1칸을 끝까지 채운 다음에야 검사한다. `)`로 시작하는 문자열만 2^(2n-1)개, 전체의 절반이다.

## 틀린 접두사는 더 키우지 않는다

앞에서부터 한 글자씩 붙여 가며 만든다면, 이미 틀린 접두사 뒤에 무엇을 붙여도 올바른 문자열이 될 수 없다. 그러니 틀리는 순간 그 갈래를 버린다. 백트래킹의 가지치기(pruning)다. 이 문제에서는 가지치기 조건이 아주 단순하다.

- `(`는 지금까지 연 개수 `open`이 n보다 적을 때만 붙인다. n개를 넘게 열면 끝에 개수를 맞출 수 없다.
- `)`는 닫은 개수 `close`가 `open`보다 적을 때만 붙인다. 같으면 잔고가 0이라 닫을 괄호가 없다.

이 두 조건만 지키면 끝까지 간 문자열은 검사할 필요 없이 모두 올바르다. 잔고가 음수가 된 적이 없고, 길이가 2n인데 `open`이 n을 넘지 않았으니 `open = close = n`이다.

n = 2의 선택 과정을 나무로 그리면 이렇다. 점선은 조건에 막혀 들어가지 않은 갈래다.

```js
function generateParenthesis(n) {
  const res = [];
  const path = []; // 만드는 중인 문자열. push/pop으로 붙이고 되돌린다

  function go(open, close) {
    if (path.length === 2 * n) {
      res.push(path.join("")); // 조건을 지켜 왔으니 검사 없이 올바르다
      return;
    }
    if (open < n) {            // 여는 괄호는 n개까지
      path.push("(");
      go(open + 1, close);
      path.pop();
    }
    if (close < open) {        // 닫는 괄호는 연 것보다 적을 때만
      path.push(")");
      go(open, close + 1);
      path.pop();
    }
  }

  go(0, 0);
  return res;
}
```

`(`를 먼저 시도하므로 답이 사전순(`(`가 `)`보다 앞)으로 나온다. n = 3이면 앞에서 손으로 적은 순서 그대로다.

### Python과 Java로 쓰면

Python은 문자열 덧셈 대신 리스트에 붙였다 빼고, 다 찼을 때만 `join`한다. `open`은 내장 함수 이름이라 `open_`으로 피했다. n이 8 이하라 재귀 깊이는 최대 16이고, 기본 한도 1000과 거리가 멀다.

```python
from typing import List

def generate_parenthesis(n: int) -> List[str]:
    res = []
    path = []

    def go(open_: int, close: int) -> None:
        if len(path) == 2 * n:
            res.append("".join(path))
            return
        if open_ < n:            # 여는 괄호는 n개까지
            path.append("(")
            go(open_ + 1, close)
            path.pop()
        if close < open_:        # 닫는 괄호는 연 것보다 적을 때만
            path.append(")")
            go(open_, close + 1)
            path.pop()

    go(0, 0)
    return res
```

Java는 길이 2n의 `char[]` 하나를 계속 덮어쓴다. 같은 자리 `buf[len]`에 다음 갈래의 글자를 그냥 쓰면 되니 pop이 필요 없다. 완성됐을 때 `new String(buf)`가 배열을 복사해 새 문자열을 만들어서, 나중에 배열을 덮어써도 답이 바뀌지 않는다.

```java
import java.util.ArrayList;
import java.util.List;

class Solution {
    public List<String> generateParenthesis(int n) {
        List<String> res = new ArrayList<>();
        go(new char[2 * n], 0, 0, 0, n, res);
        return res;
    }

    // buf[0..len) 가 지금까지 만든 접두사
    private void go(char[] buf, int len, int open, int close, int n, List<String> res) {
        if (len == buf.length) {
            res.add(new String(buf)); // 배열을 복사해 새 문자열을 만든다
            return;
        }
        if (open < n) {
            buf[len] = '(';
            go(buf, len + 1, open + 1, close, n, res);
        }
        if (close < open) {
            buf[len] = ')'; // 같은 칸을 덮어쓰니 따로 되돌릴 필요가 없다
            go(buf, len + 1, open, close + 1, n, res);
        }
    }
}
```

세 언어 모두 n = 3에서 `((()))`, `(()())`, `(())()`, `()(())`, `()()()`를, n = 8에서 1430개를 낸다.

## 재귀 없이 상태를 직접 쌓는 스택

재귀 호출은 콜 스택에 `(path, open, close)`를 쌓는 것과 같다. 그 상태를 직접 스택에 넣고 꺼내면 재귀 없이 같은 탐색을 할 수 있다. 재귀 깊이 제한이 걱정되는 언어나, 탐색을 중간에 멈췄다가 이어 가야 할 때 이렇게 바꾼다.

```js
function generateParenthesis(n) {
  const res = [];
  const stack = [["", 0, 0]]; // [만든 문자열, open, close]
  while (stack.length) {
    const [s, open, close] = stack.pop();
    if (s.length === 2 * n) {
      res.push(s);
      continue;
    }
    // 나중에 넣은 것이 먼저 나오니, ( 를 먼저 보려면 ) 를 먼저 넣는다
    if (close < open) stack.push([s + ")", open, close + 1]);
    if (open < n) stack.push([s + "(", open + 1, close]);
  }
  return res;
}
```

넣는 순서를 `)`, `(`로 뒤집은 것이 포인트다. 스택은 나중에 넣은 것을 먼저 꺼내니, `(`를 나중에 넣어야 `(` 갈래부터 탐색해 재귀 풀이와 같은 사전순이 나온다. 순서가 상관없다면 아무렇게나 넣어도 답의 집합은 같다. 스택을 큐로 바꾸면 너비 우선 탐색이 되는데, 이 문제는 답이 모두 같은 깊이(2n)의 잎에 있어서 결과는 같고 순서만 바뀐다. 대신 한 층 전체를 들고 있어야 해서 메모리가 더 든다.

여기서는 상태마다 새 문자열 `s + "("`를 만든다. 재귀 풀이처럼 `path` 하나를 공유하려면 "되돌리기"도 스택에 넣어야 해서 코드가 복잡해진다. n이 작아 문자열 복사가 비싸지 않으니 이 방식이 읽기 쉽다. n = 12(답 208012개)로 재 보니 재귀 160ms, 이 풀이 99ms였다.

## 첫 괄호가 닫히는 자리로 나누기

완전히 다른 방향에서 보자. 올바른 괄호 문자열의 첫 글자는 반드시 `(`다. 이 첫 `(`의 짝인 `)`가 어딘가에 있다. 그 짝을 기준으로 문자열을 자르면 `(A)B` 모양이 된다.

- `A`는 첫 쌍 안쪽이고, 그 자체로 올바른 괄호 문자열이다(비어 있을 수 있다).
- `B`는 첫 쌍 뒤쪽이고, 역시 올바른 괄호 문자열이다(비어 있을 수 있다).

`A`가 c쌍이면 `B`는 n - 1 - c쌍이다. 그래서 n쌍의 답은 c를 0부터 n - 1까지 바꿔 가며 "c쌍의 답"과 "n - 1 - c쌍의 답"을 짝지어 `(A)B`로 붙인 것이다. 작은 n의 답으로 큰 n의 답을 만드는 [동적 계획법](/posts/dynamic-programming)이다.

```js
function generateParenthesis(n) {
  const f = [[""]]; // f[k] = k쌍으로 만든 올바른 문자열 목록. 0쌍은 빈 문자열 하나
  for (let k = 1; k <= n; k++) {
    f[k] = [];
    for (let c = 0; c < k; c++) {          // 첫 쌍 안에 c쌍
      for (const a of f[c]) {
        for (const b of f[k - 1 - c]) {    // 첫 쌍 뒤에 k - 1 - c쌍
          f[k].push("(" + a + ")" + b);
        }
      }
    }
  }
  return f[n];
}
```

아래 그림은 n = 3까지 표가 채워지는 과정이다.

이 분해는 중복도 누락도 없다. 어떤 올바른 문자열이든 첫 `(`의 짝은 하나로 정해지니 `(A)B`로 나누는 방법이 딱 하나이고, 거꾸로 올바른 `A`, `B`로 만든 `(A)B`는 늘 올바르다. 그래서 검사나 중복 제거가 필요 없다.

k마다 답 목록을 만들어 두니 n 하나만 필요할 때는 작은 k의 목록만큼 메모리를 더 쓴다. 대신 "1쌍부터 n쌍까지 다 달라"는 요구에는 이 풀이가 가장 자연스럽다. 이 분해는 뒤에서 카탈란 수 점화식으로 다시 나온다. n = 12에서 114ms로 백트래킹과 비슷했다.

## 한 쌍씩 끼워 넣기

또 하나의 관찰이 있다. 올바른 괄호 문자열에는 반드시 `()`가 붙어 있는 곳이 있다. 가장 안쪽 쌍이다. 그걸 지우면 n - 1쌍의 올바른 문자열이 된다. 거꾸로 하면 n - 1쌍의 답마다 모든 위치에 `()`를 끼워 넣으면 n쌍의 답이 전부 나온다. 다만 같은 결과가 여러 번 나오니 집합으로 중복을 지운다.

```js
function generateParenthesis(n) {
  let cur = new Set([""]);
  for (let k = 1; k <= n; k++) {
    const next = new Set();
    for (const s of cur) {
      for (let i = 0; i <= s.length; i++) {
        next.add(s.slice(0, i) + "()" + s.slice(i)); // 모든 자리에 한 쌍을 끼운다
      }
    }
    cur = next; // Set이 중복을 지운다
  }
  return [...cur];
}
```

맞기는 하지만 중복이 많다. 단계마다 만든 개수와 남은 개수를 세어 봤다.

```text
k   만든 문자열   중복 제거 후
1        1            1
2        3            2
3       10            5
4       35           14
```

4쌍에서 35개를 만들어 14개를 남긴다. `()`를 `()` 앞에 끼우든 뒤에 끼우든 `()()`가 되는 식으로 같은 문자열이 여러 번 나온다. 문자열마다 해시를 계산하는 비용도 있다. n = 8에서 1.7ms로, 백트래킹의 세 배쯤이다. [Valid Parentheses](/posts/leetcode-valid-parentheses)의 "붙은 짝 지우기"를 거꾸로 돌린 풀이라서 함께 기억해 두면 좋다.

## 답의 개수는 카탈란 수

n에 따라 답이 1, 2, 5, 14, 42, 132, 429, 1430개로 늘어난다. 이 수열이 카탈란 수(Catalan number)다. 앞 절의 `(A)B` 분해를 개수로 바꾸면 점화식이 바로 나온다.

```text
C(0) = 1
C(n) = C(0)·C(n-1) + C(1)·C(n-2) + ... + C(n-1)·C(0)
```

닫힌 식은 `C(n) = (2n)! / ((n + 1)! · n!)`이고, n이 커지면 대략 `4^n / (n^1.5 · √π)`로 자란다. 2^(2n) = 4^n보다 n^1.5배쯤 작다. 전부 만드는 풀이가 버리는 비율이 n과 함께 커지는 이유다.

복잡도도 이 수로 말한다. 답이 C(n)개이고 각각 길이 2n이라, 답을 적는 데만 O(n · C(n))가 든다. 백트래킹은 가지치기 덕분에 막다른 갈래로 들어가지 않으므로, 방문하는 마디가 잎(답) 수의 상수 배 안팎이고(앞에서 잰 대로 다섯 배쯤) 전체 O(n · C(n)) = O(4^n / √n)이다. 공간은 재귀 깊이 O(n)에 답 목록 O(n · C(n))이다. 면접에서 "시간 복잡도가 뭔가요"라고 물으면 "출력 크기에 비례하고, 출력 크기가 카탈란 수라 O(4^n / √n)"이라고 답한다.

## 자주 틀리는 곳

닫는 괄호 조건을 `close <= open`으로 쓰면 잔고가 0일 때도 `)`를 붙여서 `)(`나 `())(` 같은 틀린 문자열이 섞인다. 반대로 `close < n`으로 쓰면 개수만 보고 순서를 안 봐서 역시 틀린 문자열이 나온다. 닫는 쪽 조건은 반드시 "연 것보다 적게 닫았나"여야 한다.

공유하는 `path`를 그대로 답에 넣는 실수도 흔하다.

```js
// path 배열 자체를 넣었다
if (path.length === 2 * n) {
  res.push(path); // 나중에 pop으로 비워지면 res의 모든 칸이 같은 빈 배열을 가리킨다
  return;
}
```

배열은 참조로 들어가니 끝나고 보면 답이 전부 같은 빈 배열이다. `path.join("")`처럼 그 순간의 값을 새로 만들어 넣어야 한다. JavaScript와 Python의 문자열은 불변이라 `s + "("`처럼 매번 새 문자열을 넘기면 이 문제가 없다. 대신 단계마다 문자열을 복사하는 비용이 든다. n이 8 이하라 차이는 작다.

`pop`을 빼먹으면 `(`를 붙이고 돌아온 뒤 `)` 갈래에서 `path`에 `(`가 남아 있어 길이가 맞지 않는다. 붙이고, 내려가고, 떼는 세 줄을 늘 한 묶음으로 쓴다.

결과 목록을 함수 밖 전역 변수에 두면, LeetCode가 같은 프로세스에서 여러 테스트를 돌릴 때 앞 테스트의 답이 남는다. `res`는 함수 안에서 새로 만든다.

## 면접관이 조건을 바꾸면

### 개수만 알려 달라면

목록이 필요 없으면 카탈란 수를 계산한다. 점화식을 그대로 쓰면 O(n²)이다.

```js
function catalan(n) {
  const c = new Array(n + 1).fill(0);
  c[0] = 1;
  for (let k = 1; k <= n; k++)
    for (let i = 0; i < k; i++) c[k] += c[i] * c[k - 1 - i]; // 첫 쌍 안에 i쌍, 밖에 k-1-i쌍
  return c[n];
}
// 3 → 5,  8 → 1430,  12 → 208012,  19 → 1767263190
```

n이 크면 수가 금방 커진다. C(31) = 14544636039226909는 이미 2^53을 넘어서 JavaScript의 `number`로는 정확하지 않고 `BigInt`가 필요하다. Java의 `long`은 C(35)까지 담고 C(36)에서 넘친다. 이 경계를 아는지가 꼬리 질문으로 나온다. 같은 수가 n개 노드로 만들 수 있는 이진 탐색 트리의 모양 수(LeetCode 96 Unique Binary Search Trees)로도 나온다.

### 사전순으로 k번째 하나만 달라면

전부 만들고 k번째를 고르면 C(n)개를 다 만든다. 대신 "남은 r칸으로 잔고 b를 0으로 만드는 방법 수"를 표로 세어 두고, 앞 글자부터 `(`를 놓았을 때 이어지는 개수가 k 이상이면 `(`, 아니면 그만큼 k에서 빼고 `)`를 놓는다. 표가 O(n²), 글자를 정하는 데 O(n)이다. n = 3이면 k = 1부터 5까지 `((()))`, `(()())`, `(())()`, `()(())`, `()()()`이 나오고, n = 4에서 7번째는 `(()())()`, 14번째는 `()()()()`다. 개수를 세어 건너뛰는 이 방식은 순열의 k번째(LeetCode 60 Permutation Sequence)에도 그대로 쓰인다.

### 괄호 종류가 여러 개라면

`()`와 `[]` 두 종류로 n쌍을 만든다면, 닫을 때 아무 괄호나 닫을 수 없고 가장 최근에 연 괄호의 짝을 닫아야 한다. 그래서 `path`와 별개로 "기다리는 닫는 괄호 스택"을 들고 다닌다. 여는 괄호를 붙일 때 그 짝을 스택에 넣고, 닫을 때는 스택 맨 위를 꺼내 붙인다. [Valid Parentheses](/posts/leetcode-valid-parentheses)의 검사 스택을 생성 쪽에서 쓰는 셈이다. 모양은 C(n)가지이고 쌍마다 종류가 2가지라 답은 C(n) · 2^n개다. n = 2에서 8개, n = 3에서 40개가 나온다.

### 중첩 깊이에 상한이 있다면

"깊이가 d를 넘지 않는" 문자열만 원하면 `(`의 조건에 `open - close < d`를 더한다. 잔고가 곧 현재 깊이라서 조건 하나로 끝난다. n = 3, d = 2면 `((()))` 하나만 빠지고 `(()())`, `(())()`, `()(())`, `()()()` 네 개가 남는다. 가지치기 조건을 늘리는 것만으로 제약을 반영하는 게 백트래킹의 장점이다.

### 비슷한 문제

틀린 괄호 문자열에서 최소 개수를 지워 올바른 문자열을 모두 구하는 LeetCode 301 Remove Invalid Parentheses는 이 문제의 잔고 개념과 너비 우선 탐색을 함께 쓴다. 가지치기가 있는 백트래킹으로는 [Subsets](/posts/leetcode-subsets), [Permutations](/posts/leetcode-permutations), [Combination Sum](/posts/leetcode-combination-sum), [N-Queens](/posts/leetcode-n-queens)가 이어진다. 스택 패턴의 다른 문제는 [단조 스택 패턴 글](/posts/monotonic-stack-pattern)에서 모아 볼 수 있다.

## 잔고가 음수가 되지 않는 길만 걷는다

올바른 괄호는 앞에서부터 센 "연 개수 - 닫은 개수"가 한 번도 음수가 되지 않고 끝에 0인 문자열이다. 그래서 만들 때도 여는 괄호는 n개까지, 닫는 괄호는 연 것보다 적을 때만 붙이면 끝에 도착한 문자열은 모두 답이다. 답의 개수가 카탈란 수라서 시간은 출력 크기인 O(4^n / √n)을 넘지 않는다. 같은 답을 `(A)B` 분해로 쌓아 올리면 동적 계획법이 되고, 그 분해가 카탈란 수 점화식이다.

## 면접에서 나올 만한 질문

### 가지치기 조건 두 개만으로 왜 올바른 문자열만 나오나요?

`(`는 `open < n`일 때, `)`는 `close < open`일 때만 붙인다. 두 번째 조건 덕분에 잔고가 음수가 된 적이 없고, 길이 2n에서 `open`이 n을 넘지 않았으니 `open = close = n`이 된다. 올바른 괄호의 두 조건을 모두 만족하니 끝에서 따로 검사할 필요가 없다.

### 시간 복잡도는 어떻게 되나요?

출력 크기에 비례한다. 답의 개수가 카탈란 수 C(n)이고 대략 `4^n / (n^1.5 · √π)`라서, 길이 2n짜리를 적는 비용까지 합하면 O(n · C(n)) = O(4^n / √n)이다. 가지치기로 막다른 갈래에 들어가지 않으니 탐색 비용도 이 범위 안이다.

### 전부 만들고 검사하는 풀이와 비교하면 얼마나 아끼나요?

전부 만들면 4^n개를 만든다. n = 8이면 65536개를 만들어 1430개만 남기고, 백트래킹은 6917번 호출로 끝난다. 차이는 n^1.5배 정도로 n이 커질수록 벌어진다. 특히 `)`로 시작하는 절반은 첫 글자에서 이미 틀렸는데 전부 만드는 풀이는 끝까지 채운다.

### 재귀 없이 풀 수 있나요?

`(문자열, open, close)` 상태를 스택에 넣고 꺼내면 된다. 재귀 호출이 콜 스택에 쌓던 것을 직접 쌓는 것이다. 사전순을 유지하려면 `)` 상태를 먼저, `(` 상태를 나중에 넣는다. 스택을 큐로 바꾸면 너비 우선 탐색이 되고, 답은 같지만 메모리를 더 쓴다.

### 동적 계획법으로는 어떻게 푸나요?

올바른 문자열은 첫 `(`의 짝을 기준으로 `(A)B`로 하나뿐인 방법으로 나뉘고, `A`와 `B`도 올바르다. `A`가 c쌍이면 `B`는 n - 1 - c쌍이라, 작은 k의 답 목록을 짝지어 붙이면 큰 k의 답이 된다. 중복이나 누락이 없어 검사가 필요 없고, 1쌍부터 n쌍까지 모두 필요할 때 좋다.

### 개수만 필요하면요? n이 크면 무엇을 조심하나요?

카탈란 수를 점화식으로 O(n²)에 계산하거나 `(2n)! / ((n+1)! n!)`으로 구한다. C(31)부터 2^53을 넘어 JavaScript `number`는 정확하지 않으니 `BigInt`를 쓰고, Java `long`은 C(36)에서 넘친다. 나머지 연산을 요구하면 모듈러 역원으로 닫힌 식을 계산한다.

### 괄호 종류가 두 가지라면 어떻게 바꾸나요?

닫는 괄호는 가장 최근에 연 괄호의 짝이어야 하니, 기다리는 닫는 괄호를 담은 스택을 함께 들고 다닌다. 열 때 종류마다 갈래를 나누고 짝을 스택에 넣고, 닫을 때는 스택 맨 위를 꺼내 붙인다. 답은 C(n) · 2^n개가 된다.
