## 굵게 보이는 글자 두 개

배송 안내 문단을 이렇게 썼다.

```html
<p>배송은 <strong>영업일 기준 3일</strong> 걸린다. <b>무료 배송</b> 상품이다.</p>
```

화면에서는 두 곳 모두 굵게 보인다. 디자이너도, 코드 리뷰어도 차이를 못 느낀다. 이 문단을 Chromium 141에서 열고 Playwright로 접근성 트리(스크린리더가 받아 가는 구조)를 찍었다.

```text
- paragraph:
  - text: 배송은
  - strong: 영업일 기준 3일
  - text: 걸린다. 무료 배송 상품이다.
```

`strong`은 트리에 strong이라는 노드로 남고, `b`는 앞뒤 글자와 합쳐져 평범한 글자가 됐다. 브라우저 입장에서 `b`는 "글자를 굵게 그려라"일 뿐 의미가 없다. 같은 방식으로 `em`은 emphasis로 남고 `i`는 사라진다.

그렇다고 스크린리더가 strong을 만나면 목소리를 바꿔 읽는 건 아니다. NVDA나 VoiceOver의 기본 설정은 대부분 강조를 소리로 구분하지 않는다. 사용자가 설정을 켜거나 서식 정보를 물을 때 드러난다. 검색 엔진도 둘을 크게 다르게 다룬다는 근거는 없다. 그럼에도 구분하는 이유는 의미가 HTML에 남아 있어야 그걸 쓰려는 도구가 쓸 수 있기 때문이다. 읽기 모드, 번역기, 요약 도구, `getByRole`로 요소를 찾는 테스트, 그리고 나중에 디자인을 바꾸는 사람까지 모두 태그를 보고 판단한다. "중요해서 굵다"와 "디자인상 굵다"가 같은 태그면, 디자인을 바꿀 때 중요한 표시까지 같이 사라진다.

이 글은 페이지 뼈대(랜드마크, 제목 계층, 폼)가 아니라 문단 안쪽의 글자를 담는 태그를 다룬다. 뼈대 쪽은 [시맨틱 HTML](/posts/html-semantics)에 있고, 글자 모양을 다루는 CSS는 [CSS 글자 다루기](/posts/css-typography)에 있다.

## 강조와 관례: em, strong, i, b

네 태그는 HTML 4 시절에는 "기울임 둘, 굵게 둘"로 불렸다. HTML5에서 의미가 다시 정해졌다.

| 태그 | 뜻 | 쓰는 곳 |
|---|---|---|
| `em` | 말할 때 힘주는 강세. 위치가 바뀌면 문장 뜻이 바뀐다 | "이건 *지금* 고쳐야 한다" |
| `strong` | 중요함, 심각함, 급함 | 경고, 놓치면 안 되는 조건 |
| `i` | 다른 목소리나 결의 말: 학명, 외국어 구절, 생각, 배 이름 | `<i lang="la">Felis catus</i>` |
| `b` | 중요하진 않지만 눈길을 끌어야 하는 말: 키워드, 제품 이름, 기사 첫머리 | 요약문 속 제품 이름 |

`em`과 `strong`의 차이는 "어떻게 말하느냐"와 "얼마나 중요하냐"다. `em`은 문장 안에서 강세를 어디 두느냐에 따라 뜻이 바뀐다. "*나는* 안 했다"와 "나는 *안* 했다"는 다른 말이다. `strong`은 강세가 아니라 무게다. "결제 전 **주소를 확인한다**"처럼 경고에 쓴다. 중첩하면 더 강해진다는 규칙도 있지만, 실무에서는 한 번이면 충분하다.

`i`와 `b`를 쓸 때는 `lang` 속성을 함께 생각한다. 외국어 구절을 `i`로 감쌌다면 `lang`을 붙여야 스크린리더가 그 언어의 발음으로 읽는다. 아무 의미 없이 굵게만 보이고 싶다면 태그 대신 CSS의 `font-weight`가 맞다. `b`는 "의미가 아주 약하게라도 있는" 굵음에 남겨 둔다.

한글 글에서는 `em`의 기본 모양이 문제가 된다. 브라우저 기본 스타일이 `em`과 `i`에 `font-style: italic`을 주는데, 한글 글꼴은 대부분 이탤릭이 없어서 글자를 비스듬히 민 가짜 기울임으로 그린다. 읽기 불편하다면 태그를 `strong`으로 바꾸지 말고 모양만 바꾼다. 의미는 그대로 두고 표현만 고치는 것이다.

```css
/* 한국어 본문에서는 강세를 기울임 대신 굵기와 색으로 */
:lang(ko) em { font-style: normal; font-weight: 600; }
```

가짜 기울임과 굵기를 다루는 `font-synthesis`는 [CSS 글자 다루기](/posts/css-typography)에서 다뤘다.

`u`도 HTML5에서 "철자 오류 표시처럼 뜻이 있는 밑줄"로 다시 정의됐다. 링크와 헷갈리니 거의 쓰지 않는다.

## 짧은 말에 붙이는 태그들

문단 안에서 낱말 하나, 구절 하나에 붙이는 태그가 몇 개 더 있다. 같은 Chromium에서 각각이 접근성 트리에 어떻게 남는지 함께 봤다.

```html
<p><mark>검색어</mark> <del>10,000원</del> <ins>8,000원</ins> <s>품절</s> H<sub>2</sub>O x<sup>2</sup></p>
<p><abbr title="HyperText Markup Language">HTML</abbr>, <dfn>시맨틱</dfn>, <cite>해리 포터</cite>, <code>let</code></p>
```

```text
- paragraph:
  - mark: 검색어
  - deletion: 10,000원
  - insertion: 8,000원
  - text: 품절 H
  - subscript: "2"
  - text: O x
  - superscript: "2"
- paragraph:
  - text: HTML,
  - term: 시맨틱
  - text: ", 해리 포터,"
  - code: let
```

- `mark`: 지금 맥락에서 눈여겨볼 부분. 검색 결과에서 검색어를 칠하는 용도가 대표적이다. 원래 글쓴이의 강조가 아니라 읽는 사람의 상황에 따른 표시라서 `strong`과 다르다.
- `del`과 `ins`: 문서를 고친 기록. 지운 것과 넣은 것이다. `datetime`과 `cite`(고친 이유가 적힌 주소) 속성을 붙일 수 있다. 할인 전 가격처럼 "고쳤다"는 사실이 의미를 갖는 곳에 쓴다.
- `s`: 더 이상 맞지 않는 내용. 고친 기록이 아니라 "이건 이제 아니다"다. 측정에서 `s`는 트리에 따로 남지 않고 글자가 됐다. 품절이나 할인 전 가격을 취소선으로만 보여 주면 스크린리더 사용자는 그 표시를 모를 수 있으니, 중요한 정보라면 "정가"처럼 글자로도 적는다.
- `sub`, `sup`: 화학식, 각주 번호, 수식처럼 위아래 위치에 뜻이 있을 때만 쓴다. "1st"의 st처럼 꾸밈이면 CSS로 처리한다.
- `abbr`: 줄임말. `title`에 풀어 쓴 말을 적지만, 측정 결과처럼 트리에는 `HTML`만 남고 `title`은 마우스를 올려야 보인다. 키보드와 터치 사용자는 볼 방법이 없다. 그래서 처음 나올 때 본문에 풀어 쓰는 쪽이 확실하다.
- `dfn`: 이 문장에서 정의하는 용어. 트리에 term으로 남는다. 용어 정의 바로 옆에 둔다.
- `cite`: 작품 제목(책, 영화, 논문). 사람 이름에는 쓰지 않는다.
- `code`, `kbd`, `samp`, `var`: 코드, 키보드 입력(`Ctrl`+`C`), 프로그램 출력, 변수. 기술 블로그에서 `kbd`를 구분해 두면 단축키를 다르게 꾸미기 쉽다.
- `time`: 날짜와 시각을 기계가 읽을 수 있게 `datetime="2026-10-24"`로 적는다.

## 인용은 짧으면 q, 길면 blockquote

문장 속 짧은 인용은 `q`, 따로 떼어 놓는 긴 인용은 `blockquote`다.

```html
<p>팀장은 <q>배포는 금요일에 하지 않는다</q>고 말했다.</p>

<figure>
  <blockquote cite="https://example.com/postmortem">
    <p>원인은 설정 파일의 들여쓰기 한 칸이었다.</p>
  </blockquote>
  <figcaption>— 장애 회고, <cite>결제 시스템 장애 보고서</cite></figcaption>
</figure>
```

`q`는 브라우저가 언어에 맞는 따옴표를 자동으로 붙인다. 그래서 `q` 안에 따옴표를 또 쓰면 두 번 찍힌다. `blockquote`의 `cite` 속성은 출처 주소를 담지만 화면에 보이지 않는다. 출처를 보여 주려면 `figcaption`처럼 눈에 보이는 글자로 따로 쓴다. 들여쓰기 효과를 내려고 `blockquote`를 쓰는 건 옛날 습관이다. 인용이 아니면 CSS의 `margin`이나 `padding`을 쓴다.

## 문단, 줄, 묶음

글을 묶는 기본 상자도 의미가 다르다.

- `p`: 문단. 생각 하나의 단위다. 빈 `p`를 줄 간격용으로 쓰면 스크린리더가 "빈 줄"을 읽는다.
- `br`: 줄바꿈이 내용의 일부일 때만. 시, 노래 가사, 주소처럼 줄이 의미를 갖는 곳이다. 문단 사이를 띄우려고 `br`을 두 번 쓰지 않는다.
- `hr`: 주제가 바뀌는 지점. 트리에 separator로 남는다. 장식 선이 필요하면 CSS `border`를 쓴다.
- `pre`: 공백과 줄바꿈을 그대로 보여 준다. 코드 블록은 `pre` 안에 `code`를 넣는다.
- `address`: 가장 가까운 `article`이나 문서 전체의 연락처. 아무 우편 주소에나 쓰는 태그가 아니다. 측정에서는 특별한 역할 없이 글자로 남았다.
- `div`와 `span`: 의미가 없는 묶음. `div`는 블록, `span`은 인라인이다. 스타일이나 스크립트를 걸 손잡이가 필요할 때 쓰고, 알맞은 의미 태그가 있으면 그걸 먼저 쓴다.

`pre`에는 파서 규칙이 하나 더 있다. 여는 태그 바로 뒤의 줄바꿈 하나는 버린다. 그래서 코드를 보기 좋게 다음 줄부터 써도 맨 위에 빈 줄이 생기지 않는다. Chromium에서 `textContent`를 확인했다.

```text
<pre>↵const a = 1;</pre>     → "const a = 1;"      (첫 줄바꿈 하나는 버림)
<pre>↵↵const b = 2;</pre>    → "\nconst b = 2;"    (두 번째부터는 남음)
```

`pre` 안이라도 태그는 태그로 읽힌다. `<pre><code>if (a<b) return;</code> 끝</pre>`을 넣고 `innerHTML`을 다시 읽으니 `<code>if (a<b) return;<="" code=""> 끝</b)></code>`가 나왔다. `<b)`부터가 이름이 `b)`인 요소로 읽혀 닫는 태그까지 삼킨 것이다. 코드 블록 안의 `<`와 `&`는 `&lt;`, `&amp;`로 바꿔 넣거나, 마크다운·하이라이터처럼 대신 바꿔 주는 도구를 거친다. 공백이 있는 `a < b`는 태그 시작으로 보지 않아 우연히 살아남는데, 이 우연에 기대지 않는다.

`p` 안에 `div`나 `ul`을 넣으면 파서가 `p`를 일찍 닫아 버린다는 함정은 [시맨틱 HTML](/posts/html-semantics)의 "파서는 틀린 HTML도 고쳐서 읽는다"에서 다뤘다.

## 목록 세 가지

목록은 개수와 위치를 알려 준다. 스크린리더는 목록에 들어가면 "목록, 항목 5개"라고 알려 주고, 항목마다 "5개 중 2번째"처럼 위치를 읽는다. 메뉴, 태그 묶음, 카드 묶음처럼 "여러 개가 나란히" 있으면 목록으로 만든다.

- `ul`: 순서 없는 목록. 순서를 바꿔도 뜻이 같다.
- `ol`: 순서 있는 목록. 레시피 단계, 순위처럼 순서가 뜻이다.
- `dl`: 이름과 설명의 짝. 용어집, 상품 사양("무게 / 1.2kg"), 메타데이터에 쓴다. `dt`가 이름, `dd`가 설명이고, 이름 하나에 설명 여러 개도 된다. 스타일을 위해 `dt`와 `dd` 묶음을 `div`로 감싸는 것도 허용된다.

`ol`에는 쓸모 있는 속성이 몇 개 있다.

```html
<ol start="3" reversed>   <!-- 3, 2, 1로 센다 -->
  <li>셋</li>
  <li>둘</li>
</ol>
<ol type="a">              <!-- a, b, c -->
  <li value="5">다섯 번째부터</li>   <!-- 이 항목부터 번호를 바꾼다 -->
</ol>
```

목록 안에 목록을 넣을 때는 하위 `ul`을 `li` 안에 둔다. `ul` 바로 아래에 `ul`을 넣으면 잘못된 구조다. 메뉴의 하위 메뉴가 이 모양이다.

```html
<ul>
  <li>프런트엔드
    <ul>
      <li>CSS</li>
      <li>HTML</li>
    </ul>
  </li>
</ul>
```

CSS 쪽에서는 `list-style`로 글머리표 모양(`disc`, `decimal`, `none`)과 위치(`inside`, `outside`)를 바꾸고, `::marker`로 글머리표 색과 글자를 바꾼다. 앞의 실험에서 Chromium은 `list-style: none`을 준 `ul`도 list로 남겼다. 사파리의 VoiceOver는 글머리표를 지운 목록을 목록으로 알리지 않는다. 메뉴처럼 목록이라는 사실이 중요하면 `role="list"`를 덧붙인다. 이 사파리 동작의 배경은 [시맨틱 HTML](/posts/html-semantics)에 있다.

```css
.tags { list-style: none; padding-inline-start: 0; }   /* 글머리표와 들여쓰기 제거 */
.steps li::marker { color: var(--accent); font-weight: 700; }
```

## 제목은 h1부터 차례로

`h1`부터 `h6`은 크기가 아니라 깊이다. 스크린리더 사용자는 제목만 골라 듣거나 `H` 키로 제목 사이를 뛰어다닌다. 그래서 `h2` 다음에 바로 `h4`가 나오면 "중간 단계를 놓쳤나" 하고 헤맨다. 크기가 마음에 안 들면 숫자를 건너뛰지 말고 CSS로 크기를 바꾼다. 카드 제목처럼 반복되는 제목은 그 영역의 깊이에 맞는 숫자를 고른다. 자세한 규칙은 [시맨틱 HTML](/posts/html-semantics)의 "제목 번호는 글자 크기가 아니다"에 있다.

## 링크와 버튼, 그리고 새 창

기준은 하나다. 주소가 바뀌면 `a`, 이 페이지에서 무언가를 하면 `button`이다. `a`는 `href`가 있어야 링크가 되고, 그래야 Tab으로 갈 수 있고 새 탭으로 열 수 있고 주소를 복사할 수 있다. `href` 없는 `a`에 클릭 핸들러를 다는 순간 키보드 사용자는 그 요소에 갈 수 없다. 이 구분은 [시맨틱 HTML](/posts/html-semantics)에 자세히 있으니, 여기서는 링크 태그에 붙는 속성을 본다.

아래 그림에서 조각을 하나씩 눌러 보면 각 속성이 무슨 일을 하는지 나온다.

`target="_blank"`의 위험은 탭내빙(tabnabbing)이라고 불린다. 새로 열린 페이지가 `window.opener.location`을 바꿔 원래 탭을 가짜 로그인 화면으로 몰래 바꿔치기하는 공격이다. 지금 브라우저는 이 위험을 기본으로 막는다. Chromium 141에서 새 탭의 `window.opener`를 확인했다.

```text
target="_blank"                       opener === null → true   (기본으로 막힘)
target="_blank" rel="opener"          opener === null → false  (일부러 열면 열린다)
target="_blank" rel="noreferrer"      opener === null → true,  Referer 헤더 없음
```

크롬 88, 파이어폭스 79, 사파리 12.1부터 `target="_blank"`는 `noopener`를 기본으로 갖는다. 그래도 `rel="noopener"`를 적는 습관은 남겨 둔다. 오래된 브라우저나 웹뷰가 있고, 린트 규칙(예: `react/jsx-no-target-blank`)도 이걸 확인한다. 둘 다 적는 `noopener noreferrer`는 Referer까지 지워서 도착한 쪽 분석 도구에서 유입 경로가 사라진다는 점을 알고 고른다. 사용자가 쓴 링크를 그대로 출력하는 곳의 보안은 [XSS](/posts/xss)에서 이어진다.

## 파서가 글자를 읽는 규칙

HTML 원문에 적은 글자가 그대로 화면에 나오지는 않는다. 파서와 CSS가 중간에 몇 가지를 바꾼다.

먼저 공백이다. 여러 칸 띄운 공백, 탭, 줄바꿈은 기본값(`white-space: normal`)에서 공백 한 칸으로 줄어들고, 줄의 시작과 끝 공백은 지워진다. 아래 그림은 `  여러↵   칸`이 화면 글자로 바뀌는 과정이다.

Chromium에서 같은 문단의 `textContent`와 `innerText`를 비교하면 차이가 보인다. `textContent`는 DOM에 있는 원문 그대로, `innerText`는 화면에 그려진 대로다.

```text
textContent  "|   여러   칸\n줄바꿈"
innerText    "| 여러 칸 줄바꿈"
```

그래서 공백 접힘은 데이터의 문제가 아니라 표시의 문제다. 사용자가 입력한 여러 줄 메모를 그대로 보여 주고 싶으면 `br`로 바꾸지 말고 CSS `white-space: pre-wrap`을 준다. 반대로 서버에서 받은 글의 공백 개수를 화면 글자 수로 세면 틀린다.

규칙을 함수로 옮겨 보자. 블록 하나의 글자를 받아 `white-space: normal`에서 보일 글자로 바꾼다. 줄바꿈 처리의 언어별 차이와 인라인 요소 경계는 빼고 단순하게 본다. 줄바꿈 없는 공백(`&nbsp;`, U+00A0)은 접히지 않는다.

<CodePlayground

다음은 문자 참조(엔티티)다. `&lt;`, `&gt;`, `&amp;`, `&quot;`처럼 `&`로 시작해 `;`로 끝나는 말은 글자 하나로 바뀐다. 화면에 `<`를 보여 주려면 `&lt;`를 쓴다. 숫자로 `&#44032;`(가)나 `&#x1F600;`(😀)처럼 쓸 수도 있다. UTF-8로 저장한 문서라면 한글과 이모지는 그대로 쓰면 되고, 꼭 바꿔야 하는 건 `<`와 `&`, 속성 값 안의 따옴표 정도다.

세미콜론을 빼먹으면 생기는 일이 있다. 같은 Chromium에서 확인했다.

```html
<p>&copy 2025 &notit; &nbsp;|</p>
```

```text
"© 2025 ¬it;  |"
```

`&copy`는 세미콜론이 없어도 ©가 됐다. 오래된 문서와의 호환 때문에 일부 이름은 세미콜론 없이도 인정한다. 그런데 `&notit;`는 정의된 이름이 아닌데도 앞부분 `&not`이 ¬로 바뀌어 "¬it;"가 됐다. 명세의 예제로도 나오는 동작이다.

이 규칙은 주소를 속성에 그대로 붙여 넣을 때 사고를 낸다. 속성 값 안에서는 세미콜론 없는 이름 뒤에 `=`나 영문·숫자가 오면 바꾸지 않는다는 예외가 있지만, 밑줄 같은 다른 글자가 오면 바꾼다. Chromium에서 `getAttribute("href")`로 확인했다.

```text
href="/s?a=1&copy=1"            → /s?a=1&copy=1          (= 앞이라 그대로)
href="/s?x=1&lang=ko&reg_id=3"  → /s?x=1&lang=ko®_id=3   (&reg가 ®로 바뀜)
```

`reg_id`라는 쿼리 이름 하나 때문에 서버는 `reg_id` 파라미터를 받지 못한다. 그래서 속성 값 안의 `&`도 `&amp;`로 쓴다. React의 JSX는 문자열을 자동으로 이스케이프하니 이 걱정이 적지만, `dangerouslySetInnerHTML`로 넣는 HTML은 이 규칙을 그대로 따른다.

`&nbsp;`는 줄바꿈 없는 공백이다. 접히지 않고 그 자리에서 줄이 바뀌지 않는다. "10 km"의 숫자와 단위처럼 떨어지면 안 되는 두 말 사이에 쓴다. 여백을 만들려고 `&nbsp;`를 여러 개 쓰는 건 CSS로 할 일이다.

태그와 속성 이름은 대소문자를 가리지 않는다. `<P ID=x>`로 써도 DOM에는 `p` 요소와 `id` 속성이 생긴다(`tagName`은 HTML 문서에서 대문자 `P`로 돌려준다). 속성 값은 다르다. 표준 모드에서 `class="Card"`와 `.card` 선택자는 맞지 않는다. 쿼크 모드에서는 클래스와 id가 대소문자를 무시해서, DOCTYPE이 빠진 페이지에서만 스타일이 먹는 버그가 생기기도 한다. HTML 안에 넣은 SVG에서는 `viewBox`처럼 대소문자가 섞인 이름을 파서가 알아서 맞춰 준다.

주석 `<!-- -->`은 화면에 안 보일 뿐 DOM에 Comment 노드로 남고, 페이지 소스로 누구나 볼 수 있다. 측정에서도 `body`의 마지막 자식이 nodeType 8(주석)이었다. 내부 주소나 TODO 메모를 HTML 주석에 남기지 않는다. 빌드 도구가 지워 주는지 배포본에서 확인한다.

## 태그가 맞게 들어갔는지 확인하는 법

손으로 마크업을 읽는 것보다 접근성 트리를 보는 편이 빠르다. 크롬 개발자 도구의 Elements → Accessibility 탭에서 고른 요소의 역할과 이름을 확인한다. 테스트로 남기고 싶으면 Playwright의 `ariaSnapshot()`이 이 글에서 쓴 것과 같은 트리를 문자열로 준다.

```ts
// Playwright: 문단의 접근성 트리를 스냅숏으로 고정해 둔다
await expect(page.locator("article")).toMatchAriaSnapshot(`
  - paragraph:
    - text: 배송은
    - strong: 영업일 기준 3일
`);
```

리뷰할 때 자주 걸리는 실수는 이렇다.

- 디자인상 굵기를 위해 `strong`을 쓰거나, 정말 중요한 경고를 `b`나 `span`과 CSS로만 만든다. 경고는 `strong`, 단순 굵기는 CSS다.
- 인용이 아닌 들여쓰기에 `blockquote`, 여백에 `br` 여러 개, 장식 선에 `hr`을 쓴다.
- 취소선(`s`, `del`)이나 `mark`의 색만으로 정보를 전달한다. 색과 선은 보지 못하는 사람에게 전달되지 않으니 글자로도 적는다.
- `abbr`의 `title`에 풀어 쓴 말을 숨겨 두고 본문에는 안 쓴다.
- 메뉴를 `div` 나열로 만든다. 목록으로 만들면 개수가 전달되고, 사파리에서는 `role="list"`까지 챙긴다.
- `target="_blank"` 링크에 새 창 안내를 빼먹는다.

이 실수들은 모두 "보이는 모양"과 "전달되는 의미"를 한 태그로 해결하려다 생긴다. 모양은 CSS가, 의미는 태그가 맡는다는 원칙 하나로 대부분 정리된다. 페이지 전체의 구조와 접근성 기준은 [시맨틱 HTML](/posts/html-semantics)과 [웹 접근성 기초](/posts/web-accessibility)로, 영상이나 다른 페이지를 문서에 넣는 태그는 [video, audio, iframe](/posts/html-media-embed)으로 이어진다.

## 면접에서 나올 만한 질문

### strong과 b는 무엇이 다른가요?

`strong`은 내용이 중요하거나 급하다는 의미를, `b`는 의미 없이 눈길을 끌게 하는 관례적 표시를 뜻한다. 화면에서는 둘 다 굵지만 Chromium 접근성 트리에서 `strong`은 strong 노드로 남고 `b`는 평범한 글자로 합쳐진다. 그래서 경고에는 `strong`을, 꾸밈뿐인 굵기에는 CSS `font-weight`를 쓴다.

### 스크린리더는 strong을 다르게 읽나요? 그런데도 구분하는 이유는요?

대부분의 스크린리더는 기본 설정에서 강조를 목소리로 구분하지 않고, 사용자가 서식 알림을 켜야 드러난다. 그래도 의미가 HTML에 남아 있어야 읽기 모드, 번역기, 테스트 도구, 나중의 디자인 변경이 그 의미를 쓸 수 있다. 모양과 의미를 한 태그에 섞으면 디자인을 바꿀 때 중요 표시까지 사라진다.

### del과 s는 언제 각각 쓰나요?

`del`은 문서를 고친 기록으로 지운 내용이고, `ins`와 짝을 이루며 `datetime`, `cite`를 붙일 수 있다. `s`는 더 이상 맞지 않는 내용, 예를 들어 지난 가격이나 끝난 이벤트를 표시한다. 둘 다 취소선은 시각 표시라 보지 못하는 사람에게 잘 전달되지 않으니, 중요한 정보는 글자로도 적는다.

### ul, ol, dl은 어떻게 고르나요?

순서를 바꿔도 뜻이 같으면 `ul`, 순서 자체가 뜻이면 `ol`, 이름과 설명의 짝이면 `dl`이다. 목록으로 만들면 스크린리더가 항목 수와 현재 위치를 알려 준다. 하위 목록은 `li` 안에 넣고, `ol`은 `start`, `reversed`, `type`, `li`의 `value`로 번호를 조절한다.

### list-style: none을 주면 무엇을 확인해야 하나요?

사파리 VoiceOver는 글머리표를 지운 목록을 목록으로 알리지 않는다. Chromium은 그대로 list로 남기니 크롬에서만 확인하면 놓친다. 메뉴처럼 목록이라는 사실이 중요하면 `role="list"`를 붙인다.

### target="_blank"에 rel="noopener"가 아직 필요한가요?

크롬 88, 파이어폭스 79, 사파리 12.1부터 `target="_blank"`는 기본으로 noopener처럼 동작해서 새 탭의 `window.opener`가 null이다. 그래도 오래된 브라우저와 웹뷰, 린트 규칙 때문에 적어 두는 편이 안전하다. `noreferrer`는 Referer 헤더까지 지우니 도착한 사이트의 유입 분석에 영향을 준다는 점을 알고 고른다.

### HTML에서 여러 칸 띄운 공백이 한 칸으로 보이는 이유와 원문대로 보이게 하는 방법은요?

CSS `white-space`의 기본값 `normal`이 이어진 공백·탭·줄바꿈을 한 칸으로 접고 줄 앞뒤 공백을 지우기 때문이다. DOM의 `textContent`에는 원문이 그대로 있고 화면과 `innerText`만 달라진다. 사용자가 입력한 여러 줄 글은 `white-space: pre-wrap`으로 보여 주고, 떨어지면 안 되는 두 말 사이는 `&nbsp;`를 쓴다.

### 문자 참조에서 세미콜론을 빼면 어떻게 되나요?

일부 오래된 이름은 세미콜론 없이도 인정돼서 `&copy`가 ©가 된다. 문제는 정의되지 않은 이름의 앞부분이 맞는 경우로, `&notit;`가 "¬it;"로 바뀐다. 그래서 주소의 쿼리 문자열처럼 `&`가 들어간 속성 값은 `&amp;`로 쓰고, 문자 참조에는 항상 세미콜론을 붙인다.
