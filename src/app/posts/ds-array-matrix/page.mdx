<EasyIntro>
  큰 격자의 숫자를 전부 더하는 코드가 있다. 덧셈 횟수는 똑같은데 가로줄 순서로 더하느냐 세로줄 순서로 더하느냐만 바꿨더니 걸리는 시간이 네 배에서 여덟 배까지 차이가 났다. 이 차이는 배열이 메모리에 어떻게 놓여 있는지를 알아야 설명된다.

  배열은 같은 크기의 칸을 메모리에 빈틈없이 이어 붙인 구조다. 그래서 시작 위치만 알면 몇 번째 칸이든 계산 한 번으로 바로 찾아가지만, 중간에 하나를 끼워 넣으려면 뒤의 칸을 전부 한 칸씩 밀어야 한다. 격자도 메모리에서는 가로줄을 차례로 이어 붙인 한 줄이라서, 그 순서대로 읽으면 컴퓨터가 한 번에 가져온 이웃 칸을 그대로 쓰고 세로로 읽으면 매번 멀리 건너뛰어야 한다.

  이 글은 그 성질에서 출발해 배열 문제에 자주 쓰는 풀이법도 함께 본다. 양 끝에서 좁혀 오기, 창을 밀면서 세기, 합을 미리 더해 두기, 행렬을 제자리에서 돌리기다.
</EasyIntro>

2048 × 2048 격자의 값을 모두 더하는 코드가 있다. 값은 전부 1이라 답은 4,194,304로 똑같다. 그런데 바깥 반복문을 행으로 도느냐 열로 도느냐만 바꿨더니 걸리는 시간이 이렇게 달라졌다.

```js
// matrix.js (Node 22)
const N = 2048;
const flat = new Float64Array(N * N).fill(1);                         // 한 줄로 이어 붙인 행렬
const nested = Array.from({ length: N }, () => new Array(N).fill(1)); // 배열의 배열

function time(name, fn) {
  fn(); // 한 번 데워 둔다
  const t = performance.now();
  let s = 0;
  for (let k = 0; k < 5; k++) s += fn();
  console.log(name.padEnd(22), ((performance.now() - t) / 5).toFixed(1) + "ms", s / 5);
}
time("flat 행 순서", () => { let s = 0; for (let r = 0; r < N; r++) for (let c = 0; c < N; c++) s += flat[r * N + c]; return s; });
time("flat 열 순서", () => { let s = 0; for (let c = 0; c < N; c++) for (let r = 0; r < N; r++) s += flat[r * N + c]; return s; });
time("nested 행 순서", () => { let s = 0; for (let r = 0; r < N; r++) { const row = nested[r]; for (let c = 0; c < N; c++) s += row[c]; } return s; });
time("nested 열 순서", () => { let s = 0; for (let c = 0; c < N; c++) for (let r = 0; r < N; r++) s += nested[r][c]; return s; });
```

```text
flat 행 순서              7.2ms 4194304
flat 열 순서              26.5ms 4194304
nested 행 순서            7.6ms 4194304
nested 열 순서            57.9ms 4194304
```

이 글의 시간은 모두 이 글을 쓴 머신(Intel Xeon 2.8GHz 4코어, L1d 32KB/코어, L2 1MB/코어, Node 22.22)에서 잰 값이다. 절대값은 머신마다 다르고, 볼 것은 비율이다. 덧셈 횟수는 같은데 열 순서가 네 배에서 여덟 배 느리다. Big O로는 둘 다 O(N²)라서 이 차이가 설명되지 않는다. 배열이 메모리에 어떻게 놓여 있는지를 알아야 설명된다.

이 글은 자료구조 시리즈의 첫 글로, 배열과 2차원 배열(행렬)을 다룬다. 메모리 배치에서 연산 비용이 어떻게 나오는지 보고, V8이 자바스크립트 배열을 실제로 어떻게 들고 있는지 확인한 다음, 배열 문제에서 반복해서 쓰는 두 포인터, 슬라이딩 윈도, 누적 합, 행렬 회전을 차례로 푼다. 같은 시리즈의 [연결 리스트](/posts/ds-linked-list)와 [스택, 큐, 덱](/posts/ds-stack-queue-deque)은 배열의 약점을 다른 방식으로 메우는 구조라 이어서 읽으면 좋다.

## 칸이 붙어 있어서 인덱스가 공짜다

배열은 같은 크기의 칸을 메모리에 빈틈없이 이어 붙인 구조다. 시작 주소만 알면 i번째 칸의 주소는 `시작 주소 + i × 칸 크기`로 바로 나온다. 덧셈과 곱셈 한 번이라 배열 길이가 10이든 1억이든 `a[i]`는 O(1)이다. 이것을 임의 접근(random access)이라고 부른다.

대신 중간에 끼워 넣거나 빼는 건 비싸다. 칸이 붙어 있어야 하니 넣을 자리 뒤의 원소를 전부 한 칸씩 밀어야 한다. 아래 그림에서 `[A, B, C, D]`의 1번 자리에 X를 넣는 과정을 따라가 보자.

뒤에서부터 미는 이유는 앞에서부터 밀면 아직 옮기지 않은 값을 덮어쓰기 때문이다. 넣는 위치가 앞일수록 옮길 원소가 많아서, 맨 앞에 넣거나 빼는 `unshift`와 `shift`가 가장 비싸다. 길이가 n이면 최악 O(n)이다. 맨 끝에 붙이는 `push`와 `pop`만 아무것도 옮기지 않는다.

| 연산 | 비용 | 이유 |
|---|---|---|
| `a[i]` 읽기·쓰기 | O(1) | 주소를 계산 한 번으로 구한다 |
| `push`, `pop` | 분할 상환 O(1) | 끝에서만 일어나고, 가끔 용량을 늘린다 |
| `unshift`, `shift`, 중간 `splice` | O(n) | 뒤쪽 원소를 전부 민다 |
| 값으로 찾기 `indexOf`, `includes` | O(n) | 정렬돼 있지 않으면 처음부터 훑는다 |
| 정렬된 배열에서 이진 탐색 | O(log n) | 반씩 버린다 |

`shift`를 반복하는 큐가 얼마나 느려지는지는 [배열을 고치는 메서드 글](/posts/js-array-mutation)에서 10만 개로 쟀다. 큐를 제대로 만드는 법은 [스택, 큐, 덱](/posts/ds-stack-queue-deque)에서 다룬다.

## 자리가 모자라면 더 큰 방으로 옮긴다

자바스크립트 배열은 길이를 정하지 않고 계속 `push`할 수 있다. 실제로는 길이보다 넉넉한 용량(capacity)을 잡아 두고, 다 차면 더 큰 메모리를 새로 잡아 원소를 옮긴다. 이런 배열을 동적 배열이라고 한다. 왜 가끔 전부 옮기는데도 `push`가 평균 O(1)인지는 [Big O 글의 분할 상환 설명](/posts/big-o-notation)에 그림과 함께 있다. 여기서는 V8이 실제로 용량을 얼마씩 늘리는지 직접 본다.

V8에는 디버깅용 내장 함수 `%DebugPrint`가 있다. `--allow-natives-syntax` 플래그를 주면 쓸 수 있고, 배열의 원소 저장소(`FixedArray`)의 크기가 찍힌다. 그 크기가 바로 용량이다. `push`할 때마다 찍어 보고 용량이 바뀌는 순간만 골라냈다.

```js
// capacity.js: push할 때마다 V8 내부 용량(FixedArray 크기)을 읽는다
const { execFileSync } = require("node:child_process");
const child = `
const a = [];
for (let i = 0; i < 1000; i++) { a.push(i); %DebugPrint(a); }
`;
const out = execFileSync(process.execPath, ["--allow-natives-syntax", "-e", child], { encoding: "utf8", maxBuffer: 1 << 28 });
let prev = 0;
for (const block of out.split("DebugPrint:").slice(1)) {
  const len = Number(block.match(/- length: (\d+)/)[1]);
  const cap = Number(block.match(/<FixedArray\[(\d+)\]>/)[1]);
  if (cap !== prev) {
    console.log(`length ${String(len).padStart(4)} -> capacity ${String(cap).padStart(4)}` + (prev ? `  (${len - 1}개 복사)` : ""));
    prev = cap;
  }
}
```

```text
length    1 -> capacity   17
length   18 -> capacity   43  (17개 복사)
length   44 -> capacity   82  (43개 복사)
length   83 -> capacity  140  (82개 복사)
length  141 -> capacity  227  (140개 복사)
length  228 -> capacity  358  (227개 복사)
length  359 -> capacity  554  (358개 복사)
length  555 -> capacity  848  (554개 복사)
length  849 -> capacity 1289  (848개 복사)
```

빈 배열에 처음 넣으면 17칸을 잡는다. 18번째에서 43칸이 된다. 숫자를 맞춰 보면 새 용량은 `새 길이 + 새 길이/2 + 16`이다(18 + 9 + 16 = 43, 44 + 22 + 16 = 82). 대략 1.5배에 16을 더하는 규칙이다. 1.5배처럼 비율로 늘리면 옮기는 횟수의 합이 n에 비례해서 분할 상환 O(1)이 지켜진다. 이 규칙은 V8 소스의 상수라 버전이 바뀌면 달라질 수 있다. Node 22 기준으로 확인한 값이다.

`%DebugPrint`의 출력 형식은 공식 API가 아니다. 학습과 디버깅에만 쓰고 운영 코드에는 넣지 않는다.

## 자바스크립트 배열은 속이 여러 가지다

C의 배열은 칸 크기가 정해져 있다. 자바스크립트 배열에는 숫자, 문자열, 객체가 섞여 들어갈 수 있는데 어떻게 칸 크기를 정할까. V8은 배열마다 원소 종류(elements kind)를 기록해 두고, 들어온 값에 맞춰 저장 방식을 고른다.

```js
// kinds.js: node --allow-natives-syntax kinds.js
const kind = (a) => {
  if (%HasDictionaryElements(a)) return "DICTIONARY";
  const holey = %HasHoleyElements(a) ? "HOLEY_" : "PACKED_";
  if (%HasSmiElements(a)) return holey + "SMI";
  if (%HasDoubleElements(a)) return holey + "DOUBLE";
  return holey + "ELEMENTS";
};
const a = [1, 2, 3];
console.log("[1, 2, 3]       ", kind(a));
a.push(4.5);
console.log("push(4.5)       ", kind(a));
a.push("x");
console.log('push("x")       ', kind(a));
a.pop(); a.pop();
console.log("pop() 두 번      ", kind(a));
const b = [1, 2, 3];
b[10] = 4;
console.log("b[10] = 4       ", kind(b));
console.log("new Array(3)    ", kind(new Array(3)));
const c = [1, 2, 3];
c[1_000_000] = 4;
console.log("c[1_000_000] = 4", kind(c));
```

```text
[1, 2, 3]        PACKED_SMI
push(4.5)        PACKED_DOUBLE
push("x")        PACKED_ELEMENTS
pop() 두 번       PACKED_ELEMENTS
b[10] = 4        HOLEY_SMI
new Array(3)     HOLEY_SMI
c[1_000_000] = 4 DICTIONARY
```

SMI는 작은 정수(small integer)다. 정수만 있으면 칸에 정수를 바로 담는다. 소수가 하나 들어오면 64비트 실수 칸(DOUBLE)으로 바꾸고, 문자열이 들어오면 아무 값이나 가리키는 포인터 칸(ELEMENTS)으로 바꾼다. 출력의 네 번째 줄이 눈여겨볼 곳이다. 문자열과 소수를 `pop`으로 다 뺐는데도 PACKED_ELEMENTS 그대로다. 아래 그림처럼 종류는 한 방향으로만 바뀌고 되돌아오지 않는다.

HOLEY는 중간에 빈 칸(hole)이 있다는 뜻이다. `b[10] = 4`처럼 길이를 건너뛰어 쓰거나 `new Array(3)`처럼 길이만 정하면 생긴다. 빈 칸을 읽으면 명세상 프로토타입 체인까지 찾아봐야 해서, 엔진은 HOLEY 배열을 읽을 때 확인을 한 단계 더 한다. 더 나쁜 건 DICTIONARY다. `c[1_000_000] = 4`처럼 너무 듬성듬성하면 100만 칸을 잡는 대신 인덱스를 키로 쓰는 해시 테이블로 바꾼다. 메모리는 아끼지만 칸을 이어 붙인 배열의 장점이 사라진다.

실무에서 이 차이가 크게 드러나는 경우는 많지 않다. 뜨거운 반복문에서 같은 배열을 수백만 번 읽을 때나 의미가 있다. 다만 습관은 들일 만하다. 배열에 한 종류의 값만 넣고, 길이를 건너뛰어 쓰지 않고, `delete arr[i]`로 구멍을 내지 않는다(`delete`는 길이를 줄이지 않고 그 칸을 빈 칸으로 만든다).

## 미리 자리를 잡으면 빨라질까

용량이 늘 때마다 옮기는 비용이 있으니, 크기를 알면 처음부터 자리를 잡는 게 낫다는 말이 있다. 1천만 개로 쟀다.

```js
// push.js
const N = 10_000_000;
function bench(name, fn) {
  const t = performance.now();
  const a = fn();
  console.log(name.padEnd(18), (performance.now() - t).toFixed(1) + "ms", a.length);
}
bench("[] + push", () => { const a = []; for (let i = 0; i < N; i++) a.push(i); return a; });
bench("new Array(N)", () => { const a = new Array(N); for (let i = 0; i < N; i++) a[i] = i; return a; });
bench("Int32Array(N)", () => { const a = new Int32Array(N); for (let i = 0; i < N; i++) a[i] = i; return a; });
```

```text
[] + push          358.3ms 10000000
new Array(N)       98.9ms 10000000
Int32Array(N)      41.0ms 10000000
```

이 크기에서는 미리 잡은 쪽이 서너 배 빨랐다. 그런데 `new Array(N)`로 만든 배열은 다 채운 뒤에도 HOLEY_SMI로 남는다(앞에서 본 대로 종류는 되돌아가지 않는다). 쓰는 비용은 아꼈지만 이후 읽을 때마다 빈 칸 확인을 한다. 숫자만 다루고 길이가 고정이면 `Int32Array`, `Float64Array` 같은 타입 배열이 가장 빠르다. 칸 크기가 고정이고 빈 칸이라는 개념이 없어서다. 대신 길이를 늘릴 수 없고 숫자 말고는 담을 수 없다. 원소가 수천 개 수준이면 셋의 차이는 측정 오차에 묻히니 읽기 쉬운 `push`나 `map`을 쓰면 된다.

## 양 끝에서 좁혀 오는 두 포인터

여기부터는 배열 문제를 푸는 기법이다. 처음은 두 포인터다. 정렬된 배열 `[1, 3, 4, 6, 8, 11]`에서 합이 10인 두 수를 찾는다고 하자. 모든 쌍을 보면 O(n²)이다. 정렬돼 있다는 사실을 쓰면 왼쪽 끝과 오른쪽 끝에서 하나씩 좁혀 오며 O(n)에 끝난다.

```js
function pairSum(sorted, target) {
  let l = 0, r = sorted.length - 1;
  while (l < r) {
    const s = sorted[l] + sorted[r];
    if (s === target) return [l, r];
    if (s < target) l++; // 합이 작다 → 작은 쪽을 키운다
    else r--;            // 합이 크다 → 큰 쪽을 줄인다
  }
  return null;
}
console.log(pairSum([1, 3, 4, 6, 8, 11], 10));
```

```text
[ 2, 3 ]
```

포인터를 움직이는 근거가 중요하다. 합이 크면 오른쪽 값은 남은 수 중 가장 작은 왼쪽 값과 더해도 크니, 그 값이 들어가는 쌍은 전부 답이 아니다. 한 번 비교로 쌍 여러 개를 한꺼번에 버리는 셈이다. 그래서 이 기법은 "한쪽을 움직이면 합이 한 방향으로만 바뀐다"는 단조성이 있어야 쓸 수 있다. 정렬되지 않은 배열이면 먼저 정렬하거나(O(n log n)), 해시맵으로 본 값을 기억하는 방법([해시맵](/posts/ds-hash-map))을 쓴다. 원래 인덱스를 돌려줘야 하는 Two Sum이라면 정렬하면 인덱스가 섞이니 해시맵 쪽이 맞다.

같은 방향으로 가는 두 포인터도 있다. 정렬된 배열에서 중복을 제자리에서 지우는 문제는 읽는 포인터가 앞서 가고, 쓰는 포인터가 새 값이 나올 때만 한 칸 전진한다. 문자열 뒤집기, 회문 확인은 양 끝 포인터의 변형이다.

## 창을 밀면서 세기

`"abcabcbb"`에서 같은 문자가 두 번 나오지 않는 가장 긴 연속 구간의 길이를 구하는 문제다. 모든 구간을 보면 O(n²) 개의 구간을 각각 확인해야 한다. 슬라이딩 윈도는 왼쪽 끝과 오른쪽 끝으로 창을 정의하고, 오른쪽을 한 칸씩 늘리다가 조건이 깨지면 왼쪽을 당긴다. 두 끝이 모두 앞으로만 가니 전체가 O(n)이다.

```js
function lengthOfLongestSubstring(s) {
  const last = new Map(); // 문자 → 마지막으로 본 위치
  let left = 0, best = 0;
  for (let right = 0; right < s.length; right++) {
    const ch = s[right];
    if (last.has(ch) && last.get(ch) >= left) left = last.get(ch) + 1;
    last.set(ch, right);
    best = Math.max(best, right - left + 1);
  }
  return best;
}
console.log(lengthOfLongestSubstring("abcabcbb"), lengthOfLongestSubstring("pwwkew"), lengthOfLongestSubstring(""));
```

## 미리 더해 두면 구간 합이 뺄셈 한 번

일별 매출 배열이 있고, "i일부터 j일까지 합"을 묻는 요청이 수없이 들어온다고 하자. 요청마다 더하면 한 번에 O(n)이다. 누적 합(prefix sum) 배열을 한 번 만들어 두면 구간 합은 뺄셈 한 번이다. `prefix[k]`는 앞에서 k개를 더한 값으로 정의하고, 맨 앞에 0을 하나 둔다.

```js
const sales = [3, 1, 4, 1, 5, 9, 2];
const prefix = [0];
for (const x of sales) prefix.push(prefix.at(-1) + x);
console.log(prefix);
const rangeSum = (i, j) => prefix[j + 1] - prefix[i]; // sales[i..j]
console.log(rangeSum(2, 5));
```

맨 앞의 0 덕분에 "0일부터"를 따로 처리하지 않아도 된다. 이 0을 빼고 만들면 `rangeSum(0, j)`에서 `prefix[-1]`을 읽는 경계 실수가 나온다. 자바스크립트는 `prefix[-1]`에 에러를 내지 않고 `undefined`를 돌려줘서 결과가 조용히 `NaN`이 된다.

누적 합이 빛나는 문제는 "합이 k인 연속 구간의 개수"다. 구간 [i..j]의 합은 `prefix[j+1] − prefix[i]`이므로, 지금까지의 합이 `sum`일 때 이전에 `sum − k`였던 적이 몇 번 있는지만 세면 된다. 그 횟수를 해시맵에 기억한다.

```js
function subarraySum(nums, k) {
  const seen = new Map([[0, 1]]); // 누적 합 → 나온 횟수 (빈 접두사의 0을 미리 넣는다)
  let sum = 0, count = 0;
  for (const x of nums) {
    sum += x;
    count += seen.get(sum - k) ?? 0;
    seen.set(sum, (seen.get(sum) ?? 0) + 1);
  }
  return count;
}
console.log(subarraySum([1, 2, 3, -2, 2], 3));
```

```text
4
```

[1, 2], [3], [2, 3, −2], [3, −2, 2] 네 개다. 이 배열에는 음수가 있어서 슬라이딩 윈도로는 못 푼다. 창을 늘리면 합이 커지고 줄이면 작아진다는 단조성이 음수 때문에 깨지기 때문이다. 원소가 모두 양수일 때만 슬라이딩 윈도를 쓰고, 음수가 섞이면 누적 합과 해시맵으로 간다. 면접에서 "슬라이딩 윈도로 풀면 안 되나요?"라는 꼬리 질문이 바로 여기서 나온다.

2차원으로 넓히면 `P[r][c]`에 왼쪽 위 직사각형의 합을 담는다. 임의의 직사각형 합은 네 값을 더하고 빼서 O(1)에 나온다. 이미지 처리에서는 같은 것을 적분 영상(integral image)이라고 부른다. 단점도 분명하다. 원본 값이 하나 바뀌면 그 뒤의 누적 합을 전부 다시 계산해야 해서 갱신이 O(n)이다. 갱신과 질의가 섞여 들어오면 펜윅 트리나 세그먼트 트리로 넘어간다.

## 2차원도 메모리에서는 한 줄이다

CPU는 메모리를 한 칸씩 가져오지 않고 64바이트짜리 캐시 라인 단위로 가져온다. `Float64Array`라면 한 번에 값 8개가 캐시에 올라온다. 행 순서로 돌면 한 번 가져온 8개를 다 쓰고 다음 줄로 간다. 하드웨어 프리페처도 순서대로 읽는 패턴을 알아채고 다음 줄을 미리 가져온다. 열 순서로 돌면 2048칸(16KB)씩 건너뛰니 가져온 줄에서 한 개만 쓰고 버린다. 2048행을 다 돌고 다음 열로 돌아왔을 때는 그 줄이 이미 캐시에서 밀려나 있다. 덧셈 횟수가 같아도 메모리를 기다리는 시간이 다르다. 이것을 공간 지역성(spatial locality)이라고 한다.

배열의 배열(`nested`)에서 열 순서가 더 느린 건 한 단계가 더 있어서다. `nested[r]`은 행 배열을 가리키는 포인터이고, 각 행은 힙의 서로 다른 곳에 따로 있다. 열 순서로 돌면 매번 다른 행 객체를 찾아가야 한다. 행 순서에서는 `const row = nested[r]`로 행을 한 번만 꺼내 두니 flat과 거의 같은 속도가 나왔다.

현장에서 이게 드러나는 곳은 이미지 픽셀 처리(`ImageData.data`는 행 우선으로 편 RGBA 배열이다), 게임 격자, 큰 행렬 연산, 그리고 데이터베이스다. 행 단위로 저장하는 DB와 열 단위로 저장하는 분석용 DB가 갈리는 이유도 같은 원리다. 집계 쿼리는 한 열을 끝까지 읽으니 열이 붙어 있는 쪽이 유리하다.

## 행렬을 제자리에서 돌리기

n × n 행렬을 시계 방향으로 90도 돌리는 문제는 면접 단골이다. 새 행렬을 만들면 `결과[c][n−1−r] = 원본[r][c]`로 간단하지만, 보통 추가 메모리 없이 제자리에서 하라는 조건이 붙는다. 대각선 기준으로 뒤집고(전치), 각 행을 좌우로 뒤집으면 된다.

```js
function rotate(m) {
  const n = m.length;
  // 1) 전치: 대각선 위쪽 칸만 돌며 (i, j)와 (j, i)를 바꾼다
  for (let i = 0; i < n; i++)
    for (let j = i + 1; j < n; j++) [m[i][j], m[j][i]] = [m[j][i], m[i][j]];
  // 2) 행마다 좌우로 뒤집는다
  for (const row of m) row.reverse();
  return m;
}
console.log(rotate([[1, 2, 3], [4, 5, 6], [7, 8, 9]]));
```

  ]}
/>

전치에서 `j`를 `i + 1`부터 시작하는 게 요점이다. `j`를 0부터 돌리면 (0,1)과 (1,0)을 한 번 바꾸고 나중에 (1,0)과 (0,1)을 또 바꿔서 원래대로 돌아온다. 반시계 방향은 전치 후 행 순서를 뒤집거나(위아래), 행마다 뒤집은 뒤 전치한다. 정사각형이 아니면 제자리 회전이 안 되니 새 배열을 만든다. 나선형 순회(spiral order)도 자주 나오는데, 위·오른쪽·아래·왼쪽 경계 네 개를 두고 한 변을 돌 때마다 그 경계를 한 칸 안으로 당기는 방식으로 푼다. 경계가 교차하는 순간 멈추는 조건이 버그가 잘 나는 곳이다.

## 배열 코드에서 반복해서 나오는 실수

격자를 만들 때 가장 흔한 실수는 `fill`에 배열을 넘기는 것이다.

```js
const grid = Array(3).fill([]);
grid[0].push("x");
console.log(grid);

const ok = Array.from({ length: 3 }, () => []);
ok[0].push("x");
console.log(ok);
```

```text
[ [ 'x' ], [ 'x' ], [ 'x' ] ]
[ [ 'x' ], [], [] ]
```

`fill`은 값을 하나 받아 모든 칸에 그 값을 넣는다. 배열은 참조라서 세 칸이 같은 배열 하나를 가리킨다([원시값과 참조](/posts/js-primitive-vs-reference)). 행마다 새 배열을 만들려면 `Array.from`의 콜백에서 만든다. BFS 방문 표시용 격자, DP 테이블에서 이 실수가 나면 한 칸을 고쳤는데 같은 열 전체가 바뀌는 증상으로 보인다.

두 번째는 앞에서부터 돌면서 지우는 코드다.

```js
const nums = [2, 4, 6, 7];
for (let i = 0; i < nums.length; i++) if (nums[i] % 2 === 0) nums.splice(i, 1);
console.log(nums);
```

```text
[ 4, 7 ]
```

짝수를 다 지우려 했는데 4가 남았다. 0번의 2를 지우면 4가 0번으로 당겨지는데 `i`는 1로 넘어가서 4를 건너뛴다. 게다가 `splice`가 매번 뒤를 미니 O(n²)이다. `filter`로 새 배열을 만들거나, 꼭 제자리에서 해야 하면 앞에서 본 같은 방향 두 포인터(쓰는 위치를 따로 두기)로 O(n)에 지운다. 뒤에서부터 도는 것도 건너뛰기는 막지만 비용은 그대로다.

그 밖에 자주 보는 것들이 있다. 숫자 배열을 `sort()`로 정렬하면 문자열로 비교해서 100이 25 앞에 온다([sort 함정](/posts/js-array-mutation)). 배열을 `for...in`으로 돌면 인덱스가 문자열로 나오고 프로토타입에 추가된 속성까지 섞인다. `arr.length = 0`은 같은 배열을 가리키는 다른 변수까지 비워 버린다.

## 배열이 아닌 걸 골라야 할 때

배열은 기본값이다. 순서대로 쌓고 인덱스로 읽고 끝에서 넣고 빼는 일이 대부분이라 대부분의 경우 배열이 맞다. 캐시 지역성 덕분에 이론상 비슷한 구조보다 실제로 빠른 경우도 많다. 다른 구조를 고르는 건 배열의 약점이 정확히 문제가 될 때다.

- 맨 앞에서 자주 빼야 한다(대기열): 링 버퍼나 head 인덱스를 쓰는 큐. [스택, 큐, 덱](/posts/ds-stack-queue-deque)
- 중간에 넣고 빼는 위치를 이미 쥐고 있다(LRU 캐시의 노드): [연결 리스트](/posts/ds-linked-list)
- 값으로 찾는다: 해시맵이나 Set. [해시맵](/posts/ds-hash-map)
- 매번 가장 작은 값을 꺼낸다: [힙](/posts/ds-heap)
- 정렬 상태를 유지하며 넣고 뺀다: 균형 이진 탐색 트리. [이진 트리와 BST](/posts/ds-binary-tree-bst)

고르는 기준 전체는 [자료구조 한눈에 보기](/posts/data-structures-overview)에 모아 두었다.

다시 처음의 격자로 가면, 같은 O(N²)인데 여덟 배가 차이 난 이유는 칸이 붙어 있다는 배열의 성질 하나에서 나온다. 인덱스가 공짜인 것도, 중간 삽입이 비싼 것도, 행 순서가 빠른 것도 같은 이유다. 다음 글 [연결 리스트](/posts/ds-linked-list)는 이 성질을 버리는 대신 무엇을 얻는지 본다.

## 면접에서 나올 만한 질문

### 배열의 인덱스 접근이 O(1)인 이유는 무엇인가요?

칸 크기가 같은 원소가 메모리에 연속으로 놓여 있어서 `시작 주소 + i × 칸 크기`로 주소를 바로 계산하기 때문이다. 길이와 상관없이 계산 한 번이다. 연결 리스트는 i번째에 가려면 앞에서부터 따라가야 해서 O(n)이다.

### 동적 배열의 push는 가끔 전부 복사하는데 왜 O(1)이라고 하나요?

분할 상환 O(1)이기 때문이다. 용량을 일정 비율로 늘리면 n번 넣는 동안 복사 횟수의 합이 n에 비례해서, 한 번에 나누면 상수다. V8은 Node 22 기준 대략 1.5배에 16을 더해 늘리는 것을 `%DebugPrint`로 확인할 수 있다. 고정된 칸 수만큼 늘리면 합이 n²이 되어 이 보장이 깨진다.

### 자바스크립트 배열은 진짜 배열인가요?

명세상으로는 정수 키를 가진 객체지만, V8은 내부적으로 연속된 저장소를 쓴다. 원소 종류에 따라 정수, 실수, 포인터 칸을 고르고, 빈 칸이 있으면 HOLEY로 표시하며, 너무 성기면 해시 테이블(DICTIONARY)로 바꾼다. 종류는 한 방향으로만 바뀌니 한 배열에 한 종류의 값을 넣고 구멍을 내지 않는 게 좋다.

### 두 포인터는 언제 쓸 수 있나요?

포인터를 한쪽으로 움직이면 판단 기준이 한 방향으로만 바뀌는 단조성이 있을 때다. 정렬된 배열의 쌍 합에서는 합이 크면 오른쪽을, 작으면 왼쪽을 움직여 한 번 비교로 쌍 여러 개를 버린다. 정렬이 안 돼 있고 원래 인덱스가 필요하면 해시맵을 쓴다.

### 합이 k인 연속 구간을 세는 문제를 슬라이딩 윈도로 풀면 안 되나요?

원소가 모두 양수라면 되지만 음수가 있으면 안 된다. 창을 늘리면 합이 커진다는 단조성이 깨져서 언제 왼쪽을 당길지 정할 수 없다. 이때는 누적 합을 쓰고, 지금 합에서 k를 뺀 값이 이전에 몇 번 나왔는지 해시맵으로 세면 O(n)이다. 해시맵에 0을 한 번 넣어 두는 걸 빠뜨리면 처음부터 시작하는 구간을 놓친다.

### 2차원 배열을 열 순서로 돌면 왜 느린가요?

메모리가 행 우선으로 놓여 있으면 열 순서는 매번 한 행 길이만큼 건너뛰어서 캐시 라인에서 값 하나만 쓰고 버리기 때문이다. 이 글의 측정에서는 2048 × 2048 `Float64Array`에서 행 순서 7ms, 열 순서 26ms였다. 배열의 배열이라면 행마다 다른 객체를 찾아가는 비용이 더해져 58ms까지 늘었다. Big O는 같아도 상수가 메모리 접근 패턴에서 나온다.

### 행렬을 제자리에서 90도 회전하는 방법을 설명해 보세요.

전치한 뒤 각 행을 좌우로 뒤집으면 시계 방향 90도다. 전치할 때는 대각선 위쪽(`j > i`)만 돌아야 두 번 바꿔서 원래대로 돌아오는 실수를 피한다. 추가 메모리는 O(1), 시간은 칸 수만큼 O(n²)이다. 정사각형이 아니면 모양이 바뀌니 새 배열을 만든다.

### Array(n).fill([])로 격자를 만들면 어떤 문제가 생기나요?

모든 행이 같은 배열 하나를 가리켜서 한 행을 고치면 전부 바뀐다. `fill`은 값 하나를 모든 칸에 넣고, 배열은 참조로 전달되기 때문이다. `Array.from({ length: n }, () => [])`처럼 칸마다 새 배열을 만들어야 한다.
