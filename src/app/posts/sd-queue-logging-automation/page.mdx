이 시리즈에서 이 글의 자리: [⑥ 데이터 센터 여러 곳](/posts/sd-multi-datacenter)으로 서버가 두 지역에 수십 대가 된 다음 단계다. 다음 글은 [⑧ 샤딩 입문](/posts/sd-sharding-intro)이다. 같은 장의 글은 [① 서버 한 대](/posts/sd-start-single-server), [② 웹과 DB 나누기](/posts/sd-split-web-and-db), [③ 로드 밸런서와 무상태 웹](/posts/sd-load-balancer-stateless), [④ DB 복제](/posts/sd-db-replication-intro), [⑤ 캐시 계층과 CDN](/posts/sd-cache-and-cdn-tier)이다.

맛집 리뷰 앱에 사진 리뷰 기능을 붙였다. 사용자가 사진을 올리면 서버가 목록용, 상세용, 공유용 썸네일 세 장을 만든 뒤 "등록됐다"고 답한다. 썸네일 세 장을 만드는 데 300ms쯤 걸린다. 평소엔 문제없었다.

금요일 저녁, 사진이 한꺼번에 몰리자 이상한 일이 생겼다. 사진 업로드만 느린 게 아니라 인기 맛집 목록 같은 가벼운 요청까지 느려졌다. 웹 서버의 CPU와 처리 슬롯을 썸네일 작업이 붙잡고 있었기 때문이다. 이미지를 줄이는 일은 사용자가 꼭 기다려야 하는 일이 아닌데, 그 일이 모든 요청의 발목을 잡았다.

그런데 이 장애를 파악하는 것도 쉽지 않았다. 서버가 두 지역에 수십 대라 어느 서버에서 무슨 오류가 났는지 보려면 서버마다 접속해 로그 파일을 열어야 했다. "느려졌다"는 것도 사용자 문의로 처음 알았다.

이 글은 이 세 가지를 차례로 고친다. 오래 걸리는 일은 메시지 큐로 요청 밖으로 빼고, 흩어진 로그와 숫자는 한곳에 모으고, 서버 수십 대를 손으로 만지는 일은 자동화로 바꾼다.

## 사용자가 기다리지 않아도 되는 일

요청 안에서 하는 일을 둘로 나눠 보자. 사용자가 결과를 봐야 다음으로 넘어갈 수 있는 일, 예를 들어 리뷰 글이 DB에 저장됐는지는 요청 안에서 끝내야 한다. 반면 썸네일 만들기, 팔로워에게 알림 보내기, 검색 색인 갱신, 통계 집계는 몇 초 늦어도 사용자가 모른다. 이런 일은 "나중에 해 달라"는 쪽지를 남기고 바로 답해도 된다.

그 쪽지를 쌓아 두는 곳이 메시지 큐(message queue)다. 쪽지를 넣는 쪽을 생산자(producer), 꺼내서 처리하는 쪽을 소비자(consumer) 또는 워커(worker)라고 부른다. 둘은 서로를 모른다. 생산자는 큐에 넣는 것까지만 책임지고, 소비자는 큐에서 꺼낼 수 있을 때 꺼낸다. 이렇게 서로 직접 부르지 않고 중간을 두어 떼어 놓는 것을 결합을 느슨하게 한다(decoupling)고 말한다.

Redis의 리스트로 아주 단순한 큐를 만들어 봤다. 웹 서버는 `LPUSH`로 왼쪽에 넣고, 워커는 `BRPOP`으로 오른쪽에서 꺼낸다. `BRPOP`의 B는 blocking이다. 큐가 비어 있으면 무언가 들어올 때까지 기다린다. 썸네일 작업은 300ms를 쉬는 것으로 흉내 냈다.

```js
// queue.mjs 일부
async function uploadSync(photo) { await resize(photo); return 201; }   // 요청 안에서 다 한다
async function uploadAsync(photo) {                                      // 큐에 넣고 바로 답한다
  await web.lPush("jobs:thumbnail", JSON.stringify({ photo, at: Date.now() - t0 }));
  return 202;
}

async function worker(name, count) {
  for (let i = 0; i < count; i++) {
    const { element } = await c.brPop("jobs:thumbnail", 0);   // 들어올 때까지 기다렸다 꺼낸다
    const job = JSON.parse(element);
    await resize(job.photo);
    console.log(`${t()} ${name} done ${job.photo}`);
  }
}
// 저녁 시간: 순식간에 사진 6장이 올라온다
for (let i = 2; i <= 7; i++) { await uploadAsync(`p${i}.jpg`); }
await Promise.all([worker("worker-A", 4), worker("worker-B", 3)]);
```

```text

async upload responded in 1ms

 627ms worker-A done p1.jpg
 628ms worker-B done p2.jpg
 929ms worker-B done p4.jpg
 929ms worker-A done p3.jpg
1231ms worker-A done p6.jpg
1231ms worker-B done p5.jpg
1533ms worker-A done p7.jpg
1534ms queue depth: 0
```

첫 두 줄이 이 절의 요점이다. 요청 안에서 다 하면 사용자가 300ms를 기다렸고, 큐에 넣으면 1ms 만에 답했다. 사진이 몰린 순간 큐에는 일곱 개가 쌓였고, 워커 두 개가 300ms마다 두 개씩 처리해서 약 1.2초 뒤 모두 비웠다. 마지막 사진의 썸네일은 올린 지 1초 남짓 뒤에 생겼지만, 그동안 웹 서버는 다른 요청을 받느라 바빴을 뿐 막히지 않았다.

이 큐는 일부러 단순하게 만들었다. `BRPOP`은 꺼내는 순간 큐에서 지우기 때문에, 워커가 꺼낸 직후 죽으면 그 작업은 사라진다. 실제로는 처리를 끝낸 뒤에 "다 했다"고 알려야 지우는 방식(ack)을 쓴다. 그 방법과 가시성 타임아웃은 [메시지 큐 기초](/posts/message-queue-basics)에서 Redis와 PostgreSQL로 직접 만든다.

## 큐는 몰리는 순간을 흡수한다

큐를 두면 생산자와 소비자가 서로 다른 속도로 움직일 수 있다. 저녁 7시에 사진이 초당 120장 올라와도, 워커가 초당 60장밖에 못 만든다면 나머지는 큐에 쌓였다가 한가해진 뒤에 처리된다. 웹 서버는 받는 속도로, 워커는 처리하는 속도로 일한다. 큐가 그 차이를 잠깐 들고 있는 완충 지대다.

## 웹과 워커를 따로 늘린다

큐가 생기면서 얻은 큰 이득이 하나 더 있다. 웹 서버와 워커가 서로 다른 서버 묶음이 되었으니 따로 늘리고 줄일 수 있다. 웹 서버는 동시 요청 수나 CPU를 보고 늘리고, 워커는 큐 깊이를 보고 늘린다. 이미지 작업처럼 CPU를 많이 쓰는 워커는 CPU가 좋은 서버에, 웹 서버는 메모리와 네트워크 위주의 서버에 두는 식으로 장비도 다르게 고를 수 있다.

큐를 두면 새로 생기는 문제도 있다. 워커가 처리하고 "다 했다"고 알리기 직전에 죽으면 같은 작업이 다시 전달되어 두 번 처리될 수 있다. 그래서 워커의 작업은 두 번 해도 결과가 같게(멱등하게) 만든다. 썸네일이라면 같은 이름으로 덮어쓰면 된다. 처리할 때마다 실패하는 작업은 끝없이 돌지 않게 따로 빼 두는 [데드 레터 큐](/posts/dead-letter-queue)로 보낸다. 전달 보장의 단계는 [메시지 전달 보장](/posts/message-delivery-semantics)에 정리되어 있다. 그리고 큐 자체도 장애 지점이 되므로 Redis라면 복제를, 규모가 크면 Kafka나 RabbitMQ 같은 전용 시스템을 쓴다. 어떤 것을 고를지는 [Kafka 기초](/posts/kafka-basics)와 [RabbitMQ 기초](/posts/rabbitmq-basics)를 보면 된다.

## 수십 대의 로그를 한곳으로

이제 두 번째 문제다. 썸네일이 안 생긴다는 문의가 왔다. 요청은 web-2가 받았고, 작업은 worker-1이 처리했다. 서버마다 접속해 로그 파일을 뒤지면 서버가 수십 대일 때 답이 없다. 서버가 오토스케일링으로 꺼지면 그 서버의 로그 파일도 함께 사라진다.

그래서 각 서버는 로그를 자기 디스크에만 두지 않고, 수집 에이전트가 읽어 중앙 저장소로 보낸다. 저장소는 여러 서버의 로그를 시간순으로 모아 검색할 수 있게 한다. Elasticsearch와 Kibana, Grafana Loki, 클라우드의 로그 서비스가 이 자리에 들어간다.

세 서버의 로그를 한 파일씩 만들어 두고(줄 내용은 예시로 만들었다) `jq`로 요청 ID 하나를 걸러 봤다. 중앙 저장소에 모인 로그에 묻는 것과 같은 모양이다.

```bash
# 세 서버의 로그를 합쳐 요청 ID r-7f3a인 줄만 시간순으로 본다
cat logs/*.log | jq -c 'select(.req == "r-7f3a") | {time, host, level, msg}' | sort
```

```text
{"time":"2026-10-21T19:02:11.012Z","host":"web-2","level":"info","msg":"POST /photos"}
{"time":"2026-10-21T19:02:11.340Z","host":"worker-1","level":"info","msg":"thumbnail start"}
{"time":"2026-10-21T19:02:11.645Z","host":"worker-1","level":"error","msg":"thumbnail failed"}
```

web-2가 업로드를 받았고, 0.3초 뒤 worker-1이 작업을 시작해 0.3초 만에 실패했다. 실패한 줄 원본에는 `"err":"unsupported format: HEIC"`가 들어 있어 원인까지 바로 보인다. 로그 레벨 정하기, 개인정보 가리기, 비용 때문에 일부만 남기는 법은 [구조화 로그](/posts/structured-logging)에서 이어진다.

## 숫자로 미리 알아채기

로그는 무슨 일이 있었는지 자세히 알려 주지만, 수십 대가 초당 수천 줄을 쏟아내면 "지금 괜찮은가"를 한눈에 보기 어렵다. 그 질문에는 숫자, 즉 지표(metric)가 답한다. 지표는 일정 간격으로 모은 숫자의 흐름이다. 초당 요청 수, 오류 비율, 응답 시간, 큐 깊이 같은 것들이다.

지표는 보는 높이에 따라 세 층으로 나눠 생각하면 빠뜨리지 않는다.

작은 Node 서버에 세 층 중 둘을 붙여 봤다. 요청 수는 계속 늘어나기만 하는 카운터로, 큐 깊이는 오르내리는 게이지로 내보낸다. Prometheus가 읽는 텍스트 형식을 손으로 만들었다.

```js
// metrics.mjs 일부
if (req.url === "/metrics") {
  const depth = await redis.lLen("jobs:thumbnail");      // 큐 깊이 (게이지)
  let body = "# TYPE http_requests_total counter\n";
  for (const [k, v] of requests) { const [route, status] = k.split("|"); body += `http_requests_total{route="${route}",status="${status}"} ${v}\n`; }
  body += `# TYPE thumbnail_queue_depth gauge\nthumbnail_queue_depth ${depth}\n`;
  body += `# TYPE reviews_created_total counter\nreviews_created_total ${reviewsCreated}\n`;
  res.writeHead(200, { "Content-Type": "text/plain; version=0.0.4" }); return res.end(body);
}
```

```bash
# 인기 목록 5번, 리뷰 작성 2번, 없는 주소 1번을 부른 뒤 지표를 읽는다 (큐에는 작업 12개를 넣어 뒀다)
curl -s http://127.0.0.1:8393/metrics
```

```text
# TYPE http_requests_total counter
http_requests_total{route="/popular",status="200"} 5
http_requests_total{route="/reviews",status="201"} 2
http_requests_total{route="other",status="404"} 1
# TYPE thumbnail_queue_depth gauge
thumbnail_queue_depth 12
# TYPE reviews_created_total counter
reviews_created_total 2
```

수집 서버(Prometheus 같은)는 이 주소를 15초나 30초마다 읽어 시간별로 저장하고, 대시보드는 그것을 그래프로 그린다. 그리고 "큐 깊이가 10분 넘게 계속 오른다", "5xx 비율이 5분간 1%를 넘는다" 같은 조건에 알람을 건다. 카운터와 게이지의 차이와 히스토그램은 [지표 타입](/posts/metrics-types), 수집과 질의는 [Prometheus 기초](/posts/prometheus-basics), 알람을 언제 울릴지는 [알림 설계](/posts/alerting)에서 이어진다. 로그, 지표, 그리고 요청 하나를 서버 여러 대에 걸쳐 따라가는 trace를 함께 쓰는 법은 [관측 가능성](/posts/observability-basics)에 정리되어 있다.

## 사람 손을 덜 타게

마지막 문제는 서버 수다. 두 지역에 웹 서버, 워커, 캐시, DB가 수십 대다. 새 버전을 올릴 때마다 사람이 서버에 접속해 파일을 바꾸고 재시작하면, 언젠가 한 대를 빠뜨리거나 순서를 틀린다. [⑥ 데이터 센터 여러 곳](/posts/sd-multi-datacenter)에서 본 "버지니아만 설정이 두 달 늦었다" 같은 일이 이렇게 생긴다.

자동화는 크게 세 곳에 들어간다.

먼저 코드가 들어오는 길이다. 개발자가 코드를 올릴 때마다 서버가 자동으로 빌드하고 테스트를 돌린다. 이걸 지속적 통합(CI)이라고 한다. 깨진 코드가 합쳐지기 전에 걸러진다. 테스트를 통과한 결과물을 운영까지 자동으로 올리는 일이 지속적 배포(CD)다.

둘째는 서버와 네트워크를 만드는 일이다. 서버 몇 대를 어떤 설정으로 띄울지, 로드 밸런서와 방화벽 규칙을 어떻게 둘지를 코드로 적어 두면(IaC, Infrastructure as Code), 버지니아 데이터 센터도 같은 코드로 똑같이 만들 수 있다. [IaC 기본 개념](/posts/iac-basics)와 [Terraform 기본](/posts/terraform-basics)에서 이어진다.

셋째는 늘리고 줄이는 일이다. 웹 서버는 CPU나 요청 수, 워커는 큐 깊이를 보고 서버 수를 자동으로 조정한다. 앞에서 만든 지표가 바로 이 자동화의 입력이다. [오토스케일링](/posts/autoscaling)에서 어떤 지표로 언제 늘리는지를 다룬다.

세 가지 모두 한 가지 생각으로 묶인다. 사람이 기억해서 하는 일은 언젠가 빠지고, 코드로 적어 둔 일은 매번 같게 일어난다. 그리고 앞 절의 로그와 지표가 있어야 자동화가 제대로 했는지 확인할 수 있다. 파이프라인 설계는 [CI/CD의 뼈대](/posts/ci-cd-basics)에서 자세히 본다.

## 큐·로그·자동화를 한 줄씩, 다음은 샤딩

다음 글 [⑧ 샤딩 입문](/posts/sd-sharding-intro)에서는 데이터를 여러 DB에 나눠 담아 쓰기까지 나누는 샤딩을 다룬다. 이 글의 각 부분을 더 깊게 보려면 큐는 [메시지 큐 기초](/posts/message-queue-basics)와 [데드 레터 큐](/posts/dead-letter-queue), 로그는 [구조화 로그](/posts/structured-logging), 지표는 [지표 타입](/posts/metrics-types)과 [Prometheus 기초](/posts/prometheus-basics), 자동화는 [CI/CD의 뼈대](/posts/ci-cd-basics)로 가면 된다.

세 가지를 한 줄씩 다시 적으면 이렇다. 큐는 기다리지 않아도 되는 일을 요청 밖으로 빼서 웹과 워커가 각자의 속도로 일하게 한다. 로그와 지표는 수십 대에 흩어진 상태를 한곳에서 보게 해서, 사용자보다 먼저 알아채게 한다. 자동화는 수십 대를 매번 같은 방법으로 다루게 해서, 사람이 빠뜨리는 실수를 없앤다.

## 면접에서 나올 만한 질문

### 메시지 큐는 언제 쓰나요?

사용자가 결과를 기다리지 않아도 되는 일을 요청 밖으로 뺄 때 쓴다. 썸네일 생성, 알림 발송, 검색 색인 갱신처럼 몇 초 늦어도 되는 일을 큐에 넣고 바로 202로 답하면 응답이 빨라지고, 무거운 일이 웹 서버를 붙잡지 않는다. 생산자와 소비자를 떼어 놓아 서로 다른 속도로 일하고 따로 늘릴 수 있다는 것도 큰 이유다.

### 트래픽이 갑자기 10배가 되면 큐가 있는 구조는 어떻게 되나요?

웹 서버는 작업을 큐에 넣기만 하므로 응답 속도는 크게 변하지 않고, 처리하지 못한 몫은 큐에 쌓인다. 잠깐의 몰림이라면 한가해진 뒤 비워지지만, 들어오는 양이 처리량보다 계속 많으면 큐는 끝없이 자란다. 그래서 큐 깊이와 가장 오래된 작업의 나이를 지표로 보고, 기준을 넘으면 워커를 늘리거나 알람을 울린다.

### 워커가 작업을 처리하다 죽으면 그 작업은 어떻게 되나요?

꺼내자마자 지우는 큐라면 사라진다. 그래서 처리를 끝낸 뒤 ack를 보내야 지우고, 일정 시간 ack가 없으면 다른 워커에게 다시 주는 방식을 쓴다. 이 경우 같은 작업이 두 번 처리될 수 있으니 작업을 멱등하게 만들고, 계속 실패하는 작업은 데드 레터 큐로 격리한다.

### 큐 자체가 죽으면 어떻게 하나요?

큐도 장애 지점이므로 복제하거나 클러스터로 운영한다. Redis라면 복제와 자동 장애 조치를 붙이고, 잃으면 안 되는 작업이 많으면 디스크에 기록하고 복제하는 Kafka나 RabbitMQ 같은 전용 시스템을 쓴다. 큐에 넣기가 실패할 때 웹 서버가 어떻게 할지, 예를 들어 짧게 재시도하거나 DB에 작업을 기록해 두고 나중에 넣을지도 정해 둔다.

### 서버가 수십 대일 때 로그는 어떻게 관리하나요?

각 서버의 수집 에이전트가 로그를 중앙 저장소로 보내고, 거기서 시간순으로 검색한다. 서버가 오토스케일링으로 사라져도 로그는 남는다. 로그는 필드가 있는 JSON 한 줄로 남기고 모든 줄에 요청 ID를 넣어, 웹 서버와 워커처럼 다른 서버에서 남긴 줄을 하나의 흐름으로 잇는다.

### 어떤 지표를 보나요?

세 높이로 본다. 서버의 CPU, 메모리, 디스크 같은 호스트 지표, 계층별 요청 수, 오류율, 지연, 캐시 히트율, 큐 깊이 같은 서비스 지표, 그리고 리뷰 등록 수나 DAU 같은 비즈니스 지표다. 기술 지표가 모두 정상인데 비즈니스 지표가 떨어지는 장애도 있어서 셋을 함께 본다.

### 자동화는 어디에 넣나요?

코드가 들어올 때 빌드와 테스트를 자동으로 돌리는 CI, 같은 결과물을 데이터 센터마다 순서대로 올리는 CD, 서버와 네트워크를 코드로 만드는 IaC, 지표를 보고 서버 수를 조정하는 오토스케일링이다. 사람이 손으로 하면 서버 수십 대 중 하나를 빠뜨리거나 지역마다 설정이 어긋나기 때문이다. 배포는 한 곳씩 하고 지표가 나빠지면 자동으로 되돌리게 해서 잘못된 배포의 피해를 줄인다.
