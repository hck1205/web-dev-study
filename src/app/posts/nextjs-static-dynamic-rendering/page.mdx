import { getPostMetadata } from "@/features/posts";

export const metadata = getPostMetadata("nextjs-static-dynamic-rendering");

이 블로그의 작업 규칙 문서에는 이런 줄이 있다. "루트 `mdx-components.tsx`의 `MdxWrapper`는 서버 컴포넌트로 유지한다. wrapper를 클라이언트 컴포넌트로 직접 연결하면 Next.js가 넘기는 `searchParams`가 직렬화되어 MDX 페이지가 동적 렌더링으로 바뀐다." 정말 그런지 저장소를 통째로 복사해서 한 줄만 바꿔 빌드해 봤다.

```tsx
// 원래: children만 넘기는 서버 래퍼를 거친다
function MdxWrapper({ children }) {
  return <PostLayout>{children}</PostLayout>;
}
return { ...mdxComponents, wrapper: MdxWrapper, ...components };

// 바꾼 것: 클라이언트 컴포넌트인 PostLayout을 그대로 wrapper로
return { ...mdxComponents, wrapper: PostLayout, ...components };
```

```text
# 바꾸기 전
├ ○ /posts/ab-testing
├ ○ /posts/dns
├ ○ /posts/oauth
# 바꾼 뒤
├ ƒ /posts/ab-testing
├ ƒ /posts/dns
├ ƒ /posts/oauth
```

글 134개가 전부 `○`에서 `ƒ`로 바뀌었다. 빌드는 에러 없이 끝났다. 코드 한 줄에 정적 사이트가 요청마다 렌더링하는 사이트가 됐는데 아무도 알려 주지 않는다. 이 글은 Next.js App Router가 라우트를 정적으로 만들지 동적으로 만들지 무엇을 보고 정하는지, 그 결과를 어디서 확인하는지를 Next.js 16.4.1로 하나씩 빌드하며 정리한다. 정적 생성과 재생성 일반은 [SSG와 ISR](/posts/rendering-ssg-isr)에, 렌더링 방식 전체 비교는 [CSR, SSR, SSG, ISR, 스트리밍](/posts/rendering-strategies)에 있다.

## 요청이 있어야 알 수 있는 값들

라우트를 동적으로 만드는 것은 결국 "요청이 없으면 답할 수 없는 것"이다. Next 16에서 그런 것들과, 실제로 빌드해 본 결과다.

```tsx
// ƒ /cookies — 요청의 쿠키
const theme = (await cookies()).get("theme")?.value;

// ƒ /search — 페이지 props의 searchParams (?q=...)
const { q } = await searchParams;

// ƒ /conn — "지금 요청이 왔다"는 것만 표시. Math.random(), new Date()를 요청마다 새로 쓰고 싶을 때
await connection();

// ƒ /fetch-nostore — 캐시하지 말라는 fetch
await fetch(url, { cache: "no-store" });
```

`headers()`, `draftMode()`도 같은 부류다. 동적 세그먼트의 `params`도 `generateStaticParams`가 없으면 동적이다. 이 실험의 `/nf-top/[id]`는 목록을 주지 않아서 `ƒ`로 나왔다. 예전 버전의 `unstable_noStore()`가 하던 일은 이제 `connection()`이 한다.

`Date.now()`나 `Math.random()`만으로는 동적이 되지 않는다. 빌드 때 한 번 계산된 값이 HTML에 굳는다. `/revalidate` 페이지가 `new Date()`를 찍는데도 `○`인 이유다. 요청마다 새 값이 필요하면 `connection()`을 먼저 부른다.

## fetch는 캐시하지 않는데 빌드 때 한 번은 부른다

Next 15부터 `fetch`는 기본으로 캐시하지 않는다. 그런데 `/fetch-default` 페이지는 옵션 없는 `fetch`를 부르는데도 `○`로 나왔다. 가격 API가 응답에 현재 시각을 넣게 해 두고 `next start` 뒤에 요청해 보면 이유가 보인다.

```text
== /fetch-default
x-nextjs-cache: HIT
Cache-Control: s-maxage=31536000
<p>가격 89000 at 2026-10-18T19:15:36.078Z</p>
== /fetch-nostore
Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate
<p>가격 89000 at 2026-10-18T19:15:46.485Z</p>
```

`/fetch-default`의 시각은 빌드한 시각이다. 몇 번을 다시 요청해도 같다. Next 문서의 표현을 옮기면, 캐시 옵션이 없는 `fetch`도 요청 시점 API보다 앞에서 불리면 라우트를 그 지점까지 미리 렌더링하므로 빌드 때 한 번 불린다. "fetch는 캐시하지 않는다"는 말만 믿고 가격 API를 옵션 없이 부르면, 배포 뒤 가격을 바꿔도 페이지는 빌드 때 가격을 보여 준다. 매번 새로 받아야 하면 `cache: "no-store"`를 주고, 일정 간격으로 받아도 되면 `next: { revalidate: 60 }`을 준다.

## 직접 정해 버리는 설정

자동 판단을 덮어쓰는 방법이 라우트 세그먼트 설정이다. `page.tsx`나 `layout.tsx`에서 상수를 export한다.

```tsx
export const dynamic = "force-dynamic"; // 무조건 요청마다. /forced가 ƒ
export const dynamic = "force-static";  // 무조건 정적. cookies(), headers(), searchParams가 빈 값이 된다
export const dynamic = "error";         // 정적이어야 한다. 요청 시점 API를 쓰면 빌드 실패
export const revalidate = 60;           // 정적으로 만들고 60초 뒤 첫 요청에서 다시 만든다
export const revalidate = 0;            // 동적. /rv0가 ƒ
export const dynamicParams = false;     // generateStaticParams 목록 밖의 주소는 404
```

`force-static`은 조심해서 쓴다. `searchParams`를 읽는 페이지에 이걸 붙이고 `?q=ab`로 요청했다.

```text
== /search?q=ab        (자동 판단, ƒ)
<p>검색어: ab</p>
== /fs-search?q=ab     (force-static, ○)
<p>검색어: []</p>
```

에러도 경고도 없이 검색어가 비었다. 정적으로 만들라고 했으니 빌드 때 기준으로 요청 값을 비워 버린 것이다. 반대로 `dynamic = "error"`는 실수를 빌드에서 잡는다. 정적이어야 하는 페이지에 걸어 두면 누가 `cookies()`를 넣었을 때 이렇게 멈춘다.

```text
Error: Route /derr with `dynamic = "error"` couldn't be rendered statically because it used `cookies()`. See more info here: https://nextjs.org/docs/app/building-your-application/rendering/static-and-dynamic#dynamic-rendering
Export encountered an error on /derr/page: /derr, exiting the build.
```

처음 장면 같은 사고를 막는 데는 이 설정이 가장 확실하다. 글 페이지처럼 반드시 정적이어야 하는 라우트에는 `error`를 걸어 두면 한 줄 바뀌어 동적으로 넘어가는 순간 빌드가 실패한다.

`generateStaticParams`는 미리 만들 목록을 정한다. 목록 밖의 주소는 기본값(`dynamicParams = true`)이면 첫 요청 때 만들어 캐시한다. 목록에 없던 `/posts/new`를 두 번 요청했다.

```text
== /posts/new   x-nextjs-cache: MISS
== /posts/new   x-nextjs-cache: HIT
```

첫 요청은 서버가 렌더링(MISS)했고, 두 번째부터는 저장된 결과(HIT)다. 빌드 출력에는 `●`이 목록에 있던 `hello`, `world`만 나온다. 목록에 있어도 `cookies()`를 부르면 소용없다. `/gsp-cookie/[slug]`는 `generateStaticParams`가 있는데도 `ƒ`로 나왔다. 동적 API가 이긴다.

## 응답 헤더로 밖에서 확인하기

빌드 로그가 없거나 배포된 결과를 보고 싶으면 응답 헤더를 본다. `next start`로 띄운 결과를 경우별로 받았다.

```bash
curl -s -D - -o /dev/null http://127.0.0.1:3200/ | grep -i -E '^(cache-control|x-nextjs-cache|x-nextjs-prerender)'
```

```text
== / (○)
x-nextjs-cache: HIT
x-nextjs-prerender: 1
x-nextjs-prerender: 1
Cache-Control: s-maxage=31536000
== /revalidate (○, revalidate 60)
x-nextjs-cache: HIT
x-nextjs-prerender: 1
x-nextjs-prerender: 1
Cache-Control: s-maxage=60, stale-while-revalidate=31535940
== /cookies (ƒ)
Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate
```

정적이면 `x-nextjs-prerender: 1`(이 버전은 같은 헤더를 두 번 붙였다)과 `s-maxage`가 있다. 동적이면 `private, no-store`다. `s-maxage`는 CDN 같은 공유 캐시가 얼마나 들고 있어도 되는지를 말한다. 헤더의 뜻은 [HTTP 캐싱과 CDN](/posts/http-caching-cdn)에서 자세히 다뤘다. Vercel 같은 플랫폼은 여기에 자기 캐시 헤더를 덧붙이니, 플랫폼에서 볼 때는 그 헤더도 함께 본다.

## 클라이언트 컴포넌트의 useSearchParams

서버 쪽 `searchParams`가 아니라 클라이언트 컴포넌트에서 `useSearchParams()`를 쓰면 이야기가 다르다. 정적 페이지 안의 클라이언트 컴포넌트가 이 훅을 쓰고 `Suspense`로 감싸지 않으면 빌드가 실패한다.

```text
⨯ useSearchParams() should be wrapped in a suspense boundary at page "/usp". Read more: https://nextjs.org/docs/messages/missing-suspense-with-csr-bailout
Error occurred prerendering page "/usp". Read more: https://nextjs.org/docs/messages/prerender-error
```

감싸면 페이지는 `○`로 남고, 그 컴포넌트만 브라우저에서 그린다. 빌드된 HTML을 열어 보면 그 자리에 fallback만 있다.

```html
<main><h1>검색</h1><!--$!--><template data-dgst=""></template><p>…</p><!--/$--></main>
```

`<!--$!-->`는 "서버가 그리지 못했으니 브라우저가 그려라"는 표시다([스트리밍 SSR](/posts/streaming-ssr-suspense) 글에서 본 그 표시다). 페이지 전체를 동적으로 만드는 대신 검색어를 쓰는 조각만 클라이언트 렌더링으로 넘긴다. 그 조각은 검색 엔진이 보는 HTML에 없다는 것도 함께 기억한다.

## 이 블로그의 MdxWrapper가 동적이 된 이유

처음 장면으로 돌아가자. `page.mdx`가 만든 페이지 컴포넌트는 Next에게서 `params`와 `searchParams`를 props로 받는다. MDX가 만든 컴포넌트는 받은 props를 그대로 `wrapper`에 넘긴다. wrapper가 클라이언트 컴포넌트라면 그 props가 서버에서 클라이언트로 경계를 건너야 하고, 그러려면 payload에 적혀야 한다. 바꾼 빌드에서 글 페이지의 payload를 받아 보니 실제로 그렇게 적혀 있었다.

```bash
curl -sL -H 'RSC: 1' http://127.0.0.1:3300/posts/oauth | grep -o '"params":"[^"]*","searchParams":"[^"]*"'
```

```text
"params":"$@1a","searchParams":"$@1b"
```

`$@1b`는 "이 값은 Promise이고 1b번 조각으로 채워진다"는 뜻이다. 그 Promise를 채우려면 요청의 쿼리 문자열을 읽어야 한다. 요청 시점 API를 건드린 것이다. 빌드는 그 순간 이 라우트를 동적으로 넘겼다. 아래 그림이 두 구조의 차이다.

서버 래퍼는 받은 props 중 `children`만 골라 `PostLayout`에 넘긴다. `searchParams`는 서버 쪽에서 버려지고 경계를 건너지 않는다. 그래서 정적으로 남는다. 두 빌드를 `next start`로 띄워 같은 글을 세 번씩 받았다.

```text
# 서버 래퍼 (○)
x-nextjs-cache: HIT
Cache-Control: s-maxage=31536000
before ttfb=0.009077
before ttfb=0.007788
before ttfb=0.006540
# 클라이언트 컴포넌트를 바로 wrapper로 (ƒ)
Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate
after ttfb=0.037627
after ttfb=0.043699
after ttfb=0.028849
```

같은 컴퓨터 안에서도 첫 바이트가 네다섯 배 늦다. 배포 환경이라면 차이가 더 커진다. 정적 페이지는 CDN이 바로 답하지만, 동적 페이지는 요청마다 서버리스 함수가 깨어나 MDX 본문 전체를 렌더링한다. `s-maxage`가 사라졌으니 CDN에 캐시되지도 않는다. 트래픽이 늘면 함수 실행 비용이 그대로 늘어난다.

이 일반 규칙은 MDX에만 해당하지 않는다. 페이지나 레이아웃이 받은 props를 펼쳐서(`{...props}`) 클라이언트 컴포넌트에 넘기면 같은 일이 생긴다. 클라이언트 컴포넌트에는 필요한 값만 골라 넘긴다. 경계를 건너는 값이 어떻게 직렬화되는지는 [React 서버 컴포넌트](/posts/react-server-components)에서 다뤘다.

## Cache Components를 켜면 판단 기준이 바뀐다

Next 16에는 `next.config`의 `cacheComponents: true`로 켜는 새 모델이 있다. 이 모드에서는 라우트를 통째로 정적·동적으로 나누지 않고, 페이지 안에서 요청이 필요한 부분만 `Suspense`로 감싸 나머지를 미리 만든다. `"use cache"`로 캐시할 함수나 컴포넌트를 표시한다. 같은 상품 페이지를 이 모드로 빌드했다.

```tsx
async function Greeting() {
  const name = (await cookies()).get("name")?.value ?? "손님";
  return <p>{name}님 안녕하세요</p>;
}
export default function Page() {
  return <main><h1>무선 이어폰</h1><Suspense fallback={<p>…</p>}><Greeting /></Suspense></main>;
}
```

```text
Route (app)
┌ ○ /
├ ○ /_not-found
└ ◐ /product

○  (Static)             prerendered as static content
◐  (Partial Prerender)  prerendered as static HTML with dynamic server-streamed content
```

`◐`는 셸(`<h1>무선 이어폰</h1>`과 fallback)을 빌드 때 만들어 두고 쿠키가 필요한 인사말만 요청 때 스트리밍한다는 뜻이다. 빌드된 HTML에 `<!--$?--><template id="B:0"></template><p>…</p><!--/$-->`가 들어 있다. 이 모드에서는 요청 시점 API를 `Suspense` 밖에서 부르면 빌드가 실패한다. 경계 없이 `cookies()`를 부르는 페이지를 넣었더니 이렇게 멈췄다.

```text
Error: Route "/plain": Next.js encountered uncached or runtime data during prerendering.
`fetch(...)`, `cookies()`, `headers()`, `params`, `searchParams`, or `connection()` accessed outside of `<Suspense>` prevents the route from being prerendered, blocking the page load and leading to a slower user experience.
Ways to fix this:
  - [stream] Provide a placeholder with `<Suspense fallback={...}>` around the data access
  - [cache] For uncached data (`fetch`, database calls): cache the access with `"use cache"` (does not apply to `connection()`)
  - [block] Set `export const instant = false` to allow a blocking route
```

조용히 동적으로 넘어가던 예전 모델과 달리, 어디가 요청을 기다리게 만드는지 빌드가 짚어 준다. 대신 `export const dynamic` 같은 예전 세그먼트 설정과 함께 쓸 수 없어서 옮기려면 손이 간다. 이 글의 나머지는 이 옵션을 켜지 않은 기본 모델 기준이다.

## 정적인 줄 알았던 페이지가 요청마다 렌더링될 때

증상은 이렇게 온다. 배포 뒤 서버리스 함수 실행 횟수가 갑자기 늘었다. 글 페이지의 TTFB가 수십 ms에서 수백 ms로 뛰었다. CDN 적중률이 떨어졌다. 원인을 좁히는 순서다.

```bash
# 1. 응답 헤더로 지금 상태를 본다. private, no-store면 동적이다
curl -s -D - -o /dev/null https://example.com/posts/oauth | grep -i -E 'cache-control|x-nextjs|x-vercel-cache'

# 2. 빌드 로그에서 ƒ로 바뀐 라우트를 찾는다. 직전 배포 로그와 비교한다
grep -E ' (○|●|ƒ) /' build-old.log | sort > old.txt
grep -E ' (○|●|ƒ) /' build-new.log | sort > new.txt
diff old.txt new.txt

# 3. 왜 동적이 됐는지 보려면 의심 가는 라우트에 dynamic = "error"를 걸고 다시 빌드한다
#    어느 API 때문인지 에러 메시지가 짚어 준다
```

2번에서 많은 라우트가 한꺼번에 바뀌었다면 공통 레이아웃이나 공통 래퍼를 의심한다. 처음 장면처럼 래퍼 하나가 글 134개를 바꾼다. 레이아웃에서 `cookies()`로 테마를 읽거나, 헤더 컴포넌트가 `headers()`로 사용자 에이전트를 읽는 코드도 아래 모든 페이지를 동적으로 만든다. 이런 값은 클라이언트 컴포넌트에서 브라우저 쪽으로 읽거나, 정말 필요한 페이지에서만 읽는다. 이 블로그는 테마를 쿠키로 읽지 않고 `html[data-theme]`와 레이아웃의 초기 인라인 스크립트로 브라우저에서 정한다. 덕분에 레이아웃이 정적으로 남는다.

라우트 하나만 바뀌었다면 그 페이지가 import하는 것을 본다. 새로 넣은 컴포넌트가 `searchParams`를 받거나, 데이터 함수가 `cache: "no-store"`로 바뀌었을 가능성이 크다. 반대 방향 증상도 있다. "가격을 바꿨는데 페이지가 안 바뀐다"면 그 라우트가 `○`인지부터 본다. 옵션 없는 `fetch`가 빌드 때 값으로 굳은 경우다.

## 다시 MdxWrapper로

처음의 한 줄은 `searchParams`라는 요청 값을 클라이언트 경계 너머로 넘겼고, 빌드는 그걸 "요청이 필요한 라우트"로 판단했다. Next App Router는 빌드 때 각 라우트를 렌더링해 보다가 쿠키, 헤더, 검색어, `connection()`, `no-store` fetch처럼 요청이 있어야 답할 수 있는 값을 만나면 그 라우트를 동적으로 넘긴다. 이 판단은 조용히 일어나니 빌드 출력의 기호와 응답 헤더로 확인하고, 정적이어야 하는 라우트에는 `dynamic = "error"`를 걸어 빌드가 지키게 한다.

## 면접에서 나올 만한 질문

### Next.js App Router는 라우트가 정적인지 동적인지 어떻게 정하나요?

빌드 때 각 라우트를 실제로 렌더링해 본다. 끝까지 렌더링되면 HTML과 payload를 저장해 정적(○, ●)으로 두고, 도중에 `cookies()`, `headers()`, `searchParams`, `connection()`, `cache: "no-store"` fetch처럼 요청이 있어야 알 수 있는 값에 손을 대면 그 라우트를 요청마다 렌더링하는 동적(ƒ)으로 표시한다. 정적 분석이 아니라 렌더링을 시도한 결과다.

### 빌드 출력의 ○, ●, ƒ는 각각 무엇인가요?

○는 빌드 때 만든 정적 HTML, ●는 동적 세그먼트가 있지만 `generateStaticParams`가 준 목록으로 미리 만든 HTML, ƒ는 요청마다 서버에서 렌더링하는 라우트다. `cacheComponents`를 켜면 셸만 미리 만들고 일부를 스트리밍하는 ◐가 더해진다. Revalidate 열에 값이 있으면 그 간격으로 다시 만들 수 있는 정적 라우트다.

### fetch를 옵션 없이 불렀는데 페이지 값이 바뀌지 않아요. 왜 그런가요?

Next 15부터 fetch는 기본으로 캐시하지 않지만, 요청 시점 API보다 앞에서 불린 fetch는 빌드 때 라우트를 미리 렌더링하면서 한 번 실행된다. 그 결과가 정적 HTML에 굳어 배포 뒤에도 빌드 때 값이 보인다. 매번 새로 받으려면 `cache: "no-store"`, 주기적으로 받으려면 `next: { revalidate }`를 준다.

### force-static과 dynamic error 설정은 어떻게 다른가요?

둘 다 정적 렌더링을 원할 때 쓰지만 요청 시점 API를 만났을 때가 다르다. `force-static`은 cookies, headers, searchParams를 빈 값으로 바꿔 조용히 정적으로 만들어서 검색어가 사라지는 식의 버그를 숨길 수 있다. `error`는 그런 API를 쓰면 빌드를 실패시켜 정적이어야 하는 라우트를 지켜 준다.

### 레이아웃에서 cookies()를 읽으면 어떤 일이 생기나요?

그 레이아웃 아래의 모든 페이지가 동적이 된다. 레이아웃 렌더링이 요청 시점 API를 건드리니 그 아래 라우트 전체를 빌드 때 완성할 수 없다. 테마처럼 브라우저가 알 수 있는 값은 클라이언트에서 읽거나, 필요한 페이지에서만 읽어서 공통 레이아웃을 정적으로 둔다.

### 클라이언트 컴포넌트로 props를 넘겼을 뿐인데 페이지가 동적이 될 수 있나요?

된다. 페이지가 받은 `searchParams`를 펼쳐서 클라이언트 컴포넌트에 넘기면 그 Promise를 payload에 적기 위해 요청의 쿼리를 읽어야 하고, 빌드는 그 라우트를 동적으로 넘긴다. 이 블로그에서 MDX wrapper를 클라이언트 컴포넌트로 바로 연결했을 때 글 134개가 ○에서 ƒ로 바뀐 게 그 경우라서, `children`만 넘기는 서버 래퍼를 둔다.

### 배포 뒤 정적 페이지가 동적으로 바뀐 걸 어떻게 알아채나요?

응답 헤더에서 `x-nextjs-prerender`와 `s-maxage`가 사라지고 `private, no-store`가 붙는다. 빌드 로그의 라우트 표를 직전 배포와 비교하면 ƒ로 바뀐 라우트가 보이고, 함수 실행 횟수나 CDN 적중률 같은 지표에서도 드러난다. 정적이어야 하는 라우트에 `dynamic = "error"`를 걸어 두면 배포 전에 빌드가 멈춘다.
