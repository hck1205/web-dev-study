코딩 테스트 문제를 열었다. "양의 정수 배열과 target이 주어진다. 합이 target 이상인 연속 부분 배열 중 가장 짧은 것의 길이를 구하라. 1 ≤ n ≤ 10⁵." 예제는 바로 맞혔다. 모든 시작점에서 오른쪽으로 더해 가다가 target을 넘으면 멈추는 코드다. 그런데 제출하니 시간 초과다.

```js
function brute(target, nums) {
  let best = Infinity;
  for (let i = 0; i < nums.length; i++) {
    let sum = 0;
    for (let j = i; j < nums.length; j++) {
      sum += nums[j];
      if (sum >= target) { best = Math.min(best, j - i + 1); break; } // 넘으면 이 시작점은 끝
    }
  }
  return best === Infinity ? 0 : best;
}
```

```text
n=20000 brute     4916 83.0ms
n=100000 brute     24635 2021.2ms
```

1~100 사이 무작위 값에 target을 n에 비례해 키우며 Node.js 22에서 재 봤다. n이 2만일 때 83ms였는데 10만이 되자 2초다. 다섯 배 늘었는데 스물네 배 느려졌다. 문장 끝의 "n ≤ 10⁵"를 처음부터 읽었다면 이 풀이는 쓰기 전에 버렸을 것이다.

알고리즘 문제를 풀 때 막히는 지점은 대개 코드가 아니라 "무엇으로 풀지"다. 이 글은 그 고르는 과정을 순서대로 정리한 지도다. 입력 크기에서 허용되는 복잡도를 계산하고, 문제 문장의 모양에서 기법을 좁히고, 같은 문제를 여러 기법으로 풀어 비교한 뒤, 면접에서 문제를 받았을 때의 흐름과 자바스크립트에서 특히 조심할 함정을 본다. 각 기법의 자세한 설명은 따로 쓴 글로 넘긴다. 자료구조를 고르는 쪽의 지도는 [자료구조 한눈에 고르기](/posts/data-structures-overview)에 있어서 여기서는 기법 쪽을 본다.

## 입력 크기가 허락하는 복잡도

먼저 자바스크립트가 1초에 얼마나 일하는지 알아야 예산을 세울 수 있다. 같은 머신의 Node 22에서 세 가지를 재 봤다.

```js
let t = performance.now(); let s = 0;
for (let i = 0; i < 1e9; i++) s += i & 7;          // 가장 단순한 덧셈 10억 번
console.log(`1e9 simple loop: ${(performance.now() - t).toFixed(0)}ms (s=${s})`);
const m = new Map(); t = performance.now();
for (let i = 0; i < 1e7; i++) m.set(i & 0xffff, (m.get(i & 0xffff) ?? 0) + 1); // Map 읽고 쓰기 1천만 번
console.log(`1e7 Map get+set: ${(performance.now() - t).toFixed(0)}ms`);
const arr = Array.from({ length: 1e6 }, (_, i) => (i * 7919) % 1000003);
t = performance.now(); arr.slice().sort((a, b) => a - b);                     // 숫자 100만 개 정렬
console.log(`sort 1e6 numbers: ${(performance.now() - t).toFixed(0)}ms`);
```

| n의 상한 | 들어가는 복잡도 | 자주 쓰는 기법 |
|---|---|---|
| 20 안팎 | O(2ⁿ), O(n!)에 가까워도 된다 | 완전 탐색, 백트래킹, 비트마스크 |
| 500 안팎 | O(n³) | 3중 반복, 구간 DP, 플로이드-워셜 |
| 5,000 안팎 | O(n²) | 2중 반복, 2차원 DP |
| 10⁵ ~ 10⁶ | O(n log n), O(n) | 정렬, 이분 탐색, 힙, 두 포인터, 해시 |
| 10⁹ 이상 | O(log n), O(1) | 이분 탐색, 수학 공식 |

처음 문제는 n ≤ 10⁵이었으니 O(n²)인 100억 번은 처음부터 탈락이고 O(n log n) 이하를 찾아야 했다. 시간 제한이 2초이거나 숫자가 경계에 걸리면 상수를 따져 봐야 하지만, 자릿수가 두 개 이상 차이 나면 고민할 필요가 없다. 이런 계산의 바탕인 Big O를 세는 법은 [Big O 표기법](/posts/big-o-notation)에 있다.

메모리도 같은 방식으로 센다. n이 10⁶인 2차원 표는 10¹²칸이라 만들 수 없다. 숫자 하나에 8바이트로 잡으면 1천만 칸이 80MB다. 상태를 n × n으로 잡은 DP가 시간 안에는 돌 것 같아도 메모리에서 먼저 막히는 경우가 많다.

## 문장의 모양이 기법을 좁힌다

예산으로 후보 복잡도를 정했으면 문장의 모양으로 기법을 좁힌다. 자료구조의 신호 단어("k번째로 큰", "괄호", "접두사")는 [자료구조 지도](/posts/data-structures-overview)에 모아 뒀다. 기법을 고를 때는 문제가 무엇을 묻는지가 더 큰 신호다.

모든 경우를 실제로 나열해야 하면(모든 순열, N-Queen의 모든 배치, 가능한 조합 출력) 답의 개수 자체가 지수라 피할 수 없다. 백트래킹으로 가망 없는 가지를 일찍 자르는 게 할 수 있는 최선이고, 자세한 건 [재귀와 백트래킹](/posts/recursion-backtracking)에 있다. 나열이 아니라 개수나 최솟값만 묻는데 백트래킹이 같은 상태를 반복해서 지나간다면 그 상태를 기억하는 순간 DP가 된다.

"최소", "최대", "몇 가지"를 묻고 매 단계의 선택이 다음 선택지를 바꾸면 [동적 계획법](/posts/dynamic-programming)과 [그리디](/posts/greedy-algorithms)가 후보다. 그리디가 더 빠르지만 지역 최선이 전체 최선이라는 근거가 있어야 한다. 근거가 안 보이면 작은 입력으로 완전 탐색과 비교해 반례부터 찾는다.

"조건을 만족하는 가장 작은 값(속도, 용량, 시간)"을 묻고, 어떤 값이 된다면 그보다 큰 값도 된다는 단조성이 있으면 답 자체를 이분 탐색한다. 답 후보가 10⁹개여도 판정 30번이면 끝난다. 이분 탐색의 경계 처리는 [이분 탐색](/posts/binary-search)에서 다룬다.

연속 구간(부분 배열, 부분 문자열)을 물으면 두 포인터, 슬라이딩 윈도, 누적 합이 먼저다. 값이 모두 양수라 창을 넓히면 합이 커진다는 단조성이 있으면 창 밀기, 음수가 섞이면 누적 합과 [해시맵](/posts/ds-hash-map)이다. 두 문자열의 비교(공통 부분 수열, 편집 거리)는 2차원 DP로 간다. 창 밀기와 누적 합 자체는 [배열과 행렬](/posts/ds-array-matrix)에 있다.

연결 여부, 최단 단계, 선후 관계를 물으면 그래프 문제다. 문제에 그래프라는 말이 없어도 격자, 단어 변환, 상태 전이가 정점과 간선으로 바뀐다. 가중치가 없으면 BFS, 순서가 필요하면 위상 정렬([그래프와 BFS·DFS](/posts/ds-graph-bfs-dfs)), 연결이 계속 추가되면 [유니온 파인드](/posts/ds-union-find), 가중치가 있으면 [힙](/posts/ds-heap)을 쓴 다익스트라다.

정렬은 이 모든 갈래 앞에 붙는 전처리인 경우가 많다. 정렬하고 나면 두 포인터, 이분 탐색, 그리디가 가능해진다. 정렬 자체의 성질(안정성, 비교 함수)은 [정렬 알고리즘](/posts/sorting-algorithms)에서 다룬다.

### 단조성이 보이면 답을 찍어 본다

"답을 이분 탐색한다"는 처음 들으면 낯설어서, 문장을 어떻게 읽는지 한 문제로 보자. 바나나 더미 [3, 6, 7, 11]을 8시간 안에 다 먹으려면 시간당 최소 몇 개씩 먹어야 하나(LeetCode 875). 한 시간에 한 더미만 먹고, 더미가 속도보다 작으면 남은 시간은 쉰다.

속도 k가 정해지면 걸리는 시간은 더미마다 올림(p / k)의 합이라 O(n)에 계산된다. 그리고 k로 8시간 안에 되면 k + 1로도 된다. 이 단조성 덕분에 1부터 가장 큰 더미 11 사이를 반으로 줄여 가며 찾을 수 있다.

```js
function minSpeed(piles, h) {
  let lo = 1, hi = Math.max(...piles);     // 답은 이 범위 안에 있다
  const steps = [];
  while (lo < hi) {
    const k = Math.floor((lo + hi) / 2);
    const hours = piles.reduce((s, p) => s + Math.ceil(p / k), 0); // 판정: k로 몇 시간?
    steps.push(`k=${k} hours=${hours} ${hours <= h ? "ok" : "slow"}`);
    if (hours <= h) hi = k; else lo = k + 1;                        // 되면 더 작게, 안 되면 더 크게
  }
  return { k: lo, steps };
}
console.log(JSON.stringify(minSpeed([3, 6, 7, 11], 8)));
```

## 한 문제를 세 가지로 풀어 보기

처음의 최소 길이 부분 배열 문제(LeetCode 209)로 돌아가자. 같은 문제를 기법만 바꿔 세 번 풀면 기법 사이의 관계가 보인다.

첫째는 앞에서 본 완전 탐색이다. 시작점마다 끝점을 늘리니 O(n²)다.

둘째는 누적 합과 이분 탐색이다. 값이 양수라 누적 합 배열 p는 계속 커진다. 시작점 i에서 합이 target 이상이 되는 첫 끝점은 "p[j] ≥ p[i] + target인 가장 작은 j"이고, p가 정렬돼 있으니 이분 탐색으로 찾는다. O(n log n)이다.

```js
function prefixBS(target, nums) {
  const p = [0];
  for (const x of nums) p.push(p[p.length - 1] + x);    // p[j] - p[i] = nums[i..j-1]의 합
  let best = Infinity;
  for (let i = 0; i < nums.length; i++) {
    const need = p[i] + target;
    let lo = i + 1, hi = p.length;
    while (lo < hi) { const m = (lo + hi) >> 1; if (p[m] >= need) hi = m; else lo = m + 1; }
    if (lo < p.length) best = Math.min(best, lo - i);
  }
  return best === Infinity ? 0 : best;
}
```

셋째는 슬라이딩 윈도다. 끝점을 오른쪽으로 늘리며 합을 더하고, 합이 target 이상인 동안 왼쪽을 당겨 창을 줄인다. 두 끝이 모두 앞으로만 가니 O(n)이다.

```js
function windowed(target, nums) {
  let left = 0, sum = 0, best = Infinity;
  for (let right = 0; right < nums.length; right++) {
    sum += nums[right];                          // 창을 오른쪽으로 넓힌다
    while (sum >= target) {                      // 조건을 만족하는 동안
      best = Math.min(best, right - left + 1);
      sum -= nums[left++];                       // 왼쪽을 당겨 더 짧은 창을 찾는다
    }
  }
  return best === Infinity ? 0 : best;
}
```

```text
n=100000 window    24635 1.2ms

```

## 자바스크립트로 풀 때 조심할 것

알고리즘은 맞는데 언어 때문에 틀리는 경우가 있다. 자바스크립트에서 자주 만나는 것들을 실제로 돌려 봤다.

```js
const lo = 3_000_000_000, hi = 4_000_000_000;
console.log("(lo+hi)>>1      =", (lo + hi) >> 1);              // 비트 연산은 32비트 정수로 자른다
console.log("Math.floor/2    =", Math.floor((lo + hi) / 2));
console.log("lo+((hi-lo)>>1) =", lo + ((hi - lo) >> 1));
console.log("default sort    =", [10, 9, 1, 100, 25].sort());     // 비교 함수가 없으면 문자열로 비교한다
console.log("numeric sort    =", [10, 9, 1, 100, 25].sort((a, b) => a - b));
const big = Array.from({ length: 200000 }, (_, i) => i);
try { console.log(Math.max(...big)); } catch (e) { console.log("Math.max(...200000):", e.constructor.name, e.message); }
console.log("reduce max      =", big.reduce((m, x) => (x > m ? x : m), -Infinity));
console.log("2**53+1         =", 2 ** 53 + 1);
```

```text
(lo+hi)>>1      = -794967296
Math.floor/2    = 3500000000
lo+((hi-lo)>>1) = 3500000000
default sort    = [ 1, 10, 100, 25, 9 ]
numeric sort    = [ 1, 9, 10, 25, 100 ]
Math.max(...200000): RangeError Maximum call stack size exceeded
reduce max      = 199999
2**53+1         = 9007199254740992
```

첫 줄은 이분 탐색에서 흔히 쓰는 `(lo + hi) >> 1`이 21억을 넘는 값에서 음수가 되는 모습이다. 비트 연산자는 피연산자를 32비트 정수로 바꾸기 때문이다. 인덱스는 이 범위를 넘지 않지만 답 이분 탐색에서 범위가 10⁹을 넘으면 그대로 터진다. 값의 범위가 크면 `Math.floor((lo + hi) / 2)`를 쓴다. 자바스크립트 숫자는 2⁵³까지 정확하니 이 정도 덧셈은 안전하다. 그보다 큰 경우의 수는 마지막 줄처럼 정밀도를 잃으니 BigInt나 나머지 연산을 쓴다.

비교 함수 없는 `sort`는 숫자를 문자열로 바꿔 사전 순으로 정렬한다. 예제의 작은 숫자로는 우연히 맞는 경우가 많아서 제출 뒤에 틀린다. `Math.max(...arr)`는 배열 원소를 함수 인자로 펼치는데, 인자가 많으면 스택 한계에 걸린다. 이 머신에서는 20만 개에서 RangeError가 났다. 크기가 큰 배열은 반복문이나 `reduce`로 구한다.

이 밖에 반복문 안의 `shift()`가 O(n)이라 BFS 큐가 O(n²)이 되는 문제는 [스택, 큐, 덱](/posts/ds-stack-queue-deque)에서, `includes`와 스프레드 복사처럼 숨은 반복문은 [Big O 표기법](/posts/big-o-notation)에서, 재귀 깊이가 수천에서 끊기는 문제는 [재귀와 백트래킹](/posts/recursion-backtracking)과 [그래프 글](/posts/ds-graph-bfs-dfs)에서 실제 숫자로 다뤘다.

## 이 지도로 공부하는 순서

처음이라면 복잡도를 세는 법([Big O 표기법](/posts/big-o-notation))부터 시작한다. 그다음 배열과 해시맵으로 두 포인터, 슬라이딩 윈도, 누적 합, "본 적 있나" 패턴을 익힌다([배열과 행렬](/posts/ds-array-matrix), [해시맵](/posts/ds-hash-map)). 여기까지가 면접 문제의 절반쯤을 덮는다.

이어서 [정렬 알고리즘](/posts/sorting-algorithms)과 [이분 탐색](/posts/binary-search)으로 "정렬하면 생기는 성질"을 익히고, [스택, 큐, 덱](/posts/ds-stack-queue-deque)과 [힙](/posts/ds-heap)으로 순서를 다루는 구조를 본다. 트리와 그래프([이진 트리](/posts/ds-binary-tree-bst), [그래프와 BFS·DFS](/posts/ds-graph-bfs-dfs), [유니온 파인드](/posts/ds-union-find), [트라이](/posts/ds-trie))로 재귀적인 사고에 익숙해지면 [재귀와 백트래킹](/posts/recursion-backtracking)이 자연스럽다.

마지막이 최적화 문제다. [동적 계획법](/posts/dynamic-programming)에서 상태를 정의하는 연습을 하고, [그리디 알고리즘](/posts/greedy-algorithms)에서 그 상태를 하나로 줄여도 되는 조건을 본다. 대규모 시스템에서 쓰이는 확률적 자료구조와 분산 알고리즘(블룸 필터, 일관 해싱, Raft 등)은 [For System Design](/topics/programming/algorithms/system-design) 토픽에 따로 모았다.

## 면접에서 나올 만한 질문

### 처음 보는 알고리즘 문제를 받으면 무엇부터 하나요?

입력 크기와 조건부터 확인한다. n의 상한으로 허용되는 복잡도를 정하면 후보 기법이 크게 줄어든다. 1초에 기본 단계 10⁸번 정도를 예산으로 잡으면 n ≤ 10⁵에서 O(n²)는 탈락이다. 그다음 음수, 중복, 빈 입력, 답이 없을 때의 반환값을 묻고, 완전 탐색과 그 복잡도를 먼저 말한다.

### 완전 탐색부터 말하는 게 왜 도움이 되나요?

느린 풀이에서 반복되는 계산을 짚으면 그게 더 빠른 기법의 근거가 되기 때문이다. 최소 길이 부분 배열 문제에서 "시작점이 오른쪽으로 가면 끝점도 오른쪽으로만 간다"는 관찰이 이분 탐색과 슬라이딩 윈도로 이어진다. 또 완전 탐색은 나중에 빠른 풀이를 검증하는 정답지로도 쓴다.

### 슬라이딩 윈도가 성립하려면 어떤 조건이 필요한가요?

창을 넓히면 조건이 한쪽으로만 변하는 단조성이 필요하다. 값이 모두 양수면 창을 넓힐수록 합이 커지니 합이 넘친 순간 왼쪽을 당기면 된다. 음수가 섞이면 넓혀도 합이 줄 수 있어서 창 밀기가 틀린다. 그때는 누적 합과 해시맵이나 정렬된 구조를 쓴다.

### 답을 이분 탐색한다는 건 무슨 뜻인가요?

최솟값이나 최댓값을 직접 구하는 대신, 후보 값 하나를 정하고 "이 값으로 되나"를 판정하며 범위를 반씩 줄이는 방법이다. 어떤 값에서 되면 그보다 큰 값에서도 된다는 단조성이 있어야 한다. 바나나 문제에서 속도 범위가 10⁹이어도 판정 30번이면 끝난다.

### DP와 그리디와 백트래킹은 어떻게 구분하나요?

모든 경우를 실제로 나열해야 하면 백트래킹이고, 나열 대신 최솟값이나 개수만 필요하면서 같은 상태가 반복되면 DP다. DP 중에서 매 단계 선택지가 하나로 정해진다는 근거(교환 논증)가 있으면 그리디로 줄일 수 있다. 근거가 없으면 작은 입력에서 그리디와 완전 탐색을 비교해 반례부터 찾는다.

### 이분 탐색의 가운데를 비트 시프트로 구해도 되나요?

배열 인덱스처럼 값이 21억 미만이면 괜찮지만, 답 이분 탐색처럼 범위가 크면 안 된다. 비트 연산자가 32비트 정수로 잘라서 30억과 40억의 중간이 -794967296이 된다. 범위가 크면 Math.floor((lo + hi) / 2)를 쓰고, 자바스크립트 숫자는 2⁵³까지 정확하니 그 덧셈은 안전하다.

### 시간 초과가 났는데 복잡도는 맞는 것 같으면 무엇을 보나요?

숨은 반복문과 상수부터 본다. 반복문 안의 shift, includes, 스프레드 복사가 O(n)이라 전체가 O(n²)이 되는 경우가 많다. 비교 함수 없는 sort처럼 결과가 틀려서 무한히 도는 경우도 있다. 그다음 재귀 깊이와 Map 같은 무거운 연산의 횟수를 세어 보고, 같은 머신에서 입력 크기를 두 배씩 늘려 시간이 어떻게 변하는지 재 본다.
