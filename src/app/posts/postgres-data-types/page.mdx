서점의 장바구니 합계를 확인하다가 이상한 숫자를 봤다. 0.1달러짜리 쿠폰 열 장을 더했더니 1이 아니라 `0.9999999999999999`가 나온다. 같은 날 다른 화면에서는 오전 9시에 들어온 주문이 오후 6시 주문으로 찍혀 있다. 정확히 9시간 차이다.

두 문제 모두 버그처럼 보이지만 원인은 컬럼 타입이다. 돈을 `double precision`에 넣었고, 시간을 시간대 없는 `timestamp`로 다뤘다. 타입은 테이블을 만들 때 한 번 고르고 나면 바꾸기가 번거롭다. 행이 수천만 개가 된 뒤에 `ALTER COLUMN ... TYPE`을 하면 테이블 전체를 다시 쓰면서 그동안 잠금이 걸린다. 그래서 처음 고를 때 이유를 알고 고르는 게 낫다. 이 글은 숫자, 문자열, 시간, UUID, 배열, enum, 범위 타입을 차례로 보면서 언제 무엇을 쓰는지 정리한다.

기준은 Ubuntu 24.04의 PostgreSQL 16(16.15)이고, 출력은 모두 실제로 돌린 결과다. 예제는 [설치 글](/posts/postgres-getting-started)에서 만든 서점 DB `shop`(`users`, `books`, `orders`, `order_items`)을 그대로 쓴다. MySQL 8과 다른 부분은 그때그때 짧게 적는다.

## 0.1을 열 번 더하면 1이 아니다

`real`(4바이트)과 `double precision`(8바이트, `float8`)은 부동소수점 타입이다. 숫자를 2진수 분수로 저장하는데, 0.1은 2진수로 딱 떨어지지 않는다(10진수에서 1/3이 0.333…으로 끝나지 않는 것과 같다). 그래서 가장 가까운 근삿값이 저장되고, 더할수록 오차가 쌓인다.

```sql
-- 부동소수점과 numeric으로 0.1 + 0.2
SELECT 0.1::float8 + 0.2::float8 AS f,
       0.1::numeric + 0.2::numeric AS n,
       0.1::float8 + 0.2::float8 = 0.3 AS eq;

-- 0.1을 열 줄 넣고 합계
CREATE TABLE cart_float (price double precision);
INSERT INTO cart_float SELECT 0.1 FROM generate_series(1, 10);
SELECT sum(price), sum(price) = 1 AS is_one FROM cart_float;
```

```text
          f          |  n  | eq
---------------------+-----+----
 0.30000000000000004 | 0.3 | f
(1 row)

        sum         | is_one
--------------------+--------
 0.9999999999999999 | f
(1 row)
```

`=` 비교가 거짓이 된다는 게 더 위험하다. "결제 금액이 주문 합계와 같은가"를 검사하는 코드가 조용히 틀린다. 반올림도 믿을 수 없다. 1.005를 100배 하면 `100.5`가 아니라 `100.49999999999999`가 돼서 반올림하면 100이 나온다.

```sql
SELECT 1.005::float8 * 100        AS f100,
       round(1.005::float8 * 100)  AS rounded,     -- 101이어야 할 것 같지만
       round(1.005::numeric * 100) AS n_rounded;
```

```text
        f100        | rounded | n_rounded
--------------------+---------+-----------
 100.49999999999999 |     100 |       101
(1 row)
```

`numeric`은 10진수 자릿수를 그대로 저장하는 타입이라 이런 일이 없다. `numeric(12, 2)`처럼 전체 자릿수(precision)와 소수 자릿수(scale)를 정하면 소수 셋째 자리는 반올림하고, 범위를 넘으면 에러를 낸다.

```sql
SELECT 12.345::numeric(5,2);      -- 소수 둘째 자리까지 반올림 → 12.35
SELECT 123456.7::numeric(5,2);    -- 정수부가 3자리를 넘는다
```

```text
ERROR:  numeric field overflow
DETAIL:  A field with precision 5, scale 2 must round to an absolute value less than 10^3.
```

정리하면 돈, 수량, 세율처럼 정확해야 하는 값은 `numeric`, 원화처럼 소수점이 없는 화폐는 그냥 `integer`나 `bigint`(원 단위)를 쓴다. 서점의 `books.price`가 `integer`인 이유다. 달러처럼 센트가 있으면 센트 단위 정수로 저장하는 방법도 흔하다. `float8`은 측정값, 좌표, 점수처럼 근삿값이어도 되고 계산이 빨라야 하는 곳에 쓴다. `numeric` 계산은 정수나 부동소수점보다 느리지만 웹 서비스의 금액 계산에서 문제가 될 정도는 드물다.

`money`라는 타입도 있는데 쓰지 않는 편이 낫다. 출력 형식이 서버의 `lc_monetary` 설정을 따라서, 설정이 다른 서버로 덤프를 옮기면 값이 다르게 해석될 수 있다.

## 정수는 범위를 넘으면 에러가 난다

정수는 세 가지다. `smallint`(2바이트, ±3만 2천), `integer`(4바이트, ±21억), `bigint`(8바이트, ±922경). 범위를 넘으면 조용히 넘치지 않고 에러를 낸다.

```sql
SELECT 2147483647 + 1;            -- integer의 최댓값 + 1
SELECT 2147483647::bigint + 1;
SELECT 10 / 4 AS int_div, 10 / 4.0 AS num_div;
```

```text
ERROR:  integer out of range

  ?column?
------------
 2147483648
(1 row)

 int_div |      num_div
---------+--------------------
       2 | 2.5000000000000000
(1 row)
```

정수끼리 나누면 소수점 아래를 버린다는 것도 같이 봐 둔다. 평균이나 비율을 계산할 때 한쪽을 `numeric`으로 바꾸지 않으면 0이 나온다.

기본 키는 처음부터 `bigint`를 권한다. `integer`의 21억은 멀어 보이지만, 로그나 이벤트 테이블은 생각보다 빨리 닿는다. 닿은 다음 `bigint`로 바꾸려면 테이블과 그 키를 참조하는 모든 외래 키 컬럼을 다시 써야 한다. 행 하나당 4바이트 아끼자고 질 위험이 아니다.

### serial 대신 identity

자동 증가 키를 만드는 방법은 두 가지다. 오래된 방식이 `serial`/`bigserial`이고, PostgreSQL 10부터는 SQL 표준인 identity 컬럼(`GENERATED ... AS IDENTITY`)이 있다. 서점 테이블은 모두 identity로 만들었다.

`serial`은 진짜 타입이 아니라 "시퀀스를 하나 만들고 기본값을 `nextval()`로 걸어 주는" 줄임말이다. 그래서 기본값을 무시하고 값을 직접 넣어도 아무도 막지 않는다. 시퀀스는 그 사실을 모르니 나중에 같은 번호를 낸다.

```sql
CREATE TABLE coupons_serial (id serial PRIMARY KEY, code text);
INSERT INTO coupons_serial (id, code) VALUES (1, 'HAND');   -- 직접 1을 넣는다
INSERT INTO coupons_serial (code) VALUES ('AUTO');          -- 시퀀스는 1을 낸다
```

```text
INSERT 0 1
ERROR:  duplicate key value violates unique constraint "coupons_serial_pkey"
DETAIL:  Key (id)=(1) already exists.
```

데이터를 옮기거나 테스트 데이터를 넣다가 이렇게 시퀀스와 실제 값이 어긋나는 일이 흔하다. `GENERATED ALWAYS AS IDENTITY`는 처음부터 직접 넣는 것을 막는다. 정말 필요하면 `OVERRIDING SYSTEM VALUE`를 명시해야 한다.

```sql
INSERT INTO books (id, title, author, price) VALUES (100, '직접 넣은 id', 'x', 1000);
```

```text
ERROR:  cannot insert a non-DEFAULT value into column "id"
DETAIL:  Column "id" is an identity column defined as GENERATED ALWAYS.
HINT:  Use OVERRIDING SYSTEM VALUE to override.
```

`GENERATED BY DEFAULT AS IDENTITY`는 직접 넣는 걸 허용한다(이때는 `serial`과 같은 문제가 생긴다). 그 밖에도 identity는 시퀀스 권한이 컬럼에 묶여 따라가고, `CREATE TABLE ... (LIKE ...)`로 복사할 때 시퀀스를 공유하는 실수가 없다. 새 테이블은 identity를 쓴다.

어느 쪽이든 번호에는 빈칸이 생긴다. 시퀀스는 트랜잭션이 롤백돼도 되돌아가지 않는다. 동시에 들어오는 트랜잭션들이 서로 기다리지 않게 하려고 일부러 그렇게 만들었다. "주문 번호가 빠짐없이 이어져야 한다"는 요구는 시퀀스로 풀 수 없고, 별도 채번 테이블과 잠금이 필요하다.

```sql
BEGIN;
INSERT INTO books (title, author, price) VALUES ('롤백될 책', 'x', 1000) RETURNING id;  -- 5
ROLLBACK;
INSERT INTO books (title, author, price) VALUES ('다음 책', 'x', 1000) RETURNING id;    -- 6. 5는 건너뛴다
```

## varchar(n)이 text보다 빠르지 않다

PostgreSQL의 문자열 타입은 `text`, `varchar(n)`, `char(n)` 세 가지다. 다른 DB에서 온 습관 때문에 `varchar(255)`를 많이 쓰는데, PostgreSQL에서는 셋 다 내부적으로 같은 가변 길이 구조로 저장한다. 공식 문서도 셋 사이에 성능 차이가 없다고 적고, `varchar(n)`은 길이 검사를 하는 만큼 아주 조금 더 일을 할 뿐이다.

차이는 제약뿐이다. `varchar(n)`은 n글자(바이트가 아니라 글자)를 넘으면 거절한다. 그런데 명시적으로 형 변환하면 에러 없이 잘라 버린다. 같은 값인데 넣는 방법에 따라 결과가 다르다.

```sql
CREATE TABLE t_vc (v varchar(5));
INSERT INTO t_vc VALUES ('hello world');         -- 거절
INSERT INTO t_vc VALUES ('안녕하세요');           -- 한글 5글자 = 15바이트지만 통과
SELECT v, length(v), octet_length(v) FROM t_vc;
SELECT 'hello world'::varchar(5);                -- 형 변환은 조용히 자른다
```

```text
ERROR:  value too long for type character varying(5)
INSERT 0 1
     v      | length | octet_length
------------+--------+--------------
 안녕하세요 |      5 |           15
(1 row)

 varchar
---------
 hello
(1 row)
```

`char(n)`은 모자란 자리를 공백으로 채워 저장하고, 비교할 때는 뒤 공백을 무시한다. 그래서 공간만 더 쓰고 헷갈리는 동작이 생긴다. 고정 길이 코드라도 쓰지 않는다.

```sql
SELECT 'ab'::char(5) || '|'             AS char_concat,  -- 연결하면 공백이 사라진다
       length('ab'::char(5))           AS char_len,
       octet_length('ab'::char(5))     AS bytes,        -- 저장은 5바이트
       'ab'::char(5) = 'ab   '::char(5) AS same;
```

```text
 char_concat | char_len | bytes | same
-------------+----------+-------+------
 ab|         |        2 |     5 | t
(1 row)
```

그래서 PostgreSQL에서는 길이 제한이 업무 규칙일 때(예: 상품 코드 최대 20자)만 `varchar(n)`이나 `text` + `CHECK (char_length(code) <= 20)`을 쓰고, 나머지는 그냥 `text`를 쓴다. 나중에 제한을 바꿀 때 `CHECK`가 더 편하다. `varchar(n)`의 n을 늘리는 건 테이블을 다시 쓰지 않지만 줄이는 건 다시 쓴다. MySQL 8은 행 크기 한도(65,535바이트)를 선언한 최대 길이로 계산하는 등 `VARCHAR` 길이가 실제로 영향을 주는 곳이 있다. 그 습관을 PostgreSQL에 그대로 가져올 필요는 없다.

`boolean`은 `true`/`false`/`NULL` 세 값이고 1바이트다. 입력은 `'yes'`, `'on'`, `'t'`, `'1'`도 받지만 출력은 `t`/`f`다. MySQL 8의 `BOOLEAN`은 `TINYINT(1)`의 별칭이라 2나 -1도 들어간다.

## 오전 9시 주문이 오후 6시로 보인다

이제 9시간 문제다. PostgreSQL에는 날짜와 시간을 담는 타입이 여럿 있는데, 실무에서 고민할 건 둘이다.

- `timestamp`(정식 이름 `timestamp without time zone`): 벽에 걸린 시계에 적힌 날짜와 시각만 저장한다. 어느 시간대의 9시인지는 모른다.
- `timestamptz`(`timestamp with time zone`): 전 세계에서 하나뿐인 "순간"을 저장한다. 내부에는 UTC 기준으로 저장하고, 보여 줄 때 세션의 `TimeZone` 설정에 맞춰 바꿔서 보여 준다. 이름과 달리 시간대 자체를 저장하지 않는다.

둘 다 8바이트다. 아래 그림에서 다음을 누르면, 한국 시각으로 9시를 의도한 값이 어떻게 18시가 되는지 나온다.

직접 해 보면 이렇다. 두 컬럼에 같은 문자열을 넣고, 세션 시간대만 바꿔서 다시 읽는다.

```sql
CREATE TABLE time_test (label text, ts timestamp, tstz timestamptz);

SET TimeZone = 'UTC';                      -- 서버 기본값이 UTC인 상황
INSERT INTO time_test VALUES ('앱 서버가 보낸 값', '2026-10-17 09:00',    '2026-10-17 09:00');
INSERT INTO time_test VALUES ('오프셋 포함',       '2026-10-17 09:00+09', '2026-10-17 09:00+09');
SELECT * FROM time_test;

SET TimeZone = 'Asia/Seoul';               -- 보는 쪽 세션만 바꾼다
SELECT * FROM time_test;
```

```text
       label       |         ts          |          tstz
-------------------+---------------------+------------------------
 앱 서버가 보낸 값 | 2026-10-17 09:00:00 | 2026-10-17 09:00:00+00
 오프셋 포함       | 2026-10-17 09:00:00 | 2026-10-17 00:00:00+00
(2 rows)

       label       |         ts          |          tstz
-------------------+---------------------+------------------------
 앱 서버가 보낸 값 | 2026-10-17 09:00:00 | 2026-10-17 18:00:00+09
 오프셋 포함       | 2026-10-17 09:00:00 | 2026-10-17 09:00:00+09
(2 rows)
```

볼 곳은 두 군데다. `tstz` 열은 시간대를 바꾸자 표시가 바뀌었다. 저장된 순간은 그대로이고 보여 주는 방식만 바뀐 것이다. 오프셋을 붙여 보낸 두 번째 줄은 서울에서 정확히 9시로 보인다. 반대로 `ts` 열은 `+09`를 붙여 보냈는데도 오프셋을 버리고 `09:00`만 남겼다. 이 값이 어느 나라의 9시였는지는 이제 아무도 모른다.

그래서 규칙은 이렇다.

1. 실제로 일어난 순간(주문 시각, 가입 시각, 로그)은 `timestamptz`에 저장한다.
2. 앱에서 보낼 때는 오프셋이 붙은 값(`2026-10-17T09:00:00+09:00`)이나 드라이버의 날짜 객체를 쓴다. 오프셋 없는 문자열을 만들지 않는다.
3. 커넥션마다 `TimeZone`을 명시하거나, 서버나 DB에 기본값을 정한다(`ALTER DATABASE shop SET TimeZone = 'Asia/Seoul'`).

`timestamp`가 맞는 곳도 있다. "매일 현지 시각 오전 9시에 알림" 같은 반복 일정은 특정 순간이 아니라 벽시계 시각이 의미라서 `timestamp`나 `time`에 시간대 이름을 따로 저장한다. MySQL 8의 `DATETIME`은 PostgreSQL의 `timestamp`와 같은 성질이고, `TIMESTAMP`는 세션 `time_zone` 기준으로 UTC로 바꿔 저장하지만 2038년 1월 19일까지만 담는다.

### 일별 매출은 어느 나라의 하루인가

`timestamptz`를 잘 썼어도 날짜로 자를 때 한 번 더 틀린다. `::date`는 세션 시간대 기준으로 날짜를 자른다. 서버가 UTC면 한국 시각 오전 8시 15분 주문이 전날 매출로 잡힌다.

```sql
SET TimeZone = 'UTC';
SELECT id,
       ordered_at::date                              AS utc_day,     -- 세션(UTC) 기준 날짜
       (ordered_at AT TIME ZONE 'Asia/Seoul')::date  AS seoul_day,   -- 서울 벽시계로 바꾼 뒤 날짜
       date_trunc('day', ordered_at, 'Asia/Seoul')   AS seoul_midnight
FROM orders ORDER BY id;
```

```text
 id |  utc_day   | seoul_day  |     seoul_midnight
----+------------+------------+------------------------
  1 | 2026-10-10 | 2026-10-10 | 2026-10-09 15:00:00+00
  2 | 2026-10-11 | 2026-10-11 | 2026-10-10 15:00:00+00
  3 | 2026-10-11 | 2026-10-12 | 2026-10-11 15:00:00+00
(3 rows)
```

3번 주문(서울 10월 12일 08:15)이 UTC 기준으로는 11일이다. `AT TIME ZONE`은 `timestamptz`를 그 시간대의 벽시계 시각(`timestamp`)으로 바꾼다. `date_trunc`의 세 번째 인자(PostgreSQL 12부터)는 그 시간대의 자정을 `timestamptz`로 돌려준다. 서울 자정이 UTC로는 전날 15시라는 게 보인다. 통계 쿼리는 세션 설정에 기대지 말고 시간대를 쿼리에 직접 적는 편이 안전하다.

### interval은 달력을 따른다

`interval`은 기간이다. `1 day`와 `24 hours`는 같아 보이지만 다르다. `interval`은 월, 일, 초를 따로 저장하고 달력 규칙으로 더한다.

```sql
SELECT date '2026-01-31' + interval '1 month'                     AS plus_month,
       date '2026-01-31' + interval '1 month' + interval '1 month' AS twice,
       date '2026-01-31' + interval '2 months'                    AS plus_2months;

-- 미국 동부는 2026-03-08에 서머타임이 시작된다
SET TimeZone = 'America/New_York';
SELECT timestamptz '2026-03-07 12:00' + interval '1 day'    AS plus_1day,
       timestamptz '2026-03-07 12:00' + interval '24 hours' AS plus_24h;
```

```text
     plus_month      |        twice        |    plus_2months
---------------------+---------------------+---------------------
 2026-02-28 00:00:00 | 2026-03-28 00:00:00 | 2026-03-31 00:00:00
(1 row)

       plus_1day        |        plus_24h
------------------------+------------------------
 2026-03-08 12:00:00-04 | 2026-03-08 13:00:00-04
(1 row)
```

1월 31일에 한 달을 더하면 2월 28일이다. 한 달씩 두 번 더하면 3월 28일, 두 달을 한 번에 더하면 3월 31일이다. 월 구독의 다음 결제일을 "지난 결제일 + 1달"로 계속 계산하면 날짜가 점점 앞으로 밀린다. 첫 결제일을 기준으로 n달을 더해야 한다. 서머타임이 있는 시간대에서는 `1 day`가 벽시계 기준 같은 시각, `24 hours`가 정확히 24시간 뒤라서 결과가 한 시간 다르다. 한국은 서머타임이 없어서 서울 시간대만 쓰면 이 차이를 볼 일이 없지만, 해외 사용자가 있으면 만난다.

하나 더. `now()`는 지금 시각이 아니라 트랜잭션이 시작된 시각이다. 한 트랜잭션 안에서 몇 번을 불러도 같은 값이 나와서, 같은 트랜잭션에서 넣은 행들이 같은 시각을 갖는다. 실제 벽시계가 필요하면 `clock_timestamp()`를 쓴다.

## UUID 키는 순서가 있어야 인덱스가 편하다

여러 서버가 DB에 묻지 않고 키를 만들어야 하거나, URL에 순번(`/orders/3`)을 드러내고 싶지 않을 때 `uuid`를 쓴다. 16바이트 고정 길이 타입이다. 문자열로 저장하면 37바이트가 되고 비교도 느리니 `text`에 넣지 않는다. PostgreSQL 13부터 확장 없이 `gen_random_uuid()`로 버전 4(무작위) UUID를 만든다.

문제는 무작위라는 점이다. B-tree 인덱스는 값을 정렬해서 잎 페이지에 담는데([인덱스 글](/posts/db-index)), 무작위 키는 들어갈 자리가 인덱스 전체에 흩어진다. 새 행이 들어올 때마다 아무 잎 페이지나 메모리로 읽어 와서 고쳐야 한다. 페이지가 차면 반으로 쪼개지니 인덱스도 커진다. 아래 그림에서 다음을 누르면 차이가 보인다.

UUID 버전 7(RFC 9562)은 앞 48비트에 밀리초 단위 유닉스 시각을, 나머지에 무작위 비트를 넣는다. 시간순으로 커지니 인덱스 끝에 붙는다. PostgreSQL 18부터는 `uuidv7()`이 기본으로 있다. 16에는 없어서 아래처럼 SQL 함수로 흉내 낼 수 있다. `gen_random_uuid()`가 만든 v4의 앞 6바이트를 현재 시각으로 덮고, 버전 비트를 7로 바꾼다.

```sql
CREATE FUNCTION uuid_v7() RETURNS uuid AS $$
  SELECT encode(
    set_bit(set_bit(                                      -- 버전 비트 0100(4) → 0111(7)
      overlay(uuid_send(gen_random_uuid())                -- v4의 16바이트에서
              placing substring(int8send((extract(epoch FROM clock_timestamp()) * 1000)::bigint) FROM 3)
              FROM 1 FOR 6),                              -- 앞 6바이트를 밀리초 시각으로 덮는다
      52, 1), 53, 1),
    'hex')::uuid;
$$ LANGUAGE sql VOLATILE;

SELECT gen_random_uuid() AS v4, uuid_v7() AS v7;
```

```text
                  v4                  |                  v7
--------------------------------------+--------------------------------------
 4873360b-76f7-47ea-801e-d28cf1dc2f27 | 01a14aa8-473d-7f33-8a68-52710f26b641
(1 row)
```

v7의 `01a14aa8-473d`가 밀리초 시각이고, 세 번째 묶음이 `7`로 시작한다. 이제 키만 다른 테이블 세 개(`bigint` identity, v4, v7, 각각 `(id, n int)`)에 100만 행씩 채워 두고, 10만 건씩 더 넣으면서 `EXPLAIN (ANALYZE, BUFFERS)`로 읽은 페이지 수를 본다. 실제 서비스에서 인덱스가 메모리보다 큰 상황을 흉내 내려고 이 실습용 클러스터만 `shared_buffers`를 16MB로 줄였다. v7 키는 실제 서비스처럼 밀리초마다 하나씩 생긴다고 치고, 시각을 인자로 받는 같은 함수 `uuid_v7_at(t)`로 1밀리초씩 늘려 만들었다.

```sql
-- v4: 무작위 키 10만 건
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
INSERT INTO ids_v4 SELECT gen_random_uuid(), g FROM generate_series(1, 100000) g;

-- v7: 시간순 키 10만 건
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
INSERT INTO ids_v7 SELECT uuid_v7_at(timestamptz '2026-10-02' + g * interval '1 millisecond'), g
FROM generate_series(1, 100000) g;
```

```text

   Buffers: shared hit=341742 read=60442 dirtied=61581 written=60009, temp read=171 written=171
 ...
 Execution Time: 1273.837 ms

 Insert on ids_v7 (actual time=393.521..393.522 rows=0 loops=1)
   Buffers: shared hit=203580 read=11 dirtied=1026 written=1855, temp read=171 written=171
 ...
 Execution Time: 394.116 ms
```

볼 숫자는 `Buffers` 줄의 `read`와 `dirtied`다. v4는 메모리에 없는 페이지를 60,442번 읽어 오고(`read`) 61,581페이지를 고쳤다(`dirtied`). 10만 건을 넣는데 거의 한 건에 한 페이지씩이다. v7은 11페이지를 읽고 1,026페이지만 고쳤다. 시간도 1.27초와 0.39초로 차이가 난다(v7 쪽 시간에는 SQL 함수 호출 비용이 섞여 있다). 고친 페이지는 결국 디스크에 써야 하고, 체크포인트 뒤 처음 고친 페이지는 WAL에 페이지 전체를 남기니 쓰기량 차이는 더 커진다. 처음 100만 건을 넣은 뒤의 인덱스 크기도 다르다.

```text
     relname     | size  | pages
-----------------+-------+-------
 ids_bigint_pkey | 21 MB |  2745
 ids_v4_pkey     | 38 MB |  4826
 ids_v7_pkey     | 30 MB |  3853
(3 rows)
```

`bigint`가 가장 작은 건 키가 8바이트라서다. 같은 16바이트인 v4와 v7의 차이 8MB는 페이지 분할로 생긴 빈 공간이다. 한 가지 주의할 점이 있다. 위의 단순한 `uuid_v7()`은 같은 밀리초 안에서 나머지가 무작위라서, 한 문장으로 100만 건을 몰아 넣었더니(밀리초마다 200건 정도) 오히려 v4보다 큰 42MB가 됐다. 같은 밀리초 안에서도 순서를 지키려면 밀리초 아래 시각이나 카운터를 넣는 구현이 필요하다. 18의 `uuidv7()`은 밀리초 아래 시각을 함께 넣어 한 세션 안에서는 순서가 늘어나게 만든다고 알려져 있는데, 세부 동작은 버전 노트에서 확인하고 쓰는 게 좋다.

그러면 무엇을 고르나. DB 하나가 키를 만들면 되는 내부 테이블은 `bigint` identity가 가장 작고 빠르다. 키를 클라이언트나 여러 서비스에서 미리 만들어야 하거나 외부에 노출되는 id라면 UUID v7을 쓴다. v7은 앞부분에서 생성 시각이 드러난다는 점도 알고 쓴다. 정말 아무 정보도 드러내면 안 되는 토큰은 v4가 맞고, 그런 값은 보통 기본 키가 아니다. MySQL 8에는 `uuid` 타입이 없어서 `BINARY(16)`에 `UUID_TO_BIN(uuid, 1)`(시간 부분을 앞으로 옮기는 옵션)로 넣는 방식을 쓴다.

바이너리 데이터는 `bytea`다. `'\xDEADBEEF'::bytea`처럼 16진수로 쓰고, 해시값(`sha256()` 결과)이나 작은 암호화 값을 담기에 알맞다. 이미지나 PDF 같은 큰 파일은 DB 백업과 복제를 무겁게 만드니 오브젝트 스토리지(S3 등)에 두고 경로만 저장한다.

## 배열은 편하지만 관계를 대신하지 않는다

PostgreSQL은 컬럼에 배열을 담을 수 있다. 책에 태그를 붙여 보자.

```sql
ALTER TABLE books ADD COLUMN tags text[] NOT NULL DEFAULT '{}';
UPDATE books SET tags = ARRAY['database','design']     WHERE id = 1;
UPDATE books SET tags = ARRAY['database','postgresql'] WHERE id = 2;
UPDATE books SET tags = ARRAY['database','sql']        WHERE id = 3;
UPDATE books SET tags = ARRAY['programming']           WHERE id = 4;

SELECT id, title, tags FROM books WHERE 'database' = ANY (tags) ORDER BY id;  -- 하나라도 포함
SELECT id, title FROM books WHERE tags @> ARRAY['database','sql'];            -- 둘 다 포함
```

```text
 id |             title             |         tags
----+-------------------------------+-----------------------
  1 | 데이터 중심 애플리케이션 설계 | {database,design}
  2 | PostgreSQL 실무 입문          | {database,postgresql}
  3 | SQL 첫걸음                    | {database,sql}
(3 rows)

 id |   title
----+------------
  3 | SQL 첫걸음
(1 row)
```

배열 인덱스는 1부터 시작한다(`tags[1]`). `@>`(포함), `&&`(겹침) 검색은 GIN 인덱스를 걸면 빨라진다. 이건 [JSONB와 전문 검색 글](/posts/postgres-jsonb-search)에서 자세히 본다.

배열이 맞는 곳은 "행에 딸린 작은 값 목록이고, 원소 하나하나가 다른 테이블을 가리키지 않는" 경우다. 태그 문자열, 허용 IP 목록 정도다. 반대로 주문에 담긴 책 목록을 `book_ids bigint[]`로 두면 문제가 생긴다. 배열 원소에는 외래 키를 걸 수 없어서 없는 책 번호가 들어가도 모른다. 수량이나 산 가격 같은 속성을 붙일 곳도 없다. 원소 하나를 바꿔도 행 전체를 새로 쓴다. 그래서 서점은 `order_items` 테이블을 따로 뒀다. 관계는 테이블로 만든다.

## 주문 상태를 담는 세 가지 방법

`orders.status`에는 `pending`, `paid`, `shipped`, `cancelled`만 들어가야 한다. 지금은 `text`라서 오타(`payed`)도 들어간다. 막는 방법은 세 가지다.

첫째, enum 타입이다. 값 목록을 타입으로 만든다. 4바이트로 저장하고, 정렬은 선언한 순서를 따른다.

```sql
CREATE TYPE order_status AS ENUM ('pending', 'paid', 'shipped', 'cancelled');

ALTER TABLE orders ALTER COLUMN status DROP DEFAULT;                             -- text 기본값을 잠시 떼고
ALTER TABLE orders ALTER COLUMN status TYPE order_status USING status::order_status;
ALTER TABLE orders ALTER COLUMN status SET DEFAULT 'pending';

INSERT INTO orders (user_id, status) VALUES (3, 'refunded');                     -- 목록에 없는 값
SELECT id, status FROM orders WHERE status > 'paid' ORDER BY id;                 -- 선언 순서로 비교
```

```text
ERROR:  invalid input value for enum order_status: "refunded"
LINE 1: INSERT INTO orders (user_id, status) VALUES (3, 'refunded');
                                                        ^
 id | status
----+---------
  3 | shipped
(1 row)
```

값을 추가하기는 쉽다. `ALTER TYPE order_status ADD VALUE 'refunded' AFTER 'shipped'`면 테이블을 다시 쓰지 않는다. 다만 추가한 값은 커밋된 뒤에야 쓸 수 있다. 같은 트랜잭션에서 바로 쓰는 마이그레이션은 실패한다.

```sql
BEGIN;
ALTER TYPE order_status ADD VALUE 'returned';
UPDATE orders SET status = 'returned' WHERE id = 3;
```

```text
ERROR:  unsafe use of new value "returned" of enum type order_status
HINT:  New enum values must be committed before they can be used.
```

빼기는 아예 문법이 없다(`ALTER TYPE ... DROP VALUE`는 `syntax error`). 이름 바꾸기(`RENAME VALUE`)는 되지만, 값을 지우려면 새 타입을 만들어 컬럼을 옮겨야 한다.

둘째, `text` + `CHECK`다. `CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled'))`. 가장 단순하고, 목록을 바꿀 때 제약을 지우고 새로 만들면 된다. 큰 테이블이면 새 제약을 `NOT VALID`로 먼저 걸고 나중에 `VALIDATE CONSTRAINT`로 검사해서 잠금 시간을 줄인다. 값마다 텍스트를 저장하니 enum보다 조금 크다.

셋째, 상태 테이블(`order_statuses`)을 만들고 외래 키로 참조한다. 상태마다 화면 표시 이름, 정렬 순서, "환불 가능 여부" 같은 속성을 붙일 수 있고, 운영자가 화면에서 상태를 추가하는 것도 된다. 대신 조회할 때 조인이 하나 늘어난다.

고르는 기준은 목록이 얼마나 자주 바뀌고, 값에 속성이 붙는가다. 거의 안 바뀌고 순서가 의미 있으면 enum, 가끔 바뀌면 `CHECK`, 속성이 붙거나 운영 중에 바뀌면 테이블이다. MySQL 8의 `ENUM`은 컬럼 정의 안에 목록을 적고, 중간에 값을 넣으면 테이블을 다시 쓸 수 있다는 차이가 있다.

## 같은 방을 두 번 예약하지 못하게

서점에 세미나실이 생겨서 회원이 시간 단위로 예약한다. 같은 방의 예약 시간이 겹치면 안 된다. 앱에서 "겹치는 예약이 있나 조회 → 없으면 INSERT"로 짜면, 두 요청이 동시에 조회하고 둘 다 INSERT하는 경쟁 상태가 생긴다. PostgreSQL에서는 범위 타입과 배제 제약으로 DB가 직접 막는다.

범위 타입은 시작과 끝을 한 값으로 담는다. 시간에는 `tstzrange`(timestamptz 범위)를 쓴다. 배제 제약(exclusion constraint)은 유니크 제약을 일반화한 것이다. 유니크가 "같은 값이 두 행에 있으면 안 된다"라면, 배제 제약은 "지정한 연산자로 비교해서 모두 참인 두 행이 있으면 안 된다"다. 아래 조각을 눌러 보면 제약 한 줄이 어떻게 읽히는지 나온다.

겹친 예약만 거절됐다. 에러 메시지에 어느 예약과 부딪혔는지까지 나온다. 두 요청이 동시에 들어와도 인덱스 수준에서 검사하니 하나는 반드시 실패한다. 앱은 이 에러(SQLSTATE `23P01`)를 받아 "이미 예약된 시간"으로 바꿔 보여 주면 된다. 범위로 검색하는 것도 쉽다.

```sql
-- 16:30에 사용 중인 방
SELECT room, lower(during) AS starts, upper(during) - lower(during) AS length
FROM room_bookings WHERE during @> timestamptz '2026-10-20 16:30';
```

```text
    room    |         starts         |  length
------------+------------------------+----------
 세미나실 A | 2026-10-20 16:00:00+09 | 02:00:00
 세미나실 B | 2026-10-20 15:00:00+09 | 02:00:00
(2 rows)
```

시작이 끝보다 늦은 범위는 넣는 순간 `range lower bound must be less than or equal to range upper bound`로 거절된다. 시작과 끝을 컬럼 두 개로 두면 이 검사도, 겹침 검사도 직접 만들어야 한다. MySQL 8에는 범위 타입과 배제 제약이 없어서 잠금(`SELECT ... FOR UPDATE`)이나 시간 슬롯 테이블에 유니크 제약을 거는 방식으로 푼다.

겹침 판정을 직접 구현해 보자. 범위는 `[시작, 끝, 경계]` 배열로 받는다. 시각은 분 단위 숫자(14:00 = 840), `null`은 끝이 없음(무한), 경계는 `"[)"`, `"[]"`, `"()"`, `"(]"` 중 하나다. 비어 있는 범위(`[600, 600)`처럼 시작과 끝이 같은데 한쪽이라도 미포함)는 아무것과도 겹치지 않는다. 테스트의 기댓값은 같은 범위를 PostgreSQL의 `int4range`로 바꿔 `&&`로 돌린 결과와 같다.

## 도메인, NULL, 기본값, 형 변환

여러 테이블에 같은 규칙이 반복되면 도메인으로 묶는다. 도메인은 기존 타입에 제약을 붙인 새 이름이다.

```sql
CREATE DOMAIN won AS integer CHECK (VALUE >= 0);                       -- 0 이상의 원화
CREATE DOMAIN email_address AS text CHECK (VALUE ~ '^[^@\s]+@[^@\s]+\.[^@\s]+$');

CREATE TABLE newsletter (email email_address PRIMARY KEY, budget won);
INSERT INTO newsletter VALUES ('kim-at-example.com', 10000);
INSERT INTO newsletter VALUES ('lee@example.com', -500);
```

```text
ERROR:  value for domain email_address violates check constraint "email_address_check"
ERROR:  value for domain won violates check constraint "won_check"
```

규칙을 바꿀 때 도메인 하나만 고치면 되니 편하다. 다만 이메일 형식 검사를 정규식으로 완벽하게 할 수는 없으니 DB에서는 이 정도로 거칠게 막고, 진짜 확인은 인증 메일로 한다.

NULL은 "값이 없음" 또는 "모름"이다. 0이나 빈 문자열과 다르고, NULL과의 연산과 비교는 거의 다 NULL이 된다. 그래서 `WHERE col = NULL`은 아무 행도 찾지 못하고 `IS NULL`을 써야 한다. 이런 3값 논리는 [SQL 기초 글](/posts/sql-basics)에 자세히 있다. 타입을 고를 때 할 일은 "이 컬럼에 값이 없는 상태가 업무적으로 의미가 있나"를 정하는 것이다. 의미가 없으면 `NOT NULL`에 적당한 `DEFAULT`를 준다. 서점의 `books.stock`이 `NOT NULL DEFAULT 0`인 이유다.

PostgreSQL 11부터는 `ADD COLUMN ... DEFAULT 상수`가 테이블을 다시 쓰지 않는다. 기본값을 카탈로그에 적어 두고, 예전 행을 읽을 때 채워 준다. 기본값이 `random()`처럼 행마다 달라지는 함수면 모든 행을 다시 써야 한다. 100만 행 테이블에서 비교하면 이렇다.

```sql
\timing on
ALTER TABLE big_orders ADD COLUMN gift_wrap boolean NOT NULL DEFAULT false;                -- 상수
ALTER TABLE big_orders ADD COLUMN coupon_seed double precision NOT NULL DEFAULT random();  -- 행마다 다른 값
```

```text
ALTER TABLE
Time: 1.290 ms
ALTER TABLE
Time: 588.374 ms
```

두 번째 문장은 테이블을 다시 쓰는 동안 `ACCESS EXCLUSIVE` 잠금을 쥐고 있어서, 큰 테이블에서는 그동안 읽기까지 막힌다. 운영 중인 테이블에 컬럼을 더할 때는 기본값이 상수인지 확인한다.

형 변환은 `값::타입` 또는 표준 문법 `CAST(값 AS 타입)`이다. 실수를 정수로 바꾸면 버리지 않고 반올림한다(0.5는 0에서 먼 쪽으로).

```sql
SELECT '42'::int + 1 AS a, CAST('2026-10-17' AS date) AS b, 3.7::int AS c, (-3.5)::int AS d;
SELECT id FROM books WHERE id = '2';            -- 따옴표 리터럴은 컬럼 타입에 맞춰 해석
SELECT id FROM books WHERE id = '2'::text;      -- 이미 text로 정해진 값은 비교 못 한다
```

```text
 a  |     b      | c | d
----+------------+---+----
 43 | 2026-10-17 | 4 | -4
(1 row)

 id
----
  2
(1 row)

ERROR:  operator does not exist: bigint = text
LINE 1: SELECT id FROM books WHERE id = '2'::text;
                                      ^
HINT:  No operator matches the given name and argument types. You might need to add explicit type casts.
```

따옴표만 친 리터럴은 아직 타입이 정해지지 않아서(unknown) 비교 상대에 맞춰 해석된다. 하지만 앱에서 파라미터를 문자열 타입으로 지정해 보내면 마지막 에러를 만난다. MySQL은 이런 경우 암묵적으로 변환해 주는데, 그 과정에서 인덱스를 못 쓰거나 `'abc' = 0`이 참이 되는 일이 생긴다. PostgreSQL은 엄격하게 막는 쪽을 택했다. 반대로 컬럼 쪽을 변환하면(`WHERE id::text = '2'`) 일반 인덱스를 쓰지 못하니, 변환은 항상 상수 쪽에 한다.

## 타입마다 몇 바이트를 쓰나

`pg_column_size()`로 값 하나가 실제로 몇 바이트인지 볼 수 있다. 아래는 테이블에 저장된 값으로 잰 크기다.

```text
smallint 2   integer 4   bigint 8   double precision 8   boolean 1
date 4   timestamptz 8   uuid 16   uuid를 text로 37
numeric 36000 → 7   numeric 123456789.12 → 11
text 'SQL 첫걸음' → 14 (글자 13바이트 + 길이 헤더 1)   같은 값 char(50) → 57
```

가변 길이 타입은 짧은 값이면 길이 헤더가 1바이트, 2KB를 넘으면 압축되거나 TOAST라는 별도 저장소로 빠진다. 행 하나에는 23바이트 헤더가 붙고, 각 컬럼은 타입 크기의 배수 위치에서 시작해야 해서(정렬, alignment) 사이에 빈 바이트가 들어간다. 그래서 컬럼 순서만 바꿔도 크기가 달라진다.

```sql
CREATE TABLE pad_bad  (a boolean, b bigint, c boolean, d bigint, e boolean, f bigint);
CREATE TABLE pad_good (b bigint, d bigint, f bigint, a boolean, c boolean, e boolean);
-- 같은 값으로 10만 행씩 넣은 뒤
SELECT pg_column_size(p.*) AS row_bytes, pg_size_pretty(pg_relation_size('pad_bad')) FROM pad_bad p LIMIT 1;
SELECT pg_column_size(p.*) AS row_bytes, pg_size_pretty(pg_relation_size('pad_good')) FROM pad_good p LIMIT 1;
```

```text
 row_bytes | pg_size_pretty
-----------+----------------
        72 | 7480 kB
(1 row)

 row_bytes | pg_size_pretty
-----------+----------------
        51 | 5888 kB
(1 row)
```

`boolean` 뒤에 `bigint`가 오면 8의 배수 위치까지 7바이트를 비워 둔다. 큰 고정 길이 컬럼(`bigint`, `timestamptz`)을 앞에, 작은 것(`boolean`, `smallint`)과 가변 길이(`text`)를 뒤에 두면 행은 72바이트에서 51바이트로, 테이블은 21% 줄었다. 수억 행짜리 테이블이 아니면 읽기 좋은 순서가 더 중요하니, 새 큰 테이블을 설계할 때만 챙기면 된다.

## 컬럼을 만들 때 묻는 것들

서점 테이블을 다시 보면 타입마다 이유가 있다. 새 컬럼을 만들 때는 이 순서로 묻는다.

- 정확해야 하는 수인가? 돈은 `integer`(원 단위)나 `numeric`, `float`는 근삿값이어도 될 때만.
- 키는 누가 만드나? DB가 만들면 `bigint GENERATED ALWAYS AS IDENTITY`, 밖에서 만들거나 노출되면 UUID v7.
- 실제로 일어난 순간인가? 그렇다면 `timestamptz`, 앱은 오프셋을 붙여 보내고 날짜로 자를 때 시간대를 적는다.
- 길이 제한이 업무 규칙인가? 아니면 그냥 `text`.
- 값 목록이 정해져 있나? 거의 안 바뀌면 enum, 가끔 바뀌면 `CHECK`, 속성이 붙으면 테이블.
- 겹치면 안 되는 구간인가? 범위 타입과 배제 제약.
- 원소가 다른 테이블을 가리키나? 그렇다면 배열이 아니라 테이블.
- 값이 없을 수 있나? 의미가 없으면 `NOT NULL`과 상수 `DEFAULT`.

처음 장면의 두 문제는 이렇게 풀린다. 쿠폰 금액은 센트 단위 정수나 `numeric`으로 바꾸면 합계가 정확히 1이 된다. 9시간 차이는 오프셋 없는 문자열이 UTC 세션에서 해석된 탓이라, 오프셋을 붙여 보내고 커넥션 시간대를 정하면 된다. 다음 글에서는 이 서점 DB에 누가 무엇을 할 수 있는지를 정한다. 앱 계정이 테이블을 `DROP`할 수 있는 상태부터 시작한다.

## 면접에서 나올 만한 질문

### 금액 컬럼에 float를 쓰면 안 되는 이유는요?

부동소수점은 0.1 같은 10진 소수를 2진수로 정확히 표현하지 못해서 근삿값을 저장한다. 0.1을 열 번 더하면 1이 아니라 0.9999999999999999가 되고, 같다 비교와 반올림이 틀린다. 돈은 10진 자릿수를 그대로 저장하는 `numeric`이나, 소수점이 없는 최소 단위(원, 센트)의 정수로 저장한다.

### timestamp와 timestamptz의 차이는요?

`timestamp`는 시간대 정보 없이 벽시계 날짜와 시각만 저장하고, `timestamptz`는 UTC 기준의 한 순간을 저장했다가 세션의 TimeZone에 맞춰 보여 준다. 이름과 달리 `timestamptz`도 시간대 이름을 저장하지는 않는다. 실제로 일어난 사건은 `timestamptz`가 맞다. 오프셋 없는 문자열은 세션 시간대로 해석되니, 앱은 오프셋을 붙여 보내고 일별 집계는 `AT TIME ZONE`이나 `date_trunc`의 시간대 인자로 기준을 명시한다.

### serial과 identity 중 무엇을 쓰나요?

identity를 쓴다. `serial`은 시퀀스와 기본값을 만들어 주는 줄임말이라 직접 넣은 값과 시퀀스가 어긋나 중복 키 에러가 나기 쉽고, 권한이나 테이블 복사에서도 시퀀스가 따로 논다. `GENERATED ALWAYS AS IDENTITY`는 SQL 표준이고 직접 넣는 걸 막는다. 둘 다 롤백된 번호를 되돌리지 않아서 빈 번호는 생긴다.

### UUID를 기본 키로 쓰면 어떤 문제가 있나요?

v4는 완전히 무작위라 B-tree 인덱스의 아무 잎 페이지에나 들어간다. 그래서 인덱스가 메모리보다 커지면 삽입마다 다른 페이지를 읽고 고쳐야 하고, 페이지 분할로 인덱스도 커진다. 실습에서 10만 건을 넣을 때 v4는 shared buffers에 없는 페이지를 6만 번 읽어 왔고 v7은 11번이었다. 앞부분이 시각인 v7을 쓰면 끝에만 붙어서 이 문제가 줄고, 18부터는 `uuidv7()`이 기본 제공된다. DB 안에서만 쓰는 키면 8바이트인 `bigint`가 더 작다.

### PostgreSQL에서 varchar(255)를 쓰는 게 의미가 있나요?

성능으로는 의미가 없다. `text`, `varchar(n)`, `char(n)`은 같은 가변 길이 구조로 저장되고 속도 차이가 없다. 길이 제한이 업무 규칙일 때만 `varchar(n)`이나 `CHECK`를 쓰고, 나머지는 `text`를 쓴다. `char(n)`은 공백을 채워 공간만 더 쓰니 피한다.

### enum, CHECK, 참조 테이블은 어떻게 고르나요?

값 목록이 얼마나 자주 바뀌고 값에 속성이 붙는지로 고른다. enum은 4바이트에 선언 순서로 정렬되지만 값을 뺄 수 없고, 추가한 값은 커밋 뒤에야 쓸 수 있다. `CHECK`는 단순하고 바꾸기 쉽다. 표시 이름이나 정책 같은 속성이 붙거나 운영 중에 바뀌면 참조 테이블과 외래 키가 맞다.

### 회의실 이중 예약은 DB에서 어떻게 막나요?

`tstzrange` 컬럼에 배제 제약 `EXCLUDE USING gist (room WITH =, during WITH &&)`을 건다. 같은 방이면서 시간이 겹치는 두 행을 인덱스 수준에서 거절하니, 앱에서 조회 후 삽입하는 방식의 경쟁 상태가 없다. `text`의 = 비교를 GiST로 하려면 `btree_gist` 확장이 필요하다. 범위는 `[)`로 써서 맞닿은 예약이 겹치지 않게 한다.

### 운영 중인 큰 테이블에 NOT NULL 컬럼을 추가해도 되나요?

기본값이 상수면 된다. PostgreSQL 11부터 상수 기본값은 카탈로그에만 적고 기존 행을 다시 쓰지 않아서 100만 행에서도 1ms 남짓이다. `random()`이나 `clock_timestamp()`처럼 행마다 다른 값이면 테이블 전체를 다시 쓰면서 `ACCESS EXCLUSIVE` 잠금을 쥐니 읽기까지 막힌다. 그런 경우는 NULL 허용으로 추가하고 나눠서 채운 다음 제약을 거는 식으로 단계를 나눈다.
