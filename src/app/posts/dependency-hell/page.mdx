플러그인 하나를 추가하려고 `npm install`을 쳤는데 빨간 글씨가 스무 줄 쏟아진다. `ERESOLVE unable to resolve dependency tree`. 마지막 줄은 `--force`나 `--legacy-peer-deps`로 다시 해 보라고 권한다. 붙여서 돌리면 설치는 된다. 그런데 이게 정말 고친 걸까, 문제를 덮은 걸까.

의존성 지옥은 내 코드가 아니라 남의 패키지들이 서로 다른 버전을 원할 때 생긴다. 이 글은 그 상황이 생기는 모양을 하나씩 직접 만들어 본다. 같은 패키지가 두 벌 깔리는 다이아몬드, node_modules를 평평하게 펴면서 생기는 유령 의존성, peer dependency 충돌과 ERESOLVE, 남의 버전을 강제로 바꾸는 overrides, 그리고 이 모든 결정을 고정하는 lockfile과 `npm ci`까지 간다. 마지막으로 설치가 곧 남의 코드를 실행하는 일이 되는 경로와, 업데이트를 봇에게 맡기는 전략을 본다.

이 주제의 다른 글: 범위 문법(`^`, `~`, 0.x 규칙)과 버전 번호의 약속은 [Semantic Versioning](/posts/semantic-versioning)에서 먼저 다뤘다. 이 글은 그 범위들이 여러 패키지 사이에서 부딪히는 이야기다. CI에서 의존성 설치를 캐시하는 법은 [빌드 캐시 글](/posts/build-caching#의존성-설치는-무엇을-캐시해야-빨라지나)에 있다.

실습은 Ubuntu 24.04, Node.js 22.22.0, npm 10.9.4, pnpm 10.28.0에서 했다. 로컬 사설 레지스트리(Verdaccio 6)에 `@acme/core`, `@acme/ui` 같은 작은 패키지를 직접 올려 상황을 재현했고, 출력은 모두 실제로 돌린 결과다. 긴 작업 경로와 로그 파일 경로만 줄여 적었다.

패키지 매니저는 설치할 때마다 여러 범위를 모두 만족하는 버전 하나가 있는지부터 찾는다. 직접 짜 보자. 기대값은 `semver.maxSatisfying`으로 확인했다.

<CodePlayground

  initialCode={`function pickShared(versions, ranges) {
  // versions: 레지스트리에 있는 정식 버전들 (순서 없음)
  // ranges: 각 패키지가 원하는 범위 ("1.3.1", "^1.2.0", "~1.2.0")
  // 모두를 만족하는 가장 높은 버전, 없으면 null
  // ^는 가장 왼쪽의 0 아닌 자리를 고정, ~는 부 버전까지 고정
  return null;
}`}
  solution={`function pickShared(versions, ranges) {
  const parse = (v) => v.split(".").map(Number);
  const cmp = (a, b) => {
    for (let i = 0; i < 3; i++) if (a[i] !== b[i]) return a[i] - b[i];
    return 0;
  };
  const ok = (v, r) => {
    const op = r[0] === "^" || r[0] === "~" ? r[0] : "";
    const b = parse(r.slice(op.length)), x = parse(v);
    if (op === "") return cmp(x, b) === 0;
    let up;
    if (op === "~") up = [b[0], b[1] + 1, 0];
    else if (b[0] > 0) up = [b[0] + 1, 0, 0];
    else if (b[1] > 0) up = [0, b[1] + 1, 0];
    else up = [0, 0, b[2] + 1];
    return cmp(x, b) >= 0 && cmp(x, up) < 0;
  };
  const hits = versions.filter((v) => ranges.every((r) => ok(v, r)));
  if (!hits.length) return null;
  hits.sort((a, b) => cmp(parse(a), parse(b)));
  return hits[hits.length - 1];
}`}

## node_modules는 왜 평평한가

npm 2까지는 트리를 그대로 폴더로 만들었다. 모든 패키지가 자기 의존성을 자기 폴더 안에 품으니 충돌이 없었다. 대신 같은 패키지가 수십 벌 깔리고 경로가 Windows의 260자 제한을 넘곤 했다. npm 3부터는 가능한 한 최상위로 끌어올린다(호이스팅). Node.js가 모듈을 찾을 때 자기 폴더의 `node_modules`부터 시작해 부모 폴더로 올라가며 찾기 때문에, 최상위에 하나만 두면 모두가 그것을 찾는다.

## 선언하지 않은 패키지를 쓰는 유령 의존성

평평한 node_modules에서는 `package.json`에 적지 않은 패키지도 `require`가 된다. 누군가 리포트 코드에서 core를 바로 불러 썼다.

```js
// report.js: package.json에는 @acme/core가 없다
const { Money, version } = require("@acme/core");
console.log("core", version, typeof Money);
```

이런 걸 유령 의존성(phantom dependency)이라고 부른다. 지금은 돈다. 문제는 무엇을 받을지 우리가 정하지 않았다는 점이다. 같은 코드를 세 상황에서 돌려 봤다.

```bash
# 1) ui와 charts가 다 있을 때
node report.js
# 2) 상관없어 보이는 charts를 지운 직후
npm uninstall @acme/charts && node report.js
# 3) node_modules와 lockfile을 지우고 새로 설치한 뒤
rm -rf node_modules package-lock.json && npm install && node report.js
```

```text
core 2.0.0 function
```

```text
removed 2 packages in 440ms
node:internal/modules/cjs/loader:1386
  throw err;
  ^

Error: Cannot find module '@acme/core'
Require stack:
- ~/v21/dia/report.js
```

```text
added 2 packages in 660ms
core 1.3.1 function
```

charts를 지우자 최상위의 2.0.0이 사라졌고, ui 안쪽에 있던 1.3.1은 그 자리로 올라오지 않았다. 새로 설치하니 이번에는 1.3.1이 최상위로 올라왔다. 코드는 한 줄도 안 바뀌었는데 결과가 "2.0.0 → 모듈 없음 → 1.3.1"로 세 번 달라졌다. 주 버전까지 바뀌었으니 API가 다르다. 이런 버그는 로컬에서는 멀쩡하고 CI의 새 설치에서만 깨지거나, 의존성 정리 PR이 엉뚱한 화면을 망가뜨리는 모양으로 나타난다.

고치는 법은 간단하다. 쓰는 패키지는 직접 의존성으로 적는다. 그리고 다시는 이런 일이 생기지 않게 도구로 막는다. ESLint의 `import/no-extraneous-dependencies`(eslint-plugin-import)나 `n/no-extraneous-require` 규칙이 선언 안 된 import를 잡고, 패키지 매니저 차원에서는 pnpm이 아예 막는다.

## pnpm은 링크로 경계를 세운다

같은 프로젝트를 pnpm으로 설치했다.

```bash

pnpm install
# 최상위에는 무엇이 보이나
ls node_modules/@acme
# 실제 파일은 어디 있나
ls node_modules/.pnpm
readlink node_modules/@acme/ui
# 유령 의존성을 쓰는 코드를 다시 돌린다
node report.js
```

```text

@acme+ui@1.0.0
```

최상위 `node_modules`에는 `package.json`에 적은 ui와 charts만 있다. 실체는 `.pnpm/패키지@버전/node_modules/` 아래에 있고, 최상위의 것은 거기로 가는 심볼릭 링크다. 각 패키지 폴더 옆에는 그 패키지가 선언한 의존성만 링크로 놓인다. 그래서 선언하지 않은 core는 처음부터 찾을 수 없다. 유령 의존성이 설치 직후 바로 드러나니 "나중에 깨지는" 일이 없다. 파일 자체는 컴퓨터 전체가 쓰는 저장소(store)에 한 번만 두고 하드 링크로 연결해서 프로젝트가 여럿이어도 디스크를 한 번만 쓴다.

엄격함에는 비용이 있다. 오래된 패키지 중에는 자기도 선언하지 않은 패키지를 불러 쓰는 것이 있다. pnpm은 이를 위해 `.pnpm/node_modules`에 모든 패키지를 한 번 더 올려 둔다(기본 `hoist-pattern=*`). 패키지끼리는 유령 의존성이 통하고, 우리 앱 코드에서만 막히는 구조다. 그래도 깨지는 도구가 있으면 `.npmrc`의 `public-hoist-pattern`으로 그 패키지만 최상위에 올리고, 최후의 수단으로 `node-linker=hoisted`를 쓰면 npm과 같은 평평한 구조가 된다. React Native처럼 평평한 구조를 기대하는 도구 체인에서 이 설정을 쓰는 경우가 있다.

## peer dependency가 부딪히면 ERESOLVE

다이아몬드에서는 두 벌을 깔아 넘어갔다. 그런데 두 벌이 있으면 안 되는 관계가 있다. 플러그인과 그 플러그인을 꽂는 본체다. React 컴포넌트 라이브러리가 자기만의 React를 따로 깔면 앞에서 본 instanceof 문제가 그대로 생긴다. 그래서 플러그인은 "본체는 당신이 깐 것을 같이 쓰겠다, 단 이 범위여야 한다"고 선언한다. 이게 `peerDependencies`다.

앱은 `@acme/host` 2.0.0을 쓰고, 추가하려는 `@acme/host-plugin`의 최신(latest) 1.0.0은 host `^1.0.0`을 peer로 요구한다.

```bash
# host 2를 쓰는 앱에 host 1용 플러그인을 추가한다
npm install @acme/host-plugin
```

```text
npm error code ERESOLVE
npm error ERESOLVE unable to resolve dependency tree
npm error
npm error While resolving: shop@1.0.0
npm error Found: @acme/host@2.0.0
npm error node_modules/@acme/host
npm error   @acme/host@"^2.0.0" from the root project
npm error
npm error Could not resolve dependency:
npm error peer @acme/host@"^1.0.0" from @acme/host-plugin@1.0.0
npm error node_modules/@acme/host-plugin
npm error   @acme/host-plugin@"*" from the root project
npm error
npm error Fix the upstream dependency conflict, or retry
npm error this command with --force or --legacy-peer-deps
npm error to accept an incorrect (and potentially broken) dependency resolution.
```

이 에러는 읽는 순서가 있다. `Found:`는 지금 트리에 이미 있는 것(host 2.0.0과 그걸 원한 주체), `Could not resolve dependency:`는 그것과 맞지 않는 요구(plugin 1.0.0이 peer로 `^1.0.0`을 원함)다. 두 줄을 맞대 보면 충돌한 범위 두 개가 보인다. npm 7부터 peer dependency를 자동으로 설치하면서 범위를 엄격하게 검사하게 됐고, 그래서 npm 6 시절에는 경고로 지나가던 프로젝트가 npm 7 이후 이 에러로 막히기 시작했다.

```bash
npm view @acme/host-plugin@1.1.0 peerDependencies
# host 2를 지원하는 버전으로 설치한다
npm install @acme/host-plugin@1.1.0
npm ls --all
```

```text
`-- @acme/host@2.0.0
```

`deduped`는 플러그인이 최상위의 host를 같이 쓴다는 뜻이다. 이게 정상적인 해결이다. 그럼 에러 메시지가 권한 두 옵션은 무엇이 다를까. 1.0.0으로 되돌려 각각 돌려 봤다.

```bash
# peer dependency를 아예 무시하고 npm 6처럼 설치한다
npm install @acme/host-plugin --legacy-peer-deps
npm ls --all
```

```text

| `-- @acme/host@2.0.0 deduped invalid: "^1.0.0" from node_modules/@acme/host-plugin
`-- @acme/host@2.0.0 invalid: "^1.0.0" from node_modules/@acme/host-plugin

npm error invalid: @acme/host@2.0.0 ~/v21/peer/node_modules/@acme/host
```

```bash
# 충돌을 경고로 바꾸고 강제로 설치한다
npm install @acme/host-plugin --force
```

```text
npm warn using --force Recommended protections disabled.
npm warn ERESOLVE overriding peer dependency
npm warn While resolving: @acme/host-plugin@1.0.0
npm warn Found: @acme/host@2.0.0
...
npm warn Conflicting peer dependency: @acme/host@1.0.0
```

결과 트리는 같다. 둘 다 플러그인이 지원한다고 한 적 없는 host 2와 함께 돌게 된다. `npm ls`는 `invalid`로 표시하고 종료 코드 1을 낸다. 차이는 범위다. `--legacy-peer-deps`는 peer 검사와 peer 자동 설치를 트리 전체에서 끈다. 그래서 다른 패키지의 peer가 빠져도 조용하다. `--force`는 peer 충돌을 경고로 낮추고, 캐시가 있어도 다시 받는 것처럼 그 밖의 안전장치도 함께 끈다. 어느 쪽이든 한 번 쓰고 끝나지 않는다는 점이 함정이다. 팀원이 `.npmrc`에 `legacy-peer-deps=true`를 넣어 두면 그 뒤로 생기는 모든 peer 충돌이 소리 없이 묻힌다. 써야 한다면 이유와 함께 주석을 달고, 해당 패키지가 고쳐지면 지운다.

pnpm은 같은 상황에서 설치를 막지 않고 경고를 낸다.

```text
 WARN  Issues with peer dependencies found
.
└─┬ @acme/host-plugin 1.0.0
  └── ✕ unmet peer @acme/host@^1.0.0: found 2.0.0
```

CI에서 이 경고를 에러로 만들려면 `strict-peer-dependencies=true`를 켜고, 확인을 마친 조합만 `package.json`의 `pnpm.peerDependencyRules.allowedVersions`로 허용한다. 그러면 "이 충돌은 우리가 보고 괜찮다고 판단했다"는 기록이 코드에 남는다.

## 남의 의존성 버전을 바꾸는 overrides

ui가 원하는 범위가 낡아서 두 벌이 깔리는데, ui 쪽이 실제로는 core 2와도 잘 돈다는 걸 확인했다고 하자. 또는 깊숙한 의존성에 보안 취약점이 나와서 수정 버전으로 당장 바꿔야 한다. 상류가 고칠 때까지 기다릴 수 없을 때 쓰는 것이 overrides다. npm은 `overrides`, pnpm은 `pnpm.overrides`(pnpm 10부터는 `pnpm-workspace.yaml`의 `overrides`도 된다), Yarn은 `resolutions`다.

```json
{
  "dependencies": {
    "@acme/ui": "^1.0.0",
    "@acme/charts": "^1.0.0"
  },
  "overrides": {
    "@acme/core": "2.0.0"
  }
}
```

```bash
# overrides를 반영해 다시 설치하고 트리를 본다
npm install
npm ls --all
node main.js
```

```text
removed 1 package in 538ms
shop@1.0.0 ~/v21/dia-ov
+-- @acme/charts@1.0.0
| `-- @acme/core@2.0.0 overridden
`-- @acme/ui@1.0.0
  `-- @acme/core@2.0.0 deduped

ui uses core 2.0.0 | charts uses core 2.0.0
isMoney(ui.price(100)) = true
```

core가 한 벌이 됐고 instanceof도 참이 됐다. `overridden`과 `deduped` 표시를 보자. ui는 `^1.2.0`이라고 선언했는데 2.0.0을 받고 있다. 이건 ui 작성자가 약속한 적 없는 조합이다. 주 버전을 건너뛰는 override는 반드시 그 패키지의 테스트 경로를 직접 확인하고 쓴다. 범위를 좁히고 싶으면 특정 부모 아래에서만 바꾸는 중첩 형식도 있다(`"@acme/ui": { "@acme/core": "2.0.0" }`).

overrides는 임시 처방이다. 상류가 고친 뒤에도 남아 있으면, 몇 달 뒤 그 패키지가 진짜로 새 버전을 요구할 때 override가 낡은 버전을 계속 박아 넣는다. override 옆에 이유와 이슈 링크를 적고(JSON은 주석이 안 되니 PR 설명이나 별도 문서에), 정기적으로 지울 수 있는지 확인한다.

CI에서 `npm install`을 쓰면 이 검사가 없다. 범위를 다시 계산해서 그날의 최신을 깔고, 로컬에서 테스트한 조합과 다른 것으로 빌드한다. [Semantic Versioning 글](/posts/semantic-versioning#현장에서-버전-때문에-깨지는-순간)의 "코드는 그대로인데 CI가 깨졌다"가 이 경로다. CI와 Docker 빌드는 `npm ci`(pnpm은 `pnpm install --frozen-lockfile`)로 고정한다.

integrity 검사가 실제로 막는 것도 봤다. lockfile의 해시 한 줄을 다른 값으로 바꾸고 캐시가 빈 상태에서 `npm ci`를 돌렸다.


몇 번 다시 받아 본 뒤 멈췄다. 레지스트리나 중간 프록시에서 tarball이 바뀌면 이렇게 잡힌다. 이 에러를 만났을 때 lockfile의 integrity 줄을 지우고 다시 설치하는 건 경고를 끄는 것과 같다. 먼저 레지스트리 주소(`resolved`)가 바뀌지 않았는지, 사내 미러가 다른 내용을 주는지 확인한다.

lockfile은 반드시 커밋한다. 라이브러리도 마찬가지다. 배포되는 패키지에는 `package-lock.json`이 실리지 않아 사용자에게는 영향이 없지만, 라이브러리 자신의 CI가 매번 같은 조합으로 돈다. 브랜치를 합치다 lockfile이 충돌하면 손으로 고치지 않는다. 한쪽 lockfile을 받아들인 뒤 `npm install`을 다시 돌려 npm이 다시 쓰게 한다(npm은 충돌 표시가 있는 lockfile을 읽어 스스로 정리하기도 한다). lockfile을 통째로 지우고 새로 만드는 것은 모든 의존성을 한 번에 올리는 것과 같으니 별도 PR로 한다.

## 설치는 남의 코드를 실행하는 일이다

`npm install`은 파일을 받기만 하지 않는다. 패키지가 `postinstall` 같은 설치 스크립트를 선언하면 내 컴퓨터, 내 CI 러너에서 그 코드를 그대로 실행한다. 레지스트리 계정이 털리거나 이름이 비슷한 가짜 패키지(타이포스쿼팅)를 깔면 그 순간 환경 변수의 토큰과 `~/.npmrc`의 인증 정보가 밖으로 나간다. 2025년 9월에는 chalk, debug 같은 주간 다운로드 수억 회의 패키지가 관리자 계정 피싱으로 악성 버전을 내보낸 일이 있었고, 같은 달 설치 스크립트로 퍼지는 웜(Shai-Hulud)도 나왔다.

npm과 pnpm 10이 설치 스크립트를 다루는 방식이 다르다. 스크립트를 가진 패키지를 각각 설치해 봤다.

```bash
# npm은 기본으로 설치 스크립트를 실행한다
npm i @acme/postinstall-demo --foreground-scripts
```

```text
> @acme/postinstall-demo@1.0.0 postinstall
> node -e "console.log(\"running postinstall\")"

running postinstall

added 1 package in 545ms
```

```bash
# pnpm 10은 허락하지 않은 패키지의 스크립트를 실행하지 않는다
pnpm add @acme/postinstall-demo
```

```text
╭ Warning ─────────────────────────────────────────────────────────────────────╮
│                                                                              │
│   Ignored build scripts: @acme/postinstall-demo@1.0.0.                       │
│   Run "pnpm approve-builds" to pick which dependencies should be allowed     │
│   to run scripts.                                                            │
│                                                                              │
╰──────────────────────────────────────────────────────────────────────────────╯
```

pnpm은 `pnpm approve-builds`로 고른 패키지만 `onlyBuiltDependencies` 목록에 넣고 실행한다. npm에서는 `.npmrc`에 `ignore-scripts=true`를 두고, 네이티브 모듈처럼 꼭 빌드가 필요한 것만 `npm rebuild 패키지 --ignore-scripts=false`로 따로 돌리는 방식이 비슷한 효과를 낸다.

막아야 할 길은 하나 더 있다. 막 올라온 버전을 바로 받지 않는 것이다. 위의 사건들에서 악성 버전은 몇 시간 안에 발견되어 내려갔다. pnpm 10.16부터는 `minimumReleaseAge`(분 단위)로 설치 단계에서 이 창을 피할 수 있다. 레지스트리에 core 1.3.2를 막 올리고, 2분 숙성을 걸어 설치했다.

```bash
# pnpm-workspace.yaml에 숙성 기간 2분을 건다
printf 'minimumReleaseAge: 2\n' > pnpm-workspace.yaml
# 방금 올라온 1.3.2가 범위 안에 있지만 고르지 않는다
pnpm add '@acme/core@^1.3.0'
```

```text
dependencies:
+ @acme/core 1.3.1 (1.3.2 is available)
```

운영에서는 며칠 단위(1440분 = 하루)로 잡는다. 사내 미러와 업데이트 봇에도 같은 정책을 두면 경로가 하나로 모인다.

## 업데이트를 봇에게 맡기는 방법

lockfile로 고정하면 안정적이지만, 손을 놓으면 1년 뒤에는 주 버전 세 개가 밀린 프로젝트가 된다. 그때 한꺼번에 올리면 어떤 변경이 무엇을 깼는지 가릴 수 없다. 그래서 작게 자주 올리고, 그 일을 봇에게 맡긴다. 대표가 Renovate와 Dependabot이다. 둘 다 새 버전이 나오면 package.json과 lockfile을 고친 PR을 열고, 그 PR에서 CI가 돈다.

전략은 위험도에 따라 나눈다. 아래는 Renovate 설정의 예다.

```json
{
  "extends": ["config:recommended"],
  "schedule": ["before 9am on monday"],
  "minimumReleaseAge": "3 days",
  "lockFileMaintenance": { "enabled": true },
  "packageRules": [
    { "matchDepTypes": ["devDependencies"], "matchUpdateTypes": ["minor", "patch"], "groupName": "dev non-major", "automerge": true },
    { "matchPackageNames": ["@acme/**"], "groupName": "acme packages" },
    { "matchUpdateTypes": ["major"], "dependencyDashboardApproval": true }
  ]
}
```

- 개발 도구의 부·수 버전은 묶어서 테스트가 통과하면 자동 머지한다. 이게 PR 수를 줄이는 가장 큰 손잡이다.
- 함께 움직여야 하는 패키지(같은 모노레포의 패키지, `react`와 `react-dom`)는 한 PR로 묶는다. 따로 오면 중간 상태에서 peer 충돌이 난다.
- 주 버전은 대시보드에서 사람이 승인해야 PR이 열린다. 변경 로그를 읽을 사람이 정해져 있어야 한다.
- `minimumReleaseAge`는 앞에서 본 숙성 기간이다. Dependabot에는 2025년에 `cooldown` 옵션이 생겼고, pnpm도 10.16부터 `minimumReleaseAge` 설정으로 설치 단계에서 같은 일을 한다.
- `lockFileMaintenance`는 범위는 그대로 두고 lockfile 안의 간접 의존성만 주기적으로 새로 고친다. 직접 의존성 PR만으로는 깊숙한 의존성이 계속 낡는다.

Dependabot은 GitHub에 붙어 있어 설정이 가볍고(`.github/dependabot.yml`), 보안 알림과 바로 이어진다. Renovate는 묶음, 일정, 자동 머지 규칙이 훨씬 세밀하고 GitLab 같은 다른 플랫폼도 지원한다. 저장소가 하나뿐이면 Dependabot으로 시작해도 충분하고, 모노레포나 저장소가 많아지면 Renovate의 그룹 규칙이 PR 홍수를 줄여 준다.

## 현장에서 의존성이 꼬였을 때

증상별로 먼저 볼 곳이 다르다.

로컬에서는 되는데 CI에서만 `Cannot find module`이 난다. 유령 의존성을 먼저 의심한다. 에러가 난 모듈이 `package.json`에 있는지 보고, 없으면 `npm explain 모듈`로 누가 끌고 왔는지 확인한 뒤 직접 의존성으로 추가한다.

"Invalid hook call"이나 instanceof가 이상하게 거짓이다. 같은 패키지가 두 벌인지 본다. `npm ls react`에서 버전이 둘 이상 나오거나 `deduped`가 아닌 줄이 있으면 그거다. 범위를 맞출 수 있으면 `npm dedupe`, 없으면 패키지를 올리거나 overrides를 검토한다. 모노레포에서 패키지마다 자기 `node_modules`에 React를 따로 가진 경우도 흔하다.

ERESOLVE가 난다. `Found`와 `Could not resolve` 두 줄에서 범위를 뽑고, `npm view 패키지@버전 peerDependencies`로 지원 버전을 찾는다. `--legacy-peer-deps`를 `.npmrc`에 박는 건 마지막 수단이다.

`npm ci`가 EUSAGE로 멈춘다. lockfile 갱신을 빠뜨린 커밋이다. 로컬에서 `npm install`을 돌려 lockfile을 함께 커밋한다. 팀원마다 npm 메이저 버전이 다르면 lockfile 형식이 왔다 갔다 하니 `packageManager` 필드(Corepack)나 `engines`로 버전을 맞춘다.

`npm ls`가 `invalid`나 `ELSPROBLEMS`를 낸다. 강제 설치나 override로 선언 밖의 버전이 들어가 있다는 뜻이다. 의도한 것인지 기록이 있는지 확인한다.

## 범위는 바람이고 lockfile은 결정이다

의존성 지옥은 여러 패키지의 범위가 겹치지 않을 때 생긴다. npm은 두 벌을 깔아 넘어가고, 그 대가로 instanceof와 싱글턴이 쪼개진다. 평평한 node_modules는 디스크를 아끼는 대신 선언하지 않은 패키지를 쓰게 만들고, pnpm은 링크로 그 길을 막는다. 두 벌이 허용되지 않는 본체와 플러그인 사이에서는 peer dependency가 충돌을 ERESOLVE로 드러낸다. 이 모든 결정은 lockfile에 적히고, CI는 `npm ci`로 그 결정만 따른다. 업데이트는 봇이 작은 PR로 가져오게 하고, 막 나온 버전은 조금 기다렸다 받는다.

## 면접에서 나올 만한 질문

### 다이아몬드 의존성이 무엇이고 npm은 어떻게 처리하나요?

두 패키지가 같은 패키지의 서로 다른 버전을 원하는 모양이다. 범위가 겹치면 하나로 합치고, 겹치지 않으면 npm은 한쪽을 최상위에, 다른 쪽을 그 패키지 폴더 안쪽에 따로 깐다. 설치는 성공하지만 두 벌은 다른 모듈이라 instanceof가 거짓이 되고 모듈 단위 상태가 쪼개진다. `npm ls 패키지`와 `npm explain`으로 확인한다.

### 유령 의존성은 무엇이고 왜 위험한가요?

package.json에 선언하지 않았는데 호이스팅 덕분에 require가 되는 패키지다. 어떤 버전이 최상위에 올라오는지는 다른 패키지 구성과 설치 순서가 정해서, 상관없는 패키지를 지우거나 새로 설치하면 다른 주 버전이 오거나 모듈이 사라진다. 쓰는 패키지는 직접 선언하고, 린트 규칙이나 pnpm의 엄격한 구조로 막는다.

### pnpm은 npm과 node_modules 구조가 어떻게 다른가요?

pnpm은 실제 파일을 `.pnpm/이름@버전` 아래에 두고, 각 패키지 옆에는 그 패키지가 선언한 의존성만 심볼릭 링크로 놓는다. 그래서 선언하지 않은 패키지는 앱 코드에서 찾을 수 없다. 파일은 전역 저장소에 한 번만 두고 하드 링크로 연결해 디스크를 아낀다. 호환성을 위해 패키지끼리는 `.pnpm/node_modules`를 통한 호이스팅이 남아 있고, 필요하면 `public-hoist-pattern`이나 `node-linker=hoisted`로 푼다.

### peerDependencies는 왜 있고 ERESOLVE는 어떻게 해결하나요?

플러그인처럼 본체와 같은 인스턴스를 공유해야 하는 패키지가 "본체는 앱이 깐 것을 쓰되 이 범위여야 한다"고 선언하는 것이다. ERESOLVE는 앱에 있는 본체 버전이 그 범위 밖일 때 난다. 에러의 Found와 Could not resolve 두 줄에서 충돌한 범위를 찾고, 그 본체 버전을 지원하는 플러그인 버전으로 올리는 것이 정석이다. 없으면 본체 업그레이드를 미루고, `--force`나 `--legacy-peer-deps`는 런타임 위험을 알고 마지막에 쓴다.

### npm install과 npm ci는 어떻게 다른가요?

`npm install`은 lockfile을 출발점으로 삼되 package.json과 어긋나면 범위를 다시 계산해 lockfile을 고쳐 쓴다. `npm ci`는 node_modules를 지우고 lockfile에 적힌 버전과 해시대로만 깔며, 둘이 어긋나면 고치지 않고 멈춘다. CI와 Docker 빌드에서는 재현성을 위해 `npm ci`를 쓰고, 의존성을 바꿀 때만 `npm install`을 쓴다.

### overrides는 언제 쓰고 무엇을 조심해야 하나요?

간접 의존성의 버전을 강제로 바꿀 때 쓴다. 보안 수정을 상류보다 먼저 넣거나, 두 벌을 한 벌로 합칠 때다. 원래 패키지가 약속하지 않은 조합이므로 해당 경로를 테스트로 확인하고, 이유와 이슈 링크를 남기고, 상류가 고치면 지운다. 남겨 두면 나중에 그 버전을 계속 낡은 것으로 묶어 버린다.

### Renovate나 Dependabot으로 업데이트를 운영할 때 어떤 전략을 쓰나요?

위험도로 나눈다. 개발 도구의 부·수 버전은 묶어서 테스트 통과 시 자동 머지하고, 함께 움직이는 패키지는 한 PR로 묶고, 주 버전은 사람이 승인한다. 막 나온 버전은 숙성 기간을 두고 받아 악성 버전이 내려갈 시간을 벌고, lockfile 유지 보수로 간접 의존성도 주기적으로 새로 고친다.
