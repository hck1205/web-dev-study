웹 서버 한 대에서 사용자가 올린 이미지를 `/var/app/uploads`에 저장하고 있었다. 트래픽이 늘어 서버를 두 대로 늘렸더니, 1번 서버로 올린 이미지가 2번 서버로 간 요청에서는 404가 난다. 당연하다. 파일은 1번 서버 디스크에만 있다. 그래서 떠오르는 첫 생각이 "그 디스크(EBS 볼륨)를 2번 서버에도 붙이면 되겠다"다. 콘솔에서 붙이려고 하면 이미 다른 인스턴스에 붙어 있다며 거절당한다. 여러 곳에 붙일 수 있는 볼륨 타입(io2의 Multi-Attach)을 찾아 억지로 붙이면, 그 순간부터 파일 시스템이 조용히 망가지기 시작한다.

이 실수는 저장소 세 종류가 내놓는 인터페이스가 다르다는 걸 모를 때 나온다. 블록 스토리지는 빈 디스크를, 파일 스토리지는 여러 서버가 함께 쓰는 폴더를, 객체 스토리지는 이름표 붙은 상자를 준다. 이 글은 AWS의 EBS, EFS, S3를 예로 세 종류의 차이(일관성, 지연, 처리량, 가격)와 EBS 볼륨 타입 고르는 법, fio로 실제 IOPS를 재는 법, 흔한 실수를 본다. 명령은 Ubuntu 24.04 기준이고, fio 출력은 이 글을 쓴 샌드박스 VM에서 실제로 돌린 것이다. 요금은 us-east-1 공개 요금 기준이다.

이 주제의 다른 글: 이 디스크가 붙는 VM이 어떻게 도는지는 [가상화와 하이퍼바이저](/posts/virtualization-hypervisors)에서, S3를 앱에서 안전하게 쓰는 법은 [S3 실전](/posts/aws-s3-in-practice)에서, S3 요금 등급과 수명 주기는 [S3 운영: 스토리지 클래스와 수명 주기](/posts/s3-storage-classes-lifecycle)에서 다룬다. 객체 저장소를 직접 만드는 내부 구조는 [객체 저장소 설계 ①](/posts/sd-object-storage-architecture)부터 이어진다.

## 세 저장소가 내놓는 말이 다르다

세 종류를 가르는 기준은 "무엇을 단위로 읽고 쓰나"다.

블록 스토리지는 번호 붙은 고정 크기 칸(블록, 보통 512바이트나 4KiB)의 배열을 준다. 할 수 있는 말은 "N번 블록부터 몇 개 읽어", "N번 블록에 이걸 써"가 전부다. 파일이나 폴더라는 개념이 없다. 그 위에 ext4나 XFS 같은 파일 시스템을 올리는 건 서버의 OS 몫이다. EBS, 데이터센터의 SAN(Fibre Channel, iSCSI로 붙는 스토리지)이 여기에 든다.

파일 스토리지는 파일 시스템을 네트워크 너머에 두고 폴더와 파일 단위로 말한다. "이 경로의 파일을 열어, 이 위치부터 4KB 읽어, 이 파일을 잠가". 파일 시스템 자체는 저장소 쪽 서버가 관리하니 여러 클라이언트가 같은 트리를 함께 볼 수 있다. 프로토콜은 리눅스의 NFS, 윈도우의 SMB가 대표다. EFS, FSx, 사내 NAS 장비가 여기에 든다.

객체 스토리지는 키(이름)와 바이트 덩어리(객체)와 메타데이터를 HTTP로 주고받는다. "이 키로 이 덩어리를 통째로 넣어", "이 키의 덩어리를 줘(원하면 일부 바이트 범위만)". 폴더처럼 보이는 `photos/2026/` 같은 건 키 이름에 든 슬래시일 뿐이다. 이미 넣은 객체의 중간을 고쳐 쓰거나 뒤에 덧붙이는 동작이 기본으로는 없다. 바꾸려면 새로 통째로 넣는다. S3, GCS, Azure Blob, MinIO가 여기에 든다.

## 블록 스토리지는 빈 디스크를 빌려 준다

EBS 볼륨을 새로 만들어 인스턴스에 붙이면 OS에는 그냥 빈 디스크 하나가 생긴다. Nitro 인스턴스에서는 NVMe 장치로 보인다.

```bash
# 붙은 디스크 목록. 새 볼륨은 파일 시스템(FSTYPE)과 마운트 위치가 비어 있다
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINT

# 비어 있는지 한 번 더 확인한다. "data"만 나오면 아무것도 없는 디스크다
sudo file -s /dev/nvme1n1

# 파일 시스템을 만들고 마운트한다. mkfs는 디스크 내용을 지운다
sudo mkfs.xfs /dev/nvme1n1
sudo mkdir -p /data
sudo mount /dev/nvme1n1 /data

# 재부팅 후에도 붙도록 UUID로 fstab에 적는다. nofail은 볼륨이 없어도 부팅을 막지 않는다
echo "UUID=$(sudo blkid -s UUID -o value /dev/nvme1n1) /data xfs defaults,nofail 0 2" | sudo tee -a /etc/fstab
sudo mount -a   # fstab 문법이 맞는지 바로 확인한다
```

`/dev/nvme1n1` 같은 이름은 붙이는 순서에 따라 바뀔 수 있다. fstab에 장치 이름 대신 UUID를 쓰는 이유다. `sudo mount -a`가 에러 없이 끝나야 재부팅해도 안전하다. fstab이 틀린 채로 재부팅하면 인스턴스가 응급 모드로 떨어지고, 클라우드에서는 콘솔 접속이 번거로워 복구가 오래 걸린다.

EBS에서 기억할 성질은 이렇다.

- 볼륨은 하나의 가용 영역(AZ)에 산다. AZ 안에서는 여러 벌로 복제돼 디스크 하나가 죽어도 괜찮지만, 다른 AZ의 인스턴스에는 붙일 수 없다. 옮기려면 스냅샷을 찍어 다른 AZ에 새로 만든다.
- 스냅샷은 S3에 증분으로 저장된다. 스냅샷에서 만든 새 볼륨은 블록을 처음 읽을 때 S3에서 끌어온다. 그래서 복원 직후 첫 읽기가 몹시 느리다. DB 복원 후 첫 쿼리가 수십 배 느린 이유가 이거다.
- 인스턴스를 꺼도 데이터가 남는다. 반대로 인스턴스 스토어는 물리 서버에 직접 꽂힌 NVMe라서 아주 빠르지만, 인스턴스를 멈추거나 종료하면(재부팅은 괜찮다) 내용이 사라진다. 캐시, 임시 파일, 여러 노드가 복제하는 데이터(Cassandra, Kafka 일부 구성)에만 쓴다.
- 크기, 타입, IOPS를 붙인 채로 바꿀 수 있다(Elastic Volumes). 다만 한 번 바꾸면 다음 변경까지 6시간을 기다려야 하고, 크기를 늘린 뒤에는 파티션과 파일 시스템도 늘려야 한다(`growpart`, `xfs_growfs` 또는 `resize2fs`).

데이터센터의 SAN도 원리는 같다. 스토리지 장비가 큰 디스크 묶음을 LUN이라는 논리 디스크로 잘라, 서버에 Fibre Channel이나 iSCSI(블록 명령을 TCP에 실어 보내는 프로토콜)로 내준다. 서버 쪽에서는 그냥 로컬 디스크처럼 보인다. EBS는 이 구조를 AWS가 대신 운영하는 것이라고 보면 된다.

ext4와 XFS는 "이 디스크는 나 혼자 쓴다"를 전제로 메타데이터를 메모리에 캐시하고 저널을 쓴다. 다른 서버가 바꾼 것을 알 방법이 없다. Multi-Attach를 제대로 쓰려면 노드끼리 잠금을 주고받는 클러스터 파일 시스템(GFS2, OCFS2)이나, 블록을 직접 다루며 스스로 조율하는 애플리케이션(일부 클러스터 DB)이 있어야 한다. 웹 서버 업로드 폴더를 나누는 용도로는 맞지 않는다. 그 용도에는 아래의 파일 스토리지나 객체 스토리지가 답이다.

## gp3, io2, 인스턴스 스토어 고르기

EBS의 SSD 볼륨은 사실상 둘 중 하나를 고른다.

gp3는 기본값이다. 크기와 상관없이 3,000 IOPS와 125MiB/s를 기본으로 주고, 따로 돈을 내면 IOPS와 처리량을 올릴 수 있다. 오랫동안 상한은 16,000 IOPS, 1,000MiB/s였고, 2025년 9월에 큰 볼륨에서 80,000 IOPS, 2,000MiB/s까지로 올라갔다. 보관 요금은 GB-월 0.08달러다. 예전 gp2는 크기에 비례해 IOPS가 정해지고 작은 볼륨은 크레딧으로 버텼는데, 크레딧이 떨어지면 성능이 뚝 떨어져서 장애가 자주 났다. 새로 만든다면 gp3를 쓴다. gp2를 gp3로 바꾸는 것도 붙인 채로 된다.

io2(Block Express)는 지연이 더 짧고 고르며, 볼륨 하나에 256,000 IOPS까지 간다. 내구성도 gp3보다 한 자리 높게 설계됐다(gp3는 연간 고장률 0.1~0.2%, io2는 0.001%로 안내된다). 대신 프로비저닝한 IOPS마다 매달 돈을 낸다. 큰 OLTP DB처럼 p99 지연이 곧 서비스 품질인 곳에 쓴다.

여기서 자주 놓치는 것이 두 가지다. 첫째, IOPS와 처리량은 따로 걸리는 두 상한이다. 4KiB씩 읽으면 IOPS 상한에 먼저 닿고, 1MiB씩 읽으면 처리량 상한에 먼저 닿는다. SSD 볼륨에서 EBS는 256KiB를 넘는 I/O를 256KiB 단위로 쪼개 여러 번으로 센다. 둘째, 인스턴스에도 EBS 대역폭 상한이 있다. 볼륨에 1,000MiB/s를 사도 인스턴스 타입의 EBS 대역폭이 그보다 낮으면 거기서 막힌다. 작은 인스턴스는 하루 중 일정 시간만 최대치까지 버스트하는 경우가 많아서, 백업이 도는 새벽에만 디스크가 느려지는 일이 생긴다.

  const ioPerSec = Math.floor(Math.min(byIops, byBandwidth));
  return {
    ioPerSec,
    mibps: Math.round((ioPerSec * ioKiB / 1024) * 10) / 10,
    limit: byIops <= byBandwidth ? "iops" : "throughput",
  };
}`}
  tests={[

마지막 경우가 실무에서 흔한 실수다. IOPS만 잔뜩 올리고 처리량은 기본에 가깝게 두면, 128KiB짜리 순차 읽기(테이블 풀 스캔, 백업)에서는 산 IOPS의 8분의 1도 못 쓴다. 볼륨을 고칠 때는 워크로드의 I/O 크기부터 본다. `iostat -x`의 `rareq-sz`, `wareq-sz`(평균 요청 크기, KiB)가 그 숫자다. 읽는 법은 [페이지 캐시와 디스크 I/O](/posts/page-cache-disk-io)에서 다뤘다.

## fio로 IOPS를 직접 잰다

볼륨 사양표의 숫자가 실제로 나오는지는 fio로 잰다. `dd`는 페이지 캐시를 거치고 큐 깊이가 1이라 저장소 성능을 거의 보여 주지 못한다.

```bash
sudo apt-get install -y fio

# 4KiB 랜덤 읽기, 동시에 32개 요청(iodepth=32), 페이지 캐시 우회(direct=1), 10초
fio --name=randread --filename=/data/fio.test --size=256M \
  --bs=4k --rw=randread --iodepth=32 --ioengine=libaio --direct=1 \
  --runtime=10 --time_based --group_reporting
```


볼 줄은 세 개다. `read: IOPS=53.5k`가 결과이고, `lat avg=596.79`(마이크로초)가 요청 하나의 평균 지연이다. 이 둘은 큐 깊이로 묶인다. 동시에 32개가 떠 있고 하나가 평균 0.597밀리초 걸리면 초당 32 ÷ 0.000597 ≈ 53,600개가 끝난다. 리틀의 법칙이다. 그래서 IOPS를 더 뽑고 싶으면 지연을 줄이거나 동시에 띄우는 요청을 늘려야 한다. 같은 파일을 `--iodepth=1`로 다시 재면 이 샌드박스에서는 `IOPS=10.2k`가 나왔다. 앱이 요청을 하나씩 기다리며 보내면 디스크가 아무리 좋아도 그 숫자에 묶인다.

처리량은 I/O를 크게 해서 따로 잰다. 같은 파일을 1MiB씩 순차로 읽게 바꾸면 숫자의 주인공이 바뀐다.

```bash
# 1MiB 순차 읽기, 동시에 8개. 이번에는 BW(처리량)를 본다
fio --name=seq --filename=/data/fio.test --size=256M \
  --bs=1M --rw=read --iodepth=8 --ioengine=libaio --direct=1 \
  --runtime=8 --time_based
```

```text
  read: IOPS=961, BW=962MiB/s (1009MB/s)(7703MiB/8008msec)
```

IOPS는 961로 4KiB 때의 50분의 1도 안 되지만, 옮긴 바이트는 초당 962MiB로 네 배가 넘는다. 디스크 성능을 말할 때 "IOPS 몇"만 말하면 반쪽이다. 어떤 크기의 I/O로 잰 숫자인지 함께 말해야 한다. gp3 기본 설정이었다면 이 테스트는 125MiB/s에서 막혔을 것이다.

세 번째는 `clat percentiles`의 꼬리다. 중앙값은 359마이크로초인데 99.99%는 358밀리초다. 이 샌드박스의 디스크는 다른 작업과 함께 쓰는 가상 디스크라 꼬리가 길다. EBS에서 재면 io2가 gp3보다 이 꼬리가 짧게 나오는 게 보통이고, 그게 io2에 돈을 내는 이유다.

재는 동안 지킬 것이 몇 가지 있다. `--direct=1`을 빼면 페이지 캐시를 재게 된다. 테스트 파일이 메모리보다 작으면 두 번째 실행부터 저장소 쪽 캐시에서 나올 수 있다. 실제 볼륨 장치(`/dev/nvme1n1`)에 직접 쓰기 테스트를 하면 파일 시스템이 날아가니, 쓰기 테스트는 파일로 하거나 빈 볼륨에서만 한다. 스냅샷에서 복원한 볼륨이라면 앞에서 말한 첫 읽기 지연 때문에 숫자가 낮게 나온다. AWS 문서는 이럴 때 볼륨 전체를 한 번 읽어 두는 방법을 안내한다.

```bash
# 스냅샷에서 만든 볼륨의 블록을 전부 한 번 읽어 S3에서 끌어온다 (읽기만 한다)
sudo fio --filename=/dev/nvme1n1 --rw=read --bs=1M --iodepth=32 \
  --ioengine=libaio --direct=1 --name=volume-initialize
```

볼륨이 크면 몇 시간이 걸린다. 복원 직후 바로 운영 트래픽을 받아야 하면 돈을 더 내고 빠른 스냅샷 복원(Fast Snapshot Restore)을 켜 둔 스냅샷을 쓴다.

## 디스크가 찼을 때는 세 층을 차례로 늘린다

새벽에 디스크 사용률 95% 알림이 온다. EBS는 붙인 채로 크기를 늘릴 수 있지만, 콘솔에서 숫자를 바꾸는 것으로 끝나지 않는다. 디스크, 파티션, 파일 시스템이 각각 따로 크기를 갖고 있어서 아래 층부터 차례로 늘려야 한다. 이 순서를 모르면 "볼륨은 200GB로 늘렸는데 `df`는 여전히 100GB"인 상태에서 한참 헤맨다.

실제 EBS 대신 루프 장치로 같은 과정을 재현했다. 200MB짜리 디스크 이미지에 파티션 하나와 ext4를 만들고, 이미지를 400MB로 늘린 상황이다. 콘솔에서 볼륨 크기를 바꾼 직후와 같다.

```bash
# 1. 디스크가 커졌는지 본다. 디스크(loop4)는 400M인데 파티션(loop4p1)은 그대로다
lsblk -o NAME,SIZE,TYPE /dev/loop4
```

```text
NAME       SIZE TYPE
loop4      400M loop
`-loop4p1  199M part
```

EBS라면 이 자리에 `nvme1n1`이 새 크기로, `nvme1n1p1`이 옛 크기로 보인다. 디스크 크기조차 그대로라면 볼륨 변경이 아직 `optimizing` 단계 전이거나 OS가 새 크기를 못 읽은 것이니 잠시 기다린다.

```bash
# 2. 파티션을 디스크 끝까지 늘린다 (파티션 번호 1). 데이터는 건드리지 않는다
sudo growpart /dev/loop4 1
lsblk -o NAME,SIZE,TYPE /dev/loop4
```

```text
CHANGED: partition=1 start=2048 old: size=407552 end=409599 new: size=817119 end=819166
NAME       SIZE TYPE
loop4      400M loop
`-loop4p1  399M part
```

`CHANGED` 줄의 시작 위치(`start=2048`)가 그대로이고 끝만 늘었는지 본다. 시작이 바뀌면 데이터 위치가 어긋난다는 뜻이라 멈춰야 한다. 파티션 없이 디스크 전체에 파일 시스템을 만든 볼륨이라면 이 단계를 건너뛴다.

```bash
# 3. 파일 시스템을 파티션 크기까지 늘린다. ext4는 resize2fs, XFS는 마운트 경로로 xfs_growfs
sudo resize2fs /dev/loop4p1
# XFS라면: sudo xfs_growfs /data
```

```text
resize2fs 1.47.0 (5-Feb-2023)
Resizing the filesystem on /dev/loop4p1 to 102139 (4k) blocks.
The filesystem on /dev/loop4p1 is now 102139 (4k) blocks long.
```

102,139개의 4KiB 블록이면 약 399MiB로 파티션 크기와 맞는다. 이 샌드박스는 권한 제한 때문에 마운트를 풀고 늘렸지만, EC2 같은 일반 서버에서는 ext4와 XFS 모두 마운트된 채로(온라인) 늘어난다. 마지막으로 `df -h`에서 새 크기가 보이면 끝이다.

반대로 줄이는 건 안 된다. EBS는 크기를 줄이는 변경을 받지 않고, XFS는 파일 시스템 축소 자체가 없다. 너무 크게 잡았다면 작은 볼륨을 새로 만들어 데이터를 복사하는 수밖에 없다. 그래서 처음부터 크게 잡기보다 알림을 걸어 두고 필요할 때 늘린다. 한 번 늘린 뒤 6시간 동안은 다시 바꿀 수 없다는 점도 새벽 대응에서 걸린다. 한 번에 넉넉히 늘린다.

## 스냅샷은 편하지만 백업 전부는 아니다

EBS 스냅샷은 블록 단위 증분이라 싸고 빠르다. 첫 스냅샷은 쓴 블록 전체를, 그다음부터는 바뀐 블록만 저장한다. Data Lifecycle Manager나 AWS Backup으로 "매일 새벽 3시, 14일 보관" 같은 규칙을 걸어 두는 게 보통이다.

조심할 점이 둘 있다. 하나는 일관성이다. 스냅샷은 그 순간의 블록을 찍을 뿐, 메모리에만 있던 쓰기나 DB가 반쯤 쓴 페이지는 모른다. 전원이 갑자기 나간 디스크와 같은 상태(crash-consistent)다. 저널을 쓰는 파일 시스템과 WAL을 쓰는 DB는 대개 이 상태에서 복구되지만, 볼륨 여러 개에 걸친 데이터(데이터와 로그를 다른 볼륨에 둔 DB)는 볼륨마다 찍힌 시각이 달라 어긋날 수 있다. 그럴 때는 여러 볼륨을 한 번에 찍는 다중 볼륨 스냅샷을 쓰거나, DB의 백업 도구를 쓴다.

다른 하나는 같은 계정, 같은 리전에 있다는 점이다. 계정 권한이 털리면 볼륨과 스냅샷을 함께 지울 수 있다. 스냅샷을 다른 계정이나 리전으로 복사하고, 지울 수 없게 잠그는 설정을 함께 쓴다. 이 이야기는 [백업 전략](/posts/backup-strategy)에서 3-2-1 원칙과 함께 다뤘다.

## 파일 스토리지는 여러 서버가 같은 폴더를 본다

업로드 폴더를 여러 서버가 함께 보게 하는 가장 직접적인 답은 파일 스토리지다. EFS는 AWS가 운영하는 NFS 서버라고 보면 된다. 리전 안 여러 AZ에 데이터를 나눠 두고(One Zone 옵션도 있다), 각 AZ의 서브넷에 마운트 타깃이라는 IP를 하나씩 둔다. 서버는 자기 AZ의 마운트 타깃으로 NFSv4.1 연결을 연다.

```bash
# NFS 클라이언트 설치 (EFS 전용 도우미 amazon-efs-utils를 써도 된다)
sudo apt-get install -y nfs-common

# AWS 문서가 권하는 옵션으로 마운트한다. fs-0123... 은 내 파일 시스템 ID
sudo mkdir -p /mnt/uploads
sudo mount -t nfs4 \
  -o nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2,noresvport \
  fs-0123456789abcdef0.efs.ap-northeast-2.amazonaws.com:/ /mnt/uploads

# 마운트된 옵션을 확인한다
findmnt -t nfs4 /mnt/uploads
```

옵션 몇 개는 뜻을 알고 쓴다. `hard`는 서버가 응답하지 않으면 끝까지 다시 시도한다. 앱이 멈춰 보일 수는 있어도 쓰다 만 데이터가 "성공"으로 끝나지는 않는다. `soft`로 바꾸면 시간이 지나 에러를 돌려주는데, 그 사이 쓰기가 일부만 반영될 수 있어 데이터용으로는 권하지 않는다. `noresvport`는 재연결 때 새 포트를 써서 네트워크가 끊겼다 붙어도 빨리 살아나게 한다. 마운트가 그냥 멈춰 있다면 열에 아홉은 마운트 타깃의 보안 그룹이 TCP 2049를 서버 쪽에 열어 주지 않은 경우다.

함께 쓰는 대가는 일관성과 지연에서 나온다. NFS 클라이언트는 성능을 위해 파일 속성과 내용을 캐시하고, "닫을 때 서버로 밀어 넣고, 열 때 서버에 다시 묻는다"는 close-to-open 일관성을 약속한다. 서버 A가 파일을 쓰고 닫은 뒤 서버 B가 그 파일을 새로 열면 새 내용을 본다. 하지만 B가 이미 열어 둔 파일을 계속 읽고 있으면, 속성 캐시 시간(기본 최대 60초) 동안 옛 크기와 내용을 볼 수 있다. 로그 파일을 두 서버가 동시에 이어 쓰면 줄이 섞이거나 사라지는 것도 같은 이유다.

지연은 블록보다 길다. 파일 하나 열기, 속성 읽기, 잠금이 전부 네트워크 왕복이라, 작은 파일 수만 개를 다루는 작업(`npm install`, `git status`, PHP 소스를 EFS에서 바로 읽는 웹 서버)이 로컬 디스크보다 몇 배에서 수십 배 느려진다. 큰 파일을 순차로 읽고 쓰는 일은 병렬로 잘 확장된다. 요금도 비싸다. EFS Standard는 GB-월 0.30달러 수준으로 gp3의 네 배쯤이다. 대신 쓴 만큼만 내고 미리 크기를 잡지 않는다.

EFS의 처리량 모드도 고른다. 기본 권장인 Elastic은 쓴 만큼 처리량이 자동으로 오르내리고 읽고 쓴 바이트에 요금이 붙는다. Bursting은 저장한 용량에 비례해 기준 처리량이 정해지고 크레딧으로 버틴다. 데이터는 적은데 많이 읽는 파일 시스템이 Bursting이면 크레딧이 떨어지는 순간 느려진다. CloudWatch의 `BurstCreditBalance`가 줄고 있다면 그 신호다. 늘 일정한 처리량이 필요하면 Provisioned로 미리 산다.

쿠버네티스에서 여러 Pod가 한 볼륨을 함께 쓰는 `ReadWriteMany`가 필요하면 EFS CSI 드라이버가 흔한 답이다. EBS는 `ReadWriteOnce`만 된다. 이 차이는 [PV와 PVC](/posts/k8s-pv-pvc)에서 다뤘다.

## DB 데이터 디렉터리를 NFS에 두면

"EFS는 여러 AZ에 복제되니 DB를 거기 두면 안전하겠다"는 생각도 자주 나온다. 대부분 좋지 않은 선택이다.

DB는 커밋마다 WAL을 `fsync`한다. 로컬 디스크나 EBS에서 fsync는 1밀리초 안쪽이지만, NFS에서는 클라이언트가 서버에 COMMIT 요청을 보내고 서버가 자기 저장소에 내려 쓴 뒤 답할 때까지 기다린다. 여러 AZ에 복제하는 EFS라면 그 왕복이 더 길다. 초당 커밋 수가 바로 이 지연에 묶인다.

장애 때의 동작도 문제다. PostgreSQL 문서는 NFS에 데이터 디렉터리를 둘 수는 있다고 하면서, 서버가 응답하지 않을 때 쓰기가 조용히 버려지지 않도록 `hard` 마운트를 쓰라고 강하게 권한다. SQLite 문서는 NFS의 파일 잠금이 고장 난 구현이 많아 DB가 깨질 수 있다고 직접 적는다. 네트워크가 잠깐 끊겼을 때 fsync 에러가 어떻게 보고되는지도 구현마다 다르다. DB는 블록 스토리지(EBS)에 두고, 여러 AZ 생존은 DB 자체의 복제(RDS Multi-AZ나 스트리밍 복제)로 해결하는 게 정석이다. 관리형 DB가 이걸 어떻게 하는지는 [RDS와 Aurora](/posts/rds-aurora-managed-db)에서 다뤘다.

## 데이터센터에서는 SAN과 NAS라고 부른다

클라우드 밖에서는 같은 구분을 장비 이름으로 부른다. SAN(Storage Area Network)은 블록 스토리지를 서버에 내주는 전용 네트워크다. 스토리지 장비가 디스크 묶음을 LUN으로 잘라 내주고, 서버는 HBA 카드와 Fibre Channel 스위치로 붙거나, 일반 이더넷 위에서 iSCSI로 붙는다. 서버 입장에서는 로컬 디스크와 똑같이 `/dev/sdb`로 보인다. 그래서 같은 LUN을 두 서버에 보여 주면 앞에서 본 EBS Multi-Attach와 똑같이 깨진다. VMware 클러스터처럼 여러 호스트가 한 LUN을 쓰는 경우는 VMFS 같은 클러스터 파일 시스템이 잠금을 맡는다.

NAS(Network Attached Storage)는 파일 서버 장비다. 자체 파일 시스템을 들고 NFS나 SMB로 폴더를 내준다. 회사 공유 드라이브, 영상 편집팀의 작업 폴더가 흔한 예다. EFS가 이 자리를 대신하고, 윈도우 앱이 SMB를 요구하면 FSx for Windows File Server를, 고성능 계산이 병렬 파일 시스템을 요구하면 FSx for Lustre를 쓴다.

iSCSI를 직접 붙여 볼 일은 클라우드에서는 드물지만, 온프레미스나 하이브리드 환경에서는 여전히 자주 본다. 리눅스에서는 `open-iscsi` 패키지의 `iscsiadm`으로 대상을 찾고(discovery) 로그인하면 새 블록 장치가 생긴다. 그 뒤는 EBS와 같다. 파일 시스템을 만들고, UUID로 fstab에 적고, 네트워크가 먼저 올라와야 하니 마운트 옵션에 `_netdev`를 붙인다. 이걸 빼면 부팅 때 네트워크보다 먼저 마운트를 시도하다 멈춘다.

## 객체 스토리지는 이름으로 통째로 넣고 꺼낸다

S3에서 할 수 있는 말은 HTTP 요청 몇 개다. `PUT`으로 키에 객체를 통째로 넣고, `GET`으로 통째로(또는 `Range` 헤더로 일부 바이트만) 꺼내고, `DELETE`로 지우고, `LIST`로 접두사(prefix) 아래 키를 훑는다. 5GB가 넘는 객체는 멀티파트 업로드로 조각내 올린다. 이미 있는 객체의 가운데 1KB만 바꾸는 동작은 없다. 1GB 파일의 한 줄을 고치려면 1GB를 다시 올린다.

이 단순함이 확장성을 준다. 객체끼리 서로 묶이지 않으니 저장소가 키를 여러 서버에 마음대로 나눌 수 있다. S3는 접두사 하나마다 초당 PUT 3,500개, GET 5,500개 이상을 처리하고, 접두사를 나누면 그만큼 늘어난다. 2020년 12월부터는 모든 요청에 강한 읽기 일관성을 준다. 새로 쓴 객체를 바로 GET하거나 LIST하면 쓴 결과가 보인다. 그 전에는 덮어쓰기 직후 옛 내용이 보일 수 있었다.

대신 요청 하나의 지연이 길다. 첫 바이트까지 보통 수십 밀리초가 걸리고, 요청마다 요금이 붙는다(us-east-1 Standard 기준 PUT 1,000건에 0.005달러, GET 1,000건에 0.0004달러). 그래서 객체 스토리지는 "작은 조각을 자주 고치는" 일에 맞지 않고, "한 번 쓰고 여러 번 읽는" 이미지, 동영상, 백업, 로그, 데이터 레이크에 맞다. 보관 요금은 Standard가 GB-월 0.023달러로 gp3의 3분의 1이 안 되고, 덜 꺼내는 데이터는 더 싼 등급으로 내릴 수 있다. 등급 이야기는 [S3 운영: 스토리지 클래스와 수명 주기](/posts/s3-storage-classes-lifecycle)에서 이어진다.

S3를 폴더처럼 마운트해 주는 도구(s3fs, AWS의 Mountpoint for Amazon S3)도 있다. 순차로 크게 읽는 분석 작업에는 쓸 만하지만 파일 시스템이 되지는 않는다. 기존 파일을 고쳐 쓰기, 이름 바꾸기, 잠금 같은 동작은 지원하지 않거나 제한적이고, 지원하더라도 뒤에서는 객체 전체를 다시 올린다. 일반 파일 시스템을 기대하는 앱(DB, 로그를 이어 쓰는 프로그램)을 그 위에 올리면 안 된다.

## 업로드 폴더 문제는 이렇게 푼다

처음의 웹 서버 두 대로 돌아가면, 선택지는 둘이다.

앱을 고칠 수 있다면 S3로 간다. 브라우저가 서버를 거치지 않고 S3에 바로 올리게 하면(presigned URL) 웹 서버는 파일 바이트를 만지지도 않는다. 서버를 몇 대로 늘리든 상관이 없고, 이미지는 CloudFront로 내보낸다. 구체적인 방법은 [S3 실전](/posts/aws-s3-in-practice)에서 다룬다.

앱이 로컬 경로에 파일을 쓴다는 가정을 깊이 깔고 있어서 당장 못 고친다면 EFS를 마운트한다. 코드 변경 없이 바로 풀린다. 대신 지연과 비용이 늘어나니, 파일 개수가 많고 작은 워크로드라면 장기적으로는 S3로 옮기는 계획을 함께 세운다.

어느 쪽이든 EBS를 두 서버에 붙이는 길은 아니다. 고르는 기준을 한 표로 모으면 이렇다.

| | 블록 (EBS) | 파일 (EFS) | 객체 (S3) |
|---|---|---|---|
| 다루는 단위 | 블록 번호 | 경로·파일 | 키·객체 통째 |
| 함께 쓰는 서버 | 한 대 (같은 AZ) | 여러 대, 여러 AZ | 제한 없음 (HTTP) |
| 지연 | 1ms 안쪽 | 수 ms | 수십 ms |
| 부분 수정 | 된다 | 된다 | 안 된다 (다시 올림) |
| 보관 요금 (GB-월) | gp3 0.08달러 (잡은 크기만큼) | Standard 0.30달러 수준 (쓴 만큼) | Standard 0.023달러 (쓴 만큼) |
| 맞는 일 | DB, 부트 디스크 | 공유 폴더, 레거시 앱 | 미디어, 백업, 로그 |

## 인터페이스가 먼저, 성능표는 그다음

블록은 한 서버가 파일 시스템을 만들어 쓰는 빈 디스크, 파일은 여러 서버가 함께 보는 네트워크 폴더, 객체는 HTTP로 통째로 넣고 꺼내는 이름표 붙은 상자다. 무엇을 고를지는 IOPS 숫자보다 먼저 "몇 대가 함께 쓰나, 부분 수정이 필요한가"로 정해진다. 블록 안에서는 I/O 크기를 보고 IOPS와 처리량 두 상한을 함께 맞추고, 숫자는 fio로 직접 확인한다.

## 면접에서 나올 만한 질문

### 블록, 파일, 객체 스토리지는 어떻게 다른가요?

다루는 단위가 다르다. 블록은 번호 붙은 블록 배열을 주고 파일 시스템은 서버 OS가 만든다. 파일은 저장소가 파일 시스템을 들고 NFS·SMB로 경로 단위 접근을 주니 여러 서버가 함께 쓴다. 객체는 키와 바이트 덩어리를 HTTP로 통째로 주고받아 부분 수정은 못 하지만 확장성이 가장 크고 싸다. AWS로는 EBS, EFS, S3다.

### EBS 볼륨 하나를 여러 EC2에 붙여 공유 폴더로 쓰면 왜 안 되나요?

ext4나 XFS는 디스크를 혼자 쓴다고 가정하고 빈 블록 지도와 메타데이터를 메모리에 캐시하기 때문이다. 두 서버가 같은 빈칸을 각자 골라 쓰면 서로 덮어써서 파일 시스템이 깨진다. io2 Multi-Attach는 클러스터 파일 시스템이나 스스로 조율하는 앱을 위한 기능이다. 공유 폴더가 필요하면 EFS 같은 파일 스토리지나 S3를 쓴다.

### gp3와 io2는 언제 고르나요?

대부분은 gp3다. 크기와 상관없이 3,000 IOPS·125MiB/s를 주고 필요하면 따로 올린다. io2는 지연이 더 짧고 고르며 IOPS를 훨씬 높게 잡을 수 있어서, p99 지연이 중요한 큰 OLTP DB에 쓴다. 어느 쪽이든 IOPS와 처리량이 따로 걸리는 상한이고 인스턴스 타입의 EBS 대역폭 상한도 있다는 점을 같이 본다.

### IOPS를 올렸는데 백업이나 풀 스캔이 빨라지지 않았습니다. 왜일까요?

처리량 상한에 걸렸을 가능성이 크다. 큰 I/O(128KiB, 1MiB)는 IOPS보다 MiB/s에 먼저 닿는다. 16,000 IOPS를 사도 처리량이 250MiB/s면 128KiB I/O는 초당 2,000번밖에 못 한다. `iostat -x`의 평균 요청 크기를 보고 처리량을 같이 올리거나, 인스턴스의 EBS 대역폭 상한도 확인한다.

### fio 결과의 IOPS와 지연은 어떤 관계인가요?

리틀의 법칙으로 묶인다. IOPS는 동시에 떠 있는 요청 수를 요청 하나의 평균 지연으로 나눈 값이다. 큐 깊이 32에 평균 0.6밀리초면 약 53,000 IOPS가 나온다. 그래서 앱이 요청을 하나씩 기다리며 보내면 디스크 사양보다 훨씬 낮은 IOPS에 묶이고, 사양표 숫자는 충분한 동시성이 있을 때만 나온다.

### DB 데이터 디렉터리를 EFS(NFS)에 두면 어떤 문제가 생기나요?

커밋마다 하는 fsync가 네트워크 왕복이 되어 초당 커밋 수가 떨어지고, NFS의 잠금과 에러 보고가 구현마다 달라 데이터가 깨질 위험이 생긴다. PostgreSQL 문서도 hard 마운트를 강하게 권하고, SQLite 문서는 NFS의 잠금이 믿을 수 없다며 피하라고 한다. DB는 EBS에 두고 가용성은 DB 복제로 해결한다.

### SAN과 NAS는 어떻게 다른가요?

SAN은 블록 스토리지를 Fibre Channel이나 iSCSI로 서버에 내주는 네트워크라서 서버가 직접 파일 시스템을 만든다. NAS는 장비가 파일 시스템을 들고 NFS·SMB로 폴더를 내준다. 그래서 SAN의 LUN 하나를 여러 서버가 쓰려면 클러스터 파일 시스템이 필요하고, NAS는 원래 여럿이 함께 쓰는 용도다. 클라우드에서는 EBS가 SAN, EFS·FSx가 NAS 자리에 있다.

### S3는 일관성이 어떻게 되나요?

2020년 12월부터 모든 PUT·DELETE 뒤의 GET과 LIST에 강한 읽기 일관성을 준다. 새로 쓴 객체를 바로 읽으면 새 내용이 보이고, 덮어쓴 직후 옛 내용이 보이던 예전 동작은 없어졌다. 다만 같은 키에 동시에 여러 번 쓰면 마지막에 도착한 것이 이긴다. 잠금은 없어서, 덮어쓰기를 막으려면 2024년에 생긴 조건부 쓰기(If-None-Match, If-Match)를 쓰거나 앱이 조율한다.
