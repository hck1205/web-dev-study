연결 리스트를 출력하는 함수를 돌렸더니 끝나지 않는다. 콘솔에 같은 숫자 몇 개가 끝없이 반복해서 찍힌다. 어딘가에서 노드의 `next`가 앞쪽 노드를 다시 가리키고 있는 것이다. 이렇게 리스트 안에 고리가 생기면 "끝까지 따라가는" 모든 코드가 무한 루프에 빠진다.

[LeetCode 141. Linked List Cycle](https://leetcode.com/problems/linked-list-cycle/)은 리스트에 이런 고리가 있는지 알아내는 문제다. 쉬움 난이도지만 면접에서 자주 나오는 이유가 있다. 해시 집합으로 푸는 건 쉽고, "추가 메모리 없이 풀 수 있나"라는 후속 질문에 Floyd의 토끼와 거북이 알고리즘이 나와야 하며, 그 뒤로 "고리의 시작점은 어떻게 찾나"라는 꼬리 질문이 이어진다. 이 글에서는 여섯 가지 풀이와 그 증명, 고리 입구 찾기까지 본다. 빠른·느린 포인터의 기본은 [연결 리스트 글](/posts/ds-linked-list)에서 다뤘다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 꼬리가 다시 앞을 가리키는 리스트

연결 리스트의 머리 `head`가 주어진다. 어떤 노드에서 `next`를 계속 따라가다가 이미 지나간 노드로 다시 돌아올 수 있으면 고리(cycle)가 있는 것이다. 고리가 있으면 `true`, 없으면 `false`를 돌려준다.

LeetCode 화면에는 `pos`라는 값이 함께 보인다. 마지막 노드의 `next`가 몇 번째 노드에 이어져 있는지를 나타내는 번호이고, `-1`이면 고리가 없다. 이 값은 테스트 입력을 만드는 데만 쓰이고 함수에는 넘어오지 않는다. 함수가 받는 건 `head` 하나뿐이다.

```text
[1, 2, 3, 4, 5, 6], pos = 2   →  6의 next가 3을 가리킨다   true
[1, 2, 3, 4, 5, 6], pos = -1  →  6의 next는 null           false
[1], pos = 0                  →  1이 자기 자신을 가리킨다   true
[], pos = -1                  →  빈 리스트                  false
```

노드는 0개에서 10^4개, 값은 -10^5에서 10^5 사이다. 값은 중복될 수 있다. 그래서 "같은 값을 다시 만나면 고리"라고 판단하면 안 된다. 같은 노드를 다시 만났는지를 봐야 한다.

## 끝을 기다리는 방법은 통하지 않는다

고리가 없는 리스트는 따라가다 보면 언젠가 `null`을 만난다. 고리가 있는 리스트는 `null`을 영원히 만나지 않는다. 그럼 따라가다가 `null`을 만나면 `false`라고 하면 될 것 같은데, 문제는 반대쪽이다. 아직 `null`을 못 만났다는 사실만으로는 "고리가 있어서 영원히 못 만난다"인지 "리스트가 길어서 아직 못 만났다"인지 알 수 없다.

고리가 있는 리스트의 모양을 그려 보면 숫자 6처럼 생겼다. 머리에서 시작하는 곧은 꼬리 부분이 있고, 그 끝이 동그란 고리로 이어진다. 그리스 문자 ρ(로)와 닮아서 이런 모양을 ρ 모양이라고 부르기도 한다. 아래 그림은 `[1, 2, 3, 4, 5, 6]`, `pos = 2`인 리스트다. 1과 2가 곧은 부분이고, 3부터 6까지가 고리다.

이 그림에서 점이 화살표를 따라 끝없이 도는 것처럼, 단순히 `next`를 따라가는 코드는 3, 4, 5, 6을 영원히 돈다. 고리를 알아내려면 "한 번 지나간 곳을 다시 지나고 있다"는 걸 어떻게든 알아차려야 한다. 그 방법이 풀이마다 다르다.

## 노드 수의 상한만큼만 걸어 보기

이 문제에는 노드가 많아야 10^4개라는 제약이 있다. 고리가 없다면 10^4번 안에 `null`을 만난다. 그러니 10^4번 넘게 걸었는데도 아직 노드가 남아 있다면, 같은 노드를 다시 지나고 있다는 뜻이다.

```js
function hasCycle(head) {
  let steps = 0;
  for (let n = head; n; n = n.next) {
    // 노드는 최대 10^4개. 그보다 많이 걸었다면 같은 노드를 다시 밟은 것이다
    if (++steps > 10000) return true;
  }
  return false; // null을 만났다
}
```

시간은 최대 10^4 + 1걸음이라 O(n)으로 볼 수 있고, 공간은 O(1)이다. 실제로 이 문제의 테스트를 모두 통과한다.

하지만 이건 문제의 제약을 정답 판단에 쓰는 요령이다. 노드 개수의 상한을 모르는 실제 코드에서는 쓸 수 없다. 상한을 너무 낮게 잡으면 긴 정상 리스트를 고리로 오판하고, 너무 높게 잡으면 고리가 있을 때 쓸데없이 오래 돈다. 면접에서 꺼낸다면 "제약이 주어졌으니 이렇게도 되지만"이라는 단서를 붙인다. 상한 없이 고리를 알아내려면 지나간 노드를 기억해야 한다.

## 지나간 노드를 집합에 적어 두기

지나간 노드를 해시 집합(Set)에 넣어 두고, 새 노드에 도착할 때마다 집합에 이미 있는지 확인한다. 이미 있으면 같은 노드를 두 번째 밟은 것이다.

```js
function hasCycle(head) {
  const seen = new Set(); // 지나간 노드 (값이 아니라 노드 객체)
  for (let n = head; n; n = n.next) {
    if (seen.has(n)) return true; // 이미 지나간 노드다
    seen.add(n);
  }
  return false;
}
```

`Set`에 노드 객체를 넣으면 객체의 참조(메모리상의 정체)로 구별한다. 값이 같은 노드가 여러 개 있어도 서로 다른 노드로 들어간다. 값을 넣으면 `[5, 5, 5]`처럼 값이 겹치는 정상 리스트를 고리로 오판한다.

시간 O(n), 공간 O(n)이다. 고리가 있으면 고리 입구에 두 번째로 도착하는 순간 멈추니, 곧은 부분과 고리 한 바퀴만큼 걷는다. 해시 집합의 동작은 [해시맵 글](/posts/ds-hash-map)에 있다.

정직하고 확실한 풀이다. 고리가 시작되는 노드도 바로 알 수 있다. `true`를 돌려주는 그 순간의 `n`이 입구다. 걸리는 건 공간이다. 노드 10^4개면 집합에도 10^4개가 들어간다. LeetCode 문제 아래에도 "O(1) 메모리로 풀 수 있나"라는 후속 질문이 붙어 있다.

## 노드에 다녀간 표시 남기기

집합 대신 노드 자체에 "다녀감" 표시를 남길 수도 있다. 표시가 이미 있는 노드에 도착하면 고리다.

```js
function hasCycle(head) {
  const MARK = Symbol("visited"); // 다른 속성과 겹치지 않는 키
  for (let n = head; n; n = n.next) {
    if (n[MARK]) return true;
    n[MARK] = true;               // 노드에 표시를 남긴다
  }
  return false;
}
```

추가 자료구조가 없어서 공간이 O(1)처럼 보인다. 하지만 노드마다 속성을 하나씩 붙였으니 실제로는 노드 수만큼 메모리를 더 쓴다. 자바스크립트 엔진은 객체에 속성이 추가되면 객체의 내부 모양(hidden class)을 바꾸기도 해서 공짜도 아니다. 값을 특별한 숫자로 덮어쓰는 방식도 있지만, 그 숫자가 원래 값으로 나올 수 없다는 보장이 필요하고 입력을 망가뜨린다.

더 큰 문제는 입력을 바꾼다는 것이다. 검사 함수가 입력을 바꾸면 같은 리스트를 두 번 검사할 때 결과가 달라진다. 표시를 지우는 두 번째 순회를 추가해야 하고, 그 사이에 다른 코드가 리스트를 읽으면 이상한 속성이 보인다. Java처럼 클래스에 필드를 마음대로 붙일 수 없는 언어에서는 노드 정의를 바꿔야 해서 아예 쓸 수 없다.

## 뒤집어 보면 머리로 돌아온다

조금 기묘하지만 실제로 성립하는 풀이가 있다. 리스트를 [Reverse Linked List](/posts/leetcode-reverse-linked-list)의 반복 풀이로 뒤집어 본다. 고리가 없으면 원래 꼬리가 새 머리가 된다. 고리가 있으면 뒤집기를 마쳤을 때 원래 머리로 돌아와 있다.

```js
function hasCycle(head) {
  if (!head || !head.next) return false;
  let prev = null, cur = head;
  while (cur) {
    const next = cur.next;
    cur.next = prev;
    prev = cur;
    cur = next;
  }
  // 고리가 있으면 머리로 돌아와서 끝난다
  return prev === head;
}
```

`1→2→3→4→5→6→3`을 뒤집는다고 해 보자. 1, 2를 지나며 화살표를 돌리고, 고리를 한 바퀴 돌며 3, 4, 5, 6의 화살표를 돌린다. 6 다음은 3인데, 3의 화살표는 이미 2를 향하도록 돌려 놨다. 그래서 3에서 2로, 2에서 1로 거꾸로 걸어 나오며 1, 2의 화살표를 다시 원래대로 돌려놓는다. 1의 `next`는 처음에 `null`로 바꿔 뒀으니 거기서 끝나고, 마지막으로 화살표를 돌린 노드가 1, 즉 원래 머리다.

반복은 고리가 없으면 n번, 있으면 곧은 부분의 두 배와 고리 한 바퀴만큼 돈다. 시간 O(n), 공간 O(1)이다. 한 번 뒤집은 뒤 고리 리스트를 찍어 보면 `1→2→3→6→5→4→3`이다. 곧은 부분은 원래대로 돌아왔지만 고리의 방향이 거꾸로 바뀌었다. 고리가 없을 때는 리스트 전체가 뒤집혀 있다. 한 번 더 뒤집으면 원래대로 돌아오지만, 검사 함수가 입력을 두 번씩 뒤집는 건 앞 절과 같은 이유로 실무에서 쓰기 어렵다. "입력을 바꾸지 않고, 추가 메모리 없이"라는 두 조건을 모두 지키는 풀이가 다음에 나오는 Floyd 알고리즘이다.

## 두 배로 달리는 토끼는 거북이를 따라잡는다

포인터 두 개를 머리에서 같이 출발시킨다. 느린 포인터 `slow`는 한 번에 한 칸, 빠른 포인터 `fast`는 한 번에 두 칸 간다. 거북이와 토끼라고 부른다. 1967년 무렵 Robert Floyd가 고안했다고 알려져서 Floyd의 순환 탐지(cycle detection)라고 한다.

- 고리가 없으면 `fast`가 먼저 끝에 닿는다. `fast`나 `fast.next`가 `null`이 되면 `false`다.
- 고리가 있으면 두 포인터 모두 결국 고리 안으로 들어가 계속 돈다. 고리 안에서 `fast`는 `slow`보다 매번 한 칸씩 더 가니, 둘 사이 간격이 한 칸씩 줄다가 언젠가 같은 노드에 선다. 만나면 `true`다.

아래 그림은 앞에서 본 `[1, 2, 3, 4, 5, 6]`, `pos = 2` 리스트에서 두 포인터가 움직이는 모습이다. 위에 화살표 표시가 붙은 칸이 `slow`, 초록 칸이 `fast`다. 둘이 같은 칸에 있으면 초록 칸 위에 화살표가 붙는다. 6 다음은 3이라는 것만 기억하고 보면 된다.

세 번째 단계부터 보면 된다. 둘 다 고리 안에 있을 때 `fast`가 `slow`를 뒤에서 쫓는다고 보면, 한 번 움직일 때마다 `slow`는 한 칸 달아나고 `fast`는 두 칸 다가오니 간격이 정확히 한 칸 준다. 간격이 2에서 1로, 1에서 0으로 줄어 만났다.

```js
function hasCycle(head) {
  let slow = head, fast = head;

  // fast가 두 칸 갈 수 있는 동안만 돈다
  while (fast && fast.next) {
    slow = slow.next;       // 한 칸
    fast = fast.next.next;  // 두 칸
    if (slow === fast) return true; // 같은 노드에서 만났다
  }
  return false; // fast가 끝에 닿았다. 고리가 없다
}
```

반복 조건 `fast && fast.next`가 고리 없는 경우를 모두 막는다. `fast`가 `null`이면 노드 수가 홀수인 리스트의 끝을 넘어선 것이고, `fast.next`가 `null`이면 `fast`가 마지막 노드에 있어 두 칸을 갈 수 없다. `slow`는 항상 `fast`보다 뒤에 있으니 따로 확인하지 않아도 된다. 빈 리스트는 반복문을 한 번도 안 돌고 `false`다.

시간은 O(n)이다. 고리가 없으면 `fast`가 n/2번 만에 끝에 닿는다. 고리가 있으면 `slow`가 고리에 들어간 뒤 고리 길이 L보다 적은 걸음 안에 만난다. 곧은 부분의 길이를 a라고 하면 반복은 a + L번을 넘지 않고, a + L은 n 이하다. 공간은 포인터 두 개라 O(1)이다. 입력도 바꾸지 않는다.

### 건너뛰지 않고 반드시 만나는 이유

두 칸씩 뛰는 `fast`가 `slow`를 뛰어넘어 지나쳐 버리면 어떡하나 하는 의문이 든다. 지나칠 수 없다. 고리 안에서 `fast`가 `slow`보다 d칸 뒤에 있다고 하자. 한 번 움직이면 `slow`는 한 칸, `fast`는 두 칸 가니 간격이 d - 1이 된다. 간격이 매번 정확히 1씩 줄어서 3, 2, 1, 0으로 가니 0을 건너뛸 수 없다.

언제까지 만나는지도 정해진다. `slow`가 고리에 들어온 순간의 간격 d는 고리 길이 L보다 작다. 그러니 `slow`가 고리 안에서 L걸음을 채우기 전에, 즉 고리를 한 바퀴 다 돌기 전에 만난다.

`fast`를 세 칸씩 보내면 어떨까. 둘 다 머리에서 출발했다면 이것도 결국 만나긴 한다. t번 움직인 뒤 둘의 거리 차이는 2t이고, t가 L의 배수가 되는 순간 고리 안에서 같은 자리에 서기 때문이다. 하지만 간격이 한 번에 2씩 줄어서 서로 지나치는 바퀴가 생길 수 있고, `fast`가 노드를 더 많이 밟는다. 두 칸은 간격이 1씩 줄어서 첫 바퀴 안에 만남이 보장되는 가장 단순한 속도다. 다음 절의 고리 입구 찾기 증명도 "두 배"라는 비율 위에서 깔끔하게 맞아떨어진다.

### Python과 Java로 쓰면

Python에서는 노드 비교에 `is`를 쓴다. `is`는 같은 객체인지 보는 비교라서 이 문제의 뜻과 정확히 맞다. `==`도 `ListNode`가 `__eq__`를 따로 정의하지 않았다면 같은 결과가 나오지만, 누군가 값 비교로 `__eq__`를 정의해 두면 엉뚱하게 동작한다.

```python
class ListNode:
    def __init__(self, x):
        self.val = x
        self.next = None

def has_cycle(head):
    slow = fast = head
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next
        if slow is fast:  # 값이 아니라 같은 노드인지 비교한다
            return True
    return False
```

Java에서는 `==`가 참조 비교라서 이 문제에서는 그대로 맞다. 같은 객체를 가리키는지 확인하는 게 목적이기 때문이다. `equals`를 쓰면 오히려 노드 클래스가 정의한 동등성 기준에 따라 결과가 달라질 수 있다.

```java
public class Solution {
    public boolean hasCycle(ListNode head) {
        ListNode slow = head, fast = head;
        while (fast != null && fast.next != null) {
            slow = slow.next;
            fast = fast.next.next;
            if (slow == fast) return true; // 참조 비교: 같은 객체인가
        }
        return false;
    }
}
```

세 언어 모두 같은 결과가 나온다.

```text
[1,2,3,4,5,6], pos=2   true
[1,2,3,4,5,6], pos=-1  false
[], pos=-1             false
[1], pos=-1            false
[1], pos=0             true
[1,2], pos=0           true
[1,2], pos=-1          false
[5,5,5], pos=1         true
```

## 거북이를 순간이동시키는 Brent 방법

Floyd 알고리즘은 한 번 반복할 때 노드를 세 번 밟는다(`slow` 한 번, `fast` 두 번). 1980년 Richard Brent가 이 횟수를 줄이는 방법을 내놓았다. 거북이는 걷지 않고 제자리에 서 있다가, 토끼가 1, 2, 4, 8, ...걸음을 갈 때마다 토끼 자리로 순간이동한다. 토끼는 한 칸씩만 간다. 토끼가 서 있는 거북이를 다시 만나면 고리다.

```js
function hasCycle(head) {
  if (!head) return false;
  let power = 1;      // 이번 구간의 길이 (1, 2, 4, 8, ...)
  let lam = 1;        // 이번 구간에서 토끼가 간 걸음 수
  let tortoise = head;
  let hare = head.next;

  while (hare && hare !== tortoise) {
    if (power === lam) {   // 구간이 끝났다: 거북이를 토끼 자리로 옮긴다
      tortoise = hare;
      power *= 2;
      lam = 0;
    }
    hare = hare.next;      // 토끼는 한 칸씩
    lam++;
  }
  // 끝에 닿았으면 고리 없음, 거북이를 만났으면 고리 있음
  return hare !== null;
}
```

구간 길이가 두 배씩 늘어나다 보면 언젠가 고리 길이 L 이상이 되고, 그 구간 안에서 토끼가 고리를 한 바퀴 돌아 거북이 자리에 돌아온다. 이때 `lam`이 정확히 고리 길이다. 위 예시 리스트에서 돌려 보면 `lam`이 4로 나온다. 고리 길이까지 덤으로 얻는 셈이다.

시간 O(n), 공간 O(1)로 Floyd와 같다. 차이는 노드를 밟는 횟수다. 곧은 부분 a와 고리 길이 L을 바꿔 가며 `next`를 따라간 횟수를 세어 봤다.

```text
a = 100000,  L = 100000   Floyd 300000   Brent 231071
a = 10,      L = 1000000  Floyd 3000000  Brent 2048575
a = 1000000, L = 10       Floyd 3000000  Brent 1048585
```

곧은 부분이 길수록 차이가 크다. `next`를 따라가는 게 싼 연결 리스트에서는 체감되지 않지만, 다음 값을 구하는 게 비싼 함수(예: 난수 생성기의 주기 찾기, 폴라드 로 소인수분해)라면 의미가 있다. 면접에서는 Floyd면 충분하고, Brent는 "더 줄일 수 있나"를 물을 때 이름과 아이디어를 말할 수 있으면 된다.

## 여섯 풀이를 나란히 놓으면

| 풀이 | 시간 | 공간 | 입력 변경 | 언제 고르나 |
|---|---|---|---|---|
| 상한만큼 걷기 | O(n) | O(1) | 없음 | 노드 수 상한이 확실할 때만. 실무에서는 쓰지 않는다 |
| 해시 집합 | O(n) | O(n) | 없음 | 가장 이해하기 쉽다. 입구도 바로 나온다 |
| 노드에 표시 | O(n) | 노드마다 속성 하나 | 있음 | 노드에 필드를 붙일 수 있고 입력을 바꿔도 될 때 |
| 뒤집어 보기 | O(n) | O(1) | 있음 (고리 방향이 바뀜) | 기묘한 성질을 아는지 보여 줄 때 |
| Floyd 토끼와 거북이 | O(n) | O(1) | 없음 | 기본 답. 입구 찾기로 바로 이어진다 |
| Brent | O(n) | O(1) | 없음 | 다음 값을 구하는 비용이 비쌀 때, 고리 길이도 필요할 때 |

면접에서는 해시 집합으로 먼저 설명하고, O(1) 공간을 요구받으면 Floyd로 넘어가는 흐름이 자연스럽다. 이어서 "입구는 어디인가"를 물을 가능성이 높으니 아래 증명까지 준비해 두면 좋다.

## 비교와 종료 조건에서 나는 실수

값으로 비교하는 실수가 가장 흔하다. `slow.val === fast.val`로 쓰면 값이 겹치는 정상 리스트를 고리로 판단한다. Python으로 `[1, 2, 1, 2, 1]`(고리 없음)을 넣어 보면 두 번째 반복에서 `slow`와 `fast`가 서로 다른 노드인데 둘 다 값이 1이라서 `True`가 나온다. `[5, 5, 5]`는 첫 반복에서 바로 틀린다. 비교 대상은 노드 자체다.

반복 조건을 `while (fast.next)`처럼 반만 쓰면 노드 수가 짝수인 리스트에서 터진다. `fast`가 두 칸씩 뛰다 `null`에 떨어지면 다음 조건 검사에서 `null.next`를 읽어 `TypeError`가 난다. `fast && fast.next`를 둘 다 확인해야 한다. 순서도 중요하다. `fast.next && fast`로 쓰면 `fast`가 `null`일 때 앞부분에서 이미 터진다.

움직이기 전에 비교하는 실수도 있다.

```js
// 출발하자마자 비교하는 코드
let slow = head, fast = head;
while (fast && fast.next) {
  if (slow === fast) return true; // 첫 바퀴에 둘 다 head라서 바로 true
  slow = slow.next;
  fast = fast.next.next;
}
```

둘 다 `head`에서 출발하니 첫 비교가 무조건 참이다. 비교는 움직인 다음에 한다. 굳이 비교를 앞에 두려면 `fast`를 `head.next`에서 출발시켜야 하는데, 그러면 뒤에 나올 입구 찾기 공식이 한 칸 어긋난다. 출발점은 둘 다 `head`로 두고 움직인 뒤 비교하는 모양을 기본으로 외워 두는 게 편하다.

빈 리스트와 노드 하나짜리는 Floyd 코드가 따로 처리하지 않아도 된다. 빈 리스트는 `fast`가 `null`이라 바로 `false`이고, 노드 하나에 고리가 없으면 `fast.next`가 `null`이라 `false`다. 노드 하나가 자기 자신을 가리키면 첫 반복에서 `slow`와 `fast`가 모두 그 노드로 돌아와 `true`다. 해시 집합 풀이도 마찬가지로 이 경우들을 자연스럽게 처리한다.

## 고리의 입구, 길이, 다른 모양의 고리

### 고리가 시작되는 노드를 찾으라면

LeetCode 142 Linked List Cycle II다. 해시 집합 풀이라면 처음 다시 만난 노드가 바로 입구다. O(1) 공간으로 하려면 Floyd 알고리즘에 한 단계를 더한다. 두 포인터가 만나면, 포인터 하나를 머리로 보내고 둘 다 한 칸씩 움직인다. 다시 만나는 곳이 입구다.

```js
function detectCycle(head) {
  let slow = head, fast = head;
  while (fast && fast.next) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) {
      let p = head;                 // 하나는 머리에서, 하나는 만난 곳에서
      while (p !== slow) { p = p.next; slow = slow.next; }
      return p;                     // 같은 속도로 걸어 만나는 곳이 입구
    }
  }
  return null;
}
// [1,2,3,4,5,6], pos=2 → 3번째 노드(인덱스 2)
// [1,2,3,4,5,6], pos=0 → 인덱스 0,  pos=5 → 인덱스 5
```

이게 왜 맞는지 계산해 보자. 머리에서 입구까지 a칸, 입구에서 만난 곳까지 b칸, 고리 길이를 L이라고 하자. 만날 때까지 `slow`는 a + b칸을 걸었다. `fast`는 두 배인 2(a + b)칸을 걸었고, 그 사이 고리를 k바퀴 더 돌았으니 a + b + kL칸이기도 하다. 두 식을 같다고 놓으면 a + b = kL, 정리하면 a = kL - b다. 만난 곳에서 a칸을 더 가면 kL - b칸을 가는 것이니, b만큼 덜 돈 k바퀴가 되어 정확히 입구에 선다. 머리에서 a칸을 간 포인터도 입구에 선다. 그래서 둘이 입구에서 만난다.

위 예시로 확인해 보면 a = 2, 만난 곳은 5번 값(입구 3에서 두 칸), b = 2, L = 4다. a = 4 - 2 = 2가 맞다. 머리 1에서 두 칸 가면 3, 만난 곳 5에서 두 칸(5→6→3) 가도 3이다.

Python으로 옮기면 두 단계가 그대로 보인다. 다중 대입으로 두 포인터를 한 줄에 움직인다.

```python
def detect_cycle(head):
    slow = fast = head
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
        if slow is fast:
            p = head                      # 2단계: 머리와 만난 곳에서 한 칸씩
            while p is not slow:
                p, slow = p.next, slow.next
            return p                      # 입구
    return None
```

`[1,2,3,4,5,6]`에 `pos`를 2, 0으로 주면 각각 인덱스 2, 0인 노드가 나오고, 고리가 없는 `[1, 2]`는 `None`, 자기 자신을 가리키는 `[1]`은 그 노드 자신이 나온다. 곧은 부분이 없으면(a = 0) 2단계 반복문은 한 번도 돌지 않는다.

### 고리의 길이를 구하라면

만난 곳에서 한 포인터만 고정하고 다른 포인터로 한 바퀴 돌며 센다. 만난 노드는 반드시 고리 안에 있으니 한 바퀴가 곧 고리 길이다. 위 예시에서는 4가 나온다. Brent 방법을 쓰면 탐지와 동시에 길이가 나온다.

### 배열에서 중복 숫자를 찾으라면

LeetCode 287 Find the Duplicate Number는 1부터 n까지의 숫자가 n + 1칸 배열에 들어 있고 한 숫자만 중복될 때 그 숫자를 찾는다. 배열을 바꾸지 말고 O(1) 공간으로 풀어야 한다. 칸 i에서 `nums[i]`번 칸으로 가는 화살표가 있다고 보면 배열이 연결 리스트가 된다. 중복 숫자는 두 칸에서 같은 칸을 가리키니 바로 그 칸이 고리의 입구다.

```js
function findDuplicate(nums) {
  let slow = nums[0], fast = nums[0];
  do {
    slow = nums[slow];          // 한 칸
    fast = nums[nums[fast]];    // 두 칸
  } while (slow !== fast);
  let p = nums[0];              // 입구 찾기
  while (p !== slow) { p = nums[p]; slow = nums[slow]; }
  return p;
}
// [1,3,4,2,2] → 2,  [3,1,3,4,2] → 3,  [1,1] → 1
```

여기서는 `do...while`로 출발 직후의 비교를 피했다. 앞 절의 "움직인 뒤 비교" 규칙을 다른 모양으로 쓴 것이다.

### 숫자를 바꾸는 규칙이 고리를 만든다면

[Happy Number](/posts/leetcode-happy-number)는 각 자리 숫자의 제곱을 더하는 일을 반복해서 1이 되는지 보는 문제다. 1이 안 되는 숫자는 같은 값들을 끝없이 돈다. 연결 리스트는 없지만 "다음 값을 구하는 함수"가 있으니 토끼와 거북이를 그대로 쓸 수 있다. `next` 대신 그 함수를 한 번, 두 번 부르면 된다. 이처럼 Floyd 알고리즘은 연결 리스트가 아니라 "다음 상태가 하나로 정해지는 모든 반복"에 쓰인다.

### 리스트의 가운데를 찾으라면

LeetCode 876 Middle of the Linked List는 같은 두 속도 포인터로 푼다. `fast`가 끝에 닿을 때 `slow`는 절반만 왔으니 가운데에 있다. 노드가 짝수 개면 이 코드는 두 가운데 중 뒤쪽을 고른다. `[1,2,3,4,5]`에서 3, `[1,2,3,4,5,6]`에서 4다. [Reorder List](/posts/leetcode-reorder-list)와 회문 연결 리스트 문제가 이 가운데 찾기로 시작한다.

### 두 리스트가 만나는 지점을 찾으라면

LeetCode 160 Intersection of Two Linked Lists는 두 리스트가 어느 노드부터 꼬리를 공유하는지 찾는다. 한 리스트의 꼬리를 다른 리스트의 머리에 잠깐 이으면 고리 입구 찾기 문제가 되지만, 입력을 바꾸지 않는 풀이가 더 흔하다. 두 포인터가 각자 리스트를 다 걸으면 상대 리스트의 머리로 건너가게 하면, 둘 다 같은 거리(두 길이의 합)를 걷고 교차점에서 만난다.

## 실제 코드에서 고리를 만나는 순간

LeetCode 밖에서 고리는 주로 객체 그래프에서 만난다. 부모와 자식이 서로를 참조하는 트리, 서로를 가리키는 두 객체가 그렇다. 이런 객체를 `JSON.stringify`에 넘기면 Node.js 22에서 이렇게 멈춘다.

```text
TypeError: Converting circular structure to JSON
    --> starting at object with constructor 'Object'
    |     property 'next' -> object with constructor 'Object'
    --- property 'next' closes the circle
```

`JSON.stringify`는 지금 직렬화 중인 객체들을 스택에 들고 있다가 같은 객체를 다시 만나면 이 오류를 낸다. 이 글의 해시 집합 풀이와 같은 생각이다. 오류 메시지가 고리를 닫는 속성 이름(`next`)까지 알려 주니, 로그 직렬화에서 이 오류가 나면 그 속성부터 본다. 반대로 `structuredClone`은 고리가 있는 객체도 복사한다. 이미 복사한 객체를 맵에 기억해 두고, 다시 만나면 새로 만들지 않고 기억한 복사본을 가리키게 하기 때문이다.

연결 리스트를 직접 다루는 코드에서 고리는 대부분 버그로 생긴다. 노드를 옮기면서 옛 `next`를 끊지 않으면 생긴다. [Reverse Linked List](/posts/leetcode-reverse-linked-list)의 재귀 풀이에서 `head.next = null`을 빼먹거나, 리스트를 둘로 자르면서 앞쪽 끝을 `null`로 만들지 않을 때가 그렇다. 증상은 "출력 함수가 안 끝난다", "테스트가 시간 초과로 죽는다"로 나타난다. 의심되면 디버깅용으로 Floyd 검사를 끼워 넣으면 어느 연산 뒤에 고리가 생겼는지 바로 좁힐 수 있다.

## 같은 노드를 다시 밟았는가

고리 탐지는 "같은 노드를 다시 밟았는가"를 알아내는 문제다. 지나간 노드를 집합에 적으면 O(n) 공간으로 쉽게 풀리고, 속도가 두 배인 포인터 두 개를 보내면 고리 안에서 간격이 한 칸씩 줄어 반드시 만나므로 O(1) 공간으로 풀린다. 만난 뒤 한 포인터를 머리로 보내 같은 속도로 걸으면 a = kL - b라는 관계 때문에 고리 입구에서 다시 만난다. 비교는 값이 아니라 노드로, 움직인 다음에 한다는 것까지 기억하면 변형 문제가 나와도 흔들리지 않는다.

## 면접에서 나올 만한 질문

### 해시 집합 풀이와 Floyd 풀이는 무엇이 다른가요?

둘 다 시간은 O(n)이다. 해시 집합은 지나간 노드를 모두 저장해서 O(n) 공간이 들지만 고리 입구를 바로 알 수 있다. Floyd는 포인터 두 개로 O(1) 공간에 풀고 입력도 바꾸지 않는다. 입구가 필요하면 Floyd에 한 단계를 더해 찾는다.

### fast가 slow를 건너뛰어 지나칠 수는 없나요?

없다. 둘 다 고리 안에 있으면 한 번 움직일 때 `slow`는 한 칸 달아나고 `fast`는 두 칸 오니 간격이 정확히 1씩 준다. 간격이 3, 2, 1, 0으로 줄어드니 0을 건너뛸 수 없다. 처음 간격이 고리 길이보다 작으니 `slow`가 고리를 한 바퀴 돌기 전에 만난다.

### 왜 fast를 두 칸으로 하나요? 세 칸이면 안 되나요?

둘 다 머리에서 출발하면 세 칸이어도 결국 만나긴 한다. 하지만 간격이 2씩 줄어 서로 지나치는 바퀴가 생길 수 있고 노드를 더 많이 밟는다. 두 칸은 간격이 1씩 줄어 첫 바퀴 안에 만남이 보장되고, 입구 찾기 공식 a = kL - b도 두 배라는 비율에서 나온다.

### 고리의 시작 노드는 어떻게 찾나요?

두 포인터가 만나면 하나를 머리로 보내고 둘 다 한 칸씩 움직여서, 다시 만나는 노드가 입구다. 만날 때까지 `slow`가 a + b, `fast`가 2(a + b) = a + b + kL을 걸었으니 a = kL - b가 된다. 그래서 머리에서 a칸, 만난 곳에서 a칸 가면 둘 다 입구에 선다.

### 노드 값을 비교하면 왜 안 되나요?

값은 중복될 수 있기 때문이다. `[5, 5, 5]`처럼 값이 같은 정상 리스트에서 서로 다른 노드가 같은 값을 가져 고리로 오판한다. 고리는 "같은 노드를 다시 밟는 것"이니 노드 참조를 비교해야 한다. Python은 `is`, Java와 JS는 객체에 대한 `==`, `===`가 참조 비교다.

### 입력을 바꿔도 된다면 다른 방법이 있나요?

노드에 방문 표시를 붙이거나, 리스트를 뒤집어서 원래 머리로 돌아오는지 보는 방법이 있다. 둘 다 O(1) 추가 자료구조로 동작하지만, 검사 함수가 입력을 바꾸니 원래대로 돌려놓는 작업이 필요하고 그 사이 다른 코드가 깨진 리스트를 볼 수 있다. 그래서 실무에서는 Floyd를 쓴다.

### 연결 리스트가 아닌 곳에도 쓸 수 있나요?

다음 상태가 하나로 정해지는 반복이라면 어디든 쓴다. Happy Number처럼 숫자를 바꾸는 규칙이 같은 값을 맴도는지 보거나, 배열 값을 다음 칸 번호로 보고 중복 숫자를 찾는 LeetCode 287이 그렇다. 난수 생성기의 주기 찾기나 폴라드 로 소인수분해도 같은 아이디어를 쓴다.
