PR을 올렸는데 GitHub의 병합 버튼이 잠겨 있다. 필수 상태 체크 `continuous-integration/jenkins/pr-merge`가 "Expected — Waiting for status to be reported"에서 움직이지 않는다. Jenkins 화면에 가 보면 빌드는 대기열에 올라가 있고, 옆에 이런 줄이 떠 있다.

```text
Still waiting to schedule task
There are no nodes with the label ‘docker’
```

코드에는 문제가 없다. 이 빌드를 돌릴 기계가 없을 뿐이다. Jenkins 파이프라인은 Jenkinsfile 한 장으로 보이지만, 그 뒤에는 일을 나눠 주는 컨트롤러, 실제로 돌리는 에이전트, GitHub와 주고받는 웹훅과 상태 체크, 비밀값 저장소가 함께 움직인다. 어느 하나가 어긋나면 위처럼 "빌드가 안 돈다"는 하나의 증상으로 보인다.

이 글은 그 부품들을 하나씩 짚는다. 선언형 Jenkinsfile의 뼈대(`stages`, `when`, `parallel`, `post`), 브랜치마다 잡이 생기는 multibranch pipeline과 GitHub 웹훅, 비밀값을 꺼내 쓰는 법, 공용 단계를 모으는 shared library, 결과물과 캐시를 남기는 자리, 그리고 자주 깨지는 지점과 확인 순서다.

이 주제의 다른 글: 파이프라인이 무엇을 보장해야 하는지는 [CI/CD 기본](/posts/ci-cd-basics), 같은 일을 GitHub Actions로 하는 법은 [GitHub Actions로 Docker 이미지를 ECR에 올리기](/posts/github-actions-docker-ecr), 캐시 키와 원격 캐시는 [빌드 캐시](/posts/build-caching)에서 다룬다. 여기서는 그 내용을 되풀이하지 않고 Jenkins에서 달라지는 부분만 쓴다.

이 글의 Jenkins 콘솔 출력은 직접 돌린 결과가 아니라 예시다. 글을 쓴 환경에서는 Jenkins 배포 서버(get.jenkins.io, updates.jenkins.io)에 접속할 수 없어서 Jenkins와 플러그인을 내려받지 못했다. 출력은 Jenkins 2.4xx LTS의 콘솔 형식에 맞춰 적었고, 버전마다 문구가 조금씩 다를 수 있다. `when` 조건을 흉내 낸 코드만 Node.js 22에서 실제로 돌렸다.

## 일을 나눠 주는 쪽과 돌리는 쪽

Jenkins 서버 하나를 컨트롤러(controller, 예전 이름은 master)라고 부른다. 컨트롤러는 잡 설정, 빌드 기록, 플러그인, 비밀값을 갖고 있고 웹 화면과 API를 연다. 빌드를 실제로 돌리는 기계는 에이전트(agent, 예전 이름은 slave 또는 node)다. 에이전트마다 동시에 몇 개의 빌드를 돌릴지 정하는 칸이 있는데, 이것을 executor라고 한다.

컨트롤러에서도 빌드를 돌릴 수 있지만 운영에서는 컨트롤러의 executor를 0으로 둔다. 빌드 스크립트는 그 기계의 파일을 읽고 쓸 수 있어서, 컨트롤러에서 돌면 `$JENKINS_HOME` 안의 비밀값과 설정까지 손이 닿는다. 무거운 빌드가 컨트롤러의 CPU와 메모리를 먹으면 웹 화면과 웹훅 처리까지 느려진다.

잡은 에이전트 이름이 아니라 레이블(label)로 기계를 고른다. Jenkinsfile에 `agent { label 'docker' }`라고 쓰면 `docker` 레이블이 붙은 에이전트 중 executor가 빈 곳에 배정된다. 처음 장면의 "There are no nodes with the label ‘docker’"는 그 레이블을 가진 에이전트가 하나도 없거나 전부 오프라인이라는 뜻이다.

에이전트를 붙이는 방식은 크게 둘이다.

- 컨트롤러가 SSH로 에이전트 기계에 접속해 에이전트 프로세스를 띄운다. 에이전트가 고정된 서버일 때 쓴다.
- 에이전트가 컨트롤러로 먼저 접속한다(inbound agent, 예전 이름 JNLP). 에이전트가 방화벽 안쪽에 있어 컨트롤러가 들어갈 수 없을 때 쓴다. TCP 포트를 따로 열거나 WebSocket으로 HTTP 포트 하나만 쓴다.

요즘은 빌드마다 에이전트를 새로 만들고 끝나면 지우는 방식이 많다. Kubernetes 플러그인은 빌드가 들어오면 파드 하나를 에이전트로 띄우고, 끝나면 지운다. 빌드끼리 디스크를 나눠 쓰지 않으니 앞 빌드의 찌꺼기가 다음 빌드를 망치는 일이 없다. 대신 매번 빈 디스크에서 시작하니 의존성 캐시를 따로 챙겨야 한다(뒤에서 다시 본다).

## 선언형 Jenkinsfile 한 장

Jenkinsfile은 저장소 루트에 두는 파이프라인 정의다. 문법은 Groovy 위에 얹은 두 가지가 있다. 처음부터 Groovy 코드로 쓰는 scripted pipeline(`node { ... }`)과, 정해진 틀에 값을 채우는 declarative pipeline(`pipeline { ... }`)이다. 새로 쓴다면 선언형으로 시작한다. 틀이 정해져 있어 저장할 때 문법 검사를 하고, `when`·`post`·`options` 같은 흔한 요구가 이미 키워드로 있다. 선언형 안에서도 복잡한 로직이 필요하면 `script { }` 블록에 Groovy를 쓸 수 있지만, 그 블록이 길어지면 shared library로 옮길 때다.

실제로 쓸 만한 모양으로 하나 적어 보면 이렇다. 주문 서비스를 빌드하고, 테스트를 둘로 나눠 동시에 돌리고, main일 때만 이미지를 올린다.

```groovy
pipeline {
  agent { label 'docker' }
  options {
    timeout(time: 30, unit: 'MINUTES')            // 30분 넘으면 끊는다
    disableConcurrentBuilds()                     // 같은 브랜치 빌드는 하나씩
    buildDiscarder(logRotator(numToKeepStr: '30')) // 빌드 기록은 30개만
  }
  environment {
    IMAGE = "registry.example.com/shop/order:${env.GIT_COMMIT.take(12)}"
  }
  stages {
    stage('Build') {
      steps { sh './gradlew --no-daemon assemble' }
    }
    stage('Test') {
      parallel {
        stage('Unit')        { steps { sh './gradlew --no-daemon test' } }
        stage('Integration') { steps { sh './gradlew --no-daemon integrationTest' } }
      }
    }
    stage('Push image') {
      when { branch 'main' }                       // PR 빌드에서는 건너뛴다
      steps {
        withCredentials([usernamePassword(credentialsId: 'registry-bot',
            usernameVariable: 'REG_USER', passwordVariable: 'REG_PASS')]) {
          sh 'echo "$REG_PASS" | docker login registry.example.com -u "$REG_USER" --password-stdin'
          sh 'docker build -t "$IMAGE" . && docker push "$IMAGE"'
        }
      }
    }
  }
  post {
    always  { junit allowEmptyResults: true, testResults: '**/build/test-results/**/*.xml' }
    failure { echo "빌드 실패: ${env.BUILD_URL}" }
    cleanup { cleanWs() }                          // 작업 공간을 비운다
  }
}
```

`sh` 안의 문자열을 작은따옴표로 쓴 것을 눈여겨본다. 작은따옴표 안의 `$IMAGE`, `$REG_PASS`는 Groovy가 건드리지 않고 셸이 환경 변수로 읽는다. 큰따옴표로 쓰면 Groovy가 먼저 값을 끼워 넣어 명령 문자열 자체에 비밀값이 박힌다. 이 차이는 비밀값을 다루는 부분에서 다시 본다.

PR 빌드에서 `Push image`는 이렇게 건너뛴다(예시).

```text
[Pipeline] stage
[Pipeline] { (Push image)
Stage "Push image" skipped due to when conditional
[Pipeline] }
[Pipeline] // stage
```

Jenkinsfile을 저장소에 올리기 전에 문법을 확인하고 싶으면 컨트롤러의 검사 API를 쓴다. 선언형 문법만 검사하고, 플러그인이 제공하는 단계 이름이 맞는지까지는 다 보지 않는다.

## 단계를 건너뛰는 조건

`when`은 단계를 돌릴지 정하는 조건이다. 실무에서 자주 쓰는 건 몇 가지다.

- `branch 'release/*'`: 빌드 중인 브랜치 이름이 패턴과 맞을 때. Ant 스타일 패턴이라 `*`는 `/`를 넘지 않는다.
- `changeRequest()`: PR 빌드일 때. multibranch에서 PR 빌드의 브랜치 이름은 `PR-42` 같은 꼴이라, PR 빌드에서 `branch 'main'`은 거짓이다.
- `changeset 'src/**'`: 이번 빌드에 들어온 변경 파일 중 패턴과 맞는 것이 있을 때. 문서만 고친 커밋에서 무거운 테스트를 건너뛸 때 쓴다.
- `environment name: 'DEPLOY', value: 'true'`: 환경 변수 값이 같을 때.
- `allOf`, `anyOf`, `not`: 조건을 묶는다. `when` 안에 조건을 여러 개 나란히 쓰면 모두 참이어야 한다.

`changeset`에는 잘 알려진 함정이 있다. 변경 목록은 "이 잡의 이전 빌드 이후 들어온 커밋"으로 만든다. 새 브랜치의 첫 빌드처럼 비교할 이전 빌드가 없으면 변경 목록이 비어서, `src/`를 고쳤는데도 단계가 건너뛰어진다. PR이라면 대상 브랜치와 비교한 변경이 필요한데, 그건 `changeset`이 아니라 `git diff --name-only origin/main...HEAD`를 직접 돌려서 판단하는 편이 확실하다.

또 하나, `when`은 기본적으로 에이전트를 잡은 뒤에 평가한다. 어차피 건너뛸 단계인데 에이전트 파드를 띄우느라 1분을 기다리는 일이 생긴다. stage에 따로 `agent`를 준 경우라면 `when { beforeAgent true; branch 'main' }`처럼 써서 조건부터 본다.

아래에서 `when` 판정을 직접 만들어 본다. `when`은 조건 이름을 키로 갖는 객체이고, 나란히 놓인 조건은 모두 참이어야 한다. `ctx`는 빌드의 브랜치, PR 여부, 변경 파일, 환경 변수다. 패턴의 `*`는 `/`를 넘지 않고 `**`는 넘는다.

  solution={`function shouldRun(when, ctx) {
  const glob = (pattern, text) => {
    const re = pattern
      .replace(/[.+^\${}()|[\\]\\\\]/g, "\\\\$&")
      .replace(/\\*\\*/g, "\\u0000")
      .replace(/\\*/g, "[^/]*")
      .replace(/\\u0000/g, ".*");
    return new RegExp("^" + re + "$").test(text);
  };
  const checks = {
    branch: (p) => glob(p, ctx.branch),
    changeRequest: (v) => ctx.isPR === v,
    changeset: (p) => ctx.changedFiles.some((f) => glob(p, f)),
    environment: (e) => ctx.env[e.name] === e.value,
    allOf: (list) => list.every((w) => shouldRun(w, ctx)),
    anyOf: (list) => list.some((w) => shouldRun(w, ctx)),
    not: (w) => !shouldRun(w, ctx),
  };
  return Object.entries(when).every(([k, v]) => checks[k](v));
}`}

## 병렬 단계와 post가 결과를 정하는 순서

`parallel` 안의 단계들은 각자 에이전트 executor를 잡고 동시에 돈다. 하나가 실패해도 기본으로는 나머지가 끝까지 돈 뒤에 전체가 실패로 끝난다. 실패하면 바로 나머지를 멈추고 싶으면 `failFast true`를 주거나 `options { parallelsAlwaysFailFast() }`를 쓴다. 느린 통합 테스트를 30분 기다렸다가 단위 테스트 실패를 확인하는 일이 줄어든다. 대신 멈춘 쪽의 결과는 끝까지 알 수 없다.

빌드 결과는 SUCCESS, UNSTABLE, FAILURE, ABORTED 중 하나다. UNSTABLE은 명령은 성공했는데 테스트 리포트에 실패가 있을 때다. `junit` 단계가 실패한 테스트를 찾으면 빌드를 UNSTABLE로 바꾼다. `sh`가 0이 아닌 코드로 끝나면 FAILURE다. 사람이 중지하거나 `timeout`이 끊으면 ABORTED다.

`post`의 조건은 위에서 쓴 순서와 상관없이 정해진 순서로 평가된다. always, changed, fixed, regression, aborted, failure, success, unstable, unsuccessful, 마지막으로 cleanup이다. cleanup이 언제나 맨 끝이라서 작업 공간 지우기는 cleanup에 둔다. always에 두면 그 뒤의 failure 블록이 쓰려던 파일이 이미 지워져 있을 수 있다.

## 브랜치마다 잡이 생기는 multibranch pipeline

잡을 하나 만들고 브랜치를 손으로 바꿔 가며 빌드하던 시절에는 PR마다 잡을 복사했다. multibranch pipeline은 저장소 하나를 등록해 두면 Jenkinsfile이 있는 브랜치와 PR마다 하위 잡을 자동으로 만든다. 브랜치가 지워지거나 PR이 닫히면 하위 잡도 정리한다(orphaned item strategy로 얼마나 남길지 정한다). 조직 전체를 등록하는 organization folder를 쓰면 저장소도 자동으로 찾는다.

GitHub와 잇는 건 GitHub Branch Source 플러그인이다. GitHub App이나 토큰으로 저장소를 읽고, 커밋에 상태를 단다. GitHub Enterprise Server라면 API 주소를 `https://github.example.com/api/v3`처럼 서버 주소로 바꿔 등록한다. 그 외의 흐름은 github.com과 같다.

PR 빌드에는 무엇을 빌드할지 고르는 전략이 있다.

- PR 머리 커밋을 그대로 빌드한다(상태 이름 `continuous-integration/jenkins/pr-head`).
- PR을 대상 브랜치에 병합해 본 결과를 빌드한다(`continuous-integration/jenkins/pr-merge`). 병합하면 깨지는 변경을 미리 잡는다. 대신 대상 브랜치가 움직이면 같은 PR이라도 빌드할 내용이 바뀐다.

어느 쪽을 쓰든 브랜치 보호 규칙의 필수 상태 체크 이름과 똑같아야 한다. 전략을 바꾸면 상태 이름이 바뀌고, 필수 체크는 옛 이름을 계속 기다린다. 처음 장면처럼 "Waiting for status to be reported"가 풀리지 않는 흔한 원인이다.

외부 PR의 Jenkinsfile 이야기는 짚고 넘어간다. PR 작성자가 Jenkinsfile을 고쳐 `sh 'cat ~/.aws/credentials'` 같은 명령을 넣으면, 그 PR 빌드가 에이전트의 비밀값을 읽을 수 있다. GitHub Branch Source는 포크에서 온 PR을 어떻게 믿을지 고르는 설정(Trust)을 두고, 믿지 않는 PR에는 대상 브랜치의 Jenkinsfile을 쓴다. 공개 저장소라면 이 설정을 기본값 그대로 두지 말고 확인한다.

웹훅이 안 오면 빌드가 아예 시작되지 않는다. 그래서 multibranch 프로젝트에는 주기적 재검색(Scan Multibranch Pipeline Triggers, 예: 1시간마다)을 같이 걸어 둔다. 웹훅을 놓쳐도 늦게라도 빌드가 돈다. 원인을 찾을 때는 GitHub 저장소 설정의 Webhooks → Recent Deliveries에서 응답 코드를 본다. 200이 아니라면 Jenkins까지 오지 못한 것이고(사내 방화벽, 리버스 프록시 경로, TLS 인증서), 200인데 빌드가 없다면 Jenkins 쪽에서 저장소와 브랜치를 못 맞춘 것이다(저장소 URL 표기, 브랜치 이름 필터). 웹훅 자체의 서명 검증과 재전송은 [웹훅](/posts/webhooks) 글에서 다룬다.

## 비밀값은 필요한 단계에서만 꺼낸다

Jenkins는 비밀값을 credentials로 저장한다. 사용자 이름과 비밀번호, 비밀 문자열, SSH 키, 파일 같은 종류가 있고, 시스템 전체 또는 폴더 단위로 범위를 둔다. 팀마다 폴더를 나누고 그 폴더에만 credentials를 두면, 다른 팀의 Jenkinsfile이 ID를 알아도 쓰지 못한다.

꺼내 쓰는 방법은 두 가지다. `environment { TOKEN = credentials('deploy-token') }`는 파이프라인 전체에서, `withCredentials([...]) { }`는 블록 안에서만 쓴다. 범위가 좁은 `withCredentials`를 기본으로 한다. 꺼낸 값이 콘솔 로그에 그대로 찍히면 Jenkins가 `****`로 가린다(예시).

```text
[Pipeline] withCredentials
Masking supported pattern matches of $REG_PASS
[Pipeline] {
[Pipeline] sh
+ echo ****
+ docker login registry.example.com -u shop-bot --password-stdin
Login Succeeded
```

가리기는 로그에 나온 글자가 비밀값과 똑같을 때만 동작한다. `echo "$REG_PASS" | base64`처럼 모양을 바꾸면 그대로 찍힌다. 가리기는 실수를 줄이는 장치일 뿐, 비밀값을 로그에 쓰지 않는 습관이 우선이다.

더 자주 나는 실수는 앞에서 본 따옴표다. 큰따옴표 안에 비밀값을 끼워 넣으면 Jenkins가 경고를 남긴다(예시).

```groovy
// 나쁜 예: Groovy가 먼저 값을 끼워 넣는다
sh "curl -H 'Authorization: Bearer ${TOKEN}' https://api.example.com/deploy"
// 좋은 예: 셸이 환경 변수로 읽는다
sh 'curl -H "Authorization: Bearer $TOKEN" https://api.example.com/deploy'
```

```text
Warning: A secret was passed to "sh" using Groovy String interpolation, which is insecure.
		 Affected argument(s) used the following variable(s): [TOKEN]
```

큰따옴표 쪽은 비밀값이 명령 문자열에 박힌 채로 에이전트에 넘어가서, 그 기계의 프로세스 목록(`ps`)에도 보일 수 있다. 작은따옴표 쪽은 명령 문자열에 `$TOKEN`이라는 글자만 있고 값은 환경 변수로 넘어간다.

클라우드 자격 증명은 오래 사는 키를 credentials에 넣기보다, 에이전트가 도는 곳의 역할을 쓰는 쪽이 낫다. EC2 인스턴스 프로파일이나 EKS의 IRSA·Pod Identity처럼 에이전트 자체가 잠깐 쓰는 자격을 받게 하면 Jenkins에 키를 저장하지 않아도 된다. GitHub Actions에서 OIDC로 같은 목표를 이루는 방법은 [GitHub Actions 글](/posts/github-actions-docker-ecr)에 있다.

## 여러 저장소가 같은 단계를 쓸 때

서비스가 스무 개면 Jenkinsfile도 스무 장이다. 이미지 빌드·푸시, 보안 검사, 배포 알림 같은 단계가 저장소마다 복사되고, 레지스트리 주소가 바뀌면 스무 군데를 고친다. shared library는 이 공용 단계를 별도 Git 저장소에 모아 두고 Jenkinsfile에서 불러 쓰는 장치다.

```text
ci-lib/
├── vars/
│   └── buildAndPush.groovy     # Jenkinsfile에서 buildAndPush(...)로 부르는 단계
├── src/com/example/ci/
│   └── Version.groovy          # 일반 Groovy 클래스
└── resources/
    └── trivy-ignore.txt        # libraryResource로 읽는 파일
```

```groovy
// vars/buildAndPush.groovy
def call(Map args) {
  def image = "registry.example.com/${args.name}:${env.GIT_COMMIT.take(12)}"
  withCredentials([usernamePassword(credentialsId: 'registry-bot',
      usernameVariable: 'REG_USER', passwordVariable: 'REG_PASS')]) {
    sh 'echo "$REG_PASS" | docker login registry.example.com -u "$REG_USER" --password-stdin'
    sh "docker build -t ${image} . && docker push ${image}"
  }
  return image
}
```

```groovy
// 서비스의 Jenkinsfile
@Library('ci-lib@v1.4.0') _
pipeline {
  agent { label 'docker' }
  stages {
    stage('Push image') {
      when { branch 'main' }
      steps { script { env.IMAGE = buildAndPush(name: 'shop/order') } }
    }
  }
}
```

`@Library('ci-lib@v1.4.0')`처럼 태그로 버전을 고정한다. `@main`으로 두면 라이브러리를 고친 순간 스무 개 서비스의 빌드가 한꺼번에 바뀌고, 하나가 깨지면 전부 깨진다. 라이브러리를 바꿀 때는 새 태그를 만들고 서비스 하나에서 먼저 올려 본다.

shared library는 등록 방식에 따라 신뢰 수준이 다르다. 컨트롤러 전역 설정에 등록한 라이브러리는 샌드박스 밖에서 돌아서 아무 Groovy 메서드나 부를 수 있다. 그래서 그 저장소에 쓰기 권한을 가진 사람은 사실상 Jenkins 관리자와 같다. 폴더에 등록한 라이브러리와 Jenkinsfile은 샌드박스 안에서 돌고, 허락되지 않은 메서드를 부르면 이렇게 멈춘다(예시).

```text
org.jenkinsci.plugins.scriptsecurity.sandbox.RejectedAccessException: Scripts not permitted to use method java.lang.String execute
```

관리 화면의 In-process Script Approval에서 그 메서드를 승인하면 풀리지만, 위 예의 `String.execute`는 컨트롤러에서 임의의 명령을 돌리는 메서드라 승인하면 안 된다. 필요한 일은 `sh` 단계로 에이전트에서 한다.

## 결과물과 캐시를 남기는 자리

빌드가 만든 것 중 무엇을 어디에 남길지도 정해야 한다.

- 테스트 리포트는 `junit`으로 올린다. 빌드 화면에서 실패한 테스트와 추이를 보고, 결과를 UNSTABLE로 바꾸는 근거가 된다.
- 작은 결과물(빌드 정보 파일, 리포트 HTML)은 `archiveArtifacts`로 빌드 기록에 붙인다. 컨트롤러 디스크에 쌓이니 `buildDiscarder`로 개수를 제한한다.
- 같은 빌드 안에서 다른 에이전트로 파일을 넘길 때는 `stash`/`unstash`를 쓴다. 파일이 컨트롤러를 거쳐 가므로 작은 파일에만 쓴다. 수백 MB짜리 빌드 결과를 stash하면 컨트롤러가 느려진다.
- 배포할 결과물(JAR, 컨테이너 이미지)은 Jenkins가 아니라 아티팩트 저장소(Nexus, Artifactory, 컨테이너 레지스트리)에 올리고, 커밋 SHA로 태그를 붙인다. 운영에 나가는 건 Jenkins 빌드 기록이 아니라 그 저장소의 결과물이다. 한 번 빌드한 것을 승격하는 이유는 [CI/CD 기본](/posts/ci-cd-basics)에 있다.

캐시는 에이전트 종류에 따라 달라진다. 고정 에이전트는 디스크가 남아 있어서 `~/.gradle`, `~/.m2`, `~/.npm` 같은 의존성 캐시가 저절로 재사용된다. 편하지만 같은 에이전트에서 여러 브랜치가 캐시를 함께 쓰다 오염되거나, 디스크가 차서 에이전트가 오프라인이 된다. 빌드마다 새로 뜨는 파드 에이전트는 캐시가 없으니 노드의 볼륨이나 원격 캐시(Gradle Build Cache, 레지스트리의 Docker 레이어 캐시)를 붙인다. 캐시 키를 어떻게 잡는지는 [빌드 캐시](/posts/build-caching)에서 자세히 다룬다.

작업 공간(workspace)도 남는다. 고정 에이전트에서는 `/var/lib/jenkins/workspace/shop_main`처럼 잡마다 폴더가 생기고 빌드가 끝나도 지워지지 않는다. 같은 잡이 같은 에이전트에서 동시에 돌면 두 번째 빌드는 `shop_main@2` 폴더를 쓴다. 앞 빌드가 남긴 `build/` 폴더나 생성 파일 때문에 "내 PC에서는 깨지는데 Jenkins에서는 통과한다"는 일이 생기면 작업 공간을 의심한다. `post { cleanup { cleanWs() } }`로 빌드가 끝날 때 비우거나, 처음부터 깨끗한 체크아웃을 강제한다.

## 빌드가 안 돌거나 이상하게 돌 때

증상별로 어디부터 보는지 모았다.

대기열에서 안 움직인다. "There are no nodes with the label" 또는 "Waiting for next available executor"가 보인다. Manage Jenkins → Nodes에서 그 레이블의 에이전트가 온라인인지, executor가 다 찼는지 본다. 에이전트가 오프라인이면 이유가 옆에 적혀 있다. 디스크 여유 공간이나 임시 폴더 공간이 정해 둔 기준 아래로 떨어지면 Jenkins가 에이전트를 스스로 오프라인으로 돌리는데, 이때는 오래된 작업 공간과 Docker 이미지를 지운다.

```bash
# 에이전트 기계에서: 작업 공간과 Docker가 디스크를 얼마나 쓰는지 본다
sudo du -sh /var/lib/jenkins/workspace/* | sort -h | tail -5
docker system df
```

inbound 에이전트가 자꾸 끊긴다. 에이전트 로그에 연결이 끊겼다는 줄이 반복되면 컨트롤러 앞의 로드 밸런서나 프록시가 오래 열린 연결을 유휴 시간으로 끊고 있을 수 있다. WebSocket으로 붙였다면 프록시의 유휴 타임아웃을, TCP 포트로 붙였다면 그 포트가 열려 있는지 본다.

PR 상태가 pending에서 안 바뀐다. 빌드가 아예 없다면 웹훅부터 본다(Recent Deliveries의 응답 코드). 빌드는 성공했는데 체크가 안 풀린다면 상태 이름이 브랜치 보호 규칙과 같은지 본다.

`RejectedAccessException`이 난다. 샌드박스가 막은 것이다. 승인하기 전에 그 메서드가 무엇을 하는지 확인하고, 가능하면 `sh`나 플러그인 단계로 바꾼다.

`java.io.NotSerializableException`이 난다. 파이프라인은 컨트롤러가 재시작해도 이어서 돌 수 있게 진행 상태를 계속 저장한다(CPS라는 방식이다). 그래서 단계 사이에 저장할 수 없는 객체(정규식 `Matcher`, JSON 파서 객체 같은 것)를 변수로 들고 있으면 이 예외가 난다. 그런 계산은 `@NonCPS`를 붙인 함수 안에서 끝내고 문자열이나 맵만 돌려준다. 같은 이유로 컨트롤러에서 도는 Groovy 코드는 무거운 계산을 하지 않게 짠다. 큰 JSON을 Groovy로 파싱하는 일은 에이전트에서 `jq`로 하는 편이 컨트롤러에 부담이 없다.

컨트롤러가 느려지고 화면이 안 뜬다. 컨트롤러는 JVM이라 힙이 차면 GC가 길어진다. 빌드 기록과 아티팩트가 무한히 쌓였는지(`buildDiscarder`가 없는 잡), 컨트롤러에서 executor가 돌고 있는지, 설치된 플러그인이 너무 많은지 본다. `$JENKINS_HOME`은 정기적으로 백업하고, 플러그인 업데이트는 같은 버전 조합의 스테이징 컨트롤러에서 먼저 해 본다. 플러그인 하나의 업데이트가 다른 플러그인과 맞지 않아 파이프라인 전체가 멈추는 일이 Jenkins 운영에서 가장 흔한 장애다.

<Callout kind="warning" title="Script Console은 컨트롤러 위의 root 셸과 같다">
Manage Jenkins → Script Console에서 실행한 Groovy는 샌드박스 없이 컨트롤러 프로세스 권한으로 돈다. 모든 credentials를 복호화해 읽을 수 있고 파일도 지울 수 있다. 장애 대응 중에 인터넷에서 찾은 스크립트를 그대로 붙여 넣지 않는다. 쓰기 전에 `$JENKINS_HOME`을 백업하고, 관리자 권한을 가진 계정을 최소로 유지한다.
</Callout>

## Jenkins와 GitHub Actions 중 고르기

이미 GitHub를 쓰는 팀이 Jenkins를 계속 쓸지는 자주 나오는 질문이다. 둘의 차이는 기능보다 누가 무엇을 운영하느냐에 있다.

| | Jenkins | GitHub Actions |
|---|---|---|
| 운영 | 컨트롤러·플러그인·에이전트를 직접 운영한다 | 호스티드 러너면 운영할 것이 거의 없다 |
| 파이프라인 정의 | Groovy 기반 Jenkinsfile, shared library | YAML 워크플로, 재사용 워크플로·액션 |
| 확장 | 플러그인 수천 개, 플러그인 간 호환이 운영 부담 | 마켓플레이스 액션, 버전 고정은 SHA로 |
| 사내망 접근 | 컨트롤러와 에이전트를 사내망에 두기 쉽다 | 사내 자원에 닿으려면 셀프 호스티드 러너 |
| 저장소 밖 일 | 여러 저장소를 엮는 배포, 예약 작업, 수동 승인 단계를 한곳에서 | 저장소 이벤트 중심, 저장소를 넘는 흐름은 따로 짜야 한다 |
| 비용 | 서버 비용과 운영 인력 | 러너 사용 시간(공개 저장소는 무료 범위가 넓다) |

사내망 안의 레거시 시스템에 배포해야 하거나, 여러 저장소의 결과물을 모아 한 번에 배포하거나, 이미 shared library에 쌓인 자산이 많으면 Jenkins가 맞다. 새 서비스이고 코드가 GitHub에 있고 배포 대상이 클라우드라면 Actions로 시작하는 쪽이 운영 부담이 적다. 둘을 섞는 팀도 많다. PR 검사는 Actions로, 사내망 배포는 Jenkins로 나누는 식이다. 이때는 같은 커밋의 결과물을 두 시스템이 서로 다르게 다시 빌드하지 않게, 레지스트리의 이미지 태그(커밋 SHA)를 둘 사이의 약속으로 삼는다.

## 다시 잠긴 병합 버튼 앞에서

처음 장면의 PR은 코드 문제가 아니었다. `docker` 레이블의 에이전트가 디스크 부족으로 오프라인이 됐고, 빌드는 실패도 성공도 아닌 채 대기열에 있었다. 그래서 상태 체크가 pending에 머물렀다. Jenkins 파이프라인에서 문제가 생기면 Jenkinsfile보다 먼저 그 바깥을 본다. 웹훅이 왔는지, 맞는 에이전트가 있는지, 상태 이름이 맞는지, 그다음에 단계와 조건을 본다.

## 면접에서 나올 만한 질문

### Jenkins의 컨트롤러와 에이전트는 어떻게 나뉘나요?

컨트롤러는 잡 설정, 빌드 기록, 플러그인, credentials를 갖고 파이프라인을 해석해 단계를 지시한다. 실제 셸 명령은 에이전트의 executor에서 돈다. 잡은 레이블로 에이전트를 고르고, 운영에서는 보안과 안정성 때문에 컨트롤러의 executor를 0으로 둔다.

### 선언형 파이프라인과 스크립트형 파이프라인은 무엇이 다른가요?

선언형은 `pipeline { agent; stages; post }`처럼 정해진 틀에 값을 채우는 방식이라 저장할 때 문법 검사가 되고 `when`, `post`, `options` 같은 흔한 요구가 키워드로 있다. 스크립트형은 Groovy 코드로 자유롭게 쓰는 대신 구조를 직접 지켜야 한다. 새로 쓰면 선언형을 쓰고, 복잡한 로직은 `script` 블록보다 shared library로 뺀다.

### post 블록의 always와 cleanup은 어떻게 다른가요?

post 조건은 쓴 순서가 아니라 정해진 순서로 평가되고, cleanup은 언제나 맨 마지막이다. always에서 작업 공간을 지우면 뒤에 오는 failure 블록이 쓰려던 파일이 없을 수 있다. 그래서 리포트 수집은 always, 작업 공간 정리는 cleanup에 둔다.

### multibranch pipeline에서 PR이 병합되지 않고 상태 체크가 계속 기다립니다. 어디를 보나요?

먼저 빌드가 생겼는지 본다. 없으면 GitHub의 Recent Deliveries에서 웹훅 응답 코드를 보고, 주기적 재검색이 걸려 있는지 본다. 빌드가 있는데 대기열에 있으면 레이블에 맞는 에이전트가 온라인인지 본다. 빌드가 성공했는데도 안 풀리면 상태 이름(`pr-merge`, `pr-head`)이 브랜치 보호 규칙의 필수 체크 이름과 같은지 본다.

### Jenkinsfile에서 비밀값을 안전하게 쓰려면 무엇을 지키나요?

`withCredentials`로 필요한 블록 안에서만 꺼내고, `sh`에는 작은따옴표로 넘겨서 셸이 환경 변수로 읽게 한다. 큰따옴표로 Groovy 보간을 하면 값이 명령 문자열에 박혀 로그 가리기를 피하거나 프로세스 목록에 보일 수 있다. 로그 가리기는 똑같은 글자만 가리니 믿지 말고, 클라우드 자격은 에이전트의 역할을 써서 키 자체를 저장하지 않는 쪽이 낫다.

### shared library의 버전을 main 브랜치로 걸어 두면 어떤 문제가 생기나요?

라이브러리를 고친 순간 그 라이브러리를 쓰는 모든 서비스의 다음 빌드가 바뀐다. 실수 하나가 전 서비스의 빌드를 동시에 깨고, 어떤 버전으로 빌드했는지 재현도 어렵다. 태그로 고정하고 서비스 하나에서 먼저 올려 본 뒤 퍼뜨린다. 전역 등록 라이브러리는 샌드박스 밖에서 돌아서 그 저장소의 쓰기 권한 관리도 함께 봐야 한다.

### 파이프라인에서 NotSerializableException이 나는 이유는 무엇인가요?

파이프라인은 컨트롤러가 재시작돼도 이어서 돌 수 있게 진행 상태를 계속 저장한다. 그래서 단계 사이에 저장할 수 없는 객체를 변수로 들고 있으면 이 예외가 난다. 그런 처리는 `@NonCPS` 함수 안에서 끝내고 단순한 값만 돌려주거나, 아예 에이전트에서 `sh`로 처리한다.

### Jenkins와 GitHub Actions 중 무엇을 고르나요?

기능보다 운영 주체와 배포 대상을 본다. 사내망 배포, 여러 저장소를 엮는 흐름, 쌓인 shared library가 있으면 Jenkins가 맞고, GitHub에 코드가 있고 클라우드에 배포하는 새 서비스면 Actions가 운영 부담이 적다. 섞어 쓸 때는 커밋 SHA로 태그한 이미지를 두 시스템 사이의 약속으로 삼아 같은 커밋을 두 번 빌드하지 않는다.
