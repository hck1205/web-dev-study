`===`로는 못 찾고 `==`로는 찾는다. 그렇다고 `==`로 바꾸면 끝일까. 그러면 `[] == false`가 `true`라는 사실도 같이 받아들여야 한다. 이 글은 자바스크립트의 세 가지 "같음"과 `==`가 값을 바꾸는 규칙을 명세 순서대로 따라간다. 객체를 비교할 때 참조를 본다는 이야기는 [원시값과 참조 글](/posts/js-primitive-vs-reference)에서, 참·거짓 판단과 `typeof`는 [truthy·falsy 글](/posts/js-truthy-falsy-typeof)에서 다룬다.

## 자바스크립트에는 같음이 네 종류 있다

명세는 "같다"를 판단하는 알고리즘을 네 개 정의한다. 연산자와 API마다 어느 것을 쓰는지가 다르다.

- IsStrictlyEqual: `===`가 쓴다. 타입이 다르면 바로 `false`다.
- IsLooselyEqual: `==`가 쓴다. 타입이 다르면 한쪽 또는 양쪽을 바꿔서 다시 비교한다.
- SameValue: `Object.is`가 쓴다. `===`와 거의 같고 `NaN`, `-0`만 다르게 본다.
- SameValueZero: `includes`, `Map`과 `Set`의 키가 쓴다. SameValue와 같은데 `0`과 `-0`을 같게 본다.

네 가지는 대부분의 값에서 같은 답을 낸다. 답이 갈리는 값만 모으면 이렇다. Node 22에서 확인한 결과다.

| 비교 | `===` | `==` | `Object.is` | `includes` |
|---|---|---|---|---|
| `NaN`과 `NaN` | false | false | true | true |
| `0`과 `-0` | true | true | false | true |
| `"1"`과 `1` | false | true | false | false |
| `null`과 `undefined` | false | true | false | false |

`switch`의 `case` 비교도 `===`다. `switch (selected) { case 2: ... }`에 문자열 `"2"`를 넣으면 어느 `case`에도 걸리지 않는다. `indexOf`와 `lastIndexOf`는 `===`를 쓰고 `includes`는 SameValueZero를 쓰는 탓에 `[NaN].indexOf(NaN)`은 `-1`, `[NaN].includes(NaN)`은 `true`로 답이 갈린다.

## 느슨한 비교가 값을 바꾸는 순서

`==`는 아무렇게나 바꾸는 게 아니라 정해진 순서가 있다. 명세의 IsLooselyEqual을 줄이면 이렇다.

1. 두 값의 타입이 같으면 `===`로 비교한다.
2. `null`과 `undefined`는 서로만 같다. 다른 어떤 값과도 같지 않다.
3. 숫자와 문자열이면 문자열을 숫자로 바꾼다.
4. 한쪽이 불리언이면 그 불리언을 숫자로 바꾼다(`true`는 1, `false`는 0).
5. 한쪽이 객체이고 다른 쪽이 원시값이면 객체를 원시값으로 바꾼다(ToPrimitive).
6. BigInt와 숫자는 수학적인 값으로 비교한다(`1n == 1`은 `true`).
7. 바꾼 값으로 1부터 다시 비교한다. 어디에도 해당하지 않으면 `false`다.

4번이 함정이다. 불리언은 "참인지"로 비교되지 않고 숫자 0이나 1로 바뀐다. 그래서 `"true" == true`는 `"true" == 1`이 되고, `"true"`를 숫자로 바꾸면 `NaN`이라 `false`다. 실제 결과를 보자.

```js
console.log(null == undefined, null == 0, undefined == 0);
console.log("1" == 1, "" == 0, " \n" == 0);
console.log(true == "1", true == "true", false == "false");
console.log([] == false, [] == ![], [0] == false, [1, 2] == "1,2");
console.log(NaN == NaN, 1n == 1, 1n === 1);
```

```text
true false false
true true true
true false false
true true true true
false true false
```

`null == 0`이 `false`인 것은 2번 규칙 때문이다. `null`은 숫자로 바뀌지 않고 `undefined`하고만 같다. 공백과 줄바꿈뿐인 문자열은 숫자로 바꾸면 `0`이라 `" \n" == 0`은 `true`다.

`[] == false`가 `true`가 되는 과정을 한 단계씩 따라가 보자. 다음을 누르면 규칙이 적용되는 순서대로 식이 바뀐다.

## 객체가 원시값으로 바뀌는 길

5번 규칙의 ToPrimitive는 `==`뿐 아니라 `+`, 템플릿 리터럴, `<` 같은 비교에서도 쓰인다. 객체를 원시값으로 바꿀 때 엔진은 원하는 결과 종류를 힌트로 넘긴다. 힌트는 `"number"`, `"string"`, `"default"` 셋이다. 템플릿 리터럴과 `String(obj)`는 `"string"`, 단항 `+`와 `-`, `*` 같은 산술은 `"number"`, `==`와 이항 `+`는 `"default"`를 넘긴다.

직접 확인해 보면 힌트에 따라 다른 메서드가 불린다.

```js
const price = {
  valueOf() { console.log("valueOf 호출"); return 1000; },
  toString() { console.log("toString 호출"); return "1,000원"; },
};
console.log(price == 1000);
console.log(`${price}`);
console.log(price + 1);

const money = {
  [Symbol.toPrimitive](hint) {
    console.log("hint:", hint);
    return hint === "number" ? 1000 : "1,000원";
  },
};
console.log(+money);
console.log(`${money}`);
console.log(money + "");
```

```text
hint: number
1000
hint: string

```

`Date`는 예외다. `default` 힌트를 `string`처럼 다룬다. 그래서 `new Date(0) + 1`은 날짜 문자열 뒤에 `"1"`이 붙은 문자열이 되고, `new Date(0) - 1`은 밀리초 숫자다. Node 22에서 `typeof (d + 1)`은 `string`, `typeof (d - 1)`은 `number`였다. 날짜를 비교할 때 `d1 == d2`가 늘 `false`인 이유는 둘 다 객체라 1번 규칙에서 참조 비교로 끝나기 때문이다. 날짜는 `d1.getTime() === d2.getTime()`으로 비교한다.

## 더하기만 다르게 행동한다

산술 연산자 중 `+`만 문자열을 좋아한다. 두 쪽을 원시값으로 바꾼 뒤 어느 한쪽이라도 문자열이면 이어 붙이고, 아니면 숫자로 더한다. `-`, `*`, `/`는 무조건 숫자로 바꾼다. 그래서 같은 식 안에서도 연산자마다 결과 타입이 바뀐다. 아래 식을 조각별로 눌러 보자.

## 크다 작다도 타입을 바꾼다

`<`, `>`, `<=`, `>=`도 값을 바꾼다. 두 쪽이 모두 문자열이면 사전 순(UTF-16 코드 단위 순)으로 비교하고, 하나라도 문자열이 아니면 숫자로 바꾼다.

```js
console.log("10" < "9", 10 < "9", "10" < 9);
console.log(null >= 0, null > 0, null == 0, undefined >= 0);
console.log(["10", "9", "1"].sort(), [10, 9, 1].sort(), [10, 9, 1].sort((a, b) => a - b));
```

```text
true false false
true false false false
[ '1', '10', '9' ] [ 1, 10, 9 ] [ 1, 9, 10 ]
```

`"10" < "9"`가 `true`인 건 첫 글자 `"1"`이 `"9"`보다 앞이기 때문이다. API가 숫자를 문자열로 내려 주면(`"price": "10"`) 정렬과 범위 필터가 조용히 틀린다. 두 번째 줄은 더 이상하다. `null >= 0`은 `true`인데 `null > 0`도 `null == 0`도 `false`다. 관계 연산자는 `null`을 숫자 0으로 바꾸지만 `==`는 2번 규칙 때문에 바꾸지 않는다. `undefined`는 숫자로 바꾸면 `NaN`이라 어떤 비교도 `false`다.

세 번째 줄의 `[10, 9, 1].sort()`는 숫자 배열인데도 `[1, 10, 9]`가 나온다. 비교 함수 없이 `sort`를 부르면 요소를 문자열로 바꿔 비교한다. 숫자 정렬에는 반드시 `(a, b) => a - b`를 넘긴다.

그래서 실무 규칙은 "경계에서 한 번 바꾸고 안쪽에서는 `===`"다. 폼 핸들러, 라우터의 파라미터 파싱, API 응답 검증(zod 같은 스키마 라이브러리)에서 타입을 맞춰 두면 안쪽 코드 곳곳에 `==`를 흩뿌릴 이유가 없다.

TypeScript를 쓰면 이 버그를 컴파일 단계에서 잡는다. 처음 예제에서 `selected`를 `string`으로 선언하고 TypeScript 5.9로 검사하면 이렇게 나온다.

```text
t1.ts(3,22): error TS2367: This comparison appears to be unintentional because the types 'number' and 'string' have no overlap.
```

다만 `any`나 단언(`as`)으로 들어온 값은 이 검사를 빠져나간다. 외부에서 들어온 값은 타입 선언보다 런타임 검증이 먼저다.

## NaN과 -0, 엄격한 비교의 구멍

`===`도 완벽하지 않다. 구멍이 두 개 있다. `NaN`은 자기 자신과도 같지 않고, `0`과 `-0`은 구분하지 못한다.

```js
console.log(NaN === NaN, Object.is(NaN, NaN));
console.log(0 === -0, Object.is(0, -0));
console.log([NaN].indexOf(NaN), [NaN].includes(NaN));
```

```text
false true
true false
-1 true
```

`NaN !== NaN`은 IEEE 754 부동소수점 표준이 정한 동작이라 다른 언어도 마찬가지다. 그래서 `x === NaN`으로 검사하면 언제나 `false`이고, `Number.isNaN(x)`를 써야 한다. `-0`은 `-1 * 0`이나 `Math.round(-0.4)` 같은 계산에서 생긴다. 화면에 찍으면 `0`으로 보이지만 `1 / -0`은 `-Infinity`다. 좌표나 방향을 다루는 코드가 아니면 신경 쓸 일이 드물다.

`Map`과 `Set`은 SameValueZero라서 `NaN`을 키로 쓸 수 있고 `-0`과 `0`을 같은 키로 본다. `new Set([0, -0, NaN, NaN]).size`는 `2`다.

React는 SameValue, 즉 `Object.is`로 비교한다. state가 `NaN`인데 다시 `NaN`을 넣으면 같은 값으로 보고 렌더링을 건너뛴다. `===`로 비교했다면 `NaN`끼리도 다르다고 판단했을 것이다. 의존성 배열도 `Object.is`라서 `useEffect(fn, [id])`의 `id`가 `"2"`에서 `2`로 바뀌면 값은 같아 보여도 이펙트가 다시 돈다. 반대로 `key`는 문자열로 바꿔서 쓰기 때문에 `key={2}`와 `key="2"`는 같은 키다. 리렌더링 판단 전체는 [React는 언제 다시 그리나](/posts/react-rerender)에 정리했다.

## 느슨한 비교를 써도 되는 곳은 한 군데

대부분의 스타일 가이드와 ESLint의 `eqeqeq` 규칙은 `===`만 쓰라고 한다. 예외로 널리 허용되는 패턴이 하나 있다. `null`과 `undefined`를 한꺼번에 검사하는 `x == null`이다.

```js
function label(name) {
  if (name == null) return "이름 없음"; // null 또는 undefined
  return name;
}
console.log(label(null), label(undefined), label(""), label(0));
```

```text
이름 없음 이름 없음  0
```

2번 규칙 덕분에 `== null`은 `null`과 `undefined`에만 `true`이고, 빈 문자열이나 `0`은 통과시킨다. `!name`으로 쓰면 빈 문자열과 `0`까지 걸러져서 의도와 달라진다. ESLint에서는 `eqeqeq: ["error", "always", { "null": "ignore" }]`로 이 패턴만 허용할 수 있다. 팀에서 `==`를 아예 금지했다면 `x === null || x === undefined`로 쓰거나, 기본값을 넣는 경우라면 `??`를 쓴다. `??`와 `||`의 차이는 [옵셔널 체이닝과 ?? 글](/posts/js-optional-chaining-nullish)에서 다룬다.

규칙을 직접 구현해 보면 순서가 머리에 남는다. 아래는 원시값(`null`, `undefined`, 불리언, 숫자, 문자열)만 받는 `==`다. 함수 안에서 `==`를 쓰지 않고 앞에서 본 순서대로 짜 보자.

## 비교 하나에 담긴 결정

`===`는 타입이 다르면 바로 거짓이고, `==`는 정해진 순서로 타입을 바꾼 뒤 다시 비교한다. 바꾸는 규칙은 null 짝짓기, 불리언은 숫자로, 문자열은 숫자로, 객체는 ToPrimitive로, 이렇게 몇 줄이다. 실무에서는 값이 들어오는 경계에서 타입을 한 번 맞추고 안쪽은 `===`로 비교한다. `== null` 하나만 예외로 두고, `NaN`은 `Number.isNaN`, 객체는 참조 비교라는 사실을 함께 기억한다.

## 면접에서 나올 만한 질문

### ==와 ===의 차이는

`===`는 타입이 다르면 바로 `false`를 돌려주고, `==`는 정해진 규칙으로 타입을 맞춘 뒤 비교한다. 규칙은 `null`과 `undefined`끼리만 같고, 불리언과 문자열은 숫자로, 객체는 원시값으로 바꾸는 순서다. 예측이 어렵기 때문에 보통 `===`를 쓰고 `== null`만 예외로 둔다.

### [] == false가 true인 이유를 단계별로 설명해 보라

불리언 `false`가 먼저 숫자 0으로 바뀌어 `[] == 0`이 된다. 배열은 객체라서 ToPrimitive로 바뀌는데 `valueOf`가 배열 자신을 돌려주니 `toString`이 불려 빈 문자열이 된다. `"" == 0`에서 빈 문자열이 0으로 바뀌어 `0 === 0`, 즉 `true`다. 불리언은 참·거짓이 아니라 숫자 0과 1로 비교된다.

### Object.is는 ===와 무엇이 다른가

두 가지만 다르다. `Object.is(NaN, NaN)`은 `true`이고 `Object.is(0, -0)`은 `false`다. React가 state, props, 의존성 배열을 비교할 때 이 알고리즘(SameValue)을 쓴다. `includes`, `Map`, `Set`은 여기서 `0`과 `-0`만 같게 본 SameValueZero를 쓴다.

### NaN인지 확인하려면 어떻게 하나

`Number.isNaN(x)`를 쓴다. `NaN`은 자기 자신과도 같지 않아서 `x === NaN`은 항상 `false`다. 전역 `isNaN`은 인수를 먼저 숫자로 바꿔서 `isNaN("abc")`도 `true`가 되니 숫자인지 검사하는 용도로는 부정확하다. 배열에서 찾을 때는 `indexOf`가 아니라 `includes`가 `NaN`을 찾는다.

### 객체를 == 로 비교하면 어떻게 되나

두 쪽이 모두 객체면 타입이 같으므로 `===`처럼 참조를 비교한다. 내용이 같아도 다른 객체면 `false`다. 한쪽만 객체이고 다른 쪽이 원시값이면 객체를 ToPrimitive로 바꾸는데, 이때 `Symbol.toPrimitive`, `valueOf`, `toString` 순서로 메서드를 찾는다. `Date`는 기본 힌트를 문자열로 다루는 예외다.

### 1 + "2"는 "12"인데 1 - "2"는 -1인 이유는

이항 `+`는 두 쪽을 원시값으로 바꾼 뒤 하나라도 문자열이면 이어 붙이고, `-`는 무조건 숫자로 바꾸기 때문이다. 그래서 폼 입력 두 개를 바로 더하면 문자열이 이어 붙는다. 계산하기 전에 `Number`로 바꾸고, 빈 문자열이 0이 되는 경우를 따로 검사한다.

### 숫자 배열을 sort()했더니 [1, 10, 9]가 나왔다. 왜인가

비교 함수 없이 `sort`를 부르면 요소를 문자열로 바꿔 사전 순으로 비교한다. `"10"`은 첫 글자 `"1"`이 `"9"`보다 앞이라 먼저 온다. 숫자 정렬은 `sort((a, b) => a - b)`로 한다. API가 숫자를 문자열로 내려 줄 때 비교 연산자 `<`도 같은 문제를 일으킨다.

### 실무에서 타입 변환 버그를 줄이는 방법은

값이 들어오는 경계에서 한 번 타입을 맞추고 안쪽에서는 `===`만 쓴다. DOM 값, 쿼리스트링, 환경 변수는 모두 문자열이고 JSON은 숫자를 유지하므로, 폼 핸들러와 라우트 파서, 응답 검증 단계에서 변환한다. ESLint `eqeqeq`로 `==`를 막고 TypeScript로 서로 겹치지 않는 타입의 비교를 잡는다.
