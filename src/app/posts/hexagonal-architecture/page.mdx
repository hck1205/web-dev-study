결제사를 바꾸기로 했다고 해 보자. 수수료가 더 싼 곳으로 옮기는 단순한 결정인데, 코드를 열어 보니 주문 서비스 곳곳에서 기존 결제사 SDK를 직접 부르고 있다. 금액 필드 이름도, 거절 코드도, 에러 클래스도 그 SDK의 것이다. 업무 규칙을 테스트하려면 결제사 샌드박스 키가 있어야 하고, 샌드박스가 느린 날은 CI가 같이 느려진다. 결제사를 바꾸는 일이 주문 로직을 다시 짜는 일이 되어 버린다.

헥사고날 아키텍처(hexagonal architecture)는 이런 상황을 막으려는 구조다. 다른 이름은 포트와 어댑터(ports and adapters)이고, 이쪽이 내용을 더 잘 말해 준다. 이 글은 [레이어드 아키텍처](/posts/layered-architecture)에서 의존 방향을 한 번 뒤집은 다음 단계를 이어 간다. 비슷한 생각을 동심원으로 정리한 [클린 아키텍처](/posts/clean-architecture)는 따로 다룬다.

예제는 Node 22와 TypeScript로 짰다. `node --experimental-strip-types`로 타입만 지우고 바로 실행했고, 저장소 어댑터에는 Node 22에 들어 있는 `node:sqlite`를 썼다.

## 결제사를 바꾸려는데 업무 코드가 SDK를 안다

SDK를 쓴 게 잘못은 아니다. 업무 규칙이 SDK의 모양을 알고 있는 게 문제다. 이런 코드다.

```ts
// 업무 규칙 안에 결제사의 말이 섞여 있다
import { PspClient, PspDeclinedError } from "some-psp-sdk";

export async function placeOrder(body: any) {
  const total = body.items.reduce((s: number, i: any) => s + i.qty * i.unitPrice, 0);
  try {
    const r = await new PspClient(process.env.PSP_KEY!).payments.create({ amount_krw: total, card: body.card });
    await db.query("INSERT INTO orders ... VALUES ($1, 'PAID', $2)", [r.payment_key, total]);
  } catch (e) {
    if (e instanceof PspDeclinedError) { /* ... */ }
    throw e;
  }
}
```

이 함수에는 "합계를 내고, 결제가 되면 PAID로 남긴다"는 업무 규칙과 "그 결제사는 금액을 `amount_krw`로 받고 거절하면 `PspDeclinedError`를 던진다"는 기술 사실이 한데 엉켜 있다. 결제사를 바꾸면 기술 사실만 바뀌어야 하는데, 둘이 같은 함수에 있으니 업무 규칙까지 다시 손대고 다시 검증해야 한다.

## 안쪽과 바깥쪽 사이에 구멍을 낸다

앨리스터 코번(Alistair Cockburn)이 2005년 무렵 정리한 이 구조는 시스템을 안쪽과 바깥쪽으로만 나눈다. 안쪽은 애플리케이션 코어, 즉 업무 규칙이다. 바깥쪽은 HTTP, CLI, DB, 결제사, 메시지 브로커, 그리고 테스트 코드다. 안쪽은 바깥쪽을 이름으로도 모른다.

둘이 만나는 지점이 포트다. 포트는 코어가 정한 인터페이스이고, 코어의 말로 쓰여 있다. "주문을 저장해 달라", "이 금액을 결제해 달라" 같은 식이다. 어댑터는 포트 한쪽 끝에 꽂혀서 바깥 기술의 말을 코어의 말로 바꾸는 코드다. 같은 포트에 어댑터를 여러 개 만들 수 있고, 실행할 때 하나를 고른다.

육각형이라는 모양에는 의미가 없다. 코번이 그림을 그릴 때 포트 여러 개를 둘레에 붙이기 좋아서 고른 도형이다. 여섯이라는 숫자를 맞출 필요는 없다.

## 들어오는 쪽과 나가는 쪽은 주인이 다르다

포트는 두 종류다. 구분하는 기준은 누가 대화를 시작하느냐다.

들어오는 포트(driving port, primary port)는 바깥이 코어를 부를 때 쓰는 입구다. 유스케이스 인터페이스가 여기에 해당한다. HTTP 컨트롤러, CLI 명령, 메시지 컨슈머, 테스트가 이 포트를 부르는 어댑터다. 이쪽 어댑터는 코어를 직접 import해서 호출한다. 바깥이 안을 아는 건 괜찮다.

나가는 포트(driven port, secondary port)는 코어가 바깥에 일을 시킬 때 쓰는 출구다. 저장소, 결제, 메일 발송, 시계, ID 생성기가 여기에 해당한다. 의존이 뒤집히는 건 이쪽이다. 인터페이스는 코어 안에 있고, 구현은 바깥 어댑터에 있다. 코어가 "나는 이런 저장소가 필요하다"고 선언하면 어댑터가 그 선언에 맞춰 구현한다. 그래서 의존 화살표가 실행 흐름과 반대로 바깥에서 안으로 향한다.

## 주문 접수를 포트와 어댑터로 나눠 보기

처음의 `placeOrder`를 이 구조로 나눠 본다. 먼저 코어의 포트다. 모든 이름이 주문과 결제의 말이다.

```ts
// src/core/ports.ts
import type { Order, OrderLine } from "./order.ts";

// 들어오는 포트
export type PlaceOrderCommand = { lines: OrderLine[]; cardToken: string };
export type PlaceOrderResult =
  | { ok: true; orderId: string; total: number }
  | { ok: false; orderId: string; reason: string };
export interface PlaceOrder {
  execute(cmd: PlaceOrderCommand): Promise<PlaceOrderResult>;
}

// 나가는 포트
export interface OrderRepository {
  save(order: Order): Promise<void>;
  findById(id: string): Promise<Order | null>;
}
export type ChargeResult = { ok: true; txId: string } | { ok: false; reason: string };
export interface PaymentGateway {
  charge(orderId: string, amount: number, cardToken: string): Promise<ChargeResult>;
}
export interface IdGenerator {
  next(): string;
}
```

유스케이스는 포트만 받는다. 무엇이 꽂힐지는 모른다.

```ts
// src/core/place-order.ts
export function makePlaceOrder(deps: {
  orders: OrderRepository;
  payments: PaymentGateway;
  ids: IdGenerator;
}): PlaceOrder {
  return {
    async execute(cmd) {
      const id = deps.ids.next();
      const total = totalOf(cmd.lines);                 // 빈 주문, 0개 이하 수량이면 던진다
      const charge = await deps.payments.charge(id, total, cmd.cardToken);
      const order: Order = charge.ok
        ? { id, lines: cmd.lines, total, status: "PAID", paymentTxId: charge.txId }
        : { id, lines: cmd.lines, total, status: "PAYMENT_FAILED" };
      await deps.orders.save(order);
      return charge.ok ? { ok: true, orderId: id, total } : { ok: false, orderId: id, reason: charge.reason };
    },
  };
}
```

결제사의 말은 어댑터 하나에 모인다. 금액 필드 이름, 멱등 키 헤더, 상태 코드의 뜻이 여기에만 있다.

```ts
// src/adapters/http-payment-gateway.ts
export function httpPaymentGateway(baseUrl: string): PaymentGateway {
  return {
    async charge(orderId, amount, cardToken) {
      const res = await fetch(`${baseUrl}/v1/payments`, {
        method: "POST",
        headers: { "content-type": "application/json", "idempotency-key": orderId },
        body: JSON.stringify({ merchant_uid: orderId, amount_krw: amount, card: cardToken }),
        signal: AbortSignal.timeout(3000),
      });
      const body = await res.json();
      if (res.status === 200) return { ok: true, txId: body.payment_key };
      if (res.status === 402) return { ok: false, reason: `DECLINED:${body.code}` };
      throw new Error(`PAYMENT_UPSTREAM_${res.status}`);
    },
  };
}
```

## 어댑터는 조립하는 곳에서만 고른다

어떤 어댑터를 꽂을지는 프로그램 시작점 한 곳에서 정한다. 이 자리를 조립하는 곳(composition root)이라고 부른다. 의존성 주입 컨테이너가 없어도 함수 인자로 넘기면 충분하다.

```ts
// src/main.ts
const local = process.env.APP_ENV === "local";
let n = 0;
const placeOrder = makePlaceOrder({
  orders: local ? memoryOrderRepository() : sqliteOrderRepository("orders.db"),
  payments: local ? fakePaymentGateway(["tok_declined"]).gateway : httpPaymentGateway(process.env.PG_URL!),
  ids: { next: () => `ord_${String(++n).padStart(4, "0")}` },
});
httpServer(placeOrder).listen(Number(process.env.PORT ?? 3000));
```

같은 코어를 두 가지로 조립해 띄웠다. 3000번은 SQLite와 결제사 흉내 서버(4000번)에, 3001번은 메모리 저장소와 가짜 결제에 꽂았다.

```bash
# 진짜에 가까운 조립
PG_URL=http://127.0.0.1:4000 PORT=3000 node --experimental-strip-types src/main.ts
# 로컬 개발용 조립
APP_ENV=local PORT=3001 node --experimental-strip-types src/main.ts

# 두 곳에 같은 요청을 보낸다
curl -s -w ' %{http_code}\n' -X POST localhost:3000/orders \
  -d '{"items":[{"sku":"MUG","qty":2,"unitPrice":12000}],"card":"tok_ok"}'
```

응답 모양과 상태 코드가 같다. 다른 건 거절 사유 문자열뿐인데, 그건 어댑터가 만든 값이라 다른 게 맞다. 결제사 흉내 서버의 로그에는 어댑터가 바꿔 보낸 필드가 찍혔다. 코어의 `orderId`가 `idempotency-key` 헤더로, `amount`가 `amount_krw`로 바뀌어 나갔다.

```text
[psp] POST /v1/payments idem=ord_0001 amount_krw=24000
[psp] POST /v1/payments idem=ord_0002 amount_krw=12000
```

결제사를 바꾸는 일은 이제 `PaymentGateway`를 구현하는 파일 하나를 새로 쓰고 조립하는 곳의 한 줄을 고치는 일이다. 코어 코드는 diff에 나오지 않는다.

## 가짜 어댑터로 도는 업무 규칙 테스트

테스트는 바깥에 서 있는 또 하나의 어댑터다. 가짜 결제 어댑터는 정해 둔 토큰이면 거절하고, 받은 호출을 배열에 남긴다. 목(mock) 라이브러리 없이 객체 하나로 된다.

## 두 구현에 같은 계약 테스트를 돌린다

가짜 어댑터에는 함정이 있다. 가짜가 진짜와 다르게 동작할 수 있다. 그러면 테스트는 통과하는데 운영에서 깨진다. 막는 방법은 포트의 약속을 테스트 묶음으로 써 두고, 모든 구현에 똑같이 돌리는 것이다. 어댑터 패턴 쪽에서 본 계약 테스트 이야기는 [어댑터 패턴 글](/posts/pattern-adapter)에 있고, 여기서는 저장소 포트에 실제로 적용해 본다.

```ts
// test/order-repository.contract.test.ts
function orderRepositoryContract(name: string, make: () => OrderRepository) {
  describe(`OrderRepository 계약: ${name}`, () => {
    test("저장한 주문을 그대로 읽는다", async () => { /* ... */ });
    test("없는 id는 null", async () => { /* ... */ });
    test("저장한 뒤 원본 객체를 고쳐도 저장된 값은 그대로다", async () => {
      const repo = make();
      const o = sample();
      await repo.save(o);
      o.status = "PAYMENT_FAILED";
      assert.equal((await repo.findById("o1"))?.status, "PAID");
    });
  });
}

orderRepositoryContract("memory", memoryOrderRepository);
orderRepositoryContract("sqlite", () => sqliteOrderRepository());
```

## 바깥의 실패를 포트의 말로 바꾼다

결제사 흉내 서버를 내린 채 요청을 보내 봤다.

```text
{"error":"fetch failed"} 502
```

`fetch failed`는 Node의 `fetch`가 연결에 실패할 때 던지는 `TypeError`의 메시지다. 이 문자열이 HTTP 어댑터까지 그대로 올라와 응답에 찍혔다. 어댑터가 결제사의 성공과 거절은 번역했지만 전송 실패는 번역하지 않은 것이다. 이대로 두면 코어나 HTTP 어댑터가 "fetch failed라는 메시지면 재시도" 같은 판단을 하게 되고, 결제 어댑터를 gRPC로 바꾸는 순간 그 판단이 조용히 깨진다.

포트에 실패의 종류도 정해 둔다. 어떤 결제사를 꽂든 "결제를 지금 못 한다"는 에러 하나로 오게 한다.

```ts
// src/core/ports.ts
export class PaymentUnavailable extends Error {
  constructor() { super("PAYMENT_UNAVAILABLE"); }
}

// src/adapters/http-payment-gateway.ts
let res: Response;
try {
  res = await fetch(`${baseUrl}/v1/payments`, { /* ... */ signal: AbortSignal.timeout(3000) });
} catch {
  throw new PaymentUnavailable();   // 연결 실패, 타임아웃을 포트의 말로 바꾼다
}
// ...
if (res.status === 200) return { ok: true, txId: body.payment_key };
if (res.status === 402) return { ok: false, reason: `DECLINED:${body.code}` };
throw new PaymentUnavailable();
```

HTTP 어댑터는 이 에러를 503으로 바꾼다. 같은 조건에서 다시 보내면 이렇게 나온다.

```text
{"error":"PAYMENT_UNAVAILABLE"} 503
```

## 트랜잭션은 어느 쪽 일인가

여기서 자주 막힌다. "주문 저장과 재고 차감을 한 트랜잭션으로" 하고 싶은데, 코어는 DB를 모른다. 그렇다고 유스케이스가 `pool.connect()`를 부르면 다시 DB에 묶인다.

흔히 쓰는 답은 트랜잭션 자체를 나가는 포트로 두는 것이다. 코어는 "이 일들을 한 단위로 해 달라"고만 말하고, 어댑터가 그 안에서 BEGIN과 COMMIT을 한다.

```ts
// 코어: 한 단위로 묶일 저장소들을 받는 포트
export interface UnitOfWork {
  run<T>(work: (repos: { orders: OrderRepository; stock: StockRepository }) => Promise<T>): Promise<T>;
}

// 유스케이스는 묶음의 범위만 정한다
await deps.uow.run(async ({ orders, stock }) => {
  await stock.decrease(cmd.lines);
  await orders.save(order);
});

// PostgreSQL 어댑터: 같은 클라이언트로 저장소를 만들어 넘긴다
export function pgUnitOfWork(pool: Pool): UnitOfWork {
  return {
    async run(work) {
      const client = await pool.connect();
      try {
        await client.query("BEGIN");
        const result = await work({ orders: pgOrders(client), stock: pgStock(client) });
        await client.query("COMMIT");
        return result;
      } catch (e) {
        await client.query("ROLLBACK");
        throw e;
      } finally {
        client.release();
      }
    },
  };
}
```

메모리 어댑터는 `work`를 그냥 부르고, 실패하면 복사해 둔 상태로 되돌리면 된다. 주의할 점이 하나 있다. 결제 같은 외부 호출을 `run` 안에 넣으면 결제사가 느린 동안 DB 트랜잭션과 커넥션이 잡혀 있는다. 외부 호출은 트랜잭션 밖에서 하고, 결과를 저장하는 일만 안에 넣는다. 위 예제의 유스케이스가 결제를 먼저 하고 저장을 나중에 하는 것도 그래서다. 트랜잭션을 어느 층이 여는지에 대한 기본은 [레이어드 아키텍처 글](/posts/layered-architecture)에서 다뤘다.

## 포트가 새는 모습들

구조를 갖춰도 포트로 바깥이 새어 들어오면 효과가 없다. 실제로 자주 보이는 모습은 이렇다.

포트 이름이나 타입이 기술을 말한다. `saveToPostgres`, `findByQuery(sql: string)`, `Promise<QueryResult>`를 돌려주는 저장소는 이름만 포트다. 메서드 이름은 업무의 말(`findPendingOlderThan`)로 짓고, 돌려주는 값은 코어의 타입으로 한다.

ORM 엔티티를 그대로 코어 모델로 쓴다. 데코레이터가 붙은 클래스는 ORM 패키지를 import하고, 지연 로딩 프록시 때문에 코어 안에서 쿼리가 몰래 나간다. 작은 서비스라면 감수할 수도 있지만, 그 순간부터 코어 테스트가 ORM 설정을 필요로 한다. 도메인 모델과 저장 모델을 나누고 어댑터에서 바꾼다. 위의 SQLite 어댑터가 `lines_json` 컬럼을 `lines` 배열로 바꾸는 부분이 그 일이다.

어댑터에 업무 규칙이 들어간다. 컨트롤러에서 "VIP면 배송비 무료"를 계산하면 CLI로 들어온 주문은 배송비를 낸다. 들어오는 어댑터는 모양만 바꾸고, 판단은 코어에서 한다.

클래스마다 인터페이스를 만든다. 포트는 바깥 경계에만 필요하다. 코어 안의 계산 함수까지 인터페이스로 감싸면 파일만 늘고 얻는 게 없다. 바꿔 끼울 일이 있거나 테스트에서 떼어 내야 하는 곳만 포트로 둔다.

시간과 무작위를 코어에서 직접 쓴다. `Date.now()`, `crypto.randomUUID()`도 바깥 세계다. 위 예제가 ID 생성기를 포트로 받은 이유다. 그래야 "주문 ID가 o1"이라고 테스트에서 단정할 수 있다.

## 프런트엔드에도 포트가 있다

React 앱에도 같은 경계가 있다. 컴포넌트와 훅이 `fetch`나 axios를 직접 부르면, 화면 로직을 테스트할 때마다 네트워크를 흉내 내야 한다. 백엔드 응답의 필드 이름이 바뀌면 컴포넌트 여러 개를 고쳐야 한다.

```ts
// 앱이 바라는 모양: 포트
export interface OrderApi {
  place(lines: OrderLine[]): Promise<{ orderId: string; total: number }>;
}

// 실제 어댑터: 서버 응답의 모양을 앱의 모양으로 바꾼다
export const httpOrderApi: OrderApi = {
  async place(lines) {
    const res = await fetch("/api/orders", { method: "POST", body: JSON.stringify({ items: lines }) });
    if (!res.ok) throw new Error(`ORDER_${res.status}`);
    const body = await res.json();
    return { orderId: body.order_id, total: body.total_amount };
  },
};

// 조립: Provider로 꽂고, 테스트에서는 가짜를 꽂는다
const OrderApiContext = createContext<OrderApi>(httpOrderApi);
export const useOrderApi = () => useContext(OrderApiContext);
```

테스트나 스토리북에서는 Provider에 가짜 객체를 넣는다. 네트워크 계층에서 요청을 가로채는 MSW 같은 도구도 결국 같은 자리에 가짜 어댑터를 꽂는 방법이고, 이쪽은 `fetch` 호출까지 진짜로 지나가게 한다는 차이가 있다. 서버 데이터를 캐시하는 라이브러리를 쓰면 `queryFn`이 이 포트를 부르게 하면 된다. 캐시 쪽 이야기는 [클라이언트 데이터 캐시 글](/posts/client-data-cache)에 있다.

## 이 구조가 값을 하는 곳, 아닌 곳

비용은 분명하다. 파일과 인터페이스가 늘고, 처음 보는 사람은 호출을 따라가려면 조립하는 곳을 먼저 찾아야 한다. 저장 모델과 도메인 모델을 나누면 필드 하나를 추가할 때 고칠 곳이 두세 군데 늘어난다.

값을 하는 곳은 바깥과 맞닿는 면이 많고 자주 바뀌는 시스템이다. 결제사, 배송사, 알림 채널처럼 갈아 끼울 대상이 있거나, 같은 업무 규칙을 HTTP와 메시지 컨슈머와 배치가 함께 써야 하거나, 업무 규칙 자체가 복잡해서 빠른 테스트가 많이 필요한 경우다.

값을 못 하는 곳은 업무 규칙이 거의 없는 CRUD다. 요청을 받아 검증하고 테이블에 넣고 돌려주는 게 전부라면, 포트와 어댑터는 같은 필드를 세 번 옮겨 적는 일이 된다. 이럴 때는 [레이어드 구조](/posts/layered-architecture)로 충분하고, 외부 시스템 하나만 포트로 빼는 식으로 부분만 써도 된다.

헥사고날은 결국 "업무 규칙이 무엇을 모르게 할 것인가"를 정하는 구조다. 나가는 포트의 인터페이스를 코어가 가지고, 바깥의 말은 어댑터에서 번역하고, 어댑터는 시작점 한 곳에서 꽂는다. 이 셋이 지켜지면 결제사를 바꾸는 일은 파일 하나를 추가하는 일이 된다.

  for (const l of lines) {

## 면접에서 나올 만한 질문

### 헥사고날 아키텍처를 한 문장으로 설명해 주세요.

업무 규칙을 가운데 두고, 바깥과는 코어가 정의한 인터페이스인 포트로만 만나게 하는 구조다. HTTP, DB, 외부 API, 테스트는 모두 포트에 꽂히는 어댑터이고, 어떤 어댑터를 쓸지는 시작점에서 고른다. 그래서 바깥 기술을 바꿔도 코어는 바뀌지 않는다.

### 들어오는 포트와 나가는 포트는 어떻게 다른가요?

누가 대화를 시작하느냐로 나뉜다. 들어오는 포트는 바깥이 코어를 부르는 유스케이스 인터페이스이고, 컨트롤러나 컨슈머가 직접 호출한다. 나가는 포트는 코어가 바깥에 일을 시키는 인터페이스이고, 코어 안에 선언되며 바깥 어댑터가 구현한다. 의존이 뒤집히는 건 나가는 쪽이다.

### 레이어드 아키텍처와 무엇이 다른가요?

레이어드는 위에서 아래로 의존하니 업무 계층이 퍼시스턴스 계층을 안다. 헥사고날은 위아래 대신 안팎만 있고, 퍼시스턴스도 HTTP와 똑같이 바깥 어댑터라서 업무 규칙이 DB를 모른다. 레이어드에 의존성 역전을 적용해 끝까지 밀면 헥사고날에 가까워진다.

### 가짜 어댑터로 테스트하면 실제 DB 버그는 어떻게 잡나요?

포트의 약속을 계약 테스트로 써서 가짜와 진짜 구현에 똑같이 돌린다. 그러면 가짜가 진짜와 다르게 동작하는 순간 테스트가 실패한다. 메모리 저장소가 객체를 복사하지 않아 저장 뒤 변경이 따라 바뀌는 문제가 대표적이다. 그 위에 진짜 DB로 도는 통합 테스트를 소수만 둔다.

### 트랜잭션은 어디서 시작하나요? 코어가 DB를 모르는데요.

트랜잭션을 유닛 오브 워크 같은 나가는 포트로 둔다. 유스케이스는 어디부터 어디까지 한 단위인지만 정하고, 어댑터가 BEGIN과 COMMIT, 같은 커넥션 공유를 맡는다. 외부 결제 같은 느린 호출은 그 단위 밖에서 해서 커넥션을 오래 잡지 않게 한다.

### 외부 API가 타임아웃 나면 그 에러는 어디서 처리하나요?

어댑터가 전송 계층의 에러를 포트가 약속한 에러로 번역한다. 예를 들어 `fetch failed`나 타임아웃을 `PaymentUnavailable` 하나로 바꾸고, 들어오는 HTTP 어댑터가 그걸 503으로 바꾼다. 번역하지 않으면 바깥 라이브러리의 메시지에 기대는 판단이 코어나 컨트롤러에 생기고, 어댑터를 바꿀 때 조용히 깨진다.

### 모든 서비스에 이 구조를 쓰는 게 좋은가요?

아니다. 업무 규칙이 적은 CRUD에서는 같은 데이터를 여러 모델로 옮겨 적는 비용만 남는다. 갈아 끼울 외부 시스템이 많거나, 같은 규칙을 여러 입구가 쓰거나, 규칙이 복잡해 빠른 테스트가 많이 필요할 때 값을 한다. 필요한 경계만 포트로 빼는 부분 적용도 충분히 쓸 만하다.

### 클래스마다 인터페이스를 만들어야 하나요?

필요 없다. 포트는 코어와 바깥의 경계에만 둔다. 코어 안의 계산 함수나 값 객체까지 인터페이스로 감싸면 파일과 간접 호출만 늘어난다. 바꿔 끼울 일이 있거나 테스트에서 떼어 내야 하는 바깥 의존, 그리고 시간과 무작위 같은 숨은 바깥 세계만 포트로 받는다.
