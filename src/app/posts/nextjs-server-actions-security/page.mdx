<EasyIntro>
  Next.js에서는 버튼을 눌렀을 때 서버에서 돌 함수를 화면 코드 옆에 그냥 적을 수 있는데, 이런 함수를 서버 액션이라고 부른다. 함수를 부르는 것처럼 보이지만 실제로는 브라우저가 서버에 편지를 보내고 답장을 받는 일이다.

  편지에는 어느 함수를 부를지 적힌 번호와 보낼 값이 들어 있다. 이 번호를 아는 사람이면 버튼을 누르지 않고도 편지를 보낼 수 있다.

  그래서 편지를 받는 쪽이 보낸 사람이 누구인지, 이 일을 해도 되는 사람인지 매번 확인해야 한다. 관리자에게만 버튼을 보여 줬다는 사실만으로는 아무것도 증명되지 않는다.

  Next.js는 다른 동네에서 온 가짜 편지를 걸러 주고, 너무 큰 편지를 막고, 편지 안의 비밀 메모를 암호로 바꿔 주는 일은 대신 해 준다. 하지만 사람을 확인하는 일은 함수 안에서 직접 해야 한다.
</EasyIntro>

코드 리뷰에서 이런 서버 액션을 봤다.

```ts
"use server";
export async function deletePost(postId: string) {
  await db.post.delete({ where: { id: postId } });
  revalidatePath("/admin/posts");
}
```

작성자는 "삭제 버튼은 관리자 화면에서만 보이니까 괜찮다"고 했다. 괜찮지 않다. `"use server"`가 붙은 함수는 빌드 때 공개 POST 엔드포인트가 된다. 버튼이 어디에 보이느냐는 그 엔드포인트를 누가 부를 수 있느냐와 관계없다. 실제로 호출 요청을 `curl`로 다시 보내 값을 바꾸는 실험은 [React 서버 컴포넌트](/posts/react-server-components#서버-액션은-경계를-넘는-함수다)에 있고, 폼 쪽에서 본 같은 이야기는 [React 폼과 액션](/posts/react-forms-actions)에 있다.

이 글은 그다음 질문에 답한다. Next.js가 서버 액션에 기본으로 걸어 둔 보호는 무엇이고 어디까지인가. 그 바깥에서 개발자가 직접 막아야 하는 것은 무엇인가. 그리고 환경 변수나 DB 레코드 같은 비밀이 클라이언트로 새지 않게 코드를 어떻게 나누는가. 실험은 Next.js 16.4.1로 했다.

## Next가 대신 막아 주는 것

### 다른 사이트에서 보낸 요청

악성 사이트가 사용자를 속여 내 사이트로 POST를 보내게 하는 공격이 CSRF다. 브라우저는 쿠키를 자동으로 붙이니 서버는 사용자가 보낸 것으로 착각한다. 원리와 SameSite, 토큰 방어는 [CSRF](/posts/csrf)에 정리했다. 서버 액션은 Origin 검사로 이걸 막는다. 다른 Origin을 넣어 호출했다.

```bash
ID=60e1de054d39fed097cd86ae7577cd66b7166e864a
curl -s -b session=u-17 -H "Next-Action: $ID" -H 'Accept: text/x-component' \
  -H 'Content-Type: text/plain;charset=UTF-8' -H 'Origin: https://evil.example' \
  --data '[42,5]' -w '\n[%{http_code}]\n' localhost:3922/shop-actions
```

```text
0:{"a":"$@1","q":"","i":false,"b":"OwrRzvWiwafUZDQNEQiZR"}
1:E{"digest":"3083871340"}

[500]
```

서버 로그에는 이유가 남았다.

```text
`x-forwarded-host` header with value `localhost:3922` does not match `origin` header with value `evil.example` from a forwarded Server Actions request. Aborting the action.
⨯ Error: Invalid Server Actions request.
```

함수는 실행되지 않았다. 클라이언트는 원인 대신 digest만 받는다. 운영에서 "액션이 500을 낸다"는 신고가 오면 이 digest로 서버 로그를 찾는다.

그런데 Origin 헤더를 아예 빼면 어떻게 될까.

```text
-- Origin 없이 같은 요청
0:{"a":"$@1","q":"","i":false,"b":"OwrRzvWiwafUZDQNEQiZR"}
1:{"ok":true,"qty":1}

[200]
```

통과한다. Next 코드의 주석이 이유를 말한다. Origin이 없는 요청은 사람이 직접 만든 요청이거나 오래된 브라우저인데, 직접 만든 요청에는 피해자의 쿠키가 실려 있지 않으니 CSRF가 아니라는 것이다. 현대 브라우저는 다른 사이트에서 보내는 POST에 Origin을 붙이므로 CSRF는 이 검사로 막힌다. 하지만 이건 "피해자의 브라우저를 빌린 요청"을 막는 장치이지, 공격자가 자기 쿠키로 직접 보내는 요청을 막는 장치가 아니다. 인증과 권한 검사를 대신하지 못한다.

리버스 프록시 뒤에서 이 검사 때문에 정상 요청이 실패하는 일도 흔하다. 사용자는 `https://shop.example.com`에서 버튼을 눌렀는데 프록시가 Host를 내부 주소로 바꾸고 `X-Forwarded-Host`를 넘기지 않으면, Next는 `shop.example.com`과 `app-internal:3000`을 비교해 막는다. 증상은 "로컬에서는 되는데 배포하면 모든 액션이 500"이다. 프록시가 원래 Host나 `X-Forwarded-Host`를 넘기게 고치거나, `allowedOrigins`에 허용할 도메인을 적는다.

```js
// next.config.js
module.exports = {
  experimental: {
    serverActions: {
      allowedOrigins: ["shop.example.com", "*.cdn.example.com"],
    },
  },
};
```

와일드카드 규칙은 Next 16.4.1의 `csrf-protection.js`를 읽고 확인했다. `*`는 정확히 한 칸(점 사이 한 조각)만, `**`는 맨 앞에서 여러 칸을 맞춘다. `*` 하나만 쓴 패턴은 막지만, `*.com`처럼 두 칸짜리는 막지 않아서 모든 `.com` 도메인을 허용해 버린다. 아래 함수로 판단 순서를 짜 보자. 기대값은 Next의 실제 함수로 계산했다.

### 너무 큰 요청

본문이 1MB를 넘으면 함수를 부르지 않는다. 1.1MB짜리 문자열을 인자로 보냈다.

```text
⨯ Error: Body exceeded 1 MB limit.
To configure the body size limit for Server Actions, see: https://nextjs.org/docs/app/api-reference/next-config-js/serverActions#bodysizelimit
    at ignore-listed frames {
  statusCode: 413,
  digest: '3502176618'
}
```

서버 안에서는 413이지만 `curl`이 받은 HTTP 상태는 500과 digest였다. 클라이언트에서 "용량 초과"를 따로 안내하려면 업로드 전에 크기를 검사한다. 큰 파일을 받는 기능이라면 `serverActions.bodySizeLimit`을 올리기보다, 브라우저가 스토리지에 직접 올리게 하는 사전 서명 URL을 먼저 고려한다. 한도를 올리면 공격자가 큰 요청으로 서버 메모리를 쓰게 하는 비용도 같이 올라간다.

### 쓰지 않는 함수와 예측 가능한 ID

앞에서 본 것처럼 어디서도 쓰지 않는 액션은 빌드가 지운다. ID는 빌드 산출물에서 만든 값이라 추측하기 어렵고, 문서에 따르면 소스가 같아도 최대 14일마다 바뀐다. 이 때문에 생기는 운영 문제가 있다. 배포 직후 옛 화면을 띄워 둔 사용자가 버튼을 누르면 옛 ID로 요청하고, 새 서버는 그 ID를 모른다. 에러 메시지는 "Failed to find Server Action"이다. 롤링 배포로 옛 인스턴스를 잠시 같이 두고, 화면에서는 이 에러를 "새로고침해 주세요"로 안내한다.

ID가 추측하기 어렵다는 것도 보안 경계는 아니다. ID는 클라이언트 번들에 그대로 들어 있어서 누구나 읽을 수 있다.

### 인라인 액션이 붙잡은 값

컴포넌트 안에 적은 액션은 바깥 변수를 붙잡을 수 있다. 쿠폰 코드를 붙잡게 했다.

```tsx
export default async function Page() {
  const couponCode = "VIP-7Q2X-SECRET";
  async function applyCoupon() {
    "use server";
    console.log("apply coupon", couponCode);
  }
  return <form action={applyCoupon}><button>쿠폰</button></form>;
}
```

액션이 나중에 불릴 때 `couponCode`를 알아야 하니, 이 값은 브라우저로 갔다가 호출 때 다시 돌아온다. 렌더링된 HTML을 열어 봤다.

```text
-- grep -c VIP-7Q2X page.html
0
-- form 안의 숨은 입력 (길어서 줄임)
<input type="hidden" name="$ACTION_1:0" value="{&quot;id&quot;:&quot;405fa2bf…&quot;,&quot;bound&quot;:&quot;$@1&quot;}"/>
<input type="hidden" name="$ACTION_1:2" value="&quot;bNqRZzFtNT1xyl1kt6BY2m//uuGVbKT3oUimb8sHvJVxg7/v+wBo…&quot;"/>
```

평문은 없고 암호문이 숨은 입력으로 실렸다. Next는 빌드마다 새 키를 만들어 붙잡힌 값을 암호화한다. 두 가지를 기억해 둔다. 첫째, 키가 빌드마다 바뀌므로 서버 여러 대가 서로 다른 빌드를 돌리면 다른 인스턴스가 만든 암호문을 풀지 못한다. 자체 호스팅으로 여러 인스턴스를 띄우면 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`를 모든 인스턴스에 같은 값으로 준다. 둘째, 문서도 암호화에만 기대지 말라고 한다. 비밀은 처음부터 붙잡지 않는다. 필요한 건 id만 붙잡고 액션 안에서 다시 읽는다.

## Next가 막아 주지 않는 것

여기서부터는 액션 함수 안의 일이다. 처음 본 `deletePost`에 빠진 것을 채우면 이렇다.

```ts
"use server";
import { z } from "zod";
import { getCurrentUser } from "@/data/auth";
import { updateTag } from "next/cache";

const Input = z.object({ postId: z.string().uuid() });

export async function deletePost(raw: unknown) {
  // 1) 누구인가
  const user = await getCurrentUser();
  if (!user) return { ok: false, error: "로그인이 필요하다" } as const;

  // 2) 입력 모양이 맞는가
  const parsed = Input.safeParse(raw);
  if (!parsed.success) return { ok: false, error: "잘못된 요청" } as const;

  // 3) 이 사람이 이 글을 지울 수 있는가 (내 글이거나 관리자)
  const post = await db.post.findFirst({ where: { id: parsed.data.postId } });
  if (!post || (post.authorId !== user.id && !user.isAdmin)) {
    return { ok: false, error: "권한이 없다" } as const;
  }

  await db.post.delete({ where: { id: post.id } });
  updateTag("posts");
  return { ok: true } as const; // DB 레코드를 통째로 돌려주지 않는다
}
```

인증은 화면이 아니라 이 함수 안에서 한다. 관리자 페이지 레이아웃이 비로그인 사용자를 돌려보내도, 액션은 레이아웃을 거치지 않고 바로 불릴 수 있다. proxy에서 막아도 matcher 밖의 경로로 같은 액션 ID를 보내는 길이 남을 수 있다([Route Handler와 Proxy](/posts/nextjs-route-handlers-proxy#proxy만-믿으면-안-되는-이유)).

권한은 "로그인했는가"보다 한 단계 더 간다. 로그인한 사용자가 남의 글 id를 넣어 보내는 공격을 IDOR라고 부른다. id는 클라이언트가 정하더라도, 그 레코드의 주인과 상태는 서버가 다시 읽어서 판단한다. 클라이언트가 보낸 객체 전체(`{ id, authorId, title }`)를 믿고 쓰는 코드는 스키마 검증을 통과해도 남의 레코드를 바꾼다. 스키마는 모양만 보고 소유권은 보지 않기 때문이다. 인증과 인가의 구분은 [인증과 인가](/posts/authn-vs-authz)에 있다.

입력은 모두 의심한다. 폼 액션의 `FormData` 값은 전부 문자열이고, 숫자 칸이라도 `"999999"`나 `"-1"`이 올 수 있다. 화면의 `max` 속성은 아무것도 막지 않는다.

반환값은 직렬화되어 그대로 브라우저로 간다. DB 행을 반환하면 비밀번호 해시나 내부 메모 열까지 네트워크 탭에 보인다. 화면이 쓰는 필드만 골라 돌려준다.

비싼 액션에는 호출 횟수 제한이 필요하다. 로그인, 쿠폰 확인, 메일 발송처럼 반복 호출로 이득을 보거나 비용을 만드는 액션이 대상이다. 사용자 id나 IP 기준으로 세는 방법은 [레이트 리밋 실전](/posts/rate-limiting-in-practice)에 있다. 삭제나 결제처럼 되돌리기 어려운 동작은 최근 로그인 시각을 확인하거나 비밀번호를 한 번 더 받는다.

## 비밀이 브라우저로 새는 길

### NEXT_PUBLIC_은 빌드 때 값이 박힌다

`.env`에 두 값을 두고 클라이언트 컴포넌트와 서버 컴포넌트에서 각각 썼다.

```text
NEXT_PUBLIC_SHOP_NAME=b22shop
SECRET_DB_PASSWORD=hunter2-db
```

```bash
# 브라우저로 가는 파일과 서버 파일에서 각 값을 찾는다
grep -l b22shop .next/static/chunks/*.js | wc -l
grep -rl hunter2 .next/static | wc -l
grep -rl hunter2 .next/server | wc -l
```

```text
1
0
0
```

`NEXT_PUBLIC_` 값은 빌드할 때 `process.env.NEXT_PUBLIC_SHOP_NAME` 자리에 문자열로 바뀌어 클라이언트 파일에 들어갔다. 접두사 없는 값은 어디에도 박히지 않았다. 서버 코드가 실행될 때 `process.env`에서 읽기 때문이다.

이 차이에서 실수 두 가지가 나온다. 하나는 비밀에 `NEXT_PUBLIC_`을 붙이는 것이다. 클라이언트에서 API 키가 `undefined`라서 접두사를 붙였다면 그 키는 이제 모든 방문자에게 공개됐다. 그 API는 Route Handler나 서버 액션을 거쳐 서버에서 부른다.

다른 하나는 Docker 이미지 하나를 개발·스테이징·운영에 돌려 쓰는 경우다. `NEXT_PUBLIC_API_URL`은 빌드한 환경의 값으로 굳어서, 운영 컨테이너에 다른 값을 줘도 바뀌지 않는다. 런타임에 바꿔야 하는 공개 설정은 서버 컴포넌트에서 읽어 props로 넘기거나 설정 API로 내려 준다. `process.env[name]`처럼 변수로 찾는 코드는 아예 치환되지 않는다는 점도 알아 둔다.

### 서버 컴포넌트의 props도 브라우저로 간다

서버 컴포넌트가 클라이언트 컴포넌트에 넘긴 props는 RSC payload에 실려 HTML 안에 텍스트로 보인다. 사용자 레코드 전체를 `<ProfileCard user={user} />`로 넘기면 클라이언트 컴포넌트가 이름만 그려도 나머지 필드가 다 실린다. 서버 전용 모듈을 클라이언트가 import하지 못하게 막는 `server-only`와 payload의 모양은 [React 서버 컴포넌트](/posts/react-server-components#서버-전용-코드가-브라우저로-새지-않게)에서 다뤘다.

여기에 한 겹을 더 두는 장치가 React의 taint API다. `next.config`에서 `experimental.taint: true`를 켜고, 클라이언트로 가면 안 되는 객체나 값에 표시를 한다.

```ts
import { experimental_taintObjectReference, experimental_taintUniqueValue } from "react";

export async function getUserRow(id: string) {
  const row = await db.user.find(id);
  // 이 객체가 통째로 클라이언트 컴포넌트 props로 넘어가면 렌더링이 에러를 낸다
  experimental_taintObjectReference("user 레코드를 그대로 넘기지 말 것", row);
  // 이 문자열 값이 어디로든 클라이언트에 넘어가면 에러를 낸다
  experimental_taintUniqueValue("세션 토큰은 클라이언트로 보내지 않는다", row, row.sessionToken);
  return row;
}
```

이름에 `experimental_`이 붙은 실험 기능이고, 표시한 그 객체·그 값만 막는다. 필드 하나를 복사한 새 객체(`{ ...row }`)는 막지 못한다. 실수를 한 번 더 잡는 그물이지 설계를 대신하지 않는다. 문서도 데이터를 걸러 내는 일은 데이터 접근 계층에서 하라고 한다.

## 데이터 접근 계층으로 모은다

위의 검사를 액션마다, 페이지마다 따로 적으면 언젠가 하나를 빠뜨린다. Next 문서가 새 프로젝트에 권하는 구조는 데이터 접근 계층(Data Access Layer, DAL)이다. DB나 내부 API를 직접 부르는 코드를 한 폴더에 모으고, 페이지와 액션은 그 폴더의 함수만 부른다.

DAL은 세 가지를 지킨다. 서버에서만 돈다(파일 첫 줄에 `import "server-only"`). 함수마다 인가를 확인한다. 화면에 필요한 필드만 담은 작은 객체(DTO)를 돌려준다.

```ts
// data/auth.ts
import "server-only";
import { cache } from "react";
import { cookies } from "next/headers";

// 한 요청 안에서 여러 번 불러도 한 번만 검증한다
export const getCurrentUser = cache(async () => {
  const token = (await cookies()).get("session")?.value;
  if (!token) return null;
  return verifySession(token); // 서명 검증 뒤 { id, isAdmin }만
});
```

```ts
// data/profile.ts
import "server-only";
import { getCurrentUser } from "./auth";

export async function getProfileDTO(slug: string) {
  const viewer = await getCurrentUser();
  const row = await db.user.findBySlug(slug);
  if (!row) return null;
  return {
    name: row.name,
    // 같은 팀이거나 관리자일 때만 전화번호를 담는다
    phone: viewer && (viewer.isAdmin || viewer.team === row.team) ? row.phone : null,
  };
}
```

이렇게 나누면 리뷰할 곳이 줄어든다. 페이지 코드에서 `db.`가 보이면 그 자체가 지적 사항이다. `getCurrentUser`를 `cache`로 감싼 덕분에 레이아웃, 페이지, 액션이 각자 불러도 검증은 요청당 한 번이다. 요청 메모이제이션은 [Next.js 캐시 네 겹](/posts/nextjs-caching-layers#요청-하나-안에서만-쓰는-메모)에서 실측했다.

이미 돌아가는 코드베이스를 점검할 때는 찾는 순서를 정해 둔다.

```bash
# "use server" 파일과 인라인 액션을 모두 찾는다
grep -rln '"use server"' app src | sort
# 클라이언트 컴포넌트에서 process.env를 읽는 곳 (NEXT_PUBLIC_ 아닌 것이 있으면 버그)
grep -rl '"use client"' app src | xargs grep -n 'process\.env\.' | grep -v NEXT_PUBLIC_
# 비밀처럼 보이는 이름에 NEXT_PUBLIC_이 붙었는지
grep -rn 'NEXT_PUBLIC_[A-Z_]*\(SECRET\|KEY\|TOKEN\|PASSWORD\)' .env* app src
```

액션 파일마다 첫 줄 가까이에 사용자 확인이 있는지, 입력 검증이 있는지, 반환값이 DTO인지 본다. 하나라도 없으면 그 액션은 공개 API처럼 취약하다.

## 바꾼 뒤의 마무리

액션이 성공한 뒤 화면을 맞추는 방법은 셋이다. 캐시를 무효화하고(`updateTag`, `revalidatePath`, `revalidateTag`), 필요하면 다른 페이지로 보내고(`redirect`), 결과를 값으로 돌려준다. 무효화 함수의 차이는 [Next.js 캐시 네 겹](/posts/nextjs-caching-layers#값을-바꾼-뒤-무엇을-부르나)에 정리했다.

`redirect()`는 내부적으로 예외를 던져서 흐름을 끊는다. 그래서 두 가지 실수가 나온다. `redirect` 뒤에 재검증을 부르면 실행되지 않는다. 재검증을 먼저 부른다. 그리고 액션 전체를 `try/catch`로 감싸면 `redirect`가 던진 예외까지 잡아 삼켜서 이동이 일어나지 않는다. `redirect`는 `try` 블록 밖에서 부른다.

실패는 두 종류로 나눈다. "이메일이 이미 있다"처럼 예상한 실패는 `{ ok: false, error }` 같은 값으로 돌려주고 `useActionState`로 화면에 보여 준다. 예상하지 못한 실패는 던진다. 프로덕션에서 서버가 던진 에러는 메시지가 가려지고 digest만 가니, 에러 메시지에 SQL이나 내부 경로가 들어 있어도 사용자에게는 보이지 않는다. 대신 로그에서 digest로 찾을 수 있게 남긴다. 폼에서 이 흐름은 [React 폼과 액션](/posts/react-forms-actions)에 있다.

하나 더, Next는 한 클라이언트의 서버 액션을 한 번에 하나씩 보낸다. `Promise.all`로 액션 세 개를 동시에 불러도 앞의 것이 끝나야 다음 것이 나간다. 병렬로 할 일이 있으면 액션 하나 안에서 병렬로 처리하거나, 읽기라면 서버 컴포넌트나 Route Handler로 옮긴다.

## 다시 삭제 버튼으로

처음 리뷰의 답은 "버튼이 어디 보이느냐는 보안과 상관없다"였다. Next는 서버 액션에 Origin 검사, 1MB 본문 제한, 쓰지 않는 액션 제거, 클로저 값 암호화를 걸어 준다. 이것들은 다른 사이트를 거친 공격과 실수로 새는 값을 줄여 주지만, 공격자가 자기 쿠키로 직접 보내는 요청은 막지 않는다. 그 요청을 막는 일은 액션 안에서 한다. 사용자를 확인하고, 입력을 검증하고, 레코드의 주인을 서버에서 다시 읽어 판단하고, 필요한 필드만 돌려준다. 이 검사를 매번 손으로 쓰지 않으려고 DAL로 모은다. 비밀은 `NEXT_PUBLIC_`과 props, 반환값, 클로저라는 네 갈래로 새니 각각을 막는다.

## 면접에서 나올 만한 질문

### 서버 액션은 어떻게 호출되나요?

`"use server"` 함수는 빌드 때 클라이언트 번들에서 함수 본문 대신 액션 ID와 호출기로 바뀐다. 호출하면 그 액션을 쓰는 페이지 주소로 POST가 나가고, `Next-Action` 헤더로 함수를, 본문으로 인자를 보낸다. 서버는 검사를 거쳐 함수를 실행하고 반환값과 필요하면 다시 그린 RSC payload를 한 응답으로 돌려준다. 즉 누구나 부를 수 있는 공개 엔드포인트다.

### Next.js가 서버 액션에 기본으로 제공하는 보호는 무엇인가요?

Origin 헤더를 Host나 X-Forwarded-Host와 비교해 다른 사이트에서 온 요청을 막고, 본문을 기본 1MB로 제한한다. 어디서도 쓰지 않는 액션은 빌드에서 제거해 엔드포인트를 만들지 않고, 인라인 액션이 붙잡은 값은 빌드마다 바뀌는 키로 암호화한다. 이 보호는 CSRF와 실수로 새는 값을 줄이지만 인증, 권한, 입력 검증은 하지 않는다.

### Origin 검사가 있는데 왜 액션 안에서 인증을 또 하나요?

Origin 검사는 피해자 브라우저를 빌린 교차 사이트 요청을 막는 장치다. Origin 헤더가 없는 요청은 통과시키는데, 직접 만든 요청에는 피해자 쿠키가 없어서 CSRF가 아니라고 보기 때문이다. 공격자가 자기 세션으로 남의 리소스 id를 넣어 보내는 요청은 Origin도 맞고 쿠키도 있다. 그래서 액션마다 사용자 확인과 소유권 확인을 해야 한다.

### 리버스 프록시 뒤에서 모든 서버 액션이 500을 냅니다. 원인은요?

프록시가 Host를 내부 주소로 바꾸고 X-Forwarded-Host를 넘기지 않아 Origin과 호스트가 달라졌을 가능성이 크다. 서버 로그에 "does not match origin header" 메시지가 남는다. 프록시가 원래 호스트를 넘기게 고치거나 `serverActions.allowedOrigins`에 도메인을 적는다. 와일드카드 `*`는 한 칸만 맞추고 `*.com` 같은 넓은 패턴은 모든 도메인을 열어 버리니 조심한다.

### NEXT_PUBLIC_ 환경 변수는 어떻게 동작하고 무엇을 조심하나요?

빌드할 때 코드의 `process.env.NEXT_PUBLIC_X`를 문자열 값으로 바꿔 클라이언트 번들에 넣는다. 그래서 비밀에 붙이면 모든 방문자에게 공개되고, 이미지 하나를 여러 환경에 쓰면 빌드 때 값으로 굳는다. 접두사 없는 변수는 서버에서 실행 시점에 읽는다. 런타임에 바뀌어야 하는 공개 설정은 서버에서 읽어 내려 준다.

### 인라인 서버 액션의 클로저 변수는 안전한가요?

붙잡힌 값은 브라우저로 갔다가 호출 때 돌아와야 해서 Next가 암호화해서 보낸다. 실험에서 HTML에는 평문 없이 암호문만 있었다. 그래도 문서는 암호화에만 기대지 말라고 하고, 여러 인스턴스는 같은 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`를 써야 서로의 암호문을 푼다. 비밀은 붙잡지 말고 id만 붙잡아 액션 안에서 다시 읽는다.

### 데이터 접근 계층(DAL)은 무엇이고 왜 쓰나요?

DB와 내부 API 호출을 `server-only` 폴더 하나로 모으고, 함수마다 인가를 확인한 뒤 화면에 필요한 필드만 담은 DTO를 돌려주는 계층이다. 페이지와 서버 액션은 이 함수만 부른다. 검사를 한 곳에 모아 빠뜨릴 여지를 줄이고, 리뷰할 곳을 좁히고, `cache`로 감싼 현재 사용자 조회를 요청 안에서 나눠 쓴다. taint API는 그 위에 얹는 보조 그물이다.

### 배포 직후 "Failed to find Server Action" 에러가 나는 이유는요?

액션 ID가 빌드 산출물에 묶여 있어 배포마다 바뀔 수 있는데, 옛 화면을 띄워 둔 사용자가 옛 ID로 요청하기 때문이다. 새 서버는 그 ID를 모른다. 롤링 배포로 옛 버전을 잠시 같이 두고, 여러 인스턴스의 암호화 키를 같게 맞추고, 화면에서는 이 에러를 새로고침 안내로 바꿔 보여 준다.
