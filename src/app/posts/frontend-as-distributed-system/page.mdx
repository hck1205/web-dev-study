지하철에서 주문 버튼을 눌렀다. 화면은 한참 돌다가 "네트워크 오류"를 띄웠다. 다시 눌렀더니 이번엔 성공했다. 그런데 주문 내역에는 같은 주문이 두 건 있다. 첫 번째 요청은 실패한 게 아니었다. 서버는 주문을 만들었고, 응답이 돌아오는 길에 터널을 만났을 뿐이다.

백엔드에서는 이런 일을 분산 시스템의 문제라고 부른다. 서버 여러 대가 네트워크로 이어져 있으면 메시지는 사라지고, 늦게 오고, 순서가 바뀌고, 시계는 서로 어긋난다. 브라우저도 다르지 않다. 사용자 기기는 가장 불안정한 네트워크 끝에 붙은 노드고, 같은 사용자가 탭 세 개를 열면 노드가 세 개가 된다. 배포를 하면 옛 코드를 실행하는 노드와 새 서버가 한동안 함께 돈다. 이 글은 그 상황들을 Chromium에서 하나씩 재현하고, 백엔드에서 쓰던 장치를 브라우저 쪽에서 어떻게 쓰는지 본다.

이 주제의 다른 글은 다른 질문에 답한다. 면접에서 이 이야기를 꺼내는 순서는 [프런트엔드 시스템 디자인 면접](/posts/frontend-system-design-interview), 상태마다 자리를 정하는 법은 [프런트엔드 상태 구조](/posts/frontend-state-architecture), 이 장치들을 큰 화면 하나에 엮은 사례는 [뉴스 피드 화면 설계](/posts/fe-sd-news-feed)에 있다. 예제는 Node 22 서버와 Chromium 141(Playwright, 헤드리스)에서 돌렸다. 오프라인은 Playwright의 `setOffline`으로, 사용자 시계는 `page.clock`으로 흉내 냈다. 출력은 찍힌 그대로다.

## 브라우저도 네트워크 끝의 노드다

## 끊긴 걸 아는 방법은 생각보다 적다

먼저 브라우저가 연결이 끊긴 걸 어떻게 알려 주는지 봤다. 페이지를 띄운 뒤 오프라인으로 바꾸고, 요청을 하나 보내고, 다시 온라인으로 돌렸다.

```text
offline 이벤트, navigator.onLine=false
fetch 실패: TypeError: Failed to fetch
online 이벤트, navigator.onLine=true
```

`offline`과 `online` 이벤트, `navigator.onLine` 값이 브라우저가 주는 신호의 전부다. 그런데 이 값은 "네트워크 인터페이스가 연결돼 있는가"에 가깝다. 와이파이에는 붙었지만 인증 페이지에 막힌 카페 와이파이, 신호는 잡히는데 패킷이 거의 안 가는 지하철 LTE에서는 `navigator.onLine`이 `true`인데 요청은 실패한다. MDN도 `true`가 인터넷에 닿는다는 뜻은 아니라고 적고 있다.

`fetch`가 던지는 에러도 정보가 적다. 연결이 끊겼든, DNS가 실패했든, CORS에 막혔든 모두 `TypeError: Failed to fetch`다. 그래서 실무에서는 `navigator.onLine`을 힌트로만 쓰고, 실제 판단은 요청 결과로 한다. 요청이 연달아 실패하면 "연결이 불안정하다"는 띠를 띄우고, 다음 성공에서 걷는다. TanStack Query의 `onlineManager`가 `online` 이벤트를 듣고 멈춘 쿼리를 다시 돌리는 것도 같은 방식이다.

오프라인에서 새로고침을 하면 아예 페이지가 뜨지 않는다.

```text
[오프라인에서 새로고침] page.reload: net::ERR_INTERNET_DISCONNECTED
```

이 지점을 넘으려면 Service Worker가 마지막으로 본 페이지와 정적 파일을 캐시에서 내줘야 한다. 이 블로그의 `sw.js`가 하는 일이 그것이다. 설치와 캐시 전략은 [프런트엔드에서 쓰는 캐시](/posts/frontend-browser-cache)에 정리했다.

## 보내지 못한 요청은 기기에 쌓아 둔다

연결이 끊긴 동안 사용자가 한 일을 버리지 않으려면, 보내지 못한 요청을 기기에 적어 두고 연결이 돌아오면 다시 보낸다. 백엔드의 아웃박스와 같은 생각이다. 요청마다 멱등성 키를 만들어 함께 적어 둔다. 다시 보낼 때 같은 키를 쓰기 위해서다.

```js
window.send = async (item) => {
  const job = { key: crypto.randomUUID().slice(0, 8), item }; // 키는 처음 만들 때 한 번만
  try {
    const r = await post(job);
    L(`보냄 ${item} → ${r.status}`);
  } catch (e) {
    save([...load(), job]);                                   // localStorage의 outbox에 적는다
    L(`실패 ${item}: ${e.name}: ${e.message} → outbox ${load().length}건`);
  }
};
addEventListener("online", () => flush());                    // 연결이 돌아오면 비운다
if (navigator.onLine && load().length) flush();               // 새로 연 페이지도 남은 걸 비운다
```

A를 보내고, 오프라인에서 B를 보내고, 온라인으로 돌렸다. 이어서 오프라인에서 C를 보낸 채 탭을 닫고, 온라인이 된 뒤 새 탭을 열었다.

```text
[탭 1]
보냄 A → 201
offline 이벤트, onLine=false
실패 B: TypeError: Failed to fetch → outbox 1건
online 이벤트, onLine=true
재전송 B (key 9b2bfd42) → 201
[오프라인에서 새로고침] page.reload: net::ERR_INTERNET_DISCONNECTED
(C를 outbox에 둔 채 탭을 닫았다)
[새 탭]
페이지 시작: 남은 outbox C
재전송 C (key a52df098) → 201
서버의 주문: A,B,C
```

B는 연결이 돌아오자 바로 나갔고, C는 탭을 닫았다가 새로 연 탭이 이어받았다. 메모리가 아니라 저장소에 적어 둔 덕분이다. 크롬 계열에는 페이지가 닫혀 있어도 Service Worker가 연결이 돌아왔을 때 깨어나 보내 주는 Background Sync API가 있지만, 사파리와 파이어폭스는 지원하지 않는다. 모든 브라우저에서 동작해야 한다면 위처럼 페이지가 열릴 때 비우는 방식을 기본으로 둔다.

여기서 바로 다음 문제가 나온다. 새 탭과 옛 탭이 동시에 열려 있으면 둘 다 같은 outbox를 비우려 한다. 같은 요청이 두 번 나간다. 키가 같으니 서버가 걸러 주지만, 서버가 키를 보지 않는다면 중복이다. 이게 분산 시스템에서 말하는 "최소 한 번" 전달이다. 클라이언트가 잃지 않으려고 다시 보내는 순간 중복은 피할 수 없고, 중복을 걸러 내는 일은 받는 쪽 몫이 된다.

## 응답을 못 받았다고 처리되지 않은 건 아니다

처음 장면을 그대로 만들었다. 서버는 주문을 만든 뒤 응답을 보내지 않고 연결을 끊는다. 클라이언트는 실패하면 한 번 다시 보낸다. 연결 상태와 키 유무를 바꿔 세 번 돌렸다. 서버 쪽 로그도 함께 찍었다.

```text
== 새 연결, 키 없음
POST /order 도착 (소켓 55634, key=없음)
POST /order 도착 (소켓 55646, key=없음)
fetch 시도 1: TypeError: Failed to fetch
fetch 시도 2: 201 {"id":2}
서버에 생긴 주문 2건
== 재사용 연결, 키 없음
POST /order 도착 (소켓 55658, key=없음)
POST /order 도착 (소켓 55672, key=없음)
fetch 시도 1: 201 {"id":2}
서버에 생긴 주문 2건
== 재사용 연결, 키 있음
POST /order 도착 (소켓 55674, key=218d5956)
POST /order 도착 (소켓 55702, key=218d5956)
fetch 시도 1: 201 {"id":1} (replayed)
서버에 생긴 주문 1건
```

첫 번째는 예상대로다. 첫 시도는 실패로 보였고, 다시 보낸 요청이 두 번째 주문을 만들었다. 두 번째 결과가 더 놀랍다. 앱 코드는 `fetch`를 한 번만 불렀고 성공했다. 그런데 서버에는 요청이 두 번 왔고 주문이 두 건이다. 페이지를 불러올 때 쓴 연결(keep-alive)을 POST가 재사용했는데, 그 연결이 응답 전에 끊기자 Chromium이 스스로 새 연결로 같은 요청을 다시 보낸 것이다. 브라우저는 재사용한 연결이 서버가 이미 닫아 둔 연결이었을 가능성을 보고 다시 보내는데, 서버가 처리를 끝냈는지는 알 수 없다. 이 동작은 Chromium 141에서 확인한 것이고 다른 브라우저가 같은지는 확인하지 않았다.

세 번째 줄이 해법이다. 요청에 멱등성 키를 실으면 브라우저가 몰래 다시 보내든 앱이 다시 보내든 서버가 같은 요청임을 알아보고 처음 응답을 돌려준다. 결제와 주문처럼 두 번 일어나면 안 되는 POST에는 클라이언트가 키를 만들어 실어 보내는 게 기본이다. 키는 사용자가 버튼을 누를 때 한 번 만들고, 재시도할 때는 새로 만들지 않는다. 버튼을 누를 때마다 새 키를 만들면 두 번 누른 주문을 막지 못한다. 서버 쪽에서 키를 저장하고 동시 중복을 막는 구현은 [멱등성 키 구현](/posts/idempotency-key)에, 무엇을 몇 번 다시 보낼지는 [재시도는 공짜가 아니다](/posts/retries)에 있다.

## 누르자마자 바꾼 화면을 서버 답과 맞추기

좋아요 버튼은 서버 답을 기다리지 않고 바로 하트를 채운다. 낙관적 업데이트다. 사용자가 좋아요를 누르고 30ms 뒤에 마음을 바꿔 다시 눌렀다. 서버는 두 요청을 도착 순서대로 처리하는데, 첫 요청의 응답만 300ms 늦게 보내게 했다. 서버는 바꿀 때마다 버전을 하나씩 올려 응답에 담는다.

```js
// 응답이 오면 화면을 서버 값으로 맞춘다
if (mode === "naive" || s.version > ui.version) ui = s;   // versioned는 더 새 버전만 받는다
```

```text
== naive
클릭 → 화면 ♥ (낙관적)
클릭 → 화면 ♡ (낙관적)
응답 v2 liked=false → 화면 ♡
응답 v1 liked=true → 화면 ♥
최종 화면 liked=true, 서버 liked=false (v2)
== versioned
클릭 → 화면 ♥ (낙관적)
클릭 → 화면 ♡ (낙관적)
응답 v2 liked=false → 화면 ♡
응답 v1 liked=true → v2보다 낡아서 버림
최종 화면 liked=false, 서버 liked=false (v2)
```

응답을 받는 대로 화면에 반영한 쪽은 마지막에 늦게 온 첫 응답이 화면을 덮어 하트가 채워진 채로 끝났다. 서버에는 좋아요가 취소돼 있다. 화면과 서버가 다른 걸 믿는 상태다. 새로고침하기 전까지 사용자는 모른다. 버전을 비교한 쪽은 낡은 응답을 버렸다.

버전 말고도 방법이 있다. 같은 항목에 대한 변경은 한 줄로 세워 앞 요청이 끝난 뒤에 다음 요청을 보내는 방법, 앞 요청의 응답을 기다리지 않고 진행 중인 조회를 취소하는 방법이 있다. TanStack Query 문서가 낙관적 업데이트 전에 `cancelQueries`를 부르라고 하는 것도, 진행 중이던 조회 응답이 낙관적으로 바꾼 값을 덮지 않게 하려는 것이다. 어느 쪽이든 원리는 같다. 늦게 온 응답이 더 새 정보라고 가정하지 않는다. 낙관적 업데이트의 기본 흐름과 실패 시 되돌리기는 [화면 데이터 캐시](/posts/client-data-cache)에, 서버에서 버전으로 덮어쓰기를 막는 방법은 [낙관적 잠금](/posts/optimistic-locking)에 있다.

직접 해 보자. 처음 상태와 도착한 순서대로 나열한 응답들이 주어진다. 더 높은 버전만 받아들일 때 마지막 상태를 돌려주는 함수다.

## 탭 세 개는 노드 세 개다

같은 사용자가 탭 두 개를 열어 두고 한쪽에서 로그아웃했다. 다른 탭은 여전히 로그인된 화면으로 남아 있다가, 다음 요청에서 401을 받고서야 깨닫는다. 탭끼리는 메모리를 공유하지 않으니 알려 줘야 한다. 같은 출처의 탭끼리 메시지를 주고받는 방법은 두 가지다. `BroadcastChannel`과 `localStorage`의 `storage` 이벤트다. 탭 1에서 둘 다 써서 로그아웃을 알렸다.

```js
// 탭 1
const ch = new BroadcastChannel("auth");
ch.postMessage({ type: "logout", at: performance.timeOrigin + performance.now() });
localStorage.setItem("session", "none");
```

```text
[탭 2]
BroadcastChannel 받음: {"type":"logout","at":1792631752524.7002} (+1.9ms)
storage 이벤트: key=session old=null new=none
[탭 1]
(아무것도 받지 않음)
```

탭 2는 2ms 안에 두 신호를 다 받았고, 보낸 탭 1은 자기 메시지를 받지 않았다. 두 방법 모두 보낸 쪽에는 알리지 않는다. 그래서 보낸 탭은 자기 상태를 직접 바꾸고, 다른 탭은 메시지를 듣고 바꾸도록 코드를 둘로 나눈다. 차이도 있다. `storage` 이벤트는 값을 실제로 저장해야 일어나고 같은 값을 다시 쓰면 일어나지 않는다. 대신 저장된 값이 남으니 나중에 열린 탭도 읽을 수 있다. `BroadcastChannel`은 아무 객체나 구조화 복제로 보낼 수 있지만, 그 순간 열려 있지 않은 탭은 받지 못한다. 로그아웃처럼 상태가 남아야 하는 건 저장소에 쓰고, "방금 새 글이 올라왔다" 같은 순간 알림은 채널로 보내는 식으로 고른다. `storage` 이벤트의 세부는 [브라우저 저장소](/posts/browser-storage)에 있다.

탭이 여럿이면 "한 탭만 해야 하는 일"도 생긴다. 실시간 알림을 받는 WebSocket을 탭마다 열면 사용자 한 명이 연결 다섯 개를 잡는다. 하나의 탭만 연결을 들고 나머지에 채널로 나눠 주면 되는데, 그 하나를 고르는 데 Web Locks API(`navigator.locks.request`)를 쓸 수 있다. 잠금을 쥔 탭이 닫히면 잠금이 풀리고 다른 탭이 이어받는다. 현재 주요 브라우저가 지원하지만 오래된 브라우저까지 받쳐야 한다면 지원 여부를 확인한다.

백그라운드에 오래 있던 탭이 다시 앞으로 오는 순간도 챙긴다. 그 사이 서버 데이터는 낡았다. `visibilitychange`나 창 포커스를 받으면 화면에 보이는 데이터를 다시 받는다. TanStack Query의 `refetchOnWindowFocus`가 이 일을 한다.

## 사용자 시계는 믿을 수 없다

토큰을 받을 때 만료 시각(`exp`)을 함께 받아, 만료 직전에 미리 갱신하는 코드가 흔하다. 문제는 그 비교를 사용자 기기의 `Date.now()`로 한다는 점이다. 사용자 시계가 10분 빠른 상황을 `page.clock`으로 만들고, 서버가 300초짜리 토큰을 줬다.

```text
== client-clock
Date 헤더 Thu, 22 Oct 2026 01:15:52 GMT, 브라우저 Date.now() Thu, 22 Oct 2026 01:25:52 GMT
추정 시계 차이 -601초, 토큰 남은 시간 -301초 → 만료로 판단, 갱신 요청
== server-offset
Date 헤더 Thu, 22 Oct 2026 01:15:52 GMT, 브라우저 Date.now() Thu, 22 Oct 2026 01:25:52 GMT
추정 시계 차이 -601초, 토큰 남은 시간 300초 → 유효
```

기기 시계로 비교한 쪽은 방금 받은 토큰을 이미 5분 전에 만료된 것으로 봤다. 이 코드가 "만료됐으면 갱신"을 반복하면 갱신 요청이 끝없이 나간다. 사용자의 시계는 손으로 바꿀 수 있고, 시간대를 잘못 고를 수 있고, 배터리가 빠진 뒤 엉뚱한 시각으로 켜지기도 한다.

고친 쪽은 응답의 `Date` 헤더로 서버와 기기의 시계 차이를 재서 보정했다. 차이가 600초가 아니라 601초로 나온 건 `Date` 헤더가 초 단위로 잘리고 왕복 시간이 섞이기 때문이다. 정밀하진 않지만 몇 분씩 어긋난 시계를 잡기엔 충분하다. 더 단순한 방법도 있다. 서버가 절대 시각 대신 "앞으로 몇 초 유효"(`expires_in`)를 주면, 클라이언트는 받은 순간부터 `performance.now()` 같은 단조 시계로 재면 된다. 단조 시계는 사용자가 시계를 바꿔도 뒤로 가지 않는다. 벽시계와 단조 시계의 차이, 서버끼리의 시계 문제는 [시계 어긋남](/posts/clock-skew)에 정리했다.

시계 문제는 화면에도 나온다. "3분 전"처럼 상대 시간을 기기 시계로 계산하면 시계가 빠른 사용자에게는 방금 쓴 댓글이 "10분 전"으로 보이고, 느린 사용자에게는 "-7분 전"이 된다. 서버 시각으로 보정하거나, 음수는 "방금"으로 고정한다.

## 옛 코드와 새 서버가 함께 돈다

배포는 서버에서는 몇 분이면 끝나지만 브라우저에서는 끝나지 않는다. 사용자가 어제 연 탭은 어제의 자바스크립트를 들고 있다. 그 탭이 오늘 배포된 서버와 대화한다. 서버 여러 대가 서로 다른 버전으로 함께 도는 상황을 버전 차이(skew)라고 하는데, 프런트엔드에서는 이 기간이 사용자가 탭을 닫을 때까지다.

가장 먼저 터지는 곳은 코드 조각을 나중에 불러오는 자리다. v1 페이지를 띄워 둔 채 v2를 배포하면서 옛 청크 파일을 지웠다. 그 뒤 v1 탭이 아직 안 불러온 청크를 불렀다.

```text
v1에서 import: chart
TypeError: Failed to fetch dynamically imported module: http://127.0.0.1:19420/assets/chart-3f9a1c.js?r=2
```

v1 코드가 아는 파일 이름은 `chart-3f9a1c.js`인데 서버에는 이제 `chart-8b72de.js`만 있다. 사용자는 차트 탭을 눌렀는데 아무것도 안 뜬다. 에러 추적 도구에 배포 직후마다 이 에러가 몰려온다면 거의 이 경우다. webpack이라면 `ChunkLoadError`로 보인다.

대응은 세 겹으로 둔다. 첫째, 옛 정적 파일을 바로 지우지 않는다. 파일 이름에 내용 해시가 들어 있으니 v1과 v2 파일이 같은 저장소에 함께 있어도 충돌하지 않는다. 며칠 또는 몇 번의 배포 동안 남겨 두면 대부분의 옛 탭이 무사히 넘어간다. 둘째, 클라이언트가 자기 버전을 알고 서버 버전과 비교한다. 아래처럼 API 응답에 서버가 배포 버전을 헤더로 실어 주면, 클라이언트는 다르다는 걸 알았을 때 다음 화면 이동에서 조용히 새로고침한다. 사용자가 입력 중인 폼을 날리지 않으려면 지금 화면에서 바로 새로고침하지 않는다.

```text
/api/me 응답 x-app-version=v2, 내 버전=v1 → 새 버전 있음, 다음 화면 이동 때 새로고침
```

셋째, 청크 로딩이 실패하면 한 번만 새로고침을 시도한다. 무한 새로고침을 막으려고 시도 여부를 `sessionStorage`에 표시해 둔다. 이 패턴과 청크 파일 이름의 해시는 [코드 스플리팅](/posts/code-splitting)에서 다뤘다. Vercel 같은 일부 플랫폼은 요청에 배포 ID를 실어 옛 클라이언트를 옛 배포로 보내 주는 기능(Skew Protection)을 제공하는데, 지원 범위와 보존 기간은 플랫폼과 요금제마다 다르니 문서를 확인한다.

API 쪽에서는 하위 호환이 이 문제를 받친다. 응답에서 필드를 빼거나 이름을 바꾸는 배포는 옛 탭을 바로 깨뜨린다. 필드는 먼저 추가하고, 클라이언트가 새 필드를 쓰게 배포하고, 옛 탭이 충분히 사라진 뒤에 옛 필드를 뺀다. 순서와 도구는 [API 버전 관리](/posts/api-versioning)에 있다.

## 증상에서 거꾸로 찾아가기

"주문이 두 건 들어갔다"는 문의가 오면 서버 로그에서 두 요청의 간격과 연결을 본다. 수백 ms 안에 같은 본문이 연달아 왔다면 재시도다. 앱의 재시도인지 브라우저나 프록시의 재전송인지는 상관없다. 멱등성 키가 없으면 어느 쪽이든 막을 수 없다.

"좋아요를 취소했는데 새로고침하면 다시 눌려 있다" 또는 그 반대라면 낙관적 업데이트 뒤 응답 순서를 의심한다. 네트워크 탭에서 같은 항목에 대한 요청이 겹쳐 있는지 보고, 응답에 버전이나 갱신 시각이 있는지 확인한다.

"배포 직후 특정 화면만 안 뜬다"면 에러 추적에서 `Failed to fetch dynamically imported module`이나 `ChunkLoadError`를 찾는다. 배포 시각과 겹치고 옛 릴리스 이름에서만 나면 버전 차이다.

"어떤 사용자만 계속 로그아웃된다"면 그 사용자 요청의 시각과 기기 시계를 비교한다. 클라이언트 로그에 `Date.now()`를 함께 남기면 서버 시각과의 차이가 바로 보인다.

"로그아웃했는데 다른 탭에서 계속 쓸 수 있었다"면 탭 사이 알림이 없는 것이다. 서버는 이미 세션을 끊었을 테니 보안 문제라기보다 경험 문제지만, 공용 컴퓨터라면 다른 탭에 개인 정보가 그대로 떠 있다.

브라우저를 믿을 수 있는 화면이 아니라 불안정한 네트워크 끝의 노드로 보면 할 일이 정해진다. 보낸 요청은 사라질 수 있으니 키를 붙이고, 응답은 거꾸로 올 수 있으니 버전을 붙이고, 탭은 여럿일 수 있으니 서로 알리고, 시계와 코드는 낡았을 수 있으니 서버 기준으로 맞춘다.

## 면접에서 나올 만한 질문

### 프런트엔드를 분산 시스템으로 본다는 건 무슨 뜻인가요?

사용자 기기를 불안정한 네트워크 끝에 붙은 노드로 본다는 뜻이다. 메시지는 사라지고 늦게 오고 순서가 바뀌며, 탭 여러 개는 각자 메모리를 가진 노드고, 배포하면 옛 코드를 실행하는 노드가 새 서버와 함께 돈다. 그래서 서버 사이에서 쓰던 재시도, 멱등성 키, 버전 비교, 시계 보정을 클라이언트에서도 쓴다. 다른 점은 클라이언트 코드를 배포로 바로 고칠 수 없다는 것이다.

### 요청이 실패로 보였는데 서버에서는 처리된 경우를 어떻게 다루나요?

응답만 사라졌을 수 있으니 실패가 곧 미처리라고 가정하지 않는다. 두 번 일어나면 안 되는 요청에는 클라이언트가 멱등성 키를 만들어 싣고, 재시도할 때 같은 키를 쓴다. 서버는 같은 키를 보면 처음 응답을 돌려준다. 실험에서는 앱이 fetch를 한 번만 불렀는데도 Chromium이 재사용 연결 실패 뒤 POST를 다시 보내 주문이 두 건 생겼고, 키를 실으면 한 건으로 끝났다.

### 오프라인 상태는 어떻게 감지하고, 그동안 한 일은 어떻게 보존하나요?

online·offline 이벤트와 navigator.onLine이 있지만 인터페이스 연결 여부에 가까워서, 연결은 됐는데 인터넷이 안 되는 상황을 잡지 못한다. 그래서 힌트로만 쓰고 실제 판단은 요청 결과로 한다. 보내지 못한 요청은 멱등성 키와 함께 저장소의 outbox에 적어 두고, online 이벤트나 다음 페이지 시작 때 비운다. 크롬 계열의 Background Sync는 다른 브라우저가 지원하지 않으니 기본 경로로 삼지 않는다.

### 낙관적 업데이트에서 응답 순서가 뒤바뀌면 어떻게 되나요?

늦게 온 낡은 응답이 화면을 덮어 화면과 서버가 서로 다른 상태로 끝날 수 있다. 실험에서 좋아요를 눌렀다 바로 취소하자 첫 응답이 늦게 와서 화면은 좋아요, 서버는 취소인 채로 남았다. 서버가 응답에 버전을 담고 클라이언트가 더 높은 버전만 받아들이면 막을 수 있다. 같은 항목의 변경을 한 줄로 세우거나 진행 중인 조회를 취소하는 방법도 있다.

### 여러 탭의 상태를 어떻게 맞추나요?

BroadcastChannel이나 localStorage의 storage 이벤트로 알린다. 둘 다 보낸 탭에는 알리지 않아서 보낸 탭은 직접 바꾸고 다른 탭은 듣고 바꾼다. 상태가 남아야 하는 로그아웃 같은 건 저장소에 쓰고, 순간 알림은 채널로 보낸다. 탭마다 WebSocket을 여는 대신 Web Locks로 한 탭만 연결을 들고 나머지에 나눠 주는 방법도 있다.

### 클라이언트 시계를 믿으면 어떤 문제가 생기나요?

사용자 시계는 바뀌거나 틀릴 수 있어서 만료 판단과 상대 시간 표시가 깨진다. 실험에서 기기 시계가 10분 빠르자 방금 받은 300초짜리 토큰이 만료로 보였다. 응답의 Date 헤더로 서버와의 차이를 재 보정하거나, 서버가 남은 초(expires_in)를 주고 클라이언트는 performance.now 같은 단조 시계로 재게 한다.

### 배포 직후 ChunkLoadError가 쏟아지는 이유와 대응은요?

옛 탭이 들고 있는 코드가 배포로 지워진 옛 청크 파일을 찾기 때문이다. 해시가 붙은 옛 정적 파일을 한동안 남겨 두고, API 응답의 버전 헤더로 새 배포를 알아채 다음 화면 이동 때 새로고침하고, 청크 로딩이 실패하면 한 번만 새로고침을 시도한다. API는 필드를 먼저 추가하고 옛 탭이 사라진 뒤에 빼는 순서로 하위 호환을 지킨다.

### 이 장치들을 넣으면 생기는 비용은 무엇인가요?

멱등성 키는 서버가 키와 응답을 저장해야 하고 보존 기간을 정해야 한다. outbox는 저장소 한도와 여러 탭의 동시 비우기를 다뤄야 하고, 버전 비교는 API가 버전을 내려 줘야 한다. 옛 정적 파일 보존은 저장 비용이 들고, 버전 헤더를 커스텀 헤더로 보내면 다른 출처 요청에서 CORS 사전 요청이 늘어난다. 모든 요청에 다 넣기보다 두 번 일어나면 안 되는 요청과 자주 바뀌는 항목부터 넣는다.
