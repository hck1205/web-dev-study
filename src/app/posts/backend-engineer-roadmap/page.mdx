"주문 API가 가끔 2초 넘게 걸린다"는 제보를 받았다고 해 보자. 대시보드의 평균 응답 시간은 230ms 근처로 평온하다. 범인을 찾으려면 꽤 여러 곳을 뒤져야 한다.

- 응답 헤더와 상태 코드를 읽어 요청이 앱까지 왔는지부터 본다.
- 로그인 요청이 몰릴 때 비밀번호 해시가 Node 스레드 풀을 다 차지했는지 본다.
- "내 주문 목록" 쿼리가 주문이 늘면서 인덱스 없이 테이블 전체를 읽게 됐는지 본다.
- 이번 배포 이미지가 테스트를 통과한 그 이미지인지 확인한다.
- 평균이 아니라 p99를 그려 본다. 그래야 2초가 그래프에 드러난다.
- 마지막으로 방금 만든 주문이 복제본에서 안 보여 클라이언트가 재시도를 반복한 건 아닌지 본다.

이 증상 하나를 쫓는 데 HTTP, 런타임, DB, 배포, 관측, 분산 시스템이 다 들어간다. "Backend Engineer Skill Hierarchy 2026"이라는 이미지는 이걸 여섯 층으로 쌓았다. 1층 HTTP·Git·JS나 Python, 2층 Node.js·Express나 FastAPI·REST, 3층 PostgreSQL·SQL 인덱스·Redis, 4층 인증·테스트·Docker, 5층 메시지 큐·CI/CD·모니터링, 6층 시스템 설계·분산 시스템이다.

이 글은 그 여섯 층을 이 블로그의 글로 잇는다. 새 개념은 설명하지 않는다. 층마다 왜 그 자리에 있는지, 먼저 읽을 글을 한 줄씩, 그 층에서 직접 만들어 볼 것, 다 됐다고 판단할 기준을 적었다. 층 안에서 더 자세한 지도가 필요하면 [자바스크립트 로드맵](/posts/javascript-roadmap), [SQL 공부 순서](/posts/sql-study-path), [시스템 디자인 공부 순서](/posts/system-design-study-path), [네트워킹 학습 지도](/posts/networking-essentials-map)로 넘어간다.

## 아래층이 위층의 재료다

미들웨어 순서 버그는 요청이 헤더와 본문으로 나뉜다는 걸 알아야 보인다. 그래서 1층이 2층 앞에 있다. 인덱스를 고르려면 내 API가 어떤 조건으로 어떤 순서의 목록을 돌려주는지 알아야 하는데, 그건 2층에서 API를 설계해 본 사람이 안다. 실제 DB에 붙는 통합 테스트는 3층 없이는 쓸 수 없고, Docker로 앱과 DB를 함께 띄우는 일은 둘 다 있어야 의미가 있다. ## 1층: 요청 한 줄을 읽는다

1층은 백엔드가 주고받는 말 자체다. HTTP가 무엇을 보내고 받는지, 코드를 어떻게 남기고 합치는지, 그리고 그 코드를 쓸 언어 하나.

[주소창에 google.com을 치면 일어나는 일](/posts/what-happens-google-com)은 DNS부터 렌더링까지 요청 하나의 전체 길을 한 번 따라가는 글이라, 1층의 첫 글로 맞다.

[HTTP 메시지는 어떻게 생겼나](/posts/http-message)에서 첫 줄, 헤더, 빈 줄, 본문을 curl로 뜯어본다. Content-Type과 Content-Length가 서버 코드의 본문 파싱을 정한다.

[HTTP 메서드와 안전성·멱등성](/posts/http-methods)은 재시도해도 되는 요청과 안 되는 요청을 가른다. 5층의 재시도와 6층의 멱등성 키가 전부 이 구분 위에 선다.

[HTTP 상태 코드 제대로 쓰기](/posts/http-status-codes)는 401과 403, 502와 504를 누가 만드는지 알려 준다. 장애 때 가장 먼저 보는 숫자다.

Git은 [작업 트리, 인덱스, HEAD](/posts/git-staging-area)로 add와 commit 사이를 이해하고, [브랜치와 병합](/posts/git-branch-merge), [원격 저장소와 협업](/posts/git-remote-collaboration)까지 읽으면 혼자가 아닌 저장소에서 일할 수 있다. 실수했을 때는 [되돌리기](/posts/git-undo)를 편다.

언어는 하나만 깊게 한다. 자바스크립트라면 [자바스크립트 로드맵](/posts/javascript-roadmap)이 열두 장을 순서대로 잇는다. 파이썬 언어 자체를 다룬 글은 이 블로그에 아직 없고, 파이썬 쪽은 2층의 FastAPI 글에서 서버 관점으로 다룬다.

이 층에서 만들 것은 프레임워크 없이 Node 내장 `http` 모듈로 띄운 서버 하나다. 주문 목록을 JSON으로 돌려주는 20줄짜리면 충분하다. 띄운 뒤 curl로 두 번 불러 봤다(Node 22).

```js
import { createServer } from "node:http";

const orders = [{ id: 1, item: "pen", qty: 2 }];

createServer((req, res) => {
  if (req.method === "GET" && req.url === "/orders") {
    res.writeHead(200, { "Content-Type": "application/json" });
    return res.end(JSON.stringify(orders));
  }
  res.writeHead(404, { "Content-Type": "application/json" });
  res.end(JSON.stringify({ error: "not found" }));
}).listen(18471);
```

```bash
curl -i http://localhost:18471/orders          # 목록 조회
curl -i -X POST http://localhost:18471/orders  # 아직 없는 생성 요청
```

```text
HTTP/1.1 200 OK
Content-Type: application/json
Date: Wed, 21 Oct 2026 18:52:01 GMT
Connection: keep-alive
Keep-Alive: timeout=5
Transfer-Encoding: chunked

[{"id":1,"item":"pen","qty":2}]

HTTP/1.1 404 Not Found
Content-Type: application/json
Date: Wed, 21 Oct 2026 18:52:01 GMT
Connection: keep-alive
Keep-Alive: timeout=5
Transfer-Encoding: chunked

{"error":"not found"}
```

출력에서 볼 곳이 세 군데 있다. 본문 길이를 미리 안 정했더니 `Transfer-Encoding: chunked`로 나갔다. `Connection: keep-alive`라 응답 뒤에도 연결이 닫히지 않고, 다음 요청 없이 5초가 지나야 닫힌다. 그리고 POST가 404를 받았다. 경로 `/orders`는 있는데 메서드만 다르니, 맞는 답은 `Allow: GET` 헤더를 붙인 405다. 이 차이가 왜 중요한지 바로 설명할 수 있으면 1층은 거의 끝났다.

다 됐다고 볼 수 있을 때는 이렇다. `curl -v` 출력에서 요청 줄, 응답 헤더, 본문을 나눠 읽는다. PUT과 POST 중 무엇을 재시도해도 되는지 이유와 함께 말한다. 동료와 같은 브랜치를 건드려 push가 거절돼도 fetch와 rebase로 혼자 풀어낸다.

## 2층: 요청을 받는 프로그램을 쓴다

2층은 1층의 요청을 받아 처리하는 프로그램이다. 런타임이 요청을 어떻게 받는지, 프레임워크가 그 위에 무엇을 얹는지, 바깥에 어떤 약속(API)을 내보일지를 다룬다.

[자바스크립트 이벤트 루프](/posts/event-loop)가 출발점이다. 콜 스택 하나로 수많은 요청을 받는 구조를 먼저 이해해야 다음 글이 읽힌다.

[Node.js 서버 런타임](/posts/nodejs-server-runtime)은 그 루프 옆의 libuv 스레드 풀을 본다. 기본 4칸짜리 풀을 비밀번호 해시가 차지하면 파일 읽기까지 느려지는 장면이 위 제보와 같은 모양이다.

[Express 미들웨어](/posts/express-middleware)는 앱을 등록 순서대로 선 함수의 줄로 본다. 순서 버그, Express 4에서 async 에러가 프로세스를 내리는 이유, 배포 때 502를 막는 정상 종료까지 다룬다.

[FastAPI](/posts/fastapi-basics)는 같은 주문 서비스를 파이썬으로 다시 만든다. 422 검증 응답, Depends, `async def` 안의 블로킹 호출이 서버를 세우는 이유를 Express와 나란히 놓는다. Express와 FastAPI 중 하나를 고르는 건 2층에서 중요한 일이 아니다. 둘 다 "요청 → 검증 → 핸들러 → 응답"이라는 같은 줄을 다른 문법으로 쓴다.

[JSON으로 데이터 주고받기](/posts/json-crud-http)에서 생성·조회·수정·삭제를 실제 요청으로 해 보고, [REST API를 설계할 때 정할 것들](/posts/rest-api-design)에서 자원 이름, 에러 형식, 커서 페이지네이션처럼 공개 전에 정할 것을 정리한다.

두 번째 언어가 궁금해지면 [Go 동시성 기본기](/posts/go-concurrency-basics)나 [JVM 메모리와 스레드](/posts/java-jvm-memory-gc)를 읽는다. 이벤트 루프 하나로 버티는 Node와, 고루틴이나 스레드 풀로 요청마다 실행 흐름을 주는 런타임을 비교해 보면 Node가 잘하는 일과 못하는 일이 더 또렷해진다.

이 층에서 만들 것은 1층 서버를 Express나 FastAPI로 옮긴 주문 CRUD API다. 저장소는 아직 메모리 배열이면 된다. 대신 본문 검증 실패는 400이나 422로, 없는 주문은 404로, 메서드가 틀리면 405로 답한다. 에러 응답 모양을 하나로 맞추고, 본문 크기 한도를 걸고, `SIGTERM`을 받으면 처리 중인 요청을 마치고 내려가게 만든다.

다 됐다고 볼 수 있을 때는 이렇다. 핸들러 안에서 `crypto.pbkdf2Sync`를 부르면 다른 요청이 왜 같이 멈추는지 설명한다. 인증 미들웨어를 라우터 뒤에 등록하면 어떤 일이 생기는지 코드 없이 말한다. 목록 API에 페이지를 붙일 때 offset 대신 커서를 쓰는 이유를 댄다.

## 3층: 데이터를 오래, 빨리 꺼낸다

메모리 배열은 서버를 껐다 켜면 사라지고, 서버를 두 대로 늘리면 둘이 다른 주문을 본다. 3층은 데이터를 프로세스 밖에 오래 두고, 커져도 빨리 꺼내는 법이다.

[PostgreSQL 설치하고 접속하기](/posts/postgres-getting-started)로 클러스터, 데이터베이스, 스키마의 구조와 psql을 익힌다. SQL 문법은 [SQL 공부 순서](/posts/sql-study-path)가 쿼리 하나를 SELECT부터 윈도 함수까지 여섯 단계로 키우며 안내하니, 여기서는 그 글로 넘긴다.

[인덱스: 책 뒤의 찾아보기](/posts/db-index)는 주문 100만 건에서 느려진 조회를 실행 계획으로 따라간다. 이어서 [인덱스가 안 타는 이유와 인덱스의 대가](/posts/db-index-pitfalls)를 읽어야 "인덱스를 걸었는데 왜 Seq Scan이냐"에 답할 수 있다.

[트랜잭션과 격리 수준](/posts/db-transaction-isolation)은 마지막 재고 하나를 두 사람이 동시에 사서 -1이 되는 장면에서 시작한다. 동시성 버그는 테스트에서 잘 안 보이고 운영에서 터진다.

[커넥션 풀 깊이 보기](/posts/connection-pool)는 앱과 DB 사이의 연결을 다룬다. 풀이 고갈되면 쿼리는 빠른데 요청이 느린, 헷갈리는 증상이 나온다.

[Redis는 왜 빠른가](/posts/redis-basics)에서 메모리와 단일 스레드 구조를 보고, [캐시 전략](/posts/caching-strategies)에서 언제 넣고 언제 지울지를 정한다. 캐시 개념 전체의 지도는 [캐시 개념 지도](/posts/caching-concepts-map)에 있다.

이 층에서 만들 것은 2층 API의 저장소를 PostgreSQL로 바꾸는 일이다. `users`, `products`, `orders` 세 테이블에 외래 키와 제약 조건을 걸고, 주문 생성은 재고 차감과 한 트랜잭션으로 묶는다. 주문을 수십만 건 넣은 뒤 "내 최근 주문 20건" 쿼리를 `EXPLAIN ANALYZE`로 재고, 인덱스를 건 전후를 비교한다. 상품 상세는 Redis에 cache-aside로 얹고, 상품을 고치면 캐시를 지운다.

다 됐다고 볼 수 있을 때는 이렇다. `EXPLAIN ANALYZE` 출력에서 Seq Scan과 Index Scan, 예상 행 수와 실제 행 수가 크게 다른 줄을 짚어 낸다. 복합 인덱스의 열 순서를 쿼리의 WHERE와 ORDER BY로 정한다. 재고가 음수가 되는 경쟁을 조건부 UPDATE 한 줄로 막는다. 캐시를 지우는 순서를 바꾸면 옛 값이 남는 경우를 그림으로 그린다.

## 4층: 막고, 확인하고, 어디서나 똑같이 띄운다

3층까지 오면 서비스가 돌아간다. 4층은 그 서비스를 남에게 내놓기 전에 필요한 세 가지다. 아무나 못 쓰게 하는 인증과 인가, 고쳐도 안 깨진다는 걸 보여 주는 테스트, 내 노트북이 아닌 곳에서도 똑같이 뜨게 하는 컨테이너다. 셋을 한 층에 묶은 이유가 있다. 셋 다 3층까지 만든 것이 있어야 시작할 수 있고, 5층의 CI가 셋을 한꺼번에 돌린다.

인증은 [쿠키와 세션으로 로그인 상태 유지하기](/posts/cookie-session-login)와 [토큰으로 로그인하기](/posts/token-login)를 이어 읽고 둘을 비교한다. 위 그림의 네 번째 단계처럼 "누구냐"와 "해도 되냐"를 가르는 이야기는 [인증과 인가](/posts/authn-vs-authz)에 있다. 다른 서비스의 계정으로 로그인시키려면 [OAuth 2.0](/posts/oauth)으로 간다.

컨테이너는 [컨테이너는 무엇인가](/posts/docker-container-basics)로 namespace와 cgroups를 확인하고, [Dockerfile과 이미지 레이어](/posts/dockerfile-image-layers)로 이미지를 작고 빠르게 만들고, [Docker Compose](/posts/docker-compose)로 앱, PostgreSQL, Redis를 한 파일로 띄운다.

이 층에서 만들 것은 3층 API에 로그인과 "내 주문만 보기"를 붙이고, 주문 금액 계산 같은 순수 로직은 단위 테스트로, 주문 생성 API는 실제 DB를 붙인 통합 테스트로 덮는 일이다. 마지막에 `docker compose up` 한 줄로 앱, DB, Redis가 뜨고 `docker compose run` 한 줄로 테스트가 도는 저장소를 만든다.

다 됐다고 볼 수 있을 때는 이렇다. 세션과 JWT 중 하나를 고르고 로그아웃과 강제 만료를 어떻게 처리하는지까지 말한다. 테스트 하나가 실패했을 때 그게 코드 버그인지 테스트가 시계나 순서에 기대서인지 가려낸다. 소스 한 줄을 고쳤는데 `npm install`부터 다시 도는 Dockerfile을 고친다.

## 5층: 요청이 끝난 뒤에도 일하는 서비스

4층까지는 요청이 들어오고 응답이 나가면 끝났다. 5층은 그 바깥이다. 요청과 떼어 놓고 나중에 하는 일(큐), 코드가 운영까지 가는 길(CI/CD), 운영 중인 서비스가 지금 어떤지 아는 법(모니터링)이다.

큐는 [메시지 큐 기초](/posts/message-queue-basics)에서 ack와 가시성 타임아웃, 최소 한 번 전달에서 생기는 중복을 Redis와 PostgreSQL로 돌려 본다. 중복을 받는 쪽에서 어떻게 걸러 내는지는 [메시지 전달 보장](/posts/message-delivery-semantics)이, 파티션과 소비자 그룹은 [Kafka 기초](/posts/kafka-basics)가 다룬다.

아래 그림은 이 층에서 만드는 메일 워커다. 처리한 주문 ID를 기록해 두고, 같은 메시지가 다시 오면 메일을 다시 보내지 않는다.

메일 발송처럼 DB 밖으로 나가는 일은 기록과 한 트랜잭션에 묶을 수 없어서, 보낸 직후 기록 전에 죽으면 여전히 두 번 나갈 수 있다. 이 틈을 어디까지 줄일지가 [메시지 전달 보장](/posts/message-delivery-semantics) 글의 주제다.

배포는 [CI/CD의 뼈대](/posts/ci-cd-basics)에서 한 번 빌드한 이미지를 digest로 승격하는 흐름을 보고, [GitHub Actions로 이미지 빌드하고 ECR에 올리기](/posts/github-actions-docker-ecr)에서 오래 사는 키 대신 OIDC를 쓰는 워크플로를 읽는다.

관측은 [모니터링 기본](/posts/monitoring-basics)에서 네 가지 황금 신호와 RED·USE로 무엇을 잴지 정하고, [구조화 로그](/posts/structured-logging)로 요청 ID가 붙은 JSON 로그를 남기고, [응답 시간은 백분위로 읽는다](/posts/percentile-latency)에서 평균이 꼬리를 가리는 이유를 본다. 이 글 첫 장면의 "평균 230ms, 가끔 2초"가 정확히 그 이야기다.

백분위는 손으로 한 번 구해 보면 오래 기억에 남는다. 아래에서 요청 20건의 응답 시간으로 p50, p95, p99를 구하는 함수를 완성해 본다. 순위는 nearest-rank 방식으로 ⌈p/100 × n⌉번째 값이다. 자바스크립트의 기본 `sort()`는 숫자를 문자열로 비교한다는 것도 같이 확인할 수 있다.

같은 20건의 평균은 234.15ms다. p50은 44ms, p99는 2100ms다. 평균 하나만 보면 대부분의 요청이 200ms쯤 걸리는 것처럼 읽히지만 실제로는 거의 다 50ms 안팎이고 두 건만 2초 가까이 걸렸다. 기본 `sort()`로 정렬하면 `1800, 2100, 35, …` 순서가 되어 p50이 42, p99가 52로 나온다. 느린 요청이 숫자에서 사라지는 셈이다. 그리고 20건에서는 p99가 그냥 최댓값이다. p99를 말하려면 창 안에 수백 건 이상이 있어야 한다.

이 층에서 만들 것은 주문 확인 메일을 큐와 워커로 떼어 내고, 워커를 일부러 죽여 중복이 걸러지는지 보는 일이다. PR마다 단위·통합 테스트를 돌리고 이미지를 한 번 만드는 CI를 붙이고, 앱에는 요청 수, 에러 수, 응답 시간 히스토그램을 내보내 p99 그래프와 "5분 동안 에러율 2% 초과" 같은 알림 하나를 건다.

다 됐다고 볼 수 있을 때는 이렇다. 큐 깊이 그래프가 계속 올라갈 때 소비자를 늘려야 하는지 처리 시간을 줄여야 하는지 가린다. 스테이징에서 본 이미지와 운영 이미지가 같은 digest인지 확인하는 법을 안다. 알림이 울렸을 때 지표에서 로그로, 로그의 요청 ID에서 그 요청 하나로 내려간다.

## 6층: 서버 한 대로 안 될 때

5층까지 만든 서비스는 서버 한 대, DB 한 대로 돌아간다. 6층은 그 한 대가 모자라거나 죽을 때의 이야기다. 늘리는 순간 아래층에서 당연했던 것들이 깨진다. 메모리에 둔 세션이 서버마다 다르고, 방금 쓴 데이터가 복제본에 없고, 네트워크가 끊기면 두 대가 서로 자기가 주인이라고 믿는다.

공부 순서는 이미 따로 정리돼 있다. [시스템 디자인 공부 순서](/posts/system-design-study-path)가 서버 한 대에 부품을 하나씩 붙이는 기초 글부터 설계 사례까지 순서를 잡고, [시스템 설계 25가지 개념 지도](/posts/system-design-concepts-map)가 개념을 일곱 묶음으로 나눈다. 여기서는 5층에서 넘어온 사람이 처음 읽을 글만 고른다.

[수평 확장과 수직 확장](/posts/scaling-horizontal-vertical)은 위 그림의 두 번째 단계, 메모리 세션 때문에 로그인이 풀리는 장면을 직접 재현한다.

[DB 한 대로 버티지 못할 때](/posts/db-replication-sharding)는 다섯 번째 단계의 복제 지연을 PostgreSQL 16에서 만들고 LSN으로 막는다. 그 다음 편인 [최종 일관성과 세션 보장](/posts/eventual-consistency)은 내 쓰기 읽기를 세션 토큰으로 지킨다.

[장애가 번지지 않게](/posts/resilience-patterns)는 느린 의존성 하나가 스레드 풀을 바닥내며 번지는 연쇄 장애와 타임아웃, 재시도, 서킷 브레이커를 다룬다. 5층의 큐와 멱등성이 여기서 다시 쓰인다.

분산 시스템의 이론 쪽은 [일관성 모델](/posts/consistency-models)과 [Raft 합의](/posts/raft-consensus)가 기둥이다. 복제본 여러 대가 같은 값을 본다는 말이 정확히 무엇인지, 리더가 죽었을 때 누가 어떻게 이어받는지가 여기 있다.

코드 구조를 어떻게 나눌지는 확장과 다른 질문이다. [백엔드 아키텍처 패턴 고르기](/posts/architecture-patterns-overview)가 모놀리스, 마이크로서비스, 헥사고날, CQRS를 배포·코드·데이터 세 축으로 나눠 놓았다.

이 층에서 만들 것은 코드보다 문서다. 5층 서비스가 트래픽 100배를 받는다고 가정하고, 어디가 먼저 터질지(커넥션 수, 쓰기 처리량, 캐시 히트율) 숫자로 추정한 설계 문서를 쓴다. 그 다음 실제로 앱 두 대와 복제본 하나를 Compose로 띄우고, 복제본을 일부러 늦추거나 앱 하나를 죽여서 문서에 적은 대로 버티는지 확인한다.

다 됐다고 볼 수 있을 때는 이렇다. "서버를 늘렸는데 왜 안 빨라지나"에 DB 커넥션, 락, 공유 자원으로 답한다. 네트워크가 끊겼을 때 일관성과 가용성 중 무엇을 포기하는 설계인지 내 서비스 기준으로 말한다. 설계 면접에서 요구 사항을 묻고, 트래픽을 추정하고, 한 대짜리 그림에서 시작해 병목이 나오는 순서대로 부품을 붙인다.

## 위층에서 막히면 아래층을 본다

공부는 아래에서 위로 하지만 장애는 위에서 시작해 아래로 내려간다. 증상은 6층처럼 보여도 원인은 2층에 있는 일이 많다. 첫 장면의 제보를 포함해 자주 만나는 증상을 층으로 거꾸로 짚어 표로 모았다.

## 여섯 층을 다 지나고 나면

여섯 층은 기술 이름의 목록이 아니라 한 서비스가 자라는 순서다. 요청을 읽고, 받는 프로그램을 쓰고, 데이터를 밖에 두고, 남에게 내놓을 만큼 막고 확인하고, 요청 밖의 일과 배포와 관측을 붙이고, 한 대로 안 될 때 나눈다. 층마다 만든 것이 다음 층의 재료라서, 같은 주문 서비스 하나를 끝까지 키워 가며 공부하는 게 가장 덜 흩어진다. 인프라 쪽으로 더 가고 싶다면 [쿠버네티스 로드맵](/posts/k8s-learning-roadmap)과 [DevOps 네트워킹 학습 순서](/posts/devops-networking-roadmap)가 이 글의 5층과 6층 옆에 이어진다.

## 면접에서 나올 만한 질문

### HTTP는 상태가 없는데 로그인은 어떻게 유지되나

요청마다 "나는 누구다"라는 증표를 함께 보내서 유지한다. 서버가 세션을 저장하고 쿠키로 세션 ID만 주는 방식과, 서버가 서명한 토큰(JWT)을 클라이언트가 들고 다니는 방식이 있다. 어느 쪽이든 HTTP 자체는 여전히 상태가 없고, 상태는 세션 저장소나 토큰 안에 있다. 서버를 여러 대로 늘리면 세션은 Redis 같은 공용 저장소로 빼야 한다.

### Node.js는 스레드가 하나인데 어떻게 동시에 많은 요청을 받나

자바스크립트를 실행하는 스레드가 하나일 뿐, 기다리는 일은 그 스레드가 하지 않는다. 소켓 입출력은 운영체제의 이벤트 알림(epoll 등)으로, 파일·`dns.lookup`·해시 같은 일은 libuv 스레드 풀로 넘기고 루프는 다음 요청을 받는다. 그래서 입출력이 많은 API에는 잘 맞고, 한 요청이 CPU를 오래 쓰면 모든 요청이 같이 멈춘다. CPU 작업은 worker_threads로 옮기고, 코어를 다 쓰려면 프로세스나 컨테이너 복제본을 늘린다.

### 인덱스를 걸면 왜 빨라지고, 무엇을 대가로 내나

B-tree 인덱스는 정렬된 키로 원하는 행 위치를 몇 단계 만에 찾게 해서 테이블 전체를 읽지 않게 한다. 대신 쓰기마다 인덱스도 고쳐야 하니 INSERT·UPDATE가 느려지고 저장 공간이 늘어난다. 인덱스가 있어도 열에 함수를 씌우거나 결과가 너무 많으면 플래너가 Seq Scan을 고른다. 그래서 인덱스는 감으로 걸지 않고 `EXPLAIN ANALYZE`로 전후를 확인한다.

### 캐시를 넣으면 어떤 문제가 새로 생기나

DB와 캐시 두 곳에 같은 데이터가 생기니 둘이 어긋날 수 있다. 쓰기 뒤 캐시를 지우는 순서가 경쟁하면 옛 값이 남고, 인기 키가 만료되는 순간 요청이 한꺼번에 DB로 몰리는 스탬피드가 난다. 그래서 TTL을 두고, 쓰기 뒤에는 갱신보다 삭제를 택하고, 만료 시각에 지터를 섞는다. 캐시가 죽어도 DB가 버틸 수 있는지도 미리 재 둔다.

### 세션과 JWT 중 무엇을 고르나

강제 로그아웃과 즉시 권한 회수가 중요하면 세션이 단순하다. 서버에서 세션을 지우면 끝나기 때문이다. JWT는 검증에 저장소 조회가 필요 없어 여러 서비스가 각자 확인하기 좋지만, 발급한 토큰을 만료 전에 무르기 어렵다. 그래서 JWT를 쓸 때는 액세스 토큰 수명을 짧게 두고 리프레시 토큰을 서버에서 관리하는 식으로 세션의 장점을 일부 되찾는다.

### 단위 테스트만 많으면 충분하지 않나

부족하다. 단위 테스트는 목으로 바깥을 대신하니 SQL 제약, 트랜잭션, 직렬화처럼 경계에서 나는 버그를 못 본다. 목이 진짜 DB와 다르게 동작하면 테스트는 초록인데 운영에서 터진다. 그래서 순수 로직은 단위 테스트로 빠르게 덮고, DB와 HTTP 경계는 실제 PostgreSQL을 붙인 통합 테스트로 몇 개라도 끝까지 돌린다.

### 메시지 큐를 쓰면 중복은 어떻게 막나

대부분의 큐는 최소 한 번 전달이라 중복을 막지 못한다. 처리 후 ack 전에 소비자가 죽으면 메시지가 다시 온다. 그래서 받는 쪽이 멱등해야 한다. 메시지 ID나 주문 ID를 처리 기록에 남기고 결과와 같은 트랜잭션으로 커밋하면, 다시 온 메시지는 기록을 보고 건너뛴다. 외부 메일 발송처럼 트랜잭션에 묶을 수 없는 일은 상대 API의 멱등성 키를 쓰거나 남는 틈을 받아들인다.

### 서버를 두 대로 늘리면 무엇부터 깨지나

프로세스 안에 둔 상태가 먼저 깨진다. 메모리 세션, 로컬 캐시, 서버 한 대를 전제로 한 크론 작업이 대표적이다. 다음은 DB다. 앱은 늘렸는데 DB 커넥션이 모자라거나, 읽기를 복제본으로 나눴더니 방금 쓴 데이터가 안 보인다. 그래서 앱은 상태를 밖으로 빼서 무상태로 만들고, 쓴 직후 읽기는 프라이머리로 보내는 규칙을 정한 뒤에 늘린다.
