배포하고 나서 첫 화면이 1초 넘게 하얗다는 제보가 왔다. Network 탭을 열어 보니 HTML은 30ms 만에 다 왔다. 문서는 이미 브라우저 손에 있는데 아무것도 그려지지 않는다. 줄을 따라 내려가 보면 `<head>`에 새로 붙은 스타일시트 하나가 1초 걸렸다. 그 파일이 오기 전까지 브라우저는 일부러 그리지 않은 것이다.

이런 일이 왜 생기는지 알려면 브라우저가 바이트를 픽셀로 바꾸는 순서를 하나씩 따라가야 한다. 이 글은 그 순서를 크로미움 141(Playwright, headless, GPU 없음)과 일부러 응답을 늦게 주는 작은 Node 서버로 직접 재 가며 본다. 숫자는 이 컨테이너 기준이라 절댓값보다 차이를 보면 된다.

큰 흐름(DOM, CSSOM, 렌더 트리, 리플로와 리페인트)은 [google.com을 치면 일어나는 일](/posts/what-happens-google-com)에 짧게 정리되어 있다. 여기서는 그 단계들이 실제로 어느 스레드에서, 무엇을 기다리며, 어떤 순서로 도는지를 판다. 이 순서에서 나오는 최적화는 다음 글 [렌더링 성능 최적화](/posts/rendering-performance-optimization)에서 다룬다.

## HTML은 받는 대로 읽는다

파서는 HTML이 다 올 때까지 기다리지 않는다. 바이트가 오는 대로 문자로 풀고(디코딩), 태그 단위로 자르고(토큰화), 노드를 만들어 DOM 트리에 붙인다. 위 트레이스에서 `ParseHTML`이 3회로 나온 것도 파서가 한 번에 다 읽지 않고 조각 단위로 나눠 읽었기 때문이다.

받는 대로 읽는다는 건 받는 대로 그릴 수도 있다는 뜻이다. 서버가 HTML 앞부분을 먼저 보내고, 1초 뒤에 나머지를 보내게 만들어 재 봤다.

```js
// 앞부분을 먼저 흘려보내고 1초 뒤에 문서를 닫는다
res.write(`<!doctype html><html><head><title>s</title></head><body><h1>상품 목록</h1><p>...</p>`);
setTimeout(() => res.end(`<p>뒷부분</p><script>performance.mark("tail-parsed")</script></body></html>`), 1000);
```

```text
stream          {"FCP":28,"DCL":1006,"load":1007,"marks":{"tail-parsed":1004},"res":[]}
```

첫 화면(FCP)은 28ms에 그려졌고, 뒷부분이 파싱된 건 1004ms다. 문서가 다 오기 전에 이미 그렸다. 서버가 응답을 끝까지 모았다가 한 번에 보내는지, 앞부분부터 흘려보내는지에 따라 첫 화면이 이만큼 달라진다. React의 스트리밍 SSR이 기대는 것도 이 성질이다([스트리밍 SSR과 Suspense](/posts/streaming-ssr-suspense)).

## 평범한 script를 만나면 파서가 선다

그런데 파서가 늘 앞으로만 가지는 않는다. `async`도 `defer`도 없는 `<script>`를 만나면 파싱을 멈춘다. 그 스크립트가 `document.write()`로 바로 뒤에 HTML을 끼워 넣을 수 있으니, 스크립트를 실행해 보기 전에는 뒤를 어떻게 읽어야 할지 모른다. 그래서 이런 스크립트를 파서 차단 스크립트라고 부른다.

`inline-end-of-body`는 `body` 맨 끝의 인라인 스크립트가 찍은 시각이라, 파서가 문서 끝에 닿은 때를 뜻한다. 평범한 스크립트는 파서를 1초 세웠고 첫 화면도 1032ms로 밀렸다. `defer`와 `module`은 파서가 21ms 만에 끝까지 읽고 36~40ms에 그렸지만, `DOMContentLoaded`는 스크립트가 실행된 뒤인 1025ms까지 미뤄졌다. `async`만 `DOMContentLoaded`까지 27ms에 끝났다. 대신 `load`는 기다린다.

이 차이는 실무에서 바로 문제가 된다. `DOMContentLoaded`에 초기화를 걸어 둔 코드가 있다면 `defer` 스크립트가 늦을 때 같이 늦어진다. 반대로 `async`로 바꾸면 그 스크립트가 DOM이 다 만들어지기 전에 돌 수 있다. 서로 의존하는 스크립트 두 개에 `async`를 붙이면 도착 순서에 따라 가끔만 터지는 버그가 생긴다. 앱 코드는 `defer`나 모듈로, 다른 코드와 순서가 상관없는 독립 스크립트(분석 도구 같은 것)만 `async`로 두는 편이 안전하다.

## 파서가 멈춘 동안 앞을 훑는 프리로드 스캐너

앞의 그림대로라면 파서가 스크립트 앞에서 멈춘 1초 동안 아래쪽 이미지와 CSS는 요청조차 못 해야 한다. 실제로는 그렇지 않다. 크롬 계열을 포함한 주요 브라우저에는 프리로드 스캐너(preload scanner)가 있다. 메인 파서가 멈춘 동안 아직 읽지 않은 HTML을 가볍게 훑어서, 받아야 할 주소(`img`, `link`, `script`의 `src`·`href`)가 보이면 요청을 먼저 보낸다. DOM은 만들지 않고 주소만 찾는다.

1초 걸리는 스크립트로 파서를 세워 두고, 그 아래에 이미지, 스타일시트, 그리고 자바스크립트로 만드는 이미지를 하나씩 두었다. 아래 그림에서 다음을 누르면 요청이 나가는 순서가 보인다. 그림 속 시각은 실제로 잰 값이다.

가장 큰 그림(LCP 이미지)이 이 중 하나라면 스캐너의 도움을 못 받는다. HTML에 `<img>`로 적거나 `<link rel="preload">`로 주소를 미리 알려 준다. 이 처방의 자세한 내용은 [Core Web Vitals](/posts/core-web-vitals)의 히어로 이미지 부분과 [리소스 힌트](/posts/resource-hints-loading)에 있다.

## CSS가 올 때까지 일부러 그리지 않는다

이제 처음 장면으로 돌아간다. `<head>`의 스타일시트는 파서를 막지는 않지만 첫 렌더링을 막는다(render-blocking). CSS 없이 먼저 그리면 스타일 없는 화면이 번쩍 보였다가 다시 바뀐다. 브라우저는 그 깜빡임보다 잠깐 하얀 화면을 고른다.

## 스타일 계산과 레이아웃은 따로 센다

DOM과 CSS 규칙이 준비되면 스타일 계산(Recalculate Style)이 요소마다 어떤 규칙이 걸리는지 정하고, 상속과 단위 변환을 거쳐 계산된 스타일(computed style)을 만든다. `getComputedStyle()`로 읽는 그 값이다. 그다음 레이아웃이 그 스타일로 상자의 위치와 크기를 정한다.

레이아웃이 다루는 트리는 DOM과 모양이 다르다. `display: none`인 요소와 `<head>`는 빠지고, `::before`처럼 DOM에 없는 의사 요소는 들어간다. 줄바꿈된 글자는 줄마다 조각이 생긴다. 그래서 DOM 노드 수와 레이아웃이 하는 일의 양이 정확히 비례하지는 않는다.

CDP의 `Performance.getMetrics`는 페이지가 지금까지 스타일 계산과 레이아웃을 몇 번, 얼마 동안 했는지 누적값을 준다. 앞의 카드 50개 페이지를 연 직후에 읽었다.

```js
await cdp.send("Performance.enable");
await page.goto("http://127.0.0.1:18600/p/pipeline");
const { metrics } = await cdp.send("Performance.getMetrics");
```

```text
Nodes=274 LayoutCount=1 RecalcStyleCount=1 LayoutDuration=28.0ms RecalcStyleDuration=0.5ms ScriptDuration=0.4ms TaskDuration=45.6ms
```

페이지를 여는 동안 스타일 계산과 레이아웃이 한 번씩만 일어났다. 파서가 노드를 붙일 때마다 레이아웃을 하지 않고, 그릴 때가 되면 모아서 한다는 뜻이다. 이 숫자를 함수 실행 전후로 비교하면 어떤 코드가 레이아웃을 몇 번 부르는지 셀 수 있다. 크기를 읽는 코드가 레이아웃을 그 자리에서 강제로 부르는 경우는 [DOM 기초](/posts/dom-basics)에서 이 지표로 쟀다.

## 페인트는 아직 그림이 아니다

이름 때문에 오해가 많은 단계다. 크로미움의 `Paint`는 픽셀을 칠하지 않는다. "이 좌표에 이 색 사각형, 그 위에 이 글자"처럼 그리기 명령을 순서대로 적은 목록(페인트 기록, display list)을 만든다. 앞의 트레이스에서 `Paint`가 합쳐 0.48ms밖에 안 걸린 이유다. 실제로 픽셀을 채우는 건 래스터(rasterize) 단계이고, 메인 스레드가 아닌 래스터 워커에서 `RasterTask` 9회로 나뉘어 돌았다.

페인트와 래스터 사이에는 층(레이어) 나누기가 있다. 브라우저는 페이지를 몇 장의 층으로 나눠 따로 래스터하고, 마지막에 합성 스레드가 겹친다. 어떤 요소가 따로 층이 되었고 왜 그런지는 CDP의 `LayerTree`로 볼 수 있다. 같은 페이지에서 읽었다.

```js

cdp.on("LayerTree.layerTreeDidChange", (e) => { if (e.layers) layers = e.layers; });
// 페이지를 연 뒤 층마다 이유를 묻는다
const { compositingReasonIds } = await cdp.send("LayerTree.compositingReasons", { layerId });
```

 390x800   drawsContent=false paintCount=0 reasons=Viewport
```

세로로 6730px인 문서 전체가 스크롤되는 층 하나(`RootScroller`)로 그려졌고, `will-change: transform`을 준 25×26 배지가 따로 층이 됐다. 스크롤할 때 브라우저가 다시 그리지 않고 이 큰 층을 옮기기만 하는 것도, 배지가 스크롤과 상관없이 제자리에 있는 것도 층이 나뉜 덕분이다.

6730px짜리 층을 한 번에 다 래스터하지는 않는다. 층을 타일로 잘라 화면에 보이는 곳과 그 근처부터 채운다. 아주 빠르게 스크롤했을 때 잠깐 빈 칸이 보이는 체커보딩(checkerboarding)은 래스터가 스크롤을 못 따라간 순간이다. 층이 늘면 메모리가 얼마나 드는지는 [애니메이션 성능](/posts/animation-performance)의 `will-change` 실험에 있다.

## 프레임 하나 안의 순서

첫 화면이 그려진 뒤에도 이 과정은 화면이 바뀔 때마다 반복된다. 차이는 매번 처음부터 하지 않고 바뀐 부분만 다시 한다는 것이다. 언제 다시 하는지는 이벤트 루프가 정한다. 태스크 하나가 끝나고 마이크로태스크를 다 비운 뒤, 그릴 때가 됐으면 렌더링 단계에 들어간다. 이 구조 자체는 [이벤트 루프](/posts/event-loop)에서 다뤘다. 여기서는 그 렌더링 단계 안을 트레이스로 들여다본다.

`setTimeout`으로 배경색을 한 번 바꾸고, `requestAnimationFrame`으로 매 프레임 폭을 5px씩 늘리는 페이지에서 메인 스레드 이벤트를 순서대로 찍었다.

let n = 0;
const tick = () => {
  box.style.width = 100 + n * 5 + "px"; // 첫 번째 tick은 100px 그대로다
  if (++n < 6) requestAnimationFrame(tick);
};
requestAnimationFrame(tick);
```

## React 코드에서 이 순서를 만나는 곳

React를 써도 브라우저가 그리는 순서는 그대로다. React는 DOM을 바꾸는 쪽에 있을 뿐이다.

클라이언트 렌더링 앱의 HTML은 빈 `<div id="root">`와 모듈 스크립트 하나다. 모듈은 `defer`처럼 동작하니 파서를 막지 않고 첫 화면도 빨리 "그린다". 문제는 그릴 내용이 없다는 것이다. 사용자가 보는 첫 화면은 번들을 받고 실행해서 React가 DOM을 만든 뒤에야 나온다. 그 사이 이미지 주소는 모두 자바스크립트 안에 있으니 프리로드 스캐너도 도와줄 수 없다. 이 과정은 [CSR](/posts/rendering-csr-spa)에서 실제로 쟀다.

훅 두 개의 차이도 이 순서로 설명된다. `useLayoutEffect`는 React가 DOM을 바꾼 직후, 브라우저가 스타일 계산과 페인트를 하기 전에 동기로 돈다. 여기서 크기를 재고 위치를 고치면 사용자는 고친 결과만 본다. 대신 이 안에서 `getBoundingClientRect()`를 읽으면 그 자리에서 레이아웃을 강제로 하게 되고, 이 훅이 오래 걸리면 그만큼 프레임이 늦는다. `useEffect`는 보통 브라우저가 그린 뒤에 돈다. 데이터 요청이나 구독처럼 화면과 상관없는 일은 여기에 둔다.

스타일도 마찬가지다. 런타임 CSS-in-JS는 렌더링 중에 `<style>` 태그를 끼워 넣는다. 새 규칙이 들어갈 때마다 브라우저는 스타일을 다시 계산해야 한다. 정적으로 뽑은 CSS 파일은 `<head>`에서 렌더링을 막는 대신 한 번에 적용된다. 둘의 비용 차이는 [CSS 성능](/posts/css-performance)에서 다룬다. React 19부터는 `<link rel="stylesheet" precedence="...">`를 컴포넌트 안에 써도 `<head>`로 끌어올리고, 스타일시트가 올 때까지 그 부분을 보여 주지 않는 기능이 들어갔다. 깜빡임을 막는 방향은 브라우저의 렌더 차단과 같다.

## 하얀 화면이 길 때 어디부터 보나

처음 장면 같은 제보가 오면 이 순서로 좁힌다.

먼저 HTML이 늦게 왔는지 본다. Network 탭에서 문서 요청의 Waiting(TTFB)이 길면 서버나 네트워크 문제이고, 이 글의 범위 밖이다. HTML은 빨리 왔는데 첫 화면이 늦으면 브라우저 안의 문제다.

Performance 패널에서 페이지를 다시 불러 기록한다. 맨 위 Network 줄에서 첫 화면(FCP 표시) 전에 끝나는 CSS와 JS를 찾는다. 최근 크롬은 요청을 누르면 렌더링을 막았는지(Render blocking)를 함께 보여 준다. 자동으로 모으려면 앞의 `renderBlockingStatus`를 쓴다. 막는 것이 CSS라면 그 파일이 왜 큰지, 첫 화면에 다 필요한지 본다. 동기 스크립트라면 `defer`나 `async`로 바꿀 수 있는지 본다. 태그 관리자가 넣는 동기 스크립트가 흔한 범인이다.

막는 리소스가 없는데도 늦다면 메인 스레드를 본다. 파싱이 끝난 뒤 긴 `Evaluate Script`나 거대한 `Layout`이 첫 페인트 앞을 덮고 있을 수 있다. 첫 레이아웃이 수백 ms라면 DOM이 너무 크거나 글꼴 처리가 무거운 경우다. 그다음은 LCP다. 첫 화면은 빨리 나왔는데 주인공 이미지가 늦게 뜬다면 그 이미지를 스캐너가 볼 수 있는지부터 확인한다.

고친 뒤에는 같은 조건으로 FCP와 `renderBlockingStatus`를 다시 읽어서 막는 리소스가 사라졌는지 숫자로 확인한다. 개발 서버가 아니라 프로덕션 빌드로 잰다. 개발 모드는 CSS를 자바스크립트로 주입하는 등 구성이 달라서 결과가 엉뚱하게 나온다.

## 다시 하얀 화면으로

브라우저는 HTML을 받는 대로 읽고, 평범한 스크립트 앞에서 서고, CSS가 올 때까지 일부러 그리지 않는다. 그 사이 프리로드 스캐너가 HTML에 적힌 주소를 먼저 받아 둔다. 그리고 그릴 때는 스타일 계산, 레이아웃, 페인트 기록까지를 메인 스레드가, 픽셀 채우기와 층 겹치기를 다른 스레드가 맡는다. 화면이 늦으면 이 중 어느 단계가 무엇을 기다렸는지 트레이스로 찾으면 된다. 이 순서를 이용해 프레임마다 하는 일을 줄이는 방법은 [렌더링 성능 최적화](/posts/rendering-performance-optimization)에서 이어 간다.

## 면접에서 나올 만한 질문

### 브라우저가 HTML을 받아 화면에 그리기까지의 과정을 설명해 주세요.

HTML을 받는 대로 토큰화해 DOM을 만들고, CSS로 스타일 규칙을 만든 뒤 요소마다 계산된 스타일을 정한다. 레이아웃이 위치와 크기를 정하고, 페인트가 그리기 명령 목록을 만들고, 층으로 나눠 합성 스레드에 넘긴다. 래스터 워커가 타일 단위로 픽셀을 채우면 합성 스레드가 층을 겹쳐 프레임을 낸다. 크롬 계열 기준으로 페인트 기록까지는 메인 스레드, 래스터와 합성은 다른 스레드에서 돈다.

### CSS는 왜 렌더링을 막고, 자바스크립트는 왜 파싱을 막나요?

CSS 없이 먼저 그리면 스타일 없는 화면이 번쩍 보였다가 바뀌니, 브라우저는 `<head>`의 스타일시트가 올 때까지 첫 렌더링을 미룬다. 평범한 스크립트는 `document.write()`로 뒤에 올 HTML을 바꿀 수 있어서 실행 전에는 파서가 앞으로 갈 수 없다. 여기에 더해 스크립트는 스타일 값을 읽을 수 있으니 앞선 CSS가 올 때까지 실행도 기다린다. 1초짜리 CSS 뒤의 인라인 스크립트가 1010ms에 실행된 것이 그 결과다.

### async, defer, type="module"은 어떻게 다른가요?

셋 다 받는 동안 파서를 막지 않는다. `defer`는 파싱이 끝난 뒤 문서 순서대로 실행하고 그다음 `DOMContentLoaded`가 뜬다. `async`는 다 받는 즉시 실행해서 순서를 보장하지 않고 `DOMContentLoaded`를 기다리게 하지도 않는다. 모듈 스크립트는 기본이 `defer`처럼 동작하고 `async`를 붙이면 받는 대로 실행한다. 측정해 보면 `defer`와 모듈은 FCP 36~40ms에 DCL 1025ms, `async`는 DCL 27ms였다.

### 프리로드 스캐너는 무엇이고, 무엇을 놓치나요?

메인 파서가 스크립트 앞에서 멈춘 동안 아직 읽지 않은 HTML을 훑어 `img`, `link`, `script`의 주소를 먼저 요청하는 보조 파서다. 1초 동안 파서가 멈춰 있어도 아래쪽 이미지와 CSS가 7ms에 요청된 것이 그 덕분이다. HTML 텍스트만 보기 때문에 자바스크립트가 만드는 요소, CSS 안의 `background-image`나 `@import`, `data-src` 방식의 지연 로딩은 놓친다. LCP 이미지가 여기 해당하면 HTML에 직접 쓰거나 `preload`로 알려 준다.

### 페인트와 래스터는 어떻게 다른가요?

크로미움의 페인트는 픽셀을 칠하지 않고 무엇을 어떤 순서로 그릴지 적은 명령 목록을 만든다. 래스터가 그 목록을 실제 픽셀로 바꾸며, 층을 타일로 잘라 래스터 워커 스레드에서 화면 근처부터 처리한다. 그래서 트레이스에서 메인 스레드의 `Paint`는 짧고 `RasterTask`는 다른 스레드에 여러 번 찍힌다. 빠르게 스크롤할 때 잠깐 보이는 빈 칸은 래스터가 따라가지 못한 순간이다.

### 레이어는 왜 나누고, 어떤 요소가 따로 층이 되나요?

층을 나눠 두면 스크롤이나 `transform`, `opacity` 변화 때 다시 그리지 않고 겹치는 위치만 바꿀 수 있다. 문서 전체를 담는 스크롤 층, `will-change: transform`을 준 요소, 3D 변환이나 비디오처럼 브라우저가 정한 이유가 있는 요소가 따로 층이 된다. CDP의 `LayerTree.compositingReasons`나 개발자 도구 Layers 패널에서 이유를 확인할 수 있다. 층마다 메모리를 쓰니 많이 만든다고 좋은 건 아니다.

### requestAnimationFrame 콜백은 프레임의 어디에서 실행되나요?

태스크와 마이크로태스크가 끝나고 브라우저가 그릴 때가 됐다고 판단하면, 스타일 계산 바로 앞에서 rAF 콜백을 실행한다. 트레이스에서도 `FireAnimationFrame` 다음에 `UpdateLayoutTree`, `Layout`, `Paint`, `Commit`이 이어졌다. 그래서 화면을 바꾸는 코드를 rAF에 두면 그 변경이 바로 다음 렌더링에 들어간다. 콜백 안에서 크기를 읽고 쓰기를 번갈아 하면 레이아웃이 여러 번 강제로 일어나니 읽기를 먼저 모은다.

### 첫 화면이 하얗게 오래 보이면 무엇부터 확인하나요?

HTML 응답이 늦은지(TTFB)부터 보고, 빨리 왔다면 첫 페인트 전에 끝나는 렌더 차단 리소스를 찾는다. Performance 패널의 Network 줄이나 Resource Timing의 `renderBlockingStatus`로 `<head>`의 CSS와 동기 스크립트를 골라낸다. 막는 리소스가 없으면 첫 페인트 앞을 덮는 긴 스크립트 실행이나 거대한 첫 레이아웃을 본다. 고친 뒤에는 프로덕션 빌드에서 같은 조건으로 다시 잰다.
