쇼핑몰 첫 화면에 "오늘의 인기 상품" 목록이 있다고 하자. 주문 테이블과 상품 테이블을 조인하고, 오늘 판매량으로 묶고, 정렬해서 상위 20개를 자른다. 이 쿼리가 80ms 걸린다. 한 번이면 괜찮은데, 첫 화면이라 초당 수백 번 같은 쿼리가 돈다. 결과는 몇 분 동안 바뀌지도 않는다.

그래서 결과를 Redis에 넣어 두고 읽기 시작한다. 같은 목록을 Redis에서 꺼내면 1ms가 안 걸린다. DB도 자주 읽는 데이터는 메모리에 올려 두는데, 왜 이만큼 차이가 날까. 그리고 이렇게 빠른 Redis가 명령 하나 때문에 통째로 멈추기도 하는데, 그건 또 왜일까. 두 질문의 답은 같은 곳에 있다. 이 글은 그 구조를 먼저 보고, Ubuntu에 설치해서 자료구조를 하나씩 써 본다.

예제는 처음부터 끝까지 같은 작은 쇼핑몰을 쓴다. 회원은 42번(kim), 43번(lee), 44번(park)이고, 상품은 1001번 무선 이어폰(39,000원), 1002번 충전 케이스(15,000원), 1003번 이어팁(5,000원)이다.

## 80ms와 1ms 사이에 있는 것

DB가 인기 상품 쿼리 하나에 하는 일을 늘어놓으면 이렇다. SQL을 파싱하고, 실행 계획을 세우고, 인덱스를 따라 페이지를 찾고, 필요하면 디스크에서 읽고, 행마다 지금 트랜잭션에서 보여도 되는 버전인지(MVCC) 확인하고, 조인하고, 묶고, 정렬한다. 데이터가 버퍼 풀(DB가 쓰는 메모리 캐시)에 다 올라와 있어도 계산 자체가 많다.

Redis에 넣어 둔 인기 상품 목록은 이미 계산이 끝난 값이다. Redis가 하는 일은 키를 해시 테이블에서 찾아 값을 돌려주는 것뿐이다. 키가 몇 개든 찾는 시간은 거의 일정하다(O(1)). 그리고 모든 데이터가 처음부터 메모리에 있다. 디스크를 읽을 일이 아예 없다.

저장 장치의 속도 차이도 크다. 메모리에서 값을 하나 읽는 데는 대략 100ns 단위가 걸리고, NVMe SSD에서 임의 위치를 읽으면 수십~100µs, 하드디스크는 수 ms가 걸린다. 장비마다 다르지만 메모리와 SSD 사이에만 수백 배 차이가 있다.

그래서 Redis 명령 하나의 실행 시간은 보통 몇 µs다. 응용 서버가 체감하는 1ms 미만의 시간은 대부분 네트워크 왕복이다. 같은 데이터센터 안이라면 왕복이 0.1~0.5ms 정도라, 여기서 응답 시간이 거의 정해진다. Redis 서버에서 직접 재 보면 이렇다.

```bash
# 1초에 수십 번 PING을 보내 왕복 시간을 잰다 (Ctrl+C로 멈춘다)
redis-cli --latency
```

```text
min: 0, max: 1, avg: 0.28 (97 samples)
```

단위는 ms다. 루프백(같은 서버) 연결이라 평균 0.28ms가 나왔다. 응용 서버가 다른 장비에 있으면 그 사이 네트워크 시간이 더해진다.

데이터가 메모리에 있고 명령이 단순하다는 것만으로는 설명이 다 안 된다. 나머지 절반은 명령을 실행하는 방식에 있다.

## 명령은 한 줄로 서서 하나씩 실행된다

Redis는 명령을 메인 스레드 하나에서 실행한다. 연결이 1만 개여도 명령을 실제로 처리하는 건 한 스레드다. 처음 들으면 느릴 것 같은데, 오히려 이게 빠른 이유다.

스레드 하나가 연결 1만 개를 다루는 방법이 I/O 다중화(multiplexing)다. 리눅스에서는 epoll을 쓴다. 메인 스레드는 소켓 1만 개를 epoll에 등록해 두고 `epoll_wait`로 "데이터가 도착한 소켓이 생기면 깨워 달라"고 기다린다. 깨어나면 준비된 소켓만 골라서 명령을 읽고, 실행하고, 응답을 쓰고, 다시 기다린다. 이 반복이 이벤트 루프다. 어떤 다중화 API를 쓰는지는 서버에서 바로 확인할 수 있다.

```bash
# 이벤트 루프가 쓰는 I/O 다중화 API (리눅스는 epoll, macOS는 kqueue)
redis-cli INFO server | grep multiplexing_api
```

```text
multiplexing_api:epoll
```

스레드가 하나라서 얻는 게 많다. 여러 스레드가 같은 자료구조를 건드리지 않으니 락이 필요 없다. 락을 잡고 기다리는 시간도, 스레드를 바꾸는 문맥 전환(context switch)도 없다. 명령 하나는 시작하면 끝까지 혼자 실행되므로, `INCR` 같은 명령은 따로 신경 쓰지 않아도 원자적이다. 두 클라이언트가 동시에 `INCR`를 보내도 하나씩 실행되니 증가분이 사라지지 않는다.

명령이 대부분 µs 단위로 끝나기 때문에 이 방식이 통한다. 병목은 CPU가 아니라 네트워크와 메모리 쪽이다. 단일 인스턴스가 초당 10만 건 넘는 단순 명령을 처리하는 것도 흔하다.

## 느린 명령 하나가 모두를 세운다

그림의 C가 바로 대가다. 명령이 한 줄로 서 있으니, 앞에서 하나가 오래 걸리면 뒤의 모든 클라이언트가 기다린다. Redis가 느려졌다는 장애의 상당수는 서버가 약해서가 아니라 이런 명령 하나 때문이다.

자주 문제 되는 명령은 이렇다.

- `KEYS *`: 모든 키를 훑는다. 키 수에 비례해서 느려진다.
- 거대한 키 지우기: 필드가 100만 개인 해시를 `DEL`하면 메모리를 하나하나 돌려주느라 오래 걸린다.
- 큰 컬렉션을 통째로 읽기: 원소가 수십만 개인 셋에 `SMEMBERS`, 해시에 `HGETALL`, 리스트에 `LRANGE 0 -1`.
- 오래 도는 Lua 스크립트: 스크립트는 원자적으로 실행되므로, 스크립트 안의 반복문이 길면 그동안 아무것도 못 한다.

직접 재 보면 감이 온다. 숫자 값이 든 키 100만 개를 넣고 `KEYS *`를 한 번, 필드 100만 개짜리 해시에 `DEL`을 한 번 실행한 뒤 느린 명령 기록(SLOWLOG)을 봤다.

```bash
# 10ms(10000µs)보다 오래 걸린 명령을 기록한다 (기본값도 10000)
redis-cli CONFIG GET slowlog-log-slower-than

# 최근에 기록된 느린 명령 2개
redis-cli SLOWLOG GET 2
```

```text

2) "10000"
```

항목마다 기록 번호, 실행 시각(유닉스 초), 실행 시간(µs), 명령과 인자, 클라이언트 주소, 클라이언트 이름 순이다. 세 번째 줄을 보면 된다. `KEYS *`가 514,316µs, 해시 하나를 지우는 `DEL`이 503,116µs 걸렸다. 둘 다 0.5초 동안 서버 전체가 멈췄다는 뜻이다. 초당 1만 건을 받는 서버라면 그 사이 5천 개의 요청이 줄을 선다.

대안은 정해져 있다. 키를 훑을 때는 뒤에서 볼 `SCAN`을 쓴다. 큰 키는 `DEL` 대신 `UNLINK`로 지운다. `UNLINK`는 키를 키 공간에서 바로 떼어 내고, 메모리를 돌려주는 일은 백그라운드 스레드에 맡긴다. 같은 해시를 `UNLINK`로 지우니 명령 자체는 몇 ms 만에 끝났다. 큰 컬렉션은 `HSCAN`, `SSCAN`, `ZSCAN`으로 나눠 읽는다. 처음부터 키 하나에 원소가 수십만 개 쌓이지 않게 나누는 게 더 낫다(예: 날짜별 키).

Lua 스크립트가 오래 돌면 Redis는 `busy-reply-threshold`(기본 5000ms, 예전 이름 `lua-time-limit`)가 지난 뒤부터 다른 클라이언트에 `BUSY` 에러를 돌려준다. 스크립트가 아직 아무것도 쓰지 않았다면 `SCRIPT KILL`로 멈출 수 있고, 이미 썼다면 원자성을 깨지 않으려고 `SHUTDOWN NOSAVE`밖에 방법이 없다. 그러니 스크립트에는 반복 횟수가 정해진 짧은 작업만 넣는다.

<Callout kind="warning" title="운영 서버에서 KEYS를 치지 않는다">
키가 많은 운영 Redis에서 `KEYS *`나 `KEYS user:*`를 실행하면 그 시간만큼 모든 요청이 멈춘다. 디버깅하다 무심코 치는 경우가 많아서, ACL로 응용 계정에서 `KEYS`와 `FLUSHALL` 같은 명령을 아예 막아 두는 편이 안전하다(아래 보안 절 참고). 이미 실행했다면 끝날 때까지 기다리는 수밖에 없다.
</Callout>

## Redis 6의 I/O 스레드는 무엇을 나눠 맡나

Redis 6.0부터 I/O 스레드가 생겼다. 이걸 보고 "이제 Redis도 멀티 스레드"라고 하는데, 반만 맞는 말이다. I/O 스레드는 소켓에서 데이터를 읽고 응답을 쓰는 네트워크 일만 나눠 맡는다. 명령 실행은 여전히 메인 스레드 하나가 한다. 그래서 `KEYS *` 문제는 I/O 스레드를 켜도 그대로다.

왜 네트워크만 나눴을까. 명령 실행은 몇 µs인데, 응답을 소켓에 쓰는 `write` 시스템 콜과 버퍼 복사가 오히려 CPU를 더 먹는 경우가 많다. 이 부분만 여러 코어에 나누면 실행 모델(한 번에 하나, 락 없음)은 그대로 두고 처리량을 올릴 수 있다.

기본값은 꺼져 있다(`io-threads 1`). `redis.conf` 주석은 코어가 4개 이상일 때만 켜고, 4코어면 2~3개, 8코어면 6개 정도를 권하며, 실제로 CPU를 많이 쓰는 성능 문제가 있을 때만 쓰라고 한다. 쓰기만 스레드로 나누는 게 기본이고, 읽기와 프로토콜 해석까지 나누려면 `io-threads-do-reads yes`를 따로 켠다. 이 값들은 실행 중에 `CONFIG SET`으로 못 바꾸고 재시작해야 한다.

```bash
# 현재 I/O 스레드 수 (1이면 메인 스레드만 쓴다)
redis-cli CONFIG GET io-threads
```

```text
1) "io-threads"
2) "1"
```

I/O 스레드 말고도 Redis 프로세스에는 원래 백그라운드 스레드가 몇 개 있다. 파일 닫기, AOF 파일의 `fsync`, `UNLINK`의 메모리 반환처럼 오래 걸릴 수 있는 일을 메인 스레드에서 떼어 낸 것이다.

```bash
# redis-server 프로세스의 스레드 목록
ps -T -p $(pidof redis-server)
```

```text
  PID  SPID TTY          TIME CMD
 5136  5136 ?        00:00:00 redis-server
 5136  5138 ?        00:00:00 bio_close_file
 5136  5139 ?        00:00:00 bio_aof_fsync
 5136  5140 ?        00:00:00 bio_lazy_free
 5136  5141 ?        00:00:00 jemalloc_bg_thd
```

`CMD` 열의 `bio_`로 시작하는 것들이 백그라운드 스레드다. 명령을 실행하는 건 첫 줄의 `redis-server` 하나다. 코어를 더 쓰고 싶으면 인스턴스를 여러 개 띄우거나 Redis Cluster로 키를 나눈다. 한 인스턴스가 한 코어를 꽉 채우는 게 Redis의 기본 확장 단위다.

## Ubuntu에 설치하고 접속하기

여기서부터는 Ubuntu 24.04 LTS 기준이다. 24.04 기본 저장소의 `redis-server` 패키지는 7.0.15이고, 22.04는 6.0 계열이다. 명령은 둘 다 같다. 더 새 버전이 필요하면 Redis가 운영하는 apt 저장소(packages.redis.io)를 추가해서 받는다.


## 밖에서 접속하게 열 때 막아야 할 것

설치 직후의 Redis는 안전한 편이다. 세 가지 설정이 겹쳐 있다.

- `bind 127.0.0.1 -::1`: 이 서버의 루프백 주소에서만 연결을 받는다.
- `protected-mode yes`: 기본 사용자에 비밀번호가 없으면 루프백이 아닌 곳에서 온 연결을 거절한다.
- 7.0부터는 `dir`처럼 민감한 설정을 `CONFIG SET`으로 바꾸지 못하게 막는다(`enable-protected-configs no`).

문제는 응용 서버가 다른 장비에 있어서 `bind`를 열 때 생긴다. 비밀번호 없이 인터넷에 열린 Redis는 자동화된 스캐너에 금방 발견된다. 예전에는 `CONFIG SET dir`로 저장 경로를 바꿔 SSH 키나 크론 파일을 덮어쓰는 공격이 흔했고, 지금도 데이터를 지우고 몸값을 요구하거나 채굴기를 심는 일이 이어진다. 열 때는 순서를 지킨다. 바꾸기 전 상태를 확인하고, 비밀번호와 ACL을 먼저 걸고, 내부망 주소에만 묶고, 방화벽으로 응용 서버만 허용한다.

```bash
# 1) 지금 어떤 주소에서 듣고 있는지 확인한다
sudo ss -lntp | grep 6379

# 2) 설정 파일을 백업해 둔다 (되돌릴 때 쓴다)
sudo cp /etc/redis/redis.conf /etc/redis/redis.conf.bak

# 3) 설정을 고친다: bind에 내부망 주소를 추가하고, 기본 사용자에 비밀번호를 건다
#    bind 127.0.0.1 -::1 10.0.1.5
#    requirepass <긴 무작위 문자열>
sudo nano /etc/redis/redis.conf

# 4) 다시 시작하고 듣는 주소를 확인한다
sudo systemctl restart redis-server
sudo ss -lntp | grep 6379

# 5) 방화벽으로 응용 서버(10.0.1.10)에서 오는 6379만 허용한다
sudo ufw allow from 10.0.1.10 to any port 6379 proto tcp
```

```text
LISTEN 0      511        127.0.0.1:6379      0.0.0.0:*    users:(("redis-server",pid=2154,fd=6))
LISTEN 0      511            [::1]:6379         [::]:*    users:(("redis-server",pid=2154,fd=7))
```

고치기 전 출력이다. 네 번째 열(Local Address)이 `127.0.0.1:6379`와 `[::1]:6379`뿐이다. 다시 시작한 뒤에는 `10.0.1.5:6379` 줄이 하나 더 보여야 한다. 문제가 생기면 백업해 둔 파일을 `sudo cp /etc/redis/redis.conf.bak /etc/redis/redis.conf`로 되돌리고 다시 시작한다. RHEL 계열이라면 패키지 이름이 `redis`, 설정 파일이 `/etc/redis/redis.conf` 또는 `/etc/redis.conf`이고, 방화벽은 `firewall-cmd`로 연다.

`requirepass`는 모든 클라이언트가 같은 비밀번호로 같은 권한을 갖는다. 6.0부터는 ACL로 사용자마다 쓸 수 있는 명령과 키를 나눌 수 있다. 응용 계정에는 필요한 키 접두사와 명령만 준다.

```bash
# 대화형으로 접속한다 (아래 명령들은 이 프롬프트에서 친다)
redis-cli
```

```text
127.0.0.1:6379> ACL SETUSER shop-app on >s3cret-pass ~cache:* ~session:* +@read +@write -@dangerous
OK
127.0.0.1:6379> AUTH shop-app s3cret-pass
OK
127.0.0.1:6379> SET cache:product:1001 x
OK
127.0.0.1:6379> SET order:7 x
(error) NOPERM this user has no permissions to access one of the keys used as arguments
127.0.0.1:6379> KEYS *
(error) NOPERM this user has no permissions to run the 'keys' command
127.0.0.1:6379> FLUSHALL
(error) NOPERM this user has no permissions to run the 'flushall' command
```

`ACL SETUSER` 한 줄을 풀면 이렇다. `on`은 계정을 켜고, `>s3cret-pass`는 비밀번호를 추가하고, `~cache:*`와 `~session:*`는 접근할 수 있는 키 패턴이다. `+@read +@write`로 읽기·쓰기 명령 묶음을 허용하고 `-@dangerous`로 `KEYS`, `FLUSHALL`, `CONFIG` 같은 위험한 명령 묶음을 뺀다. `cache:`로 시작하지 않는 `order:7`에는 쓰지 못하고, `KEYS`와 `FLUSHALL`도 거절됐다.

`ACL SETUSER`로 만든 사용자는 메모리에만 있어서 재시작하면 사라진다. 계속 쓰려면 `redis.conf`에 `user shop-app on >s3cret-pass ~cache:* ~session:* +@read +@write -@dangerous` 한 줄을 넣거나, `aclfile`을 지정하고 `ACL SAVE`로 저장한다.

비밀번호와 ACL은 평문으로 오간다. 응용 서버와 Redis 사이가 같은 장비나 믿을 수 있는 사설망이 아니라면(다른 VPC, 클라우드 간 연결) 6.0부터 들어온 TLS를 켠다. Ubuntu 패키지는 TLS를 넣어 빌드되어 있다. `tls-port`로 TLS 포트를 열고 `port 0`으로 평문 포트를 닫는다. `tls-auth-clients`의 기본값이 `yes`라 클라이언트도 인증서를 내야 하는데, 실험에서 `--tls --cacert`만 주고 붙자 서버 로그에 `peer did not return a certificate`가 남고 연결이 끊겼다. 비밀번호만으로 충분하면 `tls-auth-clients no`로 둔다. 복제와 클러스터 버스까지 암호화하려면 `tls-replication yes`, `tls-cluster yes`를 함께 준다. 암호화 비용 때문에 처리량이 줄어드니 [처리량 글](/posts/redis-high-throughput)의 방법으로 미리 재 본다.

```bash
# redis.conf: tls-port 6380 / port 0 / tls-cert-file, tls-key-file, tls-ca-cert-file 경로 지정 후 접속 확인
redis-cli -p 6380 --tls --cacert /etc/redis/tls/ca.crt --cert /etc/redis/tls/client.crt --key /etc/redis/tls/client.key PING
```

## 키 이름은 콜론으로 나눈다

Redis에는 테이블이 없다. 키 공간 하나에 모든 키가 들어간다. 그래서 키 이름이 곧 분류 체계다. 관례는 콜론(`:`)으로 단계를 나누는 것이다. `user:42:profile`, `product:1001`, `cache:product:1001`, `rank:sales:2026-10-16`처럼 "무엇:누구:어떤 부분" 순서로 쓴다. Redis가 콜론에 특별한 의미를 두지는 않지만, 이렇게 지으면 ACL의 키 패턴(`~cache:*`)과 `SCAN`의 `MATCH`로 묶어 다루기 쉽고, GUI 도구도 콜론을 기준으로 트리처럼 보여 준다.

키 이름은 짧을수록 메모리를 덜 쓰지만, 읽을 수 없을 만큼 줄이면 운영할 때 손해가 더 크다. `u:42:p`보다 `user:42:profile`이 낫다. Redis Cluster를 쓸 계획이면 여러 키를 한 명령에서 함께 다룰 때 같은 슬롯에 있어야 하는데, 키의 `{}` 안 부분만으로 슬롯을 정하는 해시 태그를 쓴다. `user:{42}:profile`과 `user:{42}:cart`는 같은 슬롯에 들어간다.

## 문자열: 값, 카운터, 락

가장 기본 자료형이다. 값은 문자열이지만 바이너리 안전(binary safe)해서 JSON이든 이미지 바이트든 최대 512MB까지 넣을 수 있다. 처음 장면의 인기 상품 목록을 JSON으로 넣어 두는 게 문자열의 가장 흔한 쓰임이다.

```bash
# 인기 상품 목록을 60초짜리 캐시로 넣는다
redis-cli SET cache:best:today '[1001,1003,1002]' EX 60

# 꺼낸다
redis-cli GET cache:best:today

# 없는 키를 읽으면 (nil)
redis-cli GET cache:best:yesterday
```

```text
OK
"[1001,1003,1002]"
(nil)
```

값이 정수 모양이면 숫자처럼 더하고 뺄 수 있다. 상품 조회수를 세는 데 쓴다. 앞에서 본 대로 명령 하나는 원자적이라, 응용 서버 열 대가 동시에 올려도 값이 꼬이지 않는다. DB에서 `SELECT` 후 `UPDATE`로 하면 생기는 갱신 손실(lost update)이 여기서는 없다.

```bash
# 조회수를 1 올린다. 키가 없으면 0에서 시작한다
redis-cli INCR product:1001:views

# 한 번에 10 올린다
redis-cli INCRBY product:1001:views 10
```

```text
(integer) 1
(integer) 11
```

락은 위에서 뜯어 본 `SET ... NX EX`다. 워커 둘이 주문 7번을 동시에 처리하려 하면 먼저 온 쪽만 `OK`를 받는다.

```bash
# 워커 a가 락을 잡는다
redis-cli SET lock:order:7 worker-a:9f3c NX EX 10

# 워커 b도 시도하지만 이미 있어서 실패한다
redis-cli SET lock:order:7 worker-b:41d0 NX EX 10

# 지금 누가 잡고 있나
redis-cli GET lock:order:7
```

```text
OK
(nil)
"worker-a:9f3c"
```

풀 때는 "값이 내 토큰이면 지운다"를 원자적으로 해야 한다. `GET`으로 확인하고 `DEL`을 따로 보내면, 그 사이에 내 락이 만료되고 다른 워커가 새로 잡은 락을 지울 수 있다. 그래서 짧은 Lua 스크립트로 묶는다.

```bash
# 값이 worker-a:9f3c일 때만 지운다. 1은 지웠다, 0은 내 락이 아니다
redis-cli EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end" 1 lock:order:7 worker-a:9f3c
```

```text
(integer) 1
```

이 락은 Redis 한 대(또는 비동기 복제 구성)를 믿는 락이다. 프라이머리가 락을 쓰고 레플리카에 복제하기 전에 죽으면, 새 프라이머리에는 락이 없어서 두 워커가 동시에 잡을 수 있다. 워커가 GC 등으로 오래 멈춘 사이 락이 만료되는 경우도 있다. 그래서 정합성이 꼭 필요한 곳에서는 락만 믿지 않고, DB 쪽에서 버전 번호나 펜싱 토큰(락을 잡을 때마다 커지는 번호)으로 늦게 온 쓰기를 거절하게 한다. 여러 Redis 노드에 과반으로 락을 잡는 Redlock이라는 알고리즘도 있지만, 시계와 멈춤에 대한 가정 때문에 안전성 논쟁이 있으니 쓰기 전에 그 논쟁을 읽어 보는 게 좋다.

## 해시: 객체 하나를 필드로 나눠 담기

상품 1001번을 JSON 문자열 하나로 넣으면, 재고 하나를 바꿀 때도 전체를 읽고 고쳐서 다시 써야 한다. 그 사이 다른 요청이 같은 일을 하면 한쪽 변경이 사라진다. 해시는 키 하나 안에 필드-값 쌍을 여러 개 둔다. 필드 하나만 읽고 쓸 수 있다.

```bash
# 상품 1001을 필드 세 개로 넣는다. 돌려주는 숫자는 새로 생긴 필드 수다
redis-cli HSET product:1001 name earbuds price 39000 stock 12

# 필드 하나만 읽는다
redis-cli HGET product:1001 price

# 재고를 원자적으로 1 줄인다
redis-cli HINCRBY product:1001 stock -1

# 전체 필드와 값
redis-cli HGETALL product:1001
```

```text
(integer) 3
"39000"
(integer) 11
1) "name"
2) "earbuds"
3) "price"
4) "39000"
5) "stock"
6) "11"
```

`HGETALL`은 필드와 값을 번갈아 나열한다. 홀수 줄이 필드, 짝수 줄이 값이다. 필드가 적은 해시는 내부적으로 listpack이라는 압축 배열로 저장돼서 메모리를 아낀다(7.0 기준, 그 전 버전은 ziplist). 필드가 128개(`hash-max-listpack-entries`)를 넘거나 값이 64바이트(`hash-max-listpack-value`)를 넘으면 일반 해시 테이블로 바뀐다. `OBJECT ENCODING product:1001`을 치면 `"listpack"`이 나온다.

해시는 필드 단위로 TTL을 주지 못한다(7.4부터 필드 만료 명령이 생겼지만 24.04의 7.0에는 없다). 만료 단위가 다르면 키를 나눈다.

```bash
# 메일 작업 세 개를 넣는다. 돌려주는 숫자는 넣은 뒤 길이다
redis-cli LPUSH queue:email mail:7 mail:8 mail:9

# 전체를 머리부터 본다 (0부터 -1, 즉 끝까지)
redis-cli LRANGE queue:email 0 -1

# 오른쪽(꼬리)에서 하나 꺼낸다
redis-cli RPOP queue:email

# 비어 있으면 최대 5초 기다리며 꺼낸다
redis-cli BRPOP queue:email 5
```

```text

2) "mail:8"
3) "mail:7"
"mail:7"
1) "queue:email"
2) "mail:8"
```

`LPUSH`에 값 여러 개를 주면 앞에서부터 하나씩 머리에 넣으므로 마지막 값(`mail:9`)이 맨 앞에 온다. `BRPOP`은 여러 큐를 한 번에 기다릴 수 있어서, 어느 키에서 꺼냈는지 함께 돌려준다. 5초 안에 아무것도 없으면 `(nil)`이다.

이 큐에는 구멍이 하나 있다. 워커가 `RPOP`으로 꺼낸 직후 죽으면 그 작업은 어디에도 남지 않는다. 꺼내면서 처리 중 리스트로 옮기는 `LMOVE`(`BLMOVE`)로 보완하거나, 처음부터 확인 응답이 있는 스트림을 쓴다. 꺼낸 뒤 죽은 작업을 되찾는 과정은 [메시지 큐 기초](/posts/message-queue-basics)에서 직접 돌려 본다.

## 셋과 정렬된 셋: 중복 없는 모음과 순위표

셋은 순서 없이 중복 없는 값을 모은다. 상품을 찜한 회원 목록이 좋은 예다. 같은 회원이 두 번 눌러도 한 번만 들어간다.

```bash
# 1001번을 찜한 회원. 새로 들어간 수를 돌려준다
redis-cli SADD product:1001:wish 42 43 44

# 42번이 다시 눌러도 늘지 않는다
redis-cli SADD product:1001:wish 42

# 43번이 찜했나 (1이면 있다)
redis-cli SISMEMBER product:1001:wish 43

# 1002번 찜 목록을 만들고, 두 상품을 모두 찜한 회원을 구한다
redis-cli SADD product:1002:wish 42 50
redis-cli SINTER product:1001:wish product:1002:wish
```

```text
(integer) 3
(integer) 0
(integer) 1
(integer) 2
1) "42"
```

`SISMEMBER`는 원소 수와 상관없이 O(1)이다. 교집합 `SINTER`, 합집합 `SUNION`, 차집합 `SDIFF`도 서버 안에서 계산하므로 목록을 응용 서버로 가져와 비교하지 않아도 된다. 다만 집합이 크면 이 연산도 원소 수만큼 걸리는 느린 명령이 된다.

정렬된 셋(sorted set, ZSET)은 원소마다 점수가 붙고, 점수 순으로 정렬된 상태를 유지한다. 처음 장면의 "오늘의 인기 상품"을 DB 집계 대신 이걸로 만들 수 있다. 주문이 들어올 때마다 판매량 점수를 올리면 순위는 늘 정렬돼 있다.

```bash
# 오늘 판매량: 1001은 120개, 1002는 80개, 1003은 95개
redis-cli ZADD rank:sales:2026-10-16 120 1001 80 1002 95 1003

# 1002가 30개 더 팔렸다. 새 점수를 돌려준다
redis-cli ZINCRBY rank:sales:2026-10-16 30 1002

# 판매량 높은 순으로 상위 3개와 점수
redis-cli ZREVRANGE rank:sales:2026-10-16 0 2 WITHSCORES

# 1003의 순위 (0부터 센다)
redis-cli ZREVRANK rank:sales:2026-10-16 1003
```

```text
(integer) 3
"110"
1) "1001"
2) "120"
3) "1002"
4) "110"
5) "1003"
6) "95"
(integer) 2
```

1002는 80에서 110이 되어 2위로 올라갔고, 1003은 3위(0부터 세서 2)로 밀렸다. `WITHSCORES`를 주면 원소와 점수가 번갈아 나온다. 정렬된 셋은 내부적으로 스킵 리스트와 해시 테이블을 함께 써서, 점수 갱신과 순위 조회가 O(log N)이다. 원소가 100만 개여도 순위 하나를 구하는 데 수십 단계면 된다. 6.2부터는 `ZRANGE ... REV`처럼 `ZRANGE` 하나로 쓰는 문법이 권장되지만, `ZREVRANGE`도 그대로 동작한다.

## 놓치지 않는 스트림, 흘려보내는 채널

리스트 큐의 구멍(꺼낸 뒤 죽으면 사라짐)을 막은 것이 스트림이다. 스트림은 지워지지 않는 로그처럼 항목을 쌓고, 소비자 그룹이 어디까지 읽었는지와 누가 아직 확인(ACK)하지 않았는지를 서버가 기억한다. Kafka의 소비자 그룹을 작게 줄인 모양이다.

```bash
# 주문 이벤트를 추가한다. *는 ID를 서버가 만들라는 뜻
redis-cli XADD stream:orders '*' order 7 user 42 total 54000

# mailer 그룹을 만든다. 0은 처음부터 읽겠다는 뜻
redis-cli XGROUP CREATE stream:orders mailer 0

# worker-1이 그룹 이름으로 아직 아무도 안 받은(>) 항목을 받는다
redis-cli XREADGROUP GROUP mailer worker-1 COUNT 10 STREAMS stream:orders '>'

# 받았지만 아직 확인하지 않은 항목 요약
redis-cli XPENDING stream:orders mailer
```

```text
"1792184898594-0"
OK
1) 1) "stream:orders"
   2) 1) 1) "1792184898594-0"
         2) 1) "order"
            2) "7"
            3) "user"
            4) "42"
            5) "total"
            6) "54000"
1) (integer) 1
2) "1792184898594-0"
3) "1792184898594-0"
4) 1) 1) "worker-1"
      2) "1"
```

ID `1792184898594-0`의 앞부분은 밀리초 시각, 뒤는 같은 밀리초 안의 순번이다. `XPENDING` 결과는 확인 대기 1건, 가장 작은 ID와 가장 큰 ID, 그리고 worker-1이 1건을 들고 있다는 뜻이다. 메일을 보낸 뒤 `XACK stream:orders mailer 1792184898594-0`을 보내야 이 목록에서 빠진다. worker-1이 죽으면 다른 워커가 `XAUTOCLAIM`으로 오래된 미확인 항목을 가져가 다시 처리한다. 스트림은 계속 쌓이므로 `XADD`에 `MAXLEN ~ 100000` 같은 상한을 함께 준다.

Pub/Sub은 반대로 아무것도 저장하지 않는다. 채널에 발행한 메시지는 그 순간 구독 중인 클라이언트에게만 가고 끝이다. 구독자가 잠깐 끊겨 있었다면 그 사이 메시지는 영영 못 받는다. 그래서 "가격이 바뀌었으니 각 서버의 로컬 캐시를 지워라" 같은, 놓쳐도 TTL이 언젠가 정리해 주는 알림에 맞다.

```bash
# 터미널 1: 가격 변경 채널을 구독한다 (기다리는 상태가 된다)
redis-cli SUBSCRIBE ch:price-changed

# 터미널 2: 메시지를 발행한다. 돌려주는 숫자는 받은 구독자 수
redis-cli PUBLISH ch:price-changed 1001:35000
```

```text
Reading messages... (press Ctrl-C to quit)
1) "subscribe"
2) "ch:price-changed"
3) (integer) 1
1) "message"
2) "ch:price-changed"
3) "1001:35000"
```

터미널 1의 출력이다. 처음 세 줄은 구독이 됐다는 확인이고(마지막 숫자는 지금 구독 중인 채널 수), 다음 세 줄이 받은 메시지다. 터미널 2에는 `(integer) 1`이 찍힌다. 구독자가 없었다면 `(integer) 0`이고 메시지는 사라진다.

## 만료 시간을 다루는 명령

캐시든 세션이든 Redis 키의 상당수는 만료 시간(TTL)을 단다. 장바구니 키로 해 보자.

```bash
# 회원 42의 장바구니를 만들고 600초 뒤 만료되게 한다
redis-cli SET cart:42 '[1001,1003]'
redis-cli EXPIRE cart:42 600

# 남은 시간(초)
redis-cli TTL cart:42

# 만료를 없앤다
redis-cli PERSIST cart:42
redis-cli TTL cart:42

# 없는 키의 TTL
redis-cli TTL cart:999
```

```text
OK
(integer) 1
(integer) 600
(integer) 1
(integer) -1
(integer) -2
```

`TTL`이 돌려주는 음수 두 개를 구분해야 한다. `-1`은 키가 있지만 만료가 없다는 뜻이고, `-2`는 키가 아예 없다는 뜻이다. 밀리초 단위가 필요하면 `PEXPIRE`와 `PTTL`을 쓴다.

흔한 실수가 하나 있다. TTL이 걸린 키에 `EX` 없이 `SET`을 다시 하면 TTL이 사라진다. 캐시 값을 갱신하는 코드가 이렇게 짜여 있으면 그 키는 영원히 남는다.

```bash
# 300초짜리 캐시를 넣고
redis-cli SET cache:product:1001 '{"price":39000}' EX 300

# EX 없이 값만 바꾸면
redis-cli SET cache:product:1001 '{"price":35000}'

# 만료가 사라졌다
redis-cli TTL cache:product:1001
```

```text
OK
OK
(integer) -1
```

TTL을 유지한 채 값만 바꾸려면 6.0부터 생긴 `KEEPTTL` 옵션을 준다(`SET key value KEEPTTL`). 만료된 키가 지워지는 방식은 두 가지다. 누가 그 키에 접근할 때 만료됐는지 보고 지우는 방식(lazy)과, 주기적으로 만료 시간이 있는 키를 표본으로 골라 지우는 방식(active)이다. 그래서 만료된 키는 정확히 그 순간 메모리에서 빠지는 게 아니라 조금 늦게 빠지기도 한다. 메모리가 가득 찼을 때 무엇을 지우는지는 다른 이야기로, [메모리와 축출 정책 글](/posts/redis-memory-eviction)에서 다룬다.

## KEYS 대신 SCAN

`user:`로 시작하는 키를 다 찾고 싶을 때 `KEYS user:*`는 한 번에 모든 키를 훑어 서버를 멈춘다. `SCAN`은 같은 일을 조금씩 나눠서 한다. 한 번 부를 때마다 일부만 훑고 다음에 이어 갈 위치(커서)를 돌려준다.

```bash
# 커서 0에서 시작해 user:로 시작하는 키를 찾는다. COUNT는 한 번에 훑을 양의 힌트
redis-cli SCAN 0 MATCH 'user:*' COUNT 10
```

```text
1) "10"
2) 1) "user:29:profile"
   2) "user:5:profile"
   3) "user:11:profile"
   4) "user:4:profile"
   5) "user:16:profile"
   6) "user:22:profile"
   7) "user:12:profile"
   8) "user:20:profile"
   9) "user:1:profile"
```

첫 줄의 `"10"`이 다음 커서다. `SCAN 10 MATCH 'user:*' COUNT 10`으로 이어서 부르고, 커서가 `"0"`으로 돌아오면 한 바퀴를 다 돈 것이다. 커서 값은 순번이 아니라 내부 해시 테이블의 위치라서 숫자가 들쭉날쭉해도 정상이다.

`SCAN`의 성질은 알아 두어야 한다. 한 번에 돌려주는 개수는 `COUNT`와 정확히 같지 않고, `MATCH`는 훑은 뒤에 거르는 것이라 결과가 비어 있어도 커서가 0이 아니면 계속 불러야 한다. 도는 동안 계속 있던 키는 반드시 한 번 이상 나오지만, 같은 키가 두 번 나올 수 있어서 응용 쪽에서 중복을 걸러야 한다. 도중에 추가되거나 지워진 키는 나올 수도, 안 나올 수도 있다. 셸에서는 `redis-cli --scan --pattern 'user:*'`가 이 반복을 대신해 준다.

`MULTI`/`EXEC`는 원자적 실행을 위한 것이다. `MULTI` 뒤의 명령은 바로 실행되지 않고 큐에 쌓였다가, `EXEC` 때 다른 클라이언트의 명령이 끼어들지 않게 한 번에 실행된다. 재고를 빼고 판매량을 올리는 두 명령을 묶어 보자. redis-cli에서 대화형으로 친다.

```text
127.0.0.1:6379> MULTI
OK
127.0.0.1:6379(TX)> HINCRBY product:1001 stock -1
QUEUED
127.0.0.1:6379(TX)> ZINCRBY rank:sales:2026-10-16 1 1001
QUEUED
127.0.0.1:6379(TX)> EXEC
1) (integer) 10
2) "121"
```

프롬프트의 `(TX)`는 트랜잭션 안이라는 표시이고, `QUEUED`는 아직 실행하지 않고 쌓아 두었다는 뜻이다. `EXEC`의 응답은 쌓인 명령의 결과를 순서대로 담은 배열이다.

여기서 관계형 DB의 트랜잭션을 기대하면 틀린다. 롤백이 없다. 큐에 넣을 때 문법 오류가 나면 `EXEC` 전체가 거절되지만, 실행 중에 오류가 난 명령(예: 문자열에 `INCR`)은 그 명령만 실패하고 나머지는 그대로 실행된다. 그리고 `MULTI` 안에서는 앞 명령의 결과를 보고 다음 명령을 정할 수 없다. 결과는 `EXEC` 뒤에야 나오기 때문이다. "재고가 0보다 크면 뺀다"를 하려면 `WATCH product:1001`로 키를 지켜보다가, `EXEC` 전에 누가 그 키를 바꿨으면 `EXEC`가 `(nil)`을 돌려주게 해서 처음부터 다시 시도하는 낙관적 방식을 쓴다.

Lua 스크립트는 이 조건 판단까지 서버 안에서 원자적으로 한다. 읽고, 판단하고, 쓰는 과정 전체가 하나의 명령처럼 실행된다.

```bash
# 재고가 0보다 크면 1 빼고 1을 돌려준다. 아니면 0
redis-cli EVAL "local s = tonumber(redis.call('HGET', KEYS[1], 'stock')) if s and s > 0 then redis.call('HINCRBY', KEYS[1], 'stock', -1) return 1 end return 0" 1 product:1001
```

```text
(integer) 1
```

운영에서는 스크립트 본문을 매번 보내지 않는다. `SCRIPT LOAD`로 한 번 올리면 본문의 SHA1(40자리 16진수)이 돌아오고, 그다음부터는 `EVALSHA <sha> 1 product:1001`로 해시만 보낸다. 이 스크립트 캐시는 재시작, 장애 조치로 바뀐 새 프라이머리, `SCRIPT FLUSH` 뒤에는 비어 있어서 `(error) NOSCRIPT No matching script. Please use EVAL.`이 돌아온다. 실험에서도 `SCRIPT FLUSH` 직후 같은 SHA로 부르자 이 에러가 났다. 그래서 클라이언트는 `NOSCRIPT`를 받으면 `EVAL`로 한 번 다시 보내는 처리를 꼭 둔다(ioredis의 `defineCommand`, redis-py의 `register_script`가 이걸 대신 해 준다).

7.0의 Functions는 이 불편을 없앤다. `FUNCTION LOAD "#!lua name=shop ..."`로 올린 라이브러리 안에서 `redis.register_function('take_stock', ...)`으로 이름을 붙이고 `FCALL take_stock 1 product:1001`로 부른다. 스크립트 캐시와 달리 함수는 RDB·AOF에 저장되고 복제본에도 전달되어 재시작 뒤에도 남는다. 스크립트든 함수든 다루는 키는 본문에 적지 말고 `KEYS`로 넘긴다. 클러스터 클라이언트는 `KEYS`를 보고 어느 노드로 보낼지 정하고, 서버도 그 키들이 이 노드의 같은 슬롯인지 검사한다. 본문에서 키 이름을 만들어 쓰면 엉뚱한 노드에서 실행되거나, 7.0에서는 다른 슬롯의 키에 손댔다는 에러로 실패한다. 오래 도는 스크립트가 `BUSY`를 내는 문제는 [앞에서](#느린-명령-하나가-모두를-세운다) 본 대로 `SCRIPT KILL`로 끊는다.

왕복만 줄이려면 파이프라인, 몇 명령을 끼어들기 없이 실행하려면 `MULTI`/`EXEC`, 읽은 값으로 판단까지 원자적으로 하려면 Lua다. Lua 스크립트는 길어지면 서버 전체를 멈추므로 짧게 쓴다. Redis Cluster에서는 스크립트와 `MULTI`가 다루는 키가 모두 같은 슬롯에 있어야 한다.

## 응용 로그에 Redis 타임아웃이 찍히면

장바구니 API의 p99가 튀고, 로그에 Redis 명령 타임아웃이 섞여 나온다. 이때 "Redis가 느려졌다"고 단정하기 전에 나눠 볼 곳이 셋 있다. 서버 안에서 명령이 오래 걸렸는지, 연결을 얻지 못했는지, Redis는 멀쩡한데 응용과 Redis 사이가 느린지다.

먼저 서버 안을 본다. 앞에서 본 `SLOWLOG`는 느린 명령을 한 건씩 남기고, `INFO commandstats`는 명령 종류별로 쓴 시간을 모아 준다. 한 번은 짧아도 아주 자주 불리는 명령은 SLOWLOG에 안 잡혀도 여기서 드러난다.

```bash
# 명령별 호출 수, 총 시간(µs), 한 번 평균(µs). 서버 시작이나 CONFIG RESETSTAT 뒤부터 센다
redis-cli INFO commandstats | grep -E 'hgetall|cmdstat_get:'
```

```text
cmdstat_hgetall:calls=3,usec=373076,usec_per_call=124358.66,rejected_calls=0,failed_calls=0
cmdstat_get:calls=200,usec=57,usec_per_call=0.28,rejected_calls=0,failed_calls=0
```

필드 30만 개짜리 장바구니 해시에 `HGETALL`을 세 번 불렀더니 한 번에 124ms씩 걸렸다. `GET`은 한 번에 0.28µs다. `usec_per_call`이 튀는 명령이 보이면 그 키를 찾아 쪼개거나 `HSCAN`으로 나눠 읽는다. 큰 키를 찾는 방법은 [메모리 글](/posts/redis-memory-eviction)에 있다. 순간적인 멈춤을 놓치지 않으려면 지연 모니터도 켜 둔다.

```bash
# 100ms 넘게 걸린 사건을 기록한다 (기본값 0은 꺼짐)
redis-cli CONFIG SET latency-monitor-threshold 100
redis-cli LATENCY LATEST
```

```text
1) 1) "command"
   2) (integer) 1792322232
   3) (integer) 133
   4) (integer) 133
```

사건 이름, 마지막으로 생긴 시각, 마지막 지연(ms), 가장 컸던 지연(ms) 순이다. `command` 대신 `fork`나 `aof-fsync-always` 같은 이름이 찍히면 명령이 아니라 디스크 저장 쪽이 멈춘 것이다. `LATENCY DOCTOR`를 치면 쌓인 기록을 문장으로 풀어 준다.

두 번째는 연결이다. 연결 수가 `maxclients`(기본 10000)에 닿으면 새 연결은 명령을 보내기도 전에 거절된다. 실습 서버를 `maxclients 20`으로 띄우고, 연결을 열기만 하고 닫지 않는 프로그램을 돌렸더니 21번째 연결부터 이 답이 왔다.

```text
ERR max number of clients reached
```

```bash
# 붙어 있는 연결 수와 한도
redis-cli INFO clients | grep -E 'connected_clients|maxclients'

# 거절한 연결 수 (누적값)
redis-cli INFO stats | grep rejected_connections

# 어느 주소가 연결을 많이 열었나. laddr=까지 세지 않게 앞에 공백을 붙인다
redis-cli CLIENT LIST | grep -o ' addr=[^:]*' | sort | uniq -c | sort -rn
```

```text
connected_clients:20
maxclients:20
rejected_connections:5
     20  addr=127.0.0.1
```

운영 서버라면 마지막 명령의 결과가 응용 서버 IP별로 나뉘어서, 어느 서버가 연결을 쌓고 있는지 바로 보인다. `CLIENT LIST`의 각 줄에서 `idle`(마지막 명령 뒤로 지난 초)이 큰 연결이 잔뜩 있으면, 요청마다 클라이언트를 새로 만들고 닫지 않는 코드를 의심한다. 클라이언트는 프로세스마다 하나(또는 풀 하나)를 만들어 재사용하고, Pod 수 × 프로세스 수 × 풀 크기가 `maxclients`보다 넉넉히 작은지 배포 전에 계산해 둔다. Redis의 `timeout` 설정이 기본 0이라 놀고 있는 연결을 서버가 먼저 끊지 않는다는 것도 기억해 둔다.

세 번째는 Redis와 응용 사이다. 서버 안 숫자는 깨끗한데 응용에서만 느리다면, 응용 서버에서 `redis-cli -h 레디스주소 --latency`를 돌려 Redis 서버에서 잰 값과 비교한다. 응용 서버에서 잰 값만 높으면 네트워크 구간이고, 둘 다 낮은데 응용 로그만 느리면 응용 안에서 기다린 것이다. Node.js라면 이벤트 루프가 다른 일에 막혀 응답을 늦게 읽었거나 풀의 빈 연결을 기다렸을 수 있다. 네트워크 구간을 좁히는 순서는 [계층별 장애 좁히기](/posts/network-troubleshooting-by-layer)에, 이벤트 루프가 막히는 모양은 [이벤트 루프 글](/posts/event-loop)에 정리해 뒀다.

타임아웃이 나자마자 재시도를 여러 번 붙이는 것도 흔한 실수다. Redis가 큰 명령 하나에 막혀 있는 동안 재시도까지 몰리면 줄이 더 길어진다. 재시도는 한두 번만 간격을 두고 하고, 캐시 조회라면 실패했을 때 DB로 가거나 기본값을 주도록 정해 둔다.

## Memcached와 무엇이 다른가

캐시 서버로 Redis와 자주 비교되는 것이 Memcached다. 둘 다 메모리에 키-값을 두지만 출발점이 다르다.

| | Redis | Memcached |
|---|---|---|
| 값의 종류 | 문자열, 해시, 리스트, 셋, 정렬된 셋, 스트림 등 | 문자열(바이트 덩어리) 하나 |
| 디스크 저장 | RDB 스냅샷, AOF 로그 | 없음. 재시작하면 비어 있다 |
| 복제·장애 조치 | 레플리카, Sentinel, Cluster | 서버 기능으로는 없다. 클라이언트가 키를 나눠 보낸다 |
| 스레드 | 명령 실행은 한 스레드, I/O만 나눌 수 있다 | 처음부터 멀티 스레드 |
| 메모리가 차면 | `maxmemory-policy`로 고른다 (기본은 거절) | LRU로 오래된 항목을 밀어낸다 |
| 값 하나의 최대 크기 | 512MB | 기본 1MB (`-I`로 조절) |

Memcached는 멀티 스레드라 코어 많은 서버 한 대에서 단순한 GET/SET 처리량을 끌어올리기 좋고, 기능이 적은 만큼 운영할 것도 적다. 데이터가 날아가도 DB에서 다시 채우면 되는 순수 캐시라면 충분한 선택이다. Redis는 자료구조 덕에 카운터, 순위표, 큐, 락, 세션처럼 캐시 이상의 일을 서버 안에서 원자적으로 처리할 수 있고, 복제와 디스크 저장으로 재시작 후에도 데이터를 살릴 수 있다. 요즘 새로 고를 때는 기능 폭 때문에 Redis(또는 호환 포크)를 고르는 경우가 많다.

Redis는 기본 설정에서 `maxmemory`가 0(제한 없음)이고 정책이 `noeviction`이다. 캐시로 쓴다면 메모리 상한과 축출 정책을 반드시 정해야 한다. 안 그러면 서버 메모리를 다 쓰고 OS가 프로세스를 죽이거나, 쓰기가 거절된다.

## 주 저장소로 쓰기 전에 따져 볼 것

Redis가 빠르고 디스크 저장도 되니 DB 대신 쓰면 안 되나 하는 생각이 든다. 쓸 수 있는 곳도 있지만, 따져 볼 게 많다.

데이터가 전부 메모리에 있어야 한다. 키 100만 개(값은 작은 숫자)를 넣었더니 `used_memory`가 86MB 정도였다. 키 하나에 수십 바이트의 관리 비용이 붙는다. 데이터가 수백 GB로 자라면 그만큼의 RAM이 필요하고, 같은 용량의 디스크보다 훨씬 비싸다.

유실 가능성이 있다. RDB 스냅샷은 몇 분 간격으로 찍으니 그 사이 쓰기가 날아갈 수 있고, AOF를 `appendfsync everysec`(흔한 설정)로 두면 최대 1초 남짓을 잃을 수 있다. 복제는 비동기라서, 프라이머리가 응답한 쓰기가 레플리카에 가기 전에 장애 조치가 일어나면 그 쓰기는 사라진다. 이 부분은 [영속성과 고가용성 글](/posts/redis-persistence-ha)에서 자세히 본다.

질의가 약하다. 키로 찾는 것 말고는 보조 인덱스, 조인, 임의 조건 검색이 없다. "지난달 3만 원 이상 주문한 회원"을 찾으려면 그 질문용 자료구조를 미리 만들어 두어야 한다. 질문이 바뀔 때마다 데이터 모양을 바꿔야 한다. 트랜잭션도 롤백이 없다.

그래서 기준은 "날아가면 다시 만들 수 있는가"다. 캐시, 세션, 요청 수 제한 카운터, 순위표, 작업 큐처럼 원본이 따로 있거나 잠깐 잃어도 되는 데이터는 Redis가 잘 맞는다. 주문, 결제, 잔액처럼 잃으면 안 되고 나중에 다양한 질문을 던질 데이터는 관계형 DB에 두고, Redis는 그 앞에서 빠르게 읽는 층으로 쓴다. 어떤 패턴으로 앞에 둘지는 [캐시 전략 글](/posts/caching-strategies)에서 이어서 다룬다.

## 라이선스가 바뀐 이야기

회사에서 Redis를 고를 때 한 번쯤 나오는 이야기라 짧게 적는다. Redis는 오래 BSD 라이선스였는데, 2024년 7.4부터 RSALv2와 SSPLv1 중 고르는 소스 공개(source-available) 라이선스로 바뀌었다. 클라우드 업체가 Redis를 그대로 관리형 서비스로 파는 것을 제한하려는 변경으로 알려져 있다. 이에 맞서 Linux Foundation 아래에서 BSD 라이선스인 7.2.4를 기반으로 한 포크 Valkey가 나왔고, 여러 클라우드가 Valkey를 지원하기 시작했다. 2025년 Redis 8부터는 AGPLv3도 선택지로 추가됐다.

이 글의 Ubuntu 24.04 패키지(7.0.15)는 바뀌기 전 버전이다. 명령과 동작은 이 글 범위에서 Redis와 Valkey가 같다. 어떤 버전을 어떤 방식으로 배포하느냐에 따라 의무가 달라질 수 있으니, 제품에 넣거나 서비스로 제공할 때는 그 시점의 라이선스를 직접 확인한다. 갈라진 뒤 달라진 명령과 기본값, 옮기는 순서는 [Valkey와 Redis 글](/posts/valkey-vs-redis)에 있다.

## 빠른 이유와 멈추는 이유는 같은 곳에 있다

Redis는 데이터를 메모리에 두고, 단순한 자료구조 연산을, 스레드 하나가 락 없이 차례로 실행해서 빠르다. 그 "차례로"가 동시에 약점이라, `KEYS *`나 큰 키 삭제 같은 명령 하나가 모든 클라이언트를 세운다. 자료구조를 잘 고르면 카운터, 락, 큐, 순위표를 응용 코드 없이 서버 안에서 원자적으로 처리할 수 있다. 다만 메모리 비용과 유실 가능성이 있으니, 다시 만들 수 있는 데이터를 빠르게 꺼내는 자리에 둔다.

## 면접에서 나올 만한 질문

### Redis는 왜 빠른가요?

데이터를 전부 메모리에 두기 때문에 디스크 I/O가 없고, 명령이 해시 테이블 조회 같은 단순한 자료구조 연산이라 계산이 적다. 명령을 스레드 하나에서 실행하니 락 경합과 문맥 전환 비용도 없다. 명령 실행은 보통 µs 단위이고, 응용 서버가 느끼는 지연은 대부분 네트워크 왕복이다.

### 싱글 스레드인데 어떻게 수많은 연결을 처리하나요?

I/O 다중화를 쓴다. 리눅스에서는 epoll에 모든 소켓을 등록해 두고, 데이터가 도착한 소켓만 골라 명령을 읽고 실행하고 응답한다. 명령 하나하나가 매우 짧아서 한 스레드로도 초당 수만~수십만 건을 처리한다. 코어를 더 쓰려면 인스턴스를 여러 개 띄우거나 Cluster로 키를 나눈다.

### 운영 환경에서 KEYS를 쓰면 왜 안 되나요?

명령이 한 줄로 실행되기 때문에, 모든 키를 훑는 `KEYS`가 도는 동안 다른 모든 클라이언트가 기다린다. 키 100만 개에서 0.5초 정도 걸리는 걸 SLOWLOG로 확인할 수 있다. 대신 커서로 조금씩 훑는 `SCAN`을 쓰고, 중복이 나올 수 있으니 응용에서 걸러 낸다. 큰 키를 지울 때도 `DEL` 대신 백그라운드에서 메모리를 돌려주는 `UNLINK`를 쓴다.

### Redis 6부터 멀티 스레드라는데, 무엇이 바뀌었나요?

소켓 읽기와 응답 쓰기 같은 네트워크 I/O를 여러 스레드에 나눌 수 있게 됐다. 명령 실행은 여전히 메인 스레드 하나라서 원자성과 락 없는 구조는 그대로이고, 느린 명령이 전체를 막는 문제도 그대로다. 기본값은 꺼져 있고 4코어 이상에서 CPU가 실제로 병목일 때 켠다.

### SET NX EX로 분산 락을 만들 때 주의할 점은요?

`SETNX`와 `EXPIRE`를 따로 보내면 그 사이에 죽었을 때 영원히 안 풀리는 락이 남으니 한 명령으로 쓴다. 값에 무작위 토큰을 넣고, 풀 때는 Lua로 "내 토큰일 때만 삭제"를 원자적으로 한다. 비동기 복제 중 장애 조치나 프로세스 멈춤으로 두 쪽이 동시에 락을 가질 수 있으므로, 정합성이 중요하면 DB 쪽에서 펜싱 토큰이나 버전으로 늦은 쓰기를 막는다.

### MULTI/EXEC와 Lua 스크립트는 어떻게 다른가요?

둘 다 다른 클라이언트의 명령이 끼어들지 않게 묶어 실행한다. `MULTI`는 명령을 쌓아 두었다가 `EXEC`에서 한 번에 실행하므로 중간 결과로 분기할 수 없고, 롤백도 없다. 조건 판단이 필요하면 `WATCH`로 낙관적 재시도를 하거나, 읽기와 판단과 쓰기를 서버 안에서 한 번에 하는 Lua를 쓴다. 파이프라이닝은 왕복만 줄일 뿐 원자성은 없다.

### Memcached 대신 Redis를 고르는 이유는요?

Redis는 해시, 리스트, 정렬된 셋 같은 자료구조와 원자적 연산이 있어서 카운터, 순위표, 큐, 락을 서버 안에서 처리할 수 있고, 복제와 디스크 저장도 된다. Memcached는 문자열만 다루고 영속성이 없지만 멀티 스레드라 단순 캐시 처리량에 강하고 운영이 단순하다. 순수 캐시면 둘 다 되고, 캐시 이상의 기능이 필요하면 Redis다.

### Redis를 주 데이터베이스로 써도 되나요?

데이터가 다시 만들 수 있거나 잠깐 잃어도 되는 종류라면 괜찮다. 하지만 전부 메모리에 있어야 해서 비싸고, RDB와 AOF 설정에 따라 수 초에서 수 분의 쓰기를 잃을 수 있으며, 비동기 복제라 장애 조치 때 응답한 쓰기가 사라질 수 있다. 보조 인덱스와 임의 질의도 없다. 그래서 주문이나 결제처럼 잃으면 안 되는 데이터는 관계형 DB에 두고 Redis는 앞단의 빠른 층으로 쓴다.
