<EasyIntro>
  주문 서비스가 재고 서비스를 부르는 방식을 gRPC로 바꿨더니 응답이 작아지고 빨라졌다. 그런데 다음 날 보니 재고 서버 세 대 중 한 대만 일하고 둘은 놀고 있었다. 이 쏠림은 gRPC의 구조에서 나온다.

  gRPC는 다른 서버의 함수를 내 코드의 함수처럼 부르게 해 주는 방식이다. 주고받을 메시지 모양을 설계도 파일에 먼저 적고, 그 파일로 양쪽 코드를 만들어 내니 모양이 어긋나는 실수가 실행 전에 걸린다. 메시지에는 필드 이름 대신 번호만 실어서 크기가 작고, 연결 하나를 오래 열어 두고 그 위로 여러 호출을 한꺼번에 실어 나른다.

  그 "연결 하나를 오래 쓴다"는 성질이 쏠림의 원인이다. 연결을 나눠 주는 장치는 연결이 처음 생길 때 한 번만 서버를 고르는데, 그 뒤로 모든 호출이 같은 연결을 타니 다시 고를 기회가 없다. 그래서 호출 단위로 나누는 중계자를 두거나, 부르는 쪽이 직접 돌아가며 고르거나, 연결에 수명을 두어 주기적으로 새로 맺게 한다.
</EasyIntro>

주문 서비스가 재고 서비스를 부르는 내부 API를 JSON REST에서 gRPC로 바꿨다. 응답 크기가 줄고 지연도 줄었다. 그런데 다음 날 대시보드를 보니 재고 서비스 Pod 세 개 중 하나만 CPU가 90%이고 나머지 둘은 놀고 있다. 쿠버네티스 Service 뒤에 두었으니 나눠서 받을 줄 알았다.

gRPC는 구글이 내부에서 쓰던 RPC 프레임워크(Stubby)를 2015년에 공개한 것이다. RPC(Remote Procedure Call)는 다른 서버의 함수를 내 코드의 함수처럼 부르는 방식이다. `inventory.Reserve(orderId)`라고 쓰면 그 아래에서 직렬화, 네트워크 전송, 역직렬화가 일어난다. gRPC는 이걸 Protocol Buffers(메시지 형식)와 HTTP/2(전송) 위에 만들었다. 위의 CPU 쏠림도 이 조합에서 나온다.

이 글에서는 실제 `protoc`(libprotoc 35.1)으로 메시지를 바이트까지 풀어 보고, node의 `@grpc/grpc-js` 1.14로 서버와 클라이언트를 띄워 스트리밍, 기한, 상태 코드, 로드 밸런싱을 직접 확인한다. REST 설계는 [REST API 설계](/posts/rest-api-design), HTTP/2 자체는 [HTTP 버전](/posts/http-versions)에서 다뤘다.

## .proto 한 장이 계약이 된다

gRPC는 인터페이스를 먼저 쓴다. 서비스의 함수와 주고받는 메시지 모양을 `.proto` 파일에 적는다.

```protobuf
syntax = "proto3";
package shop.v1;

service OrderService {
  rpc GetOrder(GetOrderRequest) returns (Order);                 // unary
  rpc WatchOrder(GetOrderRequest) returns (stream OrderEvent);  // server streaming
}

message GetOrderRequest { int64 id = 1; }

message Order {
  int64 id = 1;
  string status = 2;
  int32 amount = 3;
  repeated string items = 4;
  sint32 balance = 5;
}

message OrderEvent { string status = 1; int64 at = 2; }
```

이 파일 하나로 Go 서버 코드와 Java 클라이언트 코드, TypeScript 타입을 생성한다. 서버가 `amount`를 문자열로 바꾸면 클라이언트 코드 생성 단계나 컴파일에서 걸린다. JSON REST에서는 같은 실수가 운영 중 런타임 에러로 나타난다. 계약이 코드보다 먼저 있다는 점이 gRPC의 첫째 장점이다. 그림으로 보면 이렇다.

## 26바이트로 줄어든 주문

같은 주문을 JSON과 protobuf로 만들어 크기를 비교했다.

```bash

echo '{"id":150,"status":"PAID","amount":42000,"items":["book","pen"],"balance":-1}' | tr -d '\n' | wc -c
```

## 호출 하나는 스트림 하나

gRPC 호출 하나는 HTTP/2 스트림 하나다. 라이브러리 없이 node의 `http2` 모듈로 직접 gRPC 요청을 만들어 보냈다. 경로는 `/패키지.서비스/메서드`이고, 본문은 protobuf 앞에 5바이트 머리를 붙인 것이다.

```bash
node raw.js   # GetOrderRequest{id:150}을 HTTP/2로 직접 보낸다
```

```text
request headers: {
  ':method': 'POST',
  ':path': '/shop.v1.OrderService/GetOrder',
  'content-type': 'application/grpc',
  te: 'trailers',
  'grpc-timeout': '1000m'
}
request DATA: 00 00 00 00 03 08 96 01
response headers: { ':status': 200, 'content-type': 'application/grpc+proto' }
response DATA: 00 00 00 00 1a 08 96 01 12 04 50 41 49 44 18 90 c8 02 22 04 62 6f 6f 6b 22 03 70 65 6e 28 01
trailers: { 'grpc-status': '0', 'grpc-message': 'OK' }
```

DATA의 첫 바이트 `00`은 압축하지 않았다는 표시, 다음 4바이트가 메시지 길이다(요청 3, 응답 0x1a = 26). 그 뒤가 앞에서 본 protobuf 바이트 그대로다. 결과는 본문이 아니라 마지막의 trailers(본문 뒤에 오는 헤더)로 알린다. 스트리밍 응답은 본문이 언제 끝날지 모르니, 다 보낸 뒤에야 성공·실패를 말할 수 있어서다. 이 trailers 때문에 gRPC는 HTTP/2를 끝까지 지원하는 프록시가 필요하다. 아래 그림이 이 흐름이다.

같은 연결 위에 스트림이 여러 개 동시에 열릴 수 있다(멀티플렉싱). 호출마다 TCP·TLS 연결을 새로 맺지 않으니 빠르다. 서버 쪽에서는 이 스트림 수에 상한(`SETTINGS_MAX_CONCURRENT_STREAMS`)이 있어서(값은 서버와 프록시마다 다르고 100 안팎으로 잡는 곳이 많다), 한 연결에 동시 호출이 그 이상 쌓이면 클라이언트 쪽에서 기다린다. 클라이언트가 채널(연결 묶음)을 호출마다 새로 만들면 이 장점이 전부 사라진다. 채널은 한 번 만들어 재사용한다.

## 묻고 답하는 것만 있는 게 아니다

gRPC 메서드는 요청과 응답 각각이 하나인지 흐름(stream)인지에 따라 네 가지다. unary(하나 → 하나), server streaming(하나 → 여러 개), client streaming(여러 개 → 하나, 업로드), bidirectional streaming(양쪽 다 흐름, 채팅·실시간 위치)이다. 같은 HTTP/2 스트림 위에서 DATA 묶음을 여러 개 보내는 것뿐이라 별도 프로토콜이 필요 없다.

서버를 띄우고 unary 두 번, 기한을 짧게 준 호출 하나, 배송 상태를 흘려 주는 server streaming 하나를 차례로 불렀다.

```bash
node server.js 50051 > s1.log &   # OrderService 서버
node client.js                     # 차례로 네 가지 호출
cat s1.log
```

```text
  43ms GetOrder(150): {"id":150,"status":"PAID","amount":42000,"items":["book","pen"],"balance":-1}
  48ms GetOrder(404): 5 NOT_FOUND - order 404 not found
 550ms GetOrder(999) deadline 500ms: 4 DEADLINE_EXCEEDED - Deadline exceeded after 0.501s,LB pick: 0.001s,remote_addr=127.0.0.1:50051
 560ms WatchOrder event: PAID 1792540800
 857ms WatchOrder event: PACKED 1792540860
1156ms WatchOrder event: SHIPPED 1792540920
1457ms WatchOrder event: DELIVERED 1792540980
1459ms WatchOrder end: 0 OK
[50051] listening
```

스트리밍은 서버가 300ms마다 보낸 이벤트가 그대로 300ms 간격으로 도착했다. 폴링 없이 상태 변화를 받는다. 스트림은 연결 하나를 오래 붙잡으니 서버 배포 때 끊긴다는 전제로 짠다. 클라이언트는 끊기면 마지막으로 받은 상태부터 다시 구독하고, 서버는 종료 신호를 받으면 스트림을 정리하고 닫는다.

## 기한을 넘기면 끊고, 서버도 그만둔다

세 번째 호출을 다시 보자. 클라이언트는 500ms 기한(deadline)을 줬고, 서버는 1.5초 걸리는 주문이었다. 클라이언트는 501ms에 `DEADLINE_EXCEEDED`(4)를 받았다. 중요한 건 서버 로그의 `client gone, skip work`다. 기한이 `grpc-timeout` 헤더로 서버에 전달되고, 기한이 지나면 서버 쪽 호출도 취소 상태가 된다. 서버는 그걸 보고 남은 일을 하지 않았다.

REST에서 클라이언트 타임아웃은 클라이언트만의 사정이다. 서버는 아무도 기다리지 않는 응답을 끝까지 만든다. gRPC는 "타임아웃"이 아니라 "기한"을 쓴다. 기한은 절대 시각이라 A → B → C로 호출이 이어지면 B가 C를 부를 때 남은 시간을 그대로 넘긴다(Go의 `context`, Java의 `Context`가 이걸 한다). 맨 앞 사용자가 포기했으면 사슬 전체가 함께 멈춘다. 호출 사슬의 타임아웃을 어떻게 맞추는지는 [타임아웃](/posts/timeouts)에서 다뤘다.

흔한 실수는 기한을 안 주는 것이다. gRPC는 기본 기한이 없다. 서버가 멈추면 클라이언트 호출도 영원히 기다리고, 스트림 수 상한에 막혀 그 채널의 다른 호출까지 밀린다. 모든 호출에 기한을 준다.

## 상태 코드는 HTTP 200 안에 있다

두 번째 호출의 `NOT_FOUND`는 HTTP로 보면 어떻게 왔을까. 404번 주문을 `raw.js`로 다시 불렀다.

```text
response headers: {
  ':status': 200,
  'content-type': 'application/grpc+proto',
  'grpc-status': '5',
  'grpc-message': 'order%20404%20not%20found'
}
```

HTTP 상태는 200이다. 본문 없이 헤더에 바로 결과를 담은 trailers-only 응답이다. 그래서 HTTP 상태 코드만 세는 로드 밸런서·Ingress 지표에서 gRPC 에러율은 0%로 보인다. gRPC 서비스의 에러율은 `grpc-status`를 읽는 프록시(Envoy 등)나 서버 인터셉터의 지표로 본다.

상태 코드는 17개다. `@grpc/grpc-js`의 enum을 그대로 찍었다.

```text
0=OK 1=CANCELLED 2=UNKNOWN 3=INVALID_ARGUMENT 4=DEADLINE_EXCEEDED 5=NOT_FOUND 6=ALREADY_EXISTS 7=PERMISSION_DENIED 8=RESOURCE_EXHAUSTED 9=FAILED_PRECONDITION 10=ABORTED 11=OUT_OF_RANGE 12=UNIMPLEMENTED 13=INTERNAL 14=UNAVAILABLE 15=DATA_LOSS 16=UNAUTHENTICATED
```

재시도 판단에 쓰는 구분이 중요하다. `UNAVAILABLE`(14)은 서버에 닿지 못했거나 연결이 끊긴 것이라 다시 보내도 되는 대표 코드다. `DEADLINE_EXCEEDED`는 서버가 이미 처리했을 수 있으니 멱등한 호출만 재시도한다. `INVALID_ARGUMENT`, `NOT_FOUND`, `PERMISSION_DENIED`는 다시 보내도 같다. 애플리케이션 예외를 잡지 않고 던지면 `UNKNOWN`(2)이 되어 원인을 알 수 없게 되니, 서버에서 의미에 맞는 코드로 바꿔 돌려준다. gRPC는 서비스 설정(service config)에 재시도할 코드와 백오프를 선언하는 기능도 있다. 재시도의 일반 원칙은 [재시도](/posts/retries)에 있다.

## 연결이 오래 사니 로드 밸런서가 할 일이 없다

맨 앞의 CPU 쏠림으로 돌아온다. 쿠버네티스 ClusterIP Service는 kube-proxy가 만든 iptables 규칙으로 동작하고, 이 규칙은 TCP 연결이 처음 생길 때 한 번 백엔드를 고른다. L4 로드 밸런싱이다. HTTP/1.1 클라이언트는 연결을 여러 개 열고 자주 새로 맺으니 이걸로 충분히 퍼진다. gRPC 클라이언트는 연결 하나를 열어 몇 시간이고 그 위로 모든 호출을 보낸다. 고르는 순간이 한 번뿐이니 한 Pod가 전부 받는다.

연결마다 다음 백엔드로 보내는 L4 프록시를 node로 만들고, 그 뒤에 gRPC 서버 세 개를 띄워 재현했다. 채널 하나로 300번 부른 결과다.

```bash
bash lbrun.sh   # A: 클라이언트 1개, B: 클라이언트 3개 (각자 채널 하나), C·D: 클라이언트 쪽 round_robin
```

```text
== A: L4 LB, 클라이언트 1개
300 calls done via 127.0.0.1:50060 (default pick_first)
new TCP connection -> 50061
[50061] served=300
[50062] served=0
[50063] served=0
== B: L4 LB, 클라이언트 3개
new TCP connection -> 50061
new TCP connection -> 50062
new TCP connection -> 50063
[50061] served=300
[50062] served=300
[50063] served=300
```

A에서 TCP 연결은 딱 하나였고 300번이 전부 한 서버로 갔다. B처럼 클라이언트(연결)가 여러 개면 연결 단위로는 퍼진다. 운영에서 클라이언트 Pod가 많으면 그럭저럭 퍼지다가, 호출하는 쪽이 적거나 한쪽만 바쁘면 쏠린다. 서버 Pod를 늘린 직후에도 기존 연결은 옛 Pod에 붙어 있어서 새 Pod는 논다.

해결 방법은 세 갈래다.

첫째, 호출 단위로 나누는 L7 프록시를 둔다. Envoy, Linkerd·Istio 같은 서비스 메시의 사이드카, gRPC를 지원하는 Ingress가 HTTP/2 스트림(호출)마다 백엔드를 고른다. 코드를 안 바꿔도 되고 재시도·관측도 같이 얻는 대신 홉과 운영할 것이 하나 늘어난다([서비스 메시](/posts/service-mesh)).

둘째, 클라이언트가 직접 나눈다. 쿠버네티스에서는 `clusterIP: None`인 headless Service를 만들면 DNS가 Pod IP 목록을 돌려주고, 클라이언트는 `dns:///inventory.shop.svc.cluster.local:50051`로 그 목록에 모두 연결한 뒤 호출마다 돌아가며 고른다(`round_robin`). 서버 주소 세 개를 직접 줘서 시험했다.

```text
== C: 클라이언트 쪽 round_robin (바로 보냄)
300 calls done via ipv4:127.0.0.1:50061,127.0.0.1:50062,127.0.0.1:50063 round_robin
[50061] served=300
[50062] served=0
[50063] served=0
== D: 클라이언트 쪽 round_robin (300ms 뒤)
300 calls done via ipv4:127.0.0.1:50061,127.0.0.1:50062,127.0.0.1:50063 round_robin
[50061] served=100
[50062] served=100
[50063] served=100
```

C는 의외의 결과다. round_robin은 연결이 준비(READY)된 서버 사이에서만 돌아가는데, 첫 연결이 준비되자마자 300번을 몰아 보냈더니 나머지 둘이 연결되기 전에 전부 첫 서버로 갔다. 300ms 기다린 D에서 정확히 100씩 나뉘었다. 실제 서비스에서는 기동 직후 잠깐 쏠리고 곧 고르게 된다. 이 방식은 프록시가 없어 빠르지만, DNS가 바뀐 Pod 목록을 클라이언트가 다시 조회해야 하고(grpc-go는 연결이 끊길 때 DNS를 다시 본다) 언어별 클라이언트 설정이 필요하다.

셋째, 서버가 연결을 주기적으로 끊는다. 서버에 최대 연결 수명(`max_connection_age`)을 주면 그 시간이 지난 연결에 GOAWAY를 보내고, 클라이언트는 새 연결을 맺는다. 새 연결이니 L4 로드 밸런서가 다시 고른다. A와 같은 조건(클라이언트 1개, 채널 1개)에서 서버에 1초 수명을 주고 약 4초 동안 300번 불렀다.

```bash
# 서버: grpc.max_connection_age_ms=1000, grpc.max_connection_age_grace_ms=5000
bash agerun.sh
```

```text
sent=300 failed=0
new TCP connection -> 50061
new TCP connection -> 50062
new TCP connection -> 50063
new TCP connection -> 50061
[50061] served=108
[50062] served=99
[50063] served=93
```

연결이 네 번 새로 맺어지며 고르게 퍼졌고 실패는 0이었다. 진행 중인 호출은 grace 시간 동안 끝낼 수 있기 때문이다. 실무에서는 수명을 몇 분 단위(예: 5~30분)로 두고, 새 Pod가 늦어도 그 안에는 호출을 받기 시작하게 한다. 너무 짧으면 연결 맺는 비용(TLS 포함)이 커진다. 로드 밸런싱 알고리즘 자체는 [로드 밸런싱 알고리즘](/posts/load-balancing-algorithms)에서 비교했다.

## 브라우저에서는 바로 못 부른다

브라우저의 `fetch`는 HTTP/2 trailers를 읽을 수 없고 프레임을 직접 다룰 수도 없다. 그래서 브라우저는 gRPC를 그대로 못 쓴다. gRPC-Web은 trailers를 본문 끝에 넣는 변형 형식으로, 앞단에 Envoy 같은 변환 프록시가 필요하다. Buf가 만든 Connect 프로토콜은 같은 `.proto`로 일반 HTTP POST와 JSON까지 받아 브라우저와 curl에서 바로 부를 수 있게 한다. 공개 API는 여전히 JSON REST가 기본이고, gRPC는 서비스 사이의 내부 호출에서 주로 쓴다.

## REST, GraphQL과 고르는 기준

gRPC가 맞는 곳은 서비스끼리 많이, 자주 부르는 내부 호출이다. 스키마와 코드 생성으로 팀 사이 계약이 분명하고, 메시지가 작고, 기한 전파와 스트리밍이 기본으로 있다. 여러 언어로 된 서비스가 섞여 있으면 더 좋다.

REST가 맞는 곳은 공개 API, 브라우저, 사람이 curl로 시험해 볼 API다. HTTP 캐시와 CDN을 그대로 쓰고, 상태 코드가 프록시·모니터링 도구에 다 보인다. 디버깅 비용이 낮다.

GraphQL은 화면마다 필요한 데이터 모양이 크게 다른 클라이언트(웹·앱)가 한 번에 원하는 필드만 받아 가는 데 맞다. 서버 사이 호출보다는 프론트엔드와 백엔드 사이(BFF)에 둔다.

한 회사가 셋을 다 쓰는 경우가 흔하다. 바깥은 REST나 GraphQL, 안쪽은 gRPC다. gRPC를 고를 때 같이 떠안는 비용도 적어 둔다. `.proto` 저장소와 코드 생성 파이프라인, HTTP/2를 끝까지 지원하는 프록시, 바이너리라서 어려운 디버깅, 그리고 앞에서 본 로드 밸런싱 문제다.

## 현장에서 gRPC 호출이 실패할 때

"배포할 때마다 `UNAVAILABLE`이 잠깐 쏟아진다." 서버가 종료 신호를 받자마자 연결을 끊고 있다. 종료 전에 readiness를 내리고, 서버의 graceful shutdown(새 호출은 거절하고 진행 중인 호출은 끝낸 뒤 GOAWAY)을 쓴다. 클라이언트는 `UNAVAILABLE`에 재시도를 건다.

"`RESOURCE_EXHAUSTED: Received message larger than max`." 기본 수신 메시지 크기 상한은 4MB다. 목록 응답이 커진 것이다. 상한을 올리기 전에 페이지로 나누거나 스트리밍으로 바꿀 수 있는지 본다.

"`DEADLINE_EXCEEDED`가 늘었는데 서버 처리 시간은 짧다." 호출이 서버에 닿기 전에 기다리고 있을 수 있다. 연결 하나의 동시 스트림 상한에 걸려 클라이언트에서 대기 중이거나, 채널을 호출마다 새로 만들어 연결 맺는 데 시간을 쓰고 있다. 에러 메시지의 `LB pick` 시간과 `remote_addr`도 단서다.

"한 Pod만 바쁘다." 앞 절의 연결 쏠림이다. 클라이언트별 연결 수와 Pod별 호출 수(서버 인터셉터 지표)를 비교한다.

로그를 더 보고 싶으면 grpc-js는 환경 변수로 내부 추적을 켤 수 있다.

```bash
# 연결·로드 밸런싱·호출 단계를 자세히 찍는다 (운영에선 잠깐만)
GRPC_TRACE=channel,subchannel,round_robin GRPC_VERBOSITY=DEBUG node many.js inventory:50051
```

명령줄에서 서버를 부를 때는 grpcurl을 많이 쓴다. 서버가 reflection 서비스를 켜 두었으면 `.proto` 없이도 메서드 목록을 보고 JSON으로 요청을 보낼 수 있다(`grpcurl -plaintext localhost:50051 list`, `grpcurl -plaintext -d '{"id":150}' localhost:50051 shop.v1.OrderService/GetOrder`). 이 실습 컨테이너에는 grpcurl을 설치하지 못해 출력은 싣지 않았다. reflection은 내부 구조를 드러내니 운영의 외부 노출 포트에서는 끈다.

## 계약, 바이트, 연결

gRPC는 `.proto` 계약에서 코드를 만들고, 필드 이름 대신 번호를 쓴 작은 바이트를 HTTP/2 스트림에 실어 보낸다. 결과는 trailers의 `grpc-status`로 오고 HTTP 상태는 200이다. 기한은 호출 사슬을 따라 전달돼 모두 함께 멈춘다. 그리고 연결을 오래 쓰는 성질 때문에 L4 로드 밸런서는 연결이 생길 때 한 번밖에 고르지 못하니, L7 프록시나 클라이언트 쪽 분산, 연결 수명으로 호출 단위 분산을 따로 만들어야 한다.

## 면접에서 나올 만한 질문

### gRPC가 REST보다 빠른 이유는 무엇인가요?

메시지가 Protocol Buffers라 필드 이름 없이 번호와 값만 담겨 작고, 길이를 보고 건너뛰는 파싱이 빠르다. 전송은 HTTP/2라 연결 하나에 여러 호출을 동시에 실어 연결 비용이 적고 헤더도 압축된다. 다만 사람이 읽을 수 없고 HTTP 캐시를 쓰기 어렵다는 대가가 있다.

### Protocol Buffers에서 필드 번호를 바꾸면 안 되는 이유는요?

바이트에는 필드 이름 없이 번호만 들어가기 때문이다. 번호를 바꾸거나 지운 번호를 다른 필드에 다시 쓰면 옛 클라이언트가 새 값을 엉뚱한 필드로 읽는다. 이름은 바꿔도 되고, 지운 필드의 번호는 reserved로 막아 둔다.

### gRPC의 deadline은 일반 타임아웃과 무엇이 다른가요?

기한은 grpc-timeout 헤더로 서버에 전달되고, 지나면 서버 쪽 호출도 취소된다. 서버는 이를 보고 남은 일을 그만둘 수 있고, 다음 서비스를 부를 때 남은 기한을 그대로 넘겨 호출 사슬 전체가 함께 멈춘다. gRPC는 기본 기한이 없으니 모든 호출에 직접 줘야 한다.

### gRPC 에러는 HTTP 상태 코드로 오나요?

아니다. HTTP 상태는 거의 항상 200이고 결과는 trailers의 grpc-status(0~16)로 온다. 그래서 HTTP 상태만 세는 지표에서는 gRPC 에러가 보이지 않으니 grpc-status를 읽는 프록시나 서버 인터셉터로 에러율을 본다. 재시도는 UNAVAILABLE처럼 닿지 못한 경우에, DEADLINE_EXCEEDED는 멱등한 호출에만 건다.

### 쿠버네티스에서 gRPC 서비스의 부하가 한 Pod에 몰리는 이유와 해결책은요?

ClusterIP Service는 L4라 TCP 연결이 생길 때 한 번만 백엔드를 고르는데, gRPC는 HTTP/2 연결 하나를 오래 쓰며 모든 호출을 그 위로 보낸다. 해결은 호출 단위로 나누는 L7 프록시(Envoy, 서비스 메시), headless Service와 클라이언트 쪽 round_robin, 또는 서버의 max_connection_age로 연결을 주기적으로 새로 맺게 하는 것이다.

### 스트리밍 RPC는 언제 쓰나요?

결과가 시간에 따라 여러 번 나오거나(배송 상태, 로그 tail) 큰 데이터를 나눠 보내거나 받을 때, 양쪽이 계속 주고받을 때(채팅, 위치) 쓴다. 연결을 오래 붙잡으니 배포 때 끊긴다는 전제로 재연결과 이어 받기를 설계하고, 로드 밸런싱 쏠림도 더 심해진다는 점을 고려한다.

### gRPC와 GraphQL, REST는 어떻게 고르나요?

서비스 사이의 잦은 내부 호출, 여러 언어, 명확한 계약이 필요하면 gRPC다. 공개 API나 브라우저, 캐시와 도구 호환이 중요하면 REST다. 화면마다 필요한 데이터 모양이 크게 다른 프론트엔드에는 GraphQL이 맞다. 바깥은 REST나 GraphQL, 안쪽은 gRPC로 섞어 쓰는 경우가 많다.
