Node API의 p99 응답 시간이 몇 분에 한 번씩 튄다. 코드는 바뀐 게 없고 트래픽도 평소와 같다. 같은 서비스의 다른 Pod는 한도 512Mi에서 `OOMKilled`로 죽었는데, 로그에는 "heap out of memory"가 한 줄도 없다. 두 증상 모두 범인은 같다. 쓰지 않는 메모리를 대신 치워 주는 가비지 컬렉터(GC)가 언제, 얼마나 멈추고, 어디까지 메모리를 쓰도록 놔두는지를 몰랐다.

이 글은 GC가 쓰레기를 찾는 방식부터 시작해 V8의 세대별 수집을 `--trace-gc` 로그로 읽고, 힙 한도와 컨테이너 한도가 어긋날 때 무슨 일이 생기는지 cgroup으로 재현한다. 끝으로 JVM의 G1·ZGC와 Go의 `GOGC`·`GOMEMLIMIT`이 같은 문제를 어떻게 다르게 푸는지 실제 로그로 비교한다. 실습은 Ubuntu 컨테이너에서 Node 22.22, OpenJDK 21, Go 1.24, Python 3.13으로 했다.

이 주제의 다른 글: 참조가 새는 자리를 크롬 힙 스냅샷으로 찾는 법은 [자바스크립트 메모리 누수 찾기](/posts/js-memory-leak)에, 쿠버네티스 메모리 limits와 OOM kill 자체는 [requests와 limits](/posts/k8s-pod-resources)에 있다. 이 글은 그 사이, 런타임이 메모리를 어떻게 돌려받는지를 다룬다.

## 쓰레기를 찾는 두 가지 방법

GC가 할 일은 "이 객체를 앞으로 쓸 수 있는가"를 판단하는 것이다. 미래는 알 수 없으니 대신 쓸 수 없다는 게 확실한 것만 치운다. 방법은 크게 둘이다.

- **추적(tracing)**: 스택의 지역 변수, 전역 변수 같은 루트에서 출발해 참조를 따라가며 닿는 객체에 표시한다. 닿지 않은 것은 쓰레기다. V8, JVM, Go, .NET이 이쪽이다.
- **참조 카운팅(reference counting)**: 객체마다 "나를 가리키는 참조 수"를 들고 있다가 0이 되는 순간 바로 해제한다. CPython, Swift의 ARC, Rust의 `Rc`가 이쪽이다.

추적 방식은 "무엇을 쓰레기로 보느냐"의 기준이 루트에서 닿느냐라서, 쓰지 않는데 어딘가에서 붙잡혀 있는 객체는 치우지 못한다. 그게 메모리 누수다. 누수 이야기는 [메모리 누수 글](/posts/js-memory-leak)에 맡기고, 여기서는 치우는 쪽의 동작을 본다.

## 참조 카운팅은 즉시 치우지만 고리를 못 본다

CPython으로 둘 다 보면 차이가 선명하다. `__del__`은 객체가 실제로 해제될 때 불린다.

```python
import sys, gc

class Node:
    def __init__(self, name): self.name = name; self.peer = None
    def __del__(self): print("  freed", self.name)

a = Node("a")
print("refcount(a) =", sys.getrefcount(a) - 1)   # getrefcount 인자 몫 1을 뺀다
b = a
print("after b = a ->", sys.getrefcount(a) - 1)
del b
print("del a ->"); del a                          # 0이 되는 순간 바로 해제

print("cycle:")
x, y = Node("x"), Node("y")
x.peer, y.peer = y, x                             # 서로를 가리킨다
del x, y
print("  after del, nothing freed yet")
print("  gc.collect() found", gc.collect())
print("thresholds", gc.get_threshold())
```

```text
refcount(a) = 1
after b = a -> 2
del a ->
  freed a
cycle:
  after del, nothing freed yet
  freed x
  freed y
  gc.collect() found 9
thresholds (2000, 10, 10)
```

`del a` 바로 다음 줄에 `freed a`가 찍힌다. 참조 카운팅의 장점이 이것이다. 해제 시점이 예측 가능하고, 큰 멈춤 없이 일이 잘게 나뉜다. 파일 핸들을 `with` 없이 열어도 함수가 끝나면 대개 닫히는 게 이 덕분이다.

고리는 `del` 뒤에도 남아 있다가 `gc.collect()`에서야 풀린다. CPython은 고리만 따로 잡는 세대별 수집기를 하나 더 돌린다. `get_threshold()`의 첫 값은 "새로 만든 컨테이너 객체가 이만큼 늘면 0세대를 훑는다"는 기준이고, 3.13에서 찍어 보면 2000이다(3.12까지는 700이었다). `collect()`가 돌려준 9는 Node 두 개만이 아니라 그 속성 사전 같은 내부 객체까지 센 숫자다.

참조 카운팅에도 값이 있다. 참조를 복사할 때마다 카운터를 바꿔야 해서 멀티스레드에서는 원자적 연산이 필요하고(Python의 GIL이 오랫동안 이걸 지켜 왔다), 큰 객체 그래프가 한 번에 0이 되면 해제가 연쇄적으로 일어나 그 순간이 길어진다. Swift와 Rust는 고리를 GC 없이 `weak` 참조로 끊으라고 프로그래머에게 맡긴다.

## 표시하고 쓸고, 필요하면 모은다

추적 GC의 기본형은 표시-쓸기(mark-sweep)다. 루트에서 출발해 닿는 객체에 표시하고, 표시되지 않은 칸을 빈 칸 목록에 돌려준다. 아래 그림에서 다음을 누르면 할 일 목록(worklist)에 객체가 들어갔다 빠지며 표시가 번진다.

쓸기만 하면 빈 칸이 여기저기 흩어진다. 총 여유 공간은 충분한데 연속된 큰 칸이 없어서 큰 배열을 못 넣는 상태, 즉 단편화가 생긴다. 그래서 두 가지 변형이 있다.

- **표시-압축(mark-compact)**: 살아 있는 객체를 한쪽으로 밀어 붙인다. 단편화가 사라지지만 객체 주소가 바뀌니 가리키는 포인터를 전부 고쳐야 한다.
- **복사(copying)**: 공간을 둘로 나눠 한쪽에만 할당하다가, 차면 살아 있는 것만 반대쪽으로 복사하고 원래 쪽은 통째로 비운다. 비용이 살아 있는 객체 수에만 비례한다. 대신 메모리를 두 배로 잡아야 한다.

복사 방식의 "죽은 객체는 비용이 0"이라는 성질이 다음 절의 세대별 수집과 맞물린다.

## 대부분 금방 죽는다는 내기

요청 하나를 처리하면서 만드는 객체를 떠올려 보자. 파싱한 JSON, 중간 배열, 템플릿 문자열. 응답을 보내고 나면 전부 필요 없다. 반대로 커넥션 풀이나 캐시처럼 한번 살아남은 객체는 오래 산다. 이 관찰을 세대별 가설(generational hypothesis)이라고 부르고, 대부분의 런타임이 여기에 건다.

## --trace-gc 로그 한 줄 읽기

짧게 사는 객체를 200만 개 만들고 1%만 붙잡는 스크립트를 `--trace-gc`로 돌렸다.

```bash
# 객체 200만 개 중 1%만 배열에 남긴다
cat > gc1.js <<'EOF'
const keep = [];
for (let i = 0; i < 2_000_000; i++) {
  const o = { id: i, name: "user" + i, tags: [i, i + 1] };
  if (i % 100 === 0) keep.push(o);
}
console.log("kept", keep.length);
EOF
# GC가 돌 때마다 한 줄씩 찍는다
node --trace-gc gc1.js
```

## 힙이 한도에 닿으면

```bash
const cache = new Map(); let i = 0;
setInterval(() => {
  for (let k = 0; k < 20000; k++, i++) cache.set("k" + i, { id: i, body: "x".repeat(100) });
}, 5);
EOF

node --trace-gc --max-old-space-size=64 gc2.js
```

```text
FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory
```

패턴이 전형적이다. Mark-Compact 뒤의 값이 18.5 → 49.2 → 53.6 → 61.4로 오르고, 한도 근처에서 `(reduce)`로 77ms나 멈추며 마지막으로 쥐어짠 뒤 프로세스가 죽는다. 운영에서는 죽기 전 몇 분 동안 GC가 연달아 돌며 CPU를 먹고 응답이 느려지는 구간이 먼저 온다. "OOM 직전에 CPU가 튀었다"는 보고가 이 구간이다.

여기서 종료 코드가 134(SIGABRT)라는 것도 기억해 둔다. V8이 스스로 포기한 경우다.

## 힙 한도와 컨테이너 한도는 따로 논다

컨테이너 메모리 한도는 커널(cgroup)이 지키고, 힙 한도는 런타임이 지킨다. 둘이 어긋나면 죽는 방식이 달라진다. cgroup v1 메모리 그룹을 하나 만들어 같은 캐시 코드를 넣어 봤다.

```bash
# 실습용 메모리 cgroup을 만들고 한도를 256MiB로 건다 (cgroup v1)
sudo mkdir -p /sys/fs/cgroup/memory/v9gc
echo $((256*1024*1024)) | sudo tee /sys/fs/cgroup/memory/v9gc/memory.limit_in_bytes
# 셸 자신을 그룹에 넣고 node를 실행한다 (자식도 같은 그룹이 된다)
sudo sh -c 'echo $$ > /sys/fs/cgroup/memory/v9gc/cgroup.procs; exec node gc3.js'; echo "exit=$?"
# 커널이 이 그룹에서 몇 번 죽였는지
grep oom_kill /sys/fs/cgroup/memory/v9gc/memory.oom_control
```

`gc3.js`는 앞의 캐시 코드에 300ms마다 `process.memoryUsage()`를 찍는 줄만 더한 것이다. 한도만 바꿔 세 번 돌렸다.

```text
== cgroup 256MiB, no flag
Killed
exit=137
oom_kill 1

== cgroup 512MiB, no flag
FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory
exit=134

== cgroup 256MiB, --max-old-space-size=160
FATAL ERROR: CALL_AND_RETRY_LAST Allocation failed - JavaScript heap out of memory
exit=134
```

같은 코드가 256MiB에서는 커널에 죽고(137 = SIGKILL), 512MiB에서는 V8이 스스로 포기한다(134). 차이는 Node가 고른 힙 한도에 있다.

```text
limit 512MiB -> heap_size_limit 259 MiB
limit 256MiB -> heap_size_limit 259 MiB
no cgroup -> 2096
```

마지막 줄은 cgroup 밖, 메모리 16GB 호스트에서 잰 값(MiB)이다.

Node 22는 cgroup 한도를 읽어서 힙 한도를 줄인다. 512MiB 안에서는 그 절반쯤인 259MiB를 골라 여유가 남았다. 그런데 256MiB 안에서도 259MiB를 골랐다. 힙만으로 컨테이너를 꽉 채울 수 있다는 뜻이고, 힙 밖에서 쓰는 메모리(Buffer, 코드, 스레드 스택, 네이티브 모듈)까지 더하면 V8이 GC를 세게 돌기도 전에 커널이 먼저 죽인다. 그러면 힙 OOM 로그도, 스택 트레이스도 남지 않는다. 처음에 말한 "OOMKilled인데 로그에 아무것도 없다"가 이 경우다.

이 실습에서 하나 더 걸렸다. 이 컨테이너에는 `NODE_OPTIONS=--max-old-space-size=8192`가 환경 변수로 깔려 있어서, 처음 잰 값은 cgroup과 상관없이 8GB가 나왔다. 베이스 이미지나 Helm 차트에서 물려받은 `NODE_OPTIONS`가 한도 계산을 통째로 덮어쓰는 일은 흔하다. 컨테이너 안에서 실제 값을 찍어 보는 습관이 필요하다.

```bash
# 컨테이너 안에서 V8이 실제로 고른 힙 한도를 확인한다
node -e 'console.log(require("v8").getHeapStatistics().heap_size_limit/2**20, "MiB")'
# 런타임이 인식한 cgroup 메모리 한도 (Node 18.15+, 19.6+)
node -p 'process.constrainedMemory()/2**20'
echo "$NODE_OPTIONS"
```

정리하면 컨테이너에서는 힙 한도를 컨테이너 한도보다 확실히 작게, 대개 70~80% 선으로 직접 준다. 512Mi 컨테이너라면 `--max-old-space-size=384` 정도다. 그래야 메모리가 모자랄 때 V8이 먼저 GC를 세게 돌고, 그래도 안 되면 힙 OOM 로그를 남기고 죽는다. 원인을 아는 죽음이 낫다.

JVM은 오래전부터 이 문제를 겪어서 기본값이 보수적이다. 같은 512MiB 그룹에서 JDK 21의 결정을 찍어 봤다.

```bash
# 512MiB 그룹 안에서 JVM이 고른 힙 최대치와 GC 종류
java -XX:+PrintFlagsFinal -version | grep -E " MaxHeapSize | UseG1GC | UseSerialGC "
java -XX:MaxRAMPercentage=75 -XX:+PrintFlagsFinal -version | grep " MaxHeapSize "
```

```text
   size_t MaxHeapSize                              = 134217728                                 {product} {ergonomic}
     bool UseG1GC                                  = false                                     {product} {default}
     bool UseSerialGC                              = true                                      {product} {ergonomic}
   size_t MaxHeapSize                              = 402653184                                 {product} {ergonomic}
```

기본 `MaxRAMPercentage`가 25라서 512MiB의 4분의 1인 128MiB만 힙으로 쓴다. 더 놀라운 건 GC가 G1이 아니라 Serial로 바뀐 것이다. JVM은 메모리 1792MB 미만이거나 CPU가 2개 미만이면 "서버급 기계가 아니다"라고 보고 단일 스레드 Serial GC를 고른다. 작은 Pod에 자바를 올렸더니 GC 멈춤이 유난히 길다면 이것부터 의심한다. 보통 `-XX:MaxRAMPercentage=75`와 `-XX:+UseG1GC`를 명시한다.

얼마나 차이가 나는지 쟀다. 요청마다 캐시 항목 50개를 새 객체로 바꿔 넣는 HTTP 서버를 띄우고, 캐시에 미리 넣어 둔 객체 수(`LIVE`)만 바꿔 8초 동안 동시 8개로 요청을 보냈다.

```text
LIVE=0       reqs=55464 p50=0.90ms p99=3.98ms p99.9=8.10ms  max=26.5ms
LIVE=3000000 reqs=32811 p50=1.52ms p99=8.97ms p99.9=19.44ms max=66.5ms
```

살아 있는 객체가 300만 개가 되자 p99와 p99.9가 두 배 넘게 뛰었다. 같은 조건으로 `--trace-gc`를 켜 부하 구간을 보면 Mark-Compact보다 Scavenge가 문제였다.

```text
# LIVE=0
[11069:0x84d2000]     5657 ms: Scavenge 22.7 (42.7) -> 10.2 (42.7) MB, pooled: 0 MB, 2.11 / 0.00 ms  (average mu = 0.997, current mu = 0.997) task;
# LIVE=3000000
[10819:0x293d6000]     4264 ms: Scavenge 555.1 (581.3) -> 544.8 (583.3) MB, pooled: 0 MB, 9.89 / 0.00 ms  (average mu = 0.762, current mu = 0.765) task;
```

young GC 한 번이 2ms 안팎에서 4~19ms로 길어졌고, mu는 0.997에서 0.762로 떨어졌다. 시간의 4분의 1을 GC가 썼다는 뜻이다. old에 있는 거대한 Map이 young 객체를 계속 가리키게 되니(앞 그림의 다섯 번째 단계), Scavenge마다 기억 집합을 훑고 살아남은 객체를 복사하는 양이 늘었다. "GC 튜닝" 이전에 오래 사는 자료 구조에 새 객체를 계속 갈아 끼우는 코드 모양을 의심해야 하는 이유다. 꼬리 지연을 어떻게 재고 읽는지는 [꼬리 지연](/posts/tail-latency) 글에서 따로 다룬다.

런타임들은 멈춤을 줄이려고 같은 방향으로 갔다. 표시를 앱과 동시에(concurrent) 하거나 잘게 나눠(incremental) 하고, 앱이 표시 중에 참조를 바꾸면 쓰기 장벽으로 GC에 알린다. 멈춤이 짧아지는 대신 장벽 비용만큼 처리량이 조금 줄고, GC 스레드가 CPU를 나눠 쓴다. 지연과 처리량, 메모리 셋 중 두 개를 고르는 문제다.

## JVM의 G1과 ZGC

JVM은 GC를 골라 쓸 수 있다. JDK 9부터 기본인 G1은 힙을 같은 크기의 영역(region)으로 나누고, 쓰레기가 많은 영역부터 골라 치우며 목표 멈춤 시간(`MaxGCPauseMillis`, 기본 200ms)을 맞추려 한다. 40MB를 붙잡고 256바이트 배열을 300만 개 만드는 프로그램으로 봤다.

```bash
# G1로 돌리고 GC마다 한 줄씩 찍는다
java -Xmx256m -XX:+UseG1GC -Xlog:gc Alloc
```

```text
[0.006s][info][gc] Using G1
[0.140s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 14M->13M(216M) 19.993ms
[0.153s][info][gc] GC(1) Pause Young (Normal) (G1 Evacuation Pause) 21M->21M(216M) 6.593ms
[0.171s][info][gc] GC(2) Pause Young (Normal) (G1 Evacuation Pause) 34M->34M(216M) 14.197ms
[0.190s][info][gc] GC(3) Pause Young (Normal) (G1 Evacuation Pause) 52M->41M(216M) 5.161ms
```

G1의 young GC는 앱을 멈추고(Pause Young) 살아 있는 객체를 다른 영역으로 옮긴다(Evacuation). 5~20ms 멈췄다. ZGC는 객체를 옮기는 일까지 앱과 동시에 한다.

```bash
# 세대별 ZGC (JDK 21에서는 플래그가 필요하고, JDK 23부터 기본이다)
java -Xmx256m -XX:+UseZGC -XX:+ZGenerational -Xlog:gc+phases Alloc | grep Pause
```

```text
[0.714s][info][gc,phases] GC(0) Y: Pause Mark Start (Major) 0.028ms
[0.724s][info][gc,phases] GC(0) Y: Pause Mark End 0.020ms
[0.735s][info][gc,phases] GC(0) Y: Pause Relocate Start 0.028ms
[0.752s][info][gc,phases] GC(0) O: Pause Mark End 0.025ms
[0.782s][info][gc,phases] GC(0) O: Pause Relocate Start 0.026ms
```

멈춤이 0.02ms 단위다. 단계 경계에서 잠깐 맞추기만 하고 나머지는 동시에 한다. 대신 읽기 장벽(객체를 읽을 때마다 도는 검사) 비용과 GC 스레드가 쓰는 CPU가 있다. 힙이 크고 지연에 민감한 서비스는 ZGC, 일반적인 웹 서비스는 G1, 작은 배치는 처리량이 좋은 Parallel이 흔한 선택이다.

## Go에는 손잡이가 둘 있다

Go의 GC는 세대를 나누지 않고 객체를 옮기지도 않는 동시 표시-쓸기다. 그 대신 "언제 GC를 시작할지"를 두 값으로 정한다.

- `GOGC`(기본 100): 지난 GC가 끝났을 때 살아 있던 힙의 몇 %만큼 더 늘면 다음 GC를 시작할지. 100이면 살아 있는 힙의 두 배가 목표다.
- `GOMEMLIMIT`(Go 1.19+): 런타임 전체 메모리의 소프트 한도. 여기에 가까워지면 `GOGC`와 상관없이 GC를 앞당긴다.

살아 있는 데이터 약 40MB를 쥐고 짧은 객체를 200만 개 만드는 프로그램을 `GODEBUG=gctrace=1`로 돌렸다.

```bash
# 기본값, GC를 덜 하게, 한도만으로 운영
GODEBUG=gctrace=1 ./gcdemo
GOGC=400 GODEBUG=gctrace=1 ./gcdemo
GOGC=off GOMEMLIMIT=60MiB GODEBUG=gctrace=1 ./gcdemo
```

```text
== GOGC=100
gc 11 @0.286s 4%: 0.083+5.9+0.082 ms clock, 0.33+0/4.2/1.7+0.33 ms cpu, 75->86->51 MB, 88 MB goal, 0 MB stacks, 0 MB globals, 4 P
NumGC=11 HeapAlloc=94MB
== GOGC=400
gc 2 @0.022s 10%: 0.015+19+0.089 ms clock, 0.062+2.1/11/0.17+0.35 ms cpu, 88->162->114 MB, 92 MB goal, 0 MB stacks, 0 MB globals, 4 P
NumGC=2 HeapAlloc=480MB
== GOGC=off GOMEMLIMIT=60MiB
gc 46 @0.715s 10%: 0.061+4.6+0.004 ms clock, 0.24+0.009/4.6/0.037+0.019 ms cpu, 48->48->40 MB, 53 MB goal, 0 MB stacks, 0 MB globals, 4 P
NumGC=46 HeapAlloc=50MB
```

한 줄을 읽는 법은 이렇다. `@0.286s`는 시작 후 시각, `4%`는 지금까지 GC가 쓴 CPU 비율이다. `0.083+5.9+0.082 ms clock`은 앞뒤 두 숫자가 멈춘 시간(쓸기 마무리, 표시 마무리)이고 가운데가 앱과 동시에 표시한 시간이다. `75->86->51 MB`는 GC 시작 때 힙, 끝날 때 힙, 그중 살아 있는 힙이고, `88 MB goal`이 이번 목표였다.

세 결과가 트레이드오프를 그대로 보여 준다. `GOGC=400`은 GC를 두 번만 하고 힙을 480MB까지 키웠다. 메모리를 CPU와 바꾼 것이다. `GOMEMLIMIT=60MiB`는 힙을 50MB 근처에 묶었지만 GC를 46번 돌았다. 한도를 살아 있는 데이터에 너무 바짝 붙이면 GC가 쉬지 않고 도는 상태가 되는데, Go 런타임은 이때 GC CPU를 대략 50%로 제한해 앱이 완전히 멈추는 것은 막는다. 대신 메모리는 한도를 넘어간다. 컨테이너에서는 보통 `GOGC`는 그대로 두고 `GOMEMLIMIT`만 컨테이너 한도의 80~90%로 준다.

목표 힙을 직접 계산해 보자. 실제 런타임은 스택과 전역 변수도 더하지만 여기서는 힙만 본다.

## 메모리가 이상할 때 보는 순서

증상별로 처음 볼 것을 정리하면 이렇다.

**Pod가 OOMKilled(137)로 재시작한다.** 런타임 로그에 힙 OOM이 없으면 힙 한도가 컨테이너 한도보다 크거나, 힙 밖 메모리가 크다는 뜻이다. 먼저 컨테이너 안에서 힙 한도를 찍고(`heap_size_limit`, `MaxHeapSize`), 힙 한도를 컨테이너의 70~80%로 낮춘다. Go라면 `GOMEMLIMIT`을 준다. Node에서 `Buffer`나 스트림을 많이 쓰면 `process.memoryUsage()`의 `external`, `arrayBuffers`가 큰지 본다.

**RSS가 계단처럼 오르고 내려오지 않는다.** GC 로그에서 Mark-Compact 뒤 값("after")이 계속 오르면 살아 있는 데이터가 늘고 있다. 누수거나 상한 없는 캐시다. 힙 스냅샷 비교는 [메모리 누수 글](/posts/js-memory-leak)의 순서를 따른다. "after"는 일정한데 RSS만 높다면 런타임이 받아 둔 메모리를 OS에 천천히 돌려주는 것일 수 있다. 그건 누수가 아니다.

**p99가 주기적으로 튄다.** GC 로그의 멈춘 시간과 지연 그래프의 시각을 맞춰 본다. Node는 `--trace-gc`, JVM은 `-Xlog:gc*:file=gc.log`, Go는 `GODEBUG=gctrace=1`. 겹치면 할당량을 줄이거나(요청마다 큰 객체 복사, 거대한 JSON 파싱), 오래 사는 구조에 새 객체를 갈아 끼우는 코드를 고친다. 그다음에 GC 종류나 young 크기를 바꾼다.

**CPU가 높은데 앱 코드는 한가하다.** mu 값이 떨어지거나 Go의 `%`가 높으면 GC가 CPU를 먹고 있다. 힙에 여유가 거의 없을 때 생긴다. 한도를 올리거나 살아 있는 데이터를 줄인다.

흔한 실수도 몇 가지 있다. 코드에서 `global.gc()`나 `System.gc()`를 직접 부르면 런타임의 판단을 덮어 오히려 긴 전체 GC를 부른다. `-Xmx`를 컨테이너 한도와 같게 주면 메타스페이스, 스레드 스택, 다이렉트 버퍼 몫이 없어 커널에 죽는다. 그리고 GC 튜닝 플래그를 먼저 만지는 것. 대부분의 경우 답은 할당을 줄이는 코드 쪽에 있다.

## 치우는 비용은 결국 누가 내나

GC는 메모리 관리를 공짜로 만들어 주지 않는다. 비용을 앱 대신 런타임이 내고, 그 비용이 멈춤과 CPU와 여분의 메모리로 나타날 뿐이다. 세대별 수집은 "대부분 금방 죽는다"는 내기로 그 비용을 줄이고, 동시 수집은 멈춤을 CPU로 바꾸며, 컨테이너에서는 런타임이 아는 한도와 커널이 지키는 한도를 맞춰 줘야 한다. 다음에 GC 로그를 열면 멈춘 시간, 살아남은 크기의 추세, 한도까지의 거리 세 가지를 먼저 본다.

## 면접에서 나올 만한 질문

### 추적 GC와 참조 카운팅의 차이는 무엇인가요?

추적 GC는 루트에서 닿는 객체를 표시하고 나머지를 치우고, 참조 카운팅은 객체마다 가리키는 수를 세다가 0이 되면 바로 해제한다. 참조 카운팅은 해제 시점이 예측 가능하고 큰 멈춤이 없지만, 서로를 가리키는 고리를 해제하지 못하고 참조를 바꿀 때마다 카운터 비용이 든다. 그래서 CPython은 고리를 잡는 수집기를 따로 돌리고, Swift와 Rust는 weak 참조로 고리를 끊게 한다.

### 세대별 GC는 왜 효과가 있나요?

대부분의 객체가 만들어진 직후 죽는다는 관찰 때문이다. young 영역을 작게 두고 자주 복사 방식으로 치우면 비용이 살아남은 객체 수에만 비례해서, 죽은 객체가 많을수록 싸다. 오래 산 객체는 old로 승격해 가끔만 본다. 대신 old가 young을 가리키는 참조를 쓰기 장벽으로 기록해야 하고, 이 기록이 많아지면 young GC도 느려진다.

### 컨테이너에서 Node 앱이 OOMKilled로 죽는데 힙 OOM 로그가 없습니다. 왜 그런가요?

V8이 GC를 세게 돌기 전에 컨테이너 메모리 한도에 먼저 닿아 커널이 SIGKILL로 죽인 것이다. 힙 한도가 컨테이너 한도에 비해 크거나, Buffer와 네이티브 메모리처럼 힙 밖 사용량이 크면 생긴다. 컨테이너 안에서 `heap_size_limit`과 `NODE_OPTIONS`를 확인하고, `--max-old-space-size`를 한도의 70~80%로 직접 준다. 그러면 힙 OOM(종료 코드 134)과 로그가 남아 원인을 알 수 있다.

### GC 멈춤은 서비스 지표에서 어떻게 보이나요?

평균이나 p50에는 거의 안 보이고 p99, p99.9 같은 꼬리 지연에 나타난다. 멈춘 동안 도착한 요청만 그 시간만큼 늦기 때문이다. 확인은 GC 로그의 멈춘 시각과 지연 그래프를 맞춰 보는 것으로 한다. 줄이는 방법은 할당 자체를 줄이는 것이 먼저고, 그다음이 동시 수집 GC로 바꾸는 것이다.

### JVM을 작은 컨테이너에 올릴 때 조심할 점은요?

JDK 10 이후 JVM은 컨테이너 한도를 읽지만 기본 `MaxRAMPercentage`가 25라서 힙을 너무 작게 잡는다. 메모리가 1792MB 미만이거나 CPU가 2개 미만이면 G1 대신 Serial GC를 고르기도 한다. 그래서 `MaxRAMPercentage`를 75 정도로, GC는 명시적으로 지정한다. 반대로 `-Xmx`를 컨테이너 한도와 같게 주면 메타스페이스와 스레드 스택 몫이 없어 커널에 죽는다.

### Go의 GOGC와 GOMEMLIMIT은 어떻게 다르게 쓰나요?

`GOGC`는 살아 있는 힙 대비 얼마나 더 늘면 GC할지 정하는 비율이고, `GOMEMLIMIT`은 전체 메모리의 소프트 한도다. `GOGC`를 올리면 GC는 덜 하지만 메모리를 더 쓴다. 컨테이너에서는 `GOGC`는 두고 `GOMEMLIMIT`을 한도의 80~90%로 주는 방식이 흔하다. `GOGC=off`를 한도 없이 쓰면 GC가 돌지 않아 결국 커널에 죽는다.

### 동시(concurrent) GC는 공짜인가요?

아니다. 앱이 도는 중에 표시하려면 참조가 바뀔 때마다 GC에 알려 주는 쓰기 장벽(ZGC는 읽기 장벽까지)이 필요하고, 그만큼 앱 코드가 조금 느려진다. GC 스레드도 CPU를 나눠 쓴다. 그래서 멈춤은 줄지만 처리량과 CPU 사용량이 손해를 본다. 지연에 민감한 서비스에서는 그 값을 낼 만하고, 처리량이 중요한 배치는 멈춤이 길어도 효율적인 GC가 낫다.
