[Insert Interval](https://leetcode.com/problems/insert-interval/)은 LeetCode 57번이다. 이미 정렬돼 있고 서로 겹치지 않는 구간 목록에 새 구간 하나를 넣는다. 넣고 나서도 목록은 정렬돼 있어야 하고 겹치는 구간이 없어야 한다.

구간 문제를 푸는 공통 틀(겹침 판정 한 줄, 왜 정렬하나, 닫힌 구간과 열린 구간)은 [구간 문제 패턴](/posts/interval-problems-pattern)에 정리했다. 이 글에서는 그 틀을 이 문제 하나에 깊게 적용한다. 풀이 네 가지를 느린 것부터 보고, 실제로 틀리는 코드 조각과 면접관이 이어서 묻는 변형까지 간다. 코드는 Node.js 22, Python 3.13, Java 21에서 돌렸다.

## 정렬된 달력에 약속 하나를 끼운다

입력은 두 개다. `intervals`는 `[start, end]` 쌍의 목록이고, 시작 기준으로 정렬돼 있으며 서로 겹치지 않는다. `newInterval`은 넣을 구간 하나다. 새 구간을 넣고, 겹치는 구간은 합쳐서, 정렬되고 겹치지 않는 목록을 돌려준다.

풀이에 영향을 주는 조건은 이렇다.

- 구간 수는 최대 10^4다. 정렬 O(n log n)도 통과하지만, 입력이 이미 정렬돼 있으니 면접에서는 O(n)을 기대한다.
- 목록이 비어 있을 수 있다. 이때 답은 새 구간 하나다.
- 구간은 닫힌 구간이다. `[1, 5]`에 `[5, 7]`을 넣으면 끝점 5가 닿으므로 `[1, 7]`로 합친다.

"정렬돼 있다"는 말이 이 문제의 전부라고 봐도 된다. 같은 일을 정렬 안 된 입력에서 하는 게 [Merge Intervals](/posts/leetcode-merge-intervals)이고, 이 문제는 거기서 정렬 단계를 빼고 한 번 훑는 쪽으로 다듬은 것이다.

## 손으로 한 번 넣어 본다

이 글에서 계속 쓸 예시다.

```text
intervals   = [1,2] [4,5] [7,9] [11,12]
newInterval = [5,8]
```

수직선에 그려 보면 이렇다.

```text
 0    2    4    6    8   10   12
 |----|----|----|----|----|----|
  [==]   [=]   [===]     [=]        기존
          [=======]                 새 구간 [5,8]
```

`[1, 2]`는 2에서 끝나는데 새 구간은 5에서 시작한다. 완전히 앞이라 그대로 둔다. `[4, 5]`는 5에서 끝나고 새 구간이 5에서 시작하니 끝점이 닿는다. 합친다. `[7, 9]`는 7에서 시작하는데 새 구간이 8까지 가니 겹친다. 또 합친다. `[11, 12]`는 11에서 시작하는데 합친 구간은 9에서 끝난다. 완전히 뒤다.

합쳐진 구간의 시작은 겹친 것들 중 가장 이른 시작 4, 끝은 가장 늦은 끝 9다. 답은 `[1,2] [4,9] [11,12]`다.

손으로 해 보면 구간들이 세 무리로 나뉜다는 게 보인다. 새 구간보다 완전히 앞, 새 구간과 겹치는 것, 완전히 뒤. 그리고 정렬돼 있으니 이 세 무리는 목록에서 섞이지 않고 앞, 가운데, 뒤로 이어져 있다. 이 관찰이 가장 좋은 풀이가 된다. 그 전에 먼저 떠오르는 방법부터 본다.

## 붙이고 정렬한 뒤 합친다

가장 먼저 떠오르는 건 이미 아는 문제로 바꾸는 것이다. 새 구간을 목록 끝에 붙이면 "정렬 안 된 구간 목록을 합쳐라"가 된다. 그건 Merge Intervals 그대로다.

```js
function insert(intervals, newInterval) {
  const a = [...intervals, newInterval].sort((x, y) => x[0] - y[0]); // 붙이고 시작 순으로 정렬
  const out = [];
  for (const [s, e] of a) {
    const last = out.at(-1);
    if (last && s <= last[1]) last[1] = Math.max(last[1], e); // 겹치면 끝을 늘린다
    else out.push([s, e]);                                   // 떨어져 있으면 새로 시작
  }
  return out;
}
```

예시를 넣으면 `[[1,2],[4,9],[11,12]]`가 나온다. 합치기 루프가 왜 "마지막 결과 하나와만 비교"해도 되는지는 패턴 글의 "왜 정렬부터 하나"에서 증명했다.

시간은 정렬 때문에 O(n log n), 공간은 정렬용 복사본과 결과로 O(n)이다. 이 풀이의 장점은 틀리기 어렵다는 것이다. 합치기 코드를 이미 외우고 있다면 3분이면 쓴다. 면접에서 일단 정답을 확보해 두는 용도로는 나쁘지 않다.

한계는 입력의 성질을 버렸다는 것이다. 기존 n개는 이미 정렬돼 있고, 순서가 틀린 건 새로 붙인 하나뿐이다. 하나 때문에 전체를 다시 정렬하는 건 낭비다. 면접관은 거의 틀림없이 "입력이 정렬돼 있다는 걸 썼나요?"라고 묻는다.

## 제자리를 찾아 끼우고 합친다

정렬이 낭비라면 정렬 대신 끼워 넣으면 된다. 정렬된 배열에 값 하나를 넣는 건 삽입 정렬의 한 단계다. 새 구간의 시작보다 큰 시작을 가진 첫 구간 앞에 넣으면 정렬이 유지된다.

```js
function insert(intervals, newInterval) {
  const a = [];
  let placed = false;
  for (const iv of intervals) {
    if (!placed && newInterval[0] < iv[0]) { a.push(newInterval); placed = true; } // 제자리를 찾았다
    a.push(iv);
  }
  if (!placed) a.push(newInterval); // 모두보다 늦게 시작하면 맨 뒤
  // 이제 a는 시작 순으로 정렬돼 있다. 합치기는 앞 풀이와 같다
  const out = [];
  for (const [s, e] of a) {
    const last = out.at(-1);
    if (last && s <= last[1]) last[1] = Math.max(last[1], e);
    else out.push([s, e]);
  }
  return out;
}
```

끼우기 한 번, 합치기 한 번으로 둘 다 O(n)이다. 정렬이 사라졌으니 전체 O(n)이 됐다. 공간은 끼운 배열과 결과로 O(n)이다.

`newInterval[0] < iv[0]`의 부등호는 `<=`로 바꿔도 답이 같다. 시작이 같은 두 구간은 어느 쪽이 먼저 와도 합치기에서 하나로 묶인다. 합치기 루프는 시작 순서만 지켜지면 같은 시작끼리의 순서를 따지지 않는다.

이 풀이는 시간으로는 이미 최적이다. 아쉬운 건 배열을 두 번 훑고, 중간 배열 `a`를 하나 더 만든다는 것이다. 그리고 합치기 루프가 기존 구간끼리도 매번 비교하는데, 기존 구간끼리는 겹치지 않는다는 걸 이미 알고 있다. 비교가 필요한 건 새 구간 근처뿐이다.

## 앞, 겹침, 뒤 세 덩어리로 한 번에 훑는다

손으로 풀 때 본 세 무리를 코드로 옮긴다. 정렬돼 있으니 세 무리가 목록에서 차례로 이어진다. 인덱스 `i` 하나로 앞에서부터 훑으며 무리가 바뀌는 지점에서 다음 `while`로 넘어간다.

1. 끝이 새 구간의 시작보다 앞인 구간(`end < s`)은 완전히 앞이다. 결과에 그대로 옮긴다.
2. 남은 구간 중 시작이 새 구간의 끝 이하인 것(`start <= e`)은 겹친다. 새 구간을 늘린다. 시작은 더 이른 쪽, 끝은 더 늦은 쪽으로.
3. 늘린 새 구간을 결과에 넣는다.
4. 나머지는 완전히 뒤다. 그대로 옮긴다.

```js
function insert(intervals, newInterval) {
  const out = [];
  let [s, e] = newInterval;         // 받은 배열을 고치지 않으려고 값을 풀어 둔다
  let i = 0;
  const n = intervals.length;
  while (i < n && intervals[i][1] < s) out.push(intervals[i++]); // 1. 완전히 앞
  while (i < n && intervals[i][0] <= e) {                        // 2. 겹친다
    s = Math.min(s, intervals[i][0]);
    e = Math.max(e, intervals[i][1]);
    i++;
  }
  out.push([s, e]);                                               // 3. 합친 구간
  while (i < n) out.push(intervals[i++]);                         // 4. 완전히 뒤
  return out;
}
```

두 번째 `while`의 조건이 왜 `intervals[i][0] <= e` 하나뿐인지가 이 코드에서 가장 중요한 부분이다. 구간 `[a, b]`와 새 구간 `[s, e]`가 겹치는 조건은 `a <= e`이면서 `s <= b`다. 그런데 첫 `while`을 빠져나왔다는 건 `b < s`가 거짓이라는 뜻, 즉 `s <= b`가 이미 성립한다. 그리고 목록이 정렬돼 있어 뒤로 갈수록 끝도 커지니, 한 번 성립한 `s <= b`는 그 뒤 구간에서도 계속 성립한다. 남은 조건만 보면 된다.

두 번째 `while` 안에서 `e`가 늘어나는 것도 중요하다. `[7, 9]`를 합치는 순간 `e`가 8에서 9로 늘고, 다음 구간이 9 이하에서 시작하면 그것도 합쳐진다. 새 구간이 사슬처럼 여러 구간을 삼키는 경우가 이렇게 처리된다.

시간은 O(n)이다. `i`가 0에서 n까지 한 방향으로만 움직이고, 각 구간은 세 `while` 중 정확히 하나에서 한 번 처리된다. 공간은 결과 배열을 빼면 O(1)이다. 변수 `s`, `e`, `i`뿐이다. 결과 배열은 문제가 새 목록을 돌려 달라고 하니 어느 풀이든 O(n)이 필요하다.

이 풀이가 면접에서 기대하는 답이다. 정렬을 하지 않고, 배열을 한 번만 훑고, 비교도 필요한 만큼만 한다. 기존 구간끼리는 한 번도 비교하지 않는다.

## 새 구간이 떨어질 수 있는 자리

세 덩어리 풀이를 믿으려면, 새 구간이 어디에 떨어지든 같은 코드가 맞는다는 걸 확인해야 한다. 나는 처음에 "새 구간이 빈자리에 들어가는 경우"를 따로 처리해야 하는 줄 알았다. 그럴 필요가 없다. 겹치는 덩어리가 비어 있을 뿐이다.

기존 목록을 `[2,3] [6,7] [10,11]`로 두고 새 구간을 여러 자리에 넣어 봤다. 오른쪽 숫자는 앞, 겹침, 뒤 덩어리에 들어간 구간 수다.

```text
새 구간    결과                              앞 겹침 뒤
[0,1]     [0,1] [2,3] [6,7] [10,11]          0   0   3
[12,13]   [2,3] [6,7] [10,11] [12,13]        3   0   0
[4,5]     [2,3] [4,5] [6,7] [10,11]          1   0   2
[6,6]     [2,3] [6,7] [10,11]                1   1   1
[4,6]     [2,3] [4,7] [10,11]                1   1   1
[3,10]    [2,11]                             0   3   0
[0,20]    [0,20]                             0   3   0
```

모양별로 보면 이렇다.

- 모두보다 앞이나 뒤: 앞 덩어리나 뒤 덩어리가 전부다. 겹침 덩어리가 비어 있어서 새 구간이 그대로 들어간다.
- 빈자리(`[4, 5]`): 역시 겹침이 0개다. 첫 `while`이 `[2, 3]`에서 멈추고 두 번째 `while`은 `[6, 7]`의 시작 6이 5보다 커서 한 번도 돌지 않는다. 새 구간이 정확히 그 자리에 들어간다.
- 한 구간 안(`[6, 6]`): 겹침이 1개고, 합친 결과가 원래 구간 `[6, 7]`과 같다. 목록이 바뀌지 않는다.
- 한쪽만 걸침(`[4, 6]`): 시작은 새 구간의 4, 끝은 기존 구간의 7을 가져온다. `Math.min`과 `Math.max`가 각각 한 번씩 일한다.
- 양 끝이 닿으며 여러 개 삼킴(`[3, 10]`): 3은 `[2, 3]`의 끝에, 10은 `[10, 11]`의 시작에 닿는다. 닫힌 구간이라 셋 다 합쳐져 `[2, 11]`이 된다.
- 전부 덮음(`[0, 20]`): 새 구간이 더 넓어서 기존 구간 셋이 모두 사라진다.

경우가 일곱 가지인데 코드는 하나다. 모양을 하나씩 if로 나누는 대신, 덩어리 크기가 0일 수 있다는 걸 받아들이면 경우 나누기가 사라진다. 패턴 글에서 겹침 판정을 "겹치지 않는 두 경우를 뒤집는다"로 정리한 것과 같은 생각이다.

손으로 고른 일곱 개만으로는 불안해서 무작위로도 확인했다. 정렬되고 겹치지 않는 목록을 0~6개짜리로 만들고 새 구간을 아무 데나 놓는 입력 2만 개에서, 이 글의 네 풀이가 모두 같은 결과를 냈다. 붙이고 정렬하는 풀이는 틀리기 어려워서 기준 답으로 쓰기 좋다. 면접 연습을 할 때도 느린 풀이를 기준 삼아 빠른 풀이를 무작위 입력으로 대조해 보는 습관이 경계 실수를 많이 잡아 준다.

## 경계를 이분 탐색으로 찾는다

세 덩어리 풀이를 다시 보면, 첫 번째 `while`과 두 번째 `while`이 하는 일은 결국 "경계 두 개 찾기"다. 앞 덩어리가 끝나는 곳과 겹치는 덩어리가 끝나는 곳. 정렬된 배열에서 경계를 찾는 건 [이분 탐색](/posts/binary-search)이 잘하는 일이다.

- `left`: 끝이 s 이상인 첫 구간. 그 앞은 모두 완전히 앞이다.
- `right`: 시작이 e보다 큰 첫 구간. 거기서부터 뒤는 모두 완전히 뒤다.
- `left`부터 `right - 1`까지가 겹치는 구간이다. 이 범위가 비어 있지 않으면 시작은 `intervals[left][0]`과 s 중 작은 값, 끝은 `intervals[right - 1][1]`과 e 중 큰 값이다.

구간들이 정렬되고 겹치지 않으니 시작 목록도, 끝 목록도 각각 증가한다. 그래서 "끝이 s보다 작은가"와 "시작이 e 이하인가"는 둘 다 앞쪽에서 참이다가 어느 지점부터 거짓이 되는 단조 조건이다. 이분 탐색을 쓸 수 있는 조건이 맞다.

```js
function insert(intervals, newInterval) {
  const [s, e] = newInterval;
  const n = intervals.length;
  let lo = 0, hi = n;                       // left: 끝이 s 이상인 첫 구간
  while (lo < hi) {
    const m = (lo + hi) >> 1;
    if (intervals[m][1] < s) lo = m + 1; else hi = m;
  }
  const left = lo;
  lo = left; hi = n;                        // right: 시작이 e보다 큰 첫 구간 (left부터 찾으면 된다)
  while (lo < hi) {
    const m = (lo + hi) >> 1;
    if (intervals[m][0] <= e) lo = m + 1; else hi = m;
  }
  const right = lo;
  let ns = s, ne = e;
  if (left < right) {                       // 겹치는 구간이 하나라도 있으면 늘린다
    ns = Math.min(s, intervals[left][0]);
    ne = Math.max(e, intervals[right - 1][1]);
  }
  return [...intervals.slice(0, left), [ns, ne], ...intervals.slice(right)];
}
```

예시에서 따라가면 `left`는 1(`[4, 5]`, 끝 5가 5 이상), `right`는 3(`[11, 12]`, 시작 11이 8보다 크다)이다. 겹치는 범위는 1번과 2번이고, 합친 구간은 `[min(5, 4), max(8, 9)]` = `[4, 9]`다. 아래 그림은 두 번의 이분 탐색이 경계를 좁혀 가는 과정이다.

붙이고 정렬하는 풀이보다 네 배쯤 빠르지만, 세 덩어리 풀이와는 큰 차이가 없다. 둘 다 결과 배열을 만드는 데 시간을 쓰기 때문이다.

그럼 이 풀이는 언제 의미가 있나. 결과를 새로 만들지 않아도 될 때다. 구간을 배열 대신 균형 이진 탐색 트리(Java의 `TreeMap`, C++의 `std::map`)에 담아 두고 계속 넣는다면, 경계 찾기 O(log n)과 겹친 k개 지우기 O(k log n)만으로 끝난다. 이 이야기는 아래 변형에서 다시 한다. LeetCode 채점 기준으로는 세 덩어리 풀이와 같은 O(n)이고, 코드가 길고 경계 실수 여지가 크다. 면접에서 "더 빠르게 할 수 있나"라고 물으면 이분 탐색으로 경계는 O(log n)에 찾지만 결과를 만드는 비용 때문에 O(n)이 하한이라고 설명하는 데 쓴다.

## Python과 Java로 옮기기

가장 좋은 풀이인 세 덩어리 풀이를 옮긴다.

```python
from typing import List


class Solution:
    def insert(self, intervals: List[List[int]], newInterval: List[int]) -> List[List[int]]:
        out = []
        s, e = newInterval          # 받은 리스트를 고치지 않으려고 풀어 둔다
        i, n = 0, len(intervals)
        while i < n and intervals[i][1] < s:     # 1. 완전히 앞
            out.append(intervals[i])
            i += 1
        while i < n and intervals[i][0] <= e:    # 2. 겹친다
            s = min(s, intervals[i][0])
            e = max(e, intervals[i][1])
            i += 1
        out.append([s, e])
        out.extend(intervals[i:])                # 3. 완전히 뒤
        return out
```

Python 3.10부터 `bisect` 모듈이 `key` 인자를 받아서, 이분 탐색 풀이도 몇 줄로 줄어든다. `bisect_left`는 "이 값 이상이 처음 나오는 자리", `bisect_right`는 "이 값보다 큰 것이 처음 나오는 자리"를 준다. 위 JS 코드의 `left`, `right` 정의와 정확히 맞는다.

```python
from bisect import bisect_left, bisect_right


def insert_bisect(intervals, new):
    s, e = new
    left = bisect_left(intervals, s, key=lambda iv: iv[1])     # 끝이 s 이상인 첫 칸
    right = bisect_right(intervals, e, key=lambda iv: iv[0])   # 시작이 e보다 큰 첫 칸
    if left < right:
        s = min(s, intervals[left][0])
        e = max(e, intervals[right - 1][1])
    return intervals[:left] + [[s, e]] + intervals[right:]
```

```text
[[1, 2], [4, 9], [11, 12]] [[1, 2], [4, 9], [11, 12]]
```

예시를 두 함수에 넣은 결과다. LeetCode의 Python 버전이 3.10보다 낮은 환경이라면 `key`가 없으니 끝 목록을 따로 만들어 넘겨야 한다.

Java는 결과 크기를 미리 모르니 `List<int[]>`에 모았다가 마지막에 배열로 바꾼다.

```java
import java.util.*;

class Solution {
    public int[][] insert(int[][] intervals, int[] newInterval) {
        List<int[]> out = new ArrayList<>();
        int s = newInterval[0], e = newInterval[1];
        int i = 0, n = intervals.length;
        while (i < n && intervals[i][1] < s) out.add(intervals[i++]);   // 1. 완전히 앞
        while (i < n && intervals[i][0] <= e) {                          // 2. 겹친다
            s = Math.min(s, intervals[i][0]);
            e = Math.max(e, intervals[i][1]);
            i++;
        }
        out.add(new int[]{s, e});
        while (i < n) out.add(intervals[i++]);                           // 3. 완전히 뒤
        return out.toArray(new int[0][]);
    }
}
```

언어별로 달라지는 점은 많지 않다. 이 풀이는 정렬을 하지 않아서 Java의 빼기 비교자 오버플로 문제가 처음부터 없다. 붙이고 정렬하는 풀이를 Java로 쓴다면 `Arrays.sort(a, (x, y) -> Integer.compare(x[0], y[0]))`처럼 써야 한다. 값 범위가 0 이상 10^5 이하라 이 문제에서는 빼기로도 넘치지 않지만, 습관으로 들여 두는 게 좋다. `toArray(new int[0][])`는 크기 0짜리 배열을 넘겨 타입만 알려 주는 관용구다. 결과 배열은 알아서 맞는 크기로 만들어진다.

## 틀리는 코드 조각

### 첫 번째 while에 등호를 넣는다

첫 `while`을 `intervals[i][1] <= s`로 쓰면 끝점이 닿는 구간을 "완전히 앞"으로 분류한다.

```js
while (i < n && intervals[i][1] <= s) out.push(intervals[i++]); // 등호가 틀렸다
```

```text
bug1 [[1,5],[5,7]]
```

`[[1, 5]]`에 `[5, 7]`을 넣은 결과다. 닫힌 구간에서 5는 양쪽에 다 속하니 합쳐야 하는데 따로 남았다. 이 문제에서 "겹친다"는 끝점이 닿는 것까지 포함한다. 그래서 완전히 앞이려면 끝이 시작보다 엄격하게 작아야 한다. 두 번째 `while`의 `intervals[i][0] <= e`도 같은 이유로 등호가 있어야 한다.

### 한 번의 for 문에서 새 구간을 빠뜨린다

세 `while` 대신 for 문 하나에 조건 셋을 넣는 방식도 흔하다. 이 방식은 "새 구간을 넣었나"를 깃발로 관리하는데, 새 구간이 모든 구간보다 뒤에 있거나 모든 구간을 삼키면 루프 안에서 넣을 기회가 오지 않는다.

```js
function insert(intervals, newInterval) {
  const out = []; let cur = newInterval; let done = false;
  for (const iv of intervals) {
    if (done || iv[1] < cur[0]) out.push(iv);
    else if (iv[0] > cur[1]) { out.push(cur); out.push(iv); done = true; }
    else cur = [Math.min(cur[0], iv[0]), Math.max(cur[1], iv[1])];
  }
  return out; // 루프가 끝난 뒤 !done이면 cur를 넣어야 한다
}
```

```text
bug2 [[1,2],[4,5]] []
```

앞은 `[6, 8]`을 맨 뒤에 넣는 경우, 뒤는 `[0, 5]`가 `[1, 2]`를 삼키는 경우다. 둘 다 새 구간이 사라졌다. 고치려면 루프 뒤에 `if (!done) out.push(cur)`를 붙인다. 세 `while` 방식은 3단계에서 무조건 한 번 넣으니 이 실수가 구조적으로 안 생긴다. 면접에서 이 방식을 고른 이유로 말해도 좋다.

### 받은 newInterval을 그대로 고친다

`newInterval[0] = Math.min(...)`처럼 받은 배열을 직접 늘리면 결과는 맞는다. 그런데 호출한 쪽의 배열이 바뀐다.

```text
bug3 newInterval after [4,9]
```

`[5, 8]`을 넘겼는데 함수가 끝나고 보니 `[4, 9]`가 돼 있다. 채점에는 문제가 없지만, 실무에서 이 배열을 다른 곳에서도 쓰고 있었다면 원인을 찾기 어려운 버그가 된다. 위 풀이는 `let [s, e] = newInterval`로 값을 풀어서 피했다. 같은 이유로 "완전히 앞"과 "완전히 뒤" 구간은 입력의 배열 객체를 결과에 그대로 넣는데, 이 객체들은 고치지 않으니 괜찮다. 결과를 받은 쪽이 고칠 수 있다면 복사해서 넣는다.

### 그 밖에 확인할 입력

- 빈 목록: 세 `while`이 모두 바로 끝나고 새 구간 하나만 들어간다. 따로 처리하지 않아도 된다.
- 새 구간이 점 하나(`[4, 4]`): 시작과 끝이 같은 구간도 닫힌 구간이라 똑같이 처리된다.
- 목록이 정렬돼 있지 않다면: 세 덩어리가 섞여서 이 풀이가 틀린다. 문제가 정렬을 보장하니 쓰는 풀이다. 보장이 없다면 Merge Intervals처럼 정렬부터 해야 한다.

## 실제 코드에서 이 모양을 만나는 곳

정렬되고 겹치지 않는 구간 목록은 생각보다 자주 나온다. 목록을 그 상태로 유지하는 것이 곧 이 문제다.

- 캘린더의 바쁜 시간. 여러 일정을 합쳐 "이 사람이 바쁜 시간" 목록을 만들어 두고, 일정이 하나 추가될 때마다 다시 합친다. 전체를 다시 정렬하지 않고 하나만 끼우면 된다. 바쁜 시간들 사이의 빈틈을 구하는 게 [Employee Free Time](/posts/leetcode-employee-free-time)(759번, 프리미엄 문제)이다.
- IP 주소 범위. 허용 목록을 시작 주소 기준으로 정렬된 범위들로 들고 있으면, 주소 하나가 허용되는지는 이분 탐색 한 번이다. 범위를 추가할 때 이웃 범위와 닿으면 합쳐야 목록이 깔끔하게 유지된다. 정수로 바꾼 IPv4 주소 `10.0.0.0`~`10.0.0.255`와 `10.0.1.0`~`10.0.1.255`는 끝과 시작이 1 차이라 이어 붙일 수 있는데, 정수 구간에서는 `end + 1 == start`도 합친다는 규칙을 따로 정해야 한다. 이 문제의 "끝점이 닿으면 합친다"보다 한 칸 넓은 정의다.
- 텍스트 에디터의 선택 영역이나 문법 강조 범위. 문서 위의 범위들을 겹치지 않게 유지하다가 새 범위가 들어오면 합친다.

어느 경우든 데이터가 커지거나 추가가 잦으면 배열을 트리로 바꾸는 쪽으로 간다. 아래 첫 번째 변형이 그 이야기다.

## 면접관이 조건을 바꾸면

### 구간을 하나가 아니라 계속 넣는다면

예약이 하나씩 계속 들어오는 서비스라면 매번 O(n)짜리 새 배열을 만드는 건 비싸다. 구간을 시작 기준 균형 이진 탐색 트리에 담는다. Java라면 `TreeMap<Integer, Integer>`(시작 → 끝)다. 새 구간이 오면 `floorKey(s)`로 바로 앞 구간을 보고 닿으면 합치고, `ceilingKey`로 뒤 구간들을 하나씩 꺼내 겹치는 동안 합치며 지운다. 넣기 한 번이 O((k + 1) log n)이고, k는 지워지는 구간 수다. 각 구간은 한 번 들어가 한 번만 지워지니 전체로 보면 넣기 하나당 평균 O(log n)이다. JavaScript에는 내장 트리가 없어서 면접에서는 "정렬된 배열 + 이분 탐색 + splice"로 설명하고 splice가 O(n)이라는 한계를 같이 말한다.

Java로 짜면 이렇다. 앞 구간은 `floorEntry`로 하나만 보면 된다. 시작이 s 이하인 구간 중 마지막 것만 새 구간과 닿을 수 있다. 그보다 앞 구간들은 그 구간보다 먼저 끝나기 때문이다.

```java
import java.util.*;

class Booked {
    private final TreeMap<Integer, Integer> map = new TreeMap<>(); // 시작 -> 끝

    void add(int s, int e) {
        Map.Entry<Integer, Integer> prev = map.floorEntry(s);       // 시작이 s 이하인 마지막 구간
        if (prev != null && prev.getValue() >= s) {                  // 앞 구간과 닿거나 겹친다
            s = prev.getKey();
            e = Math.max(e, prev.getValue());
            map.remove(prev.getKey());
        }
        Map.Entry<Integer, Integer> next = map.ceilingEntry(s);     // 시작이 s 이상인 첫 구간
        while (next != null && next.getKey() <= e) {                 // 겹치는 동안 삼킨다
            e = Math.max(e, next.getValue());
            map.remove(next.getKey());
            next = map.ceilingEntry(s);
        }
        map.put(s, e);
    }
}
```

예시의 구간을 순서 없이 하나씩 넣고 마지막에 `[5, 8]`을 넣었다.

```text
add [7, 9] -> {7=9}
add [1, 2] -> {1=2, 7=9}
add [11, 12] -> {1=2, 7=9, 11=12}
add [4, 5] -> {1=2, 4=5, 7=9, 11=12}
add [5, 8] -> {1=2, 4=9, 11=12}
```

마지막 줄이 이 글의 답과 같다. 들어오는 순서가 뒤죽박죽이어도 트리가 시작 순서를 지켜 주니, 매번 세 덩어리 중 가운데만 손보면 된다. 앞 덩어리와 뒤 덩어리는 아예 건드리지 않는다. 배열 풀이에서 O(n)이 들던 부분이 그것들을 옮겨 적는 일이었다.

비슷한 문제로 겹치면 예약을 거절하는 [My Calendar I](/posts/leetcode-my-calendar-i)(729번), 구간 추가·삭제·조회를 다 하는 Range Module(715번)이 있다.

### 넣지 말고 빼라면

Remove Interval(1272번, 프리미엄 문제)은 정렬된 목록에서 구간 하나를 빼낸다. 이 문제는 구간을 반쯤 열린 `[a, b)`로 본다. 구조는 같다. 완전히 앞과 뒤는 그대로 옮기고, 겹치는 구간은 빼는 구간의 바깥쪽 조각만 남긴다. 겹치는 `[a, b)`에서 `[s, e)`를 빼면 `a < s`일 때 `[a, s)`를, `e < b`일 때 `[e, b)`를 남긴다. 한 구간이 두 조각으로 쪼개질 수 있다는 게 넣기와 다르다.

### 입력이 정렬돼 있지 않다면

그러면 Merge Intervals다. 정렬 O(n log n)이 하한이 된다. 겹치지 않는다는 보장만 있고 정렬이 안 돼 있다면 정렬 없이도 O(n)에 할 수 있다. 각 구간이 새 구간과 겹치는지 독립적으로 판정해서, 겹치는 것들의 최소 시작과 최대 끝으로 새 구간을 늘리고 나머지는 그대로 두면 된다. 다만 결과도 정렬해서 돌려 달라고 하면 다시 정렬이 필요하다.

### 끝점이 닿는 것은 겹치지 않는다면

회의 시간처럼 반쯤 열린 구간이라면 `[1, 5)`와 `[5, 7)`은 따로 둬야 한다. 두 `while`의 비교를 바꾼다. 첫 번째는 `intervals[i][1] <= s`, 두 번째는 `intervals[i][0] < e`다. 위에서 버그였던 코드가 이 정의에서는 정답이 된다. 같은 코드가 정의에 따라 맞고 틀린다는 걸 보여 주는 좋은 예라 면접에서 먼저 "끝점이 닿으면 합치나요?"라고 묻는 게 좋다.

### 합친 구간이 몇 개를 삼켰는지도 달라면

두 번째 `while`이 도는 횟수를 세면 된다. 이분 탐색 풀이라면 `right - left`다. 회의 예약 시스템이라면 "이 예약 때문에 기존 예약 몇 개가 하나로 묶였다"를 알려 주는 데 쓴다.

같은 묶음의 다른 문제로는 정렬부터 하는 [Merge Intervals](/posts/leetcode-merge-intervals), 끝 기준 정렬로 바뀌는 [Non-overlapping Intervals](/posts/leetcode-non-overlapping-intervals), 두 목록을 나란히 훑는 [Interval List Intersections](/posts/leetcode-interval-list-intersections)가 있다.

## 면접에서 나올 만한 질문

### 입력이 정렬돼 있다는 조건을 어떻게 썼나요?

다시 정렬하지 않고 한 번만 훑었다. 정렬돼 있고 겹치지 않으니 새 구간보다 완전히 앞인 것, 겹치는 것, 완전히 뒤인 것이 목록에서 차례로 이어진다. 인덱스 하나로 세 덩어리를 차례로 처리해서 O(n)이다. 붙이고 정렬하면 O(n log n)이라 조건을 버린 셈이다.

### 두 번째 while의 조건이 시작만 보는 이유는요?

겹치는 조건은 `a <= e`이면서 `s <= b`인데, 첫 번째 while을 빠져나왔다면 `s <= b`가 이미 성립한다. 목록이 정렬돼 있어 뒤 구간의 끝은 더 크니 그 조건은 계속 참이다. 그래서 남은 `a <= e`만 확인하면 된다.

### 시간과 공간 복잡도는요?

시간은 O(n)이다. 인덱스가 한 방향으로만 가고 각 구간을 한 번씩 본다. 추가 공간은 결과 배열을 빼면 변수 몇 개라 O(1)이다. 결과를 새로 돌려줘야 하니 출력 크기 O(n)은 피할 수 없다.

### 이분 탐색을 쓰면 더 빨라지나요?

경계는 O(log n)에 찾지만 결과 배열을 만드는 데 O(n)이 들어서 전체는 그대로 O(n)이다. 실제로 10만 개에서 재 보니 한 번 훑는 풀이와 거의 같았다. 구간을 트리에 담아 결과를 새로 만들지 않는 구조라면 그때 O(log n)이 의미가 있다.

### [1, 5]에 [5, 7]을 넣으면 어떻게 되나요?

이 문제는 닫힌 구간이라 끝점 5가 닿으면 겹친다고 보고 `[1, 7]`로 합친다. 그래서 첫 while은 `end < s`처럼 등호 없이, 두 번째 while은 `start <= e`처럼 등호를 넣는다. 회의처럼 반쯤 열린 구간이라면 부등호를 반대로 바꿔 따로 둔다.

### 구간이 계속 들어오는 서비스라면 어떻게 하나요?

배열 대신 시작을 키로 하는 균형 이진 탐색 트리(Java `TreeMap`)에 담는다. 앞뒤 이웃을 O(log n)에 찾아 겹치는 것만 꺼내 합친다. 각 구간은 한 번 들어가고 한 번 지워지니 넣기 하나당 평균 O(log n)이다.

### for 문 하나로 짜면 무엇을 조심해야 하나요?

새 구간을 넣는 시점을 깃발로 관리하게 되는데, 새 구간이 맨 뒤에 가거나 남은 구간을 다 삼키면 루프 안에서 넣을 기회가 없다. 루프가 끝난 뒤 아직 안 넣었으면 넣는 줄이 꼭 필요하다. 세 while 방식은 합친 구간을 무조건 한 번 넣어서 이 실수가 안 생긴다.
