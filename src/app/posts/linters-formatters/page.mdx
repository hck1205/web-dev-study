PR 하나에 리뷰 댓글이 열두 개 달렸다. 읽어 보니 열 개가 "여기 세미콜론 빠졌어요", "들여쓰기 2칸으로 맞춰 주세요", "작은따옴표로 통일하죠" 같은 이야기다. 나머지 두 개 중 하나가 진짜 버그였다. `fetch`를 `await` 없이 불러서 저장이 실패해도 아무도 모르는 코드였다. 사람 눈이 모양에 쏠려 있는 동안 버그가 지나갈 뻔했다.

이 글은 그 열 개를 기계에게 넘기는 이야기다. 모양을 맞추는 포매터(Prettier)와 버그 가능성을 찾는 린터(ESLint)가 어떻게 다른지, ESLint가 코드를 어떤 식으로 읽는지, 타입 정보를 쓰는 규칙이 왜 느린지, 둘이 부딪힐 때 무엇을 끄는지 본다. Rust로 다시 짠 Biome·oxlint가 얼마나 빠르고 무엇이 아직 없는지, 그리고 이 검사들을 에디터·커밋·CI 중 어디에 걸지도 정리한다.

실습은 Node 22, ESLint 10.13, typescript-eslint 8.72, Prettier 3.9, Biome 2.6.2, oxlint 1.89로 했다. 이 도구들은 판이 자주 바뀌니 버전이 다르면 옵션 이름부터 확인하는 게 좋다. 번들러·트랜스파일러 쪽 도구는 [빌드 도구 글](/posts/frontend-build-tooling)에서 따로 다뤘다.

## 모양과 의미는 다른 문제다

포매터와 린터는 둘 다 코드를 읽고 뭔가를 고쳐 주니 같은 부류로 보인다. 하지만 묻는 질문이 다르다.

포매터는 "이 코드를 어떤 모양으로 출력할까"만 묻는다. Prettier는 코드를 파싱해 구문 트리로 만든 다음, 원래 줄바꿈과 공백을 거의 다 버리고 자기 규칙대로 처음부터 다시 찍어 낸다. 그래서 누가 어떻게 썼든 결과가 같다. 의미는 바꾸지 않는다. 바꾸면 버그다.

린터는 "이 코드에 문제가 될 만한 곳이 있나"를 묻는다. 쓰지 않는 변수, `==`로 한 비교, 처리하지 않은 Promise, 훅 규칙 위반처럼 의미에 관한 규칙이다. 일부는 자동으로 고칠 수 있지만(`--fix`), 많은 규칙은 사람에게 알려 주기만 한다.

위 PR의 코드를 두 도구에 따로 넣어 보면 차이가 바로 보인다.

```ts
// src/cart.ts (고치기 전)
type Item = { price: number, qty: number }

export async function saveCart(items: Item[]) {
  const unused = 1
  let total = 0
  for (const item of items) { total += item.price * item.qty }
  fetch("/api/cart", { method: "POST", body: JSON.stringify({ total }) })
  if (total == null) return
  return total
}
```

Prettier는 모양만 바꾼다. 세미콜론이 붙고, 한 줄에 몰아 쓴 `for`가 풀리고, 타입의 쉼표가 세미콜론이 된다. `unused`도 `fetch`도 그대로다.

```bash
npx prettier src/cart.ts   # 고친 결과를 화면에만 찍는다 (--write를 주면 파일에 쓴다)
```

```text

  }

  return total;
}
```

ESLint는 모양에는 말이 없고 의미를 짚는다. 아래는 타입 정보를 쓰는 설정으로 돌린 결과다(설정은 뒤에서 본다).


## ESLint는 구문 트리를 한 번 걸으며 규칙을 부른다

ESLint가 소스 문자열을 정규식으로 훑는다고 생각하면 동작이 이해가 안 된다. 실제로는 코드를 AST(Abstract Syntax Tree, 구문 트리)로 바꾼 다음, 트리를 위에서 아래로 한 번 걸어 내려간다. 규칙은 "이런 종류의 노드에 도착하면 나를 불러 달라"고 등록해 둔 함수다.

`if (total == 0) reset();` 한 줄을 ESLint 기본 파서(espree)로 파싱하면 이런 트리가 나온다. 위치 정보는 지웠다.

## flat config 하나로 모인 설정

ESLint 9부터 설정 파일이 `eslint.config.js` 하나(flat config)로 바뀌었고, 10에서는 예전 `.eslintrc.*`를 아예 읽지 않는다. 실습한 10.13에서 `.eslintrc.json`을 두고 `ESLINT_USE_FLAT_CONFIG=false`까지 줘 봤지만 무시되고 상위 폴더의 `eslint.config.js`가 쓰였다. 옛 블로그 글의 `extends: ["airbnb"]` 문자열 설정은 그대로 옮겨지지 않는다.

flat config는 "설정 객체의 배열"이다. 파일 하나를 검사할 때 배열을 앞에서부터 보면서 그 파일에 맞는(`files`가 일치하는) 객체를 차례로 덮어쓴다. 뒤에 있는 객체가 이긴다. 문자열로 찾던 플러그인도 이제 `import`한 객체를 그대로 넣는다. 그래서 무엇이 어디서 왔는지 코드만 보고 따라갈 수 있다.

```js
// eslint.config.js — 타입 정보를 쓰는 TypeScript 설정
import js from "@eslint/js";
import { defineConfig } from "eslint/config";
import tseslint from "typescript-eslint";

export default defineConfig(
  { ignores: ["dist/**"] },                 // 전역 무시: 다른 키 없이 ignores만 있는 객체
  js.configs.recommended,                    // ESLint 기본 추천 규칙
  tseslint.configs.recommendedTypeChecked,   // 타입 정보가 필요한 규칙까지 켠 추천 묶음
  {
    languageOptions: {
      parserOptions: { projectService: true }, // tsconfig를 찾아 타입 정보를 붙인다
    },
    rules: {
      eqeqeq: ["error", "always", { null: "ignore" }],
    },
  },
);
```

flat config로 옮기다 보면 두 가지 오류를 자주 만난다. 실습에서 둘 다 그대로 나왔다.

첫째, `.ts` 파일을 넘겼는데 "all of the files matching the glob pattern are ignored"라며 ESLint가 멈춘다. flat config는 기본으로 `.js`, `.mjs`, `.cjs`만 검사한다. 배열 안 어떤 객체에도 `files: ["**/*.ts"]`처럼 `.ts`를 가리키는 패턴이 없으면 그 파일은 "맞는 설정 없음"으로 빠진다. typescript-eslint의 추천 묶음은 이 패턴을 갖고 있어서 문제가 없는데, 파서만 들어 있는 `tseslint.configs.base`에 규칙을 직접 붙이면 이렇게 된다.

```text
Oops! Something went wrong! :(

ESLint: 10.13.0

You are linting "c", but all of the files matching the glob pattern "c" are ignored.
```

둘째, 타입 규칙을 켠 뒤 새 폴더의 파일에서 파싱 오류가 난다. 메시지가 친절하다.

```text
d/a.ts
  0:0  error  Parsing error: d/a.ts was not found by the project service. Consider either including it in the tsconfig.json or including it in allowDefaultProject
```

타입 정보는 TypeScript 프로젝트(tsconfig)에 속한 파일에만 붙는다. `tsconfig.json`의 `include`에 그 폴더가 없으면 ESLint가 타입을 구할 수 없다. 설정 파일이나 스크립트처럼 tsconfig에 넣기 애매한 파일은 `parserOptions.projectService.allowDefaultProject`에 따로 적거나, 그 파일만 타입 규칙을 끈 객체로 덮는다.

## 타입을 아는 규칙은 비싸다

`no-floating-promises`가 `fetch(...)`를 잡은 건 `fetch`의 반환 타입이 `Promise`라는 걸 알아서다. 구문 트리만 보면 그냥 함수 호출이다. `saveCart()`가 Promise를 돌려주는지, `db.query()`가 그런지는 타입 검사기에게 물어봐야 안다. `no-misused-promises`(이벤트 핸들러에 async 함수를 그냥 넘김), `await-thenable`, `restrict-template-expressions`도 같은 부류다.

대신 값이 크다. ESLint가 TypeScript 컴파일러를 띄워 프로젝트 전체 타입을 계산한 뒤에 규칙을 돌리기 때문이다. 같은 파일 500개(위 `cart.ts`를 복사한 작은 파일들)로 재 봤다. 4코어 컨테이너이고, `npx` 시동 시간이 포함된 대략적인 숫자다.

```text
ESLint, 타입 없는 추천 규칙       2.6 ~ 3.5 s
ESLint, 타입 기반 추천 규칙       6.3 ~ 6.7 s
Biome lint (기본 규칙)            0.55 ~ 0.62 s
oxlint (기본 규칙)                0.43 ~ 0.50 s
```

작은 파일이라 차이가 덜 벌어진 편이다. 의존성이 깊은 실제 프로젝트에서는 타입 계산 비용이 더 커진다. 그래서 흔히 쓰는 조합이 있다. 에디터와 커밋 직전에는 바뀐 파일만 검사하고, 타입 규칙을 포함한 전체 검사는 CI에서 `--cache`와 함께 돌린다. `--cache`는 지난번 결과를 `.eslintcache`에 남겨 바뀌지 않은 파일을 건너뛴다. 다만 타입 규칙은 다른 파일이 바뀌어도 결과가 달라질 수 있어서, 캐시를 믿고 일부만 돌리면 놓치는 경고가 생길 수 있다는 점은 알고 쓴다.

타입 규칙이 잡는 버그는 `tsc`가 잡지 못하는 종류라는 것도 기억해 둔다. `fetch`를 `await` 없이 부르는 건 타입 오류가 아니다. 타입 검사와 린트는 서로를 대신하지 않는다. TypeScript 쪽 엄격 옵션은 [tsconfig strict 글](/posts/tsconfig-strict)에서 다뤘다.

## ESLint와 Prettier가 서로 고치기 시작할 때

ESLint에는 원래 `indent`, `quotes`, `semi` 같은 모양 규칙도 있었다. 8.53에서 모두 사용 중단(deprecated)으로 바뀌었고 `@stylistic/eslint-plugin`으로 옮겨 갔다. 10.13에도 규칙 파일은 남아 있어서 켜면 동작한다. 오래된 설정을 물려받은 프로젝트에서 이게 Prettier와 부딪힌다.

Prettier 기본값(큰따옴표, 2칸)으로 포맷한 파일에 `quotes: single`, `indent: 4`가 켜진 ESLint를 돌려 봤다.

```text
c/cart.ts
   4:1   error  Expected indentation of 4 spaces but found 2  indent
   9:9   error  Strings must use singlequote                  quotes
  ...
✖ 10 problems (10 errors, 0 warnings)
  10 errors and 0 warnings potentially fixable with the `--fix` option.
```

`eslint --fix`로 고치면 이번엔 `prettier --check`가 실패한다. 저장할 때마다 두 도구가 번갈아 파일을 바꾸는 상태가 된다. 해결은 한쪽에만 모양을 맡기는 것이다. `eslint-config-prettier`는 Prettier와 겹치는 ESLint 규칙(설치한 10.1.8 기준 358개)을 전부 `off`로 바꾸는 설정 묶음이다. 배열의 맨 끝에 둬야 앞에서 켠 규칙을 덮는다.

```js
import prettier from "eslint-config-prettier";

export default defineConfig(
  tseslint.configs.recommendedTypeChecked,
  // ...팀 규칙
  prettier, // 반드시 마지막: 모양 규칙을 끈다
);
```

같은 파일에 이 설정을 붙이자 ESLint는 아무것도 보고하지 않고 종료 코드 0으로 끝났다.

이름이 비슷한 `eslint-plugin-prettier`는 다른 물건이다. Prettier를 ESLint 규칙 하나로 돌려서, 포맷이 다르면 빨간 줄로 보여 준다. Prettier 공식 문서는 이 방식을 권하지 않는다. 모양 차이가 오류처럼 보여 에디터가 시끄럽고, Prettier를 직접 돌리는 것보다 느리다. 포매터는 저장할 때 조용히 돌게 두고, CI에서 `prettier --check`로 확인하는 편이 깔끔하다.

Prettier를 처음 들이면 한 번은 저장소 전체를 다시 포맷하는 커밋이 생긴다. 이 커밋이 `git blame`을 망친다. 그 커밋 해시를 `.git-blame-ignore-revs` 파일에 적어 두면 `git blame --ignore-revs-file .git-blame-ignore-revs`가 그 커밋을 건너뛰고, GitHub의 blame 화면은 이 파일을 자동으로 읽는다.

## Rust로 다시 짠 도구들: Biome와 oxlint

위 측정에서 Biome와 oxlint는 ESLint보다 다섯 배에서 열몇 배 빨랐다. JavaScript로 짠 파서와 규칙 대신 Rust로 짠 바이너리가 여러 코어로 파일을 나눠 처리하기 때문이다.

Biome는 포매터와 린터를 한 도구에 넣었다. `biome check` 한 번에 둘 다 돈다. 포맷 결과는 Prettier와 거의 같게 맞추는 걸 목표로 한다. 다만 기본값이 다르다. `biome init`이 만든 설정은 들여쓰기가 탭이다. Prettier에서 넘어온다면 `indentStyle: "space"`를 먼저 맞춘다. `biome migrate eslint`, `biome migrate prettier`가 기존 설정을 읽어 옮겨 준다.

```bash
npx biome init           # biome.json 생성
npx biome check src      # 포맷 차이와 린트 위반을 함께 보고
npx biome check --write  # 안전한 수정과 포맷을 파일에 반영
```

같은 `cart.ts`에 `biome check`를 돌린 결과다. 앞부분만 옮겼다.

```text
cart.ts:4:9 lint/correctness/noUnusedVariables  FIXABLE  ━━━━━━━━━━━━━━━━━━━━━━━━━━

  ! This variable unused is unused.

cart.ts format ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  × Formatter would have printed the following content:
```

여기서 빠진 게 있다. ESLint 타입 규칙이 잡았던 `fetch` 경고가 없다. Biome 2부터 자체 타입 추론으로 `noFloatingPromises`를 제공하지만, 2.6.2에서는 아직 nursery(실험 단계) 그룹이라 기본으로 꺼져 있다. 직접 켜면 같은 줄을 잡았다. typescript-eslint는 진짜 TypeScript 컴파일러에게 타입을 묻고, Biome는 자기 추론으로 근사한다는 점이 다르다. 복잡한 제네릭이나 외부 라이브러리 타입에서는 결과가 다를 수 있다.

oxlint는 린터만 한다. 기본 설정으로 돌리면 정확성(correctness) 규칙 위주라 조용한 편이다.

```text
src/cart.ts:4:9: warning eslint(no-unused-vars): Variable 'unused' is declared but never used. Unused variables should start with a '_'. help: Consider removing this declaration.
```

빠른 도구를 고를 때 따져 볼 건 속도보다 "빠진 규칙"이다. `eslint-plugin-react-hooks`, 접근성(`jsx-a11y`), 테스트 라이브러리, 프레임워크 전용 플러그인처럼 팀이 의지하던 규칙이 새 도구에 다 있는지 먼저 본다. 커스텀 규칙을 써 왔다면 Rust 도구에는 그대로 옮길 수 없다. 그래서 큰 프로젝트에서는 oxlint를 먼저 돌려 흔한 문제를 빨리 거르고, 남은 규칙만 ESLint로 돌리는 식으로 섞어 쓰기도 한다. oxlint 쪽에서 ESLint와 겹치는 규칙을 끄는 `eslint-plugin-oxlint`가 이 용도다.

pre-commit 단계는 lint-staged로 이렇게 건다. 훅 자체를 팀원 모두에게 깔아 주는 방법(husky, `core.hooksPath`)은 도구마다 다르니 각 문서를 따른다.

```json
// package.json의 일부
{
  "lint-staged": {
    "*.{ts,tsx,js}": ["eslint --fix --max-warnings 0", "prettier --write"],
    "*.{json,md,css}": "prettier --write"
  }
}
```

배열 안 명령에는 lint-staged가 스테이징된 파일 목록을 뒤에 붙여 준다. 그래서 `eslint --fix src/a.ts src/b.ts`처럼 실행된다. 여기에 `tsc --noEmit`을 넣고 싶어지는데, `tsc`는 파일 목록을 받으면 tsconfig를 무시하고 그 파일만 기본 옵션으로 검사한다. 타입 검사는 프로젝트 단위로 해야 의미가 있으니 CI에 둔다.

CI에서 `--max-warnings 0`을 주는 이유가 있다. 경고(`warn`)는 종료 코드를 바꾸지 않아서, 그대로 두면 경고가 몇백 개 쌓여도 CI는 초록불이다. 그런 경고는 아무도 읽지 않는다. 규칙은 `error`나 `off` 둘 중 하나로 정하고, 옮겨 가는 동안에만 `warn`을 쓰는 게 덜 괴롭다.

## 규칙을 끄는 주석이 쌓인다

마감이 급하면 `// eslint-disable-next-line`을 붙이고 넘어간다. 하나하나는 이유가 있었겠지만, 1년쯤 지나면 이런 주석이 수백 개가 되고 대부분은 왜 붙였는지 아무도 모른다. 코드가 바뀌어 더는 필요 없는 주석도 섞인다.

ESLint 9부터는 쓸모없어진 끄기 주석을 기본으로 경고한다(`linterOptions.reportUnusedDisableDirectives`의 기본값이 `"warn"`). 이미 `unknown`을 반환하는 줄에 `no-explicit-any` 끄기 주석이 남아 있으면 이렇게 나온다.

```text
d/a.ts
  1:1  warning  Unused eslint-disable directive (no problems were reported from '@typescript-eslint/no-explicit-any')

✖ 1 problem (0 errors, 1 warning)
  0 errors and 1 warning potentially fixable with the `--fix` option.
```

CI에 `--max-warnings 0`이 있으면 이 경고도 실패가 된다. 실습에서도 종료 코드가 1이었다. 남아 있는 주석에는 이유를 적게 한다. ESLint는 `--` 뒤의 글을 설명으로 읽는다.

```ts
// eslint-disable-next-line @typescript-eslint/no-explicit-any -- 외부 SDK 타입이 any를 돌려준다. v3에서 제거
const raw: any = sdk.read();
```

`@eslint-community/eslint-plugin-eslint-comments`의 `require-description` 규칙을 켜면 설명 없는 끄기 주석을 막을 수 있다. 파일 맨 위의 `/* eslint-disable */`처럼 파일 전체를 끄는 주석은 리뷰에서 특히 잘 본다. 규칙이 자주 꺼진다면 주석을 더 붙일 게 아니라 규칙이 그 코드베이스에 맞는지부터 다시 따진다.

흔한 실수 몇 가지를 더 적어 둔다.

- 추천 묶음을 켜 놓고 경고가 너무 많다며 규칙을 하나씩 끄다 보면 남는 게 없다. 처음 들일 때는 새 코드부터 적용하고(바뀐 파일만 검사), 옛 코드는 따로 시간을 잡아 고친다.
- 포맷 커밋과 로직 변경을 한 PR에 섞으면 리뷰할 수 없는 diff가 된다. 포맷은 별도 커밋으로 먼저 넣는다.
- 팀원마다 에디터 확장의 Prettier 버전이 달라 결과가 조금씩 다르다. 저장소의 `devDependencies`에 버전을 고정하고, 확장이 그 버전을 쓰게 한다.

## 사람은 모양을 보지 않는다

포매터는 모양을 하나로 찍어 내서 모양 논쟁을 없애고, 린터는 구문 트리를 걸으며 의미상 문제를 찾는다. 둘이 겹치는 모양 규칙은 `eslint-config-prettier`로 린터 쪽을 끈다. 타입을 아는 규칙은 `tsc`도 못 잡는 버그를 잡지만 느리니 CI에 두고, 에디터와 커밋 훅에는 빠른 검사만 둔다. Biome·oxlint는 빠르지만 쓰던 규칙이 다 있는지가 선택 기준이다. 마지막 판정은 건너뛸 수 없는 CI가 한다.

## 면접에서 나올 만한 질문

### 린터와 포매터는 무엇이 다른가요?

포매터는 코드의 모양만 정하고, 린터는 버그가 될 만한 의미상 문제를 찾습니다. Prettier는 코드를 파싱한 뒤 원래 공백을 버리고 자기 규칙으로 다시 출력해서 누가 써도 같은 모양이 됩니다. ESLint는 쓰지 않는 변수, 처리하지 않은 Promise처럼 동작에 영향을 주는 문제를 규칙으로 잡습니다. 그래서 둘을 함께 쓰고, 모양은 포매터에만 맡깁니다.

### ESLint는 코드를 어떻게 검사하나요?

소스를 파서로 AST로 바꾼 뒤 트리를 깊이 우선으로 한 번 걸으면서, 각 노드 종류에 등록된 규칙 함수를 부릅니다. 규칙은 `BinaryExpression`이나 `CallExpression[callee.name='parseFloat']` 같은 선택자를 키로 등록하고, 조건에 맞으면 `context.report`로 위치와 메시지를 보고합니다. 규칙이 많아도 트리는 한 번만 걷습니다. 이 구조 덕에 팀 전용 규칙도 몇 줄로 만들 수 있습니다.

### flat config는 이전 설정과 무엇이 다른가요?

`eslint.config.js` 하나에 설정 객체의 배열을 두고, 파일마다 `files` 패턴이 맞는 객체를 앞에서부터 덮어써서 뒤의 것이 이깁니다. 플러그인과 공유 설정을 문자열 이름 대신 `import`한 객체로 넣어서 어디서 왔는지 코드로 추적됩니다. ESLint 9부터 기본이고 10에서는 `.eslintrc`를 읽지 않습니다. 기본 검사 대상이 `.js` 계열이라 `.ts`를 가리키는 `files`가 없으면 파일이 무시된다는 점을 자주 놓칩니다.

### 타입 기반 린트 규칙은 왜 느리고, 그래도 쓰는 이유는 뭔가요?

`no-floating-promises`처럼 어떤 값이 Promise인지 알아야 하는 규칙은 TypeScript 컴파일러로 프로젝트 전체 타입을 계산해야 해서 느립니다. 실습에서 같은 파일 500개 기준 타입 없는 규칙의 두 배쯤 걸렸습니다. 그래도 `await`를 빠뜨린 호출처럼 타입 오류는 아니지만 실제 장애가 되는 버그를 잡아서 씁니다. 보통 에디터와 커밋 훅에서는 빼고 CI에서 전체로 돌립니다.

### ESLint와 Prettier가 충돌하면 어떻게 하나요?

`indent`, `quotes` 같은 ESLint 모양 규칙이 Prettier 출력과 달라서 서로 고치는 상태가 되니, `eslint-config-prettier`를 설정 배열 맨 끝에 넣어 겹치는 규칙을 모두 끕니다. 모양은 Prettier가, 의미는 ESLint가 맡도록 나누는 겁니다. Prettier를 ESLint 규칙으로 돌리는 `eslint-plugin-prettier`는 느리고 모양 차이가 오류처럼 보여서 Prettier 문서도 권하지 않습니다.

### Biome나 oxlint로 바꾸자는 제안이 오면 무엇을 확인하나요?

속도는 확실히 빠르니, 팀이 의지하는 규칙이 다 있는지를 먼저 봅니다. React 훅 규칙, 접근성, 프레임워크 플러그인, 직접 만든 커스텀 규칙, 타입 기반 규칙이 대표적입니다. Biome의 타입 기반 규칙은 자체 추론이라 typescript-eslint와 결과가 다를 수 있고, 일부는 아직 실험 단계입니다. 다 옮기기 어렵다면 oxlint로 먼저 빠르게 거르고 남은 규칙만 ESLint로 돌리는 혼합도 방법입니다.

### pre-commit 훅이 있는데 CI에서도 린트를 돌리는 이유는요?

로컬 훅은 `--no-verify`로 건너뛸 수 있고, 훅이 설치되지 않은 사람도 있어서 강제력이 없습니다. 훅은 바뀐 파일만 빠르게 보는 조기 경보이고, CI는 저장소 전체를 타입 규칙까지 포함해 검사하는 최종 판정입니다. CI 작업을 브랜치 보호의 필수 체크로 걸어야 규칙이 실제로 지켜집니다.

### eslint-disable 주석이 계속 늘어나는 걸 어떻게 막나요?

쓸모없어진 끄기 주석은 `reportUnusedDisableDirectives`(ESLint 9부터 기본 경고)로 찾고, CI에서 `--max-warnings 0`으로 실패시킵니다. 남기는 주석에는 `--` 뒤에 이유를 쓰게 하고, `eslint-comments` 플러그인의 `require-description`으로 강제할 수 있습니다. 같은 규칙이 자꾸 꺼진다면 규칙 자체가 코드베이스에 맞는지 다시 검토합니다.
