## 관리자 화면을 열자 useState가 null이다

관리자 화면 빌드는 통과했는데, 브라우저에서 열자마자 화면이 하얗게 비었다. 콘솔에는 이 한 줄이 떠 있었다.

```text
[pageerror] Cannot read properties of null (reading 'useState')
```

같은 `Button`을 쓰는 쇼핑몰 화면은 멀쩡했다. 차이는 관리자 앱의 `package.json`에 누군가 React 버전을 `19.2.9`로 고정해 둔 것 하나였다. 공용 버튼은 다른 폴더에 있고, 그 폴더는 `19.3.1`을 보고 있었다. 한 번들 안에 React가 두 벌 들어간 것이다.

이 일은 여러 앱과 공용 패키지를 한 저장소에 모은 모노레포(monorepo)에서 흔히 만난다. 이 글은 프런트엔드 모노레포를 pnpm 워크스페이스로 직접 만들어 보며, 패키지가 서로를 어떻게 찾는지, 공용 패키지를 어떤 모양으로 내보낼지, 버전을 어떻게 올릴지, 경계를 어떻게 지킬지를 따라간다. 위 에러가 왜 났는지도 그 과정에서 풀린다.

이 주제의 다른 글: 빌드가 느려질 때 작업 그래프와 캐시로 줄이는 이야기는 [모노레포 빌드: 작업 그래프와 바뀐 것만 빌드하기](/posts/monorepo-build-cache)에서, 팀마다 따로 배포해야 할 때의 선택지는 [마이크로 프런트엔드](/posts/micro-frontends)에서 다룬다.

실습 환경은 Node 22.22.0, pnpm 10.28.0, Vite 8.3.5, TypeScript 5.9.3, React 19.3.1, Changesets 2.31.1이다. 출력에 찍히는 긴 작업 폴더 경로는 `~`로 줄였다.

## 저장소가 셋이면 버튼 하나에 PR이 셋

쇼핑몰(`web`)과 관리자(`admin`) 두 앱이 같은 디자인 시스템 버튼을 쓴다고 하자. 저장소가 따로면 버튼의 클릭 상태를 고치는 일이 이렇게 흘러간다. ui 저장소에서 고치고 npm에 새 버전을 올린다. web 저장소에서 버전을 올리는 PR을 낸다. admin 저장소에서도 같은 PR을 낸다. 셋 중 하나가 늦으면 두 앱의 버튼 동작이 한동안 다르다. 고친 버전에 버그가 있으면 이 과정을 처음부터 반복한다.

모노레포는 이 셋을 한 저장소에 둔다. 버튼을 고치는 커밋 하나에 두 앱의 수정까지 같이 담을 수 있고, CI는 그 커밋으로 두 앱을 함께 빌드하고 테스트한다. 깨지면 PR 단계에서 바로 보인다. 버전을 올리고 기다리는 시간이 사라지는 것, 그리고 "이 변경이 누구를 깨뜨리는지"를 머지 전에 아는 것이 모노레포를 쓰는 가장 큰 이유다.

모노레포가 모놀리스는 아니다. 한 저장소 안에서도 앱은 각자 빌드되고 각자 배포된다. 합친 것은 코드의 위치와 변경 단위이고, 실행 단위는 그대로다. 반대로 팀마다 배포 시점까지 떼어 내야 한다면 저장소 구조만으로는 부족하고, 그때가 [마이크로 프런트엔드](/posts/micro-frontends)를 볼 때다.

대가도 있다. 저장소가 커지면 clone이 느려지고, 모든 팀이 같은 CI와 같은 도구 버전을 공유하고, 잘못 만들면 한 줄을 고쳐도 전부 다시 빌드한다. 마지막 문제는 [다음 글](/posts/monorepo-build-cache)의 주제다.

## 작업 공간을 선언한다

실습용 저장소의 모양이다. 앱 둘, 공용 패키지 셋이다.

```text
shop/
├── package.json
├── pnpm-workspace.yaml
├── apps/
│   ├── web/        @shop/web     쇼핑몰 (Vite + React)
│   └── admin/      @shop/admin   관리자 (Vite + React)
└── packages/
    ├── ui/         @shop/ui      버튼, 가격표 (TS 소스 그대로)
    ├── format/     @shop/format  가격 포맷 (tsc로 dist 빌드)
    └── tsconfig/   @shop/tsconfig 공용 tsconfig
```

pnpm은 루트의 `pnpm-workspace.yaml`을 보고 어느 폴더가 패키지인지 안다. `catalog`는 뒤에서 다시 본다.

```yaml
# pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"

catalog:
  react: ^19.3.1
  react-dom: ^19.3.1
  typescript: ^5.9.3
  vite: ^8.0.0
```

패키지끼리의 관계는 각 `package.json`의 의존성으로 적는다. 두 앱은 ui를 쓰고, ui는 format을 쓰고, 모두 tsconfig를 개발 의존성으로 쓴다. 이렇게 적어 둔 의존성이 곧 저장소의 지도다. pnpm의 빌드 순서도, 다음 글에서 볼 Turborepo의 작업 그래프도 이 지도에서 나온다.

앱의 `package.json`은 이렇게 생겼다.

```json
{
  "name": "@shop/web",
  "private": true,
  "dependencies": {
    "@shop/ui": "workspace:*",
    "react": "catalog:",
    "react-dom": "catalog:"
  },
  "devDependencies": {
    "@shop/tsconfig": "workspace:*",
    "vite": "catalog:"
  }
}
```

`"private": true`는 실수로 npm에 올라가지 않게 막는다. 앱은 배포 대상이지 배포할 패키지가 아니니 항상 붙인다.

## workspace 프로토콜은 레지스트리에 묻지 않는다

`workspace:*`는 "이 저장소 안에 있는 그 패키지를 써라"는 뜻이다. 버전 범위처럼 생겼지만 레지스트리에서 찾지 않는다. 그냥 `^1.2.0`이라고 적으면 어떻게 되는지 확인했다. web의 의존성에 `"@shop/format": "^1.2.0"`을 넣고 설치했다.

```bash
# workspace: 없이 일반 범위로 적고 설치한다
pnpm install
```

```text
~/shop/apps/web:
 ERR_PNPM_FETCH_404  GET https://registry.npmjs.org/@shop%2Fformat: Not Found - 404

This error happened while installing a direct dependency of ~/shop/apps/web

@shop/format is not in the npm registry, or you have no permission to fetch it.
```

저장소 안에 `@shop/format@1.2.0`이 있는데도 npm 레지스트리로 갔다. pnpm 9부터 `link-workspace-packages`의 기본값이 `false`라서, 일반 범위는 레지스트리에서 찾는다. 이번에는 404라서 바로 드러났지만, 같은 이름의 공개 패키지가 있었다면 남이 올린 코드가 조용히 설치됐을 것이다. 사내 패키지 이름을 노린 이런 공격을 의존성 혼동(dependency confusion)이라고 부른다. 내부 패키지는 `workspace:`로 적고, 사내 스코프(`@shop`)는 `.npmrc`에서 사내 레지스트리로 묶어 두면 이 길이 막힌다.

`workspace:` 뒤에 무엇을 붙이느냐는 개발 중에는 상관없다. 어떻게 적든 저장소 안의 폴더로 링크된다. 차이는 패키지를 밖으로 내보낼 때 생긴다. ui를 `pnpm pack`으로 묶어서 안에 들어간 `package.json`을 열어 봤다.

```bash
# ui를 tarball로 묶고, 그 안의 package.json에서 의존성을 꺼내 본다
cd packages/ui && pnpm pack --pack-destination ../..
tar -xzf ../../shop-ui-0.4.0.tgz -C ../../packed
node -e 'const p=require("../../packed/package/package.json");console.log(JSON.stringify({dependencies:p.dependencies,devDependencies:p.devDependencies},null,2))'
```

```text
{
  "dependencies": {
    "clsx": "^2.1.1",
    "@shop/format": "^1.2.0"
  },
  "devDependencies": {
    "@types/react": "^19.0.0",
    "react": "^19.3.1",
    "typescript": "^5.9.3",
    "@shop/tsconfig": "0.0.0"
  }
}
```

`workspace:^`는 지금 format 버전을 넣은 `^1.2.0`이 됐고, `workspace:*`는 정확한 버전 `0.0.0`, `catalog:`는 카탈로그에 적은 범위로 바뀌었다. 표기를 바꿔 가며 몇 번 더 묶어 봤다.

```text
workspace:~ -> ~1.2.0
workspace:^1.0.0 -> ^1.0.0
workspace:* -> 1.2.0
workspace:1.2.0 -> 1.2.0
```

아래 그림은 같은 한 줄이 개발할 때와 내보낼 때 어떻게 다르게 읽히는지 보여 준다.

```bash
ls -la apps/web/node_modules apps/web/node_modules/@shop
```

마지막 단계가 pnpm의 엄격함이다. 관리자 앱 코드에서 ui가 쓰는 `clsx`를 선언 없이 불러 봤다.

```bash
# admin의 package.json에는 clsx가 없다
pnpm --filter @shop/admin build
```

```text
error during build:
Build failed with 1 error:
Error: [vite]: Rolldown failed to resolve import "clsx" from "~/shop/apps/admin/src/main.tsx".
```

npm처럼 평평한 `node_modules`였다면 우연히 최상위로 올라온 clsx가 잡혀서 빌드가 됐을 것이다. 이렇게 선언하지 않은 패키지를 쓰는 걸 유령 의존성이라고 하고, 왜 위험한지와 호이스팅 설정(`public-hoist-pattern`, `node-linker=hoisted`)은 [의존성 지옥](/posts/dependency-hell)에서 자세히 다뤘다. 모노레포에서는 이 엄격함이 더 값지다. 앱 하나가 다른 앱의 의존성을 몰래 빌려 쓰기 시작하면 패키지를 떼어 내거나 지울 때마다 엉뚱한 앱이 깨진다.

## 공용 패키지를 빌드할까, 소스로 둘까

같은 저장소 안의 패키지를 앱이 소비하는 방법은 크게 둘이다. 실습의 format은 tsc로 `dist`를 만들어 내보내는 빌드형이고, ui는 TypeScript 소스를 그대로 내보내는 소스형이다. Turborepo 문서는 앞의 것을 Compiled Package, 뒤의 것을 Just-in-Time Package라고 부른다.

소스형의 대가는 소비자가 지는 부담이다. web에서 타입 검사를 돌리고 tsc가 읽은 파일 중 저장소 안의 것만 뽑았다.

```bash
# web의 타입 검사가 실제로 읽는 저장소 내부 파일
cd apps/web && npx tsc --noEmit --listFilesOnly | grep -v node_modules/.pnpm
```

```text

~/shop/packages/format/dist/index.d.ts
~/shop/packages/ui/src/price-tag.tsx
~/shop/packages/ui/src/index.ts
~/shop/apps/web/src/main.tsx
```

ui는 소스 파일 셋을 통째로 다시 검사하고, format은 `.d.ts` 한 장만 읽는다. ui의 타입 오류는 ui가 아니라 ui를 쓰는 앱 쪽에서 터지고, 앱이 열 개면 같은 소스를 열 번 검사한다. 번들러도 ui의 TSX를 앱마다 다시 변환한다. Vite는 링크가 풀린 실제 경로가 `node_modules` 밖이라 알아서 변환했지만, Next.js는 `transpilePackages`에 이런 패키지를 적어야 컴파일 대상에 넣는다.

빌드 단계가 없는 소스형은 수정이 바로 보여서 개발이 빠르고 설정이 적다. 대신 앱마다 같은 일을 반복하고, 저장소 밖으로 내보낼 수 없다. 빌드형은 빌드 순서와 감시 모드가 필요하지만 결과를 캐시할 수 있고, 그대로 npm에 올릴 수 있다. 저장소 안에서만 쓰는 작은 UI·유틸 패키지는 소스형으로 시작하고, 외부에 공개하거나 패키지가 커서 앱마다의 검사 비용이 눈에 띌 때 빌드형으로 바꾸는 순서가 무난하다. 둘 사이의 방법도 있다. `exports`에 사내용 조건(예: `"@shop/source": "./src/index.ts"`)을 하나 더 두고 앱의 tsconfig `customConditions`와 번들러의 `resolve.conditions`에 그 이름을 넣으면, 개발 중에는 소스를, 배포본은 `dist`를 쓰게 할 수 있다. TypeScript의 project references(`tsc -b`)로 패키지별 `.d.ts`를 증분 빌드하는 방법도 있다.

## exports에 없는 경로는 열리지 않는다

`exports`는 공개 API의 목록이면서 경계이기도 하다. 관리자 앱에서 ui 내부 파일을 바로 불러 봤다.

```tsx
// apps/admin/src/main.tsx
import { PriceTag } from "@shop/ui/src/price-tag";
```

```text
"./src/price-tag" is not exported under the conditions ["module", "browser", "production", "import"] from package ~/shop/apps/admin/node_modules/@shop/ui (see exports field in ~/shop/apps/admin/node_modules/@shop/ui/package.json)
```

```text
src/main.tsx(2,26): error TS2307: Cannot find module '@shop/ui/src/price-tag' or its corresponding type declarations.
```

번들러도 tsc(`moduleResolution: "Bundler"`)도 막았다. 같은 저장소라 파일은 바로 옆에 있지만, 패키지가 열어 둔 문으로만 들어갈 수 있다. 덕분에 ui 팀은 `src` 안의 파일 이름을 마음대로 바꿔도 된다. 공개한 `.`과 `./button`만 지키면 된다. `exports`의 조건 매칭과 ESM 쪽 동작은 [ES 모듈](/posts/js-es-modules)에서 더 다뤘다.

## tsconfig paths로 지름길을 내면

`exports`나 `workspace:` 없이 tsconfig의 `paths`로 다른 패키지의 소스를 직접 가리키는 저장소도 많다. 실험해 봤다. web의 tsconfig에 별칭을 하나 두고 format 소스를 바로 불렀다. web의 `package.json`에는 format이 없다.

```json
{
  "extends": "@shop/tsconfig/base.json",
  "compilerOptions": { "paths": { "@lib/format": ["../../packages/format/src/index.ts"] } },
  "include": ["src"]
}
```

```ts
// apps/web/src/total.ts
import { formatPrice } from "@lib/format";
export const total = formatPrice(12900 * 2);
```

tsc는 통과했다(`tsc exit 0`). Vite 8도 이 별칭을 풀어서 빌드가 됐다(`✓ built in 459ms`). 그런데 같은 파일을 Node로 실행하면 깨진다.

```bash
# Node 22는 타입만 지우고 실행한다. paths는 모른다
node src/total.ts
```

```text
Error [ERR_MODULE_NOT_FOUND]: Cannot find package '@lib/format' imported from ~/shop/apps/web/src/total.ts
  code: 'ERR_MODULE_NOT_FOUND'
}
```

도구마다 따로 별칭을 알려 줘야 한다는 것도 번거롭지만, 더 큰 문제는 따로 있다. 지도에서 선이 빠진다. `package.json`에는 web이 format을 쓴다는 기록이 없다. 그래서 pnpm은 web을 빌드하기 전에 format을 빌드해야 한다는 걸 모르고, 다음 글에서 볼 Turborepo는 format이 바뀌어도 web을 다시 빌드할 필요가 없다고 판단한다. 패키지 사이의 연결은 `paths`가 아니라 의존성으로 적는다. `paths`는 한 패키지 안의 별칭(`@/components`)에만 쓴다.

## React가 두 벌 들어가는 순간

처음 에러로 돌아가자. 관리자 앱만 React를 `19.2.9`로 고정한 상태에서 저장소의 React 버전을 찍어 봤다.

```bash
# 워크스페이스 전체에서 react가 몇 버전으로 깔렸나
pnpm -r list react --depth 0
```

```text
@shop/admin@0.0.0 ~/shop/apps/admin (PRIVATE)

dependencies:
react 19.2.9

@shop/web@0.0.0 ~/shop/apps/web (PRIVATE)

dependencies:
react 19.3.1

@shop/ui@0.4.0 ~/shop/packages/ui

react 19.3.1
```

ui는 React를 `peerDependencies`로 선언하고, 개발할 때 쓰려고 `devDependencies`에도 넣어 뒀다. 외부에 배포한 패키지라면 peer는 "앱이 가진 React를 써라"로 동작한다. 하지만 모노레포 안에서 ui는 링크로 연결된 폴더라서, `import { useState } from "react"`를 ui 폴더 기준으로 찾는다. 두 위치에서 react를 찾아보면 서로 다른 곳이 나온다.

```bash
# 같은 "react"를 두 폴더에서 찾으면
node -e '
const r = (from) => require.resolve("react", { paths: [from] }).replace(process.cwd(), ".");
console.log("apps/admin/src  ->", r("apps/admin/src"));
console.log("packages/ui/src ->", r("packages/ui/src"));'
```

```text
apps/admin/src  -> ./node_modules/.pnpm/react@19.2.9/node_modules/react/index.js
packages/ui/src -> ./node_modules/.pnpm/react@19.3.1/node_modules/react/index.js
```

번들러는 이 둘을 다른 모듈로 보고 둘 다 번들에 넣는다. 화면을 그리는 react-dom은 19.2.9 쪽 React에 현재 렌더링 중인 컴포넌트 정보를 채우는데, 버튼의 `useState`는 아무도 채우지 않은 19.3.1 쪽을 부른다. 그래서 내부 디스패처가 `null`이고, 실행해 보면 처음의 에러가 나온다. 같은 코드를 개발 모드(`NODE_ENV=development`)로 빌드해서 열면 TypeError 앞에 React의 안내가 먼저 찍힌다.

```text
[console.error] Invalid hook call. Hooks can only be called inside of the body of a function component. This could happen for one of the following reasons:
[pageerror] Cannot read properties of null (reading 'useState')
```

급하게 막는 방법은 번들러에게 한 벌만 쓰라고 시키는 것이다. 관리자 앱의 Vite 설정에 `resolve.dedupe`를 넣었더니 화면이 다시 나왔다.

```ts
// apps/admin/vite.config.ts
export default defineConfig({ plugins: [react()], resolve: { dedupe: ["react", "react-dom"] } });
```


하지만 이건 증상을 덮는 것이다. ui는 19.3.1에서 개발하고 테스트했는데 실제로는 19.2.9 위에서 돈다. 제대로 된 해결은 저장소 전체가 같은 React를 쓰는 것이고, pnpm 9.5부터 들어간 카탈로그(catalog)가 그 일을 한다. `pnpm-workspace.yaml`의 `catalog`에 버전을 한 번 적고, 각 패키지는 `"react": "catalog:"`로 그 값을 가리킨다. 관리자 앱을 `catalog:`로 되돌리자 세 곳 모두 같은 버전이 됐다.

```text
react 19.3.1
react 19.3.1
react 19.3.1
```

React, react-dom, 스타일 라이브러리, 라우터처럼 앱에 한 벌만 있어야 하는 패키지는 카탈로그로 묶는다. 앱 하나가 새 버전을 먼저 써 봐야 한다면 이름 붙은 카탈로그(`catalogs:`)를 따로 두는 방법도 있지만, 그 앱과 공용 패키지가 다른 버전을 보게 된다는 사실은 그대로다.

## 버전을 하나로 묶을지, 패키지마다 따로 올릴지

저장소 밖으로 나가지 않는 패키지라면 버전 번호는 의미가 거의 없다. 앱은 언제나 같은 커밋의 공용 패키지를 쓴다. 문제는 ui나 format을 npm에 공개하거나, 다른 저장소가 가져다 쓸 때다. 이때 고르는 방법은 두 가지다.

하나는 모든 패키지가 같은 번호를 쓰는 단일 버전이다. 무엇 하나 바뀌면 전부 함께 올라간다. 사용자는 "ui 3.2.0에는 format 3.2.0"만 기억하면 된다. 대신 바뀌지 않은 패키지도 새 버전이 나와서, 받는 쪽은 아무것도 안 바뀐 업데이트를 계속 받는다. 다른 하나는 패키지마다 따로 올리는 독립 버전이다. 바뀐 패키지만 올라가니 정직하지만, 어떤 조합이 함께 테스트됐는지는 사람이 추적해야 한다. Lerna의 fixed 모드와 independent 모드가 이 둘이고, Changesets는 기본이 독립이며 `fixed`(같이 올림), `linked`(올릴 때만 번호를 맞춤) 설정으로 묶음을 만든다.

Changesets의 흐름을 실습 저장소에서 돌려 봤다. 변경을 만든 사람이 PR에 "무엇을 얼마나 올릴지"를 적은 파일을 하나 넣는다.

```md
---
"@shop/format": minor
---

formatPrice에 통화 기호 옵션을 추가했다.
```

```bash
# 쌓인 changeset으로 무엇이 올라갈지 보고, 버전과 CHANGELOG를 고친다
npx changeset status
npx changeset version
```

```text
🦋  info NO packages to be bumped at patch
🦋  ---
🦋  info Packages to be bumped at minor:
🦋  info 
🦋  - @shop/format
🦋  ---
🦋  info NO packages to be bumped at major
```

`changeset version`을 돌리자 format만 1.3.0이 됐고 ui는 그대로다. ui가 적어 둔 `workspace:^`는 배포하면 `^1.2.0`이고, 1.3.0은 그 범위 안에 들어가니 ui를 다시 낼 이유가 없다. 이번에는 같은 changeset을 `major`로 바꿨다.

```bash
# 무엇이 올라갈지 미리 보고, 버전을 고친다
npx changeset status
npx changeset version
git diff -U0 | grep -E '^\+\+\+|^[-+] *"version"'
```

```text
🦋  info Packages to be bumped at patch:
🦋  info 
🦋  - @shop/ui
🦋  - @shop/admin
🦋  - @shop/web
🦋  ---
🦋  info NO packages to be bumped at minor
🦋  ---
🦋  info Packages to be bumped at major:
🦋  info 
🦋  - @shop/format
```


    { args: ["workspace:1.2.0", "1.2.0"], expected: "1.2.0", label: "workspace:1.2.0" },
    { args: ["^2.1.1", "1.2.0"], expected: "^2.1.1", label: "일반 범위는 그대로" },
  ]}
/>

버전 번호가 무엇을 약속하는지, 캐럿 범위가 실제로 어디까지 여는지, Changesets 릴리스 PR이 어떻게 돌아가는지는 [Semantic Versioning](/posts/semantic-versioning)에 정리했다.

## 경로마다 주인을 정한다

저장소를 합치면 누구나 아무 파일이나 고칠 수 있게 된다. 이걸 그대로 두면 결제 팀의 PR이 디자인 시스템 버튼의 여백을 바꾸고, 아무도 모른 채 머지된다. 그래서 모노레포의 경계는 세 겹으로 친다.

첫째는 리뷰 책임이다. GitHub의 `CODEOWNERS`에 경로별 주인을 적고, 브랜치 보호 규칙에서 코드 주인의 승인을 필수로 켠다. 여러 줄에 걸리면 파일에서 마지막에 맞는 줄이 이긴다.

```text
# .github/CODEOWNERS
*                      @shop/platform
/apps/web/             @shop/storefront
/apps/admin/           @shop/backoffice
/packages/ui/          @shop/design-system
/packages/format/      @shop/storefront
/pnpm-workspace.yaml   @shop/platform
```

루트 설정 파일과 카탈로그를 플랫폼 팀에 묶어 둔 이유는 앞에서 봤다. 카탈로그의 React 한 줄이 모든 앱의 런타임을 바꾼다.

둘째는 import 규칙이다. 앞에서 본 `exports`와 pnpm의 엄격한 링크가 기본 울타리가 된다. 그 위에 "앱은 다른 앱을 import하지 않는다", "ui는 format까지만 쓰고 앱을 모른다" 같은 규칙을 린트로 건다. Nx의 `@nx/enforce-module-boundaries`나 `eslint-plugin-boundaries`가 패키지에 태그를 붙여 이런 규칙을 검사한다.

셋째는 CI다. 바뀐 경로에 해당하는 패키지와 그 패키지를 쓰는 쪽만 빌드하고 테스트한다. 이게 없으면 저장소가 커질수록 모든 PR이 전부를 빌드하게 된다. 브랜치를 길게 가져가지 않고 경로로 경계를 나누는 이유는 [브랜치 전략](/posts/git-branching-strategy)의 모노레포 부분과 이어지고, CI 쪽은 [다음 글](/posts/monorepo-build-cache)에서 실제로 시간을 재 본다.

## 모노레포에서 자주 밟는 것들

앱이 다른 앱의 파일을 import한다. web의 장바구니 컴포넌트가 좋아 보여서 admin이 `../../web/src/cart`를 부르기 시작하면 두 앱은 따로 배포할 수 없게 된다. 두 곳에서 쓰는 순간 `packages/`로 올린다. 이 블로그 저장소의 "두 군데 이상이면 공용으로 올린다"는 규칙과 같은 이야기다.

공용 패키지가 하나뿐이고 이름이 `common`이나 `shared`다. 처음엔 편하지만 곧 모든 것이 거기로 들어가고, 거기 한 줄을 고치면 모든 앱이 다시 빌드된다. 쓰임새별로 쪼갠다(`ui`, `format`, `api-client`, `eslint-config`).

내부 패키지에 루트 상대 경로나 `paths`로 의존한다. 위에서 본 것처럼 지도에서 선이 빠져 빌드 순서와 캐시가 틀어진다.

빌드형 패키지의 `dist`를 커밋하거나, 반대로 `dist`가 있다고 가정한다. 깨끗한 CI에서 처음 빌드할 때만 실패한다. `dist`는 `.gitignore`에 넣고 빌드 순서는 도구에 맡긴다.

설치 스크립트를 무심코 허용한다. pnpm 10은 의존성의 `postinstall` 같은 스크립트를 기본으로 실행하지 않고, 설치 끝에 이런 안내를 띄운다.

```text
│   Ignored build scripts: esbuild@0.28.2.                                     │
│   Run "pnpm approve-builds" to pick which dependencies should be allowed     │
│   to run scripts.                                                            │
```

꼭 필요한 패키지만 `pnpm approve-builds`로 허용하고, 그 결과가 적힌 워크스페이스 설정을 커밋해서 팀 전체가 같은 허용 목록을 쓰게 한다.

## 같은 지도 위에서 일한다

모노레포는 여러 앱과 패키지를 한 저장소에 두고, 그 관계를 `package.json`의 의존성으로 적어 도구가 읽게 만드는 방식이다. `workspace:`는 저장소 안을 가리키는 링크가 되고, `exports`는 공개 API이자 경계가 되며, 카탈로그는 한 벌만 있어야 하는 라이브러리의 버전을 하나로 묶는다. 이 지도가 정확해야 빌드 순서와 버전 전파가 맞고, React가 두 벌 들어가는 일도 막힌다. 지도를 따라 바뀐 것만 빌드하는 방법은 [모노레포 빌드: 작업 그래프와 바뀐 것만 빌드하기](/posts/monorepo-build-cache)에서 이어서 본다.

## 면접에서 나올 만한 질문

### 모노레포를 왜 쓰나요?

여러 패키지에 걸친 변경을 커밋 하나로 묶고, 그 변경이 누구를 깨뜨리는지 머지 전에 알기 위해서다. 저장소가 따로면 공용 패키지를 고칠 때마다 배포하고 각 앱에서 버전을 올리는 PR이 따라붙고, 그 사이 앱마다 다른 버전을 쓰게 된다. 대신 CI와 도구를 모든 팀이 공유하고, 저장소가 커지면 바뀐 것만 빌드하는 장치가 필요하다.

### 모노레포와 모놀리스는 어떻게 다른가요?

모노레포는 코드를 두는 방식이고 모놀리스는 실행하고 배포하는 방식이다. 한 저장소 안에서도 앱은 따로 빌드되고 따로 배포될 수 있다. 반대로 저장소가 여럿이어도 한 번에 함께 배포해야 하면 사실상 모놀리스다.

### pnpm의 workspace 프로토콜은 무엇이고, 그냥 버전 범위를 쓰면 안 되나요?

`workspace:`는 레지스트리에 묻지 않고 저장소 안의 패키지로 링크하라는 표기다. pnpm 9부터는 일반 범위를 쓰면 레지스트리에서 찾기 때문에 실습에서는 404가 났고, 같은 이름의 공개 패키지가 있으면 그게 설치되는 의존성 혼동 위험도 있다. 배포할 때는 `workspace:^`가 `^1.2.0`처럼 실제 범위로 바뀌어 올라간다.

### 내부 패키지를 빌드해서 쓰는 것과 소스로 쓰는 것은 무엇이 다른가요?

소스형은 `exports`가 TS 파일을 바로 가리켜서 빌드 단계가 없고 수정이 바로 보인다. 대신 쓰는 앱마다 그 소스를 다시 변환하고 타입 검사하며, 저장소 밖으로 내보낼 수 없다. 빌드형은 `dist`와 `.d.ts`를 만들어야 해서 빌드 순서가 필요하지만, 결과를 캐시하고 그대로 배포할 수 있다.

### 공용 UI 패키지를 쓰는 앱에서 Invalid hook call이나 useState가 null이라는 에러가 납니다. 어디부터 보나요?

React가 두 벌 들어갔는지부터 본다. `pnpm -r list react`로 버전이 갈렸는지 보고, 공용 패키지 폴더와 앱 폴더에서 `require.resolve("react")`가 같은 경로를 가리키는지 확인한다. 링크로 연결된 공용 패키지는 자기 폴더 기준으로 React를 찾기 때문에, 버전이 다르면 번들에 둘이 들어간다. 번들러의 dedupe로 급히 막을 수 있지만, 카탈로그로 버전을 하나로 맞추는 것이 해결이다.

### tsconfig paths로 패키지를 연결하면 무엇이 문제인가요?

도구마다 별칭을 따로 알려 줘야 하고, Node처럼 모르는 도구에서는 바로 깨진다. 게다가 `package.json`에 의존 관계가 남지 않는다. 패키지 매니저와 빌드 도구가 그 관계를 몰라서 빌드 순서와 캐시 무효화가 틀어진다.

### 패키지마다 독립 버전과 단일 버전 중 무엇을 고르나요?

외부 사용자가 패키지를 골라 쓰고 변경 빈도가 서로 다르면 독립 버전이 정직하다. 패키지들이 항상 함께 쓰이고 조합을 설명하기 어렵다면 단일 버전이 쉽다. Changesets는 독립이 기본이고 `fixed`, `linked`로 묶음을 만들 수 있으며, 깨는 변경이 나면 범위를 벗어난 의존 패키지까지 따라 올린다.

### 모노레포에서 팀 사이 경계는 어떻게 지키나요?

경로별 CODEOWNERS로 리뷰 책임을 나누고, `exports`와 pnpm의 엄격한 링크로 공개하지 않은 파일과 선언하지 않은 의존성을 막는다. 그 위에 "앱끼리는 import하지 않는다" 같은 규칙을 린트로 검사하고, CI는 바뀐 경로와 그것에 의존하는 패키지만 빌드하고 테스트한다.
