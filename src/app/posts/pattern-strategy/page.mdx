결제 화면의 쿠폰 할인 함수를 맡았다. 처음엔 정률 할인 하나였다. 한 달 뒤 정액 할인이 붙고, 다음 달에는 "5만 원 이상 3천 원, 10만 원 이상 8천 원" 같은 구간 할인이 붙었다. 이번 주에는 마케팅팀이 "새 할인 방식을 A/B 테스트로 절반에게만 써 보자"고 한다. 함수는 이미 `if (coupon.type === ...)` 다섯 갈래고, 갈래마다 테스트하려면 결제 흐름 전체를 띄워야 한다.

같은 일(할인 금액 계산)을 하는 방법이 여러 개이고, 그중 하나를 골라 쓰는 상황이다. 전략(Strategy) 패턴은 이 "방법"을 하나씩 떼어 같은 모양의 객체(또는 함수)로 만들고, 쓰는 쪽은 그 모양만 알게 한다. 시리즈 지도는 [디자인 패턴 개요](/posts/design-patterns-overview)에 있다. 개요에서 배송비 규칙을 함수 표로 바꾼 짧은 예를 봤는데, 이 글은 그 뒤의 이야기다. 누가 전략을 고르는지, 전략이 실제 라이브러리에서 어떤 모양인지, 어디서 실수하는지를 본다.

## 쿠폰이 늘 때마다 커지는 함수

```ts
type Coupon =
  | { type: "percent"; rate: number }
  | { type: "fixed"; amount: number }
  | { type: "tiered"; tiers: [min: number, amount: number][] };

function priceAfterCoupon(price: number, coupon: Coupon): number {
  if (coupon.type === "percent") {
    return price - Math.floor((price * coupon.rate) / 100);
  } else if (coupon.type === "fixed") {
    return Math.max(0, price - coupon.amount);
  } else if (coupon.type === "tiered") {
    let off = 0;
    for (const [min, amount] of coupon.tiers) if (price >= min) off = Math.max(off, amount);
    return price - off;
  }
  return price;
}
```

이 정도면 아직 괜찮다. 함수가 아프기 시작하는 건 갈래마다 따로 필요한 것이 생길 때다. 구간 할인은 회원 등급을 봐야 하고, 새 할인 방식은 외부 추천 서버에 물어봐야 하고, A/B 테스트는 사용자마다 다른 계산을 써야 한다. 그러면 이 함수가 회원 정보, 추천 서버 클라이언트, 실험 설정을 모두 받게 된다. 정률 할인 한 줄을 테스트하려 해도 그 의존성을 모두 준비해야 한다.

## 할인 계산을 갈아 끼울 수 있게

전략 패턴의 참여자는 셋이다. 알고리즘 하나를 쓰는 Context(결제), 알고리즘의 공통 모양인 Strategy 인터페이스, 그리고 실제 계산을 하는 ConcreteStrategy들이다. Context는 지금 어느 전략을 들고 있는지 모른다. 인터페이스대로 부를 뿐이다.

```ts
interface Cart {
  subtotal: number;
  memberTier: "basic" | "vip";
}

interface DiscountPolicy {
  readonly id: string;
  discount(cart: Cart): number; // 깎아 줄 금액만 돌려준다
}

class PercentOff implements DiscountPolicy {
  readonly id = "percent";
  constructor(private readonly rate: number) {}
  discount(cart: Cart) {
    return Math.floor((cart.subtotal * this.rate) / 100);
  }
}

class TieredOff implements DiscountPolicy {
  readonly id = "tiered";
  constructor(private readonly tiers: [min: number, amount: number][]) {}
  discount(cart: Cart) {
    const base = Math.max(0, ...this.tiers.filter(([min]) => cart.subtotal >= min).map(([, a]) => a));
    return cart.memberTier === "vip" ? base * 2 : base; // 등급 규칙은 이 전략만 안다
  }
}

class Checkout {
  constructor(private policy: DiscountPolicy) {}
  usePolicy(policy: DiscountPolicy) {
    this.policy = policy; // 실행 중에도 바꿀 수 있다
  }
  total(cart: Cart) {
    const off = Math.min(cart.subtotal, this.policy.discount(cart)); // 0원 아래로는 안 내려간다
    return cart.subtotal - off;
  }
}

const cart: Cart = { subtotal: 72000, memberTier: "vip" };
const checkout = new Checkout(new PercentOff(10));
checkout.total(cart); // 64800
checkout.usePolicy(new TieredOff([[50000, 3000], [100000, 8000]]));
checkout.total(cart); // 66000
```

`Checkout`에는 쿠폰 종류가 한 번도 나오지 않는다. 0원 아래로 내려가지 않게 막는 규칙처럼 모든 할인에 공통인 것은 Context에 남고, 종류마다 다른 계산만 전략으로 나갔다. 새 할인 방식은 `DiscountPolicy`를 구현한 클래스 하나를 더하는 것으로 끝나고, 결제 코드는 열지 않는다. 개방 폐쇄 원칙이 말하는 "확장에는 열리고 수정에는 닫힌" 상태가 이것이다.

## 누가 전략을 고르나

전략을 떼어 내면 질문이 하나 남는다. 그럼 `new PercentOff(10)`은 누가 쓰나? `if (coupon.type === ...)`가 사라진 게 아니라 다른 곳으로 옮겨 갔을 뿐이다. 이게 정상이다. 고르는 일은 한 번, 시스템의 가장자리에서 하고, 안쪽은 고른 결과만 받는다. 아래 그림에서 다음을 누르면 요청 하나가 들어와 전략이 정해지는 순서가 보인다.

이 구조는 테스트에서 바로 값을 한다. `TieredOff`는 결제 흐름 없이 `new TieredOff(...).discount({ subtotal: 72000, memberTier: "vip" })`만으로 확인할 수 있다. `Checkout` 쪽은 `{ id: "fake", discount: () => 5000 }` 같은 가짜 전략을 넣어 "할인이 소계보다 크면 0원에서 멈추나"만 본다. 할인 규칙과 결제 규칙을 따로 확인할 수 있게 된다.

### 정책 표에 사용자 입력을 그대로 넣으면

이름으로 전략을 찾는 표를 평범한 객체로 만들 때 흔히 하는 실수가 있다. 쿠폰 종류가 요청 바디에서 그대로 온다면, 객체 프로토타입에 원래 있는 이름이 키로 들어올 수 있다.

```ts
type Strategy = (price: number, coupon: object) => number | string;
const strategies: Record<string, Strategy> = {
  percent: (p, c) => p - Math.floor((p * (c as { rate: number }).rate) / 100),
};
const pick = (type: string) => strategies[type] ?? ((p: number) => p);

console.log(pick("toString")(39000, {}), "|", pick("constructor")(39000, {}));
```

```text
[object Undefined] | [Number: 39000]
```

`toString`과 `constructor`는 표에 넣은 적이 없지만 `Object.prototype`에서 찾아져 기본값으로 넘어가지 않는다. 가격 자리에 문자열이나 래퍼 객체가 들어간다. 사용자 입력으로 고르는 표는 `new Map()`이나 `Object.create(null)`로 만들거나, `Object.hasOwn(strategies, type)`으로 먼저 확인한다. 타입스크립트에서는 키를 `keyof typeof strategies`로 좁혀 두되, 바깥 입력은 런타임 검증(zod 같은)을 거친 뒤에만 그 타입이 된다.

## 함수 하나면 되는 전략

자바스크립트에서는 전략이 함수 하나인 경우가 훨씬 많다. 이미 매일 쓴다. `Array.prototype.sort`의 비교 함수가 가장 흔한 전략이다. 정렬 알고리즘(V8은 TimSort)은 그대로 두고 "둘 중 무엇이 앞인가"만 바꿔 끼운다. 같은 배열에 비교 전략 세 개를 넣어 보자.

함수로 쓰는 전략은 라이브러리 옵션에도 많다. TanStack Query v5의 `retryDelay`는 몇 번째 재시도인지를 받아 기다릴 시간을 돌려주는 함수이고, 기본값이 `attemptIndex => Math.min(1000 * 2 ** attemptIndex, 30000)`이다. 백오프 방식이 마음에 들지 않으면 함수 하나를 바꿔 넣는다. Go 표준 라이브러리의 `sort.Slice(s, less)`, 자바의 `Comparator`도 같은 자리다.

그럼 클래스 형태는 언제 값을 하나? 전략이 메서드 하나로 끝나지 않을 때다. 할인 정책이 계산 말고도 화면에 보여 줄 이름, "이 장바구니에 쓸 수 있나" 검사, 로그에 남길 id를 함께 가져야 한다면 객체 하나로 묶는 편이 낫다. 설정값(구간, 비율)을 생성자에서 받아 들고 있는 것도 클래스가 편하다. 클로저로도 되지만 필드가 셋을 넘으면 읽기 어렵다.

## 비교 함수 하나로 정렬이 몇 배 느려진다

비교 전략은 결과만 바꾸는 게 아니라 속도도 바꾼다. 비교 함수는 정렬 한 번에 수십만~수백만 번 불리기 때문이다. 한글 이름 10만 개를 세 전략으로 정렬해 일곱 번씩 재고 중앙값을 냈다(Node.js 22.22).

```ts
declare const names: string[]; // "김민서" 같은 이름 100,000개

const byCodeUnit = (a: string, b: string) => (a < b ? -1 : a > b ? 1 : 0);
const byLocale = (a: string, b: string) => a.localeCompare(b, "ko");
const byCollator = new Intl.Collator("ko").compare; // 한 번 만들어 둔 비교기를 재사용

for (const cmp of [byCodeUnit, byLocale, byCollator]) names.slice().sort(cmp);
```

```text
a < b          median 124 ms
localeCompare  median 613 ms
Intl.Collator  median 271 ms
```

`localeCompare(b, "ko")`는 같은 규칙의 `Intl.Collator`를 한 번 만들어 두고 쓰는 것보다 두 배 넘게 느렸다. 코드 단위 비교는 가장 빠르지만 앞의 그림처럼 대소문자와 숫자에서 틀린다. 한글 완성형 음절은 유니코드에 가나다순으로 놓여 있어서 한글만 있으면 우연히 맞아 보이는데, 영문이나 숫자가 섞이면 바로 어긋난다. MDN도 큰 배열을 정렬할 때는 `Intl.Collator`의 `compare`를 쓰라고 권한다.

전략을 함수로 바꿔 끼울 수 있게 해 두면 이런 차이를 쉽게 잴 수 있다는 것도 장점이다. 호출하는 쪽은 그대로 두고 함수 하나만 바꿔 같은 입력으로 비교하면 된다.

## Passport는 로그인 방법을 이름으로 등록한다

전략 객체는 결과를 돌려주지 않고 Passport가 붙여 준 `success`, `fail`, `error`, `redirect`, `pass` 중 하나를 부른다. API 키 전략을 직접 하나 만들어 로컬 전략과 함께 걸었다.

```ts
declare class PassportStrategy {
  name?: string;
  success(user: object): void;
  fail(status?: number): void;
}
interface Req { headers: Record<string, string | undefined> }

class ApiKeyStrategy extends PassportStrategy {
  constructor(private readonly verify: (key: string) => object | null) {
    super();
    this.name = "apikey";
  }
  authenticate(req: Req) {
    const key = req.headers["x-api-key"];
    if (!key) return this.fail(401); // 이 전략으로는 판단할 수 없다
    const user = this.verify(key);
    return user ? this.success(user) : this.fail(401);
  }
}
```

```text
x-api-key        → next() {"id":1,"via":"apikey"}
form login       → next() {"id":2,"via":"local"}
wrong password   → 401
```

설정 파일 안에도 전략이 있다. Kubernetes Deployment의 `spec.strategy.type`은 `RollingUpdate`와 `Recreate` 중 하나를 고르는 자리이고([배포 글](/posts/k8s-deployment)), Redis의 `maxmemory-policy`는 메모리가 찼을 때 무엇을 지울지(`allkeys-lru`, `volatile-ttl` 등)를 고르는 자리다. Nginx `upstream`에서 `least_conn` 한 줄로 분배 방식을 바꾸는 것도 같다([분배 알고리즘](/posts/load-balancing-algorithms)). 쓰는 쪽(배포 컨트롤러, 메모리 관리자, 프록시)은 그대로고, 방법만 이름으로 고른다.

## 전략마다 필요한 재료가 다를 때

전략 패턴이 어려워지는 지점은 인터페이스 설계다. 정률 할인은 소계만 있으면 되지만, 구간 할인은 회원 등급이 필요하고, 새 할인은 상품 목록과 지난 구매 이력까지 필요하다고 하자. 인터페이스를 `discount(subtotal: number)`로 정했다면 새 전략을 넣을 수 없다.

흔한 해법은 두 가지다. 하나는 메서드 인자를 넓은 컨텍스트 객체 하나로 두는 것이다(`discount(cart: Cart)`). 전략마다 필요한 것만 꺼내 쓴다. 대신 `Cart`가 점점 커지고, 정률 할인은 쓰지도 않는 필드를 테스트마다 채워야 한다. 다른 하나는 전략마다 다른 재료를 생성자로 받는 것이다. 추천 서버 클라이언트가 필요한 전략은 만들 때 그 클라이언트를 받고, 메서드 인자는 모두에게 공통인 것만 남긴다. 앞의 `TieredOff`가 구간 표를 생성자로 받은 것이 이 방식이다.

또 하나 흔한 실수는 구현이 하나뿐인 전략 인터페이스다. "나중에 바뀔 수도 있으니까"로 만든 `IPasswordHasher`에 구현체가 `BcryptHasher` 하나뿐이면 읽는 사람만 한 번 더 건너간다. 두 번째 구현이 실제로 생길 때 뽑아도 늦지 않다. 테스트용 가짜를 넣기 위한 것이라면 함수 인자 하나로도 충분한 경우가 많다.

## 이름이 헷갈리는 이웃들

전략과 모양이 같은 패턴이 여럿 있어서 면접에서 자주 묻는다. [상태 패턴](/posts/pattern-state)은 구조가 같지만 필드를 바꾸는 주체가 다르다. 전략은 바깥이 골라 넣고, 상태는 객체가 일하면서 스스로 바꾼다.

[템플릿 메서드](/posts/pattern-template-method)는 같은 문제를 상속으로 푼다. 알고리즘의 뼈대를 상위 클래스에 두고 바뀌는 단계를 하위 클래스가 채운다. 전략은 바뀌는 부분 전체를 객체로 꺼내 합성한다. 상속은 컴파일할 때 정해지고, 전략은 실행 중에 바꿀 수 있다. 바뀌는 단계가 하나라면 전략 쪽이 대체로 가볍다.

[브리지](/posts/pattern-bridge)와의 차이는 그 글에서 자세히 다뤘다. 짧게 말하면 쓰는 쪽도 계층으로 늘어나는가다. [커맨드](/posts/pattern-command)는 함수 하나를 객체로 감싼다는 점이 같지만, 전략이 "어떻게"를 바꾼다면 커맨드는 "무엇을"을 값으로 만들어 나중에 실행하거나 되돌린다.

## 직접 만드는 할인 전략

`applyCoupon(price, coupon)`을 완성해 보자. 쿠폰 종류마다 계산을 전략으로 나누고, 이름으로 골라 쓴다. 모르는 종류가 오면 가격을 그대로 돌려준다.

- `percent`: `rate`%를 깎는다. 깎는 금액은 원 단위 아래를 버린다.
- `fixed`: `amount`원을 깎되 0원 아래로 내려가지 않는다.
- `tiered`: `tiers`의 `[최소 금액, 할인액]` 중 조건을 만족하는 가장 큰 할인 하나를 적용한다.

전략 패턴은 같은 일을 하는 여러 방법을 같은 모양으로 맞춰 떼어 내고, 쓰는 쪽은 그 모양만 알게 하는 패턴이다. 분기는 사라지는 게 아니라 가장자리의 고르는 곳 한 군데로 모인다. 자바스크립트에서는 대부분 함수 하나로 충분하고, 전략이 이름이나 검사 같은 여러 동작을 함께 가져야 할 때 객체로 묶는다.

## 면접에서 나올 만한 질문

### 전략 패턴은 무엇이고 언제 쓰나요?

같은 일을 하는 알고리즘 여러 개를 같은 인터페이스로 맞춰 떼어 내고, 쓰는 쪽(Context)은 인터페이스만 알게 하는 패턴이다. 종류에 따라 갈라지는 `if`가 계속 늘거나, 실행 중에 방법을 바꿔야 하거나(A/B 테스트, 설정), 각 방법을 따로 테스트하고 싶을 때 쓴다. 새 방법은 구현체 하나를 더해 넣으므로 Context를 고치지 않는다.

### 전략 패턴을 써도 결국 어딘가에서 if로 골라야 하지 않나요?

그렇다. 분기가 사라지는 게 아니라 시스템 가장자리의 한 곳으로 모인다. 요청을 받는 핸들러나 설정을 읽는 곳에서 이름으로 전략을 한 번 찾고, 안쪽 코드는 고른 결과만 받는다. 같은 분기가 여러 메서드에 흩어져 있던 것이 한 곳으로 줄어드는 것이 이득이다.

### 자바스크립트에서 전략을 클래스로 만들어야 하나요?

대부분은 함수 하나로 충분하다. `sort`의 비교 함수나 TanStack Query의 `retryDelay`가 그런 예다. 전략이 계산 말고도 이름, 적용 가능 여부 검사, 설정값 같은 여러 동작과 데이터를 함께 가져야 하면 객체나 클래스로 묶는 편이 읽기 쉽다.

### 전략 패턴과 상태 패턴은 무엇이 다른가요?

구조는 같지만 필드를 바꾸는 주체가 다르다. 전략은 Client나 설정이 골라 넣고 보통 그대로 두며, 전략끼리 서로를 모른다. 상태는 객체가 일하는 도중에 스스로 다음 상태로 바뀌고, 상태 객체가 다음 상태를 안다.

### 전략 패턴과 템플릿 메서드는 어떻게 고르나요?

둘 다 알고리즘의 일부를 바꾸지만 전략은 합성, 템플릿 메서드는 상속을 쓴다. 바뀌는 부분을 실행 중에 바꿔야 하거나 여러 축이 따로 바뀐다면 전략이 낫다. 뼈대와 순서를 상위 클래스가 강하게 지켜야 하고 바뀌는 단계가 여럿이 함께 움직인다면 템플릿 메서드가 자연스럽다.

### 전략마다 필요한 인자가 다르면 인터페이스를 어떻게 정하나요?

모두에게 공통인 것만 메서드 인자로 두고, 전략마다 다른 재료는 생성자로 받게 하는 방법이 깔끔하다. 아니면 넓은 컨텍스트 객체 하나를 넘기고 전략이 필요한 것만 꺼내 쓰게 할 수 있지만, 그 객체가 점점 커진다. 인터페이스를 구현 하나에 맞춰 너무 좁게 잡으면 두 번째 전략을 넣을 때 깨진다.

### 전략을 이름으로 찾는 표를 만들 때 주의할 점은 무엇인가요?

사용자 입력을 키로 쓴다면 평범한 객체 대신 `Map`이나 `Object.create(null)`을 쓰거나 `Object.hasOwn`으로 확인해야 한다. 그렇지 않으면 `toString`, `constructor` 같은 프로토타입의 이름이 찾아져 기본값으로 넘어가지 않고 엉뚱한 함수가 실행된다. 실제로 가격 자리에 `[object Undefined]` 같은 문자열이 들어간다.
