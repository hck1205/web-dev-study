Express의 미들웨어 순서와 async 에러, 정상 종료는 [Express 미들웨어](/posts/express-middleware)에서, Node가 요청을 어떤 스레드에서 처리하는지는 [Node.js 서버 런타임](/posts/nodejs-server-runtime)에서 다뤘으니 여기서는 프레임워크 사이의 차이에 집중한다.

## 같은 주문 API를 네 번 만든다

```bash
curl -s localhost:4001/orders/1
curl -s -X POST -H 'content-type: application/json' -d '{"sku":"B-7","qty":0}' localhost:4001/orders
curl -s localhost:4001/orders/99
```

```text
{"error":"invalid_body"}
{"error":"not_found"}
== Fastify (4002)
{"id":"1","sku":"A-100","qty":2,"status":"paid"}
{"statusCode":400,"code":"FST_ERR_VALIDATION","error":"Bad Request","message":"body/qty must be >= 1"}
```

응답 모양에서 벌써 차이가 보인다. Express와 Hono의 400은 내가 직접 쓴 검증 코드가 만든 것이고, Fastify의 400은 프레임워크가 스키마를 보고 만든 것이며, Nest의 400과 404는 예외 클래스를 던지면 프레임워크가 정해진 모양으로 바꿔 준 것이다. 누가 검증하고 누가 에러 모양을 정하는지가 네 프레임워크를 가르는 첫 번째 기준이다.

## Express: 함수를 줄 세운다

Express는 가장 단순하다. 요청이 오면 등록한 함수들을 순서대로 부르고, 각 함수가 `next()`를 부르면 다음으로 넘어간다. 프레임워크가 하는 일은 라우팅과 이 줄 세우기 정도다.

```js
import express from "express";
const app = express();
app.use(express.json({ limit: "10kb" }));

app.post("/orders", (req, res) => {
  const { sku, qty } = req.body ?? {};
  // 검증은 내가 직접 한다. 보통은 zod 같은 라이브러리를 미들웨어로 붙인다
  if (typeof sku !== "string" || !Number.isInteger(qty) || qty < 1 || qty > 100)
    return res.status(400).json({ error: "invalid_body" });
  const o = { id: String(orders.size + 1), sku, qty, status: "pending" };
  orders.set(o.id, o);
  res.status(201).json(o);
});
```

장점은 단순함과 생태계다. 미들웨어가 어디에나 있고, 대부분의 Node 개발자가 이미 안다. 단점도 같은 곳에서 나온다. 검증, 에러 모양, 로깅, 폴더 구조를 모두 팀이 정해야 한다. 정하지 않으면 라우트마다 검증 방식이 다른 코드가 쌓인다.

`next()`가 프로미스가 아니라는 점도 알아 둘 만하다. 미들웨어에서 `next()` 뒤에 코드를 써 보면 차이가 보인다.

```text
express: A before
express: handler
express: A after next()
hono: A before
hono: handler
hono: A after, status 200
```

이 실험에서는 핸들러가 동기라 Express도 "after"가 핸들러 뒤에 찍혔다. 그런데 핸들러가 `await`를 쓰는 순간 Express의 "after"는 핸들러가 끝나기 전에 실행된다. `next()`는 다음 함수를 부르고 바로 돌아올 뿐 그 함수의 비동기 작업을 기다리지 않기 때문이다. 그래서 Express에서 "응답이 끝난 뒤 시간을 잰다"는 미들웨어는 `res.on("finish")`로 짠다. Hono와 Koa는 `await next()`로 안쪽이 다 끝날 때까지 기다리는 양파 구조라 앞뒤 처리를 한 함수 안에 쓸 수 있다.

## Fastify: 스키마가 검증과 직렬화를 같이 한다

Fastify는 라우트마다 JSON 스키마를 붙이게 한다. 같은 스키마가 요청을 검증하고(Ajv), 응답을 직렬화한다(fast-json-stringify).

```js
const Order = {
  type: "object",
  properties: { id: { type: "string" }, sku: { type: "string" }, qty: { type: "integer" }, status: { type: "string" } },
};

app.post("/orders", {
  schema: {
    body: {
      type: "object", required: ["sku", "qty"], additionalProperties: false,
      properties: { sku: { type: "string", minLength: 1 }, qty: { type: "integer", minimum: 1, maximum: 100 } },
    },
    response: { 201: Order },
  },
}, async (req, reply) => {
  // 여기 들어왔다면 req.body는 이미 스키마를 통과했다
  const o = { id: String(orders.size + 1), ...req.body, status: "pending" };
  orders.set(o.id, o);
  return reply.code(201).send(o);
});
```

응답 스키마에는 숨은 효과가 하나 있다. 실험용 주문 데이터에 `internalNote: "vip"`라는 내부 필드를 일부러 넣어 뒀는데, `GET /orders/1` 응답에는 나오지 않았다. 직렬화가 스키마에 적힌 필드만 쓰기 때문이다. DB 행을 그대로 돌려주다가 비밀번호 해시 같은 컬럼이 새는 사고를 구조로 막는다. 거꾸로, 새 필드를 추가하고 스키마에 안 적으면 응답에서 조용히 빠진다. "필드를 추가했는데 안 나와요"는 Fastify에서 자주 듣는 질문이다.

요청 검증 쪽에도 기본값이 있다. Fastify는 Ajv를 타입 변환(`coerceTypes`)과 추가 속성 제거(`removeAdditional`)를 켠 채로 쓴다. 그래서 같은 요청을 보내도 Express와 결과가 다르다.

```bash
# qty를 문자열 "3"으로, 스키마에 없는 admin 필드를 붙여서 보낸다
curl -s -X POST -H 'content-type: application/json' \
  -d '{"sku":"B-7","qty":"3","admin":true}' localhost:4002/orders
```

```text
{"id":"2","sku":"B-7","qty":3,"status":"pending"}
```

`"3"`은 숫자 3으로 바뀌었고, `admin`은 `additionalProperties: false`인데도 거절되지 않고 지워졌다. 같은 요청에 Express 코드는 `invalid_body`를 돌려줬다. 어느 쪽이 맞다기보다 기본값을 알고 써야 한다. 엄격하게 거절하고 싶으면 Fastify 생성 옵션의 `ajv.customOptions`로 두 설정을 끈다. 이 관대한 기본값 이야기는 [FastAPI의 Pydantic](/posts/fastapi-basics)에서도 비슷하게 나온다.

Fastify의 또 다른 축은 플러그인과 캡슐화다. `app.register(plugin)`으로 등록한 플러그인 안에서 붙인 데코레이터와 훅은 그 플러그인 범위 안에만 보인다. 결제 라우트에만 인증 훅을 걸고 싶으면 결제 플러그인 안에서 훅을 건다. 전역으로 공유하고 싶은 것(DB 연결 같은)은 `fastify-plugin`으로 감싸 캡슐화를 푼다. Express에서 "이 미들웨어가 어디까지 걸리나"를 등록 순서로 추적하던 일을, Fastify는 범위로 정리한다.

요청이 지나가는 단계도 이름이 붙어 있다. 훅을 단계마다 하나씩 걸고 `inject`로 요청을 넣어 봤다.

```text
fastify: onRequest
fastify: preValidation
fastify: preHandler
fastify: handler
fastify: onSend
fastify: onResponse
```

아래 그림에서 다음을 누르면 요청 하나가 이 단계를 차례로 지나간다. 검증이 핸들러 앞의 정해진 자리에 있어서, 인증 훅(예: [API 키 검증](/posts/api-key-hmac-auth))을 `onRequest`에 걸면 잘못된 본문을 파싱하기도 전에 거절할 수 있다.

## NestJS: 구조와 의존성 주입을 프레임워크가 정한다

Nest는 HTTP 처리 자체를 새로 만들지 않는다. 기본으로 Express 위에서 돌고(`@nestjs/platform-express`, Nest 11은 Express 5를 쓴다), 설정 하나로 Fastify 위로 옮길 수 있다. Nest가 더하는 건 구조다. 모듈, 컨트롤러, 프로바이더라는 칸을 정하고, 칸 사이의 의존성은 컨테이너가 넣어 준다.

```ts
@Injectable()
class OrdersService {
  private orders = new Map<string, Order>(/* ... */);
  find(id: string) { return this.orders.get(id); }
}

@Controller("orders")
class OrdersController {
  constructor(private readonly orders: OrdersService) {}   // 컨테이너가 넣어 준다

  @Get(":id")
  get(@Param("id") id: string) {
    const o = this.orders.find(id);
    if (!o) throw new NotFoundException();                  // 404 모양은 Nest가 만든다
    return o;
  }
}

@Module({ controllers: [OrdersController], providers: [OrdersService] })
class OrdersModule {}
```

컨트롤러는 `OrdersService`를 직접 만들지 않는다. 생성자 인자 타입만 적어 두면 Nest가 모듈에 등록된 프로바이더 중에서 맞는 것을 찾아 넣는다. 테스트에서는 같은 자리에 가짜 서비스를 넣으면 된다. 스프링의 [IoC와 DI](/posts/spring-ioc-di)와 같은 생각이고, 실제로 스프링이나 Angular를 써 본 사람이 Nest에 빨리 적응한다.

이 주입은 TypeScript가 생성자 인자 타입을 런타임 메타데이터로 남겨 줘야 동작한다(`emitDecoratorMetadata`). 이 설정을 끄고 같은 코드를 컴파일해 봤다. 서버는 멀쩡히 뜨고, 요청이 와야 터진다.

```text
{"statusCode":500,"message":"Internal server error"}
ERROR [ExceptionsHandler] TypeError: Cannot read properties of undefined (reading 'find')
    at OrdersController.get (.../nest2/dist2/main.js:33:31)
```

생성자 인자를 무엇으로 채울지 알 수 없으니 `this.orders`가 `undefined`로 남았다. 실무에서 이 증상은 tsc 대신 esbuild 계열 도구(tsx, 일부 번들러 설정)로 Nest를 돌릴 때 자주 나온다. esbuild는 타입 메타데이터를 내보내지 않는다. Nest는 tsc나 SWC(메타데이터 지원 설정)로 빌드한다.

Nest는 요청 처리 단계에도 이름을 붙인다. 인증·권한은 Guard, 입력 변환·검증은 Pipe(보통 `ValidationPipe`와 class-validator), 응답 가공·로깅은 Interceptor, 예외를 응답으로 바꾸는 건 Exception Filter가 맡는다. Fastify의 훅과 비슷한 자리를 데코레이터로 붙이는 셈이다.

대가는 무게다. 파일과 데코레이터가 많고, 작은 API에도 모듈·컨트롤러·서비스를 다 만들게 된다. 에러 스택이 프레임워크 내부를 여러 겹 지나서 처음에는 읽기 어렵다. 팀이 세 명이고 API가 스무 개면 Express에 규칙 몇 개를 정하는 편이 빠를 수 있다. 팀이 서른 명이고 도메인이 열 개면 Nest가 강제하는 구조가 코드 리뷰의 절반을 대신한다.

## Hono: Request를 받아 Response를 돌려주는 함수

Hono는 Node 전용 프레임워크가 아니다. 웹 표준 `Request`를 받아 `Response`를 돌려주는 `fetch` 함수 하나로 앱이 끝난다. 그래서 같은 코드가 Cloudflare Workers, Deno, Bun, Node(어댑터), AWS Lambda 같은 곳에서 돈다.

```js
import { Hono } from "hono";
const app = new Hono();
app.get("/orders/:id", (c) => c.json({ id: c.req.param("id"), status: "paid" }));

// 서버를 띄우지 않고 웹 표준 Request를 바로 넣어 본다
const res = await app.fetch(new Request("http://local/orders/7"));
console.log(res.status, res.headers.get("content-type"), await res.text());
```

```text
200 application/json {"id":"7","status":"paid"}
```

서버 없이 `app.fetch`에 요청을 넣으면 응답이 나온다. 테스트가 쉬워지고, 런타임은 바깥에서 갈아 끼운다. Node에서는 `@hono/node-server`의 `serve(app.fetch)`가 Node의 요청을 웹 표준 `Request`로 바꿔 넘긴다.

엣지 런타임에 올릴 때는 그 런타임의 제약을 같이 받는다. Node의 `fs`, 네이티브 모듈, 오래 붙잡는 TCP 연결(일반적인 DB 드라이버의 연결 풀)이 없거나 제한된다. 그래서 엣지에서는 HTTP로 부르는 DB나 KV 저장소를 쓴다. 이 제약과 콜드 스타트는 [서버리스의 한계](/posts/serverless-limits)와 [콜드 스타트](/posts/cold-starts)에 있다. 엣지에 올리지 않고 Node에서만 써도 Hono는 가볍고 빠른 선택지다. 타입 추론이 강해서 라우트 정의에서 클라이언트 타입을 뽑아 쓰는 RPC 기능도 있다.

## 라우터는 경로를 어떻게 맞추나

네 프레임워크가 모두 하는 일이 하나 있다. `/orders/:id` 같은 패턴과 실제 경로 `/orders/7`을 맞춰서 `id`를 뽑는다. 가장 단순한 방법은 `/`로 잘라 조각끼리 비교하는 것이다. 아래 그림은 `/orders/:id/items/:itemId`를 `/orders/7/items/3`에 맞추는 과정이다.

## 벤치마크 숫자를 직접 재 보면

autocannon으로 동시 연결 50개, 8초씩 `GET /orders/1`을 두드렸다. 비교 기준으로 프레임워크 없는 `node:http` 서버도 넣었다. 그리고 DB를 부르는 상황을 흉내 내려고 응답 전에 20ms를 기다리는 라우트도 같은 조건으로 쟀다.

```bash
# 동시 연결 50, 2초 워밍업 후 8초 측정, 결과는 JSON으로
npx autocannon -c 50 -d 8 -w 2 -j localhost:4002/orders/1
```

```text
                    메모리 응답(바로)            20ms 기다린 뒤 응답
node:http           23499 req/s  p99  7 ms     2352 req/s  p99 27 ms
Express 5           4267 req/s  p99 27 ms     2071 req/s  p99 37 ms
Fastify 5           15172 req/s  p99 13 ms     2345 req/s  p99 25 ms
Hono (node-server)  18393 req/s  p99 12 ms     2361 req/s  p99 26 ms
NestJS (Express)    3203 req/s  p99 44 ms     1756 req/s  p99 55 ms
```

이 컨테이너는 4코어를 다른 작업과 나눠 쓰고 있었고(측정 중 load average 4~8), 같은 측정을 한 번 더 돌렸을 때는 Fastify가 16370, `node:http`가 13324, Hono가 12544로 순서가 바뀌었다. 그러니 앞의 셋 사이 순위는 이 숫자로 말할 수 없다. 두 번 다 같았던 건 큰 묶음이다. 메모리에서 바로 돌려주는 라우트에서 Fastify·Hono는 Express의 3~5배였고, Nest(Express 위)는 Express보다 조금 더 느렸다. 공개된 벤치마크들이 보여 주는 방향과도 같다.

오른쪽 열이 더 중요하다. 20ms만 기다리게 했더니 다섯 서버가 모두 초당 1700~2400 사이로 모였다. 동시 연결 50개가 각각 20ms씩 걸리면 이론상 최대가 초당 2500이다. 응답 시간 대부분이 기다림이면 프레임워크 오버헤드는 그 안에 묻힌다. 실제 서비스의 요청은 DB 쿼리 몇 개, 다른 서비스 호출, 캐시 조회를 거치고 수 ms에서 수십 ms가 걸린다. 그때 프레임워크 차이는 수십 %가 아니라 몇 %로 줄어든다.

그래도 숫자가 의미 있는 경우가 있다. 캐시 히트가 대부분인 API, 프록시나 게이트웨이처럼 요청을 받아 넘기기만 하는 서버, 응답이 큰 JSON이라 직렬화가 무거운 서버다. 이런 곳에서는 프레임워크 오버헤드가 CPU 사용량으로 바로 보이고, 같은 트래픽을 처리하는 데 필요한 인스턴스 수가 달라진다. 그 외에는 처리량보다 느린 쿼리 하나, 빠진 인덱스 하나, 블로킹 호출 하나가 훨씬 크게 작용한다.

## 서버에서 HTML을 만들던 자리: 템플릿 엔진

API 서버가 아니라 HTML을 돌려주는 서버라면 템플릿 엔진이 붙는다. React가 보편화되기 전 Express 앱의 기본 모양이 이것이었다. `app.set("view engine", "ejs")`로 엔진을 정하고 `res.render("orders", data)`로 HTML을 만든다. 같은 목록을 EJS와 Pug로 그려 봤다. 두 번째 주문의 SKU에는 일부러 스크립트 태그를 넣었다.

```html
<ul>
<% for (const o of orders) { %>  <li><%= o.sku %> x <%= o.qty %></li>
<% } %></ul>
```

```pug
ul
  each o in orders
    li #{o.sku} x #{o.qty}
```

```text
<ul>
  <li>A-100 x 2</li>
  <li>&lt;script&gt;alert(1)&lt;/script&gt; x 1</li>
</ul>
```

두 엔진 모두 같은 HTML을 만들고, 값은 기본으로 이스케이프한다. EJS는 HTML 사이에 JS를 끼워 넣는 모양이고, Pug는 들여쓰기로 태그를 표현해 짧지만 문법을 따로 익혀야 한다. 함정은 이스케이프하지 않는 출력 문법이다. EJS의 `<%- %>`, Pug의 `!{}`를 쓰면 값이 그대로 나간다.

```text
<li><script>alert(1)</script></li>
```

사용자 입력이 이 자리에 들어가면 그대로 [XSS](/posts/xss)다. 템플릿 코드 리뷰에서 `<%-`와 `!{`를 검색하는 것만으로 꽤 많은 구멍이 잡힌다. 그 밖에 eBay가 만든 Marko처럼 스트리밍 렌더링을 앞세운 엔진도 있다.

지금 템플릿 엔진이 남은 자리는 관리자 화면, 이메일 HTML, 간단한 내부 도구, 그리고 JS 없이도 동작해야 하는 페이지다. 화면이 복잡하고 상호작용이 많으면 React 기반의 서버 렌더링으로 간다. 요청마다 서버에서 HTML을 만드는 방식 자체는 같고, 차이는 브라우저에서 그 HTML을 다시 살려 내느냐다([SSR](/posts/rendering-ssr)).

## 팀과 서비스에 맞춰 고르기

네 개를 같은 축에 놓으면 이렇다.

Express는 가장 많은 사람이 알고 자료가 많다. 작은 서비스, 프로토타입, 미들웨어 생태계에 기대야 하는 곳에 맞다. 검증·에러 모양·구조를 팀 규칙으로 정해야 하고, 그걸 안 하면 코드가 제각각이 된다. 이미 Express로 된 서비스를 성능 때문에 옮길 이유는 대부분 없다.

Fastify는 Express와 비슷한 크기의 코드로 검증·직렬화·로깅을 기본으로 가져간다. 새로 만드는 Node API라면 무난한 기본값이다. 스키마를 쓰기 싫으면 장점의 절반을 버리게 된다. TypeBox나 zod 타입 공급자를 쓰면 스키마에서 TypeScript 타입까지 뽑을 수 있다.

NestJS는 구조를 산다. 여러 팀이 같은 코드베이스를 만지고, 도메인이 많고, 스프링 같은 계층 구조에 익숙한 팀에 맞다. 작은 서비스에는 무겁고, 빌드 설정(데코레이터 메타데이터)을 정확히 맞춰야 한다. HTTP 계층은 Express나 Fastify를 고를 수 있으니 성능 걱정으로 Nest를 피할 필요는 없다.

Hono는 실행 위치를 산다. 엣지나 여러 런타임에 같은 코드를 올리고 싶을 때, 작고 빠른 API를 원할 때 맞다. Node 전용 라이브러리를 많이 써야 하는 서비스라면 엣지의 이점이 줄어든다.

어느 쪽이든 프레임워크가 바꿔 주지 않는 것들이 있다. 이벤트 루프를 막는 동기 호출, DB 연결 풀 크기, 타임아웃, 정상 종료, 로그 형식. 프레임워크를 바꿨는데 p99가 그대로라면 대개 이쪽 문제다. 프레임워크와 무관하게 도메인 코드를 HTTP 계층에서 떼어 두면([헥사고날 아키텍처](/posts/hexagonal-architecture)) 나중에 옮기는 비용도 작아진다.

## 마무리

네 프레임워크는 같은 일을 하고, 갈리는 지점은 누가 무엇을 정하느냐다. Express는 거의 모든 것을 팀에 맡기고, Fastify는 스키마로 검증과 직렬화를 정하고, Nest는 모듈과 의존성 주입으로 구조를 정하고, Hono는 웹 표준 인터페이스로 실행 위치를 열어 둔다. 처리량 차이는 실제로 있지만, 응답이 기다림으로 채워지는 순간 대부분 묻힌다. 그래서 숫자보다 팀 규모, 구조를 얼마나 강제하고 싶은지, 어디에 배포할지를 먼저 묻는다.

## 면접에서 나올 만한 질문

### Express와 Fastify의 가장 큰 차이는 무엇인가요?

Express는 등록한 미들웨어를 순서대로 부르는 줄만 제공하고 검증·직렬화·로깅은 팀이 붙인다. Fastify는 라우트에 JSON 스키마를 붙여 Ajv로 요청을 검증하고 fast-json-stringify로 응답을 직렬화하며, Pino 로거와 플러그인 캡슐화를 기본으로 갖는다. 그 결과 같은 코드 크기로 더 많은 것이 정해지고, 단순한 라우트의 처리량도 몇 배 높게 나온다.

### Fastify 응답 스키마를 쓰면 어떤 효과가 있나요?

직렬화가 스키마에 적힌 필드만 써서 빨라지고, 스키마에 없는 필드는 응답에서 빠진다. 그래서 DB 행을 그대로 돌려줘도 내부 필드가 새지 않는다. 반대로 새 필드를 추가하고 스키마를 안 고치면 조용히 사라지니, 응답 필드가 안 나올 때 먼저 스키마를 본다.

### Fastify의 기본 검증이 관대하다는 건 무슨 뜻인가요?

Fastify는 Ajv를 타입 변환과 추가 속성 제거를 켠 상태로 쓴다. 그래서 숫자 칸에 "3"을 보내면 3으로 바뀌고, additionalProperties false인 스키마에 모르는 필드를 보내면 거절하지 않고 지운다. 엄격하게 거절하려면 ajv customOptions로 이 설정을 끈다.

### NestJS의 의존성 주입은 어떻게 동작하나요?

모듈에 프로바이더를 등록하면 Nest 컨테이너가 인스턴스를 만들고, 컨트롤러 생성자 인자 타입을 보고 맞는 프로바이더를 넣어 준다. 인자 타입은 TypeScript의 emitDecoratorMetadata가 남긴 런타임 메타데이터에서 읽는다. 이 설정이 빠지거나 esbuild처럼 메타데이터를 안 남기는 도구로 빌드하면 서버는 뜨지만 주입된 값이 undefined라 요청 때 터진다.

### Hono가 여러 런타임에서 돌 수 있는 이유는 무엇인가요?

앱이 웹 표준 Request를 받아 Response를 돌려주는 fetch 함수 하나이기 때문이다. Cloudflare Workers, Deno, Bun은 이 인터페이스를 그대로 쓰고, Node는 어댑터가 Node 요청을 Request로 바꿔 넘긴다. 대신 엣지에서는 fs, 네이티브 모듈, 오래 붙잡는 TCP 연결 같은 Node 기능이 제한돼 DB 접근 방식을 바꿔야 한다.

### 프레임워크 벤치마크 숫자는 얼마나 믿어야 하나요?

방향은 참고하되 그대로 서비스 성능으로 옮기면 안 된다. 직접 재 보니 메모리 응답에서는 Fastify·Hono가 Express의 3~5배였지만, 응답 전에 20ms만 기다리게 해도 모두 초당 1700~2400으로 모였다. 실제 요청은 DB·외부 호출로 수 ms 이상 걸려서 프레임워크 오버헤드가 묻힌다. 캐시 히트 위주 API나 프록시처럼 CPU가 병목인 서버에서만 차이가 크게 드러난다.

### Express에서 next() 뒤에 쓴 코드는 언제 실행되나요?

next()는 다음 미들웨어를 부르고 바로 돌아올 뿐 그 비동기 작업을 기다리지 않는다. 그래서 핸들러가 await를 쓰면 next() 뒤의 코드는 핸들러가 끝나기 전에 실행된다. 응답 시간 측정처럼 끝난 뒤의 처리는 res.on("finish")로 하고, Koa·Hono는 await next()로 안쪽이 끝날 때까지 기다리는 양파 구조라 한 함수 안에서 앞뒤를 쓸 수 있다.

### 팀 규모에 따라 어떤 프레임워크를 고르겠나요?

작은 팀과 작은 서비스라면 Express나 Fastify로 시작하고 검증·에러 규칙만 정한다. 새로 만들면 검증과 직렬화가 기본인 Fastify가 무난하다. 여러 팀이 한 코드베이스를 만지고 도메인이 많아지면 구조와 DI를 강제하는 NestJS가 리뷰 비용을 줄인다. 엣지나 여러 런타임에 올려야 하면 Hono를 고른다.
