## 13시 42분, 규칙 하나가 배포됐다

Cloudflare는 장애 당일 [짧은 첫 보고(2019년 7월 2일)](https://blog.cloudflare.com/cloudflare-outage/)를 올리고, 열흘 뒤 CTO John Graham-Cumming이 [자세한 보고서(2019년 7월 12일)](https://blog.cloudflare.com/details-of-the-cloudflare-outage-on-july-2-2019/)를 냈다. 이 글의 시각은 모두 보고서를 따라 UTC다.

보고서의 첫 문단은 이렇다. 7월 2일 WAF 관리형 규칙(WAF Managed Rules)에 새 규칙을 배포했고, 이 규칙 때문에 Cloudflare 네트워크 전 세계에서 HTTP/HTTPS 트래픽을 처리하는 모든 CPU 코어가 바닥났다. 방문자들은 Cloudflare를 거치는 모든 도메인에서 502 에러 페이지를 봤다. 502는 아직 CPU가 남아 있던 앞단 웹 서버가 HTTP/HTTPS를 처리하는 프로세스에 닿지 못해 낸 것이다. 첫 보고는 최악일 때 트래픽이 82% 떨어졌다고 적었다. 보고서는 서비스가 27분 동안 내려갔고, 6년 만의 전역 장애였다고 적는다.

문제의 정규식은 보고서에 그대로 실려 있다.

```text
(?:(?:\"|'|\]|\}|\\|\d|(?:nan|infinity|true|false|null|undefined|symbol|math)|\`|\-|\+)+[)]*;?((?:\s|-|~|!|{}|\|\||\+)*.*(?:.*=.*)))
```

한 줄로는 읽기 어려우니 조각으로 나눠 보자. 아래에서 조각을 누르면 그 부분이 무엇을 맞추는지 볼 수 있다. 조각의 해석은 패턴을 읽고 내가 붙인 것이고, 보고서가 직접 설명한 건 마지막 두 조각뿐이다.

## 정규식 하나가 CPU를 다 먹는 이유

보고서의 부록은 정규식 백트래킹을 길게 설명한다. 핵심 부분은 끝의 `.*(?:.*=.*)`이고, 묶음 괄호를 빼면 `.*.*=.*`로 생각해도 된다고 한다. "아무거나, 그다음에 또 아무거나, 그다음에 =, 그다음에 아무거나"다. 패턴만 보면 쓸데없이 복잡하지만, 실제 WAF 규칙처럼 "아무거나 뒤에 아무거나"를 요구하는 패턴이면 비슷한 일이 생긴다고 적는다.

`.*`는 탐욕적이라 일단 가능한 한 많이 먹는다. `x=x`를 맞출 때 첫 `.*`가 문자열 전체를 먹으면 두 번째 `.*`는 빈 문자열을 맞추고, `=`를 찾을 글자가 남지 않아 실패한다. 엔진은 되돌아가(backtrack) 첫 `.*`를 한 글자 줄여 `x=`까지만 먹게 하고 다시 시도한다. 그래도 실패하면 두 번째 `.*`를 줄이고, 또 첫 `.*`를 줄인다. 보고서는 세 글자짜리 `x=x` 하나를 맞추는 데 23단계가 걸린다고 적는다.

아래 그림은 같은 생각을 단순하게 따라간 것이다. 첫 `.*`와 두 번째 `.*`가 각각 어디까지 먹을지 큰 쪽부터 줄여 가며 `=`를 확인한다. 보고서가 Perl 정규식 디버거로 센 23단계와 세는 단위가 달라서 단계 수는 같지 않다.

보고서는 입력이 길어질 때의 숫자를 적는다. `x=xx`는 33단계, `x=xxx`는 45단계다. `=` 뒤에 x가 20개면 555단계이고, `x=` 없이 x 20개만 있으면 일치하지 않는다는 걸 알아내는 데 4,067단계가 걸린다. 끝에 세미콜론이 붙은 `.*.*=.*;`라면 더 나쁘다. `x=x`에 90단계, `x=` 뒤에 x 20개면 5,353단계다. 입력 길이에 대해 선형이 아니라 다항식으로 늘어난다.

게으른 매칭도 답이 아니었다고 보고서는 적는다. `.*?.*?=.*?`로 바꾸면 `x=x`도 `x=` 뒤에 x 20개도 11단계로 줄지만, 세미콜론이 붙은 패턴을 `.*?.*?=.*?;`로 바꾸면 실행 시간이 전혀 줄지 않는다. 패턴을 훨씬 구체적으로 다시 쓰는 게 아니라면, 근본 해법은 이런 백트래킹을 하지 않는 엔진으로 옮기는 것이라고 결론짓는다. 보고서는 1968년 Ken Thompson의 논문이 정규식을 NFA로 바꿔 입력 길이에 선형인 시간에 맞추는 방법을 이미 보였다고 소개한다. 여러 상태에 동시에 있으면서 글자를 한 번씩만 읽으니 되돌아갈 일이 없다.

### 되돌아가는 횟수를 직접 세 보기

아래 함수는 `.*.*=.*`(그리고 끝에 세미콜론이 붙은 `.*.*=.*;`)를 위 그림과 같은 방식으로 맞추며 글자 비교 횟수를 센다. 시작 위치를 하나씩 옮기며 찾고, 각 `.*`는 긴 쪽부터 줄여 간다. 보고서의 단계 수와 세는 단위가 달라 숫자는 다르지만, 늘어나는 모양은 같다. `=`가 없어 실패하는 입력이 성공하는 입력보다 훨씬 비싸고, 세미콜론 하나가 비용을 한 차수 더 올린다.

  solution={`function countChecks(s, withSemicolon) {
  const n = s.length;
  let checks = 0;
  for (let start = 0; start <= n; start++) {

          if (s[k] === ";") return [true, checks];
        }
      }
    }
  }
  return [false, checks];
}`}

    { args: ["xxxxxxxxxxxxxxxxxxxx", false], expected: [false, 1771], label: "= 없이 x 20개: 실패가 더 비싸다" },
    { args: ["x=x", true], expected: [false, 26], label: "; 패턴, x=x" },
    { args: ["x=xxxxxxxxxxxxxxxxxxxx", true], expected: [false, 2363], label: "; 패턴, x= 뒤에 x 20개" },
  ]}
/>

x 20개로 실패할 때 1,771번, 40개면 12,341번이다. 입력이 두 배가 되면 비교가 약 7배가 된다. WAF는 거의 모든 요청에 대부분의 규칙을 돌려야 한다. 대부분의 요청은 무해해서 어떤 규칙에도 걸리지 않으니, 실패하는 경우가 곧 평소의 경우다. 실패할 때 가장 비싼 패턴이 가장 자주 돈 셈이다.

### 지금 쓰는 JavaScript 엔진에서도 똑같다

브라우저와 Node.js의 기본 정규식 엔진(V8의 Irregexp)도 백트래킹 엔진이다. 끝에 세미콜론이 붙은 패턴을 세미콜론이 없어 결국 실패하는 입력에 돌려 시간을 재 봤다. Node.js 22.22.0, 이 블로그를 쓰는 데 쓴 리눅스 컨테이너에서 두 번 돌린 값 중 하나다.

```js
// 같은 패턴을 길이를 늘려 가며 실패하는 입력에 돌려 걸린 시간을 잰다
const pattern = /.*.*=.*;/;
for (const n of [500, 1000, 2000, 4000]) {
  const input = "x=" + "x".repeat(n);      // ; 가 없어서 결국 실패한다
  const t0 = process.hrtime.bigint();
  pattern.test(input);
  const ms = Number(process.hrtime.bigint() - t0) / 1e6;
  console.log(`n=${n}\t${ms.toFixed(1)} ms`);
}
```

```text
n=500	143.2 ms
n=1000	399.9 ms
n=2000	3606.6 ms
n=4000	26345.2 ms
```

4,000글자 남짓한 문자열 하나에 26초가 걸렸다. 길이가 두 배가 될 때마다 시간이 8배 안팎으로 는다. 세 개의 `.*`가 글자를 나눠 갖는 경우의 수가 길이의 세제곱으로 늘기 때문이다. HTTP 요청 본문이 몇 KB인 건 흔한 일이다.

V8에는 백트래킹하지 않는 실험적 선형 엔진도 있다. `--enable-experimental-regexp-engine` 플래그를 켜고 `/l` 플래그를 붙이면 그 엔진으로 돈다. 표준 JavaScript 문법이 아니라 V8의 실험 기능이다. 같은 패턴을 돌리면 이렇다.

```bash
# 실험 플래그를 켜고, 패턴만 /.*.*=.*;/l 로 바꾼 같은 스크립트를 돌린다
node --enable-experimental-regexp-engine redos-linear.js
```

```text
n=500	0.5 ms
n=1000	0.9 ms
n=2000	1.4 ms
n=4000	7.3 ms
n=100000	102.1 ms
```

4,000글자가 7ms이고, 10만 글자도 0.1초 정도다. 길이에 거의 비례한다. Cloudflare가 2019년 7월에 옮긴 RE2 계열 엔진이 주는 것이 이 보장이다.

## 여러 구멍이 한 줄로 섰다

보고서에서 가장 많이 인용되는 부분은 "무엇이 잘못됐나" 목록이다. 보고서는 이렇게 시작한다. 매주 수십 개의 새 규칙을 배포하고 나쁜 영향을 막는 시스템이 여럿 있으니, 일이 잘못되면 대개 여러 원인이 겹친 것이다. 원인 하나를 찾으면 속은 시원하지만 실제를 가릴 수 있다. 그러고는 겹친 원인을 나열한다.

- 엔지니어가 크게 백트래킹할 수 있는 정규식을 썼다.
- 정규식의 과도한 CPU 사용을 막아 줄 보호 장치가 몇 주 전 WAF 리팩터링 중 실수로 빠졌다. 그 리팩터링은 WAF의 CPU 사용을 줄이려는 작업이었다.
- 정규식 엔진에 복잡도 보장이 없었다.
- 테스트 묶음에 과도한 CPU 사용을 찾아내는 방법이 없었다.
- 표준 절차(SOP)가 긴급하지 않은 규칙 변경도 단계 배포 없이 전역으로 내보내게 허용했다.
- 되돌리기 계획이 WAF 빌드 전체를 두 번 돌려야 해서 너무 오래 걸렸다.
- 전역 트래픽 하락 첫 경보가 너무 늦게 울렸다.
- 상태 페이지를 빨리 고치지 못했다.
- 장애 때문에 자기 시스템에 접근하기 어려웠고, 우회 절차를 충분히 훈련하지 않았다.
- SRE 일부가 보안상 자격 증명이 만료돼 몇몇 시스템에 접근하지 못했다.
- 고객은 Cloudflare 대시보드와 API에 들어갈 수 없었다. 그 둘도 Cloudflare 엣지를 거치기 때문이다.

이 목록은 [포스트모템](/posts/postmortems)에서 말한 "기여 요인"의 좋은 예다. 다섯 번 "왜"를 물어 한 갈래로 내려가면 "엔지니어가 나쁜 정규식을 썼다"에서 멈추기 쉽다. 이 목록에서 사람의 실수는 첫 줄 하나뿐이고, 나머지는 그 실수가 세계 단위 장애가 되도록 길을 열어 준 시스템의 구멍이다. 특히 둘째 줄이 쓰리다. CPU를 줄이려던 리팩터링이 CPU 폭주를 막던 장치를 지웠다.

## 빠른 배포가 빠른 장애가 된 길: Quicksilver

보고서는 WAF 규칙이 왜 단계 배포를 거치지 않았는지 길게 설명한다. 일반 소프트웨어는 다른 길로 나간다. BitBucket의 git에 코드를 올리면 TeamCity가 빌드하고, 리뷰와 승인 뒤 테스트를 다시 돌린다. Change Request를 승인받으면 "동물 PoP"부터 배포한다. DOG는 직원만 지나는 PoP, PIG(기니피그)는 무료 고객 트래픽 일부가 지나는 PoP, 그다음 전 세계에 흩어진 세 곳의 Canary PoP에서 유료·무료 고객 트래픽으로 마지막 확인을 한다. 이 과정은 변경 종류에 따라 몇 시간에서 며칠이 걸린다.

WAF는 의도적으로 이 길을 타지 않았다. 새 취약점이 공개되면 개념 증명 코드가 금방 GitHub에 올라오고 공격 시도가 급증하니, 몇 시간이 아니라 몇 분 안에 막아야 한다. 보고서는 그해 5월 SharePoint 취약점 대응을 예로 든다. 그래서 WAF 규칙은 Quicksilver라는 전역 분산 키-값 저장소로 배포됐다. 고객이 대시보드나 API로 설정을 바꿀 때 쓰는 바로 그 시스템이다. 보고서 기준으로 Quicksilver는 180개가 넘는 도시에 복제되고, 초당 평균 약 350건의 변경을 퍼뜨리며, 변경이 전 세계 모든 기계에 닿는 시간의 p99가 2.29초다. 평소에는 장점인 이 속도가, 이번에는 규칙 변경이 몇 초 만에 전역으로 퍼지게 했다. WAF 쪽 사정도 하나 더 있었다. 이 WAF는 Lua로 쓰였고 내부에서 PCRE를 쓰는데, PCRE는 백트래킹으로 맞추며 폭주하는 패턴을 막는 장치가 없었다.

### Quicksilver는 왜 그렇게 빨랐나

Cloudflare는 이듬해 [Introducing Quicksilver(2020년 3월)](https://blog.cloudflare.com/introducing-quicksilver-configuration-distribution-at-internet-scale/)에서 이 시스템을 자세히 소개했다. 이전에는 Kyoto Tycoon(KT)을 수천 대에 깔아 설정을 퍼뜨렸다. 거의 모든 DNS·HTTP 요청과 TLS 핸드셰이크가 KT를 읽었으니, KT가 느리면 서비스가 느렸다. 글은 쓰기가 몰리면 읽기 지연이 치솟고(쓰기 둘을 더하자 p99.9가 1초를 넘었다), fsync를 끄자 DB가 깨지고, 타임스탬프 기반 복제가 항목을 조용히 빠뜨렸다고 적는다. KT 운영에 SRE 시간이 주당 48시간씩 들었다고 한다. 2015년 여름 새로 만들기로 했다.

Quicksilver는 LMDB를 저장 엔진으로 쓰고, 변경마다 1씩 늘어나는 순번을 붙인 로그로 복제한다. 순번이 정확히 하나씩 늘었는지만 보면 빠진 갱신을 알아챌 수 있다. 쓰기는 한 데이터센터로 모으고, 읽기는 모든 엣지 기계가 자기 복사본에서 한다. 500ms 창 안의 갱신은 묶어서 한 번에 쓴다. 글 기준으로 하루 2.5조 번의 읽기와 3천만 번의 쓰기를 9만 개가 넘는 DB 인스턴스에서 처리했다. 설정이 엣지 기계마다 로컬에 있으니 중앙과 끊겨도 각 데이터센터가 요청을 처리할 수 있다.

이 설계가 2019년 장애의 배경을 설명한다. 읽기를 모든 기계의 로컬 복사본으로 옮긴 [설정 배포 시스템](/posts/feature-flags)은 같은 설정을 모든 곳에 동시에 둔다. 좋은 설정도 나쁜 설정도 같은 속도로 모든 곳에 있게 된다.

## 그 뒤에 바뀐 것

보고서는 장애 직후 WAF 릴리스 작업을 모두 멈추고 다음을 했다고 적는다.

- 빠졌던 과도한 CPU 사용 보호를 되살렸다(완료).
- WAF 관리형 규칙 3,868개를 손으로 모두 검사해 과도한 백트래킹 가능성을 찾고 고쳤다(검사 완료).
- 테스트 묶음에 모든 규칙의 성능 프로파일링을 넣는다(7월 19일 예정).
- 실행 시간을 보장하는 re2나 Rust regex 엔진으로 바꾼다(7월 31일 예정).
- 규칙 배포 SOP를 다른 소프트웨어처럼 단계 배포로 바꾸되, 실제 공격에 대한 긴급 전역 배포 능력은 남긴다.
- 대시보드와 API를 Cloudflare 엣지에서 떼어 낼 수 있는 긴급 수단을 만든다.
- 상태 페이지 갱신을 자동화한다.

길게는 보고서를 쓴 CTO가 몇 년 전 직접 쓴 Lua WAF를 떠나 새 방화벽 엔진으로 옮긴다고 적었다. 1년 뒤 [Making the WAF 40% faster(2020년 7월)](https://blog.cloudflare.com/making-the-waf-40-faster/)는 그 결과 하나를 확인해 준다. 2019년 7월에 WAF가 PCRE 기반 엔진에서 RE2에서 영감을 받은, 백트래킹 대신 결정적 유한 오토마타(DFA)를 쓰는 엔진으로 옮겼고, 그 계기가 이 장애였다고 적는다. 옮긴 뒤 엣지의 CPU 사용량에는 측정할 만한 차이가 없었고, 실행 시간의 95·99번째 백분위 이상치가 줄었다. 입력 크기에 선형인 실행 시간을 보장하니 예상한 결과였다고 한다. WAF 엔진이 스레드 풀을 써서 스레드끼리 나누는 정규식 캐시를 따로 만들고 다듬어야 했는데, 첫 구현은 메모리를 엄청나게 썼다고 덧붙인다.

선형 시간 엔진에도 대가가 있다. RE2 계열은 역참조(backreference)와 전후방 탐색(lookaround)을 지원하지 않는다. [정규식과 glob](/posts/regex-and-globbing)의 "되돌아가는 엔진과 한 번에 훑는 엔진"에서 다룬 차이다. 규칙을 쓰는 쪽이 쓸 수 있는 문법이 줄어드는 대신 최악의 시간이 정해진다. WAF처럼 공격자가 입력을 고르는 곳에서는 최악이 곧 평소가 될 수 있어서, 이 거래가 맞는 선택이 된다.

## 회사가 직접 쓴 보고서라는 점

이 보고서는 장애 보고서 중에서도 솔직한 편으로 자주 인용된다. 부끄럽다는 말을 두 번 하고, CTO가 몇 년 전 자기가 쓴 Lua WAF를 떠나겠다고 적는다. 그래도 회사가 쓴 글이라는 한계는 있다. 고객 영향을 돈으로 얼마였는지, 어떤 고객이 얼마나 떠났는지는 없다. "6년 만의 전역 장애"라는 표현이 무엇을 전역 장애로 세는지 기준도 적혀 있지 않다. 예정이라고 쓴 후속 조치(성능 프로파일링, 단계 배포 SOP, 대시보드 분리, 상태 페이지 자동화)가 언제 실제로 끝났는지는 이번에 읽은 자료로 확인한 것이 정규식 엔진 교체 하나뿐이다. 그 뒤 Cloudflare가 겪은 다른 장애는 이 글에서 다루지 않았다.

## 우리 배포에서 같은 구멍을 찾는다면

이 사례의 교훈은 "정규식을 조심하라"보다 넓다. 같은 설정을 모든 곳에 동시에 두는 시스템이라면 규모와 상관없이 같은 일이 생길 수 있다. 서버 두 대짜리 서비스도 두 대에 같은 설정 파일을 동시에 배포하면 두 대가 같이 죽는다. 반대로 배포 속도 자체가 제품인 곳(보안 규칙, 긴급 차단, 기능 플래그 끄기)에서는 단계 배포만 고집할 수도 없다. Cloudflare의 결론도 "단계 배포를 기본으로 하되 긴급 전역 배포 능력은 남긴다"였다.

처음부터 Cloudflare 수준을 따라 할 필요는 없다. 동물 PoP나 전역 KV 저장소를 만드는 건 큰 팀의 일이다. 작은 팀이 지금 가져올 수 있는 것은 이렇다.

- 설정·규칙·플래그 변경도 코드처럼 단계 배포한다. 서버 한 대나 트래픽 일부에 먼저 적용하고 CPU와 에러율을 몇 분 본 뒤 넓힌다. [카나리 배포](/posts/canary-release)를 설정 변경에도 쓴다.
- 사용자 입력에 대는 정규식은 선형 시간 엔진을 쓰거나(Go의 `regexp`, Rust의 `regex`, RE2 바인딩), 최소한 실행 시간 상한을 둔다. 테스트에 긴 실패 입력을 넣고 실행 시간을 잰다.
- 장애 때 쓸 경로가 장애 난 시스템에 기대지 않는지 본다. 사내 인증, 관리 콘솔, 상태 페이지가 같은 엣지나 같은 클러스터를 지나면 장애 때 같이 막힌다. 우회 경로는 평소에 한 번씩 써 본다.

비슷한 신호가 보이면 이 순서로 본다. 모든 서버의 CPU가 같은 순간 찼다면 트래픽이 아니라 방금 나간 설정·규칙 변경부터 의심한다. 한 곳만 아프면 트래픽이나 하드웨어지만, 모든 곳이 같이 아프면 공통 입력이다. 502가 쏟아지는데 앱 로그에 아무것도 없으면 앞단 프록시가 뒤 프로세스에 닿지 못하는 것이니 그 사이 계층의 CPU와 연결 수를 본다. 되돌리기를 시작했다면 그 되돌리기가 몇 분 걸리는지부터 확인한다. Cloudflare의 원래 되돌리기 계획은 빌드를 두 번 돌려야 했고, 결국 구한 건 미리 만들어 둔 "전역 종료" 스위치였다.

## 면접에서 나올 만한 질문

### 정규식 하나가 어떻게 전 세계 CPU를 채웠나

`.*.*=.*`처럼 "아무거나 뒤에 아무거나"를 요구하는 패턴은 백트래킹 엔진에서 실패할 때 갈림길을 모두 시도해 입력 길이에 다항식으로 비싸진다. WAF는 거의 모든 요청에 규칙을 돌리고 대부분의 요청은 규칙에 걸리지 않으니, 가장 비싼 실패 경로가 평소 경로였다. 그 규칙이 Quicksilver로 몇 초 만에 모든 기계에 퍼져 모든 곳의 CPU가 동시에 찼다.

### 막지 않는 simulate 모드였는데 왜 장애가 됐나

simulate 모드는 결과로 요청을 막지 않을 뿐 규칙은 모든 요청에 실제로 실행한다. 오탐률을 재려면 실행해야 하기 때문이다. 영향을 줄이는 모드가 실행 비용까지 줄여 주지는 않는다. 그래서 "관찰 모드"도 성능 면에서는 운영 배포와 같게 다뤄야 한다.

### 왜 WAF 규칙은 단계 배포를 하지 않았나

새 취약점이 공개되면 공격이 금방 쏟아지니 몇 분 안에 막아야 해서였다. 일반 소프트웨어처럼 DOG, PIG, Canary를 거치면 몇 시간에서 며칠이 걸린다. 문제는 긴급하지 않은 규칙 변경까지 같은 전역 경로를 타게 둔 SOP였다. 사고 뒤에는 단계 배포를 기본으로 하고 실제 공격 대응에만 긴급 전역 배포를 남겼다.

### 애니캐스트로 여러 도시에 나눠 두었는데 왜 다 같이 죽었나

애니캐스트는 한 도시가 빠지면 다른 도시로 트래픽을 보내는 지역 장애 대비다. 모든 도시가 같은 설정을 같은 순간 받으면 그 설정이 만든 장애도 동시에 온다. 지리적 이중화는 공통 원인 장애를 막지 못하고, 그걸 막는 건 배포를 시간과 범위로 나누는 일이다.

### 원인이 정규식이면 정규식만 고치면 되지 않나

보고서는 겹친 원인을 열 개 넘게 적는다. 몇 주 전 리팩터링에서 빠진 CPU 보호 장치, 복잡도 보장 없는 엔진, CPU를 보지 않는 테스트, 단계 없는 SOP, 빌드를 두 번 돌려야 하는 되돌리기, 늦은 경보, 장애 난 Access 때문에 막힌 내부 접근이다. 정규식만 고치면 다음 규칙이 같은 길로 다시 들어온다. 그래서 엔진을 선형 시간 엔진으로 바꾸고 배포 절차도 바꿨다.

### 게으른 매칭으로 바꾸면 해결되나

일부만 된다. 보고서에 따르면 `.*?.*?=.*?`는 단계가 11로 줄지만, 끝에 세미콜론이 붙은 패턴은 게으르게 바꿔도 실행 시간이 그대로다. 근본 해법은 NFA·DFA 기반의 선형 시간 엔진이고, Cloudflare는 2019년 7월에 RE2에서 영감을 받은 엔진으로 옮겼다. 대가는 역참조 같은 일부 문법을 못 쓰는 것이다.

### 우리 서비스가 서버 몇 대 규모라면 이 사례에서 무엇을 가져오나

설정과 규칙 변경을 코드처럼 일부에 먼저 적용하고 지표를 본 뒤 넓히는 습관이다. 사용자 입력에 대는 정규식은 선형 시간 엔진이나 실행 시간 상한을 쓰고, 테스트에 긴 실패 입력을 넣는다. 그리고 장애 때 쓸 관리 콘솔과 상태 페이지가 장애 난 경로에 기대지 않는지 미리 확인하고, 미리 만든 전역 끄기 스위치를 둔다.
