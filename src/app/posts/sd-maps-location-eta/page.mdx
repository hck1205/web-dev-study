내비를 켜고 출발하면 "도착 예정 8시 42분"이 뜬다. 고속도로에 올라 10분쯤 달렸을 때 화면 위에 "전방 사고, 경로를 바꾸면 14분 빠릅니다"가 뜬다. 그 사고를 앱은 어떻게 알았을까. 누가 신고한 게 아니라, 그 구간을 지나던 다른 차들의 속도가 갑자기 떨어진 걸 서버가 본 것이다. 이 글은 수많은 휴대폰의 위치를 모으고, 그걸로 도로의 지금 속도를 알아내고, 도착 시간을 고치고, 막힌 길 위의 사람을 찾아 새 길을 밀어 주는 과정을 따라간다.

## 위치를 한 점씩 보내면

안내 중인 앱은 GPS 위치를 1초마다 얻는다. 가장 단순한 버전은 얻을 때마다 서버로 보내는 것이다. 30분 주행을 흉내 내서 1,800개의 점을 만들고, 한 점씩 보낼 때와 15초씩, 60초씩 묶어 보낼 때를 비교했다. 요청 본문은 JSON으로 하고 gzip으로 압축한 크기도 쟀다.

```js
// ingest.js 일부: 30분 동안 1초마다 찍은 점을 몇 개씩 묶어 보낼까
function measure(batch) {
  let reqs = 0, raw = 0, gz = 0;
  for (let i = 0; i < pts.length; i += batch) {
    const body = JSON.stringify({ locs: pts.slice(i, i + batch) });
    reqs++; raw += Buffer.byteLength(body); gz += gzipSync(body).length;
  }
  return { reqs, raw, gz };
}
```

```text
one point: {"locs":[{"lat":37.497994,"lng":127.027631,"ts":1761000001000,"spd":39.1}]}
batch  1: 1800 requests  body 131.1 KiB  gzip 158.0 KiB
batch 15:  120 requests  body 114.7 KiB  gzip 29.9 KiB
batch 60:   30 requests  body 113.8 KiB  gzip 21.3 KiB
```

한 점씩 보내면 요청이 1,800번이다. 요청마다 HTTP 헤더와 TLS 기록이 붙고, 휴대폰은 매번 무선 모뎀을 깨운다. 모뎀이 깨어 있는 시간이 배터리를 가장 많이 먹는다. 더 눈에 띄는 건 gzip 줄이다. 점 하나짜리 본문은 압축하면 오히려 커진다(131KiB → 158KiB). gzip 머리말과 사전이 내용보다 크기 때문이다. 15개씩 묶으면 요청이 120번으로 줄고, 비슷한 숫자가 반복되니 압축이 잘 먹어서 전송량이 30KiB로 준다.

묶는 시간이 길수록 서버는 그만큼 늦게 안다. 교통 정보를 만들려면 너무 늦으면 안 되니 10~30초 사이에서 고른다. 안내 중이 아니라 앱이 뒤에 깔려 있을 때는 더 길게 묶거나 아예 보내지 않는다.

## 하루에 들어오는 점의 수

이 글의 가상 서비스로 어림한다. 안내를 쓰는 사람이 하루 500만 명이고, 한 명이 평균 40분 동안 안내를 켠다. 하루 안내 시간은 500만 × 40분 = 2억 분이고, 1초마다 점 하나면 하루 120억 개의 점이다. 하루 86,400초로 나누면 초당 약 13만 9천 개다. 15초씩 묶어 보내면 요청은 초당 약 9,259개, 출퇴근 시간이 평균의 3배라면 약 27,778개다.

저장량은 앞의 압축 결과로 잡는다. 15개 묶음에서 점 1,800개가 29.9KiB였으니 점 하나에 약 17바이트다. 하루 120억 개면 약 200GB가 쌓인다. 1년이면 70TB를 넘는다. 이런 계산 방법은 [⑩ 용량 추정](/posts/sd-capacity-estimation)에 있다.

이 숫자가 말해 주는 건 쓰기가 압도적이라는 것이다. 위치는 들어오는 순간이 가장 쓸모 있고, 한참 지난 위치를 다시 읽는 일은 분석 작업 정도다.

## 쓰기가 몰리는 저장소

초당 13만 개 넘는 점을 관계형 DB 한 대에 넣으면 인덱스를 고치느라 버티지 못한다. 쓰기에 강한 와이드 컬럼 DB(Cassandra 같은)가 맞는다. 들어온 쓰기를 메모리와 순서대로 쓰는 로그에 먼저 적고, 나중에 모아서 정렬된 파일로 내리는 구조라 쓰기가 빠르다. 그 내부는 [⑯ 키-값 저장소의 쓰기·읽기 경로](/posts/sd-kv-store-write-read-path)에서 봤고, 와이드 컬럼 DB의 성격은 [와이드 컬럼 DB](/posts/db-type-wide-column)에 있다.

테이블은 "이 사람의 이 날 동선"을 한 번에 읽기 좋게 짠다.

```sql
-- Cassandra CQL: 사용자와 날짜로 파티션을 나누고, 그 안은 시각 순으로 정렬한다
CREATE TABLE user_locations (
  user_id bigint,
  day     date,
  ts      timestamp,
  lat     double,
  lng     double,
  speed   float,
  PRIMARY KEY ((user_id, day), ts)
) WITH CLUSTERING ORDER BY (ts DESC)
  AND default_time_to_live = 7776000;   -- 90일 뒤 자동 삭제
```

파티션 키에 날짜를 같이 넣은 이유가 있다. `user_id`만 파티션 키로 두면 매일 안내를 켜는 사람의 파티션이 끝없이 커진다. 파티션 하나는 한 노드에 통째로 들어가니, 너무 커지면 그 노드만 무거워지고 읽기도 느려진다. 날짜를 붙이면 하루치 이하로 잘린다. 보관 기간을 정해 오래된 위치를 저절로 지우는 것도 사생활 면에서 필요하다. 위치는 그 사람의 집과 직장을 드러낸다.

일관성은 약하게 둔다. 방금 쓴 점이 다른 복제본에 몇 초 늦게 보여도 문제가 없다. 사용자 위치는 금방 새 값으로 덮이니, 노드 몇 개가 죽어도 쓰기를 받아 주는 가용성 쪽을 고른다. 이 고르기는 [최종 일관성](/posts/eventual-consistency) 글에 있다.

## 한 번 받아 여러 곳으로

위치 데이터를 쓰려는 곳은 저장소 하나가 아니다. 교통 정보를 계산하는 쪽, 도착 시간 예측 모델을 학습시키는 쪽, 새로 생긴 도로나 막힌 도로를 찾는 쪽이 모두 같은 점을 원한다. 위치 서비스가 이들에게 하나씩 보내면, 받는 쪽이 늘 때마다 위치 서비스를 고쳐야 하고 하나가 느려지면 전체가 막힌다.

그래서 위치 서비스는 받은 점을 Kafka 같은 로그 기반 메시지 큐에 한 번만 쓴다. 받는 쪽은 각자 소비자 그룹을 만들어 자기 속도로 읽는다. 하나가 밀려도 다른 쪽은 영향이 없고, 새로 붙는 쪽은 로그의 앞부분부터 다시 읽을 수 있다. Kafka의 구조는 [Kafka 기초](/posts/kafka-basics)에, 그런 큐를 직접 설계하는 이야기는 다음 장 [㊴ 분산 메시지 큐](/posts/sd-mq-storage-partitions)에 있다.

## 도로 조각마다 지금 속도를 구한다

맵 매칭을 거친 점은 "이 차가 이 조각을 시속 몇 km로 지났다"가 된다. 교통 집계는 조각마다 최근 몇 분의 속도를 모아 지금 속도를 정한다. 평균을 내면 튀는 값 하나에 크게 흔들린다. 갓길에 선 차 한 대, 반대로 구급차 한 대가 평균을 끌고 간다. 그래서 중앙값처럼 덜 흔들리는 값을 쓴다.

앞 글의 도로망에서 D-G 고속도로에 사고가 났다고 치고, 최근 5분 동안 그 조각을 지난 차들의 속도 보고로 간선 무게를 바꾼 뒤 길을 다시 찾았다.

```js
// eta.js 일부: 조각별 최근 속도의 중앙값으로 간선 무게를 바꾸고 다시 찾는다
const reports = [{ seg: "D-G", kmh: 14 }, { seg: "D-G", kmh: 9 }, { seg: "D-G", kmh: 11 }, { seg: "D-G", kmh: 62 },
  { seg: "D-G", kmh: 12 }, { seg: "E-G", kmh: 55 }, { seg: "E-G", kmh: 58 }];
for (const [seg, v] of Object.entries(bySeg)) {
  const s = [...v].sort((a, b) => a - b), med = s[Math.floor(s.length / 2)];
  live.set(seg, med);                               // 이 조각의 지금 속도
}
const after = search(graph, "S", "G", h);           // 앞 글의 A* 그대로
```

```text
before: S→H→D→G ETA 10.15min
segment D-G: reports [14,9,11,62,12] -> median 12km/h
segment E-G: reports [55,58] -> median 58km/h
old route with new traffic: S→H→D→G ETA 26.06min
after : S→A→B→E→G ETA 11.69min
```

D-G의 보고 다섯 개 중 62km/h 하나는 사고 지점을 이미 빠져나간 차였을 것이다. 평균은 21.6km/h이지만 중앙값은 12km/h라 막힌 상황을 더 잘 보여 준다. 원래 경로를 그대로 가면 26.06분이 걸리고, 다시 찾은 S→A→B→E→G는 11.69분이다. 14분 넘게 아끼는 길이다.

보고가 없는 조각도 많다. 새벽의 골목은 몇 시간 동안 차 한 대 안 지나간다. 그런 조각은 그 시간대의 평소 속도(과거 같은 요일, 같은 시각의 기록)로 채운다. 이 평소 속도가 곧 ETA 학습 쪽이 밤마다 만드는 결과물이다.

## 도착 시간은 조각 시간의 합에 예측을 더한다

ETA(Estimated Time of Arrival, 도착 예정 시간)의 뼈대는 경로 위 조각마다 걸리는 시간을 더한 값이다. 조각 시간은 길이를 지금 속도로 나눈다. 아래에서 그 뼈대를 직접 짜 볼 수 있다. 조각마다 최근 속도 보고가 있으면 중앙값을, 없으면 평소 속도를 쓴다.

<CodePlayground

  functionName="eta"
  initialCode={`// segments: [[길이(m), 최근 속도 보고(km/h) 배열, 평소 속도(km/h)], ...]

// (짝수 개면 가운데 둘 중 큰 값이다). 보고가 없으면 평소 속도를 쓴다.
// 반환: 전체 분, 소수점 둘째 자리까지 반올림 (Math.round(x * 100) / 100)
function eta(segments) {
  return 0;
}`}
  solution={`function eta(segments) {
  let min = 0;
  for (const [m, reports, usual] of segments) {
    let kmh = usual;
    if (reports.length) {
      const s = [...reports].sort((a, b) => a - b);
      kmh = s[Math.floor(s.length / 2)];
    }
    min += (m / 1000 / kmh) * 60;
  }
  return Math.round(min * 100) / 100;
}`}
  tests={[

    { label: "사고 난 고속도로", args: [[[3670, [14, 9, 11, 62, 12], 90]]], expected: 18.35 },
    { label: "보고 둘 + 보고 없음", args: [[[1500, [40, 20], 50], [500, [], 25]]], expected: 3.45 },

실제 서비스의 ETA는 이 합에 예측을 얹는다. 내가 그 조각에 닿는 건 지금이 아니라 20분 뒤다. 20분 뒤 그 조각의 속도는 지금과 다를 수 있다. 퇴근 시간이 시작되면 점점 막힐 것이다. 그래서 과거 같은 시간대의 흐름과 지금의 흐름을 함께 넣은 모델로 조각별 미래 속도를 예측한다. 구글은 도로망을 그래프로 보고 그래프 신경망으로 예측한다고 공개한 바 있다. 신호등과 회전에서 기다리는 시간도 더한다.

ETA가 맞았는지는 나중에 확인할 수 있다. 실제 도착 시각이 위치 기록에 남기 때문이다. 예측과 실제의 차이를 경로 길이별, 시간대별로 지표로 보면 모델이 어디서 틀리는지 보인다. 평균만 보면 안 되고, 크게 틀린 꼬리를 본다. 그 이유는 [퍼센타일 지연](/posts/percentile-latency) 글과 같다.

## 막힌 길을 지나는 사람 찾기

사고가 감지되면 그 조각을 지날 예정인 안내 중 사용자에게 새 길을 알려야 한다. 그러려면 "이 칸을 지날 사람이 누구인가"를 빨리 찾아야 한다. 서울 상자 안에서 안내 중인 사용자 10만 명을 만들고, 각자의 경로를 100m마다 지오해시 6글자 칸으로 기록한 뒤 세 가지 방법을 비교했다. 경로는 출발과 도착을 잇는 직선으로 단순화했다.

```js
// reroute.js 일부: 사고 난 칸을 지나는 안내 중 사용자 찾기
// 1) 사용자마다 경로가 지나는 칸을 모두 저장하고 전부 훑는다
const exact = users.filter((u) => u.cells.has(incident)).length;
// 2) 출발 칸에서 한 글자씩 줄여 도착지까지 덮는 칸 사슬만 저장하고, 맨 위 칸으로 거른다
const candidates = users.filter((u) => incident.startsWith(u.top));
// 3) 거꾸로 된 색인: 칸 → 그 칸을 지나는 사용자 목록
const hit = (byCell.get(incident) || []).length;
```

세 줄을 비교해 본다. 모두 훑으면 정확하지만 사용자 수에 비례해 느려진다. 칸 사슬은 저장량이 사용자당 3.5개로 작고, 맨 위 칸이 사고 칸을 품는지만 보니 빠르다. 그런데 서울 안의 경로는 대부분 3~4글자 칸까지 올라가야 도착지를 덮어서, 맨 위 칸 하나가 도시의 큰 덩어리가 된다. 그래서 후보가 9만 3천 명이나 됐다. 1차로 거르는 데는 쓰지만 이것만으로는 부족하다.

거꾸로 된 색인은 칸마다 "이 칸을 지날 사용자" 목록을 들고 있다. 사고 칸 하나를 찾으면 바로 4,506명이 나온다. 대신 저장량이 215만 개로 가장 크고, 사용자가 경로를 바꿀 때마다 옛 칸들에서 빼고 새 칸들에 넣어야 한다. 실서비스라면 이 색인을 Redis 같은 메모리 저장소에 칸별 집합으로 두고, 안내가 끝나거나 만료되면 지운다.

## 다음 글

위치는 앱이 15초씩 묶어 압축해 보내고, 위치 서비스는 Kafka에 한 번만 써서 여러 소비자가 각자 읽게 했다. 저장은 사용자와 날짜로 파티션을 나눈 쓰기 중심 DB에 두고 기한을 걸었다. GPS 점은 맵 매칭으로 도로에 올린 뒤 조각별 중앙값 속도로 간선 무게를 바꾸고, ETA는 조각 시간의 합에 미래 속도 예측을 얹었다. 사고 칸을 지날 사람은 칸에서 사용자로 가는 거꾸로 된 색인으로 찾아, 열린 연결로 새 경로를 밀었다.

이걸로 위치 장을 마친다. 다음 글 [㊴ 분산 메시지 큐 ①: 저장과 파티션](/posts/sd-mq-storage-partitions)에서는 이 글이 당연하게 쓴 Kafka 같은 큐를 직접 설계한다. 위치 점이 같은 파티션에 순서대로 쌓인다는 성질이 어떻게 만들어지는지 거기서 본다.

## 면접에서 나올 만한 질문

### 위치를 1초마다 보내지 않고 묶는 이유는요?

요청 수와 배터리, 전송량을 줄이려고 묶는다. 30분 주행 1,800점을 한 점씩 보내면 요청이 1,800번이고, 점 하나짜리 본문은 gzip으로 오히려 커졌다. 15개씩 묶으면 요청은 120번, 압축 후 전송량은 158KiB에서 30KiB로 줄었다. 묶는 시간만큼 서버가 늦게 아니까 교통 정보에 쓸 수 있는 10~30초 사이에서 고른다.

### 위치 저장소로 무엇을 고르고, 키는 어떻게 짜나요?

초당 십만 단위의 쓰기가 들어오고 읽기는 드무니 Cassandra 같은 쓰기 중심 와이드 컬럼 DB를 고른다. 파티션 키는 사용자 ID와 날짜, 정렬 키는 시각으로 둔다. 사용자 ID만 쓰면 매일 쓰는 사람의 파티션이 끝없이 커져 한 노드가 무거워진다. 보관 기간을 TTL로 걸어 오래된 위치는 저절로 지운다.

### 위치 서비스가 여러 소비자에게 직접 보내면 안 되나요?

받는 쪽이 늘 때마다 위치 서비스를 고쳐야 하고, 하나가 느려지면 전체가 막힌다. Kafka 같은 로그에 한 번 쓰고 소비자 그룹이 각자 속도로 읽게 하면 서로 영향이 없다. 사용자 ID를 키로 쓰면 한 사람의 점이 같은 파티션에 순서대로 쌓여 속도 계산이 쉽다. 새 소비자는 로그 앞부분부터 다시 읽어 따라온다.

### 도로의 지금 속도는 어떻게 구하나요?

GPS 점을 맵 매칭으로 도로 조각에 올리고, 조각마다 최근 몇 분의 통과 속도를 모은다. 평균은 서 있는 차 한 대에 크게 흔들리니 중앙값 같은 값을 쓴다. 예제에서 사고 구간의 평균은 21.6km/h였지만 중앙값은 12km/h였다. 보고가 없는 조각은 같은 요일과 시간대의 평소 속도로 채운다.

### ETA가 자꾸 틀리면 어디부터 보나요?

예측과 실제 도착 시각의 차이를 경로 길이별, 시간대별, 지역별로 나눠 본다. 평균보다 크게 틀린 꼬리를 본다. 특정 시간대에만 틀리면 교통 예측이, 특정 지역에서만 틀리면 맵 매칭이나 도로 데이터가 의심스럽다. 지금 속도만 쓰면 출발 뒤 막히기 시작하는 퇴근길에서 체계적으로 짧게 잡는다.

### 사고가 나면 영향받는 사용자를 어떻게 찾나요?

칸에서 사용자로 가는 거꾸로 된 색인을 둔다. 사고 칸 하나를 조회하면 바로 목록이 나온다. 10만 명 실험에서 전부 훑으면 28ms였고 색인 조회는 0.014ms였다. 칸 사슬만 저장하는 방법은 저장량은 작지만 맨 위 칸이 너무 커서 후보가 9만 3천 명이나 나왔다. 색인은 경로가 바뀔 때마다 고쳐야 하니 메모리 저장소에 두고 안내가 끝나면 지운다.

### 모두를 같은 우회로로 보내면 어떻게 되나요?

이번엔 우회로가 막힌다. 그래서 새 경로가 일정 시간 이상 빠를 때만 알리고, 일부만 먼저 돌린 뒤 우회로 속도를 다시 보고 나머지를 보낸다. 한 번 바꾼 사람은 한동안 다시 바꾸지 않아 경로가 오락가락하지 않게 한다.

### 새 경로를 앱에 보내는 방법으로 무엇을 고르나요?

안내 중에는 WebSocket을 쓴다. 위치 묶음을 올리는 것과 새 경로를 받는 것을 한 연결로 하고, 서버가 아무 때나 밀 수 있다. 모바일 푸시는 크기가 약 4KB로 작고 웹에서 쓰기 어려워 앱이 뒤에 있을 때 깨우는 용도로 쓴다. 끊긴 동안의 메시지를 위해 앱이 다시 붙을 때 지금 ETA를 한 번 묻게 한다.
