앱 서버 디스크가 거의 찼다. 지난주 접근 로그 몇 GB를 분석용 서버로 옮기고 지워야 한다. 그대로 보낼지, 압축할지, 압축한다면 gzip인지 xz인지 zstd인지, 보낼 때는 `scp`인지 `rsync`인지 정해야 한다. "압축하면 빠르겠지" 하고 `xz -9`를 걸었다가 압축만 몇십 분 기다리는 일이 흔하다. 회선이 넓으면 압축이 오히려 시간을 잡아먹는다.

이 글은 tar가 무엇을 하고 무엇을 하지 않는지에서 시작해, 압축 도구들을 같은 로그로 직접 재 보고, 전송 도구와 프로토콜을 비교한다. 기준은 Ubuntu 24.04(GNU tar 1.35, rsync 3.2.7, OpenSSH 9.6)이고 출력은 모두 이 머신에서 돌린 것이다. rsync가 바뀐 부분만 보내는 원리(굴리는 체크섬)는 [rsync 알고리즘 글](/posts/rsync-algorithm)에 따로 있어서 여기서는 쓰는 법만 본다.

## tar는 묶기만 한다

tar(tape archive)는 이름 그대로 테이프에 파일을 차례로 쓰려고 만든 형식이다. 파일마다 512바이트짜리 헤더(이름, 권한, 소유자, 수정 시각, 크기)를 쓰고 그 뒤에 내용을 붙인다. 압축은 하지 않는다. 압축은 tar가 만든 한 덩어리를 gzip 같은 다른 프로그램에 통째로 넘겨서 한다. `.tar.gz`라는 이름이 "tar로 묶고 gzip으로 눌렀다"는 뜻이다.

```bash
mkdir -p src/app && echo hi > src/app/a.txt
chmod 640 src/app/a.txt
ln -s a.txt src/app/link
# c: 만든다, z: gzip으로 누른다, f: 이 파일에, -C: 이 디렉터리로 들어가서 묶는다
tar -czf app.tgz -C src app
# t: 목록, v: 자세히
tar -tvzf app.tgz
```

```text
drwxr-xr-x root/root         0 2026-10-24 00:24 app/
lrwxrwxrwx root/root         0 2026-10-24 00:24 app/link -> a.txt
-rw-r----- root/root         3 2026-10-24 00:24 app/a.txt
```

헤더에 권한(`-rw-r-----`), 소유자(`root/root`), 심볼릭 링크(`link -> a.txt`)가 그대로 들어 있다. 서버 설정 디렉터리를 백업할 때 tar를 쓰는 이유다. 풀 때 어떻게 되돌리는지는 누가 푸느냐에 따라 다르다. root가 풀면 소유자와 권한을 그대로 되살린다. 일반 사용자가 풀면 소유자는 푼 사람이 되고 권한에는 umask가 적용된다. 권한까지 그대로 살리려면 `-p`를 준다. 소유자 이름이 서버마다 다른 UID를 가리킬 수 있으니, 다른 서버로 옮길 때는 `--numeric-owner`로 숫자 그대로 쓰는 편이 안전하다. 권한과 소유자의 기본은 [파일과 권한 글](/posts/linux-files-permissions)에 있다.

자주 쓰는 옵션을 모아 둔다. 요즘 GNU tar는 풀 때 압축 형식을 알아서 알아보므로 `-xf` 하나로 `.tar.gz`, `.tar.xz`, `.tar.zst`를 다 푼다.

```bash
tar -czf logs.tar.gz logs/          # gzip
tar -cJf logs.tar.xz logs/          # xz
tar --zstd -cf logs.tar.zst logs/   # zstd (tar 1.31 이후)
tar -I 'zstd -T0 -3' -cf logs.tar.zst logs/   # 압축 프로그램에 옵션까지 넘기기
tar -xf logs.tar.zst -C /data/      # 형식은 tar가 알아본다
tar -tf logs.tar.gz | head          # 풀지 않고 목록만
tar -xf logs.tar.gz logs/access-0.log   # 하나만 꺼내기 (그래도 앞에서부터 읽는다)
tar -czf etc.tgz --exclude='*.swp' -C / etc   # 빼고 묶기
```

## 같은 로그로 재 본 압축 도구들

압축 도구는 모두 "얼마나 작게"와 "얼마나 빨리"를 맞바꾼다. 웹 서버 접근 로그와 비슷한 줄 200만 개(304.6MB)를 tar로 묶고 하나씩 돌렸다. 4코어 VM이고 다른 작업과 함께 돌아서 절대 시간은 참고만 하고 서로의 비율을 본다.

```bash
# 같은 tar 파일을 각 도구로 누르고(comp), 다시 풀어(decomp) 시간을 잰다
tar -cf logs.tar logs
run() {  # run 이름 명령...
  name=$1; shift
  s=$(date +%s.%N); "$@" < logs.tar > out.bin; e=$(date +%s.%N)
  sz=$(stat -c %s out.bin)
  s2=$(date +%s.%N)
  case $name in gzip*) gzip -dc out.bin ;; bzip2*) bzip2 -dc out.bin ;;
                xz*) xz -dc out.bin ;; zstd*) zstd -dcq out.bin ;; esac > /dev/null
  e2=$(date +%s.%N)
  printf "%-12s %6.1fMB  ratio %5.1f%%  comp %6.1fs  decomp %5.1fs\n" "$name" \
    "$(echo "$sz/1048576" | bc -l)" "$(echo "$sz*100/305000000" | bc -l)" \
    "$(echo "$e-$s" | bc)" "$(echo "$e2-$s2" | bc)"
}
run gzip-1 gzip -1; run gzip-6 gzip -6; run bzip2-9 bzip2 -9; run xz-6 xz -6
run zstd-3 zstd -3 -q; run zstd-19 zstd -19 -q
run zstd-3-T0 zstd -3 -T0 -q; run xz-6-T0 xz -6 -T0
```

```text
gzip-1         70.5MB  ratio  24.3%  comp    2.9s  decomp   1.3s
gzip-6         57.2MB  ratio  19.7%  comp    7.5s  decomp   1.5s
bzip2-9        38.8MB  ratio  13.4%  comp   30.4s  decomp  12.8s
xz-6           44.1MB  ratio  15.2%  comp  242.5s  decomp   3.2s
zstd-3         59.6MB  ratio  20.5%  comp    1.4s  decomp   0.3s
zstd-19        44.8MB  ratio  15.4%  comp  287.0s  decomp   0.4s
zstd-3-T0      59.6MB  ratio  20.5%  comp    0.9s  decomp   0.3s
xz-6-T0        44.3MB  ratio  15.2%  comp  106.5s  decomp   2.9s
```

크기는 MiB 단위이고, ratio는 원본을 대략 305MB로 잡고 나눈 값이라 소수 첫째 자리에서 조금 어긋날 수 있다. 읽을 거리가 많다.

- zstd -3은 gzip -6과 크기가 거의 같은데 압축이 5배, 풀기가 5배 빠르다. 기본값으로 쓸 만한 이유다.
- 높은 단계는 비싸다. zstd -19는 -3보다 25% 작지만 200배 오래 걸렸다. xz -6도 비슷하다. 한 번 만들어 여러 번 받는 배포 파일(패키지, 릴리스 tarball)이 아니면 맞지 않는다.
- 이 로그에서는 bzip2가 가장 작았다. bzip2의 방식(BWT)이 줄 단위로 비슷한 텍스트에 강하다. 대신 풀기가 다른 것보다 열 배 느리다. 데이터가 바뀌면 순위도 바뀌니, 중요한 결정이면 내 데이터로 직접 잰다.
- `-T0`(코어 수만큼 스레드)를 주면 zstd와 xz가 빨라진다. gzip은 단일 스레드라 여러 코어를 쓰려면 `pigz`를 따로 깐다.
- 풀기는 zstd가 압도적으로 빠르다. 로그를 매번 풀어서 grep하는 분석 서버라면 이 숫자가 더 중요하다.

Ubuntu가 21.10부터 `.deb` 패키지의 기본 압축을 xz에서 zstd로 바꾼 것도 이 풀기 속도 때문이다. 패키지를 까는 시간이 대부분 푸는 시간이다. 이미 압축된 것(`.jpg`, `.mp4`, `.gz`)은 다시 눌러도 거의 줄지 않으니 압축 단계를 빼는 게 낫다.

## 압축할지 말지는 회선이 정한다

압축이 이득인지는 "누르는 시간 + 보내는 시간 + 푸는 시간"의 합으로 따진다. 회선이 넓으면 보내는 시간이 작아져서 누르는 시간이 상대적으로 커진다. 위에서 잰 숫자를 넣어 직접 계산해 보자. `pick` 함수가 회선 속도(Mbps)를 받아 가장 빨리 끝나는 방법과 그 시간을 돌려주게 채운다. `pipelined`가 참이면 셋이 동시에 흐르는 경우라(다음 절의 파이프), 합이 아니라 셋 중 가장 느린 것이 전체 시간이 된다.

## 디스크에 쓰지 않고 바로 보낸다

디스크가 거의 찬 서버라면 압축 파일을 만들 자리도 없다. tar와 압축과 ssh를 파이프로 이으면 중간 파일 없이 바로 보낸다. 세 단계가 동시에 흐르므로 위 계산의 `pipelined` 경우가 된다.

```bash
# 보내는 쪽에서: 묶고 → 누르고 → ssh로 흘려보내고 → 받는 쪽에서 풀고 → 풀어 놓는다
tar -cf - -C /var/log/nginx . \
  | zstd -T0 -3 \
  | ssh analytics 'zstd -d | tar -xf - -C /data/nginx'
```

## zip은 다르게 묶는다

zip은 묶기와 누르기를 한 형식에서 한다. 차이는 파일마다 따로 누른다는 것이다. 덕분에 맨 뒤의 목록(central directory)만 읽으면 원하는 파일 하나를 바로 꺼낼 수 있다. `.tar.gz`는 전체를 한 덩어리로 눌렀기 때문에 마지막 파일을 꺼내려면 앞을 다 풀며 읽어야 한다. 대신 한 덩어리로 누르는 쪽이 파일 사이에 겹치는 내용까지 줄여서 보통 더 작다.

zip은 윈도와 주고받기 좋지만 유닉스 정보를 덜 챙긴다. 위의 심볼릭 링크가 든 디렉터리를 zip으로 묶어 봤다.

```bash
zip -qr app.zip src/app
unzip -Z app.zip | tail -3     # zip 안의 상세 정보
```

```text
-rw-r-----  3.0 unx        3 tx stor 26-Oct-24 00:24 src/app/link
-rw-r-----  3.0 unx        3 tx stor 26-Oct-24 00:24 src/app/a.txt
3 files, 6 bytes uncompressed, 6 bytes compressed:  0.0%
```

`link`가 링크가 아니라 3바이트짜리 일반 파일이 됐다. zip은 기본으로 링크를 따라가 내용을 담는다. 링크로 담으려면 `zip -y`를 준다. 소유자(UID·GID)도 기본으로는 담지 않는다. 서버끼리 옮기는 백업은 tar, 사람에게 건네는 파일은 zip으로 나눠 쓴다.

## 남이 준 tar를 풀 때

tar 안의 이름은 아무 문자열이나 될 수 있다. `../../etc/cron.d/x`나 `/root/.ssh/authorized_keys` 같은 이름을 넣은 파일을 풀면 대상 디렉터리 밖에 쓰게 된다. 이런 공격을 경로 탈출(path traversal, zip에서는 Zip Slip)이라고 한다. GNU tar는 기본으로 막는다. 직접 만들어 확인했다.

```bash
# 절대 경로로 묶으면 tar가 앞의 / 를 떼어 낸다
tar -czf abs.tgz /tmp/lab/src/app/a.txt
# ../escape.txt 라는 이름을 넣은 tar를 파이썬으로 만들어 푼다
tar -xvf ../evil.tar
```

```text
tar: Removing leading `/' from member names
tar: Removing leading `../' from member names
tar: ../escape.txt: Member name contains '..'
ok.txt
tar: Exiting with failure status due to previous errors
```

`..`이 든 항목을 건너뛰고 종료 코드 2로 끝났다. 위험한 쪽은 GNU tar가 아니라 내가 짠 코드다. 파이썬의 `tarfile`로 같은 파일을 풀어 봤다.

```bash
python3 -c 'import tarfile; tarfile.open("evil.tar").extractall()'
ls ..
python3 -c 'import tarfile; tarfile.open("evil.tar").extractall(filter="data")'
```

```text
<string>:1: DeprecationWarning: Python 3.14 will, by default, filter extracted tar archives and reject files or modify their metadata. Use the filter argument to control this behavior.
escape.txt
tarfile.OutsideDestinationError: '../escape.txt' would be extracted to '…/py/escape.txt', which is outside the destination
```

이 머신의 Python 3.13은 경고만 찍고 `escape.txt`를 바깥에 썼다(경로는 줄였다). `filter="data"`를 주자 막았다. 이 필터는 파이썬 3.12에 들어왔고(그보다 앞선 몇몇 버전에도 보안 패치로 들어갔다) 3.14부터 기본값이 된다. 업로드 받은 압축 파일을 서버에서 푸는 코드라면 필터를 꼭 주고, 언어 버전과 상관없이 푼 뒤의 경로가 대상 디렉터리 안인지 확인한다. 심볼릭 링크를 먼저 풀고 그 링크를 통해 밖에 쓰는 변형도 있어서, 남의 파일은 별도 디렉터리에 일반 사용자로 푸는 것이 기본이다.

## 옮기는 도구: scp, sftp, rsync, wget

옮기는 도구는 "어디서 어디로", "한 번인지 반복인지", "끊기면 어떻게 하는지"로 고른다.

`scp`는 가장 단순하다. `scp file host:/path/`로 한 번 복사한다. OpenSSH 9.0부터 scp는 내부에서 SFTP 프로토콜을 쓴다. 예전 scp 프로토콜은 원격 셸이 파일 이름을 해석하는 구조라 이름에 공백이나 따옴표가 있으면 엉키고 보안 문제도 있었다. 아주 오래된 서버와 안 맞으면 `scp -O`로 옛 방식을 쓴다. scp는 끊기면 처음부터 다시 보낸다.

`sftp`는 대화형 파일 관리자다. `ls`, `cd`, `get`, `put`, `reget`(이어 받기)이 있고, `sftp -b batch.txt host`로 명령 파일을 돌릴 수도 있다. 접속 설정과 키는 ssh와 같아서 [SSH 실전 글](/posts/ssh-in-practice)의 `~/.ssh/config`가 그대로 통한다.

`rsync`는 반복 동기화용이다. 받는 쪽에 이미 있는 파일은 건너뛰고, 바뀐 파일은 바뀐 부분만 보낸다. 가장 자주 틀리는 것이 원본 끝의 `/`다.

```bash
mkdir -p src/sub d1 d2; echo a > src/a.log; echo b > src/sub/b.log
rsync -a src d1/      # 끝에 / 없음: src 디렉터리 자체를 넣는다
rsync -a src/ d2/     # 끝에 / 있음: src 안의 내용을 넣는다
find d1 d2 | sort
```

```text
d1
d1/src
d1/src/a.log
d1/src/sub
d1/src/sub/b.log
d2
d2/a.log
d2/sub
d2/sub/b.log
```

`--delete`는 원본에 없는 파일을 받는 쪽에서 지운다. 원본과 대상을 바꿔 적거나 슬래시를 틀리면 대상 전체가 지워질 수 있으니 처음에는 `--dry-run`(`-n`)과 `--itemize-changes`(`-i`)로 무엇이 지워질지 먼저 본다.

```bash
echo old > d2/stale.log
rsync -a --delete --dry-run --itemize-changes src/ d2/   # 보기만 한다
echo c > src/c.log
rsync -ai --delete src/ d2/                               # 실제로 한다
```

```text
*deleting   stale.log
*deleting   stale.log
>f+++++++++ c.log
```

첫 줄이 미리보기, 아래 두 줄이 실제 실행이다. `>f+++++++++`는 "받는 쪽으로 보낸 새 파일"이다. 실무에서 쓰는 옵션 조합을 조각으로 나눠 보면 이렇다. 조각을 누르면 각 옵션이 무엇을 지키는지 나온다.

## FTP, FTPS, SFTP는 이름만 비슷하다

셋은 이름이 비슷해서 자주 섞어 부르지만 프로토콜이 다르다.

FTP는 1970년대부터 쓴 프로토콜이다. 명령용 연결(21번 포트)과 데이터용 연결을 따로 연다. 데이터 연결을 서버가 클라이언트로 거는 active 모드와 클라이언트가 서버의 임시 포트로 거는 passive 모드가 있어서 방화벽과 NAT에 걸리기 쉽다. 그리고 아이디와 비밀번호, 내용이 모두 평문이다.

FTPS는 FTP에 TLS를 씌운 것이다. 21번에서 `AUTH TLS`로 올리는 명시적 방식과 처음부터 990번에서 TLS로 시작하는 암묵적 방식이 있다. 데이터 연결이 따로인 구조는 그대로라, 이제는 방화벽이 암호화된 명령을 들여다볼 수 없어서 passive 포트 범위를 서버와 방화벽에 미리 맞춰 열어야 한다.

SFTP는 FTP와 관계가 없다. SSH 위에서 도는 파일 전송 서브시스템이다. 22번 연결 하나로 인증과 명령과 데이터가 모두 암호화되어 오가서 방화벽 설정이 단순하고, 키 인증을 그대로 쓴다. 새로 만드는 파일 주고받기라면 SFTP(또는 HTTPS 업로드)를 고른다. FTPS는 거래처 시스템이 그것만 지원할 때 만난다. 파일만 주고받게 할 계정이라면 `sshd_config`에서 `ForceCommand internal-sftp`와 `ChrootDirectory`로 셸 없이 SFTP만 허용할 수 있다.

## 처음의 로그 앞에서

로그 몇 GB를 옮기는 장면으로 돌아가면, tar로 묶고 zstd -3으로 누르되 회선이 10Gbps라면 압축을 빼고, 디스크가 모자라면 파이프로 ssh에 바로 흘리고, 매일 반복할 일이면 rsync로 바꾸고 `--partial`과 `--bwlimit`를 붙인다. tar는 묶기만 하고 압축은 다른 프로그램이 한다는 것, 압축은 회선과 맞바꾸는 것이라는 두 가지만 기억하면 나머지는 상황에 맞게 고를 수 있다. 같은 Linux 토픽에서 패키지 저장소와 서명은 [패키지 관리자 글](/posts/linux-package-management)에, 서버에서 파일을 고치는 편집기는 [서버에서 vim 살아남기](/posts/vim-for-servers)에 있다.

## 면접에서 나올 만한 질문

### tar와 gzip은 각각 무엇을 하나요?

tar는 여러 파일을 헤더와 내용을 이어 붙인 한 덩어리로 묶을 뿐 압축하지 않는다. 권한, 소유자, 시각, 심볼릭 링크를 헤더에 담는다. gzip은 그 한 덩어리를 압축한다. `.tar.gz`는 묶은 뒤 통째로 누른 것이라 파일 사이 중복까지 줄이지만, 파일 하나를 꺼내려면 앞부분을 다 읽어야 한다.

### gzip, xz, zstd는 어떻게 고르나요?

크기와 속도를 맞바꾼다. 직접 잰 로그에서 zstd -3은 gzip -6과 크기가 비슷하면서 압축과 해제가 몇 배 빨랐고, xz -6이나 zstd -19는 더 작지만 압축이 수백 배 느렸다. 매번 만들어 보내는 데이터는 zstd 낮은 단계, 한 번 만들어 여러 번 받는 배포 파일은 높은 단계가 맞다. 데이터에 따라 순위가 바뀌니 중요한 결정은 내 데이터로 잰다.

### 압축하면 전송이 항상 빨라지나요?

아니다. 전체 시간은 압축과 전송과 해제의 합(파이프로 이으면 가장 느린 단계)이다. 10Gbps처럼 회선이 넓으면 전송 시간이 작아서 압축 시간이 손해가 되고, 실험에서도 압축 없이 보내는 것이 가장 빨랐다. 회선이 좁을수록 더 세게 누르는 쪽이 이긴다. 이미 압축된 파일은 다시 눌러도 줄지 않는다.

### tar와 zip의 차이는요?

tar는 묶기만 하고 압축은 밖에서 통째로 하며, 유닉스 권한과 소유자, 링크를 잘 보존한다. zip은 파일마다 따로 압축해서 하나만 바로 꺼낼 수 있지만, 기본으로 링크를 따라가 내용을 담고 소유자를 담지 않는다. 서버끼리의 백업은 tar, 사람이나 윈도와 주고받는 파일은 zip이 맞다.

### 업로드된 압축 파일을 서버에서 풀 때 무엇을 조심하나요?

경로 탈출이다. 항목 이름에 `../`나 절대 경로가 있으면 대상 디렉터리 밖에 쓸 수 있다. GNU tar는 기본으로 막지만 내 코드의 라이브러리는 다를 수 있어서, 파이썬이면 `extractall(filter="data")`를 주고 언어와 상관없이 푼 경로가 대상 안인지 확인한다. 링크를 통한 우회도 있으니 별도 디렉터리에 권한 없는 사용자로 푼다.

### scp와 rsync는 언제 각각 쓰나요?

한 번 복사는 scp로 충분하다. 반복 동기화, 큰 디렉터리, 끊기기 쉬운 회선이면 rsync를 쓴다. rsync는 이미 같은 파일을 건너뛰고 바뀐 부분만 보내며, `--partial`로 이어 보내고 `--bwlimit`로 서비스 회선을 지킨다. scp는 OpenSSH 9.0부터 내부적으로 SFTP 프로토콜을 쓰고, 끊기면 처음부터 다시 보낸다.

### rsync에서 원본 끝의 슬래시는 무슨 차이를 만드나요?

`src/`는 src 안의 내용을, `src`는 src 디렉터리 자체를 대상에 넣는다. 슬래시를 빼먹으면 대상 안에 디렉터리가 한 겹 더 생기고, `--delete`와 함께 쓰면 엉뚱한 파일이 지워질 수 있다. 그래서 `--dry-run --itemize-changes`로 무엇이 바뀌고 지워지는지 먼저 본다.

### FTP, FTPS, SFTP는 어떻게 다른가요?

FTP는 명령과 데이터 연결을 따로 열고 모든 것이 평문이다. FTPS는 그 위에 TLS를 씌운 것이라 암호화되지만 데이터 연결 구조 때문에 방화벽에 passive 포트 범위를 열어야 한다. SFTP는 FTP와 무관한 SSH 서브시스템이라 22번 연결 하나로 키 인증과 암호화를 그대로 쓴다. 새로 만든다면 SFTP를 고른다.
