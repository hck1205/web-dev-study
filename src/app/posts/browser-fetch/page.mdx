주문 내역을 불러오는 코드에 `try/catch`를 둘러 두었다. 서버가 잠깐 죽어서 500을 돌려준 날, 화면에는 에러 안내가 아니라 이런 메시지가 떴다.

```
SyntaxError: Unexpected token '<', "<!DOCTYPE "... is not valid JSON
```

코드는 이랬다.

```ts
try {
  const res = await fetch("/api/orders");
  const orders = await res.json();
  render(orders);
} catch (e) {
  showError("주문 내역을 불러오지 못했다");
}
```

catch에 걸리긴 했다. 그런데 걸린 이유가 "서버가 500을 줬다"가 아니라 "HTML을 JSON으로 읽으려다 실패했다"였다. 서버가 JSON으로 에러를 줬다면 catch에도 안 걸리고 에러 객체를 주문 목록인 줄 알고 그렸을 것이다. `fetch`는 생각보다 많은 걸 개발자에게 맡긴다. 이 글은 그 맡겨진 일들을 하나씩 짚는다.

4번 단계가 `fetch`의 규칙이다. `fetch`가 reject하는 건 응답을 아예 받지 못했을 때다. 네트워크가 끊겼거나, DNS를 못 찾았거나, CORS 검사에 막혔거나, 요청을 취소했을 때다. 이때는 `TypeError`(취소는 `AbortError`)로 실패한다. 404든 500이든 HTTP 응답이 돌아왔다면 성공이다. HTTP 입장에서는 404도 정상적인 대답이기 때문이다. 상태 코드가 각각 무슨 뜻인지는 [HTTP 상태 코드](/posts/http-status-codes)에 정리했다.

그래서 상태를 직접 확인해야 한다. `res.ok`는 상태 코드가 200~299일 때만 `true`다.

```ts
const res = await fetch("/api/orders");
if (!res.ok) {
  throw new HttpError(res.status, await res.text());
}
const orders = await res.json();
```

304는 `ok`가 아닌데 왜 문제가 안 되는지 궁금할 수 있다. 브라우저가 HTTP 캐시로 재검증해서 받은 304는 캐시된 200 응답으로 바꿔서 넘겨준다. 직접 `If-None-Match`를 붙여 보냈을 때만 304가 그대로 보인다.

CORS에 막혔을 때 `TypeError`만 받고 이유는 알 수 없다는 것도 기억해 둘 만하다. 이유는 개발자 도구 콘솔에만 찍힌다. 자세한 건 [CORS](/posts/cors) 글에서 다뤘다.

## 본문은 한 번만 읽힌다

`Response`의 본문은 스트림이다. 서버에서 바이트가 흘러오는 관이라서, 한 번 끝까지 읽으면 다시 읽을 수 없다.

```ts
const res = await fetch("/api/orders");
console.log(await res.text());
await res.json(); // TypeError: body stream already read
```

에러 로그를 남기려고 `text()`로 한 번 읽고, 다시 `json()`을 부르면 이렇게 된다. 읽었는지는 `res.bodyUsed`로 확인할 수 있다. 두 번 읽어야 한다면 읽기 전에 `res.clone()`으로 복사해 둔다. 서비스 워커에서 응답을 캐시에 넣으면서 페이지에도 돌려줄 때 이 패턴을 쓴다. 다만 복제본 하나만 읽고 다른 하나를 오래 놔두면, 안 읽은 쪽을 위해 데이터가 메모리에 쌓인다. 큰 파일에서 이걸 놓치면 메모리를 꽤 먹는다.

본문 읽기에서 자주 나는 실수가 하나 더 있다. 204 No Content처럼 본문이 비어 있는 응답에 `res.json()`을 부르면 `SyntaxError: Unexpected end of JSON input`이 난다. 삭제 API처럼 본문이 없을 수 있는 곳에서는 상태 코드나 `Content-Type`을 먼저 본다.

스트림이라 좋은 점도 있다. 다 받을 때까지 기다리지 않고 도착하는 대로 읽을 수 있다. `res.body.getReader()`로 조각(`Uint8Array`)을 하나씩 꺼내면 다운로드 진행률을 만들 수 있다.

```ts
const res = await fetch("/files/report.pdf");
const total = Number(res.headers.get("Content-Length")) || 0;
const reader = res.body!.getReader();
const chunks: Uint8Array[] = [];
let received = 0;

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  chunks.push(value);
  received += value.length;
  if (total) setProgress(received / total);
}
const blob = new Blob(chunks);
```

이 진행률은 믿을 만한 숫자가 아닐 때가 있다. 서버가 gzip으로 압축해서 보냈다면 `Content-Length`는 압축된 크기인데, 스트림에서 나오는 건 브라우저가 압축을 푼 바이트다. 진행률이 100%를 넘어 버린다. 청크 전송이면 `Content-Length` 자체가 없다. 그래서 진행률은 이미 압축된 파일(이미지, PDF, zip)을 받을 때만 쓰는 편이 안전하다. LLM 응답처럼 서버가 텍스트를 조금씩 흘려보내는 API도 같은 방식으로 읽는다. 이때는 `TextDecoderStream`을 끼워 글자로 바꾼다.

본문 종류에 따라 `Content-Type`이 자동으로 붙는 경우가 있다. `URLSearchParams`는 `application/x-www-form-urlencoded`, 문자열은 `text/plain`, `Blob`은 그 Blob의 타입이 붙는다. `FormData`는 `multipart/form-data; boundary=...`가 붙는데, 여기서 흔한 실수가 나온다. 파일 업로드에 `Content-Type: multipart/form-data`를 직접 적으면 boundary 값이 빠져서 서버가 본문을 나누지 못한다. `FormData`를 보낼 때는 `Content-Type`을 적지 않는다.

`credentials`는 쿠키 세션으로 로그인하는 서비스에서 자주 문제가 된다. 프론트엔드와 API가 다른 출처면 기본값으로는 쿠키가 안 실려서 로그인이 풀린 것처럼 보인다. `include`로 바꾸면 서버도 CORS 응답에 `Access-Control-Allow-Credentials: true`와 정확한 출처를 줘야 한다. 쿠키 쪽 규칙은 [쿠키와 세션으로 로그인 유지하기](/posts/cookie-session-login)에 있다.

`mode: "no-cors"`는 CORS 에러를 없애는 스위치처럼 보여서 잘못 쓰이곤 한다. 에러는 사라지지만 응답이 불투명해서 상태 코드도 본문도 읽을 수 없다. 응답을 읽어야 하는 요청이라면 쓸 이유가 없다. 서비스 워커가 다른 출처의 이미지를 그대로 캐시에 넣어 둘 때처럼, 내용은 몰라도 되는 경우에나 쓴다.

## 페이지를 닫을 때 보내는 요청

사용자가 탭을 닫는 순간 "이 글을 몇 초 읽었는지"를 서버에 보내고 싶다고 하자. 평범한 `fetch`는 페이지가 사라지면서 같이 취소될 수 있다. 예전에는 `unload` 이벤트 안에서 동기 XHR로 페이지 종료를 붙잡았는데, 사용자는 그 사이 화면이 멈춘 걸 느끼고 크롬 계열은 이제 페이지를 닫을 때의 동기 XHR을 막는다.

지금은 두 가지 방법이 있다. `navigator.sendBeacon(url, data)`는 POST 하나를 브라우저에 맡기고 바로 돌아온다. 응답은 받을 수 없고, 헤더도 정할 수 없다. 반환값은 전송을 큐에 넣었는지일 뿐 서버가 받았는지가 아니다. `fetch`에 `keepalive: true`를 주면 같은 일을 하면서 메서드와 헤더를 고를 수 있다. 둘 다 본문 크기에 한계(keepalive는 진행 중인 요청 합계 64KiB)가 있어서 작은 데이터용이다.

언제 보내느냐도 중요하다. 모바일 브라우저는 앱 전환이나 탭 정리로 페이지를 없앨 때 `unload`를 부르지 않는 경우가 많다. `unload` 리스너가 있으면 뒤로 가기 캐시(bfcache)에서 빠지는 브라우저도 있다. 그래서 `visibilitychange`에서 `document.visibilityState === "hidden"`일 때 보내는 게 권장된다. 페이지가 숨겨지는 순간이 사실상 마지막으로 확실히 코드를 돌릴 수 있는 시점이다.

```ts
document.addEventListener("visibilitychange", () => {
  if (document.visibilityState !== "hidden") return;
  fetch("/api/analytics", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ slug, readMs: performance.now() }),
    keepalive: true,
  });
});
```

숨겨졌다가 다시 보일 수도 있으니, 서버는 같은 세션에서 여러 번 오는 걸 감안해서 받는다.

## 지난 요청은 취소한다

응답을 무시하는 것만으로 화면은 맞아진다. 하지만 낡은 요청은 여전히 네트워크를 쓰고, 큰 응답이면 내려받고 파싱까지 한다. 필요 없어진 요청은 취소하는 편이 낫다. `AbortController`가 그 일을 한다.

```ts
let controller: AbortController | null = null;

async function onInput(q: string) {
  controller?.abort();
  controller = new AbortController();
  try {
    const res = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
      signal: controller.signal,
    });
    if (!res.ok) throw new HttpError(res.status, await res.text());
    render(await res.json());
  } catch (e) {
    if (e instanceof DOMException && e.name === "AbortError") return; // 내가 취소한 것
    showError(e);
  }
}
```

새 요청을 만들기 전에 이전 컨트롤러의 `abort()`를 부르면, 이전 `fetch`는 `AbortError`라는 이름의 `DOMException`으로 reject된다. 이미 응답 헤더를 받아 본문을 읽던 중이었다면 본문 읽기가 같은 에러로 끊긴다. 취소는 사용자가 원한 일이니 에러 화면을 띄우지 않고 조용히 넘긴다. 이 분기를 빠뜨리면 빠르게 타이핑할 때마다 에러 토스트가 뜬다. 쿼리 문자열을 손으로 붙일 때 `encodeURIComponent`를 빼먹는 것도 흔하다. `&`나 `#`이 들어간 검색어가 쿼리를 깨뜨린다. 값이 여러 개면 `new URLSearchParams({ q, page: "2" })`가 인코딩까지 해 준다.

알아 둘 점이 있다. 취소는 브라우저 쪽에서 응답을 기다리지 않겠다는 뜻이다. 요청이 이미 서버에 닿았다면 서버는 하던 일을 계속한다. 검색처럼 읽기만 하는 요청이면 상관없지만, 결제 요청을 취소했다고 결제가 안 된 건 아니다.

타임아웃도 같은 장치로 건다. `AbortSignal.timeout(ms)`은 시간이 지나면 스스로 취소되는 신호를 만든다. 이때 에러 이름은 `TimeoutError`라서 "느려서 실패"와 "내가 취소"를 구분할 수 있다. 사용자의 취소와 타임아웃을 함께 걸려면 `AbortSignal.any`로 신호를 합친다.

```ts
const res = await fetch(url, {
  signal: AbortSignal.any([controller.signal, AbortSignal.timeout(5000)]),
});
```

`AbortSignal.timeout`은 2022년, `AbortSignal.any`는 2023~2024년에 주요 브라우저에 들어왔다. 오래된 브라우저까지 지원해야 하면 `setTimeout`에서 `controller.abort()`를 부르는 방식으로 대신한다. 타임아웃은 응답 헤더가 올 때까지만이 아니라 본문을 다 읽을 때까지 유효하다는 점도 기억해 둔다. 큰 파일을 받는 요청에 짧은 타임아웃을 걸면 다운로드 도중에 끊긴다.

## 실패하면 다시 보낼까

타임아웃이 났거나 503을 받았다면 다시 보내고 싶어진다. 여기에는 지켜야 할 조건이 있다.

다시 보내도 되는 요청이어야 한다. GET, PUT, DELETE는 멱등해서 여러 번 보내도 결과가 같다. POST는 보낼 때마다 새로 만들 수 있어서, 주문 생성 요청을 자동으로 다시 보내면 주문이 두 개 생길 수 있다. 메서드별 성질은 [HTTP 메서드](/posts/http-methods)에, POST를 안전하게 재시도하는 멱등성 키는 [장애가 번지지 않게 막는 패턴](/posts/resilience-patterns)에 정리했다.

다시 보내서 나아질 실패여야 한다. 네트워크 에러, 408, 429, 502, 503, 504는 잠시 뒤 성공할 수 있다. 400, 401, 403, 404, 422는 몇 번을 보내도 같은 답이 온다. 429나 503에 `Retry-After` 헤더가 있으면 그 시간만큼 기다린다.

간격을 벌리며 보내야 한다. 실패하자마자 다시 보내면 이미 힘든 서버를 더 누른다. 대기 시간을 지수적으로 늘리고 무작위성(지터)을 섞는 방식은 위의 장애 대응 글에서 계산까지 해 봤다.

## 에러를 한 곳에서 다룬다

지금까지 나온 실패를 모아 보면 종류가 꽤 많다. 네트워크 에러(`TypeError`), 취소(`AbortError`), 타임아웃(`TimeoutError`), HTTP 에러 상태, 본문 파싱 실패. 화면마다 이걸 따로 처리하면 어딘가는 빠진다. 그래서 `fetch`를 한 번 감싼 함수를 두고 모든 요청이 그걸 거치게 한다.

```ts
export class HttpError extends Error {
  constructor(
    public status: number,
    public body: unknown,
  ) {
    super(`HTTP ${status}`);
  }
}

export async function request<T>(url: string, init: RequestInit = {}): Promise<T> {
  const res = await fetch(url, {
    ...init,
    headers: { Accept: "application/json", ...init.headers },
    signal: init.signal ?? AbortSignal.timeout(10_000),
  });

  const isJson = res.headers.get("Content-Type")?.includes("json");
  const body = res.status === 204 ? null : isJson ? await res.json() : await res.text();

  if (!res.ok) throw new HttpError(res.status, body);
  return body as T;
}
```

이렇게 해 두면 화면 쪽은 `HttpError`인지, `AbortError`인지, 그 밖의 네트워크 에러인지만 보면 된다. 401이면 로그인 화면으로 보내고, 서버가 표준 에러 형식(Problem Details)으로 보낸 `detail`을 꺼내 보여 주는 것 같은 공통 처리도 이 함수 한 곳에 넣는다. 서버 쪽 에러 형식은 [REST API를 설계할 때 정할 것들](/posts/rest-api-design)에서 다룬다.

## XHR, fetch, axios

`fetch` 이전에는 `XMLHttpRequest`(XHR)가 있었다. 이벤트 콜백 방식이라 쓰기 번거롭지만 지금도 `fetch`가 못 하는 게 하나 있다. 업로드 진행률이다. `xhr.upload.onprogress`로 지금까지 보낸 바이트를 받을 수 있다. `fetch`는 받는 쪽 진행률은 스트림으로 만들 수 있어도 보내는 쪽 진행률을 알려 주는 API가 없다. 크롬 계열은 요청 본문을 스트림으로 보내는 기능(`duplex: "half"`)을 지원하지만 업로드 진행률 용도로는 아직 쓰기 어렵다. 큰 파일 업로드 화면에 진행 막대가 필요하면 XHR이나 XHR을 쓰는 라이브러리를 고른다.

axios는 브라우저에서 기본으로 XHR 위에서 돈다(1.7부터는 `fetch`를 쓰는 어댑터도 고를 수 있다). `fetch`와 비교하면 차이가 분명하다.

- 2xx가 아닌 상태면 reject한다. `validateStatus`로 바꿀 수 있다.
- 객체를 넘기면 JSON으로 바꾸고, JSON 응답은 파싱해서 `data`에 넣어 준다.
- `timeout` 옵션과 `onUploadProgress`가 있다.
- 인터셉터로 모든 요청에 토큰을 붙이거나, 401 응답이 오면 토큰을 갱신하고 원래 요청을 다시 보내는 로직을 한 곳에 둘 수 있다.

반대로 axios는 번들에 의존성이 하나 늘고, 스트림으로 응답을 조금씩 읽는 일은 브라우저에서 잘 못한다. 앞에서 만든 `request` 함수 정도면 `fetch`로도 axios가 해 주는 일의 대부분을 할 수 있다. 업로드 진행률과 인터셉터 체인이 필요하면 axios, 가볍게 가고 싶거나 스트리밍 응답을 다뤄야 하면 `fetch`나 `ky` 같은 얇은 래퍼가 맞는다. 어느 쪽이든 화면 코드가 라이브러리를 직접 부르지 않고 감싼 함수 하나를 거치게 해 두면 나중에 바꾸기 쉽다.

## 같은 요청을 두 번 보내지 않으려면

헤더의 프로필 영역과 사이드바가 둘 다 `/api/me`를 부른다. 컴포넌트가 따로 만들어졌으니 요청도 두 번 나간다. 브라우저 HTTP 캐시가 막아 줄 것 같지만, 두 요청이 거의 동시에 출발하면 첫 응답이 캐시에 들어가기 전이라 둘 다 서버까지 간다. 응답이 `Cache-Control: no-store`라면 처음부터 캐시 대상이 아니다. HTTP 캐시가 어떤 응답을 얼마나 저장하는지는 [HTTP 캐시와 CDN](/posts/http-caching-cdn)에서 다뤘다.

그래서 애플리케이션 안에 한 겹을 더 둔다. 진행 중인 요청을 키로 기억해 두고, 같은 키의 요청이 오면 새로 보내지 않고 그 Promise를 나눠 주는 방식이다. 직접 짜면 `Map<string, Promise>` 하나로 시작하지만, 캐시 만료, 화면 포커스 시 다시 받기, 에러 재시도, 취소까지 붙이다 보면 라이브러리가 하는 일을 다시 만들게 된다.

TanStack Query가 이 자리를 맡는다. 같은 `queryKey`로 동시에 부르면 요청은 한 번만 나가고, 받은 데이터는 `staleTime` 동안 신선하다고 보고 다시 묻지 않는다(기본값 0이라 마운트나 창 포커스 때마다 백그라운드에서 다시 받는다). `queryFn`에 넘어오는 `signal`을 `fetch`에 전달해 두면, 결과를 기다리던 컴포넌트가 사라졌을 때 라이브러리가 요청을 취소한다. 검색창 예시라면 `queryKey`에 검색어를 넣는 것만으로 앞의 경쟁 상태도 사라진다. 화면은 지금 키의 데이터만 보여 주기 때문이다. 쿼리는 기본 3번 재시도하고 뮤테이션은 재시도하지 않는 기본값도 앞에서 본 멱등성 원칙과 맞는다.

## 에러 수집기에 Failed to fetch만 쌓일 때

운영에서 에러 수집 도구를 열면 `TypeError: Failed to fetch`가 제일 위에 있는 경우가 많다. 문제는 이 한 줄이 서로 다른 원인을 전부 덮는다는 데 있다. 크롬 141에서 로컬 서버 두 개(`localhost:8001`의 페이지, `127.0.0.1:8002`의 API)를 띄워 세 가지 실패를 일부러 만들고 콘솔과 `catch`에 찍힌 것을 그대로 옮겼다.

```text
--- 응답에 Access-Control-Allow-Origin이 없다
[console.error] Access to fetch at 'http://127.0.0.1:8002/nocors' from origin 'http://localhost:8001' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.
[console.error] Failed to load resource: net::ERR_FAILED
[catch] TypeError: Failed to fetch

--- credentials: "include"인데 서버가 *를 줬다
[console.error] Access to fetch at 'http://127.0.0.1:8002/star' from origin 'http://localhost:8001' has been blocked by CORS policy: The value of the 'Access-Control-Allow-Origin' header in the response must not be the wildcard '*' when the request's credentials mode is 'include'.
[catch] TypeError: Failed to fetch

--- 서버 포트가 닫혀 있다
[console.error] Failed to load resource: net::ERR_CONNECTION_REFUSED
[catch] TypeError: Failed to fetch
```

`catch`가 받은 건 세 번 모두 같은 문장이다. 원인은 콘솔의 바로 윗줄과 Network 탭의 Status 칸(`CORS error`, `(failed) net::ERR_CONNECTION_REFUSED`)에만 있다. 페이지 코드는 보안상 이 이유를 읽을 수 없다. 그래서 수집기에 `e.message`만 보내면 원인을 영영 가를 수 없다. 래퍼 함수에서 실패할 때 요청 URL, 메서드, `navigator.onLine`, 걸린 시간을 같이 남겨 두면 "특정 API만 실패한다", "오프라인 사용자다", "요청 직후 바로 실패한다(CORS나 차단)"를 나눠 볼 수 있다. 광고 차단 확장 프로그램이 `/analytics`, `/track` 같은 주소를 막을 때도 같은 `TypeError`가 나고, 크롬 Network 탭에는 `net::ERR_BLOCKED_BY_CLIENT`로 보인다. 이 경우는 사용자 쪽 문제라 알림에서 빼는 게 낫다.

CORS로 의심되면 브라우저 밖에서 헤더를 직접 본다. `Origin`을 붙여 보내면 서버가 실제로 무엇을 돌려주는지 보인다.

```bash
# 브라우저처럼 Origin을 붙여 보내고 CORS 관련 헤더만 본다
curl -si -H 'Origin: http://localhost:3000' http://localhost:8001/api/orders | grep -i -E '^HTTP|access-control'
```

```text
HTTP/1.1 200 OK
Access-Control-Allow-Origin: *
```

`*`가 보이는데 프런트엔드 코드가 `credentials: "include"`라면 위의 두 번째 에러가 난다. 서버가 요청의 `Origin`을 그대로 돌려주고 `Access-Control-Allow-Credentials: true`를 붙여야 한다. 프리플라이트까지 포함한 규칙은 [CORS](/posts/cors)에, `ERR_CONNECTION_REFUSED`처럼 연결 자체가 안 되는 경우를 계층별로 좁히는 순서는 [계층별로 장애 좁히기](/posts/network-troubleshooting-by-layer)에 있다.

두 번째로 흔한 건 처음 장면의 변형이다. 상태가 200인데 JSON 파싱에서 터진다. 개발 서버나 정적 호스팅의 SPA 폴백 규칙이 "없는 경로는 전부 `index.html`"이라서, API 경로를 잘못 쳐도 404 대신 HTML이 200으로 온다.

```bash
# 오타 난 API 경로를 그대로 찔러 본다
curl -si http://localhost:8001/api/orderz
```

```text
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Date: Sun, 18 Oct 2026 11:17:05 GMT
Connection: keep-alive
Keep-Alive: timeout=5
Transfer-Encoding: chunked

<!DOCTYPE html><html><body><div id="root"></div></body></html>
```

`Content-Type: text/html`이 답이다. 브라우저에서는 `SyntaxError: Unexpected token '<', "<!DOCTYPE "... is not valid JSON`으로 보인다. 앞에서 만든 `request` 함수처럼 `Content-Type`을 보고 JSON일 때만 `res.json()`을 부르면 이 상황이 "HTML이 왔다"는 분명한 에러가 된다. 서버 쪽에서는 `/api/` 아래를 폴백 대상에서 빼서 없는 API가 진짜 404를 돌려주게 한다.

세 번째는 Network 탭에 `(canceled)`가 줄줄이 찍히는 경우다. 직접 취소한 요청과 타임아웃은 에러 이름과 문장이 다르다. 같은 크롬에서 3초 걸리는 요청을 100ms에 취소하고, 500ms 타임아웃을 걸어 본 결과다.

```text
[abort()]   AbortError: signal is aborted without reason
[timeout]   TimeoutError: signal timed out
[Network]   http://localhost:8001/api/slow net::ERR_ABORTED
```

`AbortError`는 내가 원한 취소라서 수집기에 보내지 않고, `TimeoutError`는 "서버가 느리다"는 신호라서 따로 센다. 개발 모드에서 같은 요청이 한 번 `(canceled)`되고 바로 다시 나가는 건 React `StrictMode`가 effect를 마운트, 정리, 다시 마운트하기 때문이다. 정리 함수에서 `abort()`를 부르도록 잘 짰다는 뜻이니 고칠 일이 아니다. 프로덕션 빌드에서 같은 모양이 보이면 그때는 컴포넌트가 실제로 마운트·언마운트를 반복하는지 본다.

## 다시 처음 코드로

처음 코드가 이상하게 실패한 건 `fetch`가 HTTP 에러에서 reject하지 않는데 상태를 확인하지 않았기 때문이다. `fetch`는 응답을 받는 데까지만 책임지고, 그 응답이 성공인지, 본문이 어떤 형식인지, 언제 포기할지, 낡은 응답을 버릴지는 호출하는 쪽이 정한다. `res.ok` 확인, 본문은 한 번만, `AbortController`로 취소와 타임아웃, 마지막 요청만 반영, 멱등한 요청만 재시도. 이 규칙을 감싼 함수 하나에 모아 두면 화면 코드는 데이터를 그리는 일만 하면 된다.

## 면접에서 나올 만한 질문

### fetch는 404나 500 응답에서 reject되나요?

reject되지 않는다. fetch는 응답을 받지 못했을 때만 reject한다. 네트워크 실패, CORS 차단, 취소가 그런 경우다. 404나 500도 HTTP 응답은 받은 것이라 resolve되고, `res.ok`가 false가 된다. 그래서 `res.ok`나 `res.status`를 직접 확인해서 에러로 바꿔야 한다. axios는 반대로 2xx가 아니면 reject한다.

### 응답 본문을 두 번 읽으면 어떻게 되나요?

`TypeError`가 난다. 본문은 스트림이라 한 번 읽으면 소비되고, `bodyUsed`가 true가 된다. 두 번 써야 하면 읽기 전에 `res.clone()`으로 복사한다. 다만 복제본 중 하나를 읽지 않고 두면 그쪽을 위해 데이터가 메모리에 쌓이니 둘 다 읽거나 필요한 쪽만 남긴다.

### fetch에 타임아웃은 어떻게 거나요?

fetch에는 timeout 옵션이 없어서 `AbortSignal`로 건다. `AbortSignal.timeout(5000)`을 `signal`에 넘기면 5초 뒤 `TimeoutError`로 reject된다. 사용자 취소와 함께 쓰려면 `AbortSignal.any`로 두 신호를 합친다. 타임아웃은 본문을 다 읽을 때까지 적용되고, 오래된 브라우저에서는 `setTimeout`과 `AbortController`로 대신한다.

### 검색창에서 늦게 온 응답이 최신 결과를 덮어쓰는 문제는 어떻게 막나요?

마지막으로 보낸 요청의 응답만 반영한다. 새 요청을 보낼 때 이전 요청을 `AbortController`로 취소하거나, 요청 번호를 기억했다가 최신이 아닌 응답은 버린다. React에서는 effect 정리 함수에서 무시 플래그를 세우는 방식을 쓰고, TanStack Query처럼 검색어를 키로 쓰는 라이브러리를 쓰면 지금 키의 데이터만 보여 줘서 자연스럽게 해결된다. 디바운스는 요청 수를 줄일 뿐 경쟁 상태를 없애지는 못한다.

### 요청을 abort하면 서버에서도 처리가 취소되나요?

보장되지 않는다. abort는 브라우저가 응답을 더 기다리지 않고 연결을 정리하는 것이다. 요청이 이미 서버에 닿았다면 서버는 하던 일을 끝낼 수 있다. 그래서 결제 같은 요청은 취소했다고 실패로 단정하지 말고, 결과를 다시 조회하거나 멱등성 키로 재시도를 안전하게 만든다.

### `credentials` 옵션은 무엇을 정하나요?

요청에 쿠키 같은 인증 정보를 실을지, 응답의 Set-Cookie를 받을지를 정한다. 기본값 same-origin은 같은 출처일 때만, include는 다른 출처에도, omit은 어디에도 싣지 않는다. 다른 출처 API에 include로 보내면 서버는 CORS 응답에 정확한 출처와 `Access-Control-Allow-Credentials: true`를 줘야 하고, `*`는 쓸 수 없다.

### 페이지를 떠날 때 데이터를 보내려면 어떻게 하나요?

`navigator.sendBeacon`이나 `fetch`의 `keepalive: true`를 쓴다. 둘 다 페이지가 사라진 뒤에도 요청이 끝까지 가게 해 주고, 본문 크기는 작게 제한된다(keepalive는 진행 중인 요청 합계 64KiB). sendBeacon은 POST만 되고 응답을 못 받지만, keepalive fetch는 메서드와 헤더를 고를 수 있다. 시점은 모바일에서 잘 안 불리는 unload 대신 `visibilitychange`의 hidden을 쓴다.

### fetch 대신 axios나 XHR을 고르는 경우는 언제인가요?

업로드 진행률이 필요하면 XHR이나 XHR 기반인 axios를 고른다. fetch에는 보내는 쪽 진행률 API가 없다. axios는 non-2xx reject, 자동 JSON 변환, timeout, 인터셉터를 기본으로 주니 토큰 갱신 같은 공통 로직을 모으기 편하다. 반대로 응답을 스트림으로 조금씩 읽어야 하거나 의존성을 줄이고 싶으면 fetch를 얇게 감싸 쓴다.
