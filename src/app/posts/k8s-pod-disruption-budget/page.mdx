<EasyIntro>
  기계를 점검하려고 그 위의 Pod를 다른 곳으로 옮기는 일은 흔하다. 그런데 기계를 다루는 팀과 앱을 운영하는 팀이 다르면, 한꺼번에 몇 개까지 내려도 되는지 서로 모른다. PodDisruptionBudget은 이 앱은 동시에 몇 개까지 내려가도 된다는 약속을 숫자 하나로 적어 두는 것이다.

  이 약속을 읽는 쪽은 정해져 있다. 사람이나 도구가 일부러 Pod를 내릴 때 거치는 창구만 이 숫자를 확인하고, 기계가 갑자기 고장 나서 사라지는 일은 막지 못한다. 극장에서 공연 중에 빈자리가 몇 개 이상 유지돼야 한다는 규칙이 있어도 정전은 못 막는 것과 같다.

  흔한 사고는 이 숫자를 0에 붙게 걸어 두는 것이다. 그러면 기계 교체, 업그레이드, 줄이기가 전부 멈추고, 점검 명령이 같은 오류를 영원히 반복한다. 그래서 Pod 개수를 따라가는 비율 형태로, 가장 적을 때도 하나는 내릴 수 있게 건다.
</EasyIntro>

노드 OS를 올리려고 `kubectl drain`을 걸었다. 몇 초 뒤 같은 줄이 반복되기 시작한다.

```text
evicting pod default/web-759684fbb8-dh6gx
error when evicting pods/"web-759684fbb8-dh6gx" -n "default" (will retry after 5s): Cannot evict pod as it would violate the pod's disruption budget.
evicting pod default/web-759684fbb8-dh6gx
error when evicting pods/"web-759684fbb8-dh6gx" -n "default" (will retry after 5s): Cannot evict pod as it would violate the pod's disruption budget.
```

`--timeout`을 주지 않았다면 이 줄은 영원히 반복된다. 범인은 누군가 걸어 둔 PodDisruptionBudget(PDB)이다. PDB는 "이 앱은 동시에 몇 개까지 내려가도 된다"를 클러스터에 적어 두는 오브젝트다. 노드 작업을 하는 쪽과 앱을 운영하는 쪽이 다른 팀일 때, 둘 사이의 약속을 코드로 만든 것이다.

이 글은 PDB가 어떤 중단을 막고 어떤 중단은 못 막는지, eviction API가 429를 돌려주기까지의 과정, `ALLOWED DISRUPTIONS` 숫자가 계산되는 방식, drain을 영원히 멈추게 하는 설정과 준비 안 된 Pod를 다루는 `unhealthyPodEvictionPolicy`, HPA와 함께 쓸 때의 함정을 본다. 출력은 kwok로 만든 실습 클러스터(Kubernetes 1.37.0, 가짜 노드 3대)에서 받았다. API 서버, kube-controller-manager의 disruption 컨트롤러, 스케줄러, `kubectl drain`은 진짜다. 컨테이너만 실제로 돌지 않는다.

이 주제의 다른 글: Pod 크기를 바꾸는 쪽은 [VPA](/posts/k8s-vpa)와 [재시작 없는 리소스 변경](/posts/k8s-in-place-resize), 노드를 늘리고 줄이는 쪽은 [노드 오토스케일링과 Karpenter](/posts/k8s-node-autoscaling-karpenter)에서 다룬다. 셋 다 결국 PDB를 거쳐 Pod를 내린다.

## 누가 내리느냐에 따라 규칙이 다르다

Pod가 사라지는 이유는 크게 둘이다. 하나는 사람이나 컨트롤러가 일부러 내리는 것이고, 다른 하나는 막을 수 없이 내려가는 것이다. 쿠버네티스 문서는 앞의 것을 자발적 중단(voluntary disruption), 뒤의 것을 비자발적 중단(involuntary disruption)이라고 부른다.

비자발적 중단은 노드 하드웨어 고장, 커널 패닉, 클라우드 VM이 사라지는 것, 노드 메모리가 모자라 kubelet이 Pod를 쫓아내는 것(노드 압박 eviction, [requests와 limits](/posts/k8s-pod-resources)에서 다룬다) 같은 것이다. PDB는 이것들을 하나도 막지 못한다. 노드가 꺼지는 데 허락을 구할 상대가 없기 때문이다.

PDB가 지키는 것은 자발적 중단 중에서도 **eviction API를 거치는 것**뿐이다. 아래 그림에서 실선은 PDB를 묻고 지나가는 길, 점선은 묻지 않고 지나가는 길이다.

`kubectl delete pod`는 PDB를 보지 않는다. Deployment가 롤링 업데이트 중에 옛 ReplicaSet을 줄이는 것도 마찬가지다. 그래서 배포 중의 가용성은 PDB가 아니라 maxUnavailable이 정한다([Deployment와 롤링 업데이트](/posts/k8s-deployment)). HPA가 replicas를 줄이는 것도 ReplicaSet이 Pod를 지우는 것이라 PDB와 상관없다. 실제로 PDB가 하나 걸린 상태에서 Pod를 그냥 지워 보면 아무 말 없이 지워진다.

```bash
# PDB가 있어도 delete는 바로 지운다
kubectl delete pod web-7d9f9dc754-4g85d
```

```text
pod "web-7d9f9dc754-4g85d" deleted from default namespace
```

정리하면 PDB는 "노드를 비우는 사람"을 위한 장치다. 클러스터 업그레이드, 노드 교체, 오토스케일러의 축소, VPA의 재생성처럼 노드나 Pod를 계획적으로 갈아 끼우는 작업이 앱을 한꺼번에 내리지 않게 막는다.

## eviction 한 번이 지나가는 길

같은 순서를 손으로 재현했다. 노드 셋을 모두 cordon해서 새 Pod가 뜨지 못하게 한 다음 eviction을 두 번 보냈다.

```bash
# Pod 3개, minAvailable 2. 새 Pod가 못 뜨게 노드를 모두 cordon한다
kubectl cordon node-1 node-2 node-3

# eviction 요청 본문. kubectl drain이 보내는 것과 같다
cat > ev.json <<'EOF'
{"apiVersion":"policy/v1","kind":"Eviction","metadata":{"name":"web-759684fbb8-92gzb","namespace":"default"}}
EOF

# 첫 번째 eviction
kubectl create --raw /api/v1/namespaces/default/pods/web-759684fbb8-92gzb/eviction -f ev.json

# 두 번째 eviction (ev2.json은 Pod 이름만 바꾼 것), -v=8로 응답 코드와 본문을 본다
kubectl create --raw /api/v1/namespaces/default/pods/web-759684fbb8-ljq4f/eviction -f ev2.json -v=8
```

같은 Pod를 PDB 두 개가 고르면 메시지가 다르다. 이때는 429가 아니라 500이고, 재시도해도 영원히 통과하지 못한다.

```text

```

Helm 차트가 PDB를 하나 만들고, 누군가 손으로 같은 라벨의 PDB를 또 만든 경우에 흔하다. 문서도 셀렉터가 겹치지 않게 하라고 적고 있다.

## ALLOWED DISRUPTIONS는 이렇게 센다

PDB의 status에는 숫자 넷이 있다. disruption 컨트롤러(kube-controller-manager 안에 있다)가 셀렉터에 맞는 Pod를 보고 계속 고쳐 쓴다.

```bash
# 위 상황에서 PDB의 status만 본다
kubectl get pdb web-pdb -o yaml | sed -n '/^status/,$p'
```

```text
status:
  conditions:
  - lastTransitionTime: "2026-10-21T00:48:35Z"
    message: ""
    observedGeneration: 1
    reason: InsufficientPods
    status: "False"
    type: DisruptionAllowed
  currentHealthy: 2
  desiredHealthy: 2
  disruptionsAllowed: 0
  expectedPods: 3
  observedGeneration: 1
```

`expectedPods`는 Pod를 소유한 컨트롤러(Deployment, StatefulSet 등)의 replicas다. 지금 떠 있는 Pod 수가 아니다. `currentHealthy`는 Ready 조건이 True인 Pod 수, `desiredHealthy`는 최소한 남아야 하는 수다. `disruptionsAllowed`는 그 차이다. 셋 중 하나가 빠져 Pending인 새 Pod는 Ready가 아니라 건강한 수에 들어가지 않는다.

minAvailable과 maxUnavailable은 desiredHealthy를 정하는 두 가지 방법이다. 퍼센트로 주면 올림한다. Pod 7개에 `minAvailable: 50%`면 3.5를 올려 4개가 남아야 하고, `maxUnavailable: 30%`면 2.1을 올려 3개까지 내려가도 된다. 실습 클러스터에서 두 경우를 확인했다.

```text
NAME      MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
web-pdb   50%             N/A               3                     83s

NAME      MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
web-pdb   N/A             30%               3                     3s
{"currentHealthy":7,"desiredHealthy":4,"disruptionsAllowed":3,"expectedPods":7, ...}
```

maxUnavailable 쪽의 올림은 직관과 반대다. 30%라고 적었지만 7개 중 3개(43%)가 내려갈 수 있다. "최대 30%"를 엄격히 지켜야 한다면 퍼센트 대신 정수를 쓴다. 아래 그림은 Pod 3개짜리 앱에서 노드 하나를 비울 때 숫자가 바뀌는 순서다.

## minAvailable이냐 maxUnavailable이냐

둘 중 하나만 쓸 수 있다. 차이는 replicas가 바뀔 때 드러난다. 같은 Pod 1개짜리 Deployment에 두 방식을 걸어 봤다.

```bash
# replicas 1인 앱에 PDB 두 가지를 걸어 비교한다 (실험용, 실제로는 겹치게 두지 않는다)
kubectl create pdb by-min --selector=app=web --min-available=1
kubectl create pdb by-max --selector=app=web --max-unavailable=1
kubectl get pdb
```

```text
NAME     MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
by-max   N/A             1                 1                     4s
by-min   1               N/A               0                     4s
```

`minAvailable: 1`은 Pod가 1개일 때 아무것도 허락하지 않는다. `maxUnavailable: 1`은 1개뿐이어도 하나를 내려도 된다고 한다. 앞의 것은 노드 작업을 막고, 뒤의 것은 잠깐의 다운타임을 허락한다. 어느 쪽이 맞는지는 앱이 정한다.

- 상태 없는 웹·API 서버: `maxUnavailable: 1`이나 `10%`처럼 비율로 둔다. replicas가 바뀌어도 그대로 의미가 통한다. 문서도 replicas 변화에 자동으로 따라가는 maxUnavailable을 권한다.
- 쿼럼이 있는 저장소(etcd, ZooKeeper, Kafka 컨트롤러): 5개 중 3개가 살아 있어야 쓰기가 되면 `minAvailable: 3`이나 `maxUnavailable: 1`이다. 다수결이 깨지면 쓰기가 멈추니 숫자를 정확히 계산한다.
- Pod 하나짜리 상태 있는 앱: PDB를 안 걸고 가끔의 다운타임을 받아들이거나, `maxUnavailable: 0`을 걸고 노드 작업 전에 사람끼리 이야기하는 방식이다. 문서가 실제로 이 두 가지를 제시한다.
- 재시작해도 되는 Job: PDB를 걸지 않는다. Job 컨트롤러가 새 Pod를 만든다.

컨트롤러가 없는 Pod나 scale 하위 리소스가 없는 오퍼레이터가 만든 Pod에는 제약이 더 있다. 쿠버네티스가 전체 개수를 알 수 없으니 정수 minAvailable만 쓸 수 있고 퍼센트와 maxUnavailable은 쓸 수 없다.

## drain이 끝나지 않는 설정

글 처음의 drain은 PDB를 이렇게 바꿔 두고 재현했다.

```bash
# replicas 3인데 minAvailable도 3. 한 개도 못 내린다는 뜻이다
kubectl patch pdb web-pdb --type merge -p '{"spec":{"minAvailable":3}}'
kubectl get pdb

# 20초 안에 못 끝내면 포기하게 한다. 없으면 끝없이 재시도한다
kubectl drain node-1 --ignore-daemonsets --timeout=20s
```

```bash
kubectl get pdb -A -o jsonpath='{range .items[?(@.status.disruptionsAllowed==0)]}{.metadata.namespace}/{.metadata.name}{"\t"}{.status.currentHealthy}/{.status.expectedPods}{"\n"}{end}'
```

<Callout kind="warning">
급하다고 `kubectl drain --disable-eviction`(eviction 대신 delete를 쓴다)이나 PDB 삭제로 밀어붙이면 그 순간 앱의 Pod가 한꺼번에 내려갈 수 있다. 쿼럼 저장소라면 쓰기가 멈춘다. 먼저 앱 담당자에게 replicas를 하나 늘려 달라고 하는 것(허용 수가 1이 된다)이 가장 안전하다. PDB를 지웠다면 작업 후 `kubectl apply -f`로 같은 매니페스트를 다시 만들고 `kubectl get pdb`로 ALLOWED DISRUPTIONS가 기대한 값인지 확인한다.
</Callout>

## 준비 안 된 Pod가 drain을 막을 때

다른 경우도 있다. 버그로 CrashLoopBackOff인 Pod, readiness가 계속 실패하는 Pod가 PDB 아래에 있으면 건강한 수가 이미 모자라 허용 수가 0이다. 기본 정책에서는 그 망가진 Pod조차 내보낼 수 없다. 이미 아픈 앱이 회복할 기회를 지켜 주려는 것인데, 노드를 비우려는 쪽에서는 고장 난 Pod 때문에 작업이 막히는 셈이다.

이걸 고르는 필드가 `spec.unhealthyPodEvictionPolicy`다. 1.26 알파, 1.27 베타를 거쳐 1.31에 GA가 됐다(기능 게이트 `PDBUnhealthyPodEvictionPolicy`는 1.33부터 사라졌다). 실습에서 Pod 3개 중 2개의 Ready 조건을 False로 바꾸고 준비 안 된 Pod를 eviction해 봤다.

```bash
# 기본값(IfHealthyBudget)에서 준비 안 된 Pod를 내보내 본다
kubectl create --raw /api/v1/namespaces/default/pods/web-7d9f9dc754-56rb5/eviction -f ev.json

# 정책을 바꾸고 다시 시도한다. 이어서 건강한 Pod도 시도한다
kubectl patch pdb web-pdb --type merge -p '{"spec":{"unhealthyPodEvictionPolicy":"AlwaysAllow"}}'
kubectl create --raw /api/v1/namespaces/default/pods/web-7d9f9dc754-56rb5/eviction -f ev.json
kubectl create --raw /api/v1/namespaces/default/pods/web-7d9f9dc754-8dwvv/eviction -f ev3.json  # 건강한 Pod
```

```text
Error from server (TooManyRequests): Cannot evict pod as it would violate the pod's disruption budget.

poddisruptionbudget.policy/web-pdb patched
{"kind":"Status","apiVersion":"v1","metadata":{},"status":"Success","code":201}
Error from server (TooManyRequests): Cannot evict pod as it would violate the pod's disruption budget.
```

`AlwaysAllow`에서는 Running이지만 Ready가 아닌 Pod를 언제든 내보낼 수 있다. 건강한 Pod(`8dwvv`)는 여전히 보호받는다. 망가진 Pod를 다른 노드로 옮겨 봤자 다시 망가질 가능성이 높으니 잃을 것이 없다. 운영 클러스터라면 앱 쪽 PDB에는 `AlwaysAllow`를 기본으로 두는 편이 노드 작업을 덜 막는다. 반대로 시작이 느려 Ready까지 오래 걸리는 저장소처럼 "아직 준비 중인" Pod를 지켜야 할 때는 기본값이 맞다. Pending, Succeeded, Failed Pod는 정책과 상관없이 늘 내보낼 수 있다.

## HPA와 함께 쓸 때 생기는 일

HPA가 붙은 앱에서 PDB를 정수 minAvailable로 걸면 replicas가 줄었을 때 문제가 된다. 낮에는 HPA가 10개까지 늘려 `minAvailable: 3`이 넉넉하지만, 새벽에 minReplicas 3으로 줄어들면 허용 수가 0이 된다. 노드 작업은 대개 새벽에 하니 정확히 그 시간에 막힌다. [HPA](/posts/k8s-hpa)의 minReplicas와 PDB를 함께 보고, 최소 replicas에서도 허용 수가 1 이상이 되게 맞춘다. `maxUnavailable: 1`이 가장 단순하다.

반대 방향도 기억해 둔다. HPA가 replicas를 줄이는 것은 eviction이 아니라 PDB를 지나치지 않는다. PDB는 오토스케일러를 "막는" 장치가 아니라 노드를 비우는 쪽의 속도를 정하는 장치다. 아래 그림은 노드 오토스케일러가 축소할 때 PDB가 끼어드는 지점이다.

## PDB를 걸기 전에 확인하는 것

새 서비스를 올릴 때 PDB를 함께 거는 순서를 적어 두면 이렇다.

1. replicas가 2 이상인지 본다. 1개짜리에 PDB를 걸면 노드 작업을 막거나(`minAvailable: 1`) 아무 의미가 없다(`maxUnavailable: 1`).
2. PDB 셀렉터가 Deployment의 `spec.selector`와 정확히 같은지 본다. 걸어 둔 뒤 `kubectl get pdb`에서 ALLOWED DISRUPTIONS가 0이 아니고 `expectedPods`가 replicas와 같은지 확인한다.
3. HPA가 있다면 minReplicas일 때도 허용 수가 1 이상인지 계산한다.
4. Pod들이 한 노드에 몰려 있지 않은지 본다. 3개가 한 노드에 있으면 그 노드를 비울 때 PDB가 하나씩만 허락하니 drain이 느리고, 노드가 갑자기 죽으면 PDB와 상관없이 셋이 함께 사라진다. 분산은 topologySpreadConstraints가 맡는다([스케줄링](/posts/k8s-pod-scheduling)).
5. 같은 Pod를 고르는 PDB가 둘 이상이 아닌지 본다.
6. `unhealthyPodEvictionPolicy: AlwaysAllow`를 쓸지 정한다.

drain 자체의 순서(cordon, DaemonSet, emptyDir, 되돌리기)는 [노드 점검과 drain](/posts/k8s-node-maintenance)에서 이어서 본다.

## 숫자 하나로 맺는 약속

PDB는 "이 앱은 지금 몇 개까지 내려가도 되는가"를 숫자 하나로 적어 둔 약속이고, eviction API를 쓰는 쪽만 그 약속을 읽는다. 허용 수는 건강한 Pod 수에서 남아야 할 수를 뺀 값이고, 퍼센트는 올림한다. 이 숫자가 0에 붙어 있으면 노드 교체, 업그레이드, 축소가 전부 멈춘다. 그래서 PDB는 maxUnavailable처럼 replicas를 따라가는 형태로, 최소 replicas에서도 1 이상이 남게 건다.

## 면접에서 나올 만한 질문

### PodDisruptionBudget은 무엇을 막고 무엇을 못 막나요?

eviction API를 거치는 자발적 중단만 막는다. kubectl drain, 노드 오토스케일러의 축소, VPA updater의 재생성이 여기에 해당한다. 노드 장애나 커널 OOM, kubelet의 노드 압박 eviction 같은 비자발적 중단은 못 막고, `kubectl delete pod`나 Deployment 롤링 업데이트, HPA의 축소도 eviction이 아니라서 PDB를 보지 않는다.

### eviction이 거부되면 왜 403이 아니라 429인가요?

권한이나 요청 형식의 문제가 아니라 "지금은 안 되니 나중에 다시"라는 뜻이기 때문이다. 새 Pod가 Ready가 되면 허용 수가 다시 생기므로 재시도하면 통과할 수 있다. 그래서 kubectl drain은 5초마다 재시도하고, 오토스케일러들도 429를 일시적인 실패로 다룬다. 같은 Pod를 PDB 두 개가 고르는 경우는 재시도해도 안 되는 오류라서 500이 돌아온다.

### ALLOWED DISRUPTIONS는 어떻게 계산되나요?

Ready인 Pod 수(currentHealthy)에서 남아야 할 수(desiredHealthy)를 뺀 값이다. desiredHealthy는 minAvailable이면 그 값, maxUnavailable이면 소유 컨트롤러의 replicas에서 그 값을 뺀 값이고, 퍼센트는 올림한다. 그래서 7개에 maxUnavailable 30%는 2.1을 올려 3개까지 허락한다. eviction이 허락되는 순간 API 서버가 이 값을 먼저 깎아 동시 요청이 같은 허용 수를 나눠 쓰지 못하게 한다.

### minAvailable과 maxUnavailable 중 무엇을 쓰나요?

상태 없는 서비스에는 replicas가 바뀌어도 의미가 유지되는 maxUnavailable을 쓴다. 정수 minAvailable은 HPA가 replicas를 줄였을 때 허용 수를 0으로 만들어 노드 작업을 막기 쉽다. 쿼럼이 있는 저장소처럼 살아 있어야 하는 절대 수가 정해진 경우에는 minAvailable이 의도를 더 정확히 표현한다. 컨트롤러가 없는 Pod에는 정수 minAvailable만 쓸 수 있다.

### drain이 끝나지 않으면 어디서부터 보나요?

`kubectl get pdb -A`에서 ALLOWED DISRUPTIONS가 0인 PDB를 찾고, 그 PDB가 고르는 Pod가 drain 중인 노드에 있는지 본다. minAvailable이 replicas와 같은 설정인지, Pod가 Ready가 아니라서 건강한 수가 모자란지, PDB가 겹쳤는지를 차례로 확인한다. 해결은 replicas를 늘리거나 PDB를 고치는 쪽이 먼저이고, PDB를 우회하는 것은 앱이 한꺼번에 내려가도 되는지 확인한 뒤에 한다.

### unhealthyPodEvictionPolicy는 왜 생겼나요?

CrashLoopBackOff처럼 이미 망가진 Pod가 PDB 아래에 있으면 건강한 수가 모자라 그 Pod조차 내보낼 수 없어 drain이 막혔기 때문이다. 기본값 IfHealthyBudget은 앱이 이미 PDB 기준 아래로 떨어졌으면 준비 안 된 Pod도 보호하고, AlwaysAllow는 Running이지만 Ready가 아닌 Pod를 언제든 내보낸다. 1.31에 GA가 됐고, 노드 작업이 많은 클러스터에서는 AlwaysAllow가 덜 막힌다.

### PDB가 있으면 롤링 업데이트 중 가용성도 보장되나요?

아니다. Deployment 컨트롤러가 옛 ReplicaSet을 줄이는 것은 eviction이 아니어서 PDB를 보지 않는다. 배포 중에 동시에 내려가는 수는 Deployment의 maxUnavailable과 maxSurge가 정한다. 다만 배포 중에 drain이 겹치면 PDB가 준비 안 된 새 Pod를 세지 않으므로 drain 쪽이 더 오래 기다린다.
