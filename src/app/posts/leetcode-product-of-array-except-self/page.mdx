[Product of Array Except Self](https://leetcode.com/problems/product-of-array-except-self/)는 LeetCode 238번 Medium 문제다. 겉으로는 곱셈 문제인데, 실제로는 "왼쪽에서 쌓은 정보와 오른쪽에서 쌓은 정보를 한 칸에서 만나게 하기"라는 생각을 연습하는 문제다. 이 생각은 [Trapping Rain Water](/posts/leetcode-trapping-rain-water)나 [Candy](/posts/leetcode-candy)처럼 양쪽 방향을 다 봐야 하는 문제에서 계속 다시 나온다.

이 문제는 [LeetCode 공부 가이드](/posts/leetcode-study-guide#한-문제를-푸는-여섯-단계)에서 "한 문제를 푸는 여섯 단계"의 예시로 한 번 짧게 지나갔다. 거기서는 단계를 보여 주는 데 집중했다면, 이 글은 풀이를 다섯 가지로 늘어놓고 나눗셈이 왜 막혔는지, 0이 몇 개냐에 따라 무엇이 달라지는지, 공간을 어디까지 줄일 수 있는지를 끝까지 따라간다. 예시도 가이드와 다른 배열을 쓴다. 코드는 모두 Node.js 22, Python 3.13, Java 21에서 직접 돌린 결과다.

## 나를 뺀 나머지 전부의 곱

정수 배열 `nums`가 주어진다. 같은 길이의 배열 `answer`를 만들어 돌려주는데, `answer[i]`는 `nums[i]`만 빼고 나머지 칸을 전부 곱한 값이다. 문제가 붙인 조건 중 풀이에 영향을 주는 것만 추리면 이렇다.

- 배열 길이는 2 이상 10^5 이하다. 칸마다 나머지를 다 곱하는 O(n²)는 10^10번이라 시간 안에 못 끝낸다.
- 값은 -30 이상 30 이하다. 0과 음수가 들어올 수 있다.
- 어떤 앞부분의 곱, 어떤 뒷부분의 곱도 32비트 정수 안에 들어간다고 보장한다. 이 보장이 뒤에서 Java 풀이를 안심하고 쓰게 해 준다.
- 나눗셈을 쓰지 말고 O(n) 시간에 풀어야 한다.
- 덧붙인 과제로 "결과 배열을 빼고 추가 공간 O(1)"에 풀 수 있는지 묻는다.

나눗셈 금지가 이 문제의 전부라고 해도 과장이 아니다. 나눗셈을 쓸 수 있다면 전체 곱을 한 번 구해 칸마다 나누면 끝이다. 그 길이 왜 막혔고, 막힌 길을 어떻게 돌아가는지가 이 글의 줄거리다.

## 손으로 한 칸씩 곱해 보기

글 끝까지 쓸 예시 하나를 정한다.

```text
인덱스   0   1   2   3
nums     3   2   5   4
```

0번 칸의 답은 0번을 뺀 2 × 5 × 4 = 40이다. 1번 칸은 3 × 5 × 4 = 60, 2번 칸은 3 × 2 × 4 = 24, 3번 칸은 3 × 2 × 5 = 30이다. 답은 `[40, 60, 24, 30]`이다.

2번 칸을 다시 보자. 2번을 빼면 남는 칸이 왼쪽의 3, 2와 오른쪽의 4로 갈린다. 그러니 답은 "2번 왼쪽 전부의 곱" 6과 "2번 오른쪽 전부의 곱" 4를 곱한 24다. 어떤 칸이든 똑같다. 자기 자리를 기준으로 배열이 왼쪽 덩어리와 오른쪽 덩어리로 나뉘고, 답은 두 덩어리 곱의 곱이다.

```text
칸 i      왼쪽 곱    오른쪽 곱    답
  0         1          40         40
  1         3          20         60
  2         6           4         24
  3        30           1         30
```

맨 왼쪽 칸은 왼쪽에 아무것도 없다. 이때 왼쪽 곱을 1로 둔다. 곱셈에서 1은 아무것도 곱하지 않은 것과 같기 때문이다. 오른쪽 끝도 같다. 이 표가 뒤의 모든 빠른 풀이의 설계도다. 왼쪽 곱 열을 보면 3, 6, 30으로 한 칸 내려갈 때마다 바로 윗줄 값에 `nums` 한 칸을 곱한 값이다. 이미 구한 값을 다시 쓸 수 있다는 뜻이다.

## 칸마다 나머지를 다 곱하는 풀이

가장 먼저 떠오르는 방법이다. 칸 `i`마다 배열 전체를 돌며 `j !== i`인 칸을 곱한다.

```js
function productExceptSelf(nums) {
  const n = nums.length, ans = [];
  for (let i = 0; i < n; i++) {
    let p = 1;
    // 자기 자리만 건너뛰고 나머지를 전부 곱한다
    for (let j = 0; j < n; j++) if (j !== i) p *= nums[j];
    ans.push(p);
  }
  return ans;
}

console.log(productExceptSelf([3, 2, 5, 4]));
```

```text
[ 40, 60, 24, 30 ]
```

시간은 O(n²)다. 칸이 n개고 칸마다 n-1번 곱한다. 공간은 결과 배열 말고는 변수 몇 개라 O(1)이다. 길이 10^4짜리 배열로 재 보니 227ms가 걸렸다. 10^5면 100배인 20초 남짓이다.

느린 이유는 표에서 이미 봤다. 1번 칸을 계산할 때 곱한 5 × 4를, 0번 칸에서도 2번 칸에서도 또 곱한다. 칸마다 거의 같은 곱셈을 처음부터 다시 한다. 겹치는 곱셈을 한 번만 하는 방법은 두 가지다. 전부 한 번 곱해 두고 빼거나(나눗셈), 쪼개서 쌓아 가거나(누적 곱).

## 전체 곱을 나누면 안 되나

문제가 막기 전에 누구나 떠올리는 풀이다. 전체 곱 120을 구하고 칸마다 자기 값으로 나눈다. 120 / 3 = 40, 120 / 2 = 60. 깔끔하다.

```js
function productExceptSelf(nums) {
  const total = nums.reduce((a, b) => a * b, 1);
  return nums.map((x) => total / x);
}

console.log(productExceptSelf([3, 2, 5, 4]));
console.log(productExceptSelf([3, 0, 5, 4]));
console.log(productExceptSelf([0, 2, 0]));
```

```text
[ 40, 60, 24, 30 ]
[ 0, NaN, 0, 0 ]
[ NaN, 0, NaN ]
```

0이 들어오는 순간 무너진다. `[3, 0, 5, 4]`의 1번 칸 답은 3 × 5 × 4 = 60인데, 전체 곱이 이미 0이라 0 / 0 = `NaN`이 나온다. 전체 곱에 0이 섞이면 "0이 아닌 칸들의 곱"이라는 정보가 사라지고, 나눗셈으로는 되살릴 수 없다.

0의 개수로 나눠 생각하면 고칠 수 있다.

- 0이 두 개 이상이면 어느 칸을 빼도 0이 하나는 남는다. 답은 전부 0이다.
- 0이 하나면 그 0을 뺀 칸만 "0이 아닌 값들의 곱"을 갖고, 나머지 칸은 0이다.
- 0이 없으면 전체 곱을 칸마다 나눈다.

```js
function productExceptSelf(nums) {
  let zeros = 0, prod = 1, zeroAt = -1;
  for (let i = 0; i < nums.length; i++) {
    if (nums[i] === 0) { zeros++; zeroAt = i; } // 0은 곱하지 않고 개수와 자리만 센다
    else prod *= nums[i];                       // 0이 아닌 값들의 곱
  }
  const ans = new Array(nums.length).fill(0);
  if (zeros > 1) return ans;                    // 0이 둘 이상: 전부 0
  if (zeros === 1) { ans[zeroAt] = prod; return ans; } // 0의 자리만 살아남는다
  for (let i = 0; i < nums.length; i++) ans[i] = prod / nums[i];
  return ans;
}

console.log(productExceptSelf([3, 0, 5, 4]));
console.log(productExceptSelf([0, 2, 0]));
```

```text
[ 0, 60, 0, 0 ]
[ 0, 0, 0 ]
```

시간 O(n), 추가 공간 O(1)이다. 정수끼리의 나눗셈이지만 `prod`는 항상 `nums[i]`의 배수라서 나머지가 생기지 않는다. 무작위 배열 2,000개로 브루트포스와 결과가 같은 것도 확인했다.

그럼에도 문제는 이 풀이를 막는다. 면접에서 이 풀이를 꺼내면 대개 "나눗셈 없이요"가 바로 돌아온다. 이유를 짐작해 보면 실무적인 쪽이 있다. 곱셈은 되지만 나눗셈이 없거나 비싼 연산이 꽤 있다. 소수가 아닌 수로 나머지 연산을 하면 역원이 없어 나눌 수 없고, 행렬 곱은 역행렬이 없을 수 있다. 나눗셈 없이 푸는 법을 알면 이런 경우에도 같은 틀을 그대로 쓴다. 이 풀이의 한계는 나눗셈 자체에 기대고 있다는 점이고, 그래서 다음 풀이로 간다.

## 왼쪽 곱과 오른쪽 곱으로 쪼개기

앞의 표를 코드로 옮긴다. `prefix[i]`는 `i` 왼쪽 전부의 곱, `suffix[i]`는 `i` 오른쪽 전부의 곱이다. 이렇게 앞에서부터 쌓아 가는 값을 누적 곱이라고 부른다. 누적 합(prefix sum)을 곱셈으로 바꾼 것이다.

- `prefix[0] = 1`이고, `prefix[i] = prefix[i - 1] * nums[i - 1]`이다. 바로 왼쪽 칸까지의 곱에 바로 왼쪽 칸 값을 곱한다.
- `suffix[n - 1] = 1`이고, `suffix[i] = suffix[i + 1] * nums[i + 1]`이다.
- 답은 `prefix[i] * suffix[i]`다.

```js
function productExceptSelf(nums) {
  const n = nums.length;
  const prefix = new Array(n).fill(1); // prefix[i] = nums[0..i-1]의 곱
  const suffix = new Array(n).fill(1); // suffix[i] = nums[i+1..n-1]의 곱
  for (let i = 1; i < n; i++) prefix[i] = prefix[i - 1] * nums[i - 1];
  for (let i = n - 2; i >= 0; i--) suffix[i] = suffix[i + 1] * nums[i + 1];

  const ans = [];
  for (let i = 0; i < n; i++) ans.push(prefix[i] * suffix[i]);
  return ans;
}

console.log(productExceptSelf([3, 2, 5, 4]));
```

```text
[ 40, 60, 24, 30 ]
```

중간에 찍어 보면 `prefix`는 `[1, 3, 6, 30]`, `suffix`는 `[40, 20, 4, 1]`이다. 손으로 만든 표의 두 열과 정확히 같다. 아래 그림에서 다음을 누르면 두 배열이 차례로 채워지고 마지막에 칸끼리 곱해진다.

시간은 세 번 훑으니 O(3n) = O(n)이다. 공간은 `prefix`와 `suffix` 두 배열로 O(n)이다. 나눗셈이 없으니 0이 있어도 따로 처리할 게 없다. `[3, 0, 5, 4]`면 0번 칸 오른쪽 곱에 0이 끼어 0이 되고, 1번 칸은 왼쪽 3과 오른쪽 20을 곱해 60이 된다. 0이 낀 덩어리만 0이 되고, 0을 빼낸 칸은 멀쩡하다.

이 풀이는 정답이고 면접에서도 충분히 통과한다. 남은 질문은 덧붙인 과제다. 배열을 세 개(`prefix`, `suffix`, `ans`)나 쓰는데, 줄일 수 있을까.

## 답 배열에 왼쪽 곱부터 채운다

두 관찰로 배열 두 개를 없앤다.

첫째, `prefix`를 따로 둘 필요가 없다. 어차피 `ans`도 길이 n이니 `ans`에 왼쪽 곱을 바로 적는다. 문제는 결과 배열을 추가 공간으로 세지 않으니, 여기에 무엇을 적든 공짜다.

둘째, `suffix`는 배열일 필요가 없다. 뒤에서부터 훑으며 `suffix[i]`를 쓰는 순간은 딱 한 번이고, 그 직후 `suffix[i - 1]`로 넘어간다. 지난 값을 다시 볼 일이 없으니 변수 하나 `right`에 들고 가면 된다. 같은 논리로 왼쪽 곱도 변수 `left` 하나로 쌓는다.

```js
function productExceptSelf(nums) {
  const n = nums.length;
  const ans = new Array(n).fill(1);

  // 1) 앞에서 뒤로: ans[i]에 i 왼쪽 전부의 곱을 적는다
  let left = 1;
  for (let i = 0; i < n; i++) {
    ans[i] = left;    // 먼저 적고
    left *= nums[i];  // 그다음 자기 값을 곱해 다음 칸으로 넘긴다
  }

  // 2) 뒤에서 앞으로: i 오른쪽 전부의 곱을 ans[i]에 곱한다
  let right = 1;
  for (let i = n - 1; i >= 0; i--) {
    ans[i] *= right;
    right *= nums[i];
  }
  return ans;
}

console.log(productExceptSelf([3, 2, 5, 4]));
console.log(productExceptSelf([3, 0, 5, 4]));
```

```text
[ 40, 60, 24, 30 ]
[ 0, 60, 0, 0 ]
```

반복문 안의 두 줄 순서가 이 풀이의 급소다. `ans[i] = left`가 먼저, `left *= nums[i]`가 나중이다. 적는 순간 `left`에는 `i` 왼쪽 칸들만 곱해져 있고, 자기 값은 다음 칸을 위해 곱한다. 순서를 바꾸면 자기 자신까지 곱해 버린다. 뒤의 "0과 음수에서 틀리는 코드" 절에서 실제로 틀린 출력을 본다.

시간은 두 번 훑으니 O(n)이다. 추가 공간은 `left`와 `right` 두 변수라 O(1)이다. 결과 배열은 어차피 돌려줘야 하는 것이라 세지 않는다. 면접관이 "그럼 결과 배열까지 세면요?"라고 물으면 O(n)이라고 답하고, 출력 자체가 n칸이라 그보다 줄일 수는 없다고 덧붙이면 된다.

마지막 칸을 지난 뒤 `left`는 120, 즉 전체 곱이 된다. 이 값은 쓰지 않는다. 그래서 Java에서 전체 곱이 `int`를 넘어도 답에는 영향이 없다. 이 이야기는 Java 절에서 다시 본다.

## 양 끝에서 동시에 채우는 한 번 훑기

두 번 훑는 반복문을 하나로 합칠 수도 있다. `i`를 앞에서 뒤로 보내는 동안 `j = n - 1 - i`를 뒤에서 앞으로 보낸다. `ans`를 1로 채워 두고, 앞쪽 손은 왼쪽 곱을, 뒤쪽 손은 오른쪽 곱을 각자 곱해 넣는다.

```js
function productExceptSelf(nums) {
  const n = nums.length;
  const ans = new Array(n).fill(1); // 곱해 넣을 거라 1로 시작한다
  let left = 1, right = 1;
  for (let i = 0; i < n; i++) {
    const j = n - 1 - i;            // 뒤에서 오는 손
    ans[i] *= left;  left *= nums[i];
    ans[j] *= right; right *= nums[j];
  }
  return ans;
}

console.log(productExceptSelf([3, 2, 5, 4]));
```

```text
[ 40, 60, 24, 30 ]
```

두 손이 가운데서 엇갈리고 나면 각 칸은 앞쪽 손에게 한 번, 뒤쪽 손에게 한 번 곱해진 상태가 된다. 곱셈은 순서를 바꿔도 결과가 같으니 어느 쪽이 먼저 왔는지는 상관없다. 그래서 앞 풀이처럼 "먼저 왼쪽을 다 채운다"는 순서가 필요 없다. 대신 `ans`를 반드시 1로 채워 두고 `=`가 아니라 `*=`로 넣어야 한다. 앞 풀이에서 `ans[i] = left`로 쓰던 습관대로 여기서도 `=`를 쓰면, 먼저 들어간 쪽 곱을 나중 쪽이 덮어쓴다.

복잡도는 앞 풀이와 같다. 반복문이 하나라 짧아 보이지만 반복 한 번에 일을 두 배 하니 연산 수는 같다. 실제로 잰 값도 길이 10^5에서 1.49ms와 1.53ms로 차이가 없었다. 이 풀이의 쓸모는 속도가 아니라 "양쪽 누적을 한 반복문 안에서 대칭으로 굴릴 수 있다"는 감각이다. 면접에서는 두 번 훑기를 기본 답으로 하고, 한 번 훑기는 "이렇게도 된다" 정도로 꺼내는 편이 설명하기 쉽다.

## Python과 Java로 옮기기

기본 답인 "답 배열에 왼쪽 곱부터 채우는" 풀이를 두 언어로 옮겼다.

```python
from typing import List

class Solution:
    def productExceptSelf(self, nums: List[int]) -> List[int]:
        n = len(nums)
        ans = [1] * n
        left = 1
        for i in range(n):          # 왼쪽 곱을 먼저 채운다
            ans[i] = left
            left *= nums[i]
        right = 1
        for i in range(n - 1, -1, -1):  # 오른쪽 곱을 곱해 넣는다
            ans[i] *= right
            right *= nums[i]
        return ans

s = Solution()
print(s.productExceptSelf([3, 2, 5, 4]), s.productExceptSelf([3, 0, 5, 4]), s.productExceptSelf([0, 0, -1]))
```

```text
[40, 60, 24, 30] [0, 60, 0, 0] [0, 0, 0]
```

Python 정수는 크기 제한이 없어서 곱이 아무리 커져도 넘치지 않는다. 뒤로 도는 반복문을 `range(n - 1, -1, -1)`로 쓰는 게 처음엔 헷갈린다. 끝값 -1은 포함되지 않으니 0까지 돈다. `reversed(range(n))`로 써도 같다.

```java
import java.util.*;

class Solution {
    public int[] productExceptSelf(int[] nums) {
        int n = nums.length;
        int[] ans = new int[n];
        int left = 1;
        for (int i = 0; i < n; i++) {      // ans[i] = i 왼쪽 전부의 곱
            ans[i] = left;
            left *= nums[i];
        }
        int right = 1;
        for (int i = n - 1; i >= 0; i--) { // i 오른쪽 전부의 곱을 곱한다
            ans[i] *= right;
            right *= nums[i];
        }
        return ans;
    }

    public static void main(String[] args) {
        Solution s = new Solution();
        System.out.println(Arrays.toString(s.productExceptSelf(new int[] { 3, 2, 5, 4 })));
        System.out.println(Arrays.toString(s.productExceptSelf(new int[] { 3, 0, 5, 4 })));
        System.out.println(Arrays.toString(s.productExceptSelf(new int[] { 0, 0, -1 })));
    }
}
```

```text
[40, 60, 24, 30]
[0, 60, 0, 0]
[0, 0, 0]
```

Java의 `new int[n]`은 0으로 채워진다. 그래서 첫 반복문이 `ans[i] = left`로 덮어쓰는 지금 구조는 괜찮지만, 앞의 "양 끝에서 동시에" 풀이처럼 `*=`로 시작하는 구조라면 `Arrays.fill(ans, 1)`을 먼저 해야 한다. 안 하면 전부 0이 나온다.

정수 범위는 문제의 보장 덕에 안전하다. 어떤 앞부분, 어떤 뒷부분의 곱도 32비트에 들어간다고 했으니 `left`와 `right`가 실제로 쓰이는 동안은 넘치지 않는다. 마지막 반복에서 `left *= nums[n - 1]`로 만들어지는 전체 곱은 넘칠 수도 있지만 그 값은 쓰지 않는다. Java의 `int` 곱셈은 넘치면 예외 없이 값이 돌아 버리니(wrap-around), 이 보장이 없는 변형 문제에서는 `long`이 필요하다.

## 0과 음수에서 틀리는 코드

### 적는 순서를 바꾸면 자기 자신까지 곱한다

```js
function wrongOrder(nums) {
  const n = nums.length, ans = new Array(n).fill(1);
  let left = 1;
  for (let i = 0; i < n; i++) { left *= nums[i]; ans[i] = left; } // 곱하고 나서 적는다
  let right = 1;
  for (let i = n - 1; i >= 0; i--) { right *= nums[i]; ans[i] *= right; }
  return ans;
}
console.log(wrongOrder([3, 2, 5, 4]));
```

```text
[ 360, 240, 600, 480 ]
```

0번 칸이 360 = 40 × 3 × 3이다. 왼쪽에서 한 번, 오른쪽에서 한 번, 자기 값 3이 두 번 더 곱해졌다. 다른 칸도 정답에 자기 값의 제곱이 곱해져 있다. 누적 값은 "적고 나서 곱한다"가 규칙이다. 누적 합에서 `prefix[i]`가 `i`를 포함하느냐 마느냐로 헷갈리는 것과 같은 종류의 실수다.

### 0을 그냥 나누면 NaN이 나온다

위에서 본 대로 전체 곱을 나누는 풀이는 0이 하나만 있어도 0 / 0 = `NaN`이 나온다. 나눗셈 풀이를 쓰려면 0의 개수를 세는 분기 세 개가 꼭 필요하다. 0이 하나일 때 "0의 자리만 0이 아닌 값들의 곱"이라는 부분을 빠뜨리기 가장 쉽다.

### JavaScript의 -0

`[0, 0, -1]`을 기본 답 함수에 넣고 `console.log`로 찍으면 `[ -0, -0, 0 ]`이 나온다. 0에 음수를 곱하면 JavaScript는 -0을 만든다. 값으로는 `-0 === 0`이 `true`이고 `JSON.stringify`도 `0`으로 적어서 채점에는 문제가 없다. 다만 `Object.is(x, 0)`으로 비교하는 테스트를 직접 짜면 틀린다고 나온다. Java와 Python의 정수에는 -0이 없다.

### 로그로 나눗셈을 피하면

"곱을 로그의 합으로 바꾸면 빼기로 되지 않나"라는 생각도 나온다. `exp(전체 로그 합 - log x)`다. 실제로 돌리면 이렇게 된다.

```text
[3, 2, 5, 4]  →  [ 40, 59.999999999999986, 23.999999999999993, 29.99999999999999 ]
[-2, 3]       →  [ NaN, NaN ]
```

부동소수점 오차로 정수가 안 나오고, 음수와 0은 로그를 취할 수 없어 `NaN`이 된다. 부호와 0을 따로 세고 반올림까지 붙이면 맞출 수는 있지만, 결국 나눗셈을 우회하려고 더 복잡한 나눗셈을 만든 셈이다.

### 길이 2

`[-2, 3]`이면 답은 `[3, -2]`다. 서로 상대의 값이 답이다. 반복문 경계가 하나 어긋나면 이 크기에서 바로 드러나니 테스트에 꼭 넣는다.

## 조건이 바뀌면

### 나눗셈은 되는데 나머지 연산을 하라면

"답을 어떤 수로 나눈 나머지로 돌려달라"는 변형이 있다. 나누는 수가 소수이고 0이 없으면 모듈러 역원으로 나눗셈 풀이를 살릴 수 있다. 그런데 나누는 수가 소수가 아니면 역원이 없을 수 있다. LeetCode 2906. Construct Product Matrix가 바로 이 경우로, 2차원 격자를 한 줄로 펼친 뒤 12345로 나눈 나머지를 구한다. 12345는 3 × 5 × 823이라 역원이 없는 값이 생긴다. 이때 왼쪽 곱과 오른쪽 곱 풀이는 곱셈만 쓰니 그대로 통한다. 나눗셈을 안 쓰는 풀이를 익혀 두는 이유가 여기 있다.

### 구간의 곱을 여러 번 묻는다면

"`l`부터 `r`까지의 곱"을 여러 번 물으면 누적 곱 배열 하나로 `prefix[r + 1] / prefix[l]`처럼 답하고 싶어진다. 0이 끼면 또 무너진다. LeetCode 1352. Product of the Last K Numbers는 수가 하나씩 들어오고 "마지막 k개의 곱"을 묻는데, 0이 들어오면 누적 곱 배열을 비우고 새로 시작하는 방법으로 푼다. 값이 바뀌기도 한다면 나눗셈 없이 구간 곱을 log n에 답하는 [세그먼트 트리](/posts/segment-tree-fenwick)로 간다. 곱셈도 결합법칙이 성립하니 덧셈 대신 곱셈을 넣으면 된다.

### 곱 말고 합이라면

"나를 뺀 나머지의 합"은 전체 합에서 자기 값을 빼면 끝이다. 덧셈의 역연산인 뺄셈은 언제나 되기 때문이다. 곱셈만 어려운 이유는 0이 정보를 지워 역연산이 깨지기 때문이라는 걸 이 대비로 설명하면 면접관이 원하는 핵심을 짚은 셈이다.

### 왼쪽과 오른쪽을 따로 쌓는 다른 문제

같은 틀을 쓰는 문제가 꽤 많다. [Trapping Rain Water](/posts/leetcode-trapping-rain-water)는 칸마다 "왼쪽 최댓값"과 "오른쪽 최댓값"을 쌓고 작은 쪽으로 물 높이를 정한다. [Candy](/posts/leetcode-candy)는 왼쪽에서 한 번, 오른쪽에서 한 번 훑어 두 조건을 모두 만족하는 사탕 수를 정한다. LeetCode 724. Find Pivot Index는 왼쪽 합과 오른쪽 합이 같은 칸을 찾는다. 곱의 부호와 0 때문에 앞뒤 정보를 함께 들고 가야 하는 [Maximum Product Subarray](/posts/leetcode-maximum-product-subarray)도 이 문제 다음에 보면 좋다. 같은 배열·해시 묶음의 기본 문제는 [Two Sum](/posts/leetcode-two-sum), [Contains Duplicate](/posts/leetcode-contains-duplicate), [Top K Frequent Elements](/posts/leetcode-top-k-frequent-elements)에 있다.

## 면접에서 나올 만한 질문

### 나눗셈 없이 어떻게 O(n)에 푸나요?

각 칸의 답을 "그 칸 왼쪽 전부의 곱 × 오른쪽 전부의 곱"으로 쪼갠다. 왼쪽 곱은 앞에서부터, 오른쪽 곱은 뒤에서부터 한 칸씩 누적하면 이전 값을 다시 쓸 수 있어서 각각 한 번 훑기로 끝난다. 두 번 훑으니 O(n)이다.

### 나눗셈을 쓰면 무엇이 문제인가요?

0이 있으면 전체 곱이 0이 되어 0이 아닌 값들의 곱이라는 정보가 사라지고, 0 / 0이 생긴다. 0의 개수가 0, 1, 2 이상인 세 경우로 나누면 고칠 수는 있다. 하지만 나머지 연산처럼 역원이 없는 환경에서는 나눗셈 자체가 불가능해서, 곱셈만 쓰는 풀이가 더 넓게 통한다.

### 추가 공간을 O(1)로 만들 수 있나요?

결과 배열을 세지 않는다면 된다. 결과 배열에 왼쪽 곱을 먼저 적고, 오른쪽 곱은 배열 없이 변수 하나로 들고 가며 곱해 넣는다. 오른쪽 곱은 뒤에서 앞으로 훑을 때 한 번만 쓰고 버리기 때문에 변수 하나로 충분하다. 결과 배열까지 세면 출력 크기 때문에 O(n)보다 줄일 수 없다.

### 0이 두 개 이상이면 답은 어떻게 되나요?

모든 칸이 0이다. 어떤 칸을 빼도 다른 0이 하나 남기 때문이다. 왼쪽·오른쪽 곱 풀이는 이 경우를 따로 처리하지 않아도 자연스럽게 모든 칸이 0이 된다. 0이 하나면 그 0의 자리만 0이 아닌 값들의 곱이 되고 나머지는 0이다.

### Java로 풀 때 오버플로는 괜찮나요?

이 문제는 어떤 앞부분, 뒷부분의 곱도 32비트에 들어간다고 보장해서 `int`로 충분하다. 마지막에 만들어지는 전체 곱은 넘칠 수 있지만 그 값은 답에 쓰이지 않는다. Java `int`는 넘치면 조용히 값이 돌아 버리니, 보장이 없는 변형에서는 `long`을 쓰거나 나머지 연산을 섞어야 한다.

### 이 풀이가 틀리기 쉬운 지점은 어디인가요?

누적 값을 적는 순서다. `ans[i] = left`를 먼저 하고 `left *= nums[i]`를 나중에 해야 i 왼쪽만 곱한 값이 들어간다. 순서를 바꾸면 자기 값이 두 번 더 곱해져 `[3, 2, 5, 4]`에서 `[360, 240, 600, 480]`이 나온다. 한 반복문으로 양 끝을 함께 채운다면 `ans`를 1로 채우고 `*=`로 넣어야 한다.

### 비슷한 생각을 쓰는 다른 문제는요?

양쪽에서 정보를 쌓아 한 칸에서 만나게 하는 문제들이다. Trapping Rain Water는 왼쪽 최댓값과 오른쪽 최댓값을, Candy는 왼쪽 조건과 오른쪽 조건을 따로 훑어 합친다. 누적 합으로 보면 Find Pivot Index도 같은 모양이고, 값이 바뀌는 구간 곱이라면 세그먼트 트리로 넘어간다.
