<EasyIntro>
  프로그램 안에서는 TypeScript가 값의 모양을 꼼꼼히 검사해 준다. 그런데 그 검사는 프로그램을 만들 때만 일어나고, 실제로 돌아갈 때는 사라진다. 서버가 이름 칸에 빈 값을 보내도 프로그램은 그걸 모르고 받아서 쓰다가 멈춘다.

  공항 출입국 심사대를 떠올리면 쉽다. 나라 안에서는 서로 믿고 다니지만, 바깥에서 들어오는 사람은 입구에서 여권을 한 번 확인한다. 확인을 통과한 사람만 안으로 들어오니, 안에서는 다시 물어볼 필요가 없다.

  프로그램에도 이런 입구가 있다. 서버에서 받은 답, 사용자가 입력한 값, 주소창의 값, 설정 값이 그렇다. 이 글은 입구에서 값을 확인하는 도구인 zod를 써서, 확인 규칙 하나로 타입까지 만들고, 틀린 값이 왔을 때 어떻게 할지 정하는 법을 살펴본다.

사용자 프로필을 받아 이름을 대문자로 보여 주는 코드가 있다. 타입도 붙였고 `tsc --strict`도 통과한다.

```ts
interface User { id: number; name: string }
const body = '{"id":7,"name":null}'; // 서버가 이름이 비어 있는 사용자를 보냈다
const user = JSON.parse(body) as User;
console.log(user.name.toUpperCase());
```

```text
TypeError: Cannot read properties of null (reading 'toUpperCase')
```

`name`이 `string`이라고 적었지만 실제로 온 값은 `null`이었다. 검사기는 `as User`라는 말을 믿었을 뿐 값을 본 적이 없다. 서버 팀이 탈퇴한 사용자의 이름을 `null`로 바꾸기로 한 날, 이 화면은 하얗게 멈춘다.

[타입 시스템 기초 글](/posts/ts-type-system-basics)에서 본 대로 타입은 컴파일이 끝나면 지워진다. 그 글은 경계에서 값을 확인해야 한다는 데서 멈췄다. 이 글은 그다음, "어떻게 확인할까"에 답한다. 스키마 라이브러리 zod로 검증 규칙과 타입을 한 번에 만들고, `parse`와 `safeParse`, 값을 바꾸는 `coerce`와 `transform`, 필드 사이 규칙인 `refine`, 신뢰 경계가 어디인지, 검증에 실패하면 무엇을 할지, valibot과의 번들 크기 차이와 Standard Schema까지 본다. 예제는 zod 4.6.7, valibot 1.5.0, TypeScript 5.9, Node 22로 돌렸다.

## 타입 단언은 검사가 아니라 약속이다

`as User`는 "이 값은 `User`라고 내가 보증한다"는 선언이다. 검사기는 그 보증을 받아들이고 넘어간다. 반대로 런타임 검증은 값을 실제로 열어 보고 모양이 맞을 때만 `User`를 돌려준다. 같은 응답이 두 길을 지날 때 무엇이 달라지는지 아래 그림에서 다음을 눌러 보자.

차이는 에러가 나는 위치다. 단언은 틀린 값을 앱 안까지 들여보내서, 그 값을 처음 쓰는 컴포넌트에서 터진다. 스택 트레이스는 `toUpperCase`를 가리키지만 원인은 몇 단계 위의 응답이다. 검증은 응답을 받은 자리에서 실패하고, 실패 메시지에 필드 경로(`name`)와 이유가 들어 있다. 원인과 증상이 같은 자리에 있으니 고치기 쉽다.

## 스키마 하나에서 타입을 뽑는다

손으로 검증 함수를 쓸 수도 있다. `typeof v.name === "string"`을 필드마다 확인하는 [타입 가드](/posts/ts-narrowing)다. 문제는 인터페이스와 가드가 따로 논다는 것이다. `User`에 필드를 추가하고 가드는 고치지 않아도 컴파일은 통과한다. 가드는 `value is User`라고 선언만 하면 검사기가 본문을 믿기 때문이다.

zod는 순서를 뒤집는다. 런타임에 쓰는 스키마를 먼저 쓰고, 타입은 거기서 뽑는다.

```ts
import { z } from "zod";

const User = z.object({
  id: z.number().int(),
  name: z.string(),
  email: z.email(),
  avatarUrl: z.url().nullable(),
});
export type User = z.infer<typeof User>;
// { id: number; name: string; email: string; avatarUrl: string | null }
```

스키마가 하나뿐이니 필드를 추가하면 검증과 타입이 함께 바뀐다. 어긋날 방법이 없다. `z.email()`, `z.url()`은 zod 4에서 최상위로 올라온 형식 검사다(3에서는 `z.string().email()`). 값과 타입에 같은 이름 `User`를 붙였는데, TypeScript는 값 자리와 타입 자리를 따로 찾아서 충돌하지 않는다.

`nullable()`은 `null`을 허용하고 `optional()`은 키가 없거나 `undefined`인 경우를 허용한다. JSON에는 `undefined`가 없으니, 서버가 빈 값을 `null`로 보내는지 키를 빼고 보내는지에 따라 골라야 한다. 처음 버그가 바로 이 지점이었다. 서버 계약을 모르면 `nullish()`(둘 다 허용)로 받고 화면에서 처리한다.

## parse는 던지고 safeParse는 돌려준다

검증하는 방법은 두 가지다. `parse`는 실패하면 `ZodError`를 던지고, `safeParse`는 결과 객체를 돌려준다.

```ts
const bad = { id: 7, name: null, email: "kim@example", avatarUrl: "x" };

try {
  User.parse(bad);
} catch (e) {
  if (e instanceof z.ZodError) console.log(z.prettifyError(e));
}
```

```text
✖ Invalid input: expected string, received null
  → at name
✖ Invalid email address
  → at email
✖ Invalid URL
  → at avatarUrl
```

첫 번째 문제에서 멈추지 않고 틀린 필드를 모두 모은다. 각 문제는 `e.issues` 배열의 원소이고, 원소마다 `code`, `path`, `message`가 있다. 실제 `name` 항목은 이렇다.

```text
{
  "expected": "string",
  "code": "invalid_type",
  "path": ["name"],
  "message": "Invalid input: expected string, received null"
}
```

`safeParse`는 `success`로 갈래가 나뉘는 [판별 유니온](/posts/ts-narrowing)을 돌려준다. `success`를 확인한 갈래에서만 `data`를 쓸 수 있다.

```ts
const r = z.object({ id: z.number(), name: z.string() }).safeParse({ id: 7, name: null });
if (r.success) {
  console.log(r.data.name.toUpperCase());
} else {
  console.log(r.error.issues[0].path, r.error.issues[0].message);
}
```

```text
[ 'name' ] Invalid input: expected string, received null
```

어느 쪽을 쓸지는 실패를 누가 처리하느냐로 정한다. 실패가 곧 버그라서 위로 던져 에러 경계나 에러 추적 도구가 받게 하고 싶으면 `parse`를 쓴다. API 응답을 받는 데이터 레이어가 보통 그렇다. 실패가 정상적인 흐름의 일부라서 그 자리에서 다른 화면을 보여 줘야 하면 `safeParse`를 쓴다. 사용자 입력, URL 파라미터, `localStorage`가 그렇다.

## 들어온 값을 바꾸는 coerce와 transform

검증 라이브러리는 확인만 하지 않고 값을 정리해서 돌려준다. URL 쿼리 문자열은 모든 값이 문자열이니, 숫자로 바꾸고 기본값을 채우는 일까지 스키마에 맡길 수 있다.

```ts
const Search = z.object({
  page: z.coerce.number().int().min(1).default(1),
  sort: z.enum(["new", "popular"]).catch("new"),
  tags: z.string().transform((s) => s.split(",").filter(Boolean)).optional(),
});

const params = Object.fromEntries(new URLSearchParams("page=3&sort=oops&tags=ts,react"));
console.log(Search.parse(params));
console.log(Search.parse({}));
console.log(Search.safeParse({ page: "abc" }).error?.issues[0].message);
```

```text
{ page: 3, sort: 'new', tags: [ 'ts', 'react' ] }
{ page: 1, sort: 'new' }
Invalid input: expected number, received NaN
```

`"3"`은 숫자 3이 됐고, 목록에 없는 `sort=oops`는 `catch`가 기본값 `new`로 바꿨다. `tags`는 쉼표로 잘린 배열이 됐다. 값이 `parse`를 지나며 어떤 순서로 바뀌는지 `page` 하나로 따라가 보자.

값이 바뀌니 스키마에는 타입이 두 개 생긴다. 들어가는 값의 타입과 나오는 값의 타입이다.

```ts
export type SearchIn = z.input<typeof Search>;
export type SearchOut = z.output<typeof Search>;
// 타입을 눈으로 보려고 일부러 틀린 값을 넣었다
export const i: SearchIn = 1;
export const o: SearchOut = 1;
```

```text
c.ts(8,14): error TS2559: Type '1' has no properties in common with type '{ page?: unknown; tags?: string | undefined; }'.
c.ts(9,14): error TS2322: Type 'number' is not assignable to type '{ page: number; tags?: string[] | undefined; }'.
```

출력을 짧게 하려고 `sort`를 뺀 스키마로 확인했다. 들어갈 때 `page`는 아무 값(`unknown`)이나 없어도 되고 `tags`는 문자열이다. 나올 때 `page`는 반드시 있는 숫자이고 `tags`는 배열이다. `z.infer`는 `z.output`과 같다. 폼 라이브러리에 스키마를 넘길 때 입력 타입과 출력 타입을 헷갈리면 "필드 값은 문자열인데 타입은 숫자"인 어긋남이 생긴다. React Hook Form처럼 둘을 따로 받는 API가 있는 이유다. 폼에서의 쓰임은 [폼 글](/posts/react-forms-actions)에 정리했다.

`coerce`는 편하지만 자바스크립트의 형 변환을 그대로 쓴다는 점을 기억해야 한다.

```ts
console.log(z.coerce.number().parse(""), z.coerce.number().parse(null), z.coerce.boolean().parse("false"));
```

```text
0 0 true
```

빈 칸과 `null`이 0이 되고, 문자열 `"false"`가 `true`가 된다. `Boolean("false")`가 `true`이기 때문이다. 환경 변수 `DEBUG=false`를 `z.coerce.boolean()`으로 읽으면 디버그 모드가 켜진다. 문자열로 된 불리언은 `"true"`, `"1"`, `"yes"` 같은 값을 정해진 규칙으로 읽는 `z.stringbool()`을 쓴다. 빈 칸 처리는 `preprocess`로 먼저 `undefined`로 바꾼다.

## 필드 사이의 규칙은 refine으로

"비밀번호 확인이 비밀번호와 같아야 한다"처럼 필드 하나로는 판단할 수 없는 규칙은 객체 단계에서 `refine`으로 건다.

```ts
const Signup = z.object({ pw: z.string().min(8), pw2: z.string() })
  .refine((v) => v.pw === v.pw2, { message: "비밀번호가 다르다", path: ["pw2"] });

const s = Signup.safeParse({ pw: "12345678", pw2: "1234567" });
console.log(z.flattenError(s.error!));
```

```text
{ formErrors: [], fieldErrors: { pw2: [ '비밀번호가 다르다' ] } }
```

`path`를 주지 않으면 에러가 객체 전체(`formErrors`)에 붙어서 어느 입력 칸 아래에 보여 줄지 알 수 없다. 폼에서 쓰는 `refine`에는 거의 항상 `path`를 준다.

`refine` 안에서 서버에 묻는 비동기 검사(아이디 중복 확인)도 할 수 있다. 그때는 `parse` 대신 `parseAsync`를 써야 한다.

```text
$ZodAsyncError Encountered Promise during synchronous parse. Use .parseAsync() instead.
```

동기 `parse`가 Promise를 만나면 이렇게 던진다. 다만 중복 확인 같은 네트워크 검사는 키를 누를 때마다 돌면 요청이 쏟아지니, 스키마에 넣기보다 제출할 때 서버가 확인하는 편이 낫다.

## 신뢰 경계는 어디인가

모든 함수 입구에서 검증할 필요는 없다. 검증은 값이 타입 검사기 밖에서 들어오는 자리, 즉 신뢰 경계에서 한 번만 한다. 안쪽 코드는 그 값을 믿고 타입으로만 다룬다. 프런트엔드에서 경계는 대략 이렇다.

API 응답이 가장 크다. 백엔드가 같은 팀이어도 배포 시점이 다르고, 필드는 조용히 `null`이 되거나 이름이 바뀐다. 데이터 패칭 함수 하나에서 검증하면 화면 전체가 보호된다. TanStack Query를 쓴다면 `queryFn` 안에서 `parse`한다. 실패가 쿼리의 에러 상태가 되어 기존 에러 처리 흐름을 그대로 탄다.

```ts
// features/profile/api/profile/index.ts 같은 자리
export async function fetchProfile(id: number): Promise<User> {
  const { data } = await httpClient.get<unknown>(`/users/${id}`);
  return User.parse(data); // 실패하면 queryFn이 던지고, 쿼리는 error 상태가 된다
}
```

`get<unknown>`으로 받는 데 주목한다. `get<User>`로 받으면 axios가 단언을 대신 해 준 셈이 되어 검증을 빼먹어도 컴파일이 통과한다. `unknown`으로 받으면 검증하지 않고는 쓸 수 없다.

URL 파라미터와 `localStorage`도 경계다. 사용자가 주소를 손으로 고치고, 예전 배포가 다른 모양으로 저장한 값이 남아 있다. 이쪽은 실패가 흔하니 `safeParse`나 `catch`로 기본값에 떨어뜨린다. [브라우저 저장소](/posts/browser-storage)에서 꺼낸 값을 `JSON.parse` 결과 그대로 쓰는 코드가 배포 후 첫 방문에서만 터지는 버그를 만든다.

환경 변수는 서버가 뜰 때 한 번 검증한다.

```ts
const Env = z.object({
  DATABASE_URL: z.url(),
  PORT: z.coerce.number().int().default(3000),
  DEBUG: z.stringbool().default(false),
});

const r = Env.safeParse({ PORT: "abc" });
if (!r.success) console.log(z.prettifyError(r.error));
```

```text
✖ Invalid input: expected string, received undefined
  → at DATABASE_URL
✖ Invalid input: expected number, received NaN
  → at PORT
```

실제로는 `Env.parse(process.env)`를 앱이 시작하는 곳에서 부르고, 실패하면 바로 프로세스를 끝낸다. 설정이 틀린 서버가 뜬 뒤 첫 요청에서 터지는 것보다, 배포 단계에서 뜨지 못하는 편이 훨씬 빨리 발견된다. Next.js라면 브라우저로 나가는 `NEXT_PUBLIC_` 값은 빌드할 때 문자열로 박히니, 빌드 단계에서 검증해야 의미가 있다.

서버 쪽에서는 요청 본문, 쿼리, 웹훅, 메시지 큐에서 꺼낸 메시지가 경계다. 서버의 요청 검증과 모르는 키를 버리는 동작은 [Express 미들웨어 글](/posts/express-middleware)에서 다뤘다. 그 글에서 본 대로 `z.object`는 모르는 키를 기본으로 버린다. 다른 동작이 필요하면 `z.strictObject`(모르는 키가 있으면 실패)와 `z.looseObject`(모르는 키를 그대로 둠)를 쓴다.

```text
[ { code: 'unrecognized_keys', keys: [ 'role' ], path: [], message: 'Unrecognized key: "role"' } ]
```

`strictObject`가 `role`을 거절한 결과다. 응답 검증에는 `strictObject`를 쓰지 않는다. 서버가 필드를 하나 추가하는 건 하위 호환되는 변경인데, 그것만으로 화면이 깨지기 때문이다.

## 검증에 실패하면 무엇을 할까

검증을 넣고 나면 새 질문이 생긴다. 서버가 주문 상태에 `"refunded"`를 추가했다. 클라이언트 스키마는 `paid`와 `shipped`만 안다.

```ts
const Order = z.object({ id: z.number(), status: z.enum(["paid", "shipped"]) });
const rows = [{ id: 1, status: "paid" }, { id: 2, status: "refunded" }, { id: 3, status: "shipped" }];
const all = z.array(Order).safeParse(rows);
console.log(all.success, all.error?.issues.map((i) => i.path.join(".") + " " + i.message));
```

```text
false [ '1.status Invalid option: expected one of "paid"|"shipped"' ]
```

주문 하나의 상태가 낯설다는 이유로 목록 전체가 실패했다. 검증이 없을 때는 그 한 줄만 이상하게 보였을 텐데, 이제는 주문 목록 화면이 통째로 에러가 된다. 엄격함이 장애를 키운 것이다. 고를 수 있는 방법이 몇 가지 있다.

```ts
// 1. 원소마다 따로 검증하고 실패한 것만 뺀다
const ok = rows.flatMap((r) => { const p = Order.safeParse(r); return p.success ? [p.data] : []; });
// 2. 모르는 값은 "unknown"으로 받아 화면에서 따로 그린다
const Lenient = Order.extend({
  status: z.enum(["paid", "shipped"]).or(z.literal("unknown")).catch("unknown"),
});
```

```text
[ 1, 3 ]
[ 'paid', 'unknown', 'shipped' ]
```

무엇이 맞는지는 필드가 얼마나 중요하냐에 달렸다. 결제 금액이나 권한처럼 틀리면 위험한 값은 실패시키고 에러를 보여 준다. 표시용 상태나 부가 정보는 대체 값으로 받아 화면을 살린다. 어느 쪽이든 실패를 조용히 삼키지 않는다. `safeParse`가 실패하면 issues를 [에러 추적 도구](/posts/frontend-error-tracking)로 보내서, 서버 계약이 바뀐 사실을 사용자 문의보다 먼저 안다. 검증 실패 로그는 API 계약이 깨졌다는 가장 이른 신호다.

## 번들 크기와 속도: zod, zod/mini, valibot

브라우저에서 검증하면 라이브러리가 번들에 실린다. 같은 스키마(필드 셋, 이메일 형식 하나)를 세 가지로 써서 esbuild로 최소화하고 크기를 재 봤다.

```bash
# 각 파일을 최소화해 번들하고 원래 크기와 gzip 크기를 본다
for f in sz-zod sz-mini sz-vb; do
  npx esbuild $f.ts --bundle --minify --format=esm --outfile=out/$f.js --log-level=error
  printf "%s raw=%s gz=%s\n" $f $(wc -c < out/$f.js) $(gzip -9c out/$f.js | wc -c)
done
```

```text
sz-zod raw=453999 gz=92401
sz-mini raw=13976 gz=4925
sz-vb raw=3449 gz=1396
```

차이가 크다. `import { z } from "zod"`는 메서드 체인 방식이라 쓰지 않는 메서드도 객체에 붙어 있고, 이 버전에서는 여러 언어의 에러 메시지와 JSON Schema 변환 코드까지 함께 실렸다. `zod/mini`는 같은 기능을 함수로 나눠(`z.string().check(z.minLength(8))` 같은 모양) 쓰는 것만 번들에 남긴다. valibot은 처음부터 함수 조합 방식(`v.pipe(v.string(), v.email())`)으로 설계돼서 가장 작다. 숫자는 버전과 스키마에 따라 크게 달라지니 자기 프로젝트에서 직접 재 봐야 한다. 위 명령을 그대로 쓰면 된다.

속도는 반대 방향이다. 사용자 만 명짜리 배열(JSON으로 457KB)을 검증하는 데 걸린 시간을 이 기계에서 쟀다.

```text
JSON.parse 7.23 ms
zod parse 1.12 ms
valibot parse 6.62 ms
```

zod 4는 객체 스키마를 처음 쓸 때 `new Function`으로 검사 코드를 만들어 두고 그걸 돌려서 빠르다. 이 방식을 끈 `jitless` 설정에서는 zod도 6ms 안팎이었다. 어느 쪽이든 `JSON.parse`와 같은 자릿수라서, 화면 하나 분량의 응답을 검증하는 비용은 거의 문제가 되지 않는다. 수만 줄 목록을 자주 받는 화면이라면 그때 재고 고른다.

`new Function`에는 보안 쪽 함정이 있다. [CSP](/posts/web-security-headers)에서 `unsafe-eval`을 막은 사이트에서는 그 시도가 막히고, zod는 느린 경로로 돌아간다. 동작은 하지만 CSP 위반 보고가 남을 수 있다. 엄격한 CSP를 쓰는 곳에서는 `z.config({ jitless: true })`로 처음부터 시도하지 않게 한다.

고르는 기준을 정리하면 이렇다. 서버나 번들 크기가 덜 중요한 관리 화면이라면 문서와 생태계가 가장 넓은 zod. 같은 zod 스키마 감각으로 크기를 줄이고 싶으면 `zod/mini`. 번들 크기가 성능 예산을 압박하는 공개 페이지라면 valibot. 그리고 서버와 클라이언트가 같은 스키마 파일을 import하면 규칙이 한 곳에 모인다.

## Standard Schema로 라이브러리를 갈아 끼운다

폼 라이브러리, 라우터, RPC 라이브러리가 각자 zod, valibot, ArkType용 어댑터를 따로 만들던 문제를 풀려고 이 라이브러리 작성자들이 함께 만든 인터페이스가 Standard Schema다. 스키마 객체에 `~standard`라는 속성을 두고, 그 안의 `validate` 함수가 정해진 모양으로 결과를 돌려준다.

```ts
const a = z.object({ n: z.number() });
const b = v.object({ n: v.number() });
console.log(Object.keys(a["~standard"]), a["~standard"].vendor);
console.log(Object.keys(b["~standard"]), b["~standard"].vendor);
console.log(JSON.stringify(a["~standard"].validate({ n: "1" })));
```

```text
[ 'validate', 'vendor', 'version', 'jsonSchema' ] zod
[ 'version', 'vendor', 'validate' ] valibot
{"issues":[{"expected":"number","code":"invalid_type","path":["n"],"message":"Invalid input: expected number, received string"}]}
```

실패하면 `issues` 배열, 성공하면 `value`를 담은 객체가 나온다. 이 인터페이스를 받는 라이브러리(TanStack Form, tRPC 등)는 어떤 검증 라이브러리의 스키마든 그대로 받는다. 직접 데이터 레이어를 만든다면 `validate` 하나에만 의존하게 짜 두면, 나중에 zod를 valibot으로 바꿔도 호출하는 쪽은 그대로다. 이름 앞의 `~`는 자동 완성 목록 맨 뒤로 밀려나게 하려고 붙인 것이다.

## 어디까지 검증할까

검증은 공짜가 아니다. 스키마를 쓰고 유지하는 시간, 번들 크기, 엄격함이 키운 장애가 비용이다. 판단 기준은 몇 가지로 좁혀진다.

값이 우리 코드 밖에서 왔는가. 같은 프로세스 안의 함수끼리 주고받는 값은 타입으로 충분하다. 네트워크, 저장소, 사용자, 다른 팀의 서비스에서 왔으면 검증한다.

틀리면 무엇이 깨지는가. 돈, 권한, 삭제처럼 틀린 값이 사고로 이어지는 필드는 엄격하게, 표시용 필드는 관대하게 받는다. 응답 전체를 엄격하게 검사할 필요는 없고, 화면이 실제로 쓰는 필드만 스키마에 적어도 된다. 모르는 키는 기본으로 버려지니 그만큼 스키마가 짧아진다.

계약이 이미 다른 방법으로 보장되는가. OpenAPI 명세에서 타입과 클라이언트를 생성하고 서버도 같은 명세로 응답을 검증한다면, 클라이언트 검증은 중요한 화면에만 두어도 된다. [명세 우선 개발](/posts/openapi-spec-first)에서 그 흐름을 다뤘다. 생성된 타입도 결국 "서버가 이렇게 보낼 것"이라는 약속이라, 배포 시점이 엇갈리는 동안에는 깨질 수 있다는 점은 같다.

## 직접 해 보기: 작은 스키마 검사기

zod가 하는 일의 핵심은 스키마와 값을 나란히 내려가며, 어긋난 자리를 경로와 함께 모으는 것이다. 그 부분을 직접 만들어 보자. 스키마는 `"string"`, `"number"`, `"boolean"` 같은 문자열이거나, `type`이 `object`(`shape`), `array`(`item`), `nullable`(`inner`)인 객체다. 틀린 곳마다 `"경로: expected 기대, received 실제"`를 모은다. 경로는 점으로 잇고, 최상위는 `(root)`다. 실제 종류는 `null`이면 `null`, 배열이면 `array`, 나머지는 `typeof`로 쓴다.

  const issues = [];
  const kindOf = (v) => (v === null ? "null" : Array.isArray(v) ? "array" : typeof v);
  const walk = (s, v, path) => {
    const where = path.length ? path.join(".") : "(root)";
    if (typeof s === "string") {
      if (kindOf(v) !== s) issues.push(where + ": expected " + s + ", received " + kindOf(v));
      return;
    }
    if (s.type === "nullable") {
      if (v !== null) walk(s.inner, v, path);
      return;

    if (s.type === "object") {
      if (kindOf(v) !== "object") { issues.push(where + ": expected object, received " + kindOf(v)); return; }
      for (const key of Object.keys(s.shape)) walk(s.shape[key], v[key], [...path, key]);
    }
  };
  walk(schema, value, []);
  return issues;
}`}

## 타입은 약속, 검증은 확인

타입 검사는 우리 코드끼리의 약속을 지키게 해 줄 뿐, 바깥에서 들어오는 값은 보지 못한다. `as`는 그 약속을 대신 해 주는 말이라 값이 바뀌면 같이 틀린다. 신뢰 경계에서 스키마로 한 번 확인하면 틀린 값은 원인 자리에서 멈추고, 통과한 값은 안쪽에서 타입만으로 다룬다. zod는 스키마에서 타입을 뽑아 둘이 어긋나지 않게 하고, `coerce`와 `transform`은 값을 정리하며, 실패한 경로를 모두 알려 준다. 남는 판단은 얼마나 엄격할지다. 위험한 필드는 엄격하게, 나머지는 관대하게 받되 실패는 반드시 기록한다. 선언 파일이 라이브러리에 붙이는 약속은 [선언 파일 글](/posts/ts-declaration-files-modules)에서, 허용 값 목록을 유니온으로 만드는 법은 [enum 글](/posts/ts-enum-vs-union)에서 볼 수 있다.

## 면접에서 나올 만한 질문

### TypeScript를 쓰는데 왜 런타임 검증이 필요한가

타입은 컴파일할 때만 검사되고 실행 코드에서는 지워지기 때문이다. API 응답, 사용자 입력, 저장소 값처럼 프로그램 밖에서 들어오는 값은 검사기가 본 적이 없고, `as`나 `any`로 받으면 틀린 값이 그대로 들어와 쓰는 자리에서 터진다. 경계에서 값을 실제로 확인해야 틀린 값을 원인 자리에서 멈출 수 있다.

### 타입 단언(as)과 스키마 검증은 무엇이 다른가

단언은 "이 값은 이 타입이다"라는 개발자의 보증이고 런타임 코드가 전혀 없다. 스키마 검증은 값을 열어 보고 맞을 때만 그 타입을 돌려주며, 틀리면 어느 필드가 왜 틀렸는지 알려 준다. 단언은 응답이 바뀌면 같이 틀리고, 검증은 바뀐 사실을 경계에서 드러낸다.

### z.infer로 타입을 뽑는 방식의 장점은

검증 규칙과 타입이 같은 스키마 하나에서 나오니 둘이 어긋날 수 없다. 인터페이스와 손으로 쓴 타입 가드를 따로 두면 필드를 추가하고 가드를 고치지 않아도 컴파일이 통과하는데, 스키마에서 타입을 뽑으면 필드 추가가 곧 검증 추가다. `transform`이 있으면 입력과 출력 타입이 다르고, `z.infer`는 출력 타입이다.

### parse와 safeParse는 언제 각각 쓰나

`parse`는 실패하면 `ZodError`를 던지고, `safeParse`는 `success`로 갈리는 결과 객체를 돌려준다. 실패가 버그라서 에러 경계나 쿼리 에러 상태로 올리고 싶으면 `parse`, 실패가 흔하고 그 자리에서 기본값이나 다른 화면으로 처리해야 하면 `safeParse`를 쓴다. API 데이터 레이어는 보통 `parse`, URL 파라미터나 `localStorage`는 `safeParse`가 맞는다.

### z.coerce를 쓸 때 주의할 점은

자바스크립트의 형 변환을 그대로 쓰기 때문에 빈 문자열과 `null`이 0이 되고, 문자열 `"false"`가 `true`가 된다. 빈 칸이 "입력 안 함"이 아니라 0으로 들어가거나, 환경 변수 `DEBUG=false`가 켜짐으로 읽히는 버그가 생긴다. 빈 값은 `preprocess`로 먼저 `undefined`로 바꾸고, 문자열 불리언은 `z.stringbool()`을 쓴다.

### 신뢰 경계는 어디이고, 모든 함수에서 검증해야 하나

값이 타입 검사기 밖에서 들어오는 자리다. 프런트엔드는 API 응답, 폼 입력, URL 파라미터, `localStorage`, `postMessage`, 서버는 요청 본문, 환경 변수, 웹훅, 큐 메시지가 그렇다. 경계에서 한 번 검증하면 안쪽은 타입만으로 다루면 되니 모든 함수에서 검증할 필요는 없다.

### 서버가 enum 값을 하나 추가했더니 목록 화면 전체가 깨졌다. 어떻게 설계해야 하나

배열 스키마는 원소 하나만 틀려도 전체가 실패해서, 엄격한 검증이 작은 계약 변경을 큰 장애로 키운 경우다. 원소마다 `safeParse`해서 실패한 것만 빼거나, 모르는 값을 `catch`로 `"unknown"` 같은 대체 값으로 받아 화면에서 따로 그린다. 돈이나 권한처럼 위험한 필드는 엄격하게 두고, 어느 경우든 실패 issues를 에러 추적 도구로 보내 계약 변경을 빨리 알아챈다.

### zod와 valibot은 어떻게 고르나

zod는 메서드 체인 방식이라 쓰기 편하고 생태계가 넓지만, 쓰지 않는 기능까지 번들에 실려 크다. valibot과 `zod/mini`는 기능을 함수로 나눠 쓰는 것만 남기니 훨씬 작다. 직접 재 보니 같은 스키마에서 gzip 기준 zod 약 92KB, `zod/mini` 약 5KB, valibot 약 1.4KB였고, 속도는 셋 다 `JSON.parse`와 같은 자릿수였다. 번들 예산이 빠듯한 공개 페이지는 valibot이나 `zod/mini`, 나머지는 팀이 익숙한 쪽을 고르고, Standard Schema를 받는 라이브러리라면 나중에 바꾸기도 쉽다.
