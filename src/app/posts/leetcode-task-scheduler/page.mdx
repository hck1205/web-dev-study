[Task Scheduler](https://leetcode.com/problems/task-scheduler/)는 LeetCode 621번이다. CPU가 처리할 작업 목록이 있고, 같은 종류의 작업 사이에는 정해진 시간만큼 간격을 둬야 한다. 모든 작업을 끝내는 최소 시간을 구한다.

이 문제가 재미있는 건 풀이의 성격이 크게 둘로 갈린다는 점이다. 하나는 매 시각 무엇을 할지 실제로 정해 나가는 시뮬레이션이고, 여기서 최대 힙(가장 큰 값을 맨 위에 두는 자료구조)이 쓰인다. 다른 하나는 답의 모양을 먼저 꿰뚫어 보고 식 하나로 계산하는 방법이다. 이 글은 시뮬레이션 두 가지, 식 두 가지를 차례로 보고, 그럴듯하지만 틀리는 탐욕도 하나 본다. 탐욕 선택이 왜 맞는지 따지는 법은 [그리디 알고리즘 글](/posts/greedy-algorithms)에, 힙 자체는 [힙 글](/posts/ds-heap)에 있다. 코드는 Node.js 22, Python 3.13, Java 21에서 돌렸다.

## 같은 작업 사이에 n칸을 띄운다

작업 목록 `tasks`가 주어진다. 각 작업은 대문자 하나(A부터 Z)다. 한 단위 시간에 작업 하나를 하거나 쉰다. 같은 작업 두 개 사이에는 적어도 n 단위 시간이 있어야 한다. 순서는 마음대로 바꿔도 된다. 모든 작업을 끝내는 최소 시간을 돌려준다.

풀이를 고르는 데 영향을 주는 제약은 이렇다.

- 작업 수는 최대 10^4이고, n은 0 이상 100 이하다.
- 작업 종류는 최대 26가지다. 종류마다 개수만 알면 되고, 이 26이라는 작은 숫자 덕분에 힙 연산이 사실상 상수 시간이다.
- 답은 작업 수보다 클 수 있다. 쉬는 칸까지 센다. 모두 A이고 n = 100이면 답이 100만이 넘는다.

"적어도 n칸"이라는 말을 정확히 읽어야 한다. n = 2면 A를 시각 0에 했을 때 다음 A는 시각 3부터 할 수 있다. 같은 작업이 n + 1칸마다 한 번씩 올 수 있다는 뜻이다. 이 n + 1이 뒤의 모든 식에 나온다.

## 손으로 줄을 세워 본다

이 글에서 처음 쓰는 예시다.

```text
tasks = A A A B B C,  n = 2
```

A가 세 개로 가장 많다. A를 먼저 하고, A를 다시 할 수 있을 때까지 두 칸을 다른 작업으로 채운다.

```text
시각  0  1  2  3  4  5     6
작업  A  B  C  A  B  쉼    A
```

시각 5에는 남은 작업이 A뿐인데 A는 시각 6부터 할 수 있어서 쉰다. 답은 7이다. 6칸으로 줄일 수는 없다. A 세 개만 해도 첫 A와 마지막 A 사이가 최소 2 × 3 = 6칸이라, A만으로 이미 7칸이 필요하다.

손으로 풀 때 내가 쓴 규칙은 "지금 할 수 있는 것 중 가장 많이 남은 것을 한다"였다. 가장 많은 작업이 끝까지 남으면 마지막에 그것만 남아 쉬는 칸이 생기기 때문이다. 이 규칙이 첫 풀이가 된다.

## 매 시각 가장 많이 남은 작업을 고른다

시각을 하나씩 늘리며, 26종류를 모두 훑어 "쿨다운이 끝났고 남은 개수가 가장 많은 작업"을 고른다. 고를 게 없으면 쉰다. 쿨다운은 작업마다 "다시 할 수 있는 시각"을 적어 두면 된다.

```js
function leastInterval(tasks, n) {
  const cnt = new Array(26).fill(0);            // cnt[c] = 남은 개수
  for (const t of tasks) cnt[t.charCodeAt(0) - 65]++;
  const ready = new Array(26).fill(0);          // ready[c] = 이 시각부터 다시 할 수 있다
  let left = tasks.length, time = 0;
  while (left > 0) {
    let best = -1;
    for (let c = 0; c < 26; c++) {
      if (cnt[c] > 0 && ready[c] <= time && (best < 0 || cnt[c] > cnt[best])) best = c;
    }
    if (best >= 0) {                            // 할 수 있는 것 중 가장 많이 남은 것
      cnt[best]--;
      ready[best] = time + n + 1;
      left--;
    }                                           // 없으면 이 칸은 쉰다
    time++;
  }
  return time;
}
```

예시에서 고른 순서를 찍어 보면 손으로 푼 것과 같다.

```text
A B C A B idle A
```

시간은 O(답 × 26)이다. 답은 작업 수보다 클 수 있다는 게 함정이다. 모두 A인 작업 1만 개에 n = 100이면 답이 (10000 - 1) × 101 + 1 = 1009900이고, 시각마다 26칸을 훑으니 2600만 번을 돈다. 실제로 재 보니 80ms가 걸렸다. 통과는 하지만, 쉬는 칸 하나하나를 시뮬레이션하는 게 낭비다. 공간은 26칸 배열 두 개라 O(1)이다.

## 최대 힙과 대기 줄로 쉬는 칸을 건너뛴다

두 가지를 고친다. 하나는 "가장 많이 남은 것 고르기"를 최대 힙으로 하는 것이다. 다른 하나는 쿨다운 중인 작업을 따로 대기 줄에 세워, 할 일이 없을 때는 시계를 대기 줄 맨 앞이 풀리는 시각으로 바로 건너뛰는 것이다.

대기 줄은 그냥 큐(먼저 들어온 것이 먼저 나가는 줄)면 된다. 작업이 쿨다운에 들어가는 시각이 1씩 늘어나니, 풀리는 시각도 들어온 순서대로 늘어나기 때문이다. 정렬된 순서가 저절로 지켜져서 힙을 하나 더 쓸 필요가 없다.

```js
class MaxHeap {                          // 남은 개수만 담는다. 큰 것이 위
  constructor() { this.a = []; }
  get size() { return this.a.length; }
  push(x) {
    const a = this.a;
    a.push(x);
    let i = a.length - 1;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (a[p] >= a[i]) break;
      [a[p], a[i]] = [a[i], a[p]];
      i = p;
    }
  }
  pop() {
    const a = this.a, top = a[0], last = a.pop();
    if (a.length) {
      a[0] = last;
      let i = 0;
      for (;;) {
        const l = 2 * i + 1, r = l + 1;
        let m = i;
        if (l < a.length && a[l] > a[m]) m = l;
        if (r < a.length && a[r] > a[m]) m = r;
        if (m === i) break;
        [a[m], a[i]] = [a[i], a[m]];
        i = m;
      }
    }
    return top;
  }
}

function leastInterval(tasks, n) {
  const cnt = new Map();
  for (const t of tasks) cnt.set(t, (cnt.get(t) ?? 0) + 1);
  const heap = new MaxHeap();
  for (const c of cnt.values()) heap.push(c);  // 어떤 작업인지는 상관없고 개수만 필요하다
  const wait = [];                              // [남은 개수, 다시 할 수 있는 시각]
  let head = 0, time = 0;
  while (heap.size > 0 || head < wait.length) {
    if (heap.size === 0) time = Math.max(time, wait[head][1]); // 할 게 없으면 시계를 건너뛴다
    if (head < wait.length && wait[head][1] <= time) heap.push(wait[head++][0]); // 풀린 작업을 돌려놓는다
    const c = heap.pop() - 1;                   // 가장 많이 남은 작업을 한 번 한다
    if (c > 0) wait.push([c, time + n + 1]);   // 남았으면 쿨다운에 들어간다
    time++;
  }
  return time;
}
```

힙에 작업 이름을 넣지 않고 개수만 넣은 게 눈여겨볼 점이다. 답은 시간뿐이라 어떤 작업을 했는지는 몰라도 된다. 대기 줄은 배열과 `head` 인덱스로 만들었다. `shift()`는 배열 앞을 지울 때마다 나머지를 당겨서 O(길이)이기 때문이다.

예시를 넣고 시각마다 상태를 찍어 봤다.

```text
t=0 run 3 -> 2 heap [2,1] wait []
t=1 run 2 -> 1 heap [1] wait [[2,3]]
t=2 run 1 -> 0 heap [] wait [[2,3],[1,4]]
t=3 run 2 -> 1 heap [] wait [[1,4]]
t=4 run 1 -> 0 heap [] wait [[1,6]]
t=6 run 1 -> 0 heap [] wait []
```

t=5 줄이 없다. 시각 5에 힙이 비어 있어서 시계가 대기 줄 맨 앞이 풀리는 6으로 건너뛰었기 때문이다. 그 한 칸이 쉬는 시간이다. 찍힌 숫자는 개수뿐이라, 아래 그림에서는 어떤 작업인지 이름을 붙여 따라간다.

이 풀이의 좋은 점은 실제 스케줄을 만들 수 있다는 것이다. 힙에 개수 대신 `[개수, 작업 이름]`을 넣으면 매 시각 무엇을 했는지 그대로 기록된다. 면접에서 "순서도 출력해 달라"는 꼬리 질문이 오면 이 코드로 대답한다. 한계는 힙과 큐를 직접 다뤄야 해서 코드가 길다는 것이다. 답이 시간 하나뿐이면 더 짧은 길이 있다.

## 가장 많은 작업으로 뼈대를 세운다

시뮬레이션 결과를 다시 보면 모양이 보인다. 가장 많이 나온 작업(A)이 뼈대를 만들고, 나머지는 그 사이를 채운다.

A가 maxF번 나온다고 하자. A끼리는 n칸씩 떨어져야 하니, A를 맨 앞에 두고 n + 1칸짜리 덩어리를 maxF - 1개 만든 뒤 마지막 A를 붙인다. 덩어리 하나는 "A 하나 + 빈칸 n개"다. 그러면 길이가 (maxF - 1) × (n + 1) + 1인 뼈대가 생긴다. 다른 작업을 빈칸에 채워 넣고, 못 채운 빈칸은 쉰다.

가장 많은 개수가 같은 작업이 여러 개면 마지막 덩어리 뒤에 그 수만큼 더 붙는다. 이 수를 numMax라 하면 뼈대 길이는 이렇다.

```text
(maxF - 1) × (n + 1) + numMax
```

새 예시로 그려 본다. `A A A B B B C`, n = 2다. A와 B가 모두 세 개라 maxF = 3, numMax = 2다. 뼈대 길이는 (3 - 1) × 3 + 2 = 8이다.

이게 답의 하한이라는 건 쉽다. A만 따져도 첫 A부터 마지막 A까지 (maxF - 1) × (n + 1)칸이 필요하고, 마지막 덩어리에는 가장 많은 작업이 모두 한 번씩 더 와야 한다. 어떤 순서로 놓아도 이보다 짧을 수 없다.

이 길이를 실제로 맞출 수 있다는 것도 보여야 한다. 작업을 개수가 많은 순서로 줄 세운 뒤, 마지막 줄까지 포함한 덩어리들을 첫 번째부터 위에서 아래로 한 칸씩 내려가며 채운다. 한 열을 다 채우면 다음 열로 간다. 같은 작업은 이웃한 덩어리에 차례로 들어가고 한 덩어리에 두 번 들어가지 않아서 간격이 지켜진다. 열이 넘어가는 경계까지 따지는 증명은 길어서, 나는 앞의 매 시각 시뮬레이션과 이 식을 무작위 입력 2만 개로 대조해 답이 모두 같은 것을 확인했다. 빈칸이 모자라 덩어리가 넘치면 어떻게 될까. 그때는 덩어리를 n + 1보다 길게 늘리면 된다. 덩어리가 길어지면 같은 작업 사이 간격이 더 벌어질 뿐이라 조건이 깨지지 않는다. 그리고 빈칸이 하나도 없으니 답은 작업 수 그 자체다.

그래서 답은 둘 중 큰 쪽이다.

```js
function leastInterval(tasks, n) {
  const cnt = new Array(26).fill(0);
  for (const t of tasks) cnt[t.charCodeAt(0) - 65]++;
  let maxF = 0, numMax = 0;
  for (const c of cnt) {
    if (c > maxF) { maxF = c; numMax = 1; }   // 더 큰 개수가 나오면 새로 센다
    else if (c === maxF) numMax++;            // 같은 개수면 하나 더
  }
  return Math.max(tasks.length, (maxF - 1) * (n + 1) + numMax);
}
```

세 예시를 넣어 본다.

```text
AAABBC     n=2  → maxF 3, numMax 1, 뼈대 7,  작업 6개  → 7
AAABBBC    n=2  → maxF 3, numMax 2, 뼈대 8,  작업 7개  → 8
AAABBBCCDD n=2  → maxF 3, numMax 2, 뼈대 8,  작업 10개 → 10
```

세 번째는 뼈대가 8칸인데 작업이 10개라 빈칸이 모자란다. 앞의 시뮬레이션으로 실제 순서를 뽑아 보면 `A B C A B D A B C D`로 쉬는 칸 없이 10에 끝난다. 덩어리가 4칸, 3칸, 3칸으로 늘어난 모양이다.

시간은 개수를 세는 O(T)이고, 그 뒤는 26칸만 본다. 공간은 O(1)이다. 1만 개에서 0.03~0.66ms로 가장 빠르다.

## 빈칸 수를 직접 센다

같은 생각을 다른 각도에서 쓴 식이다. 쉬는 칸의 수를 구해서 작업 수에 더한다.

뼈대에서 빈칸은 덩어리 maxF - 1개마다 n개씩, 모두 (maxF - 1) × n개다. 다른 작업은 개수만큼 빈칸을 채우는데, 한 작업이 채울 수 있는 빈칸은 덩어리 수인 maxF - 1개까지다. 그래서 개수가 maxF인 작업(가장 많은 작업과 동점)은 maxF - 1개만 빼고, 나머지는 개수만큼 뺀다. 마지막 줄에 붙는 한 개는 빈칸이 아니라 뼈대를 늘리는 쪽이라서다.

```js
function leastInterval(tasks, n) {
  const cnt = new Array(26).fill(0);
  for (const t of tasks) cnt[t.charCodeAt(0) - 65]++;
  cnt.sort((a, b) => b - a);                   // 가장 많은 작업이 맨 앞
  const maxF = cnt[0];
  let idle = (maxF - 1) * n;                   // 뼈대의 빈칸 수
  for (let i = 1; i < 26; i++) idle -= Math.min(cnt[i], maxF - 1);
  return tasks.length + Math.max(0, idle);     // 빈칸이 음수면 모자란 것이니 0
}
```

`AAABBBC`, n = 2면 빈칸이 2 × 2 = 4개다. B는 min(3, 2) = 2개를 채우고, C는 1개를 채워 빈칸이 1개 남는다. 7 + 1 = 8이다. 앞의 식과 답이 같다.

두 식은 같은 이야기라서 어느 쪽을 써도 된다. 나는 앞의 식이 외우기 쉽고, 이 식이 설명하기 쉽다고 느낀다. "쉬는 칸이 몇 개 생기는지 센다"는 말이 면접관에게 바로 전달되기 때문이다. 정렬은 26칸이라 상수 시간이다.

## 알파벳 순으로 고르면 틀린다

처음에 "쿨다운이 끝난 것 중 아무거나 하면 되지 않나"라고 생각하기 쉽다. 알파벳이 빠른 것을 고르도록 짜서 첫 풀이와 비교해 봤다. 무작위 입력 2만 개를 돌리니 금방 틀리는 입력이 나왔다.

```text
tasks = A B B B,  n = 1
알파벳 순:        A B idle B idle B   → 6
많이 남은 것 먼저: B A B idle B        → 5
```

알파벳 순은 A를 먼저 써 버려서 B 세 개 사이를 채울 작업이 없어졌다. 많이 남은 것을 먼저 하면 A가 B 사이의 빈칸 하나를 채운다. 가장 많이 남은 작업은 뼈대를 만드는 작업이라, 그걸 뒤로 미룰수록 끝에 쉬는 칸이 쌓인다. 탐욕 선택은 "무엇을 먼저 고르나"가 전부라, 기준 하나만 틀려도 답이 틀린다.

이런 반례는 손으로 찾기보다 맞다고 믿는 풀이와 의심 가는 풀이를 무작위 입력으로 대조하는 편이 빠르다. 위 반례도 작업 12개 이하, 종류 4개 이하의 작은 입력으로 돌려 찾았다. 입력이 작아야 반례가 짧게 나와 왜 틀렸는지 읽기 쉽다.

## 1만 개로 재 봤다

작업 1만 개를 두 종류로 만들었다. 모두 A인 입력과, 26종류가 고르게 섞인 무작위 입력이다. 다섯 번 돌린 가장 빠른 시간이고 괄호 안이 답이다.

```text
입력         n     매 시각 훑기          힙 + 대기 줄       뼈대 식           빈칸 세기
모두 A       2     1.69ms (29998)      1.11ms (29998)     0.51ms (29998)    0.53ms (29998)
모두 A       100   79.79ms (1009900)   0.35ms (1009900)   0.03ms (1009900)  0.03ms (1009900)
무작위 26    2     0.99ms (10000)      3.05ms (10000)     0.66ms (10000)    0.74ms (10000)
무작위 26    100   2.87ms (42825)      0.49ms (42825)     0.03ms (42825)    0.03ms (42825)
```

매 시각 훑기는 답이 클 때만 느려진다. 쉬는 칸까지 하나하나 도는 탓이다. 무작위 입력에 n = 2면 쉬는 칸이 없어 오히려 힙보다 빨랐다. 힙은 쉬는 칸을 건너뛰어 답의 크기와 상관없이 작업 수만큼만 돈다. 두 식은 개수를 세는 비용만 남아 가장 빠르다. 식이 n = 2 줄에서 0.5ms 정도로 나온 건 그 줄이 먼저 돌아 JIT 최적화 전의 실행이 섞였기 때문이다. 50번 돌린 최솟값으로 다시 재니 n과 상관없이 0.03ms였다.

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 매 시각 훑기 | O(답 × 26) | O(1) | 규칙을 처음 세울 때. 순서도 바로 나온다 |
| 최대 힙 + 대기 줄 | O(T log 26) | O(26) | 실제 스케줄이 필요하거나, 쿨다운이 작업마다 다를 때 |
| 뼈대 식 | O(T) | O(1) | 답이 시간 하나뿐일 때. 면접의 최종 답 |
| 빈칸 세기 | O(T) | O(1) | 뼈대 식과 같다. 쉬는 칸 수로 설명하고 싶을 때 |

## Python과 Java로 옮기기

최종 답인 뼈대 식과, 스케줄로 넓히기 좋은 힙 시뮬레이션을 옮긴다.

```python
import heapq
from collections import Counter, deque
from typing import List

class Solution:
    def leastInterval(self, tasks: List[str], n: int) -> int:
        cnt = Counter(tasks)
        max_f = max(cnt.values())
        num_max = sum(1 for c in cnt.values() if c == max_f)  # 가장 많은 개수를 가진 작업 수
        return max(len(tasks), (max_f - 1) * (n + 1) + num_max)

    def leastIntervalHeap(self, tasks: List[str], n: int) -> int:
        heap = [-c for c in Counter(tasks).values()]          # 음수로 넣어 최대 힙처럼 쓴다
        heapq.heapify(heap)
        wait = deque()                                        # (남은 개수, 다시 할 수 있는 시각)
        time = 0
        while heap or wait:
            if not heap:
                time = max(time, wait[0][1])                  # 할 게 없으면 시계를 건너뛴다
            if wait and wait[0][1] <= time:
                heapq.heappush(heap, -wait.popleft()[0])
            c = -heapq.heappop(heap) - 1
            if c > 0:
                wait.append((c, time + n + 1))
            time += 1
        return time

s = Solution()
for tasks, n in [("AAABBC", 2), ("AAABBBC", 2), ("AAABBBCCDD", 2), ("ABBB", 1), ("A", 5), ("AAAA", 0)]:
    print(tasks, n, s.leastInterval(list(tasks), n), s.leastIntervalHeap(list(tasks), n))
```

```text
AAABBC 2 7 7
AAABBBC 2 8 8
AAABBBCCDD 2 10 10
ABBB 1 5 5
A 5 1 1
AAAA 0 4 4
```

`heapq`는 최소 힙만 있어서 개수에 `-`를 붙여 넣고 꺼낼 때 다시 뒤집는다. 대기 줄은 `list.pop(0)`이 아니라 `collections.deque`의 `popleft()`를 쓴다. 리스트 앞에서 빼면 나머지를 당겨 O(길이)이고 `deque`는 O(1)이다. 힙이 빈 채로 `heappop`을 부르면 `IndexError`가 나므로, 시계를 건너뛰는 줄을 빼먹으면 바로 드러난다.

```java
import java.util.*;

class Solution {
    public int leastInterval(char[] tasks, int n) {
        int[] cnt = new int[26];
        for (char t : tasks) cnt[t - 'A']++;           // char끼리 빼면 0부터 25까지의 칸 번호
        int maxF = 0, numMax = 0;
        for (int c : cnt) {
            if (c > maxF) { maxF = c; numMax = 1; }
            else if (c == maxF) numMax++;
        }
        return Math.max(tasks.length, (maxF - 1) * (n + 1) + numMax);
    }

    public int leastIntervalHeap(char[] tasks, int n) {
        int[] cnt = new int[26];
        for (char t : tasks) cnt[t - 'A']++;
        PriorityQueue<Integer> heap = new PriorityQueue<>(Collections.reverseOrder()); // 최대 힙
        for (int c : cnt) if (c > 0) heap.offer(c);
        ArrayDeque<int[]> wait = new ArrayDeque<>();   // {남은 개수, 다시 할 수 있는 시각}
        int time = 0;
        while (!heap.isEmpty() || !wait.isEmpty()) {
            if (heap.isEmpty()) time = Math.max(time, wait.peekFirst()[1]);
            if (!wait.isEmpty() && wait.peekFirst()[1] <= time) heap.offer(wait.pollFirst()[0]);
            int c = heap.poll() - 1;
            if (c > 0) wait.offerLast(new int[] {c, time + n + 1});
            time++;
        }
        return time;
    }
}
```

```text
AAABBC 2 7 7
AAABBBC 2 8 8
AAABBBCCDD 2 10 10
ABBB 1 5 5
A 5 1 1
AAAA 0 4 4
```

`main`에서 Python과 같은 여섯 입력을 넣은 결과다.

Java의 `PriorityQueue`는 최소 힙이 기본이라 `Collections.reverseOrder()`로 뒤집었다. 답의 최댓값은 (10^4 - 1) × 101 + 1로 약 100만이라 `int`로 충분하다. 큐는 `LinkedList`보다 `ArrayDeque`가 빠르다. 노드 객체를 따로 만들지 않기 때문이다.

## 틀리기 쉬운 자리

### 작업 수와 비교하지 않는다

```js
return (maxF - 1) * (n + 1) + numMax;        // max가 빠졌다
```

`AAABBBCCDD`, n = 2에서 8이 나온다. 작업이 10개인데 8칸에 끝낼 수는 없다. 종류가 많아 빈칸이 모자라면 뼈대가 늘어나므로 작업 수와 비교해야 한다. n = 0일 때도 마찬가지로 답은 작업 수다.

### 가장 많은 작업이 여럿인 걸 놓친다

numMax 대신 1을 더하면 `AAABBBC`, n = 2에서 7이 나온다. 정답은 8이다. 마지막 덩어리에는 A 뒤에 B도 와야 한다. B를 앞 덩어리의 빈칸에 넣으면 B 세 개 중 하나가 갈 곳이 없다.

### n을 간격 칸 수가 아니라 주기로 읽는다

같은 작업이 n칸마다 온다고 읽으면 식에 n + 1 대신 n을 쓰게 된다. "같은 작업 사이에 n칸"이니 같은 작업은 n + 1칸마다 온다. `A A A`, n = 2면 `A _ _ A _ _ A`로 7이다. n을 쓰면 5가 나온다.

### 개수가 0인 칸이 numMax에 섞인다

26칸 배열을 앞에서부터 훑으며 numMax를 세면, A가 없는 입력에서는 첫 칸의 0이 `maxF = 0`과 같아서 numMax가 1 늘어난다. 그래도 답은 맞는다. 작업이 하나라도 있으면 언젠가 0보다 큰 개수를 만나 `numMax = 1`로 다시 시작하기 때문이다. `B C B C`, n = 5를 넣으면 0이 먼저 나오지만 maxF 2, numMax 2로 (2 - 1) × 6 + 2 = 8이 나오고, 시뮬레이션 순서도 `B C idle idle idle idle B C`로 같다. 다만 "더 큰 값이 나오면 다시 센다"는 줄을 빼고 같은 값만 세도록 고치면 이 0들이 그대로 남는다. 최댓값을 먼저 구하고 두 번째 반복에서 세는 쪽이 읽기에는 더 안전하다.

### 작업 이름을 칸 번호로 바꿀 때

`t.charCodeAt(0) - 65`는 대문자만 들어온다는 약속에 기대고 있다. 소문자 `a`가 섞이면 칸 번호가 32가 되고, JavaScript 배열은 오류 없이 길이를 33으로 늘린다. 그 칸은 `undefined`에서 시작해 `++` 하면 `NaN`이 된다. `["A", "a", "a"]`를 넣어 보면 가장 많은 개수가 2가 아니라 1로 나온다. `NaN`은 어떤 비교에서도 거짓이라 최댓값 찾기에서 조용히 빠지기 때문이다. 작업 이름이 정해지지 않았다면 `Map`으로 센다.

## 면접관이 조건을 바꾸면

### 실제 순서도 돌려 달라면

힙 시뮬레이션에서 힙에 `[개수, 작업]`을 넣고, 꺼낼 때마다 작업 이름을 기록한다. 시계를 건너뛸 때는 건너뛴 칸 수만큼 쉼을 기록한다. 식은 시간만 알려 주고 순서는 만들지 않는다.

### 같은 글자가 이웃하지만 않으면 되고, 쉴 수 없다면

n = 1에 쉬는 칸을 허용하지 않는 문제가 [Reorganize String](/posts/leetcode-reorganize-string)이다. 뼈대 식으로 보면 가장 많은 글자가 (길이 + 1) / 2개를 넘으면 불가능하다. 가능하면 같은 최대 힙 탐욕으로 문자열을 만든다. 간격을 k로 넓힌 버전이 LeetCode 358번 Rearrange String k Distance Apart(프리미엄 문제)다.

### 작업 순서를 바꿀 수 없다면

LeetCode 2365번 Task Scheduler II가 이 변형이다. 순서가 고정이라 고를 게 없으니 힙도 필요 없다. 작업마다 "다음에 할 수 있는 시각"을 해시맵에 적어 두고, 지금 시각이 그보다 이르면 그 시각으로 건너뛴다. O(T)다. 작업 종류가 26개로 제한되지 않아 배열 대신 해시맵을 쓴다.

### 작업마다 쿨다운이 다르다면

뼈대 식이 깨진다. 덩어리 길이가 작업마다 달라서 한 줄 식으로 정리되지 않는다. 힙 시뮬레이션은 대기 줄의 순서가 깨지므로 큐 대신 "풀리는 시각"이 작은 것이 위인 최소 힙을 하나 더 쓴다. 최적 순서 자체도 일반적으로는 어려운 문제가 되어, 실무 스케줄러는 최적보다 공정함과 단순함을 고른다.

### 같은 사용자에게 알림을 연달아 보내지 않으려면

실무에서 이 모양을 만나는 흔한 자리가 "같은 대상 사이에 간격 두기"다. 사용자마다 알림이 여러 개 쌓여 있고, 같은 사용자에게는 최소 몇 초 간격으로만 보내야 한다고 하자. 작업 종류가 사용자, n이 최소 간격이다. 차이는 종류가 26개가 아니라 수백만 개라는 것과, 알림이 계속 새로 들어온다는 것이다.

그래서 식은 쓸 수 없고 힙 시뮬레이션의 모양을 그대로 가져간다. 보낼 수 있는 사용자는 우선순위 큐에, 방금 보낸 사용자는 "다시 보낼 수 있는 시각"과 함께 대기 줄에 넣는다. 간격이 모두 같으면 대기 줄은 큐로 충분하다는 성질도 그대로 쓴다. 외부 API의 키별 호출 제한을 지키며 요청을 내보낼 때도 같은 구조다.

이때 "가장 많이 남은 대상부터"라는 기준이 공정한지는 따로 따져야 한다. 쌓인 알림이 많은 사용자가 계속 먼저 나가면 적게 쌓인 사용자는 오래 기다린다. 총 시간을 줄이는 것과 대기 시간을 고르게 하는 것은 다른 목표라서, 실무에서는 들어온 순서를 섞어 기준을 정한다.

### CPU 스케줄러와는 무엇이 다른가

이 문제는 모든 작업이 처음부터 주어지고 길이가 1로 같다. 실제 운영체제 스케줄러는 작업이 계속 들어오고, 길이를 모르고, 우선순위와 공정함을 함께 따진다. 그래도 "우선순위가 높은 것을 꺼내고 쓴 것은 잠시 뒤로 보낸다"는 구조는 같다. [CPU 스케줄링 글](/posts/cpu-scheduling-interrupts)이 그 세계를 다룬다.

## 면접에서 나올 만한 질문

### 답을 식 하나로 구할 수 있는 이유는요?

가장 많이 나온 작업이 뼈대를 정하기 때문이다. 그 작업을 n + 1칸 간격으로 maxF번 놓으면 (maxF - 1) × (n + 1)칸에 마지막 줄이 붙고, 마지막 줄에는 개수가 같은 작업 수만큼 칸이 생긴다. 나머지 작업은 빈칸을 채우고, 빈칸이 모자라면 덩어리를 늘려도 간격이 깨지지 않아 쉬는 칸 없이 작업 수가 답이 된다. 그래서 둘 중 큰 값이다.

### 왜 가장 많이 남은 작업을 먼저 하나요?

가장 많이 남은 작업이 끝까지 남으면 마지막에 그 작업만 남아 사이를 채울 것이 없기 때문이다. 알파벳 순 같은 다른 기준으로 고르면 `A B B B`, n = 1에서 6이 나오지만, 많이 남은 B를 먼저 하면 A가 B 사이를 채워 5가 된다. 이 선택을 힙으로 빠르게 하는 게 시뮬레이션 풀이다.

### 힙 풀이의 시간 복잡도는요?

작업 하나마다 힙에서 꺼내고 넣는 연산이 한 번씩이라 O(T log 26)이고, 종류가 26개뿐이라 사실상 O(T)다. 쉬는 칸은 대기 줄 맨 앞이 풀리는 시각으로 시계를 건너뛰어 하나씩 돌지 않는다. 그렇지 않으면 답이 100만을 넘는 입력에서 쉬는 칸마다 반복이 돈다.

### 쿨다운 대기 줄은 왜 그냥 큐로 충분한가요?

작업이 대기 줄에 들어가는 시각이 1씩 늘어나고 쿨다운 길이가 모두 n으로 같아서, 풀리는 시각도 들어온 순서대로 늘어난다. 줄 맨 앞이 항상 가장 먼저 풀리니 힙이 필요 없다. 쿨다운이 작업마다 다르면 이 성질이 깨져 풀리는 시각 기준 최소 힙을 써야 한다.

### n이 0이면 답은요?

작업 수다. 간격이 필요 없으니 쉬는 칸이 없다. 식으로 봐도 (maxF - 1) × 1 + numMax는 작업 수 이하라서 max가 작업 수를 고른다. 이 경우를 따로 처리하지 않아도 식이 맞는다.

### 실제 실행 순서도 만들 수 있나요?

힙 시뮬레이션에서 개수와 함께 작업 이름을 넣고, 매 시각 꺼낸 작업을 기록하면 된다. 시계를 건너뛸 때는 그 칸 수만큼 쉼을 넣는다. 식은 최소 시간만 알려 주므로 순서가 필요하면 시뮬레이션으로 돌아간다.

### 쉬는 칸이 몇 개 생기는지 바로 말할 수 있나요?

뼈대의 빈칸 (maxF - 1) × n개에서 다른 작업이 채우는 칸을 빼면 된다. 한 작업이 채울 수 있는 칸은 덩어리 수인 maxF - 1개까지라서, 뼈대를 만든 작업 하나를 뺀 나머지 작업마다 min(개수, maxF - 1)을 뺀다. 결과가 0 이하면 빈칸이 모자란 것이라 쉬는 칸은 없다. 답은 작업 수에 이 쉬는 칸 수를 더한 값이고, 뼈대 식과 항상 같다.
