<EasyIntro>

  그래서 뷰는 늘 최신이지만 무거운 질문이면 매번 무겁다. 머티리얼라이즈드 뷰는 반대로 계산 결과를 진짜 표처럼 저장해 두고, 갱신하라고 할 때만 다시 계산한다. 빠른 대신 마지막 갱신 시점의 숫자이고, 일반 갱신은 그동안 읽기까지 막아 버려서 읽기를 막지 않는 방식을 고르면 비용이 두 배 넘게 든다.

  이걸 알면 뷰가 걸린 칸을 지울 때 뷰부터 고치고 나서 지우는 순서를 지키게 된다. 흔히 헷갈리는 점은 모든 칸을 뜻하는 별표로 만든 뷰인데, 만든 날의 칸 목록으로 굳어 버려서 나중에 표에 칸을 더해도 뷰에는 나타나지 않는다.
</EasyIntro>

`students` 테이블의 `city` 컬럼을 주소 테이블로 옮기기로 했다. 새 테이블을 만들고 데이터를 옮긴 다음, 마이그레이션 마지막 줄에서 원래 컬럼을 지운다.

```sql
ALTER TABLE students DROP COLUMN city;
```

```text
ERROR:  cannot drop column city of table students because other objects depend on it
DETAIL:  view student_progress depends on column city of table students
view seoul_students depends on column city of table students
HINT:  Use DROP ... CASCADE to drop the dependent objects too.
```

누군가 만들어 둔 뷰 두 개가 이 컬럼을 쓰고 있다. 힌트대로 `CASCADE`를 붙이면 마이그레이션은 통과하지만, 그 뷰를 읽던 대시보드는 다음 배포 후에 `relation "student_progress" does not exist`로 깨진다. 뷰가 무엇을 저장하고 무엇에 기대는지 알아야 이 상황에서 맞는 순서를 고를 수 있다.

뷰와 머티리얼라이즈드 뷰의 기본 차이(뷰는 매번 계산하고, 머티리얼라이즈드 뷰는 `REFRESH` 때만 계산한다)와 `CONCURRENTLY`에 유니크 인덱스가 필요하다는 것은 [리포트 쿼리 글](/posts/postgres-reporting-sql#이름-붙인-쿼리와-저장해-둔-결과)에서 봤다. 이 글은 그 다음을 본다. 뷰가 조회 때 어떻게 원래 쿼리로 펼쳐지는지, `SELECT *` 뷰가 왜 새 컬럼을 못 보는지, 뷰를 지나 `UPDATE`할 때 행이 사라지는 문제와 `WITH CHECK OPTION`, 뷰로 숨긴 행이 함수 하나로 새어 나가는 틈, 그리고 `REFRESH`가 실제로 어떤 잠금을 잡고 `CONCURRENTLY`가 얼마나 더 비싼지다.

데이터는 [SELECT의 논리적 처리 순서](/posts/sql-logical-order)부터 이어 온 강의 사이트(`students`, `courses`, `enrollments`, `payments`)다. 기준은 Ubuntu 24.04의 PostgreSQL 16.15이고 출력은 모두 실제로 돌린 결과다. MySQL 8과의 차이는 문서로 확인해 짧게 적는다.

## 뷰는 조회할 때 원래 쿼리로 펼쳐진다

문제의 뷰 두 개는 이렇게 만들어져 있었다.

```sql
CREATE VIEW student_progress AS              -- 수강생별 진행 현황
SELECT s.id, s.name, s.city,
       count(e.id) AS taken,
       count(*) FILTER (WHERE e.status = 'completed') AS completed
FROM students s
LEFT JOIN enrollments e ON e.student_id = s.id
GROUP BY s.id;

CREATE VIEW seoul_students AS SELECT * FROM students WHERE city = 'seoul';

SELECT * FROM student_progress ORDER BY id;
```

```text
 id | name |  city  | taken | completed
----+------+--------+-------+-----------
  1 | kim  | seoul  |     3 |         2
  2 | lee  | busan  |     2 |         1
  3 | park | (null) |     2 |         1
  4 | choi | seoul  |     2 |         1
  5 | jung | daegu  |     0 |         0
(5 rows)
```

뷰는 데이터를 갖고 있지 않다. PostgreSQL은 뷰를 "이 이름을 읽으면 이 쿼리로 바꿔라"라는 규칙(rewrite rule)으로 저장한다. 쿼리가 들어오면 플래너보다 먼저 리라이터가 뷰 이름을 원래 쿼리로 바꿔 끼우고, 플래너는 펼쳐진 전체 쿼리를 보고 계획을 세운다. 그래서 뷰 바깥의 조건이 뷰 안으로 들어간다.

```sql
EXPLAIN (COSTS OFF) SELECT * FROM student_progress WHERE id = 1;
```

```text
 GroupAggregate
   ->  Nested Loop Left Join
         ->  Index Scan using students_pkey on students s
               Index Cond: (id = 1)
         ->  Seq Scan on enrollments e
               Filter: (student_id = 1)
```

계획에 뷰 이름이 없다. 바깥에 쓴 `id = 1`이 `students`의 기본 키 조건(`Index Cond`)이 되어 한 명만 읽고 묶었다. 다섯 명을 다 묶은 다음 한 명을 고른 게 아니다. 아래 그림에서 다음을 누르면 뷰를 읽는 쿼리가 어디서 펼쳐지는지 보인다.

조건이 늘 안으로 들어가는 건 아니다. `WHERE taken > 1`처럼 집계 결과에 거는 조건은 묶은 뒤에야 계산할 수 있어 바깥에 남는다. 뷰 안에 `LIMIT`, `DISTINCT ON`, 윈도우 함수가 있어도 결과가 바뀔 수 있는 조건은 들어가지 못한다. 뷰를 겹겹이 쌓은 쿼리가 느리면 뷰 이름 대신 `EXPLAIN`에서 펼쳐진 모습을 보고 조건이 어디에 걸렸는지 확인한다.

## SELECT *는 만든 날의 컬럼 목록으로 굳는다

`seoul_students`는 `SELECT *`로 만들었다. 저장된 정의를 보면 `*`가 없다.

```sql
SELECT pg_get_viewdef('seoul_students');
```

```text
         pg_get_viewdef
---------------------------------
  SELECT id,                    +
     name,                      +
     city                       +
    FROM students               +
   WHERE (city = 'seoul'::text);
(1 row)
```

뷰를 만드는 순간 `*`가 그때의 컬럼 목록으로 바뀌어 저장됐다. 그래서 `students`에 `email`을 추가해도 이 뷰에는 나오지 않는다.

```sql
ALTER TABLE students ADD COLUMN email text;
SELECT * FROM seoul_students;
```

```text
 id | name | city
----+------+-------
  1 | kim  | seoul
  4 | choi | seoul
(2 rows)
```

같은 정의로 `CREATE OR REPLACE VIEW`를 다시 돌려야 `email`이 붙는다. 이때 `OR REPLACE`가 허용하는 변경은 좁다. 기존 컬럼은 이름, 순서, 타입이 그대로여야 하고 새 컬럼은 끝에만 붙일 수 있다.

```sql
-- 컬럼 이름을 바꾸려 하면
CREATE OR REPLACE VIEW seoul_students AS
SELECT id, name AS student_name, city, email FROM students WHERE city = 'seoul';
```

```text
ERROR:  cannot change name of view column "name" to "student_name"
HINT:  Use ALTER VIEW ... RENAME COLUMN ... to change name of view column instead.
```

타입을 바꾸면 `cannot change data type of view column "city" from text to character varying(20)`, 컬럼을 빼면 `cannot drop columns from view`가 난다. 이 경우는 `DROP VIEW` 후 `CREATE VIEW`를 한 트랜잭션에서 하고, 권한(`GRANT`)도 다시 준다. 뷰를 지우면 그 뷰에 준 권한도 같이 사라진다.

처음의 마이그레이션으로 돌아간다. 뷰는 자기가 쓰는 컬럼 하나하나에 의존 관계를 기록해 둔다. 그래서 PostgreSQL은 컬럼을 지우기 전에 막을 수 있었다. 어떤 뷰가 걸려 있는지는 카탈로그에서 찾는다.

```sql
SELECT DISTINCT v.oid::regclass AS view_name
FROM pg_attribute a
JOIN pg_depend d  ON d.refobjid = a.attrelid AND d.refobjsubid = a.attnum   -- 이 컬럼에 기댄 것
JOIN pg_rewrite r ON r.oid = d.objid                                         -- 그중 뷰 규칙
JOIN pg_class v   ON v.oid = r.ev_class                                      -- 규칙의 주인
WHERE a.attrelid = 'students'::regclass AND a.attname = 'city'
  AND v.oid <> 'students'::regclass;
```

```text
    view_name
------------------
 student_progress
 seoul_students
(2 rows)
```

`CASCADE`가 무엇을 지우는지는 트랜잭션 안에서 미리 볼 수 있다.

```sql
BEGIN;
ALTER TABLE students DROP COLUMN city CASCADE;
ROLLBACK;                                    -- 무엇이 지워지는지만 보고 되돌린다
```

```text
NOTICE:  drop cascades to 2 other objects
DETAIL:  drop cascades to view student_progress
drop cascades to view seoul_students
```

맞는 순서는 이렇다. 뷰가 `city` 대신 새 주소 테이블을 조인하도록 먼저 고치고(`DROP VIEW` + `CREATE VIEW` + `GRANT`를 한 트랜잭션에서), 그 다음 컬럼을 지운다. PostgreSQL은 DDL도 트랜잭션 안에서 되돌릴 수 있어서 이 묶음이 중간에 실패해도 반쯤 바뀐 상태로 남지 않는다. MySQL 8은 뷰가 쓰는 컬럼을 지워도 막지 않는다. 대신 그 뷰를 읽는 순간 잘못된 컬럼을 참조한다는 에러가 난다. 실패하는 시점이 마이그레이션이 아니라 운영 조회로 밀린다.

## 뷰를 지나 쓰기와 WITH CHECK OPTION

`FROM`에 테이블 하나만 있고 `GROUP BY`, `DISTINCT`, 집계, `UNION`, `LIMIT` 같은 것이 없는 단순한 뷰는 PostgreSQL 9.3부터 자동으로 쓸 수 있다(automatically updatable view). 수강 중인 기록만 보여 주는 뷰로 관리 화면을 만들었다.

```sql
CREATE VIEW active_enrollments AS
SELECT id, student_id, course_id, status, enrolled_at
FROM enrollments WHERE status = 'active';

BEGIN;
UPDATE active_enrollments SET status = 'completed' WHERE id = 3;   -- 수강 완료 처리
SELECT id, status FROM active_enrollments ORDER BY id;
```

```text
UPDATE 1
 id | status
----+--------
  5 | active
  7 | active
(2 rows)
```

3번이 뷰에서 사라졌다. 완료 처리라면 이게 맞다. 그런데 같은 뷰로 수강 기록을 넣는 화면이 실수로 `refunded`를 넣으면 이렇게 된다.

```sql
INSERT INTO active_enrollments (student_id, course_id, status, enrolled_at)
VALUES (5, 3, 'refunded', now()) RETURNING id, status;
SELECT count(*) FROM active_enrollments WHERE student_id = 5;
ROLLBACK;
```

```text
 id |  status
----+----------
 10 | refunded
(1 row)

INSERT 0 1
 count
-------
     0
(1 row)
```

넣기는 성공했는데 넣은 뷰에서 보이지 않는다. 화면 입장에서는 저장했는데 목록에 없는 행이다. `WITH CHECK OPTION`을 붙이면 뷰의 조건을 만족하지 않는 행을 쓰려 할 때 막는다.

```sql
CREATE OR REPLACE VIEW active_enrollments AS
SELECT id, student_id, course_id, status, enrolled_at
FROM enrollments WHERE status = 'active'
WITH CHECK OPTION;

INSERT INTO active_enrollments (student_id, course_id, status, enrolled_at)
VALUES (5, 3, 'refunded', now());
UPDATE active_enrollments SET status = 'completed' WHERE id = 3;
```

```text
ERROR:  new row violates check option for view "active_enrollments"
DETAIL:  Failing row contains (11, 5, 3, refunded, null, 2026-10-21 19:18:51.462493+09).
ERROR:  new row violates check option for view "active_enrollments"
DETAIL:  Failing row contains (3, 2, 1, completed, null, 2026-10-05 13:20:00+09).
```

이번엔 완료 처리도 막혔다. 행을 뷰 밖으로 내보내는 `UPDATE`도 같은 규칙에 걸리기 때문이다. 그래서 `WITH CHECK OPTION`은 "이 뷰로는 이 범위 안의 행만 다룬다"가 맞는 화면에 쓴다. 상태 전환이 일인 화면이라면 뷰가 아니라 테이블에 쓰거나 함수로 감싼다. 롤백한 `INSERT`도 identity 값(10)은 써 버려서 다음 행은 11번부터다.

`GROUP BY`가 있는 뷰는 쓸 수 없다.

```text
ERROR:  cannot update view "enrollment_counts"
DETAIL:  Views containing GROUP BY are not automatically updatable.
HINT:  To enable updating the view, provide an INSTEAD OF UPDATE trigger or an unconditional ON UPDATE DO INSTEAD rule.
```

힌트대로 `INSTEAD OF` 트리거로 쓰기 동작을 직접 정할 수는 있다. 트리거는 [함수와 트리거 글](/posts/postgres-functions-triggers)에서 다룬다. MySQL 8도 단순한 뷰는 쓸 수 있고 `WITH CHECK OPTION`을 지원한다.

## 뷰로 숨긴 행이 함수로 새어 나간다

`seoul_students`를 만든 이유가 권한이었다고 하자. 외주 분석 계정 `s3_reader`에게 `students` 테이블은 주지 않고 이 뷰에만 `SELECT`를 준다.

```sql
CREATE ROLE s3_reader;
GRANT SELECT ON seoul_students TO s3_reader;
SET ROLE s3_reader;
SELECT id, name FROM seoul_students;   -- 된다
SELECT id, name FROM students;         -- 안 된다
RESET ROLE;
```

```text
 id | name
----+------
  1 | kim
  4 | choi
(2 rows)

ERROR:  permission denied for table students
```

뷰는 기본으로 만든 사람(소유자)의 권한으로 테이블을 읽는다. 그래서 테이블 권한이 없어도 뷰로는 읽힌다. 그런데 뷰는 원래 쿼리로 펼쳐지고, 플래너는 조건의 순서를 비용으로 정한다. 비용을 아주 낮게 선언한 함수를 조건에 넣으면 그 함수가 `city = 'seoul'`보다 먼저 돈다.

```sql
CREATE FUNCTION peek(n text) RETURNS boolean
LANGUAGE plpgsql COST 0.0000001 AS $$
BEGIN
  RAISE NOTICE 'saw %', n;   -- 받은 값을 밖으로 흘린다
  RETURN true;
END $$;

SELECT id, name FROM seoul_students WHERE peek(name);
```

```text
NOTICE:  saw kim
NOTICE:  saw lee
NOTICE:  saw park
NOTICE:  saw choi
NOTICE:  saw jung
 id | name
----+------
  1 | kim
  4 | choi
(2 rows)
```

결과는 두 줄인데 함수는 다섯 명을 다 봤다. 계획이 `Filter: (peek(name) AND (city = 'seoul'::text))`, 함수가 먼저다. 이 데모는 관리자 계정으로 돌렸지만, 함수를 만들 수 있는 계정이라면 같은 일을 할 수 있다. `security_barrier`를 켜면 뷰의 조건을 먼저 끝낸 다음에 바깥 조건을 적용한다.

```sql
ALTER VIEW seoul_students SET (security_barrier = true);
SELECT id, name FROM seoul_students WHERE peek(name);
```

```text
NOTICE:  saw kim
NOTICE:  saw choi
```

## 결과를 저장하는 머티리얼라이즈드 뷰

뷰는 매번 계산하니 무거운 집계는 매번 무겁다. 머티리얼라이즈드 뷰는 결과를 실제 테이블처럼 디스크에 저장해 두고 `REFRESH`할 때만 다시 계산한다. 일별 매출로 만든다. 언제 계산한 숫자인지 PostgreSQL이 기록해 두지 않으니 `now()`를 컬럼으로 함께 저장한다.

```sql
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT paid_at::date AS day, sum(amount) AS revenue, count(*) AS payments,
       now() AS refreshed_at                       -- 언제 계산했는지 같이 저장
FROM payments GROUP BY 1
WITH NO DATA;                                      -- 정의만 만들고 계산은 나중에

SELECT * FROM daily_revenue;
```

```text
ERROR:  materialized view "daily_revenue" has not been populated
HINT:  Use the REFRESH MATERIALIZED VIEW command.
```

`WITH NO DATA`는 배포 중에 무거운 계산을 미루고 싶을 때 쓴다. 대신 첫 `REFRESH` 전에는 읽기가 에러를 낸다. 배포 스크립트에 `REFRESH`를 빠뜨리면 이 에러가 운영에 나간다.

```sql
REFRESH MATERIALIZED VIEW daily_revenue;
SELECT day, revenue, payments, refreshed_at FROM daily_revenue ORDER BY day LIMIT 3;
```

```text
    day     | revenue | payments |         refreshed_at
------------+---------+----------+-------------------------------
 2026-09-28 |   30000 |        1 | 2026-10-21 19:19:11.189054+09
 2026-10-01 |   45000 |        1 | 2026-10-21 19:19:11.189054+09
 2026-10-05 |   30000 |        1 | 2026-10-21 19:19:11.189054+09
(3 rows)
```

대시보드에 `refreshed_at`을 "기준 시각"으로 함께 보여 주면 숫자가 늦었다는 문의가 줄고, 갱신 작업이 멈췄을 때 바로 티가 난다. 머티리얼라이즈드 뷰는 진짜 테이블이라서 인덱스도 만들 수 있다. 그냥 두면 `day = '2026-11-01'` 조회는 `Seq Scan on daily_revenue`다. 인덱스를 만든다.

```sql
CREATE UNIQUE INDEX daily_revenue_day_idx ON daily_revenue (day);
```

유니크 인덱스로 만든 이유는 다음 절의 `CONCURRENTLY` 때문이다.

## REFRESH가 잡는 잠금을 직접 본다

`REFRESH`가 오래 걸리는 상황을 흉내 낸다. 한 세션이 트랜잭션 안에서 `REFRESH`를 하고 4초 동안 커밋하지 않는다. 그 사이 다른 세션에서 어떤 잠금이 걸려 있는지 보고, `lock_timeout`을 1초로 두고 읽어 본다.

```sql
-- 세션 A
BEGIN;
REFRESH MATERIALIZED VIEW daily_revenue;
SELECT pg_sleep(4);
COMMIT;

-- 세션 B (A가 잠든 사이)
SELECT l.mode, l.granted, a.query
FROM pg_locks l JOIN pg_stat_activity a USING (pid)
WHERE l.relation = 'daily_revenue'::regclass;
SET lock_timeout = '1s';
SELECT count(*) FROM daily_revenue;
```

```text
        mode         | granted |        query
---------------------+---------+---------------------
 AccessExclusiveLock | t       | SELECT pg_sleep(4);
 ExclusiveLock       | t       | SELECT pg_sleep(4);
 ShareLock           | t       | SELECT pg_sleep(4);
(3 rows)

ERROR:  canceling statement due to lock timeout
LINE 1: SELECT count(*) FROM daily_revenue;
                             ^
```

일반 `REFRESH`는 `AccessExclusiveLock`을 잡는다. 가장 강한 잠금이라 `SELECT`도 기다린다. `lock_timeout`이 없었다면 대시보드 쿼리가 `REFRESH`가 끝날 때까지 줄을 섰을 것이다. 같은 실험을 `CONCURRENTLY`로 하면 이렇다.

```text
       mode       | granted |        query
------------------+---------+---------------------
 ExclusiveLock    | t       | SELECT pg_sleep(4);
 RowExclusiveLock | t       | SELECT pg_sleep(4);
 AccessShareLock  | t       | SELECT pg_sleep(4);
(3 rows)

 count
-------
    11
(1 row)
```

`ExclusiveLock`은 `SELECT`가 잡는 `AccessShareLock`과 충돌하지 않아서 읽기가 바로 됐다. 읽은 쪽은 갱신 전 결과를 본다. 다만 `ExclusiveLock`끼리는 충돌해서 같은 뷰의 `REFRESH ... CONCURRENTLY` 두 개는 동시에 돌지 못한다. 아래 그림에서 다음을 누르면 두 방식에서 대시보드 쿼리가 어떻게 되는지 보인다.

## CONCURRENTLY는 공짜가 아니다

`CONCURRENTLY`는 새 결과를 임시 테이블에 만들고, 유니크 인덱스를 기준으로 기존 행과 맞춰 본다. 같은 행은 두고, 바뀌었거나 없어진 행은 지우고, 새 행은 넣는다. 읽기를 막지 않는 대신 계산이 하나 더 붙는다. 30만 건짜리 `enrollments_big`([윈도우 함수 글](/posts/sql-window-functions-pg#창마다-정렬이-하나씩-붙는다)에서 만든 테이블)으로 수강생 2만 명의 통계를 만들어 잰다.

```sql
CREATE MATERIALIZED VIEW student_stats AS
SELECT student_id, count(*) AS taken, round(avg(score), 2) AS avg_score, max(enrolled_at) AS last_at
FROM enrollments_big GROUP BY student_id;
CREATE UNIQUE INDEX student_stats_pk ON student_stats (student_id);

\timing on
REFRESH MATERIALIZED VIEW student_stats;
REFRESH MATERIALIZED VIEW CONCURRENTLY student_stats;
```

```text
REFRESH MATERIALIZED VIEW
Time: 154.506 ms
REFRESH MATERIALIZED VIEW
Time: 348.529 ms
```

원본이 하나도 안 바뀐 상태에서도 `CONCURRENTLY`가 두 배 넘게 걸렸다. 비교하는 일 자체가 비싸다. 바뀐 양에 따라 다시 쟀다.

| 상황 | 일반 REFRESH | CONCURRENTLY |
|---|---|---|
| 바뀐 수강생 없음 | 139~155ms | 301~349ms |
| 100명 바뀜 (원본 1480행) | | 346ms |
| 2만 명 모두 바뀜 (원본 30만 행) | 263ms | 644ms |

두 번째 칸이 비어 있는 건 일반 `REFRESH`는 바뀐 양과 상관없이 늘 전체를 다시 쓰기 때문이다. 모두 바뀐 뒤의 일반 `REFRESH`가 263ms로 늘어난 건 원본 테이블에 `UPDATE`로 생긴 죽은 행이 쌓여서다. `CONCURRENTLY`는 흔적도 남긴다. 다 바뀐 경우 한 번 갱신하고 나서 통계를 보면 이렇다.

```sql
SELECT relname, n_live_tup, n_dead_tup, n_tup_upd, n_tup_ins, n_tup_del
FROM pg_stat_user_tables WHERE relname = 'student_stats';
```

```text
    relname    | n_live_tup | n_dead_tup | n_tup_upd | n_tup_ins | n_tup_del
---------------+------------+------------+-----------+-----------+-----------
 student_stats |      20000 |      19924 |         0 |    119948 |     39948
(1 row)
```

`n_tup_upd`가 0이다. 바뀐 행은 고치는 게 아니라 지우고 새로 넣는다. 살아 있는 행 2만 개 옆에 죽은 행이 2만 개 가까이 쌓였다. autovacuum이 치우지만, 자주 갱신하는 큰 머티리얼라이즈드 뷰는 크기가 부풀기 쉽다. 일반 `REFRESH`는 새 파일로 통째로 바꾸니 죽은 행이 남지 않는다. 아래 그림에서 다음을 누르면 `CONCURRENTLY`가 행을 어떻게 맞춰 보는지 따라간다.

## 뷰, 머티리얼라이즈드 뷰, 요약 테이블 고르기

작은 서비스에서는 뷰로 시작한다. 쿼리에 이름을 붙이고 여러 화면에서 같은 정의를 쓰는 것만으로 충분하다. 뷰를 읽는 쿼리의 `EXPLAIN ANALYZE`가 화면 응답 목표(예: 100ms)를 넘기기 시작하고, 그 숫자가 몇 분 늦어도 괜찮다면 머티리얼라이즈드 뷰로 바꾼다. 갱신이 무거워져서 `CONCURRENTLY` 시간이 갱신 주기의 상당 부분을 차지하거나, 원본의 아주 일부만 바뀌는데 매번 전체를 다시 계산하고 있다면 그때 바뀐 부분만 반영하는 요약 테이블을 쓴다. 트리거로 원본이 바뀔 때마다 더하고 빼거나, 원본에 `updated_at`을 두고 배치가 그 이후 행만 다시 계산하는 방식이다. 요약 테이블은 빠르고 최신이지만 더하고 빼는 코드가 틀리면 숫자가 조용히 어긋나서, 가끔 전체를 다시 계산해 맞춰 보는 검사가 따라붙는다.

| | 저장 | 신선도 | 읽기 비용 | 쓰기 쪽 부담 |
|---|---|---|---|---|
| 뷰 | 쿼리만 | 항상 최신 | 매번 원래 쿼리 | 없음 |
| 머티리얼라이즈드 뷰 | 결과 전체 | 마지막 REFRESH 시점 | 테이블 읽기 | REFRESH마다 전체 계산 |
| 요약 테이블 | 결과 전체 | 트리거면 즉시, 배치면 주기 | 테이블 읽기 | 원본 쓰기마다 또는 배치마다 |

같은 숫자를 애플리케이션 [캐시](/posts/caching-strategies)에 둘 수도 있다. DB 밖에 두면 DB 부하는 더 줄지만, 무효화 시점을 애플리케이션이 직접 챙겨야 한다.

## 바뀐 행만 고치는 비교를 짜 보기

`CONCURRENTLY`가 하는 비교를 자바스크립트로 짜 본다. 옛 결과 행 목록, 새 결과 행 목록, 키 컬럼 이름을 받아서 `{ deleted, inserted }`를 돌려준다. 키가 같고 나머지 값도 모두 같은 행은 그대로 두고, 값이 바뀐 행은 지우고 다시 넣으므로 두 목록에 모두 들어간다. 없어진 키는 `deleted`에만, 새 키는 `inserted`에만 들어간다. 두 배열은 키 오름차순으로 정렬한다. 첫 테스트는 위 그림의 다섯 수강생이다.

## 이름은 같아도 저장하는 것이 다르다

뷰는 쿼리를 저장하고 조회할 때 원래 쿼리로 펼쳐진다. 그래서 늘 최신이고 바깥 조건이 안으로 들어가지만, 쓰는 컬럼마다 의존 관계가 생기고 `*`는 만든 날의 컬럼으로 굳는다. 뷰로 쓰기를 열면 `WITH CHECK OPTION`으로 범위를 지키고, 뷰로 권한을 나누면 `security_barrier`나 RLS를 함께 생각한다. 머티리얼라이즈드 뷰는 결과를 저장하는 테이블이라 빠르지만 `REFRESH` 시점의 숫자이고, 일반 `REFRESH`는 읽기를 막고 `CONCURRENTLY`는 막지 않는 대신 두 배 넘게 비싸고 죽은 행을 남긴다. 뷰 안에 들어가는 쿼리 재료는 [재귀 CTE 글](/posts/sql-cte-recursive)과 [윈도우 함수 글](/posts/sql-window-functions-pg)에서 이어진다.

## 면접에서 나올 만한 질문

### 뷰는 데이터를 저장하나요? 뷰를 쓰면 느려지나요?

저장하지 않습니다. PostgreSQL은 뷰를 재작성 규칙으로 저장해 두고 조회할 때 원래 쿼리로 바꿔 끼운 뒤 계획을 세웁니다. 그래서 뷰 자체가 느리게 만들지는 않고, 바깥 조건이 기본 키나 `GROUP BY` 키라면 안으로 밀려 들어가 인덱스를 씁니다. 다만 집계 결과에 거는 조건이나 `LIMIT`·윈도우 함수가 있는 뷰는 조건이 들어가지 못해 전체를 계산한 뒤 거릅니다.

### SELECT *로 만든 뷰에 테이블 새 컬럼이 안 보입니다. 왜 그런가요?

뷰를 만드는 순간 `*`가 그때의 컬럼 목록으로 바뀌어 저장되기 때문입니다. `pg_get_viewdef`로 보면 컬럼이 나열돼 있습니다. `CREATE OR REPLACE VIEW`로 다시 만들면 새 컬럼이 끝에 붙는데, 기존 컬럼의 이름·순서·타입은 바꿀 수 없어서 그런 변경은 `DROP` 후 `CREATE`와 `GRANT`를 한 트랜잭션에서 합니다.

### 뷰가 쓰는 컬럼을 지우려면 어떻게 하나요?

PostgreSQL은 뷰가 쓰는 컬럼마다 의존 관계를 기록해서 그냥 지우면 막습니다. `CASCADE`는 뷰까지 조용히 지우니, 먼저 `pg_depend`로 어떤 뷰가 걸렸는지 찾고 뷰를 새 구조에 맞게 고친 다음 컬럼을 지웁니다. PostgreSQL은 DDL도 트랜잭션으로 묶을 수 있어서 중간 실패를 되돌릴 수 있습니다. MySQL은 지우는 걸 막지 않고 나중에 뷰를 읽을 때 에러가 납니다.

### 뷰로 INSERT나 UPDATE를 할 수 있나요?

테이블 하나에서 `GROUP BY`, 집계, `DISTINCT`, `UNION`, `LIMIT` 없이 고르는 단순한 뷰는 자동으로 쓸 수 있습니다. 이때 뷰의 `WHERE`를 만족하지 않는 행도 들어가서 넣었는데 뷰에서 안 보이는 일이 생기니, 범위를 지켜야 하면 `WITH CHECK OPTION`을 붙입니다. 복잡한 뷰는 `INSTEAD OF` 트리거로 쓰기 동작을 직접 정의합니다.

### 뷰로 권한을 나눌 때 조심할 점은요?

뷰는 기본적으로 소유자 권한으로 테이블을 읽어서 테이블 권한 없이 뷰만 열어 줄 수 있습니다. 그런데 바깥 조건에 비용이 아주 낮은 함수를 넣으면 뷰의 조건보다 먼저 돌아 숨긴 행의 값을 볼 수 있습니다. `security_barrier`를 켜면 뷰 조건을 먼저 끝내지만 조건이 안으로 들어가지 못해 느려질 수 있고, 행 단위 권한이 목적이면 RLS가 맞습니다. 15부터는 `security_invoker`로 조회하는 사람의 권한을 쓰게 할 수도 있습니다.

### REFRESH MATERIALIZED VIEW와 CONCURRENTLY는 무엇이 다른가요?

일반 `REFRESH`는 결과를 새로 계산해 통째로 바꾸며 `AccessExclusiveLock`을 잡아 그동안 `SELECT`도 기다립니다. `CONCURRENTLY`는 새 결과와 옛 결과를 유니크 인덱스로 맞춰 바뀐 행만 지우고 넣으며 `ExclusiveLock`이라 읽기를 막지 않습니다. 대신 비교 비용 때문에 측정에서 두 배 넘게 걸렸고, 바뀐 행이 죽은 행으로 남아 크기가 부풉니다.

### 머티리얼라이즈드 뷰가 언제 갱신됐는지 어떻게 아나요?

PostgreSQL 카탈로그에는 마지막 갱신 시각이 없습니다. 정의에 `now() AS refreshed_at` 같은 컬럼을 넣어 결과와 함께 저장하거나, 갱신 작업이 별도 테이블에 시각을 기록하게 합니다. 화면에 기준 시각을 함께 보여 주면 갱신 작업이 멈췄을 때 바로 알아챌 수 있습니다.

### 머티리얼라이즈드 뷰 대신 요약 테이블을 쓰는 건 언제인가요?

원본의 일부만 바뀌는데 매번 전체를 다시 계산하는 비용이 커지거나, 갱신 시간이 갱신 주기에 가까워질 때입니다. 요약 테이블은 트리거나 배치로 바뀐 부분만 반영해서 빠르고 최신이지만, 반영 코드가 틀리면 숫자가 조용히 어긋나서 주기적으로 전체를 다시 계산해 맞춰 보는 검사를 둡니다. MySQL처럼 머티리얼라이즈드 뷰가 없는 DB에서도 이 방식을 씁니다.
