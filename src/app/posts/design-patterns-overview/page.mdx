같은 주에 코드 리뷰 댓글 두 개를 받았다고 하자. 하나는 결제 수단별 `if`가 다섯 갈래로 늘어난 함수에 달렸다. "이거 전략 패턴으로 빼면 어때요?" 다른 하나는 알림 기능에 `AbstractNotificationSenderFactory`를 만든 PR에 달렸다. "이 정도면 과하지 않아요?" 한쪽은 패턴을 쓰라고, 한쪽은 빼라고 한다.

두 댓글은 모순이 아니다. 패턴은 이름 붙은 해법이고, 해법에는 언제나 맞는 문제가 따로 있다. 이 글은 디자인 패턴 시리즈의 첫 글이다. 패턴이 무엇인지, GoF가 스물세 개를 어떤 기준으로 나눴는지, 그리고 언제 꺼내고 언제 참아야 하는지를 먼저 정리하고, 각 패턴은 한 글씩 따로 깊게 다룬다.

## 반복되는 문제에 붙인 이름

패턴이라는 말은 건축에서 왔다. 건축가 크리스토퍼 알렉산더는 1977년 『A Pattern Language』에서 "창가에 앉을 자리", "두 방향에서 빛이 드는 방" 같은 253개의 패턴을 정리했다. 어떤 맥락에서 반복해서 나타나는 문제와, 그 문제의 핵심 해법을 묶어 이름을 붙인 것이다. 해법을 그대로 복사하라는 게 아니라 같은 생각으로 매번 다르게 지으라는 뜻이었다.

1994년 에리히 감마, 리처드 헬름, 랄프 존슨, 존 블리시디스 네 사람이 이 생각을 객체지향 설계에 옮겨 『Design Patterns: Elements of Reusable Object-Oriented Software』를 냈다. 저자가 넷이라 GoF(Gang of Four)라고 부른다. 이 책의 23개 패턴이 지금 "디자인 패턴"이라고 하면 떠올리는 목록이다.

GoF는 패턴 하나를 정해진 틀로 설명한다. 패턴 글을 읽거나 면접에서 설명할 때 이 틀을 알면 무엇을 말해야 하는지가 보인다. 아래 조각을 하나씩 눌러 보자.

GoF는 패턴의 필수 요소를 이름, 문제, 해법, 결과 넷으로 꼽는다. 이 중 이름이 생각보다 중요하다. "여기 전략 패턴으로"라는 한마디가 "인터페이스를 하나 만들고, 결제 수단마다 구현체를 두고, 호출하는 쪽은 인터페이스만 쓰게 바꾸자"는 긴 설명을 대신한다. 패턴은 해법이기 전에 팀이 설계를 짧게 이야기하는 어휘다.

## 스물세 개를 세 갈래로 나눈 기준

GoF는 패턴을 목적에 따라 세 갈래로 나눈다. 생성 패턴은 객체를 누가, 언제, 어떻게 만드는지를 다룬다. 구조 패턴은 클래스와 객체를 엮어 더 큰 구조를 만드는 방법을 다룬다. 행위 패턴은 객체들이 책임을 나누고 서로 말을 거는 방식을 다룬다.

말로는 추상적이니 결제 한 건에서 세 갈래가 각각 어디서 일하는지 보자. 아래 그림에서 다음을 누르면 결제 요청이 세 종류의 패턴을 차례로 지난다.

GoF는 다른 축도 하나 둔다. 관계가 클래스 사이에서 상속으로 컴파일 시점에 정해지면 클래스 범위, 객체 사이에서 런타임에 연결되면 객체 범위다. 23개 중 클래스 범위는 팩토리 메서드, 클래스 어댑터, 인터프리터, 템플릿 메서드 넷뿐이다. 나머지는 모두 객체를 조합한다. 이 비율 자체가 GoF가 상속보다 조합을 선호했다는 증거다.

아래 표가 이 시리즈의 지도다. 각 패턴을 "이럴 때 꺼낸다"는 신호 하나로 요약했다. 이름을 눌러 해당 글로 넘어갈 수 있다.

GoF 바깥의 패턴도 많다. 화면 코드를 나누는 [MVC](/posts/mvc-pattern), 장애를 다루는 [서킷 브레이커와 재시도](/posts/resilience-patterns)는 아키텍처나 운영 수준의 패턴이라 이 목록과 층위가 다르다. 이 시리즈는 클래스와 객체 수준의 GoF 23개를 다룬다.

## 두 문장으로 줄이면

23개를 외우는 것보다 GoF가 책 앞부분에서 강조한 두 원칙을 이해하는 편이 오래 남는다. 첫째, 구현이 아니라 인터페이스에 맞춰 프로그래밍하라. 둘째, 클래스 상속보다 객체 합성을 선호하라. 대부분의 패턴은 이 두 문장을 상황별로 풀어 쓴 것이다.

두 번째 원칙이 왜 중요한지는 알림 발송기를 상속으로 확장해 보면 바로 보인다. 채널(이메일, 문자)과 부가 기능(재시도, 로그)이 각각 늘어날 때 필요한 클래스 수를 세어 보자.

마지막 단계의 `withLog(withRetry(email))`이 [데코레이터 패턴](/posts/pattern-decorator)이다. 두 축이 함께 늘어나는 문제를 다른 방식으로 푸는 것이 [브리지 패턴](/posts/pattern-bridge)이다. 합성으로 바꾸면 기능을 런타임에 고를 수도 있다. 상속은 컴파일 시점에 고정된다.

SOLID 원칙과도 곧바로 이어진다. 개방 폐쇄 원칙(확장에는 열리고 수정에는 닫힌다)은 전략, 데코레이터, 팩토리 메서드가 직접 구현하는 목표다. 의존성 역전 원칙(구체가 아니라 추상에 의존한다)은 추상 팩토리와 의존성 주입의 바탕이다. 단일 책임 원칙은 퍼사드나 커맨드로 책임을 나눌 때, 인터페이스 분리 원칙은 어댑터가 넓은 외부 API를 좁은 인터페이스로 줄일 때 드러난다. 면접에서 "이 패턴이 어떤 원칙과 관련 있냐"는 질문이 나오면 이 연결을 말하면 된다.

위 그림의 앞부분을 실제로 돌려 보면 순서가 그대로 찍힌다. 헤더 없이 한 번, 토큰을 넣고 한 번 요청했다(Express 4.21).

```js
app.use((req, res, next) => {
  console.log("1 requestId");
  res.on("finish", () => console.log("5 finish event:", res.statusCode)); // 끝나면 알려 달라고 구독
  next();
});
app.use((req, res, next) => {
  console.log("2 auth");
  if (!req.headers.authorization) return res.status(401).end();
  next();
});
app.get("/orders/:id", (req, res) => {
  console.log("3 handler");
  res.json({ id: req.params.id });
  console.log("4 handler returned");
});
```

```text
1 requestId
2 auth
5 finish event: 401
-> client got 401
1 requestId
2 auth
3 handler
4 handler returned
5 finish event: 200
-> client got 200
```

첫 요청에는 3번과 4번이 없다. 인증 미들웨어가 사슬을 끊었기 때문이다. 그래도 5번은 두 번 다 찍혔다. 구독해 둔 쪽은 누가 응답을 보냈는지 몰라도 알림을 받는다. 이렇게 이름을 알고 나면 프레임워크 문서를 읽는 속도가 달라진다. "미들웨어 순서가 왜 중요하지"가 아니라 "책임 연쇄니까 앞에서 끊으면 뒤는 안 돈다"로 바로 이해된다.

React도 마찬가지다. 컴포넌트 트리는 컴포지트, Context는 깊은 곳까지 의존성을 건네는 주입 통로, `useReducer`의 액션 객체는 커맨드에 가깝다. DOM의 `addEventListener`는 옵서버, 배열의 `[Symbol.iterator]`는 이터레이터, 자바스크립트의 `Proxy` 객체는 이름부터 프록시다.

## 함수가 있으면 사라지는 패턴도 있다

GoF의 예제는 C++와 Smalltalk로 쓰였다. 함수를 값처럼 넘기기 어려운 언어에서는 "동작 하나"를 넘기려면 클래스를 만들어야 했다. 피터 노빅은 1996년 발표 "Design Patterns in Dynamic Languages"에서 23개 중 16개가 Lisp나 Dylan에서는 훨씬 단순해지거나 보이지 않게 된다고 정리했다. 자바스크립트와 타입스크립트도 함수가 일급 값이라 같은 일이 생긴다.

```ts
// Strategy: 알고리즘 객체 대신 함수
type FeeRule = (weightKg: number) => number;
const feeRules: Record<"standard" | "express", FeeRule> = {
  standard: (w) => 3000 + Math.max(0, w - 1) * 500,
  express: (w) => 6000 + Math.max(0, w - 1) * 800,
};
feeRules.express(3); // 7600

// Command: 실행과 되돌리기를 담은 객체 대신 클로저 한 쌍
function renameCommand(doc: { title: string }, next: string) {
  const prev = doc.title;
  return { run: () => { doc.title = next; }, undo: () => { doc.title = prev; } };
}

// Iterator: 커서 클래스 대신 제너레이터
function* pages(total: number, size: number) {
  for (let offset = 0; offset < total; offset += size) yield { offset, size };
}
```

클래스가 사라졌다고 패턴이 사라진 건 아니다. 전략 패턴의 핵심인 "알고리즘을 바꿔 끼울 자리를 만든다"는 생각은 함수 표에도 그대로 있다. 사라진 건 그 생각을 담던 문법적 껍데기다. 그래서 각 글에서는 클래스 버전과 함수 버전을 함께 보고, 클래스 형태가 여전히 나은 경우(상태를 가진 객체, 여러 메서드가 함께 바뀌는 경우, 프레임워크 확장점)를 따로 짚는다.

직접 하나 만들어 보자. 위 그림의 "상속 대신 합성"을 함수로 옮긴 것이다. 전송 함수를 감싸서 실패하면 다시 시도하는 `withRetry`를 완성한다. 클래스를 하나도 만들지 않고 이메일에도 문자에도 붙일 수 있다.

## 패턴을 꺼내기 전에

처음의 두 번째 댓글로 돌아가자. 알림 채널이 이메일 하나뿐인데 추상 팩토리, 팩토리 메서드, 전략 인터페이스를 다 만들었다면 과하다는 말이 맞다. 패턴은 변화에 대비해 간접 층을 하나 더 둔다. 그 변화가 오지 않으면 간접 층은 읽는 사람이 건너야 할 다리일 뿐이다.

몇 가지 기준을 두면 판단이 쉬워진다. 첫째, 같은 종류의 변경이 실제로 두세 번 일어났을 때 꺼낸다. 리팩터링에서 흔히 말하는 "세 번째에 정리한다"는 규칙이다. 처음 분기 하나를 위해 인터페이스부터 세우지 않는다. 둘째, 패턴 이름이 아니라 문제에서 출발한다. "옵서버를 써 보고 싶다"가 아니라 "결제 완료 후 할 일이 계속 늘어서 주문 서비스가 매번 바뀐다"에서 출발해야 맞는 패턴이 나온다. 셋째, 패턴을 넣었으면 그 패턴이 지키려던 것이 실제로 지켜지는지 본다. 전략 패턴을 넣었는데 새 전략을 추가할 때마다 호출부의 `switch`도 고친다면 패턴은 이름만 남은 것이다.

반대 방향의 실수도 있다. 이미 프레임워크가 해 주는 일을 패턴으로 다시 만드는 것이다. Spring 빈은 이미 컨테이너당 하나라 GoF 싱글턴을 직접 짤 필요가 없고, Node.js 모듈은 이미 한 번만 평가된다. React 상태가 바뀌면 이미 다시 그려지니 옵서버를 손으로 붙일 일도 드물다. 패턴을 아는 것은 새로 만들기 위해서이기도 하지만, 이미 쓰고 있는 도구가 무엇을 해 주는지 알아보기 위해서이기도 하다.

이름이 낯선 패턴을 만나면 이 지도로 돌아와 "이럴 때 꺼낸다"를 먼저 보자. 시리즈는 [싱글턴](/posts/pattern-singleton)에서 시작한다.

## 면접에서 나올 만한 질문

### 디자인 패턴이 무엇인가요?

특정 맥락에서 반복해서 나타나는 설계 문제와 그 핵심 해법을 묶어 이름을 붙인 것이다. 코드를 그대로 복사하는 템플릿이 아니라 상황에 맞게 다시 구현하는 생각의 틀이다. 팀 안에서는 긴 설계 설명을 짧은 이름으로 주고받는 공용 어휘 역할도 한다.

### GoF 패턴은 어떻게 분류되나요?

목적에 따라 생성, 구조, 행위 세 갈래로 나눈다. 생성은 객체를 만드는 방식, 구조는 객체를 엮어 더 큰 구조를 만드는 방식, 행위는 객체들이 책임을 나누고 소통하는 방식을 다룬다. 범위에 따라 상속으로 정해지는 클래스 패턴과 런타임 조합으로 정해지는 객체 패턴으로도 나누는데, 23개 중 클래스 패턴은 팩토리 메서드, 클래스 어댑터, 인터프리터, 템플릿 메서드뿐이다.

### 상속보다 합성을 선호하라는 말은 왜 나왔나요?

상속은 컴파일 시점에 관계가 고정되고 상위 클래스의 내부 변화에 하위 클래스가 깨지기 쉽다. 여러 축으로 기능이 늘면 하위 클래스가 곱으로 폭발한다. 합성은 런타임에 객체를 바꿔 끼울 수 있고 축마다 독립적으로 늘어나 수가 합으로만 는다. 데코레이터, 전략, 브리지가 이 원칙을 구현한 패턴이다.

### 디자인 패턴과 SOLID는 어떤 관계인가요?

SOLID는 지켜야 할 원칙이고 패턴은 그 원칙을 특정 상황에서 구현하는 구체적인 구조다. 개방 폐쇄 원칙은 전략, 데코레이터, 팩토리 메서드로, 의존성 역전 원칙은 추상 팩토리와 의존성 주입으로 드러난다. 그래서 패턴을 설명할 때 어떤 원칙을 지키기 위한 것인지 함께 말하면 이해했다는 게 드러난다.

### 함수형 스타일이 있는 언어에서도 디자인 패턴이 필요한가요?

생각은 필요하지만 형태는 많이 단순해진다. 함수가 일급 값이면 전략은 함수 표로, 커맨드는 클로저로, 이터레이터는 제너레이터로 쓸 수 있다. 노빅은 23개 중 16개가 동적 언어에서 훨씬 단순해진다고 정리했다. 다만 상태를 가진 객체나 여러 메서드가 함께 바뀌는 경우에는 클래스 형태가 여전히 읽기 좋다.

### 디자인 패턴을 쓰지 말아야 할 때는 언제인가요?

대비하려는 변화가 아직 일어나지 않았을 때다. 패턴은 간접 층을 하나 더 두기 때문에 변화가 오지 않으면 코드만 어렵게 만든다. 같은 종류의 변경이 두세 번 실제로 일어난 뒤에 꺼내고, 프레임워크가 이미 해 주는 일을 다시 만들지 않는다.
