"API 응답이 평소의 세 배다"라는 알림이 왔다. 대시보드는 CPU 사용률 80% 언저리만 보여 주고, 무엇이 그 80%를 쓰는지는 말해 주지 않는다. 서버에 SSH로 들어왔다. 이제 무엇부터 칠까.

여기서 아무 명령이나 치기 시작하면 시간만 간다. `top`을 띄워 놓고 숫자가 바뀌는 걸 구경하다 보면 5분이 지나 있다. Brendan Gregg가 Netflix에서 정리한 "60초 안에 리눅스 성능 분석하기"는 이 첫 1분을 위한 순서다. 명령 열 개를 정해진 순서로 치면서 CPU, 메모리, 디스크, 네트워크 중 어디가 넘치는지, 그리고 누가 그러는지까지 좁힌다. 무엇을 잴지의 틀(자원마다 사용률, 포화, 오류를 묻는 USE)은 [모니터링 기본 글](/posts/monitoring-basics)에 있고, 이 글은 그 틀을 서버 안에서 명령으로 채우는 쪽이다.

실습은 Ubuntu 24.04 사용자 공간에 6.18 커널이 올라간 4코어 가상 머신에서 했다. `mpstat`, `pidstat`, `iostat`, `sar`는 `sysstat` 패키지에 있다(`sudo apt install sysstat`, RHEL 계열은 `sudo dnf install sysstat`). 상황을 만들려고 세 가지를 함께 띄웠다. JSON을 계속 직렬화하는 node 스크립트(`report.js`, 단일 스레드), 4KiB를 쓸 때마다 `fsync`하는 `fio` 작업(백업 흉내), 그리고 작은 HTTP 서버와 그걸 계속 두드리는 `curl` 반복문이다. 이 VM은 다른 작업과 함께 쓰는 머신이라 내가 띄우지 않은 프로세스도 출력에 보인다. 현장의 서버도 대개 그렇다.

이 글은 앞의 두 글, [가상 메모리와 페이징](/posts/virtual-memory-paging)과 [페이지 캐시와 디스크 I/O](/posts/page-cache-disk-io)에서 본 숫자들을 한 번에 훑는 순서다. 각 숫자의 자세한 뜻은 그 글들에 있다.

## 1분 동안 치는 열 줄

순서는 이렇다. 앞의 것일수록 넓게 보고, 뒤로 갈수록 범위를 좁힌다.

```bash
uptime                 # 1. 부하가 오르는 중인가, 내리는 중인가
sudo dmesg -T | tail   # 2. 커널이 이미 남긴 경고 (OOM, I/O 오류, 연결 거절)
vmstat 1 5             # 3. CPU 대기열, 막힌 프로세스, 스왑, CPU 시간 나눔
mpstat -P ALL 1 3      # 4. 코어별로 고르게 쓰는가
pidstat 1 3            # 5. 누가 CPU를 쓰는가
iostat -xz 1 3         # 6. 디스크가 넘치는가
free -m                # 7. 메모리가 실제로 모자란가
sar -n DEV 1 3         # 8. 네트워크 처리량
sar -n TCP,ETCP 1 3    # 9. TCP 연결 수와 재전송
top                    # 10. 위에서 본 것을 한 화면으로 다시 확인
```

## 부하가 오르는 중인가 내리는 중인가

```bash
uptime
```

```text
 00:49:43 up  1:17,  0 user,  load average: 2.46, 2.70, 3.45
```

세 숫자는 1분, 5분, 15분 지수 이동 평균이다. 보는 건 크기보다 방향이다. 1분 값이 15분 값보다 크면 부하가 오르는 중이고, 작으면 이미 지나가는 중이다. 여기서는 2.46 < 3.45라 15분 전에 더 바빴다. 장애가 이미 끝나 가는 중이라면, 지금 서버를 붙잡고 볼 것보다 지나간 기록(`sar`의 과거 파일, 모니터링 그래프)을 볼 차례다.

리눅스의 load average는 CPU에서 돌거나 돌 차례를 기다리는 프로세스(`R`)에 더해 디스크나 NFS를 기다리는 프로세스(`D`)도 센다. 그래서 load가 높다고 CPU가 바쁜 건 아니다. 무엇을 세는지 그림으로 보면 이렇다.

두 번째 명령이 커널 로그인 이유는 간단하다. 성능 문제의 몇몇 원인은 커널이 이미 이름을 붙여 남겨 두기 때문이다. OOM kill, 디스크 I/O 오류(`blk_update_request: I/O error`), 파일 시스템이 읽기 전용으로 바뀐 기록, `TCP: request_sock_TCP: Possible SYN flooding`, `nf_conntrack: table full, dropping packet` 같은 줄이 보이면 그쪽부터 간다. 이번 로그의 OOM은 20분 전 다른 실험의 흔적이고([가상 메모리 글](/posts/virtual-memory-paging)에서 일부러 만든 것이다), 시각이 지금 장애와 맞지 않으니 넘어간다. `-T`를 붙이면 부팅 후 초 대신 벽시계 시각이 나와서 장애 시각과 맞춰 보기 쉽다. 일반 사용자는 `dmesg`가 막혀 있을 수 있으니 `sudo`를 붙이거나 `journalctl -k`를 쓴다.

이번 상황을 읽으면 이렇다. `r`이 3에서 13까지 오가니 4코어를 넘는 순간이 있다. `b`가 0이 아닌 줄이 있고 `wa`가 4~18%다. 디스크를 기다리는 일이 있다. `sy`가 16~23%로 높은 건 `curl` 반복문이 초당 백 번 넘게 프로세스를 만들고 `fio`가 쓸 때마다 시스템 콜을 부르기 때문이다. `si`/`so`는 0이라 메모리는 깨끗하다. 이 한 줄로 후보가 CPU와 디스크 둘로 좁혀졌다.

`wa`를 읽을 때는 조심한다. CPU가 다른 일로 바쁘면 I/O를 기다리는 작업이 있어도 `wa`로 잡히지 않는다. 그래서 `wa`가 낮다고 디스크가 괜찮다는 뜻은 아니고, 디스크는 6번의 `iostat`에서 따로 본다.

전체 평균(`all`)만 보면 사용자 시간 61%라 아직 여유가 있어 보인다. 코어별로 보면 2번이 `%usr` 98%로 꽉 찼다. 한 코어만 붙어 있는 모양은 단일 스레드 병목의 신호다. node의 이벤트 루프, Redis의 명령 처리, 락 하나를 잡고 도는 스레드가 이렇게 보인다. 코어를 더 붙여도 이런 병목은 풀리지 않는다. 그 스레드가 하는 일을 줄이거나 나눠야 한다. node라면 무거운 계산이 이벤트 루프를 붙잡는 이야기가 [이벤트 루프 글](/posts/event-loop)에 있다.

3번 코어는 `%soft`가 15%다. 소프트 인터럽트 처리 시간인데, 여기서는 루프백으로 오가는 패킷 처리로 보인다. 네트워크 패킷이 많은 서버에서 `%soft`가 코어 하나에만 몰리면 NIC 수신 큐가 한 코어로만 들어오는 것이고, RSS(Receive Side Scaling)나 RPS로 나눈다.

CPU 쪽 칸은 UID, PID, `%usr`, `%system`, `%guest`, `%wait`, `%CPU`, CPU 번호, 이름 순이다. 출력을 `%CPU`로 정렬해 위 몇 줄만 남겼다. 98%짜리 node가 둘이다. 637이 내가 띄운 `report.js`이고, 12661은 같은 VM에서 다른 작업이 띄운 node다. 둘 다 `%system`이 0이고 `%usr`만 98%라 순수하게 JavaScript를 계산하고 있다. `top`과 달리 `pidstat`은 몇 초씩 지나간 값을 계속 쌓아 줘서, 잠깐 떴다 사라지는 프로세스까지 기록으로 남는다.

`%wait`는 실행할 준비가 됐는데 CPU를 못 받아 기다린 시간의 비율이다. `fio`가 24%다. `r`이 코어 수를 넘는 순간마다 누군가는 이렇게 기다린다. `%wait`가 큰 프로세스가 지연에 민감한 서비스라면 그게 응답이 늦어지는 직접 이유가 된다.

디스크 쪽(`-d`)에서는 `fio`가 초당 29MB를 쓰고 있다. 여기서 범인 후보 둘이 이름을 얻었다. CPU의 node, 디스크의 fio.

칸이 길어서 대기 시간과 병합 칸은 `...`로 줄였다(원래 출력의 `w_await`는 0.08, `r_await`는 0.20이었다). `-z`는 아무 일도 안 한 장치를 빼 준다. 첫 보고는 `vmstat`처럼 부팅 이후 평균이라 버리고, 둘째 보고부터 읽는다.

`w/s`가 9,906인데 `f/s`가 4,484다. 쓰기 두 번에 flush가 한 번꼴이다. 4KiB씩 쓰고 매번 `fsync`하는 `fio` 작업의 모습 그대로다. 쓰기 크기(`wkB/s ÷ w/s`)가 2KiB 남짓으로 작은 것도 같은 이야기다. `d/s`는 discard(TRIM) 요청인데, 이 루트 파일 시스템은 `discard` 옵션으로 마운트되어 있어서 파일을 지울 때마다 장치에 discard가 나간다. 같은 VM의 다른 작업이 파일을 지운 몫으로 보인다.

`%util`이 84%라도 이 virtio 디스크는 요청을 병렬로 처리하니 포화라고 단정하지 않는다. 대기 시간이 0.1ms 안팎으로 짧고 `aqu-sz`도 1.8이다. 디스크 자체는 아직 버티고 있고, 문제는 `fsync`를 너무 자주 부르는 쓰는 쪽의 패턴이다. 각 칸을 읽는 법과 `%util`의 함정은 [페이지 캐시와 디스크 I/O 글](/posts/page-cache-disk-io)에서 실측과 함께 다뤘다.

## 기다린 시간을 한 파일로 본다: PSI

열 줄 목록이 만들어진 2015년 뒤에 리눅스에 들어온 게 PSI(Pressure Stall Information, 커널 4.20 이상)다. 자원 때문에 일이 멈춘 시간의 비율을 CPU, 메모리, I/O별로 한 파일씩 보여 준다. 사용률이 아니라 포화를 바로 잰다는 점에서 USE의 S 칸에 딱 맞는다.

```bash
for r in cpu io memory; do echo "== $r"; cat /proc/pressure/$r; done
```

```text
== cpu
some avg10=11.29 avg60=7.10 avg300=10.14 total=898363510
full avg10=0.00 avg60=0.00 avg300=0.00 total=0
== io
some avg10=19.49 avg60=11.08 avg300=4.52 total=172328865
full avg10=15.82 avg60=9.04 avg300=3.62 total=106230354
== memory
some avg10=0.00 avg60=0.00 avg300=0.00 total=24133
full avg10=0.00 avg60=0.00 avg300=0.00 total=23975
```

`some`은 최소 한 작업이 그 자원을 기다리며 멈춘 시간의 비율, `full`은 실행할 수 있는 작업 전부가 멈춘 시간의 비율이다. `avg10`/`avg60`/`avg300`은 10초, 1분, 5분 평균이고 단위는 %다. 지난 10초 동안 19.5%의 시간에 누군가 I/O를 기다렸고, 15.8%의 시간에는 모두가 I/O에 막혀 있었다. CPU는 11%의 시간에 누군가 코어를 기다렸다. 메모리는 0이다. 열 줄을 다 친 결론과 같은 그림이 파일 세 개에 들어 있다. 쿠버네티스 노드나 systemd의 cgroup 디렉터리마다 같은 이름의 파일(`cpu.pressure` 등, cgroup v2)이 있어서 컨테이너 단위로도 볼 수 있다.

## 뜨거운 함수까지 내려간다

어느 프로세스인지 알았으면, 그 프로세스가 어느 함수에서 시간을 쓰는지 볼 차례다. `perf`(`linux-tools-$(uname -r)` 패키지)로 1초에 99번씩 스택을 찍는다. node는 JIT으로 만든 코드라 그냥은 이름이 안 나오므로, `--perf-basic-prof`로 띄워 함수 이름 표를 `/tmp/perf-<PID>.map`에 남기게 했다.

```bash
# 99Hz로 5초 동안 637번 프로세스의 스택을 모은다
sudo perf record -F 99 -g -p 637 -o perf.data -- sleep 5

# 자기 시간(self) 기준으로 함수 순위
sudo perf report -i perf.data --stdio --no-children -g none --sort symbol | head
```

## 증상마다 먼저 보는 칸

이번 상황은 CPU와 디스크였지만 다른 날에는 다른 줄이 빛난다. 자주 만나는 모습을 정리하면 이렇다.

| 증상 | 먼저 보는 곳 | 그다음 |
|---|---|---|
| CPU 포화 | `vmstat` r이 코어 수보다 계속 큼, PSI cpu some | `pidstat`으로 누구인지, `perf`로 어느 함수인지 |
| 단일 스레드 병목 | `mpstat`에서 한 코어만 100% | `top -H`로 스레드, 이벤트 루프·락 의심 |
| 디스크 포화·fsync 과다 | `vmstat` b, `iostat` await·aqu-sz·f/s | `pidstat -d`, D 상태 프로세스의 wchan |
| 메모리 압박 | `vmstat` si·so, `sar -B` majflt·pgscand, PSI memory | `dmesg`의 OOM, 프로세스별 RSS |
| 네트워크 | `sar -n DEV` 처리량, `sar -n TCP,ETCP` retrans | `ss -ti`, tcpdump |
| 이웃이 시끄러운 VM | `vmstat`·`mpstat`의 st | 인스턴스 유형, 호스트 이동 |

이 표의 앞 칸이 "60초"에 들어가는 숫자이고, 뒤 칸은 그 숫자가 가리키는 곳을 파고드는 다음 단계다. 계층별로 네트워크 장애를 좁히는 순서는 [OSI 7계층을 현장에서 쓰는 글](/posts/osi-in-practice)에서 따로 다룬다.

## 점검하다 자주 하는 실수

- 첫 줄을 읽는다. `vmstat`, `iostat`, `mpstat`의 첫 보고는 부팅 이후 평균이다. 지금을 보려면 간격을 주고 둘째 보고부터 읽는다(`iostat -y`는 첫 보고를 생략한다).
- 평균만 본다. 4코어 평균 61%는 한 코어가 98%인 걸 숨겼다. `mpstat -P ALL`과 `top`의 `1`을 습관처럼 본다.
- `wa`로 디스크를 판단한다. `wa`는 CPU 시간의 한 갈래라, CPU가 바쁘면 I/O 대기가 있어도 작게 나온다. 디스크는 `iostat`과 `b` 칸, PSI io로 본다.
- `top`만 띄워 놓고 바라본다. 짧게 떴다 사라지는 프로세스는 한 화면에 잡히지 않는다. 이번에도 몇 초 사이에 다른 작업의 node가 다른 PID로 바뀌어 있었다. `pidstat` 1초 간격 기록이나 `sar`의 과거 기록이 더 많은 걸 말해 준다.
- 장애가 끝난 뒤에 들어와서 "아무 이상 없다"고 결론 낸다. `uptime`의 1분 값이 15분 값보다 작으면 이미 지나간 것이다. `sysstat`의 수집(`/etc/default/sysstat`에서 `ENABLED="true"`, 10분 간격 기본)을 미리 켜 두면 `sar -f /var/log/sysstat/sa<일>`로 지난 시각을 되돌려 볼 수 있다.
- 원인을 고치기 전에 프로세스를 재시작한다. 증상은 사라지지만 `perf`로 볼 기회도 함께 사라진다. 급하면 먼저 1분짜리 기록(`pidstat`, `iostat`, `perf record`)을 남기고 재시작한다.

열 줄을 다 쳤을 때 손에 남는 건 "어느 자원이, 누구 때문에"라는 두 단어다. 이번에는 "CPU, 단일 스레드 node의 JSON 복사"와 "디스크, 쓸 때마다 fsync하는 작업"이었다. 순서가 중요한 건 넓게 보고 좁혀 가기 때문이다. `uptime`과 `dmesg`로 시간과 이미 남은 증거를, `vmstat`으로 서버 전체를, `mpstat`과 `pidstat`으로 코어와 프로세스를, `iostat`·`free`·`sar`로 나머지 자원을 지우고, 마지막에 `perf`로 함수까지 내려간다. 각 숫자가 왜 그렇게 움직이는지는 [가상 메모리 글](/posts/virtual-memory-paging)과 [페이지 캐시 글](/posts/page-cache-disk-io)에서, 지표를 미리 모아 두는 쪽은 [모니터링 기본 글](/posts/monitoring-basics)에서 이어서 볼 수 있다.

## 면접에서 나올 만한 질문

### 서버가 느리다는 연락을 받으면 무엇부터 보나요?

넓은 데서 좁은 데로 정해진 순서로 본다. `uptime`으로 부하의 방향, `dmesg`로 커널이 남긴 OOM이나 I/O 오류, `vmstat 1`로 실행 대기열·막힌 프로세스·스왑·CPU 시간 나눔을 보고, `mpstat -P ALL`, `pidstat`, `iostat -xz`, `free -m`, `sar -n DEV`, `sar -n TCP,ETCP`로 자원과 프로세스를 좁힌 뒤 `top`으로 확인한다. 1분 안에 "어느 자원이, 누구 때문에"까지 가는 게 목표이고, 그다음에 `perf` 같은 도구로 함수까지 내려간다.

### load average가 8인데 CPU 사용률은 30%입니다. 어떻게 해석하나요?

리눅스 load average는 CPU를 쓰거나 기다리는 `R` 프로세스뿐 아니라 디스크나 NFS를 기다리는 `D` 프로세스도 센다. 그래서 CPU가 놀아도 I/O에 막힌 프로세스가 많으면 load가 높다. `vmstat`의 `b` 칸과 `ps`의 `D` 상태 프로세스, 그 `wchan`을 보고, `iostat -x`의 대기 시간과 대기열로 디스크 쪽인지 확인한다. 코어 수와 함께 1·5·15분 값의 방향도 본다.

### vmstat에서 무엇을 먼저 보나요? 첫 줄은 왜 버리나요?

`r`(실행 대기열, 코어 수와 비교), `b`(I/O에 막힌 프로세스), `si`/`so`(스왑 입출력), `us`/`sy`/`wa`/`st`(CPU 시간 나눔)를 먼저 본다. 첫 줄은 부팅 이후 평균이라 지금 상태가 아니어서 간격을 주고 둘째 줄부터 읽는다. `st`가 꾸준히 몇 % 넘으면 가상 머신의 이웃이 CPU를 가져가고 있다는 뜻이다.

### iowait가 낮으면 디스크는 문제가 없나요?

아니다. iowait는 CPU가 놀면서 마침 I/O를 기다리는 작업이 있던 시간이라, CPU가 다른 일로 바쁘면 I/O 대기가 있어도 작게 나온다. 디스크는 `iostat -x`의 `await`, `aqu-sz`, `f/s`와 `vmstat`의 `b`, `/proc/pressure/io`로 직접 본다. iowait는 CPU 시간의 한 갈래일 뿐 디스크 포화를 재는 지표가 아니다.

### 전체 CPU 사용률은 60%인데 응답이 느립니다. 무엇을 의심하나요?

평균이 한 코어의 포화를 숨기고 있을 수 있다. `mpstat -P ALL`에서 한 코어만 100%면 단일 스레드 병목이고, node의 이벤트 루프나 Redis, 락을 잡은 스레드가 흔한 원인이다. `top -H`나 `pidstat -t`로 어느 스레드인지 찾고, `perf record`로 그 스레드가 어느 함수에서 시간을 쓰는지 본다. 이 경우 코어를 늘려도 나아지지 않는다.

### PSI는 무엇이고 기존 지표와 무엇이 다른가요?

커널 4.20부터 있는 Pressure Stall Information으로, CPU·메모리·I/O 때문에 작업이 멈춘 시간의 비율을 `/proc/pressure/*`에 보여 준다. 사용률이 아니라 "기다리느라 잃은 시간"을 직접 재서 포화를 판단하기 좋다. `some`은 일부 작업이, `full`은 모든 작업이 멈춘 비율이고, cgroup v2에서는 컨테이너마다 같은 파일이 있어 쿠버네티스나 systemd-oomd 같은 도구가 이 값을 보고 판단한다.

### 범인 프로세스를 찾은 뒤에는 어떻게 원인 함수까지 가나요?

`perf record -F 99 -g -p <PID>`로 짧게 스택을 샘플링하고 `perf report`나 불꽃 그래프로 본다. JIT을 쓰는 런타임은 심볼 표가 필요해서 node는 `--perf-basic-prof`, JVM은 별도 에이전트 같은 준비가 있어야 함수 이름이 나온다. 이번 실습에서는 495개 샘플 중 위쪽을 V8의 JSON 파서와 직렬화기가 차지했고, 스택 위에서 `renderReport`가 나와 고칠 곳이 정해졌다.

### 장애가 이미 지나간 뒤 원인을 찾으려면?

지나간 시각의 기록이 있어야 한다. `sysstat` 수집을 켜 두면 `sar -f /var/log/sysstat/sa<일>`로 그 시각의 CPU, 메모리, 디스크, 네트워크를 되돌려 볼 수 있고, `dmesg -T`나 `journalctl -k --since`로 커널 로그를 시각에 맞춰 본다. 평소에 Prometheus 같은 모니터링으로 같은 지표를 모아 두는 게 근본적인 답이다. 장애 중이라면 재시작하기 전에 1분짜리 기록부터 남긴다.
