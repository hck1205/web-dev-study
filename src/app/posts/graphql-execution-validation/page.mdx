<EasyIntro>
  GraphQL 서버는 주문서를 받으면 세 번에 나눠 일한다. 먼저 글자를 읽어 문장 구조를 파악하고, 다음으로 그 주문이 메뉴판에 있는 것만 시켰는지 꼼꼼히 확인하고, 마지막으로 실제 요리를 시작한다. 앞의 두 단계에서 틀린 게 보이면 요리는 아예 시작하지 않는다.

  요리 단계에서는 여러 요리사가 동시에 움직인다. 한 요리사가 늦어도 다른 요리사는 기다리지 않고 자기 일을 한다. 대신 접시에 담을 때는 주문서에 적힌 순서대로 놓는다.

  어떤 요리가 실패하면 그 자리를 비워 두고 쪽지에 "여기서 실패했다"고 적는다. 그런데 메뉴판에 "이 칸은 절대 비면 안 된다"고 적혀 있으면, 그 칸이 든 쟁반을 통째로 비운다. 그래서 작은 실패 하나가 큰 쟁반을 비우기도 하고, 쪽지에 적힌 실패의 개수도 요리사들이 얼마나 빨랐는지에 따라 달라진다.
</EasyIntro>

상품 상세 화면 아래 "함께 본 상품" 영역이 가끔 통째로 사라진다. 추천 서비스 로그를 보면 정상적으로 상품 세 개를 돌려줬다. 응답을 열어 보니 이렇다.

```text
{"errors":[{"message":"가격 서비스 시간 초과","locations":[{"line":1,"column":13}],"path":["recs",1,"price"]}],"data":{"recs":null}}
```

1번 상품의 가격 하나가 시간 초과였을 뿐인데 상품 세 개가 모두 사라졌다. 스키마는 `recs: [Product!]`, `Product.price: Int!`였다. 목록을 `[Product]`로 바꾸면 이렇게 온다.

```text
{"errors":[{"message":"가격 서비스 시간 초과","locations":[{"line":1,"column":14}],"path":["recs2",1,"price"]}],"data":{"recs2":[{"id":"1","price":100},null,{"id":"3","price":300}]}}
```

가운데 하나만 null이고 나머지 둘은 산다. 이 차이는 GraphQL 실행기가 결과를 만드는 규칙에서 나온다. 스키마 쪽에서 느낌표를 어디에 붙일지는 [GraphQL 스키마 설계](/posts/graphql-schema-type-system)에서 다뤘으니, 이 글은 실행기 안쪽에서 그 규칙이 어떻게 돌아가는지를 graphql-js 16.14로 따라간다. 리졸버가 무엇이고 N+1이 왜 생기는지는 [GraphQL 기초](/posts/graphql-basics)에 있다.

## 요청 하나가 지나는 세 단계

GraphQL 명세는 요청 처리를 세 단계로 나눈다. 문서를 읽어 나무 구조(AST)로 바꾸는 파싱, 그 나무가 스키마에 맞는지 보는 검증, 그리고 실제로 리졸버를 부르는 실행이다. graphql-js의 `graphql()` 함수도 안에서 `parse`, `validate`, `execute`를 차례로 부른다. 서버 라이브러리(Apollo Server, graphql-yoga, graphql-http)는 이 셋을 따로 불러 사이에 캐시와 플러그인을 끼운다.

세 단계를 나누는 이유는 실패를 싸게 하려는 것이다. 앞의 두 단계는 문서와 스키마만 보고 데이터는 건드리지 않는다. 여기서 막히면 DB는 한 번도 불리지 않는다. 아래 그림에서 단계를 넘기며 어디서 무엇이 결정되는지 보자.

명세는 두 종류의 에러를 구분한다. 파싱, 검증, 변수 변환에서 나는 에러는 요청 에러(request error)라서 실행 자체가 없고 응답에 `data` 키가 없다. 실행 중 리졸버에서 나는 에러는 필드 에러(field error)라서 그 필드를 null로 만들고 실행은 계속된다. 클라이언트가 "data가 아예 없는가, null인가"로 이 둘을 구분한다.

```text
검증 에러   {"errors":[{"message":"Cannot query field \"nope\" on type \"Order\". Did you mean \"note\"?","locations":[{"line":1,"column":11}]}]}
필드 에러   {"errors":[{"message":"a 실패","locations":[...],"path":["order","a"]}],"data":{"order":null}}
```

검증 에러에는 `path`가 없다. 아직 응답 나무가 없으니 가리킬 경로도 없다. 문서 안의 위치(`locations`)만 있다.

## 파싱은 문자열을 나무로 바꾼다

파싱 결과는 이런 모양이다.

```js
const doc = parse(`query OrderPage($id: ID!) { order(id: $id) { id status items { name qty } shipping { carrier eta tracking } buyer { name } } }`);
doc.definitions.length;                       // 1
doc.definitions[0].kind;                      // "OperationDefinition"
doc.definitions[0].operation;                 // "query"
doc.definitions[0].name.value;                // "OrderPage"
doc.definitions[0].selectionSet.selections;   // [Field order]
```

노드마다 원래 문서의 위치(`loc`)가 붙어 있어서 뒤 단계의 에러가 `"locations":[{"line":1,"column":11}]`처럼 줄과 칸을 가리킬 수 있다.

파싱은 빠르다. 위 126글자짜리 문서를 2만 번 파싱해 평균을 냈더니 한 번에 13.7µs였다. 하지만 문서 크기에 비례해 늘어나니 공격자가 거대한 문서를 보내면 파싱만으로도 CPU를 쓴다. graphql-js는 `parse(source, { maxTokens })` 옵션으로 토큰 수가 한도를 넘으면 그 자리에서 멈춘다.

```text
parse(3000개 필드 문서, { maxTokens: 1000 })
Syntax Error: Document contains more that 1000 tokens. Parsing aborted.
```

("more that"는 graphql-js 메시지 그대로다.) 이 한도는 HTTP 본문 크기 제한과 함께 건다. 본문 크기는 바이트를, `maxTokens`는 문서 구조를 막는다.

## 검증 규칙 27개

graphql-js 16.14의 `specifiedRules`에는 규칙이 27개 들어 있다. 이름만 봐도 무엇을 보는지 알 수 있다.

```text
ExecutableDefinitionsRule, UniqueOperationNamesRule, LoneAnonymousOperationRule,
SingleFieldSubscriptionsRule, KnownTypeNamesRule, FragmentsOnCompositeTypesRule,
VariablesAreInputTypesRule, ScalarLeafsRule, FieldsOnCorrectTypeRule,
UniqueFragmentNamesRule, KnownFragmentNamesRule, NoUnusedFragmentsRule,
PossibleFragmentSpreadsRule, NoFragmentCyclesRule, UniqueVariableNamesRule,
NoUndefinedVariablesRule, NoUnusedVariablesRule, KnownDirectivesRule,
UniqueDirectivesPerLocationRule, KnownArgumentNamesRule, UniqueArgumentNamesRule,
ValuesOfCorrectTypeRule, ProvidedRequiredArgumentsRule, VariablesInAllowedPositionRule,
OverlappingFieldsCanBeMergedRule, UniqueInputFieldNamesRule, MaxIntrospectionDepthRule
```

마지막 `MaxIntrospectionDepthRule`은 명세에 있는 규칙이 아니라 graphql-js가 introspection 쿼리를 깊게 중첩하는 공격을 막으려고 더한 것이다. 나머지는 명세의 Validation 절과 대응한다. 한 번에 여러 규칙에 걸리면 에러도 여러 개 온다.

```text
query OrderPage($id: ID!, $x: Int) { order(id: $id) { id staus items } }

Cannot query field "staus" on type "Order". Did you mean "status" or "items"?       (FieldsOnCorrectTypeRule)
Field "items" of type "[Item!]!" must have a selection of subfields. Did you mean "items { ... }"?   (ScalarLeafsRule)
Variable "$x" is never used in operation "OrderPage".                               (NoUnusedVariablesRule)
```

검증이 하는 일을 실행 쪽에서 보면 "실행기가 믿고 달릴 수 있게 해 주는 것"이다. 검증을 통과한 문서라면 실행기는 모르는 필드, 모자란 인자, 타입이 안 맞는 변수 자리를 만날 일이 없다. 그래서 실행기 코드에는 이런 경우를 따로 처리하는 분기가 거의 없다. 반대로 검증을 건너뛰고 실행하면 이상한 문서가 실행기 깊은 곳에서 엉뚱하게 실패한다. 서버 라이브러리가 검증 끄기 옵션을 주더라도 끄지 않는다.

### 검증은 생각보다 비싸다

같은 문서로 세 단계를 2만 번씩 돌려 평균을 냈다. 리졸버는 메모리 값을 바로 돌려주는 동기 함수다.

```text
parse 13.7us validate 238.7us execute(sync) 34.8us
```

검증이 실행보다 7배 가까이 걸렸다. 규칙 27개가 나무를 훑고, 그중 `OverlappingFieldsCanBeMergedRule`은 같은 응답 키로 합쳐질 필드 쌍을 비교하느라 특히 무겁다. 리졸버가 DB를 부르는 실제 서비스에서는 실행 시간이 훨씬 크겠지만, 캐시 히트처럼 실행이 가벼운 요청에서는 검증이 시간의 대부분이 될 수 있다. 별칭 2000개를 붙인 72KB 문서는 검증에만 58.6ms가 걸렸다.

다행히 검증 결과는 문서와 스키마에만 달려 있고 변수 값과는 상관없다. 그래서 같은 문서 문자열의 파싱·검증 결과는 캐시할 수 있다. graphql-yoga의 파서·검증 캐시, Apollo Server의 문서 캐시가 이 일을 한다. 변수를 써서 문서를 고정해야 하는 이유가 여기서 또 나온다. 문자열을 조립하면 요청마다 다른 문서가 되어 캐시가 한 번도 맞지 않는다. 쿼리 문법 쪽 이야기는 [GraphQL 쿼리 문법](/posts/graphql-operations-syntax)에 있다.

깊이 제한이나 비용 제한 같은 서버 보호 장치도 검증 규칙으로 끼운다. `validate(schema, doc, [...specifiedRules, depthLimit])`처럼 규칙 배열에 더하면 실행 전에 막힌다. 직접 만든 깊이 규칙은 [GraphQL 기초](/posts/graphql-basics)에 있다.

## 실행 전에 변수 값부터 맞춘다

검증과 실행 사이에 작은 단계가 하나 더 있다. 명세의 `CoerceVariableValues`다. 검증은 문서만 보니 변수의 실제 값은 모른다. 그래서 실행기는 리졸버를 부르기 전에 변수 값을 선언한 타입으로 한꺼번에 변환하고, 하나라도 맞지 않으면 실행을 시작하지 않는다.

```text
query($id: ID!) { product(id: $id) { id } }   variables: {"id":1.5}
{"errors":[{"message":"Variable \"$id\" got invalid value 1.5; ID cannot represent value: 1.5","locations":[{"line":1,"column":7}]}]}

query($id: ID!) { product(id: $id) { id } }   variables: {"id":1}
  resolver got id "1" string
{"data":{"product":{"id":"1"}}}
```

첫 응답에 `data` 키가 없다. 변수 변환 실패도 요청 에러라서 리졸버가 하나도 불리지 않았다. 둘째 응답에서는 숫자 1이 문자열 `"1"`로 바뀌어 리졸버에 들어갔다. 리졸버는 변환이 끝난 값만 받으니 인자 타입을 다시 검사할 필요가 없다. 커스텀 스칼라의 `parseValue`가 불리는 곳도 여기다. 형식이 틀린 날짜 문자열이 리졸버에 닿지 않는 이유다([GraphQL 스키마 설계](/posts/graphql-schema-type-system)의 스칼라 부분).

이 순서는 클라이언트 쪽 디버깅에 쓸모가 있다. 응답에 `data` 키가 아예 없으면 서버 로그에서 리졸버를 찾을 필요가 없다. 문서나 변수가 틀린 것이니 클라이언트가 보낸 본문을 먼저 본다. `data`가 있는데 일부가 null이면 그때 리졸버 쪽을 본다.

## 실행은 필드 단위로 내려간다

실행기가 하는 일은 명세의 세 함수로 요약된다. `CollectFields`는 선택 집합에서 프래그먼트와 디렉티브를 정리해 응답 키 목록을 만든다. `ExecuteField`(그 안의 `ResolveFieldValue`)는 키마다 리졸버를 부른다. `CompleteValue`는 리졸버가 돌려준 값을 필드 타입에 맞게 마무리한다. 스칼라면 직렬화하고, 객체면 그 객체의 선택 집합으로 다시 `CollectFields`부터 반복하고, 리스트면 원소마다 반복하고, non-null이면 null인지 본다.

리졸버를 따로 정의하지 않은 필드는 기본 리졸버가 처리한다. graphql-js의 기본 리졸버는 부모 객체에서 같은 이름의 속성을 꺼내고, 그게 함수면 `(args, context, info)`로 불러 그 결과를 쓴다.

```text
{ order { id c note } }   rootValue: { order: () => ({ id: 5, c: "property", note: () => "function" }) }
{"data":{"order":{"id":"5","c":"property","note":"function"}}}
```

DB 행을 그대로 부모 객체로 넘기면 열 이름과 필드 이름이 같은 필드에는 리졸버를 쓸 필요가 없는 이유다. 열 이름이 `created_at`인데 필드가 `createdAt`이면 기본 리졸버는 undefined를 꺼내고, non-null 필드라면 그 자리에서 에러가 된다. 처음 GraphQL 서버를 붙일 때 흔히 걸리는 실수다.

### 리졸버가 받는 네 번째 인자

리졸버의 네 번째 인자 `info`에는 실행기가 지금 어디를 걷고 있는지가 들어 있다. 별칭을 붙인 쿼리에서 리스트 원소의 리졸버가 받은 값을 찍었다.

```js
// 리졸버 안에서
console.log({
  fieldName: info.fieldName,                    // 스키마의 필드 이름
  parentType: String(info.parentType),
  returnType: String(info.returnType),
  path: responsePathAsArray(info.path),         // 응답 안의 위치
  operation: info.operation.name?.value,
  alias: info.fieldNodes[0].alias?.value ?? null,
});
```

```text
query OrderPage { order { items { title: name } } }
{"fieldName":"name","parentType":"Item","returnType":"String!","path":["order","items",0,"title"],"operation":"OrderPage","alias":"title"}
```

`fieldName`은 스키마 이름 `name`인데 `path`의 마지막은 별칭 `title`이다. 실행기는 스키마 쪽 이름으로 리졸버를 찾고, 응답 쪽 이름으로 결과를 놓는다. errors의 path가 별칭으로 찍히는 이유가 여기 있다.

`info`는 운영 도구가 쓰는 재료다. 필드 단위 추적은 `parentType.fieldName`(`Item.name`)으로 리졸버 시간을 모으고, 경로는 원소 인덱스를 빼고(`order.items.title`) 묶어야 지표의 종류가 폭발하지 않는다. `info.fieldNodes`의 하위 선택을 보고 DB에서 필요한 열만 고르는 최적화도 가능하지만, 프래그먼트와 별칭, 디렉티브를 모두 따져야 해서 직접 짜기보다 검증된 라이브러리를 쓰는 편이 안전하다.

## 형제 필드는 서로를 기다리지 않는다

리졸버가 언제 불리고 언제 끝나는지 찍어 봤다. `shipping`은 40ms, `buyer`는 10ms 걸리는 비동기 리졸버이고 나머지는 동기다. 시각은 첫 리졸버가 불린 때를 0으로 맞췄다.

```text
   0ms Query.order
   1ms Order.status
   1ms Order.items
   2ms Order.shipping start
   3ms Order.buyer start
  13ms Order.buyer end
  14ms User.name
  42ms Order.shipping end
  44ms Shipping.carrier
{"data":{"order":{"id":"1","status":"SHIPPED","items":[...],"shipping":{"carrier":"CJ","eta":"10-25"},"buyer":{"name":"kim"}}}}
```

세 가지가 보인다. 첫째, `Order`의 필드들은 위에서부터 차례로 불리지만 하나가 끝나기를 기다리지 않는다. `shipping`이 Promise를 돌려주자 바로 `buyer`를 부른다. 둘째, `buyer`가 먼저 끝나자 `shipping`을 기다리지 않고 바로 `User.name`으로 내려갔다. 실행기는 단계별로 끊어 가는 너비 우선이 아니라, 끝난 가지부터 각자 내려간다. 셋째, 그런데 응답에서는 `shipping`이 `buyer`보다 앞에 있다. 명세는 응답 객체의 키 순서를 선택 집합의 순서로 정하고, 실행 순서와는 떼어 놓았다. 아래 그림에서 단계를 넘기며 대기 중인 Promise가 어떻게 늘고 줄어드는지 보자.

## 동기 리졸버와 비동기 리졸버

graphql-js의 `execute`는 리졸버가 모두 동기 값을 돌려주면 결과도 동기로 돌려준다. Promise가 하나라도 섞이면 결과가 Promise가 된다. 위에서 잰 34.8µs는 모든 리졸버가 동기인 경우다. 비동기 리졸버는 Promise를 만들고 마이크로태스크를 거치는 만큼 조금씩 비싸다. 그래서 메모리에 이미 있는 값을 돌려주는 리졸버까지 습관적으로 `async`로 만들 필요는 없다. 필드가 수천 개인 큰 응답에서는 이 차이가 쌓인다.

`graphqlSync`는 동기 실행을 강제하는 함수다. 비동기 리졸버가 섞인 스키마에 쓰면 이렇게 된다(시각은 같은 방식으로 맞췄다).

```text
   0ms Query.order
   0ms Order.status
   0ms Order.items
   0ms Order.shipping start
   0ms Order.buyer start
throw: GraphQL execution failed to complete synchronously.
  11ms Order.buyer end
  11ms User.name
  40ms Order.shipping end
  41ms Shipping.carrier
```

에러가 던져진 뒤에도 `buyer`와 `shipping`이 끝까지 돌았다. 실행기는 결과를 버렸지만 이미 시작된 Promise를 멈출 방법이 없다. 이 리졸버가 결제나 메일 발송이었다면 응답은 실패인데 부작용은 일어난다. graphql-js 16에는 실행 중인 요청을 취소하는 기능이 없다. 클라이언트가 연결을 끊거나 서버가 타임아웃으로 응답을 끊어도 리졸버는 계속 돈다. 오래 걸리는 리졸버라면 context에 요청의 `AbortSignal`을 넣어 두고 리졸버가 그걸 DB 드라이버나 `fetch`에 넘기게 해야 실제로 멈춘다. 신호를 넘기는 방법은 [AbortController](/posts/abort-controller)에 있다.

2026년 6월에 나온 graphql-js 17은 실행 인자로 `abortSignal`을 받는다. 17.0.2로 100ms 걸리는 리졸버를 실행하다가 20ms에 신호를 보내 봤다.

```js
const ac = new AbortController();
const p = execute({ schema, document: parse(`{ slow other }`), abortSignal: ac.signal, rootValue: {
  slow: async (_a, _c, info) => {
    const s = info.getAbortSignal();   // 리졸버도 같은 신호를 받는다
    await sleep(100);                   // 이 신호를 쓰지 않는 작업
    console.log("slow resolver finished at", Date.now() - t0, "aborted?", s.aborted);
    return "done";
  },
  other: () => "ok",
} });
setTimeout(() => ac.abort(new Error("클라이언트가 연결을 끊었다")), 20);
```

```text
signal in info: true
rejected: 클라이언트가 연결을 끊었다 at 34
slow resolver finished at 110 aborted? true
```

실행 결과 Promise는 34ms에 바로 거부됐다. 그런데 리졸버는 110ms에 끝까지 돌았다. 실행기는 "더 기다리지 않는다"까지만 해 주고, 하던 일을 멈추는 것은 여전히 리졸버 몫이다. 17에서는 context에 신호를 따로 넣지 않아도 `info.getAbortSignal()`로 받을 수 있으니, 이걸 DB 드라이버와 `fetch`에 넘긴다.

## 결과를 만들며 null을 올린다

이제 처음 장면을 실행기 쪽에서 보자. `CompleteValue`가 non-null 타입을 마무리할 때 안쪽 값이 null이면 필드 에러를 만든다. 그 에러는 위로 던져지고, 가장 가까운 nullable 위치를 처리하던 `CompleteValue`가 받아 그 자리를 null로 만들고 errors에 기록한다. 리스트 안의 원소라면 nullable 원소 타입(`[Product]`)일 때 원소 하나에서 멈추고, non-null 원소 타입(`[Product!]`)이면 목록 전체로 올라간다. 처음 두 응답이 정확히 이 차이였다.

errors의 `path`는 응답 키로 적힌다. 별칭을 쓰면 필드 이름이 아니라 별칭이 경로에 들어간다.

```text
{ first: order { x: a } }
{"errors":[{"message":"a 실패","path":["first","x"]}],"data":{"first":null}}
```

클라이언트가 path로 응답 안의 위치를 찾아갈 수 있게 한 설계다. 리스트 원소는 숫자 인덱스로 들어간다(`["recs",1,"price"]`).

### 에러 개수는 실행 순서에 따라 달라진다

한 객체 아래 non-null 필드 둘(`a`, `b`)과 nullable 필드 하나(`c`)가 모두 실패하게 했다. 비동기 쪽은 `a`만 5ms 뒤에 실패한다. 동기 리졸버일 때와 비동기 리졸버일 때 결과가 다르다.

```text
동기    {"errors":[{"message":"a 실패","path":["order","a"]}],"data":{"order":null}}
비동기  {"errors":[{"message":"c 실패","path":["order","c"]},{"message":"b 실패","path":["order","b"]}],"data":{"order":null}}
```

동기일 때는 `a`가 실패하는 순간 `order` 전체가 null로 정해지니 `b`와 `c`는 실행되지도 않았다. 비동기일 때는 셋이 모두 이미 불린 상태다. 바로 실패한 `c`(nullable이라 그 자리만 null)와 `b`(non-null이라 `order`를 null로)가 기록되고, 5ms 뒤에 실패한 `a`의 에러는 이미 null이 된 객체 아래라 버려졌다. graphql-js는 이미 null로 정해진 객체 아래에서 늦게 생긴 에러를 기록하지 않는다.

운영에서 이게 뜻하는 바가 있다. errors 배열의 길이로 "몇 군데가 실패했나"를 정확히 셀 수 없다. 같은 장애라도 리졸버 속도에 따라 에러가 1개로도 2개로도 찍힌다. 에러율 지표는 "errors가 하나라도 있는 응답의 비율"로 잡고, 원인 분석은 서버 쪽 리졸버 로그에서 한다.

## 작은 실행기로 null 전파를 짜 보기

지금까지 본 규칙을 동기 실행기 하나로 짜 보자. 스키마는 필드마다 타입 문자열과(객체라면) 하위 `fields`를 가진 객체로 받고, 루트 값은 그냥 JSON이다. 리졸버가 에러를 던진 자리는 값 대신 `{ error: "메시지" }`로 표시한다. 함수는 `{ data, errors }`를 돌려주고, errors에는 실패한 경로를 `"recs.1.price"`처럼 점으로 이어 넣는다. 에러를 던진 필드와, non-null 필드가 null을 받은 자리가 둘 다 에러다. 동기 실행기처럼 한 객체 안에서 null이 올라오면 남은 형제 필드는 실행하지 않는다.

## 에러 메시지가 밖으로 새는 곳

리졸버가 던진 예외의 메시지는 기본으로 그대로 응답에 실린다.

```text
{"errors":[{"message":"relation \"order_notes\" does not exist","locations":[{"line":1,"column":11}],"path":["order","note"]}],"data":{"order":{"note":null}}}
```

DB 테이블 이름이 클라이언트까지 갔다. SQL 오류, 내부 호스트 이름, 스택의 일부가 이렇게 새어 나간다. graphql-js는 메시지를 가공하지 않으니 서버 계층에서 가려야 한다. 흔한 방식은 두 종류의 에러를 나누는 것이다. 클라이언트에게 보여 줄 에러는 `GraphQLError`로 던지고 `extensions.code`에 기계가 읽을 코드를 넣는다. 그 밖의 예외는 응답에서 "Unexpected error." 같은 일반 메시지로 바꾸고 원래 내용은 서버 로그에만 남긴다.

```text
throw new GraphQLError("권한이 없다", { extensions: { code: "FORBIDDEN" } })
{"errors":[{"message":"권한이 없다","locations":[{"line":1,"column":11}],"path":["order","note"],"extensions":{"code":"FORBIDDEN"}}],"data":{"order":{"note":null}}}
```

graphql-yoga는 기본으로 이렇게 가리고(error masking), Apollo Server는 `formatError` 훅에서 가린다. 클라이언트는 메시지 문자열 대신 `extensions.code`로 분기한다. 메시지는 사람이 읽는 것이라 바뀔 수 있다.

## 구독은 같은 실행기를 이벤트마다 돌린다

뮤테이션이 실행 순서만 다르다면, 구독(subscription)은 실행 횟수가 다르다. 명세상 구독은 두 단계다. 먼저 최상위 필드 하나로 이벤트 원천(source stream)을 만든다. 그다음 이벤트가 올 때마다 그 이벤트를 루트 값으로 삼아 나머지 선택 집합을 평소의 실행 규칙(병렬, null 전파 포함)으로 실행해 결과 하나를 내보낸다.

원천을 만드는 최상위 필드가 하나여야 하므로 검증 규칙 `SingleFieldSubscriptionsRule`이 구독 작업의 최상위 필드를 하나로 제한한다. 구독이 전송 계층과 서버 여러 대에서 어떻게 운영되는지는 [GraphQL 실시간](/posts/graphql-subscriptions-defer)에서 따로 다룬다.

## 실행기를 알면 운영에서 달라지는 것

느린 요청을 볼 때 세 단계를 나눠 잰다. 분산 추적에서 parse, validate, execute를 각각 span으로 남기면(OpenTelemetry의 GraphQL 계측이 이렇게 한다) 실행이 아니라 검증이 느린 요청이 보인다. 매번 문서가 달라 캐시가 안 맞는 클라이언트, 별칭을 수천 개 붙인 문서가 여기서 드러난다.

"데이터가 일부만 왔다"는 신고는 errors의 첫 path에서 시작한다. 그 경로의 필드 타입을 스키마에서 찾고, 거기서부터 위로 올라가며 첫 nullable 조상을 찾으면 왜 그 범위가 비었는지 설명된다. 비어 있는 범위가 너무 크면 그 경로에 붙은 느낌표를 다시 본다.

타임아웃은 응답만 끊는다. 서버가 30초 타임아웃으로 응답을 504로 끊어도 그 요청의 리졸버들은 계속 DB를 부른다. 같은 무거운 요청이 몰리면 응답은 다 실패하는데 DB 부하는 줄지 않는다. 요청 단위 `AbortSignal`을 리졸버까지 내려보내고, DB 쪽에도 문장 타임아웃(PostgreSQL의 `statement_timeout`)을 따로 둔다.

리졸버 사이의 순서에 기대는 코드를 찾아낸다. 테스트에서는 모두 동기 목(mock) 리졸버라 순서가 고정되어 통과하는데, 운영에서는 비동기라 순서가 바뀌어 가끔 틀린 값을 낸다. 이런 버그는 재현이 어렵다. 리졸버가 context에 값을 쓰는 코드가 있으면 의심한다.

## 단계는 나누고, 결과는 순서대로

GraphQL 실행기는 파싱, 검증, 실행 세 단계로 요청을 처리한다. 앞의 두 단계는 문서와 스키마만 보므로 데이터를 건드리지 않고 실패하며, 검증을 통과한 문서는 실행기가 믿고 달린다. 검증은 생각보다 비싸서 문서 단위로 캐시한다. 실행에서 쿼리의 형제 필드는 서로를 기다리지 않고 각자 내려가지만 응답 키는 선택 집합 순서대로 놓인다. 리졸버가 실패하면 그 null은 가장 가까운 nullable 위치까지 올라가고, 이미 null이 된 아래쪽 에러는 버려지므로 errors 개수는 실행 순서에 따라 달라진다. 그리고 실행기가 실행을 버려도 리졸버가 하던 일은 멈추지 않으니(16은 취소 자체가 없고, 17은 abortSignal로 기다리기만 멈춘다) 끊어야 할 일은 리졸버까지 신호를 내려 직접 끊는다.

## 면접에서 나올 만한 질문

### GraphQL 요청은 서버에서 어떤 단계를 거치나요?

파싱, 검증, 실행 세 단계를 거친다. 파싱은 문서 문자열을 AST로 바꾸고, 검증은 그 AST가 스키마에 맞는지 규칙들로 확인하며, 실행은 루트 타입부터 필드를 내려가며 리졸버를 부르고 결과를 만든다. 앞의 두 단계에서 실패하면 요청 에러로 data 키 없이 errors만 돌아오고 데이터는 건드리지 않는다. 실행 중 에러는 필드 에러라 그 필드만 null이 되고 나머지 data는 나간다.

### 검증 단계를 캐시할 수 있는 이유는 무엇인가요?

검증 결과는 문서와 스키마에만 달려 있고 변수 값과는 상관없기 때문이다. 그래서 같은 문서 문자열의 파싱·검증 결과를 재사용할 수 있고, 서버 라이브러리들이 문서 캐시를 둔다. 측정해 보면 작은 쿼리에서도 검증이 실행보다 몇 배 비쌀 수 있어서 효과가 크다. 대신 클라이언트가 값을 문서에 이어 붙이면 요청마다 문서가 달라 캐시가 맞지 않으니 변수를 써야 한다.

### 쿼리의 형제 필드는 어떤 순서로 실행되고, 응답 순서는 어떻게 보장되나요?

실행기는 형제 필드의 리졸버를 차례로 부르지만 Promise가 끝나기를 기다리지 않고 다음 필드로 가므로 비동기 리졸버들은 동시에 진행된다. 먼저 끝난 가지는 다른 가지를 기다리지 않고 바로 하위 필드로 내려간다. 응답 객체의 키 순서는 실행 순서와 상관없이 선택 집합에 처음 나온 순서로 정해진다. 그래서 리졸버끼리 실행 순서에 기대는 코드를 쓰면 안 된다.

### 리졸버 에러가 왜 부모 객체까지 null로 만드나요?

non-null 타입 필드는 null을 담을 수 없으므로, 그 필드의 리졸버가 실패하거나 null을 돌려주면 실행기는 그 null을 한 단계 위로 올린다. 부모도 non-null이면 계속 올라가서 가장 가까운 nullable 위치가 null이 되고, 그 자리에서 errors에 기록한다. 리스트는 원소 타입이 nullable이면 원소 하나에서 멈추고 non-null이면 목록 전체가 null이 된다. 그래서 `[Product!]` 목록에서 가격 하나가 실패하면 목록이 통째로 사라진다.

### 같은 객체 아래 non-null 필드 두 개가 실패하면 errors는 몇 개인가요?

실행 순서에 따라 다르다. 동기 리졸버면 첫 필드가 실패하는 순간 부모가 null로 정해져 나머지 필드는 실행되지 않아 에러가 하나다. 비동기면 이미 불린 리졸버들의 실패가 기록되지만, 부모가 null로 정해진 뒤에 끝난 실패는 버려진다. 그래서 errors 개수로 실패 지점 수를 세지 말고, 에러가 있는 응답의 비율로 지표를 잡는다.

### graphqlSync를 비동기 리졸버가 있는 스키마에 쓰면 어떻게 되나요?

"GraphQL execution failed to complete synchronously." 에러가 던져진다. 그런데 이미 시작된 비동기 리졸버는 멈추지 않고 끝까지 돌아 부작용을 남긴다. graphql-js 16에는 실행 취소 기능이 없어서 타임아웃이나 연결 종료로 응답을 끊어도 같은 일이 생긴다. 17은 abortSignal을 받아 실행 결과를 바로 거부하지만, 그때도 리졸버가 신호를 쓰지 않으면 작업은 끝까지 돈다. 오래 걸리는 리졸버는 그 신호를 DB나 fetch에 넘겨야 실제로 멈춘다.

### 리졸버 에러 메시지를 그대로 내보내면 어떤 문제가 있나요?

graphql-js는 예외 메시지를 그대로 errors에 싣기 때문에 SQL 오류의 테이블 이름이나 내부 호스트 이름이 클라이언트까지 간다. 보여 줄 에러는 GraphQLError로 던지고 extensions.code에 코드를 넣으며, 나머지 예외는 일반 메시지로 가리고 원문은 서버 로그에만 남긴다. graphql-yoga는 기본으로 가리고 Apollo Server는 formatError에서 처리한다. 클라이언트는 메시지가 아니라 코드로 분기한다.
