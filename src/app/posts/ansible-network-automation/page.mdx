<EasyIntro>
  서버 수십 대에 들어가 설정을 하나씩 손으로 고치면 꼭 한 대쯤 빠뜨린다. 그 한 대만 이상하게 굴어도 원인을 찾기까지 한참 걸린다. Ansible은 서버 안의 설정, 방화벽 규칙, 장비의 접근 목록 같은 것을 코드로 적어 두고 여러 대에 똑같이 맞춰 주는 도구다.

  건물 관리인이 점검표를 들고 방마다 들어가는 모습을 떠올리면 된다. 관리인은 방에 들어가 먼저 지금 상태를 살피고, 점검표와 다른 것만 고친다. 그래서 같은 점검을 두 번 돌려도 두 번째에는 고칠 게 없어야 정상이다. 그냥 "규칙 하나 붙여라"를 시키면 돌 때마다 같은 규칙이 한 줄씩 쌓인다.

  여러 방을 한꺼번에 고치면 실수도 한꺼번에 퍼진다. 그래서 먼저 한 방만 바꾸고 바깥에서 문이 잘 열리는지 확인한 뒤, 틀렸으면 그 방을 되돌리고 나머지 방은 손대지 않는다.
</EasyIntro>

웹 서버 40대 중 한 대만 새벽마다 연결이 튄다. 한참 뒤져 보니 그 서버만 `net.core.somaxconn`이 4096이고 나머지는 8192였다. 반년 전 누군가 `sysctl -w`로 39대를 고치고 한 대를 빠뜨렸고, 재부팅된 서버는 값이 날아갔다. 방화벽 규칙도 사정이 비슷해서 `iptables -S`를 서버마다 떠 보면 줄 수가 다 다르다.

클라우드의 VPC나 보안 그룹은 Terraform이 API로 맞춘다([네트워크를 Terraform으로](/posts/terraform-network-iac)). 그런데 서버 안의 커널 값, 호스트 방화벽, 로드 밸런서의 설정 파일, 스위치의 ACL은 API가 아니라 로그인해서 명령을 쳐야 바뀐다. 이 영역을 코드로 맞추는 도구가 Ansible이다. 이 글은 인벤토리와 변수, 모듈과 멱등성, `--check --diff`, 템플릿과 핸들러, 한 대씩 바꾸고 틀리면 되돌리는 롤아웃, 그리고 네트워크 장비 모듈까지 실제로 돌려 본다.

실습은 Ubuntu 24.04에서 ansible-core 2.21.5와 Ansible 14 패키지에 든 컬렉션(ansible.posix, cisco.ios 등)으로 했다. 서버 대신 리눅스 네트워크 네임스페이스 다섯 개(lb1, web1~web3, 클라이언트)를 브리지에 묶었다. 원래 Ansible은 SSH로 접속해 모듈을 실행하는데, 실습에서는 "그 네임스페이스 안에서 python3를 띄우는 작은 스크립트"를 인터프리터로 지정해 SSH를 대신했다. 그 밖의 출력은 모두 실제로 돌린 결과다. iptables와 nftables 자체는 [iptables 기본](/posts/iptables-basics)과 [iptables NAT](/posts/iptables-nat)를 먼저 보면 편하다.

## Terraform이 들어가지 못하는 곳

두 도구는 경계가 꽤 분명하다. Terraform은 클라우드 API가 있는 것(VPC, 서브넷, 보안 그룹, 로드 밸런서 리소스)을 만들고 state로 기억한다. Ansible은 이미 있는 기계에 들어가 그 안의 상태를 맞춘다. state 파일이 없고, 매번 대상의 현재 모습을 직접 확인한 뒤 다른 것만 고친다.

## 인벤토리와 group_vars: 무엇을 어디에 적나

Ansible이 관리할 대상 목록이 인벤토리다. 그룹으로 묶어 두면 그룹마다 다른 값을 줄 수 있다.

```ini
# inventory.ini (실제 서버라면 ansible_host와 ansible_user를 적는다)
[lb]
lb1  netns=n6lb   addr=10.66.0.1

[web]
web1 netns=n6web1 addr=10.66.0.11
web2 netns=n6web2 addr=10.66.0.12
web3 netns=n6web3 addr=10.66.0.13
```

값은 인벤토리 옆의 `group_vars/{그룹}.yml`, `host_vars/{호스트}.yml`에 둔다. 플레이북에는 "무엇을 하는지"만 남기고 "어떤 값으로"는 변수 파일로 뺀다. 그래야 운영과 스테이징이 같은 플레이북을 쓴다.

```yaml
# group_vars/all.yml: 모든 호스트 공통
mgmt_cidr: 10.66.0.0/24
base_sysctls:
  net.ipv4.tcp_syncookies: 1
  net.ipv4.conf.all.rp_filter: 1

# group_vars/web.yml: web 그룹만
allowed_tcp_ports: [22, 8080]
extra_sysctls:
  net.core.somaxconn: 8192

# group_vars/lb.yml: lb 그룹만
extra_sysctls:
  net.ipv4.ip_forward: 1
backends: "{{ groups['web'] | map('extract', hostvars, 'addr') | list }}"
listen_port: 80
```

`backends`가 눈여겨볼 줄이다. LB의 백엔드 목록을 손으로 적지 않고 web 그룹의 주소를 모아 만든다. 인벤토리에 web 서버를 한 줄 더하면 LB 설정이 따라 바뀐다. 한 호스트에 최종으로 어떤 값이 들어가는지는 `ansible-inventory`로 확인한다.

```bash
# 그룹 구조와, 한 호스트에 합쳐진 변수를 본다
ansible-inventory --graph
ansible-inventory --host web2
```

```text
@all:
  |--@ungrouped:
  |--@lb:
  |  |--lb1
  |--@web:
  |  |--web1
  |  |--web2
  |  |--web3
{
    "addr": "10.66.0.12",
    "allowed_tcp_ports": [22, 8080],
    "base_sysctls": {
        "net.ipv4.conf.all.rp_filter": 1,
        "net.ipv4.tcp_syncookies": 1
    },
    "extra_sysctls": {
        "net.core.somaxconn": 8192
    },
    "mgmt_cidr": "10.66.0.0/24",
    ...
}
```

같은 변수가 여러 곳에 있으면 더 구체적인 쪽이 이긴다. 대략 `group_vars/all` < `group_vars/{그룹}` < `host_vars/{호스트}` < 플레이북의 `vars` < 명령줄의 `-e` 순이다(전체 순서는 20단계가 넘는다). 그룹 두 개에 같은 변수를 다르게 두면 그룹 이름 알파벳 순으로 나중 것이 이기는데, 이런 우연에 기대지 않도록 같은 변수는 한 단계에만 둔다.

## 플레이북 한 번 돌리기

플레이북은 "어느 호스트 그룹에, 어떤 작업을, 어떤 순서로"를 적은 YAML이다. 작업 하나하나는 모듈 호출이다. 커널 값은 `ansible.posix.sysctl`, iptables 규칙은 `ansible.builtin.iptables`, 설정 파일은 `ansible.builtin.template`이 맡는다.

```yaml
# site.yml
- name: 커널 네트워크 값
  hosts: all
  tasks:
    - name: sysctl 값을 맞춘다
      ansible.posix.sysctl:
        name: "{{ item.key }}"
        value: "{{ item.value }}"
        sysctl_file: /etc/sysctl.d/90-net.conf   # 재부팅해도 남도록 파일에도 쓴다
        sysctl_set: true                          # 지금 커널 값도 바꾼다
      loop: "{{ base_sysctls | combine(extra_sysctls | default({})) | dict2items }}"

- name: web 방화벽
  hosts: web
  tasks:
    - name: 이미 맺은 연결의 응답은 받는다
      ansible.builtin.iptables:
        chain: INPUT
        ctstate: [ESTABLISHED, RELATED]
        jump: ACCEPT
        comment: ansible-established

    - name: 관리망에서 오는 포트만 연다
      ansible.builtin.iptables:
        chain: INPUT
        protocol: tcp
        source: "{{ mgmt_cidr }}"
        destination_port: "{{ item }}"
        jump: ACCEPT
        comment: "ansible-allow-{{ item }}"
      loop: "{{ allowed_tcp_ports }}"

    - name: 나머지는 버린다
      ansible.builtin.iptables:
        chain: INPUT
        policy: DROP
```

작업 순서가 곧 안전장치다. 허용 규칙을 먼저 넣고 정책을 DROP으로 바꾼다. 순서를 거꾸로 쓰면 정책이 바뀌는 순간 Ansible 자신의 SSH 연결이 끊긴다(이미 맺은 연결은 conntrack 덕에 살 수도 있지만 다음 작업의 새 연결은 막힌다).

<Callout kind="warning">
원격 서버에 방화벽 플레이북을 처음 돌릴 때는 한 대에만(`--limit web1`) 돌리고, 콘솔 접속(클라우드의 시리얼 콘솔, IPMI)이 되는지 먼저 확인한다. 막혔을 때 되돌릴 길은 [iptables 기본](/posts/iptables-basics)의 "백업과 자동 되돌리기 예약"처럼 `at now + 5 minutes`로 이전 규칙을 복원하는 작업을 먼저 걸어 두는 것이다. 확인이 끝나면 `atrm`으로 예약을 지운다.
</Callout>

결과를 직접 확인해 보면 이렇다.

```bash
# web1의 INPUT 체인, 커널 값, lb1의 NAT 테이블을 본다 (실제 서버라면 ssh로 들어가서)
sudo iptables -S INPUT
sysctl net.core.somaxconn
sudo nft list table ip nat
```

```text
-P INPUT DROP
-A INPUT -m conntrack --ctstate RELATED,ESTABLISHED -m comment --comment ansible-established -j ACCEPT
-A INPUT -s 10.66.0.0/24 -p tcp -m tcp --dport 22 -m comment --comment ansible-allow-22 -j ACCEPT
-A INPUT -s 10.66.0.0/24 -p tcp -m tcp --dport 8080 -m comment --comment ansible-allow-8080 -j ACCEPT
net.core.somaxconn = 8192
```

규칙마다 `comment`를 달아 두면 나중에 `iptables -S`를 봤을 때 Ansible이 넣은 줄과 사람이 넣은 줄이 구별된다.

## 두 번째 실행은 아무것도 바꾸지 않아야 한다

같은 플레이북을 곧바로 한 번 더 돌린다.

```text
PLAY RECAP *********************************************************************
lb1                        : ok=4    changed=0    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
web1                       : ok=7    changed=0    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
web2                       : ok=7    changed=0    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
```

모두 `changed=0`이다. 모듈이 먼저 현재 상태를 읽고, 원하는 상태와 같으면 아무것도 하지 않기 때문이다. 이 성질을 멱등성이라 한다. 몇 번을 돌려도 결과가 같으니 스케줄로 매일 돌려도 되고, 중간에 끊긴 실행을 처음부터 다시 돌려도 된다.

같은 일을 `command` 모듈로 하면 이 성질이 사라진다. 9100번을 열려고 `iptables -A`를 그대로 실행하는 작업을 세 번 돌렸다.

```yaml
- name: 9100을 연다 (command로)
  ansible.builtin.command: iptables -A INPUT -p tcp --dport 9100 -j ACCEPT
```

```text

web1                       : ok=2    changed=1    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
web1                       : ok=2    changed=1    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
-P INPUT DROP
...

-A INPUT -p tcp -m tcp --dport 9100 -j ACCEPT
```

## 바꾸기 전에 --check --diff

새 서버 web3를 인벤토리에 한 줄 더했다. 운영에 적용하기 전에 무엇이 바뀔지 먼저 본다. `--check`는 바꾸지 않고 바뀔 것만 보고하고, `--diff`는 파일 내용이 어떻게 달라지는지 보여 준다.

```bash
# 아무것도 바꾸지 않고 바뀔 내용만 본다
ansible-playbook site.yml --check --diff
```

(경로는 줄였다.) 인벤토리 한 줄이 LB의 분배 규칙을 `mod 2`에서 `mod 3`으로 바꾼다는 것이 PR 단계에서 보인다. 출력에서 세 가지를 같이 읽어야 한다.

- iptables 규칙은 `changed`라고만 나오고 diff가 없다. diff를 지원하지 않는 모듈이 많다. 파일을 다루는 `template`, `copy`, `lineinfile`은 diff가 나온다.
- 핸들러는 `skipping`이다. `--check`에서는 `command`처럼 결과를 미리 알 수 없는 작업을 실행하지 않는다. 그래서 "설정 파일은 맞는데 리로드 명령이 틀린" 실수는 check로 잡히지 않는다.
- 앞 작업의 결과에 기대는 작업은 check에서 엉뚱하게 나온다. 패키지를 설치하고 그 패키지의 명령을 쓰는 작업이 대표적이다. 그런 작업에는 `check_mode: false`(항상 실행해도 안전한 조회)나 `when: not ansible_check_mode`를 단다.

## 설정 파일은 템플릿으로, 다시 읽기는 핸들러로

LB 쪽은 규칙을 한 줄씩 넣지 않고 nftables 설정 파일 전체를 Jinja2 템플릿으로 그린다.

```jinja
# {{ ansible_managed }}
flush ruleset

table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;
    ct state established,related accept
    iif "lo" accept
    ip saddr {{ mgmt_cidr }} tcp dport 22 accept
    tcp dport {{ listen_port }} accept
  }
}

table ip nat {
  chain prerouting {
    type nat hook prerouting priority -100;
    tcp dport {{ listen_port }} dnat to numgen inc mod {{ backends | length }} map { {% for b in backends %}{{ loop.index0 }} : {{ b }}{{ ", " if not loop.last }}{% endfor %} }:8080
  }

  chain postrouting {
    type nat hook postrouting priority 100;
    ip daddr { {{ backends | join(", ") }} } tcp dport 8080 masquerade
  }
}
```

```yaml
- name: lb 규칙
  hosts: lb
  handlers:
    - name: reload nftables
      ansible.builtin.command: nft -f /etc/nftables.conf
  tasks:
    - name: nftables 설정 파일을 만든다
      ansible.builtin.template:
        src: nftables.conf.j2
        dest: /etc/nftables.conf
        mode: "0644"
        validate: nft -c -f %s      # 문법이 틀리면 파일을 바꾸지 않는다
      notify: reload nftables       # 파일이 바뀐 경우에만 핸들러를 부른다
```

(실습에서는 네임스페이스마다 파일을 따로 두려고 `dest` 경로만 바꿨다. 서비스로 관리한다면 핸들러는 `ansible.builtin.systemd: name=nftables state=reloaded`가 된다.) 이 몇 줄에 흐름이 다 들어 있다.

## 규칙을 한 줄씩 맞출까, 파일 전체를 맞출까

`iptables` 모듈은 "이 규칙이 있게 하라"만 맞춘다. 코드에서 규칙을 빼도 서버의 규칙은 지워지지 않는다. 지우려면 `state: absent`를 적은 작업을 따로 남겨야 한다. 위에서 command로 쌓은 9100 세 줄도 모듈 방식으로는 그대로 남는다. Terraform의 개별 규칙 리소스와 같은 약점이다.

반대 방식은 규칙 파일 전체를 템플릿으로 그리고 `iptables-restore`로 통째로 갈아 끼우는 것이다.

```jinja
# rules.v4.j2
*filter
:INPUT DROP [0:0]
:FORWARD DROP [0:0]
:OUTPUT ACCEPT [0:0]
-A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
-A INPUT -i lo -j ACCEPT
{% for port in allowed_tcp_ports %}
-A INPUT -s {{ mgmt_cidr }} -p tcp --dport {{ port }} -j ACCEPT
{% endfor %}
COMMIT
```

`validate: iptables-restore --test %s`로 문법을 확인하고 적용하면 코드에 없는 규칙은 모두 사라진다. 실습에서도 이 방식으로 한 번 돌리자 9100 세 줄과 comment 꼬리표가 모두 없어지고 템플릿에 적은 다섯 줄만 남았다. 대신 다른 도구(Docker, kube-proxy, fail2ban)가 넣는 규칙까지 지운다. 그런 도구가 있는 서버라면 자기 체인만 관리하거나(`ANSIBLE-INPUT` 같은 사용자 정의 체인), 그 도구가 다시 규칙을 넣을 수 있게 재시작을 핸들러에 넣는다.

두 방식을 한 체인에 섞으면 안 된다. 실습에서 파일 방식으로 갈아 끼운 뒤 모듈 방식의 `site.yml`을 다시 돌리니 web마다 `changed=2`가 나왔다. 파일 방식이 지운 comment 붙은 규칙을 모듈이 다시 넣은 것이다. 둘을 번갈아 돌리면 매번 changed가 뜨고 규칙이 흔들린다. 한 체인에는 한 주인만 둔다.

재부팅 후에도 남기는 문제는 따로 있다. 커널 규칙은 메모리에만 있으니 `/etc/iptables/rules.v4`(Ubuntu의 `iptables-persistent`)나 `/etc/nftables.conf`(nftables 서비스)에 저장된 파일이 부팅 때 읽혀야 한다. 파일 방식은 처음부터 그 파일을 관리하니 이 문제가 없다. 자세한 저장 방법은 [iptables 기본](/posts/iptables-basics)에 있다.

## 한 대씩 바꾸고, 틀리면 멈춘다

방화벽 변경을 40대에 한 번에 밀면 실수도 40대에 한 번에 퍼진다. Ansible은 기본으로 다섯 대(`forks=5`)씩 동시에 작업하고, 한 대가 실패해도 나머지는 계속 간다. 네트워크 변경에는 이 기본값이 맞지 않는다. 플레이에 `serial`과 `max_fail_percentage`를 건다.

```yaml
- name: web 방화벽을 한 대씩 바꾸고, 실패하면 되돌린다
  hosts: web
  serial: 1                  # 한 번에 한 대
  max_fail_percentage: 0     # 한 대라도 실패하면 남은 배치를 시작하지 않는다
  tasks:
    - name: 바꾸고 확인한다
      block:
        - name: 지금 규칙을 저장해 둔다
          ansible.builtin.command: iptables-save -f {{ rules_file }}.prev
          changed_when: false
        - name: 규칙 파일 전체를 만든다
          ansible.builtin.template:
            src: rules.v4.j2
            dest: "{{ rules_file }}"
            mode: "0600"
            validate: iptables-restore --test %s
          register: rules
        - name: 적용한다
          ansible.builtin.command: iptables-restore {{ rules_file }}
          when: rules is changed
        - name: lb에서 이 서버의 8080이 열리는지 본다
          ansible.builtin.uri:
            url: "http://{{ addr }}:8080/"
            timeout: 3
          delegate_to: lb1         # 확인은 바깥(LB)에서 한다
      rescue:
        - name: 저장해 둔 규칙으로 되돌린다
          ansible.builtin.command: iptables-restore {{ rules_file }}.prev
        - name: 되돌렸다고 알리고 멈춘다
          ansible.builtin.fail:
            msg: "{{ inventory_hostname }}: 확인 실패, 이전 규칙으로 되돌렸다"
```

`group_vars/web.yml`의 포트를 `[22, 8008]`로 잘못 친 PR이 적용됐다고 하자. 8080 대신 8008을 연 셈이다.

실전에서는 `serial: 1`로 40대를 돌리면 너무 느리다. 처음에는 한 대(카나리), 다음은 일부, 마지막은 나머지 전부처럼 목록으로 준다. `serial: [1, "30%", "100%"]`이면 배치 크기가 어떻게 나오는지 직접 계산해 보자. 퍼센트는 전체 호스트 수 기준으로 내림하고 최소 1이며, 목록의 마지막 값이 끝까지 반복된다.

## 네트워크 장비도 같은 방식으로

스위치와 라우터는 파이썬을 돌릴 수 없어서 방식이 조금 다르다. 모듈이 대상에서 돌지 않고 제어 노드에서 돌며, `network_cli` 연결로 SSH 세션을 열어 CLI 명령을 보낸다. 인벤토리에 이 차이를 적는다.

```ini
[edge]
edge-sw1 ansible_host=192.0.2.10

[edge:vars]
ansible_connection=ansible.netcommon.network_cli
ansible_network_os=cisco.ios.ios
ansible_user=netops
```

예전에는 `ios_config`로 설정 줄을 그대로 밀어 넣었다. 지금은 ACL, 인터페이스, VLAN 같은 자원마다 구조화된 리소스 모듈(`cisco.ios.ios_acls`, `ios_interfaces`, `ios_vlans`)을 쓰는 쪽을 권한다. 원하는 상태를 데이터로 적으면 모듈이 장비의 현재 설정과 비교해 필요한 명령만 만든다. 장비 없이 어떤 명령이 나갈지만 보는 `state: rendered`로 돌려 봤다.

```yaml
- name: 웹 대역으로 들어오는 ACL을 코드로 정한다
  cisco.ios.ios_acls:
    state: rendered          # 장비에 접속하지 않고 명령만 만든다
    config:
      - afi: ipv4
        acls:
          - name: WEB-IN
            acl_type: extended
            aces:
              - { sequence: 10, grant: permit, protocol: tcp, source: { any: true },
                  destination: { address: 10.66.0.0, wildcard_bits: 0.0.0.255, port_protocol: { eq: "443" } } }
              - { sequence: 20, grant: permit, protocol: tcp, source: { address: 10.66.9.0, wildcard_bits: 0.0.0.255 },
                  destination: { address: 10.66.0.0, wildcard_bits: 0.0.0.255, port_protocol: { eq: "22" } } }
              - { sequence: 1000, grant: deny, protocol: ip, source: { any: true }, destination: { any: true }, log: { set: true } }
  register: out
```

```text
ok: [edge-sw1] => {
    "out.rendered": [
        "ip access-list extended WEB-IN",
        "10 permit tcp any 10.66.0.0 0.0.0.255 eq 443",
        "20 permit tcp 10.66.9.0 0.0.0.255 10.66.0.0 0.0.0.255 eq 22",
        "1000 deny ip any any log"
    ]
}
```

(cisco.ios 11.6.0. 실제 스위치에 보내는 실행은 하지 못했으므로 장비 쪽 동작은 문서 기준으로 적는다.) 리소스 모듈의 `state`가 이 방식의 중심이다.

- `merged`: 적은 것을 더한다. 장비에 있던 다른 항목은 그대로 둔다. iptables 모듈 방식과 같다.
- `replaced`: 적은 ACL(이름 단위)은 적은 그대로 바꾸고, 적지 않은 ACL은 건드리지 않는다.
- `overridden`: 장비의 그 자원 전체를 적은 것과 똑같이 만든다. 적지 않은 ACL은 지운다. 파일 전체를 갈아 끼우는 방식과 같다.
- `deleted`, 그리고 장비를 바꾸지 않는 `gathered`(지금 설정을 데이터로 읽기), `rendered`, `parsed`(설정 텍스트를 데이터로 바꾸기).

`overridden`은 강력하지만 코드에 빠진 ACL을 지운다는 뜻이라 처음 도입할 때는 `gathered`로 현재 설정을 데이터로 떠서 코드에 옮긴 뒤 쓴다. 장비 작업에서 하나 더 조심할 것은 관리 세션을 지나는 ACL이다. SSH가 들어오는 인터페이스의 ACL을 잘못 바꾸면 Ansible이 장비를 잃는다. IOS에서는 작업 전에 `reload in 10`처럼 일정 시간 뒤 재부팅을 예약해 두고(저장하지 않은 설정이면 재부팅 때 이전 설정으로 돌아온다) 확인이 끝나면 `reload cancel`하는 방법을 오래 써 왔다. Junos의 `commit confirmed`처럼 확인하지 않으면 자동으로 되돌리는 기능이 있는 장비라면 그쪽을 쓴다.

## 현장에서 자동화가 사고를 키우는 순간

자동화는 같은 실수도 빠르게 여러 대에 퍼뜨린다. 자주 보는 장면과 먼저 볼 것을 적어 둔다.

- 플레이북이 중간에 `UNREACHABLE`로 몇 대씩 떨어진다: 방화벽 작업의 순서가 틀려 SSH가 막혔을 가능성이 크다. 콘솔로 들어가 `iptables -S INPUT`부터 본다. 허용 규칙보다 `-P INPUT DROP`이 먼저 적용되지 않았는지 플레이북 순서를 확인한다.
- 매일 도는 플레이북의 RECAP에 `changed`가 늘 몇 개씩 있다: 멱등하지 않은 작업이 있다. `-v`로 어떤 작업이 changed인지 보고, `command`·`shell` 작업에 `changed_when`과 `creates`를 단다. 진짜 drift를 보려면 이 소음부터 없앤다.
- `--check`는 깨끗했는데 실제 실행에서 실패했다: check가 건너뛴 핸들러나 command에서 터졌다. 리로드 명령은 `nft -c`, `nginx -t`처럼 검사 명령을 `validate`나 앞 작업으로 따로 둔다.
- 일부만 `-e`나 `--limit`으로 돌린 뒤 서버마다 상태가 다르다: 수동 실행이 기록 없이 쌓였다. 운영 적용은 CI에서만 하고, 사람은 `--check`만 돌리게 권한을 나눈다(다음 글).
- 파일 방식으로 바꿨더니 컨테이너 통신이 끊겼다: Docker나 kube-proxy가 만든 체인까지 지웠다. 자기 체인만 관리하게 바꾸거나 해당 서비스를 핸들러로 재시작한다.
- 확인 작업이 늘 통과한다: 확인을 대상 서버 안에서 하고 있다. 확인은 트래픽이 실제로 오는 위치(LB, 다른 서브넷)에서 한다.

## 같은 값을 몇 번이고

Ansible로 네트워크 설정을 다룬다는 것은 "원하는 상태"를 변수와 템플릿으로 적고, 몇 번을 돌려도 같은 결과가 나오게 만드는 일이다. 모듈은 현재 상태를 보고 다를 때만 고치고(두 번째 실행의 `changed=0`), `--check --diff`는 바꾸기 전에 차이를 보여 주고, 템플릿의 `validate`와 핸들러는 틀린 파일이 적용되지 않게 막는다. 한 줄씩 맞출지 전체를 맞출지는 다른 도구와의 공존을 보고 정하되 한 체인에 한 주인만 둔다. 변경은 `serial`로 나눠 밀고 바깥에서 확인하며, 실패하면 `rescue`로 되돌린다. 이 플레이북과 앞 글의 Terraform 코드를 PR로 리뷰하고 자동으로 적용하는 흐름은 [네트워크 설정 CI/CD](/posts/network-config-cicd)에서 이어진다.

## 면접에서 나올 만한 질문

### Terraform과 Ansible은 어떻게 나눠 쓰나요?

Terraform은 클라우드 API가 있는 자원을 만들고 state로 기억하며, Ansible은 이미 있는 기계에 들어가 그 안의 설정을 맞춘다. 네트워크로 보면 VPC, 서브넷, 보안 그룹은 Terraform, 서버의 sysctl과 호스트 방화벽, LB 설정 파일, 스위치 ACL은 Ansible이다. 둘은 Terraform의 output이나 클라우드 인벤토리 플러그인으로 이어 준다. 같은 자원을 두 도구가 함께 고치면 서로 덮어쓰므로 주인을 하나로 정한다.

### Ansible에서 멱등성은 어떻게 지켜지고, 어떻게 깨지나요?

모듈이 현재 상태를 먼저 읽고 원하는 상태와 다를 때만 바꾸기 때문에 지켜진다. 같은 플레이북을 두 번 돌려 두 번째 RECAP이 `changed=0`인지로 확인한다. `command`나 `shell`로 `iptables -A`처럼 상태를 묻지 않는 명령을 실행하면 돌릴 때마다 규칙이 쌓이며 깨진다. 이런 작업에는 `creates`, `changed_when`, 사전 확인 작업을 붙이거나 전용 모듈을 쓴다.

### --check --diff를 돌렸는데 실제 실행에서 실패할 수 있나요?

있다. check 모드는 결과를 예측할 수 없는 `command` 작업과 핸들러를 건너뛰고, diff를 지원하지 않는 모듈은 무엇이 바뀌는지 보여 주지 않는다. 그래서 리로드 명령의 오타나 앞 작업에 기대는 작업은 check로 드러나지 않는다. 설정 파일은 `validate`로 문법을 검사하게 하고, 서비스 리로드 전에 `nginx -t`, `nft -c` 같은 검사를 따로 둔다.

### 핸들러는 왜 쓰고, 언제 실행되나요?

설정 파일이 실제로 바뀐 경우에만 서비스를 다시 읽게 하려고 쓴다. 작업이 changed일 때 `notify`로 알리면 핸들러는 플레이 끝에 한 번만 돈다. 여러 작업이 같은 핸들러를 불러도 한 번이다. 바뀐 설정을 적용한 뒤 바로 확인해야 하면 `meta: flush_handlers`로 그 자리에서 돌린다.

### 방화벽 규칙을 모듈로 한 줄씩 관리하는 것과 파일 전체로 관리하는 것의 차이는요?

모듈 방식은 적은 규칙이 있게만 하므로 코드에서 지운 규칙이 서버에 남고, 다른 도구가 넣은 규칙과 공존하기 쉽다. 파일 방식은 `iptables-restore`나 `nft -f`로 전체를 갈아 끼워 코드와 서버가 정확히 같아지지만 Docker나 kube-proxy 규칙까지 지울 수 있다. 한 체인에 두 방식을 섞으면 실행할 때마다 서로 되돌리며 changed가 뜬다. 다른 도구가 있으면 자기 체인만 파일로 관리하는 절충을 쓴다.

### 여러 대에 네트워크 변경을 안전하게 배포하려면 어떻게 하나요?

`serial`로 배치를 나누고 `max_fail_percentage`로 실패 시 다음 배치를 멈춘다. 첫 배치는 한 대(카나리), 다음은 일부, 마지막은 전부처럼 `serial: [1, "30%", "100%"]`로 준다. 각 배치 끝에 트래픽이 실제로 오는 위치에서 확인하는 작업을 두고, `block`/`rescue`로 실패하면 저장해 둔 이전 설정으로 되돌린다. 실습에서는 포트 오타가 web1에서 확인에 걸려 되돌려졌고 나머지 서버는 손대지 않았다.

### 네트워크 장비 자동화는 서버 자동화와 무엇이 다른가요?

장비에서 파이썬을 돌릴 수 없어 모듈이 제어 노드에서 돌고 `network_cli` 연결로 CLI 명령을 보낸다. 요즘은 설정 줄을 밀어 넣기보다 ACL, 인터페이스 같은 자원별 리소스 모듈에 원하는 상태를 데이터로 주고 `merged`, `replaced`, `overridden` 같은 state로 적용 범위를 고른다. `overridden`은 코드에 없는 항목을 지우므로 `gathered`로 현재 설정을 먼저 코드로 옮긴다. 관리 세션이 지나는 ACL을 바꿀 때는 자동 되돌리기 장치를 먼저 걸어 둔다.
