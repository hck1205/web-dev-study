[LeetCode 153. Find Minimum in Rotated Sorted Array](https://leetcode.com/problems/find-minimum-in-rotated-sorted-array/)는 회전된 배열 시리즈의 첫 문제다. 최솟값 하나 찾는 건 `Math.min` 한 줄이면 되는데, 문제가 O(log n)을 요구하는 순간 갑자기 어려워진다. 나도 처음엔 `nums[mid]`를 `nums[lo]`와 비교했다가 회전하지 않은 배열에서 틀린 답을 받았다. 왜 오른쪽 끝과 비교해야 하는지가 이 문제의 전부다.

문제를 내 말로 풀면 이렇다. 서로 다른 정수가 오름차순으로 정렬된 배열이 있었는데, 앞쪽 일부를 떼어 뒤에 붙였다(이걸 회전이라고 부른다). `[-4, 1, 3, 8, 12, 17, 25, 31]`을 네 칸 회전하면 `[12, 17, 25, 31, -4, 1, 3, 8]`이 된다. 회전 횟수는 1번부터 n번까지일 수 있고, n번 돌리면 원래 배열 그대로다. 이 배열의 최솟값을 O(log n)에 구한다.

풀이에 영향을 주는 제약은 이렇다.

- 배열 길이는 1 이상 5000 이하다. 빈 배열은 없다.
- 값은 모두 서로 다르다. 같은 값이 있으면 판단이 깨지는데, 그 변형(154번)은 뒤에서 따로 본다.
- 회전 횟수가 n이면 정렬된 배열이 그대로 들어온다. 이 경우를 놓치는 코드가 많다.

이분 탐색의 구간 정의는 [LeetCode 704 글](/posts/leetcode-binary-search)에서, 회전 배열에서 값을 찾는 이어지는 문제는 [Search in Rotated Sorted Array 글](/posts/leetcode-search-in-rotated-sorted-array)에서 다룬다. 실행 결과는 Node.js 22, Python 3, OpenJDK에서 돌린 값이다.

## 꺾이는 곳이 한 군데 생긴다

예시 배열을 칸 번호와 함께 써 보자.

```text
index   0   1   2   3   4   5   6   7
nums   12  17  25  31  -4   1   3   8
```

왼쪽부터 올라가다 3번(31)에서 4번(-4)으로 뚝 떨어진다. 떨어진 뒤 다시 올라간다. 회전된 정렬 배열은 이렇게 오름차순 덩어리 두 개가 이어 붙은 모양이고, 떨어지는 곳은 정확히 한 군데다. 최솟값은 떨어진 바로 다음 칸, 즉 오른쪽 덩어리의 첫 칸이다.

두 덩어리에는 눈에 띄는 차이가 있다. 왼쪽 덩어리(12, 17, 25, 31)의 값은 모두 오른쪽 덩어리(-4, 1, 3, 8)의 값보다 크다. 원래 정렬 배열에서 뒤쪽에 있던 큰 값들이 앞으로 왔기 때문이다. 그래서 배열의 마지막 값 8을 기준으로 삼으면 칸마다 이렇게 나뉜다.

```text
nums       12  17  25  31  -4   1   3   8
<= 8 ?      F   F   F   F   T   T   T   T
```

F가 이어지다 T로 한 번만 바뀐다. 최솟값의 자리는 처음으로 T가 되는 칸이다. 정렬은 깨졌지만 "마지막 값 이하인가"라는 질문은 여전히 단조롭다. 이분 탐색이 쓰이는 근거가 이것이다.

회전하지 않은 배열 `[-4, 1, 3, 8, 12, 17, 25, 31]`에서도 같은 질문을 해 보면 모든 칸이 31 이하라 전부 T다. 첫 T는 0번, 최솟값 -4가 맞게 나온다. 마지막 값을 기준으로 삼으면 회전했든 안 했든 하나의 규칙으로 처리된다. 첫 값을 기준으로 삼으면 이게 안 되는데, 아래에서 실제로 틀려 본다.

## 전부 훑어서 가장 작은 값

가장 먼저 쓰는 답은 모든 칸을 보는 것이다.

```js
function findMin(nums) {
  let min = Infinity;
  for (const x of nums) if (x < min) min = x; // 가장 작은 값을 들고 다닌다
  return min;
}
```

`Math.min(...nums)` 한 줄로도 된다. 다만 펼침 연산자(`...`)는 배열 원소를 함수 인자로 하나하나 넘기는 방식이라, 원소가 많으면 호출 스택이 넘친다. Node.js 22에서 20만 개짜리 배열을 넘겼더니 `RangeError: Maximum call stack size exceeded`가 났다. 이 문제는 5000개라 괜찮지만, 크기를 모르는 배열에는 반복문이 안전하다.

파이썬은 `min(nums)`, 자바는 스트림으로 같은 일을 한다.

```python
min(nums)                                   # 내부에서 한 번 훑는다
```

```java
Arrays.stream(nums).min().getAsInt();       // 빈 배열이면 예외. 이 문제는 길이 1 이상이다
```

시간 O(n), 공간 O(1)이다. 정렬돼 있었다는 정보를 하나도 쓰지 않았다. 문제의 O(log n) 요구도 못 맞춘다.

## 떨어지는 곳을 앞에서부터 찾기

최솟값이 "값이 떨어진 바로 다음 칸"이라는 걸 알았으니, 앞에서부터 보다가 앞 칸보다 작은 칸을 만나면 바로 멈춘다.

```js
function findMin(nums) {
  for (let i = 1; i < nums.length; i++) {
    if (nums[i] < nums[i - 1]) return nums[i]; // 떨어진 곳: 여기가 최소
  }
  return nums[0]; // 떨어진 곳이 없다 = 회전하지 않았다
}
```

떨어진 곳을 찾지 못하고 끝까지 가면 배열이 처음부터 정렬돼 있다는 뜻이고, 그때는 첫 칸이 최소다. 이 처리를 빠뜨리면 회전 횟수가 n인 입력에서 `undefined`를 돌려준다.

평균적으로는 전부 훑기보다 빠르지만 최악은 같다. 떨어진 곳이 배열 끝에 있거나(`[1, 3, 8, …, 31, -4]`) 회전하지 않았으면 끝까지 본다. 시간 O(n), 공간 O(1)이다. 길이 100만, 654,321칸 회전한 배열로 1,000번씩 돌려 봤다.

```text
linear 6315.5 ms / 1000 calls
drop 330.1 ms / 1000 calls
binary 1.4 ms / 1000 calls
```

떨어진 곳에서 멈추는 덕분에 훑기보다는 훨씬 빠르다. 그래도 아래 이분 탐색(맨 아래 줄)과는 200배 넘게 차이 난다. 떨어지는 곳이 한 군데뿐이라는 정보를 "앞에서부터 찾기"에만 쓰고 있어서다. 위에서 본 F, T 줄을 쓰면 절반씩 버릴 수 있다.

## 가운데를 오른쪽 끝과 비교한다

정석 풀이다. 구간 `[lo, hi]`를 "최솟값이 반드시 이 안에 있다"로 정하고, 가운데 값 `nums[mid]`를 구간의 오른쪽 끝 `nums[hi]`와 비교한다.

- `nums[mid] > nums[hi]`: mid에서 hi로 가는 사이에 값이 떨어지는 곳이 있다. 오름차순이라면 mid가 hi보다 클 수 없기 때문이다. mid는 왼쪽 덩어리에 있고, 최솟값은 mid보다 오른쪽이다. `lo = mid + 1`.
- `nums[mid] < nums[hi]`: mid부터 hi까지는 오름차순으로 이어진다. 그 구간의 최소는 mid 자신이다. 최솟값은 mid이거나 그보다 왼쪽이다. mid도 답일 수 있으니 남긴다. `hi = mid`.

값이 서로 다르고 `mid < hi`라서 `nums[mid] === nums[hi]`인 경우는 없다. 반복은 `lo < hi`일 때만 도니 mid는 항상 hi보다 왼쪽이다.

```js
function findMin(nums) {
  let lo = 0, hi = nums.length - 1;     // 최솟값은 반드시 [lo, hi] 안에 있다
  while (lo < hi) {                     // 한 칸 남으면 그게 답이다
    const mid = lo + Math.floor((hi - lo) / 2);
    if (nums[mid] > nums[hi]) lo = mid + 1; // 꺾이는 곳이 mid 오른쪽에 있다
    else hi = mid;                          // mid~hi는 오름차순, mid가 후보
  }
  return nums[lo];
}
```

두 번째 그림의 두 번째 단계가 중요하다. 비교 대상은 처음 배열의 끝(17)이 아니라 지금 구간의 끝 `nums[hi]`(1)다. 구간을 줄일 때마다 기준도 따라 움직인다. 처음 배열의 마지막 값과 비교해도 이 문제는 맞게 나오지만(F, T 줄의 기준값이 그것이었다), `nums[hi]`와 비교하는 쪽이 "mid~hi가 오름차순인가"라는 뜻이 분명해서 154번 변형으로 넓히기도 쉽다.

회전하지 않은 배열 `[-4, 1, 3, 8, 12, 17, 25, 31]`에서는 매번 `nums[mid] < nums[hi]`라 `hi`만 왼쪽으로 줄어 0번에 닿는다. 원소가 하나면 반복을 돌지 않고 `nums[0]`을 돌려준다. 따로 처리할 경우가 없다.

시간 O(log n), 공간 O(1)이다. 반복마다 구간이 절반 가까이 줄고, `lo < hi`에서 mid를 내림하니 두 칸 남았을 때도 반드시 한 칸 준다.

### 두 칸, 세 칸을 손으로 따라가기

경계 버그는 구간이 두세 칸일 때 난다. 그래서 가능한 회전이 몇 개 안 되는 작은 배열을 손으로 끝까지 따라가 두면 안심이 된다. 값 1, 2, 3으로 만들 수 있는 회전 배열 다섯 개를 전부 적었다.

```text
[1, 2]     mid 0: 1 < 2 → hi = 0                       → 1
[2, 1]     mid 0: 2 > 1 → lo = 1                       → 1
[1, 2, 3]  mid 1: 2 < 3 → hi = 1;  mid 0: 1 < 2 → hi = 0 → 1
[2, 3, 1]  mid 1: 3 > 1 → lo = 2                       → 1
[3, 1, 2]  mid 1: 1 < 2 → hi = 1;  mid 0: 3 > 1 → lo = 1 → 1
```

모든 줄이 한두 번 비교로 끝나고, 매번 구간이 줄어든다. 특히 `[2, 1]`과 `[3, 1, 2]`의 마지막 비교에서 mid가 lo와 같아지는데, 이때 `nums[mid] > nums[hi]`라서 `lo = mid + 1`로 확실히 한 칸 움직인다. mid를 내림으로 구하고 `hi = mid`, `lo = mid + 1`을 짝으로 쓰면 이 두 칸 상황이 항상 안전하다. 면접에서 코드를 다 쓴 뒤 `[2, 1]` 하나만 손으로 넣어 봐도 비교 방향이 맞는지 확인된다.

### 파이썬과 자바로 옮기면

```python
from typing import List

class Solution:
    def findMin(self, nums: List[int]) -> int:
        lo, hi = 0, len(nums) - 1
        while lo < hi:
            mid = (lo + hi) // 2
            if nums[mid] > nums[hi]:   # mid~hi 사이에 꺾이는 곳이 있다
                lo = mid + 1
            else:                      # mid~hi는 오름차순, mid가 그 구간의 최소
                hi = mid
        return nums[lo]
```

```java
class Solution {
    public int findMin(int[] nums) {
        int lo = 0, hi = nums.length - 1;
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] > nums[hi]) lo = mid + 1; // 꺾이는 곳이 오른쪽에 있다
            else hi = mid;                          // mid가 최소일 수도 있다
        }
        return nums[lo];
    }
}
```

예시 두 개, 회전 없는 `[-4, 1, 3, 8]`, 한 칸 `[5]`, 두 칸 `[2, 1]`을 넣은 결과는 두 언어가 같다.

```text
-4 -4 -4 5 1
```

이 문제는 배열이 5000칸이라 인덱스 오버플로가 없고, 값끼리 빼지 않고 비교만 하니 값 범위(-5000~5000)도 상관없다. 자바에서 `nums[mid] - nums[hi] > 0`처럼 빼서 비교하는 버릇이 있다면 값 범위가 큰 문제에서는 뺄셈이 넘칠 수 있으니 비교 연산자를 그대로 쓴다.

### 여덟 가지 회전을 모두 넣어 보기

회전 횟수는 0부터 n - 1까지 n가지뿐이다. 예시 배열을 모두 돌려 넣고, 최솟값과 그 자리를 함께 찍었다.

```text

[17,25,31,-4,1,3,8,12]     min -4 at 3
[25,31,-4,1,3,8,12,17]     min -4 at 2
```

## 첫 값을 기준으로 경계를 찾는다

같은 생각을 다르게 쓸 수도 있다. 첫 값 `nums[0]`을 기준으로 "첫 값보다 작은가"를 물으면, 왼쪽 덩어리는 F, 오른쪽 덩어리는 T다. 첫 T를 lower bound처럼 찾는다.

```js
function findMin(nums) {
  const n = nums.length;
  if (nums[0] <= nums[n - 1]) return nums[0]; // 회전하지 않았다: 첫 값이 최소
  let lo = 1, hi = n - 1;                       // 최솟값은 1~n-1번 중에 있다
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (nums[mid] < nums[0]) hi = mid;  // 오른쪽 덩어리: mid가 후보
    else lo = mid + 1;                  // 왼쪽 덩어리: 최소는 더 오른쪽
  }
  return nums[lo];
}
```

시간 O(log n), 공간 O(1)로 앞 풀이와 같다. 다른 점은 첫 줄의 예외 처리다. 회전하지 않은 배열은 모든 칸이 첫 값 이상이라 T가 하나도 없다. 그러면 위 반복은 마지막 칸을 돌려준다. 그래서 회전하지 않았는지 먼저 확인해야 한다. 오른쪽 끝과 비교하는 풀이는 이런 예외가 없다. 같은 이분 탐색이라도 기준을 어디에 두느냐에 따라 예외 처리가 생기기도 하고 사라지기도 한다.

그래도 이 풀이는 알아 둘 가치가 있다. "기준값과 비교해 F, T 줄을 만든다"는 생각이 그대로 드러나서, 회전 배열에서 값을 찾는 [33번 문제](/posts/leetcode-search-in-rotated-sorted-array)를 "최솟값 자리로 나눈 뒤 한쪽에서 이분 탐색"으로 풀 때 자연스럽게 이어진다.

## 정렬된 조각은 바로 답한다: 분할 정복

마지막은 재귀다. 구간 `[lo, hi]`의 양 끝을 보고 `nums[lo] <= nums[hi]`면 그 구간은 회전되지 않은 오름차순이니 최소는 `nums[lo]`다. 아니면 반으로 나눠 양쪽의 최소 중 작은 값을 돌려준다.

```js
function findMin(nums, lo = 0, hi = nums.length - 1) {
  if (nums[lo] <= nums[hi]) return nums[lo]; // 정렬된 조각: 첫 칸이 최소
  const mid = lo + Math.floor((hi - lo) / 2);
  return Math.min(findMin(nums, lo, mid), findMin(nums, mid + 1, hi));
}
```

양쪽을 다 부르니 O(n)처럼 보이지만 그렇지 않다. 회전된 구간을 반으로 자르면 꺾이는 곳은 한쪽에만 있고, 다른 쪽은 정렬된 조각이라 한 번에 돌아온다. 결국 단계마다 "바로 답하는 호출 하나 + 더 들어가는 호출 하나"라서 호출 수가 약 2 log n이다. 직접 세어 봤다.

```text
0 calls 41
calls small 3
```

2^20(약 100만)칸 배열에서 호출이 41번, 예시 8칸에서는 3번이다. 시간 O(log n), 공간은 재귀 깊이만큼 O(log n)이다. 반복문 풀이보다 공간을 더 쓰지만, "정렬된 조각은 바로 답할 수 있다"는 성질이 코드에 그대로 보여 설명하기 좋다. 이 성질은 154번(중복 허용)에서 같은 값 때문에 양쪽이 다 정렬돼 보이지 않을 때 무너진다. 그때는 진짜로 양쪽을 다 들어가 O(n)이 된다.

## 이렇게 짜면 틀린다

### 가운데를 왼쪽 끝과 비교한다

오른쪽 끝 대신 왼쪽 끝과 비교하면 될 것 같다. "가운데가 왼쪽 끝 이상이면 왼쪽은 정렬돼 있으니 최소는 오른쪽에 있다"는 논리다.

```js
if (nums[mid] >= nums[lo]) lo = mid + 1; else hi = mid;
```

예시 배열을 0칸부터 7칸까지 돌려 가며 넣어 봤다.

```text
[-4,1,3,8,12,17,25,31]  -> 31
[1,3,8,12,17,25,31,-4]  -> -4
[3,8,12,17,25,31,-4,1]  -> 1
[8,12,17,25,31,-4,1,3]  -> -4
[12,17,25,31,-4,1,3,8]  -> 8
[17,25,31,-4,1,3,8,12]  -> -4
[25,31,-4,1,3,8,12,17]  -> 1
[31,-4,1,3,8,12,17,25]  -> -4
```

여덟 개 중 네 개가 틀렸다. 회전하지 않은 첫 줄은 최대값 31이 나왔다. 왼쪽이 정렬돼 있다고 해서 최소가 오른쪽에 있다는 보장이 없기 때문이다. 배열 전체가 정렬돼 있으면 최소는 왼쪽 끝 자체다. 또 `lo = mid + 1`로 최솟값 칸을 건너뛰는 경우가 생긴다(세 번째 줄은 -4를 지나쳐 1에 멈췄다). 오른쪽 끝과의 비교는 "mid~hi가 정렬돼 있으면 mid가 그 구간의 최소"라는 확실한 결론을 주는데, 왼쪽 끝과의 비교는 "lo~mid가 정렬돼 있다"만 알려 줄 뿐 최소가 어디인지는 말해 주지 않는다. 왼쪽 기준으로 짜고 싶다면 위의 첫 값 기준 풀이처럼 회전 여부를 먼저 거르고 기준을 `nums[0]`으로 고정해야 한다.

### `hi = mid - 1`로 mid를 버린다

```js
else hi = mid - 1; // mid가 최솟값이면 버려진다
```

`nums[mid] < nums[hi]`일 때 mid가 바로 최솟값일 수 있다. 첫 그림의 마지막 비교(-4 < 1)가 그 경우다. 여기서 mid를 버리면 -4를 놓친다. "후보로 남는 칸"과 "확실히 아닌 칸"을 구분해 남는 쪽은 `hi = mid`, 아닌 쪽은 `lo = mid + 1`로 쓴다.

### `lo <= hi`로 돈다

`hi = mid`를 쓰는 코드에서 `while (lo <= hi)`로 돌면 `lo === hi`일 때 `nums[mid] > nums[hi]`가 거짓이라 `hi = mid`, 같은 상태로 영영 돈다. 답이 반드시 있는 문제에서 "한 칸 남으면 그게 답"이라는 정의라면 `lo < hi`다.

### 회전하지 않은 배열을 따로 생각하지 않는다

떨어지는 곳을 찾는 풀이에서 끝까지 못 찾았을 때 `nums[0]`을 돌려주지 않거나, 첫 값 기준 풀이에서 회전 여부를 먼저 거르지 않으면 회전 횟수 n인 입력에서 틀린다. 테스트할 때 정렬된 배열 그대로와 원소 하나, 두 칸(`[2, 1]`, `[1, 2]`)을 꼭 넣는다.

## 면접관이 이어서 묻는 것

### 같은 값이 있어도 된다면 (154. Find Minimum in Rotated Sorted Array II)

`nums[mid] === nums[hi]`가 생긴다. 이때는 꺾이는 곳이 mid의 왼쪽인지 오른쪽인지 알 수 없다. `[3, 3, 1, 3]`과 `[3, 1, 3, 3, 3]`을 보면 둘 다 가운데와 끝이 3인데, 최솟값은 한쪽은 mid 오른쪽(2번), 다른 쪽은 왼쪽(1번)에 있다. 153번 코드를 그대로 쓰면 `[3, 3, 1, 3]`에서 3을 돌려준다. 같으면 `hi = mid`로 가서 1을 지나쳐 버리기 때문이다.

할 수 있는 일은 `hi`를 한 칸만 줄이는 것이다. `nums[hi]`와 같은 값이 mid에 있으니 hi를 버려도 최솟값을 잃지 않는다.

```js
function findMin(nums) {
  let lo = 0, hi = nums.length - 1;
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (nums[mid] > nums[hi]) lo = mid + 1;
    else if (nums[mid] < nums[hi]) hi = mid;
    else hi--; // 같으면 어느 쪽인지 모른다. 끝 하나만 버린다
  }
  return nums[lo];
}
```

```text
[3, 1, 3]       -> 1
[1, 1, 1, 1]    -> 1
```

### 원형 버퍼에서 가장 오래된 기록 찾기

이 문제가 실제로 쓰이는 모양이 하나 있다. 크기가 정해진 원형 버퍼(꽉 차면 맨 앞부터 덮어쓰는 배열)에 시각을 차례로 기록하면, 버퍼는 회전된 정렬 배열이 된다. 쓰는 위치를 따로 저장해 두지 않았다면(예를 들어 장비가 재부팅된 뒤 덤프 파일만 남은 경우) 가장 오래된 기록은 최솟값 찾기로 찾는다.

```js
const cap = 8, buf = new Array(cap);
let w = 0;
for (let t = 1000; t < 1065; t += 5) { buf[w] = t; w = (w + 1) % cap; } // 13번 써서 앞쪽이 덮였다
console.log(JSON.stringify(buf), "oldest at", findMinIndex(buf), "next write", w);
```

```text
[1040,1045,1050,1055,1060,1025,1030,1035] oldest at 5 next write 5
```

`findMinIndex`는 위 코드에서 `nums[lo]` 대신 `lo`를 돌려주는 함수다. 가장 오래된 1025가 5번에 있고, 그 자리가 다음에 쓸 위치와 같다. 다만 시각이 같은 기록이 여러 개 있을 수 있으면 154번처럼 중복을 처리해야 한다.

### 몇 번 회전했는지 구하라면

최솟값의 자리가 곧 회전 횟수다. 원래 0번에 있던 최솟값이 회전으로 k번 자리에 갔기 때문이다. 위 코드에서 `nums[lo]` 대신 `lo`를 돌려주면 된다. 예시는 4, 회전하지 않은 배열은 0이다. 회전 횟수 n과 0은 같은 배열이라 구분할 수 없다.

### 최댓값을 구하라면

최댓값은 최솟값 바로 왼쪽 칸이다. 최솟값 자리 `k`를 구한 뒤 `nums[(k - 1 + n) % n]`을 읽는다. 회전하지 않았으면 `k = 0`이라 마지막 칸이 나온다. 이분 탐색을 따로 짤 필요 없다.

### 내림차순 배열을 회전했다면

비교 방향을 뒤집으면 된다. 아니면 "가장 큰 값을 찾는 문제"로 바꿔 생각한다. 이런 변형에서 막히면 F, T 줄을 다시 그려 보는 게 가장 빠르다. 어떤 기준값과 비교했을 때 답이 한 번만 바뀌는지 찾으면 코드가 따라온다.

## 끝과 비교하면 예외가 사라진다

회전된 정렬 배열은 오름차순 덩어리 두 개가 붙은 모양이고, 최솟값은 두 번째 덩어리의 첫 칸이다. 가운데 값을 지금 구간의 오른쪽 끝과 비교하면, 가운데가 더 클 때는 꺾이는 곳이 오른쪽에 있고, 더 작을 때는 가운데부터 끝까지 오름차순이라 가운데가 후보다. 이 규칙 하나가 회전하지 않은 배열, 원소 하나, 두 칸까지 모두 덮는다. 왼쪽 끝과 비교하면 "왼쪽이 정렬됐다"는 것만 알 뿐 최소의 위치를 알려 주지 않아서 틀린다. 같은 값이 허용되면 같을 때 끝 하나만 버리는 수밖에 없어 최악 O(n)이 된다.

## 면접에서 나올 만한 질문

### 왜 `nums[mid]`를 `nums[lo]`가 아니라 `nums[hi]`와 비교하나요?

오른쪽 끝과 비교해야 최솟값의 위치를 확정할 수 있기 때문이다. `nums[mid] < nums[hi]`면 mid부터 hi까지 오름차순이라 그 구간의 최소는 mid이고, `nums[mid] > nums[hi]`면 그 사이에 꺾이는 곳이 있어 최소가 mid 오른쪽이다. 왼쪽 끝과 비교하면 "lo~mid가 정렬됐다"만 알 뿐 최소가 왼쪽 끝인지(회전 안 된 경우) 오른쪽 덩어리인지 구분하지 못해서, 회전하지 않은 배열에서 최댓값을 돌려준다.

### 이 문제가 O(log n)인 이유를 단조성으로 설명해 보세요.

배열의 마지막 값을 기준으로 "이 칸이 마지막 값 이하인가"를 물으면 왼쪽 덩어리는 전부 F, 오른쪽 덩어리는 전부 T다. 왼쪽 덩어리 값이 오른쪽 덩어리 값보다 모두 크기 때문이다. 정렬은 깨졌어도 이 질문은 F에서 T로 한 번만 바뀌니, 첫 T(최솟값 자리)를 이분 탐색으로 찾는다. 비교마다 구간이 절반이 되니 O(log n)이다.

### 회전하지 않은 배열이 들어오면 어떻게 되나요?

오른쪽 끝과 비교하는 코드는 따로 처리할 필요가 없다. 매번 `nums[mid] < nums[hi]`라 hi만 줄어 0번에 닿는다. 첫 값을 기준으로 삼는 풀이나 떨어지는 곳을 찾는 풀이는 이 경우 예외가 생겨서, `nums[0] <= nums[n - 1]`이면 첫 값을 바로 돌려주는 처리가 필요하다.

### `hi = mid - 1`이 아니라 `hi = mid`인 이유는 무엇인가요?

`nums[mid] < nums[hi]`일 때 mid 자신이 최솟값일 수 있기 때문이다. 예시에서 마지막에 -4와 1을 비교하는 순간이 그렇다. mid를 버리면 최솟값을 놓친다. 반대로 `nums[mid] > nums[hi]`면 mid보다 작은 값이 오른쪽에 있으니 mid는 확실히 답이 아니라서 `lo = mid + 1`로 뺀다. 이 짝이라 반복은 `lo < hi`로 돈다.

### 중복이 허용되면 시간 복잡도가 어떻게 바뀌나요?

최악 O(n)이 된다. `nums[mid] === nums[hi]`면 꺾이는 곳이 어느 쪽인지 알 수 없어서 hi를 한 칸만 줄일 수 있다. `[3, 3, 1, 3]`과 `[3, 1, 3, 3, 3]`은 가운데와 끝이 같지만 최솟값이 서로 반대쪽에 있다. 거의 모든 값이 같은 배열에서는 한 칸씩 줄어든다. 평균적으로는 여전히 빠르다.

### 이 풀이가 Search in Rotated Sorted Array와 어떻게 이어지나요?

33번은 회전 배열에서 특정 값을 찾는 문제다. 이 문제로 최솟값의 자리 k를 구하면 배열은 `[0, k - 1]`과 `[k, n - 1]` 두 정렬 조각으로 나뉜다. target이 `nums[n - 1]` 이하면 오른쪽 조각, 아니면 왼쪽 조각에서 평범한 이분 탐색을 한다. O(log n)을 두 번 하니 여전히 O(log n)이다. 한 번의 이분 탐색으로 끝내는 방법도 있는데, 그건 가운데로 잘랐을 때 어느 절반이 정렬됐는지를 보는 방식이다.

### 최솟값의 인덱스는 어디에 쓰이나요?

회전 횟수가 곧 최솟값의 인덱스다. 그리고 이 인덱스를 경계로 배열이 정렬된 두 조각으로 나뉘니, 회전 배열에서 값을 찾는 33번 문제를 "최솟값 자리를 찾고 target이 속한 조각에서 이분 탐색"으로 풀 수 있다. 최댓값은 최솟값 바로 왼쪽 칸이다.
