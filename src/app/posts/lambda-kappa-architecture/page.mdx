<EasyIntro>

  람다 방식은 두 방법을 다 쓴다. 낮에는 화면 숫자를 보여 주고, 밤에 영수증을 다시 센 결과가 나오면 화면 숫자를 그걸로 바꿔 끼운다. 대신 세는 규칙을 두 군데에 따로 적어 둬야 해서, 한쪽만 고치면 두 숫자가 영영 안 맞는다.

  카파 방식은 영수증 뭉치를 버리지 않고 계속 보관해 두었다가, 규칙이 바뀌면 같은 계산기로 처음부터 다시 흘려 본다. 세는 규칙이 한 군데에만 있으니 어긋날 일이 적다. 대신 영수증을 오래 보관할 창고와 다시 세는 동안 버틸 힘이 필요하다.

10월 21일 저녁, 실시간 대시보드는 그날 주문 매출을 52,121,700원으로 보여 줬다. 다음 날 아침 9시에 메일로 온 일일 리포트는 51,884,400원이었다. 237,300원 차이다. 영업팀은 어느 쪽을 믿어야 하냐고 묻고, 대시보드를 만든 사람과 리포트를 만든 사람은 서로 자기 쪽 코드는 맞다고 한다. 둘 다 반쯤 맞다.

이 글은 이 차이가 어디서 오는지에서 시작해, 빠른 길과 정확한 길을 나란히 두는 람다 아키텍처, 로그 하나를 다시 재생하는 카파 아키텍처, 둘을 섞어 쓰는 하이브리드 수집을 비교한다. 배치 하나를 안전하게 돌리는 법은 [배치 처리](/posts/batch-processing)에, 상태를 키로 나눠 들고 가는 스트림 작업의 내부는 [스트림 처리](/posts/stream-processing)에, 워터마크와 창의 모양은 [이벤트 시간과 창](/posts/sd-ad-click-stream-windows)에 있으니 여기서는 그 둘을 어떻게 한 시스템으로 엮느냐만 본다.

## 숫자 두 개가 갈라지는 이유

차이가 어디서 오는지 보려고 그날 상황을 작게 흉내 냈다. 주문 2,000건을 하루에 흩뿌리고, 97%는 30초 안에, 2.5%는 1~20분 늦게, 0.5%는 앱이 오프라인이었다가 몇 시간 뒤에 도착하게 했다. 모바일 앱의 재시도 때문에 1%쯤은 같은 주문이 두 번 전송된다.

실시간 쪽은 흔한 스트림 집계처럼 짰다. 이벤트 시각 기준 1시간 창으로 더하고, 워터마크는 지금까지 본 가장 늦은 이벤트 시각에서 10분을 뺀 값이다. 워터마크를 넘긴 창은 닫고, 닫힌 창에 오는 이벤트는 버린다. 중복 제거는 하지 않는다. 배치 쪽은 다음 날 새벽 2시에 레이크에 쌓인 원본 전체를 읽어 `order_id`로 중복을 지우고 더한다.

```python
# lk_sim.py 일부 (Python 3.13, 표준 라이브러리만)
for oid, t, arr, amt in stream:            # 도착 순서대로 처리
    maxev = max(maxev, t)
    wm = maxev - 600                       # 워터마크: 본 것 중 최댓값 - 10분
    for h in range(24):
        if (h + 1) * 3600 <= wm:
            closed.add(h)                  # 끝이 워터마크 뒤로 간 창은 닫는다
    h = t // 3600
    if h in closed:
        dropped += 1; dropped_amt += amt   # 닫힌 창에 온 늦은 주문은 버린다
        continue
    win[h] += amt                          # 중복 전송도 그대로 더해진다
```


실시간 합계는 진짜 합계보다 중복 23건(575,200원)만큼 많고, 늦게 와서 버려진 13건(337,900원)만큼 적다. 51,884,400 + 575,200 − 337,900 = 52,121,700이 정확히 맞는다. 배치는 원본을 다 모은 뒤 한 번에 세니까 진짜 합계와 같다.

두 숫자가 다른 건 버그라기보다 두 길이 서로 다른 약속을 하기 때문이다. 스트림은 "지금 아는 만큼 빨리"를 약속하고, 배치는 "다 모인 뒤 정확히"를 약속한다. 스트림 쪽도 중복 제거와 늦은 데이터 수정을 넣을 수 있다. 다만 그만큼 상태를 오래 들고 있어야 하고 결과를 고쳐 쓸 수 있는 저장소가 필요하다. 그걸 감당하기 어렵던 시절에 나온 답이 람다 아키텍처다.

## 느린 길과 빠른 길을 나란히 두는 람다

람다 아키텍처는 Nathan Marz가 Storm과 Hadoop으로 대규모 집계를 하던 경험에서 정리한 구조다. 원본 데이터를 지우지 않고 계속 쌓고(불변 원본), 그 위에 길을 둘 낸다.

- 배치 층: 원본 전체(또는 큰 구간)를 주기적으로 다시 읽어 정확한 결과를 만든다. Hadoop MapReduce, 지금은 Spark가 맡는다. 결과물을 배치 뷰라고 부른다.
- 속도 층: 배치가 아직 처리하지 못한 최근 구간만 스트림으로 빠르게 센다. Storm, 지금은 Flink나 Spark Structured Streaming. 결과물이 실시간 뷰다.
- 서빙 층: 질문이 오면 배치 뷰와 실시간 뷰를 합쳐 답한다.

## 두 뷰를 이어 붙이는 자리

경계는 반드시 배치 작업이 성공한 뒤 한 번에 옮긴다. 배치가 절반만 쓴 상태에서 경계부터 옮기면 그 사이 대시보드가 반쪽짜리 하루를 보여 준다. 실시간 뷰를 지우는 것도 경계를 옮긴 다음이다. 순서를 거꾸로 하면 잠깐 동안 그 구간이 아예 비어 보인다.

직접 짜 보면 경계 처리가 생각보다 까다롭다. 배치 뷰와 실시간 뷰를 시간대별 `[hour, amount]` 목록으로 받아, 경계(`cutoff`) 앞은 배치 뷰만, 경계부터는 실시간 뷰만 더해서 시간대 순으로 돌려주는 함수를 채워 보자. 실시간 뷰에는 같은 시간대 행이 여러 개 있을 수 있다(조금씩 더한 증분).

## 같은 규칙을 두 번 짜는 값

람다의 진짜 비용은 서버 대수가 아니라 코드다. 같은 "일 매출" 규칙이 Spark 잡에 한 벌, Flink 잡에 한 벌 있다. 처음에는 같아도 시간이 지나면 갈라진다. 실제로 갈라지는 지점은 대개 이런 곳이다.

- 시간대. 배치는 `Asia/Seoul` 기준 날짜로 자르는데 스트림은 UTC 창을 쓴다. 매일 0시부터 9시까지 아홉 시간 분량이 다른 날로 간다.
- 환불과 취소. 환불 이벤트를 빼는 규칙을 배치에만 넣었다. 실시간 숫자는 언제나 조금 크다.
- 중복 판단 키. 배치는 `order_id`로 지우는데 스트림은 `(order_id, event_type)`로 지운다.
- 언어와 라이브러리. 반올림 방식, 날짜 파싱, NULL을 0으로 보는지가 엔진마다 미묘하게 다르다.

첫 항목이 얼마나 쉽게 생기는지 주문 다섯 건으로 확인해 봤다. 결제 시각은 UTC로 저장돼 있다. 스트림 잡은 UTC 날짜로 자르고, 배치 SQL은 서울 날짜로 자른다고 하자. DuckDB 1.5(Python 패키지)로 돌렸다.

```sql
CREATE TABLE orders AS SELECT * FROM (VALUES
  ('o1', TIMESTAMPTZ '2026-10-20 16:30:00+00', 12000),
  ('o2', TIMESTAMPTZ '2026-10-20 23:10:00+00', 8000),
  ('o3', TIMESTAMPTZ '2026-10-21 03:00:00+00', 25000),
  ('o4', TIMESTAMPTZ '2026-10-21 14:50:00+00', 4000),
  ('o5', TIMESTAMPTZ '2026-10-21 15:20:00+00', 30000)
) t(order_id, paid_at, amount);
SET TimeZone = 'UTC';

-- 스트림 쪽 규칙: UTC 날짜로 자른다
SELECT CAST(paid_at AS DATE) AS utc_day, sum(amount) AS sales
FROM orders GROUP BY 1 ORDER BY 1;

-- 배치 쪽 규칙: 서울 날짜로 자른다
SELECT CAST(timezone('Asia/Seoul', paid_at) AS DATE) AS kst_day, sum(amount) AS sales
FROM orders GROUP BY 1 ORDER BY 1;
```


같은 다섯 건인데 "21일 매출"이 한쪽은 59,000원, 다른 쪽은 49,000원이다. o1, o2는 UTC로는 20일이지만 서울로는 21일 새벽이고, o5는 UTC로 21일 15시 20분이라 서울로는 22일 0시 20분이다. 둘 다 SQL 한 줄짜리 차이라 코드 리뷰에서 잘 안 보인다. 실제로는 한쪽 잡의 세션 시간대 설정이나 서버 기본 시간대가 바뀌어서 생기는 경우가 더 많다.

이걸 줄이는 방법도 몇 가지 나왔다. 규칙을 공용 라이브러리로 빼서 두 잡이 같은 함수를 부르게 하거나, 한 번 쓴 코드를 배치와 스트림 양쪽으로 컴파일하는 도구(트위터의 Summingbird가 이 시도였다)를 쓰거나, 두 엔진이 모두 SQL을 받게 해서 같은 SQL 파일을 넣는다. Spark는 같은 DataFrame 코드를 `read`와 `readStream`에 둘 다 쓸 수 있고, Flink는 같은 SQL을 배치 모드와 스트리밍 모드로 돌릴 수 있다. 그래도 창, 워터마크, 상태 만료 같은 스트림 전용 설정은 결국 한쪽에만 있다.

현실적인 안전장치는 비교 작업이다. 배치가 끝나면 그 구간의 실시간 결과를 지우기 전에 두 값을 시간대별로 비교해 차이 비율을 지표로 남긴다. 평소 0.5% 안쪽이던 차이가 어느 날 10%가 되면 둘 중 한쪽 규칙이 바뀐 것이다. 이 비교를 품질 검사로 묶는 방법은 [데이터 품질 검사](/posts/data-quality-checks)에서 다룬다.

## 로그 하나만 남기는 카파

2014년 Jay Kreps(Kafka를 만든 사람 중 하나)가 "람다를 다시 생각해 보자"는 글에서 다른 길을 제안했다. 배치 층을 없애고 스트림 처리 하나만 둔다. 대신 원본을 Kafka 같은 로그에 충분히 오래 보관해 두고, 다시 계산해야 할 때는 같은 스트림 코드를 로그의 처음부터 다시 돌린다. 이게 카파 아키텍처다.

카파가 기대는 사실은 두 가지다. 하나는 로그가 원본 그 자체라는 것이다. Kafka 토픽은 순서가 있는 추가 전용 기록이라, 오프셋 0부터 다시 읽으면 처음과 같은 이벤트가 같은 순서(파티션 안에서)로 나온다. 다른 하나는 스트림 엔진이 이제 충분히 믿을 만하다는 것이다. 체크포인트로 상태를 복구하고, 트랜잭션 싱크로 결과를 한 번만 반영하는 기능이 자리를 잡았다. 그 범위가 어디까지인지는 [Kafka에서 레이크까지](/posts/kafka-to-lake-pipeline)에서 직접 잘라 봤다.

로그를 오래 둔다는 건 설정 하나로 끝나지 않는다. 토픽의 `retention.ms`를 늘리면 브로커 디스크가 그만큼 커져야 한다. Kafka 3.9부터 정식 기능이 된 티어드 스토리지(`remote.storage.enable=true`)를 켜면 오래된 세그먼트를 S3 같은 객체 저장소로 내려 브로커 디스크 부담을 덜 수 있다. 로그 컴팩션은 여기서 쓰면 안 된다. 컴팩션은 키마다 마지막 값만 남기니, 주문 이벤트처럼 모든 기록이 필요한 토픽에 켜면 다시 재생할 원본이 사라진다.

```bash
# 주문 토픽을 무기한 보관하고, 오래된 세그먼트는 원격 저장소로 내린다
# (브로커에 remote.log.storage.system.enable=true와 원격 저장소 플러그인이 설정돼 있어야 한다)
kafka-configs.sh --bootstrap-server localhost:9092 --alter \
  --entity-type topics --entity-name orders \
  --add-config retention.ms=-1,remote.storage.enable=true,local.retention.ms=259200000
```

`local.retention.ms=259200000`은 브로커 로컬 디스크에는 3일치만 두라는 뜻이다. 그보다 오래된 데이터는 원격 저장소에서 읽는다. 다시 재생할 때 원격에서 읽는 구간은 로컬보다 느리니 재처리 시간 계산에 넣어야 한다.

로그를 무한히 두기 어려운 팀은 원본의 두 번째 사본을 레이크에 둔다. Kafka에서 레이크로 원본을 그대로 옮겨 쌓고, 로그 보관 기간을 넘는 과거는 레이크 파일을 소스로 다시 재생한다. Spark는 파일 폴더도 스트림 소스로 읽을 수 있어서, 변환 함수는 그대로 두고 입력만 바꾸면 된다.

```python
# 로그 보관 기간보다 오래된 구간은 레이크의 원본 파일을 스트림처럼 재생한다
old_orders = (spark.readStream.schema(order_schema)
              .option("maxFilesPerTrigger", 200)       # 한 번에 읽을 파일 수
              .parquet("s3://lake/raw/orders/"))
daily_sales(old_orders)                                 # 실시간 잡과 같은 함수
```

이렇게 하면 엄밀한 카파는 아니다. 원본이 두 군데 있으니 둘이 같은지 확인할 일이 생긴다. 그래도 규칙은 한 벌로 유지되니, 람다의 가장 아픈 비용은 피한다. 다만 레이크 파일에는 Kafka 파티션 안의 순서가 그대로 남지 않을 수 있으니, 순서에 기대는 로직(마지막 상태만 남기기 같은)은 이벤트 시각이나 버전 번호로 정렬하도록 짜 둔다.

Spark Structured Streaming으로 짜면 v2는 체크포인트 경로와 출력 경로만 다르게 준다. `startingOffsets`는 체크포인트가 없는 새 쿼리에만 적용되니, 옛 체크포인트를 재사용하면 이 옵션은 무시되고 v1이 멈춘 자리부터 읽는다. 처음에 이걸 몰라서 "처음부터 읽으라고 했는데 왜 어제 것부터 나오지" 하고 한참 헤매기 쉽다.

```python
# 다시 계산용 v2: 체크포인트와 출력 위치를 새로 준다
orders = (spark.readStream.format("kafka")
          .option("kafka.bootstrap.servers", "kafka:9092")
          .option("subscribe", "orders")
          .option("startingOffsets", "earliest")      # 체크포인트가 없을 때만 적용된다
          .option("maxOffsetsPerTrigger", 5_000_000)  # 한 번에 너무 많이 읽지 않게
          .load())

(daily_sales(orders)                                  # v1과 같은 함수, 환불 규칙만 추가됨
   .writeStream
   .option("checkpointLocation", "s3://ckpt/sales_v2/")
   .toTable("sales_v2"))
```

컨슈머 그룹으로 직접 읽는 앱이라면 오프셋을 옮기는 명령이 있다. 그룹에 붙어 있는 컨슈머가 없어야 실행된다. `--execute` 없이 돌리면 옮길 위치만 보여 주니 먼저 그렇게 확인한다.

```bash
# 그룹 sales-v2의 오프셋을 30일 전 시각으로 옮길 계획만 본다
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group sales-v2 --topic orders --reset-offsets --to-datetime 2026-09-21T00:00:00.000

# 확인했으면 실제로 옮긴다
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group sales-v2 --topic orders --reset-offsets --to-datetime 2026-09-21T00:00:00.000 --execute
```

읽는 쪽을 바꾸기 전에 두 테이블을 날짜별로 나란히 놓고 차이가 예상한 만큼인지 본다. 환불을 빼는 규칙을 넣었으니 v2가 조금 작아야 정상이다. 예시 테이블로 돌린 비교 쿼리다.

```sql
-- 겹치는 구간에서 v1과 v2를 날짜별로 비교한다
SELECT day, a.sales AS v1, b.sales AS v2, b.sales - a.sales AS diff,
       round(100.0 * (b.sales - a.sales) / a.sales, 2) AS diff_pct
FROM sales_v1 a JOIN sales_v2 b USING (day)
ORDER BY day;
```

```text

├────────────┼──────────┼──────────┼─────────┼──────────┤
│ 2026-10-19 │ 50120300 │ 49310800 │ -809500 │    -1.62 │
│ 2026-10-20 │ 49877100 │ 49051600 │ -825500 │    -1.66 │
│ 2026-10-21 │ 51884400 │ 50972100 │ -912300 │    -1.76 │
└────────────┴──────────┴──────────┴─────────┴──────────┘
```

볼 곳은 `diff_pct` 열이다. 날마다 1.6~1.8% 줄어든 건 환불 비율과 비슷하니 납득이 간다. 어느 하루만 30% 줄었거나, 줄어야 할 값이 늘었다면 바꾸기 전에 멈춘다. 날짜가 한쪽에만 있는 행을 찾으려면 `JOIN` 대신 `FULL OUTER JOIN`으로 바꿔 NULL인 행을 본다.

다시 계산하는 데 걸리는 시간은 미리 셈해 둔다. 평균 초당 2,000건이 들어오는 토픽이면 하루 172,800,000건, 30일이면 5,184,000,000건이다. v2가 초당 100,000건을 처리하면 51,840초, 14.4시간이 걸린다. 그동안 v1은 그대로 돌아야 하니 v2는 별도 자원으로 띄운다. 같은 클러스터에서 자원을 나눠 쓰면 다시 계산하는 동안 실시간 지연이 커진다. 브로커도 평소의 몇 배를 내보내야 하고, 원격 저장소에서 읽는 구간이면 그 읽기 속도가 상한이 된다.

여기서 카파의 약점이 드러난다. 1년치를 다시 계산하려면 시간이 너무 길다. 스트림 엔진은 이벤트를 하나씩 상태에 반영하는 구조라, 같은 양을 한 번에 훑는 배치 엔진보다 대체로 느리다. 상태가 큰 잡(긴 창, 큰 조인)이면 다시 재생하는 동안 상태 저장소가 커져 더 느려진다.

## 늦은 데이터는 어느 쪽에서도 공짜가 아니다

처음 시뮬레이션에서 버려진 13건은 람다든 카파든 어딘가에서 처리해야 한다. 람다는 이걸 배치에 맡긴다. 스트림이 버려도 다음 날 배치가 원본을 다시 세면서 주워 담는다. 그래서 속도 층은 워터마크를 짧게 잡아도 된다.

카파는 스스로 해결해야 한다. 방법은 크게 둘이다. 창을 닫은 뒤에도 일정 시간 늦은 이벤트를 받아 결과를 고쳐 쓰는 방법(Flink의 allowed lateness, 결과를 키로 덮어쓰는 업서트 싱크), 그리고 늦은 이벤트를 따로 모아 두었다가 주기적으로 그 구간만 다시 계산하는 방법이다. 둘째 방법은 사실상 작은 배치를 다시 들여온 것이다. 카파를 표방하는 팀도 실제로는 이렇게 "보정용 배치"를 둔 경우가 많다.

어느 쪽이든 결과 저장소가 고쳐 쓰기를 받아 줘야 한다. 추가만 되는 파일 더미에 결과를 쓰면 같은 시간대 결과가 두 줄 생긴다. 키로 덮어쓰는 테이블이나 구간을 통째로 갈아 끼우는 쓰기 방식이 필요하다. 레이크에서 이걸 가능하게 만든 게 다음에 볼 테이블 포맷이다. 언제 창을 닫을지 숫자로 정하는 법은 [이벤트 시간과 창](/posts/sd-ad-click-stream-windows)에, 닫힌 날짜를 다시 여는 실제 사례는 [Kafka에서 레이크까지](/posts/kafka-to-lake-pipeline)에 있다.

## 테이블 포맷이 경계를 흐리게 만들었다

람다가 길을 둘로 나눈 데는 저장소 사정도 있었다. HDFS의 파일은 고쳐 쓸 수 없었고, 그래서 정확한 결과는 배치가 통째로 새로 만들고, 실시간 결과는 HBase나 Cassandra 같은 다른 저장소에 따로 두었다. 두 저장소를 서빙 층이 이어 붙였다.

Delta Lake, Apache Iceberg, Apache Hudi 같은 테이블 포맷이 이 사정을 바꿨다. 객체 저장소의 Parquet 파일 위에 커밋 로그를 얹어, 파일 더미를 트랜잭션이 되는 테이블처럼 쓰게 해 준다(원리는 [데이터 레이크와 HDFS](/posts/data-lake-hdfs)의 커밋 로그 부분에 있다). 그러자 이런 일이 가능해졌다.

- 스트림 잡이 몇 초마다 같은 테이블에 커밋하고, 배치 잡과 BI 도구는 같은 테이블을 그냥 읽는다. 실시간 뷰와 배치 뷰를 따로 둘 이유가 줄었다.
- 늦게 온 이벤트를 `MERGE INTO`로 키를 맞춰 고쳐 쓴다. 구간 하나를 다시 계산해 `replaceWhere`(Delta)나 파티션 덮어쓰기로 갈아 끼우는 것도 원자적으로 된다.
- 테이블의 변경분을 다시 스트림으로 읽는다. Spark는 `spark.readStream.format("delta")`로 Delta 테이블에 새로 커밋된 내용을 따라 읽고, Iceberg도 Flink와 Spark에서 새 스냅숏을 따라 읽는 증분 읽기를 지원한다. 원본, 정제, 집계 테이블을 스트림으로 줄줄이 이을 수 있다.
- 지난 스냅숏을 읽는 타임 트래블로 "그때 그 숫자"를 다시 볼 수 있다. 다시 계산한 결과와 이전 결과를 비교하기 쉽다.

이렇게 되면 질문이 "배치냐 스트림이냐"에서 "이 테이블을 얼마나 자주 갱신하느냐"로 바뀐다. 같은 테이블을 5초마다 스트림으로 갱신할 수도 있고, 하루에 한 번 배치로 갱신할 수도 있다. 같은 SQL을 두 방식으로 돌리는 레이크하우스 구성에서는 람다처럼 규칙을 두 벌 두지 않으면서도, 카파처럼 모든 재계산을 스트림으로 할 필요도 없다. 몇 달치를 다시 계산할 때는 같은 변환을 배치로 돌려 구간을 덮어쓰면 된다.

그래도 공짜는 아니다. 몇 초마다 커밋하면 작은 파일과 커밋 기록이 쌓여 주기적인 컴팩션과 오래된 스냅숏 정리(`OPTIMIZE`, `VACUUM`, Iceberg의 `expire_snapshots`)를 돌려야 한다. 이 문제는 [Kafka에서 레이크까지](/posts/kafka-to-lake-pipeline)의 작은 파일 부분에서 직접 쟀다.

## 섞어 쓰는 하이브리드 수집

현장에서 람다나 카파를 교과서대로 하나만 쓰는 경우는 드물다. 데이터 출처마다 성격이 달라서 들여오는 방법을 섞는다. 이걸 흔히 하이브리드 수집이라고 부른다.

- 주문, 결제처럼 늦으면 곤란한 이벤트는 Kafka로 스트림 수집한다. 운영 DB의 변경은 [CDC](/posts/cdc-change-data-capture)로 스트림으로 뽑는다.
- 하루에 한 번 파일로 오는 외부 정산 데이터, 광고 플랫폼 리포트 API는 배치로 들여온다. 상대가 스트림을 주지 않으니 선택지가 없다.
- 스트림으로 받는 테이블도 가끔 전체 스냅숏을 배치로 한 번 떠서 비교한다. CDC가 몇 건을 놓쳤는지, 슬롯이 끊겼다 이어지며 빠진 구간이 없는지 확인하는 용도다.
- 처음 시스템을 붙일 때는 과거 데이터를 배치로 한 번에 넣고(백필), 그 시점 이후는 스트림으로 이어 받는다. 두 구간의 경계를 오프셋이나 LSN 같은 위치로 정확히 맞춰야 중복이나 빈틈이 생기지 않는다.

마지막 항목은 람다의 경계 문제와 똑같은 모양이다. 배치로 넣은 구간과 스트림으로 받는 구간을 어디서 자를지 하나의 위치 값으로 정하고, 그 값을 양쪽이 같이 쓴다. 들여온 데이터를 어디서 변환할지(ETL과 ELT)는 [ETL과 ELT](/posts/etl-vs-elt)에서, 이 수집 단계가 데이터 엔지니어링 전체에서 어디에 있는지는 [데이터 엔지니어링 수명 주기](/posts/data-engineering-lifecycle)에서 이어서 볼 수 있다.

## 무엇을 기준으로 고르나

정답 하나를 고르기보다 우리 상황에서 어느 비용이 더 큰지를 따진다.

람다가 여전히 맞는 경우가 있다. 몇 년치를 자주 다시 계산해야 하고, 정확한 숫자가 법적·재무적으로 중요하며(정산, 과금), 스트림 쪽은 "대충 맞는 실시간 미리 보기"면 충분할 때다. 이때는 배치가 정답이고 스트림은 보조라는 걸 팀 전체가 받아들이면 된다. 규칙이 두 벌인 비용은 비교 작업과 공용 라이브러리로 버틴다.

카파가 맞는 경우는 실시간 결과가 곧 제품이고(추천, 이상 거래 탐지, 실시간 순위), 재계산 범위가 로그 보관 기간 안에 들어오며, 팀이 스트림 엔진 운영에 익숙할 때다. 규칙이 한 벌이라 바꿀 때 덜 무섭다.

테이블 포맷 위의 레이크하우스 구성은 둘 사이 어딘가다. 원본을 로그와 테이블 양쪽에 두고, 변환은 한 벌로 쓰되 갱신 주기를 테이블마다 고른다. 웨어하우스 쪽에서 이 층을 어떻게 나누는지는 [데이터 웨어하우스 구조](/posts/data-warehouse-architecture)에 있다.

작은 서비스라면 대부분 이 고민이 필요 없다. 하루 한 번 배치와 PostgreSQL 집계 쿼리로 충분하다. 대시보드가 "몇 분 늦어도 되냐"고 물었을 때 "안 된다"는 답이 나오고, 그 숫자를 쓰는 사람이 실제로 있을 때 스트림을 들인다.

## 두 숫자가 다르다는 문의가 오면

처음 장면으로 돌아가서, 237,300원 차이 같은 문의가 오면 이런 순서로 본다.

1. 두 숫자가 같은 구간을 말하는지부터 본다. 날짜 경계의 시간대(KST/UTC), 이벤트 시각인지 도착 시각인지, 포함하는 상태(결제 완료만인지 취소 포함인지)를 맞춘다. 의외로 여기서 끝나는 경우가 많다.
2. 시간대별로 쪼개 비교한다. 차이가 하루 내내 고르게 퍼져 있으면 규칙 차이(환불, 중복 키)이고, 특정 시간대에 몰려 있으면 그 시간대의 장애나 지연이다.
3. 실시간 쪽이 크면 중복을 의심한다. 원본에서 같은 `order_id`가 몇 번 나오는지 센다. 작으면 늦은 데이터가 버려졌는지, 스트림 잡이 그 시간에 재시작했는지 본다.
4. 스트림 잡의 지표를 본다. 늦어서 버려진 이벤트 수(Flink는 `numLateRecordsDropped`), 컨슈머 지연, 체크포인트 실패 기록이다.
5. 어느 쪽이 기준인지 정해 두고 문서로 남긴다. "정산 기준은 다음 날 배치, 대시보드는 미리 보기"처럼 쓰여 있으면 다음 문의가 훨씬 짧아진다.

## 길을 몇 개 두든 규칙은 한 벌로

람다는 빠른 길과 정확한 길을 따로 두고 배치가 실시간의 실수를 덮어쓰게 했다. 그 대가로 같은 규칙을 두 벌 유지한다. 카파는 로그를 원본으로 삼아 한 벌의 스트림 코드를 다시 재생하는 것으로 재계산을 대신했고, 그 대가로 로그 보관 비용과 긴 재처리 시간을 진다. 테이블 포맷이 나온 뒤로는 같은 테이블을 스트림으로도 배치로도 갱신하게 되면서 둘의 경계가 흐려졌다. 어떤 구조를 쓰든 지킬 것은 같다. 원본을 지우지 않고, 규칙은 한 곳에 두고, 두 길이 만나는 경계를 하나의 값으로 정한다.

## 면접에서 나올 만한 질문

### 람다 아키텍처와 카파 아키텍처의 차이를 설명해 주세요

람다는 원본을 주기적으로 전부 다시 계산하는 배치 층과 최근 구간만 빠르게 세는 속도 층을 나란히 두고, 서빙 층에서 두 결과를 합친다. 배치가 정확한 값으로 실시간 값을 덮어쓰니 스트림 쪽 실수가 오래가지 않는다. 카파는 배치 층을 없애고 스트림 처리 하나만 둔다. 원본을 로그에 오래 보관하고, 다시 계산할 때는 같은 스트림 코드를 로그의 처음부터 재생한다.

### 람다 아키텍처의 가장 큰 단점은 무엇인가요

같은 집계 규칙을 배치 엔진과 스트림 엔진에 두 벌로 유지해야 한다. 시간대, 환불 처리, 중복 판단 키 같은 세부가 시간이 지나며 갈라지고, 그러면 두 숫자가 끝내 맞지 않는다. 공용 라이브러리, 같은 SQL을 두 엔진에서 돌리기, 배치가 끝날 때 두 결과를 비교하는 작업으로 줄일 수는 있지만 없앨 수는 없다.

### 람다와 카파 중 무엇을 고를지 어떤 기준으로 판단하나요

재계산 범위와 빈도, 정확성의 무게, 팀의 운영 역량을 본다. 몇 년치를 자주 다시 계산해야 하고 정산처럼 정확한 숫자가 중요하면 배치가 기준인 람다가 낫다. 실시간 결과 자체가 제품이고 재계산 범위가 로그 보관 기간 안에 들어오면 규칙이 한 벌인 카파가 낫다. 요즘은 테이블 포맷 위에서 변환을 한 벌로 쓰고 갱신 주기만 테이블마다 고르는 레이크하우스 구성도 흔하다.

### 카파 아키텍처에서 전체 재처리는 어떻게 하나요

돌고 있는 잡을 고치지 않고 새 버전 잡을 새 컨슈머 그룹과 빈 체크포인트로 띄워 로그의 처음(또는 필요한 시각)부터 읽게 한다. 결과는 새 테이블에 쓰고, 컨슈머 지연이 현재를 따라잡으면 겹치는 구간을 비교한 뒤 읽는 쪽을 새 테이블로 바꾼다. 옛 잡과 옛 테이블은 며칠 지켜본 뒤 정리한다. Spark에서는 옛 체크포인트를 재사용하면 `startingOffsets`가 무시되니 체크포인트 경로를 꼭 새로 준다.

### 카파에서 1년치를 다시 계산해야 한다면 어떤 문제가 있나요

먼저 로그에 1년치가 있어야 한다. 브로커 디스크로 감당하기 어려우니 티어드 스토리지로 객체 저장소에 내려 두거나, 레이크에 쌓인 원본을 스트림 소스로 다시 읽는다. 다음은 시간이다. 초당 2,000건 토픽 30일치가 51억 건이고, 초당 10만 건으로 재생해도 14시간이 넘는다. 스트림 엔진은 같은 양을 훑는 배치보다 대체로 느려서, 이 경우는 같은 변환을 배치로 돌려 구간을 덮어쓰는 편이 현실적이다.

### 카파에서 늦게 도착한 데이터는 어떻게 처리하나요

배치가 대신 주워 담아 주지 않으니 스트림이 스스로 처리해야 한다. 창을 닫은 뒤에도 정해진 시간 동안 늦은 이벤트를 받아 결과를 키로 덮어쓰는 업서트 싱크를 쓰거나, 늦은 이벤트를 따로 모아 두었다가 그 구간만 주기적으로 다시 계산한다. 어느 쪽이든 결과 저장소가 고쳐 쓰기를 지원해야 하고, 추가만 되는 파일에 쓰면 같은 구간 결과가 두 줄 생긴다.

### 레이크하우스 테이블 포맷이 이 논쟁에 어떤 변화를 줬나요

Delta Lake나 Iceberg 같은 포맷은 객체 저장소의 파일 위에 커밋 로그를 얹어 트랜잭션, 업서트, 스냅숏 읽기를 가능하게 했다. 그래서 스트림 잡이 몇 초마다 커밋한 테이블을 배치와 BI가 그대로 읽고, 늦은 데이터는 `MERGE`로 고치고, 테이블 변경분을 다시 스트림으로 읽을 수 있다. 실시간 뷰와 배치 뷰를 다른 저장소에 따로 둘 이유가 줄면서 선택이 "배치냐 스트림이냐"에서 "얼마나 자주 갱신하느냐"로 바뀌었다. 대신 작은 파일 정리와 스냅숏 만료 작업이 새로 생긴다.
