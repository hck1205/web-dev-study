로그인 API에 "IP당 1분에 5번"이라는 한도를 걸었다. 그런데 접근 로그를 보면 어떤 IP는 10:00:58부터 10:01:02까지 4초 사이에 로그인을 10번 시도했고, 10번 모두 통과했다. 한도를 잘못 건 게 아니다. 한도를 세는 방법이 그렇게 생겼을 뿐이다. "1분에 5번"이라는 말은 생각보다 여러 뜻으로 읽힌다. 어느 1분인지, 처음 몇 개를 몰아서 보내도 되는지, 넘친 요청은 버리는지 기다리게 하는지에 따라 알고리즘이 갈린다.

이 글은 그 알고리즘들을 같은 요청 기록에 돌려 보며 차이를 본다. 429 응답과 헤더, 키를 무엇으로 잡을지, 장애 때 어떻게 할지 같은 운영 이야기는 [요청 수 제한을 API에 붙이기](/posts/rate-limiting-in-practice)에서 따로 다룬다.

## 한도를 거는 이유부터

요청 수 제한(rate limiting)은 정해진 시간 동안 받을 요청 수에 상한을 두고, 넘은 요청은 거절하거나 늦추는 장치다. 이유는 여러 가지다.

- 한 사용자가 폭주해도 다른 사용자가 느려지지 않게 하는 공정성
- 비밀번호 대입, 쿠폰 번호 긁기 같은 남용 막기
- 외부 API나 LLM처럼 호출마다 돈이 드는 자원 보호
- 서버가 감당할 수 있는 양만 받아서 전체가 무너지지 않게 하기

마지막 것은 서버 자신의 상태를 보고 거절하는 부하 차단(load shedding)과 비슷해 보이지만 다르다. 요청 수 제한은 "누가" 보냈는지 키로 나눠 센다. 부하 차단은 키와 상관없이 서버가 바쁘면 거절한다. 둘 다 [장애가 번지지 않게 막는 패턴](/posts/resilience-patterns)의 한 부분이다.

제한 장치는 보통 요청이 앱에 닿기 전, 게이트웨이나 미들웨어에 둔다. 서버가 여러 대면 카운터는 Redis 같은 공유 저장소에 둔다. 아래 그림에서 다음을 누르면 요청이 제한 장치를 지나거나 막히는 모습이 나온다.

## 같은 요청 열다섯 개를 다섯 방식에 흘려 본다

한도는 "10초에 5개"로 잡고, 한 사용자가 보낸 요청 15개의 시각(초)을 고정해 두었다. 9초 근처와 10초 직후에 요청이 몰리게 만들었다. 다섯 알고리즘을 Node.js로 짜서 같은 기록에 돌렸다(Ubuntu 24.04, Node 22).

## 창을 고정하면 경계에서 두 배가 샌다

고정 윈도(fixed window)는 시간을 10초짜리 칸으로 자른다. 0~10초, 10~20초. 칸마다 카운터 하나를 두고 요청이 오면 1을 더한다. 5를 넘으면 거절하고, 다음 칸이 시작되면 0부터 다시 센다. Redis라면 명령 두 개로 끝난다.

```bash
# 칸 번호(시각을 10초로 나눈 몫)를 키에 넣고 하나 더한다
redis-cli --no-raw -p 6391 INCR rl:fixed:user42:179213040
# 키가 처음 생겼을 때만 10초 수명을 건다 (NX는 Redis 7.0부터)
redis-cli --no-raw -p 6391 EXPIRE rl:fixed:user42:179213040 10 NX
```

```text
(integer) 1
(integer) 1
```

두 번째 요청에서는 `INCR`이 2를 돌려주고 `EXPIRE ... NX`는 이미 수명이 있어서 0을 돌려준다. 키 하나에 숫자 하나라 메모리가 거의 안 들고 빠르다. 그런데 표의 `fixed` 열을 보면 1초에서 11초 사이 10초 동안 2, 3, 8, 9, 10.1, 10.2, 10.3, 10.5, 11초의 9개가 통과했다. 한도의 거의 두 배다. 아래 그림에서 다음을 누르면 경계에서 무슨 일이 생기는지 보인다.

로그인 대입처럼 짧은 시간에 몰아 보내는 공격에는 이 틈이 그대로 열린다. 반대로 통계용 일일 한도처럼 "하루에 1만 건" 정도의 큰 창에서는 경계에서 두 배가 새도 큰 문제가 없고, 사용자도 "자정에 초기화"라는 규칙을 이해하기 쉽다. 고정 윈도는 큰 창, 넉넉한 한도, 단순함이 중요할 때 고른다.

한 가지 더. 모든 키의 칸이 같은 순간(정각, 0초)에 바뀌면, 한도에 걸려 기다리던 클라이언트들이 그 순간 한꺼번에 몰려온다. 칸의 시작을 키마다 다르게(키의 해시만큼 밀어서) 잡으면 이 동시 몰림이 흩어진다.

## 요청 시각을 다 적어 두는 슬라이딩 로그

경계 문제를 없애는 가장 곧은 방법은 칸을 버리는 것이다. 요청이 올 때마다 지금부터 10초 전까지 통과한 요청이 몇 개였는지 정확히 센다. 그러려면 통과한 요청의 시각을 전부 적어 둬야 한다. 이게 슬라이딩 로그(sliding log)다. 표의 `log` 열은 어느 10초를 잘라 봐도 5개를 넘지 않는다. 대신 11초 요청이 통과한 이유는 1초 요청이 10초 창 밖으로 나갔기 때문이다.

Redis에서는 시각을 점수로 하는 정렬 집합(ZSET)으로 만든다.

```bash
# 10초보다 오래된 기록을 지운다 (지금이 1792130400000ms라고 하자)
redis-cli --no-raw -p 6391 ZREMRANGEBYSCORE rl:log:user42 -inf 1792130390000
# 이번 요청 시각을 넣는다. 같은 밀리초 요청이 겹치지 않게 멤버에 고유값을 붙인다
redis-cli --no-raw -p 6391 ZADD rl:log:user42 1792130400000 1792130400000-a1
# 남은 기록 수가 곧 최근 10초의 요청 수다
redis-cli --no-raw -p 6391 ZCARD rl:log:user42
```

```text
(integer) 0
(integer) 1
(integer) 1
```

실제로는 세 명령과 "5를 넘으면 방금 넣은 것을 빼고 거절"까지 한 번에 돌아야 하니 Lua 스크립트로 묶는다(아래 여러 대 이야기에서 본다). 정확한 대신 비싸다. 한도가 "1분에 1000번"이면 키 하나에 시각 1000개를 들고 있어야 한다. 같은 Redis 7.0에서 키 하나의 메모리를 재 봤다.

```bash
# 요청 1000개를 기록한 ZSET, 숫자 하나짜리 고정 윈도 키, 해시 두 칸짜리 토큰 버킷 키
redis-cli --no-raw -p 6391 MEMORY USAGE rl:log:big
redis-cli --no-raw -p 6391 MEMORY USAGE rl:fixed:big
redis-cli --no-raw -p 6391 MEMORY USAGE rl:tb:big
```

```text
(integer) 112992
(integer) 56
(integer) 104
```

키 하나에 약 110KB와 56바이트다. 사용자 10만 명이 한도 근처까지 쓰면 로그 쪽은 10GB를 넘는다. 그래서 슬라이딩 로그는 한도가 작고(분당 수십 번) 정확해야 하는 곳, 예를 들어 로그인이나 문자 인증 발송에 쓴다.

구현할 때 하나 조심할 것이 있다. 거절한 요청까지 로그에 넣는 구현이 있다. 그러면 계속 두드리는 클라이언트는 창이 영원히 꽉 차서 한 번도 통과하지 못한다. 벌을 주는 효과를 원하면 그렇게 하고, 아니면 통과한 요청만 적는다.

## 두 칸을 섞어 어림하는 슬라이딩 윈도 카운터

고정 윈도의 가벼움과 슬라이딩 로그의 정확함 사이에 슬라이딩 윈도 카운터(sliding window counter)가 있다. 칸마다 카운터 하나만 두는 건 고정 윈도와 같다. 다만 판단할 때 직전 칸의 카운터를 지금 칸에 걸친 비율만큼 섞는다.

```text
추정치 = 직전 칸 수 × (1 − 지금 칸에서 지난 비율) + 지금 칸 수
```

10.1초라면 지금 칸(10~20초)이 1% 지났으니, 지난 10초에는 직전 칸(0~10초)의 99%가 걸쳐 있다고 본다. 직전 칸에 5개가 통과했으니 추정치는 5 × 0.99 + 0 = 4.95다. 여기에 이번 요청 1을 더하면 5를 넘어서 거절한다. 직전 칸 안의 요청이 고르게 퍼져 있었다고 가정하는 셈이다. 아래 그림은 표의 `counter` 열을 만든 계산이다.

## 토큰 버킷은 몰림을 얼마나 봐줄지 정한다

토큰 버킷(token bucket)은 생각하는 방향이 다르다. 창 안의 개수를 세는 대신, 통에 토큰이 일정한 속도로 채워지고 요청이 토큰 하나씩을 쓴다고 본다. 통이 비면 거절한다. 설정값이 두 개다.

- 용량(capacity, burst): 한꺼번에 몰려와도 받아 줄 수 있는 최대 개수
- 충전 속도(rate): 길게 보면 허용하는 평균 속도

타이머가 토큰을 실제로 채우지는 않는다. 키마다 남은 토큰과 마지막 계산 시각만 저장해 두고, 요청이 올 때 "그사이 흐른 시간 × 속도"만큼 한꺼번에 더한다. 용량을 넘게는 쌓이지 않는다. 그래서 저장하는 값은 두 개뿐이다. 아래는 표의 `token` 열이다(용량 5, 초당 0.5개).

토큰 버킷이 표에서 가장 많이(12개) 통과시킨 이유가 여기 있다. 어떤 길이 W의 구간에서든 통과할 수 있는 최대 개수는 "용량 + 속도 × W"다. 용량 5, 초당 0.5개라면 10초 동안 최대 10개까지 지나갈 수 있다. 쉬다가 몰아서 쓰는 사람에게 너그럽고, 계속 몰아치는 사람은 결국 평균 속도로 묶는다. 사람이 쓰는 API는 대개 이렇게 움직이니 잘 맞는다. AWS API Gateway의 스로틀링, Stripe의 요청 제한 설명이 토큰 버킷을 쓴다고 밝히고 있다.

설정할 때는 두 값을 따로 생각한다. 평균 속도는 "길게 보면 이 이상은 안 된다"로, 용량은 "앱 첫 화면이 한꺼번에 보내는 요청 수"처럼 정상적인 몰림의 크기로 잡는다. 용량을 1로 두면 사실상 몰림을 하나도 허용하지 않는다. 페이지 하나가 API를 6번 동시에 부르는 앱이라면 첫 화면부터 429가 난다.

## 새는 양동이는 내보내는 속도를 고르게 만든다

토큰 버킷이 "평균만 지키면 몰려도 된다"라면 리키 버킷은 "나가는 쪽은 언제나 고르게"다. 뒤에 있는 시스템이 몰림을 못 견딜 때, 예를 들어 초당 처리량이 고정된 외부 결제사나 문자 발송사로 보내는 큐 앞에 맞다. 사용자 요청에 쓰면 거절 대신 지연이 생기고, 기다리는 동안 연결과 메모리를 붙잡는다. 줄이 길어지면 클라이언트는 이미 타임아웃으로 떠났는데 서버는 그 요청을 처리하는 일도 생긴다.

이름이 같아도 대기열 없이 "계량기"처럼 쓰는 리키 버킷도 있다. 양동이에 담긴 물의 양만 숫자로 기억하고, 넘치면 바로 거절한다. nginx의 `limit_req`가 이 방식이고 `nodelay`를 붙이면 지연 없이 동작한다([nginx에서 요청 수 제한](/posts/nginx-https-performance)). 계량기 리키 버킷은 사실상 토큰 버킷과 같은 판단을 한다. 이 계산을 타임스탬프 하나로 줄인 게 GCRA(Generic Cell Rate Algorithm)다. "다음 요청이 와도 되는 이론상 시각(TAT)" 하나만 저장하고, 요청이 오면 TAT가 지금보다 너무 멀리 앞서 있지 않은지만 본다. Redis 모듈 redis-cell이 이 방식이다.

받아서 고르게 내보내는 쪽(shaping)과 넘치면 버리는 쪽(policing)의 구분은 네트워크 장비에서도 그대로 쓰인다. 리눅스 `tc`로 패킷 속도를 다루는 이야기는 [트래픽 셰이핑과 QoS](/posts/traffic-shaping-qos)에 있다.

## 다섯 가지를 놓고 고르기

| 알고리즘 | 키당 저장 | 경계 몰림 | 몰림 허용 | 어울리는 곳 |
|---|---|---|---|---|
| 고정 윈도 | 숫자 1개 | 최대 2배 샘 | 칸 안에서 자유 | 일일·월간 한도, 과금 쿼터 |
| 슬라이딩 로그 | 요청 시각 전부 | 없음 | 창 안에서 자유 | 로그인, 인증 문자 같은 작은 한도 |
| 슬라이딩 윈도 카운터 | 숫자 2개 | 거의 없음(추정) | 창 안에서 자유 | 일반 API의 분 단위 한도 |
| 토큰 버킷 | 숫자 2개 | 용량만큼 | 용량으로 조절 | 사용자 API, 게이트웨이 |
| 리키 버킷(대기열) | 대기열 | 없음 | 지연으로 흡수 | 외부로 나가는 호출, 작업 큐 |

정답이 하나는 아니다. 실무에서는 섞어 쓴다. "초당 10개(토큰 버킷) 그리고 하루 1만 개(고정 윈도)"처럼 짧은 창으로 몰림을, 긴 창으로 총량을 막는다. 둘 중 하나라도 걸리면 거절한다.

## 서버가 여러 대면 세는 일이 경쟁이 된다

앱 서버가 한 대면 메모리의 변수로 세면 된다. 여러 대면 두 가지 문제가 생긴다. 서버마다 따로 세면 한도가 대수만큼 늘어난다. 그래서 Redis 하나에 모아서 센다. 그런데 모아서 세도 "읽고, 계산하고, 쓰는" 세 단계가 끼어들 수 있다.

토큰 버킷을 Redis에서 `HMGET`으로 읽고, 앱에서 계산하고, `HSET`으로 쓰는 코드를 만들어서 앱 서버 두 대가 같은 키로 동시에 40개를 보내게 했다. 용량은 10이다. 같은 계산을 Lua 스크립트로 Redis 안에서 한 번에 하는 방식과 나란히 돌렸다.

```bash
# 앱 서버 두 대(연결 두 개)가 같은 키로 동시에 40개를 보낸다
node redis-tb.js
```

```text

마지막 응답 [allowed, 남은 토큰, 기다릴 ms]: [0,0,1000]
```

실제로 쓴 스크립트다. 시간을 앱 서버가 아니라 Redis의 `TIME`에서 가져온다. 앱 서버들의 시계가 조금씩 어긋나 있으면, 시계가 늦은 서버가 쓴 시각 때문에 토큰이 거꾸로 계산될 수 있어서다(스크립트를 통째로 복제하던 예전 방식에서는 `TIME` 같은 값이 복제본마다 달라져 제약이 있었다. Redis 5부터 스크립트가 낸 쓰기 결과를 복제하는 방식이 기본이 됐고 7.0부터는 이 방식만 남아서, 스크립트 안에서 `TIME`을 써도 된다).

```lua
-- KEYS[1]: 버킷 키, ARGV[1]: 용량, ARGV[2]: 초당 충전량
local cap  = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local t    = redis.call('TIME')                  -- Redis 서버 시계를 쓴다
local now  = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)
local b    = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or cap
local ts     = tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) / 1000 * rate)
local allowed = 0
if tokens >= 1 then tokens = tokens - 1; allowed = 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000) + 1000)
local wait = 0
if allowed == 0 then wait = math.ceil((1 - tokens) / rate * 1000) end
return {allowed, math.floor(tokens), wait}
```

`PEXPIRE`는 꼭 건다. 통이 다시 꽉 찰 시간이 지나면 키가 없을 때와 상태가 같으니 지워도 된다. 수명을 안 걸면 한 번 왔다 간 IP의 키가 영원히 남아 메모리를 채운다. 고정 윈도에서 `INCR` 뒤에 `EXPIRE`를 따로 보내는 코드도 같은 함정이 있다. 그 사이에 앱이 죽으면 수명 없는 키가 남는다. 둘을 Lua로 묶거나, 위에서처럼 `EXPIRE ... NX`를 매번 같이 보낸다.

Redis Cluster를 쓴다면 스크립트가 만지는 키는 모두 같은 슬롯에 있어야 한다. 위 스크립트는 키가 하나라 상관없지만, 초 단위 버킷과 일 단위 카운터를 한 스크립트에서 함께 보려면 `rl:{user42}:sec`, `rl:{user42}:day`처럼 중괄호 해시 태그로 같은 슬롯에 모은다.

요청마다 Redis를 한 번 다녀오는 게 부담이면 섞는다. 서버마다 메모리에 작은 토큰 버킷을 두고 Redis에서 토큰을 10개씩 미리 받아 와 쓰는 식이다. Redis 왕복은 10분의 1로 줄고, 대신 서버가 받아 두고 못 쓴 토큰만큼 정확도가 떨어진다. 정확도와 비용을 바꾸는 선택이다. Redis가 느려지거나 죽었을 때 통과시킬지 막을지는 운영 쪽 결정이라 [다음 글](/posts/rate-limiting-in-practice)에서 실제로 Redis를 멈춰 놓고 본다.

## 직접 짜 보는 토큰 버킷

## 숫자를 고를 때 자주 하는 실수

로그인처럼 막아야 하는 요청에 고정 윈도를 쓰면 위에서 본 경계 몰림이 그대로 열린다. 공격자는 칸이 바뀌는 순간을 금방 알아낸다. 작은 한도는 슬라이딩 로그나 토큰 버킷으로 건다.

창을 너무 길게 잡는 실수도 있다. "1시간에 3600번"과 "1초에 1번"은 평균이 같지만, 앞쪽은 1초에 3600번을 몰아 보내도 막지 못한다. 몰림을 막고 싶으면 짧은 한도를 함께 건다.

반대로 너무 깐깐하면 정상 사용자가 걸린다. 앱 화면 하나가 동시에 부르는 API 수, 새로고침, 실패 후 재시도까지 더한 값이 몰림의 크기다. 숫자를 정하기 전에 지금 접근 로그에서 키별 초당·분당 요청 수의 p99를 먼저 뽑아 본다. 거기서 여유를 두고 시작해서, 처음에는 거절하지 않고 기록만 하는 모드로 며칠 돌려 본다.

부동소수 토큰도 문제가 될 수 있다. 초당 0.1개처럼 작은 속도로 남은 시간을 계산하면 0.9999 같은 값 때문에 "1초 뒤에 오라"고 했는데 1초 뒤에도 거절되는 일이 생긴다. 토큰을 밀리 단위 정수로 저장하거나, 기다릴 시간을 올림하고 조금 여유를 준다.

## 다섯 가지는 결국 두 질문이다

어느 구간을 기준으로 셀지(고정 칸, 미끄러지는 창, 평균 속도)와 넘친 요청을 어떻게 할지(버린다, 늦춘다)다. 고정 윈도는 싸지만 경계에서 새고, 슬라이딩 로그는 정확하지만 비싸고, 카운터는 그 둘을 어림으로 잇는다. 토큰 버킷은 몰림의 크기를 직접 정하고, 리키 버킷은 나가는 속도를 고르게 만든다. 여러 대에서 셀 때는 읽고 쓰는 일을 원자적으로 묶는 것까지가 알고리즘의 일부다.

## 면접에서 나올 만한 질문

### 토큰 버킷과 리키 버킷은 무엇이 다른가요?

토큰 버킷은 용량만큼 몰리는 요청을 받아 주고 평균 속도만 지키게 하고, 대기열을 쓰는 리키 버킷은 나가는 속도를 언제나 일정하게 만든다. 그래서 토큰 버킷은 사용자 API처럼 가끔 몰리는 트래픽에, 리키 버킷은 뒤의 시스템이 일정한 속도만 견딜 때 맞다. 다만 대기열 없이 넘치면 거절하는 계량기 방식의 리키 버킷(nginx limit_req, GCRA)은 토큰 버킷과 같은 판단을 한다.

### 고정 윈도의 문제는 무엇이고 어떻게 고치나요?

칸이 바뀌는 순간 카운터가 0이 되어, 칸 끝과 다음 칸 처음에 몰아 보내면 짧은 시간에 한도의 두 배까지 통과한다. 정확히 막으려면 요청 시각을 모두 기억하는 슬라이딩 로그를, 메모리를 아끼려면 직전 칸을 비율만큼 섞는 슬라이딩 윈도 카운터를 쓴다. 일일 쿼터처럼 창이 크고 한도가 넉넉하면 고정 윈도로도 충분하다.

### 슬라이딩 윈도 카운터는 얼마나 정확한가요?

직전 칸 안의 요청이 고르게 퍼져 있다고 가정하는 어림이라, 요청이 칸 앞쪽에 몰렸으면 깐깐하게, 뒤쪽에 몰렸으면 너그럽게 틀린다. 키당 숫자 두 개로 경계 몰림을 거의 없애는 대가다. 트래픽이 많을수록 요청이 고르게 퍼져서 오차가 작아지고, Cloudflare는 실제 트래픽에서 잘못 판단한 비율이 0.003%였다고 밝혔다.

### 토큰 버킷에서 용량과 충전 속도는 어떻게 정하나요?

충전 속도는 길게 봤을 때 허용할 평균이고, 용량은 정상 사용자가 한꺼번에 보내는 요청 수다. 어떤 길이 W의 구간에서든 최대 "용량 + 속도 × W"개가 통과한다는 걸 기억하고 정한다. 실제 값은 접근 로그에서 키별 요청 수의 p99를 보고 여유를 둔 다음, 거절 없이 기록만 하는 모드로 먼저 확인한다.

### 서버가 여러 대일 때 요청 수 제한은 어떻게 구현하나요?

서버마다 메모리에서 세면 한도가 대수만큼 곱해지니 Redis 같은 공유 저장소에 카운터를 둔다. 이때 읽고 계산하고 쓰는 과정을 Lua 스크립트로 묶어 원자적으로 처리해야 한다. 나눠서 하면 동시 요청이 같은 값을 읽어 토큰 하나로 여러 요청이 통과하고, 실제로 용량 10에 동시 40개를 보냈을 때 40개가 모두 통과했다. 시간은 앱 서버 시계 대신 Redis의 TIME을 쓰고, 키에는 수명을 건다.

### Redis 왕복이 부담스러우면 어떻게 하나요?

서버마다 로컬 토큰 버킷을 두고 Redis에서 토큰을 묶음으로 받아 와 쓰게 할 수 있다. Redis 호출은 묶음 크기만큼 줄지만 서버가 받아 두고 못 쓴 토큰만큼 한도가 덜 정확해진다. 정확도가 덜 중요한 넉넉한 한도라면 아예 서버별 로컬 제한에 대수를 나눈 값을 걸기도 한다.

### 슬라이딩 로그에서 거절한 요청도 기록해야 하나요?

보통은 통과한 요청만 기록한다. 거절한 요청까지 기록하면 계속 두드리는 클라이언트는 창이 비지 않아 영영 통과하지 못한다. 공격자를 일부러 오래 묶어 두고 싶을 때만 그렇게 하고, 그 경우에도 키에 수명을 걸어 메모리가 끝없이 늘지 않게 한다.
