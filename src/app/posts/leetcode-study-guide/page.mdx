문제는 수천 개지만 그걸 푸는 생각은 스무 가지 남짓이다. 이 글은 그 생각, 곧 패턴 단위로 문제를 묶어 푸는 순서와 한 문제를 푸는 순서, 막혔을 때와 복습하는 법, 면접장에서 말하며 푸는 법을 정리한다. 이 블로그의 LeetCode 문제 글 88편과 패턴 글을 잇는 허브이기도 하다. 입력 크기에서 기법을 고르는 일반론은 [알고리즘 문제 접근법](/posts/algorithms-overview)에, 복잡도를 세는 법은 [Big O 표기법](/posts/big-o-notation)에 있으니 여기서는 반복하지 않는다.

## LeetCode에서 무엇을 연습하나

LeetCode는 온라인 저지(online judge)다. 문제를 읽고 함수를 짜서 제출하면 서버가 숨겨진 테스트 수십에서 수백 개를 돌려 결과를 알려 준다. 결과는 대개 넷 중 하나다. 통과(Accepted), 오답(Wrong Answer), 시간 초과(Time Limit Exceeded), 실행 중 오류(Runtime Error). 문제마다 Easy, Medium, Hard 난이도와 주제 태그가 붙어 있다.

코딩 테스트와 기술 면접에 이런 문제가 쓰이는 이유는, 짧은 시간에 몇 가지를 한꺼번에 볼 수 있어서다. 문제를 정확히 읽고 모호한 부분을 묻는지, 느린 풀이에서 낭비를 찾아 줄이는지, 경계 사례를 스스로 떠올리는지, 코드를 읽기 좋게 쓰는지. 회사마다 비중은 다르지만, 정답 여부만 보는 곳은 드물고 과정을 함께 본다는 점은 대체로 같다.

그러니 LeetCode로 연습하는 건 문제를 외우는 게 아니라 위의 과정을 몸에 붙이는 일이다. 같은 문제가 그대로 나오는 경우는 많지 않고, 조건을 바꾼 변형이 나온다. 외운 풀이는 조건이 바뀌면 무너지고, 패턴으로 이해한 풀이는 조건이 바뀌어도 어디를 고쳐야 하는지 보인다.

점선은 선수 관계가 약하다는 뜻이다. 비트 연산과 수학·기하는 배열을 다룰 줄 알면 언제 봐도 되니, 지칠 때 쉬어 가는 묶음으로 쓴다. 굵은 줄기는 셋이다.

배열 줄기. 배열과 해시맵에서 시작해 [투 포인터](/posts/two-pointers-pattern), [슬라이딩 윈도](/posts/sliding-window-pattern), [단조 스택](/posts/monotonic-stack-pattern)으로 간다. 모두 "한 번 훑으면서 무엇을 기억해 두나"의 변형이다. 이 묶음의 첫 문제는 [Two Sum](/posts/leetcode-two-sum)이고, 해시맵의 원리는 [해시맵](/posts/ds-hash-map)에 있다.

탐색 줄기. [이분 탐색](/posts/binary-search)은 정렬이 주는 단조성을 쓰는 법이고, [연결 리스트](/posts/ds-linked-list)는 포인터를 다루는 손을 만든다. 둘을 지나면 [트리](/posts/ds-binary-tree-bst)에서 재귀를 본격적으로 쓴다. 트리에서 [트라이](/posts/ds-trie), [힙](/posts/ds-heap), [백트래킹](/posts/recursion-backtracking)으로 갈라진다.

최적화 줄기. 백트래킹에서 같은 계산이 반복되는 걸 보면 [동적 계획법](/posts/dynamic-programming)으로 넘어가고, 백트래킹의 탐색을 정점과 간선 위로 옮기면 [그래프](/posts/ds-graph-bfs-dfs)가 된다. 그래프에 가중치가 붙으면 [최단 경로](/posts/shortest-path-algorithms)와 [최소 신장 트리](/posts/minimum-spanning-tree) 같은 고급 그래프 문제다. 힙에서 "지금 가장 좋은 것을 꺼낸다"를 증명과 함께 쓰면 [그리디](/posts/greedy-algorithms)이고, 그리디의 대표 무대가 [구간 문제](/posts/interval-problems-pattern)다. 비트는 [비트 연산](/posts/bit-manipulation)에 정리돼 있다.

한 패턴에서는 다섯 문제를 연달아 푼다. 첫 문제에서 틀을 익히고, 두세 번째에서 그 틀의 변형을 보고, 마지막 문제(대개 Hard)에서 틀을 다른 것과 섞는다. 다섯 문제를 다 풀면 그 패턴의 허브 글이나 자료구조 글을 다시 읽는다. 처음 읽을 때 지나쳤던 문장이 이제 무슨 말인지 보인다.

## 어떤 언어로 풀까

면접에서 언어를 고를 수 있다면, 가장 오래 쓴 언어로 푼다. 문법을 떠올리느라 생각이 끊기는 게 가장 큰 손해다. 다만 언어마다 함정이 다르니 그건 알고 들어가야 한다. 자바스크립트(Node.js 22), Python 3.13, Java 21에서 같은 것을 실제로 돌려 봤다.

| | 자바스크립트 | Python | Java |
|---|---|---|---|
| 정수 범위 | 2^53까지 정확, 넘으면 BigInt | 크기 제한 없음 | `int` 21억, `long` 9.2 × 10^18 |
| 기본 힙 | 없음 (직접 구현) | `heapq` (최소 힙) | `PriorityQueue` |
| 덱 | 없음 (`shift`는 O(n)) | `collections.deque` | `ArrayDeque` |
| 정렬된 맵 | 없음 | 없음 (`bisect`로 대신) | `TreeMap` |
| 기본 정렬 | 비교 함수 없으면 문자열 순 | 숫자 그대로, 안정 정렬 | 기본형 배열은 불안정, 객체는 안정 |
| 재귀 깊이 | 약 1.2만에서 RangeError | 기본 한도 1000 | 약 2.3만에서 StackOverflowError |

재귀 깊이는 기본 설정에서 깊이를 1씩 늘리는 함수를 돌려 끊기는 지점을 잰 값이다. 아래는 세 언어에서 각각 찍은 줄이다. 함수의 지역 변수 크기와 환경에 따라 달라지니 자릿수 정도로 보면 된다.
```text
JS depth 12556 RangeError
py depth 999 RecursionError
java depth 23077
```

Python의 1000은 꽤 낮다. 노드가 10만 개인 한쪽으로 치우친 트리를 재귀 DFS로 돌리면 바로 끊긴다. `sys.setrecursionlimit`으로 올릴 수 있지만 실제 스택 크기를 넘으면 프로세스가 죽으니, 깊어질 수 있는 탐색은 명시적인 스택으로 바꾸는 편이 안전하다.

나머지 연산도 언어마다 다르다. −7을 3으로 나눈 나머지와 몫이다.

```text
JS: -1 -3 -2
Python: 2 -3 -2
Java: -1 -2 2
```

세 언어에서 각각 찍은 줄이다. 자바스크립트는 `-7 % 3`, `Math.floor(-7 / 3)`, `Math.trunc(-7 / 3)`이고, Python은 `-7 % 3`, `-7 // 3`, `int(-7 / 3)`, Java는 `-7 % 3`, `-7 / 3`, `Math.floorMod(-7, 3)`이다. Python만 나머지가 늘 0 이상이고 몫을 내림한다. 자바스크립트와 Java는 나머지의 부호가 나눠지는 수를 따르고, 정수 나눗셈은 0 쪽으로 자른다.

원형 배열의 인덱스를 `(i - 1) % n`으로 구하면 자바스크립트와 Java에서는 `i = 0`일 때 −1이 나와 배열 밖을 읽는다. Python만 n − 1이 나온다. `((i - 1) % n + n) % n`으로 쓰면 어느 언어든 맞다.

자바스크립트로 푼다면 힙과 덱이 없다는 게 가장 크다. 힙이 필요한 문제(Top K, 다익스트라, 회의실 배정)가 꽤 많으니, 30줄 남짓한 최소 힙을 미리 짜 두고 손에 익힌다. 구현은 [힙과 우선순위 큐](/posts/ds-heap)에 있다. LeetCode의 자바스크립트 환경에는 `@datastructures-js/priority-queue` 같은 라이브러리가 들어 있는 경우가 있지만, 면접 환경에는 없을 수 있으니 기대지 않는다. 그 밖의 자바스크립트 함정(기본 정렬, `Math.max(...arr)`의 인자 한계)은 [알고리즘 문제 접근법](/posts/algorithms-overview#자바스크립트로-풀-때-조심할-것)에 실제 출력과 함께 있다.

Python은 코드가 짧고 자료구조가 다 있어서 면접에서 쓰기 편하다. 대신 같은 반복문이 느려서, 다른 언어로는 아슬아슬하게 통과하는 풀이가 Python에서는 시간 초과가 날 수 있다. Java는 코드가 길지만 정수 범위와 자료구조가 분명하다. 정수 오버플로와 비교자 빼기(`a[0] - b[0]`) 버그만 조심하면 된다. 이 버그의 실제 모습은 [구간 문제 패턴](/posts/interval-problems-pattern#경계값-닫힌-구간과-열린-구간)에 있다.

## 한 문제를 푸는 여섯 단계

패턴을 알아도 한 문제 안에서 순서가 엉키면 시간을 버린다. 매번 같은 여섯 단계를 거치면 덜 엉킨다. Product of Array Except Self(238번)로 따라가 보자. 정수 배열에서 각 칸마다 "자기를 뺀 나머지 전부의 곱"을 구한다. 나눗셈은 쓰면 안 된다.

1. 이해. 문제를 내 말로 한 줄로 줄인다. "각 칸에 대해 왼쪽 전부의 곱 × 오른쪽 전부의 곱." 이렇게 줄이는 순간 풀이 방향이 보이는 경우가 많다. 제약도 적는다. 길이 최대 10^5, 값은 −30에서 30, 곱은 32비트 정수 안에 들어간다고 보장된다.
2. 예시. 문제 예제 말고 내가 하나 만든다. 특히 경계를 건드리는 것으로. `[2, 3]`(가장 짧다), `[5, 0, 2]`(0이 하나), `[0, 0]`(0이 둘), `[-2, -3, 4]`(음수).
3. 느린 풀이. 칸마다 나머지를 다 곱하면 O(n²)이다. 10^5이면 10^10번이라 안 된다. 그래도 말로 해 둔다. 이게 나중에 정답을 확인하는 기준이 된다.
4. 개선. 느린 풀이에서 반복되는 일을 찾는다. i번 칸의 왼쪽 곱과 i + 1번 칸의 왼쪽 곱은 한 칸 차이다. 왼쪽 곱을 앞에서부터 누적하고, 오른쪽 곱을 뒤에서부터 누적하면 두 번 훑기로 끝난다. 누적 합의 곱셈 버전이다.
5. 복잡도. 시간 O(n), 추가 공간은 결과 배열을 빼면 O(1)이다. 결과 배열에 왼쪽 곱을 먼저 채우고, 오른쪽 곱은 변수 하나로 들고 가며 곱하면 된다.
6. 테스트. 2번에서 만든 예시를 손으로 넣어 본다. 0이 둘이면 모든 칸이 0이어야 한다.

이 과정을 직접 해 보자. 내 풀이는 무작위 입력 2,000개로 느린 풀이와 같은 결과를 내는 걸 확인했다.

```js
function fast(nums) {
  const total = nums.reduce((p, x) => p * x, 1);
  return nums.map((x) => total / x);
}
function slow(nums) {
  return nums.map((_, i) => nums.reduce((p, x, j) => (j === i ? p : p * x), 1));
}
for (let k = 0; k < 1000; k++) {
  const len = 2 + Math.floor(Math.random() * 4);
  const t = Array.from({ length: len }, () => Math.floor(Math.random() * 7) - 3); // -3..3, 작게
  const a = JSON.stringify(fast(t)), b = JSON.stringify(slow(t));
  if (a !== b) { console.log("입력", JSON.stringify(t), "fast", a, "slow", b); break; }
}
```

```text
입력 [3,0] fast [0,null] slow [0,3]
```

0이 하나 있으면 0 / 0이 NaN이 되고(JSON에서는 `null`로 찍힌다), 다른 칸도 0이 된다. 입력 값 범위를 −3에서 3, 길이를 2에서 5로 작게 잡은 게 요령이다. 작은 입력에서 찾은 반례는 손으로 따라갈 수 있다. 무작위라 돌릴 때마다 다른 반례가 나오지만, 0이 들어간 입력이라는 점은 같다.

## 복습은 간격을 늘려 가며

한 번 푼 문제는 생각보다 빨리 잊는다. 그래서 푼 날 바로 다시 보는 것보다 간격을 늘려 가며 다시 푸는 게 낫다. 다시 풀었을 때 막힘없이 풀리면 간격을 늘리고, 막히면 처음 간격으로 돌린다. 이 블로그의 [오늘 할 일](/study) 화면도 읽은 글을 1, 2, 4, 7, 15일 간격으로 다시 보여 주는 같은 방식(라이트너 상자)을 쓴다.

복습할 때 코드를 처음부터 다 짜지 않아도 된다. 문제 이름만 보고 30초 안에 "패턴, 핵심 관찰, 복잡도"를 말할 수 있으면 통과로 친다. 말이 막히면 그때 코드를 짠다. 그래야 하루에 복습할 수 있는 문제 수가 늘어난다.

노트는 길게 쓰지 않는다. 위 그림의 예처럼 한 줄이면 된다. 길게 쓴 노트는 다시 읽지 않는다. 특히 "내가 틀린 곳"을 꼭 적는다. 같은 사람은 같은 곳에서 또 틀린다. 노트를 몇 주 모아 보면 내가 자주 틀리는 곳(경계 등호, 빈 입력, 오버플로)이 패턴처럼 보이고, 면접 직전에는 그 목록만 다시 본다.

## 면접장에서 말하며 풀기

혼자 풀 때와 면접에서 풀 때의 가장 큰 차이는 소리 내어 말해야 한다는 것이다. 면접관은 머릿속을 볼 수 없으니, 말하지 않은 생각은 없던 것과 같다. 문제를 받은 뒤의 큰 흐름(질문으로 제약 확인 → 느린 풀이 → 개선 방향 합의 → 코드 → 손으로 실행)은 [알고리즘 문제 접근법](/posts/algorithms-overview#면접에서-문제를-받은-뒤의-순서)에 정리해 뒀다. 여기서는 단계마다 실제로 무슨 말을 하는지만 적는다.

제약을 물을 때는 질문을 구체적으로 한다. "입력이 비어 있을 수 있나요?", "음수가 있나요?", "답이 여러 개면 아무거나 돌려줘도 되나요?" 질문은 그 자체로 내가 어떤 경계를 생각하고 있는지 보여 준다.

느린 풀이를 말할 때는 복잡도까지 붙인다. "모든 짝을 보면 O(n²)이고, n이 10^5라 느립니다. 대신 정답 확인용으로는 쓸 수 있습니다." 코드를 쓰기 전에 개선 방향을 말하고 반응을 본다. "배열이 정렬돼 있으니 양 끝에서 좁혀 오면 O(n)이 될 것 같습니다. 이 방향으로 짜도 될까요?" 여기서 면접관이 고개를 갸웃하면 다른 방향을 생각할 기회가 생긴다. 20분을 짠 뒤에 듣는 것보다 훨씬 낫다.

코드를 쓰는 동안에는 무엇을 하는지 짧게 말한다. 전부 읽어 줄 필요는 없고, 결정을 내리는 줄에서만 말한다. "여기서 `l < r`로 두는 건 같은 칸을 두 번 쓰지 않으려고입니다." 막혔을 때도 침묵하지 말고 막힌 지점을 말한다. "중복 조합을 거르는 위치가 헷갈리는데, 예시로 따라가 보겠습니다." 면접관이 힌트를 줄 수 있는 건 내가 어디서 막혔는지 알 때뿐이다.

다 쓴 뒤에는 실행할 수 없는 환경이 많으니 예시 하나를 손으로 따라간다. 변수 값을 줄마다 소리 내어 적는다. 이때 버그를 스스로 찾으면 감점이 아니라 오히려 좋은 인상을 준다.

## 얼마나 풀어야 하나

숫자로 정하기보다 "패턴마다 처음 보는 Medium을 25분 안에 풀 수 있나"로 판단한다. 이 블로그의 88문제는 18개 패턴을 고르게 덮도록 고른 것이다. 다 풀고 나서 각 패턴 허브 글의 면접 질문에 막힘없이 답할 수 있으면, 그다음은 문제 수를 늘리기보다 처음 보는 문제로 시간을 재고 푸는 연습이 낫다. LeetCode의 주간 대회(Weekly Contest)가 그 연습에 좋다. 시간이 정해져 있고 문제를 처음 본다는 점이 면접과 같다.

## 면접에서 나올 만한 질문

### 문제를 받으면 가장 먼저 무엇을 하나요?

문제를 내 말로 한 줄로 다시 말하고, 입력 크기와 값 범위, 빈 입력, 음수, 중복, 답이 없을 때의 반환값을 묻는다. 입력 크기는 허용되는 복잡도를 정해 주고, 나머지는 경계 사례가 된다. 풀이를 생각하기 전에 경계 사례 예시를 하나 만들어 둔다.

### 바로 최적 풀이가 떠오르지 않으면 어떻게 하나요?

느린 풀이를 복잡도와 함께 먼저 말한다. 그다음 느린 풀이에서 같은 계산이 반복되는 곳을 찾아 줄인다. 느린 풀이는 개선의 출발점이면서 나중에 결과를 대조할 기준도 된다.

### 시간 복잡도를 어떻게 설명하나요?

반복문 하나하나가 아니라 각 원소가 몇 번 처리되는지로 센다. 안쪽에 while이 있어도 포인터가 한 방향으로만 움직이면 전체는 O(n)이다. 정렬이 들어가면 O(n log n)이 바닥이 되고, 공간은 결과를 빼고 추가로 쓴 것만 센다.

### 코드를 다 쓴 뒤 어떻게 검증하나요?

처음에 만든 경계 사례 예시를 손으로 따라가며 변수 값을 줄마다 확인한다. 실행할 수 있는 환경이면 느린 풀이와 작은 무작위 입력으로 결과를 대조한다. 작은 입력에서 찾은 반례가 버그의 위치를 가장 빨리 알려 준다.

### 면접에서 어떤 언어를 쓰는 게 좋나요?

가장 오래 쓴 언어가 가장 좋다. 다만 언어별 함정은 알고 간다. 자바스크립트는 힙과 덱이 없고 기본 정렬이 문자열 순이며, Python은 재귀 한도가 1000이고 반복문이 느리며, Java는 int 오버플로와 비교자 빼기 버그가 있다.

### 같은 문제가 나오지 않는데 LeetCode를 푸는 의미가 있나요?

문제를 외우는 게 아니라 패턴과 과정을 익히는 데 의미가 있다. 실제 면접에는 조건을 바꾼 변형이 나오는데, 패턴으로 이해한 풀이는 바뀐 조건에서 어디를 고쳐야 하는지 보인다. 질문하고, 느린 풀이에서 개선하고, 손으로 검증하는 과정 자체가 평가 대상이다.

### 막혔을 때 면접관에게 무엇을 말하나요?

막힌 지점을 구체적으로 말한다. 어떤 부분이 헷갈리는지, 지금 어떤 예시로 확인하려는지 말하면 면접관이 방향을 잡아 줄 수 있다. 침묵하면 면접관은 내가 어디까지 왔는지 알 수 없다.
