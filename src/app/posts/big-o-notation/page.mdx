주문 목록에서 이미 처리한 주문을 걸러내는 코드가 있다고 해 보자.

```js
const pending = orders.filter((order) => !processedIds.includes(order.id));
```

개발 환경에는 주문이 100건, 처리한 ID도 100개쯤이라 눈 깜짝할 새 끝난다. 그런데 운영 데이터로 돌리니 주문 10만 건, 처리한 ID 10만 개에서 요청이 시간 초과로 끊긴다. 데이터는 1,000배 늘었는데 느려진 정도는 1,000배가 아니다.

코드를 다시 보면 `filter`가 주문마다 한 번씩 돌고, 그 안의 `includes`가 처리한 ID 배열을 처음부터 훑는다. 찾는 ID가 없으면 끝까지 다 본다. 100 × 100이면 비교가 1만 번이지만, 10만 × 10만이면 100억 번이다. 데이터가 1,000배 늘 때 일이 100만 배 늘어난 것이다.

이렇게 입력이 커질 때 일이 어떤 모양으로 늘어나는지 나타내는 말이 Big O 표기법이다. 이 코드는 O(n²)이고, `processedIds`를 `Set`으로 바꾸면 O(n)이 된다. 왜 그런지, 그리고 이런 판단을 어떻게 빨리 하는지 차례로 따라가 본다.

## 몇 초가 아니라 늘어나는 모양을 센다

Big O는 실행 시간을 초 단위로 말하지 않는다. 같은 코드도 컴퓨터, 언어, 엔진의 최적화에 따라 시간이 다르게 나오기 때문이다. 대신 입력 크기 n에 따라 기본 연산(비교, 대입, 배열 칸 읽기 같은 것)을 몇 번 하는지 세고, 그 횟수가 n이 커질 때 어떤 모양으로 늘어나는지만 본다.

```js
function sum(nums) {
  let total = 0;                 // 1번
  for (const x of nums) {        // n번 돈다
    total += x;                  // n번
  }
  return total;                  // 1번
}
```

대략 2n + 2번이다. n이 두 배가 되면 일도 거의 두 배가 된다. 이렇게 n에 비례해 늘면 O(n)이라고 쓴다. 정확한 횟수가 2n + 2인지 3n + 5인지는 상관하지 않는다.

같은 방식으로 메모리도 센다. 입력 말고 추가로 얼마나 쓰는지를 공간 복잡도라고 부르고, 위 함수는 변수 하나만 더 쓰니 O(1) 공간이다. 시간과 공간은 뒤에서 서로 바꿔 쓰는 모습으로 다시 만난다.

## 상수와 작은 항을 버리는 이유

Big O에서는 상수 배와 작은 항을 버린다. 2n + 2는 O(n), 3n² + 100n + 7은 O(n²)이다. 처음엔 이게 대충 넘기는 것처럼 보였는데, n을 키워 보면 이유가 보인다.

3n² + 100n에서 n = 10이면 300 + 1,000이라 오히려 100n 쪽이 크다. n = 1,000이면 300만 + 10만이라 n² 항이 97%쯤 된다. n = 100만이면 100n은 전체의 0.003%다. n이 커질수록 가장 빨리 자라는 항 하나가 전체를 결정한다. Big O가 보려는 게 바로 "n이 아주 클 때"다.

상수 3을 버리는 것도 같은 이유다. 3n²과 n²은 n이 두 배가 될 때 둘 다 네 배가 된다. 늘어나는 모양이 같다. 반면 3n²과 n은 아무리 n 쪽에 큰 상수를 곱해도 언젠가 n² 쪽이 따라잡는다.

그렇다고 상수가 실전에서 무의미하다는 뜻은 아니다. n이 작으면 O(n²)인 삽입 정렬이 O(n log n)인 병합 정렬보다 빠를 수 있다. 그래서 V8의 `Array.prototype.sort`가 쓰는 TimSort도 짧은 구간은 삽입 정렬로 처리한다. Big O는 "n이 커지면 무엇이 이기는가"를 말해 줄 뿐, 지금 크기에서 무엇이 빠른지는 재 봐야 안다.

중첩 반복문에서 모든 쌍을 한 번씩 비교하면 몇 번 비교하는지 직접 세어 보자. `i`가 0부터, `j`는 `i + 1`부터 돈다.

## 자주 만나는 모양들

실무에서 만나는 복잡도는 대부분 몇 가지 모양 안에 들어간다. 빠른 것부터 본다.

O(1)은 입력이 아무리 커도 일이 일정하다. 배열의 `i`번째 칸 읽기, `Map`과 `Set`에서 키 찾기(평균), 배열 끝에 `push`하기(분할 상환, 뒤에서 본다)가 여기 속한다.

```js
arr[42];
seen.has(id);
```

O(log n)은 매번 남은 범위를 절반씩 버린다. 정렬된 배열에서 이진 탐색이 대표적이다. 100만 개에서도 20번이면 찾는다. 2를 20번 곱하면 1,048,576이라 100만보다 크기 때문이다. 균형 잡힌 이진 탐색 트리, DB의 B-트리 인덱스 탐색도 로그 모양이다.

O(n)은 입력을 한 번씩 본다. 반복문 하나, `map`, `filter`, `reduce`, 그리고 `includes`, `indexOf`, `find` 같은 선형 탐색이다.

O(n log n)은 좋은 정렬의 모양이다. 병합 정렬, 힙 정렬, TimSort가 여기 있다. 비교만으로 정렬하는 알고리즘은 최악의 경우 이보다 빠를 수 없다는 게 증명되어 있다. n개를 줄 세우는 방법은 n!가지이고, 비교 한 번은 가능성을 많아야 절반으로 줄이니 log₂(n!)번은 비교해야 하는데, 이 값이 대략 n log₂ n이다.

O(n²)은 반복문 안의 반복문이다. 모든 쌍 비교, 버블 정렬과 삽입 정렬, 그리고 처음 장면처럼 반복문 안에서 `includes`를 부르는 코드가 여기 있다.

O(2ⁿ)은 원소마다 "넣는다/뺀다" 두 갈래로 나뉘는 문제다. 부분집합을 전부 만들면 2ⁿ개가 나온다. 아래처럼 메모 없이 짠 피보나치도 지수 모양이다.

```js
function fib(n) {
  return n < 2 ? n : fib(n - 1) + fib(n - 2);
}
```

호출 횟수를 세어 보면 fib(10)은 177번, fib(30)은 2,692,537번, fib(40)은 331,160,281번이다. n이 1 늘 때마다 호출이 약 1.618배(황금비)씩 는다. 엄밀하게는 2ⁿ보다 조금 느리게 자라는 Θ(1.618ⁿ)이고, O(2ⁿ)은 넉넉하게 잡은 상한이다. 이미 계산한 값을 저장해 두면(메모이제이션) fib(0)부터 fib(40)까지 41개 값을 한 번씩만 계산하니 O(n)이 된다.

O(n!)은 순서를 전부 늘어놓는 문제다. n개 원소의 순열을 모두 만들거나, 외판원 문제를 모든 경로로 풀면 이렇게 된다. 10!은 3,628,800이고 12!은 479,001,600이다. 원소 12개만 돼도 손을 못 댄다.

모양마다 얼마나 빨리 커지는지 그림으로 보자. 막대 높이가 연산 횟수이고, 다음을 누르면 n이 두 배씩 커진다. 모든 단계가 같은 축척이다.

n이 2일 때는 다섯 막대가 거의 같은 높이다. 입력이 작으면 복잡도가 별 차이를 만들지 않는다는 뜻이다. n이 16이 되면 n²만 혼자 위로 솟는다. 이 그림에 2ⁿ을 그렸다면 n = 16에서 65,536이라 n² 막대의 256배 높이가 된다.

## n이 백만이 되면

그림의 n은 16까지였다. 실제 서비스의 n은 훨씬 크다. 각 모양에 n = 10, 1,000, 1,000,000을 넣어 계산하면 이렇다.

| n | log₂ n | n log₂ n | n² | 2ⁿ | n! |
|---|---|---|---|---|---|
| 10 | 3.3 | 33 | 100 | 1,024 | 3,628,800 |
| 1,000 | 10.0 | 9,966 | 1,000,000 | 약 1.07 × 10³⁰¹ | 약 4.02 × 10²⁵⁶⁷ |
| 1,000,000 | 19.9 | 19,931,569 | 10¹² | 301,030자리 수 | 5,565,709자리 수 |

컴퓨터가 단순 연산을 1초에 1억(10⁸) 번쯤 한다고 어림하면, n = 100만에서 O(n log n)은 0.2초, O(n²)은 10⁴초, 그러니까 약 2시간 47분이다. 2ⁿ은 n = 1,000에서 이미 우주 나이를 아득히 넘는다.

이 어림셈은 코딩 테스트에서도 그대로 쓴다. 입력 제한이 n ≤ 100,000이면 O(n²)은 안 되고 O(n log n) 이하를 찾아야 한다는 신호다. n ≤ 20이면 2ⁿ(약 100만)도 괜찮다는 신호이고, n ≤ 10이면 순열을 다 만들어도 된다.

## 운이 좋을 때와 나쁠 때

같은 코드라도 입력에 따라 일이 다르다. 배열에서 값을 앞에서부터 찾는 선형 탐색은 찾는 값이 맨 앞이면 1번, 없으면 n번 비교한다. 그래서 최선, 평균, 최악을 나눠서 말한다. 보통 Big O로 말할 때는 따로 밝히지 않으면 최악의 경우를 뜻한다.

퀵 정렬은 셋이 크게 갈리는 예다. 기준값(피벗)을 하나 골라 작은 것과 큰 것으로 나누고 양쪽을 다시 정렬한다. 피벗이 매번 가운데쯤이면 절반씩 나뉘어 O(n log n)이다. 그런데 이미 정렬된 배열에서 매번 첫 원소를 피벗으로 고르면 한쪽은 비고 다른 쪽에 n−1개가 남는다. 이게 n번 반복되어 O(n²)이 된다. 그래서 실제 구현은 피벗을 무작위로 고르거나 세 값의 중앙값을 쓰고, C++ 표준 라이브러리의 introsort처럼 재귀가 너무 깊어지면 힙 정렬로 갈아타서 최악을 막는다.

해시 테이블도 마찬가지다. `Map.get`이 O(1)이라는 건 평균 이야기다. 키의 해시값이 골고루 퍼진다는 가정이 깔려 있다. 모든 키가 같은 칸에 몰리면 그 칸의 목록을 훑어야 해서 한 번 찾는 데 O(n)이 된다. 일부러 충돌하는 키를 대량으로 보내 서버를 멈추게 하는 공격(HashDoS)이 2011년에 여러 언어의 웹 프레임워크를 상대로 발표됐고, 그 뒤 많은 언어가 해시 함수에 실행마다 바뀌는 무작위 값(시드)을 섞기 시작했다. ECMAScript 명세도 `Map`과 `Set`에 "평균적으로 원소 수보다 느리게 늘어나는(sublinear) 접근 시간"만 요구한다.

## O는 최악이라는 뜻이 아니다

앞에서 "따로 밝히지 않으면 최악"이라고 했는데, 이 말 때문에 O는 최악이고 Ω는 최선이라고 외우기 쉽다. 둘은 서로 다른 질문에 답한다. 최선·평균·최악은 "어떤 입력을 넣었나"를 고르는 일이고, O·Ω·Θ는 그렇게 정한 연산 횟수 함수를 다른 함수와 견주는 말이다.

정의는 이렇다. 어떤 양수 c와 n₀가 있어서 n ≥ n₀인 모든 n에서 f(n) ≤ c·g(n)이면 f(n) = O(g(n))이다. 부등호 방향만 바꿔 f(n) ≥ c·g(n)이면 Ω(g(n)), 위아래를 모두 g의 상수 배로 끼울 수 있으면 Θ(g(n))다. 숫자로 확인해 보자. f(n) = 3n² + 100n은 언제나 3n² 이상이다. 그리고 4n² 이하가 되는 건 100n ≤ n², 곧 n ≥ 100부터다. n = 99에서는 39,303 대 39,204로 아직 크고, n = 100에서 40,000으로 같아진다. c₁ = 3, c₂ = 4, n₀ = 100으로 위아래가 끼워지니 f(n) = Θ(n²)다. "작은 n은 봐주고, 상수 배는 허용한다"는 앞 절의 직관이 정의에 그대로 들어 있다.

여기서 등호는 사실 "속한다"에 가깝다. O(n²)은 n²보다 빨리 자라지 않는 함수 전체를 묶은 집합이라서, n도 n log n도 그 안에 들어간다. 선형 탐색을 O(n²)이라고 써도 수학적으로 틀리지 않은 이유다. 쓸모가 없을 뿐이다. 실무와 면접에서 "O(n)"이라고 할 때는 보통 Θ처럼 딱 맞는 상한을 뜻한다.

O와 Ω가 크거나 같음을 허용한다면, 소문자 o와 ω는 엄격하게 작고 큰 쪽이다. f(n) = o(g(n))은 c를 아무리 작게 잡아도 충분히 큰 n부터는 f(n)이 c·g(n)보다 작다는 뜻이고, 비율 f(n)/g(n)이 0으로 간다고 생각하면 쉽다. n/n²은 n = 1,000에서 0.001, n = 100만에서 0.000001로 0을 향해 가니 n = o(n²)이다. n log₂ n도 n = 100만에서 n²의 0.002%라 o(n²)다. 반면 2n/n은 n이 얼마든 2라서 2n은 O(n)이지만 o(n)은 아니다. ω는 그 반대로, n² = ω(n)이다.

| 표기 | 수의 비교로 치면 | 예 |
|---|---|---|
| f = O(g) | f ≤ g | 3n² + 100n = O(n²), n = O(n²) |
| f = Ω(g) | f ≥ g | 3n² + 100n = Ω(n²), n² = Ω(n) |
| f = Θ(g) | f = g | 3n² + 100n = Θ(n²) |
| f = o(g) | f가 g보다 작다 | n = o(n²), 그러나 2n은 o(n)이 아니다 |
| f = ω(g) | f가 g보다 크다 | n² = ω(n log n) |

이제 "최악 = O"가 왜 오해인지 보인다. 삽입 정렬로 비교 횟수를 세 보면 이미 정렬된 1,000개는 999번, 거꾸로 정렬된 1,000개는 499,500번이었다. 최선의 경우는 Θ(n), 최악의 경우는 Θ(n²)이다. 최악의 경우를 Ω로 말할 수도 있다. 비교 정렬의 하한 "최악의 경우 Ω(n log n)"은 최악을 Ω로 말한 문장이다. 최선의 경우를 O로 말하는 것도 된다("삽입 정렬은 최선의 경우 O(n)"). 경우를 정하지 않고 삽입 정렬 전체를 한 마디로 하면 O(n²)이고 Ω(n)이지만, 입력에 따라 n에서 n²까지 오가니 Θ로 묶을 수 있는 함수 하나는 없다. 최선/최악과 O/Ω는 서로 다른 축이라 "최악의 경우 Θ(n²)"처럼 함께 쓰는 게 가장 정확하다.

면접에서 "해시 조회는 O(1)인가요"를 받으면 이 축을 나눠서 답하면 된다. "평균의 경우 Θ(1), 최악의 경우 Θ(n)이다." 경우와 표기를 따로 말하면 꼬리 질문에서 말이 꼬이지 않는다.

## 가끔 비싼 연산은 나눠서 센다

자바스크립트 배열의 `push`는 O(1)이라고 한다. 그런데 배열은 메모리에 연속으로 자리를 잡아 두는 구조라, 자리가 꽉 차면 더 큰 자리를 새로 잡고 기존 원소를 전부 옮겨야 한다. 그 순간의 `push`는 O(n)이다. 그런데도 O(1)이라고 하는 이유를 아래 그림에서 보자. 용량이 1인 빈 배열에 8번 `push`하고, 꽉 차면 용량을 두 배로 늘린다.

비싼 `push`는 용량이 1, 2, 4, 8…일 때만 오고, 그 사이에는 싼 `push`가 점점 길게 이어진다. 복사 횟수를 다 더하면 1 + 2 + 4 + … 은 항상 n보다 작다. 그래서 n번 `push` 전체가 O(n)이고, 한 번에 나눠 주면 O(1)이다. 이렇게 연산 여러 번을 묶어 평균을 내는 방식을 분할 상환(amortized) 분석이라고 한다. 확률에 기대는 평균과 달리, 어떤 순서로 넣어도 보장되는 값이다.

두 배가 아니어도 일정한 비율로 늘리기만 하면 된다. V8은 대략 1.5배에 16을 더해 늘리고, 자바 `ArrayList`는 1.5배로 늘린다. 비율이 아니라 10칸씩처럼 고정된 양을 늘리면 복사가 n²/10쯤 쌓여서 `push`가 분할 상환으로도 O(n)이 된다.

분할 상환 O(1)은 매번 빠르다는 뜻이 아니다. 가끔 한 번은 길게 멈춘다. 게임의 프레임이나 지연 시간에 민감한 요청 처리에서는 이 한 번이 문제가 될 수 있어서, 크기를 알면 미리 자리를 잡아 두기도 한다(`new Array(n)`, 자바 `new ArrayList<>(n)`).

## 메모리도 같은 방식으로 센다

공간 복잡도에서 놓치기 쉬운 게 재귀의 호출 스택이다. 함수를 부를 때마다 지역 변수와 돌아갈 위치가 스택에 한 칸씩 쌓이고, 함수가 끝나야 빠진다.

```js
function sumTo(n) {
  return n === 0 ? 0 : n + sumTo(n - 1);
}
sumTo(1_000_000);
// RangeError: Maximum call stack size exceeded
```

이 함수는 변수를 따로 만들지 않지만 호출이 n단계 쌓이니 O(n) 공간이다. 스택은 크지 않다. Node.js 22 기본 설정에서 아무것도 안 하는 재귀를 돌려 보면 1만 2천 단계쯤에서 멈췄다. 엔진, 설정, 함수의 지역 변수 수에 따라 달라지는 값이다. 그래서 깊이가 입력에 비례하는 재귀는 반복문으로 바꾸는 게 안전하다. ES2015 명세에 꼬리 호출 최적화가 들어가 있긴 하지만 사파리(JavaScriptCore)만 구현했고 V8은 하지 않는다.

메모 없는 fib는 호출이 3억 번 넘게 일어나도 스택 깊이는 n을 넘지 않아서 공간은 O(n)이다. 시간과 공간이 따로 움직인다는 걸 보여 주는 예다. 퀵 정렬도 평균 O(log n)의 스택을 쓰지만, 최악에는 재귀가 n단계 쌓인다. 병합 정렬은 시간은 항상 O(n log n)인 대신 합칠 때 쓸 O(n)짜리 임시 배열이 필요하다.

두 번째 테스트가 함정이다. `Map`을 먼저 다 채우고 나서 찾으면 3을 찾을 때 자기 자신(인덱스 0)과 짝지어 `[0, 0]`이 나올 수 있다. 짝을 먼저 찾고 나서 자기를 넣으면 이 문제가 사라진다.

## 정렬해 두면 log n으로 찾는다

해시 말고 정렬로 푸는 길도 있다. 정렬된 배열이라면 가운데 값과 비교해서 절반을 버리는 이진 탐색이 된다. 아래 그림은 11칸짜리 정렬된 배열에서 91을 찾는다. 강조된 칸이 지금 비교하는 가운데 칸이다.

그런데 정렬에 O(n log n)이 든다. 한 번만 찾을 거라면 그냥 O(n)으로 훑는 게 낫다. 정렬은 한 번 해 두고 여러 번 찾을 때 이득이다. 질문이 q번이면 매번 훑을 때 O(q × n), 정렬해 두면 O(n log n + q log n)이다. q가 커질수록 차이가 벌어진다.

같은 문제를 해시로 풀면 `Set`을 만드는 데 O(n), 찾을 때마다 평균 O(1)이라 더 빨라 보인다. 그래도 정렬을 고르는 경우가 있다. "50 이상 80 이하인 값"처럼 범위를 찾거나, 가장 가까운 값을 찾거나, 순서대로 꺼내야 하면 해시는 쓸모가 없다. DB 인덱스가 해시가 아니라 정렬된 B-트리를 기본으로 쓰는 이유다. 메모리를 더 쓰지 않는다는 장점도 있다. 정렬된 배열의 두 포인터(양 끝에서 좁혀 오기)로 Two Sum을 풀면 정렬 O(n log n)에 추가 공간 없이 끝난다. 다만 원래 인덱스가 섞이니 인덱스를 돌려줘야 하는 문제라면 따로 기억해 둬야 한다.

이진 탐색을 직접 짤 때 흔한 실수가 두 가지다. 가운데를 `Math.floor((lo + hi) / 2)`로 구하면 자바스크립트에선 괜찮지만, 32비트 정수를 쓰는 언어에서는 `lo + hi`가 넘칠 수 있어서 `lo + (hi - lo) / 2`로 쓴다. 그리고 `lo <= hi`와 `lo < hi`, `hi = mid`와 `hi = mid - 1`을 섞어 쓰면 무한 루프가 나거나 마지막 칸을 놓친다. 범위를 닫힌 구간으로 볼지 반열린 구간으로 볼지 하나로 정하고 지킨다. 구간 정의와 lower bound, 답을 놓고 찾는 탐색은 [이분 탐색 글](/posts/binary-search)에서 이어서 다룬다.

## 자바스크립트에 숨은 반복문

처음 장면처럼 복잡도가 튀는 곳은 대개 반복문이 눈에 안 보이는 곳이다. 메서드 하나가 안에서 배열 전체를 훑는다.

`includes`, `indexOf`, `find`, `some`은 O(n)이다. 반복문 안에서 부르면 O(n²)이 된다. 같은 배열을 여러 번 찾는다면 `Set`이나 `Map`을 한 번 만들어 둔다.

`shift`와 `unshift`는 명세상 배열 앞에서 하나를 빼거나 넣으면서 나머지 원소의 인덱스를 전부 한 칸씩 옮긴다. 엔진이 특정 경우에 이걸 싸게 처리하기도 하지만 보장되는 건 아니다. 큐로 쓸 때 `while (queue.length) queue.shift()`는 O(n²)이 될 수 있다. BFS 같은 데서는 읽을 위치를 가리키는 인덱스(`head++`)를 따로 두는 편이 확실하다.

```js
// 앞에서 꺼낼 때마다 원소를 옮길 수 있다
while (queue.length) visit(queue.shift());

// 꺼낼 위치만 옮긴다. O(1)
for (let head = 0; head < queue.length; head++) visit(queue[head]);
```

전개 구문(`...`)은 복사다. `reduce` 안에서 매번 새 객체나 새 배열을 펼쳐 만들면, k번째 단계에서 k개를 복사하니 전체가 O(n²)이다.

```js
// O(n²): 단계마다 지금까지 모은 것을 통째로 복사한다
const byId = users.reduce((acc, u) => ({ ...acc, [u.id]: u }), {});

// O(n): 같은 객체에 하나씩 넣는다
const byId2 = Object.fromEntries(users.map((u) => [u.id, u]));
```

`splice`로 중간에 넣거나 빼는 것도 뒤쪽 원소를 옮기니 O(n)이다. 정렬을 반복문 안에서 다시 부르는 실수도 있다. 반복할 때마다 O(n log n)이 곱해진다.

문자열 이어 붙이기는 언어마다 다르다. 자바의 `String`은 바꿀 수 없어서 반복문에서 `+=`를 하면 매번 새 문자열로 전체를 복사해 O(n²)이 되고, 그래서 `StringBuilder`를 쓴다. 자바스크립트 엔진은 이어 붙인 결과를 바로 복사하지 않고 조각을 이어 둔 구조(rope)로 들고 있다가 필요할 때 한 번에 펼치는 방식을 써서, `+=`를 반복해도 보통 문제가 없다. 그래도 조각을 배열에 모아 `join`하는 쪽이 의도가 분명하다.

## 운영에서 n²은 이런 모양으로 드러난다

운영에서 복잡도 문제는 "느리다"는 한 줄로 온다. 코드를 읽기 전에 숫자로 모양을 확인하는 방법이 몇 가지 있다.

가장 간단한 건 n을 두 배씩 늘려 보는 것이다. 두 배로 늘렸을 때 시간이 두 배면 O(n), 네 배면 O(n²), 조금 넘는 두 배면 O(n log n)이다. 처음 장면의 주문 걸러내기를 `includes` 버전과 `Set` 버전으로 나눠 Node.js 22에서 재 봤다. 처리한 ID와 주문 ID가 겹치지 않게 만들어서 `includes`가 매번 끝까지 훑게 했다.

```text
pendingSlow n=10000: 119.8ms
pendingSlow n=20000: 481.6ms  (x4.0)
pendingSlow n=40000: 1941.0ms  (x4.0)
pendingSlow n=80000: 7861.7ms  (x4.1)
pendingFast n=10000: 2.5ms
pendingFast n=20000: 4.4ms  (x1.8)
pendingFast n=40000: 7.9ms  (x1.8)
pendingFast n=80000: 21.7ms  (x2.7)
```

`includes` 쪽은 두 배마다 정확히 네 배씩 는다. `Set` 쪽은 두 배 안팎이고, 마지막 단계의 2.7배는 메모리 할당과 GC가 섞인 흔들림이다. 작은 n에서는 JIT 최적화가 덜 끝나서 배율이 들쭉날쭉하니, 몇 번 돌려서 배율의 경향을 본다. 운영 지표로 치면 "주문 수와 응답 시간을 같은 그래프에 놓았을 때 직선이 아니라 위로 휘는 곡선"이 이 모양이다. 데이터가 적은 개발 환경에서는 안 보이고, 고객사 하나가 커지거나 배치가 한 달 치를 처리하는 날 갑자기 나타난다.

어느 함수가 범인인지는 CPU 프로파일로 찾는다. Node.js는 `--cpu-prof`로 실행하면 끝날 때 `.cpuprofile` 파일을 남기고, 이 파일은 크롬 개발자 도구의 Performance 패널에 끌어다 놓으면 열린다. 여기서는 파일을 직접 읽어 함수별 self time(그 함수 자신이 쓴 시간) 상위 몇 개를 뽑았다.

```bash
# n=40000으로 한 번 돌리고 프로파일을 남긴다
node --cpu-prof slow-job.js
```

```text
  1861 ms   90.5%  pendingSlow slow-job.js:1
   153 ms    7.4%  (anonymous) slow-job.js:2
    16 ms    0.8%  (program)
     6 ms    0.3%  (garbage collector)
     5 ms    0.2%  compileForInternalLoader realm:385
```

`includes`는 따로 보이지 않고 그것을 부른 함수의 self time으로 잡혔다. 엔진이 내장 메서드를 호출한 쪽에 인라인으로 넣어 버리기 때문이다. 그래서 프로파일에서 "이 함수가 시간을 다 먹는데 안에 특별한 게 없다"면, 그 안의 `includes`, `find`, `indexOf`, 전개 구문처럼 숨은 반복문을 먼저 의심한다. 브라우저라면 Performance 패널 아래쪽 Bottom-Up 탭을 Self Time으로 정렬하면 같은 걸 볼 수 있다.

반복문이 코드가 아니라 네트워크에 숨어 있기도 하다. 주문 100개를 가져온 뒤 주문마다 회원 정보를 따로 조회하면, 쿼리 하나하나는 빨라도 왕복이 n번이다. 프로파일에서는 CPU가 놀고 있고 시간은 대기로 사라진다. DB 쪽 슬로 쿼리 로그에도 안 잡힌다. 같은 모양의 짧은 쿼리가 요청 하나에 수백 번 찍히는 걸로 알아본다. 이건 [쿼리 고쳐 쓰기 글](/posts/sql-query-rewrite)의 N+1 이야기와 같다.

가장 극적인 건 정규식이다. 겹치는 반복이 들어간 패턴은 실패할 때 가능한 나누는 방법을 전부 시도해서 2ⁿ으로 느려진다.

```js
const re = /^(a+)+$/;
re.test("a".repeat(n) + "!"); // 끝의 !때문에 결국 실패한다
```

```text
n=22: 29ms
n=23: 54ms
n=24: 111ms
n=25: 219ms
n=26: 456ms
n=27: 895ms
```

글자 하나가 늘 때마다 두 배다. 같은 입력에 `/^a+$/`는 0.08ms다. 사용자가 입력한 문자열을 이런 정규식에 넣으면, 서른 글자 남짓한 요청 하나로 Node.js의 이벤트 루프를 몇십 초 동안 세울 수 있다(ReDoS). 이메일이나 URL 검증처럼 직접 짠 정규식은 중첩된 `+`, `*`가 있는지 보고, 입력 길이를 먼저 제한하고, 검증된 라이브러리를 쓴다.

## 다시 주문 걸러내기로

처음 코드가 느렸던 건 반복문 안에 숨은 `includes` 때문이었다. 주문 100건에서는 1만 번이라 보이지 않던 비용이, 10만 건에서는 100억 번이 되어 드러났다. Big O는 이걸 미리 보게 해 주는 도구다. 연산 횟수를 n의 식으로 세고, 가장 빨리 자라는 항만 남긴다. 그다음엔 반복문 안에 반복문(보이든 숨었든)이 있는지, 찾기를 해시나 정렬로 바꿀 수 있는지, 그 대가로 메모리를 얼마나 쓰는지를 따진다. 다음에는 같은 생각을 트리와 그래프 탐색에 적용해 보면 좋겠다.

## 면접에서 나올 만한 질문

### Big O 표기법이 무엇이고 왜 쓰나요?

입력 크기 n이 커질 때 연산 횟수나 메모리가 늘어나는 모양을 나타내는 표기다. 실제 시간은 기계와 언어마다 다르니 대신 증가율로 알고리즘을 비교한다. 상수 배와 작은 항은 n이 커지면 의미가 없어져서 버리고 가장 빨리 자라는 항만 남긴다. 따로 말하지 않으면 보통 최악의 경우를 기준으로 한다.

### O(n)인 알고리즘이 O(n²)보다 항상 빠른가요?

아니다. Big O는 n이 충분히 클 때의 증가율만 비교하고 상수는 버리기 때문에, n이 작으면 상수가 작은 O(n²) 쪽이 빠를 수 있다. 그래서 TimSort 같은 실제 정렬도 짧은 구간은 삽입 정렬로 처리한다. 지금 데이터 크기에서 무엇이 빠른지는 측정해서 판단한다.

### 해시 테이블 조회가 O(1)이라는 말은 항상 맞나요?

평균적으로 맞고 최악은 O(n)이다. 키가 한 칸에 몰려 충돌이 나면 그 칸을 훑어야 하기 때문이다. 일부러 충돌하는 키를 보내는 HashDoS 공격이 있어서 많은 언어가 해시 함수에 무작위 시드를 섞는다. 그리고 배열이 꽉 찼을 때 다시 키우는 비용은 분할 상환으로 O(1)에 들어간다.

### 동적 배열의 push가 O(1)인 이유를 설명해 보세요.

꽉 찰 때마다 용량을 일정한 비율(예: 두 배)로 늘리면 복사는 용량이 1, 2, 4, 8…일 때만 일어나고, 그 합은 n보다 작다. 그래서 n번 push 전체가 O(n)이고 한 번당 분할 상환 O(1)이다. 다만 늘리는 순간 한 번은 O(n)이라 지연에 민감하면 미리 용량을 잡아 둔다. 고정 크기씩 늘리면 분할 상환으로도 O(n)이 된다.

### 이중 반복문으로 짠 O(n²) 코드를 어떻게 줄이나요?

안쪽 반복문이 하는 일이 "찾기"라면 해시맵이나 Set에 미리 넣어 두고 O(1)로 찾게 바꿔 전체를 O(n)으로 만든다. Two Sum이 대표적이고, 대신 O(n) 메모리를 더 쓴다. 범위나 순서가 필요하면 정렬한 뒤 이진 탐색이나 두 포인터로 O(n log n)을 만든다. 무엇을 고를지는 메모리 여유, 찾는 횟수, 범위 질의 필요 여부로 정한다.

### 재귀 함수의 공간 복잡도는 어떻게 계산하나요?

호출 스택이 가장 깊이 쌓일 때의 깊이에 호출 하나가 쓰는 메모리를 곱한다. n부터 1씩 줄여 가는 재귀는 지역 변수가 없어도 O(n) 공간이고, 깊어지면 스택 오버플로가 난다. 메모 없는 피보나치처럼 호출 횟수는 지수인데 깊이는 n이라 공간은 O(n)인 경우도 있다. 깊이가 입력에 비례하면 반복문으로 바꾸는 게 안전하다.

### 퀵 정렬의 시간 복잡도를 최선, 평균, 최악으로 말해 보세요.

평균과 최선은 O(n log n), 최악은 O(n²)이다. 피벗이 매번 가장 작거나 큰 값이 되면 한쪽에 n−1개가 남아 나뉘지 않기 때문이고, 이미 정렬된 배열에서 첫 원소를 피벗으로 쓰면 그렇게 된다. 피벗을 무작위로 고르거나 중앙값 후보를 쓰고, 재귀가 깊어지면 힙 정렬로 바꾸는 introsort로 최악을 막는다. 추가 공간은 평균 O(log n)의 스택이다.

### Big O, Big Θ, Big Ω는 어떻게 다른가요?

O는 상한, Ω는 하한, Θ는 상한과 하한이 같은 딱 맞는 증가율이다. 선형 탐색을 O(n²)이라고 해도 틀리진 않지만 의미가 없어서, 실무에서 말하는 O는 대개 Θ처럼 딱 맞는 상한을 뜻한다. 비교 기반 정렬이 Ω(n log n)이라는 건 어떤 비교 정렬도 최악의 경우 이보다 빠를 수 없다는 하한이다. 최선·최악 경우와는 다른 축이라 "최악의 경우 Θ(n²)"처럼 함께 쓸 수 있다. 소문자 o와 ω는 같음을 뺀 엄격한 상한과 하한이라, n = o(n²)이지만 2n은 o(n)이 아니다.
