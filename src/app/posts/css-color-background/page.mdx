## 시안과 화면의 색이 다르다

디자이너가 브랜드 파랑의 단계 색 열 개를 넘겼다. 라이트 모드에서는 괜찮았는데 다크 모드에서 같은 단계를 쓰니 글자가 번져 보였다. 디자이너의 노트북에서는 버튼 빨강이 훨씬 쨍했는데 사무실 모니터에서는 탁했다. 단계 색을 HSL 밝기만 10%씩 바꿔 만들었더니 노랑 계열 단계는 거의 흰색처럼 날아갔다.

이 세 증상은 원인이 다르다. 첫 번째는 대비와 채도, 두 번째는 화면이 표현할 수 있는 색의 범위(색역), 세 번째는 HSL의 밝기가 사람 눈의 밝기와 다르다는 데서 온다. 이 글은 색을 적는 방법과 그 차이, 배경을 쌓는 규칙, 그리고 그림자·불투명도·필터처럼 상자 크기는 그대로 두고 칠만 바꾸는 속성의 비용을 따라간다.

결과는 모두 Chromium 141(Playwright 헤드리스)에서 `getComputedStyle`로 직접 확인했다. 색 값을 CSS 변수로 관리하고 테마를 바꾸는 방법은 [CSS 변수](/posts/css-custom-properties)에, 글자와 배경의 대비 비율을 계산하는 법은 [웹 접근성 기초](/posts/web-accessibility)에 있다. 여기서는 그 앞 단계, 색 자체를 다룬다.

## hex, rgb, hsl은 같은 색을 다르게 적은 것이다

`#2563eb`, `rgb(37 99 235)`, `hsl(221 83% 53%)`은 거의 같은 파랑이다. 앞의 둘은 빨강·초록·파랑 빛의 양(0~255)을 적고, hsl은 색상환의 각도(hue), 채도(saturation), 밝기(lightness)를 적는다. 세 방법 모두 sRGB라는 같은 색 공간 안의 점을 가리킨다. 브라우저는 어떻게 적든 계산값을 rgb로 바꿔 둔다.

```css
.a { color: #0f08; }                    /* 4자리 hex: 마지막 자리가 알파 */
.b { color: #ff000080; }                /* 8자리 hex: 80(16진수) = 128 */
.c { color: rgb(255 0 0 / 50%); }       /* 공백 문법 + 슬래시 알파 */
.d { color: hsl(240 100% 50% / 0.3); }
.e { color: rebeccapurple; }            /* 이름 있는 색 */
.f { color: transparent; }
```

```text
#0f08                   → rgba(0, 255, 0, 0.533)
#ff000080               → rgba(255, 0, 0, 0.5)
rgb(255 0 0 / 50%)      → rgba(255, 0, 0, 0.5)
hsl(240 100% 50% / 0.3) → rgba(0, 0, 255, 0.3)
rebeccapurple           → rgb(102, 51, 153)
transparent             → rgba(0, 0, 0, 0)
```

볼 것이 몇 가지 있다. 4자리 `#0f08`의 알파 `8`은 `88`로 늘어나 136/255, 즉 0.533이 된다. 50%가 아니다. 8자리 `80`도 128/255라서 정확히는 0.502인데 브라우저는 0.5로 보여 준다. 반투명을 hex로 쓸 때 퍼센트로 착각하기 쉬운 자리다.

`rgba()`와 `hsla()`는 이제 `rgb()`, `hsl()`의 별칭이다. 쉼표 문법(`rgba(255, 0, 0, 0.5)`)과 공백 문법(`rgb(255 0 0 / 0.5)`) 모두 된다. 다만 새 색 함수(`oklch()`, `color()`)는 공백 문법만 받으니 팀 규칙을 공백 문법으로 맞춰 두면 덜 헷갈린다.

이름 있는 색은 140개 남짓이다. 프로토타입에서는 편하지만 이름과 실제 색이 직관과 다를 때가 많다(`darkgray`가 `gray`보다 밝다). 실제 제품에서는 디자인 토큰으로만 쓴다.

`transparent`는 `rgba(0, 0, 0, 0)`이다. "투명한 검정"이라는 사실이 그라데이션에서 문제를 일으켰는데, 이건 뒤에서 본다. `currentcolor`는 그 요소의 `color` 값을 가리킨다. 테두리나 SVG 아이콘 색을 글자색에 묶을 때 쓴다.

## HSL의 50%는 눈에 같은 밝기가 아니다

hsl은 사람이 읽기 쉬워 보인다. 색상만 돌리고 밝기는 고정하면 같은 밝기의 다른 색이 나올 것 같다. 실제로 재 보면 그렇지 않다.

`hsl(60 100% 50%)`(노랑)과 `hsl(240 100% 50%)`(파랑)은 둘 다 밝기 50%다. 사람이 느끼는 밝기에 맞춘 OKLCH의 L 값으로 바꿔 보면 차이가 크다.

```css
.y { color: oklch(from hsl(60 100% 50%) l c h); }
.b { color: oklch(from hsl(240 100% 50%) l c h); }
```

```text
hsl(60 100% 50%)  → oklch(0.967983 0.210997 109.756)
hsl(120 100% 50%) → oklch(0.866435 0.294791 142.489)
hsl(0 100% 50%)   → oklch(0.627966 0.257704 29.2346)
hsl(240 100% 50%) → oklch(0.451981 0.31321 264.051)
```

같은 "50%"인데 노랑은 0.97, 파랑은 0.45다. WCAG의 상대 휘도로 계산해도 노랑 0.9278, 파랑 0.0722로 열 배 넘게 차이 난다. HSL은 RGB 정육면체를 원기둥 모양으로 다시 적은 것일 뿐이라, 밝기 축이 사람 눈과 맞지 않는다. 사람 눈은 초록과 노랑을 밝게, 파랑을 어둡게 느낀다.

그래서 HSL 밝기만 일정하게 바꿔 만든 단계 색은 색상마다 단계 간격이 다르게 보인다. 처음 장면의 "노랑 단계가 흰색처럼 날아간다"가 이것이다. 같은 단계 번호의 노랑 버튼과 파랑 버튼에 흰 글자를 올리면 한쪽은 대비가 부족해진다.

HSL이 RGB로 바뀌는 계산은 짧다. 아래에서 직접 짜 볼 수 있다. 밝기와 채도로 색의 진하기(chroma) `c`를 구하고, 색상환을 60도씩 여섯 칸으로 나눠 어느 칸인지에 따라 r, g, b 자리를 정한 뒤, 밝기에 맞춰 모두 같은 양 `m`을 더한다. 테스트 값은 Chromium의 계산값과 비교해 확인했다.

  // 1) c = (1 - |2l - 1|) * s   (s, l은 0~1로 바꿔서)

  // 3) x = c * (1 - |(칸 % 2) - 1|)

  solution={`function hslToRgb(h, s, l) {
  s /= 100;
  l /= 100;
  const c = (1 - Math.abs(2 * l - 1)) * s;
  const hp = (((h % 360) + 360) % 360) / 60;
  const x = c * (1 - Math.abs((hp % 2) - 1));
  let r = 0, g = 0, b = 0;
  if (hp < 1) [r, g, b] = [c, x, 0];
  else if (hp < 2) [r, g, b] = [x, c, 0];
  else if (hp < 3) [r, g, b] = [0, c, x];
  else if (hp < 4) [r, g, b] = [0, x, c];
  else if (hp < 5) [r, g, b] = [x, 0, c];
  else [r, g, b] = [c, 0, x];
  const m = l - c / 2;
  return [r, g, b].map((v) => Math.round((v + m) * 255));
}`}

## 눈에 고른 단계 색은 oklch로 만든다

OKLCH는 사람 눈에 맞춰 만든 색 공간 OKLab을 극좌표로 적은 것이다. `oklch(L C H)`의 L은 지각 밝기(0~1), C는 채도에 해당하는 크로마(0부터, 보통 0.4 아래), H는 색상 각도다. L이 같으면 색상이 달라도 비슷한 밝기로 보인다는 게 HSL과 다른 점이다. 크로미움 111, 사파리 15.4, 파이어폭스 113부터 쓸 수 있다.

손으로 L을 정하는 대신 기준 색에서 계산할 수도 있다. 상대 색 문법(relative color syntax)은 기준 색을 분해한 값(`l`, `c`, `h`)을 함수 안에서 바로 쓴다. 크로미움 119, 파이어폭스 128부터 되고, 사파리는 판마다 지원 범위가 달라 최신판에서 확인하고 쓴다.

```css
:root {
  --brand: #2563eb;
  --brand-light: oklch(from var(--brand) calc(l + 0.2) c h);   /* 밝기만 0.2 올린다 */
  --brand-dark: color-mix(in oklch, var(--brand), black 30%);  /* 검정을 30% 섞는다 */
  --brand-50a: rgb(from var(--brand) r g b / 50%);             /* 알파만 바꾼다 */
}
```

```text
oklch(from #2563eb l c h)                → oklch(0.546093 0.215171 262.885)
oklch(from #2563eb calc(l + 0.2) c h)    → oklch(0.746093 0.215171 262.885)
color-mix(in oklch, #2563eb, black 30%)  → oklch(0.382265 0.150619 262.885)
rgb(from #2563eb r g b / 50%)            → color(srgb 0.145098 0.388235 0.921569 / 0.5)
```

`color-mix`로 검정을 섞었는데 색상 각도가 262.885 그대로다. 검정은 색상이 없는 색이라 OKLCH에서 각도가 "없음"으로 처리되고, 섞을 때 다른 쪽 각도를 따라간다. sRGB에서 검정을 섞으면 파랑이 탁해지며 보라 기운이 도는데, oklch에서는 같은 파랑 그대로 어두워진다.

하나 주의할 점이 있다. 밝기만 0.2 올린 `--brand-light`는 sRGB 범위 밖이다. sRGB 값으로 풀어 보면 파랑 성분이 1을 넘는다.

```text
oklch(0.746 0.215 263) → color(srgb 0.377367 0.645947 1.20172)   범위 밖
oklch(0.78 0.11 263)   → color(srgb 0.572292 0.717983 0.996864)  범위 안
oklch(0.95 0.02 263)   → color(srgb 0.907478 0.936649 0.990036)  범위 안
```

계산값은 그대로 남지만, 화면에 칠할 때 브라우저가 범위 안으로 끌어당긴다(gamut mapping). 어떻게 끌어당길지는 브라우저 구현에 달려 있어서, 밝은 단계에서 크로마를 손으로 줄여 두는 편이 예측하기 쉽다. 위 그림에서 300과 100의 크로마를 줄인 이유다. 처음에 100을 크로마 0.03으로 잡았다가 풀어 보니 파랑 성분이 1.017로 넘쳐서 0.02로 내렸다.

## 넓은 색역 화면에서만 보이는 색

디자이너의 맥북에서 빨강이 더 쨍했던 건 화면이 sRGB보다 넓은 Display P3 색역을 표현하기 때문이다. sRGB의 가장 진한 빨강 `#ff0000` 바깥에도 P3 화면이 낼 수 있는 빨강이 있다. CSS에서는 `color(display-p3 1 0 0)`이나 크로마가 큰 `oklch()`로 그 색을 적는다.

```css
.cta {
  background: #ff0000;                      /* sRGB 화면용 */
  background: color(display-p3 1 0 0);      /* 이해하는 브라우저는 이 줄로 덮어쓴다 */
}

@media (color-gamut: p3) {
  .hero { background: oklch(0.65 0.29 30); } /* P3 화면에서만 더 진하게 */
}
```

같은 속성을 두 번 쓰면 이해하지 못하는 브라우저는 두 번째 줄을 버리고 첫 줄을 쓴다. 이해하는 브라우저는 두 번째 줄을 쓰고, sRGB 화면이면 알아서 범위 안으로 맞춘다. 헤드리스 크로미움에서 재 보면 `(color-gamut: srgb)`는 참, `(color-gamut: p3)`는 거짓이다. CI의 스크린샷 테스트가 P3 색을 sRGB로 찍는다는 뜻이라, 시각 회귀 테스트로는 이 차이를 잡을 수 없다.

반대 방향의 실수도 있다. 디자인 도구가 P3 프로필로 색을 뽑았는데 그 숫자를 hex로 그대로 옮기면, sRGB로 해석되어 시안보다 탁한 색이 나온다. 시안과 색이 다르다는 제보가 오면 디자인 파일의 색 프로필부터 확인한다.

## 다크 모드에서 같은 색이 번져 보인다

라이트 모드의 브랜드 파랑을 다크 배경에 그대로 쓰면, 크로마가 큰 색이 어두운 배경 위에서 번지고 떨려 보인다. 대비 비율은 통과해도 오래 읽기 불편하다. 다크 모드에서는 같은 색상(H)을 유지하되 L을 올리고 C를 조금 낮춘 값을 따로 둔다. 단계 색을 oklch로 만들어 두면 이 조정이 숫자 두 개를 바꾸는 일이 된다.

CSS에는 테마별 값을 한 줄에 적는 `light-dark()`도 있다.

```css
:root { color-scheme: light dark; }   /* 이게 없으면 light-dark()가 늘 첫 값을 쓴다 */
.card {
  background: light-dark(oklch(0.99 0 0), oklch(0.22 0.01 263));
  color: light-dark(oklch(0.25 0.02 263), oklch(0.92 0.01 263));
}
```

Playwright로 다크 모드를 켜고(`prefers-color-scheme: dark`가 참) `light-dark(white, black)`의 계산값을 재 보면, `color-scheme`을 정하지 않은 문서에서는 `rgb(255, 255, 255)`, `color-scheme: light dark`를 준 문서에서는 `rgb(0, 0, 0)`이다. 운영체제가 다크 모드여도 문서가 다크를 지원한다고 말하지 않으면 첫 값을 쓴다. 이 블로그처럼 `html[data-theme]`로 테마를 바꾸는 사이트라면 `color-scheme`도 그 선택자에서 함께 바꿔야 스크롤바와 폼 컨트롤 색까지 맞는다. 테마 값을 변수로 나누는 구조는 [CSS 변수](/posts/css-custom-properties)에서 다뤘다.

## 배경은 여러 겹을 쌓는다

`background`는 속성 여덟 개를 줄여 쓴 단축 속성이고, 쉼표로 나눈 레이어를 여러 개 쌓을 수 있다. 먼저 적은 레이어가 위에 온다. 색은 맨 아래 레이어에만 둘 수 있다. 아래에서 각 조각을 눌러 보면 무슨 뜻인지 나온다.

크로미움에서 이 한 줄의 계산값을 레이어별로 꺼내 보면 이렇다.

```css
.hero {
  background: url(hero.avif) center / cover no-repeat fixed, linear-gradient(#000, #fff);
}
```

```text
background-image:      url("hero.avif"), linear-gradient(rgb(0, 0, 0), rgb(255, 255, 255))
background-position:   50% 50%, 0% 0%
background-size:       cover, auto
background-repeat:     no-repeat, repeat
background-attachment: fixed, scroll
background-origin:     padding-box, padding-box
background-clip:       border-box, border-box
background-color:      rgba(0, 0, 0, 0)
```

두 가지를 눈여겨본다. 하나는 단축 속성에 적지 않은 값이 모두 초기값으로 돌아갔다는 점이다. 두 번째 레이어는 `repeat`, `scroll`, `0% 0%`가 되었고, 색은 투명이 되었다. 앞에서 `background-color`를 따로 정해 두고 아래에 `background: url(...)`을 쓰면 색이 사라지는 이유가 이것이다. 단축 속성은 빠진 칸을 비워 두지 않고 초기값으로 채운다.

다른 하나는 `origin`과 `clip`의 기본값이 다르다는 점이다. 위치의 기준(origin)은 패딩 상자인데, 칠하는 범위(clip)는 테두리 상자까지다. 그래서 점선 테두리 아래로 배경색이 비친다. 테두리 아래로 배경이 새는 게 싫으면 `background-clip: padding-box`를 준다. `background-clip: text`로 글자 모양대로 그라데이션을 칠하는 효과도 이 속성이다.

## 그라데이션은 어느 색 공간에서 섞느냐가 중요하다

그라데이션은 두 색 사이를 섞어 가며 칠한다. 기본은 sRGB에서 섞는다. 파랑에서 노랑으로 가는 그라데이션의 한가운데 색을 `color-mix`로 꺼내 보면 차이가 보인다.

```css
.g1 { background: linear-gradient(to right, blue, yellow); }           /* sRGB에서 섞는다 */
.g2 { background: linear-gradient(to right in oklch, blue, yellow); }  /* oklch에서 섞는다 */
```

```text
color-mix(in srgb, blue, yellow)  → color(srgb 0.5 0.5 0.5)
color-mix(in oklab, blue, yellow) → oklab(0.709982 -0.0518911 -0.0564726)
color-mix(in oklch, blue, yellow) → oklch(0.709982 0.262103 186.903)
color-mix(in hsl, blue, yellow)   → color(srgb 0 1 0.5)
```

sRGB에서 섞은 가운데는 `0.5 0.5 0.5`, 그냥 회색이다. 파랑과 노랑의 빛을 반씩 더하면 색이 상쇄되기 때문이다. 화면에서는 가운데가 칙칙하게 꺼진 띠로 보인다. oklab은 밝기는 고르게 지나가지만 크로마가 작은 회청색을 지나고, oklch는 색상환을 따라 돌며 크로마를 유지해 청록을 지난다. hsl은 색상환을 따라 초록을 지난다.

어느 쪽이 옳다기보다 의도에 맞게 고른다. 밝기가 고르게 변하는 부드러운 전환이 필요하면 `in oklab`, 색이 선명하게 이어지는 무지개 같은 전환이면 `in oklch`, 색상환을 반대 방향으로 돌고 싶으면 `in oklch longer hue`다. 색 공간 지정은 크로미움 111, 사파리 16.2, 파이어폭스 127부터 된다.

`transparent`와 섞을 때의 문제는 예전 이야기가 되었다. `transparent`가 투명한 검정이라 옛 브라우저에서는 흰색에서 투명으로 가는 그라데이션 가운데가 회색으로 탁해졌다. 지금 명세는 알파를 미리 곱한(premultiplied) 상태에서 섞어서, 재 보면 `color-mix(in srgb, #2563eb 50%, transparent)`가 `color(srgb 0.145098 0.388235 0.921569 / 0.5)`, 즉 같은 파랑에 알파만 반이다. 아주 오래된 브라우저까지 지원해야 할 때만 `rgb(255 255 255 / 0)`처럼 같은 색의 투명값을 쓴다.

## 휴대폰에서 background-attachment: fixed가 움직인다

데스크톱에서는 배경 이미지가 가만히 있고 내용만 스크롤되는 "패럴랙스 비슷한" 효과가 났는데, 아이폰에서는 배경이 그냥 같이 스크롤된다. iOS 사파리는 오랫동안 `background-attachment: fixed`를 `scroll`처럼 처리해 왔다. 이유는 비용이다. 고정 배경은 스크롤할 때마다 배경을 상자 안의 다른 위치로 다시 칠해야 하고, 스크롤을 합성 스레드에서만 처리하는 최적화를 쓸 수 없게 만든다. 지원하는 브라우저에서도 스크롤마다 다시 칠하는 비싼 효과다.

같은 효과가 필요하면 배경을 별도 요소로 빼서 `position: fixed`로 고정한다. 고정 요소는 자기 레이어로 올라가 스크롤 중에 다시 칠할 필요가 없다.

```css
.hero { position: relative; isolation: isolate; }
.hero::before {
  content: "";
  position: fixed;          /* 뷰포트에 고정된 별도 레이어 */
  inset: 0;
  z-index: -1;
  background: url(hero.avif) center / cover no-repeat;
}
```

다만 이 방법은 조상에 `transform`이나 `filter`가 있으면 깨진다. 그 이유는 아래 필터 이야기에 있다. 스크롤에 따라 움직이는 효과 자체는 [sticky와 scroll-snap](/posts/css-sticky-scroll-snap) 같은 스크롤 패턴 글과 함께 보면 좋다.

## 테두리, 그림자, 윤곽선은 자리를 차지하나

`width: 200px; padding: 10px`인 상자 아래에 형제 상자를 두고, 위 상자에 속성을 하나씩 걸어 아래 상자 위치와 위 상자 너비가 어떻게 변하는지 쟀다.

```text
아무것도 없음                      → 아래 상자 top 170, 위 상자 너비 220
box-shadow: 0 20px 40px 20px ...  → 아래 상자 top 170, 위 상자 너비 220
outline: 20px solid               → 아래 상자 top 170, 위 상자 너비 220
opacity: 0.5                      → 아래 상자 top 170, 위 상자 너비 220
border: 20px solid                → 아래 상자 top 210, 위 상자 너비 260
```

테두리만 상자를 키워 아래 상자를 밀어냈다. 그림자와 윤곽선은 상자 밖에 칠해지지만 레이아웃에서는 없는 것으로 친다. 그래서 그림자가 이웃 요소를 덮거나, `overflow: hidden`인 부모 밖으로 나간 그림자가 잘린다. 카드 그림자가 잘린다는 제보는 대개 부모의 `overflow`다.

윤곽선(outline)이 자리를 차지하지 않는다는 성질이 포커스 표시에 딱 맞다. 포커스가 생길 때 레이아웃이 흔들리지 않는다. 그런데 "클릭할 때 파란 테두리가 거슬린다"며 `outline: none`을 지우는 일이 아직도 많다. 키보드 사용자는 지금 어디에 있는지 잃는다. 지우지 말고 `:focus-visible`로 키보드 포커스일 때만 보이게 한다. 지금 브라우저들은 윤곽선이 `border-radius`를 따라 둥글게 그려지니 예전처럼 둥근 버튼에서 각진 윤곽선이 튀는 문제도 없다.

```css
button:focus { outline: none; }                 /* 하지 말 것 */

button:focus-visible {                          /* 키보드로 왔을 때만 */
  outline: 2px solid var(--focus);
  outline-offset: 2px;                          /* 상자에서 2px 떨어뜨려 그린다 */
}
```

`box-shadow`, `background`, `color`, `outline`은 레이아웃을 건너뛰지만 다시 칠한다. 특히 흐림 반경이 큰 그림자는 칠하는 비용이 크다. 호버할 때 그림자를 키우는 애니메이션을 카드 수십 장에 걸면 프레임이 떨어진다. 이럴 때는 큰 그림자를 미리 칠해 둔 가상 요소를 깔고 그 `opacity`만 바꾼다. `opacity`와 `transform`은 그 요소가 자기 레이어에 올라가 있으면 합성 단계에서만 처리된다. `filter`도 브라우저와 필터 종류에 따라 합성에서 처리되지만, 흐림처럼 무거운 필터는 레이어 크기에 비례해 비싸다. 단계별 비용과 프레임 예산은 [애니메이션 성능](/posts/animation-performance)과 [브라우저 렌더링 파이프라인](/posts/browser-rendering-pipeline)에서 자세히 다뤘다.

```css
.card { position: relative; }
.card::after {
  content: "";
  position: absolute;
  inset: 0;
  border-radius: inherit;
  box-shadow: 0 12px 32px rgb(0 0 0 / 0.25);  /* 한 번만 칠해 둔다 */
  opacity: 0;
  transition: opacity 200ms;
}
.card:hover::after { opacity: 1; }             /* 바뀌는 건 opacity뿐 */
```

## opacity와 filter가 바꾸는 것은 색만이 아니다

`opacity`를 1보다 작게 주면 그 요소는 새 쌓임 맥락이 된다. 안쪽 자식의 `z-index`가 아무리 커도 그 요소 밖의 형제를 넘어서지 못한다. 반투명 효과를 주려고 `opacity: 0.99`를 건 모달 래퍼 안에서 드롭다운이 다른 요소 밑으로 깔리는 일이 여기서 생긴다. 쌓임 맥락 규칙은 [position과 쌓임 맥락](/posts/css-position-stacking-context)에 정리해 두었다. 배경만 반투명하게 하고 싶다면 요소 전체의 `opacity` 대신 배경색의 알파(`rgb(0 0 0 / 0.5)`)를 쓴다. 그러면 쌓임 맥락도 생기지 않고 글자도 흐려지지 않는다.

`filter`는 더 멀리 간다. `filter`가 `none`이 아니면 그 요소는 `position: fixed`인 자손의 기준(포함 블록)이 된다. 위쪽 여백이 100px인 상자에 `filter: blur(0px)`를 걸고 그 안에 `position: fixed; top: 0`인 자식을 넣어 쟀다.

```text
부모 filter: blur(0px) → 고정 자식 top 100
부모 filter: none      → 고정 자식 top 0
```

흐림이 0인 필터, 사실상 아무 효과도 없는 필터 하나 때문에 고정 요소가 뷰포트가 아니라 부모 기준으로 섰다. `transform`, `perspective`, `backdrop-filter`, `will-change: transform`도 같은 일을 한다. 앞에서 본 고정 배경 가상 요소나 고정 헤더가 갑자기 스크롤을 따라 움직이면, 조상 어딘가에 이 속성들이 있는지부터 찾는다.

## 현장에서 색과 배경 문제를 좁히는 법

시안과 색이 다르다는 제보는 숫자부터 확인한다. 개발자 도구에서 요소를 고르고 Computed 탭의 `color`, `background-color`를 시안 값과 비교한다. 숫자가 같은데 다르게 보이면 화면의 색역이나 디자인 파일의 색 프로필 문제다. 크롬 개발자 도구의 색 선택기는 sRGB 경계선을 그려 주니, 넓은 색역 색이 어디서 잘리는지 볼 수 있다.

다크 모드에서만 어색하면 Rendering 탭의 `prefers-color-scheme` 에뮬레이션으로 두 모드를 오가며 같은 단계 색을 비교한다. 대비는 접근성 검사 도구로 숫자를 확인한다.

배경이 사라졌으면 Styles 탭에서 `background` 단축 속성이 아래쪽에서 `background-color`를 덮어쓰고 있지 않은지 본다. 취소선이 그어진 줄이 범인이다.

스크롤이나 호버가 버벅이면 Rendering 탭의 Paint flashing을 켠다. 초록으로 번쩍이는 영역이 매 프레임 다시 칠해지는 곳이다. 고정 배경이나 그림자 애니메이션이 넓게 번쩍이면 위에서 본 방법으로 레이어를 나눈다.

## 면접에서 나올 만한 질문

### hex, rgb, hsl은 어떻게 다른가요?

셋 다 sRGB 색 공간의 같은 점을 다르게 적는 방법이다. hex와 rgb는 빨강·초록·파랑 빛의 양을 적고, hsl은 색상 각도·채도·밝기로 적는다. 브라우저는 계산값을 rgb로 바꿔 둔다. 알파를 hex로 적을 때 `#0f08`의 `8`은 0.533이지 50%가 아닌데, 이걸 자주 틀린다.

### HSL 대신 OKLCH를 쓰는 이유는 무엇인가요?

HSL의 밝기는 사람 눈의 밝기와 맞지 않는다. 같은 50%인데 노랑은 OKLCH L 0.97, 파랑은 0.45로 보인다. OKLCH는 지각 밝기에 맞춘 색 공간이라 L을 고정하면 색상이 달라도 비슷한 밝기가 되고, 그래서 단계 색과 다크 모드 색을 숫자로 일관되게 만들 수 있다. 색상 각도도 밝기를 바꿀 때 덜 샌다.

### 그라데이션 가운데가 칙칙한 회색이 되는 이유는 무엇인가요?

기본값인 sRGB에서 섞기 때문이다. 파랑과 노랑을 sRGB에서 반씩 섞으면 `0.5 0.5 0.5` 회색이 된다. `in oklab`으로 섞으면 밝기가 고르게 지나가고, `in oklch`로 섞으면 색상환을 따라 크로마를 유지한다. 의도에 맞는 색 공간을 그라데이션에 지정하면 된다.

### background 단축 속성을 쓸 때 흔한 실수는 무엇인가요?

단축 속성은 적지 않은 하위 속성을 초기값으로 되돌린다. 위에서 정한 `background-color` 아래에 `background: url(...)`을 쓰면 색이 투명으로 돌아간다. 레이어는 먼저 적은 것이 위에 오고, 색은 맨 아래 레이어에만 둘 수 있다. 하나만 바꾸고 싶으면 `background-image`처럼 하위 속성을 쓴다.

### background-attachment: fixed가 모바일에서 동작하지 않는 이유와 대안은 무엇인가요?

고정 배경은 스크롤마다 다시 칠해야 하고 합성 스레드 스크롤 최적화를 막아서 비싸다. 그래서 iOS 사파리는 오랫동안 fixed를 scroll처럼 처리해 왔다. 대안은 배경을 가상 요소로 빼서 `position: fixed`로 고정하는 것이다. 이때 조상에 transform이나 filter가 있으면 고정 기준이 바뀌니 함께 확인한다.

### box-shadow, outline, border는 레이아웃에 어떤 영향을 주나요?

border만 상자 크기에 들어가 이웃을 밀어낸다. box-shadow와 outline은 상자 밖에 칠해지지만 레이아웃에서는 자리를 차지하지 않는다. 그래서 그림자가 부모의 overflow에 잘리고, outline은 포커스 표시를 해도 레이아웃이 흔들리지 않는다. 대신 둘 다 페인트 비용이 있어 큰 그림자 애니메이션은 opacity로 바꿔 처리한다.

### opacity나 filter를 걸었더니 z-index나 position: fixed가 이상해졌습니다. 왜 그런가요?

opacity가 1보다 작으면 새 쌓임 맥락이 생겨 안쪽 z-index가 바깥 형제를 넘지 못한다. filter가 none이 아니면 그 요소가 fixed 자손의 포함 블록이 되어, 자식이 뷰포트가 아니라 그 요소 기준으로 선다. 흐림 0인 필터도 마찬가지다. 배경만 반투명하게 하려면 opacity 대신 배경색의 알파를 쓰고, 고정 요소는 그런 조상 밖으로 옮긴다.
