회원 가입 폼에 "이름은 10자까지"라고 적어 두었다. 프런트엔드에서 글자 수를 세어 막았는데, 백엔드 로그에 "value too long" 에러가 찍힌다. 다른 날에는 이모지 하나를 넣은 닉네임이 프런트엔드 검사에서 2자로 세어진다. 엑셀로 열어 본 회원 목록 CSV는 한글 이름이 낯선 한자와 기호로 깨져 있다. 맥에서 올린 파일 이름 "보고서.pdf"는 검색해도 안 나온다.

전부 같은 뿌리에서 나온 버그다. 사람이 말하는 "글자 하나"와 컴퓨터가 세는 단위가 여러 겹으로 다르고, 바이트를 글자로 바꾸는 약속(인코딩)이 중간에서 한 번이라도 어긋나면 이렇게 된다. 이 글에서는 ASCII부터 EUC-KR, 유니코드, UTF-8과 UTF-16이 각각 무엇을 풀려고 나왔는지 보고, 글자 하나를 바이트로 바꾸는 과정을 비트 단위로 따라간다. 그다음 BOM, 정규화(NFC/NFD), 한글이 깨지는 경로, DB와 HTTP의 charset 설정까지 실제 출력으로 확인한다. 실험 환경은 Ubuntu 24.04, Python 3.13, Node 22, PostgreSQL 16이다.

## 숫자에 글자를 붙이는 약속

컴퓨터는 바이트만 저장한다. 그래서 글자를 저장하려면 두 단계의 약속이 필요하다. 첫째는 글자마다 번호를 붙이는 약속(문자 집합, character set)이고, 둘째는 그 번호를 바이트로 적는 방법(인코딩, encoding)이다. 예전에는 두 단계가 하나로 붙어 있어서 구분할 필요가 없었다. 유니코드 이후로는 이 둘을 나눠 생각해야 헷갈리지 않는다.

1963년에 나온 ASCII는 7비트, 즉 0부터 127까지 128개 번호에 영문 대소문자, 숫자, 기호, 제어 문자를 붙였다. `A`는 65(16진수 0x41), 줄바꿈은 10이다. 바이트 하나가 8비트라 위쪽 128칸(128~255)이 비는데, 나라마다 이 빈칸을 자기 글자로 채웠다. 서유럽은 ISO-8859-1(Latin-1)에 `é` 같은 글자를, 러시아는 키릴 문자를 넣었다. 같은 바이트 0xE9가 어떤 표로 읽느냐에 따라 `é`도 되고 다른 글자도 된다. 이 "같은 바이트, 다른 표" 문제가 글자 깨짐의 원형이다.

한글은 128칸에 들어가지 않는다. 그래서 바이트 두 개로 글자 하나를 나타내는 EUC-KR이 표준이 됐다. EUC-KR은 KS X 1001이라는 문자 집합을 쓰는데, 자주 쓰는 완성형 한글 2350자만 담았다. 현대 한글로 만들 수 있는 글자는 11172자라서 "똠", "햏" 같은 글자가 빠졌다. 마이크로소프트가 빠진 글자를 채워 넣은 것이 CP949(통합형 한글, UHC)다. 한국어 윈도우의 기본 인코딩이 이것이고, 우리가 흔히 "EUC-KR"이라고 부르는 파일도 실제로는 CP949인 경우가 많다.

## 세상의 모든 글자에 번호 하나씩: 유니코드

나라마다 표가 다르니 한 문서에 한글과 일본어와 그리스어를 같이 쓰기 어려웠다. 유니코드는 세상의 모든 글자에 겹치지 않는 번호를 하나씩 붙이자는 약속이다. 이 번호를 코드 포인트(code point)라고 하고, `U+` 뒤에 16진수로 적는다. `A`는 U+0041, `한`은 U+D55C, `😀`는 U+1F600이다.

번호는 U+0000부터 U+10FFFF까지, 111만 4112개 자리가 있다. 65536개씩 17개의 평면(plane)으로 나누는데, 자주 쓰는 글자는 거의 첫 평면인 BMP(Basic Multilingual Plane, U+0000~U+FFFF)에 있다. 한글 완성형 11172자는 모두 BMP의 U+AC00~U+D7A3에 순서대로 들어 있다. 이모지는 대부분 BMP 밖, U+1F000 근처에 있다.

여기까지는 번호일 뿐이다. 번호를 바이트로 어떻게 적을지가 남았다. 가장 단순한 방법은 모든 글자를 4바이트로 적는 UTF-32다. 계산은 쉽지만 영문 텍스트도 4배로 커진다. 그래서 실제로는 가변 길이 인코딩인 UTF-8과 UTF-16을 쓴다.

## UTF-8은 글자마다 칸 수가 다르다

자바스크립트 문자열이 UTF-16 칸으로 길이를 세서 생기는 일은 [자바스크립트 문자열과 유니코드](/posts/js-strings-unicode) 글에서 이어서 다룬다.

UTF-8은 1992년 켄 톰프슨과 롭 파이크가 만든 방식이다. 번호가 작은 글자는 적은 바이트로, 큰 글자는 많은 바이트로 적는다. 규칙은 네 줄이다.

| 코드 포인트 범위 | 바이트 수 | 비트 모양 |
|---|---|---|
| U+0000 ~ U+007F | 1 | `0xxxxxxx` |
| U+0080 ~ U+07FF | 2 | `110xxxxx 10xxxxxx` |
| U+0800 ~ U+FFFF | 3 | `1110xxxx 10xxxxxx 10xxxxxx` |
| U+10000 ~ U+10FFFF | 4 | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` |

`x` 자리에 코드 포인트의 비트를 뒤에서부터 채운다. `한`(U+D55C)으로 해 보자. U+D55C는 세 번째 줄 범위라 3바이트다. 0xD55C를 2진수로 쓰면 `1101 0101 0101 1100`, 16비트다. 이걸 앞에서부터 4비트, 6비트, 6비트로 나눠 각 틀에 넣는다. 아래 그림에서 조각을 누르면 각 바이트가 어떻게 만들어지는지 볼 수 있다.

이 규칙에는 영리한 성질이 셋 있다. 첫째, ASCII 글자는 UTF-8에서도 똑같은 1바이트다. 영문만 쓴 파일은 ASCII 파일이자 UTF-8 파일이다. 오래된 프로그램이 UTF-8을 그럭저럭 견딘 이유다. 둘째, 멀티바이트 글자의 어느 바이트도 0x00~0x7F 범위에 들어가지 않는다. 한글 바이트 안에 우연히 `/`나 `"`, 널 문자가 끼어들 일이 없어서, 바이트 단위로 경로나 따옴표를 찾는 C 코드가 깨지지 않는다. 셋째, 첫 바이트(`0`, `110`, `1110`, `11110`)와 이어지는 바이트(`10`)의 모양이 달라서, 중간 아무 바이트에서 읽기 시작해도 다음 글자의 시작을 찾을 수 있다. 이것을 자기 동기화(self-synchronizing)라고 한다.

직접 확인해 보자. 글자마다 코드 포인트 수, UTF-8 바이트 수, UTF-16 단위 수를 파이썬으로 찍었다.

```python
for s in ["A", "é", "한", "😀", "👍🏽", "👨‍👩‍👧"]:
    print(f"{s!r:8} cps={[hex(ord(c)) for c in s]} len={len(s)} "        # 코드 포인트 목록과 개수
          f"utf8={len(s.encode('utf-8'))} "                               # UTF-8 바이트 수
          f"utf16={len(s.encode('utf-16-le')) // 2}units "                # UTF-16 코드 유닛 수
          f"bytes={s.encode('utf-8').hex(' ')}")
```

## UTF-16과 서로게이트 쌍

자바, 자바스크립트, 윈도우 API, C#은 문자열을 안에서 UTF-16으로 다룬다. 유니코드 초기에는 65536자면 충분하다고 보고 글자 하나를 2바이트 고정으로 담는 UCS-2를 썼는데, 글자가 BMP 밖으로 넘치면서 UTF-16으로 넓혔다. BMP 글자는 2바이트 단위(코드 유닛) 하나, BMP 밖 글자는 단위 두 개로 적는다.

BMP 밖 글자를 두 단위로 쪼개는 방법이 서로게이트 쌍(surrogate pair)이다. 유니코드는 U+D800~U+DFFF를 글자에 쓰지 않고 비워 두었다. 코드 포인트에서 0x10000을 뺀 20비트를 위 10비트와 아래 10비트로 나눠, 위는 0xD800에, 아래는 0xDC00에 더한다. `😀`(U+1F600)이면 0xF600의 위 10비트가 0x3D라 0xD83D, 아래 10비트가 0x200이라 0xDE00이 된다.

```bash
python3 -c 'print("😀".encode("utf-16-be").hex(" "))'   # UTF-16 빅 엔디언 바이트
```

```text
d8 3d de 00
```

그래서 UTF-16을 쓰는 언어에서는 `length`가 코드 포인트 수가 아니라 코드 유닛 수다. 자바스크립트에서 `"😀".length`가 2인 이유다. 처음에 본 "이모지 하나가 2자로 세어진다"가 이것이다. 반대로 파이썬 3의 `len`은 코드 포인트 수, Go의 `len`은 바이트 수, Rust의 `str::len`도 바이트 수다. 같은 문자열의 "길이"가 언어마다 다르다.

```bash
node -e 'const f="👨‍👩‍👧";
console.log("😀".length, [..."😀"].length);       // 코드 유닛 수, 코드 포인트 수
console.log(f.length, [...f].length,               // 가족 이모지: 유닛 8, 포인트 5
  [...new Intl.Segmenter("ko", { granularity: "grapheme" }).segment(f)].length,  // 보이는 글자 수
  Buffer.byteLength(f));                            // UTF-8 바이트 수'
```

```text
2 1
8 5 1 18
```

사람이 "한 글자"라고 느끼는 단위는 그래핌 클러스터(grapheme cluster)다. 가족 이모지는 그래핌 1개, 코드 포인트 5개, UTF-16 단위 8개, UTF-8 바이트 18개다. 네 숫자가 전부 다르다. 닉네임 글자 수 제한을 사람 눈 기준으로 하려면 그래핌으로 세야 하고, 브라우저와 Node에서는 `Intl.Segmenter`가 그 일을 한다. 자바는 `BreakIterator`, 파이썬은 표준 라이브러리에 없어서 `regex` 패키지의 `\X`나 `grapheme` 패키지를 쓴다.

UTF-16이 2바이트 단위로 쓰이다 보니 바이트 순서 문제가 생긴다. 0xD55C를 `D5 5C`로 적을지(빅 엔디언) `5C D5`로 적을지(리틀 엔디언) 정해야 한다. 그래서 UTF-16 파일 맨 앞에 U+FEFF를 하나 넣어 순서를 알려 주는데, 이것이 BOM(Byte Order Mark)이다. `FE FF`로 읽히면 빅 엔디언, `FF FE`면 리틀 엔디언이다.

## BOM: UTF-8에 붙은 세 바이트

UTF-8은 바이트 단위라 순서 문제가 없다. 그런데도 U+FEFF를 UTF-8로 적은 `EF BB BF` 세 바이트를 파일 앞에 붙이는 프로그램이 있다. 바이트 순서가 아니라 "이 파일은 UTF-8이다"라는 표시로 쓰는 것이다. 윈도우 메모장이 예전에 기본으로 붙였고, 엑셀은 이 표시가 있어야 CSV를 UTF-8로 읽는다.

```bash
printf '\xef\xbb\xbfname,city\n김철수,서울\n' > bom.csv   # BOM 붙인 CSV
printf 'name,city\n김철수,서울\n' > nobom.csv              # BOM 없는 CSV
file bom.csv nobom.csv                                     # file 명령이 인코딩을 추측한다
head -c 16 bom.csv | od -A x -t x1z                        # 앞 16바이트를 16진수로
```

```text
bom.csv:   CSV Unicode text, UTF-8 (with BOM) text
nobom.csv: CSV Unicode text, UTF-8 text
000000 ef bb bf 6e 61 6d 65 2c 63 69 74 79 0a ea b9 80  >...name,city....<
000010
```

`ef bb bf`가 BOM이고 바로 뒤가 `name`이다. 둘째 줄 `ea b9 80`은 `김`의 UTF-8이다.

BOM은 받는 쪽이 모르면 첫 데이터의 일부가 된다. 파이썬으로 BOM 붙은 CSV를 그냥 `utf-8`로 열면 첫 열 이름이 `name`이 아니라 `﻿name`이 된다. 그러면 `row["name"]`이 `KeyError`를 낸다. 눈에 안 보이는 글자라 한참을 헤맨다. 자바스크립트의 `JSON.parse`는 BOM이 붙은 문자열을 거부한다.

```bash
python3 -c "import csv; print(next(csv.reader(open('bom.csv', encoding='utf-8'))))"
python3 -c "import csv; print(next(csv.reader(open('bom.csv', encoding='utf-8-sig'))))"   # BOM을 떼고 읽는다
node -e 'try { JSON.parse("﻿{\"a\":1}") } catch (e) { console.log(e.message) }'
```

```text
['﻿name', 'city']
['name', 'city']
Unexpected token '﻿', "﻿{"a":1}" is not valid JSON
```

정리하면 이렇다. 엑셀에서 열 CSV를 내보낼 때는 BOM을 붙인다(엑셀이 BOM 없는 CSV를 시스템 기본 인코딩, 한국어 윈도우라면 CP949로 읽기 때문이다). 그 외의 모든 곳, 특히 JSON, 셸 스크립트, 설정 파일에는 붙이지 않는다. 셸 스크립트 첫 줄 `#!` 앞에 BOM이 있으면 커널이 인터프리터를 못 찾는다. 읽는 쪽에서는 파이썬의 `utf-8-sig`처럼 있으면 떼는 옵션을 쓴다.

첫 줄이 UTF-8을 CP949로 읽은 모양이다. 낯선 한자가 섞인 이 패턴을 보면 "UTF-8인데 EUC-KR로 읽었구나"를 바로 떠올리면 된다. 둘째 줄은 반대로 EUC-KR 바이트(`c7 d1 b1 db`)를 UTF-8로 읽은 것이다. `c7`과 `db`는 UTF-8 규칙에 맞지 않아 대체 문자 `�`(U+FFFD)가 됐고, 가운데 `d1 b1`은 우연히 2바이트 규칙에 맞아 키릴 문자가 나왔다. 물음표 다이아몬드가 많이 보이면 "EUC-KR인데 UTF-8로 읽었다"는 신호다.

여기서 중요한 차이가 있다. 첫째 경우는 바이트가 그대로 남아 있어서 올바르게 다시 읽으면 복구된다. 둘째 경우처럼 `�`로 바뀐 채 다시 저장하면 원래 바이트를 잃어버려 복구할 수 없다. 그래서 깨진 글자를 봤을 때 그 상태로 저장하거나 DB에 넣으면 안 된다. 파일을 옮길 때는 `iconv`로 명시적으로 바꾼다.

```bash
iconv -f UTF-8 -t CP949 nobom.csv > cp949.csv   # UTF-8 → CP949로 변환
file cp949.csv                                   # file은 CP949를 정확히 못 맞힌다
iconv -f CP949 -t UTF-8 cp949.csv                # 올바른 방향으로 되돌리면 복구된다
iconv -f UTF-8 -t UTF-8 cp949.csv; echo "exit=$?"   # UTF-8로 검사하면 잘못된 바이트 위치를 알려 준다
```

```text
cp949.csv: CSV ISO-8859 text
name,city
김철수,서울
name,city
iconv: illegal input sequence at position 10
exit=1
```

`file` 명령은 CP949를 "ISO-8859"로 잘못 추측했다. 인코딩 추측은 어디까지나 추측이다. 마지막 줄의 `-f UTF-8 -t UTF-8`은 파일이 올바른 UTF-8인지 검사하는 요령이다. 위치 10(0부터 세서 11번째 바이트, 줄바꿈 다음)에서 UTF-8 규칙에 어긋나는 바이트를 찾았다.

이중 인코딩도 흔한 모양이다. 이미 UTF-8인 바이트를 Latin-1로 잘못 읽은 뒤 다시 UTF-8로 저장하면, 글자 하나가 2~3글자로 늘어난 `Ã©` 같은 문자열이 된다. 서구권 데이터에서 `é`가 `Ã©`로 보이면 이것이다. DB 연결 설정(클라이언트 인코딩)이 틀린 채 몇 년 쌓인 데이터에서 자주 나온다.

## 같은 글자, 다른 바이트: 정규화

맥에서 올린 파일 이름 "보고서.pdf"가 검색에 안 걸리는 이유는 정규화다. 유니코드에는 같은 글자를 적는 방법이 여러 개인 경우가 있다. `한`은 완성형 코드 포인트 U+D55C 하나로 적을 수도 있고, 자모 세 개(ㅎ U+1112, ㅏ U+1161, ㄴ U+11AB)를 이어 적을 수도 있다. 화면에는 둘 다 `한`으로 보인다. 앞의 것을 NFC(조합형으로 모으기), 뒤의 것을 NFD(분해하기)라고 한다.

```python
import unicodedata
n = "한글"
d = unicodedata.normalize("NFD", n)
print(len(n), len(d), [hex(ord(c)) for c in d], len(d.encode()), n == d,
      unicodedata.normalize("NFC", d) == n)
```

```text
2 6 ['0x1112', '0x1161', '0x11ab', '0x1100', '0x1173', '0x11af'] 18 False True
```

NFD로 바꾼 "한글"은 코드 포인트 6개, 18바이트이고 원래 문자열과 `==`로 다르다. NFC로 되돌리면 같아진다. macOS는 예전 파일 시스템(HFS+)이 파일 이름을 NFD로 저장했고, 지금도 Finder 등에서 만든 파일 이름이 NFD로 오는 경우가 많다. 그 파일을 윈도우에서 압축을 풀거나 웹으로 올리면 이름이 "ㅂㅗㄱㅗㅅㅓ"처럼 자모가 풀려 보이고, NFC로 저장된 DB 값과 비교하면 다르다고 나온다.

서버에서는 입력을 받는 곳에서 한 번 NFC로 정규화해서 저장하는 것이 안전하다. 파일 업로드 이름, 검색어, 아이디 같은 값이 대상이다. NFKC라는 더 강한 정규화도 있는데, 전각 `Ａ`를 `A`로, `①`을 `1`로 바꾸는 식으로 모양이 비슷한 글자까지 합친다. 아이디 중복 검사처럼 "비슷하게 보이면 같은 것으로 본다"가 필요할 때 쓴다. 다만 원래 글자를 잃으니 본문 저장에는 쓰지 않는다.

## DB에서 글자 수와 바이트 수

DB로 가 보자. 회원 테이블 하나로 계속 본다. PostgreSQL의 `varchar(n)`은 바이트가 아니라 글자(코드 포인트) 수로 센다.

```sql
CREATE TABLE users (id int PRIMARY KEY, name varchar(5));   -- 이름은 5자까지
INSERT INTO users VALUES (1, '김철수'), (2, 'Kim'), (3, '😀👍🏽');
SELECT id, name,
       char_length(name)  AS chars,   -- 코드 포인트 수
       octet_length(name) AS bytes    -- UTF-8 바이트 수
FROM users ORDER BY id;
```

```text
 id |  name  | chars | bytes
----+--------+-------+-------
  1 | 김철수 |     3 |     9
  2 | Kim    |     3 |     3
  3 | 😀👍🏽 |     3 |    12
```

셋 다 3자다. 그런데 `😀👍🏽`은 화면에 두 글자로 보이는데 3자로 세어졌다. 피부색 엄지가 코드 포인트 2개이기 때문이다. 프런트엔드가 그래핌으로 "5자 이하"를 검사해 통과시켜도 DB는 코드 포인트로 세어 거부할 수 있다. 다섯 글자를 넘기면 PostgreSQL은 자르지 않고 에러를 낸다. NFD 문자열은 글자 수가 세 배로 늘어서 더 쉽게 넘친다.

```sql
INSERT INTO users VALUES (4, '가나다라마바');                  -- 6자
INSERT INTO users VALUES (5, normalize('가나다', NFD));        -- 보기엔 3자, 실제로는 자모 6개
SELECT name FROM users WHERE name = normalize('김철수', NFD);  -- NFD로 검색하면?
```

```text
ERROR:  value too long for type character varying(5)
ERROR:  value too long for type character varying(5)
 name
------
(0 rows)
```

마지막 쿼리가 맥 파일 이름 버그를 그대로 보여 준다. 저장된 `김철수`(NFC)와 검색한 `김철수`(NFD)는 바이트가 달라서 아무것도 안 나온다. PostgreSQL 13부터 `normalize()` 함수와 `IS NFC NORMALIZED` 검사를 쓸 수 있다.

DB마다 세는 단위가 다르다는 점도 기억해 두자. PostgreSQL과 MySQL의 `varchar(n)`은 글자 수다. 오라클의 `VARCHAR2(10)`은 기본이 바이트 수라서 한글 3자가 9바이트로 거의 꽉 찬다. 그리고 MySQL은 strict 모드가 꺼져 있으면 넘치는 값을 에러 없이 잘라서 넣고 경고만 남긴다(MySQL 8은 기본이 strict다). "DB에서 이름이 잘렸다"는 버그는 대개 이 둘 중 하나다. 타입 고르는 법은 [PostgreSQL 데이터 타입 글](/posts/postgres-data-types)에 더 있다.

클라이언트와 서버의 인코딩이 다르면 DB가 변환해 준다. 변환할 수 없는 글자가 있으면 에러를 낸다.

```sql
SHOW server_encoding;              -- UTF8
SET client_encoding = 'LATIN1';    -- 클라이언트가 Latin-1이라고 주장하면
SELECT name FROM users WHERE id = 1;
```

```text
ERROR:  character with byte sequence 0xea 0xb9 0x80 in encoding "UTF8" has no equivalent in encoding "LATIN1"
```

`0xea 0xb9 0x80`은 앞에서 본 `김`이다. PostgreSQL은 깨진 글자를 몰래 내보내지 않고 거부한다. 다만 클라이언트 쪽에서 `SQL_ASCII`처럼 변환을 안 하는 설정을 쓰면 바이트가 그대로 들어가 나중에 깨진 데이터가 된다. 새 DB는 언제나 `UTF8`로 만든다.

## MySQL의 utf8은 UTF-8이 아니다

MySQL을 쓴다면 꼭 알아야 할 함정이 있다. MySQL의 `utf8` 문자 집합은 글자 하나에 최대 3바이트만 허용하는 `utf8mb3`의 별칭이다. MySQL이 처음 UTF-8을 넣을 때 BMP만 지원했기 때문이다. 그래서 4바이트 글자인 이모지나 일부 한자를 넣으면 `Incorrect string value: '\xF0\x9F\x98\x80...' for column` 에러가 나거나, strict 모드가 꺼져 있으면 그 자리가 `?`로 바뀐다. 진짜 UTF-8은 `utf8mb4`다. MySQL 8.0부터는 기본 문자 집합이 `utf8mb4`(정렬 규칙 `utf8mb4_0900_ai_ci`)이고 `utf8`이라는 이름은 사라질 예정이라고 경고한다.

오래된 DB를 `utf8mb4`로 옮길 때 자주 걸리는 게 인덱스 길이다. 글자당 최대 바이트가 3에서 4로 늘어서, 예전 InnoDB의 767바이트 인덱스 한도(COMPACT 행 형식)에서 `varchar(255)` 인덱스가 `Specified key was too long; max key length is 767 bytes`로 실패했다. 255 × 4 = 1020바이트라서다. MySQL 5.7 이후의 DYNAMIC 행 형식은 한도가 3072바이트라 대부분 풀렸다. 연결 설정도 함께 바꿔야 한다. JDBC URL이나 드라이버 설정의 문자 집합이 `utf8`로 남아 있으면 서버가 `utf8mb4`여도 이모지가 깨진다. MySQL 쪽 구조는 [InnoDB 기본 글](/posts/mysql-innodb-basics)에서 볼 수 있다.

## HTTP와 HTML의 charset

웹에서는 바이트가 어떤 인코딩인지 헤더로 알려 준다. `Content-Type: text/html; charset=utf-8`이 그것이다. 헤더가 없으면 브라우저는 HTML 앞부분의 `<meta charset="utf-8">`을 찾는다. 이 태그는 문서의 처음 1024바이트 안에 있어야 한다. 브라우저가 그 범위까지만 미리 훑어보고 인코딩을 정하기 때문이다. 둘 다 없으면 브라우저가 추측하는데, 이때 한국어 윈도우 사용자에게는 EUC-KR로 보이고 다른 사람에게는 다르게 보이는 일이 생긴다. 헤더 구조는 [HTTP 메시지 글](/posts/http-message)에 있다.

JSON은 다르다. 표준(RFC 8259)이 네트워크로 주고받는 JSON은 UTF-8이어야 한다고 못 박아서 `application/json`에는 charset 파라미터가 의미가 없다. 그래도 일부 오래된 클라이언트가 charset이 없으면 다른 인코딩으로 읽는 경우가 있어 `charset=utf-8`을 붙여 두는 서버도 많다.

URL에는 ASCII만 들어갈 수 있다. 한글 경로나 쿼리는 UTF-8 바이트를 `%` 뒤 16진수로 적는 퍼센트 인코딩을 거친다. `한`은 `%ED%95%9C`가 된다. 앞에서 계산한 UTF-8 바이트 그대로다. 오래된 서버가 쿼리 문자열을 EUC-KR로 해석하면 검색어가 깨진다. 폼 전송은 페이지의 인코딩을 따라가므로, 페이지가 UTF-8이면 폼 데이터도 UTF-8이다. 폼이 바이트로 바뀌는 과정은 [HTML 폼 글](/posts/html-form-http)에 있다. 바이트를 글자만 다니는 길에 싣는 또 다른 방법인 Base64는 [Base64 글](/posts/base64)에서 다뤘다.

## 현장에서 깨진 글자를 만났을 때

깨진 글자를 보면 먼저 "바이트가 상했나, 읽는 표가 틀렸나"를 가른다. 화면에 보이는 글자가 아니라 실제 바이트를 본다.

```bash
od -A x -t x1z 파일 | head          # 파일의 실제 바이트
psql -c "SELECT name, convert_to(name, 'UTF8') FROM users WHERE id = 1"   # DB에 저장된 바이트
curl -sI https://example.com | grep -i content-type   # 서버가 알려 주는 charset
```

바이트가 `ea b9 80`처럼 올바른 UTF-8이면 데이터는 멀쩡하고 읽는 쪽 설정이 틀린 것이다. 터미널 로캘(`LANG=C.UTF-8`), 엑셀의 가져오기 인코딩, 응답 헤더를 고친다. 바이트가 `ef bf bd`(U+FFFD의 UTF-8)로 바뀌어 있으면 이미 어딘가에서 한 번 잘못 읽고 다시 저장한 것이라 그 데이터는 복구할 수 없다. 이때는 입력 경로의 모든 단계(브라우저 → 서버 → 드라이버 → DB 연결 → 테이블)의 인코딩 설정을 하나씩 확인해 어디서 틀렸는지 찾고, 원본에서 다시 넣는다.

규칙은 단순하다. 처음 들어올 때 인코딩을 확실히 하고(UTF-8로 디코딩, 필요하면 NFC 정규화), 안에서는 언제나 유니코드 문자열로 다루고, 나갈 때 UTF-8로 인코딩하며 charset을 명시한다. 글자 수 제한은 무엇을 세는지(바이트, 코드 포인트, 그래핌)를 프런트엔드와 DB가 같은 단위로 맞춘다.

## 면접에서 나올 만한 질문

### 유니코드와 UTF-8은 같은 것인가요?

아니다. 유니코드는 세상의 글자에 번호(코드 포인트)를 붙이는 문자 집합이고, UTF-8은 그 번호를 바이트로 적는 인코딩 방법 중 하나다. 같은 유니코드 문자열을 UTF-8, UTF-16, UTF-32로 각각 다르게 적을 수 있다. `한`은 코드 포인트 U+D55C이고, UTF-8로는 `ED 95 9C`, UTF-16으로는 `D5 5C`다.

### UTF-8이 널리 쓰이는 이유는 무엇인가요?

ASCII와 완전히 호환되어 영문 텍스트는 1바이트 그대로이고, 멀티바이트 글자의 어떤 바이트도 ASCII 범위에 들어가지 않아 기존 C 코드나 프로토콜이 깨지지 않는다. 바이트 순서 문제가 없어 BOM이 필요 없고, 첫 바이트 모양으로 글자 길이와 시작 위치를 알 수 있어 중간부터 읽어도 다시 맞출 수 있다. 대신 한글은 UTF-8에서 3바이트로 EUC-KR(2바이트)보다 크다.

### 자바스크립트에서 이모지의 length가 2로 나오는 이유는요?

자바스크립트 문자열은 UTF-16 코드 유닛의 배열이고 `length`는 유닛 수를 센다. BMP 밖의 글자는 서로게이트 쌍, 즉 유닛 두 개로 적기 때문에 이모지 하나가 2가 된다. 피부색이나 ZWJ로 이은 이모지는 코드 포인트도 여러 개라 더 커진다. 사람 눈의 글자 수는 `Intl.Segmenter`로 그래핌 클러스터를 세어야 한다.

### 한글이 깨져 보일 때 원인을 어떻게 찾나요?

화면이 아니라 실제 바이트를 본다. 바이트가 올바른 UTF-8이면 데이터는 멀쩡하고 읽는 쪽이 다른 인코딩(대개 CP949)으로 해석한 것이니 설정만 고치면 된다. 바이트가 `EF BF BD`로 바뀌어 있으면 중간에 잘못 읽고 대체 문자로 저장한 것이라 복구가 안 되고, 입력 경로의 단계별 인코딩 설정을 확인해 원인을 찾아 원본에서 다시 넣는다. 낯선 한자가 섞이면 UTF-8을 CP949로 읽은 것, 물음표 다이아몬드가 많으면 그 반대인 경우가 많다.

### BOM은 무엇이고 언제 넣나요?

U+FEFF를 파일 맨 앞에 넣어 UTF-16의 바이트 순서나 UTF-8이라는 사실을 알리는 표시다. UTF-8에서는 `EF BB BF` 세 바이트다. 엑셀에서 열 CSV에는 붙여야 한글이 안 깨지지만, JSON, 셸 스크립트, 설정 파일에 붙으면 첫 키 이름이 바뀌거나 파싱이 실패한다. 읽는 쪽은 파이썬 `utf-8-sig`처럼 있으면 떼는 옵션을 쓴다.

### NFC와 NFD는 무엇이고 왜 문제가 되나요?

같은 글자를 완성형 코드 포인트 하나(NFC)로 적을지, 자모로 분해해서(NFD) 적을지의 차이다. 화면에는 같아 보이지만 바이트와 글자 수가 다르므로 `==` 비교, 검색, 유니크 제약이 실패한다. macOS에서 온 파일 이름이 NFD인 경우가 많아 자주 터진다. 입력 경계에서 NFC로 정규화해 저장한다.

### MySQL에서 utf8과 utf8mb4는 무엇이 다른가요?

MySQL의 `utf8`은 글자당 최대 3바이트인 `utf8mb3`의 별칭이라 이모지 같은 4바이트 글자를 저장하지 못한다. 진짜 UTF-8은 `utf8mb4`이고 MySQL 8의 기본값이다. 옮길 때는 테이블뿐 아니라 연결 문자 집합도 바꿔야 하고, 예전 767바이트 인덱스 한도에서는 `varchar(255)` 인덱스가 너무 길어지는 문제를 확인한다.

### varchar(10)에 한글 10자가 들어가나요?

DB마다 다르다. PostgreSQL과 MySQL은 글자(코드 포인트) 수로 세므로 들어간다. 오라클 `VARCHAR2(10)`은 기본이 바이트 수라 한글 3자로 거의 찬다. 그리고 "글자"가 코드 포인트라는 점도 봐야 한다. 피부색 이모지나 NFD 한글은 눈에 보이는 것보다 코드 포인트가 많아서, 프런트엔드가 그래핌으로 센 제한과 어긋난다.
