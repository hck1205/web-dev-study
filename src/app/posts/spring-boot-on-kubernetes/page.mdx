## 배포할 때마다 502가 몇 개씩 섞인다

스프링 부트 서비스를 쿠버네티스에 올리고 롤링 배포를 하면 대시보드에 502가 몇 개씩 튄다. 앱 로그에는 에러가 없다. 결제사가 잠깐 느려진 날에는 Pod가 줄줄이 재시작했고, CPU 한도를 1코어로 줄였더니 새 Pod가 뜨는 데 1분 가까이 걸리면서 HPA가 Pod를 계속 늘렸다.

셋 다 스프링 코드의 버그가 아니다. 쿠버네티스가 앱에게 묻는 것(살아 있나, 받을 준비가 됐나, 이제 끝내라)과 스프링 부트가 대답하는 방식이 어긋나서 생긴다. 이 글은 그 대답을 맞추는 법을 따라간다. 프로브가 무엇을 묻는지, Pod가 끝나는 순서 같은 쿠버네티스 쪽 이야기는 [프로브 글](/posts/k8s-pod-probes)과 [Pod의 일생](/posts/k8s-pod-lifecycle)에 있으니 여기서는 스프링 쪽에서 무엇을 켜고 어떤 숫자를 맞추는지에 집중한다. JVM 힙 크기를 컨테이너 한도에 맞추는 법은 [JVM 메모리 글](/posts/java-jvm-memory-gc)에서 다뤘다.

실험은 Spring Boot 4.1.1, JDK 21(OpenJDK 21.0.12), Docker 29에서 했다. 출력은 모두 실제로 돌린 결과이고, 클러스터가 없어서 `kubectl` 출력과 매니페스트만 예시다. 스프링이 빈을 어떻게 만들고 자동 설정이 무엇을 켜는지는 [IoC와 DI](/posts/spring-ioc-di), [자동 설정](/posts/spring-boot-auto-configuration) 글에 있다.

예제 앱은 주문 조회 API 하나다. `ms` 파라미터만큼 잠깐 멈췄다가 응답한다. 결제사 연결을 흉내 내는 헬스 지표도 하나 붙였다.

```java
@RestController
public class OrderController {
    @GetMapping("/orders/{id}")
    public String order(@PathVariable String id, @RequestParam(defaultValue = "0") long ms) throws InterruptedException {
        log.info("start /orders/{} ({}ms)", id, ms);
        Thread.sleep(ms);                       // 느린 처리를 흉내 낸다
        log.info("done  /orders/{}", id);
        return "order " + id + " ok\n";
    }
}

@Component("payment")
public class PaymentHealthIndicator implements HealthIndicator {
    @Override
    public Health health() {
        boolean up = !Boolean.getBoolean("payment.down"); // -Dpayment.down=true면 DOWN
        return up ? Health.up().withDetail("pg", "reachable").build()
                  : Health.down().withDetail("pg", "timeout after 2000ms").build();
    }
}
```

Boot 4에서는 `HealthIndicator`가 `org.springframework.boot.health.contributor` 패키지로 옮겨졌다. 3.x 코드를 그대로 가져오면 import부터 깨지니, 옮기는 과정은 [Boot 4 마이그레이션 글](/posts/spring-boot-4-migration)을 본다.

## 액추에이터가 프로브 두 개를 따로 만든다

`spring-boot-starter-actuator`를 넣고 띄우면 `/actuator/health` 아래에 그룹 두 개가 생긴다. `liveness`와 `readiness`다.

```bash
java -jar target/orders.jar &                              # 19100 포트로 뜬다
curl -s localhost:19100/actuator/health | python3 -m json.tool   # 전체 헬스
curl -si localhost:19100/actuator/health/liveness          # 살아 있나
curl -si localhost:19100/actuator/health/readiness         # 받을 준비가 됐나
```

```text
{
    "components": {
        "diskSpace": { ... "status": "UP" },
        "livenessState": { "status": "UP" },
        "payment": { "details": { "pg": "reachable" }, "status": "UP" },
        "ping": { "status": "UP" },
        "readinessState": { "status": "UP" },
        "ssl": { ... "status": "UP" }
    },
    "groups": [
        "liveness",
        "readiness"
    ],
    "status": "UP"
}

HTTP/1.1 200
Content-Type: application/vnd.spring-boot.actuator.v3+json

{"status":"UP"}
HTTP/1.1 200
Content-Type: application/vnd.spring-boot.actuator.v3+json

{"status":"UP"}
```

(`diskSpace`와 `ssl`의 세부 값은 줄였다.) 볼 곳은 `groups`다. 전체 헬스는 디스크, 결제사, SSL 인증서까지 모든 지표를 합친 값이고, 두 그룹은 기본적으로 `livenessState`와 `readinessState` 하나씩만 본다. 이 두 상태는 외부 시스템을 확인한 결과가 아니라 스프링 애플리케이션이 스스로 들고 있는 값이다. 컨텍스트가 다 뜨면 readiness가 `ACCEPTING_TRAFFIC`이 되고, 끝나기 시작하면 `REFUSING_TRAFFIC`이 된다.

버전마다 기본값이 다르다. 내려받은 jar의 설정 메타데이터를 열어 보면 3.5.16에서는 `management.endpoint.health.probes.enabled`의 기본값이 `false`이고, 4.1.1에서는 `true`다. 3.x에서는 `KUBERNETES_SERVICE_HOST` 환경 변수로 쿠버네티스 위라는 걸 알아챘을 때만 그룹이 켜졌다. 4.x는 어디서 띄우든 켜져 있다. 로컬에서 켜 둔 3.x 앱은 그룹이 없다가 클러스터에서만 생기니, 로컬과 클러스터에서 경로가 달라 헷갈렸던 사람이라면 이 차이 때문이다.

앱 안에서 상태를 직접 바꿀 수도 있다. 회복할 수 없는 상태(데드락을 감지했다, 필수 캐시가 깨졌다)를 알아챘을 때 liveness를 `BROKEN`으로 올리면 kubelet이 컨테이너를 다시 띄운다.

```java
@PostMapping("/admin/break")
public String breakLiveness() {
    AvailabilityChangeEvent.publish(events, this, LivenessState.BROKEN); // 이벤트 하나로 상태가 바뀐다
    return "liveness BROKEN\n";
}
```

```bash
curl -s -X POST localhost:19100/admin/break
curl -s -w ' %{http_code}\n' localhost:19100/actuator/health/liveness
curl -s -w ' %{http_code}\n' localhost:19100/actuator/health/readiness
```

```text
liveness BROKEN
{"status":"DOWN"} 503
{"status":"UP"} 200
```

liveness만 503이 됐고 readiness는 그대로다. 둘이 따로 움직인다는 게 중요하다. 쿠버네티스는 liveness 실패에 재시작으로, readiness 실패에 트래픽 빼기로 반응하기 때문이다.

## 결제사가 느려졌다고 Pod를 죽이면 안 된다

프로브 경로를 `/actuator/health/liveness`가 아니라 `/actuator/health`로 걸어 두는 실수가 흔하다. 결제사 연결이 끊긴 상황을 `-Dpayment.down=true`로 만들고 세 경로를 차례로 불렀다.

```bash
java -Dpayment.down=true -jar target/orders.jar &
for p in "" /liveness /readiness; do
  curl -s -o body -w "GET /actuator/health$p -> %{http_code} " localhost:19100/actuator/health$p
  python3 -c "import json;print(json.load(open('body'))['status'])"
done
```

```text
GET /actuator/health -> 503 DOWN
GET /actuator/health/liveness -> 200 UP
GET /actuator/health/readiness -> 200 UP
```

전체 헬스는 503이다. liveness를 이 경로에 걸었다면 kubelet은 모든 Pod를 재시작한다. 결제사는 여전히 느리니 다시 뜬 Pod도 또 503을 내고, 재시작이 이어지다가 CrashLoopBackOff로 대기 시간이 늘어난다. 결제와 상관없는 주문 조회까지 같이 멈춘다. 처음에 본 "결제사가 느려진 날 Pod가 줄줄이 재시작"이 이 장면이다.

그렇다고 readiness에 결제사를 넣는 것도 따져 봐야 한다. 그룹에 넣으려면 `include`에 지표 이름을 적는다.

```bash
java -Dpayment.down=true \
  -Dmanagement.endpoint.health.group.readiness.include=readinessState,payment \
  -Dmanagement.endpoint.health.group.readiness.show-details=always \
  -jar target/orders.jar &
```

```text
GET /actuator/health -> 503 DOWN
GET /actuator/health/liveness -> 200 UP
GET /actuator/health/readiness -> 503 DOWN
{"components":{"payment":{"details":{"pg":"timeout after 2000ms"},"status":"DOWN"},"readinessState":{"status":"UP"}},"status":"DOWN"}
```

이번엔 재시작은 없지만 모든 Pod가 동시에 준비 안 됨이 된다. Service 뒤에 받을 Pod가 하나도 없으니 결제와 상관없는 요청까지 전부 실패한다. 아래 그림에서 다음을 누르면 세 가지 설정에서 요청이 어디서 막히는지 차례로 보인다.

## SIGTERM을 받은 스프링이 하는 일

이제 배포 중 502로 돌아간다. Pod를 내릴 때 kubelet은 컨테이너에 SIGTERM을 보낸다. 스프링 부트가 이걸 받으면 JVM 종료 훅이 돌고, 컨텍스트를 닫는 과정에서 웹 서버가 우아한 종료(graceful shutdown)에 들어간다. 새 연결은 그만 받고, 이미 처리 중인 요청은 끝날 때까지 기다린다.

직접 재현했다. 5초 걸리는 요청을 보내 두고, 1초 뒤에 SIGTERM을 보내고, 그 0.5초 뒤에 새 요청을 보낸다.

```bash
java -jar target/orders.jar & APP=$!
curl -s -m 20 "localhost:19100/orders/1?ms=5000" &   # 5초 걸리는 요청
sleep 1; kill -TERM $APP                              # 처리 중에 SIGTERM
sleep 0.5; curl -s -m 3 localhost:19100/orders/2      # 새 요청
wait $APP; echo "app exit=$?"
```

```text
[+1.0s] kill -TERM 17283
[+1.5s] new request: rc=7 body=
[+1.5s] readiness: rc=7 http=000
[+5.0s] old request: rc=0 body=order 1 ok
[+5.1s] app exit=143
01:25:31.924-exec-3] demo.OrderController                     : start /orders/1 (5000ms)
01:25:32.917ownHook] o.s.boot.tomcat.GracefulShutdown         : Commencing graceful shutdown. Waiting for active requests to complete
01:25:36.925-exec-3] demo.OrderController                     : done  /orders/1
01:25:36.944hutdown] o.s.boot.tomcat.GracefulShutdown         : Graceful shutdown complete
```

(시각 표시는 스크립트가 붙였고, 로그는 시각과 스레드 이름 일부만 남겼다.) 처리 중이던 `/orders/1`은 SIGTERM 뒤 4초를 더 기다려 `order 1 ok`를 받았다. 로그의 `Commencing graceful shutdown`과 `Graceful shutdown complete` 사이가 그 기다림이다. 반면 SIGTERM 직후 온 새 요청은 curl 종료 코드 7, 연결 거부다. 포트가 이미 닫혔기 때문이다. 프로세스 종료 코드는 143(128 + SIGTERM 15)이다. 정상 종료로 보지 않는 모니터링이 있는데, 쿠버네티스에서는 SIGTERM으로 끝난 컨테이너의 흔한 코드다.

설정을 바꾸면 결과가 달라진다. `server.shutdown=immediate`로 같은 실험을 하면 처리 중이던 요청이 SIGTERM과 동시에 끊긴다.

```text
=== immediate
[+1.0s] kill -TERM 17958
[+1.0s] old request: rc=52 body=
[+1.5s] new request: rc=7 body=
[+1.5s] app exit=143
```

curl 종료 코드 52는 서버가 응답 없이 연결을 닫았다는 뜻이다. Ingress 뒤라면 사용자는 502를 받는다. 기다리는 시간을 `spring.lifecycle.timeout-per-shutdown-phase=2s`로 줄이면 2초를 기다리다 포기한다.

```text
=== timeout 2s
[+1.0s] kill -TERM 18336
[+3.0s] old request: rc=52 body=
[+3.1s] app exit=143
o.s.c.support.DefaultLifecycleProcessor  : Shutdown phase 2147482623 ends with 1 bean still running after timeout of 2000ms: [webServerGracefulShutdown]
o.s.boot.tomcat.GracefulShutdown         : Graceful shutdown aborted with one or more requests still active
```

`Graceful shutdown aborted with one or more requests still active`가 보이면 요청이 이 시간보다 길었다는 뜻이다. 배포 때마다 이 줄이 찍히면 타임아웃을 늘릴지, 그 요청을 짧게 만들지 정해야 한다.

## 포트가 닫히는 순간과 목록에서 빠지는 순간

우아한 종료가 있어도 502는 남는다. 앞의 실험에서 새 요청이 연결 거부를 받은 게 그 이유다. 쿠버네티스에서는 SIGTERM과 Service 목록(EndpointSlice)에서 빠지는 일이 동시에 출발하고, 모든 노드의 kube-proxy와 Ingress 컨트롤러가 목록을 갱신하기까지 시간이 걸린다. 그 사이에 이 Pod로 오는 새 요청은 이미 닫힌 포트를 만난다. 원리는 [Pod의 일생](/posts/k8s-pod-lifecycle) 글에서 Node 앱으로 재현했고, 스프링도 똑같다.

그래서 preStop에서 몇 초 기다린다. 아래 그림에서 다음을 누르면 preStop이 있는 배포에서 일이 일어나는 순서가 보인다.

매니페스트는 이렇게 된다(예시).

```yaml
spec:
  terminationGracePeriodSeconds: 45     # preStop 10초 + 스프링 기다림 30초 + 여유 5초
  containers:
    - name: orders
      image: registry.example.com/orders:1.0.0
      ports:
        - containerPort: 8080
      lifecycle:
        preStop:
          sleep:
            seconds: 10                 # 셸이 없는 이미지에서도 쓸 수 있는 sleep 동작
      startupProbe:
        httpGet: { path: /livez, port: 8080 }
        periodSeconds: 2
        failureThreshold: 60            # 최대 120초까지 뜨기를 기다린다
      livenessProbe:
        httpGet: { path: /livez, port: 8080 }
        periodSeconds: 10
        failureThreshold: 3
      readinessProbe:
        httpGet: { path: /readyz, port: 8080 }
        periodSeconds: 5
        failureThreshold: 2
```

`preStop.sleep`은 쿠버네티스 1.29에 알파로 들어와 1.30부터 기본으로 켜졌다. 그보다 오래된 클러스터나 기능을 끈 클러스터에서는 `exec: { command: ["sh", "-c", "sleep 10"] }`을 쓰는데, distroless처럼 셸이 없는 이미지에서는 이 방법이 안 된다. 어느 쪽을 쓸 수 있는지 클러스터 버전부터 확인한다.

숫자 사이의 관계를 봐야 한다. 유예 시간 타이머는 preStop이 시작될 때부터 흐른다. 스프링이 30초를 기다려도 preStop 10초와 합쳐 유예 시간 30초를 넘기면 kubelet이 SIGKILL로 끊는다. 이때는 스프링 로그에 아무것도 안 남는다. 아래에서 직접 계산해 보자.

두 번째 테스트가 흔한 실수다. 502를 없애려고 preStop을 추가하면서 유예 시간을 그대로 두면, 오래 걸리던 요청이 이번엔 SIGKILL로 끊긴다. 규칙은 `terminationGracePeriodSeconds ≥ preStop + timeout-per-shutdown-phase + 여유`다.

## 관리 포트를 나누면 보이는 것

앞의 실험에서 SIGTERM 뒤 readiness 요청도 연결 거부(종료 코드 7)였다. 같은 포트를 쓰니 포트가 닫히면 readiness도 함께 닫힌다. `management.server.port`로 관리 포트를 나누면 종료 중의 상태가 보인다.

```bash
java -Dmanagement.server.port=19101 -jar target/orders.jar & APP=$!
curl -s "localhost:19100/orders/1?ms=4000" >/dev/null & sleep 0.5   # 처리 중인 요청 하나
kill -TERM $APP
for i in 1 2 3 4 5 6; do sleep 0.5; echo "t=$i readiness(19101): $(curl -s -m 1 -w ' %{http_code}' localhost:19101/actuator/health/readiness)"; done
```

```text
t=1 readiness(19101): {"status":"OUT_OF_SERVICE"} 503
t=2 readiness(19101): {"status":"OUT_OF_SERVICE"} 503
t=3 readiness(19101): {"status":"OUT_OF_SERVICE"} 503
t=4 readiness(19101): {"status":"OUT_OF_SERVICE"} 503
t=5 readiness(19101): {"status":"OUT_OF_SERVICE"} 503
t=6 readiness(19101): {"status":"OUT_OF_SERVICE"} 503
```

종료가 시작되자 readiness가 `OUT_OF_SERVICE`(503)로 답한다. `ReadinessState.REFUSING_TRAFFIC`이 헬스 상태로는 이렇게 보인다. 남은 요청을 처리하는 동안 kubelet이 이 Pod를 준비 안 됨으로 볼 수 있다. 다만 관리 포트를 나누면 프로브가 실제 트래픽을 받는 커넥터를 거치지 않는다. 메인 포트의 스레드 풀이 바닥나도 관리 포트는 멀쩡히 200을 낼 수 있다. 그래서 관리 포트를 나눌 때는 `add-additional-paths=true`로 `/livez`, `/readyz`를 메인 포트에도 열고 프로브는 그쪽에 거는 구성을 많이 쓴다. 관리 포트는 Prometheus 수집과 운영용으로 남긴다.

## JVM은 CPU 한도를 어떻게 읽나

메모리 한도에 맞춰 힙을 정하는 법은 [JVM 메모리 글](/posts/java-jvm-memory-gc)에 있으니, 여기서는 CPU를 본다. JVM은 cgroup의 CPU 한도를 읽어 사용할 코어 수를 정하고, 그 수로 GC 종류와 스레드 수를 고른다. 같은 클래스를 한도만 바꿔 컨테이너에서 돌렸다. 이 기계의 Docker는 cgroup v1이고, JDK 21은 v1과 v2를 모두 읽는다.

```bash
# 코어 수, ForkJoin 공용 풀 크기, 최대 힙, GC 이름을 찍는 클래스
docker run --rm --name sp2-jvm --cpus=1 --memory=512m -v $PWD:/w -w /w eclipse-temurin:21-jre java Cpu
docker run --rm --name sp2-jvm --cpus=2 --memory=2g   -v $PWD:/w -w /w eclipse-temurin:21-jre java Cpu
docker run --rm --name sp2-jvm --cpus=0.5 --memory=1g -v $PWD:/w -w /w eclipse-temurin:21-jre java Cpu
```

```text
### docker run --cpus=1 --memory=512m
availableProcessors = 1
ForkJoin parallelism = 1
maxHeap MiB = 123
GC = Copy
GC = MarkSweepCompact
### docker run --cpus=2 --memory=2g
availableProcessors = 2
ForkJoin parallelism = 1
maxHeap MiB = 512
GC = G1 Young Generation
GC = G1 Concurrent GC
GC = G1 Old Generation
### docker run --cpus=0.5 --memory=1g
availableProcessors = 1
ForkJoin parallelism = 1
maxHeap MiB = 247
GC = Copy
GC = MarkSweepCompact
```

1코어 이하에서는 G1 대신 Serial GC(`Copy`, `MarkSweepCompact`)를 고른다. 0.5코어는 올림해서 1로 본다. 2코어와 2GiB가 되어야 G1이 된다. 코어 수는 GC 스레드, JIT 컴파일러 스레드, `parallelStream()`이 쓰는 ForkJoin 공용 풀 크기에 그대로 들어간다.

여기서 쿠버네티스와 어긋나는 지점이 있다. requests만 주고 limits를 안 주는 Pod가 많다. requests는 cgroup v1의 `cpu.shares`(v2는 `cpu.weight`)가 되는데, JDK 19부터 JVM은 이 값을 코어 수 계산에 쓰지 않는다.

```text
### --cpu-shares=2048 (limit 없음)
availableProcessors = 4
ForkJoin parallelism = 3
```

이 기계의 코어 4개를 다 본다. 64코어 노드라면 requests가 0.5코어인 Pod의 JVM도 64코어짜리처럼 스레드를 만든다. 반대로 limits로 1코어를 주면 Serial GC로 떨어진다. 둘 다 원하는 결과가 아닐 때는 직접 정한다.

```text
### --cpus=2 --memory=2g + -XX:ActiveProcessorCount=4 -XX:MaxRAMPercentage=75
availableProcessors = 4
ForkJoin parallelism = 3
maxHeap MiB = 1536
GC = G1 Young Generation
```

`-XX:ActiveProcessorCount`로 코어 수를 못 박으면 한도와 상관없이 그 수로 계산한다. 이 플래그는 스레드 수를 정할 뿐 CPU를 더 주지는 않는다. 2코어 한도에 4를 주면 스레드가 늘어난 만큼 한도에 더 자주 걸린다. 다음 절이 그 이야기다.

## 1코어에서 5초, 0.5코어에서 10초

시작 시간을 CPU 한도별로 쟀다. 각각 두 번씩 띄워 `Started OrdersApplication in` 줄을 읽었다.

```text
cpus=0.5 plain: Started OrdersApplication in 10.396 seconds (process running for 11.433)
cpus=0.5 plain: Started OrdersApplication in 10.338 seconds (process running for 11.367)
cpus=1 plain: Started OrdersApplication in 5.135 seconds (process running for 5.899)
cpus=1 plain: Started OrdersApplication in 5.158 seconds (process running for 5.791)
cpus=2 plain: Started OrdersApplication in 4.594 seconds (process running for 5.174)
cpus=2 plain: Started OrdersApplication in 3.524 seconds (process running for 4.229)
```

엔드포인트 하나짜리 앱이 0.5코어에서 10초가 걸린다. 실제 서비스는 빈이 훨씬 많으니 몇 배가 된다. 이유는 cgroup의 CPU 한도가 동작하는 방식에 있다. 한도는 100ms 주기마다 쓸 수 있는 CPU 시간(quota)으로 걸린다. 시작할 때 JVM은 클래스 로딩, JIT 컴파일, GC 스레드를 동시에 돌리니 몫을 빨리 다 쓰고, 남은 주기 동안 멈춘다(throttling). 시작이 끝난 직후 컨테이너의 `cpu.stat`을 읽었다.

```bash
docker run --rm --cpus=0.5 --memory=1g --entrypoint bash sp2-orders:2 -c \
  'java -Dspring.context.exit=onRefresh -jar app.jar >/dev/null 2>&1; cat /sys/fs/cgroup/cpu/cpu.stat'
```

```text
== cpus=0.5
nr_periods 108
nr_throttled 103
throttled_time 6286069058
== cpus=1
nr_periods 65
nr_throttled 13
throttled_time 198845602
== cpus=2
nr_periods 59
nr_throttled 0
throttled_time 0
```

(`nr_bursts`, `burst_time` 줄은 0이라 뺐다.) 0.5코어에서는 주기 108개 중 103개에서 멈췄고, 멈춘 시간을 더하면 6.29초다(`throttled_time`은 나노초). 시작 시간 10초의 절반 이상이 기다림이었다. 2코어에서는 한 번도 멈추지 않았다. `-Dspring.context.exit=onRefresh`는 컨텍스트가 다 뜨면 바로 끝내는 옵션이라 시작만 잴 때 편하다. 아래 그림은 0.5코어 한도에서 스레드 셋이 한 주기를 쓰는 모습을 단순하게 그린 것이다.

현장에서 이게 문제가 되는 곳이 두 군데 있다. 하나는 프로브다. liveness가 시작 시간보다 먼저 판정을 시작하면 다 뜨기 전에 재시작되고, 다음 시작도 똑같이 느리니 영영 못 뜬다. 앞의 매니페스트처럼 startupProbe로 시작을 넉넉히 기다리고, 그동안 liveness는 쉬게 한다. 다른 하나는 처음에 본 HPA다. 이건 마지막 절에서 본다.

## 이미지를 층으로 나눠 굽는다

```dockerfile
FROM eclipse-temurin:21-jre AS builder
WORKDIR /builder
COPY target/orders.jar app.jar
RUN java -Djarmode=tools -jar app.jar extract --layers --destination extracted

FROM eclipse-temurin:21-jre
WORKDIR /app
RUN useradd --system --uid 10001 app
COPY --from=builder /builder/extracted/dependencies/ ./
COPY --from=builder /builder/extracted/spring-boot-loader/ ./
COPY --from=builder /builder/extracted/snapshot-dependencies/ ./
COPY --from=builder /builder/extracted/application/ ./
RUN java -XX:ArchiveClassesAtExit=app.jsa -Dspring.context.exit=onRefresh -jar app.jar || true
USER 10001
ENTRYPOINT ["java", "-XX:SharedArchiveFile=app.jsa", "-jar", "app.jar"]
```

빌드한 이미지의 층 크기와, 응답 문자열 하나만 바꾸고 다시 빌드했을 때의 캐시다.

```bash
docker history sp2-orders:1 --format '{{.Size}}\t{{.CreatedBy}}' | head -9
docker build --progress=plain -t sp2-orders:2 . 2>&1 | grep -E "CACHED|COPY|RUN"
```


21.9MB 의존성 층은 `CACHED`, 바뀐 건 16.4kB짜리 `application`부터다. 대신 CDS 아카이브 36.7MB가 매번 새로 생긴다. 아카이브가 앱 클래스까지 담기 때문이다. 시작 시간을 얻는 대가로 배포마다 받는 양이 늘어나는 셈이라, 노드가 이미지를 받는 시간과 시작 시간 중 어느 쪽이 더 아픈지 보고 고른다.

Dockerfile을 직접 쓰지 않는 방법도 둘 있다. `mvn spring-boot:build-image`는 Cloud Native Buildpacks(Paketo)로 같은 층 구조의 이미지를 만들고 JVM 메모리 설정까지 계산해 넣는다. Docker 데몬과 빌더 이미지가 필요하다. Jib(`jib-maven-plugin`)는 Docker 데몬 없이 레지스트리에 바로 올리고 의존성·리소스·클래스를 따로 층으로 나눈다. CI에 Docker가 없을 때 편하다. 이 기계는 디스크가 넉넉하지 않아 두 방법은 돌려 보지 않았다.

## 시작을 빠르게 하는 방법들

startupProbe로 기다려 주는 건 증상을 받아 주는 것이고, 시작 자체를 줄이는 방법도 있다. 가장 손이 덜 가는 건 CDS(Class Data Sharing)다. 한 번 띄워 로딩한 클래스 정보를 파일(`app.jsa`)로 남기고, 다음부터 그 파일을 메모리에 바로 올려 클래스를 읽고 검증하는 일을 건너뛴다. 부트는 3.3부터 `extract`로 꺼낸 구조와 `spring.context.exit=onRefresh`로 이 학습 실행을 돕는다. 위 Dockerfile의 마지막 `RUN`이 그 학습 실행이다. 같은 이미지에서 CDS를 켜고 끈 시작 시간이다.

```text
cpus=0.5 plain: Started OrdersApplication in 10.396 seconds
cpus=0.5 cds:   Started OrdersApplication in 6.983 seconds
cpus=1 plain:   Started OrdersApplication in 5.135 seconds
cpus=1 cds:     Started OrdersApplication in 3.37 seconds
cpus=2 plain:   Started OrdersApplication in 3.524 seconds
cpus=2 cds:     Started OrdersApplication in 2.194 seconds
```

(두 번씩 잰 값 중 하나씩만 남기고 괄호 안의 프로세스 시간은 뺐다. 1코어 CDS는 4.09초와 3.37초로 흔들렸다.) 대략 30~40% 줄었다. 아카이브는 만든 JVM과 같은 JVM, 같은 jar 경로에서만 쓰인다. 베이스 이미지만 바꾸고 아카이브를 그대로 두면 JVM이 경고를 내고 무시한다. 그래서 이미지 안에서 만든다.

더 나가는 방법은 단정하기 어려운 부분이 많아 범위만 적는다. 스프링 AOT(`spring-boot:process-aot`)는 빌드 시점에 빈 정의를 코드로 미리 만들어 시작 때 할 일을 줄인다. 대신 프로필이나 `@Conditional` 결과가 빌드 시점에 굳는다. GraalVM 네이티브 이미지는 시작을 수십 밀리초 단위로 줄이지만 리플렉션 설정, 긴 빌드, 피크 처리량 차이를 감수해야 한다. JDK 24부터는 CDS를 넓힌 AOT 캐시(JEP 483)가 들어와 클래스를 링크한 상태까지 저장한다. JDK 21에서는 쓸 수 없어서 이 글에서는 재지 않았다.

## HPA가 JVM을 오해하는 순간

이제 처음의 세 번째 증상이다. CPU 사용률 70%를 목표로 둔 HPA가 배포나 확장 직후 Pod를 더 늘린다. 시작하는 JVM은 한도의 CPU를 다 쓴다. 1코어 한도에서 시작을 잰 결과다.

```bash
docker run --rm --cpus=1 --memory=1g --entrypoint bash sp2-orders:2 -c \
  'TIMEFORMAT="wall=%Rs user=%Us sys=%Ss"; time java -Dspring.context.exit=onRefresh -jar app.jar > /dev/null 2>&1'
```

```text
cpus=1 no-CDS wall=5.308s user=4.970s sys=0.176s
```

5.3초 동안 CPU를 5.1초 썼다. 사실상 100%다. 확장으로 새 Pod가 생기면 그 Pod가 100%를 찍고, 평균이 올라가니 HPA가 또 늘리는 일이 생길 수 있다. HPA는 막 뜬 Pod와 준비되지 않은 Pod의 CPU를 계산에서 일부 빼는 규칙이 있는데, 그 창이 JVM이 데워지는 시간(JIT가 뜨거운 코드를 컴파일하는 처음 몇 분)보다 짧으면 소용이 없다. 규칙은 [HPA 글](/posts/k8s-hpa)에서 다뤘다. 대처는 늘릴 때의 `behavior.scaleUp` 속도를 늦추고, startupProbe로 준비 시점을 실제 시작에 맞추고, CDS로 시작 자체를 줄이는 것이다.

메모리를 기준으로 한 HPA는 더 나쁘다. JVM은 GC로 힙 안을 비워도 운영체제에 메모리를 잘 돌려주지 않는다. 컨테이너 메모리 사용량은 부하가 지나간 뒤에도 내려오지 않고, HPA는 줄일 이유를 찾지 못한다. JVM 서비스는 CPU, 요청 수, 대기열 길이처럼 부하를 따라 오르내리는 지표로 확장한다.

requests와 limits도 JVM을 생각하고 정한다.

- CPU limits를 1코어 이하로 걸면 Serial GC로 떨어지고 시작이 throttling으로 늘어난다. limits를 걸려면 2코어 이상이나 `ActiveProcessorCount`와 GC 지정을 함께 둔다.
- limits 없이 requests만 주면 JVM이 노드 코어 수를 다 본다. 스레드 풀과 GC 스레드가 커지니 코어 수를 플래그로 정한다.
- 메모리는 requests와 limits를 같게 두고 힙을 그 비율로 정한다. 나머지는 [JVM 메모리 글](/posts/java-jvm-memory-gc)에서 계산했다.

## 배포 중 502를 다시 보면

502는 SIGTERM과 목록에서 빠지는 일이 동시에 출발해서 생겼다. preStop으로 목록이 먼저 비게 하고, 스프링의 우아한 종료로 남은 요청을 끝내고, 그 합이 유예 시간 안에 들어오게 숫자를 맞추면 사라진다. 결제사 때문에 Pod가 재시작한 건 프로브를 전체 헬스에 걸어서였고, liveness와 readiness 그룹을 따로 쓰면 된다. 느린 시작과 HPA의 오해는 CPU 한도와 JVM이 고르는 코어 수가 어긋나서였다. 같은 앱의 지표와 trace를 쿠버네티스에서 모으는 이야기는 [스프링 부트 관측 가능성](/posts/spring-boot-observability)으로 이어진다. 이미지를 빌드해 클러스터까지 보내는 길은 [EKS 배포 파이프라인](/posts/k8s-deploy-pipeline-eks)에 있다.

## 면접에서 나올 만한 질문

### 스프링 부트에서 liveness와 readiness를 어떻게 나눠 노출하나요?

액추에이터가 `/actuator/health/liveness`와 `/actuator/health/readiness` 두 헬스 그룹을 만든다. 각각 기본으로 애플리케이션이 스스로 들고 있는 `LivenessState`, `ReadinessState`만 본다. Boot 4에서는 기본으로 켜져 있고, 3.x는 쿠버네티스 환경을 감지했을 때나 `probes.enabled=true`일 때 켜졌다. `add-additional-paths=true`를 주면 메인 포트에 `/livez`, `/readyz`도 생긴다.

### liveness 프로브를 /actuator/health 전체에 걸면 왜 위험한가요?

전체 헬스는 DB, 외부 API 같은 의존성까지 합친 값이라 외부 하나가 느려지면 모든 Pod가 503을 낸다. kubelet은 그걸 보고 모든 Pod를 재시작하는데, 원인이 바깥에 있으니 재시작해도 낫지 않고 CrashLoopBackOff로 이어진다. 의존성과 상관없는 기능까지 같이 멈춘다. 외부 실패는 호출 코드의 타임아웃과 서킷 브레이커로 다루고, 전체 헬스는 모니터링에 쓴다.

### 그럼 readiness에는 DB를 넣어도 되나요?

여러 Pod가 함께 쓰는 DB를 넣으면 DB 장애 때 모든 Pod가 동시에 빠져 Service 뒤가 비게 된다. DB가 없으면 어차피 실패한다고 볼 수도 있지만, 캐시로 답할 수 있는 요청이나 DB와 상관없는 요청까지 연결 실패로 바뀐다. 넣는 건 이 Pod만 혼자 망가질 수 있는 것, 예를 들어 로컬 캐시 데우기 같은 것으로 한정하는 게 보통이다.

### 스프링의 graceful shutdown은 어떻게 동작하나요?

SIGTERM을 받으면 JVM 종료 훅에서 컨텍스트를 닫고, 웹 서버는 새 연결을 그만 받은 채 처리 중인 요청이 끝나기를 기다린다. 기다리는 최대 시간은 `spring.lifecycle.timeout-per-shutdown-phase`(기본 30초)이고, 넘기면 `Graceful shutdown aborted`를 남기고 끊는다. 3.4부터 `server.shutdown=graceful`이 기본값이다. readiness는 종료가 시작되면 `REFUSING_TRAFFIC`이 된다.

### graceful shutdown을 켰는데도 배포 중에 502가 나는 이유는?

SIGTERM과 EndpointSlice에서 빠지는 일이 동시에 시작되기 때문이다. 앱은 SIGTERM을 받자마자 포트를 닫는데, 아직 목록을 갱신하지 못한 kube-proxy나 Ingress가 새 요청을 이 Pod로 보낸다. preStop에서 몇 초 기다려 목록이 먼저 비게 하면 사라진다. 이때 `terminationGracePeriodSeconds`는 preStop과 스프링 대기 시간을 더한 것보다 커야 한다.

### terminationGracePeriodSeconds는 어떻게 정하나요?

preStop 시간 + 스프링 `timeout-per-shutdown-phase` + 여유로 정한다. 유예 타이머는 preStop이 시작될 때부터 흐르기 때문에, preStop을 추가하면서 유예 시간을 그대로 두면 긴 요청이 SIGKILL로 끊긴다. SIGKILL은 스프링 로그에 아무것도 남기지 않아서, 종료 코드 137과 `Graceful shutdown complete` 줄이 없는 것으로 알아챈다.

### 컨테이너 안의 JVM은 CPU 수를 어떻게 정하고, 어디서 문제가 생기나요?

cgroup의 CPU quota(limits)를 읽어 코어 수를 정하고, 그 수로 GC 종류와 GC·JIT 스레드, ForkJoin 공용 풀 크기를 고른다. 1코어 이하면 Serial GC로 떨어진다. JDK 19부터는 requests에 해당하는 `cpu.shares`를 무시해서, limits가 없으면 노드 코어 수를 다 본다. 둘 다 원하지 않으면 `-XX:ActiveProcessorCount`로 정한다.

### CPU limits를 낮게 주면 JVM 시작이 왜 그렇게 느려지나요?

CPU 한도는 100ms 주기마다 쓸 수 있는 CPU 시간으로 걸리는데, 시작하는 JVM은 클래스 로딩, JIT, GC를 여러 스레드로 동시에 돌려 몫을 금방 다 쓰고 남은 주기 동안 멈춘다. 0.5코어에서 시작을 재 보니 주기 108개 중 103개에서 멈췄고 멈춘 시간이 6.3초였다. startupProbe로 기다려 주고, CDS로 시작 작업을 줄이고, limits를 너무 낮게 잡지 않는다. 이 시작 CPU가 HPA의 CPU 평균을 끌어올려 불필요한 확장을 부르기도 한다.
