결제가 실패했는데 상품 재고가 줄어 있다는 신고가 들어온다. 재고 화면에는 "예약됨"으로 잡힌 수량이 계속 쌓이고, 실제로 남은 물건은 있는데 품절로 보인다. 코드를 따라가 보니 주문을 만드는 곳이 세 군데였다. 웹 결제 화면의 컨트롤러, 상담원이 대신 주문하는 관리자 API, 정기 배송을 돌리는 배치 작업이다. 셋 다 재고 예약, 결제 승인, 주문 저장, 알림을 차례로 부른다. 그중 관리자 API만 결제가 실패했을 때 재고 예약을 풀지 않았다.

세 곳이 같은 순서를 각자 알고 있으니, 순서나 예외 처리가 바뀔 때마다 세 곳을 다 고쳐야 한다. 이번 글은 이 순서를 한곳에 모으고 쉬운 입구 하나만 내미는 퍼사드(Facade) 패턴이다. 디자인 패턴 전체 지도는 [디자인 패턴 개요](/posts/design-patterns-overview)에 있다.

## 세 군데에 복사된 주문 절차

문제의 관리자 API는 이렇게 생겼다.

```ts
// admin/orders.controller.ts
export async function createOrderForCustomer(req: AdminOrderRequest) {
  const reservationId = await inventory.reserve(req.items);
  const amount = req.items.reduce((s, i) => s + i.price * i.qty, 0);
  const paymentId = await payments.authorize(req.userId, amount); // 여기서 던지면 예약이 남는다
  const orderId = await orders.create(req.userId, req.items, paymentId);
  await notifier.orderPlaced(req.userId, orderId);
  return { orderId };
}
```

웹 컨트롤러에는 `try/catch`와 `inventory.release`가 있었지만, 누군가 관리자 API를 만들 때 웹 코드를 보고 "핵심만" 옮기면서 빠졌다. 배치 작업은 또 다른 문제를 안고 있었다. 알림이 실패하면 예외가 위로 올라가서 이미 결제된 주문이 실패로 기록됐다.

컨트롤러 세 개가 재고, 결제, 주문, 알림이라는 네 하위 시스템을 모두 직접 안다. 하위 시스템마다 메서드가 여럿이고, 어떤 순서로 부르고 실패하면 무엇을 되돌려야 하는지는 문서 어디에도 없이 각 컨트롤러의 코드에만 있다.

## 하위 시스템 앞에 입구 하나

퍼사드는 프랑스어로 건물의 정면이라는 뜻이다. 건물 안에 방이 몇 개든 손님은 정문 하나로 들어온다. 패턴에서도 하위 시스템이 여럿인 곳 앞에 단순한 인터페이스를 가진 객체 하나를 세운다. 컨트롤러는 그 객체의 `placeOrder` 하나만 부르고, 어떤 하위 시스템을 어떤 순서로 부르는지는 퍼사드가 안다.

하위 시스템은 퍼사드가 있다는 사실을 모른다. 화살표는 위에서 아래로만 간다. 퍼사드를 지운다고 재고 모듈이 깨지지는 않는다. 그리고 퍼사드는 하위 시스템을 숨기는 벽이 아니다. 재고 화면처럼 재고 모듈만 깊게 써야 하는 곳은 여전히 직접 부를 수 있다. 퍼사드는 흔한 경우를 쉽게 만드는 입구이지, 유일한 입구가 아니다.

```ts
type Item = { sku: string; qty: number; price: number };

interface Inventory {
  reserve(items: Item[]): Promise<string>;
  release(reservationId: string): Promise<void>;
}
interface Payments {
  authorize(userId: string, amount: number): Promise<string>;
  cancel(paymentId: string): Promise<void>;
}
interface Orders {
  create(userId: string, items: Item[], paymentId: string): Promise<string>;
}
interface Notifier {
  orderPlaced(userId: string, orderId: string): Promise<void>;
}

export type PlaceOrderResult = { ok: true; orderId: string } | { ok: false; reason: string };

export class CheckoutFacade {
  constructor(
    private readonly deps: { inventory: Inventory; payments: Payments; orders: Orders; notifier: Notifier },
  ) {}

  async placeOrder(userId: string, items: Item[]): Promise<PlaceOrderResult> {
    const { inventory, payments, orders, notifier } = this.deps;
    const undo: Array<() => Promise<void>> = []; // 성공한 단계를 되돌리는 법을 쌓는다

    try {
      const reservationId = await inventory.reserve(items);
      undo.push(() => inventory.release(reservationId));

      const amount = items.reduce((s, i) => s + i.price * i.qty, 0);
      const paymentId = await payments.authorize(userId, amount);
      undo.push(() => payments.cancel(paymentId));

      const orderId = await orders.create(userId, items, paymentId);

      // 알림 실패는 주문을 되돌릴 이유가 아니다
      notifier.orderPlaced(userId, orderId).catch((e: unknown) => console.warn("notify failed", e));
      return { ok: true, orderId };
    } catch (error) {
      for (const step of undo.reverse()) await step(); // 나중에 한 것부터 되돌린다
      return { ok: false, reason: (error as Error).message };
    }
  }
}
```

세 컨트롤러는 이제 한 줄이다. `await checkout.placeOrder(req.userId, req.items)`. 처음의 버그 둘, 결제 실패 시 예약을 풀지 않은 것과 알림 실패를 주문 실패로 기록한 것이 모두 퍼사드 한 곳에서 정리됐다. 다음에 "쿠폰을 먼저 차감한다"는 단계가 생겨도 고칠 곳은 하나다.

## 퍼사드는 어디에나 있다

Node.js의 `fs.promises.readFile`은 파일을 열고, 크기만큼 버퍼를 읽고, 닫는 일을 한 번에 해 준다. 큰 파일을 조금씩 읽어야 하면 `open`과 `read`를 직접 쓰면 된다. 브라우저의 `fetch`도 DNS 조회, TCP 연결, TLS 핸드셰이크, HTTP 메시지 조립을 `fetch(url)` 한 줄 뒤에 둔다. 예전 jQuery의 `$.ajax`는 브라우저마다 다르던 `XMLHttpRequest` 사용법 앞에 선 퍼사드였다.

AWS SDK v3의 `@aws-sdk/lib-storage`에 있는 `Upload`도 그렇다. 큰 파일을 S3에 올리려면 멀티파트 업로드를 시작하고, 조각마다 올리고, 완료를 알리고, 실패하면 중단 요청을 보내야 한다. `new Upload({ client, params }).done()` 하나가 그 순서를 대신 밟는다. 멀티파트 단계를 직접 다루고 싶으면 `@aws-sdk/client-s3`의 명령을 따로 쓰면 된다.

`express()`가 돌려주는 `app`이 Node.js `http` 서버와 라우터 앞에 선 퍼사드라는 이야기는 [개요 글](/posts/design-patterns-overview#이미-매일-쓰고-있는-패턴)에서 했다.

## 서비스 앞에 선 퍼사드

서비스가 여러 개로 나뉘면 같은 고민이 네트워크 너머에서 생긴다. 모바일 앱의 홈 화면 하나를 그리려고 사용자, 주문, 추천 서비스를 각각 부르면, 앱이 세 서비스의 주소와 응답 형식과 실패 처리를 모두 알아야 한다. 화면용 서버(BFF, Backend for Frontend)를 앞에 두면 앱은 `GET /home` 하나만 부른다. 아키텍처 크기의 퍼사드다.

## 퍼사드가 신이 되는 과정

퍼사드는 편해서 커지기 쉽다. 처음에는 `placeOrder` 하나였는데, 환불이 생기면 `refund`, 교환이 생기면 `exchange`, 관리자가 쓰는 `forceCancel`, 통계용 `getDailySales`가 붙는다. 1년 뒤 `CheckoutFacade`에는 메서드 서른 개와 의존성 열두 개가 있고, 모든 기능 브랜치가 이 파일에서 충돌한다. 모든 걸 아는 신 객체(god object)가 된 것이다.

신호는 숫자로 보인다. 생성자에 넘기는 의존성이 계속 늘고, 메서드마다 쓰는 의존성이 서로 겹치지 않는다면 한 퍼사드가 여러 일을 하고 있다. 나누는 기준은 유스케이스다. `PlaceOrder`, `RefundOrder`처럼 사용자가 하려는 일 하나에 퍼사드 하나를 두면, 각각은 작고 고칠 이유도 하나다. 클린 아키텍처에서 말하는 유스케이스(인터랙터) 클래스가 사실 이 모양이다.

반대 방향의 실수도 있다. 퍼사드가 하위 시스템 메서드를 이름만 바꿔 그대로 노출한다면(`checkout.reserveInventory()`가 `inventory.reserve()`를 부르기만 한다면) 층만 하나 늘었을 뿐 숨긴 것이 없다. 퍼사드는 여러 호출을 묶어 의미 있는 단위로 만들 때 값을 한다.

규칙으로 강제하고 싶다면 린트를 쓴다. 컨트롤러 폴더에서 하위 시스템 모듈을 직접 import하지 못하게 ESLint의 `no-restricted-imports`를 걸어 두면, 다음에 네 번째 주문 경로를 만드는 사람도 퍼사드를 지나간다.

```js
// eslint.config.js (flat config)
export default [
  {
    files: ["src/controllers/**/*.ts"],
    rules: {
      "no-restricted-imports": ["error", {
        patterns: [{ group: ["**/inventory/*", "**/payments/*"], message: "주문은 CheckoutFacade로 만든다" }],
      }],
    },
  },
];
```

## 테스트는 두 층으로 나뉜다

퍼사드가 생기면 테스트도 깔끔하게 나뉜다. 퍼사드 테스트는 하위 시스템에 가짜를 넣고 순서와 보상을 검사한다. 앞의 "결제 실패" 출력이 그 테스트다. 결제가 실패하면 `release`가 불렸는지, 주문 저장이 실패하면 `cancel`이 `release`보다 먼저 불렸는지를 본다. 컨트롤러 테스트는 퍼사드 하나만 가짜로 바꾸면 된다. 하위 시스템 넷을 모두 흉내 낼 필요가 없다.

처음 코드였다면 세 컨트롤러 각각에 하위 시스템 네 개의 가짜를 준비해야 했고, 실제로 보상 로직 테스트는 웹 컨트롤러에만 있었다. 관리자 API의 버그가 테스트를 빠져나간 이유다.

## 어댑터, 중재자와 나란히 놓으면

감싸는 패턴끼리의 비교는 [어댑터 글](/posts/pattern-adapter#비슷한-구조-패턴과-헷갈릴-때)에 표로 정리했다. 퍼사드만 놓고 보면, 어댑터는 객체 하나를 이미 정해진 인터페이스에 맞추고 퍼사드는 여러 객체를 묶어 새 인터페이스를 만든다. 어댑터는 클라이언트가 원하는 모양이 먼저 있고, 퍼사드는 하위 시스템이 먼저 있다.

[중재자](/posts/pattern-mediator)와도 그림이 닮았다. 가운데 객체 하나가 여러 객체와 연결된다. 다른 점은 방향이다. 퍼사드의 하위 시스템은 퍼사드를 모르고, 요청은 바깥에서 안으로 한 방향으로 흐른다. 중재자의 동료 객체들은 중재자를 알고 서로의 일을 중재자를 거쳐 주고받는다. 퍼사드는 바깥을 위한 입구이고, 중재자는 안쪽끼리의 교통정리다.

## 직접 만들어 보는 주문 퍼사드

`placeOrder(sys)`를 완성해 보자. `sys`에는 `reserve()`, `release(id)`, `authorize()`, `cancel(id)`, `create()`가 있다. 성공하면 주문 id를 돌려주고, 어느 단계든 실패하면 그때까지 성공한 단계를 나중 것부터 되돌린 뒤 에러를 다시 던진다. `scenario`는 실패할 단계를 골라 어떤 호출이 일어났는지 기록한다.

퍼사드는 "흔한 일을 한 번의 호출로 만든다"가 전부인 패턴이다. 그 대가로 순서, 금액 계산, 실패했을 때 되돌리는 법 같은 지식이 한곳에 모인다. 처음의 버그는 그 지식이 세 곳에 복사되어 있어서 생겼다. 퍼사드를 둘 때는 하위 시스템을 잠그지 말고, 유스케이스 하나에 퍼사드 하나로 작게 유지하면 된다.

## 면접에서 나올 만한 질문

### 퍼사드 패턴은 어떤 문제를 푸나요?

여러 하위 시스템을 정해진 순서로 불러야 하는 일을 단순한 인터페이스 하나로 묶는다. 클라이언트는 퍼사드 메서드 하나만 알면 되고, 하위 시스템과의 결합이 퍼사드 한곳으로 모인다. 순서나 실패 처리가 바뀔 때 고칠 곳이 하나가 된다는 것이 실무에서 가장 큰 이점이다.

### 퍼사드가 있으면 하위 시스템을 직접 쓰면 안 되나요?

써도 된다. 퍼사드는 흔한 경우를 쉽게 만드는 입구이지 하위 시스템을 숨기는 벽이 아니다. git commit 뒤에 배관 명령이 그대로 열려 있는 것처럼, 세밀한 제어가 필요한 곳은 직접 쓴다. 팀 규칙으로 특정 계층에서만 막고 싶다면 ESLint의 no-restricted-imports 같은 도구로 강제한다.

### 퍼사드와 어댑터는 무엇이 다른가요?

어댑터는 객체 하나를 클라이언트가 이미 정해 둔 인터페이스에 맞추고, 퍼사드는 여러 객체를 묶어 쓰기 쉬운 새 인터페이스를 만든다. 어댑터는 원하는 모양이 먼저 있고 거기에 끼우는 것이고, 퍼사드는 복잡한 하위 시스템이 먼저 있고 그 앞에 입구를 세우는 것이다.

### 퍼사드와 중재자는 어떻게 구분하나요?

둘 다 가운데 객체가 여럿과 연결되지만 방향이 다르다. 퍼사드의 하위 시스템은 퍼사드를 모르고 요청이 바깥에서 안으로만 흐른다. 중재자는 동료 객체들이 중재자를 알고 서로의 상호작용을 중재자를 거쳐 주고받는다. 퍼사드는 외부 클라이언트를 위한 단순화, 중재자는 내부 객체 간 결합 제거가 목적이다.

### 퍼사드를 쓸 때 조심할 점은 무엇인가요?

편해서 기능이 계속 쌓이면 의존성 수십 개를 쥔 신 객체가 된다. 생성자 의존성이 늘고 메서드마다 쓰는 의존성이 겹치지 않으면 유스케이스별로 퍼사드를 나눈다. 반대로 하위 시스템 메서드를 이름만 바꿔 넘기기만 하는 퍼사드는 층만 늘린 것이라 가치가 없다.

### 퍼사드 안에서 여러 단계 중 하나가 실패하면 어떻게 처리하나요?

성공한 단계마다 되돌리는 동작을 쌓아 두고, 실패하면 나중에 한 것부터 실행한다. 다만 이 목록은 메모리에 있어서 중간에 프로세스가 죽으면 사라진다. 같은 DB 안이면 트랜잭션으로 묶고, 서비스가 나뉘어 있으면 단계를 기록해 두고 재시작 후에도 보상하는 사가 패턴으로 간다.

### 아키텍처 수준의 퍼사드 예를 들어 주세요.

BFF가 대표적이다. 모바일 홈 화면처럼 여러 서비스의 데이터가 필요한 화면을 위해 서버 하나가 호출을 모으고 필요한 필드만 골라 한 번에 돌려준다. 어떤 호출이 필수이고 어떤 호출은 늦으면 비워도 되는지도 BFF가 정한다. 클라이언트는 서비스 구성을 몰라도 되고, 왕복 횟수도 준다.
