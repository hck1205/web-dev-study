## 도메인을 옮겼더니 다음 주 유입이 반으로 줄었다

개인 블로그를 `old.example`에서 `new.example`로 옮겼다. 글 주소도 `/blog/글-이름`에서 `/posts/글-이름`으로 바꿨다. 새 도메인에 배포하고, 예전 도메인은 "전부 새 도메인 홈으로" 보내는 규칙 한 줄로 정리했다. 일주일 뒤 분석 도구를 보니 검색 유입이 절반 아래로 떨어져 있었다.

원인은 세 가지가 겹친 것이었다. 예전 글 주소가 새 글 주소가 아니라 홈으로 갔고, 글 몇 개는 리다이렉트가 두 번, 세 번 이어졌고, 새 도메인 쪽 배포 직후 하루 동안 5xx가 섞여 나갔다. 검색 엔진 입장에서 보면 "예전 글들이 사라지고 홈 하나만 남았다"와 "새 사이트가 불안정하다"는 신호가 동시에 들어온 셈이다.

이 글은 그 장면을 거꾸로 따라간다. 3xx 코드마다 검색 엔진이 받는 신호가 어떻게 다른지, 리다이렉트 체인과 루프를 `curl`로 찾는 법, 구 주소와 새 주소를 짝지은 매핑 표를 만들고 검증하는 법, 도메인과 프로토콜을 바꿀 때 Search Console에서 할 일, 점검 중에 내보낼 503과 영구 삭제에 쓸 410, 이전한 뒤 무엇을 지켜보는지까지 본다. title, canonical, robots, sitemap 같은 기본 태그는 [SPA와 SEO](/posts/seo-for-spa)에서 다뤘고, 3xx 각각의 HTTP 의미(메서드 유지, 캐시, 303과 PRG)는 [HTTP 상태 코드](/posts/http-status-codes)에 있다. 여기서는 검색 엔진이 그 코드를 어떻게 읽는지에 집중한다.

## 3xx가 검색 엔진에 주는 신호

검색 엔진은 리다이렉트를 받으면 두 가지를 정한다. 지금 이 주소를 따라가서 내용을 가져올지, 그리고 색인에 올릴 대표 주소(canonical)를 원래 주소로 둘지 목적지로 바꿀지다. 앞의 것은 거의 모든 3xx에서 같고, 차이는 뒤의 것에서 난다.

구글 검색 센터 문서 기준으로 정리하면 이렇다.

| 방법 | 검색 엔진이 보는 뜻 | 대표 주소 |
|---|---|---|
| 301, 308 | 영구 이동 | 목적지로 옮기는 강한 신호 |
| 302, 307 | 임시 이동 | 원래 주소를 유지하는 쪽. 목적지는 약한 신호 |
| meta refresh 0초 | 영구 이동으로 해석 | 목적지 쪽 |
| meta refresh 지연 | 임시 이동으로 해석 | 원래 주소 쪽 |
| 자바스크립트 이동 | 렌더링한 뒤에야 보인다 | 렌더링에 성공하면 따라간다 |

301과 308의 차이는 HTTP 쪽 이야기다. 308은 메서드와 본문을 그대로 유지하고, 301은 클라이언트가 `POST`를 `GET`으로 바꿔도 된다. 검색 엔진은 페이지를 `GET`으로만 가져가니 둘을 같게 본다. 그래서 페이지 이전에는 둘 중 아무거나 써도 되고, API 경로를 옮길 때는 308을 고른다.

302를 오래 걸어 두면 어떻게 될까. 구글 쪽 담당자들은 임시 리다이렉트가 오래 유지되면 결국 영구로 취급할 수 있다고 여러 번 말했다. 하지만 그건 검색 엔진이 사람의 실수를 대신 바로잡아 주는 것이지 우리가 기대할 동작이 아니다. 영구 이동이면 처음부터 301이나 308을 낸다. 반대로 정말 임시인 경우(로그인 페이지로 잠깐 보내기, A/B 테스트로 일부만 다른 페이지 보여 주기, 품절 상품을 잠시 대체 상품으로 보내기)는 302나 307이 맞다. 여기에 301을 쓰면 원래 주소가 색인에서 빠진다.

meta refresh와 자바스크립트 이동은 서버에서 3xx를 낼 수 없을 때 쓰는 차선책이다. 정적 호스팅이라 응답 코드를 못 바꾸는 경우가 그렇다. 자바스크립트 이동은 렌더링 큐를 거쳐야 보이니 반영이 늦고, 렌더링하지 않는 다른 검색 엔진과 링크 미리보기 봇은 따라가지 않는다. 가능하면 서버의 3xx로 바꾼다.

예전에는 "301을 쓰면 페이지 신호(PageRank)가 15% 정도 샌다"는 말이 돌았다. 구글은 2016년에 3xx 리다이렉트로 PageRank가 줄지 않는다고 밝혔다. 신호가 새는 진짜 원인은 대개 리다이렉트 자체가 아니라 엉뚱한 목적지다. 다음 절이 그 이야기다.

## 모든 구 주소를 홈으로 보내면 생기는 일

처음 장면의 "전부 홈으로" 규칙은 가장 흔한 실수다. 예전 글 `/blog/redirect-guide`를 찾던 사람은 홈에 떨어지고, 검색 엔진은 "이 글의 새 주소가 홈이라고? 내용이 전혀 다른데"라고 판단한다. 구글은 이런 경우를 소프트 404로 보고, 예전 주소가 가지고 있던 링크와 순위를 홈으로 넘기지 않는다. 결국 글마다 쌓아 둔 신호가 그냥 사라진다.

리다이렉트의 목적지는 "같은 내용이 지금 있는 곳"이어야 한다. 정말 대응하는 페이지가 없으면(글을 지웠다) 홈이 아니라 404나 410을 준다. 비슷한 글이 있으면 그 글로 보내도 되지만, 내용이 많이 다르면 검색 엔진은 역시 소프트 404로 볼 수 있다.

그래서 이전 작업의 대부분은 매핑 표를 만드는 일이다.

## 구 주소와 새 주소를 짝짓는 매핑 표

매핑 표는 구 주소 하나에 새 주소 하나를 적은 CSV다. 출처는 세 군데를 합친다.

- 예전 사이트의 sitemap과 CMS의 글 목록: 우리가 알고 있는 주소
- 서버 접근 로그와 분석 도구의 랜딩 페이지 목록: 실제로 사람이 들어오는 주소. 오래전에 바뀐 옛 주소나 파라미터가 붙은 주소가 여기서 나온다
- Search Console의 실적 보고서와 외부 링크 보고서: 검색 노출이 있는 주소와 다른 사이트가 링크하는 주소

이 셋의 합집합에서 중복을 지우고, 주소마다 목적지를 적는다. 대부분은 규칙으로 만들 수 있다(`/blog/(.*)` → `/posts/$1`). 규칙에 안 맞는 것만 손으로 채운다. 목적지가 없는 주소는 "410"이라고 적어 두고 일부러 지운 것임을 표에 남긴다.

```text
old,new
http://old.example/blog/redirect-guide,http://new.example/posts/redirect-guide
http://old.example/about,http://new.example/about
http://old.example/a,http://new.example/posts/a
```

표를 만들었으면 서버 설정으로 옮기기 전에 표 자체를 검사한다. 구 주소가 다른 구 주소를 가리키면 체인이 생기고, 서로 가리키면 루프가 생긴다. 이미 리다이렉트 규칙이 있던 사이트를 한 번 더 옮길 때 특히 잘 생긴다. 2년 전 이전에서 만든 `/blog/a` → `/blog/a/` 규칙이 남아 있는 상태에서 이번에 `/blog/a/` → `/posts/a`를 더하면, `/blog/a`는 두 번 건너야 도착한다.

체인이 왜 문제인지 숫자로 보면 분명하다. 구글봇은 리다이렉트를 최대 10번까지 따라가고, 그 안에 내용이 안 나오면 Search Console에 리다이렉트 오류로 표시한다. 10번은 넉넉해 보이지만, 사람에게는 한 번마다 왕복이 하나씩 더해진다. HTTP→HTTPS, 맨 도메인→www, 옛 경로→새 경로가 각각 따로 걸리면 세 번이다. 검색 엔진도 체인의 중간 주소를 각각 크롤링 대상으로 다루니, 큰 사이트에서는 크롤 예산이 그만큼 샌다. 크롤 예산이 어떻게 정해지는지는 [크롤 예산과 패싯 내비게이션](/posts/crawl-budget-faceted-navigation)에서 이어서 본다.

## curl로 실제 응답을 따라가 보기

표가 맞아도 서버 설정이 표대로 동작한다는 보장은 없다. 프레임워크 규칙, 웹 서버 규칙, CDN 규칙이 겹쳐서 예상과 다른 순서로 걸리기 때문이다. 그래서 실제 응답을 `curl`로 따라간다. 아래 출력은 스크래치 폴더에 위 매핑을 흉내 낸 Node 서버를 띄우고 받은 것이다. `--connect-to ::127.0.0.1:4316`은 어떤 호스트로 요청하든 로컬 서버에 연결하라는 옵션이라, 실제 서버에서 돌릴 때는 빼면 된다.

```bash
# -s 진행 표시 끄기, -I 헤더만(HEAD), -L 리다이렉트 따라가기
curl -sIL --connect-to ::127.0.0.1:4316 http://old.example/blog/redirect-guide \
  | grep -iE '^HTTP|^location'
```

```text
HTTP/1.1 301 Moved Permanently
Location: /blog/redirect-guide/
HTTP/1.1 301 Moved Permanently
Location: http://new.example/posts/redirect-guide
HTTP/1.1 200 OK
```

`HTTP/` 줄이 세 개면 요청이 세 번 갔다는 뜻이다. 첫 번째 301은 끝에 `/`를 붙이는 규칙이고, 두 번째가 진짜 이전 규칙이다. 끝 슬래시 규칙이 이전 규칙보다 먼저 걸려서 체인이 생겼다. 첫 301이 바로 `http://new.example/posts/redirect-guide`를 가리켜야 한다.

`-I`는 `HEAD` 요청을 보낸다. 일부 서버나 프레임워크는 `HEAD`와 `GET`에 다르게 답하니, 결과가 이상하면 `-I` 대신 `-s -o /dev/null -D -`로 `GET`의 헤더를 본다.

홉 수와 최종 주소만 한 줄로 보고 싶으면 `-w`를 쓴다.

```bash
# 최종 응답 코드, 따라간 횟수, 최종 주소
curl -sL --connect-to ::127.0.0.1:4316 -o /dev/null \
  -w "%{http_code} redirects=%{num_redirects} final=%{url_effective}\n" \
  http://old.example/blog/redirect-guide
```

```text
200 redirects=2 final=http://new.example/posts/redirect-guide
```

루프는 이렇게 보인다.

```bash
curl -sSL --max-redirs 10 --connect-to ::127.0.0.1:4316 -o /dev/null http://old.example/a
```

```text
curl: (47) Maximum (10) redirects followed
```

종료 코드 47이 리다이렉트 상한에 걸렸다는 뜻이다. 헤더를 찍어 보면 `/a`와 `/b`가 번갈아 나온다. 실무에서 루프가 생기는 흔한 구성은 CDN이 HTTPS를 받아 오리진에 HTTP로 넘기고, 오리진이 HTTP 요청을 보고 다시 HTTPS로 보내는 경우다. 오리진이 `X-Forwarded-Proto`를 보고 원래 스킴을 판단하게 하면 풀린다.

매핑 표 전체를 한 번에 검사하는 스크립트도 짧다. 구 주소마다 첫 응답이 영구 리다이렉트인지, 홉이 하나인지, 목적지가 표와 같은지, 최종 응답이 200인지를 본다.

```bash
#!/usr/bin/env bash
# 매핑 표의 구 주소마다 첫 응답 코드, 홉 수, 최종 주소를 확인한다
tail -n +2 redirects.csv | while IFS=, read -r old new; do
  first=$(curl -s -o /dev/null -w "%{http_code}" --connect-to ::127.0.0.1:4316 "$old")
  read -r code hops final < <(curl -sL --max-redirs 5 -o /dev/null \
    -w "%{http_code} %{num_redirects} %{url_effective}" --connect-to ::127.0.0.1:4316 "$old")
  status=OK
  [ "$first" != "301" ] && [ "$first" != "308" ] && status="NOT-PERMANENT"
  [ "$hops" -gt 1 ] && status="CHAIN($hops)"
  [ "$final" != "$new" ] && status="WRONG-TARGET"
  [ "$code" != "200" ] && status="FINAL-$code"
  echo "$status  $old -> $final"
done
```

```text
CHAIN(2)  http://old.example/blog/redirect-guide -> http://new.example/posts/redirect-guide
FINAL-404  http://old.example/about -> http://new.example/about
FINAL-301  http://old.example/a -> http://old.example/b
```

세 줄이 세 가지 실패를 보여 준다. 첫 줄은 도착은 하지만 체인이다. 둘째 줄은 리다이렉트는 맞게 걸렸는데 새 사이트에 `/about` 페이지를 안 만들었다. 셋째 줄은 루프라서 다섯 번 따라가다 멈췄고, 마지막으로 받은 응답이 여전히 301이다. 뒤에 나온 조건이 앞의 결과를 덮어쓰도록 순서를 잡아서, 가장 심각한 문제가 남는다. 이 스크립트를 이전 전 스테이징에서 한 번, 전환 직후 프로덕션에서 한 번 돌린다. 수만 줄이면 `xargs -P`로 병렬로 돌리되 서버에 무리가 가지 않게 동시 요청 수를 제한한다.

## 서버에 리다이렉트를 거는 자리

리다이렉트는 요청이 가장 먼저 닿는 곳에 거는 편이 빠르고 체인도 덜 생긴다. CDN이나 웹 서버에서 처리하면 앱까지 가지 않는다.

Nginx에서는 도메인 전체를 옮길 때 경로를 그대로 붙여 보낸다.

```nginx
# 예전 도메인으로 온 요청은 경로를 유지한 채 새 도메인으로
server {
    listen 80;
    listen 443 ssl;
    server_name old.example www.old.example;
    # ssl_certificate ... (예전 도메인 인증서는 이전 뒤에도 유지한다)

    location /blog/ {
        rewrite ^/blog/(.*)$ https://new.example/posts/$1 permanent;
    }
    location / {
        return 301 https://new.example$request_uri;
    }
}
```

예전 도메인의 TLS 인증서를 이전 뒤에도 갱신해야 한다는 걸 자주 잊는다. 인증서가 만료되면 브라우저는 리다이렉트 응답을 받기도 전에 경고 화면에서 멈춘다. 손으로 고른 매핑이 수천 개면 `map` 블록에 표를 그대로 넣는다. Nginx 설정 문법은 [Nginx 기초](/posts/nginx-basics)에 있다.

```nginx
map $uri $new_uri {
    default "";
    include /etc/nginx/redirects.map;   # "/old/path  /new/path;" 한 줄씩
}
server {
    # ...
    if ($new_uri) { return 301 $new_uri; }
}
```

Next.js에서는 `next.config.ts`의 `redirects()`가 이 역할을 한다. `permanent: true`는 308을, `false`는 307을 낸다. 301이 꼭 필요하면 `statusCode: 301`을 준다.

```ts
// next.config.ts
import type { NextConfig } from "next";

const config: NextConfig = {
  async redirects() {
    return [
      { source: "/blog/:slug", destination: "/posts/:slug", permanent: true },
      {
        source: "/:path*",
        has: [{ type: "host", value: "old.example" }],
        destination: "https://new.example/:path*",
        permanent: true,
      },
    ];
  },
};

export default config;
```

서버 컴포넌트 안에서 쓰는 `redirect()`는 기본 307이고, 영구 이동이면 `permanentRedirect()`(308)를 쓴다. 미들웨어의 `NextResponse.redirect(url)`도 상태를 주지 않으면 307이다. 이전 규칙을 미들웨어에 넣고 상태 코드를 안 정하면 모든 이전이 임시 리다이렉트가 된다. 이전 직후 `curl -sI`로 코드가 308(또는 301)인지 확인하는 이유다.

규칙은 언제까지 유지할까. 구글의 사이트 이전 문서는 최소 1년, 가능한 한 오래 두라고 권한다. 사람이 북마크한 주소, 다른 사이트에 박힌 링크는 몇 년이 지나도 들어온다. 규칙 수천 줄이 남는 게 싫다면, 1년 뒤 로그를 보고 요청이 거의 없는 규칙만 정리한다.

HTTP→HTTPS 이전에서 챙길 것은 이렇다. 모든 HTTP 주소를 같은 경로의 HTTPS로 301을 보내고, canonical과 sitemap과 내부 링크를 HTTPS로 바꾸고, 페이지 안의 이미지와 스크립트를 HTTPS로 불러 혼합 콘텐츠 경고를 없앤다. 그다음 HSTS를 켜면 브라우저가 첫 HTTP 요청부터 건너뛰어 체인의 한 단계가 사라진다. HSTS는 한 번 켜면 되돌리기 어렵다. `max-age`를 짧게 시작해서 늘리고, `preload`는 모든 서브도메인이 HTTPS로 준비된 뒤에 넣는다. 자세한 건 [HTTPS와 TLS](/posts/https-tls)에 있다.

도메인 변경과 경로 구조 변경, 디자인 개편을 한 번에 하면 문제가 생겼을 때 원인을 가르기 어렵다. 구글도 가능하면 단계를 나누라고 권한다. 처음 장면은 도메인과 경로를 동시에 바꿨고, 그래서 유입이 줄었을 때 무엇 때문인지 찾는 데 오래 걸렸다.

## 점검 중에는 503과 Retry-After

이전 작업을 하다 보면 몇 시간 사이트를 내려야 할 때가 있다. 이때 점검 안내 페이지를 200으로 내보내면 검색 엔진은 모든 페이지가 "점검 중"이라는 같은 내용으로 바뀌었다고 본다. 운이 나쁘면 그 화면이 검색 결과 설명으로 뜨고, 모든 페이지가 중복으로 묶인다.

점검 페이지는 503으로 낸다. "지금은 처리할 수 없지만 곧 돌아온다"는 뜻이라, 검색 엔진은 이미 색인한 내용을 그대로 두고 나중에 다시 온다.

```bash
curl -sI --connect-to ::127.0.0.1:4316 http://new.example/maintenance
```

```text
HTTP/1.1 503 Service Unavailable
Retry-After: 3600
Content-Type: text/html
Date: Sat, 24 Oct 2026 10:31:11 GMT
Connection: keep-alive
Keep-Alive: timeout=5
```

`Retry-After`는 다시 오기까지 기다릴 초(또는 날짜)다. HTTP 표준의 힌트라서 크롤러가 이 값을 그대로 지킨다는 보장은 없지만, 다른 클라이언트에게도 의도를 분명히 전한다.

503은 짧게 쓸 때만 안전하다. 구글 문서는 5xx와 429를 받으면 구글봇이 크롤링 속도를 줄이고, 이미 색인된 주소는 한동안 유지하지만 서버 오류가 계속되는 주소는 결국 색인에서 뺀다고 설명한다. 며칠씩 503을 내면 점검이 끝나도 페이지가 이미 빠져 있을 수 있다. `robots.txt`도 조심한다. `robots.txt`가 5xx를 주면 구글은 사이트 전체를 크롤링 금지로 보고 멈추고, 그 상태가 길어지면 마지막으로 받아 둔 사본을 쓴다. 점검 때문에 `robots.txt`를 `Disallow: /`로 바꾸는 건 더 나쁘다. 크롤링을 막을 뿐 아니라 되돌리는 걸 잊기 쉽다.

5xx가 꼭 점검에서만 나오는 건 아니다. 이전 직후에는 구글봇이 예전 사이트와 새 사이트를 평소보다 많이 가져가니 새 서버가 그 부하를 견뎌야 한다. 처음 장면의 하루짜리 5xx는 배포 직후 캐시가 비어 있는 상태에서 크롤링이 몰린 탓이었다. 구글봇이 자주 받은 5xx를 보고 크롤 속도를 줄이면, 이전 반영도 그만큼 늦어진다. 502와 504처럼 앱이 아니라 앞단 프록시가 만드는 오류를 가르는 법은 [HTTP 상태 코드](/posts/http-status-codes)의 access.log 절에 있다.

## 지운 페이지는 404인가 410인가

없앤 페이지에는 404나 410을 준다. 404는 "지금 여기 없다", 410은 "일부러 지웠고 돌아오지 않는다"라는 뜻이다.

```bash
curl -sI --connect-to ::127.0.0.1:4316 http://new.example/discontinued | head -1
```

```text
HTTP/1.1 410 Gone
```

구글 문서는 429를 뺀 모든 4xx를 같게 다룬다고 적고 있다. 내용이 없다는 신호를 색인에 보내고, 이미 색인된 주소는 빠진다. 그래서 404와 410 사이의 검색 결과 차이는 작다. 경험적으로 410이 조금 더 빨리 빠진다는 말이 있지만 큰 차이를 기대할 일은 아니다. 410을 고르는 진짜 이유는 의도를 기록하는 데 있다. 로그와 모니터링에서 410은 "지운 것", 404는 "깨진 링크일 수 있는 것"으로 갈라 볼 수 있다.

흔한 실수는 둘이다. 지운 페이지를 200과 "찾을 수 없습니다" 화면으로 내보내는 소프트 404, 그리고 지운 페이지를 모두 홈으로 리다이렉트하는 것. 둘 다 검색 엔진에는 소프트 404로 보이고, 사람에게는 원하던 것이 없다는 사실을 숨긴다. 404 페이지에 검색창과 관련 글 링크를 두는 편이 사람에게도 낫다.

## 이전한 뒤 무엇을 지켜보나

이전은 배포하는 날 끝나지 않는다. 처음 몇 주는 매일, 그다음 몇 달은 주마다 아래를 본다.

Search Console에서는 새 속성의 페이지 색인 생성 보고서를 본다. 새 주소의 "색인 생성됨" 수가 오르고, 예전 속성에서는 "리디렉션이 있는 페이지(Page with redirect)"가 늘어야 정상이다. "리디렉션 오류"나 "찾을 수 없음(404)"이 갑자기 늘면 매핑에서 빠진 주소가 있다는 뜻이다. 크롤링 통계 보고서는 응답 코드별 요청 수와 평균 응답 시간을 보여 준다. 5xx 비율이나 응답 시간이 이전 직후 튀면 크롤링이 줄기 전에 서버를 손본다.

서버 로그에서는 예전 도메인으로 들어온 요청 중 301이 아닌 응답을 찾는다. 구글봇인지는 User-Agent만 믿지 말고 IP를 확인한다(방법은 [AI 크롤러 다루기](/posts/ai-crawlers-bot-control)에 있다).

```bash
# 예전 도메인 접근 로그에서 301/308이 아닌 응답을 경로별로 센다 (combined 형식 기준)
awk '$9 != 301 && $9 != 308 { print $9, $7 }' /var/log/nginx/old-example.access.log \
  | sort | uniq -c | sort -rn | head -20
```

여섯 줄짜리 예제 로그로 돌린 결과다.

```text
      3 404 /tags/http
      1 200 /feed.xml
```

태그 페이지 `/tags/http`가 매핑에서 빠져 404가 나고 있고, `/feed.xml`은 예전 도메인에서 아직 200으로 직접 응답하고 있다. 피드 구독기는 리다이렉트를 따라가지만 예전 주소를 계속 쓰니, 피드도 매핑 표에 넣어 301로 보낸다.

분석 도구에서는 랜딩 페이지별 검색 유입을 이전 전 같은 기간과 비교한다. 사이트 전체 합계만 보면 일부 섹션의 손실이 다른 섹션의 증가에 가려진다. 순위 추적 도구가 있으면 주요 검색어 몇십 개를 이전 전후로 지켜본다.

몇 주 동안 순위와 유입이 출렁이는 건 흔하다. 다만 한 달이 지나도 회복되지 않고 특정 섹션만 빠져 있다면, 그 섹션의 매핑이나 canonical이 틀렸을 가능성이 크다. 처음 장면은 홈으로 몰린 글 주소를 글 단위 301로 다시 걸고, 체인을 접고, 새 서버의 캐시를 미리 데워 둔 뒤 몇 주에 걸쳐 회복됐다.

## 다시 정리하면

검색 엔진에게 리다이렉트는 "이 내용의 대표 주소가 어디인가"를 알려 주는 신호다. 영구 이동이면 301이나 308, 정말 임시면 302나 307을 쓰고, 목적지는 같은 내용이 있는 주소여야 한다. 구 주소와 새 주소의 매핑 표를 로그와 sitemap과 외부 링크에서 모아 만들고, 체인과 루프를 접은 뒤, 실제 응답을 `curl`로 확인한다. 도메인을 바꾸면 주소 변경 도구를 더하고, 점검은 짧은 503으로, 영구 삭제는 404나 410으로 답한다. 그리고 이전 뒤 몇 주는 색인 보고서와 크롤링 통계와 로그를 지켜본다. 검색 엔진이 페이지 순위를 매기는 원리는 [검색 엔진은 순위를 어떻게 매기나](/posts/search-engine-ranking-pagerank)에서 이어진다.

## 면접에서 나올 만한 질문

### 301과 302는 SEO에서 어떻게 다른가요?

301은 영구 이동이라 검색 엔진이 대표 주소를 목적지로 옮기는 강한 신호로 쓰고, 302는 임시 이동이라 원래 주소를 대표로 유지하는 쪽으로 본다. 둘 다 따라가서 내용은 가져간다. 영구로 옮긴 페이지에 302를 쓰면 예전 주소가 계속 검색 결과에 남고, 임시로 보낸 페이지에 301을 쓰면 원래 주소가 색인에서 빠진다. 308과 307은 메서드를 유지한다는 점만 다르고 검색 엔진은 각각 301, 302와 같게 본다.

### 사이트를 옮길 때 예전 주소를 모두 홈으로 리다이렉트하면 안 되나요?

안 된다. 내용이 다른 페이지로 보내면 구글은 소프트 404로 보고 예전 주소의 링크와 순위를 넘기지 않는다. 사람도 원하던 글 대신 홈에 떨어진다. 구 주소마다 같은 내용의 새 주소를 짝지은 매핑 표를 만들고, 대응하는 페이지가 없으면 404나 410을 준다.

### 리다이렉트 체인은 왜 문제이고 어떻게 찾나요?

한 번 건널 때마다 왕복이 하나씩 늘어 사람에게 느리고, 검색 엔진도 중간 주소마다 크롤링을 써서 큰 사이트에서는 크롤 예산이 샌다. 구글봇은 10번까지만 따라간다. `curl -sIL`로 `HTTP/` 줄 수를 세거나 `-w '%{num_redirects}'`로 홉 수를 보고, 규칙표를 끝까지 따라가 모든 출발점이 최종 목적지를 바로 가리키게 접는다. 이전을 여러 번 한 사이트에서 예전 규칙이 남아 생기는 경우가 많다.

### ERR_TOO_MANY_REDIRECTS가 나면 어디부터 보나요?

`curl -sIL`로 `Location`이 어떻게 오가는지 본다. 가장 흔한 원인은 CDN이나 로드 밸런서가 HTTPS를 끝내고 오리진에 HTTP로 넘기는데, 오리진이 HTTP를 보고 다시 HTTPS로 보내는 구성이다. 오리진이 `X-Forwarded-Proto`로 원래 스킴을 판단하게 하거나 리다이렉트를 한 곳에서만 걸면 풀린다. 끝 슬래시 규칙이 프레임워크와 웹 서버에서 반대로 걸린 경우도 흔하다.

### Search Console의 주소 변경 도구는 언제 쓰나요?

도메인이나 서브도메인처럼 호스트가 바뀔 때 쓴다. 두 속성의 소유를 확인하고 예전 사이트가 301을 내고 있어야 신청되고, 구글은 180일 동안 신호 이전을 앞당긴다. HTTP에서 HTTPS로 옮기거나 같은 도메인 안에서 경로만 바꿀 때는 쓰지 않고 리다이렉트로 충분하다. 도구를 써도 리다이렉트는 1년 이상 유지해야 한다.

### 점검 중에는 어떤 응답을 내야 하나요?

503에 `Retry-After`를 붙여 낸다. 검색 엔진은 일시적인 문제로 보고 색인을 유지한 채 나중에 다시 온다. 점검 페이지를 200으로 내면 모든 페이지가 같은 내용으로 바뀐 것으로 보이고, `robots.txt`로 막는 건 크롤링 자체를 끊는다. 다만 503이 며칠씩 이어지면 구글은 크롤링 속도를 줄이고 결국 그 주소를 색인에서 빼니 짧게 쓴다.

### 404와 410은 검색 결과에서 차이가 있나요?

거의 없다. 구글은 429를 뺀 4xx를 모두 "내용이 없다"는 신호로 같게 다루고, 이미 색인된 주소는 빠진다. 410이 조금 빨리 빠진다는 말은 있지만 기대할 만한 차이는 아니다. 410은 일부러 지웠다는 의도를 남겨서 로그와 모니터링에서 깨진 링크와 구분할 수 있다는 점이 쓸모 있다.

### 이전한 뒤 어떤 지표를 보나요?

Search Console에서 새 속성의 색인된 페이지 수, 예전 속성의 리디렉션 페이지 수, 404와 리디렉션 오류의 증가, 크롤링 통계의 응답 코드별 요청과 응답 시간을 본다. 서버 로그로 예전 도메인에서 301이 아닌 응답을 찾고, 분석 도구로 랜딩 페이지별 검색 유입을 이전 전과 비교한다. 몇 주의 출렁임은 흔하지만 한 섹션만 회복되지 않으면 그 섹션의 매핑과 canonical을 의심한다.
