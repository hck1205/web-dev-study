할 일 목록 API 하나를 네 가지 방식으로 올려 뒀다고 해 보자. 하나는 EC2 인스턴스에 Ubuntu를 깔고 Node.js를 직접 띄웠다. 하나는 Elastic Beanstalk에 zip을 올렸다. 하나는 Lambda 함수로 바꿨다. 마지막 하나는 아예 코드를 버리고 할 일 관리 SaaS를 팀에 사서 썼다.

AWS 계정 안에서 직접 돌려 볼 수 없어서 AWS CLI 명령은 출력 없이 명령만 적는다. 서비스별 세부 동작은 글을 쓰는 시점의 공식 문서를 따랐다.

## 클라우드라고 부르려면

남의 데이터센터에 서버를 두는 건 예전부터 있었다. 코로케이션(서버를 사서 남의 랙에 두기)이나 호스팅 업체의 전용 서버가 그렇다. 클라우드는 무엇이 다른가.

미국 NIST가 2011년에 낸 정의(SP 800-145)가 지금도 가장 많이 인용된다. 다섯 가지 성질이 있어야 클라우드라고 부른다.

- 주문형 셀프서비스: 사람에게 전화하지 않고 API나 콘솔로 바로 자원을 받는다.
- 넓은 네트워크 접근: 네트워크로 어디서든 쓴다.
- 자원 풀링: 여러 고객이 같은 물리 자원을 나눠 쓰고, 고객은 그 자원이 정확히 어느 기계인지 모른다.
- 빠른 탄력성: 필요할 때 늘리고 필요 없으면 줄인다. 고객 눈에는 거의 무한해 보인다.
- 측정되는 서비스: 쓴 만큼 재고, 쓴 만큼 낸다.

온프레미스와 비교하면 차이는 돈의 모양에서 먼저 드러난다. 온프레미스는 서버를 사는 큰돈(자본 지출)을 먼저 쓰고 몇 년에 걸쳐 감가상각한다. 피크에 맞춰 사 두니 평소에는 놀린다. 클라우드는 쓰는 만큼 매달 낸다(운영 지출). 트래픽이 작거나 들쭉날쭉하면 클라우드가 싸고, 크고 일정하면 오래 쓰는 하드웨어가 쌀 수 있다. 클라우드 비용을 줄이는 구체적인 방법은 [클라우드 비용 줄이기](/posts/cloud-cost-optimization)에 있다.

NIST 정의에는 배치 모델도 네 가지 나온다. 누구나 쓰는 퍼블릭 클라우드, 한 조직만 쓰는 프라이빗 클라우드, 비슷한 요구를 가진 몇 조직이 함께 쓰는 커뮤니티 클라우드, 그리고 이들을 섞은 하이브리드 클라우드다. 요즘은 여러 퍼블릭 클라우드를 함께 쓰는 멀티 클라우드라는 말도 흔하다. 사내 데이터센터에 오픈스택이나 쿠버네티스로 셀프서비스 API를 갖춰 놓으면 그것도 프라이빗 클라우드다. 남의 건물에 있느냐가 아니라 앞의 다섯 성질을 갖췄느냐가 기준이다.

돈 말고 더 큰 차이가 있다. 온프레미스는 건물의 출입 통제부터 디스크 폐기까지 전부 내 일이다. 클라우드로 가면 그중 일부를 클라우드 회사가 맡는다. 어디까지 맡느냐가 서비스 모델이다.

### IaaS: 가상 머신과 네트워크를 빌린다

Infrastructure as a Service. EC2, EBS 볼륨, VPC처럼 가상화된 기본 부품을 빌린다. 클라우드 회사는 데이터센터, 서버, 하이퍼바이저까지 맡는다. 그 위의 OS부터는 내 것이다. 커널 패치, 방화벽(ufw, 보안 그룹), 사용자 계정, 로그 회전, 디스크가 차는 것까지.

통제권이 가장 크다. 커널 파라미터를 바꾸고, 원하는 OS 버전을 고르고, 아무 프로그램이나 깔 수 있다. 대신 그 모든 것을 관리하는 일도 내게 온다. 새 EC2를 받고 처음 한 시간에 하는 일만 해도 꽤 길다([새 EC2 Ubuntu 서버의 첫 한 시간](/posts/aws-ec2-ubuntu-server-setup)).

### PaaS: 코드를 올리면 돌려 준다

Platform as a Service. Elastic Beanstalk, Heroku, Google App Engine, Cloud Run, AWS App Runner 같은 것이다. 코드나 컨테이너 이미지를 올리면 플랫폼이 OS와 런타임을 준비하고, 로드 밸런서와 오토스케일링을 붙이고, 로그를 모아 준다.

경계가 깔끔하지 않은 경우도 있다. Elastic Beanstalk는 실제로는 내 계정에 EC2 인스턴스를 띄워서 그 위에 앱을 올린다. 플랫폼 버전(OS와 런타임 묶음)의 패치는 관리형 플랫폼 업데이트를 켜야 정해진 유지 보수 시간에 자동으로 적용된다. 켜지 않으면 콘솔에서 내가 눌러야 한다. 그러니 같은 PaaS라도 "OS는 플랫폼이 관리한다"가 "자동으로 된다"는 뜻은 아니다. 설정 하나로 책임이 내 쪽으로 넘어온다.

컨테이너 오케스트레이션을 빌리는 형태(ECS, EKS, Fargate)를 CaaS(Container as a Service)라고 따로 부르기도 한다. IaaS와 PaaS 사이 어딘가다. EKS에서 컨트롤 플레인은 AWS가 맡지만 워커 노드를 EC2로 띄우면 그 노드의 OS는 여전히 내 몫이다. Fargate로 띄우면 노드 OS도 AWS가 맡는다.

### FaaS: 함수를 호출할 때만 돈다

Function as a Service. Lambda, Cloud Functions, Azure Functions. 이벤트(HTTP 요청, 큐 메시지, 파일 업로드)가 오면 함수가 실행되고, 끝나면 사라진다. 흔히 서버리스라고 부르는 것의 계산 부분이다.

책임의 칸만 보면 PaaS와 거의 같다. AWS가 OS와 관리형 런타임(Node.js, Python 등)을 패치한다. 그런데 칸이 다시 내 쪽으로 넘어오는 경우가 두 가지 있다.

첫째, 런타임 지원 종료다. Node.js나 Python의 한 버전이 수명을 다하면 Lambda도 그 런타임을 지원 종료로 돌린다. 그 뒤로는 보안 패치가 오지 않고, 일정이 지나면 함수 생성과 수정도 막힌다. 새 런타임으로 옮기고 코드가 그 위에서 도는지 확인하는 건 내 일이다.

둘째, 함수를 컨테이너 이미지로 배포할 때다. zip으로 올리면 AWS가 관리하는 런타임 위에서 돌지만, 이미지로 올리면 그 이미지 안의 OS와 런타임은 내가 고른 것이다. 패치가 나오면 내가 이미지를 다시 빌드해 배포해야 반영된다.

함수 코드에 넣은 라이브러리는 어느 경우든 내 몫이다. Lambda 위에서 돌아도 내 jar 안에 취약한 Log4j가 들어 있으면 그건 내 패치다.

### SaaS: 완성된 앱을 쓴다

Software as a Service. Gmail, Slack, Salesforce, Notion처럼 완성된 앱을 브라우저로 쓴다. 코드도 서버도 없다. 여기서도 남는 칸이 있다. 어떤 데이터를 넣는지, 누구에게 계정을 주는지, 다중 인증을 강제하는지, 퇴사자 계정을 언제 막는지, 외부 공유 링크를 허용하는지. SaaS 보안 사고의 상당수가 이 칸에서 난다.

비슷한 이름의 변형도 있다. DaaS(Desktop as a Service)는 가상 데스크톱을 빌리는 것이다(Amazon WorkSpaces, Azure Virtual Desktop). 원격 근무자에게 같은 업무 환경을 주고, 데이터를 단말에 남기지 않으려고 쓴다. 데스크톱 OS 이미지와 그 안의 앱 패치를 누가 하느냐는 서비스와 설정에 따라 다르다. 같은 약자를 Data as a Service의 뜻으로 쓰는 곳도 있으니 문맥으로 구분한다.

## 클라우드의 보안과 클라우드 안의 보안

AWS는 이 경계를 한 문장으로 정리한다. AWS는 클라우드의 보안(security of the cloud)을, 고객은 클라우드 안의 보안(security in the cloud)을 책임진다. 이걸 공동 책임 모델(shared responsibility model)이라고 부른다. Azure와 Google Cloud도 이름만 조금 다를 뿐 같은 모델을 쓴다.

클라우드의 보안은 데이터센터 출입, 전원과 냉각, 서버 하드웨어, 하이퍼바이저, 리전과 가용 영역을 잇는 글로벌 네트워크, 그리고 관리형 서비스의 내부 구현이다. 고객은 이걸 볼 수도 손댈 수도 없다. 대신 감사 보고서(SOC 2, ISO 27001 등)로 확인한다. AWS에서는 Artifact라는 메뉴에서 이 보고서를 받는다. 이 칸은 고객이 클라우드에서 그대로 물려받는 통제라서 상속 통제라고도 부른다. 규정 준수 심사를 받을 때 이 구분이 실제로 쓰인다. 예를 들어 데이터센터 물리 보안 항목은 클라우드 회사의 보고서로 증빙하고, 접근 통제와 로그 보관 항목은 내가 직접 증빙한다. "AWS가 인증을 받았으니 우리도 인증된 것"이 아니라, 인증받은 칸 위에 내 칸을 따로 증명해야 한다.

클라우드 안의 보안은 고객이 만든 모든 것이다. 데이터, IAM 사용자와 역할, 보안 그룹, 암호화를 켤지, 어떤 OS를 쓰고 언제 패치할지, 로그를 켤지, 백업을 얼마나 둘지.

그리고 양쪽이 나눠 맡는 칸이 있다. AWS 문서는 패치 관리, 설정 관리, 교육을 예로 든다. AWS는 자기 인프라를 패치하고 고객은 자기 OS와 앱을 패치한다. AWS는 자기 직원을 교육하고 고객은 자기 직원을 교육한다. 같은 이름의 일이 경계를 사이에 두고 양쪽에 있다.

그림의 내용을 서비스별로 펼치면 이렇다. 예시로 든 서비스 기준이고, 같은 서비스라도 설정에 따라 칸이 옮겨 간다는 점이 표의 핵심이다.

| 서비스 | OS 패치 | 런타임·엔진 패치 | 칸이 내 쪽으로 넘어오는 경우 |
|---|---|---|---|
| EC2 | 나 | 나 | 처음부터 내 칸 |
| Elastic Beanstalk | 플랫폼 | 플랫폼 | 관리형 플랫폼 업데이트를 끄면 내가 눌러야 한다 |
| EKS 워커 노드(EC2) | 나 | 나 | Fargate로 띄우면 노드 OS는 AWS 몫 |
| Lambda(zip) | AWS | AWS | 런타임 지원 종료 시 이전은 내 일 |
| Lambda(이미지) | 나 | 나 | 이미지를 다시 빌드해야 반영된다 |
| RDS | AWS | AWS(마이너) | 메이저 업그레이드, 적용 시점은 내가 정한다 |
| SaaS | 공급자 | 공급자 | 계정·공유 설정은 늘 내 칸 |

현장에서 쓸 확인 명령을 모아 두면 이렇다.

```bash
# RDS: AWS가 준비해 둔 대기 중인 유지 보수(엔진·OS 패치)를 본다
aws rds describe-pending-maintenance-actions

# Lambda: 함수마다 런타임과 배포 형태를 본다. PackageType이 Image면 런타임 패치가 내 몫이다
aws lambda list-functions --query "Functions[].[FunctionName,Runtime,PackageType]" --output table

# EC2(Ubuntu): 인스턴스 안에서 보안 업데이트가 남았는지 본다
sudo apt update && apt list --upgradable
```

## 관리형 DB에서도 내가 맡는 것

"RDS는 관리형이니까 AWS가 알아서 한다"는 말이 반만 맞다는 걸 보여 주는 대표 사례다. RDS에서 AWS가 맡는 것은 하드웨어, 스토리지, OS, DB 엔진 설치와 패치(마이너 버전 자동 업그레이드를 켰다면 유지 보수 시간에), 자동 백업을 실제로 수행하는 일, Multi-AZ를 켰을 때의 장애 조치다.

고객이 맡는 것은 생각보다 많다.

- 네트워크 노출: 퍼블릭 접근을 켤지, 어느 서브넷에 둘지, 보안 그룹에 무엇을 열지.
- DB 안의 계정과 권한: 마스터 비밀번호, 앱용 계정, 최소 권한.
- 암호화: 저장 암호화는 만들 때 정한다. 암호화하지 않고 만든 인스턴스는 나중에 켤 수 없어서, 스냅숏을 암호화된 사본으로 복사한 뒤 그걸로 새로 만들어야 한다. 전송 구간 TLS를 강제할지도 내가 정한다.
- 가용성 설계: Multi-AZ를 켤지, 백업 보존 기간을 며칠로 할지, 복원 테스트를 하는지.
- 메이저 버전 업그레이드: AWS가 자동으로 해 주지 않는다. 버전이 지원 종료에 가까워지면 내가 계획을 세워 올린다. 미루면 추가 요금이 붙는 연장 지원으로 넘어가거나 강제 업그레이드 일정이 잡힌다.
- 쿼리와 스키마: 인덱스가 없어 느린 쿼리는 관리형이라도 내 문제다.

정리하면 관리형 서비스는 "기계를 돌보는 일"을 가져가고 "무엇을 어떻게 설정할지"는 남긴다. 사고는 대부분 설정에서 난다.

## 사고가 나면 누구 책임인가

경계를 아는지 확인하는 가장 좋은 방법은 실제 사고를 판정해 보는 것이다. 판정 기준은 하나다. 그 일을 바꿀 수 있는 손잡이를 누가 쥐고 있었나.

22번 포트가 0.0.0.0/0으로 열린 보안 그룹. 고객 책임이다. 보안 그룹 규칙은 고객이 쓰는 설정이다. AWS는 보안 그룹이라는 기능이 제대로 동작하는 것까지 책임진다. 규칙이 의도대로 막고 여는지, 하이퍼바이저 수준에서 우회되지 않는지. 규칙의 내용은 고객 것이다. 이런 그룹을 찾는 명령은 이렇다.

```bash
# 22번 포트를 어디서든 받는 보안 그룹을 찾는다
aws ec2 describe-security-groups \
  --filters Name=ip-permission.from-port,Values=22 Name=ip-permission.cidr,Values=0.0.0.0/0 \
  --query "SecurityGroups[].[GroupId,GroupName]" --output table
```

공개로 설정된 S3 버킷에서 고객 데이터가 새는 것도 고객 책임이다. 그래서 AWS는 2023년부터 새로 만드는 버킷에 퍼블릭 액세스 차단을 기본으로 켜 두도록 바꿨다. 기본값을 안전하게 해 주는 건 클라우드 회사가 할 수 있는 일이지만, 그걸 끄는 건 고객의 선택이다.

2019년 Capital One 사고도 같은 쪽으로 판정됐다. 잘못 설정된 웹 방화벽을 통한 SSRF로 EC2 메타데이터에서 역할 자격 증명을 얻었고, 그 역할에 S3 읽기 권한이 너무 넓게 붙어 있었다. 하이퍼바이저도 S3도 설계대로 동작했다. 구멍은 고객 칸의 설정과 권한에 있었다. 메타데이터 엔드포인트를 노리는 공격과 IMDSv2는 [SSRF 글](/posts/ssrf)에 있다.

반대로 클라우드 쪽 책임인 경우도 있다. 하이퍼바이저 취약점으로 다른 고객의 메모리가 보인다면 AWS 책임이다. 가용 영역 하나의 전원이 나가 그 안의 인스턴스가 멈춘 것도 인프라 장애로 AWS 쪽이다. 다만 그 장애로 내 서비스가 통째로 멈췄다면 이야기가 하나 더 붙는다. 가용 영역이 하나 나가는 건 AWS가 SLA에서 미리 상정한 일이다. 여러 가용 영역에 나눠 두는 설계는 고객의 몫이다. 그래서 "인프라 장애는 AWS 책임, 그 장애에 견디는 구조는 내 책임"이라고 나눠 말하는 게 정확하다.

판정이 애매한 경계도 있다. 관리형 서비스의 기본 설정이 위험했다면? 문서에 위험이 적혀 있고 바꿀 손잡이가 고객에게 있었다면 고객 쪽으로 기운다. 실무에서 이 질문을 오래 붙잡을 이유는 없다. 사고가 나면 고객이 신뢰를 잃는 건 똑같다. 그래서 공동 책임 모델은 "누구 탓인가"를 정하는 표라기보다 "내가 빠뜨린 칸이 없는가"를 점검하는 목록으로 쓰는 게 낫다. 내 칸에서 사고가 났을 때 무엇부터 하는지는 [보안 사고 대응](/posts/security-incident-response)에 있다.

## 서버리스는 PaaS와 무엇이 다른가

칸만 보면 같은데 서버리스를 따로 부르는 이유가 있다. 차이는 단위와 수명이다.

PaaS의 앱은 인스턴스가 늘 떠 있다. 요청이 없어도 최소 한 대는 돌고, 그 시간만큼 낸다. 앱은 메모리에 상태를 들고 오래 살 수 있고, 백그라운드 작업이나 웹소켓도 된다.

FaaS의 함수는 이벤트가 올 때만 실행 환경이 생기고, 호출 수와 실행 시간으로 낸다. 요청이 없으면 0으로 줄어든다. 대신 실행 시간에 상한이 있고(Lambda는 15분), 실행 환경이 언제 사라질지 모르니 상태는 바깥에 둬야 하고, 새 환경을 만들 때 콜드 스타트가 붙는다. 동시에 실행되는 수만큼 DB 연결이 늘어나는 문제도 생긴다. 이런 제약은 [서버리스의 한계](/posts/serverless-limits)와 [콜드 스타트](/posts/cold-starts)에서 직접 재 봤다.

서버리스라는 말은 함수만 뜻하지 않는다. DynamoDB, S3, SQS처럼 용량을 미리 정하지 않고 쓴 만큼 내는 관리형 서비스를 묶어 부를 때도 쓴다. 이 둘을 이벤트로 엮는 구조는 [서버리스 아키텍처](/posts/serverless-architecture)에 있다.

책임 쪽에서 서버리스만의 함정은 권한이다. 함수가 수십 개로 쪼개지면 함수마다 실행 역할이 붙는다. 귀찮아서 함수 여러 개에 같은 넓은 역할을 붙이기 쉽다. 그러면 함수 하나가 뚫렸을 때 다른 함수의 권한까지 넘어간다. 서버가 사라진 만큼 IAM 정책이 서버 방화벽의 자리를 대신한다.

## 모델을 고르는 기준

정답 모델은 없다. 고를 때 따지는 축이 몇 개 있다.

통제권과 운영 부담은 같은 손잡이의 양 끝이다. OS 커널 파라미터를 바꿔야 하거나, 특정 버전의 드라이버가 필요하거나, GPU를 직접 다뤄야 하면 IaaS다. 그런 요구가 없는데 IaaS를 고르면 아무도 원하지 않은 일(패치, 디스크, 로그 회전)을 떠안는다. 팀에 운영을 맡을 사람이 없다면 그 일은 결국 아무도 하지 않게 되고, 그게 보안 구멍이 된다.

비용은 트래픽 모양에 따라 곡선이 다르다. FaaS는 요청이 적으면 거의 공짜에 가깝고, 요청이 늘수록 호출 단위 요금이 직선으로 오른다. 상시 인스턴스는 처음부터 고정비가 있지만 많이 쓸수록 요청당 단가가 내려간다. 그래서 두 곡선이 만나는 지점이 있고, 트래픽이 그 위에서 꾸준하면 상시 인스턴스가 싸다. 두 곡선이 만나는 지점은 직접 계산해 볼 수 있다. 아래 코드는 함수 요금(백만 요청당 요금, GB-초당 요금, 메모리, 평균 실행 시간)과 상시 인스턴스의 월 요금을 받아, 한 달에 몇 요청부터 인스턴스가 싸지는지 돌려준다. 테스트의 단가는 글을 쓰는 시점에 공시된 Lambda us-east-1 x86 요금(백만 요청당 0.20달러, GB-초당 0.0000166667달러)이고, 인스턴스 월 요금 30달러는 계산을 위한 예시다. 무료 사용량과 데이터 전송 요금은 뺐다.

첫 번째 경우는 한 달 약 2,900만 요청, 초당으로 바꾸면 평균 11건쯤이다. 함수가 무거워지면(1GB, 500ms) 그 지점이 월 350만 요청, 초당 1.4건으로 확 내려온다. 같은 서비스라도 함수 실행 시간이 비용 곡선을 크게 움직인다는 뜻이다. 실행 시간 대부분이 외부 API를 기다리는 시간이라면 그 기다림에도 GB-초 요금이 붙는다. 반대로 인스턴스 한 대가 초당 11건을 감당 못 하면 두 대, 세 대가 필요하니 실제 손익 지점은 더 복잡해진다. 평균이 아니라 피크에 맞춰 인스턴스를 띄워야 하는 것도 상시 쪽 비용을 올린다.

다만 이 계산에 사람 시간을 넣어야 한다. 패치와 장애 대응에 드는 엔지니어 시간은 청구서에 안 나오지만 대개 서버 요금보다 비싸다.

이식성도 따진다. 위로 갈수록 그 회사의 서비스에 묶인다. EC2 위의 Node.js 앱은 다른 클라우드로 옮기기 쉽지만, Lambda와 Step Functions와 DynamoDB로 짠 구조는 다시 짜야 한다. 묶이는 대가로 운영을 덜어 내는 것이니 나쁜 선택은 아니다. 다만 의식하고 고른다.

실무에서는 한 모델만 쓰지 않는다. 할 일 목록 API라면 API는 컨테이너 PaaS나 Lambda로, DB는 RDS로, 정적 파일은 S3와 CDN으로, 사내 협업 도구는 SaaS로 섞는다. 서비스마다 내 칸이 다르니, 서비스 목록 옆에 "패치는 누가, 백업은 누가, 접근 권한은 누가"를 적은 표 하나를 갖고 있으면 월요일 아침 공지에 바로 답할 수 있다.

## 새 계정을 받은 날 내 칸에서 먼저 할 일

모델을 무엇으로 고르든 계정 자체는 내 칸이다. 새 AWS 계정을 받았을 때 서비스를 올리기 전에 하는 일을 순서대로 적으면 이렇다.

1. 루트 사용자에 MFA를 걸고, 루트 액세스 키는 만들지 않는다. 루트는 결제와 계정 설정 몇 가지에만 쓴다.
2. 사람은 IAM Identity Center(SSO)로 들어오게 하고, 오래 사는 IAM 사용자 키를 만들지 않는다.
3. CloudTrail을 모든 리전에 켜고 로그를 다른 계정(또는 지울 수 없는 버킷)으로 보낸다.
4. 계정 수준의 S3 퍼블릭 액세스 차단을 켠다.
5. 예산 알림을 걸고, GuardDuty 같은 위협 탐지를 켠다.
6. 쓰지 않을 리전은 조직을 쓴다면 SCP로 막는다.

```bash
# 루트 사용자의 MFA와 액세스 키 여부를 계정 요약에서 본다
aws iam get-account-summary \
  --query "SummaryMap.[AccountMFAEnabled,AccountAccessKeysPresent]"

# 계정 전체에 S3 퍼블릭 액세스 차단을 켠다
aws s3control put-public-access-block --account-id 123456789012 \
  --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

# 모든 리전에 걸친 트레일을 만들고 기록을 시작한다
aws cloudtrail create-trail --name org-audit --s3-bucket-name audit-logs-123456789012 \
  --is-multi-region-trail
aws cloudtrail start-logging --name org-audit
```

`get-account-summary`의 `AccountMFAEnabled`가 1이면 루트에 MFA가 있고, `AccountAccessKeysPresent`가 1이면 루트 액세스 키가 남아 있다는 뜻이다. 두 번째 값이 1이면 그 키부터 지운다. 이 목록은 서비스 모델과 상관없이 똑같다. 공동 책임 모델에서 끝까지 남는 데이터와 권한 칸이 바로 이것이기 때문이다. 이 칸이 비어 있는 계정에서 사고가 나면 무슨 일이 생기는지는 [보안 사고 대응](/posts/security-incident-response)에서 따라가 봤다.

## Well-Architected 여섯 기둥을 내 칸 위에서 읽기

AWS Well-Architected Framework는 클라우드 위의 설계를 점검하는 질문 목록이다. 기둥이 여섯 개다. 운영 우수성, 보안, 안정성, 성능 효율성, 비용 최적화, 지속 가능성. 지속 가능성은 2021년에 더해졌다.

이 기둥들은 공동 책임 모델의 고객 칸 위에서 무엇을 점검하는지 정리한 목록으로 읽으면 쉽다. AWS 쪽 칸은 감사 보고서로 확인하고, 내 쪽 칸은 이 질문으로 확인한다.

- 보안: 사람과 서비스의 권한이 최소인가, 데이터가 저장과 전송 구간에서 암호화되나, 로그로 추적할 수 있나. 공동 책임 모델의 내 칸과 가장 직접 겹친다.
- 안정성: 가용 영역 하나가 나가도 견디나, 백업에서 실제로 복원해 봤나. 앞에서 본 "장애는 AWS, 견디는 구조는 나"가 이 기둥이다.
- 성능 효율성: 일에 맞는 자원 종류와 크기를 골랐나, 관리형 서비스로 대신할 수 있는데 직접 돌리고 있지 않나.
- 비용 최적화: 놀고 있는 자원이 없나, 사용 패턴에 맞는 요금제를 쓰나.
- 지속 가능성: 같은 일을 더 적은 자원으로 하나. 비용 최적화와 방향이 대부분 같다.

AWS 콘솔의 Well-Architected Tool에서 워크로드마다 이 질문에 답하고 위험 항목을 받을 수 있다. 한 번 답해 보면 "그건 AWS가 해 주는 줄 알았다"는 칸이 몇 개 나온다.

## 다시 월요일 아침으로

OpenSSL 공지에 대한 답은 이렇다. EC2는 내가 오늘 패치한다. Beanstalk는 관리형 플랫폼 업데이트를 켜 뒀는지부터 본다. Lambda는 zip이면 기다리고 이미지면 다시 굽는다. RDS는 대기 중인 유지 보수를 보고 적용 시간을 정한다. SaaS는 공급자의 공지를 확인한다. 22번 포트가 열린 보안 그룹은 어느 모델을 쓰든 내 칸이다. 서비스 모델은 클라우드에 맡기는 층의 높이고, 공동 책임 모델은 그 높이와 상관없이 데이터·권한·설정은 끝까지 내 칸이라고 말한다. 그 칸에 무엇이 있는지 아는 것이 클라우드를 쓰는 사람의 첫 번째 일이다. 그 칸에서 가장 먼저 다룰 권한 이야기는 [IAM 기본](/posts/iam-basics)으로 이어진다.

## 면접에서 나올 만한 질문

### IaaS, PaaS, SaaS의 차이를 설명해 주세요.

클라우드에 맡기는 층의 높이가 다르다. IaaS는 가상 머신과 네트워크까지 빌리고 OS부터 위는 내가 관리한다. PaaS는 OS와 런타임까지 플랫폼이 맡아서 코드만 올린다. SaaS는 완성된 앱을 쓰고 코드도 서버도 없다. 어느 모델이든 데이터와 접근 권한은 고객 몫으로 남는다.

### 공동 책임 모델이 무엇인가요?

클라우드 회사는 클라우드의 보안을, 고객은 클라우드 안의 보안을 맡는다는 모델이다. 데이터센터, 하드웨어, 하이퍼바이저, 관리형 서비스의 내부는 클라우드 회사가, 데이터, IAM, 네트워크 설정, OS와 앱 패치, 암호화 선택은 고객이 맡는다. 패치 관리처럼 같은 이름의 일이 양쪽에 나뉘어 있는 칸도 있다. 서비스 모델이 올라갈수록 고객 칸이 줄지만 사라지지는 않는다.

### 보안 그룹을 열어 둬서 생긴 사고는 누구 책임인가요?

고객 책임이다. 보안 그룹이 규칙대로 동작하게 하는 건 클라우드 회사 몫이지만, 규칙의 내용은 고객이 쓰는 설정이다. 판정 기준은 그 일을 바꿀 수 있는 손잡이를 누가 쥐고 있었느냐다. 공개 S3 버킷이나 너무 넓은 IAM 역할도 같은 쪽이다.

### RDS 같은 관리형 DB를 쓰면 고객이 맡는 것은 무엇인가요?

네트워크 노출(퍼블릭 접근, 서브넷, 보안 그룹), DB 계정과 권한, 저장 암호화를 켤지(만들 때 정하고 나중에 바로 켤 수 없다), Multi-AZ와 백업 보존 기간, 메이저 버전 업그레이드 계획, 쿼리와 인덱스다. AWS는 하드웨어, OS, 엔진 패치, 백업 수행, 장애 조치 동작을 맡는다. 기계를 돌보는 일은 가져가고 설정은 남긴다고 보면 된다.

### 서버리스(FaaS)는 PaaS와 무엇이 다른가요?

책임의 칸은 비슷하지만 단위와 수명이 다르다. PaaS는 인스턴스가 늘 떠 있어 상주 비용이 있고 오래 사는 상태와 백그라운드 작업이 된다. FaaS는 이벤트가 올 때만 실행 환경이 생겨 0까지 줄고 호출 단위로 내지만, 실행 시간 상한, 상태 없음, 콜드 스타트, 동시성만큼 늘어나는 DB 연결 같은 제약이 있다.

### Lambda를 쓰면 런타임 패치는 전혀 신경 쓰지 않아도 되나요?

zip으로 배포한 관리형 런타임이면 AWS가 패치한다. 하지만 런타임 버전이 지원 종료되면 새 버전으로 옮기는 건 고객 일이고, 컨테이너 이미지로 배포했다면 이미지 안의 OS와 런타임을 고객이 다시 빌드해 배포해야 패치가 반영된다. 함수에 넣은 라이브러리의 취약점은 어느 경우든 고객 몫이다.

### 가용 영역 하나가 멈춰 서비스가 죽었다면 누구 책임인가요?

가용 영역 장애 자체는 클라우드 회사의 인프라 문제다. 하지만 가용 영역 하나가 나가는 건 미리 상정된 일이라, 여러 가용 영역에 나눠 견디게 설계하는 건 고객 몫이다. Well-Architected의 안정성 기둥이 이 부분을 점검한다. 그래서 "장애는 클라우드 책임, 견디는 구조는 고객 책임"으로 나눠 답한다.

### 어떤 기준으로 서비스 모델을 고르나요?

통제권이 꼭 필요한지부터 본다. 커널, 드라이버, 특정 OS 버전이 필요하면 IaaS, 아니면 운영 부담이 적은 PaaS나 FaaS가 낫다. 비용은 트래픽 모양으로 보는데, 적고 들쭉날쭉하면 FaaS, 크고 꾸준하면 상시 인스턴스가 싸고, 여기에 운영하는 사람 시간을 더해서 비교한다. 위로 갈수록 그 클라우드에 묶이는 정도도 커진다는 점을 함께 따진다.
