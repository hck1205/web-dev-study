보안 점검에서 이런 질문을 받았다. "CI가 클러스터에 붙을 때 쓰는 토큰, 언제 만료돼요?" CI 설정에 들어 있던 토큰은 몇 년 전에 누군가 Secret에서 꺼내 둔 것이었다. 꺼내서 가운데 조각을 디코드해 봤다.

```bash
# Secret에 든 토큰을 꺼내 JWT의 가운데(클레임) 조각만 디코드한다
kubectl -n shop get secret orders-legacy-token -o jsonpath='{.data.token}' | base64 -d > tok.txt
python3 dec.py < tok.txt
```

```text
{
  "iss": "kubernetes/serviceaccount",
  "kubernetes.io/serviceaccount/namespace": "shop",
  "kubernetes.io/serviceaccount/secret.name": "orders-legacy-token",
  "kubernetes.io/serviceaccount/service-account.name": "orders",
  "kubernetes.io/serviceaccount/service-account.uid": "8128176a-2dee-4be0-bb72-51015c6e71cb",
  "sub": "system:serviceaccount:shop:orders"
}
```

`exp`가 없다. 만료가 없는 토큰이다. 받는 쪽(`aud`)도 정해져 있지 않고, 어느 Pod에 묶인 것도 아니다. 이 문자열을 가진 사람은 Secret이 지워질 때까지 어디서든 이 ServiceAccount로 API를 부를 수 있다. 지금 Pod 안에 들어가는 토큰은 이것과 완전히 다르다. 이 글은 두 토큰이 어떻게 다른지, 지금의 토큰이 어떻게 발급되고 갱신되고 죽는지, 그리고 그 토큰을 클러스터 밖(Vault, AWS)이 믿게 하는 방법을 kwok으로 띄운 쿠버네티스 1.37.0 클러스터에서 직접 확인한다.

이 토큰으로 무엇을 할 수 있는지는 [RBAC](/posts/k8s-rbac)가 정한다. JWT 서명과 키 교체의 일반론은 [JWT 키 교체](/posts/jwt-key-rotation)에 있다. 같은 보안 묶음의 다른 글은 [securityContext](/posts/k8s-security-context)와 [Pod Security Admission](/posts/k8s-pod-security-admission)이다.

## ServiceAccount는 Pod의 신분증이다

사람은 인증서나 OIDC로 로그인하고, Pod 안의 프로그램은 ServiceAccount로 로그인한다. 쿠버네티스가 직접 오브젝트로 갖고 있는 유일한 신원이다. 네임스페이스마다 `default`가 자동으로 생기고, Pod에 `serviceAccountName`을 안 적으면 그걸 쓴다.

```bash
# ServiceAccount를 만들고, 그 이름으로 토큰을 받아 API 서버가 누구로 보는지 확인한다
kubectl -n shop create serviceaccount orders
kubectl --token "$(kubectl -n shop create token orders --bound-object-kind=Pod --bound-object-name=vault-client)" auth whoami
```

```text
serviceaccount/orders created
ATTRIBUTE                                           VALUE
Username                                            system:serviceaccount:shop:orders
UID                                                 8128176a-2dee-4be0-bb72-51015c6e71cb
Groups                                              [system:serviceaccounts system:serviceaccounts:shop system:authenticated]
Extra: authentication.kubernetes.io/credential-id   [JTI=cf2883d3-8533-49da-9403-5696962ed451]
Extra: authentication.kubernetes.io/node-name       [node-1]
Extra: authentication.kubernetes.io/node-uid        [97f3bbd1-515b-4bb7-ab4c-3efd40c924ce]
Extra: authentication.kubernetes.io/pod-name        [vault-client]
Extra: authentication.kubernetes.io/pod-uid         [ad82a3c2-43bd-40a0-bda8-9971d35fe75e]
```

(위 명령의 kubectl 서버·CA 옵션은 줄였다.) 사용자 이름은 `system:serviceaccount:<네임스페이스>:<이름>` 형식이고 그룹이 두 개 붙는다. `system:serviceaccounts`(모든 SA)와 `system:serviceaccounts:shop`(이 네임스페이스의 모든 SA)이다. RBAC에서 "shop의 모든 SA에게 읽기를 준다"를 그룹 하나로 쓸 수 있는 이유다. 반대로 `system:serviceaccounts`에 권한을 주면 클러스터의 모든 Pod에 준 것이니 조심한다.

`Extra`에 Pod와 노드 이름까지 들어 있는 게 눈에 띈다. 이 토큰이 특정 Pod에 묶인 토큰이라서다. 이 정보는 감사 로그에도 남아서 "어느 Pod가 이 요청을 보냈나"를 추적할 수 있다.

## Pod 안의 토큰은 어디서 오나

ServiceAccount가 있는 Pod를 하나 만들고 API 서버에 저장된 모습을 보면, 매니페스트에 없던 볼륨이 붙어 있다.

```bash
# serviceAccountName만 적은 Pod를 만든다
kubectl -n shop run orders --image=busybox:1.36 --overrides='{"spec":{"serviceAccountName":"orders"}}' -- sleep 3600
kubectl -n shop get pod orders -o yaml   # volumes 부분만 옮긴다
```

```text
    volumeMounts:
    - mountPath: /var/run/secrets/kubernetes.io/serviceaccount
      name: kube-api-access-tglvq
      readOnly: true
  volumes:
  - name: kube-api-access-tglvq
    projected:
      defaultMode: 420
      sources:
      - serviceAccountToken:
          expirationSeconds: 3607
          path: token
      - configMap:
          items:
          - key: ca.crt
            path: ca.crt
          name: kube-root-ca.crt
      - downwardAPI:
          items:
          - fieldRef:
              apiVersion: v1
              fieldPath: metadata.namespace
            path: namespace
```

ServiceAccount 어드미션 플러그인이 Pod를 저장하기 전에 `kube-api-access-<랜덤>`이라는 projected 볼륨을 넣었다. projected 볼륨은 여러 출처를 한 디렉터리에 모아 주는 볼륨이다. 토큰(`token`), API 서버 인증서를 검증할 CA(`ca.crt`), 자기 네임스페이스 이름(`namespace`) 세 파일이 생긴다. client-go 같은 라이브러리가 "클러스터 안에서 실행 중"일 때 읽는 파일이 이것이다.

토큰 파일은 Secret에서 오지 않는다. kubelet이 Pod를 띄울 때 API 서버에 그 Pod용 토큰을 새로 발급해 달라고 요청한다. 이 요청을 TokenRequest라고 한다.

토큰이 etcd에 저장되지 않는다는 점이 옛 방식과 가장 큰 차이다. etcd 백업이 새도 토큰은 안 샌다. Secret처럼 `list` 권한으로 꺼낼 수도 없다.

## 1시간짜리 토큰이 1년을 사는 이유

앞의 Pod 볼륨에 적힌 수명은 `expirationSeconds: 3607`이었다. 3600이 아니라 3607이다. kubelet이 요청하는 것과 같은 조건으로 받아 봤다.

```bash
# kubelet처럼 Pod에 묶고 3607초를 요청한다
kubectl -n shop create token orders --bound-object-kind=Pod --bound-object-name=orders \
  --bound-object-uid=77a43a17-2818-4a63-a2ff-6dfe9f7c6020 --duration=3607s | python3 dec.py | grep -E 'lifetime|warnafter'
```

```text
    "warnafter": 1792547705
lifetime_s = 31536000
```

수명이 31536000초, 1년이다. API 서버의 `--service-account-extend-token-expiration`(기본 true)이 3607초 요청을 알아보고 늘려 준 것이다. 대신 `warnafter`에 원래 만료 시각을 적어 둔다. TokenRequest 응답을 그대로 보면 이 구조가 더 분명하다.

```bash
# TokenRequest API를 직접 부르고, 응답의 만료 시각과 토큰 안의 exp를 비교한다
kubectl create --raw /api/v1/namespaces/shop/serviceaccounts/orders/token -f tr.json > trout.json
date -u +%FT%TZ
jq '{expirationTimestamp: .status.expirationTimestamp, spec: .spec.expirationSeconds}' trout.json
jq -r .status.token trout.json | python3 dec.py | grep -E 'lifetime|warnafter'
```

```text
2026-10-21T01:06:10Z
{
  "expirationTimestamp": "2026-10-21T02:06:17Z",
  "spec": 3607
}
    "warnafter": 1792548377
lifetime_s = 31536000
```

응답은 kubelet에게 "1시간 뒤 만료"라고 알려 주고, 토큰 안의 `exp`는 1년 뒤다. kubelet은 응답의 시각을 믿고 1시간 안에 새 토큰으로 바꾼다. 그런데 토큰 파일을 한 번 읽고 메모리에 들고 있는 오래된 클라이언트도 1년 동안은 끊기지 않는다. 바운드 토큰이 처음 기본값이 될 때(1.21 무렵) 그런 앱이 갑자기 401을 맞지 않게 넣은 완충 장치다. `warnafter`가 지난 토큰이 쓰이면 API 서버는 감사 로그에 `authentication.k8s.io/stale-token` 주석을 남기고 `serviceaccount_stale_tokens_total` 메트릭을 올린다. 이 숫자가 0이 아니면 토큰 파일을 다시 읽지 않는 앱이 있다는 뜻이다.

kubelet의 갱신 시점을 시간 순서로 놓으면 이렇다.

길이를 직접 정할 수도 있다. TokenRequest의 최소 수명은 10분이다.

```bash
# 5분짜리를 요청하면 거절된다
kubectl -n shop create token orders --duration=5m
```

```text
error: failed to create token: TokenRequest.authentication.k8s.io "" is invalid: spec.expirationSeconds: Invalid value: 300: may not specify a duration less than 10 minutes
```

최대값은 API 서버의 `--service-account-max-token-expiration`이 정한다. 이 실습 클러스터는 따로 정하지 않아서 `--duration=48h`도 그대로 172800초짜리가 나왔다. 운영에서는 이 값을 정해 두지 않으면 누군가 `kubectl create token --duration=8760h`로 1년짜리 토큰을 만들어 CI에 넣는 일을 막을 수 없다.

## Pod가 지워지면 토큰도 죽는다

## audience로 받는 쪽을 정한다

API 서버용 토큰을 Vault에도, 사내 서비스에도 그대로 보여 주면 문제가 생긴다. 받은 쪽 누구든 그 토큰으로 API 서버를 부를 수 있다. 토큰 재사용 공격이다. 그래서 받는 쪽마다 `aud`가 다른 토큰을 따로 쓴다.

```bash
# vault용 토큰을 받는다
kubectl -n shop create token orders --audience=vault --duration=10m > tok3.txt

tr tok3.txt ""                           # API 서버가 자기 audience로 검증
tr tok3.txt ',"audiences":["vault"]'     # vault audience로 검증
```

```text
{"authenticated":null,"user":null,"error":"[invalid bearer token, token audiences [\"vault\"] is invalid for the target audiences [\"https://kubernetes.default.svc.cluster.local\"]]"}
{"authenticated":true,"user":"system:serviceaccount:shop:orders","error":null}
```

vault용 토큰은 API 서버 로그인에는 쓸 수 없다. Vault가 털려서 토큰이 새도 API 서버는 안전하다. Pod에서는 projected 볼륨으로 이런 토큰을 받는다.

```yaml
spec:
  serviceAccountName: orders
  automountServiceAccountToken: false   # API 서버용 토큰은 넣지 않는다
  containers:
  - name: app
    image: busybox:1.36
    volumeMounts:
    - name: vault-token
      mountPath: /var/run/secrets/vault
      readOnly: true
  volumes:
  - name: vault-token
    projected:
      sources:
      - serviceAccountToken:
          audience: vault
          expirationSeconds: 900     # 600 미만이면 Pod 생성이 거절된다
          path: token
```

처음에 `expirationSeconds: 300`으로 넣었더니 Pod 생성부터 막혔다.

```text
The Pod "vault-client" is invalid: 
* spec.volumes[0].projected.sources[0].serviceAccountToken.expirationSeconds: Invalid value: 300: may not specify a duration less than 10 minutes
```

받는 쪽 검증 코드에서 흔한 실수는 `aud` 확인을 빼는 것이다. JWKS로 서명만 확인하고 `aud`를 안 보면, 같은 클러스터의 다른 용도 토큰이 다 통과한다.

## 옛 방식: Secret에 든 영구 토큰

맨 앞의 만료 없는 토큰이 옛 방식이다. 1.24 전에는 ServiceAccount를 만들면 컨트롤러가 `kubernetes.io/service-account-token` 타입 Secret을 자동으로 만들고 그 토큰을 Pod에 마운트했다. 지금은 자동으로 안 만든다(1.24 기본 꺼짐, 1.26 GA). 실습 클러스터에서 SA를 만든 뒤 Secret 목록은 비어 있었다. 지금도 손으로 만들면 생긴다.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: orders-legacy-token
  namespace: shop
  annotations:
    kubernetes.io/service-account.name: orders   # 이 SA의 토큰을 채워 달라
type: kubernetes.io/service-account-token
```

```bash

kubectl apply -f legacy.yaml
curl -sS --cacert ca.crt -H "Authorization: Bearer $(cat tokL.txt)" \
  https://127.0.0.1:32732/api/v1/namespaces/shop/pods -o /dev/null -w '%{http_code}\n'
kubectl -n shop get secret orders-legacy-token --show-labels
```

```text
secret/orders-legacy-token created

NAME                  TYPE                                  DATA   AGE   LABELS
orders-legacy-token   kubernetes.io/service-account-token   3      4s    kubernetes.io/legacy-token-last-used=2026-10-21
```

## 필요 없으면 마운트하지 않는다

대부분의 앱은 쿠버네티스 API를 부르지 않는다. 그런데 기본 설정은 모든 Pod에 API 서버용 토큰을 넣는다. 앱에 원격 코드 실행 취약점이 있으면 공격자는 그 토큰으로 API를 두드려 본다. `default` SA에 실수로 권한을 줘 둔 클러스터라면 거기서 끝이다. 안 쓰면 넣지 않는다.

```bash
# shop의 default SA는 토큰을 마운트하지 않게 한다
kubectl -n shop patch sa default -p '{"automountServiceAccountToken": false}'

# 아무 설정 없는 Pod와, Pod에서 다시 켠 Pod를 비교한다
kubectl -n shop run plain --image=busybox:1.36 -- sleep 3600
kubectl -n shop run needs-api --image=busybox:1.36 --overrides='{"spec":{"automountServiceAccountToken":true}}' -- sleep 3600
for p in plain needs-api; do echo "$p: $(kubectl -n shop get pod $p -o jsonpath='{.spec.volumes[*].name}')"; done
```

```text
serviceaccount/default patched
plain: 
needs-api: kube-api-access-j6xd9
```

ServiceAccount에 둔 값은 기본값이고, Pod에 적은 값이 이긴다. 그래서 정책은 "SA에서 끄고, API가 필요한 Pod만 전용 SA를 만들어 그 Pod에서 켠다"가 깔끔하다. 하나 더. `automountServiceAccountToken: false`는 토큰을 안 넣을 뿐 SA의 신원이 사라지는 건 아니다. 앞의 vault 예처럼 다른 audience 토큰은 projected 볼륨으로 따로 받을 수 있다.

## 클러스터 밖에서 이 토큰을 믿게 하기

바운드 토큰은 OIDC 형식을 따른다. API 서버는 발급자 정보와 공개 키를 표준 주소로 내놓는다.


## 클레임을 읽는 함수 짜 보기

토큰의 가운데 조각은 서명 없이도 읽힌다. 아래 함수는 토큰을 받아 주체, audience, 수명, 묶인 Pod, 옛 토큰 여부를 돌려줘야 한다. 테스트 토큰은 실습에서 받은 토큰의 클레임을 줄이고 서명을 가짜(`c2ln`)로 바꾼 것이다. base64url은 `-`, `_`를 쓰고 끝의 `=`를 뗀다는 점을 기억하자. 브라우저의 `atob`는 표준 base64만 받는다.

## 토큰 때문에 생기는 장애

현장에서 토큰 문제는 대부분 401로 나타난다. 증상별로 보는 곳이 다르다.

몇 달 잘 돌던 오래된 컨트롤러가 갑자기 401을 낸다. 토큰 파일을 시작할 때 한 번만 읽는 클라이언트일 가능성이 크다. 1년 연장 덕에 버티다가 진짜 만료를 맞은 것이다. 앞의 stale-token 메트릭이나 감사 로그 주석으로 미리 찾을 수 있다. 라이브러리를 올리거나 파일을 주기적으로 다시 읽게 고친다.

Pod를 옮겼더니 외부 시스템 로그인이 안 된다. 토큰을 Vault 같은 곳에 캐시해 두고 재사용하는 구조라면, 원래 Pod가 지워지는 순간 그 토큰은 무효다. 오류 문구 `service account token has been invalidated`가 그 신호다.

클러스터를 옮기거나 발급자 주소를 바꿨더니 IRSA가 전부 실패한다. 토큰의 `iss`가 바뀌면 신뢰 정책에 등록된 OIDC 공급자와 맞지 않는다. API 서버의 `--service-account-issuer`는 여러 번 줄 수 있어서, 첫 값으로 새 토큰을 발급하면서 이전 발급자의 토큰도 한동안 받아 줄 수 있다. 서명 키를 바꿀 때도 옛 공개 키를 `--service-account-key-file`에 남겨 둬야 이미 나간 토큰이 살아남는다.

받는 쪽 서버에서 `token is not valid yet`이나 `exp` 관련 오류가 난다. 노드나 외부 서버의 시계가 어긋난 경우다. `nbf`와 `iat`는 발급 시각이라 몇 초만 어긋나도 엄격한 검증기는 거절한다. NTP부터 본다.

## 신분증은 짧게, 받는 쪽을 정해서

지금의 ServiceAccount 토큰은 TokenRequest로 그때그때 발급되고, etcd에 저장되지 않으며, 수명(`exp`)과 받는 쪽(`aud`)과 묶인 Pod가 정해져 있다. Pod가 사라지면 토큰도 무효가 되고, kubelet이 수명의 80%에서 바꿔 준다. 옛 Secret 토큰은 이 셋이 모두 없어서 위험하다. API를 안 부르는 Pod에는 토큰을 넣지 않고, 밖의 시스템에는 그 시스템 이름의 audience로 따로 받은 토큰을 보여 준다. 토큰이 무엇을 할 수 있는지는 [RBAC](/posts/k8s-rbac)가, 컨테이너가 노드에서 무엇을 할 수 있는지는 [securityContext](/posts/k8s-security-context)가 다룬다.

## 면접에서 나올 만한 질문

### 옛 ServiceAccount 토큰과 지금의 바운드 토큰은 무엇이 다른가요?

옛 토큰은 Secret에 저장되고 만료와 audience가 없어서, 꺼낸 사람은 Secret이 지워질 때까지 어디서든 쓸 수 있었다. 바운드 토큰은 kubelet이 TokenRequest로 그때그때 받고 etcd에 저장하지 않으며, `exp`와 `aud`가 있고 Pod에 묶여서 Pod가 지워지면 무효가 된다. 1.24부터 SA를 만들어도 옛 토큰 Secret이 자동으로 생기지 않는다.

### Pod 안의 토큰 파일은 누가 언제 바꾸나요?

kubelet이 바꾼다. 토큰 수명의 80%가 지나거나 24시간이 넘으면 새로 받아 파일을 교체한다. 앱이 파일을 다시 읽어야 새 토큰을 쓰는데, client-go는 알아서 다시 읽는다. kubelet이 요청하는 3607초 토큰은 API 서버가 실제로는 1년짜리로 늘려 주고 `warnafter`를 적어 두는데, 파일을 다시 안 읽는 옛 클라이언트가 갑자기 끊기지 않게 하는 완충 장치다.

### audience는 왜 필요한가요?

토큰을 받은 쪽이 그 토큰을 다른 곳에 재사용하지 못하게 하려고다. API 서버용 토큰을 Vault에 보여 주면 Vault를 턴 사람이 그 토큰으로 API 서버를 부를 수 있다. Vault에는 `aud: vault` 토큰을 따로 주면 API 서버는 그 토큰을 거절한다. 받는 쪽 검증 코드는 서명뿐 아니라 `aud`를 반드시 확인해야 한다.

### automountServiceAccountToken을 false로 두는 이유와 우선순위는요?

API를 부르지 않는 앱에 토큰이 있으면, 앱이 뚫렸을 때 공격자가 그 토큰으로 API를 탐색한다. ServiceAccount에 false를 두면 기본값이 되고 Pod의 값이 그걸 이긴다. 그래서 `default` SA에서 끄고, API가 필요한 Pod만 전용 SA를 쓰면서 켠다. 꺼도 신원은 남아서 다른 audience의 토큰은 projected 볼륨으로 받을 수 있다.

### IRSA는 어떻게 동작하나요?

클러스터의 ServiceAccount 토큰이 OIDC 형식이고 발급자의 공개 키가 공개돼 있다는 점을 이용한다. 웹훅이 `aud: sts.amazonaws.com` 토큰을 Pod에 넣고, SDK가 그 토큰으로 `AssumeRoleWithWebIdentity`를 부르면 STS가 공개 키로 서명을 검증하고 신뢰 정책의 `sub`, `aud` 조건을 비교한 뒤 임시 자격 증명을 준다. `sub` 조건을 넓게 쓰면 다른 SA도 그 역할을 맡게 되는 것이 흔한 실수다.

### Pod를 지웠는데 복사해 둔 토큰은 계속 쓸 수 있나요?

Pod에 묶인 토큰이라면 못 쓴다. API 서버는 검증할 때 토큰에 적힌 Pod가 아직 있는지와 UID를 확인해서, 실습에서는 지운 뒤 십여 초 안에 `token has been invalidated`로 거절했다. Pod 없이 `kubectl create token`으로 받은 토큰은 SA에만 묶여서 SA를 지우거나 만료될 때까지 유효하다. 그래서 CI용 토큰은 수명을 짧게 잡는다.

### 서명 키나 발급자 주소를 바꿀 때 주의할 점은요?

이미 나간 토큰이 깨지지 않게 겹치는 기간을 둔다. 새 키로 서명하면서 옛 공개 키를 `--service-account-key-file`에 남겨 두고, 발급자는 `--service-account-issuer`를 여러 번 줘서 옛 발급자 토큰도 받아 준다. IRSA처럼 외부가 발급자 주소를 믿는 구조라면 외부 쪽 OIDC 공급자 등록도 함께 바꿔야 한다.
