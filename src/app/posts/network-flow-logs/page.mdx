보안 그룹을 정리하라는 과제를 받았다. DB 서버의 보안 그룹에 2년 전에 누가 열어 둔 `10.0.0.0/16` 전체 허용 규칙이 있다. 지우고 싶은데, 지금 누가 실제로 이 DB에 붙는지 아는 사람이 없다. 지웠다가 결제 배치가 멈추면 곤란하다. 앱 로그를 다 뒤질 수도 없고, tcpdump를 몇 주 켜 둘 수도 없다.

이럴 때 꺼내는 게 흐름 로그(flow log)다. 패킷 내용은 버리고 "누가, 누구에게, 몇 번 포트로, 얼마나, 허용됐나 막혔나"만 연결 단위로 한 줄씩 남긴다. 2주치 흐름 로그를 모아 DB의 5432번으로 들어온 출발지를 세면, 규칙을 지우기 전에 영향받을 서버 목록이 나온다.

이 글은 흐름 레코드가 어떻게 만들어지는지 리눅스에서 직접 만들어 보고, AWS VPC 흐름 로그 한 줄을 필드별로 읽은 뒤, 거기서 "누가 누구와 이야기하나"를 뽑는 법과 비용·샘플링의 함정을 다룬다. 보안 그룹과 NACL 중 어디서 막혔는지 흐름 로그로 가르는 법은 [보안 그룹과 NACL 글](/posts/security-groups-nacl)에서 이미 봤으니 여기서는 짧게만 다룬다. 호스트 카운터로 손실을 보는 쪽은 [네트워크 모니터링 글](/posts/network-monitoring)에 있다.

실습은 Ubuntu 24.04에서 했다. 네트워크 네임스페이스 `n7-cli`(10.77.0.1, 스캐너 역할의 보조 주소 10.77.0.9)와 `n7-web`(10.77.0.2)을 veth로 잇고, `n7-web`에 HTTP 서버와 dnsmasq를 띄웠다. 흐름 기록에는 Ubuntu 패키지 softflowd 1.1.0(내보내는 쪽)과 nfdump 1.7.3(받아 저장하고 읽는 쪽)을 썼다.

## 패킷 대신 대화의 요약을 남긴다

패킷 캡처는 모든 것을 남기는 대신 너무 크다. 1Gbit/s 회선을 하루 찍으면 10TB가 넘는다. 지표는 반대로 너무 작다. "초당 몇 바이트"에는 누가 보냈는지가 없다. 흐름 로그는 그 사이에 있다. 같은 대화에 속한 패킷을 하나로 묶어, 대화마다 한 줄만 남긴다.

무엇을 "같은 대화"로 볼지는 다섯 가지 값으로 정한다. 출발지 IP, 목적지 IP, 출발지 포트, 목적지 포트, 프로토콜이다. 이 다섯 개를 5-튜플(5-tuple)이라고 부른다. 다섯 값이 같은 패킷은 한 흐름으로 합쳐 패킷 수와 바이트 수를 더하고, 처음 본 시각과 마지막으로 본 시각을 적는다.

수출기(exporter)는 이 묶음을 메모리의 흐름 캐시에 들고 있다가, 대화가 끝났거나 너무 오래 열려 있으면 레코드로 내보낸다. 아래 그림은 패킷 일곱 개가 캐시에서 흐름 셋으로 묶이는 과정이다.

언제 내보낼지가 흐름 로그의 성격을 정한다. 기준은 보통 둘이다. 일정 시간 패킷이 없으면 끝난 것으로 보는 비활성 타임아웃, 그리고 아직 이어지는 긴 연결이라도 일정 시간마다 끊어서 내보내는 활성 타임아웃이다. Cisco 장비의 기본값은 비활성 15초, 활성 30분이다. 활성 타임아웃이 30분이면 몇 시간 이어지는 백업 연결의 바이트는 30분 뒤에야 보인다. 그래서 "지금 이 순간 누가 대역폭을 먹고 있나"에는 흐름 로그가 늦다. 그건 지표와 패킷 캡처의 몫이다.

```bash
# 수집기: 10.77.0.1:9995로 받아 60초마다 파일을 나눈다
sudo ip netns exec n7-cli nfcapd -w /var/tmp/flows -p 9995 -b 10.77.0.1 -t 60 &
# 수출기: eth0을 보고 NetFlow v9으로 보낸다. 실습이라 타임아웃을 짧게 줄였다
sudo ip netns exec n7-web softflowd -d -i eth0 -v 9 -n 10.77.0.1:9995 \
  -t maxlife=60 -t expint=10 -t tcp.fin=10 -t udp=30 'not port 9995' &
# 버린 패킷은 NFLOG 그룹 5로 보내고 tcpdump로 읽는다
sudo ip netns exec n7-web iptables -A INPUT -j NFLOG --nflog-group 5 --nflog-prefix REJECT
sudo ip netns exec n7-web iptables -A INPUT -j DROP
sudo ip netns exec n7-web tcpdump -i nflog:5 -nn -l &
```

HTTP 다운로드 하나가 두 줄이다. 요청 방향은 62패킷 3,311바이트, 응답 방향은 66패킷 2.0MB다. 2MB가 66패킷인 건 veth와 호스트의 오프로드(GRO·TSO) 때문에 수출기가 합쳐진 큰 덩어리를 패킷 하나로 봤기 때문이다. 호스트에서 흐름을 만들면 패킷 수는 믿을 수 없고 바이트 수만 믿을 만하다.

`Flags` 칸은 그 흐름에서 본 TCP 플래그를 모두 OR한 값이다. `...AP.SF`는 ACK, PSH, SYN, FIN을 다 봤다는 뜻이니 정상으로 열리고 닫힌 대화다. `......S.`는 SYN만 있고 반대 방향 줄이 없다. 연결 시도가 답을 받지 못했다는 뜻이다. client가 5432번에 보낸 흐름은 패킷이 2개, 길이가 1.025초다. 답이 없어서 커널이 1초 뒤에 SYN을 한 번 더 보낸 흔적이다.

그런데 이 흐름 레코드에는 "막혔다"는 말이 없다. softflowd는 libpcap으로 eth0에 들어온 패킷을 보는데, 이 지점은 방화벽보다 앞이다. 들어온 사실만 알지, 방화벽이 무엇을 했는지는 모른다. SYN만 있고 답이 없으면 막혔거나, 서버가 꺼져 있거나, 응답이 다른 길로 나갔거나 셋 중 하나다. 판정을 알려면 판정을 내린 쪽의 기록이 필요하다. 여기서는 NFLOG가 그 역할을 한다.

### conntrack도 흐름 기록이다

리눅스 커널에도 흐름 캐시가 이미 있다. 방화벽이 쓰는 연결 추적 표(conntrack)다. `nf_conntrack_acct`를 켜면 항목마다 바이트와 패킷을 세고, 항목이 사라질 때 이벤트로 받아 볼 수 있다.

```bash
# 연결 추적 항목에 바이트·패킷 수를 센다 (기본 꺼짐)
sudo ip netns exec n7-web sysctl -w net.netfilter.nf_conntrack_acct=1
# 항목이 사라질 때마다 한 줄씩 출력 (stdbuf: 파일로 돌릴 때 버퍼링 끄기)
sudo ip netns exec n7-web stdbuf -oL conntrack -E -e DESTROY -o timestamp,extended
```

```text
[1792524119.819551]	[DESTROY] ipv4     2 udp      17 src=10.77.0.1 dst=10.77.0.2 sport=53551 dport=53 packets=1 bytes=85 src=10.77.0.2 dst=10.77.0.1 sport=53 dport=53551 packets=1 bytes=89 delta-time=30
[1792524293.903579]	[DESTROY] ipv4     2 tcp      6 TIME_WAIT src=10.77.0.1 dst=10.77.0.2 sport=46572 dport=80 packets=738 bytes=38524 src=10.77.0.2 dst=10.77.0.1 sport=80 dport=46572 packets=1215 bytes=60189371 [ASSURED] delta-time=120
```

NetFlow와 다르게 한 줄에 양방향이 들어 있다. 앞의 `src=`가 처음 연 방향, 뒤의 `src=`가 응답 방향이다. 60MB 다운로드 한 번이 60,189,371바이트로 정확히 잡혔다. 같은 연결을 softflowd는 41.9MB로 기록했다. libpcap이 아직 넘기지 않은 패킷이 버퍼에 남은 상태에서 흐름을 내보냈기 때문이다. 커널 안에서 세는 쪽이 정확하다.

대신 함정이 둘 있다. `delta-time=120`은 연결이 실제로 데이터를 주고받은 시간이 아니라 TIME_WAIT 120초까지 포함한 수명이다. 그리고 방화벽이 버린 연결은 여기에 아예 나오지 않는다. 첫 패킷이 버려지면 conntrack 항목이 확정되기 전에 사라져서 이벤트가 없다. 실제로 5432번 시도 직후 `conntrack -L -p tcp --dport 5432`는 `0 flow entries`였다. conntrack으로 흐름 로그를 만들면 ACCEPT만 남는 셈이다. ulogd2가 이 이벤트를 받아 파일이나 DB로 저장해 주는 데몬이다. conntrack 표 자체의 동작은 [iptables 기본 글](/posts/iptables-basics)에 있다.

그리고 모든 트래픽이 기록되지는 않는다. Amazon 제공 DNS 서버(VPC의 .2 주소)로 가는 질의, 인스턴스 메타데이터(169.254.169.254), Amazon Time Sync(169.254.169.123), DHCP, 기본 VPC 라우터의 예약 주소로 가는 트래픽, 트래픽 미러링으로 복사된 트래픽은 빠진다. "DNS가 이상한데 흐름 로그에 53번이 하나도 없다"는 이상한 게 아니다. DNS 질의 자체를 보려면 Route 53 Resolver 쿼리 로그를 따로 켠다.

### 사용자 지정 형식으로 더 많이 남기기

기본 형식에는 어느 VPC·서브넷·인스턴스인지, 원래 출발지가 누구인지가 없다. 흐름 로그를 만들 때 필드를 골라 형식을 정할 수 있다. 실무에서 자주 넣는 조합은 이렇다.

```text
${version} ${vpc-id} ${subnet-id} ${instance-id} ${interface-id} ${srcaddr} ${dstaddr} ${srcport} ${dstport} ${protocol} ${packets} ${bytes} ${start} ${end} ${action} ${log-status} ${tcp-flags} ${pkt-srcaddr} ${pkt-dstaddr} ${flow-direction} ${traffic-path} ${az-id}
```

`tcp-flags`는 구간 동안 본 플래그를 OR한 숫자다. FIN 1, SYN 2, RST 4, SYN-ACK 18만 기록한다. 짧은 연결은 한 줄에 합쳐져서 SYN-ACK와 FIN이 함께 보인 19 같은 값이 나온다. 인바운드 줄에서 2(SYN)만 계속 쌓이는 출발지는 답을 못 받는 시도, 즉 스캔이나 막힌 연결이다. `pkt-srcaddr`는 NAT 게이트웨이나 로드 밸런서를 지나기 전의 원래 출발지를 알려 준다. `flow-direction`(ingress·egress)과 `traffic-path`(인터넷 게이트웨이, 피어링, 같은 VPC 등 어느 길로 나갔는지)는 비용 분석에 쓴다.

한 번 만든 흐름 로그는 형식을 바꿀 수 없다. 필드를 추가하려면 새 흐름 로그를 만들고 옛것을 지워야 한다. 처음 만들 때 넉넉히 넣는 편이 낫다.

## 누가 누구와 이야기하나

처음 장면으로 돌아가자. 2주치 흐름 로그에서 DB의 5432번으로 들어온 출발지를 세면 된다. CloudWatch Logs에 보냈다면 Logs Insights가 기본 형식의 필드를 알아서 나눠 준다(`srcAddr`, `dstPort`, `action` 같은 이름으로).

```text
filter dstAddr = "10.0.3.20" and dstPort = 5432 and action = "ACCEPT"
| stats sum(bytes) as total, count(*) as records by srcAddr
| sort total desc
| limit 20
```

반대로 막히고 있는 시도를 보려면 `action = "REJECT"`로 바꾸고 출발지와 목적지 포트로 묶는다. 인터넷에 열린 ENI의 REJECT는 대부분 22, 23, 3389, 6379번을 두드리는 스캐너라서 그 자체로는 사건이 아니다. 내부 대역(10.0.0.0/8)에서 온 REJECT가 의미 있다. 배포 후에 내부 REJECT가 생겼다면 새로 띄운 서비스가 열리지 않은 포트를 부르고 있는 것이다.

손으로 묶어 볼 때 걸리는 곳이 있다. 응답 방향 줄은 목적지 포트 자리에 상대의 임시 포트가 온다. 출발지·목적지 쌍으로만 묶으면 같은 대화가 두 덩어리로 갈라지고, 포트까지 넣으면 임시 포트마다 갈라진다. 그래서 두 IP를 정렬해 한 쌍으로 만들고, 두 포트 중 작은 쪽을 서비스 포트로 어림하는 방법을 많이 쓴다. 서비스 포트가 임시 포트 범위보다 작다는 가정에 기대는 어림이라, 서비스 포트가 큰 번호(예: 30000번대 NodePort)면 틀린다.

## 다 기록하면 비싸고, 덜 기록하면 놓친다

흐름 로그는 패킷 캡처보다 훨씬 작지만 공짜는 아니다. 레코드 수는 바이트가 아니라 "구간마다 서로 다른 5-튜플의 수"에 비례한다. 큰 파일 하나를 받는 연결은 한 줄이지만, 짧은 연결을 초당 수천 개 여는 서비스, 인터넷 스캐너를 끊임없이 받는 퍼블릭 ENI, 모든 트래픽이 모이는 NAT 게이트웨이는 줄이 폭발한다. 1분 집계로 바꾸면 긴 연결의 줄 수가 10배까지 늘어난다.

그래서 현장에서는 이렇게 조절한다. 보관용은 S3로 보내고(같은 양이면 CloudWatch Logs보다 대개 싸다), Parquet 형식과 시간 단위 파티션을 켜서 Athena로 필요한 날짜만 읽는다. 빠르게 검색해야 하는 몇 개 ENI만 CloudWatch Logs로 보낸다. 모든 ENI에 1분 집계를 켜기보다, 조사할 때만 특정 ENI에 1분 흐름 로그를 추가하는 방법도 있다. 필터를 REJECT만으로 걸면 양이 크게 줄지만, 처음 장면처럼 "누가 실제로 쓰나"를 묻는 데는 쓸 수 없다.

장비 쪽 NetFlow와 sFlow는 다른 방식으로 양을 줄인다. 패킷 N개 중 하나만 보는 샘플링이다. AWS VPC 흐름 로그는 샘플링하지 않고 집계 구간으로 양을 조절하지만, 스위치와 라우터는 1:1000 같은 샘플링이 흔하다. 샘플링이 무엇을 잃는지 실습 캡처로 확인했다. 2MB 다운로드 10번과 작은 요청 200번(연결 210개, 패킷 3,748개)을 찍은 pcap을, softflowd에 샘플링 없이 한 번, 10개 중 1개만 보게(`-s 10`) 한 번 흘렸다. nfdump는 수출기가 알려 준 샘플링 비율만큼 숫자를 곱해서 보여 준다.

```bash
# 같은 pcap을 샘플링 1과 10으로 각각 흐름으로 만든다
softflowd -r mix.pcap -v 9 -n 127.0.0.1:9996 -d
softflowd -r mix.pcap -v 9 -s 10 -n 127.0.0.1:9997 -d
# 각 수집 결과의 요약
nfdump -R samp1 | grep ^Summary
nfdump -R samp10 | grep ^Summary
```

```text
Summary: total flows: 420, total bytes: 20.3 M, total packets: 3748, avg bps: 45.9 M, avg pps: 1061, avg bpp: 5404
Summary: total flows: 228, total bytes: 18.7 M, total packets: 3750, avg bps: 42.4 M, avg pps: 1062, avg bpp: 4980
```

패킷 수(3,748 → 3,750)와 바이트(20.3M → 18.7M, 8% 적음)는 곱해서 거의 맞췄다. 흐름 수는 420에서 228로 거의 반이 사라졌다. 패킷이 6개뿐인 작은 연결은 10개에 하나를 고르는 체에 걸리지 않을 확률이 크고, 걸린 흐름도 패킷 하나만 보고 10을 곱해 "10패킷짜리"로 기록된다. 샘플링된 흐름 데이터는 "누가 대역폭을 많이 쓰나"에는 쓸 만하지만, "이 서버가 저 서버에 한 번이라도 붙었나"나 "스캔 시도가 몇 번이었나"에는 쓸 수 없다. 처음 장면의 질문은 후자다. 그래서 보안 그룹 정리 같은 일에는 샘플링 없는 기록이 필요하다.

## 흐름 로그를 들고 현장에 갈 때

흐름 로그가 답을 주는 질문과 못 주는 질문을 구분해 두면 헛수고가 준다.

잘 맞는 질문은 이렇다. 이 서버에 누가 붙나(규칙을 좁히기 전 영향 조사, [제로 트러스트](/posts/zero-trust-architecture)로 칸을 나누기 전의 현황 파악). 막힌 시도가 어디서 오나(배포 후 내부 REJECT). 어떤 서버가 NAT 게이트웨이나 AZ 간 전송 요금을 만들고 있나(pkt-srcaddr, az-id, traffic-path로 묶기). 사고 후 어느 시점에 어디로 데이터가 나갔나(포렌식).

못 주는 질문도 있다. 왜 느린가(지연과 재전송은 없다. [네트워크 모니터링](/posts/network-monitoring)과 [패킷 캡처](/posts/packet-capture-tcpdump)를 본다). 어느 URL을 불렀나(L7 내용이 없다. 로드 밸런서·프록시 접근 로그를 본다). 지금 막히는가(몇 분 늦게 온다). 보안 그룹과 NACL 중 누가 막았나(action 하나뿐이라, 같은 연결의 양방향 줄을 맞춰 봐야 한다. 이 방법은 [보안 그룹과 NACL 글](/posts/security-groups-nacl)에 있다).

자주 하는 실수도 몇 가지 있다.

REJECT가 많다고 놀란다. 인터넷에 열린 ENI라면 정상이다. 출발지를 내부 대역으로 좁혀서 본다.

응답 줄의 포트를 서비스 포트로 읽는다. egress 줄의 srcport 80은 "80번에서 보냈다"는 뜻이니, 서비스는 내 쪽에 있다. 방향(flow-direction)을 넣어 두면 덜 헷갈린다.

흐름 로그가 없어서 장애 시점을 못 본다. 흐름 로그는 켠 시점부터만 남는다. 사고가 난 뒤에 켜면 사고는 기록에 없다. 적어도 VPC 단위로 REJECT라도 평소에 켜 두고, 보관 기간을 정해 둔다.

## 다시 보안 그룹 앞에서

2주치 흐름 로그에서 DB의 5432번으로 ACCEPT된 출발지는 셋이었다고 하자. 앱 서버 대역, 결제 배치, 그리고 아무도 기억 못 하던 데이터 추출 서버 하나. 이 셋을 보안 그룹 참조로 바꾸고 `10.0.0.0/16`을 지운 뒤, 일주일 동안 같은 ENI의 REJECT를 지켜본다. 흐름 로그는 패킷을 다 버리고 대화의 요약만 남기기 때문에 오래, 넓게 켜 둘 수 있고, 그래서 "누가 누구와 이야기하나"라는 질문에 답할 수 있다. 연결 하나 안에서 어느 구간이 느렸는지는 다른 질문이고, 그건 [분산 추적](/posts/distributed-tracing)이 답한다.

## 면접에서 나올 만한 질문

### 흐름 로그는 패킷 캡처나 지표와 무엇이 다른가요?

흐름 로그는 같은 5-튜플(출발지·목적지 IP와 포트, 프로토콜)의 패킷을 묶어 대화마다 패킷 수, 바이트, 시작·끝 시각, 판정만 남긴다. 패킷 캡처는 내용까지 다 남아 너무 커서 짧게만 켤 수 있고, 지표는 작지만 누가 누구와 통신했는지가 없다. 흐름 로그는 그 중간이라 몇 주씩 넓게 켜 두고 "누가 누구와 이야기하나"를 답할 수 있다.

### VPC 흐름 로그에서 같은 연결이 두 줄로 나오는 이유는?

흐름 로그가 방향마다 따로 기록하기 때문이다. 요청 방향과 응답 방향은 출발지와 목적지가 뒤집혀 5-튜플이 다르다. 게다가 같은 VPC 안의 두 인스턴스 사이라면 보내는 ENI와 받는 ENI에 각각 남아서 최대 네 줄이 된다. 집계 구간보다 긴 연결은 구간마다 또 나뉜다.

### 흐름 로그로 보안 그룹과 NACL 중 어디서 막혔는지 알 수 있나요?

action 필드만으로는 모른다. 둘 중 하나라도 막으면 REJECT다. 같은 연결의 들어오는 줄이 ACCEPT인데 나가는 응답 줄이 REJECT라면, 보안 그룹은 응답을 상태로 기억해 통과시키므로 NACL 아웃바운드가 범인이다. 들어오는 줄부터 REJECT면 보안 그룹이나 NACL 인바운드를 차례로 확인한다.

### NAT 게이트웨이 비용이 갑자기 늘었습니다. 흐름 로그로 어떻게 찾나요?

NAT 게이트웨이 ENI의 흐름 로그에서 들어오는 줄을 원래 출발지별로 묶어 바이트를 더한다. NAT를 지난 줄의 srcaddr은 NAT 게이트웨이 자신이라, 사용자 지정 형식에 pkt-srcaddr을 넣어 두어야 원래 서버를 알 수 있다. 목적지가 S3나 DynamoDB라면 게이트웨이 엔드포인트로 돌려 NAT를 거치지 않게 하는 것이 흔한 해결이다.

### 흐름 로그에 DNS 질의가 하나도 보이지 않는데 정상인가요?

Amazon 제공 DNS(VPC의 .2 주소)로 가는 트래픽은 흐름 로그에 기록되지 않으니 정상이다. 메타데이터 서비스, Time Sync, DHCP도 마찬가지다. 질의 내용이 필요하면 Route 53 Resolver 쿼리 로그를 켠다. 직접 운영하는 DNS 서버로 가는 트래픽은 기록된다.

### 샘플링된 흐름 데이터로 할 수 있는 것과 없는 것은?

샘플링된 데이터는 비율만큼 곱해서 총 패킷·바이트, 대역폭을 많이 쓰는 상대를 어림하는 데는 쓸 만하다. 대신 패킷이 적은 짧은 흐름은 통째로 빠지기 쉬워서, 실습에서 1:10 샘플링을 하자 흐름 수가 420개에서 228개로 줄었다. "한 번이라도 통신했나", "스캔 시도가 몇 번이었나" 같은 질문에는 샘플링 없는 기록이 필요하다.

### 흐름 로그를 켜 두면 비용이 어디서 커지나요?

레코드 수는 바이트가 아니라 구간마다 서로 다른 5-튜플 수에 비례하므로, 짧은 연결이 많은 서비스, 스캐너를 받는 퍼블릭 ENI, NAT 게이트웨이에서 커진다. 집계 간격을 1분으로 줄이면 긴 연결의 줄도 늘어난다. 보관은 S3와 Parquet·파티션으로 싸게 하고, 빠른 검색이 필요한 곳만 CloudWatch Logs로 보내며, 조사할 때만 특정 ENI에 세밀한 흐름 로그를 추가하는 식으로 조절한다.
