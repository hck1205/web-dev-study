이 글은 실제 서비스 사례 시리즈의 하나다. 장애 보고서를 쓰는 법은 [포스트모템](/posts/postmortems)에서, 리전 단위로 무너졌을 때 무엇을 준비하는지는 [재해 복구](/posts/disaster-recovery)에서 다뤘다. 여기서는 AWS가 직접 공개한 요약문에 적힌 시각과 문장만으로 그날을 다시 짚는다. 같은 회사가 이후 크게 밀어붙인 셀 구조는 [AWS 셔플 샤딩과 셀 구조](/posts/rw-aws-shuffle-sharding-cells)에서 이어서 본다.

2017년 2월 28일 오전, 미국 동부 버지니아(US-EAST-1) 리전의 Amazon S3가 요청을 처리하지 못했다. S3에 저장소를 기대는 같은 리전의 다른 서비스도 함께 영향을 받았다. AWS가 낸 [Summary of the Amazon S3 Service Disruption in the Northern Virginia (US-EAST-1) Region(AWS, 2017년 2월)](https://aws.amazon.com/message/41926/)이 이 글의 뼈대다. 요약문의 시각은 태평양 표준시(PST)로 적혀 있고, 이 글도 그대로 쓴다. 9:37AM PST는 UTC로 17:37이다.

요약문은 길지 않다. 본문 다섯 문단에 시각 다섯 개, 바꾼 것 네 가지가 들어 있다. 그래서 이 글은 그 문장들을 하나씩 풀어서, 어떤 일반 원리가 그 뒤에 있는지 짚는 쪽으로 간다. 요약문에 없는 숫자(몇 대가 빠졌는지, 오류율이 얼마였는지)는 쓰지 않는다.

## 청구가 느리다는 문제에서 시작했다

S3 팀은 S3 청구 시스템이 예상보다 느리게 진행되는 문제를 디버깅하고 있었다. 9:37AM, 권한을 가진 S3 팀원이 정해진 플레이북(작업 절차서)을 따라 명령 하나를 실행했다. 청구 처리에 쓰이는 S3 하위 시스템 하나에서 서버 몇 대를 빼려는 명령이었다.

명령의 입력값 하나가 잘못 들어갔고, 의도보다 훨씬 많은 서버가 빠졌다. 잘못 빠진 서버들은 다른 S3 하위 시스템 두 개를 떠받치고 있었다.

여기서 눈여겨볼 문장들이 있다. 권한이 있는 사람이었고, 정해진 플레이북을 따랐다. 요약문은 사람을 탓하지 않고 도구를 고친다. [포스트모템](/posts/postmortems)에서 말한 "누구도 탓하지 않는다"가 실제 공개 문서에서 어떻게 보이는지 보여 주는 예다. 같은 실수는 다른 사람이 해도 일어날 수 있었고, 그래서 고칠 곳은 사람이 아니라 사람이 쓰는 도구다.

## 목록이 사라지면 저장된 객체도 못 꺼낸다

잘못 빠진 서버가 떠받치던 두 하위 시스템은 이렇다.

인덱스 하위 시스템은 리전 안 모든 S3 객체의 메타데이터와 위치 정보를 관리한다. GET, LIST, PUT, DELETE 요청 모두에 필요하다. 배치(placement) 하위 시스템은 새 저장 공간을 할당하고, 제대로 돌려면 인덱스 하위 시스템이 살아 있어야 한다. PUT 요청 때 새 객체가 들어갈 자리를 고르는 데 쓴다.

요약문에 따르면 용량의 상당 부분이 빠지자 두 시스템 모두 완전히 다시 시작해야 했다. 다시 시작하는 동안 S3는 요청을 처리하지 못했다.

[객체 저장소 구조](/posts/sd-object-storage-architecture)에서 본 것처럼 객체 저장소는 보통 "메타데이터(이 키의 데이터가 어디 있나)"와 "데이터 자체"를 따로 둔다. 데이터는 디스크에 멀쩡히 있어도, 위치를 알려 주는 쪽이 멈추면 꺼낼 수 없다. AWS의 Andy Warfield가 2023년에 쓴 [Building and operating a pretty big storage system called S3(All Things Distributed, 2023년 7월)](https://www.allthingsdistributed.com/2023/07/building-and-operating-a-pretty-big-storage-system.html)는 S3의 가장 높은 수준의 구성을 REST API를 받는 프런트엔드, 네임스페이스 서비스, 하드 디스크로 가득 찬 저장 플릿, 복제·계층 이동 같은 백그라운드 작업 플릿으로 설명한다. 2017년 요약문의 "인덱스 하위 시스템"과 2023년 글의 "네임스페이스 서비스"가 같은 것인지는 두 글 어디에도 적혀 있지 않으니, 여기서는 둘을 같은 것으로 놓지 않는다.

두 하위 시스템이 어떻게 엮여 있었는지, 그리고 그 위에 무엇이 올라타 있었는지를 그림으로 보면 이렇다. 화살표는 "기댄다"는 방향이다.

## 다시 세우는 데 걸린 시간이 문제였다

요약문은 S3 하위 시스템이 원래 상당한 용량이 빠지거나 고장 나도 고객 영향이 거의 없게 설계돼 있다고 쓴다. 용량을 빼고 바꾸는 일은 S3 출시 때부터 기대어 온 핵심 운영 작업이었다.

그런데 이어지는 문장이 사고의 본체다. 큰 리전에서 인덱스와 배치 하위 시스템을 완전히 다시 시작한 건 여러 해 동안 없었다. 그사이 S3는 크게 자랐고, 이 서비스들을 다시 시작하고 메타데이터 무결성을 검증하는 안전 점검을 돌리는 데 예상보다 오래 걸렸다.

재시작은 평소 하지 않는 일이다. 평소 하지 않는 일은 시간이 얼마나 걸리는지 아무도 모른다. 데이터가 커질수록 재시작 시간도 같이 늘지만, 그걸 재 볼 기회가 없었다. GitHub이 2018년에 "복원 절차는 매일 시험했지만 클러스터 전체를 백업에서 다시 만든 적은 없었다"고 쓴 것([GitHub 2018년 10월 장애](/posts/rw-github-2018-network-partition))과 같은 모양이다. 복구 시간 목표(RTO)는 실제로 해 본 시간으로만 믿을 수 있다.

## 재시작에도 순서가 있다

12:26과 13:18, 13:54 사이의 순서는 의존 관계 그대로다. 배치는 인덱스가 있어야 일할 수 있으니, 인덱스가 먼저 살아나고 그다음 배치가 복구를 시작했다. 읽기(GET)와 삭제는 인덱스만 있으면 되니 먼저 돌아왔고, 새 자리를 골라야 하는 쓰기(PUT)는 마지막이었다.

이건 큰 시스템을 처음부터 다시 띄울 때 늘 생기는 문제다. 의존성 그래프의 바닥부터 차례로 올려야 하고, 바닥이 느리면 위가 전부 기다린다. 평소에는 시스템이 한 번에 다 내려가는 일이 없으니 이 순서가 실제로 몇 분짜리인지 아무도 재 보지 않는다. [재해 복구](/posts/disaster-recovery)에서 리전 복구 계획을 세울 때 "무엇부터 띄우는지"를 적어 두라는 이유다.

재시작 직후에는 몰려드는 요청도 문제다. 클라이언트들이 재시도를 쌓아 두고 있다가 한꺼번에 들어오면, 막 살아난 서비스가 다시 넘어진다. 요약문은 이 부분을 따로 다루지 않으니 S3가 어떻게 막았는지는 알 수 없다. 내 서비스에서는 [서킷 브레이커](/posts/circuit-breaker)와 지수 백오프로 클라이언트 쪽에서 재시도를 흩어 두는 게 기본이다.

## 커질수록 길어지는 재시작

"여러 해 동안 재시작하지 않았고 그사이 크게 자랐다"는 문장이 왜 몇 시간으로 이어지는지, 아주 작은 모형으로 재 봤다. 메타데이터 레코드(키와 위치) n개를 다시 읽으며 레코드마다 체크섬을 계산하는 파이썬 스크립트다. 실제 S3의 검증이 이렇게 생겼다는 뜻이 아니다. 시작할 때 전체를 한 번 훑어야 하는 일은 데이터 크기에 비례해 늘어난다는 걸 보려는 것이다.

```python
# verify.py: 메타데이터 레코드 n개를 다시 읽으며 체크섬을 확인하는 시간을 잰다
import hashlib, sys, time
def build(n):
    return [(f"bucket/key-{i}", f"disk-{i % 997}:{i * 7919 % 1000003}") for i in range(n)]
def verify(records):
    bad = 0
    for key, loc in records:
        if not hashlib.sha256(f"{key}|{loc}".encode()).digest():
            bad += 1
    return bad
for n in map(int, sys.argv[1:]):
    recs = build(n)
    t = time.perf_counter(); verify(recs); dt = time.perf_counter() - t
    print(f"records={n:>9,}  verify={dt:6.2f}s")
```

```bash
python3 verify.py 500000 1000000 4000000   # Python 3.13, 4코어 컨테이너에서 실행
```

```text
records=  500,000  verify=  0.49s
records=1,000,000  verify=  0.85s
records=4,000,000  verify=  3.51s
```

레코드가 8배가 되자 시간도 대략 7배가 됐다. 이 숫자 자체는 의미가 없다. 의미 있는 건 모양이다. 재시작 때 전체를 훑는 단계가 있으면, 재시작 시간은 데이터가 자란 만큼 자란다. 그리고 평소에 재시작하지 않으면 그 시간이 지금 얼마인지 아무도 모른다.

같은 400만 개를 50만 개씩 여덟 칸으로 나누면, 한 칸을 다시 세우는 데는 첫 줄의 0.49초 정도면 된다. 칸이 망가졌을 때 그 칸만 다시 세우면 되고, 칸 하나의 재시작은 평소에도 자주 연습할 수 있는 크기다. 이게 AWS가 요약문에서 말한 셀의 효과다. 칸을 나눠도 전체를 한꺼번에 다시 세우는 시간은 줄지 않으니(병렬로 돌릴 수 있다면 줄어든다), 셀의 이득은 "한 번에 다시 세우는 크기"와 "연습할 수 있는 크기"를 정해 둔다는 데 있다.

## 장애를 알리는 화면도 S3 위에 있었다

요약문의 넷째 문단은 사고 내용과 별개로 많이 인용된다. 사고가 시작된 때부터 11:37AM까지 AWS는 서비스 상태 대시보드(SHD)에서 개별 서비스 상태를 갱신하지 못했다. SHD 관리 콘솔이 Amazon S3에 기대고 있었기 때문이다. 그동안 AWS 트위터 계정(@AWSCloud)과 SHD 배너 문구로 상황을 알렸다. 사고 뒤 SHD 관리 콘솔을 여러 AWS 리전에 걸쳐 돌게 바꿨다고 적었다.

장애를 알리는 도구는 그 장애와 같은 곳에 있으면 안 된다. 당연한 말 같지만, 평소에는 같은 인프라에 올리는 게 편하고 싸다. 상태 페이지, 장애 알림, 온콜 연락처, 런북 문서가 모두 같은 클라우드 리전의 같은 저장소에 있으면, 그 리전이 멈출 때 대응하는 손도 같이 묶인다. GitHub도 2018년 장애에서 내부적으로 쓰던 GitHub Pages 빌드를 멈춰 둔 탓에 설명 글을 늦게 냈다고 썼다. 두 회사 모두 "알리는 길"이 "고장 난 길"과 겹쳐 있었다.

## 바꾼 것 네 가지

요약문 셋째 문단이 바꾼 것을 적는다.

도구에서 용량을 천천히 빼게 바꿨다. 이번 경우 도구가 너무 많은 용량을 너무 빨리 뺄 수 있었다고 썼다.

어떤 하위 시스템이든 필요한 최소 용량 아래로 내려가게 되면 용량 제거를 막는 안전장치를 넣었다. 잘못된 입력이 비슷한 사고를 다시 일으키지 못하게 하려는 것이다.

다른 운영 도구들도 비슷한 안전 점검이 있는지 감사하고 있다고 했다.

핵심 하위 시스템의 복구 시간을 줄이겠다고 했다. 여기서 셀이 처음 나온다. 서비스를 작은 파티션, AWS가 셀(cell)이라 부르는 단위로 쪼개면 가장 큰 서비스나 하위 시스템이라도 복구 절차를 평가하고 철저히 시험할 수 있다. S3가 커지면서 팀은 영향 범위를 줄이고 복구를 개선하려고 서비스 일부를 더 작은 셀로 다시 짜는 일을 상당히 해 왔다. 그런데도 이번에 인덱스의 복구 시간은 예상보다 길었다. 인덱스를 더 잘게 나누는 작업을 그해 뒤에 하려 했는데, 그 우선순위를 올려 곧바로 시작한다고 적었다.

앞의 둘은 도구에 넣는 가드레일이고, 뒤의 하나는 구조를 바꾸는 일이다. 가드레일은 "같은 실수가 같은 사고로 번지지 않게" 하고, 셀은 "다른 실수가 생겨도 다시 세우는 크기를 작게" 한다. 하나만으로는 부족하다는 게 요약문의 구성에서 읽힌다.

## 최소 용량 확인을 직접 짜 보면

요약문의 두 안전장치를 함수로 옮기면 이렇다. 빼려는 수만큼 뺐을 때 어떤 하위 시스템이라도 최소 용량 아래로 내려가면 거절하고, 한 번에 빼는 양이 기준을 넘으면 나눠서 빼게 한다. 아래 숫자는 모두 예시다. AWS는 실제 최소 용량이나 속도 제한 값을 공개하지 않았다.

둘째 테스트가 그날의 모양이다. 사람은 청구 서버만 뺀다고 생각했지만, 입력이 잘못돼 다른 하위 시스템까지 같이 빠지는 명령이 됐다. 최소 용량 확인은 "무엇을 빼려 했나"가 아니라 "빼고 나면 무엇이 남나"를 본다. 그래서 입력이 틀려도 결과를 보고 막을 수 있다. 사람의 의도 대신 결과를 검사하니, 의도가 틀린 경우에도 걸린다.

## 우리 팀의 위험한 명령에 가드를 다는 법

작은 팀은 S3 같은 도구를 만들 일이 없지만, 운영 스크립트는 있다. 서버를 빼는 스크립트, 오래된 데이터를 지우는 배치, 인스턴스 수를 바꾸는 명령. 이런 스크립트 앞에 같은 확인을 붙이는 데 큰 비용이 들지 않는다. Ubuntu 24.04의 bash로 짠 예다.

```bash
#!/usr/bin/env bash
# remove-hosts.sh <subsystem> <count> : 용량을 빼기 전에 최소 용량과 한 번에 뺄 수 있는 양을 확인한다
set -euo pipefail
declare -A CAP=([billing]=40 [index]=400 [placement]=200)   # 지금 살아 있는 서버 수 (예시, 실제로는 조회한다)
declare -A MIN=([billing]=20 [index]=300 [placement]=150)   # 이 아래로는 내려가지 않는다
MAX_PER_RUN=10                                               # 한 번 실행에 뺄 수 있는 최대 수
sub=$1; n=$2
left=$(( CAP[$sub] - n ))
if (( left < MIN[$sub] )); then
  echo "REFUSED: $sub would drop to $left (minimum ${MIN[$sub]})"; exit 1
fi
if (( n > MAX_PER_RUN )); then
  echo "REFUSED: $n hosts in one run (max $MAX_PER_RUN). Split the change."; exit 1
fi
echo "DRY-RUN: would remove $n $sub hosts, $left left (minimum ${MIN[$sub]})"
```

```bash
./remove-hosts.sh billing 4      # 의도한 작업
./remove-hosts.sh index 150      # 잘못 넣은 숫자
./remove-hosts.sh billing 15     # 최소는 지키지만 한 번에 너무 많음
```

```text
DRY-RUN: would remove 4 billing hosts, 36 left (minimum 20)
REFUSED: index would drop to 250 (minimum 300)
REFUSED: 15 hosts in one run (max 10). Split the change.
```

첫 줄의 `DRY-RUN`처럼 기본 동작을 "보여 주기만"으로 두고, 실제 실행은 `--execute` 같은 플래그를 붙여야만 하게 만드는 것도 같은 방향이다. 실행 전에 "남는 수"를 사람 눈앞에 찍어 주면, 잘못 넣은 숫자가 결과 숫자로 드러난다. 실제 운영에서는 `CAP`을 하드코딩하지 말고 로드 밸런서나 오케스트레이터에서 그 순간의 값을 읽어 와야 한다. 최소값은 "피크 트래픽을 견디는 수"로 정하고, 그 숫자를 어디서 가져왔는지 스크립트 주석에 적어 둔다.

<Callout kind="warning">
가드는 우회할 수 있으면 의미가 없다. `--force`로 최소 용량 확인을 건너뛰는 옵션을 만들었다면, 그 옵션을 쓸 때는 두 번째 사람의 확인을 받게 하거나 로그를 남겨 알림이 가게 한다. 장애 중에는 급해서 가드를 끄고 싶어지는데, 그때가 입력을 가장 잘못 넣기 쉬운 때다.
</Callout>

## 요약문이 말하지 않는 것

이 요약문은 회사가 쓴 공개 사과문이자 설명문이다. 무엇이 빠졌을 수 있는지 적어 둔다.

몇 대의 서버가 빠졌는지, 원래 몇 대를 빼려 했는지, 어떤 명령이었는지는 없다. 오류율, 영향받은 고객 수, 금전적 영향도 없다. 인덱스 재시작의 "안전 점검"이 구체적으로 무엇을 확인했는지, 그게 왜 오래 걸렸는지도 "예상보다 오래 걸렸다"는 문장뿐이다. 그 뒤 인덱스를 셀로 더 나누는 작업이 언제 끝났는지, 지금 S3 인덱스가 몇 개의 셀로 나뉘어 있는지는 이 글에서 연 자료로는 확인하지 못했다. AWS가 2023년에 낸 [셀 기반 구조 안내서](https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/reducing-scope-of-impact-with-cell-based-architecture.html)는 AWS 서비스 팀들이 10년 넘게 셀 구조를 써 왔다고만 쓰고, S3의 구체적인 셀 구성은 다루지 않는다.

그래서 이 글은 "S3가 이제 몇 분 안에 복구된다" 같은 말을 하지 않는다. 공개된 건 2017년의 방향뿐이다.

## 리전 하나에 기대는 서비스가 지금 할 일

US-EAST-1 하나에 모든 걸 둔 서비스는 2017년 2월에 S3와 함께 멈췄다. 그렇다고 모든 서비스가 멀티 리전으로 가야 하는 건 아니다. [멀티 리전](/posts/multi-region)은 데이터 복제, 비용, 운영 복잡도가 몇 배로 붙는다. 하루 몇 시간의 리전 장애를 견딜 수 있는 서비스라면, 그 시간 동안 무엇이 되고 무엇이 안 되는지를 알고 받아들이는 편이 싸다.

맞지 않는 조건도 분명하다. 결제나 의료처럼 몇 시간 멈추면 안 되는 서비스는 리전 장애를 설계에 넣어야 한다. 그때 가장 먼저 볼 것은 이 사고에서 막혔던 "새로 만드는 경로"다. 장애가 나면 다른 리전에서 인스턴스를 띄우겠다는 계획이, 그 인스턴스의 이미지나 설정을 장애 난 리전의 S3에서 읽어 오게 돼 있지는 않은지 확인한다.

작은 팀이 당장 가져올 수 있는 건 두 가지다. 하나는 위의 가드처럼 위험한 운영 명령에 "남는 수 확인"과 "한 번에 뺄 수 있는 양"을 넣는 것이다. 다른 하나는 상태 페이지와 장애 연락 수단이 서비스 본체와 다른 곳에 있는지 확인하는 것이다. 상태 페이지를 같은 클라우드의 같은 리전에 직접 올려 두었다면, 그 리전이 멈출 때 상태 페이지도 같이 멈춘다.

비슷한 신호가 보이면 볼 곳은 이 순서다. 여러 서비스가 동시에 같은 리전에서 오류를 내면 각 서비스를 따로 보기 전에 공통 의존(저장소, 인증, DNS)부터 본다. 장애 직전에 누가 어떤 운영 명령을 돌렸는지 감사 로그(예: AWS CloudTrail)에서 확인한다. 클라우드 제공자의 상태 페이지가 "정상"이라고 해도 그 페이지 자체가 갱신되지 못하고 있을 수 있다는 걸 2017년 사례가 보여 준다.

## 면접에서 나올 만한 질문

### 2017년 S3 장애는 무엇이 원인이었나

디버깅 중 정해진 플레이북으로 서버 몇 대를 빼려던 명령에 입력값 하나가 잘못 들어가, 의도보다 많은 서버가 빠졌다. 그 서버들이 인덱스와 배치 하위 시스템을 떠받치고 있었고, 용량이 크게 줄자 두 시스템 모두 완전히 다시 시작해야 했다. 큰 리전에서 여러 해 해 보지 않은 재시작이라 무결성 검증까지 오래 걸렸다.

### 데이터는 디스크에 그대로 있었는데 왜 GET까지 안 됐나

객체의 위치를 아는 인덱스 하위 시스템이 멈췄기 때문이다. 요약문에 따르면 인덱스는 GET, LIST, PUT, DELETE 모두에 필요하다. 메타데이터와 데이터를 나누는 객체 저장소에서는 데이터가 멀쩡해도 위치를 모르면 꺼낼 수 없다.

### 왜 GET은 12:26에, PUT은 13:54에 돌아왔나

의존 순서 때문이다. GET, LIST, DELETE는 인덱스만 있으면 되지만, PUT은 새 자리를 고르는 배치 하위 시스템이 필요하고, 배치는 인덱스가 동작해야 복구를 시작할 수 있었다. 그래서 인덱스가 일부 살아난 12:26에 읽기가 먼저, 13:18 인덱스 완전 복구 뒤 배치가 13:54에 끝나면서 쓰기가 돌아왔다.

### 사고 뒤 AWS가 도구에 넣은 안전장치는

두 가지다. 용량을 더 천천히 빼게 바꿨고, 어떤 하위 시스템이든 최소 용량 아래로 내려가면 제거를 막게 했다. 최소 용량 확인은 사람이 무엇을 의도했는지가 아니라 제거 뒤에 무엇이 남는지를 보니, 입력이 틀려도 결과로 막을 수 있다. 다른 운영 도구들도 같은 점검이 있는지 감사했다.

### 셀 구조는 이 사고와 어떻게 이어지나

셀은 복구 시간을 줄이는 쪽의 대책이다. 서비스를 크기가 정해진 작은 셀로 나누면, 가장 큰 하위 시스템도 재시작과 복구를 실제로 시험할 수 있는 크기가 된다. AWS는 인덱스를 더 잘게 나누는 작업을 앞당긴다고 했다. 도구의 가드레일이 같은 실수를 막는다면, 셀은 다른 실수가 생겨도 다시 세울 크기를 작게 만든다.

### 상태 대시보드 문제에서 얻는 교훈은

장애를 알리는 도구가 장애 난 곳에 기대면 안 된다는 것이다. SHD 관리 콘솔이 S3에 기대고 있어서 11:37까지 개별 서비스 상태를 갱신하지 못했고, AWS는 사고 뒤 이를 여러 리전에서 돌게 바꿨다. 내 서비스의 상태 페이지, 알림, 런북도 본체와 다른 곳에 두는지 확인한다.

### 우리 서비스가 S3 의존이 크다면 멀티 리전으로 가야 하나

먼저 리전이 몇 시간 멈출 때의 비용과 멀티 리전의 상시 비용을 비교해야 한다. 몇 시간을 견딜 수 있으면 의존 목록과 대체 연락 수단을 정리하는 쪽이 싸다. 견딜 수 없다면 데이터 복제뿐 아니라 이미지·설정처럼 "새로 띄우는 데 필요한 것"까지 다른 리전에 있어야 한다. 2017년에 막힌 건 이미 돌던 것보다 새로 만드는 경로였다.
