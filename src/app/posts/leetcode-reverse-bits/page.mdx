[Reverse Bits](https://leetcode.com/problems/reverse-bits/)는 LeetCode 190번이다. 32비트 정수의 비트 순서를 거꾸로 뒤집는다. 맨 아래 비트가 맨 위로, 맨 위 비트가 맨 아래로 간다. 반복문 32번이면 끝나는 문제라 쉬워 보이지만, 언어마다 부호 없는 32비트를 다루는 방법이 달라서 "답은 맞는데 음수로 나온다" 같은 일이 자주 생긴다. 후속 질문인 "여러 번 불린다면"에서는 표와 분할 정복이 나온다.

시프트와 마스크, JavaScript가 비트 연산에서 32비트로 자르는 규칙은 [비트 연산 글](/posts/bit-manipulation#자바스크립트는-비트-연산-앞에서-32비트로-자른다)에서 봤다. 이 글은 문자열 뒤집기부터 다섯 번 만에 끝나는 분할 정복까지 다섯 가지로 풀고, 부호 문제를 언어별로 정리한다. 코드는 Node.js 22, Python 3.13, Java 21에서 직접 돌렸다.

## 서른두 칸을 거울에 비춘다

32비트 정수 `n`이 주어진다. `n`을 32자리 이진수로 쓰고(앞을 0으로 채운다) 그 순서를 뒤집은 수를 돌려준다. 0번 비트가 31번 자리로, 1번 비트가 30번 자리로, 일반적으로 i번 비트가 31 - i번 자리로 간다.

- 폭이 32비트로 고정이다. 13처럼 작은 수라도 앞의 0 28개까지 포함해 뒤집는다. 이게 이 문제에서 가장 많이 틀리는 지점이다.
- 결과는 맨 위 비트가 켜질 수 있다. 부호 없는 정수가 없는 언어(Java, JavaScript의 비트 연산 결과)에서는 이 값이 음수로 보인다. 문제는 언어별로 이 차이를 받아 준다.
- 후속 질문으로 "이 함수가 여러 번 불린다면 어떻게 최적화하나"가 붙어 있다.

입력 폭이 32로 정해져 있어서 어떤 풀이든 O(1)이다. 비교는 "몇 번 연산하나, 메모리를 얼마나 쓰나, 읽기 쉬운가"로 한다.

## 13을 손으로 뒤집으면

예시는 13으로 끝까지 간다. 13은 이진수로 `1101`이다. 32칸에 맞춰 쓰고 뒤집으면 이렇다.

```text
13        00000000000000000000000000001101
뒤집으면  10110000000000000000000000000000
```

뒤집은 값은 `1011` 뒤에 0이 28개 붙은 수, 즉 11 × 2^28 = 2952790016이다. 손으로 할 때 하는 일은 단순하다. 오른쪽 끝부터 한 글자씩 읽어 새 줄의 왼쪽부터 적는다. 여기서 실수하기 쉬운 곳이 바로 보인다. `1101`만 뒤집어 `1011`(11)이라고 답하면 틀린다. 앞의 0 28개가 뒤집혀 뒤로 가야 한다.

32칸은 그림으로 보기에 너무 길어서, 이 글의 그림은 같은 일을 8비트로 줄여서 보여 준다. 8비트로 보면 13은 `00001101`이고 뒤집으면 `10110000` = 176이다. 32비트 풀이는 칸 수만 32로 늘린 것이다.

## 문자열로 뒤집기

가장 먼저 떠오르는 건 손으로 하는 일을 그대로 옮기는 것이다. 32자리 이진 문자열을 만들고, 뒤집고, 다시 수로 읽는다.

```js
function reverseBits(n) {
  const bits = (n >>> 0).toString(2).padStart(32, "0"); // 부호 없이 32자리로
  return parseInt([...bits].reverse().join(""), 2);     // 뒤집어 다시 수로 읽는다
}

console.log(reverseBits(13), reverseBits(1), reverseBits(0));
```

```text
2952790016 2147483648 0
```

`padStart(32, "0")`가 앞의 0을 채워 주니 13도 제대로 뒤집힌다. `n >>> 0`은 음수가 들어왔을 때 부호 없는 32비트로 바꾸는 장치다. 이게 없으면 음수에서 `toString(2)`가 `"-11"` 같은 부호 붙은 문자열을 만든다. `parseInt`로 읽은 결과는 일반 Number라서 2^31 이상이어도 양수로 나온다.

읽기는 쉽지만 문자열을 만들고, 배열로 쪼개고, 뒤집고, 다시 합치고, 파싱한다. 뒤의 측정에서 200만 번에 3.6초가 걸렸다. 가장 빠른 풀이보다 300배 넘게 느리다. 한 번만 쓰는 스크립트라면 상관없지만, 문제가 묻는 비트 조작은 아니다.

## 한 비트씩 꺼내 반대쪽에 쌓는다

문자열 없이 같은 일을 한다. `n & 1`로 맨 아래 비트를 꺼내고, 결과 `res`를 왼쪽으로 한 칸 민 뒤 그 비트를 맨 아래에 붙인다. `n`은 오른쪽으로 한 칸 밀어 다음 비트를 준비한다. 32번 반복하면 n에서 처음 꺼낸 비트는 31번 밀려 맨 위에 가 있다.

```js
function reverseBits(n) {
  let res = 0;
  for (let i = 0; i < 32; i++) {
    res = (res << 1) | (n & 1); // 결과를 한 칸 올리고 n의 맨 아래 비트를 붙인다
    n >>>= 1;                   // 다음 비트를 맨 아래로
  }
  return res >>> 0;             // 부호 없는 32비트로 읽는다
}

console.log(reverseBits(13), reverseBits(1), reverseBits(0), reverseBits(4294967293));
```

```text
2952790016 2147483648 0 3221225471
```

아래 그림은 8비트로 줄인 13을 뒤집는다. 다음을 누를 때마다 오른쪽 끝 칸 하나가 결과의 맨 아래로 들어가고, 결과는 왼쪽으로 한 칸씩 밀린다.

그림의 넷째 단계가 이 풀이에서 가장 중요한 곳이다. n이 0이 됐다고 멈추면 `res`는 `1011`(11)에서 끝난다. 남은 칸 수만큼 0을 붙여 끝까지 밀어야 앞에 있던 0들이 뒤로 간다. 그래서 반복은 `n !== 0`이 아니라 정확히 32번이다.

시간은 32번 반복이라 O(1)(비트 폭 w로 보면 O(w)), 공간은 O(1)이다. 면접에서 이 문제의 기본 답으로 내는 풀이다.

### 여기서는 `>>`를 써도 답이 같다

[Number of 1 Bits](/posts/leetcode-number-of-1-bits)에서는 음수에 `>>`를 쓰면 무한 루프가 났다. 이 풀이에서는 `n >>= 1`로 바꿔도 답이 같다. 반복이 정확히 32번이라, 부호 비트가 왼쪽에 계속 복사되더라도 원래 32비트를 다 꺼낸 뒤에 생긴 비트는 쓰이지 않기 때문이다. 실제로 `>>`로 바꾼 코드에 4294967293(32비트로 -3)을 넣어도 3221225471이 나온다. 그래도 습관은 `>>>`로 들인다. 반복 조건을 바꾸는 순간 같은 함정이 돌아온다.

### 마지막에 부호 없이 다시 읽는 이유

```js
function noUnsigned(n) {
  let res = 0;
  for (let i = 0; i < 32; i++) { res = (res << 1) | (n & 1); n >>>= 1; }
  return res; // >>> 0이 없다
}
console.log(noUnsigned(1), noUnsigned(13));
```

```text
-2147483648 -1342177280
```

JavaScript의 `<<`와 `|`는 결과를 부호 있는 32비트 정수로 낸다. 맨 위 비트가 켜지면 그 값은 음수다. 비트 모양은 정답과 똑같지만 LeetCode의 JavaScript 채점은 부호 없는 값(2147483648)을 기대한다. 마지막에 `>>> 0`으로 같은 비트를 부호 없이 다시 읽는다. 비트는 하나도 바뀌지 않고 해석만 바뀐다.

## 양 끝 비트를 바꾼다

책장의 양 끝을 바꾸는 방법이다. i번 비트와 31 - i번 비트를 바꾸고, i를 하나씩 늘린다. 두 비트가 같으면 바꿔도 같으니 건너뛰고, 다르면 두 자리를 함께 뒤집는다. "두 비트를 함께 뒤집기"는 두 자리가 켜진 마스크와 XOR하면 된다.

```js
function reverseBits(n) {
  for (let i = 0, j = 31; i < j; i++, j--) {
    const a = (n >>> i) & 1, b = (n >>> j) & 1; // 양 끝 비트
    if (a !== b) n ^= (1 << i) | (1 << j);      // 다르면 둘 다 뒤집는다 = 서로 바꾼 것
  }
  return n >>> 0;
}

console.log(reverseBits(13), reverseBits(1), reverseBits(43261596));
```

```text
2952790016 2147483648 964176192
```

반복은 16번이고 칸마다 비교와 XOR가 있다. 시간 O(1), 공간 O(1)이다. 뒤집기를 [투 포인터](/posts/two-pointers-pattern)로 한다는 점에서 배열 뒤집기와 똑같은 모양이라, 처음 보는 사람에게 설명하기 좋다. 하지만 반복마다 시프트 두 번, 비교, 분기가 있어서 측정에서는 한 비트씩 쌓는 풀이보다 5배쯤 느렸다. 분기 예측이 틀리는 일이 잦아서다. 두 비트가 같은지 다른지는 입력마다 무작위로 바뀐다.

## 여러 번 불린다면 바이트 표를 쓴다

후속 질문의 첫 번째 답이다. 0부터 255까지 8비트 값의 뒤집은 결과를 표로 만들어 둔다. 32비트 수는 네 바이트로 나눠, 바이트마다 표에서 뒤집은 값을 꺼낸 뒤 바이트 순서도 거꾸로 놓는다. 맨 아래 바이트를 뒤집은 값은 맨 위 바이트 자리로 간다.

```js
const REV8 = new Uint8Array(256);
for (let i = 0; i < 256; i++) {
  let x = i, r = 0;
  for (let k = 0; k < 8; k++) { r = (r << 1) | (x & 1); x >>= 1; } // 8비트 뒤집기
  REV8[i] = r;
}

function reverseBits(n) {
  return ((REV8[n & 0xff] << 24)          // 맨 아래 바이트 → 맨 위
        | (REV8[(n >>> 8) & 0xff] << 16)
        | (REV8[(n >>> 16) & 0xff] << 8)
        | REV8[n >>> 24]) >>> 0;          // 맨 위 바이트 → 맨 아래
}

console.log(REV8[13], REV8[1], reverseBits(13), reverseBits(43261596));
```

```text
176 128 2952790016 964176192
```

`REV8[13]`이 176이다. 8비트 그림에서 손으로 구한 값과 같다. 표는 256바이트이고 한 번만 만든다. 이후 호출마다 표 조회 네 번과 시프트·OR 몇 번이면 끝나고 반복이 없다. 16비트 표로 키우면 조회가 두 번으로 줄지만 표가 128KB(65536칸 × 2바이트)가 된다. 캐시에 잘 맞는 8비트가 보통 낫다.

LeetCode 토론에서 자주 보이는 다른 답은 "결과를 해시맵에 캐싱한다"다. 같은 입력이 반복해서 들어온다면 맞는 말이지만, 32비트 입력은 40억 가지라 캐시가 잘 맞으려면 입력 분포가 아주 치우쳐 있어야 한다. 바이트 단위 표는 어떤 입력이든 항상 맞는다는 점에서 더 낫다.

## 다섯 번 만에 뒤집는 분할 정복

책장을 묶음째로 옮기는 방법이다. 32비트를 반으로 나눠 위 16비트와 아래 16비트를 바꾼다. 그다음 각 16비트 안에서 8비트 두 덩어리를 바꾸고, 각 8비트 안에서 4비트를, 2비트를, 마지막으로 이웃한 1비트끼리 바꾼다. 다섯 단계가 끝나면 모든 비트가 거울 자리에 가 있다.

```js
function reverseBits(n) {
  n = (n >>> 16) | (n << 16);                                // 16비트 덩어리 둘을 바꾼다
  n = ((n & 0xff00ff00) >>> 8) | ((n & 0x00ff00ff) << 8);    // 8비트씩
  n = ((n & 0xf0f0f0f0) >>> 4) | ((n & 0x0f0f0f0f) << 4);    // 4비트씩
  n = ((n & 0xcccccccc) >>> 2) | ((n & 0x33333333) << 2);    // 2비트씩
  n = ((n & 0xaaaaaaaa) >>> 1) | ((n & 0x55555555) << 1);    // 1비트씩
  return n >>> 0;
}

console.log(reverseBits(13), reverseBits(1), reverseBits(43261596), reverseBits(0xffffffff));
```

```text
2952790016 2147483648 964176192 4294967295
```

마스크가 무엇을 고르는지 보면 읽힌다. `0xf0f0f0f0`은 이진수로 `11110000`이 반복되는 수라 각 바이트의 위 4비트만 고르고, `0x0f0f0f0f`는 아래 4비트만 고른다. 위쪽을 오른쪽으로 4칸, 아래쪽을 왼쪽으로 4칸 밀어 합치면 바이트마다 두 덩어리가 자리를 바꾼다. `0xcc`(`11001100`)와 `0x33`(`00110011`)은 2비트 덩어리, `0xaa`(`10101010`)와 `0x55`(`01010101`)는 1비트를 고른다.

아래 그림은 8비트로 줄여 같은 과정을 보여 준다. 8비트면 4비트, 2비트, 1비트 세 단계다. 칸에는 비트 자리 이름 a~h를 적었고, 기억 칸에는 13(`00001101`)이 실제로 어떻게 바뀌는지 적었다.

32비트는 다섯 단계, 64비트는 여섯 단계다. 폭이 w면 log₂ w단계라서 비트 폭으로 보면 O(log w)다. 반복도 분기도 표도 없이 시프트·AND·OR 스무 번 남짓으로 끝난다. 측정에서 다섯 풀이 중 가장 빨랐다. Java의 `Integer.reverse`도 이런 마스크 교환으로 구현돼 있다.

한 가지 짚어 둘 점이 있다. 첫 줄 `(n >>> 16) | (n << 16)`에는 마스크가 없다. `>>> 16`은 위 16비트를 아래로 내리며 빈자리를 0으로 채우고, `<< 16`은 아래 16비트를 위로 올리며 넘친 비트를 버린다. 둘 다 반대쪽을 저절로 지워 주니 마스크가 필요 없다. 둘째 줄부터는 덩어리가 여러 개라 마스크로 골라야 한다.

### 자리 번호로 보면 왜 다섯 번인가

비트를 보지 말고 자리 번호를 보면 이 풀이가 왜 맞는지 한 번에 보인다. 32자리의 번호는 0~31이라 다섯 비트로 쓸 수 있다. 뒤집기는 i번 자리를 31 - i번으로 보내는 일인데, 31은 `11111`이니 31 - i는 i의 다섯 비트를 모두 뒤집은 값, 즉 `i ^ 31`이다.

```text
i    i의 이진수    31 - i   이진수
0    00000         31       11111
1    00001         30       11110
5    00101         26       11010
13   01101         18       10010
30   11110          1       00001
```

16비트 덩어리를 바꾸면 모든 자리 번호의 16의 자리 비트가 뒤집힌다(i ^ 16). 8비트 덩어리 교환은 8의 자리 비트를, 4·2·1비트 교환은 각각 그 자리 비트를 뒤집는다. 다섯 단계를 다 하면 자리 번호의 다섯 비트가 모두 뒤집혀 i ^ 31이 된다. 단계의 순서는 바꿔도 된다. XOR는 순서와 상관없기 때문이다. 실제로 Java의 `Integer.reverse`는 1, 2, 4비트 교환을 먼저 하고 바이트 순서를 마지막에 뒤집는다.

## Python과 Java로 옮기기

Python과 Java는 한 비트씩 쌓는 풀이로 옮긴다. 두 언어에서 신경 쓸 곳이 정반대다.

```python
class Solution:
    def reverseBits(self, n: int) -> int:
        res = 0
        for _ in range(32):
            res = (res << 1) | (n & 1)  # n의 맨 아래 비트를 res의 맨 아래에 붙인다
            n >>= 1
        return res

    def reverseBitsStr(self, n: int) -> int:
        return int(f"{n:032b}"[::-1], 2)

s = Solution()
print(s.reverseBits(13), s.reverseBits(1), s.reverseBits(43261596))
print(s.reverseBitsStr(13), s.reverseBitsStr(43261596))
print(f"{13:032b}", bin(13))
```

```text
2952790016 2147483648 964176192
2952790016 964176192
00000000000000000000000000001101 0b1101
```

Python 정수는 폭이 없어서 `res << 1`이 32비트를 넘어도 잘리지 않는다. 그래서 정확히 32번만 돌아야 한다. 33번 돌면 답이 두 배가 된다. 반대로 부호 걱정은 없다. 2^31 이상인 값도 그대로 양수다. 문자열 풀이는 `f"{n:032b}"`가 32자리로 0을 채워 주는 게 요점이다. `bin(13)`은 `"0b1101"`이라 앞의 0이 없고 접두어까지 붙어서 그대로 뒤집으면 틀린다.

```java
class Solution {
    public int reverseBits(int n) {
        int res = 0;
        for (int i = 0; i < 32; i++) {
            res = (res << 1) | (n & 1); // n의 맨 아래 비트를 res 쪽으로 옮긴다
            n >>>= 1;
        }
        return res;
    }

    public static void main(String[] args) {
        Solution s = new Solution();
        int r = s.reverseBits(13);
        System.out.println(r + " " + Integer.toUnsignedString(r) + " " + Integer.reverse(13));
        System.out.println(s.reverseBits(1) + " " + s.reverseBits(43261596));
    }
}
```

```text
-1342177280 2952790016 -1342177280
-2147483648 964176192
```

Java의 `int`는 부호 있는 32비트라 맨 위 비트가 켜진 결과는 음수로 찍힌다. 비트 모양은 정답과 같으니 LeetCode의 Java 채점도 이걸 정답으로 받는다. 부호 없는 값으로 보고 싶으면 `Integer.toUnsignedString`을 쓴다. Java에는 `Integer.reverse`라는 내장 함수도 있다. 구현은 위의 분할 정복과 비슷한 마스크 방식이다. 실제 코드라면 이걸 쓰고, 면접에서는 직접 짜 보인다.

두 언어에서 한 비트씩 쌓는 풀이와 다른 방법을 재 봤다. Java는 무작위 32비트 수 200만 개를 세 번 돌려 마지막 회차를, Python은 20만 개를 다섯 번 돌려 가장 빠른 시간을 골랐다.

```text
Java     loop32           38.28ms
Java     Integer.reverse   4.47ms
Python   loop32          843.87ms
Python   format           94.70ms
```

Java의 내장 함수는 반복문보다 8배쯤 빠르다. JIT가 CPU의 바이트 뒤집기 명령 같은 것을 쓸 수 있어서다. Python은 순서가 뒤집힌다. JavaScript에서 300배 느렸던 문자열 풀이가 Python에서는 반복문보다 9배 빠르다. 반복문은 32번 돌 때마다 바이트코드를 실행하지만, `f"{n:032b}"`와 `[::-1]`과 `int(..., 2)`는 모두 C 안에서 한 번에 끝나기 때문이다. Python으로 성능이 필요한 코드를 쓸 때는 "반복을 C로 미룰 수 있나"를 먼저 본다.

## 틀리기 쉬운 곳

### n이 0이 되면 멈추기

```js
function early(n) {
  let res = 0;
  while (n !== 0) { res = (res << 1) | (n & 1); n >>>= 1; } // 32번이 아니다
  return res >>> 0;
}
console.log(early(13), early(1));
```

```text
11 1
```

13에서 11, 1에서 1이 나온다. 정답은 2952790016과 2147483648이다. 앞의 0들을 뒤로 보내지 않았기 때문이다. 1의 개수를 세는 문제에서는 n이 0이 되면 멈춰도 됐지만, 이 문제는 폭 전체를 뒤집는 문제라 남은 0도 자리를 차지한다. 이렇게 멈추고 싶다면 멈춘 뒤 남은 칸 수만큼 `res`를 더 밀어야 한다.

### 문자열 풀이에서 0을 채우지 않기

`(13).toString(2)`는 `"1101"`이라 그대로 뒤집으면 `"1011"`, 11이다. 위의 반복문 실수와 같은 결과다. 32자리로 `padStart`하는 걸 잊으면 안 된다. Python의 `bin(13)`은 `"0b1101"`이라 뒤집으면 `"1011b0"`이 되어 `int(..., 2)`가 에러를 낸다. 에러가 나는 쪽이 차라리 낫다.

### JavaScript에서 결과가 음수로 나온다

앞에서 본 것처럼 `>>> 0`을 빠뜨리면 맨 위 비트가 켜진 결과가 음수로 나온다. 비트는 맞으니 디버깅할 때 이진수로 찍어 보면 같은 모양이라 더 헷갈린다. 숫자가 음수인데 비트가 맞으면 해석 문제다.

### 표 풀이에서 바이트 자리를 그대로 두기

```js
const wrong = (n) =>
  ((REV8[n >>> 24] << 24) | (REV8[(n >>> 16) & 0xff] << 16) | (REV8[(n >>> 8) & 0xff] << 8) | REV8[n & 0xff]) >>> 0;
console.log(wrong(13), wrong(13).toString(2).padStart(32, "0"));
```

```text
176 00000000000000000000000010110000
```

바이트마다 안쪽 비트는 뒤집었지만 바이트의 자리는 그대로 뒀다. 그러면 13의 `1011`이 맨 위가 아니라 맨 아래 바이트에 남아 176이 나온다. 32비트 뒤집기는 "바이트 안의 비트 뒤집기"와 "바이트 순서 뒤집기" 두 가지를 모두 해야 한다. 분할 정복으로 말하면 1·2·4비트 교환만 하고 8·16비트 교환을 빼먹은 셈이다.

### Python에서 33번 돌기

`range(33)`이나 `while` 조건 실수로 한 번 더 돌면 `res`가 한 칸 더 밀려 정확히 두 배가 된다. Python은 32비트로 잘라 주지 않으니 이런 실수가 숨지 않고 큰 수로 드러난다. 그나마 다행이다.

## 면접관이 바꿔 묻는 것

### 64비트라면

한 비트씩 쌓는 풀이는 반복을 64번으로 늘린다. Java는 `long`과 `Long.reverse`를 쓴다. 분할 정복은 첫 줄에 32비트 덩어리 교환을 더하고 마스크를 64비트로 늘려 여섯 단계가 된다. JavaScript는 BigInt로 같은 반복을 돌리되, 시프트 뒤에 `BigInt.asUintN(64, ...)`로 잘라야 한다. BigInt는 자르지 않기 때문이다. 빠르게 하려면 위아래 32비트를 각각 뒤집어 자리를 바꾼다.

```js
function reverse64(n) {                      // n은 BigInt
  n = BigInt.asUintN(64, n);                 // 음수를 64비트 부호 없는 값으로
  let res = 0n;
  for (let i = 0; i < 64; i++) {
    res = (res << 1n) | (n & 1n);
    n >>= 1n;
  }
  return res;
}
console.log(reverse64(13n), reverse64(1n), reverse64(-1n));
```

```text
12682136550675316736n 9223372036854775808n 18446744073709551615n
```

13을 64비트로 뒤집으면 11 × 2^60이고, 1은 2^63이 된다. BigInt는 폭이 없어서 반복을 정확히 64번 하는 것이 곧 64비트로 자르는 일이다. 32비트 Python 풀이와 같은 이치다.

### 비트 순서가 회문인지 묻는다면

뒤집은 값이 원래 값과 같은지 보면 된다. 단, "32비트 전체가 회문"인지 "앞의 0을 뺀 이진수가 회문"인지를 먼저 물어야 한다. 13의 이진수 `1101`은 회문이 아니고, 9의 `1001`은 회문이다. 후자라면 비트 길이 `32 - Math.clz32(n)`만큼만 뒤집어 비교한다.

```js
function isBitPalindrome(n) {
  const len = 32 - Math.clz32(n);          // 앞의 0을 뺀 비트 길이
  let r = 0, x = n;
  for (let i = 0; i < len; i++) { r = (r << 1) | (x & 1); x >>>= 1; }
  return r === n;
}
console.log([9, 13, 5, 0b110011, 6].map(isBitPalindrome));
```

```text
[ true, false, true, true, false ]
```

9(`1001`), 5(`101`), 51(`110011`)은 회문이고 13(`1101`)과 6(`110`)은 아니다. 뒤집는 칸 수만 바꿨을 뿐 반복은 앞의 풀이 그대로다. 0은 길이가 0이라 `r = 0`과 같아 회문으로 나온다. 0을 어떻게 볼지는 면접관에게 묻는다.

### 십진수 자리를 뒤집으라면

[Reverse Integer](/posts/leetcode-reverse-integer)다. 비트 대신 `% 10`과 `/ 10`으로 한 자리씩 꺼내 쌓는다. 한 비트씩 쌓는 풀이와 같은 모양인데, 십진수는 결과가 32비트 범위를 넘을 수 있어서 넘침 검사가 핵심이 된다.

### 실제로 어디에 쓰이나

고속 푸리에 변환(FFT)은 입력을 "인덱스의 비트를 뒤집은 순서"로 재배치한 뒤 계산을 시작한다. 크기 8이면 인덱스 1(`001`)과 4(`100`)가 자리를 바꾼다.

```js
function bitReversalOrder(bits) {
  const size = 1 << bits, out = [];
  for (let i = 0; i < size; i++) {
    let r = 0, x = i;
    for (let k = 0; k < bits; k++) { r = (r << 1) | (x & 1); x >>= 1; } // bits칸만 뒤집는다
    out.push(r);
  }
  return out;
}
console.log(bitReversalOrder(3).join(" "));
```

```text
0 4 2 6 1 5 3 7
```

크기 8짜리 FFT는 입력을 이 순서로 다시 놓는다. 폭이 32가 아니라 3비트일 뿐 이 문제의 풀이와 똑같다. CRC 체크섬의 흔한 구현 중에는 비트를 아래부터 처리하는 반사형(reflected)이 있고, 표준 CRC32가 이 방식이다. 이런 곳에서는 수백만 번 뒤집으니 앞의 측정처럼 표나 분할 정복이 의미가 있다.

같은 패턴의 다른 문제로 [Single Number](/posts/leetcode-single-number), [Counting Bits](/posts/leetcode-counting-bits), [Sum of Two Integers](/posts/leetcode-sum-of-two-integers)가 있다.

정리하면, 이 문제는 "폭 전체를 뒤집는다"는 조건을 잊지 않는 게 절반이고, 나머지 절반은 부호 없는 32비트를 언어마다 어떻게 읽느냐다. 풀이는 한 비트씩 32번 쌓는 것으로 충분하고, 여러 번 불린다면 바이트 표나 다섯 단계 분할 정복으로 바꾼다.

## 면접에서 나올 만한 질문

### 한 비트씩 쌓는 풀이를 설명해 주세요.

결과 `res`를 왼쪽으로 한 칸 밀고, 입력의 맨 아래 비트(`n & 1`)를 붙인 뒤, 입력을 오른쪽으로 한 칸 민다. 이걸 정확히 32번 하면 처음 꺼낸 비트가 31번 밀려 맨 위에 가 있다. 시간과 공간 모두 O(1)이다.

### 왜 n이 0이 될 때까지가 아니라 32번을 돌아야 하나요?

입력의 앞쪽 0들도 뒤집혀 결과의 뒤쪽으로 가야 하기 때문이다. n이 0이 됐을 때 멈추면 그 0들이 자리를 차지하지 못해 13이 11로 나온다. 1의 개수를 세는 문제와 달리 이 문제는 폭 전체가 답에 영향을 준다.

### JavaScript에서 결과가 음수로 나오는데 왜 그런가요?

비트 연산 결과가 부호 있는 32비트 정수라서 맨 위 비트가 켜지면 음수로 해석된다. 비트 모양은 맞으니 마지막에 `>>> 0`을 붙여 부호 없는 값으로 다시 읽으면 된다. Java도 같은 이유로 음수가 나오지만 LeetCode 채점은 그대로 받아 주고, 보고 싶으면 `Integer.toUnsignedString`을 쓴다.

### 이 함수가 아주 여러 번 불린다면 어떻게 최적화하나요?

8비트 뒤집기 표를 256칸 만들어 두고, 네 바이트를 표에서 뒤집은 뒤 바이트 순서도 거꾸로 합친다. 반복 없이 조회 네 번이다. 아니면 16, 8, 4, 2, 1비트 덩어리를 마스크로 차례로 바꾸는 분할 정복으로 다섯 단계에 끝낸다. 측정에서 분할 정복이 한 비트씩 쌓는 풀이보다 4~5배 빨랐다.

### 분할 정복 풀이는 왜 맞나요?

비트 i의 최종 자리 31 - i는 i의 다섯 비트를 모두 뒤집은 값이다. 16비트 덩어리 교환이 i의 맨 위 비트를 뒤집고, 8비트 교환이 그다음 비트를 뒤집는 식으로, 단계마다 자리 번호의 비트 하나씩을 뒤집는다. 다섯 단계를 다 하면 자리 번호의 비트가 모두 뒤집혀 31 - i가 된다.

### Python에서는 무엇을 조심해야 하나요?

정수에 폭이 없어서 32비트로 잘라 주지 않는다. 반복을 정확히 32번 해야 하고, 한 번 더 돌면 결과가 두 배가 된다. 대신 부호 문제는 없다. 문자열로 풀 때는 `bin()` 대신 `f"{n:032b}"`로 32자리를 채운다.
