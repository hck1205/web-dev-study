[Meeting Rooms II](https://leetcode.com/problems/meeting-rooms-ii/)(프리미엄 문제)는 LeetCode 253번이다. 회의 시간 목록을 받고, 모든 회의를 열려면 회의실이 최소 몇 개 필요한지 구한다.

한 사람이 모든 회의에 갈 수 있는지 묻는 [Meeting Rooms](/posts/leetcode-meeting-rooms)(252번)의 다음 단계다. 252번은 "방 하나로 되나"를 물었고, 이 문제는 "몇 개면 되나"를 묻는다. 252번 글에서 사건 스위프와 차분 배열을 자세히 다뤘으니 여기서는 짧게 넘기고, 252번에 없던 최소 힙 풀이와 방 배정 복원에 시간을 쓴다. 구간 문제 전반의 겹침 판정과 경계값은 [구간 문제 패턴](/posts/interval-problems-pattern)에, 힙 자체의 동작은 [힙 글](/posts/ds-heap)에 있다. 코드는 Node.js 22, Python 3.13, Java 21에서 돌렸다.

## 회의실을 몇 개 잡아야 하나

입력 `intervals`는 `[start, end]` 쌍의 목록이다. 필요한 회의실의 최소 개수를 돌려준다.

풀이를 고르는 데 영향을 주는 조건은 이렇다.

- 회의 수는 1 이상 10^4 이하다. O(n²)이면 짝이 5,000만 개라 아슬아슬하고, O(n log n)이면 넉넉하다.
- 시각은 0 이상 10^6 이하이고 `start < end`다. 시각 범위가 좁아서 칸 배열 풀이도 성립한다.
- 회의는 반쯤 열린 구간 `[start, end)`다. 5시에 끝나는 회의와 5시에 시작하는 회의는 같은 방을 쓴다.

마지막 조건은 252번과 같다. 끝점이 닿으면 겹치지 않는다. 이 등호 하나가 이 글의 거의 모든 버그와 연결된다.

## 다섯 회의를 방에 직접 넣어 본다

이 글에서 계속 쓸 예시다.

```text
intervals = [2,7] [0,5] [5,9] [8,11] [3,6]
```

수직선에 놓아 본다.

```text

 |--|--|--|--|--|--|--|--|--|--|--|
 [==============)                      [0,5]
       [==============)                [2,7]
          [========)                   [3,6]
                [===========)          [5,9]
                         [========)    [8,11]
```

3시와 4시 사이를 세로로 그어 보면 `[0,5]`, `[2,7]`, `[3,6]` 세 회의가 동시에 열려 있다. 그러니 방이 3개보다 적으면 안 된다. 3개면 충분한지는 실제로 배정해 봐야 안다.

방 0에는 `[0,5]`와 `[5,9]`가 딱 붙어 들어갔다. 5시에 앞 회의가 나가고 다음 회의가 들어온다. 방 2에는 `[3,6]`과 `[8,11]`이 들어갔다. 방 3개로 끝났고, 위에서 센 "동시에 3개"와 맞는다.

이 손 풀이에 이 문제의 답이 다 들어 있다. 필요한 방 수는 "어느 순간 동시에 열려 있는 회의의 최대 개수"와 같다. 아래 풀이들은 이 최댓값을 얼마나 빠르게 세느냐의 차이다.

## 회의가 시작하는 순간마다 세어 본다

가장 단순하게는 모든 시각에서 열린 회의를 세면 된다. 그런데 시각은 10^6개나 있다. 다 볼 필요가 없다. 최댓값은 반드시 어떤 회의의 시작 시각에서 나온다.

이유는 이렇다. 가장 붐비는 순간 t에 열려 있는 회의들 중 가장 늦게 시작한 회의의 시작 시각을 s라고 하자. 그 회의들은 모두 s 이전에 시작했고 t 이후에 끝나니 s에도 열려 있다. 그러니 s에서 센 값은 t에서 센 값보다 작지 않다.

```js
function minMeetingRooms(intervals) {
  let best = 0;
  for (const [t] of intervals) {            // 회의가 시작하는 순간마다
    let cnt = 0;
    for (const [s, e] of intervals) {
      if (s <= t && t < e) cnt++;           // t에 열려 있다: 시작은 포함, 끝은 제외
    }
    best = Math.max(best, cnt);
  }
  return best;
}
```

`t < e`에 등호가 없는 게 반쯤 열린 구간을 그대로 옮긴 부분이다. 5시에 끝나는 회의는 5시에 이미 나갔다.

시간 O(n²), 공간 O(1)이다. 회의 1만 개(시각 0~10^6, 길이 1~1000의 무작위)를 넣으니 624ms였다. 통과는 할 수 있겠지만 정렬 없이 짝을 다 보는 셈이라 n이 조금만 커져도 버틴다고 말하기 어렵다. 그래도 이 풀이는 아래 빠른 풀이들을 검증하는 기준으로 쓸모가 있다.

## 방마다 비는 시각을 적어 두고 빈 방을 찾는다

손 풀이를 그대로 코드로 옮겨 보자. 회의를 시작 순으로 정렬하고, 방마다 "마지막 회의가 끝나는 시각"을 배열에 적어 둔다. 새 회의가 오면 배열을 앞에서부터 훑어 이미 빈 방(끝 시각이 새 회의 시작 이하)을 찾는다. 있으면 그 방의 끝 시각을 바꾸고, 없으면 방을 하나 추가한다.

```js
function minMeetingRooms(intervals) {
  const a = [...intervals].sort((x, y) => x[0] - y[0]); // 시작 순
  const rooms = [];                                      // 방마다 비는 시각
  for (const [s, e] of a) {
    let i = 0;
    while (i < rooms.length && rooms[i] > s) i++;        // 아직 사용 중인 방은 건너뛴다
    if (i === rooms.length) rooms.push(e);               // 빈 방이 없다: 새로 연다
    else rooms[i] = e;                                   // 빈 방을 이어 쓴다
  }
  return rooms.length;
}
```

아무 빈 방이나 골라도 되는지 의심이 들 수 있다. 된다. 이 코드가 방을 새로 여는 순간을 보자. 회의 `[s, e)`가 왔는데 기존 방 k개가 전부 s보다 늦게 끝난다. 각 방의 마지막 회의는 시작 순 정렬 덕분에 s 이전에 시작했다. 그러면 그 k개 회의와 지금 회의, 모두 k + 1개가 시각 s에 동시에 열려 있다. 어떤 배정을 하든 방이 k + 1개 이상 필요하다는 뜻이다. 코드는 꼭 필요할 때만 방을 늘리니 최솟값을 낸다. 정렬이 시작 순이라는 게 이 논증의 바닥이다.

시간은 정렬 O(n log n)에 회의마다 방 k개를 훑는 O(nk)가 더해진다. 무작위 1만 개에서는 방이 16개뿐이라 3.1ms로 빨랐다. 하지만 모든 회의가 서로 겹치면 k = n이 되어 O(n²)로 떨어진다. `[i, 10^6]` 꼴의 회의 1만 개를 넣으니 32ms였다. 방이 많아지면 훑는 비용이 문제다.

## 가장 먼저 비는 방 하나만 보면 된다

앞 풀이를 다시 보면 빈 방을 찾으려고 모든 방을 훑었다. 그런데 정말 알고 싶은 건 "빈 방이 하나라도 있나"다. 그건 가장 먼저 비는 방 하나만 보면 알 수 있다. 가장 이른 끝 시각도 s보다 늦으면 다른 방은 더 늦으니 빈 방이 없다. 가장 이른 끝 시각이 s 이하면 그 방을 쓰면 된다.

"계속 바뀌는 값들 중 가장 작은 것"을 빠르게 꺼내는 자료구조가 최소 힙이다. 방마다 비는 시각을 힙에 담으면 가장 이른 값을 O(1)에 보고, 꺼내고 넣는 데 O(log k)가 든다.

```js
function minMeetingRooms(intervals) {
  const a = [...intervals].sort((x, y) => x[0] - y[0]); // 시작 순
  const heap = new MinHeap();                            // 방이 비는 시각
  for (const [s, e] of a) {
    if (heap.size && heap.peek() <= s) heap.pop();       // 가장 먼저 비는 방이 비었다: 그 방을 쓴다
    heap.push(e);                                        // 이 회의가 끝나는 시각을 적는다
  }
  return heap.size;                                      // 힙에 남은 원소 수 = 연 방의 수
}
```

`MinHeap`은 배열로 만든 보통의 이진 힙이다(`push`, `pop`, `peek`, `size`). 아래 "힙을 직접 만들어 돌려 본다"에 전체 코드가 있다.

힙의 크기가 곧 방 수라는 게 이 코드의 묘한 부분이다. 빈 방을 이어 쓸 때는 하나 빼고 하나 넣으니 크기가 그대로다. 새 방을 열 때만 하나 넣어서 크기가 1 늘어난다. 그래서 끝까지 돌고 남은 크기가 지금까지 연 방의 수다.

### 하나만 꺼내도 되는 이유와 while로 바꾸면 생기는 일

회의 하나가 올 때 힙에서 많아야 하나만 꺼낸다. 지금 시각에 끝난 방이 여러 개라도 하나만 다시 쓰면 충분하기 때문이다. 나머지 빈 방은 힙에 그대로 두어도 다음 회의 때 다시 맨 위로 올라온다. 이 덕분에 "힙 크기 = 연 방의 수"가 유지된다.

`if`를 `while`로 바꿔 끝난 방을 모두 꺼내면 힙은 "지금 열려 있는 회의"만 담는다. 그 자체로 틀린 생각은 아니다. 다만 그러면 힙 크기가 방 수가 아니라 지금 열린 회의 수라서, 마지막 크기가 아니라 도중의 최댓값을 돌려줘야 한다. `[[0,5],[1,2],[3,4],[6,7]]`에서 세 가지를 돌려 봤다.

```text
while + 마지막 크기 1
while + 도중 최댓값 2
if + 마지막 크기 2
```

답은 2다(`[0,5]`와 `[1,2]`가 동시에 열린다). `while`로 다 꺼내고 마지막 크기를 돌려준 코드만 1을 냈다. 6시 회의가 올 때 앞의 회의가 모두 끝나 힙에 하나만 남았기 때문이다.

## 시작과 끝을 따로 줄 세운다

힙에서 꺼낸 값은 "지금까지 끝난 회의 중 아직 다시 쓰이지 않은 방의 끝 시각"이었다. 그런데 방이 몇 개인지 셀 때는 어느 회의가 어느 방을 쓰는지 몰라도 된다. "지금까지 몇 개가 끝났나"만 알면 된다. 그래서 시작 시각만, 끝 시각만 따로 정렬하고 두 포인터로 훑어도 같은 답이 나온다.

시작 배열을 차례로 보며 새 회의가 시작할 때마다, 끝 배열의 포인터가 가리키는 "아직 반납되지 않은 가장 이른 끝"이 지금 시작 이하인지 본다. 그렇다면 방 하나를 반납받아 이어 쓰고 끝 포인터를 한 칸 옮긴다. 아니면 새 방을 연다.

```js
function minMeetingRooms(intervals) {
  const st = intervals.map(x => x[0]).sort((a, b) => a - b); // 시작만
  const en = intervals.map(x => x[1]).sort((a, b) => a - b); // 끝만
  let rooms = 0, j = 0;                                       // j: 아직 반납받지 않은 가장 이른 끝
  for (let i = 0; i < st.length; i++) {
    if (st[i] >= en[j]) j++;   // 끝난 회의가 있다: 그 방을 이어 쓴다
    else rooms++;              // 빈 방이 없다: 새로 연다
  }
  return rooms;
}
```

## 사건으로 쪼개 세거나 칸에 적는다

나머지 두 풀이는 252번 글의 스위프와 차분 배열을 그대로 가져와서, "2가 되면 멈춘다" 대신 최댓값을 끝까지 센다. 자세한 동작과 같은 시각 사건의 순서 문제는 [Meeting Rooms의 스위프 설명](/posts/leetcode-meeting-rooms)에 있다.

```js
// 사건 스위프: 시작 +1, 끝 -1. 같은 시각이면 끝(-1)을 먼저 처리한다
function minMeetingRoomsSweep(intervals) {
  const ev = [];
  for (const [s, e] of intervals) { ev.push([s, 1]); ev.push([e, -1]); }
  ev.sort((x, y) => x[0] - y[0] || x[1] - y[1]);
  let cur = 0, best = 0;
  for (const [, d] of ev) { cur += d; best = Math.max(best, cur); }
  return best;
}

// 차분 배열: 시각 범위가 좁을 때. [s, e)라 끝 칸 e에서 뺀다
function minMeetingRoomsDiff(intervals) {
  let max = 0;
  for (const [, e] of intervals) max = Math.max(max, e);
  const diff = new Int32Array(max + 1);
  for (const [s, e] of intervals) { diff[s]++; diff[e]--; }
  let cur = 0, best = 0;
  for (let t = 0; t <= max; t++) { cur += diff[t]; if (cur > best) best = cur; }
  return best;
}
```

스위프는 사건 2n개를 정렬해서 O(n log n)이고, 무작위 1만 개에서 11.4ms로 가장 느린 O(n log n) 풀이였다. 쌍 배열을 두 단계 비교자로 정렬하는 비용이다. 시작·끝 따로 정렬 풀이는 사실 이 스위프를 두 배열로 나눠 정렬한 것이다. "같은 시각이면 끝을 먼저"라는 규칙이 `st[i] >= en[j]`의 등호에 들어가 있다.

차분 배열은 O(n + T)로 정렬이 없지만 칸을 10^6개 훑어서 9.6ms였다. 회의 수가 시각 범위보다 훨씬 많을 때 빛난다. 이 아이디어가 주인공인 문제가 [Car Pooling](/posts/leetcode-car-pooling)(1094번)이다. 회의 하나가 방 1개를 쓰는 대신 승객 여러 명을 태운다는 점만 다르다.

스위프를 따로 알아 둘 가치는 확장성에 있다. 회의마다 필요한 의자 수가 다르면 +1 대신 +의자 수를 더하면 된다. 힙 풀이와 두 배열 풀이는 이런 가중치를 받기 어렵다.

## heapq와 PriorityQueue로 옮긴다

힙 풀이를 Python과 Java로 옮겼다. 두 언어 모두 표준 라이브러리에 최소 힙이 있다.

```python
import heapq

def min_meeting_rooms(intervals):
    ends = []                                   # 사용 중인 방이 끝나는 시각 (최소 힙)
    for s, e in sorted(intervals):              # 튜플·리스트는 첫 원소(시작) 기준으로 정렬된다
        if ends and ends[0] <= s:               # 가장 먼저 비는 방이 이미 비었다
            heapq.heapreplace(ends, e)          # 꺼내고 넣기를 한 번에
        else:
            heapq.heappush(ends, e)             # 새 방을 연다
    return len(ends)

print(min_meeting_rooms([[2, 7], [0, 5], [5, 9], [8, 11], [3, 6]]))
print(min_meeting_rooms([]), min_meeting_rooms([[9, 10], [10, 11], [11, 12]]))
```

```text
3
0 1
```

Python은 `sorted`에 키를 주지 않아도 된다. 리스트끼리 비교하면 첫 원소부터 비교하니 시작 순 정렬이 된다(시작이 같으면 끝 순인데, 이 문제에서는 상관없다). `heapq`는 리스트를 힙으로 다루는 함수 모음이라 `ends[0]`이 곧 맨 위다. `heapreplace`는 맨 위를 꺼내고 새 값을 넣는 일을 한 번의 자리 맞춤으로 끝낸다. `heappop` 뒤에 `heappush`를 부르는 것보다 조금 빠르다.

```java
import java.util.*;

public class Main {
    static int minMeetingRooms(int[][] intervals) {
        int[][] a = intervals.clone();                          // 바깥 배열만 복사해 입력 순서를 지킨다
        Arrays.sort(a, (x, y) -> Integer.compare(x[0], y[0]));  // 시작 순
        PriorityQueue<Integer> ends = new PriorityQueue<>();    // 기본이 최소 힙
        for (int[] m : a) {
            if (!ends.isEmpty() && ends.peek() <= m[0]) ends.poll(); // 비는 방을 다시 쓴다
            ends.offer(m[1]);
        }
        return ends.size();
    }

    public static void main(String[] args) {
        System.out.println(minMeetingRooms(new int[][]{{2, 7}, {0, 5}, {5, 9}, {8, 11}, {3, 6}}));
        System.out.println(minMeetingRooms(new int[][]{}) + " " + minMeetingRooms(new int[][]{{9, 10}, {10, 11}, {11, 12}}));
    }
}
```

```text
3
0 1
```

Java에서 짚을 곳이 셋 있다. 첫째, `PriorityQueue`는 기본이 최소 힙이다. 최대 힙이 필요하면 `Collections.reverseOrder()`를 넘긴다. 둘째, 비교자를 `(x, y) -> x[0] - y[0]`처럼 빼기로 쓰는 코드가 흔하다. 이 문제는 시각이 0~10^6이라 넘치지 않지만, 음수와 큰 값이 섞이면 빼기가 `int` 범위를 넘어 부호가 뒤집힌다. `Integer.compare`가 안전하다. 셋째, `PriorityQueue<Integer>`는 값을 박싱해 담는다. `peek() <= m[0]`은 언박싱되어 숫자 비교가 되지만, 두 `Integer`끼리 `==`로 비교하면 객체 비교가 되니 조심한다.

두 배열 풀이를 Java로 쓰면 박싱도 비교자도 사라진다. `int[]`를 `Arrays.sort`로 정렬하면 원시 타입 전용 정렬(듀얼 피벗 퀵 정렬)이 돌고, 객체를 담지 않으니 힙 풀이보다 메모리도 적게 쓴다.

```java
import java.util.*;

public class Two {
    static int minMeetingRooms(int[][] intervals) {
        int n = intervals.length;
        int[] st = new int[n], en = new int[n];
        for (int i = 0; i < n; i++) { st[i] = intervals[i][0]; en[i] = intervals[i][1]; }
        Arrays.sort(st);                     // int[] 정렬은 비교자가 필요 없다
        Arrays.sort(en);
        int rooms = 0, j = 0;
        for (int i = 0; i < n; i++) {
            if (st[i] >= en[j]) j++;         // 끝난 방을 이어 쓴다
            else rooms++;                    // 새 방
        }
        return rooms;
    }

    public static void main(String[] args) {
        System.out.println(minMeetingRooms(new int[][]{{2, 7}, {0, 5}, {5, 9}, {8, 11}, {3, 6}}));
    }
}
```

```text
3
```

JavaScript에는 표준 힙이 없다. LeetCode의 JavaScript 환경은 `@datastructures-js/priority-queue` 라이브러리를 미리 넣어 두어 `MinPriorityQueue`를 쓸 수 있지만, 버전에 따라 꺼낸 값의 모양이 달랐고 다른 플랫폼에는 없을 수 있다. 직접 짤 수 있게 연습해 두거나, 앞의 두 배열 풀이를 쓴다.

## 방 수가 하나씩 어긋나는 코드

### 비교를 `<`로 쓴다

```js
if (heap.size && heap.peek() < s) heap.pop();   // 등호가 빠졌다
```

`[[9,10],[10,11],[11,12]]`에서 2를 낸다. 10시에 끝난 방을 10시 회의가 쓰지 못한다고 본 것이다. 답은 1이다. 두 배열 풀이라면 `st[i] > en[j]`로 쓴 경우가 같은 버그다. 스위프라면 같은 시각에 시작(+1)을 끝(−1)보다 먼저 처리한 경우다. 세 풀이 모두 "끝점이 닿으면 같은 방"이라는 규칙이 다른 모양으로 들어가 있다.

### 정렬을 빠뜨린다

```js
for (const [s, e] of intervals) { /* 정렬하지 않고 입력 순서대로 힙에 넣는다 */ }
```

`[[5,8],[0,3]]`에서 2를 낸다. 8시에 끝나는 방이 힙 맨 위에 있으니 0시 회의는 새 방을 연다. 실제로는 두 회의가 전혀 겹치지 않아 1이다. 힙은 "지금 시작보다 앞서 시작한 회의들"만 담고 있어야 맨 위 하나로 판단할 수 있다. 정렬이 그 전제를 만든다.

### 끝 순으로 정렬한다

구간 문제 중에는 끝 순 정렬이 정답인 것도 있어서([Non-overlapping Intervals](/posts/leetcode-non-overlapping-intervals)) 헷갈리기 쉽다. 이 문제에 끝 순 정렬을 쓰면 `[[2,5],[7,8],[4,8],[1,4]]`에서 3을 낸다. 끝 순으로 `[1,4]`, `[2,5]`, `[7,8]`, `[4,8]`이 되는데, `[7,8]`이 먼저 4시에 빈 방을 가져가 버려서 그보다 앞서 시작하는 `[4,8]`이 쓸 방이 없어진다. 답은 2다. 방을 새로 여는 순간 "모든 방이 지금 시각에 사용 중"이라고 말하려면 앞에 배정된 회의가 모두 지금보다 먼저 시작했어야 한다. 그 보장은 시작 순 정렬에서만 나온다.

### 정렬할 때 비교 함수를 빼먹는다

JavaScript의 `sort()`는 비교 함수가 없으면 원소를 문자열로 바꿔 비교한다. 두 배열 풀이에서 `en.sort()`라고 쓰면 `[5, 6, 7, 9, 11]`이 `[11, 5, 6, 7, 9]`가 된다. 끝 포인터가 11을 먼저 가리키니 방을 이어 쓰지 못하고, 예시에서 5를 낸다. 숫자 배열은 항상 `(a, b) => a - b`를 넘긴다.

### 원래 배열을 그대로 정렬한다

`intervals.sort(...)`는 입력 배열을 바꾼다. 방 수만 돌려주면 문제없어 보이지만, 호출한 쪽이 원래 순서를 써서 회의별 결과를 맞추고 있었다면 망가진다. 이 글의 코드는 `[...intervals]`나 `clone()`으로 복사한 뒤 정렬했다. 면접에서 입력을 바꿔도 되는지 한 번 묻는 것도 좋다.

## 느린 풀이를 기준 삼아 맞춰 본다

위의 틀린 코드들은 예시 하나로는 잘 드러나지 않는다. 등호 버그는 끝점이 닿는 회의가 있어야, 끝 순 정렬 버그는 회의 네 개가 특정 모양으로 놓여야 보인다. 그래서 연습할 때는 맨 처음의 "시작 시각마다 세기"를 정답 기준으로 두고 작은 무작위 입력을 많이 돌린다.

```js
const { bruteForce, heapRooms, twoArrays } = require("./sol.js");

function randomMeetings() {
  const n = Math.floor(Math.random() * 8);          // 0~7개
  const out = [];
  for (let i = 0; i < n; i++) {
    const s = Math.floor(Math.random() * 15);       // 시각을 좁게 잡아야 끝점이 자주 닿는다
    out.push([s, s + 1 + Math.floor(Math.random() * 6)]);
  }
  return out;
}

for (let k = 0; k < 30000; k++) {
  const iv = randomMeetings();
  const want = bruteForce(iv);
  if (heapRooms(iv) !== want || twoArrays(iv) !== want) {
    console.log("반례", JSON.stringify(iv));
    process.exit(1);
  }
}
console.log("30000개 모두 같다");
```

```text
30000개 모두 같다
```

비교를 `<`로 바꾼 힙 코드를 같은 방식으로 돌렸더니 6번째 입력에서 반례 `[[9,13],[13,16],[2,8]]`이 나왔다. 13시에 끝나는 회의와 13시에 시작하는 회의가 들어 있다. 틀린 코드는 2를, 기준 풀이는 1을 냈다. 회의 수를 0개부터 뽑는 것도 일부러다. 빈 입력에서 힙 풀이는 0을 돌려주고, 차분 배열은 길이 1짜리 배열을 만들고 0을 돌려준다. 문제 조건이 n ≥ 1이라도 빈 입력에서 터지지 않는 코드가 낫다.

시작 시각이 같은 회의가 여럿인 경우도 이 무작위 입력에 자주 섞인다. `[[1,5],[1,5],[1,5]]`처럼 같은 회의가 셋이면 방도 셋이다. 힙 풀이에서 두 번째 회의가 올 때 맨 위 값 5는 시작 1보다 크니 새 방을 연다. 시작이 같으면 서로 무조건 겹친다는 사실이 비교식에 이미 들어 있어서 따로 처리할 필요가 없다.

실제 일정 데이터라면 두 가지를 더 본다. 시각이 정수가 아니라 밀리초 타임스탬프나 실수라면 차분 배열은 쓸 수 없고, 정렬 기반 풀이만 남는다. 또 끝 시각이 시작 시각보다 앞선 잘못된 회의(`[5, 3]`)가 섞이면 어느 풀이도 오류를 내지 않고 그 회의를 그대로 계산에 넣는다. 차분 배열이라면 누적 값이 음수가 되는 구간까지 생긴다. 입력을 믿을 수 없는 서비스 코드라면 처음에 걸러 낸다.

## 여섯 풀이를 시간과 쓰임새로 고른다

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 시작 시각마다 세기 | O(n²) | O(1) | 빠른 풀이를 검증하는 기준 |
| 방 목록 훑기 | O(n log n + nk) | O(n) | 방이 적을 게 확실할 때. 배정을 바로 알 수 있다 |
| 최소 힙 | O(n log n) | O(n) | 면접 기본 답. 방 배정 복원으로 넓힐 수 있다 |
| 시작·끝 따로 정렬 | O(n log n) | O(n) | 개수만 필요하고 힙이 없는 언어일 때 |
| 사건 스위프 | O(n log n) | O(n) | 회의마다 가중치(인원, 의자 수)가 있을 때 |
| 차분 배열 | O(n + T) | O(T) | 시각 범위 T가 좁고 회의가 아주 많을 때 |

k는 필요한 방 수, T는 가장 늦은 끝 시각이다. 측정값은 모두 회의 1만 개 기준이다. 힙(4.2ms)과 두 배열(4.7ms)이 비슷했고, 스위프(11.4ms)와 차분 배열(9.6ms)이 그 뒤였다. 방 목록 훑기는 무작위 입력에서 가장 빨랐지만(3.1ms) 모두 겹치는 입력에서 32ms로 무너졌다.

## 어느 회의가 어느 방에 들어갔나

면접관이 "방 수 말고 실제 배정표를 달라"고 하면 개수만 세던 풀이는 쓸 수 없다. 힙 풀이를 넓혀 힙에 끝 시각과 함께 방 번호를 넣는다. 회의를 정렬할 때 원래 인덱스를 들고 가야 결과를 입력 순서로 돌려줄 수 있다.

```python
import heapq

def assign_rooms(intervals):
    order = sorted(range(len(intervals)), key=lambda i: intervals[i][0])
    busy = []          # (끝 시각, 방 번호) 최소 힙
    free = []          # 비어 있는 방 번호 최소 힙
    room = [0] * len(intervals)
    for i in order:
        s, e = intervals[i]
        while busy and busy[0][0] <= s:            # 지금 시각까지 끝난 방을 모두 돌려받는다
            heapq.heappush(free, heapq.heappop(busy)[1])
        r = heapq.heappop(free) if free else len(busy)  # 빈 방이 없으면 새 번호
        room[i] = r
        heapq.heappush(busy, (e, r))
    return room

print(assign_rooms([[2, 7], [0, 5], [5, 9], [8, 11], [3, 6]]))
```

```text
[1, 0, 0, 1, 2]
```

입력 순서대로 `[2,7]`은 방 1, `[0,5]`와 `[5,9]`는 방 0, `[8,11]`은 방 1, `[3,6]`은 방 2다. 무작위 입력 2만 개로 같은 방 안의 회의가 서로 겹치지 않는지, 쓴 방 수가 최솟값과 같은지 확인했다.

여기서는 `while`로 끝난 방을 모두 꺼냈다. 개수만 셀 때와 달리 빈 방들 중 번호가 가장 작은 방을 고르고 싶어서다. 그래서 `free`라는 두 번째 힙이 생겼다. 빈 방이 없을 때 새 번호가 `len(busy)`인 이유는, 그 순간 지금까지 연 방이 전부 `busy`에 있기 때문이다.

배정 그림에서는 `[8,11]`이 방 2로 갔는데 여기서는 방 1로 갔다. 8시에는 방 1(7시에 빔)과 방 2(6시에 빔)가 모두 비어 있다. 그림은 가장 먼저 빈 방을, 이 코드는 번호가 가장 작은 방을 골랐다. 방 수는 어느 쪽이든 3이다. "번호가 가장 작은 빈 방을 쓰고, 빈 방이 없으면 가장 먼저 끝나는 방을 기다린다"는 규칙으로 회의별 방을 시뮬레이션하는 문제가 2402번 Meeting Rooms III다. 이 코드에 "기다리면 회의가 뒤로 밀린다"는 처리만 더하면 된다.

## 조건이 하나씩 붙을 때

### 회의가 실시간으로 들어오고 매번 방 수를 알려 줘야 한다면

예약이 하나 들어올 때마다 "지금까지 예약으로 필요한 방 수"를 답해야 한다면 매번 정렬할 수 없다. 시각을 키로 하는 정렬된 맵(Java `TreeMap`)에 차분 값을 쌓는다. 예약 `[s, e)`가 오면 `s`에 +1, `e`에 −1을 더하고, 맵을 시각 순으로 훑으며 누적 최댓값을 구한다. 예약 하나에 O(n)이지만 정렬은 다시 하지 않는다. 이 형태가 732번 My Calendar III다. 겹치면 거절하는 버전은 [My Calendar I](/posts/leetcode-my-calendar-i)(729번)에서 다룬다.

### 회의 사이에 청소 시간이 필요하다면

방을 쓴 뒤 10분 청소가 필요하면 끝 시각에 10을 더해 힙에 넣는다. 비교식은 그대로다. 사건 스위프라면 끝 사건의 시각을 `e + 10`으로 옮긴다.

### 방이 k개뿐일 때 다 열 수 있나

이 문제의 답이 k 이하인지 보면 된다. 힙 풀이라면 힙 크기가 k를 넘는 순간 바로 `false`를 돌려줄 수 있다. k = 1이 바로 252번이다.

### 가장 붐비는 시간대를 알려 달라면

스위프에서 최댓값이 갱신되는 사건의 시각을 기록하고, 그 다음 사건의 시각까지를 구간으로 돌려준다. 최댓값이 같은 시간대가 여러 개면 갱신 조건을 `>=`로 바꿔 모두 모은다. 힙 풀이로는 시간대를 알기 어렵다. 힙에 남은 값이 어느 순간의 상태인지 흐려지기 때문이다.

### 모두가 비어 있는 시간을 찾으라면

방 수가 아니라 아무 회의도 없는 틈을 찾는 문제다. 스위프에서 누적 값이 0인 구간을 모으면 된다. 직원들의 일정이 따로 주어지는 [Employee Free Time](/posts/leetcode-employee-free-time)(759번, 프리미엄 문제)이 이 변형이다.

같은 묶음에서 이어 볼 문제로는 [Merge Intervals](/posts/leetcode-merge-intervals), [Interval List Intersections](/posts/leetcode-interval-list-intersections)(986번), 질의마다 가장 짧은 구간을 힙으로 찾는 [Minimum Interval to Include Each Query](/posts/leetcode-minimum-interval-to-include-each-query)(1851번)가 있다. 힙에서 "가장 먼저 끝나는 것만 본다"는 생각은 [Task Scheduler](/posts/leetcode-task-scheduler)(621번)에서도 다시 나온다.

## 면접에서 나올 만한 질문

### 필요한 회의실 수는 무엇과 같나요?

어느 순간 동시에 열려 있는 회의의 최대 개수와 같다. 그 순간에 열린 회의는 모두 다른 방이 필요하니 그보다 적을 수 없고, 시작 순으로 배정하면 정확히 그만큼으로 충분하다. 그래서 모든 풀이가 결국 이 최댓값을 세는 방법의 차이다.

### 최소 힙에 무엇을 넣고, 왜 맨 위만 보나요?

방마다 지금 회의가 끝나는 시각을 넣는다. 새 회의가 시작할 때 빈 방이 있는지는 가장 먼저 끝나는 방 하나로 판정된다. 그 방도 아직 사용 중이면 다른 방은 더 늦게 끝나기 때문이다. 그래서 회의 하나에 O(log n)이고 전체는 정렬 포함 O(n log n)이다.

### 왜 시작 순으로 정렬해야 하나요? 끝 순은 안 되나요?

시작 순이어야 새 방을 여는 순간 "기존 방이 모두 지금 시각에 사용 중"이라고 말할 수 있다. 앞에 배정된 회의가 모두 지금보다 먼저 시작했으니, 끝나지 않았다면 지금 열려 있는 것이다. 끝 순으로 정렬하면 늦게 시작하는 회의가 먼저 방을 가져가서 `[[2,5],[7,8],[4,8],[1,4]]`에서 2 대신 3이 나온다.

### 5시에 끝나는 회의와 5시에 시작하는 회의는요?

같은 방을 쓴다. 회의는 반쯤 열린 구간이라 끝 시각에는 이미 나간 것이다. 힙 풀이에서는 `heap.peek() <= s`의 등호, 두 배열 풀이에서는 `st[i] >= en[j]`의 등호, 스위프에서는 같은 시각이면 끝 사건을 먼저 처리하는 규칙이 이걸 담는다.

### 힙 없이 풀 수 있나요?

시작 시각과 끝 시각을 따로 정렬하고 두 포인터로 훑으면 된다. 시작을 하나 볼 때마다 아직 반납받지 않은 가장 이른 끝이 그 시작 이하이면 방을 이어 쓰고, 아니면 새 방을 연다. 복잡도는 같고 JavaScript처럼 표준 힙이 없는 언어에서 짧다. 다만 회의와 방의 연결이 끊어져서 배정표는 만들 수 없다.

### 어느 회의가 어느 방을 쓰는지도 알려 줄 수 있나요?

힙에 끝 시각과 방 번호를 같이 넣고, 원래 인덱스를 들고 정렬한다. 끝난 방 번호를 빈 방 힙에 모아 두면 번호가 가장 작은 빈 방을 고를 수 있다. 빈 방이 없을 때만 새 번호를 준다. 이 확장이 쉬운 게 두 배열 풀이 대신 힙 풀이를 기본으로 익혀 두는 이유다.

### 시각 범위가 작으면 더 빠르게 되나요?

시각이 0~T라면 길이 T + 1짜리 차분 배열에 시작 +1, 끝 −1을 적고 누적 합의 최댓값을 구하면 O(n + T)다. 정렬이 없어서 회의 수가 T보다 훨씬 많을 때 유리하다. 회의가 1만 개인데 T가 10^6이면 칸을 훑는 비용 때문에 오히려 정렬 풀이보다 느렸다.
