<EasyIntro>
  같은 장바구니를 휴대폰과 노트북에서 동시에 고쳤다. 한쪽은 빵을 넣고, 다른 쪽은 우유를 빼고 사과를 넣었다. 두 요청이 서로 다른 서버로 들어가면 서버마다 도착 순서가 달라서, 무엇이 최신인지 도착 순서로는 정할 수 없다.

  가장 쉬운 방법은 시각을 붙여 늦은 쪽을 남기는 것이다. 하지만 이러면 동시에 한 수정 하나가 오류 없이 사라지고, 서버 시계가 조금만 어긋나도 실제로 나중에 한 쪽이 진다. 그래서 값마다 가계도처럼 "어떤 값을 보고 고쳤는지"를 적어 둔다. 한쪽이 다른 쪽의 자손이면 조상을 버리고, 둘이 서로를 모른 채 갈라진 형제면 둘 다 남겨 앱이 합치게 한다.

  장바구니를 그냥 합치면 빵도 사과도 살지만, 뺐던 우유가 되살아나기도 한다. 뺀 것까지 지키려면 누가 무엇을 넣고 뺐는지까지 값 안에 적는 특별한 자료형을 쓴다.
</EasyIntro>

이 시리즈에서 이 글의 자리: 앞 글 [⑬ 링으로 나누고 쿼럼으로 복제하기](/posts/sd-kv-store-partition-replication)에서 키 하나를 서버 세 대에 복제했다. 이 글은 그 세 벌이 서로 다른 값을 들고 있을 때 무엇이 최신인지 가린다. 다음 글은 [⑮ 죽은 노드 알아채기와 대신 받아 두기](/posts/sd-kv-store-failure-handling)이고, 같은 장의 마지막은 [⑯ 쓰기 경로와 읽기 경로](/posts/sd-kv-store-write-read-path)다.

앨리스의 장바구니에는 우유와 달걀이 들어 있다. 앨리스는 출근길 지하철에서 휴대폰으로 빵을 담았다. 같은 시각, 집에 있는 가족이 같은 계정으로 노트북을 열어 우유를 빼고 사과를 넣었다. 두 화면 모두 저장 버튼을 눌렀고 둘 다 "저장했습니다"를 봤다. 잠시 뒤 장바구니를 열면 무엇이 있어야 할까.

서버가 한 대면 고민할 게 없다. 두 요청 중 늦게 도착한 것이 앞의 것을 덮거나, 잠금으로 하나씩 처리한다. 하지만 앞 글의 저장소는 아무 노드나 쓰기를 받고 세 벌을 따로 들고 있다. 휴대폰의 요청과 노트북의 요청이 서로 다른 코디네이터로 가면, 두 쓰기는 서로를 모른 채 복제본에 퍼진다. 이 글은 이 상황에서 쓰기 하나도 조용히 잃지 않는 방법을 만든다.

## 같은 키에 쓰기 두 개가 엇갈리면

복제본 세 대를 Sx, Sy, Sz라고 부르자. 휴대폰의 쓰기는 Sy가, 노트북의 쓰기는 Sz가 받았다. 각자 자기 값을 저장하고 다른 두 대에 전한다. 네트워크 경로가 달라서 Sx에는 노트북 쪽이 먼저, Sy 쪽이 나중에 닿을 수 있다. 잠깐 동안 세 복제본이 서로 다른 값을 갖는다.

## 시각을 붙여 늦은 쪽을 남기면

가장 먼저 떠오르는 근거는 시각이다. 쓰기마다 그 순간의 시각을 붙이고, 두 값을 만나면 시각이 늦은 쪽을 남긴다. 이걸 마지막 쓰기 승리(Last Write Wins, LWW)라고 부른다. 모든 노드가 같은 규칙으로 고르니 결국 같은 값에 도착한다. Cassandra가 기본으로 쓰는 방식이고, 셀(열 값 하나)마다 쓰기 시각을 붙인다.

두 가지가 걸린다. 하나는 이 상황에서 둘 중 하나는 반드시 사라진다는 것이다. 빵을 담은 쓰기와 사과를 담은 쓰기는 둘 다 의미가 있는데 하나만 남는다. 다른 하나는 서버 시계를 믿어야 한다는 것이다. 서버 시계는 NTP로 맞춰도 수 ms에서 수십 ms씩 어긋날 수 있다. 실제로 늦게 일어난 쓰기가 더 이른 시각을 달고 오면 그 쓰기가 진다. 노트북의 쓰기를 받은 노드 시계가 80ms 늦다고 놓고 돌려 봤다.

```text
LWW: 폰 쓰기 12:00:00.120 (시계 +0ms), 노트북 쓰기 12:00:00.150 (시계가 80ms 늦다 → 12:00:00.070으로 찍힘)
LWW 결과 → ["우유","달걀","빵"] (사과가 사라진다)
```

실제로는 노트북이 30ms 늦게 썼는데도 휴대폰 쪽이 남았다. 아무 오류도 나지 않는다. 사용자만 "분명히 넣었는데"라고 말한다. 시계가 왜 어긋나는지, 그리고 시계 없이 순서를 정하는 램포트 시계의 원리는 [시계 어긋남 글](/posts/clock-skew)에서 자세히 다뤘다.

그렇다고 LWW가 나쁜 선택인 것은 아니다. 값이 매번 통째로 바뀌고 마지막 하나만 의미가 있는 데이터, 예를 들어 "마지막으로 본 위치", "프로필 사진 주소" 같은 것은 LWW로 충분하다. 문제는 장바구니처럼 양쪽 수정을 모두 살려야 하는 데이터다.

## 값마다 어디서 왔는지 적어 둔다

시각 대신 쓰는 근거는 "이 값은 어떤 값을 보고 고친 것인가"다. 휴대폰의 값과 노트북의 값은 둘 다 [우유, 달걀]을 보고 고쳤다. 서로를 보지 못했으니 어느 쪽도 다른 쪽을 덮을 자격이 없다. 반대로 휴대폰이 빵을 넣은 뒤 그 결과를 다시 읽고 우유를 뺐다면, 두 번째 값은 첫 번째 값을 보고 만든 것이니 덮어도 된다.

이걸 저장소가 알게 하려면 API가 조금 바뀐다. `get`은 값과 함께 문맥(context)이라는 꼬리표를 돌려준다. 클라이언트는 고친 값을 `put`할 때 그 꼬리표를 그대로 돌려보낸다. 저장소는 꼬리표를 보고 새 값이 어떤 옛 값을 대체하는지 안다. 쓰기는 기존 값을 고치지 않고 꼬리표가 붙은 새 버전을 하나 더 만드는 일이 된다. 이걸 버전 관리(versioning)라고 한다.

비슷한 생각이 관계형 DB에도 있다. [낙관적 잠금](/posts/optimistic-locking)은 행에 버전 번호를 두고 "내가 읽은 버전이 아직 그대로일 때만 고친다"고 한다. 다른 점은 결과다. 낙관적 잠금은 늦은 쪽을 거절하고 다시 하라고 한다. 이 저장소는 가용성을 고른 저장소라서 거절하지 않고 둘 다 받은 뒤, 둘 다 들고 있다가 나중에 합친다.

## 서버마다 칸을 하나씩 둔 시계

꼬리표의 구체적인 모양이 벡터 시계(vector clock)다. 쓰기를 받는 서버마다 칸을 하나씩 두고 숫자를 센다. `{Sx:2, Sy:1}`은 "Sx가 두 번, Sy가 한 번 고친 이력을 담은 값"이라는 뜻이다. 규칙은 둘이다.

- 서버 Si가 쓰기를 받으면, 클라이언트가 보낸 문맥을 복사하고 Si 칸을 1 올린다. 칸이 없으면 1로 만든다.
- 두 버전 X, Y를 비교할 때 X의 모든 칸이 Y의 같은 칸보다 작거나 같으면 X는 Y의 조상이다. Y가 X를 보고 만든 값이니 X를 버려도 된다. 어떤 칸은 X가 크고 어떤 칸은 Y가 크면 둘은 동시(concurrent)다. 어느 쪽도 버리면 안 된다.

앞의 장바구니를 이 규칙으로 실제로 돌려 봤다. 저장소는 키마다 "살아 있는 버전 목록"을 들고, 새 버전이 덮는 옛 버전만 지운다.

```js
// vclock.js (발췌)
const inc = (vc, node) => ({ ...vc, [node]: (vc[node] || 0) + 1 });
function cmp(a, b) {               // "앞" | "뒤" | "같음" | "동시"
  let less = false, more = false;
  for (const k of new Set([...Object.keys(a), ...Object.keys(b)])) {
    const x = a[k] || 0, y = b[k] || 0;
    if (x < y) less = true;
    if (x > y) more = true;
  }
  return less && more ? "동시" : less ? "앞" : more ? "뒤" : "같음";
}
let siblings = [];                 // 이 키의 살아 있는 버전들
function put(node, value, context) {
  const clock = inc(context, node);
  siblings = siblings.filter((s) => cmp(s.clock, clock) !== "앞"); // 새 버전이 덮는 것만 지운다
  siblings.push({ value, clock });
  return clock;
}

const d1 = put("Sx", ["우유"], {});
const d2 = put("Sx", ["우유", "달걀"], d1);
const d3 = put("Sy", ["우유", "달걀", "빵"], d2);  // 휴대폰
const d4 = put("Sz", ["달걀", "사과"], d2);        // 노트북
```

```text
put via Sx ["우유"] → {Sx:1}  | 남은 버전 1개
put via Sx ["우유","달걀"] → {Sx:2}  | 남은 버전 1개
put via Sy ["우유","달걀","빵"] → {Sx:2, Sy:1}  | 남은 버전 1개
put via Sz ["달걀","사과"] → {Sx:2, Sz:1}  | 남은 버전 2개

d3 vs d4: 동시,  d2 vs d3: 앞
get → [["우유","달걀","빵"],["달걀","사과"]] 문맥 {Sx:2, Sy:1, Sz:1}
```

세 번째 줄에서 남은 버전이 1개인 이유는 d3 `{Sx:2, Sy:1}`이 d2 `{Sx:2}`를 모든 칸에서 덮기 때문이다. 네 번째 줄의 d4 `{Sx:2, Sz:1}`은 d3과 비교하면 Sy 칸은 d3이, Sz 칸은 d4가 크다. 동시다. 그래서 둘 다 남는다. 이렇게 함께 남은 버전들을 형제 버전(siblings)이라고 부른다.

## 형제를 합치는 일은 누가 하나

저장소는 둘이 동시라는 것까지만 안다. 빵을 담은 쪽과 사과를 담은 쪽을 어떻게 합쳐야 하는지는 데이터의 의미를 아는 쪽만 정할 수 있다. 그래서 `get`이 형제 여럿을 돌려주고, 앱이 합친 값을 문맥과 함께 다시 쓴다. 장바구니라면 합집합이 자연스럽다. 해 봤다.

```js
// vclock.js (이어서): 앱이 두 형제를 합집합으로 합친다
let r = get();
const union = [...new Set(r.values.flat())];
put("Sx", union, r.ctx);
```

```text
put via Sx ["우유","달걀","빵","사과"] → {Sx:3, Sy:1, Sz:1}  | 남은 버전 1개
get → [["우유","달걀","빵","사과"]]
```

빵도 사과도 살았다. 그런데 결과를 다시 보면 우유가 들어 있다. 노트북에서 분명히 뺐는데 돌아왔다. 합집합은 "넣은 것"만 합치고 "뺀 것"은 기억하지 못한다. 휴대폰 쪽 값에 우유가 남아 있었으니 합집합에 우유가 들어간다. Amazon이 2007년 Dynamo 논문에서 장바구니를 두고 직접 밝힌 한계도 이것이다. 지운 상품이 다시 나타날 수 있다고 적었다. 추가는 절대 잃지 않는 대신, 삭제가 가끔 되살아나는 쪽을 택한 것이다.

삭제까지 제대로 합치려면 "누가 무엇을 넣고 뺐는지"를 값 안에 함께 적어야 한다. 원소마다 넣은 기록에 고유한 꼬리표를 붙이고, 빼는 쓰기는 자기가 본 꼬리표만 지우게 하면 된다. 그렇게 설계해서 어떤 순서로 합쳐도 같은 결과가 나오는 자료형이 [CRDT](/posts/crdt)이고, 장바구니에 맞는 것은 OR-Set이다. Riak은 2.0부터 이런 자료형을 저장소에 직접 넣어, 앱이 합치는 코드를 짜지 않아도 되게 했다.

꼭 읽을 때 합칠 필요는 없다. 다음 쓰기 때 합쳐도 되고, 형제가 있는 줄 모르는 클라이언트가 문맥 없이 쓰면 그 값은 또 하나의 형제가 된다. 문맥을 빼먹는 클라이언트가 많으면 형제가 계속 쌓인다. Riak은 이걸 형제 폭증(sibling explosion)이라고 부르며, 2.x 설정에 형제 수 경고 기준(기본 25)과 상한(기본 100)을 둔다. 형제 수가 경고 기준을 넘는 키가 보이면 대개 문맥을 돌려보내지 않는 클라이언트가 원인이다.

## 칸에 누구 이름을 적을까

벡터 시계의 칸을 누구 이름으로 만들지도 고를 일이다. 클라이언트마다 칸을 두면 "누가 무엇을 봤는지"가 정확하지만 칸이 끝없이 늘어난다. 서버마다 칸을 두면 칸 수가 서버 수를 넘지 않는다. 쓰기 1000번을 무작위 클라이언트 5000명 중 하나가 했다고 두고 칸 수를 세 봤다.

```text
쓰기 1000번 뒤 칸 수: 클라이언트 id로 적으면 907칸, 서버 id로 적으면 3칸
```

907칸짜리 꼬리표를 값마다 붙이고 다닐 수는 없다. 그래서 Dynamo와 초기 Riak은 서버 이름으로 칸을 만들었다. 그런데 서버 이름으로만 세면 새 구멍이 생긴다. 두 클라이언트가 같은 문맥 `{Sx:2}`를 들고 같은 서버 Sx로 동시에 쓰는 경우다.

```js
// samenode.js (발췌)
const ctx = { Sx: 2 };
// 클라이언트가 준 문맥에서 Sx 칸만 +1 하면
const naive1 = { ...ctx, Sx: ctx.Sx + 1 }, naive2 = { ...ctx, Sx: ctx.Sx + 1 };
// 서버가 자기 카운터를 따로 들고 올리면
let sxCounter = 2;
const stamp = (c) => ({ ...c, Sx: ++sxCounter });
const ok1 = stamp(ctx), ok2 = stamp(ctx);
// 이 쓰기의 이름(dot)과, 쓸 때 보던 문맥(ctx)을 나누면
const w1 = { dot: ["Sx", 3], ctx: { Sx: 2 } }, w2 = { dot: ["Sx", 4], ctx: { Sx: 2 } };
const covers = (w, other) => (w.ctx[other.dot[0]] || 0) >= other.dot[1];
```

```text
순진한 방법: {"Sx":3} {"Sx":3} → 시계가 같아 한쪽이 다른 쪽을 덮는다
서버 카운터: {"Sx":3} {"Sx":4}
ok1 ≤ ok2 ? true → 실제로는 동시인데 앞뒤로 판정된다
w2가 w1을 봤나? false  w1이 w2를 봤나? false → 둘 다 남긴다
```

첫 줄은 두 쓰기가 똑같은 시계를 받아 하나가 사라진다. 둘째 줄처럼 서버가 자기 카운터를 올려도, `{Sx:4}`가 `{Sx:3}`을 덮는 것처럼 보여서 역시 하나가 사라진다. 두 쓰기 모두 `{Sx:2}`까지만 봤는데 말이다. 마지막 줄이 해결책이다. 쓰기 하나에 "Sx의 4번째 쓰기" 같은 이름(dot)을 따로 붙이고, 그 쓰기가 본 문맥과 나눠 둔다. w2의 문맥은 Sx 2까지만 봤으니 Sx 3번째 쓰기인 w1을 못 봤다는 걸 정확히 안다. 이 구조를 Dotted Version Vector라고 부르고, Riak 2.0이 이걸로 바꿨다.

## 시계가 길어지면 잘라야 한다

서버 이름으로 칸을 만들어도, 링에서 노드가 바뀌거나 느슨한 쿼럼으로 다른 노드가 쓰기를 대신 받으면 한 키에 칸이 계속 늘 수 있다. Dynamo 논문은 칸이 10개를 넘으면 가장 오래된 칸부터 버린다고 적었다. 칸마다 마지막으로 고친 시각을 함께 적어 두고 그걸로 오래된 것을 고른다.

잘라내기의 대가는 판정이 틀어질 수 있다는 것이다. 칸을 지우면 원래 조상이던 버전이 동시로 보일 수 있다.

```text
잘라내기 전: old vs full = 앞
잘라내기 후: old vs trimmed = 동시  (원래 앞이었는데 동시로 보인다)
```

`full`이 `{Sx:1, Sy:1, Sz:1}`이고 `old`가 `{Sx:1}`이면 old는 조상이다. full에서 Sx 칸을 잘라 `{Sy:1, Sz:1}`로 만들면 old의 Sx 칸이 더 커져 동시가 된다. 필요 없는 형제가 하나 더 생긴다는 뜻이다. 다행히 반대 방향, 즉 동시인 것을 앞뒤로 잘못 보고 쓰기를 버리는 일은 이 경우 생기지 않는다. 형제가 늘어 앱이 한 번 더 합치는 정도로 끝난다. Dynamo 논문도 운영 중 이 문제가 드러나지 않았다고 적었다.

## 어떤 방법을 고르나

면접에서 "충돌을 어떻게 해결하나요"라는 질문에 벡터 시계 하나만 답하면 다음 질문이 이어진다. 그럼 왜 Cassandra는 안 쓰나요. 그래서 선택지를 나란히 두고 말할 수 있어야 한다.

| 방법 | 쓰기를 잃나 | 앱이 할 일 | 맞는 데이터 |
|---|---|---|---|
| 마지막 쓰기 승리 | 동시 쓰기 중 하나를 잃는다 | 없다 | 마지막 값 하나만 의미 있는 것 (위치, 상태 값) |
| 벡터 시계와 형제 | 안 잃는다. 삭제가 되살아날 수 있다 | 형제를 읽고 합쳐서 다시 쓴다 | 장바구니처럼 합칠 규칙이 분명한 것 |
| CRDT | 안 잃는다. 삭제도 지킨다 | 자료형을 고른다 | 카운터, 집합, 협업 문서 |
| 조건부 쓰기 | 늦은 쪽을 거절한다 | 거절되면 다시 읽고 다시 쓴다 | 재고, 잔액처럼 충돌을 허용하면 안 되는 것 |

마지막 줄은 이 시리즈의 저장소와 방향이 다르다. DynamoDB는 Dynamo 논문과 이름이 비슷하지만 사용자에게 형제를 돌려주지 않는다. 대신 "버전 속성이 내가 읽은 값일 때만 써라" 같은 조건부 쓰기를 주고, 기본은 항목 단위로 마지막 쓰기가 남는다. 충돌을 허용하지 않는 쪽을 고른 것이다. 같은 키-값 저장소라도 어떤 약속을 하느냐는 제품마다 다르다.

## 현장에서 버전 문제가 드러나는 모양

증상은 대개 사용자 문의로 먼저 온다. 저장소 쪽에는 오류 로그가 없다는 점이 공통이다.

"넣은 상품이 사라졌다"는 쓰기를 잃었다는 뜻이다. 마지막 쓰기 승리를 쓰는 저장소라면 먼저 서버 시계를 의심한다. 각 노드에서 시계가 얼마나 어긋났는지 본다.

```bash
# 각 노드에서: NTP 기준 시계와의 차이 (Ubuntu 24.04의 chrony)
chronyc tracking | grep -E "System time|Last offset"
```

Cassandra라면 값마다 붙은 쓰기 시각을 직접 볼 수 있다. 사라졌다는 값을 덮은 쓰기의 시각이 실제 요청 시각과 어긋나 있으면 시계 문제다. Cassandra에서는 이 시각을 서버가 아니라 드라이버, 즉 앱 서버 쪽에서 붙이는 경우가 많으니 앱 서버들의 시계도 함께 본다.

```sql
-- CQL: 셀마다 붙은 쓰기 시각(마이크로초)을 함께 읽는다
-- items는 text 열이라고 가정한다 (컬렉션 열은 버전에 따라 WRITETIME을 쓸 수 없다)
SELECT user_id, items, WRITETIME(items) FROM shop.carts WHERE user_id = 'alice';
```

"지운 상품이 다시 나타난다"는 반대다. 형제를 합집합으로 합치고 있거나, 삭제 기록이 너무 일찍 정리됐다는 뜻이다. 앞쪽이면 합치는 규칙을 CRDT로 바꾸고, 뒤쪽은 [⑮ 장애 처리](/posts/sd-kv-store-failure-handling)의 복구 작업과 툼스톤 보관 기간을 본다.

"응답이 점점 커지고 느려진다"는 형제 폭증일 가능성이 크다. 형제 수가 많은 키를 찾아 그 키를 쓰는 클라이언트가 문맥을 돌려보내는지 확인한다. 읽고 고치고 쓰는 흐름이 아니라 그냥 덮어쓰는 코드가 범인인 경우가 많다.

## 다음에 읽을 글

동시 쓰기를 가려내는 법까지 왔다. 벡터 시계는 두 버전이 앞뒤인지 동시인지 알려 주고, 동시면 둘 다 남겨 앱에 넘긴다. 하지만 지금까지는 모든 노드가 살아 있다고 가정했다. 다음 글 [⑮ 죽은 노드 알아채기와 대신 받아 두기](/posts/sd-kv-store-failure-handling)에서는 노드가 죽었다는 걸 어떻게 아는지, 담당 노드가 죽었을 때 쓰기를 누가 대신 받는지, 다시 살아난 노드가 놓친 것을 어떻게 채우는지 본다.

충돌 없는 자료형은 [CRDT](/posts/crdt), 사용자 한 명이 기대하는 일관성 보장은 [최종 일관성](/posts/eventual-consistency)에서 이어진다.

## 면접에서 나올 만한 질문

### 같은 키를 두 곳에서 동시에 고치면 어떻게 되나요?

리더 없이 여러 노드가 쓰기를 받는 저장소에서는 두 값이 서로를 모른 채 복제본에 퍼진다. 저장소는 둘 중 무엇을 남길지 정해야 하는데, 도착 순서는 노드마다 달라서 기준이 될 수 없다. 그래서 값마다 근거를 붙인다. 시각을 붙여 늦은 쪽을 남기거나, 벡터 시계로 동시인지 가려 둘 다 남긴다.

### 마지막 쓰기 승리는 왜 위험한가요?

동시 쓰기 중 하나를 오류 없이 버린다. 게다가 서버 시계가 어긋나면 실제로 나중에 한 쓰기가 더 이른 시각을 달고 와서 진다. 80ms 늦은 시계 하나로 30ms 뒤에 한 쓰기가 사라졌다. 그래도 마지막 값 하나만 의미 있는 데이터에는 단순하고 충분하다.

### 벡터 시계로 어떻게 충돌을 알아내나요?

쓰기를 받은 서버마다 칸을 두고 그 서버 칸의 숫자를 올린다. 두 버전의 모든 칸이 한쪽이 작거나 같으면 그쪽이 조상이라 버려도 되고, 칸마다 크고 작음이 엇갈리면 서로를 보지 못한 동시 쓰기다. 동시면 형제로 둘 다 남기고 읽을 때 함께 돌려준다.

### 형제 버전은 누가 합치나요? 장바구니는 어떻게 합치나요?

데이터의 뜻을 아는 앱이 합친다. 읽기에서 형제와 문맥을 받고, 합친 값을 그 문맥과 함께 다시 쓰면 새 버전이 형제를 모두 덮는다. 장바구니는 합집합이 자연스럽지만 삭제를 기억하지 못해 지운 상품이 되살아날 수 있다. 삭제까지 지키려면 OR-Set 같은 CRDT를 쓴다.

### 벡터 시계의 칸은 클라이언트 기준인가요, 서버 기준인가요?

서버 기준이 보통이다. 클라이언트 기준은 정확하지만 칸이 끝없이 늘어나 실험에서 쓰기 1000번에 907칸이 됐다. 서버 기준은 칸 수가 작지만, 같은 서버로 들어온 동시 쓰기 두 개를 앞뒤로 잘못 보는 구멍이 있다. 쓰기마다 고유한 dot을 붙이고 본 문맥과 나누는 Dotted Version Vector가 이걸 막는다.

### 벡터 시계가 너무 커지면 어떻게 하나요?

칸 수 상한을 두고 가장 오래 안 바뀐 칸부터 자른다. 자르면 원래 조상이던 버전이 동시로 보여 불필요한 형제가 생길 수 있지만, 동시인 쓰기를 앞뒤로 착각해 버리는 일은 생기지 않는다. 그래서 대가는 앱이 한 번 더 합치는 정도다.

### 형제 수가 계속 늘어나면 무엇을 의심하나요?

문맥을 돌려보내지 않고 덮어쓰는 클라이언트를 먼저 의심한다. 문맥 없는 쓰기는 어떤 버전도 덮지 못하므로 매번 형제가 하나씩 는다. 값이 커져 읽기가 느려지고 저장소가 상한에 걸리기도 한다. 쓰는 코드가 읽고, 합치고, 문맥과 함께 쓰는 순서를 지키는지 확인한다.

### 충돌을 아예 허용하지 않으려면요?

조건부 쓰기나 합의 기반 저장소를 쓴다. "내가 읽은 버전일 때만 써라"를 걸면 늦은 쪽이 거절되고 다시 시도한다. DynamoDB의 조건식이나 etcd의 트랜잭션이 이런 방식이다. 대신 네트워크가 끊긴 쪽에서는 쓰기를 받지 못하니 가용성을 일부 내준다. 재고나 잔액처럼 틀리면 안 되는 값에 맞다.
