서버 여러 대가 단방향 링크로 묶여 있고, 한 서버가 보낸 신호가 전체에 퍼지는 데 얼마나 걸리는지 묻는 문제다. 실은 출발점 하나에서 모든 노드까지의 최단 거리를 구한 뒤 그중 가장 큰 값을 고르는 문제이고, 최단 경로 알고리즘을 처음 코드로 짜 보기에 딱 좋은 크기다.

[LeetCode 743. Network Delay Time](https://leetcode.com/problems/network-delay-time/)은 Medium이다. 이 글은 길을 전부 따라가 보는 DFS부터 플로이드-워셜, 벨만-포드, SPFA, 배열 다익스트라, 힙 다익스트라까지 여섯 가지 풀이를 느린 순서대로 짠다. 알고리즘의 증명과 일반론은 [최단 경로 알고리즘 글](/posts/shortest-path-algorithms)에 있으니 여기서는 이 문제에 맞춰 쓰는 법과 틀리는 지점에 집중한다. 힙 자체는 [힙 글](/posts/ds-heap)에서 다뤘다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 신호가 가장 늦게 닿는 노드를 찾는다

노드는 1부터 n까지 번호가 붙어 있다. `times`의 각 원소 `[u, v, w]`는 u에서 v로 가는 단방향 링크이고 신호가 지나가는 데 w만큼 걸린다. 노드 k에서 신호를 보냈을 때 모든 노드가 신호를 받는 데 걸리는 최소 시간을 구한다. 어떤 노드에 끝내 닿지 못하면 -1이다.

풀이를 고를 때 보는 조건은 이렇다.

- n은 100 이하, 간선은 6,000개 이하다. 노드가 적어서 O(n³)인 플로이드-워셜도 100만 번이면 끝난다. 이 문제는 어떤 풀이로도 통과하기 쉽고, 그래서 풀이끼리 비교하기 좋다.
- 무게 w는 0 이상 100 이하다. 음수가 없으니 다익스트라가 성립한다. 0도 있다는 점은 뒤에서 한 번 짚는다.
- 같은 (u, v) 쌍은 두 번 나오지 않는다. 노드 번호가 1부터라 배열을 n + 1 크기로 잡는다.

이 글에서 쓸 예시는 노드 5개, 간선 7개다. 출발은 1번이다.

```text
1 → 2 : 2      2 → 4 : 6      4 → 5 : 1
1 → 3 : 5      3 → 4 : 2      3 → 5 : 7
2 → 3 : 1
```

손으로 풀어 보자. 1에서 2까지는 2다. 3은 바로 가면 5지만 2를 거치면 2 + 1 = 3이라 3이다. 4는 2에서 바로 가면 2 + 6 = 8, 3을 거치면 3 + 2 = 5라서 5다. 5는 3에서 바로 가면 3 + 7 = 10, 4를 거치면 5 + 1 = 6이라 6이다. 노드별 최단 시간은 `[0, 2, 3, 5, 6]`이고 가장 큰 값 6이 답이다.

손으로 풀 때 이미 두 가지를 했다. 직접 가는 길보다 돌아가는 길이 빠를 수 있다는 것, 그리고 2를 먼저 확정하고 나서야 3을 확정할 수 있었다는 것이다. 앞의 것은 "더 짧은 길을 찾으면 값을 줄인다"는 완화(relaxation)이고, 뒤의 것은 다익스트라의 확정 순서다.

## 길을 전부 따라가 보는 DFS

가장 먼저 떠오르는 방법은 출발점에서 갈 수 있는 길을 모두 따라가 보는 것이다. 각 노드에 지금까지 찾은 가장 빠른 도착 시간을 적어 두고, 그보다 늦게 도착하면 더 가 볼 필요가 없으니 돌아온다.

```js
function networkDelayTime(times, n, k) {
  const graph = Array.from({ length: n + 1 }, () => []);
  for (const [u, v, w] of times) graph[u].push([v, w]);
  // 가벼운 간선부터 가 보면 좋은 답을 일찍 찾아 가지치기가 잘 된다
  for (const list of graph) list.sort((a, b) => a[1] - b[1]);

  const dist = new Array(n + 1).fill(Infinity);
  const dfs = (u, t) => {
    if (t >= dist[u]) return; // 이미 이만큼이나 더 빨리 도착한 적이 있다
    dist[u] = t;
    for (const [v, w] of graph[u]) dfs(v, t + w);
  };
  dfs(k, 0);

  let answer = 0;
  for (let i = 1; i <= n; i++) answer = Math.max(answer, dist[i]);
  return answer === Infinity ? -1 : answer;
}
```

`t >= dist[u]`에서 같을 때도 돌아오는 게 중요하다. 무게 0인 간선으로 고리가 있으면(`1 → 2 : 0`, `2 → 1 : 0`) 같은 시간으로 계속 서로를 부르다 스택이 넘친다.

정답은 맞지만 일을 얼마나 하는지가 문제다. 한 노드의 값이 줄어들 때마다 그 노드 뒤쪽을 처음부터 다시 훑는다. 예시는 운이 좋다. 가벼운 간선부터 가니 `1 → 2 → 3 → 4 → 5`를 먼저 밟아 처음 적은 값이 모두 답이었고, 가지치기로 돌아온 호출까지 8번으로 끝났다. 간선을 무거운 것부터 보게 바꾸면 3이 5로 적혔다가 3으로 줄고 그때마다 3 뒤쪽을 다시 훑어서, 같은 그래프에서 호출이 11번으로 는다. 노드 100개, 간선 6,000개를 무작위로 만든 그래프에서 세어 보니 호출이 227,361번이었다. 간선 수의 38배쯤이다. 값이 줄어드는 횟수는 이론상 경로 개수만큼 늘 수 있어서 최악의 시간을 다항식으로 묶을 수 없다. 재귀 깊이도 최대 n이다.

문제는 "아직 더 줄어들 수 있는 값"을 붙잡고 그 뒤를 먼저 훑는다는 데 있다. 값이 확정된 노드에서만 뻗어 나가면 같은 길을 다시 볼 일이 없다. 뒤의 풀이들은 모두 이 낭비를 줄이는 방법이다.

## 모든 쌍을 다 구하는 플로이드-워셜

출발점이 하나뿐인데 모든 쌍의 최단 거리를 구하는 건 과하다. 그래도 n이 100이라 성립하고, 코드가 가장 짧아서 시험장에서 떠올리기 쉽다.

```js
function networkDelayTime(times, n, k) {
  // d[i][j]: i에서 j까지 지금까지 아는 최단 시간
  const d = Array.from({ length: n + 1 }, (_, i) =>
    Array.from({ length: n + 1 }, (_, j) => (i === j ? 0 : Infinity))
  );
  for (const [u, v, w] of times) d[u][v] = w;

  // m을 중간에 거쳐도 되는 노드로 하나씩 늘려 간다. m이 가장 바깥이어야 한다
  for (let m = 1; m <= n; m++)
    for (let i = 1; i <= n; i++)
      for (let j = 1; j <= n; j++)
        if (d[i][m] + d[m][j] < d[i][j]) d[i][j] = d[i][m] + d[m][j];

  let answer = 0;
  for (let j = 1; j <= n; j++) answer = Math.max(answer, d[k][j]);
  return answer === Infinity ? -1 : answer;
}
```

반복 순서가 자주 틀린다. 거쳐 가는 노드 `m`이 가장 바깥 반복이어야 한다. "1번만 거쳐도 되는 최단 거리 → 1, 2번까지 거쳐도 되는 최단 거리"처럼 허용 범위를 넓혀 가는 DP이기 때문이다. `m`을 안쪽에 두면 아직 갱신되지 않은 값을 읽어 답이 틀어진다.

시간 O(n³), 공간 O(n²)이다. n = 100이면 100만 번이라 빠르게 끝나지만 노드가 1만 개만 돼도 1조 번이다. 왜 이 알고리즘이 성립하는지는 [최단 경로 글의 플로이드-워셜 절](/posts/shortest-path-algorithms#모든-쌍이-필요하면-플로이드-워셜)에서 다뤘다. 출발점이 하나면 이 정도까지 할 필요가 없다.

## 간선 전체를 n - 1번 다시 보는 벨만-포드

출발점 하나에서의 최단 거리만 구하면 된다. 가장 단순한 방법은 간선 전체를 훑으며 "u까지 오는 시간 + w가 지금 적힌 v의 시간보다 작으면 줄인다"를 반복하는 것이다. 이 한 번의 훑기를 n - 1번 하면 끝난다.

```js
function networkDelayTime(times, n, k) {
  const dist = new Array(n + 1).fill(Infinity);
  dist[k] = 0;
  for (let round = 1; round < n; round++) {
    let changed = false;
    for (const [u, v, w] of times) {
      if (dist[u] + w < dist[v]) { // 완화: 더 빠른 길을 찾으면 줄인다
        dist[v] = dist[u] + w;
        changed = true;
      }
    }
    if (!changed) break; // 한 바퀴 동안 아무것도 안 바뀌면 더 바뀔 게 없다
  }
  let answer = 0;
  for (let i = 1; i <= n; i++) answer = Math.max(answer, dist[i]);
  return answer === Infinity ? -1 : answer;
}
```

왜 n - 1번이면 충분할까. 최단 경로는 같은 노드를 두 번 지나지 않으니 간선이 많아야 n - 1개다. 한 바퀴 훑을 때마다 최단 경로의 앞쪽 간선이 적어도 하나씩 더 확정된다. 그래서 n - 1바퀴 뒤엔 모든 최단 경로가 끝까지 확정돼 있다.

`Infinity + w`는 여전히 `Infinity`라 JavaScript에서는 아직 닿지 않은 노드에서 출발한 완화가 저절로 무시된다. Java처럼 `Integer.MAX_VALUE`를 무한대로 쓰면 더하는 순간 음수로 넘어가니 `dist[u] != INF` 검사를 먼저 해야 한다.

시간은 O(n · E), 이 문제의 최대 크기에서 60만 번이다. 간선 순서가 운이 좋으면 몇 바퀴 만에 끝난다. 무작위 그래프에서는 5바퀴째에 바뀐 게 없어서 멈췄다. 반대로 `1 → 2 → … → 100` 사슬을 뒤에서부터 적어 두면 한 바퀴에 한 칸씩만 전진해서 99바퀴를 다 돈다.

벨만-포드는 무게가 음수여도 성립하고, n번째 바퀴에도 값이 줄면 음수 사이클이 있다고 알려 준다. 이 문제에선 필요 없는 능력이지만, 무게 대신 "간선 개수 제한"이 붙은 [Cheapest Flights Within K Stops](/posts/leetcode-cheapest-flights-within-k-stops)에서는 바퀴 수를 세는 이 구조가 바로 답이 된다.

## 바뀐 노드만 다시 보는 SPFA

벨만-포드는 바뀌지 않은 노드의 간선까지 매번 다시 본다. 값이 줄어든 노드만 큐에 넣고 그 노드에서 나가는 간선만 다시 보면 헛일이 준다. 이 방식을 SPFA(Shortest Path Faster Algorithm)라고 부른다.

```js
function networkDelayTime(times, n, k) {
  const graph = Array.from({ length: n + 1 }, () => []);
  for (const [u, v, w] of times) graph[u].push([v, w]);
  const dist = new Array(n + 1).fill(Infinity);
  const inQueue = new Array(n + 1).fill(false);
  dist[k] = 0;
  const queue = [k];
  inQueue[k] = true;
  for (let head = 0; head < queue.length; head++) {
    const u = queue[head];
    inQueue[u] = false; // 꺼냈으니 다시 줄어들면 또 들어갈 수 있다
    for (const [v, w] of graph[u]) {
      if (dist[u] + w < dist[v]) {
        dist[v] = dist[u] + w;
        if (!inQueue[v]) { inQueue[v] = true; queue.push(v); }
      }
    }
  }
  let answer = 0;
  for (let i = 1; i <= n; i++) answer = Math.max(answer, dist[i]);
  return answer === Infinity ? -1 : answer;
}
```

예시에서는 노드를 5번 꺼내고 끝났다. 무작위 그래프에서는 222번 꺼냈다. 노드 하나를 평균 두 번 남짓 다시 본 셈이다. 다만 최악은 벨만-포드와 같은 O(n · E)다. 값이 줄어들 때마다 다시 큐에 들어가는 걸 막을 장치가 없어서, 일부러 만든 입력에서는 노드가 수없이 다시 들어간다. 평균이 빠르다는 이유로 시험에서 SPFA만 믿으면 안 되는 이유다.

여기까지 풀이는 모두 "줄어들 수 있으면 다시 본다"는 방식이다. 다음 풀이는 순서를 잘 고르면 노드를 딱 한 번만 보면 된다는 데서 출발한다.

## 가장 이른 노드부터 확정하는 다익스트라

손으로 풀 때를 떠올려 보자. 처음에 1의 이웃 2와 3이 각각 2와 5로 적힌다. 이때 2는 더 줄어들 수 없다. 2보다 빨리 갈 수 있는 길이 있다면 그 길은 5보다 작은 어딘가를 먼저 지나야 하는데, 모든 무게가 0 이상이라 그런 노드에서 출발해 2보다 작아질 수 없다. 그래서 "아직 확정하지 않은 노드 중 시간이 가장 작은 노드"는 바로 확정해도 된다. 이게 다익스트라다.

노드가 100개뿐이니 가장 작은 노드를 고를 때 배열을 그냥 훑어도 된다.

```js
function networkDelayTime(times, n, k) {
  const graph = Array.from({ length: n + 1 }, () => []);
  for (const [u, v, w] of times) graph[u].push([v, w]);
  const dist = new Array(n + 1).fill(Infinity);
  const done = new Array(n + 1).fill(false);
  dist[k] = 0;
  for (let step = 0; step < n; step++) {
    // 아직 확정하지 않은 노드 중 시간이 가장 작은 것을 고른다: O(n)
    let u = -1;
    for (let i = 1; i <= n; i++) {
      if (!done[i] && (u === -1 || dist[i] < dist[u])) u = i;
    }
    if (dist[u] === Infinity) return -1; // 남은 노드는 닿을 수 없다
    done[u] = true;
    for (const [v, w] of graph[u]) {
      if (dist[u] + w < dist[v]) dist[v] = dist[u] + w;
    }
  }
  return Math.max(...dist.slice(1));
}
```

n번 고르고 고를 때마다 n칸을 훑으니 O(n²)이고, 간선은 전체에서 한 번씩만 보니 O(n² + E)다. 이 문제처럼 노드가 적고 간선이 많을 때(최대 6,000개, 꽉 차면 9,900개) 힙을 쓰는 풀이와 견줄 만하다. 남은 노드 중 가장 작은 값이 `Infinity`면 나머지는 출발점에서 닿을 수 없다는 뜻이라 바로 -1을 돌려줄 수 있다.

한계는 노드 수다. 노드가 10만 개인 희소한 그래프라면 고르는 데만 100억 번이다. 가장 작은 값을 빨리 꺼내는 자료구조가 필요하다.

## 힙으로 다음 노드를 빨리 고른다

"가장 작은 것을 꺼낸다"는 최소 힙이 O(log n)에 해 준다. 값이 줄어든 노드를 `[새 시간, 노드]`로 힙에 넣고, 꺼낼 때 가장 이른 노드가 나온다. 힙 안의 값을 직접 줄이는 연산은 번거로우니, 줄어들 때마다 새 후보를 또 넣고 꺼낼 때 낡은 후보를 버린다.

JavaScript에는 힙이 없어서 직접 짠다. 배열로 짠 이진 힙이고, 동작 원리는 [힙 글](/posts/ds-heap#넣으면-올라가고-꺼내면-내려간다)에 있다.

```js
function networkDelayTime(times, n, k) {
  // 인접 리스트: graph[u] = [[v, w], ...]
  const graph = Array.from({ length: n + 1 }, () => []);
  for (const [u, v, w] of times) graph[u].push([v, w]);

  const dist = new Array(n + 1).fill(Infinity);
  dist[k] = 0;
  const heap = [[0, k]]; // [시간, 노드]를 시간 작은 순으로 꺼내는 최소 힙

  const push = (item) => {
    heap.push(item);
    let i = heap.length - 1;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (heap[p][0] <= heap[i][0]) break;
      [heap[p], heap[i]] = [heap[i], heap[p]];
      i = p;
    }
  };
  const pop = () => {
    const top = heap[0];
    const last = heap.pop();
    if (heap.length > 0) {
      heap[0] = last;
      let i = 0;
      while (true) {
        const l = 2 * i + 1, r = l + 1;
        let s = i;
        if (l < heap.length && heap[l][0] < heap[s][0]) s = l;
        if (r < heap.length && heap[r][0] < heap[s][0]) s = r;
        if (s === i) break;
        [heap[s], heap[i]] = [heap[i], heap[s]];
        i = s;
      }
    }
    return top;
  };

  let settled = 0, answer = 0;
  while (heap.length > 0) {
    const [t, u] = pop();
    if (t > dist[u]) continue; // 더 짧은 길로 이미 확정된 노드의 낡은 후보
    settled++;
    answer = t;               // 꺼내는 시간은 커지기만 하므로 마지막 값이 최댓값
    for (const [v, w] of graph[u]) {
      if (t + w < dist[v]) {
        dist[v] = t + w;
        push([dist[v], v]);
      }
    }
  }
  return settled === n ? answer : -1;
}
```

마지막에 `dist`를 다시 훑지 않고 `answer = t`로 끝내는 이유가 있다. 다익스트라가 노드를 확정하는 시간은 점점 커지기만 한다. 그러니 마지막으로 확정한 노드의 시간이 곧 최댓값이다. 확정한 노드 수 `settled`가 n보다 작으면 닿지 못한 노드가 있으니 -1이다.

### Python과 Java로 쓰면

Python은 `heapq`가 리스트를 최소 힙으로 다룬다. 튜플 `(시간, 노드)`를 넣으면 첫 값부터 비교하니 시간 순으로 나온다. 시간이 같으면 노드 번호로 비교하는데, 정수라 문제없다. 노드 대신 비교할 수 없는 객체를 넣으면 시간이 같을 때 `TypeError`가 나니 그땐 순번을 두 번째 값으로 끼운다.

```python
import heapq
from collections import defaultdict
from typing import List


def network_delay_time(times: List[List[int]], n: int, k: int) -> int:
    graph = defaultdict(list)
    for u, v, w in times:
        graph[u].append((v, w))

    dist = {k: 0}
    heap = [(0, k)]  # (시간, 노드). 튜플은 첫 값부터 비교된다
    answer = 0
    while heap:
        t, u = heapq.heappop(heap)
        if t > dist[u]:
            continue  # 낡은 후보
        answer = t
        for v, w in graph[u]:
            nt = t + w
            if nt < dist.get(v, float("inf")):
                dist[v] = nt
                heapq.heappush(heap, (nt, v))
    return answer if len(dist) == n else -1


ex = [[1, 2, 2], [1, 3, 5], [2, 3, 1], [2, 4, 6], [3, 4, 2], [4, 5, 1], [3, 5, 7]]
print(network_delay_time(ex, 5, 1))
print(network_delay_time([[1, 2, 1]], 2, 2))
print(network_delay_time([], 1, 1))
```


`dist`를 딕셔너리로 두면 닿은 노드만 들어 있어서 `len(dist) == n`으로 모두 닿았는지 바로 안다. 닿은 노드는 언젠가 힙에서 꺼내져 확정되므로 이 검사가 확정 개수 검사와 같다.

Java는 `PriorityQueue`가 최소 힙이다. 비교자를 `(a, b) -> a[0] - b[0]`로 쓰는 코드가 흔한데, 값이 21억 근처까지 커지는 문제에서는 뺄셈이 넘쳐 순서가 뒤집힌다. 이 문제는 시간이 1만을 넘지 않아 괜찮지만 `Integer.compare`로 쓰는 습관을 들이는 게 안전하다.

```java
import java.util.*;

class Solution {
    public int networkDelayTime(int[][] times, int n, int k) {
        List<List<int[]>> graph = new ArrayList<>();
        for (int i = 0; i <= n; i++) graph.add(new ArrayList<>());
        for (int[] e : times) graph.get(e[0]).add(new int[]{e[1], e[2]});

        int[] dist = new int[n + 1];
        Arrays.fill(dist, Integer.MAX_VALUE);
        dist[k] = 0;
        // [시간, 노드]. 뺄셈 비교 대신 Integer.compare로 오버플로를 피한다
        PriorityQueue<int[]> pq = new PriorityQueue<>((a, b) -> Integer.compare(a[0], b[0]));
        pq.offer(new int[]{0, k});
        int settled = 0, answer = 0;
        while (!pq.isEmpty()) {
            int[] cur = pq.poll();
            int t = cur[0], u = cur[1];
            if (t > dist[u]) continue; // 낡은 후보
            settled++;
            answer = t;
            for (int[] e : graph.get(u)) {
                int v = e[0], nt = t + e[1];
                if (nt < dist[v]) {
                    dist[v] = nt;
                    pq.offer(new int[]{nt, v});
                }
            }
        }
        return settled == n ? answer : -1;
    }
}
```

```text
0
```

Java 코드에서 `t + e[1]`은 확정된 노드의 시간에만 더하므로 `Integer.MAX_VALUE`에 더해질 일이 없다. 힙에서 꺼낸 `t`는 언제나 실제로 닿은 시간이기 때문이다. 벨만-포드처럼 모든 간선을 훑는 코드로 바꿀 때는 이 성질이 없으니 넘침 검사를 다시 넣어야 한다.

## 여섯 풀이를 나란히 놓으면

노드 100개, 간선 6,000개짜리 무작위 그래프에서 20번 돌린 평균 시간도 함께 적었다. 이 크기에서는 모두 몇 ms 안에 끝나서 시간 차이보다 일의 양 차이를 보는 게 낫다.

| 풀이 | 시간 | 공간 | 무작위 그래프 | 언제 고르나 |
|---|---|---|---|---|
| 가지치기 DFS | 최악 지수 | O(n + E) | 6.2ms, 호출 22만 번 | 고르지 않는다. 출발점으로만 쓴다 |
| 플로이드-워셜 | O(n³) | O(n²) | 5.1ms | 모든 쌍이 필요하거나 n이 수백 이하 |
| 벨만-포드 | O(n · E) | O(n) | 1.0ms, 5바퀴 | 음수 무게, 간선 개수 제한, 음수 사이클 검사 |
| SPFA | 평균 빠름, 최악 O(n · E) | O(n + E) | 2.2ms | 음수 무게가 있는데 평균을 줄이고 싶을 때 |
| 배열 다익스트라 | O(n² + E) | O(n + E) | 1.6ms | 노드가 적고 간선이 꽉 찬 그래프 |
| 힙 다익스트라 | O(E log n) | O(n + E) | 2.0ms | 무게가 0 이상인 일반 그래프의 기본값 |

벨만-포드가 가장 빠르게 나온 건 무작위 그래프라 5바퀴 만에 끝났기 때문이다. 사슬처럼 불리한 입력이면 99바퀴를 다 돈다. 면접에서 기본으로 내놓을 답은 힙 다익스트라이고, "노드가 100개뿐이라 배열 다익스트라나 플로이드-워셜도 된다"를 덧붙이면 제약을 읽었다는 걸 보여 줄 수 있다.

## 틀리기 쉬운 곳

처음 짤 때 가장 흔한 실수는 무게가 있는데 BFS를 그대로 쓰는 것이다. 처음 닿은 시간을 확정해 버린다.

```js
// 틀린 풀이: 처음 닿은 시간을 그대로 확정한다
for (const [v, w] of graph[u]) {
  if (dist[v] === Infinity) {
    dist[v] = dist[u] + w;
    queue.push(v);
  }
}
```

예시에서 이 코드는 6이 아니라 12를 낸다. 1에서 바로 간 3이 5로 굳고, 거기서 간 5도 5 + 7 = 12로 굳는다. BFS가 최단 거리를 주는 건 모든 간선의 무게가 같을 때뿐이다. 이 이야기는 [BFS·DFS 글](/posts/ds-graph-bfs-dfs#선에-무게가-붙으면-bfs가-틀린다)에도 있다.

배열 크기도 자주 틀린다. 노드가 1번부터인데 `new Array(n)`으로 잡으면 노드 n이 배열 밖으로 나가고, `new Array(n + 1)`로 잡고 `Math.max(...dist)`를 하면 쓰지 않는 0번 칸의 `Infinity`가 섞여 언제나 -1이 나온다. 최댓값은 1번부터 n번까지만 본다.

```js
const dist = [Infinity, 0, 1];   // 0번 칸은 쓰지 않는다
Math.max(...dist);               // Infinity → 늘 -1이 된다
Math.max(...dist.slice(1));      // 1
```

방문 표시를 힙에 넣을 때 하는 것도 틀린다. BFS에서는 넣을 때 표시하는 게 맞지만, 다익스트라에서 넣는 순간은 "후보"일 뿐 확정이 아니다. 예시에서 3을 처음 넣을 때 5로 확정해 버리면 2를 거치는 3짜리 길이 막힌다. 확정은 꺼낼 때 한다.

낡은 후보 검사를 `t >= dist[u]`로 쓰면 모든 노드가 버려진다. 꺼낸 후보가 유효하면 `t`와 `dist[u]`가 같기 때문이다. 버리는 조건은 `t > dist[u]`, 엄격하게 크다.

무게가 0인 간선은 다익스트라를 깨지 않는다. 확정 논리는 "무게가 음수가 아니다"만 필요하다. 0인 간선 덕분에 시간이 같은 노드가 여럿 생겨도 어느 것을 먼저 확정하든 결과는 같다.

## 면접관이 바꿔 묻는 것

경로 자체를 돌려달라고 하면 완화할 때 `prev[v] = u`를 적어 두고, 끝에서 목적지부터 `prev`를 따라 거꾸로 올라간 뒤 뒤집는다. 방법은 [최단 경로 글의 경로 복원 절](/posts/shortest-path-algorithms#지나온-길을-거꾸로-따라가기)과 같다.

목적지가 하나뿐이면 그 노드를 힙에서 꺼내는 순간 멈춰도 된다. 꺼낼 때 확정되니 그 뒤로 값이 바뀌지 않는다. 지도 길찾기처럼 목적지 방향을 짐작할 수 있다면 A\*로 더 일찍 끝낼 수 있다.

무게에 음수가 섞이면 다익스트라는 틀린다. 벨만-포드로 바꾸고, n번째 바퀴에도 값이 줄면 음수 사이클이 있다고 답한다.

"최대 k번만 갈아탈 수 있다"는 조건이 붙으면 최단 시간만 들고 다니는 다익스트라로는 부족하다. 더 느려도 덜 갈아탄 경로가 나중에 필요할 수 있어서다. 이게 [Cheapest Flights Within K Stops](/posts/leetcode-cheapest-flights-within-k-stops)이고, 바퀴 수를 k + 1로 묶은 벨만-포드가 깔끔하게 맞는다.

시간을 더하는 대신 확률을 곱해 가장 큰 값을 구하라면 최대 힙으로 바꾼 다익스트라가 된다. 확률은 1 이하라 곱할수록 작아지니, 무게가 0 이상일 때 더할수록 커지는 것과 같은 구조다. [Path with Maximum Probability](/posts/leetcode-path-with-maximum-probability)가 그 문제다.

경로의 합이 아니라 "지나는 칸 중 가장 높은 값"을 최소로 하라면 다익스트라에서 `t + w` 자리를 `Math.max(t, h)`로 바꾸면 된다. [Swim in Rising Water](/posts/leetcode-swim-in-rising-water)가 그렇게 풀린다.

모든 노드에서 임계 거리 안에 몇 개가 닿는지 묻는 [Find the City With the Smallest Number of Neighbors at a Threshold Distance](/posts/leetcode-find-city-smallest-neighbors)는 출발점이 n개라 이 글의 플로이드-워셜이 그대로 쓰인다.

## 면접에서 나올 만한 질문

### 이 문제가 최단 경로 문제인 이유는

신호는 모든 링크로 동시에 퍼지니 노드마다 가장 빨리 닿는 시간은 출발점에서 그 노드까지의 최단 경로 길이다. 모든 노드가 받는 시점은 그중 가장 늦은 노드의 시간이다. 그래서 단일 출발 최단 거리를 구한 뒤 최댓값을 고르고, 닿지 않은 노드가 있으면 -1을 낸다.

### 다익스트라에서 힙에서 꺼낸 노드를 바로 확정해도 되는 이유는

무게가 0 이상이기 때문이다. 꺼낸 노드보다 더 빨리 가는 길이 있다면 그 길은 힙에 남은 다른 후보를 거쳐야 하는데, 남은 후보는 모두 지금 값 이상이고 간선을 더하면 줄지 않는다. 그래서 지금 가장 작은 값이 최종값이다. 음수 간선이 하나라도 있으면 이 논리가 깨진다.

### 힙에 같은 노드가 여러 번 들어가도 괜찮나

괜찮다. 값이 줄 때마다 새 후보를 넣고, 꺼낼 때 `t > dist[u]`이면 낡은 후보로 보고 버린다. 힙에 들어가는 건 완화가 성공한 횟수만큼이라 많아야 E개이고, 시간은 O(E log E)로 O(E log n)과 같은 급이다. decrease-key를 지원하는 힙을 짜는 것보다 단순하고 실제로도 빠른 편이다.

### n이 100뿐인데 어떤 풀이가 가장 적당한가

모두 통과하지만 기본은 힙 다익스트라다. 노드가 적고 간선이 꽉 찬 그래프에서는 O(n² + E) 배열 다익스트라가 힙 없이 짧게 짤 수 있어 좋은 대안이다. 플로이드-워셜은 100만 번이라 통과하지만 출발점이 하나인데 모든 쌍을 구하는 과한 계산이다.

### 무게에 음수가 있으면 어떻게 바꾸나

벨만-포드를 쓴다. 간선 전체를 n - 1번 훑으면 최단 거리가 확정되고, n번째 훑기에서도 값이 줄면 음수 사이클이 있어서 최단 거리가 정의되지 않는다고 답한다. SPFA는 평균이 빠르지만 최악은 같다.

### 마지막 확정 시간이 답인 이유는

다익스트라가 꺼내는 시간은 단조롭게 커진다. 꺼낸 시간 t에서 무게 0 이상을 더한 후보만 새로 들어가니 다음에 꺼낼 값이 t보다 작을 수 없다. 그래서 마지막으로 확정한 노드의 시간이 최댓값이고, 확정한 노드 수가 n과 같은지만 확인하면 된다.

### 이 코드가 틀리는 입력을 하나 들어 보라

무게를 무시하고 처음 닿은 시간을 굳히는 BFS는 돌아가는 길이 더 빠른 그래프에서 틀린다. 예시에서 3은 바로 가면 5, 2를 거치면 3인데 BFS는 5로 굳혀서 답이 6이 아니라 12가 된다. 1번부터인 노드를 0번 칸이 포함된 배열로 최댓값을 내면 늘 -1이 되는 실수도 흔하다.
