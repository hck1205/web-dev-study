다음 주 월요일 10시에 선착순 쿠폰 이벤트가 열린다. 기획에서 묻는다. "그날 서버 버티나요?" 평소 주문 API는 초당 100건 남짓이다. 이벤트 알림이 나가면 몇 배가 될지 모른다. 이 질문에 "아마요"보다 나은 답을 하려면, 미리 그만큼의 요청을 보내 보고 숫자로 말해야 한다.

이 글은 그 숫자를 만드는 과정을 따라간다. 테스트 이름마다 답하는 질문을 정하고, k6로 실제 시나리오를 짜서 돌리고, 결과의 p95·p99·오류율·처리량을 읽는다. 닫힌 부하 모델과 열린 부하 모델이 왜 다른 숫자를 내는지, 부하 생성기 자체가 병목이 되는 경우, 테스트는 통과했는데 운영에서 터지는 이유도 다룬다. 백분위가 무엇이고 왜 평균 대신 쓰는지, coordinated omission이 무엇인지는 [응답 시간은 백분위로 읽는다](/posts/percentile-latency)에서 자세히 다뤘으니 여기서는 짧게 넘긴다.

실험은 k6 v2.3.0으로 했고, 대상은 4코어 리눅스 머신 한 대에 같이 띄운 Node 22 서버다. 부하 생성기와 대상이 같은 머신에 있으니 절대 숫자보다는 모양을 보는 실험이다. 아래 출력은 모두 이 환경에서 실제로 돌린 결과다.

## 테스트 이름마다 묻는 질문이 다르다

"부하 테스트 해 봤어요?"라는 말은 여러 테스트를 뭉뚱그린다. 이름을 나누는 건 묻는 질문이 달라서다. 질문이 다르면 부하를 주는 모양도, 합격선도 다르다.

| 이름 | 묻는 질문 | 부하 모양 | 보는 숫자 |
|---|---|---|---|
| 부하 테스트 | 예상 피크에서 목표를 지키나 | 피크 도착률로 10~30분 유지 | p95·p99가 목표 안인지, 오류율 |
| 스트레스 테스트 | 어디서 무너지고, 어떻게 무너지나 | 도착률을 계단처럼 올린다 | 지연이 꺾이는 지점, 오류가 시작되는 지점 |
| 스파이크 테스트 | 갑자기 몰렸을 때 버티고 회복하나 | 몇 초 만에 여러 배로, 다시 내린다 | 실패율, 회복까지 걸린 시간 |
| 소크 테스트 | 오래 돌리면 무엇이 새나 | 평소 수준으로 몇 시간 | 메모리, 커넥션, 디스크, 지연의 추세 |

성능 테스트는 이 모두를 아우르는 넓은 말로 쓰이기도 하고, 부하 없이 요청 하나의 속도를 재는 벤치마크를 가리키기도 한다. 팀 안에서 어느 뜻인지 먼저 맞춰 두면 회의가 짧아진다.

이벤트 질문에 필요한 건 셋이다. 예상 피크에서의 부하 테스트, 피크를 넘으면 어떻게 되는지 보는 스트레스 테스트, 알림 직후의 몰림을 흉내 내는 스파이크 테스트다. 소크는 이벤트가 몇 시간씩 이어질 때 추가한다.

## 실험 대상: 커넥션 여덟 개짜리 주문 API

대상 서버는 일부러 단순하게 만들었다. DB 커넥션 풀이 8개이고, 요청 하나가 커넥션을 20ms 쓴다고 흉내 냈다. 풀이 꽉 차면 요청은 대기열에서 기다리고, 대기열이 200개를 넘으면 바로 503을 돌려준다.

```js
// server.mjs: 풀 8개, 요청당 20ms, 대기열 200개를 넘으면 503
import http from "node:http";
const POOL = 8, WORK_MS = 20, MAX_QUEUE = 200;
let busy = 0; const queue = [];
function run(res) {
  busy++;
  setTimeout(() => { busy--; res.end('{"ok":true}'); next(); }, WORK_MS);
}
function next() { while (busy < POOL && queue.length) run(queue.shift()); }
http.createServer((req, res) => {
  // /pause?ms=2000: 이벤트 루프를 그 시간만큼 막는다 (긴 GC나 락 대기 흉내)
  if (req.url.startsWith("/pause")) { /* 생략: 응답 후 busy-wait */ }
  if (queue.length >= MAX_QUEUE) { res.statusCode = 503; return res.end("busy"); }
  queue.push(res); next();
}).listen(3300);
```

계산으로는 커넥션 8개가 1초에 50번씩(1000ms ÷ 20ms) 일하니 초당 400건이 상한이다. 실제 서비스도 이 모양과 크게 다르지 않다. 한정된 자원(커넥션, 스레드, CPU)이 있고, 그 앞에 줄이 있고, 줄이 넘치면 어디선가 거절하거나 타임아웃이 난다. 커넥션 풀 크기를 어떻게 정하는지는 [커넥션 풀](/posts/connection-pool)에서 다뤘다.

## k6 스크립트 한 장

k6는 시나리오를 자바스크립트로 쓰고, 엔진은 Go로 돌아간다. 스크립트에서 `default` 함수가 가상 사용자(VU) 하나가 반복하는 일이다.

```js
// closed.js: VU 20개가 15초 동안 쉬지 않고 요청한다
import http from "k6/http";
import { check } from "k6";

export const options = { vus: 20, duration: "15s" };

export default function () {
  const res = http.get("http://localhost:3300/orders");
  check(res, { "status 200": (r) => r.status === 200 });
}
```

```bash
# 스크립트를 실행한다. 끝나면 요약이 찍힌다
k6 run closed.js
```

봐야 할 줄은 넷이다. `http_req_duration`은 요청을 보내고 응답을 다 받기까지의 시간이고, `{ expected_response:true }` 줄은 그중 성공한 응답만 모은 것이다. `http_req_failed`는 실패 비율로, k6는 기본으로 200~399가 아닌 상태 코드를 실패로 센다. `http_reqs`는 처리량, 즉 초당 요청 수다. `checks`는 내가 단 조건의 통과율인데, 실패해도 테스트를 실패로 만들지는 않는다. 합격선은 뒤에서 볼 `thresholds`가 정한다.

숫자를 하나 맞춰 본다. VU 20개가 요청마다 평균 51.2ms씩 기다리면 1초에 20 ÷ 0.0512 ≈ 390건을 보낸다. 실제 처리량 388.97/s와 맞는다. 이게 리틀의 법칙(동시에 있는 수 = 처리량 × 머무는 시간)이고, 닫힌 모델에서는 처리량이 VU 수와 응답 시간으로 정해진다는 뜻이다. 그런데 서버는 요청 하나를 20ms에 처리하는데 왜 응답이 51ms일까. VU 20개가 커넥션 8개를 두고 줄을 섰기 때문이다. 쉬는 시간 없이 VU를 너무 많이 넣으면 테스트 스스로 줄을 만든다.

## VU를 정하느냐, 도착률을 정하느냐

위 스크립트처럼 VU 수를 정하는 방식을 닫힌 모델이라 부른다. VU는 응답을 받아야 다음 요청을 보낸다. 반대로 "1초에 300번 시작한다"처럼 도착률을 정하는 방식이 열린 모델이다. 앞 요청이 끝났는지와 상관없이 정해진 간격으로 새 요청이 출발한다. k6에서는 `executor`로 고른다.

```js
// open-pause.js: 응답과 상관없이 1초에 300번 시작한다
export const options = {
  scenarios: {
    orders: {
      executor: "constant-arrival-rate",
      rate: 300, timeUnit: "1s",
      duration: "15s",
      preAllocatedVUs: 50,   // 미리 만들어 둘 VU
      maxVUs: 1000,          // 모자라면 이만큼까지 늘린다
    },
  },
  summaryTrendStats: ["avg", "med", "p(95)", "p(99)", "max"],
};
```

두 모델의 차이는 서버가 잠깐 멈출 때 드러난다. 테스트 시작 5초 뒤에 서버의 이벤트 루프를 2초 동안 막았다. GC가 길게 멈추거나 DB 락에 걸린 상황을 흉내 낸 것이다.

```bash
# 5초 뒤에 서버를 2초간 멈추게 하고, 그동안 k6를 돌린다
(sleep 5; curl -s "localhost:3300/pause?ms=2000" >/dev/null) & k6 run --quiet closed-pause.js
(sleep 5; curl -s "localhost:3300/pause?ms=2000" >/dev/null) & k6 run --quiet open-pause.js
```

`dropped_iterations` 288은 정해진 시각에 출발하지 못한 반복 수다. 멈춤 순간 갑자기 VU가 수백 개 필요해졌는데 k6가 VU를 새로 만드는 데도 시간이 걸려서 생겼다. 이 값이 0이 아니면 그만큼 계획한 부하를 주지 못한 것이니, 결과를 읽기 전에 먼저 본다.

닫힌 모델이 틀린 건 아니다. 사용자가 정해진 수만큼 있고 각자 응답을 받아야 다음 행동을 하는 시스템(사내 관리 도구, 콜센터 상담원 화면, 배치 워커)은 닫힌 모델이 더 가깝다. 이때는 VU마다 `sleep()`으로 생각하는 시간(think time)을 넣어 실제 사용자처럼 만든다. VU 20개가 요청 후 1초씩 쉬면 처리량은 초당 20건 안팎이다. 공개 API, 이벤트, 웹 트래픽처럼 사용자가 서로 모르고 각자 도착하는 시스템은 열린 모델로 테스트한다.

## 도착률을 올리며 무릎을 찾는다

스트레스 테스트로 이 서버가 어디서 무너지는지 찾았다. `constant-arrival-rate`의 `rate`만 바꿔 15초씩 여섯 번 돌렸다.

```bash
# 도착률을 바꿔 가며 같은 스크립트를 돌린다
for r in 200 300 360 390 420 500; do k6 run --quiet -e RATE=$r rate.js; done
```

## 스파이크와 회복

알림이 나간 직후를 흉내 냈다. 초당 100건에서 5초 만에 800건으로 올리고, 10초 버틴 뒤 다시 100건으로 내렸다. 합격선은 `thresholds`에 적었다.

```js
// spike.js
export const options = {
  scenarios: {
    spike: {
      executor: "ramping-arrival-rate",
      startRate: 100, timeUnit: "1s",
      preAllocatedVUs: 100, maxVUs: 2000,
      stages: [
        { target: 100, duration: "5s" },  // 평소
        { target: 800, duration: "5s" },  // 5초 만에 여덟 배
        { target: 800, duration: "10s" }, // 버틴다
        { target: 100, duration: "5s" },  // 내려온다
        { target: 100, duration: "10s" }, // 회복을 본다
      ],
    },
  },
  thresholds: {
    http_req_failed: ["rate<0.01"],                    // 실패 1% 미만
    http_req_duration: ["p(95)<300", "p(99)<800"],     // 지연 목표
  },
};
```

부하가 처리 능력 아래로 내려오자 다음 5초 안에 p95가 23ms로 돌아왔다. 이 서버는 상태가 단순해서 회복이 빠르다. 실제 서비스는 그렇지 않은 경우가 많다. 타임아웃 난 요청을 클라이언트가 재시도해서 부하가 내려와도 계속 몰리거나([재시도](/posts/retries)), 커넥션 풀이 고갈된 채로 회복하지 못하거나, 오토스케일링이 뒤늦게 서버를 늘렸다가 줄인다. 스파이크 테스트에서는 무너지는 모습보다 이 회복 구간을 더 오래 본다. 그래서 부하를 내린 뒤의 단계를 일부러 길게 둔다.

## 오래 돌려야 보이는 것: 소크 테스트

소크 테스트는 평소 피크의 70~80% 정도를 몇 시간에서 하루 동안 유지한다. 짧은 테스트로는 안 보이는 것이 시간이 지나며 쌓이는지 본다. 이 글의 실험 서버는 쌓이는 상태가 없어서 따로 돌리지 않았다. 볼 것은 서버 쪽 지표다.

- 힙 사용량이 GC 뒤에도 계단처럼 올라가는지(메모리 누수)
- 열린 커넥션, 파일 디스크립터, 스레드 수가 계속 느는지
- 디스크 사용량(로그, 임시 파일)이 계속 느는지
- 같은 도착률인데 p95가 시간이 갈수록 조금씩 오르는지
- 캐시 만료, 토큰 갱신, 크론 작업처럼 주기적인 일이 돌 때 지연이 튀는지

k6 요약은 몇 시간을 숫자 하나로 접어 버리니, 소크 테스트는 k6 결과를 프로메테우스 같은 시계열 저장소로 보내 서버 지표와 같은 시간 축에 놓고 본다. 하루짜리 소크라면 한 번 돌리는 데 하루가 걸리니 릴리스마다 하지 않고, 큰 변경 전이나 정기적으로 돌린다.

## 합격선을 코드에 적어 CI에 넣기

임계값은 "이 숫자를 넘으면 실패"를 스크립트에 적어 두는 것이다. k6는 임계값을 하나라도 넘으면 종료 코드 99로 끝나니 CI 단계가 실패로 표시된다. 계속 돌려 봐야 의미가 없는 경우를 위해 `abortOnFail`로 중간에 멈출 수도 있다.

```js
thresholds: {
  // 시작 10초 동안은 판단을 미루고, 그 뒤 실패율이 1%를 넘으면 바로 멈춘다
  http_req_failed: [{ threshold: "rate<0.01", abortOnFail: true, delayAbortEval: "10s" }],
},
```

```text
time="2026-10-23T13:03:09Z" level=error msg="thresholds on metrics 'http_req_duration, http_req_failed' were crossed; at least one has abortOnFail enabled, stopping test prematurely"
```

35초짜리 스파이크가 12초쯤에서 멈췄다. 공유 스테이징 환경을 오래 괴롭히지 않으려면 이 옵션이 유용하다.

CI에 넣을 때는 크기를 나눈다. 풀 리퀘스트마다 도는 파이프라인에는 VU 몇 개로 1분 정도 도는 스모크 테스트만 둔다. 목적은 성능 측정이 아니라 "스크립트가 깨지지 않았고 기본 경로가 통과하나"다. 공용 CI 러너는 다른 작업과 CPU를 나눠 쓰니 지연 숫자를 믿기 어렵다. 진짜 부하 테스트는 운영과 같은 크기의 스테이징에, 전용 부하 생성기에서, 야간이나 릴리스 전에 돌리고 결과를 이전 회차와 비교한다. 이전보다 p95가 20% 나빠졌다처럼 추세로 보는 편이 절대 기준 하나보다 회귀를 잘 잡는다. 파이프라인을 어떻게 나누는지는 [CI/CD 기본](/posts/ci-cd-basics)에 있다.

## 부하 생성기가 먼저 지칠 때

열린 모델에서 k6는 도착률을 맞추려고 VU를 쓴다. VU가 모자라면 계획한 부하를 주지 못한다. VU를 5개로 묶고 초당 300번을 요청해 봤다.

```text
time="2026-10-23T13:02:36Z" level=warning msg="Insufficient VUs, reached 5 active VUs and cannot initialize more" executor=constant-arrival-rate scenario=orders
    http_req_duration..............: med=20.6ms  p(95)=22.16ms p(99)=24.69ms max=33.91ms
    http_reqs......................: 2125   212.029932/s
    dropped_iterations.............: 876    87.406221/s
```

지연은 완벽해 보이지만 실제로 보낸 건 초당 212건이다. 5 ÷ 0.0235초 ≈ 212, 여기서도 리틀의 법칙이 맞는다. 필요한 VU는 도착률 × (응답 시간 + think time)이고, 느려지는 순간까지 버티려면 p99나 타임아웃 기준으로 잡는다. 초당 300건에 타임아웃이 2초면 최악의 경우 VU 600개가 필요하다. `preAllocatedVUs`는 평소에 필요한 만큼, `maxVUs`는 그 최악을 넉넉히 덮게 둔다.

VU 말고도 생성기가 지치는 곳은 많다. 생성기 머신의 CPU가 80%를 넘으면 요청을 제때 못 보내고 응답 처리도 늦어져, 서버가 아니라 생성기의 지연이 측정된다. 생성기와 대상 사이의 네트워크 대역폭, 로컬 포트 고갈(짧은 연결을 많이 열 때), 응답 본문을 다 파싱하는 무거운 `check`도 원인이 된다. 그래서 부하 테스트 중에는 서버만큼 생성기의 CPU와 네트워크도 본다. 이 글의 실험도 생성기와 서버가 같은 머신이라, 숫자를 그대로 운영 판단에 쓰면 안 된다. 한 대로 모자라면 여러 대로 나눠 돌리거나 관리형 서비스를 쓴다.

## 테스트는 통과했는데 운영에서 터지는 이유

부하 테스트가 초록색이었는데 이벤트 당일에 무너지는 경우는 대개 테스트가 운영과 달라서다. 자주 보는 차이를 적는다.

같은 URL만 두드리면 캐시가 모두 맞는다. 운영에서는 상품 ID가 수만 가지라 캐시 적중률이 훨씬 낮다. 테스트 데이터는 운영 분포를 흉내 내야 한다. 반대로 모든 VU가 같은 사용자 ID로 로그인하면, 그 한 줄에 락이 몰려 운영보다 나쁜 결과가 나오기도 한다.

DB 크기가 다르면 실행 계획이 다르다. 스테이징 테이블이 1만 줄이면 전체를 훑어도 빠르다. 운영의 1억 줄에서는 같은 쿼리가 수 초 걸린다. 테스트 전에 캐시와 JIT를 데우지 않으면 첫 몇 분 숫자가 나쁘게 나오고, 데우기만 반복한 서버로 재면 배포 직후의 차가운 상태를 놓친다.

외부 의존을 목으로 바꿨다면 그 부분은 검증하지 않은 것이다. 결제사나 문자 발송사의 요청 제한은 테스트에 나오지 않는다. 엔드포인트 하나만 때리는 테스트도 위험하다. 운영의 요청은 조회, 장바구니, 주문이 섞여 있고, 무거운 쓰기 하나가 전체를 끌어내린다. 실제 접근 로그의 비율대로 시나리오를 섞는다.

k6는 커넥션을 재사용한다. 운영의 모바일 사용자는 매번 새로 연결하고 TLS 핸드셰이크를 하니, 로드 밸런서와 서버의 연결 처리 비용이 테스트보다 훨씬 크다. 이 비용을 보려면 `noConnectionReuse` 옵션을 켜고 따로 돌려 본다. 오토스케일링도 시간이 걸린다. 스파이크가 5초 만에 오는데 서버가 늘어나는 데 3분이 걸리면, 그 3분을 버틸 여유가 처음부터 있어야 한다([오토스케일링](/posts/autoscaling)).

## 목표 RPS는 어떻게 정하나

"얼마나 보내야 하나"는 접근 로그에서 시작한다. 평균이 아니라 가장 바빴던 1분의 초당 요청 수를 찾고, 이벤트 예상 배수와 여유를 곱한다. 예를 들어 지난 이벤트의 피크가 초당 250건이었고 이번에 알림 대상이 두 배라면 500, 여기에 30% 여유를 두면 650을 부하 테스트 목표로 잡는다. 과거 데이터가 없으면 예상 사용자 수 × 사용자당 요청 수 ÷ 몰리는 시간으로 어림한다. 이 계산은 [용량 어림](/posts/sd-capacity-estimation)에서 단계별로 했다.

지연 목표는 서비스의 SLO에서 가져온다([SLI와 SLO](/posts/sli-slo)). "p95 300ms, 실패율 1% 미만"처럼 정해 두면 그대로 `thresholds`가 된다. 목표 없이 테스트를 돌리면 결과를 보고 나서 기준을 정하게 되고, 그러면 어떤 결과든 합격처럼 보인다.

결과 숫자를 직접 묶어 보면 어디서 착시가 생기는지 손에 잡힌다. 아래 함수는 `[응답 시간 ms, 상태 코드]` 목록과 테스트 시간(초)을 받아 처리량, 실패율, 성공한 응답만의 p95를 돌려준다. k6처럼 200~399를 성공으로, p95는 정렬한 뒤 95% 위치의 값(nearest-rank)으로 계산한다.

## 도구를 고르는 기준

k6 말고도 도구는 많다. 기능은 대부분 겹치고, 고르는 기준은 팀이 시나리오를 무엇으로 쓰고 싶은지와 부하 모델을 얼마나 명시적으로 다룰 수 있는지다.

- k6: 자바스크립트로 시나리오를 쓰고 Go 엔진으로 돈다. 닫힌 모델과 열린 모델 실행기를 모두 갖췄고, 임계값이 종료 코드로 이어져 CI에 넣기 쉽다.
- JMeter: GUI로 시나리오를 만들고 `.jmx`(XML)로 저장한다. 오래된 만큼 프로토콜과 플러그인이 많다. 스레드 하나가 사용자 하나라서 생성기 한 대가 만들 수 있는 부하가 상대적으로 적고, XML이라 코드 리뷰가 어렵다.
- Gatling: Java, Kotlin, Scala 코드로 시나리오를 쓴다. 주입 프로필에서 열린 모델(초당 몇 명 도착)과 닫힌 모델(동시 몇 명)을 이름부터 나눠 쓰게 되어 있고, HTML 보고서가 자세하다. JVM 팀에 잘 맞는다.
- Locust: 파이썬으로 사용자 행동을 클래스로 쓴다. 사용자 수와 `wait_time`을 정하는 닫힌 모델이 기본이다. 파이썬 생태계를 그대로 쓸 수 있다.
- Artillery: YAML로 시나리오를 쓰고 필요한 곳만 자바스크립트로 확장한다. 도착률(`arrivalRate`)로 부하를 정하는 열린 모델이 기본이다.
- Vegeta: Go로 만든 명령줄 도구다. 정해진 속도로 요청을 쏘는 열린 모델 하나만 한다. `vegeta attack -rate=300 -duration=15s`처럼 짧게 특정 엔드포인트의 한계를 볼 때 편하다.

도구보다 중요한 건 앞에서 본 것들이다. 무엇을 묻는 테스트인지, 부하 모델이 실제 사용자와 맞는지, 생성기가 계획대로 보냈는지, 성공한 응답의 지연을 실패율과 함께 읽었는지. 이 넷을 확인하면 "그날 버티나요?"에 숫자로 답할 수 있다. 이 서버라면 "초당 360건까지는 p95 22ms, 390건부터 꺾이고 420건부터 거절이 시작된다"가 답이다.

## 면접에서 나올 만한 질문

### 부하 테스트, 스트레스 테스트, 스파이크 테스트, 소크 테스트는 어떻게 다른가요?

묻는 질문이 다르다. 부하 테스트는 예상 피크에서 목표를 지키는지, 스트레스 테스트는 부하를 올려 어디서 어떻게 무너지는지, 스파이크 테스트는 갑자기 몰렸을 때 버티고 회복하는지, 소크 테스트는 오래 돌렸을 때 메모리나 커넥션이 새는지를 본다. 그래서 부하 모양도 피크 유지, 계단식 증가, 급증 후 하강, 평소 수준 장시간으로 다르다.

### 닫힌 부하 모델과 열린 부하 모델은 무엇이 다르고, 언제 무엇을 쓰나요?

닫힌 모델은 동시 사용자 수를 정하고 각자 응답을 받아야 다음 요청을 보낸다. 열린 모델은 초당 도착률을 정하고 응답과 무관하게 보낸다. 서버가 멈추면 닫힌 모델은 요청을 덜 보내서 느린 구간이 측정에서 빠진다. 실험에서 2초 멈춤에 닫힌 모델 p99는 65ms, 열린 모델은 1.99초였다. 공개 API나 이벤트처럼 사용자가 각자 도착하는 시스템은 열린 모델로, 정해진 사용자가 순서대로 일하는 시스템은 think time을 넣은 닫힌 모델로 본다.

### 부하 테스트 결과에서 무엇을 먼저 보나요?

먼저 계획한 부하를 실제로 줬는지 본다. `dropped_iterations`나 "Insufficient VUs" 경고, 생성기 CPU를 확인한다. 그다음 실패율, 그리고 성공한 응답만의 p95·p99를 본다. 빠른 실패 응답이 섞이면 전체 지연이 오히려 좋아 보이기 때문이다. 처리량은 도착률을 따라가는지, 어디서 멈추는지를 본다.

### 목표 RPS는 어떻게 정하나요?

접근 로그에서 평균이 아니라 가장 바빴던 구간의 초당 요청 수를 찾고, 예상 증가 배수와 여유를 곱한다. 과거 데이터가 없으면 예상 사용자 수와 사용자당 요청 수, 몰리는 시간으로 어림한다. 지연과 실패율 목표는 SLO에서 가져와 임계값으로 적는다. 목표를 먼저 정하지 않으면 결과를 보고 기준을 맞추게 된다.

### 부하 테스트는 통과했는데 운영에서 장애가 나는 이유는 뭘까요?

테스트가 운영과 달라서인 경우가 대부분이다. 같은 URL만 두드려 캐시가 다 맞았거나, 테스트 DB가 작아 실행 계획이 달랐거나, 외부 의존을 목으로 바꿔 요청 제한을 못 봤거나, 엔드포인트 하나만 테스트해 무거운 쓰기를 빠뜨린 경우다. 커넥션 재사용으로 TLS 비용을 놓치거나, 스파이크 속도보다 느린 오토스케일링도 원인이다. 테스트 데이터와 요청 비율을 운영 분포에 맞추는 게 첫 번째 대책이다.

### 부하 생성기가 병목인지 어떻게 알 수 있나요?

열린 모델에서 실제 처리량이 계획한 도착률보다 낮은데 서버 지연은 멀쩡하면 생성기를 의심한다. k6라면 `dropped_iterations`와 VU 부족 경고가 나온다. 필요한 VU는 도착률 × 응답 시간이라, 초당 300건에 느려질 때 2초를 버티려면 600개가 필요하다. 생성기의 CPU, 네트워크, 로컬 포트도 같이 보고, 모자라면 여러 대로 나눈다.

### 부하 테스트를 CI에 어떻게 넣나요?

크기를 나눈다. 풀 리퀘스트마다 작은 스모크 테스트로 스크립트와 기본 경로만 확인하고, 진짜 부하 테스트는 운영 크기의 스테이징에서 전용 생성기로 야간이나 릴리스 전에 돌린다. 합격선은 임계값으로 적어 넘으면 종료 코드 99로 실패하게 하고, `abortOnFail`로 일찍 멈춘다. 결과는 이전 회차와 비교해 추세로 회귀를 잡는다.
