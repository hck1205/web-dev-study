<EasyIntro>
  상품 페이지를 서버에서 그리도록 바꿨더니 다른 사람 이름이 떠 있다는 문의가 들어오는 일이 있다. 혼자 접속하는 개발 환경에서는 절대 재현되지 않는데, 서버 하나가 수많은 사람의 요청을 동시에 처리한다는 사실에서 나오는 문제다.

  SSR은 요청이 올 때마다 서버가 데이터를 가져와 컴포넌트를 실행하고 완성된 HTML을 보내는 방식이다. 브라우저는 받자마자 내용을 그릴 수 있어 첫 화면이 빠르다. 대신 데이터 조회와 렌더링이 끝나야 첫 글자가 나가고, 렌더링하는 동안 서버는 다른 요청을 받지 못한다.

  이름이 섞이는 사고는 서버를 한 사람씩 들어오는 상담실이 아니라 여러 손님이 동시에 앉는 식당 테이블로 봐야 이해된다. 모든 요청이 같이 보는 변수에 현재 사용자를 넣으면 기다리는 사이 다른 요청이 그 값을 덮어쓴다. 쿠키로 개인화한 HTML을 모두가 공유하는 캐시에 올려도 같은 사고가 난다. 사용자별 값은 요청과 함께 흘려보내고, 모두에게 같은 내용만 캐시한다.
</EasyIntro>

상품 페이지를 CSR에서 SSR로 옮기고 일주일이 지났다. 첫 화면은 확실히 빨라졌다. 그런데 고객센터에 이상한 문의가 들어온다. "상품 페이지 위에 제 이름이 아니라 다른 사람 이름이 떠 있어요." 개발 환경에서 아무리 새로고침해도 재현되지 않는다. 혼자 접속하니까 당연하다.

SSR(Server-Side Rendering)은 요청이 올 때마다 서버가 React 컴포넌트를 실행해 HTML을 만들어 보내는 방식이다. 브라우저에서 돌던 코드가 서버로 오면, 브라우저에서는 없던 문제가 따라온다. 서버 하나가 수많은 사용자의 요청을 동시에 처리한다는 사실에서 나오는 문제들이다. 이 글은 그 문제들을 실제로 재현해 보면서 SSR 서버를 운영할 때 챙길 것을 정리한다. 렌더링 방식 전체 비교는 [CSR, SSR, SSG, ISR, 스트리밍](/posts/rendering-strategies)에, CSR이 왜 느린지는 [CSR과 SPA](/posts/rendering-csr-spa)에 있다.

예제는 Node.js 22와 React 19의 `react-dom/server`로 만든 작은 서버다. 데이터 함수는 100~200ms 기다렸다가 값을 주는 가짜 API로 두었다.

## 요청 하나가 HTML이 되는 순서

SSR 서버가 하는 일은 단순하다. 주소를 보고 필요한 데이터를 가져와 컴포넌트에 넣고, 렌더링한 문자열을 응답으로 보낸다. 같은 데이터를 JSON으로도 실어 보내서 브라우저가 같은 화면을 다시 만들 수 있게 한다.

```jsx
import http from "node:http";
import { renderToString } from "react-dom/server";

http.createServer(async (req, res) => {
  const product = await getProduct(42);            // 1. 데이터
  const html = renderToString(<Page product={product} />); // 2. 렌더링
  res.writeHead(200, { "content-type": "text/html; charset=utf-8" });
  res.end(`<!doctype html>${html}
<script>window.__DATA__=${JSON.stringify(product).replace(/</g, "\\u003c")}</script>
<script src="/client.js"></script>`);              // 3. 데이터와 JS를 함께 보낸다
}).listen(3000);
```

`JSON.stringify` 결과를 HTML에 그대로 넣을 때 `<`를 이스케이프하는 줄을 빼먹으면 안 된다. 상품 설명에 `</script><script>...`가 들어 있으면 그대로 실행된다. 프레임워크는 이걸 대신 해 주지만, 직접 만들 때 가장 흔한 XSS 구멍이다.

## renderToString과 renderToPipeableStream

React가 Node.js용으로 주는 렌더링 함수는 두 가지다. `renderToString`은 트리 전체를 동기로 실행해 문자열 하나를 돌려준다. `renderToPipeableStream`은 스트림을 돌려주고, `Suspense` 경계 바깥이 준비되면 그 부분부터 흘려보낼 수 있다.

차이는 `Suspense`를 만났을 때 드러난다. 리뷰 컴포넌트가 아직 끝나지 않은 Promise를 `use`로 기다리게 하고 `renderToString`에 넣어 봤다.

```text
<main><h1>무선 이어폰</h1><!--$!--><template></template><p>리뷰 불러오는 중</p><!--/$--></main>
```

`renderToString`은 기다리지 않는다. 경계 안을 fallback으로 채우고 `<!--$!-->` 표시를 남긴다. 이 표시는 "서버가 이 경계를 끝내지 못했으니 브라우저에서 처음부터 그려라"라는 뜻이다. 리뷰는 HTML에 끝내 들어가지 않는다. 검색 로봇에게도 안 보인다. 데이터를 컴포넌트 안에서 기다리는 구조로 바꿀 거라면 `renderToString`은 맞지 않는다.

오류를 다루는 방식도 다르다. 컴포넌트가 던진 오류를 두 함수에 넣어 봤다.

```text
renderToString 바깥 오류 → 리뷰 API 503        (예외가 그대로 올라온다)
renderToString 경계 안 → <main><h1>상품</h1><!--$!--><template></template><p>리뷰 자리</p><!--/$--></main>
onError (바깥) → 리뷰 API 503
onShellError (바깥) → 리뷰 API 503
onError (경계 안) → 리뷰 API 503
onShellReady (경계 안)
stream 경계 안 → <main><h1>상품</h1><!--$!--><template></template><p>리뷰 자리</p><!--/$--></main>
```

`Suspense` 바깥에서 난 오류는 페이지 전체의 실패다. `renderToString`은 예외를 던지고, 스트림은 `onShellError`를 부른다. 이때 서버는 500 응답과 오류 페이지를 보내야 한다. 경계 안에서 난 오류는 그 부분만 fallback으로 남기고 나머지는 보낸다. 스트림에서는 `onError`로 로그가 남지만 `renderToString`은 아무 콜백 없이 조용히 fallback을 넣는다. 경계 안 오류를 놓치지 않으려면 로그를 남길 자리가 있는 쪽이 낫다.

스트림의 콜백은 응답을 보내는 시점과 상태 코드를 정하는 자리이기도 하다.

```jsx
const stream = renderToPipeableStream(<App url={req.url} />, {
  bootstrapScripts: ["/client.js"],
  onShellReady() {
    // 셸이 준비됐다. 상태 코드와 헤더는 지금 정하고 보낸다
    res.statusCode = didError ? 500 : 200;
    res.setHeader("content-type", "text/html; charset=utf-8");
    stream.pipe(res);
  },
  onShellError(err) {
    // 셸조차 못 만들었다. 정적 오류 페이지로 응답한다
    res.statusCode = 500;
    res.end("<h1>잠시 후 다시 시도해 주세요</h1>");
  },
  onError(err) {
    didError = true;
    logger.error(err); // 경계 안 오류도 여기로 온다
  },
});
```

`onShellReady`에서 `pipe`를 시작한 순간 상태 코드는 이미 나갔다. 그 뒤 경계 안에서 "상품이 없다"는 걸 알아도 404로 바꿀 수 없다. 조각을 흘려보내는 스트리밍 자체와 그 제약은 [스트리밍 SSR과 Suspense](/posts/streaming-ssr-suspense)에서 따로 다룬다. 크롤러처럼 완성된 HTML이 필요한 요청에는 `onShellReady` 대신 `onAllReady`에서 보내는 방법도 있다.

## 렌더링은 CPU를 쓰고, Node.js는 한 줄로 일한다

`renderToString`은 동기 함수다. 컴포넌트를 실행하는 동안 그 Node.js 프로세스의 이벤트 루프는 다른 일을 하지 못한다. 상품 목록 크기를 바꿔 가며 한 번 렌더링하는 시간을 쟀다(20회 중 가운데 값).

```text
NODE_ENV=production
n=100    median  0.52ms  html   6.7KB
n=1000   median  2.29ms  html  68.3KB
n=10000  median 43.35ms  html 710.0KB

NODE_ENV 없이 (개발 빌드)
n=100    median  5.61ms
n=1000   median 12.87ms
n=10000  median 179.27ms
```

두 가지가 보인다. 하나, 항목 수가 10배일 때 시간은 10배보다 더 늘었다. 문자열이 커질수록 메모리 할당과 GC 비용이 붙는다. 둘, `NODE_ENV=production`을 빠뜨리면 React가 개발용 검사를 다 켠 채 돌아서 4~5배 느리다. 컨테이너 이미지에서 이 환경 변수가 빠져 있는 경우가 생각보다 흔하다. 서버 로그에 React 개발 경고가 찍히고 있다면 의심해 본다.

렌더링이 무거우면 그 시간만큼 다른 요청이 줄을 선다. 1만 개짜리 목록 페이지(혼자 받으면 22ms)를 10개 동시에 요청하고, 그 사이에 아무 일도 안 하는 `/fast`를 하나 끼워 넣었다.

```bash
# 무거운 페이지 10개를 동시에 보내고, 가벼운 요청 하나를 끼워 넣는다
for i in $(seq 1 10); do
  curl -s -o /dev/null -w "big#$i ttfb=%{time_starttransfer}s\n" localhost:4201/big &
done
sleep 0.005
curl -s -o /dev/null -w "fast ttfb=%{time_starttransfer}s\n" localhost:4201/fast
wait
```

```text
big#2 ttfb=0.013552s
big#8 ttfb=0.034243s
big#6 ttfb=0.051751s
big#1 ttfb=0.074741s
big#10 ttfb=0.082582s
big#3 ttfb=0.093963s
big#5 ttfb=0.110678s
big#7 ttfb=0.139809s
big#9 ttfb=0.159726s
big#4 ttfb=0.167330s
fast ttfb=0.163258s
```

`/fast`는 응답에 1ms도 안 걸리는 엔드포인트인데 163ms를 기다렸다. 앞의 렌더링이 끝날 때까지 이벤트 루프가 이 요청을 집어 들지 못했기 때문이다. 헬스 체크 엔드포인트가 같은 프로세스에 있으면 트래픽이 몰릴 때 헬스 체크가 늦어져서 로드 밸런서가 멀쩡한 서버를 빼 버리는 일도 생긴다. 이벤트 루프가 막히는 원리는 [이벤트 루프](/posts/event-loop)에서 다뤘다.

대응은 여러 층에서 한다. 같은 HTML을 여러 번 만들지 않게 캐시하고(뒤에서 본다), 한 페이지에 그리는 양을 줄이고(긴 목록은 페이지를 나누거나 아래쪽을 브라우저에서 그린다), 코어 수만큼 프로세스나 파드를 띄운다. 스트리밍은 첫 바이트를 앞당기지만 렌더링에 드는 CPU 총량은 줄이지 않는다.

## 서버 안에도 폭포가 있다

SSR의 TTFB는 데이터 조회 시간과 렌더링 시간의 합이다. 데이터를 어떻게 부르느냐에 따라 같은 페이지의 TTFB가 두 배 넘게 차이 난다. 상품(100ms), 리뷰(150ms), 추천(200ms)을 하나씩 `await`한 경우와 `Promise.all`로 함께 부른 경우다.

```jsx
// /seq: 앞의 조회가 끝나야 다음을 시작한다
const product = await getProduct();
const reviews = await getReviews();
const recs = await getRecs();

// /par: 서로 기다릴 이유가 없으면 함께 출발한다
const [product, reviews, recs] = await Promise.all([getProduct(), getReviews(), getRecs()]);
```

```bash
curl -s -o /dev/null -w "/seq starttransfer=%{time_starttransfer}s\n" localhost:4201/seq
curl -s -o /dev/null -w "/par starttransfer=%{time_starttransfer}s\n" localhost:4201/par
```

```text
/seq starttransfer=0.454853s
/par starttransfer=0.201334s
```

일렬로 부르면 세 시간의 합(450ms), 함께 부르면 가장 느린 것(200ms)이다. 실제 코드에서는 이 `await`들이 한 함수에 모여 있지 않고 레이아웃, 페이지, 컴포넌트에 흩어져 있어서 일렬이 된 줄 모르기 쉽다. 추천이 상품 카테고리를 알아야 하는 것처럼 진짜로 앞의 결과가 필요한 조회만 기다리게 둔다.

## 모듈 변수는 모든 사용자가 같이 쓴다

이제 처음 장면의 다른 사람 이름이다. 브라우저에서는 모듈 최상위 변수가 그 사용자 한 명의 것이다. 서버에서는 프로세스가 뜰 때 한 번 만들어지고, 그 프로세스가 처리하는 모든 요청이 같은 변수를 본다. 아래처럼 "현재 사용자"를 모듈 변수에 넣는 코드가 문제를 만든다.

```jsx
let currentUser = null; // 모듈 변수: 이 프로세스의 모든 요청이 공유한다

function Hello() {
  return <p id="hello">{currentUser}님 안녕하세요</p>;
}

// 요청 처리
currentUser = userFrom(req);  // 1. 이번 요청의 사용자를 넣고
await getProduct();           // 2. 100ms 기다리는 동안 다른 요청이 끼어든다
send(res, renderToString(<Hello />)); // 3. 그때의 currentUser로 그린다
```

alice의 요청을 보내고 20ms 뒤에 bob의 요청을 보냈다.

```bash
curl -s -b user=alice localhost:4201/leaky &  # alice
sleep 0.02
curl -s -b user=bob localhost:4201/leaky      # bob
```

```text
alice 요청 → <p id="hello">bob<!-- -->님 안녕하세요</p>
bob 요청   → <p id="hello">bob<!-- -->님 안녕하세요</p>
```

```jsx
import { AsyncLocalStorage } from "node:async_hooks";

}

als.run({ user: userFrom(req) }, async () => {
  await getProduct();
  send(res, renderToString(<Hello />));
});
```

```text
bob 요청   → <p id="hello">bob<!-- -->님 안녕하세요</p>
```

Next.js의 `cookies()`, `headers()`도 내부적으로 이런 요청별 저장소를 쓴다. 상태 관리 라이브러리에서도 같은 함정이 있다. Redux store, Zustand store, TanStack Query의 `QueryClient`를 모듈 최상위에서 하나 만들어 서버에서도 쓰면 사용자끼리 상태가 섞인다. 서버에서는 요청마다 새로 만들고, 브라우저에서만 하나를 계속 쓰는 게 이 라이브러리들의 SSR 안내 방식이다.

## 요청이 쌓일수록 무거워지는 서버

모듈 변수의 다른 얼굴은 메모리다. 브라우저 탭은 닫으면 사라지지만 서버 프로세스는 며칠씩 산다. "렌더링 결과를 Map에 넣어 두면 빠르겠지" 하고 주소를 키로 캐시를 만들었다고 하자.

```jsx
const htmlCache = new Map(); // 상한도, 만료도 없다

if (!htmlCache.has(req.url)) htmlCache.set(req.url, renderToString(<List />));
send(res, htmlCache.get(req.url));
```

광고 링크에는 `?utm_source=ad&fbclid=...`처럼 클릭마다 다른 값이 붙는다. 그런 주소로 요청을 보내며 힙 크기를 봤다.

```text
시작             heapUsed=8MB    rss=65MB    entries=0
요청 10000개 뒤  heapUsed=376MB  rss=474MB   entries=10000
요청 30000개 뒤  heapUsed=1110MB rss=1223MB  entries=30000
```

내용은 전부 같은 페이지인데 키가 다르니 사본이 3만 개 쌓였다. 컨테이너 메모리 제한에 닿으면 프로세스는 OOM으로 죽고 재시작된다. 운영에서는 "며칠마다 파드가 재시작된다", "배포 직후엔 빠르다가 점점 느려진다"로 나타난다. 서버 안 캐시는 개수 상한(LRU)과 만료 시간을 두고, 키에서 추적용 쿼리를 빼서 정규화한다. 힙 스냅샷으로 무엇이 메모리를 잡고 있는지 찾는 방법은 [자바스크립트 메모리 누수 찾기](/posts/js-memory-leak)에 정리했다. 대부분은 프로세스 안에 캐시를 두기보다 다음 절의 HTTP 캐시에 맡기는 편이 낫다.

## SSR 결과를 캐시에 올리기

모두에게 같은 페이지라면 요청마다 렌더링할 이유가 없다. 응답에 `Cache-Control: public, s-maxage=60`을 붙이면 CDN이나 리버스 프록시가 60초 동안 사본을 들고 있다가 대신 답한다. `stale-while-revalidate=300`을 더하면 만료 뒤 300초 동안은 옛 사본을 주면서 뒤에서 새로 받아 온다. 헤더 하나하나의 뜻은 [HTTP 캐시와 CDN](/posts/http-caching-cdn)에 자세히 있다.

여기서 처음 장면의 두 번째 원인이 나온다. 쿠키를 읽어 이름을 HTML에 넣으면서 `public`을 붙인 페이지다. nginx `proxy_cache`를 앞에 두고 alice와 bob이 차례로 요청했다.

```nginx
proxy_cache_path /var/cache/nginx/ssr keys_zone=ssr:10m;
server {
  listen 80;
  location / {
    proxy_pass http://127.0.0.1:4201;
    proxy_cache ssr;
    add_header X-Cache-Status $upstream_cache_status always;
  }
}
```

```bash
for u in alice bob; do
  curl -s -D - -b user=$u localhost:4280/cached | grep -iE '^cache-control|^x-cache|id="hello"'
done
```

```text
== alice
cache-control: public, s-maxage=60
X-Cache-Status: MISS
<p id="hello">alice<!-- -->님 안녕하세요</p>
== bob
cache-control: public, s-maxage=60
X-Cache-Status: HIT
<p id="hello">alice<!-- -->님 안녕하세요</p>
```

bob은 캐시에 남은 alice의 페이지를 받았다. 캐시 키는 기본적으로 주소라서 쿠키가 달라도 같은 요청으로 본다. 같은 서버에서 `Cache-Control: private, no-store`로 바꾸면 두 번 다 `MISS`가 나고 각자 자기 이름을 받는다.

<Callout kind="warning" title="쿠키를 읽어 그린 HTML에 public을 붙이지 않는다">
사용자마다 다른 내용이 하나라도 HTML에 들어가면 그 응답은 공유 캐시에 넣으면 안 된다. 프레임워크가 기본값으로 캐시 헤더를 붙이는지, CDN이 원본 헤더를 무시하고 강제로 캐시하는 규칙이 있는지도 함께 확인한다. 이미 새어 나갔다면 CDN에서 그 경로를 즉시 무효화하고, 개인화 부분을 HTML에서 빼낸 뒤 다시 연다.
</Callout>

`Vary: Cookie`를 붙이면 쿠키 값마다 사본을 따로 두니 섞이지는 않는다. 하지만 쿠키는 사용자마다 다르고 분석 도구 쿠키까지 섞여 있어서 사본이 사용자 수만큼 생기고 적중률은 거의 0이 된다. 그래서 보통은 페이지를 둘로 나눈다. 모두에게 같은 본문(상품 이름, 설명, 가격)은 `public`으로 캐시하고, 이름, 장바구니 수, 회원가 같은 개인화 조각은 HTML에서 빼서 브라우저가 따로 부르거나 캐시하지 않는 작은 응답으로 받는다. 로그인 여부 정도만 갈린다면 로그인 쿠키가 없는 요청만 캐시하는 CDN 규칙을 두기도 한다.

## 상태 코드는 렌더링하기 전에 정한다

SSR 페이지의 상태 코드는 검색 엔진과 모니터링에게 중요한 정보다. 없는 상품을 200으로 "상품을 찾을 수 없습니다"라고 그리면 검색 엔진은 그 주소를 계속 색인하려 하고, 에러율 대시보드에는 아무것도 안 잡힌다. CSR의 소프트 404와 같은 문제다.

```jsx
const product = await getProduct(id);
if (!product) {
  res.statusCode = 404;                   // 렌더링 전에 정한다
  return send(res, renderToString(<NotFound />));
}
if (product.movedTo) {
  res.writeHead(301, { location: `/p/${product.movedTo}` }); // 옮긴 상품은 리다이렉트
  return res.end();
}
```

판단에 필요한 데이터는 렌더링을 시작하기 전에 가져온다. 렌더링 도중, 혹은 스트리밍으로 첫 조각을 보낸 뒤에는 상태 코드를 바꿀 수 없다. 렌더링 중 예외는 500으로, 데이터 API가 일시적으로 실패했다면 503으로 응답하고 오류 페이지는 `no-store`로 보내서 캐시가 오류 화면을 1분 동안 모두에게 나눠 주는 일을 막는다.

## 운영 중인 SSR 서버가 느려졌을 때

"페이지가 느리다"는 신고가 오면 먼저 어느 구간이 느린지 나눈다. `curl`의 시간 값 몇 개로 대부분 갈린다.

```bash
# DNS, 연결, TLS, 첫 바이트, 전체 시간을 나눠 본다
curl -s -o /dev/null -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://shop.example.com/p/42
```

로컬 예제 서버의 `/par`에 같은 명령을 돌리면 이렇게 나온다. HTTP라서 `tls`는 0이다.

```text
dns=0.000020 connect=0.000149 tls=0.000000 ttfb=0.202886 total=0.202985
```

`ttfb`에서 `tls`를 뺀 값이 서버가 HTML을 만드는 데 쓴 시간에 가깝다. 이 값이 크면 서버 안이 느린 것이고, `total`과 `ttfb` 차이가 크면 HTML이 크거나 망이 느린 것이다. 서버 안이 느리다면 `Server-Timing`으로 조회와 렌더링 중 어디인지 보고, 조회라면 일렬로 기다리는 `await`부터 찾는다. 렌더링이라면 `NODE_ENV`부터 확인한다.

```bash
# 실행 중인 Node 프로세스의 환경 변수에 NODE_ENV가 있는지 본다
sudo cat /proc/$(pgrep -f "node server" | head -1)/environ | tr '\0' '\n' | grep NODE_ENV
```

아무것도 안 나오면 개발 빌드로 돌고 있다. 트래픽이 몰릴 때만 느리다면 이벤트 루프가 막히는 것이다. 응답 시간이 요청 수에 비례해 늘어나고, CPU가 한 코어만 100%에 붙어 있다. 시간이 지날수록 느려지고 메모리가 계속 오른다면 앞 절의 서버 안 캐시나 요청마다 등록하고 지우지 않는 리스너를 의심한다. SSR 서버 앞에 nginx를 두는 구성은 [nginx 리버스 프록시](/posts/nginx-reverse-proxy)에서 다뤘다.

## 다시 다른 사람 이름으로

처음의 다른 사람 이름은 두 경로로 생길 수 있었다. 서버 프로세스의 모듈 변수에 요청별 값을 넣었거나, 쿠키를 읽어 그린 HTML을 공유 캐시에 올렸거나. 둘 다 "서버 하나가 여러 사용자를 동시에 처리한다"는 사실을 잊어서 생긴다. SSR은 첫 화면과 검색 노출을 얻는 대신 요청마다 데이터 조회와 렌더링을 서버가 떠안는다. 그래서 TTFB는 가장 느린 조회와 일렬로 선 `await`에 묶이고, 동기 렌더링은 이벤트 루프를 붙잡는다. 같은 결과를 매번 만들지 않으려면 캐시가 필요하고, 그 캐시를 미리 만들어 두는 것이 [SSG와 ISR](/posts/rendering-ssg-isr)이다.

## 면접에서 나올 만한 질문

### SSR은 어떻게 동작하고, CSR보다 무엇이 좋아지고 나빠지나요?

요청이 오면 서버가 데이터를 가져와 컴포넌트를 실행하고, 렌더링한 HTML과 데이터, JS 주소를 함께 보낸다. 브라우저는 받자마자 내용을 그리니 FCP와 LCP가 빨라지고 봇도 내용을 읽는다. 대신 조회와 렌더링이 끝나야 첫 바이트가 나가서 TTFB가 늘고, 요청마다 서버 CPU를 쓰며, JS가 와서 하이드레이션이 끝나기 전까지는 보여도 동작하지 않는다.

### renderToString과 renderToPipeableStream은 무엇이 다른가요?

`renderToString`은 트리 전체를 동기로 렌더링해 문자열 하나를 돌려주고, `Suspense` 안에서 기다리는 부분은 기다리지 않고 fallback을 넣어 브라우저에서 다시 그리게 한다. `renderToPipeableStream`은 셸이 준비되면 먼저 보내고 경계 안은 준비되는 대로 이어 보내며, `onShellReady`, `onShellError`, `onError`, `onAllReady` 콜백으로 응답 시점과 오류 처리를 정할 수 있다. 셸을 보낸 뒤에는 상태 코드를 바꿀 수 없다.

### SSR 서버에서 다른 사용자의 정보가 보이는 사고는 왜 생기나요?

두 가지가 흔하다. 하나는 모듈 최상위 변수나 싱글턴 store에 요청별 값을 넣은 경우다. 서버 프로세스의 모듈은 모든 요청이 공유하므로 `await` 사이에 다른 요청이 값을 덮어쓴다. props, context, `AsyncLocalStorage`로 요청별 값을 흘리고 store는 요청마다 만든다. 다른 하나는 쿠키로 개인화한 HTML에 `public` 캐시 헤더를 붙여 CDN이 다른 사람에게 그 사본을 준 경우다.

### SSR 페이지의 TTFB가 길 때 어디부터 보나요?

서버 안에서 조회와 렌더링 중 어디에 시간이 드는지 나눈다. `Server-Timing` 헤더나 APM으로 구간을 재면, 대부분은 서로 상관없는 조회를 하나씩 `await`해서 시간이 더해진 경우다. `Promise.all`로 함께 부르고 정말 앞 결과가 필요한 조회만 기다리게 한다. 렌더링이 길다면 `NODE_ENV=production`인지, 한 번에 그리는 양이 과하지 않은지 본다.

### SSR 결과를 캐시하려면 무엇을 조심해야 하나요?

모두에게 같은 응답만 `public, s-maxage`로 공유 캐시에 올린다. 쿠키로 개인화한 내용이 HTML에 있으면 `private, no-store`로 막거나 개인화 부분을 HTML 밖으로 뺀다. `Vary: Cookie`는 섞이지는 않지만 사용자마다 사본이 생겨 적중률이 거의 0이 된다. 오류 페이지는 `no-store`로 보내서 캐시가 오류를 퍼뜨리지 않게 한다.

### 렌더링이 무거운 페이지에 트래픽이 몰리면 어떤 일이 생기나요?

`renderToString`은 동기라서 렌더링하는 동안 Node.js 이벤트 루프가 다른 요청을 처리하지 못한다. 요청이 줄을 서며 응답 시간이 요청 수에 비례해 늘고, 같은 프로세스의 헬스 체크까지 늦어져 로드 밸런서가 서버를 빼기도 한다. 결과를 캐시하고, 한 페이지에 그리는 양을 줄이고, 코어 수만큼 프로세스를 띄워 나눠 받는다. 스트리밍은 첫 바이트를 앞당길 뿐 CPU 총량은 줄이지 않는다.

### 없는 상품 페이지를 SSR로 그릴 때 상태 코드는 어떻게 정하나요?

렌더링을 시작하기 전에 데이터를 확인해서 없으면 404, 옮겼으면 301, 일시적 실패면 503을 정하고 그다음에 해당 화면을 그린다. 200으로 "찾을 수 없음"을 그리면 소프트 404가 되어 검색 엔진이 계속 색인하고 모니터링에도 잡히지 않는다. 스트리밍 SSR에서는 첫 조각과 함께 상태 코드가 나가므로 이런 판단은 셸 바깥에서 먼저 끝내야 한다.
