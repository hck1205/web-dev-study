<EasyIntro>
  PR을 squash 머지하고 다 쓴 브랜치를 지우려는데 Git이 "아직 완전히 합쳐지지 않았다"며 거절한다. 코드는 분명 들어갔는데도 거절하는 이유는, Git이 합쳐졌는지를 코드 내용이 아니라 커밋으로 판단하기 때문이다.

  Git은 매번 바뀐 부분만 적는 게 아니라, 커밋할 때마다 프로젝트 전체의 사진을 찍는다. 사진첩에 들어가는 건 네 종류뿐이다. 파일 내용 한 장(blob), 폴더 목록(tree), 그 순간의 사진과 작성자와 이전 사진 번호를 적은 카드(commit), 그리고 특정 카드에 붙이는 이름표(tag)다. 각각의 이름은 내용을 해시라는 함수에 넣어 나온 긴 숫자라서, 내용이 한 글자만 달라도 이름이 완전히 바뀌고, 내용이 같으면 사진이 몇 장이든 한 번만 저장된다.

  브랜치는 그냥 "마지막 카드의 번호"를 적어 둔 메모이고, 카드가 이전 카드를 가리키는 사슬이 히스토리다. squash 머지는 브랜치의 카드들을 새 카드 하나로 다시 만들기 때문에 원래 카드들은 사슬에 없고, 그래서 Git이 합쳐지지 않았다고 말한 것이다.
</EasyIntro>

PR을 squash 머지하고 로컬에서 다 쓴 브랜치를 지우려는데 `git branch -d feature/mul`이 거절당했다. "not fully merged"란다. GitHub에서는 분명 머지됨으로 나오고, main을 열어 보면 코드도 한 줄 빠짐없이 들어가 있다. 그런데 Git은 아직 안 합쳐졌다고 한다.

Git이 틀린 게 아니다. Git은 "합쳐졌다"를 코드 내용이 아니라 커밋으로 판단한다. squash 머지는 브랜치의 커밋 세 개를 하나로 뭉친 새 커밋을 main에 만들기 때문에, 원래 커밋 세 개는 main의 히스토리에 없다. 내용은 같고 커밋은 다르다. 이 차이를 알아보려면 Git이 무엇을, 어떤 이름으로 저장하는지부터 봐야 한다.

이 글은 Git이 저장하는 객체 네 가지를 직접 열어 보고, 그 이름(해시)이 어떻게 정해지는지, `.git` 폴더 안에 무엇이 있는지 본다. 끝에서는 이 지식으로 위의 squash 문제처럼 현장에서 "같은가, 다른가"를 확인하는 법을 정리한다. 파일이 작업 트리·인덱스·저장소 사이를 어떻게 오가는지는 [다음 글](/posts/git-staging-area)에서 이어 간다.

명령과 출력은 Ubuntu 24.04 LTS의 기본 패키지인 Git 2.43.0에서 실제로 실행한 것이다. Ubuntu 22.04의 기본 패키지는 2.34.1이고, 버전에 따라 다른 부분은 그때그때 적는다. 커밋 해시는 작성자, 시각, 내용이 모두 들어간 값이라 따라 해 보면 다른 값이 나온다. 파일 내용만으로 정해지는 blob 해시는 같은 내용이면 누구 컴퓨터에서든 똑같이 나온다.

```bash
# 설치된 Git 버전 확인
git --version

# Ubuntu에서 설치 (24.04는 2.43, 22.04는 2.34가 들어온다)
sudo apt update && sudo apt install -y git

# 커밋에 들어갈 이름과 이메일 (처음 한 번)
git config --global user.name "Matt"
git config --global user.email "matt@example.com"

# 새 저장소의 기본 브랜치 이름을 main으로 (2.28부터 있는 설정)
git config --global init.defaultBranch main
```

```text
git version 2.43.0
```

`init.defaultBranch`를 정하지 않으면 2.43은 여전히 `master`로 만들고 안내 문구를 띄운다. GitHub와 GitLab은 새 저장소의 기본 브랜치를 `main`으로 만드니 맞춰 두는 편이 덜 헷갈린다.

## 서버 하나에 모든 걸 맡기지 않으려고

Git 이전에 널리 쓰던 Subversion(SVN) 같은 도구는 중앙 서버 하나가 히스토리 전체를 갖고, 개발자 컴퓨터에는 최신 파일만 있는 구조였다. 커밋은 곧 서버에 올리는 일이라 네트워크가 끊기면 커밋을 못 하고, 로그를 보거나 옛 버전과 비교할 때도 서버에 물어봐야 했다. 서버 디스크가 날아가면 히스토리도 같이 날아간다.

Git은 2005년 리눅스 커널 개발에서 나왔다. 커널 팀이 쓰던 상용 분산 버전 관리 도구 BitKeeper의 무료 사용이 끝나자 리누스 토르발스가 직접 만들었다. 목표는 수천 명이 동시에 패치를 주고받아도 빠르고, 데이터가 조용히 깨지지 않는 것이었다.

분산 버전 관리에서는 `git clone`을 하면 히스토리 전체가 내 컴퓨터로 복사된다. 커밋, 로그, 비교, 브랜치는 모두 로컬에서 끝나고, 네트워크는 `push`와 `fetch`로 다른 저장소와 맞출 때만 쓴다. 저장소마다 전체 사본이 있으니 서버가 망가져도 누군가의 클론에서 되살릴 수 있다. GitHub 같은 서버는 기술적으로 특별한 존재가 아니라 "다들 거기에 맞추기로 약속한 저장소" 하나일 뿐이다.

대가도 있다. 히스토리 전체를 받으니 동영상이나 디자인 원본 같은 큰 바이너리가 쌓이면 클론이 무거워진다. 그래서 큰 파일은 Git LFS로 따로 두거나, `git clone --depth 1`(얕은 클론), `--filter=blob:none`(필요할 때 파일 내용을 받는 부분 클론)으로 받는 양을 줄인다. 큰 파일을 잠가 두고 한 사람만 고치는 작업 방식도 중앙 집중형이 더 잘 맞는다.

## 변경분이 아니라 스냅샷을 찍는다

예전 도구들은 파일마다 "이전 버전에서 무엇이 바뀌었나"를 쌓는 방식이 많았다. Git은 커밋할 때마다 프로젝트 전체의 사진(스냅샷)을 찍는다. 그렇다고 매번 모든 파일을 새로 복사하지는 않는다. 바뀌지 않은 파일은 지난 사진의 것을 그대로 가리킨다.

이게 가능한 이유는 Git이 파일을 이름이 아니라 내용으로 찾기 때문이다. 파일 내용을 해시 함수에 넣어 나온 40자리 값이 그 내용의 주소가 된다. 내용이 같으면 주소도 같으니 한 번만 저장된다. 이 방식을 내용 주소 지정(content addressing)이라고 한다.

빈 저장소에서 직접 확인해 보자.

```bash
# todo-app이라는 새 저장소를 만든다
git init todo-app
cd todo-app

# 파일 두 개를 만든다
printf "# todo-app\n" > README.md
printf "function add(a, b) {\n  return a + b;\n}\n" > app.js

# 두 파일을 인덱스에 올리고 커밋한다
git add README.md app.js
git commit -m "첫 커밋: README와 app.js"
```

```text
Initialized empty Git repository in /tmp/git-demo-1/todo-app/.git/
[main (root-commit) 2a8cce0] 첫 커밋: README와 app.js
 2 files changed, 4 insertions(+)
 create mode 100644 README.md
 create mode 100644 app.js
```

`root-commit`은 부모가 없는 첫 커밋이라는 뜻이다. `2a8cce0`은 이 커밋의 해시 앞 일곱 자리다. 이제 이 커밋이 실제로 무엇으로 이루어져 있는지 연다.

## 객체 네 가지를 직접 열어 본다

`.git/objects` 안에는 네 종류의 객체가 있다. 파일 내용인 blob, 폴더 목록인 tree, 스냅샷 한 장인 commit, 그리고 이름표 중에서 정보를 담는 annotated tag다. `git cat-file`은 이 객체를 꺼내 보는 저수준 명령이다. `-t`는 종류를, `-p`는 내용을 사람이 읽을 수 있게 보여 준다.

```bash
# HEAD(지금 커밋)의 종류
git cat-file -t HEAD

# 커밋 객체의 내용
git cat-file -p HEAD

# 그 커밋이 가리키는 tree의 내용 (^{tree}는 "이 커밋의 tree")
git cat-file -p 'HEAD^{tree}'

# tree가 가리키는 blob, 즉 app.js의 내용
git cat-file -p HEAD:app.js
```

```text
function add(a, b) {
```

커밋 객체에는 파일 내용이 없다. 최상위 tree의 해시, 작성자와 시각, 메시지가 전부다. tree에는 파일마다 모드(`100644`는 일반 파일, `100755`는 실행 파일, `040000`은 하위 폴더), 종류, 해시, 이름이 한 줄씩 있다. 파일 이름은 blob이 아니라 tree에 있다. 그래서 내용은 그대로 두고 이름만 바꾸면 blob은 새로 생기지 않고 tree만 새로 생긴다.

`sub` 함수를 추가해서 두 번째 커밋을 만든 뒤 그 커밋을 열면 `parent` 줄이 하나 생긴다.

```bash
# 두 번째 커밋 객체
git cat-file -p 06e8251

# 두 번째 커밋의 tree
git cat-file -p '06e8251^{tree}'
```

네 번째 객체인 tag도 열어 본다. 태그에는 두 종류가 있다. `git tag v1.0`처럼 만든 가벼운 태그는 커밋 해시 하나를 적은 파일일 뿐이고, `-a`를 붙인 annotated tag는 만든 사람과 날짜, 메시지를 담은 별도 객체다.

```bash
# 메시지가 있는 태그 (tag 객체가 생긴다)
git tag -a v1.0 -m "첫 릴리스"

# 가벼운 태그 (커밋을 직접 가리키는 이름표)
git tag lightweight-v1

# 두 태그의 종류를 비교
git cat-file -t v1.0
git cat-file -t lightweight-v1

# tag 객체의 내용
git cat-file -p v1.0
```

```text

object b17978b7d09b77c54a6ae592fc20ee1e764c9bed

tag v1.0
tagger Matt <matt@example.com> 1792200060 +0900

첫 릴리스
```

릴리스에는 annotated tag를 쓴다. `git describe`가 기본으로 annotated tag만 보고, GPG나 SSH 서명도 tag 객체에 붙는다. 가벼운 태그는 혼자 잠깐 표시해 둘 때 쓴다.

## 해시는 내용에서 나온다

blob의 해시는 파일 내용만으로 계산한다. 정확히는 `blob <바이트 수>` 다음에 널 문자(`\0`) 하나, 그 뒤에 파일 내용을 이어 붙인 바이트 열을 SHA-1에 넣는다. 파일 이름이나 만든 시각은 들어가지 않는다. 그래서 같은 내용이면 누구의 컴퓨터에서든 같은 해시가 나온다.

```bash
# 표준 입력으로 받은 내용의 blob 해시를 계산만 한다 (저장하지 않음)
printf 'hello\n' | git hash-object --stdin

# 파일의 blob 해시. 위 cat-file 출력의 README.md 해시와 같다
git hash-object README.md
```

```text
ce013625030ba8dba906f756967f9e9ca394464a
```

SHA-1은 2017년에 구글과 CWI가 실제 충돌(같은 해시가 나오는 서로 다른 PDF 두 개)을 만들어 보였다. Git은 2.13부터 그런 공격 패턴을 감지하는 SHA-1DC를 기본으로 써서 이 방식의 충돌은 막는다. 더 근본적인 해결은 SHA-256으로 바꾸는 것이다. `git init --object-format=sha256`으로 64자리 해시를 쓰는 저장소를 만들 수 있다. 2.29에 들어왔고 2.42부터는 실험 기능 딱지를 뗐지만, 기존 SHA-1 저장소와 섞어 쓸 수 없고 호스팅 서비스의 지원도 아직 제한적이라 실무 저장소는 대부분 SHA-1이다.

```bash
cd sha-repo
printf "hello\n" > a.txt
git hash-object a.txt
git rev-parse --show-object-format

# 원래 저장소로 돌아간다
cd ..
```

## .git 폴더가 저장소의 전부다

`git init`이 만든 `.git` 폴더가 저장소 자체다. 이 폴더를 다른 곳에 복사하면 히스토리 전체가 옮겨 가고, 지우면 히스토리가 사라지고 파일만 남는다. 아래 출력은 첫 커밋만 있던 때에 본 것이다.

```bash
# .git 안의 주요 항목
ls .git

# 지금 어느 브랜치에 있는지
cat .git/HEAD

# 브랜치는 커밋 해시 하나를 적은 파일이다
ls .git/refs/heads
cat .git/refs/heads/main

# 첫 커밋 직후의 객체 파일들. 해시 앞 두 자리가 폴더 이름이다
find .git/objects -type f
```

```text

2a8cce00ee30d50dea8d6c5219751694fe7827af
```

첫 커밋 하나에 객체가 넷이다. 커밋(`2a8cce0`), tree(`e330fc9`), blob 두 개. 앞에서 `cat-file`로 본 해시와 그대로 맞는다.

각 항목이 하는 일은 이렇다.

- `HEAD`: 지금 서 있는 곳. 보통은 `ref: refs/heads/main`처럼 브랜치 이름을 가리키고, 브랜치가 다시 커밋을 가리킨다.
- `refs/heads/`: 로컬 브랜치. `refs/tags/`에는 태그가, `refs/remotes/`에는 원격 브랜치의 마지막 위치가 있다. 브랜치가 많아지면 `packed-refs` 파일 하나에 모아 두기도 한다.
- `objects/`: 앞에서 본 네 종류의 객체.
- `index`: 다음 커밋에 들어갈 파일 목록. [다음 글](/posts/git-staging-area)에서 자세히 본다.
- `logs/`: 브랜치와 HEAD가 언제 어디로 움직였는지 기록하는 reflog. 실수를 되돌릴 때 생명줄이 된다.
- `config`: 이 저장소에만 적용되는 설정.
- `hooks/`: 커밋 전후, 푸시 전에 자동으로 돌릴 스크립트 자리.

브랜치가 파일 하나라는 사실이 중요하다. 브랜치를 만드는 건 41바이트짜리 파일 하나를 쓰는 일이라 아무리 큰 저장소에서도 순식간에 끝난다. 이 이야기는 [브랜치 글](/posts/git-branch-merge)에서 이어진다.

## 현장에서 해시로 "같은가"를 확인하는 순간

객체와 해시를 알고 나면 평소에 막연하게 넘기던 질문 몇 개에 명령 하나로 답할 수 있다.

처음의 squash 머지 상황부터 재현한다. feature/mul에 커밋 세 개를 쌓고 `git merge --squash`로 main에 한 커밋으로 넣었다. GitHub의 "Squash and merge" 버튼이 하는 일과 같다.

```bash
# 두 브랜치의 히스토리
git log --oneline --graph --all

# 머지됐다고 보는 브랜치 목록, 그리고 지우기 시도
git branch --merged main
git branch -d feature/mul
```

```text
* 3faeb7a mul 작업 3
* 4f3ab71 mul 작업 2
* afdac1f mul 작업 1
| * a46da40 mul 함수 (#12)
|/  
* 582bfa6 주석 하나 더
* f3fa467 주석 추가
* 6c1527a 첫 커밋

* main
error: the branch 'feature/mul' is not fully merged.
If you are sure you want to delete it, run 'git branch -D feature/mul'
```

`--merged`는 "이 브랜치의 끝 커밋이 main의 조상인가"만 본다. `3faeb7a`는 main에서 부모를 따라 거슬러 올라가도 나오지 않으니 머지되지 않은 브랜치다. 그럼 내용은 정말 같을까. 커밋 해시는 부모와 시각이 달라 당연히 다르지만, tree 해시는 내용만으로 정해진다.

```bash
# 두 브랜치 끝 커밋의 최상위 tree 해시
git rev-parse 'main^{tree}' 'feature/mul^{tree}'

# 내용 차이가 있으면 파일 목록이 나온다. 아무것도 안 나오면 같다
git diff --stat feature/mul main
```

```text
39b47ed72e6738da9e8e58925baa0ebeefc88e34
39b47ed72e6738da9e8e58925baa0ebeefc88e34
```

tree 해시가 같으면 두 스냅샷의 파일 내용은 한 바이트도 다르지 않다. 이제 안심하고 `git branch -D`로 지워도 된다. 그 사이에 main에 다른 커밋이 들어왔다면 tree가 달라지니 `git diff`로 차이를 직접 본다. rebase로 커밋을 정리한 뒤 "정리 전과 결과물이 같은가"를 확인할 때도 같은 방법을 쓴다. 해시 하나가 그 아래 전체를 대신하는 이 구조를 머클 트리라고 하고, 복제본 동기화나 인증서 투명성 로그에서 어떻게 쓰이는지는 [머클 트리 글](/posts/merkle-tree)에서 다룬다.

CI 캐시 키를 정할 때도 blob 해시가 쓸모 있다. 의존성 캐시는 lock 파일이 바뀔 때만 새로 만들면 되는데, lock 파일의 blob 해시는 내용이 그대로면 커밋이 몇 개 쌓여도 변하지 않는다.

```bash
# 지금 커밋과 두 커밋 전의 package-lock.json blob 해시
git rev-parse HEAD:package-lock.json HEAD~2:package-lock.json

# tree에서 그 파일 항목만
git ls-tree HEAD package-lock.json
```

```text
ea4d7907814abf56a69559963ff441f8c430b129
ea4d7907814abf56a69559963ff441f8c430b129
100644 blob ea4d7907814abf56a69559963ff441f8c430b129	package-lock.json
```

GitHub Actions의 `hashFiles()`처럼 CI 도구가 주는 해시 함수도 원리는 같다. 내용이 키가 되니 캐시가 엉뚱하게 깨지지 않는다.

배포된 서버에 어떤 코드가 올라가 있는지 물어볼 때는 `git describe`가 짧은 답을 준다. 가장 가까운 annotated tag에서 몇 커밋 떨어졌는지와 커밋 해시를 붙여 준다. 빌드할 때 이 값을 버전 문자열로 넣어 두면 장애가 났을 때 "그 서버는 어느 커밋인가"를 바로 안다.

```bash
# 가장 가까운 annotated tag 기준의 이름
git describe
```

```text
v1.0-2-g582bfa6
```

`v1.0` 뒤로 커밋 2개, 지금 커밋은 `582bfa6`이라는 뜻이다(`g`는 git의 머리글자). 가벼운 태그까지 보려면 `--tags`를 붙인다. 저장소가 왜 이렇게 큰지 찾는 법과 큰 파일을 히스토리에서 빼는 법은 [문제 해결 글](/posts/git-troubleshooting)에서, add만 해 둔 내용을 객체 저장소에서 되찾는 법은 [stash와 reflog 글](/posts/git-stash-reflog)에서 다룬다.

## blob·tree·commit, 그리고 브랜치는 파일 하나

Git은 파일 내용을 해시로 이름 붙인 blob, 폴더 목록인 tree, 스냅샷 한 장인 commit을 `.git/objects`에 쌓고, 브랜치는 그 커밋을 가리키는 파일 하나로 둔다. 이름이 내용에서 나오니 내용이 같으면 같은 객체이고, 부모 해시가 커밋에 들어가니 히스토리를 조용히 바꿀 수 없다. 처음의 squash 브랜치가 "안 합쳐졌다"고 나온 것도 커밋은 다르고 tree만 같아서다. 다음 글에서는 이 객체들이 작업 트리와 인덱스를 거쳐 어떻게 만들어지는지 따라간다.

## 면접에서 나올 만한 질문

### Git과 SVN 같은 중앙 집중형 버전 관리의 차이는 무엇인가요?

Git은 클론마다 히스토리 전체를 갖는 분산형이라 커밋, 로그, 비교, 브랜치가 모두 로컬에서 네트워크 없이 끝난다. 원격 서버는 저장소 사본 중 하나일 뿐이고, 서버가 망가져도 아무 클론에서나 복구할 수 있다. 중앙 집중형은 서버 하나가 히스토리를 갖고 커밋이 곧 서버 반영이라 단순하고 파일 잠금 같은 통제가 쉽지만, 서버와 네트워크에 묶인다. 큰 바이너리가 많은 저장소에서는 Git도 LFS나 부분 클론을 함께 쓴다.

### Git은 변경분(diff)을 저장하나요, 스냅샷을 저장하나요?

논리적으로는 커밋마다 프로젝트 전체의 스냅샷을 저장한다. 커밋은 최상위 tree를 가리키고, tree는 파일 내용인 blob들을 가리킨다. 바뀌지 않은 파일은 같은 blob을 그대로 가리키니 중복 저장되지 않는다. 디스크에서는 gc나 전송 때 packfile로 묶으면서 비슷한 객체끼리 delta 압축을 하지만, 그건 저장 방식의 최적화이고 모델은 스냅샷이다.

### Git의 객체 종류와 각각의 역할을 설명해 주세요.

blob은 파일 내용만 담고 이름은 모른다. tree는 폴더 하나의 목록으로, 항목마다 모드·종류·해시·이름을 담는다. commit은 최상위 tree, 부모 커밋, 작성자와 커미터, 메시지를 담는다. annotated tag는 특정 객체를 가리키며 태그한 사람과 메시지, 서명을 담는다. 네 객체 모두 "종류 크기\0내용"의 SHA-1 해시로 이름이 정해져서, 내용이 같으면 같은 객체가 된다.

### 커밋 해시는 무엇으로 결정되나요? 메시지만 고쳐도 바뀌나요?

커밋 객체 전체, 즉 tree 해시, 부모 해시, author와 committer(시각 포함), 메시지의 해시라서 메시지만 고쳐도 바뀐다. 부모 해시가 들어가므로 과거 커밋 하나를 바꾸면 그 뒤 모든 커밋의 해시가 바뀐다. 그래서 amend나 rebase는 커밋을 고치는 게 아니라 새 커밋을 만드는 일이고, 이미 공유한 커밋에 하면 다른 사람의 히스토리와 어긋난다.

### squash 머지한 브랜치를 git branch -d로 지우면 왜 거절되나요?

`-d`는 브랜치의 끝 커밋이 현재 브랜치의 조상일 때만 지운다. squash 머지는 브랜치의 커밋들을 하나로 합친 새 커밋을 만들기 때문에, 원래 커밋은 main 히스토리에 없어서 머지되지 않은 것으로 보인다. 내용이 같은지는 두 커밋의 `^{tree}` 해시를 비교하거나 `git diff`가 비어 있는지로 확인하고, 같으면 `-D`로 지운다.

### SHA-1 충돌 공격이 나왔는데 Git은 안전한가요?

2017년에 실제 SHA-1 충돌이 공개된 뒤 Git은 2.13부터 충돌 공격 패턴을 감지하는 SHA-1DC를 기본으로 써서 알려진 방식의 공격은 막는다. 근본적인 대책은 SHA-256 저장소(`git init --object-format=sha256`)인데, 기존 SHA-1 저장소와 섞어 쓸 수 없고 호스팅 서비스 지원이 제한적이라 아직 대부분은 SHA-1을 쓴다. 해시는 무결성 확인용이고, 누가 만들었는지까지 보장하려면 커밋·태그 서명을 따로 쓴다.
