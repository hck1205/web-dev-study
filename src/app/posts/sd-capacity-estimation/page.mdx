이 시리즈에서 이 글의 자리: [⑨ 지연 시간과 단위 숫자](/posts/sd-latency-numbers)에서 동작 하나에 드는 시간과 데이터 크기의 단위를 모았다. 이 글은 그 숫자로 서비스 전체의 규모를 어림한다. 다음 글은 [⑪ 설계 면접 진행법](/posts/sd-interview-framework)이고, 그다음 [⑫ 요청 수 제한기 설계](/posts/sd-rate-limiter-design)에서 이 계산을 실제 설계에 쓴다. 앞의 [① 서버 한 대](/posts/sd-start-single-server)부터 [⑧ 샤딩 입문](/posts/sd-sharding-intro)까지가 이 계산으로 고를 부품들이다.

맛집 리뷰 앱이 투자를 받았다. 내년 목표는 월간 사용자 1,000만 명이다. 회의에서 이런 질문이 나온다. "그때 서버는 몇 대가 필요해요? DB 하나로 버텨요? 사진 저장 비용은 한 달에 얼마쯤 나와요?"

아직 그 사용자는 없으니 정확한 답은 아무도 모른다. 그래도 "모른다"고 끝내면 아무것도 준비할 수 없다. 필요한 건 자릿수가 맞는 답이다. 서버가 5대인지 500대인지, 사진이 수십 TB인지 수 PB인지만 맞아도 어떤 구조를 고를지가 정해진다.

이렇게 종이 한 장에 가정을 적고 곱셈 나눗셈 몇 번으로 규모를 가늠하는 것을 봉투 뒷면 계산(back-of-the-envelope estimation)이라고 부른다. 봉투 뒷면에 끄적일 정도로 간단하게 한다는 뜻이다. 시스템 설계 면접에서도 거의 빠지지 않고 나온다.

## 가정부터 적는다

계산은 숫자가 아니라 가정에서 시작한다. 가정이 적혀 있어야 나중에 틀렸을 때 어디를 고칠지 안다. 맛집 리뷰 앱의 가정을 이렇게 잡았다.

```js
const A = {
  mau: 10_000_000,        // 월간 활성 사용자 (MAU)
  dauRatio: 0.4,          // 그중 매일 쓰는 비율
  readsPerUser: 30,       // 사용자 1명의 하루 읽기 요청
  detailViewsPerUser: 20, // 그중 식당 상세 조회
  peakFactor: 3,          // 저녁 피크 / 하루 평균
  reviewRatio: 0.05,      // DAU 중 하루에 리뷰 1개를 쓰는 비율
  photosPerReview: 2,
  photoKB: 500,           // 원본을 줄여 저장한 크기
  thumbsPerDetail: 10,    // 상세 화면에 뜨는 썸네일 수
  thumbKB: 50,
  years: 5,               // 보관 기간
};
```

MAU(Monthly Active Users)는 한 달에 한 번이라도 쓴 사람 수, DAU(Daily Active Users)는 하루에 쓴 사람 수다. 둘의 비율은 서비스 성격에 따라 크게 다르다. 메신저는 MAU의 대부분이 매일 쓰고, 여행 예약 앱은 그 비율이 훨씬 낮다. 맛집 앱은 그 중간쯤인 40%로 잡았다.

이 숫자들은 어디서 오나. 이미 서비스가 있으면 로그와 분석 도구에서 가져온다. 새 서비스라면 비슷한 서비스의 공개 자료나 기획 목표에서 가져오고, 그것도 없으면 그럴듯한 값을 고른 뒤 "이렇게 가정했다"고 말한다. 면접에서도 마찬가지다. 면접관이 숫자를 주지 않으면 내가 정하고, 정한 숫자를 소리 내어 확인받는다.

## 하루를 86,400초로 나누면 초당 요청 수

서버가 버틸 수 있는지를 따질 때 쓰는 단위는 초당 요청 수, QPS(Queries Per Second)다. 웹 API에서는 RPS(Requests Per Second)라고도 한다. 하루 요청 수를 하루의 초(24 × 60 × 60 = 86,400)로 나누면 나온다.

## 평균으로 서버를 고르면 저녁에 무너진다

사람들은 하루 종일 고르게 앱을 쓰지 않는다. 맛집 앱이면 점심 직전과 저녁 6~8시에 몰리고, 새벽에는 거의 없다. 서버는 평균이 아니라 가장 바쁜 시간을 버텨야 한다. 피크가 평균의 몇 배인지는 서비스마다 다르고, 실제로는 분 단위 요청 수 그래프에서 읽는다. 자료가 없으면 2~3배로 가정하는 경우가 많다. 여기서는 3배로 잡았다.

## 읽기와 쓰기를 따로 센다

같은 계산을 쓰기에도 한다. DAU 400만 명 중 5%가 하루에 리뷰 하나를 쓰면 하루 20만 개다. 86,400으로 나누면 초당 2.3개, 피크라도 7개 정도다. 직접 돌려 본 계산 결과다(`estimate.js`는 위의 가정 객체로 이 글의 계산을 모두 하는 스크립트다).

```bash
# 가정 객체로 QPS, 저장 공간, 전송량을 계산한다. 인자는 리뷰 한 줄의 바이트 수
node estimate.js 502
```

```text
DAU                  4,000,000명
읽기 QPS 평균/피크     1,389 / 4,167
리뷰 쓰기             하루 200,000개, 평균 2.3/초, 피크 6.9/초
읽기 : 쓰기            600 : 1
사진 저장             하루 200GB, 5년 365TB
리뷰 행 저장           하루 0.1GB, 5년 183GB
썸네일 전송량          하루 40TB, 평균 3.7Gbps, 피크 11.1Gbps
```

읽기와 쓰기의 비율이 600 대 1이다. 이 비율 하나가 구조를 크게 정한다. 읽기가 압도적으로 많으니 [④ DB 복제](/posts/sd-db-replication-intro)로 읽기를 복제본에 나누고 [⑤ 캐시 계층](/posts/sd-cache-and-cdn-tier)을 앞에 두는 것이 효과가 크다. 반대로 쓰기가 초당 7개 정도면 주 DB 한 대로 충분하다. 쓰기를 여러 DB에 나누는 [⑧ 샤딩](/posts/sd-sharding-intro)은 아직 필요 없다.

## 한 줄이 몇 바이트인지는 재 보면 된다

저장 공간을 계산하려면 리뷰 하나가 몇 바이트인지 알아야 한다. 짐작해도 되지만 PostgreSQL 16에 표를 만들고 리뷰 10만 개를 넣어 실제로 쟀다. 본문은 한글 100~200자 정도로 했다.

```sql
-- 리뷰 표와, 식당별 최신 리뷰를 찾는 인덱스
CREATE TABLE reviews (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  restaurant_id bigint      NOT NULL,
  user_id       bigint      NOT NULL,
  rating        smallint    NOT NULL,
  body          text        NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX reviews_restaurant_created ON reviews (restaurant_id, created_at DESC);

-- 짧은 한글 문장을 6~12번 반복한 본문으로 10만 개를 넣는다
INSERT INTO reviews (restaurant_id, user_id, rating, body)
SELECT (random() * 500000)::bigint, (random() * 10000000)::bigint, 1 + (random() * 4)::int,
       repeat('국물이 진하고 면이 쫄깃하다 ', 6 + (random() * 6)::int)
FROM generate_series(1, 100000);
VACUUM ANALYZE reviews;

-- 본문 글자 수와 바이트 수, 한 행의 크기
SELECT round(avg(length(body)))         AS avg_chars,
       round(avg(octet_length(body)))   AS avg_body_bytes,
       round(avg(pg_column_size(r.*)))  AS avg_row_bytes
FROM reviews r;

-- 표와 인덱스를 합친 실제 디스크 크기
SELECT pg_size_pretty(pg_relation_size('reviews'))       AS heap,
       pg_size_pretty(pg_indexes_size('reviews'))        AS indexes,
       pg_size_pretty(pg_total_relation_size('reviews')) AS total,
       pg_total_relation_size('reviews') / 100000        AS bytes_per_review;
```

```text
 avg_chars | avg_body_bytes | avg_row_bytes
-----------+----------------+---------------
       144 |            360 |           424
(1 row)

 heap  | indexes | total | bytes_per_review
-------+---------+-------+------------------
 42 MB | 6344 kB | 48 MB |              502
(1 row)
```

첫 결과에서 볼 곳은 글자 수와 바이트 수의 차이다. 144자인데 360바이트다. UTF-8에서 한글 한 글자는 3바이트라서, 한글 위주의 글은 글자 수의 2~3배를 잡아야 한다. 행 하나는 424바이트이고, 행마다 붙는 머리 정보와 인덱스, 페이지의 빈 공간까지 합치면 리뷰 하나에 디스크 502바이트를 쓴다.

그래서 리뷰 텍스트는 하루 20만 개 × 약 500바이트 = 약 100MB, 5년이면 183GB다. 복제본 두 대를 두면 세 벌이고 백업도 따로 있지만, 그래도 DB 서버 한 대의 디스크에 충분히 들어간다.

## 사진이 저장 공간의 거의 전부다

리뷰 하나에 500KB짜리 사진이 평균 2장 붙으면 리뷰 하나에 1MB다. 텍스트 500바이트의 2,000배다. 하루 200GB, 5년이면 365TB가 된다. 저장소가 데이터를 세 벌씩 복제한다면 실제로 차지하는 공간은 1PB를 넘는다.

이 숫자가 두 가지를 정한다. 사진은 DB에 넣지 않고 오브젝트 스토리지(S3처럼 파일을 키로 저장하고 꺼내는 저장소)에 두고, DB에는 그 주소만 적는다. 그리고 저장 비용이 계속 쌓이니 오래된 원본은 더 싼 저장 등급으로 옮기는 규칙을 처음부터 생각해 둔다.

텍스트와 사진의 크기 차이를 보면 어림셈에서 무엇을 무시해도 되는지도 보인다. 365TB 앞에서 183GB는 0.05%다. 저장 공간 계산에서는 사진, 영상처럼 가장 큰 것 하나만 제대로 세면 자릿수가 맞는다.

## 밖으로 나가는 바이트

저장보다 놓치기 쉬운 것이 전송량이다. 식당 상세 화면 하나에 50KB짜리 썸네일이 10장 뜨면 화면 하나에 500KB다. DAU 400만 명이 하루 20번씩 상세를 보면 하루 40TB가 나간다.

초당으로 바꾸면 평균 3.7Gbps, 피크에는 11Gbps다. 계산은 이렇다. 40TB는 40 × 10¹² 바이트이고 비트로는 8을 곱한다. 이를 86,400초로 나누면 약 3.7 × 10⁹ 비트, 즉 3.7Gbps다. 바이트와 비트 단위를 바꿀 때 8을 곱하는 걸 잊으면 여기서 8배가 틀린다.

웹 서버 몇 대의 회선으로 11Gbps를 내보내는 건 비싸고, 사용자에게도 멀다. 그래서 이 숫자가 나오면 CDN을 붙인다. 아래 그림은 피크 4,167 QPS의 읽기가 각 층에서 얼마나 걸러지는지 보여 준다.

## 캐시에 올릴 몫과 서버 대수

캐시 메모리는 "자주 읽히는 것만 올린다"로 어림한다. 흔히 쓰는 가정은 요청의 80%가 데이터의 20%에 몰린다는 것이다. 식당이 50만 곳이고 상세 정보가 식당당 8KB면 전체가 4GB다. 그중 인기 있는 20%만 올리면 0.8GB이고, Redis의 키 관리 비용을 감안해 1.5배를 잡아도 1.2GB다. Redis 한 대로 충분하다. 이 80 대 20은 가정일 뿐이라, 실제 서비스에서는 키별 조회 수로 확인한다.

웹 서버 대수는 세 가지로 정한다. 피크 QPS, 서버 한 대가 처리할 수 있는 QPS, 그리고 평소에 얼마나 여유를 둘지다. 한 대가 처리할 수 있는 양은 계산으로 나오지 않는다. API가 무슨 일을 하는지에 따라 초당 수백에서 수만까지 달라지니 부하 테스트로 잰다. 여기서는 한 대가 초당 1,000건을 받는다고 가정했다.

```text
피크 4,167 ÷ (1,000 × 0.6) = 6.9 → 7대
한 대가 죽어도 버티게 예비 1대 → 8대
```

0.6은 평소 피크에도 CPU를 60%까지만 쓰겠다는 뜻이다. 100%까지 쓰도록 맞추면 응답 시간이 급격히 늘고, 한 대가 죽는 순간 나머지가 그 몫을 받을 자리가 없다.

## 어림셈에서 자주 하는 실수

정확하게 계산하려다 시간을 다 쓴다. 99,987 ÷ 9.1을 손으로 나누기보다 100,000 ÷ 10 = 10,000으로 바꾸는 편이 낫다. 어림셈의 목적은 자릿수와 결정이다.

단위를 빼먹는다. "500"이라고만 적으면 KB인지 MB인지, 초당인지 하루인지 나중에 본인도 모른다. 특히 저장은 바이트, 회선은 비트라서 8배가 섞인다. 숫자마다 단위를 붙인다.

평균만 계산하고 멈춘다. 서버는 피크를 버텨야 하고, 피크가 평균의 몇 배인지는 서비스마다 다르다. 실제 서비스라면 분 단위 그래프에서 가장 높은 구간을 확인한다.

가장 큰 항목을 놓친다. 리뷰 텍스트만 계산하고 사진을 빼면 저장 공간이 2,000배 작게 나온다. 반대로 사진이 있는데 텍스트 바이트를 소수점까지 따지는 건 시간 낭비다.

가정을 적지 않는다. 계산이 틀렸다는 지적을 받았을 때 어느 가정이 틀렸는지 짚을 수 없으면 처음부터 다시 해야 한다. 가정을 적어 두면 그 숫자 하나만 바꿔 다시 계산하면 된다.

## 면접에서 나올 만한 질문

### 월간 사용자 1,000만 명이면 초당 요청은 얼마쯤인가요?

가정에 따라 다르니 가정부터 말한다. 매일 쓰는 비율 40%, 한 명이 하루 30번 요청한다고 하면 DAU 400만에 하루 1억 2천만 요청이고, 86,400초로 나누면 평균 약 1,400 QPS다. 피크를 평균의 3배로 보면 약 4,200 QPS이고, 서버는 이 피크를 기준으로 준비한다.

### 피크 QPS는 어떻게 정하나요?

운영 중인 서비스라면 분 단위 요청 수 그래프에서 가장 높은 구간을 읽는다. 자료가 없으면 평균의 2~3배로 가정하고, 그 가정을 말로 밝힌다. 이벤트나 명절처럼 드문 폭증은 늘 띄워 둘 용량이 아니라 오토스케일링이나 요청 제한으로 대응할 대상으로 따로 다룬다.

### 저장 공간은 어떻게 어림하나요?

하루에 새로 생기는 항목 수에 항목 하나의 크기를 곱하고, 보관 기간과 복제 수를 곱한다. 이때 가장 큰 항목만 제대로 세면 자릿수가 맞는다. 리뷰 텍스트는 약 500바이트지만 사진이 1MB라서, 사진을 빼먹으면 2,000배 작게 나온다. 한 행의 크기는 짐작하지 말고 실제 표에 넣어 `pg_total_relation_size` 같은 함수로 재는 편이 정확하다.

### 웹 서버는 몇 대가 필요한지 어떻게 정하나요?

피크 QPS를 서버 한 대가 처리하는 QPS와 목표 사용률로 나누고, 한 대가 죽어도 버티도록 예비를 더한다. 한 대의 처리량은 API마다 크게 달라서 계산이 아니라 부하 테스트로 정한다. 사용률을 100%로 잡으면 응답 시간이 급격히 늘고 장애 때 받을 자리가 없어서 보통 60~70% 정도로 잡는다.

### 트래픽이 10배가 되면 무엇이 먼저 문제가 되나요?

이 예시라면 읽기 피크가 4만 QPS를 넘어서 웹 서버와 캐시가 먼저 늘어야 한다. 쓰기는 피크 70개 정도라 주 DB 한 대가 아직 받지만, 데이터가 커지면서 백업과 복제본 추가, 인덱스 작업이 오래 걸리기 시작한다. 전송량도 100Gbps 단위가 되니 CDN 히트율이 비용을 좌우한다.

### 어림셈이 틀리면 어떻게 하나요?

틀린 가정만 바꿔 다시 계산하면 되도록 가정을 처음부터 적어 둔다. 어림셈의 목적은 정확한 값이 아니라 자릿수와 그에 따른 결정이라, 결과가 두세 배 틀려도 같은 구조를 고르는 경우가 많다. 서비스를 시작한 뒤에는 실제 지표로 가정을 하나씩 바꿔 넣는다.

### 캐시 메모리는 얼마나 필요한가요?

자주 읽히는 데이터만 올린다고 보고 계산한다. 요청의 80%가 데이터의 20%에 몰린다고 가정하면, 식당 50만 곳의 상세 정보 4GB 중 0.8GB를 올리면 되고 관리 비용까지 1.5배를 잡아도 Redis 한 대에 들어간다. 이 비율은 실제로는 키별 조회 수 분포로 확인하고, 히트율을 보면서 크기를 조정한다.
