이탈 예측 모델을 학습해 보니 검증 데이터에서 AUC(이탈 고객을 이탈하지 않을 고객보다 높게 점수 매길 확률)가 0.81이 나왔다. API로 감싸 서비스에 붙였는데 몇 주 뒤에 보니 실제 성능이 기대보다 한참 낮다. 모델 파일은 학습한 그대로다. 원인을 파 보니 "최근 7일 평균 주문액" 특징을 계산하는 코드가 학습 쪽(배치 SQL)과 서빙 쪽(API 서버 코드)에 따로 있었고, 둘이 미묘하게 달랐다.

이게 학습-서빙 차이(training-serving skew)다. 모델 서빙에서 가장 흔하고 가장 조용한 사고다. 이 글은 이 장면을 직접 재현하는 데서 시작해, 배치 추론과 온라인 추론 중 무엇을 고를지, 모델을 API로 감싸는 방법과 전용 추론 서버, 동적 배칭이 처리량과 지연 시간을 어떻게 맞바꾸는지, 피처 저장소가 학습과 서빙을 맞추는 방식, 섀도·카나리·A/B로 새 모델을 내보내고 되돌리는 법, 클라우드 관리형 서비스를 쓸 때의 범위를 차례로 다룬다.

MLOps 전체 지도는 [MLOps 글](/posts/what-is-mlops)에 있고, 이 글은 그중 서빙 고리를 맡는다. LLM을 직접 띄워 서빙하는 이야기(연속 배칭, PagedAttention, vLLM)는 [LLM 자체 호스팅 글](/posts/self-hosting-llm-inference)로 넘긴다. 여기서는 표 데이터 모델과 일반 신경망 모델을 기준으로 한다. 실험은 Python 3.13, scikit-learn 1.9, FastAPI 0.162로 했다.

## 같은 모델이 서빙에서만 틀리는 이유

재현해 봤다. 고객 6,000명의 최근 30일 일별 주문액을 만들고, 두 특징으로 이탈을 예측한다. 마지막 주문 후 지난 일수와 최근 7일 평균 주문액이다. 두 번째 특징을 계산하는 코드가 학습과 서빙에서 이렇게 다르다.

```python
# 학습 쪽(배치 SQL을 옮긴 것): 어제까지 7일, 주문이 없으면 NaN → 학습 데이터 중앙값으로 채운다
def avg7_train(o):
    w = o[:, 22:29]                              # 30일 중 오늘(29) 제외, 22~28
    s, c = w.sum(1), (w > 0).sum(1)
    return np.where(c > 0, s / np.maximum(c, 1), np.nan)

# 서빙 쪽(API 서버에 다시 짠 코드): 오늘 포함 7일, 주문이 없으면 0
def avg7_serve(o):
    w = o[:, 23:30]                              # 23~29, 오늘이 들어간다
    s, c = w.sum(1), (w > 0).sum(1)
    return np.where(c > 0, s / np.maximum(c, 1), 0.0)
```

차이는 두 가지다. 7일 창이 하루 밀려 있고, 주문이 없는 고객을 학습에서는 중앙값(26,481원)으로, 서빙에서는 0으로 채운다. 둘 다 코드 리뷰에서 그냥 넘어가기 쉬운 차이다. 학습 특징으로 그래디언트 부스팅 모델을 학습한 뒤, 같은 시험 고객 1,500명을 학습 특징과 서빙 특징으로 각각 예측했다.

```text
median fill value 26481
feature mismatch rate 0.699
no-order customers: train feature 26481  serve feature 0
AUC offline(train features) 0.8099  online(serve features) 0.7635
predictions changed >0.10: 0.597   mean |diff| 0.1456
mean pred offline 0.542  online 0.406  actual 0.551
```

봐야 할 줄은 세 개다. 고객의 69.9%가 두 경로에서 특징 값이 다르다. AUC가 0.8099에서 0.7635로 떨어졌다. 그리고 평균 예측 이탈률이 0.542에서 0.406으로 내려갔는데 실제 이탈률은 0.551이다. 모델이 서빙에서 이탈을 체계적으로 과소평가한다. 주문이 없는 고객을 학습 때는 "평범한 주문액"으로 봤는데 서빙에서는 "주문액 0"으로 보니, 모델이 학습한 적 없는 값을 받은 것이다.

이 사고가 무서운 건 어디에도 오류가 나지 않는다는 점이다. API는 200을 돌려주고 예측값은 0~1 사이의 그럴듯한 숫자다. 오프라인 평가 리포트에는 0.81이 적혀 있다.

학습-서빙 차이가 생기는 흔한 원인을 적어 두면 이렇다.

- 특징 코드를 두 번 짠다. 학습은 Python·SQL, 서빙은 Java·TypeScript로 다시 구현한다. 위 사례다.
- 결측값, 범주 인코딩, 정규화 상수(평균·표준편차)를 서빙에서 다르게 처리한다. 학습 때 구한 상수를 모델과 함께 저장하지 않고 서빙에서 다시 계산한다.
- 시간 기준이 다르다. 학습은 UTC 날짜 경계로 집계했는데 서빙은 한국 시간 기준으로 "오늘"을 자른다.
- 학습 데이터에 미래 정보가 섞여 있다(데이터 누수). 학습 때는 하루 뒤에 확정되는 값을 썼는데 서빙 시점에는 그 값이 아직 없다.
- 라이브러리 버전이 다르다. 전처리 라이브러리의 기본값이 버전마다 바뀐다.

막는 방법은 결국 하나로 모인다. 특징을 계산하는 코드와 상수를 한곳에 두고 학습과 서빙이 같은 것을 쓰게 한다. 전처리를 모델과 한 객체로 묶어 저장하는 것(scikit-learn의 `Pipeline`), 특징 정의를 한곳에서 관리하는 피처 저장소, 서빙에서 실제로 쓴 특징을 로그로 남겨 다음 학습 데이터로 다시 쓰는 것이 그 방법들이다. 마지막 방법은 서빙 로그가 곧 학습 데이터가 되니 두 경로가 원천적으로 같아진다.

## 밤에 한꺼번에 할까, 요청마다 할까

서빙 방식을 고르는 첫 질문은 "예측이 언제 필요한가"다.

배치 추론은 정해진 시각에 대상 전체를 한꺼번에 예측해서 테이블에 저장해 둔다. 매일 새벽 전체 고객의 이탈 확률을 계산해 두면, 마케팅 시스템은 아침에 그 테이블을 읽기만 한다. 서빙 서버가 따로 필요 없고, 큰 배치로 돌리니 GPU·CPU를 효율적으로 쓰고, 실패하면 다시 돌리면 된다. 학습 파이프라인과 같은 도구(Airflow, Spark)로 돌릴 수 있다. 대신 예측이 최대 하루만큼 낡는다. 어제 저녁에 가입한 고객에게는 예측이 없다.

온라인 추론은 요청이 올 때마다 예측한다. 결제 직전 사기 판단, 검색 결과 순위, 지금 보고 있는 상품 기준 추천처럼 방금 생긴 정보가 예측에 필요하거나, 대상이 너무 많아 미리 다 계산할 수 없을 때 쓴다(모든 사용자 × 모든 상품 조합). 서버를 계속 띄워 둬야 하고 지연 시간 예산을 지켜야 한다.

중간도 있다. 스트리밍 추론은 이벤트가 들어올 때마다 Kafka 같은 스트림에서 읽어 예측하고 결과를 다시 스트림이나 저장소에 쓴다. 요청-응답이 아니라 이벤트 기반이라 지연에 덜 엄격하고 처리량을 맞추기 쉽다. 그리고 많이 쓰는 절충은 "배치로 미리 계산하고 온라인으로 보정"이다. 무거운 후보 추천은 밤에 배치로 만들어 두고, 요청 시점에는 가벼운 모델로 후보 수백 개의 순서만 다시 매긴다.

고르는 기준을 적어 보면 이렇다. 입력이 요청 시점에야 생기면 온라인. 예측 대상이 유한하고 하루 늦어도 되면 배치. 둘 다 아니면 배치로 시작한다. 배치는 장애가 나도 어제 결과로 버틸 수 있고, 운영할 서버가 없다. 온라인으로 바꾸는 신호는 "새로 가입한 고객에게도 예측이 필요하다", "예측이 하루 늦어서 생기는 손실이 보인다" 같은 것이다.

## FastAPI로 감싸기

가장 단순한 온라인 서빙은 웹 프레임워크로 모델을 감싸는 것이다. 위 실험의 모델을 FastAPI로 감쌌다.

```python
# app.py
from contextlib import asynccontextmanager
import os, joblib, numpy as np
from fastapi import FastAPI
from pydantic import BaseModel, Field

MODEL_PATH = os.environ.get("MODEL_PATH", "churn-v14.joblib")
state = {}

@asynccontextmanager
async def lifespan(app: FastAPI):
    state["model"] = joblib.load(MODEL_PATH)        # 프로세스가 뜰 때 한 번만 읽는다
    state["version"] = os.path.basename(MODEL_PATH)
    yield

app = FastAPI(lifespan=lifespan)

class Features(BaseModel):
    days_since_last_order: float = Field(ge=0, le=365)   # 학습 데이터 범위를 벗어난 입력을 막는다
    avg_order_7d: float = Field(ge=0)

@app.get("/healthz")
def healthz():
    return {"ok": "model" in state, "model_version": state.get("version")}

@app.post("/predict")
def predict(f: Features):                            # async가 아닌 def: CPU 계산은 스레드 풀에서 돈다
    x = np.array([[f.days_since_last_order, f.avg_order_7d]])
    p = float(state["model"].predict_proba(x)[0, 1])
    return {"churn_prob": round(p, 4), "model_version": state["version"]}
```

  -d '{"days_since_last_order": 12, "avg_order_7d": 0}'

  -d '{"days_since_last_order": -3, "avg_order_7d": 0}'
```

{"detail":[{"type":"greater_than_equal","loc":["body","days_since_last_order"],"msg":"Input should be greater than or equal to 0","input":-3,"ctx":{"ge":0.0}}]}
```

두 번째와 세 번째 줄이 skew를 한 고객으로 보여 준다. 주문이 없는 고객을 학습 방식(중앙값 26,481)으로 넣으면 이탈 확률 0.5995, 서빙 방식(0)으로 넣으면 0.2319다. 같은 고객, 같은 모델인데 쿠폰을 받을지가 갈린다. 네 번째는 입력 검증이 일하는 모습이다. 음수 일수 같은 값은 모델에 넣기 전에 422로 돌려보낸다. 모델은 학습 범위 밖 입력에도 아무 숫자나 내놓기 때문에, 범위 검사는 서빙 쪽이 해야 한다.

코드에서 몇 가지를 일부러 그렇게 했다. 모델은 요청마다 읽지 않고 시작할 때 한 번 읽는다. `healthz`는 모델이 실제로 올라왔는지까지 답해서, 쿠버네티스 readiness 검사에 쓰면 모델을 읽는 동안 트래픽이 들어오지 않는다. `predict`를 `async def`가 아닌 `def`로 둔 건, CPU를 쓰는 계산을 `async def` 안에서 하면 이벤트 루프가 멈춰 다른 요청이 모두 줄을 서기 때문이다. 이 동작은 [FastAPI 글](/posts/fastapi-basics)에 자세히 있다. 그리고 응답에 모델 버전을 넣었다.

이 방식은 트리 모델이나 작은 신경망, 요청이 초당 수백 건 정도인 서비스에서 충분하다. 한계는 GPU 모델에서 드러난다. 요청 하나씩 계산하면 GPU가 대부분 논다. 그래서 요청을 묶는다.

## 묶어서 계산하면 싸진다: 동적 배칭

[딥러닝 기초 글](/posts/deep-learning-basics)에서 본 것처럼 행렬 곱은 크게 할수록 효율이 좋다. 512 → 2048 → 2048 → 10 크기의 작은 신경망을 CPU 스레드 하나로 돌리며 배치 크기별 호출 시간을 쟀다(다른 작업이 돌던 4코어 VM, 60번 중 가장 빠른 값).

```text
batch    1  call    1.03 ms  per item  1.034 ms
batch    8  call    5.65 ms  per item  0.706 ms
batch   32  call    7.63 ms  per item  0.239 ms
batch   64  call   10.32 ms  per item  0.161 ms
batch  128  call   16.30 ms  per item  0.127 ms
```

한 건씩 하면 건당 1.03ms, 32건을 묶으면 건당 0.24ms다. 같은 하드웨어로 네 배 넘게 많은 요청을 처리한다. GPU에서는 이 차이가 훨씬 커진다. 하지만 온라인 요청은 하나씩 따로 들어온다. 그래서 서버가 짧은 시간 동안 들어온 요청을 모아서 한 배치로 계산하고 결과를 다시 나눠 돌려준다. 이게 동적 배칭이다.

동적 배칭에는 손잡이가 두 개 있다. 최대 배치 크기와 최대 대기 시간이다. 요청이 오면 큐에 넣고, 배치가 가득 차거나 첫 요청이 정해진 시간만큼 기다렸으면 그때 계산한다. 아래 그림에서 단계를 넘기면 최대 배치 4, 최대 대기 5ms인 서버가 요청을 묶는 모습을 볼 수 있다.

부하에 따라 결론이 뒤집힌다.

초당 300건처럼 한가할 때는 배칭이 손해다. 배칭 없이 p50이 1.74ms인데, 배칭을 켜면 기다리는 시간과 작은 배치(평균 2~3건)의 비싼 계산이 더해져 7~10ms가 된다. 묶을 요청이 별로 없으니 기다리기만 한 셈이다.

초당 800건이면 배칭 없는 서버는 처리량은 맞추지만 큐가 자주 밀려 p99가 98.67ms로 치솟는다. 배칭을 켜면 p99가 20ms 근처로 내려간다.

초당 1,500건이면 차이가 결정적이다. 배칭 없는 서버는 초당 939건이 한계라 요청이 끝없이 쌓이고, p50이 440ms, p99가 1.2초다. 배칭을 켜면 같은 서버가 1,510건을 다 처리하면서 p99가 20ms대다. 부하가 높을수록 배치가 저절로 커져서(평균 11~13건) 건당 비용이 내려가기 때문이다.

그래서 대기 시간은 지연 시간 예산 안에서 작게 잡고, 최대 배치는 메모리와 계산 시간이 예산을 넘지 않는 선에서 정한다. 한가한 시간에 손해를 보기 싫으면 큐가 비어 있을 때는 기다리지 않고 바로 보내는 구현도 있다. 대기 시간을 늘린다고 처리량이 계속 늘지는 않는다는 것도 위 숫자에 보인다. 2ms와 5ms의 처리량은 같고 지연만 늘었다.

## 전용 추론 서버가 대신 해 주는 것

동적 배칭, 여러 모델 동시 서빙, GPU 메모리 관리, 모델 파일 교체를 직접 짜는 대신 전용 추론 서버를 쓸 수 있다. NVIDIA Triton Inference Server는 PyTorch, TensorRT, ONNX, TensorFlow 모델 등을 같은 서버에서 올리고, 모델 설정 파일에 동적 배칭을 선언하면 위 규칙을 서버가 대신 돌린다.

```text
# config.pbtxt (Triton 모델 설정의 일부)
max_batch_size: 32
dynamic_batching {
  max_queue_delay_microseconds: 5000
}
instance_group [ { count: 2, kind: KIND_GPU } ]
```

`max_queue_delay_microseconds`가 위의 최대 대기 시간이고, `instance_group`은 GPU 하나에 모델 복사본을 몇 개 올려 동시에 돌릴지다. 복사본을 늘리면 한 배치가 계산되는 동안 다음 배치를 받을 수 있지만 GPU 메모리를 그만큼 더 쓴다.

쿠버네티스 위에서 모델 서빙을 표준화하는 KServe 같은 도구도 있다. 모델 저장 위치와 형식을 선언하면 서버 컨테이너, 오토스케일링, 트래픽 분할을 만들어 준다.

```yaml
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: churn
spec:
  predictor:
    canaryTrafficPercent: 10        # 새 버전에 10%만 보낸다
    model:
      modelFormat:
        name: sklearn
      storageUri: s3://ml-models/churn/v15
```

`storageUri`를 바꿔 적용하면 새 버전이 뜨고, `canaryTrafficPercent`만큼만 트래픽이 간다. 문제가 없으면 비율을 100으로 올린다.

언제 전용 서버로 넘어가나. 모델이 GPU를 쓰고 요청이 많아서 배칭이 필요해질 때, 같은 팀이 여러 프레임워크의 모델을 함께 운영할 때, 모델 교체와 트래픽 분할을 매번 손으로 짜기 시작할 때다. 트리 모델 몇 개를 CPU로 돌리는 정도면 FastAPI가 더 단순하고 디버깅도 쉽다. 전용 서버는 입력 형식(텐서 이름과 모양)을 맞추는 일과 서버 자체의 설정·버전을 배우는 비용이 든다. LLM은 생성 방식이 달라 vLLM 같은 전용 엔진을 쓰는데, 그 이야기는 [LLM 자체 호스팅 글](/posts/self-hosting-llm-inference)에 있다.

## 학습과 서빙에 같은 특징을 주는 곳

피처 저장소(feature store)는 skew를 구조적으로 막으려고 생겼다. 특징 정의를 한 번만 쓰고, 그 정의로 두 저장소를 채운다.

오프라인 저장소는 과거 모든 시점의 특징 값을 쌓아 둔 큰 테이블(데이터 웨어하우스나 레이크)이다. 학습 데이터를 만들 때 쓴다. 여기서 중요한 기능이 시점 맞춤 조인(point-in-time join)이다. "10월 1일에 이탈 여부를 예측한다면 그날 알 수 있었던 특징 값"만 붙여야 한다. 그냥 최신 값을 붙이면 미래 정보가 섞여서 학습 때만 성능이 좋은 모델이 된다.

온라인 저장소는 고객별 최신 특징 값만 들고 있는 빠른 키-값 저장소(Redis, DynamoDB 등)다. 서빙에서 밀리초 안에 꺼낸다. 같은 정의로 계산한 값을 주기적으로(혹은 스트림으로) 오프라인에서 온라인으로 옮긴다(materialization).

```python
# Feast 스타일의 특징 정의 예 (한 번만 정의하고 학습·서빙이 함께 쓴다)
from datetime import timedelta
from feast import Entity, FeatureView, Field
from feast.types import Float32

customer = Entity(name="customer", join_keys=["customer_id"])

customer_orders = FeatureView(
    name="customer_orders",
    entities=[customer],
    ttl=timedelta(days=2),                 # 이보다 오래된 값은 없는 것으로 본다
    schema=[Field(name="avg_order_7d", dtype=Float32),
            Field(name="days_since_last_order", dtype=Float32)],
    source=orders_daily_source,            # 배치 SQL이 만든 테이블
)
# 학습: store.get_historical_features(entity_df=..., features=[...])  ← 시점 맞춤 조인
# 서빙: store.get_online_features(features=[...], entity_rows=[{"customer_id": 4812}])
```

이 코드는 Feast의 정의 방식을 보여 주는 예시이고, 정확한 API는 버전마다 조금씩 다르니 쓰는 버전의 문서를 확인한다. 핵심은 `avg_order_7d`가 어떻게 계산되는지가 한곳(`orders_daily_source`를 만드는 쿼리)에만 있다는 것이다. 위 실험의 두 함수 같은 일이 생길 자리가 없다. 다만 결측 처리(중앙값이냐 0이냐)가 저장소 밖 모델 코드에 남아 있으면 skew는 여전히 생길 수 있다. 결측 처리까지 특징 정의나 모델 파이프라인 안으로 넣는다.

피처 저장소 제품을 꼭 들여야 하는 건 아니다. 특징이 수십 개이고 배치 서빙이 대부분인 팀은 "학습과 배치 예측이 같은 SQL 뷰를 쓴다"만으로 같은 효과를 낸다. 온라인 서빙이 생기고, 여러 모델이 같은 특징을 나눠 쓰고, 시점 맞춤 조인을 손으로 짜다 실수가 나기 시작하면 제품을 검토한다. 그리고 TTL 같은 설정을 놓치면 "온라인 저장소 값이 사흘째 갱신이 안 됐는데 모델은 그 값으로 계속 예측"하는 사고가 난다. 특징의 마지막 갱신 시각도 모니터링 대상이다.

섀도 배포는 실제 운영 입력으로 새 모델을 돌려 보는 가장 안전한 방법이다. 서빙 경로의 skew, 지연 시간, 메모리, 예외 입력이 여기서 드러난다. 한계도 분명하다. 섀도의 예측은 사용자에게 나가지 않으니 "새 모델의 예측이 사용자 행동을 더 좋게 바꾸나"는 알 수 없다. 그리고 요청을 두 번 계산하니 비용이 두 배다. 섀도에서 외부에 부작용이 있는 호출(메일 발송, 결제)을 하면 안 된다는 것도 잊기 쉽다.

카나리는 실제로 사용자 일부(1%, 10%)에게 새 모델의 답을 보낸다. 지연 시간, 오류율, 예측 분포, 그리고 늦게 들어오는 성과 지표를 보며 비율을 넓힌다. 문제가 보이면 비율을 0으로 돌리는 게 롤백이다. 비율별 표본 크기와 판정은 [카나리 릴리스 글](/posts/canary-release)에 있다.

A/B 테스트는 카나리와 모양이 비슷하지만 질문이 다르다. 카나리는 "새 모델이 깨지지 않았나"를 묻고, A/B는 "새 모델이 사업 지표(이탈률, 매출)를 더 낫게 만드나"를 묻는다. 그래서 A/B는 사용자 단위로 고정해서 나누고, 미리 정한 표본 크기만큼 충분히 오래 돌린다. 모델 정확도가 올라도 사업 지표는 그대로인 경우가 흔해서, 중요한 모델 교체는 결국 A/B로 판정한다. 설계는 [A/B 테스트 글](/posts/ab-testing)에 있다.

롤백은 빠를수록 좋다. 그래서 이전 버전 모델을 지우지 않고 레지스트리에 남겨 두고, 서빙이 "운영 중인 버전"을 설정 하나로 바꿀 수 있게 한다. 모델과 함께 바뀐 특징 정의가 있으면 롤백이 복잡해진다. 새 특징을 추가한 모델은 특징 파이프라인을 먼저 배포하고, 이전 모델도 그 상태에서 돌 수 있게(새 특징을 무시하게) 순서를 정한다.

## 실시간 추론이 느릴 때 보는 곳

p99가 예산을 넘었다는 알림이 오면 이 순서로 본다.

먼저 시간이 어디서 쓰이는지 쪼갠다. 서비스 API → 특징 조회 → 모델 서버 큐 → 계산 → 응답 직렬화마다 시간을 남겨 두지 않았다면 그것부터 한다. 분산 추적(OpenTelemetry)의 스팬으로 나누면 한눈에 보인다. 의외로 모델 계산이 아니라 특징 조회나 큰 JSON 직렬화가 범인인 경우가 많다.

모델 서버 안에서는 큐 대기와 계산을 나눠 본다. 대기가 길면 서버가 부족하거나(복제본 수, 오토스케일링 기준) 배치 대기 시간이 크다. 계산이 길면 모델이 무겁거나 배치가 너무 크다.

GPU 모델이면 사용률을 본다. 사용률이 낮은데 느리면 배칭이 안 되고 있거나, 요청마다 CPU에서 전처리(이미지 디코딩, 토크나이즈)를 하느라 GPU가 기다린다. 사용률이 높은데 느리면 GPU가 모자라다.

모델 자체를 가볍게 하는 방법도 있다. 16비트나 8비트로 줄이는 양자화, 큰 모델의 답을 작은 모델이 배우게 하는 증류, ONNX Runtime이나 TensorRT 같은 추론 전용 런타임으로 변환하기다. 정확도가 얼마나 떨어지는지는 평가 세트로 확인한 뒤에 바꾼다.

첫 요청만 유독 느리면 콜드 스타트다. 모델 파일을 처음 읽거나, GPU 커널을 처음 컴파일하거나, 오토스케일링으로 새 Pod이 막 떴을 때다. 시작할 때 더미 요청으로 미리 데우고, 그 전에는 readiness를 내주지 않는다. 큰 모델 파일은 컨테이너 이미지에 굽거나 노드에 캐시해 두면 Pod 시작 시간이 줄어든다.

## 관리형 ML 서비스는 어디까지 맡아 주나

AWS SageMaker, Google Vertex AI, Azure Machine Learning 같은 관리형 서비스는 위의 많은 부분을 대신한다. 모델 파일과 컨테이너를 지정하면 엔드포인트를 띄우고, 오토스케일링을 걸고, 버전 사이 트래픽을 나누고, 배치 추론 작업을 돌리고, 모델 레지스트리와 모니터링 기능을 붙여 준다. 서비스마다 이름은 다르지만 실시간 엔드포인트, 서버리스 엔드포인트, 배치 추론 작업이 대체로 있다.

맡기면 좋은 것: GPU 인스턴스 관리, 엔드포인트 오토스케일링, 트래픽 분할 같은 인프라 일. 팀에 쿠버네티스와 GPU 운영 경험이 없으면 이 부분만으로도 값을 한다.

여전히 내 몫인 것: 특징 계산과 skew 방지, 입력 검증, 평가 관문, 예측 로그와 모니터링 기준. 이건 어떤 플랫폼도 대신 정해 주지 않는다. 위 실험의 중앙값과 0 문제는 관리형 엔드포인트 위에서도 똑같이 생긴다.

고를 때 따져 볼 것은 비용 구조(엔드포인트는 요청이 없어도 인스턴스 시간만큼 과금되는 방식이 많다), 벤더 종속(서비스 전용 SDK와 컨테이너 규약에 코드가 묶인다), 데이터 위치(학습 데이터와 특징 저장소가 같은 클라우드에 있어야 싸고 빠르다)다. 요청이 낮에만 몰리면 서버리스 엔드포인트나 배치로 비용을 줄이고, 지연 시간이 엄격하면 상시 엔드포인트를 쓴다. 정확한 기능과 가격은 서비스 문서를 보고 판단한다.

## 서빙은 학습의 연장이다

모델 서빙은 학습한 파일을 API로 감싸는 일보다 넓다. 학습 때와 같은 특징을 같은 방식으로 만들어 넣어야 하고(skew 방지), 예측이 언제 필요한지에 따라 배치와 온라인을 고르고, 온라인이면 지연 시간 예산 안에서 동적 배칭으로 처리량을 얻고, 새 모델은 섀도와 카나리로 작게 겪은 뒤 넓히고 언제든 되돌릴 수 있게 둔다. 서빙이 남긴 예측 로그는 모니터링과 다음 학습으로 이어진다. 전체 고리는 [MLOps 글](/posts/what-is-mlops)에, 예측마다 설명을 붙여 기록하는 방법은 [SHAP과 LIME 글](/posts/explainable-ai-shap-lime)에 있다.

## 면접에서 나올 만한 질문

### 학습-서빙 차이(training-serving skew)는 무엇이고 어떻게 막나

학습 때와 서빙 때 모델 입력이 다르게 만들어져서, 오프라인 평가보다 운영 성능이 떨어지는 현상이다. 특징 코드를 두 번 구현하거나, 결측값·시간 기준·정규화 상수를 다르게 처리할 때 생긴다. 실험에서 7일 창 하루 차이와 결측값 처리(중앙값 vs 0)만으로 AUC가 0.81에서 0.76으로 떨어졌다. 특징 계산과 상수를 한곳에 두고 학습과 서빙이 같이 쓰게 하고(전처리 파이프라인 저장, 피처 저장소), 서빙에서 쓴 특징을 로그로 남겨 학습에 다시 쓰는 방법으로 막는다.

### 배치 추론과 온라인 추론은 어떻게 고르나

예측에 필요한 입력이 요청 시점에야 생기거나 대상이 너무 많아 미리 계산할 수 없으면 온라인, 대상이 정해져 있고 하루 늦어도 되면 배치다. 배치는 서버가 필요 없고 효율적이며 실패해도 다시 돌리면 된다. 애매하면 배치로 시작하고, 새 사용자에게도 즉시 예측이 필요해지는 등 신호가 보이면 온라인으로 옮긴다. 무거운 후보 생성은 배치, 가벼운 재정렬은 온라인으로 나누는 절충도 흔하다.

### 동적 배칭은 왜 쓰고 무엇을 조절하나

행렬 곱은 묶어서 계산할수록 건당 비용이 낮아서, 따로 들어오는 요청을 짧게 모아 한 번에 계산하면 같은 하드웨어로 처리량이 크게 늘어난다. 최대 배치 크기와 최대 대기 시간 두 가지로 조절한다. 실험에서 초당 1,500건을 배칭 없이 받으면 p99가 1.2초까지 밀렸지만, 배칭을 켜니 p99 20ms대로 다 처리했다. 반대로 한가할 때는 기다리는 시간만 늘어 지연이 나빠지니, 대기 시간은 지연 예산 안에서 작게 잡는다.

### 실시간 추론이 느릴 때 어디부터 보나

먼저 특징 조회, 모델 서버 큐 대기, 계산, 직렬화로 시간을 쪼갠다. 모델 계산이 아니라 특징 저장소나 직렬화가 원인인 경우가 많다. 큐 대기가 길면 복제본이나 배치 대기 설정, 계산이 길면 모델 크기와 배치 크기를 본다. GPU 사용률이 낮으면 배칭이나 CPU 전처리 병목, 첫 요청만 느리면 콜드 스타트를 의심한다.

### 섀도, 카나리, A/B 배포는 어떻게 다른가

섀도는 새 모델에 같은 요청을 복제해 예측만 기록하고 사용자에게는 보내지 않아서, 운영 입력으로 skew·지연·오류를 위험 없이 확인한다. 카나리는 사용자 일부에게 실제로 새 모델의 답을 보내며 깨지지 않았는지 보고 비율을 넓힌다. A/B는 사용자 단위로 나눠 충분한 표본으로 사업 지표가 나아지는지를 판정한다. 보통 섀도 → 카나리 → 필요하면 A/B 순으로 간다.

### 피처 저장소의 오프라인·온라인 저장소는 각각 무엇을 하나

오프라인 저장소는 과거 시점별 특징 값을 쌓아 두고, 시점 맞춤 조인으로 "예측 시점에 알 수 있었던 값"만 붙여 학습 데이터를 만든다. 온라인 저장소는 엔티티별 최신 값만 키-값 저장소에 두고 서빙에서 밀리초 안에 꺼낸다. 둘을 같은 특징 정의로 채우는 게 핵심이고, 온라인 값이 갱신되지 않는 사고를 막으려면 TTL과 마지막 갱신 시각을 감시한다.

### 관리형 ML 서비스를 쓰면 무엇이 여전히 우리 몫인가

엔드포인트, 오토스케일링, 트래픽 분할 같은 인프라는 맡길 수 있지만, 특징 계산과 skew 방지, 입력 검증, 평가 관문, 예측 로그와 모니터링 기준은 그대로 우리 일이다. 그리고 상시 엔드포인트 과금 방식, 전용 SDK에 묶이는 벤더 종속, 데이터와 같은 클라우드에 있어야 하는 위치 문제를 따져서 고른다.
