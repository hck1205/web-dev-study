배포 스크립트 맨 위에 환경 이름을 확인하는 줄이 있었다. 운영 환경이면 한 번 더 묻고, 아니면 바로 배포하는 단순한 분기다.

```bash
a=""          # 원래는 $DEPLOY_ENV를 받는데, 누가 export를 빠뜨렸다
b="prod"
if [ $a == $b ]; then echo same; else echo diff; fi
echo "exit=$?"
```

```text
t1.sh: line 3: [: ==: unary operator expected
diff
exit=0
```

에러 메시지가 한 줄 찍혔지만 스크립트는 멈추지 않았다. `else` 쪽으로 가서 "운영이 아니다"로 판단했고, 마지막 종료 코드도 0이다. 확인 질문 없이 배포가 나가는 길이 열린 셈이다. 이 한 줄에서 bash 조건문의 성질이 거의 다 드러난다. `if`가 무엇을 보는지, `[`가 무엇인지, 변수가 비면 왜 문법 오류가 나는지를 알면 반복문과 함수도 같은 규칙으로 읽힌다.

기준은 Ubuntu 24.04의 bash 5.2이고, 22.04의 bash 5.1에서도 이 글의 동작은 같다. 출력은 모두 직접 돌린 결과다. 실패를 숨기지 않는 스크립트 설정(`set -euo pipefail`, 따옴표, trap)은 [bash 스크립트 글](/posts/bash-scripting)에서 다뤘으니 여기서는 분기와 반복, 함수에 집중한다. 스크립트가 어떤 환경 변수를 받고 어디서 실행되는지는 [셸 환경과 시작 파일 글](/posts/shell-environment-startup)에서 이어진다.

## if는 조건이 아니라 명령의 성적을 본다

다른 언어의 `if`는 참과 거짓으로 계산되는 식을 받는다. bash의 `if`는 명령을 받는다. 그 명령을 실행하고, 종료 코드가 0이면 `then`으로, 0이 아니면 `else`로 간다. 종료 코드가 0이면 성공, 나머지는 실패라는 규칙은 [bash 스크립트 글](/posts/bash-scripting)에서 자세히 봤다.

```bash
# grep은 찾으면 0, 못 찾으면 1을 낸다. if는 그 숫자만 본다
if grep -q root /etc/passwd; then echo "found"; fi

# !는 성적을 뒤집는다. 응답이 없으면(0이 아니면) then으로 간다
if ! ping -c1 -W1 203.0.113.1 >/dev/null 2>&1; then echo "unreachable"; fi
```

```text
found
unreachable
```

그러니 `if` 뒤에 대괄호가 꼭 있어야 하는 게 아니다. `if mkdir /tmp/lock`, `if curl -fsS http://localhost/health`처럼 명령을 바로 쓰는 쪽이 오히려 자연스럽다. 대괄호를 써야 하는 건 값을 비교할 때뿐이고, 그 대괄호도 명령이다.

```bash
type [ [[ if        # 각각이 무엇인지 셸에게 묻는다
type -a test        # 같은 이름이 PATH에 또 있는지까지 본다
```

```text
[ is a shell builtin
[[ is a shell keyword
if is a shell keyword
test is a shell builtin
test is /usr/bin/test
test is /bin/test
```

`[`는 `test`와 같은 내장 명령이다. 이름이 `[`이고 마지막 인자로 `]`를 요구한다는 것만 다르다. 그래서 `[` 뒤와 `]` 앞에 공백이 꼭 있어야 한다. `[$a`라고 붙여 쓰면 셸은 `[$a`라는 이름의 명령을 찾는다. `/usr/bin/test`가 따로 있는 건 셸이 아닌 프로그램(`find -exec`, `xargs`)도 이 검사를 쓸 수 있게 하려는 것이다. 반면 `[[`와 `if`는 키워드다. 명령이 아니라 bash 문법의 일부라서, 셸이 줄을 읽는 방식 자체가 달라진다.

## 대괄호 하나는 명령이고 두 개는 문법이다

`[`는 받은 인자 개수로 무엇을 할지 정한다. 하나면 "비어 있지 않은가", 둘이면 단항 연산자, 셋이면 이항 연산자로 읽는다. 그래서 빈 변수 하나가 인자 개수를 바꾸면 문법 자체가 달라진다. 더 무서운 건 오류가 아니라 조용히 틀리는 경우다.

```bash
v=""
[ -n $v ] && echo "[ -n \$v ] 참 (빈 값인데!)"   # 인자가 -n 하나만 남는다
[ -n "$v" ] || echo "[ -n \"\$v\" ] 거짓"
[[ -n $v ]] || echo "[[ -n \$v ]] 거짓"
```

```text
[ -n $v ] 참 (빈 값인데!)
[ -n "$v" ] 거짓
[[ -n $v ]] 거짓
```

`[ -n $v ]`는 `[ -n ]`이 되고, 인자 하나짜리 검사는 "그 문자열이 비어 있지 않은가"다. `-n`이라는 글자는 비어 있지 않으니 참이다. "값이 있으면 지운다" 같은 분기에 이 줄이 있으면 값이 없을 때 지운다.

`[[ ]]`는 이 문제가 없다. 키워드라서 셸이 안쪽을 읽을 때 단어 분할과 글로빙을 하지 않는다. 빈 변수도 빈 문자열 하나로 남는다. 그 밖에도 몇 가지를 더 해 준다.

```bash
a="*"
[[ abc == $a ]] && echo "glob-match"        # 오른쪽의 따옴표 없는 값은 패턴이다
[[ abc == "$a" ]] || echo "literal-nomatch"  # 따옴표로 감싸면 글자 그대로 비교한다

[[ "v1.2.3" =~ ^v([0-9]+)\.([0-9]+)\.([0-9]+)$ ]] &&
  echo "major=${BASH_REMATCH[1]} minor=${BASH_REMATCH[2]} patch=${BASH_REMATCH[3]}"

[[ -f $f && -r $f ]]   # 안에서 &&, ||, 괄호를 쓸 수 있다
```

```text
glob-match
literal-nomatch
major=1 minor=2 patch=3
```

`==`의 오른쪽은 따옴표가 없으면 glob 패턴으로 쓰인다. 사용자 입력과 정확히 같은지 볼 때는 오른쪽도 따옴표로 감싸야 한다. `=~`는 확장 정규식이고 괄호로 잡은 부분이 `BASH_REMATCH`에 들어간다. 정규식은 변수에 담아 `[[ $v =~ $re ]]`처럼 따옴표 없이 쓰는 게 안전하다. 따옴표로 감싸면 정규식이 아니라 글자로 비교한다. 정규식 방언은 [정규 표현식과 glob 글](/posts/regex-and-globbing)에 있다.

정리하면 bash 스크립트에서는 `[[ ]]`를 쓰고, `/bin/sh`(Ubuntu에서는 dash)로 돌아야 하는 스크립트만 `[ ]`와 꼼꼼한 따옴표로 쓴다. `[[`는 POSIX에 없어서 dash에서는 `[[: not found`가 난다. shebang이 `#!/bin/sh`인데 안에 `[[`가 있다면 그 스크립트는 `sh script.sh`로 부르는 순간 깨진다. 이 차이는 [셸 환경 글](/posts/shell-environment-startup)에서 실행 방식과 함께 다룬다.

## 숫자, 문자열, 파일을 묻는 연산자

비교 연산자는 무엇을 비교하느냐에 따라 따로 있다. 여기서 많이 틀린다. `<`와 `>`는 `[[ ]]` 안에서 숫자가 아니라 문자열 사전 순서다.

```bash
[[ 10 < 9 ]] && echo "string: 10 < 9"       # 문자 '1'이 '9'보다 앞이다
[[ 10 -lt 9 ]] || echo "number: 10 not < 9" # 숫자 비교는 -lt, -gt, -eq ...
(( 10 < 9 )) || echo "arith: no"            # 산술 문맥에서는 < 가 숫자 비교다
```

```text
string: 10 < 9
number: 10 not < 9
arith: no
```

`[ ]` 안의 `>`는 더 나쁘다. 명령의 인자가 아니라 리다이렉션으로 읽힌다.

```bash
[ 10 > 9 ]; echo "rc=$?"   # 10을 '9'라는 파일로 출력 리다이렉션한 셈이다
ls -1 9
```

```text
rc=0
9
```

비교는 하지 않고 현재 디렉터리에 `9`라는 빈 파일을 만들었다. 종료 코드는 `[ 10 ]`의 0이다. 숫자 비교는 `-lt` 같은 연산자나 `(( ))`로 한다. `(( ))`는 C처럼 쓰는 산술 문맥이다. 결과가 0이 아니면 종료 코드 0(참), 결과가 0이면 종료 코드 1이 된다. 그래서 `if (( count > limit ))`처럼 바로 조건에 쓴다.

숫자가 아닌 값이 들어오면 세 문법의 반응이 다르다.

```bash
[ "abc" -eq 1 ]; echo "rc=$?"   # 숫자가 아니라고 거부한다
[[ "abc" -eq 1 ]]; echo "rc=$?" # abc를 변수 이름으로 보고 0으로 계산한다
x=08; (( x > 7 )) && echo big   # 0으로 시작하면 8진수다
```

```text
bash: line 1: [: abc: integer expression expected
rc=2
rc=1
bash: line 1: ((: 08: value too great for base (error token is "08")
```

`[[ ]]`의 `-eq`와 `(( ))`는 양쪽을 산술식으로 계산한다. 그래서 `abc`는 같은 이름의 변수를 찾고, 없으면 0이 된다. 경고 없이 "1과 다르다"로 끝난다. 사용자 입력이 산술식에 바로 들어가면 `a[$(명령)]` 같은 문자열로 명령을 실행시킬 수도 있으니, 숫자를 받을 때는 먼저 `[[ $n =~ ^[0-9]+$ ]]`로 모양을 확인한다. 날짜에서 잘라 낸 `08`, `09`가 8진수로 읽혀 깨지는 것도 흔하다. `$((10#$x))`처럼 10진수라고 밝혀 준다.

파일 검사 연산자는 경로 하나를 받는다. 빈 파일, 내용 있는 파일, 심볼릭 링크, 깨진 링크, 디렉터리, 없는 경로로 확인했다.

```bash
touch empty; echo hi > full; ln -s full link; ln -s nothing broken; mkdir d
for f in empty full link broken d nope; do
  printf '%-7s e=%s f=%s d=%s s=%s L=%s\n' "$f" \
    "$([[ -e $f ]] && echo y || echo n)" "$([[ -f $f ]] && echo y || echo n)" \
    "$([[ -d $f ]] && echo y || echo n)" "$([[ -s $f ]] && echo y || echo n)" \
    "$([[ -L $f ]] && echo y || echo n)"
done
```

```text
empty   e=y f=y d=n s=n L=n
full    e=y f=y d=n s=y L=n
link    e=y f=y d=n s=y L=y
broken  e=n f=n d=n s=n L=y
d       e=y f=n d=y s=y L=n
nope    e=n f=n d=n s=n L=n
```

`-e`(있나), `-f`(일반 파일인가), `-d`(디렉터리인가), `-s`(크기가 0보다 큰가)는 링크를 따라간 대상을 본다. 그래서 깨진 링크는 `-e`가 거짓인데 `-L`만 참이다. "파일이 없으면 링크를 만든다"는 분기에 `-e`만 쓰면 깨진 링크가 남은 자리에서 `ln`이 `File exists`로 실패한다. 링크 자체를 확인하려면 `-L`을 함께 본다. 빈 백업 파일을 걸러 낼 때는 `-f`가 아니라 `-s`를 쓴다.

`-r`, `-w`, `-x`는 지금 실행 중인 사용자가 그 권한을 가지는지를 본다. root로 돌리면 실행 비트를 빼고는 거의 다 참이 나와서, root로 시험한 스크립트가 일반 계정에서 깨지는 일이 생긴다. 권한을 누가 어떻게 판정하는지는 [파일 권한 글](/posts/linux-files-permissions)에 있다. `-nt`(더 최근인가)와 `-ot`도 있어서 `[[ src.c -nt app ]] && make` 같은 줄을 쓸 수 있다.

## A && B || C는 if-else가 아니다

`&&`는 앞이 성공해야 뒤를 실행하고, `||`는 앞이 실패해야 뒤를 실행한다. 짧은 확인 한 줄에는 이게 깔끔하다.

```bash
[[ -d $dir ]] || mkdir -p "$dir"              # 없을 때만 만든다
command -v jq >/dev/null || { echo "jq가 없다" >&2; exit 1; }
```

문제는 둘을 이어서 if-else처럼 쓸 때다. 배포가 성공하면 알림을 보내고, 실패하면 롤백하는 줄을 이렇게 썼다.

```bash
deploy() { echo "deploy ok"; }
notify() { echo "notify failed"; return 1; }
deploy && notify || echo "rollback!"
```

```text
deploy ok
notify failed
rollback!
```

배포는 성공했는데 롤백이 돌았다. `A && B || C`는 "A가 실패하거나, A는 성공했지만 B가 실패하면 C"라서다. `&&`와 `||`는 우선순위가 같고 왼쪽부터 묶인다. 세 덩어리가 엮이는 분기는 `if`로 쓴다.

```bash
if deploy; then
  notify || echo "notify only failed"   # 알림 실패는 따로 다룬다
else
  echo "rollback!"
fi
```

```text
deploy ok
notify failed
notify only failed
```

`B`가 절대 실패하지 않는 명령(`echo` 정도)이면 `A && B || C`도 결과가 맞는다. 하지만 나중에 누군가 `B`를 바꾸면 깨지는 줄이라서, 나는 세 덩어리부터는 `if`를 쓴다. shellcheck도 이 줄에 SC2015 경고를 붙인다.

## case는 패턴으로 고른다

하나의 값을 여러 갈래로 나눌 때는 `if`와 `elif`를 늘어놓는 것보다 `case`가 읽기 쉽다. 각 갈래는 glob 패턴이고, 위에서부터 처음 맞는 하나만 실행한다.

```bash
for arg in start STOP restart status-all "" foo.tar.gz x.zip; do
  case "$arg" in
    start|restart)    echo "[$arg] -> start 계열" ;;   # | 로 여러 패턴
    [Ss][Tt][Oo][Pp]) echo "[$arg] -> stop" ;;         # 대소문자 모두
    status*)          echo "[$arg] -> status 로 시작" ;;
    *.tar.gz|*.tgz)   echo "[$arg] -> tar" ;;
    "")               echo "[$arg] -> 빈 값" ;;
    *)                echo "[$arg] -> 모름" ;;          # 나머지 전부
  esac
done
```

```text
[start] -> start 계열
[STOP] -> stop
[restart] -> start 계열
[status-all] -> status 로 시작
[] -> 빈 값
[foo.tar.gz] -> tar
[x.zip] -> 모름
```

`;;`가 갈래의 끝이다. bash 4부터는 `;&`(다음 갈래 본문을 조건 없이 이어서 실행)와 `;;&`(다음 패턴을 계속 검사)도 있지만, C의 switch처럼 습관적으로 흘려 내리는 코드는 읽는 사람을 헷갈리게 해서 거의 쓰지 않는다.

`case`의 패턴은 정규식이 아니라 glob이다. `[0-9]+`라고 쓰면 "숫자 한 글자 다음에 +" 를 찾는다. 숫자인지 볼 때는 `*[!0-9]*`(숫자 아닌 글자가 하나라도 있으면)를 먼저 걸러 내는 식으로 쓴다. 마지막 `*)`를 빠뜨리면 모르는 값이 조용히 지나가니, 서브 명령을 받는 스크립트라면 `*)`에서 사용법을 찍고 2로 끝낸다.

## 반복문 셋과 break, continue

`for`는 단어 목록을 돌고, `while`은 조건 명령이 성공하는 동안, `until`은 실패하는 동안 돈다. 목록을 만드는 방법에서 실수가 잦다.

```bash
for i in {1..5}; do echo -n "$i "; done; echo        # 중괄호 확장
n=3; for i in {1..$n}; do echo -n "$i "; done; echo  # 변수는 안 된다
for ((i=0; i<n; i++)); do echo -n "$i "; done; echo  # C 형식
for i in $(seq 1 "$n"); do echo -n "$i "; done; echo
```

```text
1 2 3 4 5 
{1..3} 
0 1 2 
1 2 3 
```

중괄호 확장은 변수 확장보다 먼저 일어나서 `{1..$n}`은 펼쳐지지 않고 글자 그대로 남는다. 변수 범위는 C 형식이나 `seq`로 돈다.

파일 목록은 `$(ls)`가 아니라 glob으로 돈다. `logs/`에 `app 1.log`와 `app2.log`를 만들고 비교했다.

```bash
for f in $(ls logs); do echo "ls: [$f]"; done
for f in logs/*.log; do echo "glob: [$f]"; done
for f in logs/*.txt; do echo "no match: [$f]"; done
shopt -s nullglob
for f in logs/*.txt; do echo "nullglob: [$f]"; done   # 아무것도 안 돈다
```

```text
ls: [app]
ls: [1.log]
ls: [app2.log]
glob: [logs/app 1.log]
glob: [logs/app2.log]
no match: [logs/*.txt]
```

`$(ls)`의 출력은 공백에서 잘려 `app 1.log`가 둘로 쪼개졌다. glob은 파일 이름 하나를 단어 하나로 넘겨서 공백이 있어도 안전하다. 대신 맞는 파일이 없으면 패턴 문자열 `logs/*.txt`가 그대로 한 번 돈다. 루프 안에서 `rm "$f"`를 하면 `No such file` 오류가 나고, `-f`를 붙였다면 조용히 지나간다. 루프 첫 줄에 `[[ -e $f ]] || continue`를 두거나 `shopt -s nullglob`을 켠다.

`break`와 `continue`는 숫자를 받아 바깥 루프까지 빠져나갈 수 있다.

```bash
for d in a b c; do
  for n in 1 2 3; do
    [[ $n == 2 ]] && continue            # 이번 n만 건너뛴다
    [[ $d == b && $n == 3 ]] && break 2  # 바깥 for까지 끝낸다
    echo "$d$n"
  done
done
```

```text
a1
a3
b1
```

`while`로 무언가를 기다릴 때는 끝이 있어야 한다. 서비스가 뜰 때까지 기다리는 루프에 횟수 제한이 없으면 배포가 영원히 멈춘다.

```bash
for ((try=1; try<=30; try++)); do
  curl -fsS http://localhost:8080/health >/dev/null && break
  sleep 2
done
(( try <= 30 )) || { echo "60초 안에 뜨지 않았다" >&2; exit 1; }
```

`break`로 빠져나오면 `try`는 성공한 회차에 멈춰 있고, 끝까지 돌면 31이 된다. 루프 뒤에서 그 값으로 성공과 실패를 가른다.

## while read는 생각보다 많이 틀린다

파일을 한 줄씩 처리하는 `while read`는 bash에서 가장 자주 쓰는 루프이면서 가장 많이 틀리는 루프다. 공백, 탭, 백슬래시, 마지막 줄바꿈이 없는 줄을 일부러 넣은 `hosts.txt`로 시험했다.

```bash
printf '  web-1 10.0.0.1\nweb-2\t10.0.0.2\nC:\\tmp\\x 10.0.0.3\nlast-no-newline 10.0.0.4' > hosts.txt

count=0
while read line; do count=$((count+1)); echo "[$line]"; done < hosts.txt
echo "plain: count=$count"

count=0
while IFS= read -r line || [[ -n $line ]]; do count=$((count+1)); echo "[$line]"; done < hosts.txt
echo "safe: count=$count"
```

```text
[web-1 10.0.0.1]
[web-2	10.0.0.2]
[C:tmpx 10.0.0.3]
plain: count=3
[  web-1 10.0.0.1]
[web-2	10.0.0.2]
[C:\tmp\x 10.0.0.3]
[last-no-newline 10.0.0.4]
safe: count=4
```

맨 `read`는 세 가지를 바꿔 놓는다. 앞뒤 공백을 깎고(IFS의 공백 문자), 백슬래시를 이스케이프로 먹고(`C:\tmp\x`가 `C:tmpx`가 됐다), 줄바꿈 없이 끝나는 마지막 줄을 버린다. `read`는 줄바꿈을 만나기 전에 파일이 끝나면 읽은 내용을 변수에 넣긴 하지만 종료 코드 1을 내고, `while`은 그걸 보고 루프를 끝낸다. 그래서 정석은 `IFS= read -r line || [[ -n $line ]]`다. `IFS=`는 공백을 깎지 않게, `-r`은 백슬래시를 그대로 두게, 뒤의 검사는 마지막 줄을 살린다. 윈도에서 만든 파일이라면 줄 끝의 `\r`까지 변수에 들어가니 `line=${line%$'\r'}`로 떼어 낸다.

두 번째 함정은 파이프다. 같은 파일을 `cat`으로 흘려 넣었다.

```bash
count=0
cat hosts.txt | while IFS= read -r line || [[ -n $line ]]; do count=$((count+1)); done
echo "pipe: count=$count"

count=0
while IFS= read -r line; do count=$((count+1)); done < <(grep -v '^#' hosts.txt)
echo "procsub: count=$count"
```

```text
pipe: count=0
procsub: count=4
```

파이프의 각 부분은 서브셸에서 돈다. 루프에서 모은 값을 뒤에서 써야 한다면 `done < file`로 리다이렉션하거나, 명령 출력이면 프로세스 치환 `< <(명령)`을 쓴다. 스크립트에서는 `shopt -s lastpipe`를 켜면 파이프의 마지막 명령이 현재 셸에서 돈다(작업 제어가 꺼진 비대화형 셸에서만 먹는다).

세 번째는 루프 안에서 표준 입력을 읽는 명령이다. 호스트 목록을 돌며 `ssh`를 하면 첫 번째 호스트만 처리되고 루프가 끝나는 일이 있다. `ssh`가 루프의 표준 입력(남은 호스트 목록)을 원격으로 넘기려고 다 읽어 버려서다. 표준 입력을 먹는 가짜 함수로 재현했다.

```bash
fake_ssh() { cat >/dev/null; echo "ran on $1"; }   # ssh처럼 표준 입력을 읽는다
while read -r h; do fake_ssh "$h"; done < three.txt
echo ---
while read -r h; do fake_ssh "$h" < /dev/null; done < three.txt   # ssh -n과 같은 효과
echo ---
while read -r -u 3 h; do fake_ssh "$h"; done 3< three.txt         # 목록은 3번으로 읽는다
```

```text
ran on h1
---
ran on h1
ran on h2
ran on h3
---
ran on h1
ran on h2
ran on h3
```

실제 `ssh`라면 `ssh -n`이 표준 입력을 `/dev/null`로 바꿔 준다. `ffmpeg`, `docker exec -i`, 표준 입력을 읽는 모든 명령이 같은 문제를 낸다. 파일 서술자 3번으로 목록을 읽으면 루프 안 명령이 무엇이든 안전하다.

필드 나누기는 `read`에 변수를 여러 개 주면 된다. IFS로 구분자를 바꾸면 `/etc/passwd` 같은 콜론 파일도 읽힌다. 마지막 변수가 나머지를 다 받는다.

```bash
while read -r name ip; do echo "name=$name ip=$ip"; done < hosts.txt
IFS=: read -r user _ uid _ <<< "root:x:0:0:root:/root:/bin/bash"
echo "user=$user uid=$uid"
```

```text
name=web-1 ip=10.0.0.1
name=web-2 ip=10.0.0.2
name=C:\tmp\x ip=10.0.0.3
user=root uid=0
```

첫 루프는 `|| [[ -n $name ]]`을 빼서 마지막 줄을 또 잃었다. 여러 필드를 읽을 때도 이 검사는 필요하다. 줄이 수만 개를 넘으면 bash 루프는 느리다. 한 줄씩 외부 명령을 부르면 더 느리다. 그 정도 처리는 [grep, awk, sed 글](/posts/linux-grep-awk-sed)처럼 awk 한 번으로 넘기는 편이 빠르다.

## 함수는 값을 돌려주지 않는다

bash 함수의 `return`은 값이 아니라 종료 코드를 돌려준다. 0에서 255 사이의 숫자 하나다.

```bash
r() { return "$1"; }
r 3;   echo "return 3 -> $?"
r 256; echo "return 256 -> $?"
r 300; echo "return 300 -> $?"
r -1;  echo "return -1 -> $?"
f_noret() { false; }
f_noret; echo "no return -> $?"   # return이 없으면 마지막 명령의 코드
```

```text
return 3 -> 3
return 256 -> 0
return 300 -> 44
return -1 -> 255
no return -> 1
```

256으로 나눈 나머지만 남는다. 개수를 `return $count`로 돌려주면 256개일 때 0, 즉 "성공"이 된다. 값은 표준 출력으로 내보내고 부른 쪽에서 `$(...)`로 받는다. 로그는 표준 에러로 보내야 값에 섞이지 않는다. 이 나눔은 [bash 스크립트 글](/posts/bash-scripting)의 "함수는 stdout으로 값을, stderr로 로그를" 절에서 다뤘다.

`return`과 `exit`의 차이도 여기서 생긴다. `return`은 함수만 끝내고, `exit`은 셸을 끝낸다. 그런데 "셸"이 어느 셸인지가 문제다.

```bash
die() { echo "fatal: $1" >&2; exit 1; }
get() { [[ -f /nope ]] || die "no config"; echo val; }
v=$(get)
echo "still running, rc=$? v=[$v]"
```

```text
fatal: no config
still running, rc=1 v=[]
```

`die`는 스크립트를 끝내려고 `exit`을 불렀지만, `$(get)` 안은 서브셸이라 서브셸만 끝났다. 부모는 빈 값을 받고 계속 간다. `set -e`가 켜져 있으면 대입 줄의 종료 코드 1에서 멈추지만, `local v=$(get)`처럼 쓰면 그것도 가려진다. 명령 치환 안에서 부르는 함수는 `return 1`로 실패를 알리고, 부른 쪽이 `v=$(get) || exit 1`로 받는 편이 확실하다. `( ... )` 괄호, 파이프, `&` 백그라운드도 모두 서브셸이라 같은 일이 생긴다. `x=1; (x=2; exit 3); echo $x`는 1을 찍고 계속 가고, 중괄호 `{ x=2; }`는 현재 셸에서 돌아 x를 바꾼다.

## local은 부른 쪽까지 보인다

함수 안의 변수는 기본적으로 전역이다. `local`을 붙여야 그 함수 안으로 좁혀진다. 그런데 bash의 `local`은 다른 언어의 지역 변수와 다르게 동작한다.

```bash
count=0
bump() { count=$((count+1)); }        # local 없음: 전역을 바꾼다
bump; bump; echo "global count=$count"

counter() { local count=100; inner; echo "counter sees count=$count"; }
inner()   { echo "inner sees count=$count"; count=999; }
counter
echo "after: global count=$count"
```

```text
global count=2
inner sees count=100
counter sees count=999
after: global count=2
```

`inner`는 자기 안에 `count`를 선언하지 않았는데, 전역 2가 아니라 `counter`의 지역 변수 100을 봤다. 그리고 그 값을 999로 바꿨다. bash는 동적 스코프를 쓴다. 변수를 찾을 때 코드가 쓰인 위치가 아니라 지금 호출된 순서를 거슬러 올라간다. `inner`를 누가 불렀느냐에 따라 같은 줄이 다른 변수를 건드린다.

## 재귀는 되지만 깊어질수록 느려진다

함수가 자기를 부르는 재귀도 된다. 값을 표준 출력으로 돌려주니 매 단계가 `$(...)` 서브셸이 된다.

```bash
fact() {
  local n=$1
  if (( n <= 1 )); then echo 1; return; fi
  local prev; prev=$(fact $((n-1)))
  echo $(( n * prev ))
}
fact 5; fact 20; fact 21
```

```text
120
2432902008176640000
-4249290049419214848
```

bash의 정수는 부호 있는 64비트라서 21!에서 넘쳐 음수가 됐다. 경고는 없다. 소수점도 없다. `$(( 7 / 2 ))`는 3이다. 큰 수나 실수 계산이 필요하면 `bc`나 다른 언어로 넘긴다.

재귀가 자연스러운 곳은 트리 순회다. 디렉터리를 들여쓰기해 찍는 함수다.

```bash
walk() {
  local dir=$1 depth=$2 f      # f를 local로 두지 않으면 하위 호출이 덮어쓴다
  for f in "$dir"/*; do
    [[ -e $f ]] || continue
    printf '%*s%s\n' $((depth*2)) '' "${f##*/}"
    [[ -d $f ]] && walk "$f" $((depth+1))
  done
}
walk tree 0
```

```text
a
  b
    x.txt
  y.txt
c
  z.txt
```

깊이는 조심해야 한다. bash 함수 호출은 무겁고, 깊어질수록 한 번의 호출이 점점 더 느려졌다. 서브셸 없이 깊이만 늘려 재 봤다.

```bash
# n을 500, 1000, 2000, 4000으로 바꿔 가며 잰다
deep() { local n=$1; (( n == 0 )) && return; deep $((n-1)); }
s=$EPOCHREALTIME; deep "$n"; e=$EPOCHREALTIME
echo "$n: $(echo "$e - $s" | bc) s"
```

```text
500: .121772 s
1000: .322815 s
2000: 1.492940 s
4000: 12.787504 s
```

깊이가 두 배가 될 때 시간은 세 배에서 여덟 배로 늘었다. 같은 4000번 덧셈을 `for` 루프로 하면 0.03초였다. 기본으로는 깊이 제한이 없어서 계속 들어가다 메모리가 바닥나 셸이 죽을 수 있다. `FUNCNEST=50`처럼 정해 두면 `d: maximum function nesting level exceeded (50)`를 내고 멈춘다.

트리 순회 정도는 재귀로 쓰고, 그 밖의 반복은 루프로 쓴다. 파일 트리라면 대개 `find`가 더 빠르고 정확하다.

## 사람에게 묻기: read

`read`는 파일만이 아니라 사람의 입력도 받는다. 자주 쓰는 옵션은 몇 개뿐이다.

```bash
read -r -p "배포할 환경? " env              # 질문을 찍고 한 줄 받는다
read -r -s -p "비밀번호: " pw; echo           # -s: 입력을 화면에 보이지 않는다
if read -r -t 10 -p "계속할까? [y/N] " ans; then
  [[ $ans == [yY]* ]] || exit 0
else
  echo "응답이 없어 멈춘다" >&2; exit 1        # -t: 10초 안에 답이 없으면 실패
fi
read -r -a hosts <<< "web-1 web-2 web-3"     # -a: 단어를 배열로 받는다
echo "hosts=${#hosts[@]} first=${hosts[0]}"
```

시간 초과와 입력 끝(EOF)은 종료 코드가 다르다. 둘을 따로 재 봤다.

```bash
sleep 3 | bash -c 'read -r -t 1 x; echo "timeout rc=$?"'
bash -c 'read -r x < /dev/null; echo "eof rc=$?"'
```

```text
timeout rc=142
eof rc=1
```

시간 초과는 128보다 큰 값(여기서는 142), 입력이 끝나면 1이다. cron이나 CI처럼 사람이 없는 곳에서 이 스크립트가 돌면 표준 입력이 비어 있거나 닫혀 있다. `read`가 바로 실패하거나, 표준 입력이 열린 채 아무도 쓰지 않으면 영원히 기다린다. 그래서 확인 질문은 `[[ -t 0 ]]`(표준 입력이 터미널인가)로 먼저 감싸고, 자동화에서는 `-y` 같은 옵션으로 건너뛰게 만든다. `-p`의 질문 문구도 표준 입력이 터미널일 때만 찍힌다.

`-s`로 받은 비밀번호는 화면에는 안 보이지만 변수에는 평문으로 남는다. 그 값을 명령 인자로 넘기면 `ps`에 보인다. 표준 입력이나 파일로 넘기는 이유는 [비밀 관리 글](/posts/secrets-management)에 있다.

## 옵션 받기: getopts

인자가 두세 개를 넘으면 순서로 받기 힘들다. `getopts`는 `-n -v -e prod`처럼 짧은 옵션을 표준 방식으로 파싱하는 내장 명령이다.

```bash
#!/bin/bash
usage() { echo "usage: ${0##*/} [-n] [-v] -e ENV [-t TAG] HOST..." >&2; exit 2; }
dry_run=0 verbose=0 env="" tag=latest
while getopts ":nve:t:h" opt; do          # 콜론이 붙은 글자는 값을 받는다
  case $opt in
    n) dry_run=1 ;;
    v) verbose=$((verbose+1)) ;;          # -vv면 2
    e) env=$OPTARG ;;
    t) tag=$OPTARG ;;
    h) usage ;;
    :) echo "-$OPTARG 에 값이 필요하다" >&2; usage ;;
    \?) echo "모르는 옵션: -$OPTARG" >&2; usage ;;
  esac
done
shift $((OPTIND - 1))                     # 처리한 옵션을 버리고 남은 인자만 둔다
[[ -n $env ]] || usage
(( $# > 0 )) || usage
echo "env=$env tag=$tag dry_run=$dry_run verbose=$verbose hosts=$*"
```

옵션 문자열 맨 앞의 `:`는 오류 메시지를 `getopts`가 찍지 말고 스크립트가 처리하겠다는 뜻이다. 그러면 모르는 옵션에서 `opt`가 `?`, 값이 빠진 옵션에서 `:`가 되고, 문제의 글자가 `OPTARG`에 들어간다. 여러 경우를 돌려 봤다.

```bash
./deploy.sh -nvv -e prod -t v1.4 web-1 web-2; echo "rc=$?"
./deploy.sh -e prod -x web-1; echo "rc=$?"
./deploy.sh -e; echo "rc=$?"
./deploy.sh -e prod web-1 -n; echo "rc=$?"
./deploy.sh -e prod -- -weird-host; echo "rc=$?"
```

```text
env=prod tag=v1.4 dry_run=1 verbose=2 hosts=web-1 web-2
rc=0
모르는 옵션: -x
usage: deploy.sh [-n] [-v] -e ENV [-t TAG] HOST...
rc=2
-e 에 값이 필요하다
usage: deploy.sh [-n] [-v] -e ENV [-t TAG] HOST...
rc=2
env=prod tag=latest dry_run=0 verbose=0 hosts=web-1 -n
rc=0
env=prod tag=latest dry_run=0 verbose=0 hosts=-weird-host
rc=0
```

넷째 줄을 보면 `-n`이 무시되고 호스트 이름으로 들어갔다. `getopts`는 옵션이 아닌 인자를 처음 만나면 멈춘다. GNU 도구처럼 옵션을 아무 데나 섞어 쓰는 습관이 있으면 드라이런이 꺼진 채 배포가 나간다. `--`는 "여기서부터는 옵션이 아니다"라는 표시라서 `-`로 시작하는 값을 넘길 수 있다.

`OPTIND`는 다음에 읽을 인자의 번호다. 아래 그림은 `-nvv -e prod -t v1.4 web-1 web-2`를 읽는 동안 이 값이 어떻게 움직이는지 실제 출력대로 따라간다.

## 조건을 직접 판정해 보기

`[`가 인자 개수로 문법을 고르는 규칙을 직접 구현해 보면 처음 장면이 왜 그렇게 끝났는지 손에 잡힌다. 셸이 단어 분할을 끝낸 뒤 `[`가 받는 인자 배열(마지막 `]`는 뺀 것)을 받아 종료 코드 0, 1, 2 중 하나를 돌려주는 함수다. 인자 0~3개, 단항 `-n` `-z`, 문자열 `=` `==` `!=`, 정수 `-eq` `-ne` `-lt` `-le` `-gt` `-ge`, 그리고 `!`만 다룬다. 테스트의 기대값은 같은 인자를 실제 bash 5.2의 `[`에 넣어 얻은 값이다.

## 처음 그 if를 다시 쓰면

처음의 한 줄은 이렇게 고친다.

```bash
#!/bin/bash
set -euo pipefail
env=${DEPLOY_ENV:?DEPLOY_ENV가 비어 있다}     # 비어 있으면 여기서 멈춘다
if [[ $env == "prod" ]]; then
  [[ -t 0 ]] || { echo "운영 배포는 터미널에서만 확인 후 진행한다" >&2; exit 1; }
  read -r -p "운영에 배포한다. 계속할까? [y/N] " ans
  [[ $ans == [yY] ]] || exit 0
fi
```

`if`는 명령의 종료 코드만 본다. `[`는 인자 개수로 문법을 고르는 명령이라 빈 변수 하나에 뜻이 바뀌고, `[[`는 셸이 직접 읽는 문법이라 그런 일이 없다. 문법 오류도 거짓도 같은 `else`로 간다는 것, 파이프와 `$(...)` 안은 서브셸이라 변수와 `exit`이 갇힌다는 것, `local`은 호출 순서를 따라 보인다는 것, 이 세 가지만 기억해도 bash 분기에서 나는 사고는 대부분 설명된다.

## 면접에서 나올 만한 질문

### bash의 if는 무엇을 보고 분기하나요?

조건식의 참거짓이 아니라 `if` 뒤 명령의 종료 코드를 본다. 0이면 `then`, 0이 아니면 `else`로 간다. 그래서 `if grep -q ...`처럼 명령을 바로 쓸 수 있고, `[`도 비교 결과를 종료 코드로 내는 명령일 뿐이다. 문법 오류로 2가 나와도 거짓과 똑같이 `else`로 가는 게 함정이다.

### `[ ]`와 `[[ ]]`는 어떻게 다른가요?

`[`는 `test`와 같은 내장 명령이라 인자가 넘어오기 전에 단어 분할과 글로빙을 거친다. 빈 변수에 따옴표가 없으면 인자가 사라져 `unary operator expected`가 나거나 `[ -n $v ]`처럼 조용히 참이 된다. `[[`는 bash 키워드라 안쪽을 분할하지 않고, `&&`, `||`, 패턴 매칭 `==`, 정규식 `=~`를 지원한다. 대신 POSIX가 아니라서 `/bin/sh`(dash)에서는 쓸 수 없다.

### `[[ 10 < 9 ]]`가 참인 이유는요?

`[[ ]]` 안의 `<`, `>`는 문자열 사전 순서 비교라서 '1'이 '9'보다 앞이기 때문이다. 숫자 비교는 `-lt`, `-gt` 같은 연산자나 `(( 10 < 9 ))`를 쓴다. `[ 10 > 9 ]`는 더 나빠서 `>`가 리다이렉션으로 읽혀 `9`라는 파일을 만들고 0을 낸다.

### `cat file | while read`로 센 값이 루프 밖에서 0인 이유는요?

파이프의 각 부분이 서브셸에서 돌기 때문이다. while 루프는 부모 셸의 복사본에서 변수를 바꾸고, 끝나면 그 복사본과 함께 값이 사라진다. `done < file`이나 프로세스 치환 `done < <(cmd)`로 쓰면 루프가 현재 셸에서 돈다. 비대화형 스크립트라면 `shopt -s lastpipe`도 된다.

### while read를 안전하게 쓰려면 무엇을 붙이나요?

`while IFS= read -r line || [[ -n $line ]]`로 쓴다. `IFS=`는 앞뒤 공백을 지키고, `-r`은 백슬래시를 그대로 두고, 뒤의 검사는 줄바꿈 없이 끝나는 마지막 줄을 살린다. 루프 안에서 `ssh`처럼 표준 입력을 읽는 명령을 부르면 남은 줄을 먹어 버리니 `ssh -n`을 쓰거나 목록을 `read -u 3`으로 다른 서술자에서 읽는다.

### 함수에서 값을 돌려주려면 어떻게 하나요? return과 exit은요?

`return`은 0~255의 종료 코드만 돌려주고 256으로 나눈 나머지만 남으니 값에는 쓰지 않는다. 값은 표준 출력으로 내고 `v=$(f)`로 받으며, 로그는 표준 에러로 보낸다. `exit`은 현재 셸을 끝내는데, `$(...)` 안에서 부르면 서브셸만 끝나 부모 스크립트는 계속 간다. 그래서 명령 치환으로 부르는 함수는 `return 1`로 실패를 알리고 부른 쪽이 `|| exit 1`로 받는다.

### local 변수의 스코프는 어떻게 되나요?

`local`은 함수 안으로 좁혀 주지만 bash는 동적 스코프라서 그 함수가 부르는 다른 함수에서도 보이고 바뀐다. 변수를 찾을 때 코드 위치가 아니라 호출 순서를 거슬러 올라가기 때문이다. 그래서 함수의 임시 변수는 모두 `local`로 선언해야 바깥 함수의 같은 이름 변수(`i`, `f` 같은)를 덮어쓰지 않는다.

### getopts를 쓸 때 주의할 점은요?

짧은 옵션만 지원하고 옵션이 아닌 인자를 처음 만나면 멈춘다. 그래서 `deploy.sh host -n`의 `-n`은 옵션이 아니라 인자로 남는다. 루프 뒤에는 `shift $((OPTIND - 1))`로 처리한 옵션을 버리고, 옵션 문자열 앞에 `:`를 붙여 모르는 옵션(`?`)과 값 빠진 옵션(`:`)을 직접 처리한다. 긴 옵션이 필요하면 `case`로 직접 파싱한다.
