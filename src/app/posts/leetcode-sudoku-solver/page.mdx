스도쿠 앱을 만든다고 해 보자. 퍼즐 화면은 금방 그린다. 어려운 건 "힌트 보기"와 "정답 확인"이다. 둘 다 컴퓨터가 퍼즐을 직접 풀 수 있어야 한다. 그리고 새 퍼즐을 만들 때도 "이 퍼즐의 답이 정말 하나뿐인가"를 확인하려면 푸는 코드가 필요하다.

[LeetCode 37. Sudoku Solver](https://leetcode.com/problems/sudoku-solver/)가 그 푸는 코드를 짜는 문제다. 칸을 하나씩 채우다 막히면 되돌아가는 백트래킹이라 [N-Queens](/posts/leetcode-n-queens)와 뼈대가 같다. 다른 점은 "어느 칸을 먼저 채우느냐"가 속도를 수천 배 바꾼다는 것이다. 판이 규칙에 맞는지 확인하는 부분은 [Valid Sudoku](/posts/leetcode-valid-sudoku)에서 봤고, 여기서는 그 확인을 얼마나 싸게 하느냐와 칸을 고르는 순서에 집중한다. 이 글은 매번 검사하는 풀이부터 표, 비트마스크, 후보가 가장 적은 칸 고르기까지 네 가지를 같은 퍼즐로 비교한다. 백트래킹의 틀은 [재귀와 백트래킹 글](/posts/recursion-backtracking)에 있다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이고, 퍼즐은 이 글을 위해 직접 만든 것이다.

## 빈칸을 규칙대로 채워 판을 완성한다

9 × 9 판 `board`가 주어진다. 칸에는 `'1'`~`'9'` 또는 빈칸 `'.'`이 들어 있다. 빈칸을 채워 다음 세 규칙을 모두 지키는 판을 만든다.

- 가로줄(행) 9개 각각에 1~9가 한 번씩
- 세로줄(열) 9개 각각에 1~9가 한 번씩
- 3 × 3 상자 9개 각각에 1~9가 한 번씩

답은 하나뿐이라고 보장된다. 함수는 아무것도 돌려주지 않고 `board`를 직접 고친다. 판의 크기가 늘 9 × 9라 입력 크기로 복잡도를 말하기 애매한 문제다. 대신 같은 판에서 "몇 번 넣어 보고 지웠나"로 풀이를 비교한다.

## 한 칸에 무엇을 넣을 수 있는지부터

이 글에서 쓰는 퍼즐 하나를 보자. 이 글의 첫 번째 퍼즐이고 빈칸이 45개다.

```text
3 . . | . . . | . 9 5
4 2 6 | . 5 9 | . . .
9 . . | 3 . 6 | . . .
------+-------+------
2 . 1 | . . . | 7 6 8
6 . . | . . 2 | . . 4
7 . . | 5 . 8 | 3 2 1
------+-------+------
. . . | . . 5 | 8 . 3
. . . | . 3 7 | . 1 .
5 9 . | . . 1 | 2 . 6
```

0번 행 1번 열(맨 윗줄 두 번째 칸)에 무엇이 들어갈 수 있을까. 0번 행에 이미 3, 9, 5가 있다. 1번 열에는 2와 9가 있다. 이 칸이 속한 왼쪽 위 상자에는 3, 4, 2, 6, 9가 있다. 세 곳 어디에도 없는 숫자는 1, 7, 8이다. 이 칸의 후보는 셋이다.

칸 (r, c)가 몇 번 상자에 속하는지는 행과 열을 3으로 나눈 몫으로 정한다. 상자 번호 `k = Math.floor(r / 3) * 3 + Math.floor(c / 3)`이다. 왼쪽 위가 0, 그 오른쪽이 1, 오른쪽 아래가 8이다. [Valid Sudoku](/posts/leetcode-valid-sudoku)에서 쓴 공식과 같다.

이 문제의 모든 풀이는 같은 일을 한다. 빈칸 하나를 골라 후보 중 하나를 넣고 다음 빈칸으로 간다. 후보가 하나도 없는 빈칸을 만나면 마지막으로 넣은 숫자를 지우고 다른 후보를 넣는다. 풀이마다 다른 건 두 가지다. 후보를 얼마나 빨리 구하나, 그리고 다음 빈칸을 어떻게 고르나.

## 빈칸마다 1부터 9까지 넣어 보고 매번 검사하기

가장 곧이곧대로인 풀이다. 판을 왼쪽 위부터 훑어 첫 빈칸을 찾고, 1부터 9까지 하나씩 넣어 보며 행, 열, 상자를 직접 훑어 규칙에 맞는지 본다. 맞으면 넣고 재귀로 다음 빈칸을 푼다. 다음이 실패하면 지우고 다음 숫자를 넣는다. 아홉 숫자가 다 실패하면 이 칸은 막혔으니 `false`를 돌려 앞 칸에 알린다.

```js
function solveSudoku(board) {
  function ok(r, c, ch) {                  // (r, c)에 ch를 넣어도 되나
    for (let i = 0; i < 9; i++) {
      if (board[r][i] === ch || board[i][c] === ch) return false; // 같은 행, 같은 열
      const br = 3 * Math.floor(r / 3) + Math.floor(i / 3);       // 상자 안의 i번째 칸
      const bc = 3 * Math.floor(c / 3) + (i % 3);
      if (board[br][bc] === ch) return false;
    }
    return true;
  }

  function go() {
    for (let r = 0; r < 9; r++) {
      for (let c = 0; c < 9; c++) {
        if (board[r][c] !== ".") continue;   // 첫 빈칸을 찾는다
        for (let d = 1; d <= 9; d++) {
          const ch = String(d);
          if (!ok(r, c, ch)) continue;
          board[r][c] = ch;                  // 넣어 보고
          if (go()) return true;             // 나머지가 풀리면 끝
          board[r][c] = ".";                 // 안 풀리면 지운다
        }
        return false;                        // 아홉 숫자 모두 실패. 앞 칸이 틀렸다
      }
    }
    return true;                             // 빈칸이 없다. 다 풀었다
  }

  go();
}
```

이 코드에서 가장 중요한 줄은 `if (go()) return true`다. 풀린 순간 모든 호출이 줄줄이 `true`를 돌려주며 빠져나와야 한다. 이 줄이 없으면 어떻게 되는지는 뒤에서 본다.

느린 이유가 두 가지 보인다. 첫째, `go()`가 불릴 때마다 판을 처음부터 훑어 빈칸을 찾는다. 둘째, 숫자 하나를 넣어 볼 때마다 `ok`가 27칸을 훑는다. 같은 행, 같은 열을 수없이 다시 본다. 퍼즐 세 개에서 재 보면 두 번째와 세 번째 퍼즐에서 차이가 커진다. 세 번째 퍼즐은 이 풀이로 250만 번 호출하고 890ms가 걸렸다. LeetCode에서는 통과하는 경우가 많지만, 어려운 퍼즐을 넣으면 위태롭다.

## 행, 열, 상자에 쓴 숫자를 표로 기억하기

27칸을 훑는 대신, 행마다 "이 행에 이미 쓴 숫자"를 표로 들고 있으면 확인이 세 번의 조회로 끝난다. `row[r][d]`는 r행에 d가 있는지, `col[c][d]`는 c열에, `box[k][d]`는 k번 상자에 있는지다. 처음에 주어진 숫자로 표를 채우고, 숫자를 넣을 때 세 표에 표시하고, 지울 때 표시를 지운다. 빈칸 목록도 처음에 한 번만 만들어 두면 매번 판을 훑지 않아도 된다.

```js
function solveSudoku(board) {
  const row = Array.from({ length: 9 }, () => new Array(10).fill(false));
  const col = Array.from({ length: 9 }, () => new Array(10).fill(false));
  const box = Array.from({ length: 9 }, () => new Array(10).fill(false));
  const empty = [];                                    // 빈칸 목록 (행 순서)

  for (let r = 0; r < 9; r++) {
    for (let c = 0; c < 9; c++) {
      const ch = board[r][c];
      if (ch === ".") { empty.push([r, c]); continue; }
      const d = Number(ch);
      const k = Math.floor(r / 3) * 3 + Math.floor(c / 3);
      row[r][d] = col[c][d] = box[k][d] = true;        // 주어진 숫자를 표에 적는다
    }
  }

  function go(i) {                                     // i번째 빈칸을 채운다
    if (i === empty.length) return true;
    const [r, c] = empty[i];
    const k = Math.floor(r / 3) * 3 + Math.floor(c / 3);
    for (let d = 1; d <= 9; d++) {
      if (row[r][d] || col[c][d] || box[k][d]) continue; // 세 번 조회로 확인
      row[r][d] = col[c][d] = box[k][d] = true;
      board[r][c] = String(d);
      if (go(i + 1)) return true;
      row[r][d] = col[c][d] = box[k][d] = false;       // 되돌린다: 표와 판 둘 다
      board[r][c] = ".";
    }
    return false;
  }

  go(0);
}
```

호출 수는 앞 풀이와 똑같다. 같은 순서로 같은 칸을 같은 숫자로 채워 보기 때문이다. 바뀐 건 호출 하나의 값이다. 세 번째 퍼즐에서 890ms가 198ms로 줄었다.

되돌리기가 판 하나에서 네 곳(판, 행 표, 열 표, 상자 표)으로 늘었다는 점은 조심해야 한다. 하나라도 빼면 지운 숫자가 표에는 남아서, 뒤에서 그 숫자를 넣을 수 있는 칸에 못 넣게 된다. 답이 있는데 `false`로 끝난다.

## 쓴 숫자를 비트 9개로 들고 다니기

표 하나가 칸 10개짜리 불리언 배열이었다. 숫자는 1~9 아홉 개뿐이니 정수 하나의 비트 9개로 대신할 수 있다. 숫자 d를 썼다면 `d - 1`번 비트를 켠다. 그러면 행, 열, 상자 세 정수를 OR로 합치기만 해도 "이 칸에서 이미 쓰인 숫자"가 한 번에 나오고, 그걸 뒤집으면 후보가 된다. 비트 연산이 낯설면 [비트 조작 글](/posts/bit-manipulation)을 먼저 보자.

```js
const cand = ~(row[r] | col[c] | box[k]) & 0x1ff; // 0x1ff = 아홉 비트가 모두 켜진 수
```

후보를 하나씩 꺼낼 때는 가장 낮은 켜진 비트를 `cand & -cand`로 뽑고 `cand ^= bit`로 지운다. 2의 보수에서 `-cand`는 비트를 뒤집고 1을 더한 값이라, 가장 낮은 1 아래의 비트가 모두 맞물려 그 1만 남는다. `011000001`이면 `000000001`(숫자 1)이 먼저 나오고, 지우면 `011000000`에서 `001000000`(숫자 7), 그다음 `010000000`(숫자 8)이다. 비트에서 숫자로 바꾸는 건 `31 - Math.clz32(bit) + 1`이다. `Math.clz32`는 32비트 정수의 앞쪽 0 개수를 센다.

```js
function solveSudoku(board) {
  const row = new Array(9).fill(0), col = new Array(9).fill(0), box = new Array(9).fill(0);
  const empty = [];
  for (let r = 0; r < 9; r++) {
    for (let c = 0; c < 9; c++) {
      const ch = board[r][c];
      if (ch === ".") { empty.push([r, c]); continue; }
      const bit = 1 << (Number(ch) - 1);
      const k = Math.floor(r / 3) * 3 + Math.floor(c / 3);
      row[r] |= bit; col[c] |= bit; box[k] |= bit;
    }
  }

  function go(i) {
    if (i === empty.length) return true;
    const [r, c] = empty[i];
    const k = Math.floor(r / 3) * 3 + Math.floor(c / 3);
    let cand = ~(row[r] | col[c] | box[k]) & 0x1ff;  // 넣을 수 있는 숫자들
    while (cand) {
      const bit = cand & -cand;                        // 가장 작은 후보
      cand ^= bit;
      row[r] |= bit; col[c] |= bit; box[k] |= bit;
      board[r][c] = String(31 - Math.clz32(bit) + 1);
      if (go(i + 1)) return true;
      row[r] ^= bit; col[c] ^= bit; box[k] ^= bit;     // 켠 비트를 다시 끈다
      board[r][c] = ".";
    }
    return false;
  }

  go(0);
}
```

호출 수는 또 같다. 확인할 숫자 아홉 개를 하나씩 보던 걸 후보만 바로 꺼내게 바뀌었을 뿐이다. 세 번째 퍼즐에서 198ms가 96ms가 됐다. 상태가 정수 27개뿐이라 메모리도 작다. 여기까지가 "호출 하나를 싸게" 만드는 방향의 끝이다. 250만 번이라는 호출 수 자체를 줄이려면 칸을 고르는 순서를 바꿔야 한다.

## 후보가 가장 적은 칸부터 채우기

사람이 스도쿠를 풀 때는 왼쪽 위부터 차례로 채우지 않는다. 들어갈 숫자가 하나뿐인 칸을 찾아 먼저 채운다. 그 숫자를 채우면 같은 행, 열, 상자의 다른 칸 후보가 줄어서 또 하나뿐인 칸이 생긴다. 컴퓨터에게도 같은 일을 시킨다. 매번 남은 빈칸을 모두 보고 후보가 가장 적은 칸을 고른다. 제약 충족 문제에서 MRV(minimum remaining values, 남은 값이 가장 적은 변수부터)라고 부르는 방법이다.

왜 효과가 클까. 후보가 하나인 칸은 고민할 게 없다. 틀릴 수가 없으니 갈래가 생기지 않는다. 후보가 둘인 칸에서 잘못 고르면 그 아래가 통째로 헛수고지만, 갈래가 둘뿐이라 금방 다른 쪽으로 간다. 후보가 아홉인 칸에서 먼저 고르면, 그 선택이 틀렸다는 걸 한참 뒤에야 알게 된다. 그리고 후보가 0인 칸이 생기는 순간 바로 막다른 길이라는 걸 알 수 있다. 행 순서로 가면 그 칸에 도착할 때까지 모르고 수많은 갈래를 돈다.

```js
function popcount(x) {                 // 켜진 비트 수 = 후보 수
  let n = 0;
  while (x) { x &= x - 1; n++; }      // 가장 낮은 1을 하나씩 지운다
  return n;
}

function solveSudoku(board) {
  const row = new Array(9).fill(0), col = new Array(9).fill(0), box = new Array(9).fill(0);
  const empty = [];
  for (let r = 0; r < 9; r++) {
    for (let c = 0; c < 9; c++) {
      const ch = board[r][c];
      if (ch === ".") { empty.push([r, c]); continue; }
      const bit = 1 << (Number(ch) - 1);
      const k = Math.floor(r / 3) * 3 + Math.floor(c / 3);
      row[r] |= bit; col[c] |= bit; box[k] |= bit;
    }
  }

  function go(left) {                  // left: 남은 빈칸 수
    if (left === 0) return true;
    let best = -1, bestCand = 0, bestN = 10;
    for (let i = 0; i < empty.length; i++) {
      const [r, c] = empty[i];
      if (board[r][c] !== ".") continue;               // 이미 채운 칸은 건너뛴다
      const k = Math.floor(r / 3) * 3 + Math.floor(c / 3);
      const cand = ~(row[r] | col[c] | box[k]) & 0x1ff;
      const n = popcount(cand);
      if (n < bestN) {
        bestN = n; best = i; bestCand = cand;
        if (n <= 1) break;                             // 0이나 1이면 더 찾을 필요가 없다
      }
    }
    if (bestN === 0) return false;                     // 넣을 숫자가 없는 칸이 있다

    const [r, c] = empty[best];
    const k = Math.floor(r / 3) * 3 + Math.floor(c / 3);
    let cand = bestCand;
    while (cand) {
      const bit = cand & -cand;
      cand ^= bit;
      row[r] |= bit; col[c] |= bit; box[k] |= bit;
      board[r][c] = String(31 - Math.clz32(bit) + 1);
      if (go(left - 1)) return true;
      row[r] ^= bit; col[c] ^= bit; box[k] ^= bit;
      board[r][c] = ".";
    }
    return false;
  }

  go(empty.length);
}
```

호출마다 남은 빈칸을 모두 훑으니 호출 하나는 비싸졌다. 대신 호출 수가 무너진다. 첫 번째 퍼즐은 488번에서 46번이 됐다. 빈칸이 45개이니, 마지막 확인 한 번을 빼면 모든 칸을 한 번에 맞혔다는 뜻이다. 매번 후보가 하나뿐인 칸이 있었고, 되돌아갈 일이 한 번도 없었다. 세 번째 퍼즐은 2,500,202번에서 968번이 됐다. 2,500배 넘게 줄었고 시간은 96ms에서 0.5ms가 됐다.

복잡도로 말하면 빈칸이 m개일 때 최악은 여전히 9^m 근처다. MRV는 최악을 바꾸지 못한다. 하지만 실제 스도쿠 퍼즐은 답이 하나가 되도록 만들어져 있어서 제약이 강하고, 그 제약을 먼저 써먹는 순서가 탐색량을 결정한다. 판이 9 × 9로 고정이니 이론상으로는 O(1)이라고 말할 수도 있다. 면접에서는 "최악은 지수지만 판이 고정이고, 칸 고르는 순서로 실제 탐색량이 수천 배 차이 난다"고 정리하면 된다.

### Python과 Java로 옮기면

Python은 호출 하나가 무거워서 호출 수를 줄이는 게 더 중요하다. 세 번째 퍼즐을 행 순서 비트마스크 풀이로 돌리면 1342ms, MRV 풀이로 돌리면 4ms였다. 정수의 켜진 비트 수는 Python 3.10부터 `int.bit_count()`가 있다. `bit.bit_length()`가 가장 높은 켜진 비트의 자리라 `1 << (d - 1)`에서 d를 바로 돌려준다. 재귀 깊이는 빈칸 수 + 1이라 많아야 82다.

```python
from typing import List

def solve_sudoku(board: List[List[str]]) -> None:
    rows, cols, boxes = [0] * 9, [0] * 9, [0] * 9
    empty = []
    for r in range(9):
        for c in range(9):
            ch = board[r][c]
            if ch == ".":
                empty.append((r, c))
            else:
                bit = 1 << (int(ch) - 1)
                k = (r // 3) * 3 + c // 3
                rows[r] |= bit; cols[c] |= bit; boxes[k] |= bit

    def go(left: int) -> bool:
        if left == 0:
            return True
        best, best_cand, best_n = None, 0, 10
        for r, c in empty:                      # 후보가 가장 적은 빈칸을 고른다
            if board[r][c] != ".":
                continue
            cand = ~(rows[r] | cols[c] | boxes[(r // 3) * 3 + c // 3]) & 0x1FF
            n = cand.bit_count()                # Python 3.10+
            if n < best_n:
                best, best_cand, best_n = (r, c), cand, n
                if n <= 1:
                    break
        if best_n == 0:
            return False                        # 넣을 수가 없는 빈칸이 있다
        r, c = best
        k = (r // 3) * 3 + c // 3
        cand = best_cand
        while cand:
            bit = cand & -cand                  # 가장 낮은 후보 비트
            cand ^= bit
            rows[r] |= bit; cols[c] |= bit; boxes[k] |= bit
            board[r][c] = str(bit.bit_length())
            if go(left - 1):
                return True
            rows[r] ^= bit; cols[c] ^= bit; boxes[k] ^= bit
            board[r][c] = "."
        return False

    go(len(empty))
```

Python의 `~x`는 무한 정밀도 정수라 `-(x + 1)`이 된다. 음수가 나오지만 `& 0x1FF`로 아홉 비트만 남기면 원하는 값이다. 이 마스크를 빼면 `while cand`가 끝나지 않는다.

Java는 `Integer.bitCount`와 `Integer.numberOfTrailingZeros`가 있다. 판이 `char[][]`라 숫자는 `(char) ('1' + 자리)`로 넣는다. `cand &= cand - 1`이 가장 낮은 비트를 지우는 관용구다.

```java
import java.util.*;

class Solution {
    private final int[] rows = new int[9], cols = new int[9], boxes = new int[9];
    private final List<int[]> empty = new ArrayList<>();
    private char[][] board;

    public void solveSudoku(char[][] board) {
        this.board = board;
        for (int r = 0; r < 9; r++) {
            for (int c = 0; c < 9; c++) {
                if (board[r][c] == '.') { empty.add(new int[]{r, c}); continue; }
                int bit = 1 << (board[r][c] - '1');
                rows[r] |= bit; cols[c] |= bit; boxes[(r / 3) * 3 + c / 3] |= bit;
            }
        }
        go(empty.size());
    }

    private boolean go(int left) {
        if (left == 0) return true;
        int br = -1, bc = -1, bestCand = 0, bestN = 10;
        for (int[] e : empty) {                      // 후보가 가장 적은 빈칸
            int r = e[0], c = e[1];
            if (board[r][c] != '.') continue;
            int cand = ~(rows[r] | cols[c] | boxes[(r / 3) * 3 + c / 3]) & 0x1FF;
            int n = Integer.bitCount(cand);
            if (n < bestN) { bestN = n; br = r; bc = c; bestCand = cand; if (n <= 1) break; }
        }
        if (bestN == 0) return false;
        int k = (br / 3) * 3 + bc / 3;
        for (int cand = bestCand; cand != 0; cand &= cand - 1) { // 가장 낮은 비트를 하나씩 지운다
            int bit = cand & -cand;
            rows[br] |= bit; cols[bc] |= bit; boxes[k] |= bit;
            board[br][bc] = (char) ('1' + Integer.numberOfTrailingZeros(bit));
            if (go(left - 1)) return true;
            rows[br] ^= bit; cols[bc] ^= bit; boxes[k] ^= bit;
            board[br][bc] = '.';
        }
        return false;
    }
}
```

Java 코드는 상태를 필드로 둬서 같은 `Solution` 객체로 두 번 풀면 앞 퍼즐의 비트가 남는다. LeetCode는 테스트마다 객체를 새로 만들지만, 직접 쓸 때는 메서드 안에서 배열을 새로 만든다. 세 언어 모두 세 번째 퍼즐에서 같은 답 `387124695 / 426859137 / …`을 냈다.

### 풀린 뒤에도 계속 지운다

`if (go(i + 1)) return true`를 그냥 `go(i + 1)`로 쓰면 어떻게 될까.

```js
while (cand) {
  // ...넣고
  go(i + 1);                   // 결과를 보지 않는다
  // ...지운다
}
return false;
```

첫 번째 퍼즐을 넣었더니 함수가 끝난 뒤 판이 입력과 똑같았다. 마지막 빈칸까지 채워서 `go(empty.length)`가 `true`를 돌려줘도, 부른 쪽이 그 결과를 무시하고 지우기 줄로 넘어간다. 모든 호출이 자기가 넣은 숫자를 지우며 돌아가니 판은 처음으로 돌아온다. 그동안 다른 후보도 계속 시도하니 시간도 훨씬 오래 걸린다. 답을 하나만 찾으면 되는 백트래킹은 성공을 위로 전달해서 즉시 멈춰야 한다. 모든 답을 모으는 [Subsets](/posts/leetcode-subsets)나 [N-Queens](/posts/leetcode-n-queens)와 다른 점이다.

### 되돌리기를 한 곳에서만 한다

표나 비트를 쓰는 풀이에서 `board[r][c] = "."`만 하고 `row`, `col`, `box`의 표시를 지우지 않으면, 이미 지운 숫자가 표에는 남는다. 그 숫자가 꼭 들어가야 하는 칸이 나중에 그 숫자를 못 넣어서 답이 있는데도 `false`로 끝난다. 반대로 표만 되돌리고 판을 안 지우면 MRV 풀이에서 "이미 채운 칸"으로 잘못 보고 건너뛴다. 상태를 여러 곳에 나눠 들고 있으면 넣을 때와 지울 때 짝이 맞는지 한 줄씩 대조한다.

### 상자 번호를 나눗셈 그대로 쓰기

```js
const k = (r / 3) * 3 + c / 3;   // JavaScript에서는 소수 나눗셈이다
```

JavaScript의 `/`는 정수 나눗셈이 아니다. `r / 3 * 3`은 그냥 r이 돼서 상자 번호가 엉뚱한 실수가 되고, `box[1.333…]`은 `undefined`다. `Math.floor`를 꼭 쓰거나 `(r / 3 | 0)`로 정수로 만든다. Java와 C++의 `int` 나눗셈, Python의 `//`는 몫을 주니 그대로 써도 된다. 언어를 옮겨 쓸 때 가장 잘 빠지는 곳이다.

### 문자와 숫자를 섞어 비교하기

판의 칸은 `'5'` 같은 문자열이다. `board[r][c] === 5`는 늘 거짓이라 같은 숫자를 못 찾는다. 반대로 `String(d)`로 바꾸지 않고 숫자 5를 넣으면 다음 검사에서 `"5"`와 비교되지 않아 같은 숫자가 두 번 들어간다. Java에서는 `char`와 `int`가 섞이면 `'5'`가 53이 된다. 넣을 때와 비교할 때의 형식을 하나로 맞춘다.

## 스도쿠를 바꿔 묻는다면

### 답이 하나뿐인지 확인하라면

푸는 함수가 첫 답에서 멈추지 말고 답을 세게 바꾼다. 다만 끝까지 세지 않고 두 개를 찾는 순간 멈춘다. "하나뿐인가"만 알면 되니 2 이상은 다 같은 답이다. 아래 퍼즐 만들기 이야기에서 이 함수를 쓴다.

### 답이 없을 수도 있다면

먼저 주어진 숫자끼리 규칙을 어기지 않는지 본다. 같은 행에 5가 둘이면 탐색할 필요도 없다. 비트를 채울 때 이미 켜진 비트를 또 켜려 하면 그 순간 실패를 돌려주면 된다. 규칙은 지켜도 답이 없는 판도 있다. 그때는 `go`가 `false`로 끝나니 그 결과를 호출한 쪽에 돌려준다.

### 16 × 16 판이라면

숫자가 16개라 비트 16개가 필요하고, 상자는 4 × 4다. 비트마스크는 `0xffff`로, 상자 번호는 4로 나눈 몫으로 바꾸면 코드가 그대로 돈다. 다만 탐색량이 크게 늘어서 후보가 적은 칸부터 고르는 것만으로는 부족한 퍼즐이 생긴다. 그때는 "이 숫자가 들어갈 수 있는 칸이 이 행에 하나뿐"인 경우도 찾는 추가 추론을 넣거나, 다음의 정확 덮개 방식으로 바꾼다.

### 더 빠른 일반적인 방법은

스도쿠는 정확 덮개(exact cover) 문제로 바꿀 수 있다. "칸 (r, c)에 d를 넣는다"는 선택이 729개(9 × 9 × 9)이고, 지켜야 할 조건이 324개(칸마다 하나씩 81개, 행마다 숫자마다 81개, 열마다 81개, 상자마다 81개)다. 각 조건을 정확히 한 번씩 덮는 선택 81개를 고르는 문제다. 크누스(Donald Knuth)의 Algorithm X를 연결 리스트로 구현한 Dancing Links가 이 방식이고, "덮을 수 있는 선택이 가장 적은 조건부터" 고르는 규칙을 쓴다. 이 글의 MRV를 칸뿐 아니라 행, 열, 상자 조건까지 넓힌 셈이다. 면접에서 코드를 요구하지는 않지만 이름과 아이디어는 알아 두면 좋다.

### 비슷한 문제

[Valid Sudoku](/posts/leetcode-valid-sudoku)는 판이 규칙에 맞는지만 확인한다. 이 글의 표와 비트가 그 문제의 풀이다. [N-Queens](/posts/leetcode-n-queens)는 행마다 퀸 하나를 놓으며 열과 대각선 상태를 비트로 들고 다니는 같은 틀이다. [Word Search](/posts/leetcode-word-search)는 격자에서 표시하고 되돌리는 백트래킹이다.

## 퍼즐을 만들 때는 답이 몇 개인지 센다

처음의 스도쿠 앱으로 돌아가자. 이 글의 퍼즐 세 개도 이렇게 만들었다. 다 찬 판 하나를 만든 뒤, 칸을 하나씩 지워 보면서 지운 뒤에도 답이 하나뿐이면 그대로 두고, 둘 이상이 되면 되살린다.

```js
// 답을 세다가 limit개가 되면 멈춘다
function countSolutions(rows, limit = 2) { /* MRV 풀이에서 left === 0일 때 count++ 하고,
                                              count >= limit이면 true로 멈춘다 */ }

for (const p of shuffledCells) {         // 81칸을 무작위 순서로
  const keep = cell(p);
  clear(p);
  if (countSolutions(current()) !== 1) restore(p, keep); // 답이 둘 이상이면 되살린다
}
```

같은 답에서 출발해도 지우는 순서에 따라 결과가 달랐다. 한 번은 주어진 숫자가 26개 남았고, 순서를 200번 바꿔 본 것 중에는 23개까지 남은 퍼즐(이 글의 세 번째 퍼즐)이 있었다. 지울 때마다 답을 세야 하니 퍼즐 하나에 푸는 함수를 81번 부른다. 그래서 퍼즐 생성기에서는 풀이 속도가 곧 생성 속도다. 행 순서 풀이는 세 번째 퍼즐을 한 번 푸는 데만 890ms가 걸렸고, MRV로는 1ms도 안 걸렸다. 이걸 칸마다 반복한다고 생각하면 차이가 분명하다.

"힌트 보기"는 푼 판에서 사용자가 아직 못 채운 칸 하나를 보여 주면 된다. 더 사람다운 힌트를 원하면 후보가 하나뿐인 칸, 곧 MRV가 가장 먼저 고를 칸을 보여 주면 된다. 사용자가 그 칸의 이유를 직접 확인할 수 있다.

## 칸을 고르는 순서가 속도를 정한다

스도쿠 풀이는 빈칸에 후보를 넣어 보고 막히면 되돌아가는 백트래킹이다. 후보를 확인하는 비용은 27칸 훑기에서 표 조회, 비트 OR 한 번으로 줄일 수 있지만, 그건 상수 배의 개선이다. 탐색량을 바꾸는 건 순서다. 후보가 가장 적은 칸부터 채우면 확실한 칸을 먼저 메우고, 막다른 길을 일찍 알아챈다. 세 번째 퍼즐에서 호출이 250만 번에서 968번으로 줄었다. 그리고 답 하나를 찾는 백트래킹은 성공을 `return true`로 위까지 전달해 즉시 멈춰야 판이 지워지지 않는다.

## 면접에서 나올 만한 질문

### 시간 복잡도는 어떻게 되나요?

빈칸이 m개면 칸마다 최대 9개를 시도하니 최악은 O(9^m)이다. 판이 9 × 9로 고정이라 이론상 상수라고 말할 수도 있다. 실제로는 제약이 강해서 탐색량이 훨씬 작고, 칸 고르는 순서에 따라 같은 퍼즐에서 250만 번과 968번처럼 수천 배 차이가 난다.

### 숫자를 넣어도 되는지 어떻게 빨리 확인하나요?

행, 열, 상자마다 이미 쓴 숫자를 기록해 둔다. 불리언 표면 세 번 조회, 비트마스크면 `row[r] | col[c] | box[k]`를 뒤집어 아홉 비트만 남기면 후보가 한 번에 나온다. 상자 번호는 `Math.floor(r / 3) * 3 + Math.floor(c / 3)`이다.

### 왜 후보가 가장 적은 칸부터 고르나요?

후보가 하나인 칸은 틀릴 수 없으니 갈래가 생기지 않고, 후보가 0인 칸이 생기면 바로 막다른 길임을 안다. 후보가 많은 칸을 먼저 고르면 그 선택이 틀렸다는 걸 한참 뒤에 알아서 그 아래를 통째로 헛돈다. 호출 하나는 비싸지지만 호출 수가 수백에서 수천 배 줄었다.

### `if (go()) return true`가 왜 필요한가요?

답을 하나만 찾는 문제라 성공을 위로 전달해 바로 멈춰야 한다. 결과를 무시하면 마지막 칸을 채운 뒤에도 각 호출이 자기 숫자를 지우며 돌아가서 판이 입력 그대로 남는다. 모든 답을 모으는 부분집합이나 N-Queens와 다른 점이다.

### 되돌릴 때 무엇을 되돌려야 하나요?

넣을 때 바꾼 모든 상태다. 판의 칸, 행 표, 열 표, 상자 표 네 곳을 넣을 때와 같은 짝으로 되돌린다. 비트라면 켠 비트를 XOR로 다시 끈다. 하나라도 빠지면 지운 숫자가 남아 답이 있는데도 실패한다.

### 답이 하나뿐인지 어떻게 확인하나요?

첫 답에서 멈추지 않고 답을 세게 바꾸되, 두 개를 찾는 순간 멈춘다. 퍼즐 생성기는 다 찬 판에서 칸을 하나씩 지우며 이 함수로 답이 하나인지 확인하고, 둘 이상이면 되살린다. 칸마다 한 번씩 부르니 푸는 속도가 곧 생성 속도다.

### 더 빠른 방법이 있나요?

스도쿠를 정확 덮개 문제로 바꿔 Dancing Links(Algorithm X)로 푸는 방법이 있다. 선택 729개, 조건 324개로 놓고 덮을 수 있는 선택이 가장 적은 조건부터 고른다. 후보가 적은 칸부터 고르는 생각을 행, 열, 상자 조건까지 넓힌 것이다.
