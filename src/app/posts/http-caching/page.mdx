배포를 했는데 화면이 그대로인 경우가 있다. 새로고침을 몇 번 해도 옛날 버전이 나오다가, 강력 새로고침을 해야 바뀐다. 브라우저가 이전에 받은 파일을 계속 쓰고 있어서다. HTTP 캐시가 어떤 규칙으로 움직이는지 알면 왜 그런지, 어떻게 설정해야 하는지가 보인다.

## 냉장고에 넣어 두고 꺼내 쓰기

매번 마트에 가서 우유를 사 오는 대신 냉장고에 넣어 두고 꺼내 마신다. 유통기한이 남아 있으면 마트에 갈 필요가 없다. 유통기한이 지났으면 버리기 전에 "이거 아직 괜찮은가?" 확인해 볼 수 있다.

브라우저 캐시가 정확히 이렇게 동작한다. 브라우저가 냉장고, 서버가 마트다. 서버는 응답을 보낼 때 "이건 얼마 동안 그냥 써도 된다"는 유통기한과 "이 파일의 버전은 이거다"라는 표시를 붙여 준다.

## 헤더 몇 개만 알면 된다

`Cache-Control: max-age=N`은 N초 동안 신선하다는 뜻이다. 그 시간 안에는 4번 단계처럼 서버에 아예 묻지 않는다. `ETag`와 `If-None-Match`는 5, 6번처럼 바뀌었는지 확인할 때 쓴다. 비슷한 역할로 수정 시각을 쓰는 `Last-Modified`와 `If-Modified-Since`도 있다.

이름 때문에 가장 많이 헷갈리는 건 `no-cache`다. 저장하지 말라는 뜻이 아니다. 저장은 하되, 쓸 때마다 매번 5번처럼 재검증하라는 뜻이다. 아예 저장하지 말아야 하는 응답, 예를 들어 개인 정보가 담긴 응답에는 `no-store`를 쓴다.

## 배포한 화면이 안 바뀌는 이유

처음에 말한 문제로 돌아가 보면, 보통 `app.js` 같은 파일에 긴 `max-age`가 걸려 있는 경우다. 파일 이름이 그대로니 브라우저는 유통기한이 남은 옛날 파일을 계속 꺼내 쓴다.

요즘 빌드 도구들은 이 문제를 파일 이름으로 푼다. 내용으로 계산한 해시를 이름에 넣어서 `app.3f9a1c.js`처럼 만든다. 내용이 바뀌면 이름이 바뀌고, 브라우저 입장에서는 처음 보는 파일이 된다. 그러니 이름에 해시가 들어간 파일은 아주 길게 캐시해도 안전하다.

```http
# app.3f9a1c.js — 이름이 곧 버전이니 1년 동안 묻지 않아도 된다
Cache-Control: public, max-age=31536000, immutable
```

반대로 HTML은 주소가 늘 같다. 이걸 오래 캐시하면 새 해시 파일을 가리키는 새 HTML을 받지 못한다. 그래서 HTML은 매번 확인하게 둔다.

```http
Cache-Control: no-cache
```

## 정리

캐시는 유통기한(`max-age`) 안에서는 묻지 않고 쓰고, 지나면 버전(`ETag`)을 보여 주며 바뀌었는지만 확인한다. 해시가 붙은 정적 파일은 길게, HTML은 매번 확인하게 두면 빠르면서도 배포가 즉시 반영된다.
