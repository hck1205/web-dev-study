새 서버에 `sudo apt install nginx`로 nginx를 깔고, 만든 정적 사이트를 `/home/matt/site`에 올렸다. `/etc/nginx/sites-available/`에 설정 파일도 하나 만들었다. 그런데 브라우저로 서버 주소를 열면 여전히 "Welcome to nginx!"가 뜬다. 설정을 이리저리 고쳐 보니 이번엔 `403 Forbidden`이 나온다.

둘 다 nginx가 고장 난 게 아니다. 설정 파일을 nginx가 읽는 순서대로 읽지 않았을 뿐이다. 어떤 파일이 실제로 불려 들어가는지, 요청 하나가 어느 server 블록과 어느 location 블록으로 가는지만 알면 이런 문제는 대부분 몇 분 안에 풀린다. 이 글은 설치 직후 상태를 확인하는 데서 시작해 프로세스 구조, Ubuntu의 설정 파일 배치, server·location이 골라지는 규칙, 정적 파일과 403, 안전하게 설정을 바꾸고 로그를 보는 법까지 간다.

기준은 Ubuntu 24.04 LTS와 Ubuntu 저장소의 nginx 패키지(1.24.x)다. 22.04는 1.18.x가 들어 있고 이 글의 내용은 거의 그대로 통한다. 더 새 버전이 필요하면 nginx.org가 운영하는 apt 저장소를 붙여 쓸 수 있는데, 그 패키지는 설정 파일 배치가 조금 다르다. 차이는 해당 부분에서 적는다. 리버스 프록시는 [다음 글](/posts/nginx-reverse-proxy)에서, HTTPS와 성능 설정은 [그다음 글](/posts/nginx-https-performance)에서 이어서 본다.

## master 하나와 worker 몇 개

nginx가 적은 메모리로 연결을 많이 받는 이유는 프로세스 구조에 있다.

master 프로세스는 root로 돈다. 설정 파일을 읽고, 80·443처럼 1024 아래 포트를 열고(root 권한이 필요하다), worker를 띄우고 감시한다. 요청은 직접 처리하지 않는다. 실제 요청은 worker가 처리하는데, Ubuntu 패키지에서는 `www-data` 사용자로 돈다. 그래서 worker가 읽어야 하는 파일은 www-data가 읽을 수 있어야 한다. 뒤에 나오는 403의 절반이 여기서 생긴다.

worker 하나는 스레드 하나로 수천 개의 연결을 동시에 들고 있다. 비결은 이벤트 방식이다. 연결마다 스레드를 붙여 놓고 "데이터가 올 때까지 기다리는" 대신, 리눅스의 epoll에게 "이 소켓들 중 읽을 게 생기거나 쓸 수 있게 되면 알려 달라"고 맡겨 둔다. 알림이 오면 그 연결의 일을 조금 처리하고, 기다려야 하는 지점에 오면 바로 다음 알림으로 넘어간다. 어느 연결 하나 때문에 worker가 멈춰 서 있지 않는다(non-blocking).

비교 대상은 요청마다 프로세스나 스레드를 하나씩 붙이는 방식이다. Apache의 prefork·worker MPM이 대표적이다. 스레드마다 스택 메모리가 들고, 연결이 수천 개가 되면 문맥 전환 비용이 커진다. 그런데 웹 서버가 하는 일은 대부분 "기다리기"다. 느린 휴대폰 회선으로 응답을 조금씩 보내는 동안, 업스트림 앱의 응답을 기다리는 동안 스레드는 놀고 있다. 이벤트 방식은 기다리는 연결에 자원을 거의 쓰지 않는다. 대신 worker 안에서 오래 걸리는 동기 작업을 하면 그 worker가 맡은 모든 연결이 같이 멈춘다는 약점이 있다. 그래서 nginx는 무거운 계산을 직접 하지 않고 앱 서버에 넘기는 역할에 잘 맞는다. 디스크 읽기가 막히는 문제를 덜려고 `aio threads` 같은 스레드 풀 옵션도 있지만, 기본 설정에서는 쓰지 않는다.

관련 설정은 `nginx.conf` 맨 위에 있다.

```nginx
# /etc/nginx/nginx.conf (Ubuntu 기본값에서 발췌)
user www-data;
worker_processes auto;      # CPU 코어 수만큼 worker를 띄운다
pid /run/nginx.pid;

events {
    worker_connections 768; # worker 하나가 동시에 들 수 있는 연결 수
    # multi_accept on;
}
```

`worker_processes auto`는 대부분 그대로 두면 된다. 코어보다 많이 띄워도 이벤트 방식이라 이득이 없다. `worker_connections`는 Ubuntu 기본값이 768이고 nginx 자체 기본값은 512다. 동시에 받을 수 있는 연결은 대략 `worker_processes × worker_connections`인데, 리버스 프록시로 쓰면 클라이언트 쪽 연결 하나에 업스트림 쪽 연결이 하나 더 붙으니 절반으로 잡는다. 이 값을 4096처럼 올릴 때는 프로세스당 열 수 있는 파일 수도 같이 올려야 한다. 연결 하나가 파일 디스크립터 하나라서, 한도에 걸리면 error.log에 `Too many open files`가 찍힌다.

```bash
# worker 프로세스가 실제로 받은 열린 파일 수 한도 확인
cat /proc/$(pgrep -f "nginx: worker" | head -1)/limits | grep "open files"
```

```text
Max open files            1024                 524288               files
```

왼쪽이 soft 한도, 오른쪽이 hard 한도다. nginx가 직접 올리게 하려면 main 컨텍스트에 `worker_rlimit_nofile 8192;`처럼 적는다.

## Ubuntu의 설정 파일 배치

설정이 안 먹을 때 가장 먼저 의심할 건 "내가 고친 파일이 실제로 읽히고 있는가"다. Ubuntu 패키지의 배치는 이렇다.

```text
/etc/nginx/
├── nginx.conf              # 시작점. 여기서 나머지를 include 한다
├── mime.types              # 확장자 → Content-Type 표
├── conf.d/                 # *.conf 파일이 모두 읽힌다 (처음엔 비어 있다)
├── sites-available/        # 사이트 설정을 보관하는 곳 (여기 있다고 읽히지 않는다)
│   └── default
├── sites-enabled/          # 여기 있는 것만 읽힌다. 보통 sites-available로 가는 심볼릭 링크
│   └── default -> /etc/nginx/sites-available/default
├── snippets/               # 여러 사이트가 같이 쓰는 설정 조각
│   ├── fastcgi-php.conf
│   └── snakeoil.conf
└── modules-enabled/        # 동적 모듈을 불러오는 설정
```

`nginx.conf`의 http 블록 끝에 이 두 줄이 있다.

```nginx
http {
    include /etc/nginx/mime.types;
    default_type application/octet-stream;
    # ... 로그, gzip 설정 ...

    include /etc/nginx/conf.d/*.conf;
    include /etc/nginx/sites-enabled/*;
}
```

글머리의 첫 번째 문제는 여기서 풀린다. `sites-available/`에 파일을 만들기만 하고 `sites-enabled/`에 링크를 걸지 않았다. 그러면 그 파일은 아무도 읽지 않는다. 기본 사이트(`default`)만 살아 있으니 기본 페이지가 나온다.

```bash
# 새 사이트를 켠다: sites-enabled에 심볼릭 링크를 만든다
sudo ln -s /etc/nginx/sites-available/mysite /etc/nginx/sites-enabled/mysite

# 기본 사이트가 필요 없으면 링크만 지운다 (원본은 sites-available에 남는다)
sudo rm /etc/nginx/sites-enabled/default

# 지금 켜진 사이트 확인
ls -l /etc/nginx/sites-enabled/
```

`ln -s`의 첫 인자는 절대 경로로 쓴다. `cd /etc/nginx/sites-enabled && ln -s ../sites-available/mysite`처럼 상대 경로로 걸어도 되지만, 엉뚱한 곳에서 상대 경로로 걸면 깨진 링크가 생기고 `nginx -t`가 `open() "/etc/nginx/sites-enabled/mysite" failed (2: No such file or directory)`를 낸다.

`sites-enabled/*`는 확장자를 가리지 않는다. 그래서 편집기가 남긴 `mysite~`나 `mysite.bak` 같은 백업 파일까지 읽혀서 같은 server가 두 번 정의되는 일이 생긴다. 백업은 이 폴더 밖에 둔다. 반대로 `conf.d/`는 `*.conf`만 읽으니 확장자가 다르면 무시된다.

nginx.org 저장소의 패키지를 쓰면 `sites-available`·`sites-enabled`가 없고 `conf.d/default.conf` 하나로 시작한다. 그 경우엔 사이트마다 `conf.d/mysite.conf`를 만들고, 끄고 싶으면 확장자를 바꾼다. 둘을 섞지 않고 한 방식만 쓰는 게 덜 헷갈린다. worker 사용자도 `www-data`가 아니라 `nginx`다.

## 블록은 안쪽으로 상속된다

nginx 설정은 `지시어 값;`과 `블록 { }`으로 이루어진다. 블록을 컨텍스트라고 부르는데, 어떤 지시어를 어느 컨텍스트에 쓸 수 있는지는 정해져 있다.

```nginx
# main 컨텍스트: 프로세스 전체 (user, worker_processes, pid)
user www-data;
worker_processes auto;

events {
    # 연결 처리 방식 (worker_connections)
    worker_connections 768;
}

http {
    # HTTP 전체에 적용. 여기 쓴 값은 모든 server의 기본값이 된다
    sendfile on;
    gzip on;

    server {
        # 가상 호스트 하나 (포트 + 도메인)
        listen 80;
        server_name example.com;
        root /var/www/example;

        location /images/ {
            # 이 경로로 시작하는 요청에만 적용
            expires 7d;
        }
    }
}
```

바깥 블록에 쓴 값은 안쪽 블록이 따로 정하지 않으면 그대로 물려받는다. http에 `gzip on;`이 있으면 모든 server와 location이 압축을 한다. 안쪽에서 같은 지시어를 쓰면 그 블록에서는 안쪽 값이 이긴다.

여기에 함정이 하나 있다. `add_header`, `proxy_set_header`처럼 같은 지시어를 여러 줄 쓰는 배열형 지시어는 안쪽에 한 줄이라도 쓰면 바깥 것을 모두 버리고 안쪽 것만 쓴다. 합쳐지지 않는다. server에 보안 헤더 네 줄을 넣어 두고 location 하나에 `add_header Cache-Control ...`을 추가하면, 그 location에서는 보안 헤더 네 개가 사라진다. 이 문제는 HTTPS 글에서 `snippets/`로 푸는 방법과 함께 다시 본다.

설정 파일이 여러 개로 나뉘어 있어 전체 모습을 보기 어려울 때는 nginx에게 합친 결과를 달라고 한다.

```bash
# 문법 검사 후, include까지 모두 펼친 전체 설정을 출력
sudo nginx -T | less

# 특정 지시어가 어느 파일에 있는지 찾기
sudo nginx -T 2>/dev/null | grep -n "server_name\|# configuration file"
```

`nginx -T`는 파일마다 `# configuration file /etc/nginx/sites-enabled/mysite:` 같은 머리줄을 붙여 출력한다. 내가 고친 파일이 이 목록에 없으면 읽히지 않는 것이다. 장애 상황에서 다른 사람에게 설정을 보여 줄 때도 이 출력을 쓴다. 단, 인증서 키 경로나 비밀 값이 들어 있을 수 있으니 붙여 넣기 전에 확인한다.

## 요청 하나를 받을 server 고르기

nginx 하나에 사이트를 여러 개 올릴 수 있다. 요청이 오면 nginx는 두 단계로 server 블록을 고른다.

먼저 요청이 들어온 IP와 포트로 후보를 좁힌다. 80으로 온 요청에 `listen 443`만 있는 server는 후보가 아니다. 다음으로 후보 중에서 요청의 `Host` 헤더를 `server_name`과 맞춘다. 이름이 맞는 게 여럿이면 이 순서로 고른다.

1. 정확히 같은 이름 (`example.com`)
2. 앞에 별표가 붙은 이름 중 가장 긴 것 (`*.example.com`)
3. 뒤에 별표가 붙은 이름 중 가장 긴 것 (`mail.*`)
4. 정규식 이름 중 설정 파일에 먼저 나온 것 (`~^(?<user>.+)\.example\.net$`)

아무것도 맞지 않으면 그 IP·포트의 기본 server가 받는다. `listen 80 default_server;`라고 표시한 server가 기본이고, 표시한 게 없으면 그 포트를 듣는 server 중 설정에서 처음 나온 것이 기본이 된다.

글머리의 상황을 다시 보자. 링크를 걸어 `mysite`를 켰는데도 서버 IP로 접속하면 여전히 기본 페이지가 나온다면 이 규칙 때문이다. 브라우저 주소창에 IP를 치면 `Host: 203.0.113.10`이 간다. `mysite`의 `server_name`은 `example.com`이니 맞지 않고, `default` 파일의 `listen 80 default_server;`가 요청을 받는다. 도메인으로 접속하거나, 서버 안에서 Host 헤더를 붙여 확인한다.

```bash
# DNS를 바꾸기 전에 Host 헤더만 붙여서 원하는 server가 받는지 확인
curl -I -H "Host: example.com" http://127.0.0.1/

# HTTPS라면 --resolve로 이름과 IP를 직접 묶는다 (SNI도 맞게 간다)
curl -I --resolve example.com:443:127.0.0.1 https://example.com/
```

모르는 Host로 온 요청을 아무 사이트나 받게 두지 않으려면 기본 server를 일부러 비워 둔다.

```nginx
# /etc/nginx/sites-available/00-default-drop
server {
    listen 80 default_server;
    listen [::]:80 default_server;
    server_name _;      # 어떤 이름과도 맞지 않는 값. 관례일 뿐 특별한 뜻은 없다
    return 444;         # nginx 전용 코드: 응답 없이 연결을 끊는다
}
```

IP로 무작정 들어오는 스캐너나, 내 서버 IP에 남의 도메인을 붙여 둔 경우가 여기서 걸러진다. `server_name _;`이 "모든 이름"이라는 뜻이라고 오해하기 쉬운데, 그냥 어디에도 맞지 않는 이름일 뿐이고 기본 server가 되는 건 `default_server` 덕분이다. `default_server`를 같은 IP·포트에 두 번 쓰면 `nginx -t`가 `a duplicate default server for 0.0.0.0:80`으로 거부한다. 기본 사이트(`default`)에도 이 표시가 있으니 하나를 지운다.

## location은 이 순서로 고른다

server가 정해지면 요청 경로(쿼리 문자열을 뺀 부분)로 location을 고른다. 문법은 네 가지다.

```nginx
location = /          { }   # 정확히 일치할 때만
location ^~ /images/  { }   # 접두사 일치. 가장 긴 접두사가 이거면 정규식을 보지 않는다
location ~  \.php$    { }   # 정규식, 대소문자 구분
location ~* \.(css|js)$ { } # 정규식, 대소문자 무시
location /static/     { }   # 일반 접두사 일치
```

고르는 순서는 설정에 적힌 순서와 다르다. 많이 틀리는 부분이라 단계로 쓴다.

1. `=` 정확 일치가 있으면 바로 그걸 쓰고 끝낸다.
2. 모든 접두사 location(`^~`와 일반 접두사) 중 요청 경로와 맞는 가장 긴 것을 찾아 기억해 둔다. 접두사끼리는 적힌 순서가 상관없다.
3. 그 가장 긴 접두사가 `^~`이면 정규식을 보지 않고 그걸 쓴다.
4. 아니면 정규식 location을 설정에 적힌 순서대로 검사해서 처음 맞는 걸 쓴다.
5. 맞는 정규식이 없으면 2번에서 기억해 둔 접두사를 쓴다.

정규식만 "적힌 순서"가 중요하고, 일반 접두사가 정규식보다 길어도 정규식이 이긴다는 게 핵심이다. 이런 설정이 있다고 하자.

```nginx
server {
    listen 80;
    server_name example.com;
    root /var/www/example;

    location = /            { try_files /home.html =404; }
    location /              { try_files $uri $uri/ =404; }
    location /static/       { expires 1h; }
    location ^~ /images/    { expires 30d; }
    location /api/          { return 501; }
    location ~* \.(css|js)$ { expires 7d; }
}
```

아래 그림에서 칸 하나가 location 하나다. 요청 네 개를 차례로 넣어 보면, 포인터는 접두사를 훑으며 가장 긴 것을 기억하고, 그다음 정규식을 본다.

## root와 alias는 경로를 다르게 만든다

정적 파일 경로는 `root`나 `alias`로 정한다. 둘의 차이를 모르고 섞어 쓰면 404가 난다.

`root`는 요청 경로 전체를 뒤에 붙인다. `alias`는 location이 맞춘 부분을 잘라 내고 나머지를 붙인다.

```nginx
# /static/logo.png 요청이 올 때

location /static/ {
    root /var/www/example;
    # → /var/www/example/static/logo.png
}

location /static/ {
    alias /var/www/assets/;
    # → /var/www/assets/logo.png  (/static/ 이 alias 경로로 바뀐다)
}
```

흔한 실수는 `root`에 location 경로까지 써 버리는 것이다. `location /static/ { root /var/www/example/static; }`이면 `/var/www/example/static/static/logo.png`를 찾는다. 경로 끝이 location 이름과 같다면 `root`를 한 단계 위로 올리면 되고, 정말 다른 폴더를 가리켜야 할 때만 `alias`를 쓴다.

`alias`는 끝 슬래시를 location과 맞춰야 한다. `location /static/ { alias /var/www/assets; }`처럼 alias 쪽 슬래시를 빼면 `/var/www/assetslogo.png`가 된다. 반대로 `location /static { alias /var/www/assets/; }`처럼 location 쪽 슬래시를 빼면 `/static../etc/passwd` 같은 요청이 `/var/www/assets/../etc/passwd`로 풀려 상위 폴더가 노출될 수 있다. 실제 보안 감사에서 자주 지적되는 설정이다. location과 alias 양쪽에 모두 슬래시를 붙이는 습관을 들인다.

error.log에는 nginx가 실제로 찾은 경로가 찍힌다. 경로가 헷갈리면 추측하지 말고 로그를 본다.

```text
2026/10/16 09:41:27 [error] 2315#2315: *18 open() "/var/www/example/static/static/logo.png" failed (2: No such file or directory), client: 198.51.100.7, server: example.com, request: "GET /static/logo.png HTTP/1.1", host: "example.com"
```

## index와 try_files

요청 경로가 `/`로 끝나면 nginx는 디렉터리 요청으로 보고 `index` 지시어의 파일을 순서대로 찾는다. 기본값은 `index index.html;`이다.

`try_files`는 "이 순서로 찾아보고, 다 없으면 마지막 것"이다. Ubuntu 기본 사이트에 들어 있는 줄을 조각으로 나눠 보면 이렇다. 조각을 누르면 설명이 나온다.

React, Vue 같은 SPA를 올릴 때는 마지막 항목을 `/index.html`로 바꾼다. `/dashboard/settings` 같은 경로는 디스크에 없고 브라우저의 라우터가 처리하는 경로라서, 없는 경로는 모두 `index.html`을 내려 줘야 새로고침해도 404가 안 난다.

```nginx
# /etc/nginx/sites-available/mysite
server {
    listen 80;
    listen [::]:80;
    server_name example.com www.example.com;

    root /var/www/mysite/dist;
    index index.html;

    # 없는 경로는 모두 SPA의 index.html로
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 빌드 산출물은 실제 파일만. 없으면 index.html 대신 404를 준다
    location /assets/ {
        try_files $uri =404;
    }

    access_log /var/log/nginx/mysite.access.log;
    error_log  /var/log/nginx/mysite.error.log;
}
```

`/assets/`를 따로 둔 이유가 있다. 배포 후 예전 해시의 JS 파일을 요청한 브라우저에게 `index.html`을 200으로 주면, 브라우저는 HTML을 JS로 실행하려다 `Unexpected token '<'` 같은 오류를 낸다. 없는 정적 파일은 404로 끝내야 원인을 알 수 있다. 같은 이유로 `/api/`처럼 앱 서버로 갈 경로가 SPA fallback에 먹히지 않게 별도 location으로 빼 둔다.

`try_files`의 마지막 항목만 내부 리다이렉트를 일으킨다. 그러면 location 고르기가 `/index.html`로 처음부터 다시 일어난다. 위 설정에서는 `location /`이 다시 받아 실제 파일을 보낸다. 이 점 때문에 `location / { try_files $uri /index.html; }`에 `index.html`까지 없으면 내부 리다이렉트가 반복되다가 `rewrite or internal redirection cycle` 에러와 함께 500이 난다.

## 403이 나는 이유

정적 파일을 처음 올릴 때 가장 많이 보는 에러가 `403 Forbidden`이다. 원인은 거의 셋 중 하나고, error.log의 문구가 셋을 구분해 준다.

```bash
# 지금 들어오는 에러를 계속 본다 (Ctrl+C로 종료)
sudo tail -f /var/log/nginx/error.log
```

첫째, 디렉터리를 요청했는데 index 파일이 없다. 빌드 결과물을 `dist/` 안에 두고 root는 그 위로 잡은 경우가 대표적이다.

```text
2026/10/16 09:52:03 [error] 2315#2315: *21 directory index of "/var/www/mysite/" is forbidden, client: 198.51.100.7, server: example.com, request: "GET / HTTP/1.1", host: "example.com"
```

nginx는 index 파일이 없는 디렉터리의 목록을 보여 주지 않는다(`autoindex off`가 기본). 그래서 404가 아니라 403이다. root 경로와 index 파일 이름을 확인한다.

둘째, 파일 권한이다. 글머리의 `/home/matt/site`가 여기에 걸린다.

```text
2026/10/16 09:55:40 [crit] 2315#2315: *25 stat() "/home/matt/site/index.html" failed (13: Permission denied), client: 198.51.100.7, server: example.com, request: "GET / HTTP/1.1", host: "example.com"
```

worker는 www-data로 돈다. 파일 하나를 읽으려면 그 파일에 읽기(r) 권한이 있어야 하고, 루트부터 그 파일까지 거치는 모든 디렉터리에 실행(x) 권한이 있어야 한다. Ubuntu 21.04부터 새로 만든 홈 디렉터리는 `750`이라 다른 사용자가 들어갈 수 없다. 경로의 권한을 한 번에 보는 명령이 있다.

```bash
# 경로를 따라 내려가며 각 단계의 권한을 표시
namei -l /home/matt/site/index.html

# www-data로 실제로 읽히는지 확인
sudo -u www-data head -c 100 /home/matt/site/index.html
```

```text
f: /home/matt/site/index.html
drwxr-xr-x root root /
drwxr-xr-x root root home
drwxr-x--- matt matt matt
drwxrwxr-x matt matt site
-rw-rw-r-- matt matt index.html
```

`matt` 디렉터리에 다른 사용자의 x 권한이 없다. 여기서 막힌다. 홈 디렉터리 권한을 `755`로 풀 수도 있지만 홈 전체를 남에게 여는 셈이라 권하지 않는다. 웹에 낼 파일은 `/var/www` 아래에 두는 게 깔끔하다.

```bash
# 사이트 폴더를 /var/www 아래에 만들고 소유자를 정한다
sudo mkdir -p /var/www/mysite
sudo chown -R matt:www-data /var/www/mysite

# 디렉터리는 750, 파일은 640 (소유자 쓰기, www-data 그룹 읽기)
sudo find /var/www/mysite -type d -exec chmod 750 {} +
sudo find /var/www/mysite -type f -exec chmod 640 {} +

# 빌드 결과를 복사
rsync -a --delete ~/site/dist/ /var/www/mysite/dist/
```

www-data에게 쓰기 권한은 주지 않는다. 웹 서버가 자기가 서비스하는 파일을 고칠 수 있으면, 업로드 취약점 하나로 사이트가 바뀔 수 있다.

셋째, 설정이 일부러 막는 경우다. `deny all;`이나 `location ~ /\. { deny all; }` 같은 규칙에 걸리면 403이고, error.log에 `access forbidden by rule`이 찍힌다. 이건 의도한 동작이다. 드물게 SELinux가 켜진 RHEL 계열에서는 권한이 맞는데도 403이 나는데, 파일의 보안 문맥 때문이다. Ubuntu 기본 설치에는 해당하지 않는다.

## 바꾸기 전에 -t, 적용은 reload

설정을 바꾸는 순서는 언제나 같다. 지금 상태 확인, 백업, 수정, 문법 검사, reload, 동작 확인이다.

```bash
# 1. 지금 설정을 통째로 백업 (날짜를 붙여 /etc 밖에 둔다)
sudo tar czf ~/nginx-backup-$(date +%F-%H%M).tgz -C /etc nginx

# 2. 수정
sudo nano /etc/nginx/sites-available/mysite

# 3. 문법 검사
sudo nginx -t

# 4. 검사가 통과했을 때만 무중단 적용
sudo nginx -t && sudo systemctl reload nginx

# 5. 확인
curl -I -H "Host: example.com" http://127.0.0.1/
sudo tail -n 20 /var/log/nginx/error.log
```

검사가 통과하면 이렇게 나온다.

```text
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```

틀리면 파일과 줄 번호를 알려 준다. 세미콜론을 빠뜨린 경우다.

```text
nginx: [emerg] unexpected "}" in /etc/nginx/sites-enabled/mysite:14
nginx: configuration file /etc/nginx/nginx.conf test failed
```

`-t`는 문법만 보는 게 아니다. 인증서 파일이 실제로 있는지, include한 파일이 있는지, server 블록끼리 충돌하는지도 본다. 같은 이름의 server가 둘이면 이런 경고가 나온다. 경고는 `test is successful`과 함께 나와서 그냥 지나치기 쉬운데, 뒤에 나온 server는 무시된다는 뜻이다.

```text
nginx: [warn] conflicting server name "example.com" on 0.0.0.0:80, ignored
```

reload와 restart의 차이도 알아 둔다. restart는 프로세스를 모두 끄고 새로 띄운다. 그 사이 들어오는 연결은 거부되고, 진행 중인 다운로드나 WebSocket은 끊긴다. 게다가 새 설정이 틀렸다면 꺼진 채로 다시 뜨지 못한다. reload는 master에게 HUP 신호를 보낸다. 아래 그림에서 다음을 누르면 master가 그 신호를 받고 하는 일이 보인다.

<Callout kind="warning" title="restart 전에는 반드시 nginx -t">
설정이 틀린 상태에서 `systemctl restart nginx`를 하면 nginx가 꺼진 뒤 다시 뜨지 못해 모든 사이트가 내려간다. reload는 실패해도 옛 설정으로 계속 돌지만, restart는 그렇지 않다. 문제가 생기면 백업을 풀어 되돌린다: `sudo tar xzf ~/nginx-backup-날짜.tgz -C /etc` 다음에 `sudo nginx -t && sudo systemctl start nginx`. 사이트 하나만 문제라면 `sites-enabled`의 링크만 지우고 reload해도 된다.
</Callout>

설정 파일을 git으로 관리하면 되돌리기가 더 쉽다. `/etc/nginx`에서 `sudo git init` 후 변경할 때마다 커밋해 두면 `git diff`로 무엇이 바뀌었는지 바로 보이고, `git checkout`으로 되돌린다. etckeeper 패키지는 이걸 `/etc` 전체에 대해 apt 설치 때마다 자동으로 해 준다.

## 로그를 읽는 법

로그는 두 종류다. access.log는 요청 한 건마다 한 줄, error.log는 문제가 생겼을 때 남는다. Ubuntu에서는 `/var/log/nginx/`에 있고 logrotate가 매일 돌려 압축한다.

```bash
# 요청이 들어오는 걸 실시간으로 본다
sudo tail -f /var/log/nginx/access.log

# 상태 코드별 개수 (기본 combined 형식에서 9번째 칸이 상태 코드)
sudo awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn

# 404가 많이 난 경로 상위 10개
sudo awk '$9 == 404 {print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head
```

기본 형식은 `combined`다.

```text
198.51.100.7 - - [16/Oct/2026:10:02:11 +0000] "GET /about/ HTTP/1.1" 200 1843 "https://example.com/" "Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/130.0.0.0 Safari/537.36"
```

앞에서부터 클라이언트 IP, 사용자(인증 안 하면 `-` 두 개), 시각, 요청 줄, 상태 코드, 보낸 본문 바이트, Referer, User-Agent다. 성능 문제를 보려면 처리 시간이 없어서 아쉽다. `log_format`으로 칸을 늘린다. http 블록에 정의하고 server나 location에서 이름으로 쓴다.

```nginx
# /etc/nginx/conf.d/log-format.conf
log_format timed '$remote_addr - $remote_user [$time_local] "$request" '
                 '$status $body_bytes_sent "$http_referer" "$http_user_agent" '
                 'rt=$request_time uct=$upstream_connect_time urt=$upstream_response_time';
```

```nginx
# 사이트 설정에서
access_log /var/log/nginx/mysite.access.log timed;
```

`$request_time`은 요청의 첫 바이트를 읽은 순간부터 응답을 다 보내고 로그를 남길 때까지 걸린 시간이다. 클라이언트 회선이 느리면 이 값이 커진다. `$upstream_response_time`은 앱 서버가 응답하는 데 걸린 시간이다. 둘을 나란히 보면 느린 게 앱인지 회선인지 갈린다. 정적 파일만 서비스하는 server에서는 upstream 값이 `-`로 찍힌다. 로그 형식을 JSON으로 만들어 수집기로 보낼 때는 `log_format name escape=json '...'`을 쓴다.

error.log는 수준을 정할 수 있다. 기본은 `error`다. 원인을 못 찾을 때 잠깐 `error_log /var/log/nginx/mysite.error.log info;`로 낮추면 더 많이 찍힌다. `debug`는 디버그 모듈이 들어간 빌드에서만 동작한다. Ubuntu에는 `nginx -V` 출력에 `--with-debug`가 있는지 확인한다. 끝나면 원래대로 돌려 둔다. 로그가 디스크를 채울 수 있다.

logrotate가 로그 파일을 옮기고 나면 nginx는 새 파일에 써야 한다. Ubuntu의 `/etc/logrotate.d/nginx`가 회전 후 `nginx -s reopen`에 해당하는 USR1 신호를 보내 이 일을 한다. 로그를 직접 지웠는데 디스크가 안 비면, nginx가 아직 지운 파일을 붙잡고 있는 것이다. `sudo nginx -s reopen`으로 놓게 한다.

## 설정은 nginx가 읽는 순서대로 읽는다

nginx 설정 문제는 대부분 "어떤 파일이 읽히는가, 요청이 어느 server로 가는가, 어느 location이 고르는가, 그 location이 디스크의 어느 경로를 보는가"를 차례로 확인하면 풀린다. `nginx -T`로 실제로 읽힌 설정을 보고, Host 헤더를 붙인 curl로 server를 확인하고, error.log에 찍힌 경로로 root·alias와 권한을 맞춘다. 바꿀 때는 백업, `nginx -t`, reload 순서를 지킨다. 다음 글에서는 이 nginx를 앱 서버 앞에 세워 요청을 넘기고 나누는 [리버스 프록시](/posts/nginx-reverse-proxy) 설정을 본다.

## 면접에서 나올 만한 질문

### nginx가 적은 자원으로 동시 연결을 많이 처리할 수 있는 이유는?

연결마다 스레드를 붙이지 않고, worker 프로세스 하나가 epoll 같은 이벤트 알림으로 수천 개 연결을 넌블로킹으로 돌려 가며 처리하기 때문이다. 웹 서버의 시간 대부분은 네트워크를 기다리는 데 쓰이는데, 기다리는 연결은 메모리 몇 KB만 차지하고 CPU를 쓰지 않는다. 대신 worker 안에서 오래 막히는 작업을 하면 그 worker의 모든 연결이 같이 멈추니, 무거운 계산은 앱 서버에 넘긴다.

### master와 worker 프로세스는 각각 무슨 일을 하나요?

master는 root로 돌며 설정을 읽고, 1024 아래 포트를 열고, worker를 띄우고 감시한다. 요청은 www-data 같은 낮은 권한의 worker가 처리한다. 권한이 필요한 일과 외부 입력을 다루는 일을 나눠서, worker가 뚫려도 피해가 줄어든다. reload 때 새 설정으로 새 worker를 띄우고 옛 worker를 graceful하게 내리는 것도 master의 일이다.

### 요청이 왔을 때 어느 server 블록이 처리하나요?

먼저 요청이 들어온 IP와 포트를 `listen`하는 server로 좁히고, 그중 Host 헤더를 `server_name`과 맞춘다. 정확한 이름, 앞 와일드카드 중 가장 긴 것, 뒤 와일드카드 중 가장 긴 것, 먼저 나온 정규식 순서다. 아무것도 맞지 않으면 그 포트의 `default_server`, 표시가 없으면 설정에서 처음 나온 server가 받는다. IP로 접속했더니 엉뚱한 사이트가 나오는 이유가 이것이다.

### location 매칭 우선순위를 설명해 주세요.

`=` 정확 일치가 있으면 바로 쓴다. 아니면 접두사 location 중 가장 긴 것을 기억하고, 그게 `^~`면 그대로 쓴다. 아니면 정규식을 설정 순서대로 검사해 처음 맞는 걸 쓰고, 없으면 기억한 접두사를 쓴다. 그래서 `/static/app.js`는 `location /static/`보다 `~* \.js$`가 받고, 그 경우 `/static/`의 설정은 하나도 적용되지 않는다.

### root와 alias의 차이는 무엇이고, alias에서 조심할 점은요?

`root`는 요청 경로 전체를 디렉터리 뒤에 붙이고, `alias`는 location이 맞춘 부분을 alias 경로로 바꾼다. `location /static/`에 `root .../static`을 쓰면 static이 두 번 들어가 404가 난다. alias는 location과 끝 슬래시를 맞춰야 하는데, `location /static`처럼 슬래시 없는 접두사에 `alias .../;`를 쓰면 `/static../` 요청으로 상위 디렉터리에 접근되는 경로 탐색 취약점이 생긴다.

### 정적 사이트에서 403이 나면 무엇을 확인하나요?

error.log 문구로 원인을 가른다. `directory index of ... is forbidden`이면 index 파일이 없는 디렉터리를 요청한 것이라 root 경로와 index 이름을 본다. `Permission denied`면 worker 사용자(www-data)가 파일 읽기 권한과 상위 디렉터리 전부의 실행 권한을 갖는지 `namei -l`로 확인한다. `access forbidden by rule`이면 `deny` 규칙에 걸린 것이다.

### SPA를 nginx로 서비스할 때 새로고침하면 404가 납니다. 어떻게 고치나요?

`/dashboard` 같은 경로는 디스크에 파일이 없고 브라우저 라우터가 처리하니, `try_files $uri $uri/ /index.html;`로 없는 경로를 index.html로 내부 리다이렉트한다. 다만 해시 붙은 JS·CSS나 `/api/` 경로까지 index.html로 떨어지면 원인 찾기 어려운 오류가 나니, 그런 경로는 별도 location에서 `try_files $uri =404;`나 프록시로 처리한다.

### 운영 중에 설정을 바꿀 때 restart가 아니라 reload를 쓰는 이유는요?

reload는 master가 새 설정을 검사해 새 worker를 띄우고, 옛 worker는 처리 중인 요청을 끝낸 뒤 내려가서 연결이 끊기지 않는다. 새 설정이 틀리면 옛 설정으로 계속 돈다. restart는 프로세스를 다 내렸다 올리니 그 사이 연결이 끊기고, 설정이 틀리면 다시 뜨지 못해 장애가 된다. 그래서 `nginx -t && systemctl reload nginx`를 한 묶음으로 쓴다.
