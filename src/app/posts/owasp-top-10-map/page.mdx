새 서비스의 출시 전 보안 검토 양식에 "OWASP Top 10 대응 여부"라는 칸이 있다. 예, 아니오 중 하나를 고르라는데, 무엇을 확인해야 "예"인지는 적혀 있지 않다. 열 개 항목의 이름을 외워도 내 서비스의 어느 코드가 어느 칸에 해당하는지 바로 떠오르지 않는다.

이 글은 그 열 칸을 이 블로그의 보안 글들과 연결한 지도다. 각 칸이 무엇을 뜻하는지, 내 서비스에서는 어디서 나타나는지, 무엇으로 확인하는지를 짧게 적고 자세한 내용은 해당 글로 넘긴다. 칸마다 감이 오도록 일부러 구멍을 낸 작은 Node 앱을 직접 점검하고 고친 결과도 함께 둔다.

## 열 칸은 어떻게 정해지나

OWASP Top 10은 웹 애플리케이션에서 가장 중요한 보안 위험을 열 개로 묶은 인식 제고용 문서다. 여러 회사가 낸 취약점 데이터(어떤 CWE 유형이 몇 개 앱에서 발견됐나)와 실무자 설문을 합쳐 3~4년마다 순위를 새로 정한다. 먼저 짚어 둘 것은 이 문서가 표준이나 점검표가 아니라는 사실이다. "Top 10을 다 통과했다"는 말에는 정해진 기준이 없다. 항목별로 무엇을 확인할지 정한 점검 기준이 필요하면 같은 OWASP의 ASVS(Application Security Verification Standard)를 쓴다.

이 글은 2025년 11월에 공개된 2025년 판을 기준으로 한다. 직전 판은 2021년 판이다. 아래 그림에서 다음을 누르면 2021년 판의 항목이 2025년 판의 어느 칸으로 옮겨 갔는지 하나씩 보인다.

순위가 내려갔다고 덜 위험해진 건 아니다. 주입이 내려온 건 프레임워크의 파라미터 바인딩과 자동 이스케이프가 기본이 되면서 발견 빈도가 줄었기 때문이지, 한 번 터졌을 때의 피해가 작아져서가 아니다.

## 일부러 구멍을 낸 앱을 점검해 본다

칸을 실제 증상으로 느껴 보려고 작은 앱을 만들었다. 주문 조회 API, 로그인 뒤 이동하는 주소, 입력을 JSON으로 파싱하는 보고서 API, 별도의 정책 서버에 물어보는 관리자 API가 있다. 정책 서버는 일부러 꺼 뒀다. `mina`로 로그인해서 다섯 가지를 확인하는 스크립트를 돌렸다.

```bash
# 고치기 전 앱을 띄우고 점검 스크립트를 돌린다
node owasp-app.mjs & node owasp-audit.mjs
```

```text
A01  GET /api/orders/2 as mina          200 {"owner":"jun","item":"monitor"}
A01  next=https://evil.example/login    302 Location: https://evil.example/login
A02  security headers missing           content-security-policy, x-content-type-options, referrer-policy
A10  malformed input -> response        500 SyntaxError: Expected property name or '}' in JSON at position 1 (line 1 column 2) |     a
A10  admin while policy service down    200 {"users":["s-mina"]}
```

다섯 줄이 모두 문제다. `mina`가 `jun`의 주문을 읽었다(A01, 객체 단위 인가 누락). 로그인 뒤 이동 주소에 외부 사이트를 넣으니 그대로 보내 줬다(A01, 열린 리다이렉트). 보안 헤더가 없다(A02). 잘못된 JSON을 보내자 500과 함께 스택 트레이스가 응답 본문에 그대로 나왔고, 거기에는 서버의 파일 경로와 줄 번호까지 있다(A10, 그리고 정보 노출로 A02).

```text
SyntaxError: Expected property name or '}' in JSON at position 1 (line 1 column 2)
    at JSON.parse (<anonymous>)
    at Server.<anonymous> (file:///home/me/shop/owasp-app.mjs:41:22)
    at Server.emit (node:events:519:28)
```

마지막 줄이 가장 위험하다. 정책 서버가 꺼져 있는데 관리자 API가 200을 돌려줬다. 앱 로그에는 이렇게 남았다.

```text
policy check failed (TypeError) -> ALLOW
```

코드를 보면 이유가 한 줄로 보인다. 정책 확인이 예외를 던지면 `catch`에서 `allowed = true`로 넘어가게 짜 놓았다. "정책 서버 장애 때문에 서비스가 멈추면 안 된다"는 선의로 넣은 코드가, 정책 서버를 멈추게 만들 수 있는 사람에게 관리자 권한을 주는 문이 됐다. 2025년 판이 A10을 새로 만든 이유가 이런 장면이다.

```js
let allowed;
try {
  allowed = await policyAllows(user, "admin");
} catch (e) {
  allowed = false; // 고친 버전: 확인하지 못했으면 거절한다 (fail-closed)
}
if (!allowed) return json(403, { error: "forbidden" });
```

다섯 군데를 고친 버전으로 같은 점검을 돌렸다. 주문은 소유자를 확인해 없는 것처럼 404를 주고, 이동 주소는 같은 출처만 허용하고, 헤더를 붙이고, 잘못된 입력은 400으로, 처리하지 못한 오류는 추적 ID만 담은 500으로 돌려주고, 정책 확인이 실패하면 거절한다.

```text
A01  GET /api/orders/2 as mina          404 {"error":"not found"}
A01  next=https://evil.example/login    302 Location: /
A02  security headers missing           none
A10  malformed input -> response        400 {"error":"q must be JSON"}
A10  admin while policy service down    403 {"error":"forbidden"}
policy check failed (TypeError) -> DENY
```

칸은 따로 놀지 않는다. 실제 사고는 작은 구멍 여러 개가 이어져 커진다. 고치기 전 앱이라면 이런 순서가 가능했다. 오류 응답의 스택 트레이스로 내부 구조를 알아내고, 주문 번호를 하나씩 올려 남의 주문을 긁고, 정책 서버를 바쁘게 만들어 관리자 API를 열고, 그동안 로그는 쌓였지만 아무도 알림을 받지 못한다.

## A01 접근 제어: 남의 것을 열 수 있나

가장 흔한 형태는 위 점검의 첫 줄, 주소나 본문의 ID만 바꿔 남의 데이터를 여는 IDOR(BOLA)다. 로그인 여부는 확인했는데 "이 주문이 이 사람 것인가"를 확인하지 않았다. 인증과 인가를 구분하고, 검사를 어느 계층에 둘지, 목록 API에서 인가를 어떻게 하는지는 [인증과 인가](/posts/authn-vs-authz)에 있다.

같은 칸에 사는 다른 것들이 있다. 사용자가 시키지 않은 요청을 쿠키의 힘으로 보내게 만드는 [CSRF](/posts/csrf), 너무 넓게 열어 둔 [CORS](/posts/cors) 설정, 서버가 대신 내부 주소를 부르는 [SSRF](/posts/ssrf), 그리고 위에서 본 열린 리다이렉트다. 열린 리다이렉트는 혼자서는 피해가 작아 보이지만, 믿을 만한 내 도메인 주소로 시작하는 피싱 링크를 만들어 주고, OAuth의 `redirect_uri` 검사가 느슨하면 인가 코드가 새는 경로가 된다.

  caption="로그인 뒤 이동 주소 검사하기"
  functionName="isSafeRedirect"
  initialCode={`// next: 사용자가 준 이동 주소, origin: 내 사이트 출처 (예: "https://app.example.com")
// 같은 출처로만 이동하면 true
function isSafeRedirect(next, origin) {
  return next.startsWith("/");
}`}
  solution={`function isSafeRedirect(next, origin) {
  if (typeof next !== "string" || next === "") return false;
  let u;
  try {
    u = new URL(next, origin);
  } catch {
    return false;
  }
  return u.origin === origin && (u.protocol === "https:" || u.protocol === "http:");
}`}
  tests={[
    { args: ["/dashboard", "https://app.example.com"], expected: true },
    { args: ["https://app.example.com/settings", "https://app.example.com"], expected: true },
    { args: ["//evil.com", "https://app.example.com"], expected: false },
    { args: ["/\\evil.com", "https://app.example.com"], expected: false },
    { args: ["https://app.example.com.evil.com/", "https://app.example.com"], expected: false },
    { args: ["javascript:alert(1)", "https://app.example.com"], expected: false },
    { args: ["http://app.example.com/x", "https://app.example.com"], expected: false },
    { args: ["", "https://app.example.com"], expected: false },
    { args: ["/%2F%2Fevil.com", "https://app.example.com"], expected: true },
  ]}
/>

처음 코드(`startsWith("/")`)는 `//evil.com`과 `/\evil.com`을 통과시킨다. 마지막 테스트의 `/%2F%2Fevil.com`은 인코딩된 슬래시라 내 사이트의 경로 하나로 해석된다. 이동 자체는 안전하지만, 서버 라우터가 이 경로를 디코딩한 뒤 다시 리다이렉트한다면 그 단계에서 다시 검사해야 한다.

## A02 설정 실수: 기본값과 열어 둔 문

코드는 맞는데 설정이 틀린 경우다. 위 점검의 보안 헤더 누락과 스택 트레이스 노출, 기본 관리자 비밀번호, 공개로 열린 저장소 버킷, 운영에 켜 둔 디버그 모드, 필요 이상으로 열린 방화벽 규칙이 모두 이 칸이다. 클라우드와 쿠버네티스처럼 설정 파일 한 줄로 노출 범위가 바뀌는 환경에서는 특히 자주 나온다.

브라우저 쪽 설정은 [웹 보안 헤더](/posts/web-security-headers)와 [nginx HTTPS와 성능](/posts/nginx-https-performance)에, 클라우드 권한은 [IAM 기본](/posts/iam-basics)과 [보안 그룹과 NACL](/posts/security-groups-nacl)에, 컨테이너는 [쿠버네티스 securityContext](/posts/k8s-security-context)와 [RBAC](/posts/k8s-rbac)에, DB 계정은 [PostgreSQL 역할과 보안](/posts/postgres-roles-security)에 있다. 설정 실수는 사람이 한 번씩 고쳐서는 다시 생긴다. 헤더, 권한, 열린 포트를 CI에서 검사해 깨지면 배포가 멈추게 하는 쪽이 오래 간다.

## A03 공급망: 내가 쓰지 않은 코드

내 코드보다 남이 쓴 코드가 훨씬 많다. 직접 쓴 라이브러리가 열 개여도 `node_modules`에는 수백 개가 깔린다. 그중 하나에 알려진 취약점이 있거나, 관리자 계정이 털려 악성 버전이 올라오거나, 이름이 비슷한 가짜 패키지를 깔면 내 서비스가 그 코드를 실행한다. 오래된 lodash를 깔고 `npm audit`을 돌렸다(npm 10.9).

```text
# npm audit report

lodash  <=4.17.23
Severity: high
Command Injection in lodash - https://github.com/advisories/GHSA-35jh-r3h4-6jhm
Regular Expression Denial of Service (ReDoS) in lodash - https://github.com/advisories/GHSA-29mw-wpgm-hmr9
lodash vulnerable to Code Injection via `_.template` imports key names - https://github.com/advisories/GHSA-r5fr-rjxr-66jc
lodash vulnerable to Prototype Pollution via array path bypass in `_.unset` and `_.omit` - https://github.com/advisories/GHSA-f23m-r3pf-42rh
Lodash has Prototype Pollution Vulnerability in `_.unset` and `_.omit` functions - https://github.com/advisories/GHSA-xxjr-mmjv-4gpg
fix available via `npm audit fix --force`
Will install lodash@4.18.1, which is outside the stated dependency range
node_modules/lodash

1 high severity vulnerability
```

`npm audit`은 공개된 권고(advisory) 데이터베이스와 버전을 대조할 뿐이다. 경고가 떴다고 내 코드가 그 함수를 쓴다는 뜻은 아니고, 경고가 없다고 안전하다는 뜻도 아니다. 권고가 나오기 전의 악성 버전은 잡지 못한다. 그래서 공급망 방어는 여러 겹이다. lockfile을 커밋하고 CI에서는 `npm ci`로 정확히 그 버전만 깐다. 새 버전은 자동으로 올리지 않고 PR로 받아 본다. 설치 스크립트(`postinstall`)가 필요 없는 환경에서는 끈다. CI가 클라우드에 접근할 때는 오래 사는 키 대신 짧게 빌리는 자격 증명을 쓴다.

lockfile과 `npm ci`, overrides는 [의존성 지옥](/posts/dependency-hell)에, 버전 범위 표기는 [유의적 버전](/posts/semantic-versioning)에, CI에서 OIDC로 클라우드 역할을 빌리는 방법은 [GitHub Actions로 ECR에 올리기](/posts/github-actions-docker-ecr)에, 저장소에 실수로 들어간 비밀 값은 [Git 대용량 파일과 비밀](/posts/git-large-files-secrets)에 있다.

## A04 암호화 실패: 지켜야 할 것을 평문으로

전송 구간을 암호화하지 않거나, 오래된 프로토콜을 열어 두거나, 비밀번호를 빠른 해시나 평문으로 저장하거나, 키를 코드에 박아 두는 경우다. 비밀번호는 SHA-256 같은 빠른 해시가 아니라 bcrypt, scrypt, Argon2처럼 일부러 느리게 만든 해시와 사용자별 솔트로 저장한다. 빠른 해시는 GPU로 초당 수십억 번 대입할 수 있어서 유출되면 짧은 비밀번호부터 바로 풀린다.

전송 구간은 [HTTPS와 TLS 1.3](/posts/https-tls)과 [전송 구간 암호화](/posts/encryption-in-transit)에, 저장 데이터와 키 관리는 [저장 데이터 암호화](/posts/encryption-at-rest)와 [비밀 관리](/posts/secrets-management)에, 서명 키를 바꾸는 순서는 [JWT 서명 키 교체](/posts/jwt-key-rotation)에 있다.

## A05 주입: 데이터가 코드가 될 때

사용자 입력이 SQL, 셸 명령, LDAP 쿼리, HTML 같은 해석기의 문법 안으로 들어가 코드로 읽히는 문제다. 원리는 하나다. 코드와 데이터를 같은 문자열로 이어 붙였다. 해결도 하나로 모인다. 파라미터 바인딩처럼 코드와 데이터를 따로 넘기는 API를 쓰고, 그럴 수 없는 자리(식별자, HTML 출력)는 허용 목록과 자리에 맞는 인코딩으로 막는다.

SQL은 [SQL 주입](/posts/sql-injection)에서 PostgreSQL로 직접 공격하고 막아 봤고, 브라우저에서 HTML과 자바스크립트로 들어가는 경우는 [XSS](/posts/xss)에 있다. 셸 명령은 `child_process.exec`처럼 문자열 하나를 셸에 넘기는 API 대신 인자를 배열로 넘기는 `execFile`이나 `spawn`을 쓰는 게 같은 원리다.

## A06 설계: 코드는 맞는데 규칙이 틀렸다

모든 줄이 의도대로 동작하는데도 뚫리는 경우다. 비밀번호 재설정 코드를 6자리로 보내면서 시도 횟수를 막지 않았다. 쿠폰 사용 요청을 동시에 두 번 보내면 두 번 다 할인된다. 장바구니 가격을 클라이언트가 보낸 값으로 결제한다. 이런 구멍은 코드 리뷰가 아니라 "이 기능을 악용하려면 어떻게 할까"를 설계 단계에서 묻는 위협 모델링으로 찾는다.

자주 쓰는 대책은 정해져 있다. 시도 횟수와 요청 수를 제한하고([레이트 리미팅 실무](/posts/rate-limiting-in-practice)), 돈이 오가는 요청은 같은 요청이 두 번 와도 한 번만 처리하게 하고([멱등성 키](/posts/idempotency-key)), 가격과 권한처럼 중요한 값은 서버가 다시 계산한다. 공격 트래픽 자체를 견디는 설계는 [DDoS 방어](/posts/ddos-protection)에 있다.

## A07 인증 실패: 누구인지 잘못 믿었다

다른 사이트에서 유출된 비밀번호를 대입하는 크리덴셜 스터핑을 막지 못하거나, 세션을 로그인 뒤에도 바꾸지 않거나, 로그아웃해도 토큰이 살아 있거나, MFA가 없거나 쉽게 우회되는 경우다. 이 블로그에는 이 칸의 글이 가장 많다. 로그인 상태를 유지하는 [쿠키와 세션](/posts/cookie-session-login)과 [토큰 로그인](/posts/token-login), 권한을 빌려주는 [OAuth](/posts/oauth), 두 번째 요소인 [TOTP와 MFA](/posts/mfa-totp), 피싱에 강한 [패스키와 WebAuthn](/posts/passkeys-webauthn), 여러 앱의 로그인을 모으는 [SSO: SAML과 OIDC](/posts/sso-saml-oidc)다. 사내 IP를 믿지 않고 요청마다 사용자와 기기를 확인하는 구조는 [제로 트러스트](/posts/zero-trust-architecture)에 있다.

## A08 무결성 실패: 받은 것이 그것인가

내가 받은 코드나 데이터가 중간에 바뀌지 않았는지 확인하지 않는 경우다. 서명 검증 없이 자동 업데이트를 받는다, CI 파이프라인에 누구나 스크립트를 넣을 수 있다, 서명 없는 직렬화 데이터를 역직렬화한다, JWT의 `alg: none`을 받아 준다. 외부 CDN에서 스크립트를 불러오는 것도 이 칸이다. CDN의 파일이 바뀌면 내 페이지에서 남의 코드가 돈다.

`<script>`의 `integrity` 속성(Subresource Integrity)은 파일 내용의 해시를 미리 적어 두고, 받은 파일의 해시가 다르면 실행하지 않는다. 같은 태그로 원래 파일과 바뀐 파일을 차례로 크로미움 141에서 불러 봤다.

```text
integrity: sha384-Lg4WVO+aW0EjGSsByKP//hflgu3J8+kQlWTVRzw0WS7NMyABdMC9Vg8RmBRQ0vad
original -> v1
cdn file changed -> null
  [console] Failed to find a valid digest in the 'integrity' attribute for resource 'http://other.localhost:18933/lib.js' with computed SHA-384 integrity 'lRX+Aa/kbhkBtDQfrnE40ZzqZuBZeeYEI8p32H9GA25MNdsln8C/p2AsVuUZGDKP'. The resource has been blocked.
```

파일이 바뀌자 스크립트가 실행되지 않았다(`null`). 다른 출처 파일에 쓰려면 `crossorigin="anonymous"`와 CDN의 CORS 응답이 필요하다. 버전이 고정된 파일에만 쓸 수 있다는 한계도 있다. 내용이 수시로 바뀌는 분석 스크립트 같은 건 해시를 정할 수 없어서, 그런 스크립트는 CSP로 출처를 제한하는 데서 멈춘다. JWT 서명 검증의 구멍은 [토큰 로그인](/posts/token-login)에, 빌드 결과물을 다루는 법은 [Dockerfile과 이미지 레이어](/posts/dockerfile-image-layers)에 있다.

## A09 로깅과 알림: 아무도 몰랐다

로그가 없으면 침입이 있었는지조차 답할 수 없다. 로그인 실패, 권한 거부, 입력 검증 실패 같은 보안 이벤트를 남기지 않았거나, 남겼는데 아무도 보지 않거나, 알림이 너무 많아 무시됐다. 2025년 판이 이름에 "알림"을 넣은 건 남기는 것만으로는 부족하다는 뜻이다. 위 점검 앱이 정책 확인 실패를 한 줄 남긴 것도, 그 줄이 쌓였을 때 누군가에게 알림이 가야 의미가 있다.

무엇을 어떤 모양으로 남길지는 [구조화 로그](/posts/structured-logging), 모으고 묻는 곳은 [중앙 로그 파이프라인](/posts/centralized-logging-pipeline), 로그로 사건의 순서를 맞추는 법은 [로그로 버그 추적하기](/posts/debugging-with-logs), 누가 무엇을 지웠는지 답하는 기록은 [쿠버네티스 감사 로그](/posts/k8s-audit-logging), 브라우저에서 난 오류는 [프런트엔드 에러 추적](/posts/frontend-error-tracking)에 있다. 로그에 비밀번호, 토큰, OTP를 남기지 않는 것도 이 칸의 일이다. 로그가 새면 그게 다음 사고가 된다.

## A10 예외 상황 처리: 실패했을 때 어느 쪽으로 넘어지나

2025년 판의 새 칸이다. 위 점검의 두 줄이 이 칸의 대표다. 오류가 나면 권한을 허락해 버리는 fail-open, 그리고 처리하지 못한 오류가 스택 트레이스째 사용자에게 나가는 것. 그 밖에도 타임아웃 없이 외부 호출을 기다리다 스레드가 모두 묶이거나, 트랜잭션 중간에 예외가 나서 반쯤만 반영되거나, 예외를 삼키고 성공 응답을 보내는 경우가 있다.

원칙은 보안 결정은 실패하면 닫히게(fail-closed), 가용성 결정은 실패해도 서비스가 버티게 나누는 것이다. 정책 서버가 죽었을 때 관리자 API를 거절하는 건 맞지만, 추천 서비스가 죽었다고 주문까지 막을 필요는 없다. 이 판단은 기능마다 미리 정해 둔다. 장애가 번지지 않게 하는 장치는 [타임아웃](/posts/timeouts)과 [서킷 브레이커](/posts/circuit-breaker)에, Express에서 async 오류가 프로세스를 내리는 문제는 [Express 미들웨어](/posts/express-middleware)에, 탐지 장비가 죽었을 때 트래픽을 통과시킬지 막을지는 [IDS와 IPS](/posts/ids-ips)의 fail-open 이야기에 있다.

## 열 칸을 한 번에 다 보지 않는다

처음 점검할 때 열 칸을 모두 같은 무게로 볼 필요는 없다. 실제로 사고가 많이 나는 순서로 시작한다. 먼저 API 목록을 뽑아 "다른 사용자로 요청하면 어떻게 되나"를 하나씩 확인한다(A01). 다음으로 `curl -sI`와 의존성 점검처럼 자동으로 돌릴 수 있는 것을 CI에 넣는다(A02, A03). 로그인, 비밀번호 재설정, MFA 해제 같은 인증 흐름의 옆문을 본다(A07). 마지막으로 보안 이벤트가 로그에 남고 알림이 가는지, 오류가 나면 닫히는지를 장애 훈련처럼 일부러 확인한다(A09, A10). 이 순서대로 가다 보면 남는 칸(A04, A05, A06, A08)은 대개 프레임워크 기본값과 설계 검토에서 함께 잡힌다.

## 면접에서 나올 만한 질문

### OWASP Top 10은 무엇이고, 이걸 다 지키면 안전한가요?

웹 애플리케이션의 가장 중요한 보안 위험을 취약점 데이터와 설문으로 묶어 3~4년마다 새로 내는 인식 제고용 문서다. 점검 기준이 아니라서 "다 지켰다"는 판정 기준이 없다. 항목별 검증 요건이 필요하면 ASVS를 쓰고, Top 10은 우선순위와 공통 언어로 쓴다.

### 2025년 판에서 무엇이 바뀌었나요?

SSRF가 독립 항목에서 접근 제어 칸으로 합쳐졌고, 오래된 구성 요소 항목이 빌드와 배포 경로까지 넓혀져 공급망 실패가 됐다. 예외 상황을 잘못 다루는 문제가 새로 들어왔고, 설정 실수가 2위로 올라왔다. 로깅 항목은 이름에 알림을 넣어 기록만 하고 보지 않는 문제를 강조했다.

### 접근 제어 실패가 1위인 이유는 무엇인가요?

검사를 빠뜨리기 가장 쉬운 자리이기 때문이다. 인증은 보통 미들웨어 한 곳에서 처리되지만, "이 객체가 이 사용자 것인가"는 API마다 따로 확인해야 해서 하나만 빠져도 IDOR가 된다. 프레임워크가 대신해 주지 못하는 부분이라 자동 점검으로도 잘 안 잡힌다.

### 열린 리다이렉트는 왜 위험하고 어떻게 막나요?

내 도메인으로 시작하는 링크가 외부 피싱 사이트로 보내 주므로 사용자가 의심하지 않는다. OAuth 같은 흐름에서는 코드나 토큰이 새는 경로가 되기도 한다. 이동 주소를 URL 파서로 해석해 출처가 내 사이트와 같은지 비교하고, `//evil.com`이나 백슬래시 같은 우회 표기를 문자열 비교로 막으려 하지 않는다.

### fail-open과 fail-closed는 언제 무엇을 고르나요?

보안 결정은 실패하면 닫는다. 정책 서버나 인증 서버에 물어보다 실패했다면 거절하는 게 맞다. 반대로 추천이나 통계처럼 보안과 무관한 부가 기능은 실패해도 핵심 기능이 계속 돌게 둔다. 어떤 기능이 어느 쪽인지 미리 정해 두지 않으면, 장애 때 선의로 넣은 `catch`가 권한을 열어 버린다.

### npm audit에 경고가 없으면 공급망은 안전한가요?

아니다. `npm audit`은 공개된 권고와 버전을 대조할 뿐이라, 권고가 나오기 전의 악성 버전이나 이름을 흉내 낸 패키지는 못 잡는다. lockfile 커밋과 `npm ci`, 자동 업그레이드 대신 검토된 PR, 불필요한 설치 스크립트 끄기, CI 자격 증명을 짧게 빌리는 구성까지 겹쳐야 한다.

### 오류 메시지를 사용자에게 자세히 보여 주면 무엇이 문제인가요?

스택 트레이스에는 파일 경로, 라이브러리 이름과 버전, 내부 함수 이름이 들어 있어 공격자가 다음 공격을 고르는 데 쓴다. 사용자에게는 짧은 메시지와 추적 ID만 주고, 자세한 내용은 그 ID로 서버 로그에서 찾는다. 잘못된 입력은 500이 아니라 400으로 구분해 돌려준다.
