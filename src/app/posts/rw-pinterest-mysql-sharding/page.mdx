## 2년 만에 MySQL 한 대에서 80대로

2012년 11월 QCon San Francisco에서 Pinterest의 Marty Weiner와 Yashwanth Nelapati가 발표한 [Scaling Pinterest](https://qconsf.com/sf2012/dl/qcon-sanfran-2012/slides/MartyWeiner_and_YashwanthNelapati_ScalingPinterest.pdf) 슬라이드는 회사의 인프라를 시점별로 나열하는 것으로 시작한다. 슬라이드에 적힌 것만 옮기면 이렇다.

```text
2010-03  RackSpace, 작은 웹 엔진 1대, 작은 MySQL 1대, 엔지니어 1명
2011-01  EC2 + S3 + CloudFront, NGINX 1대, 웹 엔진 4대
         MySQL 1대 + 읽기 슬레이브 1대, 작업 큐 1 + 처리기 2, MongoDB 1, 엔지니어 2명
2011 가을 웹 16 + API 2, 기능별로 나눈 MySQL 5대 + 읽기 슬레이브 9대
         Cassandra 4, Membase 15(클러스터 3개), Memcache 8, Redis 10
         Elasticsearch 4, Mongo 클러스터 3, 엔지니어 3명
2012-01  웹 90 + API 50, MySQL 66대(m1.xlarge) + 각각 슬레이브 1대
         Redis 59, Memcache 51, 작업 처리기 25, 샤딩한 Solr, 엔지니어 6명
2012-10  웹 180 + API 240, MySQL 80대(cc2.8xlarge) + 각각 슬레이브 1대
         Redis 110, Memcache 200, 작업 처리기 80, 엔지니어 40명
```

"2011 가을"은 슬라이드의 페이지뷰 그래프에서 화살표가 가리키는 위치를 읽은 것이고, 슬라이드에 달 이름이 적혀 있지는 않다. 그래프의 세로축에도 숫자가 없어서 트래픽이 정확히 몇 배 늘었는지는 이 자료로 말할 수 없다. 모양만 보면 2011년 후반부터 가파르게 올라간다.

이 목록에서 볼 것은 두 가지다. 하나는 2011년 가을 무렵 저장소 종류가 급격히 늘었다는 것이다. MySQL, Cassandra, Membase, Redis, MongoDB, Elasticsearch가 엔지니어 세 명 아래 함께 돌았다. 다른 하나는 2012년에는 Cassandra, Membase, MongoDB가 목록에서 사라지고 MySQL, Redis, Memcache로 좁혀졌다는 것이다. 발표가 첫 번째 교훈으로 "그것은 실패한다. 단순하게 유지하라"를 내건 맥락이 이 목록이다.

### 남긴 저장소를 고른 말

같은 슬라이드에는 남긴 기술마다 고른 이유가 짧게 붙어 있다. MySQL은 아주 성숙했고, 잘 알려져 있고, 데이터를 크게 잃는 일이 드물고, 요청률이 늘면 응답 시간이 선형으로 늘고, XtraBackup·Innotop·Maatkit 같은 도구와 Percona의 지원이 있고, 무료다. Memcache는 성숙했고, 성능이 좋고, 죽지 않고 실패 방식이 적다. Redis는 쓸 만한 자료구조가 다양하고, 영속화와 복제가 있고, 성능이 꾸준하고, 실패 방식이 적다.

세 목록에 공통으로 들어간 말이 "잘 알려져 있다"와 "실패 방식이 적다"다. 기능이 많다는 말은 없다. EC2를 고른 이유에도 "선택지가 적다"가 단점과 장점으로 두 번 나온다. 고를 게 적으니 고민할 것도 적다는 뜻으로 읽힌다. 엔지니어가 세 명에서 여섯 명이던 시기에 고른 기준이라는 걸 함께 봐야 한다.

## 자동으로 나눠 주는 클러스터를 버린 이유

슬라이드는 데이터를 여러 대에 나누는 방법을 클러스터링과 샤딩 두 가지로 대비한다. 클러스터링은 Cassandra, Membase, HBase처럼 데이터가 자동으로 퍼지고, 옮겨 다니고, 용량에 맞춰 다시 나뉘고, 노드끼리 서로 통신한다. 샤딩은 데이터를 손으로 나누고, 데이터가 움직이지 않고, 부하를 나누려면 데이터를 쪼개고, 노드끼리 서로를 모른다.

클러스터링의 장점도 슬라이드에 그대로 적혀 있다. 저장소가 자동으로 커지고, 세우기 쉽고, 데이터를 공간적으로 분산하고, 가용성이 높고, 부하가 고르고, 단일 장애점이 없다. 그런데 버린 이유는 이렇다. 아직 꽤 젊은 기술이고, 근본적으로 복잡하고, 커뮤니티 지원이 적고, 써 본 엔지니어가 적고, 업그레이드 방식이 어렵고 무섭다. 그리고 "단일 장애점이 있다. 큰 것이."

그 큰 단일 장애점은 클러스터 관리 알고리즘이다. 같은 복잡한 코드가 모든 노드에 복제돼 돌기 때문에, 그 코드가 잘못되면 모든 노드가 함께 잘못된다. 슬라이드가 든 실패 방식은 데이터 재배치가 깨지는 것, 모든 노드에 걸친 데이터 손상, 쉽게 고칠 수 없는 잘못된 균형, 데이터의 권한(누가 진짜 값을 갖는지) 실패다. 두 번째 교훈이 "클러스터링은 무섭다"다.

반대로 샤딩을 고른 이유로는 데이터베이스를 쪼개 용량을 늘릴 수 있고, 데이터를 배치하는 알고리즘이 아주 단순하고, ID 생성이 단순하다는 점을 든다. 노드끼리 서로 모르니 한 노드의 버그가 다른 노드로 번지지 않는다. 대신 그 단순함의 비용은 애플리케이션과 운영자가 진다. 이 대비는 발표자들의 판단이고, 같은 시기 다른 회사들이 Cassandra 같은 클러스터형 저장소로 성공한 사례도 이 시리즈에 있다([Discord 메시지 저장소](/posts/rw-discord-message-storage)). 무엇이 맞는지는 팀이 그 기술을 얼마나 아는지에 달려 있었다고 읽는 게 맞다.

## 샤딩 전에 거친 다섯 단계

발표는 샤딩을 언제 하는지도 말한다. 샤딩은 스키마 설계를 어렵게 하고, 너무 오래 기다리면 전환이 더 어려워진다. 그래서 사이트 설계와 백엔드 구조를 굳히고, 조인과 복잡한 쿼리를 모두 없애고 캐시를 더하고, 기능별로 나눌 수 있는 만큼 나눈 다음, 그래도 크고 있으면 샤딩하라고 한다. Pinterest가 실제로 거친 순서는 슬라이드에 이렇게 적혀 있다.

```text
1. DB 1대 + 외래 키 + 조인
2. DB 1대 + 비정규화 + 캐시
3. DB 1대 + 읽기 슬레이브 + 캐시
4. 기능별로 나눈 DB 여러 대 + 읽기 슬레이브 + 캐시
5. ID로 샤딩한 DB + 백업 슬레이브 + 캐시
```

4단계의 기능별 분할(functional sharding)은 테이블 종류별로 다른 DB에 두는 것이고, 5단계의 ID 샤딩은 같은 테이블의 행을 ID에 따라 여러 DB에 나누는 것이다. 2011년 가을 목록의 "기능별로 나눈 MySQL 5대"가 4단계, 2012년의 "MySQL 66대 + 각각 슬레이브 1대"가 5단계다. 눈에 띄는 변화는 읽기 슬레이브가 백업 슬레이브로 바뀐 것이다. 샤딩 뒤에는 읽기를 슬레이브로 돌리지 않고 마스터에서 읽고, 슬레이브는 장애 대비용으로 둔 것으로 읽힌다. 읽기 부하는 캐시가 받는다. 읽기 복제본을 언제 쓰고 언제 쓰지 않는지는 [복제와 샤딩](/posts/db-replication-sharding) 글에서 다뤘다.

슬라이드는 샤딩하면 생기는 제약도 적는다. 대부분의 조인을 할 수 없고, 트랜잭션을 쓸 수 없고, 유일 제약을 유지하려면 따로 수고가 들고, 스키마 변경에 계획이 더 필요하고, 보고서를 만들려면 같은 쿼리를 모든 샤드에 돌려야 한다. 1~2단계에서 조인과 외래 키를 미리 없앤 건 이 제약을 샤딩하는 날 한꺼번에 맞지 않으려는 준비였다.

이 구조가 주는 것은 조회 한 번 없이 위치를 안다는 것이다. ID에서 샤드 ID를 꺼내면 어느 샤드인지 알고, 타입을 꺼내면 어느 테이블인지 알고, 로컬 ID가 그 테이블의 기본 키다. 로컬 ID를 MySQL auto-increment로 매기니 따로 ID 발급 서버가 필요 없다. 슬라이드가 샤딩의 장점으로 "ID 생성이 단순하다"를 든 이유다. 시간을 상위 비트에 넣어 정렬되게 만드는 Snowflake 계열과는 출발이 다르다. 그쪽 방식과의 차이는 [유일 ID 생성기 설계](/posts/sd-unique-id-generator)의 "64비트를 칸으로 나눠 담기"에서 비교했다.

타입과 로컬 ID가 각각 몇 비트인지는 이 글이 연 자료에 없다. Pinterest는 2015년에 이 설계를 자세히 설명한 엔지니어링 블로그 글을 냈지만, 그 글이 있는 Medium은 이 글을 쓰는 환경에서 열리지 않았다. 열어 보지 못한 자료의 숫자는 옮기지 않는다. 그래서 이 글의 실습도 ID를 비트로 쪼개는 대신, 슬라이드에 실제로 나온 조회 구조를 다룬다.

64비트 ID를 쓰는 서비스라면 어느 회사든 만나는 함정이 하나 있다. 샤드 ID 같은 상위 비트가 차 있으면 값이 2의 53제곱을 넘기 쉽고, 자바스크립트의 Number는 그 이상을 정확히 담지 못해 끝자리가 바뀐다. API에서 이런 ID를 문자열로 내보내는 이유다. 자세한 예는 [유일 ID 생성기 설계](/posts/sd-unique-id-generator)의 "자바스크립트가 번호 끝자리를 바꾼다"에 있다.

### 새 객체는 어느 샤드에 들어가나

슬라이드의 규칙은 짧다. 새 사용자는 샤드에 무작위로 배치한다. 보드, 핀 같은 것들은 그 사용자와 같은 샤드에 두려고 한다. 사용자의 프로필 페이지를 그릴 때 필요한 데이터가 대부분 한 샤드에 모이니, 한 페이지를 그리는 데 여러 샤드를 돌지 않아도 된다. 샤드 키를 사용자로 잡고 관련 데이터를 함께 두는 일반적인 생각과 같다. 샤드 키를 고를 때 무엇을 재는지는 [DB 샤딩](/posts/db-sharding)의 "샤드 키를 정하기 전에 지금 데이터로 재 본다"에 있다.

## 샤드 4,096개를 서버 8대에

처음 배치는 슬라이드 한 장에 있다. 물리 서버 8대에 각각 DB 512개, 모두 4,096개다. 서버 1번에 `db00001`부터 `db00512`, 2번에 `db00513`부터 `db01024`, 마지막 서버에 `db03585`부터 `db04096`이 들어간다. 여기서 DB 하나가 샤드 하나다. 샤드는 MySQL 인스턴스가 아니라 인스턴스 안의 데이터베이스(스키마)다.

숫자 두 개를 같이 보면 여유의 크기가 보인다. ID 공간은 샤드 65,536개를 담지만 처음엔 4,096개만 열었고, 슬라이드는 "수평으로 늘릴 수 있다"고 덧붙인다. 서버 8대에 샤드 4,096개면 서버 하나가 샤드 512개를 들고 있으니, 서버를 반씩 나누는 일을 아홉 번 할 때까지는 샤드를 새로 만들지 않아도 된다. 512를 계속 반으로 나누면 아홉 번째에 1이 된다. 2012년 10월의 MySQL 80대가 모두 이 샤드를 담은 서버인지는 슬라이드에 없지만, 숫자로는 이 여유 안이다.

샤드를 처음부터 많이 만들어 두는 비용도 있다. 서버마다 DB가 수백 개라 테이블 수가 그만큼 곱해지고, 스키마를 바꾸거나 백업을 확인할 때 다룰 대상이 많다. 뒤에 나오는 운영 도구 목록이 그 비용을 보여 준다.

이 구조에서 샤드와 서버의 관계를 들고 있는 건 작은 조회 구조 하나다. 슬라이드에 나온 모양은 이렇다.

```text
{"sharddb001a": (   1,  512),
 "sharddb002b": ( 513, 1024),
 "sharddb003a": (1025, 1536),
 ...
 "sharddb008b": (3585, 4096)}
```

서버 이름마다 맡은 샤드 ID 범위가 있다. 각 앱 서버 프로세스가 이 구조를 캐시한다. 그래서 요청마다 어디 있는지 묻는 왕복이 없다. 서버 이름 끝의 a, b는 슬라이드가 설명하지 않는다. 고가용성 슬라이드가 "멀티 마스터 복제"를 말하니, 같은 샤드 범위를 가진 마스터 쌍 중 지금 쓰는 쪽을 가리켰을 것으로 보인다. 이건 추론이다.

서버 이름과 샤드 범위만 알면 ID에서 꺼낸 샤드 ID로 서버와 DB 이름을 정할 수 있다. 아래에서 직접 짜 보자. 조회 구조는 슬라이드에 나온 네 줄만 넣었고, 슬라이드가 "..."로 줄인 범위는 비워 두었다.

## 조인 없는 표 두 종류

슬라이드는 테이블을 두 종류로만 둔다. 객체 테이블(핀, 보드, 사용자, 댓글)은 로컬 ID와 MySQL blob 한 칸이다. blob에는 JSON이나 직렬화한 Thrift가 든다. 매핑 테이블(사용자가 가진 보드, 핀에 달린 좋아요)은 전체 ID와 전체 ID, 필요하면 타임스탬프다. 이름은 `user_has_boards`처럼 명사_동사_명사로 짓는다. 쿼리는 기본 키나 인덱스 조회뿐이고 조인은 없다. 모든 테이블이 모든 샤드에 있고, 인덱스가 필요하면 새 테이블을 만들기 때문에 스키마 변경이 필요 없다.

객체 본문을 blob 한 칸에 넣으면 칸을 추가해도 `ALTER TABLE`을 돌릴 일이 없다. 대신 DB가 본문 안의 값을 모르니 본문 필드로 찾으려면 그 필드를 키로 하는 매핑 테이블을 따로 만든다. 슬라이드의 "index = new table"이 그 뜻이다. 매핑 테이블에 전체 ID를 넣는 것도 의미가 있다. 다른 샤드에 있는 객체를 가리킬 수 있고, 꺼낸 ID에서 바로 그 객체가 있는 샤드를 안다.

조인이 하던 일을 앱 서버가 쿼리 여러 번으로 나눠 한다. 쿼리 수가 늘어나는 대신 하나하나가 기본 키나 인덱스 조회라 가볍고, 캐시에 담기 쉽다. 반복문 안에서 쿼리를 하나씩 보내면 [N+1 쿼리](/posts/n-plus-one-queries) 문제가 되니, 같은 단계의 ID는 `IN`으로 묶는다. 본문과 관계를 나누는 이 설계는 비정규화의 한 형태다. 비정규화의 일반적인 장단점은 [키와 비정규화](/posts/db-keys-denormalization)에 있다.

옛 데이터를 새 샤드로 옮기는 일도 슬라이드에 한 장 있다. 핀 5억 개, 팔로워 행 16억 개 같은 데이터를 옮기려고 스크립트 농장(scripting farm)을 만들고, 일꾼을 더 띄워 더 빨리 끝냈다. 큐는 GitHub의 Resque를 바탕으로 한 Pyres를 썼다.

## 3년 뒤 공개된 운영 도구가 보여 주는 것

2012년 발표 이후의 모습은 Pinterest가 2015년 10월에 공개한 [pinterest/mysql_utils](https://github.com/pinterest/mysql_utils) 저장소로 엿볼 수 있다. MySQL 서버를 띄우고, 백업하고, 복구하고, 페일오버하고, 샤드를 옮기는 도구 모음이다. 마지막 커밋은 2019년 6월이고, README 첫 줄은 이 프로젝트를 더는 적극적으로 관리하지 않는다고 밝힌다. 그러니 아래 내용은 2015~2019년 코드에 남은 모습이다.

README가 말하는 첫 변화는 복제 구조다. 2012년 슬라이드의 고가용성은 "멀티 마스터 복제"였다. 2015년 README는 예전에는 복제 세트(replica set) 안에 쓰기 가능한 인스턴스를 여럿 두었지만 오류가 나기 쉬워서 마스터 하나와 슬레이브 하나나 둘로 단순화했다고 쓴다. 쓰기가 두 곳에서 일어나면 같은 행을 양쪽에서 고치는 충돌을 막아야 한다. 그 부담을 지는 대신 쓰는 곳을 하나로 줄인 것이다. 마스터를 바꾸는 일은 [페일오버](/posts/failover) 스크립트(`mysql_failover.py`)가 맡는다. 살아 있는 마스터든 죽은 마스터든 다룰 수 있고, 복제 구조를 고치고 서비스 디스커버리를 갱신한다.

두 번째는 ZooKeeper다. README는 관리 도구와 MySQL 애플리케이션 사이의 계약이 ZooKeeper이고, 거의 예외 없이 ZooKeeper가 클라이언트에게 DB 호스트 이름, 사용자 이름, 비밀번호를 준다고 쓴다. 코드의 샤드 맵은 서비스, 네임스페이스, 샤드 번호를 거쳐 그 샤드의 DB 이름(`mysqldb`)과 복제 세트 이름(`replica_set`)으로 이어지는 JSON이다. 2012년에 앱 프로세스가 캐시하던 "서버 이름 → 샤드 범위" 조회 구조가, 이 시점에는 ZooKeeper에서 내려받는 샤드 맵의 모양으로 남아 있다. 이런 식으로 위치 정보를 한곳에서 나눠 주는 구조가 [서비스 디스커버리](/posts/service-discovery)다.

세 번째는 서버를 고치지 않는다는 원칙이다. README는 MySQL 서버가 거의 설정 변경 없이 띄워지고, 살고, 죽는다고 쓴다. 커널 업그레이드, MySQL 버전 업, 재시작이 필요한 변경은 제자리에서 하지 않고 서버를 새로 띄워 바꾸고, 필요하면 페일오버나 슬레이브 승격을 한다. 이렇게 하니 중간 상태를 관리할 필요가 없어 자동화가 크게 단순해졌다고 한다. 새 서버는 띄워진 뒤 데이터 디렉터리가 비어 있으면 백업을 찾아 복구하고 복제를 걸고 서비스 디스커버리에 스스로를 넣는다. 서비스 디스커버리에서 빠진 서버는 은퇴 대기열에 들어가 하루 동안 상태 카운터가 늘지 않으면 종료 명령을 받고, 다시 하루가 지나면 없앤다.

### 샤드가 수천 개면 매일 확인해야 하는 것

README의 도구 목록을 보면, 샤드가 많을 때 사람이 놓치기 쉬운 것들을 스크립트로 정기 점검한 흔적이 보인다. 목적만 옮기면 이렇다.

```text
schema_verifier.py         샤딩한 데이터 묶음 전체에서 스키마가 같은지 확인
mysql_checksum.py          매일 일부 샤드에 pt-checksum을 돌려 마스터와 슬레이브가 어긋났는지, 얼마나인지 기록
check_mysql_replication.py pt-heartbeat로 계산한 복제 지연을 보여 줌
find_shard_mismatches.py   운영 서버에서 엉뚱한 곳에 있는 샤드를 찾음
mysql_backup_status.py     모든 복제 세트에 백업이 돌았는지 확인
archive_mysql_binlogs.py   복제 세트의 서버를 모두 잃어도 시점 복구를 하도록 binlog를 S3에 올림
```

"모든 테이블이 모든 샤드에 있다"는 2012년 규칙은 편하지만, 샤드 수천 개의 스키마가 실제로 같은지는 누군가 확인해야 한다. 체크섬을 전체가 아니라 매일 일부 샤드에 돌리는 것도 눈여겨볼 만하다. 전부 매일 돌리면 부하가 크니, 표본을 돌려 가며 어긋남을 잡는 방식으로 보인다. 어긋남을 찾는 도구가 복제·스키마·위치·백업마다 따로 있다는 것 자체가, 샤딩의 단순함이 운영 점검의 양으로 옮겨 간다는 걸 보여 준다.

### 2012년 슬라이드의 빈칸을 채우는 스크립트

앞에서 "나눈 뒤 남는 DB 256개는 어떻게 정리하나"를 남겨 두었다. 2015년 첫 공개 때부터 있던 `find_shard_mismatches.py`는 운영 서버를 살펴 잘못된 위치에 있는 샤드를 찾고, `fix_orphaned_shards.py`가 그 뒤를 이어 쓰지 않는 샤드의 이름을 바꾼 다음 결국 지운다. 바로 지우지 않고 이름부터 바꾸는 건, 잘못 지웠을 때 되돌릴 틈을 두는 순서다.

2017년 6월에는 샤드를 복제 세트 사이에서 옮기는 `start_shard_migration.py`와 `finish_shard_migration.py`가 추가됐다. 코드 주석에 따르면 이 시점의 샤드 이동은 일부 서비스 대상이었고, 원래의 `sharddb`, `modsharddb`는 "2017년 1분기에 배울 것"이라며 막아 두었다. 아래는 두 스크립트의 순서를 단계로 옮긴 것이다.

### 발표가 다음 과제로 남긴 것

2012년 슬라이드의 마지막 기술 장은 "진행 중인 일"이다. 서비스 기반 구조로 가는 것과 그 이유로 연결 수 제한, 기능의 격리, 접근의 격리(보안)를 들고, 팀을 키우는 일과 새 기능을 덧붙인다. 앱 프로세스 수백 개가 각자 모든 샤드 서버에 연결하면 MySQL의 연결 수가 먼저 바닥난다. 웹 180대와 API 240대가 MySQL 80대에 붙어 있던 2012년 10월 숫자를 보면 그 걱정이 이해된다. 다만 그 뒤 서비스 기반 구조가 어떻게 만들어졌는지는 이 글이 연 자료에 없다. 2015년 README가 ZooKeeper로 호스트 이름과 계정을 나눠 준다고 쓰는 것이 연결 정보를 한곳에서 관리하게 된 흔적이라는 정도만 말할 수 있다.

## 발표 슬라이드와 코드가 말하지 않는 것

이 글의 근거는 회사 사람이 한 발표의 슬라이드와 회사가 공개한 코드다. 슬라이드는 말로 한 설명을 뺀 요점이라, 각 문장 뒤의 이유와 수치가 빠져 있다. 페이지뷰 그래프에는 숫자가 없고, 서버 이름 끝의 a·b가 무엇인지, 4,096개 샤드를 어떻게 고른 수인지도 없다. 클러스터링을 "무섭다"고 한 판단은 그 시점 그 팀의 경험이고, 그 판단이 실제 어떤 장애에서 나왔는지는 적혀 있지 않다. mysql_utils는 README 스스로 "그냥은 동작하지 않는다"고 밝히는, 회사 고유의 연결 부분을 뺀 코드다. 코드에서 읽은 절차가 실제 운영에서 얼마나 자주, 어떤 문제와 함께 쓰였는지는 알 수 없다. 2015년 블로그 글을 열지 못한 것도 이 글의 한계다. 그래서 ID 칸의 비트 수는 샤드 ID의 16비트만 셈으로 적었다.

## 우리 DB가 한 대로 모자라질 때 먼저 볼 것

Pinterest의 선택이 맞았던 조건은 이렇다. 데이터가 사용자 중심으로 모이고(사용자의 보드, 보드의 핀), 화면 대부분이 한 사용자의 데이터로 그려지고, 조인 없이 기본 키와 매핑 테이블로 읽을 수 있었다. 그리고 팀이 클러스터형 저장소보다 MySQL을 훨씬 잘 알았다. 이 조건이면 ID에 샤드를 넣고 데이터를 움직이지 않는 단순한 방식이 운영 부담을 줄인다.

조건이 다르면 같은 답이 아니다. 여러 사용자의 데이터를 가로지르는 쿼리(검색, 랭킹, 관리자 보고서)가 핵심이면 모든 샤드에 같은 쿼리를 돌려야 한다. 트랜잭션으로 여러 행을 함께 바꿔야 하는 업무(결제, 재고)면 샤드를 넘는 순간 트랜잭션이 사라진다. 사용자 하나가 너무 커질 수 있는 서비스라면, 관련 데이터를 한 샤드에 모으는 규칙이 그 샤드를 뜨겁게 만든다. 처음부터 이 구조를 따라 하면 쓰기 전부터 조인, 외래 키, 유일 제약을 포기하고, 샤드 맵과 이동 도구까지 만들어야 한다. Pinterest도 DB 한 대에서 다섯 단계를 거친 뒤에 ID 샤딩으로 갔다.

작은 팀이 지금 가져올 수 있는 건 그 다섯 단계의 앞부분이다. 조인과 외래 키에 기대는 쿼리를 줄이고 캐시를 앞에 두는 것만으로도 DB 한 대가 버티는 기간이 길어진다. 나중을 대비한다면 ID를 외부에 노출할 때 DB 내부 위치에 묶이지 않는 형태로 두고, 테이블마다 "이 행의 주인 사용자"를 분명히 해 두면 샤드 키 후보가 생긴다. 지표로는 테이블별 크기와 쿼리별 실행 횟수를 꾸준히 남긴다. mysql_utils에도 테이블 크기를 기록하는 스크립트(`mysql_record_table_size.py`)가 따로 있다.

비슷한 신호가 보이면 볼 순서도 정해 둔다. 쓰기 지연이 늘면 먼저 읽기를 복제본이나 캐시로 돌릴 수 있는지 본다. 테이블 몇 개만 크다면 기능별 분할로 그 테이블만 다른 DB로 옮긴다. 그래도 한 테이블의 쓰기가 한 대를 넘을 때가 ID 샤딩을 고민할 때다. 그 전에 [Instagram](/posts/rw-instagram-sharding-ids)과 [Slack](/posts/rw-slack-vitess)처럼 같은 문제를 다르게 푼 사례를 함께 놓고 비교해 보면 좋다.

샤딩한 뒤라면 장애의 첫 질문이 달라진다. 한 사용자만 데이터가 안 보인다면 그 사용자의 샤드가 어디로 매핑돼 있는지, 앱 프로세스가 캐시한 조회 구조가 최신인지부터 본다. Pinterest처럼 앱이 맵을 캐시하는 구조에서는 샤드를 옮긴 직후 옛 맵을 든 프로세스가 옛 서버로 쓰는 일이 생길 수 있다. mysql_utils의 이동 스크립트가 마무리 단계에서 옛 마스터를 읽기 전용으로 바꾸고 "옛 마스터에 쓰기가 더 없는지" 확인하는 건 이 위험을 막는 순서로 읽힌다.

특정 샤드만 느리다면 그 샤드에 큰 사용자가 몰렸는지 본다. 관련 데이터를 사용자와 같은 샤드에 두는 규칙은 큰 사용자 하나를 그대로 샤드 하나의 부담으로 만든다. 샤드별 행 수와 쿼리 수를 따로 기록해 두지 않으면 이 질문에 답할 수 없다.

보고서나 통계 쿼리가 운영 DB를 느리게 한다면, 모든 샤드에 같은 쿼리를 돌리는 대신 백업이나 복제본에서 데이터를 뽑아 분석 저장소로 옮기는 길을 먼저 본다. mysql_utils의 `mysql_backup_csv.py`가 S3에 Hive 같은 시스템이 읽을 수 있는 CSV로 백업을 남기는 것도 같은 방향이다.

## 면접에서 나올 만한 질문

### Pinterest는 왜 Cassandra 같은 클러스터형 저장소 대신 MySQL 샤딩을 골랐나요?

2012년 발표 기준으로는 클러스터 관리 알고리즘 자체를 큰 단일 장애점으로 봤기 때문이다. 같은 복잡한 코드가 모든 노드에서 돌아 재배치가 깨지거나 데이터가 모든 노드에서 함께 망가질 수 있고, 당시 기술이 젊고 아는 엔지니어도 적었다. MySQL은 성숙하고 도구와 지원이 많았고, 샤딩은 노드끼리 서로 몰라 한 노드의 문제가 번지지 않는다. 대신 조인, 트랜잭션, 데이터 이동의 부담을 애플리케이션과 운영 도구가 진다.

### ID에 샤드 번호를 넣으면 무엇이 좋나요?

어디 있는지 묻는 조회 없이 ID만으로 위치를 안다. 샤드 ID로 서버와 DB를, 타입으로 테이블을, 로컬 ID로 행을 정한다. 로컬 ID는 각 샤드의 auto-increment로 매기니 별도 ID 발급 서버가 필요 없다. 대신 ID에 시간이 들어 있지 않아 ID 순서가 생성 순서를 뜻하지 않고, 정렬이 필요하면 매핑 테이블의 타임스탬프 같은 다른 값을 써야 한다.

### 샤드 ID가 ID에 박혀 있으면 서버를 늘릴 때 ID를 바꿔야 하지 않나요?

바꾸지 않는다. ID에 들어 있는 건 서버가 아니라 논리 샤드 번호이고, 샤드를 서버로 잇는 건 별도의 조회 구조다. 처음부터 샤드 4,096개를 서버 8대에 나눠 두고, 서버를 늘릴 때는 서버를 복제한 뒤 조회 구조의 범위만 반으로 나눈다. 데이터는 샤드째 움직이고 행 단위로 다시 해시되지 않는다.

### 조인이 없으면 프로필 페이지는 어떻게 그리나요?

매핑 테이블을 따라 기본 키 조회를 여러 번 한다. 사용자 본문, user_has_boards, 보드 본문, board_has_pins, 핀 본문 순서이고, 같은 단계의 ID는 IN으로 묶는다. 보드와 핀을 사용자와 같은 샤드에 두려 하니 대개 같은 DB 안에서 끝나고, 슬라이드는 이 호출 대부분이 캐시 적중이라고 쓴다. 쿼리 수는 늘지만 하나하나가 가볍고 캐시에 담기 쉽다.

### 객체 본문을 blob 한 칸에 넣으면 무엇을 얻고 무엇을 잃나요?

스키마 변경을 거의 없앤다. 필드를 추가해도 ALTER TABLE을 모든 샤드에 돌릴 필요가 없다. 잃는 건 DB가 본문 안의 값을 모른다는 것이다. 본문 필드로 찾으려면 그 필드를 키로 한 매핑 테이블을 새로 만들어야 하고, 슬라이드가 "index = new table"이라고 쓴 이유가 이것이다.

### 2012년의 멀티 마스터 복제는 나중에 어떻게 바뀌었나요?

마스터 하나와 슬레이브 하나나 둘로 단순해졌다. 2015년에 공개된 mysql_utils README는 쓰기 가능한 인스턴스를 여럿 두는 구조가 오류가 나기 쉬워 바꿨다고 쓴다. 쓰는 곳이 하나면 양쪽에서 같은 행을 고치는 충돌을 걱정하지 않아도 된다. 마스터 교체는 페일오버 스크립트가 복제 구조와 ZooKeeper의 서비스 디스커버리를 함께 고치는 식으로 처리했다.

### 샤드를 다른 서버로 옮기는 동안 쓰기는 어떻게 하나요?

복제로 따라오게 하고, 마지막에 잠깐만 멈춘다. mysql_utils의 2017년 스크립트는 옮길 샤드를 새 복제 세트에 가져온 뒤 원래 마스터에서 복제를 받게 하고, 마무리할 때 양쪽을 읽기 전용으로 바꿔 복제가 다 따라잡기를 기다린 다음 샤드 맵을 고친다. 옛 DB는 바로 지우지 않고 이름만 바꿔 두었다가 나중에 정리한다. 멈추는 시간은 마지막 따라잡기 동안이다.

### 우리 서비스가 DB 한 대로 아직 버티는데, 미리 이렇게 샤딩해 둘까요?

대개 아니다. Pinterest도 DB 한 대에서 비정규화, 캐시, 읽기 슬레이브, 기능별 분할을 거친 뒤에 ID 샤딩으로 갔고, 발표는 사이트 설계를 굳힌 다음 그래도 크면 샤딩하라고 한다. 미리 샤딩하면 조인, 트랜잭션, 유일 제약을 처음부터 포기하고 샤드 맵과 이동 도구까지 만들어야 한다. 지금은 조인 의존을 줄이고, 행마다 주인 사용자를 분명히 하고, 테이블 크기와 쿼리 횟수를 기록해 두는 정도가 맞다.
