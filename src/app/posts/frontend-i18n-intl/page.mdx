장바구니 아이콘 옆에 개수를 띄우는 코드를 영어 사이트에 그대로 옮겼다.

```js
const n = 1;
console.log(n + " items");
```

```text
1 items
```

한국어로는 "상품 1개"라서 문제가 없었다. 영어로 옮기자 바로 "1 items"가 찍혔다. 가격도 비슷했다. `price.toLocaleString() + "원"`을 `"$" + price`로 바꿨더니 독일 사용자에게 15000이 15,000.00이 아니라 그냥 15000으로 보였고, 독일식이라면 쉼표와 점이 반대여야 했다. 날짜는 더 미묘했다. 서버에서 그린 "10월 23일"이 브라우저에서 "10월 24일"로 바뀌며 하이드레이션 경고가 떴다.

문자열을 이어 붙여 숫자와 문장을 만드는 순간 언어 규칙을 코드에 하드코딩하게 된다. 이 글은 그 규칙을 브라우저와 Node에 내장된 `Intl` API에 맡기는 법을 보고, Next.js App Router에서 `/ko`·`/en` 주소로 언어를 나누는 법까지 따라간다. 코드 출력은 Node 22(ICU 77)에서 돌렸다. 브라우저도 같은 ICU·CLDR 데이터를 쓰지만 버전에 따라 기호나 공백 하나가 다를 수 있다. Next.js 부분은 저장소에 설치된 Next.js 16.4 문서를 기준으로 했다.

## 국제화와 현지화는 다른 일이다

국제화(internationalization, 줄여서 i18n)는 코드가 여러 언어와 지역을 받아들일 수 있게 구조를 만드는 일이다. 번역문을 코드 밖으로 빼고, 숫자·날짜를 로케일에 맞춰 찍게 하고, 주소에 언어를 담는다. 현지화(localization, l10n)는 그 구조 위에 실제 한 시장의 번역과 통화, 법적 문구를 채우는 일이다.

로케일(locale)은 언어와 지역 설정을 묶은 이름이다. `ko-KR`은 한국에서 쓰는 한국어, `en-US`는 미국 영어, `en-GB`는 영국 영어다. 앞은 ISO 639 언어 코드, 뒤는 ISO 3166 지역 코드다. 같은 영어라도 지역이 바뀌면 날짜 순서와 통화가 바뀐다.

새 나라에 서비스를 열 때 통화 자릿수, 세금, 주소 모양 같은 시장 설정을 어떻게 코드 밖으로 빼는지는 [새 나라에 서비스를 열 때 글](/posts/global-rollout-localization)에서 다뤘다. 이 글은 그중 화면 쪽, 즉 브라우저와 Next.js에서 할 일만 본다.

## 숫자와 통화는 Intl.NumberFormat에 맡긴다

같은 숫자를 여섯 로케일로 찍어 봤다.

```js
const n = 1234567.891;
for (const l of ["ko-KR", "en-US", "de-DE", "fr-FR", "hi-IN", "ar-EG"]) {
  console.log(l.padEnd(6), new Intl.NumberFormat(l).format(n));
}
```

```text
ko-KR  1,234,567.891
en-US  1,234,567.891
de-DE  1.234.567,891
fr-FR  1 234 567,891
hi-IN  12,34,567.891
ar-EG  ١٬٢٣٤٬٥٦٧٫٨٩١
```

독일은 쉼표와 점이 반대다. 프랑스는 천 단위를 좁은 공백으로 나눈다. 인도는 처음 세 자리 뒤부터 두 자리씩 끊는다. 이집트 아랍어는 숫자 모양 자체가 다르다. 이걸 손으로 맞추려면 로케일마다 분기를 써야 한다.

통화는 `style: "currency"`와 ISO 4217 통화 코드를 함께 준다. 통화마다 기본 소수 자릿수가 달라서 엔화는 소수점이 없다.

```js
new Intl.NumberFormat("ko-KR", { style: "currency", currency: "KRW" }).format(15000);
new Intl.NumberFormat("en-US", { style: "currency", currency: "USD" }).format(15000);
new Intl.NumberFormat("de-DE", { style: "currency", currency: "EUR" }).format(15000);
new Intl.NumberFormat("ja-JP", { style: "currency", currency: "JPY" }).format(15000.6);
```

```text
₩15,000
$15,000.00
15.000,00 €
￥15,001
```

엔화는 15000.6이 15,001로 반올림됐다. 화면 표시만 반올림된 것이고, 결제 금액은 서버에서 통화별 최소 단위 정수로 다뤄야 한다. 로케일과 통화는 따로 움직인다는 점도 놓치기 쉽다. 한국 사용자가 달러 상품을 볼 수도 있으니 `ko-KR` 로케일에 `USD`를 줄 수 있어야 한다.

이 밖에 `notation: "compact"`는 한국어로 `1235만`, 영어로 `12M`을 만들고, `style: "percent"`는 0.256을 `26%`로, `style: "unit"`은 `512 kB`처럼 단위를 붙인다. 숫자 조각마다 다른 스타일을 입히고 싶다면 `formatToParts`가 `integer`, `group`, `decimal`, `currency` 같은 조각 배열을 준다. 통화 기호만 작게 그리는 디자인에 쓴다.

포매터는 만들어 두고 다시 쓴다. 10만 번 포맷을 세 방법으로 쟀다.

```text
매번 new        2844ms
재사용            33ms
toLocaleString  2556ms
```

`Intl.NumberFormat`을 만들 때 로케일 데이터를 찾고 옵션을 해석하는 비용이 크다. 긴 표나 가상 스크롤 목록에서 셀마다 `toLocaleString`을 부르면 이 비용을 매번 낸다. 로케일과 옵션별로 포매터를 모듈 수준이나 `useMemo`에 두고 `format`만 부른다.

## 날짜는 시간대까지 정해야 같은 날이 된다

같은 순간을 네 로케일과 시간대로 찍었다.

```js
const d = new Date("2026-10-23T15:30:00Z");
const opts = { dateStyle: "full", timeStyle: "short" };
new Intl.DateTimeFormat("ko-KR", { ...opts, timeZone: "Asia/Seoul" }).format(d);
new Intl.DateTimeFormat("en-US", { ...opts, timeZone: "America/New_York" }).format(d);
new Intl.DateTimeFormat("en-GB", { ...opts, timeZone: "Europe/London" }).format(d);
new Intl.DateTimeFormat("de-DE", { ...opts, timeZone: "Europe/Berlin" }).format(d);
```

```text
ko-KR 2026년 10월 24일 토요일 오전 12:30
en-US Friday, October 23, 2026 at 11:30 AM
en-GB Friday, 23 October 2026 at 16:30
de-DE Freitag, 23. Oktober 2026 um 17:30
```

서울은 이미 토요일이다. 로케일은 "어떤 모양으로 쓰나"를, 시간대는 "몇 시로 보이나"를 정한다. 둘은 독립이다. 시간대를 안 주면 실행 환경의 시간대를 쓰는데, 서버와 브라우저의 시간대가 다르면 같은 코드가 다른 날짜를 찍는다. 이 문제는 아래 하이드레이션 절에서 다시 본다.

상대 시간은 `Intl.RelativeTimeFormat`이 만든다. `numeric: "auto"`를 주면 "1일 전" 대신 "어제"처럼 자연스러운 말을 고른다.

```js
const rtf = new Intl.RelativeTimeFormat("ko", { numeric: "auto" });
console.log(rtf.format(-1, "day"), rtf.format(1, "day"), rtf.format(-3, "hour"), rtf.format(2, "week"));
```

```text
어제 내일 3시간 전 2주 후
```

단위를 고르는 일(지금부터 90분 전이면 "1시간 전"인지 "2시간 전"인지)은 이 API가 해 주지 않는다. 차이를 계산해 단위를 고르는 코드는 직접 쓴다. 목록을 "사과, 배 및 감", "apple, pear, and persimmon"처럼 잇는 `Intl.ListFormat`, 언어 코드를 "영어(미국)"처럼 그 나라 말 이름으로 바꾸는 `Intl.DisplayNames`도 언어 선택 메뉴를 만들 때 쓸모 있다.

## "1 items"는 복수 규칙의 문제다

`n + " items"`의 문제는 영어에 단수와 복수가 있다는 것뿐이 아니다. 언어마다 개수에 따라 단어가 바뀌는 규칙의 수가 다르다. `Intl.PluralRules`로 확인했다.

```js
for (const l of ["en", "ko", "ru", "ar", "fr"]) {
  const pr = new Intl.PluralRules(l);
  console.log(l, [0, 1, 2, 3, 5, 11, 21, 100, 1.5].map((x) => x + ":" + pr.select(x)).join(" "));
}
```

```text
en 0:other 1:one 2:other 3:other 5:other 11:other 21:other 100:other 1.5:other
ko 0:other 1:other 2:other 3:other 5:other 11:other 21:other 100:other 1.5:other
ru 0:many 1:one 2:few 3:few 5:many 11:many 21:one 100:many 1.5:other
ar 0:zero 1:one 2:two 3:few 5:few 11:many 21:many 100:other 1.5:other
fr 0:one 1:one 2:other 3:other 5:other 11:other 21:other 100:other 1.5:one
```

한국어는 범주가 `other` 하나뿐이다. 영어는 `one`과 `other` 둘이다. 러시아어는 21이 1과 같은 `one`이고 11은 `many`다. 아랍어는 여섯 범주를 다 쓴다. 프랑스어는 0과 1.5도 단수다. `if (n === 1)`로 단수와 복수를 가르는 코드는 영어에서만 맞는다. 분기를 늘려 언어마다 `switch`를 쓰는 대신 규칙을 데이터로 빼는 이유이기도 하다. 분기와 조회 테이블 중에 고르는 기준은 [반복문과 분기 글](/posts/js-loops-control-flow)에 있다. 순서를 나타내는 `{ type: "ordinal" }`을 주면 영어에서 2는 `two`(2nd), 13은 `other`(13th), 23은 `few`(23rd)가 나온다.

그래서 번역문은 범주별로 문장을 따로 둔다. 범주 이름은 고정이고(`zero`, `one`, `two`, `few`, `many`, `other`), 로케일마다 쓰는 범주만 다르다. `new Intl.PluralRules("ar").resolvedOptions().pluralCategories`로 그 로케일이 쓰는 범주를 확인할 수 있다. 번역가에게 넘길 키를 만들 때 이 목록으로 빠진 범주를 검사한다.

## ICU 메시지 형식으로 문장을 통째로 번역한다

범주별 문장을 키 여러 개로 흩어 두면 번역가가 문맥을 놓친다. 업계에서 많이 쓰는 방식은 ICU 메시지 형식이다. 한 문장 안에 변수와 복수·선택 분기를 함께 적는다. FormatJS의 `intl-messageformat` 10.7로 돌려 봤다. next-intl, react-intl도 같은 문법을 쓴다.

```js
import { IntlMessageFormat } from "intl-messageformat";

const en = new IntlMessageFormat(
  "{count, plural, =0 {No items} one {# item} other {# items}} in your cart", "en");
const ko = new IntlMessageFormat(
  "장바구니에 {count, plural, =0 {상품이 없습니다} other {상품 #개}}", "ko");

for (const c of [0, 1, 2, 1000]) console.log(en.format({ count: c }), "|", ko.format({ count: c }));
```

```text
No items in your cart | 장바구니에 상품이 없습니다
1 item in your cart | 장바구니에 상품 1개
2 items in your cart | 장바구니에 상품 2개
1,000 items in your cart | 장바구니에 상품 1,000개
```

`#`은 그 자리의 숫자를 로케일 규칙으로 찍는다. 1000이 `1,000`이 됐다. `=0`은 범주가 아니라 정확히 0일 때를 따로 잡는다. `select`는 성별이나 역할처럼 문자열 값으로 분기하고, `selectordinal`은 서수에 쓴다. 영어 서수 메시지에 1, 2, 3, 4, 11, 22를 넣으면 `1st 2nd 3rd 4th 11th 22nd`가 나왔다.

문장을 조각으로 나눠 이어 붙이지 않는다. "님이" + 동작 + "했습니다"처럼 쪼개면 어순이 다른 언어에서 번역이 불가능해진다. 일본어와 영어는 동사 위치가 다르고, 독일어는 분리 동사가 문장 끝으로 간다. 문장 하나를 메시지 하나로 두고 변수 자리만 비운다.

메시지 문법은 생성할 때 검사된다. `other`를 빼먹으면 만들자마자 `SyntaxError: MISSING_OTHER_CLAUSE`가 났다. 번역 파일을 CI에서 한 번씩 파싱해 보면 배포 전에 깨진 메시지를 잡을 수 있다.

## 사용자 언어는 Accept-Language가 알려 준다

브라우저는 요청마다 사용자가 설정한 언어 목록을 `Accept-Language` 헤더로 보낸다. 한국어를 먼저, 영어를 다음으로 둔 크롬의 헤더는 대략 이런 모양이다. 조각을 눌러 보면 각 부분이 무엇인지 나온다.

    { key: "en", display: "en;q=0.7", title: "영어(지역 무관)", description: "en-GB만 지원한다면 이 줄 덕분에 영어로 맞출 수 있다." },
  ]}
/>

이 목록과 우리가 지원하는 로케일을 맞춰 하나를 고르는 일을 로케일 협상(locale negotiation)이라고 한다. q가 높은 것부터, 정확히 같은 로케일을 먼저, 없으면 언어만 같은 로케일을 고른다. `q=0`은 "이 언어는 원하지 않는다"는 뜻이니 빼야 하고, `*`는 아무거나 된다는 뜻이다. Next.js 문서는 `negotiator`와 `@formatjs/intl-localematcher` 라이브러리 조합을 권한다. 아래에서 그 규칙을 직접 짜 볼 수 있다.

<CodePlayground
  caption="Accept-Language로 지원 로케일 하나 고르기"
  functionName="pickLocale"
  initialCode={`function pickLocale(header, supported, fallback) {
  // header: "ko-KR,ko;q=0.9,en;q=0.7"
  // supported: ["en", "ko", "ja"]
  // 1) 쉼표로 나누고 ;q= 값을 읽는다 (없으면 1)
  // 2) q가 0인 것은 버리고, q가 높은 순(같으면 원래 순서)으로 정렬
  // 3) 대소문자 무시하고 정확히 같은 것 → 없으면 언어 부분만 같은 것
  // 4) "*"를 만나거나 끝까지 없으면 fallback
  return fallback;
}`}
  solution={`function pickLocale(header, supported, fallback) {
  if (!header) return fallback;
  const wanted = header
    .split(",")
    .map((part, i) => {
      const [tag, ...params] = part.trim().split(";");
      const qParam = params.find((p) => p.trim().startsWith("q="));
      const q = qParam ? Number(qParam.trim().slice(2)) : 1;
      return { tag: tag.trim().toLowerCase(), q: Number.isNaN(q) ? 0 : q, i };
    })
    .filter((w) => w.tag && w.q > 0)
    .sort((a, b) => b.q - a.q || a.i - b.i);

  for (const { tag } of wanted) {
    if (tag === "*") return fallback;
    const exact = supported.find((s) => s.toLowerCase() === tag);
    if (exact) return exact;
    const base = tag.split("-")[0];
    const loose = supported.find((s) => s.toLowerCase().split("-")[0] === base);
    if (loose) return loose;
  }
  return fallback;
}`}

Next.js 16 문서의 예제를 줄이면 이렇다. 로케일이 이미 붙은 주소는 그냥 통과시키고, 없으면 붙여서 리다이렉트한다. matcher는 `_next` 같은 내부 경로를 빼야 한다. 정적 파일까지 리다이렉트되면 이미지와 폰트가 깨진다. matcher를 잘못 짜서 생기는 무한 리다이렉트는 [Route Handler와 Proxy 글](/posts/nextjs-route-handlers-proxy)에서 다뤘다.

```ts
// proxy.ts
import { NextResponse, type NextRequest } from "next/server";

const locales = ["ko", "en", "ja"];

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl;
  const has = locales.some((l) => pathname === `/${l}` || pathname.startsWith(`/${l}/`));
  if (has) return;

  const cookie = request.cookies.get("locale")?.value;
  const lang = cookie && locales.includes(cookie)
    ? cookie
    : pickLocale(request.headers.get("accept-language"), locales, "ko");

  request.nextUrl.pathname = `/${lang}${pathname}`;
  return NextResponse.redirect(request.nextUrl);
}

export const config = {
  matcher: ["/((?!_next|api|.*\\..*).*)"],
};
```

검색 엔진 크롤러는 `Accept-Language` 없이 오는 경우가 많다. 그래서 로케일이 붙은 주소는 절대 다른 언어로 돌려보내지 않고, 루트처럼 로케일이 없는 주소에서만 협상한다. 그러면 크롤러도 `/en/...` 링크를 따라 모든 언어 버전을 본다.

### 검색 엔진에게 언어 버전을 알리는 법

주소를 나누는 세 가지 방법은 검색에서 차이가 난다. 나라별 도메인(ccTLD, `example.kr`)은 "이 사이트는 한국 사람용"이라는 가장 강한 지역 신호다. 대신 도메인마다 따로 사고 갱신해야 하고, 쌓인 링크와 평판이 도메인끼리 나뉜다. 하위 도메인(`ko.example.com`)은 서버나 CDN을 언어별로 따로 두기 쉽지만, 검색 엔진이 별개 사이트처럼 볼 여지가 있다. 경로(`example.com/ko/`)는 도메인 하나의 평판을 모든 언어가 나눠 쓰고 인증서도 하나다. 지역 신호는 약해서 hreflang에 기대야 한다. 나라마다 법인, 결제, 상품 구성이 완전히 다르면 ccTLD를, 그렇지 않으면 대개 경로를 고른다. 예전에는 Search Console에서 사이트의 대상 국가를 손으로 정할 수 있었지만 구글이 그 설정을 없앴다(2022년). 지금 쓸 수 있는 신호는 ccTLD, hreflang, 그리고 현지 주소·통화·전화번호 같은 페이지 내용이다.

언어와 지역은 따로다. 영어 하나로 미국과 영국에 다른 가격을 보여 준다면 `en-US`, `en-GB` 두 페이지에 hreflang을 따로 달고, 언어만 다르면 `ko`, `en`처럼 언어 코드만 쓴다. hreflang은 모든 버전이 서로를, 그리고 자기 자신을 가리켜야 인정되고, 어느 언어에도 맞지 않는 사람에게 보일 `x-default`를 하나 둔다. 각 버전의 canonical을 다른 언어 페이지로 걸면 hreflang과 부딪친다. 이 규칙과 흔한 실수는 [SPA의 SEO 글](/posts/seo-for-spa#언어마다-다른-페이지)에 모아 두었다. App Router에서는 `generateMetadata`에서 `alternates.languages`를 채우면 이 링크가 `head`에 나간다.

```ts
// app/[lang]/products/[id]/page.tsx
// 루트 layout에 metadataBase가 있어야 아래 상대 경로가 절대 주소로 바뀐다
export async function generateMetadata({ params }: Props): Promise<Metadata> {
  const { lang, id } = await params;
  return {
    alternates: {
      canonical: `/${lang}/products/${id}`,           // 자기 자신
      languages: {
        ko: `/ko/products/${id}`,
        en: `/en/products/${id}`,
        ja: `/ja/products/${id}`,
        "x-default": `/en/products/${id}`,            // 맞는 언어가 없을 때
      },
    },
  };
}
```

앞의 proxy가 로케일 없는 주소에서만 협상하는 것도 검색 때문이다. 구글봇은 대부분 미국 IP에서, `Accept-Language` 없이 크롤링한다. 로케일이 붙은 주소까지 IP나 헤더로 돌려보내면 구글봇은 영어 페이지로만 끌려가서 한국어와 일본어 버전을 색인하지 못한다. 그래서 언어를 바꾸라는 제안은 리다이렉트가 아니라 배너로 띄운다.

같은 URL 안에서 지역에 맞춰 바꾸는 것도 있다. 통화 표시나 배송 가능 여부를 IP로 고르는 개인화다. 본문이 같은 언어로 그대로라면 문제가 적지만, 구글봇은 미국 사용자가 보는 화면을 색인한다는 걸 기억해 둔다. 한국어 상품 설명이 IP에 따라 사라지는 수준이면 그건 개인화가 아니라 언어 버전이니 주소를 나눈다.

## 사전은 서버 컴포넌트에서 불러온다

번역문은 언어별 JSON 사전으로 둔다. 문서 예제는 사전을 동적 `import`로 불러오고, 파일에 `server-only`를 붙여 클라이언트에서 실수로 import하지 못하게 막는다.

```ts
// app/[lang]/dictionaries.ts
import "server-only";

const dictionaries = {
  ko: () => import("./dictionaries/ko.json").then((m) => m.default),
  en: () => import("./dictionaries/en.json").then((m) => m.default),
};

export type Locale = keyof typeof dictionaries;
export const hasLocale = (l: string): l is Locale => l in dictionaries;
export const getDictionary = (l: Locale) => dictionaries[l]();
```

```tsx
// app/[lang]/layout.tsx
import { notFound } from "next/navigation";
import { hasLocale } from "./dictionaries";

export function generateStaticParams() {
  return [{ lang: "ko" }, { lang: "en" }];
}

export default async function Layout({ children, params }: LayoutProps<"/[lang]">) {
  const { lang } = await params;
  if (!hasLocale(lang)) notFound();
  return (
    <html lang={lang} dir={lang === "ar" ? "rtl" : "ltr"}>
      <body>{children}</body>
    </html>
  );
}
```

`generateStaticParams`로 언어 목록을 주면 언어마다 페이지가 빌드 시점에 정적으로 만들어진다. 정적·동적 렌더링이 언제 갈리는지는 [정적·동적 렌더링 글](/posts/nextjs-static-dynamic-rendering)에 있다. `hasLocale`은 타입 좁히기와 404를 함께 해결한다. `/xx/products`처럼 없는 언어가 들어오면 런타임 에러 대신 404가 난다. 16.3부터는 `next/root-params`의 `lang()`으로 깊은 서버 컴포넌트에서도 `lang`을 props로 내려받지 않고 읽을 수 있다. 클라이언트 컴포넌트와 서버 액션, Route Handler에서는 쓸 수 없다.

번들 크기가 여기서 갈린다. 서버 컴포넌트에서 사전을 읽으면 결과 HTML만 내려가고 사전은 번들에 실리지 않는다. 클라이언트 컴포넌트가 번역문을 쓰려면 그 문구를 어딘가로 넘겨야 하는데, 사전 전체를 Provider로 넘기면 페이지마다 수천 개 문구가 RSC 페이로드에 실린다. 그래서 사전을 화면 단위 네임스페이스(`cart.json`, `checkout.json`)로 나누고, 클라이언트 컴포넌트에는 그 화면에 필요한 문구만 넘긴다. next-intl 같은 라이브러리도 클라이언트 Provider에 넘길 메시지를 고르는 기능을 둔다.

`html`의 `lang` 속성은 스크린리더가 발음을 고르고 브라우저가 번역을 제안하는 데 쓴다. 검색 엔진에 언어 버전끼리의 관계를 알리는 것은 `hreflang`이다. Next.js에서는 `generateMetadata`가 돌려주는 `alternates.languages`에 언어별 주소를 적으면 `link rel="alternate"` 태그가 만들어진다. 서로 가리켜야 인정되는 규칙과 `x-default`, canonical과 부딪치는 실수는 [SPA 검색 엔진 최적화 글](/posts/seo-for-spa)에서 다뤘다.

## 서버와 브라우저의 시간대가 다르면 하이드레이션이 깨진다

처음에 본 "10월 23일이 24일로 바뀌는" 증상을 재현했다. 같은 코드를 시간대만 바꿔 돌렸다. Vercel 같은 서버리스 환경의 시간대는 대개 UTC다.

```bash
# 서버(UTC)와 서울 브라우저를 흉내 낸다
TZ=UTC node -e 'console.log(new Date("2026-10-23T15:30:00Z").toLocaleString("ko-KR"))'
TZ=Asia/Seoul node -e 'console.log(new Date("2026-10-23T15:30:00Z").toLocaleString("ko-KR"))'
```

```text
2026. 10. 23. 오후 3:30:00
2026. 10. 24. 오전 12:30:00
```

서버가 23일로 그린 HTML을 서울의 브라우저가 24일로 다시 그리려 하니 React가 텍스트 불일치를 알린다. 로케일도 같은 함정이 있다. 로케일 인자 없이 `toLocaleString()`을 부르면 서버 Node는 기본값(이 컨테이너에서는 `en-US`)을, 브라우저는 사용자 설정 언어를 쓴다.

고치는 길은 세 가지다. 첫째, 로케일과 시간대를 둘 다 명시한다. 로케일은 주소의 `lang`에서, 시간대는 사용자 설정이나 서비스 기준 시간대(`Asia/Seoul`)에서 가져와 서버와 브라우저가 같은 값을 쓰게 한다. 가장 확실하다. 둘째, 사용자 기기의 시간대로 보여 줘야 하는 값이라면 서버에서는 ISO 문자열을 `time` 요소의 `dateTime`에 넣어 두고, 마운트 뒤에 클라이언트에서 포맷한다. 셋째, "3분 전"처럼 매초 바뀌는 값은 그 요소에만 `suppressHydrationWarning`을 붙인다. 한 단계 깊이까지만 경고를 끄는 탈출구라 남발하지 않는다. 불일치가 나는 다른 원인과 React가 어떻게 복구하는지는 [하이드레이션 글](/posts/hydration)에 있다.

서버 Node와 브라우저의 ICU 데이터 버전이 달라서 생기는 불일치도 있다. 같은 로케일이라도 약어나 공백 문자 하나가 버전에 따라 바뀐 적이 있다. 서버에서 그린 날짜를 클라이언트가 다시 포맷하지 않게 하면 이 위험도 사라진다.

## 오른쪽에서 왼쪽으로 쓰는 언어

아랍어와 히브리어는 오른쪽에서 왼쪽으로 쓴다(RTL). `html`에 `dir="rtl"`을 주면 텍스트 방향, 표의 열 순서, 플렉스 방향이 뒤집힌다. 문제는 CSS에 `margin-left`처럼 물리 방향을 적어 둔 곳이다. 이건 뒤집히지 않는다.

```css
/* 물리 방향: RTL에서도 왼쪽에 붙는다 */
.badge { margin-left: 8px; text-align: left; }

/* 논리 방향: 글이 시작하는 쪽 기준이라 RTL에서 자동으로 뒤집힌다 */
.badge { margin-inline-start: 8px; text-align: start; }

/* 방향을 뜻하는 아이콘만 뒤집는다 */
[dir="rtl"] .icon-arrow { transform: scaleX(-1); }
```

`margin-inline-start`, `padding-inline-end`, `inset-inline-start`, `border-start-start-radius` 같은 논리 속성은 최신 브라우저가 모두 지원한다. 처음부터 논리 속성으로 쓰면 RTL 지원이 거의 공짜다. 모든 아이콘을 뒤집으면 안 된다. 화살표, 뒤로 가기처럼 방향을 뜻하는 것만 뒤집고, 재생 버튼이나 체크 표시, 로고는 그대로 둔다. 사용자가 입력한 글의 방향을 모를 때는 요소에 `dir="auto"`를 준다. CSS 레이아웃 기초는 [Flexbox와 Grid 글](/posts/css-flexbox-grid)과 함께 보면 좋다.

어떤 언어가 RTL인지 `new Intl.Locale("ar").textInfo`로 물어볼 수 있다. Node 22(V8 12.4)에서는 `{ direction: 'rtl' }`이 나왔다. 다만 명세가 이 속성을 `getTextInfo()` 메서드로 바꾸는 중이라 엔진마다 이름이 다르고, 지원하지 않는 브라우저도 있다. 지원 언어가 정해져 있다면 RTL 언어 목록을 직접 두는 편이 안전하다.

## 번역 키를 관리하는 법

번역 키가 수천 개로 늘면 코드보다 키 관리가 더 어렵다. 실무에서 부딪치는 선택지를 정리한다.

키 이름은 문구가 아니라 자리를 나타낸다. `"Add to cart"`를 그대로 키로 쓰면 영어 문구를 고칠 때마다 모든 언어의 키가 바뀐다. `cart.addButton`처럼 화면과 역할로 짓는다. 같은 영어 단어라도 자리가 다르면 키를 나눈다. 영어 "Save"가 버튼에서는 "저장", 할인 배지에서는 "할인"으로 번역되기 때문이다.

빠진 번역은 기본 언어로 물러나게 하되 조용히 넘기지 않는다. 개발 환경에서는 키를 그대로 화면에 드러내고, 운영에서는 기본 언어로 보여 주며 로그를 남긴다. TypeScript를 쓰면 기본 언어 사전의 타입(`typeof import("./en.json")`)으로 키를 검사해 오타를 컴파일 시점에 잡는다. CI에서 언어별 사전의 키 집합을 비교하고, ICU 메시지를 한 번씩 파싱하면 배포 전에 대부분의 사고를 막는다.

문자열 길이도 바뀐다. 독일어는 영어보다 길어지는 경우가 많고, 한국어는 짧아지는 경우가 많다. 버튼에 고정 폭을 주면 번역 뒤에 글자가 잘린다. 디자인 검수 때 가장 긴 언어로 한 번 보고, 개발 중에는 문구를 일부러 늘려 보는 가짜 로케일(pseudo-localization)을 쓰는 팀도 있다.

번역 파일을 저장소에 둘지 번역 관리 서비스(TMS)에 둘지도 고른다. 언어가 두세 개이고 개발자가 번역하면 저장소의 JSON으로 충분하다. 번역가가 따로 있고 언어가 늘면 TMS에서 번역하고 빌드 때 받아 오는 쪽이 협업하기 편하다. 대신 빌드가 외부 서비스에 기대게 되니, 받아 온 파일을 커밋해 두거나 캐시한다.

## 다시 "1 items"로

`n + " items"`는 영어 복수 규칙을 코드에 박아 넣은 코드였다. 숫자·통화·날짜는 `Intl.NumberFormat`과 `Intl.DateTimeFormat`에 로케일과 통화, 시간대를 명시해 맡기고, 개수에 따라 바뀌는 문장은 ICU 메시지의 `plural`로 문장째 번역한다. 언어는 주소에 담아 `/ko`, `/en`으로 나누고, 로케일이 없는 주소만 proxy에서 쿠키와 `Accept-Language`로 협상해 돌려보낸다. 사전은 서버 컴포넌트에서 불러 번들에 싣지 않고, 서버와 브라우저가 같은 로케일·시간대를 쓰게 해서 하이드레이션 불일치를 막는다.

## 면접에서 나올 만한 질문

### 국제화(i18n)와 현지화(l10n)는 어떻게 다른가요?

국제화는 코드가 여러 언어와 지역을 받아들이도록 구조를 만드는 일이다. 번역문을 코드 밖으로 빼고, 숫자·날짜를 로케일 규칙으로 찍고, 주소에 언어를 담는다. 현지화는 그 구조 위에 특정 시장의 번역, 통화, 법적 문구를 채우는 일이다. 국제화가 되어 있어야 현지화를 코드 수정 없이 늘릴 수 있다.

### 숫자나 날짜를 문자열 연결로 만들면 왜 안 되나요?

천 단위 구분자, 소수점, 날짜 순서, 통화 기호 위치가 로케일마다 달라서 연결로 만들면 한 로케일 규칙을 하드코딩하게 된다. 독일어는 쉼표와 점이 반대이고, 인도는 두 자리씩 끊고, 엔화는 소수점이 없다. `Intl.NumberFormat`과 `Intl.DateTimeFormat`에 로케일과 통화, 시간대를 넘기면 브라우저와 Node에 내장된 CLDR 데이터로 맞게 찍는다. 포매터는 만드는 비용이 커서 만들어 두고 재사용한다.

### 복수형을 if (n === 1)로 처리하면 어떤 문제가 있나요?

영어에서만 맞는다. 한국어는 범주가 하나뿐이고, 러시아어는 21이 1과 같은 단수이고 11은 다른 범주이며, 아랍어는 zero부터 other까지 여섯 범주를 쓴다. `Intl.PluralRules`가 숫자를 범주로 바꿔 주고, 번역문은 ICU 메시지의 `plural` 구문으로 범주별 문장을 한 메시지 안에 둔다.

### 사용자의 언어는 어떻게 정하나요?

사용자가 직접 고른 값(쿠키)이 가장 먼저이고, 없으면 `Accept-Language` 헤더를 q 값 순으로 보며 지원 로케일과 협상한다. 정확히 같은 로케일이 없으면 `ko-KR`을 `ko`로 물러나 맞추고, `q=0`은 제외한다. IP 기반 추정은 여행자와 VPN 사용자에게 틀리기 쉬워 통화나 배송 국가 기본값 제안 정도에만 쓴다.

### Next.js App Router에서 다국어 라우팅은 어떻게 구성하나요?

App Router에는 Pages Router의 `i18n` 설정이 없어서 모든 라우트를 `app/[lang]` 아래 두고 proxy에서 로케일 없는 주소만 협상해 `/ko/...`로 리다이렉트한다. 레이아웃에서 `hasLocale`로 검사해 없는 언어는 `notFound()`로 404를 내고, `generateStaticParams`로 언어별 정적 페이지를 만든다. 사전은 `server-only` 파일에서 동적 import로 불러 서버 컴포넌트에서만 쓴다. 로케일이 붙은 주소는 다시 리다이렉트하지 않아야 크롤러가 모든 언어 버전을 본다.

### 번역 사전이 커지면 번들 크기는 어떻게 관리하나요?

서버 컴포넌트에서 사전을 읽으면 결과 HTML만 내려가 번들에 실리지 않는다. 문제는 클라이언트 컴포넌트에 넘기는 문구라서, 사전을 화면 단위 네임스페이스로 나누고 그 화면에 필요한 문구만 props나 Provider로 넘긴다. 사전 전체를 클라이언트 Provider에 넣으면 페이지마다 수천 개 문구가 RSC 페이로드에 실린다.

### 날짜 때문에 하이드레이션 불일치가 나는 이유와 해결법은요?

서버(대개 UTC)와 브라우저(예: 서울)의 시간대나 기본 로케일이 달라 같은 코드가 다른 문자열을 만들기 때문이다. 같은 순간이 UTC로는 23일, 서울로는 24일이다. 로케일과 시간대를 명시해 양쪽이 같은 값을 쓰게 하는 것이 가장 확실하고, 사용자 기기 시간대가 꼭 필요하면 마운트 뒤 클라이언트에서 포맷한다. 계속 바뀌는 상대 시간에만 `suppressHydrationWarning`을 쓴다.

### RTL 언어를 지원할 때 무엇을 바꿔야 하나요?

`html`에 `dir="rtl"`을 주고, CSS의 `margin-left` 같은 물리 방향을 `margin-inline-start` 같은 논리 속성으로 바꾼다. 논리 속성은 글이 시작하는 쪽 기준이라 방향이 바뀌면 자동으로 뒤집힌다. 화살표처럼 방향을 뜻하는 아이콘만 뒤집고, 입력 글처럼 방향을 모르는 텍스트에는 `dir="auto"`를 준다.
