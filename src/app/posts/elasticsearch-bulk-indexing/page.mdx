상품 1천만 건의 매핑을 바꿔 새 인덱스로 다시 넣는 작업이 있었다. 배치 프로그램은 DB에서 상품을 한 건씩 읽어 `PUT /products-v2/_doc/{id}`로 넣었고, 끝나는 데 6시간이 걸렸다. 그동안 운영 검색의 p99 지연이 두 배가 됐다. 같은 노드에서 새 인덱스가 1초마다 refresh하며 세그먼트를 만들고, 레플리카까지 같은 일을 따라 하면서 CPU와 디스크를 나눠 먹었기 때문이다. 중간에 몇 번 429가 났는데 배치는 실패한 건을 로그에만 남기고 지나갔다. 다 끝나고 세어 보니 수천 건이 빠져 있었다.

이 글은 이런 쓰기 작업을 제대로 하는 방법을 따라간다. 문서 하나를 쓰고 읽는 API가 안에서 무엇을 하는지, 두 요청이 같은 문서를 고칠 때 덮어쓰기를 막는 법, `_bulk`의 크기와 동시성, 부분 실패, 대량 적재 동안 꺼 둘 설정과 되돌리는 순서, 그리고 조건에 맞는 문서를 한꺼번에 고치는 `_update_by_query`까지 본다. refresh, translog, 세그먼트가 무엇인지는 [역색인 글](/posts/elasticsearch-inverted-index)에서 다뤘으니 여기서는 쓰기 성능과 정확성에 어떻게 영향을 주는지에 집중한다. API는 Elasticsearch 8.x~9.x 공식 문서 기준이다. 응답은 공식 문서에 나오는 형식에서 필요한 필드만 남겨 보인다.

## 문서 하나를 쓰고 읽는 네 가지 API

가장 기본은 문서 API 넷이다. ID를 정해서 넣거나 바꾸는 `PUT`, ID를 Elasticsearch에 맡기는 `POST`, 읽는 `GET`, 지우는 `DELETE`.

```http
PUT /products/_doc/1001
{ "name": "무선 이어폰", "price": 89000, "stock": 12 }

POST /products/_doc
{ "name": "충전 케이블", "price": 9000, "stock": 300 }

PUT /products/_create/1001
{ "name": "무선 이어폰", "price": 89000, "stock": 12 }

GET /products/_doc/1001

DELETE /products/_doc/1001
```

같은 `PUT /_doc/1001`을 두 번 보내면 두 번째는 문서를 통째로 바꾸고 `result`가 `updated`로 온다. 이미 있으면 실패해야 하는 경우(중복 생성 방지)는 `_create`를 쓴다. 문서가 있으면 409 `version_conflict_engine_exception`이 온다.

ID를 맡기는 `POST`는 대량 적재에서 조금 더 빠르다. ID를 정해 주면 Elasticsearch는 같은 ID의 문서가 이미 있는지 샤드에서 찾아봐야 하는데, 자동 ID는 새 값이 보장되니 그 확인을 건너뛸 수 있다. 다만 원본 DB의 기본 키를 ID로 쓰지 않으면 같은 데이터를 두 번 넣었을 때 문서가 두 벌이 된다. 재시도가 있는 파이프라인이라면 DB 키를 ID로 쓰는 쪽이 안전하다. 속도와 멱등성 중에 고르는 문제다.

`GET`은 검색과 다르다. 검색은 refresh가 끝나 세그먼트에 들어간 문서만 보지만, ID로 하는 `GET`은 기본값(`realtime=true`)에서 아직 refresh되지 않은 최신 버전도 읽는다. 그래서 "방금 넣은 문서가 GET으로는 보이는데 검색에는 안 나온다"는 정상이다.

`DELETE`도 디스크에서 바로 지우지 않는다. 세그먼트는 고치지 않는 파일이라, 문서에 삭제 표시만 하고 검색에서 빼 준다. 실제 공간은 나중에 세그먼트가 합쳐질 때 돌아온다. 이 이야기는 글 뒤쪽 병합에서 다시 나온다.

## 부분 업데이트도 문서 전체를 다시 쓴다

재고 숫자 하나만 바꾸고 싶을 때는 `_update`를 쓴다.

```http
POST /products/_update/1001
{ "doc": { "stock": 11 } }

POST /products/_update/1001
{
  "script": {
    "source": "ctx._source.stock -= params.n",
    "params": { "n": 1 }
  }
}
```

요청은 필드 하나지만 안에서 일어나는 일은 크다. Elasticsearch는 저장된 `_source`(원본 JSON)를 읽고, 바뀐 필드를 합친 새 문서를 만들어, 옛 문서에 삭제 표시를 하고 새 문서를 처음부터 다시 색인한다. 역색인과 doc_values를 필드 하나만 고치는 방법이 없기 때문이다. 그래서 문서가 크고 필드가 많을수록 "숫자 하나 바꾸기"도 비싸다. 조회수처럼 초당 수백 번 바뀌는 값을 문서마다 `_update`로 올리면 삭제 표시된 문서가 쌓이고 refresh·병합 부담이 커진다. 이런 값은 따로 모아 몇 분에 한 번 묶어서 반영하거나, 검색에 꼭 필요하지 않으면 다른 저장소에 둔다.

`doc`으로 보낸 값이 지금 값과 같으면 `result`가 `noop`으로 오고 다시 색인하지 않는다(`detect_noop` 기본값 `true`). 변경이 없는 동기화 작업을 반복할 때 이 동작이 비용을 많이 줄인다. 반면 스크립트 업데이트는 결과가 같아도 다시 쓰기 때문에, 바뀔 게 없으면 스크립트 안에서 `ctx.op = 'noop'`으로 직접 건너뛰게 한다.

`_update`는 "읽고, 합치고, 쓰기"라서 그 사이에 다른 요청이 같은 문서를 바꾸면 충돌이 난다. 이때 409를 받는데, `retry_on_conflict=3`처럼 주면 Elasticsearch가 최신 문서를 다시 읽어 몇 번 더 시도한다. 재고를 1씩 빼는 스크립트처럼 "최신 값에 상대적으로 적용"하는 변경에는 재시도가 맞다. 하지만 사용자가 화면에서 고친 내용 전체를 덮어쓰는 변경이라면 재시도로 남의 변경을 덮어쓰게 된다. 이건 다음 절의 방법으로 막는다.

## 덮어쓰기를 막는 번호표: _seq_no와 _primary_term

관리자 둘이 같은 상품 화면을 열었다. A는 가격을, B는 설명을 고쳤다. 둘 다 "읽은 문서 전체"를 `PUT`으로 저장하면 나중에 저장한 쪽이 앞의 변경을 지운다. [낙관적 잠금](/posts/optimistic-locking) 글에서 본 문제가 검색 엔진에도 그대로 있다.

Elasticsearch는 문서에 쓸 때마다 두 숫자를 매긴다. `_seq_no`는 샤드 안에서 연산마다 하나씩 늘어나는 번호이고, `_primary_term`은 프라이머리 샤드가 바뀔 때(노드 장애로 레플리카가 승격될 때) 늘어나는 번호다. 둘을 함께 보면 "내가 읽은 그 버전"을 정확히 가리킬 수 있다. `GET` 응답에 둘이 같이 온다.

```json
{
  "_index": "products",
  "_id": "1001",
  "_version": 3,
  "_seq_no": 41,
  "_primary_term": 1,
  "found": true,
  "_source": { "name": "무선 이어폰", "price": 89000, "stock": 12 }
}
```

저장할 때 읽은 번호를 조건으로 붙인다.

```http
PUT /products/_doc/1001?if_seq_no=41&if_primary_term=1
{ "name": "무선 이어폰", "price": 79000, "stock": 12 }
```

그 사이 누가 먼저 썼다면 `_seq_no`가 이미 바뀌었으니 409가 온다. 아래 그림에서 다음을 눌러 두 관리자의 요청이 어떻게 갈리는지 보자.

`_version`이라는 숫자도 보이는데, 조건에 쓰는 건 `_seq_no`와 `_primary_term`이다. 예전에는 `?version=3`으로 조건을 걸었지만 6.7에서 이 두 숫자를 쓰는 방식이 들어왔고, 7.0부터는 내부 버전으로 조건을 거는 방법이 막혔다. 프라이머리가 바뀌는 순간 옛 프라이머리가 받은 연산과 새 프라이머리가 받은 연산이 같은 버전 번호를 가질 수 있어서다.

원본이 DB에 있고 DB의 버전(갱신 시각이나 버전 컬럼)이 진짜 순서라면 `version_type=external`이 더 맞다.

```http
PUT /products/_doc/1001?version=1729665000123&version_type=external
{ "name": "무선 이어폰", "price": 79000, "stock": 12 }
```

지금 저장된 버전보다 큰 값일 때만 받아들인다. CDC 이벤트가 순서가 뒤바뀌어 도착해도 늦게 온 옛 변경이 새 값을 덮어쓰지 못한다. DB 동기화 파이프라인에서 쓰기 좋은 방식이다.

## 여러 건을 한 요청에: _bulk

한 건씩 `PUT`을 보내면 문서마다 HTTP 왕복, 요청 파싱, 샤드 라우팅, translog 동기화가 일어난다. `_bulk`는 이걸 묶는다. 본문은 NDJSON(한 줄에 JSON 하나)이고, 동작 줄과 문서 줄이 짝을 이룬다. 마지막 줄도 줄바꿈으로 끝나야 한다.

```http
POST /_bulk
{ "index": { "_index": "products-v2", "_id": "1001" } }
{ "name": "무선 이어폰", "price": 79000, "stock": 12 }
{ "create": { "_index": "products-v2", "_id": "1002" } }
{ "name": "충전 케이블", "price": 9000, "stock": 300 }
{ "update": { "_index": "products-v2", "_id": "1003" } }
{ "doc": { "stock": 0 } }
{ "delete": { "_index": "products-v2", "_id": "1004" } }
```

`delete`만 문서 줄이 없다. 각 줄은 `index`(넣거나 바꾸기), `create`(없을 때만), `update`(부분 갱신), `delete` 중 하나다.

여기서 가장 많이 놓치는 게 응답이다. `_bulk`는 일부 문서가 실패해도 HTTP 상태는 200이다. 실패는 본문 안에 있다. 형식은 이렇다.

```json
{
  "took": 30,
  "errors": true,
  "items": [
    { "index":  { "_id": "1001", "status": 201, "result": "created" } },
    { "create": { "_id": "1002", "status": 429,
                  "error": { "type": "es_rejected_execution_exception" } } },
    { "update": { "_id": "1003", "status": 404,
                  "error": { "type": "document_missing_exception" } } },
    { "delete": { "_id": "1004", "status": 404, "result": "not_found" } }
  ]
}
```

HTTP 상태만 보는 클라이언트는 이 요청을 성공으로 처리한다. 처음 장면에서 수천 건이 빠진 이유가 이것이다. 응답의 `errors`가 `true`면 `items`를 돌며 실패한 것을 골라야 하고, 실패의 종류에 따라 다르게 다뤄야 한다. 아래 그림에서 다음을 눌러 응답 하나를 훑으며 무엇을 다시 보낼지 정해 보자.

원칙은 간단하다. 429와 503처럼 "지금은 못 받는다"는 실패만 다시 보내고, 400대 데이터 오류는 몇 번을 보내도 실패하니 따로 쌓아 사람이 본다. 다시 보낼 때는 실패한 문서만 모아 새 `_bulk`로 보내고, 간격을 늘려 가며(지수 백오프) 시도 횟수에 상한을 둔다. 실패한 배치 전체를 다시 보내면 이미 성공한 문서까지 다시 쓰게 되고, 자동 ID라면 문서가 중복된다. 공식 클라이언트의 bulk 도우미(Java의 `BulkIngester`, Python의 `streaming_bulk` 등)는 이 재시도를 설정으로 제공하지만, 400대 실패를 어디에 남길지는 직접 정해야 한다.

## 한 요청에 얼마나, 동시에 몇 개나

`_bulk`가 크다고 무조건 빠르지 않다. 요청 하나는 받는 노드(코디네이터)의 메모리에 통째로 올라간 뒤 샤드별로 쪼개져 나간다. 너무 크면 힙을 압박하고, 기본 `http.max_content_length`인 100MB를 넘으면 413으로 거절된다. 너무 작으면 왕복 비용이 다시 커진다.

정답 숫자는 없고, 문서 크기와 매핑, 하드웨어에 따라 다르다. 공식 문서가 권하는 방법은 재 보는 것이다. 노드 하나, 샤드 하나에서 배치 크기를 100건에서 시작해 두 배씩 늘리며 처리량(초당 문서 수)을 보고, 더 이상 늘지 않는 지점에서 멈춘다. 그런 다음 동시에 보내는 요청 수를 하나씩 늘려 처리량이 더 오르지 않거나 429가 나기 시작하는 지점을 찾는다. 대체로 한 요청이 수 MB에서 수십 MB 사이일 때 처리량이 평평해지는 경우가 많다. 문서 크기가 제각각이면 "건수"가 아니라 "바이트"로 끊는 게 낫다. 1KB 상품과 2MB 상세 설명 문서가 섞이면 같은 1000건이라도 요청 크기가 천 배 차이 난다.

바이트 기준으로 배치를 끊어 보자. 문서 크기 배열과 한 배치의 최대 바이트가 주어질 때, 각 배치에 몇 건이 들어가는지 돌려준다. 한 문서가 혼자서 최대치를 넘으면 그 문서 하나만 배치로 보낸다(보내 보고 413이 나면 그건 데이터 문제로 따로 다룬다).

<CodePlayground

  // 각 배치의 문서 수 배열을 돌려준다

  const out = [];
  let cur = 0, n = 0;
  for (const s of sizes) {
    if (n > 0 && cur + s > maxBytes) {
      out.push(n);
      cur = 0;
      n = 0;
    }
    cur += s;
    n++;
  }
  if (n > 0) out.push(n);
  return out;
}`}

동시성은 노드 쪽 사정과 함께 본다. 각 노드에는 쓰기 전용 스레드 풀(`write`)과 대기열이 있고, 쓰기에 쓰이는 메모리에도 상한(indexing pressure, 기본 힙의 10%)이 있다. 둘 중 하나가 차면 노드는 거절하고 그 문서는 429가 된다. 429는 장애가 아니라 [백프레셔](/posts/backpressure) 신호다. "더 빨리 보내라"가 아니라 "늦춰라"라는 뜻이므로, 429 비율이 오르면 동시 요청 수를 줄이는 게 맞다. 대기열 크기를 키우는 설정 변경은 거절을 늦출 뿐 힙만 더 쓴다. 지금 거절이 얼마나 나는지는 이렇게 본다.

```http
GET _cat/thread_pool/write?v&h=node_name,active,queue,rejected
```

`rejected`는 노드가 켜진 뒤 누적값이라, 작업 전후의 차이를 본다.

## 대량 적재 동안 꺼 두는 것

1천만 건을 새 인덱스에 처음 채우는 동안에는 아무도 그 인덱스를 검색하지 않는다. 그런데 기본 설정은 여전히 1초마다 refresh하고, 레플리카도 같은 문서를 모두 다시 색인한다. 둘 다 이 시간에는 필요 없다.

```http
PUT /products-v2/_settings
{
  "index": {
    "refresh_interval": "-1",
    "number_of_replicas": 0
  }
}
```

refresh를 끄면 작은 세그먼트를 1초마다 만들고 합치는 일이 사라진다. 레플리카 0이면 문서마다 두 번 하던 색인이 한 번이 된다. 레플리카는 나중에 다 만든 세그먼트 파일을 그대로 복사해 만들어지므로 처음부터 함께 색인하는 것보다 훨씬 싸다. 앞 장면에서 운영 검색까지 느려진 이유도 새 인덱스의 refresh와 레플리카 색인이 같은 노드 자원을 먹었기 때문이었다.

<Callout kind="warning">
  레플리카 0인 동안 그 인덱스는 복사본이 없다. 노드 하나가 죽으면 그 노드의 샤드는 처음부터 다시 넣어야 한다. 원본 DB에서 언제든 다시 만들 수 있는 인덱스에만 이렇게 하고, 운영 트래픽을 받는 인덱스에는 쓰지 않는다. `refresh_interval`을 -1로 둔 채 잊으면 그 인덱스는 새 문서가 영원히 검색되지 않는다.
</Callout>

같은 맥락에서 `index.translog.durability`를 `async`로 바꾸는 방법도 있다. 기본(`request`)은 요청마다 translog를 디스크에 fsync하고 응답하는데, `async`는 `sync_interval`(기본 5초)마다 몰아서 한다. 빨라지지만 노드가 죽으면 마지막 몇 초 동안 받은 쓰기를 잃는다. 원본에서 다시 넣을 수 있는 적재 작업에서만 고려한다.

적재가 끝나면 거꾸로 되돌린다. 순서가 중요하다.

```http
PUT /products-v2/_settings
{ "index": { "refresh_interval": null } }

POST /products-v2/_refresh

PUT /products-v2/_settings
{ "index": { "number_of_replicas": 1 } }

GET _cluster/health/products-v2?wait_for_status=green&timeout=30m
```

먼저 `refresh_interval`을 `null`로 되돌려 기본값(1초)으로 돌아가게 하고, `_refresh`로 지금까지 넣은 문서를 검색에 보이게 한다. 그다음 레플리카를 올리고 green이 될 때까지 기다린다. green을 확인한 뒤에야 [매핑 글](/posts/elasticsearch-mapping)에서 본 것처럼 별칭을 새 인덱스로 돌린다. 레플리카 복사가 끝나기 전에 별칭을 돌리면 복사본 없이 운영 트래픽을 받게 된다.

이 과정을 적용하면 앞의 6시간 작업은 대략 이렇게 바뀐다. 한 건씩 보내던 것을 바이트 기준 `_bulk`로 묶고, 처리량이 평평해질 때까지 동시 요청을 늘리고, refresh와 레플리카를 끄고, 429만 백오프로 다시 보내고 400대는 따로 쌓는다. 운영 인덱스와 같은 노드를 쓴다면 동시 요청 수를 일부러 낮게 잡아 운영 검색의 몫을 남긴다. 얼마나 줄지는 데이터마다 다르니, 작은 샘플로 먼저 재 보고 전체 시간을 어림한다.

## 조건으로 한꺼번에 고치기: _update_by_query

새 필드를 추가하고 기존 문서에 기본값을 채우거나, 단종된 브랜드 상품을 모두 지워야 할 때가 있다. 문서를 하나씩 읽어 고치는 대신 질의로 고른 문서에 스크립트를 적용한다.

```http
POST /products/_update_by_query?conflicts=proceed&slices=auto&wait_for_completion=false
{
  "query": { "term": { "brand": "acme" } },
  "script": { "source": "ctx._source.discontinued = true" }
}

POST /products/_delete_by_query?slices=auto
{
  "query": { "range": { "updated_at": { "lt": "now-2y" } } }
}
```

이 API를 운영에서 쓰기 전에 알아야 할 동작이 있다. 시작하는 순간 인덱스의 스냅숏(그 시점의 문서와 버전)을 잡고, 그 목록을 차례로 처리한다. 처리하러 갔더니 그 사이 다른 요청이 문서를 바꿨다면 버전 충돌이다. 기본값에서는 충돌이 하나라도 나면 작업 전체가 멈춘다. 그리고 멈춰도 이미 고친 문서는 되돌리지 않는다. 절반만 바뀐 상태로 끝날 수 있다는 뜻이다.

쓰기가 계속 들어오는 인덱스라면 `conflicts=proceed`를 주고, 충돌한 문서는 건너뛰며 개수만 센다. 끝난 결과의 `version_conflicts`가 그 수다. 건너뛴 문서는 그 사이 누군가 새로 쓴 것이니, 그 새 쓰기가 조건을 반영했는지 확인하거나 작업을 한 번 더 돌린다. 스크립트가 멱등이면(몇 번 돌려도 결과가 같으면) 다시 돌리는 게 안전하다.

큰 인덱스에서는 `wait_for_completion=false`로 작업을 백그라운드 태스크로 돌리고, 돌아온 태스크 ID로 진행을 본다. 너무 빨라서 운영 쓰기를 밀어내면 속도를 늦출 수 있다.

```http
GET _tasks/oTUltX4IQMOUUVeiohTt8A:12345

POST _update_by_query/oTUltX4IQMOUUVeiohTt8A:12345/_rethrottle?requests_per_second=500

POST _tasks/oTUltX4IQMOUUVeiohTt8A:12345/_cancel
```

`requests_per_second`는 처음부터 줄 수도 있다. 내부적으로 1000건씩(scroll_size 기본값) 처리하고 다음 묶음 전에 쉬는 시간을 넣어 평균 속도를 맞춘다. `slices=auto`는 샤드 수만큼 나눠 병렬로 돈다. 빨라지는 만큼 클러스터 부하도 커지니 운영 시간에는 슬라이스와 속도 제한을 함께 건다.

`_delete_by_query`로 수백만 건을 지워도 디스크는 바로 줄지 않는다. 삭제 표시만 늘어나서 `_cat/indices`의 `docs.deleted`가 커질 뿐이다. 인덱스 전체 또는 기간 단위로 지우는 경우라면 문서를 지우지 말고 인덱스를 시간 단위로 나눠 두고 통째로 삭제하는 쪽이 훨씬 싸다. 로그를 날짜별 인덱스나 데이터 스트림으로 쌓는 이유다([ELK 스택 글](/posts/elk-stack-basics)의 ILM 참고).

## 지운 문서는 병합 때 사라진다

삭제 표시된 문서가 실제로 사라지는 때는 세그먼트 병합이다. Lucene은 작은 세그먼트 여럿을 골라 큰 세그먼트 하나로 다시 쓰면서 삭제 표시된 문서를 빼고 옮긴다. 이 작업은 백그라운드에서 병합 정책(기본 tiered)에 따라 저절로 돈다. 세그먼트 수가 적을수록 검색이 조금 빠르고, 삭제 문서가 빠질수록 디스크와 캐시가 가벼워진다.

그래서 `_forcemerge`로 강제로 합치고 싶어지는데, 쓸 수 있는 때는 정해져 있다.

```http
POST /logs-2026.10.22/_forcemerge?max_num_segments=1
```

더 이상 쓰지 않는 인덱스, 예를 들어 어제 날짜 로그나 롤오버된 뒤의 옛 인덱스에만 쓴다. 계속 쓰는 인덱스를 세그먼트 하나로 합치면 수십 GB짜리 세그먼트가 생기는데, 기본 병합 정책은 5GB가 넘는 세그먼트를 다시 병합 대상으로 고르지 않는다. 그 뒤로 들어오는 수정과 삭제의 표시가 그 거대한 세그먼트에 계속 쌓이고, 저절로는 치워지지 않는다. 공간을 아끼려다 오히려 디스크가 늘어나는 셈이다. 강제 병합은 디스크와 I/O도 많이 쓰니 한가한 시간에 돌린다.

병합 진행과 세그먼트 상태는 이렇게 본다.

```http
GET _cat/segments/products-v2?v&h=shard,segment,docs.count,docs.deleted,size

GET _cat/indices/products-v2?v&h=index,docs.count,docs.deleted,store.size
```

`docs.deleted`가 `docs.count`의 상당 비율이면 수정·삭제가 많은 인덱스다. 계속 쓰는 인덱스라면 강제 병합 대신 업데이트 방식(조회수 같은 잦은 갱신)부터 다시 본다.

## 6시간짜리 재색인을 다시 짜면

쓰기 작업에서 놓치기 쉬운 건 두 가지다. 하나는 Elasticsearch에서 "고치기"가 사실은 "새로 쓰고 옛것에 삭제 표시"라는 것이다. 부분 업데이트도, `_update_by_query`도, 삭제도 결국 세그먼트에 새 문서와 삭제 표시를 쌓고 병합이 치운다. 다른 하나는 `_bulk`의 200이 성공이 아니라는 것이다. 항목마다 상태를 보고 429만 늦춰서 다시 보내야 빠지는 문서가 없다. 대량 적재 때는 refresh와 레플리카를 끄고, 끝나면 refresh, 레플리카, green 확인, 별칭 교체 순서로 되돌린다. 재색인 전에 원래 인덱스를 되살릴 수 있게 스냅숏을 하나 떠 두는 습관은 [스냅숏과 재해 복구](/posts/elasticsearch-snapshot-dr) 글에서 이어진다.

## 면접에서 나올 만한 질문

### Elasticsearch에서 부분 업데이트는 어떻게 동작하나요?

필드 하나만 보내도 내부에서는 저장된 `_source`를 읽어 합친 새 문서를 처음부터 다시 색인하고, 옛 문서에는 삭제 표시를 한다. 역색인과 doc_values를 필드 단위로 고칠 수 없기 때문이다. 그래서 문서가 크거나 갱신이 잦으면 비싸고, 삭제 표시가 쌓여 병합 부담이 늘어난다. 값이 같으면 `noop`으로 건너뛰는 것도 알아 두면 좋다.

### 두 요청이 같은 문서를 동시에 고칠 때 덮어쓰기는 어떻게 막나요?

읽을 때 받은 `_seq_no`와 `_primary_term`을 저장 요청에 `if_seq_no`, `if_primary_term`으로 붙인다. 그 사이 다른 쓰기가 있었다면 409가 오고, 다시 읽어 합친 뒤 재시도한다. 원본 DB의 버전이 진짜 순서라면 `version_type=external`로 더 큰 버전만 받게 해서 순서가 뒤바뀐 이벤트가 새 값을 덮지 못하게 한다.

### _bulk 요청의 응답이 200이면 다 성공한 건가요?

아니다. `_bulk`는 일부 항목이 실패해도 HTTP 200을 돌려주고, 실패는 본문의 `errors: true`와 `items` 안의 항목별 `status`로 알려 준다. 429나 503처럼 일시적인 실패만 골라 백오프로 다시 보내고, 400대 데이터 오류는 재시도하지 말고 데드 레터에 쌓는다. 배치 전체를 다시 보내면 성공한 문서까지 다시 쓰고, 자동 ID라면 중복이 생긴다.

### _bulk 요청 크기와 동시성은 어떻게 정하나요?

정답 숫자는 없고 재서 정한다. 노드 하나, 샤드 하나에서 배치 크기를 두 배씩 늘리며 처리량이 평평해지는 지점을 찾고, 그다음 동시 요청 수를 늘리다 처리량이 멈추거나 429가 나기 시작하면 멈춘다. 문서 크기가 제각각이면 건수 대신 바이트로 끊고, 기본 100MB인 `http.max_content_length`보다 한참 작게 둔다.

### 대량 적재를 빠르게 하려면 어떤 설정을 바꾸고, 어떻게 되돌리나요?

적재하는 동안 `refresh_interval`을 `-1`, `number_of_replicas`를 0으로 둬서 작은 세그먼트 생성과 레플리카의 중복 색인을 없앤다. 끝나면 `refresh_interval`을 `null`로 되돌리고 `_refresh`, 레플리카를 올린 뒤 green이 될 때까지 기다리고, 그 뒤에 별칭을 바꾼다. 레플리카 0인 동안은 복사본이 없으니 다시 만들 수 있는 인덱스에만 쓴다.

### 429 es_rejected_execution_exception이 나면 어떻게 대응하나요?

노드의 쓰기 스레드 풀 대기열이나 indexing pressure 메모리 한도가 찼다는 백프레셔 신호다. 실패한 항목만 지수 백오프로 다시 보내고, 비율이 계속 높으면 동시 요청 수나 배치 크기를 줄인다. 대기열 크기를 키우는 건 거절을 늦출 뿐 힙 사용만 늘린다.

### _update_by_query가 중간에 version conflict로 멈췄습니다. 무슨 일이 일어난 건가요?

시작할 때 잡은 스냅숏의 문서를 처리하러 갔더니 그 사이 다른 쓰기가 같은 문서를 바꿔서 충돌이 난 것이다. 기본값에서는 충돌 하나에 작업이 멈추고, 이미 고친 문서는 되돌리지 않는다. 쓰기가 계속 들어오는 인덱스라면 `conflicts=proceed`로 건너뛰고 `version_conflicts` 수를 확인한 뒤, 스크립트가 멱등이면 한 번 더 돌린다.

### force merge는 언제 쓰고 언제 쓰면 안 되나요?

더 이상 쓰지 않는 읽기 전용 인덱스, 예를 들어 롤오버가 끝난 옛 로그 인덱스에서 세그먼트 수를 줄이고 삭제 문서를 치울 때만 쓴다. 계속 쓰는 인덱스를 하나로 합치면 5GB를 넘는 거대한 세그먼트가 생기고, 기본 병합 정책은 이를 다시 합치지 않아 이후 삭제 표시가 계속 쌓인다. I/O를 많이 쓰니 한가한 시간에 돌린다.
