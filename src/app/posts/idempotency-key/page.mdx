<EasyIntro>
  주문 요청에 "같은 요청인지 알아보는 번호표"를 붙였는데도 주문이 두 건 생겼다. 서버 코드는 번호표가 있는지 먼저 찾아보고, 없으면 주문을 만들고, 마지막에 번호표를 저장한다. 그런데 앱이 거의 동시에 두 번 보냈고, 두 요청이 모두 "번호표 없음"을 확인한 뒤 둘 다 주문을 만들었다.

  문제는 확인과 기록 사이에 틈이 있다는 것이다. 막으려면 확인을 없애고 기록을 먼저 한다. 번호표를 데이터베이스에 넣는 동작 자체가 확인이 되게 만들면, 같은 번호표를 동시에 넣으려는 두 요청 중 하나만 성공하고 그쪽이 주인이 되어 일을 한다. 주인은 주문을 만드는 것과 결과를 번호표에 적는 것을 한 묶음으로 저장하고, 나중에 같은 번호표가 오면 저장한 결과를 그대로 돌려준다.

  여기에 주인이 일하다 죽었을 때 넘겨받는 규칙과, 바깥 결제사를 부를 때 같은 번호표를 넘기는 장치까지 있어야 정말로 한 번만 처리된다. 흔한 실수는 번호표를 사용자별로 구분하지 않는 것인데, 남의 번호표를 추측해 남의 주문 결과를 받아 볼 수 있는 구멍이 된다.
</EasyIntro>

주문 API에 `Idempotency-Key` 헤더를 받기 시작했는데도 같은 키로 주문이 두 건 생겼다는 제보가 온다. 코드를 열어 보면 이렇다. 키로 저장된 응답을 먼저 찾아보고, 없으면 주문을 만들고, 마지막에 키와 응답을 저장한다. 순서만 보면 틀린 데가 없다. 그런데 앱이 타임아웃 직후 같은 요청을 두 번 다시 보냈고, 두 요청이 거의 동시에 "키 없음"을 확인한 뒤 둘 다 주문을 만들었다.

멱등성 키가 왜 필요한지, 어떤 메서드가 원래 멱등한지는 이미 다뤘다. 재시도와 멱등성 키의 큰 그림은 [장애가 번지지 않게 막는 패턴](/posts/resilience-patterns)에, 메서드별 멱등성은 [HTTP 메서드](/posts/http-methods)에, API 문서에 무엇을 약속할지는 [REST API 설계](/posts/rest-api-design)에 있다. 이 글은 그다음 질문을 다룬다. 동시에 들어온 중복, 처리 도중에 죽은 서버, 바깥 결제사 호출까지 있을 때 키 저장소를 어떻게 만들어야 정말로 한 번만 처리되는가. PostgreSQL 16과 Node.js 22로 서버를 직접 띄워서 확인했다.

## 키 한 줄에 담는 것

키 하나에 한 줄을 둔다. 주문 테이블과 같은 데이터베이스에 두는 게 중요하다. 그래야 주문을 넣는 것과 키에 응답을 적는 것을 한 트랜잭션으로 묶을 수 있다.

```sql
CREATE TABLE orders (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    bigint NOT NULL,
  item       text   NOT NULL,
  amount     int    NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE idempotency_keys (
  user_id       bigint      NOT NULL,             -- 키는 사용자마다 따로
  key           text        NOT NULL,
  request_hash  text        NOT NULL,             -- 메서드+경로+본문의 해시
  status        text        NOT NULL DEFAULT 'processing',  -- processing | done
  response_code int,
  response_body jsonb,
  locked_at     timestamptz NOT NULL DEFAULT now(),
  created_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, key)
);
```

## 선점하고, 작업하고, 응답을 적는다

요청 하나는 세 단계를 지난다.

1. 선점: `INSERT ... ON CONFLICT DO NOTHING`으로 키를 `processing` 상태로 넣고 바로 커밋한다. 한 줄이 들어갔으면 내가 주인이다.
2. 작업: 새 트랜잭션을 열어 주문을 넣는다.
3. 기록: 같은 트랜잭션에서 키 줄을 `done`으로 바꾸고 응답을 적은 뒤 커밋한다.

선점에 실패하면, 즉 이미 키가 있으면 그 줄을 읽어 보고 정한다. 해시가 다르면 422, `processing`이면 409, `done`이면 저장된 응답을 재생한다. 아래 그림은 동시에 온 중복 두 개와 나중에 온 재시도 하나다.

서버를 띄우고 같은 키로 요청 다섯 개를 동시에 보냈다. 작업 단계에 300ms가 걸리게 해서(결제사 호출 흉내) 겹치는 시간을 만들었다.

```bash
K=8e0f6a2c-3b1d-4c55-9a77-0c2f1d9e4b10
B='{"item":"keyboard","amount":89000}'
# 같은 키로 동시에 5개를 보내고 상태 코드만 찍는다
for i in 1 2 3 4 5; do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST -H "X-User-Id: 42" \
    -H "Idempotency-Key: $K" -d "$B" localhost:8082/v1/orders &
done; wait
```

```text
409
409
409
409
201
```

먼저 끝난 409 네 개는 선점에 실패한 요청들이고, 300ms 뒤에 주인의 201이 왔다. 같은 키로 한 번 더 보내면 저장된 응답이 재생된다.

```bash
# 같은 키, 같은 본문으로 다시 보낸다
curl -si -X POST -H "X-User-Id: 42" -H "Idempotency-Key: $K" -d "$B" localhost:8082/v1/orders
```

```text
HTTP/1.1 201 Created
Content-Type: application/json
Idempotent-Replayed: true
Date: Tue, 20 Oct 2026 13:26:28 GMT
Connection: keep-alive
Keep-Alive: timeout=5
Transfer-Encoding: chunked

{"id":"1","item":"keyboard","amount":89000}
```

`Idempotent-Replayed: true`는 Stripe가 쓰는 헤더 이름을 따랐다. 표준은 아니지만 클라이언트가 "이건 재생된 응답"이라는 걸 알면 로그와 디버깅이 쉬워진다. 같은 키에 금액만 바꿔 보내면 처리하지 않는다.

```bash
# 같은 키, 다른 본문
curl -si -X POST -H "X-User-Id: 42" -H "Idempotency-Key: $K" -d '{"item":"keyboard","amount":1}' localhost:8082/v1/orders
```

```text
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json
Date: Tue, 20 Oct 2026 13:26:28 GMT
Connection: keep-alive
Keep-Alive: timeout=5
Transfer-Encoding: chunked

{"title":"Idempotency-Key reused with a different request"}
```

요청은 일곱 번 갔지만 테이블에는 주문 한 건, 키 한 줄뿐이다.

```sql
SELECT id, user_id, item, amount FROM orders;
SELECT user_id, left(key, 8) AS key, request_hash, status, response_code FROM idempotency_keys;
```

```text

----+---------+----------+--------

(1 row)

---------+----------+------------------+--------+---------------
      42 | 8e0f6a2c | be2b572107122c15 | done   |           201
```

409와 422의 구분은 IETF httpapi 작업 그룹의 `Idempotency-Key` 헤더 초안을 따랐다. 초안은 키가 필요한 엔드포인트에 키가 없으면 400, 같은 키의 요청이 아직 처리 중이면 409, 같은 키를 다른 본문에 다시 쓰면 422를 제안한다. 아직 초안이라 서비스마다 다르게 하는 곳도 있으니 API 문서에 적어 둔다.

## 처리 도중에 서버가 죽으면

선점은 커밋했는데 작업을 끝내기 전에 프로세스가 죽으면 키는 `processing`으로 남는다. 넘겨받는 규칙이 없으면 이 키는 보관 기한이 끝날 때까지 영원히 409다. 그래서 선점 쿼리에 "낡은 처리 중 줄은 넘겨받는다"는 조건을 넣었다.

```sql
INSERT INTO idempotency_keys (user_id, key, request_hash) VALUES ($1, $2, $3)
ON CONFLICT (user_id, key) DO UPDATE SET locked_at = now()
  WHERE idempotency_keys.status = 'processing'
    AND idempotency_keys.request_hash = EXCLUDED.request_hash
    AND idempotency_keys.locked_at < now() - interval '5 seconds'
RETURNING (xmax = 0) AS fresh;
```

충돌하면 원래는 아무것도 안 하지만, 처리 중이고 해시가 같고 5초 넘게 묵은 줄이면 `locked_at`을 지금으로 바꾸며 넘겨받는다. 이 갱신도 행 잠금 아래에서 일어나서 넘겨받는 요청은 하나뿐이다. `xmax = 0`은 새로 넣은 줄이면 참, 갱신한 줄이면 거짓이 되는 PostgreSQL의 관용구다. 넘겨받은 경우를 로그로 남기는 데 썼다.

작업 도중 죽게 만든 서버로 요청을 보내고, 정상 서버로 바꿔 띄운 뒤 바로 재시도, 5초 뒤 다시 재시도했다.

```bash
# 작업 단계에서 죽는 서버로 첫 요청 (응답 없이 연결이 끊긴다)
curl -s -o /dev/null -w "1st: %{http_code}\n" -X POST -H "X-User-Id: 42" -H "Idempotency-Key: $K2" -d "$B" localhost:8082/v1/orders
# 정상 서버로 바꾼 뒤 바로 재시도
curl -s -w " %{http_code}\n" -X POST -H "X-User-Id: 42" -H "Idempotency-Key: $K2" -d "$B" localhost:8082/v1/orders
```

```text
1st: 000
{"title":"A request with this Idempotency-Key is in progress"}
 409
```

```sql
SELECT left(key, 8) AS key, status, now() - locked_at AS held FROM idempotency_keys WHERE key = '5d7c1e90-aa41-4f0e-8c3b-6b2e7f9d1a22';
```

```text
   key    |   status   |      held       
----------+------------+-----------------
 5d7c1e90 | processing | 00:00:01.215308
(1 row)
```

5초가 지난 뒤의 재시도와 서버 로그다.

```text
{"id":"2","item":"mouse","amount":32000}
 201
takeover key=5d7c1e90-aa41-4f0e-8c3b-6b2e7f9d1a22 (이전 처리자가 끝내지 못함)
```

주문이 두 번 생기지 않은 이유는 죽은 첫 요청의 작업 트랜잭션이 커밋되지 않았기 때문이다. 주문 INSERT도 롤백됐다. 그래서 넘겨받은 요청이 처음부터 다시 해도 안전하다.

잠금 시간은 작업이 걸릴 수 있는 최대 시간보다 넉넉히 길게 잡는다. 너무 짧으면 주인이 살아서 느리게 일하는 중에 다른 요청이 넘겨받아, 둘이 같은 작업을 동시에 한다. 이 글의 구조에서는 그래도 주문이 둘 생기지는 않는다. 키 줄을 `done`으로 바꾸는 UPDATE에 `WHERE status = 'processing' AND locked_at = 내가 잡은 시각`을 붙이면, 늦게 끝난 쪽은 0행 갱신을 보고 롤백할 수 있다. 내가 아직 주인인지 확인하고 쓰는 이 방식은 [분산 락의 펜싱 토큰](/posts/distributed-lock)과 같은 생각이다. 반대로 잠금 시간이 너무 길면 죽은 요청 뒤의 재시도가 그만큼 오래 409를 받는다.

## 트랜잭션 하나로 묶으면 기다리게 된다

선점을 따로 커밋하지 않고, 선점부터 기록까지 트랜잭션 하나로 하는 방법도 있다. 이러면 중간에 죽어도 키 줄까지 롤백되어 넘겨받기 규칙이 필요 없다. 대신 동작이 달라진다. 두 연결로 직접 해 봤다.

```bash
# A가 키를 넣고 커밋하지 않은 채 2초 일하는 동안 B가 같은 키를 넣는다
node onetx.js
```

```text
0.03s A: 키 선점 (아직 커밋 전)
0.03s B: 같은 키로 INSERT ... ON CONFLICT DO NOTHING 보냄
┌─────────┬───────┬─────────────────┬─────────────────┬────────────────────────────────────────────┐
│ (index) │ pid   │ wait_event_type │ wait_event      │ query                                      │
├─────────┼───────┼─────────────────┼─────────────────┼────────────────────────────────────────────┤
│ 0       │ 21065 │ 'Lock'          │ 'transactionid' │ 'INSERT INTO idempotency_keys (user_id, k' │
└─────────┴───────┴─────────────────┴─────────────────┴────────────────────────────────────────────┘
2.04s A: 작업 끝, COMMIT
2.04s B: 돌아옴 rowCount=0
2.04s B: status=done -> 저장된 응답을 돌려준다
```

가운데 표는 그사이 `pg_stat_activity`를 조회한 결과다. B의 INSERT는 `Lock / transactionid`에서 2초 동안 멈춰 있었다. PostgreSQL은 유니크 인덱스에 커밋되지 않은 같은 값이 있으면, 그 트랜잭션이 커밋할지 롤백할지 알 때까지 기다린다. A가 커밋하자 B는 충돌을 확인하고 0행을 돌려받았고, 곧바로 `done`을 읽어 재생했다.

클라이언트 입장에서는 409 없이 바로 정답을 받으니 더 편하다. 대가는 기다리는 동안 B가 DB 연결 하나와 앱 스레드 하나를 붙잡는다는 것이다. 작업이 짧은 DB 쓰기뿐이면 이 방식이 단순하고 좋다. 작업이 몇 초 걸리거나 바깥 API를 부르면 위의 단계 나누기를 쓴다. 트랜잭션을 연 채로 바깥 API를 기다리면 [오래 열린 트랜잭션](/posts/sql-batch-timeout-pool)이 되어 청소(vacuum)까지 막는다.

## 바깥 결제사를 부르는 단계가 끼면

주문만 넣는 거라면 DB 트랜잭션 하나로 "한 번만"을 지킬 수 있다. 그런데 결제사 API는 우리 트랜잭션에 들어오지 않는다. 결제를 요청해 놓고 우리 서버가 죽으면, 결제는 됐는데 우리 DB에는 기록이 없다. 넘겨받은 재시도가 결제를 또 요청하면 두 번 결제된다.

방법은 두 가지를 겹치는 것이다. 바깥 호출에도 멱등성 키를 넘기고, 작업을 되돌아올 수 있는 단계로 나눠 각 단계 끝에 어디까지 했는지 적는다.

## 어떤 응답을 저장할지

처음 결과가 정해진 응답만 저장한다. 201 같은 성공과 400, 422처럼 입력이 틀려서 난 4xx는 다시 보내도 같은 결과여야 하니 저장해서 재생한다. 5xx와 타임아웃은 저장하지 않는다. 서버 사정으로 실패한 것이니 재시도가 다시 해 볼 수 있어야 한다. 위 서버는 작업 중 예외가 나면 트랜잭션을 롤백하고 `processing` 줄을 지웠다.

## 키는 누가, 언제 만드나

키는 클라이언트가 만든다. 서버가 만들어 주면 첫 요청의 응답이 사라졌을 때 클라이언트는 그 키를 모른다. 만드는 시점은 "사용자의 의도 하나"에 맞춘다. 주문서 화면이 열릴 때 하나 만들고, 그 화면에서의 재시도와 중복 클릭에는 같은 키를 쓴다. 버튼을 누를 때마다 새 키를 만들면 두 번 누른 것을 막지 못한다. 반대로 주문을 마치고 같은 화면에서 새 주문을 할 때는 새 키를 만들어야 정상적인 두 번째 주문이 재생으로 막히지 않는다.

키를 오래 보관할 이유는 없다. 재시도는 보통 몇 분 안에 끝난다. Stripe는 24시간이 지난 키를 지울 수 있다고 밝히고 있다. 정리는 한꺼번에 하지 않고 묶음으로 나눠 지운다. 한 번에 수백만 줄을 지우면 잠금과 WAL이 몰린다.

```sql
CREATE INDEX idempotency_keys_created_at_idx ON idempotency_keys (created_at);

-- 하루 지난 키를 5000줄씩 지운다. 0이 나올 때까지 반복한다
DELETE FROM idempotency_keys
WHERE ctid IN (
  SELECT ctid FROM idempotency_keys
  WHERE created_at < now() - interval '24 hours'
  LIMIT 5000
);
```

```text
DELETE 5000
```

3일 묵은 키 1만 2천 줄을 넣어 두고 돌린 결과다. 키가 아주 많으면 날짜별 파티션으로 나눠 오래된 파티션을 통째로 떼어 내는 편이 더 싸다.

## 키 말고도 중복을 막는 방법

멱등성 키는 범용 장치라 무겁다. 요청 안에 이미 자연스러운 유일값이 있으면 그걸 유니크 제약으로 거는 편이 단순하다. 장바구니 ID당 주문은 하나라면 `orders(cart_id)`에 유니크를 걸고 `INSERT ... ON CONFLICT (cart_id) DO NOTHING RETURNING`으로 넣는다. 두 번째 요청은 0행을 받고 기존 주문을 조회해 돌려준다.

클라이언트가 자원 ID를 먼저 정하는 방법도 있다. `POST /orders` 대신 `PUT /orders/{uuid}`로 보내면 PUT은 원래 멱등하다. 몇 번 보내도 그 UUID의 주문 하나다.

Redis의 `SET key value NX EX 86400`으로 키를 선점하는 구현도 흔하다. 빠르지만 Redis와 DB가 따로라서, Redis에는 키가 있는데 DB 커밋은 실패한 상태가 생길 수 있다. 그러면 재시도는 "이미 처리됨"을 받지만 주문은 없다. 선점은 Redis로 하더라도 최종 기록은 DB 트랜잭션 안에 두고, Redis 키는 빠른 1차 필터로만 쓴다.

메시지 큐에서 같은 메시지가 두 번 오는 경우도 같은 구조로 막는다. 메시지 ID를 처리 기록 테이블에 유니크로 넣고, 처리 결과와 같은 트랜잭션으로 커밋한다. 큐가 왜 같은 메시지를 다시 보내는지는 [메시지 전달 보장](/posts/message-delivery-semantics)에 있다.

## 운영에서 이런 증상을 보면

"키를 받는데도 중복 주문이 생긴다"면 먼저 키를 확인하고 넣는 순서인지 본다. 유니크 제약으로 선점하는 코드가 아니면 위의 경쟁이 그대로 열려 있다. 그다음 클라이언트가 클릭마다 새 키를 만드는지, 키가 사용자별로 범위가 잡혀 있는지 본다. 로드 밸런서나 서비스 메시의 자동 재시도가 POST를 다시 보내는 경우도 있다. 키가 붙은 요청이라면 괜찮지만, 키를 붙이기 전 단계에서 재시도가 일어나면 막을 수 없다.

"409가 쏟아진다"면 클라이언트가 409를 받자마자 다시 보내고 있거나, 잠금 시간이 작업 시간보다 짧아 넘겨받기가 반복되는 경우다. 서버 로그에서 같은 키의 takeover가 여러 번 찍히는지 본다.

"키 테이블이 계속 커진다"면 정리 작업이 돌고 있는지, `created_at` 인덱스가 있는지 본다. 인덱스 없이 지우면 정리 작업이 매번 테이블 전체를 읽는다.

"재생된 응답이 이상하다"는 문의는 응답을 저장할 때 일부만 저장했거나, 응답에 사용자별로 달라지는 값(현재 시각, 남은 포인트)이 섞여 있을 때 나온다. 재생은 처음 응답 그대로라는 걸 API 문서에 적는다.

## 키 저장소가 정확해야 재시도가 안전하다

멱등성 키는 헤더 하나로 끝나지 않는다. 유니크 제약으로 먼저 선점하고, 작업과 응답 기록을 한 트랜잭션으로 묶고, 처리 중에 죽은 요청을 넘겨받는 규칙과 바깥 호출에 넘길 키까지 있어야 "한 번만"이 지켜진다. 왜 이런 장치가 필요한지는 [재시도와 서킷 브레이커 글](/posts/resilience-patterns)에서, 메서드의 멱등성은 [HTTP 메서드](/posts/http-methods)에서 이어서 볼 수 있다.

## 면접에서 나올 만한 질문

### 멱등성 키는 어떻게 구현하나요?

클라이언트가 작업마다 고유한 키를 헤더에 싣고, 서버는 그 키를 사용자별 유니크 제약이 걸린 테이블에 먼저 넣어 선점한다. 선점한 요청만 작업을 하고, 작업 결과와 응답 저장을 한 트랜잭션으로 커밋한다. 같은 키가 다시 오면 저장된 응답을 재생하고, 처리 중이면 409, 본문이 다르면 422를 돌려준다.

### 저장된 키를 먼저 SELECT로 확인하면 왜 안 되나요?

확인과 기록 사이에 틈이 있어서 동시에 온 두 요청이 둘 다 "없음"을 보고 둘 다 처리한다. 서버가 여러 대면 메모리로 거를 수도 없다. 유니크 제약이 걸린 INSERT를 확인 대신 쓰면 데이터베이스가 원자적으로 하나만 성공시킨다.

### 같은 키로 요청이 동시에 오면 어떻게 하나요?

선점한 요청만 처리하고 나머지는 409와 Retry-After로 돌려보내는 방법과, 선점과 작업을 한 트랜잭션에 넣어 나머지가 유니크 인덱스에서 기다리다 결과를 재생하게 하는 방법이 있다. 앞쪽은 자원을 붙잡지 않고, 뒤쪽은 클라이언트가 바로 정답을 받는 대신 기다리는 동안 DB 연결을 붙잡는다. 작업이 길거나 바깥 호출이 있으면 앞쪽을 쓴다.

### 처리 중에 서버가 죽으면 키는 어떻게 되나요?

선점만 커밋되고 작업은 롤백되어 키가 processing으로 남는다. locked_at을 두고 잠금 시간이 지난 줄은 같은 해시의 재시도가 넘겨받게 한다. 잠금 시간은 최대 작업 시간보다 넉넉히 잡고, 완료를 기록할 때 내가 잡은 locked_at이 그대로인지 확인해서 늦게 끝난 옛 주인이 덮어쓰지 못하게 한다.

### 결제사 같은 바깥 API를 부르는 작업은 어떻게 한 번만 처리하나요?

바깥 호출은 우리 트랜잭션에 들어오지 않으니, 우리 키에서 만든 키를 바깥 API의 멱등성 헤더로 넘긴다. 작업을 단계로 나눠 단계마다 진행을 키 줄에 기록하면, 넘겨받은 재시도가 끝난 단계는 건너뛰고 이어서 한다. 바깥 API가 키를 받지 않으면 호출 전에 조회하는 단계를 두고, 마지막은 정산으로 맞춘다.

### 키는 왜 사용자별로 범위를 잡나요?

키만으로 유일하게 하면 다른 사용자가 같은 키를 보냈을 때 남의 주문 응답을 재생해 준다. 키를 추측해서 남의 결과를 훔쳐볼 수 있는 구멍이다. (사용자, 키)를 기본 키로 잡으면 우연한 충돌도 사용자 안으로 좁혀진다.

### 어떤 응답을 저장하고 재생하나요?

다시 보내도 결과가 같아야 하는 응답, 즉 성공과 입력 오류 같은 4xx를 저장한다. 5xx와 타임아웃은 서버 사정이라 저장하지 않고 키를 풀어서 재시도가 다시 처리할 수 있게 한다. 보관은 재시도가 끝날 만큼만, 보통 24시간 정도로 하고 묶음으로 나눠 지운다.
