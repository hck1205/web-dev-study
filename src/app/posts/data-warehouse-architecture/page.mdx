  선생님들은 셋째 칸만 보고 이야기한다. 기준을 바꾸고 싶으면 셋째 칸을 다시 세면 되고, 첫 칸에 원래 종이가 남아 있으니 언제든 처음부터 다시 셀 수 있다. 데이터 웨어하우스는 회사의 숫자를 이런 칸으로 나눠 쌓아 두는 곳이다.

## 회의마다 매출 숫자가 세 개다

월간 회의에서 7월 매출이 세 개 나왔다. 마케팅팀은 4억 원, 재무팀은 2억 6800만 원, 데이터팀은 2억 6700만 원이라고 했다. 셋 다 같은 `orders` 테이블에서 뽑았다. 회의는 누구 숫자가 맞는지 따지다 끝났고, 다음 주에 다시 모였다.

세 쿼리를 나란히 놓으면 이유가 바로 보인다. 앞 글 [ETL과 ELT](/posts/etl-vs-elt)에서 쓴 주문 200만 건(가짜 데이터라 취소가 3분의 1이나 된다)을 DuckDB 1.5에 올려 같은 7월을 세 방식으로 셌다.

```sql
SET TimeZone = 'Asia/Seoul';
SELECT
  sum(amount)                                             AS a_all,        -- 마케팅: 주문이 들어온 금액 전부
  sum(amount) FILTER (WHERE status <> 'cancelled')        AS b_no_cancel,  -- 재무: 취소만 뺀다
  sum(amount) FILTER (WHERE status IN ('paid','shipped')) AS c_net         -- 데이터팀: 취소와 환불을 뺀다
FROM ods_orders
WHERE created_at >= TIMESTAMPTZ '2026-07-01 00:00:00+09'
  AND created_at <  TIMESTAMPTZ '2026-08-01 00:00:00+09';
```

```text
┌───────────────┬───────────────┬───────────────┐
│     a_all     │  b_no_cancel  │     c_net     │
│ decimal(38,2) │ decimal(38,2) │ decimal(38,2) │
├───────────────┼───────────────┼───────────────┤
│  401751065.60 │  268170124.80 │  267166784.80 │
└───────────────┴───────────────┴───────────────┘
```

여기에 "월"을 UTC로 자른 사람이 한 명 더 있으면 네 번째 숫자(267,200,760.80)가 나온다. 쿼리는 다 맞다. 매출의 뜻이 사람마다 달랐을 뿐이다. 데이터 웨어하우스 설계가 푸는 문제가 이것이다. 운영 DB에서 데이터를 옮겨 오는 일보다, 옮긴 데이터에서 회사가 쓰는 숫자의 뜻을 한 곳에서 한 번만 정하는 일이 더 어렵다.

이 글은 그 "한 곳"을 어떻게 나누는지 본다. 레이어로 칸을 나누는 법, 중앙 웨어하우스와 부서별 마트의 두 전통, 레이크·웨어하우스·레이크하우스의 차이, 저장과 계산을 떼어 놓은 구조가 요금에 미치는 영향까지다. 분석 테이블을 사실과 차원으로 나누는 모델링은 [스타 스키마](/posts/olap-star-schema)에, 분석 DB가 컬럼으로 저장해서 빠른 이유는 [컬럼형 분석 DB](/posts/db-type-columnar-olap)에 있다.

## 원본, 정제, 쓰임새로 나눈 세 칸

웨어하우스 안을 칸으로 나누는 방식은 이름이 여러 가지지만 모양은 비슷하다. Databricks가 퍼뜨린 메달리온(medallion) 이름으로 부르면 브론즈, 실버, 골드다. dbt 프로젝트에서는 흔히 staging, intermediate, marts라고 부른다.

브론즈는 원본을 그대로 쌓는 칸이다. 운영 DB에서 추출한 행, 이벤트 로그, 외부 API 응답을 모양을 바꾸지 않고 날짜별로 넣는다. 덮어쓰지 않고 쌓기만 하니 언제든 여기서부터 다시 계산할 수 있다. 실버는 정제하고 맞춘 칸이다. 타입을 고치고, 키별로 최신 행만 남기고, 시간대를 정하고, 여러 원본의 같은 개념(앱의 회원과 결제사의 고객)을 같은 키로 맞춘다. 골드는 쓰임새별 칸이다. 대시보드와 리포트가 바로 읽는 집계, 사실·차원 테이블, 머신러닝용 특성 테이블이 여기 있다.

아래 그림에서 점이 흐르는 방향이 데이터가 다듬어지는 방향이다. 분석가와 대시보드는 골드만, 데이터 엔지니어와 데이터 사이언티스트는 필요하면 실버까지 읽는다.

실험 데이터로 실버를 만들어 봤다. 타입은 이미 맞췄으니, 한국 시각 기준 주문일 컬럼을 하나 더 만들고 월별 파티션으로 Parquet에 쓴다. 이름에 `_kst`를 붙여 둔 데 뜻이 있다. 이 컬럼을 쓰는 사람은 날짜 경계를 다시 고민하지 않는다.

```sql
SET TimeZone = 'Asia/Seoul';
COPY (
  SELECT id, user_id, status, amount, created_at, updated_at,
         CAST(created_at AS DATE)        AS order_date_kst,   -- 한국 시각 기준 날짜
         strftime(created_at, '%Y-%m')   AS month              -- 파티션 키
  FROM ods_orders
) TO 'silver' (FORMAT parquet, PARTITION_BY (month));
```

```bash
ls -1 silver         # 월마다 폴더 하나
du -sh full.csv silver
```

```text
month=2026-01
month=2026-02
month=2026-03
month=2026-04
month=2026-05
month=2026-06
month=2026-07
month=2026-08
143M	full.csv
47M	silver
```

같은 200만 건이 CSV로는 150MB, 컬럼 압축된 Parquet로는 49MB였다.

칸을 나누는 데는 비용이 있다. 같은 주문이 세 번 저장되고, 단계마다 변환 작업과 실패 지점이 생긴다. 그래서 칸 수 자체가 목표는 아니다. 데이터가 작고 쓰는 사람이 한 팀이면 브론즈와 골드 두 칸으로 충분하다. 칸이 늘어야 하는 신호는 "같은 정제 로직을 여러 골드 테이블이 각자 반복한다"는 것이다. 그 반복을 모아 둔 것이 실버다.

## 매출을 한 번만 정의하기

이제 골드에 매출을 정의한다. 회의 끝에 "매출은 결제 완료와 배송 완료의 금액 합, 한국 시각 기준 주문일"로 합의했다고 하자. 그 합의를 테이블 하나로 만든다.

```sql
CREATE TABLE gold_daily_revenue AS
SELECT order_date_kst,
       count(*)    FILTER (WHERE status IN ('paid','shipped')) AS orders,
       sum(amount) FILTER (WHERE status IN ('paid','shipped')) AS net_revenue,
       sum(amount) FILTER (WHERE status = 'refunded')          AS refunded_amount
FROM read_parquet('silver/*/*.parquet', hive_partitioning = true)
GROUP BY order_date_kst;

SELECT * FROM gold_daily_revenue
WHERE order_date_kst BETWEEN '2026-08-01' AND '2026-08-03' ORDER BY 1;
```

```text
┌────────────────┬────────┬───────────────┬─────────────────┐
│ order_date_kst │ orders │  net_revenue  │ refunded_amount │
│      date      │ int64  │ decimal(38,2) │  decimal(38,2)  │
├────────────────┼────────┼───────────────┼─────────────────┤
│ 2026-08-01     │   5746 │    8661112.80 │        31856.00 │
│ 2026-08-02     │   5745 │    8730296.80 │        33996.00 │
│ 2026-08-03     │   5746 │    8598116.80 │        31500.00 │
└────────────────┴────────┴───────────────┴─────────────────┘
```

7월 하루치를 모두 더하면 267,166,784.80으로, 처음 데이터팀 쿼리와 같다. 이제 마케팅팀도 재무팀도 `gold_daily_revenue`를 읽는다. 재무팀이 취소만 뺀 숫자가 필요하면 그 뜻을 가진 컬럼을 이름을 달리해 추가한다. 같은 이름에 다른 뜻을 두지 않는 것이 이 칸의 규칙이다.

지표가 많아지면 테이블마다 정의를 SQL로 흩어 두는 것도 다시 같은 문제를 만든다. 이걸 한 겹 더 모은 것이 시맨틱 레이어다. dbt의 시맨틱 레이어(MetricFlow)나 Looker의 LookML처럼 "매출 = 이 테이블의 이 컬럼 합, 이 조건"을 정의 파일에 한 번 적고, 대시보드 도구는 그 정의를 불러다 쓴다. 회사 규모가 작을 때는 잘 이름 붙인 골드 테이블과 지표 설명 문서로 충분하다.

## 중앙부터 짓느냐, 부서별로 짓느냐

웨어하우스를 어떤 순서로 짓는지에는 두 전통이 있다. 둘 다 1990년대에 나왔고 지금도 용어가 그대로 쓰인다.

빌 인먼(Bill Inmon)의 방식은 회사 전체를 위한 중앙 웨어하우스를 먼저 짓는다. 회원, 주문, 상품, 재고를 회사 전체 관점에서 정규화(3NF)된 모델로 통합하고, 부서가 쓰는 데이터 마트는 이 중앙에서 뽑아 만든다(종속 마트). 회사 전체의 정의가 한 곳에서 맞춰진다는 것이 장점이다. 그 대신 처음 쓸 수 있는 결과가 나오기까지 오래 걸리고, 통합 모델을 바꾸는 일이 무겁다.

랄프 킴볼(Ralph Kimball)의 방식은 업무 과정 하나씩 차원 모델 마트를 지어 나간다. 이번 분기에는 주문 마트, 다음 분기에는 재고 마트 식이다. 사실 테이블과 차원 테이블로 된 스타 스키마가 기본 단위다. 마트들이 따로 놀지 않게 "날짜", "회원", "상품" 같은 차원을 모든 마트가 같은 모양으로 공유한다. 이걸 공통 차원(conformed dimension)이라고 하고, 어떤 마트가 어떤 차원을 공유하는지 적은 표를 버스 매트릭스라고 부른다. 빨리 쓸모를 보여 주는 대신, 공통 차원을 지키지 않으면 마트마다 회원 수가 다른 상황으로 돌아간다.

지금의 클라우드 웨어하우스 실무는 둘을 섞은 모양이다. 실버 칸이 인먼식 통합 계층 역할을 가볍게 하고(원본별로 정제하고 키를 맞춘다), 골드 칸은 킴볼식 차원 모델과 넓은 집계 테이블로 짓는다. 원본이 자주 바뀌고 이력 추적이 중요한 대기업 환경에서는 Data Vault(허브·링크·위성 테이블로 원본 변화를 쌓는 모델)를 통합 계층에 쓰기도 한다. 면접에서 둘을 물으면 "어느 쪽이 맞나"가 아니라 "통합을 먼저 하느냐, 쓰임새를 먼저 하느냐"의 순서 차이로 답하면 된다.

## 데이터 마트를 따로 두는 이유

데이터 마트는 한 부서나 한 주제를 위해 웨어하우스에서 떼어 낸 작은 묶음이다. 마케팅 마트에는 캠페인·유입 경로·전환이, 재무 마트에는 정산·환불·세금이 있다. 같은 웨어하우스 안의 스키마 하나일 수도 있고, 별도 DB일 수도 있다.

마트를 따로 두는 이유는 세 가지다. 첫째는 쓰기 쉬움이다. 마케터가 수백 개 테이블 사이에서 헤매지 않고 자기 업무 용어로 된 테이블 열 개만 본다. 둘째는 권한이다. 재무 마트의 정산 데이터는 재무팀만, 회원 개인정보가 들어간 차원은 마스킹한 뷰로만 보이게 마트 단위로 권한을 나누기 쉽다. 셋째는 성능과 비용이다. 대시보드가 매번 수억 건 사실 테이블을 훑지 않고 미리 묶은 작은 마트를 읽는다. 클라우드 웨어하우스에서는 이것이 바로 요금 차이로 나타난다.

위험은 마트가 중앙과 끊어질 때 생긴다. 부서가 각자 원본을 직접 끌어다 마트를 지으면(독립 마트), 처음 장면의 "매출 세 개"가 마트 세 개로 굳는다. 마트는 반드시 공통 정제 칸(실버)이나 공통 차원에서 뽑고, 매출 같은 핵심 지표는 마트마다 다시 정의하지 않는다.

## 칸마다 읽을 수 있는 사람을 나눈다

칸을 나누면 권한도 칸 단위로 나눌 수 있다. 브론즈와 실버에는 이메일, 전화번호, 주소 같은 원본 값이 그대로 있다. 분석가 대부분은 이 값이 필요 없다. 파이프라인 계정만 모든 칸을 읽고 쓰고, 분석가는 골드만 읽게 하는 것이 기본이다. PostgreSQL 16에서 스키마 셋으로 칸을 만들고 역할 둘로 나눠 봤다. Snowflake, BigQuery, Redshift도 스키마(데이터셋) 단위 권한으로 같은 모양을 만든다.

```sql
CREATE SCHEMA bronze;  CREATE SCHEMA silver;  CREATE SCHEMA gold;
-- (테이블 생성은 생략: silver.orders에는 email 컬럼이 있다)

CREATE ROLE pipeline LOGIN;   -- 적재·변환 작업이 쓰는 계정
CREATE ROLE analyst  LOGIN;   -- 분석가와 대시보드 도구

GRANT USAGE ON SCHEMA bronze, silver, gold TO pipeline;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA bronze, silver, gold TO pipeline;

GRANT USAGE ON SCHEMA gold TO analyst;                              -- 골드 칸에만 들어갈 수 있다
GRANT SELECT ON ALL TABLES IN SCHEMA gold TO analyst;               -- 지금 있는 골드 테이블
ALTER DEFAULT PRIVILEGES IN SCHEMA gold GRANT SELECT ON TABLES TO analyst;  -- 앞으로 만들 골드 테이블
```

분석가 계정으로 접속해서 두 칸을 읽어 봤다.

```bash
psql -d dw -U analyst -c "SELECT * FROM gold.daily_revenue" -c "SELECT email FROM silver.orders"
```

```text
 order_date_kst | orders | net_revenue
----------------+--------+-------------
 2026-08-01     |   5746 |  8661112.80
(1 row)

ERROR:  permission denied for schema silver
LINE 1: SELECT email FROM silver.orders
                          ^
```

`ALTER DEFAULT PRIVILEGES` 줄을 빼먹는 실수가 흔하다. `ON ALL TABLES`는 명령을 실행한 순간 있던 테이블에만 적용된다. 다음 주에 dbt가 새 골드 테이블을 만들면 분석가는 그 테이블을 못 읽고, "권한이 없다"는 문의가 온다. 기본 권한은 그 명령을 실행한 역할이 앞으로 만드는 객체에만 붙으니, 테이블을 만드는 역할(여기서는 파이프라인이 쓰는 소유자 역할)로 실행해야 한다.

개인정보가 필요한 분석도 있다. 회원별 재구매 분석에는 회원을 구분할 값이 필요하지만 이메일 원문까지는 필요 없다. 이럴 때는 골드에 가린 뷰를 만든다.

```sql
CREATE VIEW gold.orders_masked AS
SELECT id, user_id, left(md5(email), 12) AS email_hash,   -- 원문 대신 해시 앞 12자리
       status, amount, order_date_kst
FROM silver.orders;
```

```text
 id | user_id |  email_hash  | status | amount  | order_date_kst
----+---------+--------------+--------+---------+----------------
  1 |       2 | 669f75780c0d | paid   | 1000.37 | 2026-08-01
(1 row)
```

분석가는 실버 스키마 권한이 없는데도 이 뷰는 읽힌다. PostgreSQL의 뷰는 기본적으로 뷰 소유자의 권한으로 밑 테이블을 읽기 때문이다(PostgreSQL 15부터 `security_invoker` 옵션을 켜면 반대로 읽는 사람의 권한을 쓴다). 소금 없는 md5는 이메일 목록을 가진 사람이 되짚을 수 있으니, 실제로는 비밀 값을 섞은 해시나 별도의 대리 키를 쓴다. 클라우드 웨어하우스에는 컬럼 마스킹 정책(Snowflake의 masking policy, BigQuery의 정책 태그)이 따로 있어서 뷰를 만들지 않고 컬럼 단위로 가릴 수 있다.

## 레이크, 웨어하우스, 그리고 레이크하우스

데이터 레이크는 원본을 파일로 싸게 쌓아 두는 곳이다. 객체 저장소(S3, GCS)나 HDFS에 CSV, JSON, Parquet, 이미지, 로그를 그대로 넣는다. 저장할 때 스키마를 강제하지 않고 읽을 때 해석한다(schema-on-read). 아무거나 넣을 수 있다는 장점이 그대로 단점이 되어, 관리하지 않으면 무엇이 어디 있는지 모르는 "데이터 늪"이 된다. 블록과 복제, 작은 파일 문제는 [데이터 레이크와 HDFS](/posts/data-lake-hdfs)에서 다뤘다.

데이터 웨어하우스는 분석용으로 구조를 갖춘 데이터베이스다. 넣을 때 스키마를 정하고(schema-on-write), SQL로 빠르게 집계하고, 트랜잭션·권한·통계 같은 DB 기능을 갖춘다. 그 대신 이미지나 반정형 로그는 다루기 어렵고, 데이터를 웨어하우스 형식으로 넣어야 해서 레이크와 사본이 이중으로 생긴다.

레이크하우스는 레이크의 파일 위에 웨어하우스 기능을 얹는다. Delta Lake, Apache Iceberg, Apache Hudi 같은 테이블 포맷이 Parquet 파일 묶음에 커밋 로그를 붙여 ACID 트랜잭션, 스키마 관리, 타임 트래블을 준다. 그러면 같은 파일을 Spark, Trino, DuckDB, 클라우드 웨어하우스가 함께 읽는다. 사본을 하나로 줄이고 특정 엔진에 묶이지 않는 것이 목표다. 2024년 무렵부터 Snowflake와 BigQuery도 Iceberg 테이블을 직접 읽고 쓰는 기능을 내면서 웨어하우스와 레이크하우스의 경계가 흐려지고 있다.

고를 때는 이렇게 본다. 데이터가 대부분 정형이고 쓰는 사람이 SQL 분석가라면 관리형 웨어하우스 하나가 가장 덜 번거롭다. 원본이 크고 다양하고(로그, 이벤트, 이미지), 머신러닝과 BI가 같은 데이터를 써야 하고, 여러 엔진을 쓸 계획이면 레이크하우스가 맞다. 대부분의 회사는 결국 레이크(브론즈)와 웨어하우스(골드)를 함께 갖고, 그 사이를 테이블 포맷으로 잇는 쪽으로 간다.

## 저장과 계산을 떼어 놓으면

예전 웨어하우스는 서버 여러 대가 각자 디스크에 데이터를 나눠 들고 계산도 같이 했다. 저장 공간이 모자라면 계산이 남아도 서버를 늘려야 했고, 새벽 적재 작업과 아침 대시보드 쿼리가 같은 서버에서 자원을 다퉜다.

클라우드 웨어하우스는 저장과 계산을 떼어 놓는다. 데이터는 객체 저장소에 한 벌 있고, 계산 클러스터는 필요할 때 띄워 그 데이터를 읽는다. Snowflake는 이 계산 단위를 가상 웨어하우스라고 부르고, BigQuery는 슬롯, Redshift는 RA3 노드의 관리형 저장소나 Serverless로 같은 구조를 만든다. 그래서 적재용 클러스터와 대시보드용 클러스터를 따로 띄워 서로 방해하지 않게 할 수 있고, 쓰지 않을 때는 계산을 꺼 둔다.

이 구조에서 쿼리 하나를 빠르게 만드는 방법은 "덜 읽기"다. 계산 쪽이 저장소에서 데이터를 가져오는 데 시간과 돈이 들기 때문이다. 아래 그림에서 다음을 누르면 쿼리 하나가 어떤 순서로 덜 읽는지 보인다.

## 읽은 만큼 내는 요금

BigQuery의 on-demand 요금은 쿼리가 처리한 바이트로 매긴다. 미국 리전 기준으로 2023년 7월부터 TiB당 6.25달러이고(리전과 시기에 따라 다르다), 이때 바이트는 쿼리가 참조한 컬럼의 크기를 더한 값이다. 그래서 `SELECT *`는 모든 컬럼 값을 낸다. `LIMIT 10`을 붙여도 처리한 바이트는 줄지 않는다는 점이 처음 쓰는 사람을 자주 놀라게 한다. 파티션 테이블에서 파티션 조건을 걸면 그 파티션만 센다. Snowflake는 다르게, 가상 웨어하우스가 켜져 있던 시간(초 단위, 켤 때마다 최소 60초)을 크레딧으로 매긴다. 방식은 달라도 덜 읽으면 덜 낸다는 결론은 같다.

실버 파일의 컬럼별 크기를 Parquet 메타데이터에서 꺼내 봤다.

```sql
SELECT path_in_schema AS col, sum(total_compressed_size) AS bytes
FROM parquet_metadata('silver/month=2026-08/*.parquet')
GROUP BY 1 ORDER BY 2 DESC;
```

```text
┌────────────────┬─────────┐
│      col       │  bytes  │
│    varchar     │ int128  │
├────────────────┼─────────┤
│ created_at     │ 1063891 │
│ updated_at     │ 1062002 │
│ amount         │  711814 │
│ id             │  686819 │
│ user_id        │  686164 │
│ status         │    6832 │
│ order_date_kst │     414 │
```

## 데이터 허브는 무엇이 다른가

데이터 허브라는 말은 웨어하우스와 섞여 쓰이지만 목적이 다르다. 웨어하우스는 분석을 위해 데이터를 모으고 이력을 쌓는 곳이다. 데이터 허브는 시스템 사이에 데이터를 주고받기 위한 중간 지점이다. 주문 시스템, 물류 시스템, CRM이 서로 일대일로 연결하는 대신 허브를 거쳐 표준 형식으로 데이터를 넘기고, 허브가 형식 변환과 품질·권한 규칙을 맡는다. 회원·상품 같은 기준 정보(마스터 데이터)를 한 곳에서 관리해 여러 시스템에 나눠 주는 역할도 흔하다.

그래서 허브의 관심은 "지금 이 고객 정보가 무엇인가, 누구에게 언제 보냈나"이고, 웨어하우스의 관심은 "지난 3년 동안 고객별 매출이 어떻게 변했나"다. 허브는 운영 시스템이 읽고, 웨어하우스는 사람과 분석 도구가 읽는다. Kafka 같은 이벤트 플랫폼을 중심에 두고 서비스들이 이벤트를 주고받는 구조가 요즘 허브 역할을 많이 대신한다([이벤트 기반 아키텍처](/posts/event-driven-architecture)).

## 작은 팀에서 시작하는 순서

처음부터 메달리온, 시맨틱 레이어, 레이크하우스를 다 갖출 필요는 없다. 규모에 따라 이렇게 넘어간다.

처음에는 운영 PostgreSQL의 읽기 복제본에서 리포트 쿼리를 돌린다. 데이터가 수천만 행 이하이고 분석가가 한두 명이면 충분하다. 여기서 넘어갈 신호는 리포트 쿼리가 분 단위로 느려지거나, 복제본의 긴 쿼리가 복제 지연을 만들거나, 여러 원본(결제사, 광고 플랫폼)을 함께 봐야 할 때다.

다음은 관리형 웨어하우스 하나와 ELT 수집 도구다. 원본을 브론즈에 넣고 dbt로 골드 테이블 몇 개를 만든다. 실버는 아직 없어도 된다. 정제 로직이 골드 여러 곳에서 반복되기 시작하면 실버를 둔다. 같은 지표가 대시보드마다 다르게 정의되기 시작하면 지표 정의를 한 곳으로 모은다.

레이크하우스로 넘어가는 신호는 웨어하우스에 넣기 어려운 데이터(대용량 로그, 이미지, 원본 이벤트)가 커지고, 같은 데이터를 Spark 학습 작업과 SQL 대시보드가 함께 써야 하고, 웨어하우스 저장 요금이 객체 저장소보다 눈에 띄게 비싸질 때다.

## 숫자가 안 맞는다는 문의를 받으면

"대시보드 매출이 재무 보고서와 다르다"는 문의가 오면 계층을 거꾸로 올라간다.

먼저 두 숫자가 같은 정의를 쓰는지 본다. 취소·환불 포함 여부, 부가세 포함 여부, 시간대, 주문일 기준인지 결제일 기준인지. 처음 장면처럼 대부분은 여기서 끝난다. 정의가 같으면 골드 테이블이 마지막으로 언제 갱신됐는지 본다. 어제 적재가 실패해 하루가 빠졌을 수 있다. 그다음 실버와 브론즈의 같은 날짜 행 수를 비교한다. 브론즈에는 있는데 실버에 없으면 정제 단계의 필터나 중복 제거가 의심스럽고, 브론즈부터 비면 추출 문제다.

이 순서가 가능하려면 칸마다 행 수와 합계를 날짜별로 남겨 두는 편이 좋다. 칸 사이에서 숫자가 어디서 달라졌는지 바로 보이기 때문이다. 이런 검사를 파이프라인에 넣는 방법은 [데이터 품질 검사](/posts/data-quality-checks)에서 다룬다.

## 숫자의 뜻을 한 칸에 모은다

데이터 웨어하우스 설계는 결국 "이 숫자는 무슨 뜻인가"를 한 곳에서 정하는 일이다. 원본은 브론즈에 그대로 두어 언제든 다시 계산할 수 있게 하고, 정제는 실버에서 한 번 하고, 회사가 쓰는 지표는 골드에서 한 번만 정의한다. 중앙부터 짓든 마트부터 짓든 공통 차원과 공통 정의를 지켜야 마트가 따로 놀지 않는다. 저장과 계산이 떨어진 클라우드 웨어하우스에서는 덜 읽는 것이 곧 빠르고 싼 것이라, 파티션과 컬럼을 고르는 습관이 설계의 일부다.

## 면접에서 나올 만한 질문

### 데이터 레이크, 웨어하우스, 레이크하우스는 어떻게 다른가?

레이크는 원본을 파일로 싸게 쌓고 읽을 때 해석하는 곳이라 무엇이든 넣을 수 있지만 관리하지 않으면 늪이 된다. 웨어하우스는 넣을 때 스키마를 정하고 SQL 분석에 맞춘 DB라 빠르고 관리가 쉽지만 비정형 데이터가 어렵고 레이크와 사본이 이중으로 생긴다. 레이크하우스는 Delta Lake·Iceberg 같은 테이블 포맷으로 레이크 파일에 트랜잭션과 스키마 관리를 얹어, 한 벌의 데이터를 여러 엔진이 함께 쓰게 한다.

### 브론즈·실버·골드로 나누는 이유는?

브론즈에 원본을 그대로 남겨 두면 변환 규칙이 바뀌거나 버그가 나도 처음부터 다시 계산할 수 있다. 실버에서 타입·중복·시간대·키 맞추기 같은 정제를 한 번만 하니 골드 테이블마다 같은 로직을 반복하지 않는다. 골드에서는 지표의 뜻을 한 번만 정의해 모두가 같은 숫자를 본다. 칸마다 저장과 변환 비용이 드니 규모가 작으면 두 칸으로 시작해도 된다.

### 인먼 방식과 킴볼 방식의 차이는?

인먼은 회사 전체를 정규화된 중앙 웨어하우스로 먼저 통합하고 거기서 부서 마트를 뽑는다. 정의가 한 곳에서 맞지만 처음 결과까지 오래 걸린다. 킴볼은 업무 과정마다 스타 스키마 마트를 빠르게 짓고, 날짜·회원 같은 공통 차원을 공유해 마트끼리 맞춘다. 요즘은 실버에서 가볍게 통합하고 골드를 차원 모델로 짓는 혼합형이 흔하다.

### 데이터 마트를 따로 두는 이유는?

부서가 자기 업무 용어로 된 작은 테이블 묶음만 보면 되니 쓰기 쉽고, 마트 단위로 권한과 마스킹을 나누기 쉽고, 미리 묶어 둔 작은 테이블을 읽으니 빠르고 싸다. 다만 마트를 원본에서 따로 끌어다 지으면 부서마다 지표가 달라지므로, 공통 정제 칸이나 공통 차원에서 뽑아야 한다.

### 저장과 계산을 분리하면 무엇이 좋아지나?

저장과 계산을 따로 늘리고 줄일 수 있어서, 데이터가 많아도 계산은 쓸 때만 빌린다. 같은 데이터를 적재용과 대시보드용 클러스터가 따로 읽어 서로 자원을 다투지 않는다. 그 대신 계산 쪽이 저장소에서 데이터를 가져오는 비용이 생겨, 파티션과 컬럼 건너뛰기로 덜 읽는 설계가 성능과 요금을 좌우한다.

### BigQuery에서 SELECT * 에 LIMIT 10을 붙이면 비용이 줄어드나?

on-demand 요금은 쿼리가 참조한 컬럼의 처리 바이트로 매기므로 `LIMIT`으로는 줄지 않는다. 필요한 컬럼만 고르고, 파티션 조건을 걸고, 클러스터링으로 읽는 블록을 줄여야 한다. 돌리기 전에 dry run으로 처리할 바이트를 확인하고, 파티션 조건 없는 쿼리를 막는 옵션을 쓸 수 있다.

### 데이터 허브와 데이터 웨어하우스는 무엇이 다른가?

웨어하우스는 분석을 위해 데이터를 모으고 이력을 쌓아 사람과 분석 도구가 읽는다. 데이터 허브는 운영 시스템 사이에서 데이터를 표준 형식으로 주고받는 중간 지점이라, 현재 상태와 전달·권한 규칙이 관심사다. 기준 정보를 한 곳에서 관리해 나눠 주는 역할을 맡기도 하고, 요즘은 이벤트 플랫폼이 그 역할을 많이 대신한다.

### 대시보드 숫자가 재무 보고서와 다르다면 어디부터 보나?

먼저 정의가 같은지 본다. 취소·환불, 부가세, 시간대, 기준 날짜가 대부분의 원인이다. 정의가 같으면 골드 테이블의 마지막 갱신 시각을 보고, 그다음 실버와 브론즈의 같은 날짜 행 수와 합계를 비교해 어느 칸에서 숫자가 달라졌는지 좁힌다. 이 비교를 바로 하려면 칸마다 날짜별 행 수와 합계를 남겨 둔다.
