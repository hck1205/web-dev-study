운영자 계정 하나가 피싱에 걸렸다고 해 보자. 그 계정으로 클라우드 콘솔에 들어가면 운영 DB 스냅숏을 내려받을 수 있고, CI의 비밀 값을 볼 수 있고, 백업 버킷을 지울 수 있다. 공격자는 DB를 빼 가고, 배포 파이프라인에 코드를 한 줄 끼워 넣고, 나가면서 백업을 지운다. 계정 하나가 털렸을 뿐인데 데이터가 새고, 서비스 코드가 바뀌고, 복구할 수단까지 사라졌다.

과장된 이야기가 아니다. 2014년 소스 코드 호스팅 회사 Code Spaces는 AWS 콘솔 계정을 빼앗긴 뒤 공격자가 서버와 백업을 지워 버려 회사 문을 닫았다. 백업이 같은 계정 안에 있었다. 2019년 Capital One 사고에서는 웹 방화벽의 SSRF 취약점으로 EC2 인스턴스의 역할 자격 증명이 새었고, 그 역할이 필요 이상으로 많은 S3 버킷을 읽을 수 있어서 약 1억 명의 정보가 나갔다. 둘 다 처음 뚫린 곳보다 그 뒤에 열려 있던 것들이 피해를 키웠다.

이 글은 이런 사고를 읽고 설계를 고칠 때 쓰는 기본 원칙 네 가지를 다룬다. 무엇을 지키는지 나누는 CIA, 여러 겹으로 막는 심층 방어, 필요한 만큼만 주는 최소 권한, 칸을 나눠 번지지 않게 하는 격리다. 개별 공격 기법은 [OWASP Top 10 지도](/posts/owasp-top-10-map)에서 칸별로 정리했고, 네트워크 위치를 믿지 않는 설계는 [제로 트러스트 글](/posts/zero-trust-architecture)에 있다. 여기서는 그 글들이 공통으로 기대는 생각의 틀을 세운다. 명령 예시는 Ubuntu 24.04에서 돌렸다.

## 무엇을 지키는지부터 나눈다

"보안이 뚫렸다"는 말은 너무 넓다. 사고를 세 가지로 나눠 보면 무엇을 막아야 하는지가 달라진다. 이 셋의 머리글자를 따서 CIA라고 부른다.

- 기밀성(Confidentiality): 볼 권한이 없는 사람이 정보를 본다. DB 유출, 로그에 찍힌 토큰, 공개로 열린 버킷.
- 무결성(Integrity): 바뀌면 안 되는 것이 몰래 바뀐다. 주문 금액 조작, 배포 파일에 심은 백도어, 지워진 감사 로그.
- 가용성(Availability): 써야 할 때 쓸 수 없다. DDoS, 랜섬웨어로 잠긴 디스크, 지워진 백업, 인증서 만료.

처음 장면을 이 셋으로 나누면 이렇게 된다. 스냅숏을 빼 간 것은 기밀성, 파이프라인에 코드를 끼워 넣은 것은 무결성, 백업을 지운 것은 가용성이 깨진 것이다. 계정 하나가 세 축을 한꺼번에 무너뜨렸다는 게 이 사고의 무서운 점이다.

로그를 점선으로 그린 건 로그가 막는 수단이 아니라 알아채는 수단이라서다. 막는 겹이 모두 뚫려도 무엇이 언제 빠져나갔는지 알아야 피해 범위를 정하고 고객에게 알릴 수 있다. 무결성과 가용성을 따로 떼어 내지 못하는 사고도 있다. 랜섬웨어는 데이터를 바꿔서(무결성) 못 쓰게 만들고(가용성), 요즘은 먼저 빼 간 뒤 공개하겠다고 협박하니(기밀성) 세 축을 다 건드린다.

## 기밀성: 볼 수 없어야 할 사람이 본다

기밀성 사고의 대부분은 암호가 깨져서가 아니라 열려 있어서 생긴다. 공개로 설정된 버킷, 인증 없이 열린 관리 페이지, 로그와 에러 응답에 찍힌 토큰, 필요 이상으로 넓은 권한을 가진 서비스 계정이다. 그래서 기밀성의 첫 수단은 접근 통제다. 누구인지 확인하고(인증), 그 사람이 이걸 볼 수 있는지 판단한다(인가). 둘의 차이는 [인증과 인가 글](/posts/authn-vs-authz)에 있다.

암호화는 접근 통제가 미치지 않는 곳을 막는다. 네트워크 중간에서 엿보는 것은 [전송 중 암호화](/posts/encryption-in-transit)가, 디스크나 백업 파일이 통째로 새는 것은 [저장 시 암호화](/posts/encryption-at-rest)가 막는다. 저장 시 암호화가 막지 못하는 것도 분명히 알아야 한다. 앱이 정상적으로 복호화해서 읽는 경로를 공격자가 차지하면, 공격자도 평문을 본다. 처음 장면의 콘솔 계정이 DB 스냅숏을 내려받을 권한과 그 스냅숏을 풀 키 권한을 둘 다 갖고 있었다면, 암호화는 아무것도 막지 못한다. 키를 누가 쓸 수 있는지가 기밀성의 진짜 경계다.

## 무결성: 바뀌면 안 되는 것이 바뀐다

무결성은 "받은 것이 원래 그것인가"를 묻는다. 가장 단순한 도구는 해시다. 내용이 한 글자라도 바뀌면 해시가 완전히 달라진다.

```bash
printf 'release v1.4.2\n' > app.tar
sha256sum app.tar > SHA256SUMS          # 배포할 때 해시를 함께 남긴다
sha256sum -c SHA256SUMS                 # 받는 쪽에서 확인한다
printf 'release v1.4.2 + backdoor\n' > app.tar   # 누군가 파일을 바꿨다
sha256sum -c SHA256SUMS; echo "rc=$?"
```

```text
app.tar: OK
app.tar: FAILED
sha256sum: WARNING: 1 computed checksum did NOT match
rc=1
```

여기서 한 겹 더 생각해야 한다. 공격자가 `app.tar`를 바꿀 수 있는 곳이라면 `SHA256SUMS`도 바꿀 수 있다. 같은 곳에 둔 해시는 실수로 깨진 파일은 잡아도 일부러 바꾼 파일은 못 잡는다. 그래서 해시 목록에 서명을 하고, 서명 키는 배포 서버가 아닌 곳에 둔다. 해시와 서명의 차이는 [해시와 HMAC 글](/posts/hash-hmac-password-hashing)에서 다뤘다. OpenSSH 8.0부터 들어간 `ssh-keygen -Y`로 바로 해 볼 수 있다.

```bash
ssh-keygen -q -t ed25519 -N "" -C "release-signing" -f ./release-key   # 서명 키. 실제로는 배포 서버 밖에 둔다
ssh-keygen -Y sign -f ./release-key -n file SHA256SUMS                  # SHA256SUMS.sig가 생긴다
echo "release@example.com $(cat release-key.pub)" > allowed_signers     # 받는 쪽은 공개 키만 안다
ssh-keygen -Y verify -f allowed_signers -I release@example.com -n file -s SHA256SUMS.sig < SHA256SUMS
```

```text
Signing file SHA256SUMS
Write signature to SHA256SUMS.sig
Good "file" signature for release@example.com with ED25519 key SHA256:kraqoLGMxJG722UBHiVgUK/2jvrce3GI+qk6x4Vo/Ko
```

이번에는 공격자가 파일을 바꾸고 해시 목록까지 새로 만들어 덮어썼다고 하자. 해시만 보면 들키지 않는다. 서명은 다르다.

```bash
printf 'release v1.4.2 + backdoor\n' > app.tar
sha256sum app.tar > SHA256SUMS       # 해시 목록도 맞춰서 바꿨다
sha256sum -c SHA256SUMS              # 해시 검사는 통과한다
ssh-keygen -Y verify -f allowed_signers -I release@example.com -n file -s SHA256SUMS.sig < SHA256SUMS; echo "rc=$?"
```

```text
app.tar: OK
Signature verification failed: incorrect signature
Could not verify signature.
rc=255
```

비밀 키가 없으니 바뀐 목록에 맞는 서명을 만들 수 없다. 무결성을 지키는 힘은 해시 알고리즘이 아니라 서명 키가 공격자 손 밖에 있다는 사실에서 나온다. 이게 이 글에서 계속 나올 생각이다. 검증하는 수단이 검증받는 대상과 같은 손에 있으면 겹이 하나 줄어든다.

웹 서비스에서 무결성이 깨지는 자리는 더 흔하다. 요청 본문의 가격을 그대로 믿는 주문 API, 클라이언트가 보낸 `role=admin`을 받아 주는 회원 수정, 누구나 쓸 수 있는 감사 로그 테이블이다. 서버가 계산해야 할 값을 클라이언트에서 받으면 무결성은 클라이언트의 선의에 기대게 된다.

## 가용성: 써야 할 때 쓸 수 없다

가용성은 보안 이야기에서 가장 덜 대접받는 축이다. 하지만 사용자 입장에서는 데이터가 샌 것보다 서비스가 안 되는 것을 먼저 느낀다. 위협은 공격만이 아니다. 트래픽 폭주, 하드웨어 고장, 만료된 인증서, 운영자의 `rm -rf`도 가용성 사고다. 공격으로는 [DDoS](/posts/ddos-protection), 랜섬웨어, 그리고 처음 장면처럼 권한을 얻은 뒤 지우는 것이 있다.

가용성을 지키는 수단은 이중화와 백업, 속도 제한이다. 여기서도 같은 손 문제가 나온다. Code Spaces는 백업이 있었지만 운영 계정과 같은 계정 안에 있었다. 운영 계정을 쥔 사람이 백업도 지울 수 있다면 그 백업은 실수에는 대비가 되지만 공격에는 대비가 되지 않는다. 백업은 다른 계정에, 지울 수 없게(객체 잠금, 버전 관리) 두고, 운영 계정에는 쓰기만 주고 지우기는 주지 않는다. 몇 벌을 어디에 두는지는 [백업 전략 글](/posts/backup-strategy)에, 장애를 견디는 구조는 [고가용성 글](/posts/high-availability)에 있다.

## 세 축은 서로 당긴다

세 축을 모두 최대로 올릴 수는 없다. 하나를 올리면 다른 하나가 내려가는 자리가 있다.

기밀성과 가용성이 가장 자주 부딪힌다. 데이터를 강하게 암호화하고 키를 한 곳에 엄격하게 묶어 두면, 키 관리 서비스가 멈추는 순간 서비스 전체가 데이터를 읽지 못한다. 키를 잃어버리면 데이터도 영영 잃는다. 로그인 실패 다섯 번에 계정을 잠그는 정책은 비밀번호 대입을 막지만(기밀성), 공격자가 남의 아이디로 일부러 다섯 번 틀려서 진짜 사용자를 못 들어오게 만들 수도 있다(가용성). 그래서 계정 잠금 대신 점점 늘어나는 지연과 IP별 속도 제한, 그리고 다단계 인증을 함께 쓴다.

무결성과 가용성도 당긴다. 모든 쓰기를 여러 곳에서 확인하고 서명을 검증하면 느려지고, 검증 서버가 죽으면 쓰기가 멈춘다. 반대로 장애 때 검증을 건너뛰고 통과시키는(fail-open) 설정은 가용성을 지키는 대신 무결성을 내준다. 인증 서버가 응답하지 않을 때 요청을 통과시킬지 막을지는 기술이 아니라 판단의 문제다. 결제는 막고(fail-closed), 추천 목록은 통과시킨다는 식으로 데이터의 성격에 따라 정한다.

기밀성과 무결성은 대개 같은 방향이지만, 감사 로그에서는 당긴다. 무결성을 위해 모든 것을 자세히 남기면 로그에 개인 정보와 토큰이 쌓여 기밀성 위험이 된다. 로그에 남길 것과 가릴 것을 정해 두는 이유다.

## 한 겹이 뚫려도 다음 겹이 막는다

심층 방어(defense in depth)는 "어떤 겹이든 언젠가 뚫린다"는 가정에서 출발한다. 완벽한 방화벽, 완벽한 코드, 완벽한 직원은 없다. 그러니 겹을 여러 개 두고, 하나가 뚫려도 다음 겹이 막거나 적어도 늦추고 알리게 한다.

요청이 지나는 길에 겹을 얹어 보면 이렇다. 아래 그림에서 단계를 넘기면 같은 공격이 겹마다 어떻게 걸리는지 볼 수 있다. 공격자가 앱의 취약점으로 코드를 실행하게 됐다고 가정한 경로다.

그림에서 공격자는 첫 겹을 한 번 지나갔지만 그 뒤로는 한 칸도 넓히지 못했다. 각 겹이 실패해도 피해가 그 칸에서 멈춘다. 둘째 겹은 리눅스 사용자 권한으로 직접 확인할 수 있다. 앱이 root로 돌 때와 전용 사용자로 돌 때, 같은 명령의 결과가 다르다.

```bash
id                                   # 지금은 root다
head -c 0 /etc/shadow && echo "root can read shadow"
# 같은 명령을 권한 없는 사용자(nobody)로 바꿔 실행한다
setpriv --reuid=65534 --regid=65534 --clear-groups id
setpriv --reuid=65534 --regid=65534 --clear-groups cat /etc/shadow; echo "rc=$?"
setpriv --reuid=65534 --regid=65534 --clear-groups touch /etc/cron.d/evil; echo "rc=$?"
```

```text
uid=0(root) gid=0(root) groups=0(root)
root can read shadow
uid=65534(nobody) gid=65534(nogroup) groups=65534(nogroup)
cat: /etc/shadow: Permission denied
rc=1
touch: cannot touch '/etc/cron.d/evil': Permission denied
rc=1
```

root로 도는 앱이 뚫리면 공격자는 비밀번호 해시를 읽고, `/etc/cron.d`에 파일을 넣어 재부팅 뒤에도 살아남는다. 전용 사용자로 도는 앱이 뚫리면 그 사용자가 쓸 수 있는 곳까지만 간다. 같은 취약점이라도 피해가 다르다. 컨테이너에서 이 겹을 더 두껍게 하는 설정(capability 빼기, 읽기 전용 루트, seccomp)은 [securityContext 글](/posts/k8s-security-context)에 있다.

## 겹은 서로 다른 종류여야 한다

겹을 세 개 둬도 셋이 같은 이유로 뚫리면 한 겹이나 마찬가지다. 이걸 놓치기 쉽다. WAF, API 게이트웨이, 앱이 모두 같은 정규식으로 입력을 검사한다면, 그 정규식을 우회하는 입력 하나가 세 겹을 동시에 지나간다. 관리자 콘솔, DB, 백업이 모두 같은 SSO 계정 하나로 열린다면 그 계정이 털리는 순간 세 겹이 동시에 열린다. 처음 장면이 바로 이 모양이다.

그래서 겹을 고를 때는 종류를 섞는다. 네트워크 경계([보안 그룹](/posts/security-groups-nacl)), 신원 확인(MFA), 권한(IAM, DB 역할), 데이터 보호(암호화, 서명), 실행 환경(사용자, 컨테이너 격리)처럼 서로 다른 메커니즘이 다른 실패 이유를 갖도록 한다. 입력 검증 하나만 보더라도 엣지의 패턴 검사와 앱의 파라미터 바인딩은 다른 종류라서, [SQL 주입 글](/posts/sql-injection)에서 본 것처럼 바인딩이 있으면 WAF가 놓친 입력도 쿼리가 되지 못한다.

또 하나는 막는 겹만으로는 부족하다는 것이다. 겹마다 "막았다"는 기록이 남고 누군가 그걸 보고 있어야 한다. 그림의 마지막 단계에서 거부된 호출이 경보가 되지 않으면, 공격자는 시간을 들여 다른 길을 계속 찾는다. 막고, 알아채고, 대응하는 것까지가 심층 방어다. 쿠버네티스라면 [감사 로그](/posts/k8s-audit-logging)가 그 기록을 남긴다.

심층 방어에는 비용이 든다. 겹이 늘면 지연이 늘고, 설정할 곳이 늘고, 장애가 났을 때 어느 겹이 막았는지 찾기 어려워진다. "403인데 앱 로그엔 아무것도 없다"면 WAF가 막았는지, 게이트웨이가 막았는지, 보안 그룹이 막았는지 겹을 하나씩 거슬러 올라가야 한다. 겹마다 거부했을 때 무엇을 응답하고 어디에 기록하는지 정해 두면 이 추적이 빨라진다.

## 최소 권한: 필요한 만큼, 필요한 동안만

최소 권한(least privilege)은 사람이든 프로그램이든 지금 하는 일에 필요한 권한만 갖게 하는 원칙이다. 심층 방어가 겹을 늘리는 일이라면, 최소 권한은 각 겹 뒤에 놓인 것을 줄이는 일이다. 뚫렸을 때 공격자가 얻는 것은 그 주체가 가진 권한 전부라서, 권한이 작을수록 피해가 작다.

최소 권한은 세 방향으로 줄인다. 무엇을(행동과 대상: `s3:*` 대신 특정 버킷의 `GetObject`), 누구에게(사람마다 계정, 서비스마다 역할, 공용 계정 금지), 언제까지(상시 권한 대신 필요할 때 받는 임시 권한)다. 세 번째가 가장 자주 빠진다. 운영자가 1년에 두 번 쓰는 DB 관리자 권한을 늘 들고 다니면, 그 계정이 털리는 날이 1년 365일 중 어느 날이든 피해는 같다. 필요할 때 승인을 받아 한 시간만 권한을 얻는 방식(Just-In-Time 접근)이면 나머지 시간의 피해 반경이 줄어든다.

AWS에서 이 원칙이 어떻게 판정되는지는 [IAM 글](/posts/iam-basics)에서, DB에서 앱 계정의 권한을 줄이는 방법은 [PostgreSQL 역할과 보안 글](/posts/postgres-roles-security)에서, 쿠버네티스에서는 [RBAC 글](/posts/k8s-rbac)에서 다룬다. 원리는 모두 같다. 기본은 거부이고, 필요한 것만 하나씩 허락한다.

## 최소 권한은 한 번에 정해지지 않는다

현실에서 처음부터 딱 맞는 권한을 주는 일은 거의 없다. 개발 초기에는 일단 돌아가게 넓게 주고, 나중에 줄이려고 하면 무엇이 쓰이는지 몰라서 못 줄인다. 그래서 최소 권한은 설계라기보다 줄여 가는 작업이다. 순서는 대개 이렇다.

먼저 목록을 만든다. 사람 계정, 서비스 계정, API 키, CI 토큰, 배포 역할이 각각 무엇을 할 수 있는지 적는다. 이 단계에서 "누구 것인지 모르는 키"와 "퇴사자 계정"이 반드시 나온다. 그것부터 지운다.

다음은 실제 사용 기록과 맞춰 본다. 클라우드 감사 로그(AWS CloudTrail 같은)에서 지난 90일 동안 그 역할이 실제로 부른 API를 뽑고, 허락된 권한과 비교한다. AWS IAM Access Analyzer처럼 활동 기록으로 정책 초안을 만들어 주는 도구도 있다. 한 번도 안 쓴 권한은 빼는 후보다. 다만 분기마다 한 번 도는 정산 배치처럼 드물게 쓰는 권한이 있으니, 기간을 충분히 잡고 빼기 전에 담당자에게 확인한다.

빼는 것은 작게, 되돌릴 수 있게 한다. 권한을 뺀 뒤 AccessDenied가 늘어나는지 지표를 보고, 문제가 생기면 바로 되돌린다. 처음부터 거부(Deny)로 막기보다 허락 목록에서 빼는 쪽이 되돌리기 쉽다.

마지막으로 비상 통로를 따로 만든다. 모든 권한을 줄이고 나면 장애가 난 새벽에 아무도 고칠 권한이 없는 일이 생긴다. 그래서 넓은 권한을 가진 비상용(break-glass) 계정을 하나 두되, 평소에는 쓰지 않고, 쓰면 즉시 경보가 울리고, 쓴 뒤에는 비밀번호를 바꾼다. 비상 통로가 없으면 사람들은 결국 평소 계정에 넓은 권한을 다시 붙인다.

흔한 실수도 정리해 둔다. 테스트가 귀찮아 `*`를 넣고 "나중에 줄이자"고 한 뒤 잊는다. 사람마다 계정을 만들지 않고 공용 계정 하나를 돌려 써서 누가 무엇을 했는지 감사 로그로 가릴 수 없다. 서비스 하나에 역할 하나가 아니라 여러 서비스가 한 역할을 같이 써서, 한 서비스에 필요한 권한이 모든 서비스로 퍼진다. CI가 운영 계정의 장기 액세스 키를 비밀 값으로 들고 있다. 이 마지막 것은 OIDC로 임시 자격 증명을 받는 방식으로 바꿀 수 있다.

## 격리: 칸막이가 피해 반경을 정한다

격리는 칸을 나눠서 한 칸의 사고가 다른 칸으로 번지지 않게 하는 원칙이다. 배의 격벽과 같다. 한 칸에 물이 차도 배 전체가 가라앉지 않는다. 뚫렸을 때 피해가 닿는 범위를 피해 반경(blast radius)이라고 부르고, 격리는 이 반경의 경계를 긋는 일이다.

칸막이는 여러 층에 있다.

- 프로세스: 서비스마다 다른 사용자로 돌린다. 컨테이너는 네임스페이스로 보이는 것을 나누고 cgroup으로 쓰는 양을 나눈다([네임스페이스와 cgroup 글](/posts/linux-namespaces-cgroups)). seccomp와 AppArmor는 부를 수 있는 시스템 콜을 줄인다([seccomp와 AppArmor 글](/posts/seccomp-apparmor)).
- 네트워크: 서브넷과 보안 그룹, 쿠버네티스 [NetworkPolicy](/posts/k8s-network-policy)로 서로 말할 필요 없는 것끼리 길을 끊는다. 앱 서버는 DB 포트로만, DB는 아무 데로도 먼저 나가지 않게 한다.
- 계정: 운영, 스테이징, 개발을 다른 클라우드 계정으로 나누고, 백업과 감사 로그는 또 다른 계정에 둔다. 계정 경계는 클라우드에서 가장 단단한 칸막이다. 한 계정 안에서 권한을 아무리 잘 나눠도 관리자 한 명이 다 열 수 있지만, 계정이 다르면 따로 뚫어야 한다.
- 데이터: 고객마다 다른 키로 암호화하거나, 테넌트마다 행 단위 보안을 건다. 한 고객의 데이터가 새도 다른 고객의 것은 남는다.

격리는 최소 권한과 짝을 이룬다. 최소 권한이 "이 주체가 무엇을 할 수 있나"를 줄인다면, 격리는 "이 칸에서 어디까지 닿을 수 있나"를 줄인다. 앱의 권한이 아무리 작아도 같은 네트워크에 관리 포트가 열린 DB가 있으면 그쪽으로 넘어갈 수 있고, 네트워크를 아무리 나눠도 앱의 역할이 모든 버킷을 읽으면 격리는 의미가 없다. Capital One 사고는 네트워크로는 막혔어야 할 곳을, 역할 하나의 넓은 권한이 이어 버린 경우다.

서버 한 대에서 칸막이가 제대로 서 있는지는 명령 몇 개로 먼저 본다. 어떤 포트가 어느 주소에서 듣고 있는지, 어떤 프로세스가 root로 도는지다.

```bash
sudo ss -tlnp                               # 듣고 있는 TCP 포트와 프로세스
ps -eo user:10,pid,comm --sort=user | awk '$1=="root"'   # root로 도는 프로세스
```

```text
State  Recv-Q Send-Q Local Address:Port  Peer Address:PortProcess
LISTEN 0      511          0.0.0.0:3923       0.0.0.0:*    users:(("node",pid=8598,fd=21))
LISTEN 0      200        127.0.0.1:5432       0.0.0.0:*    users:(("postgres",pid=823,fd=6))
```

출력은 실험 서버에서 두 줄만 옮겼다. `Local Address`가 `127.0.0.1`이면 그 서버 안에서만 닿고, `0.0.0.0`이면 모든 인터페이스에서 받는다. DB가 `0.0.0.0`에서 듣고 있다면 앞의 보안 그룹 한 겹에만 기대고 있다는 뜻이다. 앱이 root로 돌고 있다면 위의 `setpriv` 실험에서 본 둘째 겹이 없다는 뜻이다. 둘 다 고치기 쉬운데 지나치기 쉬운 칸막이다.

## 피해 반경을 직접 세어 보기

피해 반경은 그래프로 세면 분명해진다. "A를 쥐면 B에 닿는다"는 관계를 화살표로 잇고, 털린 주체에서 화살표를 따라 닿는 모든 곳을 모으면 그게 반경이다. 사람이 그리면 놓치는 간접 경로(콘솔 → CI 비밀 → 배포 역할 → 키 → 백업)도 기계는 놓치지 않는다.

## 사고가 났을 때 네 원칙으로 묻는 순서

원칙은 설계할 때만 쓰는 게 아니다. "키가 샌 것 같다"는 연락을 받은 순간에도 같은 틀로 생각하면 첫 30분에 할 일이 정리된다.

먼저 어느 축이 깨졌는지 본다. 기밀성이면 새는 것을 멈추는 게 먼저다. 샌 키와 세션을 폐기하고, 그 키로 무엇을 읽었는지 감사 로그에서 찾는다. 무결성이면 무엇이 바뀌었는지 모르는 상태에서 그 시스템을 계속 믿으면 안 된다. 서명된 산출물이나 사고 이전 백업처럼 믿을 수 있는 출처에서 다시 세운다. 가용성이면 서비스를 살리는 게 먼저고, 원인 분석은 그다음이다. 셋이 섞여 있으면 기밀성의 확산을 먼저 막는다. 살리는 데 급급해 같은 키로 서비스를 다시 띄우면 새는 길도 같이 다시 열린다.

다음은 피해 반경을 센다. 털린 주체에서 위의 그래프처럼 닿을 수 있는 곳을 모두 적고, 감사 로그에서 실제로 닿은 곳을 표시한다. "닿을 수 있었던 곳"이 공지와 조사의 범위이고, "실제로 닿은 곳"이 복구의 범위다. 로그가 없는 칸은 닿았다고 가정해야 하니, 로그가 없을수록 반경은 넓어진다.

그리고 격리로 가둔다. 의심되는 서버를 끄지 말고(메모리의 증거가 사라진다) 보안 그룹을 모든 트래픽 거부로 바꿔 네트워크에서 떼어 낸다. 의심되는 역할에는 모든 행동을 거부하는 정책을 붙인다. 칸막이를 미리 세워 둔 시스템은 이 단계가 몇 분이면 끝나고, 모든 것이 한 계정 한 네트워크에 있는 시스템은 떼어 낼 칸이 없다.

마지막으로 다음 겹을 묻는다. 뚫린 겹을 막는 것으로 끝내지 않고, 그 뒤의 겹이 왜 막지 못했는지까지 고친다. 같은 공격이 다음에는 둘째 겹에서 멈추게 하는 것이 사고 회고의 목표다. 비밀 값이 샜을 때의 구체적인 순서는 [비밀 관리 글](/posts/secrets-management)에도 정리했다.

## 보안과 편의는 맞바꾼다

보안 원칙을 적용하면 거의 언제나 누군가 불편해진다. 권한을 줄이면 개발자가 권한 요청을 더 자주 하고, MFA를 걸면 로그인이 한 단계 늘고, 계정을 나누면 계정 사이를 오가는 설정이 생긴다. 불편이 너무 크면 사람들은 우회한다. 공용 계정을 다시 만들고, 비상 계정을 평소에 쓰고, 토큰을 슬랙에 붙인다. 우회된 보안은 문서에만 남는다.

그래서 원칙을 적용하는 순서가 중요하다. 피해가 가장 큰 곳부터, 사람이 덜 불편한 방법으로 한다. 사람 계정의 MFA, 운영과 개발 계정 분리, 백업을 다른 계정에 지울 수 없게 두기, CI의 장기 키 없애기는 불편에 비해 줄어드는 피해가 크다. 반대로 개발 환경의 모든 권한을 운영처럼 엄격하게 묶으면 불편만 크고 줄어드는 피해는 작다. 무엇을 지킬지(자산), 누가 노릴지(위협), 뚫리면 얼마나 아픈지(영향)를 먼저 따지는 작업을 위협 모델링이라고 부르는데, 거창한 문서가 아니라 이 세 질문을 서비스마다 한 번씩 묻는 것으로도 충분히 시작할 수 있다.

## 보안은 설정 하나가 아니다

현장에서 자주 듣는 말 중에 원칙과 거꾸로 가는 것들이 있다.

"WAF를 붙였으니 안전하다." WAF는 엣지의 한 겹이다. 알려진 패턴을 걸러 주지만 인가 로직의 구멍(남의 주문 번호로 조회하기)은 모른다. 정상적인 요청처럼 보이기 때문이다. WAF가 할 수 있는 일과 못하는 일은 [WAF 글](/posts/waf)에 있다.

"내부망이니까 괜찮다." 내부망은 처음 뚫린 기기 하나가 옆으로 번지는 통로가 된다. 이 가정을 버리는 것이 [제로 트러스트](/posts/zero-trust-architecture)다.

"암호화했으니 유출돼도 괜찮다." 키를 같은 손이 쥐고 있으면 그렇지 않다. 위의 기밀성 절에서 봤다.

"한 번 점검받았으니 됐다." 권한은 시간이 지나면 다시 넓어진다. 급한 장애 때 붙인 권한, 새 서비스가 빌려 쓴 역할, 퇴사자의 키가 쌓인다. 목록 만들기와 줄이기는 분기마다 다시 한다.

세 번째와 네 번째 말에서 보이듯, 보안 사고는 대개 기술 하나의 실패가 아니라 여러 겹이 같은 이유로 비어 있었던 결과다. 그래서 사고 뒤에는 "어느 겹이 뚫렸나"와 함께 "왜 다음 겹이 막지 못했나"를 묻는다.

## 처음 그 계정을 다시 보면

피싱에 걸린 운영자 계정으로 돌아가 보자. MFA가 있었다면 첫 겹에서 멈췄을 가능성이 크다(심층 방어). 그 계정이 평소에 읽기 전용이었다면 스냅숏도 CI 비밀도 볼 수 없었다(최소 권한). 백업이 다른 계정에 지울 수 없게 있었다면 서비스는 복구됐다(격리, 가용성). 배포 파이프라인이 서명된 산출물만 받았다면 끼워 넣은 코드는 운영에 닿지 못했다(무결성). 어느 하나만 있었어도 피해는 줄었다. CIA로 무엇이 깨졌는지 나누고, 겹마다 왜 막지 못했는지 묻고, 주체마다 쥔 것을 줄이고, 칸을 나눠 반경을 긋는다. 개별 보안 기술은 모두 이 네 생각 중 하나를 구현한 것이다.

## 면접에서 나올 만한 질문

### CIA 삼요소를 설명해 주세요.

기밀성은 권한 없는 사람이 정보를 보지 못하게, 무결성은 정보가 허락 없이 바뀌지 않게, 가용성은 필요할 때 쓸 수 있게 하는 것이다. 사고를 이 셋으로 나누면 막는 수단이 달라진다. 기밀성은 접근 통제와 암호화, 무결성은 해시와 서명과 서버 측 검증, 가용성은 이중화와 백업과 속도 제한이 맡는다.

### CIA 중 서로 충돌하는 것은 무엇인가요?

기밀성과 가용성이 가장 자주 부딪힌다. 키를 엄격하게 묶으면 키 서비스 장애가 곧 서비스 장애가 되고, 로그인 실패 시 계정 잠금은 대입 공격을 막지만 남의 계정을 일부러 잠그는 공격을 연다. 무결성과 가용성도 당겨서, 검증 서버가 죽었을 때 통과시킬지(fail-open) 막을지(fail-closed)를 데이터의 성격에 따라 정해야 한다.

### 심층 방어란 무엇이고, 겹을 고를 때 주의할 점은요?

어떤 겹이든 뚫린다는 가정에서 겹을 여러 개 두어, 하나가 뚫려도 다음 겹이 막거나 늦추고 알리게 하는 설계다. 주의할 점은 겹이 서로 다른 이유로 실패해야 한다는 것이다. 모든 겹이 같은 SSO 계정이나 같은 입력 검사에 기대면 한 번에 다 열린다. 그리고 거부한 기록을 누군가 보고 대응해야 겹이 의미를 가진다.

### 심층 방어와 제로 트러스트는 어떻게 다른가요?

심층 방어는 여러 겹을 쌓는다는 구조에 대한 원칙이고, 제로 트러스트는 그중 "네트워크 위치를 믿지 않고 요청마다 신원과 기기 상태를 확인한다"는 신뢰 판단에 대한 원칙이다. 경계 방화벽 하나에 기대는 구조도 겹을 더하면 심층 방어일 수 있지만, 내부망을 믿는 한 제로 트러스트는 아니다. 실제로는 제로 트러스트를 심층 방어의 한 겹 한 겹에 적용한다고 보면 된다.

### 최소 권한을 실제로 어떻게 적용하나요?

처음부터 정확히 주기는 어려워서 줄여 가는 작업으로 한다. 사람과 서비스의 권한 목록을 만들고, 감사 로그의 실제 사용 기록과 비교해 안 쓰는 권한을 작게, 되돌릴 수 있게 뺀다. 상시 권한은 필요할 때 받는 임시 권한으로 바꾸고, 대신 경보가 걸린 비상용 계정을 따로 둔다. 공용 계정, 와일드카드 권한, CI의 장기 키가 먼저 없앨 대상이다.

### 피해 반경(blast radius)을 줄이는 방법은요?

한 주체가 뚫렸을 때 닿는 범위를 줄이는 것이다. 최소 권한으로 그 주체가 쥔 것을 줄이고, 격리로 그 칸에서 갈 수 있는 길을 끊는다. 프로세스는 전용 사용자와 컨테이너로, 네트워크는 서브넷과 NetworkPolicy로, 클라우드는 계정 분리로 나눈다. 백업과 감사 로그를 운영 계정 밖에 지울 수 없게 두는 것이 가장 효과가 큰 격리 중 하나다.

### 백업이 있는데도 랜섬웨어나 계정 탈취에 무력한 경우는요?

백업을 운영과 같은 손이 지우거나 덮어쓸 수 있을 때다. 같은 클라우드 계정, 같은 관리자 권한, 마운트된 백업 디스크라면 공격자가 운영을 쥐는 순간 백업도 쥔다. 다른 계정에 객체 잠금이나 버전 관리를 건 채로 두고, 운영 쪽에는 쓰기만 주고 삭제는 주지 않으며, 복구 연습으로 실제로 되살릴 수 있는지 확인한다.
