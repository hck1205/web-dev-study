  부품마다 유리 진열장이 하나씩 있다고 생각하면 쉽다. 진열장 안에 넣은 장식은 바깥 사람이 함부로 손댈 수 없다. 그래서 페이지 전체에 "버튼은 빨갛게" 같은 규칙이 있어도 진열장 안 버튼은 그 규칙을 받지 않는다.

  진열장 안에서 버튼을 누르면 바깥에서는 "진열장이 눌렸다"고만 보인다. 안쪽 구조를 숨기기 위해서다. 이 글은 이 진열장이 어떻게 생겼고 어디까지 막고 어디를 열어 두는지 직접 확인해 본다.

디자인 시스템 팀이 버튼 하나를 만들었다. 문제는 그 버튼을 쓰는 앱이 셋이라는 것이다. 하나는 React, 하나는 Vue, 하나는 서버가 그리는 오래된 관리자 페이지다. 프레임워크마다 버튼을 따로 만들면 같은 버그를 세 번 고친다. 그래서 프레임워크에 묶이지 않는 `<ds-button>` 태그로 만들기로 했다.

처음 만든 버전은 클래스 이름을 잘 지은 평범한 DOM이었다. 관리자 페이지에 붙이자마자 깨졌다. 그 페이지의 전역 CSS에 `button { color: red; border: 3px solid red; }`가 있었다. 선택자 하나가 디자인 시스템의 버튼까지 덮었다. CSS 이름 충돌을 막는 방법은 [CSS 스타일링 방식 고르기](/posts/css-styling-approaches)에서 BEM, CSS Modules 같은 규칙으로 다뤘다. 그 방법들은 모두 내 코드 쪽의 약속이다. 남의 페이지에 있는 `button` 선택자는 막지 못한다.

Web Components는 이 문제를 브라우저 기능으로 푼다. 세 가지 표준을 묶어 부르는 이름이다. 태그를 등록하는 Custom Elements, 바깥과 분리된 DOM 조각을 붙이는 Shadow DOM, 마크업을 미리 만들어 두는 `<template>`과 내용을 꽂는 `<slot>`이다. 이 글의 출력은 모두 Chromium 141에서 직접 돌려 얻었다. 마이크로 프런트엔드 리모트를 커스텀 요소로 감싸는 이야기와 React 18·19의 속성 전달 차이 실측은 [마이크로 프런트엔드 조합 방식](/posts/micro-frontend-integration-patterns)에 있으니, 여기서는 부품 자체가 어떻게 동작하는지에 집중한다.

## 태그 이름을 브라우저에 등록한다

커스텀 요소는 `HTMLElement`를 상속한 클래스다. `customElements.define`으로 태그 이름과 클래스를 짝 지으면, 그 뒤로 브라우저는 그 태그를 만날 때마다 이 클래스로 요소를 만든다.

```js
class DsButton extends HTMLElement {
  static observedAttributes = ["variant"];   // 이 속성이 바뀔 때만 콜백을 부른다

  constructor() {
    super();                                 // 반드시 맨 처음
    const root = this.attachShadow({ mode: "open" });
    root.innerHTML = `
      <style>
        :host { display: inline-block; }
        button { background: var(--ds-accent, gray); color: inherit; border: 1px solid black; }
        :host([variant="danger"]) button { background: rgb(200, 0, 0); }
      </style>
      <button part="label"><slot>기본 글자</slot></button>`;
  }
  connectedCallback() { /* 문서에 붙었다 */ }
  disconnectedCallback() { /* 문서에서 떨어졌다 */ }
  attributeChangedCallback(name, oldValue, newValue) { /* 관찰하는 속성이 바뀌었다 */ }
}

customElements.define("ds-button", DsButton);
```

이름에는 하이픈이 하나 이상 들어가야 한다. `button`이나 `dsbutton`은 등록되지 않는다. 앞으로 HTML에 새 태그가 생겨도 하이픈 없는 이름만 쓰기로 약속해 두었기 때문에 충돌이 나지 않는다. 같은 이름을 두 번 `define`하면 예외가 난다. 한 페이지에 같은 디자인 시스템 번들이 두 번 실리는 마이크로 프런트엔드 환경에서 실제로 자주 만나는 오류다. `customElements.get("ds-button")`으로 먼저 확인하고 등록하거나, 번들을 하나만 싣게 정리해야 한다.

등록하기 전에 HTML에 이미 `<ds-button>`이 있어도 괜찮다. 브라우저는 모르는 태그를 일단 평범한 `HTMLElement`로 만들어 둔다. 나중에 `define`이 불리면 그 요소들을 하나씩 클래스로 바꾼다. 이 과정을 업그레이드라고 부른다. 업그레이드 전후는 `:defined` 가상 클래스로 구분된다. 등록 전에는 내용이 날것으로 보이니 `ds-button:not(:defined) { visibility: hidden; }` 같은 규칙으로 깜빡임을 가리는 경우가 많다.

## 생명주기 콜백이 불리는 순서

콜백이 어떤 순서로 불리는지 로그를 찍었다. 페이지에 `<ds-button variant="primary">저장</ds-button>`을 먼저 두고, 그 뒤에 스크립트로 등록하고 속성을 바꾸고 새 요소를 만들어 붙였다 뗐다.

```text
--- define
constructor isConnected=true attr=primary
attributeChangedCallback variant  -> primary
connectedCallback
--- set attr
attributeChangedCallback variant primary -> danger
--- createElement
constructor isConnected=false attr=null
--- append
connectedCallback
--- remove
disconnectedCallback
```

봐야 할 곳은 두 군데다. 이미 문서에 있던 요소를 업그레이드할 때는 생성자 안에서도 `isConnected`가 `true`이고 속성도 읽힌다. 그리고 `connectedCallback`보다 `attributeChangedCallback`이 먼저 불린다. HTML에 처음부터 적힌 속성도 "없음에서 primary로 바뀐 것"으로 한 번 알려 준다. 반대로 `document.createElement`로 만들면 생성자 시점에는 문서에 없고 속성도 없다.

그래서 생성자에서는 그림자 트리를 붙이고 내부 상태를 초기화하는 일만 한다. 속성을 읽거나 자식을 건드리거나 바깥에 이벤트 리스너를 다는 일은 `connectedCallback`으로 미룬다. 명세도 생성자에서 속성이나 자식을 추가하지 말라고 정해 두었다. `createElement` 경로에서 그렇게 하면 예외가 난다.

`connectedCallback`은 한 번만 불리는 게 아니다. 요소를 다른 부모로 옮기면 `disconnectedCallback` 다음에 `connectedCallback`이 다시 불린다. 리스트를 정렬하느라 DOM 노드를 옮기는 프레임워크 안에서는 이 일이 흔하다. 그래서 `connectedCallback`에서 단 리스너나 `ResizeObserver`는 `disconnectedCallback`에서 꼭 떼야 한다. 안 떼면 옮길 때마다 리스너가 하나씩 늘어난다.

## 그림자 트리 안쪽은 바깥 선택자가 닿지 않는다

`attachShadow`는 요소에 그림자 루트(shadow root)를 붙인다. 그림자 루트 아래는 문서와 분리된 작은 DOM 트리다. 요소를 호스트(host)라고 부르고, 호스트의 원래 자식들은 라이트 DOM(light DOM)이라고 부른다.

분리됐다는 말은 두 가지 뜻이다. 첫째, 바깥 CSS 선택자가 그림자 트리 안 요소에 맞지 않는다. 둘째, 바깥에서 `document.querySelector`로 찾을 수 없다. 처음에 깨졌던 관리자 페이지를 그대로 흉내 내서 확인했다.

```html
<style>
  button { color: red; border: 3px solid red; }
  body { color: rgb(0, 0, 255); --ds-accent: rgb(0, 128, 0); font-family: serif; }
  ds-button::part(label) { text-decoration: underline; }
</style>
<ds-button id="a" variant="primary">저장</ds-button>
<button id="plain">바깥 버튼</button>
```

```text
inner color rgb(0, 0, 255) border 1px rgb(0, 0, 0) bg rgb(200, 0, 0) deco underline font Arial
plain color rgb(255, 0, 0) border 3px
querySelector from doc finds inner button? 1
```

바깥 버튼은 빨간 글자에 3px 테두리를 받았다. 그림자 트리 안 버튼은 `button` 선택자를 받지 않고 자기 스타일의 1px 검정 테두리를 지켰다. `document.querySelectorAll("button")`도 바깥 버튼 하나만 센다. 그림자 트리 안을 보려면 `host.shadowRoot.querySelector(...)`처럼 루트를 거쳐야 한다.

`mode`는 그 `shadowRoot` 프로퍼티를 열어 둘지 정한다. `open`이면 `el.shadowRoot`로 안을 볼 수 있고, `closed`면 `null`이 나온다. 확인해 보니 closed 요소의 `shadowRoot`는 정말 `null`이었다. 다만 closed가 보안 장치는 아니다. 같은 페이지의 스크립트는 `attachShadow`를 미리 바꿔치기하거나 개발자 도구로 얼마든지 들어간다. closed는 "여기는 내부 구현이니 건드리지 말라"는 표시에 가깝고, 테스트 도구와 접근성 도구, 확장 프로그램이 안을 못 봐서 생기는 불편이 더 크다. 디자인 시스템이라면 거의 언제나 `open`을 쓴다.

## 경계를 넘는 것은 상속, 변수, part 셋뿐이다

위 출력을 다시 보면 안쪽 버튼에 바깥 영향이 셋 들어왔다.

글자색이 바깥 `body`의 파란색이다. 선택자는 경계를 넘지 못하지만, 상속은 그림자 트리를 따라 그대로 흘러내린다. 호스트가 물려받은 `color`를 안쪽 요소가 다시 물려받는다. 내 스타일에서 `color: inherit`를 줬으니 버튼도 받았다. 같은 이유로 `font-family`는 상속 속성인데도 Arial이 나왔다. 버튼은 브라우저 기본 스타일에서 글꼴을 따로 정하기 때문에 원래도 `body` 글꼴을 따르지 않는다. 상속이 왜 끊기는지는 [캐스케이드와 명시도](/posts/css-cascade-specificity)의 상속 부분에서 다뤘다.

배경은 빨간 `rgb(200, 0, 0)`이다. `variant`를 danger로 바꿨기 때문에 `:host([variant="danger"])` 규칙이 이겼다. danger가 아니었다면 `var(--ds-accent, gray)`가 바깥 `body`에 적힌 초록을 받았을 것이다. CSS 변수도 상속되는 속성이라 경계를 넘는다. 변수가 왜 그렇게 동작하는지는 [CSS 변수](/posts/css-custom-properties) 글에서 따로 다룬다.

밑줄은 `::part(label)`에서 왔다. 안쪽 요소에 `part="label"`을 붙여 두면 바깥에서 `ds-button::part(label)`로 그 요소 하나를 꾸밀 수 있다. 부품을 만든 사람이 일부러 뚫어 둔 구멍이다. `::part` 뒤에는 `:hover` 같은 상태 가상 클래스는 붙일 수 있지만, `::part(label) span`처럼 그 안으로 더 내려가는 선택자는 쓸 수 없다. 구멍은 딱 그 요소까지다.

디자인 시스템 API로 보면 세 길의 쓰임새가 다르다. 색, 간격, 둥글기처럼 값 하나를 바꾸게 하려면 CSS 변수를 문서화해 열어 둔다. 레이아웃까지 바꾸게 허락할 요소에는 `part`를 붙인다. 상속은 막을 수도 없고 막을 필요도 없다. 오히려 상속을 막고 싶다면 `:host { all: initial; }`로 경계에서 끊을 수 있는데, 그러면 페이지의 글자 크기와 색까지 안 따라와서 부품이 주변에서 혼자 튀기 쉽다.

`all: initial`에도 예외가 있다. 사용자 정의 속성은 `all`의 대상이 아니라서 변수는 그대로 넘어온다. 그래서 테마 변수를 열어 둔 채 나머지만 초기화하는 조합이 가능하다.

## 호스트 스타일은 바깥 규칙에 진다

그림자 트리 안에서 호스트 요소 자체를 꾸미는 선택자가 `:host`다. 같은 호스트에 바깥 규칙도 걸리면 누가 이길까. 안쪽 `:host { color: red }`와 바깥 `ds-x { color: blue }`를 같이 걸었다.

```text
:host vs outer rgb(0, 0, 255)
:host !important vs outer rgb(255, 0, 0)
```

바깥이 이긴다. 캐스케이드는 명시도를 보기 전에 문맥을 먼저 본다. 그림자 트리 안에서 온 규칙과 바깥 문맥의 규칙이 부딪히면, 중요도가 없는 선언은 바깥이 이긴다. `!important`를 붙이면 순서가 뒤집혀 안쪽이 이긴다. 이렇게 정한 이유가 있다. `:host`에 적는 값은 "기본값"이고, 부품을 쓰는 사람이 `ds-button { display: block; margin: 8px }`처럼 덮어쓸 수 있어야 한다. 반드시 지켜야 할 값만 `!important`로 잠근다.

`:host`에 괄호를 주면 호스트의 상태에 따라 고를 수 있다. `:host([disabled])`는 속성, `:host(.compact)`는 클래스로 고른다. `:host-context(.dark)`처럼 조상을 보는 선택자도 있지만 글을 쓰는 시점에 Firefox와 Safari가 지원하지 않아서 쓰지 않는 편이 낫다. 테마는 조상에서 CSS 변수를 바꾸는 방식이면 모든 브라우저에서 된다.

## template과 slot으로 내용을 꽂는다

버튼 글자 "저장"은 어디 있을까. 그림자 트리 안이 아니라 호스트의 라이트 DOM에 그대로 있다. 그림자 트리의 `<slot>`이 그 자리에 라이트 DOM 자식을 "보여 줄" 뿐이다. 노드가 옮겨 가지 않는다.

```text
slot assigned "저장"
```

`slot.assignedNodes()`로 보면 "저장" 텍스트 노드가 할당돼 있다. 이 구조에서 세 가지가 따라 나온다.

- 꽂힌 내용은 바깥 문서의 요소라서 바깥 CSS를 그대로 받는다. 관리자 페이지에서 `span { color: red }`를 두면 슬롯에 꽂은 `span`은 빨개진다.
- 안쪽에서 꽂힌 내용을 꾸밀 때는 `::slotted(span)`을 쓴다. 이 선택자는 꽂힌 최상위 요소에만 맞고 그 자손에는 안 맞는다. 그리고 바깥 규칙에 진다.
- 프레임워크가 자식을 그려 넣어도 그림자 트리를 건드리지 않으니 React나 Vue가 관리하는 DOM과 충돌하지 않는다.

이름 있는 슬롯은 자리를 여러 개 만든다. 안쪽에 `<slot name="icon">`을 두면 바깥에서 `<svg slot="icon">`으로 그 자리에 꽂는다. 이름 없는 슬롯은 `slot` 속성이 없는 나머지 자식을 받는다. 슬롯 안에 적은 내용("기본 글자")은 꽂힌 게 없을 때만 보이는 대체 내용이다. 내용이 바뀌는 순간을 알고 싶으면 `slotchange` 이벤트를 듣는다.

`<template>`은 슬롯과 짝으로 자주 나온다. `<template>` 안의 마크업은 파싱은 되지만 렌더링되지 않고, 이미지도 불러오지 않고, 스크립트도 실행되지 않는다. 위 예제처럼 생성자마다 `innerHTML` 문자열을 파싱하는 대신, 템플릿을 한 번 만들어 두고 요소마다 복제하면 파싱 비용을 한 번만 치른다.

```js
const tpl = document.createElement("template");
tpl.innerHTML = `<style>/* ... */</style><button part="label"><slot></slot></button>`;

class DsButton extends HTMLElement {
  constructor() {
    super();
    this.attachShadow({ mode: "open" }).append(tpl.content.cloneNode(true));
  }
}
```

스타일도 같은 이유로 공유하는 편이 낫다. 요소마다 `<style>`을 넣으면 버튼 200개에 스타일 시트가 200벌 생긴다. `new CSSStyleSheet()`로 만든 시트를 `shadowRoot.adoptedStyleSheets = [sheet]`로 붙이면 한 벌을 모든 인스턴스가 나눠 쓴다. 생성 가능한 스타일 시트(Constructable Stylesheets)라고 부르고, 현재 주요 브라우저가 모두 지원한다.

## 이벤트는 경계에서 주인이 바뀐다

안쪽 버튼을 클릭하고 그림자 루트와 문서에서 각각 `event.target`을 찍었다.

```text
shadowRoot saw target= BUTTON
document saw target= DS-BUTTON composedPath= BUTTON > #document-fragment > DS-BUTTON > BODY > HTML
```

같은 이벤트인데 그림자 루트 안에서는 대상이 `BUTTON`이고, 문서에서는 `DS-BUTTON`이다. 이벤트가 경계를 넘어 바깥으로 나갈 때 대상을 호스트로 바꿔 보여 준다. 이걸 리타깃(retarget)이라고 부른다. 안쪽 구조를 바깥에 드러내지 않으려는 장치다. 진짜 경로는 `event.composedPath()`로 볼 수 있다. 단, closed 모드면 경로에서도 안쪽 노드가 빠진다.

아래 그림은 클릭 하나가 안쪽 버튼에서 출발해 문서까지 올라가는 동안, 각 지점의 리스너가 보는 `event.target`이 어떻게 바뀌는지 따라간다.

클릭 같은 브라우저 기본 UI 이벤트는 경계를 넘도록 만들어져 있다. 그런데 내가 `dispatchEvent`로 보내는 `CustomEvent`는 기본값이 경계를 넘지 않는다. `composed` 옵션이 `false`이기 때문이다. 세 가지로 보내 봤다.

```js
inner.dispatchEvent(new CustomEvent("ds-select", { bubbles: true }));                  // 1
inner.dispatchEvent(new CustomEvent("ds-select", { bubbles: true, composed: true }));  // 2
```

```text
doc got ds-select composed= true
```

문서에 도착한 건 2번뿐이다. 1번은 `bubbles: true`인데도 그림자 루트에서 멈췄고, 호스트 요소에 단 리스너조차 받지 못했다. 호스트는 그림자 트리 바깥에 있기 때문이다. 부품을 쓰는 사람이 `ds-button`에 리스너를 달고 아무 이벤트도 안 온다고 할 때 가장 먼저 의심할 곳이 여기다.

부품의 공개 이벤트를 만드는 방법은 둘이다. 안쪽 요소에서 `bubbles: true, composed: true`로 보내거나, 호스트 자신(`this.dispatchEvent`)에서 보낸다. 호스트에서 보내면 처음부터 바깥 트리에 있으니 `composed`가 없어도 된다. 안쪽 구조를 숨기려면 두 번째가 깔끔하다. 이벤트 버블링과 캡처 단계 자체는 [이벤트 전파](/posts/event-propagation)에서 다뤘다. 리타깃 때문에 이벤트 위임 코드에서 `event.target.closest(...)`가 안쪽 요소를 못 찾는 일도 생긴다. 위임하는 쪽이 그림자 트리 바깥이면 `composedPath()`를 훑어야 한다.

## 폼에 끼려면 ElementInternals

별점을 고르는 `<ds-rating>`을 만들어 `<form>` 안에 넣으면, 기본으로는 제출 값에 들어가지 않는다. 그림자 트리 안에 `<input>`을 넣어도 마찬가지다. 그 입력은 바깥 폼과 다른 트리에 있다. 예전에는 라이트 DOM에 숨은 `<input type="hidden">`을 만들어 값을 복사하는 방법을 썼다.

지금은 폼 연동 커스텀 요소(form-associated custom element)로 만든다. `static formAssociated = true`를 선언하고 `attachInternals()`로 받은 객체에 값과 유효성을 알려 준다.

```js
class DsRating extends HTMLElement {
  static formAssociated = true;
  #internals = this.attachInternals();

  set value(v) {
    this._v = v;
    this.#internals.setFormValue(String(v));       // FormData에 들어갈 값
    if (v < 1) this.#internals.setValidity({ valueMissing: true }, "별점을 고르세요");
    else this.#internals.setValidity({});            // 빈 객체면 유효
  }
  formResetCallback() { this.value = 0; }          // form.reset() 때 불린다
}
```

```text
FormData [["score","0"],["memo","좋음"]]
checkValidity false 별점을 고르세요
FormData [["score","4"],["memo","좋음"]] valid true form===f true
formResetCallback
after reset [["score","0"],["memo","좋음"]]
```

`name` 속성만 주면 `FormData`에 값이 들어가고, `checkValidity()`가 내 규칙을 따르며, `form.reset()`도 전달된다. 제출 전 검사, `:invalid` 스타일, 브라우저 기본 오류 말풍선이 모두 일반 입력과 같이 동작한다. [React 폼과 액션](/posts/react-forms-actions)처럼 `FormData`를 그대로 서버로 보내는 흐름에도 끼워 넣을 수 있다. `ElementInternals`는 `role`, `ariaLabel` 같은 기본 접근성 값을 호스트에 속성으로 붙이지 않고 정하는 데도 쓴다. 사파리는 16.4부터 지원한다.

## 서버에서 그리려면 선언형 Shadow DOM

`attachShadow`는 자바스크립트 함수다. 그러니 서버가 그린 HTML에는 그림자 트리가 없고, 스크립트가 받아져 실행될 때까지 부품 내용이 비어 있거나 스타일 없이 보인다. 서버 렌더링으로 첫 화면을 빨리 그리려는 사이트에는 큰 약점이었다.

선언형 Shadow DOM(Declarative Shadow DOM)은 HTML만으로 그림자 루트를 만든다. `<template shadowrootmode="open">`을 호스트의 첫 자식으로 두면 HTML 파서가 그 템플릿을 그림자 루트로 바꿔 붙인다.

```html
<ds-card>
  <template shadowrootmode="open">
    <style>p { border: 2px solid rgb(0, 128, 0); }</style>
    <p><slot name="title"></slot></p>
    <slot></slot>
  </template>
  <span slot="title">제목</span>본문
</ds-card>
```

```text
before define: shadowRoot? true border rgb(0, 128, 0)
defined?  :defined matches? false
```

클래스를 등록하기도 전에 그림자 루트가 있고 스타일도 적용돼 있다. 자바스크립트 없이 캡슐화된 모습이 먼저 그려진다. 나중에 클래스가 등록되면 생성자에서 `this.shadowRoot`가 이미 있는지 보고, 있으면 새로 만들지 말고 그대로 이어서 쓴다. 이 순서가 하이드레이션과 같은 문제다. 서버가 그린 결과를 버리지 않고 재사용해야 한다([하이드레이션](/posts/hydration)).

여기에 함정이 둘 있었다.

```text
ctor existing root? true
attachShadow returned same? true children kept 0
```

이미 선언형 루트가 있는 요소에서 `attachShadow`를 또 부르면 예외 없이 같은 루트를 돌려주지만, 그 안을 비운다. 서버가 그린 내용이 사라지고 깜빡인다. 그래서 생성자는 `this.shadowRoot ?? this.attachShadow(...)`처럼 있는지부터 확인해야 한다.

두 번째로, 이 문법은 HTML 파서가 처음 읽을 때만 동작한다.

```text
innerHTML DSD shadowRoot? false
setHTMLUnsafe DSD shadowRoot? true
```

`innerHTML`로 같은 문자열을 넣으면 그림자 루트가 생기지 않고 평범한 `<template>`으로 남는다. 크롬 콘솔에 `setHTMLUnsafe()`나 `parseHTMLUnsafe()`를 쓰라는 경고도 뜬다. 클라이언트에서 서버 HTML 조각을 받아 끼우는 코드라면 이 차이 때문에 화면이 깨진다. 선언형 Shadow DOM은 크롬 계열 111 이후, 사파리 16.4, 파이어폭스 123부터 `shadowrootmode` 문법을 지원한다. Lit은 `@lit-labs/ssr`로 이 형태의 HTML을 서버에서 만들어 준다.

## 프레임워크 안에 넣을 때 막히는 곳

커스텀 요소는 결국 DOM 요소라서 어느 프레임워크든 태그로 쓸 수 있다. 막히는 곳은 값과 이벤트를 넘기는 방식이다.

React는 18까지 커스텀 요소에 모든 값을 문자열 속성으로 넘겼다. 배열을 주면 `"키보드,마우스"` 같은 문자열이 되고, `onCheckout`처럼 쓴 이벤트 핸들러는 연결되지 않아서 `ref`로 요소를 잡고 `addEventListener`를 직접 불러야 했다. React 19부터는 요소에 같은 이름의 프로퍼티가 있으면 프로퍼티로 넘기고, `on`으로 시작하는 함수는 이벤트 리스너로 단다. 실제로 어떤 값이 어떻게 넘어가는지와 이벤트 이름 대소문자 함정은 [마이크로 프런트엔드 조합 방식](/posts/micro-frontend-integration-patterns)에서 18.3.1과 19.2.0을 나란히 돌린 결과로 확인했다. Vue와 Svelte, Angular는 오래전부터 프로퍼티 바인딩과 커스텀 이벤트 바인딩을 따로 문법으로 제공했다.

타입도 손이 간다. TypeScript는 `<ds-button>`을 모르니 JSX에서 오류를 낸다. React 19 타입에서는 `react`의 `JSX.IntrinsicElements`를 모듈 보강으로 늘려 태그와 속성 타입을 알려 준다. 커스텀 요소 매니페스트(`custom-elements.json`)를 만들어 두면 이 타입과 문서를 자동으로 뽑는 도구들이 있다.

접근성에서도 경계가 문제가 된다. `aria-labelledby`, `aria-describedby`, `<label for>` 같은 id 참조는 그림자 경계를 넘지 못한다. 바깥의 `<label for="email">`은 그림자 트리 안의 `<input id="email">`을 찾지 못한다. 그래서 라벨을 슬롯으로 받아 안에서 연결하거나, 폼 연동 요소로 만들어 호스트 자체가 라벨을 받게 한다. 포커스는 `attachShadow({ mode: "open", delegatesFocus: true })`를 주면 호스트에 포커스가 올 때 안쪽 첫 포커스 가능 요소로 넘겨 준다. 키보드 포커스 관리 일반은 [ARIA와 키보드 포커스](/posts/aria-keyboard-focus)에서 다뤘다.

## 언제 Web Components를 고를까

Web Components가 빛나는 곳은 프레임워크가 여럿인 곳이다. 이 글의 출발점처럼 디자인 시스템을 React, Vue, 서버 렌더링 페이지에 같이 내보내야 할 때, 다른 회사 페이지에 위젯을 심어야 할 때(결제 버튼, 채팅 창), 팀마다 프레임워크가 다른 마이크로 프런트엔드의 경계가 그렇다. 남의 전역 CSS에서 부품을 지키는 일은 다른 방식으로는 브라우저 수준에서 보장하기 어렵다.

반대로 한 프레임워크만 쓰는 앱 안에서는 굳이 고를 이유가 약하다. 생명주기, 속성 동기화, 렌더링 갱신을 전부 직접 짜야 하고, 프레임워크의 서버 렌더링과 상태 관리에 자연스럽게 섞이지 않는다. 그림자 경계 때문에 전역 리셋 CSS, 아이콘 폰트, 전역 유틸리티 클래스가 안으로 안 들어오는 것도 이 상황에선 장점보다 짐이다. 같은 프레임워크 안의 재사용은 [React 컴포넌트 패턴](/posts/react-component-patterns)과 [디자인 시스템 만들기](/posts/design-system-building)의 헤드리스 컴포넌트 쪽이 더 맞다.

직접 `HTMLElement`를 다 쓰기보다 작은 도구를 얹는 경우가 많다. Lit은 반응형 프로퍼티와 템플릿 갱신을 몇 KB로 해 주고, Stencil은 컴파일러가 커스텀 요소와 프레임워크별 래퍼를 같이 만들어 준다. 팀이 고를 질문은 단순하다. 이 부품을 쓰는 쪽이 둘 이상의 기술인가. 남의 CSS가 내 부품을 덮을 위험이 있는가. 둘 다 아니라면 그냥 그 프레임워크의 컴포넌트로 만든다.

부품 하나를 브라우저에 등록하고, 진열장 같은 그림자 트리로 바깥 선택자를 막고, 상속과 변수와 `part`로만 바깥과 통하게 하는 것. 이벤트는 경계에서 호스트로 주인이 바뀌고, 폼과 서버 렌더링은 각각 `ElementInternals`와 선언형 Shadow DOM으로 메운다. 이 다섯 가지를 기억하면 커스텀 요소에서 나는 문제 대부분이 어느 경계에서 생겼는지 바로 짚을 수 있다.

## 면접에서 나올 만한 질문

### Web Components는 무엇이고 어떤 표준으로 이루어지나?

프레임워크 없이 브라우저가 직접 지원하는 재사용 부품을 만드는 표준 묶음이다. 태그 이름과 클래스를 등록하는 Custom Elements, 바깥과 분리된 DOM과 스타일을 붙이는 Shadow DOM, 렌더링되지 않는 마크업 틀인 `template`과 내용을 꽂는 `slot`으로 이루어진다. 어떤 프레임워크로 만든 화면에서도 일반 태그처럼 쓸 수 있는 게 가장 큰 장점이다.

### 커스텀 요소의 생명주기 콜백과 불리는 순서는?

`constructor`, `attributeChangedCallback`, `connectedCallback`, `disconnectedCallback`이 있고 문서를 옮길 때 `adoptedCallback`이 있다. HTML에 미리 있던 요소가 업그레이드될 때는 생성자, 처음 있던 속성에 대한 `attributeChangedCallback`, `connectedCallback` 순서로 불린다. 생성자에서는 그림자 루트만 붙이고 속성 읽기와 리스너 등록은 `connectedCallback`으로 미룬다. 노드를 옮기면 connected가 다시 불리므로 disconnected에서 정리해야 리스너가 쌓이지 않는다.

### Shadow DOM은 스타일을 어떻게 캡슐화하나? 바깥에서 꾸밀 방법은?

바깥 CSS 선택자는 그림자 트리 안의 요소에 맞지 않고, 안쪽 선택자도 바깥으로 새지 않는다. 다만 상속되는 속성(color, font 등)과 CSS 변수는 트리를 따라 경계를 넘는다. 그래서 부품을 만드는 쪽은 바꿔도 되는 값을 CSS 변수로 문서화하고, 레이아웃까지 허락할 요소에는 `part`를 붙여 바깥에서 `::part()`로 꾸미게 한다.

### open과 closed 모드의 차이는? closed로 하면 안전한가?

open이면 `element.shadowRoot`로 안쪽에 접근할 수 있고 closed면 `null`이 나온다. 하지만 같은 페이지의 스크립트는 `attachShadow`를 가로채는 식으로 얼마든지 들어갈 수 있어서 보안 경계가 아니다. 테스트와 접근성 도구, 확장 프로그램이 안을 못 보는 불편이 더 커서 보통 open을 쓴다.

### 그림자 트리 안에서 보낸 커스텀 이벤트가 바깥에서 안 잡힌다. 왜인가?

`CustomEvent`는 기본값이 `composed: false`라서 `bubbles: true`여도 그림자 루트에서 멈추고 호스트에도 닿지 않는다. 안쪽 요소에서 `composed: true`를 함께 주거나, 호스트 자신에서 이벤트를 보내면 된다. 경계를 넘는 이벤트는 바깥에서 `target`이 호스트로 리타깃되므로, 진짜 출발점이 필요하면 `composedPath()`를 본다.

### 커스텀 요소를 폼에 넣으면 값이 제출되지 않는다. 어떻게 하나?

`static formAssociated = true`를 선언하고 `attachInternals()`로 받은 `ElementInternals`에 `setFormValue`로 값을, `setValidity`로 유효성을 알려 준다. 그러면 `FormData`, `checkValidity`, `form.reset()`, `:invalid` 스타일이 일반 입력처럼 동작한다. 예전 방식인 숨은 input 복사보다 리셋과 검사까지 브라우저가 맞춰 준다.

### Web Components는 서버 렌더링이 안 된다고 하던데?

`attachShadow`가 자바스크립트라서 예전에는 스크립트 실행 전까지 내용이 비었다. 선언형 Shadow DOM, 즉 `template shadowrootmode="open"`을 HTML에 넣으면 파서가 그림자 루트를 만들어 스크립트 없이도 캡슐화된 화면이 먼저 그려진다. 클래스의 생성자는 이미 있는 `shadowRoot`를 재사용해야 하고, 다시 `attachShadow`를 부르면 내용이 비워진다. 또 이 문법은 파서에서만 동작해서 `innerHTML`로 넣으면 그림자 루트가 생기지 않고 `setHTMLUnsafe`를 써야 한다.

### React 앱에서 Web Components를 쓸 때 주의할 점은?

React 18까지는 값을 모두 문자열 속성으로 넘겨서 배열이나 객체가 망가지고, 커스텀 이벤트를 JSX로 연결할 수 없었다. React 19는 같은 이름의 프로퍼티가 있으면 프로퍼티로 넘기고 `on` 접두사 함수를 이벤트 리스너로 단다. 그 밖에 JSX 타입 선언을 보강해야 하고, id 참조 기반의 `label for`와 `aria-labelledby`가 그림자 경계를 넘지 못하는 접근성 문제를 슬롯이나 ElementInternals로 풀어야 한다.
