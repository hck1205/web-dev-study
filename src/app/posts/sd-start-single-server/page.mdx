맛집 리뷰 앱을 만들기로 했다. 사람들이 식당에 별점과 리뷰를 남기고, 첫 화면에는 "이번 주 맛집" 순위가 뜬다. 웹사이트도 있고 휴대폰 앱도 있다. 사용자는 아직 친구들과 그 친구들 정도다.

이때 서버를 몇 대 둘지, 로드 밸런서는 무엇을 쓸지부터 고민하기 쉽다. 시스템 설계 면접의 단골 질문인 "사용자 0명에서 수백만 명까지 키워 보라"도 출발점은 같다. 서버 한 대다. 이 글은 그 한 대가 어떻게 요청을 받는지 끝까지 따라가 보고, 사용자가 늘면 무엇이 가장 먼저 무너지는지 직접 망가뜨려 본다. 무너지는 지점 하나하나가 다음 글들의 출발점이 된다.

데모는 Node.js 22로 돌렸다. DB는 Node 프로세스 안에서 도는 PostgreSQL인 PGlite를 썼다. 진짜 PostgreSQL을 WASM으로 옮긴 것이라 SQL은 그대로 통한다. 웹 서버와 DB가 한 프로세스에 들어 있으니 "한 대에 다 있는" 상태를 그대로 재현한 셈이다.

## 주소를 치면 어디로 가나

서버(server)는 요청을 받아 답을 돌려주는 프로그램, 또는 그 프로그램이 도는 컴퓨터를 말한다. 맛집 앱의 서버 한 대에는 세 가지가 함께 산다.

- 웹 앱: 요청을 받아 로직을 돌리는 프로그램. 여기서는 Node.js다.
- DB: 식당과 리뷰를 저장하는 곳. 여기서는 PostgreSQL이다.
- 파일: 사용자가 올린 사진 같은 것들. 서버 디스크의 한 폴더에 쌓인다.

사용자는 이 서버의 IP 주소(인터넷에서 컴퓨터를 찾는 번호, 예: `203.0.113.10`)를 모른다. 대신 `www.matjip.example` 같은 이름을 안다. 이름을 IP로 바꿔 주는 것이 DNS(Domain Name System)다. 전화번호부에서 이름으로 번호를 찾는 것과 같다.

## 실제로 요청을 보내 보면

로컬에서 띄운 서버에 진짜 DNS 없이 요청을 보내려면 curl의 `--resolve`를 쓴다. "이 이름은 이 IP로 바꿔라"라고 curl에게 직접 알려 주는 옵션이다. DNS가 했을 일을 손으로 대신하는 셈이다.

```bash
# DNS 대신 www.matjip.example → 127.0.0.1 로 바꿔 보내고, 주고받은 헤더(-v)까지 본다
curl -sv --resolve www.matjip.example:8080:127.0.0.1 http://www.matjip.example:8080/
```

```text

* Hostname www.matjip.example was found in DNS cache
*   Trying 127.0.0.1:8080...
* Connected to www.matjip.example (127.0.0.1) port 8080
> GET / HTTP/1.1
> Host: www.matjip.example:8080
> User-Agent: curl/8.5.0
> Accept: */*
>
< HTTP/1.1 200 OK
< content-type: text/html; charset=utf-8
< Date: Wed, 21 Oct 2026 10:18:29 GMT
< Connection: keep-alive
< Keep-Alive: timeout=5
< Transfer-Encoding: chunked
<
<h1>이번 주 맛집</h1><ol><li>망원 만두 4.4</li><li>성수 버거 3.8</li><li>을지로 국수 3</li></ol>
```

두 군데를 보면 된다. `Added ... to DNS cache`와 `Connected to www.matjip.example (127.0.0.1)`는 이름이 IP로 바뀐 뒤 그 IP에 연결했다는 뜻이다. `> Host: www.matjip.example:8080`은 연결은 IP로 했어도 요청 안에는 이름이 그대로 실려 간다는 뜻이다. 서버 한 대가 여러 도메인을 받을 때 이 `Host` 헤더로 어느 사이트 요청인지 구분한다.

휴대폰 앱이 부르는 주소로 보내면 같은 서버가 JSON을 준다.

```bash
# 앱이 쓰는 API 주소. 화면을 그리는 건 앱이 하므로 데이터만 받는다
curl -s --resolve api.matjip.example:8080:127.0.0.1 http://api.matjip.example:8080/api/restaurants
```

```text
[{"name":"망원 만두","avg_stars":4.4,"reviews":1000},{"name":"성수 버거","avg_stars":3.8,"reviews":1000},{"name":"을지로 국수","avg_stars":3,"reviews":1000}]
```

## 웹과 앱은 받는 모양이 다르다

같은 순위인데 브라우저는 HTML을, 앱은 JSON을 받았다. 이유는 화면을 누가 그리느냐에 있다.

브라우저용 페이지는 서버가 HTML까지 만들어 보낼 수도 있고, 요즘 흔한 방식처럼 JavaScript가 브라우저에서 API를 불러 화면을 그릴 수도 있다. 앱은 화면을 그리는 코드가 이미 휴대폰에 설치돼 있다. 그래서 서버에게 필요한 건 데이터뿐이고, 가볍고 어느 언어로든 읽기 쉬운 JSON을 주고받는다.

## 한 대에 다 있으면 편한 것들

처음 시작할 때 서버 한 대는 게으른 선택이 아니다. 장점이 분명하다.

웹 앱과 DB가 같은 컴퓨터에 있으면 둘 사이에 네트워크가 없다. 쿼리 하나가 왕복하는 데 걸리는 시간이 거의 0이다. 배포는 파일을 올리고 프로세스를 다시 띄우면 끝이다. 로그는 한 곳에 쌓이니 문제가 생기면 그 서버 하나에 들어가서 보면 된다. 비용도 서버 한 대 값이다.

숫자로도 확인할 수 있다. 하루 사용자(DAU, Daily Active Users) 1만 명이 하루에 30번씩 요청하면 하루 30만 요청이다. 하루는 86,400초니까 평균은 초당 4개가 안 된다. 저녁 시간에 평소의 세 배가 몰려도 초당 12개쯤이다. 평범한 서버 한 대가 넉넉히 받는 양이다. 이런 어림 계산은 [⑩ 용량 추정](/posts/sd-capacity-estimation)에서 제대로 다룬다.

## 가장 먼저 무너지는 곳 1: 무거운 요청 하나

사용자가 늘면 무엇부터 문제가 될까. 직접 망가뜨려 봤다. 데모 서버에 월말 정산 리포트 같은 무거운 요청 `/api/report`를 하나 넣었다. CPU를 400ms 동안 붙잡고 계산만 하는 요청이다.

먼저 아무 일 없을 때 순위 API에 요청 10개를 한꺼번에 보내 걸린 시간을 쟀다. 다음엔 리포트 요청을 먼저 보내고, 20ms 뒤부터 30ms 간격으로 순위 요청 10개를 보냈다.

```bash
# 데모 드라이버: 서버를 띄우고, 평소와 리포트가 도는 중의 응답 시간을 잰다
node drive.mjs block
```

```text
idle  ms: 8 11 13 17 18 24 23 23 25 27
report ms: 401
busy  ms: 382 355 328 299 272 244 217 189 160 132
```

평소엔 8~27ms였던 순위 API가 리포트가 도는 동안 132~382ms가 됐다. 첫 요청은 리포트가 끝나기를 거의 통째로 기다렸고, 늦게 보낸 요청일수록 기다린 시간이 줄어든다. 숫자가 30ms씩 줄어드는 것은 요청을 30ms 간격으로 보냈기 때문이다. 모두 같은 순간, 리포트가 끝나는 순간에 풀려났다는 뜻이다.

Node.js는 자바스크립트를 한 스레드에서 돌린다. 동기 계산이 CPU를 잡고 있으면 그동안 다른 요청은 순서를 기다린다. 이 대기 줄을 그림으로 보면 이렇다.

## 가장 먼저 무너지는 곳 2: 서버가 꺼지는 순간

무거운 요청은 느리게 만들 뿐이다. 더 큰 문제는 서버가 아예 멈출 때다. 서버 한 대는 단일 장애 지점(SPOF, Single Point of Failure)이다. 그 하나만 멈추면 서비스 전체가 멈추는 지점이라는 뜻이다.

서버를 끄면 어떻게 되는지는 쉽게 확인된다.

```bash
# 살아 있을 때 상태 코드를 보고, 서버 프로세스를 PID로 끈 뒤 다시 요청한다
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/restaurants
kill 3400
curl -s http://127.0.0.1:8080/api/restaurants; echo "exit=$?"
```

```text
200
exit=7
```

curl의 종료 코드 7은 "서버에 연결하지 못했다"는 뜻이다. 웹사이트도, 앱도, 관리자 화면도 함께 멈춘다. 갈 곳이 그 하나뿐이니까.

꺼지는 이유는 장애만이 아니다. 새 코드를 배포할 때도 프로세스를 내렸다 올린다. 요청을 20ms마다 보내면서 서버를 껐다가 바로 다시 띄워 봤다.

```bash
# 20ms마다 요청을 보내는 도중 서버를 재시작하고, 실패한 요청을 센다
node drive.mjs restart
```

```text
kill 1483
new pid 1508
requests 221, failed 181, first fail at 591ms, last fail at 4421ms
```

591ms부터 4,421ms까지 약 3.8초 동안 요청 181개가 실패했다. 이 데모는 DB를 메모리에 다시 채우느라 뜨는 시간이 길었다. 실제 서비스에서도 프로세스를 띄우고, DB에 연결하고, 첫 요청을 받을 준비가 될 때까지 몇 초는 흔히 걸린다. 그 몇 초 동안 들어온 사용자는 모두 오류를 본다.

## 가장 먼저 무너지는 곳 3: 디스크 한 장에 모든 데이터

조용하지만 가장 무서운 문제가 하나 더 있다. 리뷰 데이터와 사진이 그 서버의 디스크 한 곳에만 있다. 디스크가 고장 나거나, 실수로 지우거나, 클라우드에서 인스턴스를 잘못 종료하면 데이터가 통째로 사라진다.

서버가 꺼진 것은 다시 켜면 되지만 데이터가 사라진 것은 되돌릴 수 없다. 그래서 서버 한 대로 운영하더라도 백업은 처음부터 다른 곳에 둔다. 매일 `pg_dump`로 덤프를 떠서 다른 저장소에 올리는 정도만 해도 최악은 피한다. 그리고 백업은 실제로 복원해 봐야 쓸 수 있는지 안다. 백업 주기와 복원 연습은 [백업 전략 글](/posts/backup-strategy)에 있다.

같은 디스크를 DB와 사진 파일이 나눠 쓰는 것도 문제다. 사진이 쌓여 디스크가 가득 차면 DB도 더 쓰지 못한다. 리뷰 작성이 갑자기 전부 실패하는데 원인은 사진 폴더인 상황이 생긴다. 사진은 나중에 객체 저장소와 CDN으로 빼낸다([⑤ 캐시와 CDN](/posts/sd-cache-and-cdn-tier)).

## 한 대로 얼마나 버틸까 계산해 보기

"언제 한 대를 넘어서야 하나"는 감이 아니라 숫자로 정한다. 하루 사용자 수, 한 사람이 하루에 보내는 요청 수, 피크 배율(가장 붐빌 때가 평균의 몇 배인지)을 알면 피크 초당 요청 수(QPS, Queries Per Second)를 구할 수 있다.

여기에 서버 한 대가 버티는 QPS를 부하 테스트로 재서 넣는다. 다만 한계까지 꽉 채워 쓰면 작은 변동에도 넘친다. 그래서 보통 70% 정도를 안전선으로 둔다. 아래 함수를 완성해 보자. 평균과 피크 QPS는 올림하고, 피크가 서버 한계의 70% 이하인지를 `fits`로 돌려준다.

## 처음부터 크게 만들면 안 되나

여기까지 읽으면 처음부터 서버 여러 대와 복제 DB로 시작하고 싶어진다. 대부분은 그럴 필요가 없다.

서버가 늘면 고장 날 곳도 늘어난다. 로드 밸런서 설정, 서버 사이 네트워크, DB 복제 지연, 세션을 어디에 둘지 같은 문제가 생긴다. 이걸 모두 감당하려면 사람과 시간이 든다. 사용자가 몇백 명인 단계에서는 그 비용이 얻는 것보다 크다.

현실적인 출발점은 이렇다. 서버 한 대로 시작하되, 나중에 쪼개기 쉽게 만들어 둔다.

- DB 주소를 코드에 박지 않고 `DATABASE_URL` 같은 환경 변수로 받는다. 그래야 DB를 다른 서버로 옮길 때 설정 한 줄만 바꾼다.
- 로그인 세션이나 업로드 파일을 웹 앱 프로세스의 메모리나 로컬 폴더에 영영 묶어 두지 않을 계획을 세운다. 서버가 두 대가 되는 순간 문제가 된다.
- 백업은 첫날부터 다른 곳에 둔다.
- 배포 중에 몇 초 끊기는 것을 언제까지 참을지 정해 둔다.

## 현장에서 한 대짜리 서버가 아플 때

증상별로 무엇부터 볼지 정리해 두면 단계를 넘어갈 시점도 보인다.

"가끔 모든 API가 함께 느려진다"면 CPU를 먼저 본다. `top`에서 웹 앱과 `postgres` 프로세스 중 누가 CPU를 쓰는지 본다. 특정 시각(리포트, 배치)에 맞춰 느려진다면 위의 무거운 요청 문제다. 그 작업만 다른 시간대로 옮기거나, 따로 떼어 내는 것이 다음 단계다.

"리뷰 쓰기만 갑자기 전부 실패한다"면 `df -h`로 디스크를 본다. 사진이나 로그가 디스크를 채운 경우가 흔하다.

"배포할 때마다 앱 리뷰에 오류 이야기가 달린다"면 배포 중 중단이다. 서버 두 대와 로드 밸런서로 가야 할 신호다.

"메모리가 부족해 프로세스가 죽는다"면 `dmesg`에서 OOM killer 기록을 찾는다. DB와 웹 앱이 메모리를 나눠 쓰다 보면 리눅스가 메모리를 가장 많이 쓰는 프로세스를 강제로 끄는데, 그게 DB일 때가 많다.

## 이어서 읽을 글

다음 글 [② 웹과 DB 나누기](/posts/sd-split-web-and-db)에서는 첫 번째로 무너진 곳, 웹 앱과 DB가 같은 자원을 다투는 문제를 푼다. DB를 다른 서버로 옮기면 무엇이 좋아지고 무엇이 새로 생기는지, DB는 어떤 종류를 골라야 하는지, 더 큰 서버로 바꾸는 것과 서버를 늘리는 것이 어떻게 다른지를 본다.

서버 한 대는 모든 것이 가깝고 단순하다는 장점과, 그 하나가 모든 것의 약점이라는 단점을 함께 가진다. 사용자가 늘면 무거운 요청이 다른 요청을 막고, 배포 한 번이 서비스 전체를 멈추고, 디스크 한 장이 데이터 전부를 쥐고 있게 된다. 이 세 가지가 보이기 시작할 때가 한 대를 넘어설 때다.

## 면접에서 나올 만한 질문

### 사용자가 주소를 입력하면 서버까지 어떻게 가나요?

먼저 DNS로 도메인 이름을 IP 주소로 바꾸고, 그 IP로 TCP 연결을 맺어 HTTP 요청을 보낸다. 이름과 IP의 대응은 TTL 동안 브라우저와 운영체제, 리졸버에 캐시된다. 요청 안의 Host 헤더에는 이름이 그대로 실려서, 서버 한 대가 여러 도메인을 받아도 구분할 수 있다.

### 웹 클라이언트와 모바일 클라이언트는 서버 입장에서 무엇이 다른가요?

둘 다 HTTP로 들어오지만 브라우저는 HTML이나 JS를 받아 화면을 그리고, 앱은 화면 코드가 이미 설치돼 있어 JSON 데이터만 받는다. 앱은 업데이트를 안 한 옛 버전이 오래 남기 때문에 API 응답 모양을 쉽게 바꿀 수 없다. 그래서 API에 버전을 붙이고 하위 호환을 지킨다.

### 처음부터 서버 여러 대로 시작하지 않는 이유는 무엇인가요?

초기 트래픽은 서버 한 대가 넉넉히 받는 수준이고, 여러 대로 나누면 로드 밸런서, 세션 공유, 복제 지연 같은 새로운 문제와 운영 비용이 생기기 때문이다. DAU 1만 명이 하루 30번 요청하면 피크도 초당 십여 개다. 대신 DB 주소를 설정으로 빼고, 상태를 프로세스 안에 묶지 않고, 백업을 다른 곳에 두는 식으로 나중에 나누기 쉽게 만들어 둔다.

### 서버 한 대 구성에서 가장 먼저 생기는 문제는 무엇인가요?

자원 다툼, 단일 장애 지점, 데이터 유실 위험이다. 무거운 요청이나 쿼리 하나가 CPU를 잡으면 가벼운 요청까지 느려지고, 데모에서는 평소 10ms대이던 API가 380ms까지 밀렸다. 서버가 꺼지거나 배포로 재시작하면 그동안 모든 요청이 실패한다. 데이터가 디스크 한 곳에만 있으면 그 디스크와 함께 사라진다.

### 트래픽이 10배가 되면 무엇부터 하나요?

먼저 무엇이 병목인지 잰다. CPU를 웹 앱이 쓰는지 DB가 쓰는지 보고, DB가 같은 자원을 다투고 있으면 DB를 다른 서버로 분리한다. 그다음 웹 서버를 여러 대로 늘리고 로드 밸런서를 붙여 한 대가 빠져도 서비스가 돌게 한다. 단기적으로는 더 큰 서버로 바꾸는 것도 빠른 처방이지만, 한 대라는 약점은 그대로 남는다.

### 이 서버가 갑자기 죽으면 어떻게 되나요?

서버 한 대가 단일 장애 지점이라 웹과 앱 모두 연결 자체가 실패한다. 재시작으로 돌아오는 동안의 요청은 잃고, 디스크까지 망가졌다면 마지막 백업 이후의 데이터를 잃는다. 그래서 이 단계에서도 백업은 다른 곳에 두고 복원 연습을 해 둔다. 근본적인 해결은 웹 서버를 여러 대로, DB를 복제로 이중화하는 것이다.

### DNS TTL은 길게 두는 게 좋나요, 짧게 두는 게 좋나요?

길면 DNS 조회가 줄어 빠르지만 IP를 바꿨을 때 옛 주소로 가는 사람이 오래 남는다. 짧으면 바꾼 것이 빨리 퍼지지만 조회가 늘어난다. 서버 이전이나 장애 전환을 앞두고 있다면 미리 TTL을 짧게 낮춰 두었다가, 전환이 끝나면 다시 늘리는 방식을 쓴다.
