로그를 모으는 S3 버킷의 비용이 매달 조금씩 늘고 있다. 첫 달 40달러였는데 1년 뒤 400달러가 됐다. 트래픽은 거의 그대로다. 들여다보니 이유가 셋이었다. 로그는 쌓이기만 하고 한 번도 지워진 적이 없었다. 버전 관리가 켜져 있어서 앱이 같은 키에 덮어쓸 때마다 옛 버전이 그대로 남았다. 그리고 실패한 대용량 업로드 조각이 `aws s3 ls`에는 보이지 않는 곳에 수백 GB 쌓여 있었다.

S3 요금은 대부분 "얼마나 오래, 어떤 등급에 두었나"로 정해진다. 이 글은 버킷과 객체의 기본, 스토리지 클래스(Standard부터 Glacier Deep Archive까지)의 요금 구조와 함정, 객체를 등급 사이로 옮기고 지우는 수명 주기 규칙, 버전 관리를 켰을 때 삭제가 어떻게 바뀌는지, Glacier에서 꺼내는 시간, 지울 수 없게 잠그는 Object Lock을 차례로 본다. 요금은 us-east-1 공개 요금(2026년 10월 확인) 기준이고 리전마다 다르다. 계정 없이 쓴 글이라 AWS CLI는 명령과 공식 문서의 응답 형식만 보인다. 비용 계산은 Node로 직접 돌린 값이다.

이 주제의 다른 글: 버킷을 앱에서 안전하게 열고 닫는 법(버킷 정책, 퍼블릭 차단, presigned URL)은 [S3 실전](/posts/aws-s3-in-practice)에서, 블록·파일 스토리지와의 차이는 [블록, 파일, 객체 스토리지](/posts/block-file-object-storage)에서 다룬다. 클라우드 청구서 전체를 읽는 법은 [클라우드 비용 줄이기](/posts/cloud-cost-optimization)에 있다.

## 버킷, 객체, 키

버킷은 객체를 담는 최상위 그릇이다. 이름은 전 세계 모든 AWS 계정을 통틀어 하나여야 하고(범용 버킷 기준), 만들 때 리전을 정한다. 복제를 따로 걸지 않는 한 데이터는 그 리전 밖으로 나가지 않는다. 버전 관리, 수명 주기, 암호화 기본값, 접근 정책 같은 설정이 버킷 단위로 붙는다.

객체는 키(이름), 데이터, 메타데이터, 그리고 버전 관리를 켰다면 버전 ID로 이뤄진다. 키는 `logs/2026/10/23/api-01.json.gz` 같은 문자열이다. 슬래시는 폴더가 아니라 이름의 일부지만, 콘솔과 `LIST` API가 슬래시를 기준으로 묶어 보여 주니 폴더처럼 보인다. 이 앞부분을 접두사(prefix)라고 부르고, 수명 주기 규칙이나 권한을 접두사 단위로 건다.

스토리지 클래스는 버킷이 아니라 객체마다 붙는 속성이다. 같은 버킷 안에 Standard 객체와 Glacier 객체가 섞여 있을 수 있다. 업로드할 때 정하거나(`--storage-class STANDARD_IA`), 나중에 수명 주기 규칙으로 바꾼다.

```bash
# 버킷의 객체를 크기와 함께 보고, 총 개수와 용량을 요약한다
aws s3 ls s3://my-log-bucket/logs/2026/10/ --recursive --human-readable --summarize

# 객체 하나의 메타데이터. StorageClass 필드가 없으면 STANDARD다
aws s3api head-object --bucket my-log-bucket --key logs/2026/10/23/api-01.json.gz
```

`--summarize`의 합계는 현재 버전만 센다. 옛 버전과 미완료 업로드 조각은 여기에 안 나온다. 처음 이야기의 청구서가 수상했던 이유다.

## 등급은 꺼내는 횟수와 기다릴 수 있는 시간으로 고른다

등급마다 매기는 값이 넷이다. GB-월 보관 요금, 꺼낼 때 GB당 검색 요금, 최소 보관 기간(그 전에 지우거나 옮겨도 남은 기간 요금을 낸다), 최소 과금 크기. 여기에 첫 바이트까지 기다리는 시간이 더해진다.

| 등급 | 보관 (GB-월) | 꺼낼 때 (GB) | 최소 기간 | 최소 크기 | 첫 바이트 |
|---|---|---|---|---|---|
| Standard | 0.023달러 | 없음 | 없음 | 없음 | 밀리초 |
| Intelligent-Tiering | 접근에 따라 자동 | 없음 | 없음 | 128KB 미만은 이동 안 함 | 밀리초(아카이브 층 제외) |
| Standard-IA | 0.0125달러 | 0.01달러 | 30일 | 128KB | 밀리초 |
| One Zone-IA | 0.01달러 | 0.01달러 | 30일 | 128KB | 밀리초 |
| Glacier Instant Retrieval | 0.004달러 | 0.03달러 | 90일 | 128KB | 밀리초 |
| Glacier Flexible Retrieval | 0.0036달러 | 등급별 (Bulk 무료) | 90일 | 객체당 40KB 덧붙음 | 분~시간 |
| Glacier Deep Archive | 0.00099달러 | 등급별 | 180일 | 객체당 40KB 덧붙음 | 12~48시간 |

보관 요금만 보면 Deep Archive가 Standard의 23분의 1이다. 하지만 표의 나머지 칸이 함정이다.

Standard-IA와 Glacier Instant Retrieval은 128KB보다 작은 객체도 128KB로 쳐서 받는다. Glacier Flexible과 Deep Archive는 객체마다 색인용 32KB를 그 등급 요금으로, 이름과 메타데이터용 8KB를 Standard 요금으로 덧붙인다. 최소 기간 전에 지우면 남은 일수만큼 한 번에 청구된다. 그리고 수명 주기로 옮길 때마다 객체 1,000개당 전환 요청 요금이 붙는다(IA로 0.01달러, Glacier IR로 0.02달러, Deep Archive로 0.05달러).

One Zone-IA는 이름대로 AZ 하나에만 저장한다. 그 AZ가 사라지면 데이터도 사라진다. 다른 곳에서 다시 만들 수 있는 데이터(썸네일, 원본이 따로 있는 사본)에만 쓴다. 반대로 지연이 아주 짧아야 하는 데이터용으로 S3 Express One Zone이라는 별도 등급도 있는데, 이건 전용 디렉터리 버킷에 쓰는 고성능 등급이라 이 글의 비용 줄이기 이야기와는 결이 다르다.

## 작은 객체를 IA로 옮기면 오히려 비싸진다

표를 보면 "30일 지난 로그는 IA로"가 당연해 보인다. 그런데 로그 파일이 작으면 계산이 뒤집힌다. 1분마다 서버마다 한 파일씩 올리는 로그라면 파일 하나가 20KB쯤이고, 1년이면 천만 개가 쉽게 쌓인다.

아래 함수는 객체 수와 평균 크기, 옮길 등급을 받아 옮기기 전과 후의 월 보관 요금, 한 번 내는 전환 요금, 그 전환 요금을 몇 달 만에 되찾는지 계산한다. 요금은 위 표의 값이고 1GB는 1,048,576KB로 센다.

AWS도 이 함정을 알아서 2024년 9월부터 수명 주기 규칙의 기본 동작을 바꿨다. 새로 만드는 규칙은 128KB보다 작은 객체를 기본으로 옮기지 않는다. 필터에 `ObjectSizeGreaterThan`이나 `ObjectSizeLessThan`을 직접 적으면 이 기본을 바꿀 수 있다. 다만 업로드할 때 `--storage-class STANDARD_IA`로 직접 넣는 경우에는 이 보호가 없다. 작은 로그는 등급을 옮기기보다 여러 파일을 하나로 묶어(시간 단위로 합쳐 압축) 객체 수부터 줄이는 게 먼저다.

## 작은 객체는 보관보다 요청에서 돈이 샌다

같은 로그 버킷에서 보관 요금보다 큰 항목이 하나 더 있다. 요청 요금이다. Standard 기준 PUT·COPY·POST·LIST는 1,000건에 0.005달러, GET은 1,000건에 0.0004달러다. 20KB 로그를 한 달에 천만 개 올리면 보관 요금은 4.39달러인데 PUT 요금은 50달러다. 열 배가 넘는다. 등급이 싼 쪽일수록 요청 단가가 비싸져서(IA는 PUT 1,000건에 0.01달러) 작은 파일을 직접 IA에 올리면 두 번 손해다.

해결은 같은 방향이다. 객체 수를 줄인다. 로그 수집기(Fluent Bit, Vector 같은)에서 버퍼 크기와 시간을 늘려 "1분에 한 파일"을 "5분에 한 파일, 또는 64MB가 차면 한 파일"로 바꾸면, 객체 수가 다섯 배 넘게 줄고 압축 효율도 오른다. 분석은 Athena 같은 쿼리 엔진이 큰 파일을 더 빨리 읽으니 그쪽도 이득이다. 실시간으로 하나씩 봐야 하는 로그라면 S3가 아니라 CloudWatch Logs나 검색 엔진이 먼저 받고, S3는 묶어서 오래 두는 곳으로 쓴다.

LIST 요청도 잊기 쉽다. 수명 주기나 배치 스크립트가 매시간 버킷 전체를 `aws s3 ls --recursive`로 훑으면, 객체가 1억 개인 버킷에서 LIST 한 번이 1,000개씩 10만 번 요청이다. 한 시간마다 0.5달러, 한 달이면 360달러다. 버킷 전체 목록이 필요하면 하루 한 번 나오는 S3 Inventory를 읽는다.

## Intelligent-Tiering이 알아서 옮겨 주는 것

꺼내는 패턴을 모르겠으면 Intelligent-Tiering에 맡긴다. 객체마다 마지막 접근을 보고, 30일 동안 안 읽힌 객체는 Infrequent Access 층으로, 90일 동안 안 읽힌 객체는 Archive Instant Access 층으로 내린다. 다시 읽히면 바로 Frequent 층으로 올라온다. 검색 요금과 최소 보관 기간이 없어서, 예측이 틀려도 벌금이 없다. 각 층의 보관 요금은 Standard, Standard-IA, Glacier IR과 비슷한 수준이다.

대가는 객체 1,000개당 월 0.0025달러의 모니터링 요금이다. 큰 객체에는 무시할 만하지만, 작은 객체가 수억 개면 꽤 된다. 그래서 128KB보다 작은 객체는 모니터링하지 않고(요금도 없다) 늘 Frequent 층에 둔다. 작은 객체를 Intelligent-Tiering에 넣으면 그냥 Standard와 같은 셈이다.

원하면 더 깊은 층(Archive Access, Deep Archive Access)도 켤 수 있다. 90일이나 180일 이상 안 읽힌 객체를 Glacier Flexible·Deep Archive 수준으로 내리는데, 이 층에 내려간 객체는 즉시 읽히지 않고 복원을 기다려야 한다. 그래서 "앱이 언제든 GET할 수 있어야 한다"는 데이터에는 켜지 않는다. 기본 세 층만 쓰면 앱 쪽에서는 Standard와 차이가 없다.

고르는 기준은 이렇다. 접근 패턴을 확실히 안다면(30일 지나면 안 본다) 수명 주기 규칙이 싸다. 패턴을 모르거나 객체마다 다르면(사용자가 올린 사진 중 일부만 계속 조회된다) Intelligent-Tiering이 낫다. 데이터 레이크처럼 객체가 크고 접근이 들쭉날쭉한 곳이 대표적인 자리다.

## 수명 주기 규칙 한 장을 뜯어본다

수명 주기 규칙은 버킷에 붙이는 JSON이다. 규칙마다 대상(필터)과 할 일(전환, 만료)을 적는다. 로그 버킷에 필요한 걸 한 규칙에 다 넣으면 이렇게 된다.

```json
{
  "Rules": [
    {
      "ID": "app-logs",
      "Status": "Enabled",
      "Filter": {
        "And": { "Prefix": "logs/", "ObjectSizeGreaterThan": 131072 }
      },
      "Transitions": [
        { "Days": 30, "StorageClass": "STANDARD_IA" },
        { "Days": 90, "StorageClass": "GLACIER_IR" },
        { "Days": 365, "StorageClass": "DEEP_ARCHIVE" }
      ],
      "Expiration": { "Days": 1095 },
      "NoncurrentVersionExpiration": { "NoncurrentDays": 30, "NewerNoncurrentVersions": 2 },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
    }
  ]
}
```

```bash
# 위 JSON을 버킷에 적용한다. 기존 규칙을 통째로 바꾸니 먼저 지금 규칙을 받아 둔다
aws s3api get-bucket-lifecycle-configuration --bucket my-log-bucket > lifecycle-before.json
aws s3api put-bucket-lifecycle-configuration --bucket my-log-bucket \
  --lifecycle-configuration file://lifecycle.json
```

`put-bucket-lifecycle-configuration`은 덧붙이는 게 아니라 통째로 바꾼다. 다른 팀이 걸어 둔 규칙이 있었다면 사라진다. 그래서 바꾸기 전 규칙을 파일로 받아 두는 게 되돌리기의 전부다. 되돌릴 때는 그 파일을 다시 넣는다.

## 버전 관리를 켜면 삭제가 바뀐다

버전 관리를 켠 버킷에서는 덮어쓰기와 삭제가 데이터를 없애지 않는다. 같은 키에 새로 PUT하면 새 버전이 현재 버전이 되고 옛 버전은 이전 버전(noncurrent)으로 남는다. 버전 ID 없이 DELETE하면 아무것도 지워지지 않고 삭제 마커라는 빈 버전이 맨 위에 쌓인다. 아래 그림에서 다음을 누르면 순서대로 보인다.

이 동작이 실수와 랜섬웨어로부터 데이터를 지켜 주지만, 수명 주기 규칙 없이 켜 두면 청구서가 는다. 같은 키에 매시간 덮어쓰는 파일(상태 파일, 집계 결과)이면 하루에 이전 버전이 24개씩 쌓인다. 그래서 버전 관리를 켤 때는 위 규칙의 `NoncurrentVersionExpiration`을 함께 건다. `NoncurrentDays: 30, NewerNoncurrentVersions: 2`는 "이전 버전이 된 지 30일 지난 것은 지우되, 최근 이전 버전 2개는 남긴다"는 뜻이다.

삭제 마커도 정리 대상이다. 현재 버전이 삭제 마커이고 그 아래 이전 버전이 모두 만료됐다면, 마커만 덩그러니 남아 LIST를 느리게 만든다. `Expiration`에 `ExpiredObjectDeleteMarker: true`를 주면 이런 마커를 치운다(같은 `Expiration` 안에 `Days`와 함께 쓸 수는 없어서 규칙을 나눈다).

한 번 켠 버전 관리는 끌 수 없고 일시 중지(Suspended)만 된다. 일시 중지하면 새 쓰기는 버전 ID `null`로 덮어쓰지만, 이미 쌓인 이전 버전은 그대로 남는다. 버전이 어떻게 저장되고 지워지는지 내부 구조는 [객체 저장소 설계 ③](/posts/sd-object-storage-versioning-multipart)에서 직접 만들어 봤다.

## 미완료 멀티파트 조각은 보이지 않는 곳에서 돈을 낸다

큰 파일은 멀티파트 업로드로 조각을 나눠 올리고 마지막에 `CompleteMultipartUpload`로 합친다. 그런데 업로드가 중간에 죽으면(배포 중 프로세스 종료, 네트워크 끊김) 이미 올라간 조각은 S3에 남는다. 합쳐지지 않았으니 `ls`에도 콘솔 객체 목록에도 안 나온다. 그런데 보관 요금은 낸다.

```bash
# 끝나지 않은 멀티파트 업로드 목록. 시작 시각(Initiated)이 오래된 것이 정리 대상이다
aws s3api list-multipart-uploads --bucket my-log-bucket

# 하나를 손으로 정리한다
aws s3api abort-multipart-upload --bucket my-log-bucket \
  --key backups/db-2026-10-01.tar --upload-id "<UploadId>"
```

손으로 치울 일이 아니다. 위 규칙의 `AbortIncompleteMultipartUpload: { DaysAfterInitiation: 7 }`이 시작한 지 7일 넘은 미완료 업로드를 치운다. 이 규칙 하나는 필터 없이 모든 버킷에 걸어 두는 게 좋다. 걸어서 손해 볼 일이 거의 없다. 버킷마다 얼마나 쌓였는지는 S3 Storage Lens의 미완료 멀티파트 업로드 지표로 계정 전체를 한 번에 본다.

## Glacier에서 꺼내는 데는 시간이 걸린다

Glacier Flexible Retrieval과 Deep Archive 객체는 바로 GET하면 `InvalidObjectState` 에러가 난다. 먼저 복원(restore)을 신청해 임시 사본을 만들고, 그 사본을 읽는다.

```bash
# 7일 동안 읽을 수 있는 임시 사본을 Bulk 등급으로 만든다
aws s3api restore-object --bucket my-log-bucket \
  --key logs/2024/03/01/api-01.json.gz \
  --restore-request '{"Days":7,"GlacierJobParameters":{"Tier":"Bulk"}}'

# 진행 상태. 응답의 Restore 필드를 본다
aws s3api head-object --bucket my-log-bucket --key logs/2024/03/01/api-01.json.gz
```

AWS 문서의 응답 형식으로는 `head-object` 결과에 `"Restore": "ongoing-request=\"false\", expiry-date=\"...\""`처럼 진행 여부와 임시 사본 만료일이 함께 나온다.

복원 등급별 시간은 이렇게 안내된다. Glacier Flexible Retrieval은 Expedited 1~5분, Standard 3~5시간, Bulk 5~12시간이고 Bulk는 검색 요금이 없다. Deep Archive는 Standard 12시간 안쪽, Bulk 48시간 안쪽이다. Glacier Instant Retrieval은 이름대로 복원 없이 바로 읽힌다. 대신 검색 요금이 GB당 0.03달러로 비싸다.

이 시간이 설계를 바꾼다. "감사팀이 3년 전 로그를 달라고 하면 하루 안에 준다"는 약속이면 Deep Archive로 충분하다. "장애 분석에 지난달 로그를 바로 본다"면 Glacier IR이나 IA에 둬야 한다. 객체가 수백만 개면 하나씩 `restore-object`를 부르지 말고 S3 Batch Operations로 목록을 넘겨 한 번에 신청한다. 복원은 임시 사본 기간 동안 Standard 요금을 더 내니, 꺼낸 데이터를 오래 쓸 거라면 다른 버킷으로 복사해 두고 `Days`는 짧게 잡는다.

## 지울 수 없게 잠그기: Object Lock

버전 관리는 실수를 되돌릴 수 있게 해 주지만, 권한이 있는 사람은 버전 ID를 붙여 영구 삭제할 수 있다. 계정 자격 증명이 털리면 공격자도 할 수 있다. 법적으로 일정 기간 지우면 안 되는 기록(금융 거래 기록, 감사 로그)이나 랜섬웨어에 대비한 백업에는 그보다 강한 장치가 필요하다. Object Lock은 객체 버전마다 "이 날짜까지는 지우거나 덮어쓸 수 없다"는 보존 기간을 붙인다. 버전 관리를 켠 버킷에서만 된다.

모드가 둘이다. Governance 모드는 `s3:BypassGovernanceRetention` 권한이 있는 사용자가 헤더를 붙여 잠금을 풀 수 있다. 정책 실수를 고칠 길이 남아 있어서, 규칙을 처음 시험할 때 쓴다. Compliance 모드는 루트 사용자를 포함해 누구도 보존 기간이 끝나기 전에는 그 버전을 지우거나 기간을 줄일 수 없다. 기간을 늘리는 것만 된다. 잘못 걸면 그 기간만큼 요금을 피할 길이 없으니, 짧은 기간으로 시험한 뒤 늘린다. 이와 별개로 법적 보존(Legal Hold)은 기간 없이 켜고 끄는 잠금으로, 소송이나 조사 동안 특정 객체를 묶어 둘 때 쓴다.

```bash
# 버킷 기본값: 새로 들어오는 모든 객체 버전을 Governance 모드로 30일 잠근다
aws s3api put-object-lock-configuration --bucket my-audit-bucket \
  --object-lock-configuration \
  '{"ObjectLockEnabled":"Enabled","Rule":{"DefaultRetention":{"Mode":"GOVERNANCE","Days":30}}}'
```

Object Lock은 원래 버킷을 만들 때만 켤 수 있었지만 지금은 기존 버킷에도 켤 수 있다. AWS는 Compliance 모드가 금융 규정(미국 SEC 17a-4 같은)의 보존 요건을 만족한다는 외부 평가를 공개해 두었다. 실제로 규정을 맞춰야 한다면 그 평가 문서와 자기 조직의 법무 해석을 같이 본다. 백업을 지울 수 없게 두는 전략 전체는 [백업 전략](/posts/backup-strategy)에서 다뤘다.

## 다른 리전의 사본은 처음부터 싼 등급으로 둔다

아카이브의 또 다른 축은 장소다. 리전 하나가 통째로 망가지거나 계정이 털리는 사고에 대비해 다른 리전이나 다른 계정에 사본을 두는 일이 많다. S3 복제(Replication)는 버킷 규칙으로 새로 들어오는 객체를 다른 버킷에 자동으로 복사한다. 리전이 다르면 교차 리전 복제(CRR), 같으면 같은 리전 복제(SRR)다. 버전 관리가 양쪽 버킷에 모두 켜져 있어야 한다.

복제 규칙에는 대상 버킷의 스토리지 클래스를 따로 정하는 칸이 있다. 재해 대비용 사본은 평소에 읽지 않으니 처음부터 Glacier IR이나 Deep Archive로 받게 하면, 원본과 같은 등급으로 복사한 뒤 수명 주기로 내리는 것보다 전환 요금과 최소 기간 부담이 줄어든다. 대신 리전 사이 전송 요금(GB당 0.02달러 수준)이 복사할 때마다 붙고, 복제는 규칙을 건 뒤 새로 들어오는 객체만 옮긴다. 이미 있는 객체는 S3 Batch Replication으로 따로 옮긴다.

삭제는 기본으로 복제되지 않는다는 점도 기억할 만하다. 원본에서 버전 ID를 붙여 지운 것은 사본에 전파되지 않고, 삭제 마커 복제는 규칙에서 켜야만 넘어간다. 원본 계정이 털려도 사본이 남는 이유이고, 사본 버킷에 Object Lock까지 걸면 그쪽 권한이 털려도 지울 수 없다. 복제 사본과 백업 계정 설계는 [멀티 리전](/posts/multi-region)과 [재해 복구](/posts/disaster-recovery)에서 더 넓게 다룬다.

## 보존은 지우는 날까지 정하는 일이다

데이터 수명 주기는 "싸게 쌓는 법"만이 아니다. 언제 지울지까지 정해야 끝난다. 개인정보는 보유 기간이 끝나거나 목적을 이루면 지체 없이 파기해야 한다는 의무가 있다(한국 개인정보 보호법 기준). 로그에 사용자 이메일이나 IP가 섞여 있다면 "혹시 모르니 영원히"는 비용 문제가 아니라 규정 위반이 된다.

그래서 아카이브 정책은 데이터마다 세 줄로 적는다. 얼마나 자주 꺼내나(등급을 정한다), 얼마나 빨리 꺼내야 하나(Glacier IR인지 Deep Archive인지 정한다), 언제까지 두고 언제 지우나(Expiration과 Object Lock 기간을 정한다). 세 줄이 정해지면 수명 주기 규칙은 그걸 옮겨 적는 일이다. 보존 기간과 Object Lock 기간이 부딪히면(잠금 3년인데 파기 의무가 1년) 잠금이 이겨서 지울 수 없게 되니, 잠금을 걸 데이터에는 개인정보를 섞지 않도록 설계 단계에서 나눈다.

## 로그 버킷 청구서를 줄인 순서

처음 이야기의 버킷으로 돌아가 실제로 할 일을 순서로 적으면 이렇다.

1. 무엇이 쌓였는지 본다. CloudWatch의 `BucketSizeBytes` 지표는 스토리지 클래스별로 나뉘어 하루 한 번 나온다. S3 Storage Lens는 현재 버전, 이전 버전, 미완료 멀티파트 바이트를 따로 보여 준다. 처음 이야기라면 이전 버전과 미완료 조각이 큰 몫이었다.
2. 누구도 손해 보지 않는 정리부터 건다. `AbortIncompleteMultipartUpload`와 `NoncurrentVersionExpiration`이다.
3. 객체 크기 분포를 본다. S3 Inventory를 켜면 객체마다 크기와 등급이 담긴 목록을 매일 받는다. 128KB 미만이 대부분이면 등급 전환보다 작은 파일을 묶는 쪽이 먼저다.
4. 접근 패턴을 확인하고 전환 규칙을 건다. 확실하면 수명 주기, 모르면 Intelligent-Tiering이다.
5. 보존 기간을 정해 `Expiration`을 건다. 이걸 빼면 1~4를 해도 비용은 언젠가 다시 오른다.

버킷 정책이나 퍼블릭 차단처럼 접근을 다루는 설정은 비용이 아니라 사고를 막는 쪽이라 [S3 실전](/posts/aws-s3-in-practice)에서 따로 본다.

## 싼 등급은 꺼낼 때 값을 받는다

S3 등급은 보관이 쌀수록 꺼내는 값과 기다리는 시간, 최소 기간, 최소 크기로 되받는다. 그래서 크고 적은 객체는 내리면 이기고, 작고 많은 객체는 내리면 진다. 수명 주기 규칙은 전환만이 아니라 만료, 이전 버전, 미완료 업로드까지 함께 다뤄야 청구서가 멈추고, 지우면 안 되는 데이터는 Object Lock으로, 지워야 하는 데이터는 Expiration으로 날짜를 박는다.

## 면접에서 나올 만한 질문

### S3 스토리지 클래스는 무엇을 기준으로 고르나요?

얼마나 자주 꺼내는지와 꺼낼 때 얼마나 기다릴 수 있는지로 고른다. 자주 읽으면 Standard, 한 달에 한 번 이하로 읽지만 바로 읽혀야 하면 Standard-IA나 Glacier Instant Retrieval, 몇 시간을 기다릴 수 있으면 Glacier Flexible, 반나절 이상 기다려도 되는 장기 보관이면 Deep Archive다. 패턴을 모르면 Intelligent-Tiering에 맡긴다. 싼 등급일수록 검색 요금, 최소 보관 기간, 최소 과금 크기가 붙는다는 점을 같이 계산한다.

### 작은 객체를 Standard-IA로 옮기면 왜 비싸질 수 있나요?

IA는 128KB 미만 객체도 128KB로 쳐서 보관료를 받고, 수명 주기 전환에는 객체 1,000개당 요청 요금이 붙기 때문이다. 20KB 객체 천만 개를 IA로 옮기면 월 보관료가 4.39달러에서 15.26달러로 오르고 전환에 100달러를 따로 낸다. 2024년 9월부터 수명 주기 기본 동작은 128KB 미만 객체를 옮기지 않는다. 작은 객체는 묶어서 수부터 줄인다.

### 수명 주기 규칙으로 무엇을 할 수 있나요?

정한 날짜가 지난 객체를 싼 등급으로 옮기고(Transition), 지우고(Expiration), 이전 버전을 옮기거나 지우고(Noncurrent...), 끝나지 않은 멀티파트 업로드를 정리하고(AbortIncompleteMultipartUpload), 남은 삭제 마커를 치운다. 접두사, 태그, 객체 크기로 대상을 거른다. 비동기로 돌아서 조건을 채운 그날 바로 반영되지는 않고, 등급은 비싼 쪽에서 싼 쪽으로만 옮긴다.

### 버전 관리를 켜면 삭제는 어떻게 바뀌나요?

버전 ID 없이 DELETE하면 데이터는 지워지지 않고 삭제 마커가 현재 버전이 된다. GET은 404를 받지만 이전 버전은 남아서 요금을 낸다. 마커를 버전 ID로 지우면 객체가 되살아나고, 특정 버전을 영구히 지우려면 버전 ID를 붙여 지운다. 그래서 버전 관리와 함께 NoncurrentVersionExpiration 규칙을 건다. 한 번 켠 버전 관리는 끌 수 없고 일시 중지만 된다.

### Glacier 복원에는 시간이 얼마나 걸리나요?

Glacier Flexible Retrieval은 Expedited 1~5분, Standard 3~5시간, Bulk 5~12시간이고, Deep Archive는 Standard 12시간, Bulk 48시간 안쪽이다. 복원은 정한 기간 동안 임시 사본을 Standard 요금으로 만든다. Glacier Instant Retrieval은 복원 없이 밀리초 안에 읽히는 대신 검색 요금이 비싸다. 많은 객체는 Batch Operations로 한 번에 신청하고 완료는 이벤트 알림으로 받는다.

### Object Lock의 Governance와 Compliance 모드는 어떻게 다른가요?

Governance는 특별 권한이 있는 사용자가 잠금을 우회할 수 있고, Compliance는 루트를 포함해 누구도 보존 기간 전에 지우거나 기간을 줄일 수 없다. 규정 보존이나 랜섬웨어 대비 백업은 Compliance, 정책을 시험하거나 운영 실수를 고칠 여지가 필요하면 Governance를 쓴다. 둘 다 버전 관리가 켜진 버킷에서만 되고, 기간 없는 법적 보존(Legal Hold)을 따로 걸 수 있다.

### 다른 리전에 둔 S3 사본은 어떤 등급으로 두나요?

재해 대비용이라 평소 읽지 않으니 복제 규칙에서 대상 스토리지 클래스를 Glacier IR이나 Deep Archive로 바로 지정한다. 같은 등급으로 복사한 뒤 수명 주기로 내리면 전환 요금과 최소 기간 요금을 한 번 더 낸다. 복제는 규칙 이후의 새 객체만 옮기고 영구 삭제는 전파하지 않으니, 기존 객체는 Batch Replication으로 옮기고 사본 버킷에는 Object Lock을 건다.

### S3 비용이 계속 늘 때 어디부터 보나요?

스토리지 클래스별 용량과 함께 이전 버전, 미완료 멀티파트 업로드 바이트를 먼저 본다. `ls`의 합계는 현재 버전만 세서 이 둘이 안 보인다. Storage Lens나 CloudWatch 지표로 확인하고, 미완료 업로드 정리와 이전 버전 만료 규칙부터 건다. 그다음 Inventory로 객체 크기 분포를 보고 전환과 만료 규칙을 정한다. 요청 요금이 크다면 작은 객체를 묶어 요청 수를 줄인다.
