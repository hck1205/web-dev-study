장애 대응 중이었다. 추천 영역이 부르는 API가 느려지면서 상품 페이지 전체가 같이 느려졌고, 그 영역만 끄기로 했다. 대시보드에서 킬 스위치를 내렸다. 그런데 에러율 그래프가 바로 꺾이지 않는다. 서버 몇 대는 곧바로 추천을 멈췄고, 나머지는 30초쯤 지나서야 따라왔다. 그 30초 동안 "플래그가 안 먹는다"는 말이 채널에 몇 번 올라왔다.

플래그는 `if` 하나로 보이지만, 그 `if`의 답은 코드 밖 어딘가에서 정해져 서버마다 배달된다. 답을 정하는 규칙, 배달하는 방식, 배달이 끊겼을 때의 기본값, 그리고 다 쓴 플래그를 지우는 일까지가 피처 플래그를 운영한다는 뜻이다. 플래그가 왜 생겼는지, 해시로 사용자를 고정해서 나누는 원리, 실험 플래그와 통계는 [A/B 테스트와 피처 플래그](/posts/ab-testing)에서 다뤘다. 이 글은 그 위에서 플래그 시스템이 어떻게 돌아가는지를 본다.

이 주제의 다른 글: [A/B 테스트와 피처 플래그](/posts/ab-testing), [CI/CD의 뼈대](/posts/ci-cd-basics), [롤백 전략](/posts/rollback-strategy).

실습은 Ubuntu 24.04, Node 22.22.0, `@openfeature/server-sdk` 1.23.0으로 했다. 플래그 서버와 SDK는 동작을 보려고 직접 짠 작은 것이다.

## 네 종류의 플래그는 운영 방식이 다르다

플래그를 용도로 나누는 분류(릴리스, 실험, 운영, 권한)는 [앞 글](/posts/ab-testing)에 있다. 운영하는 쪽에서 보면 이 분류가 중요한 이유는 종류마다 다뤄야 하는 방식이 달라서다.

| | 수명 | 누가 바꾸나 | 플래그 서비스가 죽으면 | 어디서 평가하나 |
|---|---|---|---|---|
| 릴리스 | 며칠~몇 주 | 개발팀 | 꺼진 쪽(옛 동작) | 서버·클라이언트 |
| 실험 | 실험 기간 | 제품팀 | 대조군 | 노출을 기록하는 곳 |
| 운영(킬 스위치) | 계속 | 당번(on-call) | 마지막으로 알던 값 | 서버 |
| 권한 | 계속 | 영업·운영 | 닫힌 쪽 | 서버 |

차이가 가장 큰 칸이 "플래그 서비스가 죽으면"이다. 릴리스 플래그는 답을 모를 때 옛 동작으로 가면 된다. 권한 플래그는 모를 때 닫아야 한다. 유료 기능을 공짜로 열어 주는 것보다 잠깐 막는 편이 낫다. 운영 플래그는 반대로 복잡하다. 장애 중에 끈 킬 스위치가 플래그 서비스 재시작과 함께 코드 기본값(켜짐)으로 돌아가면 장애가 다시 시작된다. 그래서 마지막으로 받은 값을 기억해 두는 장치가 필요하다.

권한 플래그는 오래 살기 때문에 결국 플래그 시스템에서 나와 요금제·권한 시스템으로 옮겨 가는 게 자연스럽다. 플래그 대시보드에서 계약 상태를 관리하기 시작하면, 누가 무엇에 접근하는지가 감사 기록이 약한 곳에 흩어진다.

## 규칙은 위에서부터 하나씩

플래그 하나에는 여러 규칙이 붙는다. "직원은 켜기", "앱 5.2 이상은 켜기", "특정 사용자는 끄기", "나머지 10%만 켜기". 평가 엔진은 이 규칙을 정해진 순서대로 보다가 처음 맞는 규칙에서 멈춘다. 순서가 결과를 바꾼다. 대부분의 플래그 서비스가 쓰는 순서는 이렇다.

1. 플래그가 꺼져 있으면 끈 값(off variant)을 돌려준다. 킬 스위치는 여기서 동작한다.
2. 개별 지정(individual targets). 특정 사용자 id를 콕 집어 정한 값이다. 버그를 신고한 사용자만 옛 화면으로 돌려놓을 때 쓴다.
3. 타기팅 규칙(targeting rules). 사용자의 속성(이메일 도메인, 앱 버전, 국가, 요금제)으로 조건을 건다. 위에서부터 처음 맞는 규칙을 쓴다.
4. 아무 규칙에도 안 맞으면 기본 분배(fallthrough). 퍼센트 롤아웃이 여기서 해시 버킷으로 정해진다.

## 설정은 어떻게 서버에 닿나

처음의 30초 이야기로 돌아가자. 대부분의 서버 SDK는 플래그를 요청마다 원격에 묻지 않는다. 시작할 때 전체 규칙을 받아 메모리에 두고, 요청이 오면 로컬에서 평가한다. 요청마다 네트워크를 타면 플래그 하나에 수 밀리초가 붙고, 플래그 서비스가 느려지면 모든 요청이 느려지기 때문이다. 대신 규칙이 바뀌면 그 변경을 받아 와야 하는데, 방법이 둘이다. 주기적으로 묻는 폴링(polling), 서버가 연결을 열어 두고 바뀔 때 밀어 주는 스트리밍(streaming, 대개 SSE)이다.

직접 확인하려고 작은 플래그 서버와 SDK를 짰다. 서버는 `GET /flags`(폴링용)와 `GET /stream`(SSE)을 열고, SDK 하나는 5초마다 폴링하고 다른 하나는 스트림을 듣는다. 둘을 띄우고 1.2초쯤 뒤에 킬 스위치를 내렸다.

```bash
# 플래그 서버와 두 가지 SDK를 띄우고, 킬 스위치를 내린다
node flag-server.mjs &
node sdk-client.mjs poll 5000 > poll.log &
node sdk-client.mjs stream > stream.log &
sleep 1.3
curl -s -X POST -d '{"enabled":false}' http://127.0.0.1:4200/flags/recs-widget
```

```text
[poll] + 5303ms got v2 enabled=false
```

스트리밍이 늘 나은 건 아니다. 서버 수천 대가 연결을 계속 열어 두니 플래그 서비스와 그 앞 프록시가 장시간 연결을 견뎌야 한다. 로드 밸런서의 유휴 타임아웃이 60초인데 SSE에 하트비트가 없으면 연결이 조용히 끊긴다. 그래서 상용 SDK는 스트림을 쓰다가 끊기면 다시 연결하고, 그동안은 폴링으로 버티는 식으로 둘을 섞는다. 서버리스 함수처럼 짧게 사는 프로세스는 연결을 열어 둘 수 없어서, 가까운 저장소(엣지 설정 저장소나 Redis)에 규칙을 복제해 두고 거기서 읽는 방식을 쓴다.

## 플래그 서비스가 죽으면

플래그 서비스도 장애가 난다. 이때 SDK가 무엇을 하느냐가 서비스 전체의 동작을 정한다. 실습에서 플래그 서버를 꺼 봤다.

```text
[poll] + 5303ms got v2 enabled=false
[poll] +15300ms poll failed (ECONNREFUSED), keep last known: enabled=false
[poll] +20304ms poll failed (ECONNREFUSED), keep last known: enabled=false
```

이미 값을 받아 둔 폴링 SDK는 마지막으로 알던 값(off)을 계속 쓴다. 킬 스위치는 꺼진 채로 남는다. 반면 직접 짠 스트림 클라이언트는 연결이 끊기자 그대로 죽었다.

```text
node:internal/deps/undici/undici:11322

TypeError: terminated
```

재연결 로직이 없는 스트림 클라이언트는 이렇게 된다. 상용 SDK를 쓰는 이유 중 하나가 이런 경계 처리다. 더 위험한 건 서버가 죽은 상태에서 새로 뜬 프로세스다.

```bash

node sdk-client.mjs poll 5000
```

```text

```

받아 둔 값이 없으니 코드에 적은 기본값을 쓴다. 이 기본값이 `true`였다면, 장애 중에 오토스케일링으로 뜬 새 서버들은 꺼 둔 추천 영역을 다시 켠다. 그래서 플래그를 부를 때 넘기는 기본값은 "아무것도 모를 때 가장 안전한 쪽"으로 정한다. 킬 스위치처럼 마지막 값이 중요한 플래그는 디스크나 공유 캐시에 마지막 규칙을 남겨 두고(상용 SDK 대부분이 이런 지속 저장 옵션을 준다), 시작할 때 그걸 먼저 읽게 한다.

## 서버에서 평가할까, 브라우저에서 평가할까

## 벤더에 묶이지 않게 OpenFeature

플래그 서비스는 LaunchDarkly, Unleash, Flagsmith, GrowthBook, 클라우드 업체의 설정 서비스까지 종류가 많고, SDK의 함수 이름도 제각각이다. 코드 수백 곳에 특정 벤더의 SDK 호출이 박혀 있으면 서비스를 옮기기 어렵다. OpenFeature는 CNCF 프로젝트로, 플래그 평가 API를 표준으로 정하고 벤더별 차이는 공급자(provider)에 맡긴다. 로깅에서 SLF4J나 OpenTelemetry가 하는 역할과 비슷하다.

## 플래그가 늘면 테스트할 조합이 폭발한다

켜기·끄기 플래그가 n개면 가능한 조합은 2ⁿ개다. 플래그 10개면 1,024가지다. 모든 조합을 테스트할 수는 없다. 다행히 실제 버그 대부분은 플래그 한두 개의 상호작용에서 나온다. 그래서 모든 두 플래그 쌍의 네 가지 값(on·on, on·off, off·on, off·off)이 적어도 한 번씩 나오도록 조합을 고르는 쌍대 테스트(pairwise testing)를 쓴다. 탐욕적으로 고르는 스크립트를 돌려 봤다.

```bash
# 켜기/끄기 플래그 n개의 모든 두 개 쌍을 덮는 조합을 찾는다
python3 pairwise.py 6
python3 pairwise.py 10 | head -1
```

```text
flags=6 all=64 pairwise=7
off off off off off off
off on  on  on  on  on 
on  off off off on  on 
on  on  on  on  off off
off off off on  off on 
off off on  off on  off
off on  off off off off
flags=10 all=1024 pairwise=9
```

64가지 대신 7가지, 1,024가지 대신 9가지면 모든 쌍을 한 번씩 본다. 탐욕적으로 고른 값이라 이론상 최솟값보다 조금 많다. 실무에서는 여기에 두 조합을 반드시 더한다. 지금 운영에 실제로 켜져 있는 조합, 그리고 다음 배포 후 켜질 조합이다. 테스트 코드에서는 플래그 SDK를 직접 부르지 말고 OpenFeature의 메모리 공급자처럼 값을 주입할 수 있는 구조로 만들어 둬야 조합을 바꿔 가며 돌릴 수 있다.

더 나은 방법은 조합 자체를 줄이는 것이다. 다 켠 릴리스 플래그를 지우면 n이 줄어든다.

## 플래그를 바꾸는 것도 운영 변경이다

플래그를 끄고 켜는 건 배포가 아니라서 배포 절차의 검토와 기록을 건너뛰기 쉽다. 하지만 사용자가 보는 동작은 배포만큼 바뀐다. 구글의 SRE 책은 장애의 70% 정도가 운영 중인 시스템을 바꾸는 데서 온다고 적었는데, 플래그 변경도 그 "바꾸는 일"에 들어간다. 그래서 배포와 같은 장치가 필요하다.

- 누가 언제 무엇을 바꿨는지 감사 기록을 남기고, 바꿀 때 이유를 적게 한다.
- 운영 환경의 규칙 변경은 리뷰를 거치게 한다. 대부분의 서비스가 승인 흐름을 기능으로 준다. 단 킬 스위치는 예외로 당번이 바로 끌 수 있게 둔다.
- 변경 이벤트를 모니터링 대시보드에 세로선으로 찍는다. 에러율이 오른 시각에 배포는 없었는데 플래그 변경이 있었다면 거기서부터 본다.
- 퍼센트를 올릴 때는 1% → 5% → 25% → 100%처럼 단계를 두고, 단계마다 지표를 본다. 이건 사실상 플래그로 하는 [카나리 배포](/posts/canary-release)다.

## 다 켠 플래그를 지우는 일

플래그가 빚이 되는 이유와 Knight Capital 사례는 [앞 글](/posts/ab-testing)에 있다. 여기서는 지우는 일을 어떻게 굴리는지만 본다. 핵심 아이디어는 사람의 기억에 기대지 않고 코드와 설정을 기계로 맞대어 보는 것이다. 장난감 저장소에 스크립트를 돌려 봤다. 코드에서 `isOn("...")` 호출을 모으고, 플래그 설정과 비교한다.

```bash
# 코드의 플래그 호출과 플래그 설정을 맞대어 본다
node find-stale-flags.mjs 2026-10-21
```

```text
STALE      new-checkout = on 100% for 141d → src/checkout.ts:1 (pay-team)
UNUSED     holiday-banner (설정에만 있음, growth)
UNUSED     search-typo-fix (설정에만 있음, search)
MISSING    serch-typo-fix at src/search.ts:2 (설정에 없음: 늘 기본값으로 평가된다)
```

네 줄이 각각 다른 일을 시킨다. `STALE`은 140일 넘게 100% 켜진 릴리스 플래그다. 코드에서 분기를 지우고 켜진 쪽만 남긴 뒤, 배포가 끝나면 설정에서도 지운다. 순서가 중요하다. 설정을 먼저 지우면 아직 그 플래그를 읽는 서버가 기본값(대개 off)으로 돌아가 옛 화면이 다시 나온다. `UNUSED`는 코드에서 이미 지운 플래그라 설정만 정리하면 된다. `MISSING`이 가장 반갑다. 코드의 `serch-typo-fix`는 오타라서 설정의 `search-typo-fix`와 이어지지 않았고, 대시보드에서 50%로 켰다고 믿는 기능이 실제로는 아무에게도 켜지지 않았다. OpenFeature 실습에서 본 `FLAG_NOT_FOUND`와 같은 문제다. 운영 플래그 `ops-recs-widget`은 100% 켜져 있지만 일부러 남기는 것이라 목록에서 뺐다.

이 검사를 CI에 넣고, 플래그를 만들 때 주인과 만료일을 필수로 받으면 정리가 습관이 된다. 플래그 이름을 문자열 대신 상수나 생성된 타입으로 쓰게 하면 `MISSING` 같은 오타는 컴파일 단계에서 잡힌다.

## 스위치 하나 뒤에 있는 시스템

피처 플래그는 코드의 `if`와 그 답을 정하는 원격 시스템의 짝이다. 답은 규칙 순서대로 정해지고, 스트림이나 폴링으로 서버에 닿고, 닿지 않을 때는 마지막 값이나 안전한 기본값으로 버틴다. 브라우저에는 규칙이 아니라 결과만 보내고, 평가가 실패해도 조용히 기본값이 나가니 reason을 지표로 본다. 그리고 다 쓴 플래그는 코드에서 먼저, 설정에서 나중에 지운다. 실험에 쓰는 플래그의 통계 쪽은 [A/B 테스트와 피처 플래그](/posts/ab-testing)를, 플래그로 해결되지 않는 되돌리기는 [롤백 전략](/posts/rollback-strategy)을 본다.

## 면접에서 나올 만한 질문

### 피처 플래그와 환경 변수 설정은 무엇이 다른가요?

환경 변수는 배포 단위로 모든 요청에 같은 값을 주고, 바꾸려면 재시작이나 재배포가 필요하다. 플래그는 실행 중에 바뀌고, 사용자 맥락에 따라 다른 값을 돌려줄 수 있다. 그래서 배포와 공개를 떼어 놓고, 일부 사용자에게만 켜고, 장애 때 재배포 없이 끌 수 있다.

### 플래그 평가 규칙은 어떤 순서로 적용되나요?

보통 플래그 꺼짐 → 개별 지정 → 타기팅 규칙(위에서부터 처음 맞는 것) → 기본 분배(퍼센트 롤아웃) 순이다. 처음 맞는 곳에서 멈추기 때문에 규칙 순서를 바꾸면 결과가 바뀐다. 규칙이 보는 속성을 맥락에 넣지 않으면 조건이 조용히 거짓이 되어 모두 기본 분배로 떨어진다.

### 킬 스위치를 내렸는데 일부 서버만 늦게 반응합니다. 왜 그런가요?

서버 SDK가 규칙을 메모리에 들고 로컬에서 평가하고, 변경을 폴링으로 받고 있어서다. 다음 폴링 전까지는 옛 값을 쓴다. 실습에서는 스트림 SDK가 바로 받았고 5초 폴링 SDK는 4초 늦게 따라왔다. 킬 스위치가 중요한 서비스는 스트리밍을 쓰고 끊기면 폴링으로 보완하며, 무거운 호출을 하기 전에 플래그를 보는지도 확인한다.

### 플래그 서비스가 죽으면 앱은 어떻게 동작해야 하나요?

이미 받은 값이 있으면 마지막으로 알던 값을 계속 쓰고, 없으면 코드의 기본값을 쓴다. 그래서 기본값은 "아무것도 모를 때 가장 안전한 쪽"으로 정한다. 장애 중에 새로 뜬 서버가 기본값으로 킬 스위치를 다시 켜지 않게, 마지막 규칙을 디스크나 공유 캐시에 남겨 두고 시작할 때 먼저 읽게 한다.

### 브라우저에서 플래그를 평가할 때 주의할 점은요?

규칙 전체를 내려보내지 않는다. 미공개 기능 이름, 직원 도메인, 고객사 id가 사용자에게 노출된다. 맥락을 서버에 보내 평가한 결과만 받고, 권한에 관련된 속성은 클라이언트가 보낸 값을 믿지 말고 서버가 세션에서 붙인다. 클라이언트 플래그는 화면 제어일 뿐 보안 장치가 아니라 API는 서버에서 따로 막는다.

### OpenFeature를 쓰면 무엇이 좋아지나요?

앱 코드가 표준 평가 API만 알고 벤더 차이는 공급자가 맡아서, 플래그 서비스를 바꿀 때 호출 코드를 고치지 않아도 된다. 평가 결과에 reason과 errorCode가 표준으로 붙고, 훅으로 로그와 지표를 벤더와 무관하게 남길 수 있다. 오타나 타입 오류가 예외 없이 기본값으로 묻히므로 ERROR reason 비율을 지표로 보는 게 좋다.

### 플래그가 많아지면 테스트는 어떻게 하나요?

모든 조합(2ⁿ)은 불가능하니 모든 두 플래그 쌍의 값을 덮는 쌍대 테스트를 쓰고, 지금 운영 조합과 다음 배포 후 조합을 반드시 더한다. 실습에서는 6개 플래그를 64가지 대신 7가지로 덮었다. 테스트에서 값을 주입할 수 있게 플래그 호출을 추상화해 두고, 근본적으로는 다 켠 플래그를 지워 n을 줄인다.

### 다 켠 플래그는 어떤 순서로 지우나요?

코드에서 분기를 먼저 지우고 켜진 쪽만 남겨 배포한 뒤, 모든 서버가 새 코드로 바뀌면 설정에서 지운다. 설정을 먼저 지우면 아직 플래그를 읽는 서버가 기본값으로 돌아가 옛 동작이 되살아난다. 코드의 플래그 호출과 설정을 기계로 맞대어 오래된 플래그, 쓰이지 않는 설정, 설정에 없는 호출(오타)을 찾는 검사를 CI에 둔다.
