<EasyIntro>

  집의 전기·수도 요금과 닮았다. 요금은 전등을 켜 둔 시간과 수도꼭지로 흘러간 물의 양으로 매겨진다. 그래서 아무도 없는 방의 불을 끄고, 너무 밝은 전등은 알맞은 크기로 바꾸고, 늘 쓰는 만큼은 미리 약정해 싸게 산다. 물은 비싼 계량기를 지나지 않는 길로 돌리면 같은 양을 써도 요금이 준다. 오래 안 꺼낼 물건은 싼 창고로 옮긴다.

  마지막으로 방마다 이름표를 붙여야 한다. 누구 방에서 쓴 요금인지 모르면 다들 자기 것이 아니라고 생각해서 아무도 줄이지 않는다.

월초에 청구서를 열었더니 지난달보다 1,500달러가 늘었다. 트래픽은 그대로고 서버도 늘린 적이 없다. 서비스별로 나눠 보니 EC2 항목이 늘었는데, EC2 인스턴스 요금은 그대로다. 더 들어가 보니 늘어난 건 `EC2-Other` 안의 `NatGateway-Bytes`였다. 새로 붙인 로그 수집기가 프라이빗 서브넷에서 S3로 하루 800GB를 보내고 있었고, 그 트래픽이 전부 NAT 게이트웨이를 지나며 GB마다 요금을 냈다.

클라우드 비용은 대개 이렇게 늘어난다. 누가 큰 결정을 해서가 아니라 작은 설정이 쌓여서다. 이 글은 돈이 어디로 나가는지(컴퓨팅, 데이터 전송, NAT, 놀고 있는 자원, 저장소 등급)를 보고, 줄이는 방법(크기 맞추기, 약정 할인과 스팟, 오토스케일링)과 팀별로 비용을 나눠 보여 주는 태깅을 다룬다. 요금은 AWS us-east-1 공개 요금 기준이고 2026년 10월 확인 값이다. 리전마다 다르고(서울은 대체로 조금 비싸다) 자주 바뀌니 계산 방법을 익히는 데 쓴다. AWS CLI와 Cost Explorer 출력은 계정 없이 실제 형식대로 쓴 예시이고, jq와 Node로 돌린 집계는 예시 데이터에 실제로 돌린 결과다.

이 주제의 다른 글: 서버리스 요금이 메모리와 시간으로 어떻게 정해지는지는 [서버리스의 한계](/posts/serverless-limits)에서, 부하에 맞춰 대수를 늘리고 줄이는 원리는 [오토스케일링](/posts/autoscaling)에서 다룬다.

## 데이터가 지나가는 길에 요금소가 있다

컴퓨팅 다음으로 큰 돈은 대개 데이터 전송에서 나온다. 들어오는 트래픽은 거의 무료지만 나가는 트래픽과 몇몇 장비를 지나는 트래픽은 GB마다 요금이 붙는다. us-east-1 기준으로 인터넷으로 나가는 데이터는 월 100GB 무료 뒤 GB당 0.09달러부터, AZ를 건너는 데이터는 방향마다 GB당 0.01달러, NAT 게이트웨이는 시간당 0.045달러에 처리한 데이터 GB당 0.045달러다. 아래 그림에서 다음을 누르면 같은 서버가 보내는 데이터가 어느 길로 가느냐에 따라 요금이 어떻게 달라지는지 볼 수 있다.

NAT와 엔드포인트가 라우트 테이블에서 어떻게 동작하는지는 [서브넷과 라우트 테이블](/posts/vpc-subnets-route-tables)에서, 인터페이스 엔드포인트의 요금 구조는 [VPC 연결](/posts/vpc-peering-transit-privatelink)에서 다뤘다. 여기서 기억할 것은 하나다. 프라이빗 서브넷에서 AWS 서비스로 가는 큰 트래픽이 있으면 NAT 요금부터 의심한다. 컨테이너 이미지를 매번 ECR에서 받는 노드, CloudWatch로 로그를 보내는 에이전트, S3 백업이 단골이다.

## 아무도 쓰지 않는데 돈이 나가는 것들

놀고 있는 자원은 줄이기 가장 쉬운 돈이다. 단골은 이렇다.

- 인스턴스를 지운 뒤 남은 EBS 볼륨(`available` 상태)과 오래된 스냅숏
- 연결되지 않은 공인 IPv4. 2024년 2월부터는 연결 여부와 상관없이 공인 IPv4 하나에 시간당 0.005달러, 한 달 3.6달러가 붙는다
- 개발·스테이징 환경이 밤과 주말에도 떠 있는 것
- 트래픽이 없는 로드 밸런서, 아무도 쓰지 않는 NAT 게이트웨이
- 보관 기간 없이 쌓이는 CloudWatch 로그 그룹(기본값이 "영구 보관"이다)

예를 들어 붙어 있지 않은 볼륨은 이렇게 찾는다. 아래 출력은 예시 JSON(`aws ec2 describe-volumes` 응답 형식)에 jq를 실제로 돌린 결과다.

```bash
# 어디에도 붙지 않은 볼륨을 ID, 종류, 크기, 생성일, team 태그로 뽑는다
aws ec2 describe-volumes --filters Name=status,Values=available > volumes.json
jq -r '.Volumes[] | select(.State=="available")
  | [.VolumeId, .VolumeType, (.Size|tostring)+"GiB", .CreateTime[0:10],
     ((.Tags // []) | map(select(.Key=="team"))[0].Value // "-")] | @tsv' volumes.json
```

```text
vol-0a1b2c3d4e5f60001	gp2	500GiB	2025-11-03	data
vol-0a1b2c3d4e5f60003	io2	2000GiB	2026-04-22	-
```

둘째 줄이 위험한 종류다. 2TB짜리 io2인데 태그가 없어서 누구 것인지 모른다. io2는 용량뿐 아니라 예약한 IOPS에도 요금이 붙어 한 달에 수백 달러가 나갈 수 있다. 지우기 전에 스냅숏을 하나 떠 두면, 잘못 지워도 되살릴 수 있다. 같은 jq로 gp2 볼륨도 찾는다. gp3는 같은 용량에서 gp2보다 GB당 20% 싸고(0.10달러 대 0.08달러) 기본 성능도 3,000 IOPS로 고정이라, 대부분 성능 손해 없이 볼륨을 온라인으로 바꿀 수 있다.

```bash
# gp2 볼륨마다 gp3로 바꾸면 한 달에 얼마나 줄어드는지 본다 (GB당 0.02달러 차이)
jq -r '.Volumes[] | select(.VolumeType=="gp2")
  | "\(.VolumeId) \(.Size)GiB gp2 → gp3 saves $\(.Size*0.02|tostring)/month"' volumes.json
# 붙어 있는 채로 종류를 바꾼다 (중단 없음)
aws ec2 modify-volume --volume-id vol-0a1b2c3d4e5f60004 --volume-type gp3
```

```text
vol-0a1b2c3d4e5f60001 500GiB gp2 → gp3 saves $10/month
vol-0a1b2c3d4e5f60004 200GiB gp2 → gp3 saves $4/month
```

개발 환경은 시간표로 끈다. 평일 9시부터 21시까지만 켜면 주 168시간 중 60시간만 쓰니 64%가 준다. 오토스케일링 그룹의 예약 작업이나 EventBridge 스케줄러로 대수를 0으로 내리면 된다. 다만 RDS는 멈춰도 7일 뒤 자동으로 다시 켜지니 그것까지 스케줄에 넣는다.

<Callout kind="warning">
놀고 있어 보이는 자원을 일괄 삭제하는 스크립트는 운영 데이터를 지우는 가장 흔한 길이다. 지우기 전에 태그로 주인을 찾고, 볼륨은 스냅숏을, 버킷은 버전 관리나 다른 곳 복사를 먼저 해 둔다. 처음에는 지우지 말고 `stop` 또는 태그(`delete-after=2026-11-01`)만 붙여 두었다가 그 날짜까지 아무도 찾지 않으면 지운다.
</Callout>

## 저장소는 꺼내는 횟수로 등급을 고른다

S3는 같은 데이터라도 등급에 따라 보관 요금이 스무 배 넘게 다르다. us-east-1 기준 Standard가 GB-월 0.023달러, Standard-IA가 0.0125달러, Glacier Instant Retrieval이 0.004달러, Glacier Deep Archive가 0.00099달러다. 싼 등급일수록 꺼낼 때 요금이 붙고, 최소 보관 기간(IA 30일, Glacier IR 90일, Deep Archive 180일)이 있어서 그 전에 지워도 남은 기간 요금을 낸다. 아주 작은 객체(128KB 미만)는 IA 계열에서 128KB로 쳐서 받는다.

그래서 "얼마나 자주 꺼내나"로 고른다. 30일 지난 로그는 거의 다시 보지 않으니 IA로, 1년 지난 감사 로그는 Deep Archive로 옮기는 수명 주기 규칙을 건다. 꺼내는 패턴을 모르겠으면 Intelligent-Tiering이 접근 기록을 보고 등급을 알아서 옮긴다(객체 수에 따라 작은 관리 요금이 있다). 반대로 자주 꺼내는 데이터를 IA에 두면 꺼내는 요금이 아낀 보관 요금보다 커진다.

```bash
# 30일 뒤 IA, 365일 뒤 Deep Archive, 3년 뒤 삭제하는 규칙을 건다
aws s3api put-bucket-lifecycle-configuration --bucket logs-archive \
  --lifecycle-configuration file://lifecycle.json
```

```text
{
  "Rules": [
    {
      "ID": "logs-tiering",
      "Filter": { "Prefix": "app/" },
      "Status": "Enabled",
      "Transitions": [
        { "Days": 30, "StorageClass": "STANDARD_IA" },
        { "Days": 365, "StorageClass": "DEEP_ARCHIVE" }
      ],
      "Expiration": { "Days": 1095 }
    }
  ]
}
```

(`lifecycle.json`의 내용이다.) 버전 관리를 켠 버킷이라면 이전 버전에도 `NoncurrentVersionExpiration`을 걸어야 한다. 안 그러면 지운 줄 알았던 객체가 이전 버전으로 계속 요금을 낸다. EBS 스냅숏, 로그 그룹 보관 기간도 같은 원리로 정리한다.

## 크기를 맞추고 나서 약정을 건다

컴퓨팅 비용을 줄이는 순서는 정해져 있다. 먼저 크기를 맞추고(rightsizing), 그다음 늘 쓰는 바닥에 약정을 걸고, 들쭉날쭉한 부분은 오토스케일링과 스팟으로 받는다. 순서를 거꾸로 하면 지나치게 큰 서버에 3년 약정을 거는 일이 생긴다.

크기 맞추기는 지표에서 시작한다. CPU 평균이 아니라 2주 정도의 최댓값이나 p95를 본다. 평균 8%라도 매일 밤 배치에서 90%를 찍는 서버를 줄이면 배치가 터진다.

```bash
# 지난 14일 동안 1시간 단위 CPU 최댓값을 본다
aws cloudwatch get-metric-statistics --namespace AWS/EC2 \
  --metric-name CPUUtilization --dimensions Name=InstanceId,Value=i-07c3b1a9e0d4f2a11 \
  --start-time 2026-10-07T00:00:00Z --end-time 2026-10-21T00:00:00Z \
  --period 3600 --statistics Maximum
```


(예시이고, 실제로는 336개 점이 나온다.) 최댓값이 2주 내내 20%를 넘지 않는다면 한 단계 작은 크기로 내려도 된다. 메모리는 기본 지표에 없어서 CloudWatch 에이전트를 깔아야 보인다. 메모리를 모른 채 줄이는 게 크기 맞추기의 가장 흔한 사고다. AWS Compute Optimizer가 같은 분석을 자동으로 해 주고, 쿠버네티스라면 Pod의 requests를 실제 사용량에 맞추는 것이 노드 수를 줄이는 길이다([requests와 limits](/posts/k8s-pod-resources)). 같은 세대라면 Graviton(ARM) 인스턴스가 비슷한 성능에 대략 20% 싸다. 이미지가 ARM으로 빌드되는지만 확인하면 된다.

## 급하지 않은 일은 한가한 시간으로 옮긴다

스팟이 "싼 자원을 사는" 방법이라면, 부하 이동(load shifting)은 일을 싼 자리로 옮기는 방법이다. 결과가 당장 필요하지 않은 일이 생각보다 많다. 리포트 생성, 썸네일 변환, 검색 색인 재구축, ML 학습, 로그 집계 같은 것들이다.

시간을 옮기면 먼저 약정이 살아난다. Savings Plans는 시간당 금액을 약속한 것이라 새벽에 서버가 줄어 쓰지 못한 약정은 그냥 버려진다. 밤마다 남는 그 자리에 배치를 넣으면 추가 요금 없이 돈다. 쿠버네티스 클러스터도 같다. 낮 피크에 맞춰 둔 노드가 새벽에 비어 있다면 배치를 그 시간에 몰아 노드를 더 늘리지 않는다. 스팟 가격과 회수 빈도도 수요에 따라 움직이니 한가한 시간에 돌리면 대개 유리하다. 다만 보장되는 건 아니라서 스팟 가격 이력을 보고 정한다. 온디맨드 요금 자체는 시간대에 따라 바뀌지 않는다.

장소를 옮기는 방법도 있다. 같은 인스턴스라도 리전마다 값이 다르고, 서울 리전은 미국 동부보다 대체로 비싸다. 학습이나 대량 변환처럼 계산은 많고 결과는 작은 일은 싼 리전에서 돌릴 만하다. 대신 리전을 건너는 전송 요금이 GB 단위로 붙으니(출발 리전에 따라 다르고 아시아 리전에서 나갈 때가 더 비싸다) 입력 데이터가 크면 계산이 뒤집힌다. 개인정보처럼 국외로 옮기면 안 되는 데이터는 처음부터 후보가 아니다.

피크를 아예 깎는 방법도 있다. 요청을 바로 처리하지 않고 큐에 넣어 두면, 처리하는 쪽은 피크가 아니라 평균에 맞춰 둘 수 있다. 하루 중 10시간은 시간당 1,000건, 나머지 14시간은 100건이 들어오고 서버 한 대가 시간당 100건을 처리한다고 하자.

- 피크에 맞추면 10대를 24시간 띄운다. 하루 240 인스턴스-시간이다.
- 큐에 쌓고 5대(시간당 500건)로 고정하면 피크 10시간 동안 5,000건이 밀리고, 남은 14시간 동안 시간당 400건씩 5,600건을 더 처리할 수 있어 하루 안에 다 비운다. 하루 120 인스턴스-시간, 절반이다.

대가는 지연이다. 피크가 끝나는 순간 줄 끝에 선 작업은 10시간 뒤에야 처리된다. 그래서 이 방법은 사용자가 기다리지 않는 일에만 쓰고, 큐 깊이로 워커를 늘리고 줄이며(이때 워커는 스팟이 잘 맞는다) "몇 시간 안에는 끝난다"는 약속을 따로 정한다. 큐를 두고 처리 속도를 고르게 만드는 패턴 자체는 [큐 기반 부하 평준화](/posts/queue-based-load-leveling)에서 자세히 다룬다.

## 작은 서버 여러 대를 한곳에 모은다

서비스마다 t3.small 한 대씩 띄우는 식으로 시작하면 서버가 금방 수십 대가 된다. 하나하나는 CPU 5%, 메모리 30%로 놀고 있는데, 인스턴스마다 OS와 모니터링 에이전트, 로그 수집기가 메모리를 먼저 차지하고 최소 두 대씩 띄우는 가용성 비용도 서비스마다 붙는다. 컴퓨트 통합(consolidation)은 이런 작은 워크로드를 큰 호스트나 공용 클러스터(ECS, 쿠버네티스)에 모아 빈 공간을 줄이는 것이다. 쿠버네티스라면 requests를 기준으로 Pod를 노드에 빽빽이 채우고, Karpenter의 consolidation이 덜 찬 노드의 Pod를 옮긴 뒤 노드를 지운다.

모으면 시끄러운 이웃(noisy neighbor) 문제가 따라온다. 한 서비스가 CPU를 다 쓰면 옆 서비스의 응답이 느려지고, 메모리를 넘게 쓰면 노드에서 다른 Pod가 쫓겨나거나 OOM으로 죽는다. 디스크 I/O와 네트워크 대역폭은 제한을 걸기도 어렵다. 증상은 "우리 코드는 안 바뀌었는데 p99만 튄다"로 온다. 그 시각에 같은 노드에서 무엇이 돌았는지, CPU 스로틀링 지표(`container_cpu_cfs_throttled_periods_total`)가 올랐는지 본다. 노드 한 대가 죽을 때 함께 쓰러지는 서비스가 많아지는 것도 같은 대가다.

그래서 모으는 정도를 고른다. 모든 Pod에 requests와 limits를 걸어 서로의 몫을 정하고([requests와 limits](/posts/k8s-pod-resources)), 지연에 민감한 서비스와 배치는 노드 그룹을 나누며, 같은 서비스의 복제본은 여러 노드와 AZ에 흩어 둔다. 노드 활용률을 무작정 90%로 올리기보다 60~70% 언저리에서 멈추는 팀이 많은 이유다. 남긴 여유가 스파이크와 노드 장애를 받는 자리다.

## 서버리스냐 상시 서버냐는 계산으로 고른다

[서버리스의 한계](/posts/serverless-limits)에서 꾸준히 바쁜 일은 서버리스가 비싸다고 했다. 얼마나 바빠야 비싸지는지는 계산해 보면 된다. Lambda(x86)는 요청 100만 건에 0.20달러, GB-초당 0.0000166667달러다. 한 달을 30일(2,592,000초)로 잡고 월 요금을 계산해 보자.

## 태그가 없으면 누구 돈인지 모른다

비용을 줄이려면 그 비용의 주인이 있어야 한다. 주인을 찾는 장치가 태그다. 모든 자원에 `team`, `service`, `env` 같은 태그를 붙이고, 결제 콘솔에서 비용 할당 태그로 활성화하면 Cost Explorer와 비용 리포트(CUR)에서 태그별로 나눠 볼 수 있다. 팀마다 자기 몫을 보여 주는 것을 쇼백(showback), 실제로 팀 예산에서 빼는 것을 차지백(chargeback)이라고 한다.

아래는 비용 리포트에서 뽑은 예시 줄 10개를 `team` 태그로 묶는 스크립트를 실제로 돌린 결과다.

```bash
# 비용 줄(resource_id, service, usage_type, team, cost)을 team별로 합친다
node showback.js cur.csv
```

```text
(untagged)     $2533.52  36.1%
order          $2160.40  30.8%
search         $1702.15  24.3%
data            $402.31   5.7%
media           $212.77   3.0%
total          $7011.15
```

가장 큰 몫이 "태그 없음"이다. 들여다보면 NAT 게이트웨이, 이름 모를 r7g.large, 2TB io2 볼륨, 놀고 있는 공인 IP다. 공유 인프라(NAT, 공용 클러스터)는 원래 한 팀 것이 아니니 트래픽 비율이나 요청 비율로 나누는 규칙을 정해 두고, 나머지는 태그를 붙인다. 태그 없는 비용이 10%를 넘으면 쇼백은 의미를 잃는다. 다들 "그건 우리 게 아닐 거야"라고 생각하기 때문이다.

태그를 사람이 기억해서 붙이게 두면 금방 빠진다. Terraform의 `default_tags`로 모든 자원에 기본 태그를 넣고, AWS Organizations의 태그 정책과 SCP로 태그 없이 만드는 것을 막는다. 쿠버네티스는 노드 비용을 네임스페이스와 레이블로 나눠 주는 Kubecost나 OpenCost 같은 도구를 쓴다. 그리고 예산(AWS Budgets)과 이상 탐지(Cost Anomaly Detection)를 걸어 청구서보다 먼저 알림을 받는다. 맨 앞의 NAT 사고도 이상 탐지가 있었다면 둘째 날 알았을 것이다.

### 줄이고 끝내지 않고 주기로 돌린다

태그는 시작일 뿐이다. 비용 관리를 엔지니어링과 재무가 함께 하는 일로 보는 흐름을 FinOps라고 하고, FinOps Foundation은 이를 세 단계가 도는 주기로 설명한다. 가시화(Inform)는 태그와 비용 리포트로 누가 얼마를 쓰는지 보이게 하는 단계, 최적화(Optimize)는 이 글에서 본 크기 맞추기·약정·스팟·삭제를 하는 단계, 운영(Operate)은 그것을 예산과 정책, 정기 리뷰로 굳히는 단계다. 한 바퀴 돌고 끝나는 게 아니라, 새 서비스가 생기면 다시 가시화부터 돈다.

운영 단계의 도구는 두 가지 경보다. AWS Budgets는 월 예산을 정해 두고 실제 금액이나 예측 금액이 예산의 몇 %를 넘으면 알린다. 예측 기준 알림을 걸어야 월말 전에 손을 쓸 수 있다. 예산을 넘으면 IAM 정책을 붙이거나 개발 계정의 EC2를 멈추는 동작(budget action)도 걸 수 있다. Cost Anomaly Detection은 정해진 금액이 아니라 평소 패턴에서 벗어난 증가를 잡는다. 서비스, 계정, 비용 할당 태그 단위로 모니터를 만들고 "평소보다 100달러 이상" 같은 기준으로 알림을 받는다. 둘 다 청구 데이터가 하루에 몇 차례 갱신되는 것을 기다리므로 실시간 경보가 아니다. 몇 시간 안에 알아야 하는 사고는 CloudWatch 지표(NAT의 `BytesOutToDestination` 같은 사용량 지표)에 따로 경보를 건다.

쇼백과 차지백은 숫자는 같아도 무게가 다르다. 쇼백은 보여 주기만 하니 시작하기 쉽고 틀려도 큰일이 아니다. 차지백은 그 돈이 팀 예산에서 실제로 빠지니, 공유 인프라를 나누는 비율, 약정 할인을 누구 몫으로 칠지(선결제를 기간에 나눠 얹는 amortized 비용으로 볼지) 같은 규칙을 팀들이 먼저 합의해야 한다. 태그 없는 비용이 많은 상태에서 차지백부터 하면 숫자를 두고 다투느라 정작 줄이지 못한다. 보통 쇼백으로 몇 달 숫자를 맞춘 뒤 차지백으로 넘어간다.

## 비용이 튀었을 때 보는 순서

현장에서는 대개 이 순서로 좁힌다.

1. Cost Explorer를 일 단위로 놓고 어느 날부터 늘었는지 찾는다. 그날의 배포, 설정 변경, 새로 붙인 에이전트를 맞춰 본다.
2. 서비스별로 나눈 뒤, 늘어난 서비스를 사용 유형별로 다시 나눈다. `EC2-Other`가 늘었다면 NAT, 데이터 전송, EBS 중 무엇인지 여기서 갈린다.
3. NAT가 늘었으면 [흐름 로그](/posts/network-flow-logs)에서 NAT의 ENI를 지나는 상위 목적지를 본다. AWS 서비스 대역이면 엔드포인트로 돌린다.
4. 데이터 전송이 늘었으면 인터넷으로 나가는지(`DataTransfer-Out-Bytes`), AZ를 건너는지(`DataTransfer-Regional-Bytes`) 본다. 앞쪽은 CDN과 압축, 뒤쪽은 같은 AZ로 붙이는 설정을 검토한다.
5. 컴퓨팅이 늘었으면 오토스케일링 최대값과 이벤트 기록을 본다. 재시도 폭풍이나 봇 트래픽이 진짜 부하처럼 보여 늘린 경우가 있다.

흔한 실수도 정리해 둔다. 개발 계정에 예산 알림이 없다. 로그 그룹 보관 기간을 정하지 않는다. 디버그 로그 레벨을 운영에 켠 채 둬서 로그 수집 요금(GB당 0.50달러)이 서버 값보다 커진다. 약정 할인을 크기 맞추기 전에 산다. 스팟에 타입 하나만 지정한다. 그리고 비용을 한 번 줄이고 끝낸다. 비용은 줄인 다음 달부터 다시 붙기 시작하니, 매달 같은 순서로 위에서부터 읽는 습관이 가장 큰 절약이다.

## 바이트와 시간에 요금이 붙는다

클라우드 비용은 켜 둔 시간과 지나간 바이트로 매겨진다. 그래서 줄이는 방법도 둘로 모인다. 켜 둔 시간을 줄이는 쪽은 크기 맞추기, 끄기, 오토스케일링, 그리고 남는 시간을 싸게 사는 약정과 스팟이다. 지나간 바이트를 줄이는 쪽은 NAT를 건너뛰는 엔드포인트, 같은 AZ 안에서 끝나는 트래픽, 꺼내는 횟수에 맞는 저장 등급이다. 그 모든 것의 바닥에는 누구 돈인지 알려 주는 태그가 있다.

## 면접에서 나올 만한 질문

### 서버는 그대로인데 EC2 비용이 늘었습니다. 어디부터 보나요?

Cost Explorer에서 EC2를 사용 유형별로 나눈다. 인스턴스 요금이 그대로라면 대개 `EC2-Other`에 묶인 NAT 게이트웨이 처리 요금, AZ 사이 데이터 전송, EBS가 늘어난 것이다. 일 단위로 놓고 늘기 시작한 날의 변경 사항을 찾고, NAT라면 흐름 로그로 상위 목적지를 본다.

### NAT 게이트웨이 비용을 줄이는 방법은요?

NAT를 지나지 않아도 되는 트래픽을 빼는 것이다. S3와 DynamoDB는 요금이 없는 게이트웨이 엔드포인트로 돌리고, ECR이나 CloudWatch처럼 큰 트래픽을 보내는 AWS 서비스는 인터페이스 엔드포인트의 시간당 요금과 NAT 처리 요금을 비교해 고른다. 이미지를 매번 받는 노드라면 캐시를 늘린다. NAT를 하나로 합치는 건 AZ 장애 위험을 키우니 운영 환경에서는 피한다.

### AZ를 나눠 고가용성을 높이면 비용은 어떻게 되나요?

AZ를 건너는 트래픽마다 양방향으로 GB당 요금이 붙는다. 서버와 캐시, DB, 메시지 브로커 복제가 AZ를 건너면 데이터가 많을수록 커진다. 같은 AZ의 레플리카에서 읽게 하거나, 쿠버네티스에서 같은 존을 우선하는 라우팅을 쓰는 식으로 줄인다. 다만 한 AZ에 몰려 가용성을 잃지 않는 선까지만 붙인다.

### 크기 맞추기와 약정 할인 중 무엇을 먼저 하나요?

크기 맞추기가 먼저다. 너무 큰 서버에 1년이나 3년 약정을 걸면 줄일 수 있었던 돈을 약정으로 굳히게 된다. 2주 이상의 CPU 최댓값과 메모리 지표로 크기를 맞추고, 그다음 지난 몇 달 동안 가장 적게 쓴 바닥 사용량만큼만 Savings Plans를 건다. 그 위의 변동은 오토스케일링과 스팟으로 받는다.

### Savings Plans와 예약 인스턴스는 어떻게 다른가요?

Savings Plans는 시간당 사용 금액을 약정하고, 예약 인스턴스는 특정 인스턴스 사양을 약정한다. Compute Savings Plans는 패밀리와 리전을 바꿔도, Fargate와 Lambda에도 적용되어 유연하고, EC2 Instance Savings Plans와 예약 인스턴스는 고정하는 대신 할인 폭이 더 크다. RDS 같은 서비스는 여전히 예약 인스턴스로 할인을 받는다.

### 스팟 인스턴스는 어디에 쓰고 어떻게 운영하나요?

중단돼도 되는 일에 쓴다. 배치, CI 러너, 상태 없는 웹 서버 일부, 쿠버네티스 워커 노드가 맞고, DB 프라이머리 같은 상태 있는 단일 서버에는 쓰지 않는다. 2분 전 회수 알림을 받아 LB에서 빼고 drain하는 처리기를 두고, 인스턴스 타입과 AZ를 여러 개 지정해 한꺼번에 회수되지 않게 하며, 온디맨드를 바닥으로 섞는다.

### 서버리스와 상시 서버 중 어느 쪽이 싼지 어떻게 판단하나요?

부하로 월 요금을 계산해 비교한다. Lambda는 요청 수와 메모리 × 실행 시간으로 요금이 나오니 초당 몇 건 수준에서는 매우 싸지만, 초당 50건에 200ms, 1GB면 월 450달러가 넘어 같은 부하를 받는 서버 몇 대보다 비싸진다. 여기에 API Gateway 요금, 로그 비용, 서버 쪽 운영 인력과 로드 밸런서까지 넣어야 실제 결정이 된다.

### 태깅이 비용 관리에서 왜 중요한가요?

태그가 있어야 비용의 주인이 생기고, 주인이 있어야 줄인다. 팀·서비스·환경 태그로 비용을 나눠 보여 주면(쇼백) 각 팀이 자기 몫을 보고 판단할 수 있다. 태그 없는 비용이 많으면 아무도 책임지지 않으니, IaC의 기본 태그와 조직 정책으로 태그를 강제하고, 공유 인프라는 나누는 규칙을 따로 정한다.
