<EasyIntro>
  비행기에서 노트북으로 회의 메모를 고치는 사이, 사무실의 데스크톱에서도 같은 파일을 고쳐 저장했다. 나중에 온 쪽이 이기게 두면 먼저 저장한 쪽의 작업이 흔적 없이 사라지고, 기기 시계가 빠른 쪽이 늘 이기는 이상한 일이 생긴다.

  알고 나면 지우기도 쉽지 않다는 게 보인다. 블록은 여러 버전이 함께 쓰니 옛 버전을 지웠다고 그 블록을 바로 지우면 남은 버전이 깨지고, 그래서 블록마다 몇 군데서 쓰는지 세어 두었다가 아무도 안 쓸 때만 지운다.

이 시리즈에서 이 글의 자리: [㉝ 파일 동기화 설계 ①](/posts/sd-file-sync-block-upload)에서 파일을 블록으로 나눠 바뀐 블록만 올리고, 해시 순서를 확정해 새 버전을 만들었다. 이 글은 같은 장의 두 번째 글로, 여러 기기가 같은 파일을 고칠 때의 충돌, 바뀐 사실을 다른 기기에 바로 알리는 방법, 쌓이는 버전과 블록의 저장 공간을 다룬다. 다음 글부터는 새 장인 [㉟ 주변 장소 검색](/posts/sd-proximity-service)이다.

비행기에서 노트북으로 회의 메모를 고쳤다. "예산 확정" 옆에 "(10% 삭감)"을 붙였다. 그 사이 사무실의 동료, 아니면 내 데스크톱이 같은 파일에 "일정 공유" 줄을 추가해 저장했다. 착륙해서 와이파이가 잡히자 노트북이 동기화를 시작한다. 서버에는 이미 데스크톱의 버전이 있다. 노트북의 변경을 그대로 덮어쓰면 "일정 공유"가 사라지고, 무시하면 "10% 삭감"이 사라진다. 어느 쪽이든 누군가의 작업이 조용히 없어진다.

이 글은 이 순간부터 시작한다. 충돌을 어떻게 알아채고, 알아챈 뒤에 무엇을 보여 줄지, 그리고 데스크톱이 저장했다는 사실을 노트북과 휴대폰이 몇 초 안에 알게 하는 방법을 본다. 마지막으로 버전과 블록이 쌓일 때 저장 공간을 아끼는 법까지 간다. 기준 환경은 Node 22와 PostgreSQL 16이고 출력은 모두 실제로 돌린 결과다.

## 같은 파일을 두 곳에서 고쳤다

충돌은 두 기기가 같은 버전에서 출발해 각자 다른 변경을 만들었을 때 생긴다. 노트북도 데스크톱도 버전 1을 들고 있다가, 데스크톱이 버전 2를 먼저 확정했다. 노트북의 변경은 버전 1을 기준으로 만든 것이라 버전 2의 내용을 모른다.

가장 쉬운 처리는 나중에 도착한 쪽이 이기는 것이다. 단순하지만 위에서 본 것처럼 먼저 저장한 쪽의 작업이 흔적 없이 사라진다. 파일을 맡기는 서비스에서 "데이터를 잃지 않는다"는 약속을 깨는 방법이다. 기기의 수정 시각을 비교해 더 늦은 쪽을 남기는 것도 답이 아니다. 노트북의 시계가 5분 빠르면 늘 노트북이 이긴다. 기기 시계를 믿기 어려운 이유는 [시계 어긋남](/posts/clock-skew)에서 봤다.

그래서 시각 대신 버전 번호를 쓴다. 기기는 "나는 버전 1을 고쳤다"는 기준 버전을 함께 들고 확정을 요청한다. 서버는 그 기준 버전이 아직 최신일 때만 받아 준다.

## 기준 버전을 들고 확정한다

[㉝](/posts/sd-file-sync-block-upload)에서 만든 작은 동기화 서버의 확정 API에 이미 이 검사가 들어 있다.

```js
// sync-server.mjs 일부: 기준 버전이 최신이 아니면 409 Conflict
const cur = files.get(path);
const latest = cur?.ver ?? 0;
if (base !== latest) return json(res, 409, { error: "conflict", base, latest, by: cur.device });
files.set(path, { ver: latest + 1, blocks: list, device });
```

노트북과 데스크톱이 버전 1에서 출발해 각자 고치고, 데스크톱이 먼저 확정하게 했다.

```js
// conflict-client.mjs 일부
await save("laptop", P, "1. 예산 확정\n", 0);                        // 버전 1. 두 기기 모두 이걸 받았다
await save("desktop", P, "1. 예산 확정\n2. 일정 공유\n", 1);          // 데스크톱이 먼저 확정한다
const [status, out] = await save("laptop", P, "1. 예산 확정 (10% 삭감)\n", 1);
if (status === 409) {
  // 내 변경을 버리지 않는다. 충돌 사본으로 따로 올리고, 원래 이름은 서버의 최신 버전을 받는다
  await save("laptop", "/notes/plan (laptop 충돌 사본 2026-10-21).txt", "1. 예산 확정 (10% 삭감)\n", 0);
}
```

```text
laptop  commit /notes/plan.txt base=0 -> 200 {"ver":1,"cursor":1}
desktop commit /notes/plan.txt base=1 -> 200 {"ver":2,"cursor":2}
laptop  commit /notes/plan.txt base=1 -> 409 {"error":"conflict","base":1,"latest":2,"by":"desktop"}
laptop  commit /notes/plan (laptop 충돌 사본 2026-10-21).txt base=0 -> 200 {"ver":1,"cursor":3}
laptop  now has server ver 2 of /notes/plan.txt
```

노트북의 확정은 기준이 1인데 최신이 2라서 409로 거절됐다. 노트북은 자기 변경을 버리지 않고 "충돌 사본"이라는 새 이름의 파일로 올렸고, 원래 이름에는 서버의 버전 2를 받았다. 이제 사용자의 폴더에는 두 파일이 나란히 있다. 둘을 보고 합치는 일은 사람이 한다. 드롭박스가 이런 식으로 충돌 사본을 만드는 것으로 알려져 있다. 어느 쪽 작업도 사라지지 않았다.

## 같은 순간에 도착한 두 확정

휴대폰과 태블릿이 같은 버전 2를 기준으로 확정을 동시에 보내면 어떨까.

```text
phone   commit /notes/plan.txt base=2 -> 200 {"ver":3,"cursor":4}
tablet  commit /notes/plan.txt base=2 -> 409 {"error":"conflict","base":2,"latest":3,"by":"phone"}
results: [ 200, 409 ]
```

하나만 이겼다. 이 데모 서버는 Node 한 프로세스라서 확인과 쓰기 사이에 다른 요청이 끼어들지 못했다. API 서버를 여러 대 두면 사정이 다르다. 두 서버가 각각 "최신이 2인가?"를 확인하고 둘 다 "그렇다"고 본 뒤 각자 버전 3을 쓰면 하나가 사라진다. 그래서 확인과 쓰기를 DB의 한 문장으로 묶는다. [㉝](/posts/sd-file-sync-block-upload)의 메타데이터 DB에서 두 세션이 같은 기준 버전 2로 동시에 확정하게 했다. 1번 세션은 확정 뒤 1초 동안 트랜잭션을 열어 둔다.

```sql
-- 기준 버전이 아직 최신일 때만 버전을 올린다. 확인과 쓰기가 한 문장이다
UPDATE files SET latest_ver = latest_ver + 1
WHERE file_id = 1 AND latest_ver = 2
RETURNING latest_ver;
```

```text
== session 1
BEGIN
 latest_ver 
------------
          3
(1 row)

UPDATE 1
 pg_sleep 
----------
 
(1 row)

COMMIT
== session 2
Timing is on.
 latest_ver 
------------
(0 rows)

UPDATE 0
Time: 690.650 ms
```

1번 세션은 `UPDATE 1`, 버전 3이 됐다. 2번 세션은 690ms를 기다린 뒤 `UPDATE 0`이다. 1번이 그 행을 잠근 채 커밋을 미루는 동안 2번은 기다렸고, 1번이 커밋하자 PostgreSQL이 바뀐 행으로 `latest_ver = 2` 조건을 다시 확인했는데 이제 3이라 맞지 않았다. API 서버는 `UPDATE 0`을 보고 409를 돌려주면 된다. 이 방법을 낙관적 잠금이라고 하고, 왜 잠그지 않는다면서 기다렸는지와 MySQL과의 차이는 [낙관적 잠금](/posts/optimistic-locking)에 자세히 있다.

버전 번호 하나로 충분한 이유도 짚어 두자. 모든 확정이 한 곳(이 파일의 메타데이터 행)을 거치니, 그곳이 순서를 정해 준다. 서버 여러 대가 각자 쓰기를 받는 저장소라면 이런 한 줄짜리 순서가 없어서 [벡터 시계](/posts/sd-kv-store-versioning)처럼 누가 무엇을 봤는지 기록하는 장치가 필요하다. 파일 동기화는 오프라인 기기가 많아도 확정은 서버 한 곳에서 하니 더 단순한 쪽을 고를 수 있다.

## 충돌을 사람에게 어떻게 내미나

충돌을 알아챈 뒤 무엇을 할지는 파일 종류와 제품이 정한다.

- 충돌 사본을 만든다. 어떤 형식의 파일에도 통하고 아무것도 잃지 않는다. 대신 사용자가 두 파일을 보고 직접 합쳐야 하고, 충돌이 잦으면 폴더가 사본으로 어지러워진다.
- 자동으로 합친다. 텍스트라면 공통 조상(버전 1), 내 변경, 남의 변경 세 가지를 놓고 서로 다른 줄을 고쳤으면 합칠 수 있다. git이 하는 3-way 병합이다. 같은 줄을 둘 다 고치면 결국 사람이 골라야 하고, 그 모양은 [Git 병합 충돌](/posts/git-merge-conflict)에서 봤다. 엑셀이나 사진처럼 줄 단위가 아닌 파일은 이 방법이 통하지 않는다.
- 나중 쪽을 남기되 이전 버전을 보관한다. 버전 기록이 있으니 덮어쓴 쪽을 되살릴 수 있다. 사용자가 사라진 걸 알아채야 한다는 점이 약하다.
- 실시간 공동 편집으로 간다. 구글 문서처럼 글자 단위로 변경을 주고받으며 합치는 방식은 파일 동기화와 다른 문제다. 바탕 기술은 [CRDT](/posts/crdt) 같은 쪽이다.

폴더와 이름도 충돌한다. 실무에서는 이쪽이 더 헷갈린다.

- 한쪽은 고치고 다른 쪽은 지웠다. 지운 쪽의 확정을 받아들이면 고친 내용이 사라진다. 보통 고친 쪽을 살린다. 지우기도 "버전 N을 지운다"는 기준 버전을 들고 와야 하고, 그 사이 새 버전이 생겼으면 지우기를 거절한다.
- 한쪽은 이름을 바꾸고 다른 쪽은 내용을 고쳤다. 파일을 경로가 아니라 고유 번호(`file_id`)로 다루면 둘이 부딪히지 않는다. 이름은 그 번호의 속성일 뿐이다.
- 두 기기가 같은 경로에 서로 다른 새 파일을 만들었다. 둘 다 기준 버전 0으로 확정하니 늦은 쪽이 409를 받는다. 역시 충돌 사본으로 처리한다.
- 대소문자만 다른 이름. 리눅스는 `Report.txt`와 `report.txt`를 다른 파일로 보고, 윈도와 맥의 기본 파일 시스템은 같은 이름으로 본다. 서버가 한 계정 안에서 대소문자만 다른 이름을 허용하면 어떤 기기에서는 한 파일이 사라진 것처럼 보인다.

## 데스크톱이 저장한 걸 노트북이 바로 알려면

충돌을 줄이는 가장 좋은 방법은 다른 기기의 변경을 빨리 받는 것이다. 노트북이 데스크톱의 버전 2를 1분 뒤에 받으면 그 1분 동안 고친 것은 모두 충돌 후보다. 그래서 서버는 바뀐 사실을 기기들에 바로 알려야 한다.

방법은 세 가지다. 기기가 몇 초마다 "바뀐 거 있어?"라고 묻는 폴링은 단순하지만 대부분의 질문이 헛걸음이고, 간격만큼 늦다. 웹소켓은 연결을 열어 두고 양쪽이 언제든 보낸다. 롱 폴링은 기기가 물으면 서버가 바뀐 게 생길 때까지(또는 정해 둔 시간까지) 답을 미루는 방식이다. 세 방식의 차이는 [실시간 통신 방식](/posts/realtime-communication)에 정리되어 있다.

파일 동기화의 알림은 드물고 한 방향이다. 파일은 분 단위로 바뀌고, 알림은 서버에서 기기로만 가며, 내용 없이 "이 파일이 바뀌었다" 정도면 된다. 그래서 롱 폴링이 잘 맞는다. 평범한 HTTP 요청이라 회사 프록시나 방화벽을 잘 통과하고, 서버는 상태를 거의 들고 있지 않아도 된다. 드롭박스도 클라이언트 알림에 롱 폴링을 쓴다고 알려져 있다.

알림이 빠지지 않게 하는 장치가 하나 더 필요하다. 서버는 확정이 일어날 때마다 사용자의 변경 기록(저널)에 한 줄씩 추가하고, 줄마다 1씩 느는 위치 번호(커서)를 붙인다. 기기는 "나는 커서 4까지 봤다"며 기다리고, 서버는 그보다 뒤의 줄을 돌려준다.

```js
// sync-server.mjs 일부: 커서 뒤에 변경이 있으면 바로, 없으면 생길 때까지 붙잡는다
const answer = () => json(res, 200, { changes: journal.slice(cursor), cursor: journal.length });
if (journal.length > cursor) return answer();             // 놓친 변경이 있으면 바로 답한다
const t = setTimeout(() => { waiters = waiters.filter((f) => f !== wake); answer(); }, timeout);
const wake = () => { clearTimeout(t); answer(); };
waiters.push(wake);                                        // 확정이 일어나면 깨운다
```

휴대폰은 롱 폴링으로 기다리고, 데스크톱이 1초 뒤에 확정하고, 사흘 꺼져 있던 태블릿이 마지막에 돌아오는 장면을 돌렸다.

## 버전이 쌓이면 블록도 쌓인다

[㉝](/posts/sd-file-sync-block-upload)에서 버전 둘을 합쳐 48MiB인데 실제 저장은 28MiB였다. 버전이 많아지면 어떻게 될까. 24MiB 파일(4MiB 블록 6개)을 서른 번 고치되 매번 블록 하나씩만 바뀐다고 흉내 냈다.

```text
versions=30 logical=720MiB stored=140MiB (35 blocks)
keep last 10: deleted 20 versions, freed 20 blocks (80MiB), stored=60MiB
oldest kept version still uses blocks: b24,b1,b20,b3,b25,b5
```

버전 서른 개를 통째로 저장하면 720MiB인데 블록을 함께 쓰니 140MiB다. 첫 버전의 블록 6개에 버전마다 새 블록 하나씩 29개가 더해진 35개다. 최근 10개 버전만 남기고 지웠더니 블록 20개, 80MiB가 풀려 60MiB가 됐다.

마지막 줄이 함정이다. 남긴 버전 중 가장 오래된 것(버전 21)이 아직 `b1`, `b3`, `b5`를 쓰고 있다. 버전 1에서 만든 블록이다. "버전 1을 지웠으니 버전 1의 블록을 지운다"고 하면 버전 21이 깨진다. 블록은 여러 버전, 여러 파일이 함께 쓰니 블록마다 몇 군데서 쓰는지 세어 두고(참조 수), 0이 된 블록만 지운다.

참조 수를 세는 방식은 버전을 만들고 지울 때마다 숫자를 정확히 맞춰야 한다. 버그 하나로 숫자가 1 작아지면 쓰는 중인 블록이 지워진다. 그래서 숫자를 믿고 바로 지우지 않는 장치를 함께 둔다. 하나는 표시하고 쓸기(mark and sweep)로, 주기적으로 살아 있는 모든 버전에서 쓰는 블록을 표시한 뒤 표시되지 않은 블록만 지운다. 느리지만 숫자가 틀릴 일이 없다. 다른 하나는 유예 기간으로, 지울 블록을 바로 지우지 않고 며칠 휴지통에 두었다가 지운다. 확정 직전에 올라온 블록이 "아직 아무도 안 쓰는" 상태로 보이는 순간도 이 유예가 지켜 준다.

## 버전을 몇 개나 남길까

버전을 무한히 남기면 자주 저장하는 파일 하나가 공간을 다 먹는다. 1분마다 자동 저장되는 문서는 하루 수백 개 버전이 생긴다. 그래서 버전 수나 기간에 한도를 두고, 오래된 버전은 듬성듬성 남긴다. 최근 것은 촘촘하게, 오래된 것은 하루에 하나씩, 아주 오래된 것은 지운다. 사람이 되살리고 싶은 건 대개 "방금 전"이거나 "지난주 어느 날"이기 때문이다.

이 규칙을 짜 보자. 버전마다 저장한 지 몇 시간 지났는지를 최신 순(작은 수부터)으로 받는다. 24시간 안의 버전은 모두 남기고, 24시간부터 30일(720시간) 전까지는 하루(`Math.floor(age / 24)`)마다 가장 최신 것 하나만 남기고, 720시간 이상은 지운다. 남길 버전의 나이를 같은 순서로 돌려준다.

## 같은 블록은 한 번만, 다만 범위를 정해서

블록을 해시로 이름 짓는 구조는 버전 사이뿐 아니라 파일 사이의 중복도 없앤다. 같은 사진을 두 폴더에 넣으면 블록은 한 번만 저장된다. [㉝](/posts/sd-file-sync-block-upload)의 실험에서 휴대폰이 같은 내용을 다른 경로로 올렸을 때 0바이트를 보낸 것이 이것이다.

그럼 모든 사용자 사이에서 중복을 없애면 더 아낄 수 있지 않을까. 공간은 더 아끼지만 두 가지 문제가 생긴다.

첫째, 정보가 샌다. 내가 어떤 파일을 올렸는데 0바이트만 보내고 끝났다면, 다른 누군가가 이미 같은 파일을 갖고 있다는 뜻이다. 유출된 문서의 해시를 들고 와서 "이 회사 누군가가 이 문서를 갖고 있나"를 확인할 수 있다. 둘째, 해시가 열쇠가 된다. 서버가 "이 해시 목록으로 파일을 만들어 달라"는 요청만 보고 블록을 내 파일에 붙여 주면, 남의 파일 해시를 아는 사람은 내용 없이 그 파일을 자기 계정에 복사할 수 있다. 그래서 중복 제거는 보통 사용자나 팀 범위 안에서만 하고, 범위 밖의 블록은 이미 있어도 다시 올리게 한다.

저장 공간을 줄이는 마지막 방법은 저장소 등급이다. 몇 달 동안 아무도 열지 않은 파일의 블록은 더 싼 보관용 등급으로 옮긴다. 보관용 등급은 GB당 값이 싼 대신 꺼낼 때 요금이 붙고, 등급에 따라 꺼내는 데 몇 분에서 몇 시간이 걸리며 최소 보관 기간이 있다. 그래서 "오래 안 열었다"를 넉넉하게 잡고, 사용자가 열면 일반 등급으로 되돌린다. 등급 고르는 법은 [클라우드 비용 줄이기](/posts/cloud-cost-optimization)에 있다.

## 다음 장: 파일에서 위치로

두 편에 걸쳐 파일 동기화를 설계했다. 이 글의 결정을 정리하면 이렇다. 확정은 기준 버전을 들고 와서 최신일 때만 받고, DB의 조건부 UPDATE 한 문장으로 확인과 쓰기를 묶는다. 충돌이 나면 아무것도 버리지 않고 충돌 사본을 남긴다. 변경은 커서가 붙은 기록으로 남기고 롱 폴링으로 알려서, 꺼져 있던 기기도 커서로 따라오게 한다. 블록은 참조 수와 유예 기간을 거쳐서만 지우고, 중복 제거는 범위를 정해서 한다.

다음 장 [㉟ 주변 장소 검색](/posts/sd-proximity-service)에서는 문제가 바뀐다. "내 주변 1km 안의 식당"을 빠르게 찾으려면 위도와 경도를 어떻게 색인해야 할까.

## 면접에서 나올 만한 질문

### 두 기기가 같은 파일을 동시에 고치면 어떻게 하나요?

기기는 확정할 때 자기가 고친 기준 버전을 함께 보내고, 서버는 그 버전이 최신일 때만 받는다. 늦게 온 쪽은 409를 받고, 자기 변경을 충돌 사본으로 따로 올린 뒤 원래 이름에는 서버의 최신 버전을 받는다. 아무것도 잃지 않고 합치는 일은 사람에게 맡긴다. 텍스트라면 공통 조상을 기준으로 자동 병합을 시도할 수 있다.

### 수정 시각이 늦은 쪽을 남기면 안 되나요?

기기 시계를 믿을 수 없다. 시계가 빠른 기기가 늘 이기고, 먼저 저장한 쪽의 작업은 흔적 없이 사라진다. 버전 번호는 서버가 한 곳에서 순서를 정해 주니 시계와 상관없이 "이 변경이 무엇을 보고 만든 것인지"를 알 수 있다.

### API 서버가 여러 대인데 두 확정이 동시에 오면요?

확인과 쓰기를 DB의 조건부 UPDATE 한 문장으로 묶는다. `WHERE latest_ver = 기준 버전` 조건으로 올리면 한쪽만 1행이 바뀌고, 다른 쪽은 행 잠금을 기다린 뒤 조건을 다시 확인해 0행이 된다. 0행이면 409를 돌려준다. 애플리케이션에서 SELECT로 확인하고 따로 UPDATE하면 두 서버가 모두 통과해 하나가 사라진다.

### 다른 기기에 변경을 어떻게 알리나요?

롱 폴링을 쓴다. 기기가 마지막으로 본 커서를 대고 기다리면 서버는 그 뒤 변경이 생길 때까지 답을 미룬다. 파일 변경은 드물고 서버에서 기기로만 가니 웹소켓까지 필요 없고, 평범한 HTTP라 프록시를 잘 통과한다. 알림에는 내용 없이 무엇이 바뀌었는지만 담고, 기기가 메타데이터와 블록을 따로 받는다.

### 기기가 일주일 꺼져 있다 켜지면 놓친 변경은요?

변경을 커서가 붙은 기록으로 남기니 마지막으로 본 커서로 물으면 그 뒤를 한 번에 받는다. 기록 보관 기간보다 오래 꺼져 있었다면 서버가 너무 오래됐다고 답하고, 기기는 파일 목록 전체를 받아 비교하는 전체 재동기화를 한다.

### 알림 서버가 죽으면요?

붙어 있던 기기들이 다른 알림 서버에 다시 붙고 커서로 묻는다. 그 사이 변경은 기록에 있으니 잃지 않는다. 수만 대가 같은 순간에 다시 붙으면 다음 서버도 쓰러지니 재연결 시점을 무작위로 흩뜨린다.

### 오래된 버전을 지울 때 블록은 어떻게 지우나요?

블록은 여러 버전과 파일이 함께 쓰니, 버전을 지웠다고 그 버전의 블록을 바로 지우면 남은 버전이 깨진다. 블록마다 참조 수를 세어 0이 된 것만 지우고, 숫자가 틀릴 때를 대비해 주기적인 표시하고 쓸기와 며칠의 유예 기간을 함께 둔다.

### 모든 사용자 사이에서 중복 블록을 없애면 더 좋지 않나요?

공간은 더 아끼지만, 0바이트로 끝난 업로드가 "누군가 이미 이 파일을 갖고 있다"는 정보를 흘리고, 해시만 알면 남의 파일을 내 계정에 붙이는 공격이 생긴다. 그래서 중복 제거는 사용자나 팀 범위 안에서 하고, 그 밖의 블록은 이미 있어도 다시 올리게 한다.
