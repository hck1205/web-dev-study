이 시리즈에서 이 글의 자리: 앞 글 [⑭ 동시에 고친 값과 벡터 시계](/posts/sd-kv-store-versioning)에서 복제본끼리 값이 엇갈릴 때 최신을 가리는 법을 만들었다. 이 글은 노드가 죽거나 끊길 때를 다룬다. 다음 글은 [⑯ 쓰기 경로와 읽기 경로](/posts/sd-kv-store-write-read-path)이고, 이 장의 첫 글은 [⑬ 링으로 나누고 쿼럼으로 복제하기](/posts/sd-kv-store-partition-replication)다.

새벽 3시, 노드 C가 요청에 답하지 않는다. 코디네이터는 C에 쓰기를 보내고 500ms를 기다렸지만 아무 답도 없다. C의 프로세스가 죽었을 수도 있고, GC 때문에 2초째 멈춰 있을 수도 있고, C까지 가는 스위치 하나가 패킷을 버리고 있을 수도 있다. 코디네이터가 아는 건 "답이 안 온다"뿐이다.

앞의 두 글은 노드가 모두 살아 있다고 가정했다. 실제 클러스터는 노드가 수십, 수백 대고, 그중 한두 대는 거의 언제나 아프다. 이 글은 세 가지를 차례로 만든다. 누가 죽었는지 클러스터 전체가 알아채는 방법, 담당 노드가 잠깐 죽었을 때 쓰기를 대신 받아 두는 방법, 오래 죽어 있던 노드가 돌아왔을 때 놓친 것을 채우는 방법이다.

## 한 노드의 말만 믿으면 안 된다

코디네이터 A가 C에서 답을 못 받았다고 C를 죽은 노드로 선언하면 어떻게 될까. A와 C 사이 회선만 끊겼고 C는 다른 노드들과 멀쩡히 일하고 있을 수 있다. A의 판단을 모두가 따르면 멀쩡한 C가 클러스터에서 빠지고, C가 맡은 키가 엉뚱한 노드로 옮겨진다. 죽음과 끊김을 밖에서 구별할 수 없다는 문제는 [네트워크 분할 글](/posts/network-partitions)에서 직접 재현했다.

그래서 "C가 죽었다"는 결론은 여러 노드의 관찰을 모아서 내린다. 한 노드가 "나는 C의 소식을 못 들었다"고 해도, 다른 노드가 "방금 C의 소식을 들었다"고 하면 C는 살아 있다. 이 글의 첫 번째 장치는 그 소식을 모두에게 싸게 퍼뜨리는 방법이다.

## 모두가 모두를 확인하면 메시지가 폭발한다

가장 단순한 방법은 노드마다 1초에 한 번씩 다른 모든 노드에게 "나 살아 있다"는 하트비트(heartbeat)를 보내는 것이다. 노드가 N대면 1초에 N × (N - 1)개의 메시지가 오간다. 노드 10대면 90개로 아무 문제 없다. 100대면 9,900개, 1,000대면 999,000개다. 노드를 열 배 늘리면 메시지는 백 배로 는다.

## 소문처럼 퍼뜨리는 가십 프로토콜

해결책은 소문이 퍼지는 방식을 흉내 내는 것이다. 사람 하나가 매일 아무나 한 명을 골라 아는 소식을 전하면, 하루에 소식을 아는 사람이 대략 두 배가 된다. 1,000명에게 퍼지는 데 10일 정도면 된다. 2의 10제곱이 1,024이기 때문이다. 이걸 컴퓨터로 옮긴 것이 가십 프로토콜(gossip protocol)이다.

규칙은 이렇다.

- 노드마다 멤버 목록을 든다. 목록에는 노드마다 하트비트 카운터, 그리고 그 카운터가 마지막으로 오른 시각이 적혀 있다.
- 노드는 주기마다(예: 1초) 자기 하트비트 카운터를 1 올린다.
- 같은 주기마다 무작위로 다른 노드 하나를 골라 멤버 목록을 주고받는다.
- 받은 목록에서 어떤 노드의 카운터가 내 것보다 크면, 내 목록을 그 값으로 바꾸고 "마지막으로 오른 시각"을 지금으로 적는다.
- 어떤 노드의 카운터가 정해 둔 시간 동안 한 번도 안 올랐으면 그 노드를 죽은 것으로 본다.

마지막 줄이 이 방식의 요점이다. C의 카운터는 C만 올릴 수 있다. 그 숫자가 다른 노드들의 입을 거쳐 내게 오르는 걸 봤다면, 누군가는 최근에 C에게서 직접 들었다는 뜻이다. 내가 C와 직접 이야기하지 못해도 된다. 아래 그림은 노드 A가 B와 목록을 주고받는 한 번의 교환이다.

소식이 정말 log N 라운드 정도에 퍼지는지, 노드 수를 바꿔 가며 돌려 봤다. 라운드마다 모든 노드가 무작위로 한 명을 골라 서로 아는 것을 주고받는다.

```js
// gossip.js (발췌): 새 소식 하나가 모두에게 닿기까지 몇 라운드?
const knows = new Array(n).fill(false); knows[0] = true;
let rounds = 0;
while (knows.some((k) => !k)) {
  rounds++;
  const snap = knows.slice();          // 이번 라운드 시작 시점에 알던 것만 전한다
  for (let i = 0; i < n; i++) {
    const p = pick(n, i);              // 나 말고 무작위 한 명
    if (snap[i] || snap[p]) { knows[i] = true; knows[p] = true; }
  }
}
```

```bash
node gossip.js   # 시드 고정 난수, 노드 수마다 5번 평균
```

```text
노드 수 | 모두 알기까지 라운드 (5회 평균) | log2(N)
     8 |   3.4 | 3
    64 |   6.2 | 6
   512 |   8.2 | 9
  4096 |  10.0 | 12
```

노드가 8대에서 4,096대로 512배 늘었는데 라운드는 3.4에서 10으로 세 배 남짓 늘었다. 1초에 한 라운드라면 4,096대 클러스터 전체에 소식이 퍼지는 데 10초 정도다. 주고받기를 양쪽으로 하면 퍼지는 속도가 log2(N)보다도 조금 빨라서, 512대와 4,096대는 계산값보다 적게 나왔다. 메시지 수는 라운드마다 노드 수만큼이라 1,000대면 1초에 1,000번 정도의 교환으로 끝난다.

실제 구현은 목록 전체를 매번 보내지 않는다. Cassandra는 매초 무작위 노드 하나와 세 번의 메시지를 주고받는데, 먼저 노드별 버전 번호만 담은 요약을 보내고, 상대가 자기에게 없는 최신 항목만 골라 요청하거나 보낸다.

가십으로 퍼지는 건 하트비트만이 아니다. 새 노드가 링의 어느 자리를 맡았는지, 어떤 노드가 클러스터를 떠나는지 같은 링 정보도 같은 길로 퍼진다. [⑬ 첫 글](/posts/sd-kv-store-partition-replication)에서 "모든 노드가 같은 링을 들고 있다"고 한 것이 이렇게 유지된다. 그래서 이 저장소에는 링 정보를 들고 있는 중앙 서버가 없다. 처음 켜진 노드가 누구와 먼저 이야기할지 알도록 시드(seed) 노드 몇 대의 주소만 설정에 적어 둔다.

## 카운터가 멈춘 노드를 표시한다

죽음 판정을 직접 돌려 봤다. 노드 6대가 1초마다 가십을 하고, n3이 t=5에 멈춘다. 4초 넘게 카운터가 안 오르면 죽은 것으로 본다.

```text
n3이 t=5에 멈춤, T_fail=4s
  n0: n3의 마지막 하트비트 4 (t=5에 받음) → t=10에 죽음으로 표시
  n1: n3의 마지막 하트비트 4 (t=5에 받음) → t=10에 죽음으로 표시
  n2: n3의 마지막 하트비트 4 (t=5에 받음) → t=10에 죽음으로 표시
  n4: n3의 마지막 하트비트 4 (t=4에 받음) → t=9에 죽음으로 표시
  n5: n3의 마지막 하트비트 4 (t=4에 받음) → t=9에 죽음으로 표시
```

두 가지가 보인다. 첫째, n3의 마지막 카운터 4는 n3이 멈추기 직전에 퍼진 값이고, 노드마다 그 소식을 받은 시각이 t=4와 t=5로 다르다. 둘째, 그래서 노드마다 죽음을 표시하는 시각도 t=9와 t=10으로 다르다. 클러스터 전체가 한순간에 같은 결론을 내리지 않는다. 각자 자기 목록으로 판단하고, 그 판단이 조금씩 어긋난다. 이 저장소는 그 어긋남을 견디게 설계한다. 잠깐 동안 어떤 노드는 C에 요청을 보내고 어떤 노드는 안 보내도, 쿼럼과 다음 절의 대신 받아 두기가 그 틈을 메운다.

기다리는 시간을 정하는 게 어렵다. 짧게 잡으면 GC로 3초 멈춘 노드를 죽었다고 보고 쓸데없이 다른 노드로 일을 옮긴다. 길게 잡으면 정말 죽은 노드에 요청을 계속 보내며 시간 초과를 기다린다. Cassandra는 고정 시간 대신 phi accrual 장애 감지기를 쓴다. 노드마다 하트비트 간격의 분포를 기억해 두고, 지금 기다린 시간이 그 분포에서 얼마나 드문지를 점수(phi)로 계산한다. 평소 간격이 들쭉날쭉한 노드는 조금 더 기다려 주는 셈이다. `cassandra.yaml`의 `phi_convict_threshold` 기본값이 8이고, 네트워크가 불안정한 클라우드 환경에서는 10~12로 올리라는 권고가 흔하다.

직접 짜 보자. 내 멤버 목록과 방금 받은 목록을 합친 뒤, 죽은 것으로 볼 노드를 고른다.

## 담당이 죽었을 때 쓰기를 대신 받아 두기

이제 죽은 노드를 안다. 다음 질문은 그 노드가 맡은 키에 쓰기가 오면 어떻게 하느냐다. 링 순서가 A, B, C, D, E이고 `cart:alice`의 담당이 A, B, C라고 하자. N=3, W=2, R=2다.

C 하나만 죽었으면 문제없다. A와 B가 확인하면 W=2를 채운다. B와 C가 함께 죽으면 담당 중 살아 있는 건 A뿐이다. 엄격한 쿼럼은 여기서 실패를 돌려준다. 장바구니 담기 버튼이 오류를 낸다. 가용성을 고른 저장소는 다른 길을 택한다. 링에서 담당 다음에 오는 건강한 노드 D에게 B의 몫을 맡긴다. D는 그 값을 "B에게 돌려줄 것"이라는 메모, 즉 힌트(hint)와 함께 따로 보관한다. 이렇게 담당이 아닌 건강한 노드까지 세어 W를 채우는 것을 느슨한 쿼럼(sloppy quorum)이라 하고, 돌아온 노드에게 힌트를 넘겨주는 것을 힌트 핸드오프(hinted handoff)라고 한다.

시뮬레이션으로 확인했다. 읽기는 담당 노드에서만 하도록 단순하게 만들었다.

```js
// sloppy.js (발췌)
function write(key, value, reachable, sloppy) {
  const acks = [];
  for (const n of home) if (reachable.has(n)) { store[n].data[key] = value; acks.push(n); }
  if (acks.length < W && sloppy) {
    const missing = home.filter((n) => !reachable.has(n));
    for (const n of order.filter((x) => !home.includes(x) && reachable.has(x))) {
      if (acks.length >= W || missing.length === 0) break;
      const owner = missing.shift();
      store[n].hints.push({ owner, key, value });   // owner에게 돌려줄 힌트로 보관
      acks.push(`${n}(hint→${owner})`);
    }
  }
  return acks.length >= W;
}
```

```text
== 1. C 하나만 죽었다
write cart:alice=v1 [엄격한 쿼럼] 닿는 노드 ABDE → 성공 acks: A, B

== 2. B와 C가 죽었다
write cart:alice=v2 [엄격한 쿼럼] 닿는 노드 ADE → 실패 acks: A
write cart:alice=v2 [느슨한 쿼럼] 닿는 노드 ADE → 성공 acks: A, D(hint→B)
read cart:alice 닿는 노드 ADE → 실패 (1개만 응답)

== 3. B, C가 돌아왔다. 힌트를 돌려주기 전에 B, C에서 읽으면
read cart:alice 닿는 노드 BC → B=v1, C=없음
handoff D → B: cart:alice=v2
read cart:alice 닿는 노드 BC → B=v2, C=없음
```

볼 곳이 네 군데다. 2번의 엄격한 쿼럼은 실패했지만 A에는 v2가 이미 들어가 있다. [⑬ 첫 글](/posts/sd-kv-store-partition-replication)에서 말한 "실패한 쓰기도 흔적을 남긴다"가 실제로 일어났다. 느슨한 쿼럼은 D의 힌트까지 세어 성공했다. 3번에서 힌트를 넘기기 전의 B는 옛 값 v1을 들고 있다가, 핸드오프 뒤에 v2가 된다. 그리고 C는 끝까지 "없음"이다. C는 1번 쓰기 때부터 죽어 있었고, 이 시뮬레이션은 엄격한 쿼럼에서 힌트를 남기지 않았기 때문이다. 이 구멍은 다음 절의 복구 작업이 메운다.

제품마다 이 두 장치를 쓰는 방식이 다르다. Dynamo 논문은 느슨한 쿼럼과 힌트 핸드오프를 함께 쓴다. Cassandra는 죽은 담당 노드 몫의 힌트를 코디네이터가 남기기는 하지만, 그 힌트를 W를 채우는 확인으로 세지 않는다. 그래서 `QUORUM` 쓰기는 담당 셋 중 둘이 죽으면 실패한다. 예외는 일관성 수준 `ANY`인데, 이때는 힌트 하나만 남아도 성공으로 친다. Cassandra의 힌트 보관 기간 `max_hint_window`(기본 3시간)와 그보다 오래 죽어 있을 때의 이야기는 [최종 일관성 글](/posts/eventual-consistency)에 정리했다.

## 느슨한 쿼럼이 깨뜨리는 약속

느슨한 쿼럼에는 대가가 있다. 첫 글에서 "W + R > N이면 쓴 집합과 읽는 집합이 겹친다"고 했다. 그 계산은 W대와 R대가 모두 같은 담당 N대 안에서 나온다는 전제 위에 있다. D가 대신 받은 쓰기는 그 N대 밖에 있다. 네트워크가 둘로 갈려 클라이언트 1은 C, D, E만 보이고 클라이언트 2는 A, B만 보이는 상황을 이어서 돌려 봤다.

```text
== 4. 네트워크가 둘로 갈렸다: 클라이언트1은 C·D·E만, 클라이언트2는 A·B만 보인다
write cart:alice=v3 [느슨한 쿼럼] 닿는 노드 CDE → 성공 acks: C, D(hint→A)
read cart:alice 닿는 노드 AB → A=v2, B=v2
```

W=2, R=2, N=3이니 숫자로는 2 + 2 > 3이다. 그런데 클라이언트 1이 v3을 쓰고 성공을 받은 뒤, 클라이언트 2는 A와 B 두 대에서 읽어 v2를 받았다. 쓴 쪽은 C와 D, 읽은 쪽은 A와 B로 한 대도 겹치지 않는다. 느슨한 쿼럼을 켜는 순간 W + R > N은 "막 쓴 값을 본다"는 약속이 아니게 된다. 쓰기가 끊긴 쪽에서도 성공하는 가용성과 맞바꾼 것이다.

## 오래 죽어 있던 노드 따라잡기

힌트는 짧은 장애용이다. 디스크가 고장 나 노드를 새로 갈아 끼웠거나, 힌트 보관 기간보다 오래 꺼져 있었다면 놓친 쓰기가 너무 많거나 아예 힌트가 없다. 앞 시뮬레이션의 C처럼 처음부터 힌트를 못 받은 경우도 있다. 이럴 때는 복제본끼리 데이터 전체를 비교해 차이를 메운다. 이걸 안티 엔트로피(anti-entropy)라고 부른다.

키 1억 개를 하나씩 주고받으며 비교하면 네트워크와 디스크를 너무 많이 쓴다. 그래서 키 범위를 구간으로 나누고, 구간마다 해시를 만들어 위로 쌓은 머클 트리(Merkle tree)를 주고받는다. 두 복제본의 맨 위 해시가 같으면 전체가 같다. 다르면 자식 해시를 비교해 다른 쪽으로만 내려간다. 구간 100만 개 중 하나만 달라도 20번 남짓 내려가면 그 구간을 찾는다. 머클 트리를 쌓고 내려가는 과정은 [머클 트리 글](/posts/merkle-tree)에서 실제 해시값으로 따라갔으니, 여기서는 흐름만 본다.

Cassandra에서는 이걸 `nodetool repair`로 돌린다. 저절로 돌지 않으니 운영자가 일정을 잡거나 Cassandra Reaper 같은 도구로 자동화한다. 여기서 반드시 지켜야 할 기한이 있다. 지운 데이터는 툼스톤이라는 "지웠음" 표시로 남는데, 이 표시는 `gc_grace_seconds`(기본 10일)가 지나면 정리된다. 어떤 복제본이 그 기간 안에 삭제를 받지 못했고 repair도 돌지 않았다면, 툼스톤이 사라진 뒤 그 복제본의 옛 값이 오히려 다른 복제본으로 퍼져 지운 데이터가 되살아난다. 그래서 repair는 이 기간보다 짧은 주기로 모든 범위를 한 번씩 돌게 잡는다.

읽을 때 발견한 차이를 바로 고치는 읽기 복구(read repair)도 있다. R대에서 읽은 값이 서로 다르면 더 새 값을 낡은 복제본에 써 준다. 자주 읽는 키는 이걸로 빨리 맞춰지고, 아무도 안 읽는 키는 안티 엔트로피가 맡는다.

## 데이터 센터 하나가 통째로 멈추면

노드 하나가 아니라 데이터 센터 전체가 정전되거나 회선이 끊길 수도 있다. 이 저장소는 같은 방법을 한 단계 위로 적용한다. 복제본을 여러 데이터 센터에 나눠 두고, 가십은 데이터 센터를 넘어 퍼진다. Cassandra라면 키스페이스를 `{'dc1': 3, 'dc2': 3}`처럼 데이터 센터마다 세 벌로 만들고, 평소에는 `LOCAL_QUORUM`으로 가까운 데이터 센터 안의 과반만 기다린다. 한 곳이 멈추면 앱이 다른 데이터 센터의 노드로 붙는다. 사용자를 어느 데이터 센터로 보낼지, 데이터 센터 사이 복제가 왜 보통 비동기인지는 [⑥ 데이터 센터 여러 곳](/posts/sd-multi-datacenter)에서 다뤘다.

## 노드 하나가 이상할 때 보는 순서

운영에서 "C가 이상하다"는 신호는 대개 지연 지표로 먼저 온다. p99 지연이 갑자기 오르거나, 특정 키 범위의 쓰기만 시간 초과가 난다. Cassandra 클러스터라면 이 순서로 본다.

```bash
# 1. 클러스터가 보는 각 노드의 상태. 첫 두 글자 UN = Up/Normal, DN = Down/Normal
nodetool status

# 2. 모든 노드가 같은 스키마 버전을 보는지 (가십이 제대로 퍼지는지)
nodetool describecluster

# 3. 쌓여 있는 힌트 (Cassandra 4.0 이상): 돌려줄 힌트가 많으면 어딘가 오래 죽어 있었다
nodetool listpendinghints
```

마지막 repair가 언제였는지는 Cassandra Reaper 같은 도구의 기록이나 `system_distributed.repair_history` 테이블에서 본다. gc_grace_seconds 안에 모든 범위가 한 번씩 돌았는지가 기준이다.

`nodetool status`에서 어떤 노드는 DN인데 그 노드 자신에게서 보면 다른 노드가 DN이라면 네트워크가 일부만 끊긴 것이다. 그 노드 하나를 의심하기 전에 노드 사이 연결부터 본다. 힌트가 계속 쌓이는데 대상 노드가 UN이라면 힌트를 넘기는 속도가 쌓이는 속도를 못 따라가는 것이니, 대상 노드의 디스크나 힌트 전송 속도 제한(`hinted_handoff_throttle`, 4.0까지는 `hinted_handoff_throttle_in_kb`) 설정을 본다. 그리고 repair 기록이 10일을 넘겼다면 삭제가 되살아나기 전에 repair부터 돌린다.

흔한 실수 하나는 노드가 오래 죽었다가 돌아왔을 때 바로 트래픽을 받게 두는 것이다. 그 노드는 놓친 쓰기가 많아서, R=1 읽기가 그 노드로 가면 한참 전 값을 돌려준다. 힌트 보관 기간보다 오래 꺼져 있었다면 repair를 먼저 돌리고 나서 정상 트래픽에 넣는다.

## 다음에 읽을 글

이제 저장소는 노드가 죽은 걸 가십으로 알아채고, 담당이 잠깐 죽으면 힌트로 대신 받아 두고, 오래 죽었던 노드는 머클 트리로 비교해 채운다. 남은 건 노드 한 대 안쪽이다. 다음 글 [⑯ 쓰기 경로와 읽기 경로](/posts/sd-kv-store-write-read-path)에서는 쓰기 하나가 커밋 로그와 메모리를 거쳐 디스크 파일이 되기까지, 그리고 읽기가 여러 파일 중 필요한 것만 열게 하는 블룸 필터까지 직접 만들어 본다.

노드가 끊겼을 때의 판단은 [네트워크 분할](/posts/network-partitions), 놓친 쓰기를 메우는 세 장치의 비교는 [최종 일관성](/posts/eventual-consistency), 리더를 뽑는 쪽의 설계는 [리더 선출](/posts/leader-election)로 이어진다.

## 면접에서 나올 만한 질문

### 노드가 죽었다는 건 어떻게 알아내나요?

가십 프로토콜로 알아낸다. 노드마다 하트비트 카운터를 올리고, 주기적으로 무작위 노드와 멤버 목록을 주고받아 더 큰 카운터로 갱신한다. 어떤 노드의 카운터가 정해 둔 시간 동안 오르지 않으면 죽은 것으로 본다. 한 노드가 직접 연락하지 못해도 다른 노드를 거쳐 카운터가 오르면 살아 있다고 보니, 한 노드의 판단에 휘둘리지 않는다.

### 모든 노드가 서로에게 하트비트를 보내면 안 되나요?

노드가 N대면 1초에 N × (N - 1)개의 메시지가 생겨서 1,000대면 백만 개 가까이 된다. 가십은 라운드마다 노드 수만큼만 교환하고, 소식은 log N 라운드 정도에 퍼진다. 실험에서 4,096대에 퍼지는 데 평균 10라운드였다. 목록 전체 대신 버전 요약부터 보내 대역폭도 줄인다.

### 죽었다고 판단하는 시간은 어떻게 정하나요?

짧으면 GC로 잠깐 멈춘 노드를 잘못 빼고, 길면 죽은 노드에 요청을 보내며 시간 초과를 기다린다. Cassandra는 고정 시간 대신 하트비트 간격 분포를 보고 지금의 침묵이 얼마나 드문지 점수로 계산하는 phi accrual 감지기를 쓴다. 기본 기준값은 8이고, 네트워크가 불안정한 환경에서는 올린다.

### 담당 노드가 죽었을 때 쓰기는 어떻게 하나요?

느슨한 쿼럼과 힌트 핸드오프를 쓴다. 링에서 담당 다음의 건강한 노드가 쓰기를 대신 받아 "원래 주인에게 줄 것"이라는 힌트로 보관하고, 그 확인까지 세어 W를 채운다. 주인이 돌아오면 가십으로 그걸 알고 힌트를 넘긴 뒤 지운다. 엄격한 쿼럼이었다면 실패했을 쓰기가 성공한다.

### 느슨한 쿼럼을 켜도 W + R > N이면 최신 값을 읽나요?

아니다. 대신 받은 노드는 원래 담당 N대 밖에 있으니, 쓴 집합과 읽은 집합이 겹친다는 계산이 깨진다. 분할된 한쪽은 C와 D에 쓰고 다른 쪽은 A와 B에서 읽어, 2 + 2 > 3인데도 막 쓴 값을 못 봤다. 끊긴 쪽에서도 쓰기를 받는 가용성과 맞바꾼 것이다. Cassandra는 그래서 힌트를 일관성 수준 확인으로 세지 않는다(ANY 제외).

### 노드가 며칠 동안 죽어 있다가 돌아오면요?

힌트만으로는 부족하다. 힌트 보관 기간이 지났거나 처음부터 힌트를 못 받은 쓰기가 있다. 그래서 머클 트리로 복제본끼리 키 범위의 해시를 비교해 다른 구간만 주고받는 안티 엔트로피를 돌린다. 이 노드가 따라잡기 전에는 R=1 읽기가 옛 값을 줄 수 있어 repair를 먼저 하고 트래픽을 넣는다.

### repair를 오래 안 돌리면 어떤 사고가 나나요?

지운 데이터가 되살아날 수 있다. 삭제는 툼스톤으로 남았다가 gc_grace_seconds(Cassandra 기본 10일) 뒤에 정리되는데, 그 기간 안에 삭제를 못 받은 복제본이 있으면 툼스톤이 사라진 뒤 그 복제본의 옛 값이 다른 복제본으로 퍼진다. 그래서 repair 주기는 이 기간보다 짧게 잡는다.

### 데이터 센터 하나가 통째로 멈추면 어떻게 버티나요?

복제본을 데이터 센터마다 따로 두고, 평소에는 가까운 데이터 센터 안에서 과반만 기다린다(LOCAL_QUORUM). 한 곳이 멈추면 앱이 다른 데이터 센터로 붙고, 돌아온 쪽은 힌트와 repair로 따라잡는다. 데이터 센터 사이는 지연이 커서 보통 비동기로 복제하니, 멈추는 순간 건너가지 못한 쓰기는 잠시 한쪽에만 있다.
