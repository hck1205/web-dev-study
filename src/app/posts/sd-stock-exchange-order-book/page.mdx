70,000원에 5주를 사겠다고 주문을 냈다. 화면에는 누군가 70,000원에 팔겠다는 호가가 분명히 떠 있었는데 내 주문은 체결되지 않았다. 몇 초 뒤 같은 가격으로 다른 사람의 주문이 체결됐다는 기록이 올라온다. 같은 가격인데 왜 저 사람이 먼저일까.

답은 거래소가 주문을 짝짓는 규칙에 있다. 면접 문제 "증권 거래소를 설계하라"의 한가운데가 이 규칙을 구현한 매칭 엔진이다. 이 글에서는 용어부터 하나씩 풀고, Node로 호가창과 매칭 엔진을 만들어 실제 체결 기록을 뽑아 본다.

## 사는 사람, 파는 사람, 그리고 호가창

거래소의 일은 사려는 사람과 팔려는 사람을 짝짓는 것이다. 개인은 거래소에 직접 주문하지 않고 증권사(브로커)의 앱을 거친다. 증권사가 주문을 모아 거래소로 보낸다.

주문에는 두 종류가 흔하다.

- 지정가 주문: "70,000원 이하라면 5주 사겠다"처럼 가격을 정한다. 맞는 상대가 없으면 기다린다. 일부만 체결되고 나머지가 기다릴 수도 있다.
- 시장가 주문: 가격을 정하지 않고 지금 있는 가장 좋은 상대와 바로 체결한다.

이 글은 지정가 주문만 다룬다. 거래소 설계 면접에서도 흔히 범위를 이렇게 좁힌다.

아직 체결되지 않고 기다리는 지정가 주문들을 가격별로 모아 놓은 표가 호가창(order book)이다. 사려는 쪽 가격을 매수 호가(bid), 팔려는 쪽 가격을 매도 호가(ask)라고 한다. 매수 호가 중 가장 높은 값과 매도 호가 중 가장 낮은 값을 최우선 호가라고 하고, 둘의 차이를 스프레드라고 한다.

```text
        매도 70,200 | 20
        매도 70,100 | 10
        매도 70,000 | 13     ← 최우선 매도 호가
        ---------------      ← 스프레드 100원
        매수 69,900 | 10     ← 최우선 매수 호가
        매수 69,800 | 4
```

이 호가창은 뒤에서 만들 엔진이 실제로 출력한 것이다. 오른쪽 숫자는 그 가격에 기다리는 수량의 합이다. 69,900원에 사겠다는 사람과 70,000원에 팔겠다는 사람이 있는데 100원 차이라 아직 거래가 안 된다. 누군가 70,000원 이상에 사겠다고 하거나 69,900원 이하에 팔겠다고 하면 그때 체결이 일어난다.

거래소가 바깥에 보여 주는 시장 데이터도 이 호가창에서 나온다. 미국 시장에서는 흔히 세 단계로 나눈다. L1은 최우선 호가와 그 수량만, L2는 여러 가격 단계의 합계 수량(위 표), L3는 가격 단계마다 줄 서 있는 주문 하나하나다. 더 자세할수록 비싸게 판다.

## 같은 가격이면 먼저 온 주문부터

매칭 규칙 중 가장 널리 쓰는 것이 가격-시간 우선이다. 먼저 가격이 좋은 주문이 앞선다. 사는 쪽에서는 높은 가격, 파는 쪽에서는 낮은 가격이 좋은 가격이다. 가격이 같으면 먼저 들어온 주문이 앞선다. 은행 창구의 번호표처럼 가격마다 줄이 하나씩 있다고 생각하면 된다.

첫 장면의 답이 이것이다. 화면에 보이던 70,000원 매도 물량은 내 주문보다 조금 먼저 거래소에 도착한 다른 매수가 가져갔다. 화면은 몇 밀리초 전의 호가창이었다. 남은 물량이 없으니 내 주문은 매수 호가창의 70,000원 줄 맨 뒤에 섰다. 그 줄에는 나보다 먼저 70,000원에 사겠다고 한 사람들이 있었고, 새 매도가 들어오자 그 사람들이 먼저 체결됐다. 같은 가격이라도 늦게 온 주문은 앞 주문들이 다 처리된 뒤에야 차례가 온다.

위 호가창의 70,000원 매도 줄을 L3로 보면 이렇다.

```text
70,000원 줄 순서(L3): s2:5, s3:8
```

s2가 5주, 그 뒤에 s3가 8주 기다린다. 여기에 b3가 70,000원에 7주를 사겠다고 들어오면 엔진은 줄 맨 앞부터 가져간다.

```text
#7 b3 매수 7주 @ 70,000
   체결 T1: 5주 @ 70,000  (b3 ← s2)
   체결 T2: 2주 @ 70,000  (b3 ← s3)
   b3 상태: filled
```

체결 가격은 기다리던 쪽(먼저 호가창에 있던 주문)의 가격으로 정한다. 호가창에 주문을 올려 두고 기다리는 쪽을 메이커(maker), 들어와서 그 주문을 가져가는 쪽을 테이커(taker)라고 한다. 테이커가 더 좋은 가격을 불렀어도 체결은 메이커 가격으로 된다. 70,100원에 사겠다고 들어온 주문이 70,000원 매도를 만나면 70,000원에 산다.

## 호가창을 담을 자료 구조

매칭 엔진이 1초에 수십만 번 하는 일은 네 가지다. 최우선 호가 찾기, 그 가격 줄의 맨 앞 주문 가져가기, 새 주문을 줄 맨 뒤에 붙이기, 주문 id로 찾아 취소하기. 이 넷이 모두 빨라야 한다.

```js
class Level {            // 가격 단계 하나 = 줄 하나
  constructor(price) { this.price = price; this.total = 0; this.head = null; this.tail = null; }
  push(o) { /* 줄 맨 뒤에 붙인다: O(1) */ }
  unlink(o) { /* 앞뒤 주문을 서로 이어 붙여 빼낸다: O(1) */ }
}
class Side {             // 매수 쪽 또는 매도 쪽
  levels = new Map();    // 가격 → Level
  prices = [];           // 좋은 가격이 앞에 오도록 정렬. 새 가격은 이진 탐색으로 끼운다
  best() { return this.levels.get(this.prices[0]); }
}
class OrderBook {
  bids = new Side(true); asks = new Side(false);
  orders = new Map();    // 주문 id → 주문. 취소할 때 바로 찾는다
}
```

가격 단계마다 줄은 이중 연결 리스트다. 주문마다 앞 주문과 뒤 주문을 가리키는 칸이 있다. 맨 앞을 빼거나 맨 뒤에 붙이는 건 배열로도 되지만, 줄 중간에 있는 주문을 취소할 때 차이가 난다. 배열이라면 그 주문을 찾아 뒤를 한 칸씩 당겨야 한다. 이중 연결 리스트는 `orders` 맵으로 주문을 바로 찾고 앞뒤를 이어 붙이면 끝이다.

가격 단계 목록(`prices`)은 정렬된 배열로 뒀다. 실제 호가창에서 주문이 몰리는 가격 단계는 최우선 호가 근처의 수십 개 정도라 배열로도 충분했다. 단계가 많아지면 균형 트리나 가격을 인덱스로 쓰는 배열(호가 단위가 정해져 있으니 가능하다)을 쓴다.

매칭의 본체는 짧다.

```js
place(o) {
  o.remaining = o.qty; const trades = [];
  const opp = o.side === "buy" ? this.asks : this.bids;               // 맞은편 호가창
  const crosses = (p) => (o.side === "buy" ? p <= o.price : p >= o.price);
  let best;
  while (o.remaining > 0 && (best = opp.best()) && crosses(best.price)) {
    const maker = best.head;                                          // 같은 가격에서는 먼저 온 주문부터
    const q = Math.min(o.remaining, maker.remaining);
    trades.push({ id: ++this.tradeId, price: best.price, qty: q, taker: o.id, maker: maker.id });
    o.remaining -= q; maker.remaining -= q; best.total -= q;
    if (maker.remaining === 0) { best.unlink(maker); this.orders.delete(maker.id); }
    if (!best.head) opp.drop(best);                                   // 빈 가격 단계는 지운다
  }
  if (o.remaining > 0) { /* 남은 수량은 내 쪽 호가창 줄 맨 뒤에 */ }
  return trades;
}
```

가격-시간 우선은 코드 두 군데에 그대로 옮겨져 있다. 체결 가격으로 메이커의 가격인 `best.price`를 쓰고, 같은 가격 안에서는 줄 맨 앞인 `best.head`부터 가져간다.

## 체결 기록을 따라가 본다

앞의 호가창(매도 70,000원 13주, 70,100원 10주, 70,200원 20주 / 매수 69,900원 10주, 69,800원 4주)에서 b3가 들어온 다음 주문들을 차례로 넣었다. 출력은 실제 엔진이 낸 것이다.

```text
#8 b4 매수 15주 @ 70,100
   체결 T3: 6주 @ 70,000  (b4 ← s3)
   체결 T4: 9주 @ 70,100  (b4 ← s1)
   b4 상태: filled
        매도 70,200 | 20
        매도 70,100 | 1
        ---------------
        매수 69,900 | 10
        매수 69,800 | 4
```

b4는 70,100원까지 낼 생각이었지만 먼저 70,000원에 남은 6주를 샀다. 더 좋은 가격부터 가져가기 때문이다. 나머지 9주는 70,100원에 샀다. 이제 70,000원 매도 줄은 비었고 최우선 매도 호가가 70,100원으로 올라갔다. 큰 매수 주문이 들어오면 가격이 오르는 이유가 이것이다.

```text
#9 s5 매도 12주 @ 69,800
   체결 T5: 10주 @ 69,900  (s5 ← b1)
   체결 T6: 2주 @ 69,800  (s5 ← b2)
   s5 상태: filled
        매도 70,200 | 20
        매도 70,100 | 1
        ---------------
        매수 69,800 | 2
```

매도 쪽도 거울처럼 같다. 69,800원 이상이면 팔겠다는 s5는 더 비싸게 사 주는 b1(69,900원)부터 팔았다.

취소도 해 봤다. 아직 2주가 남은 b2와, 이미 다 체결된 s2를 취소했다.

```text
취소 b2: {"ok":true,"canceledQty":2}
취소 s2: {"ok":false,"reason":"없거나 이미 체결된 주문"}
```

이미 체결된 주문을 취소하려는 요청은 흔하다. 사용자가 취소 버튼을 누른 순간과 체결이 일어난 순간이 몇 밀리초 차이로 엇갈리기 때문이다. 엔진은 시퀀서가 정한 순서대로 처리하니 먼저 도착한 쪽이 이긴다. 결과는 둘 중 하나로 분명해야 하고, 사용자에게는 "취소 실패: 이미 체결됨"을 보여 준다.

## 가격 단계를 훑고 지나가는 큰 주문

마지막으로 b6가 70,300원에 30주를 사겠다고 들어왔다. 지갑에서는 주문 금액 전체(70,300 × 30)를 먼저 묶었다.

```text
#10 b6 매수 30주 @ 70,300
   체결 T7: 1주 @ 70,100  (b6 ← s1)
   체결 T8: 20주 @ 70,200  (b6 ← s4)
   b6 상태: partial, 남은 9주 호가창에
   묶은 돈 2,109,000 = 체결 1,474,100 + 남은 주문 몫 632,700 + 풀어 줄 차액 2,200
        ---------------
        매수 70,300 | 9
```

b6는 매도 호가 두 단계를 훑고 21주를 샀다. 70,300원 이하 매도가 더 없으니 남은 9주는 매수 호가창에 70,300원으로 올라갔다. 매도 쪽이 텅 비었다. 70,300원을 부를 각오로 묶었던 돈 중 더 싸게 산 차액 2,200원은 바로 풀어 준다. 남은 9주 몫은 주문이 체결되거나 취소될 때까지 묶어 둔다. 주문과 지갑 사이의 이 정산을 빠뜨리면 사용자의 돈이 이유 없이 묶여 있게 된다.

## 얼마나 빨라야 하나

숫자를 어림해 본다. 종목 2,000개, 하루 주문(신규와 취소) 2억 건, 정규장 6시간 30분(09:00~15:30)이라고 하자.

```text
평균 초당 주문 = 200,000,000 ÷ (6.5 × 3,600) ≈ 8,547
장 시작 직후 평균의 10배가 몰린다면 ≈ 85,470
주문 하나를 200바이트로 저장하면 하루 200,000,000 × 200B = 40GB
```

장 시작과 마감 직전에 주문이 몰리는 건 어느 시장이나 비슷하다. 그래서 평균보다 피크를 기준으로 잡는다. 종목마다 호가창이 따로 있으니 종목별로 엔진을 나눠 맡길 수 있다. 다만 인기 종목 하나에 주문이 쏠리면 그 종목의 엔진 하나가 전부 받아야 한다. 한 종목의 호가창은 순서가 생명이라 여러 대로 쪼갤 수 없다.

앞에서 만든 엔진에 무작위 주문과 취소 100만 건을 넣어 봤다. 가격은 70,000원 근처 호가 단위 100원으로 흩었고 20%는 취소다. 이 머신의 Node 22 기준이다.

```text
주문·취소 1,000,000건, 체결 452,142건, 941ms → 초당 1,062,569건
건당 지연 p50 0.46µs  p99 2.73µs  p99.9 15.02µs  최대 20764µs
남은 주문 221219, 매수 가격 단계 12, 매도 가격 단계 13
```

한 스레드로 초당 100만 건 남짓을 처리했다. 매칭 자체는 1마이크로초 안팎이라 앞의 피크 8만 5천 건은 넉넉하다. 그런데 마지막 줄의 최대 지연이 20밀리초다. 대부분은 0.5마이크로초인데 가끔 수만 배 느린 순간이 있다. 거래소에서는 평균보다 이 꼬리가 문제다. 지연 분포를 백분위로 보는 법은 [백분위 지연 글](/posts/percentile-latency)에 있다. 이 꼬리가 어디서 오는지, 그리고 엔진 바깥의 네트워크와 디스크가 더하는 밀리초를 어떻게 줄이는지가 [다음 글](/posts/sd-stock-exchange-low-latency)의 주제다.

시장 데이터 쪽은 체결 기록에서 봉(캔들) 차트도 만든다. 봉 하나는 한 구간(예: 1분)의 시가, 고가, 저가, 종가, 거래량이다. 앞의 체결 T1~T8에 시각을 붙여 1분 봉을 만들었다.

```js
for (const tr of trades) {
  const minute = tr.t.slice(0, 5);                      // "09:00"
  const c = candles.get(minute);
  if (!c) candles.set(minute, { open: tr.price, high: tr.price, low: tr.price, close: tr.price, volume: tr.qty });
  else { c.high = Math.max(c.high, tr.price); c.low = Math.min(c.low, tr.price); c.close = tr.price; c.volume += tr.qty; }
}
```

```text
09:00 {"open":70000,"high":70100,"low":70000,"close":70100,"volume":22}
09:01 {"open":69900,"high":70200,"low":69800,"close":70200,"volume":33}
```

보고 쪽은 정확성이 우선이다. 주문과 체결의 고객 id, 가격, 수량, 체결 수량, 남은 수량을 빠짐없이 DB에 남긴다. 장이 끝난 뒤 하루치 체결을 증권사 기록과 맞춰 보는 대사도 여기서 한다.

현장에서 자주 나오는 실수 몇 가지를 적어 둔다. 가격을 부동소수점으로 다뤄 70,000.0000001 같은 값이 다른 가격 단계로 갈라지는 것, 같은 사람의 매수와 매도가 서로 체결되는 자기 거래를 막지 않는 것(시세 조작으로 볼 수 있어 거래소마다 막는 규칙이 있다), 체결된 차액을 지갑에서 풀어 주지 않는 것, 그리고 주문 저장이나 로그 쓰기를 거래 경로 안에 두는 것이다.

## 다음 글에서 엔진을 빠르고 죽지 않게 만든다

호가창은 가격마다 줄이 하나씩 있는 자료 구조이고, 매칭 엔진은 맞은편 최우선 호가의 줄 맨 앞부터 가져가는 단순한 반복이다. 가격이 좋은 주문이 먼저, 같은 가격이면 먼저 온 주문이 먼저다. 체결 가격은 기다리던 쪽의 가격이다. 체결 기록은 시장 데이터와 보고로 퍼지고, 그 일들은 거래 경로 밖에서 한다.

남은 문제가 둘 있다. 같은 가격에서 "먼저"를 누가 정하나. 그리고 엔진이 죽으면 호가창을 어떻게 똑같이 되살리나. [증권 거래소 설계 ②](/posts/sd-stock-exchange-low-latency)에서 시퀀서와 결정적 재생, 단일 스레드 루프로 이 둘을 푼다. 지갑에서 본 재생 원리가 여기서 다시 나온다.

## 면접에서 나올 만한 질문

### 가격-시간 우선이 무엇인가요?

매칭 순서를 정하는 규칙이다. 먼저 가격이 좋은 주문이 앞서고(사는 쪽은 높은 가격, 파는 쪽은 낮은 가격), 가격이 같으면 먼저 들어온 주문이 앞선다. 그래서 호가창은 가격 단계마다 FIFO 줄을 두고, 들어온 주문은 맞은편 최우선 가격 줄의 맨 앞부터 가져간다.

### 체결 가격은 어떻게 정하나요?

호가창에서 기다리던 주문, 즉 메이커의 가격으로 정한다. 70,100원에 사겠다고 들어온 주문이 70,000원 매도를 만나면 70,000원에 체결된다. 들어오는 쪽(테이커)은 자기가 부른 가격보다 나쁘게 체결되지 않으니 손해가 없고, 기다리던 쪽은 자기가 낸 가격 그대로 거래된다.

### 호가창 자료 구조는 어떻게 설계하나요?

가격 → 가격 단계의 맵과 좋은 가격 순으로 정렬된 가격 목록, 단계마다 주문을 담은 이중 연결 리스트, 주문 id → 주문의 맵을 둔다. 최우선 호가 찾기, 줄 맨 앞 빼기, 맨 뒤 붙이기, id로 취소하기가 모두 O(1)에 가깝다. 이중 연결 리스트라서 줄 중간의 주문도 앞뒤를 이어 붙이기만 하면 빠진다.

### 이미 체결된 주문에 취소 요청이 오면요?

엔진은 시퀀서가 정한 순서대로 처리하니 먼저 순번을 받은 쪽이 이긴다. 체결이 먼저면 취소는 "이미 체결됨"으로 실패하고, 취소가 먼저면 그 주문은 체결되지 않는다. 사용자에게는 둘 중 하나의 결과만 분명히 돌려준다.

### 매수 주문을 받을 때 지갑에서는 무엇을 하나요?

주문 금액(지정가 × 수량)을 먼저 묶어 둔다. 그래야 체결된 뒤 돈이 모자라는 일이 없다. 더 싼 가격에 체결되면 차액을 풀어 주고, 남은 수량 몫은 체결되거나 취소될 때까지 묶어 둔다. 실습에서 70,300원 × 30주를 묶고 체결 뒤 차액 2,200원을 풀었다.

### 주문이 10배로 늘면 매칭 엔진을 어떻게 늘리나요?

종목별로 호가창이 독립적이니 종목을 여러 엔진에 나눠 맡긴다. 한 종목의 호가창은 순서가 생명이라 쪼갤 수 없어서, 인기 종목은 엔진 하나가 감당해야 한다. 실습 엔진은 한 스레드로 초당 100만 건 남짓을 처리했으니 매칭 계산보다는 네트워크와 디스크, 지연의 꼬리가 먼저 문제가 된다.

### 시장 데이터와 보고는 왜 거래 경로 밖에 두나요?

거래 경로는 지연이 가장 중요하고, 시장 데이터와 보고는 각각 공정한 배포와 정확성이 중요하다. 요구가 다른 일을 한 길에 두면 가장 느린 일이 체결을 늦춘다. 매칭 엔진은 순번이 찍힌 체결 기록을 흘려보내기만 하고, 발행기와 보고기가 그 기록을 따라 읽으며 각자 일을 한다.
