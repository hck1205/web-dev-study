[Two Sum](/posts/leetcode-two-sum)을 해시맵으로 푼 다음 이 문제를 만나면, 대부분 같은 해시맵 풀이를 그대로 낸다. 통과는 된다. 그런데 문제 조건에 "추가 공간은 상수만 쓴다"가 붙어 있다. 해시맵은 원소 수만큼 메모리를 쓰니 조건을 어긴 답이다. 면접에서라면 여기서 "배열이 정렬돼 있다는 걸 왜 안 썼나요?"라는 질문을 받는다.

[LeetCode 167. Two Sum II - Input Array Is Sorted](https://leetcode.com/problems/two-sum-ii-input-array-is-sorted/)는 정렬이라는 조건 하나가 풀이를 얼마나 바꾸는지 보여 준다. 이 글은 모든 짝을 더해 보는 방법에서 시작해 해시맵, 이분 탐색, 투 포인터 순서로 네 가지를 본다. 특히 투 포인터에서 "한쪽을 움직여도 답을 놓치지 않는 이유"를 손으로 증명해 본다. 면접에서 가장 많이 파고드는 부분이 바로 그 증명이다. 패턴 전체 그림은 [투 포인터 패턴 글](/posts/two-pointers-pattern)에 있다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 줄 서 있는 수에서 두 개 고르기

문제를 내 말로 줄이면 이렇다. 오름차순(작은 수부터 큰 수 순서)으로 정렬된 정수 배열 `numbers`와 목표값 `target`이 주어진다. 더해서 `target`이 되는 두 수를 찾아 그 위치를 돌려준다. 단, 위치는 0이 아니라 1부터 센다. 답은 정확히 하나 있고, 같은 칸을 두 번 쓸 수는 없다. 그리고 추가 공간은 상수만 써야 한다.

예시를 직접 만들어 보자.

```text
numbers = [1, 3, 4, 6, 8, 11], target = 10
4 + 6 = 10 → 4는 3번째, 6은 4번째 → 답 [3, 4]
```

풀이를 고를 때 영향을 주는 제약은 세 가지다.

- 길이는 최대 3 × 10^4이다. 모든 짝은 약 4.5억 개라 O(n²)는 느리다.
- 값은 -1000에서 1000 사이다. 두 수를 더해도 정수 범위를 넘지 않는다. 이 조건이 없으면 Java에서 오버플로를 따져야 한다(뒤에서 실제로 터뜨려 본다).
- 추가 공간 O(1). 해시맵이나 정렬된 사본을 만들 수 없다.

반환 번호가 1부터라는 것도 꼭 기억하자. 로직은 맞았는데 `[2, 3]`을 돌려줘서 틀리는 경우가 생각보다 많다.

## 모든 짝을 더해 본다

가장 먼저 떠오르는 건 첫 번째 수를 고르고, 그 뒤의 수를 하나씩 붙여 보는 방법이다.

```js
// 풀이 1: 모든 짝 검사
function twoSum(numbers, target) {
  for (let i = 0; i < numbers.length; i++) {
    for (let j = i + 1; j < numbers.length; j++) { // j는 i 뒤에서만 → 같은 칸을 두 번 쓰지 않는다
      if (numbers[i] + numbers[j] === target) return [i + 1, j + 1];
    }
  }
  return [];
}
```

`j`를 `i + 1`부터 시작하는 게 두 가지 일을 한다. 같은 칸을 두 번 쓰는 걸 막고, (1, 3)과 (3, 1)처럼 같은 짝을 두 번 보는 것도 막는다. 그래도 짝의 수는 n(n − 1) / 2개라 O(n²)이다. 공간은 O(1)이다.

답이 배열 끝에 있는 최악의 경우를 3만 개로 만들어 재 봤다.

```text
brute [ 29999, 30000 ] 411.7ms
```

0.4초다. 시간 제한에 따라 통과하기도 하고 떨어지기도 하는 수준이다. 무엇보다 이 풀이는 배열이 정렬돼 있다는 정보를 전혀 쓰지 않았다. 정렬되지 않은 배열에도 똑같이 돌아간다는 건, 그만큼 얻을 수 있는 걸 버리고 있다는 뜻이다.

## 짝을 장부에 적어 둔다

[Two Sum](/posts/leetcode-two-sum)에서 쓴 방법이다. 수를 하나 볼 때마다 "내 짝은 `target - 나`다"를 계산하고, 지금까지 본 수를 [해시맵](/posts/ds-hash-map)에 적어 둔다. 짝이 이미 장부에 있으면 끝이다.

```js
// 풀이 2: 해시맵
function twoSum(numbers, target) {
  const seen = new Map(); // 값 → 0부터 센 인덱스
  for (let i = 0; i < numbers.length; i++) {
    const need = target - numbers[i];
    if (seen.has(need)) return [seen.get(need) + 1, i + 1]; // 먼저 본 쪽이 앞 번호
    seen.set(numbers[i], i);
  }
  return [];
}
```

시간은 O(n)이다. 해시맵 조회와 삽입이 평균 O(1)이고 배열을 한 번 훑는다. 3만 개로 재면 6ms 정도였다. 그런데 공간이 O(n)이다. 문제의 "추가 공간은 상수"를 어긴다.

순서도 한 번 짚자. `seen.has(need)`를 먼저 보고 나서 `seen.set`을 한다. 순서를 바꾸면 `[3, 3]`, `target = 6`에서 3을 넣자마자 자기 자신을 짝으로 찾아 `[1, 1]`을 돌려준다.

이 풀이도 정렬 정보를 쓰지 않았다. 다음 두 풀이는 정렬을 쓴다.

## 짝을 이분 탐색으로 찾는다

정렬된 배열에서 특정 값을 찾는다면 [이분 탐색](/posts/binary-search)이 먼저 떠오른다. 수 하나를 고를 때마다 짝 `target - numbers[i]`를 해시맵 대신 이분 탐색으로 찾으면 된다. 추가 공간이 필요 없다.

중요한 건 찾는 범위다. `i`의 오른쪽(`i + 1`부터 끝까지)에서만 찾는다. 왼쪽은 이미 그 수를 골랐을 때 오른쪽에서 찾아봤으니 다시 볼 필요가 없고, 자기 자신을 짝으로 찾는 것도 막는다.

```js
// 풀이 3: 수마다 짝을 이분 탐색
function twoSum(numbers, target) {
  for (let i = 0; i < numbers.length; i++) {
    const need = target - numbers[i];
    let lo = i + 1, hi = numbers.length - 1; // i 오른쪽에서만 찾는다
    while (lo <= hi) {
      const mid = (lo + hi) >>> 1;
      if (numbers[mid] === need) return [i + 1, mid + 1];
      if (numbers[mid] < need) lo = mid + 1;
      else hi = mid - 1;
    }
  }
  return [];
}
```

시간은 수 n개마다 O(log n)이라 O(n log n), 공간은 O(1)이다. 문제 조건을 처음으로 모두 지킨 풀이다. 3만 개로 재면 3ms 정도였다.

Python이라면 표준 라이브러리 `bisect`가 범위 시작점을 받아서 더 짧아진다.

```python
import bisect

def two_sum(numbers, target):
    for i, x in enumerate(numbers):
        j = bisect.bisect_left(numbers, target - x, i + 1)  # i + 1부터 찾는다
        if j < len(numbers) and numbers[j] == target - x:
            return [i + 1, j + 1]
    return []
```

Java는 `Arrays.binarySearch(배열, 시작, 끝, 값)`이 범위를 받는다. 끝은 포함하지 않는다. 찾지 못하면 음수를 돌려주는데, 그냥 -1이 아니라 `-(끼워 넣을 자리) - 1`이다.

```java
static int[] twoSum(int[] numbers, int target) {
    for (int i = 0; i < numbers.length; i++) {
        // [i + 1, length) 범위에서만 찾는다. 없으면 음수
        int j = Arrays.binarySearch(numbers, i + 1, numbers.length, target - numbers[i]);
        if (j >= 0) return new int[]{i + 1, j + 1};
    }
    return new int[0];
}
```

```text
[3, 4]
[1, 2]
-5
```

마지막 줄은 `[1, 3, 4, 6, 8, 11]`에서 7을 찾은 값이다. 7이 들어갈 자리는 4번이라 `-(4) - 1 = -5`다. 그래서 "찾았나"는 `j != -1`이 아니라 `j >= 0`으로 확인해야 한다. 같은 값이 여러 개면 그중 어느 칸을 돌려줄지도 정해져 있지 않다. 이 문제는 답이 하나라 상관없지만, 첫 위치가 필요하면 직접 lower bound를 짠다.

이 풀이의 한계는 log n이 남는다는 것이다. 각 수의 짝을 따로따로 찾기 때문에, 앞에서 찾다가 알게 된 정보("1의 짝 9는 없다")를 다음 수를 찾을 때 전혀 쓰지 않는다. 정렬은 그보다 더 많은 걸 알려 준다.

## 양 끝에서 한 칸씩 지워 나간다

정렬된 배열의 맨 앞은 가장 작은 수, 맨 뒤는 가장 큰 수다. 이 둘을 더해 보면 무슨 일이 생기는지 생각해 보자.

- 합이 목표보다 크다면, 맨 뒤의 수는 가장 작은 수와 더해도 크다. 그러니 다른 어떤 수와 더해도 크다. 맨 뒤의 수는 답이 될 수 없다. 버린다.
- 합이 목표보다 작다면, 맨 앞의 수는 가장 큰 수와 더해도 작다. 맨 앞의 수는 답이 될 수 없다. 버린다.
- 같으면 찾았다.

버리고 나면 남은 배열도 여전히 정렬돼 있고, 같은 질문을 반복할 수 있다. 맨 앞과 맨 뒤를 가리키는 인덱스 두 개(`l`, `r`)만 있으면 "버린다"는 포인터를 한 칸 옮기는 것으로 끝난다.

아래 그림에서 다음을 누르면 `[1, 3, 4, 6, 8, 11]`, 목표 10을 이 규칙대로 따라간다.

```js
// 풀이 4: 투 포인터
function twoSum(numbers, target) {
  let l = 0, r = numbers.length - 1;
  while (l < r) {                              // 같은 칸을 두 번 쓰지 않도록 l < r
    const sum = numbers[l] + numbers[r];
    if (sum === target) return [l + 1, r + 1]; // 1부터 세는 번호
    if (sum < target) l++;                     // 작다 → numbers[l]은 누구와도 모자란다
    else r--;                                  // 크다 → numbers[r]은 누구와도 넘친다
  }
  return [];                                   // 문제에선 답이 항상 있어서 여기 오지 않는다
}
```

비교 한 번마다 `l`이 오른쪽으로 가거나 `r`이 왼쪽으로 가서, 남은 칸이 하나씩 준다. 많아야 n − 1번 비교하면 끝나니 O(n)이다. 공간은 포인터 두 개라 O(1)이다. 3만 개로 재면 1ms도 걸리지 않았다.

```text
brute [ 29999, 30000 ] 411.7ms
hash [ 29999, 30000 ] 6.0ms
bs [ 29999, 30000 ] 2.8ms
tp [ 29999, 30000 ] 0.6ms
```

이분 탐색 풀이와의 차이를 말로 하면 이렇다. 이분 탐색은 수마다 짝을 처음부터 다시 찾았다. 투 포인터는 비교 한 번의 결과로 "이 수는 누구와도 안 된다"를 확정하고 다음으로 넘어간다. 한 번 얻은 정보를 버리지 않는다.

## 한쪽을 옮겨도 답을 놓치지 않는 이유

면접에서 투 포인터를 말하면 거의 반드시 "그렇게 옮기다가 답을 건너뛰면 어떡하나요?"라는 질문이 온다. 감으로 "정렬돼 있으니까요"라고 하면 부족하다. 짝 전체를 표로 그려 보면 증명이 눈에 보인다.

행은 왼쪽 수, 열은 오른쪽 수다. 칸에는 두 수의 합이 들어간다. 같은 칸을 두 번 쓰지 않으니 대각선 위쪽만 의미가 있다. 위 그림의 다섯 번 비교를 이 표에 옮기면 이렇다. 숫자가 적힌 칸은 실제로 더해 본 짝, `★`는 답, `·`는 더해 보지 않고 지운 짝이다.

```text
         1   3   4   6   8  11
   1         ·   ·   ·   9  12
   3             ·   9  11   ·
   4                 ★   ·   ·
   6                     ·   ·
   8                         ·
  11
```

첫 비교는 표의 오른쪽 위 모서리, 1 + 11 = 12다. 이 칸은 11이 있는 열에서 가장 작은 값이다(위로 갈수록 왼쪽 수가 작으니까). 가장 작은 값이 목표보다 크니, 11 열 전체가 목표보다 크다. 열 하나를 통째로 지운다. 이게 `r--`이다.

두 번째 비교는 1 + 8 = 9다. 이 칸은 1 행에서 가장 큰 값이다(오른쪽으로 갈수록 오른쪽 수가 크니까). 가장 큰 값이 목표보다 작으니 1 행 전체가 작다. 행 하나를 지운다. 이게 `l++`이다.

매번 지금 남은 직사각형의 오른쪽 위 모서리를 보고, 그 칸이 크면 열을, 작으면 행을 지운다. 지워진 행이나 열에는 답이 있을 수 없다는 걸 방금 확인했으니, 답이 있다면 늘 남은 직사각형 안에 있다. 직사각형은 매번 한 줄씩 작아지다가 결국 답 칸이 모서리에 오는 순간 찾는다. 15개의 짝 중 5개만 더해 보고 나머지 10개는 보지도 않고 지웠다.

이 표 그림은 같은 아이디어를 쓰는 다른 문제에도 그대로 통한다. 행과 열이 모두 정렬된 2차원 행렬에서 값을 찾는 LeetCode 240(Search a 2D Matrix II)이 오른쪽 위 모서리에서 출발해 행이나 열을 하나씩 지우는 것도 같은 증명이다.

```js
function searchMatrix(matrix, target) {
  let row = 0, col = matrix[0].length - 1; // 오른쪽 위 모서리에서 출발
  while (row < matrix.length && col >= 0) {
    const v = matrix[row][col];
    if (v === target) return true;
    if (v > target) col--; // 이 열은 아래로 갈수록 더 크다 → 열을 지운다
    else row++;            // 이 행은 왼쪽으로 갈수록 더 작다 → 행을 지운다
  }
  return false;
}
```

`[[1, 4, 7, 11], [2, 5, 8, 12], [3, 6, 9, 16], [10, 13, 14, 17]]`에서 9를 찾으면 `true`, 15를 찾으면 `false`가 나왔다. 행이 m개, 열이 n개면 많아야 m + n번 움직인다. Two Sum II의 `l`이 `row`, `r`이 `col`로 이름만 바뀐 것이다.

### Python과 Java로 옮기면

```python
from typing import List

def two_sum(numbers: List[int], target: int) -> List[int]:
    l, r = 0, len(numbers) - 1
    while l < r:
        s = numbers[l] + numbers[r]
        if s == target:
            return [l + 1, r + 1]   # 1부터 세는 번호로 돌려준다
        if s < target:
            l += 1                  # 합이 작다 → 작은 쪽을 키운다
        else:
            r -= 1                  # 합이 크다 → 큰 쪽을 줄인다
    return []
```

Python의 정수는 크기 제한이 없어서 덧셈 오버플로를 신경 쓰지 않아도 된다. 변수 이름을 `sum`으로 쓰면 내장 함수 `sum`을 가리게 되니 `s`나 `total`로 쓰는 편이 낫다.

```java
class Solution {
    public int[] twoSum(int[] numbers, int target) {
        int l = 0, r = numbers.length - 1;
        while (l < r) {
            int sum = numbers[l] + numbers[r]; // 값이 ±1000이라 int로 충분하다
            if (sum == target) return new int[]{l + 1, r + 1};
            if (sum < target) l++;
            else r--;
        }
        return new int[0];
    }
}
```

Java는 `int` 덧셈이 넘치면 조용히 음수로 감긴다. 이 문제의 값 범위에서는 일어나지 않지만, 범위가 `int` 전체라면 실제로 틀린다. 아래 "자주 틀리는 곳"에서 그 입력을 만들어 돌려 본다.

| 풀이 | 시간 | 추가 공간 | 언제 고르나 |
|---|---|---|---|
| 1. 모든 짝 | O(n²) | O(1) | n이 수백 이하이고 빨리 맞는 답이 필요할 때 |
| 2. 해시맵 | O(n) | O(n) | 배열이 정렬돼 있지 않을 때(원래 Two Sum). 이 문제에선 공간 조건 위반 |

| 4. 투 포인터 | O(n) | O(1) | 정렬된 배열의 두 수 합. 이 문제의 정답 |

정렬되지 않은 배열이라면 이야기가 달라진다. 정렬에 O(n log n)이 들고, 원래 인덱스를 돌려줘야 하면 (값, 인덱스) 쌍을 따로 만들어 정렬해야 하니 공간도 O(n)이 된다. 그럴 바엔 해시맵이 낫다. 반대로 이미 정렬돼 있다면 투 포인터가 시간과 공간 모두에서 이긴다. 같은 "두 수의 합"이라도 입력 상태가 풀이를 고른다.

## 면접관이 이어서 바꾸는 문제들

### 배열이 정렬돼 있지 않다면

원래 [Two Sum](/posts/leetcode-two-sum)이다. 해시맵으로 O(n) 시간, O(n) 공간에 푼다. 정렬하고 투 포인터를 쓸 수도 있지만 O(n log n)이 들고, 원래 인덱스를 돌려주려면 인덱스를 함께 들고 정렬해야 한다. 메모리가 정말 부족하고 인덱스가 아니라 값만 돌려주면 될 때는 제자리 정렬 + 투 포인터가 해시맵보다 낫다.

인덱스까지 돌려줘야 하는데 정렬을 쓰고 싶다면, 값을 정렬하지 말고 인덱스 배열을 값 기준으로 정렬한다.

```js
function twoSumUnsorted(nums, target) {
  const idx = nums.map((_, i) => i).sort((a, b) => nums[a] - nums[b]); // 값 순서로 늘어선 인덱스
  let l = 0, r = idx.length - 1;
  while (l < r) {
    const sum = nums[idx[l]] + nums[idx[r]];
    if (sum === target) return [idx[l], idx[r]].sort((a, b) => a - b);
    if (sum < target) l++;
    else r--;
  }
  return [];
}
```

```text
[4,5] [1,2]
```

`[8, 3, 11, 1, 6, 4]`, 목표 10과 `[3, 2, 4]`, 목표 6의 결과다. 원래 Two Sum이라 0부터 센 번호다. 인덱스 배열이 O(n) 공간을 쓰니 해시맵보다 나은 점은 없다. 그리고 JavaScript에서 비교 함수 없이 `sort()`를 부르면 수를 문자열로 바꿔 사전 순으로 정렬한다. `[10, 9, 1].sort()`는 `[1, 10, 9]`가 된다. 정렬 뒤 투 포인터를 쓰는 모든 문제에서 `(a, b) => a - b`를 빼먹으면 조용히 틀린다.

### 합이 target인 짝을 모두 구하라면

찾았을 때 멈추지 않고, 양쪽을 한 칸씩 좁히며 계속한다. 같은 값 짝이 여러 번 나오지 않게 하려면 찾은 뒤 같은 값을 건너뛴다.

```js
function allPairs(numbers, target) {
  const out = [];
  let l = 0, r = numbers.length - 1;
  while (l < r) {
    const sum = numbers[l] + numbers[r];
    if (sum < target) l++;
    else if (sum > target) r--;
    else {
      out.push([numbers[l], numbers[r]]);
      while (l < r && numbers[l] === numbers[l + 1]) l++; // 같은 왼쪽 값 건너뛰기
      while (l < r && numbers[r] === numbers[r - 1]) r--; // 같은 오른쪽 값 건너뛰기
      l++;
      r--;
    }
  }
  return out;
}
```

```text
[[1,7],[2,6],[3,5],[4,4]]
```

`[1, 1, 2, 3, 4, 4, 5, 6, 7, 7]`, 목표 8을 넣은 결과다. 1과 7이 두 개씩 있지만 `[1, 7]`은 한 번만 나왔다. 이 중복 건너뛰기가 [3Sum](/posts/leetcode-3sum)의 핵심 부품이 된다. 3Sum은 수 하나를 고정하고 나머지 두 개를 바로 이 함수로 찾는다.

### 합이 target 이하인 짝의 개수를 세라면

`numbers[l] + numbers[r]`이 target 이하라면, `r`을 고정했을 때가 아니라 `l`을 고정했을 때 `l + 1`부터 `r`까지 모든 수가 `numbers[l]`과 짝이 된다. 그래서 `count += r - l` 하고 `l++`, 넘치면 `r--`다. 짝을 하나하나 세지 않고 한 번에 묶어 세서 O(n)이다.

```js
function countPairsAtMost(numbers, target) {
  let l = 0, r = numbers.length - 1, count = 0;
  while (l < r) {
    if (numbers[l] + numbers[r] <= target) {
      count += r - l; // numbers[l]과 (l+1..r) 모두 짝이 된다
      l++;
    } else {
      r--;
    }
  }
  return count;
}
```

```text
4
```

`[1, 3, 4, 6, 8, 11]`, 목표 7이면 (1, 3), (1, 4), (1, 6), (3, 4)로 4개다. 목표에 가장 가까운 합을 찾는 변형(3Sum Closest 류)도 같은 움직임에 "지금까지 가장 가까운 합"만 기억하면 된다.

```js
function closestSum(numbers, target) {
  let l = 0, r = numbers.length - 1, best = numbers[0] + numbers[1];
  while (l < r) {
    const sum = numbers[l] + numbers[r];
    if (Math.abs(sum - target) < Math.abs(best - target)) best = sum; // 더 가까우면 갱신
    if (sum === target) return sum;  // 정확히 같으면 더 볼 필요가 없다
    if (sum < target) l++;
    else r--;
  }
  return best;
}
```

```text
12 15 -3
```

`[1, 3, 4, 6, 8, 11]`에서 목표 13과 16, 그리고 두 칸짜리 `[-5, 2]`에서 목표 100을 넣은 결과다. 13을 정확히 만드는 짝은 없어서 거리 1인 12가 나왔다(14도 거리 1이지만 먼저 만난 12를 남긴다). 포인터를 옮기는 규칙이 그대로인 이유도 같다. 합이 목표보다 크면, 지금 `r`과 짝지을 수 있는 남은 수 중 `numbers[l]`이 가장 작으니 이 합이 `r`이 만들 수 있는 합 중 목표에 가장 가깝다. 그 값을 기록했으니 `r`은 더 볼 일이 없다. 작을 때도 같은 논리로 `l`을 버린다.

### 입력이 이진 탐색 트리라면

LeetCode 653(Two Sum IV - Input is a BST)이다. 중위 순회하면 정렬된 배열이 나오니, 배열로 펼친 뒤 투 포인터를 쓰면 O(n) 시간, O(n) 공간이다. 공간을 트리 높이 O(h)로 줄이려면 오름차순 반복자와 내림차순 반복자를 스택으로 하나씩 만들어 두 포인터처럼 움직인다.

### 수가 계속 들어오고 질문도 계속 온다면

LeetCode 170(Two Sum III - Data structure design)이다. 넣기가 많은지 묻기가 많은지에 따라 고른다. 값별 개수를 해시맵에 담아 두면 넣기 O(1), 묻기 O(n)이다. 정렬 상태를 유지하면 넣기가 O(n)(또는 균형 트리로 O(log n)), 묻기가 투 포인터로 O(n)이다. 가능한 모든 합을 미리 집합에 넣어 두면 묻기 O(1), 넣기 O(n)에 공간이 O(n²)까지 커진다.

## 정렬은 정보다

이 문제의 투 포인터는 비교 한 번의 결과로 "이 수는 누구와도 답이 될 수 없다"를 확정하고, 그 수를 영원히 지운다. 정렬돼 있기 때문에 맨 앞과 맨 뒤의 합 하나가 행 하나 또는 열 하나 전체의 크기를 알려 주는 것이다. 해시맵 풀이가 틀린 건 아니지만, 정렬이라는 정보를 버리고 메모리로 그 값을 치른 셈이다. 다음 글 [3Sum](/posts/leetcode-3sum)은 이 함수를 반복문 안에 넣어 O(n²)으로 세 수의 합을 찾는다.

## 면접에서 나올 만한 질문

### 이 문제에서 해시맵 대신 투 포인터를 써야 하는 이유는 무엇인가요?

추가 공간을 상수로 제한했기 때문이다. 해시맵은 시간은 O(n)으로 같지만 원소 수만큼 메모리를 쓴다. 배열이 정렬돼 있으면 양 끝 합의 크기만 보고 한쪽을 지울 수 있어서, 포인터 두 개로 O(n) 시간, O(1) 공간에 끝난다. 실제로 재 봐도 할당이 없는 투 포인터가 해시맵보다 빨랐다.

### 포인터를 옮기다가 답을 건너뛰지 않는다는 걸 어떻게 보장하나요?

합이 목표보다 크면 오른쪽 수는 남은 수 중 가장 작은 왼쪽 수와 더해도 크니 어떤 짝으로도 답이 될 수 없다. 작으면 왼쪽 수가 가장 큰 오른쪽 수와 더해도 작으니 마찬가지다. 짝 전체를 표로 그리면 매번 남은 직사각형의 모서리를 보고 행이나 열 하나를 통째로 지우는 것이고, 지운 줄에는 답이 없다는 걸 확인한 뒤 지운다. 그래서 답은 늘 남은 영역 안에 있다.

### 이분 탐색 풀이와 비교하면 어떤가요?

이분 탐색 풀이는 수마다 짝을 따로 찾아 O(n log n), 공간 O(1)이다. 문제 조건은 지키지만, 앞에서 찾다가 얻은 정보를 다음 탐색에 쓰지 않는다. 투 포인터는 비교 결과를 바로 다음 판단에 이어 써서 O(n)이다. 짝 찾기 범위는 반드시 `i + 1`부터 잡아야 자기 자신을 짝으로 찾지 않는다.

### 두 포인터가 만나면 왜 멈추나요?

같은 칸을 두 번 쓰지 않기 위해서다. `l === r`이면 한 원소를 자기 자신과 더하는 셈이라, 그 값의 두 배가 목표와 같을 때 틀린 답을 낸다. 두 포인터가 만나면 남은 짝이 없다는 뜻이니 거기서 끝내는 게 맞다.

### 합이 넘칠 수 있는 언어에서는 무엇을 조심하나요?

Java나 C++의 `int`는 넘치면 음수로 감긴다. 큰 두 수의 합이 음수가 되면 목표보다 작다고 판단해 잘못된 포인터를 움직이고 답을 지나친다. 실제로 `[-2000000000, 5, 2000000000, 2147483647]`, 목표 2000000005에서 빈 배열이 나왔다. 한쪽을 `long`으로 바꾼 뒤 더하면 해결된다.

### 짝을 하나가 아니라 전부 구하라면 어떻게 바꾸나요?

찾았을 때 멈추지 않고 양쪽을 한 칸씩 좁히며 계속한다. 같은 값 짝이 중복으로 나오지 않게 찾은 직후 같은 값들을 건너뛴다. 시간은 여전히 O(n)이고, 이 함수가 3Sum에서 수 하나를 고정한 뒤 나머지 둘을 찾는 부품으로 그대로 쓰인다.

### 배열이 정렬돼 있지 않다면 무엇을 고르나요?

인덱스를 돌려줘야 하면 해시맵이 낫다. 정렬하면 O(n log n)이 들고 원래 인덱스를 따로 들고 다녀야 해서 공간 이점도 사라진다. 값만 돌려주면 되고 메모리가 빠듯하면 제자리 정렬 후 투 포인터가 O(1) 추가 공간이라 고려할 만하다.
