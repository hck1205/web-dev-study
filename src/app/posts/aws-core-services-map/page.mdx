AWS 계정을 처음 만든 날, 가입할 때 쓴 이메일로 로그인해서 EC2 콘솔로 갔다. 인스턴스를 하나 띄우고 SSH 포트를 `0.0.0.0/0`에 열고, 프라이빗 서브넷 실습을 따라 하느라 NAT 게이트웨이도 만들었다. 실습이 끝나자 인스턴스는 중지했다. 2주 뒤 메일이 두 통 와 있었다. 하나는 루트 사용자에 MFA가 없다는 보안 권고였고, 하나는 예상보다 큰 청구 예정 금액이었다. 인스턴스는 꺼 두었는데 NAT 게이트웨이가 시간마다 요금을 쌓고 있었다.

처음 AWS를 만지면 서비스 이름이 200개가 넘어서 무엇부터 봐야 할지 모른다. 그런데 웹 서비스 하나를 올리는 데 실제로 필요한 건 몇 개 안 된다. 이 글은 리전과 가용 영역, IAM, VPC, EC2, S3, RDS 여섯 가지가 어떻게 맞물리는지 지도를 그린다. 계정을 잠그는 순서, 리전을 고르는 기준, 셋을 엮은 기본 구성, 그리고 첫 달 청구서에서 돈이 새는 곳까지 간다. 서비스 하나하나는 이미 깊이 다룬 글이 있어서, 여기서는 연결을 보여 주고 그 글로 넘긴다.

## 가입한 이메일은 매일 쓰는 열쇠가 아니다

가입할 때 만든 계정 주인을 루트 사용자라고 부른다. 루트는 어떤 정책으로도 막을 수 없는 만능 권한을 가진다. 결제 정보를 바꾸고, 계정을 닫고, 모든 리소스를 지울 수 있다. 이 비밀번호와 루트 액세스 키가 새면 공격자는 계정에서 할 수 있는 모든 일을 한다. 흔히 보는 사고는 깃허브에 올라간 루트 키로 수십 개 리전에 GPU 인스턴스를 띄워 채굴하는 것이다.

그래서 루트는 잠가 두고, 매일 쓰는 신원을 따로 만든다. 순서는 이렇다.

1. 루트 사용자에 MFA를 건다. 보안 키나 인증 앱을 쓴다. AWS는 2024년부터 루트 사용자 MFA를 단계적으로 의무화하고 있다.
2. 루트 액세스 키가 있으면 지운다. 루트로 API를 부를 일은 거의 없다.
3. 사람이 쓸 신원을 만든다. 혼자 쓰는 계정이면 관리자 권한의 IAM 사용자 하나에 MFA를 걸어도 되지만, AWS가 권하는 방식은 IAM Identity Center로 로그인하는 것이다. 오래 사는 액세스 키 대신 몇 시간짜리 임시 자격 증명을 받는다.
4. 서버와 프로그램에는 사람의 키를 넣지 않고 IAM 역할을 붙인다. EC2에 역할을 붙이면 인스턴스 안에서 임시 자격 증명이 자동으로 바뀐다.
5. 예산 알림을 건다. 이건 뒤에서 따로 본다.

CLI로 지금 내가 누구로 일하는지는 이렇게 확인한다.

```bash
# 지금 CLI가 쓰는 자격 증명이 어떤 계정의 누구인지 본다
aws sts get-caller-identity
```

출력 형식은 이렇다. `Arn` 끝이 `:root`면 루트 키로 일하고 있다는 뜻이니 바로 바꾼다.

```text
{
    "UserId": "AIDAEXAMPLEUSERID",
    "Account": "123456789012",
    "Arn": "arn:aws:iam::123456789012:user/admin-me"
}
```

```bash
# 루트 MFA가 켜져 있는지(1), 루트 액세스 키가 있는지(0이어야 한다) 본다
aws iam get-account-summary \
  --query "SummaryMap.[AccountMFAEnabled,AccountAccessKeysPresent]"
```

사용자와 역할의 차이, 정책이 평가되는 순서, `AccessDenied`가 났을 때 보는 곳은 [IAM 기초 글](/posts/iam-basics)에 정리했다. 계정을 만든 날 해 둘 보안 설정 전체(CloudTrail, S3 퍼블릭 액세스 차단 등)는 [클라우드 서비스 모델과 공동 책임 글](/posts/cloud-service-models-shared-responsibility)에 체크리스트로 있다.

## 리전과 가용 영역은 어디에 짓느냐다

AWS 리소스는 거의 다 어느 리전에 속한다. 리전은 서울(`ap-northeast-2`), 도쿄(`ap-northeast-1`), 버지니아 북부(`us-east-1`)처럼 지리적으로 떨어진 지역이고, 리전끼리는 완전히 독립적으로 돈다. 서울에 만든 EC2는 도쿄 콘솔에서 보이지 않는다. 처음에 "인스턴스가 사라졌다"고 놀라는 경우의 대부분은 콘솔 오른쪽 위의 리전이 바뀌어 있는 것이다.

리전 안에는 가용 영역(AZ)이 여러 개 있다. 서울 리전은 `ap-northeast-2a`부터 `2d`까지 넷이다. AZ 하나는 전원·냉각·네트워크를 따로 갖춘 데이터 센터 묶음이고, AZ끼리는 몇 킬로미터 이상 떨어져 있으면서 빠른 전용 회선으로 이어져 있다. 그래서 한 AZ가 정전이나 화재로 멈춰도 다른 AZ는 산다. 서버를 두 AZ에 나눠 두는 이유가 이것이다.

한 가지 함정이 있다. `ap-northeast-2a`라는 이름은 계정마다 다른 실제 AZ에 붙을 수 있다. 다른 계정과 같은 AZ를 맞춰야 할 때(예: VPC 엔드포인트 서비스를 공유할 때)는 `apne2-az1` 같은 AZ ID로 맞춘다.

IAM, Route 53, CloudFront처럼 리전 없이 계정 전체에 걸친 서비스도 있다. 이들은 콘솔에서 리전을 "Global"로 보여 준다. CloudFront에 붙일 인증서는 반드시 `us-east-1`의 ACM에서 만들어야 하는 것처럼, 전역 서비스가 특정 리전에 기대는 예외도 있다.

### 리전을 고르는 기준

리전은 한 번 정하면 옮기기 어렵다. 데이터와 서버를 다 다시 만들어야 한다. 고를 때 보는 것은 대략 네 가지다.

사용자와의 거리가 먼저다. 한국 사용자가 대부분이면 서울 리전이 왕복 지연이 가장 짧다. 미국 동부 리전을 쓰면 왕복만 150~200ms 가까이 더해진다.

다음은 법과 계약이다. 개인정보나 금융 데이터는 국내에 두라는 규정이나 고객 계약이 있을 수 있다. 이 경우 고민할 것 없이 리전이 정해진다.

서비스가 그 리전에 있는지도 본다. 새 서비스와 새 인스턴스 타입은 `us-east-1` 같은 큰 리전에 먼저 나오고 다른 리전에는 늦게 온다. 쓰려는 서비스의 리전 목록을 먼저 확인한다.

마지막이 가격이다. 같은 인스턴스라도 리전마다 값이 다르고, 보통 `us-east-1`이 싼 편이다. 지연이 상관없는 배치 작업이나 백업 사본은 다른 리전에 둘 수 있지만, 리전 사이 데이터 전송에도 요금이 붙는다는 걸 같이 계산한다. 여러 리전에 걸쳐 서비스하는 설계는 [멀티 리전 글](/posts/multi-region)에서 다룬다.

## 여섯 가지가 붙는 기본 구성

웹 서비스 하나를 올리는 가장 흔한 모양은 3계층이다. 앞에 로드 밸런서, 가운데 앱 서버, 뒤에 데이터베이스. 여기에 파일은 S3에 둔다. 각 부품이 어느 서비스인지 짝을 지으면 이렇다.

- VPC: 내 리소스가 들어갈 사설 네트워크. 서브넷으로 나누고 라우트 테이블로 길을 정한다.
- EC2: 앱을 돌리는 가상 서버. 프라이빗 서브넷에 두고, 앞의 로드 밸런서(ALB)만 퍼블릭 서브넷에 둔다.
- RDS: AWS가 백업·패치·장애 조치를 맡아 주는 관리형 데이터베이스. 프라이빗 서브넷에 두고 EC2에서만 접근하게 한다.
- S3: 이미지, 업로드 파일, 백업을 두는 객체 저장소. VPC 밖에 있어서 가는 길을 따로 정해야 한다.
- IAM: EC2가 S3를 읽을 권한을 역할로 준다.

Multi-AZ와 읽기 복제본의 차이는 [RDS와 Aurora 글](/posts/rds-aurora-managed-db), S3 권한과 presigned URL은 [S3 실전 글](/posts/aws-s3-in-practice)에서 다룬다.

### 처음엔 이보다 작게 시작해도 된다

이 그림은 "제대로 된" 모양이지만 혼자 만드는 사이드 프로젝트에 처음부터 필요하지는 않다. ALB, NAT 게이트웨이, Multi-AZ RDS는 각각 켜 두기만 해도 시간마다 요금이 나간다.

트래픽이 거의 없는 단계라면 퍼블릭 서브넷에 EC2 한 대, 같은 VPC에 Single-AZ RDS(또는 EC2 안의 DB), S3 하나로 시작해도 된다. 대신 SSH는 내 IP에만 열거나 아예 닫고 SSM Session Manager로 접속하고, DB는 퍼블릭 접근을 끈다.

넘어갈 신호는 이런 것들이다. 서버 한 대가 내려간 동안 서비스가 멈추는 게 용납되지 않을 때 두 AZ와 ALB로 간다. DB가 몇 분 멈추면 매출이 바로 줄어들 때 Multi-AZ를 켠다. 서버를 퍼블릭에서 빼야 하는 보안 요구가 생기면 프라이빗 서브넷과 NAT(또는 필요한 서비스만 VPC 엔드포인트)로 옮긴다. 가용성을 숫자로 정하는 법은 [고가용성 글](/posts/high-availability)에 있다.

### 새 서비스 이름을 만나면 칸부터 찾는다

서비스가 200개가 넘어도 대부분은 이 지도의 어느 칸을 대신하거나 보탠다. 처음 보는 이름을 만나면 "어느 칸의 다른 선택지인가"부터 묻는다.

EC2 칸의 다른 선택지가 컨테이너를 돌리는 ECS·EKS, 서버 없이 함수만 돌리는 Lambda다. 서버를 직접 관리하는 부담이 줄어드는 대신 동작 방식과 요금 계산법이 다르다. Lambda는 요청 수와 실행 시간에, Fargate 위의 ECS는 태스크가 켜진 시간에 요금이 붙는다.

RDS 칸의 다른 선택지가 Aurora, DynamoDB, ElastiCache다. 관계형이냐 키-값이냐, 캐시냐 원본이냐로 고른다.

S3 앞에는 CloudFront(CDN)를 두어 전 세계 가까운 곳에서 파일을 내보내고, 도메인은 Route 53([라우팅 정책 글](/posts/route53-routing-policies))이 맡는다. 둘 다 리전 없이 전역으로 도는 서비스다.

그리고 모든 칸 위에 기록과 감시가 있다. CloudTrail은 누가 어떤 API를 불렀는지 남기고, CloudWatch는 지표·로그·알람을 모은다([CloudWatch 글](/posts/cloudwatch-metrics-logs-alarms)). 이 둘은 서비스를 늘려 갈수록 먼저 켜 둘 것들이다.

## 첫 달 청구서에서 돈이 새는 곳

AWS 요금은 대부분 "켜져 있는 시간"과 "옮긴 바이트"에 붙는다. 처음 장면처럼 인스턴스를 꺼 두었는데도 돈이 나가는 이유는 시간 요금이 붙는 게 인스턴스만이 아니기 때문이다.

NAT 게이트웨이가 가장 흔한 범인이다. `us-east-1` 기준으로 시간당 0.045달러, 처리한 데이터 GB당 0.045달러를 받는다(서울은 조금 더 비싸다). 한 달을 730시간으로 치면 아무 트래픽이 없어도 32.85달러다. 실습 자료가 AZ마다 하나씩 만들라고 하면 두 개, 65.7달러가 된다. 인스턴스를 멈춰도 NAT는 그대로 돈다.

공인 IPv4 주소도 2024년 2월부터 시간당 0.005달러가 붙는다. 인스턴스에 붙어 있든 아니든 마찬가지라, 하나에 한 달 3.65달러다. 퍼블릭 서브넷의 인스턴스, ALB(AZ마다 주소를 쓴다), NAT가 모두 공인 주소를 쓴다.

중지한 EC2의 EBS 볼륨도 계속 과금된다. 인스턴스를 중지하면 컴퓨팅 요금은 멈추지만 디스크는 그대로 남아 GB당 월 요금이 나간다. 인스턴스를 종료(terminate)해도 "종료 시 삭제"가 꺼진 볼륨과 스냅샷은 남는다.

RDS는 중지해도 7일이 지나면 저절로 다시 켜진다. 실습용 DB를 중지해 두고 잊으면 다음 주에 다시 요금이 나간다. 안 쓸 거면 스냅샷을 남기고 삭제한다.

데이터 전송도 있다. 들어오는 트래픽은 무료지만 인터넷으로 나가는 트래픽은 GB당 요금이 붙는다(계정 전체로 매달 100GB까지는 무료). 같은 리전 안이라도 AZ를 넘나드는 트래픽은 양방향으로 GB당 0.01달러씩 붙는다. 앞 그림의 세 번째 단계가 그 경우다.

아래에서 직접 계산해 보자. `monthlyCost`는 리소스 목록을 받아 한 달(730시간) 요금을 센트 단위로 반올림해 돌려준다. 각 리소스는 시간당 요금 `perHour`, 개수 `count`(없으면 1), GB당 요금 `perGB`, 처리량 `gb`를 가질 수 있다. 가격은 바뀌니 예제의 숫자는 위에서 말한 `us-east-1` 공개 요금으로 넣었다.

S3 요청이 하루 수백 GB씩 NAT를 지나고 있다면 첫 번째 줄처럼 처리 요금만 수십 달러가 된다. S3와 DynamoDB는 무료인 게이트웨이 엔드포인트로 이 길을 끊을 수 있다. 다른 서비스(ECR, CloudWatch Logs 등)는 인터페이스 엔드포인트가 필요한데 이건 AZ마다 시간 요금이 붙으니 NAT 요금과 비교해 고른다. 청구서를 위에서부터 읽는 법과 약정 할인, 스팟은 [클라우드 비용 최적화 글](/posts/cloud-cost-optimization)에서 이어진다.

### 무료 체험이 끝나는 날을 안다

새 계정에는 무료 혜택이 있지만 조건이 붙는다. 2025년 7월 이후 만든 계정은 가입 크레딧과 활동 크레딧을 받는 방식으로 바뀌었고, 무료 플랜은 기간이나 크레딧이 끝나면 닫힌다. 그 전에 만든 계정은 12개월 동안 t2/t3.micro 같은 일부 리소스를 정해진 시간만큼 무료로 썼다. 어느 쪽이든 NAT 게이트웨이와 공인 IPv4 주소는 무료 범위가 아니거나 범위가 작으니, "무료로 해 봤는데 청구서가 왔다"의 대부분이 여기서 나온다. 내 계정의 조건은 결제 콘솔의 Free Tier 페이지에서 확인한다.

## 돈이 나가기 전에 알람부터

예산 경보는 계정을 만든 날 걸어 두는 게 좋다. AWS Budgets로 "이번 달 실제 요금이 20달러의 80%를 넘으면 메일"을 걸 수 있다. 콘솔에서는 결제 및 비용 관리 → 예산에서 템플릿으로 1분이면 만든다. CLI로는 이렇게 한다.

```bash
# 월 20달러 예산을 정의한다
cat > budget.json <<'EOF'
{
  "BudgetName": "monthly-20usd",
  "BudgetLimit": { "Amount": "20", "Unit": "USD" },
  "TimeUnit": "MONTHLY",
  "BudgetType": "COST"
}
EOF

# 실제 요금이 80%를 넘으면 메일을 보낸다
cat > notify.json <<'EOF'
[
  {
    "Notification": {
      "NotificationType": "ACTUAL",
      "ComparisonOperator": "GREATER_THAN",
      "Threshold": 80,
      "ThresholdType": "PERCENTAGE"
    },
    "Subscribers": [{ "SubscriptionType": "EMAIL", "Address": "me@example.com" }]
  }
]
EOF

# 예산과 알림을 만든다. 계정 ID는 aws sts get-caller-identity로 확인한다
aws budgets create-budget --account-id 123456789012 \
  --budget file://budget.json \
  --notifications-with-subscribers file://notify.json
```

`ACTUAL` 대신 `FORECASTED`로 하나 더 걸면 "이 속도면 이번 달 20달러를 넘는다"는 예측 경보도 받는다. 처음 장면의 NAT 게이트웨이처럼 일정하게 새는 비용은 예측 경보가 훨씬 일찍 잡는다. 예산 경보는 집계가 하루에 몇 번 갱신되는 정도라 실시간이 아니다. 갑자기 튀는 비용을 잡으려면 Cost Anomaly Detection도 함께 켠다.

예산을 넘었다는 메일이 오면 무엇이 켜져 있는지 찾아야 한다. 리전이 많아서 콘솔로는 놓치기 쉬우니 CLI로 모든 리전을 돈다.

```bash
# 모든 리전을 돌며 실행 중이거나 중지된 인스턴스를 찾는다
for r in $(aws ec2 describe-regions --query "Regions[].RegionName" --output text); do
  echo "== $r"
  aws ec2 describe-instances --region "$r" \
    --query "Reservations[].Instances[].[InstanceId,State.Name,InstanceType]" --output text
done

# 지금 리전의 NAT 게이트웨이 중 살아 있는 것
aws ec2 describe-nat-gateways --filter Name=state,Values=available \
  --query "NatGateways[].[NatGatewayId,SubnetId]" --output text

# 어디에도 붙지 않은 EBS 볼륨과 Elastic IP
aws ec2 describe-volumes --filters Name=status,Values=available \
  --query "Volumes[].[VolumeId,Size]" --output text
aws ec2 describe-addresses --query "Addresses[?AssociationId==null].PublicIp" --output text
```

어떤 서비스가 요금을 만들었는지는 Cost Explorer에서 "서비스별"로, 그 안에서 "사용 유형별"로 쪼개 보면 `NatGateway-Hours`, `NatGateway-Bytes`, `PublicIPv4:InUseAddress` 같은 줄이 바로 보인다. 같은 구성을 반복해서 만들고 지운다면 콘솔 대신 [Terraform](/posts/terraform-basics)으로 만들어 두고 `terraform destroy`로 한 번에 지우는 쪽이 새는 리소스를 덜 남긴다.

## 콘솔에서 CLI로 옮겨 가기

콘솔은 처음 둘러볼 때 편하지만, 무엇을 만들었는지 기록이 남지 않고 리전을 바꿔 가며 확인하기도 번거롭다. 어느 정도 익숙해지면 CLI로 같은 것을 확인하는 습관을 들인다. 리눅스 기준은 Ubuntu 24.04다.

```bash
# AWS CLI v2를 공식 설치 파일로 설치한다 (apt의 awscli 패키지는 버전이 늦을 수 있다)
curl -sSL "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o awscliv2.zip
unzip -q awscliv2.zip
sudo ./aws/install
aws --version
```

액세스 키를 `aws configure`로 넣는 대신, IAM Identity Center를 켰다면 SSO 프로필을 만든다. 브라우저로 로그인하면 몇 시간짜리 임시 자격 증명이 내려오고, 디스크에 오래 사는 키가 남지 않는다.

```bash
# SSO 시작 URL, 리전, 계정, 역할을 묻는 대화형 설정을 한다
aws configure sso --profile dev

# 자격 증명이 만료되면 다시 로그인한다
aws sso login --profile dev

# 매번 --profile을 붙이기 싫으면 환경 변수로 정한다
export AWS_PROFILE=dev
export AWS_REGION=ap-northeast-2
```

이제 앞의 기본 구성에서 놓치기 쉬운 설정을 하나씩 확인해 본다. 바꾸기 전에 지금 상태부터 본다.

```bash
# RDS가 인터넷에서 접근 가능하게 열려 있지 않은지 본다 (False여야 한다)
aws rds describe-db-instances \
  --query "DBInstances[].[DBInstanceIdentifier,PubliclyAccessible,MultiAZ]" --output text

# 계정 전체의 S3 퍼블릭 액세스 차단 설정을 본다 (네 값 모두 true가 기본 권장)
aws s3control get-public-access-block --account-id 123456789012

# 이 VPC에 S3 게이트웨이 엔드포인트가 있는지 본다
aws ec2 describe-vpc-endpoints \
  --filters Name=vpc-id,Values=vpc-0abc1234 Name=service-name,Values=com.amazonaws.ap-northeast-2.s3 \
  --query "VpcEndpoints[].[VpcEndpointId,State]" --output text
```

엔드포인트가 없으면 만들고, 프라이빗 서브넷의 라우트 테이블에 붙인다. 붙이는 순간 그 서브넷의 S3 트래픽이 NAT 대신 엔드포인트로 간다.

```bash
# S3 게이트웨이 엔드포인트를 만들고 프라이빗 라우트 테이블에 연결한다
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-0abc1234 \
  --vpc-endpoint-type Gateway \
  --service-name com.amazonaws.ap-northeast-2.s3 \
  --route-table-ids rtb-0priv1111 rtb-0priv2222
```

만든 뒤에는 프라이빗 서버에서 실제로 S3를 읽어 보고, 다음 날 Cost Explorer에서 `NatGateway-Bytes`가 줄었는지 확인한다. 되돌리려면 `aws ec2 delete-vpc-endpoints --vpc-endpoint-ids vpce-...`로 지우면 경로가 다시 NAT로 돌아간다. 버킷 정책에 `aws:SourceVpce` 조건을 걸어 둔 경우라면 엔드포인트를 지우는 순간 그 버킷 접근이 막히니, 지우기 전에 버킷 정책부터 본다.

CLI 명령이 쌓이면 결국 같은 구성을 코드로 남기고 싶어진다. 그때가 Terraform 같은 IaC로 넘어갈 때다.

## 현장에서 처음 막히는 곳

처음 AWS를 쓰면서 자주 만나는 증상을 원인과 함께 모아 보면 대부분 위 지도의 경계에서 생긴다.

"인스턴스가 사라졌다"는 거의 다 콘솔 리전이 바뀐 것이다. URL의 `region=` 값과 오른쪽 위 리전을 본다.

EC2에 SSH가 안 되면 순서대로 본다. 인스턴스가 퍼블릭 서브넷에 있고 공인 IP가 있는지, 서브넷 라우트 테이블에 인터넷 게이트웨이 경로가 있는지, 보안 그룹이 22번을 내 IP에 열었는지, 키 페어와 사용자 이름(Ubuntu AMI는 `ubuntu`)이 맞는지. 서버를 퍼블릭에 두기 싫다면 SSM Session Manager로 접속하면 22번을 열 필요가 없다.

EC2에서 RDS 접속이 타임아웃이면 RDS 보안 그룹이 EC2의 보안 그룹에서 오는 5432(또는 3306)를 허용하는지 본다. 거절(connection refused)이 아니라 타임아웃이면 거의 언제나 보안 그룹이나 라우팅 문제다.

EC2의 앱이 S3에서 `AccessDenied`를 받으면 인스턴스에 역할이 붙어 있는지, 그 역할의 정책이 버킷 ARN과 객체 ARN(`arn:aws:s3:::bucket/*`)을 둘 다 다루는지, 버킷 정책이 명시적으로 막고 있지 않은지 본다. 인스턴스 안에서 액세스 키를 파일로 넣어 해결하려는 건 피한다. 키가 새는 가장 흔한 길이다.

프라이빗 서브넷의 서버에서 `apt update`가 멈추면 NAT 게이트웨이가 없거나 라우트 테이블이 NAT를 가리키지 않는 것이다. NAT를 두기 싫다면 패키지를 미리 구워 둔 AMI를 쓰거나, 필요한 AWS 서비스만 VPC 엔드포인트로 연다.

## 다시 그 청구서 앞에서

첫날의 실수 두 가지는 지도 위의 두 경계에서 났다. 루트 사용자는 계정 전체에 걸친 만능 열쇠라 MFA로 잠그고 매일은 따로 만든 신원으로 일해야 했다. NAT 게이트웨이는 VPC 안에서 인스턴스와 상관없이 시간 요금을 쌓는 부품이라, 인스턴스를 끈다고 멈추지 않았다. 리전은 어디에 짓느냐, AZ는 몇 동에 나눠 짓느냐, VPC는 울타리, EC2와 RDS는 그 안의 집과 창고, S3는 울타리 밖 보관함, IAM은 출입증이다. 이 지도를 머리에 두면 새 서비스를 만나도 "이건 어느 칸에 속하고 무엇에 요금이 붙나"부터 물을 수 있다.

## 면접에서 나올 만한 질문

### 리전과 가용 영역의 차이는 무엇인가요

리전은 지리적으로 떨어진 독립된 지역이고, 가용 영역은 한 리전 안에서 전원·냉각·네트워크를 따로 갖춘 데이터 센터 묶음이다. 리전끼리는 리소스가 공유되지 않고, AZ끼리는 빠른 전용 회선으로 이어져 있다. 그래서 고가용성은 보통 한 리전 안 여러 AZ로, 재해 복구나 지역 분산은 여러 리전으로 설계한다.

### 루트 사용자는 왜 쓰지 말라고 하나요

루트는 어떤 IAM 정책으로도 제한할 수 없는 만능 권한을 가져서, 자격 증명이 새면 피해 범위가 계정 전체다. MFA를 걸고 액세스 키는 만들지 않으며, 결제나 계정 설정처럼 루트만 할 수 있는 일에만 쓴다. 일상 작업은 IAM Identity Center나 MFA를 건 IAM 사용자로, 서버는 IAM 역할로 한다.

### EC2가 S3에 접근하게 하려면 어떻게 하나요

인스턴스에 IAM 역할(인스턴스 프로파일)을 붙이고, 역할 정책에 필요한 버킷과 객체 ARN에 대한 최소 권한을 준다. SDK는 인스턴스 메타데이터에서 임시 자격 증명을 자동으로 받아 갱신한다. 액세스 키를 인스턴스에 파일로 두는 방식은 키가 새고 회전이 어려워 피한다. 프라이빗 서브넷이면 S3 게이트웨이 엔드포인트로 NAT 요금 없이 가게 한다.

### 웹 서비스의 기본 VPC 구성을 설명해 주세요

두 AZ에 퍼블릭·프라이빗 서브넷을 하나씩 두고, 퍼블릭에는 ALB(필요하면 NAT 게이트웨이), 프라이빗에는 EC2와 RDS를 둔다. ALB 보안 그룹은 443을 열고, EC2 보안 그룹은 ALB 보안 그룹만, RDS 보안 그룹은 EC2 보안 그룹만 받는다. RDS는 Multi-AZ로 다른 AZ에 대기를 두고, 파일은 S3에 두어 게이트웨이 엔드포인트로 연결한다.

### 인스턴스를 다 중지했는데도 요금이 나가는 이유는 무엇인가요

시간 요금이 인스턴스에만 붙지 않기 때문이다. NAT 게이트웨이, 공인 IPv4 주소, ALB는 켜져 있는 동안 계속 과금되고, 중지한 인스턴스의 EBS 볼륨과 스냅샷도 저장 요금이 나간다. RDS는 중지해도 7일 뒤 자동으로 다시 켜진다. Cost Explorer에서 사용 유형별로 쪼개 보면 원인이 바로 보인다.

### NAT 게이트웨이 비용을 줄이려면 어떻게 하나요

먼저 무엇이 NAT를 지나는지 본다. S3와 DynamoDB로 가는 트래픽은 무료 게이트웨이 엔드포인트로 돌리면 처리 요금이 사라진다. ECR이나 CloudWatch 같은 다른 AWS 서비스는 인터페이스 엔드포인트를 쓸 수 있지만 AZ마다 시간 요금이 있어 NAT 요금과 비교해 고른다. 개발 환경은 AZ마다 NAT를 두지 않고 하나만 두거나, 쓰지 않을 때 지운다.

### 리전은 어떤 기준으로 고르나요

사용자와의 지연, 데이터를 어디에 둬야 하는지 정하는 법과 계약, 쓰려는 서비스와 인스턴스 타입이 그 리전에 있는지, 가격 순으로 본다. 규제가 있으면 그게 먼저 정해 준다. 한 번 정하면 데이터와 리소스를 다시 만들어야 해서 옮기기 어려우니 처음에 신중히 고르고, 백업 사본처럼 지연이 상관없는 것만 다른 리전을 고려한다.
