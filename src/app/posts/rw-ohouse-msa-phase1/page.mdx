## 2021년까지 하나의 Rails 서비스

진식의 [오늘의집 MSA Phase 1. 전환전략(2021년 11월)](https://www.bucketplace.com/post/2021-11-19-%EC%98%A4%EB%8A%98%EC%9D%98%EC%A7%91-msa-%EC%97%AC%EC%A0%95-part-1-%EC%8B%9C%EC%9E%91/)은 시작점을 이렇게 적었다.

2014년 앱을 정식 출시했고, 2016년 7월 커머스를 열었다. 그 뒤 MVP 관점에서 정말 빠른 개발과 실험에 집중했고, 더 경험 많은 개발자가 합류하면 기술 부채를 해결할 수 있다는 믿음으로 앞만 보고 달렸다. 그 결과 2021년까지 하나의 모놀리식 서비스로 자랐다.

그 모놀리스는 Ruby on Rails로 만든 `ohs-web`이다. API 게이트웨이 편이 정리한 2021년의 현실은 이렇다. 웹과 모바일 클라이언트 모두 `ohou.se`라는 단일 도메인으로 API를 불렀고, 이 도메인이 API와 웹 페이지를 모두 제공했으며, 그 뒤에는 Rails 서비스 하나만 있었다.

새 기능을 위해 작은 마이크로서비스를 만든 적은 있지만, 주요 비즈니스 로직이 모두 `ohs-web`에 있어서 그 서버들은 아주 특정한 동작만 하는 API 서버로 `ohs-web`이 불러 쓰는 형태였다.

전략 글이 꼽은 모놀리스의 문제는 다섯 가지다. 부분 장애가 전체로 번지고, 일부만 스케일 아웃하기 어렵고, 고칠 때 영향도를 파악하기 어렵고, 코드 전체가 한 프로젝트라 배포가 오래 걸리고, 한 프레임워크와 언어에 묶인다. 글쓴이도 "모두가 알고 있는 내용"이라고 넘겼다. 이 사례에서 눈여겨볼 것은 이유가 아니라 목표 하나다.

## 지금의 10배를 받는다는 목표

전략 글은 MSA로 얻을 세 가지(장애 격리, 복잡도와 의존성 제거, 고가용성과 확장성)에 네 번째 목표를 더했다. 현재 기준 10배의 트래픽을 받는 것이다. 서비스를 나누면 어차피 서비스마다 아키텍처를 다시 설계하고 코드를 새로 쓰게 되니, 이참에 트래픽 대역폭을 넓힐 기회로 삼자는 생각이었다.

높은 트래픽을 감당하게 구성하고 테스트한 뒤 평소에는 줄여(scale in) 두자는 것이다. 10배는 국내 시장 상황과 사용자, 사업 확장을 고려해 정했고, 한때 프로젝트 이름을 "10x 프로젝트"로 부를까도 고민했다고 썼다.

이 목표는 [오토스케일링](/posts/autoscaling)과 짝을 이룬다. 오토스케일링은 정해진 규칙에 따라 서버 수를 늘리지만, 늘린 서버가 실제로 처리량을 늘리려면 병목이 서버 수에 비례해 풀리는 구조여야 한다. DB 하나를 모든 기능이 함께 쓰거나, 한 요청이 모놀리스 안에서 여러 도메인의 테이블을 조인한다면 서버를 10대로 늘려도 DB가 먼저 막힌다.

오늘의집이 "나눈 다음 10배를 테스트하고 줄여 둔다"고 한 것은, 늘릴 수 있는 구조를 먼저 만들고 그 구조가 실제로 늘어나는지 미리 확인해 두겠다는 뜻으로 읽힌다. 10배 테스트를 실제로 어떤 방법으로 했는지는 연재에 나오지 않는다. Aggregator 편에 로드 테스트로 레거시 서버와 Aggregator의 적절한 파드 비율을 찾았다는 대목이 있을 뿐이다.

## 쿠버네티스와 플랫폼팀이 먼저였다

전략 글에 따르면 MSA 이야기는 2019년 1월 신년회에서 서비스 안정화 과업으로 처음 나왔다. 개발자가 인프라를 깊이 몰라도 배포할 수 있는 환경을 위해 쿠버네티스를 검토했고, 실제 적용 테스트는 2020년 2월에 시작했으며, 레거시 코드의 쿠버네티스 이관은 많은 시행착오 끝에 2020년 11월에 끝났다. MSA를 시작하기 1년 전에 배포 기반부터 바꾼 셈이다.

쿠버네티스를 옮기며 얻은 교훈 두 가지로 플랫폼팀을 만들었다. MSA는 비즈니스 과업과 떼어서 준비해야 하고, 사내 플랫폼과 라이브러리를 만들고 관리할 팀이 필요하다는 것이다. 플랫폼팀은 쿠버네티스 고도화, API 게이트웨이와 서비스 메시 PoC, 인증 서비스를 맡았다.

PoC 결과 API 게이트웨이는 Emissary-ingress(당시 이름 Ambassador)로 정했고, 서비스 메시는 글 작성 시점에 PoC 중이었지만 Linkerd를 쓸 예정이었으며, 서비스 사이 내부 통신은 gRPC로 하기로 했다.

플랫폼팀이 내놓은 것도 목록으로 나와 있다. 서비스 사이 일관된 인증을 위한 Auth Service(OIDC 지원), gRPC 통신의 메타정보 수명 주기를 관리하는 Mortar, 실험과 단순 트래픽 조절을 맡는 XPC, 마이크로서비스들의 구성 관리 데이터베이스(CMDB)를 맡는 OpsMonster, 정규화된 로그를 Datadog으로 보내는 Log SDK다.

이 순서에서 읽을 점은 분명하다. 서비스를 하나도 나누기 전에 배포, 인증, 통신 규약, 로그, 트래픽 조절을 먼저 깔았다. 같은 시리즈의 [토스페이먼츠](/posts/rw-tosspayments-legacy-rewrite)가 애플리케이션 재작성 전에 소스 관리와 재현 빌드부터 정리한 것과 같은 순서다.

## 석 달 동안 제품 개발을 멈췄다

가장 과감한 결정은 일정이었다. 전략 글은 특정 인원만 배정해 일부 서비스를 나누는 방법을 버렸다. 그렇게 하면 해 본 사람만 계속하게 되고, 서로 다른 도메인 지식이 없어 진행이 어려워질 것이라고 봤다. 대신 2021년 말 3개월 동안 제품 개발을 멈추고 모든 개발자를 MSA 관련 기술 과업에 넣자고 제안했다. 그 결과 2021년 9월부터 12월 초까지 제품 개발을 멈췄고, 이 기간을 MSA Phase 1이라고 불렀다.

백엔드 분리 편을 쓴 커머스 Tech Lead 지노는 이 3개월의 목표를 셋으로 좁혔다. 커머스, 콘텐츠, O2O 팀의 배포 독립성을 확보한다. 서비스 사이 의존성을 없애고, 다른 팀이 필요로 하는 API를 1순위로 개발한다. API 게이트웨이 안쪽 통신은 gRPC로 통일한다. 원칙도 몇 가지 세웠다. 진행하다 멈추면 안 한 것만 못하니 도전 의식은 잠시 내려놓고 현실에 집중한다. 분리하며 발견한 코드 개선이나 버그 수정은 하지 않는다. 애매하면 슬랙 허들을 켜고 이야기한다.

준비도 적혀 있다. 다른 회사의 전환 사례를 찾아봤지만 "그래서, 어떻게...?"에 답을 얻기 어려웠고, 가장 큰 성과는 목적지의 대략적인 구조를 그린 것이었다고 썼다. 팀원 사이 경험 차이를 줄이려고 업무 시간 중 매주 4시간쯤을 들여 5~6권이 넘는 책을 함께 읽었다. 브레인스토밍에서 나온 원칙 하나는 이렇다.

적은 수의 팀원이 많은 서비스를 맡는 문제를 만들지 않고, 서비스가 커지면 그때 다시 나눈다. 유사하지만 다른 도메인이 한 서비스에 있으면 패키지 구조로 경계를 분명히 한다. [컬리 OMS팀](/posts/rw-kurly-fulfillment-systems)이 엔지니어 수보다 많은 서비스를 "모두가 모든 서비스를 안다"는 조건으로 버틴 것과 반대 방향의 원칙이라 함께 읽을 만하다.

## 프런트엔드부터 떼어 냈다

첫 관문은 백엔드가 아니라 프런트엔드였다. 프런트엔드 개발자 끼로의 [프론트엔드 분리작업(2021년 12월)](https://www.bucketplace.com/post/2021-12-03-%EC%98%A4%EB%8A%98%EC%9D%98%EC%A7%91-msa-phase-1-%ED%94%84%EB%A1%A0%ED%8A%B8%EC%97%94%EB%93%9C-%EB%B6%84%EB%A6%AC%EC%9E%91%EC%97%85/)에 따르면, 오늘의집은 Rails 컨트롤러가 DB에서 데이터를 가져와 `.erb` 템플릿으로 HTML을 그리는 방식을 벗어난 적이 없었고, JSON도 `.jbuilder` 템플릿으로 그렸다.

React를 붙일 때도 `.erb`에서 자바스크립트 런타임을 불러 React에 렌더링을 맡기는 형태였다. React를 PHP나 JSP 같은 템플릿 언어처럼 쓴 셈이라고 글은 표현했다.

이 구조에서는 백엔드를 Kotlin과 Spring으로 옮기려 해도 화면이 Rails에 붙어 있다. 그래서 클라이언트 코드가 독립적으로 도는 클라이언트 서버(Node.js)를 만들어 백엔드와 클라이언트의 수명 주기를 떼어 냈다. 몇 년 동안 React로 다시 쓰며 Ruby 쪽 CSS·JS·템플릿 참조를 줄여 온 것이 바탕이 됐고, 신규 기능이 없어 리팩터링된 적 없던 레거시 페이지는 모든 프런트엔드 개발자가 함께 React로 옮겼다.

개발을 멈출 수 없는 상황이라 두 서버가 동시에 동작해야 했다. 저장소도 바로 옮길 수 없어 git subtree로 양쪽에서 커밋하고 동기화했다. 클라이언트 서버는 React로 그릴 수 있는 경로만 직접 처리하고 나머지는 프록시로 Rails에 넘겼다.

전환은 2021년 11월 트래픽 조절로 조금씩 옮겨 11월 26일에 100%를 마쳤다. 스트랭글러 피그(새 시스템을 앞에 세우고 경로를 하나씩 넘겨받는 방법, [마이크로서비스](/posts/microservices) 글의 "조금씩 옮기기" 절)를 화면 단위로 쓴 모습이다.

프런트엔드 편에서 하나 더 볼 대목은 두 저장소를 함께 굴린 방법이다. 개발을 멈출 수 없으니 새 기능은 Rails 서버와 새 클라이언트 서버 양쪽에서 모두 정상 동작해야 했다. git subtree로 기존 저장소의 프런트엔드 폴더를 새 저장소로 이어 받아 양쪽에서 커밋을 동기화했는데, 이 방식에서는 커밋이 두 벌로 복사되는 현상이 생긴다.

글쓴이는 GitHub 잔디가 진해지는 것 말고는 문제가 없다고 보고 넘어갔다. 큰 저장소를 쪼갤 때 이력을 살리는 일과 양쪽을 동시에 개발하는 일을 함께 풀어야 한다는 점에서, [프런트엔드 모노레포](/posts/frontend-monorepo) 글의 반대 방향 고민과 맞닿는다.

## 게이트웨이에서 Rails 세션을 읽어야 했다

프런트엔드와 백엔드 사이에는 API 게이트웨이가 들어갔다. Platform팀 리드 호성과 DevOps 엔지니어 제제의 [API Gateway(2021년 12월 31일)](https://www.bucketplace.com/post/2021-12-30-msa-phase-1-api-gateway/)는 게이트웨이를 고를 때 세 기능을 중점으로 봤다고 썼다.

세 기능은 Path와 Header 기반 라우팅, 가중치에 따른 트래픽 라우팅, 서비스와 사용자 인증이다. 게이트웨이의 일반적인 역할과 SPOF 위험은 [API 게이트웨이 활용](/posts/api-gateway-use-cases) 글에 있고, 이 글도 응답 시간 증가와 SPOF를 단점으로 먼저 적었다.

가장 먼저 풀어야 할 것은 인증이었다. 게이트웨이가 요청이 인증된 사용자의 것인지 판단해 주면 뒤의 서비스들은 인증을 반복하지 않아도 된다. 조건은 까다로웠다. 서비스 중단이나 모바일 앱 강제 업데이트 없이 바꾸기로 했으므로, Rails에 구현된 인증 방식(브라우저 쿠키 기반 세션 키, Static Auth Token)을 그대로 지원하면서 새로 들일 JWT도 함께 지원해야 했다.

Ambassador의 인증 기능은 유료 사용자에게만 제공돼서, Envoy의 외부 인증 인터페이스 ext-authz를 이용해 인증 계층을 직접 만들었다.

세부 구현에서 배울 점이 둘 있다. 첫째, 인증 방식을 Filter(세션→토큰 변환 S2T, JWT, IP)와 FilterPolicy(어떤 Host·Path에 어떤 Filter를 어떤 순서로)로 나누고, 둘을 쿠버네티스 Custom Resource로 정의했다. 서비스의 라우팅 규칙(Ambassador의 Mapping)과 인증 규칙을 모두 그 서비스의 배포 매니페스트 옆에서 보고 싶었기 때문이다.

둘째, 레거시 세션 해석을 "필요한 만큼만" 했다. Rails 세션은 쿠키에 담긴 정보를 Ruby 객체로 Marshal한 형식이라, 다른 언어에서 읽기 어렵다. 세 방법을 놓고 비교했다. Go에서 Ruby를 자식 프로세스로 실행하기, Rails에 해석용 내부 API를 두고 매번 부르기, Ruby Marshal 형식을 Go로 직접 읽기. 앞의 둘은 모든 요청 앞단에서 도는 인증 서버에 통신 오버헤드가 너무 컸다.

그래서 고른 세 번째 방법도 Rails 위의 객체까지 되살릴 수는 없어서, UserId가 든 값 하나만 Ruby 정수 형식으로 해석했다. 세션에서 다른 정보를 더 꺼내려면 추가 구현이 필요하다고 글이 직접 밝혔다. 세션 쿠키 방식의 일반은 [쿠키·세션 로그인](/posts/cookie-session-login) 글에 있다.

JWT 쪽은 키 공유가 문제였다. 보통은 OAuth 서버가 JWKS(서명 키 묶음)를 URL로 내주지만, 그러면 OAuth 서버에 부하가 가고 그 서버가 잘못 배포되거나 장애가 나면 JWKS에 기대는 서비스들이 함께 멈춘다. 오늘의집은 JWKS를 쿠버네티스 Secret으로 관리해 OAuth 서버와 ext-authz가 같은 Secret을 읽게 했고, Secret 주입은 External Secrets 컨트롤러로 비밀 저장소를 한 번 더 추상화해 특정 백엔드에 묶이지 않게 했다.

비밀 저장소가 내려가도 이미 만들어진 Secret 객체로 서비스가 돈다. 키 교체 때 무엇을 조심하는지는 [JWT 키 교체](/posts/jwt-key-rotation) 글에서 다룬다.

## 모든 서비스가 같은 모양으로 태어나게

플랫폼 백엔드 개발자 로버의 [서비스 구축과 배포 with Mortar(2021년 12월)](https://www.bucketplace.com/post/2021-12-17-msa-phase-1-%EC%84%9C%EB%B9%84%EC%8A%A4-%EA%B5%AC%EC%B6%95%EA%B3%BC-%EB%B0%B0%ED%8F%AC-with-mortar/)는 MSA 전환을 망설이게 하는 여섯 문제를 꼽았다. 서비스 라우팅과 인증, 프로젝트 생성과 배포 설정, 서비스 유지보수 비용, API 연동 비용, 호출 단계가 늘며 커지는 지연, 서비스 사이 로그 분석과 디버깅이다. 첫째는 앞의 게이트웨이와 인증 서비스가 2021년 초부터 풀었고, Mortar는 둘째부터 다섯째를 겨냥했다.

Mortar는 건설 현장에서 벽돌을 붙이는 모르타르에서 이름을 땄다. 처음에는 단계별 모범 사례와 도구 가이드만 주려 했지만, 각 도구가 작은 부분만 잘 풀어 주니 전체를 엮는 일을 서비스 개발자가 다 배워야 하는 문제가 남았다.

그래서 `mortar.yaml` 설정 파일 하나로 여러 도구를 조합해 init, prepare, build, deploy 단계를 자동화했다. 아래는 글에 실린 설정 예시의 주요 항목을 조각으로 나눈 것이다. 값은 예시 그대로다.

gRPC 자체의 장단점은 [gRPC](/posts/grpc) 글에 있다. 백엔드 편은 Mortar와 LINE이 만든 Armeria를 함께 써서 서비스 구축, 스텁 생성, 배포, 문서화, 테스트를 간편하게 했다고 덧붙였다.

DevOps 엔지니어 제제의 [DevOps(2022년 2월)](https://www.bucketplace.com/post/2022-02-03-%EC%98%A4%EB%8A%98%EC%9D%98%EC%A7%91-msa-phase-1-devops/) 편은 그 위의 운영을 다룬다. 쿠버네티스 위의 모든 애플리케이션과 인프라 도구를 ArgoCD로 GitOps 방식으로 관리하고, 개발자가 필요한 인프라를 스스로 정의해 PR로 DevOps 엔지니어와 협업한다.

오픈소스를 들이되 쓰는 인터페이스는 OpsMonster로 직접 만들어, 개발자가 권한 추가, 배포 내역 확인 같은 일을 스스로 하게 했다. 파이프라인은 GitHub Actions에서 돌고, 대부분의 커스텀 액션은 OpsMonster API를 부르기만 해서 서버가 바뀌면 파이프라인 정의를 고치지 않아도 새 기능이 들어간다. 글은 이 모든 것이 "한 번에 짠" 하고 적용된 것이 하나도 없었다고 썼다. GitOps의 일반은 [ArgoCD 기초](/posts/argocd-basics) 글에 있다.

## 응답을 똑같이 맞추는 층, Aggregator

백엔드 분리의 핵심 제약은 전략 글의 "최초 런칭 원칙"에 있다. 어떤 서비스든 처음 띄울 때는 기존 서버와 새 서버의 응답이 똑같아야 한다. 응답이 바뀌면 작업 범위가 커지고 QA가 오래 걸리기 때문이다. 모든 기능을 QA하기 어려우니, 응답이 같다는 것을 새 서버의 런칭 조건으로 삼았다. API를 정리하는 일은 최초 런칭 뒤로 미뤘다.

백엔드 편은 이를 위해 Martin Fowler가 정리한 Branch By Abstraction을 썼다. 레거시 시스템 앞에 추상화 층을 세우고, 그 뒤에서 마이크로서비스를 키워 레거시의 영역을 줄여 간다. 그 추상화 층이 Aggregator다.

여러 마이크로서비스의 응답을 조합해 기존과 100% 같은 결과를 만들고, 동시에 다른 팀 서비스와의 의존성을 끊는다. 예를 들어 집들이 같은 콘텐츠 화면이 커머스의 상품 정보를 보여 주거나, 상품 상세 화면이 사용자들의 스타일링샷을 보여 주는 경우다.

백엔드 편은 이 전략을 다섯 단계 그림으로 설명했다. 아래는 그 단계를 따라가며, 레거시가 맡는 몫이 어떻게 줄어드는지 본 것이다. 단계의 내용은 백엔드 편 그대로이고, 칸의 이름은 내가 붙였다.

레거시 쪽에서는 의존성을 강제로 끊었다. 직접 관리하지 않는 테이블은 DB 계정 권한으로 접근을 막았고, 그래서 못 가져오게 된 JSON 필드는 비우거나 ID만 응답하게 했다. 비어 버린 필드를 Aggregator가 다른 팀 API로 채워 원래 응답을 되살린다. 쓰지 않게 된 코드는 지웠고, 이번에도 코드 개선이나 버그 수정은 하지 않았다. 권한으로 막는 방법은 "다른 팀 테이블을 읽지 말자"는 합의를 사람의 기억 대신 DB가 지키게 만든다.

Aggregator는 버릴 것을 전제로 만들었다. 새 기능은 Aggregator를 쓰지 않게 설계하고, 개발하면서 `@Deprecated`를 붙이며, 비즈니스 로직과 코드를 최소화했다. 집계가 필요한 필드만 DTO에 선언하고 나머지는 공통 로직이 그대로 통과시킨다.

새 앱과 웹에는 화면별 BFF(Backend For Frontend)를 두고, BFF는 Aggregator를 거치지 않고 마이크로서비스와 직접 통신한다. 구버전 API를 분석해 보니 플랫폼별 분기문이 생각보다 많아, 플랫폼마다 최적의 응답을 따로 만드는 BFF가 낫다고 판단했다.

1년 차 백엔드 개발자 멀린의 [Aggregator 공통모듈(2022년 3월)](https://www.bucketplace.com/post/2022-02-22-%EC%98%A4%EB%8A%98%EC%9D%98%EC%A7%91-msa-phase-1-aggregator-%EA%B3%B5%ED%86%B5%EB%AA%A8%EB%93%88/)은 이 층을 만들기가 생각보다 어려웠던 이유를 적었다. 기존 API는 페이지 하나를 그리는 데 필요한 모든 데이터를 한 API가 내려주는 방식이라, 몇천 줄짜리 JSON 본문도 있었고 그 안 곳곳에 다른 팀 데이터가 섞여 있었다.

그래서 응답 JSON을 파싱하면서 의존성 있는 객체를 찾아 Resolver별로 모으고, 다른 팀 API에 비동기로 한꺼번에 요청해 채워 넣는 모듈을 만들었다. Spring WebFlux, Jackson, Kotlin 코루틴, Java Reflections를 썼고, Spring Cloud Gateway와 엮었다. 병렬로 요청해 응답 속도도 개선됐다고 백엔드 편은 덧붙였다.

  const out = [];
  function walk(a, b, path) {
    if (ignore.includes(path)) return;
    const isObj = (v) => v !== null && typeof v === "object";
    if (isObj(a) && isObj(b) && Array.isArray(a) === Array.isArray(b)) {

  }

  return out;

세 번째 테스트가 Aggregator가 막아야 할 전형적인 차이다. 레거시가 DB 권한을 잃어 비워 버린 필드를 Aggregator가 채우지 못하면 이렇게 잡힌다. 네 번째처럼 예외로 등록하는 순간 그 필드는 더 이상 검증되지 않으니, 예외 목록은 짧게 유지하고 이유를 함께 적어 두는 편이 안전하다.

Aggregator 편은 실제 전환 전 검증을 세 단계로 정리했다. 운영과 거의 같은 테스트 환경에서 nGrinder로 로드 테스트를 하며 레거시 서버와 Aggregator의 적절한 파드 비율을 찾았다. 운영 요청의 일부를 새 서비스에 똑같이 흘려 응답 비교 기능으로 정합성을 확인했다.

세 번째 단계에서는 A/B 테스트 플랫폼으로 요청을 새 서비스로 옮기며 에러를 확인하고 트래픽을 조금씩 늘려 100% 전환했다. 같은 시리즈의 [토스페이먼츠 글](/posts/rw-tosspayments-legacy-rewrite)에서 소개한 토스뱅크 코어뱅킹 전환이 이자 조회를 옛 서버와 새 서버에 동시에 보내 비교한 것과 같은 생각이다.

## Phase 1이 끝난 자리

백엔드 편은 3개월을 쓰고도 "이제 막 열차에 탑승하고 바퀴를 움직이기 시작한 정도"라고 썼다. 앞으로의 규칙도 정했다. 새 기능과 기존 기능의 개편은 모두 마이크로서비스에서 개발한다. 경계 맥락(Bounded Context)이 다르지만 같은 도메인이면 팀 구조에 따라 나눌지 정한다. 비즈니스 쪽에서는 조금 느려질 수 있지만 먼 미래를 보면 더 빠를 것이라고 봤다.

2022년 Tech OKR 대부분이 Phase 2이고, Rails의 Sidekiq과 Whenever를 Kotlin과 Spring으로 옮길 계획이었다. Rails가 나빠서가 아니라 여러 언어와 섞어 쓸 때 장점이 줄고, 한국 시장에서 시니어 Rails 개발자 채용이 너무 어렵다는 이유를 솔직하게 적었다.

전략 글은 완전한 전환까지 3~5년이 걸릴 것으로 내다봤고, 10배를 목표로 준비해도 서비스가 자라면 다시 설계해야 할 부분이 나올 수 있다고 했다. Aggregator 편은 약 4개월이라는 짧은 기간에 많지 않은 인원으로 전환에 성공했다고 정리했고, 모듈을 조금 바꿔 모바일 BFF 서버에 쓰고 오픈소스 공개도 논의 중이라고 했다.

## 다른 회사들의 선택과 나란히 놓으면

같은 시리즈의 [Shopify](/posts/rw-shopify-modular-monolith)는 Rails 모놀리스를 쪼개지 않고 모듈로 나누는 쪽을 골랐다. 오늘의집도 출발점은 Rails 모놀리스였지만 반대 방향을 골랐다. 연재가 든 이유를 겹쳐 보면 차이가 보인다.

오늘의집은 언어 자체를 Kotlin과 Spring으로 옮기려 했고(시니어 Rails 개발자 채용이 어렵다는 이유까지 적었다), 팀이 콘텐츠·커머스·O2O 도메인으로 이미 나뉘어 있었으며, 10배 트래픽을 받을 구조를 새로 짜려 했다. 같은 Rails 모놀리스라도 언어를 바꾸려는 회사에게 모듈화는 반쪽 답이었을 것이다.

[Segment](/posts/rw-segment-goodbye-microservices)는 마이크로서비스를 140여 개로 늘렸다가 다시 합쳤다. 오늘의집 백엔드 편의 "적은 수의 팀원이 다수의 서비스를 담당하게 되는 문제를 만들지 않는다, 서비스가 커지면 그때 다시 나눈다"는 원칙은 Segment가 겪은 문제를 미리 막으려는 규칙으로 읽힌다.

반면 [컬리 OMS팀](/posts/rw-kurly-fulfillment-systems)은 엔지니어 4명이 그보다 많은 서비스를 맡는 쪽을 골랐다. 같은 질문(사람 수와 서비스 수)에 회사마다 다른 답을 냈고, 각자 그 답이 통하는 조건을 함께 적었다는 점이 공통이다.

## 공개된 이야기에서 빠진 것

일곱 편 모두 진행 중인 프로젝트를 채용 공고와 함께 쓴 글이다. 숫자가 적다. 10배 목표의 기준이 되는 당시 트래픽, 서비스 몇 개로 나눴는지, 응답 비교에서 차이가 얼마나 나왔는지, 전환 뒤 지연이 어떻게 바뀌었는지는 없다. "병렬 요청으로 응답 속도가 개선됐다"는 문장에도 수치가 없다. 3개월 동안 제품 개발을 멈춘 비용, 사업 쪽 반응도 회사의 서술 말고는 확인할 길이 없다.

이후의 이야기는 더 비어 있다. 이 글을 쓰는 시점(2026년 10월) 오늘의집 블로그 목록에서 Phase 2를 같은 깊이로 다룬 후속 연재는 찾지 못했다. Linkerd 도입이 실제로 됐는지, Aggregator가 계획대로 사라졌는지, BFF가 몇 개가 됐는지, 3~5년 전망이 맞았는지 모두 공개되지 않았다.

그러니 이 글의 구조를 "지금의 오늘의집"으로 읽으면 안 된다. 2021년 말에서 2022년 초 사이 한 회사가 전환을 시작한 방식으로 읽어야 한다.

## 모놀리스를 나누기로 했다면

오늘의집 방식이 맞는 조건은 이렇다. 모놀리스가 여러 팀의 배포를 서로 묶고 있고, 팀 경계가 도메인 경계(콘텐츠, 커머스, O2O)와 대체로 맞고, 클라이언트를 강제 업데이트할 수 없어 기존 응답을 그대로 지켜야 한다.

이 셋이 겹칠 때 게이트웨이, 응답을 맞추는 집계 층, 비교 검증은 비용을 할 만한 장치다. 팀이 하나뿐이거나 배포가 서로를 막지 않는다면, 같은 비용으로 [모듈러 모놀리스](/posts/modular-monolith)처럼 한 배포 안에서 경계부터 긋는 편이 싸다.

처음부터 따라 하면 드는 비용도 크다. 제품 개발을 3개월 멈추는 결정은 사업이 그만큼을 견딜 수 있을 때만 가능하다. 플랫폼팀, 인증 계층, 배포 도구, 운영 도구를 먼저 만드는 데 1년 넘게 걸렸다(쿠버네티스 이관만 2020년 2월부터 11월까지). Aggregator는 버릴 코드라서, 버리는 날까지 유지하는 비용이 따로 든다.

작은 팀이 지금 가져올 수 있는 것은 이렇다.

- "옮기는 동안은 고치지 않는다"를 규칙으로 정한다. 동작을 바꾸지 않는 이동과 동작을 바꾸는 개선을 다른 PR, 다른 시기로 나누면 비교 검증이 깨끗해진다.
- 다른 팀 테이블 접근을 DB 권한으로 막아 본다. 무엇이 깨지는지가 곧 서비스 경계를 넘는 의존성 목록이다.
- 읽기 요청만이라도 그림자 트래픽으로 새 경로와 옛 경로를 비교한다. 쓰기는 두 번 실행되면 안 되니 처음부터 대상에서 뺀다.
- 집계 층을 만들 때는 처음부터 지울 날을 정해 둔다. 오늘의집처럼 새 기능은 그 층을 쓰지 않게 막고, 코드에 폐기 표시를 붙여 두면 임시 층이 영구 층으로 굳는 것을 늦출 수 있다.
- 서비스마다 이름, 소유 팀, 버전, 인터페이스 위치를 적은 설정 파일 하나를 둔다. 도구가 없어도 형식만 통일하면 나중에 자동화할 수 있다.

비슷한 신호가 보이면 무엇부터 볼까. 한 팀의 배포가 다른 팀 배포를 기다리게 하는 일이 잦다면, 어떤 코드와 어떤 테이블을 함께 건드리는지부터 적어 본다. 나눈 뒤 특정 화면에서만 데이터가 비어 보인다면 레거시가 권한을 잃은 필드를 집계 층이 채우지 못했는지 응답 비교 결과를 본다. 게이트웨이를 넣은 뒤 지연이 늘었다면 인증 질의가 요청마다 무엇을 하는지, 세션 해석을 위해 다른 서버를 부르고 있지는 않은지 확인한다.

## 면접에서 나올 만한 질문

### 오늘의집은 왜 일부 인원이 아니라 모든 개발자를 3개월 동안 MSA에 투입했나요?

일부만 맡기면 해 본 사람만 계속하게 되고, 서로 다른 도메인 지식이 없어 진행이 막힐 것이라고 봤기 때문이다. 장기 과업인 MSA를 모두가 실제로 겪어 봐야 이후 각 팀이 스스로 나눌 수 있다는 판단이었다. 그래서 2021년 9월부터 12월 초까지 제품 개발을 멈추고, 각 팀이 자기 도메인 하나씩을 분리하며 경험을 쌓게 했다.

### 서비스를 나누기 전에 무엇을 먼저 준비했나요?

배포 기반과 공통 플랫폼이다. 2020년 2월부터 11월까지 레거시를 쿠버네티스로 옮겼고, 플랫폼팀을 만들어 API 게이트웨이, 인증 서비스, gRPC 메타정보를 관리하는 Mortar, 운영 자동화 OpsMonster, 로그 SDK를 먼저 만들었다. 서비스를 나눌 때마다 배포, 인증, 통신 규약, 로그를 각 팀이 따로 고민하지 않게 하려는 순서다.

### 새 서비스의 최초 런칭 조건을 "응답이 같다"로 정한 이유는요?

응답이 바뀌면 작업 범위가 커지고 QA가 오래 걸리며, 모든 기능을 QA하기도 어렵기 때문이다. 같은 요청에 같은 응답이 나오면 클라이언트를 바꾸지 않고 서버만 바꿀 수 있다. 이를 위해 레거시 앞에 Aggregator를 두어 여러 마이크로서비스의 응답을 조합해 기존과 100% 같은 결과를 만들고, API 정리는 런칭 뒤로 미뤘다.

### 분리하는 동안 버그를 고치지 않기로 한 이유는요?

비교 검증이 작동하려면 동작이 바뀌지 않아야 하기 때문이다. 트래픽 쉐도잉에서 레거시와 새 서비스의 응답을 비교하는데, 분리하며 버그를 고치면 새 응답이 달라져 차이로 잡히고 고친 것인지 깨뜨린 것인지 가를 수 없다. 오늘의집은 이 규칙을 어기면 감당할 수 없는 알림을 받게 된다고 경고했다. 이동과 개선을 다른 시기에 하는 것이 원칙이다.

### 게이트웨이에서 Rails 세션을 어떻게 해석했고, 왜 그렇게 했나요?

Go로 만든 ext-authz 서버에서 Ruby Marshal 형식을 직접 읽되, UserId가 든 값 하나만 해석했다. Go에서 Ruby를 자식 프로세스로 실행하거나 Rails에 해석 API를 두고 매번 부르는 방법은 모든 요청 앞단에서 도는 인증 서버에 오버헤드가 너무 컸다. 대신 세션에서 다른 정보가 필요하면 추가 구현을 해야 한다는 제약을 받아들였다.

### 트래픽 쉐도잉에서 GET만 검증한 이유와 남는 위험은요?

쓰기 요청을 새 쪽에도 보내면 같은 쓰기가 두 번 실행되기 때문이다. GET은 복제해도 데이터가 바뀌지 않아 안전하게 비교할 수 있다. 대신 쓰기 경로는 이 방법으로 검증되지 않으니, 시나리오 자동화 QA와 A/B 플랫폼을 통한 점진 전환으로 따로 확인했다. 비교 예외로 등록한 필드도 더는 검증되지 않으므로 예외 목록을 짧게 유지해야 한다.

### Aggregator와 BFF는 무엇이 다르고, 왜 둘 다 뒀나요?

Aggregator는 구버전 API 응답을 그대로 유지하기 위한 임시 층이고, BFF는 새 앱과 웹에 화면별 최적의 응답을 주는 층이다. 구버전 앱은 강제 업데이트할 수 없으니 Aggregator가 옛 응답을 맞춰 주고, 새 기능은 Aggregator를 쓰지 않고 BFF가 마이크로서비스와 직접 통신한다. Aggregator 코드에는 처음부터 `@Deprecated`를 붙여 버릴 것을 전제로 했다.

### 우리 팀이 개발자 10명 남짓이라면 같은 방식으로 나눠야 할까요?

대부분은 아니다. 오늘의집은 콘텐츠, 커머스, O2O처럼 팀 경계가 도메인 경계와 맞고, 모놀리스가 여러 팀의 배포를 묶는 문제가 있었으며, 1년 넘는 플랫폼 준비와 3개월의 제품 개발 중단을 감당할 수 있었다. 팀이 하나뿐이면 모듈러 모놀리스로 경계부터 긋는 편이 싸다. 다만 이동과 개선을 나누는 규칙, DB 권한으로 의존성 드러내기, 읽기 요청 비교 검증은 규모와 상관없이 지금 쓸 수 있다.
