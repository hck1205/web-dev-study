  숙제를 낼 때 맞춤법 검사기를 먼저 돌리고, 친구에게 한 번 읽어 달라고 하고, 마지막에 선생님이 채점한다. 검사가 빠를수록 자주 할 수 있고, 꼼꼼할수록 시간이 오래 걸린다. 그래서 빠른 검사를 먼저 여러 번, 느린 검사는 꼭 필요할 때만 한다.

  인프라 코드도 같다. 띄어쓰기와 문법을 보는 검사는 몇 초면 끝난다. "이 값을 넣으면 이렇게 계산되나"를 보는 검사는 조금 더 걸리고, 실제로 서버를 만들어 보고 지우는 검사는 몇십 분과 돈이 든다.

  사람이 계획서 수백 줄을 매번 꼼꼼히 읽기는 어렵다. 그래서 "전 세계에 문을 열지 마라" 같은 규칙을 기계에게 맡기고, 사람은 기계가 판단할 수 없는 것만 본다. 규칙을 일부러 어겨야 할 때는 왜 어기는지 코드에 적어 두게 한다.
</EasyIntro>

리뷰어 두 명이 승인한 PR이 운영에 나갔다. 사흘 뒤 보안 팀에서 연락이 온다. 관리용 보안 그룹의 22번 포트가 `0.0.0.0/0`으로 열려 있다. PR을 다시 열어 보면 plan은 380줄이었고, 문제의 줄은 그 중간에 있었다.

```text
      + cidr_ipv4    = "0.0.0.0/0"
      + from_port    = 22
```

두 리뷰어는 태그 변경과 서브넷 이름 정리를 꼼꼼히 봤다. 사람이 못나서가 아니다. 사람은 긴 diff에서 맥락과 의도를 보는 데 강하고, 같은 규칙을 수백 줄에 기계적으로 대는 데 약하다. 그 일은 기계에게 맡겨야 한다.

이 글은 Terraform 코드를 기계가 검사하는 방법들을 싼 것부터 비싼 것까지 놓고, PR 파이프라인 어디에 무엇을 둘지 정한다. 형식과 문법(fmt, validate), 린트(TFLint), plan 단위 테스트(`terraform test`와 mock provider), 실제로 만들어 보는 통합·종단 테스트(Terratest), 모듈 계약, 오설정 스캐너(Checkov, Trivy 등), 정책(Sentinel, OPA), 비용(Infracost)까지 간다. 네트워크 리소스에 checkov와 conftest를 실제로 돌린 결과는 [네트워크를 Terraform으로](/posts/terraform-network-iac)에 있고, 저장한 plan을 apply하는 파이프라인 흐름과 권한 분리는 [네트워크 설정 CI/CD](/posts/network-config-cicd)에 있으니 여기서는 검사 자체에 집중한다.

실습은 Ubuntu 24.04에서 Terraform 1.16.6, TFLint 0.59.1로 했다. 출력은 직접 돌린 결과만 실었다. 스캐너와 정책 도구 중 이 환경에서 돌리지 못한 것(Sentinel, Infracost, Terratest)은 형식만 보이고 출력은 싣지 않았다.

층마다 잡는 것이 다르다. 형식과 문법 검사는 오타와 존재하지 않는 참조를, 린트는 문법은 맞지만 틀린 값(없는 인스턴스 타입)을, 스캐너와 정책은 "동작은 하지만 위험한" 설정을, plan 단위 테스트는 내가 짠 계산 로직(`for` 표현식, 조건식)을, 통합 테스트는 프로바이더와 클라우드가 실제로 받아 주는지를, 종단 테스트는 만들어진 것이 정말 동작하는지(HTTP 200이 오는지)를 본다. 위 층의 검사로 아래 층의 실수를 잡으면 비싸다. 30분짜리 통합 테스트가 끝나고서야 오타를 알게 되는 일이 없게, 아래 층을 먼저 통과해야 위 층이 돌게 한다.

## fmt와 validate

가장 싼 두 검사다. `terraform fmt`는 정해진 형식으로 코드를 고쳐 쓴다. CI에서는 고치지 않고 차이만 본다.

```bash
# 형식이 맞지 않는 파일과 차이를 출력하고, 차이가 있으면 0이 아닌 코드로 끝난다
terraform fmt -check -diff -recursive
echo "exit=$?"
```

```text
main.tf
--- old/main.tf
+++ new/main.tf
@@ -1,4 +1,4 @@
 resource "terraform_data" "x" {
-input="a"
-  triggers_replace = [ 1,2 ]
+  input            = "a"
+  triggers_replace = [1, 2]
 }
exit=3
```

종료 코드가 3이면 형식 차이가 있다는 뜻이다. 형식은 사람이 리뷰할 일이 아니니 기계가 막고, 개발자는 커밋 전에 `terraform fmt -recursive`로 고친다. pre-commit 훅에 넣어 두면 CI까지 가지도 않는다.

`terraform validate`는 코드가 문법적으로 맞고 내부적으로 일관된지 본다. 없는 변수나 리소스를 참조하는지, 인자 이름이 프로바이더 스키마에 있는지, 타입이 맞는지까지 본다. 클라우드에 접속하지는 않는다.

```bash
# 백엔드는 건드리지 않고 프로바이더만 받은 뒤 검사한다 (CI에서 자격 증명 없이 돌릴 수 있다)
terraform init -backend=false
terraform validate
```

```text
Error: Reference to undeclared input variable

  on bad.tf line 2, in resource "terraform_data" "y":
   2:   input = var.missing

An input variable with the name "missing" has not been declared. This
variable can be declared with a variable "missing" {} block.
```

validate가 못 보는 것도 분명하다. 값이 실제로 유효한지(`t3.smal` 같은 인스턴스 타입 오타, 없는 리전, 겹치는 CIDR)는 모른다. 스키마상 문자열이면 통과다. 그다음 층이 린트다.

## TFLint: 문법은 맞지만 틀린 코드

TFLint는 validate를 통과한 코드에서 "틀렸거나 나쁜 습관인" 것을 찾는다. 기본으로 들어 있는 Terraform 규칙 묶음은 버전 고정, 타입 없는 변수, 쓰지 않는 선언, 옛 문법 같은 것을 본다. 설정 파일에 규칙 묶음을 켠다.

```hcl
# .tflint.hcl
plugin "terraform" {
  enabled = true
  preset  = "recommended"
}
```

```bash
# 플러그인을 받고 현재 디렉터리를 검사한다
tflint --init
tflint
```

```text
5 issue(s) found:

Warning: terraform "required_version" attribute is required (terraform_required_version)

  on main.tf line 1:
   1: terraform {

Warning: Missing version constraint for provider "local" in `required_providers` (terraform_required_providers)

  on main.tf line 3:
   3:     local = { source = "hashicorp/local" }

Warning: `env` variable has no type (terraform_typed_variables)

  on main.tf line 7:
   7: variable "env" {}

Warning: [Fixable] variable "unused_region" is declared but not used (terraform_unused_declarations)

  on main.tf line 9:
   9: variable "unused_region" {

  on main.tf line 15:
  15:   content  = "${var.env}"
```

(규칙마다 붙는 `Reference:` 문서 링크 줄은 줄였다.) 종료 코드는 2였다. 이슈가 있으면 0이 아닌 코드로 끝나 CI를 실패시킨다. `[Fixable]`이 붙은 것은 `tflint --fix`로 고칠 수 있다.

TFLint의 진가는 클라우드별 규칙 묶음에서 나온다. AWS 규칙 묶음(`tflint-ruleset-aws`)을 켜면 존재하지 않는 인스턴스 타입(`aws_instance_invalid_type`), 없는 AMI 형식, 이전 세대 인스턴스 사용 같은 것을 plan 전에 잡는다. 이 규칙은 AWS가 받아들이는 값 목록을 플러그인 안에 담고 있어서 클라우드 접속 없이 돈다. 플러그인은 `.tflint.hcl`에 `source`와 `version`을 적고 `tflint --init`으로 받는다. 버전을 고정해야 규칙이 조용히 늘어 CI가 갑자기 깨지는 일이 없다.

## terraform test로 plan 단위 테스트

여기서부터는 "내 코드가 내가 의도한 대로 계산하나"를 본다. 1.6부터 Terraform에 내장된 `terraform test`는 `.tftest.hcl` 파일의 `run` 블록을 차례로 실행하고, 각 블록의 `assert`로 결과를 검사한다. 테스트할 모듈은 이렇게 생겼다. 환경과 허용 규칙 목록을 받아 이름과 규칙 키를 계산한다.

```hcl
# main.tf (모듈)
variable "env" {
  type = string
  validation {
    condition     = contains(["dev", "stg", "prod"], var.env)
    error_message = "env는 dev, stg, prod 중 하나여야 한다."
  }
}

variable "ingress" {
  type = list(object({
    port = number
    cidr = string
  }))
  default = []

  validation {
    condition     = alltrue([for r in var.ingress : r.cidr != "0.0.0.0/0" || r.port == 443])
    error_message = "0.0.0.0/0은 443번에만 열 수 있다."
  }
}

resource "random_pet" "suffix" {}

locals {
  name  = "app-${var.env}-${random_pet.suffix.id}"
  rules = { for r in var.ingress : "${r.port}-${r.cidr}" => r }
}

resource "local_file" "rules" {
  filename = "${path.module}/out/${var.env}-rules.txt"
  content  = join("\n", [for k, r in local.rules : "allow ${r.port} from ${r.cidr}"])
}

output "name" {
  value = local.name
}

output "rule_keys" {
  value = keys(local.rules)
}
```

처음 장면의 사고는 이 모듈에서는 변수 `validation`이 막는다. 그 검사가 정말 동작하는지, 규칙 키가 의도대로 계산되는지를 테스트로 적는다.

```hcl
# tests/unit.tftest.hcl
mock_provider "random" {
  mock_resource "random_pet" {
    defaults = {
      id = "fixed-pet"
    }
  }
}

variables {
  env = "dev"
  ingress = [
    { port = 443, cidr = "0.0.0.0/0" },
    { port = 22, cidr = "10.0.0.0/8" },
  ]
}

run "name_has_env" {
  command = plan

  assert {
    condition     = output.rule_keys == ["22-10.0.0.0/8", "443-0.0.0.0/0"]
    error_message = "규칙 키가 예상과 다르다: ${jsonencode(output.rule_keys)}"
  }
}

run "name_uses_suffix" {
  command = apply

  assert {
    condition     = output.name == "app-dev-fixed-pet"
    error_message = "이름이 예상과 다르다: ${output.name}"
  }
}

run "rejects_open_ssh" {
  command = plan

  variables {
    ingress = [{ port = 22, cidr = "0.0.0.0/0" }]
  }

  expect_failures = [var.ingress]
}

run "rejects_unknown_env" {
  command = plan

  variables {
    env = "qa"
  }

  expect_failures = [var.env]
}
```

```bash
# tests/ 디렉터리의 .tftest.hcl을 모두 실행한다
terraform test
```

```text
tests/unit.tftest.hcl... in progress
  run "name_has_env"... pass
  run "name_uses_suffix"... pass
  run "rejects_open_ssh"... pass
  run "rejects_unknown_env"... pass
tests/unit.tftest.hcl... tearing down
tests/unit.tftest.hcl... pass

Success! 4 passed, 0 failed.
```

몇 가지를 짚자. `command = plan`인 run은 아무것도 만들지 않고 plan 결과로 검사한다. 가장 싸서 대부분의 테스트를 이렇게 쓴다. 맵의 키는 사전순으로 나오므로 `"22-..."`가 `"443-..."`보다 앞이다. `expect_failures`는 "이 검사가 실패해야 통과"를 뜻해서, 막아야 할 입력이 정말 막히는지 확인하는 데 쓴다. 보안 규칙을 변수 검증으로 넣었다면 이 테스트가 그 규칙의 회귀 테스트가 된다.

누군가 검증 조건을 `true`로 풀어 버리면 이렇게 깨진다.

```text
  run "rejects_open_ssh"... fail

Error: Missing expected failure

  on tests/unit.tftest.hcl line 42, in run "rejects_open_ssh":
  42:   expect_failures = [var.ingress]

The checkable object, var.ingress, was expected to report an error but did
not.
  run "rejects_unknown_env"... skip
tests/unit.tftest.hcl... tearing down
tests/unit.tftest.hcl... fail

Failure! 2 passed, 1 failed, 1 skipped.
```

이 실습에서는 실패한 run 뒤의 run이 `skip`으로 표시됐다. 한 파일 안의 run은 앞 run의 state를 이어받으며 순서대로 돌기 때문에, 서로 독립적인 검사는 파일을 나눠 두면 하나가 깨져도 나머지 결과를 볼 수 있다.

## mock provider로 클라우드 없이

위 테스트의 `mock_provider`(1.7 이상)는 진짜 `random` 프로바이더 대신 가짜를 쓰게 한다. 가짜 프로바이더는 API를 부르지 않고, 계산된 속성(`id` 같은 것)에 내가 준 값이나 임의의 값을 채운다. 그래서 두 번째 run은 `command = apply`인데도 이름이 늘 `app-dev-fixed-pet`으로 고정되어 정확히 비교할 수 있었다.

AWS 프로바이더를 mock하면 자격 증명 없이, 몇 초 안에, 비용 없이 모듈의 계산 로직을 검사할 수 있다. data source도 `mock_data`로 돌려줄 값을 정한다.

```hcl
mock_provider "aws" {
  mock_data "aws_availability_zones" {
    defaults = {
      names = ["ap-northeast-2a", "ap-northeast-2c"]
    }
  }
}

run "two_subnets_per_az" {
  command = plan

  assert {
    condition     = length(aws_subnet.private) == 2
    error_message = "AZ마다 private 서브넷이 하나씩 있어야 한다."
  }
}
```

특정 리소스나 모듈 호출 하나만 값을 바꾸고 싶으면 run 블록 안에서 `override_resource`, `override_data`, `override_module`을 쓴다.

mock의 한계는 이름 그대로다. 가짜는 클라우드의 규칙을 모른다. 서브넷 CIDR이 VPC 범위를 벗어나도, IAM 정책 문법이 틀려도, 리전에 없는 인스턴스 타입이어도 mock은 성공을 돌려준다. mock 테스트는 "내 표현식이 의도한 값을 만드나"를 보는 것이지 "AWS가 이걸 받아 주나"를 보는 것이 아니다. 후자는 다음 층의 일이다.

## apply까지 하는 통합 테스트와 Terratest

mock 없이 `command = apply`인 run을 돌리면 `terraform test`가 진짜 리소스를 만들고, 파일의 모든 run이 끝나면 만든 것을 지운다. 위 출력의 `tearing down`이 그 단계다. 실습에서는 `local_file`이 만든 파일이 테스트가 끝난 뒤 사라져 있었다. 클라우드에서는 실제 VPC와 인스턴스가 생겼다 지워진다는 뜻이다.

이 층이 잡는 것은 프로바이더와 클라우드의 실제 반응이다. 권한이 모자라 생기는 `AccessDenied`, 리전에 없는 기능, 리소스 사이의 실제 제약(같은 VPC 안에서 겹치는 CIDR) 같은 것이다. 대신 몇 분에서 몇십 분이 걸리고 돈이 든다. 그리고 실패해서 정리 단계가 끝까지 돌지 못하면 리소스가 남는다. `terraform test`는 정리하지 못한 리소스를 출력에 알려 주지만, 그것을 지우는 것은 사람 몫이다.

Terratest는 Go로 쓰는 테스트 라이브러리다. Terraform을 apply한 뒤 그 결과로 실제 동작(HTTP 요청, SSH 접속, 쿠버네티스 API 조회)까지 검사하는 종단 테스트에 쓴다.

```go
// test/web_test.go
func TestWebModule(t *testing.T) {
	opts := &terraform.Options{
		TerraformDir: "../examples/web",
		Vars:         map[string]interface{}{"env": "test"},
	}
	// 테스트가 끝나면 성공이든 실패든 지운다
	defer terraform.Destroy(t, opts)

	terraform.InitAndApply(t, opts)

	url := terraform.Output(t, opts, "url")
	// 서버가 뜰 때까지 최대 30번, 10초 간격으로 확인한다
	http_helper.HttpGetWithRetry(t, url, nil, 200, "ok", 30, 10*time.Second)
}
```

`terraform test`의 apply run과 Terratest의 차이는 검사할 수 있는 범위다. `terraform test`는 Terraform이 아는 값(출력, 리소스 속성)만 assert할 수 있다. "로드 밸런서 주소로 요청하면 200이 오나"는 Terraform 밖의 일이라 Terratest 같은 도구가 필요하다. 대신 Go 코드를 유지해야 하고 팀이 Go에 익숙해야 한다.

언제 돌릴까. 이 층의 테스트를 모든 PR에 돌리면 리뷰가 느려지고 비용이 쌓인다. 흔한 배치는 이렇다.

- 모듈 저장소: 모듈의 새 버전을 태그하기 전에 통합 테스트를 돌린다. 모듈 사용자가 그 버전을 믿고 올리게 하려는 것이다.
- 야간: 주요 모듈의 종단 테스트를 매일 밤 돌려 프로바이더 업그레이드나 클라우드 쪽 변화로 깨진 것을 아침에 안다.
- 전용 계정: 테스트는 운영과 분리된 계정에서 돌리고, 남은 리소스를 정기적으로 쓸어 내는 도구(태그 기준 삭제)를 둔다. 테스트 리소스에는 `CreatedBy=terratest` 같은 태그를 붙인다.

## 모듈의 입출력 계약

모듈은 여러 루트가 가져다 쓰는 함수 같은 것이라, 입력과 출력의 모양이 곧 계약이다. 계약 테스트는 "이 입력을 주면 이런 출력이 나온다"와 "이런 입력은 거절한다"를 고정해 두는 것이다. 위의 `terraform test` 예제가 바로 그 모양이다. `rule_keys`의 형식을 assert하고, 잘못된 `env`와 규칙을 `expect_failures`로 고정했다.

계약을 지키는 장치는 세 군데에 나눠 둔다.

- 입력: 변수의 `type`과 `validation`. 모듈이 받을 수 없는 값은 plan 전에 거른다. 타입을 정확히 적는 법과 `optional`의 함정은 [HCL 문법과 data source](/posts/terraform-hcl-expressions-data-sources)에 있다.
- 안쪽: `precondition`과 `postcondition`. 여러 값을 함께 봐야 하는 조건(운영이면 다중 AZ여야 한다)을 리소스에 건다([의존성 그래프와 lifecycle](/posts/terraform-dependency-graph-lifecycle)).
- 출력: 출력 이름과 타입은 사용자 코드가 참조한다. 출력 이름을 바꾸거나 리스트를 맵으로 바꾸는 것은 깨는 변경이다. 테스트로 출력 형태를 고정해 두면 실수로 바꿨을 때 바로 안다.

모듈을 레지스트리나 git 태그로 배포한다면 이 계약을 버전 번호에 반영한다. 입력 추가(기본값 있음)는 MINOR, 출력 이름 변경이나 필수 입력 추가는 MAJOR다. 사용하는 쪽은 `version = "~> 3.2"`처럼 범위를 고정한다([모듈과 tfvars](/posts/terraform-modules-tfvars)).

## 오설정 스캐너

테스트는 내가 의도한 것을 검사한다. 스캐너는 내가 미처 의도하지 못한 위험을 찾는다. 공개된 S3 버킷, 암호화되지 않은 볼륨, 전 세계에 열린 22번 포트, 로그가 꺼진 로드 밸런서 같은 것이다. 수백 개의 규칙이 이미 들어 있어서 팀이 규칙을 쓰지 않아도 처음부터 쓸 만하다.

- Checkov(Prisma Cloud): 파이썬 도구. Terraform 코드와 plan JSON을 모두 읽고, 쿠버네티스 매니페스트·Dockerfile 등 다른 형식도 본다. 규칙 ID는 `CKV_AWS_24` 같은 모양이다.
- Trivy(Aqua): 컨테이너 이미지 스캐너로 유명하지만 `trivy config`로 IaC 오설정도 본다. 예전의 tfsec이 Trivy로 합쳐졌고, tfsec 저장소도 Trivy로 옮기라고 안내한다.
- Terrascan(Tenable), KICS(Checkmarx): 같은 부류의 도구다. 규칙을 Rego(OPA)나 쿼리로 쓴다.

```bash
# 코드를 정적 검사한다
checkov -d . --framework terraform --compact --quiet
trivy config .

# plan을 JSON으로 뽑아 검사한다 (모듈 안까지 값이 계산된 상태로 본다)
terraform plan -out=tfplan
terraform show -json tfplan > tfplan.json
checkov -f tfplan.json --framework terraform_plan
```

코드 스캔과 plan 스캔은 보는 것이 다르다. 코드 스캔은 빠르고 자격 증명이 필요 없지만, 변수와 모듈을 거쳐 계산되는 값은 정확히 모른다. `cidr_ipv4 = var.cidr`이면 그 변수에 무엇이 들어올지 모른다. plan 스캔은 값이 다 계산된 결과를 보니 정확하지만, plan을 만들려면 자격 증명과 시간이 든다. 둘 다 두되 PR에서는 plan 스캔을 필수로 둔다.

도구마다 아는 리소스 타입이 다르다는 것도 실제로 겪는다. [네트워크를 Terraform으로](/posts/terraform-network-iac)의 실습에서는 같은 코드에 tfsec과 checkov를 돌렸더니, tfsec은 새 보안 그룹 규칙 리소스 타입을 보지 않아 전 세계에 열린 22번을 놓쳤고 checkov는 잡았다. 스캐너 하나를 고를 때는 우리가 쓰는 리소스 타입에 규칙이 있는지 직접 확인한다. 위험한 설정 하나를 일부러 넣은 테스트 픽스처를 두고 스캐너가 잡는지 보는 것이 가장 확실하다.

## 예외를 코드에 남기는 법

스캐너를 처음 켜면 기존 코드에서 수십 개가 걸린다. 그중에는 진짜 문제도 있고, 일부러 그렇게 한 것도 있다(공개 웹사이트용 버킷, 443을 전 세계에 여는 로드 밸런서). 일부러 한 것을 CI에서 매번 무시하라고 할 수는 없으니 예외를 코드에 적는다.

```hcl
resource "aws_vpc_security_group_ingress_rule" "alb_https" {
  # 형식: #checkov:skip=규칙ID:이유. 규칙ID 자리에 걸린 규칙(CKV_AWS_...)을 그대로 적는다
  #checkov:skip=규칙ID:공개 ALB는 443을 인터넷에 연다. 2026-10 보안팀 승인 SEC-142
  security_group_id = aws_security_group.alb.id
  cidr_ipv4         = "0.0.0.0/0"
  from_port         = 443
  to_port           = 443
  ip_protocol       = "tcp"
}
```

Trivy는 리소스 위에 `#trivy:ignore:규칙ID` 주석을 쓰고, 도구에 따라 만료일을 붙이는 문법도 있다. 주석 문법은 도구와 버전마다 다르니 쓰는 버전의 문서를 확인한다. 어느 도구든 지킬 것은 같다.

- 규칙 ID를 정확히 적는다. 파일 전체나 디렉터리 단위로 끄지 않는다.
- 이유와 승인 근거(티켓 번호)를 같은 줄에 적는다. 이유 없는 skip은 리뷰에서 반려한다.
- 예외 주석이 추가된 PR은 보안 담당자 리뷰를 필수로 거치게 한다(CODEOWNERS로 그 디렉터리나 패턴을 지정).
- 기존 위반이 너무 많으면 처음에는 "새로 생긴 위반만 실패" 모드(기준선 파일)로 켜고, 기존 것은 별도로 줄여 나간다. 전부 고칠 때까지 스캐너를 꺼 두는 것보다 낫다.

## 정책을 코드로: Sentinel과 OPA

스캐너의 규칙은 업계 공통 모범 사례다. 회사마다 따로 정한 규칙도 있다. "운영 계정에서는 `t3.2xlarge` 이상을 쓰려면 승인", "모든 리소스에 `Owner` 태그", "데이터 계층 리소스는 삭제 금지" 같은 것이다. 이런 규칙은 정책 엔진에 직접 쓴다.

Sentinel은 HashiCorp의 정책 언어로, HCP Terraform과 Terraform Enterprise 안에서 plan과 apply 사이에 돈다. 정책마다 강제 수준을 정한다. `advisory`는 경고만, `soft-mandatory`는 실패하지만 권한 있는 사람이 이유를 남기고 넘길 수 있고, `hard-mandatory`는 아무도 넘길 수 없다. 오픈소스 Terraform CLI에서는 쓸 수 없다.

OPA(Open Policy Agent)는 어디서나 쓰는 범용 정책 엔진이다. Terraform에서는 plan JSON을 입력으로 Rego 규칙을 돌리는 conftest가 흔하고, HCP Terraform도 Sentinel과 함께 OPA 정책을 지원한다. 실제 Rego 정책과 출력은 [네트워크를 Terraform으로](/posts/terraform-network-iac)에 있다. 쿠버네티스에서 같은 OPA를 어드미션 단계에 쓰는 Gatekeeper와 개념이 같아서, 한 팀이 두 곳의 정책을 같은 언어로 관리할 수 있다.

어느 쪽이든 정책은 plan을 본다는 점이 중요하다. "이 변경이 무엇을 지우나", "몇 개를 교체하나"는 코드만 봐서는 알 수 없다. `resource_changes[].change.actions`에 `delete`가 든 리소스를 찾는 규칙 하나가 [prevent_destroy](/posts/terraform-dependency-graph-lifecycle)의 구멍(블록째 지우면 보호도 사라진다)을 메운다.

## 비용도 PR에서 본다: Infracost

`t3.medium`을 `m6i.4xlarge`로 바꾼 한 줄은 plan에서 조용히 지나가지만 청구서에서는 크게 보인다. Infracost는 plan이나 코드를 읽어 리소스마다 월 비용을 계산하고, 바뀌기 전과 후의 차이를 PR 댓글로 남긴다.

```bash
# 기준 브랜치의 비용을 계산해 저장하고
infracost breakdown --path . --format json --out-file infracost-base.json
# 현재 브랜치와 비교한다
infracost diff --path . --compare-to infracost-base.json
```

가격 정보를 Infracost의 가격 API에서 받아 오므로 API 키가 필요하다(코드나 state를 보내는 것이 아니라 리소스 종류와 크기 같은 가격 조회용 정보만 보낸다고 설명한다). 트래픽이나 요청 수에 비례하는 비용(데이터 전송, 람다 호출)은 사용량 파일에 예상치를 적어야 계산된다. 그래서 정확한 청구서 예측이라기보다 "이 PR이 고정비를 얼마나 바꾸나"를 보는 도구로 쓴다. 월 증가분이 기준(예: 500달러)을 넘으면 정책으로 승인을 요구하게 연결할 수 있다. 비용 자체를 줄이는 법은 [클라우드 비용 줄이기](/posts/cloud-cost-optimization)에 있다.

## PR 파이프라인에 어디 둘까

통합 테스트와 종단 테스트는 이 흐름에 넣지 않는다. 모듈 릴리스와 야간 작업으로 분리한다. 그리고 필수 검사(required status check)로 묶는 것은 정적 검사, plan 생성, 정책까지다. 비용과 스캐너 경고는 처음에는 댓글로만 두고, 팀이 익숙해지면 기준을 넘는 경우만 실패로 바꾼다. 처음부터 모든 것을 실패로 걸면 팀이 검사를 끄는 쪽으로 간다.

## 현장에서 검사가 무력해지는 순간

- 스캐너가 통과했는데 사고가 났다: 그 리소스 타입에 규칙이 없었다. 위험한 픽스처로 스캐너가 실제로 잡는지 시험해 둔다.
- 테스트는 다 통과하는데 apply가 실패한다: mock 테스트만 있다. mock은 클라우드 규칙을 모른다. 모듈 릴리스 전에 apply 테스트를 한 번은 돌린다.
- 테스트 계정 비용이 계속 오른다: 실패한 통합 테스트가 정리를 못 했다. 태그로 남은 리소스를 쓸어 내는 작업을 정기적으로 돌린다.
- 예외 주석이 수십 개다: 이유 없는 skip이 쌓였다. 이유와 티켓이 없는 skip은 CI에서 실패시키고, 예외 추가는 보안 리뷰를 필수로 한다.
- PR마다 검사가 20분이다: plan을 검사마다 따로 만들고 있거나, 통합 테스트가 PR에 들어 있다. plan은 한 번, 무거운 테스트는 릴리스와 야간으로 옮긴다.

## 사람은 의도를, 기계는 규칙을

인프라 코드의 검사는 싼 것부터 쌓는다. fmt와 validate와 TFLint가 오타와 틀린 값을, 스캐너와 정책이 위험한 설정과 회사 규칙을, mock을 쓴 `terraform test`가 내 계산 로직을, apply 테스트와 Terratest가 클라우드의 실제 반응을 본다. plan은 한 번 만들어 모든 검사가 함께 읽고, 예외는 이유와 함께 코드에 남긴다. 그래야 리뷰어가 380줄 plan의 한가운데에서 `0.0.0.0/0`을 찾는 대신, 이 변경이 왜 필요한지를 볼 수 있다.

## 면접에서 나올 만한 질문

### Terraform 코드는 어떤 단계로 검사하나요?

싼 것부터 쌓는다. fmt와 validate로 형식과 문법을, TFLint로 문법은 맞지만 틀린 값을, 스캐너와 정책으로 위험한 설정과 회사 규칙을, `terraform test`로 계산 로직을 본다. 실제로 만들어 보는 통합·종단 테스트는 느리고 비싸서 모듈 릴리스나 야간에 돌린다. 앞 단계가 실패하면 뒤는 돌지 않게 한다.

### terraform validate와 TFLint는 무엇이 다른가요?

validate는 문법과 내부 일관성(없는 참조, 스키마에 없는 인자, 타입)만 보고 값이 실제로 유효한지는 모른다. TFLint는 그 위에서 쓰지 않는 선언, 버전 미고정 같은 나쁜 습관과, 클라우드별 규칙 묶음으로 없는 인스턴스 타입 같은 틀린 값을 잡는다. 둘 다 클라우드에 접속하지 않아 빠르다.

### terraform test에서 command = plan과 apply는 언제 쓰나요?

plan은 아무것도 만들지 않고 계산 결과를 검사해서 빠르고 싸다. 표현식과 조건식, 변수 검증이 의도대로 동작하는지는 plan으로 충분하다. apply는 실제로 리소스를 만들고 파일 끝에서 지우므로, 프로바이더와 클라우드가 정말 받아 주는지 볼 때 쓴다. 정리에 실패하면 리소스가 남으니 전용 계정에서 돌린다.

### mock provider로 테스트하면 무엇을 알 수 있고 무엇을 모르나요?

자격 증명과 비용 없이 모듈의 계산 로직과 입력 검증을 확인할 수 있다. 계산된 속성을 고정해 정확히 비교할 수도 있다. 하지만 가짜는 클라우드의 규칙을 모르니 잘못된 CIDR, 틀린 IAM 정책, 리전에 없는 기능도 성공으로 돌려준다. 그건 apply 테스트의 몫이다.

### apply까지 하는 테스트는 언제 돌리나요?

모든 PR에는 돌리지 않는다. 모듈의 새 버전을 태그하기 전과, 프로바이더 변화로 깨진 것을 잡는 야간 작업에 둔다. 운영과 분리된 계정에서 돌리고, 테스트 리소스에 태그를 붙여 정리에 실패한 것을 주기적으로 지운다. HTTP 응답 같은 Terraform 밖의 동작까지 보려면 Terratest를 쓴다.

### 오설정 스캐너는 코드를 볼 때와 plan을 볼 때 무엇이 다른가요?

코드 스캔은 빠르고 자격 증명이 필요 없지만 변수와 모듈을 거쳐 계산되는 값은 정확히 모른다. plan 스캔은 값이 다 계산된 결과를 봐서 정확하고, 삭제나 교체 같은 변경 자체도 볼 수 있다. 그래서 둘 다 두되 PR에서는 plan 스캔을 필수로 둔다. 도구마다 아는 리소스 타입이 다르니 우리가 쓰는 타입을 잡는지 직접 시험한다.

### 스캐너 예외는 어떻게 관리하나요?

리소스 단위로 규칙 ID를 정확히 적고, 같은 줄에 이유와 승인 티켓을 남긴다. 파일이나 디렉터리 단위로 끄지 않는다. 예외가 추가된 PR은 CODEOWNERS로 보안 리뷰를 필수로 하고, 기존 위반이 많으면 기준선을 두어 새 위반만 실패로 시작한다.

### Sentinel과 OPA는 어떻게 고르나요?

Sentinel은 HCP Terraform과 Enterprise 안에서 plan과 apply 사이에 돌고, advisory·soft-mandatory·hard-mandatory로 강제 수준을 정할 수 있다. 오픈소스 CLI만 쓴다면 conftest로 plan JSON에 OPA 정책을 돌린다. OPA는 쿠버네티스 어드미션 같은 다른 곳에서도 같은 언어를 쓸 수 있어, 정책을 한 언어로 모으려는 팀에 맞는다.
