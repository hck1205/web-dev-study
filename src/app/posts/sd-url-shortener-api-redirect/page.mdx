<EasyIntro>
  할인 쿠폰 주소를 문자로 보내려니 80글자 가까이 되어 문자 한 통이 거의 다 찬다. 이 긴 주소를 몇 글자짜리 짧은 주소로 바꿔 주는 서비스가 URL 단축기다.

  단축기가 하는 일은 둘뿐이다. 긴 주소를 받아 짧은 이름표를 만들어 주고, 누가 짧은 주소로 오면 "저쪽으로 가세요"라는 안내문을 돌려준다. 안내문에는 "영원히 이사 갔다"와 "지금은 저쪽에 있다" 두 종류가 있다. 앞의 것을 받은 브라우저는 안내문을 기억해 두고 다음부터 묻지 않고 바로 가서 서버는 편하지만, 그 뒤의 클릭을 셀 수도 없고 나쁜 링크를 막을 수도 없다.

  링크를 누르는 일은 만드는 일보다 20배 많아서, 설계의 힘은 짧은 이름표로 긴 주소를 빨리 찾는 쪽에 쓴다. 그리고 단축 링크는 목적지를 숨기니 피싱에 악용되지 않도록 만들 때 주소를 검사하고 한 사람이 만드는 개수를 제한한다.
</EasyIntro>

이 시리즈에서 이 글의 자리: [⑰ 고유 ID 생성기](/posts/sd-unique-id-generator)에서 여러 서버가 겹치지 않는 번호를 만드는 법을 봤고, 이 글부터 두 편은 그 번호를 쓰는 URL 단축기를 설계한다. 이 글은 겉모양, 즉 API와 리다이렉트와 테이블을 정한다. 같은 장의 다음 글 [⑲ URL 단축기 ②: 단축 키 만들기와 인기 링크 캐시](/posts/sd-url-shortener-key-generation)가 짧은 키를 실제로 만드는 법을 다루고, 그다음은 [⑳ 웹 크롤러 구조](/posts/sd-web-crawler-architecture)다.

가을 할인 쿠폰 링크를 문자로 보내려고 주소를 붙여 넣었다. `https://shop.example.com/items/8812?utm_source=sms&utm_campaign=fall-sale`, 80글자에 가깝다. 단문 문자(SMS)는 90바이트까지라 영문 한 글자가 1바이트여도 링크 하나로 거의 다 찬다. 인사말을 붙이면 장문 문자로 넘어가 요금이 오른다. 이 주소를 `https://s.example/ww8`처럼 줄여 주는 서비스가 URL 단축기다.

면접에서도 "URL 단축기를 설계하라"는 아주 자주 나온다. 기능은 두 개뿐인데, 하루 수억 번 눌리는 링크를 빠르게 보내는 일, 링크가 영원히 살아 있어야 하는 일, 그리고 남이 악용하지 못하게 막는 일까지 따라온다. 이 글은 서버 한 대, 표 하나로 시작해서 무엇이 먼저 깨지는지 따라간다.

## 서버 한 대와 표 하나로 시작하기

URL 단축기가 하는 일은 둘이다. 긴 주소를 받아 짧은 키를 만들어 주는 단축, 그리고 짧은 주소로 들어온 사람을 긴 주소로 보내는 리다이렉트다. 키와 긴 주소를 짝지은 표 하나면 둘 다 된다.

가장 작은 버전을 Node 22로 만들었다. 표는 메모리의 `Map`이고, 키는 번호를 62진수 글자로 바꾼 것이다. 62진수 변환은 다음 글에서 자세히 보니 지금은 "번호를 짧은 글자로 바꾼다"고만 알면 된다.

```js
// api.js 일부: 서버 한 대, 표 하나(Map)로 만든 가장 작은 URL 단축기
const byKey = new Map(), byUrl = new Map();
let nextId = 125000;                                   // 실제로는 고유 ID 생성기가 준다

// POST /api/v1/links  { "longUrl": "..." }
let longUrl;
try { longUrl = new URL(JSON.parse(raw).longUrl); } catch { return json(res, 400, { error: "longUrl must be an absolute URL" }); }
if (!["http:", "https:"].includes(longUrl.protocol)) return json(res, 400, { error: "only http and https" });
const existing = byUrl.get(longUrl.href);
if (existing) return json(res, 200, { key: existing, shortUrl: `http://127.0.0.1:8088/${existing}` });
const key = toBase62(nextId++);
byKey.set(key, longUrl.href); byUrl.set(longUrl.href, key);
res.setHeader("Location", `/api/v1/links/${key}`);
return json(res, 201, { key, shortUrl: `http://127.0.0.1:8088/${key}` });

// GET /{key}
const target = byKey.get(req.url.slice(1));
if (!target) return json(res, 404, { error: "no such link" });
res.writeHead(302, { Location: target, "Cache-Control": "private, max-age=0" });
```

쿠폰 주소를 줄여 달라고 보냈다.

```bash
# 긴 주소를 보내 단축 키를 받는다
curl -si -X POST http://127.0.0.1:8088/api/v1/links \
  -H 'Content-Type: application/json' \
  -d '{"longUrl":"https://shop.example.com/items/8812?utm_source=sms&utm_campaign=fall-sale"}'
```

`javascript:alert(1)`처럼 http나 https가 아닌 주소는 거절했다. 단축 링크를 누른 사람의 브라우저에서 스크립트가 실행될 수 있기 때문이다. `shop.example.com`처럼 스킴이 빠진 값도 절대 주소가 아니라서 거절했다. 이제 짧은 주소를 열어 보자.

curl -si http://127.0.0.1:8088/nope

리다이렉트는 `GET /{key}` 하나다. API 경로와 짧은 주소의 경로가 섞이지 않게 단축 주소는 별도 도메인(`s.example`)으로 두는 경우가 많다. 그래야 `api`라는 키를 누가 만들어도 API와 부딪히지 않고, 짧은 주소 도메인 자체도 짧아진다. 만든 사람이 자기 링크를 보고 지우는 `GET /api/v1/links/{key}`, `DELETE /api/v1/links/{key}`도 있으면 좋다.

같은 긴 주소를 두 번 줄이면 같은 키를 줄까, 새 키를 줄까. 위 서버는 같은 키를 줬다. 저장 공간이 줄고 같은 주소의 클릭 수가 한곳에 모인다. 반대로 사람마다, 또는 캠페인마다 클릭 수를 따로 보고 싶으면 매번 새 키를 줘야 한다. 그때는 "만든 사람 + 긴 주소" 단위로 중복을 확인한다. 어느 쪽이든 API를 정할 때 함께 정해 둔다.

## 301을 줄까, 302를 줄까

리다이렉트 상태 코드는 여럿인데 단축기에서 고민하는 건 둘이다. 301 Moved Permanently는 "영구히 옮겼다", 302 Found는 "지금은 저쪽에 있다"는 뜻이다. 겉보기 동작은 같다. 차이는 브라우저가 이 응답을 기억하느냐다. 상태 코드 전체의 의미와 307·308과의 차이는 [HTTP 상태 코드](/posts/http-status-codes)에 정리되어 있다.

말로만 들으면 감이 안 와서 실제 브라우저로 재 봤다. 키 다섯 개를 상태 코드와 `Cache-Control` 헤더만 다르게 만들고, 서버가 요청을 받을 때마다 경로별로 세게 했다.

```js
// short-server.js 일부: 단축 키 다섯 개를 상태 코드만 다르게 보낸다
const links = {
  "/aB3x": { status: 301, headers: {} },
  "/Qz9k": { status: 302, headers: {} },
  "/Tm7p": { status: 301, headers: { "Cache-Control": "max-age=60" } },
  "/Nx2w": { status: 301, headers: { "Cache-Control": "no-store" } },
  "/Pk5r": { status: 302, headers: { "Cache-Control": "max-age=60" } },
};
```

```js
// browser.cjs: 진짜 브라우저(Chromium)로 같은 단축 URL을 세 번씩 연다
const page = await (await browser.newContext()).newPage();
for (const key of ["aB3x", "Qz9k", "Tm7p", "Nx2w", "Pk5r"]) {
  for (let i = 1; i <= 3; i++) {
    await page.goto(`http://127.0.0.1:8087/${key}`);
    await page.goto("about:blank");
  }
}
```

```text
server saw: {"/aB3x":1,"/landing":15,"/favicon.ico":14,"/Qz9k":3,"/Tm7p":1,"/Nx2w":3,"/Pk5r":1,"/hits":1}
```

Playwright로 띄운 Chromium 141에서 각 키를 세 번씩 열었다. 헤더 없는 301(`aB3x`)은 서버가 한 번만 봤다. 두 번째부터는 브라우저가 기억해 둔 답으로 서버에 묻지 않고 바로 긴 주소로 갔다. 헤더 없는 302(`Qz9k`)는 세 번 다 서버까지 왔다. 긴 주소(`/landing`)는 다섯 키 모두 매번 열렸으니 15번이다.

나머지 세 줄이 더 중요하다. 301이라도 `no-store`를 붙이면(`Nx2w`) 세 번 다 왔고, 302라도 `max-age=60`을 붙이면(`Pk5r`) 한 번만 왔다. 상태 코드는 헤더가 없을 때의 기본값을 정할 뿐이고, 실제로 기억할지는 `Cache-Control`이 정한다. HTTP 캐시 규칙(RFC 9111)에서 301은 따로 기한을 말하지 않아도 브라우저가 알아서 기한을 정해 저장해도 되는 응답이고, 302는 기한을 줘야만 저장된다. 기한을 정하는 규칙은 [HTTP 캐시와 CDN](/posts/http-caching-cdn)에 있다.

그러면 무엇을 고를까. 301은 서버가 받는 요청을 줄인다. 같은 사람이 같은 링크를 여러 번 눌러도 한 번만 오니, 서버 비용이 줄고 사용자도 왕복 한 번을 아낀다. 대신 서비스가 그 뒤의 클릭을 모르고, 목적지를 바꾸거나 신고된 링크를 막아도 이미 저장한 브라우저에는 반영되지 않는다. 302는 모든 클릭이 서버에 오니 서버가 더 바쁘지만, 클릭을 세고 링크를 통제할 수 있다.

단축 서비스는 대부분 클릭 통계와 악용 차단을 원하니 302 쪽이거나, 301을 주더라도 `Cache-Control: max-age`로 짧은 기한을 붙인다. 한 번 영구 기억된 301은 서버에서 고쳐도 사용자의 브라우저 캐시를 지우기 전까지 남는다는 점을 기억해 두자. 검색 엔진은 영구 이동을 보고 순위 신호를 목적지로 옮긴다고 알려져 있어서, 사이트 주소를 정말로 옮길 때는 301이 맞다. 단축 링크와 사이트 이전은 다른 문제다.

## 하루 864만 개를 만든다면

규모를 숫자로 잡아 보자. 우리 서비스는 하루 864만 개의 링크를 만들고, 링크 하나가 평균 20번 눌린다고 하자. 행 하나는 키, 긴 주소, 만든 사람, 시각을 합쳐 500바이트로 잡고, 링크는 10년 동안 지우지 않는다.

- 쓰기: 8,640,000 ÷ 86,400초 = 초당 100개.
- 읽기(리다이렉트): 그 20배인 초당 2,000번. 저녁 피크가 평균의 두 배라면 4,000번이다.
- 행 수: 864만 × 365 × 10 = 약 315억 개.
- 저장량: 315억 × 500바이트 = 약 15.8TB.

읽기가 쓰기보다 20배 많다는 숫자가 설계의 방향을 정한다. 리다이렉트를 빠르고 싸게 만드는 쪽에 힘을 쓴다. 15.8TB는 DB 한 대에 담기 버거운 크기라 언젠가 [샤딩](/posts/sd-sharding-intro)을 고민하게 되고, 315억 개를 구분하려면 키가 몇 글자 필요한지도 이 숫자에서 나온다. 어림셈 방법은 [⑩ 용량 어림하기](/posts/sd-capacity-estimation)에서 자세히 다뤘다.

직접 계산해 보자. 하루 생성 수, 읽기 배수, 행 크기(바이트), 보관 연수를 받아 `[쓰기 QPS, 읽기 QPS, 저장량 TB, 필요한 키 길이]`를 돌려준다. 쓰기 QPS는 반올림한 정수, 저장량은 1TB = 10^12바이트로 소수 첫째 자리까지, 키 길이는 62의 거듭제곱이 행 수 이상이 되는 가장 짧은 길이다.

  // writeQps: 하루 생성 수 / 86400 을 반올림
  // readQps: writeQps * readRatio
  // storageTB: 행 수 * 행 크기 / 1e12, 소수 첫째 자리

}`}
  solution={`function estimate(createsPerDay, readRatio, bytesPerRow, years) {

  const rows = createsPerDay * 365 * years;
  const storageTB = Number(((rows * bytesPerRow) / 1e12).toFixed(1));
  let keyLength = 1;
  while (62 ** keyLength < rows) keyLength++;
  return [writeQps, readQps, storageTB, keyLength];
}`}

첫 테스트의 키 길이가 6인 게 눈에 띈다. 62의 6제곱은 약 568억이라 315억 개가 들어간다. 생성이 10배가 되면 7글자가 필요하다. 처음부터 7글자를 기준으로 잡아 두면 10년 넘게 여유가 있다.

## 테이블은 키 하나로 찾게 만든다

메모리의 `Map`은 서버가 재시작하면 사라진다. PostgreSQL 16에 표를 만들었다. 기본 키는 [⑰에서 만든 고유 ID](/posts/sd-unique-id-generator)이고, 짧은 키에는 `UNIQUE`를 걸어 겹치지 않게 하면서 인덱스도 함께 만든다.

```sql
CREATE TABLE short_links (
  id         bigint PRIMARY KEY,                 -- 고유 ID 생성기가 준 번호
  short_key  varchar(10) NOT NULL UNIQUE,        -- 단축 키 (UNIQUE가 인덱스를 만든다)
  long_url   text NOT NULL,                      -- 원래 주소
  created_at timestamptz NOT NULL DEFAULT now(),
  expires_at timestamptz                         -- NULL이면 만료 없음
);
-- 20만 줄을 넣는다. 키는 번호를 문자열로 바꾼 가짜 값이다
INSERT INTO short_links (id, short_key, long_url)
SELECT g, 'k' || g, 'https://shop.example.com/items/' || g || '?utm_source=newsletter&utm_campaign=fall'
FROM generate_series(1, 200000) g;
ANALYZE short_links;
```

리다이렉트가 하는 질문은 "이 키의 긴 주소는?" 하나다. 실행 계획을 봤다.

```sql
EXPLAIN ANALYZE SELECT long_url FROM short_links WHERE short_key = 'k123456';
```

```text
 Index Scan using short_links_short_key_key on short_links  (cost=0.42..8.44 rows=1 width=77) (actual time=0.018..0.019 rows=1 loops=1)
   Index Cond: ((short_key)::text = 'k123456'::text)
 Planning Time: 0.228 ms
 Execution Time: 0.036 ms
```

`Index Scan using short_links_short_key_key`가 보면 될 줄이다. `UNIQUE`가 만든 인덱스를 타고 한 줄(`rows=1`)을 0.036ms에 찾았다. 행이 315억 개로 늘어도 B-tree의 깊이는 몇 단계만 늘어나니 이 질문은 계속 싸다.

문제는 단축 요청 쪽의 "이 긴 주소가 이미 있나"다.

```sql
EXPLAIN ANALYZE SELECT short_key FROM short_links
WHERE long_url = 'https://shop.example.com/items/123456?utm_source=newsletter&utm_campaign=fall';
```

```text
 Gather  (cost=1000.00..5319.77 rows=1 width=7) (actual time=24.447..27.948 rows=1 loops=1)
   Workers Planned: 2
   Workers Launched: 2
   ->  Parallel Seq Scan on short_links  (cost=0.00..4319.67 rows=1 width=7) (actual time=13.952..15.999 rows=0 loops=3)
         Filter: (long_url = 'https://shop.example.com/items/123456?utm_source=newsletter&utm_campaign=fall'::text)
         Rows Removed by Filter: 66666
 Planning Time: 0.035 ms
 Execution Time: 27.963 ms
```

`Parallel Seq Scan`, 표 전체를 훑었다. 20만 줄에 28ms니 315억 줄이면 쓸 수 없다. `long_url`에 인덱스가 필요한데, 긴 주소는 수백 글자가 될 수 있어 B-tree에 통째로 넣으면 인덱스가 커지고, PostgreSQL의 B-tree는 한 항목이 페이지의 약 3분의 1(8KB 페이지에서 2,700바이트 정도)을 넘으면 넣지 못한다. 그래서 해시 인덱스를 걸었다. 값 대신 값의 해시만 저장한다.

```sql
CREATE INDEX short_links_long_url_hash ON short_links USING hash (long_url);
```

```text
 Index Scan using short_links_long_url_hash on short_links  (cost=0.00..8.02 rows=1 width=7) (actual time=0.022..0.023 rows=1 loops=1)
   Index Cond: (long_url = 'https://shop.example.com/items/123456?utm_source=newsletter&utm_campaign=fall'::text)
 Planning Time: 0.134 ms
 Execution Time: 0.037 ms
```

28ms가 0.037ms가 됐다. 해시 인덱스는 같은지만 비교할 수 있고 `UNIQUE`로 만들 수 없다. 같은 주소가 동시에 두 번 들어오는 경쟁까지 막으려면 `md5(long_url)` 같은 짧은 열을 따로 두고 거기에 `UNIQUE`를 건다. MySQL 8의 InnoDB는 사용자가 해시 인덱스를 만들 수 없어서 보통 이 방법을 쓴다. 매번 새 키를 주는 정책이라면 이 인덱스 자체가 필요 없다.

이 표는 조인이 없고, 키 하나로 한 줄을 읽는 질문이 대부분이다. 그래서 관계형 DB 대신 키-값 저장소를 고르는 설계도 흔하다. 앞의 [키-값 저장소 설계](/posts/sd-kv-store-partition-replication)가 이런 질문을 위한 것이다. 관계형으로 시작하면 만든 사람별 목록, 만료 정리 같은 부가 기능을 SQL로 쉽게 만들 수 있다. 어느 쪽이든 키 하나로 찾는다는 성질 덕에 나중에 `short_key` 기준으로 샤딩하기 쉽다.

마지막 단계에 함정이 하나 있다. 링크를 만든 직후에 사용자가 바로 눌러 보면, 그 요청이 아직 새 행을 받지 못한 복제본으로 갈 수 있다. 이것을 복제 지연이라고 한다. 방금 만든 링크가 404를 내면 서비스가 고장 난 것처럼 보인다. 그래서 만든 직후 그 링크를 캐시에 미리 넣어 두거나, 복제본에서 못 찾으면 주 DB에 한 번 더 묻는다. 캐시를 어떻게 채우고 얼마나 막아 주는지는 [⑲ URL 단축기 ②](/posts/sd-url-shortener-key-generation)에서 숫자로 본다.

## 남의 피싱 링크를 대신 보내 주지 않으려면

단축 링크는 목적지를 숨긴다. 그래서 피싱이나 악성 파일 링크를 감추는 데 자주 쓰인다. 링크를 연 사람에게는 우리 도메인이 보이니, 악용이 쌓이면 우리 도메인이 메일 서비스나 브라우저의 차단 목록에 오를 수 있다. 그러면 정상 링크까지 함께 막힌다. 그래서 단축기는 처음부터 몇 가지 방어를 둔다.

- 단축 요청에 요청 수 제한을 건다. 사람이나 API 키, IP별로 분당 몇 개까지만 만들게 한다. 방법은 [요청 수 제한 알고리즘](/posts/rate-limiting-algorithms)에 있고, 넘기면 429와 `Retry-After`를 돌려준다.
- 만들 때 목적지를 검사한다. 스킴을 http와 https로 제한하고, 알려진 악성 주소 목록과 비교한다. 만든 뒤에도 신고가 들어오면 링크를 막는다. 302라면 다음 클릭부터 바로 막힌다.
- 단축 링크를 다시 단축하는 것을 막는다. 자기 도메인이나 다른 단축 서비스를 목적지로 받으면 리다이렉트가 이어져 목적지를 더 숨기고, 서로를 가리키면 끝없이 돈다.
- 키를 쉽게 짐작하지 못하게 한다. 키가 1씩 늘면 남이 비공개로 공유한 링크를 차례로 열어 볼 수 있다. 이 문제는 다음 글에서 다룬다.

운영 중에 볼 지표도 정해 둔다. 리다이렉트 응답 시간과 캐시 적중률, 404 비율, 그리고 생성 요청이 특정 계정에 몰리는지다. 404가 갑자기 늘면 누가 키를 무작위로 찍어 보는 중일 가능성이 크다.

## 겉모양은 정해졌고, 남은 건 짧은 키

URL 단축기의 겉모양은 이제 정해졌다. 단축은 `POST`로 받아 201과 키를 주고, 리다이렉트는 `GET /{key}`에 `Location`으로 답한다. 301과 302는 브라우저가 답을 기억하느냐의 차이고, 실제 동작은 `Cache-Control`이 정한다. 테이블은 키 하나로 한 줄을 찾게 만들고, 읽기가 20배 많으니 그 경로에 캐시와 복제본을 둔다.

남은 질문은 짧은 키 자체다. 315억 개를 6~7글자로 겹치지 않게 만드는 방법은 긴 주소를 해시해서 자르는 쪽과 번호를 62진수로 바꾸는 쪽으로 갈린다. [⑲ URL 단축기 ②](/posts/sd-url-shortener-key-generation)에서 두 방법을 직접 돌려 보고, 인기 링크를 캐시로 받는 법까지 이어 간다.

## 면접에서 나올 만한 질문

### URL 단축기의 API를 어떻게 설계하나요?

`POST /api/v1/links`로 긴 주소를 받아 201 Created와 단축 키, 짧은 주소를 돌려주고, `GET /{key}`로 들어온 요청에 리다이렉트 응답과 `Location` 헤더를 준다. 긴 주소는 http, https 절대 주소만 받고 길이를 제한한다. 원하는 키, 만료 시각은 선택 필드로 두고, 이미 있는 키는 409로 거절한다.

### 301과 302 중 무엇을 쓰나요?

클릭 통계와 링크 통제가 필요하면 302를 쓴다. 301은 헤더가 없으면 브라우저가 기억해 두 번째 클릭부터 서버에 오지 않아 서버 부하는 줄지만, 클릭을 셀 수 없고 목적지를 바꾸거나 막아도 반영되지 않는다. 실제 저장 여부는 `Cache-Control`이 정하므로, 301을 쓰더라도 `max-age`로 짧은 기한을 붙이는 편이 안전하다.

### 저장 공간과 QPS는 어떻게 어림하나요?

하루 생성 수를 86,400으로 나눠 쓰기 QPS를 구하고, 읽기 배수를 곱해 읽기 QPS를 구한다. 하루 864만 개, 읽기 20배면 쓰기 100, 읽기 2,000이고 피크는 두 배로 잡는다. 저장량은 행 수 곱하기 행 크기로, 10년에 315억 행, 500바이트면 약 15.8TB다. 키 길이는 62의 거듭제곱이 행 수를 넘는 길이로 정한다.

### 테이블과 인덱스는 어떻게 두나요?

`short_key`에 `UNIQUE` 인덱스를 걸어 리다이렉트가 인덱스로 한 줄만 찾게 한다. 같은 긴 주소의 중복을 막으려면 긴 주소에 인덱스가 필요한데, 긴 문자열 전체를 B-tree에 넣기보다 해시 인덱스나 해시 열에 `UNIQUE`를 건다. 조인이 거의 없고 키로만 읽으니 키-값 저장소도 좋은 선택이다.

### 링크를 만들자마자 눌렀더니 404가 납니다. 왜 그럴까요?

새 행은 주 DB에 썼는데 읽기는 아직 그 행을 받지 못한 복제본으로 갔을 가능성이 크다. 만든 직후 그 링크를 캐시에 미리 넣어 두거나, 복제본에서 못 찾으면 주 DB에 한 번 더 묻는다. 만든 사람 본인의 첫 조회만 주 DB로 보내는 방법도 있다.

### 트래픽이 10배가 되면 어디부터 손대나요?

읽기가 대부분이니 리다이렉트 경로부터 본다. 웹 서버를 늘리고, 캐시 적중률을 높이고, 복제본을 늘린다. 생성 쪽은 10배여도 초당 1,000개 정도라 주 DB가 버티지만, 저장량이 10년에 150TB를 넘으니 `short_key` 기준 샤딩을 준비한다. 키 길이도 6글자에서 7글자로 늘어난다.

### 단축 서비스가 피싱에 악용되면 어떻게 하나요?

만들 때 목적지 스킴과 악성 주소 목록을 검사하고, 사람이나 IP별 요청 수 제한을 둔다. 신고된 링크는 막는데, 302라면 다음 클릭부터 바로 반영된다. 단축 링크를 목적지로 받는 것도 막아 리다이렉트가 이어지거나 도는 것을 피한다.
