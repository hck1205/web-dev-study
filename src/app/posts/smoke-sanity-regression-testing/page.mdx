배송비 안내 문구를 바꾸는 작업이었다. "3만 원 이상 무료배송"을 "30,000원 이상 구매 시 무료배송"으로. 하는 김에 배송비 함수가 금액만 돌려주던 것을 금액과 안내 문구를 함께 돌려주도록 고쳤다. 배송비 모듈의 테스트를 고쳐서 초록불을 확인하고, 문구만 바뀐 거라 다른 테스트는 굳이 돌리지 않았다. 배포하고 40분 뒤 고객센터에서 연락이 온다. 주문서의 결제 금액이 `24000[object Object]원`으로 나오고, 결제 버튼을 누르면 결제사가 금액 형식 오류로 거절한다고.

결제 화면은 배송비 함수의 반환값을 숫자로 더하고 있었다. 숫자에 객체를 더하면 JavaScript는 둘을 문자열로 이어 붙인다. 수정 범위는 작았지만 영향 범위는 작지 않았다. 사고를 돌아보면 빠진 확인이 세 가지다. 배포 직후 "주문서가 열리고 결제 금액이 숫자로 나오는가"만 봤어도 1분 안에 알았다(스모크). 고친 함수를 쓰는 곳을 따라가 그 테스트를 돌렸으면 배포 전에 알았다(영향 분석과 회귀). 그리고 고친 김에 다른 것까지 바꾼 변경을 리뷰에서 걸렀어야 했다.

이 글은 기능·비기능 테스트의 구분에서 시작해, 스모크·새니티·회귀 테스트가 각각 어떤 질문에 답하는지, 회귀 묶음이 너무 커졌을 때 위험과 변경 영향으로 줄이는 법, 브라우저·기기 호환성, 자동화가 못 보는 것을 찾는 탐색적 테스트, 그리고 계획서와 결과 리포트를 다룬다. 케이스를 뽑는 기법은 [테스트 케이스 설계](/posts/test-design-techniques)에서, 테스트를 층별로 나누는 이야기는 [테스트 피라미드와 단위 테스트](/posts/test-pyramid-unit-tests)에서 했다. 예제는 Node 22.22와 Jest 29.7에서 돌렸다.

## 기능이 맞는지, 쓸 만한지

테스트를 나누는 첫 번째 축은 "무엇을 확인하나"다. 기능 테스트(functional testing)는 시스템이 해야 할 일을 하는지 본다. 쿠폰이 적용되나, 주문이 저장되나, 취소하면 환불되나. 입력과 기대 결과로 판정한다.

비기능 테스트(non-functional testing)는 그 일을 얼마나 잘하는지 본다. 응답이 빠른가(성능), 동시 사용자 만 명에서도 버티나(부하), 남의 주문을 못 보나(보안), 화면 낭독기로 결제할 수 있나(접근성), 사파리에서도 되나(호환성), 장애가 나도 복구되나(신뢰성). ISO/IEC 25010 품질 모델이 기능 적합성 외에 성능 효율성, 호환성, 보안성 같은 특성으로 나눠 두었다.

둘은 실패하는 방식이 다르다. 기능 결함은 대개 특정 입력에서 확실히 틀린다. 비기능 결함은 조건이 쌓여야 드러난다. 데이터가 10만 건을 넘어야 느려지고, 동시 요청이 몰려야 커넥션이 바닥난다. 그래서 비기능 테스트는 운영과 닮은 환경과 데이터가 필요하고, 기준도 숫자로 정해야 판정이 된다. "빨라야 한다"는 기준이 아니고 "p95 300ms 이하"가 기준이다.

이 글에서 다루는 스모크·새니티·회귀는 이 축과 다른 축이다. "언제, 얼마나 넓게 다시 확인하나"를 나눈다. 회귀 테스트에도 기능과 비기능이 다 들어간다. 지난주보다 결제 API가 두 배 느려졌다면 그것도 회귀다.

## 연기가 나는지부터 본다

스모크 테스트(smoke test)라는 이름은 하드웨어에서 왔다고들 한다. 새로 조립한 기판에 전원을 넣고 연기가 나는지부터 본다. 연기가 나면 더 볼 것도 없다. 소프트웨어에서는 새 빌드나 새 배포가 "더 테스트할 가치가 있을 만큼 살아 있는가"를 확인하는 짧은 묶음이다. 빌드 검증 테스트(BVT, build verification test)라고도 한다.

스모크는 넓고 얕다. 핵심 기능마다 한두 개씩, 가장 굵은 길만 지나간다. 서비스가 뜨고, 로그인이 되고, 상품이 보이고, 주문서가 열리고, 결제 승인이 돌아오는지. 쿠폰 경계값 같은 세부는 넣지 않는다. 목표는 몇 분 안에 끝나는 것이다. 배포 파이프라인에 들어가니 오래 걸리면 아무도 기다리지 않는다.

배포 직후 운영 주소에 대고 돌리는 스모크를 Node 내장 테스트 러너로 짜면 이 정도다.

```js
// smoke.test.js
import { test } from "node:test";
import assert from "node:assert/strict";

const BASE = process.env.BASE_URL ?? "http://localhost:3000";
const get = (path) => fetch(BASE + path, { signal: AbortSignal.timeout(3000) });

test("[smoke] 헬스 체크", async () => {
  assert.equal((await get("/healthz")).status, 200);
});
test("[smoke] 상품 상세가 가격을 준다", async () => {
  const res = await get("/products/1");
  assert.equal(res.status, 200);
  assert.equal(typeof (await res.json()).price, "number");
});
test("[smoke] 주문서가 열린다", async () => {
  assert.equal((await get("/checkout")).status, 200);
});
```

사고 난 빌드를 흉내 낸 로컬 서버(주문서만 500을 내게 만들었다)에 돌린 결과다.

```bash
# 배포한 주소를 넣고 스모크만 돌린다
BASE_URL=http://localhost:3000 node --test --test-reporter=spec smoke.test.js
```

```text
✔ [smoke] 헬스 체크 (92.982218ms)
✔ [smoke] 상품 상세가 가격을 준다 (15.887417ms)
✖ [smoke] 주문서가 열린다 (5.685306ms)
ℹ tests 3
ℹ suites 0
ℹ pass 2
ℹ fail 1
...
  AssertionError [ERR_ASSERTION]: Expected values to be strictly equal:
  
  500 !== 200
```

헬스 체크는 통과했다. 이게 스모크에 헬스 체크만 두면 안 되는 이유다. 프로세스가 살아 있다는 것과 주문을 받을 수 있다는 건 다르다. 실패하면 `node --test`가 0이 아닌 종료 코드를 내니, 파이프라인은 여기서 멈추고 이전 버전으로 되돌린다.

스모크 테스트의 이름에 `[smoke]`를 붙여 두면 같은 파일에 다른 테스트가 섞여 있어도 골라 돌릴 수 있다. `node --test --test-name-pattern="\[smoke\]"`는 이름이 맞는 테스트만 실행한다. Jest나 Vitest에서는 `-t` 옵션, Playwright에서는 `@smoke` 태그와 `--grep`을 같은 용도로 쓴다.

운영 스모크에서 조심할 것은 데이터다. 운영에 대고 진짜 주문을 넣으면 재고가 빠지고 정산에 잡힌다. 테스트 계정과 테스트 상품을 따로 두고 결제는 승인 직전에서 멈추거나 즉시 취소하는 식으로, 운영 데이터를 더럽히지 않는 길만 고른다. 읽기만 하는 확인은 배포 뒤에도 계속 돌릴 수 있는데, 이게 일정 간격으로 도는 합성 모니터링(synthetic monitoring)이 된다.

## 고친 곳 주변만 깊게

새니티 테스트(sanity test)는 특정 수정이나 작은 변경 뒤에, 그 부분이 말이 되게 동작하는지를 좁고 깊게 확인한다. 쿠폰 반올림 버그를 고쳤다면 쿠폰 계산의 경계값과 반올림 케이스, 쿠폰이 붙는 주문서 금액까지만 본다. 전체를 다시 돌리기 전에 "이 수정이 고쳐졌다고 말할 만한가"를 빠르게 판단해서, 아니면 바로 개발자에게 돌려보낸다.

솔직히 두 용어는 회사와 문헌마다 쓰는 법이 다르다. ISTQB 용어집처럼 둘을 거의 같은 말로 보는 곳도 있다. 흔히 쓰는 구분은 이렇다. 스모크는 새 빌드 전체가 살아 있는지 넓고 얕게, 새니티는 바뀐 부분이 맞는지 좁고 깊게. 면접에서는 이 구분을 말하되, 팀마다 정의가 다르니 "우리 팀에서는 무엇을 스모크라고 부르나"를 먼저 맞추는 게 중요하다고 덧붙이면 된다.

## 어제 되던 것이 오늘도 되나

회귀 테스트(regression test)는 변경 때문에 예전에 되던 기능이 깨지지 않았는지 확인한다. 회귀(regression)는 퇴행이라는 뜻이다. 새 기능이 동작하는지는 그 기능의 테스트가 보고, 회귀 테스트는 손대지 않은 곳을 본다. 도입부 사고는 정확히 회귀였다. 배송비 테스트는 통과했고, 그걸 쓰는 결제가 깨졌다.

회귀 묶음에는 시간이 지나며 테스트가 쌓인다. 기능을 만들 때 쓴 테스트, 그리고 버그를 고칠 때마다 그 버그를 재현하는 테스트를 하나씩 더한다. 버그 재현 테스트가 회귀 묶음에서 가장 값진 부분이다. 한 번 났던 버그는 같은 자리에서 다시 날 확률이 높다.

도입부 사고를 회귀 테스트로 바꿔 보자. 원칙은 "고치기 전에 실패하는 테스트부터"다. 버그를 재현하지 못하는 테스트는 그 버그를 지켜 주지 못한다.

```js
// checkout.js (사고 난 코드)
import { shippingFee } from "./shipping.js";
export function payAmount(items) {
  const subtotal = items.reduce((sum, i) => sum + i.price * i.qty, 0);
  return subtotal + shippingFee(subtotal);   // 예전엔 숫자였다
}
```

```js
// checkout.test.js
import { test } from "node:test";
import assert from "node:assert/strict";
import { payAmount } from "./checkout.js";

// INC-0412: 배송비 함수가 객체를 돌려주자 결제 금액이 문자열로 이어 붙었다
test("결제 금액은 상품 합계에 배송비를 더한 숫자다", () => {
  assert.equal(payAmount([{ price: 12000, qty: 2 }]), 27000);
  assert.equal(payAmount([{ price: 16000, qty: 2 }]), 32000);
});
```

```text
✖ 결제 금액은 상품 합계에 배송비를 더한 숫자다 (2.330893ms)
ℹ tests 1
ℹ pass 0
ℹ fail 1
...
  AssertionError [ERR_ASSERTION]: Expected values to be strictly equal:
  + actual - expected
  
  + '24000[object Object]'
  - 27000
```

실패 메시지에 사고의 증상이 그대로 찍힌다. 이제 `shippingFee(subtotal).fee`로 고치면 통과하고, 누가 다음에 배송비 함수의 모양을 또 바꿔도 이 테스트가 막는다. 테스트 위에 사고 번호를 주석으로 남겨 두면, 나중에 이 테스트를 지우려는 사람이 왜 있는지 찾아볼 수 있다. 3만 원 경계(24,000원과 32,000원)를 함께 넣은 건 고치면서 배송비 조건까지 건드리는 실수를 같이 막으려는 것이다.

이 사고는 타입으로도 막을 수 있었다. TypeScript였다면 `number + { fee, label }`에서 컴파일 오류가 났을 것이다. 회귀 테스트와 타입 검사는 겹치는 부분이 있지만, 타입은 모양만 보고 값(3만 원에서 배송비가 0인지)은 보지 않는다. 둘 다 둔다.

이 그림에서 중요한 건 같은 질문을 두 번 하지 않는다는 것이다. PR 단계에서 쿠폰 경계값을 확인했으면 운영 스모크에서 다시 확인하지 않는다. 각 단계는 그 단계에서만 답할 수 있는 질문(이 환경에서 뜨나, 이 브라우저에서 되나)을 맡는다.

## 느려진 것도 회귀다

기능 회귀는 테스트가 빨간불을 켠다. 성능 회귀는 조용하다. 결제 API가 120ms에서 180ms로 느려져도 모든 테스트는 통과한다. 이런 변화는 한 번에 크게 오지 않고 PR 여러 개에 걸쳐 조금씩 온다. 하나하나는 "이 정도면 괜찮다"로 넘어가고, 석 달 뒤에 두 배가 되어 있다.

그래서 비기능 회귀는 기준선(baseline)과 비교한다. 같은 환경, 같은 데이터, 같은 부하로 main의 숫자를 기록해 두고, 새 빌드의 숫자가 기준선에서 정한 비율 이상 나빠지면 실패로 본다. 판정은 평균보다 p95 같은 백분위로 한다. 평균은 느린 소수의 요청을 숨긴다. 판정 규칙을 표로 적으면 이런 모양이 된다(숫자는 예시다).

```text
지표                      기준선(main)   이번 빌드   허용    판정
POST /orders p95          182ms          241ms       +15%    실패 (+32%)
GET /products/:id p95     38ms           40ms        +15%    통과
JS 번들(주문서, gzip)     148KB          151KB       +5KB    통과
```

조심할 것은 측정의 흔들림이다. 공유 CI 러너에서 한 번 잰 숫자는 같은 코드로도 눈에 띄게 흔들린다. 옆에서 다른 작업이 같은 CPU를 쓰기 때문이다. 여러 번 재서 중앙값을 쓰고, 허용 폭을 흔들림보다 넓게 잡고, 실패하면 한 번 더 재서 확인한다. 그래도 흔들리면 PR마다 막는 대신 추세 그래프로 보고 일정 기간 계속 나빠질 때 알린다. 번들 크기처럼 흔들리지 않는 숫자는 PR마다 바로 막아도 된다.

## 다 돌릴 수 없으면 위험한 것부터

회귀 묶음은 계속 자란다. 3년쯤 지나면 E2E 회귀만 두 시간이 걸리고, 수동 회귀는 사흘이 걸린다. 매번 다 돌릴 수 없으니 순서를 정한다. 위험 기반 테스트(risk-based testing)는 기능마다 위험을 "고장 날 가능성 × 고장 났을 때의 영향"으로 매기고, 높은 것부터 돌린다.

| 기능 | 가능성 | 영향 | 위험 | 언제 돌리나 |
|---|---|---|---|---|
| 결제 승인·금액 계산 | 중간 (자주 바뀜) | 높음 (돈) | 높음 | 모든 PR, 모든 배포 |
| 로그인·회원 가입 | 낮음 | 높음 (전체 차단) | 중간 | 모든 배포 |
| 쿠폰·프로모션 | 높음 (매주 바뀜) | 중간 | 높음 | 관련 PR, 이벤트 전 |
| 마이페이지 주소 변경 | 낮음 | 낮음 | 낮음 | 밤마다 |

가능성은 숫자로도 잡힌다. 최근 변경이 잦은 파일, 과거에 결함이 많이 나온 모듈, 코드가 복잡한 곳, 새로 온 사람이 많이 만진 곳. git 로그에서 파일별 변경 횟수만 뽑아 봐도 감이 온다. 영향은 매출, 사용자 수, 법적 책임, 되돌리기 어려움(데이터 손상)으로 본다.

여기에 변경 영향을 겹친다. 위험이 낮은 기능이라도 이번 변경이 그 코드를 건드렸다면 돌린다. 반대로 위험이 높아도 이번 변경과 완전히 떨어져 있다면 PR 단계에서는 건너뛰고 머지 후 전체 실행에 맡긴다. 위험은 "평소에 얼마나 자주 볼지"를, 변경 영향은 "이번에 꼭 볼지"를 정한다.

## 바뀐 파일에서 거꾸로 따라가기

변경 영향 분석(change impact analysis)을 테스트 선택에 쓰는 가장 흔한 방법은 import 그래프를 거꾸로 따라가는 것이다. 바뀐 파일을 import하는 파일, 그 파일을 import하는 파일을 계속 따라 올라가다가 만나는 테스트 파일을 돌린다. 도입부 사고의 구조를 줄여 보면 이렇다.

```text
shipping.js        ← 배송비 계산 (이번에 바꾼 파일)
cart.js            ← shipping.js를 import
checkout.js        ← cart.js를 import
search.js          ← 아무것도 import하지 않음
*.test.js          ← 각 파일 옆에 테스트 하나씩
```

## 직접 해 보기: 영향받는 테스트 고르기

`deps`는 파일마다 그 파일이 import하는 파일 목록이다. 바뀐 파일 목록 `changed`를 받아, 영향받는 테스트 파일(`.test.js`로 끝나는 파일)을 이름순으로 돌려주는 함수를 만들어 보자. 순환 import가 있어도 멈추지 않아야 하고, 바뀐 파일이 테스트 파일이면 그 테스트도 돌린다.

## 같은 코드, 다른 브라우저

호환성 테스트(compatibility testing)는 같은 빌드가 사용자 환경마다 똑같이 동작하는지 본다. 웹이라면 브라우저 엔진(크로미움, 파이어폭스의 Gecko, 사파리의 WebKit), 운영체제, 화면 크기, 앱이라면 OS 버전과 기기다. iOS에서는 모든 브라우저가 WebKit 기반이라 크롬을 깔아도 사파리와 같은 엔진 문제를 만나는 경우가 많다(EU에서는 iOS 17.4부터 다른 엔진이 허용되는 등 지역별 차이가 있다).

모든 조합을 다 돌릴 수는 없으니, 여기도 위험으로 고른다. 분석 도구에서 실제 방문자의 브라우저·기기 비율을 뽑고, 상위 몇 개와 "점유율은 낮지만 깨지면 큰" 조합(사내 결재용 구형 브라우저 같은)을 고른다. 조합이 많으면 [테스트 케이스 설계](/posts/test-design-techniques#조합이-서른여섯-개면-아홉-개로)의 페어와이즈로 줄인다.

Playwright는 한 테스트를 엔진별로 돌리는 설정을 기본으로 준다.

```ts
// playwright.config.ts
import { defineConfig, devices } from "@playwright/test";

export default defineConfig({
  projects: [
    { name: "chromium", use: { ...devices["Desktop Chrome"] } },
    { name: "webkit", use: { ...devices["Desktop Safari"] } },
    { name: "mobile-safari", use: { ...devices["iPhone 13"] } },
  ],
});
```

다만 데스크톱에서 돌리는 WebKit이나 기기 에뮬레이션은 화면 크기, 사용자 에이전트, 터치 같은 것을 흉내 낼 뿐 실제 기기와 같지는 않다. 실제 iOS 사파리의 키보드가 올라오며 레이아웃이 밀리는 문제, 저사양 안드로이드의 성능은 실기기에서만 보인다. 그래서 자동화는 엔진 차이를 넓게 잡고, 실기기 확인(직접 또는 BrowserStack 같은 실기기 클라우드)은 핵심 흐름에만 쓴다.

## 자동화가 못 보는 것은 사람이 본다

자동화된 테스트는 우리가 미리 적어 둔 질문에만 답한다. "결제 금액이 18,000원인가"는 확인하지만, 버튼이 금액 위에 겹쳐 보이는지, 안내 문구가 오해를 부르는지, 쿠폰을 고르는 순서가 어색한지는 묻지 않는다. 처음 보는 결함은 아무도 질문을 적어 두지 않았다.

탐색적 테스트(exploratory testing)는 테스트를 설계하고 실행하고 배우는 일을 동시에 한다. 미리 정한 단계를 따르지 않고, 앞에서 본 결과에 따라 다음에 무엇을 해 볼지 정한다. 그렇다고 아무렇게나 만지는 게 아니다. 흔히 쓰는 틀은 세션 기반 테스트다. 시간을 60~90분 정도로 끊고, 세션마다 목표(차터)를 하나 정한다. 엘리자베스 헨드릭슨이 『Explore It!』에서 쓴 차터 문형이 기억하기 좋다.

```text
차터: 쿠폰 적용 화면을
      뒤로 가기·새로 고침·다른 탭으로
      탐색해서 쿠폰이 두 번 쓰이거나 금액이 어긋나는 경우를 찾는다
시간: 60분
기록: 해 본 것, 발견한 것(결함·질문·위험), 못 해 본 것
```

세션이 끝나면 기록을 남긴다. 발견한 결함은 재현 단계를 적어 결함 관리 도구로 보내고, 그중 반복 확인할 가치가 있는 것은 자동화된 회귀 테스트로 옮긴다. 탐색이 새 질문을 찾고, 자동화가 그 질문을 매번 다시 묻는 순환이다.

수동 테스트 전체가 탐색은 아니다. 정해진 케이스를 사람이 따라가는 수동 스크립트 테스트도 있다. 이건 자동화 후보다. 매번 같은 단계를 반복하는 일은 사람이 하면 지루하고 실수가 나니, 자주 도는 것부터 자동화한다. 사람이 계속 맡을 것은 판단이 필요한 일이다. 처음 만드는 화면, 자주 바뀌어 자동화가 따라가지 못하는 화면, 사용성과 문구, 그리고 "이게 정말 맞는 동작인가"라는 질문이다.

## 계획서에는 범위와 멈출 기준을 적는다

테스트 계획서는 길 필요가 없지만, 몇 가지는 꼭 적는다. 국제 표준(ISO/IEC/IEEE 29119-3, 예전 IEEE 829)이 정한 항목은 많은데, 실제로 질문을 막아 주는 건 이 정도다.

```text
범위:       쿠폰 적용(주문서, 장바구니), 결제 취소 시 쿠폰 복원
범위 밖:    쿠폰 발급 관리자 화면(이번 변경 없음), 앱 푸시 문구
접근:       단위·API 자동화 + 핵심 흐름 E2E(크로미움, 웹킷) + 탐색 세션 2회
환경:       스테이징, 테스트 결제 키, 테스트 쿠폰 20장
진입 기준:  스테이징 배포 완료, 스모크 통과, 쿠폰 테스트 데이터 준비
종료 기준:  계획한 케이스 100% 실행, 치명·높음 결함 0, 회귀 묶음 통과,
            알려진 낮음 결함은 목록과 처리 계획을 함께 기록
위험:       결제사 샌드박스 불안정 → 막히면 결제사 목으로 대체하고 위험으로 기록
```

"범위 밖"을 적는 게 생각보다 중요하다. 적지 않으면 각자 다르게 가정하고, 사고가 난 뒤에야 서로 "그건 테스트한 줄 알았다"고 말한다. 진입 기준은 테스트를 시작해도 되는 상태, 종료 기준은 멈춰도 되는 상태다. 기준이 없으면 시작은 빌드가 반쯤 깨진 채로 하고, 끝은 일정이 정한다. 통합·인수 단계의 진입·종료 기준을 숫자로 적는 법은 [SIT와 UAT](/posts/sit-uat-testing#언제-시작하고-언제-끝났다고-말하나)에서 더 자세히 다뤘다.

## 결과를 CI에 남긴다

테스트 결과는 사람이 읽기 전에 기계가 읽을 수 있어야 한다. 대부분의 CI가 JUnit XML 형식을 읽어서 실패한 테스트를 PR 화면에 보여 주고 이력을 쌓는다. Node 내장 러너도 이 형식으로 낸다.

```bash
# 결과를 JUnit XML로 파일에 남긴다 (CI가 이 파일을 읽는다)
node --test --test-reporter=junit --test-reporter-destination=report.xml
```

```text
<?xml version="1.0" encoding="utf-8"?>
<testsuites>
	<testcase name="[smoke] 주문서 페이지가 200으로 열린다" time="0.001652" classname="test"/>
	<testcase name="[smoke] 카드 결제 승인이 돌아온다" time="0.000297" classname="test"/>
	<!-- tests 2 -->
	<!-- pass 2 -->
	<!-- fail 0 -->
	...
</testsuites>
```

`--test-reporter`는 여러 번 줄 수 있어서, 화면에는 `spec`으로 보고 파일에는 `junit`으로 남기는 식으로 함께 쓴다.

결과를 쌓으면 추세가 보인다. 회귀 묶음 실행 시간이 매달 얼마나 늘고 있나, 어느 모듈에서 결함이 계속 나오나, 같은 커밋에서 성공과 실패가 섞이는 테스트가 무엇인가. 마지막이 플레이키 테스트다. 찾는 법과 격리하는 순서는 [CI/CD 기초](/posts/ci-cd-basics#가끔-실패하는-테스트)에 있다. 결함 추세는 열린 결함 수보다 "새로 열린 수와 닫힌 수"를 같이 보는 게 낫다. 출시 직전에 새로 열리는 결함이 줄지 않는다면, 테스트가 아직 결함을 찾아내는 중이라는 뜻이다.

## 회귀 묶음이 무너지는 모습들

현장에서 회귀 테스트가 제 역할을 못 할 때 보이는 증상과 먼저 볼 곳을 모았다.

- 회귀가 너무 오래 걸려 아무도 PR에서 안 돌린다: 느린 테스트 상위 10개부터 본다. E2E로 확인하던 계산 규칙을 단위 테스트로 내리고, 남은 것은 병렬로 쪼개거나(Playwright·Jest의 shard 옵션) 영향 분석으로 고른다.
- 빨간불이 떠도 다들 재실행을 누른다: 플레이키가 쌓였다. 재시도로 통과한 기록을 따로 보고, 격리하고, 주인을 정한다.
- 테스트는 다 통과했는데 운영에서 깨진다: 회귀 묶음이 그 길을 안 지나간다. 이번 사고를 재현하는 테스트를 먼저 묶음에 넣고, 영향 분석이 놓친 연결(설정, 다른 서비스의 응답 형식)을 찾는다. 서비스 사이의 응답 형식은 [API 테스트 자동화](/posts/api-test-automation)에서 다룬다.
- 회귀 묶음에 아무도 모르는 테스트가 수백 개다: 각 테스트가 무엇을 지키는지 이름만 보고 알 수 없다. 이름을 "무엇을 하면 무엇이 된다"로 고치고, 같은 것을 확인하는 중복은 지운다.
- 스모크가 통과했는데 사용자가 못 쓴다: 스모크가 헬스 체크만 본다. 핵심 업무 흐름의 첫 단계(주문서 열기, 결제 승인)를 넣는다.

## 언제, 얼마나 넓게

스모크는 "이 빌드가 살아 있나"를 넓고 얕게 몇 분 안에, 새니티는 "이 수정이 말이 되나"를 좁고 깊게, 회귀는 "어제 되던 게 오늘도 되나"를 넓게 본다. 회귀가 무거워지면 위험(가능성 × 영향)으로 평소 순서를 정하고, 변경 영향(import를 거꾸로 따라가기)으로 이번에 꼭 볼 것을 고르되, 그래프 밖의 변경과 머지 후 전체 실행이라는 안전장치를 남긴다. 자동화는 이미 아는 질문을 매번 다시 묻고, 사람은 탐색으로 새 질문을 찾는다. 테스트를 언제 쓰느냐의 문제, 즉 코드보다 먼저 쓰는 방식은 [TDD, BDD, ATDD](/posts/tdd-bdd-atdd)에서 이어진다.

## 면접에서 나올 만한 질문

### 스모크 테스트와 새니티 테스트는 어떻게 다른가요?

흔한 구분은 스모크가 새 빌드 전체가 살아 있는지 넓고 얕게 보고, 새니티는 특정 수정이 제대로 됐는지 좁고 깊게 본다는 것이다. 스모크는 배포 직후 핵심 흐름(서비스 기동, 로그인, 주문서, 결제 승인)을 몇 분 안에 확인하고, 새니티는 고친 기능과 그 주변만 본다. 다만 ISTQB 용어집처럼 둘을 같은 말로 보는 곳도 있어서, 팀 안에서 정의를 먼저 맞추는 게 좋다.

### 스모크 테스트는 누가, 언제 돌리나요?

배포 파이프라인이 자동으로 돌린다. 스테이징에 올린 직후 돌려서 통과해야 그 환경에서 더 긴 테스트를 시작하고, 운영에 올린 직후 다시 돌려서 실패하면 바로 되돌린다. 헬스 체크만으로는 부족하고, 주문서 열기처럼 핵심 업무의 첫 단계를 넣어야 한다. 운영에서는 테스트 계정과 상품으로 데이터를 더럽히지 않는 길만 고르고, 읽기 전용 확인은 합성 모니터링으로 계속 돌린다.

### 회귀 테스트는 무엇이고 왜 필요한가요?

변경 때문에 예전에 되던 기능이 깨지지 않았는지 확인하는 테스트다. 새 기능 테스트는 바뀐 곳을 보고, 회귀는 손대지 않은 곳을 본다. 작은 수정도 그 코드를 쓰는 다른 곳을 깨뜨릴 수 있어서 필요하다. 버그를 고칠 때마다 그 버그를 재현하는 테스트를 회귀 묶음에 더하는 게 가장 효과가 크다.

### 회귀 테스트가 너무 오래 걸리면 어떻게 하나요?

먼저 느린 테스트를 아래 층으로 내린다. E2E로 확인하던 계산 규칙은 단위 테스트로 충분하다. 그다음 병렬 실행과 샤딩으로 시간을 쪼개고, PR에서는 변경 영향 분석으로 바뀐 파일을 쓰는 테스트만 돌린다. 평소 순서는 위험(가능성 × 영향)으로 정한다. 대신 main 머지 뒤나 밤마다 전체를 돌려 골라 돌리기가 놓친 것을 잡는다.

### 변경 영향 분석으로 테스트를 고르면 무엇을 놓치나요?

의존 그래프(import 관계)에 나타나지 않는 연결을 놓친다. 설정 파일, lockfile, 환경 변수와 기능 플래그, 문자열로 만드는 동적 import, DB 마이그레이션, 다른 서비스가 기대하는 응답 형식이 그렇다. 그래서 그래프 밖의 파일이 바뀌면 전체를 돌리는 규칙을 두고, 고를 테스트가 0개인 결과를 성공으로 보지 않게 한다. 골라 돌리기는 빠른 피드백용이고 전체 실행을 대신하지 않는다.

### 플래키 테스트는 어떻게 다루나요?

같은 커밋에서 성공과 실패가 섞인 기록으로 찾아내고, 필수 검사에서 격리하되 결과는 계속 모은다. 주인과 기한을 정해 원인(실제 시계, 테스트 순서 의존, 공유 자원, 외부 네트워크)을 고친다. 자동 재시도를 쓰더라도 재시도로 통과했다는 사실을 리포트에 남겨야 한다. 그러지 않으면 빨간불을 무시하는 습관이 생겨 진짜 회귀도 재실행 버튼으로 넘어간다.

### 탐색적 테스트는 자동화와 어떻게 나눠 쓰나요?

자동화는 미리 적어 둔 질문을 매번 정확히 다시 묻는 데 강하고, 탐색적 테스트는 아무도 적지 않은 질문을 찾는 데 쓴다. 탐색은 60~90분 세션마다 차터(무엇을, 어떤 수단으로, 무엇을 찾으려고)를 정하고 해 본 것과 발견한 것을 기록한다. 발견한 결함 중 반복 확인할 가치가 있는 것은 자동화된 회귀 테스트로 옮긴다. 반복되는 수동 스크립트 테스트는 탐색이 아니라 자동화 후보다.

### 호환성 테스트의 범위는 어떻게 정하나요?

실제 방문자의 브라우저·기기 비율에서 상위 조합을 고르고, 점유율은 낮아도 깨지면 큰 조합을 더한다. 자동화로는 Playwright처럼 크로미움, 파이어폭스, 웹킷 엔진을 넓게 돌리고, 실제 기기에서만 보이는 문제(iOS 키보드, 저사양 기기 성능)는 핵심 흐름만 실기기로 확인한다. 조합이 많으면 페어와이즈로 줄인다.
