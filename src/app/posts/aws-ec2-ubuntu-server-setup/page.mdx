EC2에 Ubuntu 인스턴스를 하나 띄우고 앱을 올렸다. 일주일 뒤 아침, 서버가 응답하지 않는다. 콘솔에서 시스템 로그를 보니 `Out of memory: Killed process`가 찍혀 있다. 메모리 1GiB짜리 인스턴스에서 배포 때 빌드를 돌리다 메모리가 바닥났고, 스왑이 없으니 커널이 앱을 죽였다. 다시 들어가 보니 루트 디스크는 8GiB 중 7.6GiB가 차 있었다. 로그가 한 번도 돌아가지 않고 쌓인 탓이다. SSH 포트는 첫날 테스트한다고 `0.0.0.0/0`에 열어 둔 그대로였다.

새 서버를 받으면 앱을 올리기 전에 하는 일이 정해져 있다. 하나하나는 어렵지 않은데, 빠뜨린 게 몇 주 뒤 위 장면처럼 한꺼번에 돌아온다. 이 글은 새 EC2 Ubuntu 인스턴스의 첫 한 시간을 순서대로 따라간다. 무엇을 왜 하는지, 확인은 어떻게 하는지, 되돌리는 법은 무엇인지를 함께 적는다.

기준은 Ubuntu 24.04 LTS다. 22.04에서도 명령은 거의 같고, 다른 곳은 그때마다 적었다. RHEL 계열(Amazon Linux 2023 포함)은 `dnf`, `firewalld`, `dnf-automatic`을 쓰는 점이 다르다. 각 주제를 깊게 다룬 글이 따로 있어서 여기서는 첫날 할 일의 범위만 쓰고 링크로 넘긴다. SSH 키와 `sshd_config`는 [SSH 실전](/posts/ssh-in-practice), 유닛 파일과 journalctl은 [systemd와 systemctl](/posts/linux-systemd-systemctl), 보안 그룹은 [보안 그룹과 NACL](/posts/security-groups-nacl), 인증서는 [nginx HTTPS와 성능](/posts/nginx-https-performance)에 있다.

로컬 Ubuntu 24.04 머신에서 직접 돌린 명령은 출력을 그대로 실었다(경로만 줄였다). systemd가 PID 1로 떠 있지 않은 환경이라 `timedatectl`, `systemctl` 출력과 AWS CLI·콘솔 출력은 예시다.

## 띄우기 전에 정하는 것들

인스턴스를 띄우는 화면에서 고르는 몇 가지는 나중에 바꾸기 번거롭다.

키 페어는 ed25519로 만든다. 콘솔에서 만들면 개인 키 파일을 한 번만 받을 수 있다. 이미 쓰는 키가 있으면 공개 키만 가져오기(import)로 올리는 편이 낫다. Ubuntu AMI에서 이 공개 키는 cloud-init이 첫 부팅 때 `ubuntu` 사용자의 `~/.ssh/authorized_keys`에 넣는다. 그래서 첫 접속 계정은 `ubuntu`다(Amazon Linux는 `ec2-user`).

보안 그룹은 22번 포트를 내 IP(`/32`)에만 연다. 더 좋은 건 22번을 아예 열지 않는 것이다. Ubuntu AMI에는 SSM 에이전트가 들어 있어서, 인스턴스에 `AmazonSSMManagedInstanceCore` 정책이 붙은 역할을 주면 Session Manager로 셸에 들어갈 수 있다. 인바운드 포트가 하나도 필요 없고, 누가 언제 들어왔는지 기록도 남는다.

루트 볼륨은 기본 8GiB인 경우가 많다. 로그와 Docker 이미지, 빌드 캐시가 쌓이면 금방 찬다. gp3로 고르고 처음부터 20~30GiB로 잡으면 처음 장면의 디스크 문제를 한참 미룰 수 있다. 메타데이터 옵션에서 IMDSv2를 필수(required)로 둔다. 이건 뒤에서 다시 본다.

마지막으로 종료 방지(termination protection)를 켠다. 콘솔에서 인스턴스를 고르다 잘못 눌러 지우는 사고를 막는다. 중지 방지와는 다른 설정이다.

## 첫 접속과 계정 정리

처음 접속할 때 서버의 호스트 키 지문을 확인하는 법, ed25519 키와 agent는 [SSH 실전](/posts/ssh-in-practice)에서 다뤘다. EC2에서는 콘솔의 "인스턴스 설정 → 시스템 로그 가져오기"에 cloud-init이 찍은 호스트 키 지문이 나오므로 그 값과 비교한다.

`ubuntu` 계정은 비밀번호 없이 sudo를 쓸 수 있는 공용 계정이다. 사람이 여럿이면 각자 계정을 만들고, 누가 무엇을 했는지 `auth.log`에서 가를 수 있게 한다. 사람 관리자 `deploy`와 CI가 접속할 `ci-deploy`를 따로 만들었다.

```bash
# 사람 관리자 계정: 비밀번호 로그인 없이 키로만, sudo 그룹에 넣는다
sudo adduser --disabled-password --gecos "" deploy
sudo usermod -aG sudo deploy
sudo install -d -m 700 -o deploy -g deploy /home/deploy/.ssh
id deploy
```

```text
info: Adding user `deploy' ...
info: Selecting UID/GID from range 1000 to 59999 ...
info: Adding new group `deploy' (1002) ...
info: Adding new user `deploy' (1002) with group `deploy (1002)' ...
info: Creating home directory `/home/deploy' ...
info: Copying files from `/etc/skel' ...
info: Adding new user `deploy' to supplemental / extra groups `users' ...
info: Adding user `deploy' to group `users' ...
uid=1002(deploy) gid=1002(deploy) groups=1002(deploy),27(sudo),100(users)
```

UID가 1002인 건 글을 쓴 머신에 이미 사용자가 둘 있어서다. 새 EC2라면 `ubuntu`가 1000이니 1001부터 받는다. `groups`에 `27(sudo)`가 보이면 sudo 그룹에 들어간 것이다. 그다음 `/home/deploy/.ssh/authorized_keys`에 그 사람의 공개 키를 넣고 권한을 600으로 둔다. 권한이 넓으면 sshd가 키를 무시하는 이유는 [파일 권한](/posts/linux-files-permissions)에 있다.

CI 계정은 sudo 그룹에 넣지 않는다. 배포에 필요한 명령 몇 개만 허락하는 sudoers 파일을 따로 둔다. sudoers는 문법이 틀리면 sudo 자체가 안 될 수 있어서, 반드시 `visudo -c`로 검사한 뒤 넣는다.

```bash
# 허락할 명령만 적은 파일을 만들고 문법부터 검사한다
echo 'ci-deploy ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart shop-api, /usr/bin/journalctl -u shop-api *' > sudoers-ci-deploy
visudo -cf sudoers-ci-deploy
# 콜론 하나를 빠뜨린 파일
echo 'ci-deploy ALL=(ALL) NOPASSWD /usr/bin/systemctl' > bad-sudoers
visudo -cf bad-sudoers; echo "exit=$?"
```

```text
sudoers-ci-deploy: parsed OK
bad-sudoers:1:48: syntax error
ci-deploy ALL=(ALL) NOPASSWD /usr/bin/systemctl
                                               ^
exit=1
```

`NOPASSWD` 뒤의 콜론 하나가 빠지면 문법 오류다. 이 파일을 `/etc/sudoers.d/`에 그대로 넣었다면 sudo가 설정을 읽다 실패한다. 그러면 `ubuntu` 계정의 sudo까지 막혀서, 고치려면 SSM이나 볼륨을 떼어 다른 인스턴스에 붙이는 수밖에 없다. 검사를 통과한 파일만 권한 440으로 넣는다.

파일을 넣고 실제로 무엇이 허락되는지 본다.

```bash
sudo install -m 440 sudoers-ci-deploy /etc/sudoers.d/ci-deploy
sudo -l -U ci-deploy
# 허락하지 않은 명령은 비밀번호를 물어보다(-n이라 바로) 거절된다
sudo -u ci-deploy sudo -n /usr/bin/systemctl stop shop-api
```

```text
User ci-deploy may run the following commands on vm:
    (ALL) NOPASSWD: /usr/bin/systemctl restart shop-api, /usr/bin/journalctl -u shop-api *
sudo: a password is required
```

`restart`는 되고 `stop`은 안 된다. CI 계정의 키가 새어도 할 수 있는 일은 그 서비스를 재시작하고 로그를 보는 것뿐이다. 계정을 정리했으면 [SSH 실전](/posts/ssh-in-practice)의 "sshd_config를 단단하게"대로 비밀번호 로그인과 root 로그인을 끈다. 새 계정으로 다른 터미널에서 접속이 되는 걸 확인한 뒤에 기존 세션을 닫는다.

## 보안 패치는 매일 저절로

Ubuntu 서버 이미지는 보안 업데이트를 자동으로 까는 `unattended-upgrades`가 처음부터 켜져 있다. 켜져 있는지, 무엇을 까는지 확인만 하면 된다.

```bash
# 매일 목록을 받고(1) 자동 업그레이드를 돌린다(1)
cat /etc/apt/apt.conf.d/20auto-upgrades
# 어느 저장소의 업데이트를 자동으로 깔지
sed -n 6,18p /etc/apt/apt.conf.d/50unattended-upgrades
```

```text
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";
Unattended-Upgrade::Allowed-Origins {
	"${distro_id}:${distro_codename}";
	"${distro_id}:${distro_codename}-security";
	// Extended Security Maintenance; doesn't necessarily exist for
	// every release and this system may not have it installed, but if
	// available, the policy for updates is such that unattended-upgrades
	// should also install from here by default.
	"${distro_id}ESMApps:${distro_codename}-apps-security";
	"${distro_id}ESM:${distro_codename}-infra-security";
//	"${distro_id}:${distro_codename}-updates";
//	"${distro_id}:${distro_codename}-proposed";
//	"${distro_id}:${distro_codename}-backports";
};
```

기본값은 `-security`(와 ESM 보안 저장소)만 자동으로 깐다. `-updates`는 주석이다. 버그 수정 업데이트까지 자동으로 깔면 예고 없이 동작이 바뀔 수 있어서, 그건 사람이 정한 시간에 한다. 실제로 어떻게 판단하는지는 dry-run으로 본다.

```bash
sudo unattended-upgrade --dry-run -v
```

```text
Starting unattended upgrades script
Allowed origins are: o=Ubuntu,a=noble, o=Ubuntu,a=noble-security, o=UbuntuESMApps,a=noble-apps-security, o=UbuntuESM,a=noble-infra-security
Initial blacklist: 
Initial whitelist (not strict): 
```

`a=noble-security`처럼 코드네임으로 풀린 값이 보인다. 22.04라면 `jammy`다. 글을 쓴 머신은 패키지 목록이 오래돼서 이 뒤에 다운로드 404가 났는데, 실제 서버에서는 매일 `apt-daily.timer`가 목록을 새로 받으니 그런 일이 없다. 지금 깔 것이 얼마나 쌓였는지는 시뮬레이션으로 센다.

```bash
# 실제로 깔지 않고(-s) 무엇이 올라갈지만 본다
apt-get -s upgrade | grep -E "upgraded,"
```

```text
50 upgraded, 0 newly installed, 0 to remove and 0 not upgraded.
```

남은 결정은 재부팅이다. 커널이나 glibc 같은 패키지는 깔아도 재부팅하기 전까지 예전 것이 돈다. 업데이트가 재부팅을 원하면 `/var/run/reboot-required` 파일이 생긴다. `50unattended-upgrades`의 `Automatic-Reboot`는 기본이 꺼져 있다. 서버 한 대에 서비스가 하나뿐이면 자동 재부팅이 곧 장애다. 로드 밸런서 뒤에 여러 대가 있으면 `Automatic-Reboot "true"`와 `Automatic-Reboot-Time "04:00"`을 켜고 인스턴스마다 시각을 엇갈리게 두는 방법도 있다. 한 대뿐이면 꺼 두고, 그 파일이 생겼는지를 모니터링에 걸어 정한 시간에 사람이 재부팅한다.

## 시간대는 UTC로 두고 읽을 때 바꾼다

EC2의 Ubuntu 이미지는 시간대가 UTC다. 한국 시간으로 바꾸고 싶어지지만, 서버는 UTC로 두는 편이 낫다. 여러 서버와 클라우드 서비스(CloudWatch, 로드 밸런서 로그)의 시각이 모두 UTC라 장애 때 로그를 맞춰 보기 쉽고, 서머타임이 있는 지역의 서버와 섞여도 시간이 건너뛰지 않는다.

```bash
# 지금 시간대와 그 시간을 한국 시간으로 읽기
ls -l /etc/localtime
date
TZ=Asia/Seoul date
```

```text
lrwxrwxrwx 1 root root 27 Oct  3 05:36 /etc/localtime -> /usr/share/zoneinfo/Etc/UTC
Thu Oct 22 03:30:43 UTC 2026
Thu Oct 22 12:30:43 KST 2026
```

사람이 읽을 때만 `TZ=Asia/Seoul`을 붙인다. 앱 로그에는 `2026-10-22T03:30:43Z`처럼 시간대가 붙은 ISO 8601 형식을 쓴다. 꼭 바꿔야 한다면 `sudo timedatectl set-timezone Asia/Seoul`이다. 시간 동기화는 systemd-timesyncd나 chrony가 맡는다(이미지와 버전에 따라 다르다). EC2에서는 어느 쪽이든 Amazon Time Sync Service(169.254.169.123)를 쓰게 맞춘다. `timedatectl` 출력에서 이 줄을 본다(예시).

```text
               Local time: Thu 2026-10-22 03:30:43 UTC
           Universal time: Thu 2026-10-22 03:30:43 UTC
                 RTC time: Thu 2026-10-22 03:30:43
                Time zone: Etc/UTC (UTC, +0000)
System clock synchronized: yes
              NTP service: active
          RTC in local TZ: no
```

`System clock synchronized: no`가 오래 이어지면 아웃바운드 규칙이나 chrony 설정을 본다. 시계가 틀어지면 TLS 인증서 검증과 AWS API 서명(요청 시각이 크게 어긋나면 거절된다)이 실패한다.

## 메모리 1GiB 서버에는 스왑을 둔다

EC2 Ubuntu 이미지에는 스왑이 없다. t3.micro나 t4g.small처럼 메모리가 작은 인스턴스에서 배포 중에 `npm ci`나 Gradle 빌드를 돌리면 잠깐 메모리가 튀고, 갈 곳이 없으면 커널의 OOM killer가 가장 큰 프로세스를 죽인다. 대개 그게 앱이다. 처음 장면이 이것이다.

아래 그림은 메모리가 차오를 때 스왑이 있고 없음에 따라 무엇이 달라지는지 보여 준다.

스왑 파일을 만드는 순서다. 글에서는 64MiB로 만들었지만 1GiB 인스턴스라면 1~2GiB가 흔하다.

```bash
# 스왑 전 상태
free -h
# 파일을 만들고 root만 읽게 한 뒤 스왑 영역으로 만든다
sudo fallocate -l 64M /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
swapon --show
```

```text
               total        used        free      shared  buff/cache   available
Mem:            15Gi       2.9Gi       6.9Gi        14Mi       6.3Gi        12Gi
Swap:             0B          0B          0B
Setting up swapspace version 1, size = 64 MiB (67104768 bytes)
no label, UUID=c6d06a79-8261-4d03-87db-fdb124326a37
NAME      TYPE SIZE USED PRIO
/swapfile file  64M   0B   -2
```

처음 `free -h`의 `Swap: 0B`가 출발점이다. `swapon --show`에 파일이 보이면 켜진 것이다. 이대로는 재부팅하면 사라지니 `/etc/fstab`에 한 줄을 더한다.

```bash
# 재부팅 뒤에도 켜지게 한다
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
# 스왑을 얼마나 적극적으로 쓸지 (기본 60)
sysctl vm.swappiness
```

```text
vm.swappiness = 60
```

서버에서는 이 값을 10 정도로 낮춰 메모리가 정말 부족할 때만 스왑을 쓰게 하는 경우가 많다(`/etc/sysctl.d/99-swap.conf`에 `vm.swappiness=10`). 스왑은 응급 처치다. 스왑 사용량이 계속 늘어 있다면 인스턴스가 작은 것이니 크기를 올린다. 되돌릴 때는 `sudo swapoff /swapfile` 뒤 파일을 지우고 fstab 줄을 뺀다. 켜진 스왑 파일은 지워지지 않는다. 글을 쓰면서 `swapoff` 없이 지우려다 `Operation not permitted`를 봤다.

## ufw는 켜기 전에 SSH부터 연다

보안 그룹이 있는데 ufw까지 켜야 하나는 자주 나오는 질문이다. 보안 그룹은 인스턴스 밖에서, ufw는 OS 안에서 막는다. 보안 그룹은 누가 콘솔에서 규칙 하나를 넓히면 바로 무너지고, ufw는 OS 안의 프로세스가 엉뚱한 포트를 열었을 때 막아 준다. 한 겹만 둔다면 보안 그룹이 우선이다. 두 겹을 두면 규칙을 두 곳에서 관리해야 하니, 장애 때 "보안 그룹은 열었는데 왜 안 되지"를 겪지 않게 팀에서 정해 둔다.

ufw는 iptables(최근에는 nftables 백엔드) 규칙을 만들어 주는 도구다. iptables 자체는 [iptables 기본](/posts/iptables-basics)에 있다. Ubuntu에는 깔려 있지만 꺼져 있다.

```bash
sudo ufw status
sudo ufw app list
```

```text
Status: inactive
Available applications:
  Nginx Full
  Nginx HTTP
  Nginx HTTPS
  Turnserver
  iperf3
```

글을 쓴 머신에는 openssh-server가 없어서 목록에 `OpenSSH`가 없다. EC2 인스턴스에는 있으니 `OpenSSH`가 보여야 한다. 규칙이 실제로 어떤 iptables 줄이 되는지는 `--dry-run`으로 바꾸지 않고 볼 수 있다.

```bash
# 22번을 허용하면 어떤 규칙이 생기는지 (적용하지 않는다)
sudo ufw --dry-run allow 22/tcp | grep -E "^-A ufw-user-input"
# limit은 30초에 6번 넘게 새로 접속하는 IP를 막는다
sudo ufw --dry-run limit 22/tcp | grep -E "^-A ufw-user-input"
```

```text
-A ufw-user-input -p tcp --dport 22 -j ACCEPT
-A ufw-user-input -p tcp --dport 22 -m conntrack --ctstate NEW -m recent --set
-A ufw-user-input -p tcp --dport 22 -m conntrack --ctstate NEW -m recent --update --seconds 30 --hitcount 6 -j ufw-user-limit
-A ufw-user-input -p tcp --dport 22 -j ufw-user-limit-accept
```

`limit`의 두 번째 줄을 보면 `--seconds 30 --hitcount 6`이다. 30초 안에 새 연결이 6번째가 되면 막는다. 무차별 대입을 늦추는 데는 쓸모가 있지만, 배포 스크립트가 SSH를 짧게 여러 번 여는 경우 스스로 막힐 수 있다.

<Callout kind="warning" title="원격 서버에서 ufw enable 전에 SSH 허용부터">
ufw의 기본 인바운드 정책은 거부다. SSH 허용 규칙 없이 `sudo ufw enable`을 치면 지금 세션은 conntrack 덕분에 잠시 살아 있어도 새 접속이 모두 막힌다. 순서는 `sudo ufw allow OpenSSH` → `sudo ufw allow 'Nginx Full'` → `sudo ufw enable` → 다른 터미널에서 새로 접속해 확인이다. 막혔다면 Session Manager나 EC2 직렬 콘솔로 들어가 `sudo ufw disable`로 되돌린다. 둘 다 미리 쓸 수 있게 해 두지 않았다면, 볼륨을 떼어 다른 인스턴스에서 `/etc/ufw/ufw.conf`의 `ENABLED=yes`를 고쳐야 한다.
</Callout>

## 앱은 systemd 서비스로 띄운다

`nohup java -jar app.jar &`로 띄운 앱은 죽어도 다시 뜨지 않고, 재부팅하면 사라진다. 유닛 파일 한 장으로 바꾼다. 유닛 파일의 각 항목과 `enable`, `daemon-reload`, 재시작 한도는 [systemd와 systemctl](/posts/linux-systemd-systemctl)에서 자세히 다뤘다. 여기서는 EC2 첫날에 쓰는 모양만 둔다.

```ini
# /etc/systemd/system/shop-api.service
[Unit]
Description=shop-api
After=network-online.target
Wants=network-online.target

[Service]
User=deploy
WorkingDirectory=/opt/shop-api
EnvironmentFile=-/etc/shop-api/env
ExecStart=/opt/shop-api/run.sh
Restart=on-failure
RestartSec=3
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/log/shop-api

[Install]
WantedBy=multi-user.target
```

`ProtectSystem=strict`는 `/usr`, `/etc`를 포함한 파일 시스템 전체를 이 서비스에 읽기 전용으로 보이게 한다. 쓸 곳은 `ReadWritePaths`로만 연다. 앱이 뚫려도 시스템 파일을 고치지 못한다. 비밀값은 유닛 파일에 적지 않고 `EnvironmentFile`(권한 600)로 뺀다. 파일을 넣기 전에 문법을 검사한다.

```bash
# 유닛 파일 문법 검사 (systemd를 건드리지 않는다)
systemd-analyze verify ./shop-api.service
# Restart 값에 오타를 낸 파일
systemd-analyze verify ./bad.service
```

```text
./bad.service:11: Failed to parse service restart specifier, ignoring: on-fail
```

정상 파일은 아무것도 찍지 않고 끝난다. 오타 난 파일은 `ignoring`이라고 한다. 오류로 멈추지 않고 그 줄을 무시한다는 뜻이라, 검사하지 않으면 재시작 설정이 없는 서비스가 조용히 만들어진다. 그다음은 `sudo systemctl daemon-reload`, `sudo systemctl enable --now shop-api`, `systemctl status shop-api`로 확인한다.

## nginx를 앞에 두고 인증서를 붙인다

앱은 `127.0.0.1:8080`에만 묶고 바깥에는 nginx가 443으로 선다. 리버스 프록시 설정과 헤더는 [nginx 리버스 프록시](/posts/nginx-reverse-proxy)에 있다. 첫날 확인할 것은 설정 검사를 습관으로 만드는 것이다.

```bash
# 설정을 바꿀 때마다 reload 전에 검사한다
sudo nginx -t
```

```text
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```

`proxy_pass` 줄 끝의 세미콜론을 하나 지우면 이렇게 된다.

```text
2026/10/22 03:31:27 [emerg] 17921#17921: invalid number of arguments in "proxy_pass" directive in /etc/nginx/nginx.conf:11
nginx: configuration file /etc/nginx/nginx.conf test failed
```

세미콜론이 없으니 다음 줄까지 한 지시어로 읽혀 인자 개수가 틀렸다는 메시지가 나온다. 메시지가 가리킨 11번 줄은 다음 줄인 `proxy_set_header`이고, 고칠 곳은 그 위 10번 줄이다. 줄 번호가 하나씩 어긋날 수 있다. 검사가 실패하면 reload하지 않으니 지금 돌고 있는 nginx는 예전 설정으로 계속 산다. `nginx -t` 없이 `restart`를 하면 그 nginx가 내려가고 다시 뜨지 못한다.

인증서는 도메인의 A 레코드를 Elastic IP로 걸어 둔 뒤 certbot으로 받는다. Elastic IP를 쓰는 이유는 인스턴스를 중지했다 켜면 퍼블릭 IP가 바뀌기 때문이다. certbot 설치와 자동 갱신 확인은 [nginx HTTPS와 성능](/posts/nginx-https-performance)의 첫 절을 그대로 따른다. 보안 그룹에 80번이 열려 있어야 HTTP-01 검증이 통과한다. 443만 열어 두고 인증서 발급이 실패하는 경우가 흔하다.

## 로그가 디스크를 채우지 않게

처음 장면의 디스크는 앱 로그로 찼다. 로그는 두 곳에 쌓인다. systemd 서비스의 표준 출력은 journald로 가고, 앱이 직접 쓰는 파일은 그 파일에 쌓인다. journald는 기본으로 디스크의 일정 비율까지만 쓰지만(`journalctl --disk-usage`로 확인), 앱이 직접 쓰는 파일은 누군가 잘라 주지 않으면 끝없이 커진다. 그 일을 logrotate가 한다.

```bash
# /etc/logrotate.d/shop-api
sudo tee /etc/logrotate.d/shop-api > /dev/null <<'EOF'
/var/log/shop-api/*.log {
    daily
    rotate 14
    maxsize 100M
    missingok
    notifempty
    compress
    delaycompress
    copytruncate
}
EOF
# -d: 실제로 하지 않고 판단만 출력한다
sudo logrotate -d /etc/logrotate.d/shop-api
```

```text
rotating pattern: /var/log/shop-api/*.log  after 1 days (14 rotations)
empty log files are not rotated, log files >= 104857600 are rotated earlier, old logs are removed
considering log /var/log/shop-api/app.log
Creating new state
  Now: 2026-10-22 03:31
  Last rotated at 2026-10-22 03:00
  log does not need rotating (log has already been rotated)
```

`-d`는 상태 파일이 없을 때 오늘 이미 돌린 것으로 보고 "rotating 필요 없음"이라고 한다. 처음 검사할 때 이 줄 때문에 설정이 틀렸다고 오해하기 쉽다. 실제로 돌려 보려면 `-f`로 강제한다. 두 번 돌린 결과다.

```bash
sudo logrotate -f /etc/logrotate.d/shop-api; ls -l /var/log/shop-api
```

```text
-rw-r--r-- 1 root root      0 Oct 22 03:31 app.log
-rw-r--r-- 1 root root 508894 Oct 22 03:31 app.log.1
```

```text
-rw-r--r-- 1 root root     0 Oct 22 03:31 app.log
-rw-r--r-- 1 root root  9892 Oct 22 03:31 app.log.1
-rw-r--r-- 1 root root 52594 Oct 22 03:31 app.log.2.gz
```

첫 회전에서 `app.log.1`은 압축되지 않았다. `delaycompress`가 바로 직전 파일은 다음 회전 때 압축하게 미루기 때문이다. 두 번째 회전에서 그 파일이 `app.log.2.gz`가 되면서 508,894바이트가 52,594바이트로 줄었다. 같은 줄이 반복되는 로그라 압축이 특히 잘 됐다. `copytruncate`는 앱이 파일을 계속 열고 있어도 되게 복사한 뒤 원본을 비운다. 복사와 비우기 사이에 쓴 몇 줄은 잃을 수 있다. 앱이 재오픈 신호(`USR1` 같은)를 지원하면 `postrotate`에서 그 신호를 보내는 쪽이 정확하다. `maxsize 100M`은 하루가 지나지 않아도 100MB를 넘으면 다음 logrotate 실행 때 돌린다. logrotate는 하루에 한 번 도니, 하루 안에 디스크를 채울 만큼 로그가 쏟아지는 앱이라면 이것만으로는 못 막는다. 그때는 로그 수준을 낮추고 로그를 서버 밖으로 보낸다.

## 서버 밖에서 지켜보고, 서버 밖에 남긴다

EC2 기본 지표에는 CPU와 네트워크, 디스크 I/O는 있지만 메모리 사용률과 디스크 사용률이 없다. 하이퍼바이저 밖에서는 OS 안을 볼 수 없기 때문이다. 처음 장면의 두 문제(메모리, 디스크)가 정확히 기본 지표에 없는 것들이다. CloudWatch 에이전트를 깔아 `mem_used_percent`, `disk_used_percent`를 보내고, 디스크 80%·메모리 90%에 알람을 건다. 에이전트 설정은 이런 모양이다(예시).

```json
{
  "metrics": {
    "append_dimensions": { "InstanceId": "${aws:InstanceId}" },
    "metrics_collected": {
      "mem": { "measurement": ["mem_used_percent"] },
      "disk": { "measurement": ["used_percent"], "resources": ["/"] }
    }
  },
  "logs": {
    "logs_collected": {
```

IMDSv1은 GET 한 번에 자격 증명이 나와서, 앱에 SSRF 취약점이 있으면 공격자가 그 키를 가져갈 수 있었다. 자세한 공격 경로는 [SSRF](/posts/ssrf)에 있다. 인스턴스 안에서 Docker를 돌리고 컨테이너가 IMDS에 닿아야 한다면 hop limit을 2로 올려야 하는데, 그건 컨테이너에도 자격 증명을 허락하는 일이라 필요한지 먼저 따진다.

마지막은 되돌릴 수 있는 지점을 만드는 일이다. 첫날 설정이 끝나면 그 상태로 AMI를 만들어 둔다. 같은 서버를 다시 만들 때 이 한 시간을 건너뛸 수 있다. 데이터가 바뀌는 볼륨은 AWS Backup이나 Data Lifecycle Manager로 EBS 스냅샷을 정기적으로 뜬다(예시).

```bash
# 첫날 설정을 마친 상태를 이미지로 남긴다
aws ec2 create-image --instance-id i-0abc1234def567890 --name "shop-api-base-2026-10-26"
```

`--no-reboot`를 붙이면 서비스를 멈추지 않지만, 쓰는 중이던 파일이 깨진 채로 찍힐 수 있다. 첫날 이미지는 재부팅을 감수하고 만든다. 그리고 이 한 시간을 손으로 반복하지 않게, 지금까지 친 명령을 cloud-init user-data나 Ansible, 또는 Packer로 만든 AMI로 옮긴다. 두 번째 서버부터는 같은 결과가 나와야 하기 때문이다.

## 다시 그 아침의 서버

처음 장면의 서버에 빠져 있던 건 세 가지였다. 스왑이 없어 빌드 한 번에 앱이 OOM으로 죽었고, logrotate가 없어 로그가 루트 디스크를 채웠고, 테스트로 연 22번이 세상에 열려 있었다. 셋 다 기본 지표로는 보이지 않았다. 첫 한 시간의 일은 결국 이 세 갈래다. 들어오는 길을 좁히고(보안 그룹·ufw·계정), 저절로 돌아가게 하고(패치·systemd·logrotate), 밖에서 보이게 한다(CloudWatch 에이전트·알람·AMI). 앱은 그다음에 올린다.

## 면접에서 나올 만한 질문

### 새 EC2 Ubuntu 서버를 받으면 무엇부터 하나요?

들어오는 길부터 좁힌다. 보안 그룹의 22번을 내 IP로 좁히거나 Session Manager로 바꾸고, 사람마다 계정을 만들고 비밀번호·root 로그인을 끈다. 그다음 unattended-upgrades가 보안 업데이트를 받는지, 시간 동기화가 되는지 확인하고, 작은 인스턴스면 스왑을 만든다. 앱은 systemd 서비스로 띄우고 nginx 뒤에 둔 뒤, logrotate와 CloudWatch 에이전트로 디스크와 메모리를 밖에서 보이게 한다.

### 보안 그룹이 있는데 ufw도 켜야 하나요?

보안 그룹은 인스턴스 밖, ufw는 OS 안에서 막는다. 보안 그룹이 우선이고, ufw는 누가 보안 그룹을 넓히거나 OS의 프로세스가 엉뚱한 포트를 열었을 때를 위한 두 번째 겹이다. 두 겹을 두면 관리할 곳이 둘이 되니 팀이 정하고, 켤 때는 SSH 허용 규칙을 먼저 넣는다.

### unattended-upgrades는 무엇을 자동으로 깔고, 재부팅은 어떻게 하나요?

Ubuntu 기본값은 `-security`와 ESM 보안 저장소의 업데이트만 매일 자동으로 깔고, 버그 수정용 `-updates`는 깔지 않는다. 커널처럼 재부팅이 필요한 업데이트는 `/var/run/reboot-required` 파일을 남긴다. 자동 재부팅은 기본으로 꺼져 있는데, 서버가 여러 대면 시각을 엇갈려 켜고, 한 대뿐이면 그 파일을 모니터링해 정한 시간에 재부팅한다.

### 작은 인스턴스에서 앱이 갑자기 죽고 로그에 Out of memory가 있습니다. 무엇을 하나요?

OOM killer가 메모리를 가장 많이 쓰는 프로세스를 죽인 것이다. 무엇이 메모리를 튀게 했는지(배포 중 빌드, 메모리 누수) 보고, 응급으로 스왑 파일을 만들어 순간적인 초과를 받아 낸다. 근본적으로는 빌드를 CI로 옮기고, 스왑 사용량이 계속 높으면 인스턴스 크기를 올린다.

### sudoers 파일을 고칠 때 visudo를 쓰는 이유는요?

sudoers는 문법이 틀리면 sudo가 설정을 읽지 못해 관리자 권한 자체를 잃을 수 있다. `visudo -c`(파일은 `-cf`)로 문법을 먼저 검사하고, 통과한 파일만 `/etc/sudoers.d/`에 440 권한으로 넣는다. CI 계정은 sudo 그룹에 넣지 않고 필요한 명령만 인자까지 적어 허락한다.

### EC2에서 IMDSv2를 필수로 두는 이유는 무엇인가요?

IMDSv1은 GET 한 번으로 인스턴스 역할의 임시 자격 증명을 돌려줘서, 앱의 SSRF 취약점 하나로 키가 새어 나갈 수 있었다. IMDSv2는 먼저 PUT으로 세션 토큰을 받고 그 토큰을 헤더에 붙여야 해서 단순 SSRF로는 어렵고, hop limit으로 인스턴스 밖으로 토큰이 나가는 것도 막는다.

### 서버 시간대를 KST로 바꾸지 않는 이유는요?

클라우드 서비스와 다른 서버의 로그가 모두 UTC라 장애 때 시각을 맞춰 보기 쉽고, 서머타임이 있는 지역과 섞여도 시간이 건너뛰지 않기 때문이다. 앱 로그는 시간대가 붙은 ISO 8601로 쓰고, 사람이 읽을 때만 `TZ=Asia/Seoul`로 바꿔 본다.

### logrotate의 copytruncate는 언제 쓰고 무엇을 조심하나요?

앱이 로그 파일을 계속 열어 두고 재오픈 신호를 지원하지 않을 때 쓴다. 파일을 복사한 뒤 원본을 비우는 방식이라, 그 사이에 쓴 몇 줄은 잃을 수 있다. 앱이 재오픈 신호를 지원하면 `create`와 `postrotate`에서 신호를 보내는 방식이 더 정확하다.
