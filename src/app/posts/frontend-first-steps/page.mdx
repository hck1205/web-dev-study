물 마신 횟수를 세는 페이지를 만들고 싶었다. 버튼 하나, 숫자 하나. 처음엔 HTML 파일 하나에 다 넣었다. `<button onclick="...">` 안에 코드를 적고, `style` 속성에 색을 적었다. 돌아가긴 했다. 그런데 버튼을 하나 더 만들려니 같은 색과 같은 코드를 또 복사해야 했고, 스크립트를 `<head>`로 옮기자 버튼을 눌러도 아무 일이 없었다. 콘솔에는 `Cannot read properties of null (reading 'addEventListener')`가 찍혀 있었다.

이 글은 이 작은 페이지 하나로 프런트엔드의 첫 바퀴를 돈다. 같은 버튼을 HTML, CSS, 자바스크립트가 어떻게 나눠 맡는지, 브라우저가 세 파일을 어떤 순서로 읽는지, 그리고 왜 결국 npm으로 도구를 들이고 React로 넘어가게 되는지까지 간다. 각 단계마다 더 깊이 들어가는 글이 따로 있어서, 여기서는 지도를 그리고 다리를 놓는 데 집중한다.

## 버튼 하나를 세 파일로 나눈다

먼저 완성된 모습부터 보자. 파일은 세 개다.

```text
water/
├── index.html   무엇이 있는가
├── style.css    어떻게 보이는가
└── main.js      누르면 무엇이 일어나는가
```

`index.html`은 페이지의 뼈대다.

```html
<!doctype html>
<html lang="ko">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>오늘 마신 물</title>
    <link rel="stylesheet" href="style.css" />
    <script src="main.js" defer></script>
  </head>
  <body>
    <main>
      <h1>오늘 마신 물</h1>
      <p id="count" aria-live="polite">0잔</p>
      <button type="button" id="add">한 잔 더</button>
    </main>
  </body>
</html>
```

`style.css`는 모양을 정한다.

```css
/* 버튼을 손가락으로 누르기 좋은 크기로 */
button {
  min-height: 44px;
  padding: 0 1.25rem;
  border: 0;
  border-radius: 999px;
  background: #2563eb;
  color: white;
  font-size: 1rem;
}

/* 눌렀을 때 살짝 들어가는 느낌 */
button:active {
  transform: scale(0.97);
}
```

`main.js`는 동작을 붙인다.

```js
const button = document.querySelector("#add");
const output = document.querySelector("#count");
let count = 0;

button.addEventListener("click", () => {
  count += 1;
  output.textContent = `${count}잔`;
});
```

세 파일 모두 같은 버튼 이야기를 하지만 말하는 내용이 다르다. HTML은 "여기에 버튼이 있다", CSS는 "그 버튼은 파랗고 둥글다", 자바스크립트는 "누르면 숫자를 하나 올린다"를 말한다. 아래 그림은 버튼 하나에 세 언어가 어떻게 걸려 있는지 보여 준다. 화살표를 따라 흐르는 점이 각 파일이 버튼에 무엇을 보태는지 가리킨다.

### HTML은 모양이 아니라 의미를 적는다

`<button>`을 쓴 이유가 있다. `<div>`에 클릭 이벤트를 달아도 마우스로는 눌린다. 하지만 키보드 Tab으로 가지 않고, Enter나 Space로 눌리지 않으며, 스크린 리더는 그냥 글자로 읽는다. `<button>`은 이런 것들을 브라우저가 기본으로 해 준다. HTML 태그를 고르는 일은 "이게 무슨 물건인가"를 브라우저에게 알려 주는 일이다.

`type="button"`도 습관처럼 붙인다. 버튼이 `<form>` 안에 들어가면 기본 `type`이 `submit`이라 누르는 순간 페이지가 새로고침된다. 나도 처음에 숫자가 1이 됐다가 바로 0으로 돌아가서 한참 헤맸다.

`aria-live="polite"`는 숫자가 바뀌었을 때 스크린 리더가 새 값을 읽어 주게 한다. 눈으로 보는 사람은 숫자가 바뀐 걸 바로 알지만, 화면을 듣는 사람에게는 이 한 줄이 없으면 아무 일도 없었던 것과 같다. 태그를 의미에 맞게 고르는 이야기는 [시맨틱 HTML 글](/posts/html-semantics)에서 자세히 다룬다.

### CSS는 선택자로 HTML을 가리킨다

CSS 파일에는 HTML이 한 줄도 없다. 대신 `button`이라는 선택자로 "이 문서의 모든 버튼"을 가리킨다. 이 간접 연결 덕분에 버튼을 열 개 만들어도 CSS는 그대로다. 색을 바꾸고 싶으면 CSS 한 곳만 고치면 된다.

반대로 `style="background: blue"`처럼 HTML 안에 직접 적은 스타일은 그 요소 하나에만 붙고, 선택자로 쓴 규칙보다 우선순위가 높아서 나중에 CSS 파일로 덮어쓰기 어렵다. 왜 어떤 규칙이 이기는지는 [캐스케이드와 명시도 글](/posts/css-cascade-specificity), 요소가 차지하는 크기와 간격은 [박스 모델 글](/posts/css-box-model-layout), 여러 요소를 줄 세우는 법은 [Flexbox와 Grid 글](/posts/css-flexbox-grid)로 이어진다.

`min-height: 44px`는 손가락으로 누를 때 빗나가지 않는 최소 크기다. 모바일에서 버튼이 작으면 옆 버튼을 누르는 일이 잦다.

### 자바스크립트는 DOM을 찾아서 바꾼다

`document.querySelector("#add")`는 HTML에서 `id="add"`인 요소를 찾는다. 정확히는 HTML 글자가 아니라 브라우저가 HTML을 읽어 만든 객체 나무, DOM에서 찾는다. 찾은 요소에 `addEventListener("click", ...)`로 "눌리면 이 함수를 불러 달라"고 맡겨 둔다.

함수 안에서 하는 일은 두 가지다. `count`라는 변수를 하나 올리고, 화면의 글자를 새 값으로 바꾼다. 여기서 눈여겨볼 점이 있다. 숫자는 변수에 있고, 화면은 그 숫자를 보여 줄 뿐이다. 변수를 올리고 화면을 고치는 두 줄 중 하나라도 빠지면 둘이 어긋난다. 이 어긋남이 뒤에서 React로 넘어가는 이유가 된다.

DOM을 찾고 바꾸는 방법은 [DOM 기초 글](/posts/dom-basics)에서, 버튼이 여러 개일 때 이벤트를 하나로 받는 법은 [이벤트 위임 글](/posts/event-delegation)에서 이어서 본다.

## 왜 세 파일로 나누나

한 파일에 다 넣어도 브라우저는 상관하지 않는다. 나누는 건 사람을 위해서다. 이걸 관심사 분리라고 부른다. 바뀌는 이유가 다른 것끼리 떼어 두는 것이다.

디자이너가 버튼 색을 바꾸자고 하면 `style.css`만 열면 된다. 숫자를 한 번에 두 잔씩 올리자고 하면 `main.js`만 고친다. 버튼 문구를 바꾸면 `index.html`이다. 한 파일에 섞여 있으면 색 하나 바꾸다가 실수로 코드를 지우는 일이 생긴다.

나눠 두면 다시 쓰기도 쉽다. `style.css`를 다른 페이지에서도 불러오면 그 페이지의 버튼도 같은 모양이 된다. 브라우저는 한 번 받은 CSS 파일을 캐시에 넣어 두니, 페이지를 옮겨 다닐 때 다시 받지 않아도 된다.

다만 이 구분은 "언어별로 나눈다"가 정답이라는 뜻은 아니다. React를 쓰면 HTML처럼 생긴 JSX와 동작 코드가 한 파일에 들어간다. 이때는 "버튼 컴포넌트", "목록 컴포넌트"처럼 화면 조각별로 나눈다. 관심사를 언어로 자를지 기능으로 자를지가 바뀐 것뿐이지, 바뀌는 이유가 다른 것을 떼어 둔다는 생각은 같다.

## 브라우저가 세 파일을 읽는 순서

처음 장면의 오류로 돌아가자. 스크립트를 `<head>`로 옮겼더니 `null`에서 `addEventListener`를 읽을 수 없다고 했다. 이건 순서 문제다.

브라우저는 HTML을 위에서부터 한 줄씩 읽으며 DOM을 만든다. 평범한 `<script src="main.js">`를 만나면 읽기를 멈추고, 파일을 받아서 실행한 다음에야 아래로 내려간다. 스크립트가 `<head>`에 있으면 실행되는 순간에는 `<body>`를 아직 읽지 않았다. `#add` 버튼이 DOM에 없으니 `querySelector`가 `null`을 돌려준다.

아래 그림에서 다음을 누르며 `defer`를 붙인 우리 페이지가 열리는 과정을 따라가 보자. 주목할 곳은 `main.js`를 받는 동안에도 파서가 멈추지 않는다는 점, 그리고 스크립트가 맨 마지막에 실행된다는 점이다.

스크립트를 둘 자리는 세 가지가 흔하다.

```html
<!-- 1. body 맨 끝: 오래된 방법. DOM이 이미 있으니 동작은 하지만 HTML을 다 읽은 뒤에야 받기 시작한다 -->
<body>
  ...
  <script src="main.js"></script>
</body>

<!-- 2. head + defer: 받는 건 일찍, 실행은 DOM이 다 만들어진 뒤. 여러 개면 적힌 순서대로 -->
<script src="main.js" defer></script>

<!-- 3. head + async: 받는 대로 바로 실행. 순서를 믿을 수 없다 -->
<script src="analytics.js" async></script>
```

내 코드처럼 DOM을 만지는 스크립트는 `defer`가 맞다. `async`는 다 받은 순간 실행하니 DOM이 덜 만들어졌을 수 있고, 두 파일이 있으면 먼저 도착한 쪽부터 실행된다. 방문자 통계처럼 다른 코드와 상관없이 혼자 도는 스크립트에만 쓴다. `type="module"`로 불러온 스크립트는 따로 적지 않아도 `defer`처럼 동작한다.

이 순서가 첫 화면 시간에 어떻게 영향을 주는지, 프리로드 스캐너가 앞을 미리 훑는 방식까지는 [브라우저 렌더링 파이프라인 글](/posts/browser-rendering-pipeline)에서 실제로 재 본 숫자와 함께 다룬다.

### 처음 만나는 오류 세 가지

이 작은 페이지에서도 자주 보는 오류가 있다. 개발자 도구(F12)의 콘솔 탭을 열어 두고 시작하는 습관이 도움이 된다.

```text
Uncaught TypeError: Cannot read properties of null (reading 'addEventListener')
```

찾으려는 요소가 없다. 스크립트가 DOM보다 먼저 실행됐거나, 선택자에 오타가 있다(`#add` 대신 `add`라고 쓰면 태그 이름이 `add`인 요소를 찾는다).

```text
GET http://localhost:5173/main.js net::ERR_ABORTED 404 (Not Found)
```

파일 경로가 틀렸다. 개발자 도구의 네트워크 탭에서 요청 주소를 보고 실제 파일 위치와 맞춰 본다.

CSS가 안 먹을 때는 오류가 나지 않는다. 요소 탭에서 버튼을 고르고 오른쪽 스타일 패널을 보면 규칙에 취소선이 그어져 있는지, 아예 규칙이 없는지 보인다. 취소선이면 다른 규칙이 이긴 것이고, 없으면 선택자가 이 요소를 가리키지 못한 것이다. 개발자 도구를 다루는 법은 [브라우저 개발자 도구 글](/posts/browser-devtools-debugging)에 모아 두었다.

## 숫자와 화면이 어긋나기 시작할 때

페이지에 기능을 하나씩 붙여 보자. 하루 목표를 8잔으로 정하고, 남은 잔 수를 보여 주고, 다 채우면 문구를 바꾼다. 빼기 버튼도 넣는다.

```js
let count = 0;
const goal = 8;

addButton.addEventListener("click", () => {
  count += 1;
  output.textContent = `${count}잔`;
  remain.textContent = `${goal - count}잔 남음`;
  if (count >= goal) badge.hidden = false;
});

subButton.addEventListener("click", () => {
  count -= 1;
  output.textContent = `${count}잔`;
  // remain을 고치는 줄을 깜빡했다
});
```

빼기 버튼을 누르면 숫자는 줄어드는데 "남음"은 그대로다. 배지도 숨겨지지 않는다. 숫자가 바뀔 때마다 화면의 어느 곳을 고쳐야 하는지를 사람이 기억해야 하니, 처리기가 늘수록 빼먹는 곳이 생긴다.

해결책은 의외로 단순하다. 화면을 고치는 코드를 한 곳에 모으고, 숫자가 바뀌면 그 함수 하나만 부른다. 그 함수는 지금 숫자를 받아 보여 줄 내용을 돌려준다. 같은 숫자를 넣으면 늘 같은 결과가 나와야 한다.

아래에서 직접 만들어 보자. `renderCounter(count, goal)`은 지금 잔 수와 목표를 받아 화면에 쓸 문장을 돌려준다. 목표를 채웠거나 넘겼으면 "오늘 목표 달성"이라고 쓴다.

<CodePlayground

이제 처리기는 숫자만 바꾸고 `render()`를 부른다.

```js
function render() {
  output.textContent = renderCounter(count, goal);
  badge.hidden = count < goal;
}

addButton.addEventListener("click", () => { count += 1; render(); });
subButton.addEventListener("click", () => { count -= 1; render(); });
```

"화면은 상태를 넣으면 나오는 결과"라는 이 생각이 React의 출발점이다. React는 여기서 한 걸음 더 간다. `render()`를 부르는 것조차 사람이 하지 않는다. 상태를 바꾸면 React가 알아서 화면 함수를 다시 부르고, 이전 결과와 비교해 바뀐 DOM만 고친다.

## npm으로 도구를 들이는 순간

파일이 세 개일 때는 메모장과 브라우저만 있으면 된다. 그런데 자바스크립트 파일이 열 개가 되면 문제가 생긴다. `<script>` 태그를 열 개 적어야 하고, 순서가 틀리면 아직 정의되지 않은 함수를 부른다. 남이 만든 날짜 라이브러리를 쓰려면 파일을 내려받아 폴더에 넣고 버전을 손으로 관리해야 한다.

npm은 이걸 대신해 주는 패키지 관리자다. Node.js를 설치하면 함께 들어온다. 프로젝트 폴더에서 먼저 `package.json`을 만든다.

```bash
# 프로젝트 정보 파일(package.json)을 기본값으로 만든다
npm init -y

<script type="module" src="/main.js"></script>
```

## React로 넘어가는 이유

같은 카운터를 React로 쓰면 이렇게 된다.

```tsx
import { useState } from "react";

export function WaterCounter({ goal = 8 }: { goal?: number }) {
  const [count, setCount] = useState(0);
  const done = count >= goal;

  return (
    <main>
      <h1>오늘 마신 물</h1>
      <p aria-live="polite">
        {done ? `${count}잔, 오늘 목표 달성` : `${count}잔, ${goal - count}잔 남음`}
      </p>
      <button type="button" onClick={() => setCount((c) => c + 1)}>한 잔 더</button>
      <button type="button" onClick={() => setCount((c) => c - 1)}>한 잔 빼기</button>
    </main>
  );
}
```

`querySelector`도 `textContent`도 없다. `setCount`로 상태만 바꾸면 React가 이 함수를 다시 부르고, 결과를 이전 결과와 비교해 바뀐 글자만 DOM에 반영한다. 빼기 버튼에서 "남음"을 고치는 줄을 깜빡할 일이 없다. 화면 전체가 상태 하나에서 나오기 때문이다.

React를 쓴다고 HTML, CSS, 자바스크립트가 사라지지 않는다. JSX의 `<button>`은 결국 DOM의 버튼이 되고, 접근성 규칙도 그대로다. `onClick`은 `addEventListener`를 대신 걸어 주는 것이고, 스타일은 여전히 CSS다. 그래서 처음 배울 때 이 셋을 맨손으로 한 번 다뤄 보는 게 도움이 된다. React에서 버그가 났을 때 결국 내려가서 보는 곳이 DOM과 네트워크 탭이다.

그렇다고 모든 페이지에 React가 필요하지는 않다. 회사 소개 페이지처럼 거의 바뀌지 않는 화면이라면 HTML과 CSS만으로 충분하고, 자바스크립트를 안 싣는 편이 더 빠르다. 상태가 여러 곳에 나타나고 서로 얽히기 시작할 때가 넘어갈 신호다. 프레임워크끼리의 차이는 [프런트엔드 프레임워크 비교 글](/posts/frontend-frameworks-compared)에, JSX가 무엇으로 바뀌는지는 [JSX와 컴포넌트 글](/posts/react-jsx-components)에 있다.

## 면접에서 나올 만한 질문

### HTML, CSS, 자바스크립트의 역할을 설명해 주세요

HTML은 문서의 구조와 의미, CSS는 표현, 자바스크립트는 동작을 맡는다. 같은 버튼이라도 HTML은 이것이 버튼이라는 사실을, CSS는 색과 크기를, 자바스크립트는 눌렀을 때 할 일을 정한다. 이렇게 나누면 바뀌는 이유가 다른 코드끼리 떨어져 있어서 한쪽을 고칠 때 다른 쪽을 덜 건드린다.

### 관심사 분리란 무엇이고, React에서는 어떻게 바뀌나요

바뀌는 이유가 다른 코드를 따로 두는 원칙이다. 전통적인 웹에서는 언어별로 파일을 나눠 이 원칙을 지켰다. React에서는 마크업과 동작이 한 컴포넌트에 같이 들어가는 대신 화면 조각(기능) 단위로 나눈다. 자르는 축이 언어에서 기능으로 바뀌었을 뿐 원칙은 같다.

### div에 click 이벤트를 달면 안 되나요

마우스로는 동작하지만 버튼이 기본으로 주는 것을 잃는다. 키보드 포커스, Enter·Space로 누르기, 스크린 리더가 읽는 "버튼" 역할이 없다. 이걸 `tabindex`, `role`, 키 이벤트로 다시 만들 수는 있지만 빠뜨리기 쉬우니 처음부터 `button`을 쓰는 편이 낫다.

### script 태그를 head에 두면 왜 요소를 찾지 못하나요

평범한 스크립트는 파서를 멈추고 그 자리에서 실행된다. head에서 실행되는 순간에는 body를 아직 읽지 않아 DOM에 요소가 없으니 `querySelector`가 null을 돌려준다. `defer`를 붙이거나 `type="module"`로 불러오면 DOM이 다 만들어진 뒤에 실행된다.

### defer와 async의 차이는 무엇인가요

둘 다 파일을 받는 동안 파서를 멈추지 않는다. `defer`는 HTML 파싱이 끝난 뒤 DOMContentLoaded 직전에, 적힌 순서대로 실행한다. `async`는 다 받는 즉시 실행하고 순서를 보장하지 않는다. DOM을 다루거나 서로 의존하는 앱 코드는 `defer`, 통계 스크립트처럼 독립된 코드는 `async`가 맞다.

### package.json과 package-lock.json은 각각 무엇을 기록하나요

`package.json`은 내가 쓰겠다고 선언한 패키지와 허용 버전 범위(`^8.3.5` 같은), 실행 스크립트를 적는다. `package-lock.json`은 실제로 설치된 모든 패키지(하위 의존성 포함)의 정확한 버전과 출처를 적는다. 둘 다 커밋해야 다른 사람과 CI가 같은 버전을 받는다. CI에서는 잠금 파일을 그대로 따르는 `npm ci`를 쓴다.

### 왜 프레임워크를 쓰나요? 언제 쓰지 않아도 되나요

상태가 화면 여러 곳에 나타나면 상태가 바뀔 때마다 고칠 DOM을 사람이 기억해야 하고, 여기서 화면과 데이터가 어긋나는 버그가 생긴다. React 같은 프레임워크는 상태에서 화면을 다시 계산하고 바뀐 부분만 DOM에 반영해 이 일을 대신한다. 반대로 거의 바뀌지 않는 정적인 페이지는 HTML과 CSS만으로 충분하고, 자바스크립트를 덜 싣는 편이 첫 화면도 빠르다.
