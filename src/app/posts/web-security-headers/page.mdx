  보안 헤더는 서버가 응답에 적어 보내는 지시문이고, 실제로 지키는 쪽은 사용자의 브라우저다. 허락한 스크립트만 실행하라, 남의 사이트 안에 내 화면을 그리지 말라, 파일 형식을 짐작하지 말라, 주소를 다른 사이트에 알려 주지 말라 같은 약속을 한 줄씩 건다. 그래서 명령줄 도구나 서버끼리 주고받는 요청에는 아무 효과가 없다.

  막는 만큼 정상 기능도 함께 막힐 수 있다. 그래서 먼저 막지 않고 보고만 받는 모드로 시작해 무엇이 걸리는지 본 뒤에 진짜로 켠다.

외부 보안 점검 결과표에 "보안 헤더 누락"이 여섯 줄 찍혀 온다. CSP 없음, X-Frame-Options 없음, HSTS 없음, nosniff 없음. 시키는 대로 복사해서 붙이면 점검 도구의 점수는 오른다. 그런데 다음 배포에서 결제 위젯이 하얗게 비고, 분석 스크립트가 안 돌고, 외부 이미지가 깨진다. 헤더 한 줄이 브라우저에게 무엇을 시키는지 모르고 붙였기 때문이다.

이 글은 그 헤더들을 하나씩, 실제로 브라우저가 어떻게 반응하는지 크로미움 141에서 확인한 결과로 본다. 서버는 Node로 만든 두 출처(`localhost:18920`과 `other.localhost:18921`)이고, 콘솔 메시지와 위반 보고는 Playwright로 받았다. nginx에서 헤더를 붙이는 방법과 `add_header` 상속 함정, HSTS 도입 순서는 [nginx HTTPS와 성능](/posts/nginx-https-performance)에 정리해 두었고, CSP가 XSS를 어떻게 막는지는 [XSS 글](/posts/xss)에 있다. 여기서는 "헤더를 넣었을 때 브라우저에서 무엇이 막히고 무엇이 깨지나"를 본다.

## 서버는 적고 브라우저가 지킨다

보안 헤더는 서버가 브라우저에게 보내는 지시문이다. 서버는 응답에 적기만 하고, 실제로 막는 건 브라우저다. [CORS](/posts/cors)와 같은 구조라서, curl이나 서버 간 요청에는 아무 효과가 없다. 공격자의 스크립트가 아니라 "사용자의 브라우저가 내 페이지를 다룰 때"를 묶어 두는 장치다.

데모 서버의 기본 세트를 curl로 받으면 이렇다.

```bash
# 헤더만 받아 본다
curl -sI http://localhost:18920/baseline
```

```text
HTTP/1.1 200 OK
content-type: text/html
Content-Security-Policy: script-src 'nonce-yNSKeLeAqvMf5gg8tu2N8A==' 'strict-dynamic'; object-src 'none'; base-uri 'none'; frame-ancestors 'self'
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
Cross-Origin-Opener-Policy: same-origin
Date: Thu, 22 Oct 2026 00:39:05 GMT
Connection: keep-alive
Keep-Alive: timeout=5
```

줄마다 막는 것이 다르다. 조각을 눌러 보자.

## CSP는 먼저 보고만 받는다

CSP를 바로 강제하면 내가 모르던 인라인 스크립트, 태그 매니저가 심은 스크립트, 오래된 페이지의 `onclick`이 한꺼번에 멈춘다. 그래서 처음에는 `Content-Security-Policy-Report-Only`로 깐다. 같은 정책을 적용하되 막지 않고 위반만 보고한다. nonce 없는 인라인 스크립트(주입된 스크립트라고 치자)를 넣은 페이지를 열었다.

```text
result: {"trusted":"ran","injected":"ran"}
[info] [Report Only] Refused to execute inline script because it violates the following Content Security Policy directive: "script-src 'nonce-Z/vnNZXoZppEQvIwzmS/JA=='". Either the 'unsafe-inline' keyword, a hash ('sha256-pmAODrDuYAeVGJRl/a2fKva6RXwDsWkvrIUSDIZ0iDA='), or a nonce ('nonce-...') is required to enable inline execution.
```

`injected`도 `ran`이다. 실행은 됐고, 콘솔에는 `[Report Only]`가 붙은 정보 메시지만 남았다. 서버의 `report-uri`로는 이런 보고가 들어왔다.

```text
REPORT /csp-report application/csp-report {"csp-report":{"document-uri":"http://localhost:18920/csp-ro","referrer":"","violated-directive":"script-src-elem","effective-directive":"script-src-elem","original-policy":"script-src 'nonce-Z/vnNZXoZppEQvIwzmS/JA=='; report-uri /csp-report","disposition":"report","blocked-uri":"inline","line-number":1,"source-file":"http://localhost:18920/csp-ro","status-code":200,"script-sample":""}}
```

`disposition: "report"`가 보고만 한 위반이라는 표시다. 강제 모드에서는 `enforce`로 온다. 이 보고를 며칠 모아 `blocked-uri`와 `source-file`별로 세면 정책에 넣을 것(내 스크립트)과 고칠 것(인라인 핸들러), 진짜 공격 시도를 가를 수 있다. 실제 운영에서는 브라우저 확장 프로그램이 넣은 스크립트 때문에 생긴 보고가 섞여 들어온다. `source-file`이 `chrome-extension://`이면 걸러 낸다.

## 어떤 스크립트가 통과하나

이제 강제 모드다. 한 페이지에 여섯 종류의 스크립트를 넣었다. nonce가 붙은 스크립트, 그 스크립트가 `createElement`로 만든 자식 스크립트, 해시를 정책에 적어 둔 인라인 스크립트, 아무 표시 없는 인라인 스크립트, 버튼의 `onclick`, 그리고 `eval`이다.

```text
result: {"trusted":"ran","child":"ran","hashed":"ran","injected":null,"clicked":null,"evalErr":"EvalError"}
[error] Refused to execute inline script because it violates the following Content Security Policy directive: "script-src 'nonce-2yZaUGFw1va3Ho+dJID9gw==' 'strict-dynamic' 'sha256-V+qfMTfnUY22X8i5MIv0sPELC04+xFEE56Eefv2eV7Y='". ...
[error] Refused to execute inline event handler because it violates the following Content Security Policy directive: ... Note that hashes do not apply to event handlers, style attributes and javascript: navigations unless the 'unsafe-hashes' keyword is present.
```

nonce와 해시는 쓰임새가 다르다. nonce는 응답마다 새로 만드는 난수라서 서버가 HTML을 그릴 때 끼워 넣을 수 있어야 한다. 해시는 스크립트 내용이 고정일 때 쓴다. 정적으로 배포하는 페이지라면 빌드할 때 인라인 스크립트의 해시를 계산해 정책에 넣는다. 위 오류 메시지가 친절하게 "이 스크립트를 허용하려면 이 해시를 넣으라"고 알려 주는데, 그게 바로 주입된 스크립트의 해시일 수 있으니 조심한다. 보고에 뜬 해시를 생각 없이 정책에 붙이면 공격 코드를 허용 목록에 올리는 셈이다.

`'unsafe-inline'`을 같이 적으면 어떨까. nonce나 해시가 하나라도 있으면 CSP 2 이상을 지원하는 브라우저는 `'unsafe-inline'`을 무시한다. 오래된 브라우저를 위한 대비로 함께 적는 관행이 여기서 나왔다. 정책을 `script-src 'nonce-abc' 'unsafe-inline'`으로 두고 확인했다.

```text
{ withNonce: 1, withoutNonce: null }
Refused to execute inline script because it violates the following Content Security Policy directive: "script-src 'nonce-abc' 'unsafe-inline'". Note that 'unsaf...
```

React나 Next.js에서는 인라인 이벤트 핸들러 문제가 거의 없다. JSX의 `onClick`은 HTML 속성이 아니라 `addEventListener`로 붙기 때문이다. 대신 프레임워크가 하이드레이션용으로 넣는 인라인 스크립트에 nonce를 전달해야 한다. Next.js App Router는 미들웨어에서 nonce를 만들어 헤더로 넘기는 방식을 문서로 안내하는데, 그러면 페이지가 요청마다 동적으로 그려져 정적 캐시를 못 쓴다. 정적 사이트라면 해시 방식이나 정적 자원 주소 기반 정책을 따져 본다.

실제로 다섯 경우를 돌린 결과에서 차단된 경우는 iframe 자리에 크롬 오류 페이지가 들어갔다.

```text
=== frame none (embedded by other origin)
result: {"innerText":"cross-origin (not readable)","frameUrl":"chrome-error://chromewebdata/"}
[requestfailed] http://localhost:18920/framed-none net::ERR_BLOCKED_BY_RESPONSE
=== frame both (embedded by other origin)
result: {"innerText":"cross-origin (not readable)","frameUrl":"http://localhost:18920/framed-both"}
```

요청 자체는 서버까지 갔다는 점을 기억해 두자. 막는 건 응답을 그리는 단계다. 그래서 이 헤더는 HTML 페이지 응답에 붙어야 의미가 있고, API JSON 응답에는 효과가 없다. 반대로 내가 결제사나 지도 같은 다른 서비스의 화면을 iframe으로 넣는 건 상대가 보낸 헤더가 정한다. 내 페이지의 `frame-ancestors`는 "누가 나를 넣을 수 있나"이고, "내가 무엇을 넣을 수 있나"는 CSP의 `frame-src`다. 둘을 헷갈려 `frame-ancestors`에 결제사 주소를 넣는 실수가 흔하다.

## 형식을 짐작하지 말라는 한 줄

사용자가 올린 파일을 같은 출처에서 내려 주는 서비스를 생각해 보자. 공격자가 내용은 자바스크립트인 `.txt` 파일을 올리고, 다른 곳에 주입한 `<script src="/upload.txt">`로 그 파일을 부른다. 브라우저가 `Content-Type: text/plain`을 무시하고 내용을 보고 "스크립트 같다"며 실행하면, 같은 출처 스크립트로 돌아간다. 같은 파일을 nosniff 없이 한 번, 있게 한 번 불렀다.

```text
=== sniff
result: {"sniffed":1}
[error] Refused to execute script from 'http://localhost:18920/upload.txt?nosniff' because its MIME type ('text/plain') is not executable, and strict MIME type checking is enabled.
```

`sniffed`가 1이다. 헤더가 없을 때는 `text/plain` 파일이 스크립트로 실행됐고, `nosniff`가 붙은 쪽만 막혔다. 이 헤더를 켜면 반대로 서버의 `Content-Type`이 틀린 정상 파일도 막힌다. `.mjs`나 `.wasm`을 `application/octet-stream`으로 내보내는 서버라면 nosniff를 켠 날 그 파일이 멈춘다. 켜기 전에 정적 파일의 형식부터 맞춘다. 사용자 업로드 파일은 아예 다른 도메인(쿠키를 공유하지 않는 별도 등록 도메인)에서 내려 주는 게 근본적인 해결이다.

## 주소창의 토큰이 다른 사이트로 새는 길

비밀번호 재설정 링크(`/reset?token=...`)나 공유 링크처럼 주소에 비밀이 들어가는 페이지가 있다. 그 페이지에 외부 분석 스크립트나 이미지, 다른 사이트로 가는 링크가 있으면 브라우저는 요청에 `Referer` 헤더로 지금 주소를 실어 보낸다. 주소에 `token=abc123`을 넣은 페이지에서 다른 출처의 이미지를 불러오고 링크를 눌렀을 때, 상대 서버가 받은 `Referer`다.

```text

REFERER /landing  -> http://localhost:18920/
REFERER /pixel no-referrer -> (none)
REFERER /landing  -> (none)
REFERER /pixel same-origin -> (none)
REFERER /landing  -> (none)
REFERER /pixel unsafe-url -> http://localhost:18920/ref?p=unsafe-url&token=abc123
REFERER /landing  -> http://localhost:18920/ref?p=unsafe-url&token=abc123
```

## 쓰지 않는 기능은 꺼 둔다

`Permissions-Policy`는 카메라, 마이크, 위치, 결제 같은 강력한 브라우저 기능을 문서 단위로 끈다. 사용자가 이미 권한을 준 사이트라도 이 헤더가 끄면 쓸 수 없다. `geolocation=()`, `camera=(self)`로 두고 위치를 요청했다.

```text
result: {"allowsGeolocation":false,"allowsCamera":true,"geo":"error code 1: Geolocation has been disabled in this document by permissions policy."}
[error] Permissions policy violation: Geolocation access has been blocked because of a permissions policy applied to the current document. See https://crbug.com/414348233 for more details.
```

권한 창이 뜨기도 전에 오류로 끝났다. 효과는 두 군데서 나온다. 주입된 스크립트가 권한 요청 창을 띄워 사용자를 속이지 못한다. 그리고 내 페이지에 넣은 광고나 위젯 iframe이 그 기능을 쓰지 못한다. 반대로 iframe 안에서 기능을 쓰게 하려면 헤더에서 그 출처를 허용하고, iframe 태그의 `allow="camera"` 속성도 같이 줘야 한다. 둘 중 하나만 고치고 "왜 카메라가 안 열리지" 하는 경우가 많다. 헤더 문법(`camera=(self "https://video.example.com")`)은 예전 `Feature-Policy`와 다르니 옛 문법을 복사하지 않는다.

## 창과 창 사이를 끊는다

`window.open`으로 연 창은 서로를 참조할 수 있다. 연 쪽은 반환값으로, 열린 쪽은 `window.opener`로. 출처가 달라도 `location`을 바꾸는 정도는 된다. 열린 탭이 원래 탭을 몰래 피싱 페이지로 바꿔치기하는 탭내빙(tabnabbing)이 여기서 나온다. `Cross-Origin-Opener-Policy: same-origin`은 다른 출처 창과의 이 연결을 끊는다. 같은 동작을 COOP 없이 한 번, 있게 한 번 해 봤다.

```text
=== coop unsafe-none
result: {"fromOpener":{"closed":false},"fromPopup":{"hasOpener":true}}
=== coop same-origin
result: {"fromOpener":{"closed":true},"fromPopup":{"hasOpener":false}}
```

COOP를 켜자 팝업 쪽에서는 `opener`가 `null`이 됐고, 연 쪽에서는 팝업이 이미 닫힌 창처럼 보인다(`closed: true`). 둘이 서로 다른 브라우징 컨텍스트 그룹으로 갈라져 참조가 끊긴 것이다. 소셜 로그인 팝업이나 결제 팝업처럼 `opener`로 결과를 돌려받는 흐름이 있다면 이 헤더가 그 흐름을 끊는다. 그런 페이지에는 `same-origin-allow-popups`를 쓰거나, 팝업 대신 리다이렉트나 `postMessage`를 쓸 수 있는 구조로 바꾼다.

COOP에는 다른 역할도 있다. `Cross-Origin-Embedder-Policy: require-corp`와 함께 켜면 페이지가 교차 출처 격리(cross-origin isolated) 상태가 되고, 그래야 `SharedArrayBuffer`와 정밀한 타이머를 쓸 수 있다. 스펙터(Spectre) 같은 CPU 부채널 공격으로 같은 프로세스의 다른 출처 데이터를 읽어 내는 걸 막으려고, 브라우저가 "다른 출처 자원이 동의 없이 섞이지 않은 페이지"에서만 이 기능을 허락한다.

## HTTPS만 쓰겠다는 약속

HSTS는 이 목록에서 유일하게 페이지 안의 동작이 아니라 연결 방식을 바꾼다. 받은 브라우저는 그 도메인에 `http://`로 가려 해도 내부에서 `https://`로 바꿔 보낸다. 첫 평문 요청을 가로채 가짜 페이지를 보여 주는 공격(SSL 스트리핑)을 두 번째 방문부터 막는다. 명세(RFC 6797)는 브라우저가 평문 HTTP 응답에 실린 이 헤더를 무시하게 한다. 위 curl 결과처럼 `http://localhost`에 붙여도 아무 효과가 없다는 뜻이다. 도입할 때는 짧은 `max-age`로 시작해 늘리는 순서, `includeSubDomains`가 내부 HTTP 하위 도메인을 막는 문제, 프리로드 목록의 되돌리기 어려움이 중요하다. 이 순서는 [nginx HTTPS와 성능](/posts/nginx-https-performance)에 자세히 적어 두었다.

## 헤더를 넣고 나서 깨지는 것들

헤더 점검은 직접 짜 볼 수 있을 만큼 단순하다. 아래 함수는 응답 헤더 객체를 받아 빠졌거나 약한 항목을 돌려준다. 헤더 이름은 대소문자를 가리지 않고, nonce나 해시가 있으면 `'unsafe-inline'`이 무시된다는 규칙, `object-src`가 없어도 `default-src`가 있으면 된다는 규칙까지 넣는다. HSTS는 180일(15552000초)보다 짧으면 약하다고 본다.

점검기는 헤더가 있는지만 본다. 실제로 문제가 되는 건 헤더를 넣은 다음이다. 증상별로 어디를 보는지 정리하면 이렇다.

배포 뒤 특정 기능만 안 된다면 브라우저 콘솔에서 `Refused to`로 시작하는 메시지를 먼저 찾는다. CSP, frame-ancestors, nosniff 위반은 모두 이 말로 시작하고 어느 지시어에 걸렸는지 적혀 있다. 운영에서는 CSP 위반 보고 수가 배포 직후 튀었는지를 본다.

외부 이미지나 영상이 갑자기 깨졌다면 Network 패널의 실패 사유를 본다. `ERR_BLOCKED_BY_RESPONSE.NotSameOriginAfterDefaultedToSameOriginByCoep`면 COEP, `ERR_BLOCKED_BY_RESPONSE`만 있고 iframe이면 상대 쪽 frame-ancestors나 XFO다. 내 헤더가 아니라 상대 헤더일 수 있다는 점을 기억한다.

로그인 팝업이 결과를 못 돌려준다면 COOP다. 팝업이 `window.opener`로 부모에게 알리는 구조는 `same-origin`에서 끊긴다.

헤더가 응답에 아예 없다면 어디서 붙이는지를 본다. 앱, nginx, CDN이 각자 붙이면 같은 헤더가 둘 실리거나(CSP는 두 정책을 모두 만족해야 통과한다), 에러 응답에서만 빠진다. 헤더는 한 계층에서만 관리하고, `curl -sI`로 정상 응답과 404 응답을 모두 확인한다.

## 정리하며

보안 헤더는 서버가 적고 브라우저가 지키는 약속이다. CSP는 주입된 스크립트의 실행을, frame-ancestors는 다른 사이트 안에 그려지는 것을, nosniff는 형식 짐작을, Referrer-Policy는 주소 유출을, Permissions-Policy는 강력한 기능을, COOP는 창 사이의 참조를 막는다. 막는 만큼 정상 기능도 깨질 수 있으니 CSP는 보고 전용으로 시작하고, COEP는 필요한 페이지에만 켜고, 콘솔의 `Refused to`와 위반 보고로 결과를 확인한다. 이 헤더들이 OWASP의 어느 위험에 대응하는지는 [OWASP Top 10 지도](/posts/owasp-top-10-map)에서 이어서 본다.

## 면접에서 나올 만한 질문

### 보안 헤더는 누가 지키나요? 서버 간 요청에도 효과가 있나요?

서버는 응답에 적기만 하고 지키는 건 브라우저다. 그래서 curl이나 서버 간 호출, 공격자가 직접 보내는 요청에는 아무 효과가 없다. 사용자의 브라우저가 내 페이지를 그리고 실행할 때의 동작을 제한하는 장치라, 서버 쪽 인증과 입력 검증을 대신하지 못한다.

### CSP는 어떻게 도입하나요?

먼저 `Content-Security-Policy-Report-Only`로 같은 정책을 걸어 막지 않고 위반 보고만 받는다. 보고를 모아 인라인 핸들러를 옮기고 필요한 스크립트에 nonce나 해시를 붙인 뒤, 보고가 잠잠해지면 `Content-Security-Policy`로 바꿔 강제한다. 강제한 뒤에도 보고는 계속 받아 배포 문제와 공격 시도를 본다.

### nonce와 hash 방식은 어떻게 고르나요?

nonce는 응답마다 새 난수를 만들어 스크립트 태그에 붙이는 방식이라 서버가 HTML을 그릴 때 쓸 수 있다. 해시는 스크립트 내용이 고정일 때 정책에 SHA-256 값을 적는 방식이라 정적 사이트에 맞는다. 둘 다 인라인 이벤트 핸들러에는 적용되지 않으므로 `onclick` 같은 속성은 `addEventListener`로 옮긴다.

### strict-dynamic은 무엇을 해 주나요?

nonce나 해시로 신뢰한 스크립트가 동적으로 만든 스크립트도 실행을 허용한다. 태그 매니저나 번들러가 런타임에 스크립트를 추가해도 그 주소를 일일이 허용 목록에 적지 않아도 된다. 대신 신뢰한 스크립트가 공격자 입력으로 스크립트를 만들면 그것도 통과하므로 처음 스크립트의 품질이 중요해진다.

### 클릭재킹은 무엇이고 어떻게 막나요?

공격자 페이지가 내 사이트를 투명한 iframe으로 덮어 사용자가 모르게 내 사이트의 버튼을 누르게 하는 공격이다. CSP `frame-ancestors`로 나를 iframe에 넣을 수 있는 출처를 정하고, 오래된 브라우저를 위해 `X-Frame-Options`도 둔다. 둘이 다르면 지원하는 브라우저는 `frame-ancestors`를 따른다.

### X-Content-Type-Options: nosniff는 왜 필요한가요?

브라우저가 `Content-Type`을 무시하고 내용을 보고 형식을 짐작하면, 사용자가 올린 텍스트 파일이 스크립트로 실행될 수 있다. nosniff를 켜면 스크립트가 아닌 형식으로 온 파일은 script 태그로 불러도 실행하지 않는다. 켜기 전에 정적 파일의 `Content-Type`이 맞는지 확인해야 정상 파일이 막히지 않는다.

### COOP와 COEP는 무엇이고, 켜면 무엇이 깨지나요?

COOP는 다른 출처 창과의 window 참조를 끊어 탭내빙과 부채널 공격을 줄이고, COEP는 내가 불러오는 다른 출처 자원에 CORP나 CORS 동의를 요구한다. 둘을 함께 켜면 교차 출처 격리 상태가 되어 `SharedArrayBuffer`를 쓸 수 있다. 대신 opener로 결과를 돌려받는 로그인 팝업과 동의 헤더가 없는 외부 이미지·임베드가 깨진다.

### HSTS를 HTTP 응답에 붙이면 어떻게 되나요?

아무 효과가 없다. RFC 6797은 평문 HTTP로 받은 HSTS 헤더를 브라우저가 무시하게 한다. 중간자가 넣거나 지울 수 있는 응답이라 믿을 수 없기 때문이다. HTTPS 응답에 붙여야 하고, 첫 방문의 평문 요청까지 막으려면 프리로드 목록에 올린다.
