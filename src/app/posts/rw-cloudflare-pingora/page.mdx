이 글은 "실제 서비스 사례" 시리즈에서 클라우드플레어가 원본 서버로 가는 프록시를 직접 만든 이야기를 다룬다. 같은 회사의 다른 글로는 정규식 하나가 전 세계 CPU를 채운 [Cloudflare 2019년 7월 장애](/posts/rw-cloudflare-outage-regex)가 있다. 리버스 프록시가 무슨 일을 하는지는 [Nginx 리버스 프록시 글](/posts/nginx-reverse-proxy)에, 연결 풀이 왜 필요하고 크기를 어떻게 정하는지는 [커넥션 풀 글](/posts/connection-pool)에 있다. 여기서는 그 설명을 반복하지 않는다.

2022년 9월 클라우드플레어 블로그의 글은 이런 문장으로 시작한다. 새로 만든 Rust HTTP 프록시가 하루 1조 건이 넘는 요청을 처리하고, 이전 프록시 인프라에 비해 CPU와 메모리를 3분의 1만 쓴다. 바로 다음 문단이 이유다. "클라우드플레어가 커지면서 우리는 NGINX를 넘어섰다." 오랫동안 잘 썼지만, 그 규모에서는 필요한 성능도, 복잡한 환경에 필요한 기능도 얻을 수 없었다는 것이다.

## 이 글이 기대는 자료

클라우드플레어가 직접 낸 자료만 썼다. 중심은 [How we built Pingora, the proxy that connects Cloudflare to the Internet (2022년 9월)](https://blog.cloudflare.com/how-we-built-pingora-the-proxy-that-connects-cloudflare-to-the-internet/)과 [Open sourcing Pingora (2024년 2월)](https://blog.cloudflare.com/pingora-open-source/)이고, `pingora-limits`를 소개한 2023년 5월 글, 그 뒤 Pingora에서 나온 요청 밀반입(request smuggling) 취약점 보고 두 편(2025년 5월, 2026년 3월)과 [cloudflare/pingora 저장소](https://github.com/cloudflare/pingora)의 README·사용자 가이드·코드(2026년 10월 커밋 기준)를 봤다. NGINX의 연결 풀 동작은 nginx.org의 공식 문서로 확인했다. 숫자는 모두 원문 그대로다.

## 요청 하나는 워커 하나에 묶인다

2022년 글이 꼽은 첫 번째 한계는 NGINX의 워커 구조다. NGINX는 워커 프로세스 여러 개가 요청을 나눠 받는데, 요청 하나는 워커 하나만 처리할 수 있다. 글은 이 때문에 CPU 코어 사이 부하가 고르지 않고, CPU를 많이 쓰거나 I/O를 막는 요청이 같은 워커의 다른 요청까지 느리게 만든다고 적었다.

가장 큰 문제는 연결 재사용이었다. 클라우드플레어 서버는 원본 서버(origin)와 TCP 연결을 맺어 요청을 넘긴다. 연결을 풀에 남겨 두었다 다시 쓰면 TCP와 TLS 핸드셰이크를 건너뛰니 첫 바이트까지 걸리는 시간(TTFB)이 준다. 그런데 NGINX의 연결 풀은 워커마다 따로 있다. 요청이 어느 워커에 떨어지면 그 워커의 풀에 있는 연결만 쓸 수 있다. 글은 워커를 늘려 규모를 키울수록 연결이 고립된 풀 여러 개로 흩어져 재사용률이 나빠진다고 적었다. TTFB가 늘고, 유지할 연결도 늘어 클라우드플레어와 고객 양쪽의 자원과 돈이 든다.

NGINX 공식 문서도 같은 구조를 적고 있다. [upstream 모듈 문서](https://nginx.org/en/docs/http/ngx_http_upstream_module.html)의 `keepalive` 지시어 설명에 따르면, 이 값은 "각 워커 프로세스의 캐시에" 남겨 둘 놀고 있는 연결 수의 최대치이고, 넘으면 가장 오래 쓰지 않은 연결을 닫는다. 1.29.7부터는 keepalive가 기본으로 켜져 워커마다 32개가 기본 한도라고 적혀 있다. 이 시리즈의 [Nginx 리버스 프록시 글](/posts/nginx-reverse-proxy)에서 `keepalive 32`를 "worker마다 놀고 있는 연결을 최대 32개까지 남겨 둔다"고 설명한 것이 바로 이 부분이다.

  const pools = shared ? 1 : workers;

  let reused = 0;

## NGINX 워커 수를 바꿔 가며 재 보기

모형만으로는 미덥지 않아서 Ubuntu 24.04에 들어 있는 NGINX 1.24.0으로 직접 재 봤다. 원본은 Node.js로 만든 작은 HTTP 서버이고, 새 TCP 연결이 들어올 때마다 수를 센다. 원본은 놀고 있는 연결을 1초 뒤 닫는다(`keepAliveTimeout = 1000`). NGINX 설정은 아래와 같고, 워커 수만 바꿔 가며 띄웠다.

```nginx
worker_processes 8;                         # 1, 4, 8, 16, 32로 바꿔 가며 잰다
events { worker_connections 1024; }
http {
  upstream origin {
    server 127.0.0.1:9000;
    keepalive 32;                           # 워커마다 놀고 있는 연결을 32개까지 남긴다
  }
  server {
    listen 127.0.0.1:8080 reuseport;        # 커널이 새 연결을 워커들에 흩어 준다
    location / {
      proxy_pass http://origin;
      proxy_http_version 1.1;               # 1.29.7 전에는 이 두 줄이 있어야 재사용된다
      proxy_set_header Connection "";
    }
  }
}
```

클라이언트는 요청마다 새 연결로 NGINX에 붙어(`agent: false`) 0.1초 간격으로 200번 요청했다. `reuseport` 덕분에 요청이 여러 워커로 흩어진다. 요청이 끝날 때마다 원본에 쌓인 새 연결 수를 읽었다.

```text
workers=1 {"conns":1,"reqs":200}
workers=4 {"conns":5,"reqs":200}
workers=8 {"conns":20,"reqs":200}
workers=16 {"conns":66,"reqs":200}
workers=32 {"conns":120,"reqs":200}
```

볼 숫자는 `conns`다. 같은 요청 200개를 처리하는데 워커가 하나면 원본 연결은 1개로 끝났고, 워커가 32개면 120개를 새로 열었다. 워커가 늘수록 워커 하나가 원본으로 요청을 보내는 간격이 길어져, 그 사이 원본이 1초 유휴 제한으로 연결을 닫아 버린 것이다. `keepalive 32`는 워커마다 32개까지 남겨 둘 수 있다는 뜻이지만, 남겨 둔 연결이 원본 쪽에서 닫히면 소용이 없다. 클라우드플레어가 말한 "워커를 늘릴수록 재사용률이 나빠진다"가 노트북 한 대에서도 그대로 보인다. 이 실험의 머신은 코어가 4개였으니, 워커 32개는 실제 운영에서 고를 값이 아니라 효과를 키워 보려고 넣은 값이다.

## 고칠 것인가, 옮길 것인가, 만들 것인가

두 번째 한계는 기능이었다. 2022년 글은 재시도나 장애 조치(failover)를 할 때 다른 원본 서버로, 다른 요청 헤더를 붙여 보내고 싶은 경우가 있는데 NGINX가 이를 허용하지 않는다고 예를 들었다. 필요한 기능을 NGINX 둘레에 쌓아 왔지만, 업스트림 코드에서 너무 멀어지지 않으면서 그렇게 하기는 쉽지 않았다. NGINX는 C로 되어 있어 메모리 안전하지 않고, 보완으로 쓴 Lua는 덜 위험하지만 느리고 정적 타입이 없었다. 글은 NGINX 커뮤니티가 활발하지 않고 개발이 "닫힌 문 뒤에서" 이뤄진다는 점도 적었다.

클라우드플레어는 몇 년 동안 분기마다 세 길을 다시 따졌다고 한다.

1. NGINX에 계속 투자하고, 필요하면 포크해서 100% 맞춘다. 전문성은 있었지만 워커 구조의 한계 때문에 제대로 맞추려면 다시 만드는 수준의 노력이 필요했다.
2. Envoy 같은 다른 오픈소스 프록시로 옮긴다. 좋은 프로젝트들이 있지만 몇 년 뒤 같은 순환이 되풀이될 수 있다.
3. 처음부터 사내 플랫폼과 프레임워크를 만든다. 초기 엔지니어링 투자가 가장 크다.

글은 어느 쪽이 맞는지 알려 주는 공식은 없었고, 여러 해 동안 가장 저항이 적은 길, 즉 NGINX를 보강하는 쪽을 택했다고 적었다. 어느 시점에 직접 만드는 쪽의 투자 대비 효과가 그만하다고 판단했다. 이 대목은 "다시 만들기"가 처음 떠올린 답이 아니라 마지막 답이었다는 걸 보여 준다.

## 고른 것: Rust, 너그러운 HTTP 파서, 멀티스레드

설계에서 내린 결정은 네 가지다.

언어는 Rust였다. C가 하는 일을 성능을 잃지 않고 메모리 안전하게 할 수 있어서다.

HTTP 라이브러리는 hyper 같은 좋은 라이브러리가 있었지만 직접 만들었다. 클라우드플레어는 인터넷 전체의 트래픽을 다루니 RFC를 따르지 않는 이상한 HTTP도 받아 줘야 한다. 글이 든 예는 상태 코드다. RFC 9110은 상태 코드를 세 자리 정수로 정의하고 보통 100~599를 기대하지만, 599에서 999 사이의 코드를 쓰는 서버가 많다. hyper에도 이 기능을 두고 이슈가 열렸고 결국 받아들여졌지만, 거절할 이유도 충분했다. 글은 이런 경우가 많아서 "너그럽고(permissive) 고칠 수 있는 HTTP 라이브러리"를 보장받는 가장 좋은 방법은 직접 구현하는 것이라고 결론 내렸다. 이 선택은 뒤에서 대가를 치른다.

작업 스케줄링은 멀티프로세스 대신 멀티스레드로 했다. 연결 풀 같은 자원을 쉽게 나눠 쓰기 위해서다. 앞에서 말한 "한 요청이 한 워커에 묶여 다른 요청을 느리게 만드는" 문제를 피하려고 작업 훔치기(work stealing)도 필요하다고 봤다. 놀고 있는 스레드가 바쁜 스레드의 대기열에서 일을 가져가는 방식이다. Tokio 비동기 런타임이 잘 맞았다고 적었다.

마지막은 개발자 인터페이스다. NGINX/OpenResty처럼 "요청의 일생"을 단계별 이벤트로 나누고, 단계마다 코드를 끼울 수 있게 했다. 예를 들어 요청 헤더를 받았을 때 도는 "request filter" 단계에서 요청을 고치거나 거절한다. 일반적인 프록시 로직과 사업 로직이 깔끔하게 갈리고, NGINX를 다루던 개발자가 빨리 적응할 수 있다는 이유였다.

2022년 글이 예로 든 "다른 원본에 다른 헤더로 다시 보내기"는 이 단계 구조에서 자연스럽게 된다. 저장소의 장애 조치 문서에 따르면 `fail_to_connect()`에서 오류를 재시도 가능하다고 표시하면 `upstream_peer()`가 다시 불리고, 이때 컨텍스트를 보고 다른 원본을 고를 수 있다. 문서는 `fail_to_connect()`가 불렸다면 원본에 아무것도 보내지 않았다는 것을 보장한다고 적었다. 반대로 요청을 보낸 뒤의 오류(`error_while_proxy()`)에서는 원본을 잘 알지 않는 한 멱등하지 않은 요청을 다시 보내지 말라고 권한다. [멱등 키 글](/posts/idempotency-key)에서 다룬 "보냈는지 모르는 요청은 다시 보내면 안 된다"는 원칙이 프록시 프레임워크의 API에 그대로 박혀 있다.

## 숫자로 본 결과: 코드가 아니라 연결이 빨라졌다

2022년 글 시점에 Pingora는 원본과 이야기해야 하는 HTTP 요청(예를 들어 캐시 미스)을 거의 모두 처리하고 있었다. 글이 공개한 숫자는 이렇다.

- 전체 트래픽에서 TTFB 중앙값이 5ms, 95번째 백분위가 80ms 줄었다.
- 모든 고객을 합쳐 초당 새 연결 수가 이전 서비스의 3분의 1이 됐다.
- 한 큰 고객은 연결 재사용률이 87.1%에서 99.92%로 올라, 그 고객의 원본으로 가는 새 연결이 160분의 1이 됐다.
- 같은 트래픽에서 CPU를 약 70%, 메모리를 67% 덜 쓴다.
- 이 모두를 합쳐 하루에 핸드셰이크 시간 434년을 아낀다고 글은 표현했다.

글은 TTFB가 준 이유를 분명히 적었다. 코드를 더 빨리 돌려서가 아니다. 이전 서비스도 요청을 1ms 안쪽으로 처리했다. 모든 스레드가 연결을 같이 쓰니 재사용률이 오르고, TCP와 TLS 핸드셰이크에 쓰는 시간이 줄었다. 재사용률 87.1%와 99.92%를 새 연결 비율로 바꾸면 12.9%와 0.08%이고, 12.9를 0.08로 나누면 약 161이다. 글의 "160배"와 맞는다.

CPU와 메모리가 준 이유도 세 갈래로 설명한다. 첫째, Rust 코드가 이전의 Lua 코드보다 효율적이다. NGINX/OpenResty에서 Lua가 HTTP 헤더를 읽으려면 NGINX의 C 구조체에서 읽어 Lua 문자열을 할당하고 복사한 뒤, 나중에 그 문자열을 GC로 치워야 한다. Pingora는 문자열에 바로 접근한다. 둘째, 멀티스레드라 요청 사이에 데이터를 나누기가 싸다. NGINX에도 공유 메모리가 있지만 모든 접근에 뮤텍스가 필요하고 문자열과 숫자만 넣을 수 있다. Pingora에서는 대부분 원자적 참조 카운터 뒤의 공유 참조로 바로 읽는다. 셋째, 새 연결이 줄었다. TLS 핸드셰이크는 이미 맺은 연결로 데이터를 주고받는 것보다 비싸다.

안정성 숫자도 하나 있다. Pingora가 생긴 뒤 수백조 건의 요청을 처리하는 동안 서비스 코드 때문에 죽은 적은 아직 없다고 글은 적었다. 드물게 죽었을 때는 다른 원인이었다. 커널 버그를 찾았고, 몇몇 머신의 하드웨어 문제를 찾았다.

기능 쪽 결과로는 원본 쪽 HTTP/2 지원을 큰 어려움 없이 넣었고, 덕분에 곧 고객에게 gRPC를 줄 수 있었다고 적었다. 같은 기능을 NGINX에 넣으려면 훨씬 많은 노력이 들었을 것이고 실현되지 않았을 수도 있다는 게 글의 판단이다.

풀을 나눠 쓰면 재사용률이 오르는 대신, 이 키를 잘못 정하면 한 고객의 요청이 다른 고객 설정으로 맺은 연결을 탈 수 있다. 문서가 "정확성과 보안을 위해"라는 말을 붙인 이유다. 같은 문서는 요청 중에 오류가 난 연결은 재사용하지 않고, `idle_timeout`을 0으로 두면 그 Peer의 재사용을 끈다고 적었다.

크기 한도는 설정 문서에 있다. `upstream_keepalive_pool_size`는 "Tokio 워커마다" 남겨 둘 놀고 있는 연결 수이고, 풀의 실제 상한은 이 값에 스레드 수를 곱한 것이다. 문서는 "축출은 워커 사이에서 전역으로 일관된다"고 덧붙였다. `pingora-pool` 코드를 보면 연결 풀은 전체 크기 한도를 가진 LRU이고, 키를 해시해 여러 조각(shard)으로 나눠 잠금 경쟁을 줄이며, 한도를 넘으면 전체에서 가장 오래된 연결부터 버린다. NGINX의 `keepalive`와 이름도 의미도 비슷하지만, 남은 연결을 어느 워커든 꺼내 쓴다는 점이 다르다.

## 원본 수백만 개를 잠금 없이 세기

공유 자원을 스레드가 같이 쓰면 이번에는 잠금이 문제다. 2023년 5월 글 [How Pingora keeps count](https://blog.cloudflare.com/how-pingora-keeps-count/)는 그 예를 하나 보여 준다. 원본이 느려지거나 응답하지 않으면 요청이 클라우드플레어 서버에 쌓이고, 클라우드플레어와 고객 서버 양쪽에 부담이 된다. 그래서 원본마다 진행 중인 요청이나 연결 수를 세서 문제 있는 원본만 막고 싶다.

해시 테이블로 세면 간단하지만 두 가지가 걸렸다. 수백만 개의 서버로 트래픽이 가는데 그때그때 말썽을 부리는 건 몇 개뿐이라, 모든 키의 카운터를 메모리에 두는 건 낭비다. 그리고 테이블에 새 키를 넣을 때 잠금이 필요해서, 경쟁이 심하면 모든 요청 처리가 줄을 선다. 글은 이 코드가 수만 대의 머신에서 초당 2천만 건이 넘는 요청을 다룬다고 적었다.

`pingora-limits`는 [Count-Min Sketch](/posts/count-min-sketch)를 골랐다. 행 H개, 열 N개의 카운터 표를 두고, 행마다 다른 해시로 열을 골라 카운터를 하나씩 올린다. 셀 때는 그 키가 닿은 칸들 중 가장 작은 값을 읽는다. 해시, 배열 인덱스, 원자적 덧셈만 쓰니 잠금 없이 구현된다. 아래는 글의 예(H=3, N=4)를 그대로 따라간 것이다.

글의 벤치마크(키 100만 개, 이벤트 1억 개, M1 맥북 위 Debian VM)에서 이벤트 하나를 세는 데 단일 스레드는 10ns로, `Mutex<HashMap>`의 51ns, `DashMap`의 43ns보다 빨랐다. 8스레드에서는 212ns로 `DashMap`과 같았고 `Mutex<HashMap>`의 1,505ns보다 약 7배 빨랐다. 최대 메모리는 26,184바이트로, `Mutex<HashMap>`의 53,477,392바이트에 비해 약 2,000분의 1이었다. 대가는 많이 세는 쪽으로 틀릴 수 있다는 것이다. 두 키가 모든 행에서 충돌하면 값이 부풀고, 적게 세는 일은 없다.

운영에서는 원본 연결 수 제한에 쓴다. 고객 ID, 서버 IP, 서버 호스트 이름이 같은 요청이 카운터 하나를 같이 올렸다 내리고, 기준을 넘으면 새 요청을 503으로 거절한다. 서로 관계없는 두 고객이 충돌할 확률이 이론상 약 2의 52제곱분의 1이 되도록 표 크기를 정했고, 기준값도 건강한 고객의 트래픽보다 훨씬 높게 잡아 잘못 거절할 일이 거의 없다고 글은 적었다. 공유 풀로 연결을 아끼는 쪽과, 한 원본으로 연결이 몰리지 않게 막는 쪽이 같은 프레임워크 안에 함께 있는 셈이다.

## 작업 훔치기, 그 뒤

2022년 글은 작업 훔치기가 필요하다고 적었다. 그런데 지금 저장소의 `pingora-runtime` 크레이트 설명은 조금 다른 이야기를 한다. Tokio의 멀티스레드 런타임은 작업 훔치기 스케줄링 때문에 단일 스레드 런타임보다 오버헤드가 있다는 벤치마크 결과가 있고, 이 크레이트는 세 번째 방식인 "작업 훔치기 없는 멀티스레드 런타임"을 준다고 적었다. 단일 스레드 런타임만큼 효율적이면서 여러 코어를 쓸 수 있다는 설명이다. 설정 문서의 `work_stealing` 항목은 기본값이 true다.

두 문서를 합쳐 보면, 클라우드플레어는 작업 훔치기를 기본으로 두면서도 끌 수 있는 선택지를 만들어 둔 것이다. 어느 서비스가 어느 쪽을 쓰는지는 공개되지 않았다. 서비스마다 런타임을 따로 두는 기본 구조 때문에 바쁜 서비스가 여럿이면 일꾼 풀도 여럿이 된다는 문제를 풀려고, 서비스 여럿이 런타임 하나를 같이 쓰는 "runtime group" 기능도 문서에 있다. 2022년의 "자원을 나눠 쓰려고 멀티스레드를 골랐다"는 결정이 스레드 풀 수준에서도 이어지는 모습이다.

## 끊김 없이 바꿔 끼우기

프록시는 배포할 때마다 연결을 끊으면 안 된다. 저장소의 무중단 재시작 문서는 순서를 이렇게 적었다. 옛 인스턴스와 새 인스턴스가 같은 업그레이드 소켓 경로에 합의한다. 새 인스턴스를 `--upgrade` 옵션으로 띄우면 서비스 포트를 직접 열지 않고 옛 인스턴스에게서 듣고 있는 소켓을 받으려고 기다린다. 옛 인스턴스에 SIGQUIT을 보내면 듣고 있는 소켓을 넘겨주고 우아한 종료 모드로 들어간다. 잠시 기다린 뒤에는 새 연결을 받지 않고, 진행 중인 요청을 마친다.

문서가 보장하는 것은 두 가지다. 요청은 옛 인스턴스나 새 인스턴스 중 하나가 반드시 처리하니 "connection refused"를 보는 요청이 없다. 유예 시간 안에 끝날 수 있는 요청은 중간에 끊기지 않는다. 2024년 오픈소스 공개 글도 "들어오는 요청을 하나도 떨어뜨리지 않고 스스로를 업그레이드하는" 무중단 재시작을 주요 운영 기능으로 꼽았다. 소켓을 넘기는 방식이라 포트를 두 프로세스가 동시에 여는 경쟁이 없다.

## 너그러운 파서가 치른 값

2022년의 "너그러운 HTTP 라이브러리" 결정은 그 뒤 두 번 보안 문제로 돌아왔다.

첫 번째는 2025년 5월 보고서([Resolving a request smuggling vulnerability in Pingora](https://blog.cloudflare.com/resolving-a-request-smuggling-vulnerability-in-pingora/))다. 2025년 4월 11일 09:20 UTC, 버그 바운티로 요청 밀반입 취약점(CVE-2025-4366)이 들어왔다. 요청 밀반입은 요청이 지나는 두 구성 요소가 HTTP 요청의 끝을 서로 다르게 해석할 때 생긴다. 한쪽은 요청 하나가 끝났다고 보는데 다른 쪽은 남은 바이트를 같은 연결의 두 번째 요청으로 읽는 것이다.

원인은 캐시였다. Pingora는 보통 HTTP/1.1 연결에서 요청 본문을 끝까지 읽어 버리거나, 오류가 나면 연결을 재사용하지 않는다. 그런데 캐시를 켜면 캐시 적중 때 이 로직을 건너뛰었다. 응답을 보낸 뒤 연결에 읽지 않은 본문이 남고, 그 본문이 다음 요청의 앞머리처럼 해석될 수 있었다.

보고서가 든 요청은 이렇다. 겉으로는 규격에 맞는 요청 하나이고, `content-length: 79` 뒤의 79바이트는 본문이다.

```text
GET /attack/foo.jpg HTTP/1.1
Host: example.com
content-length: 79

GET / HTTP/1.1
Host: attacker.example.com
Bogus: foo
```

`/attack/foo.jpg`가 캐시에 있으면 Pingora는 캐시에서 바로 답하고, 본문 79바이트를 읽지 않은 채 연결을 다음 요청에 쓴다. 같은 연결로 다른 방문자의 `GET /victim/main.css`가 오면, 남아 있던 본문이 그 앞에 붙어 `Host: attacker.example.com` 요청처럼 읽힌다. 진짜 요청 줄은 `Bogus:` 헤더 값 뒤에 붙어 묻힌다. 연구자는 이걸로 다른 방문자의 다음 요청 헤더와 URL을 바꿔, 일부 원본이 공격자 호스트로 301 리디렉션하게 만들 수 있었다. 클라우드플레어는 당시 무료 요금제 CDN 트래픽 일부에 캐시를 켠 Pingora 구성 요소를 배포하던 중이었다. 4월 12일 06:44 UTC에 그 구성 요소로 가는 트래픽을 끊었고(신고 후 22시간 안), 4월 19일에 패치를 내고 그 구성 요소에 캐시된 데이터를 모두 무효화했다. 악용된 흔적은 찾지 못했다고 적었다.

두 번째는 2026년 3월 보고서([Fixing request smuggling vulnerabilities in Pingora OSS deployments](https://blog.cloudflare.com/pingora-oss-smuggling-vulnerabilities/))다. 2025년 12월부터 HTTP/1.x 요청 밀반입 취약점 세 건(CVE-2026-2833, 2835, 2836)이 들어왔다. 101 응답을 받기도 전에 `Upgrade` 헤더만 보고 뒤의 바이트를 그대로 흘려보내던 문제, HTTP/1.0 요청과 `Transfer-Encoding` 조합에서 요청 본문을 연결이 닫힐 때까지로 잘못 해석하던 문제, 그리고 기본 캐시 키가 URI 경로만 써서 다른 호스트끼리 캐시가 섞일 수 있던 문제다.

이번에는 클라우드플레어 CDN은 영향이 없었다. 글에 따르면 CDN에서 Pingora는 바깥 트래픽을 처음 받는 진입(ingress) 프록시로 쓰이지 않고, 앞단의 프록시 계층이 HTTP/1.1로만 넘기며 애매한 길이 표시를 거절하기 때문이다. 영향을 받은 건 Pingora를 인터넷에 직접 노출한 다른 사용자들이었다. 글은 "Pingora는 레거시 HTTP 스택을 가진 고객을 위해 RFC를 엄격히 따르지 않는 요청과 응답도 일부러 허용한다"고 설명하면서, 앞으로는 기본값을 엄격한 RFC 준수로 두겠다고 적었다. "클라우드플레어가 상대하는 것 같은 거친 인터넷을 다뤄야 하는 프레임워크 사용자는 아주 적을 것"이라는 문장이 함께 있다. 2026년 3월 2일 나온 0.8.0이 고친 버전이다.

이게 [Nginx 리버스 프록시 글](/posts/nginx-reverse-proxy)에서 본 "앞에 서서 대신 받아 주는 자리"의 위험이다. 프록시와 뒤의 서버가 요청의 끝을 다르게 보면, 프록시가 막은 경로나 다른 사용자의 응답으로 가는 문이 열린다. 클라우드플레어 안에서는 앞단 계층이 요청을 한 번 정리해 주어서 너그러운 파서가 안전했지만, 그 전제가 없는 곳에서는 같은 너그러움이 취약점이 됐다. 같은 코드라도 어디에 두느냐에 따라 안전성이 달라진다는 예다.

## 2024년 오픈소스 공개와 지금 저장소

2024년 2월 클라우드플레어는 Pingora를 Apache 2.0으로 공개했다. 공개 글은 2022년 글 이후 Pingora가 1,000조 건 가까운 요청을 처리했다고 적었다. 공개하면서 몇 가지를 분명히 했다. Pingora는 실행 파일이 아니라 라이브러리와 도구 모음이다(글의 비유로는 "자동차가 아니라 엔진"이다). 1.0 전에는 API 안정성을 보장하지 않는다. 유닉스가 아닌 OS 지원은 계획에 없다.

지금 저장소 README는 Pingora가 "몇 년 넘게" 초당 4천만 건이 넘는 인터넷 요청을 처리해 왔다고 적는다. 리눅스가 1순위 환경이고, Windows 지원은 "커뮤니티가 최선을 다하는 초기 단계"로 적혀 있다. 최소 지원 Rust 버전은 1.85다. CHANGELOG로 보면 0.1.0이 공개일인 2024년 2월 28일에 나왔고, 이 글을 쓰는 시점의 최신은 2026년 9월의 0.9.0이다. 공개 글이 말한 "1.0 전" 기간이 아직 이어지고 있다.

## 공개 자료가 말하지 않는 것

이 글의 근거는 클라우드플레어가 고른 이야기다. 2022년 글은 바꾼 결과를 보여 주지만, 옮기는 데 몇 년이 걸렸는지, 몇 명이 만들었는지, 옮기는 동안 어떤 장애가 있었는지는 말하지 않는다. "같은 트래픽에서 CPU 70% 감소" 같은 비교의 측정 조건(어떤 머신, 어떤 기간, 어떤 트래픽 구성)도 없다. 두 보안 보고서는 문제가 생겼다는 것을 직접 밝힌 드문 자료지만, 역시 고친 뒤에 쓴 글이다. 2026년 현재 클라우드플레어 안에서 Pingora가 정확히 어떤 경로를 맡는지, NGINX가 어딘가에 남아 있는지는 공개 자료로 알 수 없다.

## 우리 프록시도 Rust로 다시 짤까

클라우드플레어가 직접 만든 조건은 글에 적혀 있다. 하루 1조 건, 셀 수 없이 많은 원본, RFC를 따르지 않는 트래픽까지 받아야 하는 위치, NGINX 둘레에 쌓은 기능이 한계에 닿은 상태. 그리고 그 판단도 몇 년 동안 분기마다 다시 따진 끝에 내렸다. 이 조건이 아니라면 같은 답이 나올 이유가 적다.

대부분의 서비스는 반대 조건이다. 원본이 몇 개뿐이라 워커마다 풀이 있어도 각 워커가 원본으로 가는 요청을 충분히 자주 받는다. 앞의 계산에서 워커 8개, 0.1초 간격이면 재사용률이 99.2%였다. 이때 프록시를 바꿔서 얻을 TTFB는 거의 없다. 오히려 클라우드플레어의 2026년 보고서가 말하듯 너그러운 프록시를 인터넷 앞에 직접 두면 위험이 늘 수 있다. 처음부터 Pingora로 프록시를 짜면 설정 파일 몇 줄 대신 Rust 코드와 그 코드의 보안 검토, 1.0 전의 API 변경을 떠안는다.

작은 팀이 지금 가져올 만한 것은 두 가지다. 하나는 업스트림 keepalive를 실제로 켜고 확인하는 일이다. NGINX 공식 문서 기준으로 1.29.7 전 버전은 `upstream` 블록의 `keepalive`에 더해 `proxy_http_version 1.1`과 비운 `Connection` 헤더가 있어야 재사용되고, 1.29.7부터는 워커마다 32개 한도로 기본으로 켜진다. Ubuntu 24.04의 기본 패키지는 1.24.0이니 앞의 경우다. 원본 서버의 유휴 연결 제한이 프록시보다 짧으면 프록시가 닫힌 연결을 꺼내 쓰다 실패하니, 원본 쪽 제한을 더 길게 둔다. 다른 하나는 재사용률을 지표로 보는 습관이다. 원본 서버에서 초당 새 연결 수(또는 TLS 핸드셰이크 수)와 초당 요청 수를 나란히 그리면 재사용이 되는지 바로 보인다. 클라우드플레어가 성과를 "새 연결 수 3분의 1"로 말한 이유가 그거다.

비슷한 신호가 보이면 이 순서로 본다. 원본의 TTFB는 짧은데 프록시를 거친 TTFB만 길면 프록시와 원본 사이 핸드셰이크가 매번 일어나는지 본다. 원본 서버의 TIME_WAIT 소켓이나 새 연결 수가 요청 수에 비례해 늘면 재사용이 안 되고 있다는 뜻이다. 워커 수를 늘린 뒤 오히려 원본 연결이 늘었다면 풀이 워커마다 나뉜 구조를 의심한다. 프록시를 바꾸거나 직접 만들었다면, 프록시와 뒤 서버가 요청의 끝(Content-Length, Transfer-Encoding, Upgrade)을 같은 규칙으로 읽는지부터 시험한다.

## 면접에서 나올 만한 질문

### 클라우드플레어는 왜 NGINX를 바꿨나요?

2022년 글이 든 가장 큰 이유는 워커 프로세스 구조였다. 요청 하나가 워커 하나에 묶여 코어 사이 부하가 고르지 않았고, 연결 풀이 워커마다 따로라서 워커를 늘릴수록 재사용률이 떨어졌다. 여기에 다른 원본으로 다른 헤더를 붙여 재시도하는 것 같은 기능을 넣기 어려웠고, C의 메모리 안전성 문제와 Lua의 성능·타입 문제가 겹쳤다. 몇 년 동안 분기마다 포크, 다른 프록시로 이전, 직접 만들기를 비교한 끝에 직접 만들기로 했다.

### Pingora로 바꾼 뒤 TTFB가 줄어든 진짜 이유는 무엇인가요?

코드가 빨라져서가 아니라 연결 재사용률이 올라서다. 글은 이전 서비스도 요청을 1ms 안쪽으로 처리했다고 적었다. 모든 스레드가 연결 풀 하나를 같이 쓰니 새 연결이 3분의 1로 줄었고, 한 큰 고객은 재사용률이 87.1%에서 99.92%로 올라 새 연결이 160분의 1이 됐다. 그만큼 TCP·TLS 핸드셰이크 시간이 빠졌다.

### 워커마다 연결 풀을 두면 왜 재사용률이 떨어지나요?

워커를 늘리면 같은 원본으로 가는 요청이 더 많은 풀로 나뉘어, 풀 하나가 다음 요청을 받기까지의 간격이 길어진다. 그 사이 유휴 제한에 걸려 연결이 닫히거나, 놀고 있는 연결이 다른 워커에 있어도 쓰지 못한다. 원본이 아주 많고 원본마다 트래픽이 드문 CDN에서 특히 심하다. 원본이 몇 개뿐이고 트래픽이 꾸준하면 워커별 풀로도 재사용률이 충분히 나온다.

### 연결 풀을 여러 요청이 공유할 때 조심할 점은요?

어떤 연결을 어떤 요청에 내줘도 되는지 키를 정확히 정해야 한다. Pingora는 주소·포트, 스킴, SNI, 클라이언트 인증서, 검증 설정, 대체 인증서 이름, 프록시 설정이 모두 같아야 같은 Peer로 보고 재사용한다. 하나라도 빠지면 다른 고객이나 다른 보안 설정으로 맺은 연결을 탈 수 있다. 오류가 난 연결은 다시 쓰지 않는 규칙도 함께 필요하다.

### 직접 만든 너그러운 HTTP 파서는 어떤 대가를 치렀나요?

요청 밀반입 취약점이 두 번 나왔다. 2025년에는 캐시 적중 때 읽지 않은 요청 본문이 다음 요청으로 해석되는 문제로 실제 CDN 무료 트래픽 일부가 노출돼 22시간 안에 트래픽을 끊었다. 2026년에는 Upgrade와 HTTP/1.0 처리, 기본 캐시 키 문제가 나왔는데, CDN에서는 앞단이 요청을 정리해 줘서 영향이 없었고 Pingora를 직접 인터넷에 둔 사용자가 영향을 받았다. 클라우드플레어는 기본값을 엄격한 RFC 준수로 바꾸겠다고 했다.

### NGINX의 keepalive 32는 무슨 뜻이고, 왜 그것만으로 부족할 수 있나요?

워커 프로세스마다 원본으로 가는 놀고 있는 연결을 최대 32개까지 남겨 둔다는 뜻이고, 전체 연결 수의 상한이 아니다. 남겨 둔 연결은 그 워커만 쓰니, 워커가 많고 원본별 트래픽이 드물면 다음 요청이 오기 전에 원본이 유휴 제한으로 연결을 닫아 버린다. Ubuntu 24.04의 NGINX 1.24.0으로 0.1초 간격 요청 200개를 보냈을 때 워커 1개는 원본 연결 1개, 워커 32개는 120개를 열었다. 1.29.7 전 버전은 HTTP/1.1과 비운 Connection 헤더도 함께 설정해야 한다.

### 원본마다 연결 수를 세는 데 해시 테이블 대신 Count-Min Sketch를 쓴 이유는요?

원본이 수백만 개인데 말썽을 부리는 건 몇 개뿐이라 모든 키의 카운터를 두기엔 메모리가 아깝고, 새 키를 넣을 때의 잠금이 경쟁을 만든다. Count-Min Sketch는 고정 크기 표에 원자적 덧셈만 하니 잠금이 없고, 클라우드플레어 벤치마크에서 메모리를 약 2,000분의 1만 썼다. 많이 세는 쪽으로만 틀리니, 충돌 확률을 아주 낮게 잡고 거절 기준을 건강한 트래픽보다 훨씬 높게 두어 잘못 막는 일을 줄였다.

### 우리 서비스가 원본 서너 개짜리라면 Pingora 같은 프록시를 직접 짜야 하나요?

대부분 아니다. 원본이 적고 트래픽이 꾸준하면 워커별 풀로도 재사용률이 높아서 얻을 TTFB가 작다. 직접 짜면 설정 대신 코드와 그 보안 검토, 1.0 전 API 변경을 떠안고, 너그러운 파서를 인터넷 앞에 두는 위험도 생긴다. 먼저 기존 프록시의 업스트림 keepalive가 실제로 동작하는지, 원본의 새 연결 수와 요청 수를 나란히 놓고 확인하는 게 순서다.
