[Word Break](https://leetcode.com/problems/word-break/)는 LeetCode 139번이다. 띄어쓰기 없는 문자열이 사전의 단어들로 빈틈없이 나뉘는지 묻는다. 지금까지 본 1차원 DP([계단 오르기](/posts/leetcode-climbing-stairs), [House Robber](/posts/leetcode-house-robber), [Coin Change](/posts/leetcode-coin-change))는 칸이 숫자였는데, 이 문제는 칸이 "문자열의 i번째 자리"다. 계단 오르기의 걸음 크기가 사전의 단어로, 동전 값이 단어 길이로 바뀌었다고 보면 같은 뼈대가 그대로 보인다.

면접에서는 풀이 하나보다 "왜 메모가 필요한가", "부분 문자열을 만드는 비용까지 넣으면 복잡도가 얼마인가", "트라이를 쓰면 무엇이 좋아지나", "나누는 방법을 전부 돌려 달라면?"을 묻는다. 이 글은 탐욕 두 가지가 틀리는 걸 보고, 재귀부터 트라이까지 일곱 풀이를 차례로 놓는다. DP의 일반론은 [동적 계획법 글](/posts/dynamic-programming)에, 트라이 자체는 [트라이 글](/posts/ds-trie)과 [Implement Trie](/posts/leetcode-implement-trie)에 있다. 코드는 Node.js 22, Python 3, Java 21에서 직접 돌렸다.

## 사전 단어로 빈틈없이 자르기

문자열 `s`와 단어 목록 `wordDict`가 주어진다. `s`를 하나 이상의 단어로 나눴을 때 모든 조각이 사전에 있으면 `true`, 그렇게 나눌 방법이 없으면 `false`를 돌려준다. 같은 단어를 여러 번 써도 된다.

풀이에 영향을 주는 제약은 이렇다.

- `s` 길이는 1 이상 300 이하, 영어 소문자만 있다.
- 단어는 1000개 이하이고 길이는 1 이상 20 이하다. 단어끼리는 서로 다르다.

문자열이 300자라서 O(n²)이나 O(n³)도 들어간다. 반대로 "나누는 방법"의 수는 지수라 늘어놓는 풀이는 안 된다. 단어 길이가 20 이하라는 조건은 뒤에서 반복문을 크게 줄이는 데 쓴다.

## sunflower를 손으로 잘라 본다

글 끝까지 쓸 예시다.

```text
s        = "sunflower"
wordDict = ["sun", "sunf", "flow", "flower", "er"]
```

앞에서부터 단어를 떼어 본다.

```text
sun | flower           → 성공
sun | flow | er        → 성공
sunf | lower           → lower가 사전에 없다. 막힌다
```

답은 `true`다. 두 가지로 나뉜다. 그리고 "sunf"는 사전에 있는 단어인데도 그 뒤가 막히는 막다른 길이다. 이 막다른 길 때문에 단순한 방법이 틀린다.

## 가장 긴 단어부터 떼면 막힌다

### 가장 긴 단어부터

지금 자리에서 사전에 있는 가장 긴 단어를 떼는 탐욕을 생각해 보자. 예시에서 맨 앞의 가장 긴 단어는 "sunf"다. 떼고 나면 "lower"가 남는데, "l"로 시작하는 단어가 사전에 없어서 `false`를 낸다. 답은 `true`다.

### 가장 짧은 단어부터

반대로 가장 짧은 단어를 떼면 예시는 "sun", "flow", "er"로 성공한다. 하지만 `"abcd"`, `["ab", "abc", "d"]`이면 "ab"를 떼고 "cd"에서 막혀 `false`를 낸다. "abc" + "d"로 나뉘니 답은 `true`다.

두 탐욕 모두 한 번 자른 자리를 되돌리지 않는다. 어디서 자르는 게 맞는지는 뒤를 끝까지 봐야 알 수 있다. 그러면 자를 수 있는 자리를 모두 시도해야 한다.

## 자를 수 있는 자리를 모두 시도한다

`can(start)`를 "`start`번 글자부터 끝까지를 단어로 나눌 수 있나"로 정한다. `start`에서 시작하는 모든 접두사를 보고, 사전에 있으면 그 뒤를 다시 같은 질문으로 넘긴다.

```js
function wordBreak(s, wordDict) {
  const dict = new Set(wordDict);
  function can(start) {
    if (start === s.length) return true;              // 끝까지 잘랐다
    for (let end = start + 1; end <= s.length; end++) {
      // s[start..end)가 단어이고, 그 뒤도 나눌 수 있으면 성공
      if (dict.has(s.slice(start, end)) && can(end)) return true;
    }
    return false;                                     // 어떤 자리에서 잘라도 안 된다
  }
  return can(0);
}
```

사전은 `Set`에 넣어 단어 확인을 평균 O(1)에 한다(문자열 해시를 계산하는 데 길이만큼 걸리긴 한다). 답이 `true`인 입력에서는 첫 성공에서 바로 돌아오니 대개 빠르다. 문제는 `false`인 입력이다. 모든 길을 끝까지 다 가 봐야 한다.

최악은 `"aaa…ab"`에 사전이 `["a", "aa", "aaa", …]`인 경우다. 앞쪽 a들은 어떻게 잘라도 사전에 있어서 나누는 방법이 2^(n-1)가지에 가깝고, 마지막 b 때문에 전부 실패한다. 사전을 a 1개부터 10개짜리까지로 두고 a의 개수를 늘리며 재 봤다.

```text
naive n 15 false calls 32688 6.5ms
naive n 20 false calls 1043456 57.9ms
naive n 25 false calls 33308752 2060.2ms
naive n 28 false calls 266077952 14896.0ms
```

a가 5개 늘 때마다 호출이 32배씩 는다. 28개에서 15초다. 이 문제의 `s`는 300자까지라 이 풀이로는 어림없다.

그런데 이 호출들이 묻는 질문은 `can(0)`부터 `can(n)`까지 n+1가지뿐이다. "aaaa"를 "a|aaa"로 자르든 "aa|aa"로 자르든 "aaa|a"로 자르든 결국 `can(4)`를 묻는다. 같은 자리를 다시 묻는 게 폭발의 원인이다.

## 같은 자리를 두 번 묻지 않는다

`can(start)`의 답을 적어 둔다. 특히 `false`를 적어 두는 게 중요하다. 이 문제의 폭발은 전부 실패하는 길에서 일어나기 때문이다.

```js
function wordBreak(s, wordDict) {
  const dict = new Set(wordDict);
  const memo = new Map(); // start -> 그 자리부터 끝까지 나눌 수 있나
  function can(start) {
    if (start === s.length) return true;
    if (memo.has(start)) return memo.get(start);
    for (let end = start + 1; end <= s.length; end++) {
      if (dict.has(s.slice(start, end)) && can(end)) {
        memo.set(start, true);
        return true;
      }
    }
    memo.set(start, false);  // 실패도 적는다. 이게 빠지면 메모가 듣지 않는다
    return false;
  }
  return can(0);
}
```

`can(start)`의 본문은 자리마다 한 번만 돈다. 본문 안에서 `end`가 최대 n번 돌고, 매번 `s.slice`로 길이 최대 n인 문자열을 만들고 해시를 계산한다. 그래서 시간은 O(n² × n) = O(n³)이다. 흔히 O(n²)이라고 말하는데, 부분 문자열을 만드는 비용을 빼먹은 값이다. 면접에서 이 차이를 짚으면 좋다. n = 300이면 n³은 2700만이라 그래도 통과한다. 공간은 메모 O(n)과 재귀 깊이 O(n)이다. 깊이가 최대 300이라 이 문제에서는 스택이 넘치지 않는다.

`memo.set(start, false)`를 빼면 어떻게 될까. 성공한 자리만 기억하고 실패한 자리는 계속 다시 시도하니, 앞의 "aaa…ab" 입력에서 메모 없는 재귀와 똑같이 폭발한다. `true`인 입력에서는 차이가 없어서 이 버그는 예제 테스트를 다 통과한다.

## 칸막이 자리마다 동그라미를 친다

재귀를 뒤집는다. 이번에는 앞쪽을 기준으로 정의한다. `dp[i]`는 "앞의 i글자 `s[0..i)`를 단어로 나눌 수 있나"다. `dp[0]`은 빈 문자열이라 `true`다. `dp[i]`가 `true`가 되려면, 그보다 앞의 어떤 자리 j에서 `dp[j]`가 `true`이고 `s[j..i)`가 사전에 있으면 된다. 마지막 조각이 `s[j..i)`라는 뜻이다.

```js
function wordBreak(s, wordDict) {
  const dict = new Set(wordDict);
  const n = s.length;
  const dp = new Array(n + 1).fill(false); // dp[i]: 앞의 i글자를 나눌 수 있나
  dp[0] = true;                            // 빈 문자열
  for (let i = 1; i <= n; i++) {
    for (let j = 0; j < i; j++) {
      // 앞의 j글자를 나눌 수 있고, 마지막 조각 s[j..i)가 단어면 된다
      if (dp[j] && dict.has(s.slice(j, i))) {
        dp[i] = true;
        break;                             // 하나만 찾으면 된다
      }
    }
  }
  return dp[n];
}
```

[Coin Change](/posts/leetcode-coin-change)의 "마지막 동전"이 여기서는 "마지막 조각"이다. 동전은 값이 정해져 있었지만 조각은 j를 어디로 고르느냐에 따라 길이가 달라진다.

### 마지막 조각은 20글자를 넘지 않는다

사전 단어가 최대 20글자다. 그러면 마지막 조각 `s[j..i)`가 20글자를 넘는 j는 볼 필요가 없다. j를 `i - maxLen`부터만 돌린다.

```js
function wordBreak(s, wordDict) {
  const dict = new Set(wordDict);
  let maxLen = 0;
  for (const w of wordDict) maxLen = Math.max(maxLen, w.length); // 가장 긴 단어 길이
  const n = s.length;
  const dp = new Array(n + 1).fill(false);
  dp[0] = true;
  for (let i = 1; i <= n; i++) {
    for (let j = Math.max(0, i - maxLen); j < i; j++) { // 마지막 조각이 maxLen 이하인 j만
      if (dp[j] && dict.has(s.slice(j, i))) {
        dp[i] = true;
        break;
      }
    }
  }
  return dp[n];
}
```

이제 i마다 j가 최대 L(= `maxLen`)개, `slice`도 길이 L 이하라 시간은 O(n × L²)이다. n = 300, L = 20이면 12만 남짓이다. a 299개 뒤에 b가 붙은 입력, 사전 a 1~10개짜리로 재 보니 j 범위를 줄이지 않은 표는 약 9.5ms, 줄인 표는 0.06ms였다. 이 풀이가 기본 답이다.

## 단어 쪽에서 앞으로 뻗어 나가기

반복문을 반대로 돌릴 수도 있다. "i까지 오려면 어디서 왔나"를 묻는 대신, `dp[i]`가 `true`인 자리마다 "여기서 어떤 단어를 붙일 수 있나"를 보고 앞으로 동그라미를 친다.

```js
function wordBreak(s, wordDict) {
  const n = s.length;
  const dp = new Array(n + 1).fill(false);
  dp[0] = true;
  for (let i = 0; i < n; i++) {
    if (!dp[i]) continue;                 // 여기까지 못 오면 여기서 뻗을 수 없다
    for (const w of wordDict) {
      if (s.startsWith(w, i)) dp[i + w.length] = true; // i에서 w를 붙이면 i + |w|까지 온다
    }
  }
  return dp[n];
}
```

`startsWith(w, i)`는 새 문자열을 만들지 않고 i 자리부터 바로 비교한다. 시간은 O(n × m × L)(m은 단어 수)이다. 단어가 적고 문자열이 길 때 유리하고, 단어가 1000개면 앞의 풀이보다 불리할 수 있다. 앞으로 뻗는 방식은 [Coin Change](/posts/leetcode-coin-change)에서 BFS로 금액을 넓혀 간 것과 같은 방향이다.

0 → 3 → 9와 0 → 3 → 7 → 9 두 길이 있고, 4번 정점에서는 나가는 간선이 없다. 길이 있는지는 [BFS나 DFS](/posts/ds-graph-bfs-dfs)로 찾는다.

```js
function wordBreak(s, wordDict) {
  const dict = new Set(wordDict);
  const n = s.length;
  const seen = new Array(n + 1).fill(false); // 이미 도달한 자리
  const queue = [0];
  seen[0] = true;
  while (queue.length) {
    const start = queue.shift();
    for (let end = start + 1; end <= n; end++) {
      if (!seen[end] && dict.has(s.slice(start, end))) {
        if (end === n) return true;          // 끝 자리에 닿았다
        seen[end] = true;
        queue.push(end);
      }
    }
  }
  return false;
}
```

`seen`이 메모와 같은 역할을 한다. 한 번 도달한 자리는 다시 큐에 넣지 않으니 자리마다 한 번만 넓힌다. 복잡도는 메모 풀이와 같은 O(n³)이고, j 범위를 `maxLen`으로 줄이면 O(n × L²)이 된다. 이 관점의 쓸모는 변형에서 드러난다. "가장 적은 단어 수로 나눠라"는 이 그래프의 최단 경로라 BFS가 바로 답을 준다.

`queue.shift()`는 JavaScript 배열에서 O(n)이다. 300자면 문제없지만 큰 입력에서는 읽는 위치를 가리키는 인덱스를 따로 두는 게 낫다.

## 트라이로 한 번에 훑기

앞으로 뻗는 풀이에서 `dp[i]`가 `true`인 자리마다 단어 1000개를 다 대 봤다. 이걸 [트라이](/posts/ds-trie)로 바꾸면, i에서 글자를 하나씩 따라 내려가며 단어 끝 표시를 만날 때마다 동그라미를 친다. 트라이에 없는 글자를 만나면 그 자리에서 바로 멈춘다.

```js
function wordBreak(s, wordDict) {
  const root = {};
  for (const w of wordDict) {                 // 단어를 트라이에 넣는다
    let node = root;
    for (const ch of w) node = node[ch] ??= {};
    node.end = true;                          // 여기서 끝나는 단어가 있다
  }
  const n = s.length;
  const dp = new Array(n + 1).fill(false);
  dp[0] = true;
  for (let i = 0; i < n; i++) {
    if (!dp[i]) continue;
    let node = root;
    for (let j = i; j < n; j++) {             // i부터 한 글자씩 트라이를 따라간다
      node = node[s[j]];
      if (!node) break;                       // 이 접두사로 시작하는 단어가 없다
      if (node.end) dp[j + 1] = true;         // s[i..j]가 단어다
    }
  }
  return dp[n];
}
```

자리 i마다 트라이를 최대 L단계 내려가고, 한 단계가 O(1)이라 시간은 O(n × L)이다. 트라이를 만드는 데 사전 전체 글자 수만큼 O(m × L)이 들고 공간도 그만큼이다. 부분 문자열을 만들지도, 해시를 계산하지도 않는다는 게 앞 풀이들과의 차이다. 사전 a 1~20개짜리, a 299개 + b 입력에서 0.2ms 안쪽이었다.

이 문제의 제약에서는 maxLen 표와 트라이의 차이가 크지 않다. 트라이가 확실히 유리해지는 건 사전이 크고, 같은 사전으로 여러 문자열을 검사할 때다. 한 번 만든 트라이를 계속 쓰기 때문이다. [Word Search II](/posts/leetcode-word-search-ii)처럼 격자에서 여러 단어를 동시에 찾는 문제가 같은 이유로 트라이를 쓴다.

## Python과 Java로 옮길 때

```python
from typing import List

class Solution:
    def wordBreak(self, s: str, wordDict: List[str]) -> bool:
        words = set(wordDict)
        max_len = max(map(len, wordDict))
        n = len(s)
        dp = [False] * (n + 1)          # dp[i]: 앞의 i글자를 단어로 나눌 수 있나
        dp[0] = True                    # 빈 문자열은 나눌 수 있다
        for i in range(1, n + 1):
            for j in range(max(0, i - max_len), i):
                if dp[j] and s[j:i] in words:
                    dp[i] = True
                    break
        return dp[n]
```

예시에 `True`, "sunflowers"에 `False`, a 299개 + b에 `False`가 나왔다. Python의 `s[j:i]`도 새 문자열을 만드는 O(길이) 연산이다. `dp[j] and ...`의 순서를 지키면 `dp[j]`가 거짓일 때 슬라이싱 자체를 건너뛴다. 탑다운으로 쓰려면 `@functools.cache`를 붙인 `can(start)`가 짧은데, 깊이가 최대 300이라 재귀 한도 1000에는 안 걸린다.

```java
import java.util.*;

class Solution {
    public boolean wordBreak(String s, List<String> wordDict) {
        Set<String> words = new HashSet<>(wordDict);
        int maxLen = 0;
        for (String w : wordDict) maxLen = Math.max(maxLen, w.length());
        int n = s.length();
        boolean[] dp = new boolean[n + 1];   // dp[i]: 앞의 i글자를 나눌 수 있나
        dp[0] = true;
        for (int i = 1; i <= n; i++) {
            for (int j = Math.max(0, i - maxLen); j < i; j++) {
                if (dp[j] && words.contains(s.substring(j, i))) {
                    dp[i] = true;
                    break;
                }
            }
        }
        return dp[n];
    }
}
```

Java의 `substring`은 JDK 7u6부터 새 문자 배열을 복사한다. 그 전에는 원본 배열을 공유해서 O(1)이었다. 그래서 오래된 자료에 "substring은 O(1)"이라고 적힌 경우가 있는데, 지금 JDK에서는 길이만큼 든다. `HashSet<String>`의 `contains`도 문자열의 `hashCode`를 계산하는데, `String`은 해시를 한 번 계산하면 객체 안에 저장하지만 `substring`이 매번 새 객체를 만드니 매번 다시 계산한다. 이 비용을 없애려면 트라이를 쓴다.

## 일곱 풀이를 나란히 놓으면

n은 문자열 길이, m은 단어 수, L은 가장 긴 단어 길이다.

| 풀이 | 시간 | 추가 공간 | 언제 고르나 |
|---|---|---|---|
| 모든 자리 재귀 | O(2ⁿ) | O(n) 스택 | 점화식 확인용. "aaa…ab"에서 폭발한다 |
| 탑다운 메모 | O(n³) | O(n) | 재귀에서 바로 옮길 때. false도 꼭 적는다 |
| 바텀업 dp[i] | O(n³) | O(n) | 출발점 |
| 바텀업 + maxLen | O(n × L²) | O(n) | 기본 답 |
| 단어로 앞으로 뻗기 | O(n × m × L) | O(n) | 단어가 적을 때 |
| 자리 그래프 BFS | O(n³), 줄이면 O(n × L²) | O(n) | 최소 단어 수 같은 최단 경로 변형 |
| 트라이로 훑기 | O(n × L) + 트라이 O(m × L) | O(m × L) | 사전이 크거나 여러 문자열을 검사할 때 |

## 틀리기 쉬운 자리

### 실패를 메모하지 않는 경우

앞에서 짚었다. `true`만 적고 `false`를 안 적으면 실패하는 입력에서 메모가 전혀 듣지 않는다. 예제는 다 통과하고 "aaa…ab" 같은 입력에서만 시간 초과가 난다.

### dp 크기를 n으로 잡는 경우

`dp[i]`가 "앞의 i글자"라 i는 0부터 n까지 n+1개다. 크기를 n으로 잡으면 마지막 칸 `dp[n]`이 없다. "i번째 글자에서 끝나는가"로 n칸을 쓰면 빈 문자열 바닥이 사라져 `dp[0]`을 따로 계산해야 해서 코드가 꼬인다. 빈 앞부분을 0번 칸으로 두는 게 가장 단순하다.

### 슬라이스 끝 인덱스를 하나 틀리는 경우

`s.slice(j, i)`는 j부터 i-1까지다. `s.slice(j, i + 1)`로 쓰면 다음 글자까지 들어간다. 예시에서 dp[3]을 구할 때 "sunf"를 보게 되어 결과가 한 칸씩 밀린다. 끝을 포함하지 않는 반열린 구간 `[j, i)`로 일관되게 생각한다.

### 사전을 배열 그대로 쓰는 경우

`wordDict.includes(piece)`는 단어 수 m만큼 걸린다. 시간이 m배로 늘어 O(n² × m × L)이 된다. `Set`이나 트라이로 바꾼다.

## 면접관이 조건을 바꾸면

### 나누는 방법을 모두 돌려 달라면

LeetCode 140 Word Break II다. 자리마다 "여기서 끝까지 나누는 문장 목록"을 메모한다.

```js
function wordBreakAll(s, wordDict) {
  const dict = new Set(wordDict);
  const memo = new Map(); // start -> 그 자리부터 끝까지의 문장 목록
  function go(start) {
    if (start === s.length) return [""];
    if (memo.has(start)) return memo.get(start);
    const out = [];
    for (let end = start + 1; end <= s.length; end++) {
      const w = s.slice(start, end);
      if (!dict.has(w)) continue;
      for (const rest of go(end)) out.push(rest ? w + " " + rest : w);
    }
    memo.set(start, out);
    return out;
  }
  return go(0);
}
```

예시에서 `["sun flow er", "sun flower"]`가 나왔다. 답의 개수 자체가 지수일 수 있어서("aaaa…"에 ["a", "aa"]) 어떤 풀이도 출력 크기보다 빠를 수 없다. 그래서 먼저 이 글의 `true`/`false` 풀이로 나눌 수 있는지 확인하고, 안 되면 바로 빈 목록을 돌려주는 게 실전 요령이다. 그렇게 하지 않으면 "aaa…ab" 같은 입력에서 거대한 중간 목록만 만들다 끝난다.

### 가장 적은 단어 수로 나누라면

앞의 자리 그래프에서 0부터 n까지의 최단 경로다. BFS 단계를 세거나, `dp[i]`를 불리언 대신 "앞의 i글자를 나누는 최소 단어 수"로 바꿔 `dp[i] = min(dp[j] + 1)`로 채운다. [Coin Change](/posts/leetcode-coin-change)와 같은 모양이 된다.

```js
function minWords(s, wordDict) {
  const dict = new Set(wordDict);
  let maxLen = 0;
  for (const w of wordDict) maxLen = Math.max(maxLen, w.length);
  const n = s.length;
  const dp = new Array(n + 1).fill(Infinity); // dp[i]: 앞의 i글자를 나누는 최소 단어 수
  dp[0] = 0;
  for (let i = 1; i <= n; i++) {
    for (let j = Math.max(0, i - maxLen); j < i; j++) {
      // 단어 확인보다 값 비교를 먼저 해서, 줄어들 수 없는 j는 슬라이스를 만들지 않는다
      if (dp[j] + 1 < dp[i] && dict.has(s.slice(j, i))) dp[i] = dp[j] + 1;
    }
  }
  return dp[n] === Infinity ? -1 : dp[n];
}
```

예시에서 2("sun flower"), "sunflowers"에서 -1, "aaaa"와 ["a", "aa"]에서 2가 나왔다. 불리언 버전과 달리 `break`로 멈출 수 없다. 더 짧은 분리가 뒤의 j에서 나올 수 있어서 모든 j를 봐야 한다.

### 사전에 없는 글자가 남아도 된다면

LeetCode 2707 [Extra Characters in a String](/posts/leetcode-extra-characters-in-a-string)이다. 남는 글자 수를 최소로 하라는 문제라 `dp[i]`를 "앞의 i글자에서 남는 글자의 최소 수"로 두고, "i-1번 글자를 버린다(`dp[i-1] + 1`)"는 선택지를 하나 더 넣는다.

### 사전의 단어끼리 서로를 이어 만들 수 있나라면

LeetCode 472 Concatenated Words다. 사전의 단어마다 "자기 자신을 뺀 나머지 단어로 Word Break가 되나"를 묻는다. 단어를 길이 순으로 정렬하면 짧은 단어들로만 긴 단어를 만들 수 있으니, 짧은 것부터 검사하며 사전에 추가해 나간다. 단어가 많아서 트라이가 효과를 본다.

### 문자열이 아주 길고 사전이 고정이라면

검색어 분리, 해시태그 띄어쓰기처럼 실제로 쓰이는 형태다. 사전을 트라이(또는 여러 패턴을 한 번에 찾는 Aho-Corasick 오토마톤)로 미리 만들어 두고, 문자열은 트라이 풀이로 O(n × L)에 처리한다. 나눌 수 있는 방법이 여러 개면 단어 빈도로 점수를 매겨 가장 그럴듯한 분리를 고르는데, 그건 `dp[i]`에 불리언 대신 최고 점수를 담는 같은 DP다.

비슷한 문제로는 [Decode Ways](/posts/leetcode-decode-ways)(한 글자 또는 두 글자 조각), [Palindrome Partitioning](/posts/leetcode-palindrome-partitioning)(조각이 회문이어야 하는 백트래킹), Concatenated Words(472)가 있다.

## 면접에서 나올 만한 질문

### 왜 탐욕으로 안 되나요?

어디서 자르는 게 맞는지는 뒤를 끝까지 봐야 알기 때문이다. 가장 긴 단어부터 떼면 "sunflower"에서 "sunf"를 떼고 "lower"에서 막히고, 가장 짧은 단어부터 떼면 "abcd"에서 "ab"를 떼고 "cd"에서 막힌다. 둘 다 나눌 수 있는 입력이다.

### dp[i]는 무엇을 뜻하고 점화식은 무엇인가요?

`dp[i]`는 앞의 i글자를 단어로 나눌 수 있는지다. `dp[0]`은 빈 문자열이라 참이고, `dp[i]`는 어떤 j에서 `dp[j]`가 참이고 `s[j..i)`가 사전에 있으면 참이다. 마지막 조각이 무엇인지로 경우를 나눈 것이다.

### 시간 복잡도가 O(n²)인가요, O(n³)인가요?

부분 문자열을 만드는 비용까지 세면 O(n³)이다. i와 j의 이중 반복이 O(n²)이고, 매번 길이 최대 n인 문자열을 만들고 해시를 계산한다. 단어 최대 길이 L로 j 범위를 줄이면 O(n × L²), 트라이를 쓰면 O(n × L)이 된다.

### 메모에 false도 적어야 하나요?

적어야 한다. 이 문제의 지수 폭발은 모두 실패하는 길에서 생기는데, 실패를 안 적으면 같은 자리를 계속 다시 시도한다. 성공 입력에서는 차이가 없어 예제를 다 통과하는 버그라 더 위험하다.

### 트라이를 쓰면 무엇이 좋아지나요?

자리마다 부분 문자열을 만들고 해시를 계산하는 대신, 글자를 하나씩 따라 내려가며 단어 끝을 만날 때마다 표시한다. 사전에 없는 접두사를 만나는 순간 멈추니 낭비가 없고, 시간이 O(n × L)로 준다. 사전이 크거나 같은 사전으로 여러 문자열을 검사할 때 이득이 크다.

### 모든 분리 결과를 돌려 달라면 복잡도는 어떻게 되나요?

출력 크기 자체가 지수일 수 있어서 출력에 비례하는 시간이 든다. 자리마다 문장 목록을 메모하면 같은 접미사를 다시 계산하지는 않는다. 실전에서는 먼저 불리언 DP로 나눌 수 있는지 확인하고, 불가능하면 바로 빈 목록을 돌려줘 불필요한 목록 생성을 막는다.
