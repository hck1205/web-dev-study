<EasyIntro>
  쿠버네티스에 설정 파일 하나를 올리면 만들어졌다는 한 줄이 나오고, 몇 초 뒤 컨테이너 세 개가 돌기 시작한다. 그 사이에 누가 무엇을 했는지 물으면 대개 쿠버네티스가 띄웠다는 말에서 멈춘다. 그런데 장애는 바로 그 사이에서 난다.

  쿠버네티스는 큰 프로그램 하나가 아니라 작은 부품들의 모임이다. 가운데에 모든 요청을 받는 창구인 API 서버가 있고, 그 뒤에 상태를 저장하는 창고, 어느 서버에 띄울지 고르는 배치 담당, 원하는 개수를 맞추는 관리 담당이 있으며, 각 서버에는 실제로 컨테이너를 띄우는 일꾼이 있다. 부품들은 서로를 직접 부르지 않고 창구에 적힌 내용을 지켜보다가 자기 몫이 생기면 움직인다.

  그래서 설정을 올리는 일은 창고에 적는 것으로 끝나고, 나머지는 부품들이 차례로 채운다. 부품 하나가 멈추면 그 부품이 맡은 칸에서만 흐름이 서고, 어디서 끊겼는지 보면 어느 부품을 봐야 할지 나온다.
</EasyIntro>

`kubectl apply -f web.yaml`을 치면 `deployment.apps/web created`가 한 줄 나오고 끝난다. 몇 초 뒤 Pod 세 개가 Running이 된다. 그 사이에 누가 무엇을 했는지 물으면 대개 "쿠버네티스가 띄웠다"에서 말이 멈춘다. 그런데 장애는 바로 그 사이에서 난다. Deployment는 만들어졌는데 ReplicaSet이 안 생기고, Pod는 생겼는데 노드가 안 정해지고, 노드는 정해졌는데 STATUS가 몇 분째 Running인 채로 실제로는 죽어 있다. 어느 부품이 멈췄는지 알면 어디부터 볼지 바로 정해진다.

이 글은 쿠버네티스 클러스터를 이루는 부품을 하나씩 보고, Deployment 하나를 apply했을 때 그 부품들이 어떤 순서로 움직이는지 따라간다. 그리고 부품을 하나씩 일부러 멈춰서 무엇이 망가지는지 본다. 실습은 kwok(v0.6.1)으로 만든 클러스터에서 했다. kwok은 진짜 etcd, kube-apiserver, kube-scheduler, kube-controller-manager를 띄우고 노드와 kubelet만 흉내 낸다. 그래서 컨트롤 플레인 쪽 출력은 전부 실제이고(서버 v1.30.4, kubectl v1.31.4), 컨테이너가 실제로 도는 부분은 실제 형식대로 쓴 예시로 표시했다.

이 주제의 다른 글: 오브젝트의 apiVersion, spec, status가 무엇인지는 [API 오브젝트](/posts/k8s-api-objects)에서, 컨트롤러가 원하는 상태를 맞추는 반복은 [컨트롤러와 reconcile](/posts/k8s-controllers-reconcile)에서, apply가 필드를 합치는 규칙은 [kubectl apply와 SSA](/posts/kubectl-apply-ssa)에서 다룬다. 이 글은 부품과 그 사이의 흐름만 본다.

## 모든 부품은 API 서버하고만 이야기한다

쿠버네티스 클러스터는 두 부분으로 나뉜다. 클러스터 전체의 상태를 저장하고 결정을 내리는 컨트롤 플레인(control plane), 그리고 실제로 컨테이너를 돌리는 워커 노드다.

컨트롤 플레인에는 다섯 부품이 있다.

- **kube-apiserver**: 클러스터의 유일한 입구다. kubectl도, 다른 부품도 전부 여기에 HTTP 요청을 보낸다. 인증, 권한 확인, 검증을 하고 etcd에 쓴다.
- **etcd**: 클러스터의 모든 오브젝트를 저장하는 키-값 저장소다. Raft로 여러 대가 같은 값을 지킨다.
- **kube-scheduler**: 노드가 정해지지 않은 Pod를 찾아 어느 노드에 둘지 정한다.
- **kube-controller-manager**: Deployment, ReplicaSet, Node, Job 같은 컨트롤러 수십 개를 한 프로세스에 묶어 돌린다. 각자 원하는 상태와 실제 상태를 비교해 차이를 메운다.
- **cloud-controller-manager**: 클라우드 API와 이어지는 컨트롤러다. LoadBalancer Service에 실제 로드 밸런서를 만들고, 노드에 클라우드 정보를 붙이고, 지워진 VM의 노드를 정리한다. 클라우드가 없으면 없다.

워커 노드마다 세 부품이 돈다.

- **kubelet**: 노드의 관리인이다. 자기 노드에 배정된 Pod를 API 서버에서 받아 컨테이너 런타임에 띄우라고 시키고, 상태를 API 서버에 보고한다.
- **kube-proxy**: Service의 가상 IP로 온 트래픽이 실제 Pod로 가도록 노드의 iptables나 nftables 규칙을 만든다. CNI가 이 일을 대신하는 구성(Cilium 등)도 있다.
- **컨테이너 런타임**: containerd나 CRI-O. kubelet과 CRI라는 gRPC 규약으로 이야기한다.

이 구조에서 가장 중요한 규칙은 "API 서버만 etcd에 닿는다"이다. 스케줄러와 컨트롤러는 서로 직접 부르지 않는다. 모두 API 서버를 통해 오브젝트를 읽고(watch), 바꾸고(update), 그 변화를 다른 부품이 다시 watch로 받는다. 아래 그림에서 다음을 누르면 요청 하나가 이 길을 따라 퍼지는 모습을 볼 수 있다.

이렇게 만든 덕분에 부품 하나가 죽어도 나머지는 계속 돈다. 서로를 부르지 않으니 기다릴 상대가 없다. 죽은 부품이 돌아오면 API 서버에서 현재 상태를 다시 읽고 밀린 일을 처리한다. 뒤에서 이걸 직접 확인한다.

실습 클러스터에서 부품 목록과 API 서버의 준비 상태를 보면 이렇다.

```bash
# kwok 클러스터를 만들고 노드 두 개를 붙인다
kwokctl create cluster --name v20-arch --runtime binary
kwokctl scale node --replicas 2 --name v20-arch
# 클러스터를 이루는 부품 목록
kwokctl get components --name v20-arch
# API 서버의 준비 상태를 검사 항목별로 본다
kubectl get --raw '/readyz?verbose'
```

`kwok-controller`가 kubelet 대신 노드와 Pod 상태를 흉내 내는 부품이다. `/readyz`에서 봐야 할 줄은 `etcd ok`와 `etcd-readiness ok`다. API 서버는 etcd에 닿지 못하면 준비되지 않은 것으로 보고한다. 로드 밸런서가 여러 API 서버 중 건강한 것만 고를 때 이 주소를 헬스 체크로 쓴다. 살아만 있는지 보는 `/livez`는 따로 있다.

## kubectl apply 한 줄이 지나가는 길

이제 Deployment 하나를 apply하고 그 뒤에 일어나는 일을 순서대로 보자. 매니페스트는 이것이다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: web
          image: nginx:1.27
          resources:
            requests: { cpu: 100m, memory: 64Mi }
```

```bash

kubectl apply -f web.yaml -v=6
```

API 서버 뒤에서 일어난 일은 이벤트로 남는다. apply 직후의 이벤트를 보면 누가 무엇을 했는지 그대로 나온다.

```bash
# 최근 이벤트를 시간 순서로 본다 (kubectl 1.26부터 있는 events 명령)
kubectl events
# 이벤트를 남긴 부품별로 센다
```

## watch 하나로 상태가 흘러간다

부품들이 API 서버를 계속 물어보는(polling) 대신 watch로 변화를 받는다는 게 실제로 어떤 모습인지 보자. Pod 목록에 watch를 열어 두고 Deployment를 6개로 늘렸다.

```bash
# Pod 변화를 HTTP 스트림으로 받는다 (resourceVersion 없이 열면 현재 목록이 ADDED로 먼저 온다)
kubectl get --raw "/api/v1/namespaces/default/pods?watch=1" > watch.json &
kubectl scale deploy web --replicas=6
# 이벤트 종류, Pod 이름, resourceVersion, 노드, phase만 뽑는다
jq -r '[.type, .object.metadata.name, .object.metadata.resourceVersion, (.object.spec.nodeName // "-"), .object.status.phase] | @tsv' watch.json
```

```text
ADDED	web-6957d7fc7f-z7dp5	489	node-000000	Running
ADDED	web-6957d7fc7f-p48kx	567	-	Pending
MODIFIED	web-6957d7fc7f-p48kx	569	node-000001	Pending
MODIFIED	web-6957d7fc7f-p48kx	574	node-000001	Running
```

(앞의 기존 Pod ADDED 줄 몇 개는 줄였다.) 새 Pod 하나가 세 번 나타난다. 같은 오브젝트를 세 부품이 차례로 고친 흔적이다.

`resourceVersion`은 etcd의 리비전 번호에서 나온다. 고칠 때마다 오르고, 고치는 쪽은 "내가 읽은 버전이 아직 최신일 때만 바꿔라"를 조건으로 보낸다. 다른 부품이 먼저 바꿨으면 `409 Conflict`를 받고 다시 읽는다. [낙관적 락](/posts/optimistic-locking)과 같은 방식이다. 이 덕분에 여러 컨트롤러가 같은 오브젝트를 동시에 고쳐도 서로의 변경을 덮어쓰지 않는다.

실제 컨트롤러는 watch를 직접 쓰기보다 informer라는 라이브러리를 쓴다. 처음에 목록을 한 번 받아(list) 메모리 캐시에 두고, 그 뒤로는 watch로 받은 변화만 캐시에 반영한다. 컨트롤러가 읽는 건 이 로컬 캐시라서 API 서버에 부담이 적다. 대신 캐시는 아주 잠깐 늦을 수 있고, 그래서 컨트롤러는 "지금 본 상태가 최신이 아닐 수 있다"는 가정으로 짜인다.

## etcd에는 무엇이 어떻게 들어 있나

API 서버가 쓴 오브젝트는 etcd에 `/registry/<리소스>/<네임스페이스>/<이름>` 키로 들어간다. kwok은 etcdctl을 바로 쓸 수 있게 해 준다.

```bash
# Deployment 값의 앞 64바이트를 본다
```

값은 JSON이 아니라 `k8s\0`로 시작하는 protobuf다. 그래서 etcd를 직접 들여다보는 건 디버깅용일 뿐이고, 직접 고치면 API 서버의 검증과 어드미션을 모두 건너뛴다. 오브젝트는 언제나 API 서버를 거쳐 바꾼다. Secret도 기본으로는 이렇게 평문에 가까운 형태로 들어가니 저장 시 암호화를 켜야 한다는 이야기는 [Secret](/posts/k8s-secret)에 있다.

etcd는 Raft로 과반이 동의한 쓰기만 확정한다. 그래서 대수는 홀수로 두고, 몇 대까지 죽어도 되는지는 과반에서 나온다. 동작 원리는 [Raft 합의](/posts/raft-consensus)에서, 백업과 복구는 [etcd 백업](/posts/k8s-etcd-backup)에서 다룬다.

## 리더는 Lease 하나로 정한다

컨트롤 플레인을 고가용성으로 만들면 스케줄러와 컨트롤러 매니저도 세 대씩 뜬다. 셋이 동시에 Pod를 만들면 안 되니, 하나만 일하고 나머지는 대기한다. 누가 일할지는 `kube-system`의 Lease 오브젝트로 정한다.

```bash
# 리더 Lease와 각 노드의 하트비트 Lease를 본다
kubectl get leases -n kube-system
kubectl get leases -n kube-node-lease
```

`HOLDER`가 지금 리더인 프로세스다. 앞에서 재시작한 뒤라 컨트롤러 매니저의 holder가 처음 클러스터를 만들었을 때의 `vm_82aa7ee6-…`에서 바뀌었다. 리더는 주기적으로 `renewTime`을 갱신하고, 갱신이 멈춘 채 기간이 지나면 다른 후보가 가져간다. 이 원리와 멈췄다 깨어난 옛 리더 문제는 [리더 선출](/posts/leader-election)에서 자세히 다뤘다. API 서버는 리더가 없다. 여러 대가 동시에 요청을 받고, 일관성은 etcd가 지킨다. 그래서 API 서버 앞에는 로드 밸런서를 두고 `/readyz`로 건강한 서버만 고른다.

`kube-node-lease`의 Lease는 노드의 하트비트다. 실제 클러스터에서는 각 노드의 kubelet이 자기 이름으로 이 Lease를 쥐고 기본 10초마다 갱신한다. 실습에서는 kwok-controller 하나가 두 노드의 하트비트를 대신 내고 있어서 holder가 같다. 실습에서 kubelet 역할을 하는 kwok-controller를 멈추고 기다렸다.

```bash
# 노드 하트비트를 멈추고 유예 시간이 지난 뒤 노드 상태를 본다
kill $(cat ~/.kwok/clusters/v20-arch/pids/kwok-controller.pid)
kubectl get nodes
kubectl get node node-000000 -o jsonpath='{range .status.conditions[?(@.type=="Ready")]}{.status} {.reason} {.message}{"\n"}{end}'
kubectl get node node-000000 -o jsonpath='{range .spec.taints[*]}{.key}:{.effect}{"\n"}{end}'
```

```text
NAME          STATUS     ROLES   AGE     VERSION
node-000000   NotReady   agent   6m38s   kwok-v0.6.1
node-000001   NotReady   agent   6m38s   kwok-v0.6.1
Unknown NodeStatusUnknown Kubelet stopped posting node status.
node.kubernetes.io/unreachable:NoSchedule
```

kwok은 컨트롤러 매니저를 `--node-monitor-grace-period=3m20s`로 띄워서 3분 넘게 걸렸다. 기본값은 40초(최근 버전에서는 50초로 늘었다)다. 유예가 지나자 노드 컨트롤러(컨트롤러 매니저 안에 있다)가 Ready를 `Unknown`으로 바꾸고 새 Pod가 오지 못하게 `NoSchedule` taint를 붙였다.

그런데 Pod는 이렇게 보인다.

```bash
# 죽은 노드 위의 Pod를 본다
kubectl get pods | head -3
kubectl get pod api-65d78bd4b7-m58vp -o jsonpath='{range .spec.tolerations[*]}{.key} {.effect} {.tolerationSeconds}{"\n"}{end}{range .status.conditions[?(@.type=="Ready")]}Ready={.status}{"\n"}{end}'
```

```text
NAME                   READY   STATUS    RESTARTS   AGE
api-65d78bd4b7-m58vp   1/1     Running   0          5m9s
api-65d78bd4b7-qjsl6   1/1     Running   0          5m9s
node.kubernetes.io/not-ready NoExecute 300
node.kubernetes.io/unreachable NoExecute 300
Ready=False
```

STATUS는 여전히 `Running`이고 `1/1`이다. 마지막으로 보고한 kubelet이 더는 말이 없으니 API 서버는 그 값을 그대로 들고 있다. 대신 노드 컨트롤러가 Pod의 Ready 조건을 False로 바꿔서 Service 엔드포인트에서는 빠진다. 대시보드의 Running만 보고 "살아 있다"고 판단하면 안 되는 이유다.

Pod마다 자동으로 붙은 toleration도 보인다. 노드에 `NoExecute` taint가 붙어도 300초(5분)는 버티다가 쫓겨난다. 즉 노드가 죽으면 그 위의 Pod가 다른 노드에서 다시 뜨기까지 유예 시간 + 5분이 걸린다. 빨리 옮겨야 하는 서비스는 이 값을 줄인다.

이번 실습에서는 `NoExecute`가 아예 붙지 않았다. 컨트롤러 매니저 로그에 이유가 있다.

```text
I1021 00:36:08.222019   14044 node_lifecycle_controller.go:1031] "Controller detected that all Nodes are not-Ready. Entering master disruption mode" logger="node-lifecycle-controller"
```

노드가 전부 NotReady가 되자 노드 컨트롤러가 쫓아내기를 멈췄다. 모든 노드가 한꺼번에 죽는 일보다 컨트롤 플레인과 노드 사이 네트워크가 끊긴 경우가 훨씬 흔하기 때문이다. 그때 Pod를 다 쫓아내면 갈 곳도 없이 서비스만 내려간다. 존 하나의 노드 대부분이 죽었을 때도 비슷하게 쫓아내는 속도를 늦춘다.

## cloud-controller-manager가 없으면 생기는 일

LoadBalancer Service를 만들면 실제 로드 밸런서를 만드는 건 cloud-controller-manager다. 실습 클러스터에는 이 부품이 없다.

```bash
# LoadBalancer 타입 Service를 만들고 외부 주소를 본다
kubectl expose deploy web --port 80 --type LoadBalancer
kubectl get svc web
```

```text
NAME   TYPE           CLUSTER-IP   EXTERNAL-IP   PORT(S)        AGE
web    LoadBalancer   10.0.0.107   <pending>     80:31114/TCP   2s
```

`EXTERNAL-IP`가 `<pending>`에서 영원히 멈춘다. Service 오브젝트도, NodePort(31114)도, kube-proxy 규칙도 다 만들어졌지만 클라우드에 로드 밸런서를 요청할 컨트롤러가 없다. 직접 만든 온프레미스 클러스터나 kind·minikube에서 흔히 보는 장면이다. MetalLB 같은 컨트롤러를 넣거나 Ingress·NodePort로 우회한다. EKS에서는 AWS Load Balancer Controller가 이 일을 하고, 컨트롤 플레인 전체가 AWS 계정에 숨어 있다는 이야기는 [EKS 기본](/posts/eks-cluster-basics)에 있다. Service 타입별 차이는 [Service 타입](/posts/k8s-service-types)에서 다룬다.

## 현장에서 어느 부품을 의심할까

증상과 먼저 볼 부품을 짝지어 두면 장애 때 빨라진다.

- `kubectl`이 `connection refused`나 `Unable to connect to the server`: API 서버나 그 앞의 로드 밸런서다. kubeconfig의 주소가 맞는지, `/readyz`가 통과하는지 본다.
- 모든 쓰기가 `etcdserver: request timed out`이나 `etcdserver: no leader`: etcd 과반을 잃었다. etcd 멤버 상태와 디스크 지연(fsync)을 본다. 이때도 떠 있는 Pod는 계속 돈다.
- Deployment는 있는데 ReplicaSet이나 Pod가 안 생긴다: 컨트롤러 매니저다. 리더 Lease의 `renewTime`이 멈췄는지, 컨트롤러 매니저 로그에 권한 에러가 있는지 본다.
- Pod가 Pending이고 이벤트가 없다: 스케줄러가 죽었거나 `schedulerName`이 틀렸다. 이벤트에 `FailedScheduling`이 있으면 자원·규칙 문제다.
- `Scheduled` 뒤로 진행이 없다: 그 노드의 kubelet과 런타임이다. `journalctl -u kubelet`, `crictl ps`를 노드에서 본다. CNI가 IP를 못 주면 `FailedCreatePodSandBox`가 나온다([CNI](/posts/k8s-cni-pod-network)).
- 노드가 NotReady인데 Pod는 Running으로 보인다: kubelet 하트비트가 끊겼다. 노드의 kubelet, 노드와 API 서버 사이 네트워크, 인증서 만료를 본다.
- Service로 접속이 안 되는데 Pod는 Ready다: kube-proxy 규칙이나 EndpointSlice다. kube-proxy가 만드는 iptables 규칙은 [iptables NAT](/posts/iptables-nat)에서 따라가 봤다.

관리형 쿠버네티스(EKS, GKE, AKS)에서는 컨트롤 플레인이 보이지 않아서 앞의 셋은 클라우드 쪽 상태 페이지와 제어부 로그로 본다. 그래도 어느 부품의 문제인지 가르는 순서는 같다. kubeadm으로 직접 세운 클러스터라면 컨트롤 플레인 부품이 `/etc/kubernetes/manifests`의 정적 Pod로 떠 있고 kubelet이 그 파일을 보고 띄운다. kwok은 이 부품들을 그냥 프로세스로 띄워서 `kubectl get pods -A`에 아무것도 나오지 않았다.

## 부품은 각자 자기 오브젝트만 본다

쿠버네티스는 큰 프로그램 하나가 아니라 API 서버를 가운데 두고 각자 자기 오브젝트만 지켜보는 작은 프로그램들의 모임이다. apply는 원하는 상태를 etcd에 적는 것으로 끝나고, 컨트롤러가 ReplicaSet과 Pod를, 스케줄러가 노드를, kubelet이 컨테이너를 차례로 채운다. 그래서 부품 하나가 멈추면 그 부품이 맡은 칸에서만 흐름이 서고, 다시 뜨면 현재 상태를 읽고 이어서 한다. 이벤트가 어디서 끊겼는지 보면 어느 부품을 봐야 할지 나온다. 다음은 그 부품들이 쓰는 반복 구조인 [컨트롤러와 reconcile](/posts/k8s-controllers-reconcile)이다.

## 면접에서 나올 만한 질문

### 쿠버네티스 컨트롤 플레인과 노드의 구성 요소를 설명해 주세요.

컨트롤 플레인에는 유일한 입구인 kube-apiserver, 모든 상태를 저장하는 etcd, 노드를 정하는 kube-scheduler, 여러 컨트롤러를 돌리는 kube-controller-manager, 클라우드 자원을 다루는 cloud-controller-manager가 있다. 노드에는 Pod를 띄우고 상태를 보고하는 kubelet, Service 트래픽 규칙을 만드는 kube-proxy, 실제 컨테이너를 돌리는 containerd 같은 런타임이 있다. 모든 부품은 API 서버하고만 이야기하고, etcd에는 API 서버만 닿는다.

### kubectl apply로 Deployment를 만들면 어떤 순서로 일이 일어나나요?

kubectl이 API 서버에 POST하면 API 서버가 인증, 권한, 어드미션, 검증을 거쳐 etcd에 저장하고 201을 돌려준다. 여기서 kubectl은 끝난다. 그 뒤 Deployment 컨트롤러가 watch로 받아 ReplicaSet을 만들고, ReplicaSet 컨트롤러가 Pod를 만들고, 스케줄러가 노드를 정해 binding을 쓰고, 그 노드의 kubelet이 컨테이너를 띄우고 상태를 보고한다. 이벤트의 reason이 이 순서대로 남는다.

### 컨트롤러끼리 직접 통신하지 않는데 어떻게 협력하나요?

모두 API 서버의 오브젝트를 watch하고 고치는 방식으로 협력한다. 한 컨트롤러가 오브젝트를 바꾸면 그 변화를 보는 다른 컨트롤러가 깨어난다. 동시에 같은 오브젝트를 고치는 충돌은 resourceVersion을 조건으로 보내는 낙관적 동시성으로 막고, 지면 409를 받아 다시 읽는다. 실제로는 informer가 목록과 watch를 로컬 캐시로 유지해 API 서버 부담을 줄인다.

### 스케줄러가 죽으면 어떻게 되나요? 컨트롤러 매니저가 죽으면요?

스케줄러가 죽으면 새 Pod는 만들어지지만 노드가 정해지지 않아 Pending으로 남고 이벤트도 없다. 컨트롤러 매니저가 죽으면 Deployment를 apply해도 저장만 되고 ReplicaSet과 Pod가 생기지 않는다. 둘 다 이미 떠 있는 Pod에는 영향이 없다. 다시 뜨면 리더 Lease를 얻은 뒤 현재 상태를 읽고 밀린 일을 처리하는데, 갑자기 죽었다면 옛 Lease가 만료될 때까지(기본 15초) 기다린다.

### etcd를 3대에서 4대로 늘리면 가용성이 좋아지나요?

아니다. 과반은 3대일 때 2, 4대일 때 3이라 둘 다 한 대까지만 잃어도 된다. 짝수로 늘리면 과반만 커져 쓰기 지연이 는다. 그래서 3대나 5대처럼 홀수로 둔다. 과반을 잃으면 쓰기가 멈춰 모든 변경이 막히지만, 이미 떠 있는 Pod는 kubelet이 계속 돌린다.

### 노드가 죽으면 그 위의 Pod는 언제 다른 노드로 옮겨지나요?

kubelet의 하트비트 Lease가 끊긴 뒤 노드 감시 유예 시간(기본 40초, 최근 버전 50초)이 지나면 노드가 NotReady가 되고 taint가 붙는다. Pod에는 기본으로 300초짜리 NoExecute toleration이 붙어 있어서 그 뒤 5분이 더 지나야 쫓겨나고 ReplicaSet이 다른 노드에 새로 만든다. 그 사이 Pod STATUS는 Running으로 보이지만 Ready는 False라 엔드포인트에서는 빠진다. 모든 노드가 한꺼번에 NotReady가 되면 네트워크 분리로 보고 쫓아내기를 멈춘다.

### LoadBalancer Service의 EXTERNAL-IP가 계속 pending입니다. 왜인가요?

실제 로드 밸런서를 만드는 cloud-controller-manager나 그 역할의 컨트롤러가 없기 때문이다. Service 오브젝트와 NodePort, kube-proxy 규칙은 다 만들어졌지만 클라우드에 요청할 주체가 없다. 온프레미스나 로컬 클러스터에서는 MetalLB 같은 컨트롤러를 넣고, 클라우드라면 해당 컨트롤러가 떠 있는지와 그 권한을 확인한다.

### API 서버는 여러 대일 때 리더가 있나요?

없다. API 서버는 상태를 들고 있지 않아 여러 대가 동시에 요청을 받고, 일관성은 etcd가 지킨다. 그래서 앞에 로드 밸런서를 두고 /readyz로 건강한 서버만 고른다. 반면 스케줄러와 컨트롤러 매니저는 동시에 일하면 중복 작업이 생기니 Lease로 리더 하나를 뽑고 나머지는 대기한다.
