```js
button.addEventListener("click", () => {
  spinner.hidden = false; // 스피너를 먼저 보여 주고
  rows.sort(compareByName); // 무거운 정렬을 한다
  render(rows);
  spinner.hidden = true;
});
```

그런데 스피너는 한 번도 보이지 않는다. 버튼을 누르면 화면이 0.3초 동안 얼어 있다가 정렬된 목록이 한 번에 나타난다. 그 사이에 누른 다른 버튼은 반응도 없다. `spinner.hidden = false`는 분명히 먼저 실행됐는데 왜 화면에 안 나왔을까. 이 질문의 답이 이벤트 루프다.

## 콜 스택은 하나뿐이다

자바스크립트 코드는 한 스레드에서 돈다. 브라우저 탭이라면 그 탭의 메인 스레드 하나다. 함수를 부르면 콜 스택(지금 실행 중인 함수들이 쌓이는 곳)에 올라가고, 끝나면 내려온다. 스택이 비기 전에는 다른 자바스크립트 코드가 끼어들 수 없다. 이걸 run-to-completion, 끝날 때까지 실행한다고 한다.

문제는 메인 스레드가 자바스크립트만 하는 게 아니라는 데 있다. 스타일 계산, 레이아웃, 페인트처럼 화면을 그리는 일도 같은 스레드에서 한다. 그러니 클릭 핸들러가 300ms 동안 스택을 차지하고 있으면 그동안 화면도 그려지지 않는다. `spinner.hidden = false`는 DOM 값을 바꿨을 뿐이고, 그 값을 화면에 그릴 기회는 핸들러가 끝난 뒤에야 온다. 그때는 이미 `spinner.hidden = true`로 돌아간 다음이다.

한 스레드로 어떻게 타이머, 네트워크, 클릭을 다 처리하는지가 다음 궁금증이다.

## 기다리는 일은 브라우저가 대신 한다

`setTimeout`이나 `fetch`는 자바스크립트 엔진(V8 같은)의 기능이 아니다. 브라우저가 제공하는 API다. 엔진은 "1초 뒤에 이 함수를 불러 줘"라는 부탁만 넘기고 바로 다음 줄로 간다. 기다리는 일은 브라우저의 다른 스레드가 맡는다.

기다림이 끝나면 브라우저는 콜백을 바로 실행하지 않는다. 대기열에 넣어 둔다. 그리고 이벤트 루프가 콜 스택이 빌 때마다 대기열에서 콜백을 꺼내 스택에 올린다. 아래 그림은 그 관계를 보여 준다. 점이 흐르는 방향이 콜백이 이동하는 방향이다.

대기열은 두 종류다. 태스크 큐(매크로태스크 큐라고도 부른다)에는 `setTimeout` 콜백, 클릭 같은 사용자 이벤트, 네트워크 응답 이벤트, `postMessage`가 들어간다. 정확히는 태스크 소스마다 큐가 따로 있고 브라우저가 어느 큐를 먼저 볼지 고를 수 있다. 크롬은 사용자 입력을 타이머보다 먼저 꺼내 주는 식으로 우선순위를 둔다. 그래서 "태스크끼리의 순서"는 같은 종류 안에서만 믿을 수 있다.

마이크로태스크 큐에는 Promise의 `then`/`catch`/`finally` 콜백, `await` 다음 줄, `queueMicrotask`로 넣은 함수, `MutationObserver` 콜백이 들어간다. 이벤트 루프의 규칙은 짧다.

1. 태스크 큐에서 가장 오래된 태스크 하나를 꺼내 끝까지 실행한다.
2. 마이크로태스크 큐가 빌 때까지 전부 실행한다. 실행 중에 새로 들어온 마이크로태스크도 이번에 같이 비운다.
3. 화면을 그릴 때가 됐으면 렌더링한다.
4. 1로 돌아간다.

처음 실행되는 `<script>` 전체도 하나의 태스크다. 이 네 줄만 손에 쥐고 있으면 출력 순서 문제는 거의 다 풀린다.

## 출력 순서 퍼즐 풀기

면접 단골 문제부터 보자.

```js
console.log("A");
setTimeout(() => console.log("B"), 0);
Promise.resolve().then(() => console.log("C"));
queueMicrotask(() => console.log("D"));
console.log("E");
```

답은 `A E C D B`다. 스크립트라는 태스크가 끝날 때까지 `A`와 `E`가 찍힌다. 스택이 비면 마이크로태스크 `C`, `D`를 들어온 순서대로 비운다. 그다음에야 태스크 큐의 `B` 차례가 온다. 지연이 0이어도 `setTimeout`은 다음 태스크로 미뤄진다.

콜백 안에서 또 콜백을 등록하면 조금 더 헷갈린다.

```js
console.log("1");
setTimeout(() => {
  console.log("2");
  Promise.resolve().then(() => console.log("3"));
}, 0);
Promise.resolve().then(() => {
  console.log("4");
  setTimeout(() => console.log("5"), 0);
});
setTimeout(() => console.log("6"), 0);
console.log("7");
```

이 규칙의 꼬리 질문이 하나 있다. 마이크로태스크는 엄밀히 말하면 "태스크가 끝날 때"가 아니라 "콜 스택이 빌 때마다" 비워진다. 그래서 사용자가 버튼을 클릭해서 리스너 두 개가 차례로 불릴 때는 첫 리스너가 끝나고 두 번째 리스너가 시작되기 전에 첫 리스너의 `then`이 실행된다. 같은 버튼을 코드에서 `button.click()`으로 누르면 스택에 `click()`을 부른 코드가 남아 있으니 두 리스너가 다 끝난 뒤에야 마이크로태스크가 돈다. 같은 클릭인데 순서가 달라진다.

## 마이크로태스크는 끝까지 비운다

2단계의 "새로 들어온 것도 이번에 같이 비운다"는 규칙에는 함정이 있다. 마이크로태스크가 자기 자신을 계속 넣으면 큐가 영원히 비지 않는다.

```js
function spin() {
  Promise.resolve().then(spin);
}
spin(); // 탭이 멈춘다
```

스택은 매번 비워지지만 이벤트 루프가 2단계를 벗어나지 못한다. 다음 태스크도, 렌더링도 오지 않는다. 클릭도 안 먹고 화면도 그대로다. 이걸 기아(starvation)라고 한다. 같은 함수를 `setTimeout(spin, 0)`으로 바꾸면 CPU는 계속 쓰더라도 태스크 사이사이에 렌더링과 입력 처리가 들어갈 틈이 생긴다.

실무에서 이렇게 노골적인 무한 루프를 짜는 일은 드물다. 대신 `await`를 수천 번 도는 반복문이 있다. 예를 들어 이미 캐시에 있어서 즉시 이행되는 Promise를 1만 개 `await`하면, 비동기처럼 보여도 전부 한 번의 마이크로태스크 비우기 안에서 끝난다. 화면은 그동안 멈춰 있다. `await`를 넣었다고 메인 스레드를 양보한 게 아니다.

## await 뒤는 then 안으로 들어간다

`async`/`await`는 Promise를 편하게 쓰는 문법이다. `await` 앞까지는 동기적으로 실행되고, `await` 뒷부분은 `then` 콜백으로 잘려 나간다고 보면 된다.

```js
async function load() {
  console.log("f1");
  await null;
  console.log("f2");
}

// 대략 이렇게 바뀐다
function load() {
  console.log("f1");
  return Promise.resolve(null).then(() => {
    console.log("f2");
  });
}
```

그래서 아래 코드는 `start f1 end f2 p` 순서로 찍힌다. `load()`를 부르면 `f1`까지는 그 자리에서 실행된다. `await`를 만나 함수가 멈추고 뒷부분이 마이크로태스크로 예약된다. `p`의 `then`은 그보다 늦게 예약됐으니 뒤에 선다.

```js
console.log("start");
load();
Promise.resolve().then(() => console.log("p"));
console.log("end");
```

세세한 차이가 하나 더 있다. `async` 함수에서 `return 1` 대신 `return Promise.resolve(1)`을 하면, 바깥 Promise가 이행되기까지 마이크로태스크 두 번이 더 든다. Node.js 22에서 `h().then(...)`(return 1)과 `g().then(...)`(return Promise.resolve(1)), 그리고 `then` 세 개를 이은 체인을 같이 돌려 보면 `h t1 t2 g t3` 순서가 나온다. 순서가 중요한 코드라면 이런 틱 수에 기대지 말고 명시적으로 기다리게 짜는 게 맞다. 예전 V8(7.2 이전)에서는 `await` 자체도 지금보다 틱을 더 썼다. 엔진 구현이 바뀌면 달라질 수 있는 부분이라는 뜻이다.

## 화면은 태스크 사이에서만 그려진다

## 50ms가 넘으면 긴 작업이다

브라우저 성능 도구는 50ms를 넘는 태스크를 긴 작업(long task)으로 표시한다. 크롬 개발자 도구 Performance 패널에서 회색 막대 오른쪽 위에 빨간 삼각형이 붙는 게 이것이다. 사람이 반응이 즉각적이라고 느끼는 한계를 100ms쯤으로 보고, 입력이 들어오기 직전에 이미 다른 태스크가 돌고 있을 수 있으니 태스크 하나는 그 절반으로 끊자는 기준이다.

긴 작업이 사용자에게 어떤 비용인지 재는 지표가 INP(Interaction to Next Paint)다. 클릭, 탭, 키 입력이 들어온 순간부터 그 결과가 화면에 그려질 때까지의 시간이다. 2024년 3월부터 FID 대신 Core Web Vitals에 들어갔고, 페이지에서 일어난 상호작용 중 가장 느린 축(대체로 가장 느린 것, 상호작용이 아주 많으면 상위 몇 개를 빼고)을 대표값으로 쓴다. 200ms 이하면 좋음, 500ms를 넘으면 나쁨이다.

INP는 세 부분으로 쪼개 볼 수 있다. 입력이 큐에서 기다린 시간(input delay), 핸들러가 돈 시간(processing), 핸들러가 끝나고 실제로 그려지기까지의 시간(presentation delay)이다. 긴 작업은 첫 번째를 늘린다. 아래 그림은 300ms짜리 작업이 도는 중에 40ms 시점에 클릭이 들어온 경우다. 클릭 처리는 20ms, 그리기는 10ms 걸린다고 잡았다.

## 긴 작업을 쪼개는 방법들

가장 오래된 방법은 `setTimeout(fn, 0)`으로 나머지 일을 다음 태스크로 넘기는 것이다.

```js
async function processAll(items) {
  let deadline = performance.now() + 10;
  for (const item of items) {
    process(item);
    if (performance.now() >= deadline) {
      await new Promise((r) => setTimeout(r, 0)); // 메인 스레드를 내준다
      deadline = performance.now() + 10;
    }
  }
}
```

`await Promise.resolve()`로는 안 된다. 앞에서 봤듯이 마이크로태스크는 렌더링과 입력보다 먼저 전부 비워지니 양보가 되지 않는다. 양보하려면 반드시 태스크를 거쳐야 한다.

`setTimeout`에는 단점이 있다. HTML 표준은 타이머가 5단계 넘게 중첩되면 최소 4ms로 늘리게 되어 있어서, 잘게 자주 양보하면 그 4ms가 쌓인다. 백그라운드 탭에서는 크롬 기준 1초 이상으로 늘어난다. 또 양보한 사이에 다른 스크립트의 태스크가 큐에 많이 쌓여 있으면, 내 작업의 나머지는 그 뒤에 줄을 서야 한다.

`scheduler.yield()`는 이 문제를 풀려고 나온 API다. `await scheduler.yield()`를 하면 메인 스레드를 한 번 내주되, 이어서 실행할 부분은 일반 태스크보다 앞자리로 예약된다. 입력과 렌더링은 끼어들 수 있고, 내 작업은 다른 잡다한 태스크 뒤로 밀리지 않는다. 크롬 계열은 129부터 지원한다. 지원하지 않는 브라우저도 있으니 `"scheduler" in globalThis && "yield" in scheduler`로 확인하고 없으면 `setTimeout`으로 돌아가게 짠다. React의 스케줄러는 비슷한 목적으로 `MessageChannel`을 써서 5ms 단위로 일을 끊는다. `MessageChannel` 메시지는 4ms 지연 없이 바로 다음 태스크가 되기 때문이다.

계산 자체가 무겁고 DOM이 필요 없다면 Web Worker로 옮기는 게 가장 확실하다. 워커는 별도 스레드에서 자기 이벤트 루프로 돈다. 그 대신 DOM에 손댈 수 없고, 메인 스레드와는 `postMessage`로만 대화한다. 메시지는 구조화된 복제(structured clone)로 복사되기 때문에 수십 MB짜리 객체를 오가면 복사 비용이 메인 스레드에서 다시 생긴다. `ArrayBuffer`는 transfer 목록에 넣으면 복사 없이 소유권만 넘길 수 있다.

어느 쪽을 고를지는 일의 성격으로 정한다. DOM을 만지는 렌더링 작업은 워커로 못 보내니 쪼개서 양보한다. 정렬, 파싱, 압축, 이미지 처리처럼 데이터만 다루는 일은 워커로 보낸다. 급하지 않은 일(분석 로그 전송 같은)은 `requestIdleCallback`으로 브라우저가 한가할 때 돌린다. 사파리처럼 이 API를 지원하지 않거나 늦게 들인 브라우저가 있으니 이것도 폴백을 둔다.

## Node.js는 단계를 돈다

Node.js도 콜 스택 하나와 이벤트 루프로 돈다는 큰 그림은 같다. 다만 이벤트 루프를 libuv라는 C 라이브러리가 구현하고, 태스크 큐가 하나가 아니라 단계(phase)별로 나뉘어 있다. 한 바퀴는 이 순서로 돈다.

- timers: 시간이 다 된 `setTimeout`, `setInterval` 콜백
- pending callbacks: 지난 바퀴에서 미뤄 둔 일부 시스템 오류 콜백
- idle, prepare: 내부용
- poll: 새 I/O 이벤트를 가져와 콜백을 실행한다. 할 일이 없으면 여기서 다음 타이머 시각까지 기다린다
- check: `setImmediate` 콜백
- close callbacks: `socket.on("close")` 같은 닫힘 콜백

`setTimeout(fn, 0)`과 `setImmediate(fn)`의 순서가 여기서 갈린다. 메인 모듈에서 둘을 같이 부르면 순서가 정해져 있지 않다. Node.js는 지연 0을 1ms로 바꾸는데, 루프가 처음 timers 단계에 들어갔을 때 1ms가 지났는지는 프로세스 상태에 따라 다르기 때문이다. 반면 I/O 콜백 안에서 부르면 항상 `setImmediate`가 먼저다. 아래 그림에서 다음을 누르면 그 이유가 보인다.

```js
fs.readFile("config.json", () => {
  setTimeout(() => console.log("timeout"), 0);
  setImmediate(() => console.log("immediate"));
});
// 항상 immediate → timeout
```

마이크로태스크는 단계와 별도로 돈다. Node.js 11부터는 브라우저와 맞춰서 `setTimeout`이나 `setImmediate` 콜백 하나가 끝날 때마다 마이크로태스크를 비운다. 그 전 버전에서는 한 단계의 콜백을 다 돌고 나서야 비웠기 때문에, 예전 글에 나오는 출력 순서와 지금 결과가 다를 수 있다.

## nextTick은 Promise보다 먼저다

Node.js에는 마이크로태스크와 비슷한 큐가 하나 더 있다. `process.nextTick` 큐다. 콜백 하나가 끝날 때마다 Node.js는 nextTick 큐를 먼저 다 비우고, 그다음 Promise 마이크로태스크 큐를 비운다. 둘이 서로를 계속 채우면 둘 다 빌 때까지 이 과정을 반복한다.

```js
setTimeout(() => console.log("timeout"), 0);
setImmediate(() => console.log("immediate"));
process.nextTick(() => console.log("nextTick"));
Promise.resolve().then(() => console.log("promise"));
console.log("sync");
```

CommonJS 파일로 돌리면 `sync nextTick promise`까지는 항상 이 순서다. 그 뒤 `timeout`과 `immediate`는 앞에서 말한 이유로 순서가 보장되지 않는다(내 환경에서는 `timeout`이 먼저 나왔다). 그런데 같은 코드를 ES 모듈(`.mjs`, 또는 `"type": "module"`)로 돌리면 `sync promise nextTick`이 된다. ES 모듈의 최상위 코드는 그 자체가 Promise 처리 안에서 평가되기 때문에, 스크립트가 끝난 시점이 이미 마이크로태스크를 비우는 도중이다. 그래서 Promise 쪽이 먼저 돈다. "nextTick이 항상 먼저"라고 외우면 여기서 틀린다.

nextTick 큐도 마이크로태스크처럼 끝까지 비우기 때문에, 재귀적으로 `process.nextTick`을 부르면 poll 단계에 영영 가지 못해 I/O가 굶는다. Node.js 문서도 대부분의 경우 `queueMicrotask`나 `setImmediate`를 권한다. nextTick은 "이 함수가 반환된 직후, 다른 I/O보다 먼저" 해야 하는 일, 예를 들어 생성자에서 등록할 리스너가 붙은 뒤에 이벤트를 내보내야 하는 경우에 쓴다.

서버에서 이벤트 루프가 막히면 결과가 브라우저보다 크다. 요청 하나를 처리하면서 200ms짜리 동기 작업(큰 JSON 파싱, 동기 암호화, 복잡한 정규식)을 하면 그동안 다른 모든 요청이 멈춘다. `perf_hooks.monitorEventLoopDelay()`로 이벤트 루프 지연을 재서 지표로 두고, CPU를 오래 쓰는 일은 `worker_threads`로 보낸다.

## 누가 메인 스레드를 붙잡았는지 운영에서 찾기

내 노트북의 Performance 패널에서는 멀쩡한데, RUM 지표에서 INP가 나쁘다는 경보가 온다. 사용자 기기에서 무슨 일이 있었는지 알려면 브라우저가 긴 작업을 기록해 둔 것을 직접 모아야 한다. 오래된 방법은 `longtask` 항목이고, 크롬 123부터는 `long-animation-frame`(LoAF) 항목이 있다.

처음 장면의 정렬 버튼을 그대로 만들어 크롬 141에서 눌러 보고, 두 관찰자가 받은 내용을 찍었다. 핸들러는 `app.js`의 `sortRows` 함수이고 300ms 동안 돈다.

```js
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) report("longtask", e.toJSON());
}).observe({ type: "longtask", buffered: true });

new PerformanceObserver((list) => {
  for (const e of list.getEntries()) report("loaf", e.toJSON());
}).observe({ type: "long-animation-frame", buffered: true });
```

```text
longtask: { name: "self", duration: 304,
            attribution: [{ name: "unknown", containerType: "window" }] }

loaf:     { duration: 306, blockingDuration: 255,
            scripts: [{ invoker: "BUTTON#sort.onclick",
                        invokerType: "event-listener",
                        sourceURL: "http://localhost:8011/app.js",
                        sourceFunctionName: "sortRows",
                        duration: 300 }] }
```

`longtask`는 "이 창에서 304ms짜리 작업이 있었다"까지만 알려 준다. 어떤 코드인지는 `unknown`이다. LoAF는 그 프레임 안에서 돈 스크립트마다 무엇이 불렀는지(`BUTTON#sort.onclick`), 어느 파일의 어느 함수인지(`app.js`의 `sortRows`), 얼마나 걸렸는지를 준다. `blockingDuration` 255ms는 306ms 중 50ms를 넘긴 몫으로, 입력을 막은 시간에 가깝다. 운영에서 모을 때는 `sourceURL`을 출처별로 묶어 보는 게 가장 먼저 쓸모 있다. 내 번들이 아니라 태그 매니저나 광고 스크립트가 상위에 올라오는 경우가 꽤 있고, 그러면 고칠 곳이 코드가 아니라 스크립트 로딩 정책이 된다. LoAF는 크롬 계열에만 있으니 다른 브라우저 사용자의 INP 원인은 이 방법으로 볼 수 없다는 점도 알고 쓴다. INP를 세 구간으로 나눠 모으는 방법은 [Core Web Vitals](/posts/core-web-vitals)에 정리했다.

서버 쪽 증상은 모양이 다르다. 특정 API 하나가 느린 게 아니라 모든 엔드포인트의 p99가 같이 튄다. 헬스 체크까지 늦어져 로드밸런서나 쿠버네티스가 멀쩡한 프로세스를 죽였다 살리기도 한다. Node.js 22에서 40만 건짜리 JSON을 동기로 파싱하는 `/report`와 아무 일도 안 하는 `/health`를 같은 프로세스에 두고 재 봤다.

```js
const { monitorEventLoopDelay } = require("node:perf_hooks");
const h = monitorEventLoopDelay({ resolution: 10 });
h.enable();
setInterval(() => {
  const ms = (n) => (n / 1e6).toFixed(1);
  console.log(`eventloop p50=${ms(h.percentile(50))}ms p99=${ms(h.percentile(99))}ms max=${ms(h.max)}ms`);
  h.reset();
}, 5000).unref();
```

```bash
# 평소의 헬스 체크
curl -s -o /dev/null -w 'health(alone)  %{time_total}s\n' localhost:8012/health
# /report를 보내 놓고 50ms 뒤에 헬스 체크
curl -s localhost:8012/report & sleep 0.05; curl -s -o /dev/null -w 'health(during) %{time_total}s\n' localhost:8012/health
```

```text
health(alone)  0.005239s
parsed 400000 rows in 222ms
health(during) 0.173533s
eventloop p50=10.2ms p99=10.3ms max=13.8ms
eventloop p50=10.1ms p99=10.3ms max=230.7ms
```

`/health`는 한 줄짜리인데 5ms에서 174ms로 늘었다. 파싱이 끝날 때까지 이벤트 루프가 다음 콜백을 꺼내지 못했기 때문이다. 지연 히스토그램은 `resolution`(10ms) 간격으로 타이머를 걸어 늦어진 정도를 재므로 평소 값이 10ms 근처로 나온다. 그 바닥보다 얼마나 튀었는지를 본다. 두 번째 줄의 max 230.7ms가 파싱 시간과 거의 같다. p99는 그대로인데 max만 튄 것도 눈여겨볼 만하다. 5초 동안 한 번 막혔을 뿐이라 백분위수에는 묻힌다. 그래서 이 지표는 p99와 max를 같이 그래프로 둔다.

원인을 찾았으면 동기 작업을 `worker_threads`로 보내거나, 스트리밍 파서로 바꿔 조금씩 처리하거나, 애초에 그렇게 큰 응답을 한 번에 만들지 않도록 API를 페이지 단위로 나눈다. 흔한 실수는 `async` 함수로 감싸면 나아질 거라고 기대하는 것이다. `JSON.parse`는 `await`를 붙여도 그 자리에서 끝까지 돈다. 앞에서 본 것처럼 마이크로태스크는 양보가 아니다. 그리고 헬스 체크가 이벤트 루프 지연 때문에 실패하는 걸 보고 타임아웃만 늘리면 증상만 가려진다. 헬스 체크가 늦다는 건 그 순간 다른 사용자 요청도 똑같이 늦었다는 뜻이다.

## 다시 멈춘 스피너로

스피너가 안 보였던 건 렌더링이 태스크 사이에서만 일어나기 때문이다. 클릭 핸들러라는 태스크가 300ms 동안 메인 스레드를 쥐고 있었고, 그동안 DOM이 바뀌어도 그릴 틈이 없었다. 이벤트 루프는 태스크 하나를 끝까지 실행하고, 마이크로태스크를 전부 비우고, 필요하면 그린다. 이 순서만 머릿속에 있으면 출력 순서 문제도, INP가 나쁜 이유도, 왜 `await`가 양보가 아닌지도 같은 그림으로 설명된다. 이어지는 글로 [실행 컨텍스트와 콜 스택](/posts/js-execution-context), [마이크로태스크 순서 퍼즐](/posts/js-microtask-macrotask), [타이머 정확도](/posts/js-timers-accuracy)가 있다.

## 면접에서 나올 만한 질문

### 자바스크립트가 싱글 스레드인데 어떻게 비동기 작업을 동시에 처리하나요?

자바스크립트를 실행하는 콜 스택이 하나일 뿐, 기다리는 일은 런타임이 대신 한다. 타이머, 네트워크, 파일 I/O는 브라우저나 libuv가 다른 스레드나 OS 기능으로 처리하고, 끝나면 콜백을 큐에 넣는다. 이벤트 루프가 콜 스택이 빌 때마다 큐에서 콜백을 꺼내 실행한다. 그래서 기다림은 동시에 일어나지만 자바스크립트 코드 실행은 한 번에 하나다.

### 태스크와 마이크로태스크의 차이는 무엇인가요?

태스크는 한 바퀴에 하나씩 꺼내 실행하고, 마이크로태스크는 콜 스택이 빌 때마다 큐가 빌 때까지 전부 실행한다. `setTimeout`, 이벤트, `postMessage`가 태스크이고 Promise 콜백, `await` 뒷부분, `queueMicrotask`, `MutationObserver`가 마이크로태스크다. 그래서 같은 시점에 예약하면 Promise 콜백이 `setTimeout(0)`보다 먼저 실행된다.

### setTimeout(fn, 0)은 왜 바로 실행되지 않나요?

지연 0은 "최소 0ms 뒤에 태스크 큐에 넣어라"라는 뜻이지 즉시 실행이 아니다. 지금 실행 중인 코드와 마이크로태스크가 다 끝나고, 앞에 선 태스크들도 끝나야 차례가 온다. 게다가 브라우저는 5단계 넘게 중첩된 타이머를 최소 4ms로 늘리고, 백그라운드 탭에서는 더 크게 늘린다. Node.js는 0을 1ms로 바꾼다.

### await를 쓰면 메인 스레드를 양보하는 건가요?

아니다. `await` 뒷부분은 마이크로태스크로 예약되는데, 마이크로태스크는 렌더링이나 입력 처리보다 먼저 전부 실행된다. 이미 이행된 Promise를 반복해서 `await`하면 한 번의 비우기 안에서 모두 돌고 화면은 그동안 멈춘다. 실제로 양보하려면 `setTimeout`, `MessageChannel`, `scheduler.yield()`처럼 태스크를 거쳐야 한다.

### 무거운 계산 때문에 INP가 나쁘게 나옵니다. 어떻게 개선하나요?

먼저 Performance 패널에서 상호작용 시점에 어떤 긴 작업이 있는지 보고, 입력 지연·처리 시간·표시 지연 중 어디가 큰지 나눈다. DOM과 상관없는 계산이면 Web Worker로 옮기고, DOM 작업이면 수 ms에서 50ms 예산으로 쪼개 `scheduler.yield()`나 `setTimeout`으로 양보한다. 핸들러에서는 화면에 보일 최소한의 변경만 먼저 하고 나머지는 다음 프레임 이후로 미룬다. 쪼개면 전체 완료 시간은 조금 늘어나는 트레이드오프가 있다.

### requestAnimationFrame은 이벤트 루프의 어디에서 실행되나요?

태스크와 마이크로태스크가 끝나고 브라우저가 이번에 그리기로 한 때, 스타일과 레이아웃 계산 바로 전에 실행된다. 화면 주사율에 맞춰 보통 초당 60번 불리고, 백그라운드 탭에서는 거의 멈춘다. 그래서 애니메이션 값을 바꾸는 일은 `setTimeout`보다 rAF가 맞다. 다만 rAF 안에서 레이아웃 읽기와 쓰기를 섞으면 강제 동기 레이아웃이 생긴다.

### Node.js에서 setTimeout(0)과 setImmediate 중 무엇이 먼저 실행되나요?

메인 모듈에서 부르면 보장되지 않는다. 1ms로 바뀐 타이머가 첫 timers 단계 진입 시점에 만료됐는지가 그때그때 다르기 때문이다. I/O 콜백 안에서 부르면 poll 다음이 check라서 항상 `setImmediate`가 먼저다. "다음 바퀴에 꼭 먼저" 실행하고 싶으면 `setImmediate`를 쓴다.

### process.nextTick과 Promise 마이크로태스크는 어떤 순서로 실행되나요?

CommonJS에서는 콜백이 끝날 때마다 nextTick 큐를 먼저 비우고 Promise 큐를 비운다. 하지만 ES 모듈의 최상위 코드는 Promise 처리 안에서 평가되기 때문에 그 시점에는 Promise 콜백이 먼저 나온다. 두 큐 모두 끝까지 비우는 방식이라 재귀 호출하면 I/O를 굶길 수 있어서, 특별한 이유가 없으면 `queueMicrotask`나 `setImmediate`를 쓴다.
