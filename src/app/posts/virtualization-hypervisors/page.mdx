API 서버 여섯 대가 모두 같은 인스턴스 타입이고, 같은 이미지에 같은 설정으로 떠 있다. 그런데 p99 지연 그래프를 서버별로 나눠 보면 한 대만 하루에 몇 번씩 튄다. 그 서버의 앱 로그에는 GC도, 느린 쿼리도 없다. `top`을 켜 두고 기다리다 보니 튀는 순간 오른쪽 끝의 `st` 값이 8, 12로 오른다. 내 프로세스가 CPU를 쓰고 싶었는데 누군가 그 시간을 가져갔다는 뜻이다.

그 누군가는 같은 물리 서버에 올라간 다른 VM이다. 흔히 노이지 네이버(noisy neighbor)라고 부른다. 이 현상을 이해하려면 VM 한 대가 물리 서버 위에서 어떻게 도는지부터 알아야 한다. 이 글은 하이퍼바이저가 CPU·메모리·디스크·네트워크를 어떻게 나눠 주는지, AWS가 왜 그 일을 Nitro라는 전용 하드웨어로 내렸는지, 베어메탈 인스턴스와 라이브 마이그레이션은 언제 등장하는지, 컨테이너와는 격리가 어떻게 다른지를 본다.

실험은 이 블로그를 쓰는 샌드박스(Ubuntu 24.04, KVM 게스트)에서 직접 돌린 결과다. 클라우드 콘솔이 필요한 부분은 공식 문서 기준으로 설명만 한다. 이 주제의 다른 글: 컨테이너가 커널 기능으로 어떻게 만들어지는지는 [리눅스 네임스페이스와 cgroup](/posts/linux-namespaces-cgroups)에서, 같은 클라우드 서버에 붙이는 디스크 종류는 [블록, 파일, 객체 스토리지](/posts/block-file-object-storage)에서 다룬다.

## 한 대의 서버를 여러 대처럼 보이게 하는 층

운영체제 커널은 자기가 하드웨어를 독차지한다고 믿고 만들어졌다. 페이지 테이블을 마음대로 바꾸고, 인터럽트를 끄고, 디스크 컨트롤러 레지스터에 직접 값을 쓴다. 한 물리 서버에 커널을 여러 개 올리려면 각 커널에게 "너만의 하드웨어"가 있는 것처럼 보이게 해 주는 층이 필요하다. 그 층이 하이퍼바이저(가상 머신 모니터, VMM)다.

하이퍼바이저가 하는 일은 세 가지로 묶인다. 물리 CPU 시간을 쪼개 VM의 가상 CPU(vCPU)에 나눠 주고, 물리 메모리를 VM마다 따로 떼어 주고, 디스크·네트워크 같은 장치를 VM마다 하나씩 가진 것처럼 보여 준다. 그리고 한 VM이 다른 VM의 메모리나 장치를 건드리지 못하게 막는다. VM 안에서 도는 OS를 게스트, 바깥을 호스트라고 부른다.

이렇게 만든 VM을 클라우드에서는 인스턴스라고 부른다. EC2 인스턴스 하나는 어떤 물리 서버 위에 올라간 VM 하나다(베어메탈 인스턴스는 예외로 뒤에서 본다). 그래서 인스턴스를 멈췄다 다시 켜면 다른 물리 서버에서 뜰 수 있고, 그때 인스턴스 스토어 디스크의 내용이 사라진다. 디스크가 그 물리 서버에 붙어 있었기 때문이다.

## 하이퍼바이저가 어디에 앉아 있나

하이퍼바이저는 앉은 자리로 두 종류를 나눈다.

타입 1(베어메탈 하이퍼바이저)은 하드웨어 바로 위에서 돈다. 하이퍼바이저 자체가 작은 OS처럼 부팅하고, 그 위에 VM이 올라간다. VMware ESXi, Xen, Microsoft Hyper-V가 여기에 든다. 데이터센터와 클라우드는 거의 다 이쪽이다.

타입 2(호스트형 하이퍼바이저)는 평범한 OS 위에서 프로그램으로 돈다. VirtualBox, VMware Workstation, Parallels가 그렇다. 노트북에서 리눅스 VM을 띄울 때 쓴다. 디스크 읽기 하나도 게스트 커널 → 하이퍼바이저 프로그램 → 호스트 OS → 하드웨어로 한 단계 더 거치니 느리고, 호스트 OS의 스케줄러가 VM을 다른 프로그램과 똑같이 다룬다.

KVM은 이 구분이 애매하다. 리눅스 커널 모듈(`kvm.ko`, `kvm_intel.ko`)이라 평범한 리눅스 위에 올라가는 것처럼 보이지만, 모듈을 올리는 순간 리눅스 커널 자체가 하이퍼바이저가 된다. VM 하나는 호스트에서 프로세스 하나로 보이고 vCPU는 그 프로세스의 스레드다. 그래서 보통 타입 1로 분류한다. KVM은 CPU와 메모리 가상화를 맡고, 가상 장치(디스크 컨트롤러, 네트워크 카드)를 흉내 내는 일은 QEMU나 Firecracker 같은 사용자 공간 프로그램이 맡는다.

## 게스트가 특권 명령을 쓰면 CPU가 멈춰 세운다

게스트 커널은 자기가 진짜 하드웨어 위에 있다고 믿고 특권 명령을 실행한다. 페이지 테이블 기준 레지스터(CR3)를 바꾸거나, 장치 레지스터에 쓰거나, CPU 정보를 묻는 `cpuid`를 실행한다. 이걸 그대로 하드웨어에 넘기면 VM끼리 서로를 망가뜨린다.

예전에는 소프트웨어로 해결했다. 게스트 커널 코드를 실행 전에 훑어 위험한 명령을 안전한 코드로 바꿔 치는 바이너리 변환(VMware 초기 방식), 아예 게스트 커널을 고쳐 특권 명령 대신 하이퍼바이저를 부르게 만드는 반가상화(초기 Xen)가 그 방법이었다.

2005~2006년에 Intel VT-x와 AMD-V가 나오면서 CPU가 이 일을 직접 맡았다. CPU에 "게스트 모드"(VMX non-root)가 생겼고, 하이퍼바이저는 VM마다 어떤 사건이 나면 자기를 깨워 달라고 CPU에 적어 둔다(Intel은 이 표를 VMCS라고 부른다). 게스트는 대부분의 명령을 진짜 CPU 속도로 실행하다가, 적어 둔 사건을 만나면 CPU가 게스트를 멈추고 하이퍼바이저로 넘어간다. 이것을 VM exit(트랩)라고 한다. 하이퍼바이저가 그 명령을 대신 처리하고 결과를 게스트 레지스터에 써 준 뒤 VM entry로 돌려보낸다. 게스트는 아무 일도 없었던 것처럼 다음 명령을 실행한다.

이 한 바퀴가 얼마나 비싼지 재 봤다. 덧셈 반복과 `cpuid` 반복을 각각 20만 번 돌린다.

```bash
# 덧셈 한 번과 cpuid 한 번의 시간을 비교한다
cat > trap.c <<'EOF'
#include <stdio.h>
#include <stdint.h>
#include <time.h>
static inline void cpuid(uint32_t l){uint32_t a,b,c,d;
  __asm__ volatile("cpuid":"=a"(a),"=b"(b),"=c"(c),"=d"(d):"a"(l),"c"(0));}
static double now(){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);
  return t.tv_sec*1e9+t.tv_nsec;}
int main(){int N=200000;volatile int x=0;
  double t0=now(); for(int i=0;i<N;i++){x+=i;}
  double t1=now(); for(int i=0;i<N;i++)cpuid(0);
  double t2=now();
  printf("add loop : %.1f ns/iter\ncpuid    : %.1f ns/iter\n",(t1-t0)/N,(t2-t1)/N);}
EOF
gcc -O1 -o trap trap.c && ./trap
```

```text
add loop : 1.7 ns/iter
cpuid    : 10882.8 ns/iter
```

`cpuid` 한 번에 10.9마이크로초, 덧셈 반복보다 6,000배 넘게 느리다. 이 숫자는 샌드박스 사정 때문에 꽤 크게 나온 편이다. 이 환경은 그 아래에 가상화 층이 하나 더 있을 가능성이 높아서 exit가 바깥 하이퍼바이저까지 다녀온다. 보통 클라우드 VM에서 재면 마이크로초 안팎으로 나오는 경우가 많다. 그래도 방향은 같다. VM exit는 평범한 명령보다 수백~수천 배 비싸다.

그래서 가상화 기술의 역사는 exit를 줄이는 역사다. 다음 두 절이 그 대표다.

## 메모리는 두 번 번역한다

게스트 커널은 자기 페이지 테이블로 가상 주소를 "물리 주소"로 바꾼다. 그런데 그 물리 주소는 진짜 물리 주소가 아니라 하이퍼바이저가 VM에게 준 가짜 공간(게스트 물리 주소)이다. 진짜 메모리 칸까지 가려면 한 번 더 번역해야 한다.

VT-x 초기에는 하이퍼바이저가 두 번역을 합친 그림자 페이지 테이블을 따로 만들어 CPU에 물렸다. 게스트가 페이지 테이블을 바꿀 때마다 exit가 나서 그림자를 고쳐야 했으니, 프로세스를 자주 만드는 일(웹 서버의 fork, 컴파일)이 많이 느렸다. 2008년 전후로 Intel EPT, AMD NPT가 나오면서 CPU가 두 단계 번역을 하드웨어로 한다. 게스트는 자기 페이지 테이블을 exit 없이 마음껏 바꾸고, CPU가 TLB 미스 때 두 표를 차례로 걷는다.

대신 TLB 미스 한 번의 비용이 커진다. 4단계 페이지 테이블 두 개를 겹쳐 걸으면 최악에 메모리 접근이 스무 번 넘게 필요하다. 큰 메모리를 쓰는 DB나 JVM이 VM에서 huge page(2MB 페이지)를 켜면 체감이 큰 이유다. TLB 이야기는 [가상 메모리와 페이징](/posts/virtual-memory-paging)에서 다뤘다.

## CPU는 나눠 쓰고, 메모리는 대개 나눠 쓰지 않는다

vCPU는 호스트 입장에서 스레드 하나다. 호스트 스케줄러가 물리 코어에 vCPU 스레드를 번갈아 올린다. 그래서 물리 코어보다 vCPU를 더 많이 팔 수 있다. 사내 VMware 클러스터에서는 물리 코어 하나에 vCPU 넷을 얹는 식의 과할당(overcommit)이 흔하다. 다들 동시에 CPU를 쓰지는 않는다는 데 거는 것이다. 동시에 쓰는 순간 대기가 생기고, 그게 게스트에서는 steal로 보인다.

메모리는 사정이 다르다. CPU는 기다리면 그만이지만 메모리는 모자라면 누군가의 페이지를 디스크로 내보내야 하고, 게스트 커널은 자기 메모리가 디스크로 나간 줄도 모른 채 느려진다. 하이퍼바이저가 쓰는 회수 방법은 몇 가지다. 벌룬 드라이버(위 출력의 `virtio_balloon`)는 게스트 안에서 메모리를 할당받아 "안 쓰는 메모리"로 하이퍼바이저에 돌려준다. KSM은 VM들 사이에 내용이 같은 페이지를 하나로 합친다. 둘 다 사내 가상화에서는 쓰지만, 퍼블릭 클라우드의 일반 인스턴스는 메모리를 과할당하지 않는 것이 보통이다. 인스턴스 타입에 적힌 메모리는 그만큼 실제로 잡혀 있다고 보면 된다. KSM은 페이지가 합쳐졌는지를 쓰기 시간 차로 알아내는 부채널 공격의 통로가 되기도 해서, 서로 믿지 않는 VM 사이에서는 꺼 두는 쪽이 안전하다.

현장에서 기억할 숫자는 하나다. 게스트 안에서 `free`로 보이는 메모리는 하이퍼바이저가 약속한 양이고, 그 너머는 없다. 메모리가 모자라면 게스트 커널의 OOM killer가 프로세스를 죽인다. 호스트가 대신 스왑해 주지 않는다.

## 디스크와 네트워크는 흉내 내지 않고 약속한다

가장 비싼 exit는 장치 쪽에서 난다. 하이퍼바이저가 옛날 네트워크 카드(Intel e1000 같은)를 그대로 흉내 내면, 게스트 드라이버가 패킷 하나를 보낼 때 레지스터를 여러 번 건드리고 그때마다 exit가 난다. 패킷이 초당 수십만 개면 exit도 초당 수백만 번이다.

반가상화 드라이버는 이걸 약속으로 바꾼다. 게스트는 "나는 VM 안에 있다"는 사실을 알고, 하이퍼바이저와 공유 메모리에 링 버퍼(virtqueue)를 하나 둔다. 보낼 패킷 여러 개를 링에 쌓고 한 번만 "새 일 있음" 신호를 보낸다. 하이퍼바이저도 처리한 것들을 모아 인터럽트 한 번으로 알린다. 표준 이름이 virtio이고, 리눅스는 `virtio_net`, `virtio_blk` 드라이버를 기본으로 갖고 있다.

```bash
# 게스트 안에서 어떤 virtio 드라이버가 올라와 있는지 본다
ls /sys/bus/virtio/drivers

# 블록 장치 이름이 vd*면 virtio-blk, nvme*면 NVMe로 붙은 것이다
lsblk -d -o NAME,SIZE,TYPE
```

```text
nvproxy
virtio_balloon
virtio_blk
virtio_console
virtio_mem
virtio_net
virtio_pmem
virtio_rng
virtio_rproc_serial
vmw_vsock_virtio_transport
NAME    SIZE TYPE
vda     256G disk
vdb     9.6M disk
```

이 샌드박스의 디스크는 `vda`, 즉 virtio-blk다. 같은 명령을 Nitro 인스턴스에서 치면 EBS 볼륨이 `nvme0n1`, `nvme1n1`처럼 NVMe로 보이고 네트워크는 `ena` 드라이버로 보인다. 이 차이가 다음 절의 이야기다.

## Nitro가 하이퍼바이저를 카드로 뺀 이유

virtio를 써도 장치 처리 자체는 호스트 CPU가 한다. QEMU든 커널 스레드든 누군가 패킷을 꺼내 진짜 네트워크 카드로 넘기고, 디스크 요청을 스토리지 네트워크로 보내야 한다. Xen 시절 EC2는 이 일을 dom0이라는 관리용 VM이 했고, 그 VM이 물리 CPU와 메모리를 꽤 잡아먹었다. 장치 처리가 바쁜 순간에는 같은 호스트의 게스트 VM들 지연에도 영향을 줬다.

AWS는 2017년 c5부터 이 일을 Nitro라는 전용 하드웨어로 내렸다. 구성은 이렇다.

- Nitro 카드: VPC 네트워킹(ENA), EBS 접속, 인스턴스 스토어, 시스템 관리를 맡는 PCIe 카드들이다. 게스트는 SR-IOV로 카드의 가상 기능(VF)을 직접 받아 쓰므로, 패킷과 디스크 요청이 호스트 CPU를 거치지 않는다. 게스트 눈에는 그냥 ENA 네트워크 카드와 NVMe 컨트롤러가 붙은 것으로 보인다.
- Nitro 하이퍼바이저: 장치 일이 빠졌으니 CPU와 메모리 나누기만 하는 얇은 KVM 기반 하이퍼바이저가 남았다. 관리용 VM이 따로 없다.
- Nitro 보안 칩: 메인보드 펌웨어를 검증하고, 호스트 쪽에서 운영자가 로그인할 셸 자체를 두지 않는 설계를 받친다.

## 옆방이 시끄러울 때: steal time

처음 이야기로 돌아간다. `top`의 `st`는 steal time이다. 게스트의 vCPU가 돌 준비가 됐는데 하이퍼바이저가 그 시간에 물리 CPU를 다른 일(다른 VM, 호스트 작업)에 줬다는 뜻이다. 게스트 커널은 하이퍼바이저가 알려 주는 값(KVM은 공유 메모리의 steal 카운터)으로 이걸 센다. 게스트 안에서는 이 시간을 되찾을 방법이 없다.

```bash
# 1초 간격 3번. 맨 오른쪽 st가 steal이다
vmstat 1 3

# CPU별로 %steal을 본다. 특정 vCPU만 높은지 확인할 때 쓴다
mpstat -P ALL 1 1

# 누적값: cpu 줄의 8번째 숫자가 부팅 후 steal(단위 USER_HZ, 보통 1/100초)
head -1 /proc/stat
```

```text
procs -----------memory---------- ---swap-- -----io---- -system-- -------cpu-------
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st gu
 1  0      0 5690828 606420 6759268    0    0  1899  4709 2827   14 63  8 12 16  1  0
 1  0      0 5667392 606656 6766956    0    0     0 36224 2759 3360 29  5 64  0  1  0
 3  0      0 5633396 606956 6774872    0    0    80   292 3072 4023 31  6 60  1  1  0
```

```text
cpu  543624 81 59382 102355 136081 0 6467 9501 0 0
```

이 샌드박스는 `st`가 1% 수준이고, 누적 steal이 9501(약 95초)이다. 첫 줄은 부팅 이후 평균이라 무시하고 둘째 줄부터 본다. 판단 기준은 이렇게 잡는다. 몇 % 수준이 잠깐 보이는 건 흔하다. 두 자릿수가 꾸준하거나 지연이 튀는 시각과 정확히 겹치면 원인으로 본다. 앱 지연 그래프와 steal 그래프를 같은 시간축에 놓고 겹쳐 보는 게 가장 빠른 확인법이다.

AWS에서 steal이 보이는 대표 경우는 셋이다.

T 계열(t3, t4g 같은 버스트형)은 CPU 크레딧이 떨어지면 기준 성능(예: t3.micro는 vCPU당 10%)으로 묶인다. 이때 묶인 시간이 steal로 보인다. 진짜 이웃 때문이 아니라 내 크레딧 문제이니, CloudWatch의 `CPUCreditBalance`가 0에 붙어 있는지 먼저 본다. 꾸준히 CPU를 쓰는 서비스를 T 계열에 올리면 이렇게 된다.

T 계열이 아닌 Nitro 인스턴스는 vCPU를 물리 CPU에 과하게 몰아 넣지 않는다고 AWS가 설명한다. 그래서 steal 자체는 드물다. 그런데도 이웃의 영향이 사라지지는 않는다. L3 캐시, 메모리 대역폭, 같은 랙의 네트워크는 여전히 함께 쓴다. 이 경우 steal은 0인데 같은 코드의 IPC(명령당 사이클)가 떨어지는 식으로 나타나서 게스트 안에서는 잘 안 보인다.

마지막은 호스트 하드웨어 문제다. 특정 인스턴스만 계속 이상하면, 멈췄다 다시 켜서(재부팅이 아니라 stop/start) 다른 호스트로 옮기는 게 가장 싼 해결책이다. 재부팅은 같은 호스트에 남는다.

## 베어메탈 인스턴스가 필요한 경우

`.metal` 크기(m7i.metal-24xl, i4i.metal 같은)는 하이퍼바이저 없이 물리 서버를 통째로 준다. Nitro 카드는 그대로 있어서 VPC, EBS, 보안 그룹은 똑같이 쓴다. 그래서 일반 인스턴스와 같은 API로 빌리지만 OS가 진짜 하드웨어를 본다.

이게 필요한 경우는 대체로 이렇다.

- 내가 하이퍼바이저를 돌려야 할 때. VMware, 자체 KVM 클러스터, Firecracker로 microVM을 띄우는 샌드박스 서비스가 그렇다. 일반 인스턴스는 오랫동안 중첩 가상화를 허용하지 않았다. 최근 일부 인스턴스 계열로 넓어지고 있으니 쓰려는 타입의 문서를 확인한다.
- 하드웨어 기능을 직접 써야 할 때. CPU 성능 카운터 전체(정밀 프로파일링), 특정 CPU 확장, 하드웨어 기반 보안 기능 같은 것들이다.
- 물리 코어·소켓 단위 라이선스. 일부 상용 DB나 OS는 물리 코어 수로 값을 매긴다. 공유 호스트에서는 셈이 애매해서 전용 호스트나 베어메탈을 요구하기도 한다.
- 가상화 오버헤드가 정말 문제일 때. Nitro 덕분에 일반 인스턴스와의 차이는 작다. "조금 더 빠를 것 같아서"는 좋은 이유가 아니다. 대신 베어메탈은 크기가 크고(대개 해당 패밀리의 가장 큰 크기와 같다) 부팅이 몇 분씩 걸린다.

비슷한 이름의 전용 인스턴스(Dedicated Instance)와 전용 호스트(Dedicated Host)도 있다. 둘 다 내 계정만 그 물리 서버를 쓰게 해서 이웃을 없애지만, 하이퍼바이저는 그대로 있다. 이웃이 문제면 전용 호스트, 하이퍼바이저가 문제면 베어메탈이다.

## 살아 있는 VM을 옮기는 법

호스트를 패치하거나 하드웨어를 바꿔야 할 때, 그 위의 VM을 끄지 않고 다른 호스트로 옮기는 기술이 라이브 마이그레이션이다. 디스크는 네트워크 스토리지(EBS 같은)에 있으면 옮길 필요가 없다. 문제는 메모리다. 16GB를 복사하는 동안에도 VM은 계속 돌면서 메모리를 바꾼다.

가장 흔한 방식인 pre-copy는 이렇게 한다. 먼저 전체 메모리를 대상 호스트로 복사한다. 그동안 바뀐 페이지(dirty page)는 하이퍼바이저가 페이지 쓰기를 추적해 표시해 둔다. 다음 회차에는 표시된 페이지만 다시 보낸다. 회차마다 보낼 양이 줄어든다. 남은 양이 아주 작아지면 VM을 잠깐 멈추고 마지막 dirty 페이지와 CPU·장치 상태를 보낸 뒤 대상에서 재개한다. 이 멈춤(downtime)이 보통 수십~수백 밀리초다. 네트워크는 대상 호스트가 주소 알림(gratuitous ARP 같은)을 보내 패킷이 새 자리로 오게 만든다.

아래는 16GB VM을 1.2GB/s 링크로 옮기고, 게스트가 초당 100MB씩 메모리를 더럽힌다고 놓고 계산한 회차별 흐름이다.

dirty 속도가 링크 속도보다 빠르면 이 반복은 끝나지 않는다. 메모리를 초당 1.5GB씩 바꾸는 인메모리 DB를 1.2GB/s로 옮기려 하면 회차마다 보낼 양이 오히려 는다. 하이퍼바이저는 이때 몇 가지를 한다. 회차 수에 상한을 두고 그냥 멈춰 길게 복사하거나, 게스트 vCPU를 일부러 느리게 만들어 dirty 속도를 낮추거나(QEMU의 auto-converge), 방향을 바꿔 post-copy로 간다. post-copy는 CPU 상태만 먼저 옮겨 대상에서 바로 재개하고, 없는 페이지는 접근할 때마다 원래 호스트에서 끌어온다. 멈춤은 짧지만 그동안 페이지 폴트마다 네트워크 왕복이 생기고, 중간에 원래 호스트가 죽으면 VM을 잃는다.

클라우드마다 이걸 쓰는 방식이 다르다. Google Compute Engine은 호스트 유지 보수 때 기본으로 라이브 마이그레이션을 하고(`onHostMaintenance=MIGRATE`), 사용자는 거의 모르고 지나간다. EC2는 라이브 마이그레이션을 사용자에게 드러나는 기능으로 내놓지 않는다. 대신 호스트를 바꿔야 하면 예약 이벤트(`instance-retirement`, `system-reboot` 같은)를 보내고, 정한 날짜 전에 사용자가 stop/start로 옮기라고 한다. 그래서 EC2에서는 "언젠가 이 인스턴스는 다시 시작된다"를 전제로 설계한다. 여러 AZ에 나눠 두고, 인스턴스 하나가 내려가도 서비스가 사는 구조가 그 답이다. 이 이야기는 [고가용성](/posts/high-availability)에서 이어진다.

```bash
# 이 인스턴스에 예약 이벤트가 있는지 인스턴스 안에서 확인한다 (IMDSv2)
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/events/maintenance/scheduled
```

예정된 이벤트가 있으면 이벤트 코드(`system-reboot` 같은)와 시작·종료 시각이 담긴 JSON이 온다. 계정 전체로는 AWS Health 대시보드나 `aws ec2 describe-instance-status`로 본다.

## VM과 컨테이너, 격리의 두께가 다르다

컨테이너도 "한 서버를 여러 개로 나눈다"는 점은 같다. 하지만 나누는 층이 다르다. VM은 하드웨어를 나눠 커널을 여러 개 띄우고, 컨테이너는 커널 하나를 함께 쓰면서 프로세스마다 보이는 세상(namespace)과 쓸 수 있는 양(cgroup)만 나눈다. 원리는 [컨테이너는 무엇인가](/posts/docker-container-basics)에서 직접 띄워 봤다.

이 차이가 보안의 차이로 이어진다. VM 안의 코드가 밖으로 나가려면 하이퍼바이저가 열어 둔 좁은 문(몇 가지 virtio 장치, 정해진 hypercall, VM exit 처리 코드)을 뚫어야 한다. 컨테이너 안의 코드는 호스트 커널의 시스템 콜 수백 개를 그대로 부른다. 그중 하나에 권한 상승 버그가 있으면 그 커널 위의 모든 컨테이너가 위험하다. 2022년의 Dirty Pipe(CVE-2022-0847)가 그런 커널 버그였고, 2019년의 runc 취약점(CVE-2019-5736)은 컨테이너 런타임 쪽에서 호스트 바이너리를 덮어쓸 수 있게 했다.

그래서 남의 코드를 돌리는 서비스(서버리스, 온라인 코드 실행, 멀티테넌트 CI)는 컨테이너만으로 사용자를 나누지 않는다. 몇 가지 선택지가 있다.

- seccomp, AppArmor, user namespace로 컨테이너가 부를 수 있는 것을 줄인다. 가장 싸지만 같은 커널을 쓴다는 사실은 그대로다.
- gVisor는 사용자 공간에 커널을 하나 더 두고 컨테이너의 시스템 콜을 거기서 받는다. 호스트 커널에 닿는 문이 좁아지는 대신 시스템 콜이 많은 작업은 느려진다.
- Kata Containers나 Firecracker는 컨테이너마다 아주 작은 VM(microVM)을 띄운다. Firecracker는 장치를 몇 개만 흉내 내도록 줄여 microVM 하나를 1초 안쪽에 띄운다. AWS Lambda가 함수 실행 환경을 이걸로 나눈다. 콜드 스타트 이야기는 [콜드 스타트](/posts/cold-starts)에서 다뤘다.

반대로 내 팀의 서비스만 올라가는 클러스터라면 컨테이너 격리로 충분한 경우가 많다. 기준은 "같은 커널 위에 서로 믿지 않는 코드가 올라가는가"다. EKS 노드 하나에 여러 팀의 Pod가 섞인다면 노드 풀을 팀별로 나누거나, 믿지 않는 작업만 샌드박스 런타임으로 돌린다.

자원 면에서도 다르다. VM은 게스트 커널과 그 메모리를 통째로 들고 있어서 작은 서비스 수십 개를 VM 하나씩 올리면 낭비가 크다. 컨테이너는 그 몫이 없어서 촘촘히 올라간다. 대신 컨테이너의 메모리 제한은 cgroup이 걸고, 넘으면 OOM으로 죽는다. VM은 정한 메모리 이상을 게스트가 아예 못 본다.

## 지연이 튈 때 보는 순서

같은 타입의 인스턴스 하나만 이상할 때, 이 글의 내용을 순서로 정리하면 이렇다.

1. 앱 지연 그래프를 인스턴스별로 나눈다. 전체가 튀면 하이퍼바이저보다 앱이나 의존성 쪽이다.
2. 튀는 인스턴스에서 `mpstat -P ALL 1`이나 `vmstat 1`로 `st`를 본다. 지연과 같은 시각에 두 자릿수면 CPU를 빼앗기고 있다.
3. T 계열이면 `CPUCreditBalance`를 본다. 0에 붙어 있으면 이웃이 아니라 크레딧 문제다. 무제한 모드를 켜거나 고정 성능 계열로 옮긴다.
4. steal은 0인데 그 인스턴스만 느리면 디스크와 네트워크 상한을 의심한다. EBS 대역폭(`EBSByteBalance%`)이나 ENA의 허용치 초과 카운터(`ethtool -S eth0`의 `bw_in_allowance_exceeded`, `pps_allowance_exceeded`)가 오르는지 본다.
5. 다 깨끗한데 그 인스턴스만 계속 이상하면 stop/start로 호스트를 바꾼다. 같은 증상이 따라오면 인스턴스가 아니라 설정 문제다.

## 하이퍼바이저는 exit를 줄이는 쪽으로 발전했다

하이퍼바이저는 CPU 시간, 메모리, 장치를 VM마다 나눠 주고 서로를 막는 층이다. 평범한 명령은 진짜 CPU에서 그대로 돌고, 위험한 명령만 VM exit로 하이퍼바이저에 넘어간다. 그 exit가 비싸서 하드웨어 페이지 번역(EPT), 반가상화 장치(virtio), 장치 처리를 아예 카드로 내린 Nitro가 차례로 나왔다. 그래도 캐시와 메모리 대역폭은 함께 쓰니 이웃의 흔적은 남고, 그걸 보는 첫 번째 창이 steal time이다. 다음으로는 이 VM에 붙이는 디스크가 어떻게 다른지 [블록, 파일, 객체 스토리지](/posts/block-file-object-storage)에서 본다.

## 면접에서 나올 만한 질문

### 하이퍼바이저 타입 1과 타입 2는 어떻게 다른가요?

타입 1은 하드웨어 바로 위에서 돌고, 타입 2는 일반 OS 위에서 프로그램으로 돈다. ESXi, Xen, Hyper-V가 타입 1이고 VirtualBox, VMware Workstation이 타입 2다. 타입 2는 I/O가 호스트 OS를 한 번 더 거치고 호스트 스케줄러의 영향을 받아서 서버용으로는 잘 쓰지 않는다. KVM은 리눅스 커널 모듈이지만 커널 자체를 하이퍼바이저로 만들기 때문에 보통 타입 1로 본다.

### 하드웨어 가상화 지원(VT-x)은 무엇을 해 주나요?

CPU에 게스트 모드를 만들어 게스트 명령 대부분을 그대로 실행하게 하고, 미리 정한 민감한 명령이나 사건에서만 VM exit로 하이퍼바이저에 넘긴다. 그 전에는 바이너리 변환이나 게스트 커널 수정(반가상화)으로 특권 명령을 바꿔야 했다. VM exit는 평범한 명령보다 수백~수천 배 비싸서, EPT 같은 하드웨어 메모리 번역과 virtio 같은 반가상화 장치로 exit 자체를 줄이는 게 성능의 핵심이다.

### 반가상화 드라이버(virtio)는 왜 빠른가요?

게스트가 자기가 VM 안에 있다는 걸 알고, 하이퍼바이저와 공유 메모리 링 버퍼로 요청을 주고받기 때문이다. 옛 장치를 흉내 내면 레지스터를 건드릴 때마다 exit가 나지만, virtio는 요청 여러 개를 쌓고 알림 한 번으로 넘긴다. 처리 결과도 모아서 인터럽트 한 번으로 돌려준다.

### AWS Nitro는 기존 Xen 기반 구조와 무엇이 다른가요?

네트워크, EBS, 인스턴스 스토어, 관리 기능을 전용 하드웨어 카드로 내렸다는 점이 가장 크다. 예전에는 관리용 VM(dom0)이 호스트 CPU로 장치 처리를 했지만, Nitro에서는 게스트가 SR-IOV로 카드를 직접 쓰고 하이퍼바이저는 CPU와 메모리만 나눈다. 그 결과 호스트 자원이 거의 다 게스트에 가고, 베어메탈 인스턴스에서도 같은 VPC·EBS를 쓸 수 있다. 실무에서는 AMI에 ENA·NVMe 드라이버가 있어야 한다는 점을 챙긴다.

### steal time이 무엇이고 어떻게 확인하나요?

vCPU가 돌 준비가 됐는데 하이퍼바이저가 물리 CPU를 다른 곳에 줘서 못 돈 시간이다. `top`의 `st`, `vmstat`의 `st`, `mpstat`의 `%steal`, `/proc/stat`의 여덟 번째 값으로 본다. 앱 지연이 튀는 시각과 겹치는지가 판단 기준이다. AWS T 계열에서는 CPU 크레딧이 떨어져 기준 성능으로 묶인 시간이 steal로 보이니 `CPUCreditBalance`를 먼저 확인한다.

### 컨테이너가 VM보다 덜 안전하다고 하는 이유는요?

컨테이너들은 호스트 커널 하나를 함께 쓰고, 수백 개의 시스템 콜이 그대로 공격 표면이 되기 때문이다. 커널 권한 상승 버그 하나면 그 호스트의 모든 컨테이너가 위험해진다. VM은 하이퍼바이저가 열어 둔 좁은 인터페이스만 뚫을 수 있다. 그래서 믿지 않는 코드를 돌리는 곳은 seccomp 같은 제한을 걸거나 gVisor, Firecracker 같은 더 두꺼운 격리를 쓴다.

### 라이브 마이그레이션은 메모리를 어떤 순서로 옮기나요?

pre-copy 방식은 VM을 돌리면서 메모리 전체를 먼저 보내고, 그동안 바뀐 dirty 페이지만 회차마다 다시 보낸다. 남은 양이 충분히 작아지면 VM을 잠깐 멈추고 마지막 페이지와 CPU 상태를 보낸 뒤 대상에서 재개한다. dirty 속도가 링크 속도보다 빠르면 수렴하지 않아서, vCPU를 느리게 만들거나 post-copy로 바꾼다. EC2는 이걸 사용자 기능으로 드러내지 않고 예약 이벤트와 stop/start로 호스트를 옮기게 하니, 인스턴스가 다시 시작될 수 있다는 전제로 설계한다.

### 베어메탈 인스턴스는 언제 고르나요?

직접 하이퍼바이저를 돌려야 하거나(VMware, Firecracker), CPU 성능 카운터 같은 하드웨어 기능이 필요하거나, 물리 코어 단위 라이선스를 맞춰야 할 때 고른다. Nitro 덕분에 일반 인스턴스와의 성능 차이는 작아서 성능만 보고 고를 일은 드물다. 이웃만 없애고 싶다면 하이퍼바이저가 남아 있는 전용 호스트로도 충분하다.
