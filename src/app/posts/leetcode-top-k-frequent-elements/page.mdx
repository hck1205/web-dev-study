[Top K Frequent Elements](https://leetcode.com/problems/top-k-frequent-elements/)는 LeetCode 347번이다. 배열에서 가장 자주 나온 값 k개를 돌려준다. 실무에서도 자주 보는 모양이다. 로그에서 가장 많이 호출된 API 열 개, 검색어 순위, 에러 코드 상위 다섯 개처럼 "세고, 많이 나온 것 몇 개를 고른다"는 일은 어디에나 있다.

문제는 끝에 "O(n log n)보다 빠르게 풀어 보라"는 조건을 붙인다. 그래서 이 문제는 정렬을 넘어서는 선택지를 묻는 문제가 된다. 이 글은 세는 단계는 같다는 걸 먼저 짚고, 고르는 단계를 다섯 가지로 푼다. k번 최댓값 뽑기, 전체 정렬, 크기 k인 힙, 빈도 버킷, 퀵셀렉트다. 힙의 동작은 [힙 글](/posts/ds-heap)에, 정렬의 하한은 [정렬 알고리즘 글](/posts/sorting-algorithms)에 있다. 개수를 세는 장부는 [Contains Duplicate](/posts/leetcode-contains-duplicate)와 [Valid Anagram](/posts/leetcode-valid-anagram)에서 쓴 것과 같다. 코드는 Node.js 22, Python 3.13, Java 21에서 돌렸다.

## 많이 나온 값 k개를 고른다

정수 배열 `nums`와 정수 `k`가 주어진다. 가장 자주 나온 값 k개를 돌려준다. 순서는 상관없다. 풀이를 정하는 제약은 이렇다.

- 배열 길이 n은 1 이상 10^5 이하, 값은 -10^4 이상 10^4 이하다.
- k는 1 이상, 서로 다른 값의 개수 이하다.
- 답은 하나로 정해진다. 즉 k번째와 k+1번째의 빈도가 같아 답이 갈리는 입력은 들어오지 않는다.

세 번째 약속이 생각보다 중요하다. 동점 때문에 답이 여러 개일 수 있다면 "어느 쪽을 고르나"를 정해야 하는데, 이 문제는 그 고민을 없애 줬다. 뒤에서 동점 규칙이 붙는 변형(Top K Frequent Words)을 따로 본다.

이 글에서 n은 배열 길이, m은 서로 다른 값의 개수다. m은 n 이하다.

세는 데 O(n) 시간, O(m) 공간이 든다. 이 단계는 모든 풀이에 공통이고 피할 수 없다. 배열을 한 번은 다 봐야 빈도를 알 수 있기 때문이다. 이제 남은 일은 m개의 (값, 횟수) 쌍에서 횟수가 큰 k개를 고르는 것이다. 아래 풀이들은 전부 이 고르는 단계만 다르다.

## 가장 많은 것을 k번 골라내기

가장 단순한 방법은 장부를 훑어 가장 큰 횟수를 찾아 답에 넣고, 그 값을 장부에서 지우는 일을 k번 하는 것이다.

```js
function topKFrequent(nums, k) {
  const count = new Map();
  for (const x of nums) count.set(x, (count.get(x) ?? 0) + 1);

  const res = [];
  for (let r = 0; r < k; r++) {
    let best = null, bestC = -1;
    for (const [v, c] of count) if (c > bestC) { best = v; bestC = c; } // 남은 것 중 최댓값
    res.push(best);
    count.delete(best); // 다음 바퀴에서 다시 고르지 않게 지운다
  }
  return res;
}

console.log(topKFrequent([4, 1, 4, 6, 1, 4, 2, 1, 4], 2));
```

```text
[ 4, 1 ]
```

시간은 세기 O(n)에 고르기 O(k × m)이다. k가 작으면 꽤 빠르다. k가 1이면 O(n + m)으로 사실상 최선이다. 하지만 k가 m에 가까우면 O(m²)가 된다. 서로 다른 값 3만 개 중 5천 개를 고르게 했더니 2초 가까이 걸렸다(뒤의 측정 절). 고르는 일을 한 번에 정리하는 방법이 필요하다.

## 빈도순으로 전부 정렬하기

장부의 쌍을 횟수 내림차순으로 정렬하고 앞에서 k개를 자른다.

```js
function topKFrequent(nums, k) {
  const count = new Map();
  for (const x of nums) count.set(x, (count.get(x) ?? 0) + 1);
  return [...count.entries()]          // [[4, 4], [1, 3], [6, 1], [2, 1]]
    .sort((a, b) => b[1] - a[1])       // 횟수 내림차순
    .slice(0, k)
    .map(([v]) => v);
}

console.log(topKFrequent([4, 1, 4, 6, 1, 4, 2, 1, 4], 2));
```

```text
[ 4, 1 ]
```

시간은 O(n + m log m)이다. 값이 모두 다르면 m = n이라 O(n log n)이다. 공간은 쌍 배열 O(m)이다. 코드가 짧고 k와 상관없이 일정하게 빠르다. 면접에서 처음 꺼내기 좋은 답이다.

그런데 문제가 바로 이 O(n log n)을 넘으라고 한다. 정렬은 k개만 필요한데 m개 전부의 순서를 정한다. k + 1등부터의 순서는 아무도 묻지 않았다. 필요한 만큼만 순서를 정하는 방법이 두 가지 있다. 상위 k개만 들고 다니는 힙, 그리고 k번째 경계만 찾는 퀵셀렉트다.

## 크기 k인 힙만 들고 다니기

최소 힙(min-heap)은 가장 작은 값을 항상 맨 위에 두는 자료구조다. 넣기와 빼기가 O(log 크기)다. 이 힙에 (값, 횟수) 쌍을 횟수 기준으로 넣되, 크기가 k를 넘으면 맨 위(가장 적게 나온 것)를 버린다. 그러면 힙에는 언제나 "지금까지 본 것 중 상위 k개"만 남는다.

최대 힙이 아니라 최소 힙을 쓰는 게 처음엔 헷갈린다. 힙의 맨 위는 "상위 k개 중 꼴찌"다. 새로 온 값이 그 꼴찌보다 많이 나왔으면 꼴찌를 내보내고 들어오고, 아니면 바로 밀려난다. 꼴찌가 누구인지 O(1)에 알아야 하니 최소 힙이다.

JavaScript에는 힙이 기본으로 없어서 직접 만든다.

```js
class MinHeap {
  constructor() { this.a = []; } // 원소는 [값, 횟수]. 횟수가 작은 것이 위
  get size() { return this.a.length; }
  push(item) {
    const a = this.a; a.push(item);
    let i = a.length - 1;
    while (i > 0) {                       // 부모보다 작으면 위로 올린다
      const p = (i - 1) >> 1;
      if (a[p][1] <= a[i][1]) break;
      [a[p], a[i]] = [a[i], a[p]]; i = p;
    }
  }
  pop() {
    const a = this.a, top = a[0], last = a.pop();
    if (a.length) {
      a[0] = last; let i = 0;
      for (;;) {                          // 자식 중 작은 쪽과 바꾸며 내려간다
        const l = 2 * i + 1, r = l + 1; let m = i;
        if (l < a.length && a[l][1] < a[m][1]) m = l;
        if (r < a.length && a[r][1] < a[m][1]) m = r;
        if (m === i) break;
        [a[m], a[i]] = [a[i], a[m]]; i = m;
      }
    }
    return top;
  }
}

function topKFrequent(nums, k) {
  const count = new Map();
  for (const x of nums) count.set(x, (count.get(x) ?? 0) + 1);
  const heap = new MinHeap();
  for (const entry of count) {
    heap.push(entry);
    if (heap.size > k) heap.pop(); // 상위 k개에 못 드는 것을 버린다
  }
  return heap.a.map(([v]) => v);
}

console.log(topKFrequent([4, 1, 4, 6, 1, 4, 2, 1, 4], 2));
```

```text
[ 1, 4 ]
```

힙 풀이의 진짜 장점은 데이터가 흘러 들어올 때 드러난다. 정렬은 모든 쌍을 다 모아야 시작할 수 있지만, 힙은 쌍이 하나씩 와도 그때그때 상위 k개를 유지한다. 장부가 너무 커서 디스크에서 읽어 와야 할 때도 메모리에는 크기 k인 힙만 두면 된다. 같은 기법을 쓰는 문제가 [Kth Largest Element in an Array](/posts/leetcode-kth-largest-element-in-an-array)다.

## 빈도를 칸 번호로 쓰는 버킷

이 문제에서 가장 좋은 풀이는 빈도의 범위를 이용한다. 어떤 값이든 나온 횟수는 1 이상 n 이하다. 그러니 길이 n + 1인 배열을 만들어 `buckets[f]`에 "정확히 f번 나온 값들"을 담을 수 있다. 횟수가 곧 칸 번호라 정렬이 필요 없다. 그다음 큰 칸부터 거꾸로 훑으며 k개를 모은다.

```js
function topKFrequent(nums, k) {
  // 1) 센다
  const count = new Map();
  for (const x of nums) count.set(x, (count.get(x) ?? 0) + 1);

  // 2) 빈도를 칸 번호로 삼아 나눠 담는다. 빈도는 1..n이라 n + 1칸이면 된다.
  const buckets = Array.from({ length: nums.length + 1 }, () => []);
  for (const [v, c] of count) buckets[c].push(v);

  // 3) 큰 칸부터 내려오며 k개를 모은다
  const res = [];
  for (let f = nums.length; f >= 1 && res.length < k; f--) {
    for (const v of buckets[f]) {
      res.push(v);
      if (res.length === k) break;
    }
  }
  return res;
}

console.log(topKFrequent([4, 1, 4, 6, 1, 4, 2, 1, 4], 2));
```

시간을 따져 보자. 세기 O(n), 바구니 만들기 O(n)(칸 n + 1개), 나눠 담기 O(m), 훑기는 칸 n개를 지나며 값을 최대 m개 꺼내니 O(n + m)이다. 합쳐서 O(n)이다. 공간은 장부 O(m)과 바구니 O(n)이다.

이게 O(n log n)보다 빠를 수 있는 이유는 비교로 순서를 정하지 않기 때문이다. 비교 기반 정렬은 O(n log n)보다 빠를 수 없다는 하한이 있지만, 값의 범위가 n 이하로 정해져 있으면 그 값을 칸 번호로 써서 비교 없이 나눌 수 있다. 계수 정렬, 버킷 정렬과 같은 원리다.

한 가지 손볼 데가 있다. 바구니를 n + 1칸 만들면 n이 10만일 때 빈 배열 10만 개를 만든다. 가장 큰 빈도까지만 만들면 이 비용이 준다. 세면서 최대 빈도를 기록해 두고 `buckets`를 그 길이로 만들면 측정에서 15ms가 7~9ms로 줄었다.

## 퀵셀렉트로 경계만 찾기

정렬 없이 "상위 k개"를 고르는 또 다른 방법은 퀵셀렉트다. 퀵 정렬처럼 기준(피벗)을 하나 골라 빈도가 작은 쌍은 왼쪽, 큰 쌍은 오른쪽으로 나눈다. 기준이 끝난 자리가 정확히 m - k라면 그 오른쪽이 상위 k개다. 아니면 경계가 있는 한쪽만 다시 나눈다. 퀵 정렬은 양쪽을 다 정렬하지만, 퀵셀렉트는 한쪽만 들어가서 평균 O(m)이다.

```js
function topKFrequent(nums, k) {
  const count = new Map();
  for (const x of nums) count.set(x, (count.get(x) ?? 0) + 1);
  const items = [...count.entries()]; // [값, 횟수]
  const target = items.length - k;    // 이 자리부터 끝까지가 상위 k개
  let lo = 0, hi = items.length - 1;
  while (lo < hi) {
    const pi = lo + Math.floor(Math.random() * (hi - lo + 1)); // 무작위 피벗
    [items[pi], items[hi]] = [items[hi], items[pi]];
    const pivot = items[hi][1];
    let store = lo;
    for (let i = lo; i < hi; i++) {
      if (items[i][1] < pivot) { [items[i], items[store]] = [items[store], items[i]]; store++; }
    }
    [items[store], items[hi]] = [items[hi], items[store]]; // 피벗이 제자리로
    if (store === target) break;
    if (store < target) lo = store + 1; // 경계는 오른쪽에 있다
    else hi = store - 1;                // 경계는 왼쪽에 있다
  }
  return items.slice(target).map(([v]) => v);
}

console.log(topKFrequent([4, 1, 4, 6, 1, 4, 2, 1, 4], 2).sort((a, b) => a - b));
```

```text
[ 1, 4 ]
```

시간은 평균 O(n + m)이다. 매번 범위가 평균 절반쯤으로 줄어 m + m/2 + m/4 + … = O(m)이다. 하지만 피벗이 계속 최악으로 고르면 범위가 하나씩만 줄어 O(m²)가 된다. 피벗을 무작위로 고르는 이유가 그 최악을 특정 입력이 일부러 만들지 못하게 하기 위해서다. 공간은 쌍 배열 O(m)이고 재귀 대신 반복문이라 스택은 쓰지 않는다.

버킷이 같은 O(n)을 최악에도 보장하니 이 문제에서 퀵셀렉트를 고를 이유는 크지 않다. 다만 빈도가 아니라 실수 점수처럼 범위가 정해지지 않은 기준으로 상위 k개를 고를 때는 버킷을 쓸 수 없어서 퀵셀렉트나 힙이 남는다. 그래서 둘 다 알아 둔다.

## Python과 Java로 옮기기

```python
import heapq
from collections import Counter
from typing import List

class Solution:
    def topKFrequent(self, nums: List[int], k: int) -> List[int]:
        count = Counter(nums)
        buckets = [[] for _ in range(len(nums) + 1)]  # buckets[f] = f번 나온 값들
        for v, c in count.items():
            buckets[c].append(v)
        res = []
        for f in range(len(nums), 0, -1):
            for v in buckets[f]:
                res.append(v)
                if len(res) == k:
                    return res
        return res

    def topKFrequentHeap(self, nums: List[int], k: int) -> List[int]:
        count = Counter(nums)
        return heapq.nlargest(k, count.keys(), key=count.get)  # 내부에서 크기 k 힙을 쓴다

    def topKFrequentCounter(self, nums: List[int], k: int) -> List[int]:
        return [v for v, _ in Counter(nums).most_common(k)]

s = Solution()
nums = [4, 1, 4, 6, 1, 4, 2, 1, 4]
print(s.topKFrequent(nums, 2), s.topKFrequentHeap(nums, 2), s.topKFrequentCounter(nums, 2))
print(s.topKFrequent([7], 1), s.topKFrequent([-5, -5, 0, 0, 0, 9], 2))
```

```text
[4, 1] [4, 1] [4, 1]
[7] [0, -5]
```

`[[]] * (n + 1)`로 바구니를 만들면 같은 리스트 하나를 n + 1번 가리키게 되어, 한 바구니에 넣은 값이 모든 바구니에 보인다. 리스트 컴프리헨션으로 바구니마다 새 리스트를 만든다. Python의 `heapq`는 최소 힙만 제공하는데, `nlargest(k, …, key=…)`가 내부에서 크기 k 힙으로 상위 k개를 골라 준다. `Counter.most_common(k)`도 k가 주어지면 같은 방식을 쓴다. 코딩 테스트에서는 `most_common`이 가장 짧은 답이다. 다만 면접에서 이걸 쓰면 내부에서 무엇을 하는지, 버킷으로 O(n)을 만들 수 있는지를 이어서 묻는다.

```java
import java.util.*;

class Solution {
    public int[] topKFrequent(int[] nums, int k) {
        Map<Integer, Integer> count = new HashMap<>();
        for (int x : nums) count.merge(x, 1, Integer::sum);

        @SuppressWarnings("unchecked")
        List<Integer>[] buckets = new List[nums.length + 1]; // 제네릭 배열은 바로 못 만들어 경고를 끈다
        for (Map.Entry<Integer, Integer> e : count.entrySet()) {
            int f = e.getValue();
            if (buckets[f] == null) buckets[f] = new ArrayList<>();
            buckets[f].add(e.getKey());
        }
        int[] res = new int[k];
        int idx = 0;
        for (int f = nums.length; f >= 1 && idx < k; f--) {
            if (buckets[f] == null) continue;
            for (int v : buckets[f]) {
                res[idx++] = v;
                if (idx == k) break;
            }
        }
        return res;
    }

    public int[] topKFrequentHeap(int[] nums, int k) {
        Map<Integer, Integer> count = new HashMap<>();
        for (int x : nums) count.merge(x, 1, Integer::sum);
        // 빈도가 작은 것이 위로 오는 최소 힙. 비교자에서 뺄셈 대신 Integer.compare를 쓴다
        PriorityQueue<Integer> heap = new PriorityQueue<>((a, b) -> Integer.compare(count.get(a), count.get(b)));
        for (int v : count.keySet()) {
            heap.offer(v);
            if (heap.size() > k) heap.poll(); // 가장 덜 나온 값을 버린다
        }
        int[] res = new int[k];
        for (int i = k - 1; i >= 0; i--) res[i] = heap.poll();
        return res;
    }
}
```

```text
[4, 1] [4, 1]
[0, -5] [7]
```

`main`에서 버킷과 힙 풀이에 예시 배열(k = 2)을 넣고, `[-5, -5, 0, 0, 0, 9]`(k = 2)와 `[7]`(k = 1)을 넣은 결과다.

Java에서는 `List<Integer>[]` 같은 제네릭 배열을 `new List<Integer>[n]`으로 만들 수 없다. 그래서 원시 타입 `new List[n]`으로 만들고 경고를 끈다. 바구니를 `List<List<Integer>>`로 만들어도 된다. `count.merge(x, 1, Integer::sum)`은 없으면 1을 넣고 있으면 더하는 한 줄 세기다.

`PriorityQueue`는 기본이 최소 힙이다. 비교자를 `(a, b) -> count.get(a) - count.get(b)`처럼 뺄셈으로 쓰는 코드가 흔한데, 빈도는 작아서 괜찮지만 값 자체를 비교할 때 큰 양수와 큰 음수를 빼면 `int`가 넘쳐 부호가 뒤집힌다. 버릇처럼 `Integer.compare`를 쓴다. 힙에서 꺼내면 작은 것부터 나오니 결과 배열을 뒤에서부터 채워 많이 나온 순서로 맞췄다.

## 동점, 음수, k가 전부일 때

### 값이 음수거나 0일 때

`[-5, -5, 0, 0, 0, 9]`, k = 2면 답은 `[0, -5]`다. 장부는 값을 키로 쓰니 부호와 상관없다. 버킷의 칸 번호는 값이 아니라 빈도라서 음수가 칸 번호가 될 일도 없다. 처음 버킷 풀이를 보면 "값을 칸 번호로 쓰나?"로 오해해 음수를 걱정하는데, 칸 번호는 언제나 1 이상 n 이하인 횟수다.

### k가 서로 다른 값의 개수와 같을 때

`[1, 2, 3]`, k = 3이면 모두를 돌려준다. 버킷은 1번 칸까지 내려가 세 값을 다 꺼낸다. 퀵셀렉트는 `target`이 0이라 반복이 바로 끝나고 전부를 자른다. 힙은 아무것도 버리지 않는다. 모두 맞는다.

### 바구니 안에서 멈추지 않을 때

버킷 풀이의 안쪽 반복에서 `if (res.length === k) break`를 빼면, 마지막으로 들른 바구니의 값을 전부 쏟는다. 재미있게도 이 문제의 약속 아래에서는 그래도 답이 맞는다. 마지막 바구니에 필요한 것보다 많은 값이 있다면 k번째와 k+1번째가 같은 빈도라는 뜻이고, 그런 입력은 들어오지 않기 때문이다. 하지만 약속이 없는 입력에서는 바로 틀린다.

```js
// 안쪽 break가 없는 버킷 풀이에 동점 입력을 넣으면
console.log(topKFrequentNoBreak([1, 1, 2, 2, 3], 1));
```

```text
[ 1, 2 ]
```

k = 1인데 두 개가 나왔다. 바깥 반복의 `res.length < k`는 바구니 하나를 다 쏟은 뒤에야 검사되기 때문이다. 문제의 약속에 기대는 코드는 같은 함수를 다른 곳에 가져다 쓸 때 깨진다. 안쪽 `break`를 두는 쪽이 안전하다.

### 동점이 답의 경계에 걸리면

이 문제는 답이 하나라고 약속해서 k번째와 k+1번째가 같은 빈도인 입력이 없다. 하지만 측정에 쓴 무작위 데이터에서는 그런 동점이 생겨서, 힙 풀이와 퀵셀렉트가 서로 다른 값을 골랐다. 둘 다 "상위 k개"로는 맞다. 실무에서 동점을 어떻게 끊을지(값이 작은 쪽? 먼저 나온 쪽?)는 따로 정해야 하고, 정하지 않으면 실행할 때마다 결과가 달라질 수 있다.

### Python 바구니를 곱셈으로 만들 때

앞에서 본 `[[]] * (n + 1)`이다. 모든 칸이 같은 리스트라 한 바구니에 넣은 값이 모든 칸에 보이고, 결과에 같은 값이 여러 번 나온다.

## 데이터가 끝없이 들어온다면

### 결과를 빈도순으로 정렬해 달라면

버킷은 큰 칸부터 꺼내니 이미 빈도 내림차순이다. 힙은 꺼낼 때 작은 것부터 나오니 뒤집어야 하고, 퀵셀렉트는 상위 k개를 골랐을 뿐 그 안의 순서는 정하지 않아서 k개를 따로 정렬한다(O(k log k)).

### 같은 빈도면 사전 순으로 고르라면

LeetCode 692. Top K Frequent Words는 단어 버전인데, 빈도가 같으면 사전 순으로 앞선 단어를 먼저 고르라는 규칙이 붙는다. 정렬 풀이라면 비교 함수에 두 번째 기준을 넣는다.

```js
function topKFrequentWords(words, k) {
  const count = new Map();
  for (const w of words) count.set(w, (count.get(w) ?? 0) + 1);
  return [...count.keys()]
    .sort((a, b) => count.get(b) - count.get(a) || (a < b ? -1 : a > b ? 1 : 0)) // 빈도 내림, 같으면 사전 순
    .slice(0, k);
}
console.log(topKFrequentWords(["map", "set", "heap", "set", "map", "list", "heap"], 2));
```

```text
[ 'heap', 'map' ]
```

heap, map, set이 모두 두 번이라 사전 순으로 앞선 heap과 map이 남았다. 힙으로 풀면 비교자가 까다로워진다. 최소 힙의 맨 위는 "버릴 후보"여야 하니, 빈도가 작은 것이 위로, 빈도가 같으면 사전 순으로 뒤인 것이 위로 오게 뒤집어 써야 한다. 이 뒤집기를 헷갈려서 틀리는 경우가 많다.

### 스트림에서 실시간으로 상위 k개를 보여 달라면

값이 계속 들어오고 언제든 상위 k개를 물을 수 있다면, 장부(값 → 횟수)를 계속 고치고 상위 k개는 물을 때마다 힙으로 뽑는 것이 가장 단순하다. 질문이 아주 잦으면 빈도별 값 목록을 연결 리스트로 들고 다니며 횟수가 오를 때 한 칸씩 옮기는 구조(LFU 캐시와 같은 모양)로 값마다 O(1)에 갱신한다.

값 종류가 너무 많아 장부를 다 들고 있을 수 없으면 근사 알고리즘으로 간다. Misra-Gries 알고리즘은 카운터를 k - 1개만 두고, 새 값이 왔는데 자리가 없으면 모든 카운터를 1씩 줄인다. 전체의 1/k보다 자주 나온 값은 반드시 카운터에 남는다는 보장이 있다.

```js
function misraGries(stream, k) {
  const c = new Map(); // 최대 k - 1개의 후보와 줄어든 횟수
  for (const x of stream) {
    if (c.has(x)) c.set(x, c.get(x) + 1);
    else if (c.size < k - 1) c.set(x, 1);
    else for (const [v, n] of c) n === 1 ? c.delete(v) : c.set(v, n - 1); // 모두 하나씩 줄인다
  }
  return c;
}
console.log(misraGries([4, 1, 4, 6, 1, 4, 2, 1, 4], 3));
```

```text
Map(2) { 4 => 2, 1 => 1 }
```

9개 중 1/3인 3번보다 많이 나온 4는 반드시 남는다. 남은 횟수는 실제보다 작을 수 있어서, 정확한 횟수가 필요하면 후보만 놓고 한 번 더 센다. 횟수 추정만 필요하면 Count-Min Sketch라는 구조도 쓴다.

### 여러 서버에 나뉜 로그에서 구하라면

서버마다 상위 k개만 보내서 합치면 틀린다. 서버 A에서는 11등, 서버 B에서도 11등인 값이 합치면 1등일 수 있다. 정확히 구하려면 각 서버가 (값, 횟수)를 값의 해시로 나눠 보내 같은 값이 한 곳에 모이게 한 뒤, 거기서 횟수를 합치고 상위 k개를 고른다. [Group Anagrams](/posts/leetcode-group-anagrams#면접관이-조건을-바꾸면)에서 본 "같은 키는 같은 곳으로" 원리와 같다.

## 면접에서 나올 만한 질문

### O(n log n)보다 빠르게 풀 수 있나요?

빈도 버킷으로 O(n)에 풀 수 있다. 빈도는 1 이상 n 이하라서 빈도를 배열 칸 번호로 쓰면 비교 정렬 없이 값을 나눌 수 있다. 그다음 큰 칸부터 거꾸로 훑어 k개를 모은다. 비교 기반 정렬의 O(n log n) 하한은 값을 비교로만 다룰 때의 이야기라 여기에는 적용되지 않는다.

### 최대 힙이 아니라 최소 힙을 쓰는 이유는요?

힙에 상위 k개만 남기려면 매번 "상위 k개 중 꼴찌"를 알아야 하기 때문이다. 최소 힙의 맨 위가 바로 그 꼴찌라서, 크기가 k를 넘으면 맨 위를 버리면 된다. 그래서 힙 크기가 k로 유지되고 연산 비용이 O(log k)다. 최대 힙에 전부 넣고 k번 꺼내는 방법도 맞지만 O(m + k log m)이고 메모리를 m만큼 쓴다.

### 힙 풀이와 버킷 풀이 중 무엇을 고르나요?

이 문제처럼 기준이 정수 빈도이고 범위가 n 이하면 버킷이 최악에도 O(n)이라 좋다. 데이터가 흘러 들어오거나, 기준이 실수 점수처럼 범위가 없거나, k가 작고 메모리를 아껴야 하면 힙을 고른다. 힙은 O(k) 공간만 들고 다니면 되지만, 버킷은 빈도 범위만큼의 칸이 필요하다.

### 퀵셀렉트의 시간 복잡도는요?

평균 O(m)이고 최악 O(m²)다. 피벗이 범위를 평균 절반으로 줄이면 m + m/2 + … = 2m이지만, 계속 끝값을 피벗으로 고르면 하나씩만 줄어든다. 무작위 피벗으로 특정 입력이 최악을 만들지 못하게 한다. 최악을 보장하려면 중앙값의 중앙값 기법으로 O(m)을 지킬 수 있지만 상수가 커서 실무에서는 잘 쓰지 않는다.

### 세는 단계를 더 빠르게 할 수 있나요?

값 범위가 좁으면 해시맵 대신 배열로 센다. 이 문제는 값이 -10^4 이상 10^4 이하라 길이 20001인 배열에 `x + 10000` 칸으로 세면 해시 계산이 사라진다. 10만 개에서 `Map`의 6.4ms가 배열로 1.4ms가 됐다. 측정해 보면 고르는 단계보다 세는 단계가 대부분의 시간을 쓰니, 성능을 올리려면 여기부터 고친다.

### 여러 서버의 로그에서 상위 k개를 구하려면요?

서버마다 상위 k개만 모아 합치면 틀린다. 각 서버에서 중간 등수인 값이 합치면 1등일 수 있기 때문이다. 같은 값이 한 곳에 모이도록 값의 해시로 나눠 보내 횟수를 합친 뒤 상위 k개를 고른다. 정확도를 조금 포기해도 되면 Misra-Gries나 Count-Min Sketch 같은 근사 구조로 메모리를 크게 줄인다.
