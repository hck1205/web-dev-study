</EasyIntro>

차트에 ConfigMap 템플릿 하나를 추가하고 `helm install`을 했더니 이런 오류가 났다.

```text
Error: YAML parse error on shop-api/templates/configmap.yaml: error converting YAML to JSON: yaml: line 6: did not find expected key
```

6번째 줄을 열어 보면 아무 문제가 없어 보인다. 템플릿 파일의 6번째 줄은 `{{ include ... }}` 한 줄인데, 오류가 말하는 6번째 줄은 템플릿이 아니라 렌더링이 끝난 결과물의 6번째 줄이기 때문이다. Helm 템플릿에서 생기는 오류 대부분은 이 차이에서 온다. 우리가 쓰는 건 텍스트를 만들어 내는 프로그램이고, YAML은 그 프로그램이 출력한 결과다.

이 글은 [Helm 기본 글](/posts/helm-basics)에서 만든 `shop-api` 차트를 들고 템플릿 문법을 읽는다. 값을 꺼내는 법, 공백과 들여쓰기를 다루는 법, 조건과 반복, 공용 조각을 만드는 `_helpers.tpl`, 그리고 오류가 났을 때 결과물을 직접 보는 법까지 간다. 출력은 Helm 3.16에서 실제로 받은 것이다.

## 템플릿은 YAML이 아니라 텍스트를 찍는다

Helm 템플릿은 Go 언어의 표준 템플릿 엔진(`text/template`) 위에 Sprig라는 함수 모음을 얹은 것이다. 이름에 `text`가 붙은 데서 알 수 있듯 이 엔진은 YAML을 모른다. `{{ }}` 밖의 글자는 그대로 내보내고, `{{ }}` 안의 식은 계산해서 그 자리에 글자로 끼워 넣을 뿐이다. 들여쓰기가 맞는지, 키가 중복되는지, 값이 문자열인지 숫자인지는 렌더링이 끝난 뒤 YAML 파서가 처음 보게 된다.

그래서 템플릿을 쓸 때는 머릿속에서 두 단계를 나눠야 한다. 먼저 템플릿 엔진이 어떤 텍스트를 만들지, 그다음 그 텍스트가 올바른 YAML인지. 렌더링 결과는 언제든 클러스터 없이 볼 수 있다.

```bash
# 클러스터에 보내지 않고 렌더링 결과만 출력한다
helm template shop-api ./shop-api

# 파일 하나만 본다
helm template shop-api ./shop-api -s templates/deployment.yaml

# 값을 바꿔서 본다
helm template shop-api ./shop-api -f values-prod.yaml --set replicaCount=3
```

`helm create`가 만든 Deployment 템플릿의 앞부분과, 그걸 렌더링한 결과를 나란히 보자.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "shop-api.fullname" . }}
  labels:
    {{- include "shop-api.labels" . | nindent 4 }}
spec:
  {{- if not .Values.autoscaling.enabled }}
  replicas: {{ .Values.replicaCount }}
  {{- end }}
```

```text
---
# Source: shop-api/templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-api
  labels:
    helm.sh/chart: shop-api-0.1.0
    app.kubernetes.io/name: shop-api
    app.kubernetes.io/instance: shop-api
    app.kubernetes.io/version: "1.16.0"
    app.kubernetes.io/managed-by: Helm
spec:
  replicas: 1
```

한 줄짜리 `include`가 다섯 줄 라벨이 됐고, `if`가 있던 줄은 흔적 없이 사라졌다. 이 두 가지가 어떻게 일어나는지가 이 글의 대부분이다.

## 점 하나가 가리키는 것

`.Values`는 `values.yaml` 기본값에 `-f`와 `--set`을 덮어 합친 최종 값이다. `.Release`에는 릴리스 이름(`.Release.Name`), 네임스페이스(`.Release.Namespace`), 리비전 번호, 설치인지 업그레이드인지(`.Release.IsInstall`, `.Release.IsUpgrade`)가 있다. `.Chart`는 `Chart.yaml`의 내용인데, 필드 이름이 대문자로 시작한다는 점이 다르다(`.Chart.Name`, `.Chart.Version`, `.Chart.AppVersion`). `.Capabilities`는 대상 클러스터의 버전과 지원하는 API 목록이라서 `{{ if .Capabilities.APIVersions.Has "policy/v1" }}`처럼 클러스터에 따라 다른 리소스를 만들 때 쓴다. `.Files.Get "conf/app.properties"`는 차트 안의 일반 파일을 읽어 온다.

값 키에 하이픈이 들어가면 점으로 이어 쓸 수 없다. `.Values.my-key`는 템플릿 엔진이 빼기로 읽어서 오류가 난다. 이럴 때는 `{{ index .Values "my-key" }}`로 꺼낸다. 처음부터 values 키는 camelCase로 짓는 게 Helm 쪽 관례다.

여기서 `{{-`와 `nindent`가 짝이라는 게 핵심이다. 왼쪽을 깨끗이 지운 다음, 줄바꿈과 들여쓰기를 함수로 정확히 다시 만든다. 템플릿 파일에서 이 줄을 몇 칸 들여 썼는지는 결과에 아무 영향이 없다. 들여쓰기는 오직 `nindent` 뒤의 숫자가 정한다. 그래서 숫자는 부모 키(`labels:`)의 들여쓰기에 2를 더한 값이어야 한다. `metadata.labels`는 4, `spec.template.metadata.labels`는 8, 컨테이너의 `resources`는 12다.

## 공백을 지우는 하이픈

`{{-`는 왼쪽, `-}}`는 오른쪽의 공백을 지운다. 여기서 공백은 스페이스, 탭, 줄바꿈을 모두 포함한다. 하이픈과 괄호 사이에 공백이 하나 있어야 한다는 것도 규칙이다. `{{-3}}`은 "-3을 출력하라"로 읽힌다.

`if`, `end`, `range` 같은 제어문 줄에 `{{-`를 붙이는 이유도 같다. 제어문 자체는 아무것도 출력하지 않지만, 그 줄의 들여쓰기와 줄바꿈은 출력된다. 하이픈 없이 쓰면 결과에 빈 줄이 남는다. YAML에서 빈 줄은 대개 해가 없지만, 여러 줄이 쌓이면 결과를 읽기 어렵다. 앞의 Deployment에서 `{{- if ... }}` 줄과 `{{- end }}` 줄이 결과에 흔적도 없던 이유가 이것이다.

문제는 하이픈을 반대쪽에 잘못 붙일 때다. 이름 뒤에 습관처럼 `-}}`를 붙여 보자.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ include "shop-api.fullname" . -}}
  labels:
    {{- include "shop-api.labels" . | nindent 4 }}
data:
  LOG_LEVEL: info
```

```text
Error: YAML parse error on shop-api/templates/configmap.yaml: error converting YAML to JSON: yaml: line 4: mapping values are not allowed in this context
```

오류 메시지만으로는 무엇이 잘못됐는지 알 수 없다. `--debug`를 붙이면 Helm이 파싱에 실패한 결과물을 그대로 보여 준다.

```bash
# 오류가 나도 렌더링된 텍스트를 출력하게 한다
helm template shop-api ./shop-api -s templates/configmap.yaml --debug
```

```text
---
# Source: shop-api/templates/configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: shop-apilabels:
    helm.sh/chart: shop-api-0.1.0
    app.kubernetes.io/name: shop-api
```

`-}}`가 뒤의 줄바꿈과 다음 줄의 들여쓰기를 모두 먹어서 `name: shop-apilabels:`가 됐다. 한 줄에 콜론이 두 번 나오니 YAML 파서가 "이 위치에 매핑이 올 수 없다"고 한 것이다. 오류의 "line 4"는 `# Source` 다음부터 센 결과물의 4번째 줄이다.

## 들여쓰기가 어긋날 때 나는 오류

이번에는 반대로 `{{-` 없이 `indent`를 쓴 경우다. 처음 이 글을 시작한 오류가 이것이다.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ include "shop-api.fullname" . }}
  labels:
    {{ include "shop-api.labels" . | indent 4 }}
data:
  LOG_LEVEL: info
```

```text
Error: YAML parse error on shop-api/templates/configmap.yaml: error converting YAML to JSON: yaml: line 6: did not find expected key
```

```text
metadata:
  name: shop-api
  labels:
        helm.sh/chart: shop-api-0.1.0
    app.kubernetes.io/name: shop-api
    app.kubernetes.io/instance: shop-api
```

첫 줄만 여덟 칸이다. 템플릿 파일에 이미 네 칸이 있었고, `indent 4`가 첫 줄 앞에 또 네 칸을 붙였다. 둘째 줄부터는 `indent`가 붙인 네 칸뿐이다. YAML 파서는 여덟 칸짜리 줄 다음에 네 칸짜리 줄이 오자 길을 잃는다. `indent`를 쓰려면 템플릿 파일의 그 줄을 들여쓰지 말아야 하는데, 그러면 파일이 읽기 어려워진다. 그래서 `{{-`와 `nindent` 조합이 표준처럼 쓰인다.

`helm lint`도 같은 오류를 잡는다. CI에 넣어 두면 머지 전에 걸러진다.

```bash
# 차트 구조와 템플릿 렌더링을 검사한다
helm lint ./shop-api
```

```text
==> Linting ./shop-api
[INFO] Chart.yaml: icon is recommended
[ERROR] templates/configmap.yaml: unable to parse YAML: error converting YAML to JSON: yaml: line 6: did not find expected key

Error: 1 chart(s) linted, 1 chart(s) failed
```

더 고약한 건 `nindent` 숫자를 틀리는 경우다. `nindent 2`를 주면 라벨이 `labels:`와 같은 깊이에 놓인다. YAML 파서 입장에서는 `labels:`가 빈 값이고 라벨들은 `metadata`의 형제 키다. YAML로는 올바르니 lint도 렌더링도 통과하고, 설치하면 경고만 찍힌다.

```text

W1018 23:37:24.257693   12213 warnings.go:70] unknown field "metadata.app.kubernetes.io/managed-by"
W1018 23:37:24.257696   12213 warnings.go:70] unknown field "metadata.app.kubernetes.io/name"
W1018 23:37:24.257698   12213 warnings.go:70] unknown field "metadata.app.kubernetes.io/version"
```

```bash
# 만들어진 ConfigMap의 라벨을 본다
kubectl get cm shop-api -n tpl --show-labels
```

```text

```

API 서버는 모르는 필드를 버리고 리소스를 만든다. 라벨은 Helm이 따로 붙이는 `managed-by` 하나만 남았다. 같은 실수가 Pod 템플릿 라벨에서 일어나면 Service의 selector가 Pod를 못 찾아 엔드포인트가 비는 식으로 한참 뒤에 터진다. 오류가 안 나는 실수가 더 위험하다. 설치 로그에 `unknown field` 경고가 보이면 그냥 넘기지 않는다.

## 조각을 만드는 define, 가져다 쓰는 include

`_helpers.tpl`을 열면 `define`으로 이름 붙인 조각이 줄지어 있다. 밑줄로 시작하는 파일은 매니페스트로 렌더링되지 않고, 다른 템플릿이 가져다 쓸 조각만 정의한다는 약속이다.

```yaml
{{/* 셀렉터에 쓰는 라벨. 한 번 배포하면 바꾸면 안 된다 */}}
{{- define "shop-api.selectorLabels" -}}
app.kubernetes.io/name: {{ include "shop-api.name" . }}
app.kubernetes.io/instance: {{ .Release.Name }}
{{- end }}

{{/* 모든 리소스에 붙이는 라벨 */}}
{{- define "shop-api.labels" -}}
helm.sh/chart: {{ include "shop-api.chart" . }}
{{ include "shop-api.selectorLabels" . }}
{{- if .Chart.AppVersion }}
app.kubernetes.io/version: {{ .Chart.AppVersion | quote }}
{{- end }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
{{- end }}
```

조각을 부르는 방법은 두 가지다. `template`과 `include`. 둘 다 조각을 실행하지만 `template`은 결과를 그 자리에 바로 쓰고 끝나는 동작(action)이고, `include`는 결과를 문자열로 돌려주는 함수다. 차이는 파이프를 붙여 보면 드러난다.

```yaml
  labels:
    {{- template "shop-api.labels" . | nindent 4 }}
```

```text
Error: template: shop-api/templates/configmap.yaml:6:47: executing "shop-api/templates/configmap.yaml" at <4>: wrong type for value; expected string; got chartutil.Values
```

`template "이름" . | nindent 4`에서 파이프는 `template`의 결과에 걸리지 않는다. 템플릿 엔진은 이걸 "`. | nindent 4`의 결과를 조각에 넘겨라"로 읽는다. 그러면 `nindent`가 들여쓸 문자열 자리에 최상위 객체(`chartutil.Values`)를 받게 되고, 문자열이 아니라는 오류가 난다. 결과를 가공해야 하는 곳에서는 `include`를 쓴다. 실무 차트에서 `template`을 볼 일은 거의 없다.

`define` 안의 점은 부르는 쪽이 넘긴 값이다. `include "shop-api.labels" .`처럼 최상위를 넘기면 조각 안에서 `.Release.Name`을 쓸 수 있고, `include "shop-api.labels" .Values`처럼 넘기면 조각 안의 `.Release`는 없다. 여러 값을 넘기고 싶으면 `dict`로 묶는다. `include "shop-api.env" (dict "root" $ "container" .Values.worker)` 같은 식이다.

하나 더, selectorLabels 조각에 버전처럼 바뀌는 값을 넣으면 안 된다. Deployment의 `spec.selector`는 만든 뒤 바꿀 수 없는 필드라서, 업그레이드 때 셀렉터가 달라지면 업그레이드가 실패한다. 이 오류는 [업그레이드와 롤백 글](/posts/helm-release-lifecycle)에서 다시 본다.

## 값이 없을 때, 값이 틀린 타입일 때

값을 꺼낼 때 생기는 문제는 크게 셋이다. 값이 아예 없거나, 기본값이 의도와 다르게 들어가거나, 타입이 틀린 경우다.

먼저 없는 값. `.Values.database.host`를 쓰는데 values에 `database`가 아예 없으면 이렇게 된다.

```yaml
data:
  DB_HOST: {{ .Values.database.host }}
```

```text
Error: template: shop-api/templates/configmap.yaml:6:21: executing "shop-api/templates/configmap.yaml" at <.Values.database.host>: nil pointer evaluating interface {}.host
```

`database`가 없으니 nil이고, nil에서 `host`를 꺼내려다 멈췄다. 반드시 있어야 하는 값이라면 이 애매한 오류 대신 `required`로 사람이 읽을 메시지를 준다. 중간 키까지 없을 수 있는 값은 `dig`로 안전하게 꺼낸다. 이때 `.Values`가 아니라 `.Values.AsMap`을 넘겨야 한다는 점이 함정이다. `.Values`를 그대로 넘기면 `interface conversion: interface {} is chartutil.Values, not map[string]interface {}` 오류가 난다.

```yaml
data:
  DB_HOST: {{ required "database.host를 넣어야 한다" (dig "database" "host" "" .Values.AsMap) | quote }}
  DB_PORT: {{ (.Values.database | default dict).port | default 5432 | quote }}
  LOG_LEVEL: {{ .Values.logLevel | default "info" | quote }}
```

```bash
# 값을 빼고 렌더링하면 required가 멈춘다
helm template shop-api ./shop-api -s templates/configmap.yaml

# 값을 넣으면 통과한다
helm template shop-api ./shop-api -s templates/configmap.yaml --set database.host=pg.shop.svc
```

```text
Error: execution error at (shop-api/templates/configmap.yaml:6:14): database.host를 넣어야 한다
```

```text
data:
  DB_HOST: "pg.shop.svc"
  DB_PORT: "5432"
  LOG_LEVEL: "info"
```

다음은 `default`의 함정이다. `default`는 값이 "비어 있으면" 기본값을 쓰는데, 여기서 비어 있다는 건 nil만이 아니라 `false`, `0`, 빈 문자열, 빈 목록까지 포함한다. 그래서 불리언 기본값을 `true`로 두면 사용자가 `false`를 줘도 `true`가 된다.

```yaml
data:
  CACHE_ENABLED: {{ .Values.cacheEnabled | default true | quote }}
```

```bash
# 끄려고 false를 넣었다
helm template shop-api ./shop-api -s templates/configmap.yaml --set cacheEnabled=false
```

```text
data:
  CACHE_ENABLED: "true"
```

꺼지지 않는다. 불리언과 숫자 0처럼 "비어 있는 값"이 의미 있는 값일 때는 템플릿에서 `default`를 쓰지 말고 `values.yaml`에 기본값을 적어 둔다. 사용자가 덮어쓰면 그 값이 그대로 들어온다.

마지막은 타입이다. ConfigMap의 `data`는 문자열만 받는다. 그런데 YAML에서 `8080`은 숫자, `false`는 불리언이다.

```yaml
data:
  PORT: {{ .Values.port }}
  CACHE_ENABLED: {{ .Values.cacheEnabled }}
```

```bash
# lint는 통과한다
helm lint ./shop-api --set port=8080 --set cacheEnabled=false

# 설치하면 API 서버가 거절한다
helm install shop-api ./shop-api -n tpl --set port=8080 --set cacheEnabled=false
```

```text
==> Linting ./shop-api
[INFO] Chart.yaml: icon is recommended

1 chart(s) linted, 0 chart(s) failed
```

```text
Error: INSTALLATION FAILED: 1 error occurred:
	* ConfigMap in version "v1" cannot be handled as a ConfigMap: json: cannot unmarshal bool into Go struct field ConfigMap.data of type string
```

`helm lint`는 YAML 문법까지만 보고 쿠버네티스 스키마는 모른다. 타입 오류는 API 서버에 가서야 드러난다. 문자열이어야 하는 자리(ConfigMap 값, 환경 변수 `value`, 어노테이션 값)에는 습관처럼 `| quote`를 붙인다. `"1.16.0"`처럼 숫자로 보이는 버전 문자열도 마찬가지다.

## 조건과 반복, 그리고 바뀌는 점

`if`는 값이 비어 있지 않으면 안쪽을 출력한다. 비어 있다의 기준은 `default`와 같다. `with`는 `if`와 비슷하지만 안쪽에서 점을 그 값으로 바꾼다. `range`는 목록이나 맵을 돌면서 점을 각 원소로 바꾼다.

```yaml
data:
  {{- with .Values.database }}
  DB_URL: {{ printf "postgres://%s:%v/%s" .host .port $.Release.Name | quote }}
  {{- end }}
  {{- range $key, $value := .Values.env }}
  {{ $key }}: {{ $value | quote }}
  {{- end }}
```

```yaml
# values-dev.yaml
database:
  host: pg.shop.svc
  port: 5432
env:
  TZ: Asia/Seoul
  MAX_CONN: 20
```

```text
data:
  DB_URL: "postgres://pg.shop.svc:5432/shop-api"
  MAX_CONN: "20"
  TZ: "Asia/Seoul"
```

`with` 안에서 `.host`는 `.Values.database.host`다. 그 안에서 릴리스 이름이 필요하면 `.Release.Name`으로는 안 된다. 점이 이미 `database`로 바뀌었기 때문이다. 이때 쓰는 게 `$`다. `$`는 템플릿이 시작할 때의 최상위 객체를 끝까지 기억한다.

맵을 `range`로 돌면 키의 알파벳 순서로 나온다. values에는 TZ를 먼저 적었지만 결과는 MAX_CONN이 먼저다. 순서가 의미 있는 목록(컨테이너 `args` 같은)은 맵이 아니라 리스트로 받아야 한다.

`$`를 잊으면 이런 오류를 본다.

```yaml
data:
  {{- range .Values.hosts }}
  HOST_{{ . | upper | replace "." "_" }}: {{ .Release.Name }}
  {{- end }}
```

```text
Error: template: shop-api/templates/configmap.yaml:7:53: executing "shop-api/templates/configmap.yaml" at <.Release.Name>: can't evaluate field Release in type interface {}
```

`range` 안의 점은 `"api.shop.local"` 같은 문자열이다. 문자열에는 `Release`라는 필드가 없다. `{{ $.Release.Name }}`으로 고치면 된다.

## 구조를 통째로 넘기는 toYaml

`resources`, `nodeSelector`, `tolerations`, `affinity`처럼 쿠버네티스 필드 구조를 그대로 받는 값은 하나하나 템플릿으로 풀지 않는다. values에 쿠버네티스 문법 그대로 적게 하고, 템플릿은 `toYaml`로 통째로 옮긴다.

```yaml
          resources:
            {{- toYaml .Values.resources | nindent 12 }}
```

```yaml
# values-prod.yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    memory: 256Mi
```

```text
          resources:
            limits:
              memory: 256Mi
            requests:
              cpu: 100m
              memory: 128Mi
```

`toYaml`은 맵을 YAML 텍스트로 바꾸면서 키를 알파벳 순으로 정렬한다. values에는 requests를 먼저 적었는데 결과에는 limits가 먼저인 이유다. 의미는 같다. 값이 빈 맵(`resources: {}`)이면 `{}`가 그대로 찍히는데, 쿠버네티스는 이걸 "설정 없음"으로 받아들인다. requests와 limits가 무엇을 정하는지는 [requests와 limits 글](/posts/k8s-pod-resources)에서 다룬다.

`toYaml` 덕분에 차트 작성자는 모든 필드를 미리 예상하지 않아도 된다. 사용자가 새 필드를 넣어도 그대로 전달된다. 대신 값이 쿠버네티스 문법에 맞는지는 아무도 검사하지 않는다. 이 빈틈은 [values 글](/posts/helm-values-secrets)의 `values.schema.json`으로 메운다.

## 값 안의 템플릿을 실행하는 tpl

가끔 values 안에 템플릿을 쓰고 싶을 때가 있다. 하위 차트에 넘길 서비스 주소에 릴리스 이름을 넣는 경우가 대표적이다. 그냥 쓰면 values의 `{{ }}`는 글자 그대로 출력된다. `tpl`은 문자열을 템플릿으로 한 번 더 실행한다.

```yaml
# values.yaml
greeting: "{{ .Release.Name }} in {{ .Release.Namespace }}"
```

```yaml
data:
  greeting: {{ tpl .Values.greeting . | quote }}
```

```text
data:
  greeting: "shop-api in shop-dev"
```

편하지만 values를 넣는 사람이 템플릿 코드를 실행할 수 있게 된다는 뜻이기도 하다. 공개 차트에서 아무 값에나 `tpl`을 걸면 사용자가 `.Files`나 `lookup` 같은 기능을 values에서 부를 수 있다. 꼭 필요한 값에만 쓴다.

## 설정이 바뀌면 Pod를 다시 띄우게 하기

템플릿 문법 하나로 해결되는 운영 문제가 있다. ConfigMap 값만 바꿔 `helm upgrade`를 하면 ConfigMap은 바뀌는데 Pod는 그대로다. 환경 변수로 읽는 설정은 Pod가 처음 뜰 때 한 번 읽히기 때문에, 새 값은 Pod가 다시 떠야 적용된다. Deployment 입장에서는 Pod 템플릿이 바뀌지 않았으니 롤아웃할 이유가 없다.

흔히 쓰는 해법은 ConfigMap 내용의 해시를 Pod 어노테이션에 넣는 것이다.

```yaml
  template:
    metadata:
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
```

```bash
# 값을 바꿀 때마다 해시가 바뀌는지 확인한다
helm template shop-api ./shop-api -s templates/deployment.yaml | grep checksum
helm template shop-api ./shop-api -s templates/deployment.yaml --set logLevel=debug | grep checksum
```

```text
        checksum/config: 25b640ea7f673da7ca2a5236f2c5471763e2cc9c9231d0964f2f9943e1b29df1
        checksum/config: 372c51bc51efbfe4475ee557e184527c1d16365e728a48c7e63fa0c03234f0d3
```

ConfigMap 내용이 바뀌면 해시가 바뀌고, 해시는 Pod 템플릿의 일부이니 Deployment가 새 ReplicaSet으로 롤아웃한다. 내용이 그대로면 해시도 그대로라 불필요한 재시작이 없다. 볼륨으로 마운트한 파일은 왜 재시작 없이도 바뀌고 subPath는 왜 안 바뀌는지는 [ConfigMap 글](/posts/k8s-configmap)에서 본다.

그래서 CI에서는 단계마다 하나씩 거는 게 좋다. `helm lint --strict`로 렌더링과 YAML을, 환경별 values로 `helm template`을 돌린 결과를 kubeconform 같은 스키마 검사기에 넘겨 쿠버네티스 스키마를 본다. 마지막 단계의 실수는 렌더링 결과를 리뷰에서 눈으로 보는 수밖에 없다. 차트를 고친 PR에 `helm template` 결과의 diff를 붙이는 팀이 있는 이유다.

## 템플릿을 읽는 순서

템플릿은 YAML이 아니라 YAML을 찍어 내는 텍스트 프로그램이다. 점은 지금 손에 든 값이고, `with`와 `range` 안에서는 바뀌며, `$`는 최상위를 끝까지 기억한다. 들여쓰기는 `{{-`로 지우고 `nindent`로 다시 만들며, 숫자는 부모 키 깊이에 2를 더한 값이다. 오류가 나면 줄 번호가 템플릿 기준인지 결과물 기준인지부터 보고, 결과물 기준이면 `--debug`로 결과를 연다. 다음 글에서는 이 템플릿에 들어가는 값을 환경별로 나누고, 비밀 값을 안전하게 넣는 법을 본다.

## 면접에서 나올 만한 질문

### Helm 템플릿은 어떤 엔진으로 동작하나요?

Go의 `text/template`에 Sprig 함수 모음과 Helm 전용 함수(`include`, `tpl`, `required`, `lookup` 등)를 얹은 것이다. 텍스트 템플릿이라 YAML 구조를 모르고, 글자를 출력할 뿐이다. 그래서 들여쓰기와 타입은 렌더링이 끝난 뒤 YAML 파서와 API 서버가 처음 검사한다.

### include와 template의 차이는 무엇인가요?

둘 다 `define`한 조각을 실행하지만 `template`은 결과를 바로 출력하는 동작이고 `include`는 결과를 문자열로 돌려주는 함수다. 그래서 `nindent`나 `sha256sum` 같은 함수로 결과를 가공하려면 `include`를 써야 한다. `template`에 파이프를 붙이면 파이프가 조각에 넘길 인자 쪽에 걸려 타입 오류가 난다.

### `{{- include ... | nindent 4 }}`에서 하이픈과 nindent는 왜 같이 쓰나요?

`{{-`는 태그 앞의 공백과 줄바꿈을 지우고, `nindent`는 맨 앞에 줄바꿈을 넣은 뒤 모든 줄을 지정한 칸만큼 들여쓴다. 왼쪽을 깨끗이 지우고 함수로 정확히 다시 만들기 때문에 템플릿 파일의 들여쓰기와 상관없이 결과가 정해진다. `indent`를 그냥 쓰면 파일에 있던 들여쓰기에 더해져 첫 줄만 깊어지는 오류가 흔하다.

### `yaml: line 6: did not find expected key` 오류는 어떻게 추적하나요?

줄 번호가 템플릿 파일이 아니라 렌더링 결과 기준이라는 것부터 알아야 한다. `helm template --debug`로 실패한 결과물을 출력해서 그 줄을 본다. 대개 `indent`와 파일 들여쓰기가 겹쳤거나, `-}}`가 줄바꿈을 먹어 두 줄이 붙은 경우다.

### `default`를 불리언 값에 쓰면 왜 문제가 되나요?

`default`는 nil뿐 아니라 `false`, `0`, 빈 문자열을 모두 비어 있다고 보고 기본값으로 바꾼다. 그래서 `.Values.enabled | default true`는 사용자가 `false`를 넣어도 `true`가 된다. 이런 값은 템플릿이 아니라 `values.yaml`에 기본값을 적어 둔다.

### range 안에서 .Release.Name을 쓰면 왜 오류가 나나요?

`range`와 `with`는 안쪽에서 점을 현재 원소로 바꾼다. 원소가 문자열이면 그 문자열에는 `Release` 필드가 없으니 `can't evaluate field Release` 오류가 난다. 최상위 객체는 `$`로 꺼내서 `$.Release.Name`처럼 쓴다.

### ConfigMap만 바꿔 업그레이드했는데 Pod에 반영이 안 됩니다. 어떻게 하나요?

환경 변수로 읽는 설정은 Pod가 뜰 때 한 번 읽히고, Pod 템플릿이 그대로면 Deployment는 롤아웃하지 않는다. ConfigMap 내용을 `include ... | sha256sum`으로 해시해 Pod 템플릿 어노테이션에 넣으면, 내용이 바뀔 때만 해시가 바뀌어 롤아웃이 일어난다. 파일로 마운트한 ConfigMap은 kubelet이 잠시 뒤 갱신하지만, 앱이 파일을 다시 읽어야 반영된다는 점은 따로 챙긴다.
