<EasyIntro>
  온라인 서점을 만들 때 리뷰 화면, 주문 화면, 회원 화면은 따로 만들었다. 몇 달 뒤 기획자가 "9월에 리뷰를 남긴 회원 중 결제한 주문이 두 건 이상인 사람"을 묻는다. 아무도 미리 생각하지 않은 질문인데, 관계형 데이터베이스에서는 이게 SQL 한 문장으로 바로 나온다.

  관계형 데이터베이스는 데이터를 회원, 주문, 책 같은 표로 나눠 담고, 표 사이는 번호로 연결해 둔다. 어떤 표를 어떻게 엮을지는 읽는 쪽이 그때 정하고, 찾는 방법은 데이터베이스가 데이터 양을 보고 알아서 고른다. 또 "없는 회원의 주문은 못 넣는다", "재고는 음수가 될 수 없다" 같은 규칙을 데이터 옆에 한 번만 적어 두면 누가 어떤 경로로 쓰든 똑같이 막아 주고, 표 여러 개를 고치는 일을 하나로 묶어 중간에 멈춰도 반쯤 바뀐 상태가 남지 않는다.

  그래서 대부분의 서비스가 관계형 데이터베이스로 시작한다. 그 대가는 쓰기를 한 대에 모아야 한다는 것이고, 다른 종류의 데이터베이스는 대개 이 대가를 피하려고 관계형의 무언가를 포기한 설계다.

온라인 서점을 운영하는데 기획자가 묻는다. "9월에 리뷰를 남긴 회원 중에 결제한 주문이 두 건 이상인 사람은 누구고, 얼마나 썼어요?" 이 질문은 서비스를 처음 만들 때 아무도 생각하지 않았다. 리뷰 화면, 주문 화면, 회원 화면은 따로 만들었고, 셋을 엮어 볼 일이 생길 줄은 몰랐다.

관계형 DB에서는 이 질문이 SQL 한 문장이다. 테이블을 새로 만들 필요도, 데이터를 다시 쌓을 필요도 없다. 키-값, 와이드 컬럼, 문서 DB 글에서 계속 "접근 패턴을 먼저 정하라"는 말이 나오는데, 관계형 DB는 그 반대 지점에 서 있다. 질문을 미리 몰라도 된다. 이 글은 그게 어떻게 가능한지, 그리고 그 대가로 무엇을 내는지를 본다. [DB 종류 한눈에](/posts/db-types-overview) 글에서 이어지는 시리즈의 두 번째 글이다.

예제는 PostgreSQL 16에서 직접 돌렸다. MySQL 8과 다른 부분은 그때그때 덧붙인다.

## 미리 몰랐던 질문에 답하기

시리즈 내내 쓰는 서점 데이터다. 회원 네 명, 책 네 권, 주문 여섯 건, 리뷰 네 건이 전부다.

```sql
CREATE TABLE users (
  id    bigint PRIMARY KEY,
  name  text NOT NULL,
  email text NOT NULL UNIQUE
);

CREATE TABLE books (
  id    bigint PRIMARY KEY,
  title text NOT NULL,
  price integer NOT NULL CHECK (price >= 0),
  stock integer NOT NULL CHECK (stock >= 0)     -- 재고는 음수가 될 수 없다
);

CREATE TABLE orders (
  id         bigint PRIMARY KEY,
  user_id    bigint NOT NULL REFERENCES users(id),  -- 없는 회원의 주문은 못 넣는다
  status     text NOT NULL DEFAULT 'paid',
  ordered_at timestamptz NOT NULL
);

CREATE TABLE order_items (
  order_id bigint REFERENCES orders(id),
  book_id  bigint REFERENCES books(id),
  qty      integer NOT NULL CHECK (qty > 0),
  price    integer NOT NULL,                     -- 주문 당시 가격
  PRIMARY KEY (order_id, book_id)
);

CREATE TABLE reviews (
  user_id    bigint REFERENCES users(id),
  book_id    bigint REFERENCES books(id),
  rating     smallint NOT NULL CHECK (rating BETWEEN 1 AND 5),
  created_at timestamptz NOT NULL,
  PRIMARY KEY (user_id, book_id)               -- 한 사람이 한 책에 리뷰 하나
);
```

```text
 users                    books
 id | name                id  | title             | price | stock
----+------               ----+-------------------+-------+------
 42 | kim                 101 | 분산 시스템 입문  | 36000 |     5
 43 | lee                 102 | SQL 연습장        | 22000 |     3
 44 | park                103 | 그래프로 생각하기 | 30000 |     2
 45 | choi                104 | 리눅스 한 권      | 28000 |     0

 orders
  id  | user_id | status    | ordered_at
------+---------+-----------+------------------
 9001 |      42 | paid      | 2026-09-03 10:00
 9002 |      42 | paid      | 2026-09-15 21:30
 9003 |      43 | paid      | 2026-09-20 09:10
 9004 |      42 | cancelled | 2026-09-28 13:00
 9005 |      44 | paid      | 2026-10-01 18:40
 9006 |      42 | paid      | 2026-10-05 08:20
```

`order_items`에는 주문마다 산 책과 수량이, `reviews`에는 kim이 101번과 103번에, lee가 101번에, park이 102번에 남긴 리뷰가 들어 있다. 기획자의 질문은 이렇게 쓴다.

```sql
SET timezone = 'Asia/Seoul';

SELECT u.name,
       count(DISTINCT o.id)   AS paid_orders,  -- 결제한 주문 수
       sum(oi.qty * oi.price) AS spent         -- 쓴 돈
FROM users u
JOIN orders o       ON o.user_id = u.id AND o.status = 'paid'
JOIN order_items oi ON oi.order_id = o.id
WHERE EXISTS (                                 -- 9월에 리뷰를 남긴 적이 있는 회원만
  SELECT 1 FROM reviews r
  WHERE r.user_id = u.id
    AND r.created_at >= '2026-09-01' AND r.created_at < '2026-10-01'
)
GROUP BY u.name
HAVING count(DISTINCT o.id) >= 2;
```

```text
 name | paid_orders | spent
------+-------------+--------
 kim  |           3 | 116000
(1 row)
```

kim의 결제 주문은 9001(58,000원), 9002(30,000원), 9006(28,000원)이다. 취소한 9004는 빠졌다. lee도 9월에 리뷰를 남겼지만 주문이 한 건이라 걸러졌다.

이 쿼리를 쓰면서 "리뷰와 주문을 같이 보려면 저장을 어떻게 해야 하지"는 고민하지 않았다. 테이블은 각자 자기 사실만 담고 있고, 어떤 조합으로 묶을지는 읽는 쪽이 정한다. 관계형 DB가 지금도 대부분 서비스의 첫 번째 DB인 이유가 여기 있다. 서비스는 자라면서 처음엔 몰랐던 질문을 계속 만들어 낸다.

## 표와 키로 나눠 담는 이유

관계형 모델은 1970년 E. F. Codd가 논문으로 제안했다. 그 전의 DB는 데이터가 디스크에 어떻게 연결돼 있는지(어느 레코드가 어느 레코드를 가리키는지)를 프로그램이 알고 그 길을 따라가야 했다. 저장 구조가 바뀌면 프로그램도 고쳐야 했다. Codd의 생각은 데이터를 행과 열로 된 표(relation)로만 보여 주고, 표 사이의 연결은 값(키)으로 표현하자는 것이었다. 어떻게 찾을지는 DB가 정한다.

아래 그림은 서점 테이블 다섯 개의 관계다. 화살표는 외래 키(foreign key)로, "이 열의 값은 저 표의 기본 키 중 하나여야 한다"는 약속이다.

이렇게 나누면 사실 하나가 한 곳에만 있다. kim의 이메일은 `users`에 한 번만 적혀 있어서, 바꿀 때도 한 줄만 고친다. 주문 화면에 이메일을 복사해 뒀다면 주문 수만큼 고쳐야 했을 것이다. 같은 사실이 두 곳에 있으면 언젠가 둘이 어긋난다. 이걸 막으려고 표를 쪼개는 규칙이 정규화다. 함수 종속을 기준으로 어디서 자르는지는 [정규화 글](/posts/db-modeling-normalization)에 자세히 있다.

`order_items.price`는 예외처럼 보인다. 책 가격이 `books`에 있는데 왜 또 적을까. 이건 중복이 아니라 다른 사실이다. `books.price`는 지금 가격이고 `order_items.price`는 주문 당시 가격이다. 책 가격이 오르면 지난 주문 금액은 그대로여야 한다.

## 잘못된 데이터를 DB가 막는다

표를 나누면 표 사이가 어긋날 위험이 생긴다. 회원을 지웠는데 그 회원의 주문이 남거나, 없는 회원 번호로 주문이 들어가는 식이다. 관계형 DB는 이걸 애플리케이션에 맡기지 않고 제약 조건으로 직접 막는다. 위 테이블에 일부러 틀린 값을 넣어 봤다.

```sql
INSERT INTO orders VALUES (9007, 99, 'paid', now());      -- 없는 회원 99
INSERT INTO order_items VALUES (9006, 101, 0, 36000);     -- 수량 0
DELETE FROM users WHERE id = 43;                          -- 주문이 있는 회원 삭제
UPDATE books SET stock = stock - 1 WHERE id = 104;        -- 재고 0에서 빼기
```

```text
ERROR:  insert or update on table "orders" violates foreign key constraint "orders_user_id_fkey"
DETAIL:  Key (user_id)=(99) is not present in table "users".
ERROR:  new row for relation "order_items" violates check constraint "order_items_qty_check"
DETAIL:  Failing row contains (9006, 101, 0, 36000).
ERROR:  update or delete on table "users" violates foreign key constraint "orders_user_id_fkey" on table "orders"
DETAIL:  Key (id)=(43) is still referenced from table "orders".
ERROR:  new row for relation "books" violates check constraint "books_stock_check"
DETAIL:  Failing row contains (104, 리눅스 한 권, 28000, -1).
```

네 문장이 모두 거절됐다. 에러 메시지의 `DETAIL` 줄이 어떤 값이 어떤 약속을 어겼는지 정확히 알려 준다. 이 검사는 어느 서비스가, 어느 언어로, 어떤 경로로 쓰든 똑같이 걸린다. 배치 스크립트가 실수해도, 운영자가 psql로 직접 고쳐도 마찬가지다.

스키마 없이 저장하는 DB에서는 이 검사를 모든 쓰기 코드가 각자 해야 한다. 코드가 열 군데면 열 군데 모두 맞아야 한다. 관계형 DB는 규칙을 데이터 옆에 한 번만 적는다. 대신 규칙을 바꿀 때는 테이블 정의를 바꾸는 마이그레이션이 필요하다. 이 차이가 "스키마가 있다"와 "스키마가 없다"의 실제 의미다.

## 무엇을 원하는지만 쓰면 방법은 DB가 고른다

SQL은 결과의 모양만 말한다. "이 조건의 행을 이렇게 묶어서 달라"고 쓰지, "users를 먼저 읽고 각 행마다 orders 인덱스를 찾아라"고 쓰지 않는다. 방법은 옵티마이저(query planner)가 통계를 보고 고른다. 같은 조인이라도 데이터 양에 따라 전혀 다른 방법을 쓴다.

확인하려고 주문 50만 건, 회원 10만 명, 책 5천 권을 더 넣었다. 먼저 회원 한 명의 주문 목록이다.

```sql
CREATE INDEX orders_user_id_idx ON orders (user_id);
ANALYZE;

EXPLAIN (ANALYZE, COSTS OFF)
SELECT o.id, o.ordered_at, b.title
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN books b        ON b.id = oi.book_id
WHERE o.user_id = 42;
```

```text
 Nested Loop (actual time=0.068..0.084 rows=5 loops=1)
   ->  Nested Loop (actual time=0.060..0.069 rows=5 loops=1)
         ->  Bitmap Heap Scan on orders o (actual time=0.047..0.048 rows=4 loops=1)
               Recheck Cond: (user_id = 42)
               Heap Blocks: exact=1
               ->  Bitmap Index Scan on orders_user_id_idx (actual time=0.040..0.040 rows=4 loops=1)
                     Index Cond: (user_id = 42)
         ->  Index Only Scan using order_items_pkey on order_items oi (actual time=0.003..0.003 rows=1 loops=4)
               Index Cond: (order_id = o.id)
               Heap Fetches: 5
   ->  Index Scan using books_pkey on books b (actual time=0.002..0.002 rows=1 loops=5)
         Index Cond: (id = oi.book_id)
 Planning Time: 1.376 ms
 Execution Time: 0.196 ms
```

`Nested Loop`과 `loops=4`, `loops=5`를 보면 된다. kim의 주문 4건을 인덱스로 찾고, 그 4건마다 `order_items`의 기본 키 인덱스를 한 번씩 찾고, 나온 5줄마다 `books`를 한 번씩 찾았다. 찾을 행이 몇 개뿐이라 하나씩 따라가는 게 가장 싸다. 0.2ms에 끝났다.

이번엔 9월 한 달의 책별 매출 상위 3권이다. 조인하는 테이블은 같다.

```sql
EXPLAIN (ANALYZE, COSTS OFF)
SELECT b.title, sum(oi.qty * oi.price) AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN books b        ON b.id = oi.book_id
WHERE o.ordered_at >= '2026-09-01' AND o.ordered_at < '2026-10-01'
GROUP BY b.title
ORDER BY revenue DESC
LIMIT 3;
```

계획이 완전히 달라졌다. 9월 주문 53,786건(`Hash` 아래 `rows=53786`)을 메모리 해시 테이블로 만들어 두고, `order_items` 50만 줄을 처음부터 끝까지 읽으며(`Seq Scan`) 해시 테이블에 맞춰 본다. 5만 번 인덱스를 찾아가느니 통째로 읽고 메모리에서 맞추는 게 싸다고 판단한 것이다. 병렬 작업자를 끈 상태로 이 컨테이너에서 0.3초쯤 걸렸다(병렬을 켜면 0.1초 안쪽이었다).

두 쿼리 모두 SQL에는 방법이 없었다. 데이터가 바뀌면 같은 SQL의 계획도 바뀐다. 실행 계획을 읽는 법과 조인 세 가지(Nested Loop, Hash Join, Merge Join)의 차이는 [쿼리 튜닝 글](/posts/sql-query-tuning)에서 자세히 다룬다.

## 해시 조인을 손으로 따라가기

## 커밋이 끝났다는 건 로그가 디스크에 닿았다는 뜻

관계형 DB가 빠르게 버티는 장치는 크게 둘이다. 찾을 때는 B-tree 인덱스, 지킬 때는 WAL(Write-Ahead Log, 먼저 쓰는 로그)이다. 인덱스는 [인덱스 글](/posts/db-index)에서 다뤘으니 여기서는 쓰기 쪽을 본다.

PostgreSQL은 테이블과 인덱스를 8KB 페이지 단위로 저장한다(MySQL InnoDB는 16KB). 행 하나를 고칠 때마다 그 페이지를 디스크의 제자리에 바로 쓰면 느리다. 페이지는 디스크 여기저기 흩어져 있어서 무작위 쓰기가 되기 때문이다. 그래서 고친 페이지는 메모리(shared buffers)에만 두고, 무엇을 고쳤는지만 WAL 파일 끝에 순서대로 덧붙인다. 커밋은 이 로그가 디스크에 내려간(fsync) 순간에 끝난다. 아래 그림은 kim이 103번 책을 주문하는 커밋 과정이다.

`synchronous_commit = off`로 바꾸면 fsync를 기다리지 않고 응답해서 쓰기가 빨라진다. 대신 서버가 갑자기 죽으면 마지막 몇 백 ms의 커밋이 사라질 수 있다(데이터가 깨지지는 않는다). 로그성 데이터처럼 잃어도 되는 쓰기에만 트랜잭션 단위로 켜는 설정이다.

## 표 여러 개를 한 번에 바꾸는 트랜잭션

주문 하나를 받으려면 표 세 개를 고친다. 재고를 빼고, 주문을 넣고, 주문한 책을 넣는다. 셋 중 하나만 되면 안 된다. 재고는 빠졌는데 주문이 없거나, 주문은 있는데 재고가 그대로면 장부가 틀린다.

```sql
BEGIN;
-- 재고가 남아 있을 때만 하나 뺀다. 남은 수량을 돌려받는다
UPDATE books SET stock = stock - 1 WHERE id = 103 AND stock >= 1 RETURNING id, stock;
INSERT INTO orders (id, user_id, ordered_at) VALUES (9010, 43, '2026-10-17 10:00+09');
INSERT INTO order_items VALUES (9010, 103, 1, 30000);
COMMIT;
```

```text
BEGIN
 id  | stock
-----+-------
 103 |     1
(1 row)

UPDATE 1
INSERT 0 1
INSERT 0 1
COMMIT
```

재고가 0인 104번으로 같은 일을 하면 `UPDATE`가 한 줄도 바꾸지 못한다.

```sql
BEGIN;
UPDATE books SET stock = stock - 1 WHERE id = 104 AND stock >= 1 RETURNING id, stock;
-- 0 rows가 돌아왔으니 앱은 여기서 ROLLBACK 한다
ROLLBACK;
```

```text
BEGIN
 id | stock
----+-------
(0 rows)

UPDATE 0
ROLLBACK
```

`WHERE stock >= 1` 조건을 UPDATE에 같이 걸었기 때문에, 두 사람이 마지막 한 권을 동시에 사도 한 사람만 `UPDATE 1`을 받는다. 다른 쪽은 앞 트랜잭션이 끝날 때까지 그 행에서 기다렸다가 조건을 다시 확인하고 `UPDATE 0`을 받는다. 동시에 고칠 때 생기는 문제와 격리 수준은 [트랜잭션 글](/posts/db-transaction-isolation)에서 두 세션으로 재현해 봤다.

여러 표, 여러 행에 걸친 변경을 하나로 묶고, 동시에 들어온 요청 사이의 순서를 DB가 정리해 주는 것. 다른 종류의 DB들이 확장성을 얻으려고 가장 먼저 내려놓는 기능이 이것이다. 키-값 저장소와 와이드 컬럼 DB는 보통 키 하나(파티션 하나) 안에서만 원자성을 준다. 여러 키를 묶는 트랜잭션이 있더라도 개수 제한이 있거나 비싸다.

## PostgreSQL, MySQL, Oracle, SQL Server

관계형 DB는 SQL 표준을 공유하지만 내부 구조와 쓰임새가 꽤 다르다. 새 서비스에서 실제로 고민하는 건 대부분 앞의 둘이다.

PostgreSQL은 기능의 폭이 넓다. JSONB, 배열, 범위 타입, 전문 검색, 사용자 정의 함수와 확장(PostGIS, pgvector, TimescaleDB)까지 DB 하나에 모을 수 있다. 행을 고치면 새 버전을 따로 만들고 옛 버전은 VACUUM이 나중에 치우는 MVCC 방식이라, 고치기가 아주 잦은 테이블에서는 VACUUM 관리가 운영 포인트가 된다. 라이선스는 BSD 계열이라 제약이 거의 없다.

MySQL(InnoDB)은 표 자체가 기본 키 순서로 정렬된 B-tree(클러스터드 인덱스)다. 기본 키로 찾는 쿼리가 빠르고, 옛 버전은 undo 로그에 둔다. 단순한 읽기·쓰기가 많은 웹 서비스에서 오래 쓰였고, 복제와 운영 도구가 성숙했다. 오라클이 소유하며 GPL과 상용 라이선스로 나뉜다. MariaDB는 MySQL에서 갈라진 프로젝트다.

Oracle Database와 SQL Server는 상용 DB다. 금융, 공공, 대기업 내부 시스템에서 많이 보이고, 클러스터링(Oracle RAC), 분석 기능, 벤더 지원이 강점이다. 라이선스 비용이 크고, 새로 시작하는 웹 서비스에서 고르는 경우는 드물다. 문법 차이는 [SQL 기본 글](/posts/sql-basics)에 정리해 뒀다.

아마존 Aurora, 구글 AlloyDB 같은 관리형 서비스는 PostgreSQL이나 MySQL과 호환되는 SQL을 쓰면서 저장 계층을 따로 분산해 둔 형태다. 쓰는 입장에서는 같은 관계형 DB로 보면 된다.

## 한 대를 넘어서면 어려워지는 것

관계형 DB의 강점은 대부분 "데이터가 한 곳에 있다"는 전제에서 나온다. 조인은 두 표가 같은 서버에 있어야 싸고, 트랜잭션은 잠금과 로그가 한 곳에 있어야 단순하다. 그래서 한계도 같은 곳에서 온다.

쓰기를 받는 프라이머리는 보통 한 대다. 읽기는 복제본을 늘려서 나누지만 쓰기는 나눌 수 없다. 서버를 키우는(수직 확장) 데는 끝이 있다. 한 대가 감당할 수 있는 양은 생각보다 크다. 잘 튜닝한 PostgreSQL 한 대가 초당 수천~수만 건의 짧은 트랜잭션을 처리하는 건 흔한 일이다. 그래도 그 위로 가면 샤딩을 해야 하고, 샤딩을 하면 샤드를 넘는 조인과 트랜잭션이 비싸지거나 불가능해진다. 관계형 DB의 장점을 직접 깎아 내는 셈이다. 이 단계를 DB가 대신해 주는 게 [분산 SQL](/posts/db-type-newsql)이다.

그 밖에 관계형 DB가 잘 못하는 일이 있다.

- 수십억 줄을 훑는 집계. 행 단위로 저장해서, 열 두 개만 필요해도 행 전체를 읽는다. [컬럼형 분석 DB](/posts/db-type-columnar-olap)가 이 문제를 푼다.
- 관계를 여러 단계 따라가는 질의. "친구의 친구의 친구"는 단계마다 조인이 하나씩 늘고, 결과가 기하급수로 커진다. [그래프 DB 글](/posts/db-type-graph)에서 재귀 CTE로 직접 재 봤다.
- 초당 수십만 건의 쓰기가 끝없이 들어오는 이벤트. B-tree는 쓸 때마다 정렬된 자리를 찾아 페이지를 고친다. [와이드 컬럼 DB](/posts/db-type-wide-column)는 정렬을 나중으로 미뤄서 쓰기를 싸게 만든다.
- 모양이 제각각인 데이터. JSONB로 상당 부분 해결되지만, 문서 하나를 통째로 읽고 쓰는 게 전부라면 [문서 DB](/posts/mongodb-document-model)가 더 자연스럽다.
- 아주 큰 테이블의 스키마 변경. 수억 줄 테이블에 열을 추가하거나 타입을 바꾸면 잠금과 재작성이 생길 수 있다. PostgreSQL 11부터 기본값이 있는 열 추가는 즉시 끝나지만, 타입 변경 같은 작업은 여전히 테이블을 다시 쓴다.

## 다른 DB를 붙여도 원본은 여기에 둔다

서비스가 커지면 캐시, 검색 엔진, 분석 DB가 하나씩 붙는다. 그래도 대부분의 구성에서 관계형 DB는 원본(source of truth)으로 남는다. 주문, 결제, 재고, 회원처럼 틀리면 안 되는 데이터를 여기에 쓰고, 나머지 저장소는 그 데이터에서 만든 사본(파생 데이터)으로 둔다. 사본은 망가져도 원본에서 다시 만들 수 있다.

원본에서 사본으로 옮기는 방법은 몇 가지다. 쓰는 김에 캐시를 지우는 방법([캐시 전략 글](/posts/caching-strategies)), 같은 트랜잭션에서 아웃박스 테이블에 이벤트를 적고 따로 내보내는 방법, WAL을 읽어 변경을 흘려보내는 CDC(Change Data Capture)가 있다. 언제 어떤 저장소를 더할지는 [서비스 규모별 DB 설계](/posts/db-architecture-by-scale)에서 숫자와 함께 다뤘다.

처음부터 여러 DB를 두는 건 대개 이르다. 관계형 DB 한 대로 시작해서, 위에 적은 "잘 못하는 일"이 실제로 숫자로 보일 때 그 일만 떼어 내는 편이 안전하다. 다른 종류의 DB를 고르는 이유도 결국 "관계형 DB로는 이 접근 패턴을 감당할 수 없다"는 문장으로 설명할 수 있어야 한다.

## 기본값인 이유와 그 값

관계형 DB가 기본값인 이유는 미리 몰랐던 질문에 답할 수 있어서다. 데이터를 사실 단위로 나눠 한 번씩만 적고, 제약 조건으로 어긋남을 막고, 읽을 때 원하는 조합으로 다시 붙인다. 방법은 옵티마이저가 고르고, 여러 표에 걸친 변경은 트랜잭션과 WAL이 지킨다. 그 대가는 쓰기를 한 곳에 모아야 한다는 것이다. 이 시리즈의 다른 DB들은 대부분 이 대가를 피하려고, 관계형 DB의 무언가를 내려놓은 설계다.

## 면접에서 나올 만한 질문

### 관계형 DB를 기본으로 고르는 이유는 무엇인가요?

접근 패턴을 미리 몰라도 되기 때문이다. 데이터를 정규화해 사실마다 한 곳에 두고, 필요한 조합은 조인으로 그때그때 만든다. 외래 키와 CHECK 같은 제약 조건이 어떤 경로의 쓰기든 똑같이 검사하고, 트랜잭션이 여러 표의 변경을 하나로 묶는다. 서비스 초기에는 질문이 계속 바뀌니 이 유연함이 가장 큰 가치다.

### 같은 조인 쿼리인데 실행 방법이 바뀌는 이유는요?

SQL은 결과만 말하고 방법은 옵티마이저가 통계로 고른다. 찾을 행이 적으면 인덱스로 하나씩 따라가는 Nested Loop가, 많으면 한쪽으로 해시 테이블을 만들고 다른 쪽을 순차로 읽는 Hash Join이 싸다. 그래서 데이터 분포가 바뀌면 같은 쿼리의 계획도 바뀐다. 통계가 낡으면 잘못 고르니 ANALYZE가 중요하다.

### 커밋 직후 서버가 꺼져도 데이터가 남는 이유는 무엇인가요?

WAL 때문이다. 바뀐 페이지는 메모리에만 두고, 변경 내용을 로그 파일 끝에 순서대로 적은 뒤 fsync가 끝나야 커밋 성공을 돌려준다. 재시작하면 마지막 체크포인트부터 WAL을 다시 실행해 커밋된 변경을 복구한다. synchronous_commit을 끄면 응답은 빨라지지만 마지막 몇 백 ms의 커밋을 잃을 수 있다.

### 재고가 음수가 되지 않게 하려면 어떻게 하나요?

CHECK (stock >= 0) 제약으로 마지막 방어선을 두고, 차감은 `UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock >= 1`처럼 조건부로 한 문장에 한다. 같은 행을 동시에 고치면 뒤 트랜잭션은 앞이 끝날 때까지 기다렸다가 조건을 다시 보므로 한쪽만 성공한다. 읽고 나서 계산해 쓰는 방식은 그 사이에 틈이 생긴다.

### PostgreSQL과 MySQL은 어떻게 다른가요?

PostgreSQL은 행을 고칠 때 새 버전을 힙에 따로 만들고 VACUUM이 옛 버전을 치운다. JSONB, 확장, 다양한 인덱스 타입처럼 기능의 폭이 넓다. MySQL InnoDB는 표 자체가 기본 키 순서의 클러스터드 인덱스이고 옛 버전은 undo 로그에 둔다. 기본 키 조회가 빠르고 운영 경험이 많이 쌓여 있다. 둘 다 대부분의 웹 서비스에 충분하고, 팀의 경험과 필요한 기능으로 고르는 경우가 많다.

### 관계형 DB의 확장 한계는 어디서 오고, 어떻게 넘나요?

쓰기를 받는 프라이머리가 한 대라는 데서 온다. 읽기는 복제본으로 나누지만, 쓰기가 한 대를 넘으면 샤딩해야 하고 그러면 샤드를 넘는 조인과 트랜잭션을 잃는다. 그 전에 쿼리와 인덱스 튜닝, 캐시, 복제본, 파티셔닝을 차례로 쓴다. 샤딩까지 DB가 대신해 주길 원하면 분산 SQL을, 쓰기 패턴이 고정돼 있으면 와이드 컬럼이나 키-값 저장소를 고려한다.

### 다른 종류의 DB를 함께 쓸 때 관계형 DB는 어떤 역할을 하나요?

보통 원본을 맡는다. 주문과 결제처럼 틀리면 안 되는 데이터를 트랜잭션으로 쓰고, 캐시나 검색 엔진, 분석 DB는 거기서 만든 사본으로 둔다. 사본은 CDC나 아웃박스 이벤트로 채우고, 망가지면 원본에서 다시 만든다. 그래서 사본은 잠깐 늦을 수 있다는 걸 화면과 기능 설계에 반영한다.
