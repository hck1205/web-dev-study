<EasyIntro>
  비밀번호의 원본을 클러스터 밖의 전용 저장소에 두면 한 곳에서 관리할 수 있다. External Secrets Operator는 그 저장소의 값을 읽어 와서 쿠버네티스 안의 평범한 Secret으로 복사해 주는 프로그램이다. 앱은 바꿀 것 없이 늘 하던 대로 Secret을 읽으면 된다.

  이 프로그램은 어디에 접속할지, 무엇을 가져올지, 어디에 둘지를 따로 적어 두고 정해진 주기마다 저장소를 다시 읽어 값이 달라졌으면 Secret을 고친다. 우체부가 정해진 시간에 우편함에 새 편지를 넣어 주는 것과 같아서, 편지가 우편함에 도착한 것과 집주인이 읽은 것은 다른 일이다. 저장소에서 비밀번호를 바꿔도 앱이 새 값을 쓰려면 복사 주기에 기계의 반영과 앱의 재시작까지 더해진 시간이 걸린다.

  저장소가 잠깐 죽어도 이미 복사해 둔 Secret은 지우지 않아서 앱은 멀쩡히 뜬다. 그래서 비밀번호를 바꿀 때는 옛 값과 새 값이 함께 통하는 기간을 두어야 한다.
</EasyIntro>

DB 비밀번호를 AWS Secrets Manager에서 바꿨다. External Secrets Operator(ESO)가 쿠버네티스 Secret도 알아서 바꿔 준다고 들었다. 한 시간 뒤 DB에서 옛 비밀번호를 막았더니 앱이 인증 오류를 쏟아 낸다. 확인해 보니 Secret은 새 값으로 바뀌어 있었다. 앱이 옛 값을 계속 쓰고 있었던 것이다. 같은 주에 Secrets Manager가 잠깐 응답하지 않았는데 그때는 아무 일도 없었다. 둘 다 ESO가 어디까지 책임지는지를 알면 예상할 수 있는 일이다.

이 글은 ESO가 외부 저장소의 값을 쿠버네티스 Secret으로 옮기는 과정을 컨트롤러 입장에서 따라간다. `refreshInterval`이 실제로 무엇을 정하는지, 만들어진 Secret의 주인이 누구인지, 저장소가 죽거나 ExternalSecret을 지우면 어떻게 되는지, 그리고 Secrets Store CSI Driver, Sealed Secrets, SOPS와 언제 갈라서는지를 본다.

이 주제의 다른 글이 셋 있다. Secret이 etcd에 어떻게 저장되고 누가 읽을 수 있는지, CSI 드라이버가 Secret 없이 파일을 꽂는 흐름은 [Secret 글](/posts/k8s-secret)에, Vault의 동적 비밀과 비밀 값이 새는 길은 [비밀 관리 글](/posts/secrets-management)에, Helm 차트에서 ESO·SOPS를 쓰는 배포 흐름은 [Helm values와 비밀 값 글](/posts/helm-values-secrets)에 있다. 여기서는 그 설명을 반복하지 않는다.

실습은 Ubuntu 24.04에서 kwok으로 띄운 Kubernetes v1.37.0 클러스터에 ESO 저장소 태그 v2.13.0의 CRD 묶음(`deploy/crds/bundle.yaml`)을 설치해서 했다. 이 버전의 주요 객체는 `external-secrets.io/v1`이고 `v1beta1`은 더 제공되지 않는다. ESO 컨트롤러는 이 환경에서 빌드할 수 없어 띄우지 못했다. 그래서 객체 생성과 검증 오류는 실제 출력이고, 컨트롤러가 채우는 상태(Ready, SecretSynced)는 CRD의 출력 칸 정의와 문서에 맞춘 예시로 따로 표시했다.

- SecretStore: 저장소에 접속하는 방법이다. 어느 제공자(AWS, Vault, GCP 등)인지, 지역, 인증 수단(IRSA, Pod Identity, 토큰 Secret)을 적는다. 네임스페이스 객체라 그 네임스페이스의 ExternalSecret만 쓸 수 있다.
- ClusterSecretStore: 같은 내용을 클러스터 범위로 둔 것이다. 모든 네임스페이스가 쓸 수 있어서 편하지만, 그만큼 문을 넓게 연다(뒤에서 따로 본다).
- ExternalSecret: 저장소의 어느 키, 어느 속성을 Secret의 어느 키로 넣을지와 동기화 주기를 적는다.

결과물은 평범한 Secret이다. 앱은 ESO를 몰라도 되고, 기존 매니페스트의 `secretKeyRef`를 그대로 쓴다. 실제 저장소 대신 ESO의 `fake` 제공자를 쓰는 SecretStore로 객체를 만들었다. fake 제공자는 스펙에 적은 키-값을 저장소인 척 돌려준다.

```yaml
apiVersion: external-secrets.io/v1
kind: SecretStore
metadata:
  name: fake-store
  namespace: shop
spec:
  provider:
    fake:                       # 시험용 제공자. 실제로는 aws, vault 등이 들어간다
      data:
      - key: /prod/shop-api/db
        value: '{"username":"shop","password":"s3cr3t-v1"}'
        version: v1
---
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: shop-db
  namespace: shop
spec:
  refreshInterval: 1m           # 저장소를 다시 읽는 주기
  secretStoreRef:
    name: fake-store
    kind: SecretStore
  target:
    name: shop-db               # 만들 Secret 이름
    creationPolicy: Owner
    deletionPolicy: Retain
  data:
  - secretKey: password         # Secret의 키
    remoteRef:
      key: /prod/shop-api/db    # 저장소의 키
      property: password        # JSON 값 안의 속성
```

```bash
kubectl apply -f store.yaml
kubectl -n shop get secretstores,externalsecrets
```

```text
namespace/shop created
secretstore.external-secrets.io/fake-store created
externalsecret.external-secrets.io/shop-db created
NAME                                         AGE   STATUS   CAPABILITIES   READY
secretstore.external-secrets.io/fake-store   0s                            

NAME                                         STORETYPE     STORE        REFRESH INTERVAL   STATUS   READY   LAST SYNC
externalsecret.external-secrets.io/shop-db   SecretStore   fake-store   1m                                  
```

`STATUS`, `READY`, `LAST SYNC`가 비어 있다. 컨트롤러가 없으니 아무도 상태를 채우지 않았고 Secret도 생기지 않았다. 장애 상황에서 이 모습을 보면 ESO 컨트롤러 Pod부터 확인해야 한다는 뜻이기도 하다. 객체는 API 서버에 잘 저장돼 있어도 일하는 쪽이 없으면 아무 일도 일어나지 않는다.

`remoteRef` 한 줄이 저장소의 어디를 가리키는지 나눠 읽어 둔다.


동기화를 기다리지 않고 바로 다시 읽게 하고 싶을 때는 ExternalSecret에 아무 어노테이션이나 바꿔 붙인다. 스펙이나 메타데이터가 바뀌면 컨트롤러가 즉시 한 바퀴를 돈다.

```bash
# 어노테이션 값을 바꿔 즉시 다시 동기화하게 한다
kubectl -n shop annotate externalsecret shop-db force-sync=$(date +%s) --overwrite
```

## refreshInterval은 앱까지 걸리는 시간이 아니다

글 첫머리의 사고가 여기서 나온다. 저장소에서 비밀번호를 바꾼 뒤 앱이 새 값을 쓰기까지는 단계가 셋이다.

세 번째 단계는 ESO와 상관없는 쿠버네티스의 동작이다. 볼륨 파일이 언제 바뀌고 환경 변수와 subPath는 왜 그대로인지는 [ConfigMap 글](/posts/k8s-configmap#마운트한-파일은-늦게-바뀐다)에서 직접 확인했다. Secret도 똑같다.

그래서 비밀번호 교체는 순서가 있어야 한다. 저장소에 새 값을 넣고, ESO 동기화를 강제하고, 앱을 재시작(또는 파일을 다시 읽게)한 뒤에야 옛 값을 막는다. 옛 값과 새 값이 잠깐 함께 통하는 기간을 두는 것이 핵심이다. DB라면 사용자를 둘 두고 번갈아 쓰는 방식, Secrets Manager의 자동 교체라면 `AWSPREVIOUS`가 남아 있는 동안이 그 기간이다. Secret이 바뀔 때 Deployment를 자동으로 재시작해 주는 컨트롤러(Stakater Reloader 같은)를 함께 쓰는 팀도 많다.

`refreshInterval`을 짧게 줄이면 해결될 것 같지만 대가가 있다. 저장소 API는 호출마다 돈이 들거나 호출 한도가 있다. ExternalSecret 수, 주기, 한 번 동기화할 때의 호출 수를 곱하면 한 달 호출량이 나온다. 아래 코드로 계산해 본다. 가격은 AWS Secrets Manager의 공시 API 요금(10,000건당 0.05달러)을 쓰는 예로 두었다. 가격은 바뀔 수 있으니 실제 값으로 바꿔 넣는다.

<CodePlayground

  // 30일 기준. 하루 동기화 횟수는 86400 / refreshSeconds를 올림한다
  // 반환: { calls, usd }  usd는 소수 둘째 자리까지 반올림

1분 주기는 1시간 주기보다 호출이 60배 많다. 돈보다 먼저 문제가 되는 것은 호출 한도다. 저장소가 초당 호출 수를 제한하면, 많은 ExternalSecret이 같은 순간에 몰릴 때 일부가 거절되고 동기화 오류가 난다. 주기는 1시간쯤으로 두고, 교체할 때만 강제 동기화하는 편이 대부분 낫다. 키 여러 개를 `data`로 하나씩 읽기보다 JSON 하나에 모아 `dataFrom.extract`로 한 번에 읽으면 호출 수도 줄어든다.

동기화 방식 자체를 바꾸는 `refreshPolicy`도 있다. 기본인 `Periodic`은 주기마다 읽고, `CreatedOnce`는 Secret이 없을 때 한 번만 만들고 다시는 고치지 않는다. `OnChange`는 ExternalSecret이 바뀔 때만 읽는다. 처음 한 번 생성한 뒤 앱이 스스로 바꾸는 값(초기 관리자 비밀번호 같은)에는 `CreatedOnce`가 맞는다. 이 버전의 CRD에는 정해진 시간대에만 동기화하게 하는 `syncWindows`도 있다.

## 받은 값을 모양 바꿔 넣기

저장소의 값과 앱이 원하는 모양이 다를 때가 많다. 저장소에는 사용자 이름과 비밀번호가 따로 있는데 앱은 접속 문자열 하나를 원한다면 템플릿을 쓴다. 템플릿 엔진은 Go 템플릿이고 이 CRD에서는 `engineVersion: v2`만 받는다.

```yaml
spec:
  target:
    name: shop-db
    template:
      engineVersion: v2
      data:
        # 저장소에서 꺼낸 값(username, password)으로 접속 문자열을 만든다
        DATABASE_URL: "postgres://{{ .username }}:{{ .password }}@db.shop.svc:5432/shop?sslmode=require"
  dataFrom:
  - extract:
      key: /prod/shop-api/db     # JSON의 모든 필드를 한 번에 가져온다
```

`dataFrom.extract`는 JSON 값의 필드를 전부 키로 펼치고, `dataFrom.find`는 이름 정규식이나 태그로 여러 비밀을 한꺼번에 찾는다. `find`는 편하지만 저장소에 새 비밀이 생기면 모르는 사이에 Secret에 끼어든다. 무엇이 들어갈지 명확해야 하는 운영 환경에서는 `data`나 `extract`로 키를 적는 편이 낫다.

## 만들어진 Secret의 주인은 누구인가

ESO가 만든 Secret을 누가 소유하는지, ExternalSecret을 지우면 Secret이 어떻게 되는지는 `target`의 두 정책이 정한다. 값을 잘못 적으면 API 서버가 거절해서 고를 수 있는 값을 알 수 있다.

```text
The ExternalSecret "bad" is invalid: spec.target.creationPolicy: Unsupported value: "Create": supported values: "Owner", "Orphan", "Merge", "None", "CreateOrMerge"
```

- `creationPolicy: Owner`(기본): ESO가 Secret을 만들고 ExternalSecret을 주인(ownerReference)으로 적는다. 다른 ExternalSecret이 이미 주인인 같은 이름의 Secret이 있으면 빼앗지 않고 오류를 낸다.
- `Orphan`: 만들되 주인을 적지 않는다. ExternalSecret을 지워도 Secret이 남는다.
- `Merge`: 이미 있는 Secret에 키만 더한다. Secret이 없으면 만들지 않고 오류를 낸다. 다른 도구가 만든 Secret에 값 하나만 보태야 할 때 쓴다.
- `CreateOrMerge`: 없으면 만들고, 있으면 더한다.
- `None`: Secret을 아예 만들지 않는다. 다른 객체(PushSecret 같은)를 위해 값만 확인할 때 쓴다.

`deletionPolicy`는 저장소에서 키가 사라졌을 때다. 기본 `Retain`은 Secret을 그대로 둔다. `Delete`는 Secret을 지우고, `Merge`는 사라진 키만 뺀다. 저장소에서 실수로 키를 지웠을 때 `Delete`면 앱 재시작 순간 Pod가 뜨지 못하니, 대부분 `Retain`이 안전하다.

헷갈리기 쉬운 부분이 하나 있다. `Owner`일 때 ExternalSecret 자체를 지우면 쿠버네티스의 가비지 컬렉터가 주인 잃은 Secret을 지운다. 이건 `deletionPolicy`와 상관없는 쿠버네티스의 소유 관계 규칙이다. Helm 차트를 지우거나 Argo CD에서 ExternalSecret이 빠지는 순간 Secret도 사라지고, 다음에 재시작하는 Pod부터 `CreateContainerConfigError`가 난다. 운영 Secret이라면 이 경로를 알고 고른다.

## ClusterSecretStore를 열어 두면 생기는 구멍

## CSI 드라이버, Sealed Secrets, SOPS와 나눠 보기

비밀 값을 클러스터에 넣는 방법은 원본을 어디에 두느냐로 갈린다. ESO와 CSI 드라이버는 원본을 외부 저장소에, Sealed Secrets와 SOPS는 원본을 git에 암호화해서 둔다.

- ESO: 외부 저장소의 값을 주기적으로 Secret으로 복사한다. 앱은 바꿀 게 없고 저장소 장애에 강하다. 대신 값이 etcd에 한 벌 더 있고, 교체가 앱까지 닿는 데 시간이 걸린다.
- Secrets Store CSI Driver: Pod가 뜰 때 저장소에서 읽어 파일로 꽂는다. etcd에 값이 없고 Pod의 권한으로 읽는다. 저장소가 Pod 시작 경로에 들어오고, 환경 변수로 쓰려면 Secret 동기화 옵션을 켜야 해서 장점 일부를 내준다.
- Sealed Secrets: 클러스터의 컨트롤러가 가진 키로만 풀리는 `SealedSecret`을 git에 둔다. `kubeseal`로 암호화하고, 컨트롤러가 풀어 Secret을 만든다. 외부 저장소가 필요 없다. 대신 암호화 키를 잃으면 git의 모든 SealedSecret을 다시 만들어야 하니 키 백업이 운영의 핵심이고, 값을 바꾸려면 다시 봉인해 커밋해야 한다.
- SOPS: 파일의 값만 age나 KMS 키로 암호화해 git에 둔다. 배포 도구(Flux의 kustomize-controller, helm-secrets 플러그인 등)가 배포할 때 푼다. 쿠버네티스 밖에서도 쓰이는 일반 도구라는 게 장점이다.

외부 저장소가 이미 있고 비밀 교체를 배포와 떼어 두고 싶으면 ESO가 무난하다. 비밀이 많지 않고 git만으로 끝내고 싶으면 Sealed Secrets나 SOPS다. etcd에 값이 남으면 안 되면 CSI 드라이버다. 한 클러스터에서 섞어 쓰는 경우도 흔하다. 앱 비밀은 ESO로, ESO 자체가 저장소에 로그인하는 첫 자격 증명(이른바 secret zero)은 IRSA나 Pod Identity로 아예 없애는 식이다.

ESO는 반대 방향도 한다. `PushSecret`(이 버전에서는 아직 `v1alpha1`)은 클러스터의 Secret을 외부 저장소로 밀어 넣는다. cert-manager가 클러스터에서 발급한 인증서를 다른 클러스터나 서비스와 나누려고 저장소에 올릴 때 쓴다.

## 동기화가 안 될 때 보는 순서

ESO 문제는 세 층으로 나뉜다. 컨트롤러가 살아 있는지, 스토어가 저장소에 접속되는지, 개별 ExternalSecret이 키를 찾는지다. 아래 명령은 그 순서다.

```bash
# 1. 컨트롤러가 떠 있나 (상태 칸이 모두 비어 있으면 여기부터)
kubectl -n external-secrets get pods
# 2. 스토어가 Ready인가 (인증·권한 문제는 여기서 드러난다)
kubectl -n shop get secretstores
kubectl get clustersecretstores
# 3. ExternalSecret의 상태와 이벤트
kubectl -n shop get externalsecret shop-db
kubectl -n shop describe externalsecret shop-db | sed -n '/Status/,$p'
# 4. 만들어진 Secret의 주인과 값 (값은 꼭 필요할 때만 본다)
kubectl -n shop get secret shop-db -o jsonpath='{.metadata.ownerReferences[0].kind}{"\n"}'
# 5. 컨트롤러 로그에서 그 ExternalSecret 이름을 찾는다
kubectl -n external-secrets logs deploy/external-secrets | grep shop-db | tail -20
```

증상별로 자주 만나는 원인은 이렇다.

- 모든 ExternalSecret의 `STATUS`가 비어 있다. 컨트롤러가 없거나 죽었다. 위 실습 출력이 바로 이 모습이다.
- 스토어가 Ready가 아니다. IRSA 역할의 신뢰 정책에 ESO의 ServiceAccount가 빠졌거나, 지역(region)이 틀렸다. 스토어가 Ready가 아니면 그 스토어를 쓰는 ExternalSecret이 모두 실패한다.
- 한 ExternalSecret만 `SecretSyncedError`다. 키 이름 오타, `property` 오타, 그 키에 대한 읽기 권한 누락이다. 이벤트 메시지에 저장소가 돌려준 오류가 그대로 실린다.
- 다른 주인이 있다는 오류가 난다. ExternalSecret 두 개가 같은 `target.name`을 쓰고 둘 다 `creationPolicy: Owner`다. 하나의 Secret에는 주인이 하나뿐이니 이름을 나누거나, 값을 보태는 쪽을 `Merge`로 바꾼다.
- `refreshInterval: 1 hour`처럼 적어도 API 서버는 받아 준다(이 CRD에는 형식 검사가 없어 실제로 만들어졌다). 이 값은 Go duration 형식이어야 하니 `1h`로 쓴다. 이런 값은 컨트롤러가 처리하다 실패하므로 상태와 로그에서 드러난다.
- Secret은 새 값인데 앱이 옛 값을 쓴다. ESO의 문제가 아니다. 앞에서 본 kubelet 반영과 재시작 단계를 본다.

## 복사해 주는 것까지가 ESO의 일

ESO는 SecretStore로 저장소에 접속해 ExternalSecret에 적힌 키를 `refreshInterval`마다 읽고, 달라졌으면 평범한 Secret을 고친다. 그래서 앱은 바꿀 게 없고 저장소가 잠깐 죽어도 Pod는 뜬다. 대신 새 값이 앱에 닿는 시간은 ESO의 주기에 kubelet 반영과 앱 재시작이 더해진 것이고, 교체는 옛 값과 새 값이 함께 통하는 기간을 두고 해야 한다. Secret의 주인과 삭제는 `creationPolicy`와 소유 관계가 정하고, 다른 팀의 비밀을 못 꺼내게 하는 일은 store의 범위와 저장소 쪽 권한이 함께 맡는다. Secret 자체가 어떻게 저장되고 보호되는지는 [Secret 글](/posts/k8s-secret)에서, 저장소 쪽의 동적 비밀과 lease는 [비밀 관리 글](/posts/secrets-management)에서 이어서 볼 수 있다.

## 면접에서 나올 만한 질문

### External Secrets Operator는 무엇을 하나요?

외부 저장소(AWS Secrets Manager, Vault 등)의 값을 읽어 쿠버네티스 Secret으로 만들고 주기적으로 맞춰 주는 컨트롤러다. SecretStore에 접속 방법을, ExternalSecret에 가져올 키와 주기를 적으면, 컨트롤러가 `refreshInterval`마다 읽어 Secret과 비교하고 다르면 고친다. 앱은 평범한 Secret을 읽으니 바꿀 것이 없다.

### 저장소에서 비밀번호를 바꿨는데 앱이 옛 값을 쓰는 이유는요?

ESO가 Secret을 바꾸는 것과 앱이 새 값을 쓰는 것은 별개라서다. ESO는 다음 주기(기본 1시간)에야 읽고, 볼륨으로 넣었다면 kubelet이 파일을 바꾸기까지 또 기다리며, 환경 변수나 subPath는 Pod를 재시작해야만 바뀐다. 그래서 새 값을 넣고, 강제 동기화하고, 앱을 재시작한 뒤에 옛 값을 막는 순서로 교체한다.

### refreshInterval을 아주 짧게 두면 어떤가요?

교체가 빨리 반영되지만 저장소 API 호출이 그만큼 는다. ExternalSecret 500개를 1분마다 읽으면 한 달에 2천만 번이 넘고, 호출 요금과 초당 호출 한도에 걸릴 수 있다. 보통은 1시간 안팎으로 두고 교체할 때만 어노테이션을 바꿔 강제 동기화한다.

### 저장소가 장애일 때 ESO와 Secrets Store CSI Driver는 어떻게 다르게 동작하나요?

ESO는 읽기에 실패해도 이미 만든 Secret을 지우지 않아서 새 Pod도 etcd의 Secret으로 정상적으로 뜬다. CSI 드라이버는 Pod가 뜰 때마다 저장소를 불러 파일을 꽂으니, 저장소가 죽으면 새 Pod가 볼륨을 붙이지 못해 시작하지 못한다. 대신 CSI 방식은 etcd에 값이 남지 않는다.

### creationPolicy Owner로 만든 Secret은 언제 지워지나요?

ExternalSecret이 ownerReference로 Secret의 주인이 되므로, ExternalSecret을 지우면 쿠버네티스 가비지 컬렉터가 Secret도 지운다. 저장소에서 키가 사라졌을 때의 동작은 별개로 `deletionPolicy`가 정하고, 기본 `Retain`이면 Secret을 그대로 둔다. ExternalSecret이 배포 도구에서 빠지면 Secret이 함께 사라질 수 있다는 점을 알고 정책을 고른다.

### ClusterSecretStore를 여러 팀이 함께 쓸 때 위험한 점은요?

어느 네임스페이스에서든 ExternalSecret을 만들 수 있는 사람은 그 store의 자격 증명이 읽을 수 있는 모든 비밀을 꺼낼 수 있다. RBAC는 ExternalSecret 생성 권한만 보고 그 안의 키 이름은 보지 않기 때문이다. store의 `conditions`로 쓸 수 있는 네임스페이스를 좁히고, 저장소 쪽 IAM 권한도 팀 경로로 제한한다. 가장 단순한 방법은 팀마다 네임스페이스 SecretStore와 전용 역할을 두는 것이다.

### ESO, Sealed Secrets, SOPS는 어떻게 고르나요?

원본을 어디에 둘지로 고른다. 외부 저장소가 있고 교체를 배포와 떼어 두고 싶으면 ESO, 외부 저장소 없이 git만으로 끝내고 싶으면 클러스터 키로 봉인하는 Sealed Secrets나 파일 값을 암호화하는 SOPS다. Sealed Secrets는 컨트롤러 키 백업이 운영의 핵심이고, SOPS는 배포 도구가 복호화를 맡는다. etcd에 값이 남으면 안 되면 CSI 드라이버를 쓴다.
