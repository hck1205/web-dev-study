이 문제를 처음 보면 "가벼운 사람끼리 짝을 지으면 많이 태울 수 있겠지"라는 생각이 먼저 든다. 그렇게 짜면 예시 몇 개는 통과하고, 제출하면 틀린다. 무작위 입력 3000개로 돌려 보니 500개 넘게 틀렸다. 짝을 짓는 기준을 어디에 두느냐가 이 문제의 전부다.

[LeetCode 881. Boats to Save People](https://leetcode.com/problems/boats-to-save-people/)은 정렬과 양 끝 투 포인터, 그리고 탐욕법(greedy, 매 순간 가장 좋아 보이는 선택을 하는 방법)이 만나는 문제다. 양 끝에서 좁혀 오는 투 포인터의 기본은 [투 포인터 패턴 글](/posts/two-pointers-pattern)과 [Two Sum II](/posts/leetcode-two-sum-ii)에서 봤다. 탐욕법이 언제 맞는지 따지는 일반론은 [탐욕 알고리즘 글](/posts/greedy-algorithms)에 있다. 이 글은 완전 탐색에서 시작해 네 가지 풀이를 보고, "가장 무거운 사람을 가장 가벼운 사람과 태운다"가 왜 최적인지 바꿔치기 논증으로 증명한 뒤, 보트에 세 명이 타면 이 방법이 왜 무너지는지까지 확인한다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 보트 한 척에 두 명, 무게 제한 하나

문제를 내 말로 줄이면 이렇다. `people[i]`는 i번째 사람의 몸무게다. 보트 한 척은 많아야 두 사람을 태우고, 태운 사람 몸무게의 합이 `limit` 이하여야 한다. 모두를 태우는 데 필요한 보트의 최소 개수를 구한다. 모든 사람의 몸무게는 `limit` 이하라서 혼자라면 누구나 탈 수 있다.

손으로 하나 풀어 보자. `limit = 5`다.

```text
people = [3, 5, 3, 4, 1, 2]

5는 누구와도 못 탄다 (가장 가벼운 1과도 6)   → 보트 1: [5]
4는 1과 탈 수 있다 (합 5)                   → 보트 2: [1, 4]
3은 2와 탈 수 있다 (합 5)                   → 보트 3: [2, 3]
남은 3은 혼자                               → 보트 4: [3]

답: 4
```

풀이에 영향을 주는 제약은 이렇다. 사람 수는 최대 5 × 10^4라 O(n²)은 위험하다(25억 번 근처). 몸무게와 `limit`은 3 × 10^4 이하라서, 두 사람 합은 6만을 넘지 않는다. 정수 넘침 걱정은 없다. 그리고 `limit` 범위가 작다는 건 몸무게별로 개수를 세는 배열을 만들 수 있다는 뜻이다. 이건 뒤의 네 번째 풀이에서 쓴다.

## 모든 짝짓기를 다 해 보기

정답을 확실히 얻는 방법부터 만든다. 아직 보트에 안 탄 사람 중 맨 앞 사람을 골라, 혼자 태우거나 같이 탈 수 있는 다른 사람 하나와 태운다. 각 경우를 재귀로 끝까지 해 보고 보트 수가 가장 적은 것을 고른다.

```js
// 풀이 1: 완전 탐색 (작은 입력의 검증용)
function numRescueBoats(people, limit) {
  const n = people.length;
  const used = new Array(n).fill(false);
  let best = Infinity;
  const go = (boats) => {
    const i = used.indexOf(false);           // 아직 안 탄 첫 사람
    if (i < 0) { best = Math.min(best, boats); return; }
    used[i] = true;
    go(boats + 1);                           // i 혼자 탄다
    for (let j = i + 1; j < n; j++) {        // i와 j가 같이 탄다
      if (!used[j] && people[i] + people[j] <= limit) {
        used[j] = true;
        go(boats + 1);
        used[j] = false;
      }
    }
    used[i] = false;
  };
  go(0);
  return best;
}
```

경우의 수는 사람들을 "한 명 또는 두 명 묶음"으로 나누는 방법의 수라서 n이 늘면 폭발적으로 늘어난다. 사람 20명이면 237억 가지가 넘는다. 이 풀이의 쓸모는 다른 데 있다. 사람 8명 이하의 무작위 입력 3000개를 만들어 이 풀이의 답과 아래 풀이들의 답을 맞춰 봤다. 아래에서 "맞는다", "틀린다"고 말하는 근거가 이 비교다. 탐욕법은 그럴듯해 보여도 틀리는 경우가 많아서, 작은 입력의 완전 탐색과 맞춰 보는 습관이 특히 쓸모 있다.

## 가벼운 사람끼리 먼저 묶으면 틀린다

자연스럽게 떠오르는 탐욕은 "정렬하고, 가벼운 사람부터 옆 사람과 묶는다"다. 가벼운 사람끼리는 합이 작으니 잘 묶일 것 같다.

```js
// 틀린 탐욕: 정렬 후 이웃끼리 묶기
function adjacentPairs(people, limit) {
  const a = [...people].sort((x, y) => x - y);
  let boats = 0, i = 0;
  while (i < a.length) {
    if (i + 1 < a.length && a[i] + a[i + 1] <= limit) i += 2; // 옆 사람과 같이
    else i++;                                                  // 혼자
    boats++;
  }
  return boats;
}
```

```text
adj wrong 505 /3000
```

완전 탐색과 맞춰 보니 3000개 중 505개가 틀렸다. 가장 작은 반례는 `limit = 5`, `[1, 2, 3, 4]`다. 이웃끼리 묶으면 `[1, 2]`가 한 척, 3과 4는 합이 7이라 따로 두 척, 모두 세 척이다. 정답은 `[1, 4]`, `[2, 3]` 두 척이다. 가벼운 사람 둘이 한 척을 차지하는 바람에, 무거운 사람과 짝이 되어 줄 수 있었던 가벼운 사람을 써 버렸다.

여기서 방향이 보인다. 가벼운 사람은 귀한 자원이다. 누구와도 짝이 될 수 있으니, 짝을 찾기 가장 어려운 무거운 사람에게 먼저 줘야 한다.

## 무거운 사람부터 가장 무거운 짝을 찾아 준다

그 생각을 그대로 옮기면 이렇다. 정렬한 뒤 가장 무거운 사람부터 보트에 태우고, 아직 안 탄 사람 중에서 같이 탈 수 있는 가장 무거운 사람을 찾아 함께 보낸다. 같이 탈 수 있는 사람 중 가장 무거운 사람을 고르는 이유는, 가벼운 사람을 아껴 두기 위해서다.

```js
// 풀이 2: 무거운 사람부터, 같이 탈 수 있는 가장 무거운 짝을 찾는다
function numRescueBoats(people, limit) {
  const a = [...people].sort((x, y) => x - y);
  const used = new Array(a.length).fill(false);
  let boats = 0;
  for (let i = a.length - 1; i >= 0; i--) {
    if (used[i]) continue;
    used[i] = true;                     // 남은 사람 중 가장 무거운 사람
    boats++;
    for (let j = i - 1; j >= 0; j--) {  // 뒤에서부터 보면 처음 맞는 사람이 가장 무겁다
      if (!used[j] && a[i] + a[j] <= limit) { used[j] = true; break; }
    }
  }
  return boats;
}
```

완전 탐색과 3000개 모두 같은 답을 냈다. 하지만 안쪽 반복이 짝을 찾을 때까지 거슬러 올라가니 최악 O(n²)이다. 짝이 없는 사람이 많으면 매번 배열 앞까지 다 본다. 사람 5만 명으로 재 봤다.

```text
무작위 몸무게         1879.40ms
모두 2만 이상(짝 없음) 3941.72ms
```

모두가 혼자 타야 하는 입력에서 4초 가까이 걸렸다. 같은 답을 훨씬 빨리 내려면, "같이 탈 수 있는 가장 무거운 짝"을 찾는 대신 더 단순한 짝을 골라도 되는지 따져 봐야 한다.

## 가장 무거운 사람은 가장 가벼운 사람과 탄다

더 단순한 규칙은 이것이다. 가장 무거운 사람은 가장 가벼운 사람과 같이 탈 수 있는지만 본다.

- 가장 가벼운 사람과도 합이 `limit`을 넘으면, 이 무거운 사람은 누구와도 같이 탈 수 없다. 혼자 탄다.
- 넘지 않으면 둘을 같이 태운다.

정렬된 배열에서 "가장 가벼운 사람"은 왼쪽 끝, "가장 무거운 사람"은 오른쪽 끝이다. 둘을 태우거나 무거운 사람만 태우면 양 끝이 한 칸씩 안으로 들어온다. 양 끝 투 포인터 그대로다.

1. 배열을 오름차순으로 정렬한다.
2. `l = 0`, `r = n - 1`에서 시작한다.
3. `people[l] + people[r] <= limit`이면 `l`을 한 칸 민다(가벼운 사람도 같이 탄다).
4. 어느 경우든 `r`을 한 칸 당기고 보트를 하나 센다(무거운 사람은 이번 보트에 무조건 탄다).
5. `l > r`이 되면 끝이다.

```js
// 풀이 3: 정렬 + 양 끝 투 포인터
function numRescueBoats(people, limit) {
  people.sort((a, b) => a - b);                  // 비교 함수 필수
  let l = 0, r = people.length - 1, boats = 0;
  while (l <= r) {                               // 남은 사람이 있는 동안
    if (people[l] + people[r] <= limit) l++;     // 가장 가벼운 사람이 같이 탈 수 있으면 태운다
    r--;                                         // 가장 무거운 사람은 무조건 이번 보트에
    boats++;
  }
  return boats;
}
```

시간은 정렬 O(n log n)에 투 포인터 O(n)이라 O(n log n)이다. 반복마다 `r`이 반드시 한 칸 줄어드니 반복은 정확히 "보트 수"번, 많아야 n번이다. 공간은 포인터 셋에 정렬의 보조 공간이다. 같은 5만 명 입력으로 재면 이렇다.

```text
무작위 몸무게         15.81ms
모두 2만 이상(짝 없음) 20.99ms
```

풀이 2보다 100배 넘게 빠르다. 그리고 완전 탐색과 3000개 모두 같은 답을 냈다. 그런데 풀이 2는 "같이 탈 수 있는 가장 무거운 짝"을 골랐고, 풀이 3은 "가장 가벼운 사람"을 고른다. 고르는 짝이 다른데 왜 보트 수는 같을까. 이걸 설명하지 못하면 면접에서 "우연히 맞는 거 아닌가요?"에 막힌다.

`l === r`인 마지막 반복도 한번 보자. 그때 조건은 `people[l] * 2 <= limit`인지 보는 셈이고, 참이면 `l++`를 한다. 한 사람을 "자기 자신과" 태우는 이상한 모양이지만, 어느 쪽이든 `r--`로 반복이 끝나고 보트는 하나만 센다. 결과에는 영향이 없다. 의도를 분명히 하고 싶으면 `if (l < r && ...)`로 써도 된다.

### 바꿔치기로 보이는 최적성

증명은 탐욕법에서 자주 쓰는 바꿔치기 논증(exchange argument)이다. "어떤 최적해든 내 선택을 포함하도록 바꿀 수 있고, 바꿔도 보트 수가 늘지 않는다"를 보이면 된다.

가장 무거운 사람을 h, 가장 가벼운 사람을 l이라 하자.

첫째, `h + l > limit`이면 h는 누구와도 못 탄다. l이 가장 가벼우니 다른 누구와 더해도 합이 더 크다. 그러니 어떤 해에서든 h는 혼자 탄다. 풀이 3도 h를 혼자 보낸다. 같은 선택이다.

둘째, `h + l <= limit`인 경우. 최적해 하나를 아무거나 잡는다. 거기서 h와 l이 이미 같은 보트에 있으면 할 일이 없다. 아니라면 h는 누군가 x와 타거나 혼자 타고, l은 누군가 y와 타거나 혼자 탄다. 네 경우 모두 바꿔치기가 된다.

- h는 x와, l은 y와 탄다면: h와 l을 한 보트에, x와 y를 한 보트에 태운다. `x + y <= limit`일까? y는 h보다 가볍거나 같으니 `x + y <= x + h <= limit`이다. 원래 h와 x가 같이 탔으니 `x + h <= limit`이었다. 보트 수는 그대로 두 척이다.
- h는 혼자, l은 y와 탄다면: h와 l을 같이, y를 혼자 태운다. 두 척 그대로다.
- h는 x와, l은 혼자 탄다면: h와 l을 같이, x를 혼자 태운다. 두 척 그대로다.
- 둘 다 혼자라면: h와 l을 같이 태우면 한 척이 준다. 그럴 수는 없으니(최적해였으니까) 이 경우는 생기지 않는다.

그러니 h와 l을 같이 태운 최적해가 언제나 있다. h와 l을 빼고 남은 사람들로 같은 논리를 되풀이하면, 풀이 3이 매번 고르는 선택이 모두 어떤 최적해와 일치한다. 풀이 2가 고르는 "가장 무거운 짝"도 같은 논증으로 최적이라 두 풀이의 보트 수가 같다.

이 논증에서 쓴 사실은 두 개뿐이다. 보트에 두 명까지만 탄다는 것, 그리고 정렬 덕분에 h와 l이 바로 보인다는 것. 앞의 것이 깨지면 증명도 깨진다. 뒤의 "세 명이 탈 수 있다면"에서 실제로 깨지는 입력을 본다.

### Python과 Java의 양 끝 포인터

```python
from typing import List

def num_rescue_boats(people: List[int], limit: int) -> int:
    people.sort()
    l, r, boats = 0, len(people) - 1, 0
    while l <= r:                          # 남은 사람이 있는 동안
        if people[l] + people[r] <= limit:  # 가장 가벼운 사람이 같이 탈 수 있으면
            l += 1
        r -= 1                             # 가장 무거운 사람은 이번 보트에 무조건 탄다
        boats += 1
    return boats
```

Python의 `list.sort()`는 비교 함수 없이 숫자를 숫자 순서로 정렬한다. 입력 리스트를 바꾸니 호출한 쪽에서 원래 순서가 필요하면 `sorted(people)`를 쓴다.

```java
class Solution {
    public int numRescueBoats(int[] people, int limit) {
        Arrays.sort(people);                       // int[]는 숫자 순서로 정렬된다
        int l = 0, r = people.length - 1, boats = 0;
        while (l <= r) {
            if (people[l] + people[r] <= limit) l++; // 합은 최대 6만이라 int로 충분하다
            r--;
            boats++;
        }
        return boats;
    }
}
```

Java의 `Arrays.sort(int[])`는 기본형 배열이라 듀얼 피벗 퀵정렬을 쓰고, 비교 함수를 넘길 수 없다(넘기려면 `Integer[]`로 바꿔야 하고 그만큼 느려진다). 이 문제는 오름차순이면 충분하니 그대로 쓴다. 세 언어 모두 같은 결과를 냈다.

```text

1
1
2
```

`([3, 5, 3, 4, 1, 2], 5)`, `([1, 2], 3)`, `([5], 5)`, `([10, 2, 9], 11)`을 넣은 결과다.

## 몸무게별로 세어 정렬을 없앤다

몸무게가 `limit` 이하의 정수이고 `limit`은 3만 이하다. 그러면 비교 정렬 대신 몸무게마다 사람 수를 세는 배열(`cnt[w]` = 몸무게가 w인 사람 수)을 만들 수 있다. 계수 정렬과 같은 생각이다. 투 포인터는 배열 칸 대신 몸무게 값 위를 움직인다.

```js
// 풀이 4: 몸무게별 개수 + 투 포인터 (정렬 없음)
function numRescueBoats(people, limit) {
  const cnt = new Array(limit + 1).fill(0);
  for (const p of people) cnt[p]++;          // 몸무게마다 몇 명인지
  let l = 1, r = limit, boats = 0, left = people.length;
  while (left > 0) {
    while (cnt[r] === 0) r--;                // 남은 사람 중 가장 무거운 몸무게
    cnt[r]--; left--;                        // 그 사람을 태운다
    while (l <= r && cnt[l] === 0) l++;      // 남은 사람 중 가장 가벼운 몸무게
    if (l <= r && l + r <= limit) { cnt[l]--; left--; } // 같이 탈 수 있으면 태운다
    boats++;
  }
  return boats;
}
```

## 한 사람을 빠뜨리는 코드

### 짝짓기 문제처럼 등호를 뺀다

[Two Sum II](/posts/leetcode-two-sum-ii)나 [Container With Most Water](/posts/leetcode-container-with-most-water)에서는 `l < r`가 맞았다. 두 포인터가 서로 다른 두 칸을 짝짓는 문제였기 때문이다. 여기서는 짝을 못 찾은 사람도 보트를 타야 한다.

```js
while (l < r) { ... }   // 틀림
```

```text
ltBug 3 0 1
```

`[3, 5, 3, 4, 1, 2]`가 4가 아니라 3, `[5]`는 1이 아니라 0이 나왔다. `l === r`일 때 가운데 남은 한 사람을 태우지 않고 끝났다. 투 포인터의 반복 조건은 "포인터 사이에 처리할 원소가 남아 있는가"로 정한다. 이 문제는 원소 하나가 남아도 처리할 일이 있다.

### 몸무게를 문자열 순서로 정렬한다

```text
noCmp 3 2 [ 10, 2, 9 ]
```

`[10, 2, 9]`를 그냥 `sort()`하면 문자열 순서라 `[10, 2, 9]` 그대로다("10"이 "2"보다 앞). 그러면 가장 가벼운 사람 자리에 10이 앉아서 아무도 못 묶이고 3척이 나온다. 정답은 2와 9를 묶은 2척이다. 몸무게가 한 자리 수인 예시에서는 우연히 맞게 정렬되어 안 보인다.

### 가벼운 사람을 기준으로 움직인다

```js
while (l <= r) {
  if (people[l] + people[r] <= limit) r--; // 무거운 사람이 같이 탈 수 있으면
  l++;                                     // 가벼운 사람은 무조건 탄다
  boats++;
}
```

포인터 역할을 뒤집은 코드다. 가벼운 사람이 무거운 사람과 못 타면 가벼운 사람 혼자 보트를 탄다. 그런데 가장 무거운 사람과 못 탄다고 해서 다른 사람과 못 타는 건 아니다. `[1, 2, 3, 4]`, `limit = 4`라면 1은 4와 못 타지만 3과는 탈 수 있다. 이 코드는 1을 혼자 보내 버려서 4척이 나온다. 정답은 `[4]`, `[1, 3]`, `[2]`의 3척이다. "못 타면 혼자 간다"가 성립하는 건 가장 무거운 사람뿐이다. 가장 가벼운 사람과도 못 타면 누구와도 못 타기 때문이다. 어느 쪽 포인터를 무조건 움직일지는 이 비대칭에서 정해진다.

### 몸무게가 소수라면

실무 데이터는 정수가 아닐 때가 많다. kg 단위 소수 몸무게라면 개수 배열은 못 쓰고 정렬 풀이로 돌아가야 한다. 그리고 합을 비교하는 줄에서 부동소수점 오차가 끼어든다.

```text
> 0.1 + 0.2 <= 0.3
false
> 0.1 + 0.2
0.30000000000000004
```

`limit = 0.3`인 보트에 0.1과 0.2가 못 탄다고 나온다. 이런 비교가 문제가 되는 곳에서는 값을 정수 단위(g 단위, 센트 단위)로 바꿔 계산하거나, 작은 허용 오차를 두고 `a + b <= limit + 1e-9`처럼 비교한다. 금액이나 용량처럼 경계에서 한 끗 차이로 판정이 갈리는 문제라면 정수로 바꾸는 쪽이 안전하다.

## 세 명이 탈 수 있다면

꼬리 질문으로 "보트에 k명까지 탈 수 있다면?"이 나온다. 같은 탐욕을 넓히면 "가장 무거운 사람을 태우고, 자리가 남는 동안 가장 가벼운 사람부터 채운다"가 된다.

```js
function greedyK(p, limit, k) {
  const a = [...p].sort((x, y) => x - y);
  let l = 0, r = a.length - 1, boats = 0;
  while (l <= r) {
    let sum = a[r], size = 1;
    r--;                                                    // 가장 무거운 사람
    while (size < k && l <= r && sum + a[l] <= limit) { sum += a[l]; l++; size++; } // 가벼운 사람으로 채운다
    boats++;
  }
  return boats;
}
```

완전 탐색과 맞춰 보니 바로 반례가 나왔다. `k = 3`, `limit = 5`, `[1, 2, 2, 2, 3]`이다.

```text
탐욕: [3, 1] [2, 2] [2]   → 3척
최적: [3, 2] [1, 2, 2]    → 2척
```

탐욕은 3에게 1을 붙였는데, 그다음 2를 더하면 6이라 두 명만 태우고 보냈다. 1을 3에게 쓰는 대신 2를 붙이고 1을 2, 2와 묶었다면 두 척이면 됐다. 두 명일 때는 "h의 짝을 l로 바꿔도 손해가 없다"는 바꿔치기가 성립했지만, 세 명이면 l을 h에게 주는 순간 l이 메워 줄 수 있었던 다른 보트의 빈자리가 사라진다. k명 버전은 사실상 상자 채우기 문제(bin packing)라서, 정해진 방법으로 최적해를 빠르게 구하는 알고리즘이 알려져 있지 않다(NP-난해). 면접에서는 "두 명이라 바꿔치기 증명이 되는 것이고, 세 명 이상이면 이 탐욕은 틀린다, 반례는 이것"이라고 답하면 충분하다.

사람 수가 작으면 정확히 풀 수는 있다. 사람들의 집합을 비트 하나씩으로 나타내는 비트마스크 DP다([비트 조작](/posts/bit-manipulation)). `dp[m]`을 "집합 m의 사람들을 모두 태우는 최소 보트 수"로 두고, m에서 번호가 가장 작은 사람이 탈 보트 하나(m의 부분집합 중 그 사람을 포함하고 한 척에 탈 수 있는 것)를 정해 나머지로 넘긴다.

```js
function minBoatsK(p, limit, k) {
  const n = p.length, full = (1 << n) - 1;
  const ok = new Array(1 << n).fill(false);        // ok[s]: s에 든 사람들이 보트 한 척에 탈 수 있나
  for (let s = 1; s <= full; s++) {
    let w = 0, c = 0;
    for (let i = 0; i < n; i++) if (s & (1 << i)) { w += p[i]; c++; }
    ok[s] = c <= k && w <= limit;
  }
  const dp = new Array(1 << n).fill(Infinity);     // dp[m]: m에 든 사람들을 모두 태우는 최소 보트 수
  dp[0] = 0;
  for (let m = 1; m <= full; m++) {
    const low = m & -m;                            // 아직 안 탄 사람 중 번호가 가장 작은 사람
    for (let s = m; s; s = (s - 1) & m)            // m의 부분집합을 모두 본다
      if ((s & low) && ok[s]) dp[m] = Math.min(dp[m], dp[m ^ s] + 1);
  }
  return dp[full];
}
```

```text
2 4 0
```

`[1, 2, 2, 2, 3]`(k = 3)은 2척, 이 글의 예시(k = 2)는 4척, 빈 입력은 0척이다. 무작위 입력 2만 개를 완전 탐색과 맞춰 봤다. 모든 집합의 모든 부분집합을 보니 O(3^n)이라, 15명에 36ms였고 한 명 늘 때마다 세 배씩 늘어난다. 20명 안팎이 한계다.

### 짝까지 돌려 달라면

같은 루프에서 보트마다 태운 사람을 담으면 된다.

```js
function pairs(people, limit) {
  const a = [...people].sort((x, y) => x - y);
  let l = 0, r = a.length - 1;
  const out = [];
  while (l <= r) {
    if (l < r && a[l] + a[r] <= limit) { out.push([a[l], a[r]]); l++; } // 둘이 탄다
    else out.push([a[r]]);                                             // 혼자 탄다
    r--;
  }
  return out;
}
```

```text
[[5],[1,4],[2,3],[3]]
```

여기서는 `l < r` 검사가 꼭 필요하다. 검사를 빼고 같은 사람들을 `limit = 6`으로 넣으면 `[[1,5],[2,4],[3,3]]`이 나온다. 남은 3 한 사람이 자기 자신과 짝지어져 두 번 담긴 것이다(3 + 3 = 6이라 조건을 통과했다). 개수만 셀 때는 티가 안 나던 `l === r` 문제가 결과를 만들 때 드러난다.

### 무게 제한이 "미만"이라면

`<=`를 `<`로 바꾸면 끝이다. 바꿔치기 증명에서 쓴 부등식이 모두 그대로 성립한다. 경계 조건 하나가 문제 문장에서 바뀌는 경우는 면접에서 자주 나오니, 조건을 코드의 어느 줄이 맡는지 바로 가리킬 수 있어야 한다.

## 가장 무거운 사람이 기준이다

Boats to Save People는 정렬한 뒤 가장 무거운 사람을 무조건 이번 보트에 태우고, 가장 가벼운 사람이 같이 탈 수 있는지만 보는 문제다. 가장 가벼운 사람과도 못 타면 누구와도 못 타기 때문에 무거운 쪽 포인터는 매번 움직이고, 가벼운 쪽은 짝이 될 때만 움직인다. 이 선택이 최적인 이유는 바꿔치기 논증이다. 어떤 최적해든 무거운 사람과 가벼운 사람을 한 보트로 바꿔 태워도 보트 수가 늘지 않는다. 그 논증은 보트에 두 명만 탈 때만 성립해서, 세 명이 되면 같은 탐욕이 `[1, 2, 2, 2, 3]`에서 틀린다. 몸무게 범위가 작으면 개수 배열로 정렬도 없앨 수 있다. 수 하나를 고정하고 양 끝 투 포인터를 돌리는 다음 이야기는 [4Sum](/posts/leetcode-4sum)이다.

## 면접에서 나올 만한 질문

### 왜 가장 무거운 사람부터 처리하나요?

가장 무거운 사람이 짝을 찾기 가장 어렵기 때문이다. 이 사람이 가장 가벼운 사람과도 못 타면 누구와도 못 타니 혼자 보낸다는 결정이 확실하다. 반대로 가장 가벼운 사람은 가장 무거운 사람과 못 타도 다른 사람과는 탈 수 있어서 혼자 보낼 근거가 없다. 그래서 무거운 쪽 포인터를 매번 움직이고 가벼운 쪽은 짝이 될 때만 움직인다.

### 이 탐욕이 최적이라는 걸 어떻게 증명하나요?

바꿔치기 논증이다. 가장 무거운 h와 가장 가벼운 l이 같이 탈 수 있다고 하자. 최적해에서 h가 x와, l이 y와 탄다면 h와 l, x와 y로 바꿔 태운다. y가 h보다 가볍거나 같으니 `x + y <= x + h <= limit`이라 바꿔도 되고 보트 수는 그대로다. 한쪽이 혼자인 경우도 같은 방식으로 바꿀 수 있어서, h와 l을 함께 태운 최적해가 항상 있다.

### 가벼운 사람끼리 먼저 묶으면 왜 틀리나요?

가벼운 사람은 누구와도 짝이 될 수 있는 귀한 자원인데, 그걸 가벼운 사람끼리 써 버리면 무거운 사람이 짝을 잃는다. `limit = 5`, `[1, 2, 3, 4]`에서 이웃끼리 묶으면 `[1, 2]`, `[3]`, `[4]`로 세 척이지만 정답은 `[1, 4]`, `[2, 3]` 두 척이다. 작은 입력 3000개를 완전 탐색과 맞춰 보니 505개가 틀렸다.

### 마지막에 한 사람만 남으면 어떻게 되나요?

짝을 못 찾은 마지막 한 사람도 보트를 타야 하기 때문이다. `l === r`이면 한 사람이 남아 있다. `l < r`로 쓰면 그 사람을 빼먹어서 `[5]`에 0척, `[3, 5, 3, 4, 1, 2]`에 3척이 나온다. 두 원소를 짝짓기만 하는 Two Sum II와 달리 여기는 원소 하나도 처리 대상이다.

### 정렬 없이 더 빠르게 할 수 있나요?

몸무게가 `limit` 이하의 작은 정수라서 몸무게별 개수 배열을 만들 수 있다. 투 포인터를 배열 칸 대신 몸무게 값 위에서 움직이면 O(n + limit)이다. 5만 명 입력에서 정렬 풀이가 16~21ms, 개수 배열 풀이가 1~3.5ms였다. `limit`이 크면 배열을 만들 수 없으니 정렬 풀이로 돌아간다.

### 보트에 세 명까지 탈 수 있다면 같은 방법이 통하나요?

통하지 않는다. "가장 무거운 사람에 가벼운 사람부터 채운다"는 `k = 3`, `limit = 5`, `[1, 2, 2, 2, 3]`에서 3척을 내지만 `[3, 2]`, `[1, 2, 2]`로 2척이면 된다. 바꿔치기 논증이 두 명일 때만 성립하기 때문이다. k명 버전은 상자 채우기 문제라 일반적으로 빠른 정확한 해법이 알려져 있지 않고, 작은 입력이면 비트마스크 DP로 푼다.

### 답만 세는 코드와 짝을 돌려주는 코드는 무엇이 다른가요?

개수만 셀 때는 `l === r`에서 자기 자신과 짝지어도 `r--`로 끝나고 보트는 하나만 세니 결과가 같다. 짝을 담을 때는 `l < r` 검사가 없으면 가운데 남은 사람의 몸무게 두 배가 `limit` 이하일 때 그 사람을 `[3, 3]`처럼 두 번 담는다. 개수 문제에서 통과한 코드를 그대로 확장할 때 이런 경계가 드러난다.
