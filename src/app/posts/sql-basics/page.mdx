새로 받은 서버에 PostgreSQL을 깔고 `psql`로 처음 접속했다. 프롬프트가 깜빡인다. 뭐라도 있나 싶어 테이블 목록을 보는 `\dt`를 쳐 본다.

```text
sqlbasics_tmp=# \dt
Did not find any relations.
```

아무것도 없다. 여기서부터 테이블을 만들고, 행을 넣고, 읽고, 고치고, 지우는 데까지 가 본다. 쓰는 명령은 많지 않다. 다만 명령마다 "이걸 잘못 치면 무슨 일이 생기나"를 같이 알아야 운영 DB 앞에서 손이 덜 떨린다.

기준은 Ubuntu 24.04에 설치한 PostgreSQL 16(16.15)이다. 아래 출력과 에러 메시지는 모두 이 환경에서 실제로 돌린 결과다. SQLD 시험은 Oracle과 SQL Server 문법으로 문제를 내서, 두 DB가 다르게 움직이는 부분은 그때그때 짚고 뒤에서 한 번 더 모았다. 두 DB의 출력은 직접 돌려 볼 수 없어서 동작만 글로 적었다.

## 명령어는 네 묶음으로 나뉜다

SQL 명령은 무엇을 건드리느냐로 네 묶음으로 나눈다. SQLD에서 거의 매번 묻는 분류다.

DDL(Data Definition Language)은 테이블의 모양을 정한다. 집으로 치면 방을 새로 들이고(`CREATE`), 고치고(`ALTER`), 허물고(`DROP`), 문패를 바꾸고(`RENAME`), 가구를 한 번에 다 들어내는(`TRUNCATE`) 일이다. DML(Data Manipulation Language)은 그 안의 행을 다룬다. 읽고(`SELECT`), 넣고(`INSERT`), 고치고(`UPDATE`), 지운다(`DELETE`). 넣거나 고치기를 한 번에 하는 `MERGE`도 여기 들어간다. SQLD 교재는 `SELECT`를 DML에 넣는다. 책에 따라서는 `SELECT`만 따로 DQL(Data Query Language)로 떼기도 한다.

DCL(Data Control Language)은 누가 무엇을 할 수 있는지, 권한을 다룬다(`GRANT`, `REVOKE`). TCL(Transaction Control Language)은 DML로 바꾼 내용을 확정하거나 취소한다(`COMMIT`, `ROLLBACK`, `SAVEPOINT`). 아래 그림에서 점이 흐르는 방향이 각 묶음이 손대는 대상이다.

TCL 화살표가 DML로 가는 게 중요하다. 트랜잭션으로 되돌릴 수 있는 건 기본적으로 DML이다. DDL을 되돌릴 수 있는지는 DB마다 다르다. Oracle은 DDL을 실행하는 순간 그 앞의 작업까지 자동으로 커밋해 버리고, PostgreSQL은 DDL도 트랜잭션 안에서 되돌린다. 이 차이는 뒤의 `DROP`과 `TRUNCATE`에서 다시 본다.

## 빈 DB에 테이블 세 개 만들기

글 전체에서 쓸 작은 쇼핑몰을 만든다. 회원(`users`), 상품(`products`), 주문(`orders`) 세 개다.

```sql
-- 회원
CREATE TABLE users (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- 1, 2, 3 ... 자동으로 매긴다
  email      varchar(100) NOT NULL UNIQUE,                    -- 비어 있으면 안 되고, 겹치면 안 된다
  name       varchar(50)  NOT NULL,
  phone      varchar(20),                                     -- 없어도 된다 (NULL 허용)
  created_at timestamptz  NOT NULL DEFAULT now()              -- 안 넣으면 지금 시각
);

-- 상품
CREATE TABLE products (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  varchar(100) NOT NULL,
  price numeric(10, 0) NOT NULL CHECK (price >= 0),          -- 음수 가격은 막는다
  stock integer NOT NULL DEFAULT 0 CHECK (stock >= 0)
);

-- 주문: 누가(user_id) 무엇을(product_id) 몇 개(quantity) 샀나
CREATE TABLE orders (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    bigint NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  product_id bigint REFERENCES products (id) ON DELETE SET NULL,
  quantity   integer NOT NULL CHECK (quantity > 0),
  status     varchar(20) NOT NULL DEFAULT 'pending',          -- pending, paid, delivered, cancelled
  ordered_at timestamptz NOT NULL DEFAULT now()
);
```

`CREATE TABLE`이 성공하면 psql은 `CREATE TABLE` 한 줄만 돌려준다. 다시 `\dt`를 치면 세 개가 보인다.

```text
          List of relations
 Schema |   Name   | Type  |  Owner
--------+----------+-------+----------
 public | orders   | table | postgres
 public | products | table | postgres
 public | users    | table | postgres
(3 rows)
```

만든 테이블의 모양은 `\d 테이블이름`으로 확인한다. 제약 조건에 붙은 이름(`orders_quantity_check` 같은)은 따로 이름을 주지 않아서 PostgreSQL이 `테이블_컬럼_종류` 규칙으로 지은 것이다. 에러 메시지에 이 이름이 그대로 나온다.

```text
sqlbasics_tmp=# \d orders
                                    Table "public.orders"
   Column   |           Type           | Collation | Nullable |           Default
------------+--------------------------+-----------+----------+------------------------------
 id         | bigint                   |           | not null | generated always as identity
 user_id    | bigint                   |           | not null |
 product_id | bigint                   |           |          |
 quantity   | integer                  |           | not null |
 status     | character varying(20)    |           | not null | 'pending'::character varying
 ordered_at | timestamp with time zone |           | not null | now()
Indexes:
    "orders_pkey" PRIMARY KEY, btree (id)
Check constraints:
    "orders_quantity_check" CHECK (quantity > 0)
Foreign-key constraints:
    "orders_product_id_fkey" FOREIGN KEY (product_id) REFERENCES products(id) ON DELETE SET NULL
    "orders_user_id_fkey" FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
```

`Indexes`에 `orders_pkey`가 있다. `PRIMARY KEY`를 선언하면 PostgreSQL이 그 컬럼에 유니크 인덱스를 자동으로 만든다. `UNIQUE`도 마찬가지다. 반면 외래 키 컬럼(`user_id`)에는 인덱스가 자동으로 생기지 않는다. 회원을 지울 때마다 DB가 그 회원의 주문을 찾아야 하는데, 인덱스가 없으면 `orders`를 처음부터 끝까지 읽는다. 외래 키 컬럼에는 인덱스를 따로 만드는 습관을 들인다. 자세한 건 [인덱스 글](/posts/db-index)에 있다.

## 칸마다 담을 값의 종류 정하기

컬럼마다 타입을 정해야 한다. 자주 쓰는 것만 추리면 문자, 숫자, 날짜, 참·거짓이다.

### 문자: CHAR와 VARCHAR

`varchar(n)`은 최대 n글자까지 담고, 넣은 길이만큼만 저장한다. `char(n)`은 항상 n글자로 맞추고, 모자라면 뒤를 공백으로 채운다. 공백을 채운다는 것 때문에 비교 결과가 달라진다.

```sql
SELECT 'ab'::char(5)    = 'ab   '::char(5)    AS char_eq,     -- 뒤 공백을 무시하고 비교
       'ab'::varchar(5) = 'ab   '::varchar(5) AS varchar_eq,  -- 공백도 글자로 본다
       length('ab'::char(5))       AS char_len,
       octet_length('ab'::char(5)) AS char_bytes,              -- 저장은 5바이트
       '[' || 'ab'::char(5) || ']' AS concat;
```

```text
 char_eq | varchar_eq | char_len | char_bytes | concat
---------+------------+----------+------------+--------
 t       | f          |        2 |          5 | [ab]
(1 row)
```

`char`끼리는 뒤 공백을 무시하고 같다고 본다. `varchar`는 공백도 글자라서 다르다. SQLD에서 나오는 규칙과 같다. Oracle도 CHAR끼리(그리고 CHAR와 문자열 상수) 비교할 때는 짧은 쪽에 공백을 채워 비교하고, 한쪽이라도 VARCHAR2면 공백까지 글자로 본다. PostgreSQL은 `char`를 다른 타입과 이어 붙이거나 비교할 때 뒤 공백을 떼어 버린다. 그래서 `concat`이 `[ab]`로 나왔다.

길이가 정해진 코드(국가 코드 `KR`, 성별 `M`/`F`)가 아니면 `varchar`를 쓴다. PostgreSQL에서는 `char`가 더 빠르지도 않다. PostgreSQL에는 길이 제한이 없는 `text`도 있고 성능은 `varchar`와 같다. 정해진 길이를 넘기면 에러가 난다.

```text
ERROR:  value too long for type character varying(50)
```

MySQL 8은 기본 설정(strict 모드)에서는 똑같이 거절하지만, strict 모드를 끈 서버에서는 경고만 남기고 잘라서 넣는다. 오래된 MySQL 서버에서 데이터가 잘려 있으면 이 설정부터 본다.

### 숫자: INTEGER, BIGINT, NUMERIC

정수는 `integer`(4바이트, 약 ±21억)와 `bigint`(8바이트)를 주로 쓴다. 기본 키처럼 계속 늘어나는 번호는 처음부터 `bigint`로 잡는다. 21억을 넘기는 순간 이렇게 된다.

```sql
SELECT 2147483647::integer + 1;
```

```text
ERROR:  integer out of range
```

돈처럼 오차가 있으면 안 되는 값은 `numeric(p, s)`를 쓴다. p는 전체 자릿수, s는 소수점 아래 자릿수다. `numeric(5, 2)`는 `999.99`까지 담는다.

```sql
SELECT 3.14159::numeric(5,2) AS rounded;  -- 소수 셋째 자리에서 반올림
SELECT 1234.5::numeric(5,2);              -- 정수 부분이 세 자리를 넘는다
```

```text
 rounded
---------
    3.14
(1 row)

ERROR:  numeric field overflow
DETAIL:  A field with precision 5, scale 2 must round to an absolute value less than 10^3.
```

소수 부분은 조용히 반올림되고, 정수 부분이 넘치면 에러가 난다. `real`이나 `double precision` 같은 부동소수점은 2진수로 저장해서 0.1을 정확히 담지 못한다.

```sql
SELECT 0.1::float8 + 0.2::float8 AS float_sum, 0.1::numeric + 0.2::numeric AS numeric_sum;
```

```text
      float_sum      | numeric_sum
---------------------+-------------
 0.30000000000000004 |         0.3
(1 row)
```

Oracle은 숫자를 거의 `NUMBER(p, s)` 하나로 쓰고, SQL Server는 `INT`, `BIGINT`, `DECIMAL(p, s)`을 쓴다. 이름만 다르고 생각은 같다.

### 날짜와 시각: DATE, TIMESTAMP, TIMESTAMPTZ

PostgreSQL의 `date`는 날짜만, `timestamp`는 날짜와 시각을 담는다. `timestamptz`(timestamp with time zone)는 받은 시각을 UTC로 바꿔 저장하고, 꺼낼 때 접속한 세션의 시간대로 바꿔 보여 준다. 같은 값을 세션 시간대만 바꿔서 다시 읽어 보면 차이가 보인다.

```sql
SELECT '2026-10-17 09:00'::timestamp AS ts, '2026-10-17 09:00+09'::timestamptz AS tstz;
SET timezone = 'UTC';   -- 이 세션만 UTC로
SELECT '2026-10-17 09:00'::timestamp AS ts, '2026-10-17 09:00+09'::timestamptz AS tstz;
```

```text
         ts          |          tstz
---------------------+------------------------
 2026-10-17 09:00:00 | 2026-10-17 09:00:00+09
(1 row)

         ts          |          tstz
---------------------+------------------------
 2026-10-17 09:00:00 | 2026-10-17 00:00:00+00
(1 row)
```

`timestamp`는 시간대를 모르니 늘 "9시"다. 이게 한국 9시인지 런던 9시인지는 아무도 모른다. `timestamptz`는 같은 순간을 UTC로 보면 0시라고 정확히 바꿔 준다. 서버가 여러 나라에 있거나 서버 시간대가 바뀔 수 있으면 `timestamptz`를 쓴다. 이 글의 `created_at`, `ordered_at`이 모두 `timestamptz`인 이유다.

SQLD에서 헷갈리는 건 Oracle의 `DATE`다. Oracle의 `DATE`는 이름과 달리 초 단위 시각까지 담는다. 그래서 `WHERE order_date = DATE '2026-10-17'`이라고 쓰면 그날 0시 0분 0초인 행만 나온다. 하루 치를 찾으려면 `>= 그날 AND < 다음 날`로 범위를 쓴다. SQL Server는 `DATE`(날짜만), `DATETIME`, `DATETIME2`를 쓴다.

### 참과 거짓: BOOLEAN

PostgreSQL의 `boolean`은 `true`, `false`, 그리고 `NULL`을 담는다. `'yes'`, `'off'`, `'t'` 같은 문자열도 받아 준다. Oracle은 23ai 전까지 테이블 컬럼에 쓸 BOOLEAN 타입이 없어서 `CHAR(1)`에 `'Y'`/`'N'`을 담는 관습이 있고, SQL Server는 `BIT`(0, 1)를 쓴다.

## 잘못된 값을 DB가 막아 주는 제약 조건

이제 행을 넣는다. 여러 행을 쉼표로 이어 한 번에 넣을 수 있다.

```sql
INSERT INTO users (email, name, phone, created_at) VALUES
  ('kim@example.com',  'kim',  '010-1111-2222', '2026-10-01 09:00+09'),
  ('lee@example.com',  'lee',  NULL,            '2026-10-02 10:30+09'),
  ('park@example.com', 'park', '010-3333-4444', '2026-10-03 14:10+09'),
  ('choi@example.com', 'choi', NULL,            '2026-10-05 20:45+09')
RETURNING id, email;   -- 넣은 행에서 이 컬럼들을 바로 돌려받는다

INSERT INTO products (name, price, stock) VALUES
  ('무선 이어폰', 39000, 10),
  ('충전 케이스', 15000, 0),
  ('이어팁',      5000, 120);

INSERT INTO orders (user_id, product_id, quantity, status, ordered_at) VALUES
  (1, 1, 1, 'delivered', '2026-10-06 11:00+09'),
  (1, 3, 2, 'delivered', '2026-10-06 11:00+09'),
  (2, 2, 1, 'paid',      '2026-10-08 20:15+09'),
  (3, 1, 1, 'cancelled', '2026-10-09 08:40+09'),
  (1, 2, 1, 'pending',   '2026-10-12 23:05+09');
```

```text
 id |      email
----+------------------
  1 | kim@example.com
  2 | lee@example.com
  3 | park@example.com
  4 | choi@example.com
(4 rows)

INSERT 0 4
```

`RETURNING`은 PostgreSQL의 기능이다. 자동으로 매겨진 `id`를 다시 조회하지 않고 바로 받는다. 마지막 줄 `INSERT 0 4`의 4가 넣은 행 수다(앞의 0은 옛날 기능의 흔적이라 늘 0이다). 세 테이블은 지금 이렇다.

```text

----+------------------+------+---------------+------------------------
  1 | kim@example.com  | kim  | 010-1111-2222 | 2026-10-01 09:00:00+09
  2 | lee@example.com  | lee  |               | 2026-10-02 10:30:00+09
  3 | park@example.com | park | 010-3333-4444 | 2026-10-03 14:10:00+09
  4 | choi@example.com | choi |               | 2026-10-05 20:45:00+09
(4 rows)

 id |    name     | price | stock
----+-------------+-------+-------
  1 | 무선 이어폰 | 39000 |    10
  2 | 충전 케이스 | 15000 |     0
  3 | 이어팁      |  5000 |   120
(3 rows)

 id | user_id | product_id | quantity |  status   |       ordered_at
----+---------+------------+----------+-----------+------------------------
  1 |       1 |          1 |        1 | delivered | 2026-10-06 11:00:00+09
  2 |       1 |          3 |        2 | delivered | 2026-10-06 11:00:00+09
  3 |       2 |          2 |        1 | paid      | 2026-10-08 20:15:00+09
  4 |       3 |          1 |        1 | cancelled | 2026-10-09 08:40:00+09

(5 rows)
```

psql은 NULL을 빈칸으로 보여 준다. 빈 문자열과 구분이 안 되니 `\pset null '(null)'`을 쳐 두면 NULL이 `(null)`로 보인다. 아래부터는 이 설정을 켠 상태다.

테이블을 만들 때 걸어 둔 제약 조건은 규칙에 어긋나는 행을 아예 받지 않는다. 일부러 하나씩 어겨 본다.

```sql
INSERT INTO users (email, name) VALUES ('jung@example.com', NULL);     -- NOT NULL
INSERT INTO users (email, name) VALUES ('kim@example.com', 'kim2');    -- UNIQUE
INSERT INTO products (name, price) VALUES ('불량 상품', -100);           -- CHECK
INSERT INTO orders (user_id, product_id, quantity) VALUES (99, 1, 1);  -- FOREIGN KEY
```

```text
ERROR:  null value in column "name" of relation "users" violates not-null constraint
DETAIL:  Failing row contains (5, jung@example.com, null, null, 2026-10-17 11:57:54.783167+09).

ERROR:  duplicate key value violates unique constraint "users_email_key"
DETAIL:  Key (email)=(kim@example.com) already exists.

ERROR:  new row for relation "products" violates check constraint "products_price_check"
DETAIL:  Failing row contains (4, 불량 상품, -100, 0).

ERROR:  insert or update on table "orders" violates foreign key constraint "orders_user_id_fkey"
DETAIL:  Key (user_id)=(99) is not present in table "users".
```

첫 줄은 어긴 규칙과 제약 이름을, `DETAIL`은 문제가 된 값을 알려 준다. 응용 코드에서 에러를 사용자 메시지로 바꿀 때는 이 제약 이름(`users_email_key`)으로 구분하면 된다. 메시지 문장은 버전이나 언어 설정에 따라 바뀔 수 있다.

`DETAIL`의 실패한 행을 보면 `id`가 5, 4로 이미 매겨져 있다. 번호는 시퀀스라는 별도 객체가 나눠 주는데, 한 번 나눠 준 번호는 INSERT가 실패해도 돌려받지 않는다. 그래서 다음에 kim 다음 회원을 넣으면 5가 아니라 7이 나온다. 동시에 여러 요청이 번호를 받아 가도 서로 기다리지 않게 하려는 설계다. 자동 번호에 빈칸이 생기는 건 정상이고, "번호가 연속인지"로 데이터가 빠졌는지 판단하면 안 된다.

`GENERATED ALWAYS`로 만든 `id`에는 값을 직접 넣을 수도 없다.

```text
ERROR:  cannot insert a non-DEFAULT value into column "id"
DETAIL:  Column "id" is an identity column defined as GENERATED ALWAYS.
HINT:  Use OVERRIDING SYSTEM VALUE to override.
```

`GENERATED BY DEFAULT`로 만들면 직접 넣을 수 있지만, 그러면 시퀀스가 그 번호를 모르고 나중에 같은 번호를 나눠 줘서 기본 키 충돌이 난다. 데이터 이관처럼 꼭 필요할 때만 `OVERRIDING SYSTEM VALUE`를 쓰고 시퀀스를 맞춰 둔다.

### 기본 키와 UNIQUE는 무엇이 다른가

둘 다 중복을 막는다. 다른 점은 둘이다. 기본 키(PRIMARY KEY)는 테이블에 하나뿐이고 NULL을 허용하지 않는다(`NOT NULL` + `UNIQUE`). `UNIQUE`는 여러 개 걸 수 있고 NULL을 허용한다. PostgreSQL에서는 `UNIQUE` 컬럼에 NULL이 여러 개 들어갈 수 있다. NULL끼리는 같다고 보지 않기 때문이다. NULL을 하나만 허용하고 싶으면 PostgreSQL 15부터 생긴 `UNIQUE NULLS NOT DISTINCT`를 쓴다. SQL Server는 기본 설정에서 UNIQUE 컬럼에 NULL을 하나만 허용한다. 같은 제약인데 DB마다 다른 대표적인 예다.

### 부모 행이 지워질 때 자식 행은

외래 키는 자식이 없는 부모를 가리키지 못하게 막는다. 반대로 자식이 남아 있는 부모를 지우려 하면 `ON DELETE`에 적은 대로 움직인다.

옵션은 다섯 가지다. `CASCADE`는 자식도 같이 지운다. `SET NULL`은 자식의 외래 키를 NULL로 바꾼다. `SET DEFAULT`는 기본값으로 바꾼다. `RESTRICT`와 `NO ACTION`(기본값)은 지우지 못하게 막는다. 두 옵션의 차이는 검사 시점이다. `RESTRICT`는 바로 검사하고, `NO ACTION`은 문장이 끝날 때 검사해서 `DEFERRABLE`로 트랜잭션 끝까지 미룰 수도 있다. 대부분은 결과가 같다.

트랜잭션 안에서 실제로 지워 보고 되돌린다(`BEGIN`과 `ROLLBACK`은 뒤에서 자세히 본다).

```sql
BEGIN;
DELETE FROM products WHERE id = 3;               -- 이어팁을 지운다 → SET NULL
SELECT id, product_id, status FROM orders ORDER BY id;
DELETE FROM users WHERE id = 1;                  -- kim을 지운다 → CASCADE
SELECT id, user_id, status FROM orders ORDER BY id;
ROLLBACK;                                        -- 전부 없던 일로
```

```text
 id | product_id |  status
----+------------+-----------
  1 |          1 | delivered
  2 |     (null) | delivered
  3 |          2 | paid
  4 |          1 | cancelled
  5 |          2 | paid
(5 rows)

 id | user_id | status
----+---------+-----------
  3 |       2 | paid
  4 |       3 | cancelled
(2 rows)
```

이어팁을 지우자 2번 주문의 `product_id`가 NULL이 됐다. 주문 기록은 남고 상품만 사라졌다. kim을 지우자 kim의 주문 세 건(1, 2, 5번)이 통째로 사라졌다. 문장은 `DELETE FROM users` 하나인데 다른 테이블의 행이 함께 지워졌다. `CASCADE`가 여러 단계로 이어져 있으면 한 줄 지운 게 수만 줄 삭제로 번진다. 주문, 결제처럼 남겨야 하는 기록에는 `CASCADE`를 걸지 않고 기본값(`NO ACTION`)이나 `RESTRICT`로 막아 두는 편이 안전하다. 회원 탈퇴는 행을 지우는 대신 `deleted_at` 같은 컬럼으로 표시하는 경우가 많다.

막아 두면 이렇게 거절한다. 리뷰 테이블을 `RESTRICT`로 만들어 park의 리뷰를 하나 넣고 park을 지워 본다.

```sql
CREATE TABLE reviews (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL REFERENCES users (id) ON DELETE RESTRICT,
  body    text NOT NULL
);
INSERT INTO reviews (user_id, body) VALUES (3, '소리가 좋다');
DELETE FROM users WHERE id = 3;
```

```text
ERROR:  update or delete on table "users" violates foreign key constraint "reviews_user_id_fkey" on table "reviews"
DETAIL:  Key (id)=(3) is still referenced from table "reviews".
```

SQLD는 이 규칙을 참조 무결성 규칙이라는 이름으로 묻는다. 삭제 규칙은 Cascade, Set Null, Set Default, Restrict, No Action이고, 입력 규칙도 있다. 부모가 없는 자식을 넣으려 할 때 부모를 자동으로 만드는 Automatic, 외래 키를 NULL이나 기본값으로 넣는 Set Null과 Set Default, 부모가 있을 때만 넣는 Dependent, 아무것도 안 하는 No Action이다. 실제 DB에서 쓸 수 있는 건 삭제 규칙 쪽이고, 입력 규칙은 모델링 개념으로만 나온다. 확인을 위해 만든 `reviews`는 지운다(`DROP TABLE reviews;`).

처리 순서를 알면 이 에러가 이해된다. 부가세를 붙인 가격으로 거르려고 별칭을 `WHERE`에 썼다.

```sql
SELECT name, price * 1.1 AS with_tax FROM products WHERE with_tax > 10000;
```

```text
ERROR:  column "with_tax" does not exist

                                                             ^
```

`WHERE`를 처리할 때는 `SELECT`가 아직 실행되지 않아서 `with_tax`가 없다. `WHERE price * 1.1 > 10000`으로 식을 다시 쓰거나, 서브쿼리로 한 번 감싼다. 정리하면 처리 순서는 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT이다. SQLD에서 그대로 나온다.

별칭은 `AS`로 붙인다. 컬럼 별칭에서 `AS`는 생략할 수 있다(`price * 1.1 with_tax`). 테이블 별칭은 조인할 때 이름을 짧게 쓰려고 붙인다. Oracle은 테이블 별칭에 `AS`를 쓰면 문법 에러가 난다(`FROM products p`만 된다). PostgreSQL과 SQL Server는 둘 다 받는다.

```sql
-- kim(1번)의 주문별 금액. o, p가 테이블 별칭, product와 total이 컬럼 별칭
SELECT p.name AS product, p.price * o.quantity AS total
FROM orders AS o
JOIN products AS p ON p.id = o.product_id
WHERE o.user_id = 1
ORDER BY total DESC;   -- ORDER BY에서는 별칭을 쓸 수 있다
```

```text
   product   | total
-------------+-------
 무선 이어폰 | 39000
 충전 케이스 | 15000
 이어팁      | 10000
(3 rows)
```

## 원하는 행만 고르는 WHERE

`WHERE`에는 참과 거짓을 내는 조건을 쓴다. 비교 연산자(`=`, `<>`, `<`, `>`, `<=`, `>=`)가 기본이다. "같지 않다"는 `<>`가 표준이고 `!=`도 대부분 받아 준다.

```sql
SELECT name, email FROM users WHERE id >= 3;
```

```text
 name |      email
------+------------------
 park | park@example.com
 choi | choi@example.com
(2 rows)
```

`BETWEEN a AND b`는 a 이상 b 이하다. 양쪽 끝을 포함한다는 게 시험에 나온다. `NOT BETWEEN`은 a보다 작거나 b보다 크다.

```sql
SELECT id, name, price FROM products WHERE price BETWEEN 5000 AND 15000;  -- 5000 <= price <= 15000
```

```text
 id |    name     | price
----+-------------+-------
  2 | 충전 케이스 | 15000
  3 | 이어팁      |  5000
(2 rows)
```

`IN (...)`은 목록 중 하나와 같으면 참이다. `status = 'paid' OR status = 'pending'`과 같다.

```sql
SELECT id, status FROM orders WHERE status IN ('paid', 'pending');
```

```text
 id | status
----+---------
  3 | paid
  5 | pending
(2 rows)
```

`LIKE`는 문자열 패턴이다. `%`는 "글자 아무거나 0개 이상", `_`는 "글자 아무거나 딱 1개"다.

```sql
SELECT name, email FROM users WHERE email LIKE 'k%';  -- k로 시작
SELECT name FROM users WHERE name LIKE '_i%';         -- 두 번째 글자가 i
```

```text
 name |      email
------+-----------------
 kim  | kim@example.com
(1 row)

 name
------
 kim
(1 row)
```

`%`나 `_` 글자 자체를 찾으려면 앞에 이스케이프 문자를 붙인다. PostgreSQL은 기본이 역슬래시이고, `ESCAPE '!'`처럼 바꿀 수 있다. `'a\_b'`는 "a, 밑줄, b"만 찾는다. `LIKE '%이어%'`처럼 앞이 `%`로 열린 패턴은 B-tree 인덱스를 못 쓴다는 것도 알아 둔다. 찾아보기에서 가운데 글자만 알고 단어를 찾을 수 없는 것과 같다.

조건 여러 개는 `AND`, `OR`, `NOT`으로 잇는다. 우선순위는 `NOT` → `AND` → `OR` 순이다. 괄호 없이 섞으면 의도와 다르게 묶인다. "품절이거나 3만 원 넘는 상품 중 재고가 있는 것"을 찾으려고 이렇게 썼다.

```sql
SELECT name, price, stock FROM products WHERE stock = 0 OR price > 30000 AND stock > 0;
```

```text
    name     | price | stock
-------------+-------+-------
 무선 이어폰 | 39000 |    10
 충전 케이스 | 15000 |     0
(2 rows)
```

재고가 0인 충전 케이스가 나왔다. `AND`가 먼저 묶여서 `stock = 0 OR (price > 30000 AND stock > 0)`이 됐기 때문이다. 의도대로 하려면 `(stock = 0 OR price > 30000) AND stock > 0`으로 괄호를 친다. 그러면 무선 이어폰만 남는다. `AND`와 `OR`를 섞을 때는 우선순위를 외우기보다 늘 괄호를 친다.

## NULL은 값이 아니라 모른다는 표시

lee와 choi는 전화번호가 없다. "전화번호가 없는 회원"을 찾으려고 이렇게 쳤다.

```sql
SELECT name, phone FROM users WHERE phone = NULL;
```

```text
 name | phone
------+-------
(0 rows)
```

에러도 없이 0행이다. NULL은 "값이 없음" 또는 "모름"이라는 표시라서, 무엇과 비교해도 결과가 참도 거짓도 아닌 UNKNOWN(모름)이 된다. NULL과 NULL을 비교해도 모름이다. "lee의 번호가 choi의 번호와 같나?" 둘 다 모르니 같은지도 모른다. 그래서 NULL은 `IS NULL`, `IS NOT NULL`로 따로 묻는다.

```sql
SELECT name, phone FROM users WHERE phone IS NULL;
SELECT NULL = NULL AS eq, NULL IS NULL AS is_null;
```

```text
 name | phone
------+--------
 lee  | (null)
 choi | (null)
(2 rows)

   eq   | is_null
--------+---------
 (null) | t
(1 row)
```

`NULL = NULL`의 결과가 `t`도 `f`도 아닌 `(null)`이다. SQL의 조건은 참, 거짓, 모름 세 값을 갖는다. 이걸 3값 논리라고 한다. `WHERE`는 참인 행만 남기니, 모름이 나온 행은 거짓과 똑같이 버려진다. 이게 조용한 버그를 만든다. "kim이 아닌 회원의 번호"를 찾으려고 이렇게 쓰면 어떻게 될까. 아래 그림에서 다음을 누르면 행마다 조건을 따져 본다.

lee와 choi까지 넣으려면 `WHERE phone <> '010-1111-2222' OR phone IS NULL`로 NULL을 따로 챙긴다. PostgreSQL에는 NULL을 하나의 값처럼 비교하는 `IS DISTINCT FROM`도 있다.

`AND`와 `OR`에 모름이 섞이면 이렇게 된다. `FALSE AND 모름`은 하나가 이미 거짓이니 무조건 거짓이다. `TRUE OR 모름`은 하나가 이미 참이니 무조건 참이다. 나머지는 모름이 그대로 남는다.

```sql
SELECT TRUE AND NULL AS t_and_n, FALSE AND NULL AS f_and_n,
       TRUE OR NULL AS t_or_n,   FALSE OR NULL AS f_or_n,
       NOT NULL::boolean AS not_n;
```

```text
 t_and_n | f_and_n | t_or_n | f_or_n | not_n
---------+---------+--------+--------+--------
 (null)  | f       | t      | (null) | (null)
(1 row)
```

규칙이 몇 줄 안 되니 직접 짜 보면 금방 몸에 붙는다. `null`을 모름으로 보고, 연산자 `op`와 값 두 개를 받아 결과를 돌려주는 함수를 완성해 보자. `=`는 둘 중 하나라도 `null`이면 모름이다.

이 규칙이 실무에서 가장 크게 터지는 곳이 `NOT IN`이다. "주문을 한 번도 안 한 회원"을 찾는다.

```sql
SELECT name FROM users WHERE id NOT IN (SELECT user_id FROM orders);
```

```text
 name
------
 choi
(1 row)
```

잘 나온다. 그런데 서브쿼리 결과에 NULL이 하나라도 섞이면 결과가 통째로 사라진다.

```sql
SELECT name FROM users WHERE id NOT IN (1, 2, NULL);
```

```text
 name
------
(0 rows)
```

`id NOT IN (1, 2, NULL)`은 `id <> 1 AND id <> 2 AND id <> NULL`이다. 마지막 `id <> NULL`이 늘 모름이라, 앞의 둘이 참이어도 전체가 모름이 된다. 거짓인 행도 모름인 행도 다 버려지니 0행이다. `orders.user_id`는 `NOT NULL`이라 안전했지만, `product_id`처럼 NULL이 들어갈 수 있는 컬럼으로 `NOT IN`을 쓰면 언젠가 결과가 비어 버린다. 이럴 때는 `NOT EXISTS`를 쓴다. `NOT EXISTS`는 "맞는 행이 있나 없나"만 묻기 때문에 NULL에 흔들리지 않는다.

```sql
SELECT u.name FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
```

NULL은 계산에도 번진다. `price + NULL`은 NULL이다. 집계 함수는 반대로 NULL을 건너뛴다. `count(phone)`은 2(NULL 제외), `count(*)`는 4다. NULL을 다른 값으로 바꿀 때는 표준 함수 `COALESCE(phone, '없음')`을 쓴다. Oracle의 `NVL`, SQL Server의 `ISNULL`이 같은 일을 한다.

Oracle에는 특이한 규칙이 하나 더 있다. 빈 문자열 `''`을 NULL로 취급한다. Oracle에서 `INSERT ... VALUES ('')`로 넣으면 NULL이 들어가고, `WHERE phone = ''`은 늘 0행이다. PostgreSQL, SQL Server, MySQL에서 빈 문자열은 길이 0인 평범한 문자열이다.

```sql
-- PostgreSQL: 빈 문자열은 NULL이 아니다
SELECT ''::text IS NULL AS empty_is_null, length('') AS len;
```

```text
 empty_is_null | len
---------------+-----
 f             |   0
(1 row)
```

## 정렬하고, 겹친 것 빼고, 잘라서 보기

`ORDER BY`는 기본이 오름차순(`ASC`)이고, `DESC`를 붙이면 내림차순이다. 여기서도 NULL이 문제다. NULL을 어디에 둘지 DB마다 다르다.

```sql
SELECT name, phone FROM users ORDER BY phone;        -- 오름차순
SELECT name, phone FROM users ORDER BY phone DESC;   -- 내림차순
```

```text
 name |     phone
------+---------------
 kim  | 010-1111-2222
 park | 010-3333-4444
 lee  | (null)
 choi | (null)
(4 rows)

 name |     phone
------+---------------
 lee  | (null)
 choi | (null)
 park | 010-3333-4444
 kim  | 010-1111-2222
(4 rows)
```

PostgreSQL은 NULL을 가장 큰 값처럼 다룬다. 오름차순이면 맨 뒤, 내림차순이면 맨 앞이다. Oracle도 같다. SQL Server와 MySQL은 반대로 NULL을 가장 작은 값처럼 다뤄서 오름차순이면 맨 앞에 온다. SQLD에서 "Oracle은 NULL을 가장 큰 값, SQL Server는 가장 작은 값으로 본다"로 나온다. PostgreSQL과 Oracle은 `NULLS FIRST`, `NULLS LAST`로 직접 정할 수 있다.

```sql
SELECT name, phone FROM users ORDER BY phone NULLS FIRST;
```

```text
 name |     phone
------+---------------
 lee  | (null)
 choi | (null)
 kim  | 010-1111-2222
 park | 010-3333-4444
(4 rows)
```

`DISTINCT`는 결과에서 완전히 같은 행을 하나만 남긴다. 컬럼이 여러 개면 그 조합이 같아야 겹친 것으로 본다.

```sql
SELECT DISTINCT user_id FROM orders ORDER BY user_id;
SELECT DISTINCT user_id, status FROM orders ORDER BY user_id, status;
```

```text
 user_id
---------
       1
       2
       3
(3 rows)

 user_id |  status
---------+-----------
       1 | delivered
       1 | pending
       2 | paid
       3 | cancelled
(4 rows)
```

두 번째 결과에서 1번 회원이 두 번 나온다. `(1, delivered)`는 주문 1, 2번이 같아서 하나로 합쳐졌지만 `(1, pending)`은 다른 조합이다. `DISTINCT`는 첫 컬럼에만 걸리는 게 아니라 행 전체에 걸린다.

결과를 앞에서 몇 개만 자르는 문법은 DB마다 다르다. PostgreSQL과 MySQL은 `LIMIT n OFFSET m`을 쓴다. 표준 문법은 `OFFSET m ROWS FETCH FIRST n ROWS ONLY`이고, PostgreSQL, Oracle 12c 이상, SQL Server 2012 이상이 받는다. 둘은 결과가 같다.

```sql
-- 최근 주문 순으로, 첫 번째는 건너뛰고 2건
SELECT id, ordered_at FROM orders ORDER BY ordered_at DESC, id DESC LIMIT 2 OFFSET 1;
SELECT id, ordered_at FROM orders ORDER BY ordered_at DESC, id DESC
OFFSET 1 ROWS FETCH FIRST 2 ROWS ONLY;
```

```text
 id |       ordered_at
----+------------------------
  4 | 2026-10-09 08:40:00+09
  3 | 2026-10-08 20:15:00+09
(2 rows)
```

정렬 기준에 `id DESC`를 하나 더 붙인 이유가 있다. 1번과 2번 주문은 시각이 똑같다. 시각만으로 정렬하면 둘의 순서는 정해져 있지 않아서, 페이지를 넘길 때 같은 주문이 두 번 나오거나 아예 빠질 수 있다. 페이지를 자를 때는 정렬 기준이 행 하나를 딱 가리키도록 유일한 컬럼을 끝에 붙인다. `OFFSET`이 커질수록 앞의 행을 다 읽고 버리니 느려진다는 것도 알아 둔다. 이 문제는 [쿼리 튜닝 글](/posts/sql-query-tuning)에서 다룬다.

SQLD에는 옛날 방식도 나온다. Oracle의 `ROWNUM`은 행을 꺼내는 순서대로 1, 2, 3을 붙이는 가상 컬럼이다. `WHERE ROWNUM <= 3`은 되지만 `WHERE ROWNUM = 2`는 0행이다. 첫 행이 1번을 받아야 2번이 생기는데, 첫 행이 조건(`= 2`)에서 탈락하면 다음 행이 다시 1번을 받고 또 탈락하기 때문이다. 그리고 `ROWNUM`은 `ORDER BY`보다 먼저 붙는다. "가격 높은 순 상위 3개"는 정렬한 서브쿼리를 먼저 만들고 바깥에서 `ROWNUM`을 건다. SQL Server는 `SELECT TOP (3) ...`을 쓰고, `TOP (3) WITH TIES`로 3등과 값이 같은 행까지 함께 가져올 수 있다.

## 행 넣기와 있으면 고치기

`INSERT`는 컬럼 목록과 값 목록을 짝지어 쓴다. 컬럼 목록을 빼고 `INSERT INTO users VALUES (...)`로 쓸 수도 있지만, 테이블에 컬럼이 하나 추가되는 순간 깨진다. 컬럼 목록은 늘 적는다. 적지 않은 컬럼에는 `DEFAULT` 값이, 기본값도 없으면 NULL이 들어간다.

```sql
INSERT INTO users (email, name) VALUES ('jung@example.com', 'jung')
RETURNING id, name, created_at;
```

```text
 id | name |          created_at
----+------+-------------------------------
  7 | jung | 2026-10-17 11:58:19.114288+09
(1 row)

INSERT 0 1
```

앞에서 실패한 INSERT 두 번이 5, 6번을 써 버려서 jung은 7번이 됐다. `created_at`은 넣지 않았으니 `DEFAULT now()`가 채웠다.

자주 만나는 요구가 "있으면 고치고, 없으면 넣어라"다. 이걸 UPSERT라고 부른다. 먼저 `SELECT`로 있는지 보고 `INSERT`나 `UPDATE`를 고르면, 두 요청이 동시에 "없네"를 보고 둘 다 넣으려다 한쪽이 중복 에러를 맞는다. PostgreSQL은 `INSERT ... ON CONFLICT`로 이 판단을 문장 하나 안에서 끝낸다.

```sql
-- 이메일이 겹치면 전화번호만 새 값으로 바꾼다
INSERT INTO users (email, name, phone) VALUES ('kim@example.com', 'kim', '010-9999-0000')
ON CONFLICT (email) DO UPDATE SET phone = EXCLUDED.phone   -- EXCLUDED: 넣으려던 행
RETURNING id, email, phone;

-- 겹치면 아무것도 안 한다
INSERT INTO users (email, name) VALUES ('kim@example.com', 'kim')
ON CONFLICT (email) DO NOTHING
RETURNING id;
```

```text
 id |      email      |     phone
----+-----------------+---------------
  1 | kim@example.com | 010-9999-0000
(1 row)

INSERT 0 1

 id
----
(0 rows)

INSERT 0 0
```

`ON CONFLICT (email)`의 괄호 안에는 유니크 제약이나 유니크 인덱스가 걸린 컬럼만 쓸 수 있다. 충돌을 판단할 기준이 있어야 하기 때문이다. MySQL은 같은 일을 `INSERT ... ON DUPLICATE KEY UPDATE phone = VALUES(phone)`으로 한다. 8.0.20부터 `VALUES()` 함수는 폐기 예정이 되어 `INSERT ... VALUES (...) AS new ON DUPLICATE KEY UPDATE phone = new.phone`처럼 별칭을 쓰는 방식을 권한다. MySQL은 충돌 컬럼을 지정하지 않고, 테이블의 모든 유니크 키 중 하나라도 겹치면 UPDATE로 간다. 유니크 키가 여러 개인 테이블에서는 엉뚱한 행이 고쳐질 수 있다.

표준 SQL에는 `MERGE`가 있다. 다른 테이블(원본)의 행을 대상 테이블에 맞춰 넣거나 고친다. Oracle과 SQL Server에서 오래 써 온 문법이고 SQLD에 나온다. PostgreSQL은 15부터 지원한다. 입고 목록을 상품 테이블에 반영해 본다.

```sql
CREATE TABLE incoming_stock (name varchar(100) PRIMARY KEY, price numeric(10,0), stock integer);
INSERT INTO incoming_stock VALUES ('이어팁', 5000, 200), ('케이블', 9000, 50);

MERGE INTO products AS p
USING incoming_stock AS s
  ON p.name = s.name                      -- 이 조건으로 짝을 찾는다
WHEN MATCHED THEN                         -- 짝이 있으면 고친다
  UPDATE SET stock = s.stock
WHEN NOT MATCHED THEN                     -- 없으면 넣는다
  INSERT (name, price, stock) VALUES (s.name, s.price, s.stock);

SELECT * FROM products ORDER BY id;
```

```text
MERGE 2

 id |    name     | price | stock
----+-------------+-------+-------
  1 | 무선 이어폰 | 39000 |    10
  2 | 충전 케이스 | 15000 |    30
  3 | 이어팁      |  5000 |   200
  5 | 케이블      |  9000 |    50
(4 rows)
```

이어팁은 짝이 있어서 재고만 200으로 바뀌었고, 케이블은 새로 들어갔다. 충전 케이스 재고 30은 다음 절의 `UPDATE`로 미리 바꿔 둔 값이다. 케이블이 4번이 아니라 5번인 건 앞에서 실패한 '불량 상품'이 4번을 썼기 때문이다. PostgreSQL의 `MERGE`는 동시에 같은 행을 넣는 요청이 있으면 유니크 위반이 날 수 있다. 한 행씩 들어오는 요청의 UPSERT는 `ON CONFLICT`가 더 안전하고, `MERGE`는 배치로 테이블 두 개를 맞출 때 쓴다.

## 고치고 지우기 전에 BEGIN부터

`UPDATE`는 `SET`으로 바꿀 값을, `WHERE`로 바꿀 행을 정한다. `DELETE`는 `WHERE`에 맞는 행을 지운다.

```sql
UPDATE products SET stock = stock + 30 WHERE id = 2 RETURNING id, name, stock;  -- 충전 케이스 30개 입고
UPDATE orders SET status = 'paid' WHERE id = 5;                                  -- 5번 주문 결제 완료
```

```text
 id |    name     | stock
----+-------------+-------
  2 | 충전 케이스 |    30
(1 row)

UPDATE 1
UPDATE 1
```

`UPDATE 1`의 숫자가 바뀐 행 수다. 한 행만 바꾸려 했는데 이 숫자가 크면 `WHERE`가 잘못된 것이다. 가장 무서운 건 `WHERE`를 빠뜨린 경우다. 문법상 아무 문제가 없어서 DB는 그냥 실행한다.

```sql
BEGIN;
UPDATE products SET price = 0;   -- WHERE를 빠뜨렸다
SELECT id, name, price FROM products ORDER BY id;
ROLLBACK;                        -- 트랜잭션 안이라 되돌릴 수 있다
SELECT id, name, price FROM products ORDER BY id;
```

```text
UPDATE 3

 id |    name     | price
----+-------------+-------
  1 | 무선 이어폰 |     0
  2 | 충전 케이스 |     0
  3 | 이어팁      |     0
(3 rows)

ROLLBACK

 id |    name     | price
----+-------------+-------
  1 | 무선 이어폰 | 39000
  2 | 충전 케이스 | 15000
  3 | 이어팁      |  5000
(3 rows)
```

<Callout kind="warning" title="운영 DB에서 UPDATE나 DELETE를 칠 때">
psql은 기본이 자동 커밋이라 `BEGIN` 없이 친 `UPDATE`는 엔터를 누르는 순간 확정된다. 손으로 고칠 때는 먼저 같은 `WHERE`로 `SELECT count(*)`를 돌려 몇 행인지 보고, `BEGIN;`을 친 다음 `UPDATE`를 실행해 결과 행 수(`UPDATE 1`)를 확인하고, 맞을 때만 `COMMIT;`, 아니면 `ROLLBACK;`한다. `\set ON_ERROR_ROLLBACK interactive`와 함께 `~/.psqlrc`에 `\set AUTOCOMMIT off`를 넣어 두면 매번 `BEGIN`을 치지 않아도 된다. 이미 커밋해 버렸다면 되돌리는 방법은 백업이나 PITR(시점 복구)뿐이다. 트랜잭션을 열어 둔 채 자리를 뜨면 그 행의 잠금이 계속 남아 다른 요청이 기다리니, 확인이 끝나면 바로 닫는다.
</Callout>

`DELETE`도 같다. `DELETE FROM orders;`는 주문을 전부 지우고 `DELETE 6`을 돌려준다. `BEGIN` 안이었다면 `ROLLBACK`으로 돌아온다.

## COMMIT, ROLLBACK, SAVEPOINT로 묶고 되돌리기

트랜잭션은 여러 문장을 "전부 되거나 전부 안 되거나"로 묶는 단위다. 주문을 넣고 재고를 빼는 두 일은 하나만 되면 안 된다. `BEGIN`으로 시작해서 `COMMIT`으로 확정하거나 `ROLLBACK`으로 취소한다. `SAVEPOINT`는 트랜잭션 중간에 꽂는 책갈피다. `ROLLBACK TO SAVEPOINT 이름`으로 그 지점까지만 되돌리고 트랜잭션은 이어 간다.

실제로 돌린 출력은 이렇다. 이어팁 재고는 앞의 `MERGE`로 200이 된 상태다.

```sql

SAVEPOINT before_stock;
UPDATE products SET stock = stock - 300 WHERE id = 3;
ROLLBACK TO SAVEPOINT before_stock;
UPDATE products SET stock = stock - 3 WHERE id = 3 RETURNING id, stock;
COMMIT;
```

```text
(1 row)

ROLLBACK

----+-------
  3 |   197
(1 row)

UPDATE 1
COMMIT
```

`SAVEPOINT` 없이 트랜잭션 안에서 에러가 나면 PostgreSQL은 그 트랜잭션을 통째로 실패 상태로 만든다. 이후의 문장은 전부 거절되고, `COMMIT`을 쳐도 실제로는 `ROLLBACK`이 된다.

```sql
BEGIN;
UPDATE products SET stock = stock - 1 WHERE id = 1;
INSERT INTO orders (user_id, product_id, quantity) VALUES (99, 1, 1);  -- 없는 회원
SELECT stock FROM products WHERE id = 1;
COMMIT;
```

```text
UPDATE 1
ERROR:  insert or update on table "orders" violates foreign key constraint "orders_user_id_fkey"
DETAIL:  Key (user_id)=(99) is not present in table "users".
ERROR:  current transaction is aborted, commands ignored until end of transaction block
ROLLBACK
```

`COMMIT`의 응답이 `ROLLBACK`이다. 앞의 `UPDATE`도 함께 취소됐다. 응용 코드에서 에러를 잡고 같은 트랜잭션으로 계속 쿼리를 보내면 이 에러를 만난다. Oracle과 MySQL은 실패한 문장만 취소하고 트랜잭션은 이어 가는 방식이라, 다른 DB에서 넘어온 코드가 PostgreSQL에서 이 에러를 자주 낸다.

트랜잭션이 언제 시작되는지도 DB마다 다르다. PostgreSQL과 MySQL, SQL Server는 기본이 자동 커밋이다. `BEGIN`(SQL Server는 `BEGIN TRAN`)을 치지 않으면 문장 하나하나가 각자 트랜잭션이 되어 바로 커밋된다. Oracle은 첫 DML을 실행하는 순간 트랜잭션이 저절로 시작되고, `COMMIT`이나 `ROLLBACK`을 칠 때까지 이어진다. SQL*Plus 같은 도구에서 `UPDATE`를 하고 커밋하지 않은 채 접속을 끊었을 때 어떻게 처리되는지는 도구 설정에 따라 다르니, Oracle에서는 늘 명시적으로 끝낸다. 동시에 여러 트랜잭션이 같은 행을 건드릴 때 생기는 일은 [트랜잭션과 격리 수준 글](/posts/db-transaction-isolation)에서 이어서 본다.

## DELETE, TRUNCATE, DROP은 지우는 범위가 다르다

셋 다 "지운다"인데 지우는 대상과 되돌릴 수 있는지가 다르다. `DELETE`는 행을 하나씩 지우는 DML이다. `TRUNCATE`는 테이블 구조는 남기고 행을 한 번에 비우는 DDL이다. `DROP`은 테이블 자체를 없애는 DDL이다. 실습용 로그 테이블로 차이를 본다.

```sql
CREATE TABLE logs (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, msg text);
INSERT INTO logs (msg) VALUES ('a'), ('b'), ('c');

BEGIN;
TRUNCATE logs;
SELECT count(*) FROM logs;   -- 0
ROLLBACK;
SELECT count(*) FROM logs;   -- 다시 3
```

```text
TRUNCATE TABLE
 count
-------
     0
(1 row)

ROLLBACK
 count
-------
     3
(1 row)
```

PostgreSQL에서는 `TRUNCATE`도 트랜잭션 안에서 되돌아온다. Oracle에서는 안 된다. Oracle의 `TRUNCATE`는 DDL이라 실행 전후로 자동 커밋이 일어나고, 되돌릴 방법이 없다. SQLD 문제에서 "TRUNCATE는 ROLLBACK할 수 없다"는 Oracle 기준이다. SQL Server는 명시적 트랜잭션(`BEGIN TRAN`) 안에서 실행한 `TRUNCATE`를 `ROLLBACK`할 수 있다.

자동 번호도 다르게 다룬다. PostgreSQL의 `TRUNCATE`는 기본으로 번호를 이어 가고, `RESTART IDENTITY`를 붙여야 1부터 다시 센다.

```sql
TRUNCATE logs;
INSERT INTO logs (msg) VALUES ('d') RETURNING id;   -- 4
TRUNCATE logs RESTART IDENTITY;
INSERT INTO logs (msg) VALUES ('e') RETURNING id;   -- 1
```

```text
 id
----
  4
(1 row)

 id
----
  1
(1 row)
```

MySQL과 SQL Server의 `TRUNCATE`는 자동 증가 값을 처음으로 되돌린다. `DELETE`로 다 지우면 어느 DB든 번호는 이어진다.

다른 테이블이 외래 키로 가리키는 테이블은 `TRUNCATE`가 거절된다. `DELETE`는 행마다 외래 키를 검사하지만, `TRUNCATE`는 행을 하나씩 보지 않으니 아예 막는다.

```sql
TRUNCATE users;
```

```text
ERROR:  cannot truncate a table referenced in a foreign key constraint
DETAIL:  Table "orders" references "users".
HINT:  Truncate table "orders" at the same time, or use TRUNCATE ... CASCADE.
```

`DROP`도 같은 이유로 거절된다.

```sql
DROP TABLE products;
```

```text
ERROR:  cannot drop table products because other objects depend on it
DETAIL:  constraint orders_product_id_fkey on table orders depends on table products
HINT:  Use DROP ... CASCADE to drop the dependent objects too.
```

`DROP TABLE products CASCADE`는 `orders`를 지우지 않는다. `orders`에 걸린 외래 키 제약만 없앤다. 행 삭제의 `ON DELETE CASCADE`와 이름만 같고 하는 일이 다르다. 그래도 제약이 조용히 사라지니 쓰기 전에 무엇이 지워지는지 확인한다.

PostgreSQL은 `DROP`까지 트랜잭션 안에서 되돌린다. 테이블 생성과 삭제도 트랜잭션 로그에 남기 때문이다.

```sql
BEGIN;
DROP TABLE logs;
\dt          -- logs가 없다
ROLLBACK;
\dt          -- logs가 돌아왔다
```

```text
          List of relations
 Schema |   Name   | Type  |  Owner
--------+----------+-------+----------
 public | logs     | table | postgres
 public | orders   | table | postgres
 public | products | table | postgres
 public | users    | table | postgres
(4 rows)
```

그래서 PostgreSQL에서는 스키마 변경(마이그레이션) 여러 개를 트랜잭션 하나로 묶어서, 중간에 실패하면 전부 되돌릴 수 있다. Oracle과 MySQL은 DDL마다 자동 커밋이 일어나서, 마이그레이션이 중간에 실패하면 반쯤 바뀐 상태가 남는다. 또 Oracle에서 `UPDATE`를 하고 커밋하지 않은 채 `CREATE TABLE`을 치면, 그 `UPDATE`까지 함께 커밋된다. SQLD에 자주 나오는 함정이다.

세 명령을 비교하면 이렇다. 시험에서 표로 외우는 내용이라 한 번 정리한다.

| | DELETE | TRUNCATE | DROP |
|---|---|---|---|
| 분류 | DML | DDL | DDL |
| 지우는 것 | 조건에 맞는 행 | 모든 행 (구조는 남음) | 테이블 자체 |
| WHERE | 쓸 수 있다 | 없다 | 없다 |
| 되돌리기 | 커밋 전이면 된다 | PG·SQL Server는 트랜잭션 안에서 된다, Oracle은 안 된다 | PG·SQL Server는 된다, Oracle은 안 된다 |
| 행 단위 트리거 | 실행된다 | 실행되지 않는다 | 실행되지 않는다 |
| 속도 | 행마다 기록해서 느리다 | 파일을 통째로 비워서 빠르다 | 빠르다 |

속도 차이에는 이유가 있다. `DELETE`는 행마다 삭제 표시를 하고 트랜잭션 로그(WAL)에 남긴다. PostgreSQL에서는 지운 행이 디스크에 그대로 남았다가 `VACUUM`이 치워야 공간이 재사용되니, 큰 테이블을 `DELETE`로 비우면 파일 크기는 줄지 않는다. `TRUNCATE`는 테이블 파일을 새 빈 파일로 바꿔 끼워서 행 수와 상관없이 순식간에 끝나고 공간도 바로 돌려준다. 대신 PostgreSQL의 `TRUNCATE`는 가장 강한 잠금(ACCESS EXCLUSIVE)을 잡는다. 실행되는 동안 그 테이블은 `SELECT`도 기다린다. 운영 중인 테이블에 칠 때는 이 잠금이 오래 열린 트랜잭션 뒤에 줄 서지 않게 `SET lock_timeout = '3s'`를 먼저 걸어 둔다.

## 만든 테이블 고치기 (ALTER와 RENAME)

테이블을 다 만든 뒤에 컬럼을 더하거나 바꾸는 일은 `ALTER TABLE`이 한다. 문법이 DB마다 가장 많이 다른 곳이라 SQLD에서 보기로 자주 비튼다. PostgreSQL에서 먼저 해 본다.

```sql
ALTER TABLE users ADD COLUMN grade varchar(10) NOT NULL DEFAULT 'basic';  -- 컬럼 추가
ALTER TABLE users ALTER COLUMN phone TYPE varchar(30);                    -- 타입 변경
ALTER TABLE users RENAME COLUMN phone TO phone_number;                    -- 컬럼 이름 변경
ALTER TABLE logs RENAME TO app_logs;                                      -- 테이블 이름 변경
ALTER TABLE users DROP COLUMN grade;                                      -- 컬럼 삭제
ALTER TABLE products ADD CONSTRAINT products_name_key UNIQUE (name);      -- 제약 추가
ALTER TABLE products ALTER COLUMN stock DROP DEFAULT;                     -- 기본값 제거
```

성공하면 줄마다 `ALTER TABLE`이 돌아온다. `\d users`로 바뀐 모양을 확인한다.

```text
                                     Table "public.users"
    Column    |           Type           | Collation | Nullable |           Default
--------------+--------------------------+-----------+----------+------------------------------
 id           | bigint                   |           | not null | generated always as identity
 email        | character varying(100)   |           | not null |
 name         | character varying(50)    |           | not null |
 phone_number | character varying(30)    |           |          |
 created_at   | timestamp with time zone |           | not null | now()
Indexes:
    "users_pkey" PRIMARY KEY, btree (id)
    "users_email_key" UNIQUE CONSTRAINT, btree (email)
Referenced by:
    TABLE "orders" CONSTRAINT "orders_user_id_fkey" FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
```

같은 일을 Oracle과 SQL Server에서는 이렇게 쓴다. 실행 결과는 보여 줄 수 없어서 문법만 적었다.

```sql
-- Oracle
ALTER TABLE users ADD (grade VARCHAR2(10) DEFAULT 'basic' NOT NULL);
ALTER TABLE users MODIFY (phone VARCHAR2(30));          -- 타입·NULL 여부·기본값 변경은 MODIFY
ALTER TABLE users RENAME COLUMN phone TO phone_number;
RENAME logs TO app_logs;                                -- 테이블 이름은 RENAME 문 하나로
ALTER TABLE users DROP COLUMN grade;

-- SQL Server
ALTER TABLE users ADD grade VARCHAR(10) NOT NULL DEFAULT 'basic';  -- COLUMN을 쓰지 않는다
ALTER TABLE users ALTER COLUMN phone VARCHAR(30);                  -- 한 번에 한 컬럼만
EXEC sp_rename 'users.phone', 'phone_number', 'COLUMN';            -- 이름 변경은 저장 프로시저로
EXEC sp_rename 'logs', 'app_logs';
ALTER TABLE users DROP COLUMN grade;
```

외울 것은 세 가지다. 컬럼 타입 변경이 Oracle은 `MODIFY`, SQL Server는 `ALTER COLUMN`이다(PostgreSQL은 `ALTER COLUMN ... TYPE`). 이름 변경은 Oracle이 `RENAME A TO B`, SQL Server가 `sp_rename`이다. Oracle은 `ADD`와 `MODIFY`에서 괄호로 여러 컬럼을 한 번에 다룰 수 있고, SQL Server의 `ALTER COLUMN`은 한 번에 하나다. MySQL은 `MODIFY COLUMN`과 `CHANGE COLUMN`(이름까지 변경)을 쓴다.

운영 중인 큰 테이블에 `ALTER`를 칠 때는 잠금을 생각한다. PostgreSQL 11부터는 상수 기본값을 가진 컬럼 추가가 테이블을 다시 쓰지 않아 순식간에 끝난다. 반면 컬럼 타입 변경은 대부분 테이블 전체를 다시 쓰고, 그동안 가장 강한 잠금을 잡는다. `varchar(20)`을 `varchar(30)`으로 늘리는 것처럼 다시 쓸 필요가 없는 변경은 빨리 끝난다.

## 권한 주고 뺏기 (GRANT와 REVOKE)

서비스 응용 계정이나 분석가 계정에 슈퍼유저를 쓰면, 실수 한 번이 테이블 삭제로 이어진다. 필요한 권한만 준다. 상품 테이블만 읽을 수 있는 분석가 계정을 만들어 본다.

```sql
CREATE ROLE analyst LOGIN;                     -- 로그인할 수 있는 역할(사용자)
GRANT SELECT ON products TO analyst;           -- products 읽기만 허락
\dp products                                   -- 권한 확인
```

```text
                                  Access privileges
 Schema |   Name   | Type  |     Access privileges     | Column privileges | Policies
--------+----------+-------+---------------------------+-------------------+----------
 public | products | table | postgres=arwdDxt/postgres+|                   |
        |          |       | analyst=r/postgres        |                   |
(1 row)
```

`analyst=r/postgres`는 "analyst가 r(SELECT) 권한을 가졌고, 준 사람은 postgres"라는 뜻이다. 소유자 줄의 `arwdDxt`는 INSERT(a), SELECT(r), UPDATE(w), DELETE(d), TRUNCATE(D), REFERENCES(x), TRIGGER(t)다. analyst로 바꿔서 해 본다.

```sql
SET ROLE analyst;
SELECT id, name FROM products ORDER BY id LIMIT 2;   -- 된다
SELECT * FROM users;                                 -- 권한 없음
UPDATE products SET price = 1;                       -- SELECT만 받았다
RESET ROLE;
```

```text
 id |    name
----+-------------
  1 | 무선 이어폰
  2 | 충전 케이스
(2 rows)

ERROR:  permission denied for table users
ERROR:  permission denied for table products
```

`REVOKE`로 거둬 가면 읽기도 막힌다.

```sql
REVOKE SELECT ON products FROM analyst;
SET ROLE analyst;
SELECT id FROM products;
```

```text
ERROR:  permission denied for table products
```

사람마다 권한을 하나하나 주면 관리가 어렵다. 그래서 권한 묶음을 역할(ROLE)로 만들고, 사람에게는 역할을 준다. PostgreSQL에서는 사용자도 역할이라 `GRANT reader TO analyst`처럼 역할을 역할에 준다. Oracle도 `CREATE ROLE`과 `GRANT 역할 TO 사용자`를 쓴다.

SQLD에서는 권한을 다시 남에게 줄 수 있게 하는 옵션이 나온다. `GRANT SELECT ON products TO analyst WITH GRANT OPTION`으로 받은 analyst는 다른 사람에게 그 권한을 줄 수 있다. Oracle에서 이렇게 받은 객체 권한을 `REVOKE`하면, analyst가 남에게 준 권한까지 연쇄로 회수된다. 시스템 권한(`CREATE TABLE` 같은)이나 역할을 `WITH ADMIN OPTION`으로 받아서 남에게 준 경우에는, 원래 사람의 권한을 뺏어도 남에게 준 권한은 그대로 남는다. PostgreSQL은 `WITH GRANT OPTION`으로 받은 사람이 남에게 준 권한이 있으면 `REVOKE`가 에러를 내고, `REVOKE ... CASCADE`로 연쇄 회수를 명시해야 한다.

## Oracle과 SQL Server에서는 이렇게 다르다

SQLD는 Oracle과 SQL Server를 기준으로 문제를 내고, 두 DB에서 결과가 달라지는 부분을 자주 묻는다. 위에서 흩어 놓은 것을 한곳에 모은다.

트랜잭션 쪽이 가장 많이 나온다. Oracle은 DDL을 실행하면 그 앞뒤로 자동 커밋이 일어난다. 그래서 커밋 안 한 DML 뒤에 DDL을 치면 DML까지 확정되고, `TRUNCATE`와 `DROP`은 되돌릴 수 없다. SQL Server는 기본이 자동 커밋 모드라 문장마다 바로 확정되지만, `BEGIN TRAN`으로 연 트랜잭션 안에서는 DDL도 `ROLLBACK`된다. `SET IMPLICIT_TRANSACTIONS ON`을 켜면 Oracle처럼 첫 문장에서 트랜잭션이 저절로 시작된다. Oracle은 자동 커밋이 아니라서 첫 DML에서 트랜잭션이 시작되고 `COMMIT`이나 `ROLLBACK`까지 이어진다.

NULL 쪽은 둘이다. Oracle은 빈 문자열을 NULL로 저장한다. 정렬에서 Oracle은 NULL을 가장 큰 값, SQL Server는 가장 작은 값으로 본다.

문법 쪽은 컬럼 변경(Oracle `MODIFY`, SQL Server `ALTER COLUMN`), 이름 변경(Oracle `RENAME A TO B`, SQL Server `sp_rename`), 앞에서 n행 자르기(Oracle `ROWNUM`과 12c부터 `FETCH FIRST`, SQL Server `TOP`과 `OFFSET FETCH`), NULL 대체 함수(Oracle `NVL`, SQL Server `ISNULL`, 표준 `COALESCE`), 문자열 이어 붙이기(Oracle `||`, SQL Server `+`)가 나온다. 날짜 타입은 Oracle `DATE`가 시각까지 담는다는 것만 기억하면 대부분 풀린다.

## 다음은 빈 칸을 채울 차례

빈 DB에서 출발해 테이블 세 개를 만들고, 행을 넣고 읽고 고치고 지웠다. 명령은 DDL, DML, DCL, TCL 네 묶음이고, 그중 트랜잭션으로 되돌릴 수 있는 범위가 DB마다 다르다는 게 실무와 시험 모두에서 가장 자주 부딪히는 지점이다. NULL은 값이 아니라 모름이라서 `=`로 찾을 수 없고, `WHERE`는 모름을 거짓처럼 버린다는 것만 기억해도 조용한 버그를 꽤 피한다. 이제 테이블을 어떻게 나누고 이어야 하는지가 궁금해진다. 그건 [데이터 모델링 글](/posts/sqld-data-modeling)에서 이어 간다.

## 면접에서 나올 만한 질문

### DELETE, TRUNCATE, DROP의 차이를 설명해 주세요

`DELETE`는 조건에 맞는 행을 하나씩 지우는 DML이라 `WHERE`를 쓸 수 있고 커밋 전이면 되돌릴 수 있으며 행 단위 트리거도 실행된다. `TRUNCATE`는 구조는 남기고 모든 행을 한 번에 비우는 DDL이라 빠르고 공간도 바로 돌려준다. `DROP`은 테이블 자체를 없앤다. 되돌리기는 DB마다 다른데, Oracle은 DDL이 자동 커밋돼서 `TRUNCATE`와 `DROP`을 되돌릴 수 없고, PostgreSQL과 SQL Server는 트랜잭션 안에서라면 되돌린다.

### WHERE에서 NULL을 등호로 비교하면 왜 아무 행도 나오지 않나요?

NULL은 값이 아니라 "모름"이라서 무엇과 비교해도 결과가 참도 거짓도 아닌 UNKNOWN이 된다. `WHERE`는 참인 행만 남기니 UNKNOWN인 행은 모두 버려진다. 그래서 NULL은 `IS NULL`, `IS NOT NULL`로 확인한다. 같은 이유로 `col <> 'x'` 같은 조건도 NULL인 행을 조용히 빠뜨리니, NULL을 포함하려면 `OR col IS NULL`을 붙인다.

### NOT IN 서브쿼리를 쓸 때 주의할 점은요?

서브쿼리 결과에 NULL이 하나라도 있으면 결과가 0행이 된다. `x NOT IN (1, NULL)`은 `x <> 1 AND x <> NULL`이고, 뒤쪽이 늘 UNKNOWN이라 전체가 참이 될 수 없기 때문이다. NULL이 들어갈 수 있는 컬럼이면 `NOT EXISTS`를 쓴다. `NOT EXISTS`는 맞는 행이 있는지만 보기 때문에 NULL에 영향을 받지 않는다.

### 기본 키와 유니크 제약은 무엇이 다른가요?

기본 키는 테이블에 하나만 둘 수 있고 NULL을 허용하지 않는다. 유니크 제약은 여러 개 걸 수 있고 NULL을 허용한다. PostgreSQL은 유니크 컬럼에 NULL을 여러 개 허용하고(15부터 `NULLS NOT DISTINCT`로 바꿀 수 있다), SQL Server는 NULL을 하나만 허용한다. 둘 다 내부적으로 유니크 인덱스를 만들어 중복을 검사한다.

### 외래 키에 ON DELETE CASCADE를 걸 때 주의할 점은요?

부모 행 하나를 지우는 문장이 자식, 손자 테이블까지 연쇄로 지운다. 문장은 한 줄인데 수만 행이 사라질 수 있고, 그동안 잠금도 오래 잡는다. 주문이나 결제처럼 남겨야 하는 기록에는 걸지 않고 `RESTRICT`나 기본값 `NO ACTION`으로 막은 뒤, 삭제는 표시 컬럼으로 처리하는 편이 안전하다. 그리고 PostgreSQL은 외래 키 컬럼에 인덱스를 자동으로 만들지 않으니, 부모를 지울 때마다 자식 테이블을 전부 읽지 않게 인덱스를 따로 만든다.

### 트랜잭션 도중 에러가 나면 PostgreSQL은 어떻게 처리하나요?

그 트랜잭션 전체를 실패 상태로 만든다. 이후 문장은 "current transaction is aborted"로 거절되고, `COMMIT`을 보내도 `ROLLBACK`으로 끝난다. 실패한 문장만 취소하고 이어 가고 싶으면 그 앞에 `SAVEPOINT`를 꽂고 에러가 나면 `ROLLBACK TO SAVEPOINT`로 돌아간다. Oracle과 MySQL은 실패한 문장만 취소하는 방식이라, 다른 DB에서 옮겨 온 코드가 이 차이로 자주 깨진다.

### 있으면 수정하고 없으면 넣는 UPSERT는 어떻게 구현하나요?

조회한 뒤 결과에 따라 INSERT나 UPDATE를 고르면 동시 요청 두 개가 같이 "없다"고 보고 둘 다 넣으려다 한쪽이 실패한다. 판단과 쓰기를 문장 하나로 묶어야 한다. PostgreSQL은 `INSERT ... ON CONFLICT (유니크 컬럼) DO UPDATE`, MySQL은 `ON DUPLICATE KEY UPDATE`를 쓰고, 둘 다 유니크 제약이 충돌 판단의 기준이 된다. 표준 `MERGE`는 테이블끼리 맞추는 배치에 쓰고, PostgreSQL에서는 동시 삽입 상황에서 유니크 위반이 날 수 있다.

### TIMESTAMP와 TIMESTAMPTZ 중 무엇을 쓰나요?

대부분 `timestamptz`를 쓴다. `timestamptz`는 받은 시각을 UTC로 바꿔 저장하고 세션 시간대로 보여 주니, 서버나 사용자의 시간대가 달라도 같은 순간을 가리킨다. `timestamp`는 시간대 정보 없이 숫자만 저장해서 어느 나라 시각인지 알 수 없다. 이름과 달리 `timestamptz`도 시간대 이름을 저장하지는 않는다. 사용자가 고른 시간대를 보존해야 하면 컬럼을 따로 둔다.
