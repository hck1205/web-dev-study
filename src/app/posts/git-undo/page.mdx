Git을 쓰다 보면 등이 서늘해지는 순간이 온다. 결제 연동을 하다가 `STRIPE_KEY`가 든 `.env`를 커밋해서 푸시했다. 기능 브랜치에 할 커밋 두 개를 main에 해 버렸다. 커밋을 하나 지우려다 `git reset --hard HEAD~2`를 쳤더니 어제 한 작업까지 사라졌다.

이 셋은 대처법이 전부 다르다. 첫 번째는 Git으로 고치기 전에 키부터 교체해야 하고, 두 번째는 이름표 두 개를 옮기면 끝나고, 세 번째는 사라진 게 아니라 보이지 않을 뿐이라 reflog에서 찾아오면 된다. 되돌리는 명령이 restore, reset, revert, stash, reflog로 여러 개인 건 "실수가 어디에 있느냐"에 따라 고쳐야 할 곳이 다르기 때문이다.

이 글은 먼저 실수의 위치로 명령을 고르는 법을 보고, 작업 트리부터 푸시한 커밋까지 단계별로 되돌린 뒤, stash와 reflog, 잘못된 브랜치에 한 커밋, 지운 파일, 히스토리에 들어간 비밀 값까지 다룬다. 세 구역(작업 트리, 인덱스, 저장소)은 [첫 글](/posts/git-internals-basics)에서 설명했다. 명령은 Ubuntu 24.04의 Git 2.43.0에서 실행했고, `restore`와 `switch`는 2.23부터 있다. 그보다 오래된 Git에서는 같은 일을 `checkout`과 `reset`으로 한다.

## 실수가 어디에 있는지부터 본다

## 파일에서 고친 것을 버린다

작업 트리에서 고쳤지만 add하지 않은 변경은 `git restore`로 버린다. 인덱스에 있는 내용(add한 적이 없으면 마지막 커밋의 내용)으로 파일을 덮어쓴다.

```bash
# 두 파일을 고친 상태
git status -s

# README.md의 변경만 버린다
git restore README.md
git status -s
```

```text
 M README.md
 M server.js

 M server.js
```

`git restore`로 버린 변경은 Git이 어디에도 저장해 두지 않았던 것이라 되살릴 방법이 없다. 에디터의 실행 취소 기록이 마지막 희망이다. 그래서 확신이 없으면 `git stash`로 치워 두는 편이 안전하다.

한 파일 안에서 일부만 버리고 싶으면 `-p`를 붙인다. 바뀐 덩어리마다 버릴지 물어본다.

```bash
# 포트 변경은 남기고 디버그 로그만 버린다
git restore -p server.js
```

```text

index 77aba50..99cf01a 100644
--- a/server.js
+++ b/server.js
@@ -1,4 +1,4 @@
-const port = 3000;
+const port = 8080;
 // route 1
 // route 2
 // route 3
(1/2) Discard this hunk from worktree [y,n,q,a,d,j,J,g,/,e,?]? n
@@ -7,4 +7,5 @@ const port = 3000;
 // route 6
 // route 7
 // route 8
+console.log("DEBUG", process.env);

(2/2) Discard this hunk from worktree [y,n,q,a,d,K,g,/,e,?]? y
```

첫 덩어리(포트 변경)는 `n`으로 남기고, 둘째 덩어리(환경 변수를 통째로 찍는 로그)는 `y`로 버렸다. `git diff`를 다시 보면 포트 변경만 남아 있다.

새로 만든 파일(untracked)은 Git이 모르는 파일이라 restore 대상이 아니다. 빌드 찌꺼기나 임시 파일을 한꺼번에 치울 때는 `git clean`을 쓴다. 지운 파일은 휴지통에 가지 않으니 반드시 `-n`(dry run)으로 먼저 본다.

```bash
# 무엇이 지워질지 미리 본다 (파일만)
git clean -n

# 폴더까지 포함해서 미리 본다
git clean -nd

# 확인했으면 실제로 지운다
git clean -fd
git status -s
```

```text
Would remove tmp.log

Would remove cache/
Would remove tmp.log

Removing cache/
Removing tmp.log

 M server.js
```

`-n` 없이 `-d`만 붙이면 폴더 안의 파일은 안 보여 준다는 데 주의한다. `cache/` 한 줄 아래에 무엇이 들었는지는 직접 확인해야 한다. `.gitignore`에 걸린 파일은 기본으로 건드리지 않고, `-x`를 붙이면 그것까지 지운다. `-x`는 `.env`와 `node_modules`까지 쓸어 가니 거의 쓸 일이 없다. 하나씩 고르려면 `git clean -i`로 대화형 메뉴를 연다.

## add한 것을 내린다

인덱스에 올린 변경을 내리는 건 `git restore --staged`다. 파일의 내용은 건드리지 않고 인덱스만 마지막 커밋의 내용으로 되돌린다. 변경은 작업 트리에 그대로 남는다.

```bash
# 커밋에서 빼고 싶은 파일을 add해 버렸다
git add server.js
git status -s

# 인덱스에서만 내린다
git restore --staged server.js
git status -s
```

```text
M  server.js

 M server.js
```

두 글자 상태가 `M `에서 ` M`으로, 왼쪽에서 오른쪽으로 옮겨 갔다. 인덱스 칸에서 작업 트리 칸으로 내려온 것이다. 이 명령은 안전하다. 내용을 지우지 않는다. 2.23 이전에는 `git reset HEAD server.js`가 같은 일을 했고, 지금도 `git status`의 안내 문구가 오래된 버전에서는 이 명령을 알려 준다.

파일의 변경까지 한 번에 버리려면 `git restore --staged --worktree server.js`다. 이건 되살릴 수 없다는 점에서 앞의 restore와 같다. 다만 add했던 내용은 blob으로 이미 저장되어 있어서, 아래에서 볼 `git fsck`로 찾을 수 있다.

## 방금 한 커밋을 고친다

커밋 메시지를 잘못 썼거나 파일 하나를 빠뜨렸다면 `--amend`로 마지막 커밋을 다시 만든다.

```bash
# 커밋한 뒤에 빠뜨린 한 줄이 생각났다
echo 'module.exports = { port, host };' >> server.js
git add server.js

# 메시지는 그대로 두고 내용만 마지막 커밋에 더한다
git commit --amend --no-edit
git show --stat --format=%s HEAD
```

```text
호스트 설정

 server.js | 2 ++
 1 file changed, 2 insertions(+)
```

커밋을 아예 취소하고 다시 짜고 싶으면 `git reset --soft HEAD~1`이다. 커밋만 없어지고, 그 커밋이 담았던 변경은 인덱스에 올라간 채로 남는다. 바로 다시 커밋할 수 있는 상태다.

```bash
# 마지막 커밋을 취소한다. 변경은 staged 상태로 남는다
git reset --soft HEAD~1
git status -s
git log --oneline
```

```text
M  server.js

f9e2375 README
110dee3 서버 시작
```

amend와 reset 모두 커밋 해시를 바꾸는 일이라 푸시하기 전에만 쓴다. 이미 푸시했다면 아래의 revert로 간다.

## reset은 무엇을 어디까지 옮기나

로컬 커밋 여러 개를 되돌릴 때는 `git reset`을 쓴다. reset은 HEAD가 가리키는 브랜치 이름표를 다른 커밋으로 옮긴다. 옵션은 그다음에 인덱스와 작업 트리를 어디까지 따라 바꿀지를 정한다.

- `--soft`: 브랜치만 옮긴다. 인덱스와 작업 트리는 그대로라 되돌린 커밋들의 변경이 staged로 남는다.
- `--mixed`(기본값): 브랜치를 옮기고 인덱스도 맞춘다. 변경은 작업 트리에만 남는다(unstaged).
- `--hard`: 브랜치, 인덱스, 작업 트리를 모두 그 커밋으로 맞춘다. 커밋하지 않은 변경까지 사라진다.

"로그 1", "로그 2" 두 커밋을 각 옵션으로 되돌려 보면 차이가 보인다. 아래 그림에서 다음을 누르면 세 옵션이 각각 어디까지 바꾸는지 차례로 보여 준다. 초록으로 빛나는 칸이 바뀐 곳이다.

<Callout kind="warning" title="reset --hard와 clean -fd는 커밋하지 않은 것을 지운다">
커밋한 것은 reflog로 되찾을 수 있지만, 한 번도 커밋하거나 add하지 않은 변경과 untracked 파일은 Git 어디에도 없어서 되살릴 수 없다. 치기 전에 `git status`로 남은 변경을 확인하고, 아깝다 싶으면 `git stash -u`로 치워 두거나 `git branch backup`으로 이름표를 하나 붙여 둔다. 이미 쳤다면 커밋은 `git reflog`에서, add했던 파일은 `git fsck --lost-found`에서 찾는다. 커밋하지 않은 변경만 지키면서 되돌리고 싶으면 `--hard` 대신 `git reset --keep`을 쓴다. 지워질 변경이 있으면 멈춘다.
</Callout>

## 푸시한 커밋은 반대 커밋으로 되돌린다

## 병합을 revert하면 다시 합칠 때 함정이 있다

요청 제한 미들웨어 브랜치를 main에 병합했는데 장애가 나서 병합째로 되돌려야 한다. 병합 커밋은 부모가 둘이라 "어느 쪽으로 되돌릴지"를 알려 줘야 한다.

```bash
# 병합 커밋을 그냥 revert하려고 하면
git revert --no-edit HEAD

# 첫 번째 부모(병합 전의 main) 기준으로 되돌린다
git revert --no-edit -m 1 HEAD
```

```text
error: commit 11e08a228b905ef5f5131eacdaa5f32241e42363 is a merge but no -m option was given.
fatal: revert failed

[main b14bde1] Revert "Merge branch 'feature/rate-limit'"
 1 file changed, 1 deletion(-)
 delete mode 100644 limit.js
```

`-m 1`은 "첫 번째 부모와 같은 상태로 만들어라", 즉 브랜치에서 들어온 변경을 모두 빼라는 뜻이다. main에 병합한 기능을 빼는 경우는 거의 언제나 1이다.

함정은 그다음이다. 브랜치에서 버그를 고쳐 다시 병합하면, 처음에 들어왔다가 revert로 빠진 변경은 돌아오지 않는다.

```bash
# 기능 브랜치에서 고치고 다시 병합
git switch -q feature/rate-limit
printf 'const LIMIT = 100;\n' > limit.config.js
git add limit.config.js
git commit -qm "제한 값 설정"
git switch -q main
git merge --no-ff --no-edit feature/rate-limit
ls
```

```text
Merge made by the 'ort' strategy.
 limit.config.js | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 limit.config.js

README.md
limit.config.js
server.js
```

새로 고친 `limit.config.js`만 들어오고 미들웨어 본체 `limit.js`는 없다. Git이 보기에 처음 병합한 "요청 제한 미들웨어" 커밋은 이미 main의 조상이다. 그래서 두 번째 병합의 공통 조상이 그 커밋 이후가 되고, 그 뒤에 새로 생긴 커밋만 합친다. revert가 지운 것은 "main 쪽의 변경"으로 취급되어 그대로 남는다. 병합을 되돌리면 히스토리가 아니라 내용만 되돌린다는 걸 잊으면 생기는 일이다.

고치는 방법은 revert를 revert하는 것이다. 다시 병합하기 전에 그 revert 커밋을 되돌려서 빠진 변경을 되살린다.

```bash
# 잘못된 두 번째 병합은 버리고 (아직 푸시 전)
git reset -q --hard HEAD~1

# 병합 revert 커밋(b14bde1)을 되돌린다
git revert --no-edit b14bde1
ls

# 그다음 브랜치를 다시 병합한다
git merge --no-ff --no-edit feature/rate-limit
ls
```

```text
[main 049ec40] Reapply "Merge branch 'feature/rate-limit'"
 1 file changed, 1 insertion(+)
 create mode 100644 limit.js

README.md
limit.js
server.js

Merge made by the 'ort' strategy.
 limit.config.js | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 limit.config.js

README.md
limit.config.js
limit.js
server.js
```

revert 커밋을 revert하면 2.43부터는 메시지가 `Reapply "..."`로 붙는다. 그 전 버전에서는 `Revert "Revert ..."`로 나온다. 이제 `limit.js`와 `limit.config.js`가 다 있다. 이런 혼란이 싫어서, 병합된 기능을 끌 때는 revert 대신 기능 플래그로 끄는 팀도 많다.

## 잠깐 치워 두기

작업하다가 급한 버그 수정 요청이 왔는데 지금 변경은 커밋하기엔 어중간하다. `git stash`는 작업 트리와 인덱스의 변경을 따로 떼어 저장하고 깨끗한 상태로 만든다. 저장한 것은 스택처럼 쌓인다.

```bash
# 포트를 바꾸던 중이고, 새 메모 파일도 있다
git status -s

# 이름을 붙여서 치운다. 기본으로는 추적 중인 파일만 치운다
git stash push -m "포트 바꾸던 중"
git status -s

# untracked 파일까지 치우려면 -u
git stash push -u -m "메모 파일까지"
git status -s

# 쌓인 목록
git stash list
```

```text

?? notes.md

?? notes.md
```

## reset --hard 뒤에 사라진 커밋 찾기

처음 상황의 세 번째로 돌아간다. `git reset --hard HEAD~2`로 커밋 두 개가 사라졌다. 정확히는 main 이름표가 두 칸 뒤로 갔을 뿐, 커밋 객체는 `.git/objects`에 그대로 있다. 문제는 그 커밋의 해시를 모른다는 것이다. 그걸 알려 주는 게 reflog다. Git은 HEAD와 브랜치가 움직일 때마다 어디에서 어디로 갔는지 `.git/logs`에 적어 둔다. 다음을 누르면 찾아오는 과정을 따라간다.

맨 윗줄이 방금 한 reset이고, 그 바로 아래 `HEAD@{1}`이 reset 직전의 1c17a6f다. 이름표를 붙여 살린다.

```bash
# 이름표를 붙여 붙잡아 두고
git branch rescue 'HEAD@{1}'
git log --oneline -3 rescue

# main을 그리로 되돌린 뒤 임시 이름표는 지운다
git reset --hard rescue
git branch -d rescue
```

```text

0d8de3c 로그 1
3b10bfd README

HEAD is now at 1c17a6f 로그 2
Deleted branch rescue (was 1c17a6f).
```

reflog에서 바로 `git reset --hard 'HEAD@{1}'`을 해도 된다. 다만 reset을 하면 reflog에 줄이 하나 더 쌓이면서 번호가 밀린다. 헷갈리지 않게 해시를 직접 쓰거나 이름표부터 붙이는 습관이 안전하다. 시간으로 찾을 수도 있다. `git reflog --date=iso`로 시각을 보고, `main@{1.hour.ago}`나 `main@{yesterday}`처럼 "그 시점에 main이 있던 곳"을 가리킬 수 있다.

reflog에는 몇 가지 한계가 있다.

- 로컬에만 있다. 클론을 새로 받으면 reflog는 비어 있고, 다른 사람의 reflog는 볼 수 없다.
- 영원하지 않다. 기본값으로 브랜치에서 닿는 커밋의 기록은 90일(`gc.reflogExpire`), 닿지 않는 커밋의 기록은 30일(`gc.reflogExpireUnreachable`)이 지나면 gc 때 지워진다. 기록이 지워지고 나면 그 커밋도 gc가 정리한다.
- 커밋만 지킨다. 한 번도 커밋하지 않은 변경은 reflog에 없다.

마지막 경우에도 add까지는 했다면 희망이 있다. add하는 순간 내용이 blob으로 저장되기 때문이다. `git fsck --lost-found`는 어디에서도 가리키지 않는 객체를 찾아 `.git/lost-found`에 모아 준다.

```bash
# 새 파일을 add만 하고 커밋하기 전에 reset --hard를 쳐 버렸다
echo 'const secretFeature = true;' > feature.js
git add feature.js
git reset --hard
git status -s

# 어디서도 가리키지 않는 객체를 찾는다
git fsck --lost-found

# 찾은 blob의 내용
git show a3ee690c8f8c8b43fae21040ef31a0181c3e93ea
```

```text
HEAD is now at 1c17a6f 로그 2

dangling blob a3ee690c8f8c8b43fae21040ef31a0181c3e93ea

const secretFeature = true;
```

`dangling blob`이 add했던 파일 내용이다. 파일 이름은 tree에 있었는데 tree를 만들기 전에 날렸으니 이름은 없다. 찾은 blob이 여러 개라면 하나씩 열어 보고 `git show 해시 > feature.js`로 꺼낸다. `dangling commit`이 나오면 그건 날아간 커밋(실수로 drop한 stash도 여기 나온다)이다.

## 엉뚱한 브랜치에 커밋했을 때

로그인 기능 커밋 두 개를 `feature/login`이 아니라 main에 했다. 아직 푸시하지 않았다면 이름표 두 개만 옮기면 된다.

```bash
# main이 원격보다 두 커밋 앞서 있다
git status -sb
git log --oneline -3

# 지금 위치에 새 브랜치 이름표를 붙인다 (커밋이 이 이름표로 살아남는다)
git branch feature/login

# main은 원격 위치로 되돌린다
git reset --hard origin/main

# 작업은 새 브랜치에서 이어 간다
git switch feature/login
git log --oneline --graph --decorate --all
```

```text
## main...origin/main [ahead 2]

8412066 로그인 검증
8129a47 로그인 폼
a75bb4a 서버 시작

HEAD is now at a75bb4a 서버 시작

Switched to branch 'feature/login'

* 8412066 (HEAD -> feature/login) 로그인 검증
* 8129a47 로그인 폼
* a75bb4a (origin/main, main) 서버 시작
```

순서가 중요하다. 이름표를 먼저 붙이고 나서 main을 되돌린다. 거꾸로 하면 커밋이 이름표 없이 떠서 reflog로 찾아야 한다. `reset --hard`이니 커밋하지 않은 변경이 없는지도 먼저 확인한다. 원격 대신 `HEAD~2`처럼 칸 수로 되돌려도 된다.

옮길 브랜치가 이미 있다면 `cherry-pick`으로 커밋을 복사하고 원래 브랜치에서 지운다. main에 한 핫픽스를 `hotfix/1`로 옮기는 예다.

```bash
# 원격 main에서 hotfix/1을 만들고 main의 마지막 커밋을 복사한다
git switch -c hotfix/1 origin/main
git cherry-pick main

# main에서는 그 커밋을 지운다 (푸시 전일 때만)
git switch main
git reset --hard HEAD~1
```

```text
Switched to a new branch 'hotfix/1'
[hotfix/1 2461e34] 핫픽스
 1 file changed, 1 insertion(+)

Switched to branch 'main'
HEAD is now at a75bb4a 서버 시작
```

cherry-pick한 커밋은 내용은 같아도 부모가 다른 새 커밋(`2461e34`)이다. 이미 main에 푸시했다면 main에서 reset하지 말고 revert로 되돌린다.

## 지운 파일을 히스토리에서 꺼내기

예전에 지운 파일이 다시 필요하다. 언제 지웠는지 찾고, 지우기 직전 커밋에서 꺼내 온다.

```bash
# legacy.js를 지운 커밋 (D = deleted)
git log --oneline --diff-filter=D -- legacy.js

# 그 파일이 나온 커밋 전체
git log --oneline --all -- legacy.js
```

```text
f7bd962 레거시 정리

f7bd962 레거시 정리
1e6059b 레거시 유틸
```

지운 커밋(`f7bd962`)에는 파일이 없으니, 그 부모(`f7bd962~1`)에서 꺼낸다.

```bash
# 지우기 직전 커밋의 legacy.js를 작업 트리로 꺼낸다
git restore --source=f7bd962~1 -- legacy.js
git status -s

# 인덱스에도 같이 올리려면 --staged --worktree
git restore --source=f7bd962~1 --staged --worktree -- legacy.js
git status -s
```

```text
?? legacy.js

A  legacy.js
```

`--source`를 주면 restore는 인덱스 대신 그 커밋에서 파일을 가져온다. 기본은 작업 트리만 바꾸니, 인덱스에도 올리려면 `--staged`를 함께 쓴다. 2.23 이전이라면 `git checkout f7bd962~1 -- legacy.js`가 같은 일을 한다(이건 인덱스에도 바로 올린다). 파일을 디스크에 쓰지 않고 내용만 보고 싶으면 `git show f7bd962~1:legacy.js`다.

## 비밀 값을 커밋했을 때

처음 상황의 첫 번째, `.env`에 들어 있던 Stripe 라이브 키를 푸시했다. 여기서 가장 먼저 할 일은 Git 명령이 아니다.

<Callout kind="warning" title="키부터 교체한다">
공개 저장소에 올라간 키는 몇 분 안에 자동 수집기에 긁힌다고 보는 게 맞다. 비공개 저장소라도 클론한 사람, CI 로그, 포크, 백업에 이미 복사됐다. 히스토리를 아무리 깨끗하게 지워도 이미 복사된 것은 회수할 수 없다. Stripe, AWS, GitHub 같은 서비스의 대시보드에서 그 키를 폐기하고 새 키를 발급하는 게 첫 단계이고, 히스토리 정리는 그다음이다.
</Callout>

키를 교체했으면 히스토리를 본다. revert나 `git rm`으로는 부족하다. 최신 커밋에서 파일이 사라질 뿐, 옛 커밋에는 그대로 남아 누구나 꺼내 볼 수 있다.

```bash
# .env를 건드린 커밋
git log --oneline --all -- .env

# 키 문자열이 들어오거나 나간 커밋
git log --oneline --all -S'sk_live_'

# 추적을 멈추고 .gitignore에 넣어 커밋해도
git rm --cached -q .env
echo '.env' >> .gitignore
git add .gitignore
git commit -qm ".env 추적 중단"

# 한 커밋 전의 .env는 여전히 꺼내진다
git show HEAD~1:.env
```

```text
991ec1f 결제 연동

991ec1f 결제 연동

STRIPE_KEY=sk_live_51Hx9aExample
```

히스토리에서 파일을 완전히 빼려면 그 파일이 들어간 모든 커밋을 다시 써야 한다. Git 공식 문서가 권하는 도구는 git filter-repo다. Git에 기본으로 들어 있지 않아서 따로 설치한다. 예전의 `git filter-branch`는 느리고 실수하기 쉬워서 Git 문서 스스로 쓰지 말라고 경고한다.

```bash
# 설치 (Ubuntu 22.04 이상은 패키지가 있다. 또는 pip로)
sudo apt install -y git-filter-repo
# pip install --user git-filter-repo

# 작업하던 저장소에서 바로 돌리면 거부한다
git filter-repo --invert-paths --path .env
```

```text
Aborting: Refusing to destructively overwrite repo history since
this does not look like a fresh clone.
  (expected at most one entry in the reflog for HEAD)
Note: when cloning local repositories, you need to pass
      --no-local to git clone to avoid this issue.
Please operate on a fresh clone instead.  If you want to proceed
anyway, use --force.
```

되돌릴 수 없는 작업이라 새로 받은 클론에서만 하게 막아 둔 것이다. 모든 브랜치와 태그를 그대로 받는 mirror 클론을 새로 만들어서 한다.

```bash
# 모든 ref를 그대로 받는 mirror 클론 (로컬 경로면 --no-local)
git clone --mirror --no-local origin6.git svc-clean.git
cd svc-clean.git

# .env가 들어간 흔적을 모든 커밋에서 지운다
git filter-repo --invert-paths --path .env

# 결과 확인: 해시가 바뀌었고 .env를 건드린 커밋이 없다
git log --oneline --all
git log --oneline --all -- .env
```

```text

        in the manual if you want to push back there.
        (was /tmp/git-demo-4/origin6.git)
```

두 번째 `git log`는 아무것도 출력하지 않았다. "결제 연동" 커밋의 해시가 `991ec1f`에서 `1fa6e91`로 바뀌었고, 그 뒤 커밋도 모두 새 해시가 됐다. 첫 커밋 `3f30aa2`는 `.env`와 상관없어서 그대로다. filter-repo는 실수로 옛 원격에 밀어 넣지 않게 `origin`을 지운다. 중간의 `Note`는 main을 지우라는 안내처럼 보이지만, mirror 클론에서 main은 진짜 브랜치이니 지우지 않는다.

파일이 아니라 코드 안에 박힌 문자열이라면 `--replace-text`로 바꾼다. `원래 문자열==>바꿀 문자열` 형식의 파일을 넘긴다.

```bash
# 이 문자열을 히스토리 전체에서 바꾼다
printf 'sk_live_51Hx9aExample==>***REMOVED***\n' > ../replacements.txt
git filter-repo --replace-text ../replacements.txt
git show HEAD:server.js
```

```text
const port = 3000;
require("dotenv").config();
// 결제 로그
const key = "***REMOVED***";
```

정리한 히스토리를 원격에 강제로 밀어 넣는다.

```bash
# 원격을 다시 연결하고 모든 ref를 덮어쓴다
git remote add origin /tmp/git-demo-4/origin6.git
git push --force --mirror origin
```


이걸로 끝이 아니다. 팀원들의 클론에는 옛 히스토리가 그대로 있다. 그 상태로 pull하면 갈라졌다고 나오고, merge로 받으면 지운 커밋이 다시 섞여 들어온다.

```bash
# 팀원의 예전 클론에서 pull하면
git pull
git status -sb
```


`ahead 3, behind 3`은 옛 커밋 셋과 새 커밋 셋이 서로 다른 커밋이라는 뜻이다. 팀원은 로컬에 따로 남긴 작업을 챙긴 뒤 새로 클론하거나 `git fetch && git reset --hard origin/main`으로 맞춘다. 누군가 옛 히스토리를 다시 푸시하는 순간 정리가 헛수고가 되니 미리 알리고 함께 한다.

호스팅 서비스 쪽에도 흔적이 남는다. GitHub에서는 PR이 참조하는 커밋(`refs/pull/*`)이 강제 푸시로 지워지지 않고, 포크와 캐시된 화면에도 옛 커밋이 남을 수 있다. 완전히 지우려면 서비스의 지원 창구에 요청해야 한다. 이 모든 수고가 있어도 키 교체가 먼저인 이유가 여기 있다.

BFG Repo-Cleaner도 같은 일을 하는 도구로 많이 쓰인다. Java로 돌아가고 사용법이 단순하다. `java -jar bfg.jar --delete-files .env svc-clean.git`나 `--replace-text replacements.txt`처럼 쓰고, 끝난 뒤 그 저장소에서 `git reflog expire --expire=now --all && git gc --prune=now --aggressive`로 옛 객체를 실제로 지운다. BFG는 기본으로 최신 커밋(HEAD)의 내용은 건드리지 않으니, 최신 커밋에서 먼저 파일을 지우고 커밋한 뒤에 돌린다.

다시는 같은 일이 없게 하려면 커밋 전에 막는다. `.env`는 프로젝트를 만들 때 `.gitignore`에 넣고, 예시는 `.env.example`로 올린다. gitleaks 같은 비밀 탐지 도구를 pre-commit 훅이나 CI에 걸고, GitHub를 쓴다면 저장소의 push protection(알려진 형식의 키가 든 푸시를 거부하는 기능)을 켠다.

## 다시 정리하면

되돌리기는 실수가 있는 자리로 명령을 고르는 일이다. 작업 트리의 변경은 `restore`, 인덱스는 `restore --staged`, 푸시하지 않은 커밋은 `reset`(soft는 이름표만, mixed는 인덱스까지, hard는 작업 트리까지), 푸시한 커밋은 반대 커밋을 쌓는 `revert`다. 커밋한 것은 reset으로 날려도 reflog에 해시가 남아 있으니 이름표만 다시 붙이면 되고, add만 한 파일은 `fsck --lost-found`로 찾는다. 커밋도 add도 안 한 변경과, 이미 밖으로 새어 나간 비밀 값만은 Git이 되살려 주지 못한다. 그래서 위험한 명령 앞에서는 `git status`를 먼저 보고, 키가 새면 교체부터 한다. 이런 상황별 대처는 [문제 해결 글](/posts/git-troubleshooting)에 더 모아 두었다.

## 면접에서 나올 만한 질문

### git reset의 --soft, --mixed, --hard는 어떻게 다른가요?

셋 다 HEAD가 가리키는 브랜치를 지정한 커밋으로 옮긴다. --soft는 거기서 멈춰서 되돌린 커밋들의 변경이 인덱스에 staged로 남고, --mixed(기본값)는 인덱스도 그 커밋에 맞춰 변경이 작업 트리에만 남으며, --hard는 작업 트리까지 맞춰 변경이 사라진다. 커밋을 합치거나 다시 짤 때는 soft나 mixed, 정말 버릴 때만 hard를 쓰고, hard 전에는 커밋하지 않은 변경이 없는지 확인한다.

### reset과 revert는 언제 각각 쓰나요?

reset은 브랜치를 과거로 옮겨 커밋을 히스토리에서 빼는 것이라 아직 푸시하지 않은 로컬 커밋에 쓴다. revert는 커밋의 변경을 거꾸로 적용한 새 커밋을 쌓아 히스토리를 고쳐 쓰지 않으므로, 이미 공유된 커밋을 되돌릴 때 쓴다. 푸시한 커밋을 reset하고 강제 푸시하면 그 커밋을 받은 사람들의 히스토리와 어긋난다.

### 병합 커밋은 어떻게 revert하나요? 주의할 점은요?

병합 커밋은 부모가 둘이라 `git revert -m 1 병합커밋`처럼 기준이 될 부모를 지정한다. 1은 병합 전의 main, 즉 브랜치에서 들어온 변경을 빼겠다는 뜻이다. 주의할 점은 revert가 히스토리가 아니라 내용만 되돌린다는 것이다. 같은 브랜치를 나중에 다시 병합하면 이미 조상이 된 원래 커밋은 다시 들어오지 않으니, 재병합 전에 그 revert 커밋을 다시 revert해야 한다.

### reset --hard로 날린 커밋을 되살릴 수 있나요?

커밋했던 것이라면 대부분 된다. reset은 이름표만 옮기고 커밋 객체는 남겨 두므로, `git reflog`에서 reset 직전 줄의 해시를 찾아 `git branch rescue 해시`로 이름표를 붙이거나 `git reset --hard 해시`로 돌아간다. reflog는 로컬에만 있고 기본으로 닿지 않는 커밋 기록은 30일, 닿는 커밋 기록은 90일 뒤 만료된다. 커밋하지 않은 변경은 reflog에 없지만, add했다면 `git fsck --lost-found`로 blob을 찾을 수 있다.

### git restore와 git restore --staged는 무엇이 다른가요?

`git restore 파일`은 작업 트리의 파일을 인덱스 내용으로 덮어써서 add하지 않은 변경을 버린다. 되살릴 수 없다. `git restore --staged 파일`은 인덱스만 HEAD 내용으로 되돌려 add를 취소하고, 파일의 변경은 작업 트리에 남긴다. `--source=커밋`을 주면 그 커밋에서 파일을 가져올 수 있어 지운 파일을 되살릴 때도 쓴다. 둘 다 2.23에서 checkout과 reset의 파일 관련 기능을 나눠 만든 명령이다.

### stash pop과 apply의 차이는 무엇인가요?

둘 다 저장한 변경을 작업 트리에 적용한다. pop은 적용에 성공하면 목록에서 지우고, apply는 목록에 남긴다. pop하다 충돌이 나면 목록에서 지우지 않으니 충돌을 풀고 직접 drop한다. 기본 stash는 untracked 파일을 넣지 않아서 새 파일까지 치우려면 `-u`를 붙이고, 충돌을 피하려면 stash를 만든 커밋에서 새 브랜치로 적용하는 `git stash branch`를 쓴다.

### 비밀 키를 커밋하고 푸시했습니다. 어떻게 하나요?

먼저 그 키를 폐기하고 새로 발급한다. 이미 클론, 포크, CI 로그, 수집 봇에 복사됐을 수 있어서 히스토리 정리만으로는 회수가 안 된다. 그다음 revert나 rm은 옛 커밋에 키를 남기므로 git filter-repo(또는 BFG)로 mirror 클론에서 모든 커밋을 다시 쓰고 강제 푸시한다. 팀원은 새로 클론하거나 원격에 reset으로 맞추고, 호스팅의 PR 참조나 캐시는 지원 요청으로 지우고, 재발 방지로 비밀 탐지 훅과 push protection을 건다.

### 커밋 두 개를 엉뚱한 브랜치(main)에 했습니다. 어떻게 옮기나요?

푸시 전이라면 지금 위치에 `git branch feature/x`로 이름표를 먼저 붙이고, main은 `git reset --hard origin/main`(또는 `HEAD~2`)으로 되돌린 뒤 새 브랜치로 옮겨 간다. 이름표를 먼저 붙여야 커밋이 떠 버리지 않는다. 옮길 브랜치가 이미 있으면 그쪽에서 `git cherry-pick`으로 복사하고 main에서 reset한다. 이미 main에 푸시했다면 main은 revert로 되돌린다.
