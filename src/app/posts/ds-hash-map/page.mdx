글에 나온 단어 수를 세는 코드를 짰다. 빈 객체 하나 만들고 단어를 키로 1씩 더하는, 누구나 처음 쓰는 모양이다.

```js
const text = "the constructor calls the toString method of the constructor";
const counts = {};
for (const w of text.split(" ")) counts[w] = (counts[w] || 0) + 1;
console.log(counts.the, counts.constructor, counts.toString);
```

```text
3 function Object() { [native code] }11 function toString() { [native code] }1
```

`the`는 3으로 맞는데 `constructor`는 숫자가 아니라 함수 소스에 `11`이 붙은 문자열이 됐다. 빈 객체 `{}`도 프로토타입에서 `constructor`와 `toString`을 물려받기 때문에, 처음 읽은 값이 `undefined`가 아니라 함수였다. 함수에 1을 더하니 문자열 연결이 일어났다. 같은 일을 `Map`으로 하면 문제가 없다.

```js
const m = new Map();
for (const w of text.split(" ")) m.set(w, (m.get(w) ?? 0) + 1);
console.log(m.get("the"), m.get("constructor"), m.get("toString"));
```

```text
3 2 1
```

둘 다 "키로 값을 바로 찾는" 해시 테이블이다. 그런데 객체는 원래 프로그램의 구조를 담으려고 만든 것이고, `Map`은 처음부터 임의의 키를 담으려고 만든 것이다. 이 글은 해시 테이블이 메모리에 어떻게 놓여 있는지, 왜 평균 O(1)인지, 그 O(1)이 언제 깨지는지를 직접 구현하고 재 보면서 따라간다. 그 위에서 면접에 자주 나오는 문제를 해시로 풀고, 일부러 충돌을 일으키는 공격까지 본다. 실행 결과는 모두 Node.js 22(V8 12.4)에서 직접 돌린 값이다.

자료구조 시리즈의 다른 글은 [배열과 행렬](/posts/ds-array-matrix), [스택·큐·덱](/posts/ds-stack-queue-deque), [이진 트리와 BST](/posts/ds-binary-tree-bst), [힙](/posts/ds-heap)이고, 전체 지도는 [자료구조 한눈에 보기](/posts/data-structures-overview)에 있다.

## 키를 칸 번호로 바꾸는 함수

배열은 인덱스를 알면 한 번에 그 칸으로 간다. 주소 계산이 `시작 주소 + 인덱스 × 칸 크기` 한 번이라서다. 해시 테이블은 이 성질을 문자열 같은 임의의 키에도 쓰려는 장치다. 키를 숫자로 바꾸는 해시 함수를 두고, 그 숫자를 배열 길이 안으로 줄여서 칸 번호로 쓴다.

```js
// FNV-1a 32비트: 글자마다 XOR하고 소수를 곱한다
function fnv1a(str) {
  let h = 0x811c9dc5;
  for (let i = 0; i < str.length; i++) {
    h ^= str.charCodeAt(i);
    h = Math.imul(h, 0x01000193);
  }
  return h >>> 0;
}

for (const k of ["apple", "banana", "cherry", "melon", "lime", "mango"]) {
  const h = fnv1a(k);
  console.log(k.padEnd(7), String(h).padStart(10), "&7 =", h & 7, " &15 =", h & 15);
}
```

```text
apple    280767167 &7 = 7  &15 = 15
banana  3649609552 &7 = 0  &15 = 0
cherry  1232791672 &7 = 0  &15 = 8
melon   1927437660 &7 = 4  &15 = 12
lime     132336572 &7 = 4  &15 = 12
mango    242548693 &7 = 5  &15 = 5
```

칸이 8개면 `h % 8` 대신 `h & 7`을 쓴다. 칸 수를 2의 거듭제곱으로 잡으면 나머지 연산이 비트 AND 하나로 끝나서다. 대신 해시값의 아래 비트만 보게 되니, 아래 비트까지 고르게 섞는 해시 함수가 필요하다. 좋은 해시 함수에 바라는 건 세 가지 정도다. 같은 키는 언제나 같은 값이 나와야 하고(결정적), 비슷한 키도 전혀 다른 칸으로 흩어져야 하고, 계산이 싸야 한다. 암호학적 해시(SHA-256)는 두 번째 조건은 훌륭하지만 세 번째에서 진다. 해시 테이블은 보통 FNV, MurmurHash, xxHash, SipHash 같은 빠른 해시를 쓴다.

마지막 단계가 중요하다. 칸 번호가 같다고 같은 키는 아니다. 그래서 해시 테이블은 칸 안에 키도 함께 저장하고, 찾을 때 키를 직접 비교해서 확인한다. 해시값이 같은 일(충돌)은 피할 수 없다. 키의 종류는 무한한데 칸은 유한하니까 비둘기집 원리로 반드시 생긴다. 위 표만 봐도 6개 중 `banana`와 `cherry`, `melon`과 `lime`이 같은 칸에 떨어졌다.

## 같은 칸에 두 키가 떨어지면

충돌을 다루는 방법은 크게 둘이다. 칸마다 목록을 달아서 줄을 세우는 체이닝(separate chaining), 그리고 칸을 목록 없이 쓰고 차 있으면 다른 빈칸을 찾아가는 개방 주소법(open addressing)이다.

체이닝은 단순하고 꽉 차도 버틴다. 칸 수보다 키가 많아도 목록이 길어질 뿐이다. 대신 목록 노드가 메모리 여기저기 흩어져서 캐시 효율이 나쁘다. 자바의 `HashMap`이 체이닝을 쓰는데, 자바 8부터는 한 칸의 목록이 8개를 넘어가고 표가 64칸 이상이면 그 칸을 레드-블랙 트리로 바꾼다. 최악의 경우를 O(n)에서 O(log n)으로 막으려는 장치다.

개방 주소법은 목록 없이 배열 하나에 키를 직접 담는다. 가장 단순한 선형 탐사(linear probing)는 자기 칸이 차 있으면 옆 칸, 그다음 칸으로 한 칸씩 간다. 같은 여섯 단어를 넣어 보면 이렇다.

```js
const TOMB = Symbol("tomb");
class LinearProbing {
  constructor(cap) { this.keys = new Array(cap); this.cap = cap; }
  idx(k) { return fnv1a(k) & (this.cap - 1); }
  set(k) {
    let i = this.idx(k);
    const probes = [i];
    while (this.keys[i] !== undefined && this.keys[i] !== TOMB && this.keys[i] !== k) {
      i = (i + 1) & (this.cap - 1); // 다음 칸, 끝이면 0으로
      probes.push(i);
    }
    this.keys[i] = k;
    return probes;
  }
  find(k) {
    let i = this.idx(k);
    const probes = [i];
    while (this.keys[i] !== undefined) { // 빈칸을 만나면 멈춘다
      if (this.keys[i] === k) return { found: true, probes };
      i = (i + 1) & (this.cap - 1);
      probes.push(i);
    }
    return { found: false, probes };
  }
  delete(k, useTomb) {
    const r = this.find(k);
    if (r.found) this.keys[r.probes.at(-1)] = useTomb ? TOMB : undefined;
  }
  show() {
    return [...this.keys].map((k) => (k === undefined ? "·" : k === TOMB ? "†" : k)).join(" ");
  }
}

const words = ["apple", "banana", "cherry", "melon", "lime", "mango"];
const t = new LinearProbing(8);
for (const w of words) console.log("set", w, t.set(w), t.show());

for (const useTomb of [true, false]) {
  const u = new LinearProbing(8);
  for (const w of words) u.set(w);
  u.delete("lime", useTomb);
  console.log(useTomb ? "tomb: " : "empty:", u.show(), u.find("mango"));
}
```

```text
set apple [ 7 ] · · · · · · · apple
set banana [ 0 ] banana · · · · · · apple
set cherry [ 0, 1 ] banana cherry · · · · · apple
set melon [ 4 ] banana cherry · · melon · · apple
set lime [ 4, 5 ] banana cherry · · melon lime · apple
set mango [ 5, 6 ] banana cherry · · melon lime mango apple
tomb:  banana cherry · · melon † mango apple { found: true, probes: [ 5, 6 ] }
empty: banana cherry · · melon · mango apple { found: false, probes: [ 5 ] }
```

`mango`는 자기 칸 5번을 `lime`에게 뺏겨서 6번에 앉았다. `lime`은 원래 4번 키인데 5번에 있다. 이렇게 충돌한 키들이 한 덩어리로 뭉치는 현상을 군집(clustering)이라고 한다. 덩어리가 커질수록 그 근처에 떨어지는 키는 모두 덩어리 끝까지 걸어가야 한다.

지우기가 까다롭다. 찾기는 빈칸을 만나면 "없다"로 멈추는데, `lime`을 지우면서 5번을 그냥 비우면 `mango`를 찾으러 5번에 온 탐색이 거기서 멈춘다.

묘비가 쌓이면 빈칸이 줄어든 것처럼 탐색이 길어진다. 그래서 개방 주소 테이블은 묘비가 일정 비율을 넘으면 통째로 다시 만든다. 개방 주소법은 배열 하나를 연속으로 읽으니 캐시에 유리하고 노드 할당이 없다. 파이썬의 `dict`, 러스트의 `HashMap`(SwissTable 계열), Go 1.24부터의 `map`이 개방 주소 방식이다. 선형 탐사 대신 칸을 건너뛰는 간격을 바꾸는 이차 탐사, 해시를 하나 더 쓰는 이중 해싱도 있는데 모두 군집을 줄이려는 변형이다.

## 얼마나 채우면 느려지나

해시 테이블의 속도를 정하는 숫자는 적재율(load factor) α = 들어 있는 키 수 / 칸 수다. 칸 65,536개짜리 표를 α별로 채우고, 들어 있는 키를 찾을 때(hit)와 없는 키를 찾을 때(miss) 몇 칸을 봤는지 평균을 냈다. 괄호 안은 크누스가 계산한 선형 탐사의 이론값 `(1 + 1/(1−α)) / 2`, `(1 + 1/(1−α)²) / 2`다.

```text
load   chain-hit  probe-hit(theory)   probe-miss(theory)
0.25        1.14         1.20 (1.17)          1.40 (1.39)
0.50        1.27         1.54 (1.50)          2.54 (2.50)
0.75        1.39         2.43 (2.50)          7.52 (8.50)
0.90        1.47         4.74 (5.50)        35.13 (50.50)
0.95        1.48        9.76 (10.50)      345.78 (200.50)
```

체이닝(`chain-hit`)은 α가 0.95가 돼도 1.48칸이다. 이론값 `1 + α/2`와 거의 같다. 선형 탐사는 α 0.5까지는 비슷하다가 0.75부터 없는 키 찾기가 7칸, 0.9에서 35칸, 0.95에서 346칸으로 무너진다. 없는 키는 군집 끝의 빈칸까지 걸어가야 하는데, 꽉 찰수록 군집이 서로 붙어 거대한 덩어리가 되기 때문이다. 0.95 줄의 측정값이 이론보다 큰 건 이론이 칸 수가 무한하다고 가정해서다. 이 구간에서는 덩어리 몇 개가 결과를 좌우해 값이 크게 흔들린다.

그래서 해시 테이블은 α가 기준을 넘기 전에 칸 수를 두 배로 늘리고 모든 키를 새 칸 번호로 다시 넣는다(rehash). 자바 `HashMap`의 기준이 0.75, 파이썬 `dict`가 약 2/3이다. 칸 수가 바뀌면 `h & (칸 수 − 1)`의 결과가 바뀌니 키를 그대로 복사할 수 없고 하나씩 다시 계산해야 한다.

칸을 늘릴 때 키 하나는 원래 자리 i에 남거나 i + 8로 간다. 칸 수를 두 배로 하면 해시에서 보는 비트가 하나 늘 뿐이라서다. 자바 `HashMap`은 이 성질로 목록을 두 갈래로만 나눈다.

다시 넣기는 키 전체를 옮기니 그 한 번은 O(n)이다. 그래도 평균이 O(1)인 이유는 계산해 보면 나온다. 칸 8개에서 시작해 0.75에서 두 배로 늘리며 100만 개를 넣으면 이렇다.

```js
let cap = 8, size = 0, moved = 0, resizes = 0;
for (let i = 0; i < 1_000_000; i++) {
  if (size + 1 > cap * 0.75) { moved += size; cap *= 2; resizes++; } // 기준을 넘으면 두 배로
  size++;
}
console.log({ cap, resizes, moved, movedPerInsert: +(moved / size).toFixed(3) });
```

18번 늘리면서 옮긴 키를 다 더해도 157만 개, 넣은 키 하나당 1.57번이다. 늘릴 때마다 두 배가 되니 옮기는 양이 1/2, 1/4, 1/8 … 의 등비급수로 줄어 합이 상수로 수렴한다. 이걸 분할 상환(amortized) O(1)이라고 부른다. [배열 글](/posts/ds-array-matrix)의 `push`가 같은 계산이다.

평균은 그렇지만 그 한 번은 실제로 느리다. V8의 `Map`에 정수를 200만 개 넣으면서 `set` 한 번이 1ms를 넘긴 순간을 찍었다.

```js
  m.set(i, i);
  const d = Number(process.hrtime.bigint() - t);
  if (d > 1_000_000) slow.push([m.size, (d / 1e6).toFixed(1) + "ms"]);
}
console.log(slow);
```

## 객체와 Map은 같은 해시가 아니다

JS에서 키로 값을 찾는 도구는 객체, `Map`, `Set` 셋이다. 셋 다 해시 테이블로 구현되지만 키를 다루는 규칙이 다르다.

```js
const o = {};
o[1] = "num"; o["1"] = "str";
o[{ id: 1 }] = "a"; o[{ id: 2 }] = "b";
console.log(o);

const m = new Map();
m.set(1, "num").set("1", "str");
m.set([0, 1], "cell");
console.log(m.size, m.get([0, 1]));
m.set(NaN, "nan");
console.log(m.get(NaN), m.get(0), new Map([[-0, "zero"]]).get(0));
```

```text
{ '1': 'str', '[object Object]': 'b' }
3 undefined
nan undefined zero
```

객체의 키는 문자열(과 심볼)뿐이다. 숫자 1은 `"1"`로 바뀌어 같은 키가 되고, 객체 두 개는 모두 `"[object Object]"`가 되어 뒤의 값이 앞의 값을 덮었다. `Map`은 키를 바꾸지 않는다. 1과 `"1"`이 다른 키라 크기가 3이다. 키 비교는 SameValueZero라서 `NaN`끼리 같고 `+0`과 `-0`도 같다.

`m.get([0, 1])`이 `undefined`인 건 흔한 실수다. 객체 키는 내용이 아니라 참조로 비교한다. `set`에 넣은 배열과 `get`에 넘긴 배열은 다른 객체다. 격자 좌표처럼 값으로 비교해야 하는 키는 문자열로 만든다.

```js
const visited = new Set();
visited.add(`${r},${c}`);         // "0,1"
visited.has(`${r},${c}`);         // true
// 또는 정수 하나로: r * cols + c
```

문자열 키는 매번 문자열을 만들어 느리니, 크기를 아는 격자면 `r * cols + c` 같은 정수 키가 더 빠르다.

V8 안에서 둘의 모습도 다르다. 객체는 모양이 정해진 경우를 위해 숨은 클래스(hidden class)로 속성 위치를 고정해 두고, 속성이 계속 추가되거나 지워지면 내부 해시 테이블인 딕셔너리 모드로 바뀐다. 실험용 플래그로 확인할 수 있다.

```js
// fast.js
const a = { x: 1, y: 2 };
console.log("shape object:", %HasFastProperties(a));
const counts = {};
for (let i = 0; i < 2000; i++) counts["user:" + i] = i;
console.log("2000 dynamic keys:", %HasFastProperties(counts));
const b = { x: 1, y: 2, z: 3 };
delete b.x;
console.log("after delete:", %HasFastProperties(b));
```

```bash

node --allow-natives-syntax fast.js
```

```text

```

`{ x, y }`처럼 모양이 고정된 객체는 빠른 속성이지만, 키 2,000개를 동적으로 넣은 객체나 `delete`를 한 번 한 객체는 딕셔너리로 내려갔다. `Map`은 처음부터 해시 테이블이다. V8의 `Map`은 넣은 순서를 기억하는 결정적 해시 테이블(OrderedHashMap)로, 칸 영역과 넣은 순서대로 쌓는 항목 영역을 나눠 두고 칸에서 항목을 체이닝으로 잇는다. 그래서 순회 순서가 넣은 순서와 같다. 객체의 키 순서는 정수처럼 생긴 키가 먼저 오는 다른 규칙을 따르는데, 이건 [객체 메서드 글](/posts/js-object-methods)에서 자세히 다뤘다.

속도는 상황 따라 다르다. 문자열 키 100만 개로 두 번씩 재 봤다.

```js
const keys = Array.from({ length: 1_000_000 }, (_, i) => "user:" + i);
const o = {}, m = new Map();
time("object set", () => { for (const k of keys) o[k] = 1; });
time("Map set", () => { for (const k of keys) m.set(k, 1); });
// get, delete도 같은 모양으로 잰다. time()은 hrtime으로 걸린 ms를 찍는 함수
```

```text
-- round 1
object set            1000 ms
Map set                427 ms
object get             119 ms
Map get                259 ms
object delete          296 ms
Map delete             370 ms
-- round 2
object set             595 ms
Map set                407 ms
object get             138 ms
Map get                265 ms
object delete          245 ms
Map delete             318 ms
```

이 측정에서는 넣기는 `Map`이 빠르고 읽기는 객체가 빨랐다. 키 모양과 개수, V8 버전에 따라 순위가 바뀌는 정도의 차이라서 성능으로 고를 일은 드물다. 고르는 기준은 의미다. 키가 미리 정해진 레코드(`user.name`, `user.age`)는 객체, 키가 데이터인 사전(단어 수, id로 찾는 캐시)은 `Map`이다. `Map`은 크기를 `size`로 바로 알고, 프로토타입 키와 부딪히지 않고, 아무 값이나 키로 쓰고, 넣은 순서대로 순회한다. 객체를 사전으로 써야 한다면 `Object.create(null)`로 프로토타입을 끊고 `Object.hasOwn`으로 확인한다. 키가 객체이고 그 객체가 사라질 때 항목도 사라져야 하면 `WeakMap`인데, 이건 [메모이제이션 글](/posts/js-memoization)에서 캐시와 함께 다뤘다.

JSON은 `Map`을 모른다. `JSON.stringify(new Map([["a", 1]]))`은 `{}`가 된다. 응답으로 보낼 때는 `Object.fromEntries(map)`으로 바꾼다.

## 면접 단골 문제를 해시로 풀기

해시 테이블을 쓰는 문제는 대부분 "이미 본 것을 O(1)에 다시 묻는다"는 한 가지 아이디어다. 이중 반복문의 안쪽 반복을 표 조회 하나로 바꾼다.

### 두 수의 합

배열에서 더해서 `target`이 되는 두 수의 인덱스를 찾는다. 모든 쌍을 보면 O(n²)이다. 한 번 훑으면서 "지금 수와 짝이 되는 수(`target − 지금 수`)를 전에 봤나"를 `Map`에 묻으면 O(n)이다.

```js
function twoSum(nums, target) {
  const seen = new Map(); // 값 → 인덱스
  for (let i = 0; i < nums.length; i++) {
    const need = target - nums[i];
    if (seen.has(need)) return [seen.get(need), i];
    seen.set(nums[i], i); // 확인한 뒤에 넣는다
  }
  return [];
}
console.log(twoSum([3, 8, 4, 1, 6], 10));
```

```text
[ 2, 4 ]
```

### 애너그램끼리 묶기

글자 구성이 같은 단어끼리 묶는다. 같은 그룹이면 같은 키가 나오도록 "대표 키"를 만드는 게 전부다. 글자를 정렬한 문자열이 가장 흔한 키다.

```js
function groupAnagrams(words) {
  const groups = new Map();
  for (const w of words) {
    const key = [...w].sort().join(""); // "tea" → "aet"
    if (!groups.has(key)) groups.set(key, []);
    groups.get(key).push(w);
  }
  return [...groups.values()];
}
console.log(groupAnagrams(["eat", "tea", "tan", "ate", "nat", "bat"]));
```

### 가장 긴 연속 수열

정렬되지 않은 정수 배열에서 연속된 수(4, 5, 6, …)가 가장 길게 이어지는 길이를 O(n)에 구한다. 정렬하면 O(n log n)이라 조건을 못 맞춘다. 모든 수를 `Set`에 넣고, 수열의 시작점(n − 1이 없는 수)에서만 위로 세어 올라간다. 시작점이 아닌 수에서는 세지 않으니 모든 수가 많아야 두 번(넣을 때, 셀 때) 다뤄진다.

## 일부러 충돌을 만드는 공격

해시 테이블의 O(1)은 "키가 칸에 고르게 흩어진다"는 가정 위에 서 있다. 해시 함수가 공개되어 있고 매번 같다면, 공격자는 같은 칸에 떨어지는 키를 미리 계산해서 보낼 수 있다. 그러면 모든 키가 한 목록에 줄을 서고 넣기 하나가 O(n), n개 넣기가 O(n²)이 된다. 2011년 28C3 발표에서 PHP, 자바, 파이썬, 루비 등 여러 언어의 웹 프레임워크가 요청 파라미터를 해시 테이블에 담는 순간 이 공격(hash flooding, HashDoS)에 당한다는 게 알려졌다.

직접 만들어 보면 놀랄 만큼 쉽다. 자바의 `String.hashCode`와 같은 식 `h = h × 31 + c`에서 `"Aa"`와 `"BB"`는 해시가 같다. 두 조각을 이어 붙인 문자열은 어떤 조합이든 해시가 같으니, 조각 k개로 같은 해시를 가진 문자열 2^k개가 나온다.

```js
function weak(s) { // 씨앗 없는 약한 해시
  let h = 0;
  for (let i = 0; i < s.length; i++) h = (Math.imul(h, 31) + s.charCodeAt(i)) | 0;
  return h >>> 0;
}
console.log("Aa", weak("Aa"), "BB", weak("BB"));
function colliding(k) {
  let out = [""];
  for (let i = 0; i < k; i++) out = out.flatMap((s) => [s + "Aa", s + "BB"]);
  return out; // "AaAa…", "AaBB…", "BBAa…", …
}
```

이 키들을 칸 65,536개짜리 체이닝 테이블에 넣고, 같은 개수의 평범한 키와 시간을 비교했다. 세 번째 줄은 같은 공격 키를 프로세스가 뜰 때 무작위로 정한 씨앗(seed)을 섞은 해시로 넣은 경우다.

```text
Aa 2112 BB 2112
  4096 normal keys            8.7ms compares 128
  4096 colliding keys       116.9ms compares 8386560
  4096 colliding+seeded       5.3ms compares 773
 16384 normal keys           38.0ms compares 2125
 16384 colliding keys      1993.2ms compares 134209536
 16384 colliding+seeded      15.9ms compares 10412
 32768 normal keys           39.2ms compares 13620
 32768 colliding keys      9384.8ms compares 536854528
 32768 colliding+seeded      30.0ms compares 39022
```

키 32,768개에 9.4초다. 키 비교 횟수 5억 3,685만은 정확히 32768 × 32767 / 2다. 키는 30글자라 JSON 객체로 만들면 1.1MB(1,146,881바이트)다. 요청 하나로 CPU 코어 하나를 9초 동안 잡아 두는 셈이다. 씨앗을 섞은 해시에서는 같은 키가 30ms로 평범한 키와 다를 게 없다. 공격자가 씨앗을 모르면 어떤 키가 충돌할지 미리 계산할 수 없다. 씨앗은 실행마다 바뀌니 `seeded` 줄의 비교 횟수도 돌릴 때마다 조금씩 다르다.

지금 언어 런타임들은 대부분 무작위 씨앗을 쓴다. 파이썬은 3.3부터 문자열 해시 무작위화가 기본이고, 러스트 `HashMap`은 SipHash-1-3에 무작위 키를 쓴다. V8도 문자열 해시에 씨앗을 쓴다. Node.js는 2017년에 V8 스냅숏 때문에 이 씨앗이 버전마다 고정되어 있던 문제(CVE-2017-11499)를 고친 적이 있다.

런타임이 막아 준다고 끝은 아니다. 직접 만든 해시 테이블, 사용자 입력으로 키를 만드는 캐시, 씨앗 없는 해시를 쓰는 라이브러리에는 같은 구멍이 남는다. 그래서 입력 쪽에서도 막는다. Express의 `body-parser`는 JSON 본문을 기본 100kb로 제한하고, 쿼리 문자열 파서 `qs`는 파라미터를 기본 1,000개까지만 읽는다. 이 기본값을 "편하게" 크게 늘리는 설정 변경이 이 공격의 문을 다시 연다. 이 측정의 키 4,096개짜리 공격은 JSON으로 118,785바이트라 100kb 제한도 넘는다. 그런데도 117ms였으니, 제한 안에서 만들 수 있는 피해는 그보다 작다. 크기 제한이 공격의 크기를 묶어 두는 것이다. 요청 하나에 CPU가 수 초씩 튀면 그 요청의 키 개수부터 본다.

## 해시가 못 하는 일

해시 테이블은 "이 키 있나, 값은 뭔가"에는 최고지만 키의 순서를 버린다. 그래서 아래 질문에는 답하지 못하거나 전부 훑어야 한다.

- 범위: "점수 80~90점인 사람", "이 시각 이후 이벤트". 정렬된 구조가 필요하다. [이진 탐색 트리](/posts/ds-binary-tree-bst)나 정렬된 배열, DB라면 B-tree 인덱스다.
- 가장 작은 것: "마감이 가장 이른 작업"을 계속 꺼낸다면 [힙](/posts/ds-heap)이다.
- 접두사: "ap로 시작하는 단어"는 [트라이](/posts/ds-trie)다.
- 메모리가 모자랄 때: 1억 개의 "있나?"를 조금 틀려도 되는 대신 작게 묻고 싶으면 [블룸 필터](/posts/bloom-filter)다.
- 여러 서버에 나눌 때: `hash % 서버 수`는 서버 수가 바뀌면 거의 모든 키가 옮겨 간다. [일관된 해싱](/posts/consistent-hashing)이 이 문제를 푼다.

평균 O(1)이라는 말에도 조건이 붙는다. 해시 계산 자체가 키 길이 k에 비례하니 긴 문자열 키는 O(k)다. 다시 넣기 순간에는 O(n)이고, 해시가 나쁘거나 공격당하면 O(n)이다. 면접에서 "해시 테이블은 O(1)"이라고 답하면 거의 항상 "언제 아닌가"가 꼬리로 붙는다.

현장에서 해시 때문에 생기는 증상을 모으면 이렇다.

- 숫자가 이상하게 세지거나 `"[object Object]"` 키가 보인다: 객체를 사전으로 썼다. `Map`으로 바꾼다.
- `map.get(좌표 배열)`이 늘 `undefined`다: 참조 비교다. 문자열이나 정수 키로 만든다.
- 큰 표를 채우는 요청만 가끔 수십 ms 튄다: 다시 넣기다. 미리 만들어 두거나 나눠서 채운다.
- 키가 계속 늘기만 하는 `Map` 캐시로 메모리가 오른다: 지우는 정책이 없다. 크기 제한(LRU)이나 `WeakMap`을 쓴다.
- 요청 하나에 CPU가 수 초: 키 개수 제한과 씨앗 있는 해시를 확인한다.

해시 테이블은 키를 칸 번호로 바꿔 배열의 "바로 가기"를 임의의 키로 넓힌 구조다. 속도는 해시가 고르게 흩어 주는지와 적재율이 결정하고, 충돌은 목록(체이닝)이나 옆 칸(개방 주소)으로 받는다. 이 세 가지를 설명할 수 있으면 JS의 `Map`이 왜 객체보다 사전에 맞는지, 왜 가끔 느려지는지, 왜 씨앗이 보안 문제인지까지 이어서 말할 수 있다.

## 면접에서 나올 만한 질문

### 해시 테이블의 조회가 O(1)인 이유는 무엇인가요?

해시 함수가 키를 배열 인덱스로 바꿔 주고, 배열은 인덱스로 한 번에 접근하기 때문이다. 칸 수에 비해 키가 적당히 적고(적재율이 낮고) 해시가 고르게 흩어 주면 한 칸에 평균 상수 개의 키만 있어서 비교도 상수 번으로 끝난다. 다만 해시 계산이 키 길이에 비례하고, 충돌이 몰리면 O(n)까지 나빠질 수 있어서 "평균" O(1)이라고 말한다.

### 충돌은 어떻게 처리하나요? 체이닝과 개방 주소법의 차이는요?

체이닝은 칸마다 목록을 달아 같은 칸의 키를 줄 세우고, 개방 주소법은 배열 하나에 키를 직접 담고 칸이 차 있으면 정해진 규칙으로 다른 칸을 찾아간다. 체이닝은 꽉 차도 버티고 삭제가 쉽지만 노드가 흩어져 캐시 효율이 나쁘다. 개방 주소법은 연속된 메모리라 빠르지만 적재율이 높아지면 군집 때문에 급격히 느려지고, 삭제에 묘비가 필요하다. 자바 `HashMap`은 체이닝, 파이썬 `dict`와 러스트 `HashMap`은 개방 주소 방식이다.

### 개방 주소법에서 삭제할 때 왜 그냥 비우면 안 되나요?

찾기가 빈칸을 만나면 "없다"로 멈추기 때문이다. 충돌로 밀려난 키는 원래 칸에서 몇 칸 뒤에 있는데, 그 사이를 비우면 탐색이 거기서 끊겨 있는 키를 없다고 답한다. 그래서 지운 자리에 묘비를 남겨 찾기는 지나가고 넣기는 재사용하게 한다. 묘비가 쌓이면 탐색이 길어지므로 일정 비율을 넘으면 표를 다시 만든다.

### 적재율이 무엇이고, 다시 넣기(rehash)는 왜 평균 O(1)인가요?

적재율은 들어 있는 키 수를 칸 수로 나눈 값으로, 높을수록 충돌이 늘어 느려진다. 그래서 0.75 같은 기준을 넘으면 칸을 두 배로 늘리고 모든 키를 새 칸 번호로 다시 넣는다. 그 한 번은 O(n)이지만 두 배씩 늘리면 옮기는 양의 합이 등비급수로 n의 상수배에 그쳐서, 키 하나당 평균 비용은 O(1)이다. 실제로 100만 개를 넣을 때 키 하나당 1.57번만 옮겼다. 다만 그 한 번은 실제로 멈춤을 만들어서, V8 `Map`이 100만 개를 넘길 때 `set` 한 번이 80ms를 넘었다.

### JS에서 객체 대신 Map을 써야 하는 때는 언제인가요?

키가 데이터일 때, 즉 사전으로 쓸 때다. 객체는 키를 문자열로 바꾸고 프로토타입의 `constructor`, `toString` 같은 키와 부딪히며, 크기를 바로 알 수 없다. `Map`은 아무 값이나 키로 쓰고 SameValueZero로 비교하며, `size`가 있고 넣은 순서대로 순회한다. 키가 정해진 레코드는 객체가 맞고, 객체를 꼭 사전으로 써야 하면 `Object.create(null)`로 만든다.

### Map에 배열을 키로 넣었는데 get이 undefined를 돌려줍니다. 왜 그런가요?

객체 키는 내용이 아니라 참조로 비교하기 때문이다. `set`에 넣은 배열과 `get`에 넘긴 배열은 내용이 같아도 다른 객체라 다른 키다. 좌표 같은 값 키는 `"r,c"` 문자열이나 `r * cols + c` 같은 정수로 바꿔서 쓴다. 같은 객체 참조를 계속 들고 다닐 수 있을 때만 객체를 키로 쓴다.

### 해시 플러딩 공격은 무엇이고 어떻게 막나요?

공격자가 같은 칸에 떨어지는 키를 대량으로 보내 해시 테이블을 O(n²)으로 만들어 CPU를 묶는 서비스 거부 공격이다. 해시 함수가 고정되어 있으면 충돌 키를 미리 계산할 수 있어서 생긴다. 프로세스마다 무작위 씨앗을 섞는 해시(SipHash 등)로 계산 자체를 막고, 입력 쪽에서 본문 크기와 파라미터 개수를 제한한다. Node.js도 2017년에 해시 씨앗이 고정되던 문제를 고친 적이 있다.

### 해시 테이블 대신 다른 구조를 골라야 하는 경우는요?

키의 순서가 필요한 질문이다. 범위 조회나 정렬된 순회는 균형 이진 탐색 트리나 B-tree, 가장 작은 값을 반복해서 꺼내는 일은 힙, 접두사 검색은 트라이가 맞다. 메모리가 부족하고 약간의 오답을 허용하면 블룸 필터, 여러 서버에 키를 나누면 일관된 해싱을 쓴다. 해시 테이블은 "같은 키를 정확히 찾는" 질문에만 강하다.
