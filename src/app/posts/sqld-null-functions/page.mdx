<EasyIntro>
  사원들의 월급에 보너스를 더했더니 몇 사람의 합계가 통째로 빈칸이 됐다. 그 사람들은 보너스 칸이 비어 있었다. 데이터베이스는 빈칸을 0이 아니라 "모른다"로 보기 때문에, 모르는 값에 무엇을 더해도 결과는 모르는 값이 된다.

  비교도 마찬가지다. 빈칸과 무엇을 비교하면 맞다도 틀리다도 아닌 "모름"이 나오고, 조건에 맞는 줄만 남기는 규칙 때문에 그 줄은 조용히 빠진다. 그래서 빈칸을 미리 0 같은 값으로 바꿔 주는 함수와, 조건에 따라 값을 고르는 방법이 따로 있다.

  이걸 알면 바뀐 데이터만 고치는 작업에서 왜 몇 줄이 빠지는지 보인다. 비어 있다가 값이 생긴 줄은 보통의 "다르다" 비교로는 다르다고 나오지 않는다. 빈칸까지 하나의 값처럼 비교하는 방법을 써야 놓치지 않는다.
</EasyIntro>

영업부 사원들의 이번 달 지급액을 뽑는 쿼리를 짰다. 급여(`SAL`)에 커미션(`COMM`)을 더하면 끝이라고 생각했다. `SELECT ename, sal + comm FROM emp WHERE deptno = 30`. 결과를 보니 여섯 명 중 BLAKE와 JAMES의 지급액이 빈칸이다. 급여는 분명히 2850과 950이 들어 있는데 더한 값이 통째로 사라졌다.

범인은 `COMM` 칸의 NULL이다. NULL에 무엇을 더해도 NULL이 된다. SQLD 시험에서도 이 성질이 함수 문제, 집계 문제, 조인 문제에 모양을 바꿔 가며 계속 나오고, 현장에서는 에러 없이 행이 빠지거나 값이 사라지는 버그로 나타난다. 이 글은 이 장면에서 시작해서 NULL이 계산과 비교에서 어떻게 동작하는지, NULL을 다른 값으로 바꾸는 `NVL`, `NVL2`, `NULLIF`, `COALESCE`, 조건에 따라 값을 고르는 `CASE`와 `DECODE`를 정리한다. 문자, 숫자, 날짜 함수는 [단일행 함수 글](/posts/sqld-single-row-functions)에서, 형 변환은 [형 변환 글](/posts/sqld-type-conversion)에서 다룬다.

SQLD 문제는 주로 Oracle 문법으로 나오고, SQL Server와 다른 점을 묻는 문제가 섞여 나온다. 그래서 SQL은 Oracle 문법을 먼저 쓰고, PostgreSQL 16과 SQL Server에서 다른 부분을 옆에 적었다. 결과 표는 모두 PostgreSQL 16.15에 같은 데이터를 넣고 실제로 돌린 출력이다. `NVL`, `DECODE`처럼 Oracle에만 있는 함수는 PostgreSQL에서 같은 뜻의 식으로 돌렸고, 결과 값은 Oracle과 같다. psql은 NULL을 빈칸으로 보여 주는데, 눈에 띄게 `(null)`로 표시하도록 설정했다.

## 이 글에서 쓸 사원 테이블

Oracle을 설치하면 따라오는 SCOTT 계정의 `EMP`(사원)와 `DEPT`(부서) 테이블을 쓴다. SQLD 교재와 기출이 거의 다 이 데이터로 문제를 낸다. 집계와 조인을 다루는 다음 글들도 이 테이블을 그대로 쓴다.

```sql

  deptno integer PRIMARY KEY,   -- Oracle: NUMBER(2)
  dname  varchar(14),           -- Oracle: VARCHAR2(14)
  loc    varchar(13)
);

  empno    integer PRIMARY KEY, -- Oracle: NUMBER(4)
```

## 지급액이 빈칸이 된 이유

처음 쿼리를 다시 돌려 본다.

```sql
SELECT ename, sal, comm, sal + comm AS total
FROM emp
WHERE deptno = 30
ORDER BY empno;
```

```text
 ename  | sal  |  comm  | total
--------+------+--------+--------
 ALLEN  | 1600 |    300 |   1900
 WARD   | 1250 |    500 |   1750
 MARTIN | 1250 |   1400 |   2650
 BLAKE  | 2850 | (null) | (null)
 TURNER | 1500 |      0 |   1500
 JAMES  |  950 | (null) | (null)
(6 rows)
```

NULL은 "0"이 아니라 "모른다"는 표시다. 커미션을 모르니 급여와 더한 값도 모른다. 그래서 `2850 + NULL`은 2850이 아니라 NULL이다. 사칙연산 어디에 NULL이 끼어도 결과는 NULL이다. TURNER는 커미션이 0으로 들어 있어서 1500이 제대로 나왔다. 아래 그림에서 다음을 누르면 한 행씩 계산되는 모습이 나온다.

고치는 방법은 더하기 전에 NULL을 0으로 바꾸는 것이다. Oracle은 `NVL`, 표준 SQL과 PostgreSQL은 `COALESCE`, SQL Server는 `ISNULL`을 쓴다.

```sql
-- Oracle
SELECT ename, sal, comm, sal + NVL(comm, 0) AS total
FROM emp WHERE deptno = 30 ORDER BY empno;

-- PostgreSQL (Oracle에서도 그대로 된다)
SELECT ename, sal, comm, sal + COALESCE(comm, 0) AS total
FROM emp WHERE deptno = 30 ORDER BY empno;

-- SQL Server
SELECT ename, sal, comm, sal + ISNULL(comm, 0) AS total
FROM emp WHERE deptno = 30 ORDER BY empno;
```

```text
 ename  | sal  |  comm  | total
--------+------+--------+-------
 ALLEN  | 1600 |    300 |  1900
 WARD   | 1250 |    500 |  1750
 MARTIN | 1250 |   1400 |  2650
 BLAKE  | 2850 | (null) |  2850
 TURNER | 1500 |      0 |  1500
 JAMES  |  950 | (null) |   950
(6 rows)
```

`NVL(comm, 0)`처럼 행마다 한 번씩 실행되어 값 하나를 돌려주는 함수를 단일행 함수라고 한다. 이제 NULL이 따르는 규칙부터 하나씩 본다.

## NULL은 값이 아니라 빈칸이다

처음 장면으로 돌아간다. NULL에는 규칙이 몇 개 있고, 시험은 이 규칙을 그대로 묻는다.

첫째, NULL이 낀 산술 연산은 NULL이다. 연봉을 `sal * 12 + comm`으로 구하면 커미션이 NULL인 BLAKE와 JAMES는 연봉이 NULL이다.

```sql
SELECT ename, comm, sal * 12 + comm AS annual, sal * 12 + NVL(comm, 0) AS annual2
FROM emp WHERE deptno = 30 ORDER BY empno;
```

```text
 ename  |  comm  | annual | annual2
--------+--------+--------+---------
 ALLEN  |    300 |  19500 |   19500
 WARD   |    500 |  15500 |   15500
 MARTIN |   1400 |  16400 |   16400
 BLAKE  | (null) | (null) |   34200
 TURNER |      0 |  18000 |   18000
 JAMES  | (null) | (null) |   11400
(6 rows)
```

둘째, NULL과 비교하면 참도 거짓도 아닌 "알 수 없음"(UNKNOWN)이 된다. `WHERE`는 참인 행만 남기니 UNKNOWN인 행은 빠진다. 그래서 `comm = NULL`은 한 행도 못 찾는다. NULL은 `IS NULL`, `IS NOT NULL`로만 찾는다.

```sql
SELECT COUNT(*) FROM emp WHERE comm = NULL;           -- 0
SELECT COUNT(*) FROM emp WHERE comm IS NULL;          -- 10
SELECT COUNT(*) FROM emp WHERE comm IS NOT NULL;      -- 4
SELECT COUNT(*) FROM emp WHERE comm <> 0;             -- 3 (300, 500, 1400)
SELECT COUNT(*) FROM emp WHERE comm > 0 OR comm <= 0; -- 4
SELECT COUNT(*) FROM emp WHERE deptno IN (10, NULL);     -- 3
SELECT COUNT(*) FROM emp WHERE deptno NOT IN (10, NULL); -- 0
```

`comm <> 0`이 3인 걸 봐 둔다. "커미션이 0이 아닌 사람"을 찾았는데 NULL인 10명은 빠졌다. `comm > 0 OR comm <= 0`처럼 모든 경우를 덮는 것 같은 조건도 NULL은 못 잡는다. 마지막 줄이 가장 무섭다. `NOT IN (10, NULL)`은 `deptno <> 10 AND deptno <> NULL`이고, 뒤쪽이 늘 UNKNOWN이라 전체가 참이 될 수 없다. 결과는 0행이다. `IN (10, NULL)`은 `OR`로 풀려서 10번 부서 3행이 나온다. 서브쿼리 결과에 NULL이 섞여 `NOT IN`이 0행이 되는 경우는 [서브쿼리 글](/posts/sqld-subquery-set-operators)에서 따로 본다.

셋째, Oracle에서 빈 문자열 `''`은 NULL이다. Oracle은 길이가 0인 문자열을 따로 두지 않는다. 그래서 `WHERE ename = ''`는 `ename = NULL`과 같아서 한 행도 안 나오고, `LENGTH('')`는 0이 아니라 NULL이다. PostgreSQL과 SQL Server에서 `''`은 NULL이 아닌 빈 문자열이고 길이는 0이다.

넷째, 문자열 이어 붙이기는 DB마다 다르다. Oracle의 `||`는 NULL을 빈 문자열처럼 보고 무시한다. `'A' || NULL`이 `'A'`다. PostgreSQL의 `||`는 표준대로 NULL을 돌려준다. PostgreSQL에서 NULL을 무시하고 이으려면 `concat`을 쓴다.

```sql
-- PostgreSQL 16
SELECT NULL + 1 AS a, NULL || 'x' AS b, concat(NULL, 'x') AS c, length('') AS d, '' IS NULL AS e;
```

```text
   a    |   b    | c | d | e
--------+--------+---+---+---
 (null) | (null) | x | 0 | f
(1 row)
```

같은 쿼리를 Oracle에서 돌리면 `b`는 `x`, `d`는 NULL, `e`는 참이 된다. Oracle에서 쓰던 `ename || ' (' || comm || ')'` 같은 식을 PostgreSQL로 옮기면 커미션이 없는 행이 통째로 NULL이 된다.

## NULL을 다른 값으로 바꾸는 함수

NULL 함수는 다섯 개만 알면 된다. 모두 PostgreSQL에서 같은 뜻의 식으로 돌린 결과다.

`NVL(a, b)`는 a가 NULL이면 b, 아니면 a다. 두 인자의 타입이 맞아야 한다. `NVL(comm, '없음')`은 숫자 컬럼에 문자를 넣으려 해서 에러가 난다.

`NVL2(a, b, c)`는 a가 NULL이 아니면 b, NULL이면 c다. 이름은 비슷하지만 하는 일이 다르다. NULL이 "아닐 때"가 먼저 온다는 순서를 자주 묻는다.

`NULLIF(a, b)`는 a와 b가 같으면 NULL, 다르면 a다. 0으로 나누기를 피할 때 `sal / NULLIF(comm, 0)`처럼 쓴다. 0을 NULL로 바꾸면 에러 대신 NULL이 나온다.

```sql
-- Oracle
SELECT ename, comm,
       NVL(comm, 0)                 AS nvl_comm,
       NVL2(comm, sal + comm, sal)  AS nvl2_total,  -- comm이 있으면 sal+comm, 없으면 sal
       NULLIF(comm, 0)              AS nullif_comm  -- 0이면 NULL로
FROM emp WHERE deptno = 30 ORDER BY empno;
```

```text
 ename  |  comm  | nvl_comm | nvl2_total | nullif_comm
--------+--------+----------+------------+-------------
 ALLEN  |    300 |      300 |       1900 |         300
 WARD   |    500 |      500 |       1750 |         500
 MARTIN |   1400 |     1400 |       2650 |        1400
 BLAKE  | (null) |        0 |       2850 |      (null)
 TURNER |      0 |        0 |       1500 |      (null)
 JAMES  | (null) |        0 |        950 |      (null)
(6 rows)
```

TURNER의 `nullif_comm`이 NULL이 된 걸 본다. 커미션 0이 `NULLIF`를 지나며 NULL로 바뀌었다.

`COALESCE(a, b, c, ...)`는 인자를 왼쪽부터 보다가 처음 나오는 NULL 아닌 값을 돌려준다. 모두 NULL이면 NULL이다. 인자가 두 개면 `NVL`과 같다. 표준 SQL이라 Oracle, PostgreSQL, SQL Server에서 다 된다.

```sql
SELECT ename, comm, mgr, COALESCE(comm, mgr, 0) AS c
FROM emp WHERE empno IN (7369, 7499, 7839) ORDER BY empno;
```

```text
 ename |  comm  |  mgr   |  c
-------+--------+--------+------
 SMITH | (null) |   7902 | 7902
 ALLEN |    300 |   7698 |  300
 KING  | (null) | (null) |    0
(3 rows)
```

SMITH는 커미션이 없어서 다음 인자인 상사 번호 7902가 나왔다. KING은 둘 다 없어서 0이다. 뜻은 없는 예제지만 "처음으로 값이 있는 것"이라는 동작을 보기엔 좋다.

SQL Server의 `ISNULL(a, b)`는 `NVL`과 같다. 결과 타입은 첫 번째 인자를 따르니, 첫 인자가 `VARCHAR(2)`면 두 번째 값이 길어도 잘린다. 같은 이름의 `ISNULL`이 MySQL에서는 인자 하나를 받아 NULL인지(1, 0)를 돌려주는 전혀 다른 함수라는 것도 알아 둔다.

아래 칸에서 `COALESCE`를 직접 만들어 볼 수 있다. 자바스크립트의 `null`을 SQL의 NULL로 본다.

## 조건에 따라 값을 고르는 CASE와 DECODE

`CASE`는 SQL 안의 if문이다. 두 가지 모양이 있다. 단순 CASE는 `CASE 컬럼 WHEN 값 THEN ...`처럼 한 컬럼을 여러 값과 같은지 비교한다. 검색 CASE는 `CASE WHEN 조건 THEN ...`처럼 WHEN마다 아무 조건이나 쓴다. 범위 비교(`>=`)는 검색 CASE로만 된다.

```sql
-- 단순 CASE: deptno가 10이면, 20이면
SELECT ename, deptno,
       CASE deptno WHEN 10 THEN 'ACCOUNTING'
                   WHEN 20 THEN 'RESEARCH'
                   ELSE 'ETC' END AS simple_case
FROM emp WHERE empno IN (7369, 7499, 7782) ORDER BY empno;
```

```text
 ename | deptno | simple_case
-------+--------+-------------
 SMITH |     20 | RESEARCH
 ALLEN |     30 | ETC
 CLARK |     10 | ACCOUNTING
(3 rows)
```

```sql
-- 검색 CASE: 위에서부터 처음 참인 WHEN 하나만 고른다
SELECT ename, sal,
       CASE WHEN sal >= 3000 THEN 'HIGH'
            WHEN sal >= 1500 THEN 'MID'
            ELSE 'LOW' END AS band
FROM emp ORDER BY sal DESC, empno;
```

```text
 ename  | sal  | band
--------+------+------
 KING   | 5000 | HIGH
 SCOTT  | 3000 | HIGH
 FORD   | 3000 | HIGH
 JONES  | 2975 | MID
 BLAKE  | 2850 | MID
 CLARK  | 2450 | MID
 ALLEN  | 1600 | MID
 TURNER | 1500 | MID
 MILLER | 1300 | LOW
 WARD   | 1250 | LOW
 MARTIN | 1250 | LOW
 ADAMS  | 1100 | LOW
 JAMES  |  950 | LOW
 SMITH  |  800 | LOW
(14 rows)
```

KING의 5000은 두 번째 조건(`>= 1500`)도 만족하지만 첫 번째에서 이미 골랐으니 `HIGH` 하나만 나온다. WHEN의 순서가 결과를 바꾼다. `ELSE`를 빼면 아무 WHEN에도 맞지 않는 행은 NULL이 된다.

Oracle에는 단순 CASE를 함수로 쓴 `DECODE(컬럼, 값1, 결과1, 값2, 결과2, ..., 기본값)`이 있다. 인자 수가 짝수면 마지막이 기본값이 아니라 마지막 결과라서, 맞는 게 없으면 NULL이다.

```sql
-- Oracle: 위의 단순 CASE와 결과가 같다
SELECT ename, deptno, DECODE(deptno, 10, 'ACCOUNTING', 20, 'RESEARCH', 'ETC') AS d
FROM emp WHERE empno IN (7369, 7499, 7782) ORDER BY empno;
```

둘이 갈리는 지점은 NULL이다. 단순 CASE의 `WHEN NULL`은 내부적으로 `comm = NULL` 비교라서 절대 맞지 않는다. `DECODE`는 NULL과 NULL을 같다고 본다. 그래서 `DECODE(comm, NULL, 'none', 'has')`는 NULL인 행에 `none`을 돌려준다. 검색 CASE로 `WHEN comm IS NULL`을 쓰면 `DECODE`와 같은 결과가 나온다.

```sql
SELECT ename, comm,
       CASE comm WHEN NULL THEN 'none' ELSE 'has' END AS simple_null,   -- 늘 has
       CASE WHEN comm IS NULL THEN 'none' ELSE 'has' END AS searched_null
       -- Oracle: DECODE(comm, NULL, 'none', 'has')는 searched_null과 같다
FROM emp WHERE deptno = 30 ORDER BY empno;
```

```text
 ename  |  comm  | simple_null | searched_null
--------+--------+-------------+---------------
 ALLEN  |    300 | has         | has
 WARD   |    500 | has         | has
 MARTIN |   1400 | has         | has
 BLAKE  | (null) | has         | none
 TURNER |      0 | has         | has
 JAMES  | (null) | has         | none
(6 rows)
```

`DECODE`는 Oracle에만 있다. 이식성을 생각하면 `CASE`를 쓴다. `CASE`는 집계 함수 안에 넣어 부서별 직무 수를 세는 식으로도 많이 쓰는데, 그건 [집계 글](/posts/sqld-group-by-having)에서 이어서 본다.

## 현장에서 NULL이 바뀐 행을 숨기는 순간

외부 시스템에서 받은 값으로 테이블을 맞추는 동기화 배치를 생각해 보자. 인사 시스템이 보낸 새 커미션 값(`comm_feed`)과 지금 값을 비교해서 바뀐 행만 고치려 한다. 바뀐 행을 `<>`로 고르면 NULL이 낀 행을 놓친다.

```sql
-- 인사 시스템에서 받은 새 커미션 값
CREATE TABLE comm_feed (empno integer PRIMARY KEY, comm numeric);
INSERT INTO comm_feed VALUES (7499, 300), (7521, 600), (7698, 200), (7844, NULL), (7900, NULL);

-- 두 비교 방식이 행마다 무엇을 돌려주나
SELECT e.empno, e.ename, e.comm AS old_comm, f.comm AS new_comm,
       e.comm <> f.comm AS ne, e.comm IS DISTINCT FROM f.comm AS distinct_from
FROM emp e JOIN comm_feed f USING (empno) ORDER BY e.empno;
```

```text
 empno | ename  | old_comm | new_comm |   ne   | distinct_from
-------+--------+----------+----------+--------+---------------
  7499 | ALLEN  |      300 |      300 | f      | f
  7521 | WARD   |      500 |      600 | t      | t
  7698 | BLAKE  |   (null) |      200 | (null) | t
  7844 | TURNER |        0 |   (null) | (null) | t
  7900 | JAMES  |   (null) |   (null) | (null) | f
(5 rows)
```

BLAKE는 커미션이 없다가 200이 생겼고, TURNER는 0이던 것이 NULL이 됐다. 둘 다 바뀐 행인데 `<>`는 UNKNOWN을 돌려준다. 실제로 고쳐 보면 차이가 그대로 드러난다.

```sql
-- 바뀐 행만 고친다 (<> 버전과 IS DISTINCT FROM 버전, 각각 ROLLBACK으로 되돌림)
UPDATE emp e SET comm = f.comm FROM comm_feed f
WHERE e.empno = f.empno AND e.comm <> f.comm;

UPDATE emp e SET comm = f.comm FROM comm_feed f
WHERE e.empno = f.empno AND e.comm IS DISTINCT FROM f.comm;
```

```text
UPDATE 1
UPDATE 3
```

`<>` 버전은 WARD 한 명만 고치고 BLAKE와 TURNER를 조용히 건너뛴다. 에러도 경고도 없어서 "BLAKE 커미션이 반영이 안 됐다"는 문의가 올 때까지 모른다. `IS DISTINCT FROM`은 NULL을 하나의 값처럼 비교해서 NULL과 200은 다르고, NULL과 NULL은 같다고 본다. JAMES는 둘 다 NULL이라 고치지 않는다.

`IS DISTINCT FROM`은 PostgreSQL과 SQL Server 2022에 있고, MySQL 8은 NULL끼리 같다고 보는 `<=>` 연산자로 `NOT (e.comm <=> f.comm)`처럼 쓴다. Oracle에서는 앞에서 본 성질 그대로 `DECODE(e.comm, f.comm, 0, 1) = 1`로 쓴다. 반영 건수가 기대보다 적으면 비교 컬럼에 NULL이 있는지부터 본다(`SELECT count(*) FROM comm_feed WHERE comm IS NULL`). 같은 함정이 트리거의 "값이 바뀌었을 때만" 조건이나 변경 감지 쿼리에도 숨어 있다. `<>`로 거르는 조회 조건이 NULL을 빼먹는 경우는 [SELECT와 NULL 글](/posts/sql-select-where-null)에서도 다룬다.

## SQLD 시험 포인트

- NULL이 낀 사칙연산은 NULL이다. `sal + comm`, `sal * 12 + comm`의 결과를 묻는 문제는 NULL인 행을 먼저 찾는다.
- `= NULL`은 늘 0행이다. `NOT IN` 목록에 NULL이 있으면 결과가 0행이다. `comm <> 0`은 NULL인 행을 포함하지 않는다.
- `NVL2(a, b, c)`는 a가 NULL이 아니면 b다. `NULLIF(a, b)`는 같으면 NULL이다. `COALESCE`는 처음으로 NULL이 아닌 값이다.
- Oracle에서 `''`은 NULL이다. `'A' || NULL`은 `'A'`다.
- `DECODE`는 NULL끼리 같다고 보고, 단순 CASE의 `WHEN NULL`은 절대 맞지 않는다. `ELSE`가 없는 CASE는 NULL을 돌려준다.
- `CASE`의 WHEN은 위에서부터 처음 참인 것 하나만 고른다. 단순 CASE는 같은지 비교만, 범위 비교는 검색 CASE로 쓴다.
- SQL Server 대응: `ISNULL`(= `NVL`), `+`로 이어 붙일 때 NULL이 끼면 NULL이다.

## 면접에서 나올 만한 질문

### NULL이 있는 컬럼으로 계산하면 어떻게 되나요?

산술 연산에 NULL이 하나라도 끼면 결과가 NULL이다. NULL을 0이 아니라 "모르는 값"으로 보기 때문이다. 예제에서 `sal + comm`은 커미션이 없는 BLAKE의 급여 2850까지 같이 지워 버렸다. 계산 전에 `NVL(comm, 0)`이나 `COALESCE(comm, 0)`으로 바꾸되, NULL과 0이 업무적으로 같은 뜻인지 먼저 확인한다.

### NVL, NVL2, NULLIF, COALESCE의 차이는요?

`NVL(a, b)`는 a가 NULL이면 b로 바꾼다. `NVL2(a, b, c)`는 a가 NULL이 아니면 b, NULL이면 c를 돌려줘서 두 경우의 값을 따로 정할 수 있다. `NULLIF(a, b)`는 반대로 두 값이 같으면 NULL을 만들고, 0으로 나누기를 피할 때 쓴다. `COALESCE`는 인자 여러 개 중 처음으로 NULL이 아닌 값을 고르는 표준 함수라 DB를 옮겨도 그대로 쓸 수 있다.

### WHERE comm = NULL은 왜 아무것도 못 찾나요?

NULL과의 비교는 참도 거짓도 아닌 UNKNOWN이 되고, `WHERE`는 참인 행만 남기기 때문이다. NULL은 `IS NULL`로 찾는다. 같은 이유로 `NOT IN` 목록이나 서브쿼리 결과에 NULL이 하나라도 있으면 조건이 참이 될 수 없어서 결과가 0행이 된다. 실무에서는 `NOT EXISTS`를 쓰거나 NULL을 먼저 걸러 낸다.

### CASE와 DECODE는 무엇이 다른가요?

`DECODE`는 Oracle 전용 함수로, 한 값을 여러 값과 같은지 비교하는 단순 CASE와 하는 일이 같다. `CASE`는 표준 SQL이고, 검색 CASE로 범위나 여러 컬럼에 걸친 조건도 쓸 수 있다. NULL 처리도 다르다. `DECODE`는 NULL과 NULL을 같다고 보지만 단순 CASE의 `WHEN NULL`은 맞지 않아서 `WHEN comm IS NULL`로 써야 한다. 새로 짜는 쿼리는 이식성과 가독성 때문에 `CASE`를 쓴다.

### Oracle과 PostgreSQL은 빈 문자열을 어떻게 다르게 다루나요?

Oracle은 길이 0인 문자열을 따로 두지 않고 `''`을 NULL로 본다. 그래서 `WHERE ename = ''`는 한 행도 못 찾고 `LENGTH('')`는 NULL이며, `||`는 NULL을 무시해서 `'A' || NULL`이 `'A'`다. PostgreSQL은 `''`을 길이 0인 값으로 보고 `||`에 NULL이 끼면 결과가 NULL이라, NULL을 무시하고 이으려면 `concat`을 쓴다. 옮길 때 에러 없이 행 전체가 NULL이 되는 식을 찾아야 한다.

### 값이 바뀐 행만 고르려는데 NULL이 섞여 있으면 어떻게 비교하나요?

`old <> new`는 어느 한쪽이라도 NULL이면 UNKNOWN이라 그 행이 빠진다. 예제에서 바뀐 행이 셋인데 `<>`로는 1건만 고쳐졌다. PostgreSQL과 SQL Server 2022는 NULL을 값처럼 비교하는 `IS DISTINCT FROM`을, MySQL은 `<=>`를, Oracle은 NULL끼리 같다고 보는 `DECODE`를 쓴다. 동기화 배치나 변경 감지 조건에서 반영 건수가 적으면 이것부터 의심한다.
