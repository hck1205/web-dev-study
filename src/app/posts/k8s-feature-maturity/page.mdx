클러스터를 1.24에서 1.25로 올린 다음 날 아침, 배포 파이프라인이 빨갛다. 앱 코드는 그대로인데 `kubectl apply`가 이렇게 실패한다.

```text
error: resource mapping not found for name: "report" namespace: "" from "cronjob.yaml": no matches for kind "CronJob" in version "batch/v1beta1"

```

몇 년 전에 복사해 둔 CronJob 매니페스트가 `batch/v1beta1`을 쓰고 있었고, 그 버전은 1.25에서 사라졌다. 이미 돌고 있던 CronJob은 멀쩡하다. 새로 보내는 매니페스트만 막힌다. 업그레이드 전에 경고가 없었던 것도 아니다. 매번 apply할 때마다 `Warning:` 한 줄이 찍혔지만 CI 로그에 묻혀 아무도 보지 않았다.

이 글은 쿠버네티스가 기능과 API를 어떻게 단계별로 내놓고 거두는지 본다. alpha·beta·GA가 각각 무엇을 약속하는지, 기능의 단계(feature gate)와 API 버전의 단계가 어떻게 다른지, 폐기 정책이 정한 기한, PodSecurityPolicy와 `extensions/v1beta1`이 사라진 과정, 그리고 업그레이드 전에 옛 API를 쓰는 곳을 찾아내는 방법(경고, 지표, 감사 로그, pluto, kubectl convert)이다. 출력은 kwok로 띄운 실습 클러스터(Kubernetes 1.30)에서 받았다. 정책 문장과 버전 기록은 쿠버네티스 문서 저장소(kubernetes/website)의 원문을 2026년 10월에 확인했고, 그 시점의 최신 안정 버전은 1.37이다.

이 주제의 다른 글: `apiVersion`의 그룹과 버전이 URL과 저장 방식에서 무엇인지는 [API 오브젝트 글](/posts/k8s-api-objects)에, 실제 업그레이드 절차와 버전 차이 허용 범위는 [클러스터 업그레이드 글](/posts/k8s-cluster-upgrade)에 있다.

## alpha, beta, GA가 약속하는 것

쿠버네티스는 새 기능을 바로 안정판으로 내지 않는다. 세 단계를 거친다. 각 단계는 "얼마나 믿어도 되는지"에 대한 약속이다.

- alpha: 버전 이름에 `alpha`가 들어간다(`v1alpha1`). 기본으로 꺼져 있다. 버그가 있을 수 있고, 다음 릴리스에서 예고 없이 바뀌거나 사라질 수 있다. 문서는 짧게 쓰고 버리는 테스트 클러스터에서만 쓰라고 한다.
- beta: 이름에 `beta`가 들어간다(`v2beta3`). 충분히 테스트됐고 기능 자체가 없어지지는 않지만, 다음 beta나 GA로 넘어갈 때 필드 모양이 바뀔 수 있다. 그때는 매니페스트를 고쳐 다시 써야 한다.
- GA(stable): 이름이 `v1`, `v2`처럼 숫자뿐이다. 쿠버네티스 메이저 버전(1.x) 안에서는 없어지지 않는다.

## 기능의 단계와 API의 단계는 따로 간다

여기서 많이 헷갈린다. "기능이 beta다"와 "API 버전이 beta다"는 다른 말이다. 기능(feature)은 컴포넌트의 feature gate라는 스위치로 켜고 끈다. API 버전은 API 서버가 그 그룹/버전 경로를 내주느냐의 문제로, `--runtime-config`로 켜고 끈다. 둘의 기본값 규칙도 다르다.

- alpha 기능의 gate는 꺼져 있고, alpha API 버전도 꺼져 있다.
- beta 기능의 gate는 켜져 있다.
- beta API 버전은 꺼져 있다. 단, 1.22 이전에 나온 beta API는 그때 규칙대로 켜져 있다. 이 규칙은 1.24부터 적용됐다.

## feature gate를 켜고 끄기

feature gate는 `--feature-gates=이름=true,이름=false` 형식으로 각 컴포넌트(kube-apiserver, kubelet, controller-manager, scheduler)에 준다. 기능 하나가 여러 컴포넌트에 걸치면 모두에 같이 켜야 한다. 지금 켜져 있는 gate는 각 컴포넌트의 `kubernetes_feature_enabled` 지표로 볼 수 있다.

```bash
# API 서버가 아는 feature gate의 단계와 켜짐 여부 (일부)
kubectl get --raw /metrics | grep kubernetes_feature_enabled | grep -E 'SidecarContainers|InPlacePodVerticalScaling|HPAScaleToZero|ValidatingAdmissionPolicy'
```

```text
kubernetes_feature_enabled{name="HPAScaleToZero",stage="ALPHA"} 0
kubernetes_feature_enabled{name="InPlacePodVerticalScaling",stage="ALPHA"} 0
kubernetes_feature_enabled{name="SidecarContainers",stage="BETA"} 1
kubernetes_feature_enabled{name="ValidatingAdmissionPolicy",stage=""} 1
```

`stage=""`는 GA다. beta인 SidecarContainers는 1, alpha인 둘은 0이다. 앞에서 띄운 `r3-gates` 클러스터에서는 InPlacePodVerticalScaling이 1로 나온다.

꺼진 기능의 필드를 보내면 어떻게 될까. 에러가 나지 않는다. API 서버가 그 필드를 조용히 버린다. 컨테이너 크기를 재시작 없이 바꾸는 in-place resize의 `resizePolicy` 필드로 두 클러스터에 같은 Pod를 보내 봤다.

```bash
# 같은 매니페스트를 gate가 꺼진 클러스터와 켜진 클러스터에 보낸다
for c in kwok-r3-found kwok-r3-gates; do
  echo "== $c"
  kubectl --context $c apply -f resize-pod.yaml
  kubectl --context $c get pod resize-demo -o jsonpath='{.spec.containers[0].resizePolicy}{"\n"}'
done
```

```text
== kwok-r3-found
pod/resize-demo created

== kwok-r3-gates
pod/resize-demo created
[{"resourceName":"cpu","restartPolicy":"NotRequired"},{"resourceName":"memory","restartPolicy":"NotRequired"}]
```

gate가 꺼진 쪽은 `created`라고 해 놓고 필드를 빈 값으로 저장했다. 켜진 쪽은 보낸 cpu 항목에 memory 기본값까지 채웠다. "설정했는데 동작을 안 한다"는 증상이면 그 필드가 클러스터 버전에서 어느 단계인지, gate가 켜져 있는지부터 본다. apply가 성공했다고 필드가 들어간 게 아니다.

gate에는 끝이 있다. 기능이 GA가 되면 gate는 켜진 채로 잠기고(locked), 폐기 기간이 지나면 gate 이름 자체가 사라진다. 1.30 API 서버 바이너리에 직접 줘 보면 두 경우의 메시지가 다르다.

```bash
# 1.30에서 GA가 된 기능을 끄려 한다
kube-apiserver --feature-gates=ValidatingAdmissionPolicy=false
# 1.28 이후 gate가 없어진 기능을 끄려 한다
kube-apiserver --feature-gates=PodSecurity=false
```

```text
Error: invalid argument "ValidatingAdmissionPolicy=false" for "--feature-gates" flag: cannot set feature gate ValidatingAdmissionPolicy to false, feature is locked to true
Error: invalid argument "PodSecurity=false" for "--feature-gates" flag: unrecognized feature gate: PodSecurity
```

두 번째가 업그레이드 사고로 이어진다. 예전 버전에서 넣어 둔 `--feature-gates=어떤기능=true`가 kubelet이나 API 서버 설정에 남아 있으면, gate가 사라진 버전으로 올리는 순간 그 컴포넌트가 아예 뜨지 않는다. 업그레이드 전에 설정 파일의 feature gate 목록을 새 버전의 gate 목록과 대조한다.

## 얼마나 오래 남아 있나, 폐기 정책

쿠버네티스는 무엇을 언제까지 남겨 둘지를 폐기 정책(deprecation policy)으로 정해 두었다. 운영자가 업그레이드 일정을 세울 수 있게 하는 약속이다. API 버전에 대한 규칙은 이렇다.

- GA API 버전은 폐기 표시를 할 수는 있어도 1.x 안에서는 없애지 않는다.
- beta API 버전은 나온 지 9개월 또는 3개 마이너 릴리스(둘 중 긴 쪽) 안에 폐기 표시를 하고, 폐기 표시 후 9개월 또는 3개 릴리스(둘 중 긴 쪽)가 지나면 내주지 않는다.
- alpha API 버전은 예고 없이 어느 릴리스에서든 없앨 수 있다.
- 한 API 버전은 덜 안정된 버전으로 대체될 수 없다. GA를 beta로 갈아 치우는 일은 없다.
- 같은 릴리스 안의 버전들 사이에서 객체는 정보 손실 없이 오가야 한다(v1로 쓰고 v2로 읽고 다시 v1로 바꿔도 같아야 한다).

beta의 "3개 릴리스"는 버전 차이 허용 범위와 맞물려 있다. 쿠버네티스는 대략 넉 달에 한 번, 1년에 세 번 마이너 릴리스를 내고, 최근 세 마이너 버전만 패치를 받는다(약 1년). 그래서 beta API를 쓰고 있다면 그 API가 폐기 표시된 걸 본 뒤로도 적어도 세 번의 업그레이드 동안 옮길 시간이 있다는 뜻이다.

feature gate에도 기한이 있다. beta 기능이 GA가 되면 그 gate는 6개월 또는 2개 릴리스(긴 쪽) 동안 남아 있어야 하고, beta 기능이 없어질 때는 3개월 또는 1개 릴리스 동안 남는다. alpha 기능은 바로 없어질 수 있다. 위 그림의 "이후" 칸이 이 기간이다.

## 사라진 API의 역사

정책이 실제로 어떻게 돌아갔는지 보면 감이 온다. 문서의 "Removed APIs by release" 목록에서 운영에 많이 걸렸던 것만 골랐다.

| 사라진 버전 | 무엇이 | 옮길 곳 |
|---|---|---|
| 1.16 | `extensions/v1beta1`, `apps/v1beta1`, `apps/v1beta2`의 Deployment·DaemonSet·ReplicaSet·StatefulSet, `extensions/v1beta1`의 NetworkPolicy·PodSecurityPolicy | `apps/v1`, `networking.k8s.io/v1`, `policy/v1beta1` |
| 1.22 | `extensions/v1beta1`과 `networking.k8s.io/v1beta1`의 Ingress, CRD·웹훅 설정·APIService·Lease·RBAC의 v1beta1 | `networking.k8s.io/v1`, 각 그룹의 v1 |
| 1.25 | CronJob `batch/v1beta1`, PDB `policy/v1beta1`, HPA `autoscaling/v2beta1`, EndpointSlice·Event의 v1beta1, PodSecurityPolicy | `batch/v1`, `policy/v1`, `autoscaling/v2`, PSP는 대체 API 없음 |
| 1.26 | HPA `autoscaling/v2beta2`, FlowSchema `v1beta1` | `autoscaling/v2` |
| 1.29, 1.32 | FlowSchema·PriorityLevelConfiguration `v1beta2`, `v1beta3` | `flowcontrol.apiserver.k8s.io/v1` |

확인 시점의 문서 목록은 1.32가 마지막이다. 1.33부터 1.37까지는 이 목록에 새로 사라진 내장 API 버전이 올라와 있지 않다. 다음 업그레이드 전에는 그 버전의 릴리스 노트에서 "Removed"와 "Deprecation" 절을 꼭 다시 본다.

`extensions/v1beta1`은 쿠버네티스 초기에 새 종류를 일단 넣어 두던 잡동사니 그룹이었다. Deployment, Ingress, NetworkPolicy, PodSecurityPolicy가 모두 여기서 시작했다. 나중에 관심사별 그룹(`apps`, `networking.k8s.io`, `policy`)으로 옮겨 가면서 이 그룹을 비우는 데 여러 릴리스가 걸렸고, 마지막 남은 Ingress가 1.22에서 빠졌다. beta가 기본으로 켜져 있던 시절이라 수많은 운영 매니페스트와 Helm 차트가 이 그룹을 쓰고 있었고, 1.16과 1.22 업그레이드에서 대규모로 깨졌다.

PodSecurityPolicy는 다른 방식으로 끝났다. Pod의 보안 설정을 클러스터 단위로 강제하던 기능인데, 정책이 어느 Pod에 적용되는지가 RBAC 권한에 따라 정해져 이해하기 어렵고, 켜는 순간 기존 워크로드가 막히는 경우가 많았다. 1.21에서 폐기가 발표됐고 1.25에서 API와 어드미션 플러그인이 함께 사라졌다. 같은 모양의 다음 버전이 아니라 네임스페이스 라벨로 수준을 정하는 Pod Security Admission이라는 다른 기능으로 대체됐다(1.25 GA). 그래서 "버전만 바꾸면 되는" 다른 이전과 달리 정책을 다시 설계해야 했다. 새 방식은 [Pod Security Admission 글](/posts/k8s-pod-security-admission)에서 다룬다.

## 이미 돌고 있는 객체는 괜찮다

API 버전이 사라져도 etcd의 객체는 지워지지 않는다. [API 오브젝트 글](/posts/k8s-api-objects)에서 본 것처럼 객체는 저장 버전으로 한 벌만 있고, API 버전은 그걸 보는 창이다. 1.25에서 `batch/v1beta1` 창이 닫혀도 CronJob은 `batch/v1` 창으로 그대로 보이고 계속 돈다. 정책도 "새 버전과 옛 버전을 둘 다 지원하는 릴리스가 한 번 나온 뒤에야 저장 버전을 바꾼다"고 정해 두었다. 그래야 올렸다가 한 단계 되돌려도 저장된 데이터를 읽을 수 있다.

## 경고는 이미 와 있었다

폐기 표시된 API로 요청하면 API 서버는 응답에 `Warning` 헤더를 붙인다(1.19부터). kubectl은 그걸 stderr에 찍는다. 1.30 실습 클러스터에서 1.32에 사라질 `flowcontrol.apiserver.k8s.io/v1beta3`을 불러 봤다.

```bash
# 폐기 예정 버전으로 FlowSchema를 읽는다
kubectl get flowschemas.v1beta3.flowcontrol.apiserver.k8s.io exempt
# HTTP 응답 헤더로 보면
curl -s -i 'localhost:18093/apis/flowcontrol.apiserver.k8s.io/v1beta3/flowschemas?limit=1' | grep -i '^warning'
```

```text

NAME     PRIORITYLEVEL   MATCHINGPRECEDENCE   DISTINGUISHERMETHOD   AGE   MISSINGPL
```

메시지 하나에 필요한 게 다 있다. 언제 폐기됐고(1.29+), 언제 사라지고(1.32+), 무엇으로 옮기면 되는지. 처음 장면의 CI가 이 줄을 무시했을 뿐이다. CI에서는 `--warnings-as-errors`를 주면 경고가 실패로 바뀐다.

## 누가 아직 옛 API를 부르나

CI는 고쳤다 치자. 클러스터에 붙어 있는 다른 클라이언트는 어떻게 찾을까. API 서버는 두 가지 흔적을 남긴다. 하나는 지표다.

```bash
# 폐기된 API가 요청된 적이 있는지 (API 서버 지표)
kubectl get --raw /metrics | grep '^apiserver_requested_deprecated_apis'
```

```text
apiserver_requested_deprecated_apis{group="flowcontrol.apiserver.k8s.io",removed_release="1.32",resource="flowschemas",subresource="",version="v1beta3"} 1
```

먼저 `removed_release` 라벨을 본다. 다음 업그레이드 대상 버전 이하의 값이 하나라도 있으면 그 업그레이드는 무언가를 깨뜨린다. 이 지표는 STABLE 등급의 게이지로, 값 1은 "API 서버가 뜬 뒤로 한 번이라도 요청됐다"는 뜻이다. 몇 번인지는 `apiserver_request_total`에서 같은 group/version/resource로 거르면 된다. API 서버가 재시작하면 지워지고, API 서버가 여럿이면 각자 따로 센다. 그리고 누가 불렀는지는 알려 주지 않는다.

누가 불렀는지는 감사 로그(audit log)에 있다. 폐기된 API 요청의 감사 이벤트에는 어노테이션 두 개가 붙는다. 감사 정책(Metadata 수준)을 켠 클러스터를 하나 더 띄워 같은 요청을 보냈다.

```bash
# 감사 로그에서 폐기 API 요청 하나를 본다
grep v1beta3 audit.log | grep exempt | tail -1 | jq '{verb, requestURI, user: .user.username, userAgent, annotations}'
# 폐기 API를 부른 사용자와 클라이언트별로 센다
jq -r 'select(.annotations["k8s.io/deprecated"]=="true") | [.user.username, .userAgent, .objectRef.resource, .objectRef.apiVersion, .annotations["k8s.io/removed-release"]] | @tsv' audit.log | sort | uniq -c
```

```text
{
  "verb": "get",
  "requestURI": "/apis/flowcontrol.apiserver.k8s.io/v1beta3/flowschemas/exempt",
  "user": "kwok-admin",
  "userAgent": "kubectl/v1.31.4 (linux/amd64) kubernetes/a78aa47",
  "annotations": {
    "authorization.k8s.io/decision": "allow",
    "authorization.k8s.io/reason": "",
    "k8s.io/deprecated": "true",
    "k8s.io/removed-release": "1.32"

```

`user`와 `userAgent`가 범인을 가리킨다. 운영 클러스터라면 ServiceAccount 이름(`system:serviceaccount:monitoring:old-agent`)과 클라이언트 라이브러리 버전이 찍힌다. 관리형 쿠버네티스는 감사 로그를 클라우드 로그 서비스로 보내 주니(EKS는 CloudWatch Logs) 거기서 같은 어노테이션으로 검색한다.

## 매니페스트에서 미리 찾기: pluto

클러스터 흔적은 "이미 부른 것"만 보여 준다. 저장소에만 있고 아직 안 보낸 매니페스트, 1년에 한 번 도는 배치의 차트는 지표에 안 잡힌다. 그래서 파일 쪽도 훑는다. Fairwinds의 pluto는 디렉터리의 YAML과 Helm 차트에서 폐기·제거된 apiVersion을 찾는다. Go로 설치했다.

```bash
# pluto 설치 (Go 1.24, 모듈 경로는 소문자)
GOBIN=$PWD/bin go install github.com/fairwindsops/pluto/v5/cmd/pluto@v5.21.1
# 1.30으로 올린다고 보고 매니페스트 디렉터리를 검사한다
pluto detect-files -d manifests --target-versions k8s=v1.30.0; echo "exit=$?"
```

```text
exit=3
```

`REMOVED true`는 목표 버전에서 이미 사라졌다는 뜻, `REPL AVAIL`은 대체 버전이 목표 버전에 있다는 뜻이다. 종료 코드가 의미를 가진다. 폐기된 것이 있으면 2, 제거된 것이 있으면 3, 폐기됐는데 대체 버전을 아직 쓸 수 없으면 4다(`--ignore-deprecations` 같은 옵션으로 끌 수 있다). CI에 넣어 두면 업그레이드 계획보다 먼저 경보가 울린다. `pluto detect-helm`은 클러스터에 설치된 Helm 릴리스의 기록까지 본다.

비슷한 도구로 kubent(kube-no-trouble)가 있다. 파일보다 클러스터 쪽에 초점을 둬서, 지금 클러스터의 객체와 Helm 릴리스 기록, `last-applied-configuration` 어노테이션에 남은 원래 apiVersion을 모아 보여 준다. 저장된 객체는 어차피 새 버전으로 읽히니, 객체 자체가 아니라 "그 객체를 처음 만든 매니페스트가 어떤 버전이었나"를 추적하는 방식이다. 이 글에서는 실행하지 않았다.

## kubectl convert로 옮기기

찾았으면 옮긴다. `kubectl convert`는 매니페스트를 다른 API 버전으로 바꿔 준다. 예전에는 kubectl에 들어 있었지만 지금은 따로 받는 플러그인(`kubectl-convert`)이다.

```bash
# 클라이언트와 같은 버전의 플러그인을 받는다
curl -LO https://dl.k8s.io/release/v1.31.4/bin/linux/amd64/kubectl-convert
chmod +x kubectl-convert && mv kubectl-convert ~/bin/
# extensions/v1beta1 Deployment를 apps/v1으로 바꾼다
kubectl convert -f old-deploy.yaml --output-version apps/v1
```

```text
apiVersion: apps/v1
kind: Deployment
metadata:
  creationTimestamp: null
  labels:
    app: legacy
  name: legacy
spec:
  progressDeadlineSeconds: 2147483647
  replicas: 2
  revisionHistoryLimit: 2147483647
  selector:
    matchLabels:
      app: legacy
  strategy:
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1
    type: RollingUpdate
  template:
    ...
status: {}
```

그대로 쓰면 안 되는 이유가 출력에 보인다. 원래 매니페스트에는 `selector`가 없었다. `extensions/v1beta1`은 템플릿 라벨로 셀렉터를 채웠으니 convert가 그걸 적어 줬다. 그런데 `progressDeadlineSeconds`와 `revisionHistoryLimit`이 2147483647(int32 최대값)이다. 옛 버전의 기본값인 "마감 없음", "리비전 무한 보관"을 그대로 옮긴 것이다. `apps/v1`의 기본값은 600초와 10개다. maxSurge·maxUnavailable도 옛 기본값 1이 적혔다(`apps/v1` 기본은 25%). 문서도 convert 결과가 "이상적이지 않은 기본값을 쓸 수 있다"고 적고 있다. convert 결과는 초안으로 쓰고, 옛 기본값이 박힌 필드는 지우거나 의도한 값으로 고친다. `creationTimestamp: null`과 `status: {}`도 지운다. [라벨과 셀렉터 글](/posts/k8s-labels-selectors)에서 본 것처럼 셀렉터는 만든 뒤 바꿀 수 없으니 이때 제대로 정한다.

## 업그레이드 전에 보는 순서

1. 목표 버전의 릴리스 노트에서 Removed·Deprecated 절과 deprecation guide를 읽는다. 한 번에 한 마이너씩 올리므로 건너뛰는 버전마다 읽는다.
2. 클러스터 흔적을 본다: `apiserver_requested_deprecated_apis`에서 `removed_release`가 목표 버전 이하인 줄, 감사 로그의 `k8s.io/deprecated` 이벤트와 그 user·userAgent. API 서버가 최근 재시작했다면 지표가 비어 있을 수 있으니 며칠 쌓인 뒤 본다.
3. 파일을 훑는다: 저장소와 차트에 pluto를 돌리고, 설치된 Helm 릴리스 기록도 본다.
4. 옮긴다: apiVersion을 바꾸고 convert가 넣은 옛 기본값을 정리한 뒤 apply한다. 같은 객체가 갱신되니 다시 만들 필요가 없다.
5. 컴포넌트 설정의 feature gate를 새 버전 목록과 대조한다. 사라진 gate 이름이 남아 있으면 컴포넌트가 뜨지 않는다.
6. 스테이징에서 `--runtime-config=<group>/<version>=false`로 곧 사라질 버전을 미리 꺼 보고 무엇이 깨지는지 본다. 문서가 권하는 시험 방법이다.

kubelet은 API 서버보다 최대 세 마이너 버전 낮아도 되지만(1.25 이상 기준) 높으면 안 되고, kubectl은 위아래 한 마이너 안에서 지원된다. 그래서 순서는 컨트롤 플레인을 먼저, 노드를 나중에 올린다. 구체적인 절차는 [클러스터 업그레이드 글](/posts/k8s-cluster-upgrade)에서 이어진다.

## 단계와 기한을 알면 업그레이드가 덜 무섭다

alpha는 꺼져 있고 언제든 바뀌며, beta는 기능 gate는 켜져 있어도 1.24 이후 새로 나온 beta API는 꺼져 있고, GA는 1.x 안에서 사라지지 않는다. beta API는 폐기 표시 후 적어도 9개월 또는 세 릴리스는 남고, 그 동안 API 서버는 Warning 헤더와 `apiserver_requested_deprecated_apis` 지표, 감사 로그 어노테이션으로 계속 알려 준다. API 버전이 사라져도 저장된 객체는 새 버전으로 그대로 보이니, 고칠 것은 클러스터에 말을 거는 매니페스트·차트·클라이언트다. 업그레이드 전에 흔적과 파일을 둘 다 훑고, convert 결과의 옛 기본값을 정리하면 처음 장면의 빨간 파이프라인은 생기지 않는다.

## 면접에서 나올 만한 질문

### 쿠버네티스의 alpha, beta, GA는 무엇이 다른가요?

안정성과 지원 기간에 대한 약속이 다르다. alpha는 기본으로 꺼져 있고 예고 없이 바뀌거나 사라질 수 있다. beta는 충분히 테스트됐고 기능은 남지만 다음 버전에서 필드 모양이 바뀔 수 있으며, 폐기 표시 후 9개월 또는 세 릴리스가 지나면 내주지 않는다. GA는 1.x 안에서 없어지지 않는다.

### beta 기능과 beta API는 기본값이 왜 다른가요?

기능은 feature gate로, API 버전은 API 서버의 runtime-config로 따로 켠다. beta 기능의 gate는 기본으로 켜져 있지만, 1.24부터 새로 나온 beta API 버전은 기본으로 꺼져 있다(1.22 이전 beta는 예외). 예전에 beta API가 기본으로 켜져 있어 운영 매니페스트가 beta에 쌓였다가 제거 때 크게 깨진 경험 때문에 바뀌었다.

### 꺼진 feature gate의 필드를 매니페스트에 넣으면 어떻게 되나요?

대부분 에러 없이 저장되고 그 필드만 조용히 버려진다. 실습에서 in-place resize gate가 꺼진 클러스터는 resizePolicy를 빈 값으로 저장했고, 켜진 클러스터는 기본값까지 채웠다. 그래서 "설정했는데 동작을 안 한다"면 그 필드가 클러스터 버전에서 어느 단계인지, 관련 컴포넌트 모두에 gate가 켜져 있는지 확인한다.

### API 버전이 제거되면 이미 만들어진 객체는 어떻게 되나요?

지워지지 않고 계속 동작한다. etcd에는 저장 버전으로 한 벌만 있고 API 버전은 보는 창이라, 사라진 버전 대신 새 버전으로 읽힌다. 막히는 것은 사라진 버전으로 요청하는 매니페스트, Helm 릴리스 기록, 옛 클라이언트다. 매니페스트의 apiVersion만 바꿔 apply하면 같은 객체가 갱신된다.

### 업그레이드 전에 폐기된 API 사용처를 어떻게 찾나요?

클러스터 쪽은 API 서버 지표 apiserver_requested_deprecated_apis의 removed_release 라벨과, 감사 로그에서 k8s.io/deprecated 어노테이션이 붙은 이벤트의 user와 userAgent를 본다. 지표는 누가 불렀는지 모르고 재시작하면 지워지니 감사 로그로 호출자를 찾는다. 파일 쪽은 pluto 같은 도구로 저장소와 Helm 차트를 훑고, CI에는 kubectl --warnings-as-errors를 건다.

### kubectl convert 결과를 그대로 써도 되나요?

초안으로만 쓴다. 옛 버전의 기본값을 그대로 옮겨서 extensions/v1beta1 Deployment를 바꾸면 progressDeadlineSeconds와 revisionHistoryLimit이 int32 최대값, maxSurge가 1로 박힌다. apps/v1 기본값(600초, 10개, 25%)을 원하면 그 필드를 지우고, creationTimestamp와 status도 정리한다. 셀렉터는 만든 뒤 못 바꾸니 이때 의도대로 정한다.

### PodSecurityPolicy 제거가 다른 API 제거와 달랐던 점은요?

다른 제거는 같은 기능의 새 버전으로 apiVersion만 바꾸면 됐지만, PSP는 대체 API 없이 1.25에서 사라졌다. 적용 대상이 RBAC에 따라 정해져 이해하기 어려웠던 PSP 대신, 네임스페이스 라벨로 수준을 정하는 Pod Security Admission이라는 다른 기능이 들어왔다. 그래서 정책을 다시 설계하고 네임스페이스마다 라벨을 붙이는 이전 작업이 필요했다.

### feature gate가 업그레이드를 막는 경우가 있나요?

있다. GA가 되면 gate가 켜진 채 잠겨서 false를 주면 컴포넌트가 locked 에러로 뜨지 않고, 폐기 기간이 지나 gate가 없어지면 그 이름을 주는 것만으로 unrecognized feature gate 에러가 난다. 예전에 넣어 둔 --feature-gates 설정이 남아 있으면 업그레이드 직후 API 서버나 kubelet이 시작하지 못하니, 새 버전의 gate 목록과 미리 대조한다.
