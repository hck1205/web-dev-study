새벽 3시, 가맹점별 하루 매출을 집계하는 배치가 120번째 묶음을 처리하다 죽었다. 담당자가 일어나 재시작 버튼을 눌렀고 배치는 정상 종료됐다. 그런데 아침에 정산팀이 묻는다. 결제 원장의 합계는 10억 9970만 6000원인데 집계 테이블은 11억 515만 500원이다. 544만 4500원이 어디서 왔을까. 재시작한 배치가 죽기 직전에 처리한 1,000건을 한 번 더 더한 것이다.

여러 행을 한 문장으로 묶어 넣으면 왜 빠른지, 큰 DELETE를 왜 잘게 나누는지는 [SQL 묶어 넣기와 타임아웃](/posts/sql-batch-timeout-pool)에서 다뤘다. 이 글은 그 위의 이야기다. 몇십만에서 몇억 건을 처리하는 작업 하나를 어떻게 나누고, 죽은 자리에서 어떻게 이어 가고, 두 번 돌아도 결과가 같게 만들려면 무엇이 필요한가. PostgreSQL 16과 Node.js 22로 결제 20만 건짜리 배치를 직접 돌리고 일부러 죽여 봤다.

## 요청을 기다리지 않고 한꺼번에 처리하는 일

배치(batch processing)는 쌓인 데이터를 정해진 때에 한꺼번에 처리하는 방식이다. 사용자가 요청할 때마다 처리하는 온라인 처리, 데이터가 들어오는 대로 흘려서 처리하는 스트림 처리와 비교된다. 하루 매출 정산, 이자 계산, 추천 점수 재계산, 오래된 데이터 정리, 대량 알림 발송이 대표적이다.

배치를 쓰는 이유는 셋이다. 한 건씩 처리할 때 드는 왕복과 커밋 비용을 묶어서 나눌 수 있고(처리량), "어제 0시부터 24시까지"처럼 경계가 분명한 데이터를 한 번에 맞춰 볼 수 있고(정합성), 사용자가 적은 시간에 몰아서 돌려 운영 트래픽과 자원을 덜 다툰다. 대신 결과가 늦다. 어제 매출은 오늘 아침에야 보인다. 몇 분 안에 봐야 하는 값이면 스트림 처리나 이벤트 기반 처리가 맞다([이벤트 기반 아키텍처](/posts/event-driven-architecture)).

이 글의 예제는 결제 원장(`payments`) 20만 건을 읽어 가맹점별 하루 매출(`merchant_daily`)에 더하는 작업이다. 아래 그림에서 다음을 누르면 배치 한 번이 지나가는 길이 보인다.

## 한 번에 하지 않고 묶음으로 나눈다

20만 건을 SQL 한 문장, 트랜잭션 하나로 처리할 수도 있다. 작은 데이터라면 그게 가장 단순하다. 데이터가 커지면 문제가 생긴다. 트랜잭션이 몇십 분 열려 있으면 그동안 바뀐 행의 잠금을 쥐고 있고, 그 사이 생긴 죽은 행을 vacuum이 치우지 못하고, WAL이 한꺼번에 쏟아져 복제본이 뒤처진다. 무엇보다 99%에서 실패하면 처음부터 다시 해야 한다.

그래서 묶음(chunk) 단위로 나눈다. 묶음 하나는 "읽고, 가공하고, 쓰고, 커밋"의 한 바퀴다. Spring Batch는 이 구조를 Job(작업), Step(단계), chunk(묶음)로 부르고, 한 바퀴를 ItemReader, ItemProcessor, ItemWriter로 나눈다. 이름은 달라도 하는 일은 같다.

읽을 때는 OFFSET을 쓰지 않는다. 묶음이 뒤로 갈수록 OFFSET이 읽고 버리는 행이 늘어서 마지막 묶음이 첫 묶음보다 수백 배 느려진다. 마지막으로 처리한 id보다 큰 것을 읽는 키셋 방식으로 읽는다. 정렬 키가 유일해야 하는 이유는 [페이지와 정렬](/posts/api-pagination-sorting)에서 봤다. 아래 그림은 묶음 한 바퀴와 체크포인트다.

## 묶음 크기는 얼마가 좋나

같은 서버 안에서 정산 줄 2만 건을 묶음 크기만 바꿔 가며 넣었다. 묶음마다 `unnest`로 배열을 받아 한 문장으로 넣고 자동 커밋한다. 두 번 돌렸다.

```bash
# 묶음 크기 1, 10, 100, 1000, 5000으로 2만 건씩 넣는다
node sizes.js
```

```text
batch   round_trips   elapsed   rows/s
1       20000           7.87s   2541
10      2000            1.15s   17349
100     200             0.24s   81718
1000    20              0.12s   169806
5000    4               0.09s   234207
batch   round_trips   elapsed   rows/s
1       20000           8.54s   2341
10      2000            0.95s   21018
100     200             0.28s   71009
1000    20              0.13s   159388
5000    4               0.09s   217188
```

1건씩은 8초 안팎, 1000건씩은 0.12초다. 70배 가까운 차이가 왕복 횟수에서 나온다. 1건씩이면 문장 2만 개를 보내고 2만 번 커밋을 기다린다. 그런데 1000에서 5000으로 늘린 효과는 0.12초에서 0.09초로 작다. 왕복이 20번에서 4번으로 줄어도 이미 행 자체를 쓰는 시간이 대부분이기 때문이다.

이 측정은 같은 서버 안이라 왕복이 거의 공짜인 경우다. 앱 서버와 DB가 다른 존에 있어서 왕복에 1ms가 더 든다면, 1건씩은 2만 번 × 1ms = 20초가 더해지고 1000건씩은 20번 × 1ms = 0.02초가 더해진다. 네트워크가 멀수록 묶음의 효과가 커진다. 아래 함수로 계산해 보자. 왕복 한 번에 드는 시간과 행 하나에 드는 시간을 마이크로초로 받아 전체 시간을 어림한다.

왕복 390µs, 행당 5µs는 위 측정을 대충 맞춘 값이다. 첫 테스트(7.9초)와 둘째(0.108초)가 측정과 비슷하다. 넷째 테스트를 보면 1000에서 5000으로 늘려도 행 쓰는 시간 0.1초가 그대로 남는다.

그럼 무조건 크게 잡으면 될까. 묶음이 커지면 다른 비용이 는다. 묶음 하나의 트랜잭션이 길어져 잠금을 오래 쥐고, 실패하면 다시 할 양이 크고, 앱 메모리에 올리는 행도 많다. `VALUES`로 행마다 자리표시자를 만들면 PostgreSQL 프로토콜의 한 문장당 파라미터 상한(65,535개)에 걸린다. 위처럼 열마다 배열 하나를 넘기는 `unnest`는 행 수와 상관없이 파라미터가 4개라 이 상한을 피한다. 보통 500~5000 사이에서 시작해, 묶음 하나가 1초 안쪽으로 끝나는 크기를 고른다.

## 죽은 자리에서 다시 시작하기

처음 사례를 그대로 재현했다. 체크포인트를 집계와 따로 커밋하는 버전(`separate`)과 한 트랜잭션으로 커밋하는 버전(`same`)을 만들고, 둘 다 120번째 묶음에서 죽게 한 뒤 다시 돌렸다.

```bash
# 집계를 커밋한 직후, 체크포인트를 쓰기 전에 죽는다
node job.js separate 120
# 다시 돌린다
node job.js separate
```

```text
start mode=separate from last_id=0
crash in chunk 120 (집계 커밋 후, 체크포인트 전)
start mode=separate from last_id=119000
done chunks=81 last_id=200000 419ms
```

```sql
SELECT (SELECT sum(amount) FROM payments)      AS source_total,
       (SELECT sum(total)  FROM merchant_daily) AS daily_total,
       (SELECT sum(cnt)    FROM merchant_daily) AS daily_cnt;
```

```text
 source_total | daily_total | daily_cnt 
--------------+-------------+-----------
   1099706000 |  1105150500 |    201000
(1 row)
```

건수가 20만 1000건, 금액이 544만 4500원 많다. 120번째 묶음의 집계는 커밋됐는데 체크포인트는 119000에 머물러 있어서, 재시작이 그 묶음을 한 번 더 더했다. 아래 그림이 그 틈이다.

합계가 원장과 정확히 같다. 체크포인트와 결과를 같은 데이터베이스, 같은 트랜잭션에 두는 게 요령이다. 결과는 DB에 쓰는데 체크포인트는 파일이나 Redis에 두면 다시 위의 틈이 생긴다. 결과를 쓰는 곳이 S3나 다른 시스템이라 같은 트랜잭션에 넣을 수 없다면, 아래처럼 다시 해도 괜찮은 쓰기로 바꾼다.

## 두 번 돌아도 결과가 같게 쓴다

체크포인트가 완벽해도 배치는 두 번 돈다. 담당자가 실패한 줄 알고 수동으로 한 번 더 돌리거나, 스케줄러가 재시도하거나, 데이터를 고친 뒤 그날 치를 다시 돌린다. 그래서 쓰기 자체를 멱등하게 만든다. 같은 입력으로 몇 번을 돌려도 결과가 같게.

가장 쉬운 건 원본 한 행이 결과 한 행이 되는 경우다. 원본 키를 결과의 유니크 키로 삼고 `ON CONFLICT DO NOTHING`이나 덮어쓰기로 넣는다.

```sql
-- 결제 한 건 → 정산 줄 한 건. 다시 돌려도 이미 있는 줄은 건너뛴다
INSERT INTO settlement_lines (payment_id, merchant_id, fee, net)
SELECT id, merchant_id, round(amount * 0.03), amount - round(amount * 0.03)
FROM payments WHERE id BETWEEN 1 AND 10000
ON CONFLICT (payment_id) DO NOTHING;

-- 값이 바뀌었을 수 있으면 덮어쓴다 (더하지 않는다)
-- ON CONFLICT (payment_id) DO UPDATE SET fee = EXCLUDED.fee, net = EXCLUDED.net;
```

위의 매출 집계처럼 여러 행을 더해 하나를 만드는 경우는 `total = total + EXCLUDED.total`이라 그 자체로는 멱등하지 않다. 방법이 두 가지다. 하나는 앞에서 본 대로 더하기와 체크포인트를 한 트랜잭션에 넣는 것이다. 다른 하나는 더하지 않고 다시 계산해서 덮어쓰는 것이다. 하루 치를 통째로 다시 계산해 그날 치를 지우고 넣으면, 몇 번을 돌려도 같은 결과다.

```sql
BEGIN;
-- 그날 치 집계를 지우고 원장에서 다시 계산해 넣는다
DELETE FROM merchant_daily WHERE day = date '2026-10-19';
INSERT INTO merchant_daily (merchant_id, day, total, cnt)
SELECT merchant_id, (paid_at AT TIME ZONE 'Asia/Seoul')::date, sum(amount), count(*)
FROM payments
WHERE paid_at >= timestamptz '2026-10-19 00:00:00+09'
  AND paid_at <  timestamptz '2026-10-20 00:00:00+09'
GROUP BY 1, 2;
COMMIT;
```

```text
BEGIN
DELETE 50
INSERT 0 50
COMMIT
 source_total | daily_total | daily_cnt 
--------------+-------------+-----------
   1099706000 |  1099706000 |    200000
(1 row)
```

가맹점 50곳의 그날 치 50줄을 지우고 다시 넣었다. 앞에서 이중으로 더해진 집계가 있었더라도 이 한 번으로 원장과 맞춰진다.

덮어쓰기는 단위가 작을 때(하루, 가맹점 하나) 좋다. 단위가 크면 한 트랜잭션이 너무 길어지니 파티션을 하루 단위로 나눠 두고 그 파티션만 다시 만든다. 날짜 경계에서는 시간대를 꼭 적는다. `paid_at::date`는 세션 시간대를 따라서, 서버가 UTC면 한국 시각 오전 9시 전 결제가 전날로 들어간다.

DB 밖으로 나가는 일은 따로 생각해야 한다. 알림 메일이나 푸시를 보내는 배치는 DB를 롤백해도 이미 나간 메일을 되돌릴 수 없다. 보낼 대상마다 `sent_at` 같은 표시를 두고, "보내고 표시"가 아니라 "보낼 것을 표시하고 커밋한 뒤 보내고, 보낸 것을 표시"로 단계를 나눈다. 보내는 쪽 API가 멱등성 키를 받으면 대상 ID로 만든 키를 넘긴다. 이 이야기는 [멱등성 키 구현](/posts/idempotency-key)과 같은 구조다.

## 한 줄 때문에 전체가 멈추지 않게

20만 건 중 한 건의 금액이 음수라 제약에 걸리면 묶음 전체가 롤백된다. 재시작해도 같은 줄에서 또 실패한다. 이런 줄을 독이 든 줄(poison record)이라고 부른다. 대응은 세 가지로 나눈다.

일시적인 실패(연결 끊김, 데드락, 잠금 타임아웃)는 그 묶음을 몇 번 다시 시도한다. 데이터가 잘못된 실패는 다시 해도 같으니 건너뛰고, 실패한 행과 이유를 따로 적는다.


## 여러 작업자로 나눠 돌리기

한 프로세스로 너무 오래 걸리면 범위를 나눠 여러 작업자가 동시에 처리한다. 범위를 미리 표로 만들어 두고, 작업자가 하나씩 집어 가게 한다. 이때 `FOR UPDATE SKIP LOCKED`를 쓰면 다른 작업자가 잡은 줄은 기다리지 않고 건너뛴다.

```sql
CREATE TABLE job_chunks (
  id        int PRIMARY KEY,
  from_id   bigint NOT NULL,
  to_id     bigint NOT NULL,
  status    text   NOT NULL DEFAULT 'pending',   -- pending | running | done
  worker    text,
  locked_at timestamptz
);
-- 1만 건씩 20개 범위
INSERT INTO job_chunks (id, from_id, to_id)
SELECT g, (g - 1) * 10000 + 1, g * 10000 FROM generate_series(1, 20) g;

-- 작업자가 일감 하나를 집는 쿼리
UPDATE job_chunks SET status = 'running', worker = $1, locked_at = now()
WHERE id = (SELECT id FROM job_chunks WHERE status = 'pending'
            ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1)
RETURNING id, from_id, to_id;
```

작업자 셋을 동시에 띄웠다.

```bash
# 작업자 셋이 같은 청크 표에서 일감을 집어 간다
node worker.js w1 & node worker.js w2 & node worker.js w3 & wait
```

```text

w1 took chunks 3,6,9,12,15,19
w3 took chunks 2,5,8,10,14,17,18
```

```text

--------+--------

(3 rows)

```

20개 범위가 겹치지 않게 나뉘었고 정산 줄은 정확히 20만 건이다. 작업자가 범위를 처리하다 죽으면 그 줄은 `running`으로 남는다. `locked_at`이 충분히 오래된 `running` 줄을 다시 `pending`으로 돌리는 규칙을 둔다. 다시 처리해도 결과 쓰기가 `ON CONFLICT DO NOTHING`이라 겹치지 않는다. 앞 절의 멱등한 쓰기가 여기서도 받쳐 준다.

작업자를 늘린다고 계속 빨라지지는 않는다. 결국 같은 DB에 쓰니 DB의 CPU, 디스크, 잠금이 한계다. 작업자 수를 늘려 가며 초당 처리 행 수를 재 보고, 더 늘어나지 않는 지점에서 멈춘다. 같은 행을 여러 작업자가 갱신하는 집계라면 서로 잠금을 기다리다 [데드락](/posts/db-locking-deadlock)이 날 수 있으니, 범위를 가맹점 단위로 나눠 같은 결과 행을 한 작업자만 만지게 한다.

## 운영 DB 옆에서 조용히 돌리기

배치는 대개 운영 DB를 같이 쓴다. 배치 때문에 새벽 주문이 느려지면 안 된다.

같은 작업이 두 번 동시에 돌지 않게 막는다. 스케줄러의 이전 실행이 아직 안 끝났는데 다음 실행이 시작되는 일이 흔하다. 쿠버네티스 CronJob이라면 `concurrencyPolicy: Forbid`로 막고, DB 쪽에서도 어드바이저리 락으로 한 번 더 막는다.

```bash
# 첫 실행이 잠금을 잡은 상태에서 두 번째 실행이 같은 잠금을 시도한다
node lock.js
```

```text
run A: true
run B: false -> 이미 돌고 있으니 종료
run B again: true
```

`pg_try_advisory_lock`은 기다리지 않고 바로 참·거짓을 돌려준다. 잠금은 세션에 붙어 있어서 첫 실행의 연결이 끊기면(프로세스가 죽어도) 저절로 풀린다. PgBouncer를 트랜잭션 모드로 쓰면 세션이 연결마다 바뀌어 이 잠금이 엉뚱하게 동작하니, 배치는 풀러를 거치지 않고 직접 붙거나 `pg_try_advisory_xact_lock`을 트랜잭션 안에서 쓴다.

부하는 스스로 조절한다. 묶음 사이에 수십~수백 ms를 쉬면 autovacuum과 복제가 따라올 틈이 생긴다. 쓰기 배치를 돌리는 동안 복제본 지연(`pg_stat_replication`의 `replay_lag`)이 몇 초를 넘으면 쉬는 시간을 늘리는 식으로 만들 수도 있다. 읽기만 하는 큰 집계는 복제본에서 읽는다. 다만 복제본에서 오래 도는 쿼리는 주 서버의 정리 작업과 부딪혀 취소될 수 있다(`canceling statement due to conflict with recovery`).

세션에는 한도를 건다. `SET statement_timeout = '30s'`로 묶음 하나가 끝없이 돌지 않게, `SET lock_timeout = '5s'`로 운영 트랜잭션이 쥔 잠금을 하염없이 기다리지 않게 한다. 걸리면 그 묶음을 실패로 보고 재시도 규칙을 탄다.

진행 상황은 숫자로 남긴다. 처리한 행 수, 초당 처리 행 수, 남은 행 수로 끝나는 시각을 어림해 로그와 지표로 내보낸다. "06:00까지 안 끝나면 알림"처럼 마감 시각 기준 알림을 걸면, 실패는 안 했지만 평소보다 다섯 배 느린 배치를 아침 업무 전에 알 수 있다.

## 새벽 배치 알림을 받으면 여기부터 본다

"배치가 실패했다"는 알림이면 먼저 어디까지 했는지 본다. 체크포인트 테이블의 `last_id`와 `updated_at`, 청크 표의 상태별 개수다. 재시작하기 전에 결과가 원본과 맞는지(합계, 건수) 확인하는 쿼리를 하나 만들어 두면, 처음 사례 같은 이중 집계를 재시작 전후로 바로 잡아낸다.

"배치는 성공했는데 숫자가 안 맞는다"면 쓰기가 멱등한지, 체크포인트가 결과와 같은 트랜잭션인지 본다. 수동 재실행 이력이 있는지도 확인한다. 날짜 경계가 하루씩 밀렸다면 시간대 문제다.

"배치가 평소보다 훨씬 오래 걸린다"면 묶음 하나의 시간이 뒤로 갈수록 느는지 본다. 늘어난다면 읽기에 OFFSET을 쓰고 있을 가능성이 크다. 일정하게 느리다면 `pg_stat_activity`에서 배치 세션의 `wait_event`를 본다. `Lock`이면 운영 트랜잭션과 부딪히는 중이다.

"배치가 도는 시간에 서비스가 느려진다"면 묶음 크기와 작업자 수를 줄이고 묶음 사이에 쉬는 시간을 넣는다. 복제본 지연과 디스크 쓰기량을 함께 본다. 몇 시간짜리 트랜잭션이 하나 열려 있다면 묶음마다 커밋하지 않는 코드다.

## 나누고, 적고, 두 번 돌아도 괜찮게

배치를 튼튼하게 만드는 건 결국 세 가지다. 묶음으로 나눠서 실패해도 잃는 양을 줄이고, 결과와 같은 트랜잭션에 어디까지 했는지 적어 죽은 자리에서 이어 가고, 쓰기를 멱등하게 만들어 두 번 돌아도 숫자가 맞게 한다. 묶음을 왜 묶는지의 원리는 [SQL 묶어 넣기와 타임아웃](/posts/sql-batch-timeout-pool)에, 같은 생각을 API 요청에 적용한 건 [멱등성 키 구현](/posts/idempotency-key)에 있다.

## 면접에서 나올 만한 질문

### 대량 데이터를 트랜잭션 하나로 처리하지 않고 묶음으로 나누는 이유는 무엇인가요?

긴 트랜잭션은 잠금을 오래 쥐고, vacuum이 죽은 행을 치우지 못하게 막고, WAL을 한꺼번에 쏟아 복제를 늦춘다. 실패하면 처음부터 다시 해야 한다는 것도 크다. 묶음마다 커밋하면 실패해도 잃는 양이 묶음 하나로 줄고, 체크포인트로 이어서 할 수 있다.

### 배치가 중간에 죽었을 때 재시작하면 데이터가 중복될 수 있나요?

결과를 쓰는 것과 진행 위치(체크포인트)를 따로 커밋하면 그 사이에서 죽었을 때 중복된다. 실제로 집계 커밋 후 체크포인트 전에 죽였더니 재시작 뒤 1000건이 두 번 더해졌다. 결과와 체크포인트를 한 트랜잭션으로 커밋하거나, 결과 쓰기 자체를 멱등하게 만들어 막는다.

### 배치 쓰기를 멱등하게 만드는 방법은 무엇인가요?

원본 한 행이 결과 한 행이면 원본 키를 유니크 키로 두고 ON CONFLICT DO NOTHING이나 덮어쓰기로 넣는다. 여러 행을 더하는 집계는 더하기 대신 단위(하루, 파티션)를 통째로 다시 계산해 지우고 넣는다. DB 밖으로 나가는 메일이나 결제는 대상별 처리 표시와 멱등성 키로 막는다.

### 묶음 크기는 어떻게 정하나요?

묶음이 커질수록 왕복과 커밋 비용이 줄지만 효과는 금방 줄어든다. 같은 서버에서 2만 건을 1건씩 넣으면 약 8초, 1000건씩은 0.12초, 5000건씩은 0.09초였다. 너무 크면 트랜잭션이 길어지고 실패 시 다시 할 양과 메모리가 늘어서, 보통 묶음 하나가 1초 안쪽으로 끝나는 500~5000 사이에서 고른다.

### 배치를 여러 작업자로 병렬 처리하려면 어떻게 하나요?

처리 범위를 청크 표로 만들어 두고 작업자가 FOR UPDATE SKIP LOCKED로 하나씩 집어 가게 한다. 다른 작업자가 잡은 줄은 기다리지 않고 건너뛰어서 범위가 겹치지 않는다. 죽은 작업자의 줄은 locked_at이 오래되면 다시 대기로 돌리고, 결과 쓰기가 멱등하니 다시 처리해도 괜찮다.

### 같은 배치가 동시에 두 번 실행되는 것은 어떻게 막나요?

스케줄러 설정(CronJob의 concurrencyPolicy: Forbid 같은)으로 막고, DB에서도 pg_try_advisory_lock으로 한 번 더 막는다. 이 잠금은 세션에 붙어 있어 프로세스가 죽으면 저절로 풀린다. 트랜잭션 모드 풀러를 거치면 세션이 바뀌니 직접 연결하거나 트랜잭션 단위 잠금을 쓴다.

### 데이터 한 건이 잘못돼 묶음이 계속 실패하면 어떻게 하나요?

일시적인 실패는 재시도하고, 데이터 때문에 실패한 행은 한 건씩 다시 처리해 찾아낸 뒤 오류 표에 적고 건너뛴다. 건너뛰는 수에는 상한을 둬서 그 이상이면 코드나 스키마 문제로 보고 멈춘다. 정산처럼 한 건도 빠지면 안 되는 작업은 건너뛰지 않고 멈추는 쪽을 고른다.
