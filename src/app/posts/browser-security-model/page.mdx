결제 위젯을 iframe으로 붙였다. 위젯 내용이 길어지면 iframe 높이도 따라 늘어나야 해서, 부모 페이지에서 iframe 안의 문서 높이를 읽는 코드를 썼다. 콘솔에 이게 찍힌다.

```text
SecurityError: Failed to read a named property 'document' from 'Window': Blocked a frame with origin "http://app.example.test:18200" from accessing a cross-origin frame.
```

같은 화면에 보이는데 읽을 수 없다. 반대로 그 iframe의 주소를 바꾸는 코드는 아무 오류 없이 통과한다. 이 글은 브라우저가 페이지들 사이에 그어 둔 선을 따라간다. 무엇이 같은 출처인지, 왜 읽기는 막고 쓰기는 두는지, iframe과 대화하는 안전한 방법, 그리고 스펙터 이후 브라우저가 프로세스까지 나누게 된 이유다. 실험은 로컬 서버에 `app.example.test`, `api.example.test`, `evil.test` 같은 이름을 붙이고 크로미움 141로 돌렸다. CORS 헤더 하나하나는 [CORS](/posts/cors), 요청 위조는 [CSRF](/posts/csrf), 스크립트 주입은 [XSS](/posts/xss)에서 다루고 여기서는 그 바탕이 되는 규칙을 본다.

## 출처와 사이트는 다른 말이다

쿠키와 보안 헤더 이야기를 하다 보면 "같은 출처"와 함께 "같은 사이트(same-site)"라는 말이 나온다. 둘은 범위가 다르다. 사이트는 스킴과 등록 가능한 도메인, 흔히 eTLD+1이라 부르는 부분이다.

eTLD는 "실질적인 최상위 도메인"이다. `com`이나 `kr`만이 아니라, 누구나 그 아래에 이름을 등록할 수 있는 `co.kr`, `github.io` 같은 접미사가 모두 여기 든다. 이 목록을 공개 접미사 목록(Public Suffix List)이라 부르고 브라우저가 내장한다. eTLD+1은 그 접미사에 이름 한 칸을 더 붙인 것이다. `shop.example.co.kr`의 사이트는 `example.co.kr`이고, `alice.github.io`의 사이트는 `alice.github.io` 그 자체다.

그래서 이런 조합이 생긴다.

- `https://app.example.com`과 `https://api.example.com`은 다른 출처지만 같은 사이트다.
- `https://example.com:8443`과 `https://example.com`도 다른 출처, 같은 사이트다. 포트는 사이트에 들어가지 않는다.
- `https://alice.github.io`와 `https://bob.github.io`는 다른 사이트다. `github.io`가 공개 접미사라서 둘은 남남이다.
- `http://example.com`과 `https://example.com`은 다른 사이트다. 크롬 계열은 2021년 무렵부터 스킴까지 사이트에 넣어 비교한다(schemeful same-site).

이 차이가 바로 드러나는 곳이 `SameSite` 쿠키다. `api.example.test`가 `SameSite=Lax`와 `SameSite=Strict` 쿠키를 심은 뒤, 같은 사이트인 `app.example.test`와 다른 사이트인 `evil.test`에서 각각 `api.example.test`로 요청을 보냈다. 서버가 받은 쿠키를 적었다.

```text
GET api.example.test/me cookie=lax=1; strict=1 origin=http://app.example.test:18200
GET api.example.test/me cookie=- origin=-
```

`app`에서 보낸 요청은 출처가 다른데도 `Strict` 쿠키까지 붙었다. `SameSite`는 이름 그대로 출처가 아니라 사이트를 본다. `evil.test`에서 보낸 요청에는 아무 쿠키도 없었다. 서브도메인끼리 API를 부르는 구조에서 CORS는 필요하지만 `SameSite` 때문에 쿠키가 빠지지는 않는다는 뜻이다. 반대로 서브도메인 하나가 뚫리면 그곳은 같은 사이트라서 `SameSite`로는 막히지 않는다. 사용자가 글을 올리는 서브도메인을 본 서비스와 같은 사이트에 두지 않는 이유다. 쿠키 옵션 전체는 [CSRF](/posts/csrf)에 있다.

출처와 사이트를 직접 비교해 보자. `URL`의 `origin`으로 출처는 바로 나온다. 사이트는 공개 접미사 목록에서 가장 긴 접미사를 찾아 이름 한 칸을 더 붙이면 된다. 실제 목록은 수천 줄이니 여기서는 몇 개만 둔다.

function siteOf(url) {
  const { protocol, hostname } = new URL(url);
  const labels = hostname.split(".");
  let best = "";
  for (const s of SUFFIXES) {
    // 가장 긴 접미사를 고른다: co.kr이 kr보다 우선
    if ((hostname === s || hostname.endsWith("." + s)) && s.length > best.length) best = s;

  if (!best || hostname === best) return protocol + "//" + hostname;
  const n = best.split(".").length;
  return protocol + "//" + labels.slice(-(n + 1)).join("."); // 접미사 + 한 칸
}

  const sameSite = siteOf(a) === siteOf(b);

}`}

## 보내고 거는 건 되고, 읽는 건 안 된다

같은 출처 정책을 "다른 출처와는 아무것도 못 한다"로 기억하면 틀린다. 웹은 처음부터 다른 사이트로 링크하고, 다른 사이트의 이미지를 걸고, 다른 사이트로 폼을 보내는 구조였다. 이걸 막으면 웹이 아니다. 그래서 브라우저는 세 가지를 다르게 다룬다.

`app.example.test` 페이지에서 `evil.test`를 상대로 여러 가지를 해 봤다.

```text
"readBody":     "SecurityError: Failed to read a named property 'document' from 'Window': Blocked a frame with origin \"http://app.example.test:18200\" from accessing a cross-origin frame.",
"embedScript":  true,
"imgSize":      1,
"getImageData": "SecurityError: Failed to execute 'getImageData' on 'CanvasRenderingContext2D': The canvas has been tainted by cross-origin data.",
"fetch":        "TypeError: Failed to fetch",
"noCors":       { "type": "opaque", "status": 0, "body": "" },
"postSent":     true,
"writeLocation": "ok"
```

서버 로그에는 이 요청들이 모두 도착해 있었다.

```text
GET evil.test/img.png
GET evil.test/lib.js
GET evil.test/frame
GET evil.test/data origin=http://app.example.test:18200
POST evil.test/post origin=http://app.example.test:18200
GET evil.test/frame?moved
```

정리하면 이렇다. 아래 그림에서 점이 흐르는 방향이 데이터가 움직이는 방향이다.

쓰기는 열려 있다. 다른 출처로 폼 제출 같은 단순 POST를 보내거나(`POST evil.test/post`가 서버에 닿았다) iframe의 주소를 바꾸는 것(`writeLocation: ok`)은 된다. 이 열린 문을 악용하는 것이 CSRF다. 브라우저는 요청을 보내 주고 쿠키도 붙여 주니, 서버가 요청의 출처를 따로 확인해야 한다.

임베드도 열려 있다. 다른 출처 스크립트는 내 페이지에서 실행됐고(`embedScript: true`), 이미지는 화면에 그려지고 크기도 알 수 있다(`imgSize: 1`). 다만 임베드한 것의 내용은 못 읽는다. 이미지를 캔버스에 그린 뒤 픽셀을 읽으려 하자 "캔버스가 오염됐다(tainted)"며 막혔다. 보여 주는 것과 내 코드가 그 내용을 손에 쥐는 것은 다르다.

읽기는 막혀 있다. iframe 안의 DOM, `fetch` 응답 본문이 그렇다. `fetch`는 요청이 서버까지 갔는데 응답을 자바스크립트에 넘기지 않아 `TypeError`가 났다. `mode: "no-cors"`로 보내면 에러는 안 나지만 상태 0, 본문이 빈 불투명(opaque) 응답만 받는다. 서버가 "이 출처는 읽어도 된다"고 헤더로 허락하면 읽기 문을 여는 것이 CORS다.

쓰기가 어디까지 열려 있는지도 정해져 있다. HTML 폼이 원래 보낼 수 있던 요청, 즉 `GET`·`POST`에 폼 형식 본문 정도만 묻지 않고 바로 나간다. `Content-Type: application/json`이나 `Authorization` 헤더를 단 요청은 폼으로는 만들 수 없던 요청이라, 브라우저가 먼저 서버에 허락을 묻는 사전 요청(preflight)을 보낸다. 예전 서버들이 "폼으로는 이런 요청이 올 수 없다"고 믿고 만들어졌기 때문에, 새로 생긴 능력에만 확인을 붙인 것이다.

이 비대칭을 알면 처음 장면이 풀린다. iframe 높이를 부모가 직접 읽을 수는 없다. 위젯이 자기 높이를 재서 부모에게 알려 줘야 한다. 그 통로가 `postMessage`다.

## 다른 출처 창과 대화하는 통로, postMessage

      title: "부모가 보낸 쪽과 창을 모두 확인한다",
      detail: "event.origin이 위젯 출처와 정확히 같고, event.source가 바로 그 iframe의 contentWindow인지 본다. 두 조건을 통과한 메시지만, 모양까지 검사한 뒤 쓴다.",
    },
  ]}
/>

코드로 쓰면 이렇다.

```ts
const WIDGET_ORIGIN = "https://pay.example.net";

window.addEventListener("message", (event) => {
  if (event.origin !== WIDGET_ORIGIN) return;              // 1. 정확히 같은 문자열인가
  if (event.source !== frame.contentWindow) return;        // 2. 그 iframe이 보낸 것인가
  const data = event.data;
  if (data?.type !== "resize" || typeof data.height !== "number") return; // 3. 모양 검사
  frame.style.height = `${Math.min(data.height, 4000)}px`; // 4. 값의 범위도 제한
});

frame.contentWindow!.postMessage({ type: "ready" }, WIDGET_ORIGIN); // "*" 쓰지 않는다
```

받는 쪽에서 흔한 실수는 출처를 느슨하게 비교하는 것이다. `event.origin.includes("example.com")`은 `https://example.com.evil.test`도 통과시키고, `endsWith("example.com")`은 `https://notexample.com`을 통과시킨다. 허용 목록을 두고 문자열 전체가 같은지 본다. 그리고 받은 데이터를 `innerHTML`에 넣거나 `location.href`로 쓰면, 출처 확인이 뚫리는 순간 그대로 XSS나 열린 리다이렉트가 된다.

보내는 쪽에서는 `targetOrigin`에 `"*"`를 쓰지 않는다. 받는 창이 그사이 다른 사이트로 이동했으면 `"*"`로 보낸 토큰이 그 사이트로 간다. 출처를 지정했을 때 어떻게 되는지 확인해 봤다. 위젯(`evil.test`)에 `targetOrigin`을 `bank.test`로 한 번, `evil.test`로 한 번 보냈다.

```text
parent received: got B
```

맞지 않는 출처로 보낸 A는 전달되지 않았고, 보낸 쪽에 예외도 나지 않았다. 버려졌다는 걸 코드는 모른다. 그래서 응답이 꼭 필요한 대화는 요청에 번호를 붙이고 시간 제한을 둔다.

## iframe에 권한을 덜 주는 sandbox

다른 출처 iframe은 내 DOM을 못 읽지만, 그 안에서 할 수 있는 일은 많다. 스크립트를 돌리고, 팝업을 띄우고, 최상위 창을 피싱 페이지로 바꾸고(`top.location = ...`), 폼을 보낸다. 사용자가 올린 HTML 미리보기, 광고, 외부 위젯처럼 믿기 어려운 내용을 iframe에 담을 때는 `sandbox` 속성으로 권한을 줄인다.

`sandbox`를 값 없이 쓰면 거의 모든 것이 꺼진다. 필요한 것만 토큰으로 다시 켠다. 스크립트만 허용한 iframe 안에서 몇 가지를 확인해 봤다.

```html
<iframe sandbox="allow-scripts" srcdoc="..."></iframe>
```

```text
{"origin":"null",
 "ls":"SecurityError: Failed to read the 'localStorage' property from 'Window': The document is sandboxed and lacks the 'allow-same-origin' flag.",
 "cookie":"SecurityError: Failed to read the 'cookie' property from 'Document': The document is sandboxed and lacks the 'allow-same-origin' flag.",
 "top":"SecurityError"}
```

`allow-same-origin`이 없으면 iframe은 고유한 불투명 출처(`"null"`)를 받는다. 부모와 같은 서버에서 온 문서여도 다른 출처가 되어 부모의 쿠키와 저장소를 못 본다. 메시지를 받은 부모 쪽 `event.origin`도 `"null"`로 찍혔다. 그래서 sandbox iframe의 메시지를 받을 때는 출처 대신 `event.source`로 확인해야 한다. `"null"` 문자열을 허용 목록에 넣으면 다른 모든 sandbox iframe과 `data:` URL 문서도 통과한다.

자주 쓰는 토큰은 `allow-scripts`, `allow-forms`, `allow-popups`, `allow-modals`, 사용자가 누를 때만 최상위 이동을 허락하는 `allow-top-navigation-by-user-activation` 정도다. 피해야 할 조합은 `allow-scripts allow-same-origin`을 부모와 같은 출처 문서에 함께 주는 것이다. 같은 출처가 된 스크립트는 부모 DOM에 손을 뻗어 자기 iframe의 `sandbox` 속성을 지우고 다시 불러올 수 있다. 사용자 HTML을 미리 보여 주는 기능이라면 아예 별도 도메인(다른 사이트)에서 내려 주고 sandbox를 함께 건다. 카메라, 마이크, 위치 같은 기능 권한은 `sandbox`가 아니라 iframe의 `allow` 속성(Permissions Policy)으로 따로 준다.

## 같은 위젯도 어느 사이트에 걸렸느냐에 따라 저장소가 나뉜다

출처만으로 저장소를 나누면 새는 길이 하나 있다. `widget.test`라는 위젯이 `news.test`와 `shop.test`에 모두 iframe으로 걸려 있다고 하자. 위젯의 `localStorage`가 출처 하나에 한 칸뿐이면, 위젯은 뉴스 사이트에서 심은 방문자 번호를 쇼핑 사이트에서 다시 읽는다. 사용자가 어느 사이트들을 돌아다녔는지 위젯 회사가 이어 붙일 수 있다. 서드파티 쿠키로 하던 추적을 저장소로 똑같이 하는 셈이다.

그래서 브라우저들은 서드파티 iframe의 저장소를 최상위 사이트별로 나눈다(storage partitioning). 위젯이 처음 보는 방문자면 번호를 심고, 이미 있으면 그 값을 부모에게 알려 주게 만들어 세 번 방문했다.

```text
news.test {"before":null,"top":"http://news.test:18200/"}
shop.test {"before":null,"top":"http://shop.test:18200/"}
news.test {"before":"id-news.test","top":"http://news.test:18200/"}
widget.test top-level: null
```

뉴스 사이트에서 심은 값을 쇼핑 사이트 안의 위젯은 못 봤다. 뉴스 사이트로 돌아가면 다시 보인다. `widget.test`에 직접 들어가도 비어 있다. 같은 출처라도 "어느 최상위 사이트 아래에서 열렸나"가 열쇠에 함께 들어간다. 크롬 계열은 115 무렵부터 `localStorage`, IndexedDB, Cache Storage 같은 저장소를 이렇게 나눴고, HTTP 캐시는 그보다 먼저 최상위 사이트별로 나눴다. 다른 사이트에서 같은 파일을 받았는지 캐시 적중 시간으로 알아내는 공격도 이걸로 막힌다. 사파리와 파이어폭스도 각자의 방식으로 나눈다.

같은 실험을 Playwright 기본 설정으로 돌렸을 때는 세 번 모두 같은 값이 보였다. Playwright가 띄우는 크로미움은 호환성 때문에 이 분할 기능(`ThirdPartyStoragePartitioning`)을 꺼 둔 채로 시작한다. 위젯이나 임베드 SDK를 만든다면 E2E 테스트가 통과해도 실제 크롬에서는 저장소가 나뉠 수 있다는 걸 염두에 둔다. 쿠키 쪽 이야기, 즉 서드파티 쿠키가 막히거나 나뉠 때 로그인 흐름이 어떻게 깨지는지는 [SPA 인증 토큰 저장](/posts/spa-auth-token-storage)에서 본다.

## 내 페이지가 남의 iframe에 들어갈 때

방향을 바꾸면 다른 문제가 나온다. 공격자가 내 사이트를 투명한 iframe으로 자기 페이지에 깔고, 그 위에 "경품 받기" 버튼을 겹쳐 둔다. 사용자는 경품 버튼을 눌렀다고 생각하지만 실제로는 아래 깔린 내 사이트의 "계정 삭제"를 누른다. 클릭재킹이다. 같은 출처 정책은 이걸 막지 않는다. 공격자는 내 DOM을 읽지 않았고 그냥 화면에 걸었을 뿐이다. 임베드는 열려 있으니까.

막는 방법은 내 응답이 "나를 iframe에 넣어도 되는 곳"을 선언하는 것이다. `Content-Security-Policy: frame-ancestors 'self'`가 표준이고, 오래된 `X-Frame-Options: DENY` 또는 `SAMEORIGIN`도 함께 보내는 경우가 많다. 둘 다 있으면 지원하는 브라우저는 `frame-ancestors`를 따른다. 헤더를 실제로 걸어 보고 깨지는 것을 확인하는 과정은 [웹 보안 헤더](/posts/web-security-headers)에 있다. 로그인, 결제, 설정처럼 누르는 순간 상태가 바뀌는 페이지에는 꼭 둔다.

## 브라우저가 프로세스까지 나누는 이유

여기까지의 규칙은 모두 브라우저 코드가 "이 접근은 허용, 저 접근은 차단"이라고 확인해서 지킨다. 2018년에 공개된 스펙터(Spectre)는 이 전제를 흔들었다. CPU가 분기 결과를 미리 짐작해 실행하는 과정에서 캐시에 흔적이 남고, 그 흔적을 정밀한 타이머로 재면 같은 프로세스 메모리의 다른 데이터를 읽어 낼 수 있다. 자바스크립트로도 된다는 것이 보였다.

문제는 그때까지 다른 출처 iframe, 이미지로 받은 다른 출처 응답이 같은 렌더러 프로세스 메모리에 함께 있을 수 있었다는 점이다. 브라우저 코드가 읽기를 막아도, 메모리에 같이 있으면 부채널로 새어 나온다. 그래서 브라우저들이 꺼낸 답이 사이트 격리(Site Isolation)다. 사이트마다 다른 렌더러 프로세스를 쓰게 해서, 다른 사이트의 데이터가 애초에 내 프로세스 메모리에 들어오지 않게 한다. 크롬 데스크톱은 2018년부터 기본으로 켰고, 안드로이드 크롬은 메모리 때문에 로그인하는 사이트 위주로 적용한다. 파이어폭스는 Fission이라는 이름으로 데스크톱에 기본 적용했다. 사파리는 다른 방식과 일정으로 진행하고 있어 같은 수준이라고 단정하기 어렵다.

출처가 아니라 사이트 단위인 이유는 앞에서 본 `document.domain` 때문이다. 같은 사이트의 서브도메인끼리는 이걸로 서로의 DOM을 만질 수 있었으니 같은 프로세스에 있어야 했다. 이 기능이 사라지는 중이라, 크롬은 `Origin-Agent-Cluster` 헤더 같은 장치로 출처 단위 격리를 넓히고 있다.

프로세스를 나눠도 남는 틈이 있다. `img`나 `script` 태그로 다른 출처의 JSON이나 HTML을 부르면 그 응답은 내 프로세스로 들어온다. 이미지가 아니니 화면에는 깨져 보여도 메모리에는 있다. 크롬은 이런 응답 중 이미지·스크립트처럼 보이지 않는 것을 렌더러에 넘기기 전에 걸러 낸다(예전 이름 CORB, 지금은 ORB). 서버 쪽에서 직접 선을 긋는 헤더도 있다.

- `Cross-Origin-Resource-Policy: same-origin` 또는 `same-site`. 이 자원을 다른 출처, 다른 사이트 페이지가 임베드하지 못하게 한다. 사용자별 데이터가 담긴 응답에 둔다.
- `Cross-Origin-Opener-Policy: same-origin`. 내가 연 팝업, 나를 연 창이 다른 출처면 서로의 참조를 끊어 다른 브라우징 컨텍스트 그룹(다른 프로세스가 될 수 있다)으로 보낸다.
- `Cross-Origin-Embedder-Policy: require-corp`. 내 페이지가 임베드하는 다른 출처 자원은 모두 CORP나 CORS로 동의한 것이어야 한다.

COOP와 COEP를 함께 켜면 페이지가 교차 출처 격리 상태가 되고, 그때만 `SharedArrayBuffer`와 정밀한 타이머가 허락된다. 공유 메모리로 정밀 타이머를 만들 수 있으니, 내 프로세스에 동의 없는 다른 출처 데이터가 없다는 것이 보장될 때만 주는 것이다. 워커에서 이걸 실제로 쓰는 모습은 [Web Worker](/posts/web-workers)에 있다.

## 내가 부른 스크립트는 내 권한으로 돈다

같은 출처 정책은 출처 사이의 선이다. `<script src="https://cdn.other.com/widget.js">`로 부른 스크립트는 다른 출처에서 왔어도 내 페이지의 출처로 실행된다. 앞의 실험에서 `evil.test/lib.js`가 내 페이지의 `window`에 값을 쓴 것처럼, 내 DOM, 내 쿠키(`HttpOnly`가 아닌 것), 내 `localStorage`, 사용자가 입력하는 비밀번호 칸까지 전부 만질 수 있다. 분석 도구, 채팅 위젯, 광고, 태그 매니저가 모두 그렇다. 그 회사의 CDN이나 배포 계정이 털리면 내 사이트가 털린 것과 같다. 2024년에는 널리 쓰이던 `polyfill.io` 도메인이 다른 주인에게 넘어간 뒤 일부 방문자에게 악성 코드를 내려 준 일이 있었다.

파일이 바뀌지 않는 정적 라이브러리라면 하위 자원 무결성(SRI)으로 내용을 고정한다. `integrity`에 파일 해시를 적으면 브라우저가 받은 내용의 해시를 계산해 비교하고, 다르면 실행하지 않는다. 해시를 한 글자 다르게 넣은 것과 맞게 넣은 것을 나란히 불러 봤다.

```html
<script src="https://cdn.test/lib.js" integrity="sha384-(틀린 해시)" crossorigin="anonymous"></script>
<script src="https://cdn.test/lib.js?2" integrity="sha384-(맞는 해시)" crossorigin="anonymous"></script>
```

```text
[console] error Failed to find a valid digest in the 'integrity' attribute for resource 'http://cdn.test:18200/lib.js' with computed SHA-384 integrity 'PhPSRXHFoc7i594H66UZAq4SAI+QBdmiT1N4FByH7iw6iE36ibHIc4ZKLBdHDvFG'. The resource has been blocked.
{ first: undefined, after: true }
```

첫 번째는 막혀 실행되지 않았고, 두 번째만 실행됐다. 해시는 `openssl dgst -sha384 -binary lib.js | openssl base64 -A`로 만든다. `crossorigin="anonymous"`가 필요한 점도 기억한다. 다른 출처 응답의 내용을 확인하는 일이라 CORS로 읽기 허락을 받아야 하고, CDN이 `Access-Control-Allow-Origin`을 보내 줘야 한다.

SRI의 한계도 분명하다. "최신 버전을 항상 주는" 주소나, 태그 매니저처럼 내용이 계속 바뀌는 스크립트에는 걸 수 없다. 해시를 걸면 업데이트될 때마다 깨진다. 그런 스크립트는 다른 방법으로 반경을 줄인다. CSP의 `script-src`로 실행될 수 있는 출처를 좁히고, 결제·로그인 페이지에는 서드파티 스크립트를 아예 빼고, 채팅 위젯처럼 화면만 빌려주면 되는 것은 sandbox iframe에 담아 내 DOM과 떼어 놓는다. 공급망 관점의 정리는 [OWASP Top 10 지도](/posts/owasp-top-10-map)에도 있다.

## 현장에서 출처 문제를 만나는 순간

증상으로 거꾸로 찾아가면 대개 이 중 하나다.

`Blocked a frame with origin ... from accessing a cross-origin frame`이 뜬다면 iframe 안을 직접 읽으려 한 것이다. 높이 맞추기, 폼 값 읽기 같은 일을 `postMessage`로 바꾼다. 결제·인증 위젯이라면 제공사가 이미 메시지 규약을 문서로 주는 경우가 많다.

`The canvas has been tainted by cross-origin data`는 CDN 이미지를 캔버스에 그린 뒤 `toDataURL`이나 `getImageData`를 부를 때 난다. `<img crossorigin="anonymous">`(또는 `img.crossOrigin = "anonymous"`)로 CORS 요청을 하고, CDN이 `Access-Control-Allow-Origin`을 돌려주게 한다.

서브도메인을 옮겼더니 로그인이 풀리거나 `localStorage`의 값이 사라졌다면 출처가 바뀐 것이다. `localStorage`는 출처마다 따로라서 `www.example.com`과 `example.com`은 서로의 값을 못 본다. 쿠키는 `Domain` 속성으로 상위 도메인을 공유할 수 있어 규칙이 다르다. 이 차이는 [브라우저 저장소](/posts/browser-storage)에 정리되어 있다.

소셜 로그인 팝업이 열린 뒤 결과가 돌아오지 않는다면 COOP를 의심한다. `Cross-Origin-Opener-Policy: same-origin`을 켠 페이지에서 연 다른 출처 팝업은 `window.opener`가 `null`이 되어 결과를 보낼 곳이 없다. `same-origin-allow-popups`로 바꾸거나 리다이렉트 방식으로 바꾼다.

CORS 에러는 위의 "읽기 차단"을 서버가 풀어 주지 않은 것이다. 요청은 서버에 도착했다는 점, 그래서 CORS로는 요청 위조를 막을 수 없다는 점을 함께 기억한다.

## 면접에서 나올 만한 질문

### 같은 출처는 어떻게 판단하나요?

스킴, 호스트, 포트 세 가지가 모두 같으면 같은 출처다. 경로와 쿼리는 들어가지 않고, 포트를 생략하면 스킴의 기본 포트로 본다. 그래서 `https://example.com`과 `https://example.com:443/a`는 같고, `http://`로 바뀌거나 `api.` 서브도메인이 붙거나 포트가 `:8443`이 되면 다르다. 로컬에서 프런트 :3000과 API :8080이 다른 출처가 되는 것도 포트 때문이다.

### 출처와 사이트는 어떻게 다른가요?

사이트는 스킴과 eTLD+1, 즉 공개 접미사에 이름 한 칸을 붙인 등록 가능한 도메인이다. `app.example.com`과 `api.example.com`은 다른 출처지만 같은 사이트고, 포트도 사이트에 들어가지 않는다. `github.io`처럼 공개 접미사인 곳의 서브도메인은 서로 다른 사이트다. `SameSite` 쿠키와 사이트 격리가 이 단위로 동작한다.

### 같은 출처 정책은 무엇을 막고 무엇을 허용하나요?

다른 출처의 내용을 읽는 것을 막는다. iframe DOM, `fetch` 응답 본문, 캔버스에 그린 다른 출처 이미지의 픽셀이 그렇다. 반대로 다른 출처로 요청을 보내는 쓰기(폼 제출, 이동)와 다른 출처 자원을 거는 임베드(img, script, iframe)는 허용한다. 웹이 링크와 임베드로 이루어져 있어서다. 이 열린 쓰기를 악용하는 것이 CSRF이고, 읽기를 서버가 허락하는 장치가 CORS다.

### postMessage를 안전하게 쓰려면 무엇을 확인하나요?

받을 때는 `event.origin`을 허용 목록과 문자열 전체로 비교하고, `event.source`가 기대한 창인지 보고, 데이터 모양과 범위를 검사한다. `includes`나 `endsWith`로 비교하면 비슷한 이름의 다른 도메인이 통과한다. 보낼 때는 `targetOrigin`을 `"*"`가 아닌 정확한 출처로 지정해서, 받는 창이 다른 곳으로 이동했으면 메시지가 버려지게 한다. sandbox iframe은 출처가 `"null"`이라 `source`로 확인한다.

### iframe sandbox에서 allow-scripts와 allow-same-origin을 같이 주면 왜 위험한가요?

부모와 같은 출처 문서라면 스크립트가 부모 DOM에 접근할 수 있게 되어, 자기 iframe의 `sandbox` 속성을 지우고 다시 불러올 수 있기 때문이다. 그러면 sandbox가 아무 의미가 없다. `allow-same-origin`이 없으면 iframe은 불투명 출처를 받아 부모의 쿠키와 저장소를 못 본다. 믿기 어려운 HTML은 별도 사이트에서 내려 주고 필요한 토큰만 켠다.

### 사이트 격리는 왜 생겼나요?

스펙터 같은 CPU 부채널 공격으로 같은 프로세스 메모리의 데이터를 자바스크립트로 읽어 낼 수 있게 되어서다. 브라우저 코드가 다른 출처 읽기를 막아도 데이터가 같은 렌더러 프로세스에 있으면 새어 나온다. 그래서 사이트마다 다른 프로세스를 써서 다른 사이트 데이터가 애초에 들어오지 않게 했다. 남는 틈은 ORB 같은 응답 거르기와 CORP, COOP, COEP 헤더가 메운다.

### 서드파티 스크립트의 위험은 어떻게 줄이나요?

`script` 태그로 부른 스크립트는 내 출처 권한으로 돌아서 DOM, 쿠키, 저장소를 모두 만질 수 있다. 내용이 고정된 라이브러리는 SRI 해시로 고정해 바뀌면 실행되지 않게 하고, CSP `script-src`로 실행 가능한 출처를 좁힌다. 내용이 계속 바뀌는 태그 매니저 같은 것은 SRI를 걸 수 없으니 결제·로그인 페이지에서는 빼고, 화면만 빌려주는 위젯은 sandbox iframe에 담는다. 직접 호스팅하면 남의 CDN이 털리는 위험도 줄어든다.

### 클릭재킹은 같은 출처 정책으로 막히지 않나요?

막히지 않는다. 공격자는 내 페이지를 읽지 않고 iframe으로 걸어 둘 뿐이고, 임베드는 같은 출처 정책이 허용하는 동작이다. 내 응답에 `Content-Security-Policy: frame-ancestors 'self'`나 `X-Frame-Options: DENY`를 보내 다른 사이트가 나를 프레임에 넣지 못하게 해야 한다. 둘 다 있으면 지원하는 브라우저는 `frame-ancestors`를 따른다.
