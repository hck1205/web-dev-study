nginx 앞단에서 502가 드문드문 난다. 앱 팀은 "우리 쪽 로그에는 그런 요청이 없다"고 하고, nginx error 로그에는 `Connection reset by peer`가 찍혀 있다. 그럼 누가 RST를 보냈을까. 앱 프로세스일 수도 있고, 중간의 무언가일 수도 있다. 로그는 각자 자기가 본 것만 말하니, 서로의 로그를 들고는 결론이 나지 않는다.

이럴 때 패킷을 직접 본다. 패킷은 누가 언제 무엇을 보냈는지 그대로 남긴다. 리눅스 서버에서 그 일을 하는 기본 도구가 tcpdump다. 이 글은 curl 요청 하나를 처음부터 끝까지 찍어서 ARP, DNS, TCP, HTTP가 층별로 지나가는 걸 눈으로 보고, 필요한 패킷만 거르는 필터, 내용까지 보는 옵션, 파일로 남겨 Wireshark로 여는 법, 그리고 refused·timeout·reset·502를 패킷으로 구별하는 법까지 간다.

기준은 Ubuntu 24.04 LTS, tcpdump 4.99.4(libpcap 1.10.4)다. 22.04는 4.99.1로 출력 형식이 같다. 실습 망은 [계층별 장애 좁히기 글](/posts/network-troubleshooting-by-layer)과 같다. 노트북 `10.11.1.10` — 라우터 — 서버 `10.11.2.20`이고, 서버의 nginx가 80·443을 받아 `127.0.0.1:8000`의 앱으로 넘긴다.

```bash
# 설치 (Ubuntu Server에는 대개 이미 들어 있다)
sudo apt-get install -y tcpdump

# 버전 확인
tcpdump --version
```

```text
tcpdump version 4.99.4
libpcap version 1.10.4 (with TPACKET_V3)
```

패킷을 찍으려면 root이거나 `CAP_NET_RAW` 권한이 있어야 한다. 이 글의 명령은 모두 `sudo`를 붙여 친다.

## 어디서 찍을지부터 정한다

tcpdump는 인터페이스 하나를 지나가는 패킷만 본다. 그래서 어느 인터페이스에서 찍느냐가 무엇을 볼 수 있는지를 정한다. 클라이언트에서 찍으면 내가 무엇을 보냈고 무엇을 받았는지, 서버에서 찍으면 무엇이 실제로 도착했는지가 보인다. 둘을 비교하면 "보냈는데 안 왔다"를 증명할 수 있다.

어디인지 모를 때는 `-i any`로 모든 인터페이스를 한꺼번에 찍는다. 이 경우 출력에 인터페이스 이름과 방향(`In`, `Out`)이 붙어서 한 화면에서 두 연결을 다 볼 수 있다. 대신 이더넷 헤더 대신 리눅스가 만든 가짜 헤더(`LINUX_SLL2`)가 붙어서 `-e`로 MAC 주소를 볼 수 없다.

## curl 한 번을 처음부터 끝까지

## 필요한 패킷만 거른다

실제 서버에서 필터 없이 tcpdump를 켜면 SSH 세션 자신의 패킷까지 쏟아져 화면이 넘친다. 명령 끝에 붙이는 필터(BPF 문법)로 원하는 것만 고른다. 필터는 커널 안에서 실행되니, 거른 패킷은 tcpdump까지 올라오지도 않아 부하도 적다.

```bash
# 특정 호스트와 오간 것만
sudo tcpdump -i any -nn host 10.11.1.10

# 특정 포트만 (출발지든 목적지든)
sudo tcpdump -i any -nn port 443

# 서버가 받는 쪽 포트만, 그리고 SSH는 빼고
sudo tcpdump -i any -nn 'dst port 80 and not port 22'

# 대역 단위로
sudo tcpdump -i any -nn net 10.11.0.0/16

# 연결을 열고 끊는 패킷만 (SYN 또는 RST가 켜진 것)
sudo tcpdump -i any -nn 'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0'

# 이름 풀이와 ARP만
sudo tcpdump -i any -nn 'port 53 or arp'
```

괄호나 `&`, `|`가 들어가면 셸이 먼저 해석하지 않도록 필터 전체를 작은따옴표로 감싼다. `-nn`도 습관처럼 붙인다. 이름 풀이를 켜 두면 tcpdump가 IP마다 역방향 DNS를 물어서 출력이 느려지고, 그 DNS 질의가 다시 캡처에 섞인다.

아래 그림은 패킷이 여러 종류 섞인 흐름에 `'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0'` 필터를 건 모습이다. 칸을 넘기며 필터가 각 패킷을 통과시키는지 본다.

## 내용까지 본다

기본 출력은 헤더 요약만 보여 준다. 내용이 궁금하면 옵션을 더한다. `-A`는 내용을 ASCII로, `-X`는 16진수와 ASCII로 함께 보여 준다. 저장해 둔 파일에서 데이터가 실린 패킷만 골라 `-A`로 읽었다.

`45`는 IPv4에 헤더 20바이트, `40 06`의 `06`은 그 안이 TCP라는 뜻이다. `0a0b 010a`가 출발지 10.11.1.10, `0a0b 0214`가 목적지 10.11.2.20, 그다음 `bd44`(48452)와 `0050`(80)이 포트다. `0204 05b4`는 MSS 옵션 1460이다. 봉투를 하나씩 벗기는 이 읽기는 [계층 개요 글](/posts/network-layers-overview)에서 했다.

돌아온 SYN-ACK의 `ttl 63`도 단서다. 64에서 라우터 하나를 지나 하나 줄었다. RST를 보낸 쪽이 진짜 서버인지 중간 장비인지 헷갈릴 때, RST의 TTL을 서버가 보낸 정상 패킷의 TTL과 비교하면 출처가 다르다는 걸 알 수 있다. 중간 방화벽이 대신 보낸 RST는 TTL이 다르게 찍히는 경우가 많다.

## 파일로 남기고 Wireshark로 연다

화면으로 흘려 보는 건 짧은 확인에만 쓴다. 장애를 쫓을 때는 파일로 남긴다. 나중에 필터를 바꿔 다시 읽을 수 있고, Wireshark로 열어 흐름 단위로 볼 수 있다.

```bash
# 파일로 저장 (-w), 1000개만 받고 끝낸다 (-c)
sudo tcpdump -i any -nn -c 1000 -w /tmp/shop-502.pcap 'tcp port 80 or tcp port 8000'

# 저장한 파일을 다른 필터로 다시 읽는다 (-r)
tcpdump -nn -r /tmp/shop-502.pcap 'tcp[tcpflags] & tcp-rst != 0'
```

언제 날지 모르는 장애를 기다릴 때는 파일을 돌려 쓴다. `-C`는 파일 하나의 크기(백만 바이트 단위), `-W`는 파일 개수다. 개수를 다 채우면 가장 오래된 파일부터 덮어써서 디스크가 차지 않는다. `-s`로 패킷마다 앞부분만 저장하면 더 오래 버틴다. 헤더만 필요하면 128바이트면 충분하다.

```bash
# 패킷마다 앞 128바이트만, 1MB짜리 파일 3개를 돌려 쓴다
sudo tcpdump -i s0 -nn -s 128 -C 1 -W 3 -w ring.pcap
```

이 명령을 root 소유 폴더에서 그대로 치면 실습 서버에서는 이렇게 실패했다.

```text
tcpdump: ring.pcap0: Permission denied
```

Ubuntu의 tcpdump는 캡처 장치를 연 뒤 root 권한을 버리고 `tcpdump` 사용자로 바뀐다. `-w`만 쓸 때는 파일을 그 전에 열어서 같은 폴더에 잘 저장됐는데, 파일을 돌려 쓰는 옵션(`-C`, `-G`)을 쓰자 권한을 낮춘 뒤에 파일을 열어서 첫 파일 `ring.pcap0`부터 거절됐다. 그래서 `tcpdump` 사용자가 쓸 수 있는 폴더(`sudo install -d -o tcpdump /var/tmp/cap`처럼 미리 만든 곳)에 저장하거나, `-Z root`로 권한을 낮추지 않게 한다. `-Z root`로 다시 돌리자 파일 세 개가 돌아가며 채워졌다.

```text
-rw-r--r-- 1 root root 1000070 Oct 18 05:35 ring.pcap0
-rw-r--r-- 1 root root 1000054 Oct 18 05:35 ring.pcap1
-rw-r--r-- 1 root root  884948 Oct 18 05:35 ring.pcap2
```

Ubuntu에는 하나가 더 있다. AppArmor 프로필(`/etc/apparmor.d/usr.bin.tcpdump`)이 켜져 있으면 tcpdump는 홈 폴더 밖에서는 이름이 `.pcap`, `.pcapng`, `.cap`으로 끝나는 파일(뒤에 숫자가 붙어도 된다)만 쓸 수 있다. `-w capture.out`처럼 확장자를 바꾸면 권한이 충분해도 `Permission denied`가 난다. 이 실습 컨테이너에는 AppArmor가 돌지 않아서 직접 재현하지는 못했고, 프로필에 적힌 규칙으로 확인했다.

저장한 파일은 노트북으로 가져와 Wireshark로 연다. Wireshark는 tcpdump와 필터 문법이 다르다. tcpdump의 필터는 무엇을 찍을지 정하는 캡처 필터이고, Wireshark 화면의 필터는 이미 찍은 것 중 무엇을 보여 줄지 정하는 표시 필터다.

- `tcp.flags.reset == 1`: RST가 켜진 패킷
- `http.response.code == 502`: 502 응답
- `tcp.analysis.retransmission`: Wireshark가 재전송으로 판단한 패킷
- `tls.handshake.extensions_server_name == "shop.lab.test"`: 그 이름으로 TLS를 연 연결

패킷 하나를 고르고 "Follow → TCP Stream"을 누르면 그 연결에서 오간 내용이 대화처럼 이어 붙어 보인다. 서버에 GUI가 없다면 Wireshark의 명령줄판인 `tshark`(`sudo apt-get install -y tshark`)가 같은 표시 필터를 받는다.

## 장애 장면을 패킷으로 가른다

이제 처음 질문으로 간다. 클라이언트가 받는 메시지는 비슷해도 패킷의 모양은 확실히 다르다.

응답이 없는 경우(timeout)는 같은 `[S]`가 간격을 늘리며 반복되고 그 외에는 아무것도 없다. 거절(refused)은 `[S]` 바로 다음에 상대가 `[R.]`을 보낸다. 이 둘의 실제 캡처와 재전송 간격은 [TCP 연결의 일생 글](/posts/tcp-connection-lifecycle)에 있다.

도중에 끊기는 경우는 연결이 맺어지고 데이터가 오간 뒤에 RST가 나온다. 앱이 요청을 받자마자 연결을 리셋하게 만든 9000번 포트에 직접 붙어서 찍었다.

```bash
# 노트북: 9000번 연결만
sudo tcpdump -i c0 -nn 'tcp port 9000'
```

```text

05:34:22.940400 IP 10.11.2.20.9000 > 10.11.1.10.60992: Flags [S.], seq 2434562020, ack 3322060119, win 65160, options [mss 1460,sackOK,TS val 2126590719 ecr 1143359054,nop,wscale 10], length 0
05:34:22.940412 IP 10.11.1.10.60992 > 10.11.2.20.9000: Flags [.], ack 1, win 63, options [nop,nop,TS val 1143359054 ecr 2126590719], length 0
```

서버는 요청 86바이트를 받았다고 ACK까지 한 뒤 0.8ms 만에 RST를 보냈다. 응답은 한 바이트도 없다. RST의 출발지가 `10.11.2.20.9000`이고 TS 옵션까지 이어지는 걸 보면 서버 커널이 보낸 것이다. 클라이언트는 `curl: (56) Recv failure: Connection reset by peer`를 받았다.

같은 고장을 nginx 뒤에 두면 클라이언트에게는 RST가 아니라 502가 간다. 그 차이는 서버에서 `-i any`로 두 연결을 한꺼번에 찍으면 한눈에 보인다. 이번에는 뒤쪽 앱이 아예 떠 있지 않은 경우다.

```bash
# 서버: 앞쪽(80)과 뒤쪽(8001) 연결을 함께
```

## 컨테이너와 Pod 안에서 찍는다

컨테이너는 자기만의 네트워크 namespace를 가진다. 호스트에서 `tcpdump -i any`를 쳐도 컨테이너의 `eth0`은 보이지 않고, 호스트 쪽에 붙은 짝 인터페이스(`vethXXXX`)만 보인다. 이미지에 tcpdump가 없는 경우도 많다. 그래서 호스트의 tcpdump를 컨테이너의 namespace 안에서 실행한다. `nsenter`가 그 일을 한다.

실습 서버는 namespace 이름이 있어서 경로로 들어갔다.

```bash
# 서버 namespace 안으로 들어가 그 안의 s0를 찍는다
sudo nsenter --net=/var/run/netns/p11s tcpdump -i s0 -nn -c 3 'tcp port 80'
```

```text
0 packets dropped by kernel
```

마지막 세 줄은 tcpdump가 끝날 때 찍는 통계다. `dropped by kernel`이 0이 아니면 tcpdump가 패킷을 읽는 속도가 못 따라가서 놓친 게 있다는 뜻이다. 필터를 좁히거나 `-B`로 버퍼를 키우고, 화면 출력 대신 `-w`로 파일에 쓴다.

Docker 컨테이너는 이름 대신 컨테이너의 PID로 들어간다. 쿠버네티스 Pod는 디버그용 컨테이너를 같은 Pod에 붙이면 네트워크 namespace를 함께 쓴다. 이 실습 환경에는 Docker와 쿠버네티스가 없어서 아래 두 명령은 직접 돌리지 못했다.

```bash
# Docker: 컨테이너 web의 PID를 찾아 그 네트워크 namespace에서 tcpdump를 실행한다
sudo nsenter -t "$(docker inspect -f '{{.State.Pid}}' web)" -n tcpdump -i eth0 -nn

# 쿠버네티스: 도구가 든 이미지로 임시 컨테이너를 붙여 Pod의 네트워크를 찍는다
kubectl debug -it pod/web-7c9d -n shop --image=nicolaka/netshoot -- tcpdump -i eth0 -nn
```

Pod 안에서 찍으면 그 Pod가 실제로 받은 패킷이 보인다. Service 주소(ClusterIP)로 보낸 요청은 노드의 kube-proxy 규칙에서 이미 Pod IP로 바뀐 뒤라, Pod 안에서는 목적지가 Service IP가 아니라 Pod IP로 찍힌다. 그 변환은 [iptables NAT 글](/posts/iptables-nat)에서 다뤘다.

## TLS 안은 보이지 않는다, 이름만 빼고

HTTPS 요청을 찍으면 TCP 연결과 패킷 크기, 시간은 다 보이지만 내용은 암호문이다. 그래도 하나는 평문으로 남는다. ClientHello에 실린 접속할 이름(SNI)이다.

```bash
# 443번 연결의 패킷을 ASCII로 풀어 이름이 보이는지 찾는다
tcpdump -nn -A -r tls.pcap | grep -a -o 'shop.lab.test'
```

```text
shop.lab.test
```

```text
05:34:08.926062 IP 10.11.1.10.55304 > 10.11.2.20.443: Flags [P.], seq 1:518, ack 1, win 63, options [nop,nop,TS val 1445558216 ecr 3380308101], length 517
05:34:08.926088 IP 10.11.2.20.443 > 10.11.1.10.55304: Flags [.], ack 518, win 64, options [nop,nop,TS val 3380308103 ecr 1445558216], length 0
05:34:08.927172 IP 10.11.2.20.443 > 10.11.1.10.55304: Flags [P.], seq 1:1372, ack 518, win 64, options [nop,nop,TS val 3380308104 ecr 1445558216], length 1371
```

517바이트가 ClientHello, 1371바이트가 ServerHello부터 인증서까지 묶인 서버의 응답이다. 그 뒤의 HTTP 요청과 응답은 tcpdump로는 읽을 수 없다. TLS가 무엇을 숨기고 무엇을 드러내는지는 [HTTPS 글](/posts/https-tls)에 있다.

내 클라이언트의 트래픽을 Wireshark에서 풀어 보고 싶다면, 클라이언트가 세션 키를 파일로 남기게 한다. curl과 크롬·파이어폭스는 `SSLKEYLOGFILE` 환경 변수를 읽는다.

```bash
# 이 curl이 쓴 TLS 세션 키를 파일에 남긴다
SSLKEYLOGFILE=$HOME/keys.log curl -sS -o /dev/null --cacert ca.crt https://shop.lab.test/

# 어떤 값이 남았는지 이름만 본다 (값 자체는 비밀이다)
cut -d' ' -f1 ~/keys.log
```

```text
SERVER_HANDSHAKE_TRAFFIC_SECRET
EXPORTER_SECRET
SERVER_TRAFFIC_SECRET_0
CLIENT_HANDSHAKE_TRAFFIC_SECRET
CLIENT_TRAFFIC_SECRET_0
```

Wireshark의 TLS 설정(Preferences → Protocols → TLS)에서 이 파일을 지정하면 같은 시간에 찍은 pcap의 HTTPS 내용이 풀려 보인다. 서버 쪽 트래픽 전체를 풀 수 있는 방법이 아니라, 키를 남긴 그 클라이언트의 연결만 풀린다는 데 주의한다.

## 찍기 전에 정해 둘 것

<Callout kind="warning" title="캡처 파일에는 비밀이 들어 있다">
평문 HTTP 캡처에는 쿠키, `Authorization` 헤더, 폼에 입력한 비밀번호가 그대로 들어간다. HTTPS라도 접속한 이름과 IP, 시간은 남고, 세션 키 파일(`SSLKEYLOGFILE`)이 있으면 내용까지 풀린다. 운영 서버에서 찍을 때는 필요한 호스트와 포트로 필터를 좁히고, 헤더만 필요하면 `-s 128`처럼 앞부분만 저장한다. 파일은 분석이 끝나면 지우고, 이슈 트래커나 메신저에 원본 pcap을 그대로 올리지 않는다. 키 파일은 분석이 끝나는 즉시 지운다.
</Callout>

운영 서버에 주는 부담도 생각한다. 바쁜 서버에서 `-i any`에 필터 없이 화면 출력을 켜면 터미널 출력 자체가 CPU를 쓰고, SSH 세션의 패킷이 다시 찍혀 출력이 끝없이 늘어난다. `-c`로 개수를 정하거나 `timeout 60 tcpdump ...`처럼 시간을 정하고, 파일로 남긴 뒤 다른 곳에서 읽는다.

양쪽에서 찍을 때는 시계를 맞춘다. 두 호스트의 시간이 어긋나 있으면 "보낸 시각"과 "받은 시각"을 비교할 수 없다. NTP가 돌고 있는지(`timedatectl`) 먼저 확인한다.

## 패킷은 각자의 로그보다 정직하다

tcpdump는 계층 모델을 화면에 그대로 펼쳐 보여 준다. ARP 한 쌍, DNS 한 쌍, TCP 세 번의 인사, HTTP 요청과 응답, FIN 교환이 각자의 층에서 각자의 주소를 달고 지나간다. 장애를 볼 때는 찍을 자리를 먼저 정하고(프록시가 있으면 두 연결 모두), 필터로 좁히고, 파일로 남긴 다음, 플래그와 출발지 주소로 누가 무엇을 했는지 읽는다. 처음 장면의 RST도 이렇게 찾는다. 서버의 `lo`와 앞쪽 인터페이스를 함께 찍어, RST가 앱 포트에서 나왔는지 그 앞에서 나왔는지를 보면 된다. 메시지를 층에 대응시키는 법은 [OSI 실무 글](/posts/osi-in-practice)에서, 패킷을 찍기 전까지의 확인 순서는 [계층별 장애 좁히기 글](/posts/network-troubleshooting-by-layer)에서 볼 수 있다.

## 면접에서 나올 만한 질문

### tcpdump 출력에서 연결이 거절됐는지, 응답이 없는지 어떻게 구별하나요?

플래그 칸을 본다. 거절이면 클라이언트의 `[S]` 바로 뒤에 상대의 `[R.]`이 오고, 응답이 없으면 같은 순서 번호의 `[S]`만 간격을 늘리며 반복된다. 연결이 맺어지면 `[S]`, `[S.]`, `[.]` 세 줄이 나온다. 데이터가 오간 뒤 `[R]`이 나오면 도중에 끊긴 것이고, 그 줄의 출발지 주소가 누가 끊었는지 말해 준다.

### 프록시 뒤에서 502가 날 때 어디서 캡처하나요?

프록시가 있는 서버에서 앞쪽과 뒤쪽 연결을 함께 찍는다. `-i any`로 클라이언트 쪽 포트와 업스트림 포트를 함께 필터에 넣으면 인터페이스와 방향이 붙어 나와서, 뒤쪽 연결에서 무슨 일(RST, 무응답, 도중 종료)이 있었는지와 앞쪽으로 502가 나간 시점을 한 화면에서 비교할 수 있다. 앞쪽 인터페이스만 찍으면 뒤쪽 연결은 아예 보이지 않는다.

### 캡처 필터와 표시 필터는 무엇이 다른가요?

tcpdump에 주는 BPF 필터는 캡처 필터로, 커널 안에서 실행되어 조건에 맞지 않는 패킷은 아예 저장하지 않는다. 부하가 적은 대신 놓친 패킷은 다시 볼 수 없다. Wireshark 화면의 필터는 표시 필터로, 이미 저장한 패킷 중 무엇을 보여 줄지만 정하고 프로토콜 필드 이름(`tcp.flags.reset == 1` 같은)으로 더 깊이 거를 수 있다. 보통 캡처는 넉넉한 조건으로 하고 분석은 표시 필터로 좁힌다.

### HTTPS 트래픽을 캡처하면 무엇을 볼 수 있나요?

IP와 포트, 패킷 크기와 시간, TCP 플래그는 다 보이고, TLS ClientHello의 SNI로 접속하려는 이름도 보인다. HTTP 요청과 응답 내용은 암호화돼서 보이지 않는다. 내 클라이언트의 트래픽이라면 `SSLKEYLOGFILE`로 세션 키를 남겨 Wireshark에서 풀 수 있지만, 그 키를 남긴 연결만 풀린다.

### 컨테이너 안의 트래픽은 어떻게 캡처하나요?

컨테이너는 별도의 네트워크 namespace에 있으니, 호스트의 tcpdump를 `nsenter -t <PID> -n`으로 그 namespace 안에서 실행한다. 이미지에 도구가 없어도 된다. 호스트 쪽 veth 인터페이스를 찍는 방법도 있고, 쿠버네티스에서는 `kubectl debug`로 도구가 든 임시 컨테이너를 Pod에 붙여 같은 네트워크에서 찍는다. Pod 안에서는 Service IP가 이미 Pod IP로 바뀐 뒤의 패킷이 보인다.

### 운영 서버에서 tcpdump를 쓸 때 조심할 점은 무엇인가요?

필터를 좁히고 `-c`나 `timeout`으로 끝을 정해서 부하와 출력량을 제한하고, 화면보다 파일로 남긴다. 캡처에는 쿠키·토큰 같은 민감한 값이 들어가니 `-s`로 저장 길이를 줄이고 분석 후 지우며 공유를 제한한다. 끝날 때 나오는 `dropped by kernel`이 0이 아니면 놓친 패킷이 있다는 뜻이니 결론을 낼 때 감안한다. Ubuntu에서는 파일을 돌려 쓰는 옵션의 권한 낮추기와 AppArmor의 파일 이름 제한 때문에 저장이 실패할 수 있다는 것도 알아 둔다.
