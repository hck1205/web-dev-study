  서비스가 잘 되고 있는지를 숫자로 말하려면 세 가지를 정한다. 무엇을 어떻게 셀지(SLI), 그 숫자가 지켜야 할 목표(SLO), 그리고 목표를 못 지키면 보상이 걸린 바깥과의 약속(SLA)이다. 학교 출석으로 치면 출석률 계산법이 SLI, "한 학기 95% 이상"이 SLO, 못 지키면 장학금이 끊기는 규정이 SLA다. 출석률을 교실 안에서만 세면 학교에 오지 못한 날이 빠지듯, 성공률도 서버 바깥에서 세야 사용자가 겪은 일에 가깝다.

  목표를 100%로 잡으면 아무것도 바꿀 수 없어서, 보통 지난 기록에서 출발해 조금 낮은 값을 고르고 며칠 동안 잴지도 함께 정한다.
</EasyIntro>

월간 보고서에 "주문 API 성공률 99.57%"라고 적혀 있다고 하자. 같은 달 고객 센터에는 "주문 버튼을 눌렀는데 오류가 났다"는 문의가 평소보다 많았다. 둘 다 사실이다. 숫자는 API 서버가 받은 요청만 셌고, 배포 중 서버가 잠깐 내려간 사이 로드 밸런서가 돌려준 502는 서버 쪽 숫자에 한 건도 남지 않았다. 이번 글의 실습에서 실제로 같은 일이 생겼다. 같은 1분 동안 서버는 99.57%라고 말했고, nginx 로그는 97.84%라고 말했다.

"서비스가 잘 돌고 있나"를 숫자로 말하려면 먼저 무엇을, 어디서 셀지 정해야 한다. SLI(Service Level Indicator)는 그 숫자, SLO(Service Level Objective)는 그 숫자가 지켜야 할 목표, SLA(Service Level Agreement)는 목표를 못 지켰을 때 돈이나 보상이 걸린 바깥과의 약속이다. 이 글은 실제 요청 로그에서 가용성과 지연 SLI를 직접 계산하고, 목표와 창을 고르는 법, 아홉(nine)이 하나 늘 때 허용되는 장애 시간이 어떻게 줄어드는지를 따라간다.

이 주제의 다른 글: 사람을 깨울 알림을 고르는 [알림 설계](/posts/alerting), SLO로 남은 여유를 재고 알림을 거는 [에러 예산](/posts/error-budgets), 무엇을 지켜볼지 정하는 [모니터링 기본](/posts/monitoring-basics). 이 글은 숫자를 정의하는 데까지만 다루고, 그 숫자로 알림을 거는 계산은 에러 예산 글로 넘긴다.

실습 환경은 Ubuntu 24.04, nginx 1.24, Node.js 22, Prometheus 3.5.0(promtool)이다. 주문 API를 흉내 낸 Node 서버 앞에 nginx를 두고, 초당 100개씩 60초 동안 요청을 보냈다.

## 사용자가 겪은 일을 비율 하나로

SLI는 대부분 비율로 쓴다. 좋은 사건 수를 유효한 사건 수로 나눈 값이다.

```text
SLI = 좋은 요청 수 / 유효한 요청 수 × 100%
```

비율로 쓰는 이유는 셋이다. 0%에서 100% 사이라 서비스끼리 견줄 수 있고, 트래픽이 늘어도 뜻이 같고, 무엇보다 "실패를 몇 개까지 허용하나"라는 계산으로 바로 이어진다. 이 계산이 [에러 예산](/posts/error-budgets)이다.

사용자 여정마다 묻는 질문이 다르니 SLI 종류도 다르다. 요청에 답하는 API라면 가용성(실패하지 않았나)과 지연(빨랐나)이 기본이다. 배치 작업이면 신선도(데이터가 얼마나 최근 것인가)와 처리 완료율, 저장소면 내구성(맡긴 데이터를 잃지 않았나)을 본다. 이 글은 API의 두 가지에 집중한다.

## 좋은 요청과 유효한 요청을 정한다

nginx 로그 형식에 상태 코드와 처리 시간, User-Agent를 넣었다. 한 줄을 조각으로 보면 이렇다.

```nginx
# nginx.conf: SLI 계산에 쓸 필드만 남긴 로그 형식
log_format slo '$time_iso8601 $request_method $uri $status $request_time $upstream_response_time "$http_user_agent"';
```

이제 무엇을 "유효한 요청"으로 볼지 정한다. 실습 트래픽의 10%는 `/healthz`를 두드리는 헬스 체크다. 헬스 체크는 사람이 보낸 요청이 아니고, 대부분 빠르고 성공해서 SLI를 실제보다 좋게 만든다. 분모에서 뺀다.

"좋은 요청"은 서버 탓으로 실패하지 않은 요청이다. 5xx는 나쁜 요청, 2xx·3xx는 좋은 요청이다. 4xx는 판단이 필요하다. 잘못된 주문 번호로 받은 400은 사용자의 실수니 좋은 요청(정상 동작)으로 센다. 그런데 서버가 과부하로 내보내는 429나, 배포 실수로 생긴 404 폭증은 서버 탓이다. 그래서 4xx를 통째로 빼기보다 코드별로 정해 둔다.

```bash
# 그대로 센 성공률: 5xx가 아니면 좋은 요청
awk '{n++} $4!~/^5/{g++} END{printf "good=%d total=%d sli=%.4f%%\n", g, n, 100*g/n}' access.log
# 헬스 체크를 분모에서 뺀 성공률
awk '$3!="/healthz"{n++; if($4!~/^5/) g++} END{printf "good=%d valid=%d sli=%.4f%%\n", g, n, 100*g/n}' access.log
```

```text
good=5867 total=6000 sli=97.7833%
good=5297 valid=5414 sli=97.8389%
```

이번에는 헬스 체크도 장애 순간에 502를 받아서 차이가 작았다. 평소라면 헬스 체크는 거의 다 성공하니, 사용자 요청이 실패하는 동안에도 SLI를 끌어올리는 쪽으로 작용한다. 차이가 작든 크든 분모는 사용자 요청이어야 한다.

상태 코드 분포도 보자.

```bash
# 상태 코드별 개수
awk '{print $4}' access.log | sort | uniq -c
```

```text
   5689 200
    178 400
     22 500
    111 502
```

500 22건은 서버가 DB 오류를 흉내 내 돌려준 실패고, 502 111건은 실습 30초쯤에 서버 프로세스를 1초 동안 내렸다 올린 사이에 생겼다.

## 어디서 재느냐가 숫자를 바꾼다

같은 60초를 서버 자신의 로그로 세면 숫자가 달라진다. 서버는 응답할 때마다 상태 코드를 한 줄씩 남기게 했다.

```bash
# 서버가 직접 남긴 로그로 센 성공률
awk '{n++} $1!~/^5/{g++} END{printf "good=%d total=%d sli=%.4f%%\n", g, n, 100*g/n}' app.log
# nginx가 502를 만든 시각
grep ' 502 ' access.log | awk '{print $1}' | uniq -c
```

```text
good=5119 total=5141 sli=99.5721%
     97 2026-10-20T20:25:57+00:00
     14 2026-10-20T20:25:58+00:00
```

서버는 99.57%, nginx는 97.84%. 서버가 내려가 있던 1초 동안 들어온 요청은 서버에 도착하지 못했으니 서버 로그에 없다. 서버 안에서 잰 SLI는 "서버까지 온 요청 중에서"의 성공률이라, 서버가 아예 응답하지 못하는 가장 큰 장애를 놓친다.

어디서 잴지는 트레이드오프다. 서버 지표는 가장 자세하고 쉽지만 서버 밖의 실패를 놓친다. 로드 밸런서 로그는 서버가 죽은 경우까지 잡아서 대부분의 팀이 기본으로 쓰는 자리다. 브라우저에서 재는 RUM(Real User Monitoring)은 사용자에게 가장 가깝지만, 사용자 기기와 회선 탓의 실패가 섞여서 우리가 고칠 수 없는 잡음이 많다. 바깥 검사는 트래픽이 없을 때도 쓸 수 있지만 표본이 작다. 보통 로드 밸런서 쪽 숫자로 SLO를 정하고, 바깥 검사를 보조로 붙인다.

## 평균은 느린 사용자를 숨긴다

가용성 다음은 지연이다. 같은 로그에서 성공한 사용자 요청의 응답 시간을 봤다.

```bash
# 성공한 사용자 요청 중 0.3초 안에 끝난 비율과 평균
awk '$3!="/healthz" && $4!~/^5/ {n++; s+=$5; if($5<=0.3) f++} END{printf "valid=%d fast=%d latency_sli=%.2f%% mean=%.3fs\n", n, f, 100*f/n, s/n}' access.log
# 분위수: 정렬한 뒤 위치로 고른다
awk '$3!="/healthz" && $4!~/^5/ {print $5}' access.log | sort -n \
  | awk '{a[NR]=$1} END{printf "p50=%s p90=%s p99=%s max=%s\n", a[int(NR*0.5)], a[int(NR*0.9)], a[int(NR*0.99)], a[NR]}'
```

```text
valid=5297 fast=5054 latency_sli=95.41% mean=0.080s
p50=0.053 p90=0.081 p99=0.810 max=1.199
```

평균은 80ms다. 보고서에 "평균 응답 80ms"라고 쓰면 아주 빠른 서비스 같다. 그런데 100명 중 1명은 0.81초 넘게 기다렸고, 0.3초를 넘긴 요청이 5% 가깝다. 평균은 대다수의 빠른 요청이 소수의 느린 요청을 덮어 버린다.

그래서 지연 SLI도 비율로 쓴다. "문턱보다 빨리 끝난 요청의 비율"이다. 한 줄씩 세어 보면 이렇다.

비율 SLI가 분위수보다 SLO에 맞는 이유가 있다. p99는 서버 10대의 p99를 평균 내서 전체 p99를 구할 수 없다. 비율은 분자끼리, 분모끼리 더하면 그대로 합쳐진다. 그리고 "나쁜 요청 수"가 바로 나오니 몇 개까지 허용할지 셀 수 있다.

Prometheus에서는 히스토그램의 칸(bucket)으로 같은 값을 구한다. `le="0.3"` 칸은 0.3초 이하로 끝난 요청의 누적 개수라서, 그걸 전체 개수로 나누면 지연 SLI다. promtool로 1분에 요청 1000개, 그중 0.3초 이하 960개인 입력을 넣어 확인했다.

```yaml
# hist.test.yml (일부)
promql_expr_test:
  # 0.3초 안에 끝난 요청의 비율 = 지연 SLI
  - expr: |
      sum(rate(http_request_duration_seconds_bucket{le="0.3"}[5m]))
        / sum(rate(http_request_duration_seconds_count[5m]))
    eval_time: 10m
    exp_samples: [{ labels: '{}', value: 0.96 }]
  # 0.25초를 문턱으로 잡으면? 그런 칸이 없으니 결과가 비어 있다
  - expr: |
      sum(rate(http_request_duration_seconds_bucket{le="0.25"}[5m]))
        / sum(rate(http_request_duration_seconds_count[5m]))
    eval_time: 10m
    exp_samples: []

```

두 번째 테스트가 흔한 실수를 보여 준다. SLO 문턱을 0.25초로 정했는데 히스토그램 칸이 0.1, 0.3, 1초뿐이면 식은 아무 에러 없이 빈 결과를 낸다. 대시보드는 빈 칸으로, 알림은 침묵으로 끝난다. 문턱은 반드시 칸 경계 중 하나여야 하고, SLO를 정할 때 계측 코드의 칸도 같이 맞춘다. 히스토그램 칸을 고르는 법은 [지표 타입](/posts/metrics-types)에 있다.

문턱을 하나만 두지 않기도 한다. "90%는 100ms 안에, 99%는 1초 안에"처럼 두 개를 걸면 대부분의 체감 속도와 꼬리의 큰 지연을 함께 지킨다.

## 목표는 100%가 아니다

이제 SLI에 목표를 건다. 가장 먼저 드는 생각은 "실패는 없어야 하니 100%"다. 이건 거의 항상 틀린 목표다.

사용자는 99.99%와 100%를 구분하지 못한다. 사용자의 와이파이, 휴대폰, 통신사가 그보다 자주 실패하기 때문이다. 100%를 목표로 하면 배포도, 설정 변경도, 실험도 모두 위험이 되고 팀은 아무것도 바꾸지 못한다. 아홉을 하나 더할 때마다 드는 비용도 크게 는다. 99.9%는 잘 만든 서버 몇 대로 되지만, 99.99%는 사람이 반응하기 전에 자동으로 복구해야 하고, 99.999%는 여러 리전에 걸친 설계를 요구한다.

아홉 하나가 허용하는 장애 시간을 직접 계산해 보자. SLO와 기간(일)을 받아, 그 기간 동안 전부 실패해도 되는 시간을 분으로 돌려주는 함수다.

내 서비스가 기대는 것들의 가용성도 상한이 된다. 요청 하나가 차례로 거치는 부품이 셋이고 각각 99.9%, 99.95%, 99.99%라면, 모두 독립적으로 실패한다고 칠 때 셋 다 성공할 확률은 곱이다.

99.84%다. 이 서비스는 아무리 잘 만들어도 이 의존성들 위에서 99.9%를 약속하기 어렵다. 반대로 같은 부품 두 개를 나란히 두고 하나만 살아도 되게 하면 실패 확률이 곱해져서 가용성이 오른다. 이 계산을 실제 설계로 옮기는 이야기는 [장애 조치](/posts/failover)에 있다.

목표는 과거 데이터에서 시작한다. 지난 몇 달의 SLI를 계산해 보고, 그보다 약간 낮은 값에서 출발해 사용자 불만과 맞춰 가며 조정한다. 지금 99.5%밖에 안 나오는 서비스에 99.99%를 걸면 첫날부터 목표를 어기고, 아무도 그 숫자를 믿지 않게 된다.

## 며칠 동안 재나: 굴러가는 창과 달력 월

"99.9%"에는 기간이 붙어야 뜻이 생긴다. 1분 동안 99.9%와 한 달 동안 99.9%는 전혀 다른 약속이다. 흔히 쓰는 건 두 가지다.

달력 월(calendar month)은 매달 1일에 초기화한다. 보고서와 SLA에 맞추기 쉽다. 대신 월말에 큰 장애가 나도 다음 달 1일이면 다시 깨끗해져서, 실제 사용자 경험과 숫자가 어긋난다. 달마다 날 수가 달라 허용 시간도 조금씩 다르다.

굴러가는 창(rolling window)은 "지금부터 거꾸로 28일" 같은 식으로 매일 창이 하루씩 밀린다. 큰 장애 하루는 정확히 28일 동안 창 안에 머물렀다가 빠진다. 28일을 많이 쓰는 이유는 요일이 정확히 네 번씩 들어가서, 주말 트래픽이 많은 서비스도 창마다 같은 조건이 되기 때문이다. 아래는 7일 창으로 줄여서 하루 실패 수가 창을 지나가는 모습이다. 하루 요청 1만 건에 99.9%면 하루 10건, 7일이면 70건이 허용치다.

## SLA는 바깥과의 약속, SLO는 안쪽의 목표

SLA는 고객과 맺은 계약이다. "월 가용성이 99.5% 아래로 떨어지면 요금의 10%를 크레딧으로 돌려준다"처럼 어기면 치르는 대가가 적혀 있다. 클라우드 업체의 SLA가 대부분 이런 모양이다. 법무와 영업이 함께 정하고, 바꾸기 어렵다.

SLO는 팀이 스스로 정한 목표라서 SLA보다 엄격하게 둔다. SLA가 99.5%면 SLO는 99.9% 정도로 잡아, SLO를 어기는 시점에 아직 SLA까지는 여유가 남게 한다. SLO를 어긴 것은 계약 위반이 아니라 "이제 안정성에 시간을 쓰자"는 신호다. 그 신호를 팀의 행동으로 바꾸는 규칙은 [에러 예산 글](/posts/error-budgets)에서 다룬다.

SLA가 없는 내부 서비스에도 SLO는 필요하다. 다른 팀이 내 API에 얼마나 기대도 되는지 알려 주는 숫자이기 때문이다. 내 서비스의 SLO는 내가 기대는 서비스의 SLO보다 높을 수 없다는 앞의 계산도 여기서 쓰인다.

## SLO는 한 장의 문서로 남긴다

숫자를 정했으면 글로 적어 둔다. 사람마다 "가용성"을 다르게 계산하면 회의에서 숫자 싸움만 한다. 적어 둘 것은 SLI의 정확한 정의와 계산식, 목표, 창, 제외하는 것, 담당자다.

```yaml
# order-api의 SLO 문서 (팀 저장소에 둔다)
service: order-api
owner: order-team
slis:
  - name: availability
    description: 사용자가 보낸 주문 API 요청 중 5xx가 아닌 비율
    measured_at: nginx access log (LB)
    good: status !~ "5.." and status != "429"
    valid: uri != "/healthz" and user_agent !~ "kube-probe"
    objective: 99.9%
  - name: latency
    description: 성공한 주문 API 요청 중 0.3초 안에 끝난 비율
    measured_at: nginx access log (LB)
    threshold_seconds: 0.3          # 히스토그램 칸 경계와 같아야 한다
    objective: 99%
window: rolling 28d
exclusions:
  - 사전 공지한 점검 시간
review: 분기마다 지난 분기 SLI와 사용자 불만을 보고 조정
```

`exclusions`는 짧을수록 좋다. "외부 의존성 장애는 제외" 같은 항목이 들어가는 순간 SLO는 사용자 경험이 아니라 팀의 책임 범위를 재는 숫자가 된다. 사용자는 누구 탓인지 모르고 그냥 실패를 본다.

## SLO가 사용자와 어긋나는 순간

숫자가 멀쩡한데 불만이 들어오거나, 숫자가 깨졌는데 아무도 신경 쓰지 않는다면 정의가 틀린 것이다. 현장에서 자주 보는 경우가 있다.

SLO는 지키는데 사용자가 불만이다. 먼저 재는 자리를 본다. 서버 안에서 쟀다면 로드 밸런서 로그로 다시 계산해 본다. 이 글의 실습처럼 서버가 내려간 동안의 실패가 통째로 빠져 있을 수 있다. 다음은 섞인 엔드포인트다. 하루 100만 건인 상품 조회와 1만 건인 결제를 하나의 SLI로 합치면, 결제가 전부 실패해도 전체는 99%다. 중요한 사용자 여정은 따로 SLO를 둔다.

SLO가 늘 깨져 있는데 아무 일도 없다. 목표가 현실보다 높거나 사용자가 그만큼 신경 쓰지 않는 기능이다. 목표를 내리거나, 깨졌을 때 무엇을 할지 정해야 한다. 아무 행동도 따르지 않는 SLO는 대시보드 장식일 뿐이다.

새벽에 숫자가 크게 흔들린다. 트래픽이 적어서다. 요청 50개 중 하나만 실패해도 2%다. 창을 길게 보고, 알림은 비율이 아니라 예산 소진 속도로 건다.

느린 응답이 지연 SLI에 안 잡힌다. 클라이언트가 타임아웃으로 먼저 끊으면 nginx는 499를 남기고, 서버는 끝까지 처리해 200을 남기기도 한다. 499를 어떻게 셀지 정해 두지 않으면 가장 느린 요청이 SLI에서 사라진다. 이 경우는 나쁜 요청으로 세는 편이 사용자 경험에 가깝다.

## 다시 99.57% 앞에서

보고서의 99.57%는 서버가 받은 요청만 센 숫자였다. 로드 밸런서에서 사용자 요청만 골라 다시 세면 97.84%였고, 그게 사용자가 겪은 쪽에 가깝다. SLI는 좋은 요청을 유효한 요청으로 나눈 비율이고, 무엇을 유효하다고 볼지, 어디서 셀지를 정하는 게 일의 대부분이다. 지연도 평균 대신 문턱 안의 비율로 센다. 목표는 과거 데이터에서 출발해 100%가 아닌 값으로 잡고, 굴러가는 창으로 잰다. 다음 글 [에러 예산](/posts/error-budgets)에서는 남은 0.1%를 얼마나 빨리 쓰고 있는지로 알림을 걸고 배포를 멈출지 정한다.

## 면접에서 나올 만한 질문

### SLI, SLO, SLA는 어떻게 다른가요

SLI는 서비스 상태를 재는 숫자로, 보통 좋은 요청을 유효한 요청으로 나눈 비율이다. SLO는 그 SLI가 일정 기간 지켜야 할 목표(28일 동안 99.9%)이고, SLA는 목표를 못 지켰을 때의 보상이 적힌 고객과의 계약이다. SLO는 SLA보다 엄격하게 잡아서 SLO를 어긴 시점에 계약까지는 여유가 남게 한다.

### 가용성 SLI를 계산할 때 분모와 분자에 무엇을 넣나요

분모에는 사용자가 보낸 유효한 요청만 넣는다. 헬스 체크나 내부 모니터링 요청은 빼고, 봇은 따로 본다. 분자는 서버 탓으로 실패하지 않은 요청이다. 5xx는 나쁜 요청이고, 4xx는 사용자 실수(400)면 좋은 요청으로 세되 429나 배포 실수로 생긴 404처럼 서버 탓인 코드는 나쁜 요청으로 정해 둔다.

### SLI는 어디서 재는 게 좋나요

보통 로드 밸런서 로그나 지표에서 잰다. 서버 안에서 재면 서버가 내려가 있는 동안의 실패를 통째로 놓친다. 실습에서도 1초 동안 서버를 내렸을 때 서버 로그는 99.57%, nginx 로그는 97.84%였다. 브라우저 RUM은 더 가깝지만 사용자 회선 잡음이 섞이고, 바깥 합성 검사는 트래픽이 없을 때를 메우는 보조로 쓴다.

### 지연 SLO에 평균이나 p99 대신 문턱 안 비율을 쓰는 이유는요

평균은 소수의 느린 요청을 대다수의 빠른 요청이 덮는다. 실습에서도 평균 80ms인데 p99는 0.81초였다. p99 같은 분위수는 서버별 값을 합쳐 전체 값을 구할 수 없지만, 비율은 분자끼리 분모끼리 더하면 그대로 합쳐진다. 그리고 나쁜 요청 수가 바로 나와서 에러 예산 계산으로 이어진다.

### Prometheus 히스토그램으로 지연 SLI를 구할 때 주의할 점은요

문턱이 히스토그램 칸 경계와 같아야 한다. `le="0.3"` 칸을 전체 개수로 나누면 0.3초 이하 비율이 나오지만, 칸이 없는 0.25를 쓰면 에러 없이 빈 결과가 나와서 대시보드와 알림이 조용히 비어 버린다. 그래서 SLO를 정할 때 계측 코드의 칸도 같이 맞춘다.

### 99.99% SLO는 한 달에 얼마나 멈춰도 되나요

30일 기준 약 4.32분이다. 99.9%면 43.2분, 99%면 7.2시간이다. 4분은 사람이 알림을 받고 확인을 시작하기에도 짧아서, 99.99% 이상은 자동 복구와 중복 구성이 전제된다. 직렬 의존성의 가용성은 곱해지니 내가 기대는 서비스들보다 높은 목표는 걸기 어렵다.

### 굴러가는 창과 달력 월 창은 무엇이 다른가요

달력 월은 매달 초기화되어 보고서와 SLA에 맞추기 쉽지만, 월말 장애가 다음 달에 바로 지워져 사용자 경험과 어긋난다. 굴러가는 창은 매일 하루씩 밀려서 장애가 정확히 창 길이만큼 남는다. 28일 창은 요일이 네 번씩 들어가 창마다 조건이 같아서 많이 쓴다.
