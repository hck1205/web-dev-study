## 열 하나 추가했는데 API가 멈췄다

배포 파이프라인이 `ALTER TABLE orders ADD COLUMN coupon text`를 실행했다. 메타데이터만 바꾸는 순간적인 작업이라 리뷰도 쉽게 통과했다. 그런데 그 직후 주문 API가 전부 타임아웃을 냈고, 6초쯤 뒤에 저절로 풀렸다. 로그에는 에러가 없다. 쿼리는 하나도 느려지지 않았는데 모두가 기다렸다.

이 글은 PostgreSQL 16에서 스키마를 바꿀 때 무엇이 서비스를 멈추게 하는지를 잰다. 어떤 `ALTER`가 어떤 잠금을 잡는지, 어떤 변경이 테이블을 통째로 다시 쓰는지, 그걸 피하는 순서는 무엇인지를 주문 200만 건(123MB) 테이블에서 문장마다 직접 돌려 봤다. 마지막에는 정수 기본 키가 21억에 가까워졌을 때 `bigint`로 바꾸는 작업을 처음부터 끝까지 따라간다.

이 주제의 다른 글: [마이그레이션 도구](/posts/db-migration-tools)(파일·기록·잠금 관리), [규모별 DB 설계](/posts/db-architecture-by-scale)(열 이름을 다섯 단계로 바꾸는 expand/contract 흐름), [인덱스의 대가](/posts/db-index-pitfalls)(CREATE INDEX CONCURRENTLY와 INVALID 인덱스). 이 글은 그 단계들 하나하나가 왜 그렇게 나뉘는지, 안에서 무슨 일이 일어나는지를 잰다.

```sql
CREATE TABLE orders (
  id         int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id    int NOT NULL,
  amount     int NOT NULL,
  memo       varchar(50),
  created_at timestamptz NOT NULL DEFAULT now()
);
-- 2,000,000행, 123 MB. users는 100,000행
```

## 잠금은 줄을 선다

처음 장면을 세 세션으로 재현했다. s1은 리포트 쿼리를 돌리고 트랜잭션을 6초 열어 둔다. s2가 열을 추가하고, 그 뒤에 s3이 주문 하나를 읽는다.

```sql
SELECT a.pid, coalesce(nullif(a.application_name, 'psql'), 's1-report') AS who, l.mode, l.granted,
       pg_blocking_pids(a.pid) AS blocked_by
FROM pg_locks l JOIN pg_stat_activity a USING (pid)
WHERE l.relation = 'orders'::regclass
ORDER BY l.granted DESC, a.backend_start;
```

```text
  pid  |    who    |        mode         | granted | blocked_by 
-------+-----------+---------------------+---------+------------
 11534 | s1-report | AccessShareLock     | t       | {}
 11537 | s2-ddl    | AccessExclusiveLock | f       | {11534}
 11554 | s3-select | AccessShareLock     | f       | {11537}
(3 rows)
```

`granted` 열을 위에서부터 읽는다. s1의 `SELECT`는 가장 약한 `AccessShareLock`을 잡았다. s2의 `ALTER TABLE`은 가장 강한 `AccessExclusiveLock`이 필요해서 s1이 끝나길 기다린다. 여기까지는 당연하다. 문제는 s3이다. s3이 원하는 `AccessShareLock`은 s1과 충돌하지 않는다. 그런데도 s3은 기다리고, `blocked_by`는 s1이 아니라 s2를 가리킨다.

PostgreSQL의 잠금은 테이블마다 줄을 세운다. 새로 온 요청은 이미 잡힌 잠금뿐 아니라 줄에서 기다리는 요청과도 충돌하는지 본다. 기다리는 `AccessExclusiveLock`은 모든 것과 충돌하니, 그 뒤에 오는 평범한 `SELECT`도 전부 줄을 선다. 아래 그림에서 단계를 넘기면 줄이 어떻게 막히는지 보인다.

그래서 DDL에는 `lock_timeout`을 건다. 잠금을 정해진 시간 안에 못 얻으면 포기해서, 뒤에 선 요청들을 오래 붙잡지 않는다. 포기했으면 잠시 쉬었다가 다시 시도한다. 같은 상황에서 다른 앱 연결이 100ms마다 주문을 읽게 해 두고, 그 앱이 겪은 가장 긴 지연을 쟀다.

```text
# lock_timeout 없음
 6.0s attempt 1: ALTER TABLE 성공
 6.1s 앱 SELECT 최대 지연: 5707 ms
# lock_timeout = 1s, 재시도
 1.3s attempt 1: canceling statement due to lock timeout
 2.8s attempt 2: canceling statement due to lock timeout
 4.8s attempt 3: canceling statement due to lock timeout
 6.3s attempt 4: ALTER TABLE 성공
 6.4s 앱 SELECT 최대 지연: 998 ms
```

DDL이 성공한 시각은 6초 언저리로 같다. 차이는 앱이 겪은 지연이다. `lock_timeout`이 없으면 앱이 5.7초 멈췄고, 1초로 걸면 1초를 넘지 않았다. 재시도 사이에는 잠금 요청이 줄에서 빠지니 그동안 앱 요청이 흘러간다. 실제로는 앱의 타임아웃보다 짧게, 보통 1~3초로 잡는다.

```sql
SET lock_timeout = '2s';             -- 잠금을 2초 넘게 기다리지 않는다
SET statement_timeout = '15min';     -- 예상보다 오래 도는 작업도 끊는다
ALTER TABLE orders ADD COLUMN coupon text;
```

긴 트랜잭션이 원인이니 그쪽도 본다. `pg_stat_activity`에서 `xact_start`가 오래된 연결, 특히 `idle in transaction`은 DDL의 적이다. 배포 전에 확인하고, `idle_in_transaction_session_timeout`으로 상한을 둔다. 잠금 대기를 추적하는 방법은 [비관적 잠금 글](/posts/pessimistic-locking)에 있다.

PostgreSQL의 잠금 규칙을 직접 따라가 보자. 한 테이블에 도착한 잠금 요청을 순서대로 받아서, 각각 바로 잡히는지(`granted`) 기다리는지(`wait`) 돌려준다. 잡힌 잠금 중 하나와 충돌하거나, 앞에서 기다리는 요청 중 하나와 충돌하면 기다린다. 충돌표는 PostgreSQL 문서의 테이블 잠금 표 그대로다.

## 문장마다 무슨 잠금을 잡고, 다시 쓰는가

DDL이 위험한 이유는 둘이다. 강한 잠금을 잡는 것, 그리고 그 잠금을 오래 쥐는 것이다. 오래 쥐는 이유는 대부분 테이블 전체를 다시 쓰거나(rewrite) 전체를 훑기(scan) 때문이다. 문장마다 트랜잭션 안에서 실행한 뒤 `pg_locks`의 모드와 `pg_relation_filenode`(바뀌면 새 파일로 다시 쓴 것)를 확인하고, 시간을 쟀다. 200만 행에서의 값이다.

| 문장 | 잡는 잠금 | 다시 쓰기 | 시간 |
|---|---|---|---|
| `ADD COLUMN note text` | AccessExclusive | 없음 | 6.7 ms |
| `ADD COLUMN status text NOT NULL DEFAULT 'paid'` | AccessExclusive | 없음 | 3.1 ms |
| `ADD COLUMN paid_at timestamptz NOT NULL DEFAULT now()` | AccessExclusive | 없음 | 2.6 ms |
| `ADD COLUMN token uuid DEFAULT gen_random_uuid()` | AccessExclusive | 있음 | 7,380 ms |
| `ALTER COLUMN memo TYPE varchar(100)` (50에서 늘리기) | AccessExclusive | 없음 | 1.2 ms |
| `ALTER COLUMN memo TYPE varchar(20)` (줄이기) | AccessExclusive | 있음 | 4,359 ms |
| `ALTER COLUMN memo TYPE text` | AccessExclusive | 없음 | 2.9 ms |
| `ALTER COLUMN amount TYPE bigint` | AccessExclusive | 있음 | 3,701 ms |
| `ALTER COLUMN memo SET NOT NULL` | AccessExclusive | 전체 훑기 | 283 ms |
| `ADD CONSTRAINT ... CHECK (amount > 0)` | AccessExclusive | 전체 훑기 | 200 ms |
| `ADD CONSTRAINT ... CHECK (amount > 0) NOT VALID` | AccessExclusive | 없음 | 1.1 ms |
| `VALIDATE CONSTRAINT amount_pos` | ShareUpdateExclusive | 전체 훑기 | 153 ms |
| `ADD FOREIGN KEY ... REFERENCES users` | ShareRowExclusive (양쪽 표) | 전체 훑기 | 917 ms |
| `ADD FOREIGN KEY ... NOT VALID` | ShareRowExclusive (양쪽 표) | 없음 | 0.4 ms |
| `VALIDATE CONSTRAINT orders_user_fk` | ShareUpdateExclusive, users는 RowShare | 전체 훑기 | 818 ms |
| `CREATE INDEX` | Share | 인덱스 생성 | 977 ms |
| `RENAME COLUMN`, `DROP COLUMN`, `SET DEFAULT` | AccessExclusive | 없음 | 1 ms 안팎 |

이 표에서 읽을 것은 세 가지다.

첫째, 거의 모든 `ALTER TABLE`이 `AccessExclusive`다. 1ms짜리라도 앞 절의 줄 문제는 그대로 생긴다. "빨리 끝나니 괜찮다"가 아니라 "잠금을 얻을 때까지 기다리는 동안 무슨 일이 생기나"를 봐야 한다.

둘째, 시간이 긴 줄은 모두 다시 쓰거나 훑는 문장이다. 이 시간 내내 `AccessExclusive`를 쥐고 있으니, 200만 행에서 7초면 2억 행에서는 십 분이 넘는다. 그동안 테이블은 읽기도 안 된다.

셋째, 같은 결과를 약한 잠금으로 얻는 길이 있다. `CHECK`나 외래 키를 `NOT VALID`로 붙이면 기존 행 검사를 건너뛰어 순간에 끝나고, 따로 `VALIDATE`하면 `ShareUpdateExclusive`만 잡는다. 이 잠금은 `SELECT`, `INSERT`, `UPDATE`, `DELETE`와 충돌하지 않아서 서비스가 도는 중에 훑어도 된다. 외래 키를 그냥 추가하면 `ShareRowExclusive`가 양쪽 테이블에 걸리는데, 이 잠금은 쓰기(`RowExclusive`)와 충돌한다. 0.9초 동안 `orders`와 `users`에 쓰기가 멈춘다는 뜻이다.

## 기본값이 있는 열은 PostgreSQL 11부터 빠르다

PostgreSQL 10까지는 `ADD COLUMN ... DEFAULT 'paid'`가 모든 행에 값을 써 넣느라 테이블을 다시 썼다. 11부터는 기본값을 카탈로그에 한 번만 적어 두고, 옛 행을 읽을 때 그 값을 채워 보여 준다.

```sql
ALTER TABLE orders ADD COLUMN status text NOT NULL DEFAULT 'paid';
SELECT attname, atthasmissing, attmissingval
FROM pg_attribute
WHERE attrelid = 'orders'::regclass AND attname = 'status';
```

```text
 attname | atthasmissing | attmissingval 
---------+---------------+---------------
 status  | t             | {paid}
(1 row)
```

`attmissingval`에 `{paid}` 하나만 적혔다. 디스크의 200만 행은 그대로다. 그래서 `NOT NULL DEFAULT`를 붙여도 3ms에 끝났다.

조건이 있다. 기본값이 행마다 달라지는 함수(volatile)면 이 방법을 못 쓴다. `gen_random_uuid()`와 `clock_timestamp()`는 행마다 새 값을 만들어야 해서 7초, 4초씩 다시 썼다. `now()`는 다르다. 트랜잭션 안에서는 값이 하나라서(stable) 빠른 경로를 탄다. 대신 기존 200만 행이 모두 "ALTER를 실행한 시각"을 갖게 된다. `paid_at`처럼 의미가 있는 열이라면 옛 행에 거짓 값이 들어간 셈이니, 그럴 때는 NULL 허용으로 추가하고 실제 값을 따로 채운다.

## 타입 바꾸기는 대부분 다시 쓴다

`varchar(50)`을 `varchar(100)`이나 `text`로 넓히는 건 저장 형식이 같아서 순간에 끝났다. 반대로 `varchar(20)`으로 줄이면 모든 값을 검사하며 다시 썼다. `int`를 `bigint`로 바꾸면 한 칸의 크기가 4바이트에서 8바이트로 바뀌니 모든 행을 새로 쓰고, 그 열이 들어간 인덱스도 다시 만든다. 3.7초 동안 `AccessExclusive`다.

int에서 bigint로 가는 일은 생각보다 자주 생긴다. `int` 기본 키는 2,147,483,647에서 멈춘다.

```sql
CREATE TABLE t_overflow (id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, v text);
SELECT setval(pg_get_serial_sequence('t_overflow', 'id'), 2147483646);
INSERT INTO t_overflow (v) VALUES ('a');
INSERT INTO t_overflow (v) VALUES ('b');
```

```text
INSERT 0 1
ERROR:  nextval: reached maximum value of sequence "t_overflow_id_seq" (2147483647)
```

이 에러를 보는 날에는 그 테이블에 쓰기가 전혀 안 된다. 그때 가서 `ALTER COLUMN id TYPE bigint`를 하면 수억 행을 다시 쓰는 동안 또 멈춘다. 시퀀스 사용량은 미리 지켜본다.

```sql
-- int 시퀀스가 얼마나 찼나
SELECT schemaname, sequencename, data_type, last_value,
       round(100.0 * last_value / max_value, 1) AS used_pct
FROM pg_sequences
WHERE data_type = 'integer'::regtype
ORDER BY used_pct DESC NULLS LAST;
```

```text
 schemaname | sequencename | data_type | last_value | used_pct 
------------+--------------+-----------+------------+----------
 public     | t_seq_id_seq | integer   | 1600000000 |     74.5
(1 row)
```

시험용 표의 시퀀스를 16억까지 올려 본 결과다. 70%를 넘으면 경보를 걸어 두는 곳이 많다. 하루에 몇 행이 늘어나는지로 남은 날짜를 계산해 보면, 바꾸는 작업에 몇 주가 걸려도 여유가 있는지 알 수 있다.

새 테이블은 처음부터 `bigint`로 만드는 게 가장 싸다. 이미 `int`라면 다음 절의 방법으로 서비스를 멈추지 않고 바꾼다.

실제로 돌린 SQL과 시간이다. 단계마다 `lock_timeout`을 건다.

```sql
SET lock_timeout = '2s';

-- 1. 늘리기: 새 열 추가 (3.6 ms)
ALTER TABLE orders ADD COLUMN id_big bigint;

-- 2. 새로 들어오거나 바뀌는 행은 트리거가 채운다
CREATE FUNCTION orders_sync_id_big() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  NEW.id_big := NEW.id;
  RETURN NEW;
END $$;
CREATE TRIGGER orders_sync_id_big BEFORE INSERT OR UPDATE ON orders
  FOR EACH ROW EXECUTE FUNCTION orders_sync_id_big();

-- 3. 옛 행 채우기: 1만 행씩 200번 (앱 코드에서 반복, 22.3초)
UPDATE orders SET id_big = id
WHERE id > $1 AND id <= $1 + 10000 AND id_big IS NULL;

-- 4. NOT NULL 증명과 유니크 인덱스. 둘 다 쓰기를 막지 않는다
ALTER TABLE orders ADD CONSTRAINT orders_id_big_not_null CHECK (id_big IS NOT NULL) NOT VALID;  -- 3 ms
ALTER TABLE orders VALIDATE CONSTRAINT orders_id_big_not_null;                                  -- 797 ms
CREATE UNIQUE INDEX CONCURRENTLY orders_id_big_key ON orders (id_big);                           -- 1,583 ms
```

```sql
-- 5. 바꿔치기: 이 트랜잭션만 AccessExclusive를 잡는다
BEGIN;
SET LOCAL lock_timeout = '2s';
ALTER TABLE orders DROP CONSTRAINT orders_pkey;
ALTER TABLE orders ALTER COLUMN id_big SET NOT NULL;           -- 유효한 CHECK가 있어 훑지 않는다
ALTER TABLE orders ADD CONSTRAINT orders_pkey PRIMARY KEY USING INDEX orders_id_big_key;
ALTER TABLE orders ALTER COLUMN id DROP IDENTITY;
ALTER TABLE orders RENAME COLUMN id TO id_old;
ALTER TABLE orders RENAME COLUMN id_big TO id;
ALTER TABLE orders ALTER COLUMN id_old DROP NOT NULL;          -- 새 INSERT가 id_old를 비워도 되게
DROP TRIGGER orders_sync_id_big ON orders;
DO $$ BEGIN
  EXECUTE format('ALTER TABLE orders ALTER COLUMN id ADD GENERATED BY DEFAULT AS IDENTITY (START WITH %s)',
                 (SELECT max(id) + 1 FROM orders));
END $$;
COMMIT;
```

```text
ALTER TABLE
Time: 0.986 ms
ALTER TABLE
Time: 0.588 ms
NOTICE:  ALTER TABLE / ADD CONSTRAINT USING INDEX will rename index "orders_id_big_key" to "orders_pkey"
ALTER TABLE
Time: 1.096 ms
...
DO
Time: 2.761 ms
COMMIT
Time: 95.878 ms
```

바꿔치기 트랜잭션 안의 문장은 모두 몇 ms였고, 커밋까지 합쳐도 0.1초 남짓이다. 곧장 `ALTER COLUMN id TYPE bigint`를 했다면 테이블 재작성과 인덱스 재생성 내내 멈췄을 것이다. 결과를 확인하고 새 행을 넣어 봤다.

실제 서비스에서는 더 챙길 게 있다. 이 키를 참조하는 외래 키(`order_items.order_id`)도 `bigint`로 같은 과정을 거쳐야 하고, 바꿔치기 때 외래 키를 새 기본 키로 다시 걸어야 한다(`NOT VALID`로 걸고 나중에 `VALIDATE`). 논리 복제나 CDC가 붙어 있으면 열 이름이 바뀐 걸 소비자가 따라오는지도 본다. 시작하기 전에 스테이징에서 운영 크기에 가까운 데이터로 한 번 끝까지 돌려 보는 게 가장 확실하다.

## 옛 행 채우기는 잘게 나눈다

3단계의 배치는 왜 필요할까. 새 열을 한 번에 채우는 것과 1만 행씩 나눠 채우는 것을 비교했다. 그동안 다른 연결이 50ms마다 아무 주문 하나를 고치게 하고, 그 `UPDATE`가 겪은 가장 긴 지연을 쟀다.

```text
one-shot   dead=2000002 total=12.1s rows=2000000 longest_tx=all WAL=692 MB app_update_max=12005ms
batched    dead=1916432 total=14.6s batches=200 longest_tx=117ms WAL=683 MB app_update_max=76ms
```

한 번에 하면 12초 만에 끝나지만, 그 12초 동안 모든 행에 행 잠금이 걸려 있어서 앱의 `UPDATE`가 12초를 기다렸다. 나누면 전체 시간은 조금 늘었지만 트랜잭션 하나가 길어야 0.1초라 앱은 76ms 이상 기다리지 않았다.

WAL 양은 둘 다 700MB 가까이로 거의 같다. 바꾸는 행 수가 같으니 당연하다. 차이는 내보내는 속도다. 한 번에 하면 12초 만에 700MB가 쏟아지고, 복제본은 그걸 따라잡는 동안 뒤처진다. 복제본에서 읽는 화면은 그만큼 낡은 데이터를 보여 준다. 배치 사이에 잠깐 쉬면서 `pg_stat_replication`의 `replay_lag`을 보고 속도를 조절하는 게 안전하다. 죽은 행도 200만 개 가까이 생기니 자동 VACUUM이 따라오는지 본다. 이 부분은 [MVCC와 VACUUM 글](/posts/postgres-mvcc-vacuum)에 있다.

배치를 짤 때 몇 가지를 지킨다. 범위는 기본 키 인덱스로 찾을 수 있는 조건(`id > $1 AND id <= $1 + 10000`)으로 자른다. `OFFSET`으로 자르면 뒤로 갈수록 느려진다. `AND id_big IS NULL`을 붙여 두면 중간에 멈췄다 다시 시작해도 같은 행을 두 번 쓰지 않는다. 배치마다 커밋하고, 진행 위치를 로그로 남긴다. 큰 작업을 나눠 돌리는 일반적인 방법은 [배치 처리 글](/posts/batch-processing)이 자세하다.

## 인덱스, 이름 바꾸기, 열 지우기

인덱스는 `CREATE INDEX`가 `Share` 잠금을 잡아 만드는 내내 쓰기를 막는다(위 표에서 977ms). 운영 테이블에는 `CREATE INDEX CONCURRENTLY`를 쓴다. 잠금이 `ShareUpdateExclusive`라 쓰기를 막지 않는 대신, 테이블을 두 번 훑고 먼저 시작한 트랜잭션이 끝나길 기다려서 더 오래 걸린다. 트랜잭션 안에서는 못 쓰고, 실패하면 `INVALID` 인덱스가 남는다. 자세한 건 [인덱스의 대가 글](/posts/db-index-pitfalls)에 있고, 마이그레이션 도구에서 이걸 돌리다 생기는 함정은 [마이그레이션 도구 글](/posts/db-migration-tools)에 있다. 인덱스를 지울 때도 `DROP INDEX CONCURRENTLY`, 다시 만들 때는 `REINDEX CONCURRENTLY`(PostgreSQL 12부터)를 쓴다.

`RENAME COLUMN`과 `DROP COLUMN`은 1ms짜리지만 앱이 문제다. 배포 중에는 옛 코드와 새 코드가 함께 도는데, 옛 코드가 찾는 열이 사라지면 에러가 난다. 그래서 이름 바꾸기는 새 열 추가 → 두 열에 쓰기 → 옛 행 채우기 → 새 열 읽기 → 옛 열 삭제로 나눈다. 각 단계 사이에 배포가 하나씩 들어간다. 단계별 상태는 [규모별 DB 설계 글](/posts/db-architecture-by-scale)에 그림으로 있다.

열을 지우는 마지막 단계에도 함정이 있다. ORM이 `SELECT *`나 모델에 적힌 모든 열을 쓰고 있으면, 코드에서 그 열을 안 읽어도 지우는 순간 에러가 난다. Rails의 `ignored_columns`처럼 먼저 모델에서 빼고 배포한 다음에 지운다. PostgreSQL의 `DROP COLUMN`은 디스크에서 바로 지우지 않고 보이지 않게만 표시하니, 공간은 나중에 행이 다시 쓰일 때 돌아온다.

## MySQL은 어떻게 다른가

MySQL 8의 InnoDB는 `ALTER TABLE`마다 알고리즘을 고른다. `ALGORITHM=INSTANT`는 메타데이터만 바꾼다. 8.0.12부터 맨 뒤에 열 추가가, 8.0.29부터는 아무 위치의 열 추가와 열 삭제가 된다. `ALGORITHM=INPLACE, LOCK=NONE`은 보조 인덱스 추가처럼 테이블을 복사하지 않고 작업하면서 쓰기를 허용한다. 열 타입 변경처럼 둘 다 안 되면 `COPY`로 새 테이블을 만들어 옮기는 동안 쓰기가 막힌다. 알고리즘을 명시해 두면 원하는 방식이 불가능할 때 그냥 느린 방식으로 넘어가지 않고 에러를 낸다.

```sql
-- MySQL 8: 안 되면 에러를 내라
ALTER TABLE orders ADD COLUMN coupon varchar(50), ALGORITHM=INSTANT;
ALTER TABLE orders ADD INDEX orders_user_idx (user_id), ALGORITHM=INPLACE, LOCK=NONE;
```

INSTANT와 INPLACE도 시작과 끝에 메타데이터 잠금(MDL)을 잠깐 배타적으로 잡는다. 긴 트랜잭션 뒤에서 이 잠금을 기다리면 PostgreSQL과 똑같이 뒤의 쿼리가 모두 `Waiting for table metadata lock`으로 선다. MySQL의 `lock_wait_timeout` 기본값은 31,536,000초(1년)라서 사실상 무한히 기다린다. 마이그레이션 세션에서는 몇 초로 낮춘다.

복사가 필요한 큰 변경에는 gh-ost나 pt-online-schema-change를 쓴다. 둘 다 새 구조의 빈 테이블을 만들고, 기존 행을 조금씩 복사하면서 그사이의 변경을 따라 적용한 뒤, 이름을 바꿔치기한다. pt-online-schema-change는 트리거로, gh-ost는 binlog를 읽어서 변경을 따라간다. 앞에서 본 PostgreSQL의 bigint 바꿔치기와 같은 생각이다.

## 배포 전에 확인하는 순서

스키마 변경 PR을 리뷰할 때 이 순서로 본다.

1. 이 문장이 잡는 잠금은 무엇인가. `AccessExclusive`면 `lock_timeout`과 재시도가 있는가.
2. 테이블을 다시 쓰거나 훑는가. 그렇다면 `NOT VALID`와 `VALIDATE`, `CONCURRENTLY`, 새 열과 배치처럼 나눌 방법이 있는가.
3. 옛 코드가 이 스키마에서 돌아가는가. 배포 중에는 둘이 같이 돈다. 열 삭제와 이름 변경은 앱이 그 열을 잊은 다음 배포로 미룬다.
4. 대량 `UPDATE`가 있다면 배치로 나눴는가. 복제 지연과 VACUUM을 볼 사람이 있는가.
5. 실행 시점에 긴 트랜잭션이 없는가. `pg_stat_activity`의 `xact_start`와 `state = 'idle in transaction'`을 먼저 본다.

```sql
-- 배포 직전: 30초 넘게 열린 트랜잭션
SELECT pid, now() - xact_start AS age, state, left(query, 60) AS query
FROM pg_stat_activity
WHERE xact_start < now() - interval '30 seconds'
ORDER BY xact_start;
```

## 잠금은 짧게, 무거운 일은 잠금 밖에서

스키마 변경이 서비스를 멈추는 경로는 두 개다. 강한 잠금이 줄 앞에서 기다리며 뒤의 모든 쿼리를 막는 것, 그리고 강한 잠금을 쥔 채 테이블을 다시 쓰거나 훑는 것이다. 앞의 것은 `lock_timeout`과 재시도로, 뒤의 것은 무거운 일을 약한 잠금으로 미리 해 두고(`NOT VALID` 후 `VALIDATE`, `CONCURRENTLY`, 배치 채우기) 강한 잠금은 바꿔치기 순간에만 잡는 방법으로 피한다. 그리고 그 모든 단계가 옛 코드와 새 코드 둘 다에서 돌아가게 나눈다.

## 면접에서 나올 만한 질문

### 1ms에 끝나는 ALTER TABLE이 왜 서비스를 멈추게 하나요?

거의 모든 `ALTER TABLE`은 `AccessExclusiveLock`이 필요해서 긴 트랜잭션이 있으면 그 뒤에서 기다린다. PostgreSQL의 잠금은 줄을 서기 때문에, 이후에 오는 평범한 `SELECT`도 기다리는 `AccessExclusiveLock`과 충돌해 그 뒤에 선다. 문장 실행 시간이 아니라 잠금을 기다리는 시간 동안 테이블 전체가 멈춘다. 그래서 DDL에는 `lock_timeout`을 걸고 실패하면 재시도한다.

### lock_timeout은 얼마로 잡고, 실패하면 어떻게 하나요?

앱의 요청 타임아웃보다 짧게, 보통 1~3초로 잡는다. 실험에서 1초로 걸었더니 앱이 겪은 최대 지연이 5.7초에서 1초 아래로 줄었다. 실패하면 잠시 쉬었다가 재시도하고, 계속 실패하면 원인인 긴 트랜잭션을 `pg_stat_activity`에서 찾아 정리하거나 트래픽이 적은 시간에 다시 한다.

### PostgreSQL에서 기본값이 있는 열 추가는 왜 빠른가요? 예외는요?

PostgreSQL 11부터 상수나 stable 기본값은 카탈로그(`attmissingval`)에 한 번만 적고, 옛 행을 읽을 때 채워 보여 줘서 테이블을 다시 쓰지 않는다. `gen_random_uuid()`, `clock_timestamp()`처럼 행마다 값이 다른 volatile 기본값은 모든 행을 다시 쓴다. `now()`는 빠르지만 기존 행이 모두 ALTER 시각을 갖게 되니 의미 있는 열이면 NULL로 추가하고 따로 채운다.

### NOT NULL이나 외래 키를 큰 테이블에 안전하게 거는 방법은요?

제약을 `NOT VALID`로 먼저 붙이면 기존 행 검사 없이 바로 끝나고, `VALIDATE CONSTRAINT`가 `ShareUpdateExclusive`라는 약한 잠금으로 기존 행을 훑는다. 이 잠금은 읽기와 쓰기를 막지 않는다. NOT NULL은 `CHECK (col IS NOT NULL) NOT VALID`를 검증해 두면 PostgreSQL 12부터 `SET NOT NULL`이 훑기를 건너뛴다.

### int 기본 키가 21억에 가까워졌습니다. 어떻게 bigint로 바꾸나요?

`ALTER COLUMN TYPE bigint`는 테이블 재작성과 인덱스 재생성 내내 막으니 쓰지 않는다. bigint 새 열을 추가하고, 트리거로 새 행을 채우고, 옛 행은 범위 배치로 채운 뒤, 유니크 인덱스를 `CONCURRENTLY`로 만들고 NOT NULL을 `NOT VALID` CHECK로 증명해 둔다. 마지막에 짧은 트랜잭션 하나로 기본 키를 새 인덱스로 옮기고 이름을 바꾼다. 참조하는 외래 키도 같은 과정을 거친다.

### 대량 백필은 왜 나눠서 하나요?

한 번에 하면 모든 행에 행 잠금이 걸려 그동안 앱의 쓰기가 기다리고, WAL이 한꺼번에 쏟아져 복제본이 뒤처진다. 실험에서 200만 행을 한 번에 채우는 동안 앱의 UPDATE가 12초 기다렸고, 1만 행씩 나누니 76ms를 넘지 않았다. 배치는 기본 키 범위로 자르고, 다시 시작해도 안전하게 조건을 넣고, 복제 지연을 보며 속도를 조절한다.

### MySQL에서 무중단 스키마 변경은 어떻게 하나요?

`ALGORITHM=INSTANT`나 `INPLACE, LOCK=NONE`을 명시해 가능한 변경은 복사 없이 하고, 불가능하면 에러가 나게 한다. 이 경우에도 메타데이터 잠금을 잠깐 잡으니 긴 트랜잭션과 `lock_wait_timeout`(기본 1년)을 조심한다. 타입 변경처럼 복사가 필요한 큰 변경은 gh-ost나 pt-online-schema-change로 새 테이블에 복사하며 변경을 따라간 뒤 바꿔치기한다.
