정산 담당자에게서 메시지가 왔다. 장바구니 화면, 주문 완료 메일, 정산 리포트에 찍힌 같은 주문의 결제 금액이 각각 13,614원, 13,612원, 13,609원이라는 것이다. 15% 할인 쿠폰을 쓴 주문이었다.

세 곳의 코드를 열어 보니 계산은 다 맞았다. 다만 할인을 적용하는 시점과 끝자리 처리 방식이 달랐다.

```js
// 1,990원 × 3, 4,550원 × 1, 785원 × 7 주문에 15% 할인
const lines = [{ price: 1990, qty: 3 }, { price: 4550, qty: 1 }, { price: 785, qty: 7 }];

// 장바구니: 줄마다 할인하고 반올림해서 더한다
const cart = lines.reduce((s, l) => s + Math.round(l.price * l.qty * 0.85), 0);
// 주문: 먼저 다 더하고 한 번 할인한 뒤 내림
const sum = lines.reduce((s, l) => s + l.price * l.qty, 0);
const order = Math.floor(sum * 0.85);
// 정산: 단가에 할인을 적용해 내림하고 수량을 곱한다
const settle = lines.reduce((s, l) => s + Math.floor(l.price * 0.85) * l.qty, 0);

console.log({ sum, cart, order, settle });
```

장바구니는 5,074.5를 5,075로 올렸고, 정산은 785원의 85%인 667.25원을 667원으로 버린 뒤 7을 곱해 1.75원을 잃었다. 누구의 계산이 틀렸다기보다 "주문 금액은 어떻게 계산하는가"라는 규칙이 어디에도 한 번만 쓰여 있지 않았다.

도메인 주도 설계(DDD)의 전술 패턴은 이런 규칙을 담을 그릇을 정해 준다. 엔티티, 값 객체, 도메인 서비스, 도메인 이벤트다. 큰 경계(바운디드 컨텍스트)와 함께 지켜야 하는 규칙의 묶음(애그리거트)은 [DDD 바운디드 컨텍스트 글](/posts/ddd-bounded-context)에서 다뤘다. 이 글은 그 안을 채우는 작은 부품들을 본다. 그 부품들을 DB와 잇는 리포지토리와 작업 단위는 [엔터프라이즈 패턴 글](/posts/enterprise-application-patterns)에 있다. 예제는 TypeScript를 Node 22로 실행했다.

## 같음을 무엇으로 판단하나

전술 패턴의 첫 질문은 단순하다. 두 객체가 "같다"는 건 무슨 뜻인가.

회원 두 명의 이름이 모두 "김민수"이고 생일도 같다. 그래도 둘은 다른 사람이다. 반대로 한 회원이 이사를 가고 이름을 바꿔도 같은 회원이다. 이렇게 속성이 아니라 식별자로 같음을 판단하고, 시간이 지나며 상태가 바뀌어도 같은 것으로 이어지는 객체를 엔티티(Entity)라고 한다.

1,000원과 1,000원은 어느 쪽이든 같다. 주문서에 적힌 1,000원을 다른 1,000원으로 바꿔 써도 아무도 모른다. 배송지 "서울시 중구 세종대로 110"도 마찬가지다. 이렇게 값이 같으면 같은 것으로 보는 객체를 값 객체(Value Object)라고 한다.

이 구분이 중요한 이유는 다루는 방식이 완전히 달라지기 때문이다. 엔티티는 식별자를 들고 여기저기 참조되며, 상태가 바뀌는 순간을 추적해야 한다. 값 객체는 그런 걱정이 없다. 바뀌지 않게 만들고, 필요하면 새로 만들어 갈아 끼운다.

아래 그림은 주문 하나 안에서 둘이 어떻게 섞이는지 보여 준다. 주문과 주문 줄은 번호로 구분하는 엔티티이고, 금액과 배송지는 값 객체다.

## 값 객체는 바뀌지 않고 스스로 검사한다

처음 장면으로 돌아가면, 금액이 `number`였던 게 문제의 절반이다. 숫자는 음수도 되고, 소수도 되고, 원과 달러가 섞여도 아무 말을 하지 않는다. 이렇게 업무 개념을 원시 타입으로만 들고 다니는 걸 원시 타입 집착(primitive obsession)이라고 부른다. 금액, 이메일, 수량처럼 규칙이 있는 값에 자기 타입을 주면 그 규칙이 들어갈 자리가 생긴다.

```ts
// money.ts (Node 22, 타입 지우기로 실행)
type Currency = "KRW" | "USD";

export class Money {
  readonly amount: number; // 가장 작은 단위(원, 센트)의 정수
  readonly currency: Currency;

  private constructor(amount: number, currency: Currency) {
    if (!Number.isSafeInteger(amount)) throw new RangeError(`정수가 아닌 금액: ${amount}`);
    if (amount < 0) throw new RangeError(`음수 금액: ${amount}`);
    this.amount = amount;
    this.currency = currency;
    Object.freeze(this); // 만든 뒤에는 바꿀 수 없다
  }

  static of(amount: number, currency: Currency = "KRW") {
    return new Money(amount, currency);
  }

  add(other: Money) {
    this.#sameCurrency(other);
    return new Money(this.amount + other.amount, this.currency); // 새 객체를 돌려준다
  }

  // 할인 규칙은 여기 한 곳에만 있다: 합계에 적용하고 원 단위 내림
  discount(rate: number) {
    return new Money(Math.floor(this.amount * (1 - rate)), this.currency);
  }

  equals(other: Money) {
    return this.amount === other.amount && this.currency === other.currency;
  }

  #sameCurrency(other: Money) {
    if (other.currency !== this.currency) {
      throw new TypeError(`통화가 다르다: ${this.currency} + ${other.currency}`);
    }
  }
}
```

값 객체의 성질 세 가지가 코드에 다 들어 있다. 같음은 값으로 판단한다(`equals`). 만든 뒤에는 바뀌지 않는다(`readonly`, `Object.freeze`, 연산은 새 객체를 돌려준다). 그리고 잘못된 값으로는 아예 만들어지지 않는다(생성자 검사). 이 마지막 성질 덕분에 `Money`를 받는 코드는 "음수면 어떡하지"를 다시 검사하지 않아도 된다.

돌려 보면 이렇게 나온다.

```ts
const a = Money.of(1000);
const b = Money.of(1000);
console.log(a === b, a.equals(b));
console.log(a.add(Money.of(500)).amount, a.amount);
try { (a as any).amount = 0; } catch (e) { console.log(e.constructor.name, e.message); }
try { a.add(Money.of(3, "USD")); } catch (e) { console.log(e.message); }
try { Money.of(10.5); } catch (e) { console.log(e.message); }
```

```text
통화가 다르다: KRW + USD

```

첫 줄이 JavaScript에서 값 객체를 쓸 때 가장 먼저 걸리는 곳이다. `===`는 객체의 주소를 비교하니 같은 1,000원이어도 `false`다. 그래서 `equals`를 따로 둔다. 같은 이유로 `Set`이나 `Map`의 키로 값 객체를 넣으면 같은 값이 여러 개 들어간다. 키가 필요하면 `"1000:KRW"` 같은 문자열로 바꿔 쓴다.

둘째 줄은 `add`가 원래 객체를 건드리지 않았다는 걸 보여 준다. 셋째 줄의 `TypeError`는 이 코드가 모듈(엄격 모드)이라 나온 것이고, 엄격 모드가 아닌 스크립트에서는 대입이 조용히 무시된다. 어느 쪽이든 값은 바뀌지 않는다. TypeScript의 `readonly`는 컴파일 때만 막아 주므로 런타임까지 막고 싶으면 `Object.freeze`를 함께 쓴다.

금액을 정수로 들고 다니는 데도 이유가 있다. 부동소수점은 `0.1 + 0.2`가 `0.30000000000000004`가 되는 세계다. 원화는 원 단위 정수, 달러는 센트 단위 정수로 저장하고, 비율 계산 뒤 끝자리 처리는 `Money`가 한 가지 방식으로만 한다. 이제 장바구니, 주문, 정산이 모두 `subtotal.discount(0.15)`를 부르면 셋 다 13,612원이 나온다.

## 나머지 1원은 누구에게 가나

값 객체에 규칙이 모이면 그 규칙을 정교하게 만들 수 있다. 13,612원을 결제했는데 줄 하나만 부분 취소한다면 줄마다 얼마씩 돌려줘야 할까. 줄 금액 비율로 나누면 소수가 나오고, 각자 내림하면 합이 13,612원보다 작아진다. 파울러가 『PoEAA』에서 든 예가 이 문제다. 나누고 남은 몇 원을 앞에서부터 1원씩 나눠 준다.

## 엔티티는 식별자와 생애를 가진다

엔티티 쪽에서 신경 쓸 것은 식별자다. 같음을 식별자로 판단하니 `equals`도 식별자만 비교한다.

```ts
export class Member {
  readonly id: MemberId;     // 식별자도 값 객체로 두면 OrderId와 섞이지 않는다
  #email: Email;
  #grade: "BASIC" | "VIP";

  constructor(id: MemberId, email: Email) {
    this.id = id;
    this.#email = email;
    this.#grade = "BASIC";
  }

  changeEmail(next: Email) { this.#email = next; }   // 상태는 바뀌어도 같은 회원이다
  equals(other: Member) { return this.id.equals(other.id); }
}
```

식별자를 언제 만드느냐가 꽤 큰 결정이다. DB 시퀀스(`GENERATED ALWAYS AS IDENTITY`)에 맡기면 저장하기 전까지 객체에 id가 없다. 이 상태에서 `equals`와 `hashCode`를 id로 구현하면, 저장 전에 `Set`에 넣은 객체의 해시가 저장 뒤에 바뀌어 `Set`에서 찾을 수 없게 된다. JPA에서 엔티티의 `equals`를 어떻게 구현하느냐로 논쟁이 끊이지 않는 이유다. 애플리케이션에서 UUIDv7 같은 id를 먼저 만들어 생성자에서 넣으면 이 문제가 사라지고, 저장 전에도 다른 객체가 이 id를 참조할 수 있다. 대신 키가 커지고 인덱스 크기가 는다. 키 종류별 장단점은 [키와 반정규화 글](/posts/db-keys-denormalization)에 있다.

엔티티는 상태가 바뀌니 바뀌는 방법을 좁혀야 한다. `setGrade("VIP")`를 아무 데서나 부를 수 있으면 "누적 결제 100만 원 이상이어야 VIP"라는 규칙이 지켜진다는 보장이 없다. 상태는 `promoteIfEligible(totalPaid)` 같은 업무 동작 메서드로만 바꾸고, 그 안에서 규칙을 검사한다.

## 규칙이 객체 안에 있는 모델과 밖에 있는 모델

이렇게 엔티티와 값 객체가 자기 규칙을 가진 모델을 풍부한 도메인 모델(rich domain model)이라고 한다. 반대로 객체에는 필드와 getter, setter만 있고 규칙은 전부 서비스에 있는 모델을 빈약한 모델(anemic model)이라고 부른다. 같은 주문 취소를 두 방식으로 쓰면 차이가 바로 보인다.

```ts
// 빈약한 모델: 서비스가 주문의 속을 다 안다
class OrderService {
  cancel(order: OrderData) {
    if (order.status === "SHIPPED") throw new Error("배송된 주문");
    order.status = "CANCELED";
    order.refund = Math.floor(order.total * (1 - order.couponRate));
  }
}

// 풍부한 모델: 주문이 자기 규칙을 지킨다. 서비스는 순서만 정한다
class CancelOrder {
  constructor(private readonly orders: OrderRepository) {}
  async run(id: OrderId) {
    const order = await this.orders.findById(id);
    order.cancel();               // 검사와 환불 계산은 Order 안에 있다
    await this.orders.save(order);
  }
}
```

빈약한 모델의 진짜 문제는 규칙이 흩어질 수 있다는 점이다. `order.status = "CANCELED"`를 쓸 수 있는 곳이면 어디서든 배송 검사를 건너뛸 수 있다. 처음 장면에서 금액 계산이 세 곳에 흩어졌던 것과 같은 일이 상태 전이에도 생긴다. 이 모양이 MVC 구조에서 어떻게 생겨나는지는 [MVC 패턴 글](/posts/mvc-pattern)에서 다룬다.

## 빈약한 모델이 오히려 맞는 곳

그렇다고 모든 객체를 풍부하게 만들 필요는 없다. 규칙이 거의 없는 곳에 업무 메서드를 만들면, `rename(name)`이 하는 일이 `this.name = name` 한 줄인 메서드만 쌓인다.

다음 경우는 빈약한 모델이나 그냥 데이터 객체가 더 정직하다.

- 관리자 화면의 공지사항, 코드표, 설정값처럼 입력받은 값을 검증해 그대로 저장하는 CRUD.
- 리포트와 대시보드처럼 읽기만 하는 쪽. 여러 테이블을 조인한 결과를 그대로 DTO로 내보낸다. 읽기 모델을 따로 두는 생각은 [CQRS 글](/posts/cqrs)로 이어진다.
- 다른 시스템에서 받은 데이터를 변환만 해서 넘기는 연동 코드.

판단 기준은 "이 객체에 지켜야 할 불변식이 있는가"다. 주문 상태 전이, 금액 계산, 재고 차감처럼 어기면 돈이 틀리는 규칙이 있으면 객체 안에 둔다. 없으면 데이터 상자로 두고, 처리 절차는 [엔터프라이즈 패턴 글](/posts/enterprise-application-patterns)의 트랜잭션 스크립트로 쓴다. 한 시스템 안에서 둘이 섞여 있는 게 보통이다.

## 어느 객체의 일도 아닌 규칙

어떤 규칙은 한 객체에 넣기 어색하다. 계좌 A에서 B로 돈을 옮기는 규칙은 A의 일인가, B의 일인가. 장바구니 여러 상품의 배송비를 "같은 판매자 묶음별로 3만 원 이상이면 무료"로 계산하는 규칙은 어느 상품에 넣어야 하나.

이럴 때 쓰는 것이 도메인 서비스(Domain Service)다. 상태를 갖지 않고, 여러 엔티티와 값 객체를 받아 업무 규칙 하나를 수행한다. 이름은 업무의 말로 짓는다.

```ts
// 도메인 서비스: 상태가 없고, 규칙 하나를 맡는다
export class ShippingFeePolicy {
  static readonly FREE_OVER = Money.of(30000);
  static readonly FEE = Money.of(3000);

  feeFor(lines: OrderLine[]): Money {
    const bySeller = Map.groupBy(lines, (l) => l.sellerId);   // Node 21+, 최신 브라우저
    let fee = Money.of(0);
    for (const group of bySeller.values()) {
      const subtotal = group.reduce((s, l) => s.add(l.amount), Money.of(0));
      if (subtotal.amount < ShippingFeePolicy.FREE_OVER.amount) fee = fee.add(ShippingFeePolicy.FEE);
    }
    return fee;
  }
}
```

애플리케이션 서비스와 헷갈리기 쉽다. 애플리케이션 서비스(앞의 `CancelOrder`)는 트랜잭션을 열고, 리포지토리에서 객체를 꺼내고, 도메인 객체를 부르고, 저장하는 순서를 정한다. 업무 규칙은 없다. 도메인 서비스는 반대로 DB도 트랜잭션도 모르고 규칙만 안다. 애플리케이션 서비스에 `if`가 늘기 시작하면 그 규칙이 도메인 서비스나 엔티티로 가야 하는지 묻는다.

도메인 서비스를 쉽게 만들면 생기는 함정도 있다. 규칙마다 `OrderXxxService`를 만들다 보면 엔티티는 다시 빈약해지고 서비스만 늘어난다. 먼저 엔티티나 값 객체에 넣을 수 있는지 보고, 정말 여러 객체에 걸친 규칙일 때만 서비스로 뺀다.

## 일어난 일을 남기는 도메인 이벤트

주문이 취소되면 쿠폰을 되돌리고, 알림을 보내고, 정산에 알려야 한다. 이걸 `order.cancel()` 안에서 다 부르면 주문이 쿠폰, 알림, 정산을 알게 된다. 취소 서비스에서 줄줄이 부르면 취소가 일어나는 다른 경로(관리자 강제 취소, 결제 실패 자동 취소)마다 같은 호출을 복사해야 한다.

도메인 이벤트(Domain Event)는 "업무에서 의미 있는 일이 일어났다"를 과거형 객체로 남긴다. `OrderCanceled { orderId, refund, canceledAt }`. 엔티티는 일어난 일을 기록만 하고, 누가 듣는지는 모른다.

```ts
export class Order {
  #events: DomainEvent[] = [];

  cancel(now: Date) {
    if (this.#status === "SHIPPED") throw new OrderAlreadyShipped(this.id);
    this.#status = "CANCELED";
    this.#refund = this.#total.discount(this.#couponRate);
    this.#events.push({ type: "OrderCanceled", orderId: this.id, refund: this.#refund, at: now });
  }

  pullEvents() {
    const out = this.#events;
    this.#events = [];
    return out;
  }
}
```

언제 내보내느냐가 중요하다. 아래 그림에서 다음을 누르면 이벤트가 커밋 뒤에야 듣는 쪽으로 가는 흐름을 볼 수 있다.

커밋 전에 내보내면 듣는 쪽이 아직 커밋되지 않은 주문을 보거나, 롤백된 취소에 반응한다. Spring에서는 `AbstractAggregateRoot`의 `registerEvent`로 이벤트를 쌓고 리포지토리 `save` 때 발행되게 할 수 있고, 듣는 쪽에 `@TransactionalEventListener(phase = AFTER_COMMIT)`를 붙이면 커밋 뒤에 실행된다. 다만 커밋 뒤에 프로세스가 죽으면 이벤트는 사라진다. 이벤트를 잃으면 안 되는 경우(다른 서비스로 보내는 경우가 대부분)는 [트랜잭셔널 아웃박스 글](/posts/transactional-outbox)처럼 이벤트를 같은 트랜잭션에서 테이블에 적는다. 컨텍스트 경계를 넘는 이벤트를 어떻게 번역하는지는 [DDD 바운디드 컨텍스트 글](/posts/ddd-bounded-context)에 있다.

이벤트 이름은 과거형 업무 말로 짓는다. `OrderStatusChanged`처럼 넓은 이름보다 `OrderCanceled`, `OrderShipped`처럼 무슨 일이 있었는지 말하는 이름이 듣는 쪽 코드를 단순하게 만든다.

## 값 객체를 테이블에 담는 법

값 객체는 식별자가 없으니 보통 자기 테이블을 갖지 않는다. 엔티티 테이블의 컬럼 몇 개로 펼쳐 담는다. PostgreSQL 16 기준으로 쓰면 이렇다.

```sql
CREATE TABLE orders (
  id               bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  status           text   NOT NULL,
  -- Money 결제액: 금액과 통화를 함께 펼친다
  paid_amount      bigint NOT NULL CHECK (paid_amount >= 0),
  paid_currency    char(3) NOT NULL DEFAULT 'KRW',
  -- Money 환불액: 같은 값 객체를 컬럼 이름만 바꿔 한 번 더
  refund_amount    bigint NOT NULL DEFAULT 0 CHECK (refund_amount >= 0),
  refund_currency  char(3) NOT NULL DEFAULT 'KRW',
  -- Address 배송지
  ship_zipcode     text NOT NULL,
  ship_line1       text NOT NULL,
  ship_line2       text
);
```

`CHECK`로 값 객체의 생성자 규칙 일부를 DB에도 걸어 두면, 누가 SQL로 직접 고쳐도 음수 금액은 들어가지 않는다. 코드의 검사와 DB의 제약이 같은 규칙을 두 번 말하는 셈인데, 돈처럼 틀리면 비싼 값에서는 그 중복이 값을 한다.

JPA에서는 이 펼치기를 `@Embeddable`과 `@Embedded`로 한다. 같은 값 객체를 두 번 쓰면 `@AttributeOverride`로 컬럼 이름을 나눈다.

```java
@Embeddable
public record Money(long amount, String currency) {   // Hibernate 6.2부터 record를 임베디드로 쓸 수 있다
    public Money {
        if (amount < 0) throw new IllegalArgumentException("음수 금액");
    }
}

@Entity
public class Order {
    @Embedded
    @AttributeOverride(name = "amount",   column = @Column(name = "paid_amount"))
    @AttributeOverride(name = "currency", column = @Column(name = "paid_currency"))
    private Money paid;

    @Embedded
    @AttributeOverride(name = "amount",   column = @Column(name = "refund_amount"))
    @AttributeOverride(name = "currency", column = @Column(name = "refund_currency"))
    private Money refund;
}
```

값 객체가 여러 개인 경우(주문의 태그 목록, 회원의 배송지 목록)는 별도 테이블이 필요하다. JPA의 `@ElementCollection`이 그렇게 매핑하는데, 그 테이블의 행은 자기 식별자가 없어서 하나를 바꿀 때 Hibernate가 목록 전체를 지우고 다시 넣는 경우가 있다. 목록이 길고 자주 바뀐다면 그 항목은 사실 생애를 가진 엔티티가 아닌지 다시 묻는다. 값 객체를 PostgreSQL의 `jsonb` 컬럼 하나에 담는 방법도 있다. 스키마를 고치지 않고 모양을 바꿀 수 있지만, 안쪽 필드로 조건을 걸거나 제약을 걸기는 컬럼보다 어렵다.

## 모델과 코드를 함께 고친다

에반스는 이 부품들을 쓰는 전제로 모델 주도 설계(model-driven design)를 내세웠다. 업무를 이해한 모델과 실제 코드가 따로 놀면 안 되고, 코드가 곧 모델이어야 한다는 생각이다. 회의실 화이트보드에는 "주문을 취소하면 환불액이 정해진다"라고 그려 두고, 코드에서는 `OrderService.updateStatus(4)`가 환불 계산을 부른다면 모델은 이미 죽은 것이다.

그래서 이 방식에서는 모델을 그리는 사람과 코드를 쓰는 사람이 갈라지지 않는다. 업무 담당자와 이야기하다 새 개념(예: "부분 취소는 줄 단위가 아니라 금액 단위로 할 수도 있다")이 나오면 그 말이 그대로 코드의 클래스와 메서드 이름이 되고, 코드를 쓰다 어색한 데(줄마다 환불을 나누는 계산을 둘 곳이 없다)가 보이면 그게 모델을 다시 이야기할 신호가 된다. 처음 장면의 `allocate`가 그렇게 생긴 개념이다. 이런 결정이 왜 그렇게 내려졌는지 남겨 두는 방법은 [아키텍처 문서 글](/posts/architecture-docs-c4-adr)에서 다룬다.

## 면접에서 나올 만한 질문

### 엔티티와 값 객체는 어떻게 구분하나요?

엔티티는 식별자로 같음을 판단하고 상태가 바뀌어도 같은 것으로 이어진다. 값 객체는 값이 같으면 같은 것이고, 바뀌지 않게 만들어 필요하면 새로 만들어 갈아 끼운다. "같은 값의 다른 것으로 바꿔도 업무에 문제가 없나"를 물으면 대개 구분된다. 같은 주소라도 쇼핑몰에서는 값 객체, 배달 경로를 관리하는 시스템에서는 엔티티일 수 있다.

### 값 객체를 불변으로 만드는 이유는요?

여러 엔티티가 같은 값 객체를 공유해도 한쪽의 변경이 다른 쪽으로 번지지 않기 때문이다. 불변이면 생성자에서 한 번 검증한 값이 끝까지 유효하다는 보장도 생긴다. TypeScript의 `readonly`는 컴파일 때만 막으니 런타임까지 막으려면 `Object.freeze`를 함께 쓰고, 연산은 새 객체를 돌려준다.

### JavaScript에서 값 객체를 비교할 때 주의할 점은요?

`===`는 참조를 비교해서 같은 값의 두 객체도 `false`다. 그래서 `equals` 메서드를 따로 두고, `Set`이나 `Map`의 키로 쓸 때는 값을 문자열 키로 바꾼다. 돈은 부동소수점 오차를 피하려고 가장 작은 단위의 정수로 들고, 끝자리 처리 규칙을 값 객체 한 곳에만 둔다.

### 빈약한 모델은 언제 문제가 되고, 언제 괜찮나요?

지켜야 할 불변식이 있는데 객체에 setter만 있으면, 규칙을 건너뛰는 코드가 어디서든 생길 수 있어서 문제가 된다. 상태 전이나 금액 계산처럼 틀리면 돈이 틀리는 규칙은 객체 안에 둔다. 반대로 관리자 CRUD, 읽기 전용 리포트, 변환만 하는 연동 코드처럼 불변식이 없으면 데이터 객체와 트랜잭션 스크립트가 더 단순하고 정직하다.

### 도메인 서비스와 애플리케이션 서비스는 무엇이 다른가요?

애플리케이션 서비스는 트랜잭션을 열고 리포지토리에서 객체를 꺼내 도메인을 부르고 저장하는 순서만 정하고, 업무 규칙은 갖지 않는다. 도메인 서비스는 DB와 트랜잭션을 모르고, 한 객체에 넣기 어색한 여러 객체에 걸친 규칙 하나를 맡는다. 도메인 서비스를 남발하면 엔티티가 다시 빈약해지니 먼저 엔티티나 값 객체에 넣을 수 있는지 본다.

### 도메인 이벤트는 언제 발행해야 하나요?

트랜잭션이 커밋된 뒤에 발행한다. 커밋 전에 내보내면 롤백된 변경에 다른 쪽이 반응할 수 있다. 엔티티는 이벤트를 안쪽 목록에 기록만 하고, 서비스나 프레임워크가 커밋 뒤에 꺼내 보낸다. 잃으면 안 되는 이벤트는 같은 트랜잭션에서 아웃박스 테이블에 적고 따로 전달한다.

### 값 객체는 DB에 어떻게 저장하나요?

식별자가 없으니 보통 엔티티 테이블의 컬럼 여러 개로 펼친다. JPA에서는 `@Embeddable`과 `@Embedded`로 하고, 같은 값 객체를 두 번 쓰면 `@AttributeOverride`로 컬럼 이름을 나눈다. 목록이면 `@ElementCollection`으로 별도 테이블에 담지만 변경 때 목록 전체를 다시 쓰는 경우가 있어서, 자주 바뀌는 큰 목록이면 엔티티로 보는 게 맞는지 다시 판단한다.

### 엔티티의 equals를 DB가 만든 id로 구현하면 어떤 문제가 있나요?

저장하기 전에는 id가 비어 있어서, 저장 전에 `Set`에 넣은 객체의 해시값이 저장 뒤에 바뀌고 `Set`에서 찾을 수 없게 된다. 애플리케이션에서 UUIDv7 같은 id를 먼저 만들어 생성자에서 넣으면 저장 전에도 같음이 안정적이고 다른 객체가 참조할 수도 있다. 대신 키 크기와 인덱스 크기가 커지는 비용을 따진다.
