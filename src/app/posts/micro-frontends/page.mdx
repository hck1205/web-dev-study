쇼핑몰 웹 하나에 검색팀, 상품팀, 결제팀이 같이 붙어 있다고 해 보자. 검색팀이 검색창 placeholder 문구 하나를 고쳤다. 코드 변경은 한 줄인데 배포는 목요일이다. 저장소가 하나고 빌드도 하나라서, 이번 주에 들어간 결제팀 변경까지 전부 QA를 통과해야 같이 나간다. 그런데 결제 쪽 E2E 테스트가 하나 깨졌다. 검색팀의 한 줄은 다음 주로 밀린다.

팀이 셋일 때는 참을 만하다. 열 개가 넘어가면 배포 날마다 누군가의 변경이 다른 누군가에게 붙잡힌다. 마이크로 프런트엔드는 이 문제를 풀려고 나온 구조다. 화면을 팀 단위로 쪼개서 각 팀이 자기 조각을 따로 빌드하고 따로 배포하게 한다.

## 같은 배포 열차에 모두 타고 있다

하나의 큰 프런트엔드 앱(흔히 모놀리스라고 부른다)에서 팀이 늘어나면 생기는 일은 대개 비슷하다. 빌드 시간이 길어지고, 공용 코드 한 줄을 고칠 때 누가 영향을 받는지 알기 어려워지고, 무엇보다 릴리스가 묶인다. 배포를 기차에 비유하면 모든 팀이 같은 열차를 탄다. 한 칸에 문제가 생기면 열차 전체가 멈춘다.

백엔드는 이 문제를 마이크로서비스로 풀었다. 서비스마다 저장소, 배포 파이프라인, 담당 팀이 따로 있다. 그런데 사용자 눈에 보이는 웹 화면은 여전히 하나라서, 백엔드를 아무리 잘게 나눠도 프런트엔드는 한 팀이 몰아서 배포하는 병목으로 남았다. 마이크로 프런트엔드는 마이크로서비스의 생각을 화면까지 끌고 온 것이다. 2016년 무렵 ThoughtWorks Technology Radar에 이 이름이 실리면서 널리 알려졌다.

여기서 먼저 짚어 둘 것이 있다. 마이크로 프런트엔드가 푸는 문제는 기술이 아니라 조직이다. 코드를 빨리 돌리려고 쓰는 게 아니라, 여러 팀이 서로 기다리지 않고 일하게 하려고 쓴다. 그래서 팀이 하나뿐이라면 얻는 건 거의 없고 비용만 남는다. 이 얘기는 글 끝에서 다시 한다.

## 껍데기 앱과 조각 앱

마이크로 프런트엔드 구성에는 보통 두 종류의 앱이 있다. 하나는 셸(shell) 또는 호스트(host)라고 부르는 껍데기 앱이다. 공통 헤더와 레이아웃을 그리고, 지금 주소에 맞는 조각을 골라 화면에 끼운다. 나머지는 리모트(remote)라고 부르는 조각 앱이다. 검색, 상품 상세, 결제처럼 한 팀이 끝까지 책임지는 화면 단위다.

셸은 최대한 얇게 둔다. 셸에 업무 로직이 쌓이기 시작하면 모든 팀이 셸을 고치러 오고, 결국 셸이 새로운 모놀리스가 된다.

## 언제 합치느냐가 갈림길이다

조각을 나눴으면 언젠가는 다시 하나의 화면으로 합쳐야 한다. 합치는 시점과 장소에 따라 방식이 갈린다.

| 방식 | 합치는 곳 | 따로 배포 | 격리 | 걸리는 점 |
|---|---|---|---|---|
| 빌드 타임 패키지 | 셸 빌드 | 안 됨 | 약함 | 리모트가 바뀌면 셸도 다시 배포 |
| 서버·엣지 조합 | 서버, CDN | 됨 | 중간 | 페이지 간 상태 공유가 어렵다 |
| 런타임 (Module Federation) | 브라우저 | 됨 | 약함 | 의존성 버전 충돌 |
| iframe | 브라우저 | 됨 | 강함 | 높이·접근성·SEO·통신 |
| Web Components | 브라우저 | 방식에 따라 | 중간 | 프레임워크 간 props 전달 |

가장 단순한 건 빌드 타임 조합이다. 각 팀 화면을 npm 패키지로 내보내고 셸이 `package.json`에 적어서 함께 빌드한다. 코드는 깔끔하게 나뉘지만, 결제팀이 새 버전을 올려도 셸이 버전을 올리고 다시 배포해야 반영된다. 처음 문제였던 릴리스 결합이 그대로 남는다. 그래서 이 방식은 마이크로 프런트엔드라기보다 잘 나눈 모듈에 가깝다.

서버나 엣지에서 합치는 방식은 HTML 조각을 붙인다. 오래된 방법으로는 SSI(Server Side Includes)와 ESI(Edge Side Includes)가 있다. 응답 HTML에 `<esi:include src="/fragments/cart" />` 같은 태그를 넣어 두면 Varnish나 이를 지원하는 CDN이 그 자리를 다른 서버의 응답으로 채운다. 첫 화면이 완성된 HTML로 오니 SEO와 초기 로딩에 유리하다. 경로 단위로 아예 다른 앱에 보내는 것도 이 계열이다. Next.js가 안내하는 멀티 존(Multi-Zones)은 `/blog`는 이 Next.js 앱, `/shop`은 저 Next.js 앱이 맡게 하고 rewrites로 하나의 도메인처럼 묶는다. 다만 존 사이를 이동할 때는 클라이언트 라우팅이 아니라 전체 페이지 이동(hard navigation)이 일어난다.

브라우저에서 합치는 방식은 셸이 실행되는 중에 리모트 코드를 내려받아 끼운다. webpack 5가 2020년에 넣은 Module Federation이 대표적이고, single-spa처럼 리모트마다 `bootstrap`, `mount`, `unmount` 생명주기를 정해 두고 셸이 경로에 맞춰 켜고 끄는 프레임워크도 있다. 리모트를 다시 배포하면 셸을 건드리지 않아도 다음 새로고침부터 새 코드가 뜬다. 이 글에서 가장 길게 다룰 방식이다.

iframe은 가장 오래되고 가장 확실하게 격리된다. 리모트가 자기 문서, 자기 전역 변수, 자기 CSS를 따로 쓰니 서로 부딪칠 일이 없다. 대신 높이를 내용에 맞춰 늘리기 번거롭고, 포커스 이동과 스크린 리더 흐름이 끊기고, 검색 엔진이 본문을 셸의 일부로 보지 않으며, 모든 대화를 `postMessage`로 해야 한다. 외부 업체 위젯이나 결제창처럼 일부러 벽을 세워야 하는 곳에 어울린다.

Web Components는 Custom Elements로 `<checkout-cart>` 같은 태그를 만들고 Shadow DOM으로 스타일을 가둔다. 브라우저 표준이라 셸이 React든 Vue든 상관없다는 게 장점이다. 다만 React 18까지는 커스텀 요소에 객체나 함수 props를 넘기기 어려웠고, React 19에 와서야 속성(property)으로 넘기는 지원이 들어갔다. 보통은 Web Components를 단독으로 쓰기보다 런타임 로딩과 묶어서 리모트의 겉포장으로 쓴다.

## 런타임에 리모트를 불러오는 과정

Module Federation에서 리모트는 빌드할 때 `remoteEntry.js`라는 작은 진입 파일을 함께 만든다. 이 파일은 "나는 이런 모듈을 내보내고, 이런 공유 라이브러리가 필요하다"는 목록이다. 실제 화면 코드는 해시가 붙은 별도 청크로 나뉘어 있다가 필요할 때만 내려온다.

3번과 6번의 캐시 정책 차이를 눈여겨볼 만하다. 진입 파일은 "지금 최신이 무엇인지"를 알려 주는 포인터라서 매번 확인해야 하고, 실제 청크는 내용이 바뀌면 이름이 바뀌니 영원히 캐시해도 된다. 진입 파일을 1년짜리로 캐시해 두면 결제팀이 배포를 해도 사용자는 옛 결제 화면을 계속 보게 된다. 실무에서 꽤 흔한 실수다.

Module Federation 2.0(`@module-federation/enhanced`)부터는 `remoteEntry.js` 대신 `mf-manifest.json`이라는 JSON 목록을 쓸 수 있다. 셸이 이 목록을 보고 필요한 청크를 미리 받아 두거나, 리모트의 타입 정의를 받아 와서 셸 쪽 TypeScript가 리모트 컴포넌트의 props를 검사하게 할 수 있다. 같은 개념이 Rspack과 Vite 플러그인으로도 나와 있어서 webpack 전용 기술은 아니게 됐다.

## React가 두 개 뜨면 생기는 일

마이크로 프런트엔드에서 가장 골치 아픈 문제는 의존성 버전이다. 팀마다 따로 배포한다는 건 팀마다 따로 라이브러리 버전을 올린다는 뜻이기도 하다. 결제팀은 React 18.2를 쓰고, 상품팀은 18.3으로 올렸고, 오래된 리모트 하나는 아직 17에 머물러 있다. 이 상태를 버전 스큐(version skew)라고 부른다. 같은 시스템 안에서 버전이 서로 어긋나 있다는 뜻이다.

대부분의 라이브러리는 사본이 두 개 떠도 번들이 무거워질 뿐 동작은 한다. React는 다르다. 훅은 지금 렌더링 중인 컴포넌트 정보를 React 모듈 안의 전역 상태에서 꺼내 쓴다. 리모트가 자기 React 사본의 `useState`를 부르는데 실제 렌더링은 셸의 `react-dom`이 하고 있으면, 리모트 쪽 React는 "지금 렌더링 중인 컴포넌트가 없다"고 판단한다. 그 결과가 `Invalid hook call` 에러다. Context도 사본마다 따로라서, 셸이 내려 준 테마나 로그인 정보가 리모트에서 비어 보인다.

## 주소창은 셸이 쥔다

라우터가 여러 개 있으면 서로 주소창을 차지하려고 싸운다. 셸 라우터가 `/checkout/cart`로 바꿨는데 결제 리모트의 라우터가 자기 기준으로 `/cart`를 다시 써 버리는 식이다.

보통은 두 단계로 나눈다. 최상위 경로 접두사(`/checkout/*`)는 셸이 정하고, 그 아래(`/cart`, `/payment`)는 리모트가 정한다. 리모트에는 `basename="/checkout"`을 넘겨서 자기가 어디에 붙어 있는지 알려 준다. 브라우저 history 객체는 하나만 쓰고, 리모트가 독자적으로 `window.history`를 갈아 끼우지 않게 한다.

리모트 사이를 오가는 링크도 주의한다. 검색 화면에서 상품으로 가는 링크를 리모트 안에서 `<a href>`로 그리면 전체 페이지가 다시 로드된다. 셸이 내비게이션 함수를 내려 주고 리모트는 그걸 불러서 이동해야 클라이언트 라우팅으로 부드럽게 넘어간다. 앞에서 본 멀티 존처럼 앱이 아예 다르면 이 경계에서 전체 이동을 받아들이는 것도 선택지다.

## 버튼이 팀마다 달라 보이지 않게

팀이 화면을 따로 만들면 사용자 눈에는 버튼 모양, 여백, 글자 크기가 조금씩 다른 사이트가 된다. 그래서 거의 모든 마이크로 프런트엔드 구성에 공용 디자인 시스템이 따라온다.

디자인 시스템을 npm 패키지로 나눠 주면 다시 버전 스큐가 생긴다. 검색은 디자인 시스템 3.2를, 결제는 2.8을 쓰면 같은 화면 안에서 버튼 두 종류가 나란히 보인다. 이걸 줄이는 방법이 몇 가지 있다. 색, 간격, 글꼴 같은 디자인 토큰은 셸이 CSS 변수로 한 번만 내려 주고 컴포넌트는 그 변수를 참조하게 한다. 그러면 버튼 컴포넌트 버전이 달라도 색은 같이 바뀐다. 컴포넌트 자체는 리모트마다 번들에 넣되, 메이저 버전 간격을 하나 이내로 유지하는 규칙을 둔다.

CSS 충돌도 신경 써야 한다. 리모트 하나가 전역에 `button { padding: 0 }`을 넣으면 셸과 다른 리모트의 버튼까지 같이 바뀐다. CSS Modules나 CSS-in-JS처럼 클래스 이름을 자동으로 고유하게 만드는 방식을 쓰거나, 리모트별 접두사를 붙이거나, Shadow DOM으로 가둔다. 전역 리셋 CSS는 셸만 넣는다.

## 앱끼리 말을 거는 방법

결제 리모트가 장바구니에 상품을 담으면 셸 헤더의 장바구니 숫자가 바뀌어야 한다. 이때 가장 쉬운 방법은 셸의 전역 스토어를 리모트에 넘겨 리모트가 직접 고치게 하는 것이다. 그리고 그게 가장 피해야 할 방법이다. 스토어 모양이 팀 사이의 숨은 계약이 되어서, 셸이 스토어 구조를 바꾸는 순간 아무도 모르게 리모트가 깨진다.

대신 결합이 느슨한 순서로 고른다. 먼저 URL이다. 검색어, 필터, 선택한 상품 id처럼 주소에 담을 수 있는 상태는 주소에 담는다. 새로고침과 공유에도 살아남고 누구나 읽을 수 있다. 다음은 브라우저 이벤트다.

```ts
// 결제 리모트
window.dispatchEvent(
  new CustomEvent("cart:updated", { detail: { count: 3 } }),
);

// 셸 헤더
window.addEventListener("cart:updated", (e) => {
  setCount((e as CustomEvent<{ count: number }>).detail.count);
});
```

이벤트 이름과 `detail` 모양이 공개 계약이 된다. 계약이 작고 눈에 보이니 바꿀 때 누가 영향을 받는지 찾기 쉽다. 그래도 바꿔야 한다면 `cart:updated:v2`처럼 새 이름을 만들고 옛 이벤트를 한동안 같이 보낸다. 셸에서 리모트로는 props로 내려 준다. 로그인 사용자 정보처럼 정말로 모두가 알아야 하는 것만, 작은 인터페이스로 넘긴다.

## 따로 배포하면 따로 되돌린다

리모트를 따로 배포하는 흐름은 이렇게 된다. 결제팀이 빌드하면 `remoteEntry.js`와 청크들이 `https://checkout.cdn.example.com/v142/` 같은 버전 경로에 올라간다. 옛 버전 파일은 지우지 않는다. 그다음 설정 서버(또는 CDN의 고정 경로)가 가리키는 결제 리모트 주소를 `v142`로 바꾼다. 셸은 시작할 때 이 설정을 읽어서 리모트 주소를 정한다.

이 구조에서 롤백은 포인터를 `v141`로 되돌리는 일이다. 빌드도 배포도 다시 할 필요가 없다. 옛 파일을 지우지 않는 이유도 여기에 있다. 사용자가 탭을 열어 둔 채로 배포가 일어나면, 그 탭은 아직 옛 진입 파일을 들고 있다가 옛 청크를 요청한다. 옛 파일이 지워져 있으면 그 순간 `ChunkLoadError`가 난다. 버전마다 경로를 나누고 일정 기간 보관하면 이 문제도 같이 피한다.

독립 배포에는 그만큼의 책임이 따른다. 결제팀이 `./Cart`의 props 이름을 바꿔서 배포하면 셸은 다음 새로고침부터 깨진다. 모놀리스였다면 타입 검사에서 걸렸을 일이 런타임에야 드러난다. 그래서 다음 장치를 둔다.

- `exposes`의 props와 이벤트 계약을 타입 패키지나 Module Federation 2.0의 타입 공유로 셸에 전달한다.
- 계약 테스트(contract test)로 "셸이 기대하는 모양"을 리모트 CI에서 검사한다.
- 리모트 하나가 로드에 실패하거나 렌더링 중 에러를 던져도 페이지 전체가 하얘지지 않게 셸이 리모트마다 Error Boundary와 대체 화면을 둔다.

마지막 항목은 장애 격리 측면에서 마이크로 프런트엔드의 장점이 되기도 한다. 추천 영역 리모트가 죽어도 상품 상세와 결제는 계속 동작하게 만들 수 있다. 셸이 그렇게 설계됐을 때만 그렇다.

## 배포 다음 날 결제 영역만 비어 있을 때

리모트를 따로 배포하기 시작하면 장애도 리모트 단위로 온다. 셸은 멀쩡한데 한 영역만 옛 버전이거나 비어 있다. 자주 만나는 세 장면을 로컬에서 재현해 봤다. 리모트 파일은 nginx로, 셸과 리모트 페이지는 Node 서버로 띄우고 크롬 141에서 열었다.

결제팀이 배포했는데 일부 사용자에게 옛 결제 화면이 보인다면 진입 파일의 캐시 헤더부터 본다. 브라우저가 무엇을 받는지는 `curl`로 헤더만 받아 보면 안다.

```bash
# 진입 파일과 해시 청크의 캐시 헤더를 비교한다
curl -sI https://checkout.cdn.example.com/v142/remoteEntry.js | grep -i -E '^HTTP|cache-control|etag'
curl -sI https://checkout.cdn.example.com/v142/cart.8f3a.js | grep -i -E '^HTTP|cache-control'
```

로컬 nginx에 진입 파일은 `no-cache`, 나머지는 1년 `immutable`로 설정하고 같은 명령을 돌린 결과다. 재검증이 실제로 되는지도 `If-None-Match`로 확인했다.

```text
HTTP/1.1 200 OK
ETag: "6ad4ab36-11"
Cache-Control: no-cache
---
HTTP/1.1 200 OK
Cache-Control: public, max-age=31536000, immutable
---
# If-None-Match: "6ad4ab36-11" 를 붙여 다시 요청
HTTP/1.1 304 Not Modified
ETag: "6ad4ab36-11"
```

진입 파일에 `max-age=31536000`이 보이면 그게 원인이다. CDN이나 버킷의 기본 규칙이 `.js`를 모두 길게 캐시하게 되어 있는 경우가 많아서, 진입 파일만 따로 규칙을 빼 줘야 한다. 이미 1년짜리로 나간 사용자는 헤더를 고쳐도 브라우저 캐시가 만료될 때까지 옛 파일을 쓴다. 그래서 셸이 진입 파일 주소에 `?v=142`처럼 배포 번호를 붙이거나, 앞에서 본 것처럼 버전 경로를 설정 서버에서 받아 오게 해 두면 이런 사고에서 빠져나올 길이 생긴다.

두 번째 장면은 리모트를 다른 도메인의 CDN으로 옮긴 뒤 그 영역이 비어 버리는 경우다. 콘솔에는 이렇게 남는다. 셸(`localhost:8022`)이 다른 출처(`127.0.0.1:8023`)의 ES 모듈 리모트를 `import()`로 불렀고, 리모트 서버는 CORS 헤더를 주지 않았다.

```text
[console.error] Access to script at 'http://127.0.0.1:8023/remoteEntry.js' from origin 'http://localhost:8022' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.
[console.error] Failed to load resource: net::ERR_FAILED
[catch] TypeError: Failed to fetch dynamically imported module: http://127.0.0.1:8023/remoteEntry.js
```

ES 모듈 스크립트와 `fetch`로 읽는 `mf-manifest.json`은 다른 출처라면 CORS 검사를 받는다. webpack의 기본 방식처럼 진입 파일을 평범한 `<script>` 태그로 넣으면 검사를 받지 않지만, `output.crossOriginLoading`을 켜거나 Vite 계열 플러그인처럼 ES 모듈로 리모트를 내보내면 똑같이 막힌다. 리모트 CDN이 셸의 출처를 `Access-Control-Allow-Origin`으로 돌려주게 설정한다. 스테이징은 셸과 리모트가 같은 도메인 아래에 있고 운영만 도메인이 갈리는 구성이라면, 이 에러는 운영에서 처음 보게 된다.

세 번째는 리모트 영역만 대체 화면으로 바뀌고 콘솔에 이런 줄이 찍히는 경우다. 셸과 리모트를 각자 React를 넣어 번들하고, 리모트 컴포넌트를 셸의 `react-dom`으로 그렸다.

```text
# 프로덕션 빌드
TypeError: Cannot read properties of null (reading 'useState')
    at exports.useState (http://localhost:8022/remote-production.js:453:39)
    at Cart (http://localhost:8022/remote-production.js:527:43)
    at renderWithHooks (http://localhost:8022/host-production.js:4165:27)

# 개발 빌드
Invalid hook call. Hooks can only be called inside of the body of a function component. This could happen for one of the following reasons:
1. You might have mismatching versions of React and the renderer (such as React DOM)
2. You might be breaking the Rules of Hooks
3. You might have more than one copy of React in the same app
```

앞에서 말한 "React가 두 개 뜨면 생기는 일"이 실제로는 이렇게 보인다. 프로덕션 메시지에는 "React가 두 개"라는 말이 없어서 처음 보면 리모트 코드의 버그로 착각하기 쉽다. 스택을 보면 `useState`는 `remote-production.js` 안의 React에서, 렌더링은 `host-production.js`의 `renderWithHooks`에서 불렸다. 파일이 갈린다는 게 사본이 둘이라는 증거다. 확인은 번들 분석기로 리모트 번들 안에 `react`가 들어 있는지, Network 탭에서 react가 든 청크가 두 번 내려왔는지 보는 것이다. 리모트의 `shared` 설정에서 `react`가 빠졌거나 `singleton`이 아닌 경우가 대부분이다.

이번 재현에서 페이지 전체가 하얘지지 않고 "결제 영역을 불러오지 못했다"만 보인 건 셸이 리모트를 Error Boundary로 감싸 두었기 때문이다. 앞 절에서 리모트마다 경계를 두라고 한 이유가 이 장면이다. 경계에서 잡은 에러를 리모트 이름과 버전을 붙여 수집하면, 어느 팀의 몇 번 배포에서 시작됐는지가 바로 나온다.

## 쪼갠 만큼 무거워진다

사용자 입장에서 마이크로 프런트엔드는 공짜가 아니다. 대표적인 비용이 셋 있다.

첫째, 중복 번들이다. 공유 설정에 빠진 라이브러리는 리모트마다 하나씩 들어간다. 날짜 라이브러리, 폼 라이브러리, 아이콘 세트가 리모트 세 개에 각각 들어 있으면 사용자는 같은 코드를 세 번 받는다. 그렇다고 전부 shared에 넣으면 셸이 쓰지도 않는 라이브러리 협상 비용과 버전 결합이 늘어난다. 리모트별 번들 분석 결과를 같이 보면서 무엇을 공유할지 정기적으로 정리해야 한다.

둘째, 요청 폭포(waterfall)다. 셸 번들 → 진입 파일 → 리모트 청크 → 리모트가 부르는 API 순서로 요청이 줄줄이 이어진다. 앞 요청이 끝나야 다음 요청의 주소를 알 수 있기 때문이다. 자주 가는 경로의 진입 파일은 HTML에 `<link rel="preload">`로 미리 걸어 두거나, 매니페스트를 보고 셸이 다음 화면의 청크를 미리 받게 해서 줄인다.

셋째, 렌더링 전략이 제한된다. 브라우저에서 합치는 방식은 리모트 코드가 내려와야 화면이 그려지니, 서버 렌더링을 하려면 서버 쪽에서도 같은 조합을 해야 한다. 이건 브라우저 쪽보다 훨씬 복잡하다. 첫 화면 속도와 검색 노출이 중요한 페이지라면 서버·엣지 조합이나 멀티 존을 먼저 검토한다.

## 대부분은 모노레포로 충분하다

여기까지 읽으면 비용이 꽤 많다는 게 보인다. 공유 의존성 관리, 계약 테스트, 배포 포인터, 중복 번들, 라우터 조율. 이 비용을 감당할 만큼 팀이 많고, 팀마다 배포 주기가 달라야 할 이유가 있을 때 마이크로 프런트엔드가 값을 한다.

그 전 단계로 먼저 해 볼 것이 있다. 하나의 저장소(모노레포) 안에서 업무 영역별로 패키지를 나누고, 경계를 도구로 강제하는 것이다. Nx나 Turborepo 같은 도구는 바뀐 패키지와 그 패키지에 의존하는 것만 다시 빌드하고 테스트한다. 린트 규칙으로 "검색 패키지는 결제 패키지 내부를 import할 수 없다"를 막고, CODEOWNERS로 리뷰 책임을 나눈다. 이렇게 하면 팀 경계와 빌드 속도 문제의 상당 부분이 풀린다. 남는 건 릴리스 결합 하나다.

그 하나가 정말 아플 때, 예를 들어 배포 대기 때문에 실험과 수정이 몇 주씩 밀리는 상황이 반복될 때 리모트로 떼어 낸다. 처음부터 전부 쪼개지 않고, 가장 자주 바뀌고 다른 화면과 엮임이 적은 영역 하나부터 떼어 보면 비용이 실제로 얼마인지 알 수 있다. 모듈 경계가 이미 잘 그어져 있다면 떼어 내는 작업도 훨씬 수월하다.

## 다시 목요일 배포로

처음 장면에서 검색팀의 한 줄이 밀린 이유는 코드가 아니라 배포 단위가 하나였기 때문이다. 마이크로 프런트엔드는 셸이 주소를 보고 팀별 리모트를 끼우는 구조로 그 단위를 나눈다. 대가로 공유 의존성의 버전, 팀 사이의 계약, 번들 중복, 런타임 실패를 관리해야 한다. 그래서 순서가 있다. 먼저 모노레포 안에서 경계를 긋고, 릴리스 결합이 정말 병목일 때 그 경계를 따라 떼어 낸다. Module Federation의 공유 스코프와 리모트 장애는 [Module Federation 깊게 보기](/posts/module-federation-deep-dive)에서, 나머지 조합 방식을 직접 만들어 본 결과는 [조합 방식 직접 만들어 보기](/posts/micro-frontend-integration-patterns)에서 이어 간다.

## 면접에서 나올 만한 질문

### 마이크로 프런트엔드는 무엇이고 왜 쓰나요?

하나의 웹 앱을 업무 영역별로 나눠 각 팀이 자기 조각을 따로 개발하고 배포하게 하는 구조다. 기술 문제보다는 조직 문제를 푼다. 팀이 많은 큰 앱에서 모든 변경이 같은 빌드, 같은 배포에 묶여 서로를 기다리는 릴리스 결합을 끊는 게 목적이다. 팀이 적다면 얻는 것보다 운영 비용이 크다.

### 화면을 합치는 방식에는 무엇이 있고 어떻게 고르나요?

빌드 타임 패키지, 서버·엣지 조합(SSI, ESI, 경로별 분리), 브라우저 런타임 조합(Module Federation, single-spa), iframe, Web Components가 있다. 빌드 타임은 단순하지만 셸 재배포가 필요해서 독립 배포가 안 된다. 첫 화면 속도와 SEO가 중요하면 서버·엣지 조합을, 한 페이지 안에서 여러 팀 화면을 자연스럽게 섞어야 하면 런타임 조합을, 강한 격리가 필요한 외부 위젯이면 iframe을 고른다.

### Module Federation은 어떻게 동작하나요?

리모트는 빌드할 때 내보낼 모듈과 공유 의존성 정보를 담은 `remoteEntry.js`를 만든다. 셸은 실행 중에 이 파일을 받아 공유 스코프에서 의존성 버전을 맞춘 뒤, 실제로 import할 때 해당 청크를 내려받아 렌더링한다. 진입 파일은 최신 버전을 가리키는 포인터라 짧게 캐시하고, 해시가 붙은 청크는 길게 캐시한다.

### 리모트마다 React 버전이 다르면 어떻게 되나요?

React는 훅과 Context가 모듈 내부 전역 상태에 의존해서, 사본이 둘 뜨면 `Invalid hook call` 에러가 나거나 Context가 전달되지 않는다. 그래서 `singleton: true`로 하나만 띄우고 `requiredVersion`으로 범위를 선언한다. 범위가 맞지 않으면 기본은 경고만 내고 진행하니 `strictVersion`으로 에러를 내게 할 수 있다. 근본적으로는 셸이 메이저 버전을 정하고 리모트가 그 범위 안에서 움직이는 규칙으로 관리한다.

### 리모트끼리는 어떻게 통신하나요?

가능하면 URL에 상태를 담고, 그다음은 `CustomEvent` 같은 브라우저 이벤트로 느슨하게 주고받는다. 셸에서 리모트로는 작은 props 인터페이스로 내려 준다. 전역 스토어를 공유하면 스토어 구조가 숨은 계약이 되어 한쪽 변경이 다른 팀을 조용히 깨뜨리므로 피한다. 이벤트 이름과 payload도 공개 API처럼 버전을 관리한다.

### 리모트를 독립 배포할 때 생기는 문제와 대처법은요?

계약이 런타임에야 검증된다는 게 가장 크다. 타입 공유와 계약 테스트로 셸이 기대하는 모양을 리모트 CI에서 검사한다. 배포 결과물은 버전 경로에 쌓아 두고 설정의 포인터만 바꾸면 롤백이 빌드 없이 끝나고, 열려 있던 탭이 옛 청크를 요청해도 `ChunkLoadError`가 나지 않는다. 셸은 리모트마다 Error Boundary를 둬서 한 조각의 실패가 페이지 전체로 번지지 않게 한다.

### 성능 측면의 비용은 무엇인가요?

공유하지 않은 라이브러리가 리모트마다 중복으로 들어가는 번들 비용, 셸 → 진입 파일 → 청크 → API로 이어지는 요청 폭포, 서버 렌더링이 어려워지는 문제가 있다. 공유 목록을 번들 분석으로 정리하고, 자주 가는 경로는 진입 파일을 preload하거나 매니페스트로 청크를 미리 받는다. 첫 화면이 중요한 페이지는 서버·엣지 조합을 검토한다.

### 마이크로 프런트엔드를 도입하지 않는 게 나은 경우는요?

팀이 적거나, 팀 경계가 업무 영역으로 나뉘지 않았거나, 배포 대기가 실제 병목이 아닌 경우다. 이럴 때는 모노레포에서 영역별 패키지를 나누고 린트 규칙과 CODEOWNERS로 경계를 강제하고, 바뀐 것만 빌드하는 도구로 속도를 확보하는 편이 싸다. 그렇게 경계를 그어 두면 나중에 정말 필요할 때 한 영역씩 리모트로 떼어 내기도 쉽다.
