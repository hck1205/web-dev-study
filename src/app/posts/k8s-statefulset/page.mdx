<EasyIntro>
  Deployment는 Pod를 언제든 바꿔 끼울 수 있는 소모품으로 다룬다. 이름이 매번 바뀌고 어느 Pod가 요청을 받을지도 정해져 있지 않다. 그런데 데이터베이스처럼 누가 대장인지 정해야 하고 각자 자기 디스크를 붙여야 하는 앱에서는 그 방식이 그대로 문제가 된다.

  StatefulSet은 Pod에 0번, 1번처럼 번호를 붙이고 그 번호로 세 가지를 고정한다. 이름, 그 이름으로 찾아가는 주소, 그리고 그 번호에만 따라다니는 디스크다. 학교에서 번호마다 사물함이 정해져 있어서 자리를 옮겨도 자기 사물함을 다시 쓰는 것과 같다. 만들고 줄이고 바꾸는 순서도 번호로 정해져서, 하나가 준비돼야 다음을 만들고 줄일 때는 큰 번호부터 뺀다.

  이걸 알면 줄였다가 늘려도 데이터가 돌아오는 이유와, 업데이트가 한 대씩만 진행되고 중간에 멈추면 사람이 손봐야 하는 이유가 보인다. 다만 StatefulSet은 이름과 디스크와 순서까지만 주고, 복제와 백업 같은 운영은 해 주지 않는다.
</EasyIntro>

PostgreSQL 세 대를 Deployment로 띄우면 처음엔 잘 도는 것 같다. 그런데 복제를 붙이려는 순간 막힌다. 복제본은 "primary가 누구인지"를 설정에 적어야 하는데, Pod 이름은 `pg-7d599ff9fb-x2k8q`처럼 매번 바뀌고, Service 뒤에서는 세 대 중 아무나 받는다. PVC를 하나 적으면 세 Pod가 같은 디스크를 나눠 쓰려다 두 대는 붙지도 못한다. Pod를 가축처럼 다루는 Deployment의 방식이 여기서는 그대로 문제가 된다.

StatefulSet은 이 셋을 고정해 준다. Pod 이름(`pg-0`, `pg-1`), 그 이름으로 찾아가는 DNS 주소, Pod마다 따로 붙는 디스크. 이 글은 그 세 가지가 어떻게 만들어지고, 띄우고 줄이고 업데이트할 때 순서가 어떻게 정해지는지, 줄인 뒤 남는 PVC와 멈춰 버린 롤아웃을 어떻게 다루는지를 실습 클러스터의 실제 출력으로 따라간다. 출력은 kwok로 띄운 Kubernetes 1.34.1 클러스터에서 받았다. API 서버와 컨트롤러, 스케줄러는 진짜이고 컨테이너가 실제로 돌지는 않는다. DNS 답은 같은 API 서버에 CoreDNS 1.11.3을 붙여 받았다.

Deployment가 ReplicaSet으로 Pod 수를 맞추는 원리는 [Deployment 글](/posts/k8s-deployment)에, PVC가 PV에 묶이는 규칙은 [PV와 PVC 글](/posts/k8s-pv-pvc)에 있다. 이 글은 그 위에서 StatefulSet이 더하는 것만 본다.

## 이름이 바뀌면 안 되는 앱

StatefulSet이 약속하는 것은 네 가지다. Pod 이름이 `이름-번호`로 정해지고, 그 이름에 DNS 주소가 붙고, 번호마다 PVC가 하나씩 따라다니고, 만들고 지우고 바꾸는 순서가 번호로 정해진다. Pod가 죽어서 다른 노드에 다시 떠도 `pg-1`은 `pg-1`이고, 같은 `data-pg-1` 디스크를 다시 붙인다.

대신 Deployment가 주던 편함 몇 가지를 내준다. 업데이트할 때 새 Pod를 먼저 띄우는 maxSurge가 없다. 같은 이름의 Pod가 두 개 있으면 안 되니, 옛 `pg-2`가 완전히 지워져야 새 `pg-2`가 생긴다. 그래서 StatefulSet의 롤링 업데이트는 언제나 한 대씩 잠깐 빠지는 방식이다.

## 매니페스트에서 다른 세 줄

Deployment와 거의 같고 세 군데가 다르다. `serviceName`, `volumeClaimTemplates`, 그리고 짝이 되는 headless Service다.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: pg
  namespace: data
spec:
  clusterIP: None          # headless: VIP 없이 Pod마다 DNS 이름
  selector: {app: pg}
  ports:
  - name: postgres
    port: 5432
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: pg
  namespace: data
spec:
  serviceName: pg          # 위 Service 이름. Pod DNS 이름의 가운데 칸이 된다
  replicas: 3
  selector:
    matchLabels: {app: pg}
  template:
    metadata:
      labels: {app: pg}
    spec:
      terminationGracePeriodSeconds: 10
      containers:
      - name: postgres
        image: postgres:16.4
        ports:
        - {name: postgres, containerPort: 5432}
        volumeMounts:
        - {name: data, mountPath: /var/lib/postgresql/data}
  volumeClaimTemplates:    # 번호마다 이 틀로 PVC를 하나씩 만든다
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: local-ssd
      resources:
        requests: {storage: 10Gi}
```

실습 클러스터에는 동적 프로비저너가 없어서 `local-ssd` 클래스의 PV 여섯 개를 미리 만들어 두었다. 실제 클러스터라면 StorageClass가 PVC마다 디스크를 만들어 준다. StorageClass와 스냅숏은 [StorageClass 글](/posts/k8s-storageclass-snapshots)에서 다룬다.

`serviceName`에 적은 Service는 StatefulSet이 만들어 주지 않는다. 직접 만들어야 하고, 없으면 Pod는 잘 뜨는데 DNS 이름만 안 생긴다. 흔한 실수다.

`statefulset.kubernetes.io/pod-name` 라벨은 Pod 하나만 고르는 Service를 만들 때 쓴다. 예를 들어 `pg-0`만 바라보는 `pg-primary` Service의 selector에 이 라벨을 넣으면 쓰기 연결을 한 곳으로 모을 수 있다. `apps.kubernetes.io/pod-index`(1.32부터 정식)는 앱이 환경 변수로 자기 번호를 받을 때 편하다. 다만 "0번이 primary"라는 규칙은 처음 띄울 때만 맞는다. 장애 조치로 primary가 바뀐 뒤에도 0번에 쓰기를 보내면 안 되니, 실제 운영에서는 오퍼레이터가 역할 라벨을 따로 붙인다.

```bash

# EndpointSlice에 hostname이 함께 올라간다
kubectl -n data get endpointslices -o yaml | grep -E 'hostname|- 10\.'
```

CoreDNS는 이 EndpointSlice를 읽고 답한다. 세 가지 이름으로 물어봤다.

```bash
# Service 이름: ready인 Pod IP 전부
dig pg.data.svc.cluster.local +noall +answer
# Pod 이름: 그 Pod 하나
dig pg-1.pg.data.svc.cluster.local +noall +answer
# SRV: 포트 이름 postgres로 묻는다
dig _postgres._tcp.pg.data.svc.cluster.local SRV +noall +answer
```

```bash
kubectl -n data get pod pg-1 -o wide
kubectl -n data get pod pg-1 -o jsonpath='{.spec.volumes[0].persistentVolumeClaim.claimName}{"\n"}'
```


이름과 PVC는 같다. IP는 kwok가 같은 노드에 같은 IP를 다시 줘서 그대로 나왔지만, 실제 CNI에서는 새 Pod가 새 IP를 받는 경우가 많다. 고정되는 것은 이름이지 IP가 아니다.

여기서 현장 문제가 하나 나온다. DNS 답의 TTL은 5초인데(CoreDNS `kubernetes` 플러그인 기본값), 클라이언트가 처음 받은 IP를 오래 들고 있으면 Pod가 다시 뜬 뒤에도 옛 IP로 붙으려 한다. JVM의 DNS 캐시, 연결 풀이 처음 해석한 주소를 계속 쓰는 드라이버가 대표다. "DB Pod가 재시작된 뒤 일부 앱만 계속 연결 시간 초과가 난다"면 앱 쪽 DNS 캐시와 풀의 재연결 설정을 본다. 클러스터 DNS가 답을 만드는 과정은 [CoreDNS 글](/posts/k8s-coredns)에 있다.

### 남길지 지울지 정하는 persistentVolumeClaimRetentionPolicy

이 기본 동작을 바꾸는 필드가 `persistentVolumeClaimRetentionPolicy`다(1.27 베타로 기본 켜짐, 1.32부터 정식). `whenDeleted`는 StatefulSet을 지울 때, `whenScaled`는 줄일 때 PVC를 어떻게 할지 정한다. 둘 다 기본은 `Retain`이다. 캐시처럼 다시 만들어도 되는 데이터라면 `whenScaled: Delete`로 디스크 비용을 아낄 수 있다.

```bash
# 줄일 때 PVC를 지우게 바꾼다
kubectl -n data patch sts pg --type merge \
  -p '{"spec":{"persistentVolumeClaimRetentionPolicy":{"whenDeleted":"Retain","whenScaled":"Delete"}}}'
# 3 → 2로 줄이고, 지워질 PVC의 주인이 누구로 바뀌는지 본다
kubectl -n data scale sts pg --replicas=2
kubectl -n data get pvc data-pg-2 -o jsonpath='{range .metadata.ownerReferences[*]}{.kind}/{.name}{"\n"}{end}'
```

```text
statefulset.apps/pg patched
statefulset.apps/pg scaled
Pod/pg-2
```

컨트롤러가 직접 PVC를 지우는 게 아니다. 사라질 Pod를 PVC의 주인(ownerReference)으로 적어 두고, Pod가 지워지면 가비지 컬렉터가 PVC를 따라 지운다. 20초 뒤 상태다.

```bash
# PVC와 그 아래 PV가 어떻게 됐나
kubectl -n data get pvc
kubectl get pv pv-local-4
```

```text
NAME        STATUS   VOLUME       CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
data-pg-0   Bound    pv-local-1   10Gi       RWO            local-ssd      <unset>                 3m24s
data-pg-1   Bound    pv-local-2   10Gi       RWO            local-ssd      <unset>                 3m16s
NAME         CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS     CLAIM            STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
pv-local-4   10Gi       RWO            Retain           Released   data/data-pg-2   local-ssd      <unset>                          3m25s
```

PVC는 지워졌고, PV는 회수 정책이 `Retain`이라 `Released`로 남았다. 이제 다시 3으로 올리면 어떻게 될까.

```bash
# 다시 늘리고 새 data-pg-2가 어느 PV에 묶였나 본다
kubectl -n data scale sts pg --replicas=3
kubectl -n data get pvc data-pg-2
```

```text
NAME        STATUS   VOLUME       CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
data-pg-2   Bound    pv-local-3   10Gi       RWO            local-ssd      <unset>                 15s
```

같은 이름의 PVC가 새로 생겼지만 옛 디스크(`pv-local-4`)가 아니라 빈 디스크(`pv-local-3`)에 묶였다. `Released` PV는 옛 PVC의 기록(`claimRef`)을 들고 있어서 새 PVC가 가져가지 못한다. `pg-2`는 빈 디스크로 시작한다. DB라면 복제본 하나가 처음부터 다시 데이터를 받아야 한다는 뜻이다.

<Callout kind="warning" title="whenScaled: Delete는 줄이는 순간 데이터를 버린다">
DB, 메시지 브로커처럼 복제본마다 데이터를 들고 있는 StatefulSet에는 기본값 Retain을 쓴다. HPA나 자동화가 replicas를 건드리는 StatefulSet에 Delete를 걸면 잠깐 줄였다 늘리는 것만으로 복제본 데이터가 사라진다. 잘못 지웠다면 PV의 회수 정책이 Retain인지부터 본다. Retain이면 `kubectl patch pv <이름> --type json -p '[{"op":"remove","path":"/spec/claimRef"}]'`로 claimRef를 비우고, 새 PVC의 `volumeName`에 그 PV를 적어 다시 묶을 수 있다. Delete였다면 스냅숏이나 백업에서 되살리는 수밖에 없다.
</Callout>

## 업데이트는 큰 번호부터 하나씩, partition으로 끊어서

롤링 업데이트는 줄일 때와 같은 순서다. 가장 큰 번호를 지우고, 새 템플릿으로 다시 띄우고, 그 Pod가 Running·Ready가 되면 다음 번호로 내려간다. `partition`을 주면 그 번호 이상만 바꾼다. 카나리처럼 한 대만 먼저 새 버전으로 돌려 볼 때 쓴다.

```bash
# partition=2: 번호 2 이상만 새 버전으로

  -p '{"spec":{"updateStrategy":{"type":"RollingUpdate","rollingUpdate":{"partition":2}}}}'
kubectl -n data set image sts/pg postgres=postgres:16.6
kubectl -n data get pods -L controller-revision-hash
kubectl -n data rollout status sts/pg
```

```bash
kubectl -n data rollout undo sts/pg
kubectl -n data get pods -L controller-revision-hash
kubectl -n data get sts pg -o jsonpath='{.status.currentRevision} {.status.updateRevision}{"\n"}'
```

```text
statefulset.apps/pg rolled back
NAME   READY   STATUS    RESTARTS   AGE    CONTROLLER-REVISION-HASH
pg-0   1/1     Running   0          96s    pg-dfd9fc4d8
pg-1   1/1     Running   0          112s   pg-dfd9fc4d8
pg-2   0/1     Pending   0          73s    pg-7f985b4887
pg-dfd9fc4d8 pg-dfd9fc4d8
```

40초가 지나도 `pg-2`는 깨진 리비전 그대로 Pending이다. 템플릿은 되돌아갔는데(update 리비전이 다시 `pg-dfd9fc4d8`) 컨트롤러는 `pg-2`가 Ready가 되기를 계속 기다린다. 공식 문서도 OrderedReady에서 이렇게 멈출 수 있다고 적고 있고(오래된 이슈 kubernetes#67250), 해법은 사람이 손을 대는 것이다. 템플릿을 되돌린 뒤 깨진 Pod를 지운다.

```bash
# 깨진 리비전의 Pod를 지우면 되돌린 템플릿으로 다시 뜬다
kubectl -n data delete pod pg-2
kubectl -n data get pods -L controller-revision-hash
```

```text
pod "pg-2" deleted from data namespace
NAME   READY   STATUS    RESTARTS   AGE     CONTROLLER-REVISION-HASH
pg-0   1/1     Running   0          116s    pg-dfd9fc4d8
pg-1   1/1     Running   0          2m12s   pg-dfd9fc4d8
pg-2   1/1     Running   0          15s     pg-dfd9fc4d8
```

이미지 태그 오타로 ImagePullBackOff가 난 경우, 새 버전이 CrashLoopBackOff로 죽는 경우, readiness가 영원히 실패하는 경우가 모두 같다. 배포 파이프라인에 `rollout status --timeout`을 걸어 두고, 실패하면 "되돌리기 + 해당 리비전 Pod 삭제"까지를 한 묶음으로 실행하게 만든다. Helm의 `--atomic`이나 ArgoCD의 자동 롤백도 템플릿만 되돌리니, StatefulSet에서는 이 두 번째 단계가 빠지지 않았는지 본다.

## 노드가 죽으면 StatefulSet은 기다린다

Deployment는 노드가 응답하지 않으면 그 Pod를 포기하고 다른 노드에 새 Pod를 띄운다. 이름이 달라도 상관없으니까. StatefulSet은 그럴 수 없다. 죽은 노드의 `pg-1`이 정말 멈췄는지 모르는 상태에서 다른 노드에 `pg-1`을 또 띄우면, 같은 디스크에 두 프로세스가 쓰거나 primary가 둘이 되는 split brain이 생길 수 있다. 그래서 StatefulSet은 "같은 번호는 언제나 많아야 하나"를 지키려고 기다린다.

## DB를 쿠버네티스에 올릴까

StatefulSet은 이름, 디스크, 순서까지만 준다. 복제를 설정하고, primary가 죽으면 복제본 하나를 승격하고, 백업과 시점 복구를 돌리고, 버전을 올릴 때 순서를 지키는 일은 하지 않는다. "StatefulSet으로 PostgreSQL을 띄웠다"는 말은 사실 "프로세스 세 개에 디스크를 붙였다"에 가깝다. 그 위의 운영 지식을 코드로 만든 것이 오퍼레이터다. CloudNativePG, Zalando Postgres Operator, Percona 오퍼레이터 같은 것들이 StatefulSet(또는 Pod를 직접) 관리하면서 장애 조치와 백업을 맡는다. 오퍼레이터가 무엇을 하는지는 [오퍼레이터 글](/posts/k8s-operators)에서 이어진다.

선택지는 대략 셋이다.

| 방식 | 장점 | 대가 |
|---|---|---|
| 관리형 DB (RDS, Cloud SQL) | 장애 조치·백업·패치를 클라우드가 맡는다 | 비용, 클러스터 밖 네트워크, 세부 튜닝 제한 |
| 오퍼레이터 + StatefulSet | 같은 GitOps 흐름, 환경마다 같은 구성, 비용 | 오퍼레이터 자체를 운영하고 장애를 이해할 사람이 필요 |
| StatefulSet만 | 가장 단순하다 | 장애 조치와 백업을 사람이 해야 한다. 개발·테스트용 |

판단 기준은 기술보다 팀이다. 디스크가 존에 묶여 Pod가 그 존을 못 벗어나는 문제, 노드 업그레이드 때마다 primary가 옮겨 다니는 문제, 스토리지 지연을 진단하는 일을 누가 맡을지 정해져 있지 않으면 관리형이 싸다. 반대로 환경이 많고(개발자마다 DB 하나) 데이터가 크지 않거나, 클라우드 밖에서 돌아야 한다면 오퍼레이터가 맞다. 어느 쪽이든 StatefulSet만으로 운영 DB를 돌리는 것은 피한다.

## StatefulSet이 이상할 때 보는 순서

증상마다 먼저 볼 곳이 다르다.

```bash
# 1. 상태 숫자와 두 리비전: currentRevision과 updateRevision이 다르면 롤아웃 중이거나 멈춘 것
kubectl -n data get sts pg -o jsonpath='{.status}{"\n"}'
# 2. 어느 Pod가 어느 리비전인지
kubectl -n data get pods -l app=pg -L controller-revision-hash
# 3. 멈춘 번호의 이벤트: FailedScheduling, 볼륨 attach, 이미지
kubectl -n data describe pod pg-2 | sed -n '/Events/,$p'
# 4. PVC가 Bound인지, 어느 PV인지
kubectl -n data get pvc
# 5. DNS 이름이 안 나오면 serviceName의 Service가 있는지, clusterIP가 None인지
kubectl -n data get svc pg
```

`pg-1`이 안 생기면 `pg-0`이 Ready인지부터 본다. 줄였는데 디스크가 남았으면 정상 동작이다. 늘렸는데 데이터가 비어 있으면 retention 정책과 PV 상태를 본다. Pod가 Pending인데 이벤트가 "volume node affinity conflict"면 디스크와 다른 존의 노드에 가려는 것이다([PV와 PVC 글](/posts/k8s-pv-pvc#디스크가-다른-존에-있으면-pod가-못-간다)). 셸이 없는 이미지 안을 봐야 하면 `kubectl debug`로 임시 컨테이너를 붙인다. 방법은 [Pod 문제 해결 글](/posts/k8s-pod-troubleshooting)에 있다.

## 번호, 이름, 디스크

StatefulSet은 Pod에 번호를 주고, 번호로 DNS 이름과 PVC를 묶고, 번호 순서로 만들고 지우고 바꾼다. headless Service가 이름을 붙이고, PVC는 Pod보다 오래 살아서 줄였다 늘려도 데이터가 돌아온다. 대신 같은 번호가 둘이 되지 않도록 업데이트는 한 대씩 빠지고, 깨진 리비전에서는 되돌린 뒤 Pod를 지워 줘야 하고, 죽은 노드에서는 사람이 확인해 줘야 한다. 노드마다 하나씩 띄우는 다른 컨트롤러는 [DaemonSet 글](/posts/k8s-daemonset)에서, 끝나는 작업을 맡는 컨트롤러는 [Job과 CronJob 글](/posts/k8s-job-cronjob)에서 이어진다.

## 면접에서 나올 만한 질문

### StatefulSet과 Deployment는 무엇이 다른가요?

StatefulSet은 Pod마다 고정된 번호, 이름, 디스크를 준다. Deployment의 Pod는 서로 바꿔 끼울 수 있는 복제본이라 이름이 무작위이고 PVC를 공유하지만, StatefulSet은 `pg-0`, `pg-1`처럼 번호가 붙고 `volumeClaimTemplates`로 번호마다 PVC를 만든다. 만들 때는 작은 번호부터, 줄이고 업데이트할 때는 큰 번호부터 한 대씩 진행한다. 같은 이름이 둘이 될 수 없어서 maxSurge가 없다.

### headless Service가 왜 필요한가요?

StatefulSet Pod에 `pg-1.pg.data.svc.cluster.local` 같은 DNS 이름을 붙이는 것이 headless Service다. `serviceName`이 Pod의 subdomain이 되고, CoreDNS가 EndpointSlice의 hostname을 보고 Pod마다 A 레코드를 만든다. VIP가 없으니 클라이언트가 특정 Pod를 골라 직접 연결할 수 있다. StatefulSet이 이 Service를 만들어 주지 않아서 빠뜨리면 Pod는 떠도 이름이 생기지 않는다.

### replicas를 줄이면 PVC는 어떻게 되나요?

기본으로는 남는다. 다시 늘리면 같은 번호의 Pod가 그 PVC를 그대로 붙여 데이터가 이어진다. `persistentVolumeClaimRetentionPolicy.whenScaled: Delete`로 바꾸면 사라질 Pod를 PVC의 owner로 걸어 Pod 삭제와 함께 지운다. 다시 늘리면 같은 이름의 빈 PVC가 새로 생기므로 DB에는 Retain을 쓴다.

### partition은 언제 쓰나요?

한 대만 먼저 새 버전으로 바꿔 보는 카나리나 단계적 배포에 쓴다. partition 이상인 번호만 새 템플릿을 받고, 아래 번호는 지워져도 옛 리비전으로 다시 뜬다. 지켜본 뒤 partition을 0으로 내리면 나머지가 큰 번호부터 바뀐다. 0번을 primary로 두는 구성이면 primary가 마지막에 한 번만 재시작된다.

### 잘못된 이미지로 StatefulSet 롤아웃이 멈췄습니다. undo하면 되나요?

undo만으로는 안 된다. OrderedReady에서는 컨트롤러가 깨진 Pod가 Ready가 되기를 계속 기다려서, 템플릿을 되돌려도 그 Pod는 깨진 리비전으로 남는다. 템플릿을 되돌린 뒤 깨진 리비전의 Pod를 직접 지워야 되돌린 템플릿으로 다시 뜬다. 배포 자동화에 이 단계가 들어 있는지 확인한다.

### 노드가 죽었는데 StatefulSet Pod가 다른 노드로 옮겨지지 않습니다. 왜 그런가요?

같은 번호의 Pod가 동시에 둘 뜨지 않게 하려고 옛 Pod가 API에서 사라질 때까지 기다리기 때문이다. kubelet이 응답하지 않으면 Pod는 Terminating에 머문다. 노드가 꺼진 것을 확인한 뒤 out-of-service taint를 걸거나 Pod를 강제 삭제해야 다른 노드에 다시 뜬다. 노드가 살아 있는데 강제 삭제하면 같은 디스크에 두 프로세스가 쓸 수 있어 위험하다.

### 운영 DB를 StatefulSet으로 돌려도 되나요?

StatefulSet만으로는 권하지 않는다. StatefulSet은 이름, 디스크, 순서만 주고 복제 설정, 장애 조치, 백업, 버전 업그레이드는 하지 않는다. 쿠버네티스에서 돌린다면 그 일을 코드로 하는 오퍼레이터를 쓰고, 팀이 스토리지와 오퍼레이터 장애를 다룰 여력이 없으면 관리형 DB가 낫다.
