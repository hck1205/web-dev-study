## 내 DB에만 있는 컬럼

동료 노트북에서는 잘 도는 코드가 내 노트북에서는 `column "name" does not exist`로 죽는다. 동료가 지난주에 `ALTER TABLE users ADD COLUMN name text`를 자기 DB에서 직접 쳤고, 그 사실은 슬랙 어딘가에만 남아 있다. 스테이징에는 누가 쳤는지 모르겠고, 운영에는 배포하는 날 누군가 기억해서 쳐야 한다. 테이블 모양이 사람 기억에 달려 있는 상태다.

마이그레이션 도구는 이 문제를 푼다. 스키마 변경을 SQL이나 코드 파일로 남겨 Git에 함께 올리고, DB 안에 "어디까지 적용했는지"를 기록하는 표를 둔다. 도구는 그 표와 파일 목록을 비교해서 아직 안 한 것만 순서대로 실행한다. 개발자 노트북, CI, 스테이징, 운영이 모두 같은 파일을 같은 순서로 거치니 테이블 모양이 같아진다.

이 글은 도구가 안에서 무엇을 하는지, 파드 여러 개가 동시에 마이그레이션을 돌리면 어떻게 되는지, 중간에 실패하면 무엇이 남는지, 왜 이미 적용한 파일을 고치면 안 되는지를 실제로 돌려 보며 따라간다. 변경 하나하나를 서비스를 멈추지 않고 하는 방법은 [무중단 스키마 변경 글](/posts/zero-downtime-migrations)에서 이어진다.

이 주제의 다른 글: [무중단 스키마 변경](/posts/zero-downtime-migrations), [스키마 버전 관리(이벤트와 API 스키마)](/posts/schema-versioning), [규모별 DB 설계의 열 이름 바꾸기](/posts/db-architecture-by-scale).

실험은 PostgreSQL 16에서 Flyway 10.20, knex 3.3, node-pg-migrate 9.0, golang-migrate 4.18을 직접 돌렸다. Liquibase와 Prisma Migrate는 동작 방식만 비교한다.

실행이 끝나면 DB 안에 기록 표가 생긴다. 도구의 기억은 전부 이 표에 있다.

```sql
SELECT installed_rank, version, description, script, checksum, execution_time, success
FROM flyway_schema_history ORDER BY installed_rank;
```

```text
 installed_rank | version |  description  |        script         |  checksum   | execution_time | success 
----------------+---------+---------------+-----------------------+-------------+----------------+---------
              1 | 1       | create users  | V1__create_users.sql  |   642634823 |             17 | t
              2 | 2       | create orders | V2__create_orders.sql | -1838863248 |              7 | t
(2 rows)
```

`checksum`을 눈여겨보자. 파일 내용으로 계산한 값(Flyway는 CRC32)이다. 다음 실행 때 파일 내용을 다시 계산해 이 값과 비교한다. 뒤에서 이 칸이 사고를 막는 장면을 본다.

## 파드 세 개가 동시에 migrate를 부르면

쿠버네티스에서 앱이 시작할 때 마이그레이션을 돌리게 해 두면, 배포 순간 파드 여러 개가 동시에 `migrate`를 부른다. 잠금이 없으면 셋이 같은 `CREATE TABLE`을 동시에 실행하고 둘은 `already exists`로 죽는다. 그래서 모든 도구가 잠금을 잡는다. 잡는 방법이 달라서 실패했을 때 남는 것도 다르다.

knex로 3초 걸리는 마이그레이션을 프로세스 셋이 동시에 돌리고, 1초 뒤 DB에서 누가 누구를 기다리는지 봤다.

```bash
# 같은 마이그레이션을 프로세스 셋이 동시에 실행
for p in pod-a pod-b pod-c; do ( knex migrate:latest 2>&1 | sed "s/^/[$p] /" ) & done
```

```text
  pid  | blocked_by | state  |  wait   |                        query                         
-------+------------+--------+---------+------------------------------------------------------
 28635 | {}         | active | Timeout | SELECT pg_sleep(3)
 28636 | {28635}    | active | Lock    | update "knex_migrations_lock" set "is_locked" = $1 w
 28637 | {28636}    | active | Lock    | update "knex_migrations_lock" set "is_locked" = $1 w
(3 rows)

[pod-b] Batch 3 run: 1 migrations
[pod-a] Already up to date
[pod-c] Already up to date
```

node-pg-migrate는 행 대신 advisory lock을 쓴다. 기본값은 기다리지 않고 바로 실패하는 것이라 출력이 다르다.

```text
[pod-a] Error: Another migration is already running. Advisory lock mode is set to 'fail'.
 pid | locktype |   objid   | granted |        query        
-----+----------+-----------+---------+---------------------
 970 | advisory | 708954076 | t       | SELECT pg_sleep(3);
(1 row)
[pod-b] Migrations complete!
```

`--advisory-lock-mode wait`를 주면 knex처럼 기다린다. 앱 시작 시점에 돌린다면 기다리는 쪽이 낫다. 실패 모드에서는 pod-a가 에러로 재시작하고, 재시작하는 사이 아무 일도 안 하던 배포가 늦어진다.

## 실행하다 죽으면 무엇이 남나

잠금 방식의 차이는 프로세스가 죽었을 때 드러난다. advisory lock과 커밋 전의 행 잠금은 연결이 끊기면 PostgreSQL이 알아서 푼다. 하지만 잠금을 "표의 값"으로 기록하고 커밋해 버린 경우는 아무도 지워 주지 않는다.

knex에서 트랜잭션을 끈 마이그레이션(`CREATE INDEX CONCURRENTLY`처럼 트랜잭션 안에서 못 도는 작업)을 실행하다 프로세스를 `kill -9`로 죽여 봤다. 배포 중 파드가 OOM으로 죽는 것과 같은 상황이다.

```text
 index | is_locked 
-------+-----------
     1 |         1
(1 row)
```

```text
Can't take lock to run migrations: Migration table is already locked
If you are sure migrations are not running you can release the lock manually by running 'knex migrate:unlock'
MigrationLocked: Migration table is already locked
```

`is_locked = 1`이 커밋된 채 남았고, 다음 배포부터 모든 마이그레이션이 이 에러로 멈춘다. 정말 아무것도 안 돌고 있는지 `pg_stat_activity`로 확인한 뒤 잠금을 풀고 다시 돌린다.

```bash
# 돌고 있는 마이그레이션이 없는지 확인한 뒤에만
knex migrate:unlock
knex migrate:latest
```

```text
Succesfully unlocked the migrations lock table
Batch 4 run: 1 migrations
```

Liquibase도 `DATABASECHANGELOGLOCK` 표의 `LOCKED` 칸으로 잠그기 때문에 같은 일이 생기고, `liquibase release-locks`로 푼다. Flyway, node-pg-migrate, golang-migrate, Prisma Migrate는 advisory lock을 써서 이런 잔재가 남지 않는다.

잠금은 풀렸는데 스키마가 반쯤 바뀐 경우가 더 골치다. PostgreSQL에서는 DDL도 트랜잭션으로 되돌릴 수 있어서, 트랜잭션 안에서 도는 마이그레이션은 실패하면 깨끗하게 사라진다. Flyway에서 두 번째 문장이 틀린 파일을 돌려 봤다.

```sql
-- V3__add_order_status.sql
ALTER TABLE orders ADD COLUMN status text NOT NULL DEFAULT 'paid';
CREATE INDEX orders_status_idx ON orders (statuz);   -- 오타
```

```text
Migrating schema "public" to version "3 - add order status"
ERROR: Migration of schema "public" to version "3 - add order status" failed! Changes successfully rolled back.
Message    : ERROR: column "statuz" does not exist
```

첫 문장의 `status` 열도 같이 사라졌고 기록 표에도 V3이 없다. 오타를 고쳐 다시 돌리면 된다. MySQL 8은 다르다. DDL 문장마다 암묵적으로 커밋하기 때문에 첫 문장은 남고 두 번째에서 멈춘다. MySQL에서는 파일 하나에 DDL을 하나만 두는 습관이 이래서 생겼다.

트랜잭션 밖에서 도는 작업은 PostgreSQL에서도 반쯤 남는다. golang-migrate는 실패하면 기록 표에 `dirty` 표시를 남긴다.

```text
1/u create_users (20.18805ms)
error: migration failed: column "nmae" does not exist in line 0: ALTER TABLE users ADD COLUMN name text;
CREATE INDEX users_name_idx ON users (nmae);
 (details: pq: column "nmae" does not exist)

 version | dirty 
---------+-------
       2 | t
(1 row)

error: Dirty database version 2. Fix and force version.
```

이 경우 파일 전체가 한 번에 전송돼 PostgreSQL이 묶어서 되돌렸으니 `name` 열은 없다. 하지만 도구는 그걸 모르고 "2를 하다 말았다"고만 기록한다. 사람이 실제 스키마를 보고 판단해야 한다. 아무것도 안 남았으니 버전을 1로 되돌리고, 파일을 고쳐 다시 올린다.

```bash
# 실제 스키마를 \d users로 확인한 뒤, 기록을 마지막으로 성공한 버전으로 맞춘다
migrate -path . -database "$DB_URL" force 1
migrate -path . -database "$DB_URL" up
```

```text
2/u add_users_name (14.99175ms)
```

`force`는 기록만 바꾸고 스키마는 건드리지 않는다. 실제 스키마를 확인하지 않고 `force 2`를 하면, 도구는 열이 있다고 믿는데 실제로는 없는 상태가 되어 다음 마이그레이션에서 더 큰 사고가 난다.

## Flyway가 스스로를 기다린 날

트랜잭션 밖에서 도는 작업에는 함정이 하나 더 있었다. Flyway로 `CREATE UNIQUE INDEX CONCURRENTLY`를 돌렸더니 끝나지 않고 멈췄다. 다른 연결은 없었다. 멈춘 동안 DB를 봤다.

```text
  pid  |        state        | wait_event_type | wait_event |                       q                        
-------+---------------------+-----------------+------------+------------------------------------------------
 23511 | idle in transaction | Client          | ClientRead | SELECT COUNT(*) FROM pg_namespace WHERE nspname=$1
 23513 | active              | Lock            | virtualxid | CREATE UNIQUE INDEX CONCURRENTLY users_email_lower_key ON users (lower
```

```text
  pid  |  locktype  |     mode      | granted |   objid    
-------+------------+---------------+---------+------------
 23511 | advisory   | ExclusiveLock | t       | 4163491309
 23511 | virtualxid | ExclusiveLock | t       |           
 23513 | virtualxid | ExclusiveLock | t       |           
 23513 | virtualxid | ShareLock     | f       |           
```

두 연결 모두 Flyway의 것이다. 23511은 Flyway가 잠금을 잡으려고 연 연결로, 트랜잭션 단위 advisory lock을 잡은 채 트랜잭션을 열어 두고 있다. 23513은 실제로 인덱스를 만드는 연결이다. `CREATE INDEX CONCURRENTLY`는 마지막 단계에서 "시작 전에 열린 트랜잭션이 모두 끝나기"를 기다린다(`virtualxid` 대기). 그런데 그 열린 트랜잭션이 Flyway 자신의 잠금 연결이라 영원히 끝나지 않는다.

```bash
# 세션 단위 advisory lock을 쓰게 바꾼다
flyway ... -postgresql.transactional.lock=false migrate
```

```text
Migrating schema "public" to version "4 - users email lower unique" [non-transactional]
Successfully applied 1 migration to schema "public", now at version v4 (execution time 00:00.025s)
```

같은 실험에서 처음에는 중복 이메일 때문에 인덱스 생성이 실패했는데, 그때는 멈추지 않았다. 중복 검사는 대기 단계 전에 실패하기 때문이다. 이 실패는 다른 흔적을 남겼다.

```text
ERROR: Migration of schema "public" to version "4 - users email lower unique" [non-transactional] failed! Please restore backups and roll back database and code!
  Detail: Key (lower(email))=(kim@example.com) is duplicated.

Indexes:
    "users_email_lower_key" UNIQUE, btree (lower(email)) INVALID
```

기록 표에는 V4가 대기 중으로 남았지만, DB에는 `INVALID` 인덱스가 생겼다. 중복 데이터를 고치고 다시 돌리면 `relation "users_email_lower_key" already exists`로 또 실패한다. 반쯤 남은 인덱스를 `DROP INDEX CONCURRENTLY`로 지운 뒤에야 다시 돌릴 수 있다. 이런 파일은 처음부터 `DROP INDEX CONCURRENTLY IF EXISTS`를 앞에 두면 재실행이 안전해진다. INVALID 인덱스는 [인덱스의 대가 글](/posts/db-index-pitfalls)에서 더 다룬다.

## 적용한 파일은 고치지 않는다

운영에 나간 V2 파일에 `CHECK (amount > 0)`을 슬쩍 더하고 다시 돌려 봤다.

```text
ERROR: Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 2
-> Applied to database : -1838863248
-> Resolved locally    : -1346388768
Either revert the changes to the migration, or run repair to update the schema history.
```

Flyway가 막은 이유는 이렇다. 운영 DB에는 고치기 전 V2가 이미 적용됐다. 파일을 고쳐도 운영 DB의 테이블에는 `CHECK`가 생기지 않는다. 반면 새로 만드는 개발 DB나 CI DB는 고친 V2로 만들어진다. 같은 "버전 2"인데 환경마다 테이블 모양이 달라진다. 도구를 쓰는 이유 자체가 무너진다. 그래서 바꾸고 싶은 게 있으면 V5를 새로 만든다.

```sql
-- V5__orders_amount_positive.sql
ALTER TABLE orders ADD CONSTRAINT orders_amount_positive CHECK (amount > 0) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_amount_positive;
```

체크섬이 없는 도구도 있다. knex와 golang-migrate는 내용이 바뀐 걸 모르고 지나간다. 대신 knex는 적용된 파일이 사라지면 멈춘다. 파일 이름을 바꿔 봤다.

```text
Error: The migration directory is corrupt, the following files are missing: 20261021091000_add_users_name.js
```

순서가 꼬이는 것도 막는다. 브랜치 두 개가 각자 마이그레이션을 만들면, 나중에 머지된 쪽의 파일이 이미 적용된 파일보다 앞 번호일 수 있다. node-pg-migrate는 이렇게 멈춘다.

```text
Error: Not run migration 1761000200000_add-users-name is preceding already run migration 1761000300000_slow-orders
```

Flyway는 같은 상황에서 `outOfOrder=true`를 주면 앞 번호 파일도 실행한다. 두 변경이 서로 상관없다는 확신이 있을 때만 쓴다. 보통은 늦게 머지된 파일의 번호를 맨 뒤로 바꿔 다시 올린다. 아직 어느 환경에도 적용되지 않았으니 이름을 바꿔도 괜찮다.

도구가 하는 검사를 직접 짜 보자. 기록 표의 행 목록과 파일 목록을 받아서 대기 중인 버전과 오류를 돌려준다. 적용된 버전의 파일이 없으면 `missing 버전`, 체크섬이 다르면 `checksum 버전`, 대기 중인 버전이 적용된 가장 큰 버전보다 작으면 `out of order 버전`이다. 오류가 하나라도 있으면 아무것도 실행하지 않으니 대기 목록은 비운다.

## down 파일은 운영의 되돌리기 버튼이 아니다

knex, node-pg-migrate, golang-migrate는 `up`과 짝을 이루는 `down`을 쓴다. knex는 한 번에 실행된 묶음(batch)을 단위로 되돌린다.

```text
Batch 4 rolled back: 1 migrations
```

개발 중에는 편하다. 하지만 운영에서 `down`은 조심해야 한다. `ADD COLUMN`의 `down`은 `DROP COLUMN`이고, 그 사이 쌓인 데이터는 같이 사라진다. 옛 앱으로 되돌리는 건 이미지 하나 바꾸면 되지만, 지운 열은 백업 없이는 못 되살린다. 그래서 많은 팀이 운영에서는 "앞으로 고친다(roll forward)"를 원칙으로 둔다. 문제가 있으면 그걸 고치는 새 마이그레이션을 낸다. Flyway 무료판과 Prisma Migrate가 `down`을 아예 두지 않는 것도 같은 생각이다.

되돌리기를 정말 안전하게 만드는 방법은 `down` 파일이 아니라 마이그레이션 자체를 옛 코드와 새 코드가 둘 다 견디게 짜는 것이다. 열을 지우는 것 같은 되돌릴 수 없는 변경은 앱이 그 열을 완전히 잊은 다음 배포로 미룬다. 단계는 [무중단 스키마 변경 글](/posts/zero-downtime-migrations)에 있다.

## 도구를 고를 때 보는 것

| 도구 | 기록 표 | 잠금 | 체크섬 | down |
|---|---|---|---|---|
| Flyway | `flyway_schema_history` | advisory lock | CRC32 | 유료판(U 파일) |
| Liquibase | `DATABASECHANGELOG` | `DATABASECHANGELOGLOCK` 행 | MD5 기반 | changeset의 rollback 블록 |
| Prisma Migrate | `_prisma_migrations` | advisory lock | SHA-256 | 없음 |
| knex | `knex_migrations` | `knex_migrations_lock` 행 | 없음 | 있음(batch 단위) |
| node-pg-migrate | `pgmigrations` | advisory lock | 없음 | 있음 |
| golang-migrate | `schema_migrations(version, dirty)` | advisory lock | 없음 | 있음(`.down.sql`) |

언어와 ORM이 먼저 고른다. Prisma를 쓰면 Prisma Migrate, Java면 Flyway나 Liquibase가 자연스럽다. 그다음에 볼 것은 SQL을 직접 쓰느냐, 모델 정의에서 SQL을 생성하느냐다. 생성해 주는 도구(Prisma의 `migrate dev`, Django, Rails)는 편하지만, 생성된 SQL이 운영에서 테이블을 오래 잠그는지는 사람이 읽어 봐야 한다. 열 이름을 바꾸면 생성기가 `DROP COLUMN` 후 `ADD COLUMN`을 만드는 경우도 있다. 생성된 파일을 그대로 커밋하지 말고 열어서 고친다.

Prisma Migrate는 개발용 `migrate dev`와 운영용 `migrate deploy`가 다르다. `migrate dev`는 임시 DB(shadow database)를 만들어 차이를 계산하고, 필요하면 개발 DB를 초기화하자고 한다. 운영 파이프라인에서는 `migrate deploy`만 쓴다. 실패한 마이그레이션이 있으면 다음 배포가 `P3009` 에러로 막히고, 상태를 확인한 뒤 `prisma migrate resolve --rolled-back` 또는 `--applied`로 기록을 정리한다. golang-migrate의 `force`와 같은 역할이다.

이미 운영 중인 DB에 도구를 처음 들일 때는 지금 스키마를 첫 버전으로 찍는다. Flyway의 `baseline`, Liquibase의 `changelog-sync`가 이 일을 한다. 기존 테이블을 만드는 V1을 운영에서 실행하면 `already exists`로 실패하기 때문이다.

## 언제, 어디서 돌리나

마이그레이션을 돌리는 위치는 세 가지다. 앱이 시작할 때 돌리는 방법은 간단하지만 앞에서 본 것처럼 파드 수만큼 잠금 경쟁이 생기고, 오래 걸리는 마이그레이션이면 준비 상태 확인(readiness probe)이 실패해 파드가 재시작되는 사이 잠금만 오간다. 그래서 운영에서는 배포 파이프라인에 마이그레이션 단계를 따로 두는 경우가 많다. 쿠버네티스라면 Job, Helm의 `pre-upgrade` 훅, initContainer 중 하나다.

어디서 돌리든 지켜야 할 것이 있다. 마이그레이션 계정은 앱 계정과 나눈다. 앱 계정은 데이터만 읽고 쓰고, 테이블을 만들고 바꾸는 권한은 마이그레이션 계정에만 준다. 그리고 모든 마이그레이션 연결에 `lock_timeout`을 건다. 잠금을 오래 기다리는 DDL 하나가 그 테이블의 모든 쿼리를 막는 장면은 [무중단 스키마 변경 글](/posts/zero-downtime-migrations)에서 직접 본다.

## 스키마도 코드처럼 리뷰한다

마이그레이션 도구는 스키마 변경을 파일로 남기고, 기록 표로 어디까지 했는지 기억하고, 잠금으로 한 번에 한 프로세스만 실행하게 하는 장치다. 사고는 이 셋이 어긋날 때 난다. 적용한 파일을 고쳐 기록과 파일이 어긋나거나, 죽은 프로세스가 잠금을 남기거나, 트랜잭션 밖의 작업이 반쯤 남아 기록과 실제 스키마가 어긋난다. 고칠 때는 언제나 실제 스키마를 먼저 보고, 기록을 거기에 맞춘다.

## 면접에서 나올 만한 질문

### 마이그레이션 도구는 왜 쓰나요?

스키마 변경을 사람 기억이 아니라 파일과 기록으로 관리하려고 쓴다. 변경을 순서가 있는 파일로 Git에 남기고, DB 안의 기록 표에 어디까지 적용했는지 적어서 모든 환경이 같은 순서로 같은 변경을 거치게 한다. 코드 리뷰와 CI에서 스키마 변경을 함께 검토할 수 있다는 것도 크다.

### 이미 운영에 적용한 마이그레이션 파일을 고치면 왜 안 되나요?

운영 DB에는 고치기 전 내용이 이미 적용됐으니 고친 내용이 반영되지 않고, 새로 만드는 환경에만 반영되어 환경마다 스키마가 달라진다. Flyway나 Prisma Migrate는 체크섬으로 이걸 잡아 실행을 멈춘다. 바꿀 게 있으면 새 버전의 마이그레이션을 추가한다.

### 파드 여러 개가 동시에 마이그레이션을 실행하면 어떻게 되나요?

도구가 잠금을 잡아서 한 프로세스만 실행하고 나머지는 기다리거나 실패한다. knex나 Liquibase는 잠금 표의 행을, Flyway·node-pg-migrate·golang-migrate·Prisma는 PostgreSQL advisory lock을 쓴다. 표의 값으로 잠그는 방식은 프로세스가 죽으면 잠금이 남아 `migrate:unlock`이나 `release-locks`로 풀어야 한다. 그래서 운영에서는 Job이나 파이프라인 단계로 한 번만 돌리는 편이 낫다.

### 마이그레이션이 중간에 실패하면 어떻게 복구하나요?

먼저 실제 스키마를 확인한다. PostgreSQL은 DDL도 트랜잭션으로 되돌리니 트랜잭션 안에서 돈 마이그레이션은 깨끗하게 사라지고, 고쳐서 다시 돌리면 된다. `CREATE INDEX CONCURRENTLY`처럼 트랜잭션 밖의 작업은 INVALID 인덱스 같은 흔적을 남기니 지우고 다시 돌린다. golang-migrate의 dirty나 Prisma의 실패 기록은 실제 상태를 확인한 뒤 `force`나 `migrate resolve`로 기록을 맞춘다.

### down 마이그레이션으로 운영을 되돌려도 되나요?

조심해야 한다. 열 추가의 down은 열 삭제라서 그 사이 쌓인 데이터가 사라진다. 운영에서는 문제를 고치는 새 마이그레이션을 내는 roll forward를 기본으로 두고, 마이그레이션을 옛 코드와 새 코드가 둘 다 견디게 짜서 앱만 되돌려도 되게 만든다.

### MySQL과 PostgreSQL에서 실패한 마이그레이션의 결과가 왜 다른가요?

PostgreSQL은 DDL을 트랜잭션 안에서 실행하고 되돌릴 수 있어서, 파일 하나를 트랜잭션으로 묶으면 실패 시 전부 사라진다. MySQL 8은 DDL마다 암묵적으로 커밋해서 앞 문장은 남고 실패한 지점에서 멈춘다. 그래서 MySQL에서는 파일 하나에 DDL 하나를 두고, 실패하면 남은 부분을 사람이 정리한다.

### Flyway로 CREATE INDEX CONCURRENTLY를 돌렸더니 멈췄습니다. 무엇을 보나요?

`pg_stat_activity`와 `pg_locks`에서 인덱스 연결이 `virtualxid`를 기다리는지, 누가 트랜잭션을 열어 두고 있는지 본다. CONCURRENTLY는 먼저 시작한 트랜잭션이 끝나길 기다리는데, Flyway의 기본 트랜잭션 단위 advisory lock 연결이 그 트랜잭션일 수 있다. `postgresql.transactional.lock=false`로 세션 잠금을 쓰게 하면 풀린다.
