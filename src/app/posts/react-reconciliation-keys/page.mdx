결제 화면에 "개인" 탭과 "법인" 탭이 있다. 탭마다 `<AmountInput>`을 하나씩 그리는데, 개인 탭에서 금액을 50,000으로 적고 법인 탭으로 넘어가면 법인 탭 입력칸에도 50,000이 그대로 들어 있다. 코드에는 두 탭이 분명히 다른 컴포넌트로 적혀 있다.

```tsx
{tab === "personal" ? (
  <AmountInput label="개인 결제 금액" />
) : (
  <AmountInput label="법인 결제 금액" />
)}
```

옆 화면에서는 반대 일이 일어난다. 안내 배너를 닫는 버튼을 눌렀더니, 배너와 아무 관계 없는 아래쪽 입력칸이 비어 버린다.

```tsx
{showBanner ? (
  <>
    <Banner onClose={() => setShowBanner(false)} />
    <AmountInput label="금액" />
  </>
) : (
  <AmountInput label="금액" />
)}
```

첫 번째는 지워져야 할 상태가 남았고, 두 번째는 남아야 할 상태가 지워졌다. 둘 다 버그가 아니라 React가 이전 트리와 새 트리를 짝짓는 규칙대로 움직인 결과다. 이 글은 그 규칙, 재조정 알고리즘을 소스 코드에 있는 이름 수준까지 따라간다. 렌더와 커밋의 차이, 인덱스 key가 왜 위험한지 같은 기초는 [React는 언제 다시 그리나](/posts/react-rerender)에서 다뤘으니 여기서는 그다음 질문들을 본다. 확인은 React 19.3.1을 Node 22와 jsdom 위에 올려서 했다.

## 비교를 싸게 만든 대가

두 트리의 차이를 최소 편집으로 구하는 일반 알고리즘은 O(n³)이다. React는 이걸 O(n)으로 줄이려고 두 가지를 가정한다고 예전 공식 문서의 Reconciliation 페이지에 적어 두었다. 타입이 다른 두 엘리먼트는 다른 트리를 만든다. 그리고 개발자가 key로 "렌더링이 바뀌어도 같은 자식"을 알려 줄 수 있다.

이 가정이 무엇을 포기하는지를 알면 동작이 예측된다. React는 트리를 위에서부터 같은 깊이끼리만 비교한다. 어떤 서브트리가 다른 부모 밑으로 옮겨 갔는지는 찾지 않는다. `<List />`를 `<section>`으로 한 번 감싸기만 해도, React 입장에서는 원래 자리의 `List`가 사라지고 처음 보는 `section`이 생긴 것이다. 그 아래에 있던 모든 상태와 DOM 노드가 버려지고 새로 만들어진다.

같은 깊이 안에서도 React는 옮겨진 형제를 key가 있을 때만 찾는다. key가 없으면 형제의 순서 번호가 곧 이름이다. 그래서 React의 비교는 "아주 똑똑한 diff"가 아니라 "몇 가지 규칙으로 빠르게 짝을 짓고, 짝이 안 맞으면 과감하게 새로 만드는 diff"에 가깝다. 대부분의 UI에서는 이 정도로 충분하고, 충분하지 않은 곳에서 개발자가 key로 힌트를 준다.

## 상태는 컴포넌트가 아니라 자리에 붙는다

`useState`의 값은 컴포넌트 함수 안에 사는 것처럼 보인다. 실제로는 React가 트리의 각 자리마다 만들어 둔 내부 객체(Fiber 노드)의 `memoizedState` 필드에 저장된다. 함수는 렌더링될 때마다 호출되고 끝나면 사라지지만 Fiber는 남는다. 다음 렌더링에서 같은 Fiber를 다시 쓰면 상태가 이어지고, Fiber를 버리고 새로 만들면 상태도 처음 값으로 돌아간다.

그러니 "상태가 유지되느냐"는 "React가 이전 Fiber를 다시 쓰느냐"와 같은 질문이다. React가 이전 Fiber를 다시 쓰는 조건은 세 가지가 모두 맞을 때다.

1. 부모가 같다. 부모 Fiber를 다시 쓰고 있어야 그 아래를 비교한다.
2. 형제 사이의 이름이 같다. key가 있으면 key, 없으면 순서 번호다.
3. 타입이 같다. 함수 컴포넌트면 같은 함수 참조, 태그면 같은 태그 이름이다.

props는 조건에 없다. props가 완전히 달라져도 세 조건이 맞으면 같은 컴포넌트로 보고 props만 바꿔 넣는다. 처음 결제 화면에서 `label`이 달라도 금액이 남은 이유가 이것이다. 아래 그림은 두 탭 코드를 React가 보는 방식으로 다시 그린 것이다.

## 조건부 렌더링에서 갈리는 다섯 장면

말로만 하면 헷갈리니 다섯 가지 모양을 실제로 돌려 봤다. 카운터 컴포넌트를 세 번 눌러 상태를 3으로 만든 뒤 조건을 뒤집고, 화면에 남은 값과 마운트·언마운트 로그를 찍었다.

```tsx
function Counter({ name }) {
  const [n, setN] = useState(0);
  useEffect(() => {
    log("mount " + name);
    return () => log("unmount " + name);
  }, []);
  return <button onClick={() => setN((x) => x + 1)}>{name}:{n}</button>;
}

// 1) 같은 자리, 같은 타입
flag ? <Counter name="A" /> : <Counter name="B" />
// 2) 같은 자리, 같은 타입, key만 다르다
flag ? <Counter key="A" name="A" /> : <Counter key="B" name="B" />
// 3) 한쪽만 감싼다
flag ? <Counter name="A" /> : <section><Counter name="B" /></section>
// 4) && 로 앞 형제를 끈다
<>{flag && <Banner />}<Counter name="C" /></>
// 5) 삼항으로 앞 형제를 뺀다 (처음 배너 화면)
flag ? <><Banner /><Counter name="C" /></> : <Counter name="C" />
```

```text
ternarySameType  before=A:3          after=B:3        mount A
ternaryKeyed     before=A:3          after=B:0        mount A, unmount A, mount B
wrapperDiffers   before=A:3          after=B:0        mount A, unmount A, mount B
andHole          before=bannerC:3    after=C:3        mount C
ternaryShift     before=bannerC:3    after=C:0        mount C, unmount C, mount C
```

1번은 처음 탭 화면이다. 이름이 B로 바뀌었는데 숫자 3은 그대로고, 언마운트도 없다. 2번은 key만 달리 줬을 뿐인데 A가 언마운트되고 B가 0으로 새로 생겼다. 3번은 한쪽을 `section`으로 감싸서 0번 자리의 타입이 `Counter`에서 `section`으로 바뀌었다. 그 아래 `Counter`는 같은 함수지만 부모가 달라졌으니 새로 만들어진다.

4번과 5번의 차이가 처음 배너 화면의 답이다. `flag && <Banner />`는 flag가 false일 때 `false`를 자식으로 남긴다. React는 `false`, `null`, `undefined`를 아무것도 그리지 않는 빈 자리로 취급하지만 자리 번호는 센다. 그래서 `Counter`는 계속 1번 자리에 있고 상태가 살아남는다. 5번은 한쪽 갈래에서 Fragment 안에 두 자식을, 다른 갈래에서 `Counter` 하나를 돌려준다. 1번 자리에 있던 `Counter`가 0번 자리로 당겨졌고, 0번 자리의 타입은 `Banner`였으니 React는 짝을 찾지 못한다.

고치는 방법은 세 가지 중 고른다. 4번처럼 조건을 자리 안에 넣어 형제 순서를 고정하거나, 두 갈래의 `Counter`에 같은 key를 줘서 자리 대신 이름으로 짝을 짓게 하거나, 상태를 위로 올려 `Counter`가 다시 만들어져도 값이 유지되게 한다. 상태를 올리는 건 이 경우엔 과하다. 앞의 두 가지를 코드로 보면 이렇다.

```tsx
// 1) 형제 순서를 고정한다
<>
  {showBanner && <Banner onClose={() => setShowBanner(false)} />}
  <AmountInput label="금액" />
</>

// 2) 두 갈래에 같은 key를 준다. 위치가 달라도 같은 형제 목록 안이면 key로 짝을 찾는다
{showBanner ? (
  <>
    <Banner key="banner" onClose={() => setShowBanner(false)} />
    <AmountInput key="amount" label="금액" />
  </>
) : (
  <AmountInput key="amount" label="금액" />
)}
```

2번은 조건이 까다롭다. React는 부모의 자식 자리에 key 없는 Fragment 하나만 있으면 그 Fragment를 펼쳐서 안의 요소들을 바로 형제 목록으로 본다. 그 목록 안에서 `amount` key가 양쪽 갈래에 있으니 이전 Fiber를 찾는다. 그런데 삼항식 옆에 다른 형제가 하나라도 있으면 Fragment는 펼쳐지지 않고 자기 자리를 가진 노드가 된다. 그러면 0번 자리의 타입이 Fragment에서 `AmountInput`으로 바뀐 것이라 key가 같아도 소용없다. 세 가지를 돌려 봤다.

```text
soleChild    before=bannerC:3 after=C:3    // 삼항식이 부모의 유일한 자식, key 있음
withSibling  before=bannerC:3 after=C:0    // 삼항식 뒤에 <hr /> 형제가 있음, key 있음
noKeySole    before=bannerC:3 after=C:0    // 유일한 자식이지만 key 없음
```

이렇게 주변 코드 한 줄에 따라 결과가 달라지는 방법은 나중에 누가 형제 하나를 추가하는 순간 조용히 깨진다. 그래서 보통은 1번처럼 형제 순서를 고정하는 쪽을 고른다.

## key는 자리를 다시 만드는 스위치다

key를 목록 전용 문법으로 아는 경우가 많은데, 목록이 아닌 곳에서도 그대로 동작한다. key가 바뀌면 같은 자리, 같은 타입이어도 React는 이전 Fiber를 버리고 새로 만든다. 2번 장면이 그 예다. 처음 탭 화면에서 탭마다 입력을 따로 두고 싶다면 이렇게 쓴다.

```tsx
<AmountInput key={tab} label={tab === "personal" ? "개인 결제 금액" : "법인 결제 금액"} />
```

탭이 바뀌면 key가 바뀌고, 입력칸은 빈 값으로 새로 마운트된다. 다른 사용자의 프로필로 넘어갈 때 폼을 비우는 것, 채팅방을 옮길 때 스크롤 위치와 임시 입력을 지우는 것도 같은 방법이다. effect 안에서 `userId`가 바뀔 때마다 상태를 하나하나 초기화하는 코드보다 빠뜨릴 것이 없다. 다만 새로 마운트하면 그 아래의 DOM과 effect도 전부 다시 만들어지니, 무거운 서브트리라면 비용을 생각한다.

key에는 범위가 있다. key는 같은 부모 아래의 형제끼리만 비교된다. 그래서 전역에서 유일할 필요는 없다. 상품 목록 두 개가 같은 상품 id를 key로 써도 부모가 다르면 문제없다. 반대로 같은 부모 아래에서 key가 겹치면 React 19는 개발 모드에서 이렇게 경고하고, 어느 쪽이 남을지 보장하지 않는다.

```text
Encountered two children with the same key, `a`. Keys should be unique so that components maintain their identity across updates. Non-unique keys may cause children to be duplicated and/or omitted — the behavior is unsupported and could change in a future version.
```

같은 이유로 key는 부모를 건너가지 못한다. 칸반 보드에서 카드를 "할 일" 열에서 "진행 중" 열로 옮기면, 카드 key가 같아도 부모가 다르니 카드 컴포넌트는 언마운트됐다가 새로 마운트된다. 카드 안에 펼침 상태나 입력 중인 댓글이 있었다면 사라진다. 이런 상태는 카드 id를 키로 하는 상위 저장소에 두거나, 열을 바꿔도 같은 부모 아래 하나의 목록으로 그리는 구조로 바꿔야 유지된다.

key는 props로 전달되지 않는다. `props.key`를 읽으면 `undefined`이고, 같은 값이 필요하면 `id` 같은 다른 이름의 prop으로 한 번 더 넘긴다. 목록 안에서 Fragment로 여러 요소를 묶을 때는 `<>`에 key를 줄 수 없으니 `<Fragment key={row.id}>`로 쓴다.

## 목록은 두 번 훑는다

key가 붙은 목록을 비교하는 함수는 `react-reconciler`의 `ReactChildFiber.js`에 있는 `reconcileChildrenArray`다. 이전 자식들은 Fiber끼리 `sibling`으로 이어진 연결 리스트이고, 새 자식들은 방금 렌더링한 엘리먼트 배열이다. 둘을 맞추는 과정은 크게 두 번의 훑기로 나뉜다.

첫 번째 훑기는 앞에서부터 같은 위치끼리 맞춰 본다. 위치 i의 이전 Fiber와 새 엘리먼트의 key가 같으면 `updateSlot`이 그 Fiber를 재사용하고 다음 칸으로 간다. key가 다른 칸을 만나면 바로 멈춘다. 끝에 항목을 추가하거나 끝에서 지우는 흔한 경우는 여기서 끝난다. 새 배열이 먼저 끝나면 남은 이전 Fiber를 지우고, 이전 리스트가 먼저 끝나면 남은 새 엘리먼트를 만든다.

두 번째 훑기는 첫 훑기가 중간에서 멈췄을 때만 돈다. `mapRemainingChildren`이 남은 이전 Fiber를 key(없으면 인덱스)로 찾는 `Map`에 담는다. 그리고 남은 새 엘리먼트를 순서대로 보면서 맵에서 짝을 찾는다. 짝이 있으면 재사용하고 맵에서 뺀다. 없으면 새로 만든다. 끝까지 돈 뒤 맵에 남아 있는 Fiber는 새 목록에 없는 것이니 지운다.

재사용한 Fiber를 DOM에서 옮길지 말지는 `placeChild`가 정한다. 여기서 쓰는 값이 `lastPlacedIndex`다. "지금까지 제자리에 둔 이전 Fiber 중 가장 뒤에 있던 것의 이전 인덱스"다. 재사용한 Fiber의 이전 인덱스가 이 값보다 작으면, 예전에는 앞에 있었는데 이번에는 뒤로 와야 하니 이동으로 표시한다. 크거나 같으면 그대로 두고 `lastPlacedIndex`를 그 인덱스로 올린다.

현장에서 이 차이가 드러나는 곳은 정해져 있다. 최신 메시지가 위로 쌓이는 채팅, "최근 본 상품"처럼 고른 항목을 맨 앞으로 끌어오는 목록, 정렬 방향을 오름차순과 내림차순으로 뒤집는 표다. DOM 이동은 노드를 새로 만드는 것보다 싸지만, 줄마다 이미지나 iframe이 있으면 이동할 때 브라우저가 다시 계산할 것이 늘고 iframe은 옮기는 순간 다시 로드된다. 순서를 자주 뒤집는 큰 목록은 화면에 보이는 줄만 그리는 가상화와 함께 쓰는 편이 낫다.

## 직접 짝을 지어 보기

아래 함수는 이전 key 목록과 새 key 목록을 받아 React가 각 항목을 어떻게 다루는지 돌려준다. 새 목록 순서대로 `keep`(제자리), `move`(이동), `mount`(새로 만듦)를 넣고, 마지막에 새 목록에 없는 이전 key를 `unmount`로 넣는다. 첫 훑기를 따로 구현하지 않아도 결과는 같다. 같은 위치끼리 맞는 앞부분은 이전 인덱스가 계속 커지니 모두 `keep`이 되기 때문이다. 테스트의 기대값은 앞에서 실제 React가 부른 DOM 메서드와 이동 횟수가 같다.

## 배열 하나는 자리 하나다

JSX 자식 중에 배열이 섞이면 React는 그 배열 전체를 자리 하나로 센다. 배열 안의 항목은 그 자리 안에서 따로 key로 짝을 짓는다. 그래서 목록 앞에 조건부 요소가 있어도 목록 항목의 상태가 밀리지 않는다.

```tsx
<div>
  {showBanner && <p>banner</p>}            {/* 자리 0 */}
  {items.map((k) => <Counter key={k} name={k} />)}  {/* 자리 1: 배열 전체 */}
  <Counter name="F" />                     {/* 자리 2 */}
</div>
```

버튼을 하나씩 눌러 모두 1로 만든 뒤 배너를 껐다.

```text
arraySlot before=bannerx:1y:1F:1 after=x:1y:1F:1
```

배너 자리가 빈 자리가 됐을 뿐 배열은 계속 1번, 마지막 `Counter`는 계속 2번 자리에 있다. 반대로 `[banner, ...items]`처럼 배열을 펼쳐서 한 배열로 합치면 배너와 항목이 같은 형제 목록에 들어간다. 이때 key가 없는 배너는 자기 위치 번호를 이름으로 쓰니, 항목에 key가 있으면 괜찮지만 항목도 key가 없으면 배너가 빠질 때 모두 한 칸씩 당겨진다.

`map` 안에서 여러 요소를 돌려주려고 Fragment로 감쌀 때는 key를 Fragment에 준다. 안쪽 요소에 key를 줘도 바깥 형제 목록에서 짝을 짓는 건 Fragment이기 때문이다. 그리고 Fragment 자체도 타입이다. 컴포넌트가 한 번은 `<>...</>`를, 한 번은 `<div>`를 돌려주면 그 아래가 새로 만들어진다.

## 같은 타입이면 DOM 노드는 그대로 둔다

짝이 맞은 다음에 무엇이 일어나는지도 알아 두면 좋다. 같은 태그끼리 짝이 맞으면 React는 DOM 노드를 새로 만들지 않고, 이전 props와 새 props를 비교해 달라진 속성만 고친다. React 18까지는 렌더 단계의 `completeWork`에서 바뀐 속성 목록을 미리 계산해 두었고, React 19는 렌더 단계에서는 바뀌었다는 표시만 하고 커밋 단계의 `commitUpdate`가 이전 props와 새 props를 직접 비교하며 고친다.

```tsx
function Row({ v }) {
  return (
    <div className={v.cls} style={{ color: v.color, padding: 8 }} title={v.title}>
      <span>가격 {v.price}</span>
      <input defaultValue="메모" />
    </div>
  );
}
// cls: "row" → "row active", color: black → red, title: "a" → 없음, price: 1000 → 1200
```

사용자가 입력칸에 글을 친 상태에서 위처럼 props를 바꾸고, 커밋 동안 불린 DOM 메서드를 가로채 찍었다.

```text
text.nodeValue = "1200"
removeAttribute(type)
removeAttribute(name)
setAttribute(class, "row active")
style.color = "red"
removeAttribute(title)
input value: 사용자가 친 글
```

바뀐 것만 고쳤다. 텍스트 노드는 값만 바꿨고, `style`은 객체 전체가 아니라 바뀐 `color` 한 속성만 대입했다. `padding`은 손대지 않았다. 빠진 `title`은 속성을 지웠다. `removeAttribute(type)`과 `removeAttribute(name)`은 `input`이 업데이트될 때마다 React가 `updateInput`이라는 함수로 `value`·`type`·`name` 같은 입력 전용 속성을 따로 맞추면서 나온 호출이다. 이 컴포넌트에는 두 속성이 없으니 지우는 쪽으로 맞췄다.

마지막 줄이 중요하다. DOM 노드가 그대로라서 사용자가 친 글이 남았다. 비제어 입력칸, 스크롤 위치, 포커스, 재생 중인 `video`, CSS 트랜지션의 진행 상태처럼 DOM 노드 자체가 들고 있는 상태는 React state가 아닌데도, 같은 자리 같은 타입이면 유지되고 타입이나 key가 바뀌면 사라진다. 앞에서 본 규칙이 React state와 DOM 상태에 똑같이 적용된다.

## 타입이 바뀌는 줄 모르고 바꾸는 코드

타입이 바뀌면 서브트리가 통째로 교체된다는 규칙은 알아도, 코드가 타입을 바꾸고 있다는 걸 모르는 경우가 많다. 가장 흔한 건 컴포넌트 안에서 컴포넌트를 정의하는 것이다.

```tsx
function Form() {
  const [text, setText] = useState("");
  // 렌더링마다 새 함수가 만들어진다
  function Field() {
    return <input value={text} onChange={(e) => setText(e.target.value)} />;
  }
  return <Field />;
}
```

글자 하나를 치면 `Form`이 다시 렌더링되고, `Field`는 이전과 다른 함수 객체가 된다. React는 타입을 참조로 비교하니 다른 타입으로 보고 `input`을 버린 뒤 새로 만든다. 실제로 포커스를 준 뒤 상태를 한 번 바꾸고 확인하면 이렇게 나온다.

```text
before: same node? true focused: f
after:  same node? false focused: BODY
```

DOM 노드가 바뀌었고 포커스가 `body`로 빠졌다. 사용자는 "한 글자 칠 때마다 입력칸에서 커서가 튕겨 나간다"고 말한다. `Field`를 `Form` 밖으로 꺼내고 필요한 값은 props로 넘기면 된다.

같은 모양의 실수가 몇 가지 더 있다. 렌더링 안에서 `memo(Comp)`나 고차 컴포넌트(`withAuth(Page)`)를 호출해 감싸는 것, 렌더링 안에서 `lazy(() => import("./chart"))`를 부르는 것이 그렇다. 셋 다 매번 새 타입을 만든다. 모두 모듈 최상위에서 한 번만 만들어야 한다.

조건에 따라 감싸는 래퍼를 바꾸는 것도 같다. 툴팁이 필요할 때만 `<Tooltip>`으로 감싸면, 툴팁을 켜고 끌 때마다 안쪽 컴포넌트가 다른 부모 아래로 들어가니 새로 마운트된다. 래퍼를 항상 두고 `disabled` 같은 prop으로 끄는 편이 상태를 지킨다.

태그 이름도 타입이다. `isLink ? <a> : <button>`처럼 태그를 바꾸면 그 아래 DOM 전체가 새로 만들어진다. 반대로 같은 `input` 태그에서 `type`만 `text`에서 `password`로 바꾸면 같은 DOM 노드에서 속성만 바뀌니 입력값이 남는다. 보안상 남으면 안 되는 값이라면 key로 끊는다.

## 현장에서 재조정을 의심하는 순간

재조정 문제는 에러를 내지 않는다. 증상으로 먼저 온다. "입력할 때마다 포커스가 빠진다", "목록을 정렬했더니 체크 표시가 다른 줄에 붙어 있다", "탭을 오가면 애니메이션이 처음부터 다시 돈다", "모달을 열 때마다 내부 데이터 요청이 두 번 나간다" 같은 것들이다.

이럴 때 가장 빨리 확인하는 방법은 의심 가는 컴포넌트에 마운트 로그를 다는 것이다. 위 실험의 `Counter`처럼 빈 의존성 배열의 effect에서 `mount`와 `unmount`를 찍는다. 업데이트만 일어나야 할 동작에서 `unmount`와 `mount`가 연달아 찍히면 자리나 타입이 바뀌고 있다는 뜻이다. 개발 모드의 `StrictMode`는 첫 마운트 직후에 일부러 한 번 언마운트했다가 다시 마운트하니, 처음 한 쌍은 무시하고 동작을 일으킨 뒤의 로그만 본다.

React DevTools의 Components 탭에서는 트리에서 컴포넌트를 골라 key와 부모 경로를 볼 수 있다. 같은 자리에 있어야 할 컴포넌트가 동작 전후로 다른 부모 아래 나타나거나, 이름 옆의 key가 렌더링마다 바뀌면 원인이 거기 있다. 렌더할 때마다 `crypto.randomUUID()`로 key를 만드는 코드가 의외로 자주 나온다.

key 경고도 그냥 넘기지 않는다. 콘솔의 `Each child in a list should have a unique "key" prop.`은 어느 컴포넌트의 render에서 났는지 함께 알려 준다. 경고만 끄려고 인덱스를 넣으면 경고는 사라지지만 동작은 key가 없을 때와 같다. 인덱스 key가 어떤 장면에서 상태를 어긋나게 하는지는 [React는 언제 다시 그리나](/posts/react-rerender)의 그림으로 확인할 수 있다.

고칠 때 던질 질문은 하나다. "이 상태는 무엇에 붙어 있어야 하나." 화면의 자리에 붙어야 하면 형제 순서와 타입을 고정하고, 데이터 항목에 붙어야 하면 그 데이터의 id를 key로 쓰고, 화면이 바뀌어도 살아남아야 하면 트리 밖이나 위로 올린다.

## 짝을 짓는 규칙 하나로

처음 두 장면은 같은 규칙에서 나왔다. React는 이전 Fiber를 부모, 형제 사이의 이름(key나 순서), 타입으로 찾아 다시 쓰고, 상태는 그 Fiber에 붙어 있다. 개인·법인 탭은 세 가지가 모두 같아서 상태가 남았고, 배너 화면은 형제 순서가 당겨져서 상태가 지워졌다. 목록에서는 key 맵과 `lastPlacedIndex`로 이동을 정하는데, 최소 이동이 아니라 앞에서부터 한 번 훑는 규칙이라 맨 뒤를 맨 앞으로 옮기면 비싸다. 이 비교가 실제로 어떤 단위로 쪼개져 실행되고 언제 DOM에 반영되는지는 [Fiber와 렌더·커밋 단계](/posts/react-fiber-render-commit)에서 이어진다.

## 면접에서 나올 만한 질문

### React의 재조정은 어떻게 O(n)으로 동작하나요?

두 가지 가정을 둔다. 타입이 다른 엘리먼트는 서브트리를 통째로 교체하고, 형제 사이에서는 key로 같은 자식을 식별한다. 그래서 트리를 같은 깊이끼리만 비교하고 다른 부모로 옮겨 간 서브트리는 찾지 않는다. 대신 감싸는 래퍼 하나만 바뀌어도 그 아래가 전부 새로 마운트된다.

### 컴포넌트의 상태는 어디에 저장되고, 언제 유지되나요?

함수가 아니라 트리의 자리마다 있는 Fiber 노드의 `memoizedState`에 저장된다. 부모가 같고, 형제 사이의 이름(key 또는 순서)이 같고, 타입이 같으면 React가 그 Fiber를 다시 써서 상태가 유지된다. props가 달라져도 세 조건이 맞으면 상태는 남는다.

### 삼항 연산자로 두 컴포넌트를 바꿔 끼웠는데 상태가 남았습니다. 왜 그렇고 어떻게 고치나요?

두 갈래가 같은 자리에 같은 타입을 놓으면 React는 같은 컴포넌트의 props 변경으로 본다. 갈래마다 다른 key를 주면 자리가 새로 만들어져 상태가 초기화된다. 반대로 상태를 지켜야 하는데 지워진다면 형제 순서가 갈래마다 달라지지 않았는지 보고, `cond && <A />`처럼 자리를 고정한다.

### key는 전역에서 유일해야 하나요?

아니다. key는 같은 부모 아래 형제끼리만 비교되니 형제 안에서만 유일하면 된다. 같은 부모 아래에서 겹치면 어느 쪽이 남을지 보장되지 않아 항목이 중복되거나 빠질 수 있다. key는 부모를 건너가지 못하므로 다른 부모로 옮긴 컴포넌트는 key가 같아도 새로 마운트된다.

### key가 있는 목록은 어떤 과정으로 비교하나요?

`reconcileChildrenArray`가 먼저 앞에서부터 같은 위치끼리 key를 맞춰 보고, 어긋나면 남은 이전 Fiber를 key 맵에 담는다. 새 목록을 순서대로 보며 맵에서 짝을 찾아 재사용하고, 맵에 남은 것은 지운다. 이동 여부는 `lastPlacedIndex`와 이전 인덱스를 비교해 정한다.

### 그럼 React는 최소한의 DOM 이동을 계산하나요?

아니다. 한 방향으로 훑는 탐욕 규칙이라 맨 앞을 맨 뒤로 보내면 한 번이지만, 맨 뒤를 맨 앞으로 데려오면 나머지 n-1개를 옮긴다. 실제로 `abcd → dabc`에서 `appendChild`가 세 번 불렸다. Vue 3는 최장 증가 부분 수열로 이동을 줄이는 쪽을 택했다.

### 입력할 때마다 포커스가 빠지는 버그는 어디부터 보나요?

컴포넌트가 렌더링마다 새로 마운트되고 있는지부터 본다. 컴포넌트 안에서 다른 컴포넌트를 정의했거나, 렌더 중에 `memo`·HOC·`lazy`로 새 타입을 만들거나, key를 렌더링마다 새로 만드는 경우가 흔하다. 마운트 로그를 달아 입력 한 번에 unmount와 mount가 찍히는지 확인하고, 타입을 모듈 최상위로 옮긴다.
