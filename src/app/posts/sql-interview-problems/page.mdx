SQL 코딩 테스트에서 "두 번째로 비싼 강의의 가격을 구하라"는 문제를 받는다. 가장 먼저 떠오르는 답은 이것이다.

```sql
SELECT price FROM courses ORDER BY price DESC LIMIT 1 OFFSET 1;
```

```text
 price
-------
 90000
(1 row)
```

지금 데이터에서는 맞다. 그런데 면접관이 "튜닝 강의 가격이 12만 원으로 올라서 가장 비싼 강의가 둘이 되면요?" 하고 묻는다. 같은 쿼리가 12만 원을 두 번째로 비싼 가격이라고 답한다. 그리고 "두 번째가 없으면 무엇을 돌려주나요?"가 이어진다. SQL 면접 문제는 대부분 쿼리 한 줄보다 이런 꼬리 질문(동점, 빈 결과, NULL, 중복)에서 갈린다.

이 글은 자주 나오는 여섯 문제를 같은 데이터로 푼다. 두 번째로 큰 값, 그룹별 상위 N개, 중복 제거, 누적 합계, 연속 구간(gaps and islands), 3일 이상 연속이다. 문제마다 흔한 오답, 맞는 답, 꼬리 질문 순서로 간다. 각 문제가 기대는 문법은 시리즈의 다른 글에 자세히 있어서 여기서는 링크로 넘긴다. 실행 순서는 [SELECT의 논리적 처리 순서](/posts/sql-logical-order), NULL과 집계는 [집계 함정 글](/posts/sql-aggregation-pitfalls), 서브쿼리는 [서브쿼리 글](/posts/sql-subqueries-exists-lateral), 순위와 프레임은 [PostgreSQL 윈도우 함수 글](/posts/sql-window-functions-pg)과 [SQLD 윈도우 함수 글](/posts/sqld-window-functions)이다.

기준은 Ubuntu 24.04의 PostgreSQL 16.15이고 출력은 모두 실제로 돌린 결과다. MySQL 8과 문법이 다르면 짧게 적는다.

## 두 번째로 비싼 가격

처음 답이 동점에서 틀리는 걸 확인한다. 실제 데이터를 건드리지 않게 트랜잭션 안에서 가격을 바꾸고 되돌린다.

```sql
BEGIN;
UPDATE courses SET price = 120000 WHERE id = 2;                  -- 가장 비싼 강의가 둘이 된다
SELECT price FROM courses ORDER BY price DESC LIMIT 1 OFFSET 1;  -- 처음 답
```

```text
 price
--------
 120000
(1 row)
```

`OFFSET 1`은 두 번째 "행"을 고른다. 두 번째로 큰 "값"을 원했다면 같은 값을 먼저 하나로 줄여야 한다. 고치는 방법이 셋 있고, 셋 다 70000을 낸다.

```sql
-- 1) 값을 하나씩 남기고 건너뛴다
SELECT DISTINCT price FROM courses ORDER BY price DESC LIMIT 1 OFFSET 1;

-- 2) 가장 큰 값보다 작은 것 중 가장 큰 값
SELECT max(price) AS second FROM courses WHERE price < (SELECT max(price) FROM courses);

-- 3) 동점에 같은 등수를 주는 dense_rank
SELECT DISTINCT price FROM (
  SELECT price, dense_rank() OVER (ORDER BY price DESC) AS r FROM courses
) t WHERE r = 2;
ROLLBACK;
```

```text
 price
-------
 70000
(1 row)
```

아래 그림에서 다음을 누르면 `OFFSET`과 `dense_rank`가 같은 줄에서 어떻게 다르게 세는지 보인다.

꼬리 질문은 두 가지가 단골이다. 첫째, 두 번째가 없을 때다. `project` 분류에는 강의가 하나뿐이다.

```sql
SELECT DISTINCT price FROM courses WHERE category = 'project'
ORDER BY price DESC LIMIT 1 OFFSET 1;                                           -- 0행

SELECT max(price) AS second FROM courses WHERE category = 'project'
  AND price < (SELECT max(price) FROM courses WHERE category = 'project');      -- NULL 한 행
```

```text
 price
-------
(0 rows)

 second
--------
 (null)
(1 row)
```

`LIMIT`과 `dense_rank`는 0행을, `max`는 NULL 한 행을 낸다. 행이 없을 때 집계가 NULL 한 행을 돌려주는 이유는 [집계 함정 글](/posts/sql-aggregation-pitfalls#행이-하나도-없을-때)에 있다. 문제가 "없으면 NULL"을 요구하면 `max` 방식이나, 0행 쿼리를 스칼라 서브쿼리로 감싼 `SELECT (SELECT ... LIMIT 1 OFFSET 1) AS second`를 쓴다. 둘째, N번째로 일반화하라는 요청이다. `max` 방식은 N이 커지면 중첩이 깊어지니 `dense_rank`의 `r = N`이 깔끔하다. `r = 3`이면 지금 데이터에서 70000이다. MySQL 8도 `dense_rank`와 `LIMIT ... OFFSET`을 그대로 쓴다.

## 카테고리마다 비싼 강의 두 개

그룹별 상위 N개는 `PARTITION BY`로 그룹마다 번호를 매기고 바깥에서 거른다. 윈도우 함수는 `WHERE`에 못 쓰니 서브쿼리로 감싼다.

```sql
SELECT category, title, price FROM (
  SELECT category, title, price,
         row_number() OVER (PARTITION BY category ORDER BY price DESC, id) AS rn
  FROM courses
) t WHERE rn <= 2 ORDER BY category, price DESC;
```

```text
 category |      title      | price
----------+-----------------+--------
 db       | PostgreSQL 튜닝 |  90000
 db       | SQL 기초        |  30000
 frontend | React 입문      |  50000
 infra    | Docker 실전     |  70000
 infra    | 100% 실습 Git   |  20000
 project  | 백엔드 실전     | 120000
(6 rows)
```

강의가 하나뿐인 분류도 그 하나가 나온다. 면접에서는 세 가지를 먼저 말해 두면 좋다. 동점일 때 두 개를 정확히 원하면 `row_number`에 `id`를 덧붙이고, 동점자를 다 원하면 `rank`를 쓴다. 조건은 `rn <= 2` 모양으로 써야 PostgreSQL 15부터 `Run Condition` 최적화를 받는다. 그룹이 적고 그룹마다 행이 아주 많으면 `LATERAL`과 인덱스가 더 빠를 수 있다. 셋 다 [윈도우 함수 글](/posts/sql-window-functions-pg#그룹별-상위-n개는-15부터-일찍-멈춘다)에서 실행 계획으로 확인했다.

## 같은 결제가 두 번 들어갔다

결제 웹훅이 재시도되면서 같은 결제가 다시 저장됐다. 트랜잭션 안에서 2, 5, 7번 결제를 한 번씩, 5번은 한 번 더 복제해 상황을 만든다.

```sql
BEGIN;
INSERT INTO payments (enrollment_id, amount, paid_at)
SELECT enrollment_id, amount, paid_at FROM payments WHERE id IN (2, 5, 7);
INSERT INTO payments (enrollment_id, amount, paid_at)
SELECT enrollment_id, amount, paid_at FROM payments WHERE id = 5;

-- 무엇이 겹쳤는지부터 본다
SELECT enrollment_id, amount, paid_at, count(*), array_agg(id ORDER BY id) AS ids
FROM payments
GROUP BY enrollment_id, amount, paid_at
HAVING count(*) > 1
ORDER BY min(id);
```

```text
 enrollment_id | amount |        paid_at         | count |    ids
---------------+--------+------------------------+-------+-----------
             2 |  45000 | 2026-10-01 00:01:00+09 |     2 | {2,13}
             4 |  50000 | 2026-10-12 09:01:00+09 |     3 | {5,14,16}
             6 |  90000 | 2026-10-20 21:01:00+09 |     2 | {7,15}
(3 rows)
```

여기서 첫 번째 꼬리 질문이 나온다. "무엇이 같으면 중복인가." `enrollment_id`와 `amount`만으로 묶으면 할부 결제가 중복으로 잡힌다.

```sql
SELECT enrollment_id, amount, count(*), array_agg(id ORDER BY id) AS ids
FROM payments GROUP BY enrollment_id, amount HAVING count(*) > 1 ORDER BY 1;   -- 복제 전 원본에서
```

```text
 enrollment_id | amount | count |  ids
---------------+--------+-------+-------
             2 |  45000 |     2 | {2,3}
             8 |  35000 |     2 | {8,9}
(2 rows)
```

2번과 3번은 10월과 11월에 나눠 낸 정상 할부다. 이걸 지우면 매출이 사라진다. 중복의 기준은 업무가 정한다. 지금은 결제 시각까지 같아야 같은 결제다.

지우기는 그룹마다 `row_number`를 매기고 2번 이후를 지운다. 어느 행을 남길지(`ORDER BY id`면 가장 먼저 들어온 것)를 순서로 정한다.

```sql
DELETE FROM payments
WHERE id IN (
  SELECT id FROM (
    SELECT id, row_number() OVER (PARTITION BY enrollment_id, amount, paid_at ORDER BY id) AS rn
    FROM payments
  ) t WHERE rn > 1                       -- 그룹의 첫 행만 남긴다
)
RETURNING id;
```

```text
 id
----
 13
 14
 15
 16
(4 rows)

DELETE 4
```

셀프 조인으로 "나보다 `id`가 작은 같은 행이 있으면 지운다"(`DELETE FROM payments a USING payments b WHERE ... AND a.id > b.id`)도 같은 결과를 낸다. 다만 여기에 함정이 하나 있다. `enrollment_id`가 NULL인 12번 결제(수강 기록과 연결이 끊긴 결제)를 복제하면 `a.enrollment_id = b.enrollment_id`는 NULL끼리 비교라 참이 되지 않아 `DELETE 0`이다. `IS NOT DISTINCT FROM`으로 비교해야 지워진다. `row_number`의 `PARTITION BY`는 NULL끼리를 한 묶음으로 보니 이 문제가 없다.

다 지웠으면 다시 쌓이지 않게 막는다.

```sql
CREATE UNIQUE INDEX payments_dedupe_idx ON payments (enrollment_id, amount, paid_at);
INSERT INTO payments (enrollment_id, amount, paid_at)
SELECT enrollment_id, amount, paid_at FROM payments WHERE id = 2;
ROLLBACK;
```

```text
ERROR:  duplicate key value violates unique constraint "payments_dedupe_idx"
DETAIL:  Key (enrollment_id, amount, paid_at)=(2, 45000, 2026-10-01 00:01:00+09) already exists.
```

유니크 인덱스도 기본으로 NULL끼리는 다르다고 본다. NULL 결제의 중복까지 막으려면 PostgreSQL 15부터 되는 `NULLS NOT DISTINCT`를 붙인다. 아래 그림에서 다음을 누르면 중복을 찾고 지우고 막는 순서가 보인다.

## 수강생별 누적 결제액

수강생마다 결제할 때마다 누적 금액을 붙인다.

```sql
SELECT e.student_id, p.paid_at::date AS day, p.amount,
       sum(p.amount) OVER (PARTITION BY e.student_id ORDER BY p.paid_at, p.id
                           ROWS UNBOUNDED PRECEDING) AS running   -- 처음부터 지금 행까지
FROM payments p JOIN enrollments e ON e.id = p.enrollment_id
WHERE e.student_id IN (1, 4)
ORDER BY e.student_id, p.paid_at;
```

```text
 student_id |    day     | amount | running
------------+------------+--------+---------
          1 | 2026-09-28 |  30000 |   30000
          1 | 2026-10-01 |  45000 |   75000
          1 | 2026-10-15 |  50000 |  125000
          1 | 2026-11-01 |  45000 |  170000
          4 | 2026-10-20 |  90000 |   90000
          4 | 2026-11-01 |  50000 |  140000
          4 | 2026-11-02 | -50000 |   90000
(7 rows)
```

choi(4번)는 환불이 음수라 누적이 내려간다. 면접에서 꼭 짚을 것은 `ROWS`와 `ORDER BY`의 `p.id`다. 프레임을 생략하면 `RANGE`라서 같은 시각의 결제가 있을 때 둘에게 같은 누적이 붙는다([SQLD 윈도우 함수 글](/posts/sqld-window-functions#기본-프레임은-동점을-한꺼번에-더한다)). `ORDER BY`에 `id`가 없으면 동점의 순서도 정해지지 않는다.

꼬리 질문은 "윈도우 함수 없이 풀 수 있나"다. 행마다 나보다 앞선 결제를 더하는 상관 서브쿼리로 같은 결과가 나온다.

```sql
SELECT e.student_id, p.paid_at::date AS day, p.amount,
       (SELECT sum(p2.amount)
        FROM payments p2 JOIN enrollments e2 ON e2.id = p2.enrollment_id
        WHERE e2.student_id = e.student_id
          AND (p2.paid_at, p2.id) <= (p.paid_at, p.id)) AS running   -- 행 비교로 순서를 정한다
FROM payments p JOIN enrollments e ON e.id = p.enrollment_id
WHERE e.student_id IN (1, 4)
ORDER BY e.student_id, p.paid_at;
```

결과는 위와 같은 7행이다. 다만 행마다 앞선 행을 다시 더하니 한 사람의 결제가 n건이면 n²에 비례해 읽는다. 윈도우 함수는 정렬 한 번 뒤 한 줄씩 더한다. "매달 새로 시작하는 누적"으로 바꾸라면 `PARTITION BY e.student_id, date_trunc('month', p.paid_at)`처럼 묶음을 더 잘게 나눈다.

## 연속 출석 구간 찾기

"수강생마다 연속으로 출석한 구간의 시작일, 끝일, 일수를 구하라." gaps and islands(빈틈과 섬)라고 부르는 문제다. 연속된 날짜를 하나의 섬으로 묶어야 하는데, 섬마다 같은 값을 갖는 열쇠가 필요하다.

요령은 이렇다. 연속된 날짜는 하루씩 늘고, 그 날짜에 매긴 순번도 하나씩 는다. 둘을 빼면 연속인 동안은 같은 값이 나오고, 하루라도 빠지면 날짜만 더 많이 늘어서 값이 바뀐다.

```sql
SELECT student_id, day,
       row_number() OVER (PARTITION BY student_id ORDER BY day) AS rn,
       day - row_number() OVER (PARTITION BY student_id ORDER BY day)::int AS grp   -- date - int = date
FROM attendance WHERE student_id IN (1, 4) ORDER BY student_id, day;
```

## 3일 이상 연속으로 나온 사람

"3일 이상 연속으로 출석한 수강생과 가장 긴 연속 일수를 구하라." 앞의 섬을 사람별로 한 번 더 묶으면 된다.

```sql
WITH d AS (SELECT DISTINCT student_id, day FROM attendance),
g AS (
  SELECT student_id, day,
         day - row_number() OVER (PARTITION BY student_id ORDER BY day)::int AS grp
  FROM d
)
SELECT s.name, max(cnt) AS longest
FROM (SELECT student_id, count(*) AS cnt FROM g GROUP BY student_id, grp) x   -- 섬마다 일수
JOIN students s ON s.id = x.student_id
GROUP BY s.name HAVING max(cnt) >= 3                                          -- 사람마다 가장 긴 섬
ORDER BY longest DESC, s.name;
```

```text
 name | longest
------+---------
 lee  |       4
 choi |       3
 kim  |       3
(3 rows)
```

`DISTINCT`를 빼면 choi는 섬이 1일과 2일로 갈라져 목록에서 빠진다. 중복 없는 테스트 데이터에서는 통과하는 오답이다. "로그인 기록에서 3일 연속 로그인한 사용자"처럼 시각 데이터라면 날짜로 자르는 단계가 하나 더 붙고, 어느 시간대 기준의 하루인지를 먼저 묻는다(시간대가 결과를 바꾸는 모습은 [WHERE 연산자 글](/posts/sql-filtering-operators#같은-쿼리-다른-시간대)에 있다).

`lag`로 "어제도 왔나"를 두 번 보는 풀이(`lag(day, 2) = day - 2`)도 있다. 정확히 "3일 연속"만 묻는다면 짧지만, "가장 긴 연속"이나 "N일"로 바뀌면 다시 짜야 한다. 섬 열쇠 방식은 `HAVING`의 숫자만 바꾸면 된다.

## 문제를 받으면 먼저 묻는 것

쿼리를 쓰기 전에 조건을 확인하는 것도 평가 대상이다. 위 여섯 문제에서 답을 바꾼 질문은 몇 가지로 모인다. 동점이 있을 때 몇 개를 원하는지(`row_number`, `rank`, `dense_rank`), 결과가 없을 때 0행인지 NULL 한 행인지, NULL이 키에 있을 때 같은 값으로 볼지(`=`와 `IS NOT DISTINCT FROM`), 무엇이 같으면 중복인지(할부), 같은 날 여러 행이 있을 수 있는지(출석 중복), 날짜는 어느 시간대 기준인지다.

실무에서도 같은 질문이 그대로 장애가 된다. 리포트의 "2등 강의"가 어느 날 1등과 같은 강의로 나오거나, 중복 정리 배치가 할부 결제를 지우거나, 연속 출석 이벤트 대상자가 한 명 빠지는 식이다. 숫자가 이상하다는 문의를 받으면 먼저 그 쿼리가 이 질문들에 어떻게 답하고 있는지 본다.

## 도구는 몇 개뿐이다

여섯 문제는 `dense_rank`로 서로 다른 값을 세고, `row_number`로 그룹 안에서 한 줄씩 번호를 매기고, `sum OVER (... ROWS ...)`로 앞에서부터 더하고, "값 - 순번"으로 연속 구간의 열쇠를 만드는 것으로 풀렸다. 답을 가르는 건 쿼리보다 앞의 확인이다. 동점, 빈 결과, NULL, 중복의 기준, 같은 날의 여러 행을 먼저 묻고 그에 맞는 도구를 고른다. 이 도구들의 실행 계획과 성능은 [윈도우 함수 글](/posts/sql-window-functions-pg)에, 계층을 따라가는 문제는 [재귀 CTE 글](/posts/sql-cte-recursive)에, 자주 쓰는 결과를 저장해 두는 방법은 [뷰와 머티리얼라이즈드 뷰 글](/posts/sql-views-materialized)에 이어진다.

## 면접에서 나올 만한 질문

### 두 번째로 큰 값을 구하는 쿼리를 써 보세요. 동점이 있으면요?

`LIMIT 1 OFFSET 1`은 두 번째 행을 고르므로 가장 큰 값이 둘이면 그 값을 다시 냅니다. 값 기준이면 `DISTINCT`로 먼저 줄이거나, `max(price) WHERE price < (SELECT max(price) ...)`를 쓰거나, `dense_rank() = 2`를 씁니다. N번째로 일반화하기엔 `dense_rank`가 가장 깔끔합니다.

### 결과가 없을 때 NULL을 돌려줘야 한다면요?

`LIMIT`이나 `dense_rank` 방식은 0행을 내고, `max` 같은 집계는 행이 없어도 NULL 한 행을 냅니다. 0행 쿼리를 `SELECT (서브쿼리) AS second`처럼 스칼라 서브쿼리로 감싸도 NULL 한 행이 됩니다. 문제를 받으면 둘 중 무엇을 원하는지 먼저 확인합니다.

### 그룹별 상위 N개는 어떻게 구하나요?

`row_number() OVER (PARTITION BY 그룹 ORDER BY 기준, id)`로 번호를 매기고 서브쿼리 바깥에서 `rn <= N`으로 거릅니다. 동점자를 모두 원하면 `rank`를 쓰고, 정확히 N개면 `ORDER BY`에 고유 컬럼을 붙입니다. 그룹이 적고 그룹마다 행이 아주 많다면 `LATERAL`과 인덱스로 그룹마다 N행만 읽는 쪽이 빠를 수 있습니다.

### 중복 행을 하나만 남기고 지우려면 어떻게 하나요?

중복의 기준 컬럼으로 `PARTITION BY`하고 남길 행의 순서(`ORDER BY id`)로 `row_number`를 매겨 `rn > 1`인 행을 지웁니다. 셀프 조인 `DELETE ... USING`도 되지만 키에 NULL이 있으면 `=`가 참이 되지 않아 `IS NOT DISTINCT FROM`이 필요합니다. 지운 뒤에는 유니크 인덱스로 다시 쌓이지 않게 막고, 앱은 `ON CONFLICT DO NOTHING`이나 멱등성 키로 재시도를 흡수합니다.

### 중복 판단 기준을 잘못 잡으면 어떤 일이 생기나요?

정상 데이터를 지웁니다. 같은 수강에 같은 금액이 두 번 있는 결제는 웹훅 중복일 수도 있지만 할부일 수도 있어서, 결제 시각이나 외부 결제 ID까지 같아야 중복으로 봤습니다. 지우기 전에 `GROUP BY ... HAVING count(*) > 1`로 대상을 눈으로 확인하고, 트랜잭션 안에서 `RETURNING`으로 지워지는 행을 본 뒤 커밋합니다.

### 누적 합계를 윈도우 함수로 구할 때 주의할 점은요?

프레임을 `ROWS UNBOUNDED PRECEDING`으로 명시하고 `ORDER BY`에 고유 컬럼을 넣습니다. 생략하면 기본 프레임이 `RANGE`라서 정렬 값이 같은 행들이 같은 누적을 받습니다. 윈도우 함수 없이 상관 서브쿼리로도 풀 수 있지만 행마다 앞선 행을 다시 더해 n²에 비례해 느려집니다.

### 연속된 날짜 구간(gaps and islands)은 어떻게 찾나요?

날짜에서 그 사람 안의 순번(`row_number`)을 빼면 연속인 동안 같은 값이 나오고, 하루라도 빠지면 값이 바뀝니다. 이 값을 열쇠로 `GROUP BY`해서 `min`, `max`, `count`로 구간을 냅니다. 같은 날 행이 여러 개면 순번만 늘어 섬이 갈라지니 `DISTINCT`로 먼저 줄이거나 `dense_rank`를 씁니다.

### "3일 연속 로그인한 사용자"를 구하라는 문제에서 먼저 확인할 것은요?

로그인 시각을 어느 시간대 기준의 날짜로 자를지, 하루에 여러 번 로그인한 기록을 어떻게 다룰지입니다. 그다음 섬 열쇠로 연속 구간을 만들고 `HAVING count(*) >= 3`으로 거릅니다. `lag(day, 2)`로 이틀 전을 보는 풀이도 있지만 "가장 긴 연속"이나 다른 N으로 바뀌면 다시 짜야 해서 열쇠 방식이 더 넓게 쓰입니다.
