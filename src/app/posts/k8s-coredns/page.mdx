<EasyIntro>
  Pod가 바깥 주소 하나를 부를 때 이름 풀이에서만 가끔 5초가 사라지는 일이 있다. 쿠버네티스 안에서 이름을 주소로 바꿔 주는 것이 CoreDNS인데, Pod가 받는 이름 풀이 설정 때문에 이름 하나를 물어도 질문이 여덟 개로 불어난다. 그중 여섯 개는 없는 이름이라는 답만 받는다.

  이유는 Pod 설정에 클러스터 안 이름을 먼저 붙여 보라는 규칙이 세 줄 있고, 점이 다섯 개 미만인 이름은 그 규칙을 다 거쳐 보기 때문이다. 친구 이름을 들으면 같은 반, 같은 학년, 같은 학교 순서로 먼저 찾아보고 나서야 전화번호부를 펴는 것과 같다. CoreDNS는 클러스터 안 이름은 직접 답하고 나머지는 바깥으로 넘긴다.

  5초 지연은 두 질문이 동시에 나가다 하나가 버려져서 다시 물을 때까지 기다린 흔적이다. 이름 끝에 점을 붙이거나 규칙을 거치는 기준을 낮추면 질문이 줄고, 기계마다 캐시를 두면 그 길 자체를 없앨 수 있다.
</EasyIntro>

결제 API(`api.example.com`)를 부르는 Pod 하나에서 응답이 가끔 5초씩 늦는다. 앱 쪽 타이머를 찍어 보니 HTTP 요청이 아니라 이름 풀이에서 시간이 사라진다. CoreDNS에 `log`를 켜 보니 이 Pod가 이름 하나를 물을 때마다 질의가 여덟 줄씩 찍히고, 그중 여섯 줄이 NXDOMAIN이다.

여덟 개의 정체는 Pod의 `/etc/resolv.conf`에 있는 `search` 세 줄과 `ndots:5`이고, 5초의 정체는 리졸버의 재시도 시간이다. 이 글은 Pod가 이름을 물을 때 무엇이 일어나는지, CoreDNS가 Service와 Pod 이름을 어떻게 답하는지, 질의가 불어나고 느려지는 이유와 NodeLocal DNSCache가 그걸 어떻게 줄이는지를 실제 질의 캡처로 따라간다.

DNS 자체(재귀 리졸버, 레코드 종류, TTL, UDP에서 TCP로 넘어가는 경우)는 [DNS 글](/posts/dns)에서 다뤘다. Service 타입마다 DNS 답이 어떻게 다른지(ClusterIP, headless, ExternalName)는 [Service 글](/posts/k8s-service-types#headless와-externalname-가상-ip-없이-이름만)에 있으니 여기서는 짧게 넘긴다. NetworkPolicy가 DNS를 막는 문제는 [NetworkPolicy 글](/posts/k8s-network-policy)에 있다.

실습은 kwok로 띄운 실제 kube-apiserver(v1.30.4)에 CoreDNS 1.11.3을 붙여 돌렸다. Corefile은 kubeadm 기본 설정과 같고, kubernetes 플러그인이 실제 API 서버를 watch해서 답한다. 다만 클러스터 DNS 주소는 `10.96.0.10` 대신 루프백의 `127.0.10.10`에 띄웠고, 바깥 DNS는 `example.com`만 답하는 CoreDNS를 `127.0.10.53`에 하나 더 띄워 대신했다. 질의는 glibc 리졸버(Python의 `getaddrinfo`)로 보내고 tcpdump로 잡았다. 아래 캡처와 로그, 메트릭은 그 실습에서 나온 것이다.

## Pod가 받는 resolv.conf

Pod가 뜰 때 kubelet이 `/etc/resolv.conf`를 써 넣는다. `default` 네임스페이스의 Pod라면 이런 모양이다(예시).

```text
search default.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5
```

세 줄이 각각 무엇을 정하는지 눌러 보자.

어떤 값을 넣을지는 Pod의 `dnsPolicy`가 정한다. 기본값 `ClusterFirst`가 위의 모양이다. 이름이 헷갈리는 `Default`는 클러스터 DNS가 아니라 노드의 resolv.conf를 그대로 물려받는다. `hostNetwork: true`인 Pod는 `ClusterFirst`를 줘도 노드 설정을 받아서, 클러스터 이름을 풀려면 `ClusterFirstWithHostNet`을 명시해야 한다. `None`은 아무것도 넣지 않고 `dnsConfig`로 전부 직접 적는다. 그래서 `dnsConfig`가 없으면 API 서버가 거절한다.

```text
The Pod "bad-dns" is invalid: spec.dnsConfig: Required value: must provide `dnsConfig` when `dnsPolicy` is None
```

## 이름 하나에 질의 여덟 개

처음 장면을 그대로 재현했다. 위 resolv.conf로 `api.example.com`을 `getaddrinfo`로 풀면서 클러스터 DNS로 가는 질의를 모두 잡았다.

```bash
# 클러스터 DNS로 가는 질의만 캡처한다 (실습에서는 127.0.10.10이 클러스터 DNS)
sudo tcpdump -ni lo -l 'udp and dst host 127.0.10.10 and dst port 53'

# 다른 창에서: Pod와 같은 resolv.conf로 이름을 푼다
python3 -c 'import socket; print(sorted({a[4][0] for a in socket.getaddrinfo("api.example.com", 443)}))'
```

### 왜 5인가, 그리고 줄이는 법

`ndots:5`는 클러스터 안 이름을 짧게 써도 search로 풀리게 하려고 넉넉하게 잡은 값이다. `web`, `web.shop`, `web.shop.svc`처럼 점이 몇 개든 클러스터 안의 이름이면 search가 먼저 맞힌다. 같은 네임스페이스의 `web`은 첫 질의에서 끝난다.

```text
A? web.default.svc.cluster.local.
AAAA? web.default.svc.cluster.local.
```

반대로 바깥 이름은 거의 항상 search를 다 돌아야 한다. 줄이는 방법은 세 가지다.

첫째, 바깥 이름 끝에 점을 붙여 완전한 이름으로 쓴다. `api.example.com.`은 search를 건너뛰어 질의가 두 개로 끝난다. 설정 파일 한 줄로 끝나지만, HTTP Host 헤더나 TLS 인증서 이름에 점이 붙은 채로 들어가 문제를 일으키는 라이브러리가 있어서 써 보고 확인한다.

```text
A? api.example.com.
AAAA? api.example.com.
```

둘째, Pod의 `dnsConfig`로 ndots를 낮춘다. 2로 낮추면 점이 둘 이상인 `api.example.com`은 그대로 먼저 묻는다.

```yaml
spec:
  dnsPolicy: ClusterFirst
  dnsConfig:
    options:
      - name: ndots
        value: "2"            # value 칸의 타입은 문자열이라 따옴표로 감싼다
```

```text
A? api.example.com.
AAAA? api.example.com.
```

대신 점이 하나인 이름(`redis.cache` 같은 다른 네임스페이스 Service)은 여전히 search를 먼저 돌고, 점이 둘인 클러스터 안 이름(`web.shop.svc`)은 바깥에 먼저 물었다가 NXDOMAIN을 받고 나서야 search로 돌아온다. 클러스터 안 이름은 짧게, 바깥 이름은 길게 쓰는 서비스에 맞는 값이다.

셋째, CoreDNS의 `autopath` 플러그인이 서버에서 search 확장을 대신해 첫 질의에 바로 최종 답을 준다. 질의를 보낸 Pod의 네임스페이스를 알아야 해서 kubernetes 플러그인을 `pods verified`로 바꿔야 하는데, 그러면 CoreDNS가 모든 Pod를 watch해 메모리를 꽤 쓴다. 큰 클러스터에서는 부담을 따져 보고 켠다.

이 규칙을 코드로 옮겨 보자. glibc 리졸버가 이름을 묻는 순서를 돌려주는 함수다.

리졸버는 이 순서대로 묻다가 처음 답을 받은 곳에서 멈춘다. `web`은 첫 칸에서 끝나고, `redis.cache`는 둘째 칸 `redis.cache.svc.cluster.local`에서 끝난다. 처음 칸에서 NXDOMAIN이 아니라 시간 초과가 나면 다음 칸으로 가기 전에 timeout만큼 기다린다는 것도 기억해 두자. 그게 다음 절의 5초다.

## CoreDNS가 답을 만드는 법

CoreDNS는 플러그인을 이어 붙인 DNS 서버다. kubeadm이 만드는 기본 Corefile은 이렇고, 실습도 주소만 바꿔 같은 설정으로 돌렸다.

```text
.:53 {
    errors
    health {
       lameduck 5s
    }
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
       pods insecure
       fallthrough in-addr.arpa ip6.arpa
       ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf {
       max_concurrent 1000
    }
    cache 30
    loop
    reload
    loadbalance
}
```

질의 하나는 kubernetes 플러그인부터 본다. `cluster.local` 아래 이름이면 API 서버에서 watch해 메모리에 들고 있는 Service·EndpointSlice로 바로 답한다. API 서버에 매번 묻지 않는다. 역방향 조회(`in-addr.arpa`)는 클러스터 주소면 답하고, 아니면 `fallthrough`로 다음 플러그인에 넘긴다. 그 밖의 이름은 `forward`가 바깥 DNS로 넘긴다. `/etc/resolv.conf`는 CoreDNS Pod 자신의 것이고, CoreDNS는 `dnsPolicy: Default`로 떠서 노드의 DNS 설정을 물려받는다. `cache 30`은 답을 최대 30초 기억하고, `loadbalance`는 A 레코드 여러 개의 순서를 매번 섞는다.

Pod 이름 레코드는 `pods insecure` 모드라서 API 서버를 확인하지 않고 이름에서 IP를 그대로 만들어 답한다. 아무 IP 모양의 이름이든 답이 나온다는 뜻이다. Pod IP의 역방향 조회는 그 Pod를 엔드포인트로 가진 Service마다 PTR이 하나씩 나왔다. 로그에 역방향 이름을 찍는 앱이라면 어느 이름이 찍힐지 모른다. NXDOMAIN의 SOA 마지막 숫자 30은 "없다"는 답을 캐시해도 되는 시간이다. 방금 만든 Service가 몇 초간 안 풀리는 건 대개 직전에 받은 이 NXDOMAIN이 캐시에 남아서다.

## 가끔 5초씩 늦는 이름 풀이

처음 장면의 5초로 돌아가자. 캡처에서 A와 AAAA 질의가 같은 출발지 포트(`53947`)로 거의 동시에 나간 것을 봤다. glibc는 두 질의를 소켓 하나로 나란히 보낸다. 이 UDP 패킷들이 ClusterIP로 가면서 DNAT을 거칠 때, 두 패킷이 conntrack 항목을 동시에 만들려다 하나가 버려지는 경쟁 상태가 있었다. 버려진 쪽의 답이 안 오면 리졸버는 resolv.conf의 `timeout`(기본 5초)을 다 기다린 뒤 다시 묻는다. 그래서 정확히 5초, 그리고 가끔이다. 리눅스 커널 5.0 무렵에 conntrack 쪽 수정이 들어가 많이 줄었지만, 커널 버전과 kube-proxy 모드에 따라 여전히 보고된다.

```bash
# 노드에서 conntrack이 삽입에 실패한 횟수 (insert_failed가 늘면 의심)
sudo conntrack -S | grep -o 'insert_failed=[0-9]*' | sort | uniq -c
```

대처는 몇 가지다. glibc 기반 이미지라면 `dnsConfig.options`에 `single-request-reopen`을 넣어 A와 AAAA를 다른 소켓으로 보낸다. 실습 클러스터에 그렇게 만든 Pod의 spec이다.

```text
ClusterFirst {"options":[{"name":"ndots","value":"2"},{"name":"single-request-reopen"}]}
```

Alpine 같은 musl 기반 이미지는 이 옵션을 무시한다. 그리고 근본적으로는 질의가 conntrack과 DNAT을 거치지 않게 하는 방법이 있다. 다음 절의 NodeLocal DNSCache다.

## 노드마다 캐시를 둔다

NodeLocal DNSCache는 노드마다 DNS 캐시를 하나씩 띄우는 DaemonSet(`node-local-dns`)이다. 캐시는 노드의 더미 인터페이스에 붙은 링크 로컬 주소 `169.254.20.10`에서 듣고, Pod는 이 주소로 묻는다. 캐시에 없는 클러스터 이름은 CoreDNS에 TCP로, 바깥 이름은 바깥 DNS로 바로 묻는다. Pod와 캐시 사이는 같은 노드 안이고 raw 테이블의 NOTRACK 규칙으로 conntrack을 건너뛰게 해서 앞의 경쟁 상태가 생기지 않는다. CoreDNS로 가는 길은 TCP라서 UDP conntrack 항목이 쌓이지도 않는다.

실습에서 CoreDNS로 같은 구조의 캐시를 하나 더 띄웠다. 실제 `node-cache`도 CoreDNS 기반이고 Corefile이 거의 같다.

```text
cluster.local:53 {
    errors
    cache {
        success 9984 30
        denial 9984 5
    }
    reload
    loop
    bind 127.0.20.10
    forward . 127.0.10.10 {
        force_tcp
    }
    prometheus 127.0.20.10:9253
}
```

`bind`가 실제 배포에서는 `169.254.20.10`(iptables 모드 kube-proxy라면 kube-dns의 ClusterIP도 함께)이고, `forward`의 대상은 CoreDNS Service 주소다. `force_tcp`가 TCP로 묻게 한다. `denial 9984 5`는 NXDOMAIN을 5초만 기억해서 방금 만든 Service가 늦게 풀리는 일을 줄인다. 같은 이름을 세 번 묻고 캐시 뒤쪽(CoreDNS로 가는 길)을 캡처했다.

```bash
# 노드 캐시에 같은 이름을 세 번
for i in 1 2 3; do dig +short @127.0.20.10 web.default.svc.cluster.local; done

# 캐시에서 CoreDNS로 나간 질의 (TCP 페이로드가 실린 줄만)
sudo tcpdump -ni lo 'host 127.0.10.10 and port 53 and src host 127.0.0.1'

# 캐시 메트릭
curl -s http://127.0.20.10:9253/metrics | grep -E '^coredns_cache_hits_total'
```


## CoreDNS가 스스로 죽는 경우

CoreDNS Pod가 `CrashLoopBackOff`에 빠지는 가장 흔한 원인은 `loop` 플러그인이다. 실습에서 자기 자신에게 forward하는 설정으로 띄워 봤다.

```bash
# 자기 주소로 forward하는 설정
printf '.:53 {\n    bind 127.0.30.30\n    forward . 127.0.30.30\n    loop\n}\n' > Corefile.loop
coredns -conf Corefile.loop
```

```text
[FATAL] plugin/loop: Loop (127.0.0.1:37284 -> 127.0.30.30:53) detected for zone ".", see https://coredns.io/plugins/loop#troubleshooting. Query: "HINFO 4415316548456810544.7505102497765129258."
```

`loop`는 시작할 때 무작위 이름의 HINFO 질의를 자기에게 보내 보고, 그게 다시 자기에게 돌아오면 질의가 끝없이 돌 거라 판단해 프로세스를 끝낸다. 클러스터에서는 이런 경로로 생긴다. Ubuntu 노드의 `/etc/resolv.conf`는 systemd-resolved의 `nameserver 127.0.0.53`이다. CoreDNS는 노드 설정을 물려받으니 `forward . /etc/resolv.conf`가 `127.0.0.53`을 가리키는데, 이 주소는 CoreDNS Pod 안에서는 Pod 자신의 루프백이다. 결국 자기에게 묻는다. kubelet의 `resolvConf`를 실제 업스트림이 적힌 `/run/systemd/resolve/resolv.conf`로 지정하면 풀린다(kubeadm은 systemd-resolved를 감지하면 이렇게 설정한다). `loop`를 지워서 증상만 없애면 질의가 메모리와 CPU를 먹으며 계속 도니 그러지 않는다.

그 밖에 CoreDNS 쪽에서 볼 것은 이 정도다.

```bash
# CoreDNS Pod 상태와 재시작 (k8s-app=kube-dns 라벨)
kubectl -n kube-system get pods -l k8s-app=kube-dns -o wide

# 질의 로그를 잠깐 켜려면 ConfigMap의 Corefile에 log 한 줄 추가 (reload 플러그인이 다시 읽는다)
kubectl -n kube-system edit configmap coredns
kubectl -n kube-system logs -l k8s-app=kube-dns -f

# 문제 Pod와 같은 네임스페이스에서 직접 묻기
kubectl run dnsutils --rm -it --restart=Never --image=registry.k8s.io/e2e-test-images/jessie-dnsutils:1.3 -- \
  dig +search web
```

`SERVFAIL`이 많으면 바깥 DNS가 느리거나 막힌 것이라 `forward` 대상과 노드의 DNS를 본다. `i/o timeout`이 CoreDNS 로그에 찍히면 CoreDNS에서 바깥 DNS로 가는 길이다. Pod 쪽에서만 시간 초과가 나고 CoreDNS 로그에 질의가 안 보이면 질의가 CoreDNS까지 못 온 것이라 NetworkPolicy, kube-proxy 규칙, CoreDNS Pod가 있는 노드로 가는 Pod 네트워크([CNI 글](/posts/k8s-cni-pod-network))를 본다. 질의 수에 비해 CoreDNS가 2개(기본)뿐이면 `coredns_dns_request_duration_seconds`의 꼬리가 길어진다. 노드 수에 비례해 늘려 주는 dns-autoscaler를 두거나 NodeLocal DNSCache로 부하를 덜어 낸다.

## 이름 하나 뒤의 질의들

Pod의 이름 풀이는 kubelet이 넣은 resolv.conf에서 시작한다. `ndots:5`와 search 세 줄 때문에 바깥 이름 하나가 A·AAAA 여덟 개로 불어나고, 그중 여섯은 NXDOMAIN이다. 끝에 점을 붙이거나 ndots를 낮추거나 autopath로 줄일 수 있다. CoreDNS는 API 서버를 watch한 내용으로 클러스터 이름에 직접 답하고 나머지는 바깥으로 넘긴다. 가끔 생기는 5초 지연은 UDP 질의가 conntrack과 DNAT을 지나며 버려진 흔적이고, NodeLocal DNSCache는 노드 안에서 캐시하고 CoreDNS에는 TCP로 물어 그 길 자체를 없앤다.

## 면접에서 나올 만한 질문

### Pod에서 이름을 물으면 어떤 순서로 풀리나요?

kubelet이 넣은 resolv.conf에 따라 nameserver(보통 kube-dns ClusterIP)로 묻는다. 이름의 점 개수가 ndots(기본 5)보다 적으면 search 도메인(`<ns>.svc.cluster.local`, `svc.cluster.local`, `cluster.local`)을 차례로 붙여 묻고, 다 실패하면 이름 그대로 묻는다. 질의는 kube-proxy 규칙으로 CoreDNS Pod 중 하나에 가고, 클러스터 이름이면 kubernetes 플러그인이, 아니면 forward가 바깥 DNS로 넘겨 답한다.

### ndots:5 때문에 생기는 문제와 해결책은요?

점이 5개 미만인 바깥 이름은 search 도메인을 모두 돌고 나서야 원래 이름을 묻는다. A와 AAAA를 함께 물으니 `api.example.com` 하나에 질의 8개, 그중 6개가 NXDOMAIN이라 CoreDNS 부하와 지연이 늘어난다. 바깥 이름 끝에 점을 붙여 완전한 이름으로 쓰거나, Pod의 dnsConfig로 ndots를 2 정도로 낮추거나, CoreDNS의 autopath로 서버에서 확장을 대신하게 한다. ndots를 낮추면 점이 많은 클러스터 안 이름이 바깥에 먼저 물어지는 부작용이 있다.

### Pod에서 DNS가 가끔 정확히 5초씩 늦는 이유는요?

glibc가 A와 AAAA 질의를 같은 UDP 소켓으로 동시에 보낼 때, ClusterIP로 가는 DNAT 과정에서 두 패킷이 conntrack 항목을 동시에 만들다 하나가 버려지는 경쟁 상태가 있었다. 답을 못 받은 리졸버가 기본 timeout 5초를 기다린 뒤 다시 묻기 때문에 정확히 5초가 늘어난다. `single-request-reopen` 옵션으로 소켓을 나누거나, NodeLocal DNSCache로 conntrack을 거치지 않게 해서 해결한다. musl 기반 이미지는 그 옵션을 무시한다.

### NodeLocal DNSCache는 무엇이고 왜 쓰나요?

노드마다 DNS 캐시를 DaemonSet으로 띄우고 Pod가 같은 노드의 링크 로컬 주소(169.254.20.10)로 묻게 하는 구성이다. 캐시 적중은 노드 안에서 끝나 CoreDNS 부하와 지연이 줄고, Pod와 캐시 사이는 conntrack을 건너뛰며 캐시에서 CoreDNS로는 TCP로 물어 UDP conntrack 문제를 없앤다. 대신 캐시가 노드마다 하나라 그 Pod의 장애나 업데이트가 노드의 DNS에 영향을 주고, NetworkPolicy에서 그 주소를 따로 열어야 한다.

### headless Service의 DNS는 일반 Service와 어떻게 다른가요?

일반 ClusterIP Service는 VIP 하나의 A 레코드를 돌려주고, headless(`clusterIP: None`)는 ready인 Pod IP들을 A 레코드로 돌려준다. SRV 레코드도 headless는 Pod별 이름을 가리킨다. 클라이언트가 Pod 목록을 직접 받아 분산하거나 멤버를 찾을 때 쓰고, StatefulSet과 함께 쓰면 Pod마다 고정 이름이 생긴다.

### CoreDNS가 'Loop detected'로 CrashLoopBackOff에 빠졌습니다.

CoreDNS의 forward가 결국 자기 자신에게 돌아오는 경로라서 loop 플러그인이 시작 시 감지하고 종료한 것이다. 흔한 원인은 노드의 resolv.conf가 systemd-resolved의 `127.0.0.53`이라, CoreDNS Pod 안에서 그 주소가 자기 루프백이 되는 경우다. kubelet의 resolvConf를 실제 업스트림이 적힌 `/run/systemd/resolve/resolv.conf`로 바꾸거나 forward 대상을 직접 지정한다. loop 플러그인을 지우는 건 질의가 무한히 도는 상태를 숨길 뿐이다.

### 방금 만든 Service 이름이 몇 초간 안 풀리는 이유는요?

만들기 직전에 그 이름을 물어 받은 NXDOMAIN이 캐시에 남아 있어서다. CoreDNS의 cache와 NodeLocal DNSCache의 denial 캐시, 그리고 앱이나 언어 런타임의 자체 캐시가 그 "없다"는 답을 정해진 시간 동안 기억한다. SOA의 negative TTL이나 cache 플러그인의 denial 시간을 줄이면 짧아진다. 앱이 DNS 결과를 무기한 캐시하는 런타임(예전 JVM 설정 등)이면 그쪽 설정도 본다.
