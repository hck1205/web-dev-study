README의 오타 하나를 고쳐 PR을 올렸는데 CI의 이미지 빌드가 또 4분 걸린다. 로그를 보면 의존성은 하나도 안 바뀌었는데 `npm ci`가 매번 처음부터 돈다. 레지스트리에 올라간 이미지는 1GB가 넘어서 배포할 때마다 노드가 그걸 다시 받는다. Dockerfile은 인터넷에서 찾은 예제를 거의 그대로 쓴 것이다.

둘 다 Dockerfile을 몇 줄 바꾸면 고쳐진다. 다만 왜 그 순서여야 하는지 알려면 이미지가 레이어로 쌓이는 방식과 빌드 캐시가 맞는지 판단하는 규칙을 알아야 한다. 이 글은 Dockerfile 명령어를 한 줄씩 읽고, 명령이 레이어가 되고 캐시가 맞거나 깨지는 과정을 따라간 뒤, 멀티 스테이지 빌드와 베이스 이미지 선택으로 이미지를 줄이고, 여러 아키텍처로 빌드해 올리는 데까지 간다.

컨테이너와 이미지가 무엇인지는 [앞 글](/posts/docker-container-basics)에서 봤다. 기준은 Ubuntu 24.04 LTS에 설치한 Docker Engine 29(BuildKit 기본)이고, 예제는 Node.js API 서버다. 이미지 크기는 이 글을 쓰는 시점에 amd64에서 잰 대략의 값이고, 베이스 이미지가 갱신되면 조금씩 달라진다.

## 문제가 된 Dockerfile

처음 상태는 이랬다. 짧고, 돌아가기는 한다.

```dockerfile
FROM node:22
WORKDIR /app
COPY . .
RUN npm install
RUN npm run build
EXPOSE 3000
CMD npm start
```

문제는 다섯 군데쯤 있다. `node:22`는 빌드 도구가 잔뜩 든 풀 이미지라 그것만으로 1GB 안팎이다. `COPY . .`가 의존성 설치보다 앞에 있어서 파일 하나만 바뀌어도 설치를 다시 한다. 빌드에만 필요한 TypeScript 컴파일러와 devDependencies가 운영 이미지에 그대로 남는다. 앱이 root로 돈다. `CMD npm start`는 셸 형식이라 `docker stop`이 10초씩 걸린다. 하나씩 고쳐 가면서 각 명령어가 무슨 일을 하는지 보자.

## 명령어 한 줄씩 읽기

Dockerfile은 위에서 아래로 실행되는 이미지 조립 순서다. 자주 쓰는 명령어는 열 개 남짓이다.

`FROM`은 어떤 이미지 위에서 시작할지 정한다. 모든 Dockerfile은 `FROM`으로 시작한다(그 앞에 올 수 있는 건 `ARG`뿐이다). 한 파일에 `FROM`이 여러 번 나오면 그게 멀티 스테이지 빌드다.

`WORKDIR`은 이후 명령이 실행될 디렉터리다. 없으면 만든다. `RUN cd /app`은 그 줄이 끝나면 효과가 사라지니, 디렉터리를 옮길 때는 `WORKDIR`을 쓴다.

`COPY`는 빌드 컨텍스트(보통 `docker build .`의 `.`)에서 파일을 이미지로 복사한다. `ADD`도 비슷하지만 두 가지를 더 한다. 로컬의 tar 파일이면 자동으로 풀고, URL이면 내려받는다. 이 자동 동작이 의도와 다르게 일어나는 일이 있어서 평소에는 `COPY`를 쓰고, tar를 풀어 넣어야 할 때만 `ADD`를 쓴다. URL 다운로드는 `ADD --checksum=sha256:...`처럼 체크섬을 함께 주지 않으면 받은 내용이 바뀌어도 모른다.

`RUN`은 빌드 중에 명령을 실행하고 그 결과(바뀐 파일)를 이미지에 남긴다. 패키지 설치, 컴파일이 여기서 일어난다.

`ENV`와 `ARG`는 둘 다 변수를 정하지만 사는 기간이 다르다. `ARG`는 빌드하는 동안에만 있고 `docker build --build-arg`로 바꿀 수 있다. 완성된 이미지의 환경 변수에는 남지 않는다. `ENV`는 이미지에 박혀서 컨테이너가 실행될 때도 환경 변수로 보인다. 둘 다 `docker history`에는 값이 보일 수 있으니 토큰이나 비밀번호를 넣으면 안 된다. 빌드 중에 비밀 값이 필요하면 뒤에서 볼 `--mount=type=secret`을 쓴다.

```dockerfile
# 빌드할 때만 쓰는 값. docker build --build-arg NODE_VERSION=22 로 바꾼다
ARG NODE_VERSION=22
FROM node:${NODE_VERSION}-slim

# 컨테이너가 실행될 때도 남는 값
ENV NODE_ENV=production
```

`FROM` 앞의 `ARG`는 `FROM` 줄에서만 쓸 수 있다. 스테이지 안에서도 쓰려면 `FROM` 뒤에 `ARG NODE_VERSION`을 값 없이 한 번 더 선언한다.

`EXPOSE`는 이 이미지가 어느 포트를 듣는지 적어 두는 문서다. 포트를 실제로 열지 않는다. 밖에서 닿게 하는 건 실행할 때의 `-p`다. `docker run -P`(대문자)로 띄우면 `EXPOSE`한 포트를 호스트의 임의 포트에 연결해 주는 정도의 쓰임이 있다.

`USER`는 이후의 `RUN`과 컨테이너 실행을 어느 사용자로 할지 정한다. 기본은 root다.

`ENTRYPOINT`와 `CMD`는 컨테이너가 시작될 때 실행할 명령이다. 이 둘은 따로 볼 만하다.

## ENTRYPOINT와 CMD, exec 형식과 셸 형식

컨테이너가 실행하는 명령은 `ENTRYPOINT` 뒤에 `CMD`를 이어 붙인 것이다. `ENTRYPOINT`는 고정된 실행 파일, `CMD`는 바꿀 수 있는 기본 인자로 생각하면 된다. `docker run 이미지 뒤에 쓴 것`은 `CMD`를 갈아 끼우고, `ENTRYPOINT`를 바꾸려면 `--entrypoint`를 써야 한다.

```dockerfile
ENTRYPOINT ["node"]
CMD ["dist/server.js"]
# docker run api               → node dist/server.js
# docker run api dist/migrate.js → node dist/migrate.js
```

`ENTRYPOINT` 없이 `CMD`만 쓰면 `CMD`가 통째로 명령이 된다. 앞 글에서 본 nginx 이미지는 `ENTRYPOINT ["/docker-entrypoint.sh"]`에 `CMD ["nginx", "-g", "daemon off;"]`라서, 시작 스크립트가 설정을 준비한 뒤 마지막에 `exec "$@"`로 nginx를 실행한다. 스크립트가 PID 1을 nginx에 넘겨주는 이 패턴은 직접 엔트리포인트 스크립트를 쓸 때도 그대로 따라 한다.

쓰는 형식이 둘이다. 대괄호와 따옴표로 쓰는 exec 형식(`CMD ["node", "dist/server.js"]`)은 그 프로그램을 바로 실행한다. 대괄호 없이 쓰는 셸 형식(`CMD node dist/server.js`)은 `/bin/sh -c "node dist/server.js"`로 바뀌어 실행된다. 그러면 PID 1이 셸이 된다. 앞 글에서 봤듯 PID 1은 핸들러 없는 시그널을 무시하고, 셸은 SIGTERM을 자식에게 넘겨주지 않는다. 같은 앱을 두 형식으로 띄워 `docker stop`에 걸리는 시간을 재 보면 이렇다.

```bash
# 셸 형식으로 만든 이미지: PID 1이 무엇인지 본다
docker run -d --name s1 api:shell
docker exec s1 sh -c 'cat /proc/1/cmdline | tr "\0" " "; echo'
time docker stop s1

# exec 형식으로 만든 이미지
docker run -d --name e1 api:multi
time docker stop e1
```

```text
/bin/sh -c node dist/server.js
s1

real	0m10.220s
```

```text
e1

real	0m0.195s
```

셸 형식은 10초를 다 기다리고 SIGKILL로 끝났다. exec 형식에서는 node가 PID 1이라 SIGTERM을 직접 받고, 앱의 종료 핸들러가 바로 서버를 닫는다. 셸에 따라 명령이 하나뿐이면 셸 대신 그 명령을 exec해 주기도 하지만 보장되지 않고, 위 실험에서도 셸이 PID 1로 남았다. 그 동작에 기대지 말고 exec 형식을 쓴다. 같은 이유로 `CMD ["npm", "start"]`도 피한다. npm이 PID 1이 되고, npm은 버전에 따라 시그널을 자식에게 제대로 넘기지 않는다. 앱을 `node`로 직접 실행한다.

환경 변수를 펼치려고 셸 형식을 쓰고 싶을 때가 있다. exec 형식은 셸을 거치지 않아서 `$PORT` 같은 변수가 펼쳐지지 않는다. 그럴 때는 앱이 환경 변수를 직접 읽게 하거나, 엔트리포인트 스크립트 끝에서 `exec node dist/server.js`로 넘긴다.

## 명령 하나가 레이어 한 장

이미지는 레이어를 겹친 것이라고 앞 글에서 말했다. 그 레이어는 Dockerfile의 명령에서 나온다. 파일 시스템을 바꾸는 `RUN`, `COPY`, `ADD`는 각각 레이어 한 장을 만들고, 나머지(`ENV`, `WORKDIR`, `EXPOSE`, `USER`, `CMD` 등)는 설정(메타데이터)만 바꾼다. `docker history`로 확인한다.

```bash
# 이미지가 어떤 명령으로 쌓였는지, 각 레이어 크기는 얼마인지
docker history api:good
```

아래에서 위로 읽는다. 맨 아래 85.3MB가 Debian bookworm 베이스이고, 154MB가 Node 바이너리를 설치한 레이어다. 그 위 다섯 줄이 내 Dockerfile이다. `CMD`, `ENV`는 0B다. 레이어가 아니라 설정이라서다. `IMAGE` 열의 `<missing>`은 고장이 아니다. 그 단계가 독립된 이미지로 저장돼 있지 않다는 뜻이고, BuildKit으로 빌드하거나 레지스트리에서 받은 이미지는 원래 이렇게 보인다. `--no-trunc`를 붙이면 잘린 명령을 끝까지 볼 수 있다. 위 출력처럼 `ENV`로 넣은 값은 누구나 볼 수 있다.

레이어 구조에서 나오는 함정이 하나 있다. 레이어는 위에 쌓이기만 하고, 아래 레이어의 파일을 위에서 지워도 아래 레이어 크기는 줄지 않는다. 위 레이어에 "이 파일은 없다"는 표시(whiteout)만 남는다.

```dockerfile
# 나쁜 예: 캐시를 다음 줄에서 지워도 첫 줄 레이어에 그대로 남는다
RUN apt-get update && apt-get install -y build-essential
RUN rm -rf /var/lib/apt/lists/*

# 좋은 예: 같은 RUN 안에서 설치하고 정리한다
RUN apt-get update \
 && apt-get install -y --no-install-recommends build-essential \
 && rm -rf /var/lib/apt/lists/*
```

`COPY` 뒤에 `RUN chown -R`을 하는 것도 같은 문제다. 파일 내용은 그대로인데 소유자만 바뀐 사본이 새 레이어로 통째로 생겨서 크기가 두 배가 된다. `COPY --chown=node:node`로 복사하면서 소유자를 정한다. 비밀 파일을 `COPY`했다가 다음 줄에서 지우는 것도 소용없다. 아래 레이어를 꺼내 보면 그대로 있다.

## 겹쳐진 레이어를 직접 열어 보기

Docker 29를 새로 설치한 containerd 이미지 저장소에서는 `GraphDriver`가 `null`로 비어 있어서, 아래 실험은 `--storage-driver overlay2`로 띄운 데몬(데이터 경로 `/var/lib/docker-overlay2`)에서 했다. 기본 설치라면 같은 자리가 `/var/lib/docker/overlay2`다.

```bash
# 컨테이너가 쓰는 자리와 합쳐 보이는 자리
docker inspect demo --format '{{.GraphDriver.Data.UpperDir}}'
docker inspect demo --format '{{.GraphDriver.Data.MergedDir}}'
```

`l/` 아래의 짧은 이름은 레이어 디렉터리를 가리키는 심볼릭 링크다. 레이어가 많으면 마운트 옵션 문자열이 커널 한도(한 페이지)를 넘기 때문에 줄여 쓴다. containerd 이미지 저장소라면 같은 줄이 `.../io.containerd.snapshotter.v1.overlayfs/snapshots/593/fs`처럼 스냅숏 번호로 나온다. 구조는 같다.

이제 지운 파일이 어디 있는지 본다.

```bash
# rm 레이어 안의 /data
sudo ls -l /var/lib/docker-overlay2/overlay2/y8x0jrq4ep13jei8qmcnjlxqg/diff/data/
# mkdir 레이어 안의 /data
sudo ls -l /var/lib/docker-overlay2/overlay2/ostfqm11aotxpds9u4hoe1klm/diff/data/
```

```text
total 0
c--------- 2 root root 0, 0 Oct 24 00:33 big.bin
total 48836
-rw-r--r-- 1 root root 50000000 Oct 24 00:33 big.bin
```

`rm` 레이어에는 같은 이름의 문자 장치(맨 앞 `c`, 장치 번호 `0, 0`)가 있다. 이것이 overlay2의 whiteout이다. overlayfs는 위에서 아래로 내려가며 파일을 찾다가 whiteout을 만나면 "없다"고 답하고 멈춘다. 그래서 컨테이너 안 `ls /data`는 비어 있지만, 바로 아래 레이어에는 50MB가 그대로 있다. 레지스트리로 보내는 레이어 tar 안에서는 같은 표시가 `.wh.big.bin`이라는 빈 파일로 바뀐다. 디렉터리를 통째로 지우고 다시 만들면 `.wh..wh..opq`(opaque) 표시가 붙어 아래 디렉터리 내용을 한꺼번에 가린다.

### 컨테이너의 쓰기는 복사부터 한다

컨테이너가 아래 레이어에 있는 파일을 고치면 overlayfs는 그 파일을 먼저 upperdir로 통째로 복사하고, 사본을 고친다. 이걸 copy-up이라고 한다.

```bash
docker exec demo sh -c 'echo v2 >> /etc/app.conf'
sudo find /var/lib/docker-overlay2/overlay2/d05bd1370bdde66cfe746e3b7d91cf6e4dafe23f6c08140139e013a8b7448b44/diff -mindepth 1
# 이미지와 달라진 파일 목록. C는 변경, A는 추가, D는 삭제
docker diff demo
```

```text
/var/lib/docker-overlay2/overlay2/d05bd1370bdde66cfe746e3b7d91cf6e4dafe23f6c08140139e013a8b7448b44/diff/etc
/var/lib/docker-overlay2/overlay2/d05bd1370bdde66cfe746e3b7d91cf6e4dafe23f6c08140139e013a8b7448b44/diff/etc/app.conf
C /etc
C /etc/app.conf
```

파일이 작으면 티가 안 난다. 이미지에 500MB짜리 파일(`head -c 500000000 /dev/zero > /big.db`)을 넣고, 컨테이너에서 한 줄씩 두 번 덧붙여 봤다.

```bash
docker run -d --name big layers:big sleep 3600
docker exec big sh -c 'time sh -c "echo x >> /big.db"; time sh -c "echo y >> /big.db"'
# SIZE는 쓰기 계층 크기, virtual은 이미지까지 합친 크기
docker ps -s --format 'table {{.Names}}\t{{.Size}}'
```

```text
real	0m 0.67s
user	0m 0.00s
sys	0m 0.23s
real	0m 0.00s
user	0m 0.00s
sys	0m 0.00s
NAMES     SIZE
big       500MB (virtual 1.01GB)
demo      6B (virtual 57.8MB)
```

2바이트를 쓰려고 첫 번째에만 0.67초가 걸렸고 쓰기 계층이 500MB가 됐다. 두 번째는 이미 upperdir에 사본이 있어서 바로 끝났다. DB 파일처럼 크고 계속 고쳐 쓰는 파일을 쓰기 계층에 두면 이 복사와 overlayfs를 거치는 비용을 계속 낸다. 그리고 upperdir는 컨테이너에 딸린 디렉터리라 컨테이너를 지우면 같이 지워진다.

```bash
docker rm -f demo
docker run --rm layers:demo cat /etc/app.conf
```

```text
v1
```

`v2`를 덧붙였던 기록은 사라지고 이미지에 구운 `v1`만 남았다. 배포는 컨테이너를 새로 만드는 일이니, 배포할 때마다 쓰기 계층은 빈 상태로 돌아간다. 남겨야 하는 데이터는 볼륨에 둔다. 볼륨은 overlayfs를 거치지 않고 호스트 디렉터리를 그대로 바인드 마운트해서 copy-up도 없고, 컨테이너를 지워도 남는다. 볼륨 종류와 고르는 법은 [Docker 네트워크와 볼륨](/posts/docker-network-volume)에 있다. 반대로 쓸 일이 없는 컨테이너는 `--read-only`로 쓰기 계층을 막아 두면, 어디에 몰래 쓰는지가 바로 에러로 드러난다.

## 캐시는 처음 바뀐 줄에서 끊긴다

BuildKit은 명령마다 결과를 캐시해 둔다. 다시 빌드할 때 한 줄씩 내려가며 "이 줄의 입력이 지난번과 같은가"를 보고, 같으면 저장해 둔 레이어를 그대로 쓴다. 입력으로 보는 것은 명령마다 다르다.

- 모든 명령: 바로 위까지의 레이어(부모)가 같아야 한다. 한 줄이라도 캐시가 깨지면 그 아래는 전부 다시 실행된다.
- `RUN`: 명령 문자열이 같은지만 본다. 명령을 실행한 결과는 보지 않는다. 그래서 `RUN apt-get update`가 캐시되면 몇 달 지난 패키지 목록을 계속 쓴다.
- `COPY`, `ADD`: 복사할 파일들의 내용 체크섬을 본다. 파일 수정 시각은 보지 않는다.
- `ARG`, `ENV`: 값이 바뀌면 그 뒤에서 그 변수를 쓰는 명령의 캐시가 깨진다.

처음의 Dockerfile에 이 규칙을 대 보자. 베이스를 `node:22-slim`으로, 설치를 `npm ci`로만 바꾸고 순서는 그대로 둔 상태에서 소스 파일 하나(`src/server.js`)만 고치고 다시 빌드한다. 아래 그림에서 다음을 누르면 한 줄씩 내려가며 캐시가 맞는지 본다. 초록 칸이 캐시를 쓴 줄이고, 아래 상자에 쌓이는 것이 결과 이미지의 레이어다.

## 잘 안 바뀌는 것을 위에 둔다

고치는 방법은 단순하다. 의존성 목록(`package.json`, `package-lock.json`)만 먼저 복사해서 설치하고, 소스는 그 다음에 복사한다. 의존성 목록은 소스보다 훨씬 드물게 바뀌니, 대부분의 빌드에서 설치 레이어가 캐시에 걸린다.

```dockerfile
FROM node:22-slim
WORKDIR /app

# 1. 의존성 목록만 먼저. 이 두 파일이 같으면 아래 npm ci까지 캐시된다
COPY package.json package-lock.json ./
RUN npm ci

# 2. 자주 바뀌는 소스는 마지막에
COPY . .
CMD ["node", "src/server.js"]
```

`npm install` 대신 `npm ci`를 쓴 것도 이유가 있다. `npm ci`는 lock 파일에 적힌 버전을 그대로 설치하고, `package.json`과 lock 파일이 맞지 않으면 실패한다. 빌드할 때마다 다른 버전이 깔리는 일을 막는다. pnpm이면 `pnpm install --frozen-lockfile`, yarn이면 `yarn install --immutable`이 같은 역할이다.

```dockerfile
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "app:app"]
```

## .dockerignore로 보내는 것부터 줄인다

`docker build .`의 `.`이 빌드 컨텍스트다. `COPY . .`는 이 컨텍스트 전체를 복사한다. 여기에 로컬의 `node_modules`, `.git`, 빌드 결과물, `.env`가 섞여 있으면 문제가 셋 생긴다. 보낼 양이 많아 느려지고, 그 파일들이 체크섬에 들어가 쓸데없이 캐시가 깨지고, `.env` 같은 비밀이 이미지에 들어간다.

로컬 `node_modules`가 들어가는 건 특히 위험하다. 컨테이너 안에서 `npm ci`로 설치한 리눅스용 `node_modules` 위에 맥에서 설치한 `node_modules`를 덮어써서, 네이티브 모듈이 엉뚱한 플랫폼 바이너리로 바뀐다. 빌드 컨텍스트 루트에 `.dockerignore`를 둔다. 문법은 `.gitignore`와 비슷하다.

```bash
# 빌드 컨텍스트에서 뺄 것들
cat > .dockerignore <<'EOF'
node_modules
dist
.git
.env
.env.*
*.log
coverage
Dockerfile*
.dockerignore
EOF

# 빌드 로그에서 컨텍스트 크기를 확인
docker build --progress=plain -t api:good . 2>&1 | grep 'transferring context'
```

```text
#4 transferring context: 302B 0.0s done
```

이 숫자가 수백 MB로 나오면 `.dockerignore`가 없거나 잘못된 것이다. 아예 반대로, 모두 제외(`*`)한 뒤 필요한 것만 `!src`, `!package.json`처럼 다시 넣는 방식도 있다. 실수로 비밀 파일이 들어갈 일이 줄어든다.

## 빌드 도구는 두고 결과만 옮기는 멀티 스테이지 빌드

캐시로 빌드는 빨라졌지만 이미지는 여전히 크다. TypeScript 컴파일러, 테스트 도구, 린터 같은 devDependencies와 소스 원본이 운영 이미지에 그대로 들어 있다. 실행할 때는 컴파일된 `dist`와 운영용 의존성만 있으면 된다.

멀티 스테이지 빌드는 한 Dockerfile 안에 `FROM`을 여러 번 써서 스테이지를 나눈다. 앞 스테이지에서 빌드하고, 마지막 스테이지에는 `COPY --from=스테이지이름`으로 필요한 결과물만 가져온다. 최종 이미지는 마지막 스테이지뿐이고, 앞 스테이지에 깔았던 것들은 전부 버려진다. 아래 그림에서 점이 흐르는 화살표만 운영 이미지에 들어간다.

처음 Dockerfile을 이 방식으로 다시 쓰면 이렇게 된다. 줄마다 이유를 주석으로 달았다.

```dockerfile
# syntax=docker/dockerfile:1

# ---- 1단계: 빌드 (devDependencies 포함) ----
FROM node:22-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
# npm 다운로드 캐시를 빌드 사이에 재사용한다 (이미지에는 들어가지 않음)
RUN --mount=type=cache,target=/root/.npm npm ci
COPY . .
RUN npm run build

# ---- 2단계: 운영 의존성만 ----
FROM node:22-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev

# ---- 3단계: 실행 ----
FROM node:22-slim AS runtime
ENV NODE_ENV=production
WORKDIR /app
# 복사하면서 소유자를 정한다 (RUN chown -R은 레이어를 두 배로 만든다)
COPY --from=deps --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/dist ./dist
# node 이미지에 들어 있는 UID 1000 사용자
USER node
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD ["node", "-e", "fetch('http://127.0.0.1:3000/').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"]
CMD ["node", "dist/server.js"]
```

`build`와 `deps`는 서로를 기다리지 않으니 BuildKit이 동시에 실행한다. 최종 스테이지에 쓰이지 않는 스테이지는 아예 건너뛴다. 테스트 스테이지를 하나 더 두고 CI에서만 `docker build --target test .`로 그 스테이지까지 빌드하는 식으로도 쓴다.

여기서 줄어드는 양은 devDependencies 크기만큼이다. TypeScript, 번들러, 테스트 도구가 들어간 프로젝트는 `node_modules`의 절반 이상이 devDependencies인 경우가 흔하다. Go나 Rust처럼 실행 파일 하나로 컴파일되는 언어는 효과가 더 크다. 컴파일러가 든 수백 MB짜리 빌드 스테이지에서 바이너리만 꺼내 distroless나 `scratch` 위에 올리면 최종 이미지가 수십 MB 아래로 내려간다.

## 베이스 이미지: slim, alpine, distroless

마지막 스테이지가 무엇 위에 서 있느냐가 이미지 크기의 대부분을 정한다. 같은 Node 22라도 고를 수 있는 베이스가 여럿이다.

```bash
# 받아 둔 베이스 이미지들의 크기 비교
docker image ls
```

```text
IMAGE                                        ID             DISK USAGE   CONTENT SIZE   EXTRA
gcr.io/distroless/nodejs22-debian12:latest   8a3e96fe3345        204MB         52.6MB
node:22-alpine                               0a7108bf6c7b        238MB         61.1MB
node:22-slim                                 c3de60bf2f9d        329MB         82.5MB
python:3.12-slim                             a6e34c598f24        179MB         45.4MB
```

CONTENT SIZE가 레지스트리에서 받는 압축 크기다. DISK USAGE는 containerd 이미지 저장소에서 압축 원본과 풀어 놓은 파일을 합친 값이라 압축 크기보다 훨씬 크게 나온다. 예전 저장소(overlay2)를 쓰는 Docker에서는 `SIZE` 열 하나로 풀어 놓은 크기만 보인다. 대략 node:22-slim이 압축 80MB, alpine이 60MB, distroless가 50MB 정도이고, 풀 이미지 `node:22`는 풀었을 때 1GB 안팎이다. Node 런타임 자체가 100MB를 넘어서 베이스 사이의 차이는 생각보다 작다.

`-slim`은 Debian에서 문서, 컴파일러 같은 것을 뺀 것이다. glibc를 쓰는 평범한 Debian이라 대부분의 네이티브 모듈과 바이너리가 그대로 돈다. `apt-get`도 있고 셸도 있다. 무난한 기본값이다.

`-alpine`은 Alpine Linux 기반이다. 작지만 C 라이브러리가 glibc가 아니라 musl이다. 이 차이가 실무에서 여러 번 문제가 된다. glibc용으로 미리 빌드된 네이티브 바이너리(Node 네이티브 모듈, Python의 manylinux 휠)는 musl에서 돌지 않는다. 패키지가 musl용 빌드를 따로 주지 않으면 설치할 때 소스에서 컴파일하게 되고, 빌드에 컴파일러가 필요해지고 시간이 오래 걸린다. DNS 이름 풀이 방식, 기본 스레드 스택 크기, 메모리 할당기 성능도 glibc와 다르다. 작은 크기를 얻는 대신 "Alpine에서만 나는 문제"를 떠안는 셈이다. 의존성이 순수 JS·순수 Python이라면 잘 돈다.

distroless는 구글이 만드는 이미지로, 런타임과 그 런타임이 쓰는 라이브러리 말고는 아무것도 없다. 셸도 패키지 관리자도 없다. 공격자가 컨테이너에 들어와도 쓸 도구가 없고, 취약점 스캐너가 잡을 패키지 수도 적다. 대신 `docker exec -it ... sh`로 들어가 볼 수 없다. 디버깅할 때는 busybox 셸이 든 `:debug` 태그로 잠시 바꿔 띄우거나, 쿠버네티스라면 임시 컨테이너(`kubectl debug`)를 붙인다. distroless nodejs 이미지는 `ENTRYPOINT`가 이미 node라서 `CMD ["dist/server.js"]`처럼 스크립트 경로만 준다. `:nonroot` 태그를 쓰면 UID 65532 사용자로 돈다.

정리하면 기본은 `-slim`으로 두고, 이미지 크기와 공격 면적이 중요하면 distroless로 간다. Alpine은 의존성이 musl에서 문제없다는 걸 확인한 뒤에 고른다. 어느 쪽이든 `node:22-slim`처럼 메이저 버전을 적고, 재현성이 필요하면 `node:22-slim@sha256:...`로 다이제스트를 고정한다.

## root가 아닌 사용자로, 상태는 HEALTHCHECK로

이미지에 `USER`가 없으면 앱은 root(UID 0)로 돈다. 앞 글에서 봤듯 Docker는 기본으로 user namespace를 쓰지 않아서, 컨테이너 안 root는 호스트에서도 UID 0이다. 앱에 원격 코드 실행 취약점이 있으면 공격자는 root로 시작한다. 일반 사용자로 바꿔 두면 탈출 취약점이 있어도 피해가 줄어든다.

공식 node 이미지에는 UID 1000인 `node` 사용자가 이미 있다. 없는 베이스라면 직접 만든다.

```dockerfile
# Debian 계열: 시스템 사용자 생성
RUN groupadd --system --gid 10001 app \
 && useradd --system --uid 10001 --gid app --no-create-home app
USER 10001:10001
```

이름 대신 숫자 UID를 쓰는 편이 낫다. 쿠버네티스에서 `runAsNonRoot: true`를 켜면 kubelet이 이미지의 사용자가 root가 아닌지 확인하는데, `USER node`처럼 이름만 있으면 UID를 알 수 없어서 컨테이너를 띄우지 않는다. 포트도 신경 쓴다. 리눅스에서 1024 아래 포트는 원래 root만 열 수 있다. Docker는 20.10부터 컨테이너 안에서 이 제한을 풀어 주지만(`net.ipv4.ip_unprivileged_port_start=0`), 쿠버네티스 같은 다른 런타임에서는 안 풀려 있을 수 있다. 앱은 3000, 8080 같은 높은 포트를 듣게 해 두는 편이 어디서나 안전하다.

`HEALTHCHECK`는 Docker가 주기적으로 실행해서 앱이 정말 응답하는지 보는 명령이다. 프로세스가 살아 있어도 데드락에 걸려 요청을 못 받는 상태를 잡으려고 쓴다. 위 Dockerfile의 설정은 30초마다 3초 제한으로 검사하고, 시작 후 10초는 실패해도 세지 않고, 3번 연속 실패하면 unhealthy로 바꾼다는 뜻이다. slim이나 distroless에는 `curl`이 없는 경우가 많아서 node의 내장 `fetch`로 검사했다.

```bash
# 띄우고 잠시 뒤 STATUS 열을 본다
docker run -d --name h1 api:multi
docker ps --filter name=h1

# 누구로 돌고 있는지
docker exec h1 id

# 최근 검사 결과 기록
docker inspect -f '{{json .State.Health}}' h1
```

```text
CONTAINER ID   IMAGE       COMMAND                  CREATED          STATUS                    PORTS      NAMES
2cb4bcbc9161   api:multi   "docker-entrypoint.s…"   15 seconds ago   Up 14 seconds (healthy)   3000/tcp   h1
```

```text
uid=1000(node) gid=1000(node) groups=1000(node)
```

STATUS의 `(healthy)`를 본다. 처음 몇 초는 `(health: starting)`, 실패가 쌓이면 `(unhealthy)`로 바뀐다. 다만 Docker Engine 단독으로는 unhealthy 컨테이너를 재시작하지 않는다. 상태만 표시한다. Docker Compose의 `depends_on: condition: service_healthy`나 Swarm이 이 값을 쓴다. 쿠버네티스는 `HEALTHCHECK`를 아예 무시하고 Pod의 liveness·readiness probe를 따로 설정해야 한다.

## BuildKit 캐시 마운트와 여러 아키텍처 빌드

레이어 캐시는 "lock 파일이 같으면 설치를 건너뛴다"까지만 해 준다. lock 파일에서 패키지 하나만 바뀌어도 `npm ci`는 처음부터 전부 다시 받는다. 위 Dockerfile의 `RUN --mount=type=cache,target=/root/.npm`이 이 부분을 메운다. 빌드할 때마다 `/root/.npm`에 같은 캐시 디렉터리를 붙여 주니, 바뀐 패키지만 새로 받고 나머지는 디스크에서 꺼낸다. 이 디렉터리는 이미지 레이어에 들어가지 않는다.

```dockerfile
# pip: 캐시 마운트를 쓸 때는 --no-cache-dir를 빼야 캐시가 쌓인다
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt

# apt: Debian 이미지의 자동 정리 설정을 끄고, 동시 빌드끼리는 잠가서 공유
RUN rm -f /etc/apt/apt.conf.d/docker-clean \
 && echo 'Binary::apt::APT::Keep-Downloaded-Packages "true";' > /etc/apt/apt.conf.d/keep-cache
RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt,sharing=locked \
    apt-get update && apt-get install -y --no-install-recommends curl

# 비밀 값: 빌드 중 파일로만 보이고 레이어와 history에 남지 않는다
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
```

마지막 줄은 `docker build --secret id=npmrc,src=$HOME/.npmrc .`처럼 비밀 파일을 넘겨서 쓴다. 사설 npm 레지스트리 토큰을 `ARG`나 `COPY .npmrc`로 넣으면 이미지에 남는데, 이렇게 하면 남지 않는다.

캐시 마운트는 그 빌더가 돌고 있는 머신에만 있다. CI처럼 매번 새 러너에서 빌드하면 캐시가 비어 있다. 레이어 캐시는 `--cache-to`·`--cache-from`으로 레지스트리나 GitHub Actions 캐시에 내보내 두고 다음 빌드가 가져다 쓸 수 있다(캐시 마운트 내용은 여기에 포함되지 않는다).

여러 CPU 아키텍처용 이미지도 같은 명령으로 만든다. 서버는 amd64인데 개발자 노트북은 Apple Silicon(arm64)이거나, 비용 때문에 AWS Graviton 같은 arm64 서버를 섞어 쓰는 일이 흔하다. 공식 이미지들은 태그 하나에 여러 아키텍처 이미지를 묶어 두고(이미지 인덱스, manifest list), 받는 쪽이 자기 아키텍처를 고른다.

```bash
# node:22-slim 태그 하나에 묶인 플랫폼 목록 (unknown/unknown은 SBOM 같은 증명 정보)
docker buildx imagetools inspect node:22-slim | grep Platform
```

## 태그 붙여 올리고, 올리기 전에 검사하기

이미 빌드한 이미지에 레지스트리 이름을 붙여 올리는 순서는 이렇다.

```bash
# 레지스트리에 로그인 (ghcr.io는 GitHub 토큰을 비밀번호로)
echo "$GHCR_TOKEN" | docker login ghcr.io -u my-github-id --password-stdin

# 로컬 이미지에 레지스트리 경로가 담긴 태그를 붙인다 (복사가 아니라 이름만 하나 더)
docker tag api:multi ghcr.io/me/api:1.4.2
docker tag api:multi ghcr.io/me/api:sha-3f2c1ab

# 올린다. 레지스트리에 이미 있는 레이어는 건너뛴다
docker push ghcr.io/me/api:1.4.2
docker push ghcr.io/me/api:sha-3f2c1ab
```

태그는 사람이 읽을 버전(`1.4.2`)과 커밋 해시(`sha-3f2c1ab`)를 같이 붙여 두면, 지금 돌고 있는 이미지가 어느 커밋에서 나왔는지 바로 찾을 수 있다. 배포 매니페스트에는 `latest` 대신 이 둘 중 하나나 다이제스트를 적는다. 푸시 로그 마지막 줄의 `digest: sha256:...`이 그 다이제스트다.

올리기 전에는 이미지 안 패키지의 알려진 취약점(CVE)을 검사한다. Docker Desktop에 들어 있는 `docker scout`(Linux 엔진에서는 플러그인을 따로 설치)나 오픈 소스 Trivy를 많이 쓴다.

```bash
# Docker Scout: 심각도가 높은 취약점만
docker scout cves --only-severity critical,high ghcr.io/me/api:1.4.2

# Trivy를 컨테이너로 실행해 로컬 이미지를 검사 (HIGH 이상이 있으면 종료 코드 1)
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy image --severity HIGH,CRITICAL --exit-code 1 ghcr.io/me/api:1.4.2
```

CI에서 `--exit-code 1`로 높은 등급 취약점이 있으면 빌드를 멈추게 걸어 두는 경우가 많다. 결과를 보면 대부분이 베이스 이미지의 OS 패키지에서 나온다. 베이스가 작을수록 검사 결과도 짧아지는 이유다. 고칠 방법은 대개 베이스 이미지를 최신 패치로 다시 받아 빌드하는 것이고, 그래서 코드가 안 바뀌어도 주기적으로 다시 빌드한다. 스캐너 컨테이너를 쓸 때도 태그나 다이제스트를 고정해 둔다. 검사 도구 자체도 공급망의 일부다.

## 빌드는 됐는데 서버에서 안 뜰 때

이미지를 고치고 나면 빌드는 통과하는데 배포한 서버에서 컨테이너가 바로 죽는 일이 생긴다. `docker ps -a`의 STATUS가 `Exited (1)`이나 `Restarting`이고, 쿠버네티스라면 Pod가 `CrashLoopBackOff`다. 이때 볼 곳은 정해져 있다. 마지막으로 죽은 컨테이너의 로그와, 이미지 안에 실제로 무엇이 들어 있는지다. Docker를 쓸 수 없는 환경에서 정리한 글이라 Docker 명령의 출력은 예시이고, 그 안의 Node 에러 문구는 Node 22로 직접 확인한 형식이다.

### `exec format error`

노트북에서 빌드해 올린 이미지를 서버에 띄우자 로그에 한 줄만 남고 끝난다.

```text
exec /usr/local/bin/docker-entrypoint.sh: exec format error
```

예시다. 앱 코드는 한 줄도 실행되지 않았다. 커널이 이 실행 파일의 형식을 모른다는 뜻이고, 거의 언제나 아키텍처가 다른 경우다. Apple Silicon 노트북(arm64)에서 `--platform` 없이 빌드하면 arm64 이미지가 나오고, 이걸 amd64 서버가 받으면 이렇게 된다. 이미지가 어느 플랫폼용인지부터 본다.

```bash
# 로컬에 받은 이미지의 OS/아키텍처
docker image inspect --format '{{.Os}}/{{.Architecture}}' ghcr.io/me/api:1.4.2

# 레지스트리의 태그에 어떤 플랫폼이 묶여 있는지
docker buildx imagetools inspect ghcr.io/me/api:1.4.2 | grep Platform

# 서버의 아키텍처 (x86_64면 amd64, aarch64면 arm64)
uname -m
```

```text
linux/arm64
  Platform:    linux/arm64
x86_64
```

예시 출력이다. 태그에 arm64만 있고 서버는 x86_64다. 앞 절의 `docker buildx build --platform linux/amd64,linux/arm64 --push`로 다시 올리면 서버가 맞는 쪽을 골라 받는다. 흔한 실수는 노트북에서 `docker build` 후 `docker push`를 직접 하는 것이다. 운영 이미지는 CI에서 플랫폼을 명시해서 만든다. 셸 스크립트 엔트리포인트를 Windows에서 편집해 줄 끝이 CRLF가 되면 비슷하게 `no such file or directory`가 나는데, 이건 아키텍처가 아니라 `#!/bin/sh\r`를 찾지 못한 것이다.

### `Cannot find module '/app/dist/server.js'`

```text
node:internal/modules/cjs/loader:1386
  throw err;
  ^

Error: Cannot find module '/app/dist/server.js'
    at Function._resolveFilename (node:internal/modules/cjs/loader:1383:15)
    ...
  code: 'MODULE_NOT_FOUND',
  requireStack: []
}
```

로컬에서는 잘 되던 앱이다. 멀티 스테이지 빌드에서 `COPY --from=build /app/build ./dist`처럼 경로를 틀렸거나, `.dockerignore`에 `dist`를 넣어 놓고 빌드 스테이지가 아니라 컨텍스트에서 복사하려 한 경우가 대부분이다. 추측하지 말고 이미지 안을 본다. distroless나 slim 이미지는 셸이 없을 수 있어서 `docker exec ... sh`가 안 된다. 그럴 땐 컨테이너를 만들기만 하고 파일 목록을 꺼낸다.

```bash
# 실행하지 않고 컨테이너만 만든 뒤, 파일 시스템 목록에서 /app 아래만 본다
id=$(docker create ghcr.io/me/api:1.4.2)
docker export "$id" | tar -t | grep '^app/' | head -n 20
docker rm "$id"

# 빌드 스테이지까지 따로 확인하고 싶으면 그 스테이지만 빌드해 셸로 들어간다
docker build --target build -t api:debug . && docker run --rm -it api:debug sh
```

`app/dist/`가 목록에 없으면 COPY 쪽 문제다. 있는데도 못 찾는다면 `WORKDIR`과 `CMD`의 경로가 어긋났는지 `docker inspect -f '{{.Config.WorkingDir}} {{json .Config.Cmd}}'`로 맞춰 본다.

### root를 버리자 `EACCES`

앞에서 본 대로 `USER 10001`을 넣고 배포했더니 업로드에서 500이 난다.

```text
Error: EACCES: permission denied, open 'uploads/a.png'
    at Object.writeFileSync (node:fs:2437:20)
    ...
  errno: -13,
  code: 'EACCES',
  syscall: 'open',
  path: 'uploads/a.png'
}
```

`/app`과 그 아래 파일은 `COPY`가 만들었으니 root 소유이고, UID 10001은 거기에 쓸 수 없다. 고치는 방법은 앱이 쓰는 디렉터리를 정해 두고 그 디렉터리만 소유자를 바꾸는 것이다. `/app` 전체를 `chmod 777`로 여는 건 앱 코드까지 고칠 수 있게 만드는 셈이라 피한다.

```dockerfile
# 쓰기가 필요한 디렉터리만 만들고 앱 사용자에게 준다
RUN mkdir -p /app/uploads && chown 10001:10001 /app/uploads
USER 10001:10001
```

애초에 업로드를 컨테이너 안에 쓰면 컨테이너를 다시 만들 때 사라지니 볼륨이나 오브젝트 스토리지로 빼야 맞다. 볼륨을 붙이면 소유자 문제가 볼륨 쪽에서 다시 나오는데, 그 이야기는 [Docker 네트워크와 볼륨](/posts/docker-network-volume)의 UID 부분에 있다. 쿠버네티스에서 `readOnlyRootFilesystem: true`를 켜면 `/tmp`까지 못 쓰게 되니 `emptyDir`를 붙여 준다.

## 처음 문제로 돌아가면

이미지는 Dockerfile 명령이 만든 레이어를 쌓은 것이고, 빌드 캐시는 위에서부터 입력이 같은지 비교하다가 처음 다른 줄에서 끊긴다. 그래서 잘 안 바뀌는 것(베이스, 의존성 목록, 설치)을 위에, 자주 바뀌는 것(소스)을 아래에 두면 README를 고친 PR에서 `npm ci`가 다시 돌 일이 없다. 1GB짜리 이미지는 멀티 스테이지 빌드로 빌드 도구를 버리고 slim이나 distroless 위에 결과물만 올리면 처음의 몇 분의 일로 줄어든다. 여기에 exec 형식의 `CMD`, 일반 사용자, HEALTHCHECK를 더하면 운영에 올릴 만한 이미지가 된다.

## 면접에서 나올 만한 질문

### Docker 이미지 레이어는 어떻게 만들어지나요?

Dockerfile에서 파일 시스템을 바꾸는 `RUN`, `COPY`, `ADD`가 각각 읽기 전용 레이어 한 장을 만들고, `ENV`, `CMD` 같은 명령은 설정만 바꾼다. 레이어는 위에 쌓이기만 해서, 아래 레이어의 파일을 위에서 지워도 크기는 줄지 않고 whiteout 표시만 남는다. 그래서 설치와 정리는 같은 `RUN` 안에서 하고, 비밀 파일은 레이어에 아예 넣지 않는다.

### 빌드 캐시는 언제 깨지나요? Dockerfile 순서는 어떻게 잡나요?

BuildKit은 위에서부터 부모 레이어와 명령이 같은지 보고, `COPY`·`ADD`는 파일 내용 체크섬까지 비교한다. 한 줄이 깨지면 그 아래는 모두 다시 실행된다. 그래서 의존성 목록을 먼저 복사해 설치하고 소스는 마지막에 복사한다. `RUN`은 명령 문자열만 비교하므로 `apt-get update`를 따로 두면 오래된 목록이 캐시될 수 있다.

### CMD와 ENTRYPOINT는 어떻게 다른가요?

실행되는 명령은 `ENTRYPOINT` 뒤에 `CMD`를 붙인 것이다. `ENTRYPOINT`는 고정된 실행 파일이고 `CMD`는 기본 인자라서, `docker run` 뒤에 쓴 인자는 `CMD`를 대체하고 `ENTRYPOINT`는 `--entrypoint`로만 바뀐다. 엔트리포인트 스크립트를 쓴다면 마지막에 `exec "$@"`로 PID 1을 앱에 넘긴다.

### exec 형식과 셸 형식은 무엇이 다른가요?

exec 형식(JSON 배열)은 프로그램을 바로 실행해서 앱이 PID 1이 되고, 셸 형식은 `/bin/sh -c`로 감싸서 셸이 PID 1이 된다. 셸은 SIGTERM을 자식에게 넘기지 않고 PID 1은 핸들러 없는 시그널을 무시해서, `docker stop`이 10초 기다린 뒤 SIGKILL로 끝난다. 그래서 `CMD ["node", "dist/server.js"]`처럼 exec 형식을 쓰고, 변수 확장이 필요하면 스크립트에서 `exec`로 넘긴다.

### ARG와 ENV의 차이는요? 빌드에 필요한 비밀 값은 어떻게 넘기나요?

`ARG`는 빌드하는 동안에만 있고 `--build-arg`로 바꾸며, `ENV`는 이미지에 남아 컨테이너 실행 때도 환경 변수로 보인다. 둘 다 `docker history`나 이미지 설정에서 값이 보일 수 있으니 비밀 값에는 쓰지 않는다. BuildKit의 `RUN --mount=type=secret`을 쓰면 그 `RUN` 동안만 파일로 보이고 레이어와 기록에 남지 않는다.

### 멀티 스테이지 빌드는 왜 쓰나요?

빌드에만 필요한 컴파일러, devDependencies, 소스 원본을 운영 이미지에서 빼려고 쓴다. 앞 스테이지에서 빌드하고 마지막 스테이지에는 `COPY --from`으로 결과물만 복사하니 이미지가 작아지고, 공격자가 쓸 도구와 스캐너가 잡을 패키지도 줄어든다. 독립된 스테이지는 BuildKit이 병렬로 빌드하고, `--target`으로 테스트 스테이지만 따로 빌드할 수도 있다.

### alpine 이미지가 가장 작은데 왜 항상 쓰지 않나요?

Alpine은 glibc 대신 musl을 써서, glibc용으로 미리 빌드된 네이티브 바이너리나 Python manylinux 휠이 그대로 돌지 않는다. 그러면 소스 컴파일이 필요해져 빌드가 느려지고, DNS 처리나 메모리 할당 성능처럼 glibc와 다른 동작으로 Alpine에서만 나는 문제가 생길 수 있다. 기본은 Debian slim으로 두고, 더 줄여야 하면 glibc 기반 distroless를 검토한다.

### 컨테이너를 root가 아닌 사용자로 돌려야 하는 이유와 방법은요?

Docker는 기본으로 user namespace를 쓰지 않아서 컨테이너 안 root가 호스트에서도 UID 0이고, 앱이 뚫리거나 탈출 취약점이 있으면 피해가 커진다. Dockerfile에 일반 사용자를 만들고 `USER 10001:10001`처럼 숫자로 지정하며, 파일 소유자는 `COPY --chown`으로 맞춘다. 숫자 UID여야 쿠버네티스의 `runAsNonRoot` 검사를 통과하고, 런타임에 따라 1024 아래 포트를 못 열 수 있으니 3000, 8080 같은 높은 포트를 쓴다.
