<EasyIntro>
  Redis 한 대에 담긴 데이터가 40GB를 넘자, 저장할 때마다 서버가 잠깐씩 멈추고 메모리가 튀었다. 복사본 서버를 늘리면 읽기는 나눠도, 모든 쓰기와 모든 데이터는 여전히 한 대가 들고 있다.

  Redis Cluster는 데이터를 여러 서버에 나눠 맡긴다. 번호가 붙은 사물함 16384칸을 서버 몇 대가 나눠 맡고, 데이터 이름을 계산해서 몇 번 칸에 넣을지 정하는 방식이다. 이름이 다르면 같은 회원의 장바구니와 로그인 정보도 다른 서버 칸에 들어갈 수 있다. 그래서 함께 다뤄야 하는 데이터는 이름 안에 같은 꼬리표를 넣어 한 칸에 모은다.

  알아 둘 점은 아무 서버에 물어도 대신 찾아 주지 않고 저쪽 서버로 가라고 알려 줄 뿐이라는 것이다. 그리고 복사본 없이 서버 하나가 죽으면, 기본 설정에서는 살아 있는 서버의 칸까지 모두 문을 닫는다.
</EasyIntro>

상품 캐시와 세션을 한 Redis에 담아 쓰다가 데이터가 40GB를 넘었다. 서버 메모리는 64GB인데, `BGSAVE` 때마다 fork가 수백 ms씩 멈추고 copy-on-write로 메모리가 튀어 오른다. 레플리카를 처음 붙일 때 전체 동기화로 40GB가 네트워크를 지나간다. 레플리카를 늘리면 읽기는 나눌 수 있지만, 모든 쓰기와 모든 데이터는 여전히 프라이머리 한 대가 들고 있다.

한 대의 한계를 넘으려면 데이터를 여러 프라이머리에 나눠야 한다. Redis Cluster는 키 공간을 16384개의 해시 슬롯으로 나누고 슬롯을 노드에 나눠 준다. 대신 공짜는 아니다. 서로 다른 노드에 있는 키는 한 명령으로 다룰 수 없고, 클라이언트는 어느 키가 어느 노드에 있는지 알아야 하며, 노드 하나가 레플리카 없이 죽으면 생각보다 넓게 멈춘다.

복제와 Sentinel은 [복제와 Sentinel 글](/posts/redis-replication-sentinel)에서 봤다. 이 글은 키가 슬롯으로, 슬롯이 노드로 가는 규칙과 해시 태그, 클라이언트가 받는 `MOVED`와 `ASK`, 단일 서버부터 관리형 서비스까지 구성을 고르는 기준을 보고, 끝에서 레플리카 없는 클러스터의 노드 하나를 직접 죽여 본다. 기준은 Ubuntu 24.04 LTS의 `redis-server` 패키지(7.0.15)이고, 예제 키는 [Redis 기본 글](/posts/redis-basics)의 쇼핑몰 것(`session:42`, `cart:42`)이다.

## Cluster는 키를 16384개 슬롯으로 나눈다

한 서버로 버티는 Sentinel 구성은 결국 프라이머리 한 대가 모든 쓰기와 모든 데이터를 감당한다. 데이터가 한 서버 메모리를 넘거나 쓰기가 한 대로 모자라면 Redis Cluster로 데이터를 나눈다.

Cluster는 키 공간을 16384개의 해시 슬롯으로 나누고, 슬롯 범위를 프라이머리들에 나눠 준다. 키가 어느 슬롯에 갈지는 `CRC16(키) mod 16384`로 정해진다. 프라이머리 3대로 만들면 슬롯은 이렇게 나뉜다.

```bash
# 클러스터 모드로 띄운 서버 3대를 묶는다 (실제로는 --cluster-replicas 1로 레플리카도 붙인다)
redis-cli --cluster create 10.0.0.11:6379 10.0.0.12:6379 10.0.0.13:6379
```

```text
>>> Performing hash slots allocation on 3 nodes...
Master[0] -> Slots 0 - 5460
Master[1] -> Slots 5461 - 10922
Master[2] -> Slots 10923 - 16383
```

`cart:42`와 `session:42`는 같은 회원의 데이터인데 서로 다른 노드에 있다. 그래서 둘을 한 명령으로 다룰 수 없다.

```bash
# 서로 다른 슬롯의 키를 한 명령으로
redis-cli -c MSET cart:42 a session:42 b
```

```text
(error) CROSSSLOT Keys in request don't hash to the same slot
```

`MSET`, `MGET`, `SUNION` 같은 여러 키 명령, `MULTI`/`EXEC` 트랜잭션, Lua 스크립트는 모든 키가 같은 슬롯일 때만 된다. 같은 슬롯에 모으는 장치가 해시 태그다. 키에 `{...}`가 있으면 중괄호 안만 해시한다.

```bash
redis-cli CLUSTER KEYSLOT user:42
redis-cli CLUSTER KEYSLOT '{user:42}:cart'
redis-cli CLUSTER KEYSLOT '{user:42}:profile'
redis-cli CLUSTER KEYSLOT foo
```

```text
(integer) 15880
(integer) 15880
(integer) 15880
(integer) 12182
```

`{user:42}:cart`와 `{user:42}:profile`은 둘 다 `user:42`만 해시해서 같은 슬롯이다. 이렇게 지은 키끼리는 트랜잭션도 된다. 규칙에는 세부가 있다. 첫 `{` 뒤에 처음 나오는 `}`까지가 태그이고, 그 사이가 비어 있으면(`{}foo`) 키 전체를 해시한다. `foo{}{bar}`도 첫 태그가 비었으니 전체를 해시한다. 해시 태그를 남용하면 위험하다. 모든 키를 `{shop}`으로 묶으면 전부 한 슬롯, 한 노드로 가서 클러스터를 쓰는 의미가 없어진다. 회원 id처럼 값이 고르게 퍼지는 것으로 태그를 단다.

아래 함수에 키와 노드별 슬롯 범위를 넣으면 `[슬롯, 노드 이름]`을 돌려줘야 한다. CRC16(XMODEM 방식)은 미리 넣어 두었다. 해시 태그 규칙을 지키는 부분과 범위를 찾는 부분을 채워 보자. 테스트의 슬롯 값은 실제 Redis 7.0의 `CLUSTER KEYSLOT` 결과다.

슬롯이 왜 하필 16384개인지는 Redis를 만든 antirez가 설명한 적이 있다. 노드들은 서로 하트비트를 주고받으며 자기가 맡은 슬롯을 비트맵으로 실어 보내는데, 16384비트는 2KB다. 65536개였다면 8KB가 되어 하트비트가 무거워진다. 클러스터가 1000노드를 넘길 일은 없다고 보고 정한 크기다. 노드끼리는 Redis 포트에 10000을 더한 포트(6379면 16379)로 이 클러스터 버스를 연다. 방화벽에서 이 포트도 열어야 한다.

Cluster에는 Sentinel이 필요 없다. 프라이머리들이 서로를 감시하다가, 한 프라이머리가 `cluster-node-timeout`(기본 15초) 넘게 응답이 없고 프라이머리 과반이 동의하면 그 레플리카를 승격한다. 프라이머리는 최소 3대, 각자 레플리카를 하나씩 둔 6대 구성이 기본이다. 복제가 비동기라는 성질은 그대로라서 장애 조치 때 잃는 쓰기가 있을 수 있다는 것도 같다. 또 Cluster에서는 DB 번호가 0 하나뿐이라 `SELECT 1`을 쓸 수 없다.

## MOVED와 ASK

앱이 키의 슬롯이 어느 노드에 있는지 모르고 아무 노드에나 물으면 어떻게 될까. 노드가 프록시처럼 대신 전달해 주지는 않는다. 그 키는 저쪽 노드에 있다고 알려 줄 뿐이다.

```bash
# 노드 A(7001)에 cart:42를 물으면
redis-cli -p 7001 GET cart:42

# -c를 주면 redis-cli가 안내를 따라간다
redis-cli -c -p 7001 GET cart:42
```

```text
(error) MOVED 15749 127.0.0.1:7003
"[1001,1003]"
```

`MOVED 15749 127.0.0.1:7003`은 "슬롯 15749는 이제 7003 담당이니 앞으로 거기로 가라"는 뜻이다. 클러스터를 지원하는 클라이언트는 시작할 때 `CLUSTER SLOTS`(7.0부터는 `CLUSTER SHARDS`도)로 슬롯 지도를 받아 두고 처음부터 맞는 노드로 보낸다. `MOVED`를 받으면 지도를 새로 고친다.

슬롯을 다른 노드로 옮기는 중(resharding)에는 다른 응답이 나온다. 아래 그림은 슬롯 15749를 노드 C에서 A로 옮기는 동안 `cart:42`를 읽는 과정이다.

## 단일 서버부터 관리형 서비스까지

구성은 작은 것부터 시작해, 넘어가야 할 신호가 보일 때 올린다.

단일 서버와 레플리카. 데이터가 한 서버 메모리에 넉넉히 들어가고, 장애 때 몇 분 멈춰도 되는 서비스다. 레플리카는 백업과 수동 장애 조치용이다. 운영 부담이 가장 적다.

Sentinel. 데이터는 한 대에 들어가지만 프라이머리가 죽었을 때 사람을 기다릴 수 없는 서비스다. 세션 저장소가 대표적이다. 프라이머리 1, 레플리카 1~2, Sentinel 3이 흔한 구성이고, 클라이언트가 Sentinel 모드를 지원해야 한다.

Cluster. 데이터가 한 서버의 메모리를 넘거나(예를 들어 수십 GB를 넘어가며 fork와 전체 동기화가 부담스러워질 때), 쓰기가 한 대의 CPU 하나로 모자랄 때다. 대신 여러 키 명령에 해시 태그가 필요하고, 클라이언트가 클러스터를 지원해야 하고, 운영할 노드 수가 늘어난다. 데이터는 작은데 읽기만 많다면 Cluster보다 레플리카를 늘려 읽기를 나누는 게 먼저다.

관리형 서비스. 이 모든 걸 직접 운영하지 않는 방법이다. AWS ElastiCache(Redis OSS·Valkey 엔진, Cluster 모드를 켜거나 끌 수 있다), Azure Cache for Redis, Google Cloud Memorystore가 있다. 장애 조치, 패치, 백업 스냅샷을 대신 해 주지만 복제가 비동기라는 성질은 그대로인 경우가 많으니 서비스 문서에서 장애 조치 때의 유실 가능성을 확인한다. AWS MemoryDB는 쓰기를 여러 가용 영역에 걸친 트랜잭션 로그에 남긴 뒤 응답한다고 설명하는, 주 저장소 용도를 겨냥한 서비스다. 그만큼 쓰기 지연이 더 크다. 어느 쪽이든 엔진 버전, 사용할 수 없는 명령, 가격 구조가 서비스마다 다르니 고를 때 그 시점의 문서를 확인한다.

## 현장에서 노드 하나가 죽었을 때

레플리카 없이 프라이머리 셋만으로 클러스터를 만들면 노드 하나가 죽었을 때 어떻게 될까. 개발 환경이나 비용을 아끼려는 구성에서 흔하다. 7001~7003 포트로 띄우고 7003(슬롯 10923~16383 담당)을 내렸다.

```bash
# 클러스터 모드 노드 셋 (장애 판단을 빨리 보려고 node-timeout 5초)
for p in 7001 7002 7003; do
  redis-server --port $p --cluster-enabled yes --cluster-config-file nodes-$p.conf \
    --cluster-node-timeout 5000 --save "" --appendonly no --daemonize yes
done
redis-cli --cluster create 127.0.0.1:7001 127.0.0.1:7002 127.0.0.1:7003

redis-cli -c -p 7001 SET cart:42 '[1001,1003]'   # 슬롯 15749, 7003으로 간다
redis-cli -c -p 7001 SET session:42 s            # 슬롯 2126, 7001에 있다

# 7003을 내리고 node-timeout이 지나기를 기다린다
redis-cli -p 7003 SHUTDOWN NOSAVE
sleep 8
redis-cli -p 7001 CLUSTER INFO | head -5
redis-cli -c -p 7001 GET session:42
```

```text
cluster_state:fail
cluster_slots_assigned:16384
cluster_slots_ok:10923
cluster_slots_pfail:0
cluster_slots_fail:5461
(error) CLUSTERDOWN The cluster is down
```

`cluster_slots_fail:5461`은 죽은 노드가 맡던 슬롯 수다. 그런데 살아 있는 7001에 있는 `session:42`까지 `CLUSTERDOWN`으로 거절됐다. 기본값 `cluster-require-full-coverage yes`는 슬롯이 하나라도 담당 노드 없이 남으면 클러스터 전체가 요청을 받지 않게 한다. 데이터 일부만 보이는 상태로 돌기보다 확실히 멈추는 쪽을 고른 것이다. 상황 전체는 `--cluster check`가 요약해 준다.

```bash
redis-cli --cluster check 127.0.0.1:7001
```

```text
   slots:[0-5460] (5461 slots) master
M: 464f63b62f4039b486a2918f66f9c4b253a8e260 127.0.0.1:7002
   slots:[5461-10922] (5462 slots) master
[OK] All nodes agree about slots configuration.
>>> Check for open slots...
>>> Check slots coverage...
[ERR] Not all 16384 slots are covered by nodes.
```

남은 노드의 설정을 `no`로 바꾸면 살아 있는 슬롯은 다시 응답한다.

```bash
redis-cli -p 7001 CONFIG SET cluster-require-full-coverage no
redis-cli -p 7002 CONFIG SET cluster-require-full-coverage no
redis-cli -p 7001 CLUSTER INFO | head -1
redis-cli -c -p 7001 GET session:42
redis-cli -p 7001 GET cart:42
```

```text
OK
OK
cluster_state:ok
"s"
(error) MOVED 15749 127.0.0.1:7003
```

`session:42`는 돌아왔지만 `cart:42`는 여전히 죽은 7003을 가리키는 `MOVED`를 받는다. 클라이언트가 그 안내를 따라가면 연결이 거부된다. 결국 레플리카가 없으면 노드 하나의 장애가 데이터 3분의 1의 장애이거나(`no`), 전체 장애다(`yes`). 그래서 운영 클러스터는 프라이머리마다 레플리카를 두는 6대 구성(`--cluster-replicas 1`)이 기본이고, 레플리카가 있으면 `cluster-node-timeout`이 지난 뒤 레플리카가 승격되어 슬롯이 다시 채워진다. `require-full-coverage`를 `no`로 둘지는 "일부 키만 되는 상태"를 서비스가 견딜 수 있는지로 정한다. 세션처럼 키마다 독립적이면 `no`가 나을 수 있고, 여러 키가 함께 맞아야 하는 데이터라면 `yes`가 안전하다. 모니터링에는 `cluster_state`와 `cluster_slots_fail`을 건다.

## 데이터를 나누는 대가

Cluster는 `CRC16(키) mod 16384`로 키를 슬롯에, 슬롯을 노드에 나눠 한 서버의 메모리와 쓰기 한계를 넘는다. 그 대가로 여러 키 명령과 트랜잭션은 같은 슬롯 안에서만 되고(해시 태그로 모은다), 클라이언트는 슬롯 지도를 들고 `MOVED`와 `ASK`를 따라가야 하며, 레플리카 없이 노드 하나가 죽으면 기본 설정에서 클러스터 전체가 멈춘다. 데이터가 한 대에 들어가고 읽기만 많다면 Cluster보다 레플리카와 Sentinel이 먼저다.

## 면접에서 나올 만한 질문

### Redis Cluster에서 MGET이나 트랜잭션을 쓰려면 어떻게 하나요?

Cluster는 CRC16(키) mod 16384로 슬롯을 정하고 슬롯을 노드에 나누므로, 여러 키 명령과 MULTI, Lua 스크립트는 모든 키가 같은 슬롯일 때만 된다. 다르면 CROSSSLOT 에러가 난다. 키에 `{user:42}`처럼 해시 태그를 넣으면 중괄호 안만 해시해서 같은 슬롯에 모인다. 태그를 하나로 몰면 한 노드에 쏠리니 고르게 퍼지는 값으로 단다.

### MOVED와 ASK의 차이는 무엇인가요?

MOVED는 그 슬롯의 담당 노드가 바뀌었다는 영구적인 안내라서 클라이언트가 슬롯 지도를 고친다. ASK는 슬롯을 옮기는 중에 그 키가 이미 새 노드로 갔다는 일시적인 안내라서, 지도는 그대로 두고 이번 요청만 ASKING을 붙여 새 노드로 보낸다. 슬롯 이동이 끝나면 옛 노드는 MOVED를 돌려준다.

### 슬롯은 왜 16384개인가요?

노드들이 하트비트를 주고받을 때 자기가 맡은 슬롯을 비트맵으로 실어 보내는데, 16384비트는 2KB라서다. 65536개였다면 8KB가 되어 하트비트가 무거워진다. 클러스터가 1000노드를 넘을 일은 없다고 보고 정한 크기라고 Redis를 만든 antirez가 설명했다. 노드끼리는 Redis 포트에 10000을 더한 클러스터 버스 포트로 통신하니 방화벽에서 그 포트도 연다.

### Redis Cluster에서 노드 하나가 죽으면 어떻게 되나요?

레플리카가 있으면 다른 프라이머리 과반이 `cluster-node-timeout`(기본 15초) 동안 응답이 없다는 데 동의한 뒤 그 레플리카를 승격하고, 슬롯이 다시 채워진다. 복제는 비동기라 마지막 쓰기를 잃을 수 있다. 레플리카가 없으면 그 노드의 슬롯이 비고, 기본값 `cluster-require-full-coverage yes`에서는 살아 있는 노드의 키까지 `CLUSTERDOWN`으로 거절된다. 그래서 프라이머리 셋에 레플리카 셋인 6대 구성이 기본이다.

### 언제 Sentinel 대신 Cluster를 쓰나요?

데이터가 한 서버 메모리를 넘거나, 수십 GB가 되어 fork와 전체 동기화가 부담스럽거나, 쓰기가 한 대의 CPU로 모자랄 때다. 데이터가 한 대에 넉넉히 들어가고 읽기만 많다면 레플리카를 늘려 읽기를 나누는 게 먼저다. Cluster는 여러 키 명령에 해시 태그가 필요하고, 클라이언트가 클러스터를 지원해야 하며, DB 번호가 0 하나뿐이고, 운영할 노드가 늘어난다.
