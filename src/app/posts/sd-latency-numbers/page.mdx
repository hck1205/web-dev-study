  그래서 자주 쓰는 건 서랍(캐시)에 두고, 심부름 횟수를 줄이고, 외국 손님에게는 그 나라에 사본을 둔다. 덧붙여 저장 크기는 1,024배마다 이름이 바뀌고 회선 속도의 비트와 파일 크기의 바이트는 8배 차이가 나며, 가용성 99.9%와 99.99%는 한 달에 멈춰도 되는 시간이 43분과 4분으로 열 배 다르다.

이 시리즈에서 이 글의 자리: [⑧ 샤딩 입문](/posts/sd-sharding-intro)까지 서버 한 대를 여러 계층으로 키웠다. 이 글부터 두 편은 그 설계를 숫자로 따지는 법을 다룬다. 다음 글은 [⑩ 용량 어림하기](/posts/sd-capacity-estimation)이고, 그 뒤로 [⑪ 설계 면접 진행법](/posts/sd-interview-framework), 첫 사례인 [⑫ 요청 수 제한기 설계](/posts/sd-rate-limiter-design)가 이어진다.

맛집 리뷰 앱의 식당 상세 API가 평균 120ms 걸린다. 팀에서 누군가 "DB가 느려서 그렇다, 더 큰 서버로 바꾸자"라고 한다. 다른 누군가는 "캐시를 붙이면 된다"고 한다. 둘 다 그럴듯하지만, 어느 쪽도 120ms가 어디서 나왔는지 말하지 않는다.

로그를 열어 보니 이 API는 요청 하나를 처리하면서 DB에 쿼리를 21번 보낸다. 식당 하나를 읽고, 리뷰 20개의 작성자를 하나씩 따로 읽는다. 쿼리 하나에 왕복 포함 약 5ms가 걸리면 21번이면 100ms가 넘는다. DB 서버를 두 배 빠른 것으로 바꿔도 네트워크 왕복은 그대로라 크게 줄지 않는다. 쿼리를 두 번으로 줄이면 10ms 근처로 떨어진다.

이렇게 "대략 얼마쯤 걸리는가"를 머릿속으로 계산할 수 있으면 원인을 훨씬 빨리 좁힌다. 그러려면 계산의 재료가 되는 숫자 몇 개를 알고 있어야 한다. 이 글은 그 재료를 모은다. 데이터 크기를 셀 때 쓰는 2의 거듭제곱, 동작마다 걸리는 시간의 크기, 그리고 가용성 목표가 허락하는 멈춤 시간이다.

## 바이트를 세는 두 가지 자

컴퓨터는 2진수로 동작하니 메모리 크기는 2의 거듭제곱으로 딱 떨어진다. 2를 열 번 곱하면 1,024다. 1,000과 거의 같아서 오래전부터 1,024바이트를 1KB라고 불러 왔다. 문제는 디스크 회사와 네트워크 쪽은 같은 KB를 1,000바이트로 쓴다는 점이다. 둘을 구분하려고 1,024 기준은 KiB, MiB, GiB처럼 i를 붙여 부르는 표기가 따로 있다.

어림셈에서는 둘을 섞어 써도 대부분 괜찮다. 다만 단위가 커질수록 차이도 커진다. 직접 계산해 봤다.

```bash
# 2의 거듭제곱과 10의 거듭제곱을 나란히 비교한다
node pow2.js
```

```text
2^10 =                     1,024  KiB  ~ 10^3 천 (KB)    차이 2.4%
2^20 =                 1,048,576  MiB  ~ 10^6 백만 (MB)   차이 4.9%
2^30 =             1,073,741,824  GiB  ~ 10^9 십억 (GB)   차이 7.4%
2^40 =         1,099,511,627,776  TiB  ~ 10^12 조 (TB)    차이 10.0%
2^50 =     1,125,899,906,842,624  PiB  ~ 10^15 천조 (PB)   차이 12.6%
```

킬로바이트에서 2.4%였던 차이가 페타바이트에서는 12.6%가 된다. "1TB 디스크를 샀는데 운영체제에는 931GB로 보인다"는 문의가 이 차이 때문이다. 리눅스의 `numfmt`로 바로 확인할 수 있다.

```bash
# 10^12바이트를 1,024 단위로 읽으면
numfmt --to=iec 1000000000000
# 2^40바이트를 1,000 단위로 읽으면
numfmt --to=si 1099511627776
```

```text
932G
1.1T
```

`numfmt`는 올림해서 932G로 보여 준다(정확히는 931.3GiB). 아래 그림에서 다음을 누르면 거듭제곱이 하나씩 올라가면서 이름이 쌓인다. 2의 10제곱마다 이름이 하나씩 바뀐다는 것만 기억하면 된다.

실무에서 더 자주 틀리는 것은 비트와 바이트다. 네트워크 속도는 비트(b)로, 파일 크기는 바이트(B)로 센다. 1바이트는 8비트라서 1Gbps 회선은 1초에 많아야 125MB를 보낸다. "1기가 회선인데 왜 1GB 파일이 1초에 안 가냐"는 질문은 여기서 이미 8배가 어긋난 것이다. 계산할 때는 숫자 옆에 단위를 꼭 붙여 쓴다.

## 나노초부터 수백 밀리초까지, 지연의 사다리

이제 시간이다. 컴퓨터 안에서 일어나는 동작들은 걸리는 시간이 수천만 배까지 차이 난다. 정확한 값은 하드웨어 세대, 클라우드 인스턴스, 네트워크 경로에 따라 달라지니 외울 것은 정확한 숫자가 아니라 자릿수다. 아래 값은 요즘 서버를 기준으로 흔히 쓰는 어림값이다.

| 동작 | 어림값 | 메모 |
|---|---|---|
| CPU L1 캐시 읽기 | 약 1ns | CPU 코어 바로 옆의 아주 작은 메모리 |
| L2 캐시 읽기 | 수 ns | |
| 메인 메모리 읽기 | 약 100ns | 캐시에 없을 때 |
| 같은 서버 안 Redis 왕복 | 수십 µs | 루프백 TCP |
| NVMe SSD 4KB 무작위 읽기 | 수십~100µs | SATA SSD는 그보다 느리다 |
| 같은 데이터 센터 안 서버 사이 왕복 | 0.1~0.5ms | 클라우드에선 AZ 사이가 1~2ms |
| SSD에서 1MB 순서대로 읽기 | 0.3~1ms | |
| HDD 한 번 찾아가기(seek) | 5~10ms | 바늘이 움직이는 시간 |
| 가까운 나라 사이 왕복(서울-도쿄) | 30ms 안팎 | 경로에 따라 다르다 |
| 대륙 사이 왕복(서울-미국 동부) | 150~200ms | |

단위부터 짚자. 1초는 1,000ms(밀리초), 1ms는 1,000µs(마이크로초), 1µs는 1,000ns(나노초)다. 표의 맨 위와 맨 아래는 1억 배 넘게 차이 난다.

이 사다리에서 설계 원칙 몇 개가 바로 나온다. 메모리는 디스크보다 수백~수천 배 빠르니 자주 읽는 것은 메모리에 둔다([⑤ 캐시 계층](/posts/sd-cache-and-cdn-tier)이 이 이유로 있다). 네트워크 왕복은 메모리 접근보다 수천 배 비싸니 왕복 횟수를 줄인다. 멀리 있는 데이터 센터까지의 왕복은 어떤 최적화로도 줄일 수 없으니 사용자 가까이에 사본을 둔다.

## 이 컴퓨터에서 직접 재 보기

표의 숫자를 그대로 믿기보다 한 번 재 보는 편이 오래 남는다. 이 블로그의 실습 환경(4코어 클라우드 VM, Ubuntu 24.04, Node 22)에서 Node 스크립트로 몇 가지를 쟀다.

메모리는 배열을 "앞 칸에 적힌 번호의 칸으로 이동"하는 식으로 따라가며 읽었다. 이렇게 해야 CPU가 다음에 읽을 곳을 미리 알 수 없어서 한 번 읽을 때마다 기다림이 그대로 드러난다. 배열 크기를 16KB, 512KB, 256MB로 바꿔 가며 L1 캐시 안, L2 근처, 메모리 전체를 쓰게 했다. 이어서 4KB를 쓰고 `fsync`로 디스크까지 내려보내는 시간, 같은 컴퓨터 안에서 TCP로 1바이트를 주고받는 시간을 쟀다.

```bash
# 메모리 따라가기, fsync, 루프백 TCP 왕복을 잰다 (두 번 실행)
node latency.js
```

```text
따라가며 읽기 16KB (L1 캐시 안)     2.1 ns / 번
따라가며 읽기 512KB (L2 근처)      7.1 ns / 번
따라가며 읽기 256MB (메모리)        203.5 ns / 번
4KB 쓰기 + fsync                 345.1 µs / 번
localhost TCP 왕복               31.4 µs / 번

따라가며 읽기 16KB (L1 캐시 안)     2.1 ns / 번
따라가며 읽기 512KB (L2 근처)      9.0 ns / 번
따라가며 읽기 256MB (메모리)        233.0 ns / 번
4KB 쓰기 + fsync                 120.8 µs / 번
localhost TCP 왕복               21.8 µs / 번
```

자릿수는 표와 맞는다. 몇 가지는 짚어 둘 만하다. 메모리가 표의 100ns보다 두 배쯤 느린 것은 JavaScript 배열 접근 비용에, 큰 배열을 무작위로 돌아다니며 생기는 주소 변환(TLB) 미스와 가상 머신의 오버헤드가 더해져서다. `fsync`는 같은 스크립트를 두 번 돌렸는데 345µs와 121µs로 세 배 가까이 차이 난다. 디스크가 다른 일을 하고 있었는지에 따라 흔들린다. DB가 커밋할 때마다 이 `fsync`를 부르니 커밋 지연도 그만큼 흔들린다.

Redis도 같은 서버에서 띄우고 클라이언트 하나로 쟀다. `redis-benchmark`는 요청을 하나 보내고 답을 받은 뒤 다음을 보내니, 초당 처리량의 역수가 왕복 시간이다.

```bash
# 연결 하나(-c 1)로 PING과 GET을 2만 번씩 보낸다
redis-benchmark -p 16391 -t ping_mbulk,get -n 20000 -c 1 -q
```

```text
PING_MBULK: 63291.14 requests per second, p50=0.015 msec
GET: 56657.23 requests per second, p50=0.015 msec
```

초당 6만 번 안팎이면 한 번에 16~18µs이고, 중앙값(p50)은 15µs다. 같은 데이터 센터의 다른 서버에 있는 Redis라면 여기에 네트워크 왕복이 더해져 0.2~0.5ms 정도가 된다. 같은 서버 안에서 잰 값과 실제 운영 값이 열 배 넘게 다를 수 있다는 점도 기억해 둔다.

디스크는 `dd`에 `iflag=direct`를 줘서 운영체제의 캐시를 건너뛰고 읽었다.

```bash
# 64MB 파일을 만들고, 4KB씩 2,000번 읽은 뒤, 1MB씩 통째로 읽는다
dd if=/dev/zero of=dd.bin bs=1M count=64 oflag=direct status=none
dd if=dd.bin of=/dev/null bs=4k count=2000 iflag=direct
dd if=dd.bin of=/dev/null bs=1M iflag=direct
```

```text
8192000 bytes (8.2 MB, 7.8 MiB) copied, 0.112709 s, 72.7 MB/s
67108864 bytes (67 MB, 64 MiB) copied, 0.040905 s, 1.6 GB/s
```

첫 줄은 4KB를 2,000번 읽는 데 0.113초, 한 번에 약 56µs다. 둘째 줄은 같은 디스크인데 1MB 단위로 읽으니 초당 1.6GB가 나온다. 작은 조각을 여러 번 읽으면 매번 기다림이 붙어서 처리량이 스무 배 넘게 떨어진다. DB가 데이터를 페이지 단위로 묶어 읽고, 로그를 한 파일 끝에 이어 쓰는 이유가 여기 있다.

## 거리는 빛의 속도가 정한다

데이터 센터 사이의 지연은 하드웨어를 바꿔서 줄일 수 없다. 신호가 광섬유를 지나는 속도는 빛의 속도의 약 3분의 2, 초당 약 20만 km다. 1,000km를 가는 데 5ms, 왕복이면 10ms가 든다.

서울에서 미국 버지니아까지 지구 표면을 따라 잰 직선 거리는 약 11,100km다. 광섬유가 완벽한 직선으로 깔려 있어도 왕복에 111ms가 든다. 실제 케이블은 바다와 대륙을 돌아가고 중간 장비도 거치니 측정값은 보통 150~200ms다. 도쿄는 약 1,150km라서 이론상 최소 왕복이 12ms쯤이고 실제로는 30ms 안팎이다. 아래 그림에서 다음을 누르면 서울의 사용자가 세 곳의 데이터 센터에 한 번씩 다녀온다.

## 아홉 개수와 멈춰도 되는 시간

마지막 숫자는 가용성이다. 가용성(availability)은 전체 시간 중 서비스가 제대로 응답한 시간의 비율이다. 99.9%처럼 9가 몇 개인지로 말해서 "아홉 세 개(three nines)"라고 부른다. 퍼센트로만 보면 99.9와 99.99는 비슷해 보이지만, 멈춰도 되는 시간으로 바꾸면 차이가 확 드러난다.

```bash
# 가용성 목표별 허용 멈춤 시간 (1년 365일, 30일, 하루)
node nines.js
```

```text
99     % 1년 3.65일     30일 7.20시간    하루 14.40분
99.9   % 1년 8.76시간    30일 43.20분    하루 1.44분
99.95  % 1년 4.38시간    30일 21.60분    하루 43.2초
99.99  % 1년 52.56분    30일 4.32분     하루 8.6초
99.999 % 1년 5.26분     30일 25.9초     하루 0.9초
```

9가 하나 늘 때마다 허용 시간이 10분의 1로 준다. 99.9%면 한 달에 43분이니 사람이 알림을 받고 노트북을 열어 고칠 시간이 있다. 99.99%면 한 달에 4분 남짓이라 사람이 손대기 전에 자동으로 넘어가는 장치가 있어야 한다. 99.999%는 배포 한 번 잘못해도 1년 치를 다 쓴다.

그래서 아홉 하나는 공짜가 아니다. 서버를 두 대로, 데이터 센터를 두 곳으로 늘리는 비용이 붙는다. 여러 부품을 직렬과 병렬로 이었을 때 전체 가용성을 계산하는 법은 [고가용성](/posts/high-availability)에서, 이 숫자를 실제 목표로 정하고 재는 법은 [SLI와 SLO](/posts/sli-slo)에서 다룬다.

## 숫자를 외울 때 자주 하는 실수

첫째, 정확한 값을 외우려 한다. 표의 숫자는 몇 년마다 바뀐다. SSD는 계속 빨라졌고 클라우드 디스크는 네트워크를 거쳐 붙어 있어서 로컬 SSD보다 느리다. 외울 것은 "메모리는 ns, SSD는 µs, 데이터 센터 안 왕복은 1ms 미만, 대륙 사이는 100ms 이상"이라는 자릿수다.

둘째, 평균으로 생각한다. 위의 `fsync`처럼 같은 동작도 때에 따라 몇 배씩 흔들린다. 사용자가 느끼는 것은 평균보다 느린 쪽 꼬리다. 응답 시간을 백분위로 읽는 법은 [응답 시간 백분위](/posts/percentile-latency)에서 다룬다.

셋째, 지연과 처리량을 섞는다. 회선을 10Gbps로 올려도 서울-버지니아 왕복은 그대로 180ms다. 굵기와 길이는 다른 문제다. 이 구분은 [지연, 대역폭, 처리량](/posts/latency-bandwidth-throughput)에서 자세히 다룬다.

넷째, 개발 PC에서 잰 값을 운영 값으로 쓴다. 위에서 본 것처럼 같은 서버 안의 Redis 왕복과 다른 서버의 Redis 왕복은 열 배 넘게 다르다. 운영 환경과 같은 배치에서 다시 잰다.

## 면접에서 나올 만한 질문

### 메모리와 디스크, 네트워크의 지연은 대략 얼마나 차이 나나요?

메모리 접근은 100ns 안팎, NVMe SSD 무작위 읽기는 수십~100µs, 같은 데이터 센터 안 왕복은 0.1~0.5ms, 대륙 사이 왕복은 150ms 이상이다. 메모리와 SSD는 수백 배, 데이터 센터 안과 대륙 사이는 수백 배 차이가 난다. 정확한 값은 하드웨어마다 다르니 자릿수로 기억하고, 필요하면 그 환경에서 직접 잰다.

### 응답이 느린 API가 있습니다. 숫자로 어떻게 원인을 좁히나요?

요청 하나 안에서 무엇을 몇 번 부르는지부터 센다. 쿼리 하나가 2ms여도 21번이면 40ms가 넘으니, 서버를 키우기보다 왕복 횟수를 줄이는 게 먼저다. 분산 추적에서 짧은 호출이 계단처럼 이어져 있으면 N+1 패턴이고, 한 구간만 길면 그 구간의 디스크나 락을 본다.

### 서버를 더 좋은 것으로 바꿨는데 미국 사용자의 응답 시간이 그대로입니다. 왜 그럴까요?

지연의 대부분이 서울과 미국 사이의 왕복이기 때문이다. 광섬유 속도로 계산해도 서울-버지니아 왕복은 최소 110ms가 넘고 실제로는 150~200ms다. 이건 서버 성능과 상관없으니 CDN이나 미국 리전에 사본을 두고, 화면 하나에 필요한 왕복 횟수를 줄여야 한다.

### 1Gbps 회선이면 1GB 파일을 몇 초에 보낼 수 있나요?

이상적으로도 8초 남짓 걸린다. 네트워크 속도는 비트, 파일은 바이트로 세니 1Gbps는 초당 125MB다. 실제로는 TCP 헤더와 혼잡 제어, 상대편 디스크 속도 때문에 그보다 느리다. 계산할 때 단위를 붙여 쓰면 이런 8배 실수를 막을 수 있다.

### 99.9%와 99.99% 가용성은 운영에서 무엇이 다른가요?

30일 기준 허용 멈춤 시간이 43분과 4분 남짓으로 열 배 차이 난다. 43분이면 사람이 알림을 받고 고칠 수 있지만, 4분이면 사람이 손대기 전에 자동으로 장애 조치가 끝나야 한다. 그래서 아홉 하나를 올리면 이중화, 자동 전환, 배포 방식까지 바뀌고 비용도 크게 는다.

### 같은 동작인데 잴 때마다 시간이 크게 다릅니다. 어떤 숫자를 써야 하나요?

평균 하나가 아니라 분포를 본다. `fsync`처럼 디스크가 바쁜지에 따라 몇 배씩 흔들리는 동작이 많고, 사용자는 그 느린 꼬리를 체감한다. 설계할 때는 p50으로 대략을 잡고 p99로 타임아웃과 여유 용량을 정한다.

### 이 숫자들을 실제 설계 결정과 어떻게 연결하나요?

메모리가 디스크보다 수백 배 빠르니 자주 읽는 데이터는 캐시에 둔다. 왕복이 비싸니 여러 호출을 묶거나 병렬로 보낸다. 거리는 줄일 수 없으니 사용자 가까이에 사본을 둔다. 디스크는 작은 조각을 여러 번 읽는 것보다 큰 덩어리를 순서대로 읽는 게 수십 배 빠르니 로그는 이어 쓰고 데이터는 페이지로 묶는다.
