0, 1, 2만 들어 있는 배열을 정렬하라는 문제를 받으면 `sort()` 한 줄이 먼저 떠오른다. 그걸로도 통과한다. 그런데 면접관은 바로 "정렬 함수 없이, 한 번만 훑어서, 추가 메모리 없이"라고 조건을 붙인다. 이 조건 하나 때문에 문제가 투 포인터 문제로 바뀐다.

[LeetCode 75. Sort Colors](https://leetcode.com/problems/sort-colors/)는 네덜란드 국기 문제(Dutch National Flag)라는 이름으로 더 유명하다. 다익스트라가 낸 문제로, 국기의 세 줄처럼 세 값을 세 구역으로 나눈다. [투 포인터 패턴 글](/posts/two-pointers-pattern)의 "포인터가 셋이 되는 경우"에서 기본 코드를 봤다. 이 글은 거기서 더 들어가 다섯 가지 풀이를 느린 것부터 보고, 세 포인터 풀이가 왜 맞는지 불변식으로 따지고, 갈래 하나만 바꿔도 틀리는 입력을 직접 찾아본다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 세 가지 값을 제자리에서 세 구역으로

문제를 내 말로 줄이면 이렇다. 배열 `nums`에는 0(빨강), 1(하양), 2(파랑)만 들어 있다. 이 배열을 오름차순으로 바꾼다. 새 배열을 돌려주는 게 아니라 `nums` 자체를 고친다(제자리 정렬, in-place). 라이브러리 정렬 함수는 쓰지 말라고 한다.

손으로 하나 풀어 보자.

```text
nums = [2, 0, 1, 2, 0, 1]

0이 2개, 1이 2개, 2가 2개
→ [0, 0, 1, 1, 2, 2]
```

풀이를 고를 때 영향을 주는 제약은 두 가지다. 길이는 최대 300이라 사실 어떤 풀이를 써도 시간은 넉넉하다. 이 문제의 난이도는 시간 제한이 아니라 추가 조건에서 나온다. 문제 끝에 "상수 공간으로 한 번만 훑는 풀이를 떠올릴 수 있나"라는 후속 질문이 붙어 있다. 면접에서도 거의 항상 그 질문까지 간다.

## 정렬 함수 한 줄로 끝내기

정렬하라고 했으니 정렬한다.

```js
// 풀이 1: 내장 정렬
function sortColors(nums) {
  nums.sort((a, b) => a - b); // 제자리에서 정렬한다
}
```

시간은 O(n log n)이다. 공간은 언어마다 다르다. V8의 `Array.prototype.sort`는 TimSort라 최대 O(n) 보조 공간을 쓸 수 있다([정렬 알고리즘](/posts/sorting-algorithms) 글의 "V8의 sort는 TimSort다" 참고).

여기서 하나 짚을 게 있다. 이 문제에서는 비교 함수 없이 `nums.sort()`만 써도 결과가 맞는다. JavaScript의 기본 정렬은 값을 문자열로 바꿔 사전 순으로 비교하는데, "0", "1", "2"는 한 글자라 사전 순과 숫자 순이 같기 때문이다.

```text
> [2, 0, 1].sort()
[ 0, 1, 2 ]
```

우연히 맞는 것이다. 값이 10 이상인 배열로 옮기면 바로 깨진다. 습관처럼 비교 함수를 붙인다.

이 풀이의 한계는 문제의 조건 자체다. 정렬 함수를 쓰지 말라고 했고, 값이 세 종류뿐인데 일반 비교 정렬의 O(n log n)을 내는 건 정보를 버리는 일이다. 값이 세 종류라는 걸 써먹어야 한다.

## 몇 개인지 세고 다시 칠한다

값이 세 종류뿐이니 개수만 알면 배열을 다시 만들 수 있다. 계수 정렬(counting sort)이다. 첫 번째로 훑을 때 0, 1, 2가 각각 몇 개인지 세고, 두 번째로 훑을 때 앞에서부터 0을 그 개수만큼, 1을 그 개수만큼, 2를 그 개수만큼 덮어쓴다.

```js
// 풀이 2: 개수 세기 + 덮어쓰기 (두 번 훑기)
function sortColors(nums) {
  const cnt = [0, 0, 0];
  for (const x of nums) cnt[x]++;          // 1번째 훑기: 0, 1, 2의 개수
  let i = 0;
  for (let v = 0; v < 3; v++)              // 2번째 훑기: 값 순서대로 다시 칠한다
    for (let k = 0; k < cnt[v]; k++) nums[i++] = v;
}
```

`[2, 0, 1, 2, 0, 1]`이면 `cnt`는 `[2, 2, 2]`가 되고, 앞에서부터 0, 0, 1, 1, 2, 2로 덮어쓴다. 시간은 O(n), 공간은 개수 배열 세 칸이라 O(1)이다. 값의 종류가 k개면 O(n + k)인데 여기서는 k = 3이다.

복잡도로는 이미 최적이다. 그래도 면접관이 만족하지 않는 이유가 두 가지 있다. 하나는 배열을 두 번 훑는다는 것이다. 후속 질문이 바로 "한 번에"를 요구한다. 다른 하나는 값을 "다시 만든다"는 점이다. 원소가 숫자 0, 1, 2가 아니라 색 필드를 가진 객체(주문, 티켓 같은)라면 개수만 세서 다시 칠할 수가 없다. 원래 원소를 옮겨야 한다. 이 차이는 뒤의 "원소가 숫자가 아니라 객체라면"에서 다시 본다.

## 두 번 나눠 담기

원소를 실제로 옮기면서 두 번 훑는 방법도 있다. [Move Zeroes](/posts/leetcode-move-zeroes)에서 쓰는 쓰기 포인터를 두 번 쓴다.

1. 쓰기 포인터 `w = 0`에서 시작해 배열을 훑는다. 0을 만나면 `w` 자리와 바꾸고 `w`를 한 칸 민다. 끝나면 0이 모두 앞에 모인다.
2. `w`부터 다시 훑는다. 이번엔 1을 만나면 `w` 자리와 바꾼다. 끝나면 1이 0들 바로 뒤에 모이고, 2는 저절로 맨 뒤에 남는다.

```js
// 풀이 3: 같은 방향 포인터로 두 번 나누기
function sortColors(nums) {
  let w = 0;                                       // 다음에 0(그다음엔 1)을 놓을 자리
  for (let r = 0; r < nums.length; r++)
    if (nums[r] === 0) { [nums[w], nums[r]] = [nums[r], nums[w]]; w++; }
  for (let r = w; r < nums.length; r++)            // 0 뒤부터 1을 모은다
    if (nums[r] === 1) { [nums[w], nums[r]] = [nums[r], nums[w]]; w++; }
}
```

이 풀이는 원소를 바꾸기(swap)만 하니까 원소가 객체여도 그대로 쓸 수 있다. 시간은 두 번 훑어서 O(n), 공간은 O(1)이다. 남은 건 "한 번에"다. 첫 번째 훑기에서 1과 2를 구분하지 않고 지나가기 때문에 두 번째 훑기가 필요하다. 한 번 지나갈 때 세 값을 모두 제 구역에 보내려면 포인터가 하나 더 필요하다.

## 세 포인터가 지키는 네 구역

한 번에 끝내는 풀이는 배열을 네 구역으로 나눠서 생각한다. 포인터는 `lo`, `mid`, `hi` 세 개다.

```text
 [ 0 0 0 | 1 1 1 | ? ? ? ? | 2 2 2 ]
  0      lo      mid     hi       n-1

[0, lo)        이미 0으로 확정
[lo, mid)      이미 1로 확정
[mid, hi]      아직 안 본 칸
(hi, n-1]      이미 2로 확정
```

처음에는 `lo = mid = 0`, `hi = n - 1`이라 배열 전체가 "아직 안 본 칸"이다. 이제 `mid`가 가리키는 값을 하나 보고, 그 값을 제 구역에 붙인다.

- 0이면 `lo` 자리와 바꾸고 `lo`와 `mid`를 둘 다 한 칸 민다. 0 구역이 한 칸 늘고, 밀려난 1이 1 구역 끝으로 간다.
- 1이면 이미 1 구역 바로 뒤에 있다. `mid`만 한 칸 민다.
- 2면 `hi` 자리와 바꾸고 `hi`만 한 칸 당긴다. `mid`는 그대로 둔다.

반복할 때마다 "아직 안 본 칸"이 정확히 한 칸 줄어든다(0과 1이면 `mid`가 늘고, 2면 `hi`가 준다). 그래서 `mid > hi`가 되는 순간, 즉 안 본 칸이 없어지는 순간 끝나고, 그때까지 정확히 n번 반복한다.

`hi`와 바꾼 뒤 `mid`를 그대로 두는 장면이 두 번(1단계, 5단계) 나온다. 5단계에서 가져온 값은 0이었다. 만약 그때 `mid`를 같이 밀었다면 그 0은 3번 칸에 남은 채로 끝났을 것이다. 반대로 `lo`와 바꿀 때는 `mid`를 같이 민다. `lo` 자리에서 가져오는 값은 `[lo, mid)` 구역, 즉 이미 본 1이기 때문이다(`lo === mid`일 때는 자기 자신과 바꾸는 것이라 역시 본 값이다). 앞에서 오는 값은 이미 봤고 뒤에서 오는 값은 아직 안 봤다. 두 갈래가 비대칭인 이유가 이것 하나다.

```js
// 풀이 4: 세 포인터 (네덜란드 국기, 한 번 훑기)
function sortColors(nums) {
  let lo = 0, mid = 0, hi = nums.length - 1; // [0,lo)=0, [lo,mid)=1, [mid,hi]=미확인, (hi,끝]=2
  while (mid <= hi) {                          // 안 본 칸이 남아 있는 동안
    if (nums[mid] === 0) {
      [nums[lo], nums[mid]] = [nums[mid], nums[lo]];
      lo++;
      mid++;                                   // lo에서 온 값은 이미 본 1이다
    } else if (nums[mid] === 1) {
      mid++;
    } else {
      [nums[mid], nums[hi]] = [nums[hi], nums[mid]];
      hi--;                                    // hi에서 온 값은 아직 안 봤다. mid는 그대로
    }
  }
}
```

시간은 O(n)이고 반복 횟수는 정확히 n번이다. 공간은 포인터 세 개라 O(1)이다. 바꾸기 횟수는 입력에 따라 다르다. `[2, 2, 2, 2, 2, 0]`처럼 2가 많으면 거의 매번 바꾸고, 1만 있으면 한 번도 바꾸지 않는다.

### 이 풀이가 맞는다는 걸 말로 보이기

면접에서 "왜 맞나요?"라고 물으면 불변식으로 답한다. 불변식은 반복이 몇 번 돌든 매번 시작할 때 참인 성질이다. 여기서는 위에 적은 네 구역 그 자체다.

1. 처음에는 0, 1, 2 구역이 모두 비어 있으니 참이다.
2. 한 번 반복할 때 세 갈래 모두 구역 정의를 지킨다. 0 갈래는 `lo` 칸에 0을 놓고(0 구역이 한 칸 는다), `mid - 1` 칸에 1이 놓인다(1 구역이 한 칸 오른쪽으로 민다). 1 갈래는 1 구역을 한 칸 늘린다. 2 갈래는 `hi` 칸에 2를 놓고 2 구역을 한 칸 늘리며, 가져온 값은 미확인 구역 안에 남는다.
3. 매번 미확인 구역이 한 칸 줄어드니 반드시 끝나고, 끝날 때 미확인 구역은 비어 있다. 남은 세 구역이 0, 1, 2 순서이니 정렬이 끝난 것이다.

이 세 줄을 말할 수 있으면 갈래를 바꾸는 꼬리 질문에도 흔들리지 않는다. "2를 바꾼 뒤 mid를 왜 안 미나요?"는 2번의 "가져온 값은 미확인 구역 안에 남는다"로 답이 된다.

### Python과 Java에서 같은 세 포인터

```python
from typing import List

def sort_colors(nums: List[int]) -> None:
    lo, mid, hi = 0, 0, len(nums) - 1     # [0, lo)=0, [lo, mid)=1, (hi, 끝]=2
    while mid <= hi:
        if nums[mid] == 0:
            nums[lo], nums[mid] = nums[mid], nums[lo]
            lo += 1
            mid += 1
        elif nums[mid] == 1:
            mid += 1
        else:
            nums[mid], nums[hi] = nums[hi], nums[mid]
            hi -= 1                       # 가져온 값은 아직 안 봤다
```

Python은 튜플 대입으로 두 칸을 한 줄에 바꾼다. LeetCode의 Python 템플릿은 반환형이 `None`이라 아무것도 돌려주지 않는다. 실수로 `nums = sorted(nums)`라고 쓰면 지역 변수 이름만 새 리스트를 가리키게 되고 원래 리스트는 그대로라 틀린다. 꼭 바꿔 써야 한다면 `nums[:] = ...`처럼 슬라이스에 대입한다.

```java
class Solution {
    public void sortColors(int[] nums) {
        int lo = 0, mid = 0, hi = nums.length - 1; // [0, lo)=0, [lo, mid)=1, (hi, 끝]=2
        while (mid <= hi) {
            if (nums[mid] == 0) swap(nums, lo++, mid++);
            else if (nums[mid] == 1) mid++;
            else swap(nums, mid, hi--);           // mid는 그대로
        }
    }
    private void swap(int[] a, int i, int j) { int t = a[i]; a[i] = a[j]; a[j] = t; }
}
```

Java는 바꾸기를 함수로 빼면 `swap(nums, lo++, mid++)`처럼 후위 증가를 인자에 넣을 수 있다. 인자는 증가 전 값으로 넘어가고 호출 뒤에 증가가 반영되어 있다. 짧아지지만 처음 읽는 사람에게는 헷갈릴 수 있으니 면접에서는 풀어 써도 된다. `hi`가 -1에서 시작하는 빈 배열은 `mid <= hi`가 처음부터 거짓이라 반복이 돌지 않는다. 세 언어 모두 같은 결과를 냈다.

```text
[0, 0, 1, 1, 2, 2]
[0, 1, 2]
[0]
[1, 2, 2]
```

`[2, 0, 1, 2, 0, 1]`, `[1, 2, 0]`, `[0]`, `[2, 2, 1]`을 넣은 결과다.

## 한 번 훑으며 덧칠하기

한 번에 끝내는 방법이 하나 더 있다. 풀이 2의 "다시 칠하기"를 한 번 훑는 동안 해 버린다. 포인터 `p0`(다음에 0을 칠할 자리)와 `p1`(다음에 1을 칠할 자리)을 두고, 칸 `i`를 읽을 때마다 이렇게 한다.

1. 읽은 값을 `v`에 저장하고, `i` 칸을 일단 2로 칠한다.
2. `v`가 1 이하면 `p1` 칸을 1로 칠하고 `p1`을 민다.
3. `v`가 0이면 `p0` 칸을 0으로 칠하고 `p0`을 민다.

페인트를 덧칠하는 것과 같다. 모든 칸을 먼저 2로 칠하고, 1 이하인 값이 나올 때마다 1 페인트가 한 칸 더 오른쪽까지 덮고, 0이 나올 때마다 0 페인트가 한 칸 더 덮는다. 0 페인트는 1 페인트 위에, 1 페인트는 2 페인트 위에 칠해진다.

```js
// 풀이 5: 한 번 훑으며 덧칠하기
function sortColors(nums) {
  let p0 = 0, p1 = 0;               // 다음에 0, 1을 칠할 자리
  for (let i = 0; i < nums.length; i++) {
    const v = nums[i];              // 덮어쓰기 전에 먼저 읽는다
    nums[i] = 2;                    // 일단 2로 칠한다
    if (v <= 1) nums[p1++] = 1;     // 0과 1은 1 구역을 한 칸 늘린다
    if (v === 0) nums[p0++] = 0;    // 0은 그 위에 0 구역을 한 칸 늘린다
  }
}
```

`p0 ≤ p1 ≤ i`가 항상 성립하므로 아직 읽지 않은 칸을 덮어쓰는 일은 없다. 아래 그림에서 다음을 누르면 같은 `[2, 0, 1, 2, 0, 1]`을 덧칠하기로 따라간다. ▼는 지금 읽는 칸 `i`, 색칠한 칸은 0이나 1 페인트가 덮은 칸이다.

| 풀이 | 시간 | 추가 공간 | 훑는 횟수 | 원소가 객체여도 되나 | 언제 고르나 |
|---|---|---|---|---|---|
| 1. 내장 정렬 | O(n log n) | 언어마다 다름 | - | 된다 | 조건이 없을 때, 검증용 |

### 100만 칸으로 재 보면

길이가 300이라 LeetCode에서는 실행 시간 차이가 의미가 없다. 그래도 "한 번 훑기가 두 번 훑기보다 빠른가"는 궁금하다. 0, 1, 2가 무작위로 섞인 100만 칸 배열을 각 풀이에 다섯 번씩 넣고 가장 빠른 시간을 적었다. 두 번 돌린 결과다.

## 원소가 숫자가 아니라 객체라면

실무에서 "상태가 긴급 · 보통 · 낮음인 티켓을 긴급부터 모아 보여 달라" 같은 요구는 이 문제와 같은 모양이다. 이때 두 가지를 따진다.

첫째, 원소를 옮겨야 한다. 세 포인터는 바꾸기만 하니 그대로 쓸 수 있다. 둘째, 같은 색끼리 원래 순서가 지켜져야 하는가(안정 정렬인가). 세 포인터는 안정적이지 않다. 직접 돌려 보면 보인다.

```js
const items = [
  { id: "a", color: 2 }, { id: "b", color: 0 }, { id: "c", color: 2 },
  { id: "d", color: 0 }, { id: "e", color: 1 },
];
```

```text

stable b0 d0 e1 a2 c2
```

세 포인터(`dnfObj`)는 a와 c의 순서를 뒤집었다. `hi`와 바꾸는 순간 뒤쪽 원소가 앞으로 튀어 오기 때문이다. 순서가 중요하면 개수를 센 뒤 색마다 시작 위치(0은 0번부터, 1은 0의 개수부터, 2는 0과 1의 개수 합부터)를 정하고, 원래 배열을 앞에서부터 읽어 새 배열의 시작 위치에 하나씩 담는다. 계수 정렬의 안정 버전이고, O(n) 추가 공간이 든다.

```js
function stable(items) {
  const c = [0, 0, 0];
  for (const it of items) c[it.color]++;
  const start = [0, c[0], c[0] + c[1]];          // 색마다 첫 자리
  const out = new Array(items.length);
  for (const it of items) out[start[it.color]++] = it; // 읽은 순서대로 담는다
  return out;
}
```

## 색이 k가지로 늘어난다면

꼬리 질문으로 "색이 k가지라면?"이 나온다. LeetCode에는 없고 다른 사이트에서 Sort Colors II로 알려진 변형이다. 길은 셋이다.

- 개수 세기를 k칸으로 늘린다. O(n + k) 시간, O(k) 공간. 가장 단순하다.
- 세 포인터 분할을 색 범위로 재귀한다. 색 범위 `[cl, ch]`의 가운데 색 p를 기준으로 "p 이하"와 "p 초과"로 나누고 양쪽을 다시 나눈다. 재귀 깊이가 log k라 O(n log k) 시간, O(log k) 스택이다. 퀵 정렬을 값 범위로 나누는 셈이다.
- 세 포인터를 k − 1번 반복한다. 매번 가장 작은 색 하나를 앞으로 빼면 O(nk)다.

```js
function rainbow(a, k) {                       // 색은 1..k
  const go = (lo, hi, cl, ch) => {
    if (cl >= ch || lo >= hi) return;          // 색이 하나뿐이거나 칸이 하나 이하
    const p = Math.floor((cl + ch) / 2);
    let l = lo, r = hi;
    while (l <= r) {
      while (l <= r && a[l] <= p) l++;         // 왼쪽은 p 이하만
      while (l <= r && a[r] > p) r--;          // 오른쪽은 p 초과만
      if (l < r) { [a[l], a[r]] = [a[r], a[l]]; l++; r--; }
    }
    go(lo, r, cl, p);
    go(l, hi, p + 1, ch);
  };
  go(0, a.length - 1, 1, k);
  return a;
}
```

```text
rainbow [1,1,2,2,3,3,4] [1,1,2,2,2]
```

`[3, 2, 1, 2, 4, 1, 3]`, k = 4와 `[2, 1, 1, 2, 2]`, k = 2를 넣은 결과다. 무작위 입력 2000개로 내장 정렬과도 맞춰 봤다. 공간 제한이 없으면 첫 번째 방법을 고른다. 메모리를 O(1)에 가깝게 쓰라는 조건이 붙으면 두 번째다.

## 배열이 아니라 연결 리스트라면

같은 0, 1, 2가 [연결 리스트](/posts/ds-linked-list)에 들어 있다면 칸끼리 바꾸는 대신 노드를 떼어 세 줄에 나눠 붙이면 된다. 색마다 가짜 머리 노드(더미)를 하나씩 두고, 노드를 읽으며 제 색 줄의 꼬리에 붙인 뒤, 마지막에 0 줄, 1 줄, 2 줄을 잇는다.

```js
function sortList(head) {
  const d = [{ next: null }, { next: null }, { next: null }]; // 색마다 더미 머리
  const tail = [...d];
  for (let cur = head; cur; cur = cur.next) { tail[cur.val].next = cur; tail[cur.val] = cur; }
  tail[2].next = null;                       // 마지막 꼬리를 끊는다
  tail[1].next = d[2].next;                  // 1 줄 끝에 2 줄을
  tail[0].next = d[1].next;                  // 0 줄 끝에 1 줄을
  return d[0].next;
}
```

```text
[0,0,1,1,2,2]
[2,2]
[0]
[0,1]
[]
[1,2]
```

`[2, 0, 1, 2, 0, 1]`, `[2, 2]`, `[0]`, `[1, 0]`, `[]`, `[2, 1]`을 리스트로 만들어 넣은 결과다. 노드를 새로 만들지 않으니 추가 공간은 더미 세 개라 O(1)이고, 읽은 순서대로 붙이니 안정적이다. 배열에서는 안정성과 O(1) 공간을 같이 얻기 어려웠는데 리스트에서는 둘 다 된다. 잇는 순서가 중요하다. 1 줄이 비어 있으면 `tail[1]`이 더미 자신이라, 1 줄 끝에 2 줄을 먼저 이어 둬야 0 줄 끝이 2 줄로 바로 이어진다. `tail[2].next = null`을 빼먹으면 원래 리스트에서 마지막 2 뒤에 있던 노드를 계속 가리켜 고리가 생길 수 있다.

## 같은 칼로 자르는 다른 문제들

세 구역 분할은 이 문제 말고도 여러 곳에서 다시 나온다.

- [Kth Largest Element in an Array](/posts/leetcode-kth-largest-element-in-an-array): 퀵 셀렉트가 같은 값이 많은 입력에서 느려질 때, 기준값보다 작은 · 같은 · 큰 세 구역으로 나누는 3-way 분할로 고친다. 이 문제의 세 포인터와 코드 모양이 같다.
- [Move Zeroes](/posts/leetcode-move-zeroes): 두 구역 분할. 풀이 3의 첫 번째 훑기 그대로이고, 순서 유지가 조건으로 붙는다.
- LeetCode 905(Sort Array By Parity): 짝수와 홀수 두 구역. 양 끝 포인터 두 개로 끝난다.
- LeetCode 2161(Partition Array According to Given Pivot): 기준값보다 작은 · 같은 · 큰 순서로 나누되 각 구역 안의 순서를 지켜야 한다. 그래서 세 포인터가 아니라 위의 안정 버전처럼 담는다.
- LeetCode 324(Wiggle Sort II): 중앙값을 찾은 뒤 세 구역 분할을 응용한다. 이 문제보다 훨씬 어렵다.

## 앞에서 온 값과 뒤에서 온 값

Sort Colors는 값이 세 종류라서 정렬 대신 분할로 푸는 문제다. 개수만 세면 두 번 훑는 O(n)이 바로 나오고, 한 번에 끝내려면 `lo`, `mid`, `hi` 세 포인터로 0 구역, 1 구역, 미확인 구역, 2 구역을 지킨다. 앞(`lo`)에서 가져온 값은 이미 본 값이라 `mid`를 같이 밀고, 뒤(`hi`)에서 가져온 값은 아직 안 본 값이라 `mid`를 둔다. 이 비대칭과 `mid <= hi` 조건 두 가지가 틀리는 자리의 거의 전부다. 같은 방향 포인터로 두 구역만 나누는 이야기는 [Move Zeroes](/posts/leetcode-move-zeroes)에서 이어진다.

## 면접에서 나올 만한 질문

### 정렬 함수를 쓰면 안 되나요?

조건이 없으면 써도 통과하지만 O(n log n)이다. 값이 0, 1, 2 세 종류뿐이라는 정보를 쓰면 O(n)에 끝난다. 개수를 세어 다시 칠하면 두 번 훑는 O(n), 세 포인터로 나누면 한 번 훑는 O(n)이다. 면접에서는 "정렬로 풀 수 있지만 값의 종류가 적으니 분할로 줄이겠다"고 말하고 넘어가면 된다.

### 한 번만 훑어서 상수 공간으로 풀 수 있나요?

세 포인터 `lo`, `mid`, `hi`로 푼다. `[0, lo)`는 0, `[lo, mid)`는 1, `(hi, 끝]`은 2로 확정하고, `mid`가 본 값에 따라 0이면 `lo`와 바꾸고 둘 다 밀고, 1이면 `mid`만 밀고, 2면 `hi`와 바꾸고 `hi`만 당긴다. 반복마다 미확인 구역이 한 칸씩 줄어 정확히 n번에 끝난다. 포인터 세 개뿐이라 공간은 O(1)이다.

### 2를 hi와 바꾼 뒤에는 왜 mid를 움직이지 않나요?

`hi` 자리에서 가져온 값은 미확인 구역에 있던 값이라 아직 검사하지 않았기 때문이다. 0일 수도 있으니 그 자리에서 한 번 더 봐야 한다. 반대로 `lo`와 바꿀 때 가져오는 값은 이미 본 1(또는 `lo === mid`일 때 자기 자신)이라 `mid`를 같이 밀어도 된다. `mid`까지 밀면 `[2, 0, 1, 2, 0, 1]`이 `[0, 1, 1, 0, 2, 2]`로 끝난다.

### 반복 조건에 왜 등호가 들어가나요?

미확인 구역이 `[mid, hi]`로 양 끝을 포함하기 때문이다. `mid === hi`면 아직 한 칸이 남아 있다. `<`로 쓰면 그 마지막 칸을 보지 않아서 `[1, 0]`이 그대로 남는다. 구간을 닫힌 구간으로 정의했으면 조건도 `<=`가 된다.

### 이 풀이는 안정 정렬인가요?

아니다. 2를 `hi`와 바꾸는 순간 뒤쪽 원소가 앞쪽으로 오면서 같은 색끼리의 순서가 바뀐다. 숫자만 있는 이 문제에서는 상관없지만 객체를 색으로 나눌 때 순서가 중요하면 문제가 된다. 그때는 개수로 색마다 시작 위치를 정하고 새 배열에 읽은 순서대로 담는 안정 계수 정렬을 쓰고, O(n) 추가 공간을 받아들인다.

### 색이 k가지로 늘어나면 어떻게 하나요?

공간이 허락되면 개수 배열을 k칸으로 늘려 O(n + k)에 끝낸다. 상수에 가까운 공간이 필요하면 색 범위의 가운데를 기준으로 두 구역으로 나누고 양쪽을 재귀로 다시 나눈다. 깊이가 log k라 O(n log k)다. 세 포인터를 k − 1번 반복하는 O(nk) 방법도 있지만 k가 크면 느리다.

### 개수 세기 풀이와 세 포인터 풀이 중 실무에서는 무엇을 쓰나요?

값만 있는 배열이면 개수 세기가 읽기 쉽고 버그 낼 곳도 적다. 원소가 객체라 실제로 옮겨야 하고 추가 메모리를 쓰고 싶지 않으면 세 포인터다. 순서까지 지켜야 하면 둘 다 아니고 안정 계수 정렬이다. 조건을 먼저 묻고 고르는 게 답이다.
