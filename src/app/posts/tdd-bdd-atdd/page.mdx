회원 가입의 비밀번호 검사 함수가 있다. 처음엔 길이만 봤는데, 숫자를 넣으라는 요구가 붙고, 이메일 아이디를 비밀번호에 넣지 말라는 요구가 붙었다. 요구가 붙을 때마다 `if`가 늘고, 이번엔 이메일 검사를 넣었더니 길이가 짧은 비밀번호가 통과하기 시작했다. 고친 사람은 길이 검사를 건드리지 않았다고 말한다. 맞다. `return`의 위치를 바꿨을 뿐이다.

이런 코드가 무서운 건 버그 자체보다, 고칠 때마다 무엇이 깨질지 모른다는 점이다. 그래서 다들 손을 덜 대고, 손을 덜 대니 구조가 더 엉킨다. 테스트를 나중에 쓰려고 하면 이미 엉킨 코드라 테스트하기가 어렵고, 결국 안 쓴다.

테스트를 코드보다 먼저 쓰는 방식이 이 고리를 끊으려고 나왔다. 이 글은 TDD의 빨강-초록-리팩터를 실제로 한 바퀴씩 돌려 보며 테스트가 함수의 모양을 어떻게 바꾸는지 보고, 목을 쓰는 방식으로 갈리는 고전파와 런던파, 기획·QA와 같은 문장으로 말하는 BDD, 인수 조건을 먼저 정하는 ATDD를 다룬다. 셋이 과한 순간도 함께 본다. 테스트 대역의 종류와 테스트 피라미드는 [테스트 피라미드와 단위 테스트](/posts/test-pyramid-unit-tests)에서, 케이스를 어떻게 뽑는지는 [테스트 케이스 설계](/posts/test-design-techniques)에서 다뤘다. 예제는 Node 22.22, Cucumber.js 11.3에서 돌렸다.

## 테스트를 먼저 쓰면 무엇이 달라지나

TDD(Test-Driven Development, 테스트 주도 개발)는 켄트 벡이 『Test-Driven Development: By Example』(2002)로 정리한 방식이다. 규칙은 짧다.

1. 빨강: 아직 없는 동작을 확인하는 테스트를 하나 쓰고, 실패하는 걸 본다.
2. 초록: 그 테스트를 통과시킬 만큼만 코드를 쓴다.
3. 리팩터: 테스트가 초록인 상태를 지키면서 중복을 없애고 구조를 다듬는다.

이걸 몇 분 단위로 되풀이한다. 이름에 테스트가 들어 있지만 TDD의 주된 결과물은 테스트가 아니라 설계다. 테스트를 먼저 쓰려면 "이 함수를 어떻게 부르고, 무엇을 돌려받을지"를 구현보다 먼저 정해야 한다. 부르는 쪽의 자리에 먼저 앉아 보는 것이다. 부르기 불편한 함수, 준비할 게 너무 많은 함수는 테스트를 쓰는 순간 티가 난다.

빨강을 꼭 보라는 규칙에도 이유가 있다. 처음부터 통과하는 테스트는 아무것도 확인하지 않는 테스트일 수 있다. 단언을 빼먹었거나, 엉뚱한 함수를 import했거나, 비동기 함수를 `await` 하지 않았거나. 실패하는 걸 한 번 봐야 이 테스트가 그 동작을 실제로 잡는다고 믿을 수 있다.

## 빨강에서 시작하는 한 바퀴

비밀번호 검사를 처음부터 TDD로 다시 짠다. 첫 테스트를 쓰기 전에 정할 것이 있다. 이 함수는 무엇을 돌려줘야 하나. `true`/`false`면 쓰기는 쉽지만, 화면은 "왜 안 되는지"를 보여 줘야 한다. 테스트에서 "짧아서 실패했다"를 확인하고 싶다는 생각이 돌려줄 값을 정한다. 실패 이유 코드의 배열로 하자.

```js
// password.test.js
import { test } from "node:test";
import assert from "node:assert/strict";
import { checkPassword } from "./password.js";

test("8자보다 짧으면 too_short를 돌려준다", () => {
  assert.deepEqual(checkPassword("ab1"), ["too_short"]);
});
```

```js
// password.js — 아직 빈 껍데기
export function checkPassword(pw) {}
```

```bash
node --test --test-reporter=spec password.test.js
```

```text

ℹ tests 1
ℹ suites 0
ℹ pass 0
  AssertionError [ERR_ASSERTION]: Expected values to be strictly deep-equal:
  + actual - expected
  
  + undefined
  - [
  -   'too_short'
  - ]
```

빨강이다. 실패 이유도 예상대로다. 값이 아직 없다(`undefined`). 이제 이 테스트만 통과시킬 코드를 쓴다.

```js
export function checkPassword(pw) {
  return pw.length < 8 ? ["too_short"] : [];
}
```

너무 단순해 보이지만 이게 맞다. 지금 테스트가 요구하는 건 이것뿐이다. 더 쓰면 그 코드는 테스트 없이 들어간 코드가 된다. 켄트 벡은 이렇게 일단 통과시키는 기법을 "가짜로 시작하기(fake it)"라고 불렀다. 상수를 돌려주는 데서 시작해, 테스트가 늘면서 진짜 일반화로 넘어간다.

## 두 번째 테스트가 첫 구현을 깬다

숫자가 없는 비밀번호를 거절하는 테스트를 더한다.

```js
test("숫자가 없으면 no_digit를 돌려준다", () => {
  assert.deepEqual(checkPassword("abcdefgh"), ["no_digit"]);
});
```

```text
✔ 8자보다 짧으면 too_short를 돌려준다 (2.338524ms)
✖ 숫자가 없으면 no_digit를 돌려준다 (2.033795ms)
ℹ tests 2
ℹ suites 0
ℹ pass 1
ℹ fail 1
  AssertionError [ERR_ASSERTION]: Expected values to be strictly deep-equal:
  + actual - expected
  
  + []
  - [
  -   'no_digit'
  - ]
```

첫 테스트는 여전히 초록이고 새 테스트만 빨강이다. 이 상태가 TDD에서 가장 정보가 많은 순간이다. 실패가 하나뿐이니 무엇을 해야 하는지가 분명하다. 그리고 둘을 동시에 통과시키려면 삼항 연산자로는 안 된다. 이유를 모으는 구조가 필요해진다. 테스트 두 개가 구현을 일반화하도록 밀어붙이는 것을 삼각측량(triangulation)이라고 한다.

```js
export function checkPassword(pw) {
  const reasons = [];
  if (pw.length < 8) reasons.push("too_short");
  if (!/[0-9]/.test(pw)) reasons.push("no_digit");
  return reasons;
}
```

여기에 테스트 둘을 더 붙인다. 짧고 숫자도 없으면 이유가 둘 다 나와야 하고, 규칙을 다 지키면 빈 배열이어야 한다. 도입부의 사고("이메일 검사를 넣었더니 길이 검사가 빠졌다")를 막는 건 바로 첫 번째 것이다. 이유가 여러 개일 때 하나만 보고 `return` 해 버리는 구현은 이 테스트에서 걸린다.

```text
✔ 8자보다 짧으면 too_short를 돌려준다 (3.623691ms)
✔ 숫자가 없으면 no_digit를 돌려준다 (0.289078ms)
✔ 짧고 숫자도 없으면 이유를 둘 다 돌려준다 (0.224892ms)
✔ 규칙을 모두 지키면 빈 배열이다 (0.255385ms)
ℹ tests 4
```

## 정리는 초록일 때만

이제 새 요구가 온다. 비밀번호에 이메일 아이디(@ 앞부분)가 들어 있으면 안 된다. 테스트부터 쓰려고 하니 바로 걸리는 게 있다. 지금 함수는 비밀번호만 받는다. 이메일을 어떻게 넘기지?

```js
test("이메일 앞부분이 들어 있으면 contains_email을 돌려준다", () => {
  assert.deepEqual(checkPassword("Minji2026!", { email: "minji@x.com" }), ["contains_email"]);
});
```

테스트를 쓰는 순간 함수의 모양이 정해졌다. 두 번째 인자로 검사에 필요한 맥락을 받는다. 이 결정을 구현하다가 내렸다면 전역 변수나 요청 객체를 통째로 넘기는 식으로 흘러가기 쉽다. 부르는 쪽에서 써 보니, 필요한 것만 넘기는 모양이 자연스러웠다.

`if`가 셋이 되니 리팩터할 때다. 규칙을 데이터로 빼서, 규칙이 늘어도 함수 본문은 바뀌지 않게 한다.

```js
// password.js
const RULES = [
  { code: "too_short", fails: (pw) => pw.length < 8 },
  { code: "no_digit", fails: (pw) => !/[0-9]/.test(pw) },
  { code: "contains_email", fails: (pw, ctx) =>
      ctx.email !== undefined && pw.toLowerCase().includes(ctx.email.split("@")[0].toLowerCase()) },
];

export function checkPassword(pw, ctx = {}) {
  return RULES.filter((rule) => rule.fails(pw, ctx)).map((rule) => rule.code);
}
```

```text
✔ 8자보다 짧으면 too_short를 돌려준다 (1.584095ms)
✔ 숫자가 없으면 no_digit를 돌려준다 (0.261257ms)
✔ 짧고 숫자도 없으면 이유를 둘 다 돌려준다 (0.187812ms)
✔ 규칙을 모두 지키면 빈 배열이다 (0.125146ms)
✔ 이메일 앞부분이 들어 있으면 contains_email을 돌려준다 (1.815357ms)
ℹ tests 5
ℹ suites 0
ℹ pass 5
```

구조를 완전히 바꿨는데 앞의 네 테스트가 그대로 초록이다. 테스트가 "어떻게"가 아니라 "무엇을 돌려주나"만 확인했기 때문이다. 리팩터는 초록일 때만 한다는 규칙이 여기서 의미를 가진다. 빨강인 채로 구조까지 바꾸면, 다음 실패가 새 기능 때문인지 리팩터 때문인지 구분할 수 없다.

## 목을 언제 쓰느냐로 갈리는 두 학파

함수 하나는 쉽다. 협력하는 객체가 생기면 TDD 안에서도 방식이 갈린다. 회원 가입은 비밀번호 검사, 사용자 저장소, 해시 함수를 부른다.

고전파(classicist)는 흔히 디트로이트파 또는 시카고파라고 부른다. 켄트 벡의 TDD가 여기에 가깝다. 협력 객체는 되도록 진짜를 쓰고, DB나 네트워크처럼 느리거나 다루기 어려운 것만 가짜(메모리 저장소 같은)로 바꾼다. 확인은 결과 상태로 한다. "가입한 뒤에는 같은 이메일로 다시 가입할 수 없다."

런던파(mockist)는 스티브 프리먼과 냇 프라이스의 『Growing Object-Oriented Software, Guided by Tests』(2009)로 알려졌다. 바깥(사용자에게 가까운 쪽)에서 안으로 설계해 가면서, 아직 없는 협력 객체를 목으로 세우고 "무엇을 시켰나"를 확인한다. "저장소에 이 이메일과 해시를 저장하라고 시켰다." 목이 협력 객체의 인터페이스를 먼저 정해 주니, 구현 전에 객체 사이의 역할 분담을 설계할 수 있다.

같은 가입 코드를 두 방식으로 테스트했다.

```js
// signup.js
export async function signUp({ email, password }, { users, hasher }) {
  const reasons = checkPassword(password, { email });
  if (reasons.length > 0) return { ok: false, reasons };
  if (await users.findByEmail(email)) return { ok: false, reasons: ["email_taken"] };
  await users.save({ email, hash: await hasher.hash(password) });
  return { ok: true };
}
```

```js
// signup.test.js
```

둘 다 통과한다. 그런데 이 코드에는 경쟁 조건이 있다. 두 요청이 동시에 `findByEmail`에서 "없음"을 받으면 둘 다 저장한다. 그래서 찾기와 저장을 저장소의 한 연산(`insertIfAbsent`, DB에서는 유니크 인덱스와 `INSERT ... ON CONFLICT DO NOTHING`)으로 합쳤다. 가입의 동작은 그대로다.

```text

ℹ pass 1
ℹ fail 1
```

런던파 테스트가 깨졌다. 목은 `findByEmail`과 `save`라는 대화 방식을 고정해 두었으니, 대화 방식이 바뀌면 동작이 같아도 깨진다. 고전파 테스트는 메모리 저장소에 같은 연산을 추가하자 그대로 통과했다.

이걸 "런던파가 나쁘다"로 읽으면 반만 맞다. 런던파 입장에서 저장소의 인터페이스가 바뀐 건 설계 변경이고, 테스트가 그걸 알려 준 것이다. 객체 사이의 역할을 먼저 설계해야 하는 큰 시스템에서 바깥부터 안으로 짜 들어갈 때 목은 좋은 도구다. 대가는 리팩터링 비용이다. 실무에서는 섞어 쓰는 게 보통이다. 우리 코드끼리는 진짜를 쓰고, 프로세스 경계 밖(결제사, 메일, 메시지 큐)에만 목이나 가짜를 세운다. 목이 운영 버그를 덮는 다른 경우는 [테스트 피라미드와 단위 테스트](/posts/test-pyramid-unit-tests#목이-거짓말을-하는-두-가지-방식)에서 직접 돌려 봤다.

## 기획자와 같은 문장으로 말하기

TDD의 테스트는 개발자의 언어로 쓰인다. `checkPassword("ab1")`이 `["too_short"]`를 돌려준다는 문장을 기획자는 읽지 않는다. 그러면 기획서와 테스트 사이에 번역이 생기고, 번역에서 의미가 샌다.

BDD(Behavior-Driven Development, 행동 주도 개발)는 댄 노스가 2000년대 중반 TDD를 가르치다가 만든 말이다. "테스트"라는 단어가 사람들을 "무엇을 확인하지"로 이끄는 대신 "이 시스템이 어떻게 행동해야 하지"를 묻게 하자는 데서 시작했다. 그 문장 틀이 Given-When-Then이다. 어떤 상황에서(Given), 무엇을 하면(When), 어떻게 되어야 한다(Then).

이 틀을 기계가 읽을 수 있게 만든 문법이 Gherkin이고, Cucumber가 그걸 실행한다. Gherkin은 한국어 키워드도 지원한다. 쿠폰 기능의 행동을 적어 봤다.

```gherkin
# language: ko
기능: 주문서 쿠폰 할인
  고객은 쿠폰으로 상품 금액의 10%를 최대 5,000원까지 할인받는다.

  시나리오 개요: 쿠폰 대상 금액에 따라 할인액이 정해진다
    조건 "ISSUED" 상태의 10% 쿠폰이 있다
    그리고 장바구니에 세일 아닌 상품 <금액>원어치를 담았다
    만일 주문서에서 쿠폰을 적용하면
    그러면 할인 금액은 <할인>원이다

    예:
      | 금액  | 할인 |
      | 19999 | 0    |
      | 20000 | 2000 |
      | 60000 | 5000 |

  시나리오: 이미 쓴 쿠폰은 다시 쓸 수 없다
    조건 "USED" 상태의 10% 쿠폰이 있다
    그리고 장바구니에 세일 아닌 상품 30000원어치를 담았다
    만일 주문서에서 쿠폰을 적용하면
    그러면 "이미 사용한 쿠폰입니다" 안내가 보인다
```

`조건`, `만일`, `그러면`이 Given, When, Then이다. `시나리오 개요`와 `예:` 표는 같은 시나리오를 값만 바꿔 여러 번 돌린다. 표의 세 줄은 [테스트 케이스 설계](/posts/test-design-techniques#버그는-경계에-산다)에서 뽑은 경계값 그대로다. 기획자가 읽고 "5만 원 넘으면 5천 원 맞아요"라고 확인할 수 있는 문서가 그대로 테스트가 된다.

문장과 코드를 잇는 건 단계 정의(step definition)다.

```js
// features/steps/coupon.steps.js
import { Given, When, Then } from "@cucumber/cucumber";
import assert from "node:assert/strict";
import { applyCoupon } from "../../src/coupon.js";

Given("{string} 상태의 10% 쿠폰이 있다", function (status) {
  this.coupon = { rate: 10, status };
});
Given("장바구니에 세일 아닌 상품 {int}원어치를 담았다", function (amount) {
  this.cart = [{ price: amount, qty: 1, sale: false }];
});
When("주문서에서 쿠폰을 적용하면", function () {
  this.result = applyCoupon(this.cart, this.coupon);
});
Then("할인 금액은 {int}원이다", function (discount) {
  assert.equal(this.result.discount, discount);
});
Then("{string} 안내가 보인다", function (message) {
  assert.equal(this.result.message, message);
});
```

```bash
npx cucumber-js --import 'features/steps/*.js'
```

```text

4 scenarios (4 passed)
16 steps (16 passed)
0m00.041s (executing steps: 0m00.003s)
```

시나리오 개요의 세 줄이 시나리오 셋으로 펼쳐져서 넷이 됐다. `{string}`, `{int}`는 Cucumber 표현식으로, 문장에서 값을 뽑아 함수 인자로 넘긴다.

BDD에서 흔한 실수는 Gherkin을 UI 조작 스크립트로 쓰는 것이다. "만일 '쿠폰' 버튼을 누르고, 그리고 첫 번째 쿠폰을 클릭하고, 그리고 '적용'을 누르면". 이렇게 쓰면 화면이 바뀔 때마다 시나리오가 깨지고, 기획자가 읽어도 규칙이 안 보인다. 시나리오는 행동과 규칙을 쓰고, 클릭은 단계 정의 안에 숨긴다. 그리고 BDD의 본질은 도구가 아니다. Cucumber 없이도 테스트 이름을 "이미 쓴 쿠폰은 다시 쓸 수 없다"처럼 행동으로 짓고, 본문을 Given/When/Then 세 덩어리로 나누고, 그 예시를 기획자와 함께 정하면 BDD를 하는 것이다. 반대로 Cucumber를 깔고 개발자 혼자 시나리오를 쓴다면 번역 계층 하나가 늘었을 뿐이다.

## 인수 조건을 먼저 정한다

ATDD(Acceptance Test-Driven Development, 인수 테스트 주도 개발)는 개발을 시작하기 전에 "이게 되면 이 기능은 끝났다"는 인수 조건을 예시로 합의하고, 그걸 실패하는 인수 테스트로 먼저 만든다. BDD와 많이 겹친다. 굳이 나누면 BDD는 행동을 묘사하는 언어와 협업에, ATDD는 "완료"를 정의하는 인수 기준에 무게를 둔다. 고이코 아지치의 『Specification by Example』(2011)이 이 흐름을 예시 중심 명세로 정리했다.

합의는 보통 세 사람이 한다. 기획(무엇이 필요한가), 개발(어떻게 만들 수 있나), 테스트(어떻게 깨질 수 있나). "세 친구(three amigos)"라고 부르는 이 회의에서 나오는 것은 규칙과 그 규칙을 보여 주는 구체적인 예시다. "쿠폰은 한 장만"이라는 규칙에 "쿠폰 A를 적용한 상태에서 쿠폰 B를 고르면?"이라는 예시를 붙이면, 그 자리에서 "A가 빠지고 B가 들어가나, 거절되나"가 정해진다.

## 셋은 경쟁이 아니라 층이다

셋을 고르는 문제로 보면 헷갈린다. 범위가 다르다.

| | 누가 쓰나 | 무엇을 확인하나 | 고리의 크기 |
|---|---|---|---|
| TDD | 개발자 | 함수·객체의 동작 | 분 단위 |
| BDD | 기획·QA·개발이 함께 | 사용자가 보는 행동 | 기능 단위 |
| ATDD | 기획·QA·개발이 함께 | 완료의 기준(인수 조건) | 기능·스토리 단위 |

BDD와 ATDD는 서로 거의 같은 일을 다른 쪽에서 부르는 이름에 가깝고, 둘 다 안쪽에서는 TDD로 짜는 경우가 많다. 질문이 다를 뿐이다. TDD는 "이 코드를 제대로 만들었나", ATDD와 BDD는 "우리가 같은 걸 만들고 있나"를 묻는다. [테스트 케이스 설계](/posts/test-design-techniques#제대로-만들었나-맞는-걸-만들었나)에서 본 검증과 확인의 구분과 겹친다.

## 먼저 쓰는 게 과한 순간

테스트를 먼저 쓰려면 "무엇이 맞는 결과인지" 알아야 한다. 그걸 모르는 단계에서는 TDD가 비싸다.

탐색 단계가 그렇다. 처음 쓰는 라이브러리가 어떻게 동작하는지, 이 알고리즘이 데이터에서 쓸 만한 결과를 내는지 알아보는 중이라면 테스트부터 쓸 게 없다. 이럴 때는 스파이크(spike)를 한다. 버릴 각오로 빠르게 짜서 배우고, 배운 걸 바탕으로 TDD로 다시 짠다. 스파이크 코드를 그대로 운영에 올리는 게 실수지, 스파이크를 하는 게 실수는 아니다.

UI도 그렇다. 화면 배치나 애니메이션은 결과를 눈으로 보고 판단하는 영역이라 테스트를 먼저 쓰기 어렵다. 화면 뒤의 규칙(쿠폰 적용 가능 여부, 폼 검증)은 TDD로 짜고, 화면 자체는 만들고 나서 시각적 회귀 테스트나 사람이 확인한다.

레거시 코드는 반대 방향에서 시작한다. 테스트가 없는 코드를 고쳐야 한다면, 먼저 지금 동작을 그대로 기록하는 특성 테스트(characterization test)를 쓴다. 마이클 페더스가 『Working Effectively with Legacy Code』(2004)에서 쓴 말이다. 맞는 동작인지는 따지지 않는다. 지금 이렇게 동작한다는 사실을 고정해 두고, 그 안전망 위에서 의존을 끊고 구조를 바꾼 다음, 새 동작부터 TDD로 들어간다. 이상해 보이는 동작도 일단 기록한다. 누군가 그 동작에 기대고 있을 수 있다.

BDD 도구는 읽을 사람이 없을 때 과하다. 시나리오를 기획자가 한 번도 안 읽는다면, Gherkin 문장과 단계 정의라는 번역 계층만 유지 비용으로 남는다. 그때는 일반 테스트 코드에 행동 중심의 이름을 붙이는 것으로 충분하다.

## TDD가 느리다는 말에 답하기

TDD를 하면 처음 짜는 시간은 늘어난다. 이건 부정할 필요가 없다. 마이크로소프트와 IBM의 네 팀을 비교한 2008년 연구(나가판 등)는 TDD를 한 팀의 출시 전 결함 밀도가 40~90% 낮았고, 처음 개발 시간은 15~35% 늘었다고 보고했다. 팀 네 개짜리 사례 연구라 일반화에는 조심해야 하지만, "처음엔 느리고 나중에 덜 고친다"는 방향은 다른 경험담과도 맞는다.

그래서 답은 무엇을 재느냐에 달려 있다. 기능 하나를 처음 짜는 시간만 재면 느리다. 디버깅, 리뷰에서 되돌아오는 시간, 회귀 버그를 고치는 시간, 겁이 나서 리팩터링을 미루는 비용까지 재면 계산이 달라진다. 테스트가 빠르게 돌아야 이 계산이 성립한다. 한 바퀴에 몇 초 안에 결과가 와야 몇 분 단위 고리가 돈다. 테스트 한 번에 1분이 걸리면 TDD는 정말 느려진다.

또 하나, TDD가 느리다고 느끼는 경우의 상당수는 테스트하기 어려운 구조에서 시작해서다. 함수가 DB와 시계와 전역 설정을 직접 부르면 테스트 하나를 쓰는 데 준비가 한참 걸린다. 그 고통이 TDD가 주는 설계 신호다. 의존을 인자로 받게 바꾸면 테스트도 빨라지고 코드도 나아진다.

## 테스트가 구현에 묶이는 순간

TDD를 하다 보면 테스트가 리팩터링의 족쇄가 되는 순간이 온다. 증상과 원인은 대개 이렇다.

- 내부 함수를 export해서 따로 테스트한다: 공개된 동작으로 확인할 수 있다면 내부 함수 테스트는 구조를 바꿀 때마다 깨진다. 비공개 동작이 너무 복잡해 따로 확인하고 싶다면, 그건 별도 모듈로 빼라는 신호다.
- 모든 협력 객체를 목으로 세운다: 위의 런던파 예처럼 대화 방식이 바뀌면 깨진다. 우리 코드끼리는 진짜를 쓴다.
- 호출 순서와 횟수를 단언한다: 결과가 같다면 순서는 구현 세부다. 메일을 정확히 한 번 보내야 한다처럼 순서나 횟수 자체가 요구일 때만 확인한다.
- 테스트 하나가 여러 동작을 확인한다: 실패했을 때 무엇이 깨졌는지 이름만으로 모른다. 테스트 이름이 "무엇을 하면 무엇이 된다" 한 문장으로 안 써지면 쪼갠다.

기준은 하나다. 동작을 바꾸지 않은 변경에 테스트가 깨지면, 그 테스트는 구현에 묶여 있다.

## 테스트가 먼저 묻는 질문

TDD는 아주 작은 빨강-초록-리팩터 고리로 코드를 짜면서, 테스트를 먼저 쓰는 순간 함수의 모양(무엇을 받고 무엇을 돌려주나)을 부르는 쪽 입장에서 정하게 만든다. 고전파는 진짜에 가까운 협력 객체와 결과 상태로, 런던파는 목과 상호작용으로 확인하고, 그 차이는 리팩터링할 때 드러난다. BDD와 ATDD는 바깥 고리다. 기획·QA·개발이 규칙을 구체적인 예시로 합의하고, 그 예시를 실패하는 인수 테스트로 먼저 만든다. 탐색, 화면, 레거시처럼 정답을 먼저 알 수 없는 곳에서는 스파이크와 특성 테스트로 순서를 바꾼다. 이렇게 만든 테스트가 배포 길목마다 어떻게 다시 도는지는 [스모크, 새니티, 회귀 테스트](/posts/smoke-sanity-regression-testing)에서, API 경계에서 같은 생각을 적용하는 법은 [API 테스트 자동화](/posts/api-test-automation)에서 이어진다.

## 면접에서 나올 만한 질문

### TDD의 사이클을 설명해 주세요.

빨강-초록-리팩터를 몇 분 단위로 되풀이한다. 아직 없는 동작을 확인하는 테스트를 쓰고 실패를 확인한 뒤, 그 테스트만 통과할 만큼 코드를 쓰고, 초록인 상태에서 중복을 없애고 구조를 다듬는다. 실패를 먼저 보는 이유는 테스트가 그 동작을 실제로 잡는지 확인하려는 것이다. 리팩터는 초록일 때만 해야 다음 실패의 원인을 구분할 수 있다.

### 테스트를 먼저 쓰면 설계가 어떻게 바뀌나요?

부르는 쪽의 자리에서 함수를 먼저 써 보게 되니, 무엇을 받고 무엇을 돌려줄지를 구현보다 먼저 정한다. 비밀번호 검사가 불리언 대신 실패 이유 배열을 돌려주게 된 것, 이메일 규칙이 붙을 때 맥락을 두 번째 인자로 받게 된 것이 테스트에서 나온 결정이다. 준비할 게 많아 테스트하기 어려운 함수는 의존이 엉켰다는 신호라서, 의존을 인자로 받는 구조로 자연스럽게 간다.

### 고전파와 런던파 TDD의 차이는요?

고전파는 협력 객체를 되도록 진짜로 쓰고 느린 경계만 가짜로 바꾸며, 결과 상태로 확인한다. 런던파는 바깥에서 안으로 설계하며 협력 객체를 목으로 세우고 무엇을 시켰는지 상호작용으로 확인한다. 런던파는 객체 사이 역할을 먼저 설계하기 좋지만, 대화 방식이 바뀌는 리팩터링에 테스트가 깨진다. 실무에서는 우리 코드끼리는 진짜, 프로세스 경계 밖에만 목을 쓰는 식으로 섞는다.

### BDD는 TDD와 무엇이 다른가요?

BDD는 확인할 것을 테스트가 아니라 시스템의 행동으로 표현하고, Given-When-Then 문장으로 기획·QA·개발이 같은 언어를 쓰게 한다. Gherkin과 Cucumber를 쓰면 그 문장이 그대로 실행되는 테스트가 된다. TDD가 개발자의 코드 설계 고리라면 BDD는 팀이 같은 걸 만들고 있는지 맞추는 바깥 고리다. 시나리오는 클릭 순서가 아니라 규칙과 행동을 써야 화면 변경에 덜 깨진다.

### BDD 도구 없이 BDD를 할 수 있나요?

할 수 있다. BDD의 핵심은 도구가 아니라 예시로 합의하는 대화다. 테스트 이름을 행동 문장으로 짓고, 본문을 Given/When/Then으로 나누고, 그 예시를 기획자와 함께 정하면 된다. 오히려 개발자 혼자 Gherkin을 쓰고 아무도 안 읽는다면 번역 계층만 늘어난 것이다.

### ATDD는 어떻게 진행되나요?

개발 전에 기획·개발·테스트가 모여 규칙과 구체적인 예시로 인수 조건을 합의하고, 그것을 실패하는 인수 테스트로 먼저 만든다. 개발자는 그 안에서 TDD로 작은 고리를 여러 번 돌고, 인수 테스트가 초록이 되면 기능이 끝났다고 말한다. 남은 시나리오는 살아 있는 문서가 되어, 규칙이 바뀌면 시나리오부터 고친다.

### TDD가 느리다는 비판에는 어떻게 답하나요?

처음 짜는 시간은 실제로 늘어난다. 마이크로소프트·IBM 사례 연구에서도 개발 시간은 15~35% 늘고 출시 전 결함 밀도는 40~90% 줄었다. 디버깅, 회귀 수정, 리팩터링을 미루는 비용까지 재면 계산이 달라진다. 다만 테스트가 몇 초 안에 돌아야 하고, 느리게 느껴지는 원인이 테스트하기 어려운 구조라면 그 구조부터 고친다.

### 테스트가 구현에 묶였다는 건 어떻게 알아보나요?

동작을 바꾸지 않은 리팩터링에 테스트가 깨지면 묶인 것이다. 흔한 원인은 내부 함수를 따로 테스트하기, 모든 협력 객체를 목으로 세우기, 요구가 아닌 호출 순서와 횟수를 단언하기다. 테스트는 공개된 동작과 결과로 확인하고, 순서나 횟수는 그 자체가 요구일 때만 확인한다.
