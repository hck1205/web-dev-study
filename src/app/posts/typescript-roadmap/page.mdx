<EasyIntro>
  타입스크립트로 파일 하나를 검사했더니 에러가 여섯 줄 나왔는데, 줄마다 번호가 다르다. 메시지를 검색해서 그때그때 고치면 끝나지만, 어떤 규칙 때문에 난 에러인지 모르면 같은 에러가 계속 다시 나온다.

  타입스크립트는 자바스크립트 위에 타입이라는 안전띠를 얹은 언어다. 코드를 실행하기 전에 값의 모양이 맞는지 미리 검사해 주고, 실행할 때는 그 안전띠를 풀어 버려서 브라우저에는 타입이 전혀 남지 않는다. 그래서 빌드가 성공해도 타입이 맞다는 보장은 아니고, 검사기를 따로 돌려야 한다.

  이 글은 이 블로그의 타입스크립트 글 여섯 편이 각각 어떤 질문에 답하는지 적고, 처음 배우는 순서와 에러 번호에서 거꾸로 글을 찾아가는 길을 놓은 지도다. 자바스크립트 프로젝트에 타입을 들일 때 처음부터 가장 엄격한 설정을 켜면 에러가 수천 개 나서 포기하게 되니, 검사만 먼저 켜고 강도는 천천히 올리라는 순서도 함께 적었다.
</EasyIntro>

주문 화면 파일 하나를 `tsc`로 검사했더니 에러가 여섯 줄 나왔다. 줄마다 코드가 다르다.

```tsx
import type { ReactNode } from "react";

interface User { id: number; name: string; email: string }
interface Options { timeout?: number; retry?: number }
declare const users: User[];

const opts: Options = { timout: 3000 };

function getProp<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
getProp(users[0], "emial");

function findName(id: number) {
  return users.find((u) => u.id === id).name;
}

type Preview = Pick<User, "nmae">;

function total(items) {
  return items.length;
}

function Panel({ children }: { children: ReactNode }) {
  return <section>{children}</section>;
}
export const page = <Panel>{users[0]}</Panel>;
```

TypeScript 5.9.3, `--strict`로 검사한 결과다.

```text
checkout.tsx(7,25): error TS2561: Object literal may only specify known properties, but 'timout' does not exist in type 'Options'. Did you mean to write 'timeout'?
checkout.tsx(12,19): error TS2345: Argument of type '"emial"' is not assignable to parameter of type 'keyof User'.
checkout.tsx(15,10): error TS2532: Object is possibly 'undefined'.
checkout.tsx(18,27): error TS2344: Type '"nmae"' does not satisfy the constraint 'keyof User'.
checkout.tsx(20,16): error TS7006: Parameter 'items' implicitly has an 'any' type.
checkout.tsx(27,28): error TS2322: Type 'User' is not assignable to type 'ReactNode'.
```

객체 리터럴에만 걸리는 검사(TS2561), 제네릭 제약(TS2345), `undefined` 좁히기(TS2532), 유틸리티 타입의 키 제약(TS2344), strict 옵션이 켠 암묵적 `any` 검사(TS7006), React의 children 타입(TS2322). 여섯 줄이 각각 다른 규칙에서 나왔다. 에러 메시지만 검색하면 그때그때 고치고 끝나지만, 어느 규칙인지 알면 같은 종류의 에러가 다시 나지 않게 설계를 바꿀 수 있다.

이 블로그의 TypeScript 글은 여섯 편이다. 이 글은 새 개념을 설명하지 않는다. 글마다 어떤 질문에 답하는지 한두 문장으로 적고, 읽는 순서와 에러에서 거꾸로 찾아가는 길을 놓았다. 자바스크립트 쪽 지도는 [자바스크립트 로드맵](/posts/javascript-roadmap)에 따로 있다. TypeScript는 자바스크립트에 타입을 얹은 언어라, 런타임 동작(클로저, `this`, 비동기)은 그쪽 글이 답한다.

## 모양으로 비교하는 타입

[타입 시스템 기초](/posts/ts-type-system-basics)는 "왜 순서를 바꿔 넘긴 사용자 ID와 주문 ID가 에러 없이 통과하나"에 답한다. TypeScript는 이름이 아니라 모양으로 타입을 비교한다(구조적 타이핑). 그래서 둘 다 `string`이면 구분하지 못하고, 구분이 필요하면 브랜드 타입을 쓴다. 객체 리터럴에만 걸리는 초과 속성 검사가 처음 장면의 TS2561을 냈다. `any`, `unknown`, `never`를 집합으로 보는 법, `let`과 `const`가 리터럴을 다르게 넓히는 이유, `type`과 `interface` 중 무엇을 쓸지, 컴파일 뒤에 타입이 사라지므로 경계에서 값을 확인해야 한다는 점까지 다룬다.

## 들어간 타입과 나오는 타입을 잇기

[제네릭](/posts/ts-generics)은 "`any[]`로 받은 함수가 왜 문자열에 `toFixed`를 부르게 놔두나"에 답한다. 타입 매개변수는 호출하는 순간 인자에서 추론되고, `extends`로 할 수 있는 일을 제한한다. 처음 장면의 TS2345(`"emial"`은 `keyof User`가 아니다)가 그 제약이다. 후보가 여럿일 때 추론이 고르는 규칙, `NoInfer`(5.4)와 `const` 타입 매개변수(5.0), 반환 타입에만 쓰인 제네릭이 사실상 `as`와 같은 이유, 제네릭 컴포넌트와 훅, `.tsx`의 `<T,>` 문법까지 본다.

## 조건문이 타입을 줄인다

[타입 좁히기](/posts/ts-narrowing)는 "결제 상태를 하나 추가했는데 화면에 왜 undefined가 찍히나"에 답한다. 검사기는 `if`, `switch`, 이른 반환을 따라가며 변수의 타입을 줄인다. `typeof`, `in`, `instanceof`, 판별 유니온, 직접 만든 타입 가드와 단언 함수가 그 도구다. 처음 장면의 TS2532(`find`의 결과가 `undefined`일 수 있다)를 고치는 방법이 여기 있다. 콜백과 재할당에서 좁힌 것이 풀리는 경우, `never`로 빠진 갈래를 찾는 완전성 검사, `filter(Boolean)`과 5.5의 추론된 타입 서술어도 다룬다.

## 타입으로 타입을 만들기

[유틸리티 타입과 매핑된 타입](/posts/ts-utility-mapped-types)은 "필드를 추가했는데 왜 수정 폼 타입은 그대로였나"에 답한다. 원본 타입 하나에서 `Partial`, `Pick`, `Omit`, `Record`로 나머지를 뽑아내면 원본이 바뀔 때 어긋난 곳이 에러로 드러난다. 처음 장면의 TS2344는 `Pick`이 키를 검사한 결과다(`Omit`은 검사하지 않는다는 함정도 거기서 본다). 그 유틸리티를 만드는 재료인 매핑된 타입, 분배 조건부 타입, `infer`, 템플릿 리터럴 타입, 그리고 검사만 하고 넓히지 않는 `satisfies`를 다룬다. 타입이 너무 영리해져 TS2589가 나는 경계도 있다.

## 검사의 강도와 실행 환경 맞추기

[tsconfig와 strict 옵션](/posts/tsconfig-strict)은 "타입을 다 붙였는데 왜 `find` 결과로 운영에서 터졌나"에 답한다. `strict`는 아홉 개 검사의 묶음이고, 처음 장면의 TS7006(`noImplicitAny`)이 그중 하나다. strict 밖의 `noUncheckedIndexedAccess`를 이 블로그 저장소에 켜면 에러가 몇 개 나는지도 셌다. 검사기가 실제 실행 환경과 같은 규칙을 쓰게 하는 `moduleResolution`(bundler와 nodenext), 파일 단위 변환기를 위한 `isolatedModules`, 시간을 아끼는 대신 무엇을 놓치는지 보여 주는 `skipLibCheck`, 큰 저장소의 프로젝트 참조까지 실제 출력으로 본다.

## 컴포넌트에 타입 붙이기

[React에서 TypeScript 쓰기](/posts/typescript-in-react)는 "로직은 그대로인데 왜 `useState(null)`에서 에러가 나나"에 답한다. 상태, props, children, 이벤트, ref, 기본 요소를 감싸는 래퍼, 서로 배타적인 props, 제네릭 컴포넌트, Context와 커스텀 훅이 차례로 나온다. 처음 장면의 TS2322(`User`는 `ReactNode`가 아니다)는 React가 런타임에 "Objects are not valid as a React child"로 낼 에러를 미리 본 것이다. `@types/react` 19에서 바뀐 `useRef`와 `ref` prop도 짚는다.

## 다른 글 속의 TypeScript

TypeScript를 주제로 하지 않는 글에도 TypeScript 절이 있다. 필요할 때 이어서 읽는다.

- [var, let, const](/posts/js-var-let-const): `const`로 선언하면 리터럴 타입이 남고 `let`은 넓어지는 이유를 변수 쪽에서 본다.
- [ES 모듈](/posts/js-es-modules): TypeScript와 번들러가 import·export를 어떻게 바꿔 쓰는지, `require(esm)`과 만나는 자리.
- [호이스팅과 TDZ](/posts/js-hoisting-tdz): 선언 전에 쓰는 코드를 TypeScript와 ESLint로 미리 잡는 법.
- [커링과 부분 적용](/posts/js-currying-partial)과 [compose와 pipe](/posts/fp-composition-pipe): 함수를 조합할 때 타입을 잇는 오버로드와 재귀 타입.
- [디자인 패턴 개요](/posts/design-patterns-overview): 패턴 글의 예제는 대부분 TypeScript로 썼다. 인터페이스와 제네릭이 실제 설계에서 어떻게 쓰이는지 볼 수 있다.

그림에 다 못 넣은 번호는 문장으로 둔다.

TS18046(`'err' is of type 'unknown'`)은 `catch`의 변수나 `unknown`으로 받은 값을 확인 없이 쓴 것이다. `unknown`을 다루는 법은 타입 시스템 기초에, `catch`가 `unknown`이 된 이유는 tsconfig 글의 `useUnknownInCatchVariables`에 있다.

TS18047, TS18048(`possibly 'null'`, `possibly 'undefined'`)은 타입 좁히기다. 같은 에러가 갑자기 수십 개 늘었다면 누군가 `noUncheckedIndexedAccess`를 켰는지 tsconfig부터 본다.

TS2339(`Property 'x' does not exist on type`)가 유니온 타입에서 나면 좁히지 않고 한쪽에만 있는 속성을 읽은 것이다. 구조 분해의 `...rest`가 좁히기를 끊은 경우는 React 글에 예가 있다.

TS2307, TS2835(`Cannot find module`, `need explicit file extensions`)는 거의 항상 `moduleResolution` 문제다. `tsc --traceResolution`으로 해석 과정을 본다.

TS1205, TS1484(`export type`, `type-only import`)는 `isolatedModules`나 `verbatimModuleSyntax`가 켜진 프로젝트다. 고치는 법은 정해져 있다. `type`을 붙인다.

TS2589(`excessively deep`)나 에디터가 몇 초씩 멈추는 증상은 너무 영리한 타입이다. 유틸리티 타입 글의 마지막 절을 본다.

TS2786(`cannot be used as a JSX component`)은 컴포넌트가 그릴 수 없는 값을 돌려주거나, `@types/react`가 두 버전 설치되어 서로 다른 `ReactNode`를 보는 경우다. 뒤쪽이면 `pnpm why @types/react`로 확인한다.

## 여섯 줄로 돌아가서

처음 파일의 에러 여섯 줄은 서로 다른 여섯 규칙에서 나왔다. 모양으로 비교하는 타입, 호출마다 정해지는 타입 매개변수, 조건문을 따라 줄어드는 타입, 원본에서 계산해 내는 타입, 검사의 강도를 정하는 설정, React가 기대하는 타입. 이 지도는 그 규칙을 순서대로 읽는 길과 에러 번호에서 거꾸로 찾는 길을 함께 놓았다. 각 글을 읽고 나서 처음 출력의 줄마다 "어느 규칙이 왜 이 에러를 냈고, 같은 에러가 다시 안 나게 하려면 무엇을 바꿔야 하는지"를 자기 말로 말할 수 있으면 된다.

## 면접에서 나올 만한 질문

### TypeScript를 쓰는 이유는 무엇인가요?

실행하기 전에 값의 모양이 맞는지 검사해서, `undefined`의 속성을 읽거나 없는 필드를 쓰는 종류의 버그를 컴파일 단계에서 잡기 위해서다. 타입이 문서 역할도 해서 함수가 무엇을 받고 돌려주는지 코드만 보고 알 수 있고, 리팩터링할 때 영향받는 곳을 에러로 알려 준다. 다만 런타임에는 타입이 없으니 바깥에서 들어오는 값은 따로 검증해야 한다.

### TypeScript의 타입은 런타임에 남나요?

남지 않는다. 컴파일러나 번들러가 타입을 지우고 자바스크립트만 내보내므로, `interface`로 `instanceof` 검사를 할 수 없고 API 응답이 타입과 다르게 와도 알 수 없다. 그래서 경계에서는 `unknown`으로 받고 타입 가드나 스키마 검증으로 확인한다. `enum`처럼 값을 만들어 내는 일부 문법만 예외로 런타임 코드가 생긴다.

### 빌드는 성공했는데 타입 에러가 있을 수 있나요?

있다. Next.js나 Vite 같은 번들러는 파일 하나씩 타입을 지우기만 하고 검사하지 않으므로, 타입이 틀려도 자바스크립트를 만든다. 타입 검사는 `tsc --noEmit`을 CI의 별도 단계로 돌려야 보장된다. 파일 단위 변환이 안전하도록 `isolatedModules`를 켜는 것도 같은 이유다.

### any와 unknown은 어떻게 다른가요?

둘 다 어떤 값이든 받지만, `any`는 검사를 꺼서 아무 연산이나 허용하고 `unknown`은 확인하기 전에는 아무 연산도 허용하지 않는다. `any`는 한 번 들어오면 연산 결과도 `any`가 되어 퍼지고, `unknown`은 좁혀야만 쓸 수 있어 안전하다. 바깥 데이터나 `catch`의 에러처럼 모양을 모르는 값은 `unknown`으로 받는다.

### 기존 JS 프로젝트를 TypeScript로 옮긴다면 어떤 순서로 하나요?

`allowJs`와 `checkJs`로 지금 코드부터 검사에 넣고, 여러 곳이 쓰는 경계 파일부터 `.ts`로 바꾼다. 그다음 `noImplicitAny`, `strictNullChecks` 순으로 strict 플래그를 하나씩 켜며 에러를 0으로 만들고, 남은 것은 `@ts-expect-error`로 표시해 수를 줄여 간다. CI에 `tsc --noEmit`을 따로 두고 예외 주석 수가 늘지 않게 막는다. 한 번에 strict를 켜면 `any`와 `as`로 덮고 끝나기 쉽다.

### 타입 에러 메시지가 길 때 어떻게 읽나요?

첫 줄의 TS 번호로 어떤 규칙인지 범위를 정하고, 들여 쓴 줄을 따라 내려가 맨 아래 줄에서 가장 구체적인 원인을 찾는다. 위치는 에러가 드러난 곳이라 실제로 고칠 곳은 선언부나 타입 정의일 때가 많다. 메시지가 유틸리티 타입이 겹겹이 쌓여 읽기 어렵다면 그 결과를 이름 있는 타입으로 적어 두는 것도 방법이다.
