쇼핑몰 화면에서 장바구니 수량을 보여 주는 곳이 세 군데 있다. 헤더의 숫자 배지, 오른쪽의 미니 장바구니, "3,000원 더 담으면 무료 배송" 막대다. 그래서 `addToCart()`의 끝은 이렇게 생겼다.

```ts
declare function updateBadge(count: number): void;
declare function renderMiniCart(items: unknown[]): void;
declare function updateShippingBar(total: number): void;
declare const cart: { items: unknown[]; total: number };

function addToCart(item: unknown) {
  cart.items.push(item);
  updateBadge(cart.items.length);
  renderMiniCart(cart.items);
  updateShippingBar(cart.total);
  // 다음 달엔 "추천 상품 갱신"이 여기 한 줄 더 붙는다
}
```

`removeFromCart()`와 `changeQuantity()`에도 같은 세 줄이 있고, 그중 하나는 `updateShippingBar`를 빠뜨려서 수량을 줄여도 무료 배송 막대가 그대로다. 장바구니 코드가 화면의 모든 부품을 알고 있는 것이 문제다. 화면 부품이 늘 때마다 장바구니를 고쳐야 한다. 거꾸로 해야 한다. 장바구니는 "바뀌었다"고만 알리고, 알고 싶은 쪽이 미리 등록해 두는 것이다. 이번 글은 한 객체의 변화를 여러 객체가 자동으로 전달받게 하는 옵서버(Observer) 패턴이다.

## 바뀌었다고 알리는 쪽, 등록해 두는 쪽

옵서버에는 두 역할이 있다. 상태를 가지고 바뀔 때 알리는 주체(Subject)와, 알림을 받고 싶어 등록해 두는 관찰자(Observer)다. 주체가 관찰자를 두고 아는 것은 `update()`를 부를 수 있다는 것 하나뿐이다. 배지인지 막대인지, 몇 개가 붙어 있는지 모른다.

```ts
interface CartItem { sku: string; price: number; qty: number }

interface Observer<T> {
  update(subject: T): void;
}

class CartStore {
  private items: CartItem[] = [];
  private readonly observers = new Set<Observer<CartStore>>();

  attach(o: Observer<CartStore>) {
    this.observers.add(o);
  }
  detach(o: Observer<CartStore>) {
    this.observers.delete(o);
  }
  private notify() {
    for (const o of [...this.observers]) o.update(this); // 복사본을 돈다 (이유는 뒤에서)
  }

  add(item: CartItem) {
    this.items = [...this.items, item];
    this.notify();
  }
  remove(sku: string) {
    this.items = this.items.filter((i) => i.sku !== sku);
    this.notify();
  }
  get count() {
    return this.items.reduce((n, i) => n + i.qty, 0);
  }
  get total() {
    return this.items.reduce((sum, i) => sum + i.price * i.qty, 0);
  }
}

class CartBadge implements Observer<CartStore> {
  update(cart: CartStore) {
    console.log(`badge: ${cart.count}`);
  }
}

class ShippingBar implements Observer<CartStore> {
  constructor(private readonly freeOver: number) {}
  update(cart: CartStore) {
    const left = this.freeOver - cart.total;
    console.log(left > 0 ? `${left}원 더 담으면 무료 배송` : "무료 배송");
  }
}

const cart = new CartStore();
cart.attach(new CartBadge());
cart.attach(new ShippingBar(30000));
cart.add({ sku: "PEN-01", price: 12000, qty: 2 }); // badge: 2 / 6000원 더 담으면 무료 배송
```

`add`와 `remove`는 이제 화면을 모른다. 추천 상품 부품이 생기면 그 부품이 `cart.attach()`를 부르면 된다. 장바구니 코드는 한 줄도 바뀌지 않는다. 아래 그림에서 다음을 누르면 상품 하나를 담았을 때 알림이 퍼지는 순서가 보인다.

## 값을 실어 보낼까, 꺼내 가게 할까

알림에 무엇을 담을지는 두 갈래다. 위 코드처럼 주체 자신을 넘기고 관찰자가 필요한 값을 읽어 가는 pull 방식, 그리고 바뀐 값을 알림에 실어 보내는 push 방식(`update({ type: "added", item })`)이다.

pull은 주체가 관찰자마다 무엇이 필요한지 몰라도 되고, 관찰자는 늘 최신 상태를 읽는다. 대신 무엇이 바뀌었는지 알 수 없으니 관찰자가 매번 전체를 다시 계산한다. push는 관찰자가 "추가된 상품만 애니메이션으로 보여 주기" 같은 일을 할 수 있지만, 이벤트 모양이 주체와 관찰자 사이의 약속이 되어 함부로 바꾸지 못한다. 화면 상태 관리 라이브러리는 대부분 pull 쪽이다. "바뀌었다"만 알리고, 구독자가 `getState()`로 읽는다. 서버의 도메인 이벤트는 대부분 push 쪽이다. `OrderPaid { orderId, amount }`처럼 무슨 일이 있었는지 실어 보낸다.

## 클래스 대신 구독 함수 하나

자바스크립트에서는 `Observer` 인터페이스를 따로 두지 않는다. 관찰자는 그냥 함수이고, 구독하면 구독을 끊는 함수를 돌려받는다. 끊는 방법이 구독한 자리에 함께 있어서 짝을 맞추기 쉽다.

```ts
type Listener = () => void;

function createStore<T extends object>(initial: T) {
  let state = initial;
  const listeners = new Set<Listener>();
  return {
    get: () => state,
    set(patch: Partial<T>) {
      state = { ...state, ...patch }; // 늘 새 객체. 이전 상태와 비교하기 쉽다
      for (const l of [...listeners]) l();
    },
    subscribe(l: Listener) {
      listeners.add(l);
      return () => {
        listeners.delete(l); // 구독을 끊는 함수
      };
    },
  };
}
```

Redux의 `store.subscribe(listener)`, Zustand의 `subscribe`, Jotai의 `store.sub`가 모두 이 모양이다. 브라우저의 `addEventListener`는 끊는 함수를 돌려주지 않는 대신 `AbortSignal`을 받는다. `{ signal }`을 넘겨 두면 `controller.abort()` 한 번으로 여러 리스너를 함께 뗄 수 있다.

이런 저장소를 React에 연결하는 공식 통로가 `useSyncExternalStore`다. React는 외부 저장소의 변화를 이 훅으로 구독한다.

## 알리는 도중에 구독을 끊으면

위 코드의 `notify`가 `[...listeners]` 복사본을 도는 이유가 있다. 관찰자가 알림을 받은 김에 구독을 끊는 일은 흔하다. 한 번만 받고 싶은 분석 이벤트가 그렇다. 복사 없이 배열을 인덱스로 돌면 이렇게 된다.

```text
naive   : badge, analytics(once), shippingBar
emitter : badge, analytics(once), miniCart, shippingBar
```

첫 줄은 배열을 직접 돈 결과다. `analytics`가 자기를 배열에서 지우는 순간 뒤의 리스너가 한 칸씩 당겨졌고, 반복문은 다음 인덱스로 넘어가 `miniCart`를 건너뛰었다. 둘째 줄은 Node.js의 `EventEmitter`로 같은 일을 한 결과다. `EventEmitter`는 알리기 전에 리스너 배열을 복사해 두기 때문에 아무도 빠지지 않는다. 아래 그림에서 다음을 누르면 한 리스너가 빠지는 순간이 보인다.

## 동기 알림은 예외도 동기로 돌아온다

서버에서도 같은 구조를 쓴다. 결제가 끝나면 메일을 보내고, 포인트를 쌓고, 슬랙에 알린다. 주문 서비스는 `orders.emit("paid", order)` 한 줄만 쓰고, 각 기능은 `orders.on("paid", ...)`로 붙는다. 그런데 `EventEmitter`의 `emit`은 리스너를 등록된 순서대로 그 자리에서 하나씩 부르는 평범한 함수 호출이다. 리스너 하나가 예외를 던지면 어떻게 될까.

```js
import { EventEmitter } from "node:events";

const orders = new EventEmitter();
orders.on("paid", (o) => console.log("mail   ", o.id));
orders.on("paid", (o) => { console.log("points ", o.id); throw new Error("points DB timeout"); });
orders.on("paid", (o) => console.log("slack  ", o.id));

console.log("before emit");
try {
  orders.emit("paid", { id: 42 });
} catch (e) {
  console.log("emit threw:", e.message);
}
console.log("after emit");
```

```text
before emit
mail    42
points  42
emit threw: points DB timeout
after emit
```

포인트 리스너가 던진 예외가 `emit`을 부른 주문 서비스로 그대로 올라왔고, 슬랙 리스너는 불리지도 않았다. 주문 서비스가 이 예외를 결제 실패로 처리하면, 메일은 이미 나갔는데 결제는 실패로 기록된다. 아래 그림이 그 길이다.

리스너를 `async` 함수로 바꾸면 더 나빠진다. `emit`은 리스너가 돌려준 Promise를 기다리지도, 잡지도 않는다. 거부된 Promise는 처리되지 않은 거부가 되고, Node.js 15부터는 기본 설정에서 프로세스가 종료된다. 직접 돌렸을 때 종료 코드 1로 끝났다. `new EventEmitter({ captureRejections: true })`로 만들면 거부를 `'error'` 이벤트로 돌려준다.

```text
error listener: mail API 503
still alive
```

`'error'` 이벤트 자체도 특별하다. `'error'`를 듣는 리스너가 하나도 없는데 `emit("error", err)`이 일어나면 `EventEmitter`는 그 에러를 던진다. 처리하지 않으면 프로세스가 내려간다.

```text
node:events:497
      throw er; // Unhandled 'error' event
      ^

Error: redis connection lost
```

정리하면 이렇다. 관찰자 하나의 실패가 주체와 다른 관찰자에게 번지지 않아야 하면, 리스너마다 `try...catch`로 감싸 로그를 남기거나, 알림을 큐에 넣고 따로 처리한다. 결제처럼 실패하면 안 되는 일과 메일처럼 나중에 다시 해도 되는 일을 같은 `emit`에 묶지 않는다. 프로세스 밖으로, 다른 서버로 알려야 하면 그때부터는 이 패턴이 아니라 메시지 브로커를 두는 [발행·구독](/posts/pub-sub)의 영역이다. 옵서버는 주체가 관찰자 목록을 직접 들고 같은 프로세스에서 부르고, 발행·구독은 브로커가 사이에 있어 서로의 존재도, 같은 시각에 살아 있는지도 모른다.

## 리스너 열한 개째의 경고

`EventEmitter`에 같은 이벤트 리스너를 열한 개 붙이면 Node.js가 경고를 찍는다.

```text
(node:18678) MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 paid listeners added to [EventEmitter]. MaxListeners is 10. Use emitter.setMaxListeners() to increase limit
```

경고 문구가 "메모리 누수일 수 있다"인 이유가 있다. 옵서버에서 가장 흔한 누수는 구독만 하고 끊지 않는 것이다. 주체가 관찰자 목록으로 관찰자를 붙잡고 있으니, 관찰자가 화면에서 사라져도 GC가 치우지 못한다. 요청마다 `emitter.on()`을 하고 `off()`를 잊으면 리스너가 요청 수만큼 쌓이고, 10개를 넘는 순간 이 경고가 뜬다. 정말로 리스너가 많이 필요한 주체라면 `setMaxListeners`로 올리면 되지만, 경고를 끄기 전에 리스너가 왜 늘어나는지부터 본다. 브라우저 쪽에서 화면을 떠나도 남는 리스너를 찾는 방법은 [메모리 누수 글](/posts/js-memory-leak#페이지를-떠나도-남는-리스너)에 있다.

경고만 보고는 어디서 리스너를 붙였는지 모른다. `node --trace-warnings app.js`로 띄우면 경고에 스택이 붙는다. 요청 핸들러 안에서 `bus.on("config", ...)`을 부르는 함수를 열한 번 불러 봤더니, 스택의 `EventEmitter.addListener` 바로 아래 줄에 그 핸들러 함수 이름과 줄 번호(`at handle (…/leak.mjs:3:28)`)가 찍혔다. 운영에서는 `process.on("warning", ...)`으로 이 경고를 받아 로그로 보내 두면 누수가 시작된 배포를 찾기 쉽다. 경고는 경고일 뿐이라 리스너는 열한 번째도, 백 번째도 그대로 붙는다.

## 다음 이벤트를 await로 기다리기

콜백 대신 `await`로 이벤트를 받고 싶을 때가 있다. 서버가 `listening`을 낼 때까지 기다리거나, 스트림이 `drain`될 때까지 쓰기를 멈추는 경우다. `node:events`의 `once(emitter, name)`은 다음 한 번을 Promise로 바꿔 준다. 이벤트 인자들이 배열로 오고, 그 사이에 `'error'`가 나면 거부된다.

```js
import { EventEmitter, once, on } from "node:events";

const orders = new EventEmitter();
setTimeout(() => orders.emit("paid", { id: 1 }, "card"), 10);
console.log("once resolved:", JSON.stringify(await once(orders, "paid")));

setTimeout(() => orders.emit("error", new Error("redis connection lost")), 10);
try { await once(orders, "paid"); } catch (e) { console.log("once rejected:", e.message); }
```

```text
once resolved: [{"id":1},"card"]
once rejected: redis connection lost
```

두 번째가 중요하다. 앞에서 `'error'` 리스너가 없으면 프로세스가 내려간다고 했는데, `once`는 기다리는 동안 `'error'` 리스너를 잠깐 붙여 두니 그 에러가 거부로 바뀌어 `try...catch`에서 잡힌다.

이벤트를 계속 받으려면 `on(emitter, name)`이 비동기 이터레이터를 돌려준다. `for await`로 돌고, 멈출 때는 `AbortSignal`을 쓴다. 이벤트 세 개를 한꺼번에 내고 루프 안에서 하나에 20ms씩 걸리게 했다.

```js
const ac = new AbortController();
setTimeout(() => { for (const id of [2, 3, 4]) orders.emit("paid", { id }); }, 10);
let n = 0;
try {
  for await (const [o] of on(orders, "paid", { signal: ac.signal })) {
    console.log("for await got", o.id, "listeners:", orders.listenerCount("paid"));
    await new Promise((r) => setTimeout(r, 20)); // 느린 처리
    if (++n === 3) ac.abort();
  }
} catch (e) { console.log("loop ended:", e.name); }
console.log("after loop listeners:", orders.listenerCount("paid"));
```

```text
for await got 2 listeners: 1
for await got 3 listeners: 1
for await got 4 listeners: 1
loop ended: AbortError
after loop listeners: 0
```

첫 이벤트를 처리하는 20ms 동안 나머지 두 개가 이미 왔지만 버려지지 않고 차례로 나왔다. `on`이 안에 큐를 두고 쌓아 두기 때문이다. 대신 이 큐에는 한도가 없다. 이벤트가 처리 속도보다 빨리 오면 큐가 메모리를 계속 먹는다. 그리고 루프를 끝내면 리스너가 0개로 돌아왔다. `break`나 abort로 빠져나와야 리스너가 떨어지니, 신호 없이 무한히 도는 루프를 요청마다 만들면 앞의 누수와 같은 모양이 된다.

## 하나를 바꿨는데 두 번 알린다

주체의 값 두 개를 이어서 바꾸면 관찰자는 그 사이의 어정쩡한 상태를 본다. 상품 옵션을 "1개 1,000원"에서 "3개 묶음 500원"으로 바꾸는 상황을, 위의 `createStore`에 총액을 찍는 관찰자를 붙여 돌렸다.

```text
-- 따로 바꾸기 (옵션을 3개 묶음 500원짜리로)
total = 3 × 1000 = 3000
total = 3 × 500 = 1500
-- batch
total = 5 × 400 = 2000
```

수량만 바뀌고 단가는 아직 안 바뀐 순간의 3,000원이 관찰자에게 전달됐다. 화면이라면 숫자가 한 번 깜빡이고 끝나지만, 관찰자가 분석 이벤트를 보내거나 "3,000원 이상 무료 배송" 쿠폰을 띄운다면 틀린 값으로 일이 벌어진다. 이렇게 일관되지 않은 중간 상태가 새어 나가는 현상을 글리치(glitch)라고 부른다.

막는 방법은 알림을 모으는 것이다. 위 출력의 `batch`는 `createStore`에 메서드를 하나 더한 것으로, 함수가 도는 동안에는 알림을 미뤄 두었다가 끝난 뒤 한 번만 알린다. 아니면 두 값을 한 번의 `set({ qty: 3, unitPrice: 500 })`으로 바꾼다. React가 이벤트 핸들러 안의 `setState` 여러 번을 한 번의 렌더링으로 묶는 것, Vue나 Solid, Preact Signals 같은 반응형 라이브러리가 파생 값(computed)을 의존하는 값이 모두 갱신된 뒤에 한 번만 다시 계산하는 것이 모두 이 문제를 푸는 장치다.

알림 시점을 아예 뒤로 미루는 API도 있다. 브라우저의 `MutationObserver`는 DOM이 바뀔 때마다 바로 부르지 않고, 바뀐 기록을 모아 마이크로태스크로 한 번에 넘겨준다. `IntersectionObserver`도 교차 변화를 모아서 비동기로 알린다. 동기 알림의 예외 전파와 글리치를 피하는 대신, 알림을 받는 시점에는 이미 상태가 더 바뀌었을 수 있다. 콜백이 언제 실행되는지는 [이벤트 루프 글](/posts/event-loop)에서 다뤘다.

## 옵서버, 중재자, 발행·구독을 나란히 놓으면

셋 다 "누가 바뀌면 다른 누가 안다"를 다뤄서 자주 섞인다. 가르는 질문은 둘이다. 반응 로직이 어디에 있는가, 그리고 사이에 무엇이 있는가.

| | 사이에 있는 것 | 반응 로직의 위치 | 서로를 아나 |
|---|---|---|---|
| 옵서버 | 없음. 주체가 목록을 직접 든다 | 각 관찰자 | 주체는 관찰자 인터페이스만 안다 |
| [중재자](/posts/pattern-mediator) | 규칙을 가진 중재자 | 중재자 한곳 | 참여자는 중재자만 안다 |
| [발행·구독](/posts/pub-sub) | 브로커와 토픽 | 각 구독자 | 서로 전혀 모른다. 같은 시각에 살아 있지 않아도 된다 |

옵서버는 같은 프로세스 안, 하나의 주체에 여러 반응이 붙을 때 맞다. 반응끼리 서로 영향을 주며 규칙이 얽히기 시작하면 중재자로 모은다. 다른 서비스나 다른 시점으로 넘겨야 하면 발행·구독으로 간다. RxJS의 `Subject`는 이름 그대로 옵서버 패턴의 주체이고, `Observable`은 여기에 "끝났다(complete)", "실패했다(error)"라는 신호와 `map`, `filter` 같은 연산자를 더한 것이다. 구독하기 전엔 아무 일도 하지 않는 cold Observable은 [이터레이터](/posts/pattern-iterator)와 짝을 이룬다. 이터레이터는 쓰는 쪽이 `next()`로 당기고, Observable은 만드는 쪽이 `next()`로 민다.

## 면접에서 나올 만한 질문

### 옵서버 패턴은 무엇이고 어떤 문제를 푸나요?

한 객체(주체)의 상태가 바뀌면 그 객체에 등록된 여러 객체(관찰자)가 자동으로 알림을 받게 하는 패턴이다. 주체는 관찰자 목록과 알리는 방법만 알고, 관찰자가 무엇을 하는지는 모른다. 그래서 장바구니에 배지, 미니 장바구니, 배송 막대가 붙어도 장바구니 코드는 바뀌지 않고, 새 반응은 등록만 하면 된다.

### push 방식과 pull 방식은 어떻게 다른가요?

push는 바뀐 내용을 알림에 실어 보내고, pull은 바뀌었다는 사실만 알리고 관찰자가 주체에서 필요한 값을 읽어 간다. pull은 주체가 관찰자의 필요를 몰라도 되고 늘 최신 값을 읽지만, 무엇이 바뀌었는지 모른다. push는 변경 내용을 활용할 수 있지만 이벤트 모양이 약속이 되어 바꾸기 어렵다. 화면 상태 저장소는 대부분 pull, 서버의 도메인 이벤트는 대부분 push다.

### 옵서버와 발행·구독은 무엇이 다른가요?

옵서버는 주체가 관찰자 목록을 직접 들고 같은 프로세스에서 관찰자를 부른다. 발행·구독은 브로커와 토픽이 사이에 있어서 발행자와 구독자가 서로를 전혀 모르고, 같은 시각에 살아 있지 않아도 된다. 그래서 옵서버는 프로세스 안의 반응에, 발행·구독은 서비스 사이의 비동기 전달에 맞다.

### Node.js EventEmitter의 리스너에서 예외가 나면 어떻게 되나요?

`emit`은 리스너를 등록 순서대로 그 자리에서 동기로 부르기 때문에, 예외가 `emit`을 부른 곳으로 그대로 올라가고 뒤의 리스너는 불리지 않는다. `async` 리스너의 거부는 `emit`이 잡지 않아 처리되지 않은 거부가 되고, Node.js 15부터 기본 설정에서는 프로세스가 종료된다. 리스너마다 예외를 잡거나 `captureRejections: true`로 거부를 `'error'` 이벤트로 받고, `'error'` 리스너는 반드시 등록한다.

### 옵서버 패턴에서 메모리 누수는 왜 생기나요?

주체가 관찰자 목록으로 관찰자를 강하게 참조하기 때문이다. 관찰자가 더 이상 쓰이지 않아도 구독을 끊지 않으면 GC가 치우지 못하고, 요청이나 화면 전환마다 구독이 쌓인다. Node.js의 `MaxListenersExceededWarning`은 같은 이벤트에 리스너가 10개를 넘을 때 이 가능성을 알려 준다. 구독할 때 받은 해제 함수나 `AbortSignal`로 짝을 맞춰 끊는다.

### EventEmitter의 이벤트를 await로 받을 수 있나요?

`node:events`의 `once`는 다음 한 번을 Promise로 바꾸고, 기다리는 사이에 `'error'`가 오면 거부되어 `try...catch`로 잡힌다. 계속 받으려면 `on`이 돌려주는 비동기 이터레이터를 `for await`로 돈다. `on`은 처리하는 동안 온 이벤트를 한도 없는 큐에 쌓으니 처리 속도가 느리면 메모리가 는다. 루프를 끝내야 리스너가 떨어지므로 `AbortSignal`로 끝낼 시점을 정해 둔다.

### 알림 도중에 관찰자가 구독을 끊으면 어떤 문제가 생기나요?

리스너 배열을 직접 돌면, 지운 자리로 뒤의 리스너가 당겨지면서 바로 다음 리스너가 그 알림을 받지 못한다. 그래서 알리기 전에 목록을 복사해 그 복사본을 돈다. Node.js의 EventEmitter도 이렇게 해서 once 리스너가 빠져도 다른 리스너가 건너뛰어지지 않는다.

### 글리치는 무엇이고 어떻게 막나요?

연관된 값 두 개를 이어서 바꿀 때 관찰자가 하나만 바뀐 중간 상태를 보고 반응하는 현상이다. 수량과 단가를 따로 바꾸면 그 사이의 틀린 총액이 알림으로 나간다. 변경을 묶어 끝난 뒤 한 번만 알리거나, 두 값을 한 번에 바꾼다. React의 자동 배칭과 반응형 라이브러리의 computed 갱신 순서가 이 문제를 푸는 장치다.
