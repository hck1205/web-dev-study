장바구니 합계를 계산하는 `total` 함수가 있다. Alice는 main에서 "쿠폰은 최대 5,000원까지만"이라는 버그를 고쳤고, Bob은 `feature/tax` 브랜치에서 부가세 10%를 붙이는 작업을 했다. 둘 다 같은 함수의 마지막 줄 `return Math.max(0, sum - coupon);`을 고쳤다. Bob의 작업을 합치려고 main에서 `git merge feature/tax`를 쳤더니 이런 메시지가 나오고 멈췄다.

```text
Auto-merging cart.js
CONFLICT (content): Merge conflict in cart.js
Automatic merge failed; fix conflicts and then commit the result.
```

파일을 열면 `<<<<<<<`와 `>>>>>>>` 사이에 두 사람의 코드가 나란히 들어 있다. 처음 보면 저장소가 망가진 것 같지만, Git은 자기가 판단할 수 없는 부분만 남겨 두고 사람에게 묻는 중이다. 무엇을 기준으로 "판단할 수 없다"고 하는지 알면 충돌은 무섭지 않다.

이 글은 브랜치가 실제로는 무엇인지부터 보고, fast-forward와 3-way 병합이 어떻게 갈리는지, 충돌이 났을 때 어떤 순서로 풀고 어떻게 되돌리는지까지 따라간다. 커밋과 객체, 인덱스는 [앞 글](/posts/git-internals-basics)에서 다뤘다. 명령은 Ubuntu 24.04의 Git 2.43.0에서 실행했고, 커밋 해시는 따라 하는 사람마다 다르게 나온다.

## 브랜치는 커밋에 붙은 이름표다

장바구니 저장소를 하나 만들고 첫 커밋을 한다. 그다음 브랜치를 만들어 보면 브랜치가 무엇인지 바로 보인다.

```bash
# 지금 있는 브랜치 목록 (*가 현재 브랜치)
git branch

# 새 브랜치를 만든다 (만들기만 하고 옮겨 가지는 않는다)
git branch feature/coupon

# 브랜치마다 가리키는 커밋
git branch -v

# 브랜치의 정체: 커밋 해시 하나가 적힌 파일
cat .git/refs/heads/feature/coupon
```

```text
* main

  feature/coupon 41c076a 장바구니 합계
* main           41c076a 장바구니 합계

41c076ae12cb515b55614a77cb1fea1193caa61d
```

브랜치는 커밋 해시 하나를 적은 41바이트짜리 파일이다. 새 브랜치를 만들어도 파일이나 커밋이 복사되지 않는다. 그래서 브랜치는 저장소 크기와 상관없이 순식간에 만들어지고, 마음껏 만들고 지워도 된다. SVN에서 브랜치가 폴더 복사였던 것과 가장 크게 다른 점이다.

`HEAD`는 "지금 내가 어느 브랜치 위에 있나"를 적은 파일이다. 보통은 커밋이 아니라 브랜치 이름을 가리킨다.

```bash
# HEAD는 브랜치 이름을 가리킨다
cat .git/HEAD

# feature/coupon으로 옮겨 간다
git switch feature/coupon
cat .git/HEAD
```

```text
ref: refs/heads/main

Switched to branch 'feature/coupon'
ref: refs/heads/feature/coupon
```

커밋하면 Git은 HEAD가 가리키는 브랜치의 파일만 새 커밋 해시로 바꾼다. 다른 브랜치는 그대로다. 아래 그림에서 다음을 누르면 브랜치를 만들고, 옮겨 가고, 커밋하고, 합치는 동안 이름표가 어떻게 움직이는지 볼 수 있다.

## switch와 checkout은 무엇이 다른가

예전에는 브랜치를 옮길 때도, 파일을 되돌릴 때도 `git checkout` 하나를 썼다. `git checkout main`은 브랜치를 옮기고, `git checkout -- main`은 main이라는 파일을 되돌린다. 한 명령이 두 가지 전혀 다른 일을 하다 보니 실수가 잦았다. 그래서 Git 2.23(2019년)에서 둘을 나눴다. 브랜치 이동은 `git switch`, 파일 되돌리기는 `git restore`다. `checkout`은 지금도 그대로 동작하고, 오래된 문서나 스크립트에서는 계속 보인다.

```bash
# 브랜치 이동 (checkout main과 같다)
git switch main

# 새 브랜치를 만들면서 이동 (checkout -b와 같다)
git switch -c feature/tax

# 바로 전에 있던 브랜치로 (cd -처럼)
git switch -

# 커밋으로 이동하려면 --detach를 명시해야 한다
git switch 319be6e
```

```text
fatal: a branch is expected, got commit '319be6e'
hint: If you want to detach HEAD at the commit, try again with the --detach option.
```

`switch`는 커밋 해시를 받으면 거절한다. `checkout`은 아무 말 없이 받아서 아래에서 볼 detached HEAD 상태로 만든다. 실수로 그 상태에 들어가는 일을 막으려고 일부러 까다롭게 만든 것이다.

브랜치를 옮기면 작업 트리의 파일이 그 브랜치의 커밋 내용으로 바뀐다. 그래서 커밋하지 않은 변경이 옮겨 갈 브랜치의 내용과 부딪히면 Git이 이동을 거부한다.

```bash
# 커밋하지 않은 변경이 있는 상태에서, cart.js 내용이 다른 브랜치로 가려고 하면
echo '// 작업 중' >> cart.js
git switch feature/review
```

```text
error: Your local changes to the following files would be overwritten by checkout:
	cart.js
Please commit your changes or stash them before you switch branches.
Aborting
```

내 변경을 덮어써서 날리지 않으려는 안전장치다. 커밋하거나, `git stash`로 잠시 치워 두거나, 그 변경을 가지고 새 브랜치를 만들면(`git switch -c 새-브랜치`, 같은 커밋에서 출발하니 거절당하지 않는다) 된다. 옮겨 갈 브랜치에서도 같은 파일이 같은 내용이면 Git은 변경을 들고 그대로 옮겨 간다. 그래서 "바뀐 파일이 있는데 어떤 때는 되고 어떤 때는 안 된다"는 일이 생긴다. stash는 [되돌리기 글](/posts/git-undo)에서 자세히 본다.

## HEAD가 브랜치를 떠나면

HEAD가 브랜치 이름이 아니라 커밋 해시를 직접 가리키는 상태를 detached HEAD라고 한다. 옛 커밋을 확인하려고 `git checkout 해시`를 하거나, 태그를 체크아웃하거나, rebase 도중에 이 상태가 된다.

```bash
# 커밋으로 직접 이동한다
git checkout 319be6e

# HEAD에 브랜치 이름이 아니라 해시가 들어 있다
cat .git/HEAD
```

```text
Note: switching to '319be6e'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.

If you want to create a new branch to retain commits you create, you may
do so (now or later) by using -c with the switch command. Example:

  git switch -c <new-branch-name>

Or undo this operation with:

  git switch -

Turn off this advice by setting config variable advice.detachedHead to false

HEAD is now at 319be6e 부가세 10% 포함

319be6eec3d4b32e08845fa544dc14c61b635627
```

이 상태에서도 커밋은 된다. 문제는 그 커밋을 가리키는 브랜치가 없다는 것이다. 다른 브랜치로 옮겨 가면 그 커밋으로 돌아갈 이름이 사라진다. Git이 경고를 띄워 준다.

```bash
# detached HEAD에서 커밋하고
echo '// 확인용' >> cart.js
git commit -qam "분리된 HEAD에서 커밋"

# main으로 돌아가면
git switch main
```

```text
Warning: you are leaving 1 commit behind, not connected to
any of your branches:

  48ff667 분리된 HEAD에서 커밋

If you want to keep it by creating a new branch, this may be a good time
to do so with:

 git branch <new-branch-name> 48ff667

Switched to branch 'main'
```

커밋은 아직 지워지지 않았다. 경고에 나온 해시로 브랜치를 만들면 그대로 살아난다. 해시를 놓쳤으면 `git reflog`에서 HEAD가 지나간 자리를 찾는다. 이름표 없는 커밋은 reflog 기록이 만료되고 `git gc`가 돌 때 실제로 지워지는데, 기본 설정에서는 수십 일 여유가 있다.

```bash
# 경고에 나온 해시로 브랜치를 만들어 살린다
git branch rescue/tax-check 48ff667
git log --oneline -1 rescue/tax-check
```

```text
48ff667 분리된 HEAD에서 커밋
```

애초에 detached HEAD에서 작업을 시작할 생각이면 `git switch -c 새-브랜치`로 브랜치부터 만들면 된다. 아직 커밋 전이라면 작업 트리의 변경도 그대로 따라온다.

## fast-forward를 막거나 강제하기

fast-forward는 히스토리를 깔끔하게 남기지만, 나중에 보면 "이 커밋들이 한 기능으로 묶여 들어왔다"는 흔적이 사라진다. 기능 브랜치 단위로 기록을 남기고 싶으면 `--no-ff`로 fast-forward가 가능해도 병합 커밋을 만든다.

```bash
# 곧게 이어져 있어도 병합 커밋을 만든다
git merge --no-ff feature/log
git log --oneline --graph -3
```

```text
Merge made by the 'ort' strategy.
 cart.js | 1 +
 1 file changed, 1 insertion(+)

*   c7e17d8 Merge branch 'feature/log'
|\  
| * 5a0ba35 파일 설명 주석
|/  
```

반대로 `--ff-only`는 fast-forward가 될 때만 합치고, 양쪽에 각자 커밋이 쌓여 갈라져 있으면 아무것도 하지 않고 멈춘다. 원격의 main을 내 main에 반영할 때처럼 "내 쪽에 따로 커밋이 생겼을 리 없다"고 믿는 자리에 쓰면, 그 믿음이 틀렸을 때 바로 알 수 있다.

```bash
# main과 feature/tax가 각자 커밋을 쌓아 갈라진 상태에서 --ff-only를 쓰면
git merge --ff-only feature/tax
```

```text
hint: Diverging branches can't be fast-forwarded, you need to either:
hint: 
hint: 	git merge --no-ff
hint: 
hint: or:
hint: 
hint: 	git rebase
hint: 
hint: Disable this message with "git config advice.diverging false"
fatal: Not possible to fast-forward, aborting.
```

팀이 PR 병합 방식을 "Create a merge commit"으로 정했다면 GitHub는 내부적으로 `--no-ff`처럼 항상 병합 커밋을 만든다. 어느 쪽이 맞는지는 히스토리를 어떻게 읽고 싶은지에 달렸다. 브랜치 전략과 함께 [브랜치 전략 글](/posts/git-branching-strategy)에서 비교한다.

## 곧게 이어지지 않으면 세 스냅샷을 비교한다

fast-forward는 한쪽이 다른 쪽의 조상일 때만 된다. 두 브랜치가 각자 커밋을 쌓아 갈라졌다면 이름표를 미는 것만으로는 양쪽 변경을 다 담을 수 없다. 이때 Git은 3-way 병합을 한다. 비교하는 스냅샷이 세 개라서 붙은 이름이다.

- 우리 쪽(ours): 지금 있는 브랜치의 끝. 여기서는 main.
- 저쪽(theirs): 합칠 브랜치의 끝. 여기서는 feature/tax.
- 공통 조상(merge base): 두 브랜치가 갈라지기 직전의 커밋.

두 끝만 비교하면 "main에는 이 줄이 있고 feature/tax에는 없다"는 사실만 알 수 있다. 누가 추가했고 누가 지웠는지는 모른다. 공통 조상과 각각 비교하면 알 수 있다. 조상에 없던 줄이 한쪽에만 있으면 그쪽이 추가한 것이고, 조상에 있던 줄이 한쪽에서 사라졌으면 그쪽이 지운 것이다.

```bash
# 두 브랜치가 갈라진 모양
git log --oneline --graph --all -4

# 공통 조상
git merge-base main feature/tax
```

```text
* 152102f 쿠폰 최대 5000원
| * 319be6e 부가세 10% 포함
|/  
*   c7e17d8 Merge branch 'feature/log'

c7e17d8830d5b5e1abeec6d07838344ae2f999a7
```

Git이 공통 조상을 찾는 과정을 그림으로 보자. 다음을 누르면 양쪽 끝에서 부모를 따라 거슬러 가다가 처음 만나는 커밋이 공통 조상이 되고, 그 세 스냅샷으로 병합 커밋이 만들어진다.

한쪽만 바꾼 곳은 Git이 알아서 고른다. 양쪽이 같은 곳을 서로 다르게 바꿨을 때만 사람에게 묻는다. 서로 다른 파일을 고쳤거나 같은 파일이라도 떨어진 곳을 고쳤다면 충돌 없이 끝난다. 실제로 README를 추가한 `docs` 브랜치와 `.gitignore`를 추가한 main을 합치면 이렇다.

```bash
# 서로 다른 파일을 고친 두 브랜치를 합친다
git merge docs

# 병합 커밋 객체에 parent가 두 줄 있다
git cat-file -p HEAD
```

`|\`가 두 갈래가 병합 커밋에서 다시 만나는 곳이다. 첫 번째 parent는 병합할 때 서 있던 main의 이전 끝(`bcee6c2`), 두 번째 parent는 합쳐 들어온 docs의 끝(`8ba7c6c`)이다. 순서에 의미가 있다. `git log --first-parent`는 첫 번째 부모만 따라가서 "main에 무엇이 언제 들어왔나"만 한 줄로 보여 주고, 병합을 되돌릴 때 `git revert -m 1`의 1이 바로 이 첫 번째 부모다.

`ort`는 병합 전략 이름이다. 2.34부터 기본이 되었고, 그 전에는 `recursive`였다. 공통 조상이 여럿인 복잡한 모양에서도 결과가 같고 훨씬 빠르게 동작하도록 다시 만든 것이다. 출력에 이름만 나올 뿐 평소에 고를 일은 거의 없다.

## 같은 줄을 둘이 고쳤을 때

이제 처음 상황이다. main에서 `git merge feature/tax`를 하면 충돌이 난다. 먼저 상태를 본다.

```bash
# 충돌 난 병합
git merge feature/tax

# 지금 무슨 상태인지
git status
```

```text
Auto-merging cart.js
CONFLICT (content): Merge conflict in cart.js
Automatic merge failed; fix conflicts and then commit the result.

On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   cart.js

no changes added to commit (use "git add" and/or "git commit -a")
```

`You have unmerged paths`가 병합이 아직 끝나지 않았다는 뜻이다. Git은 `.git/MERGE_HEAD`에 합치려던 커밋을 적어 두고 사람이 마무리하기를 기다린다. 이 상태에서 할 수 있는 일은 둘이다. 충돌을 풀고 커밋하거나, `git merge --abort`로 병합 전으로 돌아가거나. `both modified`는 양쪽이 모두 고쳤다는 뜻이고, 한쪽은 고치고 다른 쪽은 지웠으면 `deleted by us`나 `deleted by them`이 나온다.

## 충돌 중에 Git이 들고 있는 것

충돌이 나면 인덱스에 그 파일이 세 버전으로 들어간다. 평소에는 스테이지 0 하나뿐인데, 충돌 중에는 1(공통 조상), 2(ours), 3(theirs)이 생긴다.

```bash
# 충돌 난 파일의 스테이지별 blob
git ls-files -u

# 스테이지 1, 공통 조상의 파일 내용
git show :1:cart.js
```

출력을 보면 `--theirs`로 고른 결과에는 Alice의 쿠폰 상한이 빠졌다. 통째로 고르면 다른 쪽의 변경은 그 파일에서 사라진다. 코드 파일에 습관적으로 `--ours`나 `--theirs`를 쓰면 안 되는 이유다. 병합 전체를 한쪽 기준으로 하는 `git merge -X ours`도 마찬가지로, 충돌 난 덩어리마다 우리 쪽을 고른다는 뜻이지 상대 변경을 검토했다는 뜻이 아니다.

충돌 블록이 길면 화면을 셋으로 나눠 보여 주는 병합 도구가 편하다. `git mergetool`은 설정한 도구로 충돌 파일을 하나씩 연다. VS Code를 쓰면 이렇게 등록한다.

```bash
# VS Code를 병합 도구로 등록한다
git config --global merge.tool vscode
git config --global mergetool.vscode.cmd 'code --wait --merge $REMOTE $LOCAL $BASE $MERGED'

# 병합 도구가 남기는 .orig 백업 파일을 만들지 않는다
git config --global mergetool.keepBackup false

# 충돌 파일을 차례로 연다
git mergetool
```

`$LOCAL`이 ours, `$REMOTE`가 theirs, `$BASE`가 공통 조상, `$MERGED`가 결과를 쓸 작업 트리 파일이다. 도구를 닫으면 Git이 자동으로 add한다.

충돌이 났을 때 "그 줄을 누가, 왜 바꿨나"를 알아야 제대로 합칠 수 있다. `git log --merge --oneline`은 충돌 난 파일을 건드린 양쪽 커밋만 보여 준다. 각 커밋 메시지를 보고 의도를 확인한 뒤 합치면 된다.

## 같은 충돌을 두 번 풀지 않게

긴 기능 브랜치에 main을 여러 번 합치거나, 병합을 되돌렸다가 다시 하면 같은 충돌을 몇 번이고 다시 풀게 된다. rerere(reuse recorded resolution)를 켜면 Git이 충돌 모양과 내가 푼 결과를 기억해 뒀다가 같은 충돌이 나면 알아서 적용한다.

```bash
# 충돌 해결 기록을 켠다
git config --global rerere.enabled true

# 앞에서 만든 병합 커밋을 버리고 같은 병합을 다시 해 본다
git reset -q --hard HEAD~1

# 충돌이 나면 충돌 모양을 기록한다
git merge feature/tax
```

```text
Auto-merging cart.js
CONFLICT (content): Merge conflict in cart.js
Recorded preimage for 'cart.js'
Automatic merge failed; fix conflicts and then commit the result.
```

```bash
# 직접 풀고 커밋하면 해결 결과를 기록한다
git add cart.js
git commit -q -m "Merge branch 'feature/tax'"

# 한 번 더 병합 커밋을 버리고 같은 병합을 하면
git reset -q --hard HEAD~1
git merge feature/tax
git status -s
```

```text
Recorded resolution for 'cart.js'.

Auto-merging cart.js
CONFLICT (content): Merge conflict in cart.js
Resolved 'cart.js' using previous resolution.
Automatic merge failed; fix conflicts and then commit the result.
UU cart.js
```

`Resolved 'cart.js' using previous resolution`이 나왔고 파일에는 마커 대신 지난번에 푼 내용이 들어 있다. 다만 `UU`가 그대로인 것처럼, rerere는 파일 내용만 채우고 add는 하지 않는다. 결과를 확인하고 직접 add해야 한다. 잘못 기억한 해결을 지우려면 `git rerere forget cart.js`를 쓴다. 기록은 `.git/rr-cache`에 있고 다른 사람과 공유되지 않는다.

## 다 쓴 브랜치는 지운다

병합이 끝난 브랜치는 지운다. 이름표만 지우는 것이라 커밋은 병합된 히스토리에 남는다. `-d`는 병합되지 않은 커밋이 있으면 거부하고, `-D`는 묻지 않고 지운다.

```bash
# 이미 main에 합쳐진 브랜치 삭제
git branch -d feature/tax

# 합쳐지지 않은 커밋이 있는 브랜치는 -d로 지울 수 없다
git branch -d feature/experiment

# 현재 브랜치에 합쳐지지 않은 브랜치 목록
git branch --no-merged
```

```text
Deleted branch feature/tax (was 319be6e).

error: the branch 'feature/experiment' is not fully merged.
If you are sure you want to delete it, run 'git branch -D feature/experiment'

  feature/experiment
```

`-d`가 거부하면 일단 멈추고 `git log main..feature/experiment`로 무엇이 남았는지 본다. 정말 필요 없으면 `-D`로 지운다. 실수로 지웠어도 `Deleted branch ... (was 해시)`에 나온 해시로 `git branch 이름 해시`를 하면 되살아난다.

여기에 squash merge가 끼면 헷갈리는 일이 생긴다. `git merge --squash`는 브랜치의 변경을 모두 합친 결과를 인덱스에 올려 줄 뿐 병합 커밋을 만들지 않는다. 내가 직접 커밋하면 부모가 하나인 평범한 커밋이 된다.

```bash
# 커밋 세 개짜리 브랜치를 하나로 뭉쳐서 합친다
git log --oneline main..feature/points
git merge --squash feature/points
git commit -qm "포인트 적립 (#42)"
git log --oneline --graph -3

# 내용은 다 들어갔는데 -d가 거부한다
git branch -d feature/points
```

```text
7c5cb3f 포인트 작업 3
febe838 포인트 작업 2
a682deb 포인트 작업 1

Updating 6b13a58..7c5cb3f
Fast-forward
Squash commit -- not updating HEAD
 cart.js | 3 +++
 1 file changed, 3 insertions(+)

* 212ac33 포인트 적립 (#42)
*   6b13a58 Merge branch 'feature/tax'
|\  
| * 319be6e 부가세 10% 포함

error: the branch 'feature/points' is not fully merged.
If you are sure you want to delete it, run 'git branch -D feature/points'
```

새 커밋 `212ac33`은 `feature/points`의 커밋들과 아무 연결이 없다. Git이 보기에 그 세 커밋은 main에 들어가지 않았으니 `-d`가 거부한다. GitHub에서 "Squash and merge"로 PR을 합친 뒤 로컬 브랜치를 지울 때 매번 보는 메시지다. 이 경우엔 `-D`가 맞다. 같은 이유로 squash 병합한 브랜치에서 작업을 이어 가다 다시 합치면 이미 들어간 변경이 또 충돌한다. squash로 합친 브랜치는 지우고 새로 만드는 편이 낫다.

## 원격 브랜치와 얼마나 차이 나는지

`git branch -vv`는 브랜치마다 연결된 원격 브랜치(upstream)와 앞서거나 뒤처진 커밋 수를 보여 준다. `-u`(`--set-upstream`)로 처음 푸시할 때 연결된다.

```bash
# 처음 푸시하면서 upstream을 연결한다
git push -u origin feature/review

# 커밋 하나를 더 한 뒤
git branch -vv
```

```text
To ../origin.git
 * [new branch]      feature/review -> feature/review
branch 'feature/review' set up to track 'origin/feature/review'.

  feature/coupon 77d96ad 쿠폰 할인
  feature/log    5a0ba35 파일 설명 주석
* feature/review 255cc74 [origin/feature/review: ahead 1] 리뷰 반영
  main           212ac33 [origin/main] 포인트 적립 (#42)
```

`ahead 1`은 아직 푸시하지 않은 커밋이 하나 있다는 뜻이고, `behind 2`가 나오면 원격에 내가 아직 받지 않은 커밋이 둘 있다는 뜻이다. 대괄호가 없는 브랜치는 원격과 연결되지 않은 로컬 전용 브랜치다. 이 숫자는 마지막으로 fetch한 시점 기준이라, 정확히 보려면 먼저 `git fetch`를 한다. 원격과 주고받는 자세한 이야기는 [원격 협업 글](/posts/git-remote-collaboration)에 있다.

## 충돌을 덜 만드는 습관

충돌은 브랜치가 오래 갈라져 있을수록, 같은 파일을 여러 사람이 고칠수록 커진다. 그래서 대응도 그 두 가지에 맞춰진다.

브랜치는 짧게 산다. 며칠 안에 합칠 수 있는 크기로 쪼개면 갈라진 동안 쌓이는 변경 자체가 적다. 기능이 덜 됐으면 기능 플래그로 숨겨서라도 자주 합친다.

오래 가는 브랜치라면 main을 자주 받아 온다. 기능 브랜치에서 `git merge main`(또는 [rebase](/posts/git-rebase))을 하루에 한 번쯤 하면, 충돌이 나도 어제 하루치만 풀면 된다. 2주 동안 미뤘다가 한 번에 합치면 2주치 충돌을 한 번에 만난다.

병합하기 전에 미리 볼 수도 있다. `git merge --no-commit --no-ff feature/tax`는 병합 결과를 만들어 두고 커밋 직전에 멈춘다. 마음에 안 들면 `git merge --abort`로 되돌린다. 원격 브랜치라면 `git diff main...feature/tax`(점 세 개)로 공통 조상 이후 그 브랜치에서 바뀐 것만 볼 수 있다.

포매터와 줄바꿈 설정을 팀이 맞춘다. 한 사람이 저장할 때마다 파일 전체의 따옴표나 들여쓰기가 바뀌면 의미 없는 충돌이 쏟아진다. Prettier 같은 포매터를 커밋 훅이나 CI로 강제하고, 대규모 포맷 변경은 따로 한 커밋으로 빠르게 합친다.

## 다시 정리하면

브랜치는 커밋 해시 하나를 적은 이름표이고, HEAD는 지금 어느 이름표 위에 있는지를 가리킨다. 커밋하면 HEAD의 이름표만 앞으로 간다. 합칠 때 한쪽이 다른 쪽의 조상이면 이름표만 미는 fast-forward로 끝나고, 갈라져 있으면 공통 조상과 양쪽 끝 세 스냅샷을 비교하는 3-way 병합으로 부모가 둘인 커밋을 만든다. 처음 상황의 충돌은 공통 조상에서 같은 줄을 양쪽이 다르게 고쳤기 때문에 생겼고, 공통 조상까지 보여 주는 zdiff3로 보면 두 사람의 의도가 보인다. 다음 글에서는 병합 대신 커밋을 옮겨 다시 쓰는 [rebase](/posts/git-rebase)를 본다.

## 면접에서 나올 만한 질문

### Git에서 브랜치는 무엇인가요?

특정 커밋의 해시 하나를 담은 움직이는 이름표다. `.git/refs/heads/브랜치명` 파일 하나라서 만들고 지우는 비용이 거의 없고, 파일이나 커밋을 복사하지 않는다. 커밋하면 HEAD가 가리키는 브랜치의 해시만 새 커밋으로 바뀐다. 브랜치를 지워도 커밋은 다른 브랜치나 reflog에서 닿을 수 있는 한 남는다.

### HEAD와 detached HEAD는 무엇인가요?

HEAD는 지금 작업 중인 위치로, 보통은 커밋이 아니라 브랜치 이름을 가리킨다. 커밋 해시나 태그를 직접 체크아웃하면 HEAD가 커밋을 바로 가리키는 detached HEAD가 된다. 그 상태에서 만든 커밋은 어떤 브랜치도 가리키지 않아서 다른 곳으로 옮겨 가면 찾기 어려워지고, 결국 gc 대상이 된다. 작업을 남기려면 `git switch -c 이름`이나 `git branch 이름 해시`로 이름표를 붙인다.

### fast-forward 병합과 3-way 병합은 언제 갈리나요?

합칠 브랜치가 현재 브랜치의 후손이면, 즉 현재 브랜치가 그 사이에 따로 커밋하지 않았으면 fast-forward로 이름표만 앞으로 민다. 양쪽이 각자 커밋해서 갈라졌으면 공통 조상(merge base)과 양쪽 끝을 비교하는 3-way 병합을 하고 부모가 둘인 병합 커밋을 만든다. `--no-ff`는 fast-forward가 가능해도 병합 커밋을 만들고, `--ff-only`는 fast-forward가 안 되면 실패한다.

### 3-way 병합에서 공통 조상이 왜 필요한가요?

두 끝만 비교하면 어떤 줄이 다를 때 누가 추가했고 누가 지웠는지 알 수 없다. 공통 조상과 각각 비교하면 한쪽만 바꾼 줄은 그쪽 변경을 자동으로 고를 수 있고, 양쪽이 같은 줄을 다르게 바꿨을 때만 충돌로 남긴다. 그래서 충돌은 "같은 곳을 둘 다 다르게 고쳤다"는 뜻이고, 서로 다른 파일이나 떨어진 줄을 고친 경우는 자동으로 합쳐진다.

### 충돌이 나면 어떻게 해결하나요?

`git status`로 충돌 파일을 확인하고, 파일의 마커 블록에서 양쪽 의도를 살려 고친 뒤 마커를 지운다. zdiff3 형식을 켜 두면 공통 조상의 원래 줄이 보여서 각자 무엇을 바꿨는지 판단하기 쉽고, `git log --merge`로 관련 커밋을 볼 수 있다. 고친 파일은 `git add`로 해결 표시를 하고, `git diff --check`로 남은 마커를 확인한 뒤 테스트를 돌리고 `git commit`으로 병합을 마친다. 정리가 안 되면 `git merge --abort`로 병합 전으로 돌아간다.

### 충돌 중에 --ours와 --theirs는 무엇을 가리키나요?

merge에서 ours는 병합을 실행한 현재 브랜치, theirs는 합쳐 들어오는 브랜치다. 인덱스의 스테이지 2와 3에 해당하고, `git checkout --ours 파일`은 그 파일을 통째로 한쪽 버전으로 꺼낸다. rebase에서는 반대로, ours가 옮겨 갈 대상(upstream)이고 theirs가 다시 적용 중인 내 커밋이다. 통째로 고르면 다른 쪽 변경이 그 파일에서 사라지니 lock 파일처럼 손으로 합칠 수 없는 파일에만 쓴다.

### squash merge한 브랜치를 git branch -d로 지우려 하면 왜 거부되나요?

squash merge는 브랜치의 변경을 합친 새 커밋 하나를 만들 뿐, 원래 브랜치 커밋과 부모 관계로 이어지지 않는다. Git은 브랜치의 커밋이 현재 브랜치에서 닿을 수 있는지로 병합 여부를 판단하므로 내용이 다 들어갔어도 "not fully merged"라고 본다. 내용을 확인했다면 `-D`로 지우고, 그 브랜치에서 작업을 이어 가지 말고 새로 만든다.

### 병합 커밋의 첫 번째 부모와 두 번째 부모는 어떻게 다른가요?

첫 번째 부모는 병합을 실행할 때 서 있던 브랜치의 이전 끝이고, 두 번째 부모는 합쳐 들어온 브랜치의 끝이다. `git log --first-parent`는 첫 번째 부모만 따라가서 main에 들어온 기능 단위 히스토리를 보여 준다. 병합을 되돌리는 `git revert -m 1`의 1도 첫 번째 부모를 기준으로 삼아 그쪽으로 되돌리겠다는 뜻이다.
