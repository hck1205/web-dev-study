역 일곱 개가 이어진 작은 노선도에서 A역부터 G역까지 몇 정거장인지 구하는 함수를 짰다. 재귀로 이웃을 따라가다 G에 닿으면 그 경로를 돌려주는 코드다. 테스트를 돌리니 6정거장이 나왔다. 그런데 노선도를 손으로 따라가 보면 4정거장짜리 길이 있다.

```text
BFS { order: 'A:0 B:1 C:1 D:2 E:2 F:3 G:4', path: 'A→B→D→F→G', hops: 4 }
DFS { path: 'A→B→D→C→E→F→G', hops: 6 }
```

두 줄은 같은 그래프를 두 가지 방법으로 훑은 결과다. 아래 줄의 깊이 우선 탐색(DFS)은 처음 찾은 길을 돌려줬고, 위 줄의 너비 우선 탐색(BFS)은 가장 짧은 길을 돌려줬다. 코드가 틀린 게 아니라 고른 탐색이 질문에 맞지 않았다.

이 글은 그래프를 메모리에 어떻게 담는지부터 BFS와 DFS가 각각 무엇을 보장하는지, 사이클 찾기와 위상 정렬, 격자에서 섬 세기까지 면접에 나오는 그래프 문제를 Node 22로 돌려 가며 따라간다. 트라이 위에서 돌렸던 DFS는 [트라이 글](/posts/ds-trie)에, 그래프의 연결 여부만 빠르게 묻는 구조는 [유니온 파인드](/posts/ds-union-find)에 있다. 자료구조 전체 지도는 [자료구조 한눈에 고르기](/posts/data-structures-overview)에 있다.

## 점과 선을 메모리에 담는 두 방법

그래프는 정점(점)과 간선(점 사이 선)으로 이루어진다. 역과 노선, 사용자와 팔로우, 패키지와 의존 관계가 모두 그래프다. 간선에 방향이 있으면 방향 그래프, 없으면 무방향 그래프라고 한다.

메모리에 담는 방법은 크게 두 가지다. 인접 리스트는 정점마다 이웃 목록을 배열로 들고 있다. 인접 행렬은 V×V 표를 만들고 `i`와 `j`가 이어져 있으면 `[i][j]` 칸에 1을 적는다.


그래서 기본은 인접 리스트다. 행렬은 정점이 수백 개 이하로 적거나, 거의 모든 쌍이 이어진 빽빽한 그래프이거나, 간선 존재 확인이 압도적으로 많을 때 고른다. 플로이드-워셜처럼 모든 쌍의 거리를 표로 다루는 알고리즘도 행렬과 잘 맞는다.

## 가까운 것부터 한 겹씩 넓히는 BFS

BFS는 출발점에서 한 정거장 떨어진 정점을 전부 보고, 그다음 두 정거장 떨어진 정점을 전부 보는 식으로 한 겹씩 넓혀 간다. 이 순서를 지키는 도구가 큐다. 먼저 넣은 것을 먼저 꺼내니, 가까운 정점이 먼 정점보다 항상 먼저 처리된다.

```js
function bfs(start, goal) {
  const dist = { [start]: 0 }, parent = { [start]: null };
  const queue = [start]; let head = 0;         // shift() 대신 머리 위치만 옮긴다
  while (head < queue.length) {
    const v = queue[head++];
    if (v === goal) break;
    for (const w of graph[v]) {
      if (w in dist) continue;                  // 이미 줄에 넣은 정점은 다시 넣지 않는다
      dist[w] = dist[v] + 1; parent[w] = v;     // 어디서 왔는지 적어 둔다
      queue.push(w);
    }
  }
  const path = []; for (let v = goal; v !== null; v = parent[v]) path.unshift(v); // 거꾸로 따라 올라간다
  return { path: path.join("→"), hops: dist[goal] };
}
```

`queue.shift()`를 쓰지 않은 데는 이유가 있다. V8에서 배열 앞을 빼면 나머지를 한 칸씩 당겨야 해서 큐가 길 때 O(n)이 된다. 그 측정은 [스택·큐·덱 글](/posts/ds-stack-queue-deque)에 있다. 여기서는 머리 위치 `head`만 옮겨서 꺼내기를 O(1)로 만든다.

아래 그림에서 다음을 누르면 큐가 어떻게 차고 빠지는지 볼 수 있다. 정점 옆 숫자는 A에서의 거리다.

가중치 없는 그래프에서 BFS가 최단 경로를 주는 이유는 이 순서에 있다. 거리 k인 정점은 모두 거리 k+1인 정점보다 먼저 큐에서 나온다. 그러니 어떤 정점이 처음 발견되는 순간은 그보다 짧은 길이 모두 검사된 뒤다. 더 짧은 길이 있었다면 그 길로 먼저 발견됐을 것이다. 그래서 처음 발견한 거리를 바로 확정하고, 다시 들르지 않는다.

모든 정점을 한 번씩 큐에 넣고, 정점마다 이웃 목록을 한 번씩 훑으니 시간은 O(V + E)다. 큐와 `dist`가 정점 수만큼 커지니 공간은 O(V)다.

## 한 갈래를 끝까지 가 보는 DFS

DFS는 이웃 하나를 골라 갈 수 있는 데까지 내려가고, 막히면 돌아와서 다음 이웃으로 간다. 처음 예제의 코드가 이것이다.

```js
function dfsFirstPath(start, goal) {
  const seen = new Set(), path = [];
  const go = (v) => {
    seen.add(v); path.push(v);
    if (v === goal) return true;
    for (const w of graph[v]) if (!seen.has(w) && go(w)) return true;
    path.pop(); return false;                   // 막혔으면 이 정점을 경로에서 뺀다
  };
  go(start);
  return { path: path.join("→"), hops: path.length - 1 };
}
```

A의 첫 이웃 B로, B의 첫 미방문 이웃 D로, D의 첫 미방문 이웃 C로 간다. C에서 E, F, G로 이어져 6정거장짜리 길에서 G를 만나고 끝난다. DFS는 길을 찾을 수는 있지만 그 길이 짧다는 보장은 없다.

그렇다고 DFS가 BFS보다 못한 방법은 아니다. DFS는 지금 경로 하나만 기억하면 되니 메모리가 경로 길이만큼이고, "이 경로 위에 내가 다시 나타나는가"를 자연스럽게 알 수 있다. 그래서 사이클 찾기, 위상 정렬, 모든 경로 나열, 백트래킹 문제에 맞는다. 브라우저의 `querySelectorAll`이 요소를 돌려주는 문서 순서도 DOM 트리를 전위 DFS로 훑은 순서다.

어느 쪽이든 "이미 본 정점"을 기억하지 않으면 사이클이 있는 그래프에서 영원히 돈다. A에서 B로 가면 B의 이웃에 다시 A가 있기 때문이다. 트리는 사이클이 없어서 방문 표시 없이도 끝나지만, 그래프 문제에서 방문 표시를 빼먹으면 무한 루프나 메모리 초과로 바로 이어진다.

## 재귀는 수천 단계에서 끊긴다

DFS를 재귀로 짜면 짧고 읽기 좋다. 대신 자바스크립트의 호출 스택에는 한계가 있다. 정점이 한 줄로 이어진 그래프로 깊이를 늘려 봤다.

```js
const line = (n) => Array.from({ length: n }, (_, i) => (i + 1 < n ? [i + 1] : []));
function dfsIterative(g) {
  const seen = new Uint8Array(g.length); let count = 0;
  const stack = [0];
  while (stack.length) {
    const v = stack.pop();
    if (seen[v]) continue;            // 꺼낼 때 확인: 스택엔 같은 정점이 여러 번 들어갈 수 있다
    seen[v] = 1; count++;
    for (const w of g[v]) if (!seen[w]) stack.push(w);
  }
  return count;
}
```

```text
n=1000 recursive=1000 iterative=1000
n=10000 recursive=RangeError: Maximum call stack size exceeded iterative=10000
n=100000 recursive=RangeError: Maximum call stack size exceeded iterative=100000
```

깊이 1만에서 재귀 버전이 `RangeError`로 죽었다. 이분 탐색으로 한계를 찾아보니 이 함수로는 실행마다 조금씩 달랐다.

```text
max depth ~ 5711
max depth ~ 6412
```

한계는 함수 하나가 스택에 차지하는 크기와 JIT 최적화 상태에 따라 달라져서 정확한 숫자를 믿으면 안 된다. Node 22 기본 설정에서 이런 클로저 재귀는 수천 단계쯤에서 끊긴다고 보면 된다. 코딩 테스트의 격자가 1000×1000이면 한 줄로 이어진 섬 하나가 깊이 100만이 될 수 있다. 입력이 크면 처음부터 명시적 스택으로 짠다. `--stack-size`로 늘리는 방법도 있지만 운영 코드에서 믿을 것은 못 된다.

명시적 스택 버전은 방문 표시를 꺼낼 때 한다. 넣을 때 표시하면 재귀 DFS와 방문 순서가 달라지는 경우가 있어서다. 순서가 상관없는 문제(연결 요소 세기 같은)라면 넣을 때 표시해도 된다.

## 방향 그래프에서 고리 찾기

빌드 도구가 "순환 의존이 있습니다"라고 말하며 멈추는 경우가 있다. 패키지 의존 관계는 방향 그래프다. `config`를 먼저 빌드해야 `db`를 빌드할 수 있고, `db`가 있어야 `auth`를 빌드한다. 누군가 `config`가 `auth`를 쓰도록 바꾸면 `auth → config → db → auth`라는 고리가 생겨 어느 것도 먼저 시작할 수 없다.

방향 그래프의 사이클은 DFS에 색 세 가지를 붙여 찾는다. 아직 안 간 정점은 흰색, 지금 걷는 경로 위의 정점은 회색, 그 아래를 다 보고 돌아온 정점은 검은색이다. 이웃 중에 회색이 있으면, 지금 경로를 따라 자기 조상으로 되돌아온 것이니 사이클이다.

```js
// 0 = 아직(흰색), 1 = 지금 경로 위(회색), 2 = 끝남(검은색)
const go = (v) => {
  color.set(v, 1); path.push(v);
  for (const w of out.get(v)) {
    if (color.get(w) === 1) return [...path.slice(path.indexOf(w)), w]; // 지금 경로로 되돌아왔다
    if (color.get(w) === 0) { const c = go(w); if (c) return c; }
  }
  color.set(v, 2); path.pop(); return null;
};
```


색이 셋이어야 하는 이유는 꼬리 질문으로 자주 나온다. 방문 여부만 두 가지로 보면, 다른 갈래에서 이미 끝낸 정점을 다시 만났을 때도 사이클이라고 오해한다. `A → B`, `A → C`, `C → B`는 B를 두 번 만나지만 고리가 아니다. 검은색은 "이미 봤지만 지금 경로 위는 아니다"를 구분해 준다.

무방향 그래프는 더 간단하다. 바로 직전에 온 부모 정점이 아닌데 이미 방문한 정점을 만나면 사이클이다. 무방향 그래프에서 간선을 하나씩 넣으며 "이 간선이 고리를 만드나"를 물어야 한다면 DFS를 매번 돌리는 것보다 [유니온 파인드](/posts/ds-union-find)가 훨씬 싸다.

## 먼저 할 일부터 줄 세우기

사이클이 없는 방향 그래프는 "모든 간선이 앞에서 뒤로 향하도록" 정점을 한 줄로 세울 수 있다. 이걸 위상 정렬이라고 한다. 빌드 순서, 강의 선수 과목, 작업 스케줄러, 마이그레이션 순서가 모두 이 문제다.

가장 많이 쓰는 방법은 칸(Kahn)의 알고리즘이다. 정점마다 "나를 기다리게 하는 간선 수"(진입 차수)를 센다. 0인 정점은 먼저 할 일이 없으니 바로 시작할 수 있다. 그걸 큐에 넣고, 하나 꺼낼 때마다 그 정점이 막고 있던 정점들의 진입 차수를 하나씩 줄인다. 0이 된 정점이 새로 줄에 선다.

```js
const queue = nodes.filter((n) => indeg.get(n) === 0); let head = 0; // 먼저 할 일이 없는 것부터
const order = [];
while (head < queue.length) {
  const v = queue[head++]; order.push(v);
  for (const w of out.get(v)) {
    indeg.set(w, indeg.get(w) - 1);            // v가 끝났으니 w가 기다릴 일이 하나 줄었다
    if (indeg.get(w) === 0) queue.push(w);
  }
}
const stuck = nodes.filter((n) => indeg.get(n) > 0); // 남은 게 있으면 사이클
```

실무에서 헷갈리는 지점이 아래 줄의 `stuck`이다. 여섯 개 전부가 남았지만 실제 고리는 `auth`, `config`, `db` 셋뿐이다. `api`, `worker`, `web`은 고리 뒤에 있어서 같이 막혔을 뿐이다. "순환 의존" 에러를 고칠 때 남은 목록 전체를 의심하면 엉뚱한 곳을 판다. 고리 자체는 색 세 가지 DFS로 찾아야 정확하다. ESLint의 `import/no-cycle` 규칙처럼 모듈 간 순환을 잡는 도구들도 결국 이 그래프 탐색을 한다.

정렬 결과는 하나가 아닐 수 있다. auth 다음에 api와 worker가 함께 풀렸고, 둘 중 무엇을 먼저 꺼내도 맞는 답이다. 면접에서 "답이 여러 개일 수 있나"를 물으면 그렇다고 답하고, 사전순처럼 하나로 정하고 싶으면 큐 대신 우선순위 큐를 쓴다고 하면 된다.

## 격자도 그래프다

## 선에 무게가 붙으면 BFS가 틀린다

BFS가 최단 경로를 주는 건 모든 간선의 길이가 같을 때만이다. 직행 버스로 30분 걸리는 A→C와, 5분씩 걸리는 지하철 A→B→C가 있다고 하자.

```text
BFS path A→C minutes 30
Dijkstra path A→B→C minutes 10
```

BFS는 간선 수가 적은 직행을 골랐다. 실제로 빠른 길은 두 번 갈아타는 쪽이다. 가중치가 있으면 "지금까지 비용이 가장 작은 정점부터" 확정하는 다익스트라를 쓴다. 큐 대신 [힙](/posts/ds-heap)으로 만든 우선순위 큐를 쓰는 BFS라고 보면 된다. 다익스트라와 목적지 쪽으로 기울이는 A*는 [지도와 길 찾기 글](/posts/sd-maps-tiles-routing)에서 실제 도로 그래프로 다룬다. 가중치가 0과 1 두 가지뿐이라면 덱의 앞뒤에 나눠 넣는 0-1 BFS로 힙 없이 O(V + E)에 풀 수 있다. 음수 가중치가 있으면 다익스트라도 틀리고 벨만-포드가 필요하다.

## 문제를 보고 탐색을 고르는 법

최단 거리, 최소 단계, 몇 번 만에 닿나를 물으면 BFS다. 가중치가 있으면 다익스트라로 바꾼다. 경로가 존재하나, 연결 요소가 몇 개인가는 BFS와 DFS 무엇이든 되고, 간선이 계속 추가되는 상황이면 유니온 파인드가 낫다. 사이클, 순서, 모든 경우를 따지는 문제는 DFS 쪽이다. 순서를 정하는 문제에서 사이클 여부만 알면 되면 칸의 알고리즘이 재귀 없이 깔끔하다.

현장에서 그래프 탐색이 문제를 일으키는 모습은 대개 셋이다. 방문 표시가 빠져 사이클에서 멈추지 않는 탐색, 깊은 입력에서 터지는 재귀, 그리고 탐색 범위를 제한하지 않아 폭발하는 질의다. 마지막은 "친구의 친구의 친구"처럼 단계가 늘 때마다 닿는 정점이 이웃 수의 거듭제곱으로 늘어나는 경우로, [그래프 DB 글](/posts/db-type-graph)에서 숫자로 볼 수 있다. 서비스에서 그래프 탐색을 돌린다면 깊이 상한과 방문 정점 수 상한을 함께 둔다.

## 면접에서 나올 만한 질문

### BFS와 DFS의 차이는 무엇이고 각각 언제 쓰나요?

BFS는 큐로 가까운 정점부터 한 겹씩 넓히고, DFS는 스택이나 재귀로 한 갈래를 끝까지 간 뒤 돌아온다. 가중치 없는 그래프의 최단 거리는 BFS가 보장한다. 사이클 찾기, 위상 정렬, 백트래킹처럼 지금 경로를 기억해야 하는 문제는 DFS가 맞는다. 둘 다 시간은 O(V + E)다.

### BFS가 가중치 없는 그래프에서 최단 경로를 보장하는 이유는요?

큐가 먼저 넣은 것을 먼저 꺼내므로, 거리 k인 정점이 모두 처리된 뒤에야 거리 k+1인 정점이 나온다. 그래서 어떤 정점이 처음 발견되는 순간 그보다 짧은 길은 이미 모두 검사된 상태다. 처음 발견한 거리를 확정하고 parent를 적어 두면 경로도 거꾸로 따라가 복원할 수 있다.

### 인접 리스트와 인접 행렬은 어떻게 고르나요?

기본은 인접 리스트다. 공간이 O(V + E)이고 이웃 훑기가 간선 수만큼이라, 대부분의 희소한 그래프에서 유리하다. 행렬은 O(V²) 공간이 들지만 간선 존재 확인이 O(1)이어서 정점이 적거나 빽빽한 그래프에 맞는다. 정점 1만, 간선 5만에서 행렬은 92MB, 리스트는 1MB가 안 됐다.

### 방향 그래프의 사이클은 어떻게 찾나요? 왜 색이 세 가지인가요?

DFS로 흰색(미방문), 회색(지금 경로 위), 검은색(완료)을 칠하고 회색 정점을 다시 만나면 사이클이다. 방문 여부만 보면 다른 갈래에서 끝낸 정점을 다시 만날 때도 사이클로 오해한다. 다이아몬드 모양처럼 한 정점에 두 길로 닿는 경우가 대표적이다. 칸의 알고리즘으로 결과가 정점 수보다 짧은지 봐도 된다.

### 위상 정렬은 어떻게 하고, 결과가 하나인가요?

칸의 알고리즘은 진입 차수 0인 정점을 큐에 넣고, 꺼낼 때마다 그 정점이 막던 정점의 차수를 줄여 0이 되면 넣는다. DFS로 끝난 순서를 뒤집어도 된다. 같은 시점에 풀리는 정점이 여럿이면 순서가 여러 개 나올 수 있고, 하나로 정하려면 큐 대신 우선순위 큐를 쓴다.

### 섬 개수 문제에서 방문 표시는 언제 하나요?

BFS에서는 큐에 넣는 순간 표시한다. 꺼낼 때 표시하면 같은 칸이 여러 이웃에게서 중복으로 들어가, 300×300 땅에서 넣는 횟수가 9만에서 18만으로 두 배가 됐다. 꺼낼 때 다시 확인하지도 않으면 결과까지 틀린다.

### 재귀 DFS의 위험은 무엇이고 어떻게 피하나요?

깊이가 호출 스택 한계를 넘으면 RangeError로 죽는다. Node 22 기본 설정에서 측정한 클로저 재귀는 수천 단계에서 끊겼고, 한계는 함수 크기와 JIT 상태에 따라 실행마다 달랐다. 입력이 크면 명시적 스택으로 바꾸고, 운영 코드에서는 스택 크기 옵션에 기대지 않는다.

### 간선에 가중치가 있으면 어떻게 하나요?

BFS는 간선 수를 최소로 할 뿐이라 틀린 답을 낸다. 음수가 없으면 힙으로 비용이 가장 작은 정점부터 확정하는 다익스트라를 쓰고, 가중치가 0과 1뿐이면 덱으로 0-1 BFS를 쓴다. 음수 간선이 있으면 벨만-포드가 필요하다.
