배포 스크립트 세 개를 어떤 순서로 돌려도 결과가 같은지 확인하고 싶었다. 마이그레이션, 캐시 비우기, 워커 재시작. 순서를 바꿔 가며 다 돌려 보면 되는데, 손으로 적다 보니 "캐시, 워커, 마이그레이션"을 빠뜨렸다. 나열할 대상이 세 개만 돼도 사람은 순서를 놓친다.

[LeetCode 46. Permutations](https://leetcode.com/problems/permutations/)가 그 나열을 짜는 문제다. [Subsets](/posts/leetcode-subsets)와 [Combination Sum](/posts/leetcode-combination-sum)이 "무엇을 고를까"였다면 이 문제는 "어떤 순서로 놓을까"다. 그래서 시작 위치 대신 "이미 쓴 원소" 표시가 필요하다. 이 글은 전부 만들고 거르는 풀이에서 시작해, 끼워 넣기, `used` 배열 백트래킹, 자리 바꾸기(swap), 다음 순열 반복, Heap 알고리즘까지 여섯 가지를 비교한다. 백트래킹의 일반적인 틀은 [재귀와 백트래킹 글](/posts/recursion-backtracking)에 있다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 같은 원소들을 줄 세우는 모든 방법

서로 다른 정수가 담긴 배열 `nums`가 주어진다. 이 원소들을 한 번씩 모두 써서 만들 수 있는 순열(permutation, 순서를 정해 늘어놓은 것)을 전부 돌려준다. 답의 순서는 상관없다.

제약은 길이가 1 이상 6 이하라는 것과 원소가 서로 다르다는 것이다. 6! = 720이라 답이 많지 않다. 원소가 서로 다르니 같은 순열이 두 번 나올 걱정은 없다. 같은 값이 섞인 버전은 LeetCode 47 Permutations II이고, 뒤에서 다룬다.

순열의 개수는 n!이다. 첫 자리에 n가지, 둘째 자리에 남은 n - 1가지, …, 마지막 자리에 1가지라서 곱하면 n · (n - 1) · … · 1이다. 이 수는 부분집합의 2^n보다 훨씬 빨리 커진다.

```text
n    2^n (부분집합)    n! (순열)
3         8                6
6        64              720
8       256            40320
10     1024          3628800
```

n = 10이면 순열이 363만 개다. 출력 자체가 n · n!이라서, 이 문제의 "빠른 풀이"는 쓸데없는 일을 덜 하는 풀이다.

## 손으로 [1, 2, 3]을 줄 세워 보면

맨 앞자리를 먼저 정하고, 남은 것으로 뒷자리를 채운다.

```text
맨 앞 1:  남은 [2, 3]  →  1 2 3,  1 3 2
맨 앞 2:  남은 [1, 3]  →  2 1 3,  2 3 1
맨 앞 3:  남은 [1, 2]  →  3 1 2,  3 2 1
```

"남은 것으로 뒷자리를 채운다"는 건 같은 문제의 작은 버전이다. 길이 3의 순열은 맨 앞을 하나 고른 뒤 남은 두 개의 순열을 붙인 것이다. 이 재귀 구조를 코드로 옮기는 방법이 여러 가지라서 풀이가 많다. 남은 것을 어떻게 표시하느냐(`used` 배열, 자리 바꾸기), 재귀를 쓰느냐 마느냐(끼워 넣기, 다음 순열)가 갈린다.

## 일단 다 만들고 겹친 걸 버리기

자리마다 n개 원소를 아무거나 넣어 보면 n^n가지 수열이 나온다. 그중 원소가 모두 다른 것만 남기면 순열이다.

```js
function permute(nums) {
  const n = nums.length;
  const res = [];
  const path = [];

  function go() {
    if (path.length === n) {
      if (new Set(path).size === n) res.push([...path]); // 겹친 원소가 없을 때만
      return;
    }
    for (const x of nums) {   // 이미 쓴 것도 상관없이 다 넣어 본다
      path.push(x);
      go();
      path.pop();
    }
  }

  go();
  return res;
}
```

답은 맞다. `[1, 2, 3]`에서 호출이 40번(1 + 3 + 9 + 27)이고, 끝까지 만든 27개 중 6개만 남는다. n = 6이면 호출이 55,987번에 끝까지 만든 46,656개 중 720개만 남긴다. n = 8에서 2568ms였다. 첫 두 자리에 같은 원소가 들어간 순간 이미 틀렸는데, 뒤를 끝까지 채운 다음에야 버린다.

## 하나씩 들이며 모든 틈에 끼워 넣기

재귀 없이 만드는 방법도 있다. 원소 하나짜리 순열 `[1]`에서 시작해, 다음 원소를 기존 순열의 모든 틈에 끼워 넣는다. 길이 k인 순열에는 틈이 k + 1개라서, 원소를 하나 들일 때마다 개수가 k + 1배가 된다.

```text
[]                → [1]
[1]  에 2 끼우기   → [2,1] [1,2]
[2,1]에 3 끼우기   → [3,2,1] [2,3,1] [2,1,3]
[1,2]에 3 끼우기   → [3,1,2] [1,3,2] [1,2,3]
```

```js
function permute(nums) {
  let res = [[]];
  for (const x of nums) {
    const next = [];
    for (const p of res) {
      for (let i = 0; i <= p.length; i++) {          // 틈이 p.length + 1개
        next.push([...p.slice(0, i), x, ...p.slice(i)]);
      }
    }
    res = next;
  }
  return res;
}
```

`[1, 2, 3]`에서 `321 231 213 312 132 123` 순서로 나온다. 겹치는 일이 없다. 어떤 순열이든 마지막 원소를 빼면 하나의 작은 순열이 되고, 그 원소가 있던 틈이 하나로 정해지기 때문이다. n = 9에서 236ms였다. 단계마다 모든 순열을 새로 복사해서 메모리를 많이 쓴다. 마지막 단계 직전에 (n - 1)!개, 마지막에 n!개를 동시에 들고 있다.

## 쓴 원소를 표시하며 자리를 채운다

손풀이를 그대로 옮긴 풀이다. 자리를 앞에서부터 채우고, 자리마다 아직 안 쓴 원소를 하나씩 놓아 본다. "아직 안 썼나"는 원소마다 불리언 하나를 두는 `used` 배열로 O(1)에 확인한다. [Subsets](/posts/leetcode-subsets)의 시작 위치 `start`는 "뒤쪽만 고른다"였지만, 순열은 앞쪽 원소도 뒷자리에 올 수 있으니 매번 처음부터 훑고 쓴 것만 건너뛴다.

아래 그림에서 칸은 원래 배열이고, 초록 칸이 `used`가 켜진 원소, 기억 장소가 채우는 중인 줄이다.

```js
function permute(nums) {
  const n = nums.length;
  const res = [];
  const path = [];
  const used = new Array(n).fill(false); // used[i]: nums[i]가 지금 줄에 있나

  function go() {
    if (path.length === n) {     // 모든 자리를 채웠다
      res.push([...path]);
      return;
    }
    for (let i = 0; i < n; i++) {
      if (used[i]) continue;     // 이미 줄에 선 원소는 건너뛴다
      used[i] = true;            // 놓고
      path.push(nums[i]);
      go();                      // 다음 자리로
      path.pop();                // 되돌린다. 두 가지를 다 되돌려야 한다
      used[i] = false;
    }
  }

  go();
  return res;
}
```

결과는 `123 132 213 231 312 321`로 사전순(원래 배열이 정렬돼 있을 때)이다. 호출 수는 n = 3에서 16번, n = 6에서 1957번이다. 깊이 k에 마디가 n! / (n - k)!개라 더하면 1 + 6 + 30 + 120 + 360 + 720 + 720 = 1957이다. 이 합은 대략 e · n!(e ≈ 2.718)로, 답 하나에 마디가 세 개가 안 된다. 막다른 갈래가 하나도 없다.

시간은 O(n · n!)이다. 마디마다 for문이 n번 돌고 마디가 약 e · n!개라 탐색이 O(n · n!), 답을 복사하는 것도 O(n · n!)이다. 공간은 출력을 빼면 `path`, `used`, 재귀 깊이 모두 O(n)이다. n = 9에서 134ms였다.

`includes`로 "이미 썼나"를 확인해도 답은 같다. `path.includes(x)`는 O(n)이라 마디마다 O(n²)이 되지만 n이 6 이하면 차이가 없다. 대신 값으로 비교해서 같은 값이 섞인 입력 `[1, 1, 2]`에서는 답이 하나도 안 나온다. `used`를 인덱스로 두는 편이 안전하다.

### Python과 Java로 쓰면

Python은 리스트 복사를 `path[:]`로 한다. 깊이가 n이라 재귀 한도와 거리가 멀다.

```python
from typing import List

def permute(nums: List[int]) -> List[List[int]]:
    n = len(nums)
    res = []
    path = []
    used = [False] * n

    def go() -> None:
        if len(path) == n:
            res.append(path[:])
            return
        for i in range(n):
            if used[i]:
                continue
            used[i] = True
            path.append(nums[i])
            go()
            path.pop()
            used[i] = False

    go()
    return res
```

실무에서는 `itertools.permutations(nums)`가 같은 순서의 튜플을 하나씩 내 준다. `[list(p) for p in permutations([1, 2, 3])]`가 위 결과와 같다. 제너레이터라서 전부 메모리에 올리지 않고 하나씩 쓸 수 있다.

Java는 `boolean[]`을 쓰고, 기록할 때 `new ArrayList<>(path)`로 복사한다.

```java
import java.util.ArrayList;
import java.util.List;

class Solution {
    public List<List<Integer>> permute(int[] nums) {
        List<List<Integer>> res = new ArrayList<>();
        go(nums, new boolean[nums.length], new ArrayList<>(), res);
        return res;
    }

    private void go(int[] nums, boolean[] used, List<Integer> path, List<List<Integer>> res) {
        if (path.size() == nums.length) {
            res.add(new ArrayList<>(path));
            return;
        }
        for (int i = 0; i < nums.length; i++) {
            if (used[i]) continue;
            used[i] = true;
            path.add(nums[i]);
            go(nums, used, path, res);
            path.remove(path.size() - 1); // 인덱스로 지운다
            used[i] = false;
        }
    }
}
```

세 언어 모두 `[1, 2, 3]`에서 같은 순서의 6개를, 길이 6에서 720개를 낸다. Java에서 `path.remove(nums[i])`로 쓰면 `int`라서 "그 값"이 아니라 "그 번째 칸"을 지운다. [Subsets 글](/posts/leetcode-subsets)에서 본 함정이다.

## 배열 안에서 자리를 바꿔 가며 채우기

`used`와 `path` 없이 원래 배열 하나로도 된다. 배열을 "앞쪽 k칸은 자리가 정해진 부분, 뒤쪽은 아직 남은 원소"로 나눠 본다. k번째 자리에 올 원소를 정할 때, 남은 원소 `a[k..n-1]` 중 하나 `a[i]`를 `a[k]`와 바꾼다. 그러면 남은 원소들이 여전히 뒤쪽에 모여 있다. 다음 자리로 들어갔다 돌아오면 다시 바꿔서 원래대로 되돌린다.

칸은 배열의 자리이고, 초록 칸이 자리가 정해진 앞쪽, 커서가 지금 정하는 자리 k다. 기억 장소는 배열의 지금 모습이다.

```js
function permute(nums) {
  const a = [...nums];  // 입력을 건드리지 않게 복사
  const n = a.length;
  const res = [];

  function go(k) {      // a[0..k-1]은 정해졌고, k번째 자리를 정한다
    if (k === n) {
      res.push([...a]); // 배열 전체가 순열 하나
      return;
    }
    for (let i = k; i < n; i++) {
      [a[k], a[i]] = [a[i], a[k]]; // 남은 원소 a[i]를 k번째 자리로
      go(k + 1);
      [a[k], a[i]] = [a[i], a[k]]; // 되돌린다
    }
  }

  go(0);
  return res;
}
```

결과는 `123 132 213 231 321 312`다. 마지막 두 개가 사전순과 다르다. 0번과 2번을 바꾸면 `321`이 되고, 그 뒤 1번과 2번을 바꿔 `312`가 나오기 때문이다. 순서가 상관없는 이 문제에서는 괜찮지만, 사전순 출력을 요구하면 이 풀이는 맞지 않는다.

호출 수는 `used` 풀이와 같은 1957번(n = 6)이지만, for문이 `k`부터 돌아서 쓴 원소를 건너뛰는 확인이 아예 없다. 추가 메모리는 재귀 깊이 O(n)뿐이다. JavaScript에서는 구조 분해 교환 `[a, b] = [b, a]`가 임시 배열을 만들어서 n = 9에서 174ms로 오히려 조금 느렸다. C++이나 Java처럼 교환이 싼 언어에서 이 풀이를 많이 쓴다.

되돌리는 교환을 빼먹으면 어떻게 될까. 실제로 돌려 보니 `123 132 312 321 123 132`가 나왔다. 개수는 6개로 맞는데 `213`, `231`이 빠지고 `123`, `132`가 두 번 나온다. 앞 갈래가 바꿔 놓은 배열 위에서 다음 갈래가 출발했기 때문이다. 개수만 세는 테스트로는 이 버그를 못 잡는다.

## 재귀 없이 다음 순열로 넘어가기

사전순으로 바로 다음 순열을 만드는 규칙이 있다. 이걸 n! - 1번 반복하면 재귀 없이 모든 순열이 나온다. LeetCode 31 Next Permutation이 이 규칙 하나를 짜는 문제다.

1. 뒤에서부터 보며 처음으로 `a[i] < a[i + 1]`인 i를 찾는다. 그 뒤쪽 `a[i+1..]`은 내림차순이라 이미 가장 큰 배치다.
2. 없으면 전체가 내림차순, 곧 마지막 순열이다. 끝낸다.
3. 뒤쪽에서 `a[i]`보다 큰 수 중 가장 오른쪽 `a[j]`(뒤쪽이 내림차순이라 가장 작은 큰 수)를 찾아 `a[i]`와 바꾼다.
4. `a[i+1..]`을 뒤집어 오름차순으로 만든다. 뒤쪽을 가장 작은 배치로 되돌리는 것이다.

`[1, 3, 2]`로 해 보자. 뒤에서 처음으로 작아지는 곳은 i = 0(1 < 3)이다. 뒤쪽 `[3, 2]`에서 1보다 큰 수 중 가장 오른쪽은 2다. 바꾸면 `[2, 3, 1]`, 뒤쪽 `[3, 1]`을 뒤집으면 `[2, 1, 3]`이다. 사전순으로 `132` 다음이 `213`이 맞다.

```js
function permute(nums) {
  const a = [...nums].sort((x, y) => x - y); // 가장 작은 순열에서 시작
  const n = a.length;
  const res = [];
  while (true) {
    res.push([...a]);
    let i = n - 2;
    while (i >= 0 && a[i] >= a[i + 1]) i--;   // 1. 뒤에서 처음 작아지는 곳
    if (i < 0) break;                         // 2. 마지막 순열
    let j = n - 1;
    while (a[j] <= a[i]) j--;                 // 3. a[i]보다 큰 가장 오른쪽 수
    [a[i], a[j]] = [a[j], a[i]];
    for (let l = i + 1, r = n - 1; l < r; l++, r--) {
      [a[l], a[r]] = [a[r], a[l]];            // 4. 뒤쪽을 오름차순으로
    }
  }
  return res;
}
```

재귀가 없고, 상태가 배열 하나뿐이라 "지금 몇 번째 순열을 보고 있었나"를 저장했다가 이어 가기 쉽다. 순열 하나에서 다음으로 넘어가는 비용은 평균 O(1)(최악 O(n))이다. n = 9에서 91ms로 여섯 풀이 중 가장 빨랐다. 다만 비교 연산자가 `>=`, `<=`라서 같은 값이 섞여 있어도 중복 없이 동작한다. `[1, 1, 2]`를 넣으면 `112 121 211` 세 개만 나온다. Permutations II를 정렬과 이 규칙만으로 푸는 방법이다.

## 교환 한 번에 순열 하나, Heap 알고리즘

B. R. Heap이 1963년에 낸 알고리즘은 이웃한 두 순열이 원소 두 개의 교환 한 번만큼만 다르게 모든 순열을 만든다. 순열 하나를 만드는 데 교환이 딱 한 번이다. 재귀 버전이 흔하지만 반복문 버전을 적었다.

```js
function permute(nums) {
  const a = [...nums];
  const n = a.length;
  const res = [[...a]];
  const c = new Array(n).fill(0); // c[i]: i번째 단계에서 몇 번 바꿨나
  let i = 1;
  while (i < n) {
    if (c[i] < i) {
      if (i % 2 === 0) [a[0], a[i]] = [a[i], a[0]];       // 짝수면 맨 앞과
      else [a[c[i]], a[i]] = [a[i], a[c[i]]];              // 홀수면 c[i]번째와
      res.push([...a]);
      c[i]++;
      i = 1;
    } else {
      c[i] = 0;
      i++;
    }
  }
  return res;
}
```

`[1, 2, 3]`에서 `123 213 312 132 231 321` 순서로 나온다. 이웃끼리 정확히 두 자리만 다르다. 순서가 사전순과 전혀 다르고, 왜 맞는지 증명이 까다로워서 면접에서 즉석으로 짜기는 어렵다. 순열마다 이전 결과를 조금만 고쳐 계산을 이어 가야 할 때(순열마다 합이나 비용을 다시 계산하지 않고 교환한 두 칸만 반영할 때) 의미가 있다. n = 9에서 113ms였다.

## 되돌리기를 하나만 하면

`used` 풀이에서 되돌릴 것은 둘이다. `path.pop()`과 `used[i] = false`. 둘 중 `used`를 되돌리는 줄을 빼먹으면 이렇게 된다.

```js
used[i] = true;
path.push(nums[i]);
go();
path.pop(); // used[i] = false가 빠졌다
```

`[1, 2, 3]`에서 결과가 `[[1,2,3]]` 하나뿐이었다. 첫 순열을 만들고 나면 세 원소가 모두 "썼다"로 남아서, 돌아온 뒤에 놓을 원소가 없다. 놓을 때 바꾼 상태는 전부, 바꾼 반대 순서로 되돌린다. 이게 백트래킹에서 "되돌린다"의 뜻이다.

복사하지 않고 `res.push(path)`를 쓰면 6개가 모두 빈 배열로 나온다. 자리 바꾸기 풀이에서는 `res.push(a)`를 쓰면 6칸이 모두 같은 배열 `a`를 가리키고, 끝나면 `a`가 원래대로 돌아오니 전부 `[1,2,3]`으로 보인다. 어느 쪽이든 기록할 때 복사한다.

자리 바꾸기 풀이에서 `nums`를 복사하지 않고 그대로 바꾸면, 결과는 맞아도 함수를 부른 쪽의 배열이 중간에 계속 흔들린다. 다른 스레드나 콜백이 그 배열을 보고 있다면 이상한 값을 본다. 입력은 복사해서 쓴다.

## 면접관이 조건을 바꾸면

### 같은 값이 섞여 있다면

LeetCode 47 Permutations II다. `[1, 1, 2]`를 이 코드에 넣으면 같은 순열이 두 번씩 6개 나온다. 정렬해서 같은 값을 붙이고, 같은 자리에서 같은 값을 두 번 놓지 않게 한다.

```js
if (used[i]) continue;
if (i > 0 && nums[i] === nums[i - 1] && !used[i - 1]) continue; // 앞의 같은 값을 아직 안 썼다면 건너뛴다
```

`!used[i - 1]` 조건은 같은 값이 여러 개면 늘 앞의 것부터 쓰게 순서를 강제한다. 그래서 같은 값끼리 자리를 바꾼 경우가 한 번만 만들어진다. `[1, 1, 2]`에서 `112 121 211` 세 개, `[1, 1, 2, 2]`에서 6개가 나온다. 자리 바꾸기 풀이라면 각 k에서 이미 그 자리에 놓아 본 값을 `Set`에 기억해 건너뛰고, 다음 순열 풀이는 고칠 게 없다.

### 사전순으로 k번째 순열 하나만 달라면

LeetCode 60 Permutation Sequence다. 다 만들면 n!개다. 대신 첫 자리를 정하면 나머지가 (n - 1)!가지라는 걸 이용한다. 0부터 센 k를 (n - 1)!로 나눈 몫이 첫 자리 원소의 순서, 나머지가 그 안에서의 위치다. 이걸 자리마다 반복하면 O(n²)에 끝난다.

```js
function getPermutation(n, k) {
  const nums = Array.from({ length: n }, (_, i) => i + 1);
  const fact = [1];
  for (let i = 1; i < n; i++) fact[i] = fact[i - 1] * i;
  k--;                                          // 0부터 센다
  let s = "";
  for (let i = n - 1; i >= 0; i--) {
    const idx = Math.floor(k / fact[i]);        // 이 자리에 올 원소의 순서
    s += nums.splice(idx, 1)[0];
    k %= fact[i];
  }
  return s;
}
// (3, 3) → "213"   (4, 9) → "2314"   (3, 6) → "321"
```

### 순열의 개수만 필요하고 n이 크다면

n!은 금방 정수 범위를 넘는다. Java `int`는 13!에서 넘쳐서 6227020800 대신 1932053504가 나온다. `long`은 20!까지 담고 21!에서 넘친다. JavaScript `number`는 22!까지 정확하고 23!부터 끝자리가 틀린다. 큰 값은 `BigInt`나 `BigInteger`를 쓰고, 문제가 나머지를 요구하면 곱할 때마다 나머지를 취한다.

### 길이 k짜리 순열만 달라면

`path.length === k`에서 기록하고 돌아가면 된다. 개수는 n! / (n - k)!이다. 이 경우에도 `used` 풀이가 그대로 맞고, 자리 바꾸기 풀이는 `k`번째 자리까지만 정하고 앞쪽 k칸을 잘라 기록한다.

### 메모리가 부족하다면

답을 모으지 않고 하나씩 처리한다. 다음 순열 풀이는 상태가 배열 하나라서, 만들고 쓰고 다음으로 넘어가면 추가 메모리가 O(1)이다. 백트래킹이라면 기록하는 자리에서 콜백을 부른다. n = 11이면 순열이 약 4천만 개라 전부 모으면 힙이 터진다. 이 숫자는 [재귀와 백트래킹 글](/posts/recursion-backtracking)에서 실제로 돌려 봤다.

### 비슷한 문제

순열에 가지치기가 붙으면 [N-Queens](/posts/leetcode-n-queens)가 된다. 행마다 열을 하나씩 고르는 게 열 번호의 순열을 만드는 것과 같고, 대각선 조건으로 갈래를 자른다. 문자열의 순열이 다른 문자열 안에 있는지 묻는 [Permutation in String](/posts/leetcode-permutation-in-string)은 순열을 만들지 않고 글자 개수만 비교하는 슬라이딩 윈도 문제다. 순열을 만들어 보려다 시간 초과가 나는 대표적인 함정이라 같이 보면 좋다.

## 순서 테스트를 실제로 돌리면

처음의 배포 스크립트 이야기로 돌아가 보자. 단계 세 개의 순서는 3! = 6가지라 이 함수 결과를 매개변수 테스트에 넘기면 끝난다.

```js
const steps = ["migrate", "flush-cache", "restart-workers"];
const orders = permute(steps);
console.log(orders.length, orders[3].join(" → ")); // 6 'flush-cache → restart-workers → migrate'
```

단계가 여덟 개면 40320가지다. 한 번에 10초 걸리는 통합 테스트라면 4일이 넘는다. 이때는 "모든 순서"가 아니라 "서로 영향을 주는 단계 쌍의 앞뒤만" 확인하는 쪽으로 바꾼다. 영향을 주는 쌍이 정해지면, 그 제약을 지키는 순서만 만드는 건 [Course Schedule](/posts/leetcode-course-schedule)의 위상 정렬 문제가 된다. n!이 얼마나 빨리 커지는지 알면 테스트 계획을 세우기 전에 이 판단을 할 수 있다.

## 쓴 것을 표시하고, 바꾼 것은 모두 되돌린다

순열은 자리를 앞에서부터 채우며 자리마다 아직 안 쓴 원소를 하나씩 놓아 보는 탐색이다. 부분집합의 시작 위치 대신 "썼다" 표시가 필요하고, 들어갔다 나올 때 `path`와 `used`를 모두 되돌린다. 답이 n!개라 어떤 풀이든 O(n · n!)이고, 풀이마다 다른 건 추가 메모리와 출력 순서다. 재귀 없이 사전순으로 가려면 다음 순열 규칙을, 추가 배열 없이 가려면 자리 바꾸기를 쓴다.

## 면접에서 나올 만한 질문

### 시간 복잡도가 왜 O(n · n!)인가요?

순열이 n!개이고 각각 길이 n이라 답을 적는 데만 n · n!이 든다. 탐색 나무의 마디는 깊이 k마다 n! / (n - k)!개로 더하면 약 e · n!이고, 마디마다 for문이 n번 돈다. 막다른 갈래가 없어서 탐색 비용도 출력과 같은 차수다.

### Subsets와 Permutations의 코드는 어디가 다른가요?

Subsets는 순서가 상관없어서 시작 위치를 넘겨 뒤쪽 원소만 고른다. Permutations는 앞쪽 원소도 뒷자리에 올 수 있으니 매번 처음부터 훑고, 이미 쓴 원소만 `used`로 건너뛴다. 기록 시점도 다르다. Subsets는 모든 호출에서, Permutations는 길이가 n일 때만 기록한다.

### `used` 배열 없이 풀 수 있나요?

자리 바꾸기 방식이 있다. 배열을 정해진 앞쪽과 남은 뒤쪽으로 나누고, k번째 자리에 남은 원소를 하나씩 바꿔 넣었다가 돌아오면 다시 바꾼다. 추가 공간이 재귀 깊이뿐이다. 다만 출력이 사전순이 아니고, 되돌리는 교환을 빼먹으면 개수는 맞는데 답이 틀린다.

### 재귀 없이 풀 수 있나요?

다음 순열 규칙을 반복한다. 뒤에서 처음으로 `a[i] < a[i+1]`인 곳을 찾고, 뒤쪽에서 `a[i]`보다 큰 가장 오른쪽 수와 바꾼 뒤 뒤쪽을 뒤집는다. 정렬된 배열에서 시작해 이걸 반복하면 사전순으로 모든 순열이 나오고, 상태가 배열 하나라 멈췄다 이어 가기도 쉽다.

### 같은 값이 섞여 있으면 어떻게 바꾸나요?

정렬해서 같은 값을 붙이고, `nums[i] === nums[i-1]`인데 `used[i-1]`이 꺼져 있으면 건너뛴다. 같은 값은 늘 앞의 것부터 쓰게 순서를 강제해서 같은 값끼리 자리를 바꾼 경우를 한 번만 만든다. 결과를 `Set`으로 지우는 방법은 같은 갈래를 이미 다 탐색한 뒤라 느리다.

### k번째 순열 하나만 구하려면요?

전부 만들지 않는다. 첫 자리를 정하면 나머지가 (n-1)!가지이니, 0부터 센 k를 (n-1)!로 나눈 몫으로 첫 자리 원소를 고르고 나머지로 다음 자리를 정한다. 자리마다 반복하면 O(n²)이다.

### n이 커지면 무엇이 먼저 문제가 되나요?

출력 크기다. n = 11이면 약 4천만 개라 모아 두면 메모리가 부족하다. 하나씩 만들어 바로 처리하는 콜백이나 다음 순열 반복으로 바꾼다. 개수만 필요하면 n!을 계산하는데, Java `int`는 13!, `long`은 21!에서 넘치고 JavaScript `number`는 23!부터 정확하지 않다.
