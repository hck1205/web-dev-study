이 시리즈에서 이 글의 자리: [⑩ 용량 어림하기](/posts/sd-capacity-estimation)까지 부품과 숫자를 모았다. 이 글은 그것들을 45분 안에 꺼내 쓰는 순서를 정리한다. 다음 글 [⑫ 요청 수 제한기 설계](/posts/sd-rate-limiter-design)부터 설계 사례가 시작되고, 모든 사례가 이 글의 네 단계를 따른다. 기초 편의 다른 글은 [① 서버 한 대](/posts/sd-start-single-server)부터 [⑨ 지연 시간과 단위 숫자](/posts/sd-latency-numbers)까지다.

설계 면접에서 "블로그 글의 조회수를 세는 기능을 설계해 보세요"라는 문제를 받았다고 하자. 긴장한 지원자는 바로 화이트보드에 상자를 그린다. 클라이언트, API 게이트웨이, Kafka, 스트림 처리기, Cassandra. 아는 이름을 다 동원해서 20분 동안 그린다.

면접관이 묻는다. "조회수가 1 정도 틀려도 되나요? 하루에 몇 번이나 조회되나요?" 지원자는 그 질문을 생각해 본 적이 없다. 알고 보니 면접관이 생각한 건 하루 수만 건짜리 사내 블로그였고, DB 표 하나에 `UPDATE`로 충분한 문제였다. 20분 동안 그린 그림은 답이 아니라 과잉 설계였다.

설계 면접에는 정답이 하나로 정해진 문제가 거의 없다. 같은 "조회수 세기"도 규모와 정확도 요구에 따라 답이 완전히 달라진다. 그래서 면접관은 답 자체보다 답에 이르는 과정을 본다. 이 글은 그 과정을 네 단계로 나눠 같은 조회수 문제에 차례로 적용해 본다.

## 45분을 네 토막으로 나눈다

설계 면접은 보통 45분에서 1시간이다. 흔히 쓰는 진행 순서는 네 단계다. 무엇을 만들지 좁히고, 큰 그림을 그려 동의를 받고, 중요한 부분을 깊이 파고, 마무리한다. 시간 배분은 문제와 면접관에 따라 달라지지만 45분이면 대략 이렇게 잡는다.

## 첫 토막: 무엇을 만들지 좁힌다

문제는 일부러 모호하게 주어진다. 실제 업무에서도 요구 사항은 늘 모호하게 오고, 그걸 좁히는 능력을 보려는 것이다. 질문은 크게 세 가지를 묻는다. 무엇을 하는가(기능), 얼마나 큰가(규모), 무엇을 포기해도 되는가(품질)다.

네 번째 질문의 답이 특히 중요하다. "조금 틀려도 된다"는 답 하나가 나중에 고를 수 있는 선택지를 크게 넓힌다. 광고 과금처럼 한 건도 틀리면 안 되는 문제였다면 같은 조회수라도 훨씬 무거운 설계가 필요하다.

질문만 계속하는 것도 좋지 않다. 5~10분 안에 핵심 서너 개를 묻고, 답이 없는 것은 내가 정해서 "이렇게 가정하겠습니다"라고 말한다. 숫자는 [⑩ 용량 어림하기](/posts/sd-capacity-estimation)의 방식으로 바로 어림해 적는다. 하루 8천만 조회를 86,400초로 나누면 평균 926, 피크를 3배로 잡으면 약 2,800이다.

## 둘째 토막: 상자 몇 개로 끝까지 그린다

다음은 큰 그림이다. 처음부터 완벽한 구조를 그리려 하지 말고, 가장 단순한 구조로 요청 하나가 처음부터 끝까지 가는 길을 그린다. 이때 API도 정한다.

```text
POST /posts/{postId}/views     조회 한 번을 기록한다 (글을 열 때 앱이 보낸다)
GET  /posts/{postId}           글과 함께 조회수를 돌려준다
```

가장 단순한 구조는 글 표에 `views` 열을 두고 조회마다 1을 더하는 것이다. 그리고 그림을 따라가며 어림한 숫자를 대 본다. 아래 그림의 마지막 단계가 이 구조의 문제다.

## 셋째 토막: 숫자가 가리키는 곳을 판다

깊이 들어갈 곳은 어림한 숫자가 정한다. 조회수 문제에서는 "같은 행에 쓰기가 몰린다"가 그곳이다. 이 말이 실제로 얼마나 큰 문제인지 PostgreSQL 16에서 쟀다. 글 10만 개짜리 표를 만들고, 연결 20개가 5초 동안 쉬지 않고 조회수를 올리게 했다. 한 번은 모두 1번 글만, 한 번은 10만 개 글에 무작위로 퍼뜨렸다.

```sql
-- 글 10만 개, 조회수 0으로 시작
CREATE TABLE posts (id bigint PRIMARY KEY, views bigint NOT NULL DEFAULT 0);
INSERT INTO posts SELECT g FROM generate_series(1, 100000) g;
```

```bash
# hot.sql: 모두 같은 글  ->  UPDATE posts SET views = views + 1 WHERE id = 1;
# spread.sql: 무작위 글  ->  \set pid random(1, 100000) 후 WHERE id = :pid
sudo -u postgres pgbench -n -f hot.sql -c 20 -j 4 -T 5 f3_views
sudo -u postgres pgbench -n -f spread.sql -c 20 -j 4 -T 5 f3_views
```

```text
latency average = 27.993 ms
tps = 714.462189 (without initial connection time)
latency average = 2.561 ms
tps = 7810.511194 (without initial connection time)
```

같은 DB, 같은 연결 수인데 한 행에 몰리면 초당 714번, 퍼지면 초당 7,810번이다. 한 번 더 돌렸을 때는 1,560번과 7,303번이 나왔다. 어느 쪽이든 열 배 가까운 차이다. 평균 응답 시간도 2.6ms에서 28ms로 늘었다. 같은 행을 고치려는 트랜잭션은 앞 트랜잭션이 커밋할 때까지 행 잠금을 기다려야 해서, 연결이 아무리 많아도 사실상 한 줄로 선다.

이제 대안을 비교한다. 이 비교가 깊이 토막의 핵심이다.

첫째, 메모리 카운터에 모았다가 몰아서 쓴다. 조회마다 Redis의 `INCR`로 1을 더하고, 작업자가 몇 초마다 쌓인 값을 꺼내 DB에 한 번에 더한다. Redis는 명령을 하나씩 순서대로 처리하지만 메모리에서 끝나니 빠르다. 같은 서버에서 연결 20개로 `INCR`을 보내면 이렇게 나온다.

```bash
# 연결 20개로 INCR 20만 번
redis-benchmark -p 16391 -t incr -n 200000 -c 20 -q
```

```text
INCR: 73909.83 requests per second, p50=0.159 msec
```

한 키에 초당 7만 번 넘게 더한다. DB에는 몇 초마다 글 하나당 `UPDATE` 한 번만 가니, 인기 글 하나에 조회가 아무리 몰려도 그 행이 받는 쓰기는 초당 1번 이하가 된다. 대가는 Redis가 죽으면 아직 DB로 옮기지 않은 몇 초 치 조회를 잃는다는 것이다. 첫 토막에서 "조금 틀려도 된다"는 답을 받아 두었기 때문에 이 대가를 받아들일 수 있다.

둘째, 카운터를 여러 행으로 쪼갠다. 1번 글의 조회수를 행 10개에 나눠 무작위로 하나를 골라 더하고, 읽을 때는 10개를 합친다. Redis 없이 DB만으로 풀지만 읽기가 무거워진다.

셋째, 조회 기록을 로그나 큐에 쌓고 나중에 집계한다. 가장 정확하고 다른 통계에도 쓸 수 있지만, 표시용 숫자 하나에는 무거운 구조다. 광고 클릭처럼 정확도가 중요하면 이쪽을 고른다.

조회수 문제라면 첫째를 고르고, 그 이유를 첫 토막에서 받은 답과 연결해 말한다. 중복 제거도 같은 Redis로 한다. 사용자와 글 조합의 키를 10분 수명으로 두고, 키가 없을 때만 센다.

```bash
# dedupe.txt에 적은 명령을 차례로 보낸다
# SET seen:u42:p7 1 NX EX 600   (두 번)  ->  사용자 u42가 7번 글을 처음 볼 때만 기록, 10분 수명
# TTL seen:u42:p7                       ->  남은 수명
# INCR views:p7                 (세 번)  ->  조회수 카운터
# GETDEL views:p7                       ->  작업자가 꺼내면서 지운다
# GET views:p7                          ->  지워졌는지 확인
redis-cli -p 16391 < dedupe.txt
```

```text
OK
(nil)
(integer) 600
(integer) 1
(integer) 2
(integer) 3
"3"
(nil)
```

첫 줄과 둘째 줄이 두 번의 `SET ... NX`다. 키가 없을 때만 저장하고 `OK`를 돌려주니, 두 번째는 이미 있어서 `(nil)`이다. 이 결과로 셀지 말지를 정한다. 작업자는 `GETDEL`(Redis 6.2부터)로 쌓인 값을 꺼내면서 지우고, 꺼낸 3을 DB에 더한다. 꺼내기와 지우기가 명령 하나라서 그 사이에 들어온 조회가 사라지지 않는다.

## 마지막 토막: 약점을 먼저 말한다

남은 5분에는 면접관이 묻기 전에 내 설계의 약점을 꺼낸다. 완벽한 설계는 없고, 약점을 알고 있다는 것 자체가 평가 대상이다. 보통 세 가지를 말한다.

무엇이 죽으면 어떻게 되나. Redis가 죽으면 몇 초 치 조회를 잃고, 그동안은 DB에 직접 쓰거나 조회 기록을 버리도록 정할 수 있다. 작업자가 죽으면 Redis에 숫자가 쌓이기만 하고 DB가 늦어지니, 꺼낸 값과 DB 반영 사이에 실패하면 다시 더하지 않도록 처리를 남긴다.

10배가 되면 어디가 먼저 막히나. 조회가 초당 2만 8천 번이 되면 Redis 한 대가 여전히 받을 수 있지만 여유가 줄어드니, 글 id로 나눠 여러 대에 둔다. 작업자도 글 id 범위로 나눠 여러 대 띄운다.

무엇을 지켜봐야 하나. Redis에 쌓여 있는 값의 총합, 작업자가 마지막으로 성공한 시각, 행 잠금 대기 시간을 지표로 둔다. 작업자가 멈추면 첫 지표가 계속 늘어나니 바로 보인다.

그래서 자주 하는 실수도 이 능력들의 반대편에 있다.

- 질문 없이 바로 그린다. 처음 장면의 Kafka 그림이 그렇다. 규모를 모르면 어떤 부품이 필요한지 정할 수 없다.
- 기술 이름을 이유 없이 꺼낸다. "Cassandra를 씁니다"보다 "쓰기가 초당 수만 건이고 한 키로만 읽으니 쓰기에 강한 저장소가 맞습니다"가 낫다. 이름은 틀려도 되지만 이유가 없으면 판단을 보여 줄 수 없다.
- 말없이 오래 그린다. 면접관은 생각을 들을 수 없으면 평가할 수 없다. 그리면서 무엇을 왜 그리는지 말한다.
- 면접관의 힌트를 흘려 듣는다. "인기 글이 생기면요?" 같은 질문은 그쪽을 파 보라는 신호다.
- 모든 곳을 조금씩 판다. 시간이 한정돼 있으니 숫자가 가리키는 한두 곳을 깊이 판다.
- 처음부터 최대 규모로 설계한다. 하루 수만 건짜리 문제에 분산 스트림 처리를 그리면 비용과 복잡도를 판단하지 못한다는 인상을 준다.

## 혼자 연습하는 법

이 시리즈의 사례 글들은 모두 이 네 토막 순서로 쓰여 있다. 글을 읽기 전에 제목만 보고 15분 동안 혼자 범위 질문과 숫자를 적어 본 뒤 글과 비교하면 연습이 된다. 소리 내어 말하면서 그리는 연습도 따로 해 둔다. 머릿속으로는 다 아는 것 같아도 말로 하면 막히는 곳이 드러난다.

숫자 연습은 아래 함수로 해 볼 수 있다. 조회수 문제의 피크 조회 수와, 가장 인기 있는 글 하나가 받는 초당 쓰기, 그리고 그 값이 행 하나가 받을 수 있는 한도를 넘는지를 돌려준다. 한도는 위에서 잰 714를 쓴다. 초당 값은 반올림한다.

<CodePlayground
  caption="인기 글 하나가 받는 쓰기는 얼마인가"
  functionName="hotRow"
  initialCode={`function hotRow(dau, viewsPerUser, peakFactor, hotShare, rowLimit) {
  // hotShare: 피크 조회 중 가장 인기 있는 글 하나의 몫 (0~1)
  return { peakViews: 0, hotRowWrites: 0, needsBatching: false };
}`}
  solution={`function hotRow(dau, viewsPerUser, peakFactor, hotShare, rowLimit) {
  const peakViews = Math.round((dau * viewsPerUser) / 86400 * peakFactor);
  const hotRowWrites = Math.round(peakViews * hotShare);
  return { peakViews, hotRowWrites, needsBatching: hotRowWrites > rowLimit };
}`}

    { label: "사용자 10배, 몫 5%", args: [40000000, 20, 3, 0.05, 714], expected: { peakViews: 27778, hotRowWrites: 1389, needsBatching: true } },
    { label: "사내 블로그 규모", args: [5000, 5, 3, 0.5, 714], expected: { peakViews: 1, hotRowWrites: 1, needsBatching: false } },

마지막 줄이 처음 장면의 답이다. 사내 블로그라면 인기 글 하나에 몰려도 초당 1번이라 `UPDATE` 한 줄이면 된다. 둘째와 셋째 줄처럼 행 하나의 한도를 넘는 경우에만 Redis와 작업자를 붙일 이유가 생긴다. 같은 문제라도 첫 토막의 답이 설계를 정한다.

## 면접에서 나올 만한 질문

### 설계 문제를 받으면 가장 먼저 무엇을 하나요?

바로 그리지 않고 질문으로 범위를 좁힌다. 어떤 기능이 핵심인지, 사용자와 요청이 얼마나 되는지, 정확도나 지연에서 무엇을 포기해도 되는지를 묻는다. 답이 없으면 내가 가정을 정해 말하고 칠판에 적어 둔 뒤, 그 숫자로 초당 요청 수와 저장 공간을 어림한다.

### 요구 사항을 물었는데 면접관이 "알아서 정하세요"라고 하면요?

합리적인 가정을 정하고 이유를 함께 말한다. "표시용 조회수라 몇 초 늦어도 되고 장애 때 조금 잃어도 된다고 가정하겠습니다"처럼 말하면, 그 가정이 이후의 선택을 어떻게 바꾸는지 보여 줄 수 있다. 가정이 바뀌면 설계의 어느 부분이 바뀌는지도 마지막에 짚는다.

### 큰 그림은 얼마나 자세하게 그려야 하나요?

요청 하나가 처음부터 끝까지 가는 길이 보일 정도면 된다. 클라이언트, 로드 밸런서, 서버, 저장소 같은 상자 몇 개와 핵심 API 두세 개, 그리고 각 상자가 받는 초당 요청 수를 적는다. 세부 구현은 동의를 받은 뒤 깊이 토막에서 한두 곳만 판다.

### 깊이 들어갈 부분은 어떻게 고르나요?

어림한 숫자가 가리키는 병목을 고른다. 조회수 문제라면 인기 글 하나에 쓰기가 몰리는 행 잠금이 그곳이다. 면접관이 특정 부분을 묻는다면 그쪽이 우선이다. 고른 곳에서는 대안을 두세 개 비교하고, 첫 토막에서 받은 요구 사항과 연결해 하나를 고른 이유를 말한다.

### "트래픽이 10배가 되면 어떻게 하나요?"라는 질문에는 어떻게 답하나요?

숫자를 다시 계산해서 어디가 먼저 한도를 넘는지 말한다. 조회수 예시라면 피크가 초당 2만 8천 번이 되어 인기 글의 행 쓰기가 한도를 넘으니 메모리 카운터와 몰아 쓰기가 필요해지고, 그다음은 Redis를 키 범위로 나누는 일이다. 모든 부분을 열 배로 늘리는 게 아니라 한도를 넘는 곳부터 바꾼다.

### "이 부품이 죽으면 어떻게 되나요?"라는 질문에는요?

그 부품이 죽었을 때 잃는 것과 사용자에게 보이는 증상, 대응을 순서대로 말한다. Redis가 죽으면 아직 DB로 옮기지 않은 몇 초 치 조회를 잃고, 표시용이라 받아들일 수 있다고 첫 토막에서 확인했다고 말한다. 잃으면 안 되는 데이터였다면 큐에 기록을 남기는 구조로 바꿔야 한다는 것도 덧붙인다.

### 설계 면접에서 가장 흔한 실수는 무엇인가요?

요구 사항을 묻지 않고 바로 큰 시스템을 그리는 것이다. 규모를 모르면 부품을 고를 근거가 없어서, 작은 문제에 분산 스트림 처리 같은 과잉 설계를 하거나 반대로 큰 문제를 단순하게 넘긴다. 말없이 오래 그리는 것과 기술 이름을 이유 없이 꺼내는 것도 판단 과정을 보여 주지 못한다는 점에서 같은 실수다.
