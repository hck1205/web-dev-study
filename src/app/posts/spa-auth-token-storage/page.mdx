대시보드를 열어 둔 채 점심을 먹고 돌아왔다. 아무 탭이나 눌렀더니 로그인 화면으로 튕긴다. 로그를 보면 대시보드가 띄워 둔 위젯 다섯 개가 동시에 API를 불렀고, 액세스 토큰이 만료돼 다섯 개 모두 401을 받았다. 응답 인터셉터는 401마다 토큰을 새로 받으려고 리프레시 요청을 보냈다. 그 다섯 번의 리프레시 중 하나만 성공하고 나머지는 실패했는데, 서버는 그걸 탈취 신호로 보고 그 사용자의 모든 토큰을 끊었다.

이 장면에는 SPA 인증의 질문이 거의 다 들어 있다. 토큰을 어디에 두나, 리프레시 토큰은 왜 한 번만 쓰게 하나, 동시에 터지는 401은 어떻게 하나, 탭이 여러 개면 어떻게 되나. JWT 구조와 리프레시 토큰의 기본 개념은 [토큰으로 로그인하기](/posts/token-login)에, 쿠키와 세션은 [쿠키와 세션](/posts/cookie-session-login)에, OAuth로 토큰을 받는 과정과 PKCE는 [OAuth 2.0](/posts/oauth)에 있다. 여기서는 토큰을 받은 다음, 브라우저에서 들고 다니는 문제를 본다.

## 토큰을 둘 수 있는 세 자리

브라우저에서 토큰을 들고 있을 수 있는 곳은 크게 셋이다.

`localStorage`는 가장 쉽다. 새로고침해도, 브라우저를 껐다 켜도 남고, 탭끼리 공유된다. 대신 같은 출처에서 도는 모든 자바스크립트가 `localStorage.getItem("token")` 한 줄로 읽는다. 페이지에 XSS가 하나라도 생기면, 또는 내가 부른 서드파티 스크립트 하나가 나쁜 마음을 먹으면, 토큰이 공격자 서버로 간다. 공격자는 그 토큰으로 자기 컴퓨터에서 만료될 때까지 API를 부른다. `sessionStorage`도 읽히는 건 같다. XSS가 저장소에서 무엇을 가져가는지는 [브라우저 저장소](/posts/browser-storage)에서 실제로 돌려 봤다.

메모리, 즉 자바스크립트 변수(모듈 스코프 변수, 클로저, 상태 관리 스토어)에 두면 `localStorage`를 뒤지는 스크립트에는 안 걸린다. 대신 새로고침하면 사라진다. 탭마다 따로라서 새 탭을 열 때도 다시 받아야 한다.

`HttpOnly` 쿠키는 자바스크립트가 아예 못 읽는다. 서버가 `rt=abc; HttpOnly`와 `theme=dark` 쿠키를 함께 내려 준 페이지에서 `document.cookie`를 찍어 봤다.

```text
document.cookie: theme=dark
```

`rt`는 보이지 않는다. 브라우저는 이 쿠키를 저장하고 요청에 붙이기만 할 뿐 페이지 스크립트에 넘기지 않는다. 그 대신 쿠키는 요청에 자동으로 붙어서, 다른 사이트에서 위조한 요청에도 붙을 수 있다. `SameSite`와 CSRF 대비가 따라와야 한다([CSRF](/posts/csrf)). 그리고 쿠키는 그 도메인으로 가는 요청에만 붙으니, API가 다른 사이트에 있으면 아래에서 볼 서드파티 쿠키 문제를 만난다.

| 자리 | XSS가 훔쳐 갈 수 있나 | 새로고침 | 다른 탭 | 따라오는 일 |
|---|---|---|---|---|
| `localStorage` | 그렇다 | 남는다 | 공유 | 없음 |
| 메모리 | 어렵다 | 사라진다 | 따로 | 다시 받는 흐름 |
| `HttpOnly` 쿠키 | 아니다 | 남는다 | 공유 | CSRF 대비, 같은 사이트 배치 |

## XSS가 나면 어디에 두든 진다

표를 보고 "`HttpOnly` 쿠키에 두면 XSS에 안전하다"고 정리하면 반만 맞다. `HttpOnly`가 막는 건 토큰을 훔쳐 가는 것이다. 페이지 안에서 도는 공격자 스크립트는 토큰을 몰라도 `fetch("/api/transfer", { method: "POST", credentials: "include" })`를 부를 수 있고, 브라우저는 쿠키를 붙여 준다. 메모리에 둔 토큰도 마찬가지다. 공격자 스크립트가 내 API 클라이언트 함수를 그대로 부르면, 클라이언트가 알아서 토큰을 붙여 준다.

차이는 피해의 범위다. 훔쳐 간 토큰은 공격자가 자기 기계에서, 사용자가 탭을 닫은 뒤에도, 토큰이 만료될 때까지 쓴다. 훔치지 못하면 공격은 사용자가 그 페이지를 열어 둔 동안, 그 브라우저 안에서만 일어난다. 그래서 토큰 저장 위치는 XSS를 막는 장치가 아니라 XSS가 났을 때 피해를 줄이는 장치다. XSS 자체는 출력 인코딩과 CSP로 막아야 하고, 그 이야기는 [XSS](/posts/xss)에 있다.

이 관점에서 흔히 쓰는 조합이 나온다. 액세스 토큰은 수명을 짧게(5~15분) 해서 메모리에 두고, 리프레시 토큰은 `HttpOnly` 쿠키에 둔다. 액세스 토큰이 새어도 금방 만료되고, 리프레시 토큰은 스크립트가 못 읽는다. 새로고침으로 메모리가 비면 쿠키로 액세스 토큰을 다시 받는다.

## 리프레시 토큰은 한 번 쓰면 버린다

리프레시 토큰은 수명이 길어서 새면 피해가 크다. 그래서 요즘은 리프레시할 때마다 새 리프레시 토큰을 함께 내주고, 방금 쓴 것은 무효로 만든다. 리프레시 토큰 회전(rotation)이다.

회전에는 재사용 감지가 붙는다. 이미 쓰고 버린 리프레시 토큰이 다시 들어오면 서버는 두 사람이 같은 토큰을 가지고 있다고 본다. 진짜 사용자와 훔쳐 간 공격자 중 누가 먼저 썼는지는 모른다. 그래서 그 토큰에서 이어진 가족(family) 전체를 무효로 만들고 다시 로그인하게 한다. 공격자가 훔친 토큰을 먼저 써서 새 토큰을 받았더라도, 진짜 사용자가 옛 토큰을 쓰는 순간 공격자의 새 토큰까지 끊긴다. OAuth 보안 권고(Security BCP)도 브라우저 같은 공개 클라이언트에는 회전이나 송신자 제한을 쓰라고 한다.

이 장치가 처음 장면을 만들었다. 다섯 요청이 같은 리프레시 토큰을 들고 리프레시를 다섯 번 보내면, 첫 번째는 성공하고 나머지 넷은 "이미 쓴 토큰"이 된다. 서버 입장에서는 탈취와 구별할 수 없다.

## 동시에 터지는 401을 하나로 묶는다

실제로 재현해 봤다. 서버는 리프레시 토큰을 한 번 쓰면 버리고, 버린 것이 다시 오면 가족 전체를 끊는다. 클라이언트는 axios 1.20의 응답 인터셉터로 401을 받으면 리프레시하고 원래 요청을 다시 보낸다. 액세스 토큰이 만료된 상태에서 요청 다섯 개를 동시에 보냈다.

```text
naive {
  refreshCalls: 5,
  revoked: true,
  ok: 0,
  failed: [
    '401 /api/item/1',
    '401 http://localhost:18300/auth/refresh',
    '401 http://localhost:18300/auth/refresh',
    '401 http://localhost:18300/auth/refresh',
    '401 http://localhost:18300/auth/refresh'
  ]
}
```

리프레시가 다섯 번 나갔고, 가족이 끊겨(`revoked: true`) 다섯 요청이 모두 실패했다. 첫 리프레시는 성공했지만 그 새 토큰마저 뒤따른 재사용 때문에 무효가 됐다. 처음 장면 그대로다.

인터셉터 코드는 이렇다. 핵심은 진행 중인 리프레시 Promise를 담는 변수 하나다.

```ts
import axios, { AxiosError, InternalAxiosRequestConfig } from "axios";

let accessToken: string | null = null;           // 메모리에만 둔다
let refreshing: Promise<string> | null = null;   // 진행 중인 리프레시

const api = axios.create({ baseURL: "/api" });

api.interceptors.request.use((config) => {
  if (accessToken) config.headers.Authorization = `Bearer ${accessToken}`;
  return config;
});

async function refresh(): Promise<string> {
  // 리프레시 요청은 인터셉터가 없는 별도 인스턴스로 보낸다. 같은 api로 보내면 401에서 또 리프레시를 부른다
  const { data } = await axios.post<{ access: string }>("/auth/refresh", null, { withCredentials: true });
  accessToken = data.access;
  return data.access;
}

api.interceptors.response.use(undefined, async (error: AxiosError) => {
  const original = error.config as InternalAxiosRequestConfig & { _retry?: boolean };
  if (error.response?.status !== 401 || original._retry) throw error; // 다시 보낸 요청의 401은 끝
  original._retry = true;

  refreshing ??= refresh().finally(() => { refreshing = null; }); // 없을 때만 새로 시작
  try {
    await refreshing;
  } catch {
    accessToken = null;
    redirectToLogin();
    throw error;
  }
  return api(original); // 요청 인터셉터가 새 토큰을 붙인다
});
```

같은 다섯 요청을 이 방식으로 다시 보냈다.

```text
single-flight { refreshCalls: 1, revoked: false, ok: 5, failed: [] }
```

리프레시는 한 번, 다섯 요청 모두 성공했다. 놓치기 쉬운 점이 셋 있다. 리프레시 요청을 인터셉터가 걸린 `api`로 보내면, 리프레시가 401일 때 다시 리프레시를 부르는 무한 반복이 생긴다. `_retry` 표시가 없으면 새 토큰으로도 401이 나는 경우(권한이 없는 API, 서버 시계 문제)에 계속 돈다. `finally`에서 변수를 비우지 않으면 다음 만료 때 이미 끝난 옛 Promise를 기다려 옛 토큰으로 다시 보낸다.

## 탭이 여러 개면 리프레시도 다툰다

인터셉터의 변수는 탭마다 따로다. 탭 두 개가 동시에 만료되면 각자 리프레시를 보낸다. 리프레시 토큰은 쿠키라 두 탭이 같은 토큰을 쓰니, 탭 안에서 묶은 것이 소용없다. 두 탭에서 동시에 리프레시를 불렀다.

```text
no lock   [ 200, 401 ] [ 'refresh rt-1 -> rt-2', 'refresh rt-1 -> 401 (reuse)' ]
with lock [ 200, 200 ] [ 'refresh rt-1 -> rt-2', 'refresh rt-2 -> rt-3' ]
```

아무 장치가 없으면 두 탭이 모두 `rt-1`을 들고 가서 하나가 재사용으로 걸렸다. 두 번째 줄은 Web Locks API로 리프레시를 탭 사이에서 한 줄로 세운 결과다.

```ts
async function refresh(): Promise<string> {
  return navigator.locks.request("auth-refresh", async () => {
    // 잠금을 기다리는 동안 다른 탭이 이미 회전했다면, 쿠키도 이미 새것으로 바뀌어 있다
    const { data } = await axios.post<{ access: string }>("/auth/refresh", null, { withCredentials: true });
    accessToken = data.access;
    return data.access;
  });
}
```

`navigator.locks.request`는 같은 출처의 모든 탭과 워커에서 같은 이름의 잠금을 한 번에 하나만 잡게 한다. 두 번째 탭은 첫 탭이 끝날 때까지 기다린다. 그동안 첫 탭의 응답이 쿠키를 `rt-2`로 바꿔 두었으므로, 두 번째 탭은 `rt-2`로 리프레시해서 둘 다 성공했다. 리프레시 토큰을 쿠키에 둔 덕분에 탭 사이에 토큰을 따로 나눠 줄 필요가 없다. Web Locks는 주요 브라우저가 모두 지원하지만, 오래된 브라우저까지 받아야 하면 없을 때는 잠금 없이 부르고 서버의 유예 시간에 기댄다.

### 한 탭에서 로그아웃하면 다른 탭도

탭 A에서 로그아웃했는데 탭 B는 메모리에 액세스 토큰을 들고 계속 화면을 보여 주면 안 된다. 같은 출처의 탭끼리 알리는 방법은 `BroadcastChannel`과 `storage` 이벤트다. 탭 A에서 둘 다 보내 보고 양쪽에서 받은 것을 적었다.

```ts
const auth = new BroadcastChannel("auth");
auth.onmessage = (e) => { if (e.data.type === "logout") { accessToken = null; redirectToLogin(); } };

function logout() {
  auth.postMessage({ type: "logout" });                       // 다른 탭(과 이 탭의 다른 채널 객체)에 알린다
  localStorage.setItem("logout-at", String(Date.now()));      // storage 이벤트로 알리는 예전 방식
}
```

```text
tab B: [ 'bc:{"type":"logout"}', 'storage:logout-at=1729650000000' ]
tab A: [ 'bc:{"type":"logout"}' ]
```

탭 B는 두 가지를 모두 받았다. 탭 A에서는 `storage` 이벤트가 오지 않았다. 바꾼 탭 자신에게는 발생하지 않기 때문이다. `BroadcastChannel`은 보낸 객체만 빼고 같은 이름의 채널 객체에 모두 전달해서, 이 실험처럼 같은 탭 안의 다른 채널 객체도 받는다. 로그아웃 처리를 두 번 하지 않게 만들어 둔다. 탭 사이 통신의 다른 쓰임은 [분산 시스템으로서의 프런트엔드](/posts/frontend-as-distributed-system)에 있다. 그리고 탭에 알리는 것과 별개로, 로그아웃은 서버에서 리프레시 토큰 가족을 무효로 만들고 쿠키를 지워야 끝난다. 화면만 로그인 페이지로 보내면 쿠키가 남아 있어 새로고침 한 번에 다시 로그인된다.

## 브라우저에 토큰을 아예 두지 않는 방법

여기까지 읽으면 질문이 생긴다. 토큰을 브라우저에 두는 게 이렇게 번거로우면, 아예 안 두면 안 되나. 그 답이 BFF(Backend for Frontend) 패턴이다. 내 프런트엔드와 같은 사이트에 작은 서버를 두고, OAuth 토큰은 그 서버가 들고 있는다. 브라우저에는 그 서버의 세션 쿠키만 준다.

로그인하면 BFF가 OAuth 인가 코드 흐름을 기밀 클라이언트(client secret을 가진 서버)로 처리하고, 받은 액세스 토큰과 리프레시 토큰을 세션 저장소에 둔다. 브라우저가 `/api/orders`를 부르면 BFF가 세션을 보고 토큰을 붙여 실제 API로 넘긴다. 만료되면 BFF가 리프레시한다. 앞에서 본 동시 401과 탭 다툼도 서버 한 곳에서 처리된다. 브라우저 쪽 코드는 쿠키 세션과 똑같아진다.

얻는 것은 토큰이 자바스크립트에 전혀 없다는 점이다. XSS가 나도 훔쳐 갈 토큰이 없다. 브라우저 앱을 위한 OAuth 권고 초안(OAuth 2.0 for Browser-Based Applications)도 보안 수준이 가장 높은 구조로 BFF를 든다. 잃는 것도 있다. 서버를 하나 더 운영해야 하고, 세션 저장소가 필요해 상태가 생긴다. 모든 API 요청이 BFF를 한 번 더 거치니 지연이 조금 늘고, 쿠키 기반이라 CSRF 대비가 다시 필요하다. Next.js처럼 이미 서버가 있는 프레임워크라면 그 서버가 BFF 역할을 맡기 쉽다. 게이트웨이 계층에서 BFF를 나누는 이야기는 [게이트웨이](/posts/gateway)에, 쿠키 세션 자체는 [쿠키와 세션](/posts/cookie-session-login)에 있다.

BFF 없이 브라우저가 직접 OAuth 토큰을 받는 순수 SPA라면, 인가 코드 흐름에 PKCE를 붙이는 것이 기본이다. 예전의 암묵적 흐름(implicit flow)처럼 토큰을 주소 해시로 받는 방식은 쓰지 않는다. 그 과정은 [OAuth 2.0](/posts/oauth)에서 한 단계씩 따라간다.

## 서드파티 쿠키 제한이 로그인을 깨는 자리

`HttpOnly` 쿠키 전략은 쿠키가 "같은 사이트" 요청에 붙는다는 전제 위에 있다. 프런트엔드가 `app.example.com`이고 API가 `api.example.com`이면 둘은 같은 사이트라 문제없다. 그런데 프런트엔드가 `myapp.vercel.app`이고 API가 `api.mycompany.com`이면 다른 사이트다. 이때 API가 심은 리프레시 토큰 쿠키는 내 페이지 입장에서 서드파티 쿠키가 된다. `SameSite=None; Secure`로 열어 줘야 보내지고, 그것도 브라우저가 서드파티 쿠키를 막으면 끝이다.

브라우저마다 상황이 다르다. 사파리는 기본으로 서드파티 쿠키를 막는다. 파이어폭스는 기본 설정에서 서드파티 쿠키를 최상위 사이트별로 나눠 담는다. 크롬은 서드파티 쿠키를 없애겠다던 계획을 2024~2025년에 거둬들여 기본으로는 허용하지만, 시크릿 창과 사용자 설정에서는 막힌다. "크롬에서는 되는데 아이폰에서는 로그인이 바로 풀린다"는 증상이 대개 여기서 나온다. 저장소가 최상위 사이트별로 나뉘는 비슷한 이야기는 [브라우저 보안 모델](/posts/browser-security-model)에 있다.

예전에 많이 쓰던 숨은 iframe으로 인가 서버에 `prompt=none`을 보내 토큰을 조용히 갱신하는 방식(silent refresh)도 같은 이유로 깨진다. 숨은 iframe 안의 인가 서버는 서드파티라서 로그인 쿠키를 못 받는다.

해결은 대개 배치를 바꾸는 쪽이다. API를 프런트와 같은 사이트의 서브도메인으로 옮기거나(`api.myapp.com`), 프런트를 서빙하는 서버가 `/api` 경로를 실제 API로 넘기는 프록시를 둔다. 그러면 쿠키가 같은 사이트, 많은 경우 같은 출처 쿠키가 되어 제한과 상관없어지고 CORS도 필요 없어진다. 앞의 BFF가 이 일을 같이 한다. 다른 사이트에 iframe으로 박히는 위젯처럼 정말 서드파티여야 하는 경우에는 `Partitioned` 속성(CHIPS)으로 최상위 사이트별로 나뉜 쿠키를 쓰는 길이 있다.

## 현장에서 자주 보는 실수

로그 한 줄에서 시작하는 경우가 많다. 에러 추적 도구에 요청 헤더를 통째로 실어 보내면 `Authorization: Bearer ...`가 그대로 남는다. 프런트엔드 에러 수집기의 breadcrumb, 네트워크 로그 설정에서 인증 헤더와 쿠키를 지우게 해 둔다.

토큰을 주소에 싣는 것도 흔하다. 이메일 링크나 리다이렉트에서 `?token=...`으로 넘기면 브라우저 방문 기록, 서버 접근 로그, 외부 링크를 누를 때의 `Referer`로 샌다. 주소로 받아야 한다면 짧은 일회용 코드로 받아 바로 교환하고, `history.replaceState`로 주소에서 지운다. `Referer` 쪽 이야기는 [웹 보안 헤더](/posts/web-security-headers)에 있다.

액세스 토큰 수명을 하루, 일주일로 늘려 리프레시를 피하는 경우도 있다. 리프레시 구현이 귀찮아서다. 그러면 탈취된 토큰이 그만큼 오래 살고, JWT는 서버가 따로 막는 목록이 없으면 중간에 되돌릴 방법도 없다. 짧은 액세스 토큰과 리프레시는 한 세트다.

로그아웃을 화면에서만 하는 실수는 앞에서 봤다. 서버에서 리프레시 토큰을 무효로 만들고, 쿠키를 `Max-Age=0`으로 지우고, 메모리의 액세스 토큰을 비우고, 다른 탭에 알린다. 그리고 데이터 캐시(TanStack Query 같은 것)도 비운다. 다음 사용자가 같은 기기에서 로그인하면 앞 사람의 데이터가 잠깐 보이는 일이 여기서 생긴다.

마지막으로, 리프레시 주소를 CSRF에서 빼먹는다. 리프레시 주소는 상태를 바꾸는 요청이다. 쿠키가 붙어서 새 토큰을 내준다. `SameSite=Strict`를 걸고, 응답 본문으로 액세스 토큰을 돌려준다면 다른 출처가 그 응답을 읽지 못하게 CORS를 좁혀 둔다. 커스텀 헤더(`X-Requested-With` 같은 것)를 요구하면 단순 폼 제출로는 보낼 수 없어 한 겹이 더 생긴다.

## 면접에서 나올 만한 질문

### SPA에서 액세스 토큰은 어디에 저장하나요?

흔한 답은 액세스 토큰은 짧은 수명으로 메모리에, 리프레시 토큰은 `HttpOnly; Secure; SameSite` 쿠키에 두는 것이다. `localStorage`는 같은 출처 스크립트가 모두 읽어서 XSS 한 번에 토큰이 밖으로 나간다. 메모리는 새로고침 때 사라지니 앱이 시작할 때 리프레시 쿠키로 다시 받는다. 가능하면 BFF로 토큰을 브라우저에 아예 두지 않는 쪽이 가장 안전하다.

### HttpOnly 쿠키에 두면 XSS에 안전한가요?

토큰을 훔쳐 가는 것은 막지만, XSS 자체를 막지는 않는다. 페이지 안의 공격자 스크립트는 토큰을 몰라도 `credentials: "include"`로 요청을 보낼 수 있고 브라우저가 쿠키를 붙여 준다. 차이는 공격이 사용자가 페이지를 연 동안 그 브라우저 안으로 제한된다는 점이다. 그래서 저장 위치는 피해를 줄이는 장치고, XSS는 출력 인코딩과 CSP로 따로 막는다.

### 리프레시 토큰 회전은 왜 하나요?

리프레시 토큰은 수명이 길어 새면 피해가 크기 때문에, 쓸 때마다 새것으로 바꾸고 옛것은 무효로 만든다. 여기에 재사용 감지를 붙여 버린 토큰이 다시 오면 그 가족 전체를 끊는다. 공격자가 훔친 토큰을 먼저 썼더라도, 진짜 사용자가 옛 토큰을 쓰는 순간 탈취가 드러나고 공격자의 토큰도 같이 무효가 된다. 대신 정상 클라이언트가 같은 토큰을 두 번 보내도 탈취로 보이므로 동시 리프레시를 막아야 한다.

### 여러 요청이 동시에 401을 받으면 어떻게 처리하나요?

첫 401만 리프레시를 시작하고, 그 Promise를 변수에 담아 나머지 요청은 같은 Promise를 기다리게 한다. 리프레시가 끝나면 기다리던 요청을 새 토큰으로 한 번씩 다시 보내고, 다시 보낸 요청이 또 401이면 로그아웃한다. 리프레시 요청은 인터셉터가 없는 별도 인스턴스로 보내 무한 반복을 막고, `finally`에서 변수를 비운다. 회전을 쓰는 서버에서 이걸 안 하면 재사용 감지에 걸려 사용자가 로그아웃된다.

### 탭이 여러 개일 때는 무엇을 더 해야 하나요?

리프레시와 로그아웃 두 가지를 탭 사이에서 맞춘다. 리프레시는 Web Locks API로 같은 이름의 잠금을 잡아 탭 사이에서 한 줄로 세운다. 리프레시 토큰이 쿠키라 뒤 탭은 이미 바뀐 쿠키로 요청해서 재사용에 걸리지 않는다. 로그아웃은 `BroadcastChannel`이나 `storage` 이벤트로 다른 탭에 알려 메모리 토큰을 비우게 하고, 서버에서 리프레시 토큰을 무효로 만든다.

### BFF 패턴은 무엇이고 언제 쓰나요?

프런트엔드와 같은 사이트에 작은 서버를 두고 OAuth 토큰은 그 서버가 보관하며, 브라우저에는 세션 쿠키만 주는 구조다. 토큰이 자바스크립트에 없어 XSS로 훔칠 것이 없고, 토큰 갱신과 동시성 문제도 서버 한 곳에서 처리한다. 대신 서버와 세션 저장소를 운영해야 하고 요청마다 한 번 더 거치며 CSRF 대비가 필요하다. 금융처럼 보안 요구가 높거나, Next.js처럼 이미 서버가 있는 경우에 잘 맞는다.

### 서드파티 쿠키 제한은 토큰 저장에 어떤 영향을 주나요?

프런트와 API가 다른 사이트에 있으면 API의 리프레시 쿠키가 서드파티 쿠키가 되어, 사파리처럼 기본으로 막는 브라우저에서 리프레시가 실패한다. 크롬은 지금 기본으로 허용하지만 시크릿 창이나 사용자 설정에서는 막히고, 파이어폭스는 최상위 사이트별로 나눈다. 숨은 iframe으로 하던 silent refresh도 같은 이유로 깨진다. API를 같은 사이트 서브도메인으로 옮기거나 같은 출처 프록시나 BFF를 두는 게 근본적인 해결이다.
