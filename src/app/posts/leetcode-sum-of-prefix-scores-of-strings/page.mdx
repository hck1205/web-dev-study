검색창에 `ca`까지 쳤을 때 "이 앞부분으로 시작하는 단어가 몇 개인지"를 바로 알려 주려면, 앞부분마다 개수를 미리 세어 두어야 한다. 단어 하나가 들어올 때 그 단어의 모든 앞부분 개수가 하나씩 오른다. [LeetCode 2416. Sum of Prefix Scores of Strings](https://leetcode.com/problems/sum-of-prefix-scores-of-strings/)는 이 개수를 단어의 앞부분마다 모두 더하라는 문제다.

[Implement Trie](/posts/leetcode-implement-trie)의 트라이에 숫자 하나만 더 들면 풀린다. 이 글은 단어마다 다른 단어를 모두 맞춰 보는 풀이에서 시작해, 앞부분 문자열을 해시맵에 세는 풀이, 롤링 해시, 개수를 든 트라이, 그리고 트라이 없이 정렬과 공통 접두사 길이만으로 푸는 풀이까지 다섯 가지를 본다. 마지막 풀이는 의외로 가장 빠르다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 앞부분마다 같은 앞부분을 가진 단어 수

입력은 단어 배열 `words`다. 문자열 `t`의 점수는 "`t`로 시작하는 단어가 `words`에 몇 개인가"다. 자기 자신도 센다. 단어 `w`마다 `w`의 모든 앞부분(길이 1부터 `w` 전체까지)의 점수를 더한 값을 구해, 같은 순서로 배열에 담아 돌려준다.

- 단어 수 n과 단어 길이 L은 각각 1,000 이하. 모두 소문자.
- 같은 단어가 여러 번 나올 수 있다.

단어 1,000개가 각각 1,000글자면 글자 수 합이 100만이다. 앞부분 개수도 단어마다 1,000개라 모두 100만 개다. 앞부분 하나를 확인할 때마다 단어 1,000개를 다 보면 10억 번을 넘긴다. 그리고 앞부분을 문자열로 하나씩 만들면 글자 수 합이 5억에 이른다. 이 숫자가 풀이 선택을 정한다.

이 글에서 쓸 예시다.

```text
words = [car, cat, cart, dog]
답    = [8, 7, 9, 3]
```

손으로 세어 보자. `cart`의 앞부분은 `c`, `ca`, `car`, `cart`다.

- `c`로 시작하는 단어: car, cat, cart. 3개.
- `ca`로 시작하는 단어: car, cat, cart. 3개.
- `car`로 시작하는 단어: car, cart. 2개.
- `cart`로 시작하는 단어: cart. 1개.

모두 더하면 9다. `car`는 3 + 3 + 2 = 8, `cat`은 3 + 3 + 1 = 7, `dog`는 앞부분 셋이 모두 자기만 가지고 있어서 1 + 1 + 1 = 3이다.

## 앞부분마다 단어를 전부 맞춰 보기

정의를 그대로 옮긴다. 단어마다, 앞부분마다, 모든 단어가 그 앞부분으로 시작하는지 본다.

```js
function sumPrefixScores(words) {
  return words.map((w) => {
    let score = 0;
    for (let k = 1; k <= w.length; k++) {
      const p = w.slice(0, k); // 길이 k인 앞부분
      for (const v of words) if (v.startsWith(p)) score++;
    }
    return score;
  });
}
```

단어 n개 × 앞부분 L개 × 단어 n개 × 비교 최대 L글자라 O(n²·L²)이다. 최악이면 10^12이라 끝나지 않는다. 공간은 앞부분 하나를 만드는 O(L)뿐이다.

낭비가 눈에 보인다. `car`와 `cart`는 앞부분 `c`, `ca`, `car`를 공유하는데, 두 단어 모두 그 앞부분의 개수를 처음부터 다시 센다. 앞부분마다 개수는 정해져 있으니 한 번만 세어 두면 된다.

## 앞부분 문자열을 해시맵에 세어 두기

모든 단어의 모든 앞부분을 해시맵에 넣고 개수를 센다. 그다음 단어마다 앞부분의 개수를 꺼내 더한다.

```js
function sumPrefixScores(words) {
  const count = new Map(); // 앞부분 -> 그 앞부분을 가진 단어 수
  for (const w of words) {
    for (let k = 1; k <= w.length; k++) {
      const p = w.slice(0, k);
      count.set(p, (count.get(p) ?? 0) + 1);
    }
  }
  return words.map((w) => {
    let score = 0;
    for (let k = 1; k <= w.length; k++) score += count.get(w.slice(0, k));
    return score;
  });
}
```

단어 n개 × 앞부분 L개라 해시맵 연산은 n·L번이다. 그런데 연산 한 번이 O(1)이 아니다. 길이 k인 문자열을 만들고 해시를 계산하는 데 O(k)가 들어서, 단어 하나에 1 + 2 + … + L = O(L²)이다. 전체는 O(n·L²), 최악이면 5억 글자를 읽는다.

1,000글자 단어 1,000개로 재 보았다. 모든 단어가 `aaa…a`로 같을 때 1,958ms, 무작위 단어일 때 2,809ms가 걸렸다. 무작위 단어에서는 앞부분이 서로 거의 다 달라서 해시맵 키가 100만 개 가까이 생긴다.

메모리도 문제다. Python이나 Java에서 부분 문자열은 글자를 복사한 새 문자열이라, 키 100만 개의 글자 수 합이 5억에 이른다. 잰 Node.js 22에서는 힙이 94MB로 생각보다 작았는데, V8이 긴 `slice` 결과를 원본을 가리키는 조각 문자열로 만들기 때문으로 보인다. 엔진의 이런 동작에 기대는 풀이는 언어를 바꾸면 무너진다.

## 문자열 대신 해시값을 이어서 계산하기

앞부분 `w[0..k]`의 해시는 `w[0..k-1]`의 해시에서 한 글자만 더 반영하면 된다. 롤링 해시다(원리는 [문자열 검색 글](/posts/string-search-algorithms)의 라빈-카프 부분).

```js
function sumPrefixScores(words) {
  const MOD = 1_000_000_007, B = 131;
  const count = new Map();
  // 해시와 길이를 함께 키로 만든다. h는 1e9+7 미만, 길이는 1000 이하라 2^53 안에 들어간다
  const key = (h, len) => h * 1001 + len;
  for (const w of words) {
    let h = 0;
    for (let k = 0; k < w.length; k++) {
      h = (h * B + w.charCodeAt(k)) % MOD; // 한 글자를 더 반영한다
      const kk = key(h, k + 1);
      count.set(kk, (count.get(kk) ?? 0) + 1);
    }
  }
  return words.map((w) => {
    let h = 0, score = 0;
    for (let k = 0; k < w.length; k++) {
      h = (h * B + w.charCodeAt(k)) % MOD;
      score += count.get(key(h, k + 1));
    }
    return score;
  });
}
```

이제 앞부분 하나가 O(1)이라 전체가 O(n·L)이다. 같은 무작위 입력에서 622ms로 4배 넘게 빨라졌다.

`h * B`가 안전한지 따져 봐야 한다. `h`는 10^9 + 7 미만이고 `B`는 131이라 곱은 약 1.3 × 10^11이다. JS의 정수 안전 범위 2^53(약 9 × 10^15) 안이다. 법을 10^9 + 7보다 훨씬 크게 잡으면 이 곱이 범위를 넘어 조용히 틀린 값이 나온다. Java의 `long`, Python의 큰 정수는 이 걱정이 없다.

남은 문제는 충돌이다. 서로 다른 앞부분의 해시가 같으면 개수가 섞인다. 길이를 키에 넣어 같은 길이끼리만 충돌하게 줄였지만, 길이마다 앞부분이 1,000개씩 길이가 1,000가지다. 생일 문제로 계산하면 법 10^9 + 7에서 어딘가 한 번이라도 충돌할 확률이 약 39%다. 법을 두 개 쓰는 이중 해시로 줄일 수는 있어도 0이 되지는 않는다. 확률에 기대지 않는 구조가 필요하다.

## 지나간 단어 수를 든 트라이

해시맵 풀이의 진짜 낭비는 `car`, `cart`, `cat`이 공유하는 `ca`를 각자 따로 만든다는 점이다. 트라이에서는 같은 앞부분이 같은 노드다. `c`에서 `a`로 내려간 노드 하나가 곧 앞부분 `ca`다.

그러면 노드마다 "이 노드를 지나간 단어 수"를 세어 두면 된다. 이게 그 앞부분의 점수다.

1. 단어를 넣을 때, 내려가며 지나는 모든 노드의 `count`를 1 올린다. 끝 표시는 필요 없다.

첫 그림의 마지막 단계에서 노드가 8개뿐이다. 네 단어의 글자 수 합은 13인데, 공유하는 `c`, `ca`, `car`가 한 번씩만 생겨서 8개로 줄었다. 해시맵 풀이에서 키 13개를 각각 문자열로 만든 것과 다르다.

```js
function sumPrefixScores(words) {
  // 노드: next는 글자 -> 자식, count는 이 노드를 지나간 단어 수
  const root = { next: {}, count: 0 };
  for (const w of words) {
    let node = root;
    for (const ch of w) {
      node = node.next[ch] ??= { next: {}, count: 0 };
      node.count++; // 이 앞부분을 가진 단어가 하나 늘었다
    }
  }
  return words.map((w) => {
    let node = root, score = 0;
    for (const ch of w) {
      node = node.next[ch]; // 넣은 단어라 자식이 반드시 있다
      score += node.count;
    }
    return score;
  });
}
```

넣기와 세기 모두 글자 하나에 노드 한 칸이라 시간은 O(n·L), 글자 수 합만큼이다. 공간은 노드 수만큼이라 최악 O(n·L)이다. 해시 충돌도, 부분 문자열 생성도 없다.

세는 단계에서 `node.next[ch]`가 `undefined`인지 확인하지 않아도 된다. 같은 단어를 이미 넣었으니 길이 반드시 있다. [Implement Trie](/posts/leetcode-implement-trie)의 `search`와 다른 점이다.

무작위 1,000글자 단어 1,000개에서 443ms, 같은 단어 1,000개에서 33ms였다. 무작위 단어는 거의 공유가 없어서 노드를 100만 개 가까이 만든다. 이 시간의 대부분이 노드 객체를 만드는 비용이다.

### Python과 Java로 쓰면

Python은 딕셔너리 노드에 개수를 `"#"` 키로 함께 둔다. `"#"`는 소문자가 아니라 글자 자식과 겹치지 않는다.

```python
from typing import List

class Solution:
    def sumPrefixScores(self, words: List[str]) -> List[int]:
        root = {}
        for w in words:
            node = root
            for ch in w:
                if ch not in node:
                    node[ch] = {"#": 0}  # "#"에 이 앞부분을 가진 단어 수를 둔다
                node = node[ch]
                node["#"] += 1

        ans = []
        for w in words:
            node, score = root, 0
            for ch in w:
                node = node[ch]
                score += node["#"]
            ans.append(score)
        return ans
```

같은 무작위 입력에서 623ms, 같은 단어 1,000개에서 121ms가 걸렸다. 재귀가 없으니 Python의 재귀 한도는 상관없다.

Java는 26칸 배열 노드다.

```java
class Solution {
    private static class Node {
        Node[] next = new Node[26];
        int count; // 이 노드까지의 앞부분을 가진 단어 수
    }

    public int[] sumPrefixScores(String[] words) {
        Node root = new Node();
        for (String w : words) {
            Node node = root;
            for (int i = 0; i < w.length(); i++) {
                int c = w.charAt(i) - 'a';
                if (node.next[c] == null) node.next[c] = new Node();
                node = node.next[c];
                node.count++;
            }
        }
        int[] ans = new int[words.length];
        for (int k = 0; k < words.length; k++) {
            Node node = root;
            int score = 0;
            String w = words[k];
            for (int i = 0; i < w.length(); i++) {
                node = node.next[w.charAt(i) - 'a'];
                score += node.count;
            }
            ans[k] = score;
        }
        return ans;
    }
}
```

세 언어 모두 예시에 `[8, 7, 9, 3]`을 냈다. 점수의 최댓값은 모든 단어가 같을 때 1,000 × 1,000 = 10^6이라 `int`로 충분하다. 단어 수나 길이가 10^5로 커지는 변형이면 `long`으로 바꾼다.

Java에서 신경 쓸 곳은 메모리다. 무작위 1,000글자 단어 1,000개로 트라이를 만들고 힙 사용량 차이를 재니 약 148MB였다. 노드 하나가 26칸 참조 배열을 들고 있어서, 자식이 하나뿐인 노드도 배열 전체를 차지한다.

노드 객체를 없애고 번호로 가리키는 배열 트라이로 바꾸어 보았다.

```java
int total = 0;
for (String w : words) total += w.length();
int[][] next = new int[total + 1][26]; // 0번이 뿌리. 값 0은 "자식 없음"도 뜻한다
int[] count = new int[total + 1];
int size = 1;
for (String w : words) {
    int node = 0;
    for (int i = 0; i < w.length(); i++) {
        int c = w.charAt(i) - 'a';
        if (next[node][c] == 0) next[node][c] = size++; // 새 노드 번호를 준다
        node = next[node][c];
        count[node]++;
    }
}
```

예시에 같은 `[8, 7, 9, 3]`이 나오고 무작위 입력에서 183ms였는데, 배열만 134MB로 기대만큼 줄지 않았다. `int[][]`도 결국 100만 개의 작은 배열이라 배열마다 헤더가 붙는다. 한 줄짜리 `int[(total + 1) * 26]`로 펴도 26 × 100만 × 4바이트 = 약 104MB다. 26칸 자식 자리를 모든 노드에 미리 잡는 한 크게 줄일 방법이 없다. 메모리가 정말 빠듯하면 아래의 정렬 풀이로 간다.

## 정렬하면 공통 접두사 길이의 합이 된다

트라이 없이 푸는 길도 있다. 점수의 정의를 뒤집어 보자.

`w`의 점수는 "`w`의 앞부분마다, 그걸로 시작하는 단어 수"의 합이다. 이걸 단어 `v` 쪽에서 세면 "`v`가 `w`의 앞부분 몇 개로 시작하나"의 합이 된다. 그런데 `v`가 `w`의 길이 1, 2, …, k 앞부분으로 시작한다는 건 `w`와 `v`의 공통 접두사 길이(LCP, longest common prefix)가 k라는 뜻이다. 그래서 이렇게 된다.

```text
score(w) = 모든 단어 v에 대한 LCP(w, v)의 합   (v = w 자신이면 LCP는 w의 길이)
```

예시로 확인하자. `cart`와 각 단어의 LCP는 car 3, cat 2, cart 4, dog 0이다. 합이 9로 트라이 풀이와 같다.

모든 쌍의 LCP를 구하면 O(n²·L)이라 느리다. 여기서 정렬이 쓰인다. 단어를 사전 순으로 정렬하면, 두 단어의 LCP는 그 사이에 있는 이웃 쌍 LCP의 최솟값이다. 정렬하면 [car, cart, cat, dog]이고 이웃 LCP는 `h = [3, 2, 0]`이다. `car`와 `cat`의 LCP는 그 사이 `h[0]`, `h[1]`의 최솟값 2다.

그러면 정렬된 위치 `i`의 점수는 "자기 길이 + 왼쪽 단어들과의 최솟값 합 + 오른쪽 단어들과의 최솟값 합"이다. `cart`(위치 1)라면 자기 길이 4, 왼쪽은 `car`까지 `min(3) = 3`, 오른쪽은 `cat`까지 `min(2) = 2`, `dog`까지 `min(2, 0) = 0`이다. 4 + 3 + 2 + 0 = 9.

"왼쪽으로 가며 최솟값을 계속 더하는 합"은 [단조 스택](/posts/monotonic-stack-pattern)으로 한 번에 구한다. `h`를 왼쪽부터 보며, 지금 값보다 크거나 같은 스택 원소는 지금 값으로 깎이니 꺼내서 합에서 빼고 개수만큼 지금 값으로 다시 더한다.

```js
function sumPrefixScores(words) {
  const n = words.length;
  // 정렬하되 원래 위치를 기억한다
  const order = words.map((_, i) => i)
    .sort((a, b) => (words[a] < words[b] ? -1 : words[a] > words[b] ? 1 : 0));
  const sorted = order.map((i) => words[i]);
  const lcp = (a, b) => {
    let k = 0;
    while (k < a.length && k < b.length && a[k] === b[k]) k++;
    return k;
  };
  const h = []; // h[i] = LCP(sorted[i], sorted[i + 1])
  for (let i = 0; i + 1 < n; i++) h.push(lcp(sorted[i], sorted[i + 1]));

  // left[i] = 위치 i의 왼쪽 단어들과의 LCP 합, right[i]는 오른쪽
  const left = new Array(n).fill(0), right = new Array(n).fill(0);
  let stack = [], sum = 0; // 스택 원소: [값, 그 값으로 깎인 개수]
  for (let t = 0; t < n - 1; t++) {
    let cnt = 1;
    while (stack.length && stack[stack.length - 1][0] >= h[t]) {
      const [v, c] = stack.pop();
      sum -= v * c; // 더 큰 최솟값들이 h[t]로 깎인다
      cnt += c;
    }
    stack.push([h[t], cnt]);
    sum += h[t] * cnt;
    left[t + 1] = sum;
  }
  stack = []; sum = 0;
  for (let t = n - 2; t >= 0; t--) {
    let cnt = 1;
    while (stack.length && stack[stack.length - 1][0] >= h[t]) {
      const [v, c] = stack.pop();
      sum -= v * c;
      cnt += c;
    }
    stack.push([h[t], cnt]);
    sum += h[t] * cnt;
    right[t] = sum;
  }
  const ans = new Array(n);
  for (let i = 0; i < n; i++) ans[order[i]] = sorted[i].length + left[i] + right[i];
  return ans;
}
```

정렬이 비교 O(n log n)번이고 비교 한 번이 최악 O(L)이라 O(L·n log n), 이웃 LCP가 O(n·L), 스택 두 번이 O(n)이다. 공간은 O(n)이다. 트라이처럼 노드를 만들지 않는다.

재 보면 놀랍다. 무작위 1,000글자 단어 1,000개에서 2ms였다. 트라이의 443ms보다 200배 빠르다. 무작위 단어는 첫 몇 글자에서 갈라져서 비교와 LCP가 몇 글자 만에 끝나기 때문이다. 같은 단어 1,000개라는 최악에서도 13ms로 트라이(33ms)보다 빨랐다. 단어 1,000개를 끝까지 비교해도 100만 글자를 몇 번 읽는 정도라서다.

왼쪽 합을 구하는 과정을 예시로 따라가 보자. 정렬된 단어는 [car, cart, cat, dog], 이웃 LCP는 `h = [3, 2, 0]`이다. 기억 칸은 스택(값×개수)과 지금의 합이다.

같은 단어가 여러 번 나와도 맞는다. 정렬하면 서로 붙고, 이웃 LCP가 단어 길이가 되어 서로의 점수에 길이만큼 더해진다. `[a, a]`에 `[2, 2]`가 나온다.

이 풀이의 약점은 설명하기 어렵다는 것이다. "LCP 합으로 바뀐다", "정렬하면 구간 최솟값이 된다", "구간 최솟값 합은 단조 스택" 세 단계를 면접에서 막힘없이 말하기는 쉽지 않다. 그리고 단어가 하나씩 추가되는 변형에서는 매번 다시 정렬해야 한다. 트라이는 추가에 강하다.

## 끝 노드에만 세거나 중복을 지우면 틀린다

가장 흔한 실수는 [Implement Trie](/posts/leetcode-implement-trie) 습관대로 단어가 끝나는 노드에만 개수를 올리는 것이다.

```js
for (const w of words) {
  let node = root;
  for (const ch of w) node = node.next[ch] ??= { next: {}, count: 0 };
  node.count++; // 끝 노드에만 올린다
}
// [car, cat, cart, dog] -> [1, 1, 2, 1] (정답은 [8, 7, 9, 3])
```

이러면 `count`가 "이 앞부분으로 시작하는 단어 수"가 아니라 "정확히 이 단어인 개수"가 된다. `c`, `ca` 노드는 어떤 단어의 끝도 아니라 0으로 남는다. 그래서 `car`는 자기 노드의 1만 얻고, `cart`는 지나가는 `car` 노드 1과 자기 노드 1을 더해 2가 된다. 앞부분 점수가 아니라 "내 앞부분 중 단어 목록에 그대로 있는 것의 수"를 센 셈이다. 지나가는 모든 노드에서 올려야 한다.

두 번째는 단어를 `Set`으로 먼저 걸러 중복을 없애는 것이다.

```js
const unique = [...new Set(words)]; // 중복을 지우고 트라이를 만든다
// [a, a] -> [1, 1] (정답은 [2, 2])
```

점수는 "단어 목록에 몇 개 있나"라서 같은 단어 두 개는 두 번 센다. 중복을 지우면 그만큼 모자란다. 위 테스트의 "같은 단어가 두 번"이 이걸 잡는다.

그 밖에 조심할 것들이다.

- 내려가기 전에 `count`를 올리고 더하는 순서로 쓰면 한 칸씩 밀린다. 뿌리(빈 앞부분)가 n으로 세어지고 단어의 마지막 노드는 빠져서, 예시에 `[10, 10, 11, 6]`이 나온다. 내려간 뒤에 올리고 더하는 순서(`node = node.next[ch]` 다음 `node.count++`, `score += node.count`)를 지킨다.
- 정렬 풀이에서 `order`로 원래 위치에 되돌려 놓지 않으면 정렬된 순서로 답이 나온다. 문제는 입력 순서대로 원한다.
- 인덱스 배열을 정렬할 때 비교 함수를 빼먹으면 JS는 인덱스 숫자를 문자열로 바꿔 `0, 1, 10, 2, …` 순서로 늘어놓는다. 단어 순서와 아무 상관이 없으니 비교 함수에서 `words[a]`와 `words[b]`를 비교한다.

## 조건을 바꾸어 묻는 꼬리 질문

### 단어가 하나씩 계속 추가된다면

트라이는 단어를 넣을 때마다 지나는 노드의 `count`를 올리면 끝이다. 다만 이미 계산한 다른 단어들의 점수도 바뀐다. 새 단어 `x`가 들어오면 기존 단어 `w`의 점수는 `LCP(w, x)`만큼 오른다. 점수를 그때그때 물어보는 방식이라면 질문이 올 때 트라이를 내려가 더하면 되니 문제없다. 정렬 풀이는 매번 다시 정렬해야 해서 이 변형에 약하다.

### 앞부분이 아니라 뒷부분 점수라면

모든 단어를 뒤집어서 같은 트라이를 쓰면 된다. 뒷부분은 뒤집은 단어의 앞부분이다.

### 한 앞부분의 점수만 빠르게 물어본다면

트라이를 그 앞부분 끝까지 내려가 `count`를 돌려준다. 앞부분 길이 m에 O(m)이다. "이 앞부분으로 시작하는 단어 수"를 세는 메서드가 있는 트라이가 1804번 Implement Trie II(프리미엄 문제)다. 단어마다 숫자를 더하는 변형은 677번 Map Sum Pairs다.

### 메모리가 아주 빠듯하다면

정렬 풀이로 바꾼다. 단어 배열 말고 O(n)만 쓴다. 트라이를 꼭 써야 하면 자식이 하나뿐인 사슬을 노드 하나로 합친 압축 트라이로 바꾼다. 무작위 단어처럼 공유가 적은 입력에서 노드 수가 단어 수 수준으로 줄어든다.

### 단어 수가 10^5, 글자 수 합이 10^6이라면

트라이와 정렬 풀이 모두 글자 수 합에 비례하니 그대로 간다. 점수 최댓값이 10^5 × 길이까지 커질 수 있어 Java는 `long`으로 바꾼다. 해시맵에 부분 문자열을 넣는 풀이는 이 크기에서 메모리가 먼저 터진다.

## 지나간 수를 세어 두면 점수가 길 위에 있다

앞부분의 점수는 "그 앞부분을 지나간 단어 수"이고, 트라이에서는 노드 하나가 앞부분 하나다. 단어를 넣을 때 지나는 노드마다 `count`를 올리고, 다시 내려가며 더하면 O(글자 수 합)으로 끝난다. 같은 점수가 "모든 단어와의 공통 접두사 길이 합"이라는 걸 알면, 정렬과 단조 스택으로 노드 없이 푸는 길도 열린다.

## 면접에서 나올 만한 질문

### 트라이 노드에 무엇을 저장하나요?

"이 노드를 지나간 단어 수" 하나다. 단어를 넣을 때 지나는 모든 노드에서 1을 올린다. 그러면 노드의 `count`가 그 노드까지의 앞부분으로 시작하는 단어 수, 곧 그 앞부분의 점수가 된다. 끝 표시는 이 문제에서 필요 없다.

### 해시맵에 앞부분을 다 넣으면 왜 느린가요?

앞부분 문자열을 만들고 해시를 계산하는 데 길이만큼 들어서, 단어 하나에 O(L²), 전체 O(n·L²)이다. 1,000글자 단어 1,000개면 5억 글자를 읽는다. 문자열을 복사하는 언어에서는 메모리도 그만큼 든다. 트라이는 공유하는 앞부분을 노드 하나로 합쳐서 글자 수 합만큼만 걷는다.

### 롤링 해시로 O(n·L)을 만들 수 있는데 트라이를 쓰는 이유는요?

롤링 해시는 충돌이 나면 다른 앞부분의 개수가 섞여 틀린 답을 낸다. 앞부분이 100만 개면 법 10^9 + 7 하나로는 충돌 확률을 무시할 수 없다. 트라이는 같은 시간에 충돌 없이 정확하다. JS에서는 해시 곱이 2^53을 넘지 않게 법을 고르는 것도 신경 써야 한다.

### 시간과 공간 복잡도는요?

트라이는 넣기와 세기 모두 글자 하나에 한 칸이라 O(글자 수 합), 최악 O(n·L)이다. 공간은 노드 수만큼이라 최악 O(n·L)이고, Java의 26칸 배열 노드로 100만 노드면 150MB 가까이 든다. 정렬 풀이는 O(L·n log n) 시간에 O(n) 공간이다.

### 트라이 없이 풀 수 있나요?

점수는 "모든 단어와의 공통 접두사 길이 합"과 같다. 단어를 정렬하면 두 단어의 LCP는 사이에 있는 이웃 LCP의 최솟값이라, 위치마다 왼쪽과 오른쪽으로 최솟값을 누적한 합을 단조 스택으로 구하면 된다. 무작위 입력에서 트라이보다 200배 빨랐지만, 단어가 추가되는 변형에는 약하다.

### 같은 단어가 여러 번 나오면요?

여러 번 센다. 점수는 목록에 있는 단어 수라서 `[a, a]`의 답은 `[2, 2]`다. 트라이는 같은 길을 두 번 지나며 자연스럽게 2를 만들고, 정렬 풀이는 둘이 붙어 이웃 LCP가 길이가 된다. 중복을 미리 지우면 틀린다.

### 이 풀이가 틀리는 입력을 들어 보세요.

단어 끝 노드에만 `count`를 올리는 코드는 `[car, cat, cart, dog]`에 `[1, 1, 2, 1]`을 낸다. 공유하는 `c`, `ca` 노드가 0으로 남기 때문이다. `count`를 내려가기 전에 올리고 더하는 코드는 뿌리를 세고 마지막 글자를 빠뜨려 `[10, 10, 11, 6]`을 낸다.
