새 정산 서비스를 무엇으로 만들지 정하는 회의였다. 한 사람은 팀이 다 아는 자바로 가자고 했고, 한 사람은 컨테이너가 가볍다며 Go를 밀었고, 프런트엔드 출신이 많은 쪽은 Node.js면 타입까지 한 언어로 끝난다고 했다. 데이터 팀은 파이썬 라이브러리를 그대로 쓰고 싶어 했다. 한 시간 동안 나온 근거는 대부분 "써 보니 좋았다"였다.

나도 처음엔 언어 비교를 문법이나 벤치마크 순위로 했다. 그런데 운영에서 실제로 차이를 만든 건 다른 것들이었다. 요청이 DB를 기다리는 동안 무엇이 묶여 있는지, 메모리를 누가 언제 치우는지, 프로세스가 뜨는 데 얼마나 걸리는지, 그리고 그 언어로 일할 사람을 구할 수 있는지.

이 글은 그 네 가지 잣대로 Java, Go, Node.js, Python, Rust, C#을 비교하고 PHP와 Ruby가 여전히 잘 버티는 자리도 짚는다. 같은 API를 여러 런타임으로 띄워 직접 재 본 숫자도 함께 본다. 고루틴과 채널 자체는 [Go 동시성 글](/posts/go-concurrency-basics)에서, JVM의 힙 밖 메모리와 가상 스레드는 [JVM 메모리와 스레드 글](/posts/java-jvm-memory-gc)에서, Node의 스레드 풀은 [Node.js 서버 런타임 글](/posts/nodejs-server-runtime)에서 깊게 다뤘다. 여기서는 그 셋을 나란히 놓는다.

## 요청이 기다리는 동안 무엇이 묶여 있나

백엔드 API 요청 하나가 하는 일을 시간으로 쪼개 보면 대개 이렇다. 요청을 파싱하고(1ms 미만), DB나 다른 서비스에 물어보고 기다리고(수십 ms), 결과를 JSON으로 만들어 보낸다(1ms 안팎). CPU를 쓰는 시간보다 기다리는 시간이 훨씬 길다. 이런 일을 I/O 바운드라고 부른다.

그래서 서버 언어의 성격은 "기다리는 동안 무엇을 붙잡고 있나"에서 갈린다. 크게 네 가지 모델이 있다.

첫째, 요청마다 OS 스레드 하나. 자바의 전통적인 서블릿 모델, Ruby의 Puma, C#의 동기 코드가 여기에 가깝다. 코드는 위에서 아래로 읽히고 디버깅이 쉽다. 대신 스레드 하나가 스택 메모리(기본 수백 KB에서 1MB)와 커널 스케줄링 비용을 들고 있어서, 기다리는 요청 수만큼 스레드가 필요하다. 보통은 스레드 풀 크기로 상한을 둔다.

둘째, 이벤트 루프 하나. Node.js가 대표다. 스레드 하나가 "이 소켓에 응답이 오면 이 함수를 불러 줘"라고 등록해 두고 다른 요청으로 넘어간다. 기다리는 요청이 만 개여도 스레드는 하나라 가볍다. 대신 그 스레드에서 CPU를 오래 쓰는 코드가 하나라도 돌면 모든 요청이 같이 멈춘다.

셋째, 런타임이 관리하는 가벼운 실행 단위. Go의 고루틴, 자바 21의 가상 스레드가 여기 속한다. 코드는 첫째처럼 순서대로 쓰고, 기다리는 순간 런타임이 그 실행 단위를 OS 스레드에서 떼어 내고 다른 걸 올린다. 실행 단위 하나가 몇 KB라서 수만 개를 띄워도 된다.

넷째, 언어에 async/await가 있고 실행기는 고르는 모델. C#의 async/await, 파이썬의 asyncio, 러스트의 async(tokio 같은 라이브러리가 실행기)다. 둘째 모델을 순서대로 읽히는 문법으로 감싼 것에 가깝다. `await`를 쓰지 않고 막는 함수를 부르면 둘째 모델과 똑같이 전체가 멈춘다.

## 같은 API를 다섯 런타임으로 띄워 봤다

말로만 비교하면 감이 안 와서, 같은 일을 하는 아주 작은 서버를 여러 런타임으로 만들었다. 할 일은 하나다. 요청을 받으면 DB 대신 50ms를 기다리고 `{"id":42,"status":"PAID"}`를 돌려준다. 실제 서비스의 DB 대기를 흉내 낸 순수 I/O 바운드 API다.

```js
// node.mjs (Node.js 22.22)
import http from "node:http";
http.createServer((req, res) => {
  setTimeout(() => {
    res.writeHead(200, { "content-type": "application/json" });
    res.end(JSON.stringify({ id: 42, status: "PAID" }));
  }, 50);
}).listen(8081);
```

```go
// main.go (Go 1.24) — 요청마다 고루틴이 하나씩 뜬다
http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
  time.Sleep(50 * time.Millisecond)
  w.Header().Set("content-type", "application/json")
  json.NewEncoder(w).Encode(map[string]any{"id": 42, "status": "PAID"})
})
http.ListenAndServe(":8082", nil)
```

```java
// Server.java (OpenJDK 21) — 인자가 없으면 가상 스레드, 숫자를 주면 고정 크기 스레드 풀
var s = HttpServer.create(new InetSocketAddress(8083), 1024);
s.setExecutor(a.length > 0
    ? Executors.newFixedThreadPool(Integer.parseInt(a[0]))
    : Executors.newVirtualThreadPerTaskExecutor());
s.createContext("/", ex -> {
  try { Thread.sleep(50); } catch (InterruptedException e) {}
  byte[] b = "{\"id\":42,\"status\":\"PAID\"}".getBytes();
  ex.sendResponseHeaders(200, b.length);
  try (var o = ex.getResponseBody()) { o.write(b); }
});
s.start();
```

```python
# app.py (Python 3.13, Starlette + uvicorn 워커 1개)
async def order(request):
    if BLOCK:
        time.sleep(0.05)          # 일부러 넣은 실수: 막는 sleep
    else:
        await asyncio.sleep(0.05)
    return JSONResponse({"id": 42, "status": "PAID"})
```

같은 4코어 리눅스 머신에서 서버를 띄우고, 첫 응답이 올 때까지 걸린 시간과 1초 뒤의 메모리(RSS)를 잰 다음 ab로 동시 200개 연결에서 요청 8,000개를 보냈다.

```bash
# 서버를 띄운 뒤 동시 200개, 총 8000개 요청 (keep-alive 요청)
ab -q -k -n 8000 -c 200 http://127.0.0.1:8081/
# 실행 중인 프로세스의 현재 RSS와 지금까지의 최대 RSS
grep -E 'VmRSS|VmHWM|Threads' /proc/<pid>/status
```

```text
go             start=  67ms idleRSS=  7600KB peakRSS= 19972KB threads=   9 rps= 3554.44 p50=  53ms p99=  65ms fail=0

```

각 줄에서 볼 곳은 세 군데다. `start`는 프로세스를 띄우고 첫 응답까지 걸린 시간, `idleRSS`와 `peakRSS`는 쉬고 있을 때와 부하 중 최대 메모리, `p50`·`p99`는 응답 시간의 중앙값과 꼬리다. 동시 200개에 50ms 대기라 이론상 상한은 초당 4,000건이고, 그때 p50은 50ms 근처여야 한다.

몇 가지가 바로 보인다. Go는 7.6MB로 떠서 67ms 만에 응답했고 p50이 53ms로 거의 이론값이다. 자바는 뜨는 데 0.6초, 부하 중 메모리가 228MB까지 올랐다. 고정 풀 16개짜리 자바는 초당 312건에서 막혔고 p50이 636ms가 됐다. 이건 언어가 느려서가 아니라 스레드 16개가 전부 `sleep`에 묶였기 때문이다. 다음 절에서 이 숫자를 계산으로 맞춰 본다.

같은 프로세스에 부하를 한 번 더 주고 두 번째 결과만 보면 그림이 또 바뀐다.

```text
java -cp . Server warm: 2104.53 rps p50=92 p99=100 rss=237740
node node.mjs warm: 3472.02 rps p50=55 p99=65 rss=93124
./goserver warm: 3752.73 rps p50=51 p99=59 rss=18604
```

Node는 두 번째 판에서 p99가 134ms에서 65ms로 내려갔다. 자바는 p99가 204ms에서 100ms로 줄었다. JIT 컴파일러가 자주 도는 코드를 기계어로 바꾸기 전과 후의 차이다. 짧게 돌고 끝나는 벤치마크가 JVM과 V8에 불리하게 나오는 이유이기도 하다. 자바의 p50이 여전히 92ms인 건 언어보다 JDK 내장 `HttpServer`의 한계다. 이 서버는 테스트·도구용에 가깝고, 실서비스는 Netty나 Tomcat, Jetty 위에서 돈다.

이 측정에는 한계가 분명하다. ab 자체가 스레드 하나라 부하 발생기가 먼저 바쁘다. Node와 uvicorn은 ab가 쓰는 HTTP/1.0 keep-alive를 받지 않아 요청마다 새 연결을 맺었다(ab의 `Keep-Alive requests: 0`). 파이썬은 워커 1개로 코어 하나만 썼다. 그래서 이 숫자를 "어느 언어가 몇 배 빠르다"로 읽으면 안 된다. 읽을 수 있는 건 "50ms를 기다리는 일에서는 모델만 맞으면 다들 이론 상한 근처에 간다"와 "시작 시간과 메모리 바닥은 런타임마다 자릿수가 다르다" 두 가지다.

## 일꾼 수와 기다림이 처리량 상한을 정한다

고정 풀 16개 자바가 312건에서 막힌 건 간단한 곱셈으로 설명된다. 요청 하나가 일꾼 하나를 50ms 붙잡는다. 일꾼 하나는 1초에 1000 ÷ 50 = 20건을 처리한다. 일꾼이 16명이면 16 × 20 = 320건이 상한이다. 측정값 312건이 거의 그 자리다. 나머지 요청은 줄을 서고, 줄 선 시간만큼 p50이 636ms로 늘었다.

이 관계는 리틀의 법칙으로 알려져 있다. 동시에 처리 중인 일의 수 = 처리량 × 한 건에 걸리는 시간. 뒤집으면 처리량 상한 = 일꾼 수 ÷ 한 건당 붙잡는 시간이다. 가상 스레드나 고루틴, 이벤트 루프가 해결하는 건 바로 "일꾼 수"를 수천, 수만으로 싸게 늘리는 일이다. 기다리는 동안 OS 스레드를 놓아주니까 일꾼 수가 OS 스레드 수에 묶이지 않는다.

아래에서 직접 계산해 보자. `workers`명이 각 요청마다 `waitMs`만큼 기다리고 `cpuMs`만큼 CPU를 쓸 때 1초에 처리할 수 있는 최대 건수를 정수로 돌려준다.

네 번째 줄이 다른 종류의 이야기다. 기다림 없이 CPU만 2ms 쓰는 일이면 일꾼은 코어 수만큼만 의미가 있다. 4코어에 스레드를 1,000개 띄워도 상한은 그대로 2,000건이다. 이때는 동시성 모델보다 언어의 실행 속도가 직접 효과를 낸다. 이미지 리사이즈, 압축, 암호화, 큰 JSON 변환처럼 CPU가 주인공인 일에서는 언어의 실행 방식이 직접 숫자로 나온다.

얼마나 차이 나는지 보려고 200만 아래의 소수를 나눗셈으로 세는 같은 반복문을 다섯 언어로 짜서 시작부터 끝까지 시간을 쟀다. 서버 없이 프로세스 하나를 띄우고 끝내는 시간이라 시작 비용도 들어 있다.

```bash
# 같은 이중 반복문(소수 세기)을 언어별로 실행하고 걸린 시간을 잰다
for c in "node primes.mjs" "./gprimes" "java -cp . Primes" "./rprimes" "python3 primes.py"; do
  s=$(date +%s%N); out=$($c | tail -1); e=$(date +%s%N)
  echo "$c -> $out  $(( (e-s)/1000000 ))ms"
done
```

```text
./gprimes -> 148933  586ms

./rprimes -> 148933  319ms
python3 primes.py -> 148933  11140ms
```

러스트(`rustc -O`), Node, 자바, Go가 0.3~0.6초 사이에 모였고 파이썬만 11초로 약 30배 느렸다. Node와 자바는 JIT가 반복문을 기계어로 바꿔서 미리 컴파일한 언어와 같은 자릿수에 들어갔다. Go가 Node보다 느리게 나온 건 Go의 `int`가 64비트라 나눗셈이 32비트(러스트 예제의 `u32`)보다 비싼 영향이 크다. 이런 마이크로벤치마크는 정수 폭 하나로도 순서가 바뀌니 순위로 읽지 않는다. 읽을 것은 하나다. 인터프리터로 도는 파이썬 반복문만 자릿수가 다르다. 그래서 파이썬 생태계는 무거운 계산을 NumPy나 C 확장처럼 파이썬 밖으로 보낸다.

## async 안에서 막는 한 줄

위 표에 넣지 않은 줄이 하나 더 있다. 파이썬 핸들러에서 `await asyncio.sleep(0.05)` 대신 실수로 `time.sleep(0.05)`를 쓴 경우다. 결과가 너무 나빠서 요청 수를 600개로 줄여 돌렸다.

```text
python-block   start= 194ms idleRSS= 28712KB peakRSS= 30552KB threads=   1 rps=   19.61 p50=10176ms p99=13183ms fail=0
```

초당 19.6건, p50은 10초다. 위 계산기의 세 번째 줄(일꾼 1명, 20건)과 같다. 이벤트 루프 스레드 하나가 `time.sleep` 동안 통째로 잠들어서 다른 199개 요청이 그 뒤에 줄을 섰다. 같은 실수를 Node에서는 `fs.readFileSync`나 큰 `JSON.parse`, `crypto.pbkdf2Sync`로 한다. 코드 리뷰에서는 한 줄짜리라 잘 안 보이고, 증상은 "평소엔 괜찮은데 몰리면 전부 느려진다"로 나온다.

스레드 모델의 자바나 Ruby는 이 실수에 덜 다친다. 막는 호출은 원래 그 모델의 기본이라, 스레드 하나만 잠들고 나머지는 계속 돈다. 대신 풀이 다 차면 앞의 고정 풀 16개처럼 같이 줄을 선다. Go와 가상 스레드는 막는 호출이 들어와도 런타임이 OS 스레드를 하나 더 붙이거나 실행 단위를 떼어 내서 대부분 버틴다. 예외는 있다. 자바 21 가상 스레드는 `synchronized` 블록 안에서 기다리면 OS 스레드에 붙은 채로 남는 pinning이 있었고, JDK 24에서 크게 줄었다. 자세한 건 [JVM 메모리와 스레드 글](/posts/java-jvm-memory-gc)에 있다.

## 메모리는 누가 치우나: GC와 소유권

두 번째 잣대는 메모리 관리다. Java, Go, C#, Node.js(V8), Python, Ruby, PHP는 모두 가비지 컬렉터(GC)가 쓰지 않는 객체를 찾아 치운다. Rust만 GC 없이 컴파일 시점에 정리 시점을 정한다.

GC 언어 사이에도 성격이 다르다. 자바와 C#은 객체가 젊은지 늙었는지로 힙을 나누는 세대별 GC를 쓰고, 힙이 클수록 유리하다. 자바는 G1이 기본이고 짧은 멈춤이 중요하면 ZGC를 고른다. 단, CPU가 2개 미만이거나 메모리가 약 1.8GB보다 작은 컨테이너에서는 JVM이 서버급 머신이 아니라고 보고 Serial GC를 고른다. 작은 Pod에서 자바가 이상하게 멈칫거리면 여기부터 의심한다.

Go의 GC는 세대를 나누지 않고 애플리케이션과 동시에 돌며 멈춤을 아주 짧게 유지하는 쪽을 골랐다. 대신 메모리를 넉넉히 쓰는 경향이 있어서, 컨테이너에서는 Go 1.19부터 있는 `GOMEMLIMIT`로 "이 선 근처에서는 더 자주 치워라"를 알려 준다. 파이썬은 참조 카운팅으로 대부분을 바로 치우고, 순환 참조만 별도 GC가 맡는다.

Rust는 소유권 규칙으로 간다. 값마다 주인이 하나 있고, 주인이 범위를 벗어나면 그 자리에서 메모리가 해제된다. 빌려 쓰는 참조는 컴파일러가 수명을 검사해서, 해제된 메모리를 가리키는 코드는 컴파일되지 않는다. 그래서 GC 멈춤이 없고 메모리 사용량이 예측 가능하다. 그 대가는 학습 곡선과 컴파일 시간이다. 소유권을 처음 배우는 사람은 컴파일러와 한참 싸운다. 디스코드가 읽음 상태(Read States) 서비스를 Go에서 Rust로 옮기며 2분마다 GC 때문에 튀던 지연이 사라졌다고 공개한 사례가 유명한데, 이건 "지연 꼬리가 몇 ms 튀는 게 사업 문제인" 아주 큰 규모의 이야기다. 일반적인 CRUD API에서 GC 멈춤이 병목이 되는 일은 드물다.

## 시작 시간과 메모리 바닥

세 번째 잣대가 생각보다 자주 결정을 뒤집는다. 앞의 측정에서 Go는 67ms에 7.6MB, 자바는 0.6초에 52MB로 떴다. 여기에 스프링 부트를 얹으면 자바는 보통 수 초가 걸리고 메모리 바닥도 수백 MB로 올라간다.

이 차이가 문제 되는 곳은 정해져 있다. 서버리스 함수처럼 요청이 올 때 프로세스를 새로 띄우는 환경에서는 시작 시간이 그대로 첫 요청의 지연이 된다([콜드 스타트 글](/posts/cold-starts)). 트래픽에 따라 Pod를 빠르게 늘려야 하는 오토스케일링에서도 뜨는 데 10초 걸리는 서비스는 급한 순간에 늦게 합류한다. 작은 서비스 수십 개를 띄우는 회사라면 서비스마다 200MB씩 차이 나는 바닥 메모리가 노드 비용으로 쌓인다.

언어 쪽에서도 대응이 있다. 자바는 GraalVM 네이티브 이미지로 미리 컴파일해서 수십 ms 시작이 가능해졌고(대신 리플렉션 설정과 빌드 시간이 든다), JDK의 CDS와 Leyden 계열 작업도 시작 시간을 줄이고 있다. .NET은 Native AOT가 있다. Go는 처음부터 의존성을 다 묶은 정적 바이너리 하나(이 예제는 8.1MB)라 `scratch`나 distroless 이미지에 넣기 쉽다. Node와 파이썬은 런타임이 이미지에 들어가야 해서 이미지가 크고, 시작은 수백 ms 수준이다.

반대로 오래 떠 있는 서비스에서는 시작 시간이 거의 의미가 없다. 한 번 뜨면 몇 주씩 도는 주문 API라면 JIT가 데워진 뒤의 자바·C#이 처리량에서 오히려 유리한 경우가 많다.

## 언어마다 잘 맞는 자리

여기까지의 잣대로 각 언어가 어디서 강한지 정리하면 이렇다. 순위가 아니라 자리다.

Java(와 Kotlin)는 크고 오래 가는 비즈니스 시스템의 기본값이다. 스프링 생태계가 트랜잭션, 보안, 배치, 메시징, 데이터 접근([Spring Data 리포지토리 글](/posts/spring-data-repositories))을 다 갖췄고 사람을 구하기 쉽다. 21부터 가상 스레드로 "스레드 하나에 요청 하나" 코드를 유지하면서 대기 비용을 줄였다. 약점은 시작 시간과 메모리 바닥이다.

Go는 인프라 도구와 네트워크 서비스에서 강하다. 쿠버네티스, 도커, 테라폼, 프로메테우스가 Go다. 정적 바이너리, 빠른 시작, 고루틴 덕에 작고 많은 서비스를 운영하기 쉽다. 언어가 일부러 작아서 팀원이 코드를 비슷하게 쓴다. 대신 추상화 도구가 적어 도메인이 복잡한 비즈니스 로직은 코드가 길어지는 편이다.

Node.js는 프런트엔드와 언어를 공유하는 팀, BFF(화면별 API 조합 계층), 실시간 연결이 많은 서비스에 맞는다. TypeScript로 타입을 프런트와 함께 쓸 수 있다. 배포 스크립트 같은 사내 명령줄 도구도 Node로 많이 만든다([Node.js CLI 글](/posts/nodejs-cli-process)). CPU 무거운 일이 섞이면 이벤트 루프가 막히므로 그 부분은 워커나 다른 서비스로 뺀다.

Python은 데이터·ML과 붙어 있는 서비스에서 대안이 거의 없다. 모델 서빙, 데이터 파이프라인, 사내 도구는 라이브러리가 결정한다. FastAPI 같은 async 프레임워크가 있지만 앞에서 본 것처럼 막는 호출 하나에 크게 다친다. GIL 때문에 한 프로세스에서 파이썬 코드는 한 번에 한 스레드만 돌아서, CPU를 다 쓰려면 워커 프로세스를 여러 개 띄운다. 3.13부터 GIL을 끈 빌드가 실험적으로 나왔지만 기본 빌드는 여전히 GIL이 있다(이 글의 3.13에서 `sys._is_gil_enabled()`는 `True`였다).

Rust는 지연 꼬리와 메모리를 엄격하게 지켜야 하는 곳, 프록시·DB·런타임 같은 시스템 소프트웨어, 다른 언어에 붙이는 고성능 모듈에 맞는다. 일반 CRUD 팀이 첫 언어로 고르기에는 학습 비용이 크다.

C#은 자바와 거의 같은 자리를 차지한다. ASP.NET Core는 처리량이 높은 편이고 async/await를 가장 먼저 대중화한 언어다(C# 5, 2012년). 이미 마이크로소프트 스택(Azure, SQL Server)을 쓰는 회사, 게임 서버(Unity와 언어가 같다)에서 자연스럽다.

PHP는 "요청마다 새로 시작하고 끝나면 다 버리는" 모델이 강점이다. PHP-FPM은 요청 하나를 처리하고 그 요청이 만든 메모리를 통째로 버린다. 메모리 누수가 쌓일 틈이 없고, 한 요청이 망가져도 다음 요청에 영향이 없다. 워드프레스와 라라벨 생태계가 크고 호스팅이 싸다. 대신 요청마다 부트스트랩 비용이 들고 연결 풀 같은 상태를 들고 있기 어려워서, Swoole이나 FrankenPHP처럼 오래 떠 있는 실행 방식도 나왔다.

Ruby는 레일스로 빠르게 제품을 만드는 데 여전히 강하다. 관례가 강해서 적은 코드로 많은 기능이 나온다. GitHub와 Shopify가 큰 레일스 앱을 운영한다. 파이썬처럼 GVL이 있어서 Puma 같은 서버는 프로세스 여러 개와 프로세스당 스레드 몇 개를 섞어 쓴다.

## 언어보다 먼저 정해지는 것들

회의에서 실제로 결정을 가른 건 기술 잣대가 아니었다. 정리하면 순서가 이랬다.

먼저 팀이다. 지금 팀이 깊게 아는 언어가 있고 그 언어로 요구 사항을 못 맞출 이유가 없다면 그걸 쓴다. 새 언어를 들이면 첫 장애 때 아무도 런타임 내부를 모른다. 힙 덤프를 읽을 줄 아는 사람, 고루틴 덤프에서 멈춘 곳을 찾을 줄 아는 사람이 있는지가 생각보다 크다.

다음은 피할 수 없는 라이브러리다. 머신러닝 모델을 직접 돌려야 하면 파이썬, 특정 결제사 SDK가 자바만 제대로 지원하면 자바다. 이 조건 하나가 다른 잣대를 다 이긴다.

그다음 운영 형태다. 서버리스나 공격적인 오토스케일링이면 시작 시간이 중요하고, 서비스가 수십 개면 메모리 바닥이 중요하다. 오래 떠 있는 큰 서비스 몇 개면 둘 다 덜 중요하다.

마지막이 일의 모양이다. 대부분이 DB를 기다리는 I/O 바운드라면 앞의 측정처럼 모델만 맞으면 다 충분하다. CPU가 주인공이거나 지연 꼬리를 ms 단위로 지켜야 하면 그때 Go, Rust, JIT 언어로 좁힌다.

그 정산 서비스는 결국 자바로 갔다. 팀이 스프링을 잘 알았고, 배치와 트랜잭션 요구가 많았고, 한 번 뜨면 오래 도는 서비스였다. 대신 가상 스레드를 켜고 외부 API 호출이 많은 부분에서 스레드 풀 고갈을 걱정하지 않게 했다.

## 현장에서 이 차이를 만나는 순간

언어의 런타임 모델을 알면 장애를 볼 때 첫 질문이 달라진다.

자바 서비스가 몰릴 때만 느려지고 CPU는 한가하다면 스레드 풀이 기다림에 묶였는지부터 본다. `jcmd <pid> Thread.print`로 스레드 덤프를 떠서 요청 스레드가 전부 소켓 읽기에 서 있으면 앞의 고정 풀 16개와 같은 상황이다. 풀을 키우거나 가상 스레드로 가거나 하위 호출에 타임아웃을 건다.

Node나 asyncio 서비스가 몰릴 때 모든 엔드포인트가 함께 느려진다면 이벤트 루프가 막혔는지 본다. Node는 `perf_hooks.monitorEventLoopDelay`로 루프 지연을 재고([Node.js 디버깅과 프로파일링 글](/posts/nodejs-debugging-profiling)), 파이썬은 `PYTHONASYNCIODEBUG=1`이나 `loop.set_debug(True)`로 오래 걸린 콜백을 로그로 남긴다.

Go 서비스의 메모리가 계단처럼 오르기만 하면 GC보다 고루틴 누수를 먼저 의심한다. `/debug/pprof/goroutine`에서 같은 줄에 서 있는 고루틴 수를 센다.

컨테이너에서 OOMKilled가 나는데 언어 쪽 힙 지표는 여유롭다면 힙 밖 메모리(JVM의 메타스페이스와 스레드 스택, Node의 Buffer, 파이썬 C 확장)를 본다. 언어마다 "한도" 설정이 힙만 가리키는 경우가 많다.

## 문법이 아니라 기다림과 정리

언어 비교는 결국 두 질문으로 줄어든다. 요청이 기다리는 동안 무엇을 붙잡고 있나, 그리고 다 쓴 메모리를 누가 언제 치우나. 50ms를 기다리는 API에서는 이 모델만 맞게 쓰면 Go, Node, 자바, 파이썬 모두 이론 상한 근처에 간다. 차이는 막는 호출을 실수했을 때 얼마나 크게 다치는지, 시작 시간과 메모리 바닥이 운영 형태에 맞는지, 그 언어로 장애를 볼 사람이 팀에 있는지에서 난다.

## 면접에서 나올 만한 질문

### 새 서비스의 백엔드 언어를 고른다면 무엇을 기준으로 보나요?

팀의 숙련도와 꼭 써야 하는 라이브러리가 먼저고, 그다음이 운영 형태와 일의 모양이다. 서버리스나 잦은 오토스케일링이면 시작 시간과 메모리 바닥을, CPU가 주인공인 일이면 실행 속도를 본다. I/O 바운드 API라면 동시성 모델을 맞게 쓰는 한 대부분의 언어가 충분해서, 언어 자체보다 장애를 볼 수 있는 사람이 있는지가 더 크다.

### 스레드 기반 서버와 이벤트 루프 서버는 무엇이 다른가요?

스레드 기반은 요청 하나가 OS 스레드 하나를 붙잡고 기다리고, 이벤트 루프는 스레드 하나가 기다림을 등록만 해 두고 다른 요청으로 넘어간다. 앞의 것은 코드가 순서대로 읽히지만 기다리는 요청 수만큼 스레드가 필요하고, 뒤의 것은 가볍지만 CPU를 오래 쓰는 코드 하나가 모든 요청을 멈춘다. 실제로 스레드 16개짜리 풀은 50ms 대기 API에서 초당 320건이 상한이었다.

### 스레드 풀 크기가 처리량을 어떻게 제한하나요?

리틀의 법칙으로 계산한다. 처리량 상한은 일꾼 수를 요청 하나가 일꾼을 붙잡는 시간으로 나눈 값이다. 50ms를 기다리는 요청이면 스레드 하나가 초당 20건, 16개면 320건이다. 그 위로 들어온 요청은 줄을 서서 지연이 늘어나므로, 풀을 키우거나 가상 스레드처럼 기다리는 동안 OS 스레드를 놓아주는 모델로 바꾼다.

### Go의 고루틴과 자바의 가상 스레드는 무엇이 같고 다른가요?

둘 다 런타임이 적은 수의 OS 스레드 위에 많은 실행 단위를 올리는 M:N 모델이고, 기다리는 순간 실행 단위를 떼어 내서 코드를 순서대로 쓰면서도 대기 비용이 싸다. 고루틴은 언어 처음부터 있었고 채널과 함께 설계됐다. 가상 스레드는 기존 `Thread` API와 블로킹 라이브러리를 그대로 쓰게 하려고 나중에 들어와서, `synchronized` 안에서의 pinning 같은 호환성 문제를 버전마다 줄여 왔다.

### async 프레임워크에서 동기 함수를 부르면 어떻게 되나요?

이벤트 루프 스레드가 그 함수가 끝날 때까지 통째로 멈춘다. asyncio 핸들러에서 `time.sleep(0.05)`를 쓰면 동시 200개 연결에서도 초당 약 20건밖에 처리하지 못했고 p50이 10초가 됐다. 막는 라이브러리를 꼭 써야 하면 스레드 풀로 넘기는 `run_in_executor`나 `asyncio.to_thread`를 쓰고, Node에서는 Sync API를 피하고 무거운 계산은 worker_threads로 뺀다.

### GC 언어와 Rust의 메모리 관리는 어떻게 다른가요?

GC 언어는 런타임이 주기적으로 쓰지 않는 객체를 찾아 치우고, 그 대가로 멈춤과 여유 메모리가 든다. Rust는 값마다 주인이 하나 있고 주인이 범위를 벗어나면 그 자리에서 해제되며, 참조의 수명을 컴파일러가 검사한다. 그래서 GC 멈춤이 없고 메모리가 예측 가능하지만 배우기 어렵고 컴파일이 느리다. 지연 꼬리가 사업 문제가 될 만큼 큰 규모가 아니면 GC 멈춤이 병목이 되는 일은 드물다.

### 자바가 시작이 느린 건 왜 문제가 되고 어떻게 줄이나요?

JVM은 클래스를 로딩하고 JIT가 데워지는 시간이 있어서, 서버리스 콜드 스타트나 급한 오토스케일링에서 그 시간이 그대로 지연과 늦은 합류가 된다. 오래 떠 있는 서비스에서는 거의 문제가 안 된다. 줄이려면 GraalVM 네이티브 이미지로 미리 컴파일하거나, CDS로 클래스 메타데이터를 미리 만들어 두거나, 스프링이라면 지연 초기화와 불필요한 자동 구성을 걷어 낸다.

### PHP의 요청마다 새로 시작하는 모델에는 어떤 장점이 있나요?

PHP-FPM은 요청 하나가 끝나면 그 요청이 만든 메모리와 상태를 통째로 버린다. 그래서 메모리 누수가 쌓이지 않고 한 요청의 실수가 다른 요청으로 번지지 않으며, 배포도 파일을 바꾸는 것만으로 된다. 대신 요청마다 부트스트랩 비용이 들고 연결 풀 같은 상태를 들고 있기 어려워, 오래 떠 있는 실행 방식(Swoole, FrankenPHP)이 그 약점을 메운다.
