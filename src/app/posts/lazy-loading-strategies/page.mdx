상품 상세 페이지를 휴대폰으로 열면 첫 화면에는 상품 이름과 사진 한 장, 설명 한 줄이 보인다. 그런데 이 화면을 띄우려고 브라우저는 요청 13개, 613KB를 받고 JS를 649ms 동안 실행한다. 스크롤을 한참 내려야 나오는 영상 플레이어, 매장 지도, 후기 위젯이 첫 로드에 전부 같이 실려 오기 때문이다. 사진은 그 짐들과 대역폭을 나눠 쓰느라 4초가 넘어서야 뜬다.

지연 로딩(lazy loading)은 지금 필요 없는 것을 필요해질 때 받는 기법이다. 말은 쉬운데 실제로 정해야 할 것은 하나다. 언제 받을 것인가. 너무 늦게 받으면 사용자가 빈 칸을 보고, 너무 일찍 받으면 미룬 의미가 없다. 이 글은 같은 상품 페이지를 두 벌 만들어서 무엇을 언제 받을지에 따라 숫자가 어떻게 바뀌는지 잰다.

코드를 청크로 나누는 방법(`import()`, 청크 그래프, 트리 셰이킹)은 [번들 쪼개기](/posts/code-splitting)에서 다뤘다. 여기서는 이미 나뉜 조각을 어느 시점에 부를지를 본다. 데이터 요청을 언제 보낼지는 [데이터 요청 최적화](/posts/data-fetching-optimization)에서, 프런트엔드 성능 전체의 순서는 [프런트엔드 성능 지도](/posts/frontend-performance-map)에서 이어진다.

예제는 React 19 앱을 esbuild로 묶어 작은 Node 서버로 띄웠다. 영상 플레이어는 다른 포트(다른 출처)의 서버가 주는 iframe으로 흉내 냈다. 플레이어 스크립트 470KB, 광고 스크립트 90KB, 포스터 이미지 113KB다. 지도와 후기 위젯은 각각 320KB짜리 라이브러리를 쓴다. 측정은 Playwright로 Chromium 141을 띄우고 왕복 150ms, 내려받기 1.6Mbps, CPU 4배 느리게를 걸어 다섯 번 잰 가운데 값이다.

## 언제 받을지 고르는 네 가지 시점

지연 로딩을 쓴다고 하면 보통 `React.lazy`부터 떠올리는데, 그건 도구이고 결정은 시점이다. 실무에서 쓰는 시점은 대략 네 가지다.

- 즉시: 첫 화면에 보이는 것. 미루면 안 된다.
- 한가할 때: 첫 화면이 다 그려진 뒤 메인 스레드가 놀 때. 분석 스크립트, 다음에 쓸 가능성이 높은 청크.
- 보일 때: 스크롤해서 화면 가까이 오면. 아래쪽 섹션, 이미지, 댓글.
- 누를 때: 사용자가 원할 때만. 모달, 지도, 영상 플레이어, 채팅 위젯.

누를 때와 보일 때는 사용자 행동 뒤에 받으니 기다림이 생긴다. 그래서 한 단계 앞의 신호를 같이 쓴다. 누르기 전에 손가락이 닿거나 포인터가 올라가는 순간, 보이기 전에 화면 근처에 다가오는 순간이다.

## 누를 때 받는 지도

지도 섹션은 "지도 보기" 버튼으로 바꿨다. 버튼을 누르기 전에는 지도 라이브러리를 받지 않는다.

```jsx
import { lazy, Suspense, useState } from "react";

// import 함수를 따로 두면 미리 부르기와 lazy가 같은 Promise를 쓴다
const importMap = () => import("./map-view.jsx");
const MapView = lazy(() => importMap().then((m) => ({ default: m.MapView })));

function MapSection() {
  const [open, setOpen] = useState(false);
  if (!open)
    return (
      <button onPointerEnter={importMap} onFocus={importMap} onClick={() => setOpen(true)} style={{ height: 240 }}>
        지도 보기
      </button>
    );
  return (
    <Suspense fallback={<div style={{ height: 240 }}>지도 불러오는 중</div>}>
      <MapView />
    </Suspense>
  );
}
```

`lazy`에 넘기는 함수를 바깥으로 꺼내 둔 게 요점이다. 브라우저는 같은 모듈 주소의 `import()`를 한 번만 받고, 두 번째 호출부터는 이미 받은 모듈(또는 진행 중인 Promise)을 돌려준다. 그래서 포인터가 올라갔을 때 `importMap()`을 한 번 불러 두면, 클릭 뒤 `lazy`가 같은 함수를 부를 때 이미 받는 중이거나 받아 둔 상태다. 아래 표현을 조각내 보면 각 부분이 하는 일이 보인다.

같은 조건에서 버튼을 누른 순간부터 지도가 그려질 때까지를 다섯 번씩 쟀다. 미리 부르는 쪽은 포인터를 올리고 300ms 뒤에 눌렀다.

```text
map hover=false 953,965,956,973,942 med 956
map hover=true 579,615,627,573,583 med 583
```

포인터를 올리고 누르기까지의 300ms 동안 청크가 먼저 출발해서 기다림이 373ms 줄었다. 줄어드는 양은 사용자가 포인터를 올린 채 머뭇거리는 시간만큼이라, 고민하며 누르는 버튼일수록 효과가 크다.

휴대폰에는 포인터를 올리는 동작이 없다. `pointerenter`는 터치에서도 손가락이 닿는 순간 발생하지만 `click`과의 간격이 탭 한 번 길이뿐이라 얻는 게 적다. 터치 화면에서는 버튼이 화면에 들어왔을 때 미리 부르거나, 첫 화면이 다 그려진 뒤 한가할 때 부르는 쪽이 낫다.

클릭 뒤에 청크를 받는 구조는 배포 직후 옛 청크가 사라져 `ChunkLoadError`가 나는 문제를 안고 있다. 사용자가 버튼을 누른 순간 실패하니 체감이 크다. 재시도와 새로고침으로 다루는 방법은 [번들 쪼개기의 청크 에러 부분](/posts/code-splitting)에 있다.

## 보일 때 받는 후기

후기 섹션은 페이지 맨 아래, 스크롤을 3,000px쯤 내려야 나온다. 화면 가까이 오면 그때 컴포넌트를 받는다.

```jsx
function WhenVisible({ children, height }) {
  const ref = useRef(null);
  const [show, setShow] = useState(false);
  useEffect(() => {
    const io = new IntersectionObserver(
      ([e]) => {
        if (e.isIntersecting) {
          setShow(true);
          io.disconnect(); // 한 번 보였으면 더 볼 필요가 없다
        }
      },
      { rootMargin: "300px" }, // 화면 아래 300px 전부터 보인 것으로 친다
    );
    io.observe(ref.current);
    return () => io.disconnect();
  }, []);
  return <div ref={ref} style={{ minHeight: height }}>{show ? <Suspense fallback={null}>{children}</Suspense> : null}</div>;
}

<WhenVisible height={400}><Comments /></WhenVisible>
```

`minHeight`를 주는 이유는 두 가지다. 빈 `div`의 높이가 0이면 위쪽 내용이 길어질 때 관찰 대상의 위치가 계속 바뀌고, 나중에 후기가 들어오며 아래 내용을 밀어 CLS가 생긴다. IntersectionObserver가 콜백을 언제 부르는지, threshold가 왜 정확하지 않은지는 [IntersectionObserver 글](/posts/scroll-triggered-intersection-observer)에 정리했다.

`rootMargin`이 얼마나 앞서 받을지를 정한다. 아래 그림은 화면(포인터)이 아래로 내려가며 섹션을 지날 때 무엇이 로드 목록에 들어가는지 보여 준다. 화면은 844px, 여유는 300px로 잡았다.

1000px을 줘도 300ms 넘게 빈 칸이 보였다. 이 망에서는 80KB 청크 하나 받고 실행하는 데 0.8초가 넘는데, 1초에 1,800px씩 내리는 사용자에게 1000px은 0.5초 거리다. 여유를 무작정 키우면 결국 즉시 받는 것과 같아지니, 빈 칸이 잠깐 보일 수 있다는 걸 받아들이고 그 자리를 스켈레톤으로 채우는 게 현실적이다. 아래 그림이 그 모습이다. 내려가면 회색 자리가 먼저 서 있다가 내용이 들어온다.

이미지는 이 관찰자를 직접 쓰지 않아도 된다. `<img loading="lazy">`와 `<iframe loading="lazy">`는 브라우저가 같은 일을 대신 하고, 얼마나 앞서 받을지도 브라우저가 망 상태를 보고 정한다. 크롬 계열 문서는 빠른 망에서 1,250px, 느린 망에서 2,500px 앞에서 받기 시작한다고 설명한다. 이미지 쪽 세부는 [이미지 최적화](/posts/image-optimization)에서 다룬다.

## 영상 플레이어는 껍데기만 먼저

서드파티 임베드(영상, 지도, SNS 게시물, 채팅 위젯)는 지연 로딩 효과가 가장 큰 곳이다. 우리 번들이 아니라서 크기를 줄일 수도 없고, iframe 하나가 자기 문서와 스크립트, 이미지, 광고를 줄줄이 받는다. 예제에서 영상 iframe 하나가 첫 로드의 278KB를 차지했다.

그래서 처음에는 진짜 플레이어 대신 겉모습만 같은 가벼운 버튼을 둔다. 썸네일 이미지 위에 재생 아이콘을 얹은 것이다. 누르면 그때 진짜 iframe으로 바꾼다. 이 껍데기를 파사드(facade)라고 부른다. 영상 서비스용으로 `lite-youtube-embed` 같은 라이브러리가 이 방식을 쓴다.

```jsx
function VideoFacade() {
  const [on, setOn] = useState(false);
  if (on)
    return <iframe src="https://player.example/embed?autoplay=1" title="제품 영상" allow="autoplay" width="100%" height="220" />;
  return (
    <button onClick={() => setOn(true)} aria-label="제품 영상 재생" style={{ width: "100%", height: 220, background: "url(/thumb.jpg) center/cover" }}>
      ▶
    </button>
  );
}
```

누른 뒤 1.8초가 걸린다는 건 공짜가 아니라는 뜻이다. 대부분이 영상을 본다면(영상이 페이지의 주인공이라면) 파사드는 오히려 손해다. 몇 가지를 더 챙긴다.

- 클릭 뒤 iframe의 자동 재생이 막힐 수 있다. 모바일 브라우저와 플레이어마다 자동 재생 정책이 달라서, 파사드를 누르고 플레이어에서 한 번 더 눌러야 하는 경우가 있다. 실제 대상 기기에서 확인해야 한다.
- 버튼에는 `aria-label`로 무엇을 재생하는지 적는다. 썸네일 배경 이미지만으로는 화면 낭독기가 아무것도 읽지 못한다.
- 누른 직후 바로 iframe의 높이가 같아야 한다. 파사드와 iframe의 크기가 다르면 그 자리에서 레이아웃이 밀린다.

파사드까지 만들 여력이 없으면 `<iframe loading="lazy">`만으로도 화면 아래 임베드는 미룰 수 있다. 다만 화면에 들어오는 순간 전체 비용을 다 치르니, 첫 화면 근처에 있는 임베드에는 효과가 없다. 채팅 위젯처럼 iframe이 아니라 스크립트 태그로 붙는 것은 첫 상호작용(스크롤, 터치)이나 한가한 시점에 `<script>`를 만들어 넣는다. Next.js의 `next/script`는 `strategy="lazyOnload"`로 같은 일을 해 준다.

## 스크립트로 붙는 서드파티는 strategy로 순서를 정한다

분석 도구, 태그 매니저, 채팅, 결제 위젯은 대개 `<script src>` 한 줄로 붙는다. HTML에 그냥 넣으면 `async`나 `defer`를 붙였는지에 따라 파싱을 막거나 우리 하이드레이션과 메인 스레드를 다툰다. Next.js의 `next/script`는 이 시점을 `strategy` 하나로 고르게 한다. 같은 레이아웃 안에서 페이지를 옮겨 다녀도 스크립트를 한 번만 넣어 준다는 점도 직접 `<script>`를 쓸 때와 다르다. 아래는 Next.js 16 문서 기준이다.

```tsx
import Script from "next/script";

// app/layout.tsx 안
<Script src="https://consent.example/cmp.js" strategy="beforeInteractive" />   {/* 동의 관리: 무엇보다 먼저 */}
<Script src="https://analytics.example/a.js" />                                {/* 기본값 afterInteractive */}
<Script src="https://chat.example/widget.js" strategy="lazyOnload" />           {/* 채팅: 한가할 때 */}
```

`beforeInteractive`는 서버가 내려 주는 첫 HTML의 `head`에 들어가 Next.js의 어떤 코드보다 먼저 받는다. 실행이 하이드레이션을 막지는 않지만 대역폭은 가장 먼저 쓴다. 그래서 루트 레이아웃에만 둘 수 있고, 다른 스크립트보다 먼저 돌아야 하는 것(쿠키 동의 관리자, 봇 탐지)에만 쓴다. 기본값인 `afterInteractive`는 페이지가 어느 정도 하이드레이션된 뒤에 넣는다. 태그 매니저나 분석처럼 일찍 돌면 좋지만 첫 화면을 막으면 안 되는 것이 여기다. `lazyOnload`는 페이지의 다른 리소스를 다 받은 뒤 브라우저가 한가할 때 넣는다. 채팅, 소셜 버튼, 설문 위젯처럼 늦게 떠도 되는 것을 둔다. `worker`는 Partytown으로 스크립트를 웹 워커에서 돌려 메인 스레드를 비우는 실험 기능인데, 아직 App Router에서는 동작하지 않고 DOM을 많이 만지는 스크립트는 워커에서 제대로 돌지 않는다.

흔한 실수는 미뤄 둔 스크립트의 전역 함수를 바로 부르는 것이다. `lazyOnload`로 넣은 채팅 위젯의 `window.Chat.open()`을 버튼 핸들러에서 부르면, 사용자가 빨리 누를 때 아직 없는 함수라 터진다. 받은 뒤에 할 일은 `onLoad`(처음 한 번)나 `onReady`(처음 받은 뒤, 그리고 컴포넌트가 다시 마운트될 때마다)에 두고, 두 콜백은 클라이언트 컴포넌트에서만 쓸 수 있다. 버튼은 준비되기 전까지 비활성으로 두거나, 누르는 순간 스크립트를 받기 시작하는 파사드로 만든다.

자주 쓰는 구글 서비스는 `@next/third-parties`가 이런 판단을 묶어 둔 컴포넌트를 준다. `GoogleTagManager`와 `GoogleAnalytics`는 하이드레이션 뒤에 스크립트를 넣고, `YouTubeEmbed`는 앞에서 본 `lite-youtube-embed` 파사드를 쓰며, `GoogleMapsEmbed`는 기본으로 `loading="lazy"`를 단다. 패키지 자체는 아직 실험 단계라고 문서에 적혀 있으니, 버전을 고정하고 올릴 때 바뀐 점을 확인한다. 직접 호스팅하는 동영상이라면 iframe이 아니라 `<video>`다. 첫 화면 아래의 영상은 `preload="none"`에 가벼운 `poster`를 붙여 누르기 전까지 영상 바이트를 받지 않게 하고, 크기를 미리 잡아 CLS를 막는다. `preload` 값마다 실제로 나가는 요청은 [HTML 미디어와 임베드](/posts/html-media-embed)에서 확인했다.

## 둘을 나란히 놓으면

영상은 파사드로, 지도는 누를 때, 후기는 보일 때로 바꾼 두 번째 버전을 처음 버전과 같은 조건에서 쟀다. 페이지를 연 뒤 5초 동안 사용자는 아무것도 하지 않았다.

| 측정 (가운데 값) | 모두 즉시 | 시점별로 미룸 |
|---|---|---|
| 요청 수 | 13 | 8 |
| 전송량 | 613KB | 196KB |
| FCP | 2164ms | 1096ms |
| LCP | 4148ms | 1848ms |
| JS 실행 시간 (ScriptDuration) | 649ms | 153ms |
| 긴 작업의 50ms 초과분 합 | 505ms | 77ms |
| 가장 긴 작업 | 356ms | 111ms |

FCP가 1초 빨라진 건 첫 화면을 그리기 전에 받고 실행하던 라이브러리 두 개가 빠져서다. 정적 import는 가져온 모듈을 모두 받아서 평가해야 앱 코드가 시작되니, 160KB를 받는 시간과 두 라이브러리의 초기화 코드가 첫 렌더링 앞을 막고 있었다. LCP가 2.3초 줄어든 건 사진이 더 이상 다른 파일과 회선을 나누지 않아서다. 지연 로딩이 "덜 실행하기"와 "중요한 것에 대역폭 몰아주기"를 함께 해 준 것이다.

## 하이드레이션을 미루면 무엇이 줄어드나

서버에서 HTML을 다 그려 보내는 페이지도 같은 고민이 있다. HTML은 이미 보이지만 브라우저가 그 위에 이벤트를 붙이는 [하이드레이션](/posts/hydration)은 JS로 한다. 화면 아래의 후기 목록 3,000줄까지 처음부터 하이드레이션할 필요는 없다. 서버 HTML은 그대로 두고, 후기 영역만 화면 가까이 왔을 때 살린다.

```jsx
hydrateRoot(document.getElementById("hero"), <HeroBox />);

const el = document.getElementById("rev");
const io = new IntersectionObserver(async ([e]) => {
  if (!e.isIntersecting) return;
  io.disconnect();
  const { Reviews } = await import("./hyd-parts.jsx");
  hydrateRoot(el, <Reviews />); // 이때 처음으로 후기 목록에 이벤트가 붙는다
}, { rootMargin: "400px" });
io.observe(el);
```

한 번에 둘 다 하이드레이션하는 버전과 비교했다. HTML은 175KB, 후기 `li`가 3,000개다.

```text
all  median fcp=352 hero=1196 blocking=429 longest=166 script=239
lazy median fcp=404 hero=1276 blocking=395 longest=207 script=113
```

JS 실행 시간은 239ms에서 113ms로 절반이 됐다. 그런데 긴 작업의 합(blocking)은 429ms와 395ms로 거의 같다. 긴 작업 대부분이 스크립트가 아니라 175KB HTML을 파싱하고 3,000줄의 스타일과 레이아웃을 계산하는 시간이었기 때문이다. 하이드레이션을 미루면 JS 일은 줄지만 DOM 자체가 큰 비용은 그대로 남는다. 그건 DOM을 줄이거나 `content-visibility`로 화면 밖 렌더링을 건너뛰는 쪽의 일이고, [렌더링 성능 최적화](/posts/rendering-performance-optimization)에서 다룬다.

영역마다 따로 살리는 방식을 프레임워크 차원으로 끌어올린 것이 Astro의 아일랜드다. `client:visible`, `client:idle` 같은 지시어가 위 코드와 같은 일을 한다. 아예 하이드레이션을 하지 않는 재개 가능성까지 포함한 비교는 [아일랜드와 재개 가능성](/posts/islands-resumability)에 있다.

## 첫 화면에 있는 것은 미루지 않는다

지연 로딩을 처음 도입하면 "다 lazy로 바꾸면 더 빠르겠지" 하는 유혹이 생긴다. 첫 화면 히어로 컴포넌트를 `React.lazy`로 자른 버전과 히어로 이미지에 `loading="lazy"`를 단 버전을 만들어 쟀다.

```text
                                   FCP     LCP
hero (그냥 import)                 1012ms  1740ms
lazyhero (히어로를 React.lazy로)   1352ms  2068ms

static-eager (HTML의 img)           604ms  1048ms
static-lazy  (img loading=lazy)     516ms  1280ms
```

히어로를 자르면 앱 코드를 실행한 뒤에야 히어로 청크를 요청하니 왕복 하나와 실행 한 번이 그대로 더해져 LCP가 328ms 늦어졌다. HTML에 직접 쓴 이미지에 `loading="lazy"`를 달면 232ms 늦어졌다. 브라우저의 프리로드 스캐너는 HTML을 훑으며 이미지를 미리 요청하는데, `lazy`가 붙은 이미지는 레이아웃을 계산해서 화면 안에 있는지 확인한 뒤에야 요청한다. 레이아웃은 CSS가 다 와야 할 수 있으니 그만큼 밀린다. `static-lazy`의 FCP가 오히려 빠른 건 이미지가 CSS와 대역폭을 다투지 않아서다. 첫 페인트는 조금 이르지만 정작 사용자가 기다리는 사진은 늦다.

[Core Web Vitals 글](/posts/core-web-vitals)에서 LCP를 네 조각으로 나눴을 때 "리소스 로드 지연"이 바로 이 구간이다. 첫 화면의 LCP 후보는 지연 로딩의 반대편에 둔다. `loading="lazy"`를 빼고 필요하면 `fetchpriority="high"`를 준다. 우선순위 힌트는 [리소스 힌트](/posts/resource-hints-loading)에서 이어진다.

어디까지가 첫 화면인지는 기기마다 다르다는 점도 함정이다. 390px 휴대폰에서 두 번째 화면인 카드가 1280px 데스크톱에서는 첫 화면에 있다. 목록의 앞 몇 개(보통 첫 줄)는 즉시, 나머지는 lazy로 나누는 게 흔한 절충이다.

## 미루고 나서 새로 생기는 문제

지연 로딩은 받는 시점을 옮길 뿐이라 옮긴 자리에서 문제가 생긴다. 현장에서 자주 만나는 것들이다.

자리를 비워 두면 화면이 밀린다. fallback이나 관찰 대상에 높이가 없으면 내용이 도착할 때 아래가 밀려 CLS가 오른다. 실제 컴포넌트와 같은 높이를 주거나 `aspect-ratio`로 비율을 잡는다.

안 받은 내용은 찾을 수 없다. 화면에 없던 후기는 브라우저의 페이지 내 찾기(Ctrl+F)에 걸리지 않는다. 검색엔진 크롤러도 스크롤을 하지 않으니, 보일 때 받는 방식으로만 존재하는 본문은 색인에 안 들어갈 수 있다. 구글은 렌더링할 때 긴 뷰포트를 써서 IntersectionObserver 기반 로딩은 대체로 처리한다고 안내하지만, 스크롤 이벤트에만 반응하는 코드는 실행되지 않는다. 검색에 걸려야 하는 본문은 서버 HTML에 넣는다.

lazy 안의 lazy는 폭포가 된다. 지연 로딩된 컴포넌트가 다시 다른 lazy 컴포넌트를 품으면, 첫 청크를 받고 실행해야 두 번째 청크 요청이 나간다. 누를 때 한 번 기다릴 일을 두 번 기다리게 된다. 함께 쓰이는 조각은 같은 청크로 묶거나 바깥 청크를 받을 때 안쪽도 같이 부른다.

데이터는 따로 늦는다. 컴포넌트 청크를 받은 뒤 그 컴포넌트가 마운트되어 API를 부르면 코드 → 데이터 순으로 일렬이 된다. 청크와 데이터 요청을 같은 신호에서 함께 출발시키는 방법은 [데이터 요청 최적화](/posts/data-fetching-optimization)에서 잰다.

## 현장에서 지연 로딩을 점검하는 순서

"페이지가 무겁다"는 말을 들었을 때 미룰 후보를 찾는 순서다.

1. 개발자 도구의 Coverage 탭(Ctrl+Shift+P → Show Coverage)을 켜고 새로고침한다. 첫 로드 뒤 사용되지 않은 바이트 비율이 큰 JS 파일이 미룰 후보다.
2. Network 탭에서 Initiator 열을 켜고, 첫 로드에 나간 요청을 출처별로 본다. 다른 도메인에서 오는 스크립트와 iframe은 파사드나 상호작용 뒤 로딩 후보다.
3. Performance 탭에서 첫 화면이 그려지기 전의 긴 작업을 찾고, 어떤 모듈의 평가 코드인지 본다. 정적 import된 라이브러리의 초기화가 자주 보인다.
4. 바꾼 뒤에는 같은 조건(망 제한, CPU 제한)에서 LCP와 긴 작업을 다시 재고, 미룬 기능을 실제로 눌러 기다림이 얼마인지도 잰다. 첫 로드만 재고 끝내면 비용을 클릭 뒤로 옮긴 사실을 놓친다.

사용자 브라우저에서 미룬 청크가 실제로 얼마나 늦게 오는지 보고 싶다면 리소스 타이밍을 모으면 된다.

```js
// 청크 파일이 언제 요청되고 언제 끝났는지 모은다
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    if (e.initiatorType === "script" || e.name.includes("/chunk-")) {
      console.log(e.name.split("/").pop(), Math.round(e.startTime), Math.round(e.responseEnd));
    }
  }
}).observe({ type: "resource", buffered: true });
```

## 다시 613KB로

처음 페이지가 무거웠던 건 코드가 커서라기보다 모든 것이 같은 순간에 출발해서였다. 영상은 누를 때, 지도는 닿을 때 미리, 후기는 다가올 때로 시점을 나누자 첫 로드는 196KB가 되고 LCP는 4.1초에서 1.8초가 됐다. 대신 누른 뒤의 기다림이 생겼고, 그걸 줄이려고 한 단계 이른 신호를 붙였다. 지연 로딩은 이 기다림을 어디에 둘지 고르는 일이고, 첫 화면에 보이는 것만은 그 대상이 아니다.

## 면접에서 나올 만한 질문

### 지연 로딩은 무엇을 줄이나요?

첫 로드에 받고 실행하는 양을 줄인다. 지금 쓰지 않는 코드와 리소스를 빼면 첫 화면에 필요한 파일이 대역폭을 독차지하고, 메인 스레드도 첫 렌더링 전에 덜 일한다. 예제에서는 전송량이 613KB에서 196KB, JS 실행이 649ms에서 153ms로 줄었고 LCP가 2.3초 빨라졌다.

### React.lazy로 자른 컴포넌트를 누를 때마다 늦게 뜨는데 어떻게 줄이나요?

누르기 직전의 신호에서 미리 부른다. `import()` 함수를 바깥에 두고 `pointerenter`나 `focus`에서 한 번 불러 두면, 같은 모듈 주소는 한 번만 받으니 클릭 뒤 `lazy`가 그 결과를 그대로 쓴다. 예제에서 포인터를 올리고 300ms 뒤 누르니 956ms가 583ms로 줄었다. 터치 화면에는 호버가 없으니 화면에 들어올 때나 한가할 때 미리 부른다.

### 첫 화면 이미지에 loading="lazy"를 달면 왜 느려지나요?

브라우저가 그 이미지를 레이아웃이 끝난 뒤에야 요청하기 때문이다. 일반 이미지는 프리로드 스캐너가 HTML을 훑을 때 바로 요청하는데, lazy 이미지는 화면 안에 있는지 계산해야 해서 CSS를 다 받은 뒤로 밀린다. 예제에서 LCP가 1048ms에서 1280ms로 늦어졌다. LCP 후보는 lazy를 빼고 필요하면 `fetchpriority="high"`를 준다.

### 서드파티 임베드는 어떻게 미루나요?

파사드를 둔다. 진짜 플레이어 대신 썸네일과 재생 버튼만 그려 두고, 누르면 iframe으로 바꾼다. 영상을 보지 않는 사용자는 플레이어 비용을 아예 내지 않지만, 누른 사용자는 그 비용을 클릭 뒤에 치른다(예제에서 1.8초). 영상이 페이지의 주인공이면 오히려 손해이고, 모바일 자동 재생 정책 때문에 한 번 더 눌러야 할 수도 있다.

### IntersectionObserver의 rootMargin은 얼마로 잡나요?

받는 데 걸리는 시간과 스크롤 속도를 곱한 거리만큼이 기준이다. 느린 망에서 0.8초 걸리는 청크라면 빠르게 훑는 사용자에게는 1000px도 부족했다. 여유를 끝없이 키우면 즉시 받는 것과 같아지니 수백 px 정도로 두고, 그 자리에 높이를 잡은 스켈레톤을 둬서 잠깐 비는 순간을 덜 어색하게 만든다.

### 하이드레이션을 미루면 TBT가 줄어드나요?

JS 실행 몫만 준다. 예제에서 화면 아래 3,000줄 목록의 하이드레이션을 미루니 스크립트 시간은 239ms에서 113ms가 됐지만 긴 작업 합은 429ms와 395ms로 비슷했다. 긴 작업 대부분이 큰 HTML의 파싱과 스타일·레이아웃이었기 때문이다. DOM이 크면 하이드레이션 지연과 별개로 DOM을 줄이거나 화면 밖 렌더링을 건너뛰어야 한다.

### 지연 로딩 때문에 생길 수 있는 부작용은요?

자리를 안 잡으면 CLS가 오르고, 안 받은 본문은 페이지 내 찾기와 크롤러에 안 잡힐 수 있다. lazy 컴포넌트 안에 또 lazy가 있으면 청크 요청이 일렬로 서고, 청크를 받은 뒤 데이터를 부르면 코드와 데이터가 또 일렬이 된다. 배포 직후 옛 청크가 사라지면 클릭 순간 `ChunkLoadError`가 나니 재시도와 새로고침 처리가 필요하다.
