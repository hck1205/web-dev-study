단위 테스트와 통합 테스트는 모두 초록불이었다. 스테이징에도 올려 봤다. 그런데 현장 영업 담당자가 인수 테스트 화면에서 할인 쿠폰을 쓴 주문을 하나 넣고 회계 시스템(ERP)을 열어 보더니 말한다. "여기 금액이 할인 전 금액인데요." 우리 테스트는 ERP 연동 부분을 가짜로 바꿔 끼웠고, 가짜는 우리가 보낸 금액을 그대로 받아 줬다. 진짜 ERP는 할인을 별도 줄로 받아야 했다.

여러 시스템이 함께 일하는 업무에서는, 각 시스템이 혼자 맞는 것과 함께 맞는 것이 다르다. 그리고 함께 맞는 것과 업무 담당자가 "이대로 써도 된다"고 말하는 것도 다르다. 앞의 것을 확인하는 단계가 SIT(System Integration Testing, 시스템 통합 테스트), 뒤의 것이 UAT(User Acceptance Testing, 사용자 인수 테스트)다. 이 글은 두 단계가 무엇을 확인하는지, 어떤 환경과 데이터에서 하는지, 언제 시작하고 언제 끝났다고 말하는지를 본다. 실습 코드는 Node 22.22.0으로 돌렸다.

이 주제의 다른 글: [벤더·레거시 시스템 연동](/posts/enterprise-system-integration), [새 나라에 서비스를 열 때](/posts/global-rollout-localization), [컷오버와 하이퍼케어](/posts/release-cutover-hypercare). 개발자가 쓰는 테스트는 [테스트 피라미드와 단위 테스트](/posts/test-pyramid-unit-tests), [진짜 DB로 하는 통합 테스트](/posts/integration-tests-real-db)에서 다뤘다.

## 개발자의 통합 테스트와 SIT는 범위가 다르다

이름이 비슷해서 헷갈린다. 개발자가 말하는 통합 테스트는 우리 서비스 하나를 진짜 DB, 진짜 HTTP 서버와 묶어서 확인한다. 바깥 시스템은 가짜로 바꾼다. SIT는 그 가짜를 걷어 낸다. 주문 서비스, ERP, 물류 벤더, 고객 관리 시스템을 실제 버전으로 연결해 업무 흐름 하나를 끝까지 흘려 본다. 처음 이야기의 할인 금액 버그는 가짜를 쓴 테스트에서는 잡힐 수 없고 SIT에서 잡혀야 했다.

UAT는 질문이 또 다르다. SIT가 "시스템들이 약속대로 주고받나"를 묻는다면, UAT는 "이게 우리 업무에 맞나"를 묻는다. 그래서 테스트하는 사람이 개발·QA가 아니라 그 시스템을 실제로 쓸 업무 담당자다. 요구 사항 문서대로 동작해도, 매장 직원이 하루에 수백 번 누르는 버튼이 세 번 클릭 깊이에 있으면 UAT에서 막힌다.

## 환경은 줄을 서서 올라간다

SIT와 UAT는 각자 환경을 따로 두는 경우가 많다. 흔한 줄은 개발(dev), SIT, UAT, 스테이징(staging), 운영(prod)이다. 회사마다 스테이징과 UAT를 합치기도 하고, 이름을 QA, pre-prod로 부르기도 한다. 이름보다 중요한 건 각 환경에서 무엇이 진짜이고 무엇이 가짜인지를 표로 적어 두는 일이다.

환경을 운영할 때 반복해서 터지는 문제는 셋이다.

첫째, 환경이 어긋난다(environment drift). SIT의 DB 스키마가 한 버전 늦고, UAT의 설정 파일 하나가 손으로 고쳐져 있다. 그러면 UAT에서 나온 버그가 운영에서는 안 나오거나, 그 반대가 된다. 환경을 코드로 만들고(IaC), 배포 파이프라인이 모든 환경에 같은 방법으로 배포하게 하면 대부분 사라진다.

둘째, 환경을 여러 팀이 같이 쓴다. SIT 하나에 세 팀이 각자 다른 브랜치를 올리면, 오전에 통과한 시나리오가 오후에 깨진다. 누가 언제 무엇을 올렸는지 보이는 배포 기록과, UAT 기간에는 그 환경에 배포를 멈추는 규칙(환경 동결)을 둔다.

셋째, 벤더 샌드박스가 불안정하다. 샌드박스는 벤더에게 운영만큼 중요하지 않아서 자주 내려가거나 데이터가 초기화된다. SIT 일정표에 벤더 샌드박스 점검 시간을 넣고, 샌드박스가 죽은 동안 돌릴 수 있는 시나리오와 없는 시나리오를 나눠 둔다.

## 테스트 데이터는 운영처럼, 개인정보는 빼고

SIT와 UAT는 운영과 닮은 데이터가 필요하다. 할인 규칙, 여러 매장, 반품이 섞인 주문, 오래된 고객의 이상한 주소 같은 것들이 운영 데이터에만 있다. 그래서 운영 데이터를 복사해 쓰고 싶어지는데, 그대로 복사하면 개인정보가 하위 환경으로 퍼진다. 하위 환경은 접근 권한이 넓고, 벤더 샌드박스로도 흘러간다.

선택지는 크게 둘이다. 처음부터 가짜 데이터를 만드는 합성 데이터와, 운영 데이터를 복사하되 개인정보를 바꾸는 마스킹이다. 여러 시스템이 엮인 SIT에서는 마스킹에 조건이 하나 붙는다. 같은 고객은 모든 시스템에서 같은 가짜 값이 되어야 한다. CRM에서 홍길동이 `user_aaa`가 되고 ERP에서는 `user_bbb`가 되면, 두 시스템을 잇는 시나리오가 전부 깨진다.

그래서 무작위 대신 키가 있는 해시(HMAC)로 결정적으로 바꾼다. 같은 입력과 같은 키면 언제나 같은 결과가 나온다.

```js
import { createHmac } from "node:crypto";
const SECRET = "sit-2026-q4"; // 환경마다 다르게, 운영 키와 분리
const h = (v) => createHmac("sha256", SECRET).update(v).digest();
const maskEmail = (e) => `user_${h(e.toLowerCase()).toString("hex").slice(0, 10)}@example.test`;
const maskPhone = (p) => {
  const tail = String(h(p.replace(/\D/g, "")).readUInt32BE(0) % 1e8).padStart(8, "0");
  return `010-${tail.slice(0, 4)}-${tail.slice(4)}`;   // 형식은 지킨다
};
const maskName = (n) => ["김", "이", "박", "최", "정"][h(n)[0] % 5] + "테스트" + (h(n)[1] % 90 + 10);

const crm = [{ id: "C-77", name: "홍길동", email: "Gildong.Hong@mail.kr", phone: "010-9876-5432" }];
const erp = [{ cust_email: "gildong.hong@mail.kr", order: "SO-501", amount: 45990000 }];
```

```text
crm C-77 박테스트25 user_8ba7004b47@example.test 010-8717-3964
erp SO-501 user_8ba7004b47@example.test 45990000
random  crm: user_33f5943a38@example.test erp: user_b6afe2b17d@example.test
```

CRM에는 `Gildong.Hong@`으로, ERP에는 소문자로 저장돼 있었지만 마스킹 전에 소문자로 맞췄기 때문에 두 시스템 모두 `user_8ba7004b47@example.test`가 됐다. 마지막 줄의 무작위 방식은 두 값이 달라 연결이 끊긴다. 전화번호는 `010-XXXX-XXXX` 형식을 지켜서 형식 검증을 하는 화면이 그대로 돈다. 도메인을 `example.test`로 둔 것도 일부러다. 실수로 메일을 보내도 실제 사람에게 닿지 않는다.

조심할 점이 있다. 키가 새면 해시는 되돌리기 쉽다. 전화번호는 경우의 수가 1억 개 남짓이라 키를 알면 전부 대입해 볼 수 있다. 키는 운영 비밀 저장소에 두고 환경마다 다르게 쓴다. 그리고 마스킹은 이름·이메일·전화번호만이 아니다. 자유 입력 칸(배송 메모, 상담 기록)에 사람들이 전화번호와 주소를 적어 넣는다. 이 칸은 통째로 지우거나 고정 문구로 바꾸는 편이 안전하다. 운영 데이터를 하위 환경에 써도 되는지, 어떤 처리를 해야 하는지는 회사의 개인정보 정책과 담당자가 정한다.

## 벤더 샌드박스에도 계약을 확인한다

SIT를 시작하자마자 반나절을 날리는 흔한 이유가 형식 차이다. 벤더 문서에는 상태 코드가 두 자리 문자열이라고 돼 있는데, 샌드박스는 `"1"`을 돌려준다. SIT 첫날 이걸 사람이 화면을 보며 찾지 말고, 샌드박스에 계약 확인 스크립트를 먼저 돌린다.

```js
const contract = {
  VND_ORD_ID: (v) => typeof v === "string" && /^V\d+$/.test(v),
  STAT_CD: (v) => ["01", "02", "99"].includes(v),
  DLV_DT: (v) => /^\d{8}$/.test(v),
  QTY: (v) => typeof v === "string" && /^\d{4}$/.test(v),
};
const body = await (await fetch("http://127.0.0.1:18051/v1/orders/V9001")).json();
for (const [k, ok] of Object.entries(contract)) console.log(ok(body[k]) ? "  ok  " : "  FAIL", k, JSON.stringify(body[k]));
```

```text
  ok   VND_ORD_ID "V9001"
  FAIL STAT_CD "1"
  FAIL DLV_DT "2026/10/23"
  FAIL QTY 3
```

샌드박스 흉내 서버(포트 18051)가 문서와 다른 세 필드를 돌려줬고, 스크립트가 바로 짚었다. 이 결과를 들고 벤더에 묻는다. 샌드박스만 다른 건지, 문서가 틀린 건지. 답에 따라 어댑터의 번역 규칙을 고친다. 번역 계층이 무엇을 맡는지는 [벤더·레거시 시스템 연동](/posts/enterprise-system-integration#벤더의-말은-경계에서-우리-말로-바꾼다)에서 다뤘다.

이 스크립트를 SIT 기간에만 쓰지 말고 매일 돌리면, 벤더가 예고 없이 형식을 바꾼 날 아침에 알 수 있다. 회사 안 팀들 사이라면 소비자가 계약을 쓰고 제공자가 배포 전에 확인하는 소비자 주도 계약 테스트가 더 낫다. 그 흐름은 [API 버전 관리](/posts/api-versioning#소비자가-쓰는-것만-지킨다)에 있다. 바깥 벤더는 대개 그런 도구에 참여하지 않으니 우리 쪽에서 확인하는 방식이 현실적이다.

## 언제 시작하고 언제 끝났다고 말하나

SIT와 UAT에는 들어가는 기준(entry criteria)과 나오는 기준(exit criteria)을 미리 적어 둔다. 들어가는 기준이 없으면 반쯤 만든 빌드로 UAT를 시작해서 업무 담당자의 시간을 버린다. 나오는 기준이 없으면 끝나는 날을 정할 수 없고, 출시 압박 속에서 "이 정도면 되지 않나"로 결정하게 된다.

SIT에 들어가는 기준의 예:
- 대상 기능의 개발 완료와 단위·통합 테스트 통과
- 모든 연동 상대의 샌드박스 접속 확인, 계약 확인 스크립트 통과
- 마스킹한 테스트 데이터 적재 완료

나오는 기준은 숫자와 이름으로 쓴다. 이번 예에서는 실행한 케이스 중 통과율 95% 이상, 필수 케이스 전부 통과, 열린 심각도 1·2 결함 0개로 정했다. 실제 결과로 판정해 보면 이렇다.

```text
executed 120/122, pass rate 98.3% (기준 95%)
must-run 미통과: TC-119, TC-121
열린 Sev1/2: D-31
exit: NO-GO
```

통과율은 98.3%로 기준을 넘었는데 판정은 NO-GO다. 실패한 두 케이스 중 하나(`TC-119`)가 필수였고, `TC-121`은 샌드박스 문제로 막혀 아예 돌지 못했다. 막힘은 실패가 아니지만 통과도 아니다. 통과율만 보고 넘어갔다면 할인 금액 버그(`D-31`)를 안은 채 UAT로 갔을 것이다. 이 판정을 함수로 짜 보자.

마지막 테스트가 일부러 넣은 경우다. 케이스를 하나도 안 돌렸는데 통과율을 100%나 "해당 없음"으로 계산하는 도구가 있다. 아무것도 확인하지 않은 상태는 GO가 될 수 없다.

UAT의 끝은 서명(sign-off)이다. 업무 쪽 책임자가 "이 범위를 이 결과로 확인했고 받아들인다"고 기록을 남긴다. 열린 결함이 남아 있다면 그 목록과 처리 계획을 함께 적는다. 이 서명이 운영 반영 승인의 근거가 되므로, 말로 하지 말고 결함 목록과 결과 링크가 붙은 문서로 남긴다.

## 고칠 때마다 다 돌릴 수는 없다

UAT 막바지에 결함 하나를 고치면 무엇을 다시 확인해야 할까. 전체 케이스를 다시 돌리면 며칠이 걸리고, 고친 곳만 보면 고치면서 깨뜨린 곳을 놓친다. 그래서 회귀 묶음(regression pack)을 둔다. 핵심 업무 흐름을 덮는 작은 케이스 묶음이고, 어떤 수정이든 그 뒤에 이것만은 다시 돌린다. 그리고 고친 곳 주변(같은 화면, 같은 연동 상대)을 골라 더 돌린다.

회귀 묶음은 사람이 손으로 도는 것에서 시작해도 되지만, 출시가 반복되면 자동화할 순서를 정한다. 매번 돌리는 것, 사람이 하면 실수하는 것(금액 대조, 긴 입력), 화면이 잘 안 바뀌는 것부터다. UAT의 판단(업무에 맞나)은 자동화하지 못한다. 자동화하는 건 "어제와 같은가"까지다.

## SIT와 UAT가 흔들리는 순간들

- UAT 첫날 업무 담당자가 로그인부터 못 한다: 들어가는 기준에 계정·권한 준비가 없었다. 환경 점검 케이스를 UAT 전날 돌린다.
- 같은 케이스가 오전엔 통과, 오후엔 실패한다: 다른 팀이 같은 환경에 배포했거나, 다른 사람이 같은 테스트 데이터를 썼다. 배포 기록과 데이터 배정표를 본다.
- 결함이 며칠째 '확인 중'이다: 주인이 정해지지 않았다. 트리아지에서 한 팀에 배정하고 상관관계 id로 로그를 붙인다.
- 운영 첫날 벤더 연동만 실패한다: 샌드박스와 운영 API의 차이다. 인증 방식, 허용 IP, 응답 형식부터 비교한다. 그 차이는 SIT 결과에 위험으로 적혀 있어야 했다.
- UAT가 끝날 기미가 없다: 나오는 기준이 없거나, UAT 중에 요구 사항이 바뀌고 있다. 새 요구는 다음 출시로 넘기는 규칙을 정한다.

## 혼자 맞는 것, 함께 맞는 것, 쓸 수 있는 것

개발자의 테스트는 우리 코드가 혼자 맞는지를, SIT는 실제 시스템들이 함께 맞는지를, UAT는 업무 담당자가 그걸 쓸 수 있는지를 확인한다. 그 사이를 잇는 것은 운영을 닮되 개인정보를 뺀 데이터, 같은 빌드가 올라가는 환경의 줄, 그리고 숫자로 쓴 들어가는·나오는 기준이다. 이렇게 확인한 빌드를 실제로 운영에 올리는 밤은 [컷오버와 하이퍼케어](/posts/release-cutover-hypercare)에서 이어진다.

## 면접에서 나올 만한 질문

### SIT와 UAT는 무엇이 다른가요?

SIT는 실제 시스템들을 연결해 서로 약속대로 주고받는지 확인하고, UAT는 업무 담당자가 그 결과가 업무에 맞는지 판정한다. 질문이 다르니 하는 사람도 다르다. SIT는 QA나 연동 팀이, UAT는 실제 사용자 쪽이 하고, UAT의 끝에는 업무 책임자의 서명이 남는다.

### 개발자가 쓰는 통합 테스트가 있는데 SIT가 왜 또 필요한가요?

개발자의 통합 테스트는 바깥 시스템을 가짜로 바꾸기 때문이다. 가짜는 우리가 생각한 대로 동작하니, 진짜와 다른 지점(할인을 별도 줄로 받아야 하는 ERP 같은)은 진짜를 연결해야만 드러난다. 반대로 SIT만 믿으면 실패 원인을 찾는 데 오래 걸리니, 아래층 테스트를 충분히 두고 SIT에는 연결의 버그만 남게 한다.

### SIT 환경에 운영 데이터를 쓰고 싶습니다. 무엇을 조심하나요?

개인정보가 하위 환경과 벤더 샌드박스로 퍼지지 않게 마스킹하되, 여러 시스템에서 같은 고객이 같은 가짜 값이 되도록 키가 있는 해시로 결정적으로 바꾼다. 형식은 지켜야 검증이 있는 화면이 돌아간다. 키는 환경마다 다르게 비밀 저장소에 두고, 배송 메모 같은 자유 입력 칸은 통째로 지운다. 운영 데이터를 써도 되는지는 회사 정책과 담당자가 정한다.

### 같은 빌드를 환경마다 올리는 이유는 무엇인가요?

다시 빌드하면 테스트한 것과 다른 산출물이 나갈 수 있기 때문이다. 의존성 버전, 빌드 시점의 설정, 빌드 도구가 바뀌면 SIT와 UAT의 결과가 운영에 그대로 적용된다고 말할 수 없다. 환경마다 바뀌는 건 설정뿐이어야 하고, 환경 자체도 코드로 만들어 어긋남을 줄인다.

### 결함의 심각도와 우선순위는 왜 따로 매기나요?

영향의 크기와 고칠 시점이 자주 다르기 때문이다. 첫 화면의 회사 이름 오타는 기능 영향이 없어 심각도는 낮지만 모든 사용자가 보니 먼저 고치고, 드문 관리자 화면의 오류는 심각도가 높아도 우회 방법이 있으면 뒤로 미룰 수 있다. 트리아지에서는 결함마다 주인을 정하는 것도 같이 한다.

### 통과율이 98%인데 출시를 막아야 할 때가 있나요?

있다. 필수 케이스 하나가 실패하거나 막혔거나, 열린 심각도 높은 결함이 있으면 통과율과 상관없이 NO-GO다. 그래서 나오는 기준을 통과율 하나가 아니라 필수 케이스 통과, 열린 심각 결함 0개처럼 여러 조건으로 미리 적어 둔다. 케이스를 하나도 안 돌린 상태가 GO로 계산되지 않는지도 확인한다.

### 벤더 샌드박스가 자주 죽고 운영과 다르게 동작합니다. 어떻게 대비하나요?

샌드박스에 계약 확인 스크립트를 매일 돌려 형식 차이를 일찍 잡고, 샌드박스가 죽은 동안 돌릴 수 있는 시나리오를 따로 나눠 둔다. 샌드박스와 운영의 차이(인증, 허용 IP, 웹훅 지원)는 SIT 결과에 위험으로 적고, 운영 첫날 그 연동을 먼저 확인하는 항목으로 넘긴다.
