## 구매자로 나눈 주문, 판매자로 다시 나눈 사본

먼저 바탕이 되는 구조부터 본다. 2025년 4월 글에 따르면 네이버페이 주문의 메인 DB는 Oracle에서 nBase-T로 바뀌었다. nBase-T는 2025년 11월 글의 설명으로 "네이버 사내 분산 RDB 플랫폼(실저장소로 mySQL 이용)"이다. Oracle은 사라지지 않고 nBase-T에서 비동기로 복제받는 쪽이 됐다.

같은 11월 글의 복제 현황 표가 이 글의 출발점이다. 원본(Source)은 모두 nBase-T이고, 대상(Target)은 이렇다. 주문 DB에서 판매자 DB로(판매자 단위 조회 기능과 성능), 주문 DB에서 Oracle로(이전 Oracle 조회 앱 대응), 주문에서 정산, 주문에서 배송, 주문에서 호스팅사(호스팅사 단위 뷰), 그리고 배송에서 판매자(판매자 대상과 같은 목적)로 복제한다. 그리고 판매자 DB를 이렇게 설명했다.

> 판매자 DB는 구매자 기준으로 샤딩된 주문 DB 데이터를 판매자 번호 기준으로 샤딩해 만든 DB입니다.

이게 바로 샤딩에서 피할 수 없는 문제다. 샤드 키를 하나 고르면 그 키로 찾는 쿼리는 샤드 하나에서 끝나지만, 다른 키로 찾는 쿼리는 모든 샤드를 돌아야 한다. 구매자가 자기 주문을 보는 일과 판매자가 자기 가게 주문을 보는 일은 둘 다 자주 일어나고 둘 다 빨라야 한다. 네이버페이의 답은 같은 데이터를 다른 키로 샤딩한 사본을 하나 더 두고, 원본의 변경을 계속 옮겨 적는 것이다.

## 변경을 옮겨 적는 길: binlog에서 Kafka로

이 경로를 처음부터 맡던 도구가 mig-data다. DB 코어 개발 경험이 있는 개발자가 순수 Java로 만든 프로세스로, 7년 동안 Plasma의 복제를 맡았다. 옆에는 forceSync라는 보조 장치가 있었다. API 호출로 원본을 읽어 대상에 바로 쓰는 동기 복제로, mig-data가 늦거나 멈출 때를 대비했다.

같은 CDC는 다른 곳에서도 쓰인다. 2024년 3월 Kafka 글에 따르면 네이버페이 주문 메시지는 결제 완료, 발송, 배송 완료, 구매 확정처럼 주문 흐름의 이벤트마다 500개 넘는 필드를 담아 연관 시스템에 전파되고, 하루 3,000만 건씩 발행된다.

원래는 [트랜잭셔널 아웃박스](/posts/transactional-outbox)로 만들었다. 주문 트랜잭션 안에서 주문 번호와 액션 타입 같은 최소한의 키만 아웃박스 테이블에 쓰고, 별도 배치가 짧은 주기로 그 키를 읽어(폴링 퍼블리셔) 데이터를 조합해 메시지를 발행했다.

주문량이 늘자 공용 Kafka의 다른 토픽과 자원을 다투고, 발행이 늦어지고, 늦게 발행되다 보니 발행 시점이 아니라 바뀐 최신 상태가 담기는 문제가 생겼다. 전용 Kafka 클러스터를 두고, 자체 개발한 CDC로 아웃박스 구현을 트랜잭션 로그 테일링(transaction log tailing) 방식으로 바꿨다.

두 이야기를 겹치면 Plasma의 데이터 흐름이 보인다. 주문은 구매자 기준으로 샤딩된 nBase-T에 쓰이고, 그 변경 로그가 판매자 DB·Oracle·정산·배송 같은 다른 모양의 저장소와, 주문 메시지를 받는 수많은 서비스로 퍼진다. 변경의 원천은 하나(원본 DB의 로그)이고, 읽는 모양은 여럿이다.

## 7년 쓴 복제 도구를 바꾼 이유

2025년 11월 글은 mig-data를 ergate라는 새 도구로 바꾼 과정이다. ergate는 일개미처럼 데이터를 계속 실어 나른다는 뜻이다. 계기는 내재화였다. Plasma를 마무리하려면 복제 도구까지 주문 개발 조직이 맡아야 했는데, DB 코어 개발자가 순수 Java로 짠 도구를 백엔드 개발자가 그대로 인수하기는 어려웠다. 참여 인원 3명 모두 주로 Spring 기반 개발 경험이 있었다.

mig-data에는 7년 동안 쌓인 기능과 제약이 있었고, 대부분 원본과 대상 사이의 양방향 복제 때문이었다. 이 시점에는 단방향 복제만 남아 있었으니 그 제약을 걷어 낼 수 있었다. 글이 꼽은 제약은 셋이다. 첫째, 레코드 하나의 복제 실패가 전체 복제 지연으로 번졌다(양방향 복제에서 무결성을 확인하려고 일부러 만든 동작이었다). 둘째, 원본과 대상에 칼럼을 추가하는 순서가 중요해서, 대상에 먼저 추가하지 않으면 대상이 모르는 칼럼이 들어와 복제가 잠시 멈췄다.

셋째, 장애 때 복구 방법과 복구할 수 있는 사람이 제한적이었다.

목표는 이렇게 잡았다. 백엔드 개발자가 유지보수하기 쉬운 형태로 다시 만든다. 스키마 변경 때 복제가 멈추지 않고 순서에 상관없게 한다. 복구 편의 기능을 준다. 양방향 복제 같은 불필요한 기능은 뺀다. 현재 QPS의 10배 이상을 처리한다. CDC 이벤트 발행 뒤 1초 안에 복제한다.

기술은 Apache Flink(2.0.0, 전환 시점 LTS)와 Spring으로 골랐다. Flink는 저지연·대용량·고가용성 처리를 프레임워크에 맡기고 복제와 검증 구현에 집중하려는 선택이었다. Kafka 연동이 쉽고, 커머스 도메인의 알리바바가 Flink에 기여하고 쓴 사례가 있다는 점도 이유로 들었다. 다만 Flink에는 속도가 중요한 복제와 검증만 두고, 복잡한 복구 로직은 Spring 모듈로 떼어 냈다.

Flink는 쿠버네티스 위에 세션 모드로 띄웠다. 복제 job 6개와 각각의 검증 job까지 12개를 배포해야 해서, job마다 클러스터가 필요한 애플리케이션 모드보다 배포가 빠르고 한 웹 UI에서 모든 job을 볼 수 있기 때문이다. 대가는 job manager를 재배포하거나 job manager에 장애가 나면 모든 job이 함께 멈춘다는 것이다. 스트림 처리 프레임워크 일반은 [스트림 처리](/posts/stream-processing) 글에 있다.

이 구조의 생각은 하나다. 복제 경로는 멈추지 않게 가볍게 두고, 정확성은 따로 도는 검증과 복구가 책임진다. mig-data가 "한 건이 실패하면 전체가 늦어지는" 구조였던 것과 정반대다. 그 대신 검증이 틀린 경보를 내지 않도록 장치를 겹쳤다. 2분 동안 행이 다시 바뀌면 레코드와 대상이 다른 게 당연하니 원본을 다시 읽는다.

Oracle은 읽기 전용(슬레이브) DB로 검증하는데, 마스터와 슬레이브의 차이로 잘못 잡힐 수 있어 복구 때는 마스터에서 다시 읽는다. 판매자 DB는 순단 때문에 샤딩 키 조회가 실패할 수 있어, 복구 때 샤딩 키를 다시 조회한다.

복제한 행에는 모니터링용 칼럼 두 개를 함께 쓴다. `ergate_yn`은 누가 썼는지(0은 mig-data, 1은 ergate, 2는 forceSync), `rpc_time`은 원본에서 커밋된 시각이다. 대상 행 하나만 보고도 어느 도구가 언제의 원본을 옮긴 것인지 알 수 있다. 서킷 브레이커의 일반 원리는 [서킷 브레이커](/posts/circuit-breaker) 글에 있다.

이 사례에서 서킷이 필요했던 이유가 흥미롭다. 대상 DB 장애를 흉내 낸 테스트에서, 검증하려고 대상 DB에 커넥션을 계속 맺으려다 대기 시간이 쌓여 Flink가 함께 장애가 났다. 원본 DB 장애 때는 이런 일이 없었는데, 검증이 레코드와 대상이 다를 때만 선택적으로 원본에 붙기 때문이었다.

## 스키마는 따로 바뀌고, 데이터는 나중에 온다

mig-data의 "칼럼 추가 순서" 제약을 푼 방법은 관찰에서 나왔다. DDL은 운영 영향을 줄이려 보통 새벽에 하고, 새 칼럼에 실제 데이터가 들어오는 것은 그 뒤 코드 배포 이후다. DDL 시점과 데이터 인입 시점이 다르다. 그래서 ergate는 테이블 스키마와 쿼리를 캐시해 PreparedStatement를 재사용하고, 복제할 때는 캐시된 칼럼만 쓴다.

원본에 먼저 칼럼이 생기면 캐시된 대상 문장이 그 칼럼을 몰라 무시하고, 문장이 갱신된 뒤부터 반영한다. 대상에 먼저 생기면 원본에서 넘어오는 값이 없어 null로 들어간다.

예외는 칼럼 삭제다. 캐시된 문장이 이미 없는 칼럼을 쓰면 쿼리가 실패한다. 그래서 칼럼을 지우기 전에 개발자가 `ignore-columns` 설정을 미리 넣어 문장에서 빼 두어야 한다. 스키마 정보는 JDBC의 `DatabaseMetaData`로 주기적으로 다시 읽고, Flink가 실행 중에 스키마 변경을 감지하면 기존 문장에 쌓인 데이터를 내보낸(flush) 뒤 새 문장으로 바꾼다.

Oracle에는 스키마에 PK를 정의하지 않고 논리적으로만 쓰는 테이블이 있어서, 복제 설정에 PK 목록을 따로 적었다.

이 방식은 [무중단 마이그레이션](/posts/zero-downtime-migrations) 글의 "expand/contract"와 같은 순서를 복제 도구에 심은 것이다. 추가는 아무 순서로 해도 되게 넓게 받고, 삭제만 먼저 쓰는 쪽에서 빼는 절차를 밟는다.

## 200ms에서 40ms로, 숫자가 남은 튜닝

성능 목표는 기존 쓰기 QPS의 10배였다. 원본·대상과 같은 스키마의 논리 DB와 전용 nbase-cdc를 새로 만들고, fixture-monkey로 자체 테스트 데이터 생성 도구(banana)를 만들어 목표 QPS를 재현했다. 처음 측정에서 레코드 하나가 원본 커밋부터 대상 커밋까지 200ms가 걸렸다. 병렬도를 올리는 대신 "DB 커넥션은 비싼 자원이고 Flink 태스크 슬롯도 한정적"이라는 전제로 병목을 찾았다. 글에 적힌 순서와 결과는 이렇다.

태스크 사이 객체 직렬화를 줄이려고 object reuse 옵션을 켜, 같은 태스크 매니저 안에서는 직렬화하지 않게 했다. 200ms가 130ms가 됐다. 다음은 데이터 쏠림이었다. Kafka 레코드 키(구매자 번호)를 그대로 Flink 키로 써서, Kafka 파티션의 쏠림이 Flink 슬롯까지 이어졌다.

Flink 키를 구매자 번호와 테이블 이름의 조합으로 바꾸자 130ms가 70ms가 됐다. 샤딩 키 하나로 모든 것을 나누면, 그 키의 쏠림이 파이프라인 끝까지 따라온다는 이야기다.

DB I/O는 횟수를 줄였다. Flink 기본 JdbcSink는 고정된 batchSize와 batchIntervalMs를 쓰는데, 데이터가 늘면 executeBatch의 블로킹이 늘어 성능이 떨어진다. 그래서 데이터 흐름에 따라 배치 크기를 바꾸는 DynamicBatchSize를 만들었다. 글은 TCP 혼잡 제어와 비슷하다고 썼다.

할당량을 채우는 데 50~100ms가 걸렸으면 그대로, 100ms가 넘게 걸렸으면 줄이고, 50ms가 안 걸렸으면 늘린다. 70ms가 40ms가 됐다. 네트워크 버퍼를 쓰지 않게(`execution.buffer-timeout`을 0으로) 하자 지연이 조금 더 줄었고, 순서가 중요하지 않은 검증은 비동기로 바꿨다. 1초 안 복제는 JdbcSink의 batchIntervalMs 설정만으로 달성했다.

## 장애를 일부러 내 본 시험

성능을 확인한 뒤에는 각 지점이 고장 났을 때 자동 복구가 설계대로 도는지 봤다. 11월 글은 애플리케이션 쪽과 DB 쪽을 나눠 시험했다.

애플리케이션 쪽은 세 곳을 내렸다. Flink job manager의 리더 파드를 내리면 팔로워가 리더로 올라와 모든 job을 다시 띄워야 한다. 처음에는 체크포인트가 사라지는 문제가 있었고, 저장소로 S3를 쓰게 바꿔 풀었다. 태스크를 돌리던 task manager 파드를 내리면 멈춘 태스크가 다른 파드로 옮겨 다시 돌아야 하고, 그렇게 됐다.

복구를 맡은 Spring 모듈을 내리면, Flink는 캐시해 둔 테이블 메타데이터로 계속 복제와 검증을 해야 하고, 그렇게 됐다. 스키마 정보를 Flink가 DB 대신 Spring의 HTTP API로 받아 캐시해 둔 설계가 여기서 값을 했다.

DB 쪽은 개발 장비를 실제로 내릴 수 없었다. nBase-T는 새로 구축하기 쉽지 않아 여러 부서가 쓰는 개발 장비 위에 논리 DB를 만든 상태였기 때문이다. 그래서 DB 커넥션 코드를 확장해, 사내 기능 토글(unleash 기반)을 켜면 쿼리 준비 시점에 3초를 기다린 뒤 실패하게 만드는 "터지는 커넥션"을 넣었다.

원본 DB 장애에서는 샤딩 키 조회가 실패해 복제가 실패하고, 검증이 모두 실패해 상태 DB에 기록되고, 장애가 풀리면 복구와 재검증으로 모두 일치하는 것을 확인했다. 대상 DB 장애에서 앞에서 말한 커넥션 대기 누적이 드러났고, 서킷 브레이커를 넣었다.

장비를 내리지 않고 코드 안에서 실패를 주입하는 이 방법은 [카오스 엔지니어링](/posts/rw-netflix-chaos-engineering)의 작은 형태다. 공용 개발 환경처럼 진짜로 끌 수 없는 의존성이 있을 때 쓸 만하다. 주입 지점을 커넥션 계층 하나로 모았기 때문에, 비즈니스 코드를 건드리지 않고 원본과 대상 각각의 장애를 따로 켤 수 있었다.

## 두 도구가 서로 모르게 함께 복제했다

전환 전략은 대담했다. mig-data와 ergate가 서로를 모르는 상태로 같은 데이터를 함께 복제하게 했다. mig-data에 중복 방어 로직을 넣으면 기존 복제에 어떤 영향을 줄지 모르고, 운영에서 문제가 나면 위험이 크다고 봤다. 두 도구가 같은 행을 번갈아 쓰면 잠깐 과거 값으로 돌아갈 수는 있지만 충분히 빨라서 사용자는 모르고 결국 일치한다고 판단했다.

과거로 되돌아가는 문제는 이미 겪어 본 것이었다. forceSync는 동기라 대개 mig-data보다 빠르다. 짧은 시간에 A, B, C로 바뀌면 forceSync가 최신인 C를 먼저 쓰고, 뒤이어 mig-data가 A, B, C를 차례로 다시 쓰면서 잠깐 A나 B로 돌아간다. 그래서 "복제 반영 시점"을 뜻하는 `sync_seq` 칼럼을 두고 복제 쿼리에 조건을 붙였다.

```sql
-- 2025년 11월 글의 조건. :commit_ts 는 반영하려는 데이터의 원본 커밋 시각
-- (forceSync는 원본을 SELECT한 시각)
WHERE sync_seq IS NULL OR :commit_ts >= sync_seq
```

반영하려는 데이터가 대상에 이미 있는 것보다 과거 커밋이면 무시한다는 뜻이다. `>`가 아니라 `>=`인 이유도 적혀 있다. 기존 메시지가 밀리초를 잘라 발행하고 있어서, 같은 초 안의 변경을 `>`로 막으면 반영이 빠질 수 있다. 메시지에 밀리초를 넣으면 mig-data의 동작을 예측하기 어려워 그대로 두었다. ergate와 forceSync 사이에도 같은 장치가 필요해 `rpc_time` 칼럼으로 같은 로직을 만들었다. 이 조건을 직접 돌려 볼 수 있다.

  ]}

두 번째 테스트에서 forceSync가 C를 먼저 쓴 뒤 mig-data의 A와 B는 커밋 시각이 더 과거라 무시되고, 마지막 C는 같은 시각이라 `>=` 덕분에 다시 반영된다. 결과는 같다. 같은 시각이 다시 들어와도 값이 같으니 해가 없고, 밀리초가 잘린 상황에서 같은 초의 다른 변경을 놓치지 않는다.

대신 같은 초 안에서 순서가 뒤집힌 두 변경은 이 조건으로 가려낼 수 없다. 글이 이 경우를 따로 다루지는 않았다. 검증과 복구가 그 틈을 잡는 구조였을 것이다.

검증은 가장 먼저 배포했다. 검증은 실제 데이터를 건드리지 않고, 자동 복구를 배포하지 않은 상태라면 잡아도 문제가 없다. 그래서 ergate 검증을 먼저 띄워 일정 기간 오검출이나 과검출이 없는지 봤다. 반대로 mig-data의 검증은 "만약을 위한 정답 선택지"로 가장 늦게까지 남겼다.

전환은 테이블을 영향도 낮은 것부터 세 차수로 나눴다(예로 1차 5개, 2차 13개, 3차 나머지). 중복 복제라 DB 자원 사용이 늘기 때문이다. 각 차수마다 1주일 동안 함께 복제하며 불일치와 Flink 클러스터를 지켜본 뒤 mig-data 복제를 끄고 ergate만 남겼다.

일정도 글에 적혀 있다. 2025년 1월 말 프로젝트를 시작할 때 2명 모두 기존 업무를 겸하고 있어 본격적인 작업은 3월부터 했고, 3명이 된 것은 5월부터다. 1차 목표였던 판매자 DB 전환은 7월에 끝냈다. 동기 보조 장치였던 forceSync는 ergate만으로 충분히 빠르고 안정적이라고 보고 실제 동작을 꺼 두었으며, 내리는 단계를 밟고 있다고 썼다.

전체 아키텍처의 결정 과정은 ADR(Architecture Decision Record)로 남겨 뒤에 맡을 사람이 근거를 볼 수 있게 했다.

## 복제 대상 Oracle이 느려진 이유

같은 Plasma에서 2025년 4월 글은 다른 쪽 복제의 장애를 다룬다. nBase-T에서 Oracle로 가는 동기화가 서비스 호출량이 많아질 때 늦어졌다. Pinpoint로 보니 Oracle의 UPDATE가 느린 쿼리가 되어 복제 서비스의 커넥션 풀을 고갈시키고 타임아웃을 냈다.

DBA 팀과 로그를 보니 특정 쿼리 하나에서 child cursor가 22,000개 넘게 생겼다(정상은 100개 이하). 응답 시간은 0.003초에서 0.308초로 100배 넘게 늘었고, 라이브러리 캐시 잠금, 뮤텍스, 커서 대기가 늘었다.

원인은 바인딩 타입이었다. Oracle은 같은 SQL이라도 바인딩 값의 타입이 다르면 기존 child cursor를 재사용하지 못하고 새로 만든다. 글은 세 경우를 짚었다. 첫째, 문자열 길이에 따라 바인딩이 VARCHAR(32), (128), (2000), (4000)으로 바뀐다. 둘째, NULL이 들어오면 타입을 추론하지 못해 다른 타입으로 바인딩된다.

셋째, TIMESTAMP나 NUMBER의 소수점 자릿수가 바뀌면 다른 타입으로 본다. 칼럼 4개가 각각 네 가지 길이를 가지면 4의 4제곱, 256개 조합이 나온다. 문제가 된 상품 주문 테이블은 칼럼이 매우 많아 수십만 개 조합이 가능했다. 복제 도구가 모든 칼럼을 한 UPDATE로 쓰는 구조가 이 조합을 키웠다.

여덟 가지를 시도했고, 최종으로 넷을 골랐다. NULL에 `setNull`로 타입을 고정하고, NUMBER 자릿수에 `setObject(scale)`를 쓰고(효과는 확실하지 않다고 썼다), 비즈니스상 필요 없는 UPDATE 칼럼을 150개에서 100개로 줄이고, TIMESTAMP를 밀리초로 잘라 바인딩했다. 마지막이 효과가 컸다.

nBase-T는 TIMESTAMP를 밀리초 단위로 만드는데 Oracle은 원래 다르게 저장하고 있어서, 복제 과정에서 자릿수 차이가 생겼던 것이다. 쿼리마다 무작위 주석으로 parent cursor를 나누거나, 세션에서 VARCHAR 바인딩을 4000으로 고정하는 방법은 근본 원인을 풀지 못하거나 부작용 우려로 고르지 않았다. 결과로 child cursor가 99.8% 줄었다.

이 사례의 교훈은 글 끝에 있다. 문제는 점진 전환의 10% 트래픽 단계에서 일찍 발견돼 큰 장애로 번지지 않았다. 그리고 원본과 대상의 타입 체계가 다른 이기종 복제에서는, 같은 값이라도 "어떤 모양으로 바인딩되는가"가 대상 DB의 성능을 좌우할 수 있다.

## 주문 메시지의 Kafka를 통째로 옮긴 법

2024년 3월 글로 돌아가면, 주문 메시지 시스템 개편에는 두 관문이 있었다. 하나는 새로 만든 발행 모듈이 옛것과 같은 메시지를 내는지, 다른 하나는 30개 남짓한 컨슈머를 새 Kafka 브로커로 끊김 없이 옮기는 것이다.

첫째는 운영에서 메시지를 두 벌 만드는 검증으로 풀었다. 정합성 검증 컨슈머는 기존 주문 메시지를 소비해 키를 꺼내고, 새 모듈의 로직으로 검증용 메시지를 만들어 둘을 비교했다. 발행 검증은 기존과 새 메시지의 키만 저장소에 모아 배치로 "같은 메시지가 같은 수만큼 나갔는지"를 봤다. 이 과정에서 빠진 필드, 다른 값, 암호화가 필요한데 안 된 필드, 작업 중 기존 시스템에 추가된 새 스펙을 잡아냈다고 썼다.

둘째가 흥미롭다. 컨슈머가 브로커 주소만 바꾸면 컨슈머 그룹 오프셋이 초기화돼 누락이나 중복이 생긴다. 모든 컨슈머가 멱등하다면 처음부터 다시 읽게 해도 되지만, 멱등하지 않은 컨슈머를 많은 부서가 오래 써 왔다. 그래서 MirrorMaker로 기존 브로커의 메시지와 컨슈머 그룹 오프셋까지 새 브로커로 복제하고, 컨슈머가 각자 리스너만 새 브로커로 바꾸게 했다.

같은 그룹 ID를 써야 오프셋을 이어받고, 두 브로커를 동시에 소비하면 오프셋이 꼬여 중복이 생기니 블루-그린 배포를 조심하고, 오프셋 동기화가 주기적이라 간격만큼 잠깐 멈춰야 한다고 적었다. 3주 동안 30여 개 컨슈머를 순간적인 중단만으로 옮겼다.

## 다른 회사의 샤딩 사례와 나란히 놓으면

같은 시리즈의 [Instagram](/posts/rw-instagram-sharding-ids)과 [Pinterest](/posts/rw-pinterest-mysql-sharding)는 ID 안에 샤드 정보를 넣어 "이 ID의 데이터는 어느 샤드에 있나"를 계산으로 풀었다.

이것은 한 키로 찾는 문제의 답이다. 네이버페이 사례는 그 다음 질문을 다룬다. 샤드 키가 아닌 키로 찾아야 할 때다. ID에 샤드를 넣는 설계는 이 질문에 답하지 않는다. 판매자 번호로 찾으려면 결국 판매자 기준으로 모은 다른 배치가 필요하다.

[Discord의 메시지 저장소](/posts/rw-discord-message-storage)나 [Notion의 Postgres 샤딩](/posts/rw-notion-postgres-sharding)처럼 샤딩 이야기는 보통 "어떻게 나눴나"에서 끝난다. 네이버페이 글들은 나눈 뒤의 일, 즉 다른 모양의 사본을 몇 개나 두고 그것들을 원본과 맞추는 데 드는 일을 길게 적었다는 점에서 드물다.

원본 하나에 사본이 판매자, Oracle, 정산, 배송, 호스팅사로 다섯 갈래다. 샤딩을 고민하는 팀이라면 "나누는 비용"보다 "나눈 뒤 다른 키로 묻는 비용"을 먼저 세어 볼 만하다.

## 공개된 이야기에서 빠진 것

세 글은 네이버페이 주문 개발 쪽이 직접 쓴 기록이지만, 회사가 고른 성공담이다. 샤드 수, 샤딩 키를 샤드로 바꾸는 규칙, nBase-T의 내부 구조는 나오지 않는다. 판매자 DB 복제 지연이 실제로 몇 ms인지, 검증에서 하루에 몇 건이 잡히는지, 자동 복구가 몇 번 도는지도 없다. 제목의 "연간 수십조"는 처리하는 거래 금액으로 읽히지만 본문에 따로 설명이 없다. 11월 글은 "서비스 이슈 없는 전환", "무중단, 무장애"라고 했는데, 회사의 평가다.

Flink 세션 모드의 대가도 글이 일부만 보여 준다. 사용자 코드의 static 필드를 부모 클래스로더가 붙잡아 job manager가 Metaspace OOM을 낸 일, 쿠버네티스 리더 선출에서 lease-duration과 renew-deadline을 같은 값(5초, 5초, 재시도 1초)으로 둬서 스플릿 브레인이 난 일(30초, 20초, 6초로 바꿔 해결)은 적었지만, 그 장애가 운영에서 났는지 테스트에서 났는지는 분명하지 않다.

리더 선출의 일반은 [리더 선출](/posts/leader-election) 글에 있다. Oracle을 언제까지 대상으로 남길지, 판매자 DB 말고 정산·배송 대상의 전환이 끝났는지도 글이 쓰인 시점 이후로는 공개되지 않았다.

## 다른 키로 찾아야 하는 날이 오면

네이버페이 구조가 맞는 조건은 분명하다. 데이터가 이미 한 키(구매자)로 샤딩돼 있고, 다른 키(판매자, 호스팅사)로 찾는 질문이 자주 오며 빨라야 하고, 그 질문이 조금 늦은 데이터를 견딘다. 판매자 화면이 1초 늦은 주문을 보는 것은 괜찮지만, 결제 승인을 1초 늦은 사본으로 하면 안 된다. 사본은 읽기 전용이고 원본만 쓴다는 규칙이 이 구조의 전제다.

처음부터 따라 하면 드는 비용이 크다. CDC, Kafka, 복제 도구, 검증 job, 복구 모듈, 상태 DB가 모두 운영 대상이 된다. 샤딩하지 않은 서비스라면 판매자 기준 조회는 인덱스 하나로 끝날 수 있다. 샤딩한 뒤에도 다른 키 조회가 드물다면 모든 샤드에 묻는 산개 쿼리(scatter-gather)로 버티는 편이 싸다. 사본을 만드는 날은 산개 쿼리가 모든 샤드의 부하를 끌어올리기 시작하는 날이다.

작은 팀이 지금 가져올 수 있는 것은 이렇다.

- 복제한 행에 "원본에서 언제 커밋됐는가"를 함께 쓴다. `rpc_time`, `sync_seq`처럼 칼럼 하나가 과거 회귀를 막고, 지연을 재는 지표가 된다.
- 복제와 검증을 떼어 놓는다. 복제는 실패해도 멈추지 않게 두고, 같은 이벤트를 몇 분 늦게 다시 읽어 대상과 비교하는 작은 검증부터 만든다.
- 새 복제·발행 경로는 검증부터 배포한다. 데이터를 건드리지 않는 검증으로 오검출이 없는지 먼저 보고, 옛 경로의 검증은 가장 늦게 끈다.
- 파티션 키와 전환 스위치의 키를 같게 맞춘다. 비율로 옮길 때 같은 키의 메시지가 두 경로로 갈라지지 않아야 순서가 지켜진다.

비슷한 신호가 보이면 무엇부터 볼까. 판매자 화면 같은 사본에서 방금 바뀐 값이 잠깐 옛 값으로 돌아갔다가 돌아온다면, 두 경로가 같은 행을 쓰고 있는지와 커밋 시각 조건이 있는지 본다. 복제 대상 DB의 UPDATE가 갑자기 느려지면 쿼리 하나당 커서·실행 계획 수가 늘었는지, 원본과 대상의 타입 차이(밀리초, NULL)가 있는지 본다. 파이프라인의 지연이 특정 슬롯이나 파티션에만 몰리면 샤딩 키 하나를 처리 키로 그대로 쓰고 있지 않은지 본다.

## 면접에서 나올 만한 질문

### 구매자로 샤딩한 주문 DB에서 판매자별 주문 목록을 빠르게 보려면 어떻게 하나요?

같은 데이터를 판매자 키로 샤딩한 사본을 따로 두고 원본의 변경을 계속 옮겨 적는다. 네이버페이는 구매자 기준으로 샤딩한 nBase-T 주문 DB의 binlog를 CDC로 Kafka에 내보내고, 복제 도구가 판매자 번호 기준으로 샤딩한 판매자 DB에 반영한다. 판매자 조회는 샤드 하나로 끝나는 대신, 사본은 원본보다 조금 늦고 동기화 장치를 운영해야 한다.

### 사본을 만드는 대신 모든 샤드에 묻는 방법과 비교하면요?

산개 쿼리는 운영할 부품이 없지만 질문마다 모든 샤드를 깨운다. 판매자 조회가 드물면 산개 쿼리가 싸고, 자주 오고 빨라야 하면 사본이 낫다. 네이버페이는 판매자 단위 조회 기능과 성능을 이유로 사본을 골랐고, 그 대가로 1초 안 복제와 검증·복구 체계를 만들었다.

### 복제 도구에서 한 건이 실패하면 멈추는 것과 넘어가는 것 중 무엇이 낫나요?

정확성을 따로 보장할 장치가 있다면 넘어가는 쪽이 낫다. 옛 도구 mig-data는 양방향 복제의 무결성 때문에 한 건 실패가 전체 지연으로 번졌다. ergate는 실패를 넘기고 같은 토픽을 2분 늦게 읽는 검증으로 잡아, DLQ와 상태 DB를 거쳐 5분 뒤 자동 복구, 그다음 배치와 수동 복구로 고친다. 복제는 빠르게, 정확성은 뒤에서 책임지는 분업이다.

### 두 복제 경로가 같은 행을 쓸 때 과거 값으로 되돌아가는 문제는 어떻게 막나요?

행에 원본 커밋 시각을 함께 쓰고, 그보다 과거의 변경은 무시한다. 네이버페이는 `sync_seq` 칼럼을 두고 `WHERE sync_seq IS NULL OR :commit_ts >= sync_seq` 조건을 붙였다. 동기 복제 forceSync가 최신 값을 먼저 써도 비동기 복제가 뒤늦게 가져온 옛 값은 무시된다. 메시지의 시각이 밀리초를 자르고 있어 같은 초를 놓치지 않으려고 `>`가 아니라 `>=`를 썼다.

### 새 복제 도구로 바꿀 때 왜 두 도구를 서로 모르게 함께 돌렸나요?

옛 도구에 중복 방어 로직을 넣는 것이 더 위험했기 때문이다. 운영 중인 민감한 복제 도구를 고치면 어떤 영향이 생길지 모르니, 둘이 같은 데이터를 함께 쓰게 하고 커밋 시각 조건과 검증으로 결과를 맞췄다. 검증을 먼저 배포해 오검출을 보고, 테이블을 영향도 낮은 것부터 세 차수로 나눠 차수마다 1주일 함께 돌린 뒤 옛 도구를 껐다.

### CDC로 Oracle에 복제했더니 UPDATE가 느려졌다면 무엇을 의심하나요?

같은 쿼리의 바인딩 타입이 매번 달라 커서를 재사용하지 못하는지 본다. 네이버페이 사례에서 쿼리 하나에 child cursor가 22,000개 넘게 생겨 응답이 0.003초에서 0.308초로 늘었다. 원인은 문자열 길이별 VARCHAR 바인딩, NULL, TIMESTAMP 자릿수 차이였고, NULL 타입 고정, 불필요한 UPDATE 칼럼 제거, TIMESTAMP를 밀리초로 잘라 바인딩해 child cursor를 99.8% 줄였다.

### 컨슈머가 30개 넘는 Kafka 토픽을 새 브로커로 옮길 때 오프셋은 어떻게 지키나요?

메시지와 함께 컨슈머 그룹 오프셋까지 새 브로커로 복제하고, 컨슈머가 같은 그룹 ID로 리스너만 바꾸게 한다. 네이버페이는 MirrorMaker로 이렇게 3주 동안 30여 개 컨슈머를 옮겼다. 두 브로커를 동시에 소비하면 오프셋이 꼬이니 블루-그린 배포를 조심하고, 오프셋 동기화 주기만큼 잠깐 멈춘다. 발행 쪽을 비율로 옮길 때는 전환 키를 파티션 키와 같게 해 순서를 지켰다.

### 샤딩하지 않은 작은 서비스라면 이 구조에서 무엇을 가져오면 좋을까요?

복제 장치 전체가 아니라 습관 몇 가지다. 샤딩하지 않았다면 판매자 조회는 인덱스로 충분하고, 사본과 CDC는 비용만 늘린다. 다만 다른 저장소(검색 색인, 캐시, 분석 DB)로 데이터를 옮기고 있다면, 행에 원본 커밋 시각을 남기고, 옮긴 결과를 늦게 다시 비교하는 작은 검증을 두고, 새 경로는 검증부터 배포하는 습관은 지금 바로 쓸 수 있다.
