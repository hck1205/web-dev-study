결제 화면의 버튼에 누군가 `isLoading` prop을 추가했다. 로딩 중에는 글자 대신 점 세 개를 보여 주도록 했더니, 버튼을 누르는 순간 너비가 98px에서 50px로 줄어들며 옆의 "취소" 버튼이 왼쪽으로 튀어나왔다. 결제가 느린 날 사용자가 버튼을 한 번 더 눌렀고 결제가 두 번 됐다. 같은 주에 접근성 점검에서는 검색 아이콘 버튼 열두 개가 "이름 없는 버튼"으로 걸렸다.

"디자인 시스템의 Button을 설계해 보라"는 프런트엔드 면접에서 자주 나오는 질문이다. 이 질문에서 보는 건 props 이름을 잘 짓는 능력보다, 버튼이 가질 수 있는 상태를 빠짐없이 떠올리고 각 상태에서 무엇을 약속하는지 정하는 능력이다. 이 글은 Button을 따라가며 상태 표를 그리고, 같은 틀로 Avatar, Badge, Card, Banner, List를 정리한다. 브라우저 동작은 Chromium(Playwright 1.56)에서 직접 확인했다.

토큰 계층, variant·tone·size를 축으로 나누는 법, `as`와 `asChild`의 차이, Storybook은 [디자인 시스템 만들기](/posts/design-system-building)에, children과 슬롯, Compound Components 같은 합성 패턴은 [React 컴포넌트 설계 패턴](/posts/react-component-patterns)에 있다. 여기서는 그 위에서 상태와 접근성 약속, 그리고 그 결정을 기록하는 방법에 집중한다.

## props보다 상태 표를 먼저 그린다

컴포넌트를 만들 때 props부터 쓰기 시작하면 상태 하나가 빠지기 쉽다. 순서를 바꿔서, 이 부품이 가질 수 있는 상태를 먼저 행으로 적고, 각 상태에서 보이는 것, 누를 수 있는지, 키보드 포커스를 받는지, 보조 기술(스크린 리더)에 무엇을 알리는지를 열로 채운다. Button이라면 이렇다.

| 상태 | 보이는 것 | 누를 수 있나 | 포커스 | 보조 기술에 알리는 것 |
|---|---|---|---|---|
| 기본 | 배경색, 글자 | 예 | 받는다 | 역할 button, 이름 |
| 호버 | 배경 한 단계 진하게 | 예 | 받는다 | 바뀌지 않음 |
| 포커스 | `:focus-visible` 테두리 | 예 | 지금 여기 | 바뀌지 않음 |
| 눌림 | 배경 두 단계 진하게 | 예 | 받는다 | 토글이면 `aria-pressed` |
| 비활성 | 흐린 색, 커서 기본 | 아니요 | 정책에 따라 | disabled |
| 로딩 | 글자 자리 유지, 스피너 | 아니요(두 번 누르기 막음) | 유지 | `aria-busy`, 진행 알림 |

이 표가 있으면 리뷰에서 물어볼 것이 분명해진다. "로딩 중에 포커스는 어디로 가나", "비활성일 때 왜 안 되는지 어떻게 알려 주나" 같은 질문은 props 목록만 봐서는 나오지 않는다. 디자인 시안도 표의 행마다 하나씩 있어야 한다. 시안에 로딩 상태가 없으면 개발자가 즉석에서 만들고, 그게 처음 장면의 점 세 개다.

## 버튼의 타입 기본값부터 정한다

props는 상태 표에서 나온다. 모양과 크기 같은 축은 [디자인 시스템 만들기](/posts/design-system-building)에서 다룬 대로 유니언으로 나누고, 여기서는 상태와 관련된 결정만 본다.

```tsx
// button.type.ts
import type { ComponentPropsWithRef, ReactNode } from "react";

export type ButtonProps = Omit<ComponentPropsWithRef<"button">, "disabled"> & {
  variant?: "solid" | "outline" | "ghost";
  size?: "sm" | "md" | "lg";
  /** 처리 중. 클릭을 무시하고 aria-busy를 켠다. 너비는 유지한다 */
  loading?: boolean;
  /** 로딩 중 보조 기술에 알릴 문구. 없으면 "처리 중" */
  loadingText?: string;
  /** 누를 수 없지만 포커스는 받게 할지. 이유를 툴팁으로 보여 줄 때 쓴다 */
  disabled?: boolean | "focusable";
  leadingIcon?: ReactNode;
};
```

가장 먼저 정할 것은 `type`의 기본값이다. HTML의 `<button>`은 `type`을 적지 않으면 `submit`이다. 폼 안에 "비밀번호 보기" 버튼을 넣었는데 누를 때마다 폼이 제출되는 버그가 여기서 나온다. 공용 Button은 기본값을 `type="button"`으로 두고, 제출 버튼만 `type="submit"`을 적게 한다. 쓰는 사람 대부분이 이 차이를 모르기 때문에 시스템이 안전한 쪽을 기본값으로 가져가야 한다.

`loading`과 `disabled`를 따로 둔 것도 결정이다. 둘 다 "지금 못 누른다"지만 이유가 다르다. 로딩은 곧 끝나는 일시적인 상태라 포커스와 이름을 그대로 두고, 비활성은 조건이 바뀌기 전까지 계속되는 상태라 이유를 알려 줘야 한다. 하나의 `state` prop으로 합치는 설계도 있는데, 그러면 "로딩 중이면서 비활성"처럼 동시에 켜질 수 없는 조합을 타입이 막아 주는 장점이 있다. 어느 쪽을 골랐는지와 그 이유는 뒤에서 볼 결정 기록에 남긴다.

## 이동이면 링크, 동작이면 버튼

버튼처럼 생긴 것이 실제로는 링크여야 하는 경우가 많다. 기준은 하나다. 누르면 다른 주소로 이동하면 `<a href>`, 이 화면에서 무언가를 실행하면 `<button>`이다. "요금제 보기"는 링크, "장바구니 담기"는 버튼이다.

이걸 어기면 사용자가 바로 느낀다. 링크는 가운데 클릭이나 Ctrl+클릭으로 새 탭에서 열 수 있고, 주소를 복사할 수 있고, 스크린 리더의 링크 목록에 나온다. `onClick`에서 `router.push`를 부르는 버튼은 이 중 아무것도 안 된다. 반대로 `href` 없는 `<a>`에 `onClick`만 달면 더 나쁘다. Chromium에서 탭 순서와 접근성 트리를 확인해 봤다.

```html
<a id="a-nohref" class="btn">더 보기</a>
<a id="a-href" class="btn" href="/more">더 보기</a>
```

```text
tab order: aria-disabled > swap > overlay > icon-none > icon-label > a-href > bell > card-link > fav > BODY
- text: 더 보기
- link "더 보기":
  - /url: /more
```

탭 순서에 `a-href`만 있고 `a-nohref`는 없다. 접근성 트리에서도 `href` 없는 쪽은 링크가 아니라 그냥 글자다. 키보드로는 갈 수도 없고, 스크린 리더는 눌리는 것인지 모른다. `href` 없는 `<a>`는 링크가 아니다.

그래서 디자인 시스템은 "버튼처럼 보이는 링크"를 따로 지원해야 한다. `as="a"`나 `asChild`로 Button의 모양을 링크에 입히는 방법은 [디자인 시스템 만들기](/posts/design-system-building)에서 비교했다. 어느 쪽이든 원칙은 같다. 모양은 버튼, 요소는 링크다. 이때 `loading`이나 `disabled` 같은 버튼 전용 prop은 링크에서 의미가 없으니, 타입에서 함께 쓸 수 없게 막는 편이 좋다.

## 누를 수 없을 때 이유를 숨기지 않는다

비활성 버튼에는 두 가지 방법이 있다. 네이티브 `disabled` 속성과 `aria-disabled="true"`다. 같은 페이지에 둘을 놓고 확인했다.

```html
<button id="native-disabled" class="btn" disabled>저장</button>
<button id="aria-disabled" class="btn" aria-disabled="true">저장</button>
```

```text
tab order: aria-disabled > swap > overlay > ...
clicks: [ 'aria-disabled', 'aria-disabled' ]
- button "저장" [disabled]
- button "저장" [disabled]
```

세 가지가 보인다. 접근성 트리에서는 둘 다 `[disabled]`로 보인다. 그런데 탭 순서에는 `aria-disabled` 쪽만 들어 있다. 네이티브 `disabled`는 포커스를 받지 않는다. 그리고 클릭 기록을 보면, 두 버튼을 강제로 클릭하고 `aria-disabled` 버튼에서 Enter도 눌렀더니 `aria-disabled` 버튼의 클릭 이벤트만 두 번 들어왔다. `aria-disabled`는 보조 기술에 상태를 알릴 뿐, 브라우저가 클릭을 막아 주지 않는다.

여기서 트레이드오프가 생긴다. 네이티브 `disabled`는 안전하다. 핸들러가 불리지 않고, 폼 제출에서도 빠진다. 하지만 포커스를 받지 못하니 키보드 사용자는 그 버튼이 있다는 것조차 모르고 지나갈 수 있고, 마우스를 올려야 보이는 "필수 항목을 먼저 입력하세요" 툴팁은 영영 볼 수 없다. `aria-disabled`는 포커스를 받아 이유를 들려줄 수 있지만, 컴포넌트가 클릭과 Enter, Space를 직접 막아야 하고 흐린 스타일도 직접 입혀야 한다.

```tsx
// button.ts (container): focusable 비활성과 로딩은 클릭을 직접 막는다
export function useButton({ disabled, loading, onClick }: ButtonProps) {
  const blocked = disabled === "focusable" || loading;
  const handleClick: React.MouseEventHandler<HTMLButtonElement> = (event) => {
    if (blocked) {
      event.preventDefault();          // 폼 제출도 막는다
      return;
    }
    onClick?.(event);
  };
  return {
    handleClick,
    nativeDisabled: disabled === true,  // 이유를 알릴 필요가 없을 때만 진짜 disabled
    ariaDisabled: blocked || undefined,
  };
}
```

이 글의 Button은 `disabled`에 `true`와 `"focusable"` 두 값을 받게 했다. 대부분은 네이티브로 충분하고, 이유를 보여 줘야 하는 곳만 포커스를 남긴다. 더 나은 방법은 버튼을 아예 비활성으로 만들지 않는 것이다. 제출 버튼을 늘 누를 수 있게 두고, 눌렀을 때 빠진 항목으로 포커스를 옮기며 오류를 보여 주면 "왜 안 눌리지"라는 질문 자체가 사라진다. 폼 검증과 오류 연결은 [폼 검증](/posts/html-form-validation)에서 다룬다.

## 로딩 중에도 너비와 이름을 지킨다

처음 장면의 두 문제, 너비가 바뀌는 것과 두 번 눌리는 것을 보자. 글자를 바꾸는 방식과, 글자를 숨기고 스피너를 겹치는 방식의 너비를 쟀다.

```css
/* 겹치기 방식: 글자와 스피너를 같은 격자 칸에 둔다 */
.btn { display: inline-grid; place-items: center; }
.btn > * { grid-area: 1 / 1; }
.btn[aria-busy="true"] .label { visibility: hidden; }
```

```text
swap text: 98 -> 50px, overlay: 98 -> 98px
```

글자를 "…"로 바꾸면 98px에서 50px로 줄고, 글자를 그 자리에 남긴 채 숨기면 98px 그대로다. 같은 격자 칸에 글자와 스피너를 겹쳐 두면, 버튼 너비는 늘 글자가 정한다. `min-width`를 고정값으로 주는 방법도 있지만 번역된 긴 문구나 큰 글꼴 설정에서 깨진다.

그런데 같은 실험의 접근성 트리에서 문제가 하나 더 보였다.

```text
- button "…"
- button
- button "결제하기"
```

첫 줄은 글자를 바꾼 버튼으로, 이름이 "…"가 됐다. 둘째 줄은 `visibility: hidden`으로 숨긴 버튼인데 이름이 아예 사라졌다. `visibility: hidden`은 그 요소를 접근성 트리에서도 빼기 때문에, 이름을 만들던 글자가 없어진 것이다. 셋째 줄은 같은 구조에서 `visibility` 대신 `opacity: 0`으로 숨긴 버튼이다. 너비도 98px 그대로였고 이름도 남았다. 눈에 안 보이게 하는 방법이 보조 기술에도 보이지 않게 하는지 아닌지를 함께 따져야 한다.

로딩 중이라는 사실도 알려야 한다. 버튼에 `aria-busy="true"`를 붙이는 건 좋은 표시지만, 스크린 리더마다 이 속성을 읽는 방식이 달라서 그것만 믿기 어렵다. 확실한 방법은 화면 어딘가의 라이브 리전에 "결제 중"을 넣었다가 끝나면 "결제 완료"나 오류 문구로 바꾸는 것이다. 라이브 리전 자체는 [ARIA와 키보드·포커스 관리](/posts/aria-keyboard-focus)에 정리돼 있다. 아래 그림이 이 흐름이다. 버튼 모양이 처리 중임을 말하고, 끝나면 결과로 바뀐다.

두 번 누르기는 화면 표시만으로는 막을 수 없다. 사람은 스피너가 그려지기 전 수십 밀리초 사이에도 두 번 누른다. 그래서 막는 일은 세 겹으로 한다. 컴포넌트는 `loading` 동안 클릭을 무시한다(위 `useButton`). 호출하는 쪽은 요청이 진행 중이면 다시 보내지 않는다. React 19의 폼 액션을 쓰면 `useFormStatus`의 `pending`이 이 상태를 준다([React 폼과 액션](/posts/react-forms-actions)). 그리고 결제처럼 두 번 실행되면 안 되는 요청은 서버가 멱등 키로 같은 요청을 한 번만 처리한다. 앞의 두 겹은 사용자 경험이고, 마지막 한 겹이 진짜 안전장치다.

로딩 중에 포커스를 다른 곳으로 옮기지 않는 것도 약속이다. 포커스를 가진 버튼을 `disabled`로 바꾸면 어떻게 되는지 확인했다.

```text
before: pay
after disabled: BODY#
```

Chromium에서는 포커스가 `body`로 떨어졌다. 버튼의 포커스 표시가 사라지고, 로딩이 끝나 버튼이 다시 살아나도 포커스는 저절로 돌아오지 않는다. 키보드 사용자는 결과를 확인하려고 다시 버튼을 찾아가야 한다. 로딩을 `disabled` 대신 클릭 무시로 구현한 이유가 이것이다.

## 아이콘만 있는 버튼의 이름

접근성 점검에서 걸린 열두 개의 검색 버튼은 이렇게 생겼다.

```html
<button id="icon-none" class="btn"><svg aria-hidden="true">...</svg></button>
<button id="icon-label" class="btn" aria-label="검색"><svg aria-hidden="true">...</svg></button>
```

```text
- button
- button "검색"
```

첫 번째 버튼은 이름이 없다. 스크린 리더는 "버튼"이라고만 읽는다. 눈으로 보면 돋보기가 있지만, 그 SVG는 `aria-hidden`이라 이름 계산에서 빠진다. 이름을 붙이는 방법은 `aria-label`, 눈에 안 보이는 글자(sr-only), `aria-labelledby` 세 가지가 있다. 마우스를 올렸을 때 보이는 툴팁은 이름과 별개다. `title` 속성은 터치 기기와 키보드에서 보이지 않고 스크린 리더마다 다루는 방식이 달라서 이름의 유일한 출처로 쓰지 않는다.

디자인 시스템에서는 `IconButton`을 따로 두고 `aria-label`을 타입에서 필수로 만든다(타입 예시는 [디자인 시스템 만들기](/posts/design-system-building)에 있다). 툴팁을 함께 보여 준다면 툴팁의 글자와 `aria-label`을 같은 값에서 만들어, 보이는 이름과 들리는 이름이 어긋나지 않게 한다. 음성 명령으로 화면을 조작하는 사람은 보이는 글자를 말해서 버튼을 누르기 때문이다.

## Avatar: 이미지가 실패하는 순간

Avatar는 사진 하나를 보여 주는 단순한 부품처럼 보이지만, 상태 표를 그려 보면 행이 셋이다. 이미지를 불러오는 중, 불러왔음, 실패. 실패는 생각보다 흔하다. 프로필 사진을 지운 사용자, 만료된 CDN 주소, 회사 방화벽이 막은 외부 이미지가 다 여기에 온다.

없는 이미지를 그대로 그리면 브라우저는 깨진 이미지 아이콘이나 `alt` 글자를 40×40 칸에 억지로 그린다. 실험에서 404가 난 이미지는 이 상태였다.

```text
avatar: { complete: true, naturalWidth: 0 }
- img "김민지"
```

`complete`는 참인데 `naturalWidth`가 0이다. "다 불러왔는데 그림이 없다"는 뜻이고, 이 조합으로 실패를 알 수 있다. 흔한 구현은 `<img onError>`에서 이니셜로 바꾸는 것인데, 그러면 깨진 이미지가 한 프레임 보였다가 이니셜로 바뀌는 깜빡임이 생긴다. 처음부터 이니셜을 그려 두고, 이미지가 실제로 불러와졌을 때만 바꿔 끼우면 깜빡임이 없다.

```tsx
// avatar/hooks/use-image-status/use-image-status.ts
"use client";
import { useEffect, useState } from "react";

export type ImageStatus = "loading" | "loaded" | "error";

export function useImageStatus(src?: string): ImageStatus {
  const [status, setStatus] = useState<ImageStatus>(src ? "loading" : "error");
  useEffect(() => {
    if (!src) return setStatus("error");
    const img = new Image();
    img.onload = () => setStatus(img.naturalWidth > 0 ? "loaded" : "error");
    img.onerror = () => setStatus("error");
    img.src = src;                       // 캐시에 있으면 곧바로 onload가 온다
    setStatus(img.complete && img.naturalWidth > 0 ? "loaded" : "loading");
    return () => {
      img.onload = null;
      img.onerror = null;
    };
  }, [src]);
  return status;
}
```

화면은 `status`가 `loaded`일 때만 `<img>`를 그리고, 그 전에는 이니셜이나 기본 실루엣을 그린다. Radix의 Avatar 같은 헤드리스 라이브러리도 같은 방식으로, 이미지 로딩 상태를 보고 대체 내용을 언제 보일지 정한다. 느린 네트워크에서 이니셜이 잠깐 보였다가 사진으로 바뀌는 것도 깜빡임으로 느껴진다면, 대체 내용을 수백 밀리초 늦게 보여 주는 지연 옵션을 둔다.

`alt`도 상태 표에 들어간다. 아바타 바로 옆에 이름이 글자로 있으면 아바타는 장식이므로 `alt=""`로 두어 이름이 두 번 읽히지 않게 한다. 댓글 목록처럼 아바타만 있고 이름이 없으면 `alt="김민지"`가 이름 역할을 한다. 이니셜 대체 내용에도 같은 규칙을 적용한다. 이니셜 "민지"를 그대로 읽게 둘지, `aria-hidden`으로 숨기고 옆 글자에 맡길지를 Avatar API의 `decorative` 같은 prop으로 정한다.

## Badge: 99+와 스크린 리더 문구

알림 아이콘 위의 숫자 배지는 두 가지를 결정해야 한다. 큰 숫자를 어떻게 줄일지, 그리고 줄인 숫자를 보조 기술에 어떻게 알릴지.

화면에는 "99+"를 보여 주는 게 흔하다. 세 자리가 넘으면 원 모양이 깨지기 때문이다. 그런데 스크린 리더에 "99+"를 그대로 읽히면 "구십구 플러스"가 되고, 진짜 개수를 알 수 없다. 실험한 두 가지 마크업이다.

```html
<button class="btn">알림<span aria-hidden="true">99+</span><span class="sr-only">, 읽지 않은 알림 128개</span></button>
<button class="btn">알림<span aria-hidden="true">99+</span><span class="sr-only">(읽지 않음 128개)</span></button>
```

```text
- button "알림 , 읽지 않은 알림 128개"
- button "알림 (읽지 않음 128개)"
```

보이는 "99+"는 `aria-hidden`으로 빼고, 진짜 개수는 눈에 안 보이는 글자로 넣었다. 첫 번째는 글자 조각을 이어 붙이는 과정에서 쉼표 앞에 공백이 들어가 "알림 , 읽지 않은…"이 됐다. 읽을 때 큰 문제는 아니지만 이름이 지저분하고, 같은 내용이 반복된다. 두 번째처럼 짧게 붙이면 "알림 (읽지 않음 128개)"로 깔끔하다. 이름이 어떻게 합쳐지는지는 실제 접근성 트리로 확인해야 안다.

배지 숫자를 만드는 규칙도 컴포넌트 안에 둔다. 0이면 배지를 숨기고, 음수나 소수, 숫자가 아닌 값이 들어와도 깨지지 않게 한다. 직접 짜 보자. 보여 줄 글자(`text`, 숨기면 `null`)와 보조 기술용 문구(`srText`)를 돌려준다.

## Card: 카드 전체를 누르게 하기

글 목록의 카드는 어디를 눌러도 글로 가길 원한다. 가장 쉬운 방법은 카드 전체를 `<a>`로 감싸는 것인데, 두 가지 문제가 있다. 링크의 이름이 카드 안의 모든 글자(제목, 요약, 날짜, 작성자)를 이어 붙인 긴 문장이 되어 스크린 리더의 링크 목록이 읽기 어려워진다. 그리고 카드 안에 즐겨찾기 버튼이 있으면 링크 안에 버튼이 들어가는데, HTML은 대화형 요소 안에 대화형 요소를 넣는 것을 허용하지 않는다.

대안은 늘린 링크(stretched link)다. 링크는 제목에만 두고, 링크의 `::after` 가상 요소를 카드 전체로 펼쳐서 누를 수 있는 면적만 넓힌다.

```css
.card { position: relative; }
.card a::after { content: ""; position: absolute; inset: 0; }  /* 카드 전체를 덮는다 */
.card .fav { position: relative; z-index: 1; }                  /* 버튼은 그 위로 올린다 */
```

```html
<div class="card">
  <h3><a href="/posts/1">카드 제목</a></h3>
  <p>요약 문장</p>
  <button class="fav">즐겨찾기</button>
</div>
```

카드 오른쪽 아래 구석과 즐겨찾기 버튼 위에서 어느 요소가 눌리는지 `elementFromPoint`로 확인했다.

```text
hit corner: A/posts/1
- heading "카드 제목" [level=3]:
  - link "카드 제목":
    - /url: /posts/1
- paragraph: 요약 문장
- button "즐겨찾기"
hit fav: fav
```

구석을 눌러도 링크가 잡히고, 즐겨찾기 버튼 위에서는 버튼이 잡힌다. 접근성 트리에서 링크의 이름은 "카드 제목" 한 마디이고, 버튼은 링크 바깥에 따로 있다. 이 블로그의 글 목록도 같은 방식으로 제목 링크가 줄 전체를 덮고, 별 버튼을 `z-index: 1`로 올려 둔다.

늘린 링크에도 비용이 있다. 카드 안의 글자를 드래그로 선택하기 어려워진다(누르면 링크가 된다). 카드 안에 다른 링크가 여러 개면 각각 `z-index`로 올려야 하고, 하나라도 빠뜨리면 그 링크는 눌리지 않는다. 그리고 카드의 `position: relative`가 빠지면 `::after`가 바깥 조상까지 펼쳐져 페이지의 엉뚱한 부분이 링크가 된다. Card API에서 링크 자리를 `Card.Title href`처럼 정해 두고 이 CSS를 컴포넌트 안에 넣으면 이런 실수를 쓰는 사람이 할 수 없다.

## Banner와 List도 같은 표로

같은 틀을 나머지 부품에도 쓴다. 표의 행을 채우다 보면 빠진 결정이 드러난다.

Banner(페이지 상단 알림 띠)는 종류(정보, 성공, 경고, 오류)마다 색과 아이콘을 정하고, 어떤 역할로 알릴지를 정한다. 페이지를 열 때부터 있던 배너는 그냥 글자로 두면 된다. 동작의 결과로 새로 나타나는 배너만 알림이 필요하다. 저장 성공 같은 소식은 `role="status"`(공손하게 기다렸다 읽는다), 세션 만료처럼 바로 알아야 하는 것만 `role="alert"`(하던 말을 끊고 읽는다)로 한다. 모든 배너를 `alert`로 만들면 사용자가 알림에 무뎌진다. 배너가 포커스를 가져가면 안 된다는 것도 약속이다. 닫기 버튼이 있다면 닫은 뒤 다시 보이지 않게 할지, 그 기억을 어디에 둘지(배너 id를 키로 브라우저 저장소에 둘지, 서버에 둘지)까지가 API다.

List는 행이 하나 더 많다. 데이터가 있을 때, 불러오는 중, 비었을 때, 실패했을 때. 컴포넌트가 이 네 상태를 슬롯으로 받게 만들면(`emptyState`, `errorState`) 화면마다 빈 목록이 제각각인 문제가 사라진다. 마크업은 `<ul>`과 `<li>`로 두어 스크린 리더가 "목록, 항목 12개"를 알려 주게 하고, 항목을 누르는 목록이면 행 전체를 버튼이나 링크 하나로 만든다(Card와 같은 원리). 항목이 수천 개라 가상 스크롤을 쓰면 화면에 없는 항목은 DOM에 없으니 "항목 12개"가 실제 개수와 달라진다. 이때는 `aria-setsize`와 `aria-posinset`으로 전체 개수와 위치를 알려 준다.

## 결정을 적어 두는 기록

상태 표를 그리면서 내린 결정은 반드시 남긴다. 반년 뒤 누군가 "로딩 중에 왜 disabled를 안 쓰나요"라고 물으며 PR을 올렸을 때, 답이 기록에 있어야 같은 실수를 되풀이하지 않는다. 아키텍처 결정 기록(ADR)의 형식을 컴포넌트 단위로 줄여 쓰면 충분하다. ADR 형식 자체는 [C4 모델과 ADR](/posts/architecture-docs-c4-adr)에 있다.

```text
# Button-003: 로딩 상태는 disabled 대신 클릭 무시로 구현한다

상태: 채택 (2026-10)
맥락: 포커스를 가진 버튼을 disabled로 바꾸면 Chromium에서 포커스가 body로 떨어졌다.
      글자를 스피너로 바꾸면 너비가 98px에서 50px로 줄어 옆 버튼이 움직였다.
결정: loading 동안 aria-busy를 켜고 클릭·Enter·Space를 무시한다.
      글자는 opacity: 0으로 같은 격자 칸에 남겨 너비와 접근 이름을 유지한다.
      진행 알림은 라이브 리전으로 따로 보낸다.
버린 대안: visibility: hidden (접근 이름이 사라진다), min-width 고정 (번역 문구에서 깨진다)
결과: 두 번 누르기를 컴포넌트가 막지만, 결제 같은 요청은 서버 멱등 키가 최종 안전장치다.
```

기록에는 확인한 증거를 함께 둔다. 위 기록의 숫자는 이 글의 실험값이다. 증거가 있으면 결정을 바꾸자는 제안도 같은 실험으로 반박하거나 받아들일 수 있다. 기록은 Storybook의 해당 컴포넌트 문서 옆에 두면 쓰는 사람이 함께 본다.

## 다시 결제 버튼으로

처음 장면의 결제 버튼은 상태 표의 로딩 행 하나가 비어 있어서 생긴 일이다. 로딩 중 너비는 글자가 같은 칸에 남아 있어야 지켜지고, 이름은 그 글자를 `visibility`가 아닌 `opacity`로 숨겨야 지켜지고, 두 번 누르기는 컴포넌트와 호출하는 쪽과 서버가 함께 막는다. Avatar의 실패, Badge의 99+, Card의 클릭 면적, Banner의 알림 역할, List의 빈 상태도 같은 질문으로 정리된다. 어떤 상태가 있고, 상태마다 무엇이 보이고, 무엇을 누를 수 있고, 무엇이 들리는가. 그 답을 표로 그리고, 결정을 기록으로 남기면 컴포넌트 API는 거기서 나온다.

## 면접에서 나올 만한 질문

### 디자인 시스템의 Button을 설계한다면 무엇부터 하나?

props보다 상태 표부터 그린다. 기본, 호버, 포커스, 눌림, 비활성, 로딩 상태마다 보이는 것, 누를 수 있는지, 포커스를 받는지, 보조 기술에 무엇을 알리는지를 채운다. 그다음 모양과 크기 같은 축을 유니언 props로 나누고, type 기본값을 button으로 두고, 링크가 필요할 때를 위한 asChild나 as를 정한다. 결정은 기록으로 남긴다.

### 공용 Button의 type 기본값을 button으로 두는 이유는?

HTML button의 기본 type은 submit이라서, 폼 안에 둔 "비밀번호 보기" 같은 버튼이 누를 때마다 폼을 제출한다. 쓰는 사람 대부분이 이 기본값을 모르기 때문에 시스템이 안전한 쪽을 기본으로 가져가고, 제출 버튼만 type="submit"을 적게 한다.

### disabled와 aria-disabled는 어떻게 다른가?

둘 다 접근성 트리에 비활성으로 보이지만, 네이티브 disabled는 포커스를 받지 않고 클릭 이벤트도 막는다. aria-disabled는 포커스를 받아 이유를 들려줄 수 있지만 브라우저가 클릭을 막지 않아서, 실험에서도 클릭과 Enter가 그대로 들어왔다. 그래서 aria-disabled를 쓰면 컴포넌트가 클릭과 키 입력을 직접 막고 스타일도 입혀야 한다.

### 로딩 버튼에서 너비가 바뀌지 않게 하려면?

글자를 스피너로 바꾸지 말고, 글자와 스피너를 같은 격자 칸에 겹쳐 두고 글자만 투명하게 만든다. 그러면 너비는 늘 글자가 정한다. 실험에서 글자를 바꾸면 98px이 50px로 줄었고 겹치기는 98px을 유지했다. 이때 글자를 visibility: hidden으로 숨기면 접근성 트리에서도 빠져 버튼 이름이 사라지므로 opacity: 0으로 숨긴다.

### 로딩 중 두 번 클릭은 어디서 막나?

세 겹으로 막는다. 컴포넌트가 loading 동안 클릭을 무시하고, 호출하는 쪽이 진행 중인 요청을 다시 보내지 않고(React 19라면 useFormStatus의 pending), 결제처럼 중복 실행이 위험한 요청은 서버가 멱등 키로 한 번만 처리한다. 화면 표시만으로는 스피너가 그려지기 전의 빠른 두 번 누르기를 막지 못한다.

### Avatar 이미지가 실패할 때 깜빡임 없이 대체하려면?

onError에서 바꾸면 깨진 이미지가 한 프레임 보였다가 바뀐다. 처음부터 이니셜이나 실루엣을 그려 두고, Image 객체로 미리 불러와 naturalWidth가 0보다 클 때만 img로 바꿔 끼운다. 옆에 이름이 글자로 있으면 아바타는 장식이라 alt를 비우고, 이름이 없을 때만 alt가 이름 역할을 한다.

### 카드 전체를 클릭하게 할 때 카드를 a로 감싸지 않는 이유는?

링크 이름이 카드 안 모든 글자를 이어 붙인 긴 문장이 되고, 카드 안 즐겨찾기 버튼이 링크 안에 들어가 대화형 요소 중첩이 된다. 대신 제목에만 링크를 두고 ::after를 카드 전체로 펼치는 늘린 링크를 쓴다. 안쪽 버튼은 position: relative와 z-index로 올리고, 카드에 position: relative가 빠지지 않게 컴포넌트 안에 넣는다.
