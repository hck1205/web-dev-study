매주 월요일 아침, 데이터 과학자 한 명이 노트북을 열어 셀을 위에서부터 차례로 돌린다. 지난주 데이터를 뽑고, 특징을 만들고, 모델을 학습시키고, AUC를 확인하고, 괜찮으면 모델 파일을 S3에 올리고 서빙 팀에 메시지를 보낸다. 몇 달은 잘 돌았다.

어느 월요일, AUC가 0.72에서 0.78로 올랐다. 반가운 마음에 그대로 올렸다. 일주일 뒤 신규 가입자의 클릭률이 눈에 띄게 떨어졌다는 보고가 왔다. 원인은 그 주에 바뀐 데이터 추출 쿼리였다. 조인 조건이 바뀌면서 가입한 지 7일이 안 된 사용자 행이 대부분 빠졌다. 모델은 기존 사용자는 더 잘 배웠고, 기존 사용자가 85%라서 전체 AUC는 올랐다. 신규 사용자는 거의 못 본 채 학습됐다. 노트북에는 이걸 잡을 단계가 없었다.

이 글은 이 흐름을 파이프라인으로 바꾼다. 데이터 검증 → 특징 생성 → 학습 → 평가 → 승인 → 배포를 단계로 나누고, 코드 CI와 별도로 데이터와 모델을 시험하는 단계를 둔다. PR마다 학습 결과를 리포트로 붙이는 CML, Kubeflow Pipelines와 Airflow의 쓰임 차이, 재학습을 언제 돌릴지, 지속 학습이 자동 배포까지 가면 왜 위험한지를 다룬다. 실행 기록과 모델 레지스트리는 [실험 추적 글](/posts/ml-experiment-tracking)에서, 재학습 신호가 되는 드리프트는 [모델 모니터링 글](/posts/ml-model-monitoring-drift)에서 다뤘다. 일반적인 CI/CD 개념은 [CI/CD 기초 글](/posts/ci-cd-basics)에 있다.

실습은 Python 3.13, scikit-learn 1.9.1, DVC 3.67.1, KFP SDK 2.17.3으로 했다.

## ML의 CI는 코드, 데이터, 모델을 따로 시험한다

일반 서비스의 CI는 코드를 시험한다. 같은 코드면 같은 결과가 나오니 코드만 시험하면 된다. ML은 같은 코드라도 데이터가 바뀌면 다른 모델이 나온다. 그래서 시험할 대상이 셋이다.

코드 테스트는 일반 단위 테스트와 같다. 특징을 만드는 함수가 빈 입력, 결측, 경계값에서 기대대로 동작하는지 본다. "최근 7일 구매 수" 함수에 정확히 7일 전 0시의 주문을 넣었을 때 포함되는지 같은 테스트다. 학습 코드에는 작은 표본(수백 행)으로 몇 초 만에 끝나는 학습 스모크 테스트를 둔다. 학습이 에러 없이 끝나고, 출력 모양이 맞고, 손실이 줄어드는지만 확인한다. 이건 PR마다 돌린다. 단위 테스트를 쓰는 법은 [테스트 피라미드 글](/posts/test-pyramid-unit-tests)에 있다.

데이터 테스트는 파이프라인이 돌 때마다 그날 데이터로 돈다. 스키마(컬럼과 타입), 결측률, 값의 범위, 행 수, 구간별 비율, 학습 기간에 미래 데이터가 섞이지 않았는지를 본다. 처음 장면의 "신규 사용자 비율 1%"는 이 단계에서 잡혀야 했다. 규칙은 Great Expectations, pandera 같은 도구로 선언하거나 직접 짠다. 구체적인 검사 예는 [모델 모니터링 글](/posts/ml-model-monitoring-drift)의 데이터 품질 부분에 있다.

모델 테스트는 학습이 끝난 뒤 돈다.

- 기준선 비교: 현재 운영 모델(champion)과 같은 시험 세트에서 비교한다. 절대 기준(AUC 0.7 이상)만 두면 조금씩 나빠지는 걸 못 막는다.
- 구간별 비교: 신규·기존 사용자, 국가, 기기처럼 중요한 구간마다 따로 비교한다.
- 행동 테스트: 결과가 바뀌면 안 되는 입력 변화(이름 철자만 바꾼 리뷰)에 예측이 그대로인지, 바뀌어야 하는 변화(별점 1과 5)에 기대한 방향으로 움직이는지 몇십 개 예시로 확인한다.
- 서빙 조건: 모델 크기, 한 건 추론 지연, 메모리가 서빙 환경의 한도 안인지 본다.

### 행동 테스트를 pytest로 걸어 보면

지표 숫자로는 안 보이는 이상한 행동이 있다. 이탈 예측 모델을 예로 들면 "마지막 접속 뒤 지난 날이 늘수록 이탈 확률이 떨어지면 안 된다", "국가만 바꿨을 때 예측이 크게 바뀌면 안 된다(이 데이터에서 국가는 이탈과 무관하다)" 같은 기대가 있다. 이걸 pytest 테스트로 적는다.

```python
@pytest.fixture(scope="module")
def model():
    return HistGradientBoostingClassifier(random_state=0).fit(X, y)   # X: 지난 날, 세션 수, 국가

def churn(m, days, sess, c=0):
    return m.predict_proba([[days, sess, c]])[0, 1]

def test_more_idle_days_never_lowers_churn(model):
    probs = [churn(model, d, 5) for d in range(0, 60, 5)]
    drops = [(a, b) for a, b in zip(probs, probs[1:]) if b < a - 0.02]   # 0.02 넘게 떨어지는 구간
    assert not drops, f"접속 안 한 날이 늘었는데 이탈 확률이 떨어진 구간: {len(drops)}개"

@pytest.mark.parametrize("c", [1, 2])
def test_country_does_not_change_prediction(model, c):
    base, other = churn(model, 20, 5, 0), churn(model, 20, 5, c)
    assert abs(base - other) < 0.05, f"국가만 바꿨는데 {base:.3f} -> {other:.3f}"
```

데이터 5천 건(정답은 지난 날과 세션 수로만 정했다)으로 학습한 그래디언트 부스팅 모델에 돌렸다.

```text
E       AssertionError: 접속 안 한 날이 늘었는데 이탈 확률이 떨어진 구간: 2개
E       AssertionError: 국가만 바꿨는데 0.596 -> 0.657
2 failed, 1 passed
```

유연한 모델이 표본의 우연한 흔들림까지 배워서 두 가지 기대를 모두 어겼다. AUC 같은 평균 지표로는 이런 건 안 보인다. 여기서는 단조 제약(`monotonic_cst=[1, -1, 0]`, 지난 날은 증가, 세션 수는 감소 방향만 허용)을 주고 다시 학습했더니 세 테스트가 모두 통과했다(`3 passed`). 제약을 줄 수 없는 모델이라면 문제가 된 특징을 빼거나 규제(regularization)를 세게 건다. 이런 테스트는 정답이 하나로 정해지지 않아서 허용치(위의 0.02, 0.05)를 두고, 몇십 개 대표 예시로만 돌린다.

## 전체 AUC가 올랐는데 내보내면 안 되는 모델

처음 장면을 재현해 보자. 신규 사용자(15%)와 기존 사용자의 클릭 규칙이 다르게 만든 가짜 데이터로, 운영 모델(로지스틱 회귀)과 후보 모델(그래디언트 부스팅)을 비교했다. 후보는 신규 사용자 행의 95%가 빠진 데이터로 학습했다.

```python
keep = (g_train == 0) | (rng.random(len(g_train)) < 0.05)   # 신규 사용자 행 대부분이 빠진 데이터
cand = HistGradientBoostingClassifier(random_state=0).fit(X_train[keep], y_train[keep])

def report(model):
    s = model.predict_proba(X_test)[:, 1]
    p = (s >= 0.5).astype(int)
    out = {"auc": roc_auc_score(y_test, s)}
    for name, gv in [("existing", 0), ("new", 1)]:
        mask = g_test == gv
        out[f"auc_{name}"] = roc_auc_score(y_test[mask], s[mask])
        out[f"recall_{name}"] = recall_score(y_test[mask], p[mask])
    return out
```

```text
champion {'auc': 0.7242, 'auc_existing': 0.7106, 'recall_existing': 0.2958, 'auc_new': 0.7989, 'recall_new': 0.4241}
candidate {'auc': 0.7843, 'auc_existing': 0.795, 'recall_existing': 0.4709, 'auc_new': 0.7398, 'recall_new': 0.3215}
new share test 0.1485 new share cand train 0.01 rows 17123
```

전체 AUC만 보면 0.7242 → 0.7843, 확실한 개선이다. 그런데 신규 사용자 구간은 AUC 0.7989 → 0.7398, 재현율 0.4241 → 0.3215로 나빠졌다. 기존 사용자가 85%라 전체 평균을 끌고 간 것이다. 학습 데이터의 신규 사용자 비율이 1%였다는 것도 보인다. 시험 세트는 14.85%다.

같은 방식으로 공정성 검사도 한다. 성별이나 나이대처럼 차별이 문제 되는 속성이 있는 서비스(대출, 채용, 보험)라면, 구간 사이의 재현율 차이(기회 균등)나 양성 예측 비율 차이(인구 통계 동등성)를 계산해 기준을 넘으면 막는다. 두 기준을 동시에 만족시키는 건 일반적으로 불가능해서 어떤 기준을 쓸지는 법무·정책과 함께 정한다. Fairlearn 같은 라이브러리가 이런 지표를 계산해 준다.

이 판단을 함수로 만들어 보자. 후보와 운영 모델의 지표를 받아 승격 여부와 걸린 이유를 돌려준다. 규칙은 셋이다. 전체 AUC가 떨어지면 안 된다. 운영 모델에 있는 구간마다 후보 AUC가 허용치(tol)보다 많이 떨어지면 안 되고, 후보에 그 구간 값이 없으면 그것도 실패다. p95 지연이 운영 모델의 1.2배를 넘으면 안 된다.

## PR마다 학습 결과를 붙인다: CML

코드 리뷰에서 "이 PR이 모델을 얼마나 바꾸나"를 보고 싶다. 특징 하나를 추가하는 PR이라면 리뷰어는 코드보다 지표 변화가 더 궁금하다. CML(Continuous Machine Learning)은 DVC를 만든 Iterative가 만든 도구로, CI 잡 안에서 학습을 돌리고 결과를 PR 댓글로 남기는 일을 맡는다. GitHub Actions와 GitLab CI에서 쓸 수 있다. GitHub Actions 워크플로 자체는 [GitHub Actions 글](/posts/github-actions-workflows)에서 다뤘다.

워크플로는 형식이 대략 이렇다.

```yaml
name: train-report
on: pull_request
jobs:
  train:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write          # PR 댓글을 달려면 필요
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0            # main과 비교하려면 전체 기록이 필요
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
      - uses: iterative/setup-cml@v2
      - run: pip install -r requirements.txt
      - name: 학습하고 리포트 남기기
        env:
          REPO_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          AWS_ACCESS_KEY_ID: ${{ secrets.DVC_AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.DVC_AWS_SECRET_ACCESS_KEY }}
        run: |
          dvc pull
          dvc repro
          git fetch origin main:main
          echo "## 파라미터" > report.md
          dvc params diff main --md >> report.md
          echo "## 지표" >> report.md
          dvc metrics diff main --md >> report.md
          cml comment create report.md
```

리포트에 들어가는 표는 실제로 이렇게 나온다. 랜덤 포레스트의 `max_depth`를 4에서 8로 바꾼 작업 공간을 기본 브랜치와 비교했다. 실습 저장소의 기본 브랜치 이름이 master라 열 이름이 master로 나온다.

```text
| Path        | Param           | master   | workspace   |
|-------------|-----------------|----------|-------------|
| params.yaml | train.max_depth | 4        | 8           |

| Path         | Metric   | master   | workspace   | Change   |
|--------------|----------|----------|-------------|----------|
| metrics.json | test_auc | 0.8965   | 0.9477      | 0.0512   |
```

예전 CML 버전의 명령 이름은 `cml send-comment`였고 지금은 `cml comment create`다. 오래된 예제를 복사할 때 확인한다.

PR CI에서 전체 데이터로 몇 시간짜리 학습을 돌리면 PR마다 비용이 크고 리뷰가 느려진다. 그래서 PR에서는 표본 데이터로 빠르게 돌려 방향만 확인하고, 전체 학습은 main에 합친 뒤 학습 파이프라인이 돌게 나누는 팀이 많다. GitHub Actions는 포크에서 온 PR의 `pull_request` 실행에 비밀 값을 넘기지 않는다. 이걸 피하려고 `pull_request_target`으로 바꿔 데이터 저장소 키를 넘기면, 누구나 학습 코드를 고친 PR로 그 키와 데이터를 빼 갈 수 있다.

## 학습 파이프라인을 돌리는 곳: Kubeflow Pipelines와 Airflow

PR CI는 "이 변경이 괜찮나"를 본다. 매주 새 데이터로 다시 학습하는 일은 CI가 아니라 학습 파이프라인을 돌리는 오케스트레이터가 맡는다. 많이 비교되는 둘이 Kubeflow Pipelines와 Airflow다.

Kubeflow Pipelines(KFP)는 쿠버네티스 위에서 ML 파이프라인을 돌리는 데 특화돼 있다. 단계마다 컨테이너 하나가 뜨고, 단계 사이에는 데이터셋·모델 같은 아티팩트가 객체 저장소를 거쳐 넘어간다. 파이썬 함수로 단계를 쓰고 YAML로 컴파일한다.

```python
from kfp import dsl, compiler
from kfp.dsl import Dataset, Input, Model, Output, Metrics

@dsl.component(base_image="python:3.12", packages_to_install=["pandas==3.1.0"])
def validate(raw: Input[Dataset], clean: Output[Dataset]):
    import pandas as pd
    df = pd.read_csv(raw.path)
    assert df["user_id"].notna().all(), "user_id 결측"
    assert df["is_new"].mean() > 0.05, "신규 사용자 비율이 너무 낮다"   # 처음 장면을 막는 검사
    df.to_csv(clean.path, index=False)

@dsl.component(base_image="python:3.12", packages_to_install=["scikit-learn==1.9.1", "pandas==3.1.0"])
def train(data: Input[Dataset], max_depth: int, model: Output[Model], metrics: Output[Metrics]):
    import pandas as pd, pickle
    from sklearn.ensemble import RandomForestClassifier
    df = pd.read_csv(data.path)
    m = RandomForestClassifier(max_depth=max_depth, random_state=42).fit(
        df.drop(columns="churned"), df["churned"])
    pickle.dump(m, open(model.path, "wb"))
    metrics.log_metric("train_rows", len(df))

@dsl.pipeline(name="churn-retrain")
def churn_pipeline(raw_uri: str, max_depth: int = 8):
    raw = dsl.importer(artifact_uri=raw_uri, artifact_class=Dataset)
    v = validate(raw=raw.output)
    train(data=v.outputs["clean"], max_depth=max_depth)

compiler.Compiler().compile(churn_pipeline, "churn_pipeline.yaml")
```

컴파일된 YAML(188줄)을 보면 단계 사이 의존과 캐시 설정이 들어 있다.

```text
      train:
        cachingOptions:
          enableCache: true
        componentRef:
          name: comp-train
        dependentTasks:
        - validate
        inputs:
          artifacts:
            data:
              taskOutputArtifact:
                outputArtifactKey: clean
                producerTask: validate
```

`enableCache: true`라서 입력과 단계 정의가 같으면 이전 결과를 재사용한다. 각 아티팩트가 어느 단계에서 나왔는지 메타데이터로 남아서 "이 모델은 어느 데이터셋에서 나왔나"를 UI에서 따라갈 수 있다. 구글 클라우드의 Vertex AI Pipelines는 이 KFP 형식을 그대로 받아 관리형으로 돌린다.

Airflow는 범용 워크플로 스케줄러다. 언제 무엇을 어떤 순서로 돌릴지, 실패하면 재시도할지, 지난 날짜를 다시 채울지(백필)에 강하다. 데이터 구간과 백필은 [Airflow 글](/posts/airflow-orchestration)에서 다뤘다. 반면 태스크 사이로 큰 데이터를 넘기는 기능(XCom)은 작은 값용이라, 학습 데이터나 모델은 S3 같은 곳에 쓰고 경로만 넘긴다. GPU 학습은 Airflow 워커에서 직접 하지 않고 `KubernetesPodOperator`나 SageMaker·Vertex 연산자로 밖에 맡긴다.

고르는 기준은 대체로 이렇다. 이미 데이터 팀이 Airflow로 ETL을 돌리고 있고 학습이 그 뒤에 붙는 단계 하나라면 Airflow에 학습 DAG를 추가하는 게 운영 부담이 적다. 쿠버네티스 위에서 GPU 학습 단계가 많고, 단계별 캐시와 아티팩트 계보가 중요하면 KFP가 맞다. 둘을 같이 쓰기도 한다. Airflow가 데이터 준비를 끝내면 KFP 파이프라인 실행을 트리거하는 식이다. 이 밖에 Argo Workflows(KFP의 실행 엔진으로도 쓰인다), Prefect, Dagster, Metaflow, SageMaker Pipelines도 같은 자리를 놓고 경쟁한다.

## 배포 단계는 서빙 방식에 따라 다르다

파이프라인의 마지막 "배포"가 무엇을 뜻하는지는 모델을 어떻게 쓰느냐에 따라 다르다. 배치 예측이면 다음 배치 잡이 새 모델 버전을 읽게 하는 것이고, 새 모델의 점수 테이블을 기존 테이블 옆에 따로 만들어 분포를 비교한 뒤 바꿔치기하면 섀도 단계를 거의 공짜로 둘 수 있다. 온라인 서빙이면 새 모델이 실린 컨테이너를 [카나리 릴리스](/posts/canary-release)나 [블루-그린 배포](/posts/blue-green-deployment)로 내보내는 일이라 일반 서비스 배포와 같다.

파이프라인 쪽에서 정할 것은 하나다. 모델 파일을 이미지에 굽느냐, 서버가 시작할 때 레지스트리에서 받느냐. 이미지에 구우면 이미지 태그 하나가 코드와 모델을 함께 가리켜 되돌리기가 명확하고, 시작할 때 받으면 이미지를 다시 만들지 않아도 되지만 시작이 느려지고 레지스트리가 장애 지점이 된다. 배치와 온라인 추론을 고르는 기준, 섀도·카나리·A/B로 넘기는 순서는 [모델 서빙 글](/posts/model-serving)에서 다뤘다.

## 언제 다시 학습하나: 일정과 드리프트

파이프라인이 있으면 다음 질문은 언제 돌리느냐다.

일정 기반은 매일, 매주처럼 정해진 시각에 돈다. 단순하고 예측 가능하며, 비용과 검토 일정을 미리 잡을 수 있다. 대신 아무것도 안 바뀌었는데도 돌고, 갑작스러운 변화에는 다음 일정까지 기다려야 한다.

트리거 기반은 조건이 맞을 때 돈다. 새 데이터가 일정량 쌓였을 때, 드리프트 지표가 임계값을 넘었을 때, 성능 지표가 떨어졌을 때다. 필요할 때만 돌지만, 드리프트 경보가 오탐이면 쓸데없이 돌고, 경보가 못 잡는 개념 드리프트에는 반응하지 않는다. 드리프트를 어떻게 재는지는 [모델 모니터링 글](/posts/ml-model-monitoring-drift)에 있다.

얼마나 자주 돌려야 하는지는 데이터로 정한다. 과거 데이터로 "1월 데이터로 학습한 모델을 2월, 3월, 4월에 평가"하는 식으로 시간이 지날수록 성능이 얼마나 빨리 떨어지는지 재 본다. 한 달에 0.5%p 떨어지면 매주 돌릴 이유가 없고, 일주일 만에 크게 떨어지면 매일 돌려야 한다. 대부분은 일정 기반을 기본으로 두고, 드리프트나 성능 경보가 오면 일정을 앞당기는 방식을 쓴다.

## 지속 학습이 자동 배포까지 가면 위험한 이유

학습 파이프라인을 자동화하는 것을 지속 학습(CT, continuous training)이라고 부른다. 여기서 한 걸음 더 가면 "학습이 끝나고 평가를 통과하면 사람 없이 바로 운영에 배포"가 된다. 기술적으로는 쉽지만 위험하다.

망가진 데이터가 바로 운영으로 간다. 처음 장면처럼 업스트림 쿼리 하나가 바뀌면, 사람이 손으로 하던 시절에는 누군가 "어, 행 수가 왜 이렇지"라고 볼 기회라도 있었다. 자동 배포는 그 기회를 없앤다. 데이터 검증 규칙이 그 버그를 예상하지 못했다면 아무도 모르게 나간다.

평가 세트도 같이 망가진다. 매번 최신 데이터로 학습하고 같은 파이프라인에서 시험 세트도 새로 뽑으면, 데이터가 망가질 때 시험 세트도 함께 망가져서 "망가진 시험에서 높은 점수"가 나온다. 사람이 검토한 고정 평가 세트(골든 세트)를 따로 두고 매번 그걸로도 비교한다.

되먹임이 빨라진다. 모델이 보여 준 것만 클릭되고, 그 클릭으로 다음 모델을 학습하면 모델은 점점 자기가 고른 것만 좋다고 배운다. 사람이 끼어 있으면 주기가 느려 이 고리가 천천히 돌지만, 하루 단위 자동 배포에서는 몇 주 만에 추천이 좁아질 수 있다.

공격받기 쉬워진다. 사용자 행동이 다음 날 모델에 바로 반영되면, 가짜 계정으로 클릭을 만들어 특정 상품을 올리는 데이터 오염 공격의 효과가 빨리 나타난다.

그래서 많은 팀이 학습과 평가까지는 자동으로 돌리고, 운영 승격에는 사람의 승인을 둔다. 자동 배포를 한다면 안전장치를 겹겹이 둔다.

- 데이터 검증과 승격 관문(위의 `gate`)을 통과하지 못하면 멈춘다.
- 골든 세트와 구간별 지표로도 비교한다.
- 섀도 배포로 실제 트래픽에서 점수 분포를 먼저 본다.
- [카나리 릴리스](/posts/canary-release)로 일부 트래픽에만 내보내고, 서비스 지표가 떨어지면 자동으로 이전 버전으로 되돌린다.
- 한 번에 바뀔 수 있는 폭을 제한한다(예: 예측 분포가 직전 모델과 너무 다르면 사람에게 넘긴다).

## 파이프라인을 만들고 나서 흔한 실수

학습과 서빙이 특징을 따로 계산한다. 학습 파이프라인은 SQL로, 서빙은 애플리케이션 코드로 같은 특징을 다시 짜면 언젠가 둘이 어긋난다. 특징 정의를 한 곳(공용 라이브러리나 피처 스토어)에 두고 양쪽이 같은 코드를 쓴다.

파이프라인 단계가 다시 돌리면 다른 결과를 낸다. "오늘 기준 최근 7일"처럼 실행 시각에 의존하면 어제 실패한 실행을 오늘 다시 돌렸을 때 다른 데이터가 들어간다. 실행에 데이터 구간을 인자로 넘기고, 같은 인자면 같은 결과가 나오게 만든다.

평가 단계가 운영 모델을 다시 평가하지 않는다. 지난달에 기록한 운영 모델의 점수와 오늘 학습한 후보의 점수를 비교하면 시험 세트가 달라서 비교가 안 된다. 같은 시험 세트에서 둘을 함께 다시 평가한다.

모델은 배포했는데 파이프라인 코드는 리뷰 없이 바꾼다. 학습 코드도 서비스 코드만큼 운영에 영향을 준다. 파이프라인 정의도 PR과 CI를 거친다.

실패 알림이 없다. 예약된 학습이 3주째 실패하고 있는데 아무도 몰라서 3주 전 모델이 계속 돈다. 학습 파이프라인의 성공·실패와 "마지막으로 성공한 학습 시각"도 지표로 올리고 경보를 건다.

## 자동화할수록 관문이 중요해진다

ML 파이프라인은 노트북의 셀을 단계로 나누고 단계마다 통과 조건을 두는 일이다. CI는 코드뿐 아니라 데이터와 모델을 따로 시험하고, 모델 시험은 운영 모델과 같은 시험 세트에서 전체·구간별·서빙 조건을 함께 본다. 전체 AUC가 0.72에서 0.78로 올랐는데 신규 사용자 구간은 떨어진 후보처럼, 평균은 많은 것을 가린다. CML은 PR마다 지표 변화를 리뷰어 앞에 놓고, KFP나 Airflow는 정기 재학습을 돌린다. 학습까지 자동화해도 운영 승격에는 관문과 사람의 확인, 카나리와 자동 되돌리기를 겹쳐 둔다. 배포한 모델을 지켜보는 일은 [모델 모니터링 글](/posts/ml-model-monitoring-drift), 기기 안에서 모델을 돌리는 경우는 [엣지 AI 글](/posts/edge-ai-on-device)에서 이어진다.

## 면접에서 나올 만한 질문

### ML CI에서는 무엇을 테스트하나요?

코드, 데이터, 모델을 따로 시험한다. 코드는 특징 함수의 단위 테스트와 작은 표본으로 몇 초 만에 끝나는 학습 스모크 테스트를 PR마다 돌린다. 데이터는 파이프라인이 돌 때마다 스키마, 결측률, 값 범위, 행 수, 구간 비율을 검사한다. 모델은 학습 뒤 운영 모델과 같은 시험 세트에서 전체·구간별 지표, 행동 테스트, 지연과 크기를 비교한다.

### 전체 지표가 좋아졌는데도 배포를 막아야 하는 경우는요?

중요한 구간에서 성능이 떨어진 경우다. 신규 사용자 행이 빠진 데이터로 학습한 후보는 전체 AUC가 0.7242에서 0.7843으로 올랐지만 신규 사용자 구간은 0.7989에서 0.7398로 떨어졌다. 기존 사용자가 85%라 평균이 가려 준 것이다. 그래서 구간별 허용치를 두고, 후보가 구간 지표를 내지 않으면 그것도 실패로 처리한다. 허용치는 구간 지표가 평소 흔들리는 폭을 보고 정한다.

### 지속 학습(CT)이 자동 배포까지 가면 왜 위험한가요?

업스트림 데이터 버그가 사람의 눈을 거치지 않고 바로 운영으로 가기 때문이다. 같은 파이프라인에서 시험 세트도 뽑으면 망가진 데이터로 만든 시험에서 높은 점수가 나온다. 모델이 고른 것만 정답이 생기는 되먹임과, 사용자 행동을 조작하는 데이터 오염의 효과도 빨라진다. 그래서 학습·평가는 자동으로 하되 승격에는 사람 승인을 두거나, 골든 세트·섀도 배포·카나리·자동 되돌리기를 겹쳐 둔다.

### Kubeflow Pipelines와 Airflow는 어떻게 다르고 언제 무엇을 쓰나요?

KFP는 쿠버네티스 위에서 단계마다 컨테이너를 띄우고 단계 사이에 데이터셋·모델 아티팩트를 넘기며, 단계 캐시와 아티팩트 계보를 남기는 ML 특화 도구다. Airflow는 일정, 재시도, 백필에 강한 범용 스케줄러로, 큰 데이터는 외부 저장소 경로로 넘기고 GPU 학습은 쿠버네티스 파드나 관리형 서비스에 맡긴다. 이미 Airflow로 ETL을 돌리면 학습 DAG를 붙이고, GPU 단계가 많고 계보가 중요하면 KFP를 쓴다. Airflow가 데이터 준비 뒤 KFP를 트리거하는 조합도 흔하다.

### CML은 어떤 문제를 푸나요?

PR 리뷰에서 코드 변경이 모델 지표를 얼마나 바꾸는지 보이게 한다. CI 잡에서 `dvc pull`과 `dvc repro`로 학습하고, `dvc metrics diff main --md`로 만든 표와 그래프를 `cml comment create`로 PR 댓글에 단다. GPU가 필요하면 클라우드 러너를 띄워 쓴다. PR마다 전체 학습을 돌리면 비싸니 표본으로 방향만 보고 전체 학습은 병합 뒤 파이프라인에 맡기는 경우가 많다.

### 재학습 주기는 어떻게 정하나요?

과거 데이터로 한 시점에 학습한 모델을 다음 달, 그다음 달에 평가해 성능이 얼마나 빨리 떨어지는지 재 보고 정한다. 일정 기반은 단순하고 예측 가능하지만 변화에 늦고, 드리프트·성능 트리거는 필요할 때만 돌지만 오탐과 놓침이 있다. 보통 일정 기반을 기본으로 두고 경보가 오면 앞당긴다. 학습이 조용히 실패해 옛 모델이 계속 도는 일을 막으려면 마지막 성공 시각에도 경보를 건다.

### 학습-서빙 차이는 파이프라인에서 어떻게 막나요?

특징 정의를 한 곳에 두고 학습과 서빙이 같은 코드를 쓰게 한다. 공용 라이브러리나 피처 스토어가 그 역할을 한다. 서빙 시점에 모델이 실제로 받은 특징 값을 로그로 남겨, 같은 요청을 학습 파이프라인 방식으로 다시 계산한 값과 주기적으로 비교한다. 단계는 실행 시각이 아니라 데이터 구간을 인자로 받아 같은 인자면 같은 결과가 나오게 만든다.
