이 시리즈에서 이 글의 자리: 같은 장의 첫 글 [결제 시스템 설계 ①: 돈이 움직이는 길과 복식부기 원장](/posts/sd-payment-flow)에서 PSP와 호스티드 결제 페이지, 결제 건의 상태, 합이 0인 원장을 만들었다. 모든 요청이 한 번에 성공하는 경우였다. 이 글은 그 반대, 응답이 끊기고 웹훅이 두 번 오거나 안 오고, 우리 장부와 PSP 기록이 어긋나는 경우를 다룬다. 다음 글은 새 장인 [디지털 지갑 설계 ①](/posts/sd-wallet-transfer)이다.

고객 센터에 문의가 들어온다. "주문은 하나인데 카드에서 15,000원이 세 번 빠져나갔어요." 주문 서비스 로그에는 결제 실패만 찍혀 있다. 결제 서비스 로그를 보니 PSP 호출이 세 번 다 시간 초과였다. 우리 쪽에서는 한 번도 성공한 적이 없는데, 구매자의 카드에서는 세 번 다 돈이 나갔다.

이 글은 앞 글에서 만든 가짜 PSP(Node 22)와 결제 서비스, PostgreSQL 16 원장으로 이런 사고를 하나씩 재현하고 막는다. 가짜 PSP에는 응답을 늦추고, 웹훅을 잃어버리고, 같은 웹훅을 두 번 보내는 고장 스위치를 달았다.

## 시간 초과는 실패가 아니다

저장된 카드로 바로 청구하는 서버 간 API를 부른다고 하자. 결제 서비스는 PSP 응답을 200ms까지 기다리고, 넘으면 끊고 다시 보낸다. 가짜 PSP는 카드 청구를 끝낸 뒤 응답만 500ms 늦게 보내게 했다.

```text
--- without Idempotency-Key
[psp] charged card: pi_1 order=po_3001 amount=15000
[svc] attempt 1: TimeoutError after 200ms
[psp] charged card: pi_2 order=po_3001 amount=15000
[svc] attempt 2: TimeoutError after 200ms
[psp] charged card: pi_3 order=po_3001 amount=15000
[svc] attempt 3: TimeoutError after 200ms
PSP charges for po_3001: 3
```

처음의 문의가 그대로 나왔다. 결제 서비스는 세 번 다 실패로 봤고, PSP는 세 번 다 청구했다. 문제는 시간 초과를 "실패"로 읽은 데 있다. 시간 초과는 "모른다"는 뜻이다.

## 같은 키로 다시 보내면 PSP가 알아본다

앞 글에서 결제 건 ID(`po_3002`)를 PSP에 멱등성 키로 보낸다고 했다. 같은 조건에서 `Idempotency-Key` 헤더를 붙여 다시 돌렸다.

```text
--- with Idempotency-Key
[psp] charged card: pi_4 order=po_3002 amount=15000
[svc] attempt 1: TimeoutError after 200ms
[psp] same Idempotency-Key po_3002 -> pi_4 (replayed, no new charge)
[svc] attempt 2: 200 pi_4 succeeded
PSP charges for po_3002: 1
```

첫 시도는 똑같이 시간 초과였다. 두 번째 시도에서 PSP는 이 키를 이미 처리했다는 걸 알아보고 새로 청구하지 않은 채 첫 결과(`pi_4`)를 다시 돌려줬다. 카드 청구는 한 번뿐이다.

키는 "이 결제 건"을 가리켜야 한다. 시도마다 새 UUID를 만들면 키가 매번 달라 아무것도 막지 못한다. 그래서 재시도 루프 밖에서, 결제 건을 만들 때 정한 ID를 쓴다. 같은 키에 금액이 다른 요청이 오면 PSP는 거절해야 하고, 실제 PSP들도 보통 그렇게 한다. 키를 얼마나 오래 기억하는지, 처리 중인 키로 동시에 요청이 오면 어떻게 답하는지(기다리게 하거나 충돌 오류를 주거나)는 PSP마다 다르니 연동 문서에서 확인한다.

PSP가 키를 알아보는 원리, 그리고 우리 API가 브라우저의 중복 클릭을 같은 방식으로 막을 때 키 저장소를 어떻게 만드는지는 [멱등성 키](/posts/idempotency-key)에서 동시 요청과 서버가 죽는 경우까지 실험했다. 여기서는 결제에서 키가 붙어야 하는 자리만 짚고 넘어간다.

## 다시 보낼 실패, 멈출 실패, 모르는 실패

모든 실패를 재시도하면 안 된다. 실패는 세 종류로 나눠 다룬다.

- 다시 보낼 실패: 시간 초과, 연결 끊김, PSP의 5xx, `429 Too Many Requests`. 일시적일 가능성이 높다. 멱등성 키를 붙인 채로 간격을 늘려 가며 다시 보낸다. 서버가 `Retry-After`로 기다릴 시간을 알려 주면 따른다.
- 멈출 실패: 카드 거절, 한도 초과, 잘못된 카드 번호 같은 4xx. 몇 번을 보내도 결과가 같다. 바로 `FAILED`로 두고 구매자에게 다른 카드를 쓰라고 안내한다.
- 모르는 실패: 재시도를 다 써도 답을 못 받았다. 이건 `FAILED`가 아니다. 돈이 빠져나갔을 수도 있다. 결제 건은 `EXECUTING`에 그대로 두고, 웹훅이나 상태 조회, 대사로 결과가 확정될 때까지 기다린다.

간격은 보통 지수적으로 늘린다. 처음 실험 코드는 50ms, 100ms, 200ms로 두 배씩 늘렸다.

## 한 번만 청구하려면 구간마다 거른다

"결제는 정확히 한 번(exactly-once) 처리돼야 한다"는 요구는 사실 두 약속의 합이다. 잃어버리지 않게 될 때까지 다시 보내는 것(at-least-once), 그리고 여러 번 도착해도 효과는 한 번만 나게 거르는 것(at-most-once 효과). 재시도는 첫 번째를, 멱등성 키와 중복 검사는 두 번째를 맡는다.

이 두 약속은 메시지가 지나는 구간마다 따로 지켜야 한다. 한 구간이라도 빠지면 거기서 두 번 처리된다.

브라우저에서 결제 버튼을 두 번 누르면 같은 장바구니 ID로 결제 이벤트를 만들려다 유니크 제약에 걸린다. 결제 서비스에서 PSP로는 멱등성 키, PSP에서 우리로 오는 웹훅은 이벤트 ID, 원장은 `(kind, ref)` 유니크 제약이 거른다. 큐에서 주문 서비스로 넘어가는 구간은 받는 쪽이 처리한 메시지 ID를 기억하는 인박스 테이블로 거른다. 큐 구간의 장치들은 [메시지 전달 보장](/posts/message-delivery-semantics)에서 자세히 다뤘다.

## 웹훅은 두 번 오고, 가짜가 오고, 안 온다

PSP에서 우리로 오는 구간을 실험으로 확인한다. 웹훅을 받는 코드에서 중요한 부분만 옮기면 이렇다.

```js
// 1) 서명 확인: PSP와 나눈 비밀 키로 "시각.본문"의 HMAC을 만들어 비교한다
if (!verifySignature(req.headers["psp-signature"], raw)) return reply(400);
await c.query("BEGIN");
// 2) 같은 이벤트를 이미 받았으면 아무것도 하지 않는다
const ins = await c.query(
  "INSERT INTO psp_webhook_events (event_id, intent_id, type) VALUES ($1,$2,$3) ON CONFLICT DO NOTHING",
  [ev.id, ev.intent_id, ev.type]);
if (ins.rowCount === 0) { await c.query("ROLLBACK"); return reply(200); }
// 3) 상태는 앞으로만 간다: EXECUTING일 때만 바꾸고, 바뀐 경우에만 원장에 적는다
const u = await c.query(
  "UPDATE payment_orders SET status = $2 WHERE id = $1 AND status = 'EXECUTING' RETURNING seller_id, amount",
  [ev.order_id, "SUCCESS"]);
if (u.rowCount === 1) { /* 원장 세 줄 */ }
await c.query("COMMIT");
```

가짜 PSP에 같은 웹훅을 두 번 보내게 하고, 서명 없는 가짜 웹훅을 보내 보고, 웹훅 하나를 잃어버리게 했다.

```text
--- duplicate delivery
[psp] buyer paid on hosted page: pi_1 succeeded
[svc] po_4001_a -> SUCCESS, ledger txn 1 (+12000 / -11604 / -396)
[psp] webhook evt_1 payment_intent.succeeded -> 200
[svc] webhook evt_1 duplicate, ignored
[psp] webhook evt_1 payment_intent.succeeded -> 200 (resent)
--- forged webhook
[svc] webhook rejected: bad signature
[attacker] forged webhook -> 400
--- lost webhook, sweeper
[psp] buyer paid on hosted page: pi_2 succeeded
[psp] webhook evt_2 lost (network)
po_4001_a=SUCCESS po_4001_b=EXECUTING
```

두 번 온 `evt_1`은 이벤트 ID로 걸러져 원장에 한 번만 적혔다. 두 번째에도 200으로 답한 것이 중요하다. 오류로 답하면 PSP는 실패로 보고 계속 다시 보낸다. 서명이 틀린 가짜 웹훅은 400으로 거부됐다. 그리고 `evt_2`가 사라지자 `po_4001_b`는 PSP에서는 성공인데 우리 쪽에서는 `EXECUTING`에 멈췄다. 앞 글에서 말한 "결제했는데 결제 대기로 나온다"는 문의가 이렇게 생긴다. 웹훅 자체의 서명 방식과 받는 서버를 공격해 보는 실험은 [웹훅](/posts/webhooks)에 있다.

## 우리 기록과 PSP 기록을 맞춰 본다

여기까지 막아도 어긋남은 남는다. 버그가 있고, 사람이 실수하고, PSP도 틀린다. 그래서 매일 우리 장부와 바깥 기록을 한 줄씩 맞춰 보는 대사(reconciliation)를 돌린다. PSP는 보통 하루 한 번 그날 처리한 거래 목록을 정산 파일로 보내 준다.

하루 동안 이런 일이 있었다고 하자. 정상 결제 두 건, 멱등성 키 없이 재시도해서 PSP에서 두 번 청구된 건(`po_5003`), 카드가 거절됐는데 리다이렉트 주소의 결과 값만 보고 성공 처리한 건(`po_5004`), PSP 결제 화면에서만 쿠폰 500원이 적용돼 금액이 어긋난 건(`po_5005`). 가짜 PSP가 만든 정산 파일은 이렇다.

```text
intent_id,order_id,amount
pi_1,po_5001,12000
pi_2,po_5002,8000
pi_4,po_5005,5000
pi_5,po_5003,15000
pi_6,po_5003,15000
```

정산 파일을 임시 테이블에 올리고, 우리 원장의 "PSP에게 받을 돈" 줄과 `FULL OUTER JOIN`으로 맞춘다. 양쪽 어디에든 있는 줄을 모두 남기는 조인이라 한쪽에만 있는 거래가 빠지지 않는다.

```sql
CREATE TEMP TABLE psp_settlement (intent_id text PRIMARY KEY, order_id text NOT NULL, amount bigint NOT NULL);
\copy psp_settlement FROM 'settlement-2026-10-22.csv' WITH (FORMAT csv, HEADER true)
WITH ours AS (           -- 우리 원장: 결제 건별로 PSP에서 받을 돈
  SELECT o.psp_intent_id AS intent_id, o.id AS order_id, e.amount
  FROM payment_orders o
  JOIN ledger_txns t ON t.kind = 'pay_in' AND t.ref = o.id
  JOIN ledger_entries e ON e.txn_id = t.id AND e.account = 'psp_receivable'
)
SELECT coalesce(p.order_id, o.order_id) AS order_id,
       coalesce(p.intent_id, o.intent_id) AS intent_id,
       p.amount AS psp_amount, o.amount AS our_amount,
       CASE
         WHEN o.intent_id IS NULL THEN 'PSP에만 있음'
         WHEN p.intent_id IS NULL THEN '우리에게만 있음'
         WHEN p.amount <> o.amount THEN '금액 다름'
         ELSE '일치'
       END AS result
FROM psp_settlement p
FULL OUTER JOIN ours o ON o.intent_id = p.intent_id
ORDER BY 1, 2;
```

```text
 order_id | intent_id | psp_amount | our_amount |     result      
----------+-----------+------------+------------+-----------------
 po_5001  | pi_1      |      12000 |      12000 | 일치
 po_5002  | pi_2      |       8000 |       8000 | 일치
 po_5003  | pi_5      |      15000 |            | PSP에만 있음
 po_5003  | pi_6      |      15000 |      15000 | 일치
 po_5004  | pi_3      |            |      30000 | 우리에게만 있음
 po_5005  | pi_4      |       5000 |       5500 | 금액 다름
(6 rows)
```

세 가지 사고가 각각 다른 모양으로 드러났다. `po_5003`은 PSP에 청구가 두 개인데 우리는 하나만 알고 있다. 구매자가 15,000원을 더 냈다. `po_5004`는 우리 장부에는 30,000원을 받을 돈이 있는데 PSP에는 기록이 없다. 판매자에게 받지도 않은 돈을 지급할 뻔했다. `po_5005`는 양쪽에 있지만 500원 차이가 난다.

## 어긋난 줄을 처리하는 순서

어긋난 줄은 종류별로 처리 방법을 정해 둔다.

- PSP에만 있음: 이중 청구거나, 우리가 기록을 잃은 결제다. 결제 건에 이미 성공한 청구가 있으면 남는 청구를 환불하고, 없으면 그 청구를 결제 건에 연결해 원장에 적는다. 같은 원인이 반복되면 멱등성 키가 빠진 호출 경로를 찾는다.
- 우리에게만 있음: 우리가 성공으로 잘못 기록했다. 결제 건을 `FAILED`로 바꾸고, 원장에는 반대 방향 거래를 적어 되돌린다. 원장 줄을 지우지 않는다. 주문 서비스에 알려 배송을 막는다.
- 금액 다름: 쿠폰, 부분 취소, 통화 변환처럼 원인이 다양해서 자동으로 고치기 어렵다. 재무 담당자가 확인하는 목록으로 보낸다. 이번 예처럼 웹훅에 금액이 실려 오면, 웹훅을 받을 때 우리 결제 건 금액과 비교해 그 자리에서 잡을 수도 있다.

실무에서는 이렇게 나눈다. 원인을 알고 처리 절차도 정해진 것은 자동으로 고친다. 원인은 알지만 사람이 판단해야 하는 것은 담당자에게 보낸다. 원인을 모르는 것은 따로 조사한다. 어떤 경우든 대사 결과 자체를 테이블에 남겨, 오늘 몇 건이 어긋났고 몇 건이 해결됐는지 지표로 본다. 어긋남이 0이 아닌 날이 이어지면 그건 버그가 계속 새고 있다는 신호다.

대사는 PSP와 우리 사이에만 하는 게 아니다. 원장과 지갑 잔액, 원장과 은행 입출금 내역처럼 같은 돈을 서로 다른 곳에 적어 두는 모든 쌍을 맞춘다. 앞 글에서 지갑을 "원장의 사본"이라고 했는데, 그 사본이 맞는지 확인하는 것도 대사다.

## 결제 DB의 복제와 읽기

결제 상태를 담은 DB에 읽기 복제본을 두면, 방금 `SUCCESS`로 바뀐 결제를 복제본에서 읽었을 때 아직 `EXECUTING`으로 보일 수 있다. 결과 화면이 "확인 중"으로 남거나, 스위퍼가 이미 끝난 결제를 다시 PSP에 묻는 정도면 다행이고, 지급 배치가 복제본을 보고 금액을 계산하면 사고가 된다.

그래서 결제처럼 일관성이 중요한 데이터는 읽기와 쓰기를 모두 주 DB에서 하고, 복제본은 장애 조치와 분석용으로만 쓰는 경우가 많다. 결제 건수는 하루 수백만 건이어도 초당 수십 건이라 주 DB 한 대가 감당하기 어려운 양이 아니다. 복제본까지 항상 같은 값을 보장해야 한다면 합의 알고리즘으로 복제하는 분산 DB를 고르는 방법도 있다. 복제 지연 자체는 [DB 복제 입문](/posts/sd-db-replication-intro)에서 다뤘다.

## 결제에서 빠뜨리기 쉬운 보안

- 카드 정보는 PSP의 결제 화면이 받고, 저장된 카드는 PSP가 준 토큰으로만 다룬다. 우리 DB에는 카드 번호가 없어야 한다.
- 웹훅은 서명과 시각을 확인하고, 웹훅 본문의 금액과 상태를 그대로 믿기보다 결제 건과 대조한다.
- 결제 API와 웹훅 수신 경로에는 요청 수 제한을 건다. 카드 번호를 대입해 보는 공격이 결제 API로 들어온다.
- 리다이렉트 주소의 결과 값, 클라이언트가 보낸 금액은 믿지 않는다. 금액은 항상 서버의 장바구니에서 다시 계산한다.

## 결제 장애가 났을 때 보는 순서

- 이중 청구 문의: 결제 건 ID로 PSP 관리 화면에서 청구가 몇 개인지 본다. 둘 이상이면 PSP 호출 로그에서 `Idempotency-Key` 헤더가 붙어 있었는지, 재시도마다 키가 같았는지 확인한다.
- 결제 대기에서 안 넘어감: 웹훅 수신 로그에 그 이벤트가 있는지, 응답 코드가 무엇이었는지 본다. 500으로 답하고 있었다면 PSP는 계속 재전송하고 있을 것이다. 스위퍼가 돌고 있는지, 기준 시간이 너무 긴지도 본다.
- 대사에서 "우리에게만 있음"이 반복된다: 리다이렉트 결과나 클라이언트 값으로 상태를 바꾸는 경로가 있는지 코드를 찾는다.
- 웹훅이 갑자기 전부 400: 서명 비밀 키를 교체했거나, 서버 시계가 틀어져 시각 검사에 걸린 경우가 많다. 서버의 NTP 동기화 상태를 본다.

## 대사를 직접 짜 보기

대사의 핵심을 함수로 짜 보자. `psp`는 정산 파일의 줄, `ours`는 우리 원장의 줄이다. 둘 다 `{ id, amount }` 배열이고 `id`는 PSP 등록 번호다. 양쪽에 나온 모든 `id`를 문자열 오름차순으로 정렬해 `[id, 결과]` 쌍의 배열을 돌려준다. 결과는 `"match"`, `"psp_only"`, `"ours_only"`, `"amount_mismatch"` 중 하나다.

## 다음에 읽을 글

결제의 실패는 대부분 "결과를 모르는 상태"에서 시작한다. 시간 초과는 실패가 아니니 같은 결제 건 ID를 멱등성 키로 붙여 다시 보내고, 다 써도 모르면 `FAILED`가 아니라 확인 대기로 둔다. 정확히 한 번은 다시 보내기와 거르기의 합이고, 구간마다 따로 지킨다. 웹훅은 서명을 확인하고 이벤트 ID와 "앞으로만 가는 상태"로 거르며, 사라진 웹훅은 스위퍼가 PSP에 물어 메운다. 그래도 남는 어긋남은 매일 정산 파일과 원장을 양쪽 모두 남기는 조인으로 맞춰 잡는다.

결제 두 편은 여기까지다. 다음 장 [디지털 지갑 설계 ①](/posts/sd-wallet-transfer)에서는 돈이 우리 시스템 안에서 사용자끼리 움직인다. 보내는 사람과 받는 사람의 잔액이 서로 다른 샤드에 있을 때 둘을 함께 바꾸는 문제를 [2단계 커밋](/posts/distributed-transactions-2pc)과 [사가](/posts/saga-pattern)로 비교한다.

## 면접에서 나올 만한 질문

### PSP 호출이 시간 초과되면 어떻게 처리하나요?

실패로 보지 않고 결과를 모르는 상태로 본다. 요청이 안 갔을 수도, 처리됐는데 응답만 늦었을 수도 있다. 결제 건 ID를 멱등성 키로 붙인 채 간격을 늘려 가며 다시 보내고, PSP는 같은 키를 알아보고 첫 결과를 돌려준다. 재시도를 다 써도 답이 없으면 진행 중 상태로 두고 웹훅, 상태 조회, 대사로 확정한다.

### 멱등성 키를 재시도할 때마다 새로 만들면 어떻게 되나요?

키가 매번 달라서 PSP는 매번 새 결제로 보고 청구한다. 실험에서 키 없이 세 번 재시도하자 청구가 세 번 일어났다. 키는 시도가 아니라 결제 건을 가리켜야 하니, 결제 건을 만들 때 정한 ID를 재시도 루프 밖에서 정해 쓴다.

### 결제에서 정확히 한 번 처리는 어떻게 보장하나요?

잃지 않을 때까지 다시 보내는 것과, 여러 번 도착해도 한 번만 반영하는 것을 합쳐서 만든다. 이 둘을 구간마다 따로 지킨다. 브라우저에서 결제 서비스까지는 장바구니 ID 유니크 제약, 결제 서비스에서 PSP까지는 멱등성 키, PSP 웹훅은 이벤트 ID와 상태 조건, 원장은 결제 건별 유니크 제약, 큐 소비자는 인박스 테이블이 거른다.

### 같은 웹훅이 두 번 오면요? 다른 이벤트 ID로 같은 결과가 오면요?

같은 이벤트 ID는 수신 기록 테이블의 기본 키로 걸러 두 번째를 무시하고 200으로 답한다. 오류로 답하면 PSP가 계속 재전송한다. 이벤트 ID가 달라도 같은 결과일 수 있으니, 상태를 `EXECUTING`일 때만 바꾸고 바뀐 경우에만 원장에 적는다. 실험에서 스위퍼가 먼저 끝낸 결제에 늦게 온 웹훅이 이 조건에 걸려 아무것도 바꾸지 않았다.

### 웹훅이 끝내 안 오면 어떻게 하나요?

오래 진행 중에 머문 결제 건을 주기적으로 찾아 PSP 상태 조회 API로 직접 묻는 스위퍼를 둔다. 결과는 웹훅과 같은 함수, 같은 상태 규칙으로 반영해서 나중에 웹훅이 와도 중복되지 않게 한다. 그래도 남는 건 하루 단위의 대사가 잡는다.

### 대사는 무엇을 어떻게 비교하나요?

PSP가 보내는 정산 파일과 우리 원장의 결제 줄을 PSP 거래 번호로 맞춘다. 한쪽에만 있는 줄이 빠지지 않게 양쪽을 모두 남기는 `FULL OUTER JOIN`을 쓰고, 결과를 일치, PSP에만 있음, 우리에게만 있음, 금액 다름으로 나눈다. PSP에만 있으면 이중 청구나 기록 누락, 우리에게만 있으면 잘못된 성공 처리, 금액 다름은 쿠폰이나 부분 취소 같은 원인을 사람이 확인한다.

### 결제 상태를 읽기 복제본에서 읽어도 되나요?

조심해야 한다. 복제 지연 때문에 방금 성공한 결제가 진행 중으로 보이고, 그 값으로 지급이나 재시도를 결정하면 사고가 된다. 결제는 초당 수십 건 규모라 읽기와 쓰기를 주 DB에서 하고 복제본은 장애 조치와 분석에만 쓰는 경우가 많다. 항상 같은 값을 봐야 하면 합의 기반으로 복제하는 분산 DB를 고른다.

### 결제 서비스 트래픽이 열 배가 되면 무엇을 먼저 보나요?

결제 건수 자체보다 PSP 호출과 재시도가 먼저 문제가 된다. PSP의 요청 수 제한에 걸리면 `429`가 늘고, 재시도가 한꺼번에 몰리면 더 악화되니 지터를 섞은 백오프와 재시도 큐로 흩는다. PSP 하나에 의존하는 위험도 커지므로 PSP를 둘 이상 연동해 장애 때 넘기는 방안을 검토하고, 대사와 원장 쓰기가 늘어난 건수를 하루 안에 처리하는지 본다.
