로그인을 한 번 하면 새로고침을 해도, 다른 페이지로 넘어가도 로그인 상태가 그대로다. 당연해 보이지만 HTTP만 놓고 보면 이상한 일이다. HTTP는 요청 하나하나가 서로 독립이라, 서버는 방금 들어온 요청이 1초 전에 로그인한 그 사람이 보낸 건지 알 방법이 없다. 이걸 이어 주는 가장 오래되고 지금도 널리 쓰이는 방법이 쿠키와 세션이다. 인증 글을 정리하면서 여기서부터 시작한다.

## 외투 보관소 번호표

공연장 외투 보관소를 떠올리면 구조가 그대로 보인다. 외투를 맡기면 직원은 외투를 안쪽 옷걸이에 걸고 번호표를 준다. 다시 찾으러 갈 때는 번호표만 내밀면 된다. 직원은 내 얼굴을 기억할 필요가 없다.

쿠키 세션 방식에서 외투는 "이 사람은 42번 사용자다" 같은 로그인 정보다. 서버가 이걸 세션 저장소에 보관하고, 브라우저에는 번호표, 즉 세션 ID만 쿠키로 돌려준다. 이후 요청마다 브라우저가 번호표를 붙여 보내면, 서버는 저장소에서 그 번호를 찾아 누구인지 알아낸다.

## 자동으로 붙는다는 것의 함정, CSRF

쿠키는 브라우저가 알아서 붙여 준다. 편한 대신 문제가 하나 생긴다. 내가 은행 사이트에 로그인한 상태로 다른 사이트를 구경한다고 해 보자. 그 사이트에 은행으로 송금 요청을 보내는 폼이 숨어 있으면, 그 요청에도 은행 쿠키가 붙을 수 있다. 은행 서버 입장에서는 내가 보낸 요청과 구별할 방법이 없다. 이게 CSRF(Cross-Site Request Forgery)다.

## 세션을 노리는 공격들

세션 ID는 그 자체로 로그인 상태다. 누가 이 값을 손에 넣으면 비밀번호 없이도 나로 행세할 수 있다. 그래서 공격도 대부분 세션 ID를 훔치거나 심는 쪽으로 들어온다.

가장 흔한 건 세션 하이재킹, 즉 쿠키를 훔쳐 가는 공격이다. 페이지에 악성 스크립트가 끼어드는 XSS로 `document.cookie`를 읽어 가거나, 암호화되지 않은 통신을 엿본다. 앞에서 본 `HttpOnly`가 첫 번째, `Secure`가 두 번째 경로를 막는다.

덜 알려졌지만 면접에서 자주 나오는 게 세션 고정(session fixation)이다. 공격자가 자기가 아는 세션 ID를 피해자 브라우저에 미리 심어 두고, 피해자가 그 세션 ID를 가진 채 로그인하게 만든다. 서버가 로그인할 때 세션 ID를 그대로 두면, 공격자는 이미 알고 있던 그 ID로 로그인된 세션을 쓸 수 있다. 막는 방법은 간단하다. **로그인에 성공하는 순간 세션 ID를 새로 발급**하고 이전 것은 버린다. 대부분의 웹 프레임워크가 이 동작을 기본으로 하거나 옵션으로 제공한다. 권한이 바뀌는 순간(관리자 권한 획득 등)에도 같은 이유로 새로 발급한다.

세션이 언제 끝나는지도 정해야 한다. 마지막 요청 후 일정 시간 동안 아무것도 안 하면 끝나는 유휴 만료(idle timeout)와, 활동과 상관없이 로그인 후 일정 시간이 지나면 끝나는 절대 만료(absolute timeout)를 함께 두는 경우가 많다. 유휴 만료만 있으면 탈취된 세션을 계속 써서 영원히 살려 둘 수 있기 때문이다.

쿠키가 어디까지 보내지는지도 신경 써야 한다. `Domain=example.com`을 지정하면 `blog.example.com` 같은 모든 하위 도메인에도 쿠키가 간다. 하위 도메인 하나가 뚫리면 세션도 같이 위험해진다. 그래서 세션 쿠키에는 보통 `Domain`을 생략해 그 호스트에만 보내고, 더 엄격하게는 이름 앞에 `__Host-`를 붙인다. `__Host-` 쿠키는 브라우저가 `Secure`, `Path=/`, `Domain` 없음 조건을 강제한다.

## 서버가 여러 대가 되면

서버가 한 대일 때는 세션을 서버 메모리에 둬도 된다. 서버를 두 대 이상으로 늘리면 문제가 생긴다. 로그인은 A 서버에서 했는데 다음 요청이 B 서버로 가면, B는 그 세션을 모른다. 그래서 세션은 보통 모든 서버가 함께 보는 별도 저장소(대개 Redis 같은 인메모리 DB)에 둔다.

    { from: "browser", to: "lb", label: "쿠키" },
    { from: "lb", to: "a" },
    { from: "lb", to: "b" },
    { from: "a", to: "redis", arrow: "both" },
    { from: "b", to: "redis", arrow: "both" },
  ]}
/>

다른 방법으로 같은 사용자를 계속 같은 서버로 보내는 고정 세션(sticky session)도 있다. 다만 그 서버가 죽으면 거기 있던 세션이 전부 사라진다. 저장소를 따로 두는 쪽이 더 흔하다.

## 배포하고 나니 로그인이 자꾸 풀릴 때

로컬에서는 잘 되던 로그인이 서버에 올리자 풀린다. 로그인 요청은 200인데 바로 다음 요청이 401이다. 이럴 때는 쿠키가 세 군데 중 어디서 끊겼는지 본다. 브라우저가 쿠키를 저장했는지, 저장한 쿠키를 요청에 실었는지, 서버가 그 세션을 찾았는지다. 작은 Node.js 서버를 띄우고 curl로 하나씩 재현해 봤다. 이 서버는 로그인하면 앞에서 본 옵션을 그대로 붙여 준다.

```bash
# -i: 응답 헤더까지 본다
curl -si -X POST http://127.0.0.1:3101/login
```

```text
HTTP/1.1 200 OK
Set-Cookie: sid=ba0ec583871a08c41e230d208ed627f4; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
...
login ok (A)
```

첫 번째 함정은 `Secure`다. 같은 서버를 HTTPS 없이 사설 IP로 열어 둔 스테이징이라고 치고, curl의 쿠키 저장소(`-c`로 쓰고 `-b`로 읽는다)로 브라우저 흉내를 냈다.

```bash
curl -s -c jar.txt -X POST http://192.0.2.2:3101/login   # 로그인
tail -n +4 jar.txt                                        # 저장된 쿠키 (머리말 3줄은 건너뛴다)
curl -si -b jar.txt http://192.0.2.2:3101/me | head -1    # 다음 요청
```

```text
login ok (A)

HTTP/1.1 401 Unauthorized
```

응답에는 `Set-Cookie`가 분명히 왔는데 저장소가 비어 있다. HTTPS가 아닌 곳에서 받은 `Secure` 쿠키는 저장하지 않기 때문이다. 요즘 브라우저도 똑같이 버린다. 크롬, 파이어폭스와 curl은 `localhost`와 `127.0.0.1`을 HTTPS처럼 안전한 곳으로 쳐 주기 때문에 로컬에서는 이 문제가 안 보인다. 크롬이라면 개발자 도구 Network 패널에서 로그인 요청을 열고 Cookies 탭을 보면, 막힌 쿠키 옆에 노란 경고 표시와 막힌 이유가 나온다.

HTTPS인데도 같은 일이 생기면 TLS를 앞의 로드 밸런서나 Ingress에서 풀고 있는지 본다. 앱은 평문 HTTP로 요청을 받으니 자기가 HTTPS 뒤에 있는 줄 모른다. Express의 `express-session`은 `cookie.secure`가 켜져 있는데 요청이 HTTPS가 아니라고 판단하면 `Set-Cookie`를 아예 보내지 않는다. 프록시가 붙여 주는 `X-Forwarded-Proto`를 믿도록 `app.set("trust proxy", 1)`을 설정해야 한다. 프록시가 어디서 TLS를 푸는지는 [리버스 프록시 글](/posts/proxy-reverse-proxy)에서 다뤘다.

두 번째는 서버를 두 대로 늘린 날부터 새로고침할 때마다 로그인이 됐다 풀렸다 하는 경우다. 세션을 서버 메모리에 둔 채 로드 밸런서가 번갈아 보내면 이렇게 된다. 서버 A와 B를 띄우고 앞에 번갈아 보내는 프록시를 둔 뒤 같은 쿠키로 네 번 불렀다.

```bash
curl -s -c jar.txt -X POST http://127.0.0.1:3100/login
for i in 1 2 3 4; do curl -s -w '  -> %{http_code}\n' -b jar.txt http://127.0.0.1:3100/me; done
```

```text
login ok (A)
no session (B)
  -> 401
user 42 (A)
  -> 200
no session (B)
  -> 401
user 42 (A)
  -> 200
```

로그인한 A로 가면 200, 세션을 모르는 B로 가면 401이다. 증상이 "가끔" 풀리는 것처럼 보여서 처음엔 만료 시간을 의심하기 쉬운데, 응답마다 어느 서버가 답했는지(응답 헤더에 서버 이름을 넣거나 접근 로그로) 찍어 보면 바로 갈린다. 앞에서 본 공용 세션 저장소로 옮기는 게 답이다. 배포할 때마다 모두 로그아웃된다면 같은 이유로 세션이 프로세스 메모리에 있다는 신호다.

세 번째는 프런트엔드와 API의 주소가 다를 때다. `app.example.com`에서 `api.example.com`을 부르는 건 출처(origin)는 다르지만 같은 사이트(site)라서, `SameSite=Lax` 쿠키도 함께 간다. 다만 `fetch`에 `credentials: "include"`를 줘야 하고, API는 `Access-Control-Allow-Origin`에 정확한 출처를 적고 `Access-Control-Allow-Credentials: true`를 보내야 한다. 이 부분은 [CORS 글](/posts/cors)에 있다. 프런트가 `shop-web.vercel.app`처럼 아예 다른 사이트에 있다면 `Lax` 쿠키는 `fetch`에 실리지 않는다. `SameSite=None; Secure`로 바꿀 수는 있지만 그만큼 CSRF 방어를 직접 챙겨야 하고, 서드파티 쿠키를 막는 브라우저도 있다. 그래서 보통은 API를 같은 사이트의 하위 도메인으로 옮기거나, 프런트 서버가 API를 대신 불러 주게 한다.

어느 경우든 고친다고 `Domain=.example.com`부터 붙이는 실수가 잦다. 하위 도메인 전체로 세션이 퍼질 뿐 위 문제들은 그대로다.

## 정리

쿠키 세션 방식에서 서버는 로그인 정보를 직접 보관하고, 브라우저는 그걸 찾을 번호표만 쿠키로 들고 다닌다. 세션을 지우면 바로 로그아웃되고, HttpOnly·Secure·SameSite만 잘 붙이면 웹에서 꽤 안전하게 쓸 수 있다. 대신 요청마다 저장소를 찾아봐야 하고, 쿠키가 자동으로 붙는 만큼 CSRF를 신경 써야 한다. 서버가 아무것도 기억하지 않는 반대쪽 방식은 [토큰 기반 로그인](/posts/token-login)에서 이어서 정리한다.

## 면접에서 나올 만한 질문

### 쿠키와 세션은 무엇이 다른가요?

쿠키는 브라우저에 저장되는 작은 데이터이고, 세션은 서버가 보관하는 사용자 상태다. 쿠키 세션 방식에서는 둘을 함께 쓴다. 세션 데이터는 서버(세션 저장소)에 두고, 쿠키에는 그 세션을 찾는 ID만 넣는다. 그래서 민감한 정보가 브라우저로 나가지 않고, 서버가 세션을 지우면 바로 로그아웃시킬 수 있다.

### HTTP는 무상태인데 로그인 상태는 어떻게 유지되나요?

HTTP 요청은 서로를 기억하지 못하니, 요청마다 "내가 누구인지"를 증명할 값을 같이 보낸다. 쿠키 세션 방식에서는 로그인 때 받은 세션 ID 쿠키를 브라우저가 매 요청에 자동으로 붙이고, 서버는 그 ID로 세션 저장소를 조회해 사용자를 알아낸다. 상태는 HTTP가 아니라 서버의 세션 저장소에 있는 셈이다.

### HttpOnly, Secure, SameSite는 각각 무엇을 막나요?

HttpOnly는 자바스크립트가 쿠키를 읽지 못하게 해서 XSS로 세션 ID를 훔쳐 가는 걸 막는다. Secure는 HTTPS에서만 쿠키를 보내서 네트워크 도청을 막는다. SameSite는 다른 사이트에서 시작된 요청에 쿠키를 붙일지 정해서 CSRF를 막는다. Lax는 링크 이동 같은 최상위 GET에만 붙이고, Strict는 아예 안 붙이며, None은 항상 붙인다(None은 Secure가 필요하다).

### CSRF는 무엇이고 어떻게 막나요?

쿠키가 자동으로 붙는 점을 이용해, 다른 사이트에서 피해자의 브라우저가 내 서버로 요청을 보내게 만드는 공격이다. 서버는 정상 요청과 구별하지 못한다. SameSite=Lax 이상으로 쿠키가 아예 안 붙게 하는 게 첫 번째 방어선이고, 중요한 요청에는 서버가 발급한 CSRF 토큰을 폼이나 헤더에 실어 검증한다. Origin·Referer 헤더를 확인하는 방법도 함께 쓴다.

### XSS와 CSRF는 무엇이 다른가요?

XSS는 공격자의 스크립트가 내 사이트 안에서 실행되는 것이고, CSRF는 공격자의 사이트가 내 사이트로 요청을 보내게 만드는 것이다. XSS는 내 사이트의 권한으로 무엇이든 할 수 있어서 더 위험하고, CSRF 방어(CSRF 토큰)도 XSS가 있으면 뚫린다. XSS는 출력 이스케이프와 CSP로, CSRF는 SameSite와 CSRF 토큰으로 막는다.

### 로그인할 때 세션 ID를 새로 발급해야 하는 이유는요?

세션 고정 공격 때문이다. 공격자가 미리 심어 둔 세션 ID로 피해자가 로그인하면, 그 ID를 아는 공격자도 로그인된 세션을 쓰게 된다. 로그인 성공 시 새 세션 ID를 발급하고 이전 것을 폐기하면, 공격자가 알던 ID는 쓸모가 없어진다.

### 서버를 여러 대로 늘리면 세션은 어떻게 하나요?

모든 서버가 함께 보는 공용 세션 저장소(보통 Redis)를 둔다. 같은 사용자를 같은 서버로 보내는 고정 세션도 있지만, 그 서버가 죽으면 세션이 사라지고 부하가 고르게 나뉘지 않는다. 이 조회 비용과 저장소 운영 부담이 싫다면 토큰 방식을 검토하게 된다.
