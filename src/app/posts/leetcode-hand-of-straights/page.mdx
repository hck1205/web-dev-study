[Hand of Straights](https://leetcode.com/problems/hand-of-straights/)는 LeetCode 846번이다. 카드 숫자 배열과 묶음 크기가 주어지고, 카드를 모두 "연속한 숫자로 된 같은 크기의 묶음"으로 나눌 수 있는지 묻는다. 그리디 문제지만 [Jump Game](/posts/leetcode-jump-game)이나 [Gas Station](/posts/leetcode-gas-station)처럼 한 번 훑는 계산이 아니라, 정렬과 개수 세기가 함께 들어가는 문제다. 그래서 정렬, 해시맵, 힙을 고르는 판단까지 묻기 좋다.

이 글은 다섯 풀이를 본다. 정렬한 배열에서 매번 카드를 지우는 풀이, 개수 장부로 지우는 일을 줄이는 풀이, 최소 힙으로 가장 작은 숫자를 꺼내는 풀이, 숫자마다 열려 있는 묶음 수만 세는 풀이, 정렬 없이 줄의 맨 앞을 찾아가는 풀이다. 그리디가 맞는지 확인하는 일반적인 방법은 [그리디 알고리즘 글](/posts/greedy-algorithms)에 있다. 코드는 Node.js 22, Python 3, Java 21에서 돌렸다.

## 카드를 연속한 묶음으로 나누기

정수 배열 `hand`와 정수 `groupSize`가 주어진다. 카드를 모두 써서, 크기가 `groupSize`이고 숫자가 1씩 이어지는 묶음들로 나눌 수 있으면 `true`, 아니면 `false`를 돌려준다. 같은 숫자의 카드가 여러 장 있을 수 있고, 한 묶음 안에는 같은 숫자가 두 번 들어갈 수 없다.

풀이 선택에 영향을 주는 제약은 이렇다.

- 카드는 최대 10^4장이다. O(n²)도 10^8 정도라 아슬아슬하게 버틸 수 있지만, 카드 수가 조금만 늘어도 무너진다.
- 카드 숫자는 0 이상 10^9 이하다. 숫자 크기만큼 배열을 잡는 카운팅 정렬은 못 쓴다. 개수는 해시맵에 센다.
- `groupSize`는 1 이상 카드 수 이하다. 1이면 무조건 `true`다.

먼저 걸러 낼 수 있는 경우가 하나 있다. 카드 수가 `groupSize`로 나누어떨어지지 않으면 어떻게 묶어도 남는 카드가 생긴다. 이 검사는 답을 바꾸지 않는 지름길이지만, 대부분의 실패 입력을 O(1)에 걸러 준다.

## 손으로 먼저 묶어 본다

이 글에서 계속 쓸 예시다. 카드는 `[3, 1, 2, 2, 4, 3]`, 묶음 크기는 3이다.

정렬하면 `1, 2, 2, 3, 3, 4`다. 1은 가장 작으니 누구 뒤에도 붙을 수 없다. 1이 들어간 묶음은 1로 시작해야 하고, 크기가 3이니 `1, 2, 3`이 된다. 이 세 장을 빼면 `2, 3, 4`가 남는다. 다시 가장 작은 2로 시작하는 묶음 `2, 3, 4`를 만든다. 카드가 남지 않았으니 `true`다.

실패하는 예시도 하나 본다. `[1, 2, 4, 5, 6, 7]`, 묶음 크기 3. 가장 작은 1로 시작하면 `1, 2, 3`이 필요한데 3이 없다. 1을 다른 묶음에 넣을 방법이 없으니 여기서 바로 `false`다. 장수는 6장으로 3의 배수라 첫 검사는 통과했다.

손으로 하다 보면 고민할 것이 거의 없다는 게 보인다. 매 순간 가장 작은 카드가 무엇을 해야 하는지는 정해져 있다.

## 가장 작은 카드는 갈 곳이 하나뿐이다

이 문제가 그리디로 풀리는 근거는 한 문장이다. 남은 카드 중 가장 작은 숫자 x는 반드시 어떤 묶음의 맨 앞이다.

x보다 작은 카드가 남아 있지 않으니, x가 묶음 중간이나 끝에 서려면 x - 1이 필요한데 그런 카드가 없다. 그래서 x가 든 묶음은 `x, x + 1, ..., x + groupSize - 1`로 정해진다. 고를 여지가 없는 선택이라 "이 선택 때문에 나중에 손해를 본다"는 일이 생길 수 없다. 이렇게 고를 여지가 없는 결정을 하나씩 확정해 나가는 모양은 [그리디 알고리즘 글의 "일찍 끝나는 회의" 증명](/posts/greedy-algorithms#일찍-끝나는-회의가-왜-맞는가)과 같은 결이다. 거기서도 "가장 먼저 끝나는 회의를 고른 답으로 바꿔도 손해가 없다"를 보인다.

x가 여러 장이면 어떻게 될까. x 한 장마다 묶음 하나를 따로 시작해야 한다. 같은 묶음에 x가 두 번 들어갈 수 없기 때문이다. x가 3장이면 `x`로 시작하는 묶음이 정확히 3개 생기고, x + 1도 최소 3장 필요하다. 이 관찰이 뒤에서 "묶음 단위로 한꺼번에 빼는" 풀이가 된다.

이제 남은 일은 구현이다. "가장 작은 카드를 찾는다"와 "다음 숫자 카드를 하나 뺀다"를 얼마나 싸게 하느냐에 따라 풀이가 갈린다.

## 정렬해 두고 매번 배열에서 지운다

가장 곧은 구현이다. 정렬한 배열의 맨 앞이 가장 작은 카드다. 그 숫자부터 `groupSize`개의 연속한 숫자를 배열에서 찾아 지운다.

```js
function isNStraightHand(hand, groupSize) {
  if (hand.length % groupSize !== 0) return false;
  const cards = [...hand].sort((a, b) => a - b);   // 숫자 비교로 정렬
  while (cards.length > 0) {
    const first = cards[0];                        // 남은 카드 중 가장 작은 숫자
    for (let k = 0; k < groupSize; k++) {
      const idx = cards.indexOf(first + k);        // 다음 숫자 카드를 찾는다
      if (idx === -1) return false;                // 없으면 묶음을 못 만든다
      cards.splice(idx, 1);                        // 찾은 카드를 지운다
    }
  }
  return true;
}
```

정렬이 O(n log n)이고, 카드를 지울 때마다 `indexOf`와 `splice`가 각각 O(n)이다. 카드 n장을 모두 지우니 전체 O(n²)이다. 공간은 복사한 배열 O(n)이다.

같은 숫자가 몰려 있으면 느려진다. 1, 2, 3이 각각 n/3장씩 있고 묶음 크기가 3인 입력을 재 봤다.

```text
9999 brute true 35.0
99999 brute true 3051.2
```

LeetCode 제약인 1만 장에서는 35ms라 통과한다. 그런데 카드가 10배가 되면 시간이 100배 가까이 늘어 3초가 걸린다. 매번 지울 카드를 찾아 배열을 훑고, 지운 뒤 뒤쪽 원소를 한 칸씩 당기는 일이 낭비다. 카드 하나하나의 위치는 필요 없고, 숫자마다 몇 장 남았는지만 알면 된다.

## 개수 장부로 지우는 일을 줄인다

배열에서 지우는 대신 숫자별 남은 장수를 해시맵에 적어 둔다. 장부라고 부르자. 카드를 뺄 때는 장부의 숫자만 1 줄인다. 해시맵 자체는 [해시맵 글](/posts/ds-hash-map)에 있다.

가장 작은 카드는 정렬한 배열을 앞에서부터 훑으며 찾는다. 장부에서 그 숫자가 0이면 이미 앞선 묶음에 들어간 카드이니 건너뛴다. 0이 아니면 그 숫자로 묶음을 시작한다.

```js
function isNStraightHand(hand, groupSize) {
  if (hand.length % groupSize !== 0) return false;
  const count = new Map();                         // 숫자 -> 남은 장수
  for (const c of hand) count.set(c, (count.get(c) ?? 0) + 1);
  const sorted = [...hand].sort((a, b) => a - b);
  for (const c of sorted) {
    if (count.get(c) === 0) continue;              // 이미 다른 묶음에 들어갔다
    for (let k = 0; k < groupSize; k++) {          // c로 시작하는 묶음을 만든다
      const v = count.get(c + k) ?? 0;
      if (v === 0) return false;                   // 이어질 숫자가 없다
      count.set(c + k, v - 1);
    }
  }
  return true;
}
```

훑는 동안 c가 "남은 카드 중 가장 작은 숫자"라는 게 보장된다. c보다 작은 숫자는 앞에서 이미 지나왔고, 지나올 때 장부가 0이 될 때까지 묶음을 만들었기 때문이다. 정확히 말하면 c의 두 번째 장에서도 다시 묶음을 시작하는데, 그때도 c보다 작은 카드는 남아 있지 않다.

예시 `[3, 1, 2, 2, 4, 3]`에서 장부가 바뀌는 모습을 찍었다.

```text
init 1:1 2:2 3:2 4:1
0 1 group 1,2,3 1:0 2:1 3:1 4:1
1 2 group 2,3,4 1:0 2:0 3:0 4:0
2 2 skip 1:0 2:0 3:0 4:0
```

시간은 정렬 O(n log n)에 묶음 만들기를 더한 것이다. 묶음 하나를 만들 때 `groupSize`번 장부를 고치는데, 묶음은 모두 `n / groupSize`개라 장부를 고치는 횟수는 합쳐서 n번이다. 건너뛰는 카드도 한 장에 한 번이라 O(n)이다. 전체 O(n log n), 공간은 장부와 정렬 배열 O(n)이다. 앞에서 3초 걸린 10만 장 입력이 22ms로 줄었다.

이 풀이가 기본 답이다. 다만 같은 숫자가 1만 장 있으면 정렬한 배열에도 1만 칸이 들어 있고, 그중 대부분은 건너뛰기만 한다. 서로 다른 숫자만 정렬하면 정렬 비용을 줄일 수 있다. 다음 두 풀이가 그 방향이다.

## 최소 힙으로 가장 작은 숫자를 꺼낸다

NeetCode 풀이로 많이 알려진 방법이다. 서로 다른 숫자만 최소 힙에 넣는다. 힙은 가장 작은 값을 O(1)에 보여 주고 O(log m)에 꺼내 주는 자료구조로, [힙 글](/posts/ds-heap)에 자세히 있다. 여기서 m은 서로 다른 숫자의 개수다.

힙의 맨 위가 남은 카드 중 가장 작은 숫자다. 그 숫자부터 묶음을 만들며 장부를 줄인다. 어떤 숫자의 장수가 0이 되면 힙에서 빼야 하는데, 이때 그 숫자가 힙의 맨 위가 아니면 바로 실패다.

왜 실패일까. 장수가 0이 된 숫자 k가 맨 위가 아니라면, k보다 작은 숫자 j가 아직 카드를 갖고 있다. j의 남은 카드는 언젠가 j 이하에서 시작하는 묶음에 들어가야 한다. 그런데 j는 지금 묶음의 시작점 이상이라 `j + groupSize - 1`이 k 이상이고, j가 든 묶음은 k를 지나간다. k는 이미 바닥났으니 그 묶음은 만들 수 없다.

```js
function isNStraightHand(hand, groupSize) {
  if (hand.length % groupSize !== 0) return false;
  const count = new Map();
  for (const c of hand) count.set(c, (count.get(c) ?? 0) + 1);
  const heap = new MinHeap();                      // 서로 다른 숫자만 넣는다
  for (const c of count.keys()) heap.push(c);
  while (heap.size > 0) {
    const first = heap.peek();                     // 남은 카드 중 가장 작은 숫자
    for (let k = first; k < first + groupSize; k++) {
      const v = count.get(k) ?? 0;
      if (v === 0) return false;                   // 이어질 숫자가 없다
      count.set(k, v - 1);
      if (v - 1 === 0) {                           // k가 바닥났다
        if (k !== heap.peek()) return false;       // 더 작은 숫자가 남았는데 k가 먼저 바닥났다
        heap.pop();
      }
    }
  }
  return true;
}
```

JavaScript에는 기본 힙이 없어서 `MinHeap`을 직접 썼다. 배열로 만든 평범한 이진 힙이다.

```js
class MinHeap {
  constructor() { this.a = []; }
  get size() { return this.a.length; }
  peek() { return this.a[0]; }
  push(x) {
    const a = this.a; a.push(x);
    let i = a.length - 1;
    while (i > 0) {                                // 부모보다 작으면 위로 올린다
      const p = (i - 1) >> 1;
      if (a[p] <= a[i]) break;
      [a[p], a[i]] = [a[i], a[p]]; i = p;
    }
  }
  pop() {
    const a = this.a; const top = a[0]; const last = a.pop();
    if (a.length) {
      a[0] = last; let i = 0;
      for (;;) {                                   // 자식 중 작은 쪽과 바꾸며 내려간다
        const l = 2 * i + 1, r = l + 1; let m = i;
        if (l < a.length && a[l] < a[m]) m = l;
        if (r < a.length && a[r] < a[m]) m = r;
        if (m === i) break;
        [a[m], a[i]] = [a[i], a[m]]; i = m;
      }
    }
    return top;
  }
}
```

Python이면 `heapq`, Java면 `PriorityQueue`가 같은 일을 한다.

힙에 서로 다른 숫자 m개를 넣는 데 O(m log m), 꺼내는 데 O(m log m), 장부를 고치는 데 O(n)이다. 전체 O(n + m log m), 공간 O(m)이다. 같은 숫자가 많을수록 정렬 풀이보다 유리하다. 1, 2, 3이 3만 3천여 장씩 있는 10만 장 입력에서 정렬 풀이가 22ms, 힙 풀이가 15ms였다.

반대로 숫자가 모두 다르면 m이 n이라 이득이 없고, 힙 연산이 정렬보다 느려서 오히려 손해다. 10만 장의 서로 다른 숫자에서 힙 풀이가 170ms, 정렬 풀이가 39ms였다. 힙은 "가장 작은 것을 계속 꺼낸다"는 의도가 코드에 그대로 드러나는 게 장점이고, 서로 다른 숫자만 정렬해도 같은 효과를 얻는다.

## 숫자마다 열린 묶음 수만 센다

가장 작은 숫자 x가 c장이면 x로 시작하는 묶음이 c개 생긴다는 관찰을 그대로 쓴다. 카드를 한 장씩 빼지 않고, 서로 다른 숫자를 작은 것부터 보면서 "지금 이어 가는 중인 묶음이 몇 개인가"만 센다.

숫자 key에 도착했을 때 열려 있는 묶음이 `open`개라고 하자.

- 열린 묶음이 있는데 key가 바로 앞 숫자 + 1이 아니면 실패다. 이어 갈 숫자가 끊겼다.
- key의 장수 c가 `open`보다 적으면 실패다. 열린 묶음마다 key가 한 장씩 필요하다.
- 남는 `c - open`장은 key에서 새 묶음을 연다.
- `groupSize`칸 전에 연 묶음은 key에서 길이가 꽉 차 닫힌다.

어느 칸에서 몇 개를 열었는지를 큐에 적어 두면 닫히는 묶음 수를 바로 알 수 있다.

```js
function isNStraightHand(hand, groupSize) {
  if (hand.length % groupSize !== 0) return false;
  const count = new Map();
  for (const c of hand) count.set(c, (count.get(c) ?? 0) + 1);
  const keys = [...count.keys()].sort((a, b) => a - b); // 서로 다른 숫자만 정렬
  const opened = [];   // opened[j]: j번째 숫자에서 새로 연 묶음 수
  let open = 0;        // 지금 이어 가는 중인 묶음 수
  let prev = null;
  for (const key of keys) {
    const c = count.get(key);
    if (open > 0 && key !== prev + 1) return false;    // 이어 갈 숫자가 끊겼다
    if (open > c) return false;                         // 열린 묶음을 다 못 잇는다
    const start = c - open;                             // 남는 카드로 새 묶음을 연다
    opened.push(start);
    open += start;
    if (opened.length >= groupSize) open -= opened[opened.length - groupSize]; // 꽉 찬 묶음은 닫힌다
    prev = key;
  }
  return open === 0;                                    // 끝에서 덜 찬 묶음이 없어야 한다
}
```

예시 `[1, 1, 2, 2, 3, 3, 3, 4, 5]`, 묶음 크기 3으로 찍었다.

```text
key 1 c 2 new 2 opened [2] open 2
key 2 c 2 new 0 opened [2,0] open 2
key 3 c 3 new 1 opened [2,0,1] open 1
key 4 c 1 new 0 opened [2,0,1,0] open 1
key 5 c 1 new 0 opened [2,0,1,0,0] open 0
end open 0
```

서로 다른 숫자 m개를 정렬하는 O(m log m)과 장부를 만드는 O(n)이 전부다. 숫자마다 하는 일은 O(1)이라 `groupSize`가 커도 느려지지 않는다. 장부 풀이와 힙 풀이는 묶음 하나마다 `groupSize`칸을 돌았는데, 이 풀이는 같은 숫자로 시작하는 묶음을 한꺼번에 다룬다. 공간은 O(m)이다. 큐는 끝의 `groupSize`칸만 보니 길이 `groupSize`의 원형 버퍼로 줄일 수도 있다.

이 풀이는 카드 장수가 "숫자별 개수"로만 주어지는 변형에서 특히 쓸모가 있다. 장부만 있고 카드 배열이 없어도 그대로 돈다.

## 정렬 없이 줄의 맨 앞을 찾아간다

정렬은 "가장 작은 카드"를 찾으려고 했다. 그런데 꼭 전체에서 가장 작은 카드가 아니어도 된다. 이어진 숫자 줄 하나 안에서 가장 작은 카드면 충분하다. 예를 들어 카드가 `1, 2, 3`과 `10, 11, 12`로 떨어져 있으면, 10은 전체 최솟값이 아니지만 자기 줄의 맨 앞이라 묶음의 시작이 될 수밖에 없다.

그래서 아무 카드나 잡고, 장부를 보며 `card - 1`, `card - 2`, ...로 장수가 남은 동안 내려간다. 더 내려갈 수 없는 곳이 그 줄의 맨 앞이다. 거기서부터 올라오며 장수가 남은 숫자마다 묶음을 만든다.

```js
function isNStraightHand(hand, groupSize) {
  if (hand.length % groupSize !== 0) return false;
  const count = new Map();
  for (const c of hand) count.set(c, (count.get(c) ?? 0) + 1);
  for (const card of hand) {
    let start = card;
    while ((count.get(start - 1) ?? 0) > 0) start--;   // 이어진 줄의 맨 앞으로 내려간다
    while (start <= card) {                             // 맨 앞부터 card까지 차례로
      while ((count.get(start) ?? 0) > 0) {             // start가 남은 동안 묶음을 시작한다
        for (let k = start; k < start + groupSize; k++) {
          const v = count.get(k) ?? 0;
          if (v === 0) return false;
          count.set(k, v - 1);
        }
      }
      start++;
    }
  }
  return true;
}
```

시간이 O(n)인 이유가 조금 미묘하다. 내려가는 반복이 카드마다 길게 돌면 O(n²) 같지만, 한 번 내려간 구간은 바로 이어지는 올라오는 반복에서 장수가 모두 0이 된다. 다음 카드가 내려갈 때는 0이 된 숫자에서 멈추니, 숫자 하나를 내려가며 지나가는 일은 한 번뿐이다. 묶음을 만드는 일은 앞 풀이처럼 합쳐서 n번이다. 해시맵 연산을 O(1)로 보면 평균 O(n), 공간 O(m)이다.

이론으로는 가장 빠르지만 실제 시간은 정렬 풀이와 비슷했다(10만 장에서 39~42ms). 해시맵 접근이 정렬보다 상수가 크기 때문이다. 면접에서 "정렬 없이 할 수 있나"를 물으면 꺼낼 답이다. 처음 답으로는 장부 풀이가 설명하기 쉽다.

다섯 풀이가 무작위 입력 3만 개에서 모두 같은 답을 내는지 맞춰 봤다. 카드 1~9장, 숫자 0~5, 묶음 크기 1~4로 만들었고 어긋난 입력은 없었다.

## Python과 Java로 쓴 장부 풀이

```python
from collections import Counter
from typing import List


class Solution:
    def isNStraightHand(self, hand: List[int], groupSize: int) -> bool:
        if len(hand) % groupSize:              # 장수가 나누어떨어지지 않으면 바로 실패
            return False
        count = Counter(hand)                  # 숫자별 남은 장수
        for card in sorted(hand):
            if count[card] == 0:               # 이미 다른 묶음에 들어갔다
                continue
            for k in range(card, card + groupSize):
                if count[k] == 0:              # 이어질 숫자가 없다
                    return False
                count[k] -= 1
        return True
```

```text
[3, 1, 2, 2, 4, 3] 3 True
[1, 2, 3, 4, 5] 4 False
[1, 2, 3, 6, 2, 3, 4, 7, 8] 3 True
[5] 1 True
[1, 2, 4, 5, 6, 7] 3 False
[8, 10, 12] 3 False
```

`Counter`는 없는 키를 읽으면 0을 돌려줘서 `count.get(k, 0)`을 쓸 필요가 없다. 다만 `count[k] == 0`처럼 읽기만 해도 키가 생기지는 않는다. `count[k] -= 1`은 0보다 클 때만 실행되니 음수 장수가 생기지 않는다. Python의 `sorted`는 숫자를 숫자로 비교하니 JavaScript 같은 비교자 문제가 없다.

```java
import java.util.*;

class Solution {
    public boolean isNStraightHand(int[] hand, int groupSize) {
        if (hand.length % groupSize != 0) return false;   // 장수가 나누어떨어지지 않는다
        Map<Integer, Integer> count = new HashMap<>();
        for (int c : hand) count.merge(c, 1, Integer::sum);
        int[] sorted = hand.clone();
        Arrays.sort(sorted);                                // int[]는 오름차순 정렬
        for (int c : sorted) {
            if (count.get(c) == 0) continue;                // 이미 다른 묶음에 들어갔다
            for (int k = c; k < c + groupSize; k++) {
                int v = count.getOrDefault(k, 0);
                if (v == 0) return false;                   // 이어질 숫자가 없다
                count.put(k, v - 1);
            }
        }
        return true;
    }
}
```

```text
[3, 1, 2, 2, 4, 3] 3 true
[1, 2, 3, 4, 5] 4 false
[1, 2, 3, 6, 2, 3, 4, 7, 8] 3 true
[5] 1 true
[1, 2, 4, 5, 6, 7] 3 false
[8, 10, 12] 3 false
```

`main`에서 같은 입력을 넣은 결과다. Java에서 짚을 곳이 두 군데 있다. `c + groupSize`는 최대 10^9 + 10^4라 `int`에 들어간다. 카드 숫자 상한이 21억 근처까지 올라가는 변형이면 넘친다. 그리고 `count.get(c) == 0`은 `Integer`를 `int`로 풀어서 비교하니 괜찮지만, 두 `Integer`를 `==`로 비교하면 -128~127 밖의 값에서 틀린다. 장부 대신 `TreeMap`을 쓰면 `firstKey()`가 가장 작은 숫자를 주니 정렬 배열 없이 힙 풀이와 같은 흐름으로 쓸 수 있다. 바닥난 키를 `remove`하면 된다.

## 다섯 가지 묶는 법의 비용

n은 카드 수, m은 서로 다른 숫자의 수다.

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 정렬 후 배열에서 지우기 | O(n²) | O(n) | 생각을 확인할 때만 |
| 정렬 + 개수 장부 | O(n log n) | O(n) | 기본 답. 설명이 가장 쉽다 |
| 최소 힙 | O(n + m log m) | O(m) | 같은 숫자가 많을 때, "가장 작은 것"을 드러내고 싶을 때 |
| 열린 묶음 수 세기 | O(n + m log m) | O(m) | 묶음이 클 때, 개수만 주어질 때 |
| 줄의 맨 앞 찾기 | 평균 O(n) | O(m) | 정렬 없이 하라는 꼬리 질문에 |

## 묶다가 틀리는 자리

### JavaScript 기본 정렬로 숫자를 정렬한다

```js
const sorted = [...hand].sort();   // 비교자가 없다
```

비교자 없이 `sort()`를 부르면 숫자를 문자열로 바꿔 사전 순으로 정렬한다. `[9, 10, 11].sort()`는 `[10, 11, 9]`가 된다. 장부 풀이에 이 줄을 넣으면 10을 가장 작은 카드로 보고 10, 11, 12를 찾다가 `false`를 낸다. 정답은 `true`다. 한 자리 숫자만 있는 테스트에서는 안 드러나서 늦게 발견된다. 정렬 비교자 이야기는 [정렬 알고리즘 글](/posts/sorting-algorithms)에도 있다.

### 정렬하지 않고 들어온 순서대로 묶는다

정렬을 빼고 `hand`를 그대로 훑으면 가장 작은 카드에서 시작한다는 보장이 깨진다. `[2, 3, 1, 4]`, 묶음 크기 2에서 2로 먼저 `2, 3`을 묶고 나면 1은 2가 없어 묶이지 못해 `false`가 나온다. 정답은 `1, 2`와 `3, 4`로 `true`다. 마지막 풀이가 정렬 없이 되는 이유는 아무 카드에서 시작하지 않고 줄의 맨 앞까지 내려가기 때문이다.

### 같은 숫자를 한 묶음에 두 번 넣는다

장부 대신 집합(Set)으로 "있는지"만 보면 장수가 사라진다. `[1, 1, 2, 3]`, 묶음 크기 2를 집합으로 보면 1, 2, 3만 남아 실제보다 카드가 적어진다. 반대로 장부를 쓰면서 묶음 안에서 같은 숫자를 두 번 빼는 실수도 있다. 묶음 안의 숫자는 `c, c + 1, ...`로 하나씩만 커져야 한다.

### 장부가 0인 카드에서 묶음을 시작한다

정렬 배열을 훑을 때 `count.get(c) === 0`이면 건너뛰는 줄을 빼먹으면, 이미 앞 묶음에 쓴 카드로 또 묶음을 시작하려다 `v === 0`에 걸려 `false`가 난다. 예시 `[3, 1, 2, 2, 4, 3]`에서 두 번째 2에 도착하면 2의 장부가 이미 0이라 바로 실패한다. 이 줄은 "가장 작은 카드"의 정의를 지키는 줄이다.

### 장수 검사로 끝내 버린다

카드 수가 `groupSize`의 배수인지만 보고 `true`를 돌려주는 코드는 `[1, 2, 4, 5, 6, 7]`, 묶음 크기 3에서 틀린다. 이 검사는 실패를 빨리 거르는 지름길일 뿐이다. 반대로 이 검사를 빼도 장부 풀이의 답은 바뀌지 않는다. 남는 카드가 생기면 결국 이어질 숫자가 없어 `false`가 난다.

## 묶는 규칙이 바뀌면

### 묶음 길이가 정해져 있지 않다면

LeetCode 659번 Split Array into Consecutive Subsequences는 정렬된 배열을 길이 3 이상의 연속 수열들로 나눌 수 있는지 묻는다. 길이가 자유로워서 "새로 시작할까, 기존 줄에 붙일까"를 골라야 한다. 이때 그리디 규칙은 "이어 붙일 수 있는 줄이 있으면 먼저 붙인다"다. 숫자 x마다 x - 1에서 끝나는 줄의 수를 장부로 세 두고, 있으면 붙이고, 없을 때만 x, x + 1, x + 2를 한꺼번에 떼어 새 줄을 연다. 열린 묶음 수를 세는 풀이와 같은 장부 감각이다.

### 같은 문제의 다른 이름

LeetCode 1296번 Divide Array in Sets of K Consecutive Numbers는 문제 설명만 다르고 846번과 같은 문제다. 이 글의 코드를 그대로 쓸 수 있다.

### 실제로 묶음을 돌려 달라면

`true`/`false` 대신 묶음 목록을 돌려 달라면 장부 풀이에서 묶음을 만들 때마다 `[c, c + 1, ...]`를 결과 배열에 넣으면 된다. 복잡도는 같고 결과 공간 O(n)이 든다. 열린 묶음 수 풀이는 숫자를 묶음 단위로 다루지 않아서 목록을 만들기 번거롭다.

### 카드가 스트림으로 들어온다면

카드를 다 받기 전에 판정해야 하면 가장 작은 카드를 알 수 없으니 이 그리디를 바로 쓸 수 없다. 대신 카드가 정렬된 순서로 들어온다고 보장되면, 열린 묶음 수 풀이가 그대로 스트림에서 돈다. 숫자 하나를 받을 때마다 O(1)에 판정을 이어 가고, 메모리는 최근 `groupSize`칸의 큐만 든다.

### 숫자 범위가 작다면

카드 숫자가 0~10^4처럼 작으면 해시맵 대신 길이가 숫자 범위인 배열을 장부로 쓰고, 정렬 없이 0부터 차례로 훑으면 된다. 카운팅 정렬과 같은 생각으로 O(n + 범위)다. 이 문제는 숫자가 10^9까지라 못 쓰지만, 꼬리 질문으로 자주 나온다.

같은 그리디 패턴의 다른 문제로는 [Merge Triplets to Form Target Triplet](/posts/leetcode-merge-triplets-to-form-target-triplet), [Valid Parenthesis String](/posts/leetcode-valid-parenthesis-string), [Candy](/posts/leetcode-candy), [IPO](/posts/leetcode-ipo), 그리고 [Partition Labels](/posts/leetcode-partition-labels)가 있다.

## 면접에서 나올 만한 질문

### 왜 가장 작은 카드부터 묶나요?

남은 카드 중 가장 작은 숫자는 자기 앞에 올 숫자가 없어서 반드시 어떤 묶음의 맨 앞이어야 하기 때문이다. 그러면 그 묶음의 나머지 숫자도 정해진다. 고를 여지가 없는 선택만 하니 그리디가 나중에 손해 볼 일이 없다. 그 묶음을 만들 수 없으면 어떤 방법으로도 만들 수 없어서 바로 `false`다.

### 시간 복잡도는 얼마이고 어디서 나오나요?

기본 풀이는 O(n log n)이고 정렬이 그 대부분이다. 묶음을 만드는 일은 묶음마다 `groupSize`번인데 묶음이 `n / groupSize`개라 합쳐서 O(n)이다. 서로 다른 숫자만 정렬하면 O(n + m log m)이고, 줄의 맨 앞을 찾아가면 정렬 없이 평균 O(n)이다.

### 해시맵 대신 정렬 배열에서 직접 지우면 안 되나요?

답은 맞지만 O(n²)이다. 다음 숫자 카드를 찾는 `indexOf`와 지우는 `splice`가 각각 배열을 훑어서, 1만 장에서는 버티지만 10만 장에서는 3초가 걸렸다. 카드의 위치는 필요 없고 숫자별 장수만 알면 되니 장부로 바꾸는 게 맞다.

### 최소 힙 풀이에서 바닥난 숫자가 맨 위가 아니면 왜 실패인가요?

그 숫자보다 작은 숫자가 아직 카드를 갖고 있다는 뜻이기 때문이다. 그 작은 숫자로 시작하거나 이어 가는 묶음은 범위상 바닥난 숫자를 꼭 지나야 하는데, 그 카드가 이미 없다. 그래서 그 자리에서 `false`를 돌려준다. 이 검사가 있어야 "힙의 맨 위 = 남은 카드 중 가장 작은 숫자"라는 약속이 지켜지고, 실패도 가장 이른 시점에 알아챈다.

### 묶음 크기가 크면 느려지지 않나요?

장부 풀이는 묶음 하나마다 `groupSize`칸을 돌지만 전체로는 카드 수만큼이라 괜찮다. 다만 같은 숫자로 시작하는 묶음을 한 번에 다루고 싶으면 숫자마다 열린 묶음 수만 세는 풀이를 쓴다. 숫자 하나에 O(1)이라 `groupSize`와 상관없이 O(n + m log m)이다.

### 정렬 없이 풀 수 있나요?

있다. 아무 카드나 잡고 장부에서 `card - 1`이 남아 있는 동안 내려가면 그 줄의 맨 앞이 나오고, 거기서 묶음을 시작하면 된다. 한 번 내려간 구간은 바로 장수가 0이 되니 다시 내려가지 않아 평균 O(n)이다. 해시맵 상수가 커서 실제로는 정렬 풀이와 비슷하게 걸렸다.

### Java로 옮길 때 주의할 점은?

`c + groupSize`가 `int` 범위를 넘지 않는지 본다. 이 문제는 최대 10^9 + 10^4라 괜찮다. 장부를 `Map<Integer, Integer>`로 쓰면 두 값을 `==`로 비교하는 실수를 조심한다. 가장 작은 키를 바로 꺼내고 싶으면 `TreeMap`의 `firstKey()`를 쓰면 힙 풀이와 같은 흐름이 된다.
