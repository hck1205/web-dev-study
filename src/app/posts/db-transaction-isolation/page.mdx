무선 이어폰 재고가 딱 1개 남았다. 두 사람이 거의 같은 순간에 구매 버튼을 눌렀다. 주문 코드는 단순하다. 재고를 읽어서 0보다 크면 1을 빼고 주문을 만든다. 테스트할 때는 한 번도 문제가 없었다. 그런데 이날 두 주문이 모두 성공했고, 관리자 화면의 재고는 -1이 됐다.

또 다른 장면도 있다. kim의 계좌에서 lee의 계좌로 30,000원을 보내는 코드가 출금 `UPDATE`를 실행한 직후 서버가 죽었다. 다시 켜 보니 kim의 돈은 빠져나갔는데 lee는 받지 못했을까.

두 장면 모두 트랜잭션 이야기다. 두 번째는 트랜잭션이 기본으로 막아 주고, 첫 번째는 트랜잭션을 썼는데도 생긴다. 이 글은 왜 그런지, 격리 수준이 정확히 무엇을 막고 무엇을 안 막는지를 실제로 두 세션을 띄워 재현하면서 따라간다. 재고 -1을 실제로 고치는 방법과 교착 상태는 [잠금과 교착 상태 글](/posts/db-locking-deadlock)에서 이어 간다.

예제는 끝까지 같은 테이블을 쓴다. 계좌 `accounts`(1번 kim 100,000원, 2번 lee 50,000원), 상품 `products`(1001번 무선 이어폰 재고 1개, 1002번 충전 케이스 30개, 1003번 이어팁 120개), 주문 `orders`다. SQL은 PostgreSQL 16 기준이고, MySQL 8(InnoDB)과 다른 부분은 따로 짚는다. 출력은 PostgreSQL 16.15에 psql 두 개를 붙여 실제로 실행한 결과다.

```sql
CREATE TABLE accounts (
  account_id bigint PRIMARY KEY,
  owner      text   NOT NULL,
  balance    bigint NOT NULL CHECK (balance >= 0)   -- 잔액은 음수가 될 수 없다
);

CREATE TABLE products (
  product_id bigint  PRIMARY KEY,
  name       text    NOT NULL,
  stock      integer NOT NULL,                      -- 일부러 CHECK를 안 걸었다
  version    integer NOT NULL DEFAULT 1             -- 낙관적 잠금에서 쓴다
);

CREATE TABLE orders (
  order_id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    bigint NOT NULL,
  product_id bigint NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

INSERT INTO accounts VALUES (1, 'kim', 100000), (2, 'lee', 50000);
INSERT INTO products VALUES (1001, '무선 이어폰', 1), (1002, '충전 케이스', 30), (1003, '이어팁', 120);
```

## 마지막 1개를 둘이 샀다

처음 장면의 주문 코드를 SQL로 옮기면 이렇다. 앱은 `SELECT`로 재고를 읽고, 0보다 크면 `UPDATE`로 1을 뺀다. 두 사람의 요청을 세션 A와 세션 B로 놓고, 실제로 실행된 순서대로 번호를 붙였다. PostgreSQL의 기본 격리 수준인 `READ COMMITTED`다.

```sql
-- [1] A
BEGIN;
SELECT stock FROM products WHERE product_id = 1001;   -- 1. 재고가 있으니 진행

-- [2] B
BEGIN;
SELECT stock FROM products WHERE product_id = 1001;   -- 1. B도 재고가 있다고 본다

-- [3] A
UPDATE products SET stock = stock - 1 WHERE product_id = 1001;   -- UPDATE 1

-- [4] B
UPDATE products SET stock = stock - 1 WHERE product_id = 1001;   -- 응답 없이 멈춘다

-- [5] A
COMMIT;            -- 이 순간 B의 UPDATE가 풀려서 UPDATE 1

-- [6] B
COMMIT;
SELECT stock FROM products WHERE product_id = 1001;
```

```text
 stock
-------
    -1
(1 row)
```

[4]에서 B가 멈춘 이유는 행 잠금이다. A가 1001번 행을 `UPDATE`하면서 그 행에 배타 잠금을 잡았고, 커밋할 때까지 다른 트랜잭션은 같은 행을 고칠 수 없다. A가 커밋하자 B는 행의 최신 값(0)을 다시 읽어 거기서 1을 뺐다. DB는 시킨 대로 정확히 했다. 문제는 [2]에서 B가 본 "재고 1"이 [5] 이후에는 이미 틀린 정보였다는 데 있다. 앱은 낡은 정보로 판단했고, DB는 그 판단을 검사할 방법이 없었다. 아래 그림에서 다음을 누르면 순서대로 볼 수 있다.

## 트랜잭션이 약속하는 네 가지

트랜잭션은 여러 SQL을 하나의 작업 단위로 묶는 것이다. 이 묶음이 지켜 주는 성질을 머리글자로 ACID라고 부른다. 하나씩, 없으면 무엇이 깨지는지로 보면 쉽다.

원자성(Atomicity)은 묶음 안의 변경이 전부 반영되거나 전부 취소된다는 약속이다. 두 번째 장면의 송금이 그렇다. 출금 `UPDATE`만 실행되고 서버가 죽으면, 그 트랜잭션은 커밋되지 않았으니 재시작 후 없던 일이 된다. PostgreSQL은 변경을 먼저 WAL(Write-Ahead Log, 데이터 파일보다 먼저 쓰는 변경 기록)에 적고, 복구할 때 이 로그를 다시 재생한다. 커밋 기록이 없는 트랜잭션이 만든 행은 "중단된 트랜잭션의 것"으로 표시돼 아무에게도 보이지 않는다. 원자성이 없으면 kim의 30,000원이 공중에서 사라진다.

일관성(Consistency)은 트랜잭션 전후로 DB가 정한 규칙(제약 조건)이 지켜진다는 약속이다. `accounts`의 `CHECK (balance >= 0)`이 그 규칙이다. 규칙을 어기는 변경이 하나라도 있으면 트랜잭션 전체가 실패한다. 다만 DB가 지켜 주는 건 DB에 적어 둔 규칙뿐이다. "재고는 음수가 될 수 없다"를 제약으로 안 적었으니 처음 장면의 -1은 DB 입장에서 일관된 상태다.

격리성(Isolation)은 동시에 실행되는 트랜잭션이 서로의 중간 상태를 보거나 서로를 방해하지 않는다는 약속이다. 그런데 이 약속에는 강도가 있다. 완벽하게 지키면 느리고, 느슨하게 지키면 빠르지만 처음 장면 같은 일이 생긴다. 그 강도가 격리 수준이고, 이 글 대부분이 이 이야기다.

지속성(Durability)은 커밋이 성공했다고 응답한 변경은 전원이 꺼져도 남는다는 약속이다. PostgreSQL은 `COMMIT`에 응답하기 전에 WAL을 디스크에 `fsync`한다. `synchronous_commit = off`로 바꾸면 커밋 응답이 빨라지는 대신, 장애 때 최근 몇백 ms 안에 커밋한 트랜잭션이 사라질 수 있다(데이터가 깨지지는 않는다). MySQL InnoDB에서는 `innodb_flush_log_at_trx_commit = 1`(기본값)이 같은 역할이고, 복제용 binlog까지 지키려면 `sync_binlog = 1`도 함께 둔다.

## BEGIN, COMMIT, ROLLBACK, SAVEPOINT

psql은 기본이 자동 커밋(autocommit)이다. `BEGIN` 없이 실행한 문장은 각자 하나의 트랜잭션으로 바로 커밋된다. 여러 문장을 묶으려면 `BEGIN`으로 열고 `COMMIT`으로 닫는다.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 30000 WHERE account_id = 1;   -- kim 출금
UPDATE accounts SET balance = balance + 30000 WHERE account_id = 2;   -- lee 입금
COMMIT;
SELECT * FROM accounts ORDER BY account_id;
```

```text
BEGIN
UPDATE 1
UPDATE 1
COMMIT
 account_id | owner | balance
------------+-------+---------
          1 | kim   |   70000
          2 | lee   |   80000
(2 rows)
```

이번엔 kim의 잔액(70,000원)보다 많은 200,000원을 보내 보자. 입금을 먼저 쓰고 출금을 나중에 썼다.

```sql
BEGIN;
UPDATE accounts SET balance = balance + 200000 WHERE account_id = 2;  -- 입금은 성공
UPDATE accounts SET balance = balance - 200000 WHERE account_id = 1;  -- CHECK 위반
SELECT * FROM accounts;                                              -- 뭘 해도 거부된다
COMMIT;                                                              -- 커밋이 아니라 롤백된다
```

```text
BEGIN
UPDATE 1
ERROR:  new row for relation "accounts" violates check constraint "accounts_balance_check"
DETAIL:  Failing row contains (1, kim, -130000).
ERROR:  current transaction is aborted, commands ignored until end of transaction block
ROLLBACK
```

여기서 두 가지를 봐야 한다. PostgreSQL은 트랜잭션 안에서 에러가 하나 나면 그 트랜잭션을 "중단됨" 상태로 만들고, 이후 모든 문장을 거부한다. 그리고 마지막 줄을 보면 `COMMIT`을 보냈는데 `ROLLBACK`이 돌아왔다. 먼저 성공했던 lee의 입금도 함께 취소됐다. 원자성이 동작한 것이다.

MySQL은 다르다. 제약 위반 같은 에러는 그 문장만 취소하고 트랜잭션은 계속 열어 둔다(교착 상태처럼 트랜잭션 전체를 롤백하는 에러도 있다). 앱이 에러를 무시하고 `COMMIT`하면 입금만 반영된다. 그래서 MySQL에서는 에러가 나면 앱이 반드시 `ROLLBACK`을 보내야 한다.

트랜잭션 전체가 아니라 일부만 되돌리고 싶으면 `SAVEPOINT`를 쓴다.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 10000 WHERE account_id = 1;
SAVEPOINT before_bonus;                                              -- 여기까지 표시
UPDATE accounts SET balance = balance - 999999 WHERE account_id = 2; -- 실패
ROLLBACK TO SAVEPOINT before_bonus;                                  -- 실패한 부분만 되돌린다
UPDATE accounts SET balance = balance + 10000 WHERE account_id = 2;
COMMIT;
SELECT * FROM accounts ORDER BY account_id;
```

```text
BEGIN
UPDATE 1
SAVEPOINT
ERROR:  new row for relation "accounts" violates check constraint "accounts_balance_check"
DETAIL:  Failing row contains (2, lee, -919999).
ROLLBACK
UPDATE 1
COMMIT
 account_id | owner | balance
------------+-------+---------
          1 | kim   |   60000
          2 | lee   |   90000
(2 rows)
```

`ROLLBACK TO SAVEPOINT`가 중단 상태를 풀어 줘서, 이어지는 `UPDATE`와 `COMMIT`이 정상 처리됐다. 첫 번째 출금은 살아 있다. Django의 중첩 `atomic`, Spring의 `NESTED` 전파, SQLAlchemy의 `begin_nested`가 이 세이브포인트를 쓴다.

하나 더 있다. PostgreSQL은 `CREATE TABLE`, `ALTER TABLE` 같은 DDL도 트랜잭션 안에서 롤백된다. 마이그레이션이 중간에 실패해도 테이블이 반쯤 바뀐 채로 남지 않는다. MySQL은 DDL을 실행하는 순간 그 전까지의 트랜잭션을 암묵적으로 커밋하고, DDL 자체도 롤백되지 않는다.

## 동시에 고치면 생기는 다섯 가지 일

격리 수준은 "어떤 이상한 일을 허용하느냐"로 정의된다. SQL 표준이 이름 붙인 세 가지에, 실무에서 더 자주 부딪히는 두 가지를 더해 다섯 가지를 실제로 재현해 봤다.

### 커밋 안 된 값을 읽는다 (dirty read)

A가 kim의 잔액에서 30,000원을 뺐지만 아직 커밋하지 않았다. 이 순간 B가 잔액을 읽어 70,000원을 봤는데, A가 롤백하면 B는 존재한 적 없는 값을 본 셈이다. 가장 낮은 `READ UNCOMMITTED`에서 표준이 허용하는 현상이다. PostgreSQL에서 그대로 해 보면 이렇다.

```sql
-- [1] A
BEGIN;
UPDATE accounts SET balance = balance - 30000 WHERE account_id = 1;   -- 아직 커밋 안 함

-- [2] B
BEGIN ISOLATION LEVEL READ UNCOMMITTED;
SELECT balance FROM accounts WHERE account_id = 1;

-- [3] A
ROLLBACK;
```

```text
 balance
---------
  100000
(1 row)
```

B는 `READ UNCOMMITTED`를 요청했는데도 커밋된 값 100,000원을 봤다. PostgreSQL은 `READ UNCOMMITTED`를 받아 주기는 하지만 실제로는 `READ COMMITTED`로 동작한다. 커밋 안 된 값을 보여 주는 방법이 아예 없다. MySQL InnoDB의 `READ UNCOMMITTED`는 실제로 커밋 안 된 값을 보여 준다.

### 같은 줄을 두 번 읽었는데 값이 다르다 (non-repeatable read)

```sql
-- [1] A  (READ COMMITTED)
BEGIN;
SELECT balance FROM accounts WHERE account_id = 1;   -- 100000

-- [2] B  (자동 커밋)
UPDATE accounts SET balance = balance - 30000 WHERE account_id = 1;

-- [3] A
SELECT balance FROM accounts WHERE account_id = 1;   -- 같은 트랜잭션, 같은 쿼리
COMMIT;
```

```text
 balance
---------
   70000
(1 row)
```

A는 한 트랜잭션 안에서 같은 행을 두 번 읽었는데 100,000과 70,000을 봤다. `READ COMMITTED`는 문장마다 그 시점에 커밋된 데이터를 새로 본다. 잔액을 읽어 검사하고 다시 읽어 계산하는 코드라면 두 값이 다를 수 있다는 뜻이다. 같은 실험을 `REPEATABLE READ`로 하면 결과가 달라진다.

```sql
-- [1] A
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE account_id = 1;   -- 70000

-- [2] B
UPDATE accounts SET balance = balance + 30000 WHERE account_id = 1;   -- 커밋됨

-- [3] A
SELECT balance FROM accounts WHERE account_id = 1;   -- 여전히 70000
COMMIT;
SELECT balance FROM accounts WHERE account_id = 1;   -- 이제 100000
```

`REPEATABLE READ`의 A는 트랜잭션에서 첫 쿼리를 실행한 시점의 스냅숏(그 순간 커밋된 데이터의 사진)을 끝까지 쓴다. B가 커밋한 변경은 A가 커밋하고 새 트랜잭션을 시작한 뒤에야 보인다.

### 조건에 맞는 줄 수가 바뀐다 (phantom read)

이번엔 행 하나의 값이 아니라 조건에 맞는 행의 집합이 바뀌는 경우다. 재고 50개 미만인 상품을 센다.

```sql
-- [1] A  (READ COMMITTED)
BEGIN;
SELECT count(*) FROM products WHERE stock < 50;   -- 2

-- [2] B
INSERT INTO products (product_id, name, stock) VALUES (1004, '케이블', 10);

-- [3] A
SELECT count(*) FROM products WHERE stock < 50;   -- 3
COMMIT;
```

없던 행이 유령처럼 나타났다고 팬텀(phantom)이라 부른다. 표준은 `REPEATABLE READ`에서도 팬텀을 허용한다. 하지만 PostgreSQL의 `REPEATABLE READ`는 스냅숏을 쓰니 새로 들어온 행도 안 보인다. 같은 실험에서 [3]의 결과가 2로 그대로였다. 표준보다 강하게 동작하는 것이다.

### 둘 다 고쳤는데 하나가 사라진다 (lost update)

충전 케이스 재고가 30개다. 이번 코드는 앱에서 재고를 읽어 1을 뺀 값을 계산하고, 그 숫자를 그대로 쓴다. ORM에서 객체를 읽어 필드를 바꾸고 저장하는 코드가 대부분 이렇게 동작한다.

```sql
-- [1] A
BEGIN;
SELECT stock FROM products WHERE product_id = 1002;   -- 30

-- [2] B
BEGIN;
SELECT stock FROM products WHERE product_id = 1002;   -- 30

-- [3] A  (앱이 30 - 1을 계산했다)
UPDATE products SET stock = 29 WHERE product_id = 1002;
COMMIT;

-- [4] B  (B도 30 - 1을 계산했다)
UPDATE products SET stock = 29 WHERE product_id = 1002;
COMMIT;
SELECT stock FROM products WHERE product_id = 1002;
```

```text
 stock
-------
    29
(1 row)
```

두 개가 팔렸는데 재고는 하나만 줄었다. B의 쓰기가 A의 쓰기를 덮어써서 A의 갱신이 사라졌다. 이게 갱신 손실(lost update)이다. 에러는 하나도 없었다. 처음 장면의 -1과 원인이 같다. 둘 다 읽은 값을 근거로 쓰는데, 읽은 뒤 쓰기 전에 다른 트랜잭션이 끼어들었다.

`REPEATABLE READ`에서 처음 장면을 다시 해 보면 PostgreSQL이 막는다.

```sql
-- [1] A
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT stock FROM products WHERE product_id = 1001;   -- 1

-- [2] B
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT stock FROM products WHERE product_id = 1001;   -- 1

-- [3] A
UPDATE products SET stock = stock - 1 WHERE product_id = 1001;   -- UPDATE 1

-- [4] B
UPDATE products SET stock = stock - 1 WHERE product_id = 1001;   -- 대기

-- [5] A
COMMIT;            -- B의 UPDATE가 에러로 끝난다

-- [6] B
COMMIT;
```

```text
ERROR:  could not serialize access due to concurrent update
ROLLBACK
```

B의 스냅숏에서 재고는 1인데, 고치려는 행은 스냅숏 이후에 다른 트랜잭션이 이미 바꿔 놓았다. PostgreSQL의 `REPEATABLE READ`는 이걸 그냥 덮어쓰지 않고 에러를 낸다. 재고는 0으로 끝난다. B는 재시도해야 하고, 재시도하면 재고 0을 보고 주문을 거절한다.

MySQL InnoDB의 `REPEATABLE READ`는 이 에러를 내지 않는다. B의 `UPDATE`는 기다렸다가 최신 커밋 값(0)에서 1을 빼서 -1을 만든다. 같은 격리 수준 이름인데 결과가 다르다.

### 각자 맞게 했는데 합치면 틀린다 (write skew)

"1인 1개 한정" 이어팁 이벤트가 있다. 주문 코드는 kim(user_id 1)의 이어팁 주문이 이미 있는지 세고, 0이면 주문을 넣는다. kim이 탭 두 개에서 동시에 눌렀다.

```sql
-- [1] A, B 둘 다
BEGIN ISOLATION LEVEL REPEATABLE READ;

-- [2] A
SELECT count(*) FROM orders WHERE user_id = 1 AND product_id = 1003;   -- 0
-- [3] B
SELECT count(*) FROM orders WHERE user_id = 1 AND product_id = 1003;   -- 0

-- [4] A
INSERT INTO orders (user_id, product_id) VALUES (1, 1003);   -- INSERT 0 1
-- [5] B
INSERT INTO orders (user_id, product_id) VALUES (1, 1003);   -- INSERT 0 1

-- [6] A, B
COMMIT;            -- 둘 다 COMMIT
SELECT order_id, user_id, product_id FROM orders;
```

```text
 order_id | user_id | product_id
----------+---------+------------
        1 |       1 |       1003
        2 |       1 |       1003
(2 rows)
```

`REPEATABLE READ`인데 둘 다 성공했다. 두 트랜잭션은 같은 조건을 읽고, 서로 다른 행을 썼다. 같은 행을 고친 게 아니니 갱신 손실 검사에 걸리지 않는다. 각자는 "주문이 0개였으니 넣어도 된다"는 올바른 판단을 했지만, 상대방이 넣은 행은 자기 스냅숏에 없었다. 이게 쓰기 왜곡(write skew)이다. 교과서에서는 "당직 의사가 최소 한 명은 남아야 하는데, 두 의사가 동시에 서로 남아 있는 걸 보고 둘 다 퇴근한다"는 예로 설명한다.

PostgreSQL에서 이걸 막는 격리 수준은 `SERIALIZABLE`뿐이다. 같은 순서로 실행하면 이렇게 된다.

이 이벤트처럼 규칙이 "최대 1개"면 더 간단한 방법이 있다. `UNIQUE (user_id, product_id)`를 걸면 격리 수준과 상관없이 DB가 막는다.

```text
ERROR:  duplicate key value violates unique constraint "orders_one_per_user"
DETAIL:  Key (user_id, product_id)=(1, 1003) already exists.
```

같은 순서로 실행하면 B의 `INSERT`가 A의 커밋을 기다렸다가 이 에러로 끝난다. 하지만 "1인 최대 3개"나 "당직 최소 1명"처럼 제약 하나로 표현할 수 없는 규칙이면 `SERIALIZABLE`을 쓰거나, 규칙의 기준이 되는 행(회원 행 같은 것)을 `FOR UPDATE`로 먼저 잠가서 줄을 세운다.

## 격리 수준 네 단계와 실제 동작

SQL 표준은 격리 수준 네 개를 "어떤 현상을 허용하는가"로 정의한다. 문제는 DB마다 구현이 달라서 같은 이름이 다른 동작을 한다는 것이다. 위에서 직접 재현한 결과를 기준으로 정리했다.

| 격리 수준 | PostgreSQL 16 | MySQL 8 InnoDB |
|---|---|---|
| READ UNCOMMITTED | READ COMMITTED와 같다 | dirty read가 실제로 생긴다 |
| READ COMMITTED | 문장마다 새 스냅숏. 기본값 | 문장마다 새 스냅숏. 갭 잠금을 거의 안 쓴다 |
| REPEATABLE READ | 트랜잭션 스냅숏. 팬텀 없음. 같은 행 동시 수정은 40001 에러. write skew는 생긴다 | 기본값. 일반 SELECT는 스냅숏, 잠금 읽기와 UPDATE는 최신 값과 넥스트 키 잠금. 동시 수정은 에러 없이 기다렸다 덮어쓴다 |
| SERIALIZABLE | SSI. 충돌 시 40001, 재시도 필요 | 자동 커밋이 꺼져 있으면 일반 SELECT를 FOR SHARE로 바꿔 잠금으로 줄을 세운다 |

격리 수준은 트랜잭션마다 정할 수도 있고, 세션이나 DB 전체의 기본값을 바꿀 수도 있다.

```sql
SHOW default_transaction_isolation;                      -- read committed

BEGIN ISOLATION LEVEL SERIALIZABLE;                       -- 이 트랜잭션만
-- 또는 BEGIN; 직후 첫 쿼리 전에
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

ALTER DATABASE shop_tx SET default_transaction_isolation = 'serializable';  -- 새 연결부터 적용
```

```sql
-- MySQL 8
SELECT @@transaction_isolation;                          -- REPEATABLE-READ
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

높은 수준이 무조건 안전한 것도 아니다. PostgreSQL의 `REPEATABLE READ`와 `SERIALIZABLE`은 충돌하면 에러를 내니, 재시도 코드가 없는 앱에 그대로 켜면 동시 요청이 몰릴 때 에러가 사용자에게 그대로 간다. 격리 수준을 올리는 건 재시도 코드와 한 세트다.

## 버전을 남겨서 읽기와 쓰기를 떼어 놓기 (MVCC)

`REPEATABLE READ`의 A가 B의 커밋 후에도 옛 값을 계속 볼 수 있었던 건, 옛 값이 어딘가에 남아 있었기 때문이다. PostgreSQL은 행을 고칠 때 덮어쓰지 않는다. 옛 버전은 두고 새 버전을 하나 더 쓴다. 이렇게 여러 버전을 두고 트랜잭션마다 볼 버전을 골라 주는 방식이 MVCC(Multi-Version Concurrency Control)다. 덕분에 읽기는 쓰기를 기다리지 않고, 쓰기도 읽기를 기다리지 않는다.

각 행 버전에는 숨은 열이 있다. `xmin`은 이 버전을 만든 트랜잭션 번호, `xmax`는 이 버전을 지운(또는 새 버전으로 바꾼) 트랜잭션 번호, `ctid`는 행 버전의 물리적 위치(페이지 번호, 페이지 안 순번)다. 직접 볼 수 있다. kim의 잔액이 100,000원인 새 테이블에서 시작한다.

```sql
-- [1] B
SELECT xmin, xmax, ctid, balance FROM accounts WHERE account_id = 1;

-- [2] A
BEGIN;
UPDATE accounts SET balance = balance - 30000 WHERE account_id = 1;
SELECT xmin, xmax, ctid, balance FROM accounts WHERE account_id = 1;

-- [3] B  (A는 아직 커밋 전)
SELECT xmin, xmax, ctid, balance FROM accounts WHERE account_id = 1;

-- [4] A
COMMIT;

-- [5] B
SELECT xmin, xmax, ctid, balance FROM accounts WHERE account_id = 1;
```

```text
-- [1] B
 xmin | xmax | ctid  | balance
------+------+-------+---------
 1202 |    0 | (0,1) |  100000

-- [2] A
 xmin | xmax | ctid  | balance
------+------+-------+---------
 1203 |    0 | (0,3) |   70000

-- [3] B
 xmin | xmax | ctid  | balance
------+------+-------+---------
 1202 | 1203 | (0,1) |  100000

-- [5] B
 xmin | xmax | ctid  | balance
------+------+-------+---------
 1203 |    0 | (0,3) |   70000
```

[2]에서 A는 트랜잭션 1203번이다. A가 보는 행은 `ctid`가 `(0,3)`인 새 버전이다. 원래 행 `(0,1)`을 고친 게 아니라 같은 페이지의 세 번째 자리에 새로 썼다. [3]에서 B는 여전히 `(0,1)`을 본다. 그런데 `xmax`가 1203으로 바뀌어 있다. "1203번 트랜잭션이 이 버전을 지우는 중"이라는 표시다. B의 스냅숏에서 1203은 아직 커밋 전이니, B에게 이 버전은 살아 있다. 아래 그림에서 다음을 누르면 두 버전이 언제 누구에게 보이는지 따라갈 수 있다.

이 방식에는 청소 비용이 따른다. 옛 버전(dead tuple)은 `UPDATE`나 `DELETE`마다 하나씩 쌓이고, 이걸 치우는 게 `VACUUM`이다. 보통은 autovacuum이 알아서 돌지만, 옛 버전을 볼 수 있는 트랜잭션이 하나라도 열려 있으면 치울 수 없다. 오래 열린 `REPEATABLE READ` 트랜잭션 하나를 두고 다른 세션에서 lee의 행을 고친 뒤 `VACUUM`을 돌려 봤다.

```sql
-- [1] A
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE account_id = 2;    -- 스냅숏을 잡는다

-- [2] B
UPDATE accounts SET balance = balance + 1000 WHERE account_id = 2;
VACUUM (VERBOSE) accounts;

-- [3] A
COMMIT;

-- [4] B
VACUUM (VERBOSE) accounts;
```

```text
-- [2]의 VACUUM 출력 중 일부
tuples: 0 removed, 3 remain, 1 are dead but not yet removable

-- [4]의 VACUUM 출력 중 일부
tuples: 1 removed, 2 remain, 0 are dead but not yet removable
```

봐야 할 줄은 `1 are dead but not yet removable`이다. 죽은 버전이 하나 있는데 A의 스냅숏이 아직 볼 수 있어서 못 치웠다. A가 끝나자 `1 removed`로 바뀌었다. 운영에서 몇 시간 열린 트랜잭션 하나가 있으면 그동안 DB 전체의 모든 테이블에서 죽은 버전이 쌓인다. 테이블과 인덱스가 부풀고(bloat), 같은 데이터를 읽는 데 더 많은 페이지를 읽게 되어 느려진다.

MySQL InnoDB도 MVCC를 쓰지만 방식이 다르다. 행은 제자리에서 고치고, 옛 값은 undo 로그에 따로 남긴다. 옛 스냅숏이 읽을 때는 undo 로그를 거슬러 옛 버전을 다시 만든다. 청소는 purge 스레드가 한다. 오래 열린 트랜잭션이 있으면 undo 로그가 치워지지 못하고 쌓이는 건 똑같다(`SHOW ENGINE INNODB STATUS`의 `History list length`가 계속 늘어난다).

## MySQL InnoDB는 어떻게 다른가

InnoDB의 기본값은 `REPEATABLE READ`다. 이 수준에서 읽기는 두 종류로 갈린다.

일관된 읽기(consistent read)는 잠금 없는 일반 `SELECT`다. 트랜잭션에서 첫 일관된 읽기를 한 시점의 스냅숏을 끝까지 쓴다. `BEGIN`한 시점이 아니라 첫 `SELECT` 시점이다(`START TRANSACTION WITH CONSISTENT SNAPSHOT`이면 시작 시점).

잠금 읽기(locking read)는 `SELECT ... FOR UPDATE`, `SELECT ... FOR SHARE`, 그리고 `UPDATE`, `DELETE`다. 이건 스냅숏이 아니라 최신 커밋 값을 읽고 잠금을 건다. 같은 트랜잭션 안에서 일반 `SELECT`로 본 값과 `UPDATE`가 고친 값이 다를 수 있는 이유다. 앞에서 InnoDB가 처음 장면을 -1로 만든 것도 `UPDATE`가 최신 값 0을 읽었기 때문이다.

잠금 읽기가 범위를 훑으면 InnoDB는 찾은 행뿐 아니라 행 사이의 빈 간격(gap)에도 잠금을 건다. 행 잠금과 그 앞 간격의 잠금을 합친 걸 넥스트 키 잠금(next-key lock)이라 부른다. 다른 트랜잭션이 그 간격에 새 행을 넣지 못하니, 잠금 읽기끼리는 팬텀이 생기지 않는다. 대신 `stock`에 인덱스가 없는 상태에서 범위를 잠그면 훑은 모든 행과 간격이 잠겨 사실상 테이블 전체가 막힌다. 아래 출력은 MySQL을 띄우지 않고 적은 예시다(에러 형식은 MySQL 8 그대로다).

```sql
-- [1] A (MySQL 8, REPEATABLE READ)
START TRANSACTION;
SELECT * FROM products WHERE stock < 50 FOR UPDATE;   -- 범위와 간격을 잠근다

-- [2] B
INSERT INTO products (product_id, name, stock) VALUES (1004, '케이블', 10);  -- 기다린다
```

```text
-- 예시: innodb_lock_wait_timeout(기본 50초)이 지나면
ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction
```

InnoDB의 잠금 대기 시간 초과는 기본적으로 그 문장만 롤백하고 트랜잭션은 열어 둔다(`innodb_rollback_on_timeout = OFF`). PostgreSQL과 반대라서, 에러를 받으면 앱이 직접 `ROLLBACK`할지 정해야 한다. 갭 잠금 때문에 교착 상태가 잦으면 `READ COMMITTED`로 내리는 선택지도 있다. 그 수준에서는 갭 잠금을 외래키·중복 검사 같은 경우 말고는 쓰지 않는다.


## SQLD에서 묻는 트랜잭션과 격리 수준

SQLD에서 트랜잭션은 2과목 TCL(Transaction Control Language) 부분에서 주로 나오고, 격리 수준과 잠금은 기출 범위와 회차에 따라 비중이 다르다. 응시 회차의 공식 출제 기준을 확인하고, 자주 보이던 내용을 시험 말로 다시 묶으면 이렇다.

트랜잭션의 특성은 원자성, 일관성, 고립성(격리성), 지속성이다. 보기에서 "트랜잭션이 실행되는 동안 다른 트랜잭션이 중간 결과를 볼 수 없다"는 고립성, "성공한 트랜잭션의 결과는 영구 저장된다"는 지속성, "전부 실행되거나 전부 실행되지 않는다"는 원자성, "실행 전후 데이터베이스 상태가 모순 없다"는 일관성이다.

TCL 문제는 DBMS 차이를 자주 묻는다. Oracle은 DDL을 실행하면 자동 커밋되고, DML은 명시적으로 `COMMIT`해야 한다. SQL Server는 기본이 자동 커밋 모드이고, `BEGIN TRANSACTION`으로 명시적 트랜잭션을 연다. 세이브포인트 문법도 다르다. Oracle은 `SAVEPOINT sp1;` / `ROLLBACK TO sp1;`, SQL Server는 `SAVE TRANSACTION sp1;` / `ROLLBACK TRANSACTION sp1;`이다. 세이브포인트로 되돌린 뒤에도 트랜잭션은 끝나지 않았으니, 그 전 변경은 마지막 `COMMIT`이나 `ROLLBACK`에 따라 정해진다. 같은 이름의 세이브포인트를 다시 만들면 나중 것이 앞의 것을 대신한다는 것도 단골이다.

격리 수준별로 생길 수 있는 현상은 표준 기준으로 이렇게 외운다.

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read |
|---|---|---|---|
| READ UNCOMMITTED | 발생 | 발생 | 발생 |
| READ COMMITTED | 없음 | 발생 | 발생 |
| REPEATABLE READ | 없음 | 없음 | 발생 |
| SERIALIZABLE | 없음 | 없음 | 없음 |

이 표는 표준의 최소 요구다. 위에서 본 것처럼 PostgreSQL의 REPEATABLE READ는 팬텀도 막는다. 시험은 표준 표대로 답한다.


잠금 종류, 2단계 잠금, 교착 상태의 네 조건은 [잠금과 교착 상태 글](/posts/db-locking-deadlock)에 모아 두었다.

## 격리 수준은 무엇을 허용하느냐의 문제다

트랜잭션은 원자성과 지속성으로 "반만 반영"을 막아 주지만, 동시에 실행되는 트랜잭션끼리의 문제는 격리 수준만큼만 막는다. PostgreSQL 기본값 `READ COMMITTED`는 커밋 안 된 값을 보여 주지 않을 뿐, 읽은 값이 쓰기 전에 바뀌는 건 막지 않는다. 그래서 처음 장면의 재고 -1과 갱신 손실이 생긴다. `REPEATABLE READ`는 같은 행을 동시에 고치면 에러로 알려 주지만 서로 다른 행을 쓰는 쓰기 왜곡은 놓치고, `SERIALIZABLE`은 그것까지 잡는 대신 재시도를 요구한다. 이 모든 동작의 바탕에는 행을 덮어쓰지 않고 버전을 남기는 MVCC가 있고, 그 옛 버전은 열린 트랜잭션이 끝나야 치워진다. 그 틈을 실제로 어떻게 막는지는 [잠금과 교착 상태 글](/posts/db-locking-deadlock)에서 본다.

## 면접에서 나올 만한 질문

### ACID를 설명해 주세요.

원자성은 트랜잭션의 변경이 전부 반영되거나 전부 취소되는 것, 일관성은 전후로 제약 조건이 지켜지는 것, 격리성은 동시에 실행되는 트랜잭션이 서로의 중간 상태에 영향받지 않는 것, 지속성은 커밋된 변경이 장애 후에도 남는 것이다. PostgreSQL은 WAL을 먼저 디스크에 쓰고 커밋 응답을 해서 원자성과 지속성을 지킨다. 격리성은 수준을 고를 수 있고, 기본값 READ COMMITTED는 갱신 손실을 막지 않는다.

### 격리 수준별로 어떤 현상이 생기나요?

표준상 READ UNCOMMITTED는 dirty read, READ COMMITTED는 non-repeatable read와 phantom read, REPEATABLE READ는 phantom read를 허용하고 SERIALIZABLE은 모두 막는다. 실제 동작은 DB마다 다르다. PostgreSQL은 READ UNCOMMITTED가 READ COMMITTED와 같고, REPEATABLE READ가 스냅숏이라 팬텀도 안 보이지만 write skew는 생긴다. MySQL InnoDB는 기본이 REPEATABLE READ이고 잠금 읽기에 넥스트 키 잠금을 써서 팬텀을 막는다.

### PostgreSQL의 MVCC는 어떻게 동작하나요?

UPDATE는 행을 덮어쓰지 않고 새 버전을 쓰며, 각 버전에 만든 트랜잭션(xmin)과 지운 트랜잭션(xmax) 번호를 남긴다. 트랜잭션은 스냅숏을 기준으로 자기가 볼 버전을 골라서, 읽기와 쓰기가 서로 기다리지 않는다. 옛 버전은 VACUUM이 치우는데, 그 버전을 볼 수 있는 트랜잭션이 열려 있으면 치울 수 없다. 그래서 오래 열린 트랜잭션이 테이블 비대화의 흔한 원인이다.

### REPEATABLE READ에서 write skew는 왜 생기나요?

두 트랜잭션이 같은 조건을 읽고 서로 다른 행을 쓰기 때문이다. 같은 행을 고치지 않으니 동시 수정 검사에 걸리지 않고, 각자의 스냅숏에는 상대가 쓴 행이 없다. 1인 1개 한정 주문을 두 탭에서 동시에 넣으면 둘 다 성공한다. SERIALIZABLE을 쓰면 PostgreSQL이 읽기·쓰기 의존의 순환을 찾아 하나를 40001로 실패시키고, 규칙이 단순하면 UNIQUE 제약이나 기준 행에 FOR UPDATE를 거는 방법이 더 간단하다.

### PostgreSQL에서 READ UNCOMMITTED로 설정하면 dirty read가 생기나요?

생기지 않는다. PostgreSQL은 `READ UNCOMMITTED`를 받아들이지만 실제로는 `READ COMMITTED`와 똑같이 동작해서, 커밋 안 된 값은 어떤 수준에서도 보이지 않는다. MVCC로 커밋된 버전만 골라 보여 주기 때문이다. MySQL InnoDB의 `READ UNCOMMITTED`에서는 dirty read가 실제로 생긴다. 같은 이름의 격리 수준이라도 DB마다 동작이 다르니 표준 표만 믿지 말고 쓰는 DB에서 확인한다.
