출시 전날. 기능은 다 됐고 테스트도 통과했다. 그런데 보안팀이 돌린 외부 점검 보고서에 "SQL 주입 가능"이 떴다. 검색창에 따옴표를 넣으면 DB 에러가 그대로 노출됐고, 거기서 쿼리를 조작할 수 있었다. 출시는 사흘 밀렸다. 억울한 건, 이 구멍이 **두 달 전 그 코드를 짜던 날** 이미 있었다는 것이다. 그때 알았으면 5분이면 고쳤을 걸, 다 쌓인 뒤에 찾으니 되돌리는 비용이 컸다.

이게 "왼쪽으로 옮기기(shift-left)"가 나온 이유다. 개발 과정을 왼쪽(기획·코딩)에서 오른쪽(배포·운영)으로 흐르는 줄로 보면, 보안 검사는 늘 맨 오른쪽 끝에 있었다. 그걸 왼쪽으로 당겨 코드를 짜는 순간순간에 자동으로 돌리자는 것이다. 개발(Dev)과 운영(Ops)을 합친 DevOps에 보안(Sec)을 끼워 넣은 DevSecOps는 이걸 문화와 파이프라인으로 제도화한 말이다. 핵심 차이는 "보안을 마지막 관문으로 두느냐, 모든 단계에 녹이느냐"다.

이 글은 일부러 구멍을 낸 Node 앱 하나를 로컬에 두고, 네 종류 도구를 실제로 돌려 각각 무엇을 잡고 무엇을 놓치는지 본다. SAST(소스를 읽는), SCA(의존성을 보는), DAST(돌아가는 앱을 찌르는), 시크릿 스캔(비밀 값을 뒤지는)이다. 각 도구가 보는 자리가 다르다는 걸 그림으로 먼저 잡자.

## 소스를 읽는 SAST

SAST(Static Application Security Testing)는 소스 코드를 읽어 위험한 패턴을 찾는다. 대표 도구가 Semgrep(규칙을 사람이 읽기 쉽게 쓰는 오픈소스)과 CodeQL(코드를 데이터베이스로 바꿔 질의하는 깃허브의 도구)이다. 핵심 능력은 **테인트 추적(taint tracking)**, 즉 "믿을 수 없는 입력(소스)이 위험한 함수(싱크)까지 손대지 않고 흘러가나"를 따라가는 것이다.

취약 앱에 SQL 문자열 이어 붙이기와 셸 명령 조립을 심어 두고, 요청 값이 싱크까지 흐르는 규칙을 Semgrep으로 돌렸다.

```text
3 Code Findings

   sql-string-concat
      요청 값이 이어 붙인 SQL 문자열로 pool.query에 들어간다. $1 바인딩을 쓴다.
       13┆ const { rows } = await pool.query(sql);
   command-injection-exec
      요청 값이 셸 명령으로 들어간다. execFile과 인자 배열을 쓴다.
       17┆ exec("ping -c 1 " + url.searchParams.get("host"), ...);
   order-by-concat
       32┆ const { rows } = await pool.query("SELECT id, name FROM products ORDER BY " + sort);
```

세 군데를 정확히 짚었다. 주목할 건 세 번째다. `ORDER BY` 뒤에 붙는 `sort`는 사실 코드에서 허용 목록으로 걸러져 안전한데, SAST는 "요청 값이 쿼리 문자열에 들어간다"는 **패턴**만 보고 걸었다. 이게 SAST의 성격이다.

- **장점**: 코드를 짜자마자, 앱을 띄우지 않고도 돈다. PR마다 몇 초 만에 돌아 가장 왼쪽에 둘 수 있다. [SQL 주입](/posts/sql-injection), 명령 주입, 안전하지 않은 역직렬화처럼 코드 구조로 드러나는 결함에 강하다.
- **약점**: **오탐(false positive)** 이 많다. 위 `ORDER BY`처럼 실제로는 안전한 코드를 거는 일이 흔하다. 또 런타임에만 드러나는 문제(설정 실수, 환경에 따라 달라지는 흐름)는 못 본다. 코드에 없는 결함은 영원히 못 본다.

오탐이 많다는 건 치명적인 약점이다. 경고가 열 개 뜨는데 여덟 개가 가짜면 사람들은 전부 무시하기 시작한다. 그래서 SAST는 규칙을 프로젝트에 맞게 조정하고, 이미 아는 오탐은 베이스라인으로 걸러 "새로 생긴 것"만 PR을 막게 쓴다.

## 의존성을 보는 SCA

우리가 짠 코드는 빙산의 일각이다. `node_modules`에는 남이 짠 코드가 수백 개 들어 있다. SCA(Software Composition Analysis)는 그 의존성 목록을 알려진 취약점 데이터베이스와 대조한다. `npm audit`, Dependabot, Snyk, OSV-Scanner가 여기 속한다. 일부러 낡은 `lodash`를 넣고 `npm audit`을 돌렸다.

```text
# npm audit report

lodash  <=4.17.23
Severity: high
Command Injection in lodash - https://github.com/advisories/GHSA-35jh-r3h4-6jhm
Prototype Pollution in lodash - https://github.com/advisories/GHSA-p6mc-m468-83gw
...
1 high severity vulnerability
```

우리 코드는 한 줄도 안 봤다. 버전 번호를 공개 권고 데이터베이스와 맞춰 본 것이다. SCA의 성격이 여기서 나온다.

- **장점**: 내가 짜지 않은 코드의 결함을 잡는다. 실제 침해의 상당수가 낡은 라이브러리에서 온다. 자동 PR(Dependabot)로 올려 주기까지 한다.
- **약점**: "이 버전에 취약점이 있다"는 알지만 "우리가 그 취약한 함수를 **실제로 쓰나**"는 기본적으로 모른다. 그래서 쓰지도 않는 의존성 때문에 경고가 쌓인다(도달 가능성 분석을 하는 도구도 늘고 있다). 또 공개 데이터베이스에 아직 안 올라온 결함(제로데이)은 못 본다. 공급망 쪽(타이포스쿼팅, 악성 설치 스크립트)은 SCA가 아니라 다른 방어가 필요한데, 이건 [소프트웨어 공급망 공격과 빌드 파이프라인 강화](/posts/software-supply-chain-ci-hardening)에서 다룬다.

## 돌아가는 앱을 찌르는 DAST

DAST(Dynamic Application Security Testing)는 반대다. 소스를 안 본다. 앱을 **실제로 띄워 놓고** 바깥에서 요청을 쏘며 반응을 본다. OWASP ZAP(오픈소스), Burp Suite(펜테스터가 가장 많이 쓰는 상용 프록시)가 대표다. 취약 앱을 staging에 띄우고, 입력에 마커를 넣어 응답에 그대로 반사되는지, 따옴표에 DB 에러가 새는지, 보안 헤더가 빠졌는지 긁는 작은 프로브를 돌렸다. ZAP 이미지는 이 실험 환경에 받기에 너무 커서 node로 짠 프로브를 대신 썼고, 앱의 DB도 실제 DB 대신 가짜 모듈로 바꿔 두었다. 그래서 아래 출력은 도구가 하는 일의 모양을 보여 주는 것이고, ZAP 리포트 형식은 아니다.

```text
/hello     reflected-unescaped=true  quote->200
           missing: Content-Security-Policy
           missing: X-Content-Type-Options
/products  reflected-unescaped=false  quote->500 SQL error leaked
           missing: Content-Security-Policy
           missing: X-Content-Type-Options
/orders    reflected-unescaped=false  quote->200
```

`/hello`는 입력이 이스케이프 없이 반사됐다([XSS](/posts/xss) 신호). `/products`는 따옴표 하나에 500과 함께 DB 에러가 노출됐다(SQL 주입 신호). 모든 응답에 보안 헤더가 없다. 이건 실제 HTTP 응답을 보고 판단한 것이다.

- **장점**: **오탐이 적다**. 실제로 요청을 쏴서 반응을 확인하므로 "진짜 뚫리는지"에 가깝다. 소스 언어·프레임워크를 몰라도 되고, 설정 실수·인증 흐름 문제·헤더 누락처럼 런타임에만 드러나는 걸 본다. 블랙박스라 외부 공격자의 시점과 같다.
- **약점**: 앱이 돌아야 하고, 환경을 꾸려야 하므로 느리다(PR마다 돌리기 부담스러워 보통 야간에 돈다). **미탐(false negative)** 이 큰 문제다. 크롤러가 닿지 못한 화면, 특정 상태에서만 열리는 경로는 아예 안 찔러 보니 "구멍이 있어도 못 찾는다". 어디가 뚫렸는지는 알려 줘도 소스 어느 줄인지는 직접 알려 주지 않는다.

여기서 SAST와 DAST의 **오탐·미탐 성향**이 선명하게 갈린다. SAST는 코드를 다 훑어 "있을 법한 것"까지 걸어 **오탐이 많고**, DAST는 실제로 찔러 봐서 **오탐은 적지만** 못 찔러 본 곳을 통째로 놓쳐 **미탐이 크다**. 그래서 둘은 경쟁이 아니라 보완이다. 이 둘을 코드 실행 중에 계측기를 심어 합치려는 게 IAST(Interactive AST)인데, 테스트가 돌 때 안에서 데이터 흐름을 관찰해 "실제로 도달하는 취약점"을 낮은 오탐으로 잡는다. 대신 런타임 계측 비용이 들고 언어 지원이 갈린다.

## 비밀 값을 뒤지는 시크릿 스캔

네 번째. 코드에 실수로 적어 둔 API 키·비밀번호를 찾는다. gitleaks, truffleHog, 깃허브의 push protection이 여기 속한다. 커밋 히스토리에 Stripe 키처럼 생긴 문자열을 심고 gitleaks를 돌렸다.

```text
Finding:     const STRIPE_KEY = "sk_live_••••(글에서는 가림)"
RuleID:      stripe-access-token
Entropy:     5.162621
File:        server.js
Line:        6
```

키 형식에 맞는 정규식과 엔트로피(문자열이 얼마나 무작위한가)로 찾아낸다. 지운 커밋에도 남아 있는 비밀 값까지 히스토리를 거슬러 뒤진다. 이 결이 더 궁금하면 [비밀 관리](/posts/secrets-management)와 [커밋에 들어가면 안 되는 것](/posts/git-large-files-secrets)을 보라. 핵심은 **한 번 올라간 비밀은 지워도 유출된 것으로 간주하고 로테이션(교체)** 해야 한다는 점이다.

## 네 도구를 파이프라인에 배치한다

## 무엇을 보고 빌드를 막나

관문에 두면 "언제 병합을 막을지"를 정해야 한다. 전부 막으면(심각도 낮은 것까지) 개발이 멈추고, 아무것도 안 막으면 관문이 무의미하다. 보통 **심각도 문턱**을 정하고, 이미 아는 것은 베이스라인으로 뺀 뒤 "문턱 이상이면서 새로 생긴 것"만 막는다. 이 판정 로직을 직접 짜 보자.

  solution={`function gateDecision(findings, opts) {\n  const order = { info: 0, low: 1, medium: 2, high: 3, critical: 4 };\n  const threshold = order[opts.failOn];\n  const baseline = new Set(opts.baseline ?? []);\n  const blocking = findings.filter(\n    (f) => order[f.severity] >= threshold && !baseline.has(f.id)\n  );\n  return { pass: blocking.length === 0, blocking: blocking.map((f) => f.id) };\n}`}
  tests={[
    { args: [[{ id: "A", severity: "high" }, { id: "B", severity: "medium" }, { id: "C", severity: "low" }, { id: "D", severity: "critical" }], { failOn: "high" }], expected: { pass: false, blocking: ["A", "D"] } },
    { args: [[{ id: "A", severity: "high" }, { id: "B", severity: "medium" }, { id: "C", severity: "low" }, { id: "D", severity: "critical" }], { failOn: "high", baseline: ["A", "D"] }], expected: { pass: true, blocking: [] } },
    { args: [[{ id: "A", severity: "high" }, { id: "D", severity: "critical" }], { failOn: "critical" }], expected: { pass: false, blocking: ["D"] } },
    { args: [[], { failOn: "low" }], expected: { pass: true, blocking: [] } },
  ]}
/>

두 번째 테스트가 베이스라인의 쓸모를 보여 준다. 기존에 알던 `A`, `D`를 베이스라인에 넣으면 그건 막지 않는다. 그래서 레거시 코드에 결함이 수십 개 있어도 "오늘부터 새로 생긴 것"만 막아, 관문을 당장 켤 수 있다. 베이스라인은 따로 이슈로 관리해 조금씩 줄인다. 문턱은 보통 `high` 이상을 막고 `medium` 이하는 리포트만 남긴다.

## 스캐너가 0건이면 안전한가

가장 위험한 착각이다. 스캐너 네 종류가 모두 0건이어도 안전하다는 뜻이 아니다.

- SAST는 코드로 드러나는 패턴만, DAST는 크롤러가 닿은 화면만 본다. **업무 로직 결함**은 거의 못 잡는다. "가격 필드에 음수를 넣어 결제가 줄어든다", "주문 번호만 바꿔 남의 주문을 본다(IDOR)" 같은 건 코드 패턴으로도, 무작위 요청으로도 안 걸린다. 이런 [인가](/posts/authn-vs-authz) 결함은 그 시스템을 이해한 사람만 찾는다.
- 자동 도구는 "알려진 모양"을 찾는다. 새로운 공격, 설계 수준의 결함, 여러 요청을 엮어야 터지는 것은 못 본다.

그래서 자동 스캔은 **바닥을 까는 것**이고, 그 위에 사람이 하는 수동 펜테스트와 [위협 모델링](/posts/threat-modeling-stride)과 [코드 리뷰](/posts/code-review-practices)가 올라간다. 역할 분담은 이렇다. 반복되고 기계적인 건 자동 도구에 맡겨 매 PR마다 거르고, 사람은 그 위에서 **업무 로직과 설계**를 본다. 펜테스트는 출시 전이나 분기마다, 중요한 기능이 바뀔 때 한다. "스캐너 0건"은 "알려진 흔한 구멍은 없다"이지 "안전하다"가 아니다.

## 정리

보안 검사를 맨 끝에 두면 가장 비싼 때에 걸린다. 그래서 왼쪽으로 당겨 파이프라인에 녹인다. SAST는 소스를 읽어 코드 패턴 결함을 잡되 오탐이 많고, SCA는 의존성의 알려진 취약점을 잡되 실제 사용 여부는 모르고, DAST는 돌아가는 앱을 찔러 오탐은 적지만 못 찔러 본 곳을 놓치고, 시크릿 스캔은 새어 든 비밀 값을 찾는다. 빠른 셋은 PR 관문에, 느린 DAST는 야간에 두고, 심각도 문턱과 베이스라인으로 "새로 생긴 심각한 것"만 막는다. 그리고 이 모두를 돌려 0건이어도 업무 로직 결함은 남으니, 자동 스캔 위에 사람의 펜테스트와 리뷰를 얹는다.

## 면접에서 나올 만한 질문

### SAST와 DAST의 차이는?

SAST는 소스 코드를 실행하지 않고 읽어 위험한 패턴을 찾고, DAST는 앱을 실제로 띄워 바깥에서 요청을 쏘며 반응을 본다. SAST는 PR마다 몇 초에 돌 만큼 빠르고 어느 줄이 문제인지 짚어 주지만 오탐이 많다. DAST는 환경이 필요해 느리지만 실제로 뚫리는지에 가까워 오탐이 적다. 보는 자리가 달라 경쟁이 아니라 보완이다.

### SAST는 오탐이 많고 DAST는 미탐이 크다는 게 무슨 뜻인가?

SAST는 코드 전체를 훑어 "요청 값이 쿼리에 들어간다" 같은 패턴을 다 거는데, 실제로는 허용 목록으로 걸러져 안전한 코드까지 걸어 가짜 경고(오탐)가 많다. DAST는 실제로 찔러 봐서 걸린 건 대체로 진짜지만, 크롤러가 닿지 못한 화면이나 특정 상태에서만 열리는 경로는 아예 안 찔러 봐서 구멍이 있어도 못 찾는 누락(미탐)이 크다.

### SCA가 "취약한 버전"을 찾아도 안심할 수 없는 이유는?

SCA는 의존성 버전을 알려진 취약점 데이터베이스와 대조할 뿐, 우리가 그 취약한 함수를 실제로 호출하는지는 기본적으로 모르기 때문이다. 그래서 쓰지도 않는 코드 때문에 경고가 쌓인다(도달 가능성 분석을 하는 도구도 늘고 있다). 반대로 공개 데이터베이스에 아직 없는 결함은 버전만으론 못 잡는다.

### IAST는 무엇이고 SAST·DAST와 어떻게 다른가?

IAST는 앱이 돌 때(보통 테스트 중) 안에 계측기를 심어 데이터 흐름을 관찰하며 취약점을 찾는다. SAST처럼 코드 내부를 알면서 DAST처럼 실제 실행을 보기 때문에, 실제로 도달하는 취약점을 낮은 오탐으로 짚고 소스 위치까지 알려 줄 수 있다. 대신 런타임 계측 비용이 들고 언어·프레임워크 지원이 갈린다.

### 보안 검사를 파이프라인 어디에 배치하나?

속도와 깊이로 나눈다. SAST·SCA·시크릿 스캔은 수십 초라 PR 관문에 두어 병합 전에 거르고, DAST는 앱이 돌아야 하고 느리니 staging 배포 뒤 야간 배치에 둔다. 전부 PR마다 돌리면 느려서 아무도 안 쓰므로, 빠른 건 왼쪽에, 느린 건 뒤로 미루는 것이 원칙이다.

### 스캐너가 모두 0건이면 안전한가?

아니다. 자동 도구는 "알려진 모양"만 찾는다. 가격에 음수를 넣거나 주문 번호를 바꿔 남의 것을 보는 업무 로직·인가 결함은 코드 패턴으로도 무작위 요청으로도 안 걸린다. 그래서 자동 스캔은 바닥을 까는 것이고, 그 위에 사람의 수동 펜테스트·위협 모델링·코드 리뷰가 필요하다. 0건은 "흔한 구멍은 없다"이지 "안전하다"가 아니다.

### 보안 검사로 빌드를 막는 기준은 어떻게 정하나?

심각도 문턱을 정하고 이미 아는 것은 베이스라인으로 뺀 뒤, 문턱 이상이면서 새로 생긴 것만 병합을 막는다. 보통 high 이상을 막고 medium 이하는 리포트만 남긴다. 베이스라인이 중요한 이유는, 레거시에 결함이 수십 개 있어도 "오늘부터 새로 생긴 것"만 막아 관문을 당장 켤 수 있고 기존 것은 따로 줄여 나갈 수 있기 때문이다.
