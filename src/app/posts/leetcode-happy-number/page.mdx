어떤 과정을 반복하다 보면 끝나거나, 아니면 같은 상태를 다시 만나 영원히 돈다. 무한 반복을 감지하는 일은 프로그램 곳곳에 나온다. 리다이렉트가 서로를 가리키는 링크, 상태 기계가 같은 상태 사이를 오가는 경우, 의사 난수 생성기의 주기 같은 것들이다. [Happy Number](https://leetcode.com/problems/happy-number/)는 그 문제를 가장 작게 줄여 놓은 연습이다. 계산은 덧셈과 곱셈뿐이지만, 면접에서는 "왜 반드시 끝나나요?"와 "메모리를 안 쓰고 할 수 있나요?"가 이어진다.

이 글은 풀이 네 개를 놓는다. 본 숫자를 집합에 적어 두는 방법, 느린 포인터와 빠른 포인터로 고리를 찾는 방법(플로이드), 걸음을 두 배씩 늘리는 방법(브렌트), 그리고 숫자의 성질을 써서 4 하나만 확인하는 방법이다. 고리 찾기 자체는 [Linked List Cycle](/posts/leetcode-linked-list-cycle)에서 연결 리스트로 다뤘다. 이 글은 리스트가 없는데도 같은 기법이 왜 통하는지에 집중한다. 코드는 모두 Node.js 22, Python 3, Java 21에서 직접 돌렸다.

## 자릿수를 제곱해서 더하는 일을 되풀이한다

양의 정수 `n`이 주어진다. `n`을 "각 자릿수의 제곱의 합"으로 바꾸는 일을 되풀이한다. 언젠가 1이 되면 `true`, 1이 되지 않고 끝없이 돌면 `false`를 돌려준다.

- `n`은 1 이상 2^31 - 1(2,147,483,647) 이하다.

제약은 이것 하나다. 그런데 이 범위가 풀이의 안전성을 보장해 준다. 아무리 큰 `n`이 들어와도 한 번 바꾸면 730 이하가 된다는 걸 뒤에서 확인한다. 1이 되면 1의 다음도 1이라(1² = 1) 1에서 영원히 머문다. 그래서 "1이 된다"는 "1이라는 한 칸짜리 고리에 들어간다"로 볼 수도 있다. 이 관점이 플로이드 풀이에서 쓸모 있다.

## 19와 2를 손으로 굴려 보기

19부터 해 본다.

```text
19  → 1² + 9²         = 82
82  → 8² + 2²         = 68
68  → 6² + 8²         = 100
100 → 1² + 0² + 0²    = 1      행복한 수
```

이번엔 2다.

```text
2 → 4 → 16 → 37 → 58 → 89 → 145 → 42 → 20 → 4 → 16 → ...
```

4가 다시 나왔다. 그 뒤로는 앞에서 본 순서 그대로 영원히 돈다. 2는 행복한 수가 아니다.

아래 그림이 두 경우다. 위쪽 줄은 1에 닿아 멈추는 길이고, 아래쪽은 2가 4로 들어가 여덟 숫자짜리 고리를 도는 모습이다. 점이 화살표를 따라 흐르는 걸 보면 고리 안에서는 끝이 없다는 게 보인다.

그림을 연결 리스트로 봐도 된다. 숫자 하나가 노드고, "다음 숫자"가 `next` 포인터다. 다만 리스트가 메모리에 있는 게 아니라 함수 하나로 그때그때 계산된다. 이 문제는 그 리스트에 고리가 있는지, 아니면 1에서 끝나는지를 묻는 것과 같다.

## 숫자가 끝없이 커지지 않는 이유

손으로 해 볼 때는 두 결과만 나왔다. 1에 닿거나, 고리에 들어가거나. 세 번째 가능성은 없을까. 숫자가 반복되지도 않고 1에 닿지도 않으면서 계속 새로운 숫자로 커져 가는 경우다. 그런 경우가 있다면 "본 숫자를 기억해 두는" 풀이는 메모리를 다 쓰고 죽는다. 이걸 배제해야 모든 풀이가 성립한다.

d자리 수의 다음 값은 각 자리가 9일 때 가장 크니 많아야 81 × d다.

```text
자릿수 d   이 자릿수의 가장 작은 수   다음 값의 상한 81d
1          1                         81
2          10                        162
3          100                       243
4          1,000                     324
10         1,000,000,000             810
```

d가 4 이상이면 81d가 그 자릿수의 가장 작은 수 10^(d-1)보다 작다. 즉 네 자리 이상의 수는 한 번 바꿀 때마다 반드시 더 작아진다. 그러니 어떤 수에서 시작해도 언젠가 999 이하로 내려오고, 999 이하의 수의 다음 값은 243 이하라서 한번 내려오면 다시 커지지 않는다. 문제 범위의 가장 큰 경우도 직접 확인했다. 2^31 - 1 이하에서 다음 값이 가장 큰 수는 1,999,999,999이고, 그 값은 1 + 9 × 81 = 730이다.

결국 숫자는 243 이하의 유한한 범위 안에서 움직인다. 유한한 칸 안에서 같은 규칙으로 계속 걸으면 언젠가 이미 밟은 칸을 다시 밟는다(비둘기집 원리). 1을 다시 밟든, 다른 고리를 다시 밟든 둘 중 하나다. 세 번째 가능성은 없다.

1부터 100만까지 모든 수를 돌려 봤을 때 1이나 고리에 닿기까지 가장 오래 걸린 수는 15999로, 20번이었다. 실제 걸음 수가 아주 짧다는 뜻이다.

## 몇 걸음이면 끝나나

범위가 유한하다는 건 알았는데, 실제로 몇 걸음이 걸리는지도 궁금했다. 1부터 100만까지 모든 수를 집합 풀이로 돌리며 1에 닿거나 본 숫자를 다시 만나기까지의 걸음 수를 셌다.

```text
걸음 수 : 그 걸음 수가 걸린 수의 개수
0:1  1:6  2:3885  3:18636  4:56058  5:26175  6:37803  7:507  8:8
9:10066  10:52019  11:68919  12:158926  13:90100  14:136033
15:158099  16:86968  17:60293  18:19058  19:13980  20:2460
```

가장 오래 걸린 수(15999)도 20걸음이다. 0걸음은 1 자신이고, 걸음이 10 이상인 수가 많은 건 대부분이 불행한 수라서 여덟 칸짜리 고리를 한 바퀴 돌아야 "다시 만났다"가 되기 때문이다. 복잡도 표기로는 O(log n)이라 쓰지만, 실제로는 "아무리 커도 수십 걸음"이라고 말하는 쪽이 정확한 그림이다.

## 다음 숫자를 계산하는 함수

모든 풀이가 쓰는 부품부터 만든다. 10으로 나눈 나머지가 마지막 자릿수고, 10으로 나눈 몫이 그 자릿수를 떼어 낸 나머지 수다.

```js
function next(n) {
  let s = 0;
  while (n > 0) {
    const d = n % 10;        // 마지막 자릿수
    s += d * d;
    n = Math.floor(n / 10);  // 마지막 자릿수를 떼어 낸다
  }
  return s;
}
console.log(next(19), next(2147483647)); // 82 260
```

자릿수가 d = log₁₀n + 1개니 이 함수는 O(log n)이다. 첫 걸음 뒤에는 숫자가 세 자리 이하라 사실상 상수 시간이다.

JavaScript에서 `Math.floor`를 빼먹기 쉽다. `n = n / 10`으로 쓰면 1.9, 0.19, 0.019처럼 소수가 되면서 `n > 0`이 아주 오래 참이고, 그동안 `n % 10`이 소수 나머지를 더한다. 실제로 `next(19)`가 82가 아니라 84.64646464646465가 나왔다. 반복이 끝나는 건 숫자가 0으로 반올림될 때라 300번 넘게 돈다. Java나 C의 `int` 나눗셈은 소수점을 버리니 이 실수가 없다. 문자열로 바꿔 자릿수를 꺼내는 방법(`String(n).split("")`)도 같은 답을 주지만, 문자열과 배열을 만드느라 나머지 연산보다 느리다.

## 본 숫자를 집합에 적어 둔다

앞 절에서 숫자가 유한한 범위 안에서 반드시 반복된다는 걸 확인했다. 그렇다면 지나간 숫자를 모두 적어 두고, 이미 적힌 숫자가 다시 나오면 고리라고 판단하면 된다.

```js
function isHappy(n) {
  const seen = new Set();               // 지나간 숫자
  while (n !== 1 && !seen.has(n)) {     // 1이면 성공, 본 숫자면 고리
    seen.add(n);
    n = next(n);
  }
  return n === 1;
}
console.log(isHappy(19), isHappy(2)); // true false
```

해시 집합의 조회와 추가는 평균 O(1)이다. 집합이 어떻게 O(1)을 내는지는 [해시맵 글](/posts/ds-hash-map)에 있다.

복잡도를 따질 때 "n의 크기"가 아니라 "몇 걸음 만에 끝나나"를 봐야 한다. 걸음 수는 앞에서 본 대로 첫 몇 걸음에 숫자가 243 이하로 내려오고 그 뒤로는 243개를 넘는 새 숫자가 나올 수 없으니, 대략 O(log n) 걸음으로 본다. 걸음마다 `next`가 O(log n)이지만 첫 걸음 이후엔 상수라, 전체를 O(log n)으로 말하는 게 보통이다. 공간은 집합에 담긴 숫자 수만큼이다. 같은 범위라 O(log n)이고 실제로는 몇십 개다.

이 풀이는 짧고 틀릴 곳이 없어 면접의 첫 답으로 좋다. 꼬리 질문은 거의 항상 "집합 없이 할 수 있나요?"다.

## 두 사람이 다른 속도로 달린다

집합이 하던 일은 "다시 왔나"를 알아차리는 것이다. 이걸 메모리 없이 하는 방법이 플로이드의 고리 찾기(Floyd's cycle detection), 흔히 토끼와 거북이라고 부르는 방법이다. 두 숫자를 들고, 거북이(`slow`)는 한 번에 한 걸음, 토끼(`fast`)는 두 걸음씩 움직인다.

- 1에 닿는 길이면 토끼가 먼저 1에 닿는다.
- 고리가 있으면 둘 다 고리에 들어간 뒤, 토끼가 한 바퀴 뒤에서 거북이를 따라잡는다.

```js
function isHappy(n) {
  let slow = n, fast = next(n);         // 토끼는 한 걸음 앞에서 출발
  while (fast !== 1 && slow !== fast) {
    slow = next(slow);                  // 한 걸음
    fast = next(next(fast));            // 두 걸음
  }
  return fast === 1;
}
```

토끼를 한 걸음 앞에서 출발시킨 건 반복 조건 때문이다. 둘 다 `n`에서 출발하면 시작하자마자 `slow === fast`라 반복이 한 번도 돌지 않는다. 같은 자리에서 출발하고 싶으면 `do...while`로 먼저 한 번 움직이고 비교한다.

```js
function isHappy(n) {
  let slow = n, fast = n;
  do {
    slow = next(slow);
    fast = next(next(fast));
  } while (slow !== fast);   // 1도 자기 자신으로 가는 고리라 결국 만난다
  return slow === 1;         // 만난 곳이 1이면 행복한 수
}
```

이 모양은 `fast !== 1` 검사가 없다. 1을 "길이 1짜리 고리"로 보면 행복한 수도 고리에서 만나는 경우가 되니, 만난 자리가 1인지만 보면 된다. 1부터 10만까지 집합 풀이와 답이 같았다.

2에서 시작하는 고리 경우를 실제로 돌리며 두 값을 찍어 옮겼다. 위의 칸은 2가 지나가는 숫자 순서다. 강조된 칸이 토끼, 화살표가 거북이 위치다.

### 고리 안에서 반드시 만나는 이유

둘 다 고리에 들어온 순간부터 보자. 토끼가 거북이보다 고리 방향으로 k칸 뒤에 있다고 하면, 한 번 움직일 때마다 토끼는 두 칸, 거북이는 한 칸 가니 간격이 정확히 1씩 줄어든다. 간격이 2에서 1, 1에서 0이 되지 건너뛰지 않는다. 그래서 고리 길이가 L이면 고리에 들어온 뒤 L번 안에 반드시 같은 칸에 선다. 2의 경우 고리 길이가 8이고 실제로 8번 움직여 만났다.

1에 닿는 경우도 같은 틀로 설명된다. 1은 길이 1짜리 고리라서, 토끼가 먼저 1에 들어가고 거북이가 들어오면 만난다. 위 코드는 토끼가 1에 닿는 순간 바로 끝내서 거북이를 기다리지 않는다. `fast !== 1` 조건이 그 지름길이다. 이 조건을 빼도 거북이가 1에 도착하면 `slow === fast`로 끝나고, 마지막에 그 값이 1인지 보면 같은 답이 나온다.

복잡도는 집합 풀이와 같은 O(log n) 시간이고 공간은 변수 두 개라 O(1)이다. 대신 `next` 호출이 늘어난다. 직접 세어 보니 2에서 집합 풀이는 9번, 플로이드는 22번 불렀다. 토끼가 두 걸음씩 가고 거북이도 따로 계산하니 대략 세 배다. 걸음이 수십 번뿐이라 차이는 의미가 없지만, "공간을 줄인 대가로 계산을 더 한다"는 건 말할 수 있어야 한다.

## 걸음을 두 배씩 늘려 가며 기다린다

플로이드는 거북이도 매번 `next`를 계산한다. 브렌트(Brent)의 방법은 거북이를 가만히 세워 두고 토끼만 달리게 한다. 토끼가 1, 2, 4, 8, ... 걸음을 갈 때마다 거북이를 토끼 자리로 순간 이동시킨다. 고리 길이가 L이면 기다리는 걸음 수가 L 이상이 되는 순간 토끼가 고리를 한 바퀴 돌아 거북이 자리에 돌아온다.

```js
function isHappy(n) {
  let power = 1, lam = 1;               // 이번 구간 길이, 지금까지 걸은 수
  let tortoise = n, hare = next(n);
  while (hare !== 1 && tortoise !== hare) {
    if (power === lam) {                // 이번 구간을 다 걸었으면
      tortoise = hare;                  // 거북이를 토끼 자리로 옮기고
      power *= 2;                       // 다음 구간은 두 배로
      lam = 0;
    }
    hare = next(hare);                  // 토끼만 한 걸음
    lam++;
  }
  return hare === 1;
}
```

`next` 호출이 걸음당 한 번이라 플로이드보다 적게 부른다. 고리 길이(`lam`)도 덤으로 알 수 있다. 이 문제의 걸음 수에서는 차이가 보이지 않으니 면접에서는 "이런 방법도 있다" 정도로 말하면 된다. 1부터 20만까지 네 풀이의 답이 모두 같은 걸 확인했다.

## 행복하지 않은 수는 모두 4를 지난다

앞에서 숫자가 243 이하로 내려온다는 걸 봤다. 그 범위를 전부 돌려 보면 더 강한 사실이 나온다. 1부터 999까지 모든 수가 다시 밟는 첫 숫자를 모았더니 1, 4, 16, 20, 37, 42, 58, 89, 145 아홉 개뿐이었다. 1을 빼면 모두 4에서 시작하는 그 여덟 칸짜리 고리의 숫자다. 즉 십진수에서 자릿수 제곱합이 만드는 고리는 1과 이 고리, 딱 두 개다.

999 이하의 모든 수가 이 둘 중 하나로 가고, 더 큰 수는 999 이하로 내려오니 모든 양의 정수에서 성립한다. 그렇다면 고리를 찾을 필요 없이 "1이나 4가 나올 때까지" 돌리면 된다.

```js
function isHappy(n) {
  while (n !== 1 && n !== 4) n = next(n); // 4는 불행한 고리의 입구 중 하나
  return n === 1;
}
```

4를 고른 건 고리 안의 아무 숫자나 하나면 되기 때문이다. 고리에 들어온 수는 여덟 걸음 안에 4를 지난다. 2는 바로 다음이 4라 `next`를 한 번만 부른다.

가장 빠르고 짧지만 코드만 봐서는 왜 맞는지 알 수 없다. 이 코드의 정당성은 "고리가 하나뿐"이라는 수학적 사실에 걸려 있고, 그 사실은 컴퓨터로 1000 아래를 모두 돌려 보거나 증명을 알아야 확인된다. 면접에서 이걸 첫 답으로 내면 "4는 어디서 나왔나요?"에 답해야 한다. 집합이나 플로이드로 먼저 풀고, 덤으로 꺼내는 게 좋다. 자릿수를 세제곱하는 변형처럼 규칙이 바뀌면 이 코드는 바로 틀린다.

## Python과 Java로 옮기기

```python
class Solution:
    def next_num(self, n: int) -> int:
        s = 0
        while n > 0:
            n, d = divmod(n, 10)    # 몫과 나머지(마지막 자릿수)를 한 번에
            s += d * d
        return s

    def isHappy(self, n: int) -> bool:
        slow, fast = n, self.next_num(n)
        while fast != 1 and slow != fast:
            slow = self.next_num(slow)                   # 한 칸
            fast = self.next_num(self.next_num(fast))    # 두 칸
        return fast == 1

s = Solution()
print([x for x in range(1, 50) if s.isHappy(x)])
print(s.isHappy(2147483647), s.isHappy(1111111))
```

```text
[1, 7, 10, 13, 19, 23, 28, 31, 32, 44, 49]
False True
```

Python의 `divmod(n, 10)`은 몫과 나머지를 함께 돌려준다. `n // 10`과 `n % 10`을 따로 써도 된다. `/`를 쓰면 실수가 되니 JavaScript의 `Math.floor` 실수와 같은 버그가 난다. 집합 풀이를 쓴다면 `seen = set()`이고, 함수 이름이 `next`면 Python 내장 함수 `next`를 가리게 되니 `next_num`처럼 다른 이름을 쓴다.

```java
class Solution {
    private int next(int n) {
        int s = 0;
        while (n > 0) {
            int d = n % 10;     // 마지막 자릿수
            s += d * d;
            n /= 10;            // int 나눗셈은 소수점을 버린다
        }
        return s;
    }

    public boolean isHappy(int n) {
        int slow = n, fast = next(n);
        while (fast != 1 && slow != fast) {
            slow = next(slow);          // 한 칸
            fast = next(next(fast));    // 두 칸
        }
        return fast == 1;
    }

    public static void main(String[] args) {
        Solution s = new Solution();
        System.out.println(s.isHappy(19) + " " + s.isHappy(2) + " " + s.isHappy(1) + " " + s.isHappy(Integer.MAX_VALUE));
    }
}
```

```text
true false true false
```

Java에서 제곱합이 `int`를 넘칠 걱정은 없다. 가장 큰 입력에서도 다음 값이 730 이하라서다. 집합 풀이라면 `Set<Integer> seen = new HashSet<>()`에 `int`가 `Integer`로 박싱돼 들어간다. 값이 작아서 `==`로 비교해도 우연히 맞는 경우가 있지만(-128~127은 캐시된 객체), 집합 조회는 `contains`가 `equals`로 비교하니 걱정할 필요는 없다.

집합 풀이를 Java로 쓰면 이렇다. `Set.add`는 이미 있던 값이면 `false`를 돌려주니 조회와 추가를 한 번에 할 수 있다.

```java
import java.util.HashSet;
import java.util.Set;

class SetSolution {
    public boolean isHappy(int n) {
        Set<Integer> seen = new HashSet<>();
        while (n != 1 && seen.add(n)) {   // add가 false면 이미 본 숫자, 즉 고리
            int s = 0;
            for (int x = n; x > 0; x /= 10) s += (x % 10) * (x % 10);
            n = s;
        }
        return n == 1;
    }

    public static void main(String[] args) {
        SetSolution s = new SetSolution();
        System.out.println(s.isHappy(19) + " " + s.isHappy(2) + " " + s.isHappy(7));
    }
}
```

```text
true false true
```

## 네 풀이를 나란히

| 풀이 | 시간 | 추가 공간 | 언제 고르나 |
|---|---|---|---|
| 집합에 적기 | O(log n) | O(log n) | 첫 답. 짧고 정당성이 분명하다 |
| 플로이드 (토끼와 거북이) | O(log n) | O(1) | 메모리 없이 고리를 찾으라는 꼬리 질문의 답 |
| 브렌트 | O(log n) | O(1) | `next`가 비쌀 때. 고리 길이도 함께 얻는다 |
| 4가 나오면 멈추기 | O(log n) | O(1) | 고리가 하나뿐이라는 사실을 안다고 밝힐 때 |

시간이 모두 같은 건 걸음 수가 숫자 범위로 묶여 있기 때문이다. 고르는 기준은 공간과 설명하기 쉬운 정도다.

## 고리를 찾다가 자주 틀리는 곳

### 두 포인터를 같은 자리에서 출발시킨다

```js
let slow = n, fast = n;
while (fast !== 1 && slow !== fast) { /* ... */ } // 한 번도 돌지 않는다
return fast === 1;   // isHappy(19) → false
```

시작하자마자 `slow === fast`라 반복이 바로 끝나고, `n`이 1이 아니면 모두 `false`다. 토끼를 한 걸음 앞에 두거나, `do...while`로 먼저 움직인 뒤 비교한다.

### 반복 조건에 1 검사만 둔다

`while (n !== 1) n = next(n);`은 행복한 수에서는 맞는 답을 내지만, 2를 넣으면 영원히 돈다. 테스트를 행복한 수로만 하면 못 잡는다. 불행한 수 하나는 꼭 넣는다. 무한 반복은 시간 초과로 나타나서 원인이 코드의 어디인지 바로 보이지 않는다.

### 토끼가 1에 닿았는지 확인하지 않고 거북이만 본다

`return slow === 1`로 쓰면 틀린다. 플로이드 반복이 `fast === 1`로 끝났을 때 거북이는 아직 1에 오지 않았다. 19에서 반복이 끝날 때 거북이는 68이다. 반복을 끝낸 쪽, 즉 토끼를 봐야 한다.

### 자릿수를 꺼낼 때 소수가 생긴다

앞에서 본 `n / 10` 실수다. 정수 나눗셈이 따로 없는 JavaScript에서 특히 조심한다. `Math.floor` 대신 `(n / 10) | 0`을 쓰는 코드도 보이는데, 비트 연산은 피연산자를 32비트 부호 있는 정수로 바꾸기 때문에 몫이 2^31을 넘는 수(약 214억 이상)에서 엉뚱한 값이 된다. 이 문제의 범위에서는 괜찮지만 습관으로 쓰면 다른 문제에서 터진다. [비트 연산 글](/posts/bit-manipulation)에 그 이유가 있다.

## 규칙이 바뀌면 무엇이 달라지나

### 행복한 수를 모두 세라면

1부터 N까지 행복한 수의 개수를 구하라면 수마다 처음부터 돌리지 않는다. 문제 범위의 수는 한 걸음만 가면 810 이하가 되니, 810 이하의 답을 한 번 계산해 표로 만들어 두고 큰 수는 `next` 한 번 뒤 표를 찾는다.

```js
// 문제 범위의 수는 한 걸음이면 810 이하가 된다. 그 아래 답을 미리 계산해 둔다
const LIMIT = 810;
const table = new Array(LIMIT + 1);
for (let v = 1; v <= LIMIT; v++) table[v] = isHappy(v);

function countHappy(N) {
  let count = 0;
  for (let n = 1; n <= N; n++) {
    const v = n <= LIMIT ? n : next(n);   // 큰 수는 한 걸음 가면 표 안으로 들어온다
    if (table[v]) count++;
  }
  return count;
}
console.log(countHappy(100), countHappy(1000), countHappy(1000000));
```

```text
20 143 143071
```

100만까지 수마다 집합 풀이를 돌리면 내 컴퓨터에서 약 1.05초, 표를 쓰면 57ms였다. 같은 부분 문제(810 이하의 수가 행복한가)를 수없이 다시 푸는 걸 한 번으로 줄였으니 [동적 계획법](/posts/dynamic-programming)의 메모이제이션과 같은 생각이다. 표 크기는 입력 범위에서 나온 값이라, 범위가 커지면 한도를 다시 계산해야 한다. 열 자리까지는 81 × 10 = 810이면 충분하다.

### 자릿수를 세제곱해서 더한다면

같은 논리로 숫자는 유한한 범위에 갇히지만 고리가 여러 개다. 1부터 9999까지 돌려 보면 제자리 고리(자기 자신으로 돌아오는 수)가 1, 153, 370, 371, 407이고, 55에서 시작하는 세 칸 고리, 136과 919에서 시작하는 두 칸 고리, 160에서 시작하는 세 칸 고리가 따로 있다. "4가 나오면 멈추기" 같은 지름길은 쓸 수 없고, 집합이나 플로이드는 그대로 통한다. 일반적인 방법이 더 오래 살아남는 경우다.

### 다른 진법이라면

2진법과 4진법에서는 모든 양의 정수가 행복한 수다. 5000 아래를 모두 돌려 확인했다. 3진법에서는 그렇지 않다. 진법이 바뀌면 고리 구조가 통째로 바뀌니, 역시 일반적인 고리 찾기를 쓴다.

### 고리가 시작되는 숫자까지 구하라면

플로이드에서 두 포인터가 만난 뒤 한 포인터를 처음 수로 되돌리고, 둘을 한 걸음씩 움직이면 고리의 입구에서 만난다. 2의 경우 입구는 4다. 이 방법이 왜 맞는지는 [Linked List Cycle](/posts/leetcode-linked-list-cycle)에서 거리 계산으로 다뤘다. 연결 리스트의 142. Linked List Cycle II가 바로 이 문제다.

- 287. Find the Duplicate Number는 배열의 값을 "다음 인덱스"로 보면 고리가 생기고, 고리의 입구가 중복된 수다. 이 글처럼 리스트가 없는데 리스트로 보는 문제다.

## 면접에서 나올 만한 질문

### 이 과정이 반드시 끝나거나 반복된다는 걸 어떻게 아나요?

d자리 수의 다음 값은 많아야 81d인데, d가 4 이상이면 81d가 그 자릿수의 가장 작은 수보다 작아서 숫자가 반드시 줄어든다. 그래서 어떤 수든 999 이하로 내려오고, 그 뒤로는 243 이하에 머문다. 유한한 범위 안에서 같은 규칙으로 계속 움직이면 이미 본 숫자를 다시 만나니, 1에 머물거나 다른 고리를 도는 것 둘 중 하나다.

### 집합을 쓰는 풀이의 복잡도는요?

걸음 수가 숫자 범위로 묶여 있어서 O(log n)으로 본다. 첫 걸음에 자릿수만큼 계산하고, 그 뒤로는 243 이하의 수라 걸음마다 상수 시간이다. 집합에 들어가는 숫자도 같은 수만큼이라 공간도 O(log n)이고, 실제로는 몇십 개다.

### 추가 메모리 없이 풀 수 있나요?

플로이드의 고리 찾기를 쓴다. 숫자의 흐름을 "다음 숫자"를 포인터로 하는 연결 리스트로 보고, 한 걸음씩 가는 포인터와 두 걸음씩 가는 포인터를 움직인다. 빠른 포인터가 1에 닿으면 행복한 수고, 두 포인터가 1이 아닌 곳에서 만나면 고리다. 공간 O(1)이고, 대신 다음 숫자 계산을 세 배쯤 더 한다.

### 두 포인터가 고리 안에서 서로를 건너뛰지는 않나요?

건너뛰지 않는다. 고리 안에서 빠른 포인터가 느린 포인터보다 k칸 뒤에 있으면 한 번 움직일 때마다 간격이 정확히 1씩 줄어서 언젠가 0이 된다. 그래서 고리 길이가 L이면 둘 다 고리에 들어온 뒤 L번 안에 만난다. 빠른 포인터가 세 걸음씩 가면 간격이 2씩 줄어 건너뛸 수 있으니, 두 걸음이 기본이다.

### "4가 나오면 false"는 왜 맞나요?

십진수 자릿수 제곱합이 만드는 고리가 1과 4, 16, 37, 58, 89, 145, 42, 20으로 이루어진 고리 둘뿐이기 때문이다. 999 이하를 모두 계산해 보면 확인되고, 더 큰 수는 999 이하로 내려오니 모든 수에 성립한다. 가장 빠르지만 수학적 사실에 기대는 코드라 규칙이 세제곱이나 다른 진법으로 바뀌면 틀린다.

### 1만 확인하는 while 반복은 어떤 입력에서 깨지나요?

행복하지 않은 수에서 무한 반복에 빠진다. 2를 넣으면 4에서 시작하는 고리를 영원히 돈다. 행복한 수로만 테스트하면 통과해서 놓치기 쉽고, 채점에서는 시간 초과로 나타난다.

### 실무에서 이런 고리 찾기를 어디에 쓰나요?

상태가 함수 하나로 다음 상태를 정하는 과정이면 어디든 쓴다. 리다이렉트 체인이 서로를 가리키는지, 설정 파일의 include가 순환하는지, 의사 난수 생성기의 주기가 얼마인지 같은 것들이다. 상태를 모두 저장할 수 있으면 집합이 단순하고, 상태가 크거나 저장이 비싸면 플로이드나 브렌트를 쓴다.

### 해시 집합 대신 배열을 써도 되나요?

된다. 첫 걸음 뒤의 숫자는 문제 범위에서 810 이하라서, 크기 811짜리 불리언 배열로 "본 숫자"를 표시할 수 있다. 처음 `n`만 따로 다루면 된다. 해싱 비용이 없어 조금 빠르고 공간도 상수지만, 그 상수가 입력 범위에서 나온 값이라는 걸 설명해야 한다.

### 브렌트의 방법은 플로이드보다 무엇이 나은가요?

다음 상태 계산을 덜 한다. 플로이드는 한 번 움직일 때 느린 쪽 한 번, 빠른 쪽 두 번 해서 세 번 계산하지만, 브렌트는 거북이를 순간 이동시키고 토끼만 한 걸음씩 가서 걸음당 한 번이다. 고리 길이도 함께 나온다. 다음 상태 계산이 비싼 문제(예: 해시 함수의 주기 찾기)에서 차이가 커진다.
