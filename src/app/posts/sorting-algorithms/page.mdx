  면접 준비로 교과서대로 퀵 정렬을 짰더니 무작위 숫자는 잘 되는데, 이미 순서대로 놓인 배열을 넣자 프로그램이 죽었다. 첫 칸을 기준값으로 삼는 방식이라 매번 가장 작은 값이 기준이 되고, 그러면 한쪽에만 나머지가 전부 몰려 수천 단계를 파고들기 때문이다. 같은 알고리즘이 입력 모양 하나로 빠른 정렬에서 느린 정렬로 바뀐다.

  정렬 알고리즘은 결국 값을 얼마나 멀리, 몇 번 옮기느냐의 차이다. 옆자리끼리만 바꾸는 방법은 느리지만 거의 정렬된 입력에서는 빠르고, 반으로 쪼개 합치는 방법은 늘 같은 시간을 보장하는 대신 메모리를 더 쓰고, 기준값으로 가르는 방법은 평균이 가장 빠르지만 기준값을 잘못 고르면 무너진다. 값의 범위가 좁은 정수라면 비교 없이 개수만 세서 더 빠르게 끝낼 수도 있다.

  실제로 직접 정렬을 짤 일은 드물고, 대신 같은 값끼리 원래 순서를 지키는지와 내가 넘기는 비교 함수가 제대로 짜였는지가 더 자주 문제가 된다.

면접 준비를 하면서 퀵 정렬을 직접 짰다. 교과서처럼 첫 원소를 기준값으로 잡고, 작은 값은 앞으로 모은 뒤 양쪽을 재귀로 정렬한다.

```js
function quickSort(arr, lo = 0, hi = arr.length - 1) {
  if (lo >= hi) return arr;
  const pivot = arr[lo]; // 첫 원소를 기준값으로
  let i = lo + 1;
  for (let j = lo + 1; j <= hi; j++) {
    if (arr[j] < pivot) { [arr[i], arr[j]] = [arr[j], arr[i]]; i++; }
  }
  [arr[lo], arr[i - 1]] = [arr[i - 1], arr[lo]];
  quickSort(arr, lo, i - 2);
  quickSort(arr, i, hi);
  return arr;
}
```

무작위 숫자로 돌리면 잘 된다. 그런데 DB에서 id 순으로 받아 온 배열, 즉 이미 정렬된 배열을 넣으면 이야기가 달라진다. Node 22에서 돌린 결과다.

```text

sorted 10000       RangeError: Maximum call stack size exceeded
random 100000      11.1ms
sorted 100000      RangeError: Maximum call stack size exceeded
```

1만 개짜리 정렬된 배열에서 스택이 넘쳤다. 5,000개로 줄여 재귀 깊이를 세 보면 원인이 바로 보인다.

```text
random 5000     6.5ms max depth 25
sorted 5000    19.6ms max depth 4999
```

무작위 입력은 깊이 25에서 끝나는데, 정렬된 입력은 4,999단계까지 내려갔다. 기준값이 매번 가장 작은 값이라 한쪽은 비고 다른 쪽에 n − 1개가 몰리기 때문이다. 같은 알고리즘이 입력 모양 하나로 O(n log n)에서 O(n²)으로 바뀐다.

이 글은 이런 차이가 어디서 오는지 보면서 정렬 알고리즘 여섯 가지(버블, 삽입, 병합, 퀵, 힙, 계수)를 직접 짜고 잰다. 그 위에서 안정성, 자바스크립트 `sort`가 쓰는 TimSort, 비교 함수 때문에 생기는 문제까지 따라간다. 복잡도 표기 자체는 [Big O 글](/posts/big-o-notation)에서, `sort`가 원본을 바꾸는 문제와 기본 문자열 비교는 [배열 메서드 글](/posts/js-array-mutation)에서 다뤘으니 여기서는 링크만 건다. 실행 결과는 모두 Node.js 22(V8)에서 직접 돌린 값이다.

## 정렬을 고를 때 묻는 것들

정렬 알고리즘의 차이는 결국 몇 가지 질문으로 갈린다. 평균과 최악에 얼마나 걸리나. 배열 말고 메모리를 얼마나 더 쓰나. 같은 값끼리 원래 순서를 지키나(안정성). 이미 거의 정렬된 입력에서 빨라지나(적응성).

| 알고리즘 | 평균 | 최악 | 추가 메모리 | 안정 | 거의 정렬된 입력 |
|---|---|---|---|---|---|
| 버블 | O(n²) | O(n²) | O(1) | 예 | 빨라진다 (조기 종료 시 O(n)) |
| 삽입 | O(n²) | O(n²) | O(1) | 예 | O(n)에 가깝다 |
| 병합 | O(n log n) | O(n log n) | O(n) | 예 | 변화 없음 |
| 퀵 | O(n log n) | O(n²) | O(log n) 스택 | 아니오 | 기준값 고르기에 달렸다 |
| 힙 | O(n log n) | O(n log n) | O(1) | 아니오 | 변화 없음 |
| 계수 | O(n + k) | O(n + k) | O(k) | 구현에 따라 | 변화 없음 |

표만 외우면 면접 첫 질문은 넘기지만 꼬리 질문에서 막힌다. "왜 퀵 정렬이 최악인데도 많이 쓰이나", "왜 자바스크립트는 퀵 정렬을 버렸나" 같은 질문은 각 알고리즘이 실제로 무엇을 옮기는지 봐야 답할 수 있다. 하나씩 움직여 본다.

```js
function bubbleSort(a) {
  for (let end = a.length - 1; end > 0; end--) {
    let swapped = false;
    for (let i = 0; i < end; i++) {
      if (a[i] > a[i + 1]) { [a[i], a[i + 1]] = [a[i + 1], a[i]]; swapped = true; }
    }
    if (!swapped) break; // 한 바퀴 동안 안 바꿨으면 이미 정렬됐다
  }
  return a;
}
```

바퀴마다 한 칸씩 덜 보니 비교는 (n − 1) + (n − 2) + … + 1 = n(n − 1)/2번이다. `swapped` 플래그가 없으면 정렬된 입력에서도 이 횟수를 다 채운다. 플래그를 두면 첫 바퀴에서 끝나 O(n)이다. 면접에서 "버블 정렬의 최선은 O(n)인가"를 물으면 이 플래그가 있을 때만 그렇다고 답한다.

실무에서 버블 정렬을 쓸 일은 없다. 값을 한 번에 한 칸씩만 옮기니 멀리 있는 값이 제자리를 찾는 데 오래 걸린다. 다음 절의 삽입 정렬도 O(n²)이지만 같은 크기에서 서너 배 빠르다.

```js
function insertionSort(a) {
  for (let i = 1; i < a.length; i++) {
    const x = a[i];
    let j = i - 1;
    while (j >= 0 && a[j] > x) { a[j + 1] = a[j]; j--; } // 큰 값을 한 칸씩 민다
    a[j + 1] = x;
  }
  return a;
}
```

미는 횟수는 입력에서 순서가 뒤바뀐 쌍(inversion)의 수와 같다. 무작위 입력이면 쌍의 절반쯤이 뒤바뀌어 O(n²)이지만, 거의 정렬된 입력이면 미는 일이 거의 없다. 10만 개를 두 경우로 돌려 봤다. 거의 정렬된 쪽은 100군데만 가까운 칸끼리 바꿔 둔 배열이다.

```text
insertion nearly sorted 1e5 3.7ms
insertion random 1e5 2831.6ms
```

같은 알고리즘이 700배 넘게 차이 난다. 이 성질 때문에 삽입 정렬은 죽지 않았다. 원소가 수십 개 이하면 함수 호출도 추가 메모리도 없는 삽입 정렬이 병합 정렬보다 빠르다. 그래서 TimSort를 포함해 실제로 쓰이는 정렬은 짧은 구간을 삽입 정렬로 처리한다. 뒤에서 다시 만난다.

## 반으로 쪼개고 줄 세워 합치는 병합 정렬

병합 정렬은 배열을 반으로 나누고, 각각을 정렬한 뒤, 정렬된 두 줄을 하나로 합친다. 나누기는 길이가 1이 될 때까지 재귀로 내려간다. 길이 1은 그 자체로 정렬돼 있으니, 일은 전부 합치는 단계에서 한다.

합치기는 두 줄의 맨 앞만 비교하면 된다. 각 줄이 이미 정렬돼 있으니 두 머리 중 작은 쪽이 전체에서 다음으로 작은 값이다.

```js
function mergeSort(a) {
  const buf = new Array(a.length);
  (function sort(lo, hi) {
    if (hi <= lo) return;
    const mid = (lo + hi) >> 1;
    sort(lo, mid);
    sort(mid + 1, hi);
    let i = lo, j = mid + 1, k = lo;
    // <= 라서 같은 값이면 앞쪽(원래 앞에 있던 것)을 먼저 꺼낸다 → 안정 정렬
    while (i <= mid && j <= hi) buf[k++] = a[i] <= a[j] ? a[i++] : a[j++];
    while (i <= mid) buf[k++] = a[i++];
    while (j <= hi) buf[k++] = a[j++];
    for (k = lo; k <= hi; k++) a[k] = buf[k];
  })(0, a.length - 1);
  return a;
}
```

반으로 나누니 층이 log₂ n개 생기고, 층마다 전체 n개를 한 번씩 합치니 O(n log n)이다. 입력 모양과 상관없이 늘 이만큼 걸린다. 최악이 없다는 게 병합 정렬의 장점이고, 결과 버퍼로 O(n) 메모리를 더 쓴다는 게 단점이다.

비교 조건의 `<=` 하나가 안정성을 결정한다. `<`로 쓰면 같은 값일 때 뒤쪽을 먼저 꺼내서 원래 순서가 뒤집힌다. 동작은 맞는데 안정성만 조용히 깨지는 실수라 테스트로 잡아야 한다(이 글 끝의 연습 문제가 그 테스트다).

합치기는 앞에서부터 차례로 읽고 쓰기만 하니 디스크나 네트워크에서도 쓸 수 있다. 메모리에 다 안 들어가는 큰 파일은 조각마다 정렬해서 파일로 쓰고, 그 파일들의 머리를 힙에 넣어 하나씩 꺼내며 합친다(외부 정렬). k개 줄을 힙으로 합치는 방법은 [힙 글](/posts/ds-heap)에 있다. DB가 `ORDER BY`를 하다 `work_mem`을 넘기면 디스크에 임시 파일을 쓰는 것도 같은 방식이다.

### 기준값을 잘 고르는 법

최악을 피하는 방법은 기준값 고르기에 달렸다. 무작위로 고르면 특정 입력이 늘 최악이 되는 일은 없어진다. 처음 코드에서 기준값만 바꿔 5,000개로 다시 쟀다.

```text
first pivot   sorted       59.6ms depth 4999
first pivot   all equal    25.8ms depth 4999
random pivot  sorted        9.8ms depth 28
random pivot  all equal    29.1ms depth 4999
```

정렬된 입력은 무작위 기준값으로 깊이가 28로 줄었다. 그런데 모든 값이 같은 배열은 무작위로 골라도 여전히 4,999단계다. 처음 코드는 `arr[j] < pivot`인 것만 앞으로 보내서, 기준값과 같은 값이 전부 한쪽에 몰리기 때문이다. 상태값, 점수, 날짜처럼 중복이 많은 데이터에서 실제로 일어난다.

고치는 방법은 두 가지다. 양 끝에서 포인터 두 개가 다가오며 같은 값도 양쪽으로 나눠 보내는 호어(Hoare) 분할을 쓰거나, 작은 값·같은 값·큰 값 세 구역으로 나누는 3-way 분할을 쓴다. 앞 측정의 `quickSort`는 무작위 기준값에 호어 분할을 쓴 버전이고, 같은 값 100만 개를 68.8ms에 정렬했다.

스택 깊이도 막아야 한다. 두 쪽 중 작은 쪽만 재귀로 부르고 큰 쪽은 반복문으로 돌리면, 작은 쪽은 많아야 절반이라 깊이가 log n을 넘지 않는다.

```js
function quickSort(a, lo = 0, hi = a.length - 1) {
  while (lo < hi) {
    const pivot = a[lo + Math.floor(Math.random() * (hi - lo + 1))];
    let i = lo, j = hi;
    while (i <= j) { // 호어 분할: 같은 값도 양쪽으로 갈라진다
      while (a[i] < pivot) i++;
      while (a[j] > pivot) j--;
      if (i <= j) { [a[i], a[j]] = [a[j], a[i]]; i++; j--; }
    }
    if (j - lo < hi - i) { quickSort(a, lo, j); lo = i; } // 작은 쪽만 재귀
    else { quickSort(a, i, hi); hi = j; }
  }
  return a;
}
```

재귀 깊이와 콜 스택이 왜 넘치는지는 [실행 컨텍스트와 콜 스택 글](/posts/js-execution-context)에서 자세히 다룬다.

## 힙 정렬과 인트로 정렬

힙 정렬은 배열을 최대 힙으로 만든 뒤 루트(가장 큰 값)를 하나씩 뒤로 보내는 방식이다. 추가 메모리 없이 최악도 O(n log n)이라 이론상으로는 완벽해 보인다. 실제로는 위 측정처럼 퀵 정렬보다 느리다. 부모와 자식 인덱스가 2배씩 떨어져 있어 캐시를 덜 타고, 같은 값의 순서도 지키지 않는다. 힙의 올리기·내리기와 O(n) heapify는 [힙 글](/posts/ds-heap)에서 다뤘다.

그래서 힙 정렬은 혼자보다는 안전장치로 쓰인다. 퀵 정렬로 시작하다가 재귀가 2 log n쯤보다 깊어지면 운이 나쁜 입력으로 보고 힙 정렬로 갈아타고, 짧은 구간은 삽입 정렬로 마무리하는 방식을 인트로 정렬(introsort)이라고 한다. C++ `std::sort`의 주요 구현(libstdc++ 등)이 이 방식을 쓴다. 평균은 퀵 정렬만큼 빠르고 최악은 힙 정렬이 막는다.

## 비교를 안 하면 n log n보다 빨라진다

비교만으로 정렬하면 최악에 n log n번보다 적게 비교할 수 없다. [Big O 글](/posts/big-o-notation)에서 본 대로 n개의 순서는 n!가지이고, 비교 한 번으로는 가능성을 절반밖에 못 줄이기 때문이다.

## 같은 값의 순서를 지키는 안정 정렬

안정 정렬은 비교 결과가 같은 원소끼리 원래 순서를 지킨다. 이게 왜 필요한지는 두 번 정렬해 보면 보인다. 주문을 시각순으로 받아 둔 상태에서 상태별로 다시 정렬한다. `p`는 paid, `s`는 shipped다.

```js
const byStatus = (a, b) => a.status.localeCompare(b.status);
console.log("Array.sort  ", show(orders.slice().sort(byStatus)));
console.log("heapSort    ", show(heapSortBy(orders.slice(), byStatus)));
```

```text
Array.sort   p1@09:00 p3@09:10 p5@09:20 s2@09:05 s4@09:15 s6@09:25
heapSort     p3@09:10 p5@09:20 p1@09:00 s6@09:25 s4@09:15 s2@09:05
```

내장 `sort`는 같은 상태 안에서 시각순이 그대로다. 힙 정렬은 상태별로는 맞게 나눴지만 시각순이 섞였다. 화면에서 "상태 → 시각" 순으로 보여 주려던 목록이 새로고침할 때마다 다르게 보일 수 있다. 표의 열 머리를 차례로 눌러 여러 기준으로 정렬하는 UI는 안정 정렬을 전제로 한다.

자바스크립트 `sort`의 안정성은 ES2019에서 명세로 정해졌다. 그 전 V8은 길이에 따라 불안정했다. 이 역사와 문자열 기본 비교는 [배열 메서드 글](/posts/js-array-mutation)에 있다. 안정성에 기대기 싫거나 불안정한 정렬을 써야 한다면, 동점일 때 볼 기준을 비교 함수에 직접 넣는다. 아래 그림에서 조각을 눌러 보자.

## V8의 sort는 TimSort다

V8은 7.0(크롬 70, 2018년)부터 `Array.prototype.sort`를 TimSort로 바꿨다. 그 전에는 짧은 배열은 삽입 정렬, 긴 배열은 퀵 정렬이었다. TimSort는 2002년 팀 피터스가 파이썬을 위해 만든 알고리즘으로, 자바도 객체 배열 정렬에 쓴다. 바꾼 이유는 두 가지였다. 안정 정렬이 필요했고, 실제 데이터는 무작위가 아니라 이미 정렬된 덩어리를 많이 품고 있다.

TimSort는 먼저 배열을 앞에서부터 훑으며 이미 정렬된 구간(run)을 찾는다. 오름차순이면 그대로, 엄격하게 내림차순이면 뒤집어서 오름차순 run으로 만든다. 너무 짧은 run은 이진 삽입 정렬로 최소 길이(32~64 사이)까지 늘린다. 그다음 run들을 스택에 쌓으면서 길이가 비슷한 것끼리 병합한다.

무작위 숫자에서는 오히려 직접 짠 퀵 정렬이 빨랐다. 내장 `sort`는 원소마다 자바스크립트 비교 함수를 불러야 하고, 배열에 아무 값이나 들어올 수 있어서 이것저것 확인한다. 숫자만 정렬한다면 타입 배열이 답이다. 타입 배열의 `sort`는 비교 함수 없이 숫자 순서로 정렬한다.

```text
Array.sort((a,b)=>a-b)   569.6ms
Float64Array.sort()      128.7ms
```

100만 개에서 4배 넘게 차이 난다. 그리고 570ms는 그동안 메인 스레드가 다른 일을 전혀 못 한다는 뜻이다. 서버라면 그동안 들어온 요청이 전부 기다리고, 브라우저라면 클릭에 반응하지 않는다. 큰 정렬은 DB의 인덱스에 맡기거나(`ORDER BY` 컬럼에 인덱스가 있으면 정렬 없이 순서대로 읽는다, [인덱스 글](/posts/db-index) 참고), 워커 스레드로 넘기거나, 애초에 필요한 만큼만 가져온다. 메인 스레드가 막히는 구조는 [이벤트 루프 글](/posts/event-loop)에서 다룬다.

## 비교 함수 하나가 정렬을 망친다

내장 `sort`를 쓰면 알고리즘은 신경 쓸 일이 없지만 비교 함수는 내가 짠다. 참거짓을 돌려주는 실수는 [배열 메서드 글](/posts/js-array-mutation)에서 다뤘으니, 여기서는 그 밖의 세 가지를 본다.

첫째, 비교 함수가 일관되지 않으면 결과도 정해지지 않는다. 명세는 비교 함수가 `a < b`이고 `b < c`면 `a < c` 같은 일관성을 지킬 때만 결과를 보장하고, 어기면 구현이 정한 순서가 나온다고만 말한다. `NaN`이 섞인 숫자 배열이 흔한 예다. `NaN`과의 뺄셈은 늘 `NaN`이고, 정렬기는 이걸 0(같음)으로 다룬다.

```js
console.log([3, NaN, 1, 2].sort((a, b) => a - b));
console.log([3, 1, NaN, 2, 0].sort((a, b) => a - b));
```

```text
[ 3, NaN, 1, 2 ]
[ 0, 1, 2, 3, NaN ]
```

첫 줄은 하나도 정렬되지 않았다. `NaN`이 "3과도 같고 1과도 같은" 값이 되면서, 3과 1의 관계를 정렬기가 알 수 없게 됐다. 둘째 줄은 우연히 맞아 보인다. 입력 모양에 따라 결과가 달라지니 테스트를 통과하고 운영에서 깨진다. 정렬하기 전에 `NaN`과 `undefined`를 걸러 내거나 끝으로 보내는 규칙을 비교 함수에 명시한다.

둘째, `sort(() => Math.random() - 0.5)`로 섞으면 고르게 섞이지 않는다. `["a", "b", "c"]`를 60만 번 섞어 순열별로 세 봤다. 고르게 섞였다면 각각 10만 번 근처여야 한다.

```text
sort(random)   abc 224887  acb 37554  bac 75018  bca 37206  cab 37517  cba 187818
Fisher-Yates   abc 100107  acb 99907  bac 99662  bca 99804  cab 100356  cba 100164
```

원래 순서 `abc`가 22만 번, 뒤집힌 `cba`가 19만 번으로 몰렸다. 무작위 비교 함수는 일관성 조건을 정면으로 어기고, 정렬기는 원소마다 비교 횟수가 달라 특정 순서가 더 자주 나온다. 섞기는 뒤에서부터 무작위 칸과 바꾸는 피셔-예이츠(Fisher-Yates)로 한다. O(n)이고 모든 순열이 같은 확률이다.

셋째, 비교 함수는 생각보다 훨씬 많이 불린다. 무작위 10만 개에서 152만 번이었다. 비교 함수 안에서 무거운 일을 하면 그만큼 곱해진다. 주문 10만 건을 이름과 시각으로 정렬하며 쟀다.

```text
comparator calls 1528911
localeCompare(b,'ko')     458.8ms
Intl.Collator.compare     217.9ms
Date.parse in comparator  777.4ms
key precomputed (map)     81.9ms
ISO string compare        62.3ms
```

`localeCompare`에 로캘을 넘기면 호출마다 로캘 인자를 처리하는 비용이 붙는다. `Intl.Collator`를 한 번 만들어 두고 `compare`를 쓰면 절반이 됐다. 날짜 문자열을 비교 함수 안에서 `Date.parse`하면 호출마다 두 번씩, 300만 번 넘게 파싱하는 셈이라 777ms가 걸렸다. 정렬 전에 키를 한 번씩만 계산해 두면(10만 번) 82ms다. 같은 형식의 UTC ISO 8601 문자열이라면 글자 순서가 곧 시간 순서라 파싱 없이 문자열 비교로도 된다. 시간대 표기가 섞여 있으면 이 방법은 틀린다.

React 컴포넌트에서 목록을 정렬할 때도 같은 원칙이다. 렌더링마다 정렬하지 말고, 키 계산과 정렬을 `useMemo`로 묶어 목록이 바뀔 때만 다시 한다. props 배열을 `sort`로 직접 정렬하면 부모의 배열까지 바뀌니 `toSorted`를 쓴다(역시 [배열 메서드 글](/posts/js-array-mutation)에 있다).

## 정렬 문제를 만났을 때 확인하는 순서

정렬이 느리거나 결과가 이상할 때 실제로 보는 순서를 정리하면 이렇다.

1. 정렬 결과가 매번 다르면 비교 함수가 동점을 어떻게 다루는지 본다. 고유 키를 마지막 기준으로 넣었는지, `NaN`·`null`이 섞이지 않았는지 확인한다.
2. 느리면 먼저 n이 얼마인지, 정렬을 몇 번 하는지 센다. 반복문 안의 정렬, 렌더링마다 하는 정렬이 가장 흔하다.
3. 비교 함수 호출 횟수를 세고(위처럼 카운터 하나면 된다), 그 안에서 파싱이나 객체 생성을 하지 않는지 본다.
4. 숫자만 정렬한다면 타입 배열을, 범위가 좁은 정수라면 계수 정렬을 검토한다.
5. 수십만 개 이상을 매번 정렬한다면 정렬된 상태로 유지하는 구조(힙, 정렬된 인덱스)로 바꾸거나 DB에 맡긴다.

직접 짠 정렬 알고리즘을 운영 코드에 넣을 일은 거의 없다. 그래도 알고리즘을 알아야 내장 정렬이 언제 빠르고 언제 느린지, 비교 함수가 왜 그렇게 중요한지 설명할 수 있다.

## 직접 짜 보는 안정 정렬

## 정렬을 고르는 감각

여섯 가지 알고리즘은 결국 무엇을 얼마나 멀리 옮기느냐의 차이다. 버블과 삽입은 한 칸씩 옮겨서 느리지만 거의 정렬된 입력에 강하고, 병합은 늘 n log n을 보장하는 대신 버퍼를 쓰고, 퀵은 평균이 가장 빠르지만 기준값이 나쁘면 무너지고, 힙은 최악을 막는 안전장치로 남았다. 비교를 버리면 계수 정렬처럼 n log n 아래로도 간다. 내장 `sort`는 이 중 병합과 삽입을 섞어 실제 데이터의 정렬된 덩어리를 활용하는 TimSort다. 정렬된 배열을 얻고 나면 그 위에서 할 수 있는 일이 크게 늘어나는데, 그 대표가 다음 글의 [이분 탐색](/posts/binary-search)이다.

## 면접에서 나올 만한 질문

### 퀵 정렬의 최악은 언제 생기고 어떻게 피하나요?

기준값이 매번 최솟값이나 최댓값이어서 분할이 한쪽으로 몰릴 때 O(n²)이 된다. 첫 원소를 기준값으로 쓰면 이미 정렬된 입력에서 그렇게 되고, 재귀 깊이가 n이라 스택도 넘친다. 무작위나 세 값의 중앙값으로 기준값을 고르고, 작은 쪽만 재귀로 불러 깊이를 log n으로 묶는다. 실무 구현은 깊이가 너무 깊어지면 힙 정렬로 넘어가는 인트로 정렬로 최악을 막는다.

### 중복 값이 많으면 퀵 정렬에 무슨 일이 생기나요?

작은 값만 앞으로 보내는 로무토 분할은 기준값과 같은 값이 전부 한쪽으로 몰려서, 무작위 기준값을 써도 O(n²)이 된다. 같은 값 5,000개에서 깊이가 4,999였다. 같은 값을 양쪽으로 나눠 보내는 호어 분할이나, 같은 값 구역을 따로 두는 3-way 분할로 고친다. 3-way 분할은 같은 값 구역을 다시 정렬하지 않아서 중복이 많을수록 빨라진다.

### 안정 정렬이 무엇이고 언제 필요한가요?

비교 결과가 같은 원소끼리 원래 순서를 지키는 정렬이다. 시각순으로 받은 주문을 상태별로 다시 정렬할 때, 같은 상태 안의 시각순이 유지되려면 안정 정렬이어야 한다. 병합 정렬과 삽입 정렬, TimSort는 안정적이고 퀵 정렬과 힙 정렬은 아니다. 안정성에 기대지 않으려면 비교 함수 끝에 고유 키를 넣어 동점을 없앤다.

### 병합 정렬과 퀵 정렬은 어떻게 고르나요?

최악을 보장해야 하거나 안정성이 필요하거나 연결 리스트·외부 파일처럼 순서대로만 읽을 수 있으면 병합 정렬이다. 메모리를 더 쓰기 어렵고 평균 속도가 중요하면 퀵 정렬이다. 퀵 정렬은 제자리에서 바꾸고 캐시를 잘 타서 같은 크기에서 보통 더 빠르다. 실측에서도 100만 개 기준 퀵 112ms, 병합 223ms였다.

### 비교 정렬은 왜 O(n log n)보다 빨라질 수 없고, 계수 정렬은 어떻게 그보다 빠른가요?

n개의 가능한 순서는 n!가지이고 비교 한 번은 가능성을 많아야 절반으로 줄이니, 최악에 log₂(n!) ≈ n log₂ n번은 비교해야 한다. 계수 정렬은 비교를 하지 않고 값 자체를 개수 배열의 인덱스로 써서 O(n + k)에 끝낸다. 대신 값의 범위 k가 좁은 정수여야 하고 그만큼 메모리를 쓴다. 범위가 넓으면 자릿수별로 나눈 기수 정렬을 쓴다.

### 자바스크립트의 sort는 어떤 알고리즘이고 왜 그걸 쓰나요?

V8은 7.0(크롬 70)부터 TimSort를 쓴다. 이미 정렬된 구간(run)을 찾아 짧은 것은 이진 삽입 정렬로 늘리고, run끼리 병합한다. 안정 정렬이 필요했고, 실제 데이터에는 정렬된 덩어리가 많아서다. 10만 개 측정에서 정렬된 입력은 비교가 n − 1번으로 끝났고 무작위보다 25배 빨랐다.

### sort(() => Math.random() - 0.5)로 섞으면 안 되는 이유는 무엇인가요?

비교 함수가 일관성 조건을 어겨서 결과가 정렬 구현에 따라 달라지고, 순열이 고르게 나오지 않기 때문이다. 세 원소를 60만 번 섞었더니 원래 순서가 22만 번, 다른 순열은 4만 번 안팎이었다. 피셔-예이츠 셔플을 쓰면 O(n)에 모든 순열이 같은 확률로 나온다.

### 정렬이 느리다는 제보를 받으면 무엇부터 보나요?

정렬을 몇 번, 몇 개로 하는지부터 본다. 반복문이나 렌더링마다 다시 정렬하는 경우가 가장 흔하다. 다음으로 비교 함수가 몇 번 불리는지 세고, 그 안에서 날짜 파싱이나 로캘 비교 준비 같은 무거운 일을 하는지 본다. 키를 미리 계산하거나 `Intl.Collator`를 재사용하고, 숫자라면 타입 배열을 쓰고, 큰 데이터는 DB 인덱스나 워커로 넘긴다.
