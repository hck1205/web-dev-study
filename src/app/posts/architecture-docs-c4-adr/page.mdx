<EasyIntro>
  새로 들어온 팀에서 주문 서버와 결제 서버 사이에 메시지 큐가 하나 끼어 있는 걸 봤다. 왜 그냥 직접 부르지 않는지 물었더니, 그걸 정한 사람은 이미 회사를 떠났고 아무도 이유를 모른다고 했다. 이 글은 이런 일을 막는 두 가지 습관을 다룬다. 지도 앱을 떠올리면 쉽다. 나라 전체를 보는 지도, 도시를 보는 지도, 동네 골목을 보는 지도가 따로 있고, 필요한 만큼 확대해서 본다. 시스템 그림도 이렇게 확대 단계를 나눠 그리면 처음 온 사람도 큰 그림부터 차례로 이해할 수 있다. 그리고 중요한 결정을 내릴 때마다 무엇을 고민했고 무엇을 골랐고 그 대가가 무엇인지 짧은 기록으로 남긴다. 이 기록은 고치지 않고 차곡차곡 쌓아서, 몇 년 뒤에도 왜 이렇게 만들었는지 읽을 수 있게 한다.
</EasyIntro>

입사 첫 주에 주문 서비스 코드를 보다가 이상한 걸 찾았다. 주문 API가 결제 완료를 알릴 때 결제 서비스를 HTTP로 직접 부르지 않고, Kafka 토픽에 메시지를 쓰고, 결제 서비스가 그걸 읽는다. 트래픽이 그렇게 많은 서비스도 아니다. 왜 이렇게 했냐고 물었더니 돌아온 답은 "그거 정한 분이 작년에 나가셨어요"였다.

그 큐를 걷어 내도 되는 걸까. 걷어 냈더니 결제사 장애 때 주문이 같이 멈추는 문제가 다시 생긴다면? 반대로 그때의 이유가 지금은 사라졌다면? 코드는 무엇을 하는지 말해 주지만 왜 그렇게 했는지는 말해 주지 않는다.

이 글은 그 빈칸을 채우는 두 가지 도구를 다룬다. 시스템을 확대 단계별로 그리는 C4 모델, 그리고 결정을 하나씩 남기는 ADR(Architecture Decision Record)이다. 둘 다 무겁지 않게 시작할 수 있고, 저장소 안에서 코드와 함께 관리할 수 있다.

## 그림 한 장에 다 넣으면 아무도 못 읽는다

팀 위키에 "시스템 구성도"라는 그림이 하나 있다고 하자. 고객, 웹 앱, API 서버 다섯 개, DB 세 개, Redis, Kafka, 결제사, 문자 발송 업체, 그리고 API 서버 안의 주요 클래스까지 한 장에 들어 있다. 화살표는 마흔 개쯤 되고 대부분 라벨이 없다. 그린 사람은 다 알아보지만, 처음 보는 사람은 어디서부터 읽어야 할지 모른다.

문제는 서로 다른 질문의 답이 한 그림에 섞여 있다는 것이다. 기획자는 "우리 시스템이 바깥의 누구와 이야기하나"를 알고 싶고, 신규 개발자는 "배포되는 덩어리가 몇 개고 무엇으로 통신하나"를 알고 싶고, 특정 기능을 고칠 사람은 "이 서버 안이 어떻게 나뉘어 있나"를 알고 싶다.

사이먼 브라운(Simon Brown)이 만든 C4 모델은 이 질문들을 확대 단계로 나눈다. 지도 앱에서 나라, 도시, 동네, 건물로 확대하듯이 시스템도 네 단계로 확대해 그린다. 단계 이름의 첫 글자가 모두 C라서 C4다.

## 확대 단계 네 개

1단계 시스템 컨텍스트(System Context)는 가장 멀리서 본 그림이다. 우리 시스템을 상자 하나로 두고, 그 시스템을 쓰는 사람과 연동하는 바깥 시스템만 그린다. 기술 용어가 거의 없어서 개발자가 아닌 사람도 읽는다.

아래가 쇼핑몰의 컨텍스트 그림이다. 화살표를 따라 흐르는 점이 요청의 방향이다.

이 그림만 있어도 처음 장면의 질문 절반은 풀린다. 주문 API와 결제 워커 사이에 토픽이 있다는 사실이 보이고, 신규 개발자는 "왜 여기에 토픽이 있지"라는 질문을 정확하게 던질 수 있다. 그 답은 그림이 아니라 뒤에서 볼 ADR이 맡는다.

3단계 컴포넌트(Component)는 컨테이너 하나를 열어 본 그림이다. 주문 API 안의 주문 접수, 결제 확인, 재고 예약 같은 주요 묶음과 그 사이의 의존을 그린다. 클래스 하나하나가 아니라 인터페이스 뒤에 묶인 기능 단위다. [헥사고날 아키텍처](/posts/hexagonal-architecture)나 [레이어드 아키텍처](/posts/layered-architecture)로 나눈 구조가 이 단계에서 드러난다.

4단계 코드(Code)는 컴포넌트 하나의 클래스 구조다. UML 클래스 다이어그램이나 ER 다이어그램이 여기에 해당한다. 브라운 자신도 이 단계는 꼭 필요할 때만, 가능하면 IDE나 도구로 자동 생성해서 쓰라고 권한다. 코드가 바뀌는 속도를 손으로 그린 그림이 따라가지 못하기 때문이다. 실제로 많은 팀이 1, 2단계만 꾸준히 관리하고 3단계는 복잡한 컨테이너에만 그린다.

## 컨테이너는 도커 컨테이너가 아니다

C4를 처음 쓰는 팀이 가장 많이 헷갈리는 단어가 컨테이너다. C4의 컨테이너는 도커 컨테이너보다 먼저 나온 말로, "코드가 실행되거나 데이터가 저장되는 독립된 단위"라는 뜻이다. 브라우저에서 도는 SPA도, 모바일 앱도, DB 스키마 하나도, S3 버킷도 컨테이너다.

그래서 같은 주문 API를 도커 컨테이너 여섯 개로 띄워도 C4 그림에서는 상자 하나다. 몇 개를 어디에 띄우는지는 별도의 배포 그림(deployment diagram)에서 보여 준다. 반대로 하나의 Kubernetes Pod 안에 앱과 사이드카가 함께 떠 있으면, 그 사이드카가 업무적으로 의미 있는 역할을 할 때만 따로 그린다.

그림을 그릴 때 자주 하는 실수가 몇 가지 더 있다.

- 단계를 섞는다. 컨테이너 그림에 특정 클래스 이름이 튀어나오면 읽는 사람이 확대 수준을 잃는다.
- 화살표에 라벨이 없다. "주문 API → 결제 워커"만으로는 동기 호출인지, 이벤트인지, 무엇을 보내는지 알 수 없다. 동사와 프로토콜을 적는다.
- 양방향 화살표를 쓴다. 요청과 응답을 모두 그리면 화살표가 두 배가 된다. 요청을 시작하는 쪽에서 한 방향으로만 그린다.
- 범례가 없다. 점선이 비동기인지, 계획 중인 구성인지 그린 사람만 안다. 그림마다 제목, 범례, 기준 날짜를 둔다.

C4는 표기법을 강제하지 않는다. 상자 모양과 색은 팀이 정하면 된다. 대신 위 규칙처럼 "그림만 보고 의미를 알 수 있게" 하는 데 집중한다. 네 단계 말고도 시스템 여러 개를 한 장에 놓는 시스템 랜드스케이프(system landscape), 특정 흐름의 호출 순서를 보여 주는 동적 그림(dynamic diagram), 배포 그림을 보조로 둔다.

## 그림을 코드로 그린다

그림을 드로잉 툴로 그리면 원본 파일이 누구 노트북에 있는지 모르게 되고, 바뀐 곳을 리뷰할 수도 없다. 그래서 그림을 텍스트로 쓰고 도구가 그리게 하는 방식(diagrams as code)을 많이 쓴다.

Structurizr DSL은 C4를 만든 브라운이 만든 도구다. 모델(무엇이 있고 무엇이 무엇을 부르나)을 한 번 쓰고, 뷰(어느 단계로 볼까)를 여러 개 뽑는 구조다.

```text
workspace "Shop" {
  model {
    customer = person "고객"
    pg = softwareSystem "결제대행사" "카드 승인"
    shop = softwareSystem "쇼핑몰" {
      web = container "웹 앱" "" "Next.js"
      api = container "주문 API" "" "Spring Boot"
      db = container "주문 DB" "" "PostgreSQL 16" "Database"
      topic = container "order-events" "" "Kafka"
      pay = container "결제 워커" "" "Spring Boot"
    }
    customer -> web "주문한다" "HTTPS"
    web -> api "주문 요청" "JSON/HTTPS"
    api -> db "읽고 쓴다" "JDBC"
    api -> topic "OrderPaid를 쓴다"
    pay -> topic "구독한다"
    pay -> pg "승인을 요청한다" "HTTPS"
  }
  views {
    systemContext shop { include * autolayout lr }
    container shop { include * autolayout lr }
  }
}
```

모델이 하나라서 컨텍스트 그림과 컨테이너 그림이 서로 어긋날 수 없다. `pay -> pg` 관계 하나를 적으면 컨테이너 그림에는 결제 워커에서, 컨텍스트 그림에는 쇼핑몰 전체에서 결제대행사로 가는 화살표가 자동으로 생긴다.

GitHub나 GitLab의 마크다운에 바로 보이는 그림이 필요하면 Mermaid를 쓴다. Mermaid에도 C4 문법이 있는데, 공식 문서에서 아직 실험 기능으로 표시하고 있어서 배치가 마음대로 안 될 때가 있다. 간단한 컨텍스트 그림 정도에 쓰기 좋다.

```text
C4Context
  title 쇼핑몰 시스템 컨텍스트
  Person(customer, "고객", "웹과 앱으로 주문한다")
  System(shop, "쇼핑몰", "주문과 결제를 처리한다")
  System_Ext(pg, "결제대행사", "카드 승인")
  Rel(customer, shop, "주문한다", "HTTPS")
  Rel(shop, pg, "승인을 요청한다", "HTTPS")
```

어느 도구든 핵심 이득은 같다. 그림이 저장소에 텍스트로 있으니 PR에서 바뀐 줄을 리뷰할 수 있고, 코드와 같은 커밋에 묶을 수 있다.

특정 흐름 하나를 따라가는 동적 그림도 같은 모델에서 뽑는다. 결제 완료가 어떤 순서로 퍼지는지 보여 주고 싶으면 `views` 안에 이렇게 더한다.

```text
dynamic shop "payment-flow" "결제 완료가 퍼지는 순서" {
  web -> api "결제 완료 콜백을 넘긴다"
  api -> db "주문 상태와 아웃박스 행을 한 트랜잭션에 쓴다"
  api -> topic "OrderPaid를 쓴다"
  pay -> topic "구독한다"
  pay -> pg "승인을 확인한다"
  autolayout lr
}
```

동적 그림에는 모델에 이미 있는 관계만 쓸 수 있다. 모델에 없는 화살표를 그리려 하면 도구가 오류를 낸다. 덕분에 흐름 그림이 구성 그림과 다른 말을 하는 일이 생기지 않는다.

## 이미 돌아가는 시스템을 처음 그릴 때

문서가 하나도 없는 시스템에 들어갔다면 기억이 아니라 실제로 돌고 있는 것에서 출발한다. 사람에게 물으면 "원래는 이렇게 하려고 했던" 그림이 나오기 쉽다.

컨테이너 목록은 배포 설정에서 뽑는다. Kubernetes를 쓴다면 네임스페이스별 Deployment와 Service 목록이, 그렇지 않다면 CI의 배포 작업 목록이나 클라우드 콘솔의 서비스 목록이 출발점이다. 데이터 저장소는 애플리케이션 설정의 접속 문자열(환경 변수, 시크릿)에서 찾는다. 앱 하나가 DB 둘에 붙어 있는 경우가 생각보다 많다.

화살표는 실제 트래픽에서 찾는다. 분산 추적을 쓰고 있다면 추적 도구의 서비스 맵이 가장 정확하다. 없다면 각 앱의 나가는 HTTP 클라이언트 설정(호출하는 base URL 목록), 메시지 브로커의 토픽별 생산자와 소비자 그룹, 방화벽이나 보안 그룹 규칙에서 누가 누구에게 열려 있는지를 모은다. [분산 추적 글](/posts/distributed-tracing)에서 서비스 맵이 어떻게 만들어지는지 볼 수 있다.

이렇게 모은 것으로 컨테이너 그림을 먼저 그리고, 그 다음에 컨텍스트 그림으로 줄인다. 그린 그림을 팀에 보여 주면 "이 화살표는 작년에 없앴는데 아직 살아 있었어요?" 같은 반응이 꼭 나온다. 그 반응 하나하나가 숨어 있던 결정이고, ADR로 남길 후보다. 이미 지난 결정을 거꾸로 적을 때는 상태 옆에 "사후 기록"이라고 밝히고, 확인하지 못한 이유는 추측이라고 적는다.

## 결정을 한 장씩 남기는 ADR

그림은 지금 무엇이 있는지를 보여 준다. 왜 그렇게 됐는지는 보여 주지 못한다. 마이클 나이가드(Michael Nygard)가 2011년 글에서 제안한 ADR은 그 이유를 결정 하나당 짧은 문서 하나로 남기는 방식이다. 처음 장면의 Kafka 토픽에 ADR이 있었다면 이랬을 것이다.

```markdown
# 7. 결제 완료 알림을 Kafka 토픽으로 보낸다

- 상태: 승인됨 (2025-03-12)
- 결정한 사람: 주문팀, 결제팀

## 맥락
주문 API가 결제 서비스를 HTTP로 직접 부른다. 지난 분기 결제대행사 장애 두 번 동안
결제 서비스 응답이 30초까지 늘었고, 주문 API의 스레드가 모두 대기에 묶여 주문 접수까지 멈췄다.
결제 확인은 주문 접수 응답에 꼭 필요하지 않다.

## 결정
주문 API는 결제 완료 사실을 order-events 토픽에 쓰고 바로 응답한다.
결제 워커가 토픽을 구독해 처리한다. 토픽 쓰기는 아웃박스 테이블을 거친다.

## 검토한 선택지
- HTTP 호출에 타임아웃 2초와 서킷 브레이커: 주문은 지키지만 결제 확인이 유실될 수 있다.
- RabbitMQ 큐: 팀에 운영 경험이 없다. 이미 운영 중인 Kafka 클러스터가 있다.

## 결과
- 결제사 장애가 주문 접수로 번지지 않는다.
- 결제 확인이 수 초 늦어질 수 있다. 화면은 "결제 확인 중" 상태를 보여 줘야 한다.
- 메시지 중복을 견디도록 결제 워커를 멱등하게 만든다.
- 트래픽이 지금의 10배가 되기 전에는 토픽 하나, 파티션 6개로 충분하다고 본다.
```

이걸 읽은 신규 개발자는 큐를 걷어 내기 전에 확인할 것이 생긴다. 결제사 장애가 여전히 있는지, 주문 접수가 정말 결제를 기다리지 않아도 되는지. 이유가 사라졌다면 새 ADR로 결정을 바꾸면 된다.

나이가드의 원래 형식은 제목, 상태, 맥락, 결정, 결과 다섯 칸이다. 이걸 넓힌 MADR(Markdown Architectural Decision Records)은 결정 동인, 검토한 선택지, 선택지별 장단점을 따로 둔다. 한 문장으로 줄이고 싶으면 올라프 짐머만(Olaf Zimmermann)의 Y-문장 형식도 있다.

```text
In the context of 주문 접수,
facing 결제사 장애가 주문 API의 스레드를 묶는 문제,
we decided for Kafka 토픽을 통한 비동기 전달
and neglected 타임아웃과 서킷 브레이커만 두는 안,
to achieve 결제 장애와 주문 접수의 분리,
accepting 결제 확인 지연과 중복 메시지 처리 비용.
```

형식보다 중요한 건 결정할 때 쓰는 것이다. 결정하고 몇 달 뒤에 쓰면 버린 선택지와 그때의 숫자가 기억에서 사라지고, 결과에는 좋은 점만 남는다.

## ADR은 고치지 않고 새로 쓴다

ADR의 규칙 중 가장 낯선 것이 승인된 ADR은 고치지 않는다는 것이다. 오타나 링크 정도는 고치지만, 결정 내용이 바뀌면 새 ADR을 쓰고 옛 ADR의 상태를 "대체됨, 0012 참고"로 바꾼다.

이렇게 하는 이유는 결정의 역사가 남기 때문이다. 2025년에는 Kafka가 맞았고, 2027년에 결제사가 바뀌면서 HTTP 호출로 돌아갔다면, 둘 다 그때는 옳은 결정이었다. 옛 문서를 덮어쓰면 "왜 한때 Kafka였지"라는 질문에 다시 답할 수 없다.

파일은 저장소 안 `docs/adr/` 같은 폴더에 `0007-payment-via-kafka.md`처럼 번호와 제목으로 둔다. 번호를 붙여 두면 PR 설명이나 코드 주석에서 "ADR-0007"로 짧게 가리킬 수 있다. npryce의 adr-tools 같은 셸 도구는 `adr new 제목`으로 다음 번호의 템플릿을 만들고, `adr new -s 7 제목`으로 7번을 대체하는 ADR을 만들면서 옛 문서의 상태도 함께 고친다. 도구가 없어도 템플릿 파일 하나와 번호 규칙이면 충분하다.

팀이 커지면 번호가 부딪힌다. 두 사람이 같은 주에 각자 브랜치에서 `0008`을 만들면, 먼저 머지된 쪽이 번호를 갖고 나중 쪽은 이름을 바꿔야 한다. 파일 이름이 같으면 Git이 충돌로 알려 주지만, 제목이 달라 파일 이름이 다르면 `0008`이 두 개 생긴 채로 조용히 머지된다. 해결책은 몇 가지가 있다.

- 머지 직전에 번호를 매긴다. 리뷰 중에는 `0000-payment-via-kafka.md`처럼 두고, 머지하는 사람이 다음 번호로 바꾼다.
- 번호 대신 날짜를 앞에 붙인다(`2025-03-12-payment-via-kafka.md`). 충돌이 거의 없지만 "ADR-7"처럼 짧게 부르기는 어렵다.
- CI에서 같은 번호의 파일이 둘 이상이면 실패하게 하는 한 줄짜리 검사를 둔다.

어느 쪽이든 한 번 정하면 바꾸지 않는다. 번호는 다른 문서와 코드 주석이 가리키는 주소이기 때문이다.

상태가 쌓이면 지금 유효한 결정이 무엇인지 한눈에 보고 싶어진다. 승인된 ADR 중 다른 승인된 ADR에 대체되지 않은 것만 고르면 된다. 제안 단계의 ADR이 대체를 선언해도, 승인되기 전에는 옛 결정이 그대로 유효하다는 점에 주의한다.

  const replaced = new Set();
  for (const a of adrs) {
    if (a.status !== "accepted") continue;
    for (const old of a.supersedes ?? []) replaced.add(old);
  }
  return adrs

    .map((a) => a.id)
    .sort((x, y) => x - y);

## 어떤 결정까지 남기나

모든 결정을 ADR로 쓰면 아무도 안 읽는 문서 더미가 된다. 나이가드는 "아키텍처적으로 중요한" 결정만 쓰라고 했는데, 그 기준을 현장에서 쓰기 좋게 바꾸면 이렇다.

- 되돌리는 데 몇 주 이상 걸린다. DB 종류, 메시지 브로커, 서비스 분리 경계, 인증 방식.
- 다른 팀의 작업 방식을 바꾼다. API 버전 정책, 이벤트 스키마 규칙, 공용 라이브러리 도입.
- 품질 특성을 맞바꾼다. 일관성 대신 가용성을 고르거나, 지연을 받아들이고 처리량을 얻는 결정.
- 나중에 누군가 "왜 이렇게 했어요?"라고 물을 게 뻔하다. 일부러 표준과 다르게 간 곳은 특히.

라이브러리의 마이너 버전 업그레이드, 변수 이름, 폴더 하나의 위치 같은 건 커밋 메시지와 PR 설명이면 충분하다. 애매하면 일단 짧게 쓴다. 다섯 줄짜리 ADR도 없는 것보다 낫다. ADR 형식이 [DDD 전술 패턴 글](/posts/ddd-tactical-patterns)의 "금액 계산은 Money 한 곳에서만" 같은 모델 결정이나, [엔터프라이즈 패턴 글](/posts/enterprise-application-patterns)의 "이 모듈은 트랜잭션 스크립트로 둔다" 같은 구조 선택을 남기기에도 잘 맞는다.

## 쓸모없어지는 ADR의 모양

ADR을 쓰기 시작한 팀이 몇 달 뒤 겪는 문제는 대개 형식이 아니라 내용이다. 리뷰에서 자주 돌려보내는 모양이 정해져 있다.

결정이 없는 ADR이 있다. "메시지 브로커 비교"라는 제목 아래 Kafka, RabbitMQ, SQS의 특징이 두 쪽에 걸쳐 정리돼 있는데 무엇을 골랐는지는 없다. 그건 조사 보고서다. 조사는 링크로 붙이고 ADR에는 결정을 쓴다.

결정 여러 개를 한 장에 넣은 ADR도 있다. "주문 서비스 재설계"라는 한 장에 DB 분리, 이벤트 도입, API 버전 정책이 다 들어 있으면, 나중에 그중 하나만 바꿀 때 대체 관계를 적을 수 없다. 결정 하나에 한 장이다.

맥락에 숫자가 없는 ADR은 나중에 판단의 기준이 되지 못한다. 아래 두 문장을 비교해 보면 차이가 분명하다.

```text
나쁜 예: 결제 서비스가 가끔 느려서 문제가 된다.
좋은 예: 2025년 1분기 결제대행사 장애 2회, 결제 서비스 p99 응답 30초, 그동안 주문 API 스레드 200개가 모두 대기.
```

앞 문장으로는 "지금도 가끔 느린가"를 확인할 방법이 없다. 뒤 문장은 지금의 지표와 바로 비교할 수 있다.

마지막은 구현이 다 끝난 뒤에 형식으로 쓰는 ADR이다. 이미 정해진 걸 문서로 옮기는 일이라 버린 선택지가 빈칸으로 남고, 결과에는 좋은 점만 남는다. 결정 전에 "제안됨" 상태로 PR을 열고, 그 PR이 곧 결정을 논의하는 자리가 되게 하면 이 문제가 거의 사라진다.

## 서랍장을 미리 정해 두는 arc42

C4가 그림을, ADR이 결정을 맡는다면, 아키텍처 문서 전체를 어떤 순서로 둘지는 arc42 같은 템플릿이 정해 준다. arc42는 독일에서 만든 무료 템플릿으로, 열두 칸짜리 서랍장이다. 도입과 목표, 제약, 컨텍스트와 범위, 해법 전략, 빌딩 블록 뷰, 런타임 뷰, 배포 뷰, 공통 개념, 아키텍처 결정, 품질 요구사항, 위험과 기술 부채, 용어집 순서다.

C4와 ADR은 이 서랍에 그대로 들어간다. 컨텍스트 그림은 3번 "컨텍스트와 범위"에, 컨테이너와 컴포넌트 그림은 5번 "빌딩 블록 뷰"에, 동적 그림은 6번 "런타임 뷰"에, ADR 목록은 9번 "아키텍처 결정"에 둔다. 모든 칸을 채울 필요는 없다. arc42 문서도 필요 없는 칸은 비워 두라고 한다. 다만 칸 이름이 있으면 "품질 요구사항은 어디에 적었더라"를 찾아 헤매지 않는다. 12번 용어집은 [DDD 바운디드 컨텍스트 글](/posts/ddd-bounded-context)의 유비쿼터스 언어를 적어 두기에 좋은 자리다.

## 문서가 낡지 않게 리뷰에 묶는다

아키텍처 문서의 가장 큰 적은 낡는 것이다. 처음 그렸을 때는 정확했는데, 서비스가 두 개 늘고 DB 하나가 빠지면서 그림은 거짓말이 된다. 틀린 그림은 그림이 없는 것보다 나쁘다. 신규 입사자가 틀린 그림을 믿고 판단하기 때문이다.

낡지 않게 하는 방법은 문서를 코드와 같은 흐름에 태우는 것이다. 아래 그림에서 다음을 누르면, 구조를 바꾸는 PR 하나가 그림과 ADR을 함께 바꾸고 리뷰를 거쳐 문서 사이트까지 가는 흐름을 볼 수 있다.

장치 자체는 파일 두 개면 된다. GitHub 기준으로 쓰면 이렇다.

```text
# .github/CODEOWNERS: 이 경로가 바뀌는 PR에 리뷰어를 자동으로 붙인다
/docs/adr/            @shop/architecture
/docs/architecture/   @shop/architecture
```

```markdown
<!-- .github/pull_request_template.md -->
## 구조 변경 확인
- [ ] 새 컨테이너(앱, DB, 토픽, 외부 연동)가 생기거나 없어지나요? 그렇다면 workspace.dsl을 고쳤나요?
- [ ] 되돌리기 어려운 결정이 들어 있나요? 그렇다면 ADR 번호: ____
```

CODEOWNERS는 저장소 설정에서 해당 브랜치에 "코드 소유자 리뷰 필수"를 켜야 머지를 막는다. 켜지 않으면 리뷰어 지정만 되고 승인 없이도 머지된다. 체크 항목은 강제가 아니라 기억을 돕는 장치다. 이 두 줄 때문에 "아, 이거 ADR 써야 하는 건가" 하고 멈추는 순간이 생기는 게 목적이다.

이 흐름에 몇 가지 장치를 더하면 효과가 크다. 컴포넌트 수준의 의존 규칙은 그림 대신 ArchUnit이나 dependency-cruiser 같은 아키텍처 테스트로 써 두면, 어기는 순간 CI가 실패해서 문서가 코드와 어긋날 수 없다. [클린 아키텍처 글](/posts/clean-architecture)에서 의존 규칙을 검사기로 지키는 모습을 볼 수 있다. 그래도 사람이 그린 그림은 낡으니, 그림마다 마지막 확인 날짜를 적고 분기마다 한 번 1, 2단계 그림만 훑어보는 시간을 잡는다.

위키와 저장소 중 어디에 둘지도 자주 나오는 질문이다. 저장소는 리뷰와 버전 관리가 되지만 개발자가 아닌 사람은 잘 안 본다. 위키는 누구나 읽지만 코드와 따로 논다. 원본은 저장소에 두고 문서 사이트로 내보내 누구나 읽게 하는 게 둘의 장점을 함께 가져가는 방법이다. 여러 저장소에 걸친 결정(공통 인증 방식처럼)은 조직 단위의 아키텍처 저장소를 하나 두고 거기에 쓴다.

## 그림과 기록이 값을 하는 순간

이 문서들이 가장 자주 쓰이는 곳은 회의실이 아니라 장애 대응과 온보딩이다.

결제 워커가 죽었다는 알림이 왔을 때, 컨테이너 그림이 있으면 영향 범위를 바로 말할 수 있다. 워커는 토픽을 구독하니 주문 접수는 계속되고, 결제 확인만 쌓인다. 토픽 보존 기간 안에 워커를 살리면 밀린 메시지는 다시 처리된다. 그림이 없으면 이걸 코드를 뒤져 가며 알아내야 하고, 그 사이 누군가 "주문도 막아야 하나요?"라고 묻는다.

보안 검토에서도 같은 그림을 쓴다. 개인정보가 어느 컨테이너를 거쳐 어느 바깥 시스템으로 나가는지 화살표를 따라가면 데이터 흐름이 정리된다. 화살표에 프로토콜을 적어 두었다면 암호화되지 않은 구간도 그림에서 찾을 수 있다.

ADR은 "이거 바꿔도 되나요?"라는 질문을 받을 때 쓰인다. 신규 개발자가 처음 장면처럼 큐를 걷어 내자고 제안하면, ADR-0007의 맥락 칸에 적힌 숫자(결제사 장애 두 번, 응답 30초)가 지금도 사실인지 확인하는 것에서 대화가 시작된다. 사실이 바뀌었으면 새 ADR로 결정을 바꾸고, 그대로면 제안을 접는다. 같은 논쟁을 해마다 처음부터 다시 하는 일이 줄어든다.

## UML과는 어떤 관계인가

C4를 UML의 대체품으로 보는 경우가 있는데, 둘은 다른 것을 정한다. UML은 표기법이다. 클래스, 시퀀스, 상태, 배포 다이어그램마다 상자와 화살표의 모양과 뜻을 정해 둔다. C4는 추상화 수준을 정한다. 무엇을 어느 확대 단계에서 그릴지만 말하고, 모양은 자유다.

그래서 둘은 함께 쓴다. C4의 4단계 코드 그림은 UML 클래스 다이어그램으로 그리고, 2단계 컨테이너 사이의 복잡한 흐름은 UML 시퀀스 다이어그램(이 글의 흐름 그림 같은 것)으로 보충한다. 주문 상태 전이처럼 규칙이 복잡한 곳은 UML 상태 다이어그램이 말보다 정확하다. 다만 UML 전체 표기법을 팀 모두가 아는 경우는 드무니, C4 그림에는 범례를 붙여 표기법을 몰라도 읽히게 한다.

## 면접에서 나올 만한 질문

### C4 모델의 네 단계를 설명해 주세요.

시스템을 지도처럼 확대 단계로 나눠 그리는 방법이다. 1단계 컨텍스트는 우리 시스템과 그걸 쓰는 사람, 연동하는 바깥 시스템만 그린다. 2단계 컨테이너는 따로 배포되고 실행되는 단위(앱, API, DB, 토픽)와 그 사이의 통신을, 3단계 컴포넌트는 컨테이너 하나의 내부 구성을, 4단계 코드는 클래스 구조를 그린다. 실무에서는 1, 2단계를 꾸준히 관리하고 3, 4단계는 필요한 곳에만 둔다.

### C4의 컨테이너는 도커 컨테이너와 같은 뜻인가요?

아니다. 코드가 실행되거나 데이터가 저장되는 독립된 단위라는 뜻으로, SPA, 모바일 앱, DB, 버킷도 컨테이너다. 같은 API를 도커 컨테이너 여러 개로 띄워도 C4에서는 상자 하나이고, 몇 개를 어디에 띄우는지는 배포 그림에서 따로 보여 준다.

### ADR에는 무엇을 쓰고, 왜 쓰나요?

결정 하나당 제목, 상태, 맥락, 결정, 결과를 짧게 쓴다. 코드는 무엇을 하는지만 말하고 왜 그렇게 했는지는 말하지 않아서, 결정한 사람이 떠나면 이유가 사라진다. 특히 검토했지만 버린 선택지와 나빠지는 결과를 함께 적어야, 나중에 그 결정을 바꿔도 되는지 판단할 수 있다.

### 승인된 ADR의 내용이 바뀌면 어떻게 하나요?

옛 ADR을 고치지 않고 새 ADR을 쓴 뒤 옛 것의 상태를 "대체됨"으로 바꾸고 새 번호를 적는다. 그래야 그때는 왜 그 결정이 맞았는지라는 역사가 남는다. 오타나 링크 같은 사소한 수정만 직접 고친다.

### 어떤 결정까지 ADR로 남겨야 하나요?

되돌리는 비용이 크거나, 다른 팀의 작업 방식을 바꾸거나, 성능과 일관성 같은 품질 특성을 맞바꾸는 결정이다. DB와 브로커 선택, 서비스 경계, 인증 방식, API 버전 정책이 대표적이다. 라이브러리 마이너 업그레이드나 이름 짓기는 PR 설명으로 충분하다. 애매하면 다섯 줄로라도 짧게 남긴다.

### 아키텍처 문서가 낡는 문제는 어떻게 막나요?

문서를 저장소에 텍스트로 두고 코드와 같은 PR에서 바꾸게 한다. Structurizr DSL이나 Mermaid처럼 그림을 코드로 쓰면 리뷰가 되고, CI가 문법과 링크를 검사하고 문서 사이트를 다시 만든다. CODEOWNERS로 문서 리뷰어를 자동 지정하고, PR 템플릿에 문서 체크 항목을 둔다. 컴포넌트 수준의 의존 규칙은 아키텍처 테스트로 써서 어기면 빌드가 깨지게 한다.

### C4와 UML, arc42는 어떤 관계인가요?

UML은 상자와 화살표의 표기법을 정하고, C4는 어느 확대 단계에서 무엇을 그릴지를 정한다. 그래서 C4의 코드 단계나 흐름 그림을 UML로 그리는 식으로 함께 쓴다. arc42는 문서 전체의 목차를 정하는 템플릿이라, C4 그림은 컨텍스트와 빌딩 블록 뷰 칸에, ADR은 아키텍처 결정 칸에 들어간다.
