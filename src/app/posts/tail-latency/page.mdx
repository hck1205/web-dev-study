<EasyIntro>
  상품 페이지 하나를 그리려고 뒤에서 가격, 재고, 리뷰, 추천 같은 서비스 여러 개에 동시에 묻는 구조가 있다. 서비스마다 100번에 한 번만 느린데, 페이지는 거의 매번 느리다. 어느 서비스도 잘못한 게 없는데 그렇다.

  반 친구 100명에게 동시에 심부름을 시키고 전원이 돌아와야 출발하는 소풍과 같다. 한 명이 늦을 확률이 1%뿐이어도 100명 중 하나라도 늦을 확률은 63%라서, 드문 일이 묻는 곳이 많아지는 순간 흔한 일이 된다. 늦는 이유는 대개 그 친구의 그 순간 사정(잠깐 멈춤, 줄 서기, 옆 사람 방해)이라 없앨 수 없다.

  그래서 꼬리를 없애기보다 느린 친구가 있어도 덜 기다리게 만든다. 줄이 너무 길면 뒤에 온 사람은 바로 돌려보내고, 늦는 친구 대신 다른 친구에게 같은 심부름을 한 번 더 시키고, 빠져도 되는 심부름은 다 안 와도 출발한다. 이 판단은 서비스별 대시보드가 아니라 사용자 쪽에서 잰 값으로 확인해야 한다.
</EasyIntro>

상품 상세 페이지 하나를 만들려고 뒤에서 서비스 여러 개에 동시에 묻는 구조가 있다. 가격, 재고, 리뷰, 추천, 쿠폰을 따로 받아 합친다. 서비스별 대시보드는 모두 초록색이다. 각자 p99가 200ms 안쪽이고 p50은 5ms다. 그런데 페이지의 p50이 200ms 근처에 붙어 있다. 어느 서비스도 느리지 않은데 페이지는 늘 느리다.

이 현상이 꼬리 지연(tail latency)의 증폭이다. 서버 하나에서는 100번에 한 번 일어나는 느림이, 요청 하나가 서버 여러 대를 기다리는 순간 흔한 일이 된다. 이 글은 그 증폭을 직접 재 보고, 꼬리가 어디서 생기는지, 그리고 꼬리를 잘라 내는 방법(넘치는 요청 거절하기, 다른 서버에 한 번 더 묻기, 다 기다리지 않기)을 실험과 함께 정리한다. 실습은 Ubuntu 24.04, Node 22로 했다. 큰 틀은 구글의 Jeffrey Dean과 Luiz André Barroso가 2013년 Communications of the ACM에 실은 글 "The Tail at Scale"을 따른다.

이 주제의 다른 글: 꼬리를 숫자로 재는 법(백분위, 히스토그램, coordinated omission)은 [응답 시간은 백분위로 읽는다](/posts/percentile-latency)에서 다뤘다. 느린 요청을 다른 서버에 한 번 더 보내는 헤징의 실험과 설정은 [재시도](/posts/retries) 글에, 기다림에 상한을 거는 일은 [타임아웃](/posts/timeouts) 글에 있다.

## 하나일 때 드문 일이 백 개면 흔해진다

잎(leaf) 서버를 하나 띄웠다. 요청의 99%는 5ms, 1%는 200ms가 걸린다. p99가 200ms인, 대시보드로 보면 멀쩡한 서버다. 그리고 사용자 요청 하나가 이 서버에 N번 동시에 묻고, 전부 답해야 끝나게 했다. 페이지 하나가 서비스 N개를 부르는 상황이다.

```js
// 사용자 요청 하나 = 잎 서버 N개에 동시에 묻고 전부 기다리기
await Promise.all(Array.from({ length: n }, () => get("http://127.0.0.1:19421/")));
```

```bash
# N을 1, 10, 50, 100으로 바꿔 가며 사용자 요청 2000개씩
node fanout.js
```

```text
N=  1 users=2000 p50=6.3ms p90=6.9ms p99=201.1ms  >150ms: 1.1%  (1-0.99^N = 1.0%)
N= 10 users=2000 p50=6.7ms p90=15.8ms p99=202.6ms  >150ms: 9.5%  (1-0.99^N = 9.6%)
N= 50 users=2000 p50=14.4ms p90=205.7ms p99=212.3ms  >150ms: 40.9%  (1-0.99^N = 39.5%)
N=100 users=2000 p50=204.7ms p90=210.5ms p99=222.1ms  >150ms: 61.5%  (1-0.99^N = 63.4%)
```

잎이 하나면 느린 요청은 1%다. 열 개면 9.5%, 백 개면 61.5%다. N=100에서는 p50이 204.7ms, 즉 사용자 요청의 절반 이상이 "드문" 200ms를 겪는다. 잎 서버는 하나도 바뀌지 않았다.

계산은 단순하다. 잎 하나가 빠를 확률이 0.99면, N개가 모두 빠를 확률은 0.99를 N번 곱한 값이다. 그러니 하나라도 느릴 확률은 1 − 0.99ᴺ이다. 100개면 1 − 0.366 = 63.4%다. 측정값(61.5%)이 이 식과 거의 같다. "The Tail at Scale"이 든 예도 같은 계산이다. p99가 1초인 서버 100대에 동시에 묻는 요청은 63%가 1초를 넘긴다.

## 느린 잎이 몇 개까지 괜찮은가 직접 계산하기

N개 중 k개만 답하면 끝내는 경우까지 넣어 계산기를 만들어 보자. 잎 하나가 느릴 확률이 `p`일 때 느린 잎의 수는 이항 분포를 따른다. k개만 기다린다면 느린 잎이 `n - k`개보다 많을 때만 사용자 요청이 느려진다. 결과는 퍼센트로, 소수 첫째 자리까지 반올림한다.

<CodePlayground
  caption="잎 n개에 묻고 k개를 기다릴 때 느려질 확률(%)"
  functionName="slowChance"
  initialCode={`function slowChance(p, n, k = n) {
  // p: 잎 하나가 느릴 확률, n: 묻는 잎 수, k: 기다리는 응답 수
  // 1) k = n이면 1 - (1 - p)^n
  // 2) 일반적으로는 P(느린 잎 수 > n - k)
  return 0;
}`}
  solution={`function slowChance(p, n, k = n) {
  let fast = 0;                       // P(느린 잎 수 <= n - k)
  let term = Math.pow(1 - p, n);      // 느린 잎이 0개일 확률
  for (let s = 0; s <= n - k; s++) {
    fast += term;
    term = term * ((n - s) / (s + 1)) * (p / (1 - p)); // 이항 분포 다음 항
  }
  return Math.round((1 - fast) * 1000) / 10;
}`}
  tests={[
    { label: "잎 1개", args: [0.01, 1], expected: 1 },
    { label: "잎 10개", args: [0.01, 10], expected: 9.6 },
    { label: "잎 100개", args: [0.01, 100], expected: 63.4 },
    { label: "p99.9 잎 100개", args: [0.001, 100], expected: 9.5 },
    { label: "100개 중 99개만", args: [0.01, 100, 99], expected: 26.4 },
    { label: "100개 중 95개만", args: [0.01, 100, 95], expected: 0.1 },
  ]}
/>

결과에서 두 가지를 읽는다. 하나는 잎의 꼬리를 한 단계 줄이면 효과가 크다는 것이다. 잎의 느린 비율을 1%에서 0.1%로 줄이면(p99를 p99.9로) 100개 팬아웃의 느린 요청이 63.4%에서 9.5%로 내려간다. 거꾸로 말하면, 팬아웃 요청의 99%를 지키려면 잎 하나는 0.99^(1/100) ≈ 99.99%, 즉 p99.99에서 그 시간을 지켜야 한다. 다른 하나는 전부 기다리지 않으면 확률이 극적으로 바뀐다는 것이다. 이건 뒤에서 실제로 재 본다.

## 꼬리는 어디서 생기나

잎 서버가 1%의 확률로 느린 이유는 코드가 1%의 확률로 느린 경로를 타서가 아닌 경우가 많다. 같은 요청인데 그 순간 서버의 사정 때문에 느리다. 원인은 몇 갈래로 나뉜다.

런타임 멈춤은 GC가 대표다. 멈추는 동안 그 프로세스에 들어온 모든 요청이 함께 기다린다. 멈춤이 어떻게 생기고 어떻게 줄이는지는 [가비지 컬렉션](/posts/garbage-collection) 글에서 다룬다.

줄 서기는 가장 흔하고 가장 과소평가된다. 서버가 한가하면 요청은 바로 처리되지만, 요청이 무작위로 몰려 들어오면 평균 사용률이 낮아도 순간적으로 줄이 생긴다. 사용률이 오를수록 줄이 길어지는 속도가 급해진다. 단순한 대기열 모형에서 사용률 50%일 때의 평균 응답 시간이 95%에서 열 배가 되는 이야기는 [지연, 대역폭, 처리량](/posts/latency-bandwidth-throughput) 글에 있다. 꼬리(p99)는 평균보다 먼저, 더 크게 늘어난다.

자원 공유는 같은 호스트의 다른 작업(시끄러운 이웃, noisy neighbor)이 CPU 캐시, 메모리 대역폭, 디스크, 네트워크를 함께 쓰면서 생긴다. 이 글의 실험도 그 영향을 받았다. CPU를 1ms 쓰는 서버에 초당 200건을 고르게 보내는 같은 측정을 연달아 돌렸더니 p99가 11.3ms, 42.0ms, 70.2ms, 16.5ms로 나왔다. 코드도 부하도 같았고, 다른 작업들이 같은 기계를 쓰고 있었다. 반대로 일부러 같은 코어에 CPU를 태우는 프로세스를 붙였을 때는 차이가 뚜렷하지 않았다. 이 서버가 쓰는 CPU가 20% 정도라 스케줄러가 나눠 주는 몫 안에 들었기 때문이다. 이웃의 영향은 이렇게 예측하기 어렵고, 그래서 평소 분포를 계속 재 두는 수밖에 없다.

뒤에서 도는 일은 LSM 저장소의 컴팩션, 로그 회전, 백업, 크론 작업처럼 주기적으로 자원을 크게 쓰는 일이다. 재시도는 실패를 덮어 주지만, 꼬리가 길어진 서버에 요청을 더 보내 줄을 더 길게 만든다([재시도](/posts/retries) 글에서 계층마다 세 번이면 27배가 되는 과정을 쟀다). 패킷 손실은 TCP 재전송 대기로 이어져 200ms~1초짜리 꼬리를 만든다.

이 원인들은 대부분 없앨 수 없다. GC를 끌 수 없고, 사용률을 0%로 둘 수 없고, 이웃을 고를 수 없다. 그래서 꼬리를 줄이는 기술은 "느려지지 않게"보다 "느린 것이 있어도 사용자가 덜 기다리게"에 가깝다. 논문의 표현을 빌리면, 결함 내성(fault-tolerant) 시스템처럼 꼬리 내성(tail-tolerant) 시스템을 만든다.

## 넘치는 요청은 빨리 거절한다

먼저 줄 서기부터 본다. 동시에 4개만 처리하고 하나에 10ms가 걸리는 서버를 만들었다. 최대 처리량은 초당 400개다. 나머지 요청은 서버 안의 큐에서 기다린다. 클라이언트는 열린 모델로(정해진 속도로, 응답과 상관없이) 10초 동안 요청을 보내고, 1초가 지나면 포기한다.

```bash
# 사용률 80%(초당 320개), 150%(초당 600개)로 보내 본다
MODE=none node shed-server.js &
node open-load.js 320 10
node open-load.js 600 10
```

```text
rate=320/s sent=3200 ok=3200 503=0 client_timeout=0 | ok p50=11ms p99=29ms | goodput=320/s
rate=600/s sent=6000 ok=1038 503=0 client_timeout=4962 | ok p50=561ms p99=1019ms | goodput=104/s
```

80%에서는 p99 29ms로 괜찮다. 150%가 되자 무너진다. 6000건 중 4962건이 클라이언트 쪽에서 타임아웃 났다. 서버가 1초마다 찍은 큐 길이와 누적 처리 수를 같이 보면 더 아프다.

```text

queue=357 done=593 shed=0
queue=573 done=977 shed=0
queue=600 done=1367 shed=0
...
queue=598 done=3302 shed=0
queue=603 done=3679 shed=0
queue=244 done=4067 shed=0
queue=0 done=4228 shed=0
```

서버는 쉬지 않고 4,228건을 처리했다. 그런데 1초 안에 클라이언트에 닿은 건 1,038건뿐이다. 나머지 3천여 건은 사용자가 이미 떠난 뒤에 끝난 헛일이다. 처리 능력은 초당 400개인데 쓸모 있는 처리량(goodput)은 초당 104개로 떨어졌다. 줄이 길어지면 모든 요청이 늦어지고, 늦어진 요청은 버려지고, 버려질 요청을 처리하느라 다음 요청이 또 늦어진다.

이번에는 큐가 20개를 넘으면 들어오는 요청을 바로 503으로 거절하게 했다. load shedding이다.

```bash
# 큐 길이 20을 넘으면 즉시 503
MODE=shed MAXQ=20 node shed-server.js &
node open-load.js 600 10
```

```text
rate=600/s sent=6000 ok=3893 503=2107 client_timeout=0 | ok p50=61ms p99=74ms | goodput=389/s
```

2,107건은 거절당했다. 대신 받아들인 3,893건은 p99 74ms로 끝났고, 쓸모 있는 처리량이 초당 389개로 서버 능력에 붙었다. 거절당한 요청도 1초를 기다리다 타임아웃 나는 대신 몇 ms 만에 503을 받아, 클라이언트가 바로 다른 서버로 가거나 조금 뒤 다시 시도할 수 있다. 아래 그림에서 다음을 누르면 두 서버의 차이가 보인다.

거절 기준은 여러 가지로 잡는다. 이 실험처럼 큐 길이로 자르는 방법이 가장 단순하다. 큐 안에서 기다린 시간으로 자를 수도 있다. 꺼낼 때 이미 클라이언트의 데드라인이 지난 요청은 처리하지 않고 버린다([타임아웃](/posts/timeouts) 글의 데드라인 전파가 여기 쓰인다). 동시 처리 수의 상한을 지연 변화에 맞춰 자동으로 조절하는 적응형 방식도 있다. 중요도가 다르면 우선순위를 두어, 결제 같은 요청은 남기고 추천 같은 요청부터 버린다.

흔한 실수는 거절을 실패로만 보고 클라이언트가 곧바로 재시도하게 두는 것이다. 그러면 거절한 만큼 요청이 다시 몰린다. 503에 `Retry-After`를 붙이고, 클라이언트는 [지수 백오프와 지터](/posts/exponential-backoff-jitter)로 흩어 보낸다. 서버가 들어오는 양을 미리 제한하는 일은 [요청 수 제한 알고리즘](/posts/rate-limiting-algorithms)에서, 받는 쪽이 보내는 쪽 속도를 늦추는 일은 [백프레셔](/posts/backpressure)에서 이어진다.

## 다른 서버에 한 번 더 묻기: 헤징과 묶인 요청

줄을 관리해도 GC나 이웃 때문에 서버 하나가 잠깐 느린 건 남는다. 같은 데이터를 가진 복제본이 여럿이면, 느린 서버를 기다리는 대신 다른 서버에 한 번 더 물을 수 있다.

헤징(hedged request)은 첫 요청을 보내고 일정 시간(보통 p95 근처) 안에 답이 없으면 다른 복제본에 같은 요청을 보낸다. 먼저 온 답을 쓰고 나머지는 취소한다. 실제 측정과 gRPC 설정은 [재시도](/posts/retries) 글에서 다뤘으니 여기서는 그 다음 단계를 본다. 논문에 실린 구글 BigTable 실험에서는 서버 100대에 흩어진 키 1,000개를 읽을 때 10ms 뒤에 헤징 요청을 보내자 p99.9가 1,800ms에서 74ms로 줄었고, 늘어난 요청은 2%였다.

헤징의 약점은 기다리는 시간이다. 10ms를 기다린 뒤에야 두 번째를 보내니, 그 10ms는 이미 쓴 시간이다. 그렇다고 처음부터 두 군데 보내면 일이 두 배가 된다. 묶인 요청(tied request)은 그 사이를 노린다. 처음부터 두 서버의 큐에 같이 넣되, 각 사본에 "다른 서버에도 넣었다"는 표시를 붙인다. 어느 한쪽이 그 요청을 실제로 처리하기 시작하는 순간 다른 쪽에 취소를 보낸다. 큐에서 기다리는 동안은 둘 다 기다리고, 일은 거의 한 번만 한다.

세 방식을 같은 조건에서 비교하려고 이산 사건 시뮬레이션을 짰다. 서버 4대가 각자 큐 하나와 일꾼 하나를 두고, 요청 처리는 4ms인데 1%의 확률로 그 서버가 50ms 멈춘다(GC 같은 서버 사정). 사용률은 60%, 요청 20만 개다. 실제 네트워크가 아니라 모형이므로 절대값보다 비교에 쓴다.

```bash
# 한 서버에만 / 10ms 뒤 헤징 / 처음부터 묶기 / 2ms 늦게 묶기
node tied-sim.js
```

```text
single           p50=5.8ms p95=53.2ms p99=70.2ms p99.9=126.2ms  work=+0.0%
hedge            p50=6.7ms p95=21.9ms p99=37.8ms p99.9=58.2ms  work=+11.4%
tied             p50=6.2ms p95=17.4ms p99=42.0ms p99.9=63.6ms  work=+34.4%
tied +2ms        p50=6.0ms p95=14.9ms p99=43.0ms p99.9=60.8ms  work=+12.7%
```

헤징과 묶인 요청 모두 p99.9를 절반 아래로 줄였다. 묶인 요청은 p95가 가장 낮다. 기다리지 않고 처음부터 두 큐에 서 있었기 때문이다. 대신 둘 다 바로 넣으면 일이 34% 늘었다. 두 서버가 다 한가할 때 취소가 닿기 전에 양쪽이 동시에 처리를 시작해서다. 두 번째 사본을 2ms 늦게 넣자 추가 작업이 12.7%로 줄었다. p99와 p99.9는 헤징이 조금 더 좋았는데, 이미 처리를 시작한 사본은 멈춰도 취소되지 않는 모형이라 그 차이가 남았다.

이 방법들은 조건이 있다. 읽기처럼 두 번 해도 되는 요청이어야 한다. 느림이 서버 하나의 사정이어야 한다. 모든 서버가 과부하라면 사본은 부하만 늘린다. 그래서 헤징 비율에 상한을 두고, 과부하 신호(거절 503이 늘어남)가 보이면 끈다.

## 다 기다리지 않는다

팬아웃 자체를 바꾸는 방법도 있다. 검색 결과처럼 잎 몇 개가 빠져도 쓸 만한 답이 되는 경우, 전부를 기다리지 않고 대부분이 오면 답한다. 앞의 잎 서버 100개 실험을 기다리는 수만 바꿔 다시 돌렸다.

```bash
# 잎 100개에 묻고 100개, 99개, 95개가 답하면 끝낸다
node goodenough.js
```

```text
wait for 100/100  p50=204.0ms p90=207.0ms p99=216.0ms
wait for  99/100  p50=15.4ms p90=205.2ms p99=210.5ms
wait for  95/100  p50=16.1ms p90=22.7ms p99=30.1ms
```

하나만 덜 기다려도 p50이 204ms에서 15.4ms로 내려간다. 느린 잎이 두 개 이상일 확률(26.4%)만큼은 여전히 느려서 p90은 그대로다. 다섯 개를 덜 기다리면 p99가 30.1ms다. 앞의 계산기로 구한 확률(0.1%)과 맞는다. 논문은 이런 답을 good-enough response라고 부른다. 대가는 결과의 완전성이다. 상품 페이지의 가격처럼 빠지면 안 되는 조각에는 못 쓰고, 추천이나 검색 결과의 일부처럼 빠져도 되는 조각에만 쓴다. 상품 페이지라면 가격·재고는 반드시 기다리고, 추천은 50ms 안에 안 오면 빈 칸으로 보내는 식으로 조각마다 다르게 정한다.

논문이 함께 소개하는 장치들도 짧게 적어 둔다.

- 마이크로 파티셔닝: 데이터를 서버 수보다 훨씬 많은 조각으로 나눠, 느린 서버에서 조각 몇 개만 옮겨도 부하가 고르게 맞춰지게 한다.
- 선택적 복제: 자주 찾는 조각은 복제본을 더 둬서 헤징할 곳을 늘린다.
- 지연 기반 격리(probation): 유난히 느린 서버를 잠시 요청 대상에서 빼고, 그동안 가벼운 요청으로 회복을 지켜본다. [서킷 브레이커](/posts/circuit-breaker)의 느린 호출 비율과 생각이 같다.
- 카나리 요청: 수천 대에 한꺼번에 보내기 전에 한두 대에 먼저 보내 본다. 특정 요청이 서버를 죽이는 버그가 있을 때 전체가 동시에 쓰러지는 것을 막는다.

## 현장에서 꼬리를 쫓는 순서

"페이지가 가끔 느리다"는 말이 들어오면 이 순서로 좁힌다.

먼저 팬아웃 구조를 그린다. 요청 하나가 어떤 서비스를 몇 번 부르는지, 병렬인지 순차인지다. [분산 추적](/posts/distributed-tracing)의 폭포 그림에서 느린 요청 몇 개를 열어 보면, 매번 같은 서비스가 늦는지 매번 다른 서비스가 늦는지가 보인다. 매번 다르다면 위의 증폭이다. 서비스 하나하나는 멀쩡하고, 고칠 곳은 팬아웃의 모양과 각 서비스의 p99.9다.

다음으로 느린 쪽의 서버별 분포를 쪼갠다. 서버 한 대만 꼬리가 길면 그 서버의 이웃, 디스크, GC를 본다. 모든 서버가 같이 길면 사용률과 큐를 본다. CPU 사용률이 60~70%를 넘었는데 p99가 같이 오르기 시작했다면 줄 서기다. 서버 측정에는 큐 대기가 빠지기 쉬우니 LB 쪽 지연도 같이 본다.

그다음 설정을 확인한다.

- 팬아웃 호출마다 타임아웃이 있나. 없다면 가장 느린 잎이 사용자의 시간을 정한다. 호출별 타임아웃의 합이 아니라 남은 시간(데드라인)을 넘겨준다.
- 재시도가 꼬리를 키우고 있지 않나. 서비스로 들어오는 요청 수가 사용자 요청 수보다 몇 배 많으면 재시도 증폭이다.
- 서버 큐에 상한이 있나. 없다면 과부하 때 위 실험처럼 헛일을 하며 무너진다.
- 헤징을 쓴다면 비율 상한과 과부하 때 끄는 조건이 있나.

흔한 실수는 서비스별 p99 대시보드만 보고 "다 정상"이라고 결론 내리는 것이다. 팬아웃이 있는 시스템에서는 사용자 쪽 백분위를 따로 재야 한다. 그리고 꼬리를 줄이겠다고 모든 호출에 헤징을 켜는 것도 위험하다. 과부하가 원인이면 헤징은 불에 기름을 붓는다.

## 드문 느림을 드물게 남기려면

서버 하나의 p99는 그 서버를 거치는 요청 100개 중 하나의 이야기다. 요청 하나가 서버 100대를 거치면 그 하나가 거의 모든 요청의 이야기가 된다. 꼬리의 원인(GC, 줄 서기, 이웃, 백그라운드 작업, 재시도)은 대부분 없앨 수 없으니, 넘치는 요청은 빨리 거절하고, 느린 서버 대신 다른 복제본에 묻고, 빠져도 되는 조각은 기다리지 않는다. 그리고 이 모든 판단은 사용자 쪽에서 잰 백분위로 확인한다.

## 면접에서 나올 만한 질문

### 서비스마다 p99가 200ms인데 왜 페이지의 p50이 200ms가 되나요?

페이지가 서비스 여러 개에 동시에 묻고 전부를 기다리면, 하나라도 느릴 확률이 1 − 0.99ᴺ로 커지기 때문이다. 잎 100개면 63%라서 사용자 요청의 절반 이상이 200ms를 겪는다. 실험에서도 N=100일 때 p50이 204.7ms였다. 그래서 팬아웃 시스템은 잎의 p99가 아니라 p99.9, p99.99를 관리한다.

### 꼬리 지연은 주로 어디서 생기나요?

같은 요청이 그 순간 서버 사정 때문에 느린 경우가 대부분이다. GC 같은 런타임 멈춤, 요청이 순간적으로 몰려 생기는 큐 대기, 같은 호스트를 쓰는 이웃과의 자원 경쟁, 컴팩션이나 백업 같은 백그라운드 작업, 재시도가 키운 부하, 패킷 손실 뒤의 재전송 대기가 대표적이다. 대부분 없앨 수 없어서 느린 것이 있어도 사용자가 덜 기다리게 만드는 쪽으로 대응한다.

### load shedding은 왜 필요하고 어떻게 하나요?

과부하에서 큐에 상한이 없으면 모든 요청이 늦어지고, 사용자가 떠난 요청을 처리하느라 쓸모 있는 처리량이 무너지기 때문이다. 실험에서 처리 능력의 150%를 보내자 서버는 4천여 건을 처리했지만 1초 안에 닿은 건 1,038건이었다. 큐 길이나 큐 대기 시간, 데드라인을 기준으로 넘치는 요청을 즉시 503으로 거절하면 받은 요청은 p99 74ms로 끝났다. 거절에는 Retry-After를 붙이고 클라이언트는 백오프로 다시 보낸다.

### 헤징 요청과 묶인 요청은 무엇이 다른가요?

헤징은 첫 요청 뒤 일정 시간 안에 답이 없을 때 두 번째를 보내고, 묶인 요청은 처음부터 두 서버의 큐에 넣되 한쪽이 처리를 시작하면 다른 쪽을 취소한다. 헤징은 기다린 시간만큼 손해를 보고, 묶인 요청은 그 대기 없이 짧은 큐를 고르는 효과를 얻는다. 두 서버가 모두 한가하면 둘 다 처리를 시작할 수 있어서 두 번째 사본을 아주 짧게 늦춰 보낸다.

### 헤징은 언제 쓰면 안 되나요?

모든 서버가 과부하라서 느린 상황, 그리고 두 번 실행하면 안 되는 요청에는 쓰면 안 된다. 과부하에서 사본은 부하만 늘려 꼬리를 더 길게 만든다. 그래서 헤징 비율에 상한을 두고 거절이 늘어나는 등의 과부하 신호가 보이면 끈다. 쓰기 요청이라면 멱등성 키 같은 장치 없이 헤징하지 않는다.

### 팬아웃 요청에서 일부 응답을 기다리지 않는 건 어떤 경우에 괜찮나요?

빠져도 결과가 쓸 만한 조각일 때만 괜찮다. 검색 결과의 일부, 추천, 부가 정보 같은 것이다. 잎 100개 중 95개만 기다리자 p99가 216ms에서 30ms로 줄었지만 결과는 불완전하다. 가격이나 재고처럼 빠지면 안 되는 조각은 반드시 기다리고, 조각마다 기다릴지와 시간 한도를 따로 정한다.

### "모든 서비스 대시보드가 정상인데 사용자는 느리다"고 하면 어디부터 보나요?

사용자 요청 단위의 백분위와 팬아웃 구조부터 본다. 분산 추적으로 느린 요청 몇 개를 열어 매번 같은 서비스가 늦는지 매번 다른지 확인한다. 매번 다르면 팬아웃 증폭이니 잎의 p99.9와 타임아웃, 헤징, 부분 응답을 검토한다. 특정 서버만 늦으면 그 서버의 GC, 이웃, 디스크를 보고, 전체가 같이 늦으면 사용률과 큐를 본다.
