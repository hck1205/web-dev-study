<EasyIntro>
  상품 하나의 가격을 고치려고 UPDATE를 쳤는데 조건을 빠뜨려서 세 줄이 전부 바뀌고, 기본 설정이 자동 확정이라 이미 되돌릴 수 없게 된 일이 있다. 행을 넣고 고치고 지우는 명령은 문법이 짧아서 실수도 짧게 난다.

  그래서 바꾸기 전에 트랜잭션을 연다. 트랜잭션은 여러 문장을 전부 되거나 전부 안 되거나로 묶는 단위라서, 결과 행 수를 확인한 뒤 확정하거나 없던 일로 되돌릴 수 있다. 연필로 쓰고 확인한 뒤에야 볼펜으로 덧쓰는 것과 같다. 다만 트랜잭션을 연 채 자리를 비우면 그 행을 고치려는 다른 요청이 끝없이 기다린다.

  지우는 명령은 셋이고 범위가 다르다. 조건에 맞는 행만 지우는 것, 구조는 두고 모든 행을 한 번에 비우는 것, 테이블 자체를 없애는 것이다. 되돌릴 수 있는지는 데이터베이스마다 달라서 Oracle은 뒤의 둘을 되돌리지 못하고 PostgreSQL은 트랜잭션 안이면 되돌린다.
</EasyIntro>

운영 DB에서 상품 하나의 가격을 고치려고 `UPDATE products SET price = 0`을 쳤다. 엔터를 누르고 나서야 `WHERE`가 없다는 걸 본다. 화면에는 `UPDATE 3`이 떠 있다. 한 줄을 고치려던 문장이 세 줄을 바꿨고, psql은 기본이 자동 커밋이라 이미 확정됐다.

행을 넣고 고치고 지우는 명령은 문법이 짧다. 그래서 잘못 쳤을 때 무슨 일이 생기는지, 어디까지 되돌릴 수 있는지를 함께 알아야 한다. 테이블을 만드는 과정은 [SQL 기본 명령어 글](/posts/sql-basics)에서, 행을 골라 읽는 방법은 [SELECT와 NULL 글](/posts/sql-select-where-null)에서 다뤘다. 이 글은 그다음, 데이터를 바꾸는 쪽이다. 기준은 Ubuntu 24.04의 PostgreSQL 16(16.15)이고 Oracle과 SQL Server의 동작은 직접 돌려 보지 못해 글로만 적었다.

## 이어서 쓰는 작은 쇼핑몰

[SQL 기본 명령어 글](/posts/sql-basics)에서 만든 회원, 상품, 주문 테이블을 그대로 쓴다. 처음부터 따라 하려면 아래를 먼저 돌린다.

```sql
-- 회원
CREATE TABLE users (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- 1, 2, 3 ... 자동으로 매긴다
  email      varchar(100) NOT NULL UNIQUE,                    -- 비어 있으면 안 되고, 겹치면 안 된다
  name       varchar(50)  NOT NULL,
  phone      varchar(20),                                     -- 없어도 된다 (NULL 허용)
  created_at timestamptz  NOT NULL DEFAULT now()              -- 안 넣으면 지금 시각
);

-- 상품
CREATE TABLE products (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  varchar(100) NOT NULL,
  price numeric(10, 0) NOT NULL CHECK (price >= 0),          -- 음수 가격은 막는다
  stock integer NOT NULL DEFAULT 0 CHECK (stock >= 0)
);

-- 주문: 누가(user_id) 무엇을(product_id) 몇 개(quantity) 샀나
CREATE TABLE orders (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    bigint NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  product_id bigint REFERENCES products (id) ON DELETE SET NULL,
  quantity   integer NOT NULL CHECK (quantity > 0),
  status     varchar(20) NOT NULL DEFAULT 'pending',          -- pending, paid, delivered, cancelled
  ordered_at timestamptz NOT NULL DEFAULT now()
);
```

```sql
INSERT INTO users (email, name, phone, created_at) VALUES
  ('kim@example.com',  'kim',  '010-1111-2222', '2026-10-01 09:00+09'),
  ('lee@example.com',  'lee',  NULL,            '2026-10-02 10:30+09'),
  ('park@example.com', 'park', '010-3333-4444', '2026-10-03 14:10+09'),
  ('choi@example.com', 'choi', NULL,            '2026-10-05 20:45+09');

INSERT INTO products (name, price, stock) VALUES
  ('무선 이어폰', 39000, 10),
  ('충전 케이스', 15000, 0),
  ('이어팁',      5000, 120);

INSERT INTO orders (user_id, product_id, quantity, status, ordered_at) VALUES
  (1, 1, 1, 'delivered', '2026-10-06 11:00+09'),
  (1, 3, 2, 'delivered', '2026-10-06 11:00+09'),
  (2, 2, 1, 'paid',      '2026-10-08 20:15+09'),
  (3, 1, 1, 'cancelled', '2026-10-09 08:40+09'),
  (1, 2, 1, 'pending',   '2026-10-12 23:05+09');
```

아래 출력의 번호는 그 글을 따라온 상태라 중간이 비어 있다. 그 글에서 제약 조건을 일부러 어겨 본 INSERT들이 실패하면서 회원 번호 5, 6과 상품 번호 4를 이미 써 버렸기 때문이다. 시퀀스는 한 번 나눠 준 번호를 실패해도 돌려받지 않는다. 위 SQL만 돌리고 시작하면 번호가 이 글과 다르게 나온다.

## 행 넣기와 있으면 고치기

`INSERT`는 컬럼 목록과 값 목록을 짝지어 쓴다. 컬럼 목록을 빼고 `INSERT INTO users VALUES (...)`로 쓸 수도 있지만, 테이블에 컬럼이 하나 추가되는 순간 깨진다. 컬럼 목록은 늘 적는다. 적지 않은 컬럼에는 `DEFAULT` 값이, 기본값도 없으면 NULL이 들어간다.

```sql
INSERT INTO users (email, name) VALUES ('jung@example.com', 'jung')
RETURNING id, name, created_at;
```

```text
 id | name |          created_at
----+------+-------------------------------
  7 | jung | 2026-10-17 11:58:19.114288+09
(1 row)

INSERT 0 1
```

기본 명령어 글에서 실패한 INSERT 두 번이 5, 6번을 써 버려서 jung은 7번이 됐다. `created_at`은 넣지 않았으니 `DEFAULT now()`가 채웠다.

자주 만나는 요구가 "있으면 고치고, 없으면 넣어라"다. 이걸 UPSERT라고 부른다. 먼저 `SELECT`로 있는지 보고 `INSERT`나 `UPDATE`를 고르면, 두 요청이 동시에 "없네"를 보고 둘 다 넣으려다 한쪽이 중복 에러를 맞는다. 아래 그림에서 다음을 누르면 두 요청이 어떻게 엇갈리는지 보인다.

PostgreSQL은 `INSERT ... ON CONFLICT`로 이 판단을 문장 하나 안에서 끝낸다.

```sql
-- 이메일이 겹치면 전화번호만 새 값으로 바꾼다
INSERT INTO users (email, name, phone) VALUES ('kim@example.com', 'kim', '010-9999-0000')
ON CONFLICT (email) DO UPDATE SET phone = EXCLUDED.phone   -- EXCLUDED: 넣으려던 행
RETURNING id, email, phone;

-- 겹치면 아무것도 안 한다
INSERT INTO users (email, name) VALUES ('kim@example.com', 'kim')
ON CONFLICT (email) DO NOTHING
RETURNING id;
```

```text
 id |      email      |     phone
----+-----------------+---------------
  1 | kim@example.com | 010-9999-0000
(1 row)

INSERT 0 1

 id
----
(0 rows)

INSERT 0 0
```

`ON CONFLICT (email)`의 괄호 안에는 유니크 제약이나 유니크 인덱스가 걸린 컬럼만 쓸 수 있다. 충돌을 판단할 기준이 있어야 하기 때문이다. MySQL은 같은 일을 `INSERT ... ON DUPLICATE KEY UPDATE phone = VALUES(phone)`으로 한다. 8.0.20부터 `VALUES()` 함수는 폐기 예정이 되어 `INSERT ... VALUES (...) AS new ON DUPLICATE KEY UPDATE phone = new.phone`처럼 별칭을 쓰는 방식을 권한다. MySQL은 충돌 컬럼을 지정하지 않고, 테이블의 모든 유니크 키 중 하나라도 겹치면 UPDATE로 간다. 유니크 키가 여러 개인 테이블에서는 엉뚱한 행이 고쳐질 수 있다.

표준 SQL에는 `MERGE`가 있다. 다른 테이블(원본)의 행을 대상 테이블에 맞춰 넣거나 고친다. Oracle과 SQL Server에서 오래 써 온 문법이고 SQLD에 나온다. PostgreSQL은 15부터 지원한다. 입고 목록을 상품 테이블에 반영해 본다.

```sql
CREATE TABLE incoming_stock (name varchar(100) PRIMARY KEY, price numeric(10,0), stock integer);
INSERT INTO incoming_stock VALUES ('이어팁', 5000, 200), ('케이블', 9000, 50);

MERGE INTO products AS p
USING incoming_stock AS s
  ON p.name = s.name                      -- 이 조건으로 짝을 찾는다
WHEN MATCHED THEN                         -- 짝이 있으면 고친다
  UPDATE SET stock = s.stock
WHEN NOT MATCHED THEN                     -- 없으면 넣는다
  INSERT (name, price, stock) VALUES (s.name, s.price, s.stock);

SELECT * FROM products ORDER BY id;
```

```text
MERGE 2

 id |    name     | price | stock
----+-------------+-------+-------
  1 | 무선 이어폰 | 39000 |    10
  2 | 충전 케이스 | 15000 |    30
  3 | 이어팁      |  5000 |   200
  5 | 케이블      |  9000 |    50
(4 rows)
```

이어팁은 짝이 있어서 재고만 200으로 바뀌었고, 케이블은 새로 들어갔다. 충전 케이스 재고 30은 다음 절의 `UPDATE`로 미리 바꿔 둔 값이다. 케이블이 4번이 아니라 5번인 건 기본 명령어 글에서 실패한 '불량 상품'이 4번을 썼기 때문이다. PostgreSQL의 `MERGE`는 동시에 같은 행을 넣는 요청이 있으면 유니크 위반이 날 수 있다. 한 행씩 들어오는 요청의 UPSERT는 `ON CONFLICT`가 더 안전하고, `MERGE`는 배치로 테이블 두 개를 맞출 때 쓴다.

## 고치고 지우기 전에 BEGIN부터

`UPDATE`는 `SET`으로 바꿀 값을, `WHERE`로 바꿀 행을 정한다. `DELETE`는 `WHERE`에 맞는 행을 지운다.

```sql
UPDATE products SET stock = stock + 30 WHERE id = 2 RETURNING id, name, stock;  -- 충전 케이스 30개 입고
UPDATE orders SET status = 'paid' WHERE id = 5;                                  -- 5번 주문 결제 완료
```

```text
 id |    name     | stock
----+-------------+-------
  2 | 충전 케이스 |    30
(1 row)

UPDATE 1
UPDATE 1
```

`UPDATE 1`의 숫자가 바뀐 행 수다. 한 행만 바꾸려 했는데 이 숫자가 크면 `WHERE`가 잘못된 것이다. 가장 무서운 건 `WHERE`를 빠뜨린 경우다. 문법상 아무 문제가 없어서 DB는 그냥 실행한다.

```sql
BEGIN;
UPDATE products SET price = 0;   -- WHERE를 빠뜨렸다
SELECT id, name, price FROM products ORDER BY id;
ROLLBACK;                        -- 트랜잭션 안이라 되돌릴 수 있다
SELECT id, name, price FROM products ORDER BY id;
```

```text
UPDATE 3

 id |    name     | price
----+-------------+-------
  1 | 무선 이어폰 |     0
  2 | 충전 케이스 |     0
  3 | 이어팁      |     0
(3 rows)

ROLLBACK

 id |    name     | price
----+-------------+-------
  1 | 무선 이어폰 | 39000
  2 | 충전 케이스 | 15000
  3 | 이어팁      |  5000
(3 rows)
```

<Callout kind="warning" title="운영 DB에서 UPDATE나 DELETE를 칠 때">
psql은 기본이 자동 커밋이라 `BEGIN` 없이 친 `UPDATE`는 엔터를 누르는 순간 확정된다. 손으로 고칠 때는 먼저 같은 `WHERE`로 `SELECT count(*)`를 돌려 몇 행인지 보고, `BEGIN;`을 친 다음 `UPDATE`를 실행해 결과 행 수(`UPDATE 1`)를 확인하고, 맞을 때만 `COMMIT;`, 아니면 `ROLLBACK;`한다. `\set ON_ERROR_ROLLBACK interactive`와 함께 `~/.psqlrc`에 `\set AUTOCOMMIT off`를 넣어 두면 매번 `BEGIN`을 치지 않아도 된다. 이미 커밋해 버렸다면 되돌리는 방법은 백업이나 PITR(시점 복구)뿐이다. 트랜잭션을 열어 둔 채 자리를 뜨면 그 행의 잠금이 계속 남아 다른 요청이 기다리니, 확인이 끝나면 바로 닫는다.
</Callout>

`DELETE`도 같다. `DELETE FROM orders;`는 주문을 전부 지우고 `DELETE 6`을 돌려준다. `BEGIN` 안이었다면 `ROLLBACK`으로 돌아온다.

## COMMIT, ROLLBACK, SAVEPOINT로 묶고 되돌리기

트랜잭션은 여러 문장을 "전부 되거나 전부 안 되거나"로 묶는 단위다. 주문을 넣고 재고를 빼는 두 일은 하나만 되면 안 된다. `BEGIN`으로 시작해서 `COMMIT`으로 확정하거나 `ROLLBACK`으로 취소한다. `SAVEPOINT`는 트랜잭션 중간에 꽂는 책갈피다. `ROLLBACK TO SAVEPOINT 이름`으로 그 지점까지만 되돌리고 트랜잭션은 이어 간다.

실제로 돌린 출력은 이렇다. 이어팁 재고는 앞의 `MERGE`로 200이 된 상태다.

```sql
BEGIN;
INSERT INTO orders (user_id, product_id, quantity) VALUES (4, 3, 3) RETURNING id;
SAVEPOINT before_stock;
UPDATE products SET stock = stock - 300 WHERE id = 3;
ROLLBACK TO SAVEPOINT before_stock;
UPDATE products SET stock = stock - 3 WHERE id = 3 RETURNING id, stock;
COMMIT;
```

```text
 id
----
  8
(1 row)

INSERT 0 1
SAVEPOINT
ERROR:  new row for relation "products" violates check constraint "products_stock_check"
DETAIL:  Failing row contains (3, 이어팁, 5000, -100).
ROLLBACK
 id | stock
----+-------
  3 |   197
(1 row)

UPDATE 1
COMMIT
```

`SAVEPOINT` 없이 트랜잭션 안에서 에러가 나면 PostgreSQL은 그 트랜잭션을 통째로 실패 상태로 만든다. 이후의 문장은 전부 거절되고, `COMMIT`을 쳐도 실제로는 `ROLLBACK`이 된다.

```sql
BEGIN;
UPDATE products SET stock = stock - 1 WHERE id = 1;
INSERT INTO orders (user_id, product_id, quantity) VALUES (99, 1, 1);  -- 없는 회원
SELECT stock FROM products WHERE id = 1;
COMMIT;
```

```text
UPDATE 1
ERROR:  insert or update on table "orders" violates foreign key constraint "orders_user_id_fkey"
DETAIL:  Key (user_id)=(99) is not present in table "users".
ERROR:  current transaction is aborted, commands ignored until end of transaction block
ROLLBACK
```

`COMMIT`의 응답이 `ROLLBACK`이다. 앞의 `UPDATE`도 함께 취소됐다. 응용 코드에서 에러를 잡고 같은 트랜잭션으로 계속 쿼리를 보내면 이 에러를 만난다. Oracle과 MySQL은 실패한 문장만 취소하고 트랜잭션은 이어 가는 방식이라, 다른 DB에서 넘어온 코드가 PostgreSQL에서 이 에러를 자주 낸다.

트랜잭션이 언제 시작되는지도 DB마다 다르다. PostgreSQL과 MySQL, SQL Server는 기본이 자동 커밋이다. `BEGIN`(SQL Server는 `BEGIN TRAN`)을 치지 않으면 문장 하나하나가 각자 트랜잭션이 되어 바로 커밋된다. Oracle은 첫 DML을 실행하는 순간 트랜잭션이 저절로 시작되고, `COMMIT`이나 `ROLLBACK`을 칠 때까지 이어진다. SQL*Plus 같은 도구에서 `UPDATE`를 하고 커밋하지 않은 채 접속을 끊었을 때 어떻게 처리되는지는 도구 설정에 따라 다르니, Oracle에서는 늘 명시적으로 끝낸다. 동시에 여러 트랜잭션이 같은 행을 건드릴 때 생기는 일은 [트랜잭션과 격리 수준 글](/posts/db-transaction-isolation)에서 이어서 본다.

## DELETE, TRUNCATE, DROP은 지우는 범위가 다르다

셋 다 "지운다"인데 지우는 대상과 되돌릴 수 있는지가 다르다. `DELETE`는 행을 하나씩 지우는 DML이다. `TRUNCATE`는 테이블 구조는 남기고 행을 한 번에 비우는 DDL이다. `DROP`은 테이블 자체를 없애는 DDL이다. 실습용 로그 테이블로 차이를 본다.

```sql
CREATE TABLE logs (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, msg text);
INSERT INTO logs (msg) VALUES ('a'), ('b'), ('c');

BEGIN;
TRUNCATE logs;
SELECT count(*) FROM logs;   -- 0
ROLLBACK;
SELECT count(*) FROM logs;   -- 다시 3
```

```text
TRUNCATE TABLE
 count
-------
     0
(1 row)

ROLLBACK
 count
-------
     3
(1 row)
```

PostgreSQL에서는 `TRUNCATE`도 트랜잭션 안에서 되돌아온다. Oracle에서는 안 된다. Oracle의 `TRUNCATE`는 DDL이라 실행 전후로 자동 커밋이 일어나고, 되돌릴 방법이 없다. SQLD 문제에서 "TRUNCATE는 ROLLBACK할 수 없다"는 Oracle 기준이다. SQL Server는 명시적 트랜잭션(`BEGIN TRAN`) 안에서 실행한 `TRUNCATE`를 `ROLLBACK`할 수 있다.

자동 번호도 다르게 다룬다. PostgreSQL의 `TRUNCATE`는 기본으로 번호를 이어 가고, `RESTART IDENTITY`를 붙여야 1부터 다시 센다.

```sql
TRUNCATE logs;
INSERT INTO logs (msg) VALUES ('d') RETURNING id;   -- 4
TRUNCATE logs RESTART IDENTITY;
INSERT INTO logs (msg) VALUES ('e') RETURNING id;   -- 1
```

```text
 id
----
  4
(1 row)

 id
----
  1
(1 row)
```

MySQL과 SQL Server의 `TRUNCATE`는 자동 증가 값을 처음으로 되돌린다. `DELETE`로 다 지우면 어느 DB든 번호는 이어진다.

다른 테이블이 외래 키로 가리키는 테이블은 `TRUNCATE`가 거절된다. `DELETE`는 행마다 외래 키를 검사하지만, `TRUNCATE`는 행을 하나씩 보지 않으니 아예 막는다.

```sql
TRUNCATE users;
```

```text
ERROR:  cannot truncate a table referenced in a foreign key constraint
DETAIL:  Table "orders" references "users".
HINT:  Truncate table "orders" at the same time, or use TRUNCATE ... CASCADE.
```

`DROP`도 같은 이유로 거절된다.

```sql
DROP TABLE products;
```

```text
ERROR:  cannot drop table products because other objects depend on it
DETAIL:  constraint orders_product_id_fkey on table orders depends on table products
HINT:  Use DROP ... CASCADE to drop the dependent objects too.
```

`DROP TABLE products CASCADE`는 `orders`를 지우지 않는다. `orders`에 걸린 외래 키 제약만 없앤다. 행 삭제의 `ON DELETE CASCADE`와 이름만 같고 하는 일이 다르다. 그래도 제약이 조용히 사라지니 쓰기 전에 무엇이 지워지는지 확인한다.

PostgreSQL은 `DROP`까지 트랜잭션 안에서 되돌린다. 테이블 생성과 삭제도 트랜잭션 로그에 남기 때문이다.

```sql
BEGIN;
DROP TABLE logs;
\dt          -- logs가 없다
ROLLBACK;
\dt          -- logs가 돌아왔다
```

```text
          List of relations
 Schema |   Name   | Type  |  Owner
--------+----------+-------+----------
 public | logs     | table | postgres
 public | orders   | table | postgres
 public | products | table | postgres
 public | users    | table | postgres
(4 rows)
```

그래서 PostgreSQL에서는 스키마 변경(마이그레이션) 여러 개를 트랜잭션 하나로 묶어서, 중간에 실패하면 전부 되돌릴 수 있다. Oracle과 MySQL은 DDL마다 자동 커밋이 일어나서, 마이그레이션이 중간에 실패하면 반쯤 바뀐 상태가 남는다. 또 Oracle에서 `UPDATE`를 하고 커밋하지 않은 채 `CREATE TABLE`을 치면, 그 `UPDATE`까지 함께 커밋된다. SQLD에 자주 나오는 함정이다.

세 명령을 비교하면 이렇다. 시험에서 표로 외우는 내용이라 한 번 정리한다.

| | DELETE | TRUNCATE | DROP |
|---|---|---|---|
| 분류 | DML | DDL | DDL |
| 지우는 것 | 조건에 맞는 행 | 모든 행 (구조는 남음) | 테이블 자체 |
| WHERE | 쓸 수 있다 | 없다 | 없다 |
| 되돌리기 | 커밋 전이면 된다 | PG·SQL Server는 트랜잭션 안에서 된다, Oracle은 안 된다 | PG·SQL Server는 된다, Oracle은 안 된다 |
| 행 단위 트리거 | 실행된다 | 실행되지 않는다 | 실행되지 않는다 |
| 속도 | 행마다 기록해서 느리다 | 파일을 통째로 비워서 빠르다 | 빠르다 |

속도 차이에는 이유가 있다. `DELETE`는 행마다 삭제 표시를 하고 트랜잭션 로그(WAL)에 남긴다. PostgreSQL에서는 지운 행이 디스크에 그대로 남았다가 `VACUUM`이 치워야 공간이 재사용되니, 큰 테이블을 `DELETE`로 비우면 파일 크기는 줄지 않는다. `TRUNCATE`는 테이블 파일을 새 빈 파일로 바꿔 끼워서 행 수와 상관없이 순식간에 끝나고 공간도 바로 돌려준다. 대신 PostgreSQL의 `TRUNCATE`는 가장 강한 잠금(ACCESS EXCLUSIVE)을 잡는다. 실행되는 동안 그 테이블은 `SELECT`도 기다린다. 운영 중인 테이블에 칠 때는 이 잠금이 오래 열린 트랜잭션 뒤에 줄 서지 않게 `SET lock_timeout = '3s'`를 먼저 걸어 둔다.

## 열어 둔 트랜잭션이 다른 요청을 붙잡을 때

앞의 경고 상자에서 "트랜잭션을 열어 둔 채 자리를 뜨면 잠금이 남는다"고 했다. 현장에서는 이게 이렇게 보인다. 누군가 데이터를 손으로 고치려고 `BEGIN`과 `UPDATE`를 치고 확인하다가 회의에 들어갔다. 그 사이 주문 API가 같은 상품의 재고를 빼려다 멈추고, 응답 시간이 타임아웃까지 늘어난다. 앱 로그에는 에러가 없다. 요청이 끝나지 않았을 뿐이다.

이럴 때 DB에서 먼저 보는 곳은 `pg_stat_activity`다. 지금 접속한 세션마다 한 줄씩 상태를 보여 준다. 아래는 두 세션을 띄워 같은 상황을 만든 뒤 세 번째 세션에서 본 결과다. 손으로 고치는 세션은 `application_name`을 `manual_fix`로, 주문 API 쪽은 `order_api`로 붙였다.

```sql
-- 누가 누구를 막고 있나
SELECT pid, application_name, state, wait_event_type, pg_blocking_pids(pid) AS blocked_by
FROM pg_stat_activity
WHERE datname = current_database() AND pid <> pg_backend_pid()
ORDER BY pid;
```

```text
 pid  | application_name |        state        | wait_event_type | blocked_by
------+------------------+---------------------+-----------------+------------
 5306 | manual_fix       | idle in transaction | Client          | {}
 5311 | order_api        | active              | Lock            | {5306}
(2 rows)
```

`state`가 `idle in transaction`이면 트랜잭션을 연 채 아무것도 하지 않고 있다는 뜻이다. `order_api`는 `active`인데 `wait_event_type`이 `Lock`이다. 일을 하는 게 아니라 잠금을 기다리는 중이고, `blocked_by`가 그 상대(5306)를 가리킨다. 막고 있는 세션의 주인을 찾아 `COMMIT`이나 `ROLLBACK`을 부탁하는 게 먼저다. 연락이 안 되면 그 세션을 끊는다. 끊긴 세션의 트랜잭션은 롤백된다.

```sql
SELECT pg_terminate_backend(5306);   -- 5306 세션을 끊는다. 하던 트랜잭션은 롤백된다
```

```text
 pg_terminate_backend
----------------------
 t
(1 row)
```

다음부터 같은 일이 생기지 않게 하는 설정은 둘이다. 손으로 고치는 세션에는 `lock_timeout`을 걸어, 내가 남을 오래 기다리지 않게 한다. 기다림이 3초를 넘으면 내 문장이 에러로 끝난다.

```sql
SET lock_timeout = '3s';
UPDATE products SET price = 40000 WHERE id = 1;   -- 다른 세션이 이 행을 잡고 있다
```

```text
ERROR:  canceling statement due to lock timeout
CONTEXT:  while updating tuple (0,1) in relation "products"
```

반대로 내가 남을 붙잡지 않게 하려면 `idle_in_transaction_session_timeout`을 건다. 트랜잭션을 연 채 정해진 시간 동안 아무것도 안 하면 DB가 세션을 끊는다. 5초로 걸고 `UPDATE` 뒤에 7초를 쉬었다가 다음 문장을 보냈다.

```sql
SET idle_in_transaction_session_timeout = '5s';
BEGIN;
UPDATE products SET stock = stock - 1 WHERE id = 1;
-- 7초 동안 아무것도 안 한다
SELECT stock FROM products WHERE id = 1;
```

```text
SET
BEGIN
UPDATE 1
FATAL:  terminating connection due to idle-in-transaction timeout
server closed the connection unexpectedly
	This probably means the server terminated abnormally
	before or while processing the request.
connection to server was lost
```

`UPDATE`는 롤백됐고 잠금도 풀렸다. 운영 계정에는 이 값을 역할 단위로 걸어 둘 수 있다(`ALTER ROLE 역할 SET idle_in_transaction_session_timeout = '5min'`). 응용 코드에서도 같은 일이 생긴다. 트랜잭션을 연 뒤 외부 API를 부르고 응답을 기다리면, 그동안 DB에서는 `idle in transaction` 세션이 행을 잡고 있다. 트랜잭션 안에서는 DB 일만 하고, 느린 바깥 호출은 트랜잭션 밖으로 뺀다.

## Oracle과 SQL Server에서는 이렇게 다르다

SQLD는 Oracle과 SQL Server를 기준으로 문제를 내고, 두 DB에서 결과가 달라지는 부분을 자주 묻는다. 이 글과 [SQL 기본 명령어 글](/posts/sql-basics), [SELECT와 NULL 글](/posts/sql-select-where-null)에 흩어 놓은 것을 한곳에 모은다.

트랜잭션 쪽이 가장 많이 나온다. Oracle은 DDL을 실행하면 그 앞뒤로 자동 커밋이 일어난다. 그래서 커밋 안 한 DML 뒤에 DDL을 치면 DML까지 확정되고, `TRUNCATE`와 `DROP`은 되돌릴 수 없다. SQL Server는 기본이 자동 커밋 모드라 문장마다 바로 확정되지만, `BEGIN TRAN`으로 연 트랜잭션 안에서는 DDL도 `ROLLBACK`된다. `SET IMPLICIT_TRANSACTIONS ON`을 켜면 Oracle처럼 첫 문장에서 트랜잭션이 저절로 시작된다. Oracle은 자동 커밋이 아니라서 첫 DML에서 트랜잭션이 시작되고 `COMMIT`이나 `ROLLBACK`까지 이어진다.

NULL 쪽은 둘이다. Oracle은 빈 문자열을 NULL로 저장한다. 정렬에서 Oracle은 NULL을 가장 큰 값, SQL Server는 가장 작은 값으로 본다.

문법 쪽은 컬럼 변경(Oracle `MODIFY`, SQL Server `ALTER COLUMN`), 이름 변경(Oracle `RENAME A TO B`, SQL Server `sp_rename`), 앞에서 n행 자르기(Oracle `ROWNUM`과 12c부터 `FETCH FIRST`, SQL Server `TOP`과 `OFFSET FETCH`), NULL 대체 함수(Oracle `NVL`, SQL Server `ISNULL`, 표준 `COALESCE`), 문자열 이어 붙이기(Oracle `||`, SQL Server `+`)가 나온다. 날짜 타입은 Oracle `DATE`가 시각까지 담는다는 것만 기억하면 대부분 풀린다.

## 바꾸기 전에 되돌릴 길부터

행을 넣는 `INSERT`, 고치는 `UPDATE`, 지우는 `DELETE`는 문법이 짧은 만큼 실수도 짧게 난다. 그래서 바꾸기 전에 `BEGIN`으로 되돌릴 길을 열고, 결과 행 수를 확인한 뒤에만 `COMMIT`한다. "있으면 고치고 없으면 넣기"는 조회와 쓰기를 나누지 말고 `ON CONFLICT` 한 문장으로 끝낸다. 지우는 명령 셋은 범위와 되돌릴 수 있는지가 다르고, 그 범위가 DB마다 다르다. 같은 행을 여러 트랜잭션이 동시에 고칠 때 생기는 일은 [트랜잭션과 격리 수준 글](/posts/db-transaction-isolation)에서 이어서 본다.

## 면접에서 나올 만한 질문

### DELETE, TRUNCATE, DROP의 차이를 설명해 주세요

`DELETE`는 조건에 맞는 행을 하나씩 지우는 DML이라 `WHERE`를 쓸 수 있고 커밋 전이면 되돌릴 수 있으며 행 단위 트리거도 실행된다. `TRUNCATE`는 구조는 남기고 모든 행을 한 번에 비우는 DDL이라 빠르고 공간도 바로 돌려준다. `DROP`은 테이블 자체를 없앤다. 되돌리기는 DB마다 다른데, Oracle은 DDL이 자동 커밋돼서 `TRUNCATE`와 `DROP`을 되돌릴 수 없고, PostgreSQL과 SQL Server는 트랜잭션 안에서라면 되돌린다.

### 트랜잭션 도중 에러가 나면 PostgreSQL은 어떻게 처리하나요?

그 트랜잭션 전체를 실패 상태로 만든다. 이후 문장은 "current transaction is aborted"로 거절되고, `COMMIT`을 보내도 `ROLLBACK`으로 끝난다. 실패한 문장만 취소하고 이어 가고 싶으면 그 앞에 `SAVEPOINT`를 꽂고 에러가 나면 `ROLLBACK TO SAVEPOINT`로 돌아간다. Oracle과 MySQL은 실패한 문장만 취소하는 방식이라, 다른 DB에서 옮겨 온 코드가 이 차이로 자주 깨진다.

### 있으면 수정하고 없으면 넣는 UPSERT는 어떻게 구현하나요?

조회한 뒤 결과에 따라 INSERT나 UPDATE를 고르면 동시 요청 두 개가 같이 "없다"고 보고 둘 다 넣으려다 한쪽이 실패한다. 판단과 쓰기를 문장 하나로 묶어야 한다. PostgreSQL은 `INSERT ... ON CONFLICT (유니크 컬럼) DO UPDATE`, MySQL은 `ON DUPLICATE KEY UPDATE`를 쓰고, 둘 다 유니크 제약이 충돌 판단의 기준이 된다. 표준 `MERGE`는 테이블끼리 맞추는 배치에 쓰고, PostgreSQL에서는 동시 삽입 상황에서 유니크 위반이 날 수 있다.

### WHERE 없는 UPDATE를 막으려면 어떻게 하나요?

손으로 고칠 때는 같은 `WHERE`로 `SELECT count(*)`를 먼저 돌려 행 수를 보고, `BEGIN` 안에서 `UPDATE`를 실행해 응답의 행 수(`UPDATE 1`)를 확인한 뒤에만 `COMMIT`한다. psql은 `\set AUTOCOMMIT off`로 매번 트랜잭션 안에서 시작하게 할 수 있다. 이미 커밋했다면 되돌리는 방법은 백업이나 시점 복구뿐이라, 예방이 사실상 유일한 대책이다.

### 운영 중인 테이블에 TRUNCATE를 칠 때 주의할 점은요?

PostgreSQL의 `TRUNCATE`는 가장 강한 잠금(ACCESS EXCLUSIVE)을 잡아서, 실행되는 동안 그 테이블은 `SELECT`도 기다린다. 앞에 오래 열린 트랜잭션이 있으면 `TRUNCATE`가 그 뒤에 줄을 서고, 그 뒤로 들어온 모든 요청이 다시 `TRUNCATE` 뒤에 줄을 선다. 그래서 `SET lock_timeout = '3s'`를 먼저 걸어 오래 기다리지 않게 한다. 다른 테이블이 외래 키로 가리키는 테이블은 `CASCADE` 없이는 비울 수 없다는 것도 알아 둔다.

### 트랜잭션을 열어 둔 채 오래 두면 어떤 문제가 생기나요?

그 트랜잭션이 고친 행의 잠금이 계속 남아서, 같은 행을 고치려는 다른 요청이 끝없이 기다린다. `pg_stat_activity`에서 `state`가 `idle in transaction`인 세션과 `pg_blocking_pids()`로 누가 누구를 막는지 찾는다. 막는 세션을 정리한 뒤에는 `idle_in_transaction_session_timeout`으로 오래 노는 트랜잭션을 DB가 끊게 하고, 트랜잭션 안에서 외부 API를 부르는 코드를 고친다.
