회원 가입 API가 가끔 8초씩 걸린다. 들여다보니 환영 메일을 보내는 SMTP 서버가 느린 날이었다. 메일은 가입이 끝난 뒤에 가도 되니 큐에 넣고 따로 도는 워커가 보내게 바꿨다. 응답은 50ms로 줄었다. 그런데 이번엔 배포할 때마다 환영 메일 몇 통이 사라진다. 큐에도 없고, 보낸 기록에도 없다.

메시지 큐는 "나중에 할 일"을 맡겨 두는 곳이다. 맡기는 쪽(프로듀서)과 처리하는 쪽(컨슈머)이 서로를 몰라도 되고, 처리하는 쪽이 잠깐 죽거나 느려도 일이 쌓여 있다가 처리된다. 이 글은 메시지 한 건이 큐에 들어가서 확실히 처리되고 지워지기까지를 따라간다. 꺼냈는데 처리 전에 죽으면 어떻게 되나, 왜 같은 메시지를 두 번 받나, 워커를 늘리면 순서는 어떻게 되나, 큐 길이 그래프에서 무엇을 읽어야 하나를 Redis 7.0과 PostgreSQL 16, Node.js 22로 직접 돌려 봤다. Amazon SQS의 동작도 같은 틀로 짚는다.

이 주제의 다른 글: 한 메시지를 여러 곳에 뿌리는 [발행·구독](/posts/pub-sub), 끝까지 실패하는 메시지를 따로 빼 두는 [데드 레터 큐](/posts/dead-letter-queue), 전달 보장 세 단계를 정리한 [메시지 전달 보장](/posts/message-delivery-semantics). Kafka와 RabbitMQ의 내부는 [Kafka 기초](/posts/kafka-basics)와 [RabbitMQ 기초](/posts/rabbitmq-basics)에 있다.

## 요청 안에서 끝내지 않아도 되는 일

큐가 없을 때 가입 API는 메일 서버를 직접 부른다. 메일 서버가 느리면 가입이 느리고, 메일 서버가 죽으면 가입이 실패한다. 가입과 메일은 사실 성공과 실패를 함께할 이유가 없는데 한 요청에 묶여 있어서 그렇다.

큐를 사이에 두면 API는 "메일 보낼 것" 한 줄을 넣고 바로 응답한다. 워커는 자기 속도로 꺼내 처리한다. 아래 그림에서 다음을 누르면 메시지가 API에서 큐를 거쳐 워커로 간다.

얻는 건 세 가지 정도다. 느린 일이 요청 시간에서 빠지고, 메일 서버가 잠깐 죽어도 작업이 큐에 남아 있다가 나중에 처리되며, 가입이 갑자기 몰려도 워커는 감당할 수 있는 속도로만 처리한다(몰린 만큼은 큐에 쌓인다). 대신 잃는 것도 있다. 사용자에게 "메일 보냈습니다"를 확정해서 말할 수 없고, 큐라는 저장소 하나를 더 운영해야 하며, 처음 장면처럼 일이 "어딘가에서" 사라질 수 있다.

## 꺼낸 순간 사라지는 큐

처음 만든 워커는 Redis 리스트에서 `BRPOP`으로 꺼내 보냈다. 리스트를 큐로 쓰는 기본 명령은 [Redis 기초](/posts/redis-basics)에 있다. 문제는 꺼내는 순간 그 메시지가 Redis에서 지워진다는 것이다. 보내기 전에 워커가 죽으면 메시지는 워커 메모리에만 있다가 같이 사라진다. 배포는 워커를 죽이는 일이다.

일부러 세 번째 메일을 보내다 죽는 워커를 돌려 봤다.

```bash
# 메일 작업 다섯 개를 넣는다
redis-cli -p 6492 LPUSH queue:mail mail:1 mail:2 mail:3 mail:4 mail:5

# BRPOP으로 꺼내는 워커. mail:3을 꺼낸 직후 죽는다
node lossy.js mail:3

# 큐에 남은 것
redis-cli -p 6492 LRANGE queue:mail 0 -1
```

```text
5
took mail:1
sent mail:1
took mail:2
sent mail:2
took mail:3
crash while sending mail:3
mail:5
mail:4
```

`mail:3`은 큐에도 없고 보낸 기록에도 없다. 다시 워커를 띄우면 4와 5만 보낸다. 처음 장면의 "배포할 때마다 몇 통씩" 사라지던 메일이 이것이다. 배포 순간 처리 중이던 메시지 수만큼 사라진다.

## 처리했다고 말해야 지운다

고치는 방법은 꺼내는 것과 지우는 것을 두 단계로 나누는 것이다. 꺼낼 때는 "처리 중" 자리로 옮겨만 두고, 처리가 끝나면 컨슈머가 "끝났다"고 알려서 그때 지운다. 이 알림이 ack(확인 응답)다. 처리하지 못했다고 알리는 건 nack다.

Redis 리스트로는 `BLMOVE`(6.2부터, 그 전엔 `BRPOPLPUSH`)가 이 일을 한다. 큐의 오른쪽 끝에서 꺼내는 동시에 `processing` 리스트의 왼쪽에 넣는다. 한 명령이라 그 사이에 죽을 틈이 없다. 처리가 끝나면 `LREM`으로 `processing`에서 지우는 것이 ack다.

아래 그림에서 다음을 누르면 메시지가 두 리스트 사이를 옮겨 다닌다. 아래 칸은 각 시점에 두 리스트에 무엇이 들어 있는지다.

같은 시나리오를 이번엔 `BLMOVE` 워커로 돌렸다. 꺼낼 때 `queue:mail:deadline`이라는 정렬된 셋에 "이 시각까지 끝내겠다"는 마감을 함께 적는다(5초).

```bash
# BLMOVE로 꺼내 processing에 두는 워커. mail:3에서 죽는다
node reliable.js w1 mail:3

# 큐, 처리 중 목록, 마감 시각을 각각 본다
redis-cli -p 6492 LRANGE queue:mail 0 -1
redis-cli -p 6492 LRANGE queue:mail:processing 0 -1
redis-cli -p 6492 ZRANGE queue:mail:deadline 0 -1 WITHSCORES
```

```text
w1: took mail:2
w1: sent mail:2, ack
w1: took mail:3
w1: crash while sending mail:3
1) "mail:5"
2) "mail:4"

```

`mail:3`이 `processing`에 남아 있고, 마감 시각(밀리초 유닉스 시각)도 적혀 있다. 이제 누군가가 마감이 지난 것을 큐로 되돌려야 한다. 리퍼(reaper)라고 부르는 작은 프로세스가 주기적으로 이 일을 한다. 되돌리는 동작이 다른 워커의 ack와 엇갈리지 않게 Lua 스크립트 하나로 묶었다.

```lua
-- KEYS[1]=queue:mail, KEYS[2]=processing, KEYS[3]=deadline, ARGV[1]=지금 시각(ms)
local expired = redis.call('ZRANGEBYSCORE', KEYS[3], '-inf', ARGV[1])
for _, job in ipairs(expired) do
  if redis.call('LREM', KEYS[2], 1, job) == 1 then  -- 아직 처리 중 목록에 있으면
    redis.call('RPUSH', KEYS[1], job)                -- 꺼내는 쪽 끝에 되돌린다
  end
  redis.call('ZREM', KEYS[3], job)
end
return expired
```

```bash
# 마감 전에 돌리면 아무것도 안 옮긴다
node reaper.js

# 5초가 지난 뒤 다시 돌린다
sleep 5.2 && node reaper.js

# 새 워커를 띄운다
node reliable.js w2
```

```text
requeued: []
requeued: [ 'mail:3' ]
w2: took mail:3
w2: sent mail:3, ack
w2: took mail:4
w2: sent mail:4, ack
w2: took mail:5
w2: sent mail:5, ack
w2: queue empty, exit
```

`RPUSH`로 꺼내는 쪽 끝에 넣었으니 되돌린 3번이 가장 먼저 다시 나갔다. 이 구현에도 틈은 남아 있다. `BLMOVE`와 `ZADD` 사이에 워커가 죽으면 마감 없이 `processing`에만 남아서 리퍼가 영영 못 본다. 그래서 운영에서는 이런 큐를 직접 짜기보다 처음부터 확인 응답과 재전달을 서버가 관리하는 도구를 쓴다. Redis라면 스트림의 소비자 그룹이 그렇고([발행·구독](/posts/pub-sub)에서 다룬다), SQS·RabbitMQ·Kafka도 각자 방식으로 이걸 해 준다.

## 가시성 타임아웃: 죽은 워커의 몫을 되찾는 시계

방금 만든 "마감 시각"을 SQS는 가시성 타임아웃(visibility timeout)이라고 부른다. 컨슈머가 메시지를 받으면 큐는 그 메시지를 지우지 않고 정해진 시간 동안 다른 컨슈머에게 안 보이게 숨긴다. 그 안에 `DeleteMessage`(ack)가 오면 지우고, 안 오면 다시 보이게 해서 다른 컨슈머가 받게 한다. 리퍼를 따로 둘 필요 없이 큐가 시계를 들고 있는 셈이다.

같은 동작을 PostgreSQL 테이블로 만들면 메커니즘이 더 잘 보인다. `visible_at` 열이 "이 시각부터 꺼낼 수 있다"를 뜻한다. 꺼낼 때 지우지 않고 `visible_at`을 3초 뒤로 미루는 것이 가시성 타임아웃이다. `FOR UPDATE SKIP LOCKED`의 기본 동작은 [잠금과 교착 상태](/posts/db-locking-deadlock)에, 아웃박스 릴레이에 쓰는 모양은 [규모별 DB 구조](/posts/db-architecture-by-scale)에 있다. 여기서 다른 점은 잠금을 처리하는 내내 들고 있지 않는다는 것이다. 잠금은 꺼내는 순간에만 쓰고, 처리 중이라는 표시는 `visible_at`이 맡는다. 그래야 메일 하나 보내는 동안 트랜잭션을 열어 둘 필요가 없다. SMTP 응답을 기다리는 8초 내내 트랜잭션을 열어 두면 커넥션 하나가 묶이고, 오래 열린 트랜잭션은 VACUUM이 죽은 튜플을 치우지 못하게 막는다.

```sql
CREATE TABLE jobs (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  queue      text        NOT NULL,
  payload    jsonb       NOT NULL,
  visible_at timestamptz NOT NULL DEFAULT now(),  -- 이 시각부터 꺼낼 수 있다
  attempts   int         NOT NULL DEFAULT 0,      -- 몇 번 꺼내 갔나
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX jobs_ready ON jobs (queue, visible_at, id);
```

```sql
-- 꺼내기: 보이는 것 하나를 잠그고, 3초 동안 숨기고, 횟수를 올린다
UPDATE jobs
   SET visible_at = now() + interval '3 seconds',
       attempts   = attempts + 1
 WHERE id = (
   SELECT id FROM jobs
    WHERE queue = 'mail' AND visible_at <= now()
    ORDER BY id
    FOR UPDATE SKIP LOCKED   -- 다른 워커가 지금 잡은 줄은 건너뛴다
    LIMIT 1)
RETURNING id, payload->>'to' AS "to", attempts;

-- ack: 처리가 끝나면 지운다
DELETE FROM jobs WHERE id = $1;
```

세 건을 넣고, w1이 2번을 꺼낸 직후 죽게 했다. 죽은 직후 테이블을 보고, w2를 띄웠다.

```bash
# w1: 처리 200ms, 2번에서 죽는다
node pgworker.js w1 200 2

# 남은 작업과 숨겨진 상태
psql -h 127.0.0.1 -U v2mq -d v2mq_demo -c "SELECT id, payload->>'to' AS to, attempts, visible_at > now() AS hidden FROM jobs ORDER BY id"

# w2를 띄운다
node pgworker.js w2 200
```


2번은 `hidden = t`라서 w2가 먼저 3번을 가져갔다. 3초가 지난 3.5초에 2번이 다시 보였고, `attempts=2`로 w2에게 갔다. 왼쪽 시각은 첫 워커가 뜬 때부터 잰 초다.

## 같은 메시지를 두 번 받는 건 정상이다

가시성 타임아웃에는 반대쪽 함정이 있다. 큐는 컨슈머가 죽었는지, 아직 일하는 중인지 구별하지 못한다. 시간만 본다. 처리가 타임아웃보다 오래 걸리면 멀쩡히 일하는 중인 메시지가 다른 컨슈머에게도 간다.

w1의 처리 시간을 4.5초로 늘리고, 0.5초 뒤 w2를 띄웠다. 타임아웃은 그대로 3초다.

```bash
# w1은 느리고, w2는 0.5초 뒤에 뜬다
node pgworker.js w1 4500 & (sleep 0.5; node pgworker.js w2 300) & wait
```

```text
 0.1s w1: took job 1 (user1@example.com) attempts=1
 3.2s w2: took job 1 (user1@example.com) attempts=2
 3.5s w2: sent job 1, ack deleted=1
 4.7s w1: sent job 1, ack deleted=0
```

user1에게 메일이 두 통 갔다. w1의 ack가 `deleted=0`인 건 w2가 이미 지웠기 때문이다. 어느 컨슈머도 버그가 없는데 중복이 생겼다. 이게 "최소 한 번(at-least-once)" 전달이다. 큐는 잃어버리지 않는 대신 두 번 줄 수 있다고 약속한다. ack를 보냈는데 네트워크에서 응답이 끊겨 컨슈머가 다시 보내는 경우, 브로커가 장애 조치 중에 기록을 잃은 경우에도 같은 일이 생긴다. 세 가지 전달 보장의 차이와 "정확히 한 번"이 어디까지 가능한지는 [메시지 전달 보장](/posts/message-delivery-semantics)에 따로 정리돼 있다.

그래서 할 일은 둘이다. 하나는 타임아웃을 실제 처리 시간보다 넉넉하게 잡고, 오래 걸리는 작업은 처리하는 동안 주기적으로 타임아웃을 늘리는 것이다(하트비트). SQS에서는 `ChangeMessageVisibility`가 이 일을 한다. PostgreSQL 큐에서 1초마다 늘리게 바꿔서 같은 실험을 했다.

```sql
-- 처리하는 동안 1초마다 실행한다. attempts가 같을 때만, 즉 아직 내 것일 때만 늘린다
UPDATE jobs SET visible_at = now() + interval '3 seconds'
 WHERE id = $1 AND attempts = $2;
```

```text
 0.1s w1: took job 1 (user1@example.com) attempts=1
 1.1s w1: extend job 1 updated=1
 2.1s w1: extend job 1 updated=1
 3.1s w1: extend job 1 updated=1
 3.7s w2: idle, exit
 4.1s w1: extend job 1 updated=1
 4.6s w1: sent job 1, ack deleted=1
```

w2는 1번을 끝내 받지 못하고 할 일 없이 끝났다. `attempts = $2` 조건은 SQS의 receipt handle과 같은 역할이다. 내가 받은 뒤 누가 또 받아 갔다면 내 연장은 0줄을 바꾸고, 그걸 보고 내가 더 이상 주인이 아니라는 걸 안다. SQS도 지우거나 연장할 때 가장 최근에 받은 영수증을 써야 한다.

다른 하나는 컨슈머를 멱등하게 만드는 것이다. 하트비트를 넣어도 컨슈머가 GC로 멈추거나 네트워크가 끊기면 중복은 생긴다. 메시지마다 고유 ID를 두고, 처리한 ID를 기록해 두었다가 같은 ID가 오면 건너뛴다. 처리 결과와 그 기록을 한 트랜잭션에 넣어야 "처리는 했는데 기록은 못 한" 틈이 없다. 키 저장소를 만드는 방법은 [멱등성 키](/posts/idempotency-key)와 같다. 메일처럼 바깥으로 나가는 부수 효과는 받는 쪽(메일 발송 API)에도 멱등성 키를 넘길 수 있는지 확인한다.

## 실패를 알리는 nack

처리하다가 예외가 나면 컨슈머는 두 가지 중 하나를 한다. 아무 말 없이 두면 가시성 타임아웃이 지난 뒤 다시 나온다. 바로 다시 받게 하고 싶으면 타임아웃을 0으로 바꾼다(SQS의 `ChangeMessageVisibility` `VisibilityTimeout=0`, RabbitMQ의 `basic.nack` `requeue=true`). 이게 nack다.

바로 되돌리는 nack는 조심해서 쓴다. 메일 서버가 죽어서 실패한 거라면 1ms 뒤에 다시 받아도 또 실패한다. 컨슈머 열 대가 같은 메시지를 초당 수천 번 돌리면서 CPU만 태운다. 일시적인 실패는 지연을 두고 다시 보이게 한다. 시도 횟수에 따라 지연을 늘리는 방법(지수 백오프와 지터)은 [지수 백오프와 지터](/posts/exponential-backoff-jitter)에 있다. PostgreSQL 큐라면 `visible_at = now() + 지연`으로 돌려놓기만 하면 된다.

몇 번을 해도 실패하는 메시지(필수 필드가 빠진 JSON, 지워진 회원의 ID)는 언젠가 포기해야 한다. 안 그러면 영원히 돌아온다. 시도 횟수가 기준을 넘으면 따로 떼어 두는 곳이 [데드 레터 큐](/posts/dead-letter-queue)다.

## 경쟁하는 컨슈머

메일이 쌓이면 워커를 늘린다. 같은 큐를 여러 컨슈머가 나눠 받는 구조를 경쟁하는 컨슈머(competing consumers)라고 부른다. 메시지 하나는 컨슈머 하나에게만 간다. 이게 점대점(point-to-point) 큐의 성질이다. 한 메시지를 모두에게 보내는 쪽은 [발행·구독](/posts/pub-sub)이다.

이 구조 덕분에 워커는 상태 없이 몇 대든 띄울 수 있고, 한 대가 죽어도 다른 워커가 이어받는다. 오토스케일링도 쉽다. 큐 깊이를 보고 워커 수를 정하면 된다.

워커가 한 번에 몇 개를 받아 갈지는 따로 정한다. SQS는 `ReceiveMessage`의 `MaxNumberOfMessages`(최대 10), RabbitMQ는 prefetch(`basic.qos`)다. 한 번에 많이 받으면 왕복이 줄지만, 받아 놓고 처리 못 한 것들이 그 워커에 묶인다. 그 워커가 느리면 다른 워커는 놀고 있는데 그 몫은 기다린다. 처리 시간이 들쭉날쭉한 작업일수록 적게 받는다.

빈 큐를 계속 물어보는 것도 비용이다. SQS의 짧은 폴링은 빈 응답을 바로 돌려주므로, 빈 큐에 초당 몇 번씩 요청이 나가고 요청마다 요금이 붙는다. `WaitTimeSeconds`(최대 20초)를 주면 메시지가 올 때까지 연결을 붙잡고 기다린다(롱 폴링). Redis의 `BLMOVE`·`BRPOP`이 블로킹인 것과 같은 이유다.

## 워커를 늘리면 순서가 깨진다

큐는 들어온 순서대로 내준다. 그런데 처리가 끝나는 순서는 큐가 정하지 않는다. 주문 7번의 이벤트 세 개(생성, 결제, 배송)를 워커 둘이 나눠 처리하게 했다. 생성 처리만 300ms가 걸리게 했다.

```bash
# 워커 둘이 같은 큐에서 꺼낸다
node order.js
```

```text
  26ms w1 start order7:created
  26ms w2 start order7:paid
  77ms w2 done  order7:paid
  77ms w2 start order7:shipped
 128ms w2 done  order7:shipped
 327ms w1 done  order7:created
```

꺼낸 순서는 생성, 결제, 배송인데 끝난 순서는 결제, 배송, 생성이다. 결제 처리기가 "없는 주문"이라며 실패하거나, 배송 상태를 생성 상태가 덮어쓴다. 아래 그림은 두 워커의 진행을 시간 순으로 다시 보여 준다.

순서가 중요한 메시지를 다루는 방법은 몇 가지다. 가장 흔한 건 "전체 순서" 대신 "같은 키끼리의 순서"만 지키는 것이다. SQS FIFO 큐는 `MessageGroupId`가 같은 메시지를 한 번에 하나씩만 내준다. 앞 메시지가 ack되기 전에는 같은 그룹의 다음 메시지가 안 나가고, 다른 그룹은 동시에 처리된다. Kafka는 같은 키를 같은 파티션에 넣고 파티션 하나를 컨슈머 하나만 읽게 해서 같은 효과를 낸다([Kafka 기초](/posts/kafka-basics)). 주문 ID를 그룹 키로 쓰면 주문끼리는 병렬로, 한 주문 안에서는 차례로 처리된다.

이렇게 해도 대가가 있다. 한 그룹의 메시지 하나가 계속 실패하면 그 그룹 전체가 멈춘다(head-of-line blocking). 그래서 FIFO 큐에는 데드 레터 큐가 더 중요하다. 키 하나에 메시지가 몰리면 그 키는 한 워커 속도를 넘지 못한다.

아예 순서에 기대지 않게 만드는 방법도 있다. 메시지에 버전이나 발생 시각을 넣고, 컨슈머가 지금 저장된 것보다 오래된 이벤트는 버린다. 상태를 통째로 담은 메시지라면 마지막 것만 반영하면 되니 순서가 섞여도 결과가 같다. 결제 전에 배송이 오면 잠시 미뤄 두는(다시 지연시키는) 방법도 있다. 실무에서는 이 방법이 FIFO보다 더 자주 쓰인다. 같은 메시지가 두 번 오는 문제(앞 절)와 함께 풀리기 때문이다.

## 큐 깊이 그래프를 읽는 법

큐를 운영하면 가장 먼저 보는 지표가 큐 깊이(queue depth, 지금 쌓여 있는 메시지 수)다. 깊이는 "들어오는 속도 - 처리하는 속도"를 시간으로 쌓은 값이다. 깊이 숫자 하나보다 기울기가 더 많은 걸 말해 준다.

초당 대략 90개씩 넣고, 25ms짜리 워커 하나로 시작해 2초 뒤 둘을 더 붙였다. 0.5초마다 깊이와 가장 오래된 메시지의 나이를 찍었다. 프로듀서는 4초에 멈춘다.

```bash
# 리스트 오른쪽 끝(가장 오래된 것)의 enqueue 시각으로 나이를 잰다
node depth.js
```

```text
0.5s  depth= 29  oldest_age=287ms
1.0s  depth= 59  oldest_age=594ms
1.5s  depth= 89  oldest_age=892ms
2.0s  +2 workers
2.0s  depth=119  oldest_age=1201ms
2.5s  depth=108  oldest_age=1097ms
3.0s  depth= 98  oldest_age=984ms
3.5s  depth= 90  oldest_age=907ms
4.0s  depth= 77  oldest_age=798ms
4.5s  depth= 20  oldest_age=719ms
5.0s  depth=  0  oldest_age=0ms
```

워커가 하나일 때는 0.5초마다 30개씩 늘었다. 처리 속도가 들어오는 속도를 못 따라간다는 뜻이고, 이대로 두면 끝없이 쌓인다. 셋이 된 뒤에는 0.5초마다 10개쯤 줄었다. 처리 속도가 겨우 이긴다. 프로듀서가 멈춘 4초 이후에야 빠르게 빠졌다.

깊이와 함께 봐야 할 것이 가장 오래된 메시지의 나이다. 깊이 1000이 많은지 적은지는 처리 속도에 따라 다르지만, "가장 오래된 메일이 15분 전에 들어왔다"는 사용자 경험으로 바로 읽힌다. SQS는 CloudWatch에서 `ApproximateNumberOfMessagesVisible`(깊이), `ApproximateNumberOfMessagesNotVisible`(받아 가서 처리 중인 것), `ApproximateAgeOfOldestMessage`(가장 오래된 나이)를 준다. 알람은 나이에 거는 편이 오탐이 적다.

```bash
# 예시: SQS 큐의 깊이와 처리 중인 수를 본다
aws sqs get-queue-attributes \
  --queue-url https://sqs.ap-northeast-2.amazonaws.com/123456789012/mail \
  --attribute-names ApproximateNumberOfMessages ApproximateNumberOfMessagesNotVisible
```

```text
{
    "Attributes": {
        "ApproximateNumberOfMessages": "1182",
        "ApproximateNumberOfMessagesNotVisible": "40"
    }
}
```

위 출력은 예시다(실제 AWS 계정에서 돌린 값이 아니다). `NotVisible`이 40이라는 건 지금 40개가 컨슈머 손에 있다는 뜻이고, 워커 수 × 한 번에 받는 수와 비슷해야 정상이다. 워커는 다 놀고 있는데 이 값만 크면, 받아 간 뒤 ack도 nack도 안 하고 버리는 코드가 있다는 신호다. 이름처럼 근삿값이라 몇 개씩 흔들린다.

깊이에서 워커 수를 거꾸로 셈할 수도 있다. 지금 쌓인 것을 T초 안에 비우려면, 새로 들어오는 것까지 처리해야 하니 필요한 처리량은 `쌓인 수 / T + 들어오는 속도`다. 아래 함수를 완성해 보자. 워커 한 대의 처리량으로 나누고 올림한다.

    { args: [1200, 90, 37, 30], expected: 4, label: "위 실험과 비슷한 숫자" },
    { args: [10000, 0, 50, 100], expected: 2, label: "유입이 멈춘 뒤 남은 것만" },
  ]}
/>

두 번째 테스트가 중요하다. 밀린 게 없어도 유입 속도보다 처리량이 작으면 큐는 늘어난다. 워커를 늘릴 때는 바깥 의존성도 함께 본다. 워커 열 대가 같은 SMTP 서버나 DB를 동시에 두드리면 병목이 그쪽으로 옮겨 갈 뿐이다. 이런 경우엔 처리량 상한을 정해 두고 큐에 쌓이게 두는 편이 낫다. 큐가 받아 주는 동안 아래쪽 시스템을 지키는 이 성질은 [백프레셔](/posts/backpressure)와 같은 이야기다.

## 큐를 무엇으로 만드나

지금까지 Redis 리스트, PostgreSQL 테이블, SQS를 오갔다. 셋 다 같은 개념을 구현하지만 고르는 기준은 다르다.

PostgreSQL 테이블 큐는 이미 DB가 있고 처리량이 초당 수백 건 수준일 때 좋다. 가장 큰 장점은 업무 데이터와 같은 트랜잭션으로 작업을 넣을 수 있다는 것이다. 회원 행을 넣는 트랜잭션에 메일 작업도 함께 넣으면, 가입이 롤백될 때 메일 작업도 사라진다. 큐가 따로 있으면 "가입은 됐는데 큐에 넣기 전에 죽은" 틈을 [트랜잭셔널 아웃박스](/posts/microservices) 같은 장치로 메워야 한다. 대신 꺼낼 때마다 `UPDATE`와 `DELETE`가 일어나 죽은 튜플이 쌓이고, autovacuum이 따라가지 못하면 테이블과 인덱스가 부푼다([MVCC와 VACUUM](/posts/postgres-mvcc-vacuum)). 꺼내는 쿼리가 인덱스를 못 타면 더 빨리 무너진다. 예약 작업 20만 건(1시간 뒤에 보일 것) 사이에서 지금 보이는 5건을 찾는 쿼리를 인덱스 없이 돌렸다.

```bash
# 꺼내는 쿼리의 실행 계획을 본다
psql -h 127.0.0.1 -U v2mq -d v2mq_demo -f explain.sql
```

```text
 Limit (actual time=38.449..38.451 rows=1 loops=1)
   ->  LockRows (actual time=38.448..38.448 rows=1 loops=1)
         ->  Index Scan using jobs_pkey on jobs (actual time=38.383..38.383 rows=1 loops=1)
               Filter: ((queue = 'mail'::text) AND (visible_at <= now()))
               Rows Removed by Filter: 200000
 Planning Time: 0.424 ms
 Execution Time: 38.485 ms
```

`ORDER BY id`를 맞추려고 기본 키 인덱스를 처음부터 훑다가 조건에 안 맞는 20만 줄을 버렸다(`Rows Removed by Filter`). 워커 열 대가 이걸 초당 몇 번씩 돌리면 DB CPU가 큐 하나에 다 간다. `(queue, visible_at, id)` 인덱스를 만든 뒤다.

```text
 Limit (actual time=0.107..0.162 rows=1 loops=1)
   ->  LockRows (actual time=0.106..0.107 rows=1 loops=1)
         ->  Sort (actual time=0.077..0.077 rows=1 loops=1)
               Sort Key: id
               Sort Method: quicksort  Memory: 25kB
               ->  Index Scan using jobs_ready on jobs (actual time=0.041..0.043 rows=5 loops=1)
                     Index Cond: ((queue = 'mail'::text) AND (visible_at <= now()))
 Planning Time: 2.432 ms
 Execution Time: 0.212 ms
```

`Index Cond`로 보이는 5줄만 읽고 정렬했다. 38ms에서 0.2ms가 됐다. 처리가 끝난 행을 지우지 않고 `status = 'done'`으로 남기는 설계라면 `WHERE status = 'ready'` 같은 부분 인덱스를 쓴다.

Redis 리스트나 스트림은 처리량이 훨씬 높고 지연이 짧다. 대신 영속성은 설정에 달려 있다. AOF를 `everysec`로 두면 장애 때 마지막 1초 안쪽의 메시지를 잃을 수 있다([Redis 영속성](/posts/redis-persistence-ha)). 메모리가 차면 `maxmemory-policy`에 따라 큐 키가 축출될 수도 있으니, 큐를 담는 Redis에는 `noeviction`을 쓴다([Redis 메모리](/posts/redis-memory-eviction)). Node에서 이 위에 재시도, 지연, 락까지 얹은 라이브러리가 BullMQ이고, 동작은 [BullMQ 작업 큐](/posts/bullmq-job-queue)에서 따로 따라갔다.

SQS 같은 관리형 큐는 운영할 서버가 없고, 가시성 타임아웃·재전달·데드 레터 큐가 기본으로 있다. 표준 큐는 순서를 보장하지 않고 드물게 중복을 준다. FIFO 큐는 그룹별 순서와 5분 안의 중복 제거(`MessageDeduplicationId`)를 주는 대신 처리량 상한이 낮다. 메시지를 오래 보관하며 여러 번 다시 읽어야 하거나(재처리, 새 서비스가 과거 이벤트부터 읽기) 처리량이 매우 크면 Kafka 같은 로그가 맞고, 라우팅 규칙이 복잡하면 RabbitMQ가 맞다. 둘의 차이는 각 글에서 다룬다.

## 메시지가 사라지거나 쌓일 때 보는 순서

처음 장면처럼 배포 때마다 메시지가 사라지면, 컨슈머가 ack를 언제 보내는지부터 본다. 꺼내자마자 ack하는 코드(`autoAck: true`, SQS에서 받자마자 `DeleteMessage`, Kafka에서 처리 전에 오프셋 커밋)가 가장 흔한 원인이다. ack는 처리가 끝난 뒤에 보낸다. 그다음은 종료 처리다. 쿠버네티스는 Pod를 내릴 때 SIGTERM을 보내고 `terminationGracePeriodSeconds`(기본 30초) 뒤 SIGKILL을 보낸다. 워커는 SIGTERM을 받으면 새 메시지를 그만 받고, 손에 든 것을 끝내 ack한 뒤 나가야 한다. 처리 하나가 30초보다 길면 이 값을 늘린다.

같은 메시지가 두 번 처리됐다는 신고가 오면, 처리 시간 분포와 가시성 타임아웃을 나란히 본다. 처리 시간의 p99가 타임아웃에 가까우면 그게 원인이다. 메시지에 받은 횟수(`ApproximateReceiveCount`, 위 실험의 `attempts`)를 로그에 함께 남겨 두면 "2"가 찍힌 줄을 바로 찾을 수 있다. 타임아웃을 늘리기 전에 컨슈머가 멱등한지부터 확인한다. 타임아웃을 아무리 늘려도 중복은 0이 되지 않는다.

깊이가 계속 늘면 워커 수부터 늘리기 전에 워커 하나의 처리 시간이 늘었는지 본다. 처리 시간이 갑자기 늘었다면 원인은 대개 아래쪽 의존성(DB, 외부 API)이고, 워커를 늘리면 그쪽이 더 힘들어진다. 깊이는 그대로인데 같은 메시지 ID가 로그에 반복해서 찍히면 독이 든 메시지(poison message)가 돌고 있는 것이다. 이건 [데드 레터 큐](/posts/dead-letter-queue)로 뺀다. 깊이가 0인데 일이 안 되고 있다면 프로듀서가 엉뚱한 큐 이름에 넣고 있는지 확인한다. 개발 큐 URL이 운영 설정에 남아 있는 일이 의외로 흔하다.

## 잃지 않는 것과 두 번 하지 않는 것

큐는 일을 맡아 두는 곳이고, 맡은 일을 잃지 않으려면 "꺼내기"와 "지우기" 사이에 처리 중 상태를 둬야 한다. 그 상태를 언제 풀지 정하는 게 가시성 타임아웃이고, 시계로만 판단하니 같은 메시지가 두 번 갈 수 있다. 그래서 컨슈머는 멱등해야 하고, 순서가 필요하면 키별로만 지킨다. 다음 글인 [발행·구독](/posts/pub-sub)에서는 메시지 하나를 여러 서비스가 각자 받아야 할 때를 다룬다.

## 면접에서 나올 만한 질문

### 메시지 큐를 왜 쓰나요?

요청 안에서 끝낼 필요가 없는 일을 떼어 내서 응답을 빠르게 하고, 처리하는 쪽이 느리거나 죽어도 일을 잃지 않게 하려고 쓴다. 갑자기 몰린 요청을 큐가 받아 두고 워커가 감당할 수 있는 속도로 처리하니 아래쪽 시스템도 보호된다. 대신 결과를 바로 알 수 없고, 운영할 구성 요소가 늘며, 중복과 순서 문제를 컨슈머가 떠안는다.

### ack는 언제 보내야 하나요?

처리가 끝나고 그 결과가 저장된 뒤에 보낸다. 받자마자 보내면 처리 중에 죽었을 때 메시지가 사라진다(최대 한 번). 끝나고 보내면 ack 직전에 죽었을 때 다시 처리하게 되므로(최소 한 번) 컨슈머가 멱등해야 한다. 보통은 잃는 것보다 두 번 하는 게 고치기 쉬워서 뒤쪽을 고른다.

### 가시성 타임아웃은 무엇이고 얼마로 잡나요?

컨슈머가 받아 간 메시지를 다른 컨슈머에게 숨겨 두는 시간이다. 그 안에 ack가 없으면 다시 보이게 해서 죽은 컨슈머의 몫을 되찾는다. 처리 시간의 최댓값보다 넉넉히 잡고, 처리 시간이 들쭉날쭉하면 짧게 잡은 뒤 처리하는 동안 주기적으로 연장한다. 너무 짧으면 멀쩡히 일하는 중인 메시지가 중복 처리되고, 너무 길면 죽은 컨슈머의 메시지가 오래 묶인다.

### 컨슈머를 멱등하게 만들면 가시성 타임아웃 조정은 필요 없나요?

여전히 필요하다. 멱등하면 중복이 결과를 망치지 않을 뿐이고, 중복 처리에 드는 시간과 비용, 바깥으로 나간 부수 효과(메일, 푸시)는 그대로 남는다. 멱등성은 정확성을, 타임아웃과 하트비트는 효율을 지킨다. 둘 다 둔다.

### 워커를 여러 대 띄우면 순서는 어떻게 되나요?

큐가 내주는 순서는 유지돼도 처리가 끝나는 순서는 섞인다. 순서가 필요하면 전체 순서 대신 키별 순서를 지킨다. SQS FIFO의 메시지 그룹이나 Kafka의 파티션 키처럼 같은 키는 한 번에 하나씩 처리하고, 다른 키는 병렬로 처리한다. 아니면 이벤트에 버전을 넣어 오래된 이벤트를 무시하게 해서 순서에 기대지 않게 만든다.

### 큐 모니터링에서 무엇을 보나요?

깊이, 가장 오래된 메시지의 나이, 처리 중인 수, 처리 시간, 실패와 재시도 횟수, 데드 레터 큐 깊이를 본다. 깊이 숫자보다 기울기가 중요하고, 알람은 사용자 영향으로 바로 읽히는 가장 오래된 메시지의 나이에 거는 게 낫다. 깊이가 늘 때는 워커를 늘리기 전에 처리 시간과 아래쪽 의존성부터 확인한다.

### PostgreSQL 테이블을 큐로 써도 되나요?

처리량이 크지 않고 이미 PostgreSQL을 쓰고 있다면 좋은 선택이다. 업무 데이터와 같은 트랜잭션으로 작업을 넣을 수 있어 "저장은 됐는데 작업은 안 들어간" 틈이 없다. `FOR UPDATE SKIP LOCKED`로 꺼내고, 처리 중 상태는 잠금 대신 `visible_at` 같은 열로 표시해서 긴 트랜잭션을 피한다. 꺼내는 쿼리에 맞는 인덱스와 autovacuum 상태를 계속 봐야 하고, 처리량이 커지면 전용 브로커로 옮긴다.

### 배포할 때 메시지가 사라지지 않게 하려면?

ack를 처리 뒤로 옮기고, 워커가 SIGTERM을 받으면 새 메시지를 그만 받은 뒤 손에 든 것을 끝내고 나가게 한다. 처리 시간이 종료 유예 시간(쿠버네티스 기본 30초)보다 길면 유예 시간을 늘린다. 그래도 강제 종료되는 경우는 가시성 타임아웃이 메시지를 되살려 주므로, 결국 같은 메시지가 다시 와도 괜찮게 만드는 게 마지막 안전장치다.
