웨어하우스에 뷰가 340개 있다. 이름은 `v_sales_final`, `v_sales_final2`, `v_sales_final_new_kim` 같은 식이다. 대부분 다른 뷰를 다시 읽는 뷰라, 하나를 고치면 어디가 깨질지 아무도 모른다. 누군가 `v_orders_clean`에서 컬럼 하나를 지웠더니 다음 날 아침 대시보드 열두 개가 빈 화면이 됐다. 뷰 정의는 웨어하우스 콘솔에서 손으로 고쳤으니 이력도 없다.

dbt(data build tool)는 이 문제를 이렇게 푼다. 변환 하나를 SELECT 문 하나짜리 파일(모델)로 만들고, 다른 모델을 읽을 때 테이블 이름 대신 `ref()`를 쓰게 한다. dbt는 `ref()`를 모아 의존 그래프를 만들고, 그 순서대로 SQL을 웨어하우스에 보내 테이블이나 뷰를 만든다. 파일은 git에 있으니 리뷰와 이력이 생기고, 테스트와 문서도 같은 저장소에 붙는다.

원본을 먼저 웨어하우스에 넣고 그 안에서 변환하는 ELT 흐름 자체는 [ETL과 ELT](/posts/etl-vs-elt)에서, 웨어하우스를 원본·정제·쓰임새 층으로 나누는 법은 [데이터 웨어하우스 구조](/posts/data-warehouse-architecture)에서 다뤘다. dbt는 그 흐름에서 T(변환)만 맡는다. 데이터를 꺼내 오거나 옮기지 않는다. 이 글은 dbt Core 1.12.6과 dbt-duckdb 1.11.0으로 작은 쇼핑몰 프로젝트를 만들어 모델, `ref()`, 물질화 방식, 증분 모델, 스냅숏, 테스트를 직접 돌려 본다. 실행할 때 새 엔진(v2) 안내가 함께 찍히지만 여기서는 1.x 기준으로 쓴다. 버전마다 설정 키 이름이 조금씩 바뀌어 왔으니 쓰는 버전의 문서를 같이 본다.

## SELECT 하나가 모델 하나

설치는 어댑터 패키지 하나면 된다. 어댑터가 dbt Core를 같이 끌고 온다. DuckDB는 파일 하나짜리 DB라 웨어하우스 없이 연습하기 좋다.

```bash
# 가상 환경에 dbt Core와 DuckDB 어댑터를 설치한다
python3 -m venv venv && ./venv/bin/pip install dbt-duckdb
./venv/bin/dbt --version
```

```text
Core:
  - installed: 1.12.6
  - latest:    1.12.6 - Up to date!

Plugins:
  - duckdb: 1.11.0 - Up to date!
```

프로젝트는 설정 파일 두 개와 SQL 파일 몇 개다. `profiles.yml`은 어느 DB에 붙을지, `dbt_project.yml`은 폴더별 기본 설정을 적는다.

```yaml
# profiles.yml: 접속 정보. 운영에서는 홈 디렉터리(~/.dbt)에 두고 비밀 값은 환경 변수로 넣는다
shop:
  target: dev
  outputs:
    dev:
      type: duckdb
      path: shop.duckdb
      threads: 4
```

```yaml
# dbt_project.yml: staging 폴더 모델은 뷰로, marts 폴더 모델은 테이블로 만든다
name: shop
version: "1.0.0"
profile: shop
models:
  shop:
    staging:
      +materialized: view
    marts:
      +materialized: table
```

원본은 주문 다섯 줄과 회원 세 줄이다. 실제로는 수집 도구가 웨어하우스에 넣어 둔 테이블이겠지만, 여기서는 CSV를 `dbt seed`로 올렸다. seed는 국가 코드표처럼 작고 잘 안 바뀌는 기준표용이고, 원본 데이터를 seed로 넣지는 않는다.

```text
order_id,customer_id,status,amount,updated_at
1,101,paid,12000,2026-10-20 10:00:00
2,102,paid,8000,2026-10-20 11:30:00
3,101,refunded,25000,2026-10-21 09:10:00
4,103,paid,4000,2026-10-21 14:50:00
5,102,paid,30000,2026-10-21 18:20:00
```

모델은 SELECT 문이 든 `.sql` 파일이다. CREATE 문은 쓰지 않는다. 무엇으로 만들지는 dbt가 설정을 보고 감싼다.

```sql
-- models/staging/stg_orders.sql: 원본을 다듬기만 하는 층. 이름과 타입을 정리한다
select
    order_id,
    customer_id,
    status,
    amount,
    cast(updated_at as timestamp) as updated_at
from {{ ref('raw_orders') }}
```

```sql
-- models/marts/fct_daily_sales.sql: 쓰임새 층. 날짜·등급별 결제 매출
select
    cast(o.updated_at as date) as day,
    c.grade,
    count(*) as orders,
    sum(o.amount) as sales
from {{ ref('stg_orders') }} o
join {{ ref('stg_customers') }} c using (customer_id)
where o.status = 'paid'
group by 1, 2
```

`{{ ref('stg_orders') }}`가 이 글의 주인공이다. `dbt compile`로 보면 실제 테이블 이름으로 바뀐다.

```sql
-- target/compiled/shop/models/marts/fct_daily_sales.sql
select
    cast(o.updated_at as date) as day,
    c.grade,
    count(*) as orders,
    sum(o.amount) as sales
from "shop"."main"."stg_orders" o
join "shop"."main"."stg_customers" c using (customer_id)
where o.status = 'paid'
group by 1, 2
```

`ref()`가 하는 일은 두 가지다. 하나는 이름을 환경에 맞게 바꾸는 것이다. 개발자는 `dev_kim` 스키마에, 운영은 `analytics` 스키마에 만들게 설정해 두면 같은 SQL이 각자의 스키마를 가리킨다. 다른 하나가 더 중요하다. dbt는 SQL을 실행하기 전에 모든 파일의 `ref()`를 모아 누가 누구를 읽는지 그래프로 만든다. 테이블 이름을 직접 쓰면 이 그래프에 선이 빠진다. 손으로 쓴 `from analytics.stg_orders` 한 줄 때문에 순서가 틀어지고, 바뀐 모델의 영향 범위를 찾을 때도 그 선이 안 보인다.

이 그래프가 있으면 선택 문법으로 일부만 돌릴 수 있다. `+모델`은 그 모델과 조상 전부, `모델+`는 그 모델과 자손 전부다. 컬럼을 지우기 전에 `dbt ls --select stg_orders+`를 돌리면 영향을 받는 모델 목록이 나온다. 처음 장면의 "컬럼 하나 지웠더니 대시보드 열두 개"를 미리 막는 명령이다.

```bash
# stg_orders를 고치면 다시 만들어야 하는 모델들
dbt ls --select stg_orders+ --resource-type model
```

```text
shop.marts.fct_daily_sales
shop.marts.fct_orders
shop.staging.stg_orders
```

dbt가 아는 범위는 dbt 프로젝트 안까지다. 대시보드나 다른 팀의 파이썬 스크립트가 이 테이블을 읽는다는 건 모른다. exposures 설정으로 대시보드를 그래프 끝에 적어 둘 수는 있지만, 사람이 적어야 한다. 프로젝트 바깥까지 이어지는 계보를 모으는 법은 [메타데이터와 데이터 계보](/posts/data-catalog-lineage)에서 이어서 본다.

그래프는 되돌아오는 길이 있으면 안 된다. `stg_customers`가 실수로 `fct_daily_sales`를 읽게 바꿔 봤다.

```text
[ERROR]: Encountered an error:
Compilation Error
Found a cycle: model.shop.fct_daily_sales --> model.shop.stg_customers
```

SQL을 하나도 실행하기 전에, 컴파일 단계에서 멈춘다. 손으로 만든 뷰라면 뷰 A가 뷰 B를 읽고 B가 A를 읽는 상태가 만들어지지는 않더라도, "어제 테이블을 읽어 오늘 테이블을 만들고 그걸 다시 어제 테이블로 덮어쓰는" 식의 고리가 운영 중에 몰래 생긴다. 순환이 필요해 보이면 대개 모델 하나가 너무 많은 일을 하는 것이다. 공통 부분을 앞쪽 모델로 빼서 둘 다 그걸 읽게 한다.

dbt가 이 순서를 정하는 방법은 위상 정렬이다. 들어오는 선이 없는 노드부터 꺼내고, 꺼낸 노드에서 나가는 선을 지우고, 다시 들어오는 선이 없어진 노드를 꺼낸다. 끝까지 꺼내지 못한 노드가 남으면 고리가 있다는 뜻이다. 모델 이름과 그 모델이 `ref()`하는 이름 목록을 받아 만들 순서를 돌려주는 함수를 짜 보자. 동시에 꺼낼 수 있는 노드가 여럿이면 이름 순으로 꺼내고, 고리가 있으면 `"cycle"`을 돌려준다.

  solution={`function buildOrder(models) {
  const indeg = {};
  const next = {};
  for (const name of Object.keys(models)) { indeg[name] ??= 0; next[name] ??= []; }
  for (const [name, deps] of Object.entries(models)) {
    for (const dep of deps) {
      indeg[dep] ??= 0; next[dep] ??= [];
      next[dep].push(name);
      indeg[name] += 1;
    }
  }
  const ready = Object.keys(indeg).filter((n) => indeg[n] === 0).sort();
  const order = [];
  while (ready.length) {
    const n = ready.shift();
    order.push(n);
    for (const m of next[n]) {
      indeg[m] -= 1;
      if (indeg[m] === 0) { ready.push(m); ready.sort(); }
    }
  }
  return order.length === Object.keys(indeg).length ? order : "cycle";
}`}

마지막 테스트에서 `d`는 꺼낼 수 있지만 `a`, `b`, `c`는 서로 기다리느라 영영 들어오는 선이 0이 되지 않는다. dbt의 오류 메시지가 고리에 든 모델 이름을 짚어 주는 것도 이렇게 남은 노드를 보고 알 수 있어서다.

## view, table, incremental 중에 고르기

모델을 무엇으로 만들지(materialization)는 설정 한 줄이지만 비용과 신선도가 여기서 갈린다.

- `view`: SELECT를 뷰로 저장만 한다. 만드는 데는 거의 시간이 안 든다. 대신 읽을 때마다 원본부터 계산한다. 가볍게 다듬기만 하는 staging 층에 맞다.
- `table`: 돌릴 때마다 결과를 통째로 새로 만든다(`create table as select`). 읽기는 빠르고 늘 정확하다. 데이터가 크면 매번 전부 다시 계산하는 비용이 든다.
- `incremental`: 처음에는 테이블로 만들고, 다음부터는 새로 들어온 행만 골라 기존 테이블에 넣거나 고쳐 쓴다. 크고 계속 쌓이는 이벤트·주문 테이블에 쓴다.
- `ephemeral`: 테이블을 만들지 않고, 읽는 모델의 SQL 안에 CTE로 끼워 넣는다. 여러 모델이 같은 조각을 쓸 때 편하지만, 많이 쓰면 디버깅할 때 중간 결과를 볼 곳이 없다.

출발점은 "staging은 view, marts는 table"이고, 실행 시간이나 웨어하우스 비용이 문제가 되는 모델만 incremental로 바꾼다. 처음부터 전부 incremental로 짜는 건 흔한 과잉 설계다. 증분 모델은 아래에서 보듯 틀리는 방법이 많고, 틀렸을 때 조용히 틀린다. 반대로 하루 수억 행이 쌓이는 이벤트 테이블을 `table`로 두면 매일 전체를 다시 읽는 비용이 청구서에 그대로 찍힌다. "이 모델이 매번 다시 읽는 양이 하루에 얼마인가"를 기준으로 바꾼다. 읽은 양으로 요금을 매기는 웨어하우스의 비용 구조는 [데이터 웨어하우스 구조](/posts/data-warehouse-architecture)의 요금 부분에 있다.

## 증분 모델은 새로 온 것만 넣는다

`fct_orders`를 증분 모델로 만들었다.

```sql
-- models/marts/fct_orders.sql
{{ config(materialized='incremental', unique_key='order_id') }}

select order_id, customer_id, status, amount, updated_at
from {{ ref('stg_orders') }}
{% if is_incremental() %}
where updated_at > (select max(updated_at) from {{ this }})
{% endif %}
```

`is_incremental()`은 이 테이블이 이미 있고, 증분 모델이고, `--full-refresh`로 돌리지 않았을 때 참이다. 그때만 WHERE가 붙어 "지금 테이블에 있는 가장 늦은 `updated_at`보다 뒤에 바뀐 행"만 읽는다. `{{ this }}`는 지금 만들고 있는 이 모델 자신이다.

`unique_key`가 있으면 새로 읽은 행과 같은 키가 이미 있을 때 덮어쓴다. dbt-duckdb에서 실제로 실행된 SQL을 `target/run/`에서 꺼내 보면 지우고 넣는 방식이었다.

```sql
-- target/run/shop/models/marts/fct_orders.sql (두 번째 실행)
delete from "shop"."main"."fct_orders"
where (
    order_id) in (
    select (order_id)
    from "fct_orders__dbt_tmp20261024100721365569"
);

insert into "shop"."main"."fct_orders" ("order_id", "customer_id", "status", "amount", "updated_at")
(
    select "order_id", "customer_id", "status", "amount", "updated_at"
    from "fct_orders__dbt_tmp20261024100721365569"
)
```

새 행을 임시 테이블에 먼저 만들고, 같은 키를 지운 뒤 넣는다. 어댑터와 설정(`incremental_strategy`)에 따라 `merge`, `delete+insert`, `append`, 파티션을 통째로 갈아 끼우는 `insert_overwrite`(BigQuery, Spark 계열) 같은 방식을 고를 수 있다. 어느 방식이 기본인지는 어댑터마다 다르니, 처음 쓸 때 `target/run/`에서 실제 SQL을 한 번 열어 본다.

이제 둘째 날 원본이 바뀐 상황을 만들었다. 4번 주문이 환불되어 `updated_at`이 22일 09:30으로 바뀌었고, 6번 주문이 새로 생겼다. 그리고 7번 주문이 있다. 이 주문은 21일 16:00에 결제됐는데 결제 시스템 쪽 장애로 원본 테이블에 늦게 들어왔다. 첫 실행 때 테이블의 가장 늦은 시각은 5번 주문의 21일 18:20이었다.

```text
│        7 │ paid     │ 2026-10-21 16:00:00 │
└──────────┴──────────┴─────────────────────┘
```

정리하면 증분 모델이 틀리는 길은 두 가지다. 같은 행이 다시 오면(상태 변경, 재전송, 겹쳐 읽기) `unique_key`가 없을 때 중복이 된다. 기준 시각보다 앞선 시각을 달고 늦게 오면 `unique_key`가 있어도 빠진다. 앞의 것은 키로, 뒤의 것은 겹쳐 읽는 구간(lookback)으로 막는다. 겹쳐 읽는 기간은 실제로 데이터가 얼마나 늦게 오는지 재서 정한다. 원본에 "적재된 시각" 컬럼이 따로 있다면 업무 시각 대신 그 컬럼으로 거르는 편이 낫다. 늦게 들어온 행도 적재 시각은 최신이기 때문이다. 이 문제가 원본을 꺼내 오는 단계에서 나타나는 모습은 [ETL과 ELT](/posts/etl-vs-elt)의 늦게 커밋된 주문 부분에 있다.

`unique_key`로 고르는 컬럼이 정말 유일한지도 확인해야 한다. 키가 유일하지 않으면 `delete+insert`는 같은 키의 여러 행을 지우고 다시 넣고, `merge`는 웨어하우스에 따라 "한 행에 여러 행이 맞는다"는 오류로 멈춘다. 아래 테스트가 이걸 잡는다.

dbt 1.9부터는 `microbatch`라는 증분 방식도 생겼다. 모델에 `event_time` 컬럼과 `batch_size`(예: 하루), `lookback`을 적으면 dbt가 기간을 잘라 배치마다 따로 돌리고, 특정 기간만 다시 돌리기(`--event-time-start`, `--event-time-end`)도 지원한다. 위에서 손으로 쓴 WHERE를 dbt가 대신 만들어 주는 셈이다. 어댑터마다 지원 여부가 다르니 쓰기 전에 확인한다.

증분 모델은 가끔 처음부터 다시 만들어야 한다. 컬럼을 추가했거나, 규칙이 바뀌었거나, 위처럼 빠진 행이 의심될 때다. `dbt run --select fct_orders --full-refresh`로 돌리면 `is_incremental()`이 거짓이 되어 전체를 다시 만든다. 테이블이 크면 이게 몇 시간짜리 작업이 되니, 큰 모델에는 `full_refresh: false` 설정을 걸어 실수로 전체를 다시 만드는 일을 막는 팀도 있다. 컬럼이 바뀌었을 때의 동작은 `on_schema_change`(`ignore`가 기본, `append_new_columns`, `sync_all_columns`, `fail`)로 정한다. 기본값에서는 새 컬럼이 조용히 무시된다.

## 스냅숏으로 등급이 바뀐 날을 남긴다

`stg_customers`는 회원의 지금 등급만 안다. 10월 22일에 이도윤 회원이 gold에서 vip가 되면, 21일 매출을 등급별로 다시 계산할 때도 vip로 잡힌다. 지난 사실을 지난 등급으로 보려면 바뀔 때마다 이력을 남겨야 한다. 차원 테이블에서 이걸 SCD 2형이라 부르고, 왜 필요한지와 설계 선택지는 [스타 스키마](/posts/olap-star-schema)의 회원 이사 이야기에서 자세히 다뤘다. dbt에서는 스냅숏이 이 일을 한다.

```yaml
# snapshots/customers_snapshot.yml
snapshots:
  - name: customers_snapshot
    relation: ref('raw_customers')
    config:
      unique_key: customer_id
      strategy: timestamp
      updated_at: updated_at
```

`strategy: timestamp`는 `updated_at`이 바뀐 행을 변경으로 본다. 원본에 믿을 만한 수정 시각이 없으면 `strategy: check`와 `check_cols`로 지정한 컬럼 값이 바뀌었는지 비교한다. 한 번 `dbt snapshot`을 돌리고, 102번 회원의 등급과 수정 시각을 바꾼 뒤 다시 돌렸다.

```text
┌─────────────┬─────────┬─────────────────────┬─────────────────────┐
│ customer_id │  grade  │   dbt_valid_from    │    dbt_valid_to     │
│    int32    │ varchar │      timestamp      │      timestamp      │
├─────────────┼─────────┼─────────────────────┼─────────────────────┤
│         101 │ silver  │ 2026-10-01 00:00:00 │ NULL                │
│         102 │ gold    │ 2026-10-01 00:00:00 │ 2026-10-22 00:00:00 │
│         102 │ vip     │ 2026-10-22 00:00:00 │ NULL                │
│         103 │ silver  │ 2026-10-01 00:00:00 │ NULL                │
└─────────────┴─────────┴─────────────────────┴─────────────────────┘
```

102번은 두 줄이 됐다. gold였던 줄은 `dbt_valid_to`가 닫혔고, 새 vip 줄은 열려 있다(NULL). 주문 시각이 `dbt_valid_from` 이상이고 `dbt_valid_to` 미만(또는 NULL)인 줄과 조인하면 그때의 등급이 붙는다.

스냅숏에는 다른 모델과 다른 성질이 하나 있다. 원본에서 다시 만들 수 없다. 원본은 지금 상태만 들고 있으니, 스냅숏을 지우면 지난 이력은 사라진다. 그래서 스냅숏은 `--full-refresh`의 대상이 아니고, 따로 백업을 챙긴다. 또 스냅숏은 돌릴 때만 변경을 본다. 하루 한 번 돌리면 하루 안에 두 번 바뀐 값의 중간 상태는 남지 않는다. 그 사이 변화까지 필요하면 원본 DB의 변경을 [CDC](/posts/cdc-change-data-capture)로 받아야 한다.

## 테스트가 모델 사이를 막는다

dbt 테스트는 "결과가 0행이면 통과"인 SELECT 문이다. 자주 쓰는 네 가지는 기본으로 들어 있고 YAML에 적기만 하면 된다.

```yaml
# models/schema.yml
version: 2
models:
  - name: stg_orders
    columns:
      - name: order_id
        data_tests: [unique, not_null]
      - name: status
        data_tests:
          - accepted_values:
              arguments:
                values: ['paid', 'refunded', 'cancelled']
      - name: customer_id
        data_tests:
          - relationships:          # 모든 customer_id가 stg_customers에 있어야 한다
              arguments:
                to: ref('stg_customers')
                field: customer_id
```

`unique` 테스트가 실제로 만드는 SQL을 보면 단순하다. 위의 `unique_key` 없는 증분 모델에 걸었더니 4번 주문 때문에 실패했다.

```sql
-- target/compiled/.../unique_fct_orders_append_order_id.sql
select
    order_id as unique_field,
    count(*) as n_records
from "shop"."main"."fct_orders_append"
where order_id is not null
group by order_id
having count(*) > 1
```

테스트는 `dbt build`와 함께 쓸 때 힘이 생긴다. `build`는 seed, 모델, 스냅숏, 테스트를 그래프 순서대로 섞어 돌리고, 어떤 모델의 테스트가 실패하면 그 아래 모델들을 건너뛴다. 아래 그림은 원본에 `paied`라는 오타 상태가 섞여 들어온 날의 `dbt build` 흐름이다.

`dbt run` 다음에 `dbt test`를 따로 돌리면 이 보호가 없다. 틀린 데이터로 모든 모델을 다 만든 뒤에야 테스트가 실패를 알린다. 모든 테스트가 실행을 멈출 만큼 중요하지는 않으니, 덜 중요한 것은 `severity: warn`으로 경고만 내게 한다. 기본 네 가지 말고 행 수가 갑자기 줄었는지, 값의 분포가 바뀌었는지 같은 검사를 어떻게 설계하는지는 [데이터 품질 검사](/posts/data-quality-checks)에서 다룬다.

## Airflow와 dbt가 일을 나누는 자리

dbt는 스케줄러가 아니다. 언제 돌릴지, 원본 적재가 끝났는지 기다리는 일, 실패하면 누구에게 알릴지는 모른다. 그건 [Airflow](/posts/airflow-orchestration) 같은 오케스트레이터가 맡는다. 흔한 나눔은 이렇다.

- Airflow: 원본 적재 작업을 돌리고, 끝났다는 표시를 기다리고, `dbt build`를 부르고, 끝나면 리포트나 리버스 ETL 동기화를 이어 부른다.
- dbt: 웨어하우스 안의 모델 사이 순서, 테스트, 문서.

가장 단순한 연결은 Airflow 태스크 하나에서 `dbt build`를 통째로 부르는 것이다. 설정이 쉽지만, 모델 300개 중 하나가 실패해도 Airflow에서는 태스크 하나가 실패한 것으로만 보이고 다시 돌릴 때도 통째로 돈다. 반대쪽 끝은 dbt 모델 하나를 Airflow 태스크 하나로 펼치는 방식이다(astronomer-cosmos 같은 패키지가 `manifest.json`을 읽어 이걸 만든다). 실패한 모델만 다시 돌리기 쉬운 대신, Airflow DAG가 커지고 dbt의 동시 실행 대신 Airflow 스케줄링을 거치니 느려질 수 있다. 중간 방법으로 `dbt build --select tag:hourly`처럼 태그나 폴더 단위로 태스크를 나눈다. 데이터를 다시 돌릴 날짜를 dbt에 넘길 때는 `--vars '{"run_date": "2026-10-21"}'`처럼 Airflow의 데이터 구간을 변수로 넘기고, 모델 안에서 `var('run_date')`로 읽는다.

CI에서는 바뀐 모델과 그 자손만 돌리는 방법이 많이 쓰인다. 운영 실행에서 나온 `manifest.json`을 내려받아 두고 `dbt build --select state:modified+ --state prod-artifacts/`로 돌리면, PR에서 고친 모델과 그 아래만 빌드하고 테스트한다. 모델이 수백 개인 프로젝트에서 PR마다 전체를 돌리면 CI가 한 시간씩 걸린다.

## 흔히 밟는 실수

- `ref()` 대신 테이블 이름을 직접 쓴다. 그래프에 선이 빠져 순서가 틀어지고, 개발 환경에서 운영 테이블을 읽는다. 원본 테이블은 `sources:`에 등록하고 `source('app', 'orders')`로 읽는다. 원본도 그래프에 들어가고, `dbt source freshness`로 원본이 언제 마지막으로 들어왔는지 검사할 수 있다.
- 증분 모델에 `unique_key`가 없거나, 있는데 유일하지 않다. 위에서 본 대로 중복이나 오류가 난다. 키에 `unique` 테스트를 꼭 붙인다.
- 증분 필터가 업무 시각 기준이라 늦은 데이터가 빠진다. 겹쳐 읽는 구간을 두거나 적재 시각으로 거른다.
- 모든 모델을 `table`로 두고 매시간 `dbt run`을 돈다. 바뀌지 않은 큰 테이블을 매시간 다시 만든다. 실행 기록(`target/run_results.json`)에서 오래 걸리는 모델부터 본다.
- 운영에서 `dbt run`과 `dbt test`를 따로 돌려 틀린 데이터가 끝까지 흘러간다. `dbt build`를 쓴다.
- 한 모델에 CTE 열 개를 넣어 500줄 SQL을 만든다. 테스트를 붙일 곳이 없고 중간 결과를 볼 수 없다. 여러 곳에서 쓰는 조각은 intermediate 모델로 뺀다.
- 매크로(Jinja)로 SQL을 너무 많이 생성한다. 읽는 사람이 컴파일 결과를 열어 봐야 이해할 수 있게 되면 손해다.

## SQL을 파일로, 순서는 ref로

dbt는 웨어하우스 안의 변환을 SELECT 하나짜리 모델 파일로 나누고, `ref()`로 모델 사이의 선을 그어 순서와 영향 범위를 dbt가 알게 만든다. 물질화 방식은 view로 시작해 비용이 보이는 곳만 table과 incremental로 바꾼다. 증분 모델은 같은 행이 다시 오면 키로, 늦게 오면 겹쳐 읽기로 막아야 하고, 그걸 `unique` 테스트와 `dbt build`가 지킨다. 지금 상태만 있는 원본에서 이력을 남기는 건 스냅숏이고, 스냅숏은 다시 만들 수 없으니 따로 지킨다.

## 면접에서 나올 만한 질문

### dbt는 ELT에서 어떤 일을 맡나요

T, 즉 웨어하우스 안의 변환만 맡는다. 원본을 꺼내 오거나 옮기는 일은 수집 도구가, 언제 돌릴지는 오케스트레이터가 한다. dbt는 SELECT 문 하나짜리 모델 파일을 받아 `ref()`로 의존 그래프를 만들고, 그 순서대로 테이블이나 뷰를 만들며, 테스트와 문서를 같은 저장소에서 관리한다. 변환 SQL에 버전 관리, 리뷰, 테스트를 붙이는 도구라고 보면 된다.

### ref()를 쓰는 이유는 무엇인가요

dbt가 모델 사이의 의존 관계를 알게 하려고 쓴다. 실행 전에 모든 `ref()`를 모아 그래프를 만들고, 그 순서대로 실행하며 고리가 있으면 컴파일 단계에서 멈춘다. 같은 SQL이 개발자 스키마와 운영 스키마를 환경에 따라 가리키게 해 주는 효과도 있다. 테이블 이름을 직접 쓰면 그래프에서 선이 빠져 순서와 영향 범위 계산이 틀어진다.

### view, table, incremental은 어떻게 고르나요

가볍게 다듬는 staging은 view, 자주 읽히는 쓰임새 테이블은 table로 시작한다. 데이터가 커서 매번 전체를 다시 만드는 비용이나 시간이 문제가 되는 모델만 incremental로 바꾼다. incremental은 빠르고 싸지만 중복과 누락으로 조용히 틀리는 길이 많아서, 처음부터 모든 모델을 증분으로 짜는 건 과잉이다.

### 증분 모델이 중복을 만드는 경우는 언제인가요

같은 키의 행이 다시 들어오는데 `unique_key`가 없을 때다. 주문 상태가 바뀌어 `updated_at`이 갱신되면 그 주문이 다시 읽히고, 키가 없으면 옛 행 옆에 새 행이 추가된다. 실험에서는 환불된 4번 주문이 paid와 refunded 두 줄로 남았다. `unique_key`를 줬는데 그 컬럼이 실제로 유일하지 않을 때도 문제가 생기니 키에 `unique` 테스트를 붙인다.

### 증분 모델에서 늦게 도착한 데이터가 빠지는 이유와 해결책은 무엇인가요

`max(updated_at)`보다 뒤인 행만 읽는 필터는 기준보다 앞선 시각을 달고 늦게 들어온 행을 영영 건너뛴다. 실험에서 21일 16시에 결제됐지만 늦게 적재된 7번 주문이 `unique_key`가 있어도 빠졌다. 기준을 며칠 당겨 겹쳐 읽고 겹친 행은 `unique_key`로 덮어쓰거나, 업무 시각 대신 적재 시각 컬럼으로 거른다. 겹쳐 읽는 기간은 실제 지연 분포를 재서 정한다.

### dbt 스냅숏은 무엇이고 일반 모델과 무엇이 다른가요

지금 상태만 있는 원본에서 변경 이력을 남기는 SCD 2형 테이블을 만든다. 바뀐 행이 보이면 옛 행의 `dbt_valid_to`를 닫고 새 행을 연다. 일반 모델은 원본에서 언제든 다시 만들 수 있지만, 스냅숏은 지우면 이력을 되살릴 수 없어서 전체 재빌드 대상이 아니고 따로 백업한다. 돌릴 때만 변경을 보니 그 사이 여러 번 바뀐 중간 값은 남지 않는다.

### dbt run 대신 dbt build를 쓰는 이유는 무엇인가요

`build`는 모델과 테스트를 그래프 순서대로 섞어 돌리고, 어떤 모델의 테스트가 실패하면 그 자손 모델을 건너뛴다. 원본에 틀린 값이 들어온 날 쓰임새 테이블이 틀린 숫자로 덮이지 않고 어제 상태로 남는다. `run` 다음 `test`를 따로 돌리면 틀린 데이터로 모든 모델을 다 만든 뒤에야 실패를 알게 된다.

### Airflow와 dbt는 어떻게 역할을 나누나요

Airflow는 언제 돌릴지, 원본 적재를 기다리는 일, 재시도와 알림, dbt 앞뒤의 작업 연결을 맡고, dbt는 웨어하우스 안 모델 사이의 순서와 테스트를 맡는다. 태스크 하나에서 `dbt build`를 통째로 부르면 단순하지만 실패 지점이 안 보이고, 모델마다 태스크를 펼치면 다시 돌리기는 쉽지만 DAG가 커진다. 태그나 폴더 단위로 나누는 중간 방법을 많이 쓴다.
