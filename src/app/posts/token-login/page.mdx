[쿠키 기반 로그인](/posts/cookie-session-login)에서는 서버가 세션을 보관하고 브라우저는 번호표만 들고 다녔다. 토큰 기반 로그인은 정반대로 간다. 서버는 아무것도 기억하지 않는다. 대신 "이 사람은 42번 사용자다"라는 내용 자체를 위조할 수 없게 서명해서 클라이언트에게 들려 보낸다. 모바일 앱이나 여러 서비스가 같은 로그인을 나눠 쓰는 구조에서 자주 쓰는 방식이라, 쿠키 세션과 무엇이 다른지 비교하며 정리했다.

## 명단 대신 손목 팔찌

외투 보관소 비유를 이어 가 보면, 쿠키 세션은 직원이 번호표를 받아 안쪽 옷걸이(세션 저장소)를 확인하는 방식이었다. 토큰 방식은 페스티벌 입장 팔찌에 가깝다. 입구에서 한 번 신분을 확인하고 팔찌를 채워 준다. 그다음부터 공연장 직원들은 명단을 찾아보지 않고 팔찌만 보고 들여보낸다. 팔찌에는 위조할 수 없는 도장이 찍혀 있고, 언제까지 유효한지도 적혀 있다.

이 팔찌가 토큰이고, 도장이 서명이다. 웹에서는 JWT(JSON Web Token)라는 형식을 가장 많이 쓴다.

## 한 번 준 토큰은 되돌리기 어렵다

서버가 아무것도 기억하지 않는다는 장점은 그대로 약점이 된다. 쿠키 세션은 서버가 세션을 지우면 끝이었다. 토큰은 서버가 기억하는 게 없으니 지울 대상도 없다. 로그아웃 버튼을 눌러도 클라이언트가 토큰을 버릴 뿐이고, 누가 미리 복사해 둔 토큰은 exp까지 계속 통한다.

그래서 보통 액세스 토큰은 15분 정도로 아주 짧게 주고, 대신 리프레시 토큰을 하나 더 준다. 액세스 토큰이 만료되면 리프레시 토큰으로 새 액세스 토큰을 받는다. 리프레시 토큰은 서버가 저장해 두고 관리하므로, 로그아웃할 때 이걸 폐기하면 길어야 액세스 토큰 수명만큼만 더 버틴다.

## 토큰은 어디에 둘까

웹에서 가장 고민되는 부분이다. `localStorage`에 두면 쓰기는 편하지만, 페이지에 악성 스크립트가 끼어드는 XSS가 하나만 생겨도 토큰을 그대로 읽어 간다. 자바스크립트 변수(메모리)에만 두면 읽어 가기 어렵지만 새로고침하면 사라진다. 그래서 리프레시 토큰은 `HttpOnly` 쿠키에 두고, 액세스 토큰은 메모리에 두는 조합을 많이 쓴다. 새로고침하면 리프레시 토큰 쿠키로 액세스 토큰을 다시 받으면 된다.

결국 웹 브라우저에서는 다시 쿠키를 쓰게 되는 셈이다. 차이는 쿠키에 담기는 것이 세션 번호표냐, 서명된 토큰이냐다. 쿠키를 쓰는 이상 [앞 글](/posts/cookie-session-login)에서 본 SameSite와 CSRF 대비도 그대로 필요하다.

## 쿠키 세션과 나란히 놓고 보면

| | 쿠키 세션 | 토큰(JWT) |
|---|---|---|
| 로그인 정보를 누가 들고 있나 | 서버(세션 저장소) | 클라이언트(토큰 안에) |
| 요청마다 서버가 하는 일 | 저장소에서 세션 조회 | 서명과 만료만 계산 |
| 즉시 로그아웃 | 세션을 지우면 끝 | 어렵다. 짧은 수명 + 리프레시 토큰으로 보완 |
| 서버를 늘릴 때 | 공용 세션 저장소가 필요 | 비밀 키만 공유하면 된다 |
| 잘 맞는 곳 | 브라우저 위주의 웹 서비스 | 모바일 앱, 여러 서비스가 같은 로그인을 공유하는 구조 |

## 정리

토큰 기반 로그인은 로그인 정보를 서버에 보관하지 않고, 위조할 수 없게 서명한 토큰을 클라이언트가 들고 다니게 하는 방식이다. 서버는 요청마다 서명과 만료만 확인하면 되니 가볍고 늘리기 쉽다. 대신 한 번 내준 토큰을 거둬들이기 어려워서, 짧은 액세스 토큰과 서버가 관리하는 리프레시 토큰을 함께 쓴다. 토큰을 다른 서비스에 위임하는 규칙은 [OAuth 2.0 글](/posts/oauth)에서 이어진다.
