이 글은 실제 서비스 사례 시리즈의 하나다. 샤드 키를 고르는 기준, 리샤딩, scatter-gather의 비용 같은 일반 원리는 [샤딩 입문](/posts/sd-sharding-intro)과 [DB 샤딩](/posts/db-sharding)에서 다뤘다. 여기서는 Slack이 직접 공개한 글 세 편을 따라, 워크스페이스 단위 샤딩이 어디서 깨졌고 왜 직접 만들지 않고 Vitess를 골랐는지, 옮긴 뒤 무엇이 남았는지를 본다.

중심 자료는 Slack Engineering 블로그에 2020년 12월 1일에 올라온 ["Scaling Datastores at Slack with Vitess"](https://slack.engineering/scaling-datastores-at-slack-with-vitess/)다. Arka Ganguli, Guido Iaquinti, Maggie Zhou, Rafael Chacón이 썼다. 옮긴 뒤의 장애는 2023년 11월의 ["The Query Strikes Again"](https://slack.engineering/the-query-strikes-again/), 데이터 모델 변화는 2024년 7월의 ["Unified Grid"](https://slack.engineering/unified-grid-how-we-re-architected-slack-for-our-largest-customers/) 글에서 가져왔다. Vitess 용어는 [Vitess 공식 문서](https://vitess.io/docs/22.0/concepts/shard/)를 따랐다.

## 메시지 하나도 DB를 거쳐야 보인다

2020년 글은 데이터 저장 계층이 왜 중요한지부터 적는다. Slack에서 보내는 메시지는 모두 먼저 저장되고, 그다음에 실시간 웹소켓 계층을 타고 채널의 다른 사람들에게 보인다. 저장이 느리면 메시지가 늦게 뜨고, 저장이 멈추면 메시지를 보낼 수 없다. 글을 쓴 시점의 숫자는 이렇다. 피크 때 초당 230만 쿼리, 그중 읽기 200만, 쓰기 30만. 쿼리 지연은 중앙값 2ms, p99 11ms. Vitess가 전체 쿼리 부하의 99%를 받고 있었고, 나머지는 2020년 말까지 옮길 예정이라고 했다.

출발점은 LAMP(Linux, Apache, MySQL, PHP)였다. 데이터는 MySQL 기반의 세 클러스터에 있었다.

- 샤드: 메시지, 채널, DM처럼 고객 데이터 거의 전부. 워크스페이스 ID로 나눴다. 한 워크스페이스의 데이터는 모두 같은 샤드에 있어서 애플리케이션은 그 DB 하나에만 붙으면 됐다.
- 메타데이터 클러스터: 워크스페이스 ID를 샤드 ID로 바꾸는 조회 테이블. 샤드를 찾으려면 여기를 먼저 들러야 했다.
- "키친 싱크" 클러스터: 앱 디렉터리처럼 워크스페이스에 묶이지 않는 나머지 테이블.

샤딩은 모놀리스 애플리케이션 "webapp"이 관리했다. webapp이 메타데이터를 조회해 샤드를 찾고 그 샤드에 직접 연결했다. 샤드 하나에는 워크스페이스 수천 개가 들어 있었고, 샤드마다 서로 다른 데이터 센터에 MySQL 인스턴스를 최소 둘 두고 서로 비동기로 복제하는 액티브-액티브 구성이었다. 두 쪽 모두 읽기와 쓰기를 받았다. 평소에는 간단한 해시로 한쪽을 골라 쿼리하고, 연결에 실패하면 다른 쪽으로 다시 보냈다.

이 구조의 장점을 글은 네 가지로 적었다. 한쪽이 죽어도 다른 쪽으로 재시도하면 되니 가용성이 높았다. 워크스페이스 데이터가 한 호스트에 다 있으니 새 기능을 설계하기 직관적이었다. 고객 문의를 받으면 엔지니어가 몇 분 안에 그 고객의 DB 호스트를 찾아 들어갈 수 있었다. 고객이 늘면 샤드를 더 만들어 새 팀을 넣으면 됐다. 글은 바로 이어서 질문을 던진다. "팀 하나와 그 데이터가 우리의 가장 큰 샤드에 들어가지 않으면?"

## 워크스페이스 하나가 샤드 하나를 넘을 때

글이 적은 단점은 다섯 가지다. 이 부분이 이 사례의 중심이다.

규모 한계. 큰 고객을 받을수록 그 고객의 샤드가 쓸 수 있는 가장 큰 하드웨어에 닿았고, 호스트 한 대가 버틸 수 있는 한계에 자주 부딪혔다. 샤드 키가 워크스페이스라서 한 워크스페이스를 두 서버로 나눌 방법이 없었다.

데이터 모델 고정. Enterprise Grid(여러 워크스페이스를 묶은 조직)와 Slack Connect(회사 사이 채널)는 "한 팀의 데이터는 한 샤드에 있다"는 전제를 깨는 제품이었다. 2024년 Unified Grid 글은 그 결과를 구체적으로 적었다. Grid에서는 조직 단위 데이터가 조직의 샤드에 저장되니, 백엔드가 워크스페이스 샤드를 보고 없으면 조직 샤드를 또 봐야 했다.

핫스팟. 수천 명 규모의 엔터프라이즈 고객이 늘면서 몇몇 샤드는 크게 달아오르고 나머지 대부분은 놀았다. 샤드를 쪼개거나 팀을 옮기기 어렵고 사용량을 예측하기도 어려워서, 대부분의 샤드를 넉넉하게 잡아 두었고 그 긴 꼬리가 놀고 있었다. 큰 고객 한 곳의 부하를 여러 서버로 흩을 수 없다는 문제는 [샤딩 입문](/posts/sd-sharding-intro)의 "유명한 키 하나가 샤드를 태우는" 경우와 같다. 여기서는 그 키가 워크스페이스였다.

가용성. 로그인, 메시지, 채널 참여 같은 핵심 기능이 모두 그 팀의 샤드에 기대니, 샤드 하나가 멈추면 그 샤드의 모든 고객이 Slack을 통째로 못 썼다. 글은 부하를 흩어 핫스팟을 줄이는 동시에, 덜 중요한 기능이 멈춰도 메시지 보내기 같은 핵심 기능은 살아 있도록 워크로드를 나누고 싶었다고 적었다. 장애가 퍼지는 범위를 줄이는 일반론은 [멀티테넌시 격리](/posts/multi-tenancy-isolation)에 있다.

운영. 액티브-액티브는 표준 MySQL 구성이 아니어서 운영 도구를 많이 직접 만들어야 했다. 토폴로지에 읽기 전용 복제본이 없고 애플리케이션이 DB 호스트로 직접 라우팅하니, 라우팅을 다시 짜지 않고는 복제본을 안전하게 쓸 수도 없었다.

2016년 가을, Slack은 초당 수십만 MySQL 쿼리와 샤딩된 MySQL 호스트 수천 대를 운영하고 있었다. 애플리케이션 성능 팀은 워크스페이스 샤딩의 한계를 피해 가는 우회책을 계속 만들고 있었다.

## 직접 짤까, Vitess를 들일까

원하는 것은 분명했다. 예를 들어 워크스페이스의 모든 채널과 DM 메시지를 한 샤드에 넣는 대신, 메시지를 채널의 고유 ID로 나누고 싶었다. 그러면 가장 큰 고객의 메시지도 여러 샤드에 고르게 퍼진다. 데이터 종류마다 다른 샤드 키를 고를 수 있어야 했다.

동시에 버릴 수 없는 것도 분명했다. 애플리케이션에는 서로 다른 쿼리가 수천 개 있었고, 일부는 MySQL 전용 문법을 썼다. 배포, 데이터 내구성, 백업, 데이터 웨어하우스 ETL, 컴플라이언스까지 몇 년 쌓인 운영 관행이 모두 MySQL 기준이었다. 그래서 DynamoDB나 Cassandra 같은 NoSQL, Spanner나 CockroachDB 같은 NewSQL은 사실상 제외했다. 글은 맥락도 덧붙였다. Slack은 핵심 제품 스택에 새 기술을 들이는 데 보수적이고, 작은 데이터스토어·인프라 팀은 움직이는 부품이 적은 단순한 해법을 원했다.

가장 자연스러운 길은 webapp 안에 새 샤딩 방식을 넣는 것이었다. 이미 webapp이 샤드 라우팅을 하고 있었으니 채널 ID 기준 라우팅을 그 층에 더하면 된다. 실제로 시제품도 만들어 봤다. 그런데 애플리케이션 로직과 저장 방식이 이미 강하게 엮여 있었다. 채널의 메시지 수를 세는 코드조차 그 채널이 어느 팀에 있는지를 가정했고, 여러 워크스페이스를 가진 조직을 위해 샤드 여러 개를 명시적으로 뒤지는 코드가 곳곳에 있었다. 이 엉킴을 푸는 동시에 새 방식을 만드는 데 오래 걸린다는 게 보였다. 그리고 애플리케이션 안의 샤딩은 운영 문제나 복제본 활용을 해결하지 못하고, 한 팀의 샤드가 쓰기 경로에서 갑자기 달아오르면 수평으로 늘리기 어려운 문제도 그대로 남는다고 판단했다.

그때 Vitess가 눈에 들어왔다. 글은 네 칸을 채웠다고 적었다. 바닥이 MySQL이라 저장과 복제 엔진으로 MySQL의 신뢰와 경험을 그대로 쓴다. 샤딩이 내장돼 애플리케이션에 로직을 넣지 않고 나누고 늘릴 수 있다. 기본 서버 장애 조치와 백업을 자동으로 하고, 락 서버로 서버를 추적해 애플리케이션이 토폴로지를 몰라도 된다. 100% 오픈소스(Go)라 필요하면 고칠 수 있다. 마지막 칸이 실제로 쓰였다. Slack은 여러 격리 지역(isolation region)에 걸친 토폴로지 메타데이터 서비스 재구성, MySQL 쿼리 호환성의 빈틈 메우기, 데이터 이전 도구, 부하 시험·관찰 도구, Prometheus·Orchestrator·Percona xtrabackup 연동을 Vitess에 기여했다고 적었다.

같은 고민을 다른 회사는 다르게 풀었다. Uber는 2014년에 MySQL 위에 자체 층인 Schemaless를 만들었다([Uber Schemaless와 Docstore](/posts/rw-uber-schemaless-docstore)). 일정이 몇 달이었고, 필요한 기능(쓰기 버퍼, 변경 알림)이 기존 제품에 없었다. Slack의 2016~2017년에는 Vitess라는 선택지가 있었고, 바꾸고 싶은 것이 "샤드 키를 자유롭게"였다. 샤드 ID를 ID 안에 넣어 애플리케이션이 라우팅하는 방식은 [Pinterest 사례](/posts/rw-pinterest-mysql-sharding)에 있다.

## 키스페이스, 샤드, VTGate

Vitess의 단어 몇 개를 짚고 가자. 2023년 Slack 글과 Vitess 문서가 같은 설명을 한다.

키스페이스(keyspace)는 분산 데이터베이스 하나다. 클라이언트에게는 MySQL 인스턴스 하나처럼 보이지만, 실제로는 여러 MySQL 인스턴스의 스키마에 나뉘어 있다. 키스페이스는 샤드로 이루어지고, 샤드 하나는 MySQL 기본 서버(primary) 하나와 복제본 여러 대다. Vitess에서는 이 MySQL 하나하나를 태블릿(tablet)이라 부른다. 2020년 글은 Slack이 지역별 Vitess 클러스터 여러 개에 키스페이스 수십 개를 두었다고 적었다. 키스페이스는 사용자 수, 팀 수, 채널 수처럼 같은 비율로 커지는 데이터를 묶은 논리 모음이다.

행이 어느 샤드에 있는지는 키스페이스 ID(keyspace ID)가 정한다. 열 값(예: 채널 ID)을 vindex라는 함수로 키스페이스 ID로 바꾸고, 샤드마다 키스페이스 ID의 범위를 맡는다. 샤드 이름이 그 범위다. `-80`은 `0x80`보다 작은 쪽, `80-`은 `0x80` 이상인 쪽이다. 이름은 16진수로, 왼쪽부터 맞춰 읽고 오른쪽을 0으로 채운다. 문서의 예로 xxhash vindex는 부호 없는 64비트 정수를 내니, 맨 위 비트가 0이면 `-80`, 1이면 `80-`로 간다. 맨 위 비트로 반을 나누는 방식이다.

VTGate는 가벼운 프록시다. MySQL 프로토콜을 말하니 애플리케이션은 VTGate를 MySQL 서버처럼 대하고, VTGate가 샤딩 방식을 보고 맞는 태블릿으로 보내고 결과를 합쳐 돌려준다. 샤드 키(Vitess 용어로 primary vindex)가 없는 질의는 모든 샤드에 펼쳐야 하니, 다른 열로도 찾아야 하면 열 값에서 키스페이스 ID로 가는 조회 테이블(lookup vindex)을 둔다. Schemaless의 반정규화 인덱스, 일반적인 [보조 인덱스 샤딩](/posts/db-sharding)과 같은 자리다. 또 primary vindex 열의 값은 넣은 뒤 바꿀 수 없다.

샤드 이름 규칙은 짧은 함수로 옮길 수 있다. 아래에서 키스페이스 ID(16진수)와 샤드 목록을 받아 담당 샤드를 찾아 보자. 문서가 든 함정, "`80-FF`는 `80-`과 다르다"도 테스트에 넣었다. `80-FF`의 끝은 `FF00`으로 읽히니 `FFFF`는 범위 밖이다. 기대값은 같은 함수를 node로 돌려 얻었다.

  const kid = keyspaceId.toLowerCase();
  for (const name of shards) {
    const [lo, hi] = name.toLowerCase().split("-");
    const len = Math.max(kid.length, lo.length, hi.length);
    const pad = (s) => s.padEnd(len, "0");
    const k = pad(kid);
    const geLo = lo === "" || k >= pad(lo);
    const ltHi = hi === "" || k < pad(hi);
    if (geLo && ltHi) return name;

다섯 번째 테스트가 범위 샤딩의 장점이다. `80-` 샤드 하나를 `80-c0`과 `c0-`로 쪼개도 `-80` 쪽 키는 한 줄도 움직이지 않는다. 문서도 "샤드 하나를 범위를 합쳐 같은 영역을 덮는 둘 이상의 새 샤드로 바꾸면, 다른 샤드의 레코드는 옮기지 않아도 된다"고 적었다. `hash % N`으로 나눴다면 샤드 수를 바꿀 때 대부분의 키가 옮겨 간다. 이 차이는 [일관된 해싱](/posts/consistent-hashing)에서 숫자로 봤다.

## RSS 피드 하나로 시작해 3년

Slack은 먼저 작은 기능 하나를 Vitess로 끝까지 옮겨 보는 시제품을 만들었다. 슬랙 채널에 RSS 피드를 붙이는 기능이었다. 기능은 작았지만 바꿔야 할 것이 많았다. 배포 프로비저닝, 서비스 디스커버리, 백업·복원, 토폴로지 관리, 자격 증명 같은 운영 절차를 다시 짰다. 애플리케이션 쪽에는 쿼리를 Vitess로 보내는 새 연결 지점, 기존 테이블을 복제하면서 애플리케이션이 양쪽에 쓰는 범용 백필 시스템, 양쪽에서 읽어 결과를 비교하는 병렬 이중 읽기 비교 시스템을 만들었다. 결과는 같았고 성능은 더 좋았고 운영은 더 단순했다고 적었다.

이 순서, 양쪽에 쓰고 채우고 양쪽에서 읽어 비교하는 방식은 Uber Mezzanine과 거의 같다. DB를 옮기는 일반적인 틀이다. 무중단 이전과 binlog를 쓰는 도구 이야기는 [MySQL 복제와 온라인 DDL](/posts/mysql-replication-online-ddl)에 있다.

이전은 2017년에 시작해 정확히 3년 만인 2020년 말에 99%에 닿았다. 0 QPS에서 230만 QPS까지 오는 동안 샤드 키를 고르고, 기존 애플리케이션을 Vitess에 맞게 고치고, 규모에 맞는 운영을 익혔다고 적었다. 전체 쿼리 부하의 20%를 차지하는 테이블 하나를 옮긴 이야기는 Slack 엔지니어 Maude Lemaire와 함께 쓴 책 "Refactoring at Scale"에 사례로 실었다고 했다(그 책은 이번에 확인하지 못했다). 도중에 테이블 단위가 아니라 샤드 통째로 옮기는 방식으로 전략을 바꿨다는 언급도 있다.

옮긴 효과가 드러난 순간도 적혀 있다. 2020년 3월 코로나19로 일과 학교가 원격으로 바뀌면서, 데이터스토어 쪽에서는 한 주 만에 쿼리 비율이 50% 늘었다. Slack은 가장 바쁜 키스페이스 하나를 Vitess의 분할 워크플로로 수평 확장했다. 글은 "리샤딩과 Vitess 이전이 없었다면 가장 큰 고객들을 위해 전혀 늘릴 수 없었고, 장애로 이어졌을 것"이라고 적었다. 앞의 테스트에서 본 범위 쪼개기가 실제로 쓰인 장면이다. 새로 만드는 서비스들도 webapp과 같은 저장 기술을 쓰게 됐고, 국제 데이터 레지던시(데이터를 특정 지역에 두는 제품)는 Vitess 클러스터를 6개 지역에 두고 만들었다.

2024년 Unified Grid 글은 그 뒤를 보여 준다. Vitess 이전으로 워크스페이스나 조직 ID가 아닌 축으로도 나눌 수 있게 됐고, 가장 중요한 테이블들은 쿼리를 라우팅하는 데 워크스페이스가 더는 필요 없어졌다. 메시지 테이블은 이제 채널 ID로 샤딩돼 있어 채널의 메시지를 큰 변경 없이 가져올 수 있었다고 적었다. 2016년에 원했던 "메시지는 채널 ID로"가 2024년 글에 사실로 적혀 있다. 반면 워크스페이스 단위로 남은 데이터는 여전히 워크스페이스마다 샤드를 뒤져야 했다. 그래서 사용자가 수백 개 워크스페이스에 속한 긴 꼬리를 위해 "관련 워크스페이스"를 50개로 제한했다. 샤드 키를 바꾸지 못한 데이터는 scatter-gather의 비용을 계속 낸다.

## 샤드 키를 바꿔도 몰리는 순간

2023년 11월 글은 2022년 10월 12~13일의 장애를 다룬다. 이 사례에서 가장 실무적인 부분이다.

한 고객이 워크스페이스에서 사용자를 한꺼번에 많이 지웠다. 보통은 사람이 퇴사할 때 조금씩 지우는 일이다. 사용자 삭제는 "forget user"라는 비동기 작업으로 도는데, 지운 사용자마다 그 사람이 구독한 모든 채널과 스레드의 구독 레코드를 찾아 지워야 한다. 쿼리 수는 "지운 사용자 수 × 사용자당 구독 수"가 된다. 그런데 한 샤드가 그 사용자들의 구독 데이터의 6%를 갖고 있었다. 그 샤드에 쓰기가 쏟아졌고, 다음 순서로 무너졌다.

해결은 세 팀이 나눠 했다. 데이터스토어 팀은 CPU와 메모리가 더 큰 인스턴스로 복제본을 손으로 띄워 OOM을 끊고, 자동 교체 대신 수동 프로비저닝으로 바꿔 루프를 멈췄다. 작업을 맡은 팀은 "채널 떠나기" 작업이 처리하는 채널의 구독만 조회하고 UPDATE에도 그 ID만 넣도록 고쳤고, 접속할 수 없는 비활성 사용자에게 보내던 클라이언트 알림 단계를 뺐다. 클라이언트 팀은 스레드 화면을 잠시 꺼서 복제본으로 가는 읽기를 줄였다. 첫날에는 JobQueue 팀이 그 작업을 "shim"으로 막아 새 작업이 처리되지 않게 했다.

재발 방지로는 Vitess에 쿼리 스로틀링 기능과 버그 수정을 기여하고, 샤드의 태블릿이 건강하지 않으면 그 샤드로 가는 쿼리를 제한하거나 취소하는 서킷 브레이커를 도입했다. 작업 쪽은 사용자마다 채널 수만큼 작업을 만드는 대신 "모든 스레드 구독 해제" 작업 하나만 넣도록 구조를 바꾸고, 지수 백오프와 서킷 브레이커를 달아 의존성이 아플 때 재시도를 멈추게 했다. 각각의 일반론은 [서킷 브레이커](/posts/circuit-breaker), [지수 백오프와 지터](/posts/exponential-backoff-jitter), [레이트 리미팅 실무](/posts/rate-limiting-in-practice)에 있다.

이 장애가 보여 주는 것은 샤드 키를 바꿔도 핫스팟이 사라지지는 않는다는 점이다. 워크스페이스로 나눌 때는 큰 고객이 늘 한 샤드를 달궜다. 키를 바꾼 뒤에는 평소에는 고르게 퍼지지만, 드문 대량 작업이 특정 샤드에 쏠리는 순간이 생긴다. 그리고 그 순간을 키운 것은 데이터 배치보다 작업의 모양(사용자 × 채널만큼 만들어지는 작업, 필요 없는 전체 조회)과 자동 복구의 가정(교체본은 금방 따라잡는다)이었다.

## Slack 글들이 말하지 않는 것

세 편 모두 Slack이 고른 이야기다. 2020년 글은 "성공을 확신할 때까지 기다렸다가" 썼다고 스스로 밝혔다. 3년 동안의 이전 중 실패한 시도, 되돌린 테이블, 들어간 인력과 비용은 나오지 않는다. 샤드 키를 테이블마다 어떻게 골랐는지, Vitess가 맞지 않아 남긴 1%가 무엇이었는지도 자세하지 않다. 액티브-액티브에서 primary-replica로 바꾸며 잃은 것(양쪽 쓰기 가용성)이 어떤 대가였는지도 평가하지 않는다. 2022년 장애 글은 영향받은 고객 수나 시간 같은 숫자를 주지 않는다. 2020년 이후 QPS가 얼마나 늘었는지, 지금도 같은 구성인지는 이번에 찾은 자료로는 알 수 없다.

## 우리 DB를 Vitess로 나누기 전에

Slack의 조건을 다시 보면, 고객 단위로 이미 샤딩된 MySQL 호스트가 수천 대, 초당 수십만 쿼리, MySQL 전용 쿼리 수천 개와 MySQL 기준의 운영 관행, 그리고 한 고객이 가장 큰 서버를 넘는 문제가 있었다. 이 조건에서 "MySQL은 그대로, 샤딩은 프록시로"가 합리적이었다. 데이터가 서버 한 대와 복제본 몇 대로 버티고, 큰 고객 하나가 서버 하나를 넘을 일이 없다면 같은 답이 아니다. Vitess를 들이면 VTGate, 태블릿, 토폴로지 서버라는 부품이 늘어난다. Slack도 RSS 기능 하나를 옮기는 데 배포·백업·디스커버리 절차를 다시 짜야 했다.

처음부터 따라 하면 드는 비용은 운영 부품만이 아니다. Slack 글이 강조한 것은 애플리케이션 쪽이다. 팀 ID를 가정한 코드, 샤드를 직접 여러 번 뒤지는 코드를 풀어야 했고, 그게 3년 이전의 상당 부분이었을 것이다. 샤드를 넘는 쿼리는 VTGate가 대신 펼쳐 줄 뿐 비용이 사라지지 않는다. Unified Grid의 "관련 워크스페이스 50개 제한"이 그 비용을 보여 준다.

작은 팀이 지금 가져올 것은 두 가지다. 첫째, 테넌트 ID 하나로 모든 테이블을 나누겠다고 정하기 전에, 가장 큰 테넌트가 서버 하나를 넘을 수 있는지, 테넌트를 넘는 기능(Slack Connect 같은)이 생길지를 먼저 묻는다. 둘째, 대량 작업(일괄 삭제, 재계산)에는 처음부터 속도 제한과 일괄 크기 상한을 둔다. Slack 장애의 출발점은 저장소가 아니라 사용자 수 × 채널 수만큼 불어난 작업이었다. 복제본을 쓰는 서비스라면 복제 지연을 지표로 보고, 지연이 기준을 넘는 복제본을 읽기에서 빼는 규칙을 정해 둔다. Slack은 그 기준을 1시간으로 적었다. 우리 서비스의 기준은 읽는 쪽이 얼마나 낡은 데이터를 견디는지에서 정한다.

비슷한 신호가 보이면 볼 곳도 있다. 특정 샤드만 CPU와 복제 지연이 치솟으면, 그 순간 돌고 있는 배치·비동기 작업과 그 작업이 만든 쿼리 모양부터 본다(같은 사용자의 전체 구독을 반복 조회하는 식). 자동 복구가 같은 호스트를 계속 만들고 지우면, 복구 조건(따라잡기 제한 시간)이 부하 상황을 가정했는지 본다. 그런 루프에서는 자동화를 멈추고 사람이 큰 인스턴스로 끊는 판단이 필요했다는 게 Slack의 기록이다.

## 면접에서 나올 만한 질문

### Slack의 워크스페이스 단위 샤딩은 왜 한계에 닿았나요?

샤드 키가 워크스페이스라서 한 고객을 두 서버로 나눌 수 없었기 때문이다. 큰 고객의 샤드는 가장 큰 하드웨어에 닿았고, 몇몇 샤드는 달아오르고 나머지는 놀았다. Enterprise Grid와 Slack Connect처럼 워크스페이스를 넘는 제품은 "한 팀의 데이터는 한 샤드"라는 전제를 깼고, 샤드 하나가 멈추면 그 샤드의 고객들은 Slack 전체를 못 썼다. 액티브-액티브라는 비표준 구성 때문에 운영 도구도 많이 직접 만들어야 했다.

### 왜 Slack은 애플리케이션 안에 새 샤딩 로직을 넣지 않고 Vitess를 골랐나요?

애플리케이션 로직과 저장 방식이 이미 강하게 엮여 있었고, 앱 안의 샤딩은 운영 문제와 복제본 활용을 풀지 못했기 때문이다. 시제품을 만들어 보니 팀 ID를 가정한 코드를 풀면서 새 방식을 만드는 데 오래 걸린다는 게 보였다. Vitess는 MySQL을 그대로 쓰면서 샤딩, 장애 조치, 백업, 토폴로지 관리를 맡아 줬고, 오픈소스라 부족한 기능을 Slack이 직접 기여할 수 있었다.

### 왜 Cassandra나 Spanner 같은 다른 저장소로 가지 않았나요?

MySQL 전용 문법을 포함한 쿼리 수천 개와 MySQL 기준으로 쌓인 운영 관행(백업, ETL, 컴플라이언스) 때문이다. 관계형 모델이나 MySQL을 떠나면 변경 폭이 훨씬 커서 NoSQL과 NewSQL을 제외했다고 글은 적었다. 작은 인프라 팀이 움직이는 부품이 적은 해법을 원했고, 회사가 핵심 스택에 새 기술을 들이는 데 보수적이었다는 맥락도 있다.

### Vitess에서 VTGate와 키스페이스 ID는 무엇을 하나요?

VTGate는 MySQL 프로토콜을 말하는 프록시라 애플리케이션은 샤드를 몰라도 되고, VTGate가 맞는 태블릿으로 보내 결과를 합친다. 행의 위치는 열 값을 vindex 함수로 바꾼 키스페이스 ID가 정하고, 샤드는 `-80`, `80-`처럼 키스페이스 ID 범위를 맡는다. 범위 샤딩이라 샤드 하나를 둘로 쪼개도 다른 샤드의 행은 옮기지 않는다. 샤드 키가 없는 질의는 모든 샤드로 펼쳐지니 lookup vindex를 둔다.

### 2020년 3월 쿼리가 한 주 만에 50% 늘었을 때 Slack은 어떻게 대응했나요?

가장 바쁜 키스페이스 하나를 Vitess의 분할 워크플로로 수평 확장했다. 범위 샤드를 쪼개 새 샤드로 복사하고 따라잡은 뒤 트래픽을 옮기는 방식이다. 글은 워크스페이스 샤딩에 머물렀다면 가장 큰 고객들을 위해 전혀 늘릴 수 없었을 것이라고 적었다.

### Vitess로 옮긴 뒤에도 2022년에 장애가 난 이유는요?

드문 대량 작업이 한 샤드에 쏠렸고, 자동 복구가 그 부하를 가정하지 않았기 때문이다. 한 고객의 대량 사용자 삭제가 사용자 × 채널 수만큼 작업을 만들었고, 구독 데이터의 6%를 가진 샤드에서 복제 지연과 primary OOM이 났다. 교체 복제본이 따라잡지 못하자 자동화가 건강하지 않다고 보고 지우면서 승격과 교체가 무한히 돌았다. 큰 인스턴스를 손으로 띄워 루프를 끊고, 작업 구조를 바꾸고, 스로틀링과 서킷 브레이커를 도입했다.

### 우리 서비스가 Slack 2016년의 10분의 1 규모라면 Vitess를 도입하나요?

먼저 샤딩이 필요한지부터 따진다. 데이터가 서버 한 대와 복제본으로 버티고 가장 큰 고객이 서버 하나를 넘을 일이 없다면, 인덱스·쿼리 정리와 읽기 복제본으로 충분하고 Vitess의 부품(VTGate, 태블릿, 토폴로지 서버)은 운영 부담만 늘린다. 다만 테넌트 하나가 서버를 넘을 조짐이 있거나 테넌트를 넘는 기능이 계획돼 있다면, 테넌트 ID로 모든 것을 나누는 설계를 피하고 데이터 종류별 샤드 키를 미리 생각해 둔다.

### 샤드 키를 워크스페이스에서 채널로 바꾸면 무엇을 잃나요?

한 고객의 데이터가 한 호스트에 있다는 단순함을 잃는다. 2020년 글이 장점으로 꼽은 "몇 분 안에 고객 문의를 DB 호스트로 연결"하는 디버깅이 어려워지고, 워크스페이스 전체를 훑는 쿼리는 여러 샤드로 펼쳐진다. Unified Grid 글이 워크스페이스 단위 데이터를 조회할 때 관련 워크스페이스를 50개로 제한한 것도 그 비용 때문이다. 대신 큰 고객의 부하가 여러 샤드로 흩어지고, 샤드 장애의 영향 범위가 줄어든다.
