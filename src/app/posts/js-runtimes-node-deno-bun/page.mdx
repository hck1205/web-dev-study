## 엔진부터 다르다

런타임은 자바스크립트 코드를 실제로 실행하는 엔진 위에 서 있다. 엔진이 코드를 기계어로 바꾸고, 가비지 컬렉션을 하고, 숫자와 문자열을 다룬다. 그 위에 런타임이 파일 읽기, 네트워크, 타이머 같은 바깥세상 기능을 붙인다.

- Node.js와 Deno는 구글의 V8 엔진을 쓴다. 크롬과 같은 엔진이다
- Bun은 애플 사파리의 JavaScriptCore(JSC)를 쓴다

엔진이 다르면 성능 특성이 달라진다. JSC는 시작이 빠르고 메모리를 적게 쓰는 편이고, V8은 오래 도는 서버에서 최적화가 잘 무르익는 편이다. 하지만 "어느 엔진이 빠르다"는 작업마다 뒤집히니 단정하기 어렵다. 실제로 세 런타임에서 같은 `node:http` 서버를 띄우고 메모리를 재 봤다.

```text
node  node-http.mjs            RSS 56704 KB
deno run node-http.mjs         RSS 65856 KB
bun  node-http.mjs             RSS 23436 KB
```

같은 서버인데 Bun이 메모리를 절반 이하로 썼다. 시작 시간도 같은 맥락이다. `console.log` 한 줄짜리 스크립트를 스무 번 돌린 중간값이다.

```text
node            40ms
deno run        54ms
bun              8ms
```

Bun의 빠른 시작은 짧게 끝나는 스크립트, CLI 도구, 서버리스 콜드 스타트에서 유리하다. 오래 도는 서버에서는 이 차이가 거의 묻힌다.

<Callout kind="note">
  이 숫자는 한 컨테이너(4코어)에서 특정 버전으로 한 번 잰 것이다. 버전과 하드웨어, 워크로드에 따라 쉽게 뒤집히니 "경향"으로만 읽는다. 중요한 건 숫자 자체가 아니라, 왜 이런 경향이 나오는지다.
</Callout>

## 코드가 바깥에 손대려면 허락을 받는다

가장 눈에 띄는 차이는 권한 모델이다. Node에서 스크립트를 실행하면 그 코드는 기본적으로 내 홈 디렉터리 파일을 읽고, 네트워크로 어디든 접속하고, 환경 변수를 다 볼 수 있다. 내가 설치한 npm 패키지 하나가 몰래 그런 일을 해도 막을 장치가 없다. 공급망 공격이 무서운 이유다.

Deno는 반대로 시작한다. 아무 권한도 없이 시작하고, 필요한 것만 플래그로 연다. 파일 읽기는 `--allow-read`, 네트워크는 `--allow-net`, 환경 변수는 `--allow-env`다. 범위도 좁힐 수 있다. `--allow-read=/etc/hostname`은 그 파일만 읽게 한다.

실험으로 확인해 봤다. 권한 없이 서버를 띄우면 환경 변수 접근부터 막힌다.

```text
error: Uncaught NotCapable: Requires env access to "PORT", run again with the --allow-env flag
```

`--allow-env`만 주고 네트워크를 안 열면 포트를 열 때 막힌다.

```text
error: Uncaught NotCapable: Requires net access to "0.0.0.0:3004", run again with the --allow-net flag
```

파일 하나만 읽게 하고 네트워크 접속을 시도하면, 읽기는 되고 접속만 막힌다.

```text
read ok: 2 chars
error: Uncaught (in promise) NotCapable: Requires net access to "example.com:443", run again with the --allow-net flag
```

코드가 몰래 파일을 빼내 외부로 보내려 해도, 네트워크 권한을 안 줬으면 못 보낸다. 공급망 공격의 피해를 줄이는 실질적인 장치다.

Node도 이 방향을 따라오고 있다. `--permission` 플래그로 비슷한 모델을 쓸 수 있다. Node 22에서 실험해 봤다.

```bash
# 이 폴더만 읽게 허용하고 /etc/hostname은 막는다
node --permission --allow-fs-read="$PWD/*" read.mjs
```

```text
Error: Access to this API has been restricted. Use --allow-fs-read to manage permissions.
  code: 'ERR_ACCESS_DENIED',
  permission: 'FileSystemRead',
  resource: '/etc/hostname'
```

`/etc/hostname`을 추가로 허용하니 통과했다. Node의 권한 모델은 Deno보다 늦게 나왔고 세부가 다르니, 쓸 거라면 지금 버전의 문서를 확인한다.

## 도마와 칼이 들어 있다

Node는 오래 "작은 코어 + npm 생태계" 철학이었다. 번들러, 테스트 러너, 포매터, 타입스크립트 실행을 각각 npm 패키지로 깔았다. Deno와 Bun은 이걸 런타임 안에 넣었다.

- 테스트: `deno test`, `bun test`가 내장이다. Node도 22부터 `node --test`가 기본이다
- 번들링: Deno는 `deno bundle`, Bun은 `bun build`가 있다
- 패키지 매니저: Bun은 `bun install`이 npm보다 훨씬 빠르다고 내세운다. Deno는 URL이나 `jsr:`, `npm:` 지정자로 모듈을 가져온다
- 타입스크립트: 셋 다 `.ts` 파일을 설정 없이 실행한다

타입스크립트 실행에는 중요한 차이가 있다. 같은 타입 붙은 파일을 세 런타임에서 돌려 봤다.

```ts
type User = { id: number; name: string };
const u: User = { id: 1, name: "kim" };
console.log(`user ${u.name}`);
```

```text
node       user kim
deno run   user kim
bun        user kim
```

셋 다 잘 돌았다. 하지만 이건 "타입을 지우고 실행"하는 것이지 "타입을 검사"하는 게 아니다. Node의 기본 방식(type stripping)은 타입 표기만 떼어 내고 자바스크립트로 돌린다. 그래서 자바스크립트로 단순 변환되지 않는 TypeScript 전용 문법은 막힌다. `enum`을 써 봤다.

```text
SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript enum is not supported in strip-only mode
```

`enum`은 런타임 코드를 만들어 내야 해서 단순 제거로는 안 된다. 그래서 타입 검사는 여전히 `tsc`나 에디터가 따로 해야 하고, 런타임이 `.ts`를 돈다는 건 "타입이 맞는지 봐 준다"가 아니라 "컴파일 단계를 건너뛰고 바로 실행한다"는 뜻이다. 이 구분은 [번들러 기초](/posts/bundler-basics)에서 트랜스파일과 타입 검사를 나눈 것과 같다.

## 테스트 하나로 세 러너를 보기

내장 테스트 러너를 비교하려고, 일부러 실패하는 테스트를 하나 넣었다. 부동소수점의 `0.1 + 0.2`가 `0.3`과 다른 그 유명한 문제다.

```ts
import { test } from "node:test";
import assert from "node:assert/strict";

const sum = (xs: number[]) => xs.reduce((a, b) => a + b, 0);
test("빈 배열은 0", () => assert.equal(sum([]), 0));
test("소수 합", () => assert.equal(sum([0.1, 0.2]), 0.3)); // 일부러 실패
```

세 러너의 출력이다.

```text
== node --test
ok 1 - 빈 배열은 0
not ok 2 - 소수 합
  expected: 0.3
  actual: 0.30000000000000004
# pass 1
# fail 1

== deno test
빈 배열은 0 ... ok (0ms)
소수 합 ... FAILED (2ms)
FAILED | 1 passed | 1 failed

== bun test
(fail) 소수 합
 1 pass
 1 fail
```

세 러너 모두 같은 실패를 잡았다. 흥미로운 건 Deno와 Bun이 `node:test`와 `node:assert`를 그대로 실행했다는 점이다. Node의 내장 모듈을 다른 런타임이 지원하는 것, 이게 다음 주제다.

이 `sum`은 간단하니 직접 고쳐 볼 수 있다. 빈 배열은 0, 소수 합은 정밀도 문제까지 다루는 함수를 만들어 보자.

## npm 호환은 범위의 문제다

Deno와 Bun을 쓸 수 있느냐는 결국 "내가 쓰는 npm 패키지가 거기서 도느냐"로 갈린다. 둘 다 npm 설치와 `node:` 내장 모듈을 지원하지만 범위가 다르다.

- Bun은 처음부터 Node 호환을 최우선으로 삼았다. `node_modules`를 그대로 쓰고 `package.json`을 읽는다. 대부분의 Express 앱이 바로 돈다
- Deno는 초기엔 Node와 일부러 다른 길을 갔다가, 2.0부터 `node_modules`와 `package.json`, `npm:` 지정자를 본격 지원했다. 이제 상당수 Node 패키지가 돈다

실험에서 세 런타임 모두 같은 `node:http` 서버를 실행했다. 다 돌았다. 하지만 함정은 네이티브 애드온(C++로 짠 모듈)과, 잘 안 쓰이는 `node:` API의 구석진 동작이다. 이런 건 런타임마다 지원이 다르고 버전마다 바뀐다. 그래서 "대부분 돈다"는 말과 "우리 의존성 전부가 돈다"는 말 사이엔 늘 간격이 있다. 옮기기 전에 실제 의존성으로 테스트를 돌려 보는 게 유일한 답이다. 의존성이 뒤엉키는 문제는 [의존성 지옥](/posts/dependency-hell)에서 따로 다뤘다.

## 웹 표준 fetch로 서버를 짜면

세 런타임이 수렴하는 지점도 있다. 웹 표준 `Request`를 받아 `Response`를 돌려주는 함수 하나로 서버를 짜는 방식이다. 브라우저의 `fetch`와 같은 객체다.

```ts
// 세 런타임에서 거의 같은 코드
export default {
  fetch(req: Request): Response {
    const url = new URL(req.url);
    if (url.pathname === "/hello") return Response.json({ hello: "world" });
    return new Response(null, { status: 404 });
  },
};
```

Deno는 `deno serve`로, Bun은 `Bun.serve`로 이 함수를 바로 서빙한다. 이 흐름은 WinterTC(옛 WinterCG)라는 모임이 표준화하려는 방향이다. 서버와 엣지, 서버리스에서 같은 `Request`/`Response` API를 쓰자는 것이다. Cloudflare Workers, Vercel Edge 같은 엣지 런타임이 이 모양을 따르기 때문에, 이 스타일로 짜 두면 런타임을 옮기기 쉽다.

Node는 이 함수를 직접 서빙하지 않아 `node:http`에 잇는 작은 어댑터가 필요하다. 그래서 이 스타일은 Deno와 Bun이 더 자연스럽다.

## 벤치마크 숫자가 서비스에서 녹는 자리

이제 "세 배 빠르다"를 직접 확인해 보자. 같은 `/hello` 응답을 autocannon으로 동시 연결 50개, 6초씩 두드렸다. 두 가지로 쟀다. 하나는 순수 HTTP 서버, 하나는 각 런타임의 네이티브 fetch 서버다.

```text
node  node:http              req/s 22489  p99 9ms
deno  node:http compat       req/s 18333  p99 8ms
bun   node:http compat       req/s 20543  p99 10ms
deno  deno serve(fetch)      req/s 24626  p99 10ms
bun   Bun.serve(fetch)       req/s 33404  p99 6ms
```

여기선 Bun의 네이티브 서버가 가장 빨랐다. `node:http` 호환 모드로는 셋이 비슷했다. 광고의 "몇 배"는 보통 네이티브 서버로, 아무 일도 안 하는 응답을 쟀을 때 나온다. 문제는 실제 서비스가 아무 일도 안 하지 않는다는 것이다.

DB를 부르는 상황을 흉내 내려고, 응답 전에 20ms만 기다리는 라우트로 같은 측정을 했다.

```text
node  20ms wait              req/s 2136  p99 35ms
deno  20ms wait              req/s 2037  p99 45ms
bun   20ms wait              req/s 2278  p99 30ms
```

20ms 기다림 하나가 들어가자 처리량이 10분의 1로 떨어지고, 세 런타임의 차이는 거의 사라졌다. 실제 서비스는 DB 조회, 외부 API 호출, 직렬화에 훨씬 많은 시간을 쓴다. 런타임이 요청을 받아 넘기는 데 드는 시간은 전체의 작은 조각이다. 그래서 "라우팅 벤치마크에서 3배"가 "우리 서비스에서 3배"로 이어지는 일은 드물다. 이건 [Node.js 웹 프레임워크](/posts/nodejs-web-frameworks) 비교에서 본 것과 똑같은 결론이다.

<Callout kind="tip">
  런타임이나 프레임워크를 고를 때 라우팅 처리량보다 먼저 볼 것은, 내 서비스가 시간을 어디에 쓰는가다. 대부분은 I/O 대기이고, 거기선 런타임 차이가 거의 묻힌다.
</Callout>

## 운영에서 고를 때

그래서 셋을 언제 고르나.

Node는 기본값이다. 생태계가 가장 넓고, 네이티브 애드온까지 거의 다 돌고, 문제가 생겼을 때 검색으로 답이 나온다. 권한 모델과 내장 테스트까지 따라오면서 "오래된 것"의 단점도 줄었다. 특별한 이유가 없으면 Node다.

Deno는 권한 모델이 중요하거나, 설정 없이 타입스크립트와 내장 도구로 빠르게 시작하고 싶을 때, 그리고 엣지/서버리스 스타일의 fetch 서버를 짤 때 매력적이다. 믿을 수 없는 코드를 실행하는 자리라면 기본 차단 권한이 큰 장점이다.

Bun은 빠른 시작과 빠른 설치, 낮은 메모리가 분명한 이점이다. 콜드 스타트가 잦은 서버리스나 CI에서 특히 그렇다. 다만 운영에서 고를 땐 위험을 함께 본다. Node보다 역사가 짧아 구석진 `node:` API나 네이티브 애드온에서 예상 못 한 차이가 나올 수 있고, 커뮤니티와 운영 사례가 아직 얇다. 그래서 핵심 서비스에 넣기 전에 실제 의존성과 부하로 충분히 검증하고, 되돌릴 길을 열어 둔다.

세 런타임이 서로의 좋은 점을 빠르게 베끼고 있다는 것도 흐름이다. Node는 권한과 내장 테스트를, Deno는 npm 호환을, 모두가 웹 표준 fetch를 향해 수렴한다. 그래서 웹 표준에 가깝게, 특정 런타임 전용 API를 줄여 짜 두면 나중에 갈아타기 쉽다.

## 면접에서 나올 만한 질문

### Node, Deno, Bun은 각각 어떤 엔진을 쓰고 그게 왜 중요한가

Node와 Deno는 구글 V8을, Bun은 애플 JavaScriptCore를 쓴다. 엔진이 시작 시간, 메모리, 최적화 특성을 좌우한다. 실험에서 Bun은 시작이 빠르고(스크립트 기동 중간값 8ms 대 Node 40ms) 메모리를 적게 썼다. 다만 "어느 엔진이 빠르다"는 작업마다 뒤집히니 경향으로만 본다.

### Deno의 권한 모델이 공급망 공격에 어떻게 도움이 되나

Deno는 기본적으로 파일, 네트워크, 환경 변수 접근이 모두 막혀 있고 필요한 것만 플래그로 연다. 그래서 내가 설치한 패키지가 몰래 파일을 읽어 외부로 보내려 해도, 네트워크 권한을 안 줬으면 못 보낸다. 실험에서 파일 읽기 권한만 준 코드는 읽기는 되고 외부 접속만 막혔다. Node도 `--permission`으로 비슷한 모델을 제공하지만 더 늦게 나왔고 세부가 다르다.

### 런타임이 .ts 파일을 바로 실행한다는 것이 타입 검사를 해 준다는 뜻인가

아니다. 기본 방식은 타입 표기만 떼어 내고(type stripping) 자바스크립트로 실행하는 것이다. 타입이 맞는지는 보지 않는다. 그래서 타입 검사는 여전히 `tsc`나 에디터가 따로 해야 한다. 또 `enum`처럼 런타임 코드를 만들어 내야 하는 TypeScript 전용 문법은 단순 제거로 안 돼 막히기도 한다.

### Bun이 벤치마크에서 몇 배 빠르다는데 실제 서비스에서도 그런가

보통 그렇지 않다. 광고 숫자는 네이티브 서버로 아무 일도 안 하는 응답을 쟀을 때 나온다. 실험에서 응답 전에 20ms만 기다리게 하자 세 런타임 처리량이 모두 10분의 1로 떨어지고 차이가 거의 사라졌다. 실제 서비스는 DB, 외부 API, 직렬화에 시간을 쓰고 대부분 I/O 대기라, 런타임이 요청을 넘기는 시간은 전체의 작은 조각이다.

### WinterTC(옛 WinterCG)와 웹 표준 fetch 서버가 왜 중요한가

`Request`를 받아 `Response`를 돌려주는 함수로 서버를 짜는 방식을 서버, 엣지, 서버리스에서 공통으로 쓰자는 표준화 흐름이다. Cloudflare Workers, Vercel Edge 같은 엣지 런타임이 이 모양을 따른다. 이 스타일로, 특정 런타임 전용 API를 줄여 짜 두면 런타임을 옮기기 쉽다. Deno의 `deno serve`와 Bun의 `Bun.serve`가 이 함수를 바로 서빙한다.

### 운영 서비스에 Bun을 고를 때 조심할 점은

빠른 시작과 설치, 낮은 메모리는 분명한 장점이지만, Node보다 역사가 짧아 구석진 `node:` API나 네이티브 애드온에서 예상 못 한 차이가 나올 수 있고 운영 사례가 아직 얇다. 그래서 핵심 서비스에 넣기 전에 실제 의존성과 부하로 검증하고, 네이티브 애드온 지원을 확인하며, 문제가 생기면 Node로 되돌릴 길을 열어 둔다.

### 세 런타임 중 하나를 골라 두면 나중에 갈아타기 쉽게 하려면 어떻게 짜나

웹 표준에 가깝게 짠다. `Request`/`Response`, `fetch`, `URL` 같은 표준 API를 쓰고, 특정 런타임 전용 API는 얇은 층으로 감싸 한곳에 모은다. 세 런타임이 서로의 기능을 빠르게 베끼며 웹 표준으로 수렴하고 있어서, 표준에 붙어 있을수록 이식이 쉽다.
