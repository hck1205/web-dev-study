밤새 돈 데이터 내보내기 Job이 아침에 `Failed`로 남아 있다. Pod를 열어 보니 네 개가 전부 `Error`이고, 로그는 마지막 하나만 남았다. 같은 설정 오류로 네 번 실패하는 데 3분이 걸렸고, 그동안 같은 파일을 네 번 반쯤 썼다. 다른 날에는 노드 점검으로 쫓겨난 것까지 실패로 세서 재시도 횟수를 다 써 버렸다. 끝나는 작업을 맡기는 Job은 단순해 보이지만, 실패를 어떻게 세고 언제 포기할지를 정하지 않으면 이런 일이 생긴다.

이 글은 Job 컨트롤러가 Pod를 몇 개, 몇 번, 얼마나 오래 돌리는지 정하는 필드를 따라간다. completions와 parallelism, backoffLimit와 재시도 간격, activeDeadlineSeconds와 ttlSecondsAfterFinished, 번호를 붙여 일을 나누는 Indexed Job과 번호별 재시도, 실패의 종류를 가르는 podFailurePolicy, 그리고 CronJob이 놓친 회차를 어떻게 처리하는지다. 출력은 kwok로 띄운 Kubernetes 1.34.1 클러스터에서 받았다. Job 컨트롤러는 진짜이고, 컨테이너가 성공하거나 정해진 종료 코드로 실패하는 것만 kwok 단계(stage) 설정으로 흉내 냈다.

이 주제의 다른 글: CronJob의 스케줄 문법, 시간대와 서머타임, concurrencyPolicy 세 값의 비교는 [크론 잡 글](/posts/cron-jobs#쿠버네티스-cronjob의-설정들)에서 실제 이벤트로 다뤘다. 여기서는 그 아래의 Job 쪽을 깊게 본다. 작업 자체를 두 번 돌아도 괜찮게 만드는 법은 [배치 처리 글](/posts/batch-processing#두-번-돌아도-결과가-같게-쓴다)에 있다.

## 끝나야 성공인 Pod

Deployment의 Pod는 끝나면 실패다. 컨테이너가 종료되면 kubelet이 다시 띄운다. Job의 Pod는 종료 코드 0으로 끝나야 성공이다. 그래서 Job의 Pod 템플릿에는 `restartPolicy: Always`를 쓸 수 없고 `Never`나 `OnFailure`만 받는다.

- `Never`: 컨테이너가 실패하면 Pod가 `Failed`로 끝나고, Job 컨트롤러가 새 Pod를 만든다. 실패한 Pod가 남아서 로그를 볼 수 있다.
- `OnFailure`: kubelet이 같은 Pod 안에서 컨테이너만 다시 띄운다. Pod가 노드에 남으니 빠르지만, 재시작 횟수가 backoffLimit에 닿으면 Pod 자체가 종료되어 로그를 보기 어렵다. 공식 문서도 디버깅할 때는 `Never`를 권한다.

Job이 알아야 할 숫자는 두 개다. `completions`는 성공한 Pod가 몇 개 나와야 끝나는지, `parallelism`은 동시에 몇 개까지 돌릴지다. 둘 다 생략하면 1이다.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: thumbs
  namespace: batch
spec:
  completions: 5        # 성공한 Pod가 5개 나와야 끝난다
  parallelism: 2        # 동시에 최대 2개
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: thumbs
        image: example/thumbs:1.4
```

```bash
# 시각을 붙여 Pod가 생기고 끝나는 순간을 본다
kubectl -n batch get pods -w --output-watch-events | while read -r l; do echo "$(date +%T) $l"; done
```

이 방식은 Pod들이 같은 일을 나눠 가질 방법을 Job이 주지 않는다는 점을 기억해 둔다. Pod 다섯이 모두 같은 명령을 받는다. 일감을 나누려면 큐에서 하나씩 꺼내 가게 하거나(작업 큐 패턴, 이때는 completions를 비우고 parallelism만 준다), 아래에서 볼 Indexed Job으로 번호를 받아 범위를 나눈다.

공식 문서에는 한 문장이 더 있다. parallelism과 completions를 1로 두고 `Never`를 써도 같은 프로그램이 두 번 시작될 수 있다. 노드가 끊겨 컨트롤러가 Pod를 잃었다고 판단하는 경우 같은 것이다. 그래서 Job으로 돌리는 작업은 두 번 돌아도 결과가 같아야 한다. 이 이야기는 글 끝에서 다시 한다.

## 실패를 몇 번까지 참나: backoffLimit

`backoffLimit`(기본 6)은 실패한 Pod를 몇 개까지 참을지다. 언제나 실패하는 Job에 3을 줬다.

```yaml
spec:
  backoffLimit: 3          # 실패를 3번까지 참는다. 4번째 실패에서 Job이 실패한다
```

```bash
# Pod가 만들어진 시각과 끝난 시각, 종료 코드
kubectl -n batch get pods -l job-name=export --sort-by=.metadata.creationTimestamp \
  -o custom-columns=NAME:.metadata.name,CREATED:.metadata.creationTimestamp,FINISHED:.status.containerStatuses[0].state.terminated.finishedAt,EXIT:.status.containerStatuses[0].state.terminated.exitCode
kubectl -n batch describe job export | sed -n '/Events/,$p'
```


Job의 상태 조건도 함께 본다.

```bash
# 실패 이유는 conditions에 남는다
kubectl -n batch get job export -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}: {.message}{"\n"}{end}'
```

```text
FailureTarget=True BackoffLimitExceeded: Job has reached the specified backoff limit
Failed=True BackoffLimitExceeded: Job has reached the specified backoff limit
```

`FailureTarget`이 먼저 붙고, 남은 Pod가 모두 정리된 뒤 `Failed`가 붙는다. 실패를 감지하는 스크립트나 알림은 `Failed` 조건을 보면 된다. `kubectl wait --for=condition=Failed job/export`로 기다릴 수도 있다.

숫자를 고를 때는 작업의 성격을 본다. 외부 API 일시 장애처럼 다시 하면 될 실패가 많으면 기본값 6이 괜찮다. 결제나 메일처럼 두 번 하면 안 되는 작업은 0으로 두고, 재시도는 작업이 멱등할 때만 켠다. 그리고 "다시 해 봐야 소용없는 실패"(설정 오류, 잘못된 입력)는 횟수와 상관없이 바로 멈추고 싶다. 그게 아래 podFailurePolicy다.

## 시간 한도와 뒷정리

`activeDeadlineSeconds`는 Job 전체가 쓸 수 있는 시간이다. 재시도를 포함해 이 시간을 넘기면 돌던 Pod까지 지우고 실패로 끝낸다. 2분 걸리는 작업에 20초를 줬다.

```yaml
spec:
  activeDeadlineSeconds: 20   # Job 전체가 20초를 넘기면 끝낸다
  backoffLimit: 6
```

```bash
# 시간 한도에 걸린 Job
kubectl -n batch get job reindex
kubectl -n batch get pods -l job-name=reindex
kubectl -n batch describe job reindex | sed -n '/Events/,$p'
```

```text
NAME      STATUS   COMPLETIONS   DURATION   AGE
reindex   Failed   0/1           30s        30s
No resources found in batch namespace.
Events:
  Type     Reason            Age   From            Message
  ----     ------            ----  ----            -------
  Normal   SuccessfulCreate  30s   job-controller  Created pod: reindex-4znsm
  Normal   SuccessfulDelete  10s   job-controller  Deleted pod: reindex-4znsm
  Warning  DeadlineExceeded  5s    job-controller  Job was active longer than specified deadline
```

Pod가 지워져서 로그도 없다. 시간 한도로 죽은 작업이 어디까지 했는지 알려면 로그를 클러스터 밖으로 보내 두거나, 작업이 진행 위치를 DB에 남겨야 한다. `activeDeadlineSeconds`가 `backoffLimit`보다 먼저다. 시간 안에 재시도가 남아 있어도 시간이 끝나면 멈춘다.

이 값이 없으면 멈춰 버린 작업(데드락, 응답 없는 외부 호출)이 영원히 돈다. CronJob에서 `concurrencyPolicy: Forbid`와 만나면 그 하나가 이후 모든 회차를 막는다. 그래서 정기 작업에는 평소 실행 시간의 몇 배 정도로 꼭 걸어 둔다.

뒷정리는 `ttlSecondsAfterFinished`가 맡는다. 성공이든 실패든 끝나고 이 시간이 지나면 TTL 컨트롤러가 Job과 Pod를 지운다(1.23부터 정식).

```yaml
spec:
  ttlSecondsAfterFinished: 30  # 끝나고 30초 뒤 Job과 Pod를 지운다
```

실습에서 `cleanup` Job은 끝난 지 30초 남짓 뒤에 목록에서 사라졌다. 이 값이 없는 Job은 끝나도 Pod와 함께 계속 남는다. 하루에 수천 개를 만드는 파이프라인이라면 etcd와 API 서버에 끝난 객체가 쌓인다. 반대로 너무 짧으면 실패 원인을 보기 전에 사라진다. 실패를 조사할 시간(예: 하루)을 남기고, 로그는 따로 모은다. CronJob이 만든 Job은 `successfulJobsHistoryLimit`, `failedJobsHistoryLimit`로 개수 기준 정리를 하니 둘 중 먼저 걸리는 쪽이 지운다.

## 번호를 받아 일을 나누는 Indexed Job

`completionMode: Indexed`로 두면 Pod마다 0부터 `completions-1`까지 번호가 붙는다. 번호마다 성공이 하나씩 나와야 Job이 끝난다.

```yaml
spec:
  completionMode: Indexed   # Pod마다 0..completions-1 번호를 준다
  completions: 4
  parallelism: 2
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: worker
        image: example/shard-worker:1.0
        command: ["sh", "-c", "process --shard=$JOB_COMPLETION_INDEX --total=4"]
```

```bash
# 번호, hostname, 컨트롤러가 넣은 환경 변수
kubectl -n batch get pods -l job-name=shard \
  -o custom-columns=NAME:.metadata.name,INDEX:.metadata.annotations.batch\\.kubernetes\\.io/job-completion-index,HOSTNAME:.spec.hostname,STATUS:.status.phase
kubectl -n batch get pod shard-0-7kt25 \
  -o jsonpath='{range .spec.containers[0].env[*]}{.name}={.valueFrom.fieldRef.fieldPath}{"\n"}{end}'
kubectl -n batch get job shard -o jsonpath='{.status.completedIndexes} succeeded={.status.succeeded}{"\n"}'
```

```text
NAME            INDEX   HOSTNAME   STATUS
shard-0-7kt25   0       shard-0    Running
shard-1-nf97t   1       shard-1    Running
JOB_COMPLETION_INDEX=metadata.labels['batch.kubernetes.io/job-completion-index']
0-3 succeeded=4
```

매니페스트에 적지 않은 `JOB_COMPLETION_INDEX` 환경 변수를 컨트롤러가 넣었다. 값은 Pod 라벨에서 온다. 번호는 어노테이션, 라벨, hostname, Pod 이름에 모두 들어간다. Pod 이름을 조각으로 읽어 보면 이렇다.

범위를 실행 시각이 아니라 번호로 정하면, 같은 번호가 다시 돌아도 같은 범위를 본다. 재시도가 안전해지는 첫걸음이다. DB에서 범위를 나눠 여러 작업자가 돌리는 다른 방법(SKIP LOCKED 작업 큐)은 [배치 처리 글](/posts/batch-processing#여러-작업자로-나눠-돌리기)에 있다.

### 번호마다 따로 세는 backoffLimitPerIndex

backoffLimit은 Job 전체의 실패를 센다. 번호 하나가 계속 실패하면 그 하나가 한도를 다 써서 멀쩡한 나머지까지 멈춘다. `backoffLimitPerIndex`(1.33부터 정식)는 번호마다 따로 센다. 번호 2만 언제나 종료 코드 3으로 실패하게 만들어 돌렸다.

```yaml
spec:
  completionMode: Indexed
  completions: 4
  parallelism: 4
  backoffLimitPerIndex: 1   # 번호마다 재시도 1번
  maxFailedIndexes: 1       # 실패한 번호가 1개를 넘으면 Job 전체를 일찍 멈춘다
```

```bash
# 번호별 결과와 Job 상태
kubectl -n batch get pods -l job-name=shard-pi --sort-by=.metadata.creationTimestamp \
  -o custom-columns=NAME:.metadata.name,INDEX:.metadata.annotations.batch\\.kubernetes\\.io/job-completion-index,STATUS:.status.phase,EXIT:.status.containerStatuses[0].state.terminated.exitCode
kubectl -n batch get job shard-pi \
  -o jsonpath='completed={.status.completedIndexes} failed={.status.failedIndexes} succeeded={.status.succeeded} failedPods={.status.failed}{"\n"}{range .status.conditions[*]}{.type}={.status} {.reason}: {.message}{"\n"}{end}'
```


## 실패의 종류를 가르는 podFailurePolicy

backoffLimit은 실패를 모두 같게 센다. 하지만 실패에는 종류가 있다. 앱이 "설정이 틀렸다"고 정해진 코드로 끝났다면 다시 해 봐야 소용없다. 노드 점검으로 쫓겨났다면 앱 잘못이 아니니 횟수에서 빼야 한다. `podFailurePolicy`(1.31부터 정식)가 이 구분을 한다.

```yaml
spec:
  backoffLimit: 6
  podFailurePolicy:
    rules:
    - action: FailJob            # 설정 오류(42)는 다시 해 봐야 소용없다
      onExitCodes:
        containerName: migrate
        operator: In
        values: [42]
    - action: Ignore             # 노드 drain·선점으로 쫓겨난 건 실패로 세지 않는다
      onPodConditions:
      - type: DisruptionTarget
  template:
    spec:
      restartPolicy: Never       # podFailurePolicy는 Never에서만 쓸 수 있다
```

규칙은 위에서부터 차례로 맞춰 보고 처음 맞은 것 하나만 적용한다. 동작은 넷이다. `FailJob`은 Job을 바로 실패시키고, `Ignore`는 실패로 세지 않고 다시 만들고, `Count`는 평소처럼 세고, `FailIndex`는 Indexed Job에서 그 번호만 실패로 표시한다. 맞는 규칙이 없으면 `Count`다. 아래 그림은 Pod 하나가 끝났을 때 컨트롤러가 무엇을 보는지다.

### 쫓겨난 Pod는 세지 않는다

두 번째 규칙을 확인하려고 `backoffLimit: 0`인 Job을 띄우고 그 노드를 drain했다. 실패를 하나도 못 참는 Job이다.

```bash

kubectl drain worker-2 --ignore-daemonsets --delete-emptydir-data --pod-selector=job-name=nightly
```

## 멈춰 두고, 손으로 돌리고

Job은 `suspend: true`로 만들면 Pod를 만들지 않고 기다린다. 대기열 시스템이 자리가 날 때 풀어 주는 방식이 이걸 쓴다.

```bash
# 멈춘 채로 만든 Job을 풀어 준다
kubectl -n batch get job backfill
kubectl -n batch patch job backfill --type merge -p '{"spec":{"suspend":false}}'
kubectl -n batch describe job backfill | sed -n '/Events/,$p'
```

```text
NAME       STATUS      COMPLETIONS   DURATION   AGE
backfill   Suspended   0/1                      3s
job.batch/backfill patched
Events:
  Type    Reason            Age   From            Message
  ----    ------            ----  ----            -------
  Normal  Suspended         7s    job-controller  Job suspended
  Normal  SuccessfulCreate  4s    job-controller  Created pod: backfill-jnhjc
  Normal  Resumed           4s    job-controller  Job resumed
```

돌고 있는 Job을 suspend하면 아직 끝나지 않은 Pod에 SIGTERM을 보내 종료시키고, 이렇게 끝난 Pod는 completions에 들어가지 않는다. 앱이 종료 유예 시간 안에 진행 위치를 저장해야 하는 이유다. 다시 풀면 시작 시각이 새로 잡혀 activeDeadlineSeconds도 처음부터 잰다. 그리고 Job의 Pod 템플릿은 만든 뒤에 못 바꾼다.

```bash
# 만든 Job의 이미지를 바꿔 본다
kubectl -n batch set image job/backfill backfill=example/backfill:1.1
```

```text
error: failed to patch image update to pod template: Job.batch "backfill" is invalid: spec.template: Invalid value: ...: field is immutable
```

(가운데의 긴 템플릿 덤프는 줄였다.) 고친 이미지로 다시 돌리려면 지우고 새로 만든다. 같은 이름을 쓰려면 이전 Job을 먼저 지워야 하니, 파이프라인에서는 이름에 실행 번호나 시각을 붙이거나 `generateName`을 쓴다. Helm 훅으로 마이그레이션 Job을 돌리다 "field is immutable"을 만나는 것도 같은 이유다([Helm 릴리스 글](/posts/helm-release-lifecycle)).

## CronJob은 놓친 회차를 몰아서 돌리지 않는다

CronJob은 정해진 시각마다 Job 템플릿으로 Job을 하나 만든다. 설정 하나하나의 동작은 [크론 잡 글](/posts/cron-jobs#쿠버네티스-cronjob의-설정들)에서 실제 이벤트로 봤으니, 여기서는 그 글에서 다루지 않은 질문 하나를 확인했다. 컨트롤러가 회차를 여러 번 놓치면 돌아왔을 때 몇 번 돌리나.

매분 도는 CronJob을 만들고, 3분 넘게 `suspend: true`로 멈췄다가 풀었다. `startingDeadlineSeconds`는 300초라 놓친 세 회차 모두 "늦게라도 시작해도 되는" 범위 안이다.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: digest
  namespace: batch
spec:
  schedule: "* * * * *"
  timeZone: "Asia/Seoul"
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 300
  jobTemplate:
    spec:
      backoffLimit: 2
      ttlSecondsAfterFinished: 3600
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: digest
            image: example/digest:1.2
```

```bash
# 01:23:35에 멈추고 01:26:55에 풀었다. 풀고 20초 뒤
kubectl -n batch get cronjob digest
kubectl -n batch get jobs
kubectl -n batch get events --field-selector involvedObject.kind=CronJob --sort-by=.lastTimestamp
```

Job 이름 끝 숫자는 예정 시각을 유닉스 분으로 적은 것이다. 29875763 × 60초는 2026-10-21 01:23:00 UTC(한국 시각 10:23), 29875766은 01:26:00, 29875767은 01:27:00이다. 멈춰 있던 동안 01:24, 01:25, 01:26 세 회차를 놓쳤는데, 풀린 뒤 만든 것은 가장 최근의 01:26 회차 하나뿐이다. 01:24와 01:25는 그냥 지나갔다. 그다음 01:27 회차는 정상으로 돌았다.

정리하면 컨트롤러는 놓친 회차를 세기는 하지만 그중 마지막 하나만 실행한다. 정산처럼 회차마다 한 번씩 꼭 돌아야 하는 작업이라면, 이 동작 때문에 빠진 날이 생긴다. 그래서 작업이 "어제 하루"처럼 고정된 범위가 아니라 "마지막으로 처리한 지점부터 지금까지"를 처리하게 만들면 빠진 회차가 다음 회차에서 메워진다. 반대로 고정 범위로 처리하는 작업이라면 빠진 회차를 알아채는 감시가 필요하다([크론 잡 글](/posts/cron-jobs#안-돈-것을-알아채는-법)의 dead man's switch).

놓친 회차가 100개를 넘으면 아예 시작하지 않고 "too many missed start times" 에러를 남긴다고 공식 문서가 적고 있다. `startingDeadlineSeconds`를 주면 그 시간 안의 회차만 세니 이 문제를 피한다. 매분 도는 CronJob에 이 값이 없으면 컨트롤러가 두 시간 가까이 멈췄다 돌아왔을 때 이 한도에 걸린다.

### 손으로 한 번 돌리기

배포 직후 확인하거나 실패한 회차를 다시 돌릴 때는 CronJob에서 Job을 바로 만든다.

```bash
# CronJob 템플릿으로 Job 하나를 지금 만든다
kubectl -n batch create job digest-manual --from=cronjob/digest
kubectl -n batch get job digest-manual -o jsonpath='{.metadata.annotations}{"\n"}{.metadata.ownerReferences}{"\n"}'
```

```text
job.batch/digest-manual created
{"cronjob.kubernetes.io/instantiate":"manual"}
[{"apiVersion":"batch/v1","controller":true,"kind":"CronJob","name":"digest","uid":"0ac42f02-da86-4d7e-827e-9fe32bbe470a"}]
```

`instantiate: manual` 어노테이션이 붙고 주인은 CronJob이다. CronJob을 지우면 이 Job도 함께 지워진다. 손으로 돌린 시각이 예약 회차와 가까우면 두 Job이 같은 범위를 처리할 수 있으니, 정기 작업 바로 앞뒤에는 손 실행을 피하거나 작업 쪽 잠금에 기댄다.

CronJob의 `jobTemplate`을 고치면 다음 회차부터 적용된다. 이미 돌고 있는 Job은 옛 템플릿 그대로다. 이미지를 고쳤는데 "아직도 옛 버전이 돈다"면 그 회차가 고치기 전에 만들어졌는지 Job의 생성 시각을 본다.

## 두 번 돌아도 괜찮게 만들기

여기까지 본 장치를 모아 보면, 쿠버네티스가 약속하는 것은 "정확히 한 번"이 아니다. Job은 같은 프로그램을 두 번 시작할 수 있고, 교체 정책에 따라 옛 Pod와 새 Pod가 겹칠 수 있고, CronJob은 회차를 건너뛰거나 드물게 두 번 만든다. 그래서 작업 쪽이 마지막 방어선이 된다.

- 처리 범위는 번호나 회차로 정한다. Indexed Job의 번호, CronJob 회차 시각(Job 이름 끝 숫자를 환경 변수로 넘기는 방법이 있다)으로 범위를 계산하면 다시 돌아도 같은 범위다.
- 쓰기는 덮어쓰기(upsert)로 한다. 더하기는 두 번 돌면 두 배다.
- 바깥으로 나가는 동작(메일, 결제, 웹훅)에는 회차와 대상으로 만든 키를 붙인다. [멱등성 키 글](/posts/idempotency-key)의 방식이다.
- 긴 작업은 진행 위치를 결과와 같은 트랜잭션에 적어 둔다. activeDeadlineSeconds로 끊겨도 이어서 할 수 있다.
- "다시 해도 안 되는 실패"는 정해진 종료 코드로 끝내고 podFailurePolicy로 바로 멈춘다.

사이드카를 붙인 Job이 끝나지 않는 문제(메인 컨테이너는 끝났는데 프록시가 계속 돈다)는 네이티브 사이드카로 풀린다. [멀티 컨테이너 글](/posts/k8s-pod-multicontainer#job이-끝나지-않는-이유)에 있다.

## Job이 이상할 때 보는 순서

```bash
# 1. 상태 조건: 왜 끝났는지 reason이 말해 준다
kubectl -n batch get job export -o jsonpath='{range .status.conditions[*]}{.type} {.reason}: {.message}{"\n"}{end}'
# 2. Pod별 종료 코드와 시각
kubectl -n batch get pods -l job-name=export --sort-by=.metadata.creationTimestamp \
  -o custom-columns=NAME:.metadata.name,PHASE:.status.phase,EXIT:.status.containerStatuses[0].state.terminated.exitCode
# 3. 마지막으로 실패한 Pod의 로그
kubectl -n batch logs job/export
# 4. CronJob이면 마지막 예약 시각과 성공 시각
kubectl -n batch get cronjob digest -o jsonpath='{.status.lastScheduleTime} {.status.lastSuccessfulTime}{"\n"}'
```

reason으로 갈래가 나뉜다. `BackoffLimitExceeded`면 Pod 로그와 종료 코드를 본다. `DeadlineExceeded`면 작업이 느려졌거나 멈춘 것이니 Pod가 지워지기 전의 로그(로그 수집 시스템)를 본다. `PodFailurePolicy`면 메시지에 걸린 규칙 번호가 있다. `FailedIndexes`면 `status.failedIndexes`의 번호만 다시 돌린다. Job이 Running인데 Pod가 없으면 suspend인지, Pending이면 [Pod 문제 해결 글](/posts/k8s-pod-troubleshooting)의 순서로 간다. 끝난 Pod에 셸을 붙여 볼 수는 없으니, 같은 템플릿으로 명령만 바꾼 Pod를 띄워 들어가는 `kubectl debug --copy-to`를 쓴다([kubectl 필수 명령 글](/posts/kubectl-essentials)).

## 끝나는 작업의 숫자들

Job은 성공한 Pod 수(completions)를 채울 때까지 동시에 parallelism만큼 Pod를 돌린다. 실패는 backoffLimit까지 10초부터 두 배씩 기다리며 다시 하고, 전체 시간은 activeDeadlineSeconds로 자르고, 끝난 뒤에는 ttlSecondsAfterFinished로 치운다. Indexed Job은 번호로 일을 나누고 번호마다 실패를 센다. podFailurePolicy는 다시 해도 안 되는 실패를 바로 멈추고, 쫓겨난 Pod는 세지 않는다. CronJob은 놓친 회차 중 마지막 하나만 돌린다. 이 모든 것 위에서 작업은 두 번 돌아도 결과가 같아야 한다. 계속 떠 있는 Pod를 다루는 [StatefulSet](/posts/k8s-statefulset)과 [DaemonSet](/posts/k8s-daemonset) 글과 함께 보면 Workloads의 컨트롤러가 각자 무엇을 고정하는지 정리된다.

## 면접에서 나올 만한 질문

### Job의 completions와 parallelism은 무엇을 정하나요?

completions는 성공한 Pod가 몇 개 나와야 Job이 끝나는지, parallelism은 동시에 몇 개까지 돌릴지다. 하나가 끝나면 남은 성공 수 안에서 빈자리를 채운다. Pod들이 일을 어떻게 나눌지는 Job이 정하지 않으니, 작업 큐에서 꺼내 가게 하거나 Indexed Job으로 번호를 받아 범위를 나눈다.

### backoffLimit에 걸리기까지 어떤 일이 일어나나요?

실패한 Pod 수가 backoffLimit(기본 6)을 넘으면 Job이 BackoffLimitExceeded로 실패한다. 그 사이 새 Pod는 10초, 20초, 40초처럼 두 배씩 늘어나는 간격(상한 10분)을 두고 만들어진다. restartPolicy가 OnFailure면 컨테이너 재시작 횟수도 함께 센다. 두 번 하면 안 되는 작업은 0으로 두고, 재시도는 멱등할 때만 켠다.

### activeDeadlineSeconds와 ttlSecondsAfterFinished는 어떻게 다른가요?

activeDeadlineSeconds는 Job이 돌 수 있는 최대 시간이고, 넘기면 Pod를 지우고 DeadlineExceeded로 실패시킨다. 재시도가 남아 있어도 시간이 우선이다. ttlSecondsAfterFinished는 끝난 뒤 Job과 Pod를 지우기까지의 시간이라 뒷정리용이다. 앞의 것은 멈춘 작업이 다음 회차를 막지 않게, 뒤의 것은 끝난 객체가 쌓이지 않게 한다.

### Indexed Job은 언제 쓰나요?

Pod마다 0부터 번호를 줘서 일을 겹치지 않게 나눌 때 쓴다. 번호는 JOB_COMPLETION_INDEX 환경 변수와 라벨, hostname으로 들어가고, 번호마다 성공이 하나씩 나와야 끝난다. backoffLimitPerIndex로 번호마다 실패를 따로 세면 하나가 계속 실패해도 나머지는 끝까지 가고, failedIndexes의 번호만 다시 돌리면 된다. 리더만 성공하면 되는 작업은 successPolicy로 성공 조건을 바꾼다.

### podFailurePolicy는 왜 필요한가요?

실패의 종류에 따라 다르게 처리하려고 쓴다. 설정 오류처럼 다시 해도 안 되는 실패는 정해진 종료 코드로 FailJob을 걸어 바로 멈추고, drain이나 선점으로 쫓겨난 Pod는 DisruptionTarget 조건으로 Ignore해서 실패로 세지 않는다. restartPolicy가 Never여야 쓸 수 있고, 규칙은 위에서부터 처음 맞는 하나만 적용된다. 이게 있으면 Pod가 완전히 끝난 뒤에 교체 Pod를 만든다.

### CronJob이 회차를 여러 번 놓치면 돌아왔을 때 어떻게 되나요?

놓친 회차 중 가장 최근 하나만 실행한다. 실습에서 세 회차를 놓친 뒤 풀자 마지막 회차 하나만 만들어졌다. startingDeadlineSeconds 밖의 회차는 아예 실행하지 않고, 이 값 없이 놓친 회차가 100개를 넘으면 시작을 포기한다. 회차마다 꼭 돌아야 하는 작업은 마지막 처리 지점부터 이어서 처리하게 만들거나 빠진 회차를 감시한다.

### 쿠버네티스 Job은 정확히 한 번 실행을 보장하나요?

보장하지 않는다. 공식 문서도 parallelism 1, Never로 둬도 같은 프로그램이 두 번 시작될 수 있다고 적고, CronJob도 회차당 Job을 대략 한 번 만든다고 적는다. 그래서 범위를 회차나 번호로 고정하고, upsert로 쓰고, 바깥 동작에는 멱등성 키를 붙여 여러 번 돌아도 결과가 한 번이 되게 만든다.
