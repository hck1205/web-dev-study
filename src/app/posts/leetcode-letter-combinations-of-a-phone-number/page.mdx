[LeetCode 17. Letter Combinations of a Phone Number](https://leetcode.com/problems/letter-combinations-of-a-phone-number/)가 그 조합을 모두 만드는 문제다. 백트래킹 문제 중 가장 단순한 축에 속한다. 겹치는 답을 걸러야 하는 [Subsets II](/posts/leetcode-subsets-ii)나, 조건으로 가지를 잘라야 하는 [Combination Sum](/posts/leetcode-combination-sum)과 달리 모든 갈래가 답이 된다. 그래서 백트래킹의 뼈대만 남은 모양을 보기 좋고, 같은 결과를 반복문, 재귀, 주행 거리계 방식으로 만들며 각각의 비용을 비교하기도 좋다. 재귀와 백트래킹의 일반적인 틀은 [재귀와 백트래킹 글](/posts/recursion-backtracking)에 있다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 숫자 버튼마다 글자 하나씩 고르기

2부터 9까지의 숫자로 된 문자열 `digits`가 주어진다. 휴대폰 키패드처럼 숫자마다 글자가 정해져 있다.

```text
2: abc    3: def    4: ghi    5: jkl
6: mno    7: pqrs   8: tuv    9: wxyz
```

숫자마다 글자 하나씩 골라 순서대로 이어 붙인 문자열을 모두 돌려준다. 답의 순서는 상관없다. `digits`가 빈 문자열이면 빈 목록을 돌려준다.

제약은 이렇다.

- `digits`의 길이는 0 이상 4 이하다.
- 숫자는 2~9만 나온다. 0과 1에는 글자가 없다.

길이가 4 이하라 답은 많아야 4^4 = 256개다. 7과 9만 글자가 넷이고 나머지는 셋이다. 시간 걱정은 없는 문제라, 면접에서는 코드를 깔끔하게 짜는지와 빈 입력 같은 경계를 처리하는지를 본다. 그리고 "자릿수가 늘면 어떻게 되나"를 꼬리 질문으로 묻는다.

## "37"을 손으로 적으면

3은 d, e, f, 7은 p, q, r, s다. 첫 글자를 하나 정하고 둘째 글자를 차례로 바꾸며 적는다.

```text
d: dp dq dr ds
e: ep eq er es
f: fp fq fr fs
```

3 × 4 = 12개다. 자릿수마다 고르는 글자 수를 곱하면 답의 개수가 된다. 일반적으로 숫자 n개에서 글자 수가 k₁, k₂, …, kₙ이면 답은 k₁ × k₂ × … × kₙ개다. 모두 4글자인 최악이면 4^n이다.

적는 순서에 규칙이 있었다. 앞자리를 고정한 채 뒷자리를 다 돌고, 뒷자리가 끝나면 앞자리를 하나 올렸다. 숫자를 셀 때 끝자리부터 올리는 것과 같다. 이 규칙을 코드로 옮기는 방법이 여러 가지다.

## 자릿수만큼 for문을 겹치면

자릿수가 두 개라고 정해져 있다면 for문 두 개로 끝난다.

```js
const KEYS = { 2: "abc", 3: "def", 4: "ghi", 5: "jkl", 6: "mno", 7: "pqrs", 8: "tuv", 9: "wxyz" };

function twoDigits(digits) {                // 길이가 정확히 2일 때만 맞다
  const res = [];
  for (const a of KEYS[digits[0]]) {
    for (const b of KEYS[digits[1]]) {
      res.push(a + b);
    }
  }
  return res;
}
```

손으로 적은 순서와 정확히 같다. 문제는 자릿수가 입력마다 다르다는 것이다. 길이 0부터 4까지 for문 깊이가 다른 함수 다섯 개를 따로 짤 수는 없다. "for문을 몇 겹으로 쌓을지가 입력에 달려 있다"는 게 이 문제의 출발점이다. 겹을 반복문으로 하나씩 쌓아 가거나, 재귀 호출로 겹을 대신한다.

## 앞에서부터 한 자리씩 늘려 가기

for문을 겹으로 쌓는 대신, 지금까지 만든 접두사(앞부분) 목록을 들고 다니며 숫자 하나를 볼 때마다 모든 접두사 뒤에 그 숫자의 글자를 하나씩 붙인다. 빈 문자열 하나에서 시작하면 첫 숫자를 본 뒤 목록은 첫 글자들이 되고, 둘째 숫자를 본 뒤 두 글자짜리가 된다.

```js
function letterCombinations(digits) {
  if (digits.length === 0) return [];      // 이 줄이 없으면 [""]가 나온다
  let res = [""];                          // 길이 0인 접두사 하나
  for (const d of digits) {
    const next = [];
    for (const prefix of res) {
      for (const ch of KEYS[d]) {
        next.push(prefix + ch);            // 접두사마다 이번 숫자의 글자를 붙인다
      }
    }
    res = next;                            // 한 자리 늘어난 목록으로 바꾼다
  }
  return res;
}
```

재귀가 없어서 읽기 쉽다. JavaScript는 `reduce`와 `flatMap`으로 한 줄로도 쓴다.

```js

  !d ? [] : [...d].reduce((acc, x) => acc.flatMap((p) => [...KEYS[x]].map((c) => p + c)), [""]);
```

결과는 같다. 다만 이 방식은 층마다 목록 전체를 새로 만든다. 마지막 층의 목록이 곧 답이니 메모리는 답의 크기만큼 들고, 그 직전 층의 목록도 잠깐 같이 살아 있다. 숫자가 많아져 답이 수백만 개가 되면 중간 목록까지 메모리에 올라간다. 그리고 "dp로 시작하는 것만" 같은 조건을 붙이고 싶을 때, 조건에 안 맞는 접두사도 층마다 다 만든 뒤에야 거를 수 있다. 하나씩 끝까지 만들어 보는 탐색이 필요해진다.

## 한 자리씩 골라 끝까지 내려가기

재귀 함수 `go(i)`가 "i번째 숫자의 글자를 고르는 겹"을 맡는다. 글자를 하나 골라 `path`에 넣고 `go(i + 1)`로 다음 숫자를 맡긴 뒤, 돌아오면 빼고 다음 글자를 넣는다. i가 끝에 닿으면 `path`가 답 하나다. for문을 몇 겹 쌓을지를 재귀 깊이가 대신 정한다.

```js
function letterCombinations(digits) {
  if (digits.length === 0) return [];
  const res = [];
  const path = [];

  function go(i) {
    if (i === digits.length) {          // 숫자마다 글자를 다 골랐다
      res.push(path.join(""));
      return;
    }
    for (const ch of KEYS[digits[i]]) { // i번째 숫자의 글자 중 하나를
      path.push(ch);                    // 고르고
      go(i + 1);                        // 다음 숫자로 내려가고
      path.pop();                       // 되돌린다
    }
  }

  go(0);
  return res;
}
```

"34"(d, e, f와 g, h, i)에서 `path`가 바뀌는 모습이다. 칸은 두 버튼의 글자를 이어 놓은 것이고, 초록 칸이 지금 고른 글자다.

호출 수는 트리의 마디 수와 같다. 뿌리 1개, 첫 층 3개, 둘째 층 9개라 "34"는 13번이다. 직접 세어 보니 "37"은 1 + 3 + 12 = 16번, "7979"는 1 + 4 + 16 + 64 + 256 = 341번이었다. 잎(답)이 256개이고 안쪽 마디가 85개다. 층마다 갈래가 3~4개씩이라 안쪽 마디는 잎의 3분의 1 정도밖에 안 된다. 그래서 호출 비용보다 답을 만드는 비용이 시간을 정한다. 갈래가 둘뿐인 [Subsets](/posts/leetcode-subsets)의 넣는다/안 넣는다 트리는 안쪽 마디가 잎과 거의 같은 수였던 것과 비교된다.

이 트리에는 점선이 없다. 모든 갈래가 답으로 이어지기 때문이다. [Combination Sum](/posts/leetcode-combination-sum)이나 [N-Queens](/posts/leetcode-n-queens)에서는 같은 틀에 "이 갈래는 가망이 없다"는 검사가 들어가 점선 갈래가 생긴다. 백트래킹 문제를 만나면 먼저 이 트리를 그리고, 층이 무엇이고(자리, 원소, 행), 갈래가 무엇이며(글자, 넣기/안 넣기, 열), 어디서 잘라도 되는지를 정하면 코드가 거의 자동으로 나온다.

### 문자열을 넘기면 되돌리기가 필요 없다

이 문제에서는 되돌리기를 문자열로 대신할 수도 있다. JavaScript 문자열은 바꿀 수 없는 값이라 `cur + ch`가 새 문자열을 만들고, 호출이 돌아오면 원래의 `cur`가 그대로 남아 있다. pop이 필요 없다.

```js
function letterCombinations(digits) {
  if (!digits) return [];
  const res = [];
  function go(i, cur) {
    if (i === digits.length) {
      res.push(cur);                   // cur는 이미 새 문자열이라 복사할 필요가 없다
      return;
    }
    for (const ch of KEYS[digits[i]]) go(i + 1, cur + ch);
  }
  go(0, "");
  return res;
}
```

측정해 보면 이쪽이 더 빨랐다. 끝에서 `path.join("")`으로 매번 문자열을 새로 만드는 대신, 내려가면서 한 글자씩 붙인 문자열을 그대로 쓰기 때문이다. 길이 n의 문자열을 층마다 만드니 복사량은 비슷한데, 배열 push/pop과 join 호출이 빠진 만큼 가볍다.

복잡도는 어느 쪽이든 같다. 답이 최대 4^n개이고 하나마다 길이 n이라 시간은 O(n · 4^n)이다. 출력 자체가 그만큼이라 더 빨라질 수 없다. 추가 공간은 재귀 깊이와 `path`로 O(n)이다. 앞의 반복문 풀이와 달리 중간 층의 목록을 들고 있지 않아서, 답을 저장하지 않고 하나씩 처리(출력, 검사)만 한다면 메모리가 O(n)으로 끝난다. 면접에서 기대하는 답이 이 풀이다.

### Python과 Java로는

Python은 `path` 리스트와 `"".join`으로 쓴다. 재귀 깊이는 많아야 n + 1 = 5다.

```python
from typing import List

KEYS = {"2": "abc", "3": "def", "4": "ghi", "5": "jkl",
        "6": "mno", "7": "pqrs", "8": "tuv", "9": "wxyz"}

def letter_combinations(digits: str) -> List[str]:
    if not digits:
        return []                    # 빈 입력은 빈 목록 ([""]가 아니다)
    res, path = [], []

    def go(i: int) -> None:
        if i == len(digits):
            res.append("".join(path))
            return
        for ch in KEYS[digits[i]]:
            path.append(ch)
            go(i + 1)
            path.pop()

    go(0)
    return res
```

라이브러리로는 `itertools.product`가 정확히 이 일을 한다. 여러 문자열의 데카르트 곱(가능한 모든 짝)을 만들어 준다.

```python
from itertools import product

def letter_combinations_lib(digits: str) -> List[str]:
    if not digits:
        return []
    return ["".join(p) for p in product(*(KEYS[d] for d in digits))]
```

`product()`에 아무것도 안 넘기면 빈 튜플 하나를 내놓는다. 그래서 여기서도 빈 입력 검사가 없으면 `[""]`가 나온다.

Java는 숫자를 배열 인덱스로 바꿔 글자를 찾는다. `digits.charAt(i) - '0'`이 숫자 값이다. 답의 길이가 정해져 있으니 `char[]`를 하나 두고 i번 칸을 덮어쓰면, 다음 글자가 그 칸을 덮어쓰니까 되돌리기가 필요 없다. `StringBuilder`로 쓴다면 돌아올 때 `sb.deleteCharAt(sb.length() - 1)`을 해야 한다.

```java
import java.util.*;

class Solution {
    private static final String[] KEYS = {"", "", "abc", "def", "ghi", "jkl", "mno", "pqrs", "tuv", "wxyz"};

    public List<String> letterCombinations(String digits) {
        List<String> res = new ArrayList<>();
        if (digits.isEmpty()) return res;          // 빈 입력은 빈 목록
        go(digits, 0, new char[digits.length()], res);
        return res;
    }

    // 길이가 정해져 있으니 char[]의 i번 칸을 덮어쓰면 되돌릴 필요가 없다
    private void go(String digits, int i, char[] path, List<String> res) {
        if (i == digits.length()) {
            res.add(new String(path));             // 그 순간의 내용을 새 문자열로
            return;
        }
        String letters = KEYS[digits.charAt(i) - '0'];
        for (int k = 0; k < letters.length(); k++) {
            path[i] = letters.charAt(k);
            go(digits, i + 1, path, res);
        }
    }
}
```

`new String(path)`가 복사다. `res.add(path.toString())`으로 쓰면 배열 내용이 아니라 `[C@1b6d3586` 같은 객체 이름이 들어간다. 세 언어 모두 "37"에서 같은 12개를, 빈 문자열에서 빈 목록을, "7979"에서 256개를 냈다.

## 나머지 자리의 답에 앞 글자를 붙인다

재귀를 다르게 쪼갤 수도 있다. "`digits[i..]`로 만들 수 있는 문자열 목록"을 돌려주는 함수를 생각하자. i번째 숫자의 글자마다, 나머지 `digits[i+1..]`의 목록 각각의 앞에 그 글자를 붙이면 된다. 나머지가 비었으면 빈 문자열 하나가 답이다.

```js
function letterCombinations(digits) {
  if (!digits) return [];
  function all(i) {
    if (i === digits.length) return [""];  // 남은 숫자가 없으면 빈 문자열 하나
    const rest = all(i + 1);               // 뒷부분의 답을 먼저 받아 온다
    const out = [];
    for (const ch of KEYS[digits[i]]) {
      for (const r of rest) out.push(ch + r);
    }
    return out;
  }
  return all(0);
}
```

`path`도 되돌리기도 없다. 수학의 정의("앞 글자 × 뒷부분의 모든 조합")를 그대로 옮겨서 정확성을 설명하기 쉽다. 뒷부분의 목록을 한 번만 만들고 앞 글자 수만큼 재사용한다는 점에서는 오히려 일을 덜 한다. 실제로 열 자리에서 가장 빨랐다.

대신 메모리가 앞의 반복문 풀이와 같은 모양이다. 마지막에 답 전체와 그 직전 층의 목록이 함께 메모리에 있다. 답을 하나씩 처리하고 버리는 쓰임에는 맞지 않는다.

## 자동차 주행 거리계처럼 끝자리부터 올린다

손으로 적을 때의 규칙, "끝자리를 돌리다 다 돌면 앞자리를 올린다"를 그대로 옮긴 풀이다. 자리마다 지금 고른 글자의 번호 `idx[i]`를 들고 있다가, 답 하나를 만들 때마다 끝자리 번호를 1 올린다. 글자 수를 넘으면 0으로 되돌리고 앞자리를 올린다. 맨 앞자리까지 넘치면 끝이다. 자리마다 진법이 다른 수(혼합 기수, mixed radix)를 1씩 세는 것과 같다.

```js
function letterCombinations(digits) {
  if (!digits) return [];
  const n = digits.length;
  const letters = [...digits].map((d) => KEYS[d]);
  const idx = new Array(n).fill(0);        // 자리마다 고른 글자의 번호
  const res = [];
  while (true) {
    let word = "";
    for (let i = 0; i < n; i++) word += letters[i][idx[i]];
    res.push(word);

    let k = n - 1;                          // 끝자리부터 올린다
    while (k >= 0) {
      idx[k]++;
      if (idx[k] < letters[k].length) break; // 넘치지 않았으면 끝
      idx[k] = 0;                           // 넘치면 0으로 되돌리고 앞자리로
      k--;
    }
    if (k < 0) break;                       // 맨 앞자리까지 넘쳤다
  }
  return res;
}
```

"37"이면 `idx`가 `[0,0] [0,1] [0,2] [0,3] [1,0] …` 순으로 바뀌며 `dp dq dr ds ep …`이 나온다. `[0,3]`에서 끝자리를 올리면 4가 되어 넘치니 0으로 돌리고 앞자리를 1로 올려 `[1,0]`이 된다.

재귀가 없고 상태가 정수 배열 하나뿐이라, 탐색을 멈췄다가 `idx`만 저장해 두고 나중에 이어 갈 수 있다. 더 좋은 점은 k번째 답을 바로 구할 수 있다는 것이다. k를 끝자리부터 각 자리의 글자 수로 나눈 나머지가 그 자리의 번호다. "37"에서 5번째(0부터 셈)는 5를 4로 나눈 나머지 1이 끝자리(q), 몫 1이 앞자리(e)라 "eq"다. 백트래킹 결과의 5번째와 같다. 답 전체를 만들지 않고 O(n)에 답한다.

## 빈 문자열 하나가 답으로 나올 때

### 빈 입력에서 `[""]`

이 문제에서 가장 많이 틀리는 곳이다. 한 자리씩 늘리는 풀이에서 빈 입력 검사를 빼면 for문이 한 번도 돌지 않아 시작값 `[""]`가 그대로 나온다. 백트래킹도 `go(0)`이 들어가자마자 `i === digits.length`(0 === 0)라 빈 문자열 하나를 기록한다. 수학적으로는 "아무것도 고르지 않는 방법 하나"라 틀린 말이 아니지만, 이 문제는 빈 목록을 요구한다. [Subsets](/posts/leetcode-subsets)는 빈 입력에 `[[]]`(빈 집합 하나)가 정답이라, 두 문제를 연달아 풀면 이 차이에서 헷갈린다. 경계 조건은 문제마다 다시 읽는다.

### 글자표를 배열로 만들고 인덱스를 어긋나게 쓰기

`["abc", "def", …]`처럼 2번부터 시작하는 배열을 만들고 `KEYS[digit]`로 찾으면 두 칸씩 밀린다. "2"에서 "ghi"가 나온다. 앞에 빈 칸 두 개를 넣어 인덱스를 숫자와 맞추거나(`["", "", "abc", …]`), `KEYS[digit - 2]`로 쓴다. Java 코드가 앞에 빈 문자열 두 개를 둔 이유다.

### 문자열 숫자를 그대로 계산하기

JavaScript에서 `digits[i]`는 `"3"` 같은 문자열이다. 객체 `KEYS["3"]`은 키가 문자열로 바뀌어서 잘 찾지만, 배열에서 `KEYS[digits[i] - 2]`는 `"3" - 2`가 1이라 맞고 `KEYS[digits[i] + 1]`은 `"31"`이 돼서 `undefined`다. 빼기는 숫자로 바꿔 주고 더하기는 문자열을 이어 붙인다. `Number(digits[i])`로 바꿔 쓰면 헷갈릴 일이 없다.

### 0이나 1이 들어오면

문제는 2~9만 준다고 했지만, 실무 입력이라면 0과 1이 섞일 수 있다. 그때 `KEYS["1"]`이 `undefined`라 `for…of`가 `TypeError: ... is not iterable`로 죽는다(Node 22에서는 `KEYS.1 is not iterable`라고 나왔다). 그 숫자를 건너뛸지, 빈 결과를 돌려줄지, 숫자 그대로 넣을지 먼저 정하고 코드로 드러낸다.

## 버튼 규칙이 바뀌면

### 답의 개수만 달라면

목록을 만들지 않고 숫자마다 글자 수를 곱한다. "7979"는 4 × 4 × 4 × 4 = 256이다. 빈 입력이면 0으로 정해야 한다(곱의 항등원 1이 아니라).

### k번째 조합 하나만 달라면

주행 거리계 풀이에서 본 대로 k를 끝자리부터 글자 수로 나눈 나머지가 그 자리의 글자 번호다. "2345"에서 50번째(0부터 셈)는 "bfhl"로 백트래킹 결과의 50번째와 같았다. O(n)이다.

### 자릿수가 20이라면

4^20은 1조가 넘는다. 답을 다 만드는 건 불가능하고, 질문을 바꿔야 한다. 개수만 필요하면 곱셈, 특정 위치만 필요하면 k번째 계산, 조건에 맞는 것만 필요하면 그 조건으로 가지를 친다. 사전에 있는 단어만 원하면 [트라이](/posts/ds-trie)를 따라 내려가다가 트라이에 없는 접두사에서 멈춘다. "그 접두사로 시작하는 단어가 없으면 그 아래를 다 버린다"는 가지치기다. 아래 T9 이야기가 그 경우다.

### 결과를 사전순으로 달라면

이미 사전순이다. 버튼마다 글자가 알파벳 순으로 적혀 있고, 백트래킹은 앞자리를 고정한 채 뒷자리를 앞 글자부터 돌기 때문이다. 한 자리씩 늘리는 반복문, 주행 거리계도 같은 순서를 낸다. 순서가 깨지는 건 글자표가 정렬돼 있지 않을 때다. 예를 들어 표를 `7: "sqrp"`처럼 바꾸면 결과도 그 순서를 따른다. 정렬된 결과가 요구 사항이라면 표가 정렬돼 있다는 가정에 기대지 말고, 표를 만들 때 정렬해 두거나 마지막에 `sort()`를 한 번 부른다. 정렬 비용 O(n · m log m)(m은 답의 개수)이 붙는다.

### 버튼 하나에 숫자 자체도 포함한다면

글자표를 `2: "abc2"`처럼 바꾸기만 하면 코드가 그대로 돈다. 표와 탐색을 분리해 둔 덕분이다. 어떤 글자를 고를 수 있는지는 표가, 어떻게 빠짐없이 고르는지는 탐색이 맡는다.

### 비슷한 문제

[Subsets](/posts/leetcode-subsets)는 칸마다 "넣는다, 안 넣는다" 두 후보, 이 문제는 칸마다 서너 글자 후보인 결정 트리다. [Generate Parentheses](/posts/leetcode-generate-parentheses)는 칸마다 "(" 또는 ")" 두 후보에 개수 조건으로 가지를 친다. [Permutations](/posts/leetcode-permutations)는 이미 쓴 원소를 후보에서 빼는 결정 트리다. LeetCode 784 Letter Case Permutation은 글자마다 대문자, 소문자 두 후보를 고르는 같은 틀이다.

## 피처폰 T9 단어 추천은 거꾸로 푼다

처음의 T9으로 돌아가자. 4663을 누르면 "home", "good"을 띄워 주려고 할 때, 이 문제의 코드로 81개 조합을 다 만들고 사전에 있는지 확인할 수 있다.

```js
const words = ["good", "home", "gone", "hood", "hoof", "inn", "golf", "ink"];
letterCombinations("4663").filter((c) => words.includes(c));
// 81개를 만들어 [ 'gone', 'good', 'home', 'hood', 'hoof' ]
```

자릿수가 늘면 이 방법은 무너진다. 8자리면 조합이 수만 개인데 그중 사전에 있는 단어는 몇 개 안 된다. 실제로는 반대 방향으로 미리 계산해 둔다. 사전의 단어마다 그 단어를 치려면 누를 숫자열을 구해 그 숫자열을 키로 묶는다.

```js
const toDigit = {};
for (const [d, s] of Object.entries(KEYS)) for (const c of s) toDigit[c] = d;

const byDigits = new Map(); // 숫자열 → 단어들
for (const w of words) {
  const key = [...w].map((c) => toDigit[c]).join("");
  if (!byDigits.has(key)) byDigits.set(key, []);
  byDigits.get(key).push(w);
}
byDigits.get("4663"); // [ 'good', 'home', 'gone', 'hood', 'hoof' ]
byDigits.get("465");  // [ 'ink' ]
```

사전을 한 번 훑어 두면 추천은 해시맵 조회 한 번이다. 조합을 만드는 비용이 입력 자릿수에 지수적인 반면, 이 방법은 사전 크기에 비례하는 준비 한 번이면 끝난다. "모든 조합을 만들어 걸러라"라는 문제를 받았을 때, 걸러 낼 기준이 작은 집합(사전)이라면 그 집합 쪽에서 거꾸로 가는 게 더 싼지 먼저 따져 본다. 입력 중간까지만 눌렀을 때 후보를 띄우려면 숫자열 대신 숫자 트라이에 단어를 넣어 두면 된다.

## 칸마다 후보를 하나씩, 끝에 닿으면 기록

이 문제는 칸마다 고를 수 있는 후보가 정해진 결정 트리를 끝까지 다 펼치는 문제다. 자릿수가 입력마다 달라서 for문의 겹 수를 정할 수 없으니, 층마다 목록을 불리거나 재귀 깊이로 겹을 대신한다. 모든 갈래가 답이라 가지치기도 중복 처리도 없고, 시간은 출력 크기 O(n · 4^n) 그대로다. 남는 판단은 메모리와 경계다. 답을 하나씩 처리할 거면 O(n) 공간의 백트래킹을, k번째 하나만 필요하면 혼합 기수 계산을 쓰고, 빈 입력에 빈 목록을 돌려주는 것만 잊지 않으면 된다.

## 면접에서 나올 만한 질문

### 시간 복잡도는 어떻게 되나요?

글자가 넷인 버튼만 누르면 답이 4^n개이고 하나마다 길이가 n이라 O(n · 4^n)이다. 버튼마다 글자 수가 다르면 그 곱에 n을 곱한 만큼이다. 출력 크기 자체가 이만큼이라 어떤 풀이도 더 빨라질 수 없다.

### 공간 복잡도는요?

출력을 빼면 백트래킹은 재귀 깊이와 `path`로 O(n)이다. 한 자리씩 늘리는 반복문은 직전 층의 목록을 들고 있어서 답의 크기에 가까운 메모리를 더 쓴다. 답을 저장하지 않고 하나씩 처리할 수 있다면 백트래킹이 유리하다.

### 빈 입력은 왜 따로 처리하나요?

아무 숫자도 안 누르면 "아무것도 고르지 않은 방법 하나"인 빈 문자열이 나오는 게 코드의 자연스러운 결과다. 하지만 이 문제는 빈 목록을 요구한다. 검사를 빼면 `[""]`가 나와서 틀린다. Subsets처럼 빈 입력에 빈 집합 하나가 정답인 문제도 있어서 문제마다 확인해야 한다.

### 백트래킹에서 되돌리기를 안 해도 되는 경우는요?

다음 상태를 새 값으로 넘기면 된다. JavaScript나 Python 문자열은 바꿀 수 없는 값이라 `cur + ch`를 넘기면 호출이 끝난 뒤 원래 `cur`가 그대로다. Java에서 길이가 정해진 `char[]`의 i번 칸을 덮어쓰는 방식도 다음 글자가 같은 칸을 덮어쓰니 되돌릴 필요가 없다.

### 재귀 없이 풀 수 있나요?

두 가지가 있다. 빈 문자열에서 시작해 숫자마다 모든 접두사 뒤에 글자를 붙이는 반복문이 있고, 자리마다 글자 번호를 들고 끝자리부터 1씩 올리는 주행 거리계 방식이 있다. 뒤의 것은 상태가 정수 배열 하나라 멈췄다 이어 가기 좋고, k번째 조합을 O(n)에 바로 구할 수 있다.

### 자릿수가 아주 크면 어떻게 하나요?

4^n은 n = 20만 돼도 1조가 넘어 다 만들 수 없다. 개수가 필요하면 글자 수를 곱하고, 특정 순번이 필요하면 혼합 기수로 계산한다. 사전 단어만 원하면 트라이로 없는 접두사를 잘라 내거나, 사전 단어를 숫자열로 바꿔 미리 묶어 두고 조회한다.

### 다른 백트래킹 문제와 무엇이 다른가요?

모든 갈래가 답이라 가지치기와 중복 처리가 없다. Combination Sum은 합이 넘치는 갈래를, N-Queens는 공격받는 칸을 잘라 내고, Subsets II는 같은 자리의 같은 값을 건너뛴다. 이 문제는 그런 조건 없이 결정 트리를 끝까지 펼치는 뼈대만 남은 모양이라, 층(숫자)과 갈래(글자)를 정하는 연습으로 좋다.
