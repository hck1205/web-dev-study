새 프로젝트의 첫 주, 상태 관리를 무엇으로 할지 정하는 회의가 열린다. Redux, Zustand, Jotai, Recoil, MobX, 시그널이 차례로 나온다. 누군가 "Redux는 코드가 너무 많다"고 하고, 누군가 "Zustand는 규칙이 없어서 커지면 엉망이 된다"고 한다. 결론 없이 끝난다.

이 회의가 어긋나는 이유는 라이브러리를 같은 저울에 올려 보지 않아서다. 이 글은 먼저 저장소가 필요 없는 상태를 덜어 내고, 남은 것을 넣을 저장소들이 내부적으로 같은 세 함수로 시작한다는 걸 본다. 그다음 라이브러리마다 무엇을 다르게 고르는지, React가 바깥 저장소를 어떻게 구독하는지, 화면이 찢어지는 tearing과 셀렉터 무한 루프가 어디서 오는지 따라간다. 마지막에 작은 저장소를 직접 만들어 본다.

## 저장소에 넣기 전에 덜어 낼 것

"상태 관리 라이브러리"라고 부르지만, 요즘 앱에서 그 안에 넣을 값은 생각보다 적다. 서버에서 받은 데이터는 원본이 서버에 있고 언제든 낡을 수 있는 사본이다. 이건 캐싱, 재요청, 중복 제거를 해 주는 TanStack Query나 SWR 같은 서버 상태 도구가 맡는다([화면 데이터 캐시](/posts/client-data-cache)). 필터와 정렬은 주소에, 입력 중인 값은 폼에, 드롭다운 열림은 그 컴포넌트의 state에 둔다. 상태를 종류별로 나누고 자리를 고르는 순서는 [프런트엔드 상태 구조](/posts/frontend-state-architecture)에서 정리했다.

이렇게 덜어 내면 전역 저장소에 남는 건 로그인 사용자, 테마, 장바구니처럼 서버와 별개로 이 기기에서 정해지고 여러 화면이 함께 보는 값, 그리고 편집기나 대시보드처럼 클라이언트에서 복잡하게 바뀌는 도메인 상태 정도다. 라이브러리 선택은 이 남은 부분의 크기와 모양을 보고 한다. 서버 데이터를 Redux에 복사해 두던 시절의 "Redux는 코드가 너무 많다"는 불만은 상당 부분 서버 상태를 같이 들고 있어서 생긴 것이었다.

## 모든 저장소는 세 함수로 시작한다

라이브러리 이름을 지우고 보면 바깥 저장소의 뼈대는 같다. 값을 꺼내는 `getState`, 값을 바꾸고 구독자에게 알리는 `setState`(Redux에서는 `dispatch`), 바뀌면 불러 달라고 등록하는 `subscribe`다.

```ts
function createStore<T>(initial: T) {
  let state = initial;
  const listeners = new Set<() => void>();
  return {
    getState: () => state,
    setState: (patch: Partial<T>) => {
      state = { ...state, ...patch }; // 바꿀 때마다 새 객체
      listeners.forEach((l) => l());
    },
    subscribe: (listener: () => void) => {
      listeners.add(listener);
      return () => listeners.delete(listener); // 구독 해제 함수를 돌려준다
    },
  };
}
```

React 바깥에 있는 이 객체를 컴포넌트에 연결하는 다리가 React 18에서 생긴 `useSyncExternalStore`다.

```tsx
const store = createStore({ count: 0, theme: "light" });

function useStore<S>(selector: (s: ReturnType<typeof store.getState>) => S) {
  return useSyncExternalStore(store.subscribe, () => selector(store.getState()));
}

function CartBadge() {
  const count = useStore((s) => s.count); // count가 바뀔 때만 다시 렌더링된다
  return <span>{count}</span>;
}
```

React는 `subscribe`에 자기 콜백을 등록해 두고, 저장소가 알리면 두 번째 인자인 `getSnapshot`을 불러 지난번 값과 `Object.is`로 비교한다. 다를 때만 그 컴포넌트를 다시 렌더링한다. 셀렉터로 고른 값이 `count`라면 `theme`이 바뀌어도 숫자가 같으니 건너뛴다. Context가 값 객체 전체를 구독하는 것과 다른 점이 여기다. 알림을 보내고 받는 구조 자체는 [옵서버 패턴](/posts/pattern-observer)이다.

`subscribe`는 컴포넌트 밖에 두거나 고정된 함수여야 한다. 렌더링할 때마다 새 함수를 넘기면 React가 매번 구독을 끊고 다시 건다. 서버 렌더링이 있으면 세 번째 인자 `getServerSnapshot`으로 서버와 하이드레이션 때 쓸 값을 준다.

라이브러리들은 이 뼈대 위에서 세 가지를 다르게 고른다. 상태를 바꾸는 길을 하나로 강제하나, 구독 단위가 저장소 하나인가 잘게 쪼갠 조각인가, 바꿀 때 새 객체를 만드나 제자리에서 고치나.

## Redux: 바뀌는 길을 하나로 만든다

이 구조의 값은 추적에 있다. 모든 변경이 이름 있는 액션으로 남으니 "이 숫자가 왜 바뀌었나"를 개발 도구에서 시간 순서로 되짚을 수 있다. 미들웨어 자리에 로그, 분석 이벤트, 되돌리기 기록, 서버 동기화를 끼울 수 있다. 사람이 많은 팀에서 상태 변경 규칙을 코드 리뷰로 지키기 쉽다.

비용은 코드 양이었다. 예전 Redux는 액션 타입 상수, 액션 생성 함수, switch 리듀서, 불변 업데이트를 손으로 써야 했다. 지금 공식 권장 방식인 Redux Toolkit(RTK)은 이걸 줄였다.

```ts
const cartSlice = createSlice({
  name: "cart",
  initialState: { items: [] as CartItem[] },
  reducers: {
    added(state, action: PayloadAction<CartItem>) {
      state.items.push(action.payload); // Immer가 이 "고치기"를 새 객체 만들기로 바꾼다
    },
  },
});

export const { added } = cartSlice.actions;
export const store = configureStore({ reducer: { cart: cartSlice.reducer } });
```

`createSlice`가 액션 생성 함수와 타입을 만들고, 안에서 Immer를 써서 `push`처럼 고치는 코드를 불변 업데이트로 바꿔 준다. `configureStore`는 thunk 미들웨어를 기본으로 넣고, 개발 모드에서는 상태를 제자리에서 고친 실수와 직렬화할 수 없는 값(함수, Promise, 클래스 인스턴스)을 넣은 실수를 잡는 검사 미들웨어도 넣는다. 서버 데이터는 같은 패키지의 RTK Query가 맡는다. 불변 업데이트 자체가 왜 필요한지는 [React 상태를 불변으로 바꾸기](/posts/js-immutability-react)에 있다.

## useSelector는 액션마다 모든 셀렉터를 돈다

Redux에서 성능 문제는 대개 리듀서가 아니라 셀렉터에서 난다. 액션이 하나 dispatch될 때마다 화면에 있는 모든 `useSelector`의 셀렉터가 실행되고, 결과를 이전 결과와 `===`로 비교한다.

```tsx
// 액션마다 새 객체를 만든다 → 아무 액션에나 다시 렌더링된다
const { name, theme } = useSelector((s: RootState) => ({ name: s.user.name, theme: s.ui.theme }));

// 고치는 방법 1: 원시값을 따로 고른다
const name = useSelector((s: RootState) => s.user.name);
const theme = useSelector((s: RootState) => s.ui.theme);

// 고치는 방법 2: 얕은 비교를 쓴다
const picked = useSelector((s: RootState) => ({ name: s.user.name, theme: s.ui.theme }), shallowEqual);
```

첫 줄은 장바구니에 무엇을 담든, 아무 상관없는 액션이 와도 객체 리터럴이 새로 만들어지니 매번 "바뀌었다"가 된다. 에러는 나지 않고 렌더링만 조용히 는다. react-redux 8.1부터는 개발 모드에서 같은 입력에 다른 참조를 돌려주는 셀렉터를 콘솔 경고로 알려 준다. "Selector unknown returned a different result when called with the same parameters"로 시작하는 경고가 보이면 이 경우다.

`filter`나 `map`으로 목록을 만드는 셀렉터는 얕은 비교로도 못 막는다. 이럴 때는 입력이 같으면 지난 결과를 돌려주는 메모 셀렉터(`createSelector`)를 쓴다. 직접 만들어 보는 과정과 불변성에 기대는 이유는 [React 안의 함수형](/posts/fp-in-react)에서 다뤘다. 셀렉터 비용 자체도 따져 볼 만하다. 컴포넌트 500개가 각자 셀렉터를 들고 있으면 액션 하나에 셀렉터 500개가 돈다. 대부분 값싸서 문제가 안 되지만, 셀렉터 안에서 큰 목록을 정렬하면 액션마다 그 비용을 낸다.

## Zustand: 훅 하나로 끝나는 바깥 저장소

Zustand는 앞의 세 함수 뼈대에 훅 하나를 붙인 모양에 가깝다. 액션 객체, 리듀서, Provider가 없다.

```ts
import { create } from "zustand";
import { useShallow } from "zustand/react/shallow";

type CartStore = { items: CartItem[]; coupon: string | null; add: (item: CartItem) => void };

export const useCart = create<CartStore>()((set) => ({
  items: [],
  coupon: null,
  add: (item) => set((s) => ({ items: [...s.items, item] })), // 최상위는 얕게 합쳐진다
}));

const count = useCart((s) => s.items.length);                       // 숫자 하나만 구독
const { coupon, add } = useCart(useShallow((s) => ({ coupon: s.coupon, add: s.add })));
useCart.getState().add(item);                                        // React 밖에서도 부른다
```

`create`가 돌려주는 훅에 셀렉터를 넘기면 그 조각만 구독한다. 저장소가 모듈 변수라서 React 밖, 예를 들어 axios 인터셉터나 웹소켓 핸들러에서 `getState()`와 `setState()`로 바로 쓸 수 있다. 미들웨어로 `persist`(localStorage 저장), `devtools`(Redux 개발 도구 연결), `immer`를 붙인다.

Zustand 5로 올리면서 많이 만나는 증상이 있다. 4에서 잘 돌던 화면이 "Maximum update depth exceeded"로 멈춘다. 셀렉터가 매번 새 객체를 돌려주는 코드다.

```tsx
const { coupon, add } = useCart((s) => ({ coupon: s.coupon, add: s.add })); // 5에서 무한 루프
```

5는 React의 `useSyncExternalStore`를 그대로 쓴다. React는 렌더링 중에 스냅숏을 다시 읽어 비교하는데, 부를 때마다 새 객체가 나오니 저장소가 계속 바뀐 줄 안다. react-redux의 `useSelector`는 같은 저장소 상태라면 셀렉터 결과를 기억하는 래퍼를 거쳐서 무한 루프 대신 불필요한 렌더링으로 끝나지만, Zustand 5의 기본 훅은 그 래퍼가 없다. 고치는 방법은 `useShallow`로 감싸 얕은 비교를 하거나, 원시값을 하나씩 고르는 것이다. 4에서 쓰던 비교 함수 두 번째 인자는 5의 `create`에서 빠졌고, 꼭 필요하면 `zustand/traditional`의 `createWithEqualityFn`을 쓴다.

Zustand의 약점은 강점의 뒷면이다. 규칙이 없다. 저장소 하나에 아무 함수나 넣을 수 있고, 어느 컴포넌트에서든 `setState`를 부를 수 있다. 작은 팀에서는 빠르지만, 저장소가 커지면 "이 값을 누가 바꾸나"를 찾기 어려워진다. 저장소를 관심사별로 여러 개 나누고, 바꾸는 함수는 저장소 안에만 두는 규칙을 팀이 정해야 한다.

## Jotai: 상태를 원자로 쪼개고 의존을 따라간다

Redux와 Zustand가 큰 저장소 하나에서 셀렉터로 조각을 고른다면, Jotai는 처음부터 상태를 작은 조각(atom)으로 만든다. 그리고 다른 atom에서 계산되는 atom을 만들 수 있다.

```ts
import { atom, useAtomValue, useSetAtom } from "jotai";

const itemsAtom = atom<CartItem[]>([]);
const couponAtom = atom<string | null>(null);
const subtotalAtom = atom((get) => get(itemsAtom).reduce((sum, i) => sum + i.price * i.qty, 0));
const totalAtom = atom((get) => {
  const subtotal = get(subtotalAtom);
  return get(couponAtom) === "WELCOME" ? subtotal * 0.9 : subtotal;
});

function Total() {
  const total = useAtomValue(totalAtom); // totalAtom이 바뀔 때만 렌더링된다
  return <strong>{total}</strong>;
}
```

계산 atom은 `get`으로 무엇을 읽었는지 기록한다. 그래서 Jotai는 atom 사이의 의존 그래프를 알고 있다. 아래 그림에서 점이 흐르는 방향이 "이 값이 바뀌면 다시 계산할 곳"이다.

이 방식은 셀렉터 메모이제이션을 따로 신경 쓸 일이 적다. 계산 atom이 자기 의존 atom이 바뀔 때만 다시 계산되고, 결과가 같으면 구독자도 깨우지 않는다. 비동기 atom은 Promise를 돌려주고 Suspense와 엮인다. 값이 여러 화면에 흩어져 있고 서로 계산으로 얽힌 화면, 예를 들어 설정 패널이나 견적 계산기에 잘 맞는다. 이 블로그도 테마와 검색창 열림 같은 값을 Jotai atom으로 다룬다.

Recoil은 같은 원자 모델을 먼저 들고 나온 라이브러리다. Meta가 실험 저장소로 공개했지만 오래 새 버전이 나오지 않다가 2025년 초 저장소가 보관(archived) 처리되어 더 이상 관리되지 않는다. 새로 고르는 대상은 아니고, 남아 있는 코드라면 Jotai가 개념이 가장 가까운 이전 대상이다.

Jotai의 비용은 atom이 많아질 때 흐름이 그래프에 숨는다는 점이다. 어느 atom이 어느 atom을 바꾸는지 한눈에 안 보인다. 그리고 모든 라이브러리가 `useSyncExternalStore`를 쓰는 건 아니다. Jotai 2의 `useAtomValue`는 `useReducer`로 렌더링을 일으키고 `useEffect`에서 store를 구독한다. 비동기 atom과 Suspense를 함께 다루기 위한 선택인데, 그래서 다음 절의 tearing 보장도 라이브러리마다 같지 않다.

## MobX와 시그널: 읽은 것을 기억해 두는 방식

MobX는 반대쪽 끝에 있다. 불변 업데이트 대신 상태를 제자리에서 고친다.

```ts
class CartStore {
  items: CartItem[] = [];
  constructor() { makeAutoObservable(this); }
  add(item: CartItem) { this.items.push(item); }       // 그냥 고친다
  get count() { return this.items.length; }            // 계산 값은 캐시된다
}

const CartBadge = observer(({ cart }: { cart: CartStore }) => <span>{cart.count}</span>);
```

`makeAutoObservable`이 속성을 관찰 가능한 값으로 바꾸고, `observer`로 감싼 컴포넌트는 렌더링하는 동안 어떤 속성을 읽었는지 기록한다. 나중에 그 속성이 바뀌면 그 컴포넌트만 다시 렌더링한다. 셀렉터를 쓰지 않아도 읽은 것만 구독하는 셈이다. 도메인 객체가 크고 서로 참조하는 편집기, 도면 도구처럼 객체 지향으로 모델을 짜는 쪽에서 편하다. 대신 "어디서 바뀌었나"가 Redux만큼 드러나지 않고, `observer`를 빼먹은 컴포넌트는 값이 바뀌어도 그대로라 버그가 조용하다.

시그널은 이 아이디어를 더 작게 만든 것이다. Solid, Preact, Angular, Vue의 반응형 값이 이 계열이다. `signal(0)` 같은 값 상자를 만들고, 그 값을 읽은 계산이나 DOM 조각만 다시 실행한다. Preact에서는 시그널을 JSX 텍스트로 바로 넘기면 컴포넌트를 다시 렌더링하지 않고 그 텍스트 노드만 바꾼다. 이렇게 컴포넌트보다 작은 단위로 반응하는 걸 미세 반응성(fine-grained reactivity)이라고 한다.

React는 이 모델이 아니다. React에서 화면이 바뀌는 단위는 여전히 컴포넌트 렌더링이고, 시그널을 붙이는 라이브러리도 결국 컴포넌트를 다시 렌더링하게 하거나 별도의 변환을 거친다. 자바스크립트 표준에 시그널을 넣자는 TC39 제안도 있지만 아직 초기 단계(Stage 1)라서 언어 차원의 이야기로 보기에는 이르다.

## 렌더링 도중에 저장소가 바뀌면

React 18의 동시성 렌더링은 긴 렌더링을 조각내고 중간에 브라우저에 양보한다. 그 틈에 바깥 저장소의 값이 바뀌면 문제가 생긴다. 앞에서 렌더링한 컴포넌트는 옛 값을, 뒤에서 렌더링한 컴포넌트는 새 값을 읽는다. 한 화면에 서로 다른 시점의 값이 섞여 그려지는 걸 tearing(찢어짐)이라고 한다.

React의 state와 Context는 React가 직접 관리하니 렌더링 도중에 바뀌지 않는다. 문제는 React가 모르는 사이에 바뀌는 바깥 값이다. 아래는 transition 렌더링 중에 저장소의 테마가 바뀌는 상황이다.

`useSyncExternalStore`가 이름에 "sync"를 단 이유가 마지막 단계에 있다. 렌더링 도중 저장소가 바뀐 걸 발견하면 그 렌더링을 끊지 않는 동시성 모드로 이어 가지 않고, 막는(blocking) 동기 렌더링으로 다시 그려 모든 컴포넌트가 같은 값을 보게 한다. 대가도 있다. 저장소가 바뀌어서 생긴 렌더링은 `startTransition`으로 감싸도 낮은 우선순위로 미뤄지지 않는다. 바깥 저장소의 값으로 큰 목록을 거르는 화면이라면 입력은 저장소에, 무거운 결과는 `useDeferredValue`로 미루는 식으로 나눈다.

`getSnapshot`은 저장소가 그대로면 같은 참조를 돌려줘야 한다는 규칙도 이 비교 때문에 생겼다. 부를 때마다 새 배열을 돌려주면 React는 매번 바뀌었다고 보고 렌더링을 반복하다 멈춘다. 개발 빌드는 "The result of getSnapshot should be cached to avoid an infinite loop"를 찍는다. 앞의 Zustand 5 무한 루프와 같은 원인이다.

## 작은 저장소를 직접 만들어 보기

여기까지의 이야기를 함수 세 개로 확인해 보자. `createStore`는 상태를 들고 바뀔 때 구독자에게 알린다. `subscribeWithSelector`는 셀렉터로 고른 값이 비교 함수로 달라졌을 때만 콜백을 부른다. React의 `useSyncExternalStore`가 컴포넌트마다 하는 일이 이것이다. `shallow`는 객체의 최상위 값을 하나씩 비교한다.

아래쪽 `runStore`는 테스트용 진행기다. 콜백이 불릴 때마다 "이름 값"을 기록하니, 기록이 곧 렌더링 횟수다. 세 번째 테스트는 셀렉터가 매번 새 객체를 만들어 상관없는 `count`가 바뀌어도 header가 두 번 깨어나는 경우이고, 네 번째는 같은 셀렉터에 `shallow`를 써서 막는 경우다.

  if (typeof a !== "object" || typeof b !== "object" || a === null || b === null) return false;

## 서버 상태를 빼고 남은 전역 값부터 센다

라이브러리를 고를 때 따질 것은 기능 목록보다 팀과 상태의 모양이다. 같은 저울에 올리면 이렇다.

| | 바꾸는 길 | 구독 단위 | 바꾸는 방식 | 잘 맞는 곳 |
|---|---|---|---|---|
| Context + useState | setter | Provider 값 전체 | 새 값 | 테마, 로그인 사용자처럼 드물게 바뀌는 값 |
| Redux Toolkit | 액션 → 리듀서 | 셀렉터 | 불변(Immer) | 큰 팀, 변경 이력과 미들웨어가 필요한 도메인 |
| Zustand | 저장소의 함수 | 셀렉터 | 불변 | 작은 팀, React 밖에서도 만지는 전역 값 |
| Jotai | atom setter | atom | 불변 | 계산으로 얽힌 작은 값이 많은 화면 |
| MobX | 객체 메서드 | 읽은 속성 | 제자리 수정 | 객체로 모델링한 큰 도메인(편집기, 도면) |

순서대로 따져 보면 대개 답이 좁혀진다. 먼저 서버 데이터를 서버 상태 도구로 빼고 나서 남은 전역 값이 몇 개인지 센다. 서너 개이고 드물게 바뀐다면 Context로 충분하고, 라이브러리를 더하지 않는 게 가장 싸다. 자주 바뀌는 값이 섞여 Context 리렌더링이 보이기 시작하면 셀렉터가 있는 저장소로 옮긴다. 작은 팀이면 Zustand나 Jotai가 코드가 적다. 둘 중에서는 값이 한 덩어리로 다뤄지면 Zustand, 서로 계산으로 엮인 작은 값이 많으면 Jotai가 자연스럽다.

여러 팀이 한 앱의 상태를 함께 건드리고, "이 값이 왜 바뀌었나"를 추적하는 일이 잦고, 되돌리기나 감사 로그처럼 모든 변경을 한곳에서 가로채야 한다면 Redux Toolkit의 규칙이 비용보다 값어치가 있다. 상태가 클래스로 짠 도메인 모델이고 객체끼리 참조가 많으면 MobX가 코드를 덜 비튼다.

옮겨 가는 일도 생각해 둔다. 이 라이브러리들은 한 앱에 함께 있을 수 있어서 한 번에 바꿀 필요가 없다. 보통 서버 데이터부터 서버 상태 도구로 옮기면 기존 저장소의 크기가 크게 줄고, 남은 조각을 화면 단위로 새 저장소로 옮긴다. 어느 쪽이든 컴포넌트가 라이브러리 API를 직접 부르지 않고 `useCartCount()` 같은 자기 훅을 거치게 해 두면 바꿀 때 고칠 곳이 그 훅으로 모인다.

## 면접에서 나올 만한 질문

### 상태 관리 라이브러리가 왜 필요한가요? Context로는 안 되나요?

여러 화면이 함께 보는 클라이언트 값을 한곳에 두고, 바뀐 값을 보는 컴포넌트만 다시 렌더링하려고 쓴다. Context는 값 객체 전체를 구독해서 한 칸만 바뀌어도 읽는 컴포넌트 전부가 렌더링되고, 일부만 구독하는 셀렉터가 없다. 드물게 바뀌는 값 몇 개면 Context로 충분하고, 자주 바뀌는 값이 섞이면 셀렉터나 atom 단위로 구독하는 저장소가 낫다. 서버 데이터는 애초에 서버 상태 도구로 뺀다.

### Redux의 데이터 흐름을 설명해 보세요.

컴포넌트가 무슨 일이 있었는지 담은 액션을 dispatch하면, 미들웨어가 먼저 보고 리듀서가 이전 상태와 액션으로 다음 상태를 순수하게 계산한다. 저장소는 새 상태로 바꾼 뒤 구독자에게 알리고, useSelector의 셀렉터가 다시 돌아 결과가 달라진 컴포넌트만 렌더링된다. 변경이 모두 이름 있는 액션으로 남아 추적과 되감기가 쉽다. 지금은 Redux Toolkit의 createSlice와 configureStore로 쓰는 게 표준이다.

### Zustand에서 셀렉터가 객체를 돌려주면 왜 무한 루프가 나나요?

Zustand 5는 useSyncExternalStore를 그대로 쓰는데, React는 렌더링 중에 스냅숏을 다시 읽어 Object.is로 비교한다. 셀렉터가 매번 새 객체를 만들면 늘 달라 보여서 렌더링을 반복하다 최대 업데이트 깊이에 걸린다. useShallow로 감싸 얕은 비교를 하거나 원시값을 하나씩 고른다. react-redux는 같은 상태에 대한 셀렉터 결과를 기억하는 래퍼를 거쳐서 무한 루프 대신 불필요한 렌더링으로 나타난다.

### useSyncExternalStore는 무엇을 해결하나요?

React 바깥 저장소를 구독하는 표준 방법이고, 동시성 렌더링에서 생기는 tearing을 막는다. 렌더링 도중 저장소가 바뀌면 커밋 전에 스냅숏을 다시 확인해 달라진 걸 알아채고 동기 렌더링으로 다시 그려, 한 화면의 모든 컴포넌트가 같은 값을 보게 한다. 대신 저장소 변경으로 생긴 렌더링은 transition으로 미룰 수 없다. getSnapshot은 상태가 그대로면 같은 참조를 돌려줘야 한다.

### Tearing이 무엇인가요?

한 번에 그려진 화면 안에 서로 다른 시점의 값이 섞이는 현상이다. 동시성 렌더링이 중간에 양보하는 틈에 바깥 저장소가 바뀌면 앞의 컴포넌트는 옛 값, 뒤의 컴포넌트는 새 값을 읽는다. React state와 Context는 React가 관리해서 생기지 않고, 구독 없이 바깥 값을 직접 읽을 때 생긴다. useSyncExternalStore로 구독하면 막을 수 있다.

### Jotai 같은 원자 모델은 Redux와 무엇이 다른가요?

Redux는 큰 상태 하나에서 셀렉터로 조각을 고르고, Jotai는 처음부터 작은 atom으로 나누고 다른 atom에서 계산하는 atom을 만든다. 계산 atom이 무엇을 읽었는지 기록하니 의존 그래프를 따라 필요한 것만 다시 계산하고, 결과가 같으면 구독자를 깨우지 않아 메모 셀렉터를 따로 챙길 일이 적다. 대신 atom이 많아지면 변경 흐름이 그래프에 흩어져 한눈에 안 보인다.

### MobX나 시그널의 미세 반응성은 React의 렌더링 모델과 어떻게 다른가요?

MobX와 시그널은 렌더링이나 계산 중에 읽은 값을 기록해 두고, 그 값이 바뀌면 그것을 읽은 곳만 다시 실행한다. 시그널 계열 프레임워크는 컴포넌트보다 작은 텍스트 노드 단위로도 갱신한다. React는 상태가 바뀌면 컴포넌트를 다시 렌더링해 비교하는 모델이라, 이런 라이브러리를 붙여도 결국 컴포넌트 렌더링을 일으키는 방식으로 연결된다. MobX는 제자리 수정을 허용하는 대신 변경 경로가 덜 드러난다.

### 팀에 상태 관리 라이브러리를 고르라고 하면 어떻게 정하나요?

먼저 서버 데이터를 TanStack Query 같은 도구로 빼고, URL과 폼과 지역 상태를 제자리에 둔 뒤 남은 전역 값의 양과 모양을 본다. 적고 드물게 바뀌면 Context, 작은 팀에 자주 바뀌는 값이면 Zustand나 Jotai, 여러 팀이 함께 건드리고 변경 추적과 미들웨어가 중요하면 Redux Toolkit을 고른다. 어느 쪽이든 컴포넌트가 라이브러리를 직접 부르지 않고 자기 훅을 거치게 해서 나중에 바꿀 비용을 줄인다.
