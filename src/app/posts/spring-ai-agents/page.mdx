import { getPostMetadata } from "@/features/posts";

export const metadata = getPostMetadata("spring-ai-agents");

고객센터 챗봇에 "A-1001 주문 어디쯤 왔어요?"라고 묻는다. 모델은 이 질문에 답할 수 없다. 주문 정보는 우리 DB에 있고, 모델은 그 DB에 닿지 못한다. 그래서 모델이 할 수 있는 일은 "배송 조회 기능을 이 주문 번호로 불러 달라"고 요청하는 것까지다. 실제로 부르고 결과를 다시 건네는 건 애플리케이션의 몫이다.

이 주고받기를 도구 호출(tool calling)이라고 하고, 결과를 보고 또 도구를 부를지 정하는 반복을 에이전트 루프라고 부른다. 개념 쪽은 [에이전틱 RAG](/posts/agentic-rag)에서 다뤘다. 이 글은 스프링 애플리케이션 안에서 그 루프를 Spring AI로 짜면 실제로 어떤 HTTP 요청이 오가는지, 그리고 루프가 멈추지 않거나 도구가 권한 밖의 일을 하려 할 때 어디서 막는지를 본다.

예제는 JDK 21, Spring Boot 4.1.1, Spring AI 2.0.1(`spring-ai-starter-model-openai`)로 돌렸다. Spring AI 2.0.1의 루트 pom이 `spring-boot.version`을 4.1.1로 잡고 있어서 이 조합을 골랐다. 실제 LLM API 키는 쓰지 않았다. 대신 OpenAI 호환 API(`/v1/chat/completions`, `/v1/embeddings`)를 흉내 내는 작은 스텁 서버를 Node로 직접 짜서 19201 포트에 띄웠다. 스텁은 규칙대로 답한다. 질문에 주문 번호가 있으면 `tool_calls`를 돌려주고, 도구 결과를 받으면 그걸 문장으로 엮는다. 그러니 모델의 "판단"은 가짜지만, Spring AI가 보내는 요청 본문과 루프는 진짜다. 아래 로그에서 `[시각] #번호 POST`로 시작하는 줄은 스텁이 받은 요청을 요약한 것이고, usage의 토큰 수는 스텁이 UTF-8 바이트 수를 4로 나눈 어림값이다.

## 요청 한 번에 들어가는 것

설정은 이렇다. 스프링 부트가 `ChatClient.Builder`를 빈으로 만들어 주므로 코드에서는 받아서 쓰기만 한다. 어떤 조건에서 이런 빈이 생기는지는 [Spring Boot 자동 구성](/posts/spring-boot-auto-configuration) 글에서 봤다.

```properties
spring.ai.openai.base-url=http://127.0.0.1:19201/v1   # 스텁 서버. 실제로는 생략하면 OpenAI로 간다
spring.ai.openai.api-key=stub-key
spring.ai.openai.chat.model=stub-gpt
spring.ai.openai.embedding.model=stub-embed
```

2.0부터는 모델 이름 같은 옵션을 `spring.ai.openai.chat.model`처럼 바로 쓴다. 1.x의 `spring.ai.openai.chat.options.model`도 아직 동작하지만 2.0.0부터 deprecated다.

```java
String answer = chat.prompt()
    .system("너는 쇼핑몰 고객센터 상담원이다. 짧게 답한다.")
    .user(u -> u.text("{product} 배송은 보통 며칠 걸리나요?").param("product", "냉장고"))
    .call()
    .content();
```

```text
[03:19:07.870] #1 POST /v1/chat/completions model=stub-gpt messages=2 tools=[]
    system: 너는 쇼핑몰 고객센터 상담원이다. 짧게 답한다.
    user: 냉장고 배송은 보통 며칠 걸리나요?
    -> stop: 스텁 모델의 답: 냉장고 배송은 보통 며칠 걸리나요? usage=29+18
```

`{product}` 자리는 Spring AI가 채운 다음 보냈다. 모델 쪽에서 보면 메시지 두 개짜리 평범한 요청이다. 여기까지는 HTTP 클라이언트를 직접 써도 금방 만든다. Spring AI가 값을 하는 건 그 위에 얹는 것들이다. 아래 그림의 가운데 줄이 요청이 지나는 길이고, 위아래가 그 길에 끼어드는 부품이다.

## 문자열이 아니라 객체로 받고 싶을 때

고객 문의를 분류해 `Ticket` 객체로 받고 싶다고 하자. `content()` 대신 `entity()`를 부른다.

```java
enum Sentiment { POSITIVE, NEUTRAL, NEGATIVE }
record Ticket(String category, Sentiment sentiment, String summary, boolean urgent) {}

Ticket t = chat.prompt()
    .user("고객 문의를 분류해라: 주문한 지 일주일인데 배송이 사흘째 같은 곳에 멈춰 있어요.")
    .call()
    .entity(Ticket.class);
```

```text
ticket = Ticket[category=배송, sentiment=NEGATIVE, summary=배송이 사흘째 멈춰 있다는 불만, urgent=true]
```

모델이 자바 클래스를 알 리 없다. 스텁이 받은 요청을 그대로 찍어 보면 Spring AI가 한 일이 보인다. 사용자 메시지 뒤에 형식 지시문과 JSON Schema를 덧붙였다.

```text
고객 문의를 분류해라: 주문한 지 일주일인데 배송이 사흘째 같은 곳에 멈춰 있어요.
Your response should be in JSON format.
Do not include any explanations, only provide a RFC8259 compliant JSON response following this format without deviation.
Do not include markdown code blocks in your response.
Remove the ```json markdown from the output.
Here is the JSON Schema instance your output must adhere to:
```{
  "$schema" : "https://json-schema.org/draft/2020-12/schema",
  "type" : "object",
  "properties" : {
    "category" : { "type" : "string" },
    "sentiment" : { "type" : "string", "enum" : [ "POSITIVE", "NEUTRAL", "NEGATIVE" ] },
    "summary" : { "type" : "string" },
    "urgent" : { "type" : "boolean" }
  },
  "required" : [ "category", "sentiment", "summary", "urgent" ],
  "additionalProperties" : false
}```
```

(스키마 부분은 줄 수를 줄이려고 속성 하나를 한 줄로 모았다.) 스텁은 일부러 답을 ` ```json ` 울타리로 감싸 돌려줬는데, 변환기가 울타리를 걷어 내고 파싱했다. 이 방식은 프롬프트로 부탁하는 것이라 모델이 지키지 않을 수 있다. 스텁이 `sentiment`에 목록에 없는 `"ANGRY"`를 넣게 하면 이렇게 된다.

```text
tools.jackson.databind.exc.InvalidFormatException: Cannot deserialize value of type `demo.ai.AgentApp$Sentiment` from String "ANGRY": not one of the values accepted for Enum class: [POSITIVE, NEGATIVE, NEUTRAL]
```

패키지가 `tools.jackson`인 건 Spring Boot 4가 Jackson 3을 쓰기 때문이다([Spring Boot 4 마이그레이션](/posts/spring-boot-4-migration) 참고). 모델 출력을 파싱하는 코드는 이 예외를 정상 흐름의 하나로 다뤄야 한다. 다시 묻거나, 기본값으로 떨어지거나, 사람에게 넘긴다.

모델 API가 스키마 강제를 지원하면 그쪽에 맡길 수 있다. `entity(Ticket.class, spec -> spec.useProviderStructuredOutput())`로 바꾸면 지시문이 사라지고 요청에 `response_format`이 붙는다.

```text
[03:19:34.948] #2 POST /v1/chat/completions model=stub-gpt messages=1 tools=[] response_format=json_schema
    user: 고객 문의를 분류해라: 주문한 지 일주일인데 배송이 사흘째 같은 곳에 멈춰 있어요.
  "response_format": { "type": "json_schema", "json_schema": { "name": "json_schema", "strict": true, "schema": { ... } } }
```

프롬프트 토큰이 226에서 29로 줄었다(스텁 어림값). 스키마가 본문이 아니라 별도 필드로 가서다. 다만 이건 제공자가 `json_schema` 형식을 지원해야 쓸 수 있고, 지원 범위는 모델마다 다르다. OpenAI 호환이라고 내세우는 서버라도 이 필드를 무시하는 경우가 있으니 실제로 돌려 보고 고른다.

## 도구를 부르는 건 모델이 아니다

이제 처음 질문으로 돌아간다. 도구는 평범한 메서드에 `@Tool`을 붙여 만든다.

```java
@Component
public class OrderTools {
  @Tool(description = "주문 번호로 배송 상태를 조회한다")
  public String getOrderStatus(@ToolParam(description = "주문 번호. 예: A-1001") String orderId, ToolContext ctx) {
    System.out.println("  >> tool getOrderStatus(" + orderId + ") user=" + ctx.getContext().get("userId"));
    return "{\"orderId\":\"" + orderId + "\",\"status\":\"IN_TRANSIT\",\"hub\":\"대전 HUB\",\"eta\":\"2026-10-28\"}";
  }

  @Tool(description = "주문을 취소한다. 본인 주문만 취소할 수 있다")
  public String cancelOrder(@ToolParam(description = "취소할 주문 번호") String orderId, ToolContext ctx) { ... }
}
```

```java
ChatResponse r = chat.prompt()
    .user("A-1001 주문 어디쯤 왔어요?")
    .tools(tools)                              // 이번 요청에서 쓸 수 있는 도구
    .toolContext(Map.of("userId", "u-7"))      // 도구에만 건네는 값. 모델에는 가지 않는다
    .call()
    .chatResponse();
```

첫 요청에 Spring AI가 도구 목록을 어떻게 실어 보내는지부터 보자. 메서드 시그니처와 어노테이션에서 만든 정의다. 조각을 눌러 보면 모델이 무엇을 보고 도구를 고르는지 알 수 있다.

여기서 짚을 점이 두 가지 있다. 하나는 모델이 아무것도 실행하지 않는다는 것이다. 모델이 돌려준 건 텍스트다. 그러니 모델이 `cancelOrder`를 부르라고 했다고 그 요청이 정당하다는 보장은 없다. 다른 하나는 `toolContext`의 `userId`가 모델 요청에 실리지 않았다는 것이다. 사용자 신원처럼 모델이 정하면 안 되는 값은 이 통로로만 도구에 건넨다.

## 어드바이저 순서가 루프의 안과 밖을 가른다

위 출력에서 `[timing]`이 두 번 찍혔다. 어드바이저 하나가 요청마다 한 번씩, 루프 안에서 돌았다는 뜻이다. 도구 실행 루프 자체가 `ToolCallingAdvisor`라는 어드바이저이고, 체인에서 자기보다 뒤(order 값이 큰 쪽)에 있는 어드바이저만 매 바퀴 다시 부른다. 2.0.1 소스 기준으로 각 어드바이저의 기본 순서는 이렇다.

## 대화를 기억하는 건 모델이 아니다

모델 API는 상태가 없다. 앞에서 한 말을 기억하게 하려면 매번 앞의 대화를 같이 보내야 한다. `MessageChatMemoryAdvisor`가 그 일을 한다.

```java
ChatMemory memory = MessageWindowChatMemory.builder().maxMessages(10).build();
ChatClient c = builder.clone().defaultAdvisors(MessageChatMemoryAdvisor.builder(memory).build()).build();

c.prompt().user(q).advisors(a -> a.param(ChatMemory.CONVERSATION_ID, "u-7")).call().content();
```

```text
Q: 안녕, 내 이름은 민지야.
A: 스텁 모델의 답: 안녕, 내 이름은 민지야.
Q: 오늘 주문한 거 언제 와?
A: 스텁 모델의 답: 오늘 주문한 거 언제 와?
Q: 내 이름이 뭐였지?
A: 민지라고 했다.
다른 대화방: 이름을 들은 적이 없다.
```

스텁이 받은 메시지 수는 1, 3, 5로 늘었고, 대화 ID를 `u-8`로 바꾼 마지막 요청은 다시 1이었다. 모델이 기억한 게 아니라 애플리케이션이 매번 다시 보낸 것이다. 그래서 대화가 길어질수록 프롬프트 토큰이 쌓인다. `MessageWindowChatMemory`는 최근 메시지 N개(기본 20개)만 남기는 창이다. 기본 저장소는 메모리 안의 맵이라 재시작하면 사라지고, 인스턴스가 여러 대면 요청이 다른 Pod로 갈 때 기억이 끊긴다. 운영에서는 JDBC, Redis 같은 `ChatMemoryRepository` 구현으로 바꾼다. 대화 ID는 사용자가 보낸 값을 그대로 쓰지 말고 서버가 인증 정보에서 만든다. 남의 대화 ID를 넣으면 남의 기록이 붙는다.

## 찾은 문서를 붙여 주는 어드바이저

RAG도 어드바이저 하나로 붙는다. 청크를 어떻게 자르고 검색 품질을 어떻게 재는지는 [기본 RAG](/posts/rag-classic-pipeline)에 있으니, 여기서는 Spring AI가 실제로 무엇을 보내는지만 본다. 메모리 안에서 도는 `SimpleVectorStore`에 FAQ 세 줄을 넣고 `QuestionAnswerAdvisor`를 붙였다. 스텁의 임베딩은 글자 두 개씩 묶어 64칸에 해시한 가짜 벡터다.

```java
SimpleVectorStore store = SimpleVectorStore.builder(embeddingModel).build();
store.add(List.of(
    new Document("반품은 상품을 받은 날부터 7일 안에 신청할 수 있다.", Map.of("source", "faq/return.md")),
    new Document("냉장고 같은 대형 가전은 설치 기사가 방문해 배송한다.", Map.of("source", "faq/delivery.md")),
    new Document("포인트는 결제 금액의 1%가 적립된다.", Map.of("source", "faq/point.md"))));

var qa = QuestionAnswerAdvisor.builder(store)
    .searchRequest(SearchRequest.builder().topK(2).similarityThreshold(0.3).build())
    .build();
```

## 다른 서버의 도구를 빌려 쓰기: MCP

재고 조회 도구는 재고팀 서비스에 있다고 해 보자. 그 코드를 우리 앱에 복사해 `@Tool`로 만드는 대신, 재고팀이 도구를 서버로 내놓고 우리가 가져다 쓰는 방법이 MCP(Model Context Protocol)다. 도구 목록 조회와 호출을 JSON-RPC로 주고받는 규약이다. 재고 서버는 `spring-ai-starter-mcp-server-webmvc`에 메서드 하나로 만들었다.

```java
@Component
class InventoryTools {
  @McpTool(name = "getStock", description = "상품 코드로 남은 재고 수량을 조회한다",
      annotations = @McpTool.McpAnnotations(readOnlyHint = true, destructiveHint = false))
  public String getStock(@McpToolParam(description = "상품 코드. 예: C-3003") String sku) { ... }
}
```

```properties
server.port=19203
spring.ai.mcp.server.name=inventory
spring.ai.mcp.server.protocol=STREAMABLE   # 2.0.1의 기본값. 엔드포인트는 /mcp
```

규약이 실제로 어떻게 생겼는지 curl로 직접 말을 걸어 봤다. 먼저 `initialize`로 세션을 연다.

```bash
curl -sS -i -X POST http://127.0.0.1:19203/mcp \
  -H 'content-type: application/json' -H 'accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"0"}}}'
```

```text
HTTP/1.1 200

Content-Type: application/json
Content-Length: 276

{"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-06-18","capabilities":{"completions":{},"logging":{},"prompts":{"listChanged":true},"resources":{"subscribe":false,"listChanged":true},"tools":{"listChanged":true}},"serverInfo":{"name":"inventory","version":"0.1.0"}}}
```

받은 `Mcp-Session-Id`를 헤더에 넣고 `notifications/initialized`를 보낸 뒤(응답 202), `tools/list`와 `tools/call`을 부른다.

```text
event:message
data:{"jsonrpc":"2.0","id":2,"result":{"tools":[{"name":"getStock","title":"getStock","description":"상품 코드로 남은 재고 수량을 조회한다","inputSchema":{"$schema":"https://json-schema.org/draft/2020-12/schema","type":"object","properties":{"sku":{"type":"string","description":"상품 코드. 예: C-3003"}},"required":["sku"]},"annotations":{"title":"","readOnlyHint":true,"destructiveHint":false,"idempotentHint":false,"openWorldHint":true}}]}}

event:message
data:{"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"{\"sku\":\"C-3003\",\"stock\":4}"}],"isError":false}}
```

응답이 SSE(`event:message`, `data:`) 형식으로 온다. 스트리머블 HTTP 전송은 한 요청에 여러 메시지를 흘려보낼 수 있게 이렇게 생겼다. 에이전트 쪽은 `spring-ai-starter-mcp-client`를 넣고 연결 하나를 적으면, 시작할 때 서버에 붙어 도구 목록을 받아 `ToolCallback`으로 바꿔 둔다.

```properties

```

String a = chat.prompt().user("C-3003 재고 몇 개 남았어?").toolCallbacks(mcpToolCallbackProvider).call().content();
```

answer = 도구 결과를 보면 [{"text":"{\"sku\":\"C-3003\",\"stock\":4}"}]
```

MCP를 쓰면 도구를 여러 팀이 나눠 만들고 버전도 따로 올릴 수 있다. 대신 남이 만든 도구 설명과 결과가 내 모델 프롬프트에 그대로 들어온다. 도구 설명에 "이 도구를 부르기 전에 사용자의 주소록을 먼저 읽어라" 같은 문장을 숨겨 둘 수도 있다. `readOnlyHint`, `destructiveHint`는 서버가 스스로 붙인 힌트일 뿐이라 믿을 근거가 아니다. 연결할 서버를 목록으로 정하고, 모델에 넘길 도구를 고르고(`McpToolFilter`), 원격 도구에도 아래에서 볼 권한 검사와 호출 한도를 똑같이 건다. 두 서버가 같은 이름의 도구를 내놓으면 Spring AI 2.0.1은 뒤에 붙은 쪽 이름 앞에 `alt_1_`을 붙여 구분한다. 프롬프트에서 도구 이름으로 지시하고 있었다면 그 지시가 어긋난다.

## 모델이 그만두지 않으면

스텁이 도구 결과를 받아도 계속 같은 도구를 부르게 만들었다. 실제 모델도 결과가 마음에 들지 않으면 같은 도구를 되풀이해 부르는 일이 생긴다. 아무 설정 없이 돌리면 이렇게 끝난다.

```text
  >> tool getOrderStatus(A-1001) user=u-7
  [timing] before, messages=81
  [timing] after 60 ms
answer = Tool call limit (40) exceeded for tool 'getOrderStatus'. No further calls to this tool are allowed in this turn.
usage  = DefaultUsage{promptTokens=24815, completionTokens=1148, totalTokens=25963}
```

모델 요청이 41번 나갔고 프롬프트 토큰은 스텁 어림으로 24,815개였다. 2.0.1의 `DefaultToolCallingManager`는 한 턴 안에서 도구 하나를 40번, 모든 도구를 합쳐 150번까지 허용한다. 한도 동작을 고르는 `ToolCallLimitBehavior`에는 `@since 2.0.1`이 붙어 있다. 버전마다 기본값이 다를 수 있으니, 쓰는 버전에서 이 숫자부터 확인한다. 마지막 `answer`는 모델이 쓴 문장이 아니다. 한도를 넘자 Spring AI가 예외 메시지를 답 자리에 넣어 돌려준 것이다. 사용자 화면에 이 영어 문장이 그대로 나가지 않게 처리해야 한다.

토큰이 왜 이렇게 불어나는지는 메시지 목록을 보면 안다. 바퀴마다 assistant와 tool 메시지가 둘씩 붙고, 다음 요청은 그 전부를 다시 보낸다. 한도를 3으로 낮춰 바퀴별로 보면 아래와 같다.

바퀴마다 보내는 양이 늘어나니 합계는 바퀴 수의 제곱에 가깝게 커진다. 실제 모델이면 응답 시간도 그만큼 길어진다. 한도는 이렇게 건다.

```properties
spring.ai.tools.limits.max-calls-per-tool-default=3      # 도구 하나당 한 턴에 3번
spring.ai.tools.limits.max-calls-per-tool.cancelOrder=1  # 위험한 도구는 따로 더 낮게
spring.ai.tools.limits.max-total-tool-calls=10           # 모든 도구 합계
spring.ai.tools.limits.on-limit-exceeded=THROW           # 기본값. 넘으면 바로 끝낸다
```

`on-limit-exceeded`에는 `RETURN_ERROR_RESPONSE`도 있다. 도구를 실행하지 않고 "한도를 넘었다"는 결과를 모델에 돌려줘서, 모델이 다른 길을 찾게 하는 방식이다. 모델이 그 메시지를 알아듣고 멈추면 사용자에게 더 나은 답이 나간다. 하지만 이 스텁처럼 거절을 무시하고 계속 부르면 끝나지 않았다. 거절 응답도 다시 대화에 쌓이니 합계 한도 150을 넘어도 계속 거절 응답만 돌아왔다. 4,300번째 요청 언저리에서 프로세스를 직접 죽였고, 그때 요청 하나의 프롬프트가 스텁 어림으로 12만 토큰이 넘었다.

<Callout kind="warning">
`RETURN_ERROR_RESPONSE`는 멈출지를 모델에게 맡긴다. 이 설정을 쓸 때는 모델 호출 횟수나 턴 전체 시간을 따로 세서 강제로 끊는 장치를 함께 둔다. 기본값 `THROW`는 그 자리에서 끝낸다.
</Callout>

바깥 장치는 어드바이저로 만들 수 있다. 루프 안쪽(order 0)에 두고 모델 호출을 셌다. 같은 턴의 바퀴들은 요청 컨텍스트를 공유하므로 그 안에 카운터를 넣었다.

```java
static class RoundGuardAdvisor implements CallAdvisor {
  public int getOrder() { return 0; }   // ToolCallingAdvisor보다 안쪽: 매 바퀴를 본다
  public ChatClientResponse adviseCall(ChatClientRequest req, CallAdvisorChain chain) {
    var rounds = (AtomicInteger) req.context().get("rounds");
    if (rounds.incrementAndGet() > maxRounds) {
      throw new IllegalStateException("모델 호출 " + maxRounds + "번을 넘겨 이번 턴을 끊는다");
    }
    return chain.nextCall(req);
  }
}

chat.prompt().user(q).tools(tools)
    .advisors(a -> a.param("rounds", new AtomicInteger()).advisors(new RoundGuardAdvisor(5)))
    .call().content();
```

```text
  >> tool getOrderStatus(A-1001) user=u-7
  >> tool getOrderStatus(A-1001) user=u-7
  >> tool getOrderStatus(A-1001) user=u-7
IllegalStateException: 모델 호출 5번을 넘겨 이번 턴을 끊는다
```

`RETURN_ERROR_RESPONSE`에 한도 3을 준 채로 돌렸다. 도구는 세 번 실행됐고, 네 번째 요청에서 모델은 거절 메시지를 받았는데도 또 불렀고, 다섯 번째 요청 뒤에 가드가 끊었다. 스텁 로그에도 요청이 정확히 5번 찍혔다.

## 도구가 실패하거나 남의 주문을 건드리려 할 때

`u-7` 사용자가 남의 주문 `B-2002`를 취소해 달라고 했다. 도구 안에서 `ToolContext`의 사용자와 주문 주인을 비교해 예외를 던지게 했다.

```java
if (!user.equals(owners.get(orderId))) {
  throw new IllegalStateException("주문 " + orderId + "은(는) 요청한 사용자의 주문이 아니다");
}
```

```text
  >> tool cancelOrder(B-2002) user=u-7
answer = 도구 결과를 보면 주문 B-2002은(는) 요청한 사용자의 주문이 아니다
```

    user: B-2002 주문 취소해 주세요
    assistant:  tool_calls=cancelOrder({"orderId":"B-2002"})
    tool(call_1): 주문 B-2002은(는) 요청한 사용자의 주문이 아니다
```

예외가 호출한 쪽으로 튀어 나오지 않고 예외 메시지가 tool 메시지가 되어 모델로 갔다. `spring.ai.tools.throw-exception-on-error`의 기본값이 `false`라서다. 모델이 오류를 보고 사용자에게 설명하거나 다른 방법을 찾게 하려는 기본값이다. 대신 예외 메시지가 모델과 사용자에게 그대로 보이니, 스택 트레이스나 내부 테이블 이름이 메시지에 들어가지 않게 한다. 예외를 애플리케이션에서 직접 처리하고 싶으면 `true`로 바꾼다.

권한 검사가 도구 코드 안에 있다는 점이 중요하다. 시스템 프롬프트에 "본인 주문만 취소하라"고 적는 건 검사가 아니다. 모델은 지시를 어길 수 있고, 질문이나 검색된 문서에 숨은 지시가 모델을 속일 수도 있다. 도구는 HTTP API와 똑같이 다룬다. 모델이 보낸 인자는 사용자 입력과 같은 등급으로 검증하고, 신원은 모델이 아니라 인증된 세션에서 가져온다. 이 글에서는 `ToolContext`로 넘겼다.

위험도에 따라 더 나눈다. 조회 도구는 바로 실행하고, 취소·환불·메일 발송처럼 되돌리기 어려운 도구는 실행 전에 사람의 확인을 받는다. Spring AI는 자동 실행을 끄는 길을 열어 두었다. `spring.ai.chat.client.tool-calling.enabled=false`로 두면 `ToolCallingAdvisor`가 자동으로 붙지 않아서, 응답의 `tool_calls`를 애플리케이션이 받아 확인 화면을 띄운 뒤 직접 실행할 수 있다. 도구가 많아지면 요청마다 필요한 도구만 `tools(...)`로 넘긴다. 쓸 수 있는 도구가 적을수록 모델이 잘못 고를 일도, 공격자가 노릴 문도 줄어든다. 2.0.1에서는 요청에 실리지 않은 도구 이름을 모델이 지어내 부르면 실행하지 않는다(`spring.ai.tools.resolution.fallback.enabled` 기본값 `false`).

## 모델 API가 느리거나 503을 줄 때

모델 API는 다른 외부 API보다 느리고, 과부하 응답(429, 503)도 자주 준다. 스텁이 503만 돌려주게 해 봤다.

```text

    -> 503 (시도 1)
[03:20:49.133] #7 POST /v1/chat/completions model=stub-gpt messages=1 tools=[]
    -> 503 (시도 2)
[03:20:49.949] #8 POST /v1/chat/completions model=stub-gpt messages=1 tools=[]
    -> 503 (시도 3)
[03:20:51.924] #9 POST /v1/chat/completions model=stub-gpt messages=1 tools=[]
    -> 503 (시도 4)
```

```text
error after 5073 ms: com.openai.errors.InternalServerException: 503: stub overloaded
```

`call()` 한 번에 네 번 보냈다. 2.0의 OpenAI 모듈은 OpenAI 공식 Java SDK 위에 올라가 있고, `spring.ai.openai.max-retries` 기본값 3에 따라 SDK가 간격을 0.46초, 0.82초, 1.98초로 늘려 가며 재시도했다. 도구 루프 안에서 이런 재시도가 겹치면 사용자 요청 하나가 수십 초를 붙잡는다.

느린 응답도 봤다. 스텁이 5초 뒤에 답하게 하고 `spring.ai.openai.timeout=2s`를 줬는데, 끊기지 않고 5초를 기다려 답을 받았다. 2.0.1 소스를 보면 `OpenAiChatModel`이 요청마다 채팅 옵션의 타임아웃을 SDK 요청 옵션으로 넣는데, 설정 파일에서 만든 채팅 옵션에는 타임아웃이 들어가지 않아 옵션 클래스의 기본값 60초가 들어간다. 이 조합에서는 요청마다 옵션으로 주니 걸렸다.

```java
chat.prompt().user("안녕 #slow")
    .options(OpenAiChatOptions.builder().timeout(Duration.ofSeconds(2)))
    .call().content();
```

    -> 5초 지연
[03:23:14.306] #4 POST /v1/chat/completions model=stub-gpt messages=1 tools=[]
    -> 5초 지연
    -> stop: 스텁 모델의 답: 안녕 #slow usage=4+9
[03:23:17.290] #5 POST ...
[03:23:21.217] #6 POST ...

2초에서 끊기긴 했지만 타임아웃도 재시도 대상이라 네 번 시도하고 12.8초 만에 실패했다. 그리고 스텁 쪽 로그를 보면 끊긴 요청들도 서버에서는 끝까지 답을 만들었다. 실제 모델 API라면 버린 응답의 토큰 값도 낸다. 그래서 숫자는 바깥에서부터 정한다. 사용자에게 몇 초 안에 답해야 하는지(예: 20초)를 먼저 정하고, 거기서 모델 호출 한 번의 타임아웃과 재시도 횟수, 도구 루프의 바퀴 수를 나눠 갖는다. 계층별 타임아웃을 맞추는 법은 [타임아웃](/posts/timeouts), 모델 API가 계속 실패할 때 호출을 끊어 주는 장치는 [서킷 브레이커](/posts/circuit-breaker)에 있다.

## 운영에서 보는 숫자

Spring AI는 모델 호출마다 Micrometer 관측을 남긴다. 소스에 정의된 이름으로는 호출 시간 `gen_ai.client.operation`과 토큰 사용량 `gen_ai.client.token.usage`가 있고, 모델 이름과 토큰 종류(입력·출력)가 태그로 붙는다. 메트릭과 트레이스를 Prometheus, Tempo로 보내는 설정은 [Spring Boot 관측](/posts/spring-boot-observability)에서 이어 간다. 프롬프트와 응답 본문은 개인정보가 섞이기 쉬워 기본으로 로그에 남기지 않는다(`spring.ai.chat.client.observations.log-prompt` 기본값 `false`).

현장에서 자주 보는 증상과 볼 곳을 짝지으면 이렇다. 요청당 토큰이 갑자기 몇 배로 뛰면 도구 루프의 바퀴 수와 대화 메모리 창 크기를 본다. 답이 영어 예외 문장으로 나가면 도구 호출 한도에 걸린 것이다. 같은 도구가 한 턴에 여러 번 찍히면 도구 결과가 모델이 원하는 정보를 담고 있는지, 설명이 모호하지 않은지 본다. 응답 시간 꼬리가 길면 재시도 로그부터 확인한다. 어느 경우든 바퀴마다 모델 요청과 도구 실행을 한 줄씩 남겨 두어야 따라갈 수 있다. 이 글의 `[timing]` 같은 루프 안쪽 어드바이저가 그 자리다.

## 루프를 쥔 쪽이 책임도 진다

Spring AI가 해 주는 일은 요청 조립, 도구 정의 생성, 루프 실행, 대화와 문서 붙이기다. 모델은 매번 텍스트로 부탁만 하고, 실행은 전부 애플리케이션 안에서 일어난다. 그래서 무엇을 실행할지(도구 목록과 권한), 몇 번까지 할지(한도와 가드), 얼마나 기다릴지(타임아웃과 재시도)도 애플리케이션이 정한다. 스프링 앱 여러 개가 서로 부르는 구조에서 장애가 번지지 않게 하는 이야기는 [Spring Cloud와 쿠버네티스](/posts/spring-cloud-vs-kubernetes)에서 이어 간다.

## 면접에서 나올 만한 질문

### LLM의 도구 호출은 어떻게 동작하나요?

모델은 도구를 실행하지 않고, 어떤 도구를 어떤 인자로 불러 달라는 JSON을 돌려줄 뿐입니다. 애플리케이션이 요청에 도구 이름·설명·JSON Schema를 실어 보내면, 모델이 `finish_reason: tool_calls`와 함께 호출 요청을 냅니다. 애플리케이션이 그 함수를 실행하고 결과를 tool 메시지로 대화에 붙여 다시 보내고, 모델이 `stop`을 낼 때까지 반복합니다. Spring AI에서는 `ToolCallingAdvisor`가 이 루프를 돌고, 그래서 `call()` 한 번에 HTTP 요청이 여러 번 나갑니다.

### Spring AI의 어드바이저는 무엇이고, 순서가 왜 중요한가요?

어드바이저는 모델 호출 앞뒤에 끼어드는 체인으로, 대화 메모리·RAG·도구 루프가 모두 어드바이저입니다. 도구 루프가 자기보다 order 값이 큰 어드바이저만 바퀴마다 다시 부르기 때문에, order가 그 어드바이저가 턴마다 한 번 도는지 모델 호출마다 도는지를 정합니다. 메모리 어드바이저는 루프 바깥(HIGHEST_PRECEDENCE+200)에 있어 턴이 끝난 결과만 저장합니다. 호출 횟수나 비용을 세는 어드바이저를 바깥에 두면 도구를 수십 번 부른 턴도 한 번으로 셉니다.

### 에이전트가 같은 도구를 끝없이 부르면 어떻게 막나요?

호출 수 한도를 두고, 넘으면 루프를 끊습니다. Spring AI 2.0.1은 기본으로 도구당 40번, 합계 150번 한도가 있고 넘으면 바로 끝냅니다. 바퀴마다 앞의 대화를 전부 다시 보내니 비용은 바퀴 수의 제곱에 가깝게 늘어서, 실제 서비스에서는 훨씬 낮게(예: 3~10) 잡습니다. 한도 초과를 모델에 알려 주는 모드는 모델이 무시하면 끝나지 않으므로, 턴 전체의 모델 호출 수나 시간을 세는 바깥 가드를 같이 둡니다.

### 모델이 위험한 도구를 잘못 부르는 걸 어떻게 막나요?

권한 검사는 프롬프트가 아니라 도구 코드에 둡니다. 모델이 보낸 인자는 사용자 입력처럼 검증하고, 사용자 신원은 모델이 채울 수 없는 경로(Spring AI의 `ToolContext`)로 인증 정보에서 가져옵니다. 되돌릴 수 없는 도구는 자동 실행을 끄고 사람의 확인을 거치게 하며, 요청마다 필요한 도구만 넘겨 노출 면적을 줄입니다. 검색 문서나 원격 MCP 도구 설명에 숨은 지시가 모델을 조종할 수 있다는 점을 전제로 설계합니다.

### 구조화 출력은 어떻게 보장하나요?

프롬프트 방식과 제공자 강제 방식이 있고, 어느 쪽이든 파싱 실패를 처리해야 합니다. Spring AI의 `entity()`는 기본으로 JSON Schema와 형식 지시문을 사용자 메시지 뒤에 붙이는데, 모델이 enum 밖의 값을 넣으면 Jackson 역직렬화 예외가 납니다. 제공자가 지원하면 `response_format: json_schema`(strict)로 보내 모델 쪽에서 형식을 강제하게 할 수 있고, 프롬프트 토큰도 줄어듭니다. 실패하면 다시 묻거나 기본값으로 떨어지거나 사람에게 넘기는 경로를 미리 정합니다.

### 챗봇이 이전 대화를 기억하게 하려면 무엇이 필요한가요?

모델 API에는 상태가 없어서, 애플리케이션이 대화를 저장하고 요청마다 다시 실어 보내야 합니다. Spring AI의 `MessageChatMemoryAdvisor`와 `MessageWindowChatMemory`가 대화 ID별로 최근 N개 메시지를 붙입니다. 기본 저장소는 프로세스 메모리라 재시작이나 여러 인스턴스에서 끊기므로 운영에서는 JDBC나 Redis 저장소를 씁니다. 대화가 길수록 토큰이 늘고, 대화 ID를 클라이언트 값으로 받으면 남의 기록이 붙으니 서버가 정합니다.

### MCP는 무엇이고, 쓸 때 무엇을 조심하나요?

MCP는 도구와 리소스를 서버로 내놓고 클라이언트가 JSON-RPC로 목록 조회와 호출을 하는 규약입니다. 도구를 다른 팀이나 다른 프로세스가 따로 만들고 배포할 수 있다는 게 장점입니다. 대신 원격 서버의 도구 설명과 결과가 내 모델 프롬프트에 그대로 들어오므로, 연결할 서버를 제한하고, 넘길 도구를 거르고, 로컬 도구와 같은 권한 검사와 한도를 겁니다. `readOnlyHint` 같은 힌트는 서버가 스스로 붙인 것이라 보안 근거가 되지 않습니다.

### 모델 API 호출의 타임아웃과 재시도는 어떻게 정하나요?

사용자에게 답해야 하는 시간에서 거꾸로 나눕니다. Spring AI 2.0의 OpenAI 모듈은 기본 재시도 3번이라 실패 한 번이 네 번의 요청이 되고, 타임아웃도 재시도 대상이라 2초 타임아웃이 12초 넘게 걸리기도 했습니다. 끊은 요청도 서버에서는 계속 생성해서 비용이 나갈 수 있습니다. 그래서 호출당 타임아웃·재시도·도구 루프 바퀴 수를 전체 예산 안에서 정하고, 계속 실패하면 서킷 브레이커로 빠르게 실패시킵니다. 설정이 실제로 먹는지는 느린 스텁을 세워 확인합니다.
