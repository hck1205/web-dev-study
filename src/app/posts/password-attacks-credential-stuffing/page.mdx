로그인 실패 알림이 울려서 대시보드를 열었다. 실패 건수가 평소의 스무 배쯤 된다. 그런데 계정 잠금은 한 건도 걸리지 않았다. 실패 로그를 계정별로 묶어 보니 이상했다. 한 계정에 수십 번 틀린 게 아니라, 수천 개의 서로 다른 계정이 각각 한 번씩만 틀려 있었다. 그 사이사이에 성공한 로그인도 섞여 있었다.

"5번 틀리면 잠근다"는 정책은 한 계정을 집중해서 두드리는 공격만 상정한다. 지금 본 장면은 다른 공격이다. 이 글은 비밀번호를 노리는 공격 네 가지가 각각 무엇을 노리는지, 왜 계정 잠금 하나로는 못 막고 오히려 서비스 거부가 되는지, 그래서 무엇을 층층이 쌓아야 하는지를 정리한다. 실험 값은 이 컨테이너(Node 22)에서 직접 잰 것이다. 비밀번호를 저장하는 쪽 이야기는 [해시와 비밀번호 저장](/posts/hash-hmac-password-hashing)에, 두 번째 요소는 [TOTP와 2단계 인증](/posts/mfa-totp)에, 비밀번호를 아예 없애는 쪽은 [패스키](/posts/passkeys-webauthn)에 있다.

## 같은 실패 로그, 네 가지 공격

공격 이름이 비슷해서 헷갈리는데, 기준은 두 가지다. 계정을 하나 고르고 비밀번호를 바꿔 가는지, 비밀번호를 하나 고르고 계정을 바꿔 가는지. 그리고 비밀번호를 어디서 가져오는지.

무차별 대입(brute force)은 한 계정에 가능한 조합을 전부 넣어 본다. `aaaa`, `aaab`, `aaac` 순서로 간다. 온라인 로그인 폼에 대고 하기에는 너무 느려서, 지금은 주로 유출된 해시를 손에 넣은 뒤 오프라인에서 한다.

사전 공격(dictionary attack)은 무차별 대입에서 순서만 바꾼 것이다. 모든 조합 대신 사람이 실제로 자주 쓰는 비밀번호 목록부터 넣는다. `123456`, `password`, `qwerty`, 거기에 이름·생일·계절 같은 변형 규칙을 붙인다. 온라인에서도 상위 수백 개로 꽤 많이 맞힌다.

패스워드 스프레이(password spraying)는 방향을 뒤집는다. 비밀번호 하나(예: `Spring2026!`)를 정해 놓고 수천 계정에 한 번씩 넣는다. 한 계정당 실패가 한두 번이라 계정 잠금 임계값에 닿지 않는다. 회사 메일처럼 계정 목록을 쉽게 추측할 수 있고 비밀번호 정책이 "대문자·숫자·특수문자 포함, 90일마다 변경"인 곳에서 잘 통한다. 그런 정책 아래 사람들은 `계절+연도+!` 같은 패턴으로 수렴하기 때문이다.

크리덴셜 스터핑(credential stuffing)은 비밀번호를 추측하지 않는다. 다른 사이트에서 유출된 이메일·비밀번호 쌍을 그대로 내 서비스에 넣어 본다. 사람들이 여러 사이트에 같은 비밀번호를 쓰니, 성공률은 낮아도 목록이 수억 줄이면 맞는 쌍이 상당히 나온다. 각 쌍은 한 번만 시도하고, 비밀번호가 "맞을 수도 있는" 진짜 값이라 실패 로그만 보면 사람의 오타와 구별이 어렵다.

공격마다 로그에 남는 모양이 다르다. 무차별·사전 공격은 계정 하나에 실패가 몰린다. 스프레이는 IP 하나(또는 몇 개)에서 수많은 계정으로 같은 비밀번호가 퍼진다. 스터핑은 IP도 계정도 비밀번호도 다 다르고, 실패율이 평소보다 높다는 것과 성공 로그인 직후의 행동이 이상하다는 것 정도만 남는다. 어느 공격이냐에 따라 막는 지점이 달라지니, 실패 로그를 계정 기준 하나로만 보면 안 된다.

## 잠그면 공격자가 잠근다

계정 잠금은 무차별 대입에는 잘 듣는다. 5번 틀리면 30분 잠그면, 한 계정에 하루 240번 남짓밖에 못 넣는다. 문제는 잠금이 공격자에게도 버튼이 된다는 것이다.

스프레이는 잠금 임계값을 미리 알고 그 아래로 시도한다. 임계값이 5면 계정당 하루 3~4번만 넣는다. 임계값을 3으로 낮추면 사람의 오타에도 계정이 잠긴다. 스터핑은 계정당 한 번이라 잠금에 아예 걸리지 않는다.

더 나쁜 건 반대 방향이다. 잠금이 공격자 손에 있으면 공격자가 남의 계정을 일부러 잠글 수 있다. 계정 목록(이메일, 사번, 고객 번호)만 있으면 각각 다섯 번씩 틀린 비밀번호를 넣어서, 진짜 사용자를 전부 로그인 못 하게 만든다. 비밀번호를 하나도 몰라도 되는 서비스 거부 공격이다. 쇼핑몰이라면 할인 행사 날 아침에, 사내 시스템이라면 경쟁사가 아니라 퇴사자가 할 수도 있다.

<Callout kind="warning">
"N번 틀리면 계정을 무기한 잠그고 고객센터로 풀게 한다" 같은 하드 잠금은 공격자가 계정 목록만으로 전 사용자를 묶어 둘 수 있게 만든다. 잠금을 쓴다면 시간이 지나면 풀리게 하고, 잠긴 동안에도 MFA를 통과하거나 이메일 링크를 거치면 들어올 수 있는 길을 남긴다.
</Callout>

그래서 요즘은 "잠근다" 대신 "느리게 한다"를 쓴다. 실패가 쌓일수록 다음 시도를 받기까지 기다리는 시간을 늘린다(점진 지연). 1~3회는 그대로, 4회부터 1초, 2초, 4초, 8초로 늘려 상한(예: 15분)에서 멈춘다. 사람은 몇 번 틀려도 거의 못 느끼고, 기계는 시간당 시도 횟수가 확 떨어진다.

지연 시간을 정하는 함수는 짧다. 무료 횟수와 상한만 정해 두면 된다.

```js
// 무료 3회, 그다음부터 1초에서 두 배씩, 최대 900초(15분)
function delaySeconds(failures, { free = 3, cap = 900 } = {}) {
  if (failures <= free) return 0;
  return Math.min(2 ** (failures - free - 1), cap);
}
```

```text
1회 실패 → 0초
3회 실패 → 0초
4회 실패 → 1초
5회 실패 → 2초
6회 실패 → 4초
8회 실패 → 16초
10회 실패 → 64초
14회 실패 → 900초
```

10번째 실패에서 이미 1분을 기다린다. 사람이 10번 틀리는 일은 드물고, 틀렸다면 비밀번호 찾기로 넘어갈 때다. 지연은 서버가 요청을 붙잡고 `sleep`하는 방식으로 구현하면 안 된다. 그러면 공격자가 연결을 잔뜩 열어 서버의 동시 처리 자리를 다 차지한다. "다음 시도는 몇 시 이후부터"라는 시각을 저장해 두고, 그 전에 온 요청은 비밀번호를 검증하지 않고 바로 429와 `Retry-After`로 돌려보낸다.

```js
// 실패 카운터와 다음 허용 시각을 Redis에 둔다. 키는 계정+IP 조합
const key = `login:fail:${userId}:${ip}`;
const nextAt = Number(await redis.hget(key, "nextAt") ?? 0);
if (Date.now() < nextAt) {
  const wait = Math.ceil((nextAt - Date.now()) / 1000);
  return reply.code(429).header("Retry-After", String(wait)).send({ error: "too_many_attempts" });
}
// ... 비밀번호 검증. 실패하면 count를 올리고 nextAt = now + delaySeconds(count) * 1000
// 성공하면 키를 지운다. 키에는 TTL(예: 24시간)을 걸어 오래된 실패가 남지 않게 한다
```

키도 계정 하나만 쓰지 않는다. 계정 기준 카운터만 있으면 공격자가 남의 계정을 늦출 수 있으니, "이 계정 + 이 IP(또는 이 기기)" 조합으로 세는 카운터를 앞에 둔다. 진짜 사용자는 평소 쓰던 기기와 IP에서 들어오니 공격자가 만든 실패에 덜 휘말린다. NIST SP 800-63B(개정 3판)도 계정당 연속 실패를 100회 이하로 제한하라고만 하고, 그 안에서 지연·CAPTCHA·위험 기반 판단을 섞으라고 권한다. 5회 하드 잠금을 요구하지 않는다.

## 키를 여러 개로 세어야 보인다

스프레이와 스터핑을 잡으려면 계정 말고 다른 축으로 묶어 본다. 카운터를 한 개가 아니라 여러 개 둔다.

- IP 하나가 짧은 시간에 실패한 서로 다른 계정 수. 스프레이가 여기서 튄다.
- 계정 하나가 실패한 횟수와 그 계정을 시도한 서로 다른 IP 수.
- 기기 지문(브라우저 특성, 쿠키에 심어 둔 기기 ID) 하나가 시도한 계정 수.
- 서비스 전체의 로그인 실패율. 평소 10% 안팎이던 게 60%로 뛰면 스터핑을 의심한다.
- 같은 비밀번호 해시가 여러 계정의 실패에 반복해서 등장하는지(스프레이).

IP 기준 카운터는 쉽게 우회된다. 스터핑 도구는 주거용 프록시를 빌려 요청마다 IP를 바꾸고, 그러면 IP 하나당 시도가 한두 번이다. 그래도 IP 카운터를 버리지 않는 이유는 비용이다. 공격자가 IP를 바꿀수록 돈이 들고, 데이터센터 IP 대역이나 평판이 나쁜 대역은 따로 더 낮은 한도를 줄 수 있다. 여러 축 중 하나라도 튀면 그 요청에 CAPTCHA나 추가 확인을 붙인다.

실제로는 이 집계를 슬라이딩 윈도(예: 10분)로 돌리고, 저장소는 Redis의 집합이나 HyperLogLog를 쓴다. 한도 숫자와 429 응답, Redis가 멈췄을 때 열지 막을지는 [요청 수 제한을 API에 붙이기](/posts/rate-limiting-in-practice)에서, 윈도 알고리즘은 [요청 수 제한 알고리즘](/posts/rate-limiting-algorithms)에서 다룬다.

## 사람인지 묻는 일은 마지막에

CAPTCHA는 효과가 있지만 비싸다. 정상 사용자의 이탈을 늘리고, 시각 장애가 있는 사용자에게는 벽이 된다. 그리고 공격자는 CAPTCHA를 사람에게 싸게 풀게 하는 대행 서비스나 자동 풀이 도구를 쓴다. 그래서 모든 로그인에 붙이지 않고, 위 카운터 중 하나가 튀었을 때만 붙인다.

요즘 많이 쓰는 건 보이지 않는 검사다. 브라우저가 JS를 실행하는지, 마우스·키보드 이벤트가 사람처럼 들어오는지, 헤더 조합이 실제 브라우저와 맞는지를 점수로 매긴다. 점수가 낮을 때만 퍼즐을 띄운다. 이것도 결국 "의심스러운 요청에만 비용을 더한다"는 같은 생각이다. 공격을 완전히 막는 게 아니라 공격 한 번의 비용을 사람 한 명의 비용보다 높이는 게 목표다.

## 이미 털린 비밀번호는 받지 않는다

스터핑이 통하는 이유는 사용자가 다른 곳에서 털린 비밀번호를 내 서비스에도 쓰기 때문이다. 그렇다면 가입하거나 비밀번호를 바꿀 때 "이 비밀번호가 이미 유출 목록에 있나"를 확인해서 받지 않으면 된다. NIST SP 800-63B도 새 비밀번호를 유출 목록, 사전 단어, 서비스 이름 같은 금지 목록과 대조하라고 요구한다.

문제는 유출 목록이 수억 개라 직접 들고 있기 부담스럽고, 그렇다고 사용자 비밀번호를 외부 API에 보낼 수는 없다는 것이다. Have I Been Pwned의 Pwned Passwords API는 k-익명성으로 이걸 푼다. 비밀번호를 SHA-1로 해시한 뒤 앞 5글자만 보낸다. 서버는 그 5글자로 시작하는 모든 해시의 나머지 35글자와 등장 횟수를 돌려주고, 대조는 내 서버에서 한다. API 쪽은 내가 어떤 비밀번호를 확인했는지 알 수 없다. 앞 5글자가 같은 해시가 수백 개씩 있어서다.

## 계정이 있는지 알려 주지 않는다

스프레이와 스터핑 모두 출발점은 "이 서비스에 있는 계정 목록"이다. 서비스가 그 목록을 알려 주면 공격자는 없는 계정에 시도를 낭비하지 않는다. 로그인 실패 메시지가 "존재하지 않는 이메일입니다"와 "비밀번호가 틀렸습니다"로 나뉘어 있으면 그게 계정 확인 API가 된다. 이걸 사용자 열거(user enumeration)라고 한다.

메시지만 합쳐서는 부족하다. 응답 시간이 새기 때문이다. 아래는 일부러 열거가 되게 짠 로그인 서버다. 계정이 없으면 바로 404를 돌려주고, 있으면 scrypt로 비밀번호를 검증한다.

```js
const users = new Map([["alice@example.com", hash("correct horse")]]);

// 고치기 전: 계정이 없으면 해시 계산 없이 바로 돌아간다
const u = users.get(email);
if (!u) return send(404, { error: "user_not_found" });
const ok = timingSafeEqual(scryptSync(password, u.salt, 32, P), u.dk);
if (!ok) return send(401, { error: "wrong_password" });
```

curl로 각 15번씩 보내 응답 시간을 쟀다.

```bash
# 있는 계정과 없는 계정에 틀린 비밀번호를 보내고 걸린 시간만 출력한다
for e in alice@example.com nobody@example.com; do
  curl -s -o /dev/null -w "%{http_code} %{time_total}\n" \
    -H 'content-type: application/json' \
    -d "{\"email\":\"$e\",\"password\":\"wrong\"}" localhost:3000
done
```

```text
alice@example.com   401  min 0.1086s  median 0.1202s  max 0.1603s
nobody@example.com  404  min 0.0009s  median 0.0010s  max 0.0014s
```

상태 코드를 같게 맞춰도 120ms와 1ms는 숨길 수 없다. 공격자는 요청 몇 번이면 구분한다. 그래서 계정이 없을 때도 미리 만들어 둔 가짜 해시로 같은 계산을 한다.

```js
// 고친 뒤: 계정이 없어도 같은 비용의 계산을 하고, 같은 응답을 준다
const DUMMY = hash("dummy-password-never-used");
const rec = users.get(email) ?? DUMMY;
const ok = timingSafeEqual(scryptSync(password, rec.salt, 32, P), rec.dk) && users.has(email);
if (!ok) return send(401, { error: "invalid_credentials" });
```

```text
alice@example.com   401  min 0.1062s  median 0.1562s  max 0.2269s
nobody@example.com  401  min 0.1088s  median 0.1365s  max 0.1860s
```

이제 두 분포가 겹친다(이 컨테이너는 다른 작업과 CPU를 나눠 써서 흔들림이 크다). 가짜 해시는 실제 해시와 같은 알고리즘·같은 비용 파라미터로 만들어야 한다. 비용을 올리면서 가짜 해시를 안 바꾸면 다시 시간이 벌어진다.

로그인만 막으면 끝이 아니다. 가입 폼의 "이미 사용 중인 이메일입니다", 비밀번호 찾기의 "등록되지 않은 이메일입니다"도 같은 구멍이다. 비밀번호 찾기는 "입력한 주소로 가입된 계정이 있다면 메일을 보냈습니다"로 통일하고, 메일 발송은 큐로 빼서 응답 시간을 같게 만든다. 가입은 완전히 숨기기 어려우니(사용자 경험이 나빠진다) 가입 API에 더 낮은 요청 한도를 준다. 아이디 중복 확인 버튼 같은 공개 API도 같은 취급을 한다.

## 비밀번호 하나에 기대지 않는다

위의 장치를 다 쌓아도 스터핑을 완전히 막지는 못한다. 맞는 비밀번호를 들고 정상 사용자처럼 한 번만 들어오면 구별할 방법이 거의 없다. 그래서 비밀번호가 맞아도 그것만으로 들어오지 못하게 하는 게 가장 확실하다.

[TOTP 같은 두 번째 요소](/posts/mfa-totp)를 붙이면 유출된 비밀번호만으로는 로그인이 끝나지 않는다. 다만 숫자 코드는 가짜 사이트가 사용자에게서 받아 실시간으로 전달하는 피싱에는 뚫린다. [패스키](/posts/passkeys-webauthn)는 서명에 사이트 주소가 묶여 있어 그것도 막고, 서버에 털릴 비밀이 남지 않아 스터핑의 재료 자체가 사라진다.

스터핑 한 건이 계정 탈취로 이어지는 길을 따라가면, 막을 자리가 어디에 있는지 보인다.

모든 사용자에게 MFA를 강제하기 어렵다면 위험 기반 인증으로 타협한다. 평소와 다른 국가, 처음 보는 기기, 1시간 전 서울에서 로그인한 계정이 지금 다른 대륙에서 들어오는 경우(불가능한 이동)에만 추가 확인을 요구한다. 그리고 로그인 성공 뒤의 행동도 본다. 로그인하자마자 배송지나 이메일을 바꾸고 포인트를 쓰는 건 스터핑으로 들어온 계정의 전형적인 동선이다. 민감한 변경에는 비밀번호 재확인이나 MFA를 한 번 더 받는다.

로그인 폼을 단단히 막고 나면 공격자는 옆문으로 간다. 비밀번호 재설정, 모바일 앱 전용 로그인 API, 오래된 v1 API, SSO를 붙이기 전의 관리자 로그인처럼 같은 계정을 검증하는 다른 입구가 있으면 거기에 똑같이 넣어 본다. 요청 한도와 열거 방지는 로그인 함수 하나가 아니라 "비밀번호를 검증하는 모든 곳"에 붙어야 한다. 그래서 검증 로직을 한 서비스(또는 한 함수)로 모으고, 입구마다 따로 구현하지 않는다. 배치 서버나 파트너 연동처럼 사람이 아닌 클라이언트에는 아예 비밀번호를 주지 말고 [API 키나 서명 요청](/posts/api-key-hmac-auth)을 쓰게 한다.

재설정도 마찬가지다. 재설정 토큰은 충분히 긴 무작위 값으로 만들고, 한 번 쓰면 버리고, 짧게(예: 30분) 살게 한다. 재설정이 끝나면 그 계정의 다른 세션을 모두 끊는다. 공격자가 이미 들어와 있던 세션이 살아남으면 비밀번호를 바꾼 의미가 없다.

## 주기적 변경을 강요하지 않는 이유

NIST SP 800-63B는 정기적으로 비밀번호를 바꾸게 하지 말라고 한다(유출 증거가 있을 때만 바꾸게 한다). 대문자·숫자·특수문자를 섞으라는 구성 규칙도 요구하지 말라고 한다. 최신 개정판(800-63B-4)은 비밀번호만으로 로그인하는 경우 최소 길이를 15자로 올렸고, MFA와 함께 쓰면 8자를 허용한다. 대신 긴 비밀번호(64자 이상)와 공백·유니코드를 받아 주고, 위에서 본 유출 목록 대조를 하라고 한다.

이유는 사람이 실제로 어떻게 반응하느냐다. 90일마다 바꾸라고 하면 사람들은 `Spring2026!`에서 `Summer2026!`으로 끝자리만 바꾼다. 공격자도 이 패턴을 알고 사전에 넣는다. 바로 스프레이가 노리는 비밀번호다. 구성 규칙은 `P@ssw0rd`처럼 규칙은 지키지만 사전 맨 위에 있는 비밀번호를 만든다. 규칙이 강해 보일수록 실제 엔트로피는 비슷하고 사용자는 메모지에 적는다. 길이를 늘리고 유출 목록을 막는 편이 실제로 공격을 더 어렵게 한다.

국내에서는 보안 인증 심사나 내부 규정이 아직 주기적 변경을 요구하는 경우가 있다. 그럴 때는 규정 근거를 확인하고, 유출 목록 대조와 MFA를 보완 통제로 제시해 예외를 받는 쪽으로 이야기한다.

## 해시가 새면 속도 제한은 의미가 없다

지금까지는 모두 온라인 공격, 즉 내 로그인 API를 거쳐야 하는 공격이었다. 지연, 카운터, CAPTCHA는 그 길목에서만 효과가 있다. DB가 통째로 유출되면 공격자는 해시를 자기 GPU에서 돌린다. 이때 남는 방어는 해시 비용뿐이다.

bcrypt의 cost를 바꿔 가며 이 컨테이너에서 재 봤다. 순수 JS 구현(bcryptjs)이라 네이티브 구현보다 느리지만, cost가 1 오를 때마다 시간이 두 배가 되는 모양은 같다.

```text
bcrypt cost 10   108 ms
bcrypt cost 12   367 ms
bcrypt cost 14  1552 ms
```

cost 12면 내 서버에서도 한 번에 수백 ms가 든다. 공격자의 GPU에서는 빨라지지만, MD5나 SHA-256처럼 초당 수십억 번 단위로는 가지 못한다. 결과적으로 사전 상위 몇백만 개는 결국 풀리고, 길고 유출된 적 없는 비밀번호는 오래 버틴다. 해시 비용은 "약한 비밀번호를 구한다"가 아니라 "강한 비밀번호를 쓴 사람이 털리지 않게 한다"와 "공지·강제 재설정까지 시간을 번다"는 역할이다. 비용 파라미터를 고르는 법과 Argon2id는 [해시와 비밀번호 저장](/posts/hash-hmac-password-hashing)에 있다.

한 가지 연결이 더 있다. 해시 비용을 높이면 로그인 API 하나가 CPU를 많이 먹는다. 공격자가 로그인 요청을 쏟아부으면 그 자체로 서버가 넘어간다. 그래서 비싼 해시 검증 앞에 IP 기준의 가벼운 요청 한도를 먼저 두고, 해시 검증은 그걸 통과한 요청에만 한다. 대규모 트래픽 공격은 [DDoS 방어](/posts/ddos-protection) 쪽에서 막는다.

## 실패 로그가 튈 때 보는 순서

알림이 왔을 때 무엇부터 보면 좋은지 순서로 적어 둔다.

그 전에 로그 모양부터 정해 둔다. 실패 한 건이 JSON 한 줄이고, 계정·IP·시각과 함께 비밀번호 원문 대신 서버 비밀 키로 만든 HMAC 앞부분을 남긴다(이유는 아래에 적었다). 연습용으로 76줄짜리 로그를 만들어 `jq`로 묶어 봤다.

```text
{"ts":"2026-10-20T03:00:07.000Z","event":"login_failed","user":"u1000","ip":"203.0.113.77","pw_hmac":"a91f3c"}
{"ts":"2026-10-20T03:00:14.000Z","event":"login_failed","user":"u1001","ip":"203.0.113.77","pw_hmac":"a91f3c"}
```

```bash
# 계정별 실패 횟수 (무차별 대입이면 여기서 한 계정이 튄다)
jq -r 'select(.event=="login_failed") | .user' auth.log | sort | uniq -c | sort -rn | head -3

# IP별로 실패한 "서로 다른 계정" 수 (스프레이면 여기서 튄다)
jq -r 'select(.event=="login_failed") | "\(.ip) \(.user)"' auth.log | sort -u | awk '{print $1}' | uniq -c | sort -rn | head -3

# 같은 비밀번호가 몇 번 쓰였나 (스프레이는 비밀번호 하나가 반복된다)
jq -r 'select(.event=="login_failed") | .pw_hmac' auth.log | sort | uniq -c | sort -rn | head -3
```

```text
      6 u2001
      1 u5029
      1 u5028

     40 203.0.113.77
      1 198.51.100.11
      1 198.51.100.10

     40 a91f3c
      1 f9
      1 f8
```

첫 결과에서 `u2001` 한 계정에 6번 실패가 몰렸다. 두 IP에서 번갈아 온 걸 보면 본인이 기억을 더듬는 중일 수도 있고 작은 무차별 대입일 수도 있다. 둘째와 셋째 결과가 진짜 신호다. `203.0.113.77` 하나가 40개 계정에서 실패했고, 그 40번이 모두 같은 비밀번호(`a91f3c`)였다. 계정 카운터만 보면 한 건도 안 튀는 스프레이다. 나머지 30줄은 IP·계정·비밀번호가 다 흩어져 있고 그 사이에 성공이 3건 섞여 있었는데, 실패율이 평소보다 높다면 스터핑을 의심할 모양이다.

1. 실패율을 본다. 건수만 보면 트래픽이 늘어서인지 공격인지 구분이 안 된다. 실패 비율이 평소의 몇 배인지 본다.
2. 실패를 계정별, IP별, 비밀번호 해시별로 각각 묶는다. 계정 하나에 몰리면 무차별 대입, IP 하나가 계정 수천 개면 스프레이, 다 흩어져 있으면 스터핑이다.
3. 같은 시간대의 성공 로그인을 본다. 스터핑이면 성공이 섞여 있고, 그 계정들이 피해자다. 성공 직후 개인정보 변경이나 결제가 있었는지 본다.
4. 성공한 계정의 세션을 끊고, 비밀번호 재설정을 강제하고, 사용자에게 알린다. 다른 사이트에서 같은 비밀번호를 썼다면 거기도 바꾸라고 안내한다.
5. 공격 IP 대역, 사용자 에이전트, 기기 지문 중 공통점이 있으면 WAF나 게이트웨이에서 임시로 막거나 CAPTCHA를 강제한다. 영구 차단은 정상 사용자를 휘말리게 하니 기한을 둔다.
6. 사후에 로그인 API 응답(메시지·시간)으로 계정 존재 여부가 새는지 다시 본다.

로그에 비밀번호 원문을 남기면 안 된다는 것도 이때 자주 드러난다. 실패한 비밀번호는 대부분 사용자의 진짜 비밀번호에서 한 글자 틀린 값이다. 스프레이를 잡으려고 비밀번호를 묶어 보고 싶다면 원문 대신 서버 비밀 키로 만든 HMAC 값을 짧은 보관 기간과 함께 남긴다.

## 마무리

비밀번호 공격은 무엇을 고정하고 무엇을 바꿔 가는지로 나뉜다. 계정 하나를 두드리면 잠금과 지연이 듣지만, 스프레이와 스터핑은 계정당 한두 번이라 계정 카운터에 걸리지 않고, 잠금을 세게 걸면 공격자가 그걸로 사용자를 내쫓는다. 그래서 계정·IP·기기를 여러 축으로 세고, 의심스러운 요청에만 지연과 CAPTCHA를 붙이고, 유출된 비밀번호를 받지 않고, 응답 메시지와 시간으로 계정이 있는지 알려 주지 않는다. 그리고 결국 비밀번호 하나에 기대지 않도록 MFA나 패스키를 둔다.

## 면접에서 나올 만한 질문

### 무차별 대입, 패스워드 스프레이, 크리덴셜 스터핑은 어떻게 다른가요?

무차별 대입과 사전 공격은 계정 하나를 고정하고 비밀번호를 바꿔 가며 넣는다. 스프레이는 흔한 비밀번호 하나를 고정하고 수많은 계정에 한 번씩 넣어 잠금 임계값을 피한다. 크리덴셜 스터핑은 다른 사이트에서 유출된 이메일·비밀번호 쌍을 그대로 넣어 보는 것으로, 비밀번호 재사용을 노린다. 로그에서 실패가 계정에 몰리는지, IP에 몰리는지, 다 흩어지는지로 구분한다.

### 계정 잠금만으로 충분하지 않은 이유는 무엇인가요?

스프레이는 임계값 아래로 계정당 한두 번만 시도하고, 스터핑은 계정당 한 번이라 잠금에 걸리지 않는다. 반대로 잠금은 공격자가 계정 목록만으로 진짜 사용자를 전부 잠그는 서비스 거부 수단이 된다. 그래서 하드 잠금 대신 점진 지연을 쓰고, 계정과 IP·기기를 묶은 카운터로 공격자가 만든 실패가 진짜 사용자를 덜 막게 한다.

### IP 기준 요청 제한은 스터핑에 효과가 있나요?

혼자서는 약하다. 스터핑 도구는 주거용 프록시로 요청마다 IP를 바꿔 IP당 시도가 한두 번에 그친다. 그래도 공격 비용을 올리고 데이터센터·평판 나쁜 대역에 낮은 한도를 줄 수 있어 버리지 않는다. 서비스 전체 실패율, 기기 지문, 계정당 시도 IP 수 같은 다른 축과 함께 써서 하나라도 튀면 CAPTCHA나 추가 확인을 붙인다.

### 유출된 비밀번호를 외부 API로 확인하면 비밀번호가 새지 않나요?

HIBP Pwned Passwords는 k-익명성을 쓴다. 비밀번호의 SHA-1 해시에서 앞 5글자만 보내면 그 앞자리로 시작하는 해시 수백 개의 나머지와 횟수가 오고, 대조는 내 서버에서 한다. API는 그중 무엇을 찾았는지 알 수 없다. 응답 크기로 추측하지 못하게 Add-Padding 헤더를 쓰거나, 목록을 내려받아 내부에서 조회할 수도 있다.

### 사용자 열거는 어떻게 막나요?

로그인 실패는 계정 유무와 상관없이 같은 상태 코드와 같은 메시지로 돌려준다. 메시지만으로는 부족한데, 계정이 없을 때 해시 계산을 건너뛰면 응답 시간이 1ms와 120ms처럼 갈린다. 그래서 없는 계정에도 같은 비용의 가짜 해시로 검증을 돌린다. 비밀번호 찾기는 "계정이 있다면 메일을 보냈다"로 통일하고, 가입·중복 확인 API에는 낮은 요청 한도를 준다.

### NIST는 왜 주기적인 비밀번호 변경을 권하지 않나요?

강제로 바꾸게 하면 사람들이 계절·연도처럼 예측 가능한 패턴으로 조금씩만 바꾸고, 공격자도 그 패턴을 사전에 넣어 스프레이에 쓴다. 구성 규칙도 규칙만 지킨 흔한 비밀번호를 만든다. SP 800-63B는 대신 충분한 길이, 유출 목록 대조, 긴 비밀번호 허용을 요구하고, 변경은 유출 증거가 있을 때만 하게 한다.

### DB가 유출되면 온라인 방어는 소용이 있나요?

없다. 지연·카운터·CAPTCHA는 로그인 API를 거쳐야 하는 공격에만 듣고, 해시를 가져간 공격자는 오프라인에서 GPU로 돌린다. 이때 남는 방어는 bcrypt·scrypt·Argon2id의 비용과 사용자별 솔트다. 약한 비밀번호는 결국 풀리지만 긴 비밀번호는 오래 버티고, 그 사이에 강제 재설정과 공지를 할 시간을 번다.

### 해시 비용을 높이면 생기는 부작용은 무엇인가요?

로그인 한 번이 CPU를 수십~수백 ms 쓰니, 로그인 요청을 쏟아붓는 것만으로 서버가 넘어갈 수 있다. 그래서 비싼 해시 검증 앞에 가벼운 IP 기준 요청 한도를 먼저 두고 통과한 요청만 검증한다. 계정이 없을 때 쓰는 가짜 해시도 같은 비용으로 같이 올려야 응답 시간으로 계정 유무가 다시 새지 않는다.
