<EasyIntro>
  사진 앱에서 피드의 사진을 누르면 피드 위에 사진이 크게 뜨고, 주소창도 그 사진의 주소로 바뀐다. 친구가 그 주소를 열면 피드 없이 사진 페이지가 바로 열린다.

  같은 주소인데 어떻게 들어왔느냐에 따라 다른 화면이 나오는 셈이다. Next.js는 이걸 두 가지 기능을 합쳐서 만든다.

  하나는 한 화면에 칸을 여러 개 두고 칸마다 다른 페이지를 넣는 기능이다. 다른 하나는 다른 페이지로 가려는 이동을 중간에 붙잡아서 지금 화면의 빈칸에 대신 넣어 주는 기능이다.

  극장으로 치면 무대 앞쪽에 작은 칸을 하나 더 만들어 두고 다음 장면 배우를 그 칸에 먼저 세우는 것과 비슷하다. 무대 뒤의 원래 장면은 그대로 남아 있다.
</EasyIntro>

사진 피드를 만드는데 요구 사항이 이렇다. 피드에서 사진을 누르면 피드 위에 모달로 뜬다. 주소는 `/photo/1`로 바뀌어서 그대로 공유할 수 있다. 그 주소를 새로고침하거나 공유받아 열면 모달이 아니라 사진 상세 페이지가 나온다. 뒤로 가기를 누르면 모달이 닫히고 피드가 그대로 있다.

처음에는 `useState`로 모달을 띄웠다. 주소가 바뀌지 않으니 공유가 안 됐다. 다음에는 클릭할 때 `router.push("/photo/1")`를 했다. 주소는 바뀌었지만 상세 페이지로 넘어가 버려 피드가 사라졌다. 피드를 보면서 사진 주소까지 바꾸려면 "한 화면에 페이지 둘"과 "같은 주소를 들어온 길에 따라 다르게 그리기"가 같이 필요하다. Next.js App Router에서는 앞의 것을 병렬 라우트, 뒤의 것을 가로채는 라우트라고 부른다. 이 글은 Next.js 16.4.1로 이 모달을 직접 만들고 Playwright로 클릭, 새로고침, 뒤로 가기를 따라가며 확인한다. 폴더와 세그먼트, layout의 기본 규칙은 [App Router 라우팅](/posts/nextjs-app-router-routing)에 먼저 정리해 두었다.

## 한 레이아웃에 페이지를 여러 개 두는 슬롯

병렬 라우트는 `@` 로 시작하는 폴더로 만든다. 이 폴더를 슬롯이라고 부른다. 슬롯은 주소에 나오지 않고, 같은 위치의 레이아웃에 props로 들어온다.

```text
app/feed
├── layout.js
├── page.js           # children 슬롯의 내용
└── @modal
    ├── default.js    # 맞는 페이지가 없을 때 그릴 것
    ├── page.js       # /feed 에서 modal 칸에 그릴 것
    └── (..)photo/[id]/page.js
```

```js
// app/feed/layout.js
export default function FeedLayout({ children, modal }) {
  return (
    <div>
      <h1>feed</h1>
      {children}
      {modal}
    </div>
  );
}
```

`children`도 사실 이름이 정해진 슬롯이다. `app/feed/page.js`는 `app/feed/@children/page.js`라고 써도 같다. 레이아웃은 슬롯을 원하는 자리에 놓거나, 조건에 따라 하나만 그릴 수 있다.

## 슬롯은 이동 방식에 따라 다르게 채워진다

Next는 슬롯마다 지금 무엇을 그리고 있는지 기억한다. 링크를 눌러 이동하는 소프트 내비게이션에서는 새 주소에 맞는 페이지가 있는 슬롯만 바꾸고, 맞는 페이지가 없는 슬롯은 이전 내용을 그대로 둔다. 그래서 `/feed`에서 `/photo/1`로 링크 이동하면 `modal` 칸만 바뀌고 `children` 칸은 피드로 남는다.

새로고침이나 주소 직접 입력 같은 하드 내비게이션에서는 이전 내용을 알 방법이 없다. 그때는 맞는 페이지가 없는 슬롯에 그 슬롯의 `default.js`를 그린다. `default.js`가 없으면 404다. 문서는 이 404가 의도하지 않은 페이지에 병렬 라우트를 실수로 그리는 일을 막는 장치라고 설명한다.

Next 16부터는 이 파일을 빼먹으면 빌드가 멈춘다. `@modal/default.js` 없이 빌드했다.

```text
⚠ Strict route matching is enabled by default. This validation indicates a bug in your app's route structure, but you can temporarily restore loose route matching by setting `deprecated.looseRouteMatching` to `true` in your Next.js config.
> Build error occurred
Error: Turbopack build failed with 2 errors:
Error: Parallel route slots cannot render the same URLs
The following layouts have parallel route slots that cannot render the same URLs:
app/feed/layout.js
- /feed is missing a matching page or default.tsx in @modal
Every URL matched by one slot must have a matching page or default.tsx in every sibling slot.
Error: Unmatched app pages
The following page files do not match any complete route:
- app/feed/page.js
```

메시지가 규칙을 그대로 말한다. 한 슬롯이 그리는 주소는 형제 슬롯에도 맞는 페이지나 `default`가 있어야 한다. 15 버전까지는 빌드가 통과하고 새로고침할 때 404가 나서 배포 뒤에야 알았다. 16에서 옛 동작으로 잠시 돌리려면 경고에 나온 `deprecated.looseRouteMatching`을 켤 수 있지만, 이름 그대로 없어질 옵션이다. 대부분은 `null`을 돌려주는 `default.js` 한 줄로 끝난다.

```js
// app/feed/@modal/default.js
export default function Default() {
  return null;
}
```

`children`도 슬롯이라 같은 규칙을 받는다. 슬롯 안에 하위 경로가 있고 `children` 쪽에 같은 경로의 페이지가 없으면 `app/feed/default.js`도 필요하다.

## 이동을 가로채는 폴더 이름

이제 `modal` 칸에 사진을 넣을 차례다. 사진 주소는 `/photo/[id]`인데, 이 주소로 가는 소프트 이동을 붙잡아 `feed` 안의 모달로 그리고 싶다. 폴더 이름 앞에 점 표시를 붙이면 된다.

```text
(.)photo      같은 레벨의 photo를 가로챈다
(..)photo     한 레벨 위의 photo
(..)(..)photo 두 레벨 위의 photo
(...)photo    app 루트의 photo
```

여기서 레벨은 파일 시스템 폴더가 아니라 라우트 세그먼트로 센다. 슬롯 `@modal`과 라우트 그룹 `(main)` 같은 괄호 폴더는 주소에 나오지 않으니 세지 않는다. 그래서 `app/feed/@modal/(..)photo/[id]`는 `@modal`을 건너뛰고 `feed`에서 한 레벨 위, 즉 루트의 `/photo/[id]`를 가로챈다. 폴더 깊이만 보고 `(..)(..)`를 쓰면 엉뚱한 주소를 기다리게 된다. 실험 앱의 빌드 표에는 이렇게 나왔다.

```text
├ ○ /feed
├ ƒ /feed/(..)photo/[id]
├ ƒ /photo/[id]
```

가로채는 라우트와 진짜 상세 페이지가 따로 있다. 둘 다 있어야 한다. 아래 함수는 가로채는 폴더 경로를 받아 그 폴더가 가로챌 주소를 돌려준다. 슬롯과 그룹을 세지 않는다는 규칙만 지키면 된다.

  // 2) (.) 같은 레벨, (..) 하나 위, (..)(..) 둘 위, (...) 루트
  // 3) 가로채는 표시가 없으면 null
  return null;
}`}
  solution={`function interceptTarget(folder) {
  const segs = folder.split("/").slice(1);
  const skip = (s) => s.startsWith("@") || /^\\([^.].*\\)$/.test(s);
  const route = [];
  for (let i = 0; i < segs.length; i++) {
    const m = segs[i].match(/^((?:\\(\\.\\.\\))+|\\(\\.\\.\\.\\)|\\(\\.\\))(.+)$/);
    if (m) {
      const marker = m[1];
      let base;
      if (marker === "(...)") base = [];
      else if (marker === "(.)") base = route.slice();
      else base = route.slice(0, route.length - marker.length / 4);
      const rest = segs.slice(i + 1).filter((s) => !skip(s));
      return "/" + [...base, m[2], ...rest].join("/");
    }
    if (!skip(segs[i])) route.push(segs[i]);
  }
  return null;
}`}

마지막에서 두 번째 테스트가 흔한 실수다. 모달을 `feed` 안에 두면서 `(.)`를 쓰면 `/feed/photo/[id]`를 기다린다. 피드에서 `/photo/1`로 가는 링크는 가로채지지 않고 상세 페이지로 그냥 넘어간다. 에러가 없어서 "가로채기가 안 된다"로만 보인다.

## 클릭할 때와 새로고침할 때 서버가 고르는 페이지

같은 `/photo/1`인데 서버는 어떻게 모달과 상세 페이지 중 하나를 고를까. 소프트 이동 요청에 단서가 있다. Playwright로 피드에서 사진을 누를 때 나간 RSC 요청의 헤더를 찍었다.

```text
rsc fetch /photo/1?_rsc=… next-url: /feed
```

라우터는 RSC payload를 요청하면서 `Next-Url` 헤더에 지금 보고 있는 주소를 담는다. 서버는 이 값을 보고 `/feed`에서 출발한 이동이면 `feed` 안의 가로채는 라우트를, 아니면 진짜 `/photo/[id]`를 고른다. 새로고침은 RSC 요청이 아니라 문서 요청이라 이 헤더가 없다. 아래 그림에서 두 경우를 이어서 보자.

실제로 브라우저를 움직여 확인한 결과다. `feed`는 피드 제목, `modal`은 모달 내용, `full`은 상세 페이지 본문이 화면에 있는지다.

```text
open /feed             /feed     | feed: 1 | modal: 0 | full: 0
click photo 1          /photo/1  | feed: 1 | modal: 1 | full: 0
reload                 /photo/1  | feed: 0 | modal: 0 | full: 1
back                   /feed     | feed: 1 | modal: 0 | full: 0
click photo 2          /photo/2  | feed: 1 | modal: 1 | full: 0
close (router.back)    /feed     | feed: 1 | modal: 0 | full: 0
forward                /photo/2  | feed: 1 | modal: 1 | full: 0
```

클릭하면 모달, 새로고침하면 상세 페이지, 뒤로 가기는 모달 닫기, 앞으로 가기는 모달 다시 열기다. 처음 요구 사항이 모두 맞는다. 앞으로 가기에서 모달이 다시 열리는 건 브라우저 history에 소프트 이동의 상태가 남아 있어서다.

## 모달 코드와 닫는 방법

가로채는 페이지는 모달 틀에 내용을 넣을 뿐이다. 진짜 상세 페이지와 같은 데이터 컴포넌트를 나눠 쓰면 두 화면이 어긋나지 않는다.

```js
// app/feed/@modal/(..)photo/[id]/page.js
import { Modal } from "@/components/modal";
import { PhotoView } from "@/components/photo-view";

export default async function PhotoModal({ params }) {
  const { id } = await params;
  return (
    <Modal>
      <PhotoView id={id} />
    </Modal>
  );
}
```

```js
// components/modal.js
"use client";
import { useRouter } from "next/navigation";

export function Modal({ children }) {
  const router = useRouter();
  return (
    <dialog open aria-modal="true">
      {children}
      <button onClick={() => router.back()}>닫기</button>
    </dialog>
  );
}
```

닫기는 `router.back()`이 기본이다. 모달을 열 때 history에 한 칸이 쌓였으니 한 칸 돌아가면 이전 상태(모달 없는 피드)가 된다.

`Link`로 피드에 돌아가게 하면 함정이 있다. `@modal/page.js` 없이 열린 모달에서 상단 메뉴의 `/feed` 링크를 눌렀다.

```text
click photo 1          /photo/1  | feed: 1 | modal: 1 | full: 0
Link to /feed (nav)    /feed     | feed: 1 | modal: 1 | full: 0
```

주소는 `/feed`인데 모달이 그대로 떠 있다. 소프트 이동에서 `modal` 슬롯에 `/feed`에 맞는 페이지가 없으니 이전 내용을 유지한 것이다. `default.js`는 하드 내비게이션에서만 쓰인다. `null`을 돌려주는 `@modal/page.js`를 더하고 같은 동작을 다시 했다.

```text
click photo 1          /photo/1  | feed: 1 | modal: 1 | full: 0
Link to /feed (nav)    /feed     | feed: 1 | modal: 0 | full: 0
```

이번에는 닫혔다. 모달 슬롯을 루트 레이아웃에 두는 구성이라면 어디로 가든 슬롯이 남으므로, 문서 예시처럼 `@modal/[...catchAll]/page.js`가 `null`을 돌려주게 해서 다른 모든 주소에서 모달을 비운다. 실험 앱처럼 `feed` 레이아웃에 슬롯을 두면 `/dash/a`처럼 피드 밖으로 나갈 때 레이아웃째로 사라지니 이 문제가 범위 안에서만 생긴다. 슬롯을 어느 레이아웃에 둘지가 이 비용을 정한다.

## 이 모달에서 자주 만나는 증상

새로고침하면 404가 난다. 두 가지 중 하나다. 진짜 `/photo/[id]/page.js`를 만들지 않았거나, 새로고침한 주소에서 형제 슬롯이 그릴 `default.js`가 없다. 16에서는 뒤의 것을 빌드가 잡지만 `deprecated.looseRouteMatching`을 켜 두었다면 다시 런타임에서 404가 난다.

사진을 눌러도 모달이 아니라 상세 페이지로 간다. 가로채는 폴더의 점 개수가 라우트 세그먼트 기준으로 맞는지 본다. 그리고 이동이 정말 소프트 내비게이션인지 본다. 일반 `<a>`로 링크했거나, `window.location`으로 옮기거나, 다른 루트 레이아웃으로 가는 이동이면 가로채기가 일어나지 않는다. 네트워크 탭에서 `_rsc` 요청에 `Next-Url`이 실려 나가는지 확인한다.

주소를 바꿔 다른 페이지에 갔는데 모달이 남는다. 앞 절처럼 그 주소에 맞는 `null` 페이지가 슬롯에 없어서다. catch-all `null` 페이지를 둔다.

공유받은 링크로 상세 페이지에 들어와 "닫기"를 누르면 사이트 밖으로 나간다. 모달 컴포넌트를 상세 페이지에서도 재사용하면서 `router.back()`을 그대로 부른 경우다. 상세 페이지에서는 모달 틀을 쓰지 않거나, 닫기 버튼을 `Link href="/feed"`로 바꾼다.

키보드 사용자가 모달을 열었는데 포커스가 뒤의 피드에 남아 있다. 주소가 바뀌어도 접근성은 따로 챙겨야 한다. 열릴 때 모달 안으로 포커스를 옮기고, Esc로 닫고, 닫힐 때 누른 사진으로 포커스를 돌려준다. 네이티브 `<dialog>`를 `showModal()`로 열면 바깥이 비활성화되고 Esc가 기본으로 동작해서 손이 덜 간다. 포커스 이동의 원칙은 [ARIA와 키보드 포커스](/posts/aria-keyboard-focus)에 있다. 모달이 열린 동안 뒤 페이지가 스크롤되지 않게 막는 것도 잊기 쉽다.

모달과 상세 페이지의 데이터가 다르다. 두 페이지가 각자 다른 함수로 데이터를 가져오면 생긴다. 같은 데이터 함수를 쓰고, 그 함수를 React `cache`나 캐시되는 fetch로 묶어 두면 요청 안에서 한 번만 불린다. 캐시 층은 [Next.js 캐시 네 겹](/posts/nextjs-caching-layers)에 있다.

## 다른 방법과 비교하면

주소가 있는 모달을 만드는 길이 이것만은 아니다. 처음에 버린 방법까지 포함해 셋을 놓고 보면 언제 이 구조가 값어치를 하는지 보인다.

쿼리 파라미터로 여는 방법이 가장 단순하다. 피드 페이지가 `?photo=1`을 읽어 모달을 그린다. 공유할 수 있고, 새로고침해도 피드 위 모달이 그대로 열린다. 폴더도 하나다. 대신 그 주소는 사진의 정식 주소가 아니다. 검색 엔진에 노출할 사진 상세 페이지는 따로 만들어야 하고, 같은 사진에 주소가 둘 생긴다. 그리고 페이지가 `searchParams`를 읽는 순간 그 라우트는 요청마다 렌더링된다. [정적·동적 렌더링](/posts/nextjs-static-dynamic-rendering#요청이-있어야-알-수-있는-값들)에서 본 규칙이다. 클라이언트 컴포넌트의 `useSearchParams`로 읽으면 페이지는 정적으로 남지만 Suspense로 감싸야 한다.

클라이언트 상태와 `window.history.pushState`를 쓰는 방법도 있다. Next 라우터는 직접 부른 `pushState`를 알아채서 `usePathname`과 맞춰 준다. 모달 내용은 클라이언트에서 받아 와야 하고, 새로고침하면 그 주소의 진짜 페이지가 열린다. 서버 렌더링 없이 빠르게 붙이기 좋지만, 데이터 받기와 로딩·에러 처리를 모두 클라이언트에서 다시 짠다.

병렬 라우트와 가로채기는 정식 주소 하나로 두 화면을 서버에서 그린다. 공유한 링크는 상세 페이지로, 피드 안의 클릭은 모달로 가고, 데이터 받기와 로딩·에러 경계를 서버 컴포넌트 규칙 그대로 쓴다. 치르는 값은 폴더 구조와 규칙이다. `default.js`, `null` 페이지, 점 개수, 슬롯이 동적이면 형제가 같이 동적이 되는 제약을 알아야 한다. 팀에 이 규칙을 아는 사람이 없으면 "가끔 모달이 안 닫힌다" 같은 버그가 오래 남는다.

고르는 기준은 상세 페이지가 독립된 주인공이냐다. 사진, 상품, 게시글처럼 검색과 공유의 대상이면 가로채는 라우트가 맞는다. 필터 패널이나 미리 보기처럼 그 페이지 안에서만 의미가 있으면 쿼리 파라미터로 충분하다.

## 모달 말고 병렬 라우트가 쓰이는 곳

대시보드처럼 한 화면에 독립적인 영역이 여럿 있을 때도 슬롯을 쓴다. 매출 그래프와 팀 목록을 `@revenue`, `@team` 슬롯으로 나누면 슬롯마다 `loading.js`와 `error.js`를 따로 둘 수 있다. 느린 그래프가 팀 목록까지 붙잡지 않고, 그래프 API가 실패해도 팀 목록은 정상으로 보인다. 각 영역이 자기 Suspense와 에러 경계를 가진 셈이다. 스트리밍이 조각을 흘려보내는 방식은 [스트리밍 SSR과 Suspense](/posts/streaming-ssr-suspense)에 있다.

```text
app/dashboard
├── layout.js           # revenue, team, children을 받는다
├── page.js
├── @revenue
│   ├── page.js
│   ├── loading.js      # 그래프만 스켈레톤
│   └── error.js        # 그래프만 에러 화면
└── @team
    ├── page.js
    └── default.js
```

실험 앱에서 `@revenue/page.js`가 "revenue api down"을 던지게 하고 `@revenue/error.js`를 두었다.

```text
/dashboard 500 | rev: 매출을 불러오지 못했다 다시 | team: kimlee
```

매출 칸에는 그 슬롯의 에러 화면이, 팀 칸에는 정상 목록이 나왔다. 다만 응답 상태는 500이었다. 슬롯 하나가 실패해도 문서 전체의 상태 코드는 실패로 나간다. 모니터링에서 이 페이지의 5xx가 늘어 보이는 이유가 되고, 검색 엔진도 500을 본다. 같은 슬롯에 `loading.js`를 더하고 에러를 300ms 늦게 던지게 바꿔 다시 요청했다.

```text
/dashboard 200 | rev: 매출을 불러오지 못했다 다시 | team: kimlee
```

화면은 같은데 상태가 200이다. `loading.js`가 그 슬롯을 Suspense로 감싸서 페이지의 나머지가 먼저 스트리밍되기 시작했고, 상태 코드는 첫 바이트와 함께 이미 나갔다. 그 뒤에 난 에러는 슬롯의 에러 화면으로만 바뀐다. 일부 영역의 실패를 페이지 실패로 세고 싶지 않다면 이렇게 Suspense 안에 두거나, 에러를 던지지 않고 "불러오지 못했다"를 값으로 그린다. 반대로 정말 페이지가 실패한 것이라면 이 방식은 모니터링에서 실패를 숨긴다는 점도 같이 기억한다.

역할에 따라 다른 화면을 보여 줄 때도 쓴다. 레이아웃이 사용자 역할을 읽어 `admin` 슬롯과 `user` 슬롯 중 하나만 돌려준다. 편하지만 이건 화면 분기일 뿐 권한 검사가 아니다. 관리자 슬롯이 부르는 데이터 함수나 서버 액션 안에서 권한을 다시 확인해야 한다. 이유는 [Route Handler와 Proxy](/posts/nextjs-route-handlers-proxy)의 "proxy만 믿으면 안 되는 이유"와 같다.

한 가지 제약이 있다. 같은 레벨의 슬롯은 정적·동적을 따로 가질 수 없다. 슬롯 하나가 동적이면 그 레벨의 슬롯이 모두 동적으로 렌더링된다. 실험 앱의 `/feed`는 빌드 표에서 `○`였는데, 문서 규칙대로라면 슬롯 하나가 `cookies()`를 읽는 순간 `/feed` 전체가 `ƒ`로 바뀐다. 사용자별 알림 같은 슬롯을 하나 넣을 때 정적 페이지 하나를 통째로 잃는 셈이다. 레이아웃 쪽 클라이언트 컴포넌트에서 슬롯의 현재 세그먼트를 알고 싶으면 `useSelectedLayoutSegment("modal")`처럼 슬롯 이름을 넘긴다.

## 다시 사진 피드로

처음 요구 사항은 두 장치를 합쳐서 풀렸다. 병렬 라우트는 `feed` 레이아웃에 `children`과 `modal` 두 칸을 만들고, 소프트 이동에서는 맞는 페이지가 없는 칸을 그대로 둔다. 그래서 피드가 남는다. 가로채는 라우트는 `Next-Url`로 출발지를 보고, 피드에서 온 `/photo/1` 이동을 `modal` 칸에 대신 그린다. 새로고침에는 출발지가 없으니 진짜 상세 페이지가 나온다. 빠뜨리기 쉬운 것은 셋이다. 하드 내비게이션을 위한 `default.js`, 소프트 이동에서 모달을 비울 `null` 페이지, 세그먼트 기준으로 센 점의 개수다.

## 면접에서 나올 만한 질문

### 병렬 라우트란 무엇이고 어떻게 만드나요?

한 레이아웃 안에서 여러 페이지를 동시에, 독립적으로 렌더링하는 기능이다. `@이름` 폴더로 슬롯을 만들면 같은 위치의 레이아웃이 그 이름의 prop으로 받는다. 슬롯은 주소에 나오지 않고, `children`도 이름이 정해진 슬롯이다. 슬롯마다 `loading.js`와 `error.js`를 따로 둘 수 있어 대시보드 영역을 독립적으로 로딩하고 실패시킬 수 있다.

### default.js는 왜 필요한가요?

새로고침 같은 하드 내비게이션에서는 슬롯이 이전에 무엇을 그렸는지 알 수 없어서, 현재 주소에 맞는 페이지가 없는 슬롯에 `default.js`를 그린다. 없으면 404다. Next 16부터는 형제 슬롯에 맞는 페이지나 default가 없으면 빌드가 실패한다. 보통 `null`을 돌려주는 한 줄짜리로 충분하다.

### 소프트 내비게이션과 하드 내비게이션에서 슬롯 동작은 어떻게 다른가요?

소프트 내비게이션에서는 새 주소에 맞는 페이지가 있는 슬롯만 바뀌고, 맞는 페이지가 없는 슬롯은 이전 내용을 유지한다. 그래서 모달이 열려도 피드가 남는다. 하드 내비게이션에서는 맞지 않는 슬롯에 `default.js`를 그린다. 이 차이 때문에 링크로 다른 주소에 가도 모달이 남는 문제가 생기고, 그 주소에 `null` 페이지를 둬서 해결한다.

### 가로채는 라우트의 (.), (..), (...)는 무엇을 기준으로 세나요?

파일 시스템 폴더가 아니라 라우트 세그먼트를 기준으로 센다. `(.)`는 같은 레벨, `(..)`는 한 레벨 위, `(..)(..)`는 두 레벨 위, `(...)`는 app 루트다. 슬롯 폴더와 라우트 그룹은 주소에 나오지 않으니 세지 않는다. 그래서 `feed/@modal/(..)photo`는 루트의 `/photo`를 가로챈다.

### 서버는 같은 주소에서 모달과 상세 페이지를 어떻게 구분하나요?

소프트 이동 때 라우터가 RSC 요청에 `Next-Url` 헤더로 현재 주소를 함께 보낸다. 서버는 출발지 라우트 안에 대상 주소를 가로채는 폴더가 있으면 그걸 렌더링한다. 새로고침이나 공유 링크는 문서 요청이라 출발지 정보가 없어 진짜 페이지를 그린다. 일반 `<a>` 링크나 다른 루트 레이아웃으로의 이동도 가로채지 않는다.

### 주소가 있는 모달을 만들 때 놓치기 쉬운 점은요?

모달을 닫는 경로를 모두 챙겨야 한다. `router.back()`은 직접 들어온 사용자를 사이트 밖으로 보낼 수 있고, `Link`로 다른 주소에 가면 슬롯이 이전 모달을 유지할 수 있어 `null` 페이지나 catch-all이 필요하다. 포커스를 모달 안으로 옮기고 Esc와 포커스 복귀, 뒤 페이지 스크롤 잠금을 처리한다. 모달과 상세 페이지가 같은 데이터 함수를 쓰게 해서 내용이 어긋나지 않게 한다.

### 역할별 대시보드를 병렬 라우트로 나누면 권한 문제는 해결되나요?

화면 분기일 뿐 권한 검사는 아니다. 레이아웃이 admin 슬롯을 그리지 않아도 그 슬롯이 쓰는 서버 액션이나 Route Handler는 누구나 직접 부를 수 있다. 데이터를 읽고 쓰는 함수 안에서 세션과 역할을 다시 확인해야 한다.
