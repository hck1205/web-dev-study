[이진 탐색 트리 글](/posts/ds-binary-tree-bst)은 정렬된 키 2만 개를 넣었더니 높이가 2만이 되어 찾기 한 번에 1만 단계가 걸린다는 데서 끝났다. 기울어진 BST(unbalanced tree)는 사실상 연결 리스트다. 실제 데이터는 자주 정렬된 채 들어온다. 자동 증가 id, 시각, 이미 정렬된 파일을 다시 넣는 일이 다 그렇다. 그래서 라이브러리의 정렬된 맵은 그냥 BST를 쓰지 않는다.

넣고 지울 때마다 높이를 O(log n)으로 묶어 두는 트리를 균형 탐색 트리(balanced search tree)라고 부른다. 방법은 크게 세 갈래다. 회전으로 모양을 고치는 AVL과 레드-블랙, 노드에 키를 여러 개 넣어 넓게 만드는 2-3-4 트리와 B-트리, 그리고 동전 던지기로 확률적으로 균형을 맞추는 스킵 리스트다. 이 글은 셋을 같은 질문으로 비교한다. 균형을 얼마나 엄격하게 지키나, 그 대가로 쓰기가 얼마나 비싸지나, 그래서 어디에 쓰이나. 출력은 모두 Node 22에서 직접 돌린 것이다.

## 회전 한 번이 높이를 하나 줄인다

모든 균형 트리의 기본 도구는 회전(rotation)이다. 부모와 자식의 위아래를 바꾸되 중위 순서, 즉 정렬 순서는 그대로 두는 연산이다. 아래 그림에서 y의 왼쪽이 오른쪽보다 둘 깊다. 오른쪽으로 회전하면 x가 올라가고 y가 내려간다.

움직이는 건 포인터 세 개다. y의 왼쪽이 x에서 B로, x의 오른쪽이 B에서 y로, y의 부모가 가리키던 자리가 x로 바뀐다. 키를 옮기지도 않고 다른 노드를 건드리지도 않으니 회전 한 번은 O(1)이다. B가 x에서 y로 옮겨 가도 괜찮은 이유는 B의 키가 모두 x보다 크고 y보다 작기 때문이다. 회전 전에도 후에도 B는 x와 y 사이에 있다.

```js
function rotateRight(y) {
  const x = y.left;
  y.left = x.right;   // B를 y에게 넘긴다
  x.right = y;        // y가 x 밑으로 내려간다
  updateHeight(y);    // 아래쪽부터 높이를 다시 잰다
  updateHeight(x);
  return x;           // 부모는 이제 x를 가리켜야 한다
}
```

반환값을 부모에 다시 이어 주지 않는 실수가 흔하다. 회전은 그 부분 트리의 뿌리를 바꾸니, 부모의 자식 포인터나 트리의 루트를 새 뿌리로 고쳐야 한다. 안 그러면 트리 절반이 사라진다.

## 높이 차를 1 이하로 지키는 AVL

AVL 트리는 1962년에 나온 첫 균형 트리다. 규칙은 하나다. 모든 노드에서 왼쪽과 오른쪽 부분 트리의 높이 차, 균형 인수가 -1, 0, 1 중 하나여야 한다. 넣거나 지운 뒤 뿌리 쪽으로 올라가며 높이를 고치다가 차이가 2가 된 노드를 만나면 회전한다.

기울어진 모양은 네 가지다. 왼쪽 자식의 왼쪽이 깊은 LL은 오른쪽 회전 한 번, 오른쪽의 오른쪽인 RR은 왼쪽 회전 한 번이다. 왼쪽 자식의 오른쪽이 깊은 LR은 자식을 먼저 왼쪽으로 돌려 LL로 만든 뒤 오른쪽으로 돌리는 이중 회전이고, RL은 그 반대다.

```js
const height = (n) => (n ? n.height : 0);

function insert(node, key) {
  if (!node) return { key, left: null, right: null, height: 1 };
  if (key < node.key) node.left = insert(node.left, key);
  else node.right = insert(node.right, key);
  node.height = 1 + Math.max(height(node.left), height(node.right)); // 올라오며 높이를 고친다
  const balance = height(node.left) - height(node.right);
  if (balance > 1) {                                   // 왼쪽이 둘 깊다
    if (key > node.left.key) node.left = rotateLeft(node.left); // LR이면 먼저 LL로 만든다
    return rotateRight(node);
  }
  if (balance < -1) {                                  // 오른쪽이 둘 깊다
    if (key < node.right.key) node.right = rotateRight(node.right); // RL이면 먼저 RR로
    return rotateLeft(node);
  }
  return node;
}
```

LR과 RL 판별에 방금 넣은 키를 쓰는 게 넣기 쪽의 요령이다. 키가 왼쪽 자식보다 크면 왼쪽 자식의 오른쪽으로 들어갔다는 뜻이다. 지우기에서는 넣은 키가 없으니 자식의 균형 인수를 직접 보고 고른다. 1부터 7까지 정렬된 순서로 넣으며 회전과 층별 모양을 찍었다.

```text
insert 1: no rotation | levels 1
insert 2: no rotation | levels 1 / 2
insert 3: RR at 1: rotate left | levels 2 / 1,3
insert 4: no rotation | levels 2 / 1,3 / 4
insert 5: RR at 3: rotate left | levels 2 / 1,4 / 3,5
insert 6: RR at 2: rotate left | levels 4 / 2,5 / 1,3,6
insert 7: RR at 5: rotate left | levels 4 / 2,6 / 1,3,5,7
```

1부터 차례로 넣었는데 꽉 찬 트리가 나왔다. 그냥 BST였다면 한 줄짜리 높이 7이다. AVL의 높이는 최악이어도 약 1.44 log₂ n이라 키 100만 개면 28을 넘지 않는다. 대가는 쓰기다. 넣을 때는 회전이 많아야 두 번(이중 회전 한 번)이면 끝나지만, 지울 때는 뿌리까지 올라가며 층마다 회전이 생길 수 있어 O(log n)번까지 돈다. 노드마다 높이나 균형 인수도 저장해야 한다.

지우기 쪽 균형 맞추기는 이렇게 생겼다. 지운 키가 없으니 어느 쪽으로 꺾였는지를 자식의 균형 인수로 판단한다.

```js
function rebalance(node) {
  node.height = 1 + Math.max(height(node.left), height(node.right));
  const balance = height(node.left) - height(node.right);
  if (balance > 1) {
    if (height(node.left.left) < height(node.left.right)) node.left = rotateLeft(node.left); // LR
    return rotateRight(node);
  }
  if (balance < -1) {
    if (height(node.right.right) < height(node.right.left)) node.right = rotateRight(node.right); // RL
    return rotateLeft(node);
  }
  return node;
}
```

넣기에서는 회전 한 번이 그 부분 트리의 높이를 넣기 전으로 되돌려서 위쪽은 더 볼 필요가 없다. 지우기에서는 회전 뒤 부분 트리의 높이가 하나 줄 수 있고, 그러면 위쪽 노드에서 다시 균형이 깨진다. 그래서 `rebalance`를 뿌리까지 올라가며 매번 불러야 하고 회전이 층마다 생길 수 있다.

## 노드를 넓혀서 맞추는 2-3-4 트리

회전과 전혀 다른 방법이 있다. 노드 하나에 키를 여러 개 넣는 것이다. 2-3-4 트리는 노드가 키 1개와 자식 2개(2-노드), 키 2개와 자식 3개(3-노드), 키 3개와 자식 4개(4-노드) 중 하나다. 키 2개짜리까지만 허용하면 2-3 트리다.

이 트리는 위로 자란다. 키는 항상 잎에 넣고, 잎이 넘치면 가운데 키를 부모로 올리며 둘로 쪼갠다(split). 부모가 넘치면 또 쪼개고, 뿌리가 넘치면 가운데 키로 새 뿌리를 만든다. 높이가 느는 곳은 뿌리 하나뿐이라 모든 잎의 깊이가 늘 같다. 기울 수가 없다. 10부터 100까지 10씩 넣었다. 이 구현은 내려가는 길에 꽉 찬 노드를 미리 쪼개는 방식이라, 넣을 자리가 넘치기 전에 쪼개기가 일어난다.

```text
insert 10: - | [10]
insert 20: - | [10 20]
insert 30: - | [10 20 30]
insert 40: split root, 20 goes up | [20] / [10] [30 40]
insert 50: - | [20] / [10] [30 40 50]
insert 60: split full child, 40 goes up | [20 40] / [10] [30] [50 60]
insert 70: - | [20 40] / [10] [30] [50 60 70]
insert 80: split full child, 60 goes up | [20 40 60] / [10] [30] [50] [70 80]
insert 90: split root, 40 goes up | [40] / [20] [60] / [10] [30] [50] [70 80 90]
insert 100: split full child, 80 goes up | [40] / [20] [60 80] / [10] [30] [50] [70] [90 100]
```

정렬된 키 10개를 넣었는데 잎 다섯 개가 모두 깊이 3에 있다. 40을 넣을 때 뿌리 [10 20 30]이 꽉 차 있어서 20이 위로 올라가 새 뿌리가 됐다. 90을 넣을 때는 뿌리 [20 40 60]이 꽉 차서 40이 올라가며 높이가 3이 됐다.

지우기는 반대 방향이다. 잎에서 키를 빼서 노드가 비면 옆 형제에게 키를 하나 빌리고(형제가 넉넉하면), 빌릴 수 없으면 형제와 부모의 키 하나를 합쳐(merge) 한 노드로 만든다. 합치다 뿌리가 비면 높이가 하나 준다. 이 쪼개기와 합치기가 그대로 B-트리의 연산이다.

```js
// 꽉 찬 자식 parent.kids[i](키 2t-1개)를 둘로 나누고 가운데 키를 parent로 올린다
function splitChild(parent, i, t) {
  const full = parent.kids[i];
  const right = { keys: full.keys.slice(t), kids: full.kids.slice(t) }; // 뒤쪽 t-1개
  const middle = full.keys[t - 1];
  full.keys = full.keys.slice(0, t - 1);                                // 앞쪽 t-1개
  full.kids = full.kids.slice(0, t);
  parent.keys.splice(i, 0, middle);       // 가운데 키가 부모의 i번째 칸으로
  parent.kids.splice(i + 1, 0, right);    // 오른쪽 반쪽이 새 자식으로
}
```

넣기는 뿌리에서 잎으로 내려가며 꽉 찬 노드를 만나면 이 함수로 미리 쪼갠다. 그러면 잎에 닿았을 때 늘 자리가 있고, 위로 되돌아가며 다시 쪼갤 일이 없다. 위 출력에서 90을 넣을 때 아직 넘치지 않았는데 뿌리가 쪼개진 이유다.

## 레드-블랙은 2-3-4 트리를 이진으로 쓴 것

2-3-4 트리는 노드 종류가 셋이라 코드가 지저분하다. 레드-블랙 트리는 같은 구조를 이진 트리로 표현한다. 3-노드와 4-노드를 검은 노드 하나와 거기 매달린 빨간 자식들로 펼친다. 빨간 간선은 "사실 위 노드와 한 몸"이라는 표시다. 아래 그림의 화살표가 그 대응이다.

이렇게 보면 레드-블랙의 규칙이 외울 거리가 아니라 2-3-4 트리의 성질을 옮긴 말이 된다.

- 노드는 빨강이나 검정이고 뿌리는 검정이다.
- 빨간 노드의 자식은 검정이다. 빨강이 두 번 이어지면 키 4개짜리 노드라는 뜻이라 허용되지 않는다.
- 어떤 노드에서 그 아래 모든 빈 자리(NIL)까지 가는 길에 있는 검은 노드 수가 같다. 2-3-4 트리의 모든 잎 깊이가 같다는 성질이다.

가장 긴 길은 검정과 빨강이 번갈아 나오는 길이고 가장 짧은 길은 검정만 있는 길이라, 높이는 최악 2 log₂(n + 1)이다. AVL보다 느슨하다. 넣을 때 삼촌 노드가 빨강이면 색만 바꾸는데(recolor), 이게 2-3-4 트리에서 꽉 찬 4-노드를 쪼개는 일이다. 삼촌이 검정이면 회전하는데, 이건 3-노드의 모양을 다시 잡는 일이다. 회전은 넣을 때 많아야 두 번, 지울 때 많아야 세 번이다. 색 바꾸기는 위로 번질 수 있지만 평균적으로는 상수 번이다.

넣기 뒤 고치기를 코드로 보면 두 갈래가 그대로 보인다. 새 노드는 빨강으로 넣고, 부모도 빨강이라 규칙이 깨진 동안만 반복한다. 부모가 할아버지의 왼쪽인 경우만 적었다. 오른쪽은 좌우를 바꾼 대칭이다.

```js
function fixAfterInsert(tree, z) {
  while (z.parent.red) {
    const g = z.parent.parent;                // 할아버지
    const uncle = g.right;
    if (uncle.red) {                          // 삼촌도 빨강: 4-노드가 넘쳤다 → 쪼개기
      z.parent.red = false;
      uncle.red = false;
      g.red = true;                           // 가운데 키(g)가 위 노드로 올라간다
      z = g;                                  // 위에서 다시 검사
    } else {
      if (z === z.parent.right) {             // 꺾인 모양이면 먼저 펴 준다
        z = z.parent;
        rotateLeft(tree, z);
      }
      z.parent.red = false;                   // 3-노드 모양을 다시 잡는다
      g.red = true;
      rotateRight(tree, g);                   // 여기까지 오면 반복이 끝난다
    }
  }
  tree.root.red = false;
}
```

반복이 위로 계속 올라가는 건 삼촌이 빨강인 색 바꾸기 경우뿐이고, 회전하는 경우는 한 번 돌면 바로 끝난다. 그래서 회전 수가 상수로 묶인다. 빈 자리를 `null`로 두면 `uncle.red`에서 터지니, 구현은 보통 검은색 감시 노드(NIL) 하나를 모든 빈 자리에 공유한다.

비슷하게 2-3 트리에 대응하는 좌편향 레드-블랙(LLRB)도 있다. 빨간 간선을 왼쪽에만 허용해 경우의 수를 줄인 변형이고, 교재 예제로 많이 쓰인다. 라이브러리는 대부분 위의 고전적인 레드-블랙을 쓴다.

## AVL과 레드-블랙, 무엇을 고르나

같은 키 100만 개를 정렬된 순서와 무작위 순서로 두 트리에 넣고 높이, 평균 깊이(찾을 때 거치는 노드 수의 평균), 넣기 한 번당 회전 수, 시간을 쟀다. 정렬된 순서의 그냥 BST는 높이가 n인 걸 이미 알고 있고 만드는 데 O(n²)이 걸려서 재지 않았다.

```text
n=1000000 sorted BST h=- | AVL h=20 avg=18.95 rot/ins=1.000 508ms | RB h=37 avg=19.33 rot/ins=1.000 261ms
n=1000000 random BST h=72 | AVL h=24 avg=19.33 rot/ins=0.698 2302ms | RB h=24 avg=19.39 rot/ins=0.582 1972ms
```

정렬된 입력에서 차이가 가장 크다. AVL은 높이 20, 레드-블랙은 37이다. 레드-블랙이 허용하는 기울기만큼 한쪽이 길어졌다. 그런데 평균 깊이는 18.95와 19.33으로 거의 같다. 최악의 경로가 길 뿐 대부분의 키는 비슷한 깊이에 있다. 무작위 입력에서는 둘 다 높이 24이고, 넣기 한 번당 회전은 AVL 0.698번, 레드-블랙 0.582번이었다. 그냥 BST도 무작위 입력이면 높이 72로 버틴다. 위험한 건 정렬된 입력이다.

시간은 레드-블랙이 빨랐지만 이 숫자로 우열을 가리면 안 된다. AVL은 재귀로, 레드-블랙은 부모 포인터를 쓰는 반복문으로 짰다. 무작위 입력이 정렬 입력보다 몇 배 느린 건 트리 연산보다 캐시 미스 때문이다. 정렬된 순서로 넣으면 방금 만든 노드 근처를 계속 건드리고, 무작위면 메모리 이곳저곳을 뛰어다닌다.

정리하면 읽기가 압도적으로 많고 최악 깊이를 줄이고 싶으면 AVL, 넣고 지우기가 섞여 있으면 레드-블랙이다. 레드-블랙은 지울 때 회전이 상수 번이라 쓰기 비용이 더 예측 가능하다. 자바 `TreeMap`과 `TreeSet`, C++ `std::map`과 `std::set`의 주요 구현이 레드-블랙을 쓰는 이유가 이것이다. 범용 라이브러리는 어떤 작업이 많을지 모르니 쓰기가 덜 비싼 쪽을 고른다.

같은 이유로 자바 8부터 `HashMap`은 한 칸에 충돌한 원소가 8개를 넘으면(배열 크기가 64 이상일 때) 그 칸의 연결 리스트를 레드-블랙 트리로 바꾼다. 일부러 충돌을 몰아넣는 [해시 플러딩](/posts/ds-hash-map) 공격에서 그 칸의 찾기가 O(n)이 되는 걸 O(log n)으로 막는다.

## 디스크에서는 높이가 곧 읽기 횟수다: B-트리

메모리에서는 노드 하나 따라가는 데 수십 ns다. 디스크나 SSD에서 페이지 하나를 읽는 데는 수십 µs에서 ms가 걸린다. 그러면 비교 횟수보다 몇 페이지를 읽느냐가 시간을 정한다. B-트리는 2-3-4 트리를 일반화해서 노드 하나를 디스크 페이지 하나 크기로 키운다. 자식 수가 4가 아니라 수백이다.

최소 차수 t인 B-트리는 노드마다 키를 t - 1개부터 2t - 1개까지 담는다(뿌리는 예외). t = 2가 바로 2-3-4 트리다. 같은 코드로 t만 바꿔 키 100만 개를 넣고 높이를 봤다.

```text
t=2 (max 4 children) n=1000000: height 17
t=50 (max 100 children) n=1000000: height 4
t=250 (max 500 children) n=1000000: height 3
```

자식이 4개면 높이 17, 500개면 3이다. 찾기 한 번이 페이지 3장을 읽는 일이 된다. 위쪽 한두 층은 자주 읽히니 메모리 버퍼에 늘 올라가 있고, 실제 디스크 읽기는 잎 한 장뿐인 경우가 많다. 노드 안에서는 키 수백 개를 [이진 탐색](/posts/binary-search)으로 훑는데, 한 페이지가 연속 메모리라 캐시에도 잘 맞는다.

DB 인덱스는 대부분 B+트리라는 변형을 쓴다. 차이는 두 가지다. 값(또는 행 위치)은 잎에만 두고 안쪽 노드에는 길 안내용 키만 둔다. 그러면 안쪽 노드에 키가 더 많이 들어가 자식 수가 늘고 높이가 더 낮아진다. 그리고 잎끼리 옆으로 이어 둔다. `WHERE price BETWEEN 100 AND 200` 같은 범위 질의는 시작 잎 하나만 찾은 뒤 옆 잎으로 쭉 따라가면 된다. 그냥 B-트리라면 중위 순회로 위아래를 오가야 한다. PostgreSQL이 페이지 8KB짜리 B-tree 인덱스를 세 층으로 읽는 모습은 [인덱스 글](/posts/db-index)에서 실제 `EXPLAIN`으로 볼 수 있다. MySQL InnoDB는 테이블 자체가 기본 키 순서의 B+트리다.

B-트리 이전에는 ISAM(색인 순차 접근 방식)이 쓰였다. 데이터를 정렬해 두고 그 위에 고정된 색인을 한 번 만들어 둔다. 찾기는 빠르지만 색인이 정적이라, 새로 들어온 행은 넘침 페이지에 사슬처럼 붙는다. 넣기가 쌓일수록 사슬이 길어져 느려지고 주기적으로 다시 만들어야 했다. 넣을 때마다 쪼개고 합치며 스스로 균형을 지키는 B-트리가 이 문제를 풀었다. MySQL의 옛 저장 엔진 MyISAM의 이름에 그 흔적이 남아 있다.

## 동전 던지기로 균형 잡기: 스킵 리스트

지금까지는 모두 규칙을 지키려고 회전하거나 쪼갰다. 스킵 리스트는 규칙 대신 확률을 쓴다. 정렬된 연결 리스트 위에 듬성듬성한 지름길 층을 얹는다. 새 노드를 넣을 때 동전을 던져 앞면이 나오는 동안 층을 하나씩 올린다. 확률 p로 한 층씩 올라가면 위층으로 갈수록 노드가 p배로 줄어 층 수가 평균 log₁/ₚ n이 된다. 찾을 때는 맨 위층에서 오른쪽으로 가다가 넘칠 것 같으면 한 층 내려간다. 순위를 세는 방법까지는 [순위표 글](/posts/sd-leaderboard-sorted-set)에서 그림으로 따라갔다.

```js
function randomLevel(p = 0.25, max = 32) {
  let level = 1;
  while (Math.random() < p && level < max) level++; // 앞면이 나오는 동안 한 층씩
  return level;
}

function search(list, key) {
  let x = list.head;
  for (let i = list.level - 1; i >= 0; i--) {        // 맨 위층부터
    while (x.next[i] && x.next[i].key < key) x = x.next[i]; // 넘치기 전까지 오른쪽으로
  }                                                  // 넘칠 것 같으면 한 층 내려간다
  x = x.next[0];
  return x && x.key === key ? x : null;
}
```

넣기는 같은 길을 내려가며 층마다 "마지막으로 멈춘 노드"를 적어 두고, 새 노드의 층 수만큼 그 노드들 뒤에 끼워 넣는다. 회전도 쪼개기도 없다.

키 100만 개를 p = 1/2와 1/4로 넣고, 무작위 키 10만 개를 찾으며 지나는 걸음 수를 쟀다.

```text
p=0.5 n=1000000: levels=19 pointers/node=2.00 steps/search=38.5
p=0.25 n=1000000: levels=10 pointers/node=1.33 steps/search=35.9
```

p = 1/2면 노드당 포인터가 평균 2개, 1/4이면 1.33개다. 걸음 수는 오히려 1/4 쪽이 조금 적었다. 층마다 오른쪽으로 가는 걸음은 늘지만 층 수가 절반이라서다. Redis의 정렬된 셋이 p = 1/4를 쓰는 이유가 메모리다. 찾기 비용은 비슷하고 포인터는 3분의 2로 준다.

처음엔 층을 정하는 난수로 직접 만든 단순한 선형 합동 생성기를 썼다. 연속해서 뽑는 값끼리 상관이 있는 생성기다. 결과가 이랬다.

```text
p=0.5 n=1000000: levels=13 pointers/node=2.05 steps/search=124.1
p=0.25 n=1000000: levels=9 pointers/node=1.35 steps/search=95.3
```

평균 포인터 수는 멀쩡해 보이는데 층이 13개에서 멈췄고 찾기 걸음이 세 배로 늘었다. 높은 층이 나와야 할 만큼 앞면이 연달아 나오지 않은 것이다. 스킵 리스트의 균형은 난수의 질에 기대고 있다. 난수가 나쁘거나 공격자가 층 배정을 예측할 수 있으면 리스트로 무너질 수 있다. 회전형 트리에는 없는 위험이다.

그런데도 쓰는 이유가 있다. 회전이 없어서 구현이 짧고, 한 번에 바뀌는 포인터가 노드 근처 몇 개뿐이라 여러 스레드가 동시에 고치기 쉽다. 자바의 `ConcurrentSkipListMap`이 잠금 없는 동시성 정렬 맵으로 스킵 리스트를 쓰고, LevelDB와 RocksDB는 메모리에 쓰기를 모아 두는 memtable을 스킵 리스트로 만든다. 범위 질의도 맨 아래층을 따라가면 되니 B+트리 잎처럼 자연스럽다.

## 현장에서 균형 트리를 고르는 순간

애플리케이션 코드에서 균형 트리를 직접 짤 일은 드물다. 고르는 일이 더 많다. 자바스크립트에는 정렬된 맵이 내장되어 있지 않아서, 범위 질의나 "이 값 다음으로 큰 키"가 필요하면 정렬 배열과 이진 탐색으로 버틸지, 라이브러리를 들일지 정해야 한다. 키가 한 번에 다 주어지고 잘 안 바뀌면 정렬 배열이 가장 빠르고 작다. 넣기와 지우기가 계속 섞이면 배열은 넣을 때마다 O(n)을 밀어야 하니 트리 쪽으로 간다.

DB에서는 B+트리의 성질이 설계 판단으로 나온다. 무작위 UUID를 기본 키로 쓰면 새 행이 잎 곳곳에 흩어져 들어가서 페이지 쪼개기가 잦고 페이지가 반쯤 빈 채로 남는다. 시간 순서로 커지는 키는 늘 오른쪽 끝 잎에만 넣으니 쪼개기가 적다. 앞의 AVL 실험에서 정렬된 입력이 캐시에 유리했던 것과 같은 이야기다. 시간 정렬이 되는 UUIDv7이나 ULID를 쓰는 이유가 여기서 나온다. 범위 질의가 많은 컬럼에 해시 인덱스를 걸면 잎이 이어져 있지 않아 범위를 못 쓴다.

메모리 문제도 있다. 트리 노드는 키 하나에 포인터 둘, 높이나 색, 객체 헤더까지 붙는다. 키 100만 개를 담은 레드-블랙 트리는 같은 키를 담은 정렬 배열보다 몇 배 크다. 노드를 넓게 만든 B-트리를 메모리 안에서 쓰는 이유도 이것이다. 노드 하나에 키를 여러 개 넣으면 포인터가 줄고 캐시 줄 하나에 여러 키가 들어간다. Rust의 `BTreeMap`이 이 이유로 레드-블랙 대신 B-트리를 쓴다.

마지막은 재귀 깊이다. 균형 트리는 높이가 log n이라 재귀로 짜도 안전하다. 그냥 BST를 재귀로 짰다가 정렬된 입력에서 콜 스택이 터진 사고가 [이진 탐색 트리 글](/posts/ds-binary-tree-bst)의 출발점이었다. 균형만 지키면 같은 코드가 100만 개에서도 깊이 20대에서 끝난다.

## 노드에 숫자를 하나 더 얹으면

균형 트리는 노드에 정보를 하나 더 얹어 쓰기 좋다. 노드마다 자기 아래 키의 개수 `size`를 들고 있으면, "k번째로 작은 키"와 "이 키는 몇 번째인가"를 O(log n)에 답한다. 이런 트리를 순서 통계 트리(order statistic tree)라고 부른다.

```js
function kth(node, k) {                     // 0부터 센 k번째 키
  while (node) {
    const leftSize = node.left ? node.left.size : 0;
    if (k < leftSize) node = node.left;     // 왼쪽 안에 있다
    else if (k === leftSize) return node.key;
    else { k -= leftSize + 1; node = node.right; } // 왼쪽과 자기 자신을 건너뛴다
  }
  return undefined;
}
```

대가는 넣기와 지우기, 그리고 회전 때마다 `size`를 고쳐야 한다는 것이다. 회전은 두 노드의 자식만 바꾸니 그 두 노드의 `size`만 아래쪽부터 다시 계산하면 된다. 높이를 고치는 자리에 한 줄을 더하는 셈이다. 구간 트리(interval tree)도 같은 방식으로 노드마다 "아래 구간 끝점의 최댓값"을 얹는다. 값이 자주 바뀌는 배열에서 구간 합을 묻는 문제는 트리 모양이 고정된 [세그먼트 트리와 펜윅 트리](/posts/segment-tree-fenwick)가 더 단순하다.

## 면접에서 나올 만한 질문

### 균형 탐색 트리가 왜 필요한가요?

그냥 이진 탐색 트리는 정렬된 순서로 키가 들어오면 한 줄로 기울어 찾기, 넣기, 지우기가 모두 O(n)이 된다. 자동 증가 id나 시각처럼 정렬된 채 들어오는 데이터가 흔하다. 균형 트리는 넣고 지울 때마다 모양을 고쳐 높이를 O(log n)으로 묶는다. 키 100만 개를 정렬된 순서로 넣어도 AVL은 높이 20이었다.

### 회전은 어떻게 동작하고 왜 정렬 순서가 깨지지 않나요?

부모와 자식의 위아래를 바꾸고, 둘 사이에 있던 부분 트리를 내려가는 쪽으로 넘기는 연산이다. 포인터 세 개만 바뀌어 O(1)이다. 넘어가는 부분 트리의 키는 원래부터 두 노드 사이 값이라 회전 뒤에도 중위 순서가 같다. 회전한 뒤 부모 포인터를 새 뿌리로 이어 주는 걸 빠뜨리는 실수가 흔하다.

### AVL과 레드-블랙 트리의 차이는요?

AVL은 모든 노드의 좌우 높이 차를 1 이하로 지켜 높이가 약 1.44 log n 이하이고, 레드-블랙은 색 규칙으로 느슨하게 지켜 2 log n 이하다. 그래서 찾기는 AVL이 조금 유리하고, 쓰기는 레드-블랙이 회전이 적다. 레드-블랙은 넣을 때 회전 2번, 지울 때 3번 이하인데 AVL은 지울 때 O(log n)번까지 돈다. 실험에서 정렬 입력 높이는 20과 37이었지만 평균 깊이는 18.95와 19.33으로 거의 같았다.

### 자바 TreeMap이나 C++ map은 왜 레드-블랙 트리를 쓰나요?

범용 라이브러리는 읽기와 쓰기 중 무엇이 많을지 모르니 쓰기 비용이 덜 비싸고 예측 가능한 쪽을 고른다. 레드-블랙은 넣기와 지우기의 회전이 상수 번이고 색 바꾸기도 평균 상수 번이다. 찾기 깊이는 AVL과 평균적으로 거의 차이가 없다. 자바 `HashMap`도 한 칸에 충돌이 몰리면 그 칸을 레드-블랙 트리로 바꾼다.

### 레드-블랙 트리와 2-3-4 트리는 어떤 관계인가요?

같은 구조의 다른 표현이다. 2-3-4 트리의 3-노드와 4-노드를 검은 노드 하나와 빨간 자식으로 펼치면 레드-블랙이 된다. "빨강이 두 번 이어지면 안 된다"는 키 4개짜리 노드가 없다는 뜻이고, "모든 길의 검은 노드 수가 같다"는 모든 잎의 깊이가 같다는 뜻이다. 넣을 때 색 바꾸기가 4-노드 쪼개기에 해당한다.

### DB 인덱스는 왜 레드-블랙이 아니라 B+트리를 쓰나요?

디스크에서는 비교 횟수보다 페이지를 몇 장 읽느냐가 시간을 정하기 때문이다. B+트리는 노드 하나를 페이지 크기로 키워 자식이 수백 개라, 키 100만 개도 높이 3이면 된다. 이진 트리면 20층이 넘는다. 값은 잎에만 두어 안쪽 노드의 자식 수를 더 늘리고, 잎끼리 이어 두어 범위 질의를 옆으로 따라가며 처리한다.

### Redis 정렬된 셋은 왜 균형 트리 대신 스킵 리스트를 쓰나요?

구현이 단순하고, 범위 조회가 맨 아래층을 따라가면 되며, 지름길마다 건너뛴 칸 수를 적어 두면 순위 계산도 쉽기 때문이다. 찾기는 평균 O(log n)으로 균형 트리와 같다. 대신 균형이 확률에 기대서 최악은 보장하지 않고 난수의 질에 민감하다. 실험에서 질 나쁜 난수를 쓰자 찾기 걸음이 세 배로 늘었다. Redis는 p = 1/4로 노드당 포인터를 1.33개로 줄인다.

### 정렬된 맵에서 k번째 원소나 순위를 빨리 구하려면요?

노드마다 자기 아래 키 개수를 얹은 순서 통계 트리를 쓴다. 왼쪽 부분 트리 크기와 k를 비교하며 내려가면 O(log n)에 k번째 키를 찾고, 내려오며 건너뛴 크기를 더하면 순위가 된다. 넣기, 지우기, 회전 때 그 개수를 함께 고쳐야 한다. Redis 스킵 리스트가 지름길마다 건너뛴 칸 수를 적어 두는 것도 같은 생각이다.

### 메모리 안에서도 B-트리를 쓰는 경우가 있나요?

있다. 노드 하나에 키를 여러 개 넣으면 노드당 포인터와 객체 헤더가 줄고, 한 노드의 키들이 연속 메모리라 캐시 줄 하나에 여러 키가 들어간다. 그래서 키를 따라갈 때 캐시 미스가 줄어든다. Rust 표준 라이브러리의 `BTreeMap`이 이 이유로 레드-블랙 대신 B-트리를 쓴다.
