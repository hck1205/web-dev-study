고객센터에서 문의가 넘어왔다. "u_7731 고객, TV 한 대를 주문했는데 129만 원이 두 번 결제됐다." 주문 화면에는 주문이 하나뿐이고, 결제 완료로 떠 있다. 에러 알림은 울린 적이 없다.

가진 것은 사용자 ID, 대략의 시각, 증상 한 줄이다. 그리고 세 서비스(web, orders, payments)가 그 시간대에 남긴 로그 2,216줄이 있다. 그중 info가 2,215줄, warn이 1줄이다. 이 글은 이 로그에서 버그를 찾아 재현하고 고치기까지의 과정을 실제 출력으로 따라간다.

이 주제의 다른 글: 로그 한 줄에 무엇을 어떤 형식으로 남길지는 [구조화 로그](/posts/structured-logging), 로그를 한곳에 모으고 OpenSearch·Loki로 묻는 길은 [중앙 로그 파이프라인](/posts/centralized-logging-pipeline), 요청이 서비스를 건널 때 `traceparent`가 어떻게 전해지는지는 [분산 추적](/posts/distributed-tracing)에 있다. 브라우저 쪽 에러를 모으는 법은 [프런트엔드 에러 추적](/posts/frontend-error-tracking), 증상별로 어느 도구를 여는지는 [로그 도구 지도](/posts/logging-tools-overview)에서 다룬다. 이 글은 이미 남은 로그로 버그를 추적하는 기술에 집중한다.

실습은 Node.js 22로 만든 서비스 셋이다. 브라우저(Chromium 141)가 web의 `/api/checkout`을 부르고, web이 orders를, orders가 payments를 부른다. 모든 서비스가 JSON 한 줄 로그를 파일에 쓰고, 그동안 다른 사용자 200명의 평범한 주문이 함께 흘렀다. payments 안의 가짜 카드사에는 버그가 드러날 조건을 일부러 심어 두었다. 무엇을 심었는지는 로그로 찾아가며 밝힌다. 로그는 jq 1.7로 읽었다.

## 증상이 기록된 쪽에서 시작한다

첫 질문은 "어디부터 보나"다. 증상이 실제로 일어난 자리부터 본다. "두 번 결제됐다"는 payments가 승인한 기록이 두 개라는 뜻이니, payments 로그에서 그 사용자의 승인 줄을 찾는다.

```bash
# payments 로그에서 u_7731의 결제 승인 줄만
jq -c 'select(.user=="u_7731" and .msg=="charge captured")' payments.log
```

```text

{"time":"2026-10-21T23:51:56.081Z","level":"info","service":"payments","trace_id":"1a85d4bfa46aa90816bc3b3645e9da59","span_id":"1f0798fea4ff2339","msg":"charge captured","order_id":"o_430222","charge_id":"ch_88b769","amount":1290000,"user":"u_7731"}
```

## 사용자 ID로는 절반만 보인다

이제 이 요청에서 일어난 일을 다 모아야 한다. 먼저 떠오르는 건 사용자 ID로 grep하는 것이다.

```bash
grep -h 'u_7731' web.log orders.log payments.log | jq -c '{time:.time[11:23],service,msg}'
```

```text
{"time":"23:51:54.776","service":"web","msg":"checkout requested"}
{"time":"23:51:55.831","service":"web","msg":"checkout done"}
{"time":"23:51:54.778","service":"orders","msg":"order created"}
{"time":"23:51:55.828","service":"payments","msg":"charge captured"}
{"time":"23:51:56.081","service":"payments","msg":"charge captured"}
```

다섯 줄이다. 2,216줄 중 유일한 warn, 즉 이 사건의 핵심 단서는 빠져 있다. 그 줄에는 사용자 ID가 없기 때문이다. 업무 필드(사용자, 주문 번호)는 로그를 쓴 사람이 그 자리에서 알던 값만 들어간다. 반면 `trace_id`는 로거가 모든 줄에 자동으로 붙인다. 그래서 찾는 방법은 "업무 값으로 첫 줄을 찾고, 그 줄의 `trace_id`로 갈아타서 넓힌다"이다.

`trace_id`는 요청 하나를, `order_id`는 비동기 작업까지 포함한 업무 하나를 묶는다. 결제 대행사나 카드사에 확인할 때는 그쪽이 아는 `charge_id`로 바꿔 묻는다. 어느 키로든 다른 키에 닿을 수 있게, 상태가 바뀌는 줄에는 둘 이상의 키를 함께 남긴다.

이 요청의 `trace_id`는 브라우저에서 시작됐다. 실습 페이지는 버튼을 누를 때 trace ID를 만들어 `traceparent` 헤더로 보냈다.

```text
[browser] click trace_id=1a85d4bfa46aa90816bc3b3645e9da59
[request] POST http://127.0.0.1:18810/api/checkout traceparent=00-1a85d4bfa46aa90816bc3b3645e9da59-2788372ba6e02203-01
[browser] response 200 {"order_id":"o_430222","status":"paid"}
```

web은 이 헤더를 이어받았다. web의 마지막 줄에 `parent_span: 2788372ba6e02203`이 찍힌 걸 뒤에서 볼 수 있다. 브라우저의 에러 이벤트나 브레드크럼에 이 ID를 남기면, 프런트엔드 에러 화면에서 서버 로그로 바로 건너간다. 다만 인터넷에서 들어온 헤더를 그대로 믿으면 남이 정한 ID나 샘플링 플래그가 섞이니, 첫 관문에서 걸러야 한다. 그 이야기는 분산 추적 글의 "헤더가 한 번 끊기면" 절에 있다.

## 세 서비스의 줄을 시각순으로 세운다

이제 `trace_id` 하나로 세 파일에서 줄을 모아 시각순으로 세운다. 실습에서 쓴 스크립트다.

```bash
# timeline.sh <trace_id>: 같은 trace_id 줄만 골라 시각순으로, 한 줄에 한 사건
cat web.log orders.log payments.log | jq -c --arg t "$1" 'select(.trace_id==$t)' | jq -s -r 'sort_by(.time)[]
  | "\(.time[11:23]) \((.service+"        ")[0:8]) \((.level+"     ")[0:5]) \(.msg) \(del(.time,.service,.level,.msg,.trace_id,.span_id)|tostring)"'
```

## 시계가 틀린 서버의 줄은 순서를 속인다

방금 타임라인은 세 서비스가 한 컴퓨터에서 돌아 시계가 같았다. 실제로는 서버마다 시계가 조금씩 다르다. payments의 시계를 400ms 늦게 돌려 같은 실험을 다시 했다.

```bash
# payments만 시계를 400ms 늦게 (CLOCK_OFFSET_MS=-400) 돌려 같은 시나리오를 다시
PAY_OFFSET=-400 bash start.sh; node load.mjs 200 & node browser.mjs
```

그래서 호출을 보낼 때 남기는 줄에 `client_span`(보낸 span ID)을, 받을 때 남기는 줄에 `parent_span`을 넣어 두는 게 좋다. 분산 추적을 쓰고 있다면 trace 화면이 이 짝 맞추기를 대신해 준다. 그래도 trace는 샘플링으로 버려졌을 수 있으니 로그에도 남긴다. 시계 자체를 맞추는 일(NTP, chrony)과 시계가 틀렸을 때 생기는 다른 문제는 [시계 차이](/posts/clock-skew) 글에 있다. 같은 서비스 안의 순서는 그 서버의 시계로 믿어도 된다. 의심할 것은 서비스를 건너는 순서다.

이 짝 맞추기를 직접 짜 보자. 로그 줄 배열을 받아 orders의 호출 시도마다 클라이언트가 본 결과와 서버가 실제로 처리한 시간을 이어 붙인다. 서버 쪽 줄이 없으면 `server_ms`는 `null`이다. 첫 테스트는 위의 시계 틀린 실습 값이다.

## 경계마다 남길 것

경계마다 남길 것을 정리하면 이렇다. 요청을 받을 때는 끝나는 시점에 한 줄(경로 틀, 상태, 걸린 시간, 받은 부모 span). 남을 부를 때는 결과가 나온 시점에 한 줄(대상, 시도 번호, 타임아웃, 보낸 span, 결과와 걸린 시간). 판단을 내린 곳에는 그 판단을(재시도한다, 캐시로 대신한다, 중복이라 건너뛴다). 상태가 바뀐 곳에는 바뀐 대상의 ID를 둘 이상(주문 생성, 결제 승인).

실습 코드에는 하나 아쉬운 점이 있었다. 재시도한다는 판단(`retrying charge`)을 debug로 남겨서 운영 로그에 안 보였다. 위의 warn 줄이 사실상 그 역할을 했지만, 돈이 오가는 호출을 다시 보낸다는 판단은 info 이상이어야 한다. 레벨을 정하는 일반 기준은 [구조화 로그](/posts/structured-logging)에 있다.

## 재배포 없이 한 사람만 debug로

경계 로그로 대부분은 찾지만, 가끔은 "그 안에서 무슨 값이 오갔나"까지 봐야 한다. 그렇다고 운영 전체에 debug를 켜면 로그가 몇 배로 늘고 다른 사람들의 값까지 쌓인다. 그래서 요청 단위로 켠다.

실습 서비스는 요청이 들어올 때 사용자 ID가 debug 대상 목록에 있는지 보고, 그 결과를 `AsyncLocalStorage`에 넣어 그 요청의 모든 로그 호출이 읽게 했다. 목록은 파일인데 요청마다 다시 읽으니 재배포 없이 바뀐다. 실제로는 이 자리를 [기능 플래그](/posts/feature-flags) 서비스가 맡는다.

```js
import { AsyncLocalStorage } from "node:async_hooks";
export const als = new AsyncLocalStorage();

export function log(level, msg, fields = {}) {
  const ctx = als.getStore() || {};
  const min = ctx.debug ? LEVELS.debug : BASE;   // 이 요청만 debug까지
  if (LEVELS[level] < min) return;
  out.write(JSON.stringify({ time: new Date().toISOString(), level, service: SERVICE,
    trace_id: ctx.traceId, span_id: ctx.spanId, msg, ...fields }) + "\n");
}

// 요청이 들어올 때
const ctx = contextFrom(req);           // traceparent를 이어받는다
ctx.debug = debugFor(body.user);        // 플래그: 이 사용자만 debug
als.run(ctx, () => handle(req, res, body));
```

`debug-users.json`에 `["u_7731"]`를 넣고 같은 시나리오를 다시 돌렸다. 타임라인에 debug 줄이 끼어든다(debug 줄만 골랐다).

## 같은 일이 또 있었나

버그 하나를 찾으면 다음 질문은 "몇 건이나 당했나"다. 같은 주문에 승인이 두 번 이상인 것을 전부 센다.

```bash
# 같은 order_id에 charge captured가 2개 이상인 주문
jq -s -c '[.[] | select(.msg=="charge captured")] | group_by(.order_id)
  | map(select(length>1) | {order_id: .[0].order_id, user: .[0].user, charges: map(.charge_id), amount: .[0].amount})' payments.log
# payments의 처리 시간 분포
jq -s 'map(select(.msg=="request finished" and .path=="/charge") | .duration_ms) | sort
  | {n: length, p50: .[length/2|floor], p99: .[(length*0.99)|floor], max: .[-1]}' payments.log
```

```text
[{"order_id":"o_430222","user":"u_7731","charges":["ch_6fc395","ch_88b769"],"amount":1290000}]
{
  "n": 202,
  "p50": 56.2,
  "p99": 75,
  "max": 1300.5
}
```

이 구간에서는 한 건이다. p99는 75ms라 평균이나 p99만 보는 대시보드에서는 이상이 안 보인다. 최댓값 하나가 1300.5ms다. "평소엔 빠른데 가끔 아주 느린" 호출과 짧은 타임아웃, 그리고 재시도가 겹칠 때만 터지는 버그라서 알림이 울리지 않았다.

로그 저장소에서도 같은 질문을 던진다. Loki라면 이런 모양이다(예시, 이 실습은 파일로 했다).

```text
sum by (order_id) (count_over_time({app="payments"} |= "charge captured" | json [24h])) > 1
```

OpenSearch라면 `msg`로 거른 뒤 `order_id`로 terms 집계를 하고 `min_doc_count: 2`를 준다. 레이블과 색인 설계에 따라 어느 쪽이 싼지 갈리는데, 그 이야기와 실제로 돌린 쿼리는 중앙 로그 파이프라인 글에 있다. 질문 순서는 같다. 범위(서비스, 시간)를 먼저 좁히고, 메시지로 거르고, 업무 키로 묶어 센다.

## 로그로 찾은 조건을 재현으로 옮긴다

로그에서 찾은 건 아직 가설이다. "고액 결제의 첫 승인이 1초를 넘으면, orders가 같은 결제를 다시 보내 두 번 승인된다." 이 조건을 그대로 만들어서 버그가 나는지 본다. 실습에 심어 둔 조건이 바로 이것이다. 가짜 카드사는 100만 원 이상 결제의 첫 승인에만 1300ms가 걸린다. 이 조건으로 몇 번을 돌려도 매번 두 번 결제됐고, 같은 시간대의 32만 원 이하 주문 200건은 한 번도 겹치지 않았다. 재현이 되면 고친 뒤에 같은 방법으로 "이제는 안 난다"를 확인할 수 있다. 재현 없이 고치면 고쳐졌는지 알 길이 없다.

고칠 방법은 여러 가지가 떠오른다. orders의 타임아웃을 늘리는 건 이번 숫자에만 맞춘 땜질이다. 카드사가 2초 걸리는 날 또 터진다. 재시도를 없애면 일시적인 네트워크 오류마다 결제가 실패한다. 근본적인 방법은 같은 결제 요청을 몇 번 받아도 한 번만 승인하게 만드는 것, 즉 멱등성이다. orders가 주문 ID를 멱등 키로 보내고, payments는 같은 키의 결제가 진행 중이면 새로 승인하지 않고 그 결과를 기다려 돌려준다. 멱등 키를 어디에 저장하고 얼마나 두는지는 [멱등 키](/posts/idempotency-key) 글에 있다.

## 추적을 막는 로그 습관

이번 추적이 쉬웠던 이유를 거꾸로 하면 추적을 막는 습관이 된다.

시각에 시간대가 없거나 서버마다 다르다. 세 파일을 합쳐 정렬하는 순간 순서가 틀린다. 모든 서비스가 UTC에 `Z`를 붙여 쓴다.

같은 값을 서비스마다 다른 이름으로 쓴다. `order_id`, `orderId`, `oid`가 섞이면 jq 한 줄이 세 줄이 된다.

요청을 잇는 ID가 일부 줄에만 있다. 로거가 자동으로 붙이지 않고 개발자가 손으로 넣으면 꼭 빠지는 줄이 생긴다. 하필 그 줄이 이번의 warn 같은 줄이다. 비동기 작업(큐, 배치)으로 넘어갈 때도 ID를 메시지에 실어 넘긴다.

실패할 때만 로그를 남긴다. 성공한 호출의 줄이 없으면 "두 번째 시도는 성공했다"를 알 수 없고, 실패 줄 하나만으로는 앞뒤를 못 맞춘다. 경계의 결과 줄은 성공이든 실패든 남긴다.

에러를 삼킨다. `catch {}`로 아무것도 안 남기고 넘어가면, 그 뒤의 이상한 상태가 어디서 왔는지 영영 모른다. 처리하고 넘어가더라도 warn 한 줄은 남긴다.

반복문 안에서 줄을 찍는다. 장바구니 상품 100개면 줄 100개다. 정작 필요한 줄이 그 사이에 묻힌다. 반복이 끝난 뒤 개수와 요약을 한 줄로 남긴다.

요청 본문, 토큰, 카드 번호를 그대로 남긴다. debug를 켤 때 가장 흔히 새는 길이다. 가리기 규칙은 debug 줄에도 똑같이 적용한다.

## 열다섯 줄로 돌아가서

2,216줄에서 출발해, 증상이 기록된 payments에서 첫 줄을 찾고, `trace_id`로 갈아타 세 서비스의 열다섯 줄을 세웠다. 시계가 틀린 경우에는 시각 대신 span ID로 순서를 맞췄고, 한 사람만 debug를 켜서 숨은 값을 봤고, 같은 조건으로 재현한 뒤 고친 것을 확인했다. 로그로 버그를 쫓는 일은 대부분 이 반복이다. 가진 값으로 첫 줄을 찾고, 더 넓게 묶는 키로 갈아타고, 짝이 안 맞는 곳을 찾는다.

## 면접에서 나올 만한 질문

### 사용자가 "결제가 두 번 됐다"고 합니다. 로그에서 어떻게 원인을 찾나요?

증상이 기록된 서비스(결제)에서 그 사용자의 승인 줄부터 찾는다. 두 줄의 trace_id가 같으면 요청 하나 안에서 두 번 승인된 것이고, 다르면 사용자가 두 번 요청한 것이다. 그다음 trace_id로 모든 서비스의 줄을 모아 시각순으로 세우고, 요청과 응답의 짝이 안 맞는 곳을 찾는다. 실습에서는 첫 시도의 타임아웃 뒤 재시도가 있었고, 첫 요청이 늦게 승인되면서 두 번 결제됐다.

### 사용자 ID로 검색하면 되지 왜 trace_id가 필요한가요?

업무 필드는 그 코드를 쓴 사람이 그 자리에서 알던 값만 들어가서 빠지는 줄이 많다. 실습에서 사용자 ID로 찾은 줄은 다섯 개였고, 유일한 warn 줄이 빠졌다. trace_id는 로거가 모든 줄에 자동으로 붙이고 서비스를 건너 전파되니 요청 하나의 줄을 빠짐없이 묶는다. 그래서 업무 값으로 첫 줄을 찾고 trace_id로 갈아타서 넓힌다.

### 여러 서버의 로그를 시각순으로 합쳤더니 순서가 이상합니다. 왜 그렇고 어떻게 하나요?

서버마다 시계가 조금씩 달라서다. 실습에서 한 서비스의 시계를 400ms 늦추자 결제 요청이 주문 요청보다 먼저 온 것처럼 보였다. 서비스를 건너는 순서는 시각이 아니라 인과로 맞춘다. 부르는 쪽이 보낸 span ID와 받는 쪽의 부모 span ID를 짝지으면 시계와 상관없이 어느 시도가 어느 처리였는지 나온다. 같은 서비스 안의 순서는 그 서버 시계로 믿어도 된다.

### 호출한 쪽이 타임아웃으로 포기했는데 왜 상대 쪽 작업이 실행되나요?

타임아웃은 "나는 더 안 기다린다"는 뜻이지 상대의 작업을 취소하지 않는다. 받는 쪽은 연결이 끊긴 줄 모르고 끝까지 처리하고 성공으로 기록하기도 한다. 그래서 타임아웃이 난 호출은 "실패"가 아니라 "결과를 모름"으로 다뤄야 하고, 그 상태에서 다시 보내려면 받는 쪽이 멱등해야 한다. 서버 쪽 로그가 아예 없으면 요청이 닿지 않은 것이라 재시도가 안전하다.

### 서비스 경계에서는 무엇을 로그로 남기나요?

요청을 받으면 끝날 때 경로 틀, 상태, 걸린 시간, 받은 부모 span을 한 줄로 남긴다. 남을 부르면 대상, 시도 번호, 타임아웃, 보낸 span ID, 결과와 걸린 시간을 남긴다. 재시도나 중복 제거 같은 판단과, 주문 생성·결제 승인 같은 상태 변화도 남기고, 상태 변화 줄에는 ID를 둘 이상 넣어 다른 키로 갈아탈 수 있게 한다. 성공한 호출도 남겨야 앞뒤 짝을 맞출 수 있다.

### 운영에서 특정 사용자만 debug 로그를 켜려면 어떻게 하나요?

요청이 들어올 때 기능 플래그로 대상인지 판단하고, 그 결과를 요청 문맥(Node.js라면 AsyncLocalStorage)에 넣어 로거가 요청마다 레벨을 정하게 한다. 실습에서는 한 사용자만 켜서 200건 중 그 요청에만 debug 줄 6개가 붙었다. 플래그에는 끝나는 시각을 달고, debug 줄에도 가리기를 적용하고, 헤더로 켜게 한다면 내부 인증된 요청에만 허용한다.

### 로그로 원인을 찾은 뒤 바로 고치면 안 되나요?

로그에서 찾은 건 가설이라 그 조건으로 재현부터 한다. 재현이 돼야 가설이 맞는지 알고, 고친 뒤 같은 방법으로 안 난다는 걸 확인할 수 있다. 고칠 때는 이번 숫자에만 맞추는 땜질(타임아웃 늘리기)보다 조건 자체를 없애는 방법(멱등 키)을 고른다. 고친 코드에도 판단 줄을 남겨 다음 사람이 로그만 보고 이해하게 한다.
