"지난달에 성능 좋았던 이탈 예측 모델 있잖아요. 그걸로 다시 만들어 주세요." 이 요청을 받고 노트북 폴더를 열어 본다. `model_final.pkl`, `model_final2.pkl`, `model_real_final.pkl`이 있다. 어느 게 지난달 그 모델인지 모른다. 하이퍼파라미터는 노트북 셀을 몇 번 고쳐 돌린 뒤라 남아 있지 않다. 학습 데이터는 "그때 DB에서 뽑은 CSV"였는데, 그 테이블은 이미 매일 갱신돼서 같은 쿼리를 돌려도 다른 데이터가 나온다. 코드는 Git에 있지만 어느 커밋으로 돌렸는지 모른다.

모델 하나는 코드, 데이터, 설정, 환경(라이브러리 버전), 무작위성이 함께 만든 결과물이다. 코드만 버전 관리해서는 다시 만들 수 없다. 이 글은 다섯 가지를 함께 남기는 방법을 다룬다. MLflow로 실행마다 파라미터·지표·모델 파일을 기록하고, DVC로 큰 데이터셋을 Git 밖에 두면서 커밋과 묶고, 모델 레지스트리로 "지금 운영에 나간 모델"을 이름 붙여 관리한다. 재현성이 어디서 깨지는지도 직접 확인한다.

실습은 Python 3.13, scikit-learn 1.9.1, MLflow 3.17.2, DVC 3.67.1로 했다. 데이터는 `make_classification`으로 만든 4천 건이다. 모델을 평가하는 지표는 [모델 평가 글](/posts/ml-model-evaluation)에서 다뤘다.

## 같은 코드, 같은 데이터인데 숫자가 다르다

먼저 무엇이 재현성을 깨는지 보자. 랜덤 포레스트를 학습시키고 시험 세트의 AUC를 세 번 쟀다. 코드와 데이터는 똑같다.

```python
from sklearn.datasets import make_classification
from sklearn.model_selection import train_test_split
from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import roc_auc_score
import numpy as np

X, y = make_classification(n_samples=4000, n_features=20, n_informative=6, random_state=7)

def run(X, y, split_seed, model_seed):
    Xtr, Xte, ytr, yte = train_test_split(X, y, test_size=0.25, random_state=split_seed)
    m = RandomForestClassifier(n_estimators=100, random_state=model_seed).fit(Xtr, ytr)
    return round(roc_auc_score(yte, m.predict_proba(Xte)[:, 1]), 4)

print("seed 없음:", [run(X, y, None, None) for _ in range(3)])
print("seed 고정:", [run(X, y, 42, 42) for _ in range(3)])
perm = np.random.default_rng(1).permutation(len(y))
print("행 순서만 바뀜:", run(X[perm], y[perm], 42, 42))
```

```text
seed 없음: [0.9687, 0.9714, 0.9733]
seed 고정: [0.9673, 0.9673, 0.9673]
행 순서만 바뀜: 0.9646
```

시드를 안 주면 돌릴 때마다 0.9687, 0.9714, 0.9733이 나온다. 이 차이만으로도 "이번 실험이 0.003 좋아졌다"는 결론이 의미 없어진다. 시드를 고정하면 매번 0.9673이다.

마지막 줄이 더 무섭다. 시드를 고정했는데 데이터의 행 순서만 바뀌어도 0.9646이 나온다. `train_test_split`은 같은 시드면 같은 위치의 행을 고르는데, 행 순서가 바뀌면 그 위치에 다른 행이 있기 때문이다. `ORDER BY` 없는 SQL로 데이터를 뽑으면 DB가 돌려주는 순서는 보장되지 않는다. 같은 테이블, 같은 쿼리, 같은 시드인데 다른 모델이 나올 수 있다.

재현성을 깨는 것들을 모아 보면 이렇다.

- 무작위성: 분할, 가중치 초기값, 배치 섞기, 드롭아웃. 시드를 고정하고 기록한다. GPU 연산은 시드를 고정해도 연산 순서 때문에 미세하게 달라질 수 있어서, PyTorch에서는 결정적 알고리즘 설정(`torch.use_deterministic_algorithms`)을 따로 켜야 하고 그만큼 느려질 수 있다.
- 데이터: 갱신되는 테이블, 순서가 보장되지 않는 쿼리, 손으로 고친 CSV. 학습에 쓴 데이터의 스냅숏과 해시를 남긴다.
- 라이브러리 버전: 기본값이 바뀐다. scikit-learn 0.22에서는 `LogisticRegression`의 기본 solver가 `liblinear`에서 `lbfgs`로 바뀌었다. 코드를 한 줄도 안 바꿨는데 버전을 올리면 다른 모델이 나온다. 정확한 버전을 기록한다.
- 설정: 하이퍼파라미터, 특징 목록, 문턱값. 노트북 셀에서 고치고 돌린 값은 남지 않는다.
- 코드: 커밋하지 않은 수정. 실행할 때의 커밋 해시와 작업 트리가 깨끗했는지 남긴다.

## 실행마다 무엇을 남기나: MLflow 기록

이걸 매번 엑셀에 적을 수는 없다. 실험 추적(experiment tracking) 도구는 학습 코드에서 몇 줄로 이것들을 기록하게 해 준다. 많이 쓰는 건 MLflow(오픈소스, 직접 띄우거나 Databricks 같은 관리형으로), Weights & Biases(관리형 SaaS, 딥러닝 학습 곡선 시각화가 강점), Neptune, Comet이다. 개념은 비슷해서 여기서는 MLflow로 본다.

MLflow의 단위는 셋이다. 실험(experiment)은 같은 문제를 푸는 실행들을 묶는 폴더다. 실행(run)은 학습 한 번이다. 실행 하나에 파라미터(params), 지표(metrics), 태그(tags), 아티팩트(artifacts, 모델 파일·그림 같은 파일)를 남긴다.

```python
import hashlib
import mlflow, mlflow.sklearn
from mlflow.models import infer_signature

mlflow.set_tracking_uri("sqlite:///mlflow.db")   # 실행 기록을 저장할 곳
mlflow.set_experiment("churn")                   # 실행을 묶는 실험 이름

data_hash = hashlib.sha256(X.tobytes() + y.tobytes()).hexdigest()[:12]
Xtr, Xte, ytr, yte = train_test_split(X, y, test_size=0.25, random_state=42)

for depth in [4, 8, None]:
    with mlflow.start_run(run_name=f"rf-depth-{depth}") as run:
        params = {"n_estimators": 100, "max_depth": depth, "random_state": 42}
        mlflow.log_params(params)                          # 하이퍼파라미터
        mlflow.set_tag("data_hash", data_hash)             # 어떤 데이터로 학습했나
        m = RandomForestClassifier(**params).fit(Xtr, ytr)
        auc = roc_auc_score(yte, m.predict_proba(Xte)[:, 1])
        mlflow.log_metric("test_auc", auc)                 # 지표
        info = mlflow.sklearn.log_model(                   # 모델 파일과 입출력 형태
            m, name="model",
            signature=infer_signature(Xte, m.predict_proba(Xte)),
            skops_trusted_types=["sklearn.tree._tree.Tree"],
        )
        print(run.info.run_id[:8], depth, round(auc, 4), info.model_uri[:12])
```

```text
cbb14832 4 0.8965 models:/m-dc
07a29fe3 8 0.9477 models:/m-7c
f20813af None 0.9673 models:/m-1c
```

실행 세 개가 기록됐다. 나중에 코드로 가장 좋은 실행을 찾을 수 있다.

```python
best = mlflow.search_runs(experiment_names=["churn"],
                          order_by=["metrics.test_auc DESC"], max_results=1)
print(best[["run_id", "params.max_depth", "metrics.test_auc", "tags.data_hash"]].to_string(index=False))
```

```text
                          run_id params.max_depth  metrics.test_auc tags.data_hash
f20813af35a745b49977e14f11569266             None          0.967279   984ef58b5b34
```

`mlflow ui`(또는 `mlflow server`)를 띄우면 같은 내용을 웹 화면에서 표로 비교하고, 지표를 파라미터별로 그래프로 그려 볼 수 있다. MLflow는 Git 저장소 안에서 실행하면 커밋 해시를 `mlflow.source.git.commit` 태그로 자동으로 남긴다.

`log_model`이 남기는 파일을 열어 보면 재현에 필요한 것들이 들어 있다.

```text
MLmodel
conda.yaml
model.skops
python_env.yaml
requirements.txt
```

```text
mlflow==3.17.2
numpy==2.5.4
pandas==3.1.0
psutil==7.2.2
rich==15.0.0
scikit-learn==1.9.1
scipy==1.18.1
skops==0.16.0
```

`requirements.txt`에 학습할 때의 라이브러리 버전이 고정돼 있고, `MLmodel` 파일에는 입력이 float64 20열이라는 signature와 Python 버전(3.13.16)이 적혀 있다. 서빙할 때 입력 열 수가 다르면 signature 검사에서 걸린다.

`skops_trusted_types`는 MLflow 3.x의 scikit-learn 모델이 기본으로 pickle 대신 skops 형식으로 저장되면서 생긴 인자다. pickle 파일은 불러오는 순간 임의의 코드를 실행할 수 있어서, 남이 만든 모델 파일을 그대로 `pickle.load`하는 건 남의 스크립트를 실행하는 것과 같다. skops는 허용한 타입만 불러온다. 트리 모델의 내부 구조체는 기본 허용 목록에 없어서 직접 신뢰한다고 적어 줘야 했다. 공개된 모델을 내려받아 쓸 때도 같은 이유로 pickle 대신 safetensors나 ONNX 같은 형식이 선호된다.

MLflow 3부터는 모델이 실행 아래 폴더가 아니라 별도의 "로그된 모델"(`models:/m-...`)로 관리된다. 위 출력의 `info.model_uri`가 그 주소다. 2.x 시절 예제의 `runs:/<run_id>/model` 주소로 등록하면 경고와 함께 이 주소로 바꿔 등록한다.

## 큰 데이터는 Git 밖에, 버전은 Git 안에: DVC

파라미터와 지표는 작아서 어디든 저장할 수 있다. 문제는 데이터다. 학습 데이터가 수 GB면 Git 저장소에 넣을 수 없다. 넣는 순간 clone이 느려지고, 데이터가 바뀔 때마다 저장소가 그만큼 불어난다. 큰 파일을 실수로 커밋했을 때 생기는 일은 [Git 큰 파일 글](/posts/git-large-files-secrets)에 있다.

DVC(Data Version Control)는 데이터 파일을 Git 밖의 저장소(S3, GCS, 로컬 디렉터리 등)에 두고, Git에는 그 파일의 해시가 적힌 작은 포인터 파일만 넣는다. 그러면 Git 커밋 하나가 "이 코드 + 이 데이터 해시"를 함께 가리킨다.

실제로 해 보자. 20만 줄짜리 CSV(약 2.2MB)를 만들어 추적한다. 원격 저장소는 실습이라 로컬 디렉터리로 잡았다.

```bash
git init && dvc init                 # Git 저장소 안에 DVC를 켠다 (.dvc/ 폴더 생성)
git commit -m "dvc init"
dvc add data/train.csv               # 파일을 DVC 캐시에 넣고 포인터 파일을 만든다
```

```text
To track the changes with git, run:

	git add data/train.csv.dvc data/.gitignore
```

DVC는 두 파일을 만든다. `data/.gitignore`에는 `/train.csv`가 들어가서 원본이 Git에 올라가지 않게 막고, `data/train.csv.dvc`가 포인터다.

```text
outs:
- md5: 62632b610335b37c631b950549459b2e
  size: 2249726
  hash: md5
  path: train.csv
```

```bash
dvc remote add -d storage ../remote          # 기본 원격 저장소 지정 (실무에선 s3://bucket/path)
git add data/train.csv.dvc data/.gitignore .dvc/config
git commit -m "data v1"
dvc push                                     # 실제 데이터를 원격 저장소로 올린다
```

```text
Setting 'storage' as a default remote.
1 file pushed
```

데이터에 한 줄을 추가하면 `dvc status`가 바뀐 걸 알려 준다. 다시 `dvc add`, 커밋, 푸시하면 v2가 된다.

```text
data/train.csv.dvc:
	changed outs:
		modified:           data/train.csv
```

이제 예전 데이터로 돌아가 보자. Git으로 코드를 옛 커밋으로 돌리고 `dvc checkout`으로 포인터에 맞는 데이터를 가져온다.

```bash
git checkout HEAD~1      # 포인터 파일(.dvc)이 v1 해시로 돌아간다
dvc checkout             # 포인터에 맞는 데이터를 캐시에서 꺼내 놓는다
wc -l data/train.csv
```

```text
M       data/train.csv
200001 data/train.csv
```

헤더 포함 200,001줄, v1으로 돌아왔다. 다시 최신 커밋으로 가서 `dvc checkout`하면 200,002줄이 된다. 처음 장면의 "그때 데이터"는 이렇게 커밋 하나로 다시 꺼낼 수 있다.

원격 저장소를 들여다보면 한 가지 비용이 보인다.

```text
../remote/files/md5/62/632b610335b37c631b950549459b2e
../remote/files/md5/cd/d0edf328346c9d65c0b1e607939111
4.4M	../remote
```

한 줄만 바꿨는데 2.2MB짜리 파일이 통째로 하나 더 저장됐다. DVC는 파일 단위로 중복을 없애지 줄 단위 차이를 저장하지 않는다. 매일 조금씩 쌓이는 데이터라면 하나의 큰 파일보다 날짜별 파일이 든 디렉터리로 두는 게 낫다. 바뀌지 않은 날짜 파일은 해시가 같아서 다시 저장되지 않는다.

### Git LFS로는 안 되나

Git LFS도 큰 파일을 Git 밖에 두고 포인터만 커밋한다는 점은 같다. 차이는 그 위에 무엇이 있느냐다.

- 저장소: Git LFS는 LFS 서버(GitHub, GitLab의 LFS 저장소)에 올린다. 호스팅 서비스의 용량·대역폭 한도에 묶이고, 수백 GB 데이터를 두기엔 비싸다. DVC는 이미 쓰는 S3·GCS 버킷을 그대로 쓴다.
- 파이프라인: DVC는 "이 데이터와 이 코드로 이 단계를 돌리면 이 결과가 나온다"를 `dvc.yaml`로 적고, 입력이 바뀐 단계만 다시 돌린다. LFS에는 이런 개념이 없다.
- 지표와 파라미터: DVC는 커밋 사이의 파라미터·지표 차이를 비교하는 명령이 있다.
- 쓰는 법: LFS는 `git add`만 하면 돼서 팀원이 따로 배울 게 거의 없다. DVC는 `dvc push`·`dvc pull`을 따로 해야 하고, 잊으면 포인터만 있고 데이터가 없는 커밋이 생긴다.

그래서 디자인 에셋이나 몇백 MB짜리 바이너리면 LFS로 충분하고, 데이터셋이 크고 학습 단계를 파이프라인으로 묶고 싶으면 DVC가 맞다. 데이터가 이미 데이터 레이크 테이블(Delta Lake, Iceberg)에 있다면 그 테이블의 스냅숏 ID나 타임 트래블 버전을 기록하는 것도 같은 효과를 낸다. 도구가 무엇이든 "학습에 쓴 데이터를 정확히 다시 꺼낼 수 있는 주소"를 남기면 된다.

### 단계를 묶으면 바뀐 것만 다시 돈다

DVC 파이프라인은 단계마다 의존(입력)과 출력을 적는다.

```bash
dvc stage add -n train -d train.py -d data/train.csv -p train.threshold \
  -o model.txt -M metrics.json python train.py    # train 단계를 dvc.yaml에 추가
dvc repro                                          # 바뀐 단계만 실행
```

```text
stages:
  train:
    cmd: python train.py
    deps:
    - data/train.csv
    - train.py
    params:
    - train.threshold
    outs:
    - model.txt
    metrics:
    - metrics.json:
        cache: false
```

처음 `dvc repro`는 단계를 실행하고 입력·출력의 해시를 `dvc.lock`에 적는다. 아무것도 안 바꾸고 다시 돌리면 건너뛴다.

```text
'data/train.csv.dvc' didn't change, skipping
Stage 'train' didn't change, skipping
Data and pipelines are up to date.
```

`params.yaml`의 문턱값만 0.4에서 0.3으로 바꾸면 차이를 보여 주고, 다시 돌린 뒤 지표 차이도 비교할 수 있다.

```text
Path         Param            HEAD    workspace
params.yaml  train.threshold  0.4     0.3
Path          Metric     HEAD    workspace    Change
metrics.json  threshold  0.4     0.3          -0.1
```

`dvc.lock`이 커밋에 들어가 있으니, 나중에 이 커밋을 꺼내면 어느 데이터 해시와 어느 코드 해시로 어떤 출력이 나왔는지가 그대로 남아 있다. 이 파이프라인을 CI에서 자동으로 돌리는 이야기는 [ML 파이프라인과 CI/CD 글](/posts/ml-pipelines-ci-cd)에서 이어 간다.

## 운영에 나간 모델에 이름표를 붙인다: 모델 레지스트리

실험 추적은 "무엇을 해 봤나"를 기록한다. 실행이 수백 개 쌓이면 다음 질문이 생긴다. 지금 운영에서 도는 모델은 어느 것인가. 다음에 내보낼 후보는 무엇인가. 문제가 생기면 어디로 되돌리나. 이걸 맡는 게 모델 레지스트리(model registry)다.

레지스트리에는 "churn-model" 같은 이름으로 모델을 등록하고, 등록할 때마다 버전 번호(1, 2, 3...)가 붙는다. 서빙 쪽은 특정 실행 ID나 파일 경로가 아니라 이 이름을 보고 모델을 가져온다.

예전 MLflow 레지스트리는 버전마다 단계(stage)를 두었다. None, Staging, Production, Archived 넷 중 하나를 고르는 방식이다. MLflow 2.9부터 이 단계 기능은 사용 중단(deprecated) 예고가 붙었고, 대신 별칭(alias)과 태그를 쓴다. 단계가 고정된 네 개라 "A/B 테스트 중인 두 모델"이나 "지역마다 다른 운영 모델" 같은 상황을 표현하지 못했기 때문이다. 별칭은 `champion`, `challenger`, `prod-kr`처럼 마음대로 이름을 지어 한 버전에 붙이는 포인터다. 한 별칭은 한 번에 한 버전만 가리킨다.

```python
from mlflow import MlflowClient
c = MlflowClient()

v1 = mlflow.register_model(model_uri_depth8, "churn-model")     # AUC 0.9477 모델
c.set_registered_model_alias("churn-model", "champion", v1.version)
v2 = mlflow.register_model(model_uri_depth_none, "churn-model") # AUC 0.9673 모델
c.set_registered_model_alias("churn-model", "challenger", v2.version)
c.set_model_version_tag("churn-model", v2.version, "validation", "passed")
```

```text
version 1 aliases ['champion'] run 07a29fe3 tags {}
version 2 aliases ['challenger'] run f20813af tags {'validation': 'passed'}
```

서빙 코드는 별칭으로 불러온다.

```python
model = mlflow.sklearn.load_model("models:/churn-model@champion")
```

여기서 조심할 점이 하나 있다. 서빙이 `@champion`을 언제 읽느냐다. 프로세스가 시작할 때 한 번만 읽으면 별칭을 옮겨도 재시작 전까지 옛 모델이 돈다. 주기적으로 다시 읽게 만들면 서버마다 바뀌는 시점이 달라서 잠깐 두 버전이 섞인다. 그래서 별칭 변경을 배포 이벤트로 취급해서 새 버전이 실린 컨테이너를 [카나리 릴리스](/posts/canary-release)처럼 점진적으로 내보내는 팀이 많다. 레지스트리는 "무엇을 내보낼지"를 정하고, 실제로 트래픽을 옮기는 건 배포 시스템이 한다.

### 승격 규칙은 사람이 정하고 기계가 지킨다

별칭을 아무나 옮길 수 있으면 레지스트리는 또 하나의 공유 폴더가 된다. 승격 조건을 정해 둔다. 예를 들면 이렇다.

- 같은 시험 세트에서 현재 champion보다 주요 지표가 나쁘지 않다(허용 오차 안).
- 중요한 사용자 구간(신규·기존, 국가)별 지표가 기준선 아래로 떨어지지 않는다.
- 실행에 데이터 해시, 커밋 해시, 학습 코드가 깨끗한 작업 트리에서 돌았다는 태그가 있다.
- 입력 signature가 서빙 쪽 입력과 맞는다.
- 사람 한 명 이상이 결과 리포트를 보고 승인했다.

이 검사를 CI 잡으로 만들어 통과한 버전에만 `validation=passed` 태그를 붙이고, 태그가 있는 버전만 champion이 될 수 있게 막는다. MLflow 오픈소스 자체에는 세밀한 권한 관리가 약해서, 관리형 플랫폼(Databricks Unity Catalog, SageMaker Model Registry, Vertex AI Model Registry)이나 별칭 변경을 CI에서만 하도록 하는 운영 규칙으로 보완한다.

## 기록을 남기고도 재현이 안 되는 경우

도구를 다 깔고도 재현이 깨지는 지점이 있다.

노트북에서 돌린 실행. 셀을 순서 없이 실행하고 중간 셀을 고치면, 기록된 파라미터와 실제로 모델을 만든 상태가 다를 수 있다. 등록할 모델은 노트북이 아니라 스크립트나 파이프라인 잡에서 만든다.

데이터 포인터는 있는데 데이터가 없다. `dvc push`를 잊고 커밋만 푸시하면 팀원은 포인터만 받는다. `dvc pull`에서 파일을 못 찾는다는 오류가 난다. CI에서 `dvc status -c`(원격과 비교)로 막거나, Git 훅에 `dvc push`를 건다.

원격 저장소의 수명 주기 정책. S3 버킷에 "90일 지난 객체 삭제" 정책이 걸려 있으면 레지스트리에 남은 옛 모델의 학습 데이터가 사라진다. 운영에 나간 적 있는 모델의 데이터는 지우지 않도록 따로 표시한다.

특징 계산 코드가 다른 저장소에 있다. 학습 저장소는 커밋 해시를 남겼는데, 특징을 만드는 SQL은 데이터 팀 저장소에 있어서 그쪽 버전이 기록되지 않았다. 특징 정의 버전도 실행 태그로 남긴다. 피처 스토어를 쓴다면 피처 뷰의 버전을 남긴다.

환경은 같은데 하드웨어가 다르다. CPU와 GPU, GPU 세대에 따라 부동소수점 연산 순서가 달라 마지막 자리가 달라진다. 이 정도 차이는 받아들이고, 재현성의 기준을 "같은 숫자"가 아니라 "허용 오차 안의 같은 지표"로 정하는 게 현실적이다.

## 다시 만들 수 있어야 고칠 수 있다

모델은 코드, 데이터, 설정, 환경, 무작위성이 함께 만든다. 시드를 고정해도 데이터 행 순서 하나로 숫자가 바뀌는 걸 봤다. 그래서 실행마다 MLflow 같은 실험 추적 도구로 파라미터·지표·환경·모델 파일을 남기고, 데이터는 DVC 포인터나 테이블 스냅숏으로 커밋과 묶고, 운영에 나가는 모델은 레지스트리의 별칭으로 가리킨다. 처음 장면의 요청에는 이제 "레지스트리에서 지난달 champion이던 버전을 찾아 실행 ID를 따라가면 커밋과 데이터 해시가 나온다"로 답할 수 있다. 이렇게 묶어 둔 기록을 자동으로 돌리는 방법은 [ML 파이프라인과 CI/CD 글](/posts/ml-pipelines-ci-cd)에서, 운영에 나간 뒤 모델을 지켜보는 방법은 [모델 모니터링 글](/posts/ml-model-monitoring-drift)에서 다룬다.

## 면접에서 나올 만한 질문

### ML 모델의 재현성은 왜 코드 버전 관리만으로 안 되나요?

모델은 코드뿐 아니라 데이터, 하이퍼파라미터, 라이브러리 버전, 무작위성이 함께 만들기 때문이다. 같은 코드라도 갱신된 테이블이나 순서가 보장되지 않는 쿼리로 데이터를 뽑으면 다른 모델이 나온다. 실험에서 시드를 고정했는데 행 순서만 바꿔도 AUC가 0.9673에서 0.9646으로 달라졌다. 그래서 데이터 스냅숏과 해시, 파라미터, 환경, 시드를 실행마다 함께 기록한다.

### 실험 추적 도구에는 무엇을 기록하나요?

실행마다 하이퍼파라미터, 평가 지표, 모델 파일과 입출력 signature, 라이브러리 버전, 코드 커밋 해시, 학습 데이터의 버전이나 해시를 남긴다. MLflow라면 `log_params`, `log_metric`, `set_tag`, `log_model`로 남기고, `log_model`이 `requirements.txt`와 `MLmodel` 파일에 환경과 signature를 함께 저장한다. 그래야 나중에 가장 좋은 실행을 검색하고 그 실행을 그대로 다시 만들 수 있다.

### 데이터 버전 관리를 Git LFS 대신 DVC로 하는 이유는 무엇인가요?

둘 다 큰 파일을 Git 밖에 두고 포인터만 커밋하지만, DVC는 S3·GCS 같은 이미 쓰는 저장소를 원격으로 쓸 수 있고, `dvc.yaml`로 단계별 의존과 출력을 적어 바뀐 단계만 다시 돌리며, 커밋 사이의 파라미터·지표 차이를 비교할 수 있다. LFS는 호스팅 서비스의 용량 한도에 묶이고 파이프라인 개념이 없다. 대신 DVC는 `dvc push`를 따로 해야 해서 잊으면 데이터 없는 커밋이 생긴다. 큰 바이너리 몇 개면 LFS, 데이터셋과 학습 파이프라인이면 DVC가 맞다.

### DVC가 데이터를 저장하는 방식의 한계는 무엇인가요?

파일 단위로 내용 해시를 매겨 중복을 없앨 뿐 줄 단위 차이는 저장하지 않는다. 실험에서 2.2MB 파일에 한 줄만 추가했는데 원격 저장소가 4.4MB가 됐다. 매일 쌓이는 데이터라면 날짜별 파일로 나눈 디렉터리로 관리해 바뀌지 않은 파일을 다시 저장하지 않게 한다. 데이터가 이미 Iceberg나 Delta Lake 테이블에 있으면 스냅숏 ID를 기록하는 방법도 있다.

### 모델 레지스트리는 배포에서 어떤 역할을 하나요?

학습 결과물 중 "운영에 나갈 모델"을 이름과 버전으로 관리하고, 서빙이 파일 경로 대신 `models:/churn-model@champion` 같은 이름으로 모델을 가져오게 한다. 승격은 별칭을 새 버전으로 옮기는 일이고, 되돌리기는 별칭을 이전 버전으로 다시 옮기는 일이라 재학습 없이 바로 된다. 각 버전은 실행 ID를 가리켜 커밋과 데이터까지 거꾸로 추적할 수 있다. 실제 트래픽 전환은 레지스트리가 아니라 배포 시스템이 카나리 같은 방식으로 한다.

### MLflow의 stage 대신 alias를 쓰는 이유는 무엇인가요?

stage는 None·Staging·Production·Archived 네 가지로 고정돼 있어서 A/B 테스트 중인 두 모델이나 지역별 운영 모델 같은 상황을 표현하기 어려웠다. MLflow 2.9부터 stage는 사용 중단 예고가 붙었고, 이름을 자유롭게 짓는 별칭과 태그를 쓰도록 바뀌었다. 별칭은 한 번에 한 버전만 가리키는 포인터라 `champion`, `challenger`, `prod-kr`처럼 필요한 만큼 만들 수 있다. 검증 통과 여부 같은 상태는 태그로 남긴다.

### 시드를 고정했는데도 결과가 다르게 나오는 이유는 무엇인가요?

데이터의 행 순서가 바뀌면 같은 시드로도 분할과 배치 구성이 달라진다. `ORDER BY` 없는 쿼리는 순서를 보장하지 않는다. 라이브러리 버전이 바뀌면 기본값이 바뀌기도 한다. GPU에서는 병렬 연산의 순서 때문에 시드를 고정해도 미세하게 달라질 수 있어서 결정적 알고리즘 설정을 따로 켜야 한다. 그래서 재현의 기준을 허용 오차 안의 같은 지표로 두는 게 현실적이다.

### 모델 파일을 pickle로 주고받으면 어떤 위험이 있나요?

pickle은 불러오는 순간 파일 안에 적힌 임의의 코드를 실행할 수 있어서, 출처를 모르는 모델 파일을 불러오는 건 남의 스크립트를 실행하는 것과 같다. MLflow 3.x는 scikit-learn 모델을 기본으로 skops 형식으로 저장해 허용한 타입만 불러온다. 공개 모델을 받을 때도 safetensors나 ONNX처럼 코드 실행이 없는 형식을 선호하고, 레지스트리에 올리는 권한을 제한한다.
