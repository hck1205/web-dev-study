[Majority Element](https://leetcode.com/problems/majority-element/)는 LeetCode 169번 Easy 문제다. 해시맵으로 세면 바로 풀린다. 그런데 문제 끝에 "O(n) 시간, O(1) 공간으로 풀 수 있나"라는 꼬리가 붙어 있고, 면접관이 기다리는 건 그 꼬리의 답인 보이어-무어 투표 알고리즘이다. 이 알고리즘이 왜 맞는지를 자기 말로 증명할 수 있느냐가 이 문제의 실제 난이도다.

이 문제는 풀이가 유난히 많다. 이 글은 일곱 가지를 놓는다. 수마다 세기, 해시맵, 정렬, 무작위로 골라 확인하기, 분할 정복, 비트마다 다수결, 보이어-무어 투표다. 빈도를 해시맵에 세는 기본은 [Top K Frequent Elements](/posts/leetcode-top-k-frequent-elements)에서, 비트를 다루는 기초는 [비트 연산 글](/posts/bit-manipulation)에서 다뤘다. 코드는 모두 Node.js 22, Python 3.13, Java 21에서 직접 돌렸다.

## 절반을 넘게 나오는 수 하나

길이 n인 정수 배열 `nums`에서 n / 2번보다 많이 나오는 수를 찾아 돌려준다. 이런 수를 과반수 원소라고 부른다.

- 과반수 원소는 반드시 있다고 보장한다. 없을 때의 처리는 하지 않아도 된다.
- 길이는 1 이상 5 × 10^4 이하, 값은 -10^9 이상 10^9 이하다.
- 덧붙인 과제로 O(n) 시간과 O(1) 공간을 동시에 만족하는 풀이를 묻는다.

"n / 2보다 많이"가 정확한 조건이다. 길이 7이면 4번 이상, 길이 6이면 4번 이상이다. 길이 6에서 3번은 절반과 같을 뿐 넘지 않는다. 과반수가 있다는 보장이 몇몇 풀이를 가능하게 한다. 보장이 없어지면 어떤 풀이가 틀리는지도 뒤에서 본다.

## 손으로 세어 보기

글 끝까지 쓸 예시다.

```text
인덱스   0  1  2  3  4  5  6
nums     3  3  1  1  1  2  1
```

길이 7이니 4번 이상 나오는 수를 찾는다. 3은 2번, 1은 4번, 2는 1번이다. 답은 1이다.

손으로 셀 때 하는 일은 "수마다 몇 번 나왔나"를 어딘가에 적는 것이다. 그런데 이 문제는 개수를 다 알 필요가 없다. "절반을 넘는 하나"만 찾으면 된다. 이 차이가 보이어-무어 투표를 가능하게 한다. 3과 1을 하나씩 짝지어 지워 보자. 3 두 개가 1 두 개와 짝지어 지워지고, 남은 1 두 개 중 하나가 2와 짝지어 지워진다. 마지막에 1 하나가 남는다. 짝을 다 지어도 과반수는 남는다.

## 수마다 처음부터 세는 풀이

수 `x`를 하나 고르고 배열을 다 훑어 `x`가 몇 번 나오는지 센다. n / 2를 넘으면 답이다.

```js
function majorityElement(nums) {
  const n = nums.length;
  for (const x of nums) {
    let c = 0;
    for (const y of nums) if (y === x) c++; // x가 몇 번 나오나
    if (c > n / 2) return x;
  }
  return null; // 과반수가 있다는 보장 때문에 여기 오지 않는다
}

console.log(majorityElement([3, 3, 1, 1, 1, 2, 1]));
```

```text
1
```

시간은 최악 O(n²)이다. 과반수가 배열 뒤쪽에 몰려 있으면 앞의 다른 수를 하나하나 다 세어 본 뒤에야 답을 만난다. 길이 10^4에서 앞 절반을 서로 다른 수로, 뒤 절반을 과반수로 채웠더니 52ms가 걸렸다. 공간은 O(1)이다.

재미있게도 무작위로 섞은 배열에서는 같은 크기가 0.06ms였다. 과반수가 절반 넘게 있으니 첫 칸이 과반수일 확률이 절반을 넘고, 대개 처음 한두 번 만에 답을 만난다. 이 관찰은 뒤의 "무작위로 골라 확인하기" 풀이로 이어진다. 최악을 보장하려면 같은 수를 다시 세지 않게 개수를 적어 둬야 한다.

## 장부에 횟수를 적는 풀이

수 → 지금까지 나온 횟수를 해시맵에 적는다. 횟수가 n / 2를 넘는 순간 바로 돌려준다.

```js
function majorityElement(nums) {
  const count = new Map();   // 수 → 지금까지 나온 횟수
  const half = nums.length / 2;
  for (const x of nums) {
    const c = (count.get(x) ?? 0) + 1;
    if (c > half) return x;  // 절반을 넘는 순간 끝낸다
    count.set(x, c);
  }
  return null;
}

console.log(majorityElement([3, 3, 1, 1, 1, 2, 1]));
```

```text
1
```

시간은 O(n), 공간은 서로 다른 수의 개수만큼이라 최악 O(n)이다. 과반수가 절반 넘게 차지하니 서로 다른 수는 많아야 n / 2개쯤이지만, 등급으로는 여전히 O(n)이다. 10^6개에서 116ms였다. 과반수가 아닌 칸을 모두 서로 다른 큰 수로 채워 맵에 50만 개가 들어갔기 때문이다.

이 풀이가 면접의 기본 답이고, 대부분의 상황에서 이걸로 충분하다. 덧붙인 과제는 이 해시맵을 없앨 수 있냐는 것이다.

## 정렬하면 가운데에 있다

정렬하면 같은 수가 모여 한 덩어리가 된다. 과반수 덩어리는 길이가 n / 2보다 기니, 어디에 놓이든 반드시 배열 한가운데 칸 `Math.floor(n / 2)`를 덮는다.

```js
function majorityElement(nums) {
  const a = [...nums].sort((x, y) => x - y);
  return a[Math.floor(a.length / 2)]; // 과반수 덩어리는 반드시 가운데를 덮는다
}

console.log(majorityElement([3, 3, 1, 1, 1, 2, 1]));
```

```text
1
```

정렬하면 `[1, 1, 1, 1, 2, 3, 3]`이고 가운데 3번 칸이 1이다. 왜 반드시 덮는지 두 끝을 생각해 보면 된다. 덩어리가 맨 왼쪽에서 시작하면 길이가 n / 2보다 길어서 가운데를 넘어간다. 맨 오른쪽에서 끝나도 마찬가지로 가운데까지 들어온다. 그 사이 어디에 있든 덮는다.

여기서 다른 문제와 다른 점이 하나 있다. JavaScript에서 비교자 없이 `sort()`를 하면 숫자가 문자열로 정렬되는데, 이 문제에서는 그래도 답이 맞는다. `[10, 9, 10, 100, 10].sort()`는 `[10, 10, 10, 100, 9]`가 된다. 크기 순서는 틀렸지만 같은 값끼리는 여전히 붙어 있다. 이 풀이에 필요한 건 "같은 값이 모인다"는 성질뿐이라 어떤 순서든 일관되기만 하면 된다. 그렇다고 비교자를 빼는 습관은 들이지 않는 게 좋다. 다른 문제에서는 바로 틀린다.

시간은 O(n log n)이다. 복사본을 만들면 공간 O(n), 원래 배열을 정렬해도 되면 정렬 구현에 따라 O(log n)에서 O(n)이다. 10^6개에서 304ms로 일곱 풀이 중 가장 느렸다. 코드가 가장 짧다는 게 장점이다.

## 아무거나 집어 확인하기

무작위로 칸 하나를 고르면 그 칸이 과반수일 확률이 절반을 넘는다. 고른 수를 세어 보고, 맞으면 끝, 아니면 다시 고른다.

```js
function majorityElement(nums) {
  const n = nums.length;
  while (true) {
    const cand = nums[Math.floor(Math.random() * n)]; // 아무 칸이나 고른다
    let c = 0;
    for (const x of nums) if (x === cand) c++;
    if (c > n / 2) return cand;                       // 맞으면 끝
  }
}

console.log(majorityElement([3, 3, 1, 1, 1, 2, 1]));
```

```text
1
```

한 번 고를 때 맞을 확률이 1/2보다 크니, 맞을 때까지 고르는 횟수의 기댓값은 2보다 작다. 고를 때마다 O(n)으로 세니 기대 시간은 O(n)이고, 공간은 O(1)이다. 10^6개에서 5.65ms로 실측은 가장 빨랐다. 과반수가 50만 1개라 대개 한두 번 만에 맞았다.

문제는 최악이다. 운이 나쁘면 계속 틀린 수를 고를 수 있어서 최악 시간에 상한이 없다. 확률로는 k번 연속 틀릴 가능성이 1/2^k보다 작아 실제로 오래 걸릴 일은 거의 없다. 하지만 면접에서 "최악은요?"에 답이 궁하고, 과반수가 없는 입력에서는 영원히 돈다. 보장이 깨질 수 있는 입력이라면 시도 횟수에 상한을 둬야 한다.

## 반씩 나눠 이긴 쪽끼리 겨루기

배열을 반으로 나눠 각 절반의 과반수를 구한다. 전체의 과반수는 두 절반 중 적어도 한쪽의 과반수다. 양쪽 모두에서 절반 이하로 나오는 수는 합쳐도 전체의 절반 이하이기 때문이다. 그러니 두 후보를 전체 구간에서 세어 더 많은 쪽을 고른다.

```js
function majorityElement(nums) {
  const countIn = (x, lo, hi) => {
    let c = 0;
    for (let i = lo; i <= hi; i++) if (nums[i] === x) c++;
    return c;
  };
  const rec = (lo, hi) => {
    if (lo === hi) return nums[lo];       // 한 칸짜리 구간의 과반수는 그 칸
    const mid = (lo + hi) >> 1;
    const left = rec(lo, mid), right = rec(mid + 1, hi);
    if (left === right) return left;      // 두 후보가 같으면 그대로
    // 다르면 이 구간 전체에서 세어 많은 쪽
    return countIn(left, lo, hi) > countIn(right, lo, hi) ? left : right;
  };
  return rec(0, nums.length - 1);
}

console.log(majorityElement([3, 3, 1, 1, 1, 2, 1]));
```

```text
1
```

한 단계에서 두 번 세는 일이 구간 길이에 비례하고, 단계가 log n개라 시간은 O(n log n)이다. 공간은 재귀 깊이 O(log n)이다. 10^6개에서 30ms였다. 정렬과 등급은 같은데 열 배쯤 빠른 건, 두 후보가 같으면 세지 않고 넘어가는 경우가 많고 배열을 복사하지 않기 때문이다.

이 풀이의 쓸모는 생각의 틀에 있다. "부분의 답을 합쳐 전체의 답을 만든다"는 성질이 있으면 여러 기계에 데이터를 나눠 처리할 수 있다. 다만 합칠 때 원래 구간을 다시 세야 해서 기계마다 데이터를 다시 봐야 한다. 뒤의 보이어-무어는 다시 보지 않고 합치는 방법을 준다.

## 자리마다 다수결

과반수 원소의 0번 비트가 1이라고 하자. 그러면 배열 전체에서 0번 비트가 1인 수가 절반을 넘는다. 과반수만으로도 절반이 넘기 때문이다. 0번 비트가 0이라면 반대로 0인 수가 절반을 넘는다. 그래서 비트 자리마다 1이 절반을 넘는지 세면, 과반수 원소의 비트를 한 자리씩 그대로 얻는다.

```js
function majorityElement(nums) {
  const n = nums.length;
  let res = 0;
  for (let b = 0; b < 32; b++) {
    let ones = 0;
    for (const x of nums) ones += (x >> b) & 1; // b번 비트가 1인 수를 센다
    if (ones > n / 2) res |= 1 << b;            // 절반을 넘으면 답의 b번 비트도 1
  }
  return res;
}

console.log(majorityElement([3, 3, 1, 1, 1, 2, 1]));
console.log(majorityElement([-1, -1, 7]));
```

```text
1
-1
```

음수도 맞는다. JavaScript의 비트 연산은 값을 32비트 2의 보수 정수로 바꿔서 하고, `1 << 31`은 부호 비트를 켠 음수가 된다. 그래서 -1의 비트 32개가 모두 1로 모이면 결과도 -1이다. 값이 32비트 범위를 넘는 언어나 문제라면 자릿수를 늘려야 한다. Python은 정수에 비트 수 제한이 없어서 음수를 이렇게 모으면 부호 처리를 따로 해야 한다.

## 서로 다른 둘을 짝지어 지운다

이제 보이어-무어 투표다. 후보 하나와 표 수 하나만 들고 배열을 한 번 훑는다.

1. 표가 0이면 지금 수를 새 후보로 삼는다.
2. 지금 수가 후보와 같으면 표를 하나 더하고, 다르면 하나 뺀다.

끝났을 때의 후보가 답이다.

```js
function majorityElement(nums) {
  let cand = null, count = 0;
  for (const x of nums) {
    if (count === 0) cand = x;       // 표가 바닥나면 지금 수를 새 후보로
    count += x === cand ? 1 : -1;    // 같으면 +1, 다르면 서로 하나씩 지운다
  }
  return cand;
}

console.log(majorityElement([3, 3, 1, 1, 1, 2, 1]));
```

```text
1
```

표를 하나 빼는 건 "후보 하나와 다른 수 하나를 짝지어 함께 지운다"는 뜻이다. 아래 그림에서 다음을 누르면 3이 후보였다가 1에게 지워지고, 1이 다시 후보가 되는 과정이 보인다.

### 왜 남은 후보가 과반수인가

표가 0이 되는 순간마다 배열을 끊어 보자. 예시에서는 3번 칸 뒤와 5번 칸 뒤에서 표가 0이 됐다. 그러면 배열이 `[3, 3, 1, 1]`, `[1, 2]`, `[1]`로 나뉜다.

표가 0으로 끝나는 덩어리에서는 그 덩어리의 후보가 정확히 절반이고 나머지가 절반이다. 그러니 그 덩어리 안에서 어떤 수든 절반을 넘지 못한다. 후보는 정확히 절반, 다른 수는 절반 이하다. 과반수 원소 m도 이 덩어리들에서는 많아야 절반씩만 차지한다.

전체에서 m은 절반을 넘는다. 표가 0으로 끝난 덩어리들에서 많아야 절반씩만 썼으니, 남은 마지막 덩어리에서 m은 여전히 절반을 넘어야 한다. 마지막 덩어리는 표가 0으로 떨어지지 않은 구간이라 처음 정한 후보가 끝까지 가장 많고, 절반을 넘는 수는 그 후보뿐이다. 그래서 마지막 후보가 m이다.

짝짓기로 말하면 더 짧다. 표를 빼는 건 서로 다른 두 수를 한 쌍으로 지우는 것이다. m이 아닌 수를 모두 m과 짝지어 지워도 m은 남는다. m이 아닌 수끼리 짝지어 지워지면 m은 더 많이 남는다. 어떤 순서로 짝지어도 마지막에 남는 건 m뿐이다.

시간은 한 번 훑기라 O(n), 공간은 변수 두 개라 O(1)이다. 10^6개에서 8.32ms였다. 덧붙인 과제의 정답이다.

## Python과 Java로 옮기기

```python
from typing import List

class Solution:
    def majorityElement(self, nums: List[int]) -> int:
        cand, count = None, 0
        for x in nums:
            if count == 0:          # 표가 바닥나면 지금 수를 새 후보로
                cand = x
            count += 1 if x == cand else -1
        return cand

s = Solution()
print(s.majorityElement([3, 3, 1, 1, 1, 2, 1]), s.majorityElement([5]), s.majorityElement([-1, -1, 7]))
```

```text
1 5 -1
```

Python이라면 `Counter(nums).most_common(1)`이 `[(1, 4)]`를 돌려줘서 한 줄로도 끝난다. 해시맵 풀이를 표준 라이브러리로 쓴 것이라 공간은 O(n)이다. 면접에서 한 줄 답을 먼저 말하는 건 좋지만, O(1) 공간을 물으면 위의 투표 풀이로 넘어간다.

```java
class Solution {
    public int majorityElement(int[] nums) {
        int cand = 0, count = 0;
        for (int x : nums) {
            if (count == 0) cand = x;          // 표가 바닥나면 지금 수를 새 후보로
            count += (x == cand) ? 1 : -1;
        }
        return cand;
    }

    public static void main(String[] args) {
        Solution s = new Solution();
        System.out.println(s.majorityElement(new int[] { 3, 3, 1, 1, 1, 2, 1 }));
        System.out.println(s.majorityElement(new int[] { 5 }));
        System.out.println(s.majorityElement(new int[] { Integer.MIN_VALUE, Integer.MIN_VALUE, 5 }));
    }
}
```

```text
1
5
-2147483648
```

Java에서는 `cand`를 `int`로 두고 0으로 시작해도 괜찮다. 첫 칸에서 표가 0이라 바로 덮어쓰기 때문이다. 표는 많아야 n이라 `int`로 넘치지 않는다. `int[]`를 `==`로 비교하니 `Integer` 비교 함정도 없다. 해시맵 풀이를 Java로 쓴다면 `HashMap<Integer, Integer>`에서 꺼낸 값을 `==`로 비교하지 않도록 조심한다. 이 함정은 [Two Sum](/posts/leetcode-two-sum)의 Java 절에서 실제 출력과 함께 봤다.

## 틀리기 쉬운 자리

### 과반수가 없는데 투표 결과를 믿는다

보이어-무어는 과반수가 있을 때만 맞는다. 없으면 뭔가 후보를 돌려주긴 하지만 의미가 없다.

```text
[1, 2, 3]        → 3
[1, 1, 2, 2]     → 1
[2, 2, 1, 1, 3]  → 3
```

세 입력 모두 과반수가 없다. `[2, 2, 1, 1, 3]`의 3은 한 번 나왔을 뿐이다. 보장이 없는 문제라면 후보를 얻은 뒤 한 번 더 훑어 실제로 n / 2를 넘는지 센다. 두 번 훑어도 O(n), O(1)은 그대로다. 실무 데이터는 보장이 없는 경우가 대부분이라, 이 확인 단계가 있어야 쓸 수 있는 알고리즘이 된다.

### 표가 0이 되는 순간 후보를 바꾼다

```js
function wrongVote(nums) {
  let cand = nums[0], count = 0;
  for (const x of nums) {
    if (x === cand) count++;
    else {
      count--;
      if (count === 0) cand = x; // 지금 수가 방금 마지막 표를 지웠는데, 그 수를 후보로 삼는다
    }
  }
  return cand;
}
console.log(wrongVote([3, 3, 1, 1, 1, 2, 1]));
```

```text
2
```

얼핏 같은 규칙 같지만 다르다. 3번 칸의 1이 마지막 3을 지워 표가 0이 되자 그 1을 후보로 삼았는데, 표는 0인 채로 둔다. 그 1은 이미 3과 짝지어 지워진 수인데 후보 자리에 남은 것이다. 4번 칸의 1이 표를 1로 올리고, 5번 칸의 2가 그 표를 지우며 후보가 2로 바뀐다. 마지막 1은 표를 하나 더하지 못하고 2를 지우며 표가 -1로 내려간다. 답이 2로 나왔다. 무작위 입력 3,000개에서 804개가 틀렸다. 올바른 규칙은 "다음 수를 볼 때 표가 0이면 그 수를 새 후보로"다. 지운 수와 새 후보는 다른 수여야 한다.

### 절반을 넘는다와 절반 이상

`c > n / 2` 대신 `c >= n / 2`로 쓰면 길이 4인 `[1, 1, 2, 2]`에서 1을 과반수로 돌려준다. 1은 두 번으로 절반과 같을 뿐이다. 보장이 있는 이 문제의 테스트에서는 안 드러나고, 보장이 없는 변형에서 틀린다. Java와 Python 2처럼 정수 나눗셈이 몫을 주는 경우 `n / 2`가 버림이 되는데, `c > n / 2`는 길이가 홀수든 짝수든 "절반을 넘는다"와 같은 뜻이 된다. 길이 7이면 `7 / 2 = 3`이고 `c > 3`은 4 이상, 길이 6이면 `c > 3`은 4 이상이다.

### 원소가 하나

`[5]`의 답은 5다. 첫 칸에서 표가 0이라 5가 후보가 되고 끝난다. 정렬 풀이는 `a[0]`, 분할 정복은 `lo === hi`로 바로 끝난다. 원소가 하나일 때 재귀가 멈추는지는 분할 정복에서 꼭 확인한다.

## 조건이 바뀌면

### 과반수가 있다는 보장이 없다면

투표로 후보를 얻고, 두 번째로 훑어 그 후보가 실제로 n / 2를 넘는지 센다. 넘지 않으면 과반수가 없다고 답한다. 시간 O(n), 공간 O(1)이 그대로다. 해시맵 풀이는 셀 때 바로 확인되니 따로 할 게 없다.

### n / 3을 넘는 수를 모두 찾으라면

LeetCode 229. Majority Element II다. n / 3을 넘는 수는 많아야 두 개다. 세 개라면 합이 n을 넘기 때문이다. 그래서 후보와 표를 두 쌍 들고, 서로 다른 세 수를 한 묶음으로 지운다. 이번에는 보장이 없으니 확인 단계가 필수다.

```js
function majorityElementII(nums) {
  // 1) 후보 둘을 뽑는다: 서로 다른 세 수를 한 묶음으로 지운다
  let c1 = null, k1 = 0, c2 = null, k2 = 0;
  for (const x of nums) {
    if (x === c1) k1++;
    else if (x === c2) k2++;
    else if (k1 === 0) { c1 = x; k1 = 1; }
    else if (k2 === 0) { c2 = x; k2 = 1; }
    else { k1--; k2--; }
  }
  // 2) 후보가 진짜 n/3을 넘는지 다시 센다
  const res = [];
  for (const c of [c1, c2]) {
    if (c === null || res.includes(c)) continue;
    if (nums.filter((x) => x === c).length > nums.length / 3) res.push(c);
  }
  return res;
}
console.log(majorityElementII([3, 2, 3]), majorityElementII([1, 2, 3, 1, 2, 1, 2]), majorityElementII([1, 2, 3]));
```

```text
[ 3 ] [ 1, 2 ] []
```

`x === c1`, `x === c2` 확인을 `k1 === 0` 확인보다 먼저 하는 순서가 중요하다. 순서를 바꾸면 c1의 표가 0일 때 c2와 같은 수가 c1 자리에 또 들어가 두 후보가 같아질 수 있다. 무작위 입력 5,000개로 개수를 직접 센 결과와 비교해 모두 맞았다. 일반화하면 n / k를 넘는 수는 후보 k - 1개로 찾고, 이것을 미스라-그리스(Misra-Gries) 알고리즘이라고 부른다. 흐름에서 자주 나오는 값(heavy hitter)을 적은 메모리로 찾는 데 쓴다.

### 데이터가 여러 기계에 나뉘어 있다면

보이어-무어의 결과 (후보, 표)는 합칠 수 있다. 두 조각의 후보가 같으면 표를 더하고, 다르면 표가 많은 쪽에서 적은 쪽을 뺀다. 서로 다른 두 수를 짝지어 지운다는 원래 규칙을 조각 단위로 한 것이다.

```js
// 조각 하나를 훑어 (후보, 표) 쌍을 만든다
function vote(nums) {
  let cand = null, count = 0;
  for (const x of nums) {
    if (count === 0) cand = x;
    count += x === cand ? 1 : -1;
  }
  return [cand, count];
}
// 두 조각의 결과를 합친다: 같은 후보면 표를 더하고, 다르면 서로 상쇄한다
function merge([c1, k1], [c2, k2]) {
  if (c1 === c2) return [c1, k1 + k2];
  return k1 >= k2 ? [c1, k1 - k2] : [c2, k2 - k1];
}

const nums = [3, 3, 1, 1, 1, 2, 1, 1, 4];
const parts = [nums.slice(0, 3), nums.slice(3, 6), nums.slice(6)];
const results = parts.map(vote);
console.log(results);
console.log(results.reduce(merge));
```

```text
[ [ 3, 1 ], [ 1, 1 ], [ 1, 1 ] ]
[ 1, 1 ]
```

세 조각을 따로 훑어 (3, 1), (1, 1), (1, 1)을 얻고, 합치면 후보 1이 남는다. 분할 정복과 달리 합칠 때 원래 데이터를 다시 볼 필요가 없다. 무작위 입력 5,000개를 무작위로 세 조각 내 합친 결과도 모두 맞았다. 맵리듀스처럼 기계마다 부분 결과만 넘기는 구조에 바로 들어간다. 보장이 없는 데이터라면 마지막 후보를 다시 세는 단계가 한 번 더 필요하다.

### 구간마다 과반수를 묻는다면

LeetCode 1157. Online Majority Element In Subarray는 `[l, r]` 구간의 과반수를 여러 번 묻는다. 투표 결과를 합칠 수 있다는 성질 덕분에 [세그먼트 트리](/posts/segment-tree-fenwick)의 노드마다 (후보, 표)를 저장해 구간 후보를 log n에 얻고, 값마다 등장 위치 목록을 [이분 탐색](/posts/binary-search)해 실제 개수를 확인한다.

같은 배열·해시 묶음에서 빈도를 다루는 문제로는 [Top K Frequent Elements](/posts/leetcode-top-k-frequent-elements), 중복을 찾는 [Contains Duplicate](/posts/leetcode-contains-duplicate)가 있다.

## 면접에서 나올 만한 질문

### 해시맵 말고 O(1) 공간으로 풀 수 있나요?

보이어-무어 투표로 된다. 후보 하나와 표 수 하나만 들고, 표가 0이면 지금 수를 후보로 삼고, 같으면 표를 더하고 다르면 뺀다. 한 번 훑기라 O(n) 시간, O(1) 공간이다. 비트 자리마다 1이 절반을 넘는지 세는 방법도 O(32n), O(1)이다.

### 보이어-무어가 왜 맞나요?

표를 빼는 건 서로 다른 두 수를 짝지어 지우는 것이다. 과반수가 아닌 수를 모두 과반수와 짝지어 지워도 과반수는 남고, 아닌 수끼리 지워지면 더 많이 남는다. 그래서 끝까지 남는 후보는 과반수뿐이다. 표가 0이 되는 지점으로 배열을 끊으면 각 덩어리에서 과반수가 많아야 절반만 쓰여, 마지막 덩어리에서 여전히 절반을 넘는다는 식으로도 설명할 수 있다.

### 과반수가 없으면 어떻게 되나요?

투표는 의미 없는 후보를 돌려준다. `[2, 2, 1, 1, 3]`에서 한 번 나온 3이 나온다. 보장이 없으면 후보를 얻은 뒤 한 번 더 훑어 실제 개수가 n / 2를 넘는지 확인한다. 두 번 훑어도 O(n), O(1)이다.

### 정렬해서 가운데를 돌려주는 풀이는 왜 맞나요?

정렬하면 같은 값이 한 덩어리로 모이고, 과반수 덩어리는 길이가 n / 2보다 길어서 어디에 놓이든 가운데 칸을 덮는다. 같은 값이 모이기만 하면 되니 크기 순서가 아니어도 된다. 시간은 O(n log n)이라 덧붙인 과제는 만족하지 못한다.

### n / 3을 넘는 수를 찾으라면요?

그런 수는 많아야 두 개라 후보와 표를 두 쌍 들고, 서로 다른 세 수를 한 묶음으로 지운다. 이 문제는 보장이 없어서 마지막에 두 후보를 실제로 세어 확인한다. n / k로 일반화하면 후보 k - 1개를 쓰는 미스라-그리스 알고리즘이다.

### 데이터가 여러 서버에 나뉘어 있으면요?

서버마다 투표를 돌려 (후보, 표)만 모은다. 후보가 같으면 표를 더하고, 다르면 많은 쪽에서 적은 쪽을 빼서 합친다. 원래 데이터를 다시 볼 필요가 없어 맵리듀스 구조에 그대로 맞는다. 보장이 없으면 최종 후보의 개수를 서버마다 세어 더하는 단계를 한 번 더 둔다.

### 무작위로 골라 확인하는 풀이는 어떤가요?

한 번 고를 때 과반수일 확률이 절반을 넘어 기대 시도 횟수가 2보다 작고, 기대 시간은 O(n)이다. 실측으로는 가장 빨랐다. 하지만 최악 시간에 상한이 없고 과반수가 없는 입력에서는 끝나지 않아서, 시도 횟수에 상한을 두거나 다른 풀이로 넘어가는 장치가 필요하다.
