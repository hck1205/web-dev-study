새로 받은 서버에 ssh로 들어왔다. "nginx 설정에서 업로드 크기 제한만 늘려 주세요"라는 부탁인데, 설정 파일이 어디 있는지 모른다. 고친 다음 에러가 나면 로그도 봐야 하는데 그것도 어디 쌓이는지 모른다. 홈 디렉터리에서 `ls`를 쳐 봐도 아무것도 없다.

리눅스는 디렉터리마다 무엇을 두는지 대체로 정해져 있다. 이 약속을 FHS(Filesystem Hierarchy Standard, 파일 시스템 계층 표준)라고 부른다. 배포판마다 조금씩 다르지만 큰 틀은 같아서, 한 번 익혀 두면 처음 보는 서버에서도 "설정은 /etc, 로그는 /var/log"부터 찾아갈 수 있다.

이 글은 그 지도를 먼저 보고, 돌아다니고 만들고 옮기고 찾고 지우는 명령을 실무에서 쓰는 옵션 위주로 본다. 기준은 Ubuntu 24.04 LTS이고 22.04도 거의 같다. 권한(`rwx`, umask, sticky bit)은 [파일 권한 글](/posts/linux-files-permissions)에서, 디스크와 inode는 [디스크와 파일 시스템 글](/posts/linux-disks-filesystems)에서 따로 다룬다.

`/etc`에는 설정이 있다. 거의 전부 사람이 읽을 수 있는 텍스트 파일이다. nginx는 `/etc/nginx/`, ssh 서버는 `/etc/ssh/sshd_config`, 사용자 목록은 `/etc/passwd`, 이름 풀이 순서는 `/etc/nsswitch.conf`, 정적 호스트 목록은 [/etc/hosts](/posts/hosts-file)다. 처음 부탁받은 업로드 제한은 `/etc/nginx/nginx.conf`나 `/etc/nginx/sites-enabled/` 아래 파일에 있다.

`/var`는 운영 중에 바뀌는 데이터를 담는다. `/var/log`에는 로그, `/var/lib`에는 프로그램의 상태 데이터(PostgreSQL의 데이터 디렉터리는 `/var/lib/postgresql/16/main`, Docker는 `/var/lib/docker`), `/var/cache`에는 지워도 다시 만들어지는 캐시, `/var/spool`에는 처리를 기다리는 작업(메일 큐, cron)이 들어간다. 디스크가 찼다는 경보가 오면 대부분 여기부터 본다.

`/usr`는 패키지 관리자가 설치한 프로그램과 라이브러리다. 실행 파일은 `/usr/bin`, 관리자용은 `/usr/sbin`, 라이브러리는 `/usr/lib`. 운영 중에 직접 고치는 곳이 아니다. 패키지를 업데이트하면 덮어써진다. 손으로 빌드해서 넣은 프로그램은 `/usr/local` 아래에, 회사 하나가 만든 묶음(벤더 에이전트 같은 것)은 `/opt/{이름}` 아래에 통째로 둔다.

`/home`은 사람 계정의 집이고, `/srv`는 이 서버가 제공하는 서비스의 데이터(웹 루트, 배포본)를 두라고 정한 자리다. 실제로는 `/var/www`를 쓰는 곳도 많아서 팀마다 하나로 정해 두면 된다. `/boot`에는 커널과 부트로더 파일이 있다. 여기가 차면 커널 업데이트가 실패한다.

요즘 Ubuntu는 `/bin`, `/sbin`, `/lib`가 따로 있지 않다. `/usr` 아래로 합치고 옛 경로는 링크로 남겼다(usr merge).

```bash
# 옛 경로가 /usr 아래를 가리키는 링크인지 본다
ls -ld /bin /sbin /lib
```

```text
lrwxrwxrwx   1 root root     7 Apr 22  2024 /bin -> usr/bin
lrwxrwxrwx   1 root root     7 Apr 22  2024 /lib -> usr/lib
lrwxrwxrwx   1 root root     8 Apr 22  2024 /sbin -> usr/sbin
```

맨 앞 글자 `l`이 심볼릭 링크라는 뜻이다. 그래서 스크립트 첫 줄을 `#!/bin/bash`로 쓰든 `#!/usr/bin/bash`로 쓰든 같은 파일이 실행된다.

## /proc와 /sys는 디스크에 없다

그림에서 오른쪽 아래만 점선으로 그렸다. `/proc`, `/sys`, `/dev`는 디스크에 저장된 파일이 아니라 커널이 지금 상태를 파일 모양으로 보여 주는 창이다. 파일 시스템 종류를 물어보면 바로 드러난다.

```bash
# 각 경로가 어떤 파일 시스템 위에 있는지 본다
stat -f -c '%T' /proc /sys /dev/shm /tmp
```

```text
proc
sysfs
tmpfs
ext2/ext3
```

`/proc`는 procfs, `/sys`는 sysfs, `/dev/shm`은 메모리 위의 tmpfs이고, `/tmp`만 진짜 디스크(ext4)다. `stat`은 ext 계열을 구분하지 않고 `ext2/ext3`이라고만 찍는다.

`/proc`에서 실무에 자주 여는 파일은 몇 개 안 된다.

```bash
# 1분·5분·15분 평균 부하, 실행 중/전체 태스크 수, 마지막 PID
cat /proc/loadavg

# 메모리 총량과 남은 양 (free 명령이 여기서 읽는다)
head -3 /proc/meminfo

# 지금 이 셸(self)이 열어 둔 파일 디스크립터
ls -l /proc/self/fd
```

```text
0.97 2.16 2.12 5/137 26367
MemTotal:       16477348 kB
MemFree:        12401428 kB
MemAvailable:   15111112 kB
total 0
lr-x------ 1 root root 64 Oct 24 00:08 0 -> /dev/null
l-wx------ 1 root root 64 Oct 24 00:08 1 -> pipe:[115933]
l-wx------ 1 root root 64 Oct 24 00:08 2 -> pipe:[115933]
lr-x------ 1 root root 64 Oct 24 00:08 3 -> /proc/26365/fd
```

메모리가 부족한지 볼 때는 `MemFree`가 아니라 `MemAvailable`을 본다. 페이지 캐시처럼 필요하면 비울 수 있는 메모리까지 셈한 값이라서, 이 서버는 남은 게 12GB가 아니라 15GB쯤이다. `top`, `ps`, `free` 같은 명령도 결국 `/proc/{PID}/` 아래 파일을 읽어서 보여 준다. 프로세스 쪽은 [프로세스와 시그널 글](/posts/linux-processes-signals)에서 더 본다.

`/sys`는 장치와 커널 설정을 계층으로 보여 주고, 일부 파일은 써서 값을 바꿀 수도 있다. `/dev`에는 장치 파일이 있다. 출력을 버릴 때 쓰는 `/dev/null`, 디스크 `/dev/vda`나 `/dev/nvme0n1`이 여기 있다. `/proc/sys/` 아래 값을 바꾸는 커널 튜닝은 [네트워크 튜닝 글](/posts/linux-network-tuning)에서 다룬다.

## /tmp는 언제 비워지나

"/tmp는 재부팅하면 지워진다"는 말은 반만 맞다. 누가 언제 지우는지는 systemd-tmpfiles 설정에 적혀 있다.

```bash
# Ubuntu가 /tmp와 /var/tmp를 어떻게 청소하는지 본다
cat /usr/lib/tmpfiles.d/tmp.conf
```

```text
# See tmpfiles.d(5) for details

# Clear tmp directories separately, to make them easier to override
D /tmp 1777 root root 30d
#q /var/tmp 1777 root root 30d
```

`D`는 부팅할 때 그 디렉터리 안을 비우라는 뜻이다. 마지막 칸 `30d`는 나이 기준이다. `systemd-tmpfiles-clean.timer`가 하루에 한 번쯤 돌면서 30일 넘게 쓰지 않은 파일을 지운다. 그러니 Ubuntu 24.04에서 `/tmp`는 재부팅 때도 비워지고, 재부팅하지 않아도 오래된 파일은 사라진다. `/var/tmp` 줄은 주석 처리돼 있어서 Ubuntu 기본값으로는 재부팅에도 남는다. 재부팅 뒤에도 필요한 임시 파일은 `/var/tmp`에 두라는 FHS의 구분과 맞는다.

Ubuntu 24.04의 `/tmp`는 위에서 본 것처럼 기본적으로 디스크 위에 있다. 배포판에 따라 `/tmp`를 메모리(tmpfs)에 올리는 곳도 있고(Debian 13이 그렇게 바꿨다), 그러면 큰 파일을 `/tmp`에 풀다가 메모리를 먹는다. 처음 보는 서버면 `stat -f`나 `df -h /tmp`로 먼저 확인한다.

헷갈리는 장면이 하나 더 있다. 서비스가 `/tmp`에 남긴 파일이 셸에서 보이지 않는다. systemd 유닛에 `PrivateTmp=yes`가 있으면 그 서비스는 자기만의 `/tmp`를 따로 받는다. 파일은 실제로 `/tmp/systemd-private-...` 아래에 있다. 유닛 설정은 [systemd 글](/posts/linux-systemd-systemctl)에서 본다.

## 돌아다니고 둘러보기

이제 명령이다. 처음 들어간 서버에서 하는 일은 대개 이 정도다.

```bash
# 지금 어디 있는지
pwd

# 설정 디렉터리로 가서 둘러본다. -l 자세히, -a 숨김 파일 포함, -h 사람이 읽는 크기
cd /etc/nginx && ls -lah

# 방금 있던 디렉터리로 돌아간다 (cd -), 홈으로 간다 (cd 또는 cd ~)
cd -
cd

# 로그 디렉터리를 수정 시각 순으로, 가장 최근 것이 맨 아래에 오게
ls -ltr /var/log | tail -5

# 디렉터리 안이 아니라 디렉터리 자체의 정보를 본다
ls -ld /var/log
```

`ls -ltr`의 `-t`는 수정 시각 순, `-r`은 거꾸로라서 방금 쓴 로그가 화면 맨 아래, 프롬프트 바로 위에 온다. 로그 디렉터리에서 가장 손이 많이 가는 조합이다. `ls -d`를 빼고 `ls -l /var/log`를 치면 디렉터리 안 목록이 나오고, 디렉터리 자체의 권한은 보이지 않는다. 권한 문제를 볼 때 자주 하는 실수다.

## 만들고 복사하기

```bash
# 중간 디렉터리까지 한 번에 만든다. 이미 있어도 에러를 내지 않는다
mkdir -p /srv/app/releases/2026-10-24

# 빈 파일을 만들거나, 이미 있으면 수정 시각만 지금으로 바꾼다
touch /srv/app/releases/2026-10-24/.keep

# 디렉터리를 통째로 복사하되 시각·권한·소유자·링크를 그대로 보존한다
sudo cp -a /etc/nginx /etc/nginx.bak-20261024
```

`mkdir -p`는 스크립트에서 특히 좋다. 두 번 돌려도 같은 결과가 나와서 배포 스크립트가 "이미 있다"는 에러로 멈추지 않는다.

`cp -r`과 `cp -a`의 차이는 복사본을 보면 바로 보인다. 수정 시각을 올해 1월 2일로 맞춘 설정 파일과 그 파일을 가리키는 링크를 두 방식으로 복사했다.

```bash
cp -r src dst1   # 재귀 복사만
cp -a src dst2   # 보존 복사
ls -l --time-style=long-iso src dst1 dst2
```

```text
dst1:
total 4
-rw-r----- 1 root root 3 2026-10-24 00:08 app.conf
lrwxrwxrwx 1 root root 8 2026-10-24 00:08 current.conf -> app.conf

dst2:
total 4
-rw-r----- 1 root root 3 2026-01-02 03:04 app.conf
lrwxrwxrwx 1 root root 8 2026-10-24 00:08 current.conf -> app.conf

src:
total 4
-rw-r----- 1 root root 3 2026-01-02 03:04 app.conf
lrwxrwxrwx 1 root root 8 2026-10-24 00:08 current.conf -> app.conf
```

`cp -r`의 복사본은 수정 시각이 복사한 순간으로 바뀌었고, `cp -a`는 원본의 `2026-01-02 03:04`를 지켰다. 이 실험은 root로 해서 소유자 차이는 안 보이지만, 일반 사용자가 `cp -r`로 남의 파일을 복사하면 소유자도 자기로 바뀐다. 설정 백업은 "언제 마지막으로 고쳤나"가 중요한 정보라서 `-a`로 뜬다. `-a`는 `-dR --preserve=all`과 같다.

복사 대상 디렉터리가 이미 있으면 동작이 달라지는 것도 알아 둔다. `cp -r src dst`에서 `dst`가 없으면 `dst`가 `src`의 복사본이 되고, 있으면 `dst/src`가 생긴다. 같은 명령을 두 번 돌리면 결과가 달라지는 셈이다. 스크립트에서는 `cp -a src/. dst/`처럼 "안에 든 것을 복사"라고 적으면 두 경우가 같아진다.

## 같은 디스크 안에서 mv는 이름만 바꾼다

200MB짜리 파일을 같은 디스크의 다른 디렉터리로 옮기고, 이어서 메모리 위의 `/dev/shm`으로 옮겼다. `strace`로 `mv`가 커널에 무엇을 부탁하는지 같이 봤다.

```bash
# 200MB 파일을 만든다
dd if=/dev/zero of=big.bin bs=1M count=200 status=none

# 같은 파일 시스템 안에서 옮길 때 시스템 콜을 본다
strace -e trace=renameat2,copy_file_range,unlinkat mv big.bin d1/

# 다른 파일 시스템(/dev/shm, tmpfs)으로 옮길 때
strace -e trace=renameat2,copy_file_range,unlinkat mv big2.bin /dev/shm/
```

```text
renameat2(AT_FDCWD, "big.bin", AT_FDCWD, "d1/", RENAME_NOREPLACE) = -1 EEXIST (File exists)
renameat2(AT_FDCWD, "big.bin", 3, "big.bin", RENAME_NOREPLACE) = 0
```

```text
renameat2(AT_FDCWD, "big2.bin", AT_FDCWD, "/dev/shm/", RENAME_NOREPLACE) = -1 EXDEV (Invalid cross-device link)
renameat2(AT_FDCWD, "big2.bin", 3, "big2.bin", RENAME_NOREPLACE) = -1 EXDEV (Invalid cross-device link)
unlinkat(3, "big2.bin", 0)              = -1 ENOENT (No such file or directory)
copy_file_range(4, NULL, 5, NULL, 9223372035781033984, 0) = -1 EXDEV (Invalid cross-device link)
unlinkat(AT_FDCWD, "big2.bin", 0)       = 0
```

첫 번째 줄의 `EEXIST`는 `d1/`이라는 이름 자체로 바꾸려다 이미 있는 디렉터리라 실패한 것이고, 두 번째에 `d1` 안의 `big.bin`으로 바꾸는 데 성공(`= 0`)했다. 시스템 콜 하나로 끝났다. 두 번째 경우는 `rename`이 `EXDEV`(다른 장치라서 이름만 바꿀 수 없다)로 실패하자, `mv`가 복사로 방향을 바꾸고 다 복사한 뒤 원본을 지웠다(`unlinkat ... = 0`). 걸린 시간도 0.002초와 0.137초로 차이가 난다. 파일이 수십 GB면 이 차이가 분 단위가 된다.

같은 파일 시스템 안의 `rename`은 원자적이다. 새 이름을 여는 쪽은 옛 파일이나 새 파일 중 하나만 보고, 반쯤 바뀐 상태는 보지 않는다. 이 성질 덕분에 배포에서 자주 쓰는 방법이 있다. 새 버전 디렉터리를 다 준비한 뒤 `current` 링크만 갈아 끼우는 것이다.

```bash
# 새 링크를 임시 이름으로 만든 다음, rename 한 번으로 current를 바꿔 끼운다
ln -s /srv/app/releases/2026-10-24 /srv/app/current.tmp
mv -T /srv/app/current.tmp /srv/app/current
```

`-T`는 `current`가 디렉터리를 가리키는 링크여도 "그 안으로 옮기기"가 아니라 "그 이름을 덮어쓰기"로 처리하라는 옵션이다. 빠뜨리면 `current/current.tmp`가 생긴다. `ln -sfn`으로 바로 바꿔도 Ubuntu 24.04의 coreutils 9.4는 `strace`로 보면 임시 이름에 링크를 만들고 `renameat`으로 덮어써서 원자적이었다. 옛 버전은 지우고 다시 만드는 방식이라 링크가 없는 짧은 순간이 있었으니, 버전에 기대지 않으려면 위처럼 `mv -T`를 쓴다.

같은 이유로 설정 파일을 고칠 때도 "임시 파일에 다 쓰고 rename"이 안전하다. 같은 디렉터리(같은 파일 시스템)에 임시 파일을 만들어야 이 성질이 지켜진다. 임시 파일을 `/tmp`에 쓰고 `/etc`로 옮기면 파일 시스템이 다를 수 있고, 그러면 복사가 된다.

## 파일을 읽는 세 가지 방법

`cat`은 파일 전체를 한 번에 화면에 쏟는다. 짧은 설정 파일에만 쓴다. 수백 MB짜리 로그에 `cat`을 치면 터미널이 한참 멈춘다.

긴 파일은 `less`로 연다. 파일을 한 화면씩만 읽어서 크기와 상관없이 바로 열린다.

```bash
# 로그를 연다. 안에서 /단어 로 찾고 n으로 다음, G로 끝, g로 처음
less /var/log/nginx/error.log

# 긴 줄을 접지 않고 옆으로 스크롤 (-S), 색 코드를 해석 (-R)
less -SR /var/log/syslog

# 끝에서 시작해 새 줄을 계속 따라간다. Ctrl+C로 멈추면 다시 탐색할 수 있다
less +F /var/log/nginx/access.log

# 압축된 지난 로그도 풀지 않고 본다
zless /var/log/nginx/access.log.2.gz
```

새로 쌓이는 줄만 보고 싶으면 `tail -f`를 쓰는데, 로그 회전을 겪는 파일이면 `tail -F`가 낫다. `-f`는 처음 연 파일을 끝까지 붙잡고 있어서, logrotate가 파일 이름을 바꾸고 새 파일을 만들면 옛 파일만 보고 멈춘다. `-F`는 이름을 기준으로 다시 열어 준다. systemd가 관리하는 서비스의 로그는 파일이 아니라 저널에 있을 수 있어서 `journalctl -u nginx -f`로 본다. 로그 안에서 원하는 줄을 걸러 내는 방법은 [grep·awk·sed 글](/posts/linux-grep-awk-sed)에 있다.

## find로 조건을 걸어 찾는다

디스크를 정리하라는 부탁을 받았다고 하자. 30일 넘은 회전 로그를 찾는다. 실습용 디렉터리에 이름에 공백이 있는 파일까지 섞어 두고 두 개만 40일 전으로 시각을 돌렸다.

```bash
# logs 아래에서 이름이 *.log* 이고 수정한 지 30일이 넘은 파일
find logs -name '*.log*' -mtime +30
```

```text
logs/old access.log
logs/a.log.1
```

`find`는 "어디서" 다음에 조건을 줄줄이 적는 구조다. 조건은 기본으로 AND로 묶인다. 실무에서 자주 쓰는 것만 추리면 이렇다.

```bash
# 일반 파일만, 100MB보다 큰 것, 같은 파일 시스템 안에서만 (-xdev: 다른 마운트로 넘어가지 않음)
sudo find /var -xdev -type f -size +100M

# 최근 10분 안에 바뀐 설정 파일 (누가 뭘 고쳤나)
sudo find /etc -type f -mmin -10

# 바로 아래 한 단계만 본다
find /srv/app/releases -mindepth 1 -maxdepth 1 -type d

# node_modules 안으로는 들어가지 않고 .env 파일을 찾는다
find /srv -path '*/node_modules' -prune -o -name '.env' -print
```

`-mtime +30`은 숫자를 조심해서 읽어야 한다. `find`는 지난 시간을 24시간 단위로 잘라 버린 값과 비교한다. 그래서 `+30`은 "30일을 조금이라도 넘긴 것"이 아니라 "잘라서 31일 이상인 것"이다. 정확히 30일 하고 반나절 된 파일은 걸리지 않는다. 시간 단위로 정확히 끊고 싶으면 `-mmin +43200`처럼 분으로 쓴다.

`-xdev`는 `/var`를 뒤질 때 그 안에 마운트된 다른 디스크(백업 볼륨, NFS)까지 내려가지 않게 막는다. 네트워크 디스크를 실수로 전부 훑으면 몇 시간이 걸린다.

## -exec, xargs, 그리고 공백이 든 파일 이름

찾은 파일에 명령을 걸 때 방법이 셋 있다. 같은 두 파일에 `ls -l`을 걸어 봤다.

```bash
# 1) find의 출력을 그대로 xargs에 넘긴다
find logs -name '*.log*' -mtime +30 | xargs ls -l

# 2) 이름을 NUL 문자로 끊어서 넘긴다
find logs -name '*.log*' -mtime +30 -print0 | xargs -0 ls -l

# 3) find가 직접 실행한다
find logs -name '*.log*' -mtime +30 -exec ls -l {} +
```

```text
ls: cannot access 'logs/old': No such file or directory
ls: cannot access 'access.log': No such file or directory
-rw-r--r-- 1 root root 0 Sep 14 00:08 logs/a.log.1
```

```text
-rw-r--r-- 1 root root 0 Sep 14 00:08 logs/a.log.1
-rw-r--r-- 1 root root 0 Sep 14 00:08 logs/old access.log
```

첫 번째는 망가졌다. `xargs`는 기본으로 공백과 줄바꿈에서 인자를 끊어서 `logs/old access.log`가 `logs/old`와 `access.log` 두 개가 됐다. `ls`라서 에러로 끝났지만 `rm`이었다면 엉뚱한 이름의 파일을 지울 수도 있다. 파일 이름에는 `/`와 NUL(값이 0인 바이트)을 빼고 무엇이든, 줄바꿈까지 들어갈 수 있다. 그래서 끊는 글자로 안전한 건 NUL 하나뿐이고, `-print0 | xargs -0`이 그 짝이다. 두 번째와 세 번째는 같은 결과를 냈다.

`-exec`도 끝을 무엇으로 맺느냐에 따라 다르다. `\;`는 파일 하나마다 명령을 한 번씩, `+`는 파일을 모아서 가능한 한 적게 실행한다. 파일 24개에 `/usr/bin/true`를 걸고 `execve`(프로그램 실행) 횟수를 셌다.

```bash
strace -f -c -e trace=execve find logs -type f -exec /usr/bin/true {} \;
strace -f -c -e trace=execve find logs -type f -exec /usr/bin/true {} +
```

```text
100.00    0.000976          39        25           execve
  0.00    0.000000           0         2           execve
```

`\;`는 `find` 자신 1번에 파일마다 1번씩 25번, `+`는 2번이다. 파일이 수십만 개면 이 차이가 몇 분이 된다. `xargs`가 더 나은 건 `-P 4`처럼 병렬로 돌리고 싶을 때 정도다. 그냥 지우기만 할 거면 `find ... -delete`가 가장 짧다. 다만 `-delete`는 맨 뒤에 둔다. `find . -delete -name '*.log'`처럼 앞에 두면 조건을 보기 전에 전부 지운다.

## rm -rf에 빈 변수가 들어가면

`rm`에는 휴지통이 없다. 지우면 끝이다. 그중에서도 가장 흔한 사고는 경로를 변수로 받는 스크립트에서 난다.

```bash
#!/usr/bin/env bash
BUILD_DIR="$1"
rm -rf "$BUILD_DIR/"*
```

인자를 깜빡하고 이 스크립트를 실행하면 무슨 일이 생기는지, `rm` 대신 `echo`로 바꿔서 돌려 봤다.

```text
would run: rm -rf /*
```

아래 그림에서 다음을 누르면 bash가 이 한 줄을 어떻게 고쳐 쓰는지 보인다.

GNU `rm`은 기본으로 `--preserve-root`가 켜져 있어서 `rm -rf /`는 거절한다. 하지만 `/*`는 글롭이 펼쳐진 뒤의 `/bin`, `/etc` 같은 개별 경로라서 이 보호에 걸리지 않는다. 실제로 2015년 Steam 리눅스 클라이언트의 정리 스크립트가 이 모양의 줄 때문에 사용자의 파일을 지운 일이 있었다.

<Callout kind="warning">
  경로를 변수로 받는 `rm -rf`는 변수가 비거나 오타가 났을 때 무엇을 지울지 먼저 따져 본다. 처음 돌릴 때는 `rm`을 `echo`로 바꿔서 펼쳐진 인자를 눈으로 확인하고, 운영 서버라면 지우기 전에 `ls`로 대상 목록부터 본다.
</Callout>

막는 장치는 여러 겹으로 건다.

```bash
#!/usr/bin/env bash
set -euo pipefail                      # -u: 정의 안 된 변수를 쓰면 바로 멈춘다

BUILD_DIR="${1:?빌드 디렉터리를 인자로 주세요}"   # 비어 있으면 메시지를 찍고 멈춘다

# 지우는 줄에서도 한 번 더. -- 뒤는 옵션으로 읽지 않는다 (이름이 -로 시작해도 안전)
rm -rf -- "${BUILD_DIR:?}/"*
```

인자 없이 돌리면 `rm`까지 가지 못하고 멈춘다. 변수 이름에 오타를 낸 경우는 `set -u`가 잡는다.

```text
c2.sh: line 3: 1: 빌드 디렉터리를 인자로 주세요
exit=1
```

```text
c3.sh: line 3: BUILD_DIRR: unbound variable
exit=1
```

`${VAR:?}`는 비었거나 정의되지 않았으면 에러를 내고 멈추는 매개변수 확장이다. 확장 문법 전체는 [bash 확장 글](/posts/bash-expansions-variables)에 있다. `"$dir/"*` 대신 `find "$dir" -mindepth 1 -delete`를 쓰면 글롭이 펼쳐지지 않아서 숨김 파일까지 같은 규칙으로 지워지고, 인자 개수 제한(`Argument list too long`)에도 걸리지 않는다.

`rmdir`은 빈 디렉터리만 지운다. 안에 뭔가 남아 있으면 `Directory not empty`로 거절하니, "비었을 것"이라고 믿는 디렉터리를 정리할 때는 `rm -r`보다 `rmdir`이 안전한 확인이 된다.

## 현장에서 이 지도를 쓰는 순간

처음 부탁으로 돌아가 보자. 업로드 제한을 고치려면 `/etc/nginx`에서 `grep -rn client_max_body_size /etc/nginx/`로 어느 파일에 있는지부터 찾는다. Ubuntu의 nginx는 `sites-available`에 설정을 두고 `sites-enabled`에 링크를 걸어서 켜는 구조라, 링크가 없는 `sites-available` 파일을 고치면 아무 일도 일어나지 않는다. `ls -l /etc/nginx/sites-enabled/`로 화살표가 어디를 가리키는지 본다. 고치기 전에 `sudo cp -a`로 백업하고, `sudo nginx -t`로 문법을 확인한 뒤 다시 읽힌다.

디스크 경보가 오면 `/var`부터 본다.

```bash
# /var 안에서 같은 디스크에 있는 것만, 큰 순서로 위 10개
sudo du -xh --max-depth=2 /var 2>/dev/null | sort -h | tail -10
```

대개 `/var/log`의 회전되지 않은 로그, `/var/lib/docker`의 이미지와 컨테이너 로그, `/var/cache/apt`가 범인이다. `du`로 찾은 크기와 `df`가 말하는 사용량이 다르면 지웠지만 아직 열려 있는 파일이 의심된다. 그 이야기는 [디스크 글의 df와 du 비교](/posts/linux-disks-filesystems)에 있다.

손으로 만든 백업 파일(`nginx.conf.bak`, `nginx.conf.old`)을 `/etc/nginx/conf.d/` 안에 두는 것도 흔한 실수다. 그 디렉터리는 `*.conf`만 읽으니 `.bak`은 괜찮지만, `nginx.conf.bak.conf`처럼 끝이 `.conf`로 끝나면 같은 설정이 두 번 읽혀 `duplicate` 에러가 난다. 백업은 읽히는 디렉터리 밖에 둔다.

## 지도를 외우면 명령이 짧아진다

설정은 `/etc`, 쌓이는 건 `/var`, 깔린 프로그램은 `/usr`와 `/opt`, 커널이 비추는 창은 `/proc`과 `/sys`다. 이걸 알면 처음 보는 서버에서도 찾는 범위가 좁아진다. `mv`는 같은 파일 시스템에서 이름만 바꾸기 때문에 즉시 끝나고 원자적이며, 그 성질이 배포의 링크 교체를 받친다. 이름은 NUL로 끊어야 안전하고, `rm -rf`의 변수는 비었을 때 멈추게 만든다. 다음으로는 셸에서 출력을 이어 붙이는 [리다이렉션과 파이프](/posts/shell-redirection-pipes)를 보면 `find`와 `xargs`를 엮는 방식이 더 잘 보인다.

## 면접에서 나올 만한 질문

### 리눅스에서 /etc, /var, /usr는 각각 무엇을 두는 곳인가요?

`/etc`는 시스템과 서비스의 설정 파일, `/var`는 로그·DB 데이터·캐시·큐처럼 운영 중에 바뀌는 데이터, `/usr`는 패키지 관리자가 설치한 프로그램과 라이브러리다. `/usr`는 읽기 전용에 가깝게 다뤄서 패키지 업데이트가 덮어쓰고, 손으로 빌드한 것은 `/usr/local`, 벤더 묶음은 `/opt`에 둔다. 그래서 디스크가 차면 `/var`, 설정 문제면 `/etc`부터 본다.

### /proc는 무엇이고 왜 디스크 공간을 차지하지 않나요?

커널이 프로세스와 시스템 상태를 파일 모양으로 보여 주는 가상 파일 시스템(procfs)이라서 디스크에 저장된 데이터가 없다. 파일을 읽는 순간 커널이 그 값을 만들어 준다. `top`, `ps`, `free` 같은 도구도 `/proc/{PID}/`와 `/proc/meminfo`를 읽어서 보여 주고, 메모리 여유는 `MemAvailable`을 본다.

### /tmp는 재부팅하면 항상 지워지나요?

배포판 설정에 따라 다르다. Ubuntu 24.04는 `tmpfiles.d`의 `D /tmp ... 30d` 설정으로 부팅할 때 비우고, 재부팅하지 않아도 30일 넘게 쓰지 않은 파일은 정리 타이머가 지운다. `/var/tmp`는 기본으로 재부팅에도 남는다. 또 `/tmp`가 tmpfs인 배포판이면 메모리를 쓰고, 서비스에 `PrivateTmp=yes`가 있으면 그 서비스는 따로 떨어진 `/tmp`를 본다.

### 같은 파일 시스템에서 mv가 큰 파일도 즉시 끝나는 이유는요?

데이터를 옮기지 않고 디렉터리 항목만 바꾸는 `rename` 시스템 콜 하나로 끝나기 때문이다. 파일은 같은 inode를 그대로 쓰고 이름만 다른 디렉터리로 옮겨진다. 다른 파일 시스템이면 커널이 `EXDEV`로 거절하고, `mv`가 내용을 전부 복사한 뒤 원본을 지우므로 크기만큼 시간이 들고 원자적이지도 않다.

### 그 성질을 배포에 어떻게 쓰나요?

새 릴리스 디렉터리를 다 준비한 뒤 `current` 심볼릭 링크를 새 이름으로 만들고 `mv -T`로 덮어써서 교체한다. 같은 파일 시스템 안의 `rename`이라 요청은 옛 버전이나 새 버전 중 하나만 보고, 롤백은 링크를 이전 릴리스로 되돌리면 된다. 설정 파일도 같은 디렉터리의 임시 파일에 다 쓰고 rename해야 반쯤 쓴 파일을 읽는 일이 없다.

### find -exec의 \;와 +, xargs는 어떻게 다르고 무엇을 고르나요?

`\;`는 파일마다 명령을 한 번씩 실행하고, `+`는 파일을 모아 몇 번만 실행해서 훨씬 빠르다. `xargs`는 기본으로 공백과 줄바꿈에서 인자를 끊기 때문에 공백이 든 파일 이름을 망가뜨리고, 반드시 `find -print0 | xargs -0`로 NUL 구분을 써야 한다. 보통은 `-exec ... +`나 `-delete`로 충분하고, 병렬 실행(`-P`)이 필요할 때 `xargs -0`을 쓴다.

### rm -rf "$DIR/"* 같은 줄이 위험한 이유와 막는 방법은요?

`DIR`이 비면 `rm -rf /*`가 되고, 글롭이 펼쳐진 개별 경로라서 `--preserve-root` 보호도 받지 못한다. `set -u`로 정의 안 된 변수를 막고, `${DIR:?}`로 빈 값이면 멈추게 하고, `--`로 옵션 해석을 끊는다. 더 나아가 `realpath`로 경로를 풀어 허락한 디렉터리 아래인지 검사하고, 처음에는 `echo`로 펼쳐진 인자를 확인한다.
