고객 문의 요약 기능을 만들 때 가장 좋은 모델을 붙였다. 품질은 만족스러웠다. 문의 하나에 입력 4,000토큰, 요약 600토큰이고 하루 3만 건이 들어오니, Claude Opus 5.5 정가로 계산하면 하루 $840이었다. 그런데 첫 주 청구서는 하루 평균 $2,340이 찍혔다. 로그를 보니 요약마다 보이지 않는 생각 토큰이 2,500개씩 붙어 있었다. 출력 단가로 청구되는 토큰이다.

그때 처음으로 "이 일에 이 모델이 꼭 필요한가"를 따져 봤다. 이 글은 그 과정을 정리한 것이다. 닫힌 모델과 오픈 웨이트 모델의 차이, 생각하는 모델이 값을 하는 일과 그렇지 않은 일, 단가표를 실제 요청 모양으로 바꿔 읽는 법, 벤치마크 대신 내 시험지로 고르는 법, 작은 모델로 먼저 보내는 라우팅, 그리고 모델을 갈아 끼울 때 생기는 회귀를 차례로 본다.

토큰과 컨텍스트 창, 단가표의 기본 모양은 [LLM 기본기 글](/posts/llm-basics-for-developers)에 있다. 모델을 직접 띄우는 방법과 GPU 메모리 계산은 [LLM 직접 띄우기 글](/posts/self-hosting-llm-inference)로, 후보 모델을 채점하는 시험지 만들기는 [LLM 평가 글](/posts/llm-evals)로 넘긴다. 이 글의 가격은 2026년 10월 Anthropic 공식 정가 기준이고, 자주 바뀌니 쓰기 전에 가격표를 다시 본다.

## 청구서를 요청 한 건으로 쪼개 보기

청구서가 커지면 먼저 요청 한 건의 비용을 분해한다. 비용은 입력 토큰 × 입력 단가 + 출력 토큰 × 출력 단가다. 생각(thinking) 토큰은 출력으로 센다. 처음 장면을 그대로 넣어 계산했다.

```text
모델              입력   출력(생각 포함)   한 건       하루 3만 건   30일
Opus 5.5          4000   600              $0.02800    $840.00      $25,200
Opus 5.5 + 생각   4000   3100             $0.07800    $2,340.00    $70,200
Sonnet 5.5        4000   600              $0.01400    $420.00      $12,600
Haiku 5.5         4000   600              $0.00070    $21.00       $630
```

단가는 100만 토큰당 Opus 5.5 입력 $4·출력 $20, Sonnet 5.5 $2·$10, Haiku 5.5 $0.10·$0.50이다. Haiku 5.5는 프롬프트가 10만 토큰을 넘으면 $0.50·$2.50으로 올라가니, 긴 문서를 통째로 넣는 일이면 그 구간으로 계산해야 한다.

두 가지가 눈에 들어온다. 하나는 생각 토큰이다. 600토큰짜리 요약에 2,500토큰을 생각하면 출력 비용이 다섯 배를 넘는다. 다른 하나는 같은 공급사 안에서도 가장 비싼 줄과 가장 싼 줄이 100배 넘게 벌어진다는 것이다. 요약처럼 정답의 폭이 넓은 일에서 이 차이를 품질로 메울 수 있는지가 모델 선택의 출발점이다.

이 분해는 손댈 곳도 알려 준다. 입력 4,000토큰 중 3,000토큰이 매번 같은 시스템 프롬프트와 예시라면 프롬프트 캐시로 읽을 수 있다. Opus 5.5의 캐시 읽기 단가는 100만 토큰당 $0.20이라서 입력 비용이 $0.016에서 1,000 × $4 + 3,000 × $0.20 = $0.0046으로 내려간다(처음 한 번은 캐시 쓰기 비용이 더 든다). 결과를 몇 시간 뒤에 받아도 되는 대량 요약이면 배치 API로 보내 절반 가격을 받는다. 모델을 바꾸기 전에 이 두 가지부터 확인한다. 품질을 건드리지 않고 깎는 돈이다.

### 요청마다 비용을 남겨 둔다

이 분해를 매번 손으로 할 수는 없다. 응답의 `usage`를 기능 이름(route)과 함께 남기고, 단가표를 곱해 달러로 바꿔 두면 "어느 기능이 돈을 쓰는가"가 대시보드에 바로 보인다. 처음 장면의 세 가지 요청 모양을 넣어 돌려 봤다.

```js
// cost-log.mjs: usage 한 건을 달러로 바꾼다
const PRICE = {               // 100만 토큰당 달러: [입력, 출력, 캐시 읽기]
  "claude-opus-5-5":  [4.0, 20.0, 0.20],
  "claude-haiku-5-5": [0.10, 0.50, null], // 이 경로는 캐시를 안 쓴다
};

function costOf(model, usage) {
  const [inP, outP, cacheP] = PRICE[model];
  const cached = usage.cache_read_input_tokens ?? 0;
  return (usage.input_tokens * inP + cached * (cacheP ?? inP) + usage.output_tokens * outP) / 1e6;
}

const samples = [
  { route: "summary", model: "claude-opus-5-5",  usage: { input_tokens: 4000, output_tokens: 3100 } },
  { route: "summary", model: "claude-opus-5-5",  usage: { input_tokens: 1000, cache_read_input_tokens: 3000, output_tokens: 700 } },
  { route: "summary", model: "claude-haiku-5-5", usage: { input_tokens: 4000, output_tokens: 600 } },
];

for (const s of samples) {
  console.log(s.route, s.model, JSON.stringify(s.usage), "$" + costOf(s.model, s.usage).toFixed(5));
}
```

```text
summary claude-opus-5-5 {"input_tokens":4000,"output_tokens":3100} $0.07800
summary claude-opus-5-5 {"input_tokens":1000,"cache_read_input_tokens":3000,"output_tokens":700} $0.01860
summary claude-haiku-5-5 {"input_tokens":4000,"output_tokens":600} $0.00070
```

두 번째 줄은 같은 Opus 5.5에 캐시를 맞추고 effort를 낮춰 생각 토큰이 100개로 줄었다고 가정한 모양이다. 모델을 바꾸지 않고도 한 건이 $0.078에서 $0.0186으로 내려간다. `input_tokens`는 캐시로 읽지 않은 부분만 센다는 점을 기억해 둔다. 캐시 읽기 토큰을 따로 더하지 않으면 비용을 적게 잡는다. 단가표는 코드에 박지 말고 설정으로 빼 둔다. 가격이 바뀌면 지난 로그를 다시 계산해야 할 때도 있다.

## 닫힌 모델과 오픈 웨이트 모델

모델은 가중치(학습으로 정해진 숫자 덩어리)를 받을 수 있느냐로 크게 나뉜다.

닫힌 모델은 가중치를 공개하지 않고 API로만 쓴다. Anthropic의 Claude, OpenAI의 GPT와 o 계열, Google의 Gemini가 여기에 든다. Cohere의 Command 계열도 API가 주력인데, Cohere는 검색용 임베딩과 리랭크 모델로 더 많이 쓰인다. 공급사가 GPU와 운영을 맡고 우리는 토큰만큼 낸다. 가장 높은 성능이 보통 이쪽에서 먼저 나온다.

오픈 웨이트 모델은 가중치 파일을 내려받아 직접 돌릴 수 있다. Meta의 Llama, Alibaba의 Qwen, Mistral, Google의 Gemma, DeepSeek가 대표적이다. "오픈 소스"라고 부르는 일이 많지만, 학습 데이터와 학습 코드까지 공개된 경우는 드물어서 "오픈 웨이트"가 정확한 말이다. 같은 모델을 여러 클라우드 업체가 API로도 판다. 그래서 오픈 웨이트라고 꼭 직접 띄워야 하는 건 아니다.

둘 사이를 다섯 가지로 비교하면 아래와 같다.

| 기준 | 닫힌 모델 API | 오픈 웨이트 직접 운영 |
|---|---|---|
| 라이선스 | 이용 약관 하나 | 모델마다 다름(Apache 2.0, MIT, 공급사 자체 라이선스) |
| 데이터 반출 | 공급사 서버로 나간다. 보존 기간·지역은 계약과 설정으로 정한다 | 우리 네트워크 밖으로 안 나간다 |
| 비용 | 쓴 토큰만큼. 쓰지 않으면 0 | GPU 시간만큼. 놀아도 나간다 |
| 지연 | 공급사 부하에 따라 흔들린다 | 직접 조절하지만 GPU를 꽉 채우면 느려진다 |
| 품질 | 같은 시기 기준 최상위가 대체로 이쪽 | 격차가 줄었지만 일에 따라 다르다 |

라이선스는 "오픈"이라는 이름만 믿고 넘어가기 쉬운 곳이다. Llama는 월간 활성 사용자 7억 명을 넘는 서비스에 별도 허가를 요구하는 커뮤니티 라이선스를 쓰고, Gemma는 금지 용도 목록이 붙은 자체 약관을 쓴다. Qwen과 Mistral은 모델마다 Apache 2.0인 것과 아닌 것이 섞여 있다. 버전이 바뀌면서 라이선스가 바뀐 모델도 있으니 모델 카드가 아니라 저장소의 LICENSE 원문을 본다. 자세한 확인 항목은 [LLM 직접 띄우기 글](/posts/self-hosting-llm-inference)에 있다.

데이터 반출은 법무와 보안 팀이 가장 먼저 묻는 질문이다. 닫힌 모델이라고 다 안 되는 건 아니다. 대부분의 공급사는 API로 들어온 데이터를 기본적으로 학습에 쓰지 않는다고 약관에 적고, 보존 기간을 줄이거나 없애는 계약(zero data retention)과 처리 지역을 정하는 옵션을 둔다. AWS Bedrock, Google Vertex AI, Azure 같은 클라우드를 거쳐 쓰면 이미 계약한 클라우드 안에서 처리된다는 점 때문에 승인이 쉬워지는 경우가 많다. 이 모든 걸로도 안 되는 데이터(병원 기록, 망 분리 환경)일 때 오픈 웨이트 직접 운영이 유일한 답이 된다.

## 생각하는 모델은 언제 값을 하나

요즘 큰 모델은 답을 쓰기 전에 생각 토큰을 만든다. 공급사마다 이름과 손잡이가 다르다. OpenAI의 o 계열과 GPT-5 계열은 `reasoning_effort`, Gemini 2.5 계열은 생각 토큰 예산, Claude는 적응형 생각(adaptive thinking)과 `effort`로 조절한다. Claude Opus 5.5는 생각을 끌 수 없고, `effort`가 기본 `medium`이며 `low`부터 `max`까지 고른다. 손잡이 이름은 모델 세대마다 바뀌어 왔으니 쓰는 모델의 문서를 확인한다.

```ts
// 같은 모델에서 일의 성격에 따라 생각의 깊이만 바꾼다 (@anthropic-ai/sdk)
const summary = await client.messages.create({
  model: "claude-opus-5-5",
  max_tokens: 2000,
  output_config: { effort: "low" },     // 요약: 생각을 짧게
  messages: [{ role: "user", content: ticketText }],
});

const refundDecision = await client.messages.create({
  model: "claude-opus-5-5",
  max_tokens: 16000,
  output_config: { effort: "high" },    // 환불 규정 여러 개를 따져야 하는 판단
  messages: [{ role: "user", content: caseText }],
});

console.log(summary.usage.output_tokens, refundDecision.usage.output_tokens);
```

생각이 값을 하는 일에는 공통점이 있다. 중간 단계가 틀리면 답이 틀리는 일이다. 여러 조건을 동시에 맞춰야 하는 판단, 계산, 코드 수정, 여러 도구를 거치는 작업이 그렇다. 이런 일에서는 생각 토큰을 아끼다가 재시도가 늘어 오히려 비싸진다. 반대로 요약, 분류, 형식 바꾸기, 짧은 추출처럼 읽고 바로 쓰면 되는 일은 생각을 길게 해도 결과가 거의 안 바뀐다. 생각 자체를 프롬프트로 유도하던 기법과 추론 모델에서 그 효과가 줄어든 이유는 [생각을 시키는 프롬프트 글](/posts/prompt-reasoning-techniques)에서 다룬다.

지연도 따진다. 생각 토큰도 하나씩 만들어야 하니 첫 글자가 늦게 나온다. 사용자가 화면 앞에서 기다리는 채팅이면 생각이 2,500토큰 붙을 때 그만큼 빈 화면이 길어진다. 스트리밍으로 생각 요약이나 진행 메모를 보여 주는 방법도 있지만, 기다림 자체가 줄지는 않는다.

처음 장면의 요약 기능은 결국 같은 모델에서 `effort`를 `low`로 내려 비교하는 것부터 했다. 공급사 문서도 모델을 바꾸기 전에 가장 좋은 모델을 낮은 effort로 먼저 재 보라고 권한다. 모델 하나를 유지하면 프롬프트와 캐시도 하나로 간다.

## 벤치마크 점수로 고르지 않는다

모델이 나올 때마다 MMLU, GPQA, SWE-bench 같은 점수표가 따라온다. 이 숫자로 후보를 추리는 건 괜찮지만 최종 선택에 쓰면 틀리기 쉽다. 이유가 몇 가지 있다.

첫째, 시험 문제가 학습 데이터에 섞였을 수 있다(오염). 공개된 지 오래된 벤치마크일수록 그렇다. 둘째, 점수표는 공급사가 고른 프롬프트와 설정으로 잰 값이다. 같은 모델도 퓨샷 예시 개수, 생각 설정, 답 추출 방식에 따라 점수가 꽤 움직인다. 셋째, 상위권 모델들이 90점대에 몰려 있으면 1~2점 차이는 우리 일에서 의미가 없다. 넷째, 가장 중요한데, 벤치마크는 우리 일이 아니다. 대학원 물리 문제를 잘 푸는 모델이 한국어 상담 요약을 잘한다는 보장이 없다.

그래서 우리 일로 시험지를 만든다. 실제 문의 100~300건에 사람이 좋은 요약 기준(빠뜨리면 안 되는 항목, 길이, 말투)을 적어 두고, 후보마다 같은 프롬프트로 돌려 채점한다. 채점 방법과 채점관 보정은 [LLM 평가 글](/posts/llm-evals)에 있다. 점수 옆에 한 건 비용과 p95 지연을 함께 적는다. 표가 이렇게 생겨야 고를 수 있다.

```text
후보                    통과율   한 건 비용   p95 지연   비고
Opus 5.5 effort=high    ...      $0.07800     ...       현재 운영
Opus 5.5 effort=low     ...      ...          ...
Sonnet 5.5              ...      ...          ...
Haiku 5.5               ...      ...          ...
```

빈칸은 내 시험지를 돌려서 채운다. 표를 보고 정하는 규칙도 미리 적어 둔다. 예를 들면 "통과율이 현재 모델보다 2%p 넘게 떨어지지 않는 후보 중 가장 싼 것"이다. 기준을 결과를 본 뒤에 정하면 마음에 드는 모델 쪽으로 기준이 움직인다.

시험지가 작으면 통과율 차이가 우연일 수 있다는 것도 기억한다. 100건에서 96%와 93%는 세 건 차이다. 같은 문항에서 두 모델이 어디서 갈렸는지 짝지어 보는 방법은 평가 글에서 다룬다.

## 작은 모델로 먼저 보내기

시험지를 돌려 보면 보통 이런 결과가 나온다. 작은 모델이 쉬운 문의 대부분은 큰 모델만큼 처리하고, 어려운 일부에서만 크게 틀린다. 그러면 모든 요청을 큰 모델로 보낼 이유가 없다. 요청을 나눠 보내는 방법이 두 가지 있다.

라우팅은 요청을 보기 전에 정한다. 문의 길이, 카테고리, 첨부 유무, 고객 등급 같은 규칙으로 갈 곳을 고르거나, 아주 싼 분류 모델에게 "쉬움/어려움"을 먼저 묻는다. 요청당 모델 호출은 한 번(분류까지 치면 한 번 반)이다.

캐스케이드는 일단 작은 모델에 보내고, 결과를 보고 넘긴다. 작은 모델의 답이 형식 검사를 통과하지 못하거나, 필수 항목이 빠졌거나, 모델 스스로 "확신 낮음"을 표시하면 큰 모델로 다시 보낸다. 아래 그림에서 점이 흐르는 방향을 보면 대부분은 왼쪽 아래 길로 끝나고, 일부만 오른쪽 위로 올라간다.

넘어간 요청은 작은 모델 값과 큰 모델 값을 둘 다 낸다. 그래도 싸다. 큰 모델(생각 포함) 한 건이 $0.078, 작은 모델 한 건이 $0.0007일 때, 넘어가는 비율을 p라고 하면 한 건 평균은 $0.0007 + p × $0.078이다.

```text
넘어가는 비율   한 건 평균    하루 3만 건   큰 모델만 쓸 때 대비
10%            $0.00850      $255.00       10.9%
20%            $0.01630      $489.00       20.9%
30%            $0.02410      $723.00       30.9%
```

작은 모델이 이만큼 싸면 손해가 나는 지점은 p가 99.1%를 넘을 때다. 사실상 비용으로는 늘 이긴다. 진짜 비용은 다른 곳에 있다. 첫째, 넘어간 요청은 두 번 기다린다. 작은 모델 응답 시간에 큰 모델 응답 시간이 더해지니 p95 지연이 나빠진다. 둘째, 검사가 놓친 나쁜 답은 그대로 사용자에게 간다. 형식은 맞는데 내용이 틀린 요약은 규칙 검사로 잡기 어렵다. 그래서 캐스케이드의 품질은 검사의 품질과 같고, 검사를 통과한 작은 모델 답을 표본으로 뽑아 계속 채점해야 한다. 셋째, 모델이 둘이면 프롬프트와 캐시도 둘이다. 캐시는 모델별로 따로라서 요청이 두 모델로 나뉘면 캐시 적중률이 떨어진다.

// cascade.ts: 작은 모델 → 검사 → 큰 모델
async function summarize(ticket: Ticket) {
  const first = await callModel("claude-haiku-5-5", ticket);
  const problem = validate(first, ticket);         // null이면 통과
  metrics.count("summary.small", { ok: problem === null });
  if (problem === null) return first;

  log.info("escalate", { ticketId: ticket.id, reason: problem });

  const again = validate(second, ticket);
  if (again !== null) return enqueueHumanReview(ticket, again);
  return second;

운영에서 꼭 보는 숫자는 넘어간 비율과 그 이유별 분포다. 넘어간 비율이 갑자기 오르면 입력 데이터가 바뀌었거나(새 상품군, 새 언어), 작은 모델 쪽 프롬프트가 깨졌다는 신호다.

확신도를 모델에게 직접 물어 쓰는 방법은 편하지만 그 숫자를 그대로 믿기 어렵다. 모델이 말하는 확신과 실제 정답률이 얼마나 맞는지 재는 법은 [LLM 평가 글](/posts/llm-evals)의 확신도 보정 부분을 본다. 규칙으로 판정할 수 있는 신호(빠진 항목, 스키마 위반, 원문에 없는 숫자)를 먼저 쓰고, 확신도는 보조로 둔다.

## 가격표에 없는 숫자

단가가 같아도 못 쓰는 모델이 있다. 가격표 옆에서 함께 확인하는 숫자들이다.

컨텍스트 창과 최대 출력. 계약서 100쪽을 통째로 넣어야 하면 창 크기가 먼저 후보를 거른다. 지금 Claude 5.5 세대는 창이 100만 토큰이지만, 오픈 웨이트 모델은 학습 때 다룬 길이가 짧은 것이 많고, 직접 띄울 때는 GPU 메모리가 창을 더 줄인다. 최대 출력도 본다. 긴 보고서를 한 번에 써야 하는 일에서 출력 상한이 낮으면 잘라서 이어 쓰는 코드를 따로 짜야 한다.

속도. 첫 토큰까지의 시간과 초당 출력 토큰 수는 모델과 시간대에 따라 다르다. 가격표에는 없으니 내 요청으로 하루 중 여러 번 재 본다. 사람이 기다리는 화면은 품질만큼 이 숫자가 중요하다.

호출 한도. 분당 요청 수와 분당 토큰 수에 계정 등급별 한도가 있다. 출시 첫날 트래픽을 한도가 막아 429가 쏟아지는 일은 모델 품질과 상관없이 생긴다. 큰 행사가 있으면 미리 한도 상향을 요청한다.

기능. 구조화 출력, 이미지 입력, 도구 호출, 프롬프트 캐시, 배치 API, 처리 지역 지정 같은 기능이 모델과 플랫폼마다 다르다. 같은 Claude라도 Anthropic API와 클라우드 플랫폼에서 열린 기능과 가격이 다를 수 있다. 쓰려는 기능을 목록으로 적고 후보마다 표시한다.

수명. 모델에는 지원 종료 일정이 붙는다. 고른 모델이 1년 안에 내려간다면 교체 비용을 미리 계산에 넣는다. 오픈 웨이트를 직접 운영하면 이 일정에서 자유롭다는 것도 장점 중 하나다.

## 일 세 가지에 모델 붙여 보기

같은 기준을 성격이 다른 세 가지 일에 대 보면 고르는 방향이 갈린다. 계산은 모두 위의 정가로 했다.

첫째, 문의 분류. 입력 800토큰, 출력 20토큰(카테고리 이름 하나), 하루 20만 건이다. Haiku 5.5면 하루 $18, Opus 5.5면 $720이다. 정답이 정해진 일이라 코드로 채점하는 시험지를 만들기 쉽고, 작은 모델이 시험지를 통과하면 고민할 것이 없다. 이런 일은 큰 모델을 쓰는 것이 낭비이고, 오히려 지연이 짧은 작은 모델이 사용자 경험에도 낫다.

둘째, 코드 리뷰 에이전트. PR 하나에 모델을 12번 부르고, 부를 때마다 입력 3만 토큰(코드와 대화 기록)과 출력 1,500토큰을 쓴다. Opus 5.5로 PR 하나에 $1.80, Sonnet 5.5로 $0.90이다. 여기서는 단가보다 호출 수와 성공률이 비용을 정한다. 싼 모델이 길을 잃어 20번을 부르거나 리뷰가 틀려 사람이 다시 봐야 한다면 더 비싸다. 비용은 요청당이 아니라 끝난 일 하나당으로 잰다. 이 일에서는 입력 대부분이 매번 같은 앞부분이라 캐시가 크게 먹는다. 3만 토큰 중 2만 6천 토큰을 캐시로 읽으면 Opus 5.5로도 PR 하나에 $0.614다.

셋째, 진료 기록 요약. 데이터가 병원 밖으로 나갈 수 없다면 가격 비교 전에 후보가 오픈 웨이트 직접 운영으로 좁혀진다. 그다음 기준은 우리 GPU에 들어가는 크기 중 시험지를 통과하는 가장 작은 모델이다. 계약으로 데이터 처리 지역과 보존을 보장받는 클라우드 API가 허용되는 병원도 있으니, "밖으로 못 보낸다"가 정확히 어떤 조건인지 법무와 먼저 확인한다.

## 중계 서비스를 끼울 때

OpenRouter처럼 여러 공급사 모델을 API 하나로 묶어 주는 중계 서비스가 있다. OpenAI 호환 형식으로 요청하면서 모델 이름만 바꿔 여러 공급사를 오갈 수 있고, 한 공급사가 막히면 다른 곳으로 넘기는 설정도 둔다. 모델 비교 실험을 빠르게 할 때 특히 편하다.

대신 데이터 경로에 회사가 하나 더 낀다. 데이터 처리 약관을 두 곳과 맺어야 하고, 중계 서비스의 장애가 곧 우리 장애가 된다. 비용 구조(충전 수수료 등)와 공급사 고유 기능을 얼마나 그대로 넘겨주는지도 확인해야 한다. 프롬프트 캐시나 공급사별 새 파라미터가 호환 형식에서 빠지는 경우가 있다. 실험은 중계로 빠르게 하고, 운영 경로는 쓰기로 정한 공급사에 직접 붙이는 팀이 많은 이유다. 여러 공급사를 오가는 코드를 어떻게 짤지는 [에이전트 도구 설계 글](/posts/agent-tool-design)에서 도구 호출 형식의 차이와 함께 다룬다.

## 직접 띄우는 게 싸지는 지점

오픈 웨이트 모델을 GPU에 직접 띄우면 비용이 토큰 단위가 아니라 시간 단위로 바뀐다. 계산 틀은 "GPU 시간당 비용 ÷ 그 GPU가 한 시간에 만드는 토큰 수"다. 같은 GPU라도 하루 종일 꽉 차 있으면 토큰당 비용이 싸고, 밤에 놀면 그 시간도 돈이다. 숫자를 넣은 계산은 [LLM 직접 띄우기 글](/posts/self-hosting-llm-inference)에 있다.

모델 선택의 눈으로 보면 질문이 하나 더 있다. 비교 대상이 무엇이냐다. 처음 장면의 요약 일을 직접 띄운 8B 모델과 비교할 상대는 Opus가 아니라 Haiku 5.5다. Haiku로 하루 $21인 일을 GPU 두 장(장애 대비)과 사람 운영 시간으로 이기기는 어렵다. 직접 운영이 비용으로 이기는 건 작은 API 모델로는 품질이 안 나오는데 큰 API 모델로는 너무 비싼 대량 작업이거나, 파인튜닝한 작은 모델이 그 일에서 큰 모델을 따라잡는 경우다. 데이터 반출이 막혀서 고르는 경우는 비용 비교가 애초에 의미가 없다.

## 모델을 바꾸면 프롬프트도 바뀐다

모델을 정했으면 언젠가 바꾸게 된다. 새 버전이 나오거나, 쓰던 모델이 지원 종료 일정에 들어간다. 이때 생기는 일이 몇 가지 있다.

같은 프롬프트에 다르게 반응한다. 예전 모델에 맞춰 "반드시", "절대" 같은 강한 말을 잔뜩 넣어 둔 프롬프트는 지시를 더 잘 따르는 새 모델에서 지나치게 경직된 답을 낸다. 출력 길이, 말투, JSON 바깥에 설명을 붙이는 습관도 모델마다 다르다.

토큰 수가 달라진다. 토크나이저가 바뀌면 같은 글이 다른 토큰 수가 된다. Anthropic 문서는 Opus 4.7부터 쓴 토크나이저가 이전보다 같은 글에 1~1.35배 토큰을 쓴다고 적는다. 단가가 내려가도 토큰이 늘면 청구서는 생각만큼 안 준다. 바꾸기 전에 실제 요청 표본으로 토큰 수를 다시 센다.

API 모양이 바뀐다. 같은 공급사 안에서도 새 모델에서 막히는 파라미터가 생긴다. 예를 들어 Claude Opus 5.5는 생각을 끄는 설정과 특정 도구를 강제하는 `tool_choice`를 400 오류로 거절한다. 모델 이름만 바꿔 배포하면 첫 요청에서 바로 터진다.

그래서 모델 교체는 코드 배포처럼 다룬다.

```text
1. 모델 ID를 설정값으로 뺀다. 별칭(최신을 가리키는 이름) 대신 고정된 ID를 쓴다
2. 시험지를 새 모델로 돌린다. 통과율, 한 건 비용, p95 지연을 이전 모델 옆에 적는다
3. 떨어진 문항을 하나씩 본다. 프롬프트 문제인지 모델 한계인지 가른다
4. 트래픽 일부(예: 5%)만 새 모델로 보내고 넘어간 비율·불만·비용을 본다
5. 이전 모델 ID로 되돌리는 설정을 남겨 둔다
```

시험지가 없으면 2번과 3번을 할 수 없다. 모델 선택에서 가장 오래 남는 자산은 고른 모델이 아니라 이 시험지다.

## 현장에서 받는 질문들

"청구서가 갑자기 두 배가 됐다"는 제보가 오면 모델보다 토큰부터 본다. `usage`를 요청마다 남겨 두었다면 입력·출력·캐시 읽기·생각 토큰 중 무엇이 늘었는지 바로 보인다. 흔한 원인은 대화 기록을 자르지 않아 입력이 계속 쌓인 것, 시스템 프롬프트에 날짜 같은 값을 넣어 캐시가 매번 깨진 것, effort 기본값이 다른 모델로 바꾼 것이다.

"작은 모델로 바꿨더니 가끔 이상한 답이 나온다"는 캐스케이드 검사가 놓친 경우다. 통과한 답에서 표본을 뽑아 큰 모델이나 사람이 채점하는 흐름이 없으면 이 문제는 사용자가 알려 줄 때까지 안 보인다.

"새 모델이 벤치마크에서 훨씬 좋다는데 왜 안 바꾸냐"는 질문에는 시험지 표로 답한다. 우리 일에서 몇 %p가 좋아지고 한 건이 얼마가 되는지 숫자가 있으면 이야기가 짧아진다.

## 고르는 기준을 먼저 적는다

모델 선택은 "가장 좋은 모델"을 찾는 일이 아니라 일마다 품질, 비용, 지연, 데이터 통제의 균형점을 찾는 일이다. 가장 좋은 모델을 낮은 effort로 먼저 재 보고, 캐시와 배치로 공짜로 깎을 수 있는 걸 깎은 다음, 내 시험지에서 작은 모델이 버티는 만큼 라우팅으로 내려보낸다. 그리고 모델을 바꿀 때마다 같은 시험지를 다시 친다. 에이전트처럼 모델을 여러 번 부르는 구조에서는 이 계산이 호출 수만큼 곱해지니, [에이전트 구조 글](/posts/agent-reasoning-patterns)에서 호출 수를 함께 본다.

## 면접에서 나올 만한 질문

### LLM을 고를 때 무엇을 기준으로 보나요?

품질, 비용, 지연, 데이터 통제 네 가지를 내 일로 잰다. 품질은 벤치마크가 아니라 실제 요청으로 만든 시험지 통과율로 보고, 비용은 요청 한 건의 입력·출력·생각 토큰에 단가를 곱해 하루·한 달로 환산한다. 지연은 평균보다 p95를 보고, 데이터를 외부로 보낼 수 있는지는 법무·보안 조건으로 먼저 거른다. 이 표를 놓고 "품질 하한을 넘는 후보 중 가장 싼 것"처럼 결과를 보기 전에 정한 규칙으로 고른다.

### 오픈 웨이트 모델과 닫힌 모델 API의 트레이드오프는 무엇인가요?

닫힌 모델은 쓴 토큰만큼 내고 운영을 공급사가 맡으며, 같은 시기 최고 성능이 보통 이쪽에 있다. 대신 데이터가 공급사 서버로 나가고 가격과 모델 수명이 공급사에 달려 있다. 오픈 웨이트는 데이터를 우리 네트워크 안에 두고 모델을 고정할 수 있지만, GPU가 놀아도 비용이 나가고 운영 인력이 든다. 라이선스도 모델마다 달라서 상업 사용 조건을 원문으로 확인해야 한다.

### 추론 모델(생각하는 모델)은 언제 쓰나요?

중간 단계가 틀리면 답이 틀리는 일, 즉 여러 조건을 따지는 판단, 계산, 코드 수정, 여러 도구를 거치는 작업에 쓴다. 요약이나 분류처럼 읽고 바로 쓰는 일은 생각을 길게 해도 결과가 거의 같고 출력 단가로 청구되는 생각 토큰만 늘어난다. 생각 토큰은 첫 글자를 늦추기도 하니 채팅 화면에서는 지연도 함께 본다. 실무에서는 같은 모델에서 effort만 낮춰 먼저 재 보는 것이 출발점이다.

### 벤치마크 점수를 그대로 믿으면 안 되는 이유는요?

테스트 문제가 학습 데이터에 섞였을 수 있고, 공급사가 고른 프롬프트와 설정으로 잰 점수라 조건이 다르면 숫자가 움직인다. 상위 모델들이 비슷한 점수에 몰려 있으면 작은 차이는 의미가 없다. 무엇보다 벤치마크 과제와 우리 일은 다르다. 후보를 추리는 데만 쓰고, 고르는 건 실제 요청으로 만든 시험지로 한다.

### 작은 모델로 먼저 보내는 라우팅이나 캐스케이드를 설계해 보세요.

요청 특징으로 미리 갈라 보내는 라우팅과, 작은 모델 답을 검사해 실패한 것만 큰 모델로 넘기는 캐스케이드가 있다. 작은 모델이 수십 배 싸면 넘기는 비율이 꽤 높아도 비용은 줄지만, 넘어간 요청은 두 번 기다려서 p95 지연이 나빠진다. 캐스케이드 품질은 검사 품질과 같으니 스키마·필수 항목처럼 규칙으로 판정할 신호를 먼저 쓰고, 통과한 답도 표본 채점을 계속한다. 넘기는 비율과 이유를 지표로 남겨서 비율이 갑자기 오르면 입력 변화나 프롬프트 문제를 의심한다.

### 셀프 호스팅이 API보다 싸지는 건 언제인가요?

GPU 시간당 비용을 그 GPU가 실제로 만드는 토큰 수로 나눠 API 단가와 비교한다. GPU를 하루 종일 꽉 채우는 대량 작업이면 유리하고, 사용량이 적고 들쭉날쭉하면 노는 시간 때문에 API가 거의 이긴다. 비교 상대는 같은 품질을 내는 가장 싼 API 모델이어야 하고, 여분 GPU와 운영 인력 비용도 넣어야 한다. 데이터 반출이 막혀 있으면 비용과 상관없이 직접 운영이 답이다.

### 모델을 새 버전으로 바꿀 때 무엇을 확인하나요?

같은 시험지로 새 모델의 통과율, 한 건 비용, 지연을 이전 모델 옆에 놓고, 떨어진 문항을 하나씩 본다. 토크나이저가 바뀌면 같은 글의 토큰 수가 달라지니 실제 표본으로 다시 세고, 새 모델에서 거절되는 파라미터가 없는지 API 변경 사항을 본다. 예전 모델에 맞춘 강한 지시가 새 모델에서 과하게 먹히는 경우가 많아 프롬프트도 손본다. 배포는 고정된 모델 ID를 설정으로 빼서 일부 트래픽부터 보내고, 되돌릴 수 있게 둔다.

### OpenRouter 같은 중계 서비스를 운영에 쓰면 어떤 점을 따져야 하나요?

모델 이름만 바꿔 여러 공급사를 오갈 수 있고 장애 시 다른 공급사로 넘기기 쉬운 것이 장점이다. 대신 데이터 경로에 회사가 하나 더 끼어 데이터 처리 약관과 장애 범위가 늘고, 프롬프트 캐시나 공급사 고유 파라미터가 호환 형식에서 빠질 수 있다. 수수료 구조도 확인해야 한다. 그래서 비교 실험에는 중계를 쓰고, 운영 경로는 고른 공급사에 직접 붙이는 경우가 많다.
