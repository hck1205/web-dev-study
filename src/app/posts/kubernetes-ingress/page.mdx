쿠버네티스에 서비스를 하나 올리고 밖에서 접속하게 하려면 Service에 `type: LoadBalancer`를 붙이면 된다. 클라우드가 알아서 로드 밸런서를 만들어 주고 외부 IP가 생긴다. 쉽다. 문제는 서비스가 열 개가 되면 로드 밸런서도 열 개가 된다. 도메인은 하나인데 입구가 열 개다. Ingress는 이 입구를 하나로 합치려고 생겼다.

## 서비스마다 로드 밸런서를 달면

먼저 Service가 밖으로 열리는 방법부터 짚고 가자. Pod는 수시로 죽고 다시 뜨면서 IP가 바뀐다. 그래서 Pod 묶음 앞에 변하지 않는 주소를 하나 세우는데, 이게 Service다.

ClusterIP는 기본값이다. 클러스터 안에서만 닿는 가상 IP를 하나 받는다. 다른 Pod가 `api.shop.svc.cluster.local` 같은 이름으로 부를 때 쓴다. 밖에서는 보이지 않는다.

NodePort는 모든 노드의 같은 포트(기본 범위 30000~32767)를 열어서, 어느 노드로 들어오든 그 Service로 보낸다. 밖에서 닿기는 하지만 사용자에게 `http://노드IP:31234`를 알려 줄 수는 없다. 노드가 바뀌면 IP도 바뀌고, 포트 번호도 보기 흉하다.

LoadBalancer는 NodePort 위에 클라우드 로드 밸런서를 하나 얹는다. 고정된 외부 주소가 생기니 운영에 쓸 만하다. 대신 Service 하나에 로드 밸런서 하나다. 로드 밸런서는 시간당 요금이 붙는 자원이라 서비스 수만큼 비용이 늘고, 외부 IP와 DNS 레코드도 서비스마다 관리해야 한다. 게다가 이 로드 밸런서는 대개 L4(TCP) 수준이라 `/api`는 이쪽, `/`는 저쪽 같은 HTTP 경로 판단을 하지 못한다. 인증서도 서비스마다 따로 붙여야 한다.

원하는 건 이런 모습이다. 로드 밸런서는 하나만 두고, 그 뒤에서 HTTP 요청의 호스트와 경로를 보고 알맞은 Service로 나눠 주는 무언가. 그 "무언가"를 쿠버네티스 방식으로 선언하는 게 Ingress다.

## 규칙과 규칙을 실행하는 쪽

Ingress를 처음 배울 때 가장 헷갈리는 지점이 여기다. Ingress 리소스를 만들어도 그것만으로는 아무 일도 일어나지 않는다. Ingress는 "shop.example.com의 /api는 api Service로 보내라" 같은 라우팅 규칙을 적어 둔 문서일 뿐이다. 이 문서를 읽고 실제로 트래픽을 받아 나눠 주는 프로그램이 따로 있어야 하는데, 그게 Ingress Controller다.

컨트롤러는 쿠버네티스가 기본으로 깔아 주지 않는다. 직접 고르고 설치해야 한다. 흔히 쓰는 것으로는 nginx를 감싼 ingress-nginx, Traefik, HAProxy 기반 컨트롤러가 있고, 클라우드는 자기 로드 밸런서를 직접 조작하는 컨트롤러를 준다. AWS Load Balancer Controller는 Ingress를 보고 ALB를 만들고, GKE의 기본 Ingress는 구글 클라우드 HTTP(S) 로드 밸런서를 만든다. 앞의 것들은 클러스터 안에서 Pod로 돌며 프록시 역할을 하고, 클라우드형은 클러스터 밖의 로드 밸런서 설정을 바꾼다는 차이가 있다.

컨트롤러가 여러 개 깔린 클러스터도 있다. 내부용 nginx 하나, 외부용 ALB 하나 같은 식이다. 그러면 이 Ingress를 누가 처리할지 정해야 한다. 그 연결 고리가 IngressClass다. IngressClass 리소스의 `spec.controller`에는 담당 컨트롤러 이름(`k8s.io/ingress-nginx` 같은)이 적혀 있고, Ingress는 `spec.ingressClassName`으로 그 클래스를 고른다.

예전에는 `kubernetes.io/ingress.class`라는 어노테이션으로 같은 일을 했다. 지금은 이 방식이 deprecated이고 `ingressClassName` 필드를 쓴다. 클래스를 안 적으면 `ingressclass.kubernetes.io/is-default-class: "true"`가 붙은 기본 클래스가 맡는다. 기본 클래스도 없으면 어느 컨트롤러도 줍지 않아서, Ingress는 만들어졌는데 아무 데도 반영되지 않는 상태가 된다.

<Callout kind="warning" title="ingress-nginx의 상태">
  2025년 11월 쿠버네티스 SIG Network는 커뮤니티 프로젝트인 ingress-nginx(kubernetes/ingress-nginx)의 은퇴를 발표했다. 유지보수는 2026년 3월까지 최선 노력 수준으로만 이어졌고, 그 뒤로는 새 릴리스나 보안 패치가 나오지 않는다. 이미 돌고 있는 컨트롤러가 멈추지는 않지만, 새로 고른다면 Gateway API 구현체나 다른 컨트롤러를 검토하는 게 맞다. F5가 만드는 NGINX Ingress Controller는 이름이 비슷한 별개의 프로젝트다.
</Callout>

## 매니페스트 한 줄씩 읽기

shop.example.com 하나로 API 서버와 웹 프론트를 함께 여는 Ingress를 예로 들어 보자. `/api`로 시작하는 요청은 api Service로, 나머지는 web Service로 보낸다. HTTPS 인증서는 cert-manager가 발급해서 Secret에 넣어 준다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  namespace: shop
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - shop.example.com
      secretName: shop-example-com-tls
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api
                port:
                  number: 8080
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web
                port:
                  number: 80
```

## 경로가 겹치면 누가 이기나

pathType은 세 가지다. Exact는 경로가 글자 그대로 같을 때만 맞는다. `/foo`는 `/foo`와만 맞고 끝에 슬래시가 붙은 `/foo/`와도 맞지 않는다. Prefix는 경로를 `/`로 잘라 마디 단위로 비교한다. 문자열 앞부분만 같다고 맞지는 않는다. `/api`는 `/api/orders`와 맞지만 `/apis`와는 맞지 않는다. 끝의 슬래시는 무시해서, `/api/`로 적어도 `/api` 요청이 맞는다.

ImplementationSpecific은 판단을 컨트롤러에 넘긴다. ingress-nginx에서 정규식 경로를 쓸 때 이걸 골랐다. 이름 그대로 컨트롤러를 바꾸면 동작이 달라질 수 있어서, 이식성을 생각하면 Prefix나 Exact를 쓰는 게 낫다.

여러 규칙이 동시에 맞을 때는 가장 긴 경로가 이긴다. 길이가 같으면 Exact가 Prefix보다 먼저다. 그래서 위 예제에서 `/`와 `/api`를 함께 적어도 `/api/orders`는 api로, `/login`은 web으로 간다. 어떤 규칙에도 맞지 않는 요청은 `spec.defaultBackend`로 가고, 그것도 없으면 컨트롤러가 자기 기본 응답(ingress-nginx는 404)을 준다.

## 요청 하나가 Pod에 닿기까지

규칙을 알았으니 실제 요청이 어떻게 흐르는지 따라가 보자. 컨트롤러도 결국 클러스터 안에서 도는 Pod라서, 밖에서 닿으려면 자기 앞에 로드 밸런서가 있어야 한다. 보통 컨트롤러를 설치할 때 컨트롤러용 Service를 `type: LoadBalancer`로 만든다. 서비스마다 하나씩이던 로드 밸런서가 컨트롤러 앞의 하나로 줄어드는 것이다.

6번이 의외일 수 있다. Ingress에는 Service 이름을 적었는데 정작 트래픽은 Service의 가상 IP를 거치지 않는다. ingress-nginx나 Traefik은 기본으로 Service에 딸린 EndpointSlice를 지켜보다가 Pod IP 목록을 자기 업스트림으로 쓴다. 이렇게 하면 kube-proxy를 한 번 덜 거치고, 컨트롤러가 직접 부하 분산 방식(라운드 로빈, 세션 고정 등)을 정할 수 있다. Service는 "어떤 Pod 묶음인지"를 알려 주는 이름표로만 쓰인다.

클라이언트 IP도 이 그림에서 이해하면 쉽다. 앱이 보는 출발지 IP는 컨트롤러 Pod의 IP다. 진짜 클라이언트 IP는 `X-Forwarded-For` 헤더로 넘어온다. 그런데 그 앞 단계에서 이미 IP가 바뀌는 경우가 있다. 로드 밸런서가 들어온 연결을 아무 노드로나 보내고 그 노드가 다시 다른 노드의 컨트롤러 Pod로 넘기면(`externalTrafficPolicy: Cluster`, 기본값), 그 과정에서 출발지가 노드 IP로 바뀐다. 컨트롤러 Service를 `externalTrafficPolicy: Local`로 두거나 로드 밸런서의 PROXY protocol을 켜서 원래 IP를 보존한다. 둘 다 앞뒤 설정을 같이 맞춰야 해서 한쪽만 켜면 연결이 깨진다.

## HTTPS는 컨트롤러에서 끝난다

위 흐름에서 TLS는 컨트롤러에서 풀렸다. 이걸 TLS 종료(termination)라고 한다. 인증서를 컨트롤러 한 곳에서만 관리하고, 앱은 평문 HTTP만 다루면 된다. 컨트롤러가 HTTP 내용을 읽을 수 있어야 경로를 보고 나눌 수 있으니 L7 라우팅에는 사실상 필수다.

대신 컨트롤러에서 Pod까지 구간은 평문이다. 클러스터 안 네트워크를 믿지 못하는 환경이라면 컨트롤러가 Pod로 다시 HTTPS를 맺게 하거나(ingress-nginx는 `backend-protocol: "HTTPS"` 어노테이션), 서비스 메시의 mTLS에 맡긴다. 암호를 아예 풀지 않고 그대로 Pod까지 보내는 TLS 패스스루도 있지만, 그러면 컨트롤러는 SNI만 볼 수 있고 경로 라우팅은 못 한다.

TLS를 켜면 ingress-nginx는 기본으로 HTTP 요청을 HTTPS로 308 리다이렉트한다. 인증서는 Secret에 넣어 두면 되는데, 사람이 90일마다 갱신해서 Secret을 바꾸는 건 언젠가 잊는다. 그래서 보통 cert-manager를 같이 쓴다. ## 어노테이션이 자꾸 늘어난다

Ingress 스펙은 일부러 작게 만들어졌다. host, path, backend, tls 정도가 전부다. 그런데 실제 운영에는 훨씬 많은 게 필요하다. 업로드 크기 제한, 타임아웃, 경로 재작성, CORS, 요청 수 제한, 카나리 배포, 인증 연동. 표준 필드가 없으니 컨트롤러마다 자기 어노테이션으로 이걸 해결했다.

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "20m"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "300"
    nginx.ingress.kubernetes.io/use-regex: "true"
    nginx.ingress.kubernetes.io/rewrite-target: /$2
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"
```

몇 개만 붙여도 이렇다. 어노테이션은 그냥 문자열이라 오타가 나도 API 서버는 받아 준다. 컨트롤러가 조용히 무시할 뿐이다. 그리고 전부 `nginx.ingress.kubernetes.io/` 접두사가 붙어 있어서, 컨트롤러를 Traefik이나 ALB로 바꾸는 순간 같은 기능을 그쪽 문법으로 다시 써야 한다. Ingress라는 표준을 쓰는데 실제로는 컨트롤러에 묶이는 것이다.

보안 문제도 있다. ingress-nginx에는 nginx 설정 조각을 그대로 끼워 넣는 snippet 어노테이션이 있었는데, Ingress를 만들 권한만 있으면 컨트롤러의 설정을 마음대로 바꿀 수 있다는 뜻이었다. 그래서 최근 버전은 이 기능을 기본으로 꺼 두었다. 2025년 3월에는 ingress-nginx의 어드미션 웹훅을 거쳐 원격 코드 실행이 가능한 취약점(IngressNightmare, CVE-2025-1974)이 공개되기도 했다. 컨트롤러는 클러스터 전체 Secret을 읽을 권한을 갖는 경우가 많아서, 여기가 뚫리면 피해가 크다.

Ingress의 또 다른 한계는 권한이다. 로드 밸런서 설정(어느 IP, 어느 인증서)과 앱 라우팅(어느 경로를 어느 Service로)이 한 리소스에 섞여 있다. 플랫폼 팀과 앱 팀이 같은 객체를 만져야 한다. 헤더 기반 라우팅이나 가중치 분배도 표준에 없다. 쿠버네티스는 Ingress API를 더 키우지 않기로 하고(문서에 "frozen"이라고 적혀 있다) 새 기능은 Gateway API에 넣고 있다. 이 이야기는 [게이트웨이 글](/posts/gateway)에서 이어 간다.

## 502, 503, 413을 만났을 때

Ingress를 붙이면 에러가 나도 어디서 난 건지 헷갈린다. 응답 페이지 하단에 nginx라고 찍혀 있으면 앱이 아니라 컨트롤러가 준 응답이다. 상태 코드로 대략 범위를 좁힐 수 있다.

404는 규칙에 맞는 게 없다는 뜻이다. host 오타, 경로 pathType 착각(`/api`를 Exact로 적고 `/api/orders`를 기대하는 식)이 흔하다. 아예 Ingress가 반영되지 않은 경우도 있는데, ingressClassName이 틀렸거나 기본 클래스가 없을 때다. `kubectl describe ingress`의 Address가 비어 있으면 어떤 컨트롤러도 이 Ingress를 맡지 않은 것이다.

503은 규칙은 맞았는데 보낼 Pod가 없다는 뜻이다. Service selector가 Pod 라벨과 다르거나, 포트 이름이 다르거나, Pod가 readiness probe를 통과하지 못해 EndpointSlice에서 빠진 상태다. `kubectl get endpointslice -l kubernetes.io/service-name=api`로 Pod IP가 있는지부터 본다.

502는 Pod까지 갔는데 응답이 이상했다는 뜻이다. 앱이 그 포트에서 듣고 있지 않거나, HTTPS로 듣는 앱에 평문으로 보냈거나, 배포 중 종료되는 Pod로 요청이 갔을 때 난다. 마지막 경우는 Pod 종료 시 preStop에서 몇 초 기다려 컨트롤러가 목록을 갱신할 시간을 주면 줄어든다.

413은 요청 본문이 너무 크다는 뜻이다. ingress-nginx의 기본 `proxy-body-size`는 1m라서, 파일 업로드 기능을 붙이면 처음 한 번은 꼭 만난다. 웹소켓이나 긴 작업이 60초 근처에서 끊긴다면 `proxy-read-timeout` 기본값(60초)을 의심한다.

## Ingress가 하는 일, 다시

Ingress는 하나의 로드 밸런서 뒤에서 HTTP 요청을 host와 path로 나눠 여러 Service에 보내는 규칙이고, 그 규칙을 실제로 실행하는 건 따로 설치한 컨트롤러다. 컨트롤러는 TLS를 끝내고, EndpointSlice에서 Pod IP를 골라 바로 보낸다. 표준이 작아서 쓰기 쉬운 대신, 그 밖의 기능은 컨트롤러별 어노테이션에 기대게 되고 그게 Gateway API가 나온 이유가 됐다.

## 면접에서 나올 만한 질문

### Service 타입이 LoadBalancer면 충분한데 Ingress가 왜 필요한가요?

LoadBalancer는 Service 하나에 클라우드 로드 밸런서 하나를 만든다. 서비스가 늘수록 비용과 외부 IP, 인증서 관리가 같이 늘고, 대부분 L4라 경로 기반 라우팅을 못 한다. Ingress를 쓰면 로드 밸런서 하나 뒤에서 host와 path로 여러 Service에 나눠 보내고, TLS도 한 곳에서 끝낼 수 있다.

### Ingress와 Ingress Controller는 어떻게 다른가요?

Ingress는 라우팅 규칙을 적은 API 리소스이고, 그것만으로는 아무 일도 하지 않는다. Ingress Controller는 그 규칙을 지켜보다가 실제 프록시 설정(nginx 설정, 클라우드 ALB 규칙 등)으로 바꿔 트래픽을 처리하는 프로그램이다. 쿠버네티스가 기본으로 제공하지 않아서 직접 설치해야 하고, 여러 개일 때는 IngressClass와 ingressClassName으로 담당을 정한다.

### pathType Prefix와 Exact의 차이, 규칙이 겹치면 어떻게 되나요?

Exact는 경로가 글자 그대로 같아야 하고, Prefix는 `/`로 나눈 마디 단위로 앞부분을 비교한다. 그래서 Prefix `/api`는 `/api/orders`와 맞지만 `/apis`와는 맞지 않는다. 여러 규칙이 맞으면 가장 긴 경로가 이기고, 길이가 같으면 Exact가 우선이다.

### TLS는 어디서 종료되고, 인증서는 어떻게 관리하나요?

보통 Ingress Controller에서 종료한다. Ingress의 tls 블록에 도메인과 kubernetes.io/tls 타입 Secret을 연결하면, 컨트롤러가 SNI를 보고 맞는 인증서로 핸드셰이크를 한다. 인증서 발급과 갱신은 cert-manager에 맡기는 경우가 많다. ACME HTTP-01이나 DNS-01로 도메인을 증명하고 만료 전에 자동으로 다시 받아 Secret을 갱신한다.

### Ingress를 거치면 트래픽이 Service의 ClusterIP를 지나가나요?

ingress-nginx나 Traefik 같은 컨트롤러는 기본으로 지나가지 않는다. Service에 딸린 EndpointSlice를 지켜보다가 Ready인 Pod IP로 바로 보낸다. kube-proxy를 한 번 덜 거치고, 세션 고정 같은 부하 분산 방식을 컨트롤러가 직접 정할 수 있기 때문이다.

### 앱 로그에 클라이언트 IP가 전부 같은 값으로 찍힙니다. 왜 그런가요?

앱이 보는 출발지는 컨트롤러 Pod라서, 진짜 IP는 X-Forwarded-For 헤더에서 읽어야 한다. 그 헤더에도 노드 IP가 찍힌다면 로드 밸런서에서 컨트롤러로 오는 사이에 SNAT가 일어난 것이다. 컨트롤러 Service를 externalTrafficPolicy: Local로 두거나 PROXY protocol을 로드 밸런서와 컨트롤러 양쪽에서 켜서 보존한다.

### Ingress 뒤에서 503이 나면 무엇부터 보나요?

503은 규칙은 맞았지만 보낼 Pod가 없다는 신호다. EndpointSlice에 Pod IP가 있는지 먼저 보고, 없다면 Service selector와 Pod 라벨, 포트 이름, readiness probe를 확인한다. 404라면 규칙 매칭이나 ingressClassName 문제, 502라면 Pod의 포트·프로토콜 문제일 가능성이 크다.

### Ingress의 한계는 무엇이고, 대안은 무엇인가요?

스펙이 작아서 헤더 매칭, 가중치 분배, 타임아웃 같은 기능을 컨트롤러별 어노테이션으로 해결해야 하고, 그래서 이식성이 떨어진다. 인프라 설정과 앱 라우팅이 한 리소스에 섞여 있어 역할을 나누기도 어렵다. 쿠버네티스는 Ingress API를 동결하고 새 기능을 Gateway API에 넣고 있으며, Gateway API는 GatewayClass·Gateway·HTTPRoute로 역할을 나누고 이런 기능을 표준 필드로 갖고 있다.
