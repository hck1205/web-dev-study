지금까지 본 창 문제는 모두 "가장 긴 창"을 찾았다. [Longest Substring Without Repeating Characters](/posts/leetcode-longest-substring-without-repeating)와 [Longest Repeating Character Replacement](/posts/leetcode-longest-repeating-character-replacement)는 조건이 깨지면 왼쪽을 당겨 조건을 되살렸다. 이번 문제는 반대다. 조건을 만족하는 동안 왼쪽을 당겨 창을 줄이고, 그 과정에서 가장 짧은 창을 기록한다. 같은 두 포인터인데 기록하는 순간과 멈추는 조건이 뒤집힌다.

또 하나 새로 나오는 게 "창이 조건을 만족하나"를 O(1)에 판정하는 방법이다. 매번 글자 52종을 다 비교하면 느리다. 모자란 글자 수 하나를 들고 다니는 `missing` 카운터가 이 문제의 요령이다. 이 글은 시작점마다 늘리기, 길이 이분 탐색, 창과 전체 비교, `missing` 카운터 창, 필요한 글자만 걸러 낸 창, 128칸 배열 창 순서로 간다. 문제 원문은 [LeetCode 76](https://leetcode.com/problems/minimum-window-substring/)이다. 코드는 모두 Node.js 22, Python 3.13, Java로 돌렸다.

## t를 모두 품는 가장 짧은 구간

문자열 `s`와 `t`가 주어진다. `s`의 부분 문자열(이어진 구간) 중에서 `t`의 모든 글자를 개수까지 포함하는 가장 짧은 것을 돌려준다. `t`에 A가 두 개면 구간에도 A가 두 개 이상 있어야 한다. 그런 구간이 없으면 빈 문자열을 돌려준다. 답이 되는 구간은 하나뿐이라고 보장된다.

순서는 상관없다. `t = "ABC"`이면 구간 안에 C, A, B 순으로 있어도 된다. 구간 안에 다른 글자가 끼어 있어도 된다.

풀이에 영향을 주는 제약은 이렇다.

- `s`와 `t`의 길이는 각각 1 이상 10만 이하다. `s`의 구간은 약 50억 개라 전부 볼 수 없다.
- 글자는 영문 대문자와 소문자, 52종이다. 대소문자를 구분한다. 개수를 128칸 배열로 셀 수 있다.
- 원 문제의 추가 질문이 "O(m + n)에 풀 수 있나"다. m은 `s`, n은 `t`의 길이다. 이 글의 목표가 그 풀이다.

## 손으로 먼저 풀어 보기

예시는 `s = "BAXCAYBCA"`, `t = "ABC"`다. 인덱스로 쓰면 0:B, 1:A, 2:X, 3:C, 4:A, 5:Y, 6:B, 7:C, 8:A.

왼쪽에서부터 A, B, C가 모두 들어오는 순간을 찾는다.

```text
B A X C            0~3에서 처음으로 A, B, C가 다 있다. 길이 4
  A X C A Y B      B를 빼면 B가 모자라다. 오른쪽으로 가 6번 B를 만나 다시 채운다
    X C A Y B      A를 빼도 4번 A가 남아 괜찮다
      C A Y B      X를 빼도 괜찮다. 길이 4
        A Y B C    C를 빼면 모자라다. 7번 C를 만나 다시 채운다. 길이 4
          Y B C A  A를 빼면 모자라다. 8번 A를 만나 다시 채운다
            B C A  Y를 빼도 괜찮다. 길이 3, 가장 짧다
```

답은 `"BCA"`(6~8번)다. 이 과정을 보면 두 가지 움직임이 번갈아 나온다. 모자라면 오른쪽을 늘리고, 다 품었으면 왼쪽을 줄인다. 다 품은 상태에서만 길이를 기록한다.

두 번째 줄에서 빼면 안 되는 글자와 빼도 되는 글자가 갈린다. 4번 A가 들어온 뒤에는 창 안에 A가 두 개라, 1번 A를 빼도 여전히 하나가 남는다. 그래서 "글자가 창에 있나"가 아니라 "몇 개 있나"를 세야 한다.

## 시작점마다 처음으로 다 품는 곳까지

시작 `i`를 고정하고 오른쪽으로 늘리다가 처음으로 `t`를 다 품는 `j`에서 멈춘다. 시작점이 `i`인 가장 짧은 답은 그 `[i, j]`다. 더 늘려 봐야 길어지기만 한다.

판정을 빠르게 하려고 `remain`(글자별로 아직 필요한 개수)과 `missing`(아직 못 채운 글자 수 합)을 쓴다. 이 둘은 뒤의 최적 풀이에서도 그대로 쓰는 장치라 여기서 먼저 익혀 둔다.

```js
function minWindowExtend(s, t) {
  const need = new Map();
  for (const c of t) need.set(c, (need.get(c) || 0) + 1);
  let best = "";
  for (let i = 0; i < s.length; i++) {
    const remain = new Map(need); // 시작점마다 필요한 개수를 새로 복사
    let missing = t.length;       // 아직 못 채운 글자 수 (중복 포함)
    for (let j = i; j < s.length; j++) {
      const c = s[j];
      if (remain.has(c)) {
        if (remain.get(c) > 0) missing--; // 필요했던 글자를 하나 채웠다
        remain.set(c, remain.get(c) - 1);
      }
      if (missing === 0) { // 처음으로 다 품었다
        if (best === "" || j - i + 1 < best.length) best = s.slice(i, j + 1);
        break;
      }
    }
  }
  return best;
}
```

시간은 최악 O(m²)이다. 시작점마다 끝까지 갈 수 있기 때문이다. 1만 자에서 68ms였으니 10만 자면 수 초가 걸린다. 공간은 글자 종류 수만큼이다.

이 풀이의 낭비는 시작점을 하나 옮길 때마다 `remain`을 처음부터 다시 만든다는 데 있다. `i = 0`에서 `[0, 3]`이 다 품는다는 걸 알았는데, `i = 1`에서 다시 1번부터 센다. 실제로는 0번 글자 하나만 빼고 이어서 오른쪽을 늘리면 된다. 그게 창이다.

## 길이로 이분 탐색하기

창으로 가기 전에 한 가지 관찰을 더 해 둔다. 길이 L인 구간 중 `t`를 품는 게 있으면, 그 구간을 한 칸 늘린 길이 L + 1 구간도 `t`를 품는다. 글자가 늘기만 하니까. 그래서 "길이 L로 품는 구간이 있나"는 L이 작을 땐 아니오, 어느 지점부터 예다. 그 경계가 답의 길이다. [이분 탐색](/posts/binary-search)으로 찾을 수 있다.

길이가 고정되면 고정 길이 창을 밀며 `missing`을 관리한다. 들어오는 글자는 필요한 개수를 1 줄이고, 나가는 글자는 1 늘린다.

```js
function minWindowBinary(s, t) {
  const need = new Map();
  for (const c of t) need.set(c, (need.get(c) || 0) + 1);
  // 길이 len인 창 중 t를 품는 첫 시작 위치. 없으면 -1
  const find = (len) => {
    const remain = new Map(need);
    let missing = t.length;
    for (let r = 0; r < s.length; r++) {
      const c = s[r];
      if (remain.has(c)) {
        if (remain.get(c) > 0) missing--;
        remain.set(c, remain.get(c) - 1);
      }
      if (r >= len) { // 창 밖으로 나간 글자
        const o = s[r - len];
        if (remain.has(o)) {
          remain.set(o, remain.get(o) + 1);
          if (remain.get(o) > 0) missing++;
        }
      }
      if (r >= len - 1 && missing === 0) return r - len + 1;
    }
    return -1;
  };
  let lo = t.length, hi = s.length + 1; // 답의 길이는 [lo, hi). s.length + 1은 '없음'
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    if (find(mid) !== -1) hi = mid;
    else lo = mid + 1;
  }
  if (lo > s.length) return "";
  const start = find(lo);
  return s.slice(start, start + lo);
}
```

판정 O(m)을 log m번 하니 O(m log m)이다. 10만 자에서 42ms였다. 답의 하한을 `t.length`로 둔 것도 작은 최적화다. `t`보다 짧은 구간이 `t`를 품을 수는 없다.

이 풀이는 "없음"을 `s.length + 1`이라는 가짜 길이로 표현하는 반열린 구간 연습으로도 좋다. 하지만 아래 창 풀이는 길이를 따로 정하지 않고 한 번에 늘이고 줄이며 O(m)으로 끝낸다.

## 창을 늘이고 줄이며 매번 다 비교하기

창 `[l, r]` 안의 글자 개수를 `have`에 들고 다닌다.

1. `r`을 한 칸 늘려 `s[r]`을 `have`에 넣는다.
2. 창이 `t`를 다 품는 동안: 길이를 기록하고, `s[l]`을 빼고 `l`을 한 칸 당긴다.
3. 다 품지 못하게 되면 1로 돌아간다.

"다 품나"는 `t`의 글자 종류마다 `have`가 필요한 개수 이상인지 비교해서 판정한다.

```js
function covers(have, need) {
  for (const [c, k] of need) if ((have.get(c) || 0) < k) return false;
  return true;
}

function minWindowCompare(s, t) {
  const need = new Map();
  for (const c of t) need.set(c, (need.get(c) || 0) + 1);
  const have = new Map(); // 창 안 글자 개수
  let l = 0, bestL = 0, bestLen = Infinity;
  for (let r = 0; r < s.length; r++) {
    have.set(s[r], (have.get(s[r]) || 0) + 1);
    while (covers(have, need)) { // 다 품는 동안 줄인다
      if (r - l + 1 < bestLen) { bestLen = r - l + 1; bestL = l; }
      have.set(s[l], have.get(s[l]) - 1);
      l++;
    }
  }
  return bestLen === Infinity ? "" : s.slice(bestL, bestL + bestLen);
}
```

`l`과 `r`이 앞으로만 가니 창 이동은 2m번 이하다. 다만 이동할 때마다 `covers`가 `t`의 글자 종류 k(최대 52)를 다 훑으니 O(m·k)다. 10만 자에서 62ms였다. 판정을 O(1)로 만들면 이 k가 사라진다.

## 모자란 글자 수 하나만 들고 다닌다

`have`와 `need`를 따로 두지 않고, `need` 하나에 "아직 더 필요한 개수"를 적는다. 창에 글자가 들어오면 1 빼고, 나가면 1 더한다. 값이 음수면 필요한 것보다 남는다는 뜻이다. 그리고 `missing`에 "아직 못 채운 글자 수의 합"을 둔다. 처음엔 `t.length`다.

`missing`이 바뀌는 순간은 두 가지뿐이다.

- 글자 `c`가 들어올 때 `need[c]`가 양수였다면, 필요한 걸 하나 채운 것이니 `missing`을 1 줄인다. 0 이하였다면 남는 글자라 `missing`은 그대로다.
- 글자 `c`가 나갈 때 `need[c]`를 1 더한 결과가 양수가 되면, 필요한 걸 하나 잃은 것이니 `missing`을 1 늘린다.

`missing === 0`이면 창이 `t`를 다 품는다. 판정이 O(1)이다.

```js
function minWindow(s, t) {
  const need = new Map(); // 글자 -> 아직 더 필요한 개수 (음수면 남는 것)
  for (const c of t) need.set(c, (need.get(c) || 0) + 1);
  let missing = t.length; // 아직 못 채운 글자 수 (중복 포함)
  let l = 0, bestL = 0, bestLen = Infinity;
  for (let r = 0; r < s.length; r++) {
    const c = s[r];
    if (need.has(c)) {
      if (need.get(c) > 0) missing--; // 필요한 글자를 하나 채웠다
      need.set(c, need.get(c) - 1);
    }
    while (missing === 0) { // t를 다 품었다. 왼쪽을 줄여 본다
      if (r - l + 1 < bestLen) { bestLen = r - l + 1; bestL = l; }
      const out = s[l];
      if (need.has(out)) {
        need.set(out, need.get(out) + 1);
        if (need.get(out) > 0) missing++; // 필요한 글자를 내보냈다
      }
      l++;
    }
  }
  return bestLen === Infinity ? "" : s.slice(bestL, bestL + bestLen);
}
```

시간 O(m + n)이다. `t`를 한 번 훑어 `need`를 만들고(n), `s` 위에서 `l`과 `r`이 각각 많아야 m번 움직이며 매번 O(1)이다. 공간은 `t`의 글자 종류 수, 많아야 52라 O(1)이다. 10만 자에서 7ms로, 매번 비교하는 풀이보다 9배쯤 빨랐다.

`t`에 없는 글자(X, Y)는 `need.has`에서 걸러 아예 건드리지 않는다. 그래서 `need`에는 `t`의 글자만 들어 있다.

긴 창 문제와 비교하면 차이가 보인다. 가장 긴 창은 조건이 깨졌을 때 `while`로 되살리고 반복문 끝에서 기록했다. 가장 짧은 창은 조건을 만족하는 동안 `while` 안에서 기록하고 줄인다. 기록의 위치가 `while` 바깥이냐 안쪽이냐가 다르다.

## 필요한 글자의 위치만 골라서 돈다

`s`가 아주 길고 `t`의 글자가 `s`에 드물게 나오면, 창이 쓸데없는 글자(위 예시의 X, Y) 위를 오래 지나간다. `t`에 있는 글자의 위치만 미리 배열 `pos`에 모아 두고 그 위에서 창을 돌리면 이동 횟수가 줄어든다. 창의 실제 길이는 `pos[r] - pos[l] + 1`로 원래 인덱스에서 구한다.

```js
function minWindowFiltered(s, t) {
  const need = new Map();
  for (const c of t) need.set(c, (need.get(c) || 0) + 1);
  const pos = []; // t에 있는 글자의 위치만 모은다
  for (let i = 0; i < s.length; i++) if (need.has(s[i])) pos.push(i);
  let missing = t.length, l = 0, bestL = 0, bestLen = Infinity;
  for (let r = 0; r < pos.length; r++) {
    const c = s[pos[r]];
    if (need.get(c) > 0) missing--;
    need.set(c, need.get(c) - 1);
    while (missing === 0) {
      const len = pos[r] - pos[l] + 1; // 원래 문자열에서의 길이
      if (len < bestLen) { bestLen = len; bestL = pos[l]; }
      const out = s[pos[l]];
      need.set(out, need.get(out) + 1);
      if (need.get(out) > 0) missing++;
      l++;
    }
  }
  return bestLen === Infinity ? "" : s.slice(bestL, bestL + bestLen);
}
```

복잡도는 그대로 O(m + n)이고 `pos`만큼 공간을 더 쓴다. 이득은 입력 모양에 달렸다. 52종이 고르게 섞인 10만 자에서는 `pos`를 만드는 비용 때문에 오히려 조금 느렸다(7.25ms → 8.82ms). 10만 자 중 `t`의 글자가 30개 남짓뿐인 입력에서는 2.59ms → 1.16ms로 절반이 됐다. 면접에서는 "`t`의 글자가 `s`에 드물면 이렇게 거를 수 있다"고 말할 수 있으면 충분하다.

## 해시맵 대신 128칸 배열

글자가 ASCII 영문자로 제한되니 `need`를 128칸 배열로 바꾼다. 그러면 `t`에 없는 글자를 걸러 낼 필요도 없어진다. `t`에 없는 글자는 0에서 시작해 들어오면 음수가 되고 나가면 0으로 돌아올 뿐, 양수가 되는 일이 없으니 `missing`을 건드리지 않는다.

```js
function minWindowArray(s, t) {
  const need = new Int32Array(128); // 글자 코드 -> 아직 더 필요한 개수
  for (let i = 0; i < t.length; i++) need[t.charCodeAt(i)]++;
  let missing = t.length, l = 0, bestL = 0, bestLen = Infinity;
  for (let r = 0; r < s.length; r++) {
    if (need[s.charCodeAt(r)]-- > 0) missing--; // 줄이기 전 값이 양수면 필요한 글자였다
    while (missing === 0) {
      if (r - l + 1 < bestLen) { bestLen = r - l + 1; bestL = l; }
      if (++need[s.charCodeAt(l)] > 0) missing++; // 늘린 뒤 값이 양수면 필요한 글자를 잃었다
      l++;
    }
  }
  return bestLen === Infinity ? "" : s.slice(bestL, bestL + bestLen);
}
```

`need[x]-- > 0`은 줄이기 전 값을 비교하고, `++need[x] > 0`은 늘린 뒤 값을 비교한다. 후위·전위 연산자 차이를 정확히 써야 하는 곳이라 처음엔 풀어 쓰는 편이 안전하다. 10만 자에서 2.2ms로 해시맵 풀이보다 3배쯤 빨랐다.

## 세 언어로 쓴 최종 코드

Python은 `Counter`가 없는 키를 0으로 돌려줘서 `t`에 없는 글자도 따로 거르지 않고 배열 풀이처럼 쓸 수 있다.

```python
from collections import Counter

class Solution:
    def minWindow(self, s: str, t: str) -> str:
        need = Counter(t)          # 글자 -> 아직 더 필요한 개수 (음수면 남는 것)
        missing = len(t)           # 아직 못 채운 글자 수 (중복 포함)
        l = 0
        best_l, best_len = 0, float("inf")
        for r, c in enumerate(s):
            if need[c] > 0:
                missing -= 1
            need[c] -= 1           # t에 없는 글자도 음수로 기록된다
            while missing == 0:    # 창이 t를 다 품는 동안 왼쪽을 줄인다
                if r - l + 1 < best_len:
                    best_l, best_len = l, r - l + 1
                need[s[l]] += 1
                if need[s[l]] > 0:
                    missing += 1
                l += 1
        return "" if best_len == float("inf") else s[best_l:best_l + best_len]
```

Java는 `int[128]` 배열 버전이 가장 짧다.

```java
class Solution {
    public String minWindow(String s, String t) {
        int[] need = new int[128];               // 글자 -> 아직 더 필요한 개수
        for (char c : t.toCharArray()) need[c]++;
        int missing = t.length();
        int l = 0, bestL = 0, bestLen = Integer.MAX_VALUE;
        for (int r = 0; r < s.length(); r++) {
            if (need[s.charAt(r)]-- > 0) missing--; // 필요한 글자였으면 하나 채웠다
            while (missing == 0) {                   // t를 다 품었으면 왼쪽을 줄인다
                if (r - l + 1 < bestLen) {
                    bestLen = r - l + 1;
                    bestL = l;
                }
                if (++need[s.charAt(l)] > 0) missing++; // 필요한 글자를 내보냈다
                l++;
            }
        }
        return bestLen == Integer.MAX_VALUE ? "" : s.substring(bestL, bestL + bestLen);
    }
}
```

`("BAXCAYBCA", "ABC")`, `("a", "aa")`, `("AABXA", "AA")`, `("bba", "ab")`, `("XYZ", "Q")`를 넣어 세 언어 모두 `"BCA"`, `""`, `"AA"`, `"ba"`, `""`가 나왔다. 여섯 풀이가 같은 답(위치까지)을 내는지는 A·B·C로 만든 무작위 `s`, `t` 4000쌍으로 비교했다.

언어별로 짚을 점이다.

- Python의 `Counter`는 없는 키를 읽으면 0을 돌려주지만, `need[c] -= 1`처럼 쓰면 그 키가 생긴다. 메모리는 글자 종류만큼이라 문제없다. 일반 `dict`라면 `KeyError`가 나니 `get`을 쓴다.
- 답 문자열을 반복문 안에서 매번 `s.slice`나 `substring`으로 만들지 않는다. 줄일 때마다 문자열을 새로 만들면 O(m²)까지 갈 수 있다. 시작 위치와 길이만 기록하고 마지막에 한 번 자른다.
- Java의 `substring`은 Java 7u6 이후 새 배열을 복사하니 O(길이)다. 마지막 한 번이라 괜찮다.

## 여섯 풀이 비교

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 시작점마다 늘리기 | O(m²) | O(k) | 정답 확인용 |
| 길이 이분 탐색 | O(m log m) | O(k) | 길이의 단조성을 보여 줄 때 |

A 두 개가 `missing`을 2에서 0으로 만들어 버린다. 들어올 때는 "줄이기 전 값이 양수였나", 나갈 때는 "늘린 뒤 값이 양수인가"를 봐야 한다.

없는 경우를 처리하지 않고 자른다. `bestLen`이 `Infinity`인 채로 `s.slice(bestL, bestL + bestLen)`을 부르면 `s.slice(0, Infinity)`라서 빈 문자열이 아니라 `s` 전체가 나온다. `"BAXC".slice(0, Infinity)`는 `"BAXC"`다. 따로 검사해야 한다.

기록을 줄인 뒤에 한다. `while` 안에서 `l++`을 먼저 하고 길이를 기록하면 이미 조건이 깨진 창(한 글자 모자란 창)의 길이를 기록하게 된다. 기록은 조건을 만족하는 창에서, 줄이기 전에 한다.

`t`가 `s`보다 길다. 답이 없으니 바로 `""`를 돌려줘도 되고, 위 코드는 `missing`이 0이 되지 않아 자연스럽게 `""`가 나온다. 이분 탐색 풀이는 하한이 `t.length`라 `lo > s.length`에서 `""`를 돌려준다.

## 조건을 바꿔 보면

### 순서까지 지켜야 한다면 (LeetCode 727)

`t`가 구간 안에 부분 수열로, 즉 순서대로 나와야 한다면 개수 세기로는 안 된다. 앞에서부터 `t`를 순서대로 맞춰 끝을 찾고, 거기서 거꾸로 `t`를 맞춰 시작을 최대한 당기는 두 포인터 방법이나, `dp[i][j]`(`s`의 i번째에서 끝나며 `t`의 앞 j글자를 순서대로 품는 가장 늦은 시작)로 푼다. 글자 개수가 아니라 위치 관계가 조건이 되기 때문이다.

### 정확히 t의 순열(애너그램)인 구간을 찾는다면 (LeetCode 567, 438)

창 길이가 `t.length`로 고정된다. 같은 `missing` 카운터를 고정 길이 창에 쓰면 된다. 한 칸 밀 때 들어오는 글자와 나가는 글자를 함께 처리하고, `missing === 0`인 위치를 모은다.

```js
function findAnagrams(s, p) { // 소문자만 들어온다고 가정
  const need = new Array(26).fill(0);
  for (const c of p) need[c.charCodeAt(0) - 97]++;
  let missing = p.length;
  const res = [];
  for (let r = 0; r < s.length; r++) {
    if (need[s.charCodeAt(r) - 97]-- > 0) missing--;            // 들어온 글자
    if (r >= p.length && ++need[s.charCodeAt(r - p.length) - 97] > 0) missing++; // 나간 글자
    if (missing === 0) res.push(r - p.length + 1);
  }
  return res;
}
findAnagrams("bacdcab", "abc"); // [0, 4]
```

길이가 고정이라 `missing === 0`이 곧 "개수가 정확히 같다"는 뜻이 된다. 창 길이가 `p.length`인데 필요한 글자를 모두 채웠으면 남는 글자가 끼어들 자리가 없다.

### t를 품는 구간의 개수를 센다면 (LeetCode 1358과 같은 모양)

오른쪽 끝 `r`마다 "`r`에서 끝나며 `t`를 품는 구간"의 수를 더한다. 같은 창을 돌리되, `while`로 최대한 줄인 뒤의 `l`이 곧 그 개수다. 시작이 0부터 `l - 1`까지인 구간이 모두 `t`를 품기 때문이다.

```js
function countCovering(s, t) {
  const need = new Map();
  for (const c of t) need.set(c, (need.get(c) || 0) + 1);
  let missing = t.length, l = 0, count = 0;
  for (let r = 0; r < s.length; r++) {
    const c = s[r];
    if (need.has(c)) { if (need.get(c) > 0) missing--; need.set(c, need.get(c) - 1); }
    while (missing === 0) { // 품지 않게 될 때까지 줄인다
      const o = s[l];
      if (need.has(o)) { need.set(o, need.get(o) + 1); if (need.get(o) > 0) missing++; }
      l++;
    }
    count += l; // 시작이 0..l-1인 구간은 모두 t를 품는다
  }
  return count;
}
countCovering("BAXCAYBCA", "ABC"); // 19
```

모든 구간을 세는 코드와 무작위 문자열 2000개로 비교해 같은 값이 나왔다.

### s가 스트림으로 들어온다면

오른쪽은 들어오는 대로 처리하면 되지만, 왼쪽을 줄일 때 `s[l]`을 다시 읽어야 한다. 창 안의 글자를 큐에 들고 있어야 하고, 창이 길어지면 메모리도 그만큼 든다. 필요한 글자의 위치만 거른 풀이처럼 `t`에 있는 글자만 (글자, 위치) 쌍으로 큐에 넣으면 메모리를 줄일 수 있다.

### 단어 목록을 모두 이어 붙인 구간이라면 (LeetCode 30)

글자 대신 같은 길이의 단어를 한 칸으로 보고, 단어 길이만큼 시작 위치를 바꿔 가며 같은 고정 길이 창을 돌린다. 창의 단위가 글자에서 단어로 바뀔 뿐 `missing`으로 판정하는 생각은 같다.

## 정리하며

가장 짧은 창은 모자라면 오른쪽을 늘리고, 다 품었으면 기록한 뒤 왼쪽을 줄인다. 다 품었는지는 글자마다 "아직 더 필요한 개수"와 그 양수 부분의 합 `missing`으로 O(1)에 안다. 들어올 때는 줄이기 전 값이, 나갈 때는 늘린 뒤 값이 양수인지가 `missing`을 움직인다. `l`과 `r`이 앞으로만 가니 O(m + n)이다. 창 안의 최댓값처럼 개수로 판정할 수 없는 정보가 필요하면 다른 도구가 필요하다. 다음 글 [Sliding Window Maximum](/posts/leetcode-sliding-window-maximum)에서 그 도구인 단조 덱을 만든다.

## 면접에서 나올 만한 질문

### 이 문제를 O(m + n)에 푸는 방법은 무엇인가요?

`t`의 글자마다 아직 필요한 개수를 `need`에 적고, 모자란 개수의 합을 `missing`에 둔다. 오른쪽을 늘리며 필요한 글자가 들어오면 `missing`을 줄이고, `missing`이 0인 동안 길이를 기록하며 왼쪽을 줄인다. 필요한 글자가 나가 `missing`이 다시 양수가 되면 멈춘다. 두 포인터가 각각 m번 이하로 움직이고 판정이 O(1)이라 O(m + n)이다.

### missing은 언제 줄이고 언제 늘리나요?

글자가 들어올 때 그 글자의 `need`가 양수였으면, 즉 필요한 걸 채웠을 때만 줄인다. 이미 충분한 글자가 더 들어오면 `need`가 음수가 될 뿐 `missing`은 그대로다. 나갈 때는 `need`를 1 늘린 결과가 양수가 되면, 즉 필요한 만큼을 밑돌게 됐을 때만 늘린다. 이 구분을 안 하면 남는 글자가 `missing`을 깎아 틀린다.

### 가장 긴 창 문제와 비교해 무엇이 다른가요?

가장 긴 창은 조건이 깨지면 되살릴 때까지 왼쪽을 당기고 반복문 끝에서 기록한다. 가장 짧은 창은 조건을 만족하는 동안 `while` 안에서 기록하며 왼쪽을 당긴다. 그래서 기록 위치가 `while` 안이냐 밖이냐가 다르다. 또 가장 긴 창에서 쓸 수 있던 "창 크기를 줄이지 않는" 트릭은 짧은 창에서는 쓸 수 없다. 창을 적극적으로 줄여야 하기 때문이다.

### 왜 개수를 세야 하고 Set으로는 안 되나요?

`t`에 같은 글자가 여러 개 있으면 구간에도 그만큼 있어야 하기 때문이다. `t = "AA"`일 때 Set으로 종류만 보면 A 하나만 있어도 다 품었다고 판정한다. 왼쪽을 줄일 때도 "그 글자를 빼도 아직 충분한가"를 알려면 개수가 필요하다. 예시에서 A가 두 개 들어온 뒤 하나를 빼도 괜찮았던 이유가 이것이다.

### 이 문제를 이분 탐색으로도 풀 수 있나요?

풀 수 있다. 길이 L인 구간이 `t`를 품으면 한 칸 늘린 구간도 품으니 "길이 L로 가능한가"가 단조롭다. 길이를 이분 탐색하고 고정 길이 창으로 O(m)에 판정하면 O(m log m)이다. 가변 창이 O(m)이라 최선은 아니지만 단조성을 찾아 경계를 찾는 생각을 보여 줄 수 있다.

### 답 문자열을 언제 만들어야 하나요?

반복문 안에서는 시작 위치와 길이만 기록하고 마지막에 한 번만 자른다. 줄일 때마다 `slice`나 `substring`으로 문자열을 만들면 매번 O(길이)가 들어 최악 O(m²)까지 간다. 그리고 답이 없을 때를 따로 처리해야 한다. JS에서 `s.slice(0, Infinity)`는 `s` 전체를 돌려주기 때문이다.

### t의 글자가 s에 드물게 나오면 더 빠르게 할 수 있나요?

`t`에 있는 글자의 위치만 미리 배열로 모아 그 위에서 창을 돌리면 쓸데없는 글자를 건너뛴다. 창의 길이는 원래 위치의 차이로 계산한다. 복잡도는 O(m + n)으로 같지만, `t`의 글자가 30개 남짓인 10만 자 입력에서 시간이 절반으로 줄었다. 글자가 고르게 섞인 입력에서는 위치 배열을 만드는 비용 때문에 오히려 조금 느렸다.
