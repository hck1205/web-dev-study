이벤트 상품 재고를 Redis로 옮겼다. 주문이 들어오면 재고를 하나 빼고, 판매 수를 하나 올리고, 전체 주문 수를 하나 올린다. 세 명령은 `MULTI`와 `EXEC`로 묶었다. 트랜잭션으로 묶었으니 셋 다 되거나 셋 다 안 될 거라고 생각했다. 그런데 재고와 주문 수는 바뀌었고 판매 수만 그대로다. 오류 로그에는 `ERR value is not an integer or out of range` 한 줄이 남아 있다.

Redis 문서는 `MULTI`/`EXEC`를 트랜잭션이라고 부른다. MongoDB에도, DynamoDB에도, Cassandra에도 트랜잭션이라는 말이 있다. 단어는 같은데 약속하는 내용은 저장소마다 다르다. 이 글은 PostgreSQL 한 대 안에서 당연했던 네 글자(원자성, 일관성, 격리성, 지속성)가 노드가 여러 대가 되거나 NoSQL로 가면 어떻게 바뀌는지, 그리고 비는 글자를 앱이 어떻게 메우는지 본다.

이 주제의 다른 글: 네 글자가 PostgreSQL 한 대 안에서 어디까지 지켜지는지는 [ACID 글](/posts/acid-transactions)에, 격리 수준은 [트랜잭션과 격리 수준](/posts/db-transaction-isolation)에, 복제본 사이의 최신성은 [CAP과 PACELC](/posts/db-consistency-cap)와 [최종 일관성](/posts/eventual-consistency)에 있다. 여기서는 그 설명을 반복하지 않는다. 실험은 Ubuntu 24.04, Redis 7.0.15, PostgreSQL 16.15에서 했다.

## 같은 실패를 PostgreSQL에 넣으면

먼저 처음 장면을 그대로 재현한다. 판매 수 키 `sold:1001`에는 예전 코드가 숫자 대신 `"N/A"`를 넣어 두었다. 그 키에 `INCR`을 하면 실패한다.

```bash
# 실습용 Redis를 따로 띄운다 (영속화 끔)
redis-server --port 18117 --save "" --appendonly no --daemonize yes
redis-cli -p 18117 SET stock:1001 10
redis-cli -p 18117 SET sold:1001 "N/A"
redis-cli -p 18117 SET order:count 0
```

```text
127.0.0.1:18117> MULTI
OK
127.0.0.1:18117(TX)> DECR stock:1001
QUEUED
127.0.0.1:18117(TX)> INCR sold:1001
QUEUED
127.0.0.1:18117(TX)> INCR order:count
QUEUED
127.0.0.1:18117(TX)> EXEC
1) (integer) 9
2) (error) ERR value is not an integer or out of range
3) (integer) 1
127.0.0.1:18117> MGET stock:1001 sold:1001 order:count
1) "9"
2) "N/A"
3) "1"
```

`EXEC`의 응답 배열을 보면 된다. 1번과 3번은 성공했고 2번만 오류다. 재고는 9, 주문 수는 1로 바뀌었다. 실패한 명령 하나 때문에 나머지가 취소되지 않는다.

같은 일을 PostgreSQL에 시킨다. 판매 수 열을 일부러 텍스트로 만들어 같은 값을 넣었다.

```sql
CREATE TABLE products (id int PRIMARY KEY, stock int NOT NULL CHECK (stock >= 0), sold text NOT NULL);
CREATE TABLE orders (id serial PRIMARY KEY, product_id int NOT NULL);
INSERT INTO products VALUES (1001, 10, 'N/A');

BEGIN;
UPDATE products SET stock = stock - 1 WHERE id = 1001;            -- 재고 차감
UPDATE products SET sold = (sold::int + 1)::text WHERE id = 1001;  -- 여기서 실패한다
INSERT INTO orders (product_id) VALUES (1001);                    -- 주문 기록
COMMIT;
SELECT p.id, p.stock, p.sold, (SELECT count(*) FROM orders) AS orders FROM products p;
```

```text
UPDATE 1
ERROR:  invalid input syntax for type integer: "N/A"
ERROR:  current transaction is aborted, commands ignored until end of transaction block
ROLLBACK
  id  | stock | sold | orders 
------+-------+------+--------
 1001 |    10 | N/A  |      0
(1 row)
```

두 번째 문장이 실패하자 트랜잭션 전체가 실패 상태가 됐다. 세 번째 문장은 실행도 안 되고 거절됐고, `COMMIT`을 보냈는데 돌아온 답은 `ROLLBACK`이다. 재고는 10 그대로, 주문은 0건이다. 아래 그림에서 다음을 누르면 두 저장소가 같은 명령 셋을 어떻게 처리하는지 차례로 보인다.

## Redis가 약속하는 것은 끼어들지 않는다는 것뿐

Redis의 `MULTI`/`EXEC`는 롤백을 하지 않는다. Redis 공식 문서도 롤백을 지원하지 않는다고 분명히 적어 두었다. 이 트랜잭션이 보장하는 건 두 가지다. 큐에 쌓인 명령은 `EXEC` 때 순서대로 한 번에 실행되고, 그 사이에 다른 클라이언트의 명령이 끼어들지 않는다. 명령을 한 줄로 세워 하나씩 처리하는 Redis 구조([Redis 기본 글](/posts/redis-basics))에서 나오는 성질이다.

ACID로 옮기면 격리성은 강하다. 실행 중간 상태를 남이 볼 수 없기 때문이다. 원자성은 반쪽이다. 실행 도중 오류가 나도 나머지는 그대로 실행된다. 다만 오류가 큐에 넣는 순간 드러나면 이야기가 다르다. 명령 이름을 틀리면 이렇게 된다.

```text
127.0.0.1:18117> MULTI
OK
127.0.0.1:18117(TX)> DECR stock:1001
QUEUED
127.0.0.1:18117(TX)> INCRR order:count
(error) ERR unknown command 'INCRR', with args beginning with: 'order:count' 
127.0.0.1:18117(TX)> INCR order:count
QUEUED
127.0.0.1:18117(TX)> EXEC
(error) EXECABORT Transaction discarded because of previous errors.
127.0.0.1:18117> MGET stock:1001 order:count
1) "9"
2) "1"
```

모르는 명령이나 인자 개수가 틀린 명령은 큐에 넣는 단계에서 거절되고, `EXEC`는 `EXECABORT`로 전체를 버린다(2.6.5부터 이렇게 동작한다). 앞 실험의 값 9와 1이 그대로다. 반면 키에 든 값의 종류가 맞지 않는 오류는 실행해 봐야 알기 때문에 그 명령 하나만 실패한다. 아래 그림에서 다음을 누르면 오류가 어느 단계에서 나느냐에 따라 결말이 갈리는 모습이 보인다.

Lua 스크립트로 옮겨도 마찬가지다. 스크립트는 통째로 끼어들기 없이 실행되지만, 중간에 오류가 나면 그 전까지 쓴 것은 남는다.

```bash
# 재고를 빼고 판매 수를 올리는 스크립트. 두 번째 호출이 실패한다
redis-cli -p 18117 EVAL "redis.call('DECR', KEYS[1]) redis.call('INCR', KEYS[2]) return 'ok'" 2 stock:1001 sold:1001
redis-cli -p 18117 GET stock:1001
```

```text
(error) ERR value is not an integer or out of range script: d20ba0b3ea78166ce903e0b99101a3c0bc4a4d33, on @user_script:1.
"8"
```

앞 실험에서 9였던 재고가 8이 됐다. 스크립트 전체는 오류로 끝났는데 `DECR`은 반영됐다. 그래서 Lua를 쓸 때는 쓰기 전에 필요한 검사를 모두 끝내고, 쓰기는 실패할 일이 없는 명령만 마지막에 몰아 둔다. "검사 먼저, 쓰기는 나중"이 Redis에서 원자성을 흉내 내는 방법이다.

<Callout kind="warning">
`EXEC`가 오류 없이 돌아왔다는 것은 명령이 실행됐다는 뜻이지, 모든 명령이 성공했다는 뜻이 아니다. 클라이언트 라이브러리마다 응답 배열 안의 오류를 예외로 던지는지, 값으로 돌려주는지가 다르다. 쓰는 라이브러리에서 실제로 실패를 일으켜 보고 어떻게 보이는지 확인한다.
</Callout>

## 읽고 판단하는 일은 WATCH가 맡는다

`MULTI` 안에서는 앞 명령의 결과를 볼 수 없다. "재고가 1 이상이면 뺀다"를 하려면 `MULTI` 전에 값을 읽어야 하는데, 읽은 뒤 `EXEC`까지 사이에 누가 값을 바꾸면 판단이 틀린다. `WATCH`는 이 틈을 잡는다. 지켜보던 키가 `EXEC` 전에 바뀌면 `EXEC`가 아무것도 실행하지 않고 `(nil)`을 돌려준다.

재고를 1로 두고, 클라이언트 A가 읽고 판단하는 사이 클라이언트 B가 마지막 하나를 가져가게 했다.

```bash
R="redis-cli --no-raw -p 18117"   # 파이프로 보낼 때도 (integer) 형식으로 보이게
$R SET stock:1001 1
# A: 지켜보고 읽은 뒤 1초 쉬었다가 MULTI/EXEC
( printf 'WATCH stock:1001\nGET stock:1001\n'; sleep 1
  printf 'MULTI\nDECR stock:1001\nINCR order:count\nEXEC\nGET stock:1001\n' ) | $R &
# B: 그 사이에 마지막 하나를 가져간다
sleep 0.5; echo "B: $($R DECR stock:1001)"; wait
```

```text
OK
"1"
B: (integer) 0
OK
QUEUED
QUEUED
(nil)
"0"
```

앞의 `OK`와 `"1"`은 A의 `WATCH`와 `GET`, 그다음 줄이 B의 차감이다. 이어서 A의 `MULTI`, 두 번의 `QUEUED`, 그리고 `EXEC`의 응답이 온다.

A의 `EXEC`는 `(nil)`이다. 재고는 음수가 되지 않았고, A는 다시 읽어서 품절을 알려 주면 된다. 잠그지 않고 충돌을 알아채는 [낙관적 잠금](/posts/optimistic-locking)과 같은 모양이다. 격리성 중에서도 "읽은 값이 쓰기 전까지 그대로인가"는 이렇게 앱이 직접 요청해야 얻는다.

## OK를 받았어도 디스크에는 없을 수 있다

네 번째 글자 지속성은 설정이 정한다. Ubuntu 패키지의 `/etc/redis/redis.conf`는 AOF(쓰기 명령을 파일에 한 줄씩 적는 방식)가 꺼져 있다.

```bash
# 영속화 설정 확인
grep -nE "^(appendonly|appendfsync)" /etc/redis/redis.conf
```

```text
1379:appendonly no
1438:appendfsync everysec
```

트랜잭션을 `EXEC`하고 `OK`를 받은 직후 프로세스를 `kill -9`로 죽이고 다시 띄워 봤다. 한 번은 AOF를 끈 채로, 한 번은 `appendfsync always`로 켜고 했다.

```bash
# 트랜잭션 실행 → 강제 종료 → 같은 설정으로 재시작 → 값 확인
MODE="--appendonly no"            # 두 번째는 "--appendonly yes --appendfsync always"
redis-server --port 18118 $MODE --daemonize yes --pidfile r.pid
redis-cli -p 18118 SET stock:1001 10
printf 'MULTI\nSET order:42 paid\nDECR stock:1001\nEXEC\n' | redis-cli -p 18118
kill -9 "$(cat r.pid)"
redis-server --port 18118 $MODE --daemonize yes --pidfile r.pid
redis-cli -p 18118 MGET order:42 stock:1001
```

AOF를 끈 경우다. `EXEC`는 성공했는데 재시작 뒤에는 아무것도 없다.

```text
1) OK
2) (integer) 9
1) (nil)
2) (nil)
```

`appendfsync always`로 켠 경우다. 같은 순서인데 값이 남았다.

```text
1) OK
2) (integer) 9
1) "paid"
2) "9"
```

AOF가 꺼져 있으면 응답까지 받은 주문이 통째로 사라진다. 7.0의 기본 스냅숏 조건(`CONFIG GET save`로 보면 `3600 1 300 100 60 10000`, 1시간에 1건 또는 5분에 100건 또는 1분에 1만 건)으로는 변경 몇 건짜리 스냅숏이 한 시간 뒤에야 찍히는데, 그 전에 죽었기 때문이다. 기본값인 `everysec`으로 켜면 최대 1초 정도의 쓰기를 잃을 수 있고, `always`는 명령마다 `fsync`를 해서 잃지 않는 대신 느리다. 각 방식의 비용과 복구 과정은 [Redis 영속화 글](/posts/redis-persistence-ha)에 있다. 복제본을 붙여도 Redis 복제는 기본이 비동기라, 주 서버가 응답한 뒤 복제본에 닿기 전에 죽으면 그 쓰기는 장애 조치 뒤에 없다.

일관성도 짚어 둔다. PostgreSQL 쪽 표에는 `CHECK (stock >= 0)`이 있어서 재고가 0일 때 빼려고 하면 거절된다. Redis에는 그런 규칙을 적을 곳이 없다.

```text
127.0.0.1:18117> SET stock:2001 0
OK
127.0.0.1:18117> DECR stock:2001
(integer) -1
```

```text
ERROR:  new row for relation "products" violates check constraint "products_stock_check"
DETAIL:  Failing row contains (1001, -1, N/A).
```

위가 Redis, 아래가 PostgreSQL이다. Redis에서는 재고 -1이 아무렇지 않게 저장된다. 규칙은 `WATCH`나 Lua로 앱이 직접 지킨다.

## 노드가 여러 대면 글자마다 값이 붙는다

Redis 한 대에서 비는 글자는 설계 선택의 결과다. 노드가 여러 대가 되면 다른 이유가 생긴다. 네 글자를 여러 대에서 지키려면 매번 노드끼리 말을 주고받아야 한다.

- 원자성: 두 노드에 걸친 변경을 함께 성공시키려면 모두에게 먼저 묻고 결정을 알리는 [2단계 커밋](/posts/distributed-transactions-2pc)이 필요하다. 왕복이 두 번 늘고, 결정 직전에 조정자가 죽으면 참여자가 잠금을 쥔 채 기다린다.
- 격리성: 여러 노드에서 일어난 쓰기의 순서를 하나로 정해야 한다. 시계가 노드마다 조금씩 다르니 시각 발급 서버나 오차를 감안해 기다리는 장치가 붙는다.
- 지속성: 한 대의 디스크로는 부족하고 과반의 복제본에 적혀야 커밋이라고 부른다. 복제본이 다른 리전에 있으면 그 왕복이 커밋 시간이 된다.
- 일관성: `UNIQUE`나 외래 키가 여러 노드의 데이터를 봐야 하면 검사 자체가 분산 읽기가 된다.

## BASE는 보장이 아니라 설계 태도다

오른쪽 길에 붙은 이름이 BASE다. ACID와 대비되도록 지은 말로, 2000년 무렵 Eric Brewer 쪽에서 나왔고 2008년 eBay의 Dan Pritchett가 ACM Queue에 쓴 글 "BASE: An Acid Alternative"로 널리 알려졌다. 세 부분으로 나뉜다.

- Basically Available: 일부 노드가 죽거나 끊겨도 요청에 답한다. 답이 조금 낡았거나 일부만 처리됐더라도 거절하지 않는 쪽을 고른다.
- Soft state: 시스템 상태가 입력이 없어도 바뀔 수 있다. 복제본들이 서로 맞춰 가는 중이라, 아무도 쓰지 않았는데 다음 읽기의 값이 달라진다.
- Eventually consistent: 새 쓰기가 멈추면 언젠가 모든 복제본이 같은 값이 된다. "언젠가"가 얼마인지와 그동안 사용자가 무엇을 보는지는 [최종 일관성 글](/posts/eventual-consistency)이 다룬다.

ACID는 트랜잭션 하나가 지켜야 할 성질을 정확히 정의한 말이지만, BASE는 그만큼 정확한 정의가 없다. "가용성을 위해 강한 일관성과 다중 행 원자성을 기본으로 두지 않고, 필요한 곳에서 앱이 보완한다"는 설계 방향에 붙인 이름에 가깝다. 그래서 "이 DB는 ACID냐 BASE냐"는 질문은 잘 맞지 않는다. 같은 DB 안에서도 연산마다, 설정마다 서 있는 자리가 다르다. 그 자리를 저장소별로 본다.

## MongoDB는 문서 하나가 기본 단위다

MongoDB에서 문서 하나에 대한 쓰기는 언제나 원자적이다. 배열과 중첩 필드까지 한 번에 바뀐다. 여러 문서를 묶는 트랜잭션은 4.0부터 복제 세트에서, 4.2부터 샤드 클러스터에서 쓸 수 있다. 문서 모델 설계와 트랜잭션 비용은 [MongoDB 글](/posts/mongodb-document-model)에 있으니, 여기서는 네 글자 중 무엇이 설정에 달렸는지만 본다.

트랜잭션 안에서 원자성과 격리성은 보장된다. 지속성과 "읽은 값이 얼마나 확실한가"는 쓰기 확인 수준(write concern)과 읽기 수준(read concern)이 정한다. 연결 문자열에서 이 값을 읽어 보자. 아래 조각을 누르면 각각의 뜻이 나온다.

## DynamoDB와 Cassandra는 조건을 걸고 쓴다

키-값과 와이드 컬럼 저장소에서 가장 많이 쓰는 도구는 트랜잭션보다 조건부 쓰기다. "지금 값이 이럴 때만 바꿔라"를 쓰기 한 번에 넣는다. PostgreSQL로 치면 이런 문장이다.

```sql
-- 재고가 남아 있을 때만 뺀다. 이미 0이면 아무 행도 바뀌지 않는다
UPDATE products SET stock = stock - 1 WHERE id = 1001 AND stock > 0;
```

```text
UPDATE 0
```

재고가 0인 상태에서 돌렸더니 `UPDATE 0`이 돌아왔다. 오류가 아니라 "조건이 맞지 않아 아무것도 안 했다"는 답이다. DynamoDB에서는 같은 일을 `ConditionExpression`으로 한다.

```bash
# DynamoDB: 재고가 1 이상일 때만 1을 뺀다
aws dynamodb update-item --table-name products \
  --key '{"id":{"N":"1001"}}' \
  --update-expression "SET stock = stock - :one" \
  --condition-expression "stock >= :one" \
  --expression-attribute-values '{":one":{"N":"1"}}'
```

```text
(예시) An error occurred (ConditionalCheckFailedException) when calling the UpdateItem operation: The conditional request failed
```

DynamoDB는 이 조건 검사를 항목 하나 안에서 원자적으로 한다. 여러 항목을 묶어야 하면 `TransactWriteItems`를 쓴다. 한 번에 최대 100개 동작을 묶고, 조건 하나라도 실패하면 전부 취소되며 `TransactionCanceledException`과 함께 어느 항목이 왜 실패했는지(`CancellationReasons`)가 돌아온다. 같은 요청을 다시 보내도 한 번만 반영되게 하는 `ClientRequestToken`도 받는다(AWS 문서 기준 10분 동안 유효). 트랜잭션 쓰기는 일반 쓰기보다 용량을 두 배 쓰고, 글로벌 테이블에서는 트랜잭션이 쓰인 리전 안에서만 원자성과 격리성이 보장된다. 다른 리전 복제본에는 나중에 따로 도착한다.

Cassandra는 조건부 쓰기를 경량 트랜잭션(LWT, Lightweight Transaction)이라고 부른다. 일반 쓰기는 복제본에 보내고 정해진 수가 답하면 끝이지만, `IF`가 붙은 쓰기는 복제본들과 Paxos 합의를 거친다. 아래 그림에서 다음을 누르면 한 번의 조건부 쓰기에 왕복이 몇 번 드는지 보인다.

왕복 네 번은 Cassandra 3.x·4.0까지의 클래식 방식 기준이다. 4.1에서 들어온 Paxos v2(`paxos_variant: v2`)는 이 왕복을 줄였다고 문서에 적혀 있지만, 여전히 일반 쓰기보다는 비싸다. 그리고 LWT는 파티션 하나 안에서만 동작한다. 여러 파티션에 걸친 원자적 변경은 Cassandra의 기본 기능에 없다. 같은 파티션을 LWT와 일반 쓰기로 섞어 쓰면 일반 쓰기가 Paxos 순서를 모른 채 끼어들 수 있으니, 조건부로 다루는 칸은 모든 쓰기를 LWT로 한다.

이 정도로 정리하면 저장소마다 기본으로 서 있는 자리가 보인다. 모두 설정과 버전에 따라 달라지니, 기본값 기준의 대략적인 비교로 읽는다.

| 저장소 | 원자성의 범위 | 조건 검사 | 지속성 기본값 |
|---|---|---|---|
| PostgreSQL | 트랜잭션 전체 | 제약, `WHERE` | WAL `fsync` 후 응답 |
| Redis | 롤백 없음, 끼어들기만 막음 | `WATCH`, Lua | Ubuntu 기본은 AOF 꺼짐 |
| MongoDB | 문서 하나, 트랜잭션은 여러 문서 | 필터 조건 | `w: majority`(5.0부터 대부분) |
| DynamoDB | 항목 하나, 트랜잭션은 최대 100개 | `ConditionExpression` | 여러 AZ에 저장 후 응답 |
| Cassandra | 파티션 하나 | LWT(Paxos) | 일관성 수준과 commitlog 동기화 설정 |

## 분산 SQL은 네 글자를 지키고 왕복으로 값을 치른다

RTT 값은 예시다. 실제 값은 클라우드와 경로에 따라 다르니 직접 재 봐야 한다. 두 구간에 걸친 트랜잭션이면 구간마다 합의가 필요하고, 제품에 따라 그 단계를 겹쳐 실행해 줄이기는 하지만(CockroachDB의 parallel commits처럼) 합의 한 번보다 짧아지지는 않는다. Spanner는 여기에 시계 오차만큼 기다리는 커밋 대기가 붙는다.

또 하나의 대가는 재시도다. SERIALIZABLE에서 충돌하면 DB가 트랜잭션 하나를 버리고 다시 하라고 돌려보낸다. PostgreSQL 호환 오류 코드 `40001`(serialization failure)이 오고, 앱은 트랜잭션 전체를 처음부터 다시 실행해야 한다. 한 대짜리 PostgreSQL을 READ COMMITTED로 쓰던 코드를 그대로 옮기면 이 오류를 처리하지 않아 배포 첫날 500이 늘어나는 일이 흔하다. 재시도 루프가 꼭 필요하고, 재시도해도 같은 결과가 나오게 트랜잭션 안에서 외부 호출을 하지 않는다.

## 비는 글자를 앱이 메우는 방법

BASE 쪽 저장소를 쓰거나 서비스마다 DB를 나누면, 비는 글자를 앱이 채운다. 글자별로 쓰는 도구가 정해져 있다.

원자성이 빠지면 "되돌리기" 대신 "반대로 하기"를 쓴다. 여러 서비스에 걸친 주문이면 각 단계를 로컬 트랜잭션으로 커밋하고, 실패하면 앞 단계를 취소하는 보상 동작을 실행하는 [사가](/posts/saga-pattern)다. 상태를 바꾸고 이벤트를 보내는 두 일을 묶어야 하면, 이벤트를 같은 DB의 표에 같은 트랜잭션으로 적고 따로 보내는 [아웃박스](/posts/transactional-outbox)를 쓴다. 둘 다 결국 "한 곳에서는 ACID, 그 사이는 결국 맞춰짐"이라는 구조다.

격리성과 일관성이 빠지면 조건부 쓰기로 메운다. 위에서 본 `WHERE stock > 0`, `ConditionExpression`, `WATCH`, LWT가 다 같은 일을 한다. 확인과 쓰기 사이의 틈을 쓰기 한 번 안으로 넣는 것이다.

지속성과 커밋 결과 불명은 멱등성으로 메운다. 응답을 못 받았으면 다시 보내는데, 다시 보내도 한 번만 반영되게 요청마다 번호를 붙인다. 아웃박스가 보낸 이벤트는 적어도 한 번 이상 도착하므로, 받는 쪽도 처리한 이벤트 번호를 기록해 두 번째부터는 건너뛴다. 번호를 어디에 두고 언제 지우는지는 [멱등성 키 글](/posts/idempotency-key)에 있다. 아래 그림에서 다음을 누르면 세 가지가 주문 하나에서 함께 움직이는 모습이 보인다.

## 직접 짜 보기: 두 가지 EXEC

명령 목록을 받아 실행하는 함수를 짜 보자. `mode`가 `"redis"`면 Redis처럼, `"sql"`이면 PostgreSQL처럼 동작한다. 값은 모두 문자열로 저장한다.

- 명령은 `["SET", key, value]`, `["GET", key]`, `["INCR", key]`, `["DECR", key]` 넷이다. 그 밖의 이름이 하나라도 있으면 아무것도 실행하지 않고 `{ state, replies: "EXECABORT" }`를 돌려준다(두 모드 공통).
- `SET`의 응답은 `"OK"`, `GET`은 값 문자열(없으면 `null`), `INCR`/`DECR`은 바뀐 숫자다. 없는 키는 `"0"`으로 보고 계산한다.
- 정수가 아닌 값에 `INCR`/`DECR`을 하면 `redis` 모드는 응답에 `"ERR"`를 넣고 다음 명령을 계속한다. `sql` 모드는 원래 상태와 `replies: "ROLLBACK"`을 돌려준다.
- 입력으로 받은 `state` 객체는 바꾸지 않는다.

## 저장소를 옮기기 전에 확인할 것

관계형 DB에서 쓰던 로직을 NoSQL이나 분산 DB로 옮길 때, 또는 이미 옮긴 뒤 데이터가 이상할 때 보는 순서다.

반만 반영된 데이터가 보이면, 그 묶음이 그 저장소에서 정말 원자적인 단위인지부터 본다. Redis라면 `EXEC` 응답 배열에 오류가 섞여 있었는지 앱 로그를 찾는다. 응답 배열을 로그에 남기지 않는 코드라면 여기서 막히니, 실패 응답을 남기는 것부터 고친다. Redis Cluster에서는 `MULTI`와 Lua가 다루는 키가 모두 같은 슬롯에 있어야 하고, 아니면 `CROSSSLOT` 오류가 난다. 키 이름에 `{user:42}:cart`처럼 해시 태그를 붙여 같은 슬롯에 모은다.

재고가 음수이거나 같은 쿠폰이 두 번 쓰였으면, 그 규칙을 누가 지키는지 본다. 관계형에서는 `CHECK`와 `UNIQUE`가 하던 일이다. 옮긴 저장소에서는 조건부 쓰기를 썼는지, 읽고 나서 따로 쓰지 않았는지 코드를 본다. DynamoDB라면 `ConditionalCheckFailedException`이 지표에 한 번도 없는 테이블이 오히려 의심스럽다. 조건을 안 걸었다는 뜻일 수 있다.

장애 조치 뒤 최근 데이터가 없으면 지속성 설정을 본다. Redis는 `CONFIG GET appendonly`와 `appendfsync`, MongoDB는 쓰는 곳의 write concern이 `majority`인지, Cassandra는 쓰기 일관성 수준이 `ONE`이 아닌지 확인한다.

```bash
# Redis 영속화 상태: AOF가 켜져 있고 마지막 쓰기가 성공했는지
redis-cli -p 18117 INFO persistence | grep -E "aof_enabled|aof_last_write_status|rdb_last_bgsave_status"
```

```text
rdb_last_bgsave_status:ok
aof_enabled:0
aof_last_write_status:ok
```

`aof_enabled:0`이면 AOF가 꺼져 있다. 캐시로만 쓰는 인스턴스라면 괜찮지만, 주문 상태 같은 원본 데이터를 두고 있다면 이 한 줄이 장애 보고서의 원인이 된다.

분산 SQL로 옮긴 뒤 오류율이 올랐다면 `40001` 재시도 오류부터 센다. 재시도 루프가 있는지, 트랜잭션이 너무 많은 행을 오래 쥐고 있지 않은지, 모두가 같은 행(전역 카운터 같은)을 고치고 있지 않은지 본다.

## 트랜잭션이라는 같은 단어

트랜잭션이라는 말을 보면 "네 글자 중 무엇을, 어느 범위에서"를 먼저 묻는다. Redis는 끼어들기를 막지만 롤백하지 않고, MongoDB와 DynamoDB는 하나는 늘 원자적이고 여러 개는 비용을 내고 묶으며, Cassandra는 파티션 하나에서 조건부 쓰기만 준다. 분산 SQL은 네 글자를 다 주는 대신 커밋마다 리전 간 왕복과 재시도를 요구한다. BASE는 그중 일부를 내려놓고 조건부 쓰기, 사가, 아웃박스, 멱등성으로 앱이 메우는 설계다. 어느 쪽이 낫다기보다, 데이터마다 어느 글자가 꼭 필요한지 정하는 일이 먼저다.

## 면접에서 나올 만한 질문

### ACID와 BASE는 무엇이 다른가요?

ACID는 트랜잭션 하나가 지켜야 할 네 성질을 정확히 정의한 것이고, BASE는 가용성을 위해 강한 일관성과 여러 행에 걸친 원자성을 기본으로 두지 않는 설계 방향이다. Basically Available, Soft state, Eventually consistent의 줄임말이다. BASE는 정밀한 보장이 아니라서 "이 DB가 ACID냐 BASE냐"보다 연산마다 무엇을 보장하는지 따지는 게 정확하다.

### Redis의 MULTI/EXEC는 ACID 트랜잭션인가요?

아니다. 다른 클라이언트가 끼어들지 못하게 한 번에 실행하는 것만 보장하고 롤백은 없다. 명령 이름이 틀린 것처럼 큐에 넣을 때 드러나는 오류는 `EXECABORT`로 전체를 버리지만, 문자열에 `INCR`을 하는 것처럼 실행해야 아는 오류는 그 명령만 실패하고 나머지는 반영된다. 지속성은 AOF 설정에 달려 있고, 값에 규칙을 걸 제약도 없다.

### Redis에서 "재고가 있으면 뺀다"를 안전하게 하려면 어떻게 하나요?

`WATCH`로 키를 지켜보고 읽은 다음 `MULTI`/`EXEC`로 쓰면, 그사이 누가 키를 바꿨을 때 `EXEC`가 `(nil)`을 돌려준다. 그러면 다시 읽어서 재시도한다. 경합이 심하면 Lua 스크립트로 읽기, 판단, 쓰기를 서버 안에서 한 번에 한다. Lua도 중간 오류에 롤백하지 않으므로 검사를 먼저 끝내고 쓰기는 마지막에 둔다.

### MongoDB에서 여러 문서 트랜잭션을 쓸 때 주의할 점은?

먼저 트랜잭션이 필요 없게 문서 하나에 담을 수 있는지 본다. 문서 하나의 쓰기는 늘 원자적이고, 여러 문서 트랜잭션은 복제 세트나 샤드 클러스터에서만 되며 비용이 크다. 쓴다면 write concern을 `majority`로 두고, `TransientTransactionError`면 트랜잭션 전체를, `UnknownTransactionCommitResult`면 커밋만 다시 시도한다. 드라이버의 `withTransaction`이 이 구분을 해 준다.

### Cassandra의 경량 트랜잭션은 왜 느린가요?

조건을 판단하고 쓰는 과정을 복제본 과반과 Paxos로 합의하기 때문이다. 클래식 방식은 준비, 읽기, 제안, 커밋으로 왕복이 네 번이라 왕복 한 번으로 끝나는 일반 쓰기보다 몇 배 느리다. 4.1의 Paxos v2가 왕복을 줄였지만 여전히 비싸고, 파티션 하나 안에서만 동작한다. 그래서 조건부 쓰기가 계속 필요한 데이터는 다른 저장소에 두는 경우가 많다.

### 분산 SQL은 어떻게 여러 노드에서 ACID를 지키고, 대가는 무엇인가요?

데이터 구간마다 Raft로 과반에 복제하고, 여러 구간에 걸친 트랜잭션은 2단계 커밋 변형과 시각 발급(또는 시계 오차를 감안한 대기)으로 순서를 정한다. 대가는 지연이다. 커밋마다 과반 복제본까지 왕복이 들고, 복제본이 다른 리전에 있으면 그 RTT가 커밋 시간의 하한이 된다. 또 SERIALIZABLE 충돌이 나면 `40001`로 돌려보내므로 앱에 재시도 루프가 꼭 있어야 한다.

### 트랜잭션이 없는 저장소나 여러 서비스에 걸친 작업에서 정합성은 어떻게 지키나요?

글자별로 도구를 쓴다. 원자성이 없으면 단계마다 로컬로 커밋하고 실패 시 보상하는 사가, 상태 변경과 이벤트 발행을 묶어야 하면 아웃박스를 쓴다. 확인 후 쓰기의 틈은 조건부 쓰기로 쓰기 한 번 안에 넣고, 재시도와 중복 배달은 요청이나 이벤트 번호로 멱등하게 만든다. 사가는 중간 상태가 남에게 보인다는 점을 화면과 업무 규칙에서 감안해야 한다.

### DynamoDB에서 같은 트랜잭션 요청이 두 번 가면 어떻게 되나요?

`TransactWriteItems`에 `ClientRequestToken`을 붙였다면 일정 시간(문서 기준 10분) 안의 같은 토큰 요청은 한 번만 반영되고 같은 결과를 돌려받는다. 토큰이 없으면 두 번 실행된다. 조건식이 함께 있으면 두 번째가 조건에 걸려 `TransactionCanceledException`이 날 수도 있는데, 이걸 실패로 보고 사용자에게 오류를 보여 주면 이미 성공한 주문을 실패로 안내하게 된다.
