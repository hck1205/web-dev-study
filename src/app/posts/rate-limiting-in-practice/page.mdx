요청 수 제한을 배포한 다음 날 아침, 고객사 한 곳에서 문의가 온다. 사내 직원 300명이 아침 9시에 우리 서비스에 로그인하는데 절반이 "요청이 너무 많습니다"를 본다고 한다. 로그를 보니 300명 모두 같은 IP였다. 회사 공인 IP 하나로 나가는 NAT 뒤에 있었던 것이다. 알고리즘은 제대로 동작했다. 키를 잘못 골랐을 뿐이다.

알고리즘 자체는 [요청 수 제한 알고리즘](/posts/rate-limiting-algorithms)에서 다뤘다. 이 글은 그걸 실제 API에 붙일 때 정할 것들이다. 어디서 셀지, 무엇을 키로 삼을지, 거절할 때 무엇을 돌려줄지, Redis가 멈추면 어떻게 할지, 배포는 어떤 순서로 할지. 예제는 Node.js 22와 Redis 7.0으로 직접 띄운 작은 서버다.

## 한 군데에서 다 막으려고 하지 않는다

요청은 여러 층을 지나 앱에 닿는다. 각 층이 아는 정보가 달라서 막을 수 있는 것도 다르다. CDN이나 WAF는 아직 누가 로그인했는지 모르지만 IP는 안다. 게이트웨이는 API 키를 검증한 뒤라 고객사별 요금제를 안다. 앱은 "이 사용자가 오늘 쿠폰을 몇 번 받았나" 같은 업무 맥락까지 안다. 아래 그림에서 다음을 누르면 층마다 다른 이유로 막히는 요청이 보인다.

## 무엇을 키로 셀지가 절반이다

키는 "누구의 요청인가"다. 고르는 순서는 대체로 이렇다. 인증된 요청이면 사용자 ID나 API 키, 로그인 전이면 IP, 둘 다 애매하면 둘을 섞는다(로그인 시도는 "IP별"과 "아이디별"을 둘 다 센다. IP를 바꿔 가며 한 계정을 두드리는 공격과 한 IP에서 여러 계정을 두드리는 공격을 같이 막기 위해서다).

IP를 키로 쓸 때 두 가지를 조심한다.

첫째, 많은 사람이 IP 하나를 나눠 쓴다. 회사, 학교, 모바일 통신사의 CGNAT 뒤에서는 수백에서 수천 명이 같은 공인 IP로 나간다. 사용자별로 생각한 한도를 IP에 걸면 처음 사례처럼 된다. IP 한도는 사람 한 명이 아니라 건물 하나가 정상적으로 보낼 양으로 넉넉히 잡는다.

둘째, 앱이 보는 IP가 진짜 클라이언트 IP인지 확인한다. 앞에 로드 밸런서나 CDN이 있으면 소켓의 상대 주소는 그 장비다. 아래 그림이 그 모습이다.

그렇다고 `X-Forwarded-For`의 맨 앞 값을 그대로 믿으면 안 된다. 클라이언트가 헤더를 직접 넣어 보내면 LB는 그 뒤에 자기가 본 주소를 덧붙일 뿐이다. 맨 앞 값은 클라이언트 마음대로 바꿀 수 있어서, 공격자가 요청마다 다른 가짜 IP를 넣으면 한도를 완전히 피한다. 믿을 수 있는 건 내가 운영하는 프록시가 붙인 값뿐이다. 그래서 오른쪽부터 읽으며 내 프록시 주소를 건너뛰고, 처음 나오는 남의 주소를 클라이언트로 본다. 직접 짜 보자.

  if (!trusted.includes(remoteAddr)) return remoteAddr;
  const hops = xff.split(",").map((s) => s.trim()).filter(Boolean);

  for (let i = hops.length - 1; i >= 0; i--) {
    if (!trusted.includes(hops[i])) return hops[i];

  return hops[0];

nginx의 `real_ip_recursive on`과 `set_real_ip_from`, Express의 `trust proxy` 설정이 이 일을 한다. 두 번째 테스트에서 맨 앞 값을 고르는 코드는 `1.2.3.4`를 돌려준다.

IPv6라면 주소 하나가 아니라 앞 64비트(/64) 단위로 묶어서 센다. 가정이나 서버 하나에 /64 대역이 통째로 배정되는 경우가 흔해서, 한 사람이 주소를 2의 64승 개 가까이 바꿔 가며 보낼 수 있다. 주소 단위로 세면 사실상 제한이 없다.

## 거절할 때 돌려주는 것

거절은 `429 Too Many Requests`로 한다. 503은 "서버가 지금 못 받는다"이고 429는 "너는 한도를 넘었다"다. 둘을 섞으면 클라이언트가 원인을 모르고, 모니터링에서도 장애와 정상적인 거절이 섞인다. 서버 한 대가 한도를 Redis 토큰 버킷(용량 5, 2초에 1개)으로 세게 만들고 curl로 두드려 봤다.

```bash
# 같은 API 키로 7번 연달아 보내고 상태 코드만 찍는다
for i in 1 2 3 4 5 6 7; do curl -s -o /dev/null -w "%{http_code} " -H "X-API-Key: k1" localhost:8081/v1/orders; done; echo
# 다른 키로 첫 요청의 응답 헤더를 본다
curl -si -H "X-API-Key: k2" localhost:8081/v1/orders
```

브라우저에서 다른 출처로 부르는 API라면 `Access-Control-Expose-Headers: RateLimit, RateLimit-Policy, Retry-After`를 함께 보내야 프런트엔드 코드가 이 헤더를 읽는다. 429 응답이 CDN에 캐시되지 않게 하는 것도 확인한다. 캐시 규칙을 넓게 잡아 둔 CDN이 429를 저장하면 한도와 상관없는 사용자까지 같은 429를 받는다.

## 클라이언트는 기다릴 줄 알아야 한다

서버가 아무리 정확히 막아도 클라이언트가 429를 받자마자 다시 보내면 거절된 요청만 쌓인다. 배치 작업 클라이언트를 하나 만들어, 429를 받으면 `Retry-After`만큼 기다리되 0~300ms의 지터를 더하게 했다. 같은 서버에 8번 요청한 기록이다.

```bash
# 429를 받으면 Retry-After + 지터만큼 쉬었다가 다시 보낸다
node client.js
```

0.1s  #3 200  "burst";r=2;t=6

`Retry-After`가 없는 429를 받으면 [지수 백오프와 지터](/posts/resilience-patterns)로 기다린다. 흔한 실수는 HTTP 클라이언트 라이브러리의 자동 재시도가 429를 받자마자 짧은 간격으로 세 번 다시 보내는 것이다. 사용자 한 명의 요청 하나가 거절 네 개로 불어난다. 429와 503에 대해서는 자동 재시도가 `Retry-After`를 따르는지 라이브러리 설정을 확인한다. POST를 다시 보내도 괜찮은지는 [멱등성 키](/posts/idempotency-key)가 있는지에 달렸다. 429는 처리 전에 거절된 것이니 다시 보내도 겹치지 않는다.

## 인스턴스마다 세면 한도가 곱해진다

node instances.js
```

```

## Redis가 멈추면 다 막을까, 다 열까

공유 저장소에 세기 시작하면 그 저장소가 새 장애 지점이 된다. Redis가 느려지면 모든 요청이 제한 장치에서 기다린다. 그래서 제한 장치의 Redis 호출에는 아주 짧은 타임아웃을 걸고, 실패했을 때의 동작을 미리 정한다. 위 서버는 Redis 명령 타임아웃을 50ms로 두고, 환경 변수로 실패 시 동작을 고르게 했다. `CLIENT PAUSE`로 Redis를 1초 동안 멈춰 놓고 요청을 보냈다.

```bash
# Redis가 1초 동안 모든 클라이언트 명령을 붙잡게 한다 (멈춘 Redis 흉내)
redis-cli -p 6391 CLIENT PAUSE 1000 ALL
# 그사이 요청을 보낸다
curl -si -H "X-API-Key: k9" localhost:8081/v1/orders | sed -n '1,4p'
```

실패하면 통과시키는 설정(`FAIL_OPEN=1`)의 응답과 서버 로그다.

```text
HTTP/1.1 200 OK
Content-Type: application/json
Date: Tue, 20 Oct 2026 13:18:07 GMT
Connection: keep-alive
limiter error: Command timed out -> fail open
```

실패하면 막는 설정(`FAIL_OPEN=0`)이다.

```text
HTTP/1.1 503 Service Unavailable
Retry-After: 5
Date: Tue, 20 Oct 2026 13:18:10 GMT
Connection: keep-alive
limiter error: Command timed out -> fail closed
```

열어 두는 쪽(fail open)은 Redis 장애가 서비스 장애로 번지지 않는다. 대부분의 일반 API는 이쪽을 고른다. 요청 수 제한은 보호 장치일 뿐 기능 그 자체가 아니라서, 잠깐 제한 없이 받는 편이 전체 장애보다 낫다. 막아 두는 쪽(fail closed)은 제한이 곧 보안이거나 돈일 때 고른다. 로그인 시도, 문자 인증 발송, 건당 돈이 나가는 외부 API 호출이 그렇다. 문자 발송 한도가 Redis 장애로 풀리면 몇 분 만에 문자 요금이 수백만 원 나갈 수 있다. 실패 응답에 429가 아니라 503을 쓴 이유는 클라이언트 잘못이 아니기 때문이다.

## 요청마다 무게가 다르다

목록 조회 한 번과 엑셀 내보내기 한 번을 똑같이 1로 세면, 내보내기를 한도까지 부르는 클라이언트가 DB를 혼자 다 쓴다. 비싼 요청은 따로 낮은 한도를 걸거나 토큰을 여러 개 쓰게 한다. 위 Lua 스크립트라면 "1개 쓴다"를 인자로 받은 비용만큼 쓰게 바꾸면 된다. GitHub GraphQL API는 쿼리가 가져오는 노드 수로 점수를 매겨 시간당 점수 한도를 걸고, LLM API들은 요청 수와 별개로 분당 토큰 수를 센다.

동시에 처리 중인 요청 수를 세는 제한도 따로 있다. 1초에 1개만 보내도 요청 하나가 30초씩 걸리면 30개가 동시에 서버를 붙잡는다. 오래 걸리는 내보내기나 리포트에는 "초당 몇 개"보다 "동시 몇 개"가 더 맞는다. 시작할 때 1을 더하고 끝날 때 1을 빼는 카운터라서, 앱이 죽으면 빼는 걸 못 하고 카운터가 새는 일이 생긴다. 항목마다 만료 시각을 두는 정렬 집합으로 세거나 키에 짧은 수명을 건다.

## 처음 배포할 때는 세기만 한다

한도를 처음 걸 때 가장 흔한 사고가 처음 사례 같은 정상 사용자 차단이다. 그래서 순서를 지킨다.

1. 지금 접근 로그에서 키별 요청 수 분포를 뽑는다. 초 단위와 분 단위의 p99, 최댓값, 상위 20개 키를 본다.
2. 한도를 정하고 거절하지 않고 "거절했을 요청"만 기록하는 모드로 배포한다. nginx의 `limit_req_dry_run`이 이 모드다.
3. 며칠 동안 걸렸을 키를 본다. 사내 NAT, 모니터링 도구, 파트너 배치 작업 같은 정상 트래픽이 섞여 있으면 한도를 고치거나 예외 키로 뺀다.
4. 거절을 켠다. 고객이 볼 수 있는 문서에 한도와 헤더 형식을 적는다.

거절을 켠 뒤에는 이런 지표를 본다. 전체 응답 중 429 비율과 키별 429 상위 목록, 제한 장치의 Redis 호출 지연(p99), Redis 에러와 fail open 횟수. 429 비율이 갑자기 오르면 공격일 수도 있지만, 배포 직후라면 키를 뽑는 코드나 앞단 설정이 바뀐 걸 먼저 의심한다. 위에서 본 LB 주소로 세는 실수가 대표적이다.

헬스 체크와 내부 서비스 사이 호출은 사용자 한도에서 뺀다. 로드 밸런서의 헬스 체크가 429를 받으면 정상 인스턴스를 빼 버린다. 쿠버네티스라면 프로브 경로를 제한 장치 앞에서 분기한다.

## 이런 증상이면 여기부터 본다

"배포 직후 전체 사용자가 429를 받는다"면 키가 하나로 뭉친 것이다. 제한 장치 로그에서 거절한 키를 찍어 보고 LB나 CDN의 IP가 보이면 실제 IP 설정(`set_real_ip_from`, `trust proxy`)을 확인한다.

"한 고객사만 아침마다 429를 받는다"면 NAT 뒤의 여러 사람이 IP 한도를 나눠 쓰는 경우가 많다. 로그인 전 한도를 넉넉히 하고, 로그인 뒤에는 사용자 키로 센다.

"한도를 걸었는데도 특정 IP의 요청이 계속 들어온다"면 `X-Forwarded-For`의 맨 앞 값을 쓰고 있는지 본다. 공격자가 매번 다른 값을 넣고 있을 수 있다. IPv6라면 /128 단위로 세고 있는지도 본다.

"평소엔 괜찮은데 Redis 장애 때 API 전체가 느려졌다"면 제한 장치의 Redis 타임아웃이 기본값(수 초)으로 남아 있는 것이다. 수십 ms로 줄이고 실패 시 동작을 정해 둔다.

"429 수보다 요청 수가 몇 배 많다"면 클라이언트가 429에 즉시 재시도하고 있다. 클라이언트 쪽 재시도 설정을 고치고, 공개 API라면 `Retry-After`를 무시하는 키에 더 긴 차단을 거는 것도 방법이다.

## 알고리즘보다 오래 손대는 것

알고리즘은 한 번 고르면 잘 바뀌지 않는다. 운영하면서 계속 손대는 건 키를 무엇으로 뽑을지, 층마다 어떤 한도를 걸지, 저장소가 멈추면 어떻게 할지다. 거절할 때는 429와 `Retry-After`로 언제 다시 오면 되는지 알려 주고, 처음 배포는 세기만 하는 모드로 시작한다.

## 면접에서 나올 만한 질문

### 요청 수 제한은 어디에 두나요?

한 곳이 아니라 층마다 아는 정보에 맞춰 나눠 둔다. 엣지(CDN, WAF, nginx)에서는 IP 기준으로 명백한 폭주를 싸게 막고, 게이트웨이에서는 인증된 API 키나 사용자 기준으로 요금제 한도를, 앱에서는 문자 발송처럼 업무 맥락이 필요한 한도를 건다. 앞단일수록 싸게 막지만 아는 게 적고, 뒷단일수록 정밀하지만 이미 자원을 썼다.

### IP로 제한할 때 주의할 점은 무엇인가요?

NAT 뒤의 많은 사용자가 IP 하나를 나눠 쓰고, 앞단 프록시가 있으면 소켓 주소가 프록시 주소라는 점이다. X-Forwarded-For는 오른쪽부터 내 프록시를 건너뛰고 처음 나오는 주소를 써야 하고, 맨 앞 값은 클라이언트가 위조할 수 있다. IPv6는 /64 단위로 묶어 센다.

### 429와 503은 어떻게 구분하나요?

429는 클라이언트가 자기 한도를 넘었다는 뜻이고, 503은 서버가 지금 감당할 수 없다는 뜻이다. 둘 다 Retry-After를 붙일 수 있다. 제한 저장소 장애로 막을 때처럼 클라이언트 잘못이 아니면 503을 쓰고, 둘을 나눠 두면 모니터링에서 장애와 정상적인 거절이 섞이지 않는다.

### 제한 저장소인 Redis가 죽으면 어떻게 하나요?

먼저 Redis 호출에 수십 ms의 짧은 타임아웃을 걸어 제한 장치가 장애의 원인이 되지 않게 한다. 그다음 일반 API는 통과시키고(fail open), 로그인이나 문자 발송처럼 한도가 곧 보안이나 비용인 곳은 막는다(fail closed). fail open이라도 인스턴스마다 넉넉한 로컬 한도를 하나 더 걸어 최소한의 바닥을 남긴다.

### 클라이언트는 429를 받으면 어떻게 해야 하나요?

Retry-After가 있으면 그 시간만큼, 없으면 지수 백오프로 기다리고 지터를 더해 여러 클라이언트가 동시에 몰리지 않게 한다. 라이브러리의 자동 재시도가 429에 즉시 다시 보내면 거절이 몇 배로 불어나니 설정을 확인한다. 429는 처리 전에 거절된 응답이라 POST라도 다시 보내도 겹치지 않는다.

### 한도 숫자는 어떻게 정하고 배포하나요?

접근 로그에서 키별 초당·분당 요청 수의 p99와 상위 키를 먼저 보고 여유를 둔 값으로 시작한다. 처음에는 거절하지 않고 거절했을 요청만 기록하는 모드로 배포해서, 사내 NAT나 파트너 배치 같은 정상 트래픽이 걸리는지 확인한 뒤 거절을 켠다. 켠 뒤에는 429 비율과 키별 상위 목록, 제한 장치 지연을 지표로 본다.

### 요청마다 비용이 다르면 어떻게 제한하나요?

비싼 엔드포인트에 따로 낮은 한도를 걸거나, 요청마다 비용만큼 토큰을 여러 개 쓰게 한다. 오래 걸리는 작업은 초당 요청 수보다 동시 처리 수를 제한하는 편이 맞다. GitHub GraphQL API의 점수 한도나 LLM API의 분당 토큰 한도가 같은 생각이다.
