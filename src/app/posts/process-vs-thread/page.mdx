<EasyIntro>
  컴퓨터에서 프로그램 하나가 돌아가려면 자기만의 작업 공간이 필요하다. 이 작업 공간 하나를 프로세스라고 부르고, 그 안에서 실제로 일을 하는 일꾼을 스레드라고 부른다.

  프로세스는 벽으로 나뉜 작업실과 같다. 작업실마다 책상과 서랍이 따로 있어서 옆 작업실에서 불이 나도 내 작업실의 물건은 멀쩡하다. 대신 옆 작업실에 물건을 건네려면 문을 열고 복도를 지나야 해서 번거롭다.

  스레드는 한 작업실 안에서 일하는 여러 일꾼이다. 같은 책상과 서랍을 같이 쓰니 물건을 주고받기가 아주 빠르다. 하지만 한 명이 서랍을 엉망으로 만들면 모두가 피해를 보고, 작업실에 불이 나면 다 같이 나가야 한다.

  그래서 크롬은 탭이 하나 고장 나도 다른 탭이 살아남도록 작업실을 여러 개 쓰고, 많은 서버는 빠르게 협력하려고 한 작업실에 일꾼을 여럿 둔다. 무엇을 고를지는 안전함과 빠름 중 무엇이 더 중요한지에 달려 있다.
</EasyIntro>

크롬에서 탭 하나가 멈추면 "앗, 이런!" 화면이 그 탭에만 뜨고 나머지 탭은 멀쩡하다. 작업 관리자를 열어 보면 탭과 확장 프로그램마다 줄이 따로 있고, 각 줄에 메모리가 따로 잡혀 있다. 반대로 Node.js 서버는 `ps`로 보면 프로세스 하나가 조용히 떠 있을 뿐인데 초당 수천 건을 받는다. 같은 "많은 일을 동시에 하기"인데 하나는 프로세스를 잔뜩 띄우고, 하나는 거의 한 줄로 버틴다.

이 차이를 이해하려면 프로세스와 스레드가 각각 무엇을 따로 갖고 무엇을 같이 쓰는지 알아야 한다. 이 글에서는 둘이 나눠 갖는 것과 공유하는 것, 둘 사이를 오갈 때 드는 컨텍스트 스위칭 비용, `fork`와 copy-on-write, 병렬과 동시성의 차이를 직접 재 본다. 그다음 Nginx·Gunicorn·PostgreSQL·JVM·Go·Node가 각자 어떤 모양을 골랐는지, 스레드를 늘리면 어디서부터 느려지는지까지 간다. 환경은 Ubuntu 24.04, 4코어 VM, gcc 13, Go 1.24, Node 22다. 시간 숫자는 이 VM에서 잰 값이라 절댓값보다 비율을 보면 된다.

이 주제의 다른 글: 여러 스레드가 순서를 맞추는 도구는 [뮤텍스, 세마포어, 모니터 글](/posts/mutex-semaphore-monitor), 누가 다음에 CPU를 받는지는 [CPU 스케줄링과 인터럽트 글](/posts/cpu-scheduling-interrupts)에서 다룬다.

## 작업실과 일꾼

운영체제 입장에서 프로세스는 "실행 중인 프로그램 하나에 묶인 자원 꾸러미"다. 주소 공간(코드, 전역 변수, 힙), 열린 파일 목록, 권한, 시그널 처리 방법 같은 것이 들어 있다. 스레드는 그 꾸러미 안에서 실제로 CPU 위를 달리는 실행 흐름이다. 지금 어느 명령을 실행 중인지 가리키는 프로그램 카운터, 레지스터 값, 함수 호출을 쌓는 스택이 스레드마다 따로 있다.

EasyIntro의 비유로 말하면 프로세스는 벽으로 나뉜 작업실이고, 스레드는 그 안의 일꾼이다. 작업실이 하나뿐이면 일꾼도 하나다. 우리가 "단일 스레드 프로그램"이라고 부르는 것은 일꾼이 한 명인 작업실이다.

운영체제는 프로세스마다 이 정보를 담는 기록부를 둔다. 교과서는 이것을 PCB(Process Control Block)라고 부른다. 리눅스에서는 `task_struct`라는 구조체가 그 역할을 하는데, 재미있게도 리눅스는 프로세스와 스레드를 구분하지 않고 둘 다 `task_struct` 하나로 표현한다. 차이는 "무엇을 같이 쓰기로 했느냐"뿐이다.

## 무엇을 같이 쓰고 무엇을 따로 갖나

리눅스에서 새 실행 흐름은 `clone()` 시스템 콜로 만든다. 이때 플래그로 무엇을 부모와 같이 쓸지 고른다. `CLONE_VM`이면 주소 공간을, `CLONE_FILES`면 파일 디스크립터 표를, `CLONE_SIGHAND`면 시그널 처리기를 같이 쓰고, `CLONE_THREAD`면 같은 스레드 그룹(같은 PID)에 들어간다. glibc의 `pthread_create`는 이 플래그를 모두 켜서 부르고, `fork`는 거의 다 끈 채로 부른다. 그래서 같은 함수를 부르는데 하나는 스레드가 되고 하나는 프로세스가 된다.

같이 쓰는 것과 따로 갖는 것을 정리하면 이렇다.

| | 스레드끼리 같이 쓴다 | 스레드마다 따로 갖는다 |
|---|---|---|
| 메모리 | 코드, 전역 변수, 힙, mmap 영역 | 스택, 스레드 로컬 저장소(TLS, `errno` 포함) |
| 실행 상태 | | 프로그램 카운터, 레지스터, 스케줄링 정보 |
| 자원 | 파일 디스크립터, 현재 디렉터리, 시그널 처리기, 사용자 권한 | 시그널 마스크, TID |

표로 보면 당연한 말 같지만 결과는 크다. 전역 변수 하나를 고치는 실험으로 확인해 보자. 자식 프로세스와 스레드가 같은 `counter`에 100을 더한다.

```c
int counter = 0;
void *work(void *arg) { counter += 100; return NULL; }

int main(void) {
    pid_t pid = fork();
    if (pid == 0) {                       // 자식 프로세스
        counter += 100;
        printf("child  pid=%d counter=%d\n", getpid(), counter);
        exit(0);
    }
    waitpid(pid, NULL, 0);
    printf("parent after fork  counter=%d\n", counter);

    pthread_t t;
    pthread_create(&t, NULL, work, NULL); // 같은 프로세스 안의 스레드
    pthread_join(t, NULL);
    printf("parent after thread counter=%d\n", counter);
}
```

```bash
gcc -O2 -pthread share.c -o share && ./share   # 빌드하고 실행
```

```text
child  pid=28851 counter=100
parent after fork  counter=0
parent after thread counter=100
```

자식은 100을 봤지만 부모의 `counter`는 그대로 0이다. 자식이 고친 것은 자기 사본이었다. 스레드가 더한 100은 부모에게 그대로 보인다. 같은 메모리를 쓰기 때문이다.

이 차이에서 두 가지가 따라 나온다. 스레드는 데이터를 주고받는 비용이 0에 가깝다. 포인터 하나를 넘기면 끝이다. 대신 둘이 동시에 같은 값을 고치면 깨진다. 그래서 스레드를 쓰는 순간 [경쟁 상태](/posts/race-conditions)와 [스레드 안전](/posts/thread-safety)을 신경 써야 한다. 프로세스는 반대로 서로의 메모리를 망가뜨릴 수 없지만, 데이터를 주고받으려면 파이프, 소켓, 공유 메모리 같은 IPC(프로세스 간 통신)를 따로 놓아야 한다.

장애 격리도 여기서 갈린다. 스레드 하나가 널 포인터를 밟아 SIGSEGV를 받으면 프로세스 전체가 죽는다. 시그널 처리와 주소 공간을 같이 쓰기 때문이다. 크롬이 탭과 사이트를 프로세스로 나누는 첫 번째 이유가 이것이고, 두 번째 이유는 보안이다. 2018년 Spectre 공격이 알려진 뒤 크롬은 사이트마다 렌더러 프로세스를 나누는 Site Isolation을 데스크톱에서 기본으로 켰다. 같은 프로세스 안이면 다른 사이트의 메모리를 추측으로 읽어 낼 여지가 있어서, 벽을 아예 주소 공간 단위로 세운 것이다. 다만 메모리가 모자라면 크롬도 같은 사이트의 탭을 한 프로세스로 묶기 때문에 "탭 하나에 프로세스 하나"가 언제나 맞지는 않다.

## ps로 스레드 세어 보기

이론을 실제 프로세스에서 확인해 보자. 타이머 하나만 걸어 둔 Node 프로세스를 띄우고 스레드를 센다.

```bash
node -e 'setInterval(()=>{},1000)' &   # 아무 일도 안 하는 Node 프로세스
P=$!
ps -o pid,nlwp,cmd -p $P               # NLWP: 이 프로세스의 스레드 수
ps -eLf | awk -v p=$P 'NR==1||$2==p'   # -L: 스레드마다 한 줄씩
```

```text
  PID NLWP CMD
 1718    7 node -e setInterval(()=>{},1000)
UID        PID  PPID   LWP  C NLWP STIME TTY          TIME CMD
root      1718  1717  1718  7    7 18:39 ?        00:00:00 node -e setInterval(()=>{},1000)
root      1718  1717  1720  0    7 18:39 ?        00:00:00 node -e setInterval(()=>{},1000)
root      1718  1717  1721  0    7 18:39 ?        00:00:00 node -e setInterval(()=>{},1000)
root      1718  1717  1722  0    7 18:39 ?        00:00:00 node -e setInterval(()=>{},1000)
root      1718  1717  1723  0    7 18:39 ?        00:00:00 node -e setInterval(()=>{},1000)
root      1718  1717  1724  0    7 18:39 ?        00:00:00 node -e setInterval(()=>{},1000)

```

"싱글 스레드"라는 Node도 스레드가 7개다. `PID`는 모두 1718로 같고 `LWP`(light-weight process, 리눅스의 스레드 ID)만 다르다. 첫 줄은 LWP가 PID와 같은 메인 스레드다. 자바스크립트는 이 메인 스레드 하나에서 돌고, 나머지는 V8의 GC·컴파일 보조 스레드와 libuv 스레드 풀이다. 이 이야기는 [Node.js 서버 런타임 글](/posts/nodejs-server-runtime)에서 자세히 다뤘다.

같은 정보는 `/proc`에도 있다. 스레드마다 `/proc/<pid>/task/<tid>/` 디렉터리가 하나씩 생긴다.

```bash
grep -E '^(Threads|voluntary|nonvoluntary)' /proc/$P/status   # 스레드 수와 문맥 교환 횟수
cat /proc/$P/task/*/comm | sort | uniq -c                      # 스레드 이름별 개수
kill $P
```

```text
Threads:	7
voluntary_ctxt_switches:	5
nonvoluntary_ctxt_switches:	2
      1 DelayedTaskSche
      6 node
```

`voluntary_ctxt_switches`와 `nonvoluntary_ctxt_switches`는 뒤에서 다시 읽는다. 이름만 기억해 두자. 앞은 스스로 CPU를 내놓은 횟수, 뒤는 빼앗긴 횟수다. `/proc/<pid>/status`의 값은 메인 스레드 기준이고, 스레드별 값은 `task/<tid>/status`에 따로 있다.

직접 비용은 레지스터 저장·복원과 스케줄러 코드 실행이다. 프로세스 사이를 오가면 하나가 더 붙는다. 주소 공간이 다르니 페이지 테이블을 바꿔야 하고, 가상 주소를 물리 주소로 바꾼 결과를 담아 두는 TLB가 쓸모없어진다. TLB가 무엇인지는 [가상 메모리 글](/posts/virtual-memory-paging)에 있다. 요즘 x86은 PCID라는 기능으로 TLB 항목에 주소 공간 꼬리표를 붙여, 전환할 때마다 전부 버리지는 않는다(리눅스 4.14부터 쓴다). 그래서 "프로세스 전환은 TLB 플러시 때문에 훨씬 비싸다"는 말은 예전만큼 크게 맞지는 않다.

얼마나 차이 나는지 재 봤다. 파이프 두 개로 1바이트를 주고받는 핑퐁을 프로세스 둘, 스레드 둘로 각각 돌린다. `taskset -c 0`으로 한 코어에 묶어 두면 한 번 주고받을 때마다 반드시 교환이 일어난다.

```bash
gcc -O2 -pthread pingpong.c -o pingpong
taskset -c 0 ./pingpong process   # 프로세스 둘이 0번 코어에서 핑퐁
taskset -c 0 ./pingpong thread    # 같은 프로세스의 스레드 둘이 핑퐁
```

```text
process 100000 round trips: 2.07 us per switch
thread  100000 round trips: 1.75 us per switch
process 100000 round trips: 1.92 us per switch
thread  100000 round trips: 1.78 us per switch
```

파이프 시스템 콜 비용이 들어간 값인데도 스레드 쪽이 10~15% 빠르다. 생각보다 작은 차이다. 진짜 비용은 이 숫자 밖에 있다. 교환 직후의 스레드는 캐시가 차갑다. L1·L2 캐시에는 방금 내려간 스레드의 데이터가 차 있으니 처음 몇 마이크로초는 메모리를 기다리며 보낸다. 작업 데이터가 클수록 이 간접 비용이 직접 비용보다 커진다. 캐시가 왜 그렇게 중요한지는 [CPU 캐시 글](/posts/cpu-cache-hierarchy)에서 숫자로 봤다.

## fork는 복사하는 척만 한다

`fork()`는 부모 프로세스를 통째로 복제한다. 1GiB를 쓰는 프로세스가 fork할 때마다 1GiB를 복사한다면 아무도 못 쓸 것이다. 그래서 커널은 페이지를 복사하지 않고 페이지 테이블만 복사한 뒤 양쪽 모두 읽기 전용으로 표시한다. 누군가 그 페이지에 쓰려고 하면 그때 page fault가 나고, 커널이 그 페이지 하나만 복사해 준다. 이것이 copy-on-write(COW)다.

그렇다고 fork가 공짜는 아니다. 페이지 테이블 자체는 복사해야 하고, 페이지 테이블 크기는 프로세스가 쓰는 메모리에 비례한다. 부모의 힙을 미리 채워 두고 fork 속도를 재 봤다.

```bash
./spawn 0 1000      # 힙 0MiB, 1000번 fork
./spawn 256 200     # 힙 256MiB를 채운 뒤 fork
./spawn 1024 100    # 힙 1GiB를 채운 뒤 fork
```

```text
heap=0MiB fork+wait: 1234.6 us/each   pthread_create+join: 292.9 us/each
heap=256MiB fork+wait: 26807.6 us/each   pthread_create+join: 506.2 us/each
heap=1024MiB fork+wait: 103337.4 us/each   pthread_create+join: 20.6 us/each
```

fork는 힙이 커질수록 거의 정비례로 느려진다. 1GiB면 한 번에 100ms가 넘는다. 스레드 생성은 힙 크기와 상관이 없다(이 VM에서는 값이 들쭉날쭉했지만 커지는 경향은 없다). 이 차이가 실무에서 보이는 곳이 Redis다. Redis는 RDB 스냅숏을 뜰 때 fork를 하는데, 데이터가 수십 GiB면 그 순간 메인 스레드가 멈추고 요청 지연이 튄다. `INFO` 명령의 `latest_fork_usec`가 그 시간이다. 그리고 fork 뒤에 쓰기가 많으면 COW로 복사되는 페이지가 늘어 메모리가 최대 두 배 가까이 늘 수 있다.

새 프로그램을 실행할 목적으로 fork하는 거라면 더 나은 길이 있다. `posix_spawn`은 glibc 2.24부터 부모의 주소 공간을 복사하지 않고 잠깐 빌려 쓰는 방식(`CLONE_VM`과 `CLONE_VFORK`)으로 자식을 만든다. 같은 실험을 `/bin/true` 실행으로 바꿔 비교했다.

```text
heap=   0MiB  fork+exec:   2136.4 us   posix_spawn:   1884.6 us
heap= 256MiB  fork+exec:  20631.2 us   posix_spawn:   1772.7 us
heap=1024MiB  fork+exec:  59760.2 us   posix_spawn:   1592.9 us
```

부모가 클수록 차이가 벌어진다. 메모리를 많이 쓰는 JVM이나 Node 서버가 외부 명령을 자주 부르면 이 차이가 그대로 지연이 된다. 자바의 `ProcessBuilder`는 리눅스에서 기본으로 `posix_spawn`을 쓰고, Node의 `child_process.spawn`은 libuv가 플랫폼에 맞는 방법을 고른다.

## 스레드가 여럿인 프로세스를 fork하면

fork에는 함정이 하나 더 있다. 스레드가 여럿인 프로세스에서 fork하면 자식에는 fork를 부른 스레드 하나만 복제된다. 메모리는 통째로 넘어가는데 일꾼은 한 명만 따라온다. 그 순간 다른 스레드가 쥐고 있던 뮤텍스는 자식 메모리 안에서 "잠긴 상태"로 남고, 그 락을 풀어 줄 스레드는 자식에 존재하지 않는다.

가장 흔하게 밟는 곳이 `malloc`이다. 다른 스레드가 메모리 할당기의 내부 락을 쥔 채 fork가 일어나면, 자식이 `malloc`을 부르는 순간 영원히 멈춘다. 그래서 POSIX는 멀티스레드 프로세스에서 fork한 자식은 exec하기 전까지 비동기 시그널 안전 함수만 부르라고 정해 두었다. 파이썬 3.12부터는 스레드가 여럿인 상태에서 `os.fork()`를 부르면 `DeprecationWarning`을 내고, 3.14부터 리눅스의 `multiprocessing` 기본 시작 방식이 fork에서 forkserver로 바뀐 것도 이 문제 때문이다. 멀티스레드 서버에서 자식이 필요하면 fork 뒤 바로 exec하거나, 처음부터 `posix_spawn`을 쓴다. 이런 멈춤을 덤프로 찾는 법은 [데드락 글](/posts/deadlocks)에 있다.

## 벽 너머로 말을 거는 방법

프로세스로 나누기로 했다면 데이터를 주고받을 길을 따로 놓아야 한다. 고를 수 있는 길은 생각보다 많고, 속도와 편의가 서로 다르다.

- 파이프: 부모와 자식 사이의 한 방향 바이트 흐름이다. 셸의 `|`가 이것이다. 앞의 핑퐁 실험도 파이프로 했다.
- 유닉스 도메인 소켓: 같은 머신 안에서 쓰는 소켓이다. TCP처럼 쓰지만 네트워크 스택을 거치지 않아 빠르다. PostgreSQL과 Docker 데몬이 기본으로 여는 `/var/run/...sock` 파일이 이것이고, 파일 디스크립터 자체를 다른 프로세스에 넘길 수도 있다.
- 공유 메모리: `shm_open`과 `mmap`으로 같은 물리 페이지를 두 프로세스가 같이 본다. 복사가 없어 가장 빠르지만, 그 순간부터 스레드와 똑같이 동기화를 직접 해야 한다. 벽에 창문을 하나 뚫는 셈이다.
- 시그널: 정수 하나짜리 알림이다. 데이터를 싣기보다 "설정을 다시 읽어라"(SIGHUP)처럼 쓴다. 시그널은 [프로세스와 시그널 글](/posts/linux-processes-signals)에서 다뤘다.

여러 머신으로 넘어가면 결국 TCP와 메시지 큐가 된다. 프로세스로 나눈 설계는 나중에 머신을 나누기도 쉽다는 장점이 있다. 반대로 스레드끼리 포인터를 주고받던 설계는 머신을 나누려면 다시 짜야 한다.

## 동시에 한다는 말의 두 가지 뜻

여기서 용어 하나를 바로잡고 가자. 동시성(concurrency)과 병렬성(parallelism)은 다르다. 동시성은 여러 일이 "진행 중"인 상태다. 코어가 하나여도 일을 잘게 쪼개 번갈아 하면 동시성이 있다. 병렬성은 여러 일이 같은 순간에 "실행"되는 것이고, 코어가 여러 개여야 가능하다.

Node 서버는 동시성은 높지만 자바스크립트 실행에는 병렬성이 없다. 요청 1만 개를 붙잡고 있어도 어느 순간이든 JS를 실행하는 스레드는 하나다. 기다리는 일(네트워크, 디스크)이 대부분이라 이걸로 충분하다. 반대로 이미지 변환처럼 CPU를 태우는 일은 동시성으로는 빨라지지 않고 병렬성이 있어야 빨라진다.

CPU만 쓰는 계산을 스레드 수를 바꿔 가며 돌려 봤다. 전체 일의 양은 4억 번 더하기로 고정하고 스레드끼리 나눈다.

```bash
for n in 1 4 16 256; do ./nthreads $n; done        # 락 없이 각자 계산
for n in 1 4 16 256; do ./nthreads $n lock; done   # 256번마다 공유 카운터를 뮤텍스로 갱신
```

```text
threads=   1 lock=0  0.74s  voluntary=1 nonvoluntary=57
threads=   4 lock=0  0.24s  voluntary=2 nonvoluntary=107
threads=  16 lock=0  0.22s  voluntary=4 nonvoluntary=198
threads= 256 lock=0  0.20s  voluntary=83 nonvoluntary=235
threads=   1 lock=1  0.68s  voluntary=1 nonvoluntary=10
threads=   4 lock=1  0.52s  voluntary=4178 nonvoluntary=186
threads=  16 lock=1  0.46s  voluntary=5630 nonvoluntary=806
threads= 256 lock=1  0.41s  voluntary=6317 nonvoluntary=654
```

락이 없으면 1개에서 4개로 늘릴 때 3배 빨라지고, 그 뒤로는 거의 그대로다. 코어가 4개니 동시에 달릴 수 있는 스레드도 4개다. 16개, 256개로 늘려도 남는 스레드는 줄 서서 기다릴 뿐이고 `nonvoluntary`(빼앗긴 횟수)만 늘어난다.

공유 카운터를 뮤텍스로 갱신하게 하면 이야기가 달라진다. 4개로 늘려도 0.68초가 0.52초로 줄 뿐이다. `voluntary`가 1에서 4178로 뛰었다. 락을 못 잡은 스레드가 잠들었다 깨기를 반복한 흔적이다. 일의 일부가 한 줄로만 지나갈 수 있으면 코어를 아무리 늘려도 그 부분이 상한을 정한다.

## 코어를 늘려도 빨라지지 않는 몫

이 상한을 식으로 적은 것이 암달의 법칙이다. 전체 일 중 병렬로 나눌 수 있는 비율이 p이고 코어가 n개면, 최대 속도 향상은 1 / ((1 − p) + p / n)이다. p가 0.9여도 코어를 무한히 늘리면 10배에서 멈춘다. 나머지 10%가 한 줄로 지나가기 때문이다. 같은 식은 서버 대수를 늘릴 때도 그대로 적용된다([수평·수직 확장 글](/posts/scaling-horizontal-vertical)).

직접 계산해 보자. 소수 둘째 자리에서 반올림한다.

## 서버들은 각자 다른 모양을 골랐다

이제 같은 문제, "요청을 여러 개 동시에 처리한다"를 서버들이 어떻게 풀었는지 보면 고른 이유가 보인다.

Nginx는 마스터 프로세스 하나와 워커 프로세스 여럿으로 돈다. `worker_processes auto;`면 코어 수만큼 워커를 띄운다. 각 워커는 스레드 하나로 이벤트 루프를 돌며 수천 개 연결을 다룬다. 프로세스로 나눈 덕에 워커 하나가 죽어도 마스터가 새로 띄우고, 설정을 다시 읽을 때도 새 워커를 띄운 뒤 옛 워커를 천천히 내린다. 연결 수는 이벤트 루프로, 코어 활용은 프로세스 수로 푼 모양이다. 자세한 설정은 [Nginx 기본 글](/posts/nginx-basics)에 있다.

Gunicorn(파이썬)은 프리포크(pre-fork) 모델이다. 미리 워커 프로세스를 여럿 띄워 두고 각자 요청을 받는다. 파이썬은 GIL 때문에 한 프로세스 안에서 파이썬 코드를 실행하는 스레드가 한 번에 하나뿐이라, CPU를 여러 개 쓰려면 프로세스를 늘려야 한다. 공식 문서는 워커 수를 `2 × 코어 + 1`에서 시작하라고 권한다. `--threads`로 워커마다 스레드를 더 주면 I/O 대기는 겹칠 수 있다. 파이썬 3.13부터 GIL을 끈 빌드가 실험적으로 나왔지만 아직 기본값은 아니다.

PostgreSQL은 연결마다 백엔드 프로세스를 하나씩 띄운다. 그래서 연결 하나가 몇 MB씩 먹고, 연결을 수천 개 열면 서버가 버거워한다. 앞단에 커넥션 풀을 두는 이유다. MySQL은 같은 일을 연결마다 스레드로 한다. 같은 DB인데 고른 모양이 달라서 "연결 수 한도"의 감각도 다르다.

JVM 서버(Tomcat, Spring MVC)는 요청마다 스레드 하나를 쓰는 thread-per-request다. Tomcat의 기본 `maxThreads`는 200이다. 자바 스레드는 OS 스레드와 1:1이라 스레드 하나마다 스택(기본 1MiB 예약)과 커널 자료 구조가 붙는다. 수만 개로 늘리기 어려운 이유다. Java 21의 가상 스레드는 이 1:1을 끊어서 OS 스레드 몇 개 위에 자바 스레드 수십만 개를 올린다. 이 이야기는 [JVM 메모리와 스레드 글](/posts/java-jvm-memory-gc)에서 다뤘다.

## 스레드를 더 가볍게: 그린 스레드와 고루틴

OS 스레드가 무거운 이유는 커널이 하나하나 관리하기 때문이다. 만들 때 시스템 콜이 필요하고, 교환할 때 커널에 들어가야 하고, 스택을 넉넉히 예약해야 한다. 그렇다면 런타임이 사용자 공간에서 직접 실행 흐름을 관리하면 어떨까. 이런 것을 그린 스레드, 또는 사용자 수준 스레드라고 부른다. 런타임이 M개의 가벼운 스레드를 N개의 OS 스레드 위에 얹는다고 해서 M:N 모델이라고도 한다.

Go의 고루틴이 대표적이다. 고루틴은 2KB 스택으로 시작해 필요하면 늘고, Go 스케줄러가 GOMAXPROCS개의 OS 스레드 위에서 고루틴을 돌린다. 고루틴 1만 개와 pthread 1만 개를 각각 잠재워 두고 비교했다.

```bash
./gor &                                  # 고루틴 1만 개가 1시간씩 잔다
ps -o pid,nlwp,rss,cmd -p $!
./t &                                    # pthread 1만 개가 1시간씩 잔다
sleep 10; ps -o pid,nlwp,rss,vsz,cmd -p $!
```

```text
  PID NLWP   RSS CMD
 2786    6 28496 ./gor
  PID NLWP   RSS    VSZ CMD
10648 10001 84616 81965472 ./t
```

고루틴 1만 개는 OS 스레드 6개 위에 올라가 있고 메모리(RSS)는 28MB다. pthread 1만 개는 스레드가 10001개, RSS 85MB에 가상 메모리(VSZ)가 78GiB다. 스레드마다 스택 8MiB(`ulimit -s`의 기본값 8192KB)를 예약했기 때문이다. 실제로 쓴 페이지만 RSS에 잡혀서 서버가 당장 죽지는 않지만, 만드는 데만 몇 초가 걸렸고 커널은 1만 개를 따로 스케줄링해야 한다. 고루틴 이야기는 [Go 동시성 글](/posts/go-concurrency-basics)에서 더 볼 수 있다.

가벼운 스레드에도 대가가 있다. 고루틴 하나가 cgo 호출이나 블로킹 시스템 콜에 갇히면 런타임은 그 OS 스레드를 놓아주고 새 스레드를 만들어야 한다. 자바 가상 스레드는 `synchronized` 블록 안에서 블로킹하면 OS 스레드에 붙어 버리는 pinning 문제가 있었다(JDK 24에서 대부분 풀렸다). 런타임이 모든 블로킹 지점을 알아야 M:N이 제대로 돈다.

## 스레드가 너무 많을 때 나타나는 증상

현장에서 프로세스·스레드 모델을 잘못 고르면 증상은 대개 셋 중 하나로 나온다.

첫째, 스레드를 못 만든다. 자바라면 `java.lang.OutOfMemoryError: unable to create native thread`, C나 Go라면 `pthread_create failed: Resource temporarily unavailable`이 찍힌다. 메모리가 아니라 개수 한도에 걸린 경우가 많다. 한도는 여러 겹이다.

```bash
cat /proc/sys/kernel/threads-max        # 시스템 전체 스레드 한도
ulimit -u                               # 이 사용자가 만들 수 있는 프로세스+스레드 수
cat /sys/fs/cgroup/pids.max             # 컨테이너(cgroup v2)의 pids 한도. 쿠버네티스 podPidsLimit가 여기로 간다
```

리눅스는 스레드도 task 하나로 세기 때문에 `pids.max`에는 스레드가 포함된다. 컨테이너 안에서 스레드가 수천 개로 불어나는 서비스라면 이 값부터 본다. cgroup 파일을 읽는 법은 [네임스페이스와 cgroup 글](/posts/linux-namespaces-cgroups)에 있다.

둘째, CPU는 다 쓰는데 처리량이 안 는다. 이때 `pidstat -w`로 문맥 교환 횟수를 본다.

```bash
pidstat -w -t -p <pid> 1    # 스레드별 초당 자발적(cswch/s)·비자발적(nvcswch/s) 교환
```

`nvcswch/s`가 높으면 코어보다 달리려는 스레드가 많아서 타임 슬라이스마다 빼앗기고 있다는 뜻이다. CPU 위주 작업의 스레드 풀이 너무 크다. `cswch/s`가 높으면 스레드들이 락이나 I/O를 기다리며 자주 잠든다. 앞의 뮤텍스 실험에서 `voluntary`가 수천으로 뛴 모양이다. 이때는 스레드를 줄이거나 락이 지키는 구간을 줄인다.

셋째, 컨테이너에서 코어 수를 잘못 읽는다. CPU limit이 2인 Pod에서 런타임이 노드의 64코어를 보고 스레드 풀을 64개로 잡으면, 한도 안에서 64개가 다투다 쓰로틀링에 걸린다. JVM은 10 버전 무렵부터 cgroup 한도를 읽고, Go는 1.25부터 GOMAXPROCS가 CPU limit을 따른다. 그 전 버전이나 직접 짠 풀은 직접 맞춰야 한다. 쓰로틀링이 어떻게 일어나는지는 [CPU 스케줄링 글](/posts/cpu-scheduling-interrupts)과 [requests와 limits 글](/posts/k8s-pod-resources)에서 본다.

## 벽을 세울지, 책상을 같이 쓸지

프로세스는 주소 공간에 벽을 세워 안전을 사고, 스레드는 벽을 허물어 빠른 협력을 산다. 장애와 보안을 격리해야 하면 프로세스, 데이터를 잘게 자주 주고받아야 하면 스레드, 기다리는 일이 대부분이면 이벤트 루프나 가벼운 스레드가 맞다. 실제 서버는 대개 이 셋을 섞는다. Nginx는 프로세스와 이벤트 루프를, Node는 이벤트 루프와 스레드 풀을, Go는 OS 스레드 위의 고루틴을 쓴다. 어떤 모양이든 스레드를 같이 쓰기로 한 순간부터는 순서를 맞추는 도구가 필요하다. 그 이야기는 [뮤텍스, 세마포어, 모니터 글](/posts/mutex-semaphore-monitor)에서 이어 간다.

## 면접에서 나올 만한 질문

### 프로세스와 스레드의 차이는 무엇인가요?

프로세스는 주소 공간, 파일 디스크립터, 권한 같은 자원을 가진 실행 단위이고, 스레드는 그 안에서 스택과 레지스터만 따로 가진 실행 흐름이다. 스레드끼리는 힙과 전역 변수, 열린 파일을 같이 쓰므로 데이터 공유는 빠르지만 동기화가 필요하고, 하나가 죽으면 프로세스 전체가 죽는다. 프로세스끼리는 메모리가 격리되어 안전하지만 통신하려면 IPC가 필요하다. 리눅스는 둘 다 `task_struct`로 표현하고 `clone()` 플래그로 무엇을 공유할지만 다르게 정한다.

### 컨텍스트 스위칭은 왜 비용이 드나요? 프로세스 전환이 스레드 전환보다 비싼 이유는요?

레지스터를 저장하고 복원하며 커널의 스케줄러 코드를 도는 직접 비용이 있고, 새 스레드가 차가운 캐시로 시작하는 간접 비용이 있다. 다른 프로세스로 넘어가면 페이지 테이블을 바꿔야 하므로 TLB 항목이 쓸모없어진다. 다만 PCID 덕분에 요즘은 TLB를 매번 다 비우지는 않아서, 한 코어 핑퐁으로 재 보면 직접 비용 차이는 10~15% 정도였다. 실무에서 더 큰 건 캐시 오염과 교환 횟수 자체다.

### fork는 메모리를 다 복사하나요?

복사하지 않는다. 페이지 테이블만 복사하고 페이지를 읽기 전용으로 공유하다가, 쓰기가 일어난 페이지만 그때 복사하는 copy-on-write를 쓴다. 그래도 페이지 테이블 복사 비용은 부모 메모리에 비례해서, 1GiB 프로세스의 fork는 이 VM에서 100ms가 넘었다. Redis 스냅숏의 지연 스파이크가 이것이고, 새 프로그램 실행이 목적이면 `posix_spawn`이 부모 크기와 상관없이 빠르다.

### 동시성과 병렬성은 어떻게 다른가요?

동시성은 여러 작업이 진행 중인 상태라서 코어 하나로도 번갈아 실행하면 된다. 병렬성은 같은 순간에 여러 작업이 실제로 실행되는 것이라 코어가 여러 개여야 한다. Node는 요청 수만 개를 동시에 다루지만 JS 실행은 병렬이 아니어서, 기다림이 많은 일에는 강하고 CPU를 태우는 일에는 약하다.

### 멀티프로세스 서버와 멀티스레드 서버는 언제 고르나요?

장애 격리와 보안이 중요하거나 언어 런타임이 병렬 실행을 막으면(GIL) 멀티프로세스를 고른다. Nginx 워커, Gunicorn, PostgreSQL이 이쪽이다. 요청끼리 메모리 캐시나 커넥션 풀을 자주 같이 써야 하면 멀티스레드가 싸다. JVM 서버, MySQL이 이쪽이다. 실무에서는 코어 수만큼 프로세스를 두고 그 안에서 이벤트 루프나 스레드 풀을 돌리는 혼합형이 흔하다.

### 스레드를 늘리면 계속 빨라지나요?

아니다. CPU만 쓰는 일은 코어 수에서 멈추고, 그 뒤로는 비자발적 문맥 교환만 늘어난다. 공유 자원이 있으면 암달의 법칙대로 직렬 구간이 상한을 정하고, 락 경합과 캐시 라인 이동 때문에 실제로는 그보다 일찍 꺾인다. CPU 작업은 코어 수 근처, I/O 작업은 대기 비율만큼 더 크게 풀을 잡는다.

### 그린 스레드, 고루틴, 가상 스레드는 OS 스레드와 무엇이 다른가요?

런타임이 사용자 공간에서 많은 가벼운 스레드를 적은 OS 스레드 위에 얹는 M:N 모델이다. 생성과 교환에 커널이 끼지 않고 스택이 작게 시작해서, 고루틴 1만 개가 OS 스레드 6개와 28MB로 돌았다. 대신 런타임이 모르는 블로킹(cgo, 일부 시스템 콜, 예전 자바의 synchronized pinning)을 만나면 OS 스레드를 붙잡혀 이점이 사라진다.

### 컨테이너에서 "스레드를 만들 수 없다"는 오류가 나면 무엇을 보나요?

메모리보다 개수 한도부터 본다. 리눅스는 스레드도 task로 세므로 cgroup의 `pids.max`, `ulimit -u`, `threads-max`에 스레드가 포함된다. `ps -o nlwp`로 프로세스의 스레드 수를 세고, 어떤 풀이 끝없이 커지는지 스레드 이름(`/proc/<pid>/task/*/comm`)으로 찾는다. 런타임이 노드 코어 수를 보고 풀을 크게 잡은 것은 아닌지도 확인한다.

### 스레드가 여럿인 프로세스에서 fork하면 무엇이 위험한가요?

자식에는 fork를 부른 스레드 하나만 복제되고, 다른 스레드가 쥐고 있던 락은 잠긴 채로 메모리에 남는다. 그 락을 풀 스레드가 자식에 없으니 자식이 `malloc` 같은 함수를 부르면 영원히 멈출 수 있다. 그래서 fork 뒤에는 바로 exec하거나 `posix_spawn`을 쓰고, 파이썬도 3.14부터 리눅스 기본 시작 방식을 forkserver로 바꿨다.
