## 분석 패키지 한 줄에 작업 열네 개

분석 이벤트에 스키마 버전 필드 하나를 넣는 PR을 올렸다. 바뀐 파일은 `packages/analytics` 아래 두 개뿐이다. 그런데 CI 로그를 열면 관리자 앱 빌드, 가격 포맷 테스트, UI 타입 검사까지 열네 개 작업이 전부 돈다. 분석 패키지를 쓰지도 않는 관리자 앱이 왜 다시 빌드되는 걸까.

CI가 저장소의 모양을 모르기 때문이다. `pnpm -r build && pnpm -r typecheck && pnpm -r test`는 "모든 패키지에서 이 스크립트를 돌려라"일 뿐, 무엇이 바뀌었고 그 변경이 누구에게 닿는지는 따지지 않는다. 이 글은 패키지 사이의 의존성으로 작업 그래프를 만들고, 바뀐 것과 그것에 의존하는 것만 골라 돌리고, 지난 결과를 가져다 쓰는 과정을 Turborepo로 직접 재 본다. 그리고 그 장치가 틀린 답을 내는 경우와, 모노레포가 오히려 짐이 되는 경우도 본다.

이 주제의 다른 글: 저장소 구조와 pnpm 워크스페이스, 공용 패키지 설계는 [프런트엔드 모노레포](/posts/frontend-monorepo)에서 다뤘다. 캐시 키가 무엇으로 만들어지는지, 환경 변수가 해시에서 빠질 때의 틀린 적중, 원격 캐시 서버와 캐시 오염은 [빌드 캐시로 CI 줄이기](/posts/build-caching)에 있으니 여기서는 반복하지 않는다.

실습 저장소는 앞 글의 것에 패키지 둘(`api-client`, `analytics`)을 더해 앱 둘, 패키지 다섯이다. 환경은 Node 22.22.0, pnpm 10.28.0, Turborepo 2.11.10, vCPU 4개 머신이다. 출력의 긴 작업 폴더 경로는 `~`로 줄였다. 시간은 이 머신에서 잰 값이라 다른 환경에서는 다르게 나온다.

## 패키지 그래프에서 작업 그래프로

Turborepo는 패키지가 아니라 작업(task) 단위로 생각한다. `turbo.json`에 각 작업이 무엇을 먼저 끝내야 하는지 적는다.

```json
{
  "tasks": {
    "build": { "dependsOn": ["^build"], "outputs": ["dist/**"] },
    "typecheck": { "dependsOn": ["^build"] },
    "test": { "dependsOn": ["build"] }
  }
}
```

`^build`의 `^`는 "내가 의존하는 패키지의"라는 뜻이다. web의 build는 web이 쓰는 ui, api-client, analytics의 build가 끝나야 시작한다. typecheck도 `^build`를 기다리는데, 다른 패키지의 `.d.ts`가 있어야 타입을 검사할 수 있어서다. `^`가 없는 `build`는 같은 패키지의 build를 뜻한다. 테스트가 `dist`를 불러 쓰니 내 빌드가 먼저다.

이 규칙과 `package.json`의 의존성을 곱하면 작업 그래프가 나온다. `--graph`를 주면 그래프를 DOT 형식 텍스트로 찍는다.

```bash
# 실행하지 않고 build 작업 그래프만 출력한다
npx turbo run build --graph
```

## 그래프가 정하는 실행 순서

그래프가 있으면 서로 기다릴 필요가 없는 작업을 동시에 돌릴 수 있다. 의존성이 없는 것부터 한 겹씩 벗겨 내듯 실행된다. 같은 겹에 있는 작업들은 CPU가 허락하는 만큼 함께 돈다(기본 동시 실행 수는 10이고 `--concurrency`로 바꾼다).

`pnpm -r`도 패키지 순서는 지킨다. 다만 `pnpm -r build && pnpm -r typecheck && pnpm -r test`처럼 쓰면 build가 저장소 전체에서 끝나야 typecheck가 시작한다. format의 test는 format의 build만 끝나면 돌 수 있는데도 두 앱의 Vite 빌드를 기다린다. Turborepo는 세 작업을 한 그래프에 놓고 돌리니 이런 빈틈이 메워진다. 캐시 없이도 그만큼 빨라진다. 아래 측정에서 6.52초가 5.60초가 된 부분이다.

## 바뀐 것과 그 위쪽만 고르기

빨라지는 진짜 이유는 고르는 데 있다. `--filter`는 작업을 돌릴 패키지를 고르는 선택자다. 실습 저장소의 main에서 마지막 커밋은 analytics만 고쳤다. 선택자를 바꿔 가며 어떤 패키지가 뽑히는지 `--dry=json`으로 봤다.

```bash
# 실행하지 않고, 뽑힌 패키지 목록만 본다
for f in '[HEAD^]' '...[HEAD^]' '@shop/analytics' '...@shop/format' '...^@shop/format' '@shop/web...'; do
  echo "== --filter=$f"
  npx turbo run build --filter="$f" --dry=json | jq -c '.packages'
done
```

```text
== --filter=[HEAD^]
["@shop/analytics"]
== --filter=...[HEAD^]
["@shop/analytics","@shop/web"]
== --filter=@shop/analytics
["@shop/analytics"]
== --filter=...@shop/format
["@shop/admin","@shop/api-client","@shop/format","@shop/ui","@shop/web"]
== --filter=...^@shop/format
["@shop/admin","@shop/api-client","@shop/ui","@shop/web"]
== --filter=@shop/web...
["@shop/analytics","@shop/api-client","@shop/format","@shop/tsconfig","@shop/ui","@shop/web"]
```

`[HEAD^]`는 git으로 "HEAD^ 이후 파일이 바뀐 패키지"를 고른다. 앞에 `...`를 붙이면 그 패키지에 의존하는 쪽까지, 뒤에 붙이면 그 패키지가 의존하는 쪽까지 넓힌다. `^`는 기준 패키지 자신을 뺀다. CI에서 쓰는 모양은 대개 "기준 커밋 이후 바뀐 패키지와 그것을 쓰는 쪽"이다. 아래 명령을 조각별로 눌러 보면 각 부분의 뜻이 나온다.

뽑힌 패키지만 돈다고 생각하기 쉬운데, 실제로 실행된 작업은 그보다 많다.

```bash
# analytics와 web이 뽑혔을 때 실제로 계획된 작업
npx turbo run build typecheck test --filter='...[HEAD^]' --dry=json \
  | jq -r '.tasks[] | select(.command != "<NONEXISTENT>") | .taskId' | sort
```

```text
@shop/analytics#build
@shop/analytics#test
@shop/analytics#typecheck
@shop/api-client#build
@shop/format#build
@shop/web#build
@shop/web#typecheck
```

web의 build가 `^build`를 요구하니 web이 쓰는 api-client와 format의 build도 따라왔다. 선택자는 "어느 패키지의 작업을 돌릴까"를 고르고, `dependsOn`은 "그 작업을 돌리려면 무엇이 먼저 있어야 하나"를 채운다. 대신 format의 test나 admin의 작업은 빠졌다. 그 위쪽 빌드까지 다시 하지 않으려면 캐시가 필요하다. 그 이야기는 조금 뒤에 한다.

## 기준 커밋을 잘못 고르면 테스트가 통과해 버린다

`[HEAD^]`는 예제로 쓰기 좋지만 PR에서는 위험하다. 바로 앞 커밋 하나와만 비교하기 때문이다. 기능 브랜치에 커밋 두 개를 쌓았다. 첫 커밋은 가격 포맷에 띄어쓰기를 넣었고(테스트가 깨지는 변경이다), 두 번째 커밋은 analytics에 주석만 달았다.

```bash
# PR 브랜치의 커밋과, 기준을 달리 했을 때 뽑히는 패키지
git log --oneline origin/main..HEAD
npx turbo run build --filter='...[HEAD^]' --dry=json | jq -c '.packages'
npx turbo run build --filter='...[origin/main...HEAD]' --dry=json | jq -c '.packages'
```

```text
15b7f78 analytics: comment
a212dfc format: space before unit
["@shop/analytics","@shop/web"]
["@shop/admin","@shop/analytics","@shop/api-client","@shop/format","@shop/ui","@shop/web"]
```

`[HEAD^]`로는 format이 아예 빠진다. 테스트를 그렇게 돌리면 이렇게 된다.

```bash
# 마지막 커밋만 보고 테스트한다
npx turbo run test --filter='...[HEAD^]'
```

```text
@shop/analytics:test: # pass 1
@shop/analytics:test: # fail 0
 Tasks:    5 successful, 5 total
```

종료 코드 0, 초록불이다. 깨진 format 테스트는 돌지도 않았다. 기준을 main과 갈라진 지점으로 잡으면 결과가 다르다.

```bash
# main과의 merge base부터 본다. 실패해도 끝까지 돌린다
TURBO_SCM_BASE=origin/main npx turbo run test --affected --continue
```

출력에서 통과한 줄과 스택 줄은 뺐다.

```text
@shop/format:test: not ok 1 - formatPrice
@shop/format:test:   code: 'ERR_ASSERTION'
@shop/format:test:   expected: '12,900원'
@shop/format:test:   actual: '12,900 원'
@shop/api-client:test: not ok 1 - cart line
@shop/api-client:test:   expected: '양말 x2 = 6,000원'
@shop/api-client:test:   actual: '양말 x2 = 6,000 원'
 Tasks:    6 successful, 8 total
Cached:    5 cached, 8 total
Failed:    @shop/api-client#test, @shop/format#test
```

`--affected`는 `--filter=...[기준...HEAD]`와 같은 일을 하는 단축 옵션이고, 기준은 `TURBO_SCM_BASE`로 준다. format 자신의 테스트와, format을 쓰는 api-client의 테스트가 함께 잡혔다. 바뀐 것만 돌리는 기능은 기준 커밋에 모든 것을 건다. 기준이 틀리면 빠르기만 하고 틀린 CI가 된다.

## 얕은 clone에서는 기준을 찾지 못한다

CI의 checkout은 보통 마지막 커밋 하나만 받는다(GitHub Actions의 `actions/checkout`은 `fetch-depth: 1`이 기본이다). 그 상태에서 같은 명령을 돌려 봤다.

```bash
# 커밋 하나만 받은 clone에서
git clone --depth 1 --branch feat/price file://$PWD/shop pr-shallow && cd pr-shallow
npx turbo run build --filter='...[HEAD^]'
```

```text
  x Unable to query SCM: Git error: fatal: ambiguous argument 'HEAD^': unknown
  | revision or path not in the working tree.
```

`HEAD^`가 없으니 바로 실패한다. 이건 차라리 낫다. `--affected`는 기준을 못 찾으면 멈추지 않고 전부 돌린다.

```text
 WARNING  unable to detect git range, assuming all files have changed: Unable to resolve base branch. Please set with `TURBO_SCM_BASE`.
   • Packages in scope: //, @shop/admin, @shop/analytics, @shop/api-client, @shop/format, @shop/tsconfig, @shop/ui, @shop/web
```

결과는 맞지만, 바뀐 것만 돌린다고 믿었던 CI가 매번 전부 돌고 있었다는 뜻이다. 경고 한 줄은 로그에 묻히기 쉽다. main 브랜치 하나만 커밋 하나 깊이로 더 받아도 부족하다.

```bash
# main을 커밋 하나만 받아 오면 두 히스토리가 만나는 지점이 없다
git fetch --depth=1 origin main:refs/remotes/origin/main
TURBO_SCM_BASE=origin/main npx turbo run build --affected --dry=text
```

```text
 WARNING  unable to detect git range, assuming all files have changed: Git error: fatal: no merge base found
```

갈라진 지점(merge base)까지 히스토리가 있어야 한다. 히스토리를 조금 더 받자 제대로 뽑혔다.

```bash
# 몇 커밋 더 받아 merge base를 찾을 수 있게 한다
git fetch --deepen=5 origin
TURBO_SCM_BASE=origin/main npx turbo run build --affected --dry=json | jq -c '.packages'
```

```text
["@shop/admin","@shop/api-client","@shop/format","@shop/ui","@shop/web"]
```

GitHub Actions라면 이런 모양이 된다. 아래는 설정 예시이고 이 글에서 Actions로 돌려 본 것은 아니다.

```yaml
# .github/workflows/ci.yml (예시)
- uses: actions/checkout@v4
  with:
    fetch-depth: 0              # merge base를 찾을 수 있게 히스토리를 받는다
- run: pnpm install --frozen-lockfile
- run: pnpm turbo run build typecheck test --affected --continue
  env:
    TURBO_SCM_BASE: ${{ github.event.pull_request.base.sha }}
```

저장소가 커서 전체 히스토리가 부담이면 `fetch-depth`를 적당히 주고 `git fetch --deepen`으로 merge base가 나올 때까지 늘리는 방법도 쓴다. 그리고 main에 머지된 뒤의 빌드는 고르지 말고 전부 돌리는 편이 안전하다. main 위에서 `--affected`를 기본값(main과 비교)으로 돌리면 실습에서는 루트(`//`)만 뽑히고 패키지는 하나도 뽑히지 않았다. 배포 직전에 아무것도 검사하지 않는 셈이다.

아래 그림은 PR 하나가 CI에서 처리되는 순서다. 고르는 단계와 캐시를 찾는 단계가 따로 있다.

## 캐시가 그래프를 만나면

고르기만으로는 "위쪽의 선행 빌드"를 매번 다시 한다. 여기에 작업 결과 캐시를 붙이면, 바뀌지 않은 패키지의 작업은 전부 적중으로 끝난다. CI 러너는 매번 빈 머신이라 로컬 캐시가 없으니, 실무에서는 원격 캐시를 붙인다. 이 실습에서는 원격 캐시 대신 러너들이 같은 캐시 폴더(`--cache-dir`)를 보게 해서 같은 효과를 냈다. 앞 커밋에서 한 번 전체를 돌려 캐시를 채운 뒤, analytics를 고친 커밋을 새로 clone해서 돌렸다.

```bash
# 앞 커밋에서 채운 캐시 폴더를 보고 전체를 돌린다
npx turbo run build typecheck test --cache-dir=$CACHE
```

```text
@shop/admin:build: cache hit
@shop/admin:typecheck: cache hit
@shop/analytics:build: cache miss
@shop/analytics:test: cache miss
@shop/analytics:typecheck: cache miss
@shop/api-client:build: cache hit
@shop/api-client:test: cache hit
@shop/api-client:typecheck: cache hit
@shop/format:build: cache hit
@shop/format:test: cache hit
@shop/format:typecheck: cache hit
@shop/ui:typecheck: cache hit
@shop/web:build: cache miss
@shop/web:typecheck: cache miss
 Tasks:    14 successful, 14 total
Cached:    9 cached, 14 total
```

필터를 주지 않았는데도 실제로 돈 것은 analytics와 web의 작업 다섯 개다. 의존하는 패키지의 해시가 내 해시의 입력으로 들어가기 때문에, 캐시만으로도 "바뀐 것과 그 위쪽"이 저절로 가려진다. 해시가 무엇으로 만들어지는지, 원격 캐시를 직접 띄우는 방법과 남이 올린 결과물을 믿어도 되는지는 [빌드 캐시로 CI 줄이기](/posts/build-caching)에서 실제로 해 봤다.

## 다섯 가지 방법으로 재 본 CI 시간

같은 상황(analytics만 바뀐 커밋)에서 다섯 가지 방법을 각각 다섯 번씩 돌렸다. 매번 저장소를 새로 clone하고 오프라인으로 설치한 뒤, 작업 명령이 도는 시간만 쟀다. 값은 다섯 번의 중앙값이다.

```bash
# 각 방법을 깨끗한 clone에서 돌린다 (설치 시간은 빼고 잰다)
pnpm -r build && pnpm -r typecheck && pnpm -r test                         # A
npx turbo run build typecheck test --cache-dir=.turbo-none                 # B
npx turbo run build typecheck test --filter='...[HEAD^]' --cache-dir=.turbo-none  # C
npx turbo run build typecheck test --cache-dir=$CACHE                      # D
npx turbo run build typecheck test --filter='...[HEAD^]' --cache-dir=$CACHE       # E
```

```text
A-pnpm: 5.69s 5.70s 6.52s 6.60s 7.05s
B-turbo: 5.33s 5.57s 5.60s 5.62s 5.73s
C-filter: 3.47s 3.48s 3.59s 3.77s 4.70s
D-cache: 2.62s 2.63s 2.68s 2.71s 2.84s
E-both: 2.53s 2.54s 2.63s 2.68s 3.07s
```

| 방법 | 실행한 작업 | 중앙값 |
|---|---|---|
| A. `pnpm -r` 세 번 | 14개 전부, 단계별로 | 6.52초 |
| B. turbo, 캐시 없음 | 14개 전부, 한 그래프로 | 5.60초 |
| C. turbo, 바뀐 것과 위쪽 | 7개 | 3.59초 |
| D. turbo, 공유 캐시 | 14개 중 5개 실행, 9개 적중 | 2.68초 |
| E. 고르기와 캐시 함께 | 7개 중 5개 실행, 2개 적중 | 2.63초 |

작은 저장소라 절댓값은 몇 초 차이지만 비율은 그대로 커진다. 그래프로만 돌려도 14%쯤 줄고, 고르기나 캐시를 붙이면 절반 아래로 내려간다. 남은 2.6초에는 다시 돌아야 하는 web의 Vite 빌드와 타입 검사, 그리고 npx와 turbo가 뜨는 시간이 들어 있다. D와 E가 거의 같은 것도 눈여겨볼 만하다. 캐시가 잘 맞으면 고르기가 더 줄일 것이 별로 없다. 둘은 성격이 다르다. 고르기는 git 기준이 틀리면 돌아야 할 작업을 빼먹지만, 캐시는 해시가 정확한 한 빠뜨리지 않는다. 그래서 캐시를 기본으로 두고, 고르기는 캐시로도 줄일 수 없는 작업(배포, 미리보기 환경 만들기, 오래 걸리는 E2E)에 쓰는 편이 안전하다.

## 해시를 흔드는 파일들

캐시가 자꾸 빗나가면 무엇이 해시를 바꾸는지 본다. 실습 저장소에서 파일을 하나씩 건드려 보며 적중 수를 셌다. 모든 작업이 적중한 상태(14개)에서 시작한다.

먼저 format 폴더에 `README.md` 하나를 추가했다.

```text
== README added to format
@shop/format:typecheck: cache miss
@shop/format:build: cache miss
@shop/ui:typecheck: cache miss
@shop/format:test: cache miss
@shop/api-client:build: cache miss
@shop/api-client:typecheck: cache miss
@shop/admin:build: cache miss
@shop/admin:typecheck: cache miss
@shop/web:typecheck: cache miss
@shop/api-client:test: cache miss
@shop/web:build: cache miss
```

문서 한 장에 작업 열한 개가 빗나갔다. 기본 입력은 그 패키지 폴더의 git이 무시하지 않는 모든 파일이라 README도 들어간다. format의 해시가 바뀌면 format을 쓰는 모든 작업의 해시가 따라 바뀐다. `dist`가 한 글자도 달라지지 않았는데도 그렇다. 작업이 실제로 읽는 파일만 입력으로 좁혔다.

```json
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "inputs": ["$TURBO_DEFAULT$", "!**/*.md", "!test/**"],
      "outputs": ["dist/**"]
    },
    "typecheck": { "dependsOn": ["^build"], "inputs": ["$TURBO_DEFAULT$", "!**/*.md", "!test/**"] },
    "test": { "dependsOn": ["build"], "inputs": ["$TURBO_DEFAULT$", "!**/*.md"] }
  }
}
```

`$TURBO_DEFAULT$`는 기본 입력 전체이고, `!`로 시작하는 줄이 거기서 뺄 것이다. build와 typecheck는 테스트 파일도 읽지 않으니 뺐다. 다시 README를 고치고, 이번에는 테스트 파일도 고쳐 봤다.

```text
== README edited
Cached:    14 cached
== test file edited
@shop/format:test: cache miss
Cached:    13 cached
```

README는 이제 아무것도 건드리지 않고, 테스트 파일은 format의 test 하나만 다시 돌린다. 입력을 좁힐 때는 반대 방향의 사고를 조심해야 한다. 빌드가 실제로 읽는 파일(예를 들어 `src` 밖의 `assets/`나 설정 파일)을 빼 버리면, 그 파일을 고쳐도 캐시가 옛 결과를 돌려준다. 뺄 것은 확실히 읽지 않는 것만 뺀다.

의존성을 바꾸면 어떨까. analytics에만 패키지 하나를 추가했다.

```bash
# analytics에만 의존성을 추가한다. pnpm-lock.yaml도 바뀐다
pnpm --filter @shop/analytics add ms@2.1.3
npx turbo run build typecheck test
```

```text
@shop/analytics:build: cache miss
@shop/analytics:typecheck: cache miss
@shop/analytics:test: cache miss
@shop/web:build: cache miss
@shop/web:typecheck: cache miss
Cached:    9 cached
```

lockfile은 저장소에 하나지만, Turborepo는 lockfile에서 각 패키지가 실제로 쓰는 부분만 떼어 해시에 넣는다. 그래서 analytics와 그 위쪽만 빗나갔다. 루트 `package.json`의 스크립트 한 줄을 고쳤을 때는 14개가 그대로 적중했다.

반대로 모두가 쓰는 패키지를 고치면 전부 빗나간다. 공용 `tsconfig/base.json`에 옵션 하나를 넣었다.

```text
@shop/admin:build: cache miss
@shop/admin:typecheck: cache miss
@shop/analytics:build: cache miss
@shop/analytics:test: cache miss
@shop/analytics:typecheck: cache miss
@shop/api-client:build: cache miss
@shop/api-client:test: cache miss
@shop/api-client:typecheck: cache miss
@shop/format:build: cache miss
@shop/format:test: cache miss
@shop/format:typecheck: cache miss
@shop/ui:typecheck: cache miss
@shop/web:build: cache miss
@shop/web:typecheck: cache miss
Cached:    0 cached
```

이건 버그가 아니라 정확한 동작이다. 컴파일 옵션이 바뀌면 모든 결과가 달라질 수 있다. 다만 이런 공용 설정을 자주 고치는 저장소는 캐시를 붙여도 효과가 적다. 설정 패키지는 가능한 한 안정적으로 두고, 자주 바뀌는 값은 쓰는 패키지 쪽으로 내린다. 저장소 루트에 있어서 어느 패키지의 입력도 아닌데 빌드가 읽는 파일(루트 `.env`, 공용 스크립트)은 반대로 해시에서 빠지니 `globalDependencies`에 적는다. 해시에서 빠진 입력이 만드는 틀린 적중은 [빌드 캐시 글](/posts/build-caching)의 환경 변수 실험이 보여 준다.

아래 코드에서 `...[범위]`가 하는 일을 직접 구현해 볼 수 있다. 패키지별 의존 목록과 바뀐 패키지들을 받아, 바뀐 것과 그것에 의존하는 모든 패키지를 이름순으로 돌려주면 된다. 첫 두 테스트의 기대값은 실습 저장소에서 turbo가 실제로 골라 준 목록과 같다.

## 앱 하나만 이미지로 만들 때

배포 이미지를 만들 때도 같은 그래프를 쓴다. 관리자 앱 이미지에 쇼핑몰 코드와 그 의존성까지 넣을 이유가 없다. `turbo prune`은 앱 하나에 필요한 패키지만 골라 작은 저장소를 만든다.

```bash
# admin과 admin이 쓰는 패키지만 out/에 뽑는다
npx turbo prune @shop/admin --docker
find out -maxdepth 3 -not -path "*/node_modules*" | sort
```

## Nx는 같은 일을 어떻게 하나

Nx도 원리는 같다. 프로젝트 그래프를 만들고, 바뀐 프로젝트와 그 위쪽에서만 작업을 돌리고, 작업 결과를 해시로 캐시한다. 명령 모양만 다르다. 아래는 예시이고 이 글에서 Nx로 돌려 본 것은 아니다.

```bash
# 예시: Nx에서 main 이후 영향받은 프로젝트만 빌드·테스트한다
npx nx affected -t build test --base=origin/main --head=HEAD
# 예시: 프로젝트 그래프를 브라우저에서 본다
npx nx graph
```

차이는 대체로 범위에 있다. Turborepo는 `package.json` 스크립트를 돌리는 작업 실행기에 가깝게 가볍게 시작하고, Nx는 코드 생성기, 모듈 경계 린트 규칙, 플러그인으로 프레임워크별 작업을 추론하는 기능까지 갖춘 쪽이다. 저장소가 이미 pnpm 워크스페이스로 잘 나뉘어 있고 빌드 시간만 줄이고 싶다면 Turborepo가 들이기 쉽고, 경계 규칙과 생성기까지 한 도구로 묶고 싶다면 Nx가 맞는다. 두 도구 모두 기능이 자주 바뀌니 세부는 쓰는 버전의 문서를 확인한다.

## 모노레포가 오히려 짐이 될 때

여기까지 장치를 다 붙여도 모노레포가 손해인 경우가 있다.

거의 모든 변경이 그래프의 바닥을 건드리는 저장소다. 실습에서 공용 tsconfig 한 줄에 적중이 0개가 됐다. 모두가 쓰는 공용 패키지가 매일 바뀌면 고르기도 캐시도 소용이 없다. 이럴 때는 도구보다 패키지 경계를 다시 그어야 한다.

서로 아무 관계도 없는 앱들을 한 저장소에 모은 경우다. 공유하는 코드가 없으면 얻는 것은 없고, 같은 CI 설정과 같은 도구 버전에 묶이는 비용만 남는다. TypeScript 메이저를 올리려면 모든 앱이 동시에 따라와야 한다.

저장소 자체가 무거워진 경우다. clone과 checkout이 몇 분씩 걸리고, IDE가 전체를 색인하느라 느려진다. 부분 clone과 sparse-checkout으로 줄일 수 있지만 그것도 운영할 일이다. 경로로 경계를 나누는 방법은 [브랜치 전략](/posts/git-branching-strategy)의 모노레포 부분에 짧게 적었다.

접근 권한을 나눠야 하는 경우다. 저장소 단위 권한이 기본이라, 특정 팀만 볼 수 있어야 하는 코드는 모노레포에 넣기 어렵다.

팀마다 배포 시점이 완전히 달라야 하는 경우는 저장소보다 런타임에서 나누는 문제다. 그때는 [마이크로 프런트엔드](/posts/micro-frontends)를 본다.

## 지도를 정확히 그리면 덜 돈다

모노레포 CI를 빠르게 만드는 일은 결국 저장소의 지도를 정확히 그리는 일이다. 패키지 의존성과 `dependsOn`이 작업 그래프를 만들고, 그래프가 있으면 기다릴 필요 없는 작업이 함께 돌고, 바뀐 것과 그 위쪽만 고를 수 있고, 바뀌지 않은 작업은 캐시에서 꺼낸다. 고르기는 git 기준이 맞아야 하고(merge base, 충분한 히스토리), 캐시는 입력이 맞아야 한다(빠진 입력도 넘치는 입력도 없게). 둘 중 캐시가 빠뜨리지 않는 쪽이라 기본이 되고, 고르기는 그 위에 얹는다.

## 면접에서 나올 만한 질문

### 모노레포 CI가 느릴 때 무엇부터 하나요?

먼저 패키지 의존성과 작업 사이의 선후를 선언해 작업 그래프를 만든다. 그래야 기다릴 필요 없는 작업을 동시에 돌리고, 바뀐 패키지와 그것에 의존하는 패키지만 고르고, 바뀌지 않은 작업은 캐시에서 꺼낼 수 있다. 실습에서 단계별 `pnpm -r` 6.5초가 그래프만으로 5.6초, 공유 캐시를 붙이자 2.7초가 됐다.

### dependsOn의 ^build와 build는 무엇이 다른가요?

`^build`는 내가 의존하는 패키지들의 build가 먼저 끝나야 한다는 뜻이고, `build`는 같은 패키지의 build가 먼저라는 뜻이다. 앱의 build는 공용 패키지의 dist가 필요하니 `^build`를 쓰고, 테스트가 내 dist를 불러 쓰면 test에 `build`를 쓴다.

### --filter=...[HEAD^]를 PR CI에 쓰면 어떤 문제가 있나요?

바로 앞 커밋 하나와만 비교해서, PR에 커밋이 여럿이면 앞 커밋의 변경을 놓친다. 실습에서 첫 커밋이 깨뜨린 format 테스트가 아예 돌지 않고 CI가 초록불이 됐다. 기준은 main과의 merge base(`origin/main...HEAD` 또는 `TURBO_SCM_BASE`와 `--affected`)로 잡는다.

### CI의 얕은 clone에서 affected 빌드가 이상하게 동작하는 이유는요?

기준 커밋이나 merge base가 히스토리에 없어서다. `[HEAD^]` 필터는 바로 에러가 나고, `--affected`는 경고만 남기고 모든 패키지를 돌린다. 결과는 맞지만 빠르지 않고, 경고는 로그에 묻힌다. `fetch-depth: 0`이나 deepen으로 merge base까지 받는다.

### 바뀐 것만 고르기와 작업 캐시 중 무엇을 기본으로 두나요?

캐시를 기본으로 둔다. 캐시는 입력 해시가 정확한 한 돌아야 할 작업을 빠뜨리지 않고, 의존 패키지의 해시가 내 해시에 들어가서 바뀐 것과 그 위쪽이 저절로 가려진다. 고르기는 git 기준이 틀리면 빠뜨리므로, 캐시로 줄일 수 없는 배포나 E2E처럼 비싼 작업을 거르는 데 얹어 쓴다.

### README 하나 고쳤는데 캐시가 다 빗나갑니다. 왜 그렇고 어떻게 고치나요?

기본 입력이 패키지 폴더의 모든 파일이라 README도 해시에 들어가고, 그 패키지에 의존하는 작업의 해시까지 연쇄로 바뀐다. 실습에서 문서 한 장에 열한 개가 빗나갔다. `inputs`에 `$TURBO_DEFAULT$`와 `!**/*.md`처럼 작업이 읽지 않는 파일을 빼면 된다. 단, 실제로 읽는 파일을 빼면 틀린 적중이 나니 확실한 것만 뺀다.

### 하나의 lockfile을 쓰는데 의존성 하나 추가하면 전부 다시 빌드되나요?

Turborepo는 lockfile에서 각 패키지가 쓰는 부분만 떼어 해시에 넣어서 그렇지 않다. 실습에서 analytics에 의존성을 추가하자 analytics와 그것을 쓰는 web의 작업 다섯 개만 빗나갔다. 반면 모두가 쓰는 공용 설정 패키지를 고치면 그래프 전체가 빗나간다.

### 모노레포가 맞지 않는 경우는 언제인가요?

공유하는 코드가 거의 없는 앱들을 모은 경우, 거의 모든 변경이 모두가 쓰는 바닥 패키지를 건드리는 경우, 저장소가 너무 커서 clone과 색인이 부담인 경우, 코드 접근 권한을 팀별로 나눠야 하는 경우다. 팀마다 배포 시점까지 독립해야 한다면 저장소가 아니라 런타임에서 나누는 마이크로 프런트엔드를 검토한다.
