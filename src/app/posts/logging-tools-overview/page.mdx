"주문 API가 504가 나요. 로그 좀 봐 주세요." 이 말을 들으면 먼저 정해야 할 게 있다. 어느 로그인가. 요청 하나는 사용자 브라우저에서 출발해 프록시를 지나 앱 프로세스에 닿는다. 그 앱은 서버 한 대 위의 서비스일 수도, 쿠버네티스 파드일 수도, 클라우드 함수일 수도 있다. 지나는 자리마다 로그가 따로 있고, 보는 도구도 다르다. 엉뚱한 곳을 열면 "로그에는 아무것도 없다"가 결론이 된다.

실제로 이 글의 실습에서 504가 난 요청의 앱 로그는 이랬다.

```text
{"time":"2026-10-21T23:59:39.478Z","req_id":"669b8288e2f31d9bb0b1b6d61a721890","path":"/slow/report","status":200,"msg":"request finished","duration_ms":2000}
```

앱은 200을 줬다고 적었다. 사용자는 504를 받았다. 둘 다 사실이다. 이 글은 증상마다 어디를 먼저 열어야 하는지, 각 도구가 답할 수 있는 질문과 답하지 못하는 질문을 실제 출력과 함께 정리한다.

이 주제의 다른 글: 브라우저 에러를 모으고 소스맵으로 되돌리는 법은 [프런트엔드 에러 추적](/posts/frontend-error-tracking), 여러 서비스 로그로 버그 하나를 끝까지 쫓는 기술은 [로그로 버그 추적하기](/posts/debugging-with-logs), 여러 서버의 로그를 한곳에 모으는 구조는 [중앙 로그 파이프라인](/posts/centralized-logging-pipeline)에 있다. 이 글은 도구 고르기만 다룬다.

실습 환경은 Ubuntu 24.04, Node.js 22, nginx 1.24, Chromium 141(Playwright 1.55), GNU coreutils 9.4다. 쿠버네티스와 클라우드 콘솔은 이 환경에 없어서 그 부분의 출력은 예시로 표시했다.

로그를 찾을 때 먼저 할 일은 "이 증상을 마지막으로 본 자리"를 정하는 것이다. 사용자가 504를 받았다면 그 504를 만든 자리가 있다. 앱이 만들었다면 앱 로그에, 프록시가 만들었다면 프록시 로그에 있다. 아래에서 자리별로 본다.

## 브라우저 개발자 도구: 사용자가 실제로 받은 것

사용자 화면에서만 나는 문제는 서버 로그 어디에도 없다. 개발자 도구에서 볼 곳은 정해져 있다.

Console 탭의 레벨 필터(Errors, Warnings)와 텍스트 필터. 그리고 Preserve log다. 이 옵션이 꺼져 있으면 페이지를 이동할 때마다 콘솔이 지워진다. 로그인 폼을 제출하고 리다이렉트되는 흐름에서 첫 페이지의 에러를 보려면 켜 둬야 한다. Network 탭에도 같은 이름의 옵션이 있다.

Network 탭에서는 상태 코드와 시간, 요청·응답 헤더, 그리고 Initiator(누가 이 요청을 보냈나)를 본다. 요청을 우클릭해 Copy as cURL로 복사하면 같은 요청을 터미널에서 다시 보낼 수 있다. 서버 쪽 사람에게 넘길 때 이게 가장 정확하다. 그다음 할 일은 [curl로 디버깅하기](/posts/curl-for-debugging)에 있다.

콘솔에 찍히는 빨간 줄이 모두 JS 코드에서 나온 건 아니다. Chromium에서 CSP 위반과 404가 있는 페이지를 열고, 페이지의 `console` 호출과 브라우저 자체가 남긴 기록(CDP의 `Log` 도메인)을 함께 받아 봤다.

`Log.network`, `Log.security`가 짝으로 붙은 줄은 브라우저가 직접 낸 메시지다. 페이지 코드가 `console.error`를 감싸 수집기로 보내도 이 줄들은 잡히지 않는다. 404나 CSP 위반을 모으려면 리소스 에러 이벤트나 `securitypolicyviolation` 이벤트를 따로 들어야 한다. 이 차이는 프런트엔드 에러 추적 글에서 다뤘다.

### HAR을 받을 때 같이 오는 것

재현이 안 되는 문제는 사용자에게 HAR(네트워크 기록 파일)을 받기도 한다. 위 세션을 Playwright로 HAR로 저장하고 안을 봤다.

```bash
# HAR에 든 요청 목록
jq -c '.log.entries[] | {m: .request.method, url: .request.url, s: .response.status}' session.har
# 민감한 값이 몇 번 들어 있나
grep -o 's3cr3t-session\|eyJhbGciOi.fake\|abc123' session.har | sort | uniq -c
```

```text
{"m":"GET","url":"http://127.0.0.1:18821/","s":200}
{"m":"GET","url":"http://127.0.0.1:18821/app.js","s":200}
{"m":"GET","url":"http://127.0.0.1:18821/missing.png","s":404}
{"m":"POST","url":"http://127.0.0.1:18821/login","s":303}
{"m":"GET","url":"http://127.0.0.1:18821/home","s":200}
{"m":"GET","url":"http://127.0.0.1:18821/api/me?token=abc123","s":401}
      3 abc123
      2 eyJhbGciOi.fake
      6 s3cr3t-session
```

세션 쿠키가 여섯 번, Bearer 토큰이 두 번, URL의 토큰이 세 번 들어 있다. 세션 쿠키는 `HttpOnly`라서 페이지의 JS는 못 읽지만 HAR에는 그대로 실린다. 이 파일을 받은 사람은 그 사용자로 로그인할 수 있다. 최근 크롬 계열 개발자 도구는 내보낼 때 쿠키와 Authorization 헤더를 빼는 쪽을 기본으로 두고 민감한 값을 포함한 내보내기를 따로 고르게 하지만(버전에 따라 다르다), URL에 실린 토큰까지 지워 주지는 않는다. HAR은 받자마자 가리고, 쓴 뒤에는 지운다.

HAR 항목 하나에서 민감한 값을 가리는 함수를 짜 보자. 쿠키·Set-Cookie·Authorization 헤더와 `token` 같은 쿼리 파라미터의 값을 `[redacted]`로 바꾼다. 헤더 이름은 대소문자를 가리지 않는다. 첫 테스트는 위 HAR의 실제 항목을 줄인 것이다.

## 프록시 로그: 앱이 아니라 앞단이 만든 에러

처음 장면의 504로 돌아간다. 실습은 nginx를 앞에 두고 뒤의 Node 앱을 부르게 했다. `proxy_read_timeout`은 1초다. access 로그는 JSON으로 남기고, 요청마다 만든 `$request_id`를 앱에 `X-Request-Id` 헤더로 넘겼다.

```nginx
log_format json escape=json '{"time":"$time_iso8601","req_id":"$request_id","method":"$request_method","uri":"$request_uri",'
  '"status":$status,"upstream":"$upstream_addr","upstream_status":"$upstream_status","rt":$request_time,"urt":"$upstream_response_time"}';
access_log logs/access.log json;

location / {
  proxy_pass http://127.0.0.1:18823;
  proxy_set_header X-Request-Id $request_id;   # 앱 로그와 잇는 열쇠
  proxy_read_timeout 1s;
}
```

앱을 끈 채로 한 번, 켜고 나서 빠른 요청과 2초 걸리는 요청을 한 번씩 보냈다.

```bash
curl -s -o /dev/null -w "%{http_code}\n" localhost:18822/api/orders    # 앱이 꺼져 있을 때
curl -s -o /dev/null -w "%{http_code}\n" localhost:18822/api/orders    # 앱을 켠 뒤
curl -s -o /dev/null -w "%{http_code}\n" localhost:18822/slow/report   # 2초 걸리는 요청
```

```text
502
200
504
```

## 프로세스 하나: 표준 출력과 표준 에러

앱 로그가 "비어 있다"는 문의의 상당수는 앱이 어디에 쓰는지를 잘못 알고 있는 경우다. 정보는 표준 출력(stdout)에, 에러는 표준 에러(stderr)에 쓰는 앱을 `>`로만 받아 봤다.

```bash
node app.js > out.log                  # stdout만 파일로
wc -l out.log; grep -c '"level":"error"' out.log
node app.js > all.log 2>&1             # stderr도 같은 파일로
grep -c '"level":"error"' all.log
```

```text
2 out.log
0
1
```

`>`만 쓰면 에러는 파일이 아니라 터미널로 가고, 백그라운드로 돌렸다면 어디에도 안 남는다. Node.js의 `console.error`, 대부분 언어의 기본 예외 출력은 stderr로 간다. systemd 서비스는 기본으로 둘 다 journald로 보내고, 컨테이너 런타임도 둘 다 받아 각 줄에 stdout/stderr 표시를 붙인다. 문제가 되는 건 손으로 띄운 프로세스와 오래된 init 스크립트다.

### 파일을 따라 읽을 때

로그 파일을 실시간으로 볼 때 `tail -f`를 쓰는데, 로그가 돌아가는(rotate) 순간 조용히 멈춘다. 파일 이름을 바꾸고 새 파일을 만드는 방식의 회전을 그대로 재현했다.

```bash
echo "line1 before rotate" > access.log
tail -n +1 -f access.log > seen_f.txt &      # -f: 처음 연 파일(inode)을 따라간다
tail -n +1 -F access.log > seen_F.txt &      # -F: 이름을 따라가고, 바뀌면 다시 연다
echo "line2 before rotate" >> access.log
mv access.log access.log.1; echo "line3 after rotate (new file)" > access.log
echo "line4 after rotate" >> access.log
```

```text
== tail -f
line1 before rotate
line2 before rotate
== tail -F
line1 before rotate
line2 before rotate
tail: 'access.log' has become inaccessible: No such file or directory
tail: 'access.log' has appeared;  following new file
line3 after rotate (new file)
line4 after rotate
```

## 서버 한 대: journalctl

systemd로 띄운 서비스의 로그는 journald가 모아 바이너리 저널로 저장하고, `journalctl`로 읽는다. 실습 VM의 저널은 부팅 직후 기록만 있지만 명령의 모양은 그대로다.

```bash
journalctl -u systemd-udevd -o short-iso -n 2 --no-pager   # 한 서비스의 마지막 2줄, ISO 시각
journalctl -p warning -n 2 --no-pager                       # warning 이상만
journalctl --disk-usage                                     # 저널이 차지한 공간
journalctl --list-boots --no-pager                          # 저장된 부팅 목록
```

기본 출력의 `Oct 20 14:26:46`에는 연도와 시간대가 없다. 다른 로그와 맞춰 볼 때는 `-o short-iso`로 바꾼다. 줄마다 붙는 필드를 보려면 `-o json`이다. 앱이 평문으로 써도 journald가 PID, 실행 파일, 유닛, 우선순위를 붙여 두니 이 필드로 거르고 셀 수 있다.

```bash
# 저널의 줄 수를 유닛별로 센다
journalctl -o json --no-pager | jq -r '._SYSTEMD_UNIT // ._TRANSPORT' | sort | uniq -c | sort -rn | head -4
```

```text
    831 kernel
      9 systemd-udevd.service
      6 systemd-journald.service
      4 journal
```

이 VM에서 하나 배운 게 있다. 커널 메시지가 831줄인데 `journalctl -k`는 `-- No entries --`를 냈다. `-k`는 현재 부팅의 커널 메시지만 보여 주는데, 저장된 저널은 그 전 부팅 것이었다. 서버가 재부팅된 뒤 "로그가 없다"면 `--list-boots`로 부팅 목록을 보고 `-b -1`(직전 부팅)로 연다. 이것도 저널이 디스크(`/var/log/journal`)에 남게 설정돼 있을 때 얘기고, 메모리(`/run/log/journal`)에만 두는 설정이면 재부팅과 함께 사라진다.

메모리 부족으로 커널이 프로세스를 죽였다면 앱 로그에는 마지막 말이 없고, 커널 쪽에 `Out of memory: Killed process …`가 남는다. 앱 로그가 갑자기 끊겼다면 `journalctl -k`(또는 `dmesg`)도 함께 본다. `systemctl`과 유닛 설정, 저널 보관 크기 설정(`SystemMaxUse`)은 [systemd와 systemctl](/posts/linux-systemd-systemctl)에서 다뤘다.

## 여러 서버를 한 번에: 로그 저장소의 화면

서버나 파드가 여러 개가 되면 하나씩 들어가 보는 방식은 끝난다. 로그를 한곳에 모아 검색 화면에서 묻는다. 어떤 저장소든 화면에서 하는 일은 같다. 시간 범위를 먼저 고르고, 서비스나 레이블로 좁히고, 필드로 거르고, 필요하면 시간 단위로 센다.

Grafana의 Explore에서 Loki를 고르면 LogQL로 묻는다. 같은 화면을 둘로 나눠 한쪽에 지표, 다른 쪽에 로그를 띄우고 시간 범위를 맞춰 볼 수 있어서, "그래프가 튄 그 1분 동안의 로그"를 보기 좋다. trace ID를 클릭해 trace 화면으로 넘어가는 연결도 여기서 설정한다. 대시보드 쪽은 [Grafana 대시보드](/posts/grafana-dashboards)에, LogQL을 실제로 돌린 결과는 [구조화 로그](/posts/structured-logging)에 있다.

OpenSearch Dashboards(또는 Kibana)의 Discover는 색인된 필드를 왼쪽에 늘어놓고, 필드 값을 눌러 바로 거르거나 빼게 해 준다. 본문 단어 검색이 빠른 것이 장점이다. 쿼리 DSL로 같은 질문을 던진 결과는 [중앙 로그 파이프라인](/posts/centralized-logging-pipeline)에 있다.

둘 다 "모은 로그만" 보여 준다. 수집기가 밀렸거나 파싱에 실패해 버려진 줄은 화면에 없다. 최근 몇 분만 비어 있다면 앱보다 수집 지연을 먼저 의심한다.

## 클라우드 콘솔: CloudWatch Logs Insights

AWS에서 Lambda나 ECS의 로그는 CloudWatch Logs의 로그 그룹에 쌓이고, Logs Insights로 묻는다. 이 환경에는 AWS 계정이 없어서 아래는 예시다.

```text
# 예시: 최근 1시간 orders 함수의 오류를 5분 단위로 센다
fields @timestamp, @message
| filter @message like /"level":"error"/
| stats count(*) as errors by bin(5m)
| sort @timestamp desc
```

```text
# 예시: 같은 쿼리를 CLI로. start-query가 돌려준 queryId로 결과를 받는다
aws logs start-query --log-group-name /aws/lambda/orders \
  --start-time $(date -d '-1 hour' +%s) --end-time $(date +%s) \
  --query-string 'fields @timestamp, @message | filter @message like /timeout/ | limit 20'
aws logs get-query-results --query-id <queryId>
```

Logs Insights는 쿼리가 훑은 데이터 양으로 값을 매긴다(정확한 단가는 리전마다 다르다). 시간 범위를 넓게 잡고 여러 로그 그룹을 한꺼번에 고르면 한 번 묻는 데에도 비용이 든다. 앱이 JSON으로 쓰면 필드가 자동으로 추출돼 `filter level = "error"`처럼 바로 쓸 수 있다. 다른 클라우드도 비슷한 화면이 있다. GCP는 Logs Explorer, Azure는 Log Analytics(KQL)다. 문법은 달라도 "범위 먼저, 필드로 거르기, 시간으로 세기" 순서는 같다.

## 에러 추적과 APM 도구가 답하는 질문

에러 추적 도구는 "어떤 에러가, 몇 명에게, 어느 릴리스부터" 나는지 답한다. 같은 에러를 묶고, 스택을 소스맵으로 되돌리고, 새 에러가 생기면 알린다. 로그 저장소가 "그때 무슨 일이 있었나"를 줄 단위로 답한다면, 에러 추적 도구는 에러를 이슈 단위로 관리한다. APM 도구는 요청 단위로 느린 구간과 외부 호출을 보여 주고, 대개 trace와 로그를 함께 엮는다.

SaaS로 쓰는 것과 직접 설치하는 것이 있고, 같은 제품이 둘 다 내놓기도 한다. 어느 쪽이든 고르기 전에 볼 것은 비슷하다. 수집량으로 값을 매기는지, 데이터가 어디 저장되는지, OpenTelemetry로 보낼 수 있어 나중에 바꾸기 쉬운지. 도구 이름보다 "이 질문을 어디서 답할지"를 먼저 정한다.

## 증상별로 먼저 여는 곳

지금까지를 증상별로 묶으면 이렇다.

| 증상 | 먼저 여는 곳 | 확인할 것 |
|---|---|---|
| 특정 사용자 화면에서만 안 된다 | 개발자 도구 Console·Network, 에러 추적 도구 | Preserve log 켜고 재현, 실패한 요청의 상태와 응답 |
| 502인데 앱 로그에 없다 | 프록시·로드 밸런서 error 로그 | connection refused, DNS, TLS, 헬스 체크 |
| 504인데 앱 로그는 200 | 프록시 access 로그 | 응답 시간이 앞단 타임아웃과 같은지 |
| 앱 로그가 갑자기 끊겼다 | `journalctl -k`, `kubectl describe pod` | OOM kill, 재시작 횟수, 직전 컨테이너 로그 |
| 서버 재부팅 뒤 로그가 없다 | `journalctl --list-boots` | `-b -1`, 저널이 디스크에 남는 설정인지 |
| 실시간으로 보는데 줄이 안 올라온다 | `tail -F`로 다시 | 로그 회전, 다른 파일에 쓰는지 |
| 여러 서버 중 어디서 났는지 모른다 | 로그 저장소 화면(Grafana, Dashboards) | 시간 범위, 요청 ID 검색 |
| 최근 몇 분 로그만 없다 | 수집기 지표와 로그 | 수집 지연, 파싱 실패 |

표의 어느 칸으로 가든 마지막에 쓰는 열쇠는 요청 ID다. 프록시가 만든 `$request_id`나 trace ID를 모든 자리에 같은 이름으로 남겨 두면, 도구가 바뀌어도 같은 값으로 다음 자리를 찾는다.

## 504 앞에서 다시

처음 장면의 "504가 나요"는 이제 순서가 있다. 504를 누가 만들었는지부터 본다. 앞단 access 로그에서 그 요청의 응답 시간이 타임아웃과 같다면 앞단이 포기한 것이고, 같은 요청 ID를 앱 로그에서 찾으면 앱이 실제로 얼마나 걸렸는지 나온다. 로그 도구는 많지만 각자 자기 자리에서 본 것만 안다. 증상을 마지막으로 본 자리를 먼저 열고, 요청 ID로 옆자리로 건너간다.

## 면접에서 나올 만한 질문

### 사용자가 504를 받았는데 앱 로그에는 200이 남아 있습니다. 어떻게 된 건가요?

504는 앱이 아니라 앞단 프록시나 로드 밸런서가 만든 응답이다. 앞단의 읽기 타임아웃이 앱의 처리 시간보다 짧아서, 앞단이 기다리다 포기하고 504를 줬고 앱은 그걸 모른 채 끝까지 처리했다. 실습에서는 nginx access 로그의 응답 시간이 타임아웃과 같은 1.000초였고 error 로그에 upstream timed out이 남았다. 같은 요청 ID로 두 로그를 맞춰 보면 확인된다.

### 502가 나는데 앱 로그에 그 요청이 아예 없습니다. 어디를 보나요?

요청이 앱까지 가지 못한 것이니 앞단의 error 로그를 본다. nginx라면 connect() failed (111: Connection refused) 같은 줄이 있고, 앱이 꺼져 있거나 포트가 다르거나 헬스 체크에서 빠진 경우다. DNS 실패나 TLS 오류도 여기 남는다. 앱 로그를 아무리 뒤져도 답이 없는 경우다.

### 개발자 도구의 Preserve log는 언제 켜나요?

페이지 이동이 끼어 있는 흐름을 볼 때 켠다. 꺼져 있으면 이동할 때마다 Console과 Network 기록이 지워져서, 로그인 폼 제출 뒤 리다이렉트처럼 첫 페이지에서 난 에러를 놓친다. 콘솔에는 JS 코드가 찍은 줄 말고도 브라우저가 직접 낸 404나 CSP 위반 메시지가 함께 보인다는 것도 알아 둔다.

### 사용자에게 HAR 파일을 받을 때 주의할 점은요?

HAR에는 쿠키, Authorization 헤더, URL의 토큰이 그대로 들어 있어서 받은 사람이 그 사용자로 로그인할 수 있다. HttpOnly 쿠키도 JS는 못 읽지만 HAR에는 실린다. 최근 크롬 계열은 헤더를 빼고 내보내는 쪽이 기본이지만 URL의 토큰은 남는다. 받자마자 가리고, 쓴 뒤 지우고, 세션은 만료시킨다.

### journalctl에서 자주 쓰는 옵션은 무엇이고, 재부팅 뒤 로그가 안 보이면 어떻게 하나요?

-u로 유닛을, -p로 우선순위를, --since로 시간을 좁히고, -o short-iso나 -o json으로 다른 로그와 맞추기 쉬운 형식으로 바꾼다. -k와 -b는 현재 부팅만 보기 때문에 재부팅 뒤에는 --list-boots로 목록을 보고 -b -1로 직전 부팅을 연다. 저널이 /var/log/journal에 저장되게 설정돼 있어야 재부팅 뒤에도 남는다.

### kubectl logs로 볼 수 없는 정보는 무엇인가요?

앱이 stdout·stderr에 쓰지 않은 것은 볼 수 없다. OOMKilled, 이미지 풀 실패, 프로브 실패는 파드 상태와 이벤트에 있으니 kubectl describe와 get events를 본다. 재시작했다면 --previous로 직전 컨테이너 로그는 보지만 그 전 것은 없고, 파드가 지워지면 로그도 노드에서 정리된다. 지난 장애를 보려면 중앙 로그 저장소가 필요하다.

### tail -f로 로그를 보는데 어느 순간부터 새 줄이 안 나옵니다. 왜 그럴까요?

로그 회전으로 파일 이름이 바뀌고 새 파일이 생겼는데, tail -f는 처음 연 파일을 계속 붙잡고 있어서다. 새 줄은 새 파일에 쓰이니 아무것도 안 나온다. tail -F는 이름을 따라가다 가리키는 파일이 바뀌면 다시 연다. 실습에서도 -F만 회전 뒤의 줄을 받았다.
