  그래서 어떤 도구를 쓰느냐에 따라 맞는 방식을 골라야 한다. 섞어 쓰면 스티커가 엉뚱하게 붙거나 아예 붙지 않는다.

NestJS 프로젝트에 처음 들어가면 이런 코드를 본다.

```ts
@Injectable()
export class UserService {
  constructor(private readonly repo: UserRepository) {}
}
```

`new UserService(...)`를 부르는 곳이 어디에도 없는데, 컨트롤러에서 `this.userService.get(1)`을 부르면 잘 돈다. `UserRepository`도 누가 만들어서 넣어 줬다. 그러다 테스트 러너를 Vitest로 바꾼 날, 모든 테스트가 `Cannot read properties of undefined`로 터진다. 코드는 한 줄도 안 바꿨다.

두 장면 모두 `@` 뒤에 무엇이 숨어 있는지 알면 풀린다. 이 글은 데코레이터가 결국 함수라는 데서 출발해, 클래스·메서드·필드·접근자 데코레이터가 어떤 순서로 실행되는지, TypeScript 5.0에 들어온 TC39 표준 데코레이터와 예전 `experimentalDecorators`가 무엇이 다른지, `emitDecoratorMetadata`와 `reflect-metadata`로 DI(의존성 주입)가 어떻게 돌아가는지를 본다. 실습은 TypeScript 5.9.3과 Node 22로 했다. Node 22는 데코레이터 문법을 직접 실행하지 못해서(`@d class A`에서 SyntaxError) 모두 `tsc`로 내린 결과를 돌렸다.

`@` 문법과 GoF 데코레이터 패턴의 관계는 [데코레이터 패턴 글](/posts/pattern-decorator)에서, 클래스 자체의 문법은 [TypeScript 클래스 글](/posts/ts-classes-access-modifiers)에서 다뤘다. Nest가 다른 Node 프레임워크와 어떻게 다른지는 [Node.js 웹 프레임워크 글](/posts/nodejs-web-frameworks)에 있다.

## 데코레이터는 정의할 때 한 번 부르는 함수다

데코레이터는 특별한 문법 요소가 아니라 함수다. `@trimmed`라고 쓰면 클래스를 정의하는 순간 `trimmed`라는 함수가 불린다. 인스턴스를 만들 때마다 불리는 게 아니다. 표준 데코레이터는 두 인자를 받는다. 첫째는 꾸밀 대상(메서드라면 그 함수), 둘째는 대상에 대한 정보를 담은 `context` 객체다. 무언가를 돌려주면 원래 것과 바꿔 끼우고, 아무것도 안 돌려주면 그대로 둔다.

```ts
// 메서드를 감싸 실행 시간을 찍는 데코레이터 (표준 방식)
function timed<This, Args extends unknown[], R>(
  target: (this: This, ...args: Args) => R,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => R>,
) {
  return function (this: This, ...args: Args): R {
    const start = performance.now();
    try {
      return target.call(this, ...args);
    } finally {
      console.log(`${String(context.name)}: ${(performance.now() - start).toFixed(0)}ms`);
    }
  };
}
```

`@timed`를 메서드 위에 붙이면 클래스 프로토타입의 그 메서드가 위에서 돌려준 함수로 바뀐다. 그래서 `@timed detail() {}`은 손으로 `OrderController.prototype.detail = timed(원래 detail, context)`를 한 것과 거의 같다. 돌려 보면 이렇게 찍힌다.

```text
detail: 9ms
```

`@log("field")`처럼 괄호가 붙은 건 데코레이터 팩토리다. `log("field")`를 먼저 불러서 그 결과(진짜 데코레이터 함수)를 붙인다. 설정값을 받고 싶을 때 쓰는 흔한 모양이다. Nest의 `@Injectable()`에 괄호가 있는 것도 이 때문이다. 괄호를 빼먹고 `@Injectable`이라고 쓰면 팩토리 자체가 데코레이터로 불려서 엉뚱하게 동작한다.

`context`에는 쓸 만한 정보가 들어 있다. `kind`는 `"class"`, `"method"`, `"getter"`, `"setter"`, `"field"`, `"accessor"` 중 하나이고, `name`, `static`, `private`, 값을 읽고 쓰는 `access`, 그리고 초기화 때 실행할 함수를 거는 `addInitializer`가 있다.

## 무엇에 붙이느냐에 따라 받는 것이 다르다

메서드 데코레이터는 함수를 받고 함수를 돌려준다. 필드는 조금 다르다. 클래스를 정의하는 시점에는 필드 값이 아직 없다. 그래서 필드 데코레이터는 첫 인자로 `undefined`를 받고, 값을 바꾸고 싶으면 "초기값을 받아 새 초기값을 돌려주는 함수"를 돌려준다.

```ts
// 필드: 초기값만 바꿀 수 있다
function trimmed(_value: undefined, _context: ClassFieldDecoratorContext<unknown, string>) {
  return (initial: string) => initial.trim();
}

// 접근자(accessor): get/set을 바꿔 끼울 수 있다
function positive<This>(
  target: ClassAccessorDecoratorTarget<This, number>,
  context: ClassAccessorDecoratorContext<This, number>,
): ClassAccessorDecoratorResult<This, number> {
  return {
    set(value) {
      if (value <= 0) throw new RangeError(`${String(context.name)}은 0보다 커야 한다: ${value}`);
      target.set.call(this, value);
    },
  };
}

class Product {
  @trimmed name = "  키보드  ";
  @positive accessor price = 39000;
}

const p = new Product();
console.log(JSON.stringify(p.name), p.price);
p.name = "  마우스 ";
console.log(JSON.stringify(p.name));
try { p.price = -1; } catch (e) { console.log((e as Error).message); }
```

```text
"키보드" 39000
"  마우스 "
price은 0보다 커야 한다: -1
```

둘째 줄을 보자. `@trimmed`는 처음 한 번만 공백을 지웠고, 나중에 대입한 `"  마우스 "`는 그대로 들어갔다. 필드 데코레이터는 필드를 감시하지 못한다. 대입할 때마다 무언가를 하려면 `accessor` 키워드를 쓴다. `accessor price`는 보이지 않는 저장소와 get/set 한 쌍을 자동으로 만들고, 데코레이터는 그 get/set을 바꿔 끼울 수 있다.

여기에도 함정이 하나 있다. `accessor price = -5`라고 쓴 클래스를 만들어 보면 오류 없이 `-5`가 들어간다. 초기값은 `set`을 거치지 않고 `init`으로 들어가기 때문이다. 초기값까지 검사하려면 돌려주는 객체에 `init(value)`도 넣어야 한다.

## 실행 순서: 먼저 다 평가하고, 안쪽부터 붙인다

데코레이터가 여러 개면 순서가 중요해진다. `@a @b greet()`에서 무엇이 바깥에서 감쌀까. 아래 코드에 로그를 심어 돌려 봤다.

```ts
function log(name: string) {
  console.log(`평가: ${name}`);
  return function (_value: unknown, context: DecoratorContext) {
    console.log(`적용: ${name} (${context.kind} ${String(context.name)})`);
    context.addInitializer?.(function () {
      console.log(`초기화: ${name}`);
    });
  };
}

@log("class")
class User {
  @log("field") name = "kim";
  @log("method-a") @log("method-b") greet() {}
  @log("static") static create() {}
}

console.log("--- new User()");
new User();
```

```text
평가: class
평가: field
평가: method-a
평가: method-b
평가: static
적용: static (method create)
적용: method-b (method greet)
적용: method-a (method greet)
적용: field (field name)
적용: class (class User)
초기화: static
초기화: class
--- new User()
초기화: method-b
초기화: method-a
초기화: field
```

`addInitializer`로 건 함수는 시점이 또 다르다. static 멤버와 클래스의 초기화 함수는 클래스 정의가 끝날 때 돌고, 인스턴스 멤버의 초기화 함수는 `new` 할 때마다 생성자 앞부분에서 돈다. 메서드를 `this`에 묶어 두는 `@bound` 같은 데코레이터가 이 훅을 쓴다.

## 표준 데코레이터와 experimentalDecorators는 다른 물건이다

TypeScript에는 데코레이터가 두 벌 있다. 2015년쯤 TC39 초안을 보고 먼저 넣은 레거시 방식은 `"experimentalDecorators": true`를 켜야 동작한다. Angular, NestJS, TypeORM, class-validator, InversifyJS가 이 방식 위에서 컸다. 그사이 TC39 제안이 크게 바뀌어 Stage 3에 올랐고, TypeScript 5.0이 이 새 표준을 넣었다. 지금은 플래그를 켜지 않으면 표준 방식으로 컴파일된다.

둘은 이름만 같고 함수 모양부터 다르다. 레거시 메서드 데코레이터는 `(target, propertyKey, descriptor)`를 받아 프로토타입과 속성 설명자를 직접 만진다. 표준은 `(value, context)`를 받고 값을 돌려준다. 레거시 데코레이터 함수를 표준 설정에서 붙이면 타입 오류가 나고, 반대도 마찬가지다.

실행 순서도 다르다. 같은 로그 코드를 `experimentalDecorators`로 돌리면 멤버마다 평가와 적용이 번갈아 일어나고, 인스턴스 멤버가 static보다 먼저다.

```text
평가: field
적용: field
평가: method-a
평가: method-b
적용: method-b
적용: method-a
평가: static
적용: static
평가: class
평가: param
적용: param
적용: class
```

출력에 `param`이 있다. 레거시에는 생성자 매개변수에 붙이는 데코레이터(`constructor(@Inject("MAILER") m)`)가 있다. 표준에는 없다. 같은 코드를 표준 설정으로 컴파일하면 이렇게 거절된다.

```text
param.ts(2,23): error TS1206: Decorators are not valid here.
```

매개변수 데코레이터는 TC39에 별도 제안으로 남아 있고 아직 표준이 아니다. Nest의 `@Inject()`, `@Body()`, `@Param()`이 모두 매개변수 데코레이터라서, Nest는 지금도 레거시 방식을 쓴다. 한 프로젝트 안에서 둘을 섞을 수는 없다. 플래그가 파일 단위가 아니라 프로젝트 단위라서다.

| | 표준 (TS 5.0+) | 레거시 (`experimentalDecorators`) |
|---|---|---|
| 시그니처 | `(value, context)` | `(target, key, descriptor)` |
| 매개변수 데코레이터 | 없음 | 있음 |
| 타입 메타데이터 자동 생성 | 없음 | `emitDecoratorMetadata`로 생성 |
| 메타데이터 저장 | `context.metadata` (TS 5.2+) | `reflect-metadata` 라이브러리 |
| 주로 쓰는 곳 | 새 코드, Lit 3, MobX 6 | NestJS, TypeORM, Angular 기존 코드 |

새 코드라면 표준을 고른다. 프레임워크가 레거시를 요구하면 그 프레임워크 문서의 tsconfig를 그대로 따른다. MobX 6이나 Lit 3처럼 두 방식을 다 지원하는 라이브러리도 있다.

## 송장을 몰래 붙여 주는 emitDecoratorMetadata

이제 첫 장면의 비밀이다. Nest는 `UserService`를 만들려면 `UserRepository`가 필요하다는 걸 어떻게 알까. 타입은 컴파일하면 사라지는데 말이다.

답은 `emitDecoratorMetadata`다. 이 옵션을 켜면 TypeScript가 데코레이터가 붙은 클래스에 생성자 매개변수의 타입을 런타임 값으로 적어 넣는다. 아래 작은 DI 컨테이너를 컴파일해서 결과를 봤다.

```json
// tsconfig.json의 일부
{
  "compilerOptions": {
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true
  }
}
```

```ts
import "reflect-metadata";

type Ctor<T = unknown> = new (...args: any[]) => T;
const providers = new Set<Ctor>();

function Injectable(): ClassDecorator {
  return (target) => {
    providers.add(target as unknown as Ctor); // 등록만 한다
  };
}

function resolve<T>(token: Ctor<T>, seen: Ctor[] = []): T {
  if (!providers.has(token)) throw new Error(`${token.name}에 @Injectable이 없다`);
  if (seen.includes(token)) throw new Error(`순환 의존: ${[...seen, token].map((c) => c.name).join(" -> ")}`);
  // 컴파일러가 붙여 둔 생성자 매개변수 타입을 꺼낸다
  const deps: Ctor[] = Reflect.getMetadata("design:paramtypes", token) ?? [];
  console.log(`${token.name} 생성자 인자:`, deps.map((d) => d?.name));
  return new token(...deps.map((d) => resolve(d, [...seen, token])));
}

@Injectable()
class Database {
  query(sql: string) { return `run: ${sql}`; }
}

@Injectable()
class UserRepository {
  constructor(private readonly db: Database) {}
  find(id: number) { return this.db.query(`SELECT * FROM users WHERE id = ${id}`); }
}

@Injectable()
class UserService {
  constructor(private readonly repo: UserRepository) {}
  get(id: number) { return this.repo.find(id); }
}

console.log(resolve(UserService).get(1));
```

컴파일된 JavaScript에서 `UserService` 부분을 보면 송장이 보인다. `__metadata("design:paramtypes", [UserRepository])` 한 줄이 생성자 첫 인자의 타입을 클래스 값 자체로 적어 둔다.

```text
UserService = __decorate([
    Injectable(),
    __metadata("design:paramtypes", [UserRepository])
], UserService);
```

## 메타데이터가 Object로 찍히는 날

`emitDecoratorMetadata`는 편하지만 조용히 틀린다. 컴파일러가 적을 수 있는 건 런타임에 값으로 존재하는 것뿐이기 때문이다.

인터페이스로 받은 매개변수를 보자.

```ts
import "reflect-metadata";
interface Mailer { send(to: string): void }
const Injectable = (): ClassDecorator => () => {};

@Injectable()
class SignupService {
  constructor(private mailer: Mailer, private retries: number) {}
}
console.log(Reflect.getMetadata("design:paramtypes", SignupService));
```

```text
[ [Function: Object], [Function: Number] ]
```

`Mailer`는 인터페이스라서 컴파일하면 사라진다. 컴파일러는 대신 `Object`를 적는다. 컨테이너는 `Object`를 보고 무엇을 넣어야 할지 모른다. Nest가 인터페이스에 `@Inject("MAILER")` 같은 토큰을 따로 붙이게 하는 이유가 이것이다. 유니언 타입, 제네릭 매개변수도 같은 이유로 `Object`가 된다. `import type { UserRepository }`로 타입만 가져와도 런타임 값이 없어져 같은 일이 생긴다. 레거시 데코레이터 클래스에서 `import type` 자동 정리를 켜 둔 [린터](/posts/linters-formatters)가 DI를 깨뜨리는 경우가 여기서 나온다.

순서 문제도 있다. 두 클래스가 서로를 생성자로 받으면, 메타데이터를 적는 순간 아직 정의되지 않은 클래스를 참조해 `undefined`가 들어간다. 위 실습 코드에서 `deps.map((d) => d?.name)`에 물음표를 붙인 것도 이 때문이다. Nest는 이럴 때 `forwardRef(() => OtherService)`로 참조를 늦추게 한다. 하지만 순환 의존 자체가 설계 냄새인 경우가 많다. 공통 부분을 세 번째 클래스로 떼어 내는 편이 낫다.

그리고 첫 장면의 Vitest. 메타데이터는 `tsc`가 타입 정보를 보고 만든다. esbuild는 파일 하나씩 타입 없이 변환하는 도구라서 `emitDecoratorMetadata`를 지원하지 않는다. Vite·Vitest는 기본으로 esbuild로 TypeScript를 변환하니 `design:paramtypes`가 비고, 컨테이너는 생성자에 아무것도 넣지 못한다. 그래서 `this.repo`가 `undefined`다. Nest를 Vitest로 테스트할 때는 메타데이터를 지원하는 SWC 플러그인(`unplugin-swc`)으로 변환기를 바꾼다. SWC는 `decoratorMetadata` 옵션으로 이 출력을 흉내 낸다. 빌드 도구가 타입을 언제 버리는지는 [빌드 도구 글](/posts/frontend-build-tooling)에서 더 자세히 다뤘다.

## 표준 쪽의 메타데이터: context.metadata

표준 데코레이터에는 `emitDecoratorMetadata`에 해당하는 기능이 없다. 타입을 자동으로 적어 주지 않는다. 대신 TypeScript 5.2부터 데코레이터 메타데이터 제안을 지원해서, 데코레이터끼리 정보를 모아 둘 객체(`context.metadata`)를 준다. 클래스 정의가 끝나면 이 객체가 `Class[Symbol.metadata]`에 붙는다.

```ts
// Node 22에는 Symbol.metadata가 없어 직접 만들어 둔다
(Symbol as { metadata?: symbol }).metadata ??= Symbol("Symbol.metadata");

function route(path: string) {
  return (_t: unknown, context: ClassMethodDecoratorContext) => {
    const routes = (context.metadata.routes ??= []) as string[];
    routes.push(`${path} -> ${String(context.name)}`);
  };
}

class OrderController {
  @route("/orders") list() { return []; }
  @route("/orders/:id") detail() { return null; }
}

console.log(OrderController[Symbol.metadata]);
```

```text
[Object: null prototype] {
  routes: [ '/orders -> list', '/orders/:id -> detail' ]
}
```

맨 윗줄의 폴리필을 빼고 돌리면 `context.metadata`가 `undefined`라서 `Cannot read properties of undefined (reading 'routes')`로 바로 터진다. 컴파일된 코드가 `Symbol.metadata`가 있을 때만 메타데이터 객체를 만들기 때문이다. 이 폴리필은 데코레이터가 붙은 클래스보다 먼저 실행돼야 한다.

이 방식으로 라우트 표나 검증 규칙은 모을 수 있지만, 생성자 타입을 보고 자동으로 주입하는 Nest식 DI는 만들 수 없다. 표준 위의 DI 라이브러리들이 토큰을 명시적으로 적게 하는 이유다.

## 데코레이터를 쓸 때와 말 때

데코레이터는 "이 클래스는 무엇이다"를 선언으로 보여 주는 데 강하다. `@Controller("/orders")`, `@Column()`, `@IsEmail()`은 코드를 읽는 사람에게 역할을 바로 알려 주고, 프레임워크는 그 표시를 모아 라우팅·스키마·검증을 만든다. 같은 일을 함수 호출로 하면 클래스 밖에 등록 코드가 흩어진다.

대가도 분명하다. 동작이 보이지 않는 곳에서 일어난다. `@Transactional()` 하나가 메서드를 감싸서 예외를 삼키는지, 커밋을 언제 하는지는 데코레이터 코드를 열어 봐야 안다. 스택 트레이스에는 감싼 함수가 끼어든다. 메서드를 바꿔 끼우는 데코레이터가 겹치면 순서에 따라 결과가 달라진다(위 a·b 순서). 테스트에서 데코레이터 효과만 빼고 싶어도 클래스 정의에 박혀 있어 떼어 내기 어렵다.

그래서 흔히 이렇게 나눈다. 프레임워크가 정한 데코레이터는 그 프레임워크의 언어로 받아들이고 쓴다. 직접 만드는 데코레이터는 부작용 없이 표시만 남기는 것(메타데이터 수집, 이름 등록) 위주로 두고, 로깅·재시도·캐시처럼 동작을 바꾸는 건 평범한 고차 함수나 명시적인 감싸기를 먼저 생각한다. 객체마다 다른 기능을 조합해야 한다면 [데코레이터 패턴](/posts/pattern-decorator)처럼 실행 중에 감싸는 쪽이 맞다.

## 결국 함수와 송장

데코레이터는 클래스 정의 때 한 번 불리는 함수이고, 받은 것을 돌려주거나 바꿔 끼운다. 표준 방식은 모두 평가한 뒤 멤버 종류 순서대로, 같은 대상에서는 가까운 것부터 적용한다. 레거시 `experimentalDecorators`는 시그니처와 순서가 다르고 매개변수 데코레이터가 있으며, `emitDecoratorMetadata`가 생성자 타입을 런타임 값으로 적어 줘서 Nest 같은 DI가 가능하다. 그 송장은 런타임 값이 있는 타입만 적을 수 있고, `tsc`가 아닌 변환기는 적지 않을 수 있다는 점을 기억하면 대부분의 이상한 장애가 설명된다.

## 면접에서 나올 만한 질문

### 데코레이터는 무엇이고 언제 실행되나요?

데코레이터는 클래스나 멤버를 받아 그대로 두거나 바꿔 끼운 것을 돌려주는 함수다. 인스턴스를 만들 때가 아니라 클래스를 정의하는 순간 한 번 실행된다. 표준 방식에서는 대상과 `context`를 받고, 메서드라면 새 함수를 돌려줘서 프로토타입의 메서드를 교체한다. `@log("x")`처럼 괄호가 있으면 팩토리를 먼저 불러 진짜 데코레이터를 얻는다.

### 데코레이터가 여러 개 붙으면 어떤 순서로 실행되나요?

표준 방식은 모든 데코레이터 식을 위에서부터 먼저 평가한 뒤, 멤버 종류 순서로 적용하고 클래스 데코레이터를 마지막에 적용한다. 실습한 TS 5.9에서는 static 메서드, 인스턴스 메서드, static 필드, 인스턴스 필드, 클래스 순이었다. 한 대상에 여럿이 붙으면 대상에 가까운 것부터 적용해서 `@a @b`는 `a(b(원래))`가 된다. 그래서 호출하면 바깥인 a가 먼저 돈다.

### 표준 데코레이터와 experimentalDecorators의 차이는 무엇인가요?

표준은 TC39 Stage 3 제안으로 TS 5.0부터 기본이고 `(value, context)`를 받아 값을 돌려준다. 레거시는 `(target, key, descriptor)`로 프로토타입을 직접 만지며, 매개변수 데코레이터와 `emitDecoratorMetadata`가 있다. 실행 순서도 달라서 레거시는 멤버마다 평가와 적용이 번갈아 일어난다. 플래그가 프로젝트 단위라 섞어 쓸 수 없고, NestJS·TypeORM은 지금도 레거시를 쓴다.

### NestJS는 생성자에 무엇을 넣어야 할지 어떻게 아나요?

`emitDecoratorMetadata`를 켜면 컴파일러가 데코레이터가 붙은 클래스에 `design:paramtypes` 메타데이터로 생성자 매개변수의 클래스를 런타임 값으로 적어 둔다. 컨테이너는 `reflect-metadata`의 `Reflect.getMetadata`로 이 목록을 읽고, 의존성 그래프를 아래부터 만들어 넣는다. 만든 인스턴스는 기본으로 캐시해 재사용한다.

### 인터페이스 타입으로 주입받으려 했더니 동작하지 않습니다. 왜 그런가요?

인터페이스는 컴파일 후 사라지는 타입이라 메타데이터에 `Object`로 적히고, 컨테이너는 `Object`만 보고 무엇을 넣을지 모른다. 유니언, 제네릭, `import type`으로 가져온 클래스도 같은 문제가 생긴다. 이럴 때는 문자열이나 심볼 토큰을 `@Inject(TOKEN)`으로 명시하고 모듈에서 그 토큰에 구현을 연결한다.

### Vitest로 바꿨더니 Nest 테스트에서 주입된 값이 undefined입니다. 원인은요?

Vitest가 쓰는 esbuild는 타입 정보 없이 파일 단위로 변환해서 `emitDecoratorMetadata` 출력을 만들지 않는다. 메타데이터가 비니 컨테이너가 생성자에 아무것도 넣지 못한다. `unplugin-swc`로 SWC 변환기를 쓰고 `decoratorMetadata`를 켜거나, 메타데이터를 만드는 `tsc` 기반 변환기를 쓴다.

### 표준 데코레이터에는 매개변수 데코레이터가 왜 없고, 메타데이터는 어떻게 다루나요?

매개변수 데코레이터는 TC39에서 별도 제안으로 분리돼 아직 표준이 아니다. 메타데이터는 TS 5.2부터 데코레이터 메타데이터 제안을 따라 `context.metadata` 객체에 모으고 `Class[Symbol.metadata]`로 읽는다. 다만 타입을 자동으로 적어 주지는 않아서 Nest식 자동 주입은 안 되고, 런타임에 `Symbol.metadata`가 없으면 폴리필이 필요하다.

### 데코레이터를 남용하면 어떤 문제가 생기나요?

동작이 선언 뒤에 숨어서 트랜잭션이나 예외 처리가 어떻게 되는지 코드를 열어 봐야 알고, 스택 트레이스에 감싼 함수가 끼어든다. 메서드를 교체하는 데코레이터가 겹치면 순서에 따라 결과가 바뀌고, 클래스 정의에 박혀 있어 테스트에서 떼어 내기 어렵다. 직접 만들 때는 메타데이터 수집 같은 표시 위주로 두고, 동작을 바꾸는 기능은 고차 함수나 명시적인 감싸기를 먼저 고려한다.
