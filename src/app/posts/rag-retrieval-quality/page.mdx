청크를 60자로 줄였더니 "PAY-4012가 나면 재시도해도 돼?"는 더 잘 찾는다. 그런데 며칠 뒤 "기능 플래그는 언제 지워?"에 엉뚱한 답이 나온다는 제보가 온다. 질문 몇 개를 손으로 넣어 보고 "좋아진 것 같다"로 배포하면 이런 일이 반복된다. 검색은 바꿀 때마다 어떤 질문은 좋아지고 어떤 질문은 나빠지기 때문이다.

이 글은 RAG의 검색 단계를 숫자로 재고, 그 숫자를 보면서 고치는 방법을 다룬다. 색인과 프롬프트 조립 같은 기본 흐름은 [기본 RAG 파이프라인 글](/posts/rag-classic-pipeline)에서, 임베딩과 HNSW 인덱스는 [벡터 DB 글](/posts/vector-db)에서, BM25 점수 계산은 [Elasticsearch와 역색인 글](/posts/elasticsearch-inverted-index)에서 이미 다뤘다. 실험은 기본 RAG 글과 같은 사내 위키 20편과 같은 코드로 Node 22에서 돌렸다. 임베딩 자리에는 글자 바이그램을 해시한 TF-IDF 벡터를 대역으로 썼다. 진짜 임베딩 모델보다 훨씬 단순해서 숫자 자체보다 비교하는 방법을 보면 된다.

## 정답지부터 만든다

재려면 정답지가 있어야 한다. 질문마다 "이 질문에는 어느 문서가 답인가"를 적어 둔 목록이다. 이 데모는 18개를 만들었다. 관련도는 2(답이 있다), 1(도움이 된다) 두 단계로 매겼고, 답이 되는 문장도 함께 적었다.

```js
export const EVAL = [
  { q: "롤백은 어떻게 해?", rel: { rollback: 2 } },
  { q: "배포는 어떻게 진행돼?", rel: { deploy: 2 } },
  { q: "PAY-4012가 나면 재시도해도 돼?", rel: { "payment-error": 2, idempotency: 1 } },
  { q: "429를 받으면 언제 다시 보내야 해?", rel: { "rate-limit": 2 } },
  { q: "실수로 깃허브에 API 키를 올렸어", rel: { "security-incident": 2 } },
  // ... 18개
];
// 답이 되는 문장: 조각 안에 이 문장이 통째로 있어야 "답을 담았다"고 본다
export const SPANS = ["직전 버전을 고르고 되돌리기 버튼을 누르면 된다", /* ... */];
```

질문은 실제 사용자가 쓰는 말투로 쓴다. "API 키 유출 대응 절차"처럼 문서 제목을 베낀 질문은 너무 쉽다. 실제 질문은 "실수로 깃허브에 API 키를 올렸어"처럼 온다. 서비스가 이미 돌고 있다면 검색 로그에서 자주 나오는 질문과 "답이 틀렸다" 피드백이 달린 질문을 골라 정답 문서를 사람이 붙이는 게 가장 좋다. 처음이라면 문서마다 질문을 두세 개씩 직접 쓰거나 LLM에게 문서를 주고 질문을 만들게 한 뒤 사람이 고른다. LLM이 만든 질문은 문서 표현을 그대로 따라 쓰는 경향이 있어서 점수가 실제보다 높게 나오기 쉽다.

정답지는 시험지다. 시험지가 실제 시험과 닮지 않으면 점수가 아무리 높아도 소용없다.

## 순위 하나에서 세 숫자 뽑기

세 숫자는 묻는 게 다르다. recall@k는 "프롬프트에 붙일 k개 안에 정답이 들어오나"를 본다. RAG에서 가장 먼저 볼 숫자다. k개 안에만 들면 모델이 읽을 수 있기 때문이다. MRR은 "첫 정답이 얼마나 위에 있나"를 본다. 정답이 하나뿐인 질문에 잘 맞는다. nDCG는 관련도의 높낮이와 순서를 함께 본다. 정답이 여럿이고 그중 더 좋은 답이 있을 때 쓴다. 순서를 바꿔 보면 차이가 보인다. 같은 세 문서가 kafka-lag, payment-error, idempotency 순서로 나왔다면 recall@3은 그대로 1이지만 nDCG@3은 0.659로 떨어진다.

RAG에서는 여기에 하나를 더 본다. 문서는 맞혔는데 답이 든 문장이 조각 경계에서 잘려 나갔다면 모델은 답을 못 한다. 그래서 "상위 3개 조각 중 하나에 답 문장이 통째로 들어 있나"(아래 표의 답포함@3)를 따로 쟀다. 문서 단위 지표만 보면 이 실패가 안 보인다.

## 같은 시험지로 세 가지 검색 비교

벡터 검색, BM25 키워드 검색, 둘을 합친 하이브리드를 같은 18개 질문으로 쟀다. 조각은 120자, 겹침 30자로 35개다.

```text
vector  recall@1=0.722 recall@3=0.944 MRR=0.866 nDCG@3=0.874
bm25    recall@1=0.750 recall@3=0.917 MRR=0.866 nDCG@3=0.868
hybrid  recall@1=0.833 recall@3=0.917 MRR=0.931 nDCG@3=0.914
```

하이브리드가 recall@1과 MRR을 끌어올렸다. 1등이 정답인 질문이 18개 중 14개에서 16개로 늘었다. recall@3은 오히려 0.944에서 0.917로 조금 내려갔다. 질문별로 보면 이유가 있다. "PAY-4012가 나면 재시도해도 돼?"에서 벡터는 멱등 키 문서를 3등에 올렸는데, 하이브리드에서는 BM25가 질문의 "나면"과 "장애가 나면"이 겹친 롤백 문서를 2등으로 끌어올려 멱등 키 문서가 밀려났다. 조사를 떼어 낸 정도의 단순한 분석기에서는 이런 흔한 낱말이 점수를 흔든다. 평균 하나만 보면 이런 맞바꿈이 안 보인다. 지표가 움직였으면 어느 질문이 좋아지고 나빠졌는지 꼭 열어 본다.

둘이 서로 다른 질문을 놓친다는 점이 합치는 이유다. "429를 받으면 언제 다시 보내야 해?"에서 벡터 대역은 기능 플래그 문서를 1등, 요청 제한 문서를 2등에 올렸다(RR 0.5). BM25는 "429"를 낱말 하나로 정확히 맞혔지만, "다시"가 두 번 나오는 멱등 키 문서와 "받으면"이 겹친 온콜 문서를 더 위에 놓았다(RR 0.33). 하이브리드는 이 질문에서 요청 제한 문서를 1등으로 올렸다. 그 과정은 아래 RRF에서 본다. 실제 임베딩 모델에서도 에러 코드, 제품명, 사람 이름처럼 글자가 정확히 맞아야 하는 질문은 키워드 검색이 강하고, 표현이 달라도 뜻이 같은 질문은 벡터 검색이 강하다.

## 두 순위를 합치는 방법, RRF

두 검색의 점수를 그냥 더하면 안 된다. 같은 질문의 실제 점수를 보면 바로 보인다.

```text
BM25 단어: 429 | 받으면 | 언제 | 다시 | 보내야 | 해
vector: feature-flag#0(0.197), rate-limit#0(0.153), vendor-faq#1(0.144), oncall#1(0.100), idempotency#0(0.094)
bm25  : idempotency#0(4.14), oncall#1(3.22), rate-limit#0(3.09), db-backup#0(2.84), oncall#0(2.31)
```

코사인 점수는 0.1대, BM25 점수는 2~4 사이다. 더하면 BM25가 순위를 혼자 정한다. 정규화해서 가중합을 낼 수도 있지만, 점수 분포가 질문마다 달라서 가중치를 정하기 까다롭다. RRF(Reciprocal Rank Fusion)는 점수를 버리고 순위만 쓴다. 문서가 각 목록에서 r등이면 1/(k + r)을 받고, 목록마다 받은 값을 더한다. k는 보통 60이다. Cormack 등이 2009년 논문에서 제안한 값이 그대로 널리 쓰인다.

RRF가 좋아하는 건 합의다. 한쪽에서 압도적인 1등보다, 양쪽에서 꾸준히 위쪽인 문서가 이긴다. 점수 눈금을 맞출 필요가 없어서 검색기를 셋, 넷으로 늘려도 그대로 쓴다. 단점도 그 성질에서 나온다. 한쪽 검색기가 확실히 맞힌 경우(벡터 점수 0.9, 나머지 0.1)에도 그 차이를 버린다. 그럴 때는 점수를 0~1로 정규화한 가중합이 낫기도 하다. 고르는 기준은 역시 평가 세트다.

직접 짜 본다. 순위는 0부터 세니까 1/(k + r + 1)이다.

## 청크 크기를 바꾸면 무엇이 움직이나

조각 크기와 겹침을 다섯 가지로 바꿔 하이브리드 검색으로 쟀다. 문서recall@3은 상위 3개 문서 안에 정답 문서가 있는 비율, 답포함@3은 상위 3개 조각 중 하나에 답 문장이 통째로 있는 비율, 마지막 열은 상위 3개 조각을 합친 글자 수의 평균이다. 프롬프트에 붙는 양이다.

```text
size/overlap  청크수  문서recall@3  답포함@3  top3글자수(평균)
  60/15        66      0.944       0.500     165
 120/0         34      0.917       0.889     305
 120/30        35      0.917       0.944     287
 200/40        21      0.972       1.000     426
 400/0         20      0.972       1.000     446
```

60자 조각은 문서는 가장 잘 찾는데(0.944) 답 문장을 온전히 담은 건 절반뿐이다. 문서 단위 지표만 봤다면 60자가 좋아 보였을 것이다. 120자에서 겹침 0과 30을 비교하면 문서recall은 같은데 답포함이 0.889에서 0.944로 오른다. 겹침이 경계에서 잘린 문장을 살린 몫이다. 200자 이상은 둘 다 높지만 붙는 글이 1.5배로 는다. 아래 그림에서 단계를 넘기며 두 막대가 어떻게 엇갈리는지 본다.

작은 조각으로 찾고 큰 조각을 붙이는 방법도 있다. 검색은 문장 단위 작은 조각으로 정밀하게 하고, 프롬프트에는 그 조각이 속한 문단이나 앞뒤 조각을 함께 붙인다. 부모-자식 청크, 문장 창(sentence window) 같은 이름으로 불린다. 문서 제목을 조각 앞에 붙여 임베딩하는 것도 짧은 조각이 맥락을 잃지 않게 하는 흔한 방법이다.

## 넉넉히 뽑고 다시 줄 세우기

벡터 검색은 질문과 문서를 따로따로 벡터로 만든 뒤 거리만 잰다. 이런 모델을 바이인코더(bi-encoder)라고 한다. 문서 벡터를 미리 만들어 둘 수 있어서 빠르지만, 질문과 문서를 함께 읽지는 않는다. 리랭커는 보통 크로스인코더(cross-encoder)다. 질문과 문서 하나를 한 입력으로 붙여서 모델에 넣고 관련도 점수 하나를 받는다. 두 글을 함께 읽으니 "재시도해도 돼?"와 "재시도해도 소용없다"의 관계까지 본다. 대신 후보마다 모델을 한 번씩 돌려야 해서 미리 계산해 둘 수 없다.

## 질문을 고쳐서 다시 묻기

18개 중 세 검색이 모두 놓친 질문이 있다. "배포는 어떻게 진행돼?"다. 지금 배포 문서에는 "진행"이라는 말이 없고, 구버전 문서에만 있다. 사용자의 말과 문서의 말이 다르다. 질문을 검색하기 좋은 말로 고쳐 쓰는 쿼리 재작성(query rewriting)이 이걸 노린다. 보통 LLM에게 "이 질문을 검색어로 다시 써라"라고 시킨다.

이 환경에는 모델이 없어서, 모델이 쓸 법한 재작성 문장을 손으로 써서 넣었다. 재작성 문장은 손으로 쓴 것이고, 그 문장으로 돌린 하이브리드 검색 결과는 실제 출력이다.

```text
배포는 어떻게 진행돼?
  → deploy-old#0, deploy-freeze#0, rollback#1
배포 절차: 브랜치 머지, CI 빌드, 스테이징, 프로덕션 반영
  → deploy#0, deploy#1, rollback#0
실수로 깃허브에 API 키를 올렸어
  → vendor-faq#1, vendor-faq#0, security-incident#0
저장소에 API 키가 노출된 보안 사고 대응
  → security-incident#0, rate-limit#0, vendor-faq#1
```

고친 질문은 두 경우 모두 정답 문서를 1등으로 올렸다. "깃허브"와 "저장소"처럼 뜻은 같고 글자가 다른 경우가 특히 그렇다. 주의할 점도 있다. 재작성에 LLM 호출이 한 번 더 들어가니 지연과 비용이 는다. 모델이 질문의 뜻을 바꿔 버릴 수도 있다. 그래서 원래 질문과 고친 질문으로 둘 다 검색해서 RRF로 합치는 방식을 많이 쓴다.

HyDE(Hypothetical Document Embeddings)는 한 걸음 더 간다. 질문 대신 "이 질문에 대한 그럴듯한 답"을 모델에게 먼저 쓰게 하고, 그 가짜 답으로 검색한다. 질문보다 답이 문서와 생김새가 비슷하다는 생각이다. Gao 등이 2022년에 제안했다.

## 권한 없는 조각은 검색 안에서 거른다

검색 품질에는 "보면 안 되는 걸 찾지 않는 것"도 들어간다. 위키에는 인사팀만 볼 수 있는 보상 기준 문서가 있다. 조각마다 `acl` 메타데이터를 붙여 뒀다. 엔지니어 그룹 사용자가 "연봉 인상률 기준이 뭐야?"라고 물었을 때 벡터 검색으로 세 가지 방식을 돌려 봤다.

```text
ACL 없이     : salary#0[hr], security-incident#0[all], oncall#1[all]
top-3 뒤 거름: security-incident#0, oncall#1
먼저 거름    : security-incident#0(0.182), oncall#1(0.097), feature-flag#0(0.056)
```

권한을 안 보면 인사 문서가 1등으로 프롬프트에 들어간다. 모델에게 "이 내용은 말하지 마"라고 지시해도 소용없다. 프롬프트에 들어간 순간 유출될 수 있다고 봐야 한다. 상위 3개를 뽑은 뒤에 거르면 유출은 막지만 결과가 2개로 줄어든다. 걸러질 문서가 많은 사용자일수록 결과가 비어 간다. 권한 조건을 검색 안에서 함께 걸어야 권한 있는 문서 중에서 top-3을 채운다.

필터를 검색 전에 거느냐 뒤에 거느냐는 HNSW 같은 근사 인덱스에서 성능 문제로도 이어진다. pgvector에서 필터 때문에 결과가 모자라는 모습과 부분 인덱스로 푸는 법은 [벡터 DB 글](/posts/vector-db)에 실제 `EXPLAIN` 출력과 함께 있다. 권한 말고도 날짜, 팀, 제품, 언어 같은 메타데이터 필터는 같은 방식으로 건다. 사용자가 "작년 장애 회고"처럼 조건을 말로 하면, 질문에서 조건을 뽑아 필터로 바꾸는 단계를 따로 두기도 한다.

권한도 색인할 때 찍어 둔 값이다. 이걸 잊기 쉽다. 위키에서 문서 권한을 바꿨는데 조각의 `acl`을 다시 쓰지 않으면, 이미 비공개가 된 문서가 계속 검색된다. 권한 변경도 문서 변경과 똑같이 다시 색인하는 신호로 다룬다.

## 바꿀 때마다 시험을 다시 친다

여기까지의 실험을 한 스크립트로 묶으면 회귀 테스트가 된다. 기준 설정(120자/30자, 하이브리드)과 후보 설정(60자/15자)을 같은 평가 세트로 돌리고, 어떤 지표든 0.02 넘게 떨어지면 실패로 끝낸다.

```bash
node gate.mjs; echo "exit=$?"   # 기준과 후보를 비교하고 종료 코드를 본다
```

```text
metric     base   cand   diff
recall3   0.917  0.944  +0.028
mrr       0.931  0.917  -0.014
answer3   0.944  0.500  -0.444  ✗
새로 틀린 질문: 429를 받으면 언제 다시 보내야 해? / 온콜 알림을 놓치면 어떻게 돼? / 기능 플래그는 언제 지워? / 같은 결제 요청을 두 번 보내면 어떻게 돼? / 상품 정보를 바꾸면 검색에 언제 반영돼? / 블랙프라이데이 기간에 배포해도 돼? / 실수로 깃허브에 API 키를 올렸어 / cdn_hit_ratio는 어디서 봐?
FAIL: 기준보다 0.02 넘게 떨어진 지표가 있다
exit=1
```

문서recall@3만 봤다면 후보 설정이 더 좋아 보였을 것이다(+0.028). 답포함@3이 0.944에서 0.5로 떨어진 걸 잡아낸 건 지표를 하나 더 둔 덕분이다. 새로 틀린 질문 목록이 있으면 무엇을 들여다볼지 바로 안다. 종료 코드가 1이니 CI에 그대로 넣으면 이 변경은 머지되지 않는다.

운영하면서 지킬 것도 몇 가지 있다. 평가 세트는 사용자 피드백과 장애 사례로 계속 늘린다. 다만 늘린 질문에 맞춰 설정을 계속 고르면 그 질문들에만 맞춘 설정이 되니, 일부는 떼어 두고 가끔만 본다. 임베딩 모델이나 문서가 바뀌면 숫자가 바뀌므로 기준값도 다시 잡는다. 마지막으로 검색 지표가 좋아도 최종 답이 좋은지는 따로 봐야 한다. 답이 근거 조각과 맞는지, 질문에 답했는지를 사람이 표본으로 보거나 LLM에게 채점을 맡기는 방법이 있고, 이건 검색 지표와 다른 층의 평가다.

## 시험지가 먼저다

검색 품질은 감으로 고치면 한쪽이 좋아질 때 다른 쪽이 망가진다. 실제 질문으로 정답지를 만들고, recall@k와 MRR과 nDCG에 답포함 같은 RAG용 지표를 더해 잰 뒤, 하이브리드와 RRF, 청크 크기, 리랭킹, 쿼리 재작성을 하나씩 켜 보며 숫자로 고른다. 권한 필터는 품질 이전의 조건이라 검색 안에 넣는다. 한 번 찾아서는 안 되는 질문은 검색을 아무리 다듬어도 남는데, 그건 [GraphRAG](/posts/graph-rag)와 [에이전틱 RAG](/posts/agentic-rag)에서 다룬다.

## 면접에서 나올 만한 질문

### RAG의 검색 품질은 어떻게 재나요?

질문마다 정답 문서를 붙인 평가 세트를 만들고, 검색 결과 순위로 recall@k, MRR, nDCG를 계산한다. RAG에서는 프롬프트에 붙일 k개 안에 정답이 드는지가 중요해서 recall@k를 먼저 본다. 문서는 맞혔는데 답 문장이 조각 경계에서 잘리는 실패가 있어서, 상위 조각에 답 문장이 들어 있는지도 따로 잰다.

### recall@k, MRR, nDCG는 각각 무엇을 보나요?

recall@k는 정답 중 상위 k개 안에 든 비율이라 순서를 따지지 않는다. MRR은 첫 정답 순위의 역수 평균이라 정답이 하나인 질문에 맞는다. nDCG는 관련도 등급과 순위를 함께 보고 이상적인 순서 대비 비율로 나타낸다. 같은 결과에서도 순서만 바뀌면 recall은 그대로이고 nDCG는 떨어진다.

### 하이브리드 검색은 왜 쓰나요?

벡터 검색과 키워드 검색이 서로 다른 질문을 놓치기 때문이다. 에러 코드나 제품명처럼 글자가 정확히 맞아야 하는 질문은 BM25가, 표현이 달라도 뜻이 같은 질문은 벡터가 강하다. 둘을 합치면 실험에서 recall@1이 0.722에서 0.833으로 올랐지만 일부 질문은 나빠졌으므로 질문별로 확인한다.

### RRF는 어떻게 동작하고, 점수를 그냥 더하면 안 되는 이유는 무엇인가요?

문서가 각 목록에서 r등이면 1/(k + r)을 받고, 그 합으로 다시 정렬한다. k는 보통 60이다. 코사인 점수와 BM25 점수는 눈금이 달라서 그냥 더하면 한쪽이 순위를 혼자 정한다. RRF는 순위만 쓰니 정규화가 필요 없고 여러 목록에서 꾸준히 위에 있는 문서를 올린다. 대신 한쪽이 확실히 맞힌 점수 차이는 버린다.

### 청크 크기는 어떻게 정하나요?

여러 크기로 같은 평가 세트를 돌려 비교한다. 작으면 문서는 잘 찾아도 답 문장이 잘리고, 크면 답은 담기지만 붙는 글이 늘고 긴 문서에서는 벡터가 여러 주제의 평균이 된다. 답포함 비율이 충분하면서 붙는 글이 가장 적은 지점을 고르고, 작은 조각으로 찾고 부모 문단을 붙이는 방식도 고려한다.

### 리랭커는 무엇이고 왜 두 단계로 쓰나요?

리랭커는 보통 질문과 문서를 한 입력으로 함께 읽고 관련도를 매기는 크로스인코더다. 벡터 검색의 바이인코더보다 정확하지만 문서마다 모델을 돌려야 해서 전체 문서에 쓸 수 없다. 그래서 빠른 검색으로 후보를 넉넉히 뽑고 리랭커로 상위 몇 개만 고른다. 1단계 후보에 정답이 없으면 리랭커도 살릴 수 없으니 넓은 k의 recall을 따로 본다.

### 쿼리 재작성과 HyDE는 언제 쓰나요?

사용자의 말과 문서의 말이 다를 때 쓴다. 재작성은 질문을 검색어 형태로 다시 쓰고, HyDE는 가상의 답을 먼저 쓰게 한 뒤 그 답으로 검색한다. LLM 호출이 한 번 더 들어가 지연과 비용이 늘고 뜻이 바뀔 위험이 있어서, 원래 질문 결과와 RRF로 합치고 평가 세트로 효과를 확인한다. HyDE의 가상 답은 검색에만 쓰고 프롬프트에는 넣지 않는다.

### 권한이 있는 문서는 어떻게 다루나요?

조각마다 권한 메타데이터를 붙이고 검색 조건 안에서 거른다. 거르지 않으면 볼 수 없는 문서가 프롬프트에 들어가고, 그 순간 유출될 수 있다고 봐야 한다. top-k를 뽑은 뒤 거르면 결과 개수가 줄어든다. 사용자 그룹은 서버가 인증 정보에서 꺼내고, 문서 권한이 바뀌면 다시 색인한다.
