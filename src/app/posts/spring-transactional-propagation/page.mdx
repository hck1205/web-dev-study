<EasyIntro>
  주문을 저장하다가 쿠폰 확인에서 에러가 났다. 그 에러를 잡아서 넘겼으니 주문은 저장될 줄 알았는데, 마지막에 "조용히 되돌렸다"는 에러가 나면서 주문까지 사라졌다.

  트랜잭션은 여러 작업을 한 묶음으로 처리해서, 다 되거나 하나도 안 되게 만드는 장치다. 같이 장을 보는 친구들이 장바구니 하나를 함께 쓰는 것과 비슷하다. 누군가 장바구니에 "이번 장보기는 취소"라는 쪽지를 붙이면, 다른 친구가 아무리 계산대로 가져가도 계산이 되지 않는다. 처음 장면에서는 쿠폰 확인이 그 쪽지를 붙이고 나갔다.

  이 글은 장바구니를 함께 쓸지, 잠깐 다른 장바구니를 쓸지 정하는 규칙을 본다. 어떤 에러에서 취소되고 어떤 에러에서는 그대로 계산되는지, 읽기만 하겠다고 표시하면 무엇이 달라지는지, 장바구니를 든 채 오래 기다리면 왜 다른 손님이 장바구니를 못 받는지도 실제로 돌려 보며 확인한다.
</EasyIntro>

## 예외를 잡았는데 커밋이 실패한다

주문을 저장하고 쿠폰을 쓰는 메서드가 있다. 쿠폰이 만료됐으면 쿠폰 없이 주문만 받으려고 예외를 잡았다.

```java
@Service
class OrderService {
  @Transactional
  public void placeWithCoupon(String code) {
    orders.save(new Order("PLACED"));
    try { coupons.use(code); }   // CouponService.use()에도 @Transactional이 붙어 있다
    catch (IllegalArgumentException e) { System.out.println("caught: " + e.getMessage()); }
  }
}
```

예외는 분명히 잡혔다. 그런데 메서드가 끝나는 순간 다른 예외가 튀어나오고, 주문도 저장되지 않았다.

```text
caught: expired coupon
org.springframework.transaction.UnexpectedRollbackException: Transaction silently rolled back because it has been marked as rollback-only
-> orders=0 audit=0
```

`placeWithCoupon`이 연 트랜잭션에 쿠폰 메서드가 참여했고, 쿠폰 메서드가 런타임 예외로 끝나면서 트랜잭션 전체에 "롤백만 가능" 표시를 붙였다. 바깥에서 예외를 잡아 커밋하려 해도, 표시가 붙은 트랜잭션은 커밋되지 않는다. 스프링은 롤백한 뒤 "당신은 커밋을 원했지만 롤백됐다"는 사실을 `UnexpectedRollbackException`으로 알린다.

이 글은 이런 일을 만드는 규칙을 하나씩 실제 로그로 따라간다. 트랜잭션 매니저가 커넥션을 스레드에 묶는 방식, 전파 옵션(REQUIRED, REQUIRES_NEW, NESTED), 체크 예외의 기본 규칙, `readOnly`가 하는 일, 트랜잭션 안의 외부 호출, 커밋 뒤에 도는 이벤트 리스너다. `@Transactional`이 같은 클래스 안의 호출에서 사라지는 프록시 문제는 [IoC 컨테이너와 DI](/posts/spring-ioc-di)에서 다뤘으니 여기서는 반복하지 않는다. 트랜잭션 자체의 성질(원자성, 격리)은 [ACID](/posts/acid-transactions)와 [트랜잭션과 격리 수준](/posts/db-transaction-isolation)에 있다.

예제는 JDK 21, Spring Boot 4.1.1(Spring Framework 7.0.9, Hibernate 7.4.5), H2 메모리 DB로 돌렸다. 트랜잭션 매니저는 JPA를 쓰면 자동 구성되는 `JpaTransactionManager`다. 로그는 아래 설정으로 켰다.

```properties
logging.level.org.springframework.orm.jpa.JpaTransactionManager=DEBUG
```

JDBC나 MyBatis만 쓰면 Boot는 `DataSourceTransactionManager`를 상속한 `JdbcTransactionManager`를 등록하고, 하는 일은 같고 로그 이름만 다르다.

## 트랜잭션은 스레드에 묶인 커넥션이다

`@Transactional` 메서드가 불리면 프록시가 트랜잭션 매니저에게 트랜잭션을 시작해 달라고 한다. 매니저는 커넥션 풀에서 커넥션 하나를 꺼내 자동 커밋을 끄고, 그 커넥션(JPA라면 EntityManager)을 지금 스레드에 묶어 둔다. 스레드 로컬 저장소에 넣는 것이다. 그 뒤로 같은 스레드에서 리포지토리가 쿼리를 날리면 새 커넥션을 꺼내지 않고 이 묶인 커넥션을 쓴다. 그래서 서로 다른 리포지토리의 저장이 한 트랜잭션이 된다.

처음 장면의 로그를 보면 이 묶임이 그대로 보인다.

```text
D: Creating new transaction with name [demo.tx.OrderService.placeWithCoupon]: PROPAGATION_REQUIRED,ISOLATION_DEFAULT
D: Opened new EntityManager [SessionImpl(1798680820<open>)] for JPA transaction
D: Exposing JPA transaction as JDBC [org.springframework.orm.jpa.vendor.HibernateJpaDialect$HibernateConnectionHandle@2cf669f2]
D: Found thread-bound EntityManager [SessionImpl(1798680820<open>)] for JPA transaction
D: Participating in existing transaction
```

첫 줄에서 트랜잭션 이름이 메서드 이름으로 정해지고, 기본 전파(REQUIRED)와 기본 격리(DB 기본값)가 찍힌다. 그다음 `orders.save()`가 불리자 "스레드에 묶인 EntityManager를 찾았다", "이미 있는 트랜잭션에 참여한다"가 나온다. `SessionImpl(1798680820)`이라는 같은 번호가 이어진다.

스레드에 묶인다는 사실에서 바로 따라 나오는 함정이 있다. 트랜잭션 안에서 `@Async` 메서드를 부르거나 `CompletableFuture.supplyAsync`, `parallelStream()`으로 다른 스레드에 일을 넘기면, 그 스레드에는 묶인 커넥션이 없다. 거기서 한 저장은 바깥 트랜잭션과 상관없는 별도 트랜잭션이 되거나, 트랜잭션 없이 바로 커밋된다. 바깥이 롤백돼도 그 저장은 남는다. 또 트랜잭션은 메서드가 끝날 때까지 커넥션 하나를 계속 쥐고 있다. 이 사실은 뒤의 외부 호출 절에서 다시 나온다.

## 전파: 이미 열린 트랜잭션을 만나면

`@Transactional` 메서드가 다른 `@Transactional` 메서드를 부를 때, 안쪽 메서드는 바깥 트랜잭션에 참여할 수도, 새로 열 수도 있다. 이걸 정하는 속성이 전파(propagation)다. 자주 쓰는 것은 셋이고, 나머지는 드물다.

| 전파 | 바깥 트랜잭션이 있으면 | 없으면 |
|---|---|---|
| `REQUIRED` (기본) | 참여한다 | 새로 연다 |
| `REQUIRES_NEW` | 바깥을 잠시 내려놓고 새로 연다 | 새로 연다 |
| `NESTED` | 바깥 안에 세이브포인트를 만든다 | 새로 연다 |
| `SUPPORTS` | 참여한다 | 트랜잭션 없이 돈다 |
| `MANDATORY` | 참여한다 | 예외 |
| `NOT_SUPPORTED` | 바깥을 내려놓고 트랜잭션 없이 돈다 | 트랜잭션 없이 돈다 |
| `NEVER` | 예외 | 트랜잭션 없이 돈다 |

### REQUIRED는 하나의 운명을 나눈다

REQUIRED로 참여한 안쪽 메서드는 따로 커밋하거나 롤백하지 못한다. 물리적인 트랜잭션은 바깥이 연 하나뿐이고, 안쪽은 그 위에 얹힌 논리적인 트랜잭션이다. 안쪽이 런타임 예외로 끝나면 할 수 있는 일은 "이 물리 트랜잭션은 롤백만 가능"이라고 표시하는 것뿐이다. 처음 장면의 로그 뒷부분이 그 순간이다.

```text
D: Participating transaction failed - marking existing transaction as rollback-only
D: Setting JPA transaction on EntityManager [SessionImpl(1798680820<open>)] rollback-only
  caught: expired coupon
D: Initiating transaction commit
D: Committing JPA transaction on EntityManager [SessionImpl(1798680820<open>)]
D: Closing JPA EntityManager after transaction
  org.springframework.transaction.UnexpectedRollbackException: Transaction silently rolled back because it has been marked as rollback-only
```

고치는 방법은 쿠폰 실패가 주문 전체를 무르는 일인지 아닌지에 달렸다. 쿠폰이 실패해도 주문은 받아야 한다면 쿠폰 메서드가 예외를 던지지 않게 한다. "쓸 수 있는지 확인"과 "쓰기"를 나누고, 확인은 boolean이나 결과 객체로 돌려준다. 쿠폰 메서드에 `@Transactional`이 꼭 필요하지 않다면 빼는 것도 방법이다. 트랜잭션 프록시를 지나지 않으면 롤백 표시도 붙지 않는다. 쿠폰 사용 기록이 주문과 독립된 일이라면 다음에 볼 REQUIRES_NEW를 쓴다.

`noRollbackFor = IllegalArgumentException.class`를 안쪽 메서드에 붙이는 방법도 있다. 그 예외로는 롤백 표시를 남기지 않는다. 다만 예외 타입 하나로 롤백 여부가 갈리면 나중에 읽는 사람이 놓치기 쉽다.

### REQUIRES_NEW는 잠시 바깥을 내려놓는다

결제가 실패해도 "주문 시도가 있었다"는 감사 로그는 남기고 싶다. 감사 로그 저장을 REQUIRES_NEW로 바꾼다.

```java
@Service
class AuditService {
  @Transactional(propagation = Propagation.REQUIRES_NEW)
  public void record(String m) { repo.save(new AuditLog(m)); }
}

@Transactional
public void placeAndAuditThenFail() {
  orders.save(new Order("PLACED"));
  audit.record("order attempt");
  throw new IllegalStateException("payment timeout");   // 결제가 실패했다
}
```

```text
D: Creating new transaction with name [demo.tx.OrderService.placeAndAuditThenFail]: PROPAGATION_REQUIRED,ISOLATION_DEFAULT
D: Opened new EntityManager [SessionImpl(754346482<open>)] for JPA transaction
D: Suspending current transaction, creating new transaction with name [demo.tx.AuditService.record]
D: Opened new EntityManager [SessionImpl(788790720<open>)] for JPA transaction
D: Committing JPA transaction on EntityManager [SessionImpl(788790720<open>)]
D: Resuming suspended transaction after completion of inner transaction
D: Initiating transaction rollback
D: Rolling back JPA transaction on EntityManager [SessionImpl(754346482<open>)]
  payment timeout
  -> orders=0 audit=1
```

`Suspending`과 `Resuming` 사이에서 EntityManager 번호가 바뀌었다. 바깥 트랜잭션을 스레드에서 떼어 내 보관하고, 새 커넥션으로 새 트랜잭션을 열어 커밋한 뒤, 보관했던 바깥을 다시 붙였다. 그 뒤 바깥은 결제 실패로 롤백됐고, 감사 로그 한 줄만 남았다. 아래 그림이 스레드에 묶인 트랜잭션이 쌓였다 빠지는 모습이다.

REQUIRES_NEW에는 비용과 함정이 있다.

- 커넥션을 두 개 쓴다. 바깥이 쥔 커넥션 A는 안쪽이 도는 동안에도 반납되지 않는다. 풀이 10개인데 동시에 10개 요청이 REQUIRES_NEW에 들어가면, 모두 두 번째 커넥션을 기다리며 아무도 끝나지 않는다. 이것도 교착이다. 풀 크기는 "동시 요청 수 × 한 요청이 동시에 쥐는 커넥션 수"로 따진다.
- 안쪽은 바깥이 아직 커밋하지 않은 데이터를 못 본다. 바깥에서 막 넣은 주문 행을 안쪽에서 읽으면 다른 트랜잭션이라 안 보인다(격리 수준에 따라). 그 행을 외래 키로 참조하는 감사 로그를 넣으려 하면 바깥의 행 잠금을 기다리다 멈출 수도 있다.
- 안쪽이 커밋된 뒤 바깥이 롤백되면 둘이 어긋난다. 감사 로그처럼 어긋나도 되는 일에만 쓴다.

### NESTED는 세이브포인트다

NESTED는 바깥 트랜잭션 안에 세이브포인트를 만들고, 안쪽이 실패하면 세이브포인트까지만 되돌린다. 커넥션 하나로 "부분 롤백"을 할 수 있다는 점에서 REQUIRES_NEW와 다르다. 바깥이 롤백되면 안쪽 것도 함께 사라진다.

그런데 JPA에서 그냥 쓰면 동작하지 않는다. 감사 저장을 NESTED로 바꿔 돌려 봤다.

```text
org.springframework.transaction.NestedTransactionNotSupportedException: Transaction manager does not allow nested transactions by default - specify 'nestedTransactionAllowed' property with value 'true'
```

`JpaTransactionManager`는 기본으로 중첩 트랜잭션을 막아 둔다. 설정을 켜고 다시 돌렸다.

```text
org.springframework.transaction.NestedTransactionNotSupportedException: JpaDialect does not support savepoints - check your JPA provider's capabilities
```

Hibernate와 함께 쓰는 JPA 트랜잭션에서는 세이브포인트를 지원하지 않는다. DB를 세이브포인트까지 되돌려도 영속성 컨텍스트에 올라와 있는 엔티티 상태는 되돌릴 방법이 없으니, 둘이 어긋나는 걸 막는 셈이다. NESTED는 JDBC를 직접 쓰는 `DataSourceTransactionManager`(`JdbcTransactionManager`)에서 쓴다. JPA에서 부분 실패를 다루려면 실패할 수 있는 일을 트랜잭션 밖에서 먼저 확인하거나, REQUIRES_NEW로 떼어 낸다.

## 체크 예외는 롤백하지 않는다

결제 거절을 체크 예외(`Exception`을 상속한 예외)로 만들었다고 해 보자.

```java
class PaymentDeclined extends Exception { ... }

@Transactional
public void placeChecked() throws PaymentDeclined {
  orders.save(new Order("PLACED"));
  throw new PaymentDeclined("card declined");
}
```

```text
  card declined
  -> orders=1 audit=0
```

예외가 났는데 주문이 저장됐다. 스프링의 기본 규칙은 "`RuntimeException`과 `Error`에서만 롤백, 체크 예외는 커밋"이다. EJB 시절부터 내려온 관례로, 체크 예외는 호출자가 처리할 수 있는 업무상 결과라고 보는 관점이다. 실무에서는 이 기본값 때문에 사고가 난다. 외부 SDK가 던지는 `IOException`이나 직접 만든 업무 예외가 `Exception`을 상속했다면, 실패했는데 절반만 저장된 데이터가 남는다.

체크 예외에서도 롤백하려면 `rollbackFor`를 준다.

```java
@Transactional(rollbackFor = Exception.class)
public void placeCheckedRollback() throws PaymentDeclined { ... }
```

```text
  card declined
  -> orders=0 audit=0
```

메서드마다 붙이기 번거로우면 Spring Framework 6.2부터 생긴 전역 설정이 있다. `@EnableTransactionManagement(rollbackOn = RollbackOn.ALL_EXCEPTIONS)`로 모든 예외에서 롤백하게 바꾼다. 팀 규칙으로 "업무 예외는 런타임 예외로 만든다"를 정해 두는 곳도 많다.

롤백 규칙은 트랜잭션을 연 메서드에만 해당하지 않는다. 앞에서 본 것처럼 REQUIRED로 참여한 안쪽 메서드에서 빠져나간 예외도 같은 규칙으로 롤백 표시 여부를 정한다. 체크 예외가 안쪽에서 나오면 표시가 붙지 않는다.

## readOnly가 실제로 하는 일

`@Transactional(readOnly = true)`는 "읽기만 할 테니 최적화해 달라"는 힌트다. 무엇이 최적화되는지는 트랜잭션 매니저와 드라이버에 따라 다르다. JPA와 Hibernate 조합에서 확인한 것을 먼저 본다. 읽기 전용 트랜잭션 안에서 엔티티 필드를 바꿨다.

```java
@Transactional(readOnly = true)
public void renameReadOnly(Long id) {
  Order o = orders.findById(id).orElseThrow();
  o.status = "CHANGED_IN_READONLY";   // 바꿨지만 save()는 부르지 않는다
}
```

```text
Hibernate: select o1_0.id,o1_0.status from orders o1_0 where o1_0.id=?
  after readOnly: PLACED
Hibernate: select o1_0.id,o1_0.status from orders o1_0 where o1_0.id=?
Hibernate: update orders set status=? where id=?
  after normal: CHANGED
```

읽기 전용에서는 UPDATE가 나가지 않았다. 같은 코드를 일반 트랜잭션으로 돌리면 `save()` 없이도 UPDATE가 나간다. 이 "부르지 않았는데 나가는 UPDATE"는 영속성 컨텍스트의 더티 체킹 때문이고, [JPA 영속성 컨텍스트](/posts/jpa-persistence-context)에서 자세히 본다. readOnly일 때 스프링은 Hibernate 세션의 flush 모드를 MANUAL로 바꾸고 세션을 읽기 전용으로 둔다. 바뀐 걸 비교할 스냅숏을 덜 만들어 메모리와 시간도 아낀다.

드라이버 쪽에서는 JDBC 커넥션에 `setReadOnly(true)`가 걸린다. PostgreSQL 드라이버는 이걸 읽기 전용 트랜잭션으로 시작하고, 그 안에서 쓰기를 하면 DB가 `cannot execute UPDATE in a read-only transaction`으로 거절한다. MySQL 8도 읽기 전용 트랜잭션으로 시작한다. 그리고 읽기 복제본으로 보내는 라우팅 데이터소스가 이 표시를 보고 커넥션을 고르는 구성이 흔하다. 다만 그건 앱이 직접 그렇게 구성했을 때 이야기다. readOnly 자체가 쿼리를 복제본으로 보내 주지는 않는다.

흔한 실수는 둘이다. 클래스에 `@Transactional(readOnly = true)`를 붙이고 쓰기 메서드에 `@Transactional`을 다시 붙이는 걸 잊는 것. 이때 저장이 조용히 무시된다(위 실험처럼 에러도 없다). 그리고 REQUIRED로 참여하는 안쪽 메서드의 `readOnly`는 무시된다는 것. 트랜잭션 속성은 물리 트랜잭션을 여는 쪽이 정한다.

## 격리 수준과 타임아웃은 시작할 때 정해진다

`isolation`과 `timeout`도 같은 원리를 따른다. 트랜잭션을 새로 여는 메서드의 값만 적용된다.

```java
@Transactional(isolation = Isolation.REPEATABLE_READ, timeout = 3)
public Report monthlyReport() { ... }
```

격리 수준을 지정하면 트랜잭션 매니저가 커넥션의 격리 수준을 바꿔서 시작하고, 끝나면 원래대로 돌려놓는다. 기본값 `ISOLATION_DEFAULT`는 DB 기본을 따른다. PostgreSQL 16은 READ COMMITTED, MySQL 8 InnoDB는 REPEATABLE READ다. 같은 코드가 DB를 바꾸면 다르게 동작하는 이유가 이것이다. 격리 수준마다 무엇이 보이고 안 보이는지는 [트랜잭션과 격리 수준](/posts/db-transaction-isolation)에서 실험했다.

`timeout`은 초 단위다. 트랜잭션이 시작된 뒤 남은 시간이 그 안에서 실행하는 쿼리의 타임아웃으로 전해지고, 시간이 다 지난 뒤에 쿼리를 날리면 그 쿼리가 실패한다. 메서드를 중간에 끊는 타이머는 아니다. 트랜잭션 안에서 외부 HTTP 호출로 기다리는 동안에는 아무도 끊어 주지 않는다. 다음 절이 그 이야기다.

## 트랜잭션 안에서 외부 API를 부르면

주문을 저장하고 같은 트랜잭션 안에서 결제사 API를 부르는 코드는 흔하다. 결제사가 1초씩 걸린다고 치고, 커넥션 풀을 2개로 줄여 세 요청을 동시에 보냈다.

```java
@Transactional
public void placeSlowCall(int n) throws InterruptedException {
  orders.save(new Order("P" + n));
  orders.flush();
  Thread.sleep(1000);   // 외부 결제 API를 기다린다고 친다
}
```

```properties
spring.datasource.hikari.maximum-pool-size=2
spring.datasource.hikari.connection-timeout=500
```

```text
WARN ... HikariPool-1 - Connection is not available, request timed out after 502ms (total=2, active=2, idle=0, waiting=0)
  req3 532ms CannotCreateTransactionException: Could not open JPA EntityManager for transaction
  req1 ok 1051ms
  req2 ok 1049ms
```

세 번째 요청은 DB에 쿼리 하나 못 날리고 0.5초 만에 실패했다. 앞의 두 요청이 결제사를 기다리는 1초 동안 커넥션을 쥐고 있었기 때문이다. DB는 한가했다. `active=2, idle=0`이 그 장면이다. 운영에서는 기본값(풀 10개, 대기 30초)이라 바로 실패하지 않고, 응답 시간이 30초까지 늘어지다가 이 메시지로 끝난다. 결제사가 느려졌는데 DB 커넥션 고갈 알람이 울리는 이유다. 풀이 고갈될 때 보는 지표는 [커넥션 풀](/posts/connection-pool)에 정리했다.

외부 호출은 트랜잭션 밖으로 꺼낸다.

1. 트랜잭션 1: 주문을 `PENDING`으로 저장하고 커밋한다.
2. 트랜잭션 밖: 결제사 API를 부른다. 타임아웃을 건다.
3. 트랜잭션 2: 결과에 따라 `PAID`나 `FAILED`로 바꾼다.

이러면 2번에서 앱이 죽었을 때 `PENDING` 주문이 남는다. 그래서 오래된 `PENDING`을 찾아 결제사에 상태를 묻는 정리 작업이 함께 필요하다. 반대로 DB를 먼저 커밋하고 메시지를 보내야 하는 경우라면 [트랜잭셔널 아웃박스](/posts/transactional-outbox)가 이 틈을 메우는 표준 방법이다. 이 구조를 만들 때 같은 클래스 안에서 두 트랜잭션 메서드를 `this`로 부르면 프록시를 지나지 않는다는 점도 잊지 않는다. 트랜잭션 경계가 필요한 메서드는 다른 빈에 두거나 `TransactionTemplate`으로 코드 안에서 경계를 긋는다.

```java
// 프록시 없이 코드로 경계를 긋는다
Long id = tx.execute(status -> orders.save(new Order("PENDING")).id);
PaymentResult r = paymentClient.charge(id);   // 트랜잭션 밖
tx.executeWithoutResult(status -> orders.markPaid(id, r));
```

## 커밋된 뒤에 할 일: @TransactionalEventListener

주문이 저장되면 메일을 보내고 싶다. 저장 메서드 안에서 메일을 보내면, 메일은 나갔는데 트랜잭션이 롤백되는 일이 생긴다. `@TransactionalEventListener`는 이벤트를 받아 두었다가 트랜잭션이 커밋된 뒤에 처리한다(기본 phase가 `AFTER_COMMIT`).

```java
@Transactional
public Long placeWithEvent(boolean fail) {
  Order o = orders.save(new Order("PLACED"));
  events.publishEvent(new OrderPlaced(o.id));
  if (fail) throw new IllegalStateException("fail after publish");
  return o.id;
}

@Component
class OrderEvents {
  @TransactionalEventListener
  public void afterCommit(OrderPlaced e) {
    audit.save(new AuditLog("mail sent for " + e.id()));   // 메일 발송 기록을 남긴다
  }
}
```

성공 한 번, 실패 한 번을 돌렸다.

```text
  event published
  [listener] AFTER_COMMIT order=7 txActive=true
  -> orders=1 audit=0
  event published
  fail after publish
  -> orders=1 audit=0
```

실패한 쪽에서는 리스너가 아예 불리지 않았다. 롤백됐으니 커밋 후 이벤트도 없다. 이게 이 리스너를 쓰는 이유다.

그런데 성공한 쪽에서도 `audit=0`이다. 리스너는 불렸는데 저장이 사라졌다. `txActive=true`가 단서다. 커밋은 끝났지만 트랜잭션 자원은 아직 스레드에 묶여 있는 정리 단계라서, 리스너 안의 `audit.save()`가 REQUIRED로 이 "끝난 트랜잭션"에 참여했다. 이미 커밋을 마친 트랜잭션이니 다시 커밋되지 않는다. 스프링 문서도 이 단계에서는 "이미 커밋된 트랜잭션에 참여할 뿐 커밋되지 않는다"고 경고한다.

리스너에서 DB에 쓰려면 새 트랜잭션을 연다.

```java
@TransactionalEventListener
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void afterCommitNewTx(OrderPlaced e) {
  audit.save(new AuditLog("fixed mail for " + e.id()));
}
```

```text
  event published
  [fixed listener] REQUIRES_NEW tx=demo.tx.FixedEvents.afterCommitNewTx
  -> orders=1 audit=1
```

`@TransactionalEventListener`에 `@Transactional`을 함께 붙일 때 Spring 6.1부터는 REQUIRES_NEW나 NOT_SUPPORTED만 허용한다. 기본 REQUIRED로 붙여 봤더니 시작할 때 이렇게 멈췄다. 위의 함정을 막으려는 장치다.

```text
Caused by: java.lang.IllegalStateException: @TransactionalEventListener method must not be annotated with @Transactional unless when declared as REQUIRES_NEW or NOT_SUPPORTED: public void demo.txl.Lis.on(demo.txl.Ev)
```

이 방식에도 빈틈은 남는다. 커밋 직후 앱이 죽으면 리스너는 돌지 않고 메일은 안 나간다. 이벤트가 메모리에만 있기 때문이다. 메일 한 통쯤 빠져도 되면 이걸로 충분하고, 빠지면 안 되는 메시지라면 같은 트랜잭션에서 아웃박스 테이블에 적어 두는 방식으로 간다.

## 전파 규칙을 직접 계산해 본다

지금까지의 규칙을 함수로 옮겨 본다. 바깥은 REQUIRED 트랜잭션이고, 안쪽 호출의 예외는 모두 바깥에서 잡는다고 하자. `propagate(calls, outerFails)`는 안쪽 호출 목록과, 바깥이 마지막에 런타임 예외를 던지는지를 받는다. 각 호출은 `propagation`("REQUIRED" 또는 "REQUIRES_NEW")과 `throws`("none", "runtime", "checked")를 가진다. 돌려줄 값은 배열이다. 첫 칸은 바깥의 결과("commit", "rollback", "UnexpectedRollbackException"), 그다음 칸들은 각 호출이 쓴 데이터의 운명("commit" 또는 "rollback")이다.

  let rollbackOnly = false;
  const own = [];
  for (const c of calls) {

## 트랜잭션이 이상할 때 보는 순서

1. `JpaTransactionManager`(또는 `JdbcTransactionManager`) 로그를 DEBUG로 켠다. `Creating new transaction`이 아예 없으면 프록시를 안 지난 것이다. 같은 클래스 안의 호출, `private` 메서드, `new`로 만든 객체를 의심한다.
2. `Participating in existing transaction`과 `Suspending current transaction`으로 전파가 의도대로인지 본다.
3. `UnexpectedRollbackException`이면 `marking existing transaction as rollback-only` 줄 바로 앞의 예외를 찾는다. 그 예외를 낸 안쪽 메서드가 범인이다.
4. 예외가 났는데 데이터가 남았으면 그 예외가 체크 예외인지, 다른 스레드에서 저장했는지 본다.
5. 커넥션 고갈(`Connection is not available`)이면 트랜잭션 안에서 기다리는 외부 호출과 REQUIRES_NEW를 찾는다. HikariCP의 `active`, `waiting` 숫자가 단서다.

## 경계를 긋는 쪽이 결정한다

`@Transactional`은 스레드에 커넥션 하나를 묶어 두고, 메서드가 끝날 때 커밋할지 롤백할지 정하는 장치다. 트랜잭션을 새로 여는 메서드가 격리 수준, 타임아웃, readOnly를 정하고, 참여한 메서드는 롤백 표시만 남길 수 있다. 런타임 예외만 롤백하는 기본 규칙, JPA에서 NESTED가 안 되는 이유, 커밋 뒤 리스너의 함정도 모두 이 구조에서 나온다. 트랜잭션 안에서 엔티티가 어떻게 추적되고 언제 SQL이 나가는지는 [JPA 영속성 컨텍스트](/posts/jpa-persistence-context)에서 이어 간다.

## 면접에서 나올 만한 질문

### @Transactional은 어떻게 동작하나요?

스프링이 빈을 프록시로 감싸고, 프록시가 메서드 호출 전에 트랜잭션 매니저로 트랜잭션을 시작한다. 매니저는 커넥션을 꺼내 자동 커밋을 끄고 현재 스레드에 묶어서, 같은 스레드의 리포지토리들이 그 커넥션을 쓰게 한다. 메서드가 정상으로 끝나면 커밋하고, 롤백 규칙에 맞는 예외가 빠져나가면 롤백한다. 프록시를 지나지 않는 자기 호출에서는 동작하지 않는다.

### UnexpectedRollbackException은 왜 나나요?

REQUIRED로 참여한 안쪽 메서드가 런타임 예외로 끝나면 물리 트랜잭션에 롤백 표시가 붙는다. 바깥에서 그 예외를 잡고 정상 종료해 커밋을 요청해도, 표시 때문에 실제로는 롤백되고 이 예외가 난다. 안쪽이 예외를 던지지 않게 결과값으로 바꾸거나, 독립된 일이면 REQUIRES_NEW로 떼어 내거나, 안쪽에서 트랜잭션을 빼서 고친다.

### REQUIRED, REQUIRES_NEW, NESTED의 차이는 무엇인가요?

REQUIRED는 바깥 트랜잭션에 참여해 운명을 같이하고, 없으면 새로 연다. REQUIRES_NEW는 바깥을 잠시 떼어 두고 새 커넥션으로 독립 트랜잭션을 열어, 안쪽 커밋이 바깥 롤백과 무관하게 남는다. NESTED는 같은 커넥션에 세이브포인트를 만들어 안쪽만 부분 롤백하지만, 바깥이 롤백되면 함께 사라진다. JPA와 Hibernate 조합의 `JpaTransactionManager`에서는 NESTED가 지원되지 않는다.

### REQUIRES_NEW를 쓸 때 주의할 점은 무엇인가요?

한 요청이 커넥션을 동시에 두 개 쥔다. 풀 크기만큼 동시 요청이 안쪽에 들어가면 서로 두 번째 커넥션을 기다리며 멈출 수 있다. 안쪽은 바깥이 커밋하지 않은 데이터를 볼 수 없고, 바깥이 잠근 행을 건드리면 기다리다 멈춘다. 안쪽 커밋 뒤 바깥이 롤백되면 데이터가 어긋나니 감사 로그처럼 어긋나도 되는 일에만 쓴다.

### 체크 예외가 나면 롤백되나요?

기본으로는 안 된다. 스프링은 `RuntimeException`과 `Error`에서만 롤백하고 체크 예외는 커밋한다. 체크 예외에서도 롤백하려면 `rollbackFor = Exception.class`를 주거나, Spring 6.2부터 생긴 `@EnableTransactionManagement(rollbackOn = RollbackOn.ALL_EXCEPTIONS)` 전역 설정을 쓴다. 업무 예외를 런타임 예외로 만드는 팀 규칙도 흔하다.

### readOnly = true는 무엇을 하나요?

JPA와 Hibernate에서는 flush 모드를 MANUAL로 바꾸고 세션을 읽기 전용으로 둬서 더티 체킹으로 인한 UPDATE가 나가지 않고 스냅숏 비용도 줄어든다. JDBC 커넥션에도 읽기 전용이 걸려 PostgreSQL 같은 DB는 그 트랜잭션의 쓰기를 거절한다. 복제본 라우팅은 앱이 이 표시를 보고 데이터소스를 고르도록 구성했을 때만 일어난다. REQUIRED로 참여한 메서드의 readOnly는 무시된다.

### 트랜잭션 안에서 외부 API를 부르면 왜 문제가 되나요?

트랜잭션은 끝날 때까지 커넥션을 쥐고 있어서, 외부 API를 기다리는 동안 그 커넥션을 다른 요청이 못 쓴다. 외부가 느려지면 DB는 한가한데 커넥션 풀이 고갈되고, 무관한 요청까지 `Connection is not available`로 실패한다. 외부 호출을 트랜잭션 밖으로 빼고 앞뒤를 짧은 트랜잭션 둘로 나누며, 그 사이 실패를 정리하는 작업이나 아웃박스를 둔다.

### @TransactionalEventListener에서 DB에 저장했는데 반영이 안 됩니다. 왜인가요?

기본 phase인 AFTER_COMMIT에서는 커밋이 끝난 트랜잭션 자원이 아직 스레드에 묶여 있어서, REQUIRED 저장이 이 끝난 트랜잭션에 참여하고 다시 커밋되지 않는다. 리스너에 `@Transactional(propagation = REQUIRES_NEW)`를 붙여 새 트랜잭션을 연다. 커밋 직후 앱이 죽으면 리스너가 돌지 않으니, 빠지면 안 되는 일은 아웃박스로 처리한다.
