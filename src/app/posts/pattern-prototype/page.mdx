화면 편집기에 "선택한 도형 복제(Ctrl+D)" 기능을 넣는다. 처음 짠 코드는 이랬다.

```ts
function duplicate(shape: Shape): Shape {
  switch (shape.kind) {
    case "rect":
      return new Rect(shape.x + 16, shape.y + 16, shape.w, shape.h, shape.style);
    case "text":
      return new Text(shape.x + 16, shape.y + 16, shape.content, shape.font);
    // 도형이 하나 늘 때마다 여기에 case가 하나 는다
  }
}
```

두 가지가 마음에 걸린다. 도형 종류가 늘면 복제 함수도 함께 고쳐야 한다. 그리고 `shape.style`을 그대로 넘겼으니 사본의 그림자를 끄면 원본의 그림자도 꺼진다. 복제는 도형마다 사정이 다르고, 그 사정을 가장 잘 아는 건 도형 자신이다. 그래서 복제를 객체에게 맡기는 것이 프로토타입 패턴이다. 생성 패턴 전체의 지도는 [디자인 패턴 개요](/posts/design-patterns-overview)에 있다.

## 복사할 줄 아는 건 객체 자신이다

GoF(1994)는 이 패턴을 "원형이 되는 인스턴스를 정해 두고, 그것을 복사해 새 객체를 만든다"고 정의한다. 등장인물은 단순하다. `clone()`을 약속하는 Prototype 인터페이스, 그걸 구현하는 구체 클래스들, 그리고 구체 클래스를 모른 채 `clone()`만 부르는 Client다.

```ts
interface Style { fill: string; stroke: string; shadow: { blur: number } }

export interface Shape {
  clone(): Shape;
  moveBy(dx: number, dy: number): void;
  describe(): string;
}

let nextId = 1;

export class Rect implements Shape {
  readonly #id = nextId++;
  constructor(public x: number, public y: number, public w: number, public h: number, public style: Style) {}

  clone(): Rect {
    // 새 id를 받고, 중첩된 style은 따로 복사한다
    return new Rect(this.x, this.y, this.w, this.h, structuredClone(this.style));
  }
  moveBy(dx: number, dy: number) { this.x += dx; this.y += dy; }
  describe() { return `Rect#${this.#id} (${this.x},${this.y}) ${this.w}x${this.h} ${this.style.fill}`; }
}

// 편집기는 구체 클래스를 모른다. 선택된 것이 무엇이든 clone()만 부른다
export function duplicate(selection: Shape[]): Shape[] {
  return selection.map((s) => {
    const copy = s.clone();
    copy.moveBy(16, 16);
    return copy;
  });
}
```

`Text`도 같은 식으로 `font`를 복사하는 `clone()`을 가진다. `switch`가 사라졌고, 새 도형은 자기 `clone()`만 구현하면 복제 기능에 그대로 들어온다. 아래 그림에서 다음을 누르면 사용자가 카드와 제목을 함께 골라 복제하는 흐름이 나온다.

## 자바스크립트의 프로토타입과는 다른 이야기

이름 때문에 가장 많이 헷갈리는 부분이다. 자바스크립트의 프로토타입 체인은 복사가 아니라 연결이다. `Object.create(base)`로 만든 객체는 `base`의 값을 갖고 있지 않다. 찾는 속성이 자기에게 없으면 `base`에게 물어볼 뿐이다.

```js
const baseButton = { size: "md", variant: "primary", label: "확인" };
const linked = Object.create(baseButton); // 복사가 아니라 연결
const copied = { ...baseButton };          // 복사
linked.label = "저장";
baseButton.variant = "danger";
console.log("linked :", linked.variant, linked.label, "| own keys:", Object.keys(linked));
console.log("copied :", copied.variant, copied.label);
```

```text
linked : danger 저장 | own keys: [ 'label' ]
copied : primary 확인
```

원본의 `variant`를 바꾸자 연결된 객체도 `danger`가 됐다. 복사본은 영향을 받지 않았다. 연결된 객체가 직접 가진 건 덮어쓴 `label` 하나뿐이다. 자바스크립트의 상속은 이렇게 위임으로 동작하고, 프로토타입 패턴은 독립된 사본을 만든다. 둘 다 "기존 객체에서 새 객체를 만든다"는 발상에서 나왔지만, 원본이 바뀔 때 결과가 정반대다.

Spring의 `@Scope("prototype")`도 이름만 같다. 빈을 요청할 때마다 새 인스턴스를 생성자로 만들어 주는 설정이고, 원본을 복사하지 않는다.

## 얕은 복사가 기본값을 오염시킨다

복제에서 가장 흔한 사고는 깊이다. 아래는 API 클라이언트의 기본 설정을 펼쳐서 사용자별 설정을 만드는 코드다.

```js
const defaults = { timeoutMs: 3000, headers: { accept: "application/json" }, retry: { times: 2, on: [502, 503] } };
const a = { ...defaults };
a.headers.authorization = "Bearer user-a";
a.retry.on.push(500);
console.log("defaults after a:", JSON.stringify(defaults));
```

```text
defaults after a: {"timeoutMs":3000,"headers":{"accept":"application/json","authorization":"Bearer user-a"},"retry":{"times":2,"on":[502,503,500]}}
```

펼침 연산자와 `Object.assign`은 한 층만 복사한다. `headers`와 `retry`는 객체를 가리키는 참조라서 참조만 복사됐다. 그다음에 만드는 사용자 B의 설정에도 A의 토큰이 들어 있다. 아래 그림의 칸은 설정의 각 필드이고, 오른쪽은 원본과 사본이 그 필드를 따로 가졌는지 같이 쓰는지다.

얕은 복사가 늘 틀린 건 아니다. 안쪽 객체를 절대 고치지 않는다면 같이 쓰는 편이 메모리와 시간을 아낀다. Redux와 Immer가 그렇게 한다. 바뀐 경로의 객체만 새로 만들고 나머지는 이전 상태와 같이 쓴다. 이 방식이 안전하려면 "안쪽은 아무도 고치지 않는다"는 약속이 지켜져야 하고, 위 코드는 그 약속을 깼다.

## 깊은 복사 도구마다 잃어버리는 것

깊게 복사하는 손쉬운 방법은 두 가지다. 오래된 `JSON.parse(JSON.stringify(x))`와, 브라우저와 Node.js 17부터 전역으로 쓸 수 있는 `structuredClone(x)`다. 같은 객체를 둘에 넣어 봤다.

```js
const original = {
  createdAt: new Date("2026-10-21T09:00:00Z"),
  tags: new Set(["sale"]),
  price: new Map([["KRW", 39000]]),
  note: undefined,
  big: 10n,
};
```

```text
JSON: Do not know how to serialize a BigInt
JSON w/o bigint: { createdAt: '2026-10-21T09:00:00.000Z', tags: {}, price: {} }
structuredClone: {
  createdAt: 2026-10-21T09:00:00.000Z,
  tags: Set(1) { 'sale' },
  price: Map(1) { 'KRW' => 39000 },
  note: undefined,
  big: 10n
} true
```

JSON 왕복은 BigInt에서 바로 멈추고, BigInt를 빼면 조용히 망가진다. `Date`는 문자열이 되고, `Set`과 `Map`은 빈 객체가 되고, `undefined`인 필드는 사라진다. 에러가 나지 않으니 한참 뒤에 `createdAt.getTime is not a function`으로 터진다. `structuredClone`은 이 타입들을 모두 살리고 순환 참조도 따라간다. 대신 함수는 복사하지 못한다.

```text
cycle kept: true different from original: true
DataCloneError: onClick() {} could not be cloned.
```

정리하면 이렇다. 실제로 고를 때 기준이 되는 차이라 표로 둔다.

| 값 | 펼침 연산자 | JSON 왕복 | structuredClone |
| --- | --- | --- | --- |
| 중첩 객체 | 참조 공유 | 복사 | 복사 |
| Date, Map, Set | 참조 공유 | 문자열, 빈 객체 | 복사 |
| undefined 필드 | 유지 | 사라짐 | 유지 |
| 순환 참조 | 참조 공유 | TypeError | 복사 |
| 함수 | 참조 공유 | 사라짐 | DataCloneError |
| 클래스 인스턴스 | 프로토타입 잃음 | 일반 객체 | 일반 객체 |

마지막 줄이 프로토타입 패턴이 따로 필요한 이유다.

## 클래스 인스턴스는 스스로 복제해야 한다

앞의 `Rect`를 클래스를 모르는 방법으로 복사해 봤다.

```ts
const sc = structuredClone(card);
console.log("structuredClone instanceof Rect:", sc instanceof Rect, "| keys:", Object.keys(sc).join(","));
sc.describe();

const viaProto = Object.assign(Object.create(Object.getPrototypeOf(card)), card);
viaProto.describe();
```

```text
structuredClone instanceof Rect: false | keys: x,y,w,h,style
TypeError: sc.describe is not a function
Object.create copy instanceof Rect: true
TypeError: Cannot read private member #id from an object whose class did not declare it
```

`structuredClone`은 자기 속성만 복사한 일반 객체를 준다. 메서드와 `#id`가 사라졌다. 두 번째 방법은 인터넷에서 "클래스 인스턴스 복제"로 자주 보이는 한 줄인데, 프로토타입을 이어 붙여 메서드는 살렸지만 `#` 비공개 필드는 옮기지 못했다. 이 한 줄을 조각내 보면 어디서 빠지는지 보인다.

## 원본을 등록해 두고 꺼내 쓰기

디자인 툴의 컴포넌트 패널처럼 "자주 쓰는 원형"을 이름으로 꺼내 쓰는 경우가 많다. GoF는 이것을 프로토타입 관리자(registry)로 설명한다. 원형을 한 번 만들어 등록해 두고, 요청이 오면 복제본을 내준다.

```ts
export class ShapeRegistry {
  private readonly prototypes = new Map<string, Shape>();

  register(name: string, prototype: Shape) {
    this.prototypes.set(name, prototype);
  }

  create(name: string): Shape {
    const prototype = this.prototypes.get(name);
    if (!prototype) throw new Error(`unknown prototype: ${name}`);
    return prototype.clone(); // 원형 자체는 절대 내주지 않는다
  }
}
```

`create()`가 원형을 그대로 돌려주면 받은 쪽이 원형을 고치고, 다음 사람은 고쳐진 원형의 복제본을 받는다. 앞의 기본 설정 오염과 같은 사고다.

## 복제가 정말 빠른가

프로토타입 패턴은 보통 "생성 비용이 클 때 쓴다"고 설명된다. 틀린 말은 아니지만 어떤 비용이냐에 따라 결과가 달라진다. 실제로 재 봤다. Node.js 22에서 `--expose-gc`로 측정 전후에 GC를 돌리고 `process.memoryUsage().heapUsed` 차이를 쟀다. 먼저 블록 2,000개짜리 문서 템플릿에서 문서 1,000개를 만드는 경우다.

```js
measure("parse template every time", () => JSON.parse(templateText));
measure("structuredClone(proto)", () => structuredClone(prototype));
measure("shallow clone (share)", () => ({ ...prototype }));
```

```bash
# GC를 직접 부를 수 있게 켜고 실행한다
node --expose-gc bench.mjs
```

```text
parse template every time   1437 ms   335.8 MB 1000
structuredClone(proto)      3500 ms   381.5 MB 1000
shallow clone (share)          0 ms     0.1 MB 1000
```

같은 머신에서 두 번 돌렸고 시간은 매번 달랐지만(첫 실행은 3683ms, 4519ms) 순서는 같았다. 원형을 `structuredClone`하는 쪽이 JSON 문자열을 다시 파싱하는 것보다 오히려 느렸다. 객체 그래프 전체를 새로 만드는 일이라면 복제나 재생성이나 비슷한 양을 할당한다. 큰 차이를 만든 건 같이 쓰기였다. 블록을 고치지 않는다면 1,000개 문서가 블록 배열 하나를 같이 써서 메모리가 0.1MB만 늘었다.

이번에는 생성 비용이 할당이 아니라 바깥 일인 경우다. 금칙어 규칙 3,000줄을 파일에서 읽어 정규식으로 컴파일하는 필터를 채널마다 하나씩 만든다.

```js
class ProfanityFilter {
  constructor(compiled, disabled = new Set()) {
    this.compiled = compiled; // 무겁고 바뀌지 않는 부분
    this.disabled = disabled; // 가볍고 채널마다 바뀌는 부분
  }
  static load(path) {
    const lines = readFileSync(path, "utf8").split("\n");
    return new ProfanityFilter(lines.map((l) => new RegExp(l, "iu")));
  }
  clone() {
    return new ProfanityFilter(this.compiled, new Set(this.disabled));
  }
}
```

```text
load() x200 : 195.5 ms
clone() x200: 0.1 ms
```

파일 읽기와 정규식 컴파일은 원형을 만들 때 한 번만 하고, 복제는 바뀌는 부분인 `disabled`만 새로 만든다. 프로토타입이 값을 하는 건 이런 경우다. 비싼 준비를 한 번 끝낸 원형에서, 바뀌지 않는 무거운 부분은 같이 쓰고 바뀌는 가벼운 부분만 복사한다. 어디까지 같이 쓸지를 `clone()`이 정하니, 이 결정도 클래스 안에 있어야 한다.

## 매일 쓰는 복제

DOM의 `node.cloneNode(true)`가 가장 가까운 예다. 목록 줄 하나를 `<template>`에 만들어 두고 `template.content.cloneNode(true)`로 복제해 값만 채운다. 이때 `addEventListener`로 붙인 리스너는 복제되지 않는다. 복제한 뒤에 다시 붙이거나 부모에 위임한다.

fetch의 `Response.clone()`도 같은 이름이다. 본문 스트림은 한 번만 읽을 수 있어서, 서비스 워커가 응답을 캐시에 넣으면서 페이지에도 돌려줄 때 복제한다. 이 부분은 [fetch](/posts/browser-fetch) 글에서 자세히 다뤘다.

쿠버네티스의 Deployment도 같은 발상이다. `spec.template`에 Pod의 원형을 적어 두면 ReplicaSet이 그 원형으로 Pod를 찍어 내고, 각 Pod는 이름과 IP를 새로 받는다. 앞의 `Rect`가 복제하면서 새 `#id`를 받은 것과 같다. Go에는 `clone()` 관례가 없고, 구조체를 대입하면 필드가 얕게 복사된다. 슬라이스와 맵은 안쪽 배열을 같이 쓰니 위의 기본 설정 오염과 같은 사고가 난다. Go 1.21부터 `slices.Clone`, `maps.Clone`이 표준 라이브러리에 들어왔다.

## 직접 만드는 깊은 복사

## 복제가 맞지 않는 객체

정체성이 중요한 객체는 복제하면 안 된다. DB 커넥션, 소켓, 파일 핸들, 타이머처럼 바깥 자원을 쥔 객체를 복사하면 두 객체가 같은 자원을 닫으려 한다. 이런 객체는 `clone()`을 만들지 않거나, 새 자원을 여는 생성으로 처리한다. 이벤트 구독도 비슷하다. 원본이 어딘가에 리스너로 등록돼 있었다면 사본도 등록해야 하는지, 하지 말아야 하는지를 `clone()`이 정해야 한다.

비슷해 보이는 패턴과는 이렇게 나뉜다. [빌더](/posts/pattern-builder)는 빈 상태에서 단계를 밟아 조립하고, 프로토타입은 이미 다 만들어진 것을 복사해 조금 고친다. [팩토리 메서드](/posts/pattern-factory-method)는 어떤 클래스를 만들지 하위 클래스가 정하지만, 프로토타입은 클래스 계층 없이 "어떤 원형을 넣었느냐"로 정한다. [플라이웨이트](/posts/pattern-flyweight)는 반대 방향이다. 복사하지 않고 한 객체를 여러 곳이 같이 쓴다. 되돌리기를 위해 상태를 복사해 두는 건 [메멘토](/posts/pattern-memento)다. 메멘토도 내부적으로 복제를 쓰지만, 목적이 새 객체가 아니라 과거로 돌아가는 데 있다.

처음의 `switch`로 돌아가면, 복제를 객체에게 맡기자 분기가 사라지고 깊이 문제도 각 클래스가 책임지게 됐다. 남은 판단은 하나다. 무엇을 같이 쓰고 무엇을 따로 가질지. 이 판단이 틀리면 얕은 복사 사고가 나고, 지나치게 깊게 복사하면 앞의 측정처럼 시간과 메모리를 다 쓴다.

## 면접에서 나올 만한 질문

### 프로토타입 패턴은 무엇이고 언제 쓰나요?

원형 객체를 정해 두고 그것을 복제해 새 객체를 만드는 패턴이다. 호출하는 쪽이 구체 클래스를 몰라도 clone()만으로 같은 종류의 객체를 얻을 수 있다. 파일 읽기나 컴파일처럼 준비가 비싼 객체를 여러 개 만들거나, 런타임에 등록된 원형에 따라 만들 객체를 바꾸고 싶을 때 쓴다.

### 자바스크립트의 프로토타입 상속과 같은 건가요?

다르다. 프로토타입 체인은 복사가 아니라 위임이라서, Object.create로 만든 객체는 없는 속성을 원본에 물어본다. 그래서 원본이 바뀌면 연결된 객체도 바뀌어 보인다. 프로토타입 패턴은 독립된 사본을 만들어서 원본이 바뀌어도 사본은 그대로다.

### 얕은 복사와 깊은 복사의 차이와, 각각의 위험은요?

얕은 복사는 첫 층만 새로 만들고 안쪽 객체는 참조를 같이 쓴다. 사본의 안쪽을 고치면 원본도 바뀌는 사고가 난다. 깊은 복사는 모든 층을 새로 만들어 안전하지만 큰 그래프에서는 시간과 메모리가 많이 들고, 바깥 자원을 쥔 객체까지 복사하는 문제가 생길 수 있다.

### structuredClone과 JSON.parse(JSON.stringify())는 어떻게 다른가요?

JSON 왕복은 Date를 문자열로, Map과 Set을 빈 객체로 바꾸고 undefined 필드를 지우며, BigInt와 순환 참조에서는 에러가 난다. structuredClone은 이 타입들과 순환 참조를 그대로 복사한다. 둘 다 함수와 클래스 정보는 옮기지 못해서, 클래스 인스턴스는 일반 객체가 된다.

### 클래스 인스턴스는 어떻게 복제하나요?

클래스에 clone()을 두고 생성자를 거쳐 사본을 만든다. 비공개 필드, 새로 받아야 할 id, 깊게 복사할 필드와 같이 써도 되는 필드는 클래스만 안다. Object.create와 Object.assign을 섞는 방법은 메서드는 살리지만 #비공개 필드를 옮기지 못해 TypeError가 난다.

### 복제가 항상 새로 만드는 것보다 빠른가요?

아니다. 객체 그래프 전체를 새로 할당하는 일이라면 structuredClone이 JSON 재파싱보다 느린 경우도 있었다. 복제가 값을 하는 건 준비 비용이 할당이 아니라 파일 읽기, 정규식 컴파일 같은 바깥 일일 때이고, 바뀌지 않는 무거운 부분을 같이 쓰고 바뀌는 부분만 복사할 때 차이가 크다.

### 프로토타입과 플라이웨이트는 어떻게 다른가요?

방향이 반대다. 프로토타입은 원형을 복사해 각자 독립된 객체를 갖게 하고, 플라이웨이트는 복사하지 않고 바뀌지 않는 상태를 여러 곳이 한 객체로 같이 쓴다. 실무의 clone()은 둘을 섞는 경우가 많아서, 무거운 불변 부분은 같이 쓰고 바뀌는 부분만 복사한다.
