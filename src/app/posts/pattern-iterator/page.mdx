주문 API는 커서 기반 페이지네이션을 쓴다. 한 번에 100건과 `nextCursor`를 주고, 마지막 페이지면 `nextCursor`가 `null`이다. 그런데 이 API를 쓰는 곳이 주문 내보내기, 정산 배치, 알림 대상 추리기 세 군데다. 세 곳 모두 아래 반복문을 복사해 가지고 있다.

```ts
interface Order { id: number; status: "paid" | "cancelled" }
interface Page { items: Order[]; nextCursor: string | null }
declare function fetchOrders(cursor: string | null): Promise<Page>;
declare function writeCsvRow(order: Order): void;

async function exportOrders() {
  let cursor: string | null = null;
  do {
    const page: Page = await fetchOrders(cursor);
    for (const order of page.items) {
      if (order.status === "paid") writeCsvRow(order);
    }
    cursor = page.nextCursor;
  } while (cursor);
}
```

하고 싶은 일은 "결제된 주문마다 한 줄 쓰기"인데, 코드의 절반이 페이지를 넘기는 방법이다. API가 커서 대신 `page=2` 방식으로 바뀌면 세 곳을 다 고쳐야 하고, 한 곳은 `cursor = page.nextCursor`를 빠뜨려 첫 페이지만 무한히 도는 버그를 만든다. 쓰는 쪽은 `for (const order of 모든주문)`만 쓰고 싶다. 이 글은 컬렉션의 내부 구조를 숨긴 채 원소를 하나씩 꺼내 주는 이터레이터(Iterator) 패턴이다. 자바스크립트에서는 언어에 들어 있는 패턴이라, 그 규약이 실제로 어떻게 움직이는지를 중심으로 본다.

## 돌 줄 아는 것과 도는 것을 나눈다

이터레이터 패턴에는 두 역할이 있다. 원소를 가진 쪽(Aggregate)과, 그 원소를 하나씩 꺼내는 쪽(Iterator)이다. 둘을 나누는 이유는 "어디까지 꺼냈나"라는 위치를 컬렉션이 아니라 반복자가 들고 있게 하려는 것이다. 그래야 같은 컬렉션을 두 곳에서 동시에 돌아도 서로의 위치가 섞이지 않는다.

자바스크립트는 이 두 역할을 규약으로 정해 두었다. `[Symbol.iterator]()` 메서드가 있으면 반복 가능한 객체(iterable)이고, 그 메서드가 돌려준 객체가 `next()`로 `{ value, done }`을 주면 반복자(iterator)다. 비동기 버전은 `[Symbol.asyncIterator]()`와 `Promise`를 돌려주는 `next()`다. 컬렉션마다 이 메서드가 자기 반복자를 만들어 주는 구조가 [팩토리 메서드](/posts/pattern-factory-method)라는 이야기는 그 글에서 했다.

클래스로 그대로 옮기면 이렇다. 반복자는 받아 둔 주문(buffer)과 다음 커서를 들고 있다가, 버퍼가 비면 다음 페이지를 가져온다.

```ts
interface Order { id: number; status: "paid" | "cancelled" }
interface Page { items: Order[]; nextCursor: string | null }
type FetchPage = (cursor: string | null) => Promise<Page>;

class OrderIterator implements AsyncIterator<Order> {
  private buffer: Order[] = [];
  private cursor: string | null = null;
  private finished = false;
  constructor(private readonly fetchPage: FetchPage) {}

  async next(): Promise<IteratorResult<Order>> {
    while (this.buffer.length === 0) {
      if (this.finished) return { done: true, value: undefined };
      const page = await this.fetchPage(this.cursor); // 버퍼가 비었을 때만 요청한다
      this.buffer = page.items;
      this.cursor = page.nextCursor;
      this.finished = page.nextCursor === null;
    }
    return { done: false, value: this.buffer.shift()! };
  }
}

class OrderCollection implements AsyncIterable<Order> {
  constructor(private readonly fetchPage: FetchPage) {}
  [Symbol.asyncIterator]() {
    return new OrderIterator(this.fetchPage); // 돌 때마다 새 반복자, 새 위치
  }
}
```

한 페이지에 3건, 모두 10건인 가짜 API로 돌리면 반복자 안에서 이런 일이 일어난다. 아래 그림에서 다음을 누르면 위치(▲)가 옮겨 가고 버퍼가 비었다 채워지는 모습이 보인다.

## for await가 실제로 부르는 것

이제 쓰는 쪽은 페이지를 모른다.

```ts
declare const orders: AsyncIterable<{ id: number; status: string }>;

async function firstFivePaid() {
  const ids: number[] = [];
  for await (const order of orders) {
    if (order.status !== "paid") continue;
    ids.push(order.id);
    if (ids.length === 5) break; // 다섯 건이면 그만
  }
  return ids;
}
```

`for await...of`는 문법 설탕이다. 안에서는 반복자 메서드를 차례로 부른다. 특히 중간에 `break`하거나 예외가 나면 반복자의 `return()`을 불러 "이제 그만 꺼낼 테니 정리하라"고 알려 준다. 아래 그림이 그 호출 순서다.

`return()`이 왜 중요한지는 제너레이터로 보면 바로 드러난다. 제너레이터에서 `return()`이 불리면 `try...finally`의 `finally`가 실행된다.

```ts
function* rows() {
  try {
    yield 1;
    yield 2;
    yield 3;
  } finally {
    console.log("finally: 커넥션 반납");
  }
}

for (const r of rows()) {
  console.log("row", r);
  if (r === 2) break;
}
```

```text
row 1
row 2
finally: 커넥션 반납
```

데이터베이스 커서나 파일 핸들처럼 다 돌지 않고 멈춰도 반드시 닫아야 하는 자원은 이렇게 `finally`에 둔다. 손으로 만든 반복자 클래스라면 `return()` 메서드를 직접 구현해야 같은 효과가 난다. 위 `OrderIterator`에는 `return()`이 없어서, 붙잡은 자원이 있다면 `break` 때 정리되지 않는다.

## 제너레이터가 위치를 대신 들고 있다

반복자 클래스의 필드 셋(`buffer`, `cursor`, `finished`)은 "어디까지 했나"를 기억하려고 있다. 제너레이터는 이 기억을 함수의 지역 변수와 실행 위치로 대신한다. `yield`에서 멈췄다가 다음 `next()`에 그 자리에서 이어서 돌기 때문이다. 위의 클래스 두 개가 함수 하나가 된다.

```ts
interface Order { id: number; status: "paid" | "cancelled" }
interface Page { items: Order[]; nextCursor: string | null }
declare function fetchOrders(cursor: string | null): Promise<Page>;

// 페이지를 넘기는 방법은 이 함수만 안다
async function* allOrders(): AsyncGenerator<Order> {
  let cursor: string | null = null;
  do {
    const page: Page = await fetchOrders(cursor);
    yield* page.items; // 배열의 원소를 하나씩 내보낸다
    cursor = page.nextCursor;
  } while (cursor);
}
```

같은 가짜 API로 "결제된 주문 다섯 건"을 찾아 돌려 봤다. 10건 중 #4가 취소 주문이다.

```text
GET /orders?cursor=
GET /orders?cursor=3
[ 1, 2, 3, 5, 6 ] requests: 2
```

요청은 두 번만 나갔다. 끝까지 돌았다면 네 번이었다. 처음의 `do...while`을 복사해 쓰던 코드는 다섯 건을 찾은 뒤 멈추려면 바깥 반복문을 빠져나오는 플래그를 따로 둬야 했다. 아래 그림에서 다음을 누르면 요청이 언제 나가고 언제 멈추는지 보인다.

## 필요한 만큼만 꺼내는 게으른 반복

반복자는 값을 미리 만들어 두지 않는다. 누가 `next()`를 부를 때 하나 만든다. 이 성질 덕분에 끝이 없는 수열도 다룰 수 있고, 앞의 몇 개만 필요하면 나머지 계산을 하지 않는다. ES2025에 들어간 이터레이터 헬퍼(`Iterator.prototype.map`, `filter`, `take`, `toArray` 등)는 이 체인을 배열처럼 쓰게 해 준다. Node.js 22와 크롬 122부터 들어 있고, 타입스크립트는 5.6부터 `lib`에 `esnext`를 넣으면 타입을 준다.

배열 체인은 100만 개를 모두 두 배 한 중간 배열을 만들고, 그것을 다시 걸러 낸 다음에야 앞의 세 개를 잘랐다. 반복자 체인은 일곱 개만 보고 끝났다. 끝이 없는 수열도 같은 방식으로 다룬다.

```ts
function* naturals() {
  let i = 1;
  while (true) yield i++; // 끝나지 않는다. 그래도 필요한 만큼만 돈다
}
naturals().map((x) => x * x).filter((x) => x % 3 === 1).take(4).toArray(); // [ 1, 4, 16, 25 ]
```

## 도는 중에 컬렉션이 바뀌면

반복자는 컬렉션을 복사하지 않고 위치만 들고 있다. 그래서 도는 동안 컬렉션이 바뀌면 이상한 일이 생긴다. 자바스크립트에서 직접 해 봤다.

```js
const arr = [1, 2, 3];
for (const x of arr) {
  if (arr.length < 6) arr.push(x * 10); // 도는 중에 뒤에 붙인다
}
console.log(arr); // [ 1, 2, 3, 10, 20, 30 ]  — 붙인 것까지 돌았다

const ids = [1, 2, 2, 3];
ids.forEach((id, i) => {
  if (id === 2) ids.splice(i, 1); // 2를 모두 지우려 했다
});
console.log(ids); // [ 1, 2, 3 ]  — 하나가 살아남았다
```

배열 반복자는 "다음 인덱스"만 기억하고 매번 길이를 다시 본다. 뒤에 붙인 원소는 다음 차례에 그대로 나온다. 앞에서 지우면 뒤의 원소가 한 칸씩 당겨지는데 인덱스는 그대로 올라가니, 지운 바로 다음 원소를 건너뛴다. 두 번째 예가 "가끔 하나씩 안 지워진다"는 버그 신고의 흔한 원인이다. `filter`로 새 배열을 만들거나 뒤에서부터 돌며 지운다.

`Set`과 `Map`도 비슷하다. 도는 중에 추가한 원소를 그 반복에서 만난다. 지웠다가 다시 넣으면 맨 뒤로 가니, 원소마다 `delete` 후 `add`를 하면 반복이 끝나지 않는다. 직접 돌렸을 때 다섯 바퀴에서 강제로 멈추지 않으면 영원히 돌았다.

Java는 다르게 막는다. `ArrayList`의 반복자는 도는 중에 리스트가 다른 경로로 바뀐 것을 알아채면 `ConcurrentModificationException`을 던진다. 자바 문서는 이것을 "최선을 다해 감지하는(fail-fast)" 동작이라 부르고, 이 예외에 기대어 프로그램을 짜지 말라고 적어 두었다. 지우면서 돌아야 하면 반복자 자신의 `remove()`를 쓰라는 것이 정석이다. 반복자가 컬렉션을 바꾸면 위치도 같이 맞출 수 있기 때문이다.

## 한 번 돌면 끝나는 반복자

반복 가능한 객체와 반복자는 다르다. 배열은 반복 가능한 객체라서 `for...of`를 할 때마다 새 반복자를 만든다. 제너레이터 객체는 자기 자신이 반복자이고 `[Symbol.iterator]()`가 자기를 돌려준다. 그래서 한 번 다 돌면 다시 돌 수 없다.

```js
const g = rows(); // 위에서 만든 제너레이터
console.log([...g].length, [...g].length); // 3 0
```

이 차이가 실제 버그로 나타나는 곳이 있다. 함수가 `allOrders()`의 결과를 받아 "건수를 세고, 그다음에 내보내기"를 하면 두 번째 반복은 빈손이다. 에러도 나지 않고 0건이 처리된다. 여러 번 돌아야 하는 값이라면 제너레이터 객체가 아니라 제너레이터 함수를 넘기거나, `[Symbol.iterator]() { return gen(); }`처럼 돌 때마다 새로 만드는 객체로 감싼다. `fetch` 응답 본문도 한 번만 읽히는 스트림이라 `res.json()`을 두 번 부르면 에러가 난다(Node.js 22에서는 `TypeError: Body is unusable: Body has already been read`).

## 안에서 도는 반복자, 밖에서 당기는 반복자

지금까지 본 것은 쓰는 쪽이 `next()`로 값을 당기는 외부 반복자다. 반대로 컬렉션이 함수를 받아 원소마다 불러 주는 방식을 내부 반복자라고 한다. `Array.prototype.forEach`가 그렇다.

내부 반복자는 쓰기 쉽지만 흐름을 컬렉션이 쥔다. `forEach` 안에서는 `break`를 쓸 수 없고, 콜백에 `async`를 붙여도 `forEach`는 그 Promise를 기다리지 않는다. 주문마다 `await sendMail()`을 하려고 `forEach(async ...)`를 쓰면 메일 요청이 한꺼번에 나가고, 함수는 메일이 끝나기 전에 돌아온다. 순서대로 기다려야 하면 `for...of`(외부 반복자)를 쓴다.

Go는 1.23에서 내부 반복자 쪽을 언어에 넣었다. `iter.Seq[V]`는 `func(yield func(V) bool)` 모양의 함수이고, `for v := range seq`를 쓰면 컴파일러가 반복문 몸통을 `yield` 함수로 바꿔 넘긴다. `yield`가 `false`를 돌려주면 그만 돌라는 뜻이다. 당기는 방식이 필요할 때를 위해 `iter.Pull`도 함께 있다. 언어마다 기본 방향은 다르지만, 둘 다 "어떻게 도는지 숨긴다"는 같은 목적이다.

## 반복자를 꺼내지 않아도 될 때

반복자 추상은 공짜가 아니다. 1000만 개 숫자를 더하는 데 Node.js 22에서 걸린 시간이다. 실행할 때마다 꽤 흔들려서 자릿수만 본다.

```text
for (let i…)           21 ms
for…of array          140 ms
for…of generator      513 ms
```

원소 하나에 수십 나노초 차이다. 네트워크 요청 한 번(수십 밀리초)이 끼는 페이지네이션에서는 보이지도 않는다. 수백만 번 도는 계산 반복문에서만 신경 쓴다. 이미 배열이고, 전부 메모리에 있고, 한 번만 돈다면 그냥 배열 메서드를 쓴다. 반복자를 꺼낼 때는 이런 경우다.

- 원소를 한 번에 메모리에 올릴 수 없다(페이지, 스트림, 큰 파일).
- 앞의 몇 개만 필요하거나, 끝이 없다.
- 내부 구조가 바뀔 수 있어 숨겨야 한다(트리, 페이지 방식, 캐시 계층).
- 같은 컬렉션을 여러 순서로 돌아야 한다. 트리라면 `depthFirst()`, `breadthFirst()`처럼 반복자를 만드는 메서드를 둘 둔다.

클래스형 반복자가 여전히 나은 경우도 있다. 위치를 저장했다가 나중에 이어서 돌아야 할 때다. 제너레이터의 위치는 함수 실행 상태라 직렬화할 수 없다. 배치가 중간에 죽었다가 이어서 돌아야 하면, 커서 문자열 같은 위치 값을 필드로 들고 꺼내 볼 수 있는 반복자가 필요하다. 데이터베이스의 서버 측 커서나 Kafka의 컨슈머 오프셋이 같은 생각이다.

이터레이터는 컬렉션이 어떻게 생겼는지 숨기고, 쓰는 쪽에는 "다음 것"만 주는 패턴이다. 자바스크립트에서는 `[Symbol.iterator]`와 `next()` 규약으로 언어에 들어 있고, 제너레이터가 위치를 대신 기억해 주니 클래스를 짤 일이 드물다. 실무에서 챙길 것은 세 가지다. `break`하면 `return()`이 불리니 자원 정리는 `finally`에 두고, 제너레이터 객체는 한 번만 돌 수 있고, 도는 중에 컬렉션을 바꾸지 않는다.

## 면접에서 나올 만한 질문

### 이터레이터 패턴은 무엇이고 왜 쓰나요?

컬렉션의 내부 구조를 드러내지 않고 원소를 하나씩 꺼낼 수 있게 하는 패턴이다. 꺼내는 위치를 컬렉션이 아니라 반복자가 들고 있어서, 같은 컬렉션을 여러 곳에서 동시에 돌 수 있고 컬렉션 구조가 바뀌어도 쓰는 쪽은 그대로다. 페이지네이션 API를 `for await` 하나로 돌게 감싸는 것이 대표적인 쓰임이다.

### 자바스크립트의 iterable과 iterator는 어떻게 다른가요?

iterable은 `[Symbol.iterator]()` 메서드로 반복자를 만들어 줄 수 있는 객체이고, iterator는 `next()`로 `{ value, done }`을 돌려주는 객체다. 배열은 iterable이라 돌 때마다 새 반복자를 만들지만, 제너레이터 객체는 자기 자신이 반복자라 한 번 다 돌면 다시 돌 수 없다. 그래서 제너레이터 결과를 두 번 돌면 두 번째는 조용히 0건이 된다.

### for...of 도중 break하면 어떤 일이 일어나나요?

반복문이 반복자의 `return()` 메서드를 불러 정리할 기회를 준다. 제너레이터라면 `try...finally`의 `finally`가 실행되니, DB 커서나 파일 핸들처럼 중간에 멈춰도 닫아야 하는 자원은 거기서 정리한다. 직접 만든 반복자 클래스라면 `return()`을 구현해야 같은 효과가 난다.

### 제너레이터가 이터레이터 패턴을 어떻게 단순하게 만드나요?

반복자 클래스가 필드로 들고 있던 위치 정보를 제너레이터는 지역 변수와 실행 위치로 대신 기억한다. `yield`에서 멈췄다가 다음 `next()`에 그 자리에서 이어서 돌기 때문이다. 그래서 커서와 버퍼를 관리하던 클래스 두 개가 `async function*` 하나가 된다. 다만 실행 위치는 직렬화할 수 없어서, 중간 위치를 저장해 두고 나중에 이어서 돌아야 하면 위치를 필드로 가진 클래스형 반복자가 낫다.

### 이터레이터를 쓰면 성능상 이점이 있나요?

게으른 평가로 필요한 만큼만 계산한다는 이점이 있다. 100만 개 배열에서 앞의 세 개를 구할 때 배열 체인은 map 콜백을 100만 번 불렀고, 이터레이터 헬퍼 체인은 일곱 번만 불렀다. 반면 원소 하나를 꺼내는 비용은 인덱스 반복문보다 커서, 전부 메모리에 있는 배열을 한 번 다 도는 계산이라면 일반 반복문이 빠르다.

### 순회 중에 컬렉션을 수정하면 어떻게 되나요?

언어마다 다르다. 자바스크립트 배열 반복자는 인덱스만 기억해서, 뒤에 붙인 원소는 그대로 돌고 앞에서 지우면 다음 원소를 건너뛴다. Java의 `ArrayList` 반복자는 변경을 감지하면 `ConcurrentModificationException`을 던지고, 지우려면 반복자의 `remove()`를 쓴다. 안전한 방법은 순회 중에 원본을 바꾸지 않고 `filter`로 새 컬렉션을 만드는 것이다.

### 내부 반복자와 외부 반복자의 차이는 무엇인가요?

외부 반복자는 쓰는 쪽이 `next()`로 값을 당기고, 내부 반복자는 컬렉션이 받은 함수를 원소마다 불러 준다. `forEach` 같은 내부 반복자는 간단하지만 중간에 `break`할 수 없고 콜백의 Promise를 기다리지 않아서, 순서대로 `await`해야 하면 `for...of`를 쓴다. Go 1.23의 range-over-func는 내부 반복자 방식이고 `iter.Pull`로 외부 반복자로 바꿀 수 있다.
