카메라 앱에 "찍는 순간 물건 이름 보여 주기" 기능을 붙였다. 첫 버전은 프레임을 서버로 보내 분류하고 결과를 받았다. 사무실 와이파이에서는 괜찮았는데, 출시 뒤 리뷰가 이렇다. "지하철에서는 이름이 2초 뒤에 떠요." "카메라 화면을 서버로 보낸다고요? 집 안을 찍는데요." 서버 비용도 문제다. 사용자가 카메라를 켜 두는 동안 초당 몇 장씩 요청이 들어온다.

## 기기에서 돌릴까, 서버에 둘까

먼저 정말 기기로 옮겨야 하는지부터 따진다. 기기 안 추론이 주는 것과 대가가 분명히 다르다.

기기에서 돌리면 얻는 것.

- 지연: 네트워크 왕복이 없다. 실시간 카메라, 음성 호출어("헤이 ○○") 감지, 키보드 자동 완성처럼 수십 ms 안에 답해야 하는 기능은 사실상 기기에서만 된다.
- 오프라인: 지하철, 비행기, 공장 안처럼 연결이 불안정한 곳에서도 동작한다.
- 프라이버시: 사진·음성·건강 데이터가 기기를 떠나지 않는다. 규제나 사용자 신뢰 때문에 이게 결정적인 이유가 되기도 한다.
- 비용: 추론 한 번의 서버 비용이 0이다. 사용자가 계산을 대신 내 주는 셈이다.

대신 치르는 것.

- 자원: 메모리, 저장 공간, 배터리, 발열. 오래 돌리면 기기가 뜨거워지고 운영체제가 성능을 낮춘다(스로틀링). 처음 1분은 빠르다가 5분 뒤 느려지는 일이 흔하다.
- 정확도: 기기에 들어가는 작은 모델은 서버의 큰 모델보다 대체로 덜 정확하다.
- 업데이트: 서버 모델은 배포 한 번이면 바뀌지만, 기기 모델은 앱 업데이트나 모델 다운로드가 퍼질 때까지 옛 버전이 오래 남는다.
- 파편화: 기기마다 칩, NPU(신경망 전용 가속기) 지원, 운영체제 버전이 달라 같은 모델이 어떤 기기에서는 5ms, 어떤 기기에서는 80ms 걸린다.
- 모델 보호: 앱 안의 모델 파일은 꺼내 볼 수 있다. 모델 자체가 핵심 자산이면 부담이다.

그래서 둘을 섞는 경우가 많다. 기기에서 작은 모델이 먼저 판단하고, 확신이 낮거나 무거운 일만 서버로 보낸다. 카메라 앱이라면 물체가 있는지와 대략의 종류는 기기에서 바로 보여 주고, 사용자가 눌렀을 때 자세한 설명은 서버의 큰 모델이 한다. 서버 쪽에서 모델을 띄우고 내보내는 방법은 [모델 서빙 글](/posts/model-serving)에 있다.

## 모델 크기는 파라미터 수 × 바이트

기기에 넣을 수 있는지는 먼저 크기로 가늠한다. 가중치 하나를 32비트 실수(FP32)로 저장하면 4바이트, 16비트(FP16)면 2바이트, 8비트 정수(INT8)면 1바이트다. 이미지 분류에 많이 쓰이던 MobileNetV2는 파라미터가 약 350만 개라 FP32로 약 14MB, INT8로 약 3.5MB다. ResNet-50은 약 2,560만 개라 FP32로 약 100MB다. 앱 하나에 넣기에는 크다.

실행할 때의 메모리는 가중치보다 크다. 층마다 중간 결과(활성값)를 담을 공간이 필요하고, 런타임 자체도 메모리를 쓴다. 학습할 때만큼은 아니지만 입력 해상도가 크면 활성값이 커진다. 학습 메모리 계산은 [딥러닝 기초 글](/posts/deep-learning-basics)에 있다.

작은 실험으로 줄이는 효과를 보자. 8×8 손글씨 숫자 이미지(scikit-learn의 digits, 1,797장)를 분류하는 신경망(은닉층 512, 256)을 학습시켰다. 파라미터는 167,178개다.

```python
import numpy as np
from sklearn.datasets import load_digits
from sklearn.model_selection import train_test_split
from sklearn.neural_network import MLPClassifier
from skl2onnx import to_onnx
from onnxruntime.quantization import quantize_dynamic, QuantType

X, y = load_digits(return_X_y=True)
X = (X / 16.0).astype(np.float32)
Xtr, Xte, ytr, yte = train_test_split(X, y, test_size=0.3, random_state=0)
mlp = MLPClassifier(hidden_layer_sizes=(512, 256), max_iter=300, random_state=0).fit(Xtr, ytr)

onx = to_onnx(mlp, Xtr[:1], options={id(mlp): {"zipmap": False}}, target_opset=17)  # ONNX로 내보내기
open("mlp_fp32.onnx", "wb").write(onx.SerializeToString())
quantize_dynamic("mlp_fp32.onnx", "mlp_int8.onnx", weight_type=QuantType.QInt8)    # 가중치를 INT8로
```

두 파일을 ONNX Runtime의 CPU 실행기로 스레드 하나만 써서 불러, 시험 세트 정확도와 한 장 추론 시간(2천 번 평균)을 쟀다.

```text
sklearn acc 0.9796
mlp_fp32.onnx   size=654KB acc=0.9796 latency=0.030ms outputs=['label', 'probabilities']
mlp_int8.onnx   size=169KB acc=0.9796 latency=0.025ms outputs=['label', 'probabilities']
label agreement 1.0 max prob diff 0.0299
```

파일은 654KB에서 169KB로 약 4분의 1이 됐다. 167,178개 × 4바이트 ≈ 653KB가 1바이트씩으로 줄어든 것이다. 정확도는 0.9796으로 같고, 시험 세트 540장 모두에서 두 모델의 답이 같았다. 확률값은 최대 0.0299까지 차이가 났다. 지연은 이 모델이 워낙 작아서 둘 다 0.03ms 근처라 의미 있는 비교가 아니다. 큰 합성곱 모델을 INT8을 잘 지원하는 하드웨어에서 돌리면 속도 차이가 훨씬 커진다. 반대로 INT8 연산을 지원하지 않는 하드웨어에서는 정수를 다시 실수로 바꾸느라 오히려 느려질 수도 있다.

## 양자화는 범위를 256칸으로 나누는 일

양자화(quantization)는 실수를 적은 비트의 정수로 바꿔 적는 것이다. 8비트면 256칸이다. [LLM 직접 띄우기 글](/posts/self-hosting-llm-inference)에서는 가중치를 원점 대칭으로 나누는 방식을 봤는데, 기기용 모델에서는 활성값까지 정수로 바꾸는 경우가 많아서 영점(zero point)이 있는 비대칭 방식도 자주 쓴다.

비대칭 8비트(uint8) 양자화는 이렇다.

1. 값의 최솟값과 최댓값을 구한다. 0이 정확히 표현되도록 범위에 0을 포함시킨다.
2. 배율 scale = (최댓값 − 최솟값) / 255. 한 칸이 실수로 얼마인지다.
3. 영점 zero point = round(−최솟값 / scale). 실수 0이 몇 번 칸에 오는지다.
4. 정수 q = round(x / scale) + zero point를 0~255로 자른다.
5. 되돌릴 때는 (q − zero point) × scale.

활성 함수 ReLU를 지난 값은 0 이상만 있으니 원점 대칭으로 −127~127을 쓰면 절반을 버리게 된다. 영점을 두면 0~255를 다 쓴다. 0을 정확히 표현해야 하는 이유는 패딩처럼 0이 아주 많이 나오는 곳에서 0이 0.003 같은 값으로 바뀌면 오차가 쌓이기 때문이다.

직접 짜 보자. 배열을 받아 배율, 영점, 정수 배열, 되돌렸을 때 가장 큰 오차를 돌려준다.

### 활성값의 범위는 언제 정하나

가중치는 학습이 끝나면 고정이라 범위를 바로 안다. 활성값은 입력마다 다르다. 이걸 정하는 시점에 따라 방식이 나뉜다.

동적 양자화(dynamic)는 가중치만 미리 INT8로 바꾸고, 활성값은 실행할 때마다 범위를 재서 바꾼다. 준비가 필요 없고 위 실험처럼 한 줄로 끝난다. 자연어 모델처럼 가중치 읽기가 병목인 모델에 잘 맞는다. 대신 실행 중 범위 계산 비용이 든다.

정적 양자화(static)는 대표 입력 수백 개(보정 데이터, calibration)를 미리 흘려 층마다 활성값 범위를 재 두고, 실행할 때는 그 범위를 그대로 쓴다. 이미지 모델에서 가장 빠르다. 대신 보정 데이터가 실제 입력과 다르면(밝은 사진만 넣었는데 실제로는 밤 사진이 많다) 범위가 맞지 않아 정확도가 떨어진다. 위 숫자 모델에 정적 양자화를 해 봤더니 보정 데이터 200장과 5장 모두 정확도 0.9796을 유지했다. 이 작은 모델은 둔감했지만, 큰 이미지 모델에서는 보정 데이터의 양과 다양성이 결과를 바꾼다. 구글의 Edge TPU처럼 정수 연산만 하는 가속기는 입력부터 출력까지 전부 정수인 완전 정수 양자화가 필요해서 정적 방식이 필수다.

양자화 인식 학습(QAT, quantization-aware training)은 학습할 때부터 양자화 오차를 흉내 내서 모델이 그 오차에 적응하게 한다. 학습이 끝난 뒤 바꾸는 방식(PTQ, post-training quantization)으로 정확도가 많이 떨어질 때 쓴다. 학습 파이프라인을 다시 돌려야 해서 비용이 크다.

양자화로 정확도가 떨어지면 순서대로 시도한다. 먼저 채널 단위 배율로 바꾸고, 보정 데이터를 실제 입력 분포에 가깝게 늘린다. 그래도 안 되면 민감한 층(보통 첫 층과 마지막 층)만 FP16으로 남기는 혼합 정밀도를 쓴다. 마지막으로 QAT를 한다. 판단은 전체 정확도만이 아니라 어두운 사진, 작은 물체처럼 어려운 구간별로 한다. 양자화 오차는 쉬운 입력보다 경계에 있는 입력에서 먼저 드러난다.

## 덜 중요한 가중치를 지운다: 가지치기

가지치기(pruning)는 크기가 작은, 즉 결과에 영향이 적은 가중치를 0으로 만드는 것이다. 위 숫자 모델의 가중치를 절댓값이 작은 순서대로 지워 봤다. 지운 뒤 다시 학습은 하지 않았다.

```python
for frac in [0, 0.5, 0.8, 0.9, 0.95, 0.98]:
    m = copy.deepcopy(mlp)
    allw = np.concatenate([np.abs(w).ravel() for w in m.coefs_])
    th = np.quantile(allw, frac) if frac else -1          # 하위 frac 비율의 경계값
    for i, w in enumerate(m.coefs_):
        m.coefs_[i] = np.where(np.abs(w) > th, w, 0)      # 경계보다 작은 가중치는 0
    raw = b"".join(w.astype(np.float32).tobytes() for w in m.coefs_)
    print(f"prune {frac:.2f} acc={m.score(Xte, yte):.4f} raw={len(raw)/1024:.0f}KB "
          f"gzip={len(gzip.compress(raw))/1024:.0f}KB")
```

```text
prune 0.00 acc=0.9796 raw=650KB gzip=608KB
prune 0.50 acc=0.9741 raw=650KB gzip=341KB
prune 0.80 acc=0.9426 raw=650KB gzip=153KB
prune 0.90 acc=0.8130 raw=650KB gzip=81KB
prune 0.95 acc=0.5370 raw=650KB gzip=42KB
prune 0.98 acc=0.3556 raw=650KB gzip=18KB
```

절반을 지워도 정확도는 0.9796에서 0.9741로 조금만 떨어진다. 80%까지는 0.9426으로 버티다가 90%부터 무너진다. 실무에서는 한 번에 지우지 않고 조금씩 지우면서 다시 학습시켜(반복 가지치기) 정확도를 회복시키기 때문에 이보다 많이 지울 수 있다.

`raw` 열을 보면 함정이 보인다. 가중치의 90%를 0으로 바꿔도 원본 크기는 650KB 그대로다. 0도 4바이트 실수로 저장되기 때문이다. 압축(gzip)하면 81KB로 줄어서 앱 다운로드 크기에는 도움이 되지만, 메모리에 올리면 다시 650KB이고, 행렬 곱셈도 0을 곱하는 계산을 그대로 한다. 이렇게 흩어진 0(비정형 가지치기)으로 실제로 빨라지려면 희소 행렬 연산을 지원하는 런타임과 하드웨어가 필요하다.

그래서 기기용으로는 채널이나 필터를 통째로 지우는 정형 가지치기(structured pruning)를 많이 쓴다. 층의 너비 자체가 줄어서 별도 지원 없이도 작아지고 빨라진다. 대신 같은 비율을 지웠을 때 정확도 손실이 더 크다.

## 큰 모델이 작은 모델을 가르친다: 지식 증류

증류(distillation)는 처음부터 작은 모델을 만들되, 큰 모델(선생)의 출력을 정답 삼아 작은 모델(학생)을 학습시키는 방법이다. 선생은 "이건 3이다"만이 아니라 "3일 확률 0.9, 8일 확률 0.08"처럼 비슷한 것끼리의 관계까지 알려 준다. 이 부드러운 정답이 학생에게 더 많은 정보를 준다. 원래 제안(Hinton 등, 2015)에서는 온도(temperature)로 확률 분포를 더 평평하게 만들어 이 관계를 드러낸다. LLM에서 증류를 쓰는 이야기는 [파인튜닝 비교 글](/posts/fine-tuning-vs-rag-vs-prompting)에 있다.

증류가 특히 빛나는 건 라벨이 적고 라벨 없는 데이터가 많을 때다. 숫자 데이터에서 라벨을 150장만 주고, 나머지 학습 데이터는 라벨 없이 선생(위의 512·256 모델)의 확률만 붙여 학생(은닉층 32개, 파라미터 2,410개)을 학습시켰다. 온도는 쓰지 않고 선생 확률을 회귀로 따라 하게 한 단순한 형태다.

```text
student hard labels (150 labeled) 0.8759
student distilled (teacher probs on all train) 0.9426
student hard labels (all train) 0.9667
teacher 0.9796 student params 2410 teacher params 167178
```

라벨 150장만으로 학습한 학생은 0.8759, 라벨 없는 데이터에 선생의 확률을 붙여 학습한 학생은 0.9426이다. 파라미터가 선생의 약 70분의 1인 모델이 사람이 라벨을 붙이지 않은 데이터로 6.7%p를 올렸다. 다만 학습 데이터 전체에 진짜 라벨이 있을 때(0.9667)보다는 낮았다. 이 작은 문제에서는 라벨이 충분하면 증류의 이점이 크지 않았다는 뜻이다. 복잡한 문제일수록, 그리고 온도와 진짜 라벨 손실을 섞는 제대로 된 증류일수록 효과가 커진다고 알려져 있다.

세 방법은 함께 쓴다. 증류로 작은 구조를 만들고, 가지치기로 더 줄이고, 마지막에 양자화한다. 순서를 바꾸면 각 단계의 오차가 겹쳐 회복하기 어려우니 단계마다 정확도를 확인한다.

LiteRT는 TensorFlow Lite의 새 이름이다(2024년에 이름이 바뀌었다). `.tflite` 형식을 읽고, 안드로이드와 마이크로컨트롤러까지 가장 넓게 쓰인다. 가속기는 델리게이트(delegate)로 붙인다. GPU 델리게이트, iOS의 Core ML 델리게이트 같은 식이다. 안드로이드의 NNAPI는 Android 15에서 사용 중단 예고가 붙어서, 칩 제조사의 전용 델리게이트나 GPU 쪽으로 옮겨 가는 추세다.

ExecuTorch는 PyTorch 쪽의 기기용 런타임으로, 예전 PyTorch Mobile의 뒤를 잇는다. PyTorch Mobile은 더 이상 새 기능이 들어가지 않으니 새 프로젝트는 ExecuTorch로 시작한다. `torch.export`로 그래프를 뽑아 `.pte` 파일을 만들고, XNNPACK(CPU), Core ML, Qualcomm 같은 백엔드에 연산을 나눠 맡긴다.

ONNX Runtime은 ONNX라는 공통 형식을 읽는다. PyTorch, TensorFlow, scikit-learn(위 실험처럼 skl2onnx로) 어디서든 ONNX로 내보낼 수 있어서 학습 프레임워크에 덜 묶인다. 가속기는 실행 제공자(execution provider)로 붙인다. CUDA, TensorRT, Core ML, Qualcomm QNN, DirectML 같은 것들이다. 브라우저용 onnxruntime-web은 WebGPU나 WebAssembly로 돈다. 브라우저 추론은 [LLM 직접 띄우기 글](/posts/self-hosting-llm-inference)에서도 다뤘다.

애플 기기만 대상이면 Core ML로 바로 변환해 뉴럴 엔진을 쓰는 게 가장 빠른 경우가 많다.

런타임을 고를 때 자주 부딪히는 문제는 연산자 지원이다. 학습 때 쓴 연산 하나를 가속기가 지원하지 않으면 그 연산만 CPU로 떨어지고(fallback), 가속기와 CPU 사이로 데이터를 옮기느라 전체가 CPU만 쓸 때보다 느려지기도 한다. 이 현상은 에러 없이 조용히 일어난다. 변환 뒤에는 어떤 연산이 어느 백엔드에 배정됐는지 런타임의 프로파일러나 로그로 확인하고, 대표 기기 몇 대에서 실제로 잰다. ONNX의 opset 버전과 런타임 버전이 맞지 않으면 모델을 아예 못 여는 문제도 있다. 위 실험은 opset 17로 내보냈다.

## 엣지 가속기: Jetson 같은 보드

휴대폰이 아니라 공장 카메라, 매장의 계산대, 로봇, 드론처럼 전용 장비에서 돌리는 엣지도 있다. 여기서는 NVIDIA Jetson이 대표적이다. GPU가 붙은 작은 컴퓨터 모듈로, Orin 세대는 개발 키트 기준 Orin Nano Super가 67 TOPS(초당 정수 연산 조 단위), AGX Orin이 275 TOPS까지 낸다고 공개돼 있다. JetPack SDK에 CUDA, cuDNN, TensorRT가 함께 들어 있다.

Jetson에서는 보통 모델을 ONNX로 내보낸 뒤 TensorRT로 그 기기에 맞는 엔진 파일을 만든다. TensorRT는 층을 합치고, FP16·INT8로 줄이고, 그 GPU에서 가장 빠른 연산 방식을 골라 엔진에 굽는다. 그래서 엔진 파일은 만든 기기와 TensorRT 버전에 묶인다. 다른 Jetson 모델이나 JetPack 버전에서는 다시 만들어야 한다. 장비마다 첫 부팅 때 엔진을 빌드하게 하거나, 기종별 엔진을 따로 배포한다.

전력도 설정이다. Jetson은 전력 모드(`nvpmodel`)를 바꿔 최대 전력을 제한할 수 있고, 모드에 따라 같은 모델의 처리량이 달라진다. 팬 없는 함체에 넣으면 발열로 클럭이 내려가니, 벤치마크는 실제 함체와 실제 온도에서 오래 돌려 잰다.

이 밖에 정수 연산만 하는 구글 Coral Edge TPU, 인텔 CPU·GPU·NPU용 OpenVINO, 마이크로컨트롤러용 LiteRT for Microcontrollers 같은 선택지가 있다. 고를 때는 성능 숫자보다 쓰려는 모델의 연산이 그 가속기에서 다 돌아가는지를 먼저 본다.

몇 가지를 꼭 둔다.

- 호환성 표: 모델 버전마다 필요한 런타임·앱 최소 버전을 적고, 설정 서버가 맞는 기기에만 준다. 옛 앱에 새 opset 모델을 주면 열지 못한다.
- 옛 모델 보관: 새 모델이 기기에서 실패하면 바로 돌아갈 수 있게 직전 모델을 지우지 않는다. 앱에 기본 모델 하나를 내장해 두면 다운로드가 다 실패해도 기능이 돈다.
- 단계적 배포: 서버의 [카나리 릴리스](/posts/canary-release)처럼 비율을 조금씩 늘린다. 비율은 [기능 플래그](/posts/feature-flags)나 원격 설정으로 조절한다. Firebase 같은 서비스가 커스텀 모델 배포 기능을 제공한다.
- 기종별 관측: 평균 지연은 의미가 적다. 기종·칩·운영체제 버전별로 p50·p95를 보고, CPU 폴백 비율을 함께 본다. 특정 기종에서만 NPU를 못 써서 느려지는 경우가 많다.

정확도 관측은 더 어렵다. 입력이 기기를 떠나지 않으니 서버처럼 예측과 정답을 모아 비교할 수 없다. 사용자가 결과를 고친 비율(자동 완성을 지운 비율, 분류 결과를 직접 바꾼 비율), 점수 분포의 변화, 동의한 사용자에게서만 모은 표본으로 간접적으로 본다. 드리프트를 보는 방법 자체는 [모델 모니터링 글](/posts/ml-model-monitoring-drift)과 같지만, 계산을 기기에서 집계해 요약만 보낸다는 점이 다르다. 원본 데이터를 모으지 않고 기기에서 학습한 변화분만 모아 모델을 개선하는 연합 학습(federated learning)도 있다. 휴대폰 키보드의 다음 단어 예측에 쓰인 사례가 잘 알려져 있다.

모델 파일이 기기에 있다는 건 누군가 꺼내 볼 수 있다는 뜻이기도 하다. 암호화해 두더라도 실행하려면 기기에서 풀어야 하니 완전히 막을 수는 없다. 모델 자체가 경쟁력이면 기기에는 작은 모델만 두고 중요한 부분은 서버에 남기는 것도 설계 판단이다. 어떤 데이터로 학습해 어떤 버전을 어느 기기에 내보냈는지는 [실험 추적 글](/posts/ml-experiment-tracking)의 레지스트리와 같은 방식으로 남기고, 변환과 양자화 단계도 [ML 파이프라인](/posts/ml-pipelines-ci-cd)의 한 단계로 넣어 정확도 관문을 거치게 한다.

## 작게 만들고, 기기마다 재고, 되돌릴 길을 둔다

엣지 AI는 지연, 오프라인, 프라이버시, 서버 비용을 얻는 대신 배터리, 발열, 정확도, 업데이트, 파편화를 떠안는 선택이다. 모델 크기는 파라미터 수 × 바이트라 INT8 양자화만으로 4분의 1이 되고, 실험에서는 정확도도 그대로였다. 이상치 하나가 양자화 칸을 망칠 수 있어 채널 단위 배율과 보정 데이터가 중요하다. 비정형 가지치기는 파일을 압축하면 작아지지만 메모리와 속도는 그대로라 기기용으로는 정형 가지치기를 쓰고, 증류는 라벨 없는 데이터가 많을 때 작은 모델을 크게 끌어올린다. 런타임은 연산이 가속기에서 다 도는지 대표 기기에서 직접 재서 고르고, 흩어진 모델은 호환성 표, 단계적 배포, 기종별 관측, 옛 모델 보관으로 다룬다.

## 면접에서 나올 만한 질문

### 엣지 추론과 서버 추론은 어떤 기준으로 고르나요?

수십 ms 안에 답해야 하거나, 오프라인에서도 돌아야 하거나, 입력이 기기를 떠나면 안 되면 기기에서 돌린다. 초당 30프레임 카메라라면 한 프레임 예산이 33ms라 네트워크 왕복만으로 넘기 쉽다. 반대로 큰 모델의 정확도가 필요하거나, 모델을 자주 바꿔야 하거나, 모델 자체를 보호해야 하면 서버가 낫다. 기기에서 작은 모델이 먼저 판단하고 어려운 경우만 서버로 보내는 혼합 구성이 흔하다.

### 양자화는 어떻게 동작하고, 왜 모델이 작아지나요?

실수 범위를 8비트면 256칸으로 나눠 각 값을 가장 가까운 칸 번호로 적고, 칸 하나의 크기(scale)와 실수 0의 위치(zero point)를 함께 저장한다. 4바이트 실수가 1바이트 정수가 되니 가중치 크기가 4분의 1이 된다. 실험에서 167,178개 파라미터 모델이 654KB에서 169KB가 됐고 정확도는 0.9796으로 같았다. INT8 연산을 지원하는 하드웨어에서는 연산도 빨라지지만, 지원하지 않으면 오히려 느려질 수 있다.

### 양자화로 정확도가 떨어지면 어떻게 대처하나요?

먼저 원인이 이상치인지 본다. 이상치 하나가 범위를 넓히면 작은 값들이 같은 칸에 몰린다. 텐서 단위 배율을 채널 단위로 바꾸고, 정적 양자화라면 보정 데이터를 실제 입력 분포에 맞게 늘리고 다양하게 한다. 그래도 떨어지면 첫 층과 마지막 층처럼 민감한 층만 FP16으로 남기는 혼합 정밀도를 쓰고, 최후에는 학습 중에 양자화 오차를 흉내 내는 QAT를 한다. 판단은 어려운 입력 구간별로 한다.

### 동적 양자화와 정적 양자화는 무엇이 다른가요?

동적 양자화는 가중치만 미리 INT8로 바꾸고 활성값의 범위는 실행할 때마다 잰다. 준비가 필요 없고 가중치 읽기가 병목인 모델에 맞다. 정적 양자화는 보정 데이터로 활성값 범위를 미리 재 두고 실행 때 그대로 써서 이미지 모델에서 가장 빠르지만, 보정 데이터가 실제 입력과 다르면 정확도가 떨어진다. 정수 연산만 하는 가속기는 완전 정수 양자화가 필요해서 정적 방식을 써야 한다.

### 가지치기를 했는데 모델이 빨라지지 않는 이유는요?

흩어진 가중치를 0으로 만드는 비정형 가지치기는 0도 그대로 저장하고 계산하기 때문이다. 실험에서 가중치 90%를 지워도 원본은 650KB 그대로였고, gzip으로 압축해야 81KB가 됐다. 메모리와 연산이 줄려면 희소 연산을 지원하는 런타임과 하드웨어가 필요하다. 기기용으로는 채널이나 필터를 통째로 지우는 정형 가지치기를 써서 층 너비 자체를 줄인다.

### 지식 증류는 언제 효과가 큰가요?

라벨이 적고 라벨 없는 데이터가 많을 때다. 큰 선생 모델의 확률 출력을 정답 삼아 작은 학생을 학습시키면 사람이 라벨을 붙이지 않은 데이터도 쓸 수 있다. 실험에서 라벨 150장만 쓴 학생은 0.8759였고, 라벨 없는 데이터에 선생 확률을 붙여 학습한 학생은 0.9426이었다. 선생의 부드러운 확률은 비슷한 클래스 사이의 관계까지 알려 줘서 진짜 라벨보다 정보가 많다.

### 기기에 흩어진 모델 버전은 어떻게 배포하고 관측하나요?

모델을 앱과 따로 내려받게 하고, 설정 서버가 앱·런타임 버전과 기종을 보고 호환되는 모델만 단계적 비율로 내려 준다. 기기는 해시와 서명, 시험 추론으로 검증한 뒤에만 바꿔 끼우고 직전 모델을 보관해 둔다. 관측은 원본 입력 대신 모델 버전·기종별 지연 분위수, CPU 폴백 비율, 크래시, 점수 분포 같은 요약을 기기에서 집계해 보낸다. 나빠지면 설정 서버에서 배포를 멈추고 옛 버전으로 돌린다.

### 변환한 모델이 가속기에서 예상보다 느린 이유는 무엇일 수 있나요?

가속기가 지원하지 않는 연산이 하나라도 있으면 그 연산만 CPU로 떨어지고, 가속기와 CPU 사이로 데이터를 옮기는 비용 때문에 전체가 느려질 수 있다. 이건 에러 없이 조용히 일어난다. 프로파일러로 연산별 배정을 확인하고, 지원되는 연산으로 바꾸거나 모델 구조를 조정한다. 오래 돌리면 발열로 클럭이 내려가는 스로틀링도 있어서, 실제 기기와 실제 환경에서 충분히 오래 돌려 잰다.
