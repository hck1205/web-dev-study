주문 내역 API가 가끔 504를 돌려준다는 문의가 왔다. nginx 로그를 보면 응답 시간이 정확히 60.0초다. 그런데 앱 로그에는 같은 요청이 "200, 74초 걸림"으로 찍혀 있다. 앱은 끝까지 일했고 결과도 만들었다. 다만 그 결과를 받을 사람이 14초 전에 이미 떠났다. 사용자는 504를 봤고 새로고침을 눌렀으니, 앱은 같은 무거운 쿼리를 한 번 더 돌리기 시작했다.

타임아웃은 "몇 초 기다릴까" 하나로 끝나는 설정이 아니다. 요청 하나가 지나가는 길에는 단계마다, 장비마다 기다림의 한도가 따로 걸려 있고, 그 값들이 서로 맞지 않으면 위처럼 아무도 받지 않을 일을 하게 된다. 이 글은 그 한도들이 어디에 몇 개나 있는지, 각각 무엇을 재는지, 서로 어떻게 맞물려야 하는지를 직접 재 보며 정리한다. 실습 환경은 Ubuntu 24.04 계열 컨테이너(커널 6.18), Node 22, nginx 1.24, PostgreSQL 16이다.

이 주제의 다른 글: 타임아웃이 왜 필요한지와 연쇄 장애 전체 그림은 [장애가 번지지 않게](/posts/resilience-patterns)에서, 타임아웃이 난 뒤 다시 보낼지는 [재시도](/posts/retries)에서, 다시 보낼 때 얼마나 기다릴지는 [지수 백오프와 지터](/posts/exponential-backoff-jitter)에서 다룬다.

## 요청 하나에 기다림이 여섯 번 있다

HTTPS 요청 하나는 한 번에 끝나는 동작이 아니다. 이름을 IP로 바꾸고, TCP 연결을 맺고, TLS 협상을 하고, 요청을 보내고, 첫 바이트를 기다리고, 나머지 본문을 받는다. 각 단계는 실패하는 이유가 다르고, 그래서 따로 한도를 건다. 아래 그림에서 다음을 누르면 단계마다 어떤 타임아웃이 지키고 있는지 나온다.

curl의 `-w` 옵션으로 각 단계가 끝난 시각을 직접 볼 수 있다. 로컬에 띄운 nginx(TLS)가 앱에 넘기고, 앱은 0.7초 걸려 답하게 해 두었다.

```bash
# 출력 형식 파일: 각 값은 요청 시작부터 그 단계가 끝날 때까지 누적 시간이다
printf '   namelookup: %%{time_namelookup}s\n      connect: %%{time_connect}s\n   appconnect: %%{time_appconnect}s\nstarttransfer: %%{time_starttransfer}s\n        total: %%{time_total}s\n' > fmt.txt
# 단계별 시각을 찍는다 (-k: 자체 서명 인증서 허용, --resolve: DNS 대신 IP 지정)
curl -sS -k -o /dev/null -w "@fmt.txt" --resolve api.local:8443:127.0.0.1 https://api.local:8443/orders
```

```text
   namelookup: 0.000017s
      connect: 0.000378s
   appconnect: 0.004882s
starttransfer: 0.708584s
        total: 0.708638s
```

값은 누적이라 빼서 읽는다. TCP 연결은 0.4ms, TLS 협상은 `appconnect - connect`로 4.5ms, 서버가 일한 시간은 `starttransfer - appconnect`로 약 0.7초다. "느리다"는 문의가 오면 이 다섯 줄로 어느 구간이 느린지부터 가른다. 연결이 느리면 네트워크나 서버의 accept 대기열 문제이고, 첫 바이트가 느리면 서버 안쪽 문제다.

## 연결이 안 될 때는 커널이 2분 넘게 기다린다

연결 단계의 실패는 두 가지 모양이다. 서버는 살아 있는데 그 포트에 아무도 없으면 커널이 RST로 바로 거절한다. 서버가 꺼졌거나 방화벽이 패킷을 조용히 버리면 아무 대답도 오지 않는다. 실습용 네트워크 네임스페이스에서 81번 포트로 가는 SYN은 버리게(DROP) 해 두고, 82번 포트는 그냥 비워 두었다.

```bash
# 81번: SYN을 버린다(응답 없음), 82번: 듣는 프로세스가 없다(RST)
curl -sS --connect-timeout 2 http://127.0.0.1:81/ ; echo "exit=$?"
curl -sS http://127.0.0.1:82/ ; echo "exit=$?"
```

```text
curl: (28) Failed to connect to 127.0.0.1 port 81 after 2001 ms: Timeout was reached
exit=28
curl: (7) Failed to connect to 127.0.0.1 port 82 after 0 ms: Couldn't connect to server
exit=7
```

거절은 0ms 만에 끝났다. 거절은 오히려 고마운 실패다. 무서운 건 대답이 없는 쪽이다. `--connect-timeout`을 빼고 같은 요청을 보내면 얼마나 기다릴까.

```bash
# 앱 쪽 한도 없이: 커널이 포기할 때까지 기다린다
time curl -sS http://127.0.0.1:81/
```

```text
curl: (28) Failed to connect to 127.0.0.1 port 81 after 133893 ms: Couldn't connect to server

real	2m13.900s
user	0m0.009s
sys	0m0.005s
```

```bash

sudo tcpdump -ni lo -tttt 'tcp port 81'
```

몇 번 보내는지는 `net.ipv4.tcp_syn_retries`(기본 6)가 정한다. 예전 커널은 1, 2, 4, 8, 16, 32초 간격으로 보내고 마지막 64초를 기다려 약 127초 만에 포기했다. 이 컨테이너의 커널(6.18)에는 처음 몇 번을 1초 간격으로 보내는 `tcp_syn_linear_timeouts`(기본 4)가 있어서 134초가 나왔다. 정확한 숫자는 커널 버전마다 다르지만 "앱이 한도를 안 걸면 2분 넘게 묶인다"는 결론은 같다.

```bash
# 현재 커널의 SYN 재전송 설정을 본다 (없는 항목은 그 커널에 없는 설정이다)
sysctl net.ipv4.tcp_syn_retries net.ipv4.tcp_syn_linear_timeouts
```

```text
net.ipv4.tcp_syn_retries = 6
net.ipv4.tcp_syn_linear_timeouts = 4
```

그래서 connect 타임아웃은 앱에서 짧게 건다. 같은 데이터센터 안이라면 연결은 1ms 안쪽에 맺어지니, 수백 ms에서 1~2초면 충분하다. 연결이 1초 넘게 안 맺어진다는 건 상대가 없거나 길이 막혔다는 뜻이고, 더 기다려 봐야 소용이 없다. 라이브러리 기본값은 제각각이다. Node 내장 `fetch`(undici)는 연결에 10초 한도가 있어서 같은 81번 포트로 보내면 이렇게 끝난다.

```text
TypeError: fetch failed / cause: UND_ERR_CONNECT_TIMEOUT after 10594ms
```

Go의 기본 `http.Client`는 전체 한도가 없다. 기본 Transport 값을 찍어 보면 TLS 협상에만 10초가 걸려 있다.

```text
Client.Timeout: 0s
TLSHandshakeTimeout: 10s
ResponseHeaderTimeout: 0s
IdleConnTimeout: 1m30s
ExpectContinueTimeout: 1s
```

`Client.Timeout: 0s`는 무한이다. Go에서 `http.Get`을 그대로 쓰면 서버가 연결만 받아 두고 답을 안 줄 때 요청이 영영 돌아오지 않는다.

## 읽기 타임아웃은 전체 시간이 아니다

연결이 된 뒤의 한도가 더 헷갈린다. 많은 라이브러리의 "타임아웃"은 응답 전체가 아니라 소켓이 조용한 시간을 잰다. 데이터가 한 바이트라도 오면 시계가 처음으로 돌아간다. nginx의 `proxy_read_timeout`이 "두 번 읽는 사이 간격"이라는 건 [nginx 리버스 프록시](/posts/nginx-reverse-proxy) 글에서 다뤘는데, 같은 성질이 Node의 `http.request({ timeout })`, 자바의 소켓 읽기 타임아웃에도 있다.

0.5초마다 점 하나씩, 10초 동안 흘려 보내는 서버를 띄우고 두 가지 한도로 받아 봤다.

```js
// 1) 소켓 유휴 타임아웃 1초
http.get({ port: 18701, path: "/drip", timeout: 1000 }, ...)
// 2) 처음부터 재는 전체 한도 3초
fetch("http://127.0.0.1:18701/drip", { signal: AbortSignal.timeout(3000) })
```

```text
[total 3000ms] TimeoutError: The operation was aborted due to timeout after 3009ms
[idle timeout 1000ms] finished: 21 bytes after 10102ms
```

1초 유휴 타임아웃은 한 번도 걸리지 않고 10초를 다 기다렸다. 점이 0.5초마다 오니 소켓이 1초 동안 조용한 순간이 없었다. 같은 서버를 `proxy_read_timeout 1s`인 nginx 뒤에 둬도 결과는 같다.

```text
200 up=200 rt=10.021 uct=0.000 uht=0.504 urt=10.021 "GET /drip HTTP/1.1"
```

느린 서버는 대개 이렇게 조금씩 보내지 않고 한참 조용하다가 한꺼번에 보낸다. 그래서 평소에는 유휴 타임아웃만으로도 버틴다. 문제는 스트리밍 응답, 큰 파일을 천천히 내려 주는 서버, 그리고 일부러 한 바이트씩 보내 연결을 붙잡는 공격(slowloris의 반대 방향)이다. 사용자가 실제로 기다릴 수 있는 시간을 지키려면 유휴 한도와 함께 처음부터 재는 전체 한도가 있어야 한다. 브라우저와 Node의 `fetch`에서는 `AbortSignal.timeout(ms)`, Go에서는 `context.WithTimeout`, 자바 `HttpClient`에서는 `HttpRequest.timeout()`이 그 역할을 한다.

그림의 숫자는 흔히 보는 기본값이다. 정리하면 이렇다. 표로 모아 두는 이유는 실제로 이 값들을 한 번에 펼쳐 놓고 맞춰 봐야 하기 때문이다.

| 위치 | 설정 | 기본값 | 무엇을 재나 |
|---|---|---|---|
| 브라우저 `fetch` | 없음 | 없음 | `AbortSignal.timeout`으로 직접 건다 |
| axios | `timeout` | 0(무한) | 요청 전체 |
| AWS ALB | idle timeout | 60초 | 연결이 조용한 시간 |
| nginx | `proxy_connect_timeout` | 60초 | 업스트림 연결 맺기 |
| nginx | `proxy_read_timeout` | 60초 | 업스트림에서 두 번 읽는 사이 |
| Node HTTP 서버 | `requestTimeout` | 300초(Node 18부터) | 요청을 다 받기까지 |
| Node HTTP 서버 | `keepAliveTimeout` | 5초 | 응답 뒤 놀고 있는 연결 |
| Node `fetch` | 연결 | 10초 | TCP 연결 맺기 |
| HikariCP | `connectionTimeout` | 30초 | 풀에서 연결을 빌리기까지 |
| PostgreSQL | `statement_timeout` | 0(무한) | 쿼리 하나 |

Node `http.request`의 `req.setTimeout()`은 소켓이 연결된 뒤에야 시계를 켜서 연결 단계를 재지 않는데, 패킷 손실을 넣어 이 차이를 드러낸 실험은 [카오스 엔지니어링](/posts/chaos-engineering)에 있다.

Node HTTP 서버의 값은 직접 찍어 확인했다.

```text
keepAliveTimeout=5000 headersTimeout=60000 requestTimeout=300000 timeout=0
```

## 앞에서 포기해도 뒤에서는 계속 일한다

타임아웃이 끝나면 기다리던 쪽은 연결을 닫는다. 그게 전부다. 안쪽에 "그만해"라는 신호가 따로 가지 않는다. 안쪽이 연결이 닫힌 걸 알아채고 스스로 멈추지 않는 한 일은 계속된다. nginx 앞에서 실험해 보면 바로 보인다. 앱은 3초 걸리는 일을 하고, nginx는 1초만 기다린다.


앱은 1.5초에 연결이 닫힌 걸 이벤트로 받았지만, 하던 일을 멈추는 코드가 없으니 3.5초까지 일했다. Node라면 `req.on("close")`나 `AbortController`로, Go라면 `r.Context().Done()`으로 닫힘을 받아 하던 일을 멈춰야 한다.

DB는 더 둔하다. PostgreSQL은 쿼리를 돌리는 동안 클라이언트 소켓을 들여다보지 않는다. 10초짜리 쿼리를 보낸 psql을 1초 만에 강제로 죽이고, 3초 시점에 `pg_stat_activity`를 봤다.

```sql
-- 클라이언트가 이미 떠난 쿼리가 아직 도는지 본다
SELECT pid, state, now() - query_start AS running, left(query, 30) AS query
FROM pg_stat_activity
WHERE datname = 'v1_timeouts' AND query LIKE '%pg_sleep(10)%' AND pid <> pg_backend_pid();
```

```text
 pid  | state  |     running     |             query              
------+--------+-----------------+--------------------------------
 2948 | active | 00:00:03.015985 | SELECT pg_sleep(10) /* report 
(1 row)
```

쿼리는 10초를 다 채우고, 결과를 보내려는 순간에야 클라이언트가 없다는 걸 알았다. 서버 로그다.

```text
2026-10-20 13:48:49.149 UTC [2948] postgres@v1_timeouts LOG:  could not send data to client: Broken pipe
2026-10-20 13:48:49.149 UTC [2948] postgres@v1_timeouts FATAL:  connection to client lost
```

PostgreSQL 14부터 있는 `client_connection_check_interval`을 켜면 쿼리 도중에도 주기적으로 연결이 살아 있는지 본다(리눅스 같은 일부 OS에서만 동작한다). 1초로 두고 같은 실험을 하면 3초 시점의 조회 결과가 비어 있고, 로그는 2초 무렵에 찍힌다.

```bash
# 이 연결에서만 1초마다 클라이언트 연결을 확인하게 한다
PGOPTIONS='-c client_connection_check_interval=1s' psql -d v1_timeouts -c 'SELECT pg_sleep(10)'
```

```text
2026-10-20 13:48:51.224 UTC [3569] postgres@v1_timeouts FATAL:  connection to client lost
2026-10-20 13:48:51.224 UTC [3569] postgres@v1_timeouts STATEMENT:  SELECT pg_sleep(10) /* report */
```

그래도 기본 방어는 쿼리 쪽 한도다. `statement_timeout`, `lock_timeout`, `idle_in_transaction_session_timeout`을 역할 단위로 거는 방법은 [쿼리 한도와 커넥션 풀](/posts/sql-batch-timeout-pool) 글에 있다. 여기서는 그 값이 앱의 요청 한도보다 짧아야 한다는 것만 확인해 둔다. 이 실습의 세 한도는 각각 이런 메시지로 끝났다.

```text
ERROR:  canceling statement due to statement timeout
ERROR:  canceling statement due to lock timeout
FATAL:  terminating connection due to idle-in-transaction timeout
```

PostgreSQL 17에는 트랜잭션 전체 시간을 재는 `transaction_timeout`이 더해졌다. 16에는 없다.

## 바깥이 안쪽보다 길어야 한다

여기까지 보면 규칙 하나가 나온다. 호출 사슬에서 바깥 한도는 안쪽이 쓸 수 있는 최악의 시간보다 길어야 한다. 반대로 되면 바깥은 포기했는데 안쪽은 일하는 시간이 생긴다. 안쪽이 재시도까지 하면 최악의 시간은 "한도 × 시도 횟수"에 백오프 대기까지 더한 값이다.

## 남은 시간을 넘겨주는 데드라인 전파

고정값을 계층마다 맞추는 방식에는 한계가 있다. 주문 서비스는 자기 앞에서 시간이 얼마나 쓰였는지 모른다. 게이트웨이가 900ms를 쓰고 넘겼든 10ms를 쓰고 넘겼든 똑같이 3초를 기다린다. 그래서 바깥에서 "이 요청은 이 시각까지 끝나야 한다"는 데드라인을 정하고, 호출할 때마다 남은 시간을 함께 넘긴다. 받은 쪽은 남은 시간만큼만 기다리고, 이미 시간이 없으면 일을 시작하지 않는다.

게이트웨이 → 주문 → 재고 세 서비스를 Node로 띄우고 실험했다. 게이트웨이의 예산은 1000ms, 주문 서비스는 DB 작업에 450ms를 쓰고 재고를 부르고, 재고 확인은 800ms 걸린다. 먼저 계층마다 고정값(주문 → 재고 2초)을 쓴 경우다.

```text
    0ms gateway   budget 1000ms (fixed)
  112ms order     got request
  563ms order     db done, calling inventory
  567ms inventory got request, no deadline
 1008ms gateway   gave up: TimeoutError
 1366ms inventory work done
 1391ms order     inventory -> 200
```

게이트웨이는 1008ms에 포기했는데, 재고 서비스는 1366ms까지 일했고 주문 서비스는 1391ms에 아무도 받지 않을 200을 받았다. 이번에는 `x-deadline` 헤더로 절대 시각을 넘기고, 각 서비스가 남은 시간만큼만 기다리게 했다.

```text
    0ms gateway   budget 1000ms (deadline)
  137ms order     got request, 863ms left
  601ms order     db done, calling inventory
  604ms inventory got request, 396ms left
 1004ms order     inventory TimeoutError
 1012ms inventory stopped at deadline
 1020ms gateway   order -> 504
```

재고 서비스는 396ms가 남았다는 걸 알고 시작해서 데드라인에 맞춰 멈췄다. 모든 계층이 1초 언저리에서 함께 정리됐다. 아래 그림이 두 번째 실행을 따라간다.

실제로는 이걸 직접 짜기보다 프레임워크에 맡긴다. gRPC는 클라이언트가 데드라인을 정하면 `grpc-timeout` 헤더로 남은 시간을 넘기고(`850m`은 850밀리초, `2S`는 2초), 서버의 컨텍스트에 그 데드라인이 들어 있다. 서버가 같은 컨텍스트로 다음 호출을 하면 데드라인이 자동으로 이어진다. Go의 `context.WithTimeout`도 같은 원리이고, HTTP 서비스 사이에서는 위처럼 사내 규칙으로 헤더를 정한다.

넘길 때 절대 시각을 보낼지 남은 시간을 보낼지도 골라야 한다. 위 실험은 한 컴퓨터 안이라 절대 시각을 썼다. 서버마다 시계가 조금씩 어긋나 있으면 절대 시각은 그 차이만큼 틀어진다. 시계가 200ms 앞선 서버는 남은 시간을 200ms 적게 본다. gRPC가 남은 시간(상대값)을 보내는 이유가 이것이다. 남은 시간을 보내면 네트워크를 건너는 시간만큼 조금 넉넉해지는 대신 시계 차이의 영향은 받지 않는다. 남은 시간에서 응답을 돌려보낼 여유(수십 ms)를 빼고 넘기는 것도 흔한 방법이다.

데드라인이 들어오면 지켜야 할 것도 있다. 남은 시간이 이미 0 이하면 DB에 쿼리를 보내지 않고 바로 실패한다. 데드라인을 넘겼다는 실패는 재시도할 실패가 아니다. 위에서 다시 보내도 시간은 더 없다.

## keep-alive 유휴 시간이 어긋나면 생기는 502

타임아웃이 짧아서가 아니라 서로 다른 장비의 유휴 한도가 어긋나서 생기는 장애도 있다. 로드 밸런서와 앱 사이의 연결은 재사용된다(keep-alive). 양쪽은 각자 "이 연결이 이만큼 놀면 닫는다"는 한도를 갖고 있다. 앱 쪽 한도가 더 짧으면 앱이 연결을 닫는 순간과 로드 밸런서가 그 연결에 새 요청을 싣는 순간이 겹칠 수 있다.

이 경쟁은 아주 좁은 틈에서 일어나서 로컬에서 재현하기 어렵다. 이 실습에서도 Node 클라이언트로 1초 한도의 서버에 990~1009ms 간격으로 200번 보냈는데 한 번도 걸리지 않았다(Node 클라이언트 쪽 연결 관리가 닫힌 소켓을 미리 걸러 냈다). 실제 서비스에서는 LB와 앱 사이 지연과 트래픽 양 때문에 하루 몇 건씩 나온다. 해법은 정해져 있다. 연결을 먼저 닫는 쪽이 항상 앞단(LB, nginx)이 되도록, 앱의 keep-alive 한도를 앞단보다 길게 둔다. ALB 문서도 앱의 유휴 한도를 LB보다 길게 잡으라고 권한다. nginx 업스트림 keepalive에서 같은 증상을 잡은 로그와 설정은 [nginx 리버스 프록시](/posts/nginx-reverse-proxy) 글에 있다.

## 값을 고르는 순서

숫자를 고를 때는 바깥에서 안으로 내려온다.

1. 사용자가 기다릴 수 있는 시간에서 시작한다. 화면 조회라면 몇 초, 파일 업로드라면 분 단위다. 이게 가장 바깥 데드라인이다.
2. 연결 한도는 짧게 고정한다. 같은 망 안이면 1초 안팎이다. 연결 실패는 빨리 알수록 재시도나 다른 인스턴스로 넘기기 쉽다.
3. 응답 한도는 상대의 지연 분포를 보고 정한다. 평소 p99가 200ms라면 500ms~1초쯤이 출발점이다. 평균으로 정하면 정상 요청이 잘린다.
4. 안쪽 계층의 최악 시간(재시도 포함)이 바깥 한도에 들어가는지 위 함수처럼 계산해 본다.
5. 스트리밍이나 긴 다운로드가 있는 경로는 따로 뺀다. 그 경로만 유휴 한도를 길게 두고, 전체 한도는 다른 수단(최대 크기, 진행률)으로 지킨다.

한도를 너무 짧게 잡아도 문제다. 평소 p99.9가 800ms인 서비스에 500ms 한도를 걸면 정상 요청 0.1% 이상이 실패로 바뀌고, 그 실패가 재시도로 돌아오면 부하가 늘어 지연이 더 길어진다. 타임아웃 비율이 갑자기 오른다면 한도를 늘리기 전에 상대가 왜 느려졌는지부터 본다. 오래 걸리는 게 정상인 작업(리포트 생성, 대량 내보내기)은 한도를 늘리는 대신 202로 바로 답하고 작업은 큐로 넘긴다.

## 504와 끝나지 않는 요청을 만났을 때

현장에서 타임아웃 문제는 대개 세 가지 증상 중 하나로 온다.

응답 시간이 정확히 어떤 숫자(60.0초, 30.0초)에 몰려 있다. 누군가의 기본값이 터진 것이다. nginx 로그에 `$upstream_connect_time`, `$upstream_header_time`, `$upstream_response_time`을 남겨 두면 어디서 끝났는지 바로 보인다. 이 실습의 로그다.

```text
504 up=504 rt=1.001 uct=0.000 uht=- urt=1.001 "GET /read HTTP/1.1"
504 up=504 rt=1.000 uct=- uht=- urt=1.001 "GET /connect HTTP/1.1"
502 up=502 rt=0.000 uct=- uht=- urt=0.000 "GET /refused HTTP/1.1"
```

첫 줄은 연결은 됐고(`uct=0.000`) 헤더를 못 받았다(`uht=-`). 앱이 느리다. 둘째 줄은 연결 시간 자체가 없다(`uct=-`). 앱 인스턴스가 없거나 망이 막혔다. 셋째는 즉시 502, 거절이다.

요청이 끝나지 않고 매달려 있다. 어딘가에 한도가 0인 호출이 있다. 스레드 덤프(`jstack`)나 Node의 `--inspect`로 어디서 기다리는지 보고, HTTP 클라이언트와 DB 드라이버의 한도를 확인한다. axios `timeout: 0`, Go 기본 `http.Client`, 자바 `HttpURLConnection` 기본값이 단골이다.

504가 났는데 DB에서는 같은 쿼리가 여러 개 돌고 있다. 앞단이 포기한 뒤 사용자가 다시 시도해서 쌓인 것이다. `pg_stat_activity`에서 `now() - query_start`가 앱 요청 한도보다 긴 쿼리를 찾고, `statement_timeout`을 요청 한도보다 짧게 건다. 급하면 `pg_cancel_backend(pid)`로 그 쿼리만 멈춘다.

## 면접에서 나올 만한 질문

### connect 타임아웃과 read 타임아웃은 무엇이 다른가

connect 타임아웃은 TCP 연결을 맺기까지, read 타임아웃은 연결된 뒤 응답 데이터를 기다리는 시간을 잰다. 연결은 상대가 살아 있으면 같은 망에서 1ms 안쪽에 끝나니 1초 안팎으로 짧게 잡고, read는 상대의 처리 시간 분포(p99)를 보고 정한다. 앱에서 connect 한도를 안 걸면 대답 없는 서버에 커널이 SYN을 계속 다시 보내며 2분 넘게 기다린다.

### read 타임아웃을 3초로 걸었는데 요청이 10초 걸렸다. 어떻게 가능한가

대부분의 read 타임아웃은 응답 전체가 아니라 두 번 읽는 사이의 간격을 잰다. 서버가 3초가 되기 전에 조금씩 데이터를 보내면 시계가 계속 처음으로 돌아가서 끊기지 않는다. 사용자가 기다리는 시간을 지키려면 `AbortSignal.timeout`이나 `context.WithTimeout`처럼 처음부터 재는 전체 한도를 함께 건다.

### nginx가 504를 돌려줬다. 앱은 그 요청을 멈췄을까

멈추지 않는다. 타임아웃은 기다리던 쪽이 연결을 닫는 것뿐이고, 안쪽은 닫힘을 감지해 스스로 멈추는 코드가 없으면 끝까지 일한다. DB도 마찬가지라 PostgreSQL은 결과를 보내려는 순간에야 클라이언트가 없다는 걸 안다. 그래서 안쪽 한도를 바깥보다 짧게 두고, 연결 닫힘을 받아 작업을 취소하고, DB에는 `statement_timeout`을 건다.

### 여러 계층의 타임아웃은 어떻게 맞춰야 하나

바깥 한도가 안쪽의 최악 시간보다 길어야 한다. 최악 시간에는 재시도 횟수와 백오프 대기도 들어간다. 같은 값도 피하는데, 안쪽이 먼저 끝나야 안쪽이 원인이 담긴 에러를 만들어 돌려줄 수 있기 때문이다. 계층마다 고정값을 맞추는 것보다 나은 방법은 데드라인 전파다.

### 데드라인 전파는 무엇이고 왜 필요한가

가장 바깥에서 요청이 끝나야 하는 시각을 정하고, 호출할 때마다 남은 시간을 함께 넘기는 방식이다. 각 계층은 앞에서 시간이 얼마나 쓰였는지 알고 남은 만큼만 기다리며, 남은 시간이 없으면 일을 시작하지 않는다. 고정 한도로는 바깥이 포기한 뒤에도 안쪽이 일하는 시간을 없앨 수 없는데, 데드라인을 넘기면 모든 계층이 같은 시각에 정리된다. gRPC는 `grpc-timeout` 헤더로 이를 기본 제공한다.

### 데드라인을 넘길 때 절대 시각과 남은 시간 중 무엇을 보내나

서버 사이 시계가 어긋날 수 있으면 남은 시간을 보낸다. 절대 시각은 시계 차이만큼 틀어져서, 시계가 앞선 서버는 시간이 이미 없다고 판단할 수 있다. 남은 시간은 네트워크를 건너는 동안의 시간만큼 조금 넉넉해지는 대신 시계 차이에 영향을 받지 않는다. gRPC가 이 방식을 쓴다.

### 로드 밸런서 뒤에서 간헐적인 502가 나고 앱 로그에는 흔적이 없다. 무엇을 의심하나

keep-alive 유휴 한도가 어긋났을 가능성이 크다. 앱(예를 들어 Node 기본 5초)이 LB(ALB 기본 60초)보다 먼저 놀고 있는 연결을 닫으면, 닫히는 순간 LB가 그 연결에 요청을 실어 RST를 받는다. 앱의 keep-alive 한도를 LB보다 길게 잡아 항상 앞단이 먼저 닫게 한다.
