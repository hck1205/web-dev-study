기획서에 "스크롤하면 제품 소개 페이지처럼 움직이게"라는 한 줄이 적혀 있다. 이 한 줄로는 무엇을 만들지 정할 수 없다. 내리면 제목이 위에 붙는 것인지, 사진이 커지는 것인지, 배경이 느리게 따라오는 것인지, 세로로 내리는데 카드가 옆으로 지나가는 것인지에 따라 쓰는 도구가 다르고 망가지는 방식도 다르다. 스크롤에 반응하는 화면에도 이름이 있다. 이름을 알면 부탁이 짧아지고, 고를 API도 정해진다.

## 스크롤이 무엇을 움직이는지로 나눈다

아홉 가지를 외우기 전에 하나만 묻는다. 스크롤이 화면에 무엇을 시키는가. 답은 세 갈래다.

첫째는 자리를 정하는 규칙이다. 스크롤해도 머리글이 위에 남아 있거나(sticky), 손을 놓으면 카드가 칸에 맞춰 선다(scroll snap). 브라우저의 레이아웃이 스크롤과 함께 알아서 처리하고, 자바스크립트가 필요 없다.

둘째는 경계를 넘는 순간이다. 요소가 화면에 들어오면 한 번 무언가 일어난다. 카드가 떠오르고(scroll triggered, 흔히 scroll reveal), 목록 끝에 닿으면 다음 페이지를 붙인다(infinite scroll). 일어나느냐 마느냐만 있고, 중간값이 없다.

셋째는 스크롤 위치를 시계로 쓰는 것이다. 페이지를 30% 내렸으면 애니메이션도 30% 지점에 있다. 읽은 만큼 차는 막대(scroll driven, 흔히 scroll progress), 다가올수록 커지는 사진(zoom on scroll), 배경이 느리게 따라오는 깊이감(parallax)이 여기에 든다. 다시 올리면 거꾸로 돌아간다.

나머지 둘은 섞은 것이다. horizontal scroll은 sticky로 섹션을 붙잡아 두고 그동안 세로 진행률로 가로 이동을 돌린다. scrollytelling은 sticky로 그림을 붙잡아 두고 글 단계가 경계를 넘을 때마다 그림을 바꾼다.

## 레이아웃에 맡기는 둘

<ScrollDemo
  caption="Sticky는 머리글이 위에 붙었다가 다음 머리글에 밀려난다. Scroll snap은 손을 놓으면 가장 가까운 칸에 선다."
  patterns={["sticky", "scroll-snap"]}
/>

sticky는 평소에는 제자리에 있다가 스크롤 영역의 가장자리에 닿으면 거기 붙는다. 긴 표의 머리글, 연락처 목록의 ㄱ·ㄴ 구분, 글 옆의 목차, 장바구니 합계가 흔한 쓰임이다. 위 그림에서 A가 위에 붙어 있다가 B가 올라오면 밀려 나간다. A가 자기 섹션 안에서만 붙어 있을 수 있어서 생기는 움직임이다.

```css
.section-title {
  position: sticky;
  top: 0; /* 이 값이 없으면 붙지 않는다 */
}
```

scroll snap은 스크롤이 끝나는 자리를 정한다. 카러셀, 사진 넘기기, 화면 하나씩 넘기는 소개 페이지에 쓴다. 예전에는 터치 이벤트로 끝 위치를 계산하는 라이브러리가 필요했지만 지금은 CSS 두 줄이면 된다.

```css
.carousel {
  overflow-x: auto;
  scroll-snap-type: x mandatory; /* 가로로, 반드시 칸에 맞춘다 */
}
.carousel > * {
  scroll-snap-align: center; /* 칸의 가운데를 스크롤 영역 가운데에 맞춘다 */
}
```

둘 다 자주 망가지는 지점이 있다. sticky는 조상 하나에 `overflow: hidden`이 붙으면 조용히 안 붙는다. 붙어 있는 것이 많아지는 것도 문제다. 모바일에서 사이트 헤더, sticky 탭, 하단 고정 버튼이 겹치면 글이 보이는 칸이 화면의 절반으로 준다. snap은 `mandatory`인데 칸이 화면보다 길면 칸 안의 내용을 읽기 어려울 수 있다. 크로미움에서 실제로 재 본 결과와 고치는 법은 [sticky와 scroll-snap](/posts/css-sticky-scroll-snap)에 모았다.

## 선을 넘는 순간 한 번

<ScrollDemo
  caption="Scroll reveal: 카드 윗변이 기준선을 넘어 올라오면 그때 한 번 나타난다."
  patterns={["scroll-reveal"]}
/>

scroll triggered는 "이 요소가 화면에 이만큼 들어오면 한 번 실행"이다. 소개 페이지의 카드가 아래에서 떠오르는 reveal, 화면에 들어온 차트가 그려지기 시작하는 것, 영상이 보이면 재생하고 벗어나면 멈추는 것, 광고 노출 집계가 모두 같은 구조다.

예전에는 스크롤 이벤트마다 모든 카드의 `getBoundingClientRect()`를 불러 위치를 비교했다. 지금은 브라우저에 "이 요소가 화면과 겹치기 시작하면 알려 달라"고 맡긴다. 아래 그림에서 다음을 누르면 그 순서를 따라간다.

```js
const io = new IntersectionObserver(
  (entries) => {
    for (const e of entries) {
      if (!e.isIntersecting) continue;
      e.target.classList.add("is-in"); // 상태만 바꾼다. 움직임은 CSS가 맡는다
      io.unobserve(e.target); // 한 번 나타나면 끝
    }
  },
  { rootMargin: "0px 0px -20% 0px", threshold: 0.1 }, // 화면 아래 20%를 빼고, 10% 보이면
);
document.querySelectorAll(".reveal").forEach((el) => io.observe(el));
```

reveal의 함정은 숨겨 둔 상태가 기본값이라는 데 있다. 스크립트가 늦게 붙거나 오류로 멈추면 내용이 그대로 투명하게 남는다. 그리고 투명해도 그 안의 링크는 살아 있다. 크로미움에서 아직 나타나지 않은 섹션(`opacity: 0`) 안에 링크를 두고 Tab을 두 번 눌러 봤다.

```text
Tab x2 → {
  focused: '숨은 링크',
  sectionOpacity: '0',
  top: 341,
  inViewport: true,
  checkVisibility: true,
  checkVisibilityWithOpacity: false
}
```

포커스는 숨은 링크로 갔고, 브라우저는 그 링크가 보이도록 화면까지 스크롤했다. 그런데 섹션의 `opacity`는 여전히 0이다. 키보드 사용자에게는 포커스 테두리도 글자도 보이지 않는 곳에 커서가 있는 셈이다. `checkVisibility()`가 기본으로 `true`를 돌려주는 것도 눈여겨본다. 불투명도까지 따지려면 `opacityProperty: true`를 줘야 `false`가 나온다.

그래서 기본 스타일은 보이게 두고, 스크립트가 준비됐을 때만 숨긴다.

```css
/* 스크립트가 html에 js 클래스를 붙였을 때만 숨긴다. 실패하면 그냥 보인다 */
.js .reveal:not(.is-in) {
  opacity: 0;
  transform: translateY(24px);
}
.reveal {
  transition: opacity 400ms cubic-bezier(0.22, 1, 0.36, 1), transform 400ms cubic-bezier(0.22, 1, 0.36, 1);
}
```

무한 스크롤도 같은 갈래다. 목록 끝에 보이지 않는 감시용 요소를 두고, 그 요소가 화면 가까이 오면 다음 페이지를 받아 붙인다.

무한 스크롤이 푸터를 삼키고 뒤로 가기에서 위치를 잃는 문제는 [로딩 패턴](/posts/loading-patterns)에서 다뤘다. `rootMargin`으로 미리 불러오는 거리, 문턱값 배열, 관찰을 끊는 시점은 [IntersectionObserver로 만드는 스크롤 트리거](/posts/scroll-triggered-intersection-observer)에서 재 본다.

## 스크롤 위치를 시계로 쓴다

<ScrollDemo
  caption="Progress는 읽은 비율, Zoom은 사진이 다가온 정도, Parallax는 층마다 다른 속도. 셋 다 스크롤 위치가 곧 애니메이션의 현재 시각이다."
  patterns={["scroll-progress", "zoom-on-scroll", "parallax"]}
/>

scroll driven은 스크롤 위치를 0에서 1 사이 진행률로 바꾸고, 그 값을 애니메이션의 현재 시각으로 쓴다. 시간이 흐르면 진행되는 보통 애니메이션과 달리, 사용자가 멈추면 같이 멈추고 올리면 거꾸로 간다. trigger와 가장 크게 다른 점이다. trigger는 한 번 일어나면 끝이고, driven은 스크롤과 계속 묶여 있다.

진행률 계산은 단순하다. 움직일 수 있는 최대 거리는 문서 높이에서 화면 높이를 뺀 값이다.

```js
const max = el.scrollHeight - el.clientHeight; // 끝까지 내렸을 때의 scrollTop
const progress = el.scrollTop / max; // 0 ~ 1
```

이 두 줄에도 함정이 있다. 내용이 화면보다 짧으면 `max`가 0이라 `NaN`이 나온다. iOS 사파리에서 끝을 지나 고무줄처럼 당기면 `scrollTop`이 음수나 최댓값보다 큰 값이 되기도 한다. 화면 배율에 따라 끝까지 내려도 `scrollTop`이 0.5px쯤 모자라서 "99.9%"에서 멈추기도 한다. 아래에서 직접 고쳐 본다.

<CodePlayground
  caption="스크롤 진행률을 0~100 사이, 소수 첫째 자리까지 구한다. 스크롤할 거리가 없으면 0이다."
  functionName="scrollProgress"
  initialCode={`function scrollProgress(scrollTop, scrollHeight, clientHeight) {
  // 움직일 수 있는 최대 거리를 구하고,
  // 0~1로 자른 뒤 백분율(소수 첫째 자리)로 바꾼다
  return scrollTop / (scrollHeight - clientHeight) * 100;
}`}
  solution={`function scrollProgress(scrollTop, scrollHeight, clientHeight) {
  const max = scrollHeight - clientHeight;
  if (max <= 0) return 0; // 스크롤할 거리가 없다

}`}

이 값을 자바스크립트로 매 프레임 계산해서 `transform`에 넣어도 되지만, 크롬 계열에서는 CSS만으로 같은 일을 할 수 있다. 진행 막대는 이렇다.

```css
.reading-bar {
  transform-origin: left;
  animation: grow linear both;
  animation-timeline: scroll(root block); /* 문서의 세로 스크롤을 시계로 쓴다 */
}
@keyframes grow {
  from { transform: scaleX(0); }
  to { transform: scaleX(1); }
}
```

사진이 다가오며 커지는 zoom은 문서 전체가 아니라 그 요소가 화면을 지나가는 구간을 시계로 쓴다. `view()`가 그 구간이고, `animation-range`로 어디부터 어디까지 쓸지 자른다.

```css
.hero-photo {
  animation: zoom-in linear both;
  animation-timeline: view(); /* 이 요소가 화면에 들어와서 나갈 때까지 */
  animation-range: entry 0% cover 50%; /* 들어오기 시작할 때부터 화면 가운데까지만 */
}
@keyframes zoom-in {
  from { transform: scale(0.6); }
  to { transform: scale(1); }
}
```

패럴랙스는 층마다 진행률에 다른 배율을 곱한다. 위 그림에서 점 무늬 배경은 스크롤의 0.3배만 움직이고 글 카드는 1배로 움직인다. 같은 거리를 내렸는데 배경이 덜 움직이니 멀리 있는 것처럼 보인다.

지원 범위는 갈린다. 이 글에서 쓴 크로미움 141은 `CSS.supports("animation-timeline: scroll()")`과 `view()`에 모두 `true`를 돌려준다. 크롬 계열은 115부터 지원하지만 모든 브라우저가 그렇지는 않으니 `@supports`로 감싸고, 지원하지 않으면 정지된 모습이나 IntersectionObserver로 대신한다. 브라우저별 상황과 대체 방법, `animation-range`의 구간 이름은 [스크롤 기반 애니메이션](/posts/scroll-driven-animations)에 정리했다.

scrollytelling은 신문사 데이터 기사에서 많이 보는 형식이다. 그래프가 화면에 붙어 있고, 그 위로 글 단계가 하나씩 지나간다. 단계가 화면 가운데 선을 넘을 때마다 그래프가 강조할 막대나 보여 줄 연도를 바꾼다. sticky와 scroll triggered를 합친 것이다. 각 단계는 IntersectionObserver로 보고, 그래프는 단계 번호 하나만 상태로 갖는다.

섞은 패턴은 망가지는 지점도 두 배다. sticky 쪽에서 오는 문제(조상의 overflow, 모바일 주소창 때문에 바뀌는 `100vh`)와 진행률 쪽 문제(지원 범위, 움직임 줄이기)를 다 안는다. 특히 horizontal scroll은 키보드로 Tab을 누르면 화면 밖 카드로 포커스가 가는데 세로 위치는 그대로여서 포커스가 보이지 않는 경우가 생긴다. `100vh`와 `100dvh`의 차이, 단계 전환 시점 잡기는 [패럴랙스와 스크롤리텔링](/posts/parallax-scrollytelling)에서 다룬다.

크로미움에서 `scrollTo({ top: 3000, behavior: "smooth" })`로 부드럽게 내리면서 세어 보니 프레임 44개 동안 `scroll` 이벤트는 42번 왔고, 한 프레임에 두 번 온 적은 없었다. 이벤트가 쏟아져서 느린 게 아니라는 뜻이다. 느려지는 건 핸들러 안에서 하는 일 때문이다. 흔한 경우가 셋 있다.

- 핸들러가 스타일을 쓴 뒤 바로 `getBoundingClientRect()`나 `offsetTop`을 읽는다. 브라우저가 그 자리에서 레이아웃을 다시 계산해야 한다. 이 현상은 [DOM 기초](/posts/dom-basics)의 강제 동기 레이아웃에서 재 봤다.
- `wheel`이나 `touchmove` 리스너에 `passive: true`가 없다. 브라우저는 핸들러가 `preventDefault()`를 부를지 몰라 스크롤을 시작하기 전에 메인 스레드를 기다린다. 위 그림의 첫 단계가 메인 스레드에 묶이는 셈이다. 자세한 이유는 [이벤트 전파](/posts/event-propagation)의 passive 절에 있다.
- `top`, `height`, `background-position`처럼 레이아웃이나 페인트를 다시 하게 만드는 속성을 움직인다. `transform`과 `opacity`로 바꿀 수 있는지 먼저 본다. 이유는 [애니메이션 성능과 접근성](/posts/animation-performance)에 있다.

스크롤 핸들러를 시간 간격으로 스로틀해야 하는지는 하는 일에 따라 다르다. 화면 갱신이면 어차피 프레임당 한 번이라 의미가 적고, 네트워크 요청이면 시간 기준으로 줄인다. [디바운스와 스로틀](/posts/debounce-throttle)에서 숫자로 비교했다.

## 스크롤이 사람을 괴롭힐 때

스크롤 패턴은 사용자가 시작한 움직임에 반응한다. 그래서 괜찮을 것 같지만, 손가락을 1cm 움직였는데 화면이 그보다 훨씬 크게 움직이면 그 차이가 멀미를 부른다. 전정 기관이 예민한 사람에게 큰 패럴랙스와 화면을 채우는 확대는 몇 초 만에 어지럼증을 일으킨다. WCAG 2.3.3(상호작용으로 생기는 움직임)이 바로 이 경우를 다룬다. 움직임 줄이기 설정을 켠 사람에게는 위치를 시계로 쓰는 효과를 꺼야 한다.

```css
@media (prefers-reduced-motion: reduce) {
  .hero-photo,
  .parallax-layer,
  .reading-bar {
    animation: none; /* 시계로 쓰던 효과를 끈다. 최종 모습이 그대로 보이게 둔다 */
  }
  html {
    scroll-behavior: auto; /* 앵커 이동을 부드럽게 미끄러지지 않고 바로 간다 */
  }
}
```

sticky와 snap은 움직임을 만들지 않으니 그대로 둬도 된다.

더 나쁜 경우는 스크롤 재킹(scroll-jacking)이다. 휠 이벤트를 막고(`preventDefault()`) 스크립트로 직접 스크롤 위치를 옮기는 방식이다. 휠 한 칸에 화면 하나씩 넘기거나, 스크롤 속도를 바꾸려고 쓴다.

```js
// 하지 말아야 할 모양: 휠을 막고 직접 옮긴다
addEventListener("wheel", (e) => {
  e.preventDefault(); // passive: false가 필요하고, 스크롤이 메인 스레드에 묶인다
  goToSection(current + Math.sign(e.deltaY));
}, { passive: false });
```

이렇게 하면 트랙패드 관성이 사라지고, Space·PageDown·방향키가 따로 놀고, 화면 확대 기능을 쓰는 사람의 스크롤이 엉뚱하게 튄다. 브라우저가 지켜 주던 것을 전부 직접 다시 만들어야 하는데 대개 일부만 만든다. 화면 하나씩 넘기는 게 정말 필요하면 `scroll-snap-type: y mandatory`가 낫다. 브라우저가 스크롤을 그대로 다루면서 끝나는 자리만 정하기 때문에 키보드도 칸 단위로 움직인다.

마지막은 보이지 않는 내용이다. 앞에서 본 것처럼 reveal 전의 내용은 투명하지만 포커스를 받는다. 찾기에도 걸린다. 크로미움에서 비표준 함수 `window.find()`로 숨긴 방식마다 문장을 찾아 봤다.

```text
opacity: 0           { found: true }
visibility: hidden   { found: false }
display: none        { found: false }
```

`opacity: 0`인 문장만 찾았고, 찾은 자리로 스크롤까지 했다. 페이지 내 찾기(Ctrl+F)도 투명한 글자를 찾는다고 보고 만드는 편이 안전하다. 그러면 사용자는 찾았다는 표시만 있고 글자는 없는 화면을 본다. 내용을 숨기는 효과는 "기본은 보이고, 스크립트가 숨긴다"는 순서를 지키고, 효과가 끝나지 않아도 읽을 수 있게 만든다.

## 패턴마다 고르는 도구

| 패턴 | 기본 도구 | 자바스크립트 없이 | 움직임 줄이기 |
|---|---|---|---|
| Sticky | `position: sticky` | 된다 | 그대로 |
| Scroll snap | `scroll-snap-type`, `scroll-snap-align` | 된다 | 그대로 |
| Scroll reveal | `IntersectionObserver` + CSS 전환 | `view()` 타임라인으로 가능(지원 브라우저) | 바로 보이게 |
| Infinite scroll | `IntersectionObserver` + 감시용 요소 | 안 된다(데이터를 받아야 한다) | 해당 없음 |
| Scroll progress | `animation-timeline: scroll()` | 된다(지원 브라우저) | 숨기거나 정지 |
| Zoom on scroll | `animation-timeline: view()` | 된다(지원 브라우저) | 끈다 |
| Parallax | `view()`·`scroll()` + `transform` | 된다(지원 브라우저) | 끈다 |
| Horizontal scroll | sticky + `view-timeline` | 된다(지원 브라우저) | 세로 목록으로 |
| Scrollytelling | sticky + `IntersectionObserver` | 안 된다(단계 상태가 필요) | 전환만 즉시 |

"지원 브라우저"라고 적은 칸은 scroll 타임라인을 지원하지 않는 브라우저에서 IntersectionObserver나 `requestAnimationFrame` 방식으로 대신하거나, 효과 없이 최종 모습만 보여 준다.

## 증상에서 거꾸로 찾아가기

"sticky를 줬는데 같이 올라가 버린다"면 조상 중에 `overflow`가 `visible`이 아닌 요소가 있는지부터 본다. 가로 넘침을 막으려고 감싼 `overflow-x: hidden` 하나가 범인인 경우가 많다. 개발자 도구 콘솔에서 조상을 거슬러 올라가며 찾는 코드와 실제 측정 값은 [sticky와 scroll-snap](/posts/css-sticky-scroll-snap)에 있다.

"스크롤할 때 진행 막대가 페이지보다 늦게 따라온다"면 성능 패널에서 스크롤하는 동안 기록을 남기고, 메인 스레드에 `scroll` 이벤트 핸들러와 그 아래 Layout이 프레임마다 쌓이는지 본다. 막대를 CSS `scroll()` 타임라인으로 옮기면 메인 스레드가 바빠도 같은 프레임에 움직인다.

"아이폰에서만 패럴랙스 배경이 안 움직인다"면 `background-attachment: fixed`로 만든 패럴랙스일 가능성이 높다. iOS 사파리는 오랫동안 이 값을 `scroll`처럼 처리해 왔다. 배경을 별도 층으로 빼서 `transform`으로 움직인다.

"스크롤하면 내용이 조금씩 튄다"면 reveal이 `transform` 대신 `margin-top`이나 `height`를 바꾸는지 본다. 레이아웃 속성을 바꾸면 아래 내용이 밀리고, 이 밀림은 [Core Web Vitals](/posts/core-web-vitals)의 CLS 점수에도 잡힐 수 있다.

## 다시 기획서의 한 줄로

"제품 소개 페이지처럼"을 받으면 화면마다 세 질문을 던진다. 스크롤이 자리를 정하나, 경계를 넘는 순간 한 번 일어나나, 위치가 곧 시계인가. 답이 정해지면 sticky·snap은 CSS로, 경계는 IntersectionObserver로, 시계는 scroll 타임라인으로 만든다. 그리고 셋 모두에 같은 조건을 붙인다. 움직임 줄이기를 켜면 끄고, 스크립트가 실패해도 내용이 보이고, 휠과 키보드는 브라우저 그대로 둔다.

## 면접에서 나올 만한 질문

### scroll triggered와 scroll driven 애니메이션의 차이는 무엇인가요?

trigger는 요소가 경계를 넘는 순간 한 번 실행되고, driven은 스크롤 위치가 애니메이션의 현재 시각이 된다. 그래서 trigger는 일단 시작하면 시간에 따라 끝까지 재생되고, driven은 사용자가 멈추면 멈추고 올리면 거꾸로 돈다. trigger는 IntersectionObserver로, driven은 `animation-timeline: scroll()`·`view()`로 만든다.

### 스크롤 이벤트 리스너로 reveal을 만들면 무엇이 문제인가요?

스크롤하는 동안 프레임마다 모든 대상의 위치를 읽어야 하고, 그 사이에 스타일을 쓰면 강제 동기 레이아웃이 생긴다. IntersectionObserver는 브라우저가 렌더링 단계에서 겹침을 계산하고, 문턱값을 넘은 요소만 모아서 알려 준다. 핸들러가 매 프레임 돌지 않으니 메인 스레드가 가볍다. 한 번 나타난 요소는 `unobserve`로 빼서 계산 대상을 줄인다.

### 스크롤 핸들러를 requestAnimationFrame으로 감싸면 호출 횟수가 줄어드나요?

크롬 계열에서는 거의 줄지 않는다. `scroll` 이벤트가 이미 그리기 직전 단계에서 프레임당 최대 한 번 오기 때문이다. rAF로 감싸는 의미는 횟수 절감보다 DOM 쓰기를 그리기 직전으로 모으는 데 있다. 무거운 계산이나 요청을 줄이려면 시간 기준 스로틀을 쓴다.

### scroll 타임라인 애니메이션이 스크롤 리스너보다 부드러운 이유는요?

크로미움에서는 `transform`과 `opacity`를 움직이는 scroll 타임라인 애니메이션을 합성 스레드에서 돌린다. 스크롤 자체도 합성 스레드가 처리하니 진행률 계산과 적용이 같은 프레임에 끝난다. 리스너 방식은 메인 스레드를 거쳐야 해서, 메인 스레드가 긴 작업에 막히면 페이지는 내려갔는데 효과만 늦게 따라온다.

### 스크롤 재킹은 무엇이고 왜 피하나요?

휠·터치 이벤트를 `preventDefault()`로 막고 스크립트로 스크롤 위치를 직접 옮기는 방식이다. 관성 스크롤, 키보드 스크롤, 화면 확대, 페이지 내 찾기처럼 브라우저가 기본으로 해 주던 동작을 잃고, 리스너가 passive일 수 없어 스크롤이 메인 스레드에 묶인다. 화면 단위로 넘겨야 하면 `scroll-snap-type: y mandatory`처럼 브라우저의 스크롤을 그대로 두고 끝 위치만 정하는 방법을 쓴다.

### reveal 애니메이션에서 접근성 문제가 생기는 지점은 어디인가요?

숨긴 상태가 기본값이면 스크립트가 늦거나 실패할 때 내용이 투명하게 남는다. 투명한 요소는 여전히 포커스를 받고 페이지 내 찾기에도 걸려서, 키보드 사용자는 보이지 않는 곳에 포커스가 가 있게 된다. 스크립트가 준비됐을 때만 숨기는 클래스를 붙이고, `prefers-reduced-motion`에서는 움직임 없이 바로 보이게 한다.

### 패럴랙스를 움직임 줄이기 설정에서 꺼야 하는 이유는 사용자가 직접 스크롤했기 때문에 괜찮지 않나요?

사용자가 시작한 움직임이어도 입력보다 훨씬 크거나 다른 방향으로 화면이 움직이면 전정 장애가 있는 사람에게 어지럼증을 일으킨다. WCAG 2.3.3이 상호작용으로 생기는 움직임을 끌 수 있게 하라고 정한 이유다. 그래서 패럴랙스와 확대는 `prefers-reduced-motion: reduce`에서 끄고 최종 모습만 보여 준다. 움직임을 만들지 않는 sticky와 snap은 그대로 둔다.
