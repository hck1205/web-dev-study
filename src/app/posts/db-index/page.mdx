마이페이지의 주문 내역 화면은 쿼리 하나로 끝난다. `SELECT * FROM orders WHERE user_id = 42`. 서비스 초기에 주문이 몇천 건일 때는 아무도 이 쿼리를 신경 쓰지 않았다. 주문이 100만 건을 넘기자 같은 쿼리가 35ms씩 걸리기 시작한다. 한 번이면 참을 만한데, 마이페이지는 초당 수백 번 열린다. DB 서버의 CPU가 이 쿼리 하나로 차오른다.

이 쿼리는 회원 한 명의 주문 8건을 찾으려고 주문 100만 건을 전부 읽고 있었다. 두꺼운 책에서 "B-tree"라는 단어가 나오는 쪽을 찾으려고 첫 쪽부터 끝까지 넘기는 것과 같다. 보통은 책 뒤의 찾아보기를 편다. 단어가 가나다순으로 정렬돼 있고 옆에 쪽수가 적혀 있다. 인덱스가 바로 이 찾아보기다. 이 글은 이 비유 하나로 끝까지 간다.

기준은 Ubuntu 24.04에 설치한 PostgreSQL 16(16.15)이다. 아래에 나오는 실행 계획은 모두 이 환경에서 실제로 돌린 출력이다. 시간(ms)은 장비와 캐시 상태에 따라 달라지니 자릿수만 보면 된다. MySQL 8과 다른 부분은 마지막에 따로 모았다.

## 실험에 쓸 작은 쇼핑몰

글 전체에서 같은 테이블 세 개를 쓴다. 회원(`users`), 상품(`products`), 주문(`orders`)이다.

```sql
-- 회원
CREATE TABLE users (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- 1, 2, 3 ... 자동 증가
  email      text NOT NULL,
  name       text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

-- 상품
CREATE TABLE products (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  text NOT NULL,
  price integer NOT NULL
);

-- 주문: 누가(user_id) 무엇을(product_id) 얼마에(amount) 샀나
CREATE TABLE orders (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    bigint NOT NULL REFERENCES users (id),
  product_id bigint NOT NULL REFERENCES products (id),
  status     text NOT NULL,          -- pending, paid, delivered, cancelled
  amount     integer NOT NULL,
  created_at timestamptz NOT NULL
);
```

처음에는 몇 줄만 넣는다. 회원 셋, 상품 셋, 주문 다섯 건이다.

```sql
INSERT INTO users (email, name, created_at) VALUES

  ('lee@example.com',  'lee',  '2025-10-02 10:30+09'),
  ('park@example.com', 'park', '2025-10-03 14:10+09');

INSERT INTO products (name, price) VALUES
  ('무선 이어폰', 39000),
  ('충전 케이스', 15000),
  ('이어팁', 5000);

  (1, 1, 'delivered', 39000, '2025-10-27 11:00+09'),
  (1, 3, 'delivered',  5000, '2025-10-27 11:00+09'),
  (2, 2, 'paid',      15000, '2025-10-28 20:15+09'),
  (3, 1, 'cancelled', 39000, '2025-10-29 08:40+09'),
  (1, 2, 'pending',   15000, '2025-10-30 23:05+09');

SELECT * FROM orders ORDER BY id;
```

다섯 줄짜리 테이블에서는 인덱스가 있든 없든 차이가 없다. 그래서 `generate_series`로 회원 10만 명, 상품 1,000개, 주문 100만 건까지 채운다. `generate_series(4, 100000)`은 4부터 100000까지 숫자를 한 줄씩 만들어 주는 함수다. 그 숫자로 이메일과 시간을 만든다.

```sql
SELECT setseed(0.42);  -- random() 결과를 매번 같게 고정한다

-- 회원 4번 ~ 100000번
INSERT INTO users (email, name, created_at)
SELECT 'user' || i || '@example.com',
       'user' || i,
       timestamptz '2025-10-04 00:00+09' + i * interval '1 minute'
FROM generate_series(4, 100000) AS i;

-- 상품 4번 ~ 1000번
INSERT INTO products (name, price)
SELECT '상품 ' || i, (1 + floor(random() * 100)::int) * 1000
FROM generate_series(4, 1000) AS i;

-- 주문 6번 ~ 1000000번: 30초마다 한 건, 회원과 상품은 무작위
INSERT INTO orders (user_id, product_id, status, amount, created_at)
SELECT 1 + floor(random() * 100000)::bigint,
       1 + floor(random() * 1000)::bigint,
       CASE WHEN r < 0.80 THEN 'delivered'   -- 80%
            WHEN r < 0.94 THEN 'paid'        -- 14%
            WHEN r < 0.99 THEN 'cancelled'   -- 5%
            ELSE 'pending' END,              -- 1%
       (1 + floor(random() * 100)::int) * 1000,
       timestamptz '2025-10-31 00:00+09' + i * interval '30 seconds'
FROM (SELECT i, random() AS r FROM generate_series(6, 1000000) AS i) AS s;

VACUUM ANALYZE;  -- 통계를 모으고 정리한다
```

```sql
SELECT status, count(*) FROM orders GROUP BY status ORDER BY status;
```

```text

-----------+--------

(4 rows)
```

## 100만 줄을 처음부터 끝까지 읽는 계획

쿼리 앞에 `EXPLAIN`을 붙이면 DB가 이 쿼리를 어떻게 실행할지(실행 계획)를 보여 준다. `ANALYZE`를 더하면 실제로 실행하고 걸린 시간과 행 수를 함께 적는다. `BUFFERS`는 메모리나 디스크에서 페이지를 몇 개 읽었는지 보여 준다. 성능을 볼 때는 이 셋을 같이 쓴다.

```sql
-- 실제로 실행하고, 읽은 페이지 수까지 보여 달라
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id = 42;
```

```text
                                                     QUERY PLAN
---------------------------------------------------------------------------------------------------------------------
 Gather  (cost=1000.00..15555.43 rows=11 width=45) (actual time=2.877..35.116 rows=8 loops=1)
   Workers Planned: 2
   Workers Launched: 2
   Buffers: shared hit=9346
   ->  Parallel Seq Scan on orders  (cost=0.00..14554.33 rows=5 width=45) (actual time=5.122..28.438 rows=3 loops=3)
         Filter: (user_id = 42)
         Rows Removed by Filter: 333331
         Buffers: shared hit=9346
 Planning:
   Buffers: shared hit=72
 Planning Time: 0.308 ms
 Execution Time: 35.175 ms
(12 rows)
```

실행 계획은 나무 모양이다. `->`로 들여 쓴 줄이 안쪽 단계이고, 안쪽부터 실행해서 결과를 바깥으로 올린다. 여기서는 `Parallel Seq Scan`이 테이블을 읽고, 바깥의 `Gather`가 워커들의 결과를 모은다. PostgreSQL은 큰 테이블을 통째로 읽을 때 워커 프로세스를 여러 개 띄워 나눠 읽는다. 지금은 워커 2개와 원래 프로세스, 합쳐서 셋이 나눠 읽었다.

Seq Scan(순차 스캔)은 테이블의 페이지를 처음부터 끝까지 읽으면서 행마다 조건을 검사한다. 책을 첫 쪽부터 넘기는 방법이다. 줄 하나에 정보가 많이 담겨 있으니 조각으로 나눠 읽어 보자. 아래 줄의 조각을 눌러 보면 각각 무슨 뜻인지 나온다.

나머지 줄도 하나씩 보면 이렇다.

`Rows Removed by Filter: 333331`은 조건에 맞지 않아 버린 행 수다(이것도 루프당 평균). 셋이 합쳐 100만 행을 검사해서 8행을 남기고 나머지를 다 버렸다. 버린 행이 결과보다 압도적으로 많으면 인덱스가 필요하다는 신호다.

`Buffers: shared hit=9346`은 PostgreSQL의 메모리 캐시(shared buffers)에서 페이지 9,346개를 읽었다는 뜻이다. PostgreSQL은 테이블을 8KB짜리 페이지로 나눠 저장한다. `orders` 테이블은 73MB, 페이지로는 정확히 9,346개다. 테이블 전체를 한 번씩 다 읽은 것이다. `hit`은 캐시에 있었다는 뜻이고, 캐시에 없어서 운영체제에 요청했으면 `read`로 따로 센다. 지금은 테이블이 전부 캐시에 올라와 있어서 35ms로 끝났다. 디스크에서 읽어야 했다면 훨씬 오래 걸렸을 것이다.

```sql
-- 테이블이 몇 페이지인지는 pg_class에 있다
SELECT relpages, pg_size_pretty(pg_relation_size('orders')) AS size
FROM pg_class WHERE relname = 'orders';
```

```text
 relpages | size
----------+-------
     9346 | 73 MB
(1 row)
```

정리하면 이 쿼리는 8행을 위해 9,346페이지를 읽었다. 시간은 캐시 상태에 따라 오르내리지만, 읽은 페이지 수는 데이터가 같으면 그대로다. 그래서 튜닝할 때는 시간보다 `Buffers`가 더 믿을 만한 숫자다.

## 찾아보기를 하나 만들면

`user_id`에 인덱스를 만든다.

```sql
-- orders.user_id 값으로 찾는 찾아보기를 만든다
CREATE INDEX orders_user_id_idx ON orders (user_id);

-- 인덱스 크기
SELECT pg_size_pretty(pg_relation_size('orders_user_id_idx'));
```

```text
 pg_size_pretty
----------------
 9088 kB
(1 row)
```

같은 쿼리를 다시 본다. 아래는 캐시가 데워진 상태에서 두 번째로 돌린 출력이다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id = 42;
```

```text
                                                         QUERY PLAN
----------------------------------------------------------------------------------------------------------------------------
 Bitmap Heap Scan on orders  (cost=4.51..47.52 rows=11 width=45) (actual time=0.020..0.032 rows=8 loops=1)
   Recheck Cond: (user_id = 42)
   Heap Blocks: exact=8
   Buffers: shared hit=11
   ->  Bitmap Index Scan on orders_user_id_idx  (cost=0.00..4.51 rows=11 width=0) (actual time=0.013..0.014 rows=8 loops=1)
         Index Cond: (user_id = 42)
         Buffers: shared hit=3
 Planning Time: 0.062 ms
 Execution Time: 0.047 ms
(9 rows)
```

먼저 볼 숫자는 `Buffers`다. 9,346에서 11로 줄었다. 시간은 35ms에서 0.05ms가 됐다. 비용 추정도 15555에서 47.52로 줄어서, 플래너가 이 계획을 고른 이유가 보인다.

읽은 11페이지를 나눠 보면 이렇다. 안쪽의 `Bitmap Index Scan`이 인덱스에서 3페이지를 읽고(`Buffers: shared hit=3`), 바깥의 `Bitmap Heap Scan`이 테이블에서 8페이지를 읽었다(`Heap Blocks: exact=8`). 주문 8건이 서로 다른 페이지 8곳에 흩어져 있어서다. `Filter`와 `Rows Removed by Filter`가 사라지고 `Index Cond`가 생긴 것도 봐 둔다. 조건을 행마다 검사해서 버린 게 아니라, 인덱스에서 바로 맞는 위치만 찾았다는 뜻이다.

인덱스에서 3페이지를 읽어서 어떻게 주문 8건의 위치를 알았을까. 인덱스 안을 열어 보면 알 수 있다.

## B-tree는 세 번 만에 잎에 닿는다

`CREATE INDEX`는 따로 지정하지 않으면 B-tree 인덱스를 만든다. B-tree는 정렬된 값을 페이지 단위로 나눠 담고, 그 위에 "어느 페이지에 어디부터 어디까지 있다"는 안내 페이지를 층층이 쌓은 나무다. 맨 위가 루트, 맨 아래가 잎(leaf), 사이가 중간 페이지다.

책 찾아보기에 비유하면 잎 페이지가 찾아보기 본문이다. `user_id` 값이 정렬돼 있고, 값마다 그 행이 테이블의 어디에 있는지 적혀 있다. 이 위치를 ctid라고 부른다. `(470,90)`이면 테이블의 470번 페이지, 90번째 칸이라는 뜻이다. 찾아보기의 쪽수에 해당한다. 테이블 본체는 인덱스와 구분해서 힙(heap)이라고 부른다. 행이 정렬되지 않고 들어온 순서대로 쌓여 있어서 붙은 이름이다.

```sql
-- 회원 42번 주문이 힙의 어디에 있는지
SELECT ctid, id FROM orders WHERE user_id = 42 ORDER BY id;
```

```text
   ctid    |   id
-----------+--------
 (470,90)  |  50380
 (622,9)   |  66563
 (1735,41) | 185686
 (2634,28) | 281866
 (2805,4)  | 300139
 (6058,86) | 648292
 (7031,12) | 752329
 (9334,15) | 998753
(8 rows)
```

인덱스 구조는 `pageinspect` 확장으로 직접 들여다볼 수 있다. 슈퍼유저만 쓸 수 있으니 실습용 DB에서만 쓴다.

```sql
CREATE EXTENSION pageinspect;

-- 루트 페이지 번호와 나무 높이 (level 2 = 루트 아래로 두 층)
SELECT root, level FROM bt_metap('orders_user_id_idx');

-- 페이지 종류별 개수 (l = 잎, i = 중간, r = 루트)
SELECT count(*) FILTER (WHERE type = 'l') AS leaf_pages,
       count(*) FILTER (WHERE type = 'i') AS internal_pages,
       count(*) FILTER (WHERE type = 'r') AS root_pages
FROM generate_series(1, 1135) AS b, bt_page_stats('orders_user_id_idx', b);
```

```text
 root | level
------+-------
  290 |     2
(1 row)

 leaf_pages | internal_pages | root_pages
------------+----------------+------------
       1130 |              4 |          1
(1 row)
```

루트 1페이지, 중간 4페이지, 잎 1,130페이지다. 루트에는 경계값이 세 개 있다. 16진수로 저장돼 있는데 풀면 25143, 50318, 75490이다. "25143보다 작으면 첫 번째 중간 페이지로, 50318보다 작으면 두 번째로" 같은 안내다. 아래 그림에서 다음을 누르면 `user_id = 42`를 찾아 내려가는 과정이 나온다.

100만 행인데 나무 높이가 겨우 3층인 이유는 페이지 하나에 경계값이 수백 개 들어가기 때문이다. 한 층 내려갈 때마다 범위가 수백분의 1로 좁아진다. 이 인덱스는 루트에서 4갈래, 중간에서 각각 약 285갈래로 나뉘어 잎 1,130개에 닿는다. 행이 수억 개로 늘어도 4~5층이면 된다. 찾는 비용이 행 수 n에 비례하지 않고 log n에 비례한다는 말이 이 뜻이다.

잎 페이지끼리는 옆으로도 이어져 있다. `user_id BETWEEN 40 AND 200` 같은 범위 조건이면 시작 잎을 찾은 다음 옆 잎으로 넘어가며 읽으면 된다. 값이 정렬돼 있으니 `ORDER BY user_id`도 정렬 없이 잎을 순서대로 읽어서 해결된다. 해시 인덱스는 이 두 가지를 못 한다. B-tree가 기본값인 이유다.

## 같은 인덱스를 읽는 네 가지 방법

앞에서 나온 `Bitmap Heap Scan`은 인덱스를 쓰는 방법 중 하나다. 플래너는 몇 행이 나올지 예상해서 넷 중 하나를 고른다.

Index Scan은 인덱스에서 하나 찾을 때마다 바로 힙에 가서 행을 가져온다. 결과가 한두 행일 때 흔하다. 기본 키로 찾으면 이렇게 나온다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE id = 500000;
```

```text
                                                     QUERY PLAN
---------------------------------------------------------------------------------------------------------------------
 Index Scan using orders_pkey on orders  (cost=0.42..8.44 rows=1 width=45) (actual time=0.010..0.011 rows=1 loops=1)
   Index Cond: (id = 500000)
   Buffers: shared hit=4
 Planning Time: 0.017 ms
 Execution Time: 0.019 ms
(5 rows)
```

인덱스 3층에 힙 1페이지, 합쳐서 4페이지다. `PRIMARY KEY`를 선언하면 PostgreSQL이 `orders_pkey`라는 유니크 인덱스를 자동으로 만든다.

Bitmap Heap Scan은 결과가 수십~수천 행일 때 나온다. 인덱스로 찾은 위치를 바로 따라가지 않고, 먼저 모아서 페이지 번호 순으로 정렬한다(비트맵). 그다음 힙을 앞에서 뒤로 한 번에 읽는다. 같은 페이지에 행이 여러 개 있으면 그 페이지를 한 번만 읽으면 되고, 디스크에서도 앞뒤로 왔다 갔다 하지 않는다. 아래 그림에서 다음을 누르면 순서가 나온다.

Index Only Scan은 힙을 아예 안 간다. 쿼리가 필요로 하는 컬럼이 모두 인덱스 안에 있을 때 가능하다. 회원 42번의 주문 개수만 세면 `user_id` 말고는 필요한 게 없다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders WHERE user_id = 42;
```

```text
                                                              QUERY PLAN
---------------------------------------------------------------------------------------------------------------------------------------
 Aggregate  (cost=4.64..4.65 rows=1 width=8) (actual time=0.022..0.023 rows=1 loops=1)
   Buffers: shared hit=4
   ->  Index Only Scan using orders_user_id_idx on orders  (cost=0.42..4.62 rows=11 width=0) (actual time=0.016..0.018 rows=8 loops=1)
         Index Cond: (user_id = 42)
         Heap Fetches: 0
         Buffers: shared hit=4
 Planning:
   Buffers: shared hit=6
 Planning Time: 0.049 ms
 Execution Time: 0.033 ms
(10 rows)
```

여기서 볼 줄은 `Heap Fetches: 0`이다. PostgreSQL은 한 행의 여러 버전을 힙에 두고(MVCC), 지금 트랜잭션에서 그 행이 보여도 되는지는 힙에만 적어 둔다. 인덱스만 보고는 그 행이 아직 살아 있는지 모른다. 그래서 가시성 맵(visibility map)을 본다. 페이지마다 "이 페이지의 모든 행은 모두에게 보인다"는 표시가 있고, 표시가 켜진 페이지는 힙을 건너뛴다. 이 표시는 `VACUUM`이 켠다. 수정이 잦은 테이블에서 VACUUM이 밀리면 `Heap Fetches`가 늘어나고, Index Only Scan이 이름과 달리 힙을 많이 읽는다. 위에서 4페이지는 인덱스 3페이지와 가시성 맵 1페이지다.

마지막은 Seq Scan이다. 인덱스가 있어도 결과가 테이블의 큰 부분이면 플래너는 그냥 처음부터 읽는다. 언제 그렇게 되는지는 [인덱스가 안 타는 이유 글](/posts/db-index-pitfalls)에서 다시 본다.

## MySQL 8은 표 자체가 인덱스다

MySQL의 기본 저장 엔진인 InnoDB는 테이블을 저장하는 방식부터 다르다. PostgreSQL은 행을 힙에 들어온 순서대로 쌓고, 인덱스는 모두 ctid로 힙을 가리킨다. 기본 키 인덱스도 다른 인덱스와 다를 게 없다. InnoDB는 테이블 자체가 기본 키로 정렬된 B-tree다. 기본 키 인덱스의 잎에 행 전체가 들어 있어서 클러스터드 인덱스라고 부른다. 기본 키가 없으면 NOT NULL인 첫 유니크 인덱스를, 그것도 없으면 숨은 6바이트 행 번호를 기본 키로 쓴다.

그러면 `user_id` 같은 보조 인덱스(secondary index)의 잎에는 무엇이 들어 있을까. 위치 대신 그 행의 기본 키 값이 들어 있다. 보조 인덱스로 찾으면 기본 키를 얻고, 그 기본 키로 클러스터드 인덱스를 한 번 더 내려가야 행이 나온다.

기본 키로 찾는 게 가장 빠르고, 기본 키 범위 조회는 행이 물리적으로 붙어 있어서 특히 빠르다. 보조 인덱스에는 기본 키가 공짜로 따라오니 `SELECT id FROM orders WHERE user_id = 42`는 따로 설정하지 않아도 커버링이다. MySQL은 `INCLUDE` 문법이 없어서, 다른 컬럼을 커버링하려면 인덱스 컬럼 끝에 붙인다.

기본 키를 무작위 UUID로 잡으면 아프다. 새 행이 B-tree의 아무 데나 끼어드니 꽉 찬 페이지가 계속 쪼개지고, 페이지가 반쯤 빈 채로 흩어져 테이블이 커진다. 최근에 쓴 페이지만 메모리에 두면 되던 것이 테이블 전체를 메모리에 올려야 하는 상황이 된다. 게다가 보조 인덱스마다 기본 키가 복사되니, 8바이트 `BIGINT` 대신 36자 문자열 UUID를 쓰면 모든 보조 인덱스가 같이 커진다. 순서대로 늘어나는 `BIGINT AUTO_INCREMENT`를 쓰거나, UUID가 꼭 필요하면 시간 순으로 커지는 UUIDv7을 `BINARY(16)`으로 저장한다. PostgreSQL은 힙이 정렬되지 않아 덜 아프지만, 기본 키 인덱스 자체는 같은 이유로 흩어지고 커진다. PostgreSQL 18부터는 `uuidv7()` 함수가 들어 있다.

실행 계획 모양도 다르다. MySQL의 기본 `EXPLAIN`은 표로 나온다. 아래는 같은 쿼리를 인덱스 전후로 본 예시 출력이다.

```sql
-- MySQL 8
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
```

```text
-- 인덱스 없음 (예시 출력)
+----+-------------+--------+------------+------+---------------+------+---------+------+--------+----------+-------------+
| id | select_type | table  | partitions | type | possible_keys | key  | key_len | ref  | rows   | filtered | Extra       |
+----+-------------+--------+------------+------+---------------+------+---------+------+--------+----------+-------------+
|  1 | SIMPLE      | orders | NULL       | ALL  | NULL          | NULL | NULL    | NULL | 996520 |    10.00 | Using where |
+----+-------------+--------+------------+------+---------------+------+---------+------+--------+----------+-------------+

-- idx_user_id 생성 후 (예시 출력)
+----+-------------+--------+------------+------+---------------+-------------+---------+-------+------+----------+-------+
| id | select_type | table  | partitions | type | possible_keys | key         | key_len | ref   | rows | filtered | Extra |
+----+-------------+--------+------------+------+---------------+-------------+---------+-------+------+----------+-------+
|  1 | SIMPLE      | orders | NULL       | ref  | idx_user_id   | idx_user_id | 8       | const |    8 |   100.00 | NULL  |
+----+-------------+--------+------------+------+---------------+-------------+---------+-------+------+----------+-------+
```

`type` 열부터 본다. `ALL`은 테이블 전체 스캔, `index`는 인덱스 전체 스캔, `range`는 인덱스 범위, `ref`는 인덱스로 같은 값 찾기, `eq_ref`와 `const`는 유니크하게 한 행 찾기다. 뒤로 갈수록 좋다. `rows`는 예상치이고, `key_len`은 복합 인덱스에서 몇 번째 컬럼까지 썼는지 가늠하는 데 쓴다. `Extra`의 `Using index`는 커버링(PostgreSQL의 Index Only Scan), `Using filesort`는 인덱스로 정렬을 못 해 따로 정렬했다는 뜻이다.

MySQL 8.0.18부터는 `EXPLAIN ANALYZE`가 있고, PostgreSQL처럼 나무 모양으로 실제 시간과 행 수를 보여 준다.

```text
-- MySQL 8 EXPLAIN ANALYZE (예시 출력)
-> Index lookup on orders using idx_user_id (user_id=42)  (cost=2.8 rows=8) (actual time=0.0412..0.0503 rows=8 loops=1)
```

기능 차이도 몇 가지 알아 둔다. MySQL에는 부분 인덱스가 없다. 식 인덱스는 8.0.13부터 `CREATE INDEX idx_email_lower ON users ((lower(email)))`처럼 괄호를 한 번 더 써서 만든다. 인덱스를 지우기 전에 `ALTER TABLE orders ALTER INDEX idx_user_id INVISIBLE`로 플래너에서만 숨겨 볼 수 있어서, 문제가 생기면 바로 되돌릴 수 있다. PostgreSQL에는 이 기능이 없다. 보조 인덱스 추가는 InnoDB의 온라인 DDL로 쓰기를 막지 않고 진행된다.

## 현장에서 인덱스가 필요한 곳을 찾는 순서

처음의 마이페이지 장면으로 돌아가 보자. 실제로는 "어떤 쿼리가 느린지"부터 모르는 경우가 많다. DB CPU가 높다는 알림만 왔다. 이럴 때 테이블 단위로 먼저 좁힌다. PostgreSQL은 테이블마다 순차 스캔과 인덱스 스캔을 몇 번 했고, 순차 스캔으로 행을 몇 개 읽었는지 센다.

아래는 인덱스를 만들기 전 상태에서 통계를 리셋하고(`SELECT pg_stat_reset();`), 마이페이지 쿼리 세 번과 회원 조회 한 번을 돌린 뒤의 결과다.

```sql
-- 순차 스캔으로 많이 읽은 테이블부터
SELECT relname, seq_scan, seq_tup_read, idx_scan,
       seq_tup_read / NULLIF(seq_scan, 0) AS avg_rows_per_seq_scan
FROM pg_stat_user_tables
ORDER BY seq_tup_read DESC;
```

```text
 relname  | seq_scan | seq_tup_read | idx_scan | avg_rows_per_seq_scan
----------+----------+--------------+----------+-----------------------
 orders   |        9 |      3000000 |        0 |                333333
 products |        0 |            0 |        0 |
 users    |        0 |            0 |        1 |
(3 rows)
```

`orders`는 순차 스캔 한 번에 평균 33만 행을 읽었고 인덱스 스캔은 0번이다. 쿼리는 세 번 돌렸는데 `seq_scan`이 9인 건 병렬 워커 둘과 원래 프로세스가 각자 한 번씩 세기 때문이다. 큰 테이블에서 `seq_tup_read`가 빠르게 늘고 `idx_scan`이 거의 없으면, 그 테이블을 거르는 쿼리 중에 인덱스가 없는 것이 있다는 신호다. 어떤 쿼리인지는 [느린 쿼리 고치기 글](/posts/sql-query-tuning)의 `pg_stat_statements`로 찾는다.

쿼리를 찾았으면 실행 계획을 본다. 여기서 흔한 실수가 하나 있다. `EXPLAIN ANALYZE`는 쿼리를 정말로 실행한다. `DELETE`나 `UPDATE`의 계획을 보려고 그냥 돌리면 행이 지워진다. 쓰기 쿼리는 트랜잭션 안에서 보고 되돌린다.

```sql
BEGIN;
EXPLAIN (ANALYZE, BUFFERS) DELETE FROM orders WHERE user_id = 42;  -- 실제로 지운다
ROLLBACK;                                                          -- 그래서 되돌린다
```

```text
                                                 QUERY PLAN
------------------------------------------------------------------------------------------------------------
 Delete on orders  (cost=0.00..21846.00 rows=0 width=0) (actual time=54.108..54.110 rows=0 loops=1)
   Buffers: shared hit=9362
   ->  Seq Scan on orders  (cost=0.00..21846.00 rows=11 width=6) (actual time=2.476..53.972 rows=8 loops=1)
         Filter: (user_id = 42)
         Rows Removed by Filter: 999992
         Buffers: shared hit=9346
 Planning:
   Buffers: shared hit=3
 Planning Time: 0.053 ms
 Execution Time: 54.171 ms
(10 rows)
```

8행을 지우려고 100만 행을 훑었다. 회원 탈퇴 API가 느린 이유가 이런 모양으로 나온다. 쓰기 쿼리는 병렬로 돌지 않아서 `Parallel Seq Scan`이 아니라 `Seq Scan`이고, 비용도 앞에서 계산한 병렬이 아닐 때의 21846이다.

계획을 읽을 때 기억할 것은 앞에서 본 그대로다. `cost`는 ms가 아니고, 시간은 캐시 상태에 따라 오르내리니 `Buffers`로 비교하고, `Rows Removed by Filter`가 결과보다 훨씬 크면 인덱스 후보다. 그리고 운영 DB에서 처음 돌린 결과(`read`가 많은)와 두 번째 결과(`hit`이 많은)를 섞어 비교하지 않는다.

## 찾아보기는 정렬된 사본이다

인덱스는 정렬된 사본이다. 정렬돼 있어서 몇 페이지만 내려가면 원하는 값에 닿고, 사본이라서 쓸 때마다 같이 고쳐야 한다. PostgreSQL에서는 인덱스와 힙이 따로 있어서 위치(ctid)를 찾은 뒤 힙을 한 번 더 간다. MySQL InnoDB에서는 테이블 자체가 기본 키 B-tree라서 보조 인덱스가 기본 키를 거쳐 행에 닿는다. 어떤 인덱스를 어떤 순서로 만들지는 [인덱스 고르기 글](/posts/db-index-design)에서, 인덱스가 있는데도 안 타는 경우와 인덱스가 쓰기에 매기는 값은 [인덱스가 안 타는 이유 글](/posts/db-index-pitfalls)에서 이어 본다.

## 면접에서 나올 만한 질문

### 인덱스가 무엇이고, 왜 조회가 빨라지나요?

컬럼 값을 정렬해서 행의 위치와 함께 따로 저장해 둔 자료구조다. 인덱스가 없으면 조건에 맞는 행을 찾으려고 테이블 전체를 읽어야 하지만, 정렬된 B-tree에서는 루트부터 몇 페이지만 내려가면 위치를 안다. 예제의 주문 100만 건에서는 9,346페이지를 읽던 쿼리가 인덱스 3페이지와 힙 8페이지, 합쳐 11페이지로 줄었다. 대가로 저장 공간과 쓰기 비용이 든다.

### 왜 해시나 이진 트리가 아니라 B-tree를 쓰나요?

B-tree는 페이지 하나에 키를 수백 개 담아서 나무가 아주 낮다. 100만 행이 3층, 수억 행도 4~5층이라 디스크 페이지를 몇 번만 읽으면 된다. 이진 트리는 노드마다 둘로만 갈라져 층이 깊다. 해시는 같다 비교만 되지만 B-tree는 정렬돼 있어서 범위 조건, `ORDER BY`, 앞부분 일치 `LIKE`까지 처리한다.

### Index Scan과 Bitmap Heap Scan은 언제 갈리나요?

결과 행 수에 따라 플래너가 고른다. 한두 행이면 인덱스에서 하나 찾을 때마다 바로 힙에 가는 Index Scan이 싸다. 수십에서 수천 행이면 위치를 먼저 모아 페이지 번호 순으로 정렬한 뒤(비트맵) 힙을 앞에서 뒤로 한 번에 읽는 Bitmap Heap Scan이 낫다. 같은 페이지를 한 번만 읽고 디스크를 앞뒤로 오가지 않기 때문이다. 결과가 테이블의 큰 부분이면 Seq Scan이 된다.

### Index Only Scan인데 Heap Fetches가 많이 나오는 이유는요?

PostgreSQL은 행이 지금 트랜잭션에 보여도 되는지를 힙에만 적어 두기 때문에, 인덱스만 보고는 살아 있는 행인지 모른다. 그래서 가시성 맵에서 "이 페이지의 모든 행은 모두에게 보인다"는 표시를 확인하고, 표시가 없는 페이지는 힙을 읽는다. 이 표시는 VACUUM이 켜니, 수정이 잦은데 VACUUM이 밀리면 `Heap Fetches`가 늘어난다.

### 실행 계획을 비교할 때 무엇을 보나요?

시간보다 `Buffers`를 본다. 시간은 캐시에 페이지가 있었는지에 따라 크게 바뀌지만, 읽은 페이지 수는 데이터가 같으면 그대로다. `rows` 예상과 실제가 크게 다른지, `Rows Removed by Filter`가 결과보다 훨씬 큰지도 본다. 쓰기 쿼리에 `EXPLAIN ANALYZE`를 쓸 때는 실제로 실행되니 `BEGIN`과 `ROLLBACK`으로 감싼다.

### MySQL InnoDB에서 기본 키로 무작위 UUID를 쓰면 왜 안 좋나요?

InnoDB는 테이블이 기본 키 순으로 정렬된 B-tree(클러스터드 인덱스)라서, 무작위 키는 새 행을 트리 여기저기에 끼워 넣게 만든다. 페이지 분할이 잦아지고 페이지가 반쯤 빈 채 흩어지며, 메모리에 올려야 할 페이지가 늘어난다. 보조 인덱스마다 기본 키 값이 들어가니 키가 길면 모든 인덱스가 커진다. 자동 증가 `BIGINT`나 시간 순으로 커지는 UUIDv7을 `BINARY(16)`으로 쓴다.
