<EasyIntro>
  큰 일을 여럿이 나눠 하면 빨라질 것 같지만 늘 그렇지는 않다. 클로드 코드도 일을 나눠 맡기는 방법이 몇 가지 있고, 방법마다 잘 맞는 일이 다르다.

  학교 조별 과제에 비유할 수 있다. 첫째는 내가 친구에게 "이 책에서 이것만 찾아 줘"라고 부탁하고 답만 받는 방법이다. 둘째는 서로 상관없는 숙제를 각자 집에서 따로 해 오는 방법이다. 셋째는 조장이 할 일 목록을 칠판에 적고, 조원들이 하나씩 가져가며 서로 쪽지를 주고받는 방법이다.

  셋째 방법은 서로 의견을 나눠야 하는 일에 좋지만 가장 손이 많이 간다. 조원마다 책을 처음부터 다시 읽어야 하고, 두 사람이 같은 종이에 동시에 쓰면 글이 덮인다. 그래서 작고 간단한 일은 혼자 하거나 친구에게 부탁하는 편이 빠르고, 여럿이 진짜로 따로 맡을 수 있는 큰일에만 조를 짠다.
</EasyIntro>

결제 모듈을 새 API로 옮기는 리팩터링이 있다. API 호출 계층, React 화면, 테스트 세 갈래로 나뉘고 각각 반나절 일이다. 세션 하나로 하면 하루가 간다. 셋을 동시에 맡기면 오후에 끝날 것 같다. 그래서 "세 명이 동시에 하게 해 줘"라고 말하려는데, Claude Code에는 동시에 일을 나누는 방법이 여러 개다. 서브에이전트, 백그라운드 세션, 에이전트 팀. 무엇을 고르느냐에 따라 비용이 두세 배, 많게는 몇 배가 달라지고, 고른 방법이 일과 안 맞으면 셋이 같은 파일을 덮어쓴다.

이 글은 세 방법의 구조를 비교하고, 언제 무엇을 고르는지, 나눠 맡길 때 생기는 충돌과 조율 비용, 사람이 끼어들어야 할 자리를 정리한다. 여러 에이전트를 쓰는 일반 원리(언제 나누면 빨라지고 언제 비싸지기만 하나)는 [멀티 에이전트 글](/posts/multi-agent-systems)에 있고, 여기서는 Claude Code가 제공하는 장치에 집중한다. 같은 저장소의 작업 폴더를 git worktree로 나누는 방법 자체는 [병렬 세션과 예약 작업 글](/posts/claude-code-parallel-and-scheduled)에서 다뤘다.

기준은 Claude Code 2.1.310(Ubuntu 24.04)과 2026년 10월의 [에이전트 팀 문서](https://code.claude.com/docs/en/agent-teams), [병렬 실행 비교 문서](https://code.claude.com/docs/en/agents)다. 에이전트 팀은 실험 기능이고 기본으로 꺼져 있으며, 대화형 세션에서만 팀원을 띄운다. 그래서 팀 자체는 문서에 적힌 동작으로 쓰고, `claude -p`로 잴 수 있는 서브에이전트 비용은 직접 쟀다.

서브에이전트는 메인 세션 안의 일꾼이다. 메인 Claude가 일을 넘기면 자기 컨텍스트에서 파일을 읽고 명령을 돌린 뒤 요약 하나만 돌려준다. 메인 대화에는 요약만 남는다. 조율은 메인이 전부 한다. 서브에이전트를 만드는 법은 [확장 글](/posts/claude-code-extensions)에 있다.

백그라운드 세션은 내가 직접 따로 띄운 완전한 세션이다. `claude --bg "flaky 테스트 원인 찾기"`로 띄우면 터미널을 붙이지 않고 돌고, `claude agents`(agent view)에서 무엇이 돌고 무엇이 나를 기다리는지 한 화면에 본다. 세션끼리는 서로 모르고, 결과는 나에게만 온다. 문서 기준으로 이렇게 띄운 세션은 파일을 고치기 전에 `.claude/worktrees/` 아래의 자기 worktree로 옮겨 가서 같은 checkout을 덮지 않는다.

에이전트 팀은 리더 세션 하나가 팀원 세션 여럿을 띄우고, 공유 작업 목록과 메일함으로 조율하는 구조다. 팀원은 각자 완전한 Claude Code 세션이고, 리더를 거치지 않고 서로 직접 메시지를 보낸다. 나도 팀원 하나를 골라 직접 말을 걸 수 있다.

| | 서브에이전트 | 백그라운드 세션 | 에이전트 팀 |
| :- | :- | :- | :- |
| 누가 나누나 | 메인 Claude | 나 | 리더 Claude |
| 결과가 가는 곳 | 부른 세션에 요약 | 나에게 | 작업 목록과 메시지, 리더가 종합 |
| 일꾼끼리 대화 | 이름 붙은 것끼리 제한적으로 | 없음(세션 간 메시지 기능을 따로 쓰면 가능) | 직접 메시지 |
| 파일 격리 | 따로 없음 | 편집 전 worktree로 이동 | 없음. 파일을 나눠 맡겨야 한다 |
| 비용 | 일꾼 몫이 더해진다 | 세션마다 따로 | 팀원 수에 거의 비례 |
| 상태 | 정식 기능 | 연구 미리보기 | 실험 기능, 기본 꺼짐 |

표의 "파일 격리" 줄을 기억해 둔다. 에이전트 팀은 팀원을 worktree로 나누지 않는다. 문서도 두 팀원이 같은 파일을 고치면 덮어쓴다고 적고, 팀원마다 다른 파일 묶음을 맡기라고 권한다.

## 결과만 필요하면 서브에이전트

가장 가벼운 것부터 잰다. 서브에이전트는 나눠 맡기면 빨라질까. 300줄짜리 파일 세 개에서 export된 함수 이름을 뽑는 일을 두 방식으로 시켰다. 하나는 메인이 직접 읽게 하고, 하나는 파일마다 서브에이전트를 하나씩 동시에 띄우게 했다. 모두 Haiku로 돌렸다.

```bash
# 같은 일을 직접 읽기와 서브에이전트 셋으로 각각 시키고, 비용과 시간을 본다
claude -p "Read src/a.js, src/b.js and src/c.js yourself (do not use subagents) and list the exported function names of each file." \
  --model haiku --allowedTools "Read,Grep,Glob,Agent" --output-format json \
  | jq '{cost: .total_cost_usd, turns: .num_turns, wall_ms: .duration_ms, spawned: .subagent_stats.spawned}'
```

```text
single  cost=0.0049  turns=4  wall_ms=7594   api_ms=5407   spawned=0
sub3    cost=0.0104  turns=5  wall_ms=14963  api_ms=18089  spawned=3
```

둘 다 정답(파일마다 9개)을 냈다. 그런데 서브에이전트 셋으로 나눈 쪽이 비용은 2.1배, 벽시계 시간은 2배였다. API 시간 합(18초)이 벽시계 시간(15초)보다 긴 것은 셋이 동시에 돌았다는 뜻인데도 그렇다. 이유는 셋이다. 서브에이전트마다 자기 시스템 프롬프트와 도구 정의를 새로 싣고 시작하고, 메인 캐시를 읽지 못하며, 리더 역할을 한 메인이 결과를 받아 "원본과 맞는지" 다시 확인했다(답에 "the subagents' results match the source files"라고 적었다).

이 일은 파일 세 개를 읽는 작은 일이라 나누는 비용이 나눠서 얻는 시간보다 컸다. 그러면 서브에이전트는 언제 이길까. 문서의 답은 결과가 장황해서 메인 컨텍스트를 아껴야 할 때다. 그래서 읽을 양을 늘려 다시 쟀다. 2,500줄짜리 로그 세 개(ERROR 21, 26, 23줄)에서 파일마다 ERROR 줄 수와 메시지 종류를 세게 했다. 실제로는 grep 한 줄이면 끝나는 일이지만, 통째로 읽어야 하는 상황을 만들려고 Grep, Bash, Glob을 막고 Read만 허용했다.

```bash
# 읽기 도구만 남기고, 직접 읽기와 서브에이전트 셋을 비교한다
claude -p "..." --model haiku --allowedTools "Read,Agent" --disallowedTools "Grep,Bash,Glob" \
  --output-format json > out.json
# 메인 대화의 마지막 요청이 실은 입력 토큰(= 메인 컨텍스트 크기)과 전체 비용
jq '{cost: .total_cost_usd, turns: .num_turns,
     main_ctx: (.usage.input_tokens + .usage.cache_read_input_tokens + .usage.cache_creation_input_tokens)}' out.json
```

```text
single  cost=0.3918  turns=16  main_ctx=461770  결과: "Read output came back in 597-line chunks that I mixed up while tallying" (집계 실패)
sub3    cost=0.1894  turns=1   main_ctx=40381   결과: a 21, b 26, c 23줄, 메시지별 개수까지 모두 정답
```

이번에는 반대로 나왔다. 메인이 직접 읽은 쪽은 컨텍스트가 46만 토큰까지 불었고, 16턴을 돌고도 "나눠 읽은 조각을 세다가 섞여서 믿을 만한 숫자를 줄 수 없다"고 답했다. 비용도 두 배였다. 서브에이전트 셋은 각자 자기 파일 하나만 들고 세었고, 메인에는 결과 몇 줄만 돌아와 컨텍스트가 4만 토큰에 머물렀다. 숫자는 `grep`으로 확인한 값과 모두 맞았다. 서브에이전트 셋은 백그라운드로 돌아서 이 JSON의 시간 필드로는 벽시계 시간을 비교할 수 없었다. 메인 쪽은 160초가 걸렸다.

두 실험을 합치면 기준이 나온다. "읽을 것은 많은데 필요한 결론은 몇 줄"인 일, 수천 줄 로그나 테스트 전체 출력, 저장소 전체를 훑는 조사는 나누면 싸고 정확해진다. 금방 끝나는 작은 일은 나누면 고정 비용만 더한다. 하나 더 있다. 이 로그 집계는 grep 하나면 몇 백 토큰으로 끝난다. 나누기 전에 도구로 줄일 수 있는지부터 본다. 비용을 아끼려면 [모델과 비용 글](/posts/claude-code-models-and-cost)에서 본 것처럼 서브에이전트 정의에 `model: haiku`를 붙인다.

## 서로 모르는 일은 백그라운드 세션

리팩터링과 상관없는 일이 동시에 몇 개 있다고 하자. flaky 테스트 원인 찾기, PR 리뷰 코멘트 반영, 의존성 업데이트. 서로 결과를 주고받을 필요가 없다. 이럴 때는 리더도 팀도 필요 없고, 세션을 따로 띄우면 된다.

```bash
# 세션을 바로 백그라운드로 보낸다. 프롬프트는 -p 값이 아니라 위치 인자다
claude --bg --name "flaky-test-fix" "investigate the flaky SettingsChangeDetector test"
# 한 화면에서 상태를 본다
claude agents
```

문서에 실린 출력 형식은 이렇다. 띄우면 짧은 ID와 관리 명령을 알려 준다.

```text
backgrounded · 7c5dcf5d · flaky-test-fix
  claude agents             list sessions
  claude attach 7c5dcf5d    open in this terminal
  claude logs 7c5dcf5d      show recent output
  claude stop 7c5dcf5d      stop this session
```

`--bg`는 `-p`와 함께 쓸 수 없다. `-p`는 대화형 세션을 만들지 않으니 agent view가 붙을 대상이 없어서다. 신뢰하지 않은 폴더에서 띄우면 신뢰 창이 먼저 뜨고, 창을 띄울 수 없는 스크립트에서는 시작하지 않고 끝난다. 백그라운드 세션은 각자 메인 대화라서 구독이면 1시간 캐시를 쓰고, 비용은 세션 수만큼 더해진다. 장점은 조율 비용이 0이라는 것이다. 사람이 일을 나누고 결과를 본다. 세션끼리 발견을 주고받게 하고 싶으면 세션 간 메시지(cross-session messaging)를 쓰면 되지만, 그쯤 되면 팀을 고려할 때다.

## 서로 따지고 나눠 맡기면 에이전트 팀

에이전트 팀이 필요한 일은 따로 있다. 문서가 꼽는 강한 경우는 넷이다. 여러 관점으로 같은 대상을 동시에 조사하고 서로의 결론을 반박하는 리뷰·조사, 팀원마다 독립된 모듈을 맡는 새 기능, 원인이 불분명한 버그를 가설마다 한 명씩 맡겨 서로 반증하게 하는 디버깅, 프런트엔드·백엔드·테스트처럼 계층이 나뉜 변경이다. 결제 리팩터링은 마지막 경우다.

켜려면 설정에 실험 플래그를 넣는다.

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

이 플래그는 팀을 부를 때만 영향을 주지 않는다. 켜 두면 Claude가 이름을 붙여 띄운 서브에이전트가 팀원으로 뜬다. Claude는 나중에 메시지를 보내려고 서브에이전트에 스스로 이름을 붙이기도 해서, 팀을 요청하지 않았는데 팀이 생길 수 있다. 서브에이전트로 돌아가게 하려면 값을 `0`으로 바꾼다. 실행 중인 세션에도 저장하는 즉시 다시 적용된다. 그리고 팀원은 대화형 세션에서만 뜬다. `-p`와 Agent SDK에서는 이름 붙은 서브에이전트도 평범한 서브에이전트로 돈다.

팀은 자연어로 시킨다. 이름을 정해 주면 나중에 그 이름으로 부를 수 있다.

```text
결제 모듈을 새 Payments API로 옮긴다. 팀원 셋을 Sonnet으로 띄워라.
- api: src/payments/api/ 아래 파일만 고친다. 새 클라이언트와 오류 매핑.
- ui: src/payments/ui/ 아래 파일만 고친다. api가 정한 타입을 import해서 쓴다.
- tests: test/payments/ 아래 파일만 고친다. api와 ui가 끝난 작업부터 테스트를 쓴다.
공유 타입 src/payments/types.ts는 api만 고친다. 다른 팀원은 바꿔야 하면 api에게 메시지로 요청한다.
```

팀원 사이의 메시지는 메일함 파일로 오간다. 문서 기준으로 `~/.claude/teams/{팀 이름}/inboxes/{에이전트 이름}.json`이고, 받는 쪽에 자동으로 전달되어 리더가 확인하러 다닐 필요가 없다. 팀 설정(`~/.claude/teams/{팀 이름}/config.json`)은 세션이 끝나면 지워지고, 작업 목록(`~/.claude/tasks/{팀 이름}/`)은 남는다. 팀 이름은 `session-`에 세션 ID 앞 여덟 글자를 붙인 것이다. 팀 설정에는 세션 ID 같은 실행 상태가 들어 있으니 손으로 고치거나 미리 써 두지 않는다. 역할을 재사용하고 싶으면 서브에이전트 정의를 만들어 "security-reviewer 타입으로 팀원을 띄워라"처럼 부른다.

## 팀원 화면을 보는 법

팀원은 기본으로 내 터미널 안에서 돈다(in-process 모드). 입력창 아래 에이전트 패널에 팀원 줄이 생기고, 몇 가지 키로 다룬다.

```text
↑ / ↓     팀원 고르기
Enter     고른 팀원의 대화 열기 (여기서 치는 글은 그 팀원에게 간다)
Esc       선택 해제. 팀원 대화를 보는 중이면 그 팀원의 현재 턴을 끊는다
x         고른 팀원 멈추기
Ctrl+T    공유 작업 목록 열고 닫기
```

팀원 대화를 보는 중에 친 일반 글과 스킬은 그 팀원에게 가지만, 내장 명령은 리더 쪽으로 간다. `/compact`, `/clear`, `/rewind`는 리더 대화에 적용되니 Claude Code가 확인을 묻고, `/model`과 `/fast`는 이 화면에서 아예 돌지 않는다. 팀원의 모델은 띄울 때 정해지기 때문이다.

모든 팀원이 쉬고 있으면 30초 뒤 줄이 숨는다. 멈춘 것이 아니라 숨은 것이고, 이름으로 메시지를 보내면 다시 나타난다. 쉬는 팀원이 넷 이상이면 셋을 넘는 줄은 `2 idle agents` 같은 한 줄로 접힌다. "팀원이 사라졌다"는 문의 대부분이 이 경우다.

팀원마다 창을 나눠 한꺼번에 보고 싶으면 split pane 모드를 쓴다. tmux나 iTerm2(`it2` CLI)가 있어야 한다.

```json
{
  "teammateMode": "auto"
}
```

`"auto"`는 이미 tmux 안이거나 iTerm2에 `it2`가 있을 때만 창을 나누고, 아니면 in-process로 돈다. `"tmux"`는 split pane을 켜고 tmux와 iTerm2 중 무엇을 쓸지 알아서 고른다. 한 세션에만 주려면 `claude --teammate-mode auto`로 띄운다(이 플래그는 `--help`에 나오지 않는 실험 플래그다). Ubuntu 서버에서는 tmux를 깔고 tmux 안에서 `claude`를 띄우면 된다.

```bash
# tmux를 설치하고, tmux 세션 안에서 Claude Code를 띄운다
sudo apt-get install -y tmux
tmux new -s payments
claude --teammate-mode auto
```

Claude Code 세션이 끝났는데 tmux 세션이 남는 경우가 있다. 목록을 보고 팀이 만든 세션을 지운다.

```bash
# 남은 tmux 세션을 확인하고 정리한다
tmux ls
tmux kill-session -t <세션 이름>
```

## 역할을 정의해 두고 팀원으로 부르기

같은 역할을 자주 쓰면 서브에이전트 정의로 한 번 만들어 두고 팀원으로 부른다. 서브에이전트로 위임할 때와 팀원으로 띄울 때 같은 정의를 쓴다.

```markdown
---
name: security-reviewer
description: 인증·세션·입력 검증 관점으로 변경을 리뷰한다.
tools: Read, Grep, Glob, Bash
model: sonnet
---

src/auth/와 바뀐 파일만 본다. 토큰 저장 위치, 세션 만료, 입력 검증, 비밀값 로그 출력을 확인한다.
찾은 것은 심각도(높음·중간·낮음)와 파일:줄로 적는다. 파일을 고치지 않는다.
```

```text
security-reviewer 타입으로 팀원을 하나 띄워 PR #142의 인증 변경을 리뷰하게 해라.
```

정의의 모든 필드가 팀원에게 적용되지는 않는다. 문서 기준으로 `tools`는 적용되고, in-process 팀원에게는 메시지용 `SendMessage`와 작업 목록 도구가 자동으로 더해진다. `model`은 프롬프트가 모델을 정하지 않았을 때 쓰인다. 본문은 in-process 팀원에게는 기본 시스템 프롬프트 뒤에 덧붙고, split pane 팀원에게는 기본 시스템 프롬프트를 대신한다. `skills` 필드는 어느 모드에서도 적용되지 않고 팀원은 프로젝트와 사용자 설정의 스킬을 읽는다. `mcpServers`는 split pane 팀원에게만 적용된다. 모드에 따라 같은 정의가 다르게 동작하니, 역할이 도구 제한에 기대는 경우(리뷰어는 Edit이 없어야 한다)는 `tools`로 정하고 본문의 말에 기대지 않는다.

## 원인이 안 보이는 버그는 가설마다 한 명

팀이 가장 빛나는 경우로 문서가 드는 예가 경쟁 가설 디버깅이다. "앱이 메시지 하나를 보낸 뒤 연결이 끊긴다"처럼 원인이 불분명할 때, 세션 하나는 그럴듯한 설명 하나를 찾으면 거기서 멈추는 경향이 있다. 처음 본 가설에 끌려 다음 조사도 그쪽으로 기우는 고정 효과(anchoring)다.

```text
사용자들이 메시지 하나를 보낸 뒤 앱이 연결을 끊는다고 한다.
팀원 다섯을 띄워 서로 다른 가설을 조사하게 해라.
서로의 가설을 반증하려고 직접 대화하게 하고, 합의된 결론을 docs/findings.md에 정리해라.
```

핵심은 팀원끼리 서로 반박하게 하는 구조다. 하트비트 타임아웃, 프록시의 유휴 연결 종료, 인증 토큰 만료, 서버의 예외 처리, 클라이언트 재연결 버그를 한 명씩 맡기고, 각자 자기 가설의 증거를 찾는 동시에 남의 가설을 깨려 한다. 살아남은 가설이 진짜 원인일 가능성이 높다. 이 일은 코드를 고치지 않으니 파일 충돌도 없고, 처음 팀을 써 보기에 좋다. 실시간 연결이 끊기는 원인을 계층별로 좁히는 방법은 [계층별 장애 좁히기 글](/posts/network-troubleshooting-by-layer)과 함께 보면 가설 목록을 세우기 쉽다.

## 팀원은 리더의 대화를 모른다

팀원이 시작할 때 받는 것은 일반 세션과 같은 프로젝트 컨텍스트(CLAUDE.md, MCP 서버, 스킬)와 리더가 쓴 띄우기 프롬프트뿐이다. 리더의 대화 이력은 넘어가지 않는다. 내가 리더와 한 시간 동안 "Payments API는 금액을 센트 정수로 받는다", "환불은 v2 엔드포인트만 쓴다"를 정했어도 팀원은 모른다.

그래서 띄우기 프롬프트에 결정 사항을 적어 줘야 한다. 리더에게 "팀원 프롬프트에 지금까지 정한 것을 넣어라"라고 시키거나, 정한 것을 파일(`docs/payments-migration.md`)로 남기고 팀원에게 그 파일부터 읽게 한다. 문서가 드는 예시도 같은 방식이다. 검토할 경로, 볼 관점, 앱이 쓰는 인증 방식, 결과 형식을 프롬프트에 직접 쓴다. 반대로 띄우기 프롬프트에 넣은 것은 팀원마다 처음부터 컨텍스트에 실리니 꼭 필요한 것만 넣는다.

팀원의 모델은 이 순서로 정해진다. 띄우기 프롬프트가 지정한 모델, 서브에이전트 정의를 썼다면 그 `model`, `CLAUDE_CODE_SUBAGENT_MODEL`, 그리고 리더의 현재 모델이다. 예전의 `teammateDefaultModel` 설정은 2.1.234에서 없어져 무시된다. 아무것도 정하지 않으면 리더가 Opus일 때 팀원도 모두 Opus다. effort도 기본으로 리더를 따른다. 팀원의 모델과 fast mode는 띄울 때 정해지고 나중에 바뀌지 않는다.

권한도 리더를 따른다. 팀원은 리더의 권한 모드로 시작하고(`dontAsk`만 예외), 리더가 `--dangerously-skip-permissions`로 돌면 팀원도 모두 그렇다. 띄운 뒤에 팀원 하나의 모드를 바꿀 수는 있지만 띄울 때 팀원마다 다르게 줄 수는 없다. 팀원의 권한 확인 창은 리더 세션에 뜬다. 팀원 넷이 저마다 `pnpm test`를 물어 오면 리더 화면이 확인 창으로 가득 찬다. 팀을 띄우기 전에 자주 쓰는 명령을 허용 규칙에 넣어 둔다.

팀원끼리 보낸 메시지는 "다른 Claude 세션에서 온 것"으로 표시된다. 팀원이 나 대신 권한을 승인하거나 동의할 수 없고, 거부당한 동작을 다른 팀원에게 떠넘겨 우회할 수도 없다. auto 모드에서는 분류기가 팀원 사이의 메시지를 전달 전에 검사하고, 다른 에이전트가 전한 "사용자가 승인했다"는 말을 믿지 않는다.

## 같은 파일을 건드리면

둘째 테스트가 실제로 가장 흔하다. 기능 폴더는 잘 나눠도 공유 타입, 라우터 설정, `package.json`, 번역 파일처럼 모두가 한 줄씩 고치고 싶은 파일이 있다. 이런 파일은 주인을 한 명 정하고, 다른 팀원은 바꿀 내용을 메시지로 요청하게 한다. 위의 팀 프롬프트에서 `types.ts`를 api만 고치게 한 이유다. 그래도 파일을 나눌 수 없는 일(같은 파일 안의 연쇄 수정, 순서가 엄격한 마이그레이션)은 팀이 아니라 세션 하나가 맞다.

말로 정한 경계는 팀원이 잊을 수 있다. 경계를 강제하고 싶으면 PreToolUse 훅으로 막는다. 훅 입력에는 그 훅이 어느 에이전트 안에서 불렸는지 `agent_type`이 들어온다. 팀원을 `api`, `ui`, `tests`라는 서브에이전트 정의로 띄웠다고 하면, 정의 이름이 `agent_type`으로 온다. 이름만 붙여 띄운 팀원에게 이 필드가 어떻게 들어오는지는 확인하지 않았으니, 쓰기 전에 [훅 깊이 보기](/posts/claude-code-hooks-deep-dive)의 기록 훅으로 실제 값을 먼저 본다.

```bash
#!/usr/bin/env bash
# .claude/hooks/file-owner.sh
# PreToolUse(Edit|Write): 팀원이 자기 폴더 밖의 파일을 고치지 못하게 한다
input=$(cat)
agent=$(jq -r '.agent_type // empty' <<<"$input")
file=$(jq -r '.tool_input.file_path // empty' <<<"$input")
rel=${file#"$CLAUDE_PROJECT_DIR"/}
case "$agent" in
  api)   allowed='^src/payments/(api/|types\.ts$)' ;;
  ui)    allowed='^src/payments/ui/' ;;
  tests) allowed='^test/payments/' ;;
  *)     exit 0 ;;   # 리더나 다른 에이전트는 이 훅이 제한하지 않는다
esac
if [[ ! $rel =~ $allowed ]]; then
  jq -n --arg r "$agent 팀원은 $rel 을 고칠 수 없다. 이 파일의 주인에게 메시지로 요청한다." \
    '{hookSpecificOutput: {hookEventName: "PreToolUse",
      permissionDecision: "deny", permissionDecisionReason: $r}}'
fi
exit 0
```

훅 입력 JSON을 만들어 넣어 보면 이렇게 판정한다.

```text
api    src/payments/api/client.ts     allow
api    src/payments/types.ts          allow
ui     src/payments/types.ts          deny
ui     src/payments/ui/Checkout.tsx   allow
tests  src/payments/api/client.ts     deny
(리더) package.json                   allow
```

`deny`의 이유 글은 그 팀원에게 도구 오류로 돌아가니, ui 팀원은 막힌 뒤 api에게 메시지를 보내는 쪽으로 움직인다. 다만 이 훅은 Edit과 Write만 본다. 팀원이 Bash로 `sed -i`를 돌리면 빠져나간다. 경계를 단단히 하려면 팀원의 서브에이전트 정의에서 `tools`로 Bash를 빼거나, Bash에도 같은 검사를 거는데, 셸 명령 검사가 완벽할 수 없다는 점은 [확장 글](/posts/claude-code-extensions)에서 본 그대로다.

같은 파일이 아니어도 충돌은 생긴다. 개발 서버 포트 하나, 로컬 DB 하나, `node_modules` 하나를 셋이 함께 쓴다. 한 팀원이 마이그레이션을 돌리는 동안 다른 팀원이 테스트를 돌리면 테스트가 이상하게 깨진다. 이런 공유 자원 문제는 [병렬 세션 글](/posts/claude-code-parallel-and-scheduled)의 포트와 DB 절과 같은 이야기다.

## 리더의 조율 비용과 팀 크기

팀은 비싸다. 팀원마다 자기 컨텍스트 창을 가진 별도의 Claude라서 토큰 사용이 활성 팀원 수에 거의 비례한다. 비용 문서는 팀원이 플랜 모드로 돌 때 일반 세션의 약 7배 토큰을 쓴다고 적는다. 팀원 요청은 본 대화 바깥으로 분류되어 구독이어도 캐시가 5분이고, 1시간으로 늘리려면 `subagentPromptCacheTtl`을 `1h`로 준다. 앞의 서브에이전트 실험에서 작은 일 하나를 셋으로 나눴더니 2배가 들었다. 팀은 거기에 메시지, 작업 목록 관리, 리더의 종합이 더해진다.

문서의 권고는 구체적이다. 대부분 3~5명으로 시작한다. 독립된 작업이 15개면 팀원 셋이 좋은 출발점이고, 팀원 한 명에 작업 5~6개가 되도록 나누면 다들 바쁘게 돌고 누가 막히면 리더가 다시 나눠 줄 수 있다. 작업이 너무 작으면 조율 비용이 이득보다 크고, 너무 크면 확인 없이 오래 돌아 헛수고가 커진다. 함수 하나, 테스트 파일 하나, 리뷰 하나처럼 결과물이 분명한 크기가 맞다. 문서도 "집중한 셋이 흩어진 다섯보다 나을 때가 많다"고 적는다.

비용을 줄이는 습관은 이렇다. 팀원은 Sonnet으로 띄운다(프롬프트에 "Use Sonnet for each teammate"). 띄우기 프롬프트는 짧고 정확하게 쓴다. 일이 끝난 팀원은 이름으로 종료를 요청한다("researcher 팀원에게 종료를 요청해"). 종료하지 않은 팀원은 세션이 끝날 때까지 토큰을 쓴다. 처음 써 본다면 코드를 쓰지 않는 일(PR 리뷰, 라이브러리 조사, 버그 원인 찾기)부터 시작한다. 병렬 조사의 이득은 그대로 보면서, 병렬 구현의 충돌 문제는 피한다.

## 사람이 검토할 자리

팀이 알아서 돌게 두면 안 되는 지점이 있다. 문서의 문제 해결 절과 한계 목록을 모으면 사람이 봐야 할 자리가 보인다.

첫째, 팀을 띄우기 전의 분할이다. 역할, 맡을 파일, 공유 파일의 주인, 작업 사이의 의존을 사람이 확인한다. 리더에게 "팀을 띄우기 전에 분할 계획만 보여 줘"라고 하면 된다. 위험한 작업이면 리더를 먼저 플랜 모드로 두고 팀원을 띄운다. 그러면 팀원이 읽기 전용 플랜 모드에서 계획을 세운다. 다만 문서 기준으로, 띄운 뒤 그 팀원의 권한 모드를 바꾸지 않았다면 계획 승인 요청은 리더가 검토하지 않고 바로 승인된다. 계획을 정말 검토하고 싶으면 그 팀원 화면에서 Shift+Tab으로 플랜 모드를 다시 걸어야 리더가 검토한다. 이 차이를 모르면 "계획을 승인받고 시작한다"고 믿은 팀원이 아무 검토 없이 구현에 들어간다.

둘째, 리더가 직접 일하기 시작할 때다. 리더가 팀원을 기다리지 않고 작업을 스스로 하기 시작하면 같은 파일을 둘이 고친다. "팀원들이 작업을 끝낼 때까지 기다린 뒤에 진행해"라고 멈춘다. 반대로 리더가 모든 작업이 끝나기 전에 끝났다고 판단하기도 한다. 그때는 계속하라고 말한다.

셋째, 멈춘 작업이다. 팀원이 작업을 끝내고도 완료로 표시하지 않아 뒤의 작업이 막히는 일이 있다. 작업 목록(Ctrl+T)에서 오래 in progress인 것을 보고, 실제로 끝났는지 확인해 직접 바꾸거나 리더에게 팀원을 재촉하게 한다. 오류를 만나 회복하지 못하고 멈춘 팀원은 화면에 들어가 지시를 더 주거나 대신할 팀원을 띄운다.

넷째, 끝난 뒤의 diff다. 팀원들이 각자 맡은 파일은 그럴듯해도, 합쳐 놓으면 서로 다른 가정을 한 경우가 있다. 한쪽은 금액을 센트로, 다른 쪽은 원 단위로 다뤘다면 테스트가 둘 중 한쪽 가정만 따라 쓰여 통과할 수도 있다. 경계(타입, API 계약)를 사람이 직접 읽는다.

한계도 알아 둔다. `/resume`과 `/rewind`는 in-process 팀원을 되살리지 않는다. 이어 연 뒤 리더가 없는 팀원에게 메시지를 보내려 하면 새로 띄우라고 말한다. 세션 하나에 팀은 하나이고, 팀원이 또 팀원을 띄울 수 없으며(중첩 팀 없음), 리더는 바꿀 수 없다. 팀원 화면마다 창을 나누는 split pane 모드는 tmux나 iTerm2가 필요하고 VS Code 통합 터미널, Windows Terminal, Ghostty에서는 지원하지 않는다. 기본 in-process 모드는 어느 터미널에서나 된다.

결제 리팩터링으로 돌아가면, 세 갈래가 각자 다른 폴더를 맡고 공유 타입의 주인을 정할 수 있으니 팀이 맞는 일이다. 다만 처음 써 본다면 먼저 세 갈래의 설계를 팀으로 리뷰시키고, 구현은 worktree 세 개에서 사람이 띄운 세션으로 해도 된다. 고르는 기준은 "일꾼끼리 말해야 하나, 누가 나누나, 같은 파일을 건드리나" 세 가지다.

## 면접에서 나올 만한 질문

### 서브에이전트와 에이전트 팀은 무엇이 다른가?

서브에이전트는 메인 세션 안의 일꾼으로, 자기 컨텍스트에서 일하고 요약만 부른 쪽에 돌려준다. 조율은 메인이 다 한다. 에이전트 팀은 리더가 띄운 팀원 각각이 완전한 세션이고, 공유 작업 목록에서 작업을 가져가며 서로 직접 메시지를 주고받는다. 결과만 필요하면 서브에이전트, 일꾼끼리 발견을 나누고 반박해야 하면 팀이다.

### 작은 일을 서브에이전트 셋으로 나누면 빨라지나?

꼭 그렇지 않다. 300줄 파일 셋에서 export 함수를 뽑는 일은 서브에이전트 셋으로 나누니 비용 2.1배, 시간 2배였다. 시작할 때마다 시스템 프롬프트와 도구 정의를 새로 싣고, 메인 캐시를 못 읽고, 메인이 결과를 다시 확인했기 때문이다. 반대로 2,500줄 로그 셋을 통째로 읽어 세는 일은 직접 읽은 쪽이 컨텍스트 46만 토큰에 집계까지 실패했고, 서브에이전트 셋은 절반 비용에 정확히 셌다. 읽을 것은 많고 결론은 짧은 일에서 나눈다.

### 백그라운드 세션은 언제 쓰나?

서로 결과를 주고받을 필요가 없는 일 여러 개를 내가 나눠 맡길 때다. `claude --bg`로 띄우고 `claude agents`에서 상태를 보며, 파일을 고치기 전에 각자 worktree로 옮겨 가서 서로 덮지 않는다. 조율 비용이 없고 사람이 나누고 사람이 결과를 본다.

### 팀원은 리더 세션에서 무엇을 물려받나?

CLAUDE.md, MCP 서버, 스킬 같은 프로젝트 컨텍스트와 띄우기 프롬프트를 받고, 리더의 대화 이력은 받지 않는다. 모델은 프롬프트 지정, 서브에이전트 정의, `CLAUDE_CODE_SUBAGENT_MODEL`, 리더 모델 순으로 정해지고 권한 모드는 리더를 따른다. 그래서 리더와 정한 결정은 프롬프트나 파일로 넘겨야 한다.

### 팀원 둘이 같은 파일을 고치면? 어떻게 막나?

팀원은 worktree로 나뉘지 않고 같은 폴더를 쓰니 나중에 쓴 쪽이 덮는다. 띄우기 전에 팀원마다 맡을 파일을 나누고, 공유 타입이나 설정 파일은 주인을 한 명 정해 나머지는 메시지로 요청하게 한다. 파일을 나눌 수 없는 연쇄 수정은 팀이 아니라 세션 하나로 한다.

### 에이전트 팀의 비용은 어떻게 관리하나?

토큰이 활성 팀원 수에 거의 비례하고, 문서 기준으로 팀원이 플랜 모드로 돌면 일반 세션의 약 7배다. 3~5명으로 시작하고, 팀원은 Sonnet으로 띄우고, 프롬프트를 짧게 쓰고, 끝난 팀원은 바로 종료시킨다. 작업은 팀원당 5~6개로 결과물이 분명한 크기로 나눈다.

### 팀에서 사람이 꼭 확인해야 하는 지점은?

띄우기 전의 분할(역할, 파일 경계, 의존), 리더가 기다리지 않고 직접 일하기 시작할 때, 완료 표시가 안 돼 막힌 작업, 끝난 뒤 팀원 사이의 경계(타입, API 계약)다. 팀원의 계획 승인은 기본으로 리더 검토 없이 바로 통과하니, 계획을 검토하려면 그 팀원에 플랜 모드를 다시 걸어야 한다. TaskCompleted 훅으로 테스트 통과를 완료 조건으로 강제할 수도 있다.

### 팀을 켜 두었더니 부탁하지 않은 팀원이 생긴다. 왜인가?

실험 플래그를 켜면 Claude가 이름을 붙여 띄운 서브에이전트가 팀원으로 뜨는데, Claude는 나중에 메시지를 보내려고 서브에이전트에 스스로 이름을 붙이기도 한다. 서브에이전트로 돌리려면 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`를 `0`으로 바꾸면 되고, 실행 중인 세션에도 저장 즉시 적용된다. 더 높은 우선순위 설정이나 관리형 설정이 켜 두었으면 그쪽을 바꿔야 한다.
