Postgres를 컨테이너로 띄우고 `-p 5432:5432`로 포트도 열었다. 호스트에서 `psql -h localhost`로 붙으면 잘 된다. 그래서 앱 컨테이너의 접속 주소도 `postgres://app:change-me@localhost:5432/app`으로 적었다. 앱을 띄우자마자 로그에 이게 찍힌다.

```text
Error: connect ECONNREFUSED 127.0.0.1:5432
```

할 수 없이 DB 컨테이너를 지우고 다시 띄워서 이것저것 해 보는데, 이번에는 아까 만든 테이블이 전부 없다. `docker rm` 한 번에 데이터가 날아간 것이다.

두 문제의 뿌리는 같다. 컨테이너는 자기만의 네트워크와 자기만의 파일 시스템을 가진 격리된 공간이고, 그 격리를 어디까지 풀어 줄지는 사람이 정해야 한다. 이 글은 컨테이너끼리 이름으로 대화하게 만드는 네트워크와, 컨테이너가 사라져도 데이터가 남게 하는 볼륨을 다룬다. 컨테이너가 무엇인지, 이미지가 어떻게 쌓이는지는 [컨테이너 기초](/posts/docker-container-basics)와 [Dockerfile과 이미지 레이어](/posts/dockerfile-image-layers)에서 다뤘으니 여기서는 넘어간다.

기준은 Ubuntu 24.04 LTS에 Docker 공식 apt 저장소의 Docker Engine(`docker-ce`)을 설치한 환경이다. 22.04도 같다. 명령은 사용자가 `docker` 그룹에 들어 있다고 보고 `sudo` 없이 적었고, 호스트의 iptables나 `/var/lib/docker`를 직접 보는 명령에만 `sudo`를 붙였다. Mac이나 Windows의 Docker Desktop은 리눅스 VM 안에서 Docker를 돌리기 때문에, 호스트에서 `docker0`나 `/var/lib/docker`가 보이지 않는다는 차이가 있다.

## 컨테이너 안의 localhost는 컨테이너 자신이다

첫 번째 에러부터 보자. 컨테이너를 만들 때 Docker는 리눅스의 네트워크 네임스페이스를 하나 새로 만든다. 네임스페이스는 네트워크 장치, IP, 라우팅 표, 포트 번호 공간을 따로 갖는 칸막이다. 컨테이너 안의 `lo`(127.0.0.1)는 그 칸막이 안의 루프백이라서 호스트의 루프백과도, 다른 컨테이너의 루프백과도 상관이 없다.

그러니 앱 컨테이너가 `localhost:5432`로 접속하면 앱 컨테이너 자기 자신의 5432 포트를 두드린다. 거기에는 아무것도 듣고 있지 않으니 커널이 바로 RST를 돌려주고, 그게 `ECONNREFUSED 127.0.0.1:5432`다. 호스트에서는 됐던 이유도 같은 이야기다. 호스트의 `localhost:5432`는 `-p`로 게시한 포트라 Docker가 DB 컨테이너로 넘겨 준다.

컨테이너 안에서 직접 확인해 보면 장치가 둘뿐이다.

```bash
# busybox 컨테이너 하나를 띄워 네트워크 장치 목록을 본다 (끝나면 --rm으로 지워진다)
docker run --rm busybox ip -4 addr
```

```text
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue qlen 1000
    inet 127.0.0.1/8 scope host lo
       valid_lft forever preferred_lft forever
8: eth0@if9: <BROADCAST,MULTICAST,UP,LOWER_UP,M-DOWN> mtu 1500 qdisc noqueue
    inet 172.17.0.2/16 brd 172.17.255.255 scope global eth0
       valid_lft forever preferred_lft forever
```

`lo`는 이 컨테이너만의 루프백이고, `eth0@if9`가 바깥과 이어진 유일한 통로다. `@if9`는 이 장치가 호스트 쪽 9번 인터페이스와 짝이라는 뜻이다. 이 짝을 veth(가상 이더넷) 쌍이라고 부르는데, 한쪽 끝은 컨테이너 안에 `eth0`로, 다른 끝은 호스트에 `vethXXXX`로 꽂혀 있는 가상 랜선이다. 호스트 쪽 끝은 다시 `docker0`라는 가상 스위치(리눅스 브리지)에 꽂힌다.

그러면 앱이 DB에 닿으려면 무엇을 적어야 할까. DB 컨테이너의 IP(`172.17.0.3` 같은)를 적으면 일단 닿기는 한다. 하지만 이 IP는 컨테이너를 다시 만들 때마다 바뀔 수 있다. 필요한 건 바뀌지 않는 이름이다.

## 네트워크 드라이버 다섯 가지

Docker 네트워크는 드라이버로 성격이 정해진다. 설치 직후에는 세 개가 미리 만들어져 있다.

```bash
# 지금 있는 네트워크 목록
docker network ls
```

```text
NETWORK ID     NAME      DRIVER    SCOPE
b2c9d4e1f0a3   bridge    bridge    local
5e7f1a2b3c4d   host      host      local
9a8b7c6d5e4f   none      null      local
```

`bridge`라는 이름의 네트워크가 기본 브리지다. `--network`를 주지 않고 띄운 컨테이너는 전부 여기에 붙는다. 호스트의 `docker0` 브리지가 이 네트워크이고, 대역은 기본으로 `172.17.0.0/16`, 게이트웨이는 `docker0`에 붙은 `172.17.0.1`이다. 같은 기본 브리지의 컨테이너끼리는 IP로 통신이 되지만 이름으로는 서로를 찾지 못한다. 예전에는 `--link`로 이름을 이어 줬는데 지금은 레거시 기능이다.

사용자 정의 브리지는 `docker network create`로 직접 만든 브리지 네트워크다. 드라이버는 같은 bridge인데 동작이 꽤 다르다. 이 네트워크에 붙은 컨테이너는 Docker 내장 DNS로 서로를 컨테이너 이름으로 찾을 수 있고, 다른 네트워크의 컨테이너와는 격리된다. 실무에서 컨테이너 여러 개를 엮을 때는 거의 항상 이걸 쓴다. Docker Compose가 프로젝트마다 네트워크를 하나 만들어 주는 것도 같은 원리다.

host 드라이버는 네트워크 네임스페이스를 아예 만들지 않는다. 컨테이너가 호스트의 네트워크를 그대로 쓰니 컨테이너 안의 `localhost`가 곧 호스트의 `localhost`이고, 앱이 80을 열면 호스트의 80이 열린다. NAT를 거치지 않아 아주 조금 빠르고, 포트가 많이 필요한 프로그램에 편하다. 대신 격리가 사라지고 같은 포트를 쓰는 컨테이너를 둘 띄울 수 없다. `-p` 옵션은 무시된다. 리눅스에서만 제대로 동작한다.

none은 루프백만 있는 네트워크다. 바깥과 전혀 통신하지 않아야 하는 일괄 작업에 쓴다.

overlay는 여러 호스트에 흩어진 컨테이너를 하나의 네트워크처럼 묶는다. 호스트 사이를 VXLAN 터널로 잇는데, Docker Swarm 모드에서 쓰는 드라이버다. 쿠버네티스는 이 자리를 자체 CNI 플러그인으로 채우므로 Docker의 overlay를 쓰지 않는다. 이 밖에 컨테이너에 물리 네트워크의 MAC 주소를 따로 주는 macvlan, ipvlan도 있다.

## 이름으로 찾아가는 사용자 정의 브리지

앱과 DB를 같은 사용자 정의 브리지에 올려 보자. 바꾸기 전 상태를 먼저 본다.

```bash
# 1) 확인: 지금 떠 있는 컨테이너와 붙어 있는 네트워크
docker ps --format 'table {{.Names}}\t{{.Networks}}\t{{.Ports}}'

# 2) 변경: appnet이라는 사용자 정의 브리지를 만든다
docker network create appnet

# 이미 떠 있는 db 컨테이너를 appnet에도 꽂는다 (재시작 없이 eth1이 하나 생긴다)
docker network connect appnet db

# 필요 없어지면 기본 브리지에서는 뺀다
docker network disconnect bridge db
```

`docker network inspect`로 서브넷과 붙어 있는 컨테이너를 본다.

```bash
# appnet의 설정과 붙은 컨테이너를 JSON으로 본다
docker network inspect appnet
```

볼 곳은 `IPAM.Config`의 서브넷과 `Containers`다. 기본 브리지가 172.17을 쓰고 있으니 새 네트워크는 다음 대역인 172.18을 받았다. 호스트에는 `br-` 뒤에 네트워크 ID 앞 12자리가 붙은 브리지 장치(`br-3c5e8f0a1b2d`)가 새로 생긴다(출력의 긴 ID와 일부 필드는 줄였다).

이제 앱을 같은 네트워크에 띄우고, 접속 주소의 호스트 자리에 컨테이너 이름을 적는다.

```bash
# app 컨테이너를 appnet에 띄운다. DB 주소의 호스트는 localhost가 아니라 db다
docker run -d --name app --network appnet \
  -e DATABASE_URL=postgres://app:change-me@db:5432/app \
  my-app:1.0

# 3) 확인: app 네트워크 안에서 db라는 이름이 무엇으로 풀리는지
docker run --rm --network appnet busybox nslookup db
```

```text
Server:		127.0.0.11
Address:	127.0.0.11:53

Non-authoritative answer:
Name:	db
Address: 172.18.0.2
```

질문을 받은 서버가 `127.0.0.11`이다. 사용자 정의 네트워크에 붙은 컨테이너의 `/etc/resolv.conf`에는 이 주소가 적혀 있고, 그건 Docker 엔진이 컨테이너 안에 심어 둔 내장 DNS다. 같은 네트워크에 있는 컨테이너 이름(과 `--network-alias`로 준 별칭)은 내장 DNS가 직접 답하고, `google.com` 같은 바깥 이름은 호스트의 DNS 서버로 넘긴다. Ubuntu는 호스트의 `/etc/resolv.conf`가 systemd-resolved의 `127.0.0.53`을 가리키는데, 이 주소는 컨테이너에서 닿지 않는다. 그래서 Docker는 그걸 감지하면 `/run/systemd/resolve/resolv.conf`에 있는 실제 업스트림 서버를 쓴다.

마지막 단계가 중요하다. `-p`는 호스트 바깥에서 컨테이너로 들어오는 길을 여는 옵션이지, 컨테이너끼리 통신하는 데는 필요 없다. 앱만 DB를 쓴다면 DB에는 `-p`를 붙이지 않는 게 맞다. 열지 않은 포트는 공격받을 일도 없다.

반대로 앱과 DB가 서로 다른 사용자 정의 네트워크에 있으면 이름도 안 풀리고 IP로도 닿지 않는다. 이 격리를 이용해서 프론트용 네트워크와 DB용 네트워크를 나누고, 둘 다에 붙는 앱 컨테이너만 다리 역할을 하게 만들기도 한다. `docker network create --internal`로 만든 네트워크는 바깥 인터넷으로 나가는 길까지 막는다.

기본 브리지에서 이름으로 접속하면 어떻게 되는지도 알아 두면 좋다. Node 앱이라면 `Error: getaddrinfo ENOTFOUND db`가 난다. 기본 브리지 컨테이너의 resolv.conf에는 내장 DNS가 아니라 호스트의 DNS 서버가 들어가기 때문이다.

게시하면 Docker는 호스트의 iptables nat 테이블에 DNAT 규칙을 넣는다. 목적지 주소를 컨테이너 IP로 바꿔 쓰는 규칙이다. 바꾸기 전과 후를 비교해 보자.

```bash
# 1) 확인: 지금 Docker가 nat 테이블에 넣은 DNAT 규칙
sudo iptables -t nat -S DOCKER

# 2) 변경: 기본 브리지에 nginx를 띄우고 8080을 게시한다
docker run -d --name web -p 8080:80 nginx:1.27

# 3) 확인: 규칙이 하나 늘었는지, 어디에 게시됐는지
sudo iptables -t nat -S DOCKER
docker port web
```

```text
-N DOCKER
-A DOCKER -i docker0 -j RETURN
-A DOCKER ! -i docker0 -p tcp -m tcp --dport 8080 -j DNAT --to-destination 172.17.0.2:80
```

```text
80/tcp -> 0.0.0.0:8080
80/tcp -> [::]:8080
```

</Callout>

`ss`로 보면 게시한 포트를 `docker-proxy`라는 프로세스가 듣고 있기도 하다. 대부분의 트래픽은 iptables DNAT이 커널에서 처리하고, docker-proxy는 호스트 자신이 `localhost:8080`으로 접속하는 경우처럼 DNAT이 닿지 않는 길을 메우는 보조 프로그램이다. 설정(`"userland-proxy": false`)으로 끌 수 있다.

## 컨테이너에서 호스트로 가는 길

거꾸로 컨테이너 안의 앱이 호스트에서 돌고 있는 서비스(호스트에 직접 깐 Postgres, 개발 중인 API 서버)에 붙어야 할 때도 있다. 이때 `localhost`가 안 되는 건 이제 안다. Docker Desktop은 `host.docker.internal`이라는 이름을 자동으로 넣어 주지만, 리눅스의 Docker Engine은 그러지 않는다. 직접 넣어 줘야 한다.

```bash
# host-gateway는 Docker가 호스트의 브리지 게이트웨이 주소로 바꿔 넣는 특별한 값이다
docker run --rm --add-host=host.docker.internal:host-gateway busybox \
  grep host.docker.internal /etc/hosts
```

```text
172.17.0.1	host.docker.internal
```

`host.docker.internal`이 `172.17.0.1`, 곧 호스트의 `docker0` 주소로 들어갔다. 여기서 두 번 막히는 경우가 많다. 하나는 호스트의 서비스가 `127.0.0.1`에만 묶여 있는 경우다. 패킷은 `docker0`의 172.17.0.1로 오는데 서비스는 루프백만 듣고 있으니 거절된다. 서비스를 `0.0.0.0`이나 `172.17.0.1`에 묶어야 한다. 다른 하나는 ufw다. 컨테이너에서 호스트로 오는 패킷은 이번에는 진짜 호스트가 목적지라 INPUT을 지난다. ufw 기본 정책이 deny라면 `sudo ufw allow in on docker0 to any port 5432`처럼 열어 줘야 한다.

## docker rm 하면 데이터가 왜 사라지나

두 번째 문제로 넘어가자. 컨테이너는 이미지의 읽기 전용 레이어 위에 얇은 쓰기 레이어를 하나 얹어서 만들어진다(레이어 이야기는 [Dockerfile과 이미지 레이어](/posts/dockerfile-image-layers)에서 다뤘다). 컨테이너 안에서 파일을 만들거나 고치면 전부 이 쓰기 레이어에 들어가고, 쓰기 레이어는 컨테이너와 생명을 같이한다. `docker stop`으로는 남아 있지만 `docker rm`을 하면 같이 지워진다. 컨테이너는 언제든 버리고 새로 만들 수 있어야 하니, 남겨야 할 데이터는 처음부터 컨테이너 바깥에 둬야 한다.

Postgres 공식 이미지는 사정이 조금 더 복잡하다. 이 이미지는 Dockerfile에 `VOLUME /var/lib/postgresql/data`를 선언해 두어서, `-v` 없이 띄워도 Docker가 이름 없는 익명 볼륨을 만들어 그 경로에 붙인다. 그래서 데이터는 사실 디스크에 남아 있다. 다만 `docker rm`으로 지우고 새로 띄우면 새 컨테이너는 또 다른 익명 볼륨을 받으니 빈 DB가 뜬다. 예전 데이터는 64자리 해시 이름의 볼륨으로 주인 없이 남는다. 데이터가 사라진 것처럼 보이는 이유가 이것이다. (Postgres 18 이미지부터는 선언된 볼륨 경로가 `/var/lib/postgresql`로 바뀌었으니, 쓰는 버전의 이미지 문서를 확인한다.)

```bash
# 주인 없이 남은 볼륨(어떤 컨테이너도 쓰지 않는 볼륨)을 본다
docker volume ls -f dangling=true
```

```text
DRIVER    VOLUME NAME
local     6f2d0a8c41b7e93d5a2f1c8e7b6d4a3f2e1d0c9b8a7f6e5d4c3b2a1f0e9d8c7b
```

## 데이터를 바깥에 두는 네 가지 방법

컨테이너가 파일을 쓸 수 있는 곳은 네 군데다.

쓰기 레이어는 아무 설정도 안 했을 때의 자리다. 컨테이너를 지우면 같이 사라지고, overlay2 같은 스토리지 드라이버를 거쳐서 쓰기 때문에 쓰기가 많은 작업(DB 파일)에는 느리다. 로그나 임시 파일처럼 버려도 되는 것만 둔다.

이름 있는 볼륨(named volume)은 Docker가 관리하는 저장 공간에 이름을 붙인 것이다. Ubuntu에서는 `/var/lib/docker/volumes/{이름}/_data`에 실제 파일이 있다. 컨테이너를 지워도 남고, 여러 컨테이너가 같은 볼륨을 붙일 수 있다. 경로나 권한을 Docker가 알아서 다루니 DB 데이터 같은 운영 데이터에 가장 무난하다. 빈 볼륨을 이미지에 이미 파일이 있는 경로에 처음 붙이면, Docker가 이미지 쪽 파일을 볼륨으로 복사해 준다는 것도 특징이다.

바인드 마운트(bind mount)는 호스트의 특정 경로를 컨테이너 안에 그대로 비춘다. 호스트에서 고친 소스가 바로 컨테이너에 보여서 개발할 때 편하고, 설정 파일 하나를 넣어 줄 때도 쓴다. 대신 호스트의 디렉터리 구조와 권한에 묶이고, 컨테이너 쪽 경로에 원래 있던 이미지 파일은 가려진다(복사해 주지 않는다).

tmpfs 마운트는 메모리에만 존재한다. 컨테이너가 멈추면 사라지고 디스크에 절대 쓰이지 않으니, 잠깐 쓰는 비밀 값이나 빠른 임시 공간에 쓴다. 리눅스에서만 된다.

## 볼륨을 만들고 들여다보기

볼륨은 `docker volume` 명령으로 다룬다.

```bash
# 볼륨을 만든다 (docker run -v pgdata:... 로 처음 쓸 때 자동으로 만들어지기도 한다)
docker volume create pgdata

# 목록
docker volume ls

# 실제 위치와 드라이버를 본다
docker volume inspect pgdata
```

```text
DRIVER    VOLUME NAME
local     pgdata
```

```text
[
    {
        "CreatedAt": "2026-10-16T10:12:03+09:00",
        "Driver": "local",
        "Labels": null,
        "Mountpoint": "/var/lib/docker/volumes/pgdata/_data",
        "Name": "pgdata",
        "Options": null,
        "Scope": "local"
    }
]
```

`Mountpoint`가 호스트 디스크의 실제 경로다. 이 디렉터리는 root만 읽을 수 있어서 `sudo ls /var/lib/docker/volumes/pgdata/_data`로 들여다볼 수는 있지만, 여기서 파일을 직접 고치는 건 피한다. 컨테이너 안에서 다루는 게 원칙이다. 볼륨이 어느 컨테이너에 붙어 있는지는 반대 방향에서 찾는다.

```bash
# pgdata를 쓰는 컨테이너 찾기 (멈춘 것 포함)
docker ps -a --filter volume=pgdata

# 볼륨이 차지하는 용량
docker system df -v
```

지우는 건 `docker volume rm pgdata`다. 쓰는 컨테이너가 있으면(멈춘 컨테이너도 포함) `volume is in use` 에러를 내고 거부한다. `docker volume prune`은 어떤 컨테이너도 쓰지 않는 볼륨을 지우는데, 최근 Docker(23 이후)는 기본으로 익명 볼륨만 지우고 이름 있는 볼륨까지 지우려면 `-a`를 붙여야 한다. 어느 쪽이든 되돌릴 방법이 없으니 아래 백업을 먼저 해 둔다.

## 볼륨을 tar로 백업하고 되살리기

볼륨은 Docker가 관리하는 경로에 있으니, 백업도 Docker 방식으로 한다. 임시 컨테이너 하나에 볼륨과 백업 받을 호스트 디렉터리를 같이 붙이고, 그 안에서 `tar`를 돌린다.

```bash
# 0) 일관된 백업을 위해 DB 컨테이너를 멈춘다 (켜 둔 채 파일을 복사하면 깨진 사본이 될 수 있다)
docker stop db

# 1) pgdata를 읽기 전용으로, 현재 디렉터리를 /backup으로 붙여 tar.gz로 묶는다
docker run --rm \
  -v pgdata:/data:ro \
  -v "$PWD":/backup \
  alpine tar czf /backup/pgdata-2026-10-16.tar.gz -C /data .

# 2) DB를 다시 켠다
docker start db

# 3) 확인: 백업 파일이 생겼고 내용이 보이는지
ls -lh pgdata-2026-10-16.tar.gz
tar tzf pgdata-2026-10-16.tar.gz | head -5
```

되살릴 때는 방향만 반대로 한다. 새 볼륨을 만들고 거기에 푼다.

```bash
# 새 볼륨을 만들고 백업을 푼다
docker volume create pgdata-restore
docker run --rm \
  -v pgdata-restore:/data \
  -v "$PWD":/backup:ro \
  alpine tar xzf /backup/pgdata-2026-10-16.tar.gz -C /data

# 같은 메이저 버전의 postgres로 붙여서 떠지는지 본다
docker run -d --name db-check -e POSTGRES_PASSWORD=change-me \
  -v pgdata-restore:/var/lib/postgresql/data postgres:16
docker logs db-check | tail -3
```

`-C /data .`로 디렉터리 안쪽부터 묶는 이유는, 풀 때 `data/` 같은 상위 디렉터리가 한 겹 더 생기지 않게 하려는 것이다. alpine의 tar는 소유자 UID를 숫자 그대로 보존하니 postgres(UID 999) 소유도 그대로 돌아온다.

DB라면 파일 백업 말고 `docker exec db pg_dump -U app app > app.sql` 같은 논리 백업이 더 안전하다. 파일 백업은 같은 메이저 버전에서만 열리고, 멈추지 않고 뜨면 일관성이 깨질 수 있다. 볼륨 tar 백업은 DB가 아닌 업로드 파일, 설정, 멈춰도 되는 데이터에 잘 맞는다.

## 바인드 마운트와 UID

바인드 마운트에서 가장 자주 막히는 건 권한이다. 리눅스 커널은 파일 주인을 이름이 아니라 숫자 UID로 기억하고, 컨테이너와 호스트는 같은 커널을 쓴다. 그래서 컨테이너 안에서 UID 0(root)으로 만든 파일은 호스트에서도 root 소유다. 이름이 같아도 UID가 다르면 다른 사람이다.

Node 프로젝트에서 의존성을 컨테이너로 설치해 보면 바로 보인다.

```bash
# 현재 디렉터리를 /app으로 붙이고 컨테이너 안(root)에서 npm install
docker run --rm -v "$PWD":/app -w /app node:22 npm install

# 확인: 숫자 UID로 소유자를 본다
ls -ln | grep node_modules
```

```text
drwxr-xr-x 120 0 0 4096 Oct 16 10:31 node_modules
```

소유자가 `0 0`, 곧 root다. 호스트의 내 계정(UID 1000)으로는 이 디렉터리를 지우지도 못한다. 이럴 때는 컨테이너를 내 UID로 돌린다.

```bash
# 소유권을 내 계정으로 되돌린다 (되돌리기)
sudo chown -R "$(id -u):$(id -g)" node_modules

# 처음부터 내 UID:GID로 컨테이너를 돌리면 생기는 파일도 내 소유다
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD":/app -w /app node:22 npm install
```

반대 방향도 있다. postgres 이미지는 데이터 디렉터리를 컨테이너 안의 postgres 사용자(Debian 계열 이미지에서 UID 999)로 바꿔 놓는다. 바인드 마운트로 붙인 호스트 디렉터리가 UID 999 소유, 권한 700이 되니 호스트의 내 계정으로는 열어 볼 수 없다.

```text
ls: cannot open directory '/home/ubuntu/pgdata-bind': Permission denied
```

그래서 DB 데이터는 바인드 마운트보다 이름 있는 볼륨이 편하다. 권한 문제를 Docker 쪽에 가둬 두기 때문이다. 바인드 마운트를 꼭 써야 하면 이미지가 쓰는 UID를 확인해 호스트 디렉터리를 그 UID로 맞춰 둔다. RHEL·Rocky 계열처럼 SELinux가 켜진 배포판은 UID가 맞아도 막히는데, 그때는 마운트 끝에 `:z`(여러 컨테이너 공유)나 `:Z`(이 컨테이너 전용)를 붙여 라벨을 바꿔 준다. Ubuntu는 기본으로 AppArmor를 쓰므로 이 옵션이 필요 없다.

## Postgres와 앱을 처음부터 다시 띄우기

이제 처음의 두 문제를 한 번에 고쳐 보자. 순서는 확인, 변경, 동작 확인, 영구성 확인, 되돌리기다.

```bash
# 1) 확인: 이름이 겹치는 컨테이너, 네트워크, 볼륨이 있는지
docker ps -a --filter name=db --filter name=app
docker network ls --filter name=appnet
docker volume ls --filter name=pgdata

# 2) 변경: 네트워크와 볼륨을 만들고
docker network create appnet
docker volume create pgdata

# DB는 포트를 게시하지 않는다. 앱만 같은 네트워크에서 db라는 이름으로 접속한다
docker run -d --name db --network appnet \
  -e POSTGRES_USER=app \
  -e POSTGRES_PASSWORD=change-me \
  -e POSTGRES_DB=app \
  -v pgdata:/var/lib/postgresql/data \
  --restart unless-stopped \
  postgres:16

# 앱은 리버스 프록시가 같은 호스트에 있다고 보고 루프백에만 게시한다
docker run -d --name app --network appnet \
  -e DATABASE_URL=postgres://app:change-me@db:5432/app \
  -p 127.0.0.1:8080:3000 \
  --restart unless-stopped \
  my-app:1.0
```

`--restart unless-stopped`는 컨테이너가 죽거나 호스트가 재부팅돼도 Docker가 다시 띄워 준다는 뜻이다. 사람이 `docker stop`으로 멈춘 경우만 예외다. 이게 컨테이너 쪽의 "영구 저장"에 해당한다.

동작을 확인한다. 테이블을 만들고 한 줄 넣는다.

```bash
# 3) 동작 확인: db 컨테이너 안의 psql로 테이블을 만들고 한 줄 넣는다
docker exec -it db psql -U app -d app \
  -c "CREATE TABLE notes (id serial PRIMARY KEY, body text);" \
  -c "INSERT INTO notes (body) VALUES ('hello');"

# 앱이 응답하는지
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/
```

이제 처음에 데이터가 날아갔던 그 동작을 일부러 해 본다.

```bash
# 4) 영구성 확인: 컨테이너를 지우고 같은 볼륨으로 다시 띄운다
docker rm -f db
docker run -d --name db --network appnet \
  -e POSTGRES_USER=app -e POSTGRES_PASSWORD=change-me -e POSTGRES_DB=app \
  -v pgdata:/var/lib/postgresql/data \
  --restart unless-stopped postgres:16

docker exec -it db psql -U app -d app -c "SELECT * FROM notes;"
```

```text
 id | body
----+-------
  1 | hello
(1 row)
```

컨테이너는 새것인데 데이터는 그대로다. 앱 쪽은 아무것도 바꾸지 않았는데 다시 붙는다. 새 db 컨테이너의 IP가 달라졌더라도 이름 `db`가 새 IP로 풀리기 때문이다. 참고로 `POSTGRES_PASSWORD` 같은 초기화 변수는 데이터 디렉터리가 비어 있을 때 처음 한 번만 쓰인다. 볼륨에 데이터가 있으면 값을 바꿔도 비밀번호가 바뀌지 않는다.

<Callout kind="warning" title="볼륨을 지우는 명령은 되돌릴 수 없다">
  `docker volume rm pgdata`, `docker volume prune -a`, `docker rm -v`(컨테이너의 익명 볼륨까지 삭제)는 디스크에서 데이터를 바로 지운다. 실행 전에 `docker ps -a --filter volume=pgdata`로 누가 쓰는지 보고, 위의 tar 백업이나 `pg_dump`를 먼저 떠 둔다. 복구는 그 백업을 새 볼륨에 푸는 것뿐이다.
</Callout>

다 실험했으면 만든 것들을 거꾸로 지운다.

```bash
# 5) 되돌리기: 컨테이너, 네트워크를 지운다. 데이터까지 지울 때만 마지막 줄을 실행한다
docker rm -f app db
docker network rm appnet
# docker volume rm pgdata
```

컨테이너 여러 개를 이렇게 `docker run` 몇 줄로 맞춰 띄우다 보면, 옵션 하나를 빠뜨리거나 순서가 꼬이기 쉽다. 같은 구성을 파일 하나로 적어 두는 방법이 [Docker Compose](/posts/docker-compose)다.

## 격리를 얼마나 풀어 줄지 정하는 일

컨테이너는 네트워크도 파일도 따로 갖고 태어난다. 사용자 정의 브리지는 같은 네트워크의 컨테이너끼리만 이름으로 통하게 풀어 주고, `-p`는 호스트의 특정 주소와 포트에서 들어오는 길만 DNAT로 열어 준다. 볼륨은 컨테이너의 수명과 데이터의 수명을 떼어 놓는다. `localhost`가 안 되고 `docker rm`에 데이터가 사라졌던 건, 이 격리를 아직 풀어 주지 않았기 때문이다.

## 면접에서 나올 만한 질문

### 컨테이너 안에서 localhost로 DB에 접속하면 왜 안 되나요?

컨테이너마다 네트워크 네임스페이스가 따로 있어서, 컨테이너 안의 localhost는 그 컨테이너 자신의 루프백이기 때문이다. DB가 다른 컨테이너에 있으면 그 컨테이너의 5432에는 아무도 듣고 있지 않아 연결이 거부된다. 같은 사용자 정의 네트워크에 두고 컨테이너 이름(서비스 이름)으로 접속하는 게 맞다.

### 기본 bridge 네트워크와 사용자 정의 bridge 네트워크는 무엇이 다른가요?

사용자 정의 브리지는 Docker 내장 DNS(127.0.0.11)가 붙어서 컨테이너 이름으로 서로를 찾을 수 있고, 다른 네트워크와 격리된다. 기본 브리지는 IP로만 통신되고, 이름 해석은 레거시인 --link로만 됐다. 여러 컨테이너를 엮을 때는 항상 사용자 정의 네트워크를 만든다.

### -p 8080:80은 내부적으로 어떻게 동작하나요?

Docker가 호스트의 iptables nat 테이블 DOCKER 체인에 DNAT 규칙을 넣어, 호스트 8080으로 온 패킷의 목적지를 컨테이너 IP의 80으로 바꾼다. 바뀐 패킷은 FORWARD를 지나 브리지를 거쳐 컨테이너로 가고, 응답은 conntrack이 역변환한다. 호스트 자신의 localhost 접속처럼 DNAT이 닿지 않는 경우는 docker-proxy가 메운다.

### ufw로 막았는데 왜 컨테이너 포트가 밖에서 열려 있나요?

게시 포트로 온 패킷은 PREROUTING에서 목적지가 컨테이너로 바뀌어 INPUT이 아니라 FORWARD로 가는데, ufw의 허용·차단 규칙은 INPUT 쪽에 있기 때문이다. 게다가 -p에 IP를 생략하면 0.0.0.0에 묶인다. 바깥에 열 필요가 없으면 127.0.0.1에 게시하고, 걸러야 하면 DOCKER-USER 체인에 규칙을 넣는다.

### 컨테이너에서 호스트의 서비스에 접속하려면 어떻게 하나요?

리눅스에서는 --add-host=host.docker.internal:host-gateway로 호스트의 브리지 게이트웨이 주소(기본 172.17.0.1)를 이름으로 넣어 준다. 호스트 서비스가 127.0.0.1에만 묶여 있으면 닿지 않으니 그 주소에서도 듣게 해야 한다. 이 트래픽은 호스트의 INPUT을 지나므로 ufw에서 docker0 인터페이스를 허용해야 할 수도 있다.

### named volume과 bind mount는 언제 각각 쓰나요?

DB 데이터처럼 Docker가 수명과 권한을 관리해도 되는 운영 데이터는 named volume을 쓴다. 호스트의 정확한 경로가 중요한 경우, 곧 개발 중 소스 코드를 실시간으로 비추거나 설정 파일 하나를 넣을 때는 bind mount를 쓴다. bind mount는 호스트의 UID·권한과 디렉터리 구조에 묶이고, 이미지에 있던 파일을 가린다는 점을 감안한다.

### 볼륨은 어떻게 백업하나요? 돌고 있는 DB 볼륨을 그대로 tar로 떠도 되나요?

볼륨과 호스트 디렉터리를 함께 붙인 임시 컨테이너에서 tar로 묶는다. 다만 돌고 있는 DB의 파일을 그대로 복사하면 쓰는 도중의 상태가 섞여 일관성이 깨질 수 있다. DB는 컨테이너를 멈추고 뜨거나, pg_dump 같은 논리 백업을 쓰는 편이 안전하다.

### 바인드 마운트한 디렉터리의 파일이 root 소유가 되는 이유와 해결법은요?

컨테이너와 호스트는 같은 커널을 쓰고 파일 주인을 숫자 UID로 기록하기 때문에, 컨테이너 안에서 root(UID 0)로 만든 파일은 호스트에서도 root 소유다. --user "$(id -u):$(id -g)"로 컨테이너를 호스트 사용자 UID로 돌리거나, 이미지가 쓰는 UID에 맞춰 호스트 디렉터리 소유자를 바꾼다. 근본적으로 UID를 분리하려면 userns-remap이나 rootless 모드를 쓴다.
