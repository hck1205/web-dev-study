비밀번호 없이 메일로 로그인 링크를 보내는 기능을 만들었다고 해 보자. 링크는 `GET /login/verify?token=...`이고, 서버는 이 주소가 열리면 토큰을 확인해 세션을 만들고 토큰을 지운다. 한 번 쓰면 끝나는 링크다. 그런데 회사 메일을 쓰는 사용자들이 "링크를 눌렀더니 이미 사용된 링크라고 나온다"고 한다.

사용자보다 먼저 링크를 연 쪽이 있었다. 기업용 메일 보안 서비스는 메일 속 링크가 피싱 사이트인지 확인하려고 받은 링크를 미리 열어 본다. 메신저가 링크 미리보기를 만들 때도 같은 일이 일어난다. 이들은 GET 요청이라면 열어 봐도 아무것도 바뀌지 않는다고 믿는다. 그 믿음은 근거가 있다. HTTP가 GET에 그런 약속을 붙여 두었기 때문이다. 이 링크는 약속을 어겼다.

HTTP 메서드는 요청 줄 맨 앞의 단어 하나지만, 그 단어에는 "이 요청은 무엇을 바꾸는가", "두 번 보내도 되는가" 같은 약속이 담겨 있다. 메시지의 생김새는 [HTTP 메시지는 어떻게 생겼나](/posts/http-message)에서 봤고, 여기서는 그 첫 단어가 하는 약속을 본다.

## 안전, 멱등, 캐시 가능

위의 성질 세 가지는 HTTP 의미론 표준(RFC 9110)에 정의가 있다. 말이 비슷해 보여도 가리키는 대상이 다르다.

안전(safe)은 클라이언트가 이 요청으로 서버 상태가 바뀌기를 요청하지도, 기대하지도 않는다는 뜻이다. GET, HEAD, OPTIONS, TRACE가 안전하다. 여기서 중요한 단어는 "요청하지도 기대하지도"다. 서버가 GET을 받고 접근 로그를 남기거나 조회수를 올리는 건 상관없다. 그건 서버가 알아서 한 일이고, 클라이언트가 바란 게 아니다. 다만 그 부수 효과로 문제가 생기면 책임은 서버에 있다. 처음 장면의 로그인 링크가 바로 그 경우다. 크롤러, 메일 스캐너, 브라우저 프리페치처럼 사람이 누르지 않아도 GET을 보내는 프로그램은 모두 이 약속을 믿고 움직인다.

멱등(idempotent)은 같은 요청을 여러 번 보냈을 때 서버에 의도한 효과가 한 번 보낸 것과 같다는 뜻이다. PUT과 DELETE, 그리고 안전한 메서드 전부가 멱등이다. 아무것도 바꾸지 않으면 몇 번을 해도 같으니, 안전한 메서드는 자동으로 멱등이다. 반대는 성립하지 않는다. DELETE는 멱등하지만 안전하지 않다.

멱등은 응답이 같다는 말이 아니다. `DELETE /orders/7`을 두 번 보내면 처음엔 204, 다음엔 404가 온다. 그래도 서버 상태는 "주문 7이 없다"로 같으니 멱등이다. 반대로 `DELETE /orders/latest`처럼 주소가 매번 다른 대상을 가리키게 설계하면 메서드가 DELETE여도 두 번 보낼 때 두 개가 지워진다. 멱등성은 메서드 이름이 보장해 주는 게 아니라, 서버가 그 의미대로 구현해야 생기는 성질이다.

캐시 가능(cacheable)은 응답을 저장했다가 다음 요청에 재사용해도 되느냐다. 표준이 캐시 가능하다고 정한 메서드는 GET, HEAD, POST다. POST는 응답에 명시적인 유효 기간과 `Content-Location`이 있어야 한다는 까다로운 조건이 붙어서, 실제로 POST 응답을 캐시하는 브라우저나 CDN은 거의 없다. 사실상 GET과 HEAD만 캐시된다고 보면 된다. 캐시 규칙은 [HTTP 캐시와 CDN](/posts/http-caching-cdn)에서 자세히 다뤘다.

멱등이 왜 따로 이름을 가질 만큼 중요하냐면, 네트워크에서는 "요청이 갔는지 모르는" 상황이 늘 생기기 때문이다. 요청을 보냈는데 응답이 오기 전에 연결이 끊겼다. 서버가 처리를 했는지 안 했는지 클라이언트는 알 수 없다. 멱등한 요청이면 고민할 것 없이 다시 보내면 된다. 그래서 HTTP 클라이언트와 프록시는 멱등한 요청만 자동으로 재시도한다. nginx도 1.9.13부터 POST, PATCH 같은 멱등하지 않은 요청은 이미 뒷단에 보냈다면 다른 서버로 다시 보내지 않는다(`proxy_next_upstream`에 `non_idempotent`를 주지 않는 한).

  const result = { ...target };
  for (const [key, value] of Object.entries(patch)) {
    if (value === null) {
      delete result[key];
    } else if (typeof value === "object" && !Array.isArray(value)) {
      const base = result[key] && typeof result[key] === "object" && !Array.isArray(result[key]) ? result[key] : {};
      result[key] = mergePatch(base, value);
    } else {
      result[key] = value;
    }
  }
  return result;
}

function applyRequest(state, req) {
  switch (req.method) {
    case "PUT":
      return JSON.parse(JSON.stringify(req.body));
    case "PATCH":
      return state === null ? null : mergePatch(state, req.body);
    case "POST":

      return null;
    default:
      return state; // GET, HEAD는 아무것도 바꾸지 않는다

}

  let state = initial;

  return state;

## PUT은 통째로, PATCH는 일부만

위에서 PUT 한 번에 쿠폰이 사라졌다. PUT은 "이 본문이 자원의 새 모습 전체"라는 뜻이라서, 본문에 없는 필드는 지워지는 게 맞다. 실무에서 이름은 PUT인데 보낸 필드만 고치는 API를 자주 본다. 그렇게 만들면 클라이언트는 "빠진 필드는 지워지는지, 그대로인지"를 문서를 봐야만 알 수 있다. 일부만 고치려면 PATCH를 쓴다.

PUT은 주소도 클라이언트가 정한다. `PUT /users/matt/avatar`는 그 주소에 이 내용을 두라는 뜻이고, 몇 번을 보내도 그 자리 하나만 덮어쓴다. POST는 `POST /orders`처럼 모음(collection)에 보내고, 새 주문의 주소는 서버가 정해 `Location`으로 알려 준다. 그래서 같은 POST를 두 번 보내면 주소가 다른 주문이 두 개 생긴다.

PATCH 본문의 형식은 정해져 있지 않다. 그래서 형식을 `Content-Type`으로 밝히는데, 표준으로 정해진 JSON 형식이 두 가지 있다.

JSON Merge Patch(RFC 7396, `application/merge-patch+json`)는 고칠 필드만 적은 JSON이다. 위 연습에서 쓴 방식이다. 적은 필드는 덮어쓰고, 값이 `null`이면 지우고, 객체는 안쪽까지 합친다. 읽고 쓰기 쉽다. 대신 필드 값을 진짜 `null`로 만들 수 없고, 배열은 통째로 바꾸는 것만 된다. 배열 중간에 항목 하나를 넣는 건 표현할 수 없다.

JSON Patch(RFC 6902, `application/json-patch+json`)는 변경 지시의 목록이다.

```json
[
  { "op": "test", "path": "/version", "value": 3 },
  { "op": "replace", "path": "/memo", "value": "문 앞" },
  { "op": "add", "path": "/items/-", "value": "milk" }
]
```

`add`, `remove`, `replace`, `move`, `copy`, `test` 여섯 가지가 있고, 목록 전체가 한 번에 적용되거나 하나라도 실패하면 아무것도 적용되지 않는다. 배열 끝에 추가하는 `/items/-` 같은 표현이 가능한 대신, 이 지시는 보낼 때마다 우유가 하나씩 늘어난다. 같은 PATCH라도 Merge Patch는 멱등이고 이 JSON Patch는 멱등이 아니다. PATCH가 "멱등 보장 X"인 이유다. 맨 앞의 `test`처럼 현재 값이 예상과 같을 때만 적용하게 하면 다시 보내도 두 번째는 실패하므로 안전해진다.

멱등이라고 해서 동시에 고치는 문제까지 풀리는 건 아니다. 나와 동료가 같은 문서를 열어 각자 PUT으로 저장하면 나중에 저장한 쪽이 앞사람의 수정을 통째로 지운다(lost update). 이건 조건부 요청으로 막는다. 문서를 읽을 때 받은 `ETag`를 `If-Match`에 실어 보내면, 그사이 누가 바꿔서 ETag가 달라졌을 때 서버가 `412 Precondition Failed`로 거절한다.

```
PUT /docs/42 HTTP/1.1
If-Match: "v7"
Content-Type: application/json

{"title":"회의록","body":"..."}
```

POST를 멱등하게 만드는 방법은 두 가지다. 하나는 그림 끝처럼 멱등성 키를 쓰는 것이다. 키를 언제 저장하고 얼마나 보관하는지, 처리 중에 같은 키가 또 오면 어떻게 하는지는 [장애가 번지지 않게](/posts/resilience-patterns)에서 다뤘다. 다른 하나는 클라이언트가 주문 번호를 먼저 만들어 `PUT /orders/{uuid}`로 보내는 것이다. 주소가 고정되니 몇 번 보내도 그 자리 하나만 덮어쓴다.

브라우저에서도 같은 문제가 있다. POST로 폼을 제출한 결과 페이지에서 새로고침을 누르면 브라우저가 "양식을 다시 제출하겠느냐"고 묻는다. POST를 다시 보내면 무슨 일이 생길지 모르기 때문이다. 그래서 폼 처리 후에는 결과를 바로 그리지 않고 `303 See Other`로 결과 페이지에 보내서 GET으로 다시 열게 한다. Post/Redirect/Get(PRG) 패턴이다. 그러면 새로고침은 안전한 GET만 다시 보낸다.

## GET에 본문을 싣지 않는 이유

검색 조건이 길어지면 GET에 JSON 본문을 싣고 싶어진다. 스펙(RFC 9110)은 GET 요청 본문에 정해진 의미가 없고, 본문이 요청의 의미나 대상을 바꿀 수 없으며, 일부 구현이 요청 스머글링 위험 때문에 그런 요청을 거절하고 연결을 끊을 수 있다고 적어 두었다. 실제로 막히는 곳이 많다.

- 브라우저 `fetch`는 GET이나 HEAD에 `body`를 주면 요청을 보내지도 않고 `TypeError`를 던진다.
- 캐시는 주소만 키로 쓰고 본문은 보지 않는다. 본문만 다른 두 GET이 같은 캐시 사본을 받는다.
- 프록시나 로드 밸런서, API 게이트웨이 중 일부는 GET 본문을 버리거나 요청을 거절한다.

Elasticsearch의 `_search`처럼 GET 본문을 받아 주는 서버도 있지만, 그런 API도 같은 요청을 POST로 받게 열어 둔다. 조건이 길면 POST로 검색을 보내는 게 현실적이다. 대신 POST라서 캐시와 자동 재시도의 혜택을 잃는다. 이 틈을 메우려고 IETF에서 본문을 실을 수 있는 안전한 메서드 `QUERY`를 표준화하는 작업이 진행되어 왔지만, 이 글을 쓰는 시점에 지원하는 서버와 CDN이 넓지 않다.

## HEAD와 OPTIONS는 묻기만 한다

HEAD는 GET과 같은 처리를 하고 본문만 빼서 돌려준다. 그래서 응답 헤더도 GET과 같아야 한다. 2GB짜리 파일을 내려받기 전에 `Content-Length`로 크기를 보거나, `Last-Modified`와 `ETag`로 바뀌었는지 확인하거나, 링크가 살아 있는지 점검할 때 쓴다. 헤더를 만들려면 결국 GET만큼 일을 하는 서버도 많으니 무조건 가볍다고 보면 안 된다. 많은 프레임워크가 GET 라우트를 만들면 HEAD를 자동으로 붙여 준다.

OPTIONS는 원래 "이 자원에 무엇을 할 수 있는가"를 묻는 메서드다. 응답의 `Allow` 헤더에 쓸 수 있는 메서드를 적는다. 지금은 대부분 CORS preflight로 만난다. 다른 출처로 PUT이나 JSON POST를 보내기 전에 브라우저가 OPTIONS로 허락을 먼저 받는 절차다. 자세한 흐름은 [CORS](/posts/cors)에 있다. preflight 요청에는 쿠키나 `Authorization`이 실리지 않으니, 인증 미들웨어가 OPTIONS까지 막아서 401을 내면 실제 요청은 영원히 나가지 못한다.

## 405와 Allow, 대소문자

자원은 있는데 그 메서드를 받지 않으면 `405 Method Not Allowed`다. 이때 서버는 `Allow` 헤더로 쓸 수 있는 메서드를 반드시 알려야 한다.

```
HTTP/1.1 405 Method Not Allowed
Allow: GET, HEAD, OPTIONS
```

서버가 아예 모르는 메서드라면 `501 Not Implemented`다. 405는 "이 자원에는 안 된다", 501은 "이 서버는 그런 메서드를 모른다"다.

메서드 이름은 대소문자를 가린다. `GET`과 `get`은 다른 메서드다. 헤더 이름이 대소문자를 가리지 않는 것과 반대라서 헷갈린다. 여기서 실무 함정이 하나 나온다. 브라우저 `fetch`는 `get`, `post`, `put`, `delete`, `head`, `options`는 대문자로 바꿔 주지만 `patch`는 바꾸지 않는다. `fetch(url, { method: "patch" })`는 소문자 `patch`를 그대로 보내고, 서버는 모르는 메서드로 보고 거절한다. PATCH는 항상 대문자로 쓴다.

## 폼은 GET과 POST만 안다

HTML `<form>`의 `method`는 `get`과 `post`만 HTTP 요청이 된다(`dialog`는 대화 상자를 닫는 용도라 요청을 보내지 않는다). `method="delete"`라고 적으면 브라우저는 GET으로 보낸다. 자바스크립트 없이 PUT이나 DELETE를 보낼 방법이 없어서, Rails나 Laravel 같은 프레임워크는 POST 폼에 `_method=DELETE` 같은 숨은 필드를 넣고 서버가 메서드를 바꿔 읽는 방식(method override)을 쓴다. `X-HTTP-Method-Override` 헤더로 같은 일을 하는 API도 있다.

이 기능은 POST에서만 허용해야 한다. GET에도 override를 허용하면 `/posts/42?_method=DELETE` 같은 링크 하나로 글이 지워진다. 다른 사이트에 이 링크를 심어 두고 로그인한 사용자가 누르게 하면, 쿠키가 따라가서 CSRF 공격이 된다. 링크로 넘어가는 최상위 GET에는 `SameSite=Lax` 쿠키도 실린다.

## CONNECT와 TRACE

CONNECT는 프록시에게 "이 호스트까지 TCP 터널을 뚫어 달라"고 하는 메서드다. 회사망처럼 HTTP 프록시를 거쳐야 하는 환경에서 HTTPS 사이트에 접속하면, 클라이언트는 먼저 프록시에 CONNECT를 보내고 터널이 열리면 그 안에서 TLS를 시작한다. 프록시 설정이 된 환경에서 `curl -v`를 해 보면 첫 줄에 이게 보인다.

```
> CONNECT example.com:443 HTTP/1.1
> Host: example.com:443
```

다른 메서드와 달리 요청 대상이 경로가 아니라 `호스트:포트`다. 프록시는 암호화된 내용을 보지 못하고 바이트만 넘긴다.

TRACE는 서버가 받은 요청을 그대로 본문에 담아 돌려주는 디버깅용 메서드다. 중간 프록시가 요청을 어떻게 바꿨는지 볼 수 있다. 그런데 이걸로 자바스크립트가 읽을 수 없게 해 둔 `HttpOnly` 쿠키를 응답 본문에서 읽어 내는 공격(Cross-Site Tracing)이 알려진 뒤로 대부분의 서버가 꺼 둔다. 브라우저도 `fetch`와 `XMLHttpRequest`에서 CONNECT, TRACE를 금지 메서드로 막는다.

## 스펙대로 하지 않는 서버들

메서드의 의미는 약속일 뿐, 서버가 지키지 않아도 요청은 처리된다. 그래서 어긴 대가는 늦게, 엉뚱한 곳에서 나타난다.

상태를 바꾸는 GET이 가장 흔하다. 처음 장면의 로그인 링크, `GET /logout`, 관리 화면의 삭제 링크가 그렇다. 크롤러와 메일 스캐너, 링크 미리보기, 브라우저의 프리페치와 프리렌더가 사람 대신 이 주소를 연다. 보안 문제도 있다. 쿠키의 `SameSite=Lax`는 다른 사이트에서 넘어오는 최상위 GET 이동에는 쿠키를 붙여 준다. 상태를 바꾸는 GET은 이 보호를 그대로 통과한다. 쿠키와 CSRF 이야기는 [쿠키와 세션으로 로그인 상태 유지하기](/posts/cookie-session-login)에 있다.

반대로 모든 걸 POST로 보내는 API도 있다. GraphQL이 대표적이다. 조회도 POST로 보내면 HTTP 캐시와 CDN을 쓸 수 없고, 클라이언트가 실패한 요청을 안심하고 재시도할 수 없다. 그래서 GraphQL 서버들도 조회는 GET으로 받아 CDN에 캐시하는 방법(persisted query 등)을 따로 지원한다.

상태 코드도 비슷하다. 실패했는데 `200 OK`에 `{"error": ...}`를 담아 보내면 프록시, 모니터링, 재시도 로직이 모두 성공으로 읽는다. 이건 [HTTP 상태 코드](/posts/http-status-codes)에서 이어서 다룬다.

## 프록시는 멱등성을 보고 재시도를 고른다

멱등성은 면접에서만 나오는 말이 아니다. 내가 짠 코드가 재시도를 하지 않아도, 앞단의 프록시가 메서드를 보고 대신 재시도할지 정한다. Ubuntu 24.04의 nginx 1.24로 확인해 봤다. 업스트림을 두 대 두고, 한 대(18602번)는 요청을 받자마자 연결을 끊게 만들었다. 나머지 한 대(18601번)는 정상이다.

```nginx
upstream two {
    server 127.0.0.1:18602 max_fails=0;  # 요청을 받으면 바로 끊는 서버
    server 127.0.0.1:18601;              # 정상 서버
}

server {
    listen 127.0.0.1:18610;
    location /retry/ { proxy_pass http://two/; }
}
```

같은 주소에 POST 두 번, GET 두 번을 보낸다. 라운드 로빈이라 매번 고장 난 서버부터 번갈아 걸린다.

```bash
# 주문을 만드는 POST 두 번
for i in 1 2; do
  curl -s -o /dev/null -w '%{http_code}\n' -X POST -H 'Content-Type: application/json' -d '{"item":"book"}' http://localhost:18610/retry/echo
done

# 조회하는 GET 두 번
for i in 1 2; do
  curl -s -o /dev/null -w '%{http_code}\n' http://localhost:18610/retry/echo
done
```

```text
200
```

GET은 고장 난 서버에 걸려도 200이 나왔는데 POST는 502를 받았다. access.log에 `$upstream_status`를 남기게 해 두면 이유가 보인다.

```text
127.0.0.1 "POST /retry/echo HTTP/1.1" 502 166 rt=0.001 ups=502 urt=0.001
127.0.0.1 "POST /retry/echo HTTP/1.1" 200 90 rt=0.002 ups=200 urt=0.002
127.0.0.1 "GET /retry/echo HTTP/1.1" 200 56 rt=0.003 ups=502, 200 urt=0.001, 0.002
127.0.0.1 "GET /retry/echo HTTP/1.1" 200 56 rt=0.002 ups=200 urt=0.001
```

세 번째 줄의 `ups=502, 200`이 재시도의 흔적이다. GET은 첫 서버가 끊자 nginx가 다음 서버로 다시 보내서 사용자는 실패를 모른다. 첫 줄의 POST는 `ups=502` 하나로 끝났다. nginx는 1.9.13부터 POST, LOCK, PATCH 같은 멱등이 아닌 요청을, 이미 업스트림에 보낸 뒤에는 다음 서버로 넘기지 않는다. 첫 서버가 주문을 만들고 나서 끊겼을 수도 있기 때문이다. error.log에는 두 요청 모두 같은 줄이 남는다.

```text
2026/10/18 11:01:28 [error] 899#899: *1 upstream prematurely closed connection while reading response header from upstream, client: 127.0.0.1, server: , request: "POST /retry/echo HTTP/1.1", upstream: "http://127.0.0.1:18602/echo", host: "localhost:18610"
```

그래서 배포나 서버 장애 때 "GET은 멀쩡한데 주문·결제 API만 502가 튄다"는 증상이 나온다. 이걸 없애겠다고 `proxy_next_upstream ... non_idempotent;`를 켜면 502는 줄지만 주문이 두 번 생길 수 있는 길을 직접 여는 셈이다. 옳은 순서는 앞에서 본 멱등성 키를 먼저 붙이고, 서버가 같은 키를 걸러 낼 수 있게 된 뒤에야 재시도를 허락하는 것이다. 클라이언트 라이브러리도 같다. axios-retry나 SDK의 재시도 기본값이 어떤 메서드를 다시 보내는지 한 번은 확인해 둔다.

정적 파일 경로에 POST를 보내 405를 받는 경우도 자주 본다. 폼의 `action`이 비어 있거나 API 경로 앞의 프록시 설정이 빠져, 요청이 정적 파일을 서빙하는 `location`으로 떨어진 것이다.

```bash
# 정적 파일에 POST를 보낸다
curl -si -X POST http://localhost:18610/app.css | head -1
```

```text
HTTP/1.1 405 Not Allowed
```

nginx 정적 서빙은 GET과 HEAD만 받는다. 여기서 나온 405에는 앱이 붙이던 `Allow` 헤더도 없고, 이유 문구도 표준의 `Method Not Allowed`가 아니라 `Not Allowed`다. 응답의 `Server` 헤더와 이 문구만 봐도 앱까지 가지 못했다는 걸 안다. 앱 라우터가 만든 405인지, 프록시가 만든 405인지부터 가르면 어디를 고칠지가 정해진다. 프록시 설정 자체는 [nginx 리버스 프록시](/posts/nginx-reverse-proxy)에서 다룬다.

## 다시 메일 링크로

로그인 링크는 GET으로 열리는 확인 페이지만 보여 주고, 실제 로그인은 그 페이지의 버튼이 보내는 POST에서 하게 바꾸면 된다. 스캐너는 링크를 열어도 버튼을 누르지 않는다. 메서드는 요청 줄의 단어 하나지만, 그 단어를 보고 브라우저, 캐시, 프록시, 크롤러, 재시도 로직이 각자 행동을 정한다. GET은 읽기만 하고, PUT과 DELETE는 몇 번 보내도 같고, POST는 한 번만 보내야 한다. 이 약속을 지키면 중간의 모든 프로그램이 나를 도와주고, 어기면 그 프로그램들이 사고를 낸다.

## 면접에서 나올 만한 질문

### 안전한 메서드와 멱등한 메서드의 차이는요?

안전은 클라이언트가 서버 상태 변경을 요청하지 않는다는 뜻이고, GET·HEAD·OPTIONS·TRACE가 해당한다. 멱등은 같은 요청을 여러 번 보내도 서버에 의도한 효과가 한 번과 같다는 뜻이고, 안전한 메서드에 PUT과 DELETE가 더해진다. 안전하면 항상 멱등이지만, DELETE처럼 멱등이어도 안전하지 않은 메서드가 있다. 로그 기록 같은 서버의 부수 효과는 이 정의에 포함되지 않는다.

### DELETE를 두 번 보내면 두 번째는 404인데, 그래도 멱등인가요?

멱등이다. 멱등성은 응답이 아니라 서버 상태에 대한 정의이고, 두 번 보낸 뒤에도 "그 자원이 없다"는 상태는 같다. 다만 `/orders/latest`처럼 요청할 때마다 다른 자원을 가리키는 주소를 만들면 DELETE여도 멱등이 깨진다. 멱등성은 메서드 이름이 아니라 서버 구현이 지켜야 하는 성질이다.

### PUT과 PATCH는 어떻게 다른가요?

PUT은 본문을 자원의 새 모습 전체로 보고 통째로 바꾸므로, 본문에 없는 필드는 사라진다. PATCH는 본문에 적은 변경 지시대로 일부만 바꾼다. PUT은 멱등이지만 PATCH는 형식에 따라 다르다. JSON Merge Patch처럼 값을 덮어쓰는 방식은 멱등이고, JSON Patch의 배열 추가(`/items/-`)처럼 상대적인 변경은 멱등이 아니다.

### POST는 왜 멱등이 아니고, 결제 같은 요청은 어떻게 안전하게 재시도하나요?

POST는 모음에 보내 서버가 새 자원과 주소를 정하므로, 두 번 보내면 자원이 두 개 생긴다. 응답만 유실된 경우 클라이언트는 성공 여부를 알 수 없어 재시도가 위험하다. 클라이언트가 고유한 멱등성 키를 헤더에 붙이고 서버가 키별로 처음 결과를 저장했다가 돌려주거나, 클라이언트가 ID를 정해 PUT으로 보내는 방식으로 멱등하게 만든다.

### 멱등한 요청이면 동시에 보내도 문제가 없나요?

아니다. 멱등성은 같은 요청을 반복할 때의 이야기이고, 서로 다른 클라이언트가 같은 자원을 고치는 경쟁은 막지 못한다. 두 사람이 각자 PUT하면 나중 요청이 앞의 수정을 덮는다. 읽을 때 받은 ETag를 `If-Match`에 실어 보내고, 그사이 바뀌었으면 412로 거절하는 조건부 요청으로 막는다.

### GET 요청에 본문을 넣으면 안 되나요?

스펙상 GET 본문에는 정해진 의미가 없고, 일부 구현은 스머글링 위험 때문에 거절한다. 브라우저 fetch는 아예 에러를 내고, 캐시는 본문을 키로 쓰지 않아 다른 요청이 같은 사본을 받을 수 있다. 조건이 길면 POST로 검색하거나 쿼리 문자열을 쓴다. 이 틈을 메우려는 QUERY 메서드가 표준화 중이지만 아직 지원이 넓지 않다.

### OPTIONS 메서드는 어디에 쓰이나요?

대상 자원이 지원하는 메서드를 묻는 용도이고, 응답의 `Allow`에 목록을 적는다. 실무에서는 대부분 CORS preflight로 만난다. 브라우저가 교차 출처로 PUT이나 JSON POST를 보내기 전에 OPTIONS로 허락을 받는다. preflight에는 인증 정보가 없으므로 서버는 OPTIONS를 인증 없이 통과시켜야 한다.

### GET으로 상태를 바꾸면 어떤 문제가 생기나요?

크롤러, 메일 보안 스캐너, 링크 미리보기, 브라우저 프리페치가 GET은 안전하다고 믿고 사람 대신 주소를 열어서 의도치 않은 변경이 일어난다. 보안 면에서는 `<img>` 태그 하나로 요청을 일으킬 수 있고, SameSite=Lax 쿠키도 최상위 GET 이동에는 실리므로 CSRF에 그대로 노출된다. 상태 변경은 POST·PUT·PATCH·DELETE로 하고, 링크로 시작해야 하면 확인 페이지에서 POST를 보내게 한다.
