<EasyIntro>
  컴퓨터의 메모리는 똑같이 생긴 사물함이 끝없이 늘어선 복도 같다. 프로그램이 "이름을 적을 사물함 16칸을 줘"라고 하면 복도의 한 구역을 받는다. 그런데 20글자짜리 이름을 억지로 밀어 넣으면, 받은 16칸을 넘어 옆 사물함까지 글자가 흘러 들어간다.

  옛날 언어인 C는 "16칸만 써"라고 말해 주지 않는다. 그래서 프로그래머가 매번 길이를 재야 하고, 한 번 깜빡하면 바로 사고가 난다.

  이걸 막는 길은 둘이다. 하나는 사물함 사이에 "들키는 봉인"을 붙이거나, 돌아갈 주소를 매번 다른 곳에 숨기는 것이다. 다른 하나는 아예 "16칸을 넘으면 안 돼"라고 언어가 대신 막아 주는 새 언어를 쓰는 것이다. 요즘은 둘을 같이 쓴다.
</EasyIntro>

C로 짠 작은 함수가 있다. 이름을 받아 16바이트 칸에 복사하고 인사만 한다. 짧은 이름은 멀쩡하다. 그런데 40글자짜리를 넣자 프로그램이 멈추며 `*** stack smashing detected ***`라는 말을 남기고 죽었다.

```c
void greet(const char *name) {
    char buf[16];          /* 16바이트 칸 */
    strcpy(buf, name);     /* 길이를 확인하지 않고 복사한다 */
    printf("hello, %s\n", buf);
}
```

```text
$ ./greet kim
hello, kim
$ ./greet AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
*** stack smashing detected ***: terminated
Aborted (core dumped)
```

16칸짜리 `buf`에 40바이트를 복사했으니 24바이트가 칸 밖으로 넘쳤다. 이 글은 그 넘친 바이트가 스택에서 무엇을 덮는지, 그래서 왜 프로그램이 "엉뚱한 주소로 뛸" 수 있는지, 그걸 막는 스택 카나리·NX·ASLR이 각각 무엇을 하는지, 그리고 Rust·Go·자바스크립트 같은 메모리 안전 언어가 어디까지 막고 어디서 다시 구멍이 생기는지를 본다. 실습은 Ubuntu 24.04의 gcc 13.3으로 했다. 이 글은 방어가 어떻게 동작하는지에 초점을 맞추고, 공격 코드 자체는 싣지 않는다.

정수가 넘쳐서 생기는 사고는 [정수 오버플로와 2의 보수](/posts/logic-gates-alu)에서 다뤘는데, 뒤에서 그 넘침이 메모리 사고의 방아쇠가 되는 장면을 본다.

## 스택 프레임에 돌아갈 주소가 적혀 있다

함수를 부르면 CPU는 돌아올 주소를 스택에 적는다. 이 과정은 [CPU 명령어 사이클](/posts/cpu-instruction-cycle)에 자세히 있다. 함수 하나가 쓰는 스택 구역을 스택 프레임이라고 하고, 그 안에 지역 변수(`buf`)와 돌아갈 주소(리턴 주소)가 함께 들어 있다. x86-64에서 스택은 높은 주소에서 낮은 주소로 자라고, 배열에 쓰는 방향은 반대다. 그래서 `buf`에 넘치게 쓰면 더 높은 주소 쪽, 즉 리턴 주소가 있는 방향으로 덮인다.

마지막 칸이 처음 장면의 정체다. 리턴 주소가 덮이면 `ret` 명령이 그 값을 `rip`에 넣어 실행 흐름이 공격자가 고른 주소로 넘어간다. 1988년 모리스 웜이 쓴 수법이 바로 이것이고, 그 뒤 40년 가까이 방어 기술은 "이 흐름 탈취를 어떻게 막느냐"를 두고 쌓여 왔다.

## 힙에서도 비슷한 일이, 다만 다른 모양으로

스택만 위험한 게 아니다. `malloc`으로 받은 힙 메모리를 넘치게 쓰면 옆에 있는 다른 할당 구역이나, 할당자가 관리용으로 쓰는 메타데이터(청크 헤더)가 덮인다. 힙에는 리턴 주소가 없는 대신, "다음에 쓸 함수 포인터"나 할당자 내부 포인터가 표적이 된다.

더 자주 터지는 건 use-after-free다. 이미 돌려준(`free`) 메모리를 계속 가리키는 포인터로 읽거나 쓰는 실수다.

```c
char *name = malloc(16);
strcpy(name, "kim");
free(name);                 /* 돌려줬다 */
printf("%s\n", name);       /* 돌려준 칸을 다시 읽는다 */
```

이 코드를 그냥 돌리면 운 좋게 "kim"이 찍히기도 한다. 그래서 더 무섭다. 버그가 눈에 안 보인다. AddressSanitizer(`-fsanitize=address`)로 컴파일하면 정체가 드러난다.

```text
==9575==ERROR: AddressSanitizer: heap-use-after-free on address 0x502000000010
READ of size 2 at 0x502000000010 thread T0
    #0 ... in puts
freed by thread T0 here:
    #1 ... in main uaf.c:7
SUMMARY: AddressSanitizer: heap-use-after-free ... in puts
```

`free` 뒤에 그 칸이 다른 할당에 재사용되면, 옛 포인터로 쓰는 값이 남의 데이터를 덮는다. 그 "남"이 함수 포인터나 객체의 타입 정보라면 다시 흐름 탈취로 이어진다. 브라우저와 커널에서 보고되는 메모리 취약점의 큰 몫이 use-after-free다. 더블 프리(같은 메모리를 두 번 `free`), 해제 후 재할당을 노린 조작도 같은 뿌리다.

## 봉인을 붙인다: 스택 카나리

처음 실험에서 프로그램이 조용히 탈취당하지 않고 `stack smashing detected`를 외친 건, 요즘 컴파일러가 기본으로 스택 카나리를 심기 때문이다. 카나리는 지역 변수와 리턴 주소 사이에 넣어 두는 임의의 값이다. 광산에서 가스를 먼저 감지하던 카나리 새에서 온 이름이다. 함수가 끝날 때 이 값이 그대로인지 확인하고, 바뀌었으면 `__stack_chk_fail`을 불러 프로그램을 즉시 죽인다.

```bash
# 카나리가 심겼는지 심볼로 확인한다
readelf -s greet | grep -i stack_chk
```

```text
24: 0000000000000000  0 FUNC  GLOBAL DEFAULT  UND __stack_chk_fail
```

카나리를 끄면(`-fno-stack-protector`) 같은 입력에 봉인 없이 그대로 넘어간다.

```text
$ gcc -O0 -fno-stack-protector -o greet3 greet.c && ./greet3 AAAA...(40)
Segmentation fault (core dumped)
```

이번엔 "들켰다"는 말 없이 바로 세그폴트가 났다. 카나리의 한계가 여기서 보인다. 카나리는 리턴 주소가 덮였는지 함수가 끝나는 순간에만 확인한다. 함수 중간에 함수 포인터를 덮어 바로 호출하거나, 카나리를 건드리지 않고 그 너머만 노리면 소용이 없다. 그래서 카나리는 "흔한 스택 오버플로를 늦게라도 잡는" 그물이지, 완벽한 벽이 아니다.

## 데이터에서는 실행하지 않는다: NX

옛날 공격은 넘친 데이터 안에 기계어를 심고, 리턴 주소를 그 데이터로 돌려 거기부터 실행시켰다. NX(No-eXecute) 비트는 이걸 막는다. 스택과 힙처럼 데이터가 들어가는 메모리 영역에 "실행 금지" 표시를 달아, 그 주소로 뛰어도 CPU가 실행을 거부한다. 리눅스에서는 실행 파일 헤더의 `GNU_STACK` 플래그로 표시된다.

```bash
readelf -lW greet | grep GNU_STACK
```

```text
GNU_STACK  0x000000 0x0000000000000000 ... RW  0x10
```

`RW`만 있고 `E`(실행)가 없다. 스택은 읽고 쓸 수만 있고 실행은 안 된다는 뜻이다. 요즘 리눅스·윈도·맥OS와 대부분의 CPU가 기본으로 켠다.

NX가 "심은 코드 실행"을 막자, 공격은 코드를 심는 대신 이미 프로그램 안에 있는 코드 조각을 재활용하는 쪽으로 옮겨 갔다. 이게 ROP(Return-Oriented Programming)다. 라이브러리 곳곳에 흩어진 "`ret`으로 끝나는 짧은 명령 조각"(가젯)의 주소를 스택에 줄줄이 늘어놓으면, 각 조각이 끝날 때마다 다음 주소로 넘어가며 원하는 동작을 꿰맞춘다. 새 코드를 심지 않으니 NX에 걸리지 않는다. NX는 공격의 한 수법을 닫았을 뿐, 끝을 낸 게 아니다.

## 주소를 숨긴다: ASLR과 PIE

ROP가 통하려면 공격자가 가젯의 주소를 알아야 한다. ASLR(Address Space Layout Randomization)은 실행할 때마다 스택·힙·라이브러리·코드가 놓이는 위치를 무작위로 바꿔 그 주소를 모르게 만든다. 같은 프로그램을 두 번 돌려 주요 주소를 찍어 봤다.

```bash
./where   # 지역 변수, malloc, 코드, libc 주소를 찍는다
./where
```

```text
stack=0x7ffeea8b0efc heap=0x55b009e7d2a0 code=0x55aff29d1179 libc=0x7f5fc0060100
stack=0x7ffda16d5f5c heap=0x560f07ecb2a0 code=0x560eea7a2179 libc=0x7f3879460100
```

네 값이 실행마다 다 바뀌었다. 코드 주소까지 바뀌는 건 이 프로그램이 PIE(Position-Independent Executable)로 빌드됐기 때문이다. gcc가 기본으로 PIE를 만들고, 그래서 헤더 타입이 `EXEC`가 아니라 `DYN`으로 나온다.

```text
$ readelf -h greet | grep Type
  Type:  DYN (Position-Independent Executable file)
```

PIE가 아니면 코드 주소는 고정이라 ROP 가젯 위치가 그대로 노출된다. ASLR을 끄면(`setarch -R`) 주소가 실행마다 똑같이 나와 공격자가 외우기 쉬워진다.

```text
$ setarch -R ./where
stack=0x7fffffffc55c heap=0x5555555592a0 code=0x555555555179 libc=0x7ffff7c60100
$ setarch -R ./where
stack=0x7fffffffc55c heap=0x5555555592a0 code=0x555555555179 libc=0x7ffff7c60100
```

두 번 다 같은 주소다. 그래서 디버깅할 때 말고는 ASLR을 끄지 않는다. ASLR의 약점도 분명하다. 무작위에 쓰는 비트 수가 적으면(특히 32비트 시스템) 몇 번 시도로 맞힐 수 있고, 주소 하나가 어딘가로 새어 나가면(정보 유출 버그) 라이브러리 전체의 상대 위치가 드러나 무력화된다. 그래서 ASLR은 카나리·NX와 함께 겹겹이 두는 것이지, 단독 방어가 아니다. 가상 메모리가 어떻게 주소를 매핑하는지는 [가상 메모리와 페이징](/posts/virtual-memory-paging)에 있다.

## 언어가 대신 막는다: 메모리 안전 언어

Rust, Go, 자바, C#, 자바스크립트, 파이썬 같은 언어는 메모리 안전(memory-safe)하다. 배열 범위를 벗어난 접근, 해제한 메모리 재사용, 널 역참조를 언어가 막는다. 방식은 둘로 갈린다.

가비지 컬렉션 언어(Go, 자바, 자바스크립트)는 런타임이 모든 접근을 검사하고 메모리 회수를 자동으로 한다. use-after-free가 애초에 생길 수 없는 건, 아직 가리키는 포인터가 있으면 회수되지 않기 때문이다. 배열 접근은 매번 길이를 검사한다. Rust는 가비지 컬렉터 없이, 소유권과 빌림 규칙을 컴파일 시점에 검사해 같은 안전을 얻는다. 해제한 값을 가리키는 참조는 컴파일 자체가 안 된다.

실행 시점에 결정되는 인덱스로 배열 범위를 벗어나 보면, C는 조용히 넘어가지만 Rust는 멈춘다.

```text
$ ./rust_bounds           # buf는 16칸인데 21번을 읽으려 하면
thread 'main' panicked at main.rs:4:20:
index out of bounds: the len is 16 but the index is 21
```

프로그램이 죽긴 죽는데, "덮기 전에, 정해진 자리에서" 죽는다. 공격자가 끼어들 틈이 없다. 자바스크립트의 `Buffer`도 범위를 넘는 쓰기를 예외로 막는다.

```text
$ node -e 'const b=Buffer.alloc(4); b.writeUInt32LE(1, 2)'
RangeError [ERR_OUT_OF_RANGE]: The value of "offset" is out of range.
It must be >= 0 and <= 0. Received 2
```

미국 정부 기관(CISA, NSA)과 구글·마이크로소프트가 신규 코드를 메모리 안전 언어로 쓰라고 권고하는 이유가 이거다. 두 회사 모두 자사 제품 보안 취약점의 약 70%가 메모리 안전 버그였다고 공개했다. 카나리·NX·ASLR이 아무리 쌓여도 그건 사고를 "비싸게" 만들 뿐이고, 메모리 안전 언어는 사고의 범주 자체를 없앤다.

## 안전 언어에도 구멍이 다시 생기는 자리

그렇다고 메모리 안전 언어를 쓰면 끝나는 건 아니다. 구멍은 "안전 보장을 벗어나는 경계"에서 다시 생긴다.

Rust의 `unsafe` 블록은 컴파일러의 검사를 끄고 생 포인터를 다루게 해 준다. FFI(C 라이브러리 호출)나 저수준 자료구조에 필요하지만, 그 안의 실수는 C와 똑같은 메모리 사고를 낸다. Go의 `unsafe.Pointer`, 자바의 `sun.misc.Unsafe`, JNI, 자바스크립트/파이썬의 네이티브 모듈(C로 짠 확장)도 같다. 안전 언어 프로그램의 메모리 취약점은 거의 이 네이티브 경계에서 나온다.

경계 검사를 벗어난 API도 있다. Node의 `Buffer.allocUnsafe`는 0으로 채우지 않은 메모리를 그대로 주므로, 다 안 채우고 내보내면 이전에 그 자리에 있던 남의 데이터가 새어 나간다. WASM(WebAssembly)은 선형 메모리라는 하나의 큰 바이트 배열 안에서는 경계 검사를 받지만, 그 배열 "안에서" 일어나는 버퍼 오버플로는 WASM 모듈 안의 다른 데이터를 덮을 수 있다. 브라우저 밖으로 새지는 않지만 모듈 내부는 C만큼 위험하다.

그리고 모든 언어가 공유하는 방아쇠가 정수 오버플로다. 할당 크기를 `count * size`로 계산하는데 이 곱이 넘쳐서 작은 값이 되면, 작은 버퍼를 받아 놓고 큰 데이터를 쓰게 된다. 결국 버퍼 오버플로다. C에서 32비트로 계산하면 이렇게 넘친다.

```text
$ ./mul    # count = 0x40000001(약 10억 7천만), size = 4
count=1073741825 bytes=4
size_t bytes=4294967300
```

10억 개가 넘는 요소에 4바이트씩이면 40억 바이트가 넘어야 하는데, 32비트 `bytes`는 4로 줄었다. 이 4바이트짜리 버퍼에 원래 크기만큼 쓰면 바로 넘친다. 그래서 할당 크기 계산에는 넘침을 먼저 확인하는 습관이 든다. 아래에서 직접 짜 본다.

<CodePlayground
  caption="할당 크기 계산: 넘치면 -1을 돌려준다"

  if (!Number.isInteger(count) || !Number.isInteger(size)) return -1;
  if (count < 0 || size < 0) return -1;
  if (size !== 0 && count > Math.floor(MAX / size)) return -1;
  return count * size;
}`}

## 현장에서 메모리 버그를 좁히는 법

C/C++ 코드에서 "가끔 죽는데 재현이 안 되는" 문제는 메모리 버그일 때가 많다. 운에 따라 덮는 자리가 달라서 증상이 들쭉날쭉하다. 개발·CI에서는 AddressSanitizer(`-fsanitize=address`)를 켜 두면 use-after-free, 범위 밖 접근, 더블 프리를 터지는 순간에 잡고 어느 줄에서 할당·해제했는지까지 찍어 준다. 메모리 누수와 초기화 안 된 값은 LeakSanitizer, MemorySanitizer가 맡는다. 운영에서 죽으면 코어 덤프를 `gdb`로 열어 리턴 주소가 정상 코드 영역을 벗어났는지 본다.

새 코드를 짠다면 선택이 갈린다. 성능이 극한으로 필요하고 기존 C 자산이 많으면 C/C++에 방어 플래그를 다 켜고 샌타이저와 퍼징(무작위 입력을 쏟아 crash를 찾는 것)을 돌린다. 그럴 이유가 없으면 처음부터 메모리 안전 언어로 쓰는 게 장기 비용이 싸다. 기존 C 코드베이스를 통째로 바꿀 수 없으면, 가장 위험한 모듈(입력을 파싱하는 곳)부터 Rust 같은 언어로 바꿔 끼우는 점진 전환이 현실적인 길이다.

## 방어는 겹겹이, 해법은 언어에서

버퍼 오버플로는 받은 칸을 넘겨 써서 스택의 리턴 주소나 힙의 포인터를 덮고, 그 틈으로 실행 흐름을 빼앗기는 사고다. 카나리는 덮인 걸 함수 끝에 들키고, NX는 데이터 실행을 막고, ASLR·PIE는 주소를 숨긴다. 셋 다 공격을 비싸게 만들 뿐 완벽하진 않아서 겹겹이 쓴다. 근본 해법은 경계를 언어가 대신 지켜 주는 메모리 안전 언어이고, 그래도 `unsafe`·네이티브 모듈·정수 오버플로라는 경계에서는 같은 사고가 다시 생길 수 있다는 걸 안고 간다.

## 면접에서 나올 만한 질문

### 버퍼 오버플로가 왜 위험한가요?

받은 버퍼보다 많이 쓰면 옆 메모리가 덮이는데, 스택이면 함수가 끝날 때 돌아갈 주소(리턴 주소)가 덮일 수 있다. 그 값이 바뀌면 `ret` 명령이 공격자가 고른 주소로 실행을 넘긴다. 즉 단순한 메모리 손상이 아니라 프로그램 흐름 탈취, 결국 원격 코드 실행으로 이어질 수 있어서 위험하다.

### 스택 오버플로와 힙 오버플로는 어떻게 다른가요?

스택 오버플로는 지역 변수를 넘쳐 리턴 주소나 저장된 레지스터를 덮는다. 힙 오버플로는 `malloc`으로 받은 영역을 넘쳐 옆 할당이나 할당자의 메타데이터(청크 헤더), 함수 포인터를 덮는다. 힙에는 리턴 주소가 없어 공격이 더 복잡하고, use-after-free나 더블 프리와 엮이는 경우가 많다. 둘 다 결국 포인터를 조작해 흐름을 바꾸는 것이 목표다.

### 스택 카나리는 무엇이고 한계는 무엇인가요?

지역 변수와 리턴 주소 사이에 넣는 임의의 값으로, 함수가 끝날 때 바뀌었는지 확인해 바뀌었으면 즉시 프로그램을 죽인다. 순차적인 스택 오버플로를 잡는다. 한계는 함수 종료 시점에만 검사한다는 것이다. 함수 중간에 함수 포인터를 덮어 바로 쓰거나, 카나리를 안 건드리고 정보를 읽어 내면 소용이 없다. 그래서 단독 방어가 아니라 다른 층과 함께 쓴다.

### NX 비트가 켜졌는데도 공격이 가능한 이유는 무엇인가요?

NX는 데이터 영역(스택·힙)에 심은 코드의 실행을 막지만, 이미 프로그램·라이브러리 안에 있는 코드는 실행을 막지 않는다. ROP는 그 기존 코드의 짧은 조각(가젯)들을 리턴 주소로 줄줄이 연결해 원하는 동작을 꿰맞춘다. 새 코드를 심지 않으니 NX에 걸리지 않는다. NX는 한 가지 수법을 막았을 뿐 공격 전체를 끝내지 못한다.

### ASLR은 어떻게 동작하고 언제 무력화되나요?

실행할 때마다 스택·힙·라이브러리·코드의 위치를 무작위로 바꿔 공격자가 가젯이나 함수의 주소를 모르게 한다. 코드까지 바꾸려면 PIE로 빌드해야 한다. 무력화되는 경우는 둘이다. 무작위 비트가 적으면(특히 32비트) 반복 시도로 맞힐 수 있고, 주소 하나가 정보 유출 버그로 새면 상대 위치를 역산해 전체가 드러난다. 그래서 카나리·NX와 겹쳐 쓴다.

### 메모리 안전 언어로 전환하라는 권고가 왜 나오나요?

구글·마이크로소프트 모두 자사 보안 취약점의 약 70%가 메모리 안전 버그라고 공개했고, 카나리·NX·ASLR은 사고를 비싸게 만들 뿐 범주 자체를 없애지는 못한다. Rust·Go·자바스크립트 같은 언어는 범위 검사와 자동/컴파일 시점 메모리 관리로 버퍼 오버플로와 use-after-free를 원천 차단한다. 그래서 CISA·NSA와 두 회사가 신규 코드에는 메모리 안전 언어를 권고한다.

### 메모리 안전 언어를 써도 메모리 버그가 생길 수 있나요?

있다. 안전 보장을 벗어나는 경계에서 생긴다. Rust의 `unsafe`, Go의 `unsafe.Pointer`, JNI, 자바스크립트·파이썬의 네이티브(C) 모듈 안의 실수는 C와 똑같은 사고를 낸다. `Buffer.allocUnsafe`처럼 초기화를 건너뛰는 API는 정보 유출을, 정수 오버플로로 작게 계산된 할당 크기는 버퍼 오버플로를 다시 부른다. 그래서 안전 언어에서도 이 경계를 특히 조심한다.

### 정수 오버플로가 메모리 안전과 어떻게 엮이나요?

할당 크기를 `count * size`로 구하는데 이 곱이 정수 범위를 넘쳐 작은 값으로 접히면, 필요한 것보다 작은 버퍼를 받는다. 거기에 원래 크기만큼 쓰면 바로 버퍼 오버플로다. 정수 오버플로 자체는 메모리 손상이 아니지만 그 방아쇠가 된다. 그래서 크기 계산은 곱하기 전에 넘침을 확인한다. C의 `__builtin_mul_overflow`, Rust의 `checked_mul`이 그 역할을 한다.
