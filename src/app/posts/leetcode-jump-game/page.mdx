[Jump Game](https://leetcode.com/problems/jump-game/)은 LeetCode 55번이다. 그리디(매 순간 가장 좋아 보이는 선택을 하는 방법) 문제 중에서 가장 먼저 만나는 문제이고, 같은 문제를 재귀, 메모이제이션, DP, 그리디로 차례로 풀 수 있어서 "왜 그리디가 맞나"를 설명하는 연습으로 좋다. 이 글은 느린 풀이부터 여섯 가지를 보고, 그럴듯하지만 틀리는 탐욕도 하나 본다. 그리디를 일반적으로 증명하는 법은 [그리디 알고리즘 글](/posts/greedy-algorithms)에, DP의 기본은 [동적 계획법 글](/posts/dynamic-programming)에 있다. 코드는 Node.js 22, Python 3.13, Java 21에서 돌렸다.

## 칸마다 적힌 숫자만큼 뛸 수 있다

정수 배열 `nums`가 있다. 처음에는 0번 칸에 서 있다. `nums[i]`는 i번 칸에서 앞으로 뛸 수 있는 최대 칸 수다. 최대라서 그보다 적게 뛰어도 된다. 마지막 칸(n - 1번)에 도착할 수 있으면 `true`, 아니면 `false`를 돌려준다.

풀이를 고르는 데 영향을 주는 제약은 이렇다.

- 배열 길이는 1 이상 10^4 이하다. O(n²)은 1억 번 정도라 아슬아슬하고, 지수 시간은 어림없다.
- `nums[i]`는 0 이상 10^5 이하다. 음수가 없으니 뒤로 가는 일은 없다. 0이 있는 칸에서는 더 갈 수 없다.
- 배열 길이가 1이면 이미 마지막 칸에 서 있으니 답은 `true`다.

"최대"라는 말이 이 문제의 전부다. 2가 적힌 칸에서는 1칸도, 2칸도 뛸 수 있다. 이 덕분에 뒤의 그리디가 성립한다.

## 손으로 두 줄을 건너 본다

이 글에서 쓸 예시 두 개다.

```text
가) nums = [2, 0, 3, 0, 0, 1]
나) nums = [1, 2, 0, 1, 0, 3]
```

가)를 손으로 따라가 본다. 0번 칸(2)에서 1칸 또는 2칸을 뛸 수 있다. 1칸을 뛰면 1번 칸인데 0이라 막힌다. 2칸을 뛰면 2번 칸(3)이고, 거기서 3칸 뛰면 5번 칸, 마지막이다. 답은 `true`다.

나)는 0번(1) → 1번(2) → 2번 또는 3번이다. 2번은 0이라 막히고, 3번(1)에서는 4번까지만 간다. 4번도 0이다. 어떤 길로 가도 5번 칸에 닿지 않는다. 답은 `false`다. 마지막 칸에 적힌 3은 아무 의미가 없다. 도착만 하면 되니 마지막 칸의 숫자는 쓰이지 않는다.

손으로 풀다 보면 두 가지가 눈에 띈다. 하나는 0인 칸이 함정이라는 것이다. 숫자가 1 이상이면 언제나 한 칸은 나아갈 수 있으니, 길을 막는 건 0뿐이다. 다른 하나는 같은 칸을 여러 길로 다시 방문한다는 것이다. 나)에서 3번 칸에는 1번에서도 오고, 다른 길에서도 올 수 있다. 이 반복이 첫 풀이를 느리게 만든다.

## 갈 수 있는 길을 모두 걸어 본다

가장 곧은 생각은 모든 경로를 시도하는 것이다. i번 칸에서 1칸부터 `nums[i]`칸까지 뛰어 보고, 그중 하나라도 마지막 칸에 닿으면 성공이다. 이렇게 갈림길마다 하나씩 해 보고 막히면 되돌아오는 방식을 백트래킹이라 한다([재귀와 백트래킹 글](/posts/recursion-backtracking)).

```js
function canJump(nums) {
  const last = nums.length - 1;
  function go(i) {
    if (i >= last) return true;                 // 마지막 칸에 닿았거나 넘었다
    for (let step = nums[i]; step >= 1; step--) {
      if (go(i + step)) return true;            // 멀리 뛰는 것부터 해 본다
    }
    return false;                               // 어떤 걸음으로도 안 된다
  }
  return go(0);
}
```

멀리 뛰는 것부터 해 보게 한 건 성공하는 경우를 빨리 찾으려는 작은 꾀다. 답이 `false`일 때는 소용이 없다. 모든 길을 다 봐야 "없다"고 말할 수 있기 때문이다.

최악의 입력을 만들어 보면 감이 온다. `[5, 4, 3, 2, 1, 0, 0]`처럼 줄어드는 숫자를 놓으면 어디서 출발해도 정확히 끝에서 두 번째 칸(0)에 모이고, 마지막 칸에는 못 간다. 이 모양을 길이 n으로 늘려 호출 수를 세어 봤다.

```text
brute n 16 calls 16384 ms 2.1
brute n 20 calls 262144 ms 6.4
brute n 24 calls 4194304 ms 76.3
brute n 26 calls 16777216 ms 180.9
```

호출 수가 정확히 2^(n - 2)다. 칸이 하나 늘 때마다 두 배가 된다. 길이 26에서 이미 0.2초인데, 제약은 10^4칸이다. 시간은 O(2^n), 공간은 재귀 깊이만큼 O(n)이다.

느린 이유는 같은 칸을 몇 번이고 다시 검사하기 때문이다. i번 칸에서 마지막에 갈 수 있는지는 어떤 길로 i번에 왔는지와 상관이 없다. 그러니 한 번 알아낸 답은 적어 두면 된다.

## 한 번 알아낸 칸은 적어 둔다

"i번 칸에서 출발하면 마지막에 갈 수 있나"를 칸마다 한 번만 계산하고 배열에 적어 둔다. 이게 탑다운 메모이제이션이다. 칸의 상태는 셋이다. 아직 모름, 된다, 안 된다.

```js
function canJump(nums) {
  const last = nums.length - 1;
  const memo = new Array(nums.length).fill(0);  // 0 모름, 1 된다, -1 안 된다
  function go(i) {
    if (i >= last) return true;
    if (memo[i] !== 0) return memo[i] === 1;    // 이미 계산한 칸
    const far = Math.min(last, i + nums[i]);    // 배열 밖으로 나가지 않게 자른다
    for (let j = far; j > i; j--) {
      if (go(j)) { memo[i] = 1; return true; }
    }
    memo[i] = -1;
    return false;
  }
  return go(0);
}
```

칸은 n개이고, 칸마다 최대 n칸을 훑으니 시간은 O(n²)이다. 공간은 메모 배열과 재귀 깊이로 O(n)이다. 앞의 26칸 입력도 순식간에 끝난다.

문제는 재귀 깊이다. 모두 1인 배열은 0 → 1 → 2 → ... 로 한 칸씩 내려가서 깊이가 n이 된다. 내 Node 22 기본 설정에서는 5000칸은 통과했고 8000칸에서 `Maximum call stack size exceeded`가 났다. 제약의 10^4칸이 들어오면 실제로 터진다. Python은 기본 재귀 한도가 1000이라 훨씬 빨리 막히고, `sys.setrecursionlimit`을 올려도 C 스택이 먼저 넘칠 수 있다. 재귀를 반복문으로 바꾸면 이 걱정이 없어진다.

Python으로 같은 메모 풀이를 쓰면 이렇다. `functools.cache`가 메모 배열 역할을 한다.

```python
from functools import cache


def can_jump_memo(nums):
    last = len(nums) - 1

    @cache                                     # 같은 i는 한 번만 계산한다
    def go(i):
        if i >= last:
            return True
        return any(go(j) for j in range(min(last, i + nums[i]), i, -1))

    return go(0)


print(can_jump_memo([2, 0, 3, 0, 0, 1]))
print(can_jump_memo([1] * 10000))
```

```text
True
RecursionError: maximum recursion depth exceeded
```

두 번째 줄은 `try`로 감싸서 오류 메시지만 찍은 결과다. 짧은 입력은 맞게 나오지만 1만 칸에서는 계산을 끝내기도 전에 멈춘다. 답이 틀린 게 아니라 실행이 끊긴 것이라, 채점 결과로는 런타임 에러로 보인다.

## 뒤에서부터 표를 채운다

메모 풀이의 계산 방향을 보면 i번의 답은 i보다 뒤에 있는 칸들의 답에만 기댄다. 그러니 마지막 칸부터 거꾸로 채우면 필요한 값이 언제나 먼저 준비되어 있다. 바텀업 DP다.

`good[i]`를 "i번 칸에서 출발하면 마지막에 갈 수 있다"로 정한다. 마지막 칸은 당연히 `true`다. i번은 뛸 수 있는 범위 안에 `good`인 칸이 하나라도 있으면 `good`이다.

```js
function canJump(nums) {
  const n = nums.length;
  const good = new Array(n).fill(false);
  good[n - 1] = true;                           // 도착점
  for (let i = n - 2; i >= 0; i--) {
    const far = Math.min(n - 1, i + nums[i]);
    for (let j = i + 1; j <= far; j++) {
      if (good[j]) { good[i] = true; break; }   // 좋은 칸 하나면 충분하다
    }
  }
  return good[0];
}
```

가) `[2, 0, 3, 0, 0, 1]`에 넣으면 뒤에서부터 이렇게 채워진다.

```text
i=5 good   (도착점)
i=4 bad    (0이라 못 뛴다)
i=3 bad
i=2 good   (2 + 3 = 5까지 뛰어 5번을 만난다)
i=1 bad
i=0 good   (2번이 범위 안에 있다)
```

시간은 여전히 O(n²)이고 공간은 O(n)이다. 재귀가 없으니 스택은 안전하다. 그런데 10만 칸짜리 최악 입력을 넣어 보니 7.6초가 걸렸다. 제약 안쪽인 10^4칸에서는 76ms라 통과는 하지만, 표를 들여다보면 낭비가 보인다.

## 가장 가까운 좋은 칸만 기억한다

위 표에서 i번 칸이 `good`인지 알려면 "i보다 뒤에 있는 good 칸 중 가장 가까운 것"이 범위 안에 있는지만 보면 된다. 가까운 good 칸에 닿지 못하면 더 먼 good 칸에도 닿지 못한다. 뛰는 거리는 최대치까지 아무 값이나 고를 수 있으니, 먼 칸에 닿는다면 가까운 칸에도 닿는다.

그래서 표 전체가 필요 없다. 가장 가까운 good 칸의 위치 하나만 들고 뒤에서부터 걸어오면 된다. 이 위치를 목표(goal)라 부르자. i번 칸에서 goal까지 닿으면 i번이 새 목표가 된다. 목표를 앞으로 당겨 오는 셈이다.

```js
function canJump(nums) {
  let goal = nums.length - 1;                   // 처음 목표는 마지막 칸
  for (let i = nums.length - 2; i >= 0; i--) {
    if (i + nums[i] >= goal) goal = i;          // 여기서 목표에 닿으면 여기가 새 목표
  }
  return goal === 0;                            // 목표가 출발점까지 당겨졌나
}
```

아래 그림에서 다음을 누르면 목표가 가) 배열의 뒤에서 앞으로 당겨지는 모습을 볼 수 있다. 초록 칸이 good 칸이다.

시간은 O(n), 공간은 O(1)이다. 10만 칸에서 0.3ms였다. 앞의 바텀업 DP와 결과가 같다는 건 무작위 배열 2만 개로 다섯 풀이를 서로 맞춰 봐서 확인했다.

이 풀이를 그리디라고 부르는 이유는 "가장 가까운 good 칸 하나면 된다"는 선택 때문이다. DP 표에서 시작해서 필요 없는 정보를 지우다 보니 그리디가 나왔다. 면접에서 그리디가 왜 맞는지 묻는다면 이 흐름으로 설명하는 게 가장 설득력 있다.

## 칸을 정점으로 보고 넓게 퍼진다

이번에는 앞에서부터 생각한다. 칸을 정점, "i에서 j로 뛸 수 있다"를 간선으로 보면 이 문제는 그래프에서 0번 정점이 마지막 정점과 이어져 있는지 묻는 문제다. 처음의 재귀가 깊이 우선 탐색(DFS)이었다면, 이번에는 너비 우선 탐색(BFS)으로 가까운 칸부터 퍼져 나간다. BFS 자체는 [그래프 탐색 글](/posts/ds-graph-bfs-dfs)에 있다.

그냥 BFS를 하면 칸마다 최대 n개의 간선을 보니 O(n²)이다. 그런데 한 칸에서 뛸 수 있는 칸은 언제나 `i + 1`부터 `i + nums[i]`까지 이어진 범위다. 그래서 "지금까지 줄에 넣은 가장 먼 칸" farthest를 기억해 두면, 새로 넣을 칸은 farthest 다음 칸부터만 보면 된다. 이미 넣은 칸을 다시 확인할 필요가 없다.

```js
function canJump(nums) {
  const last = nums.length - 1;
  const queue = [0];
  let head = 0, farthest = 0;                   // farthest: 지금까지 줄에 넣은 가장 먼 칸
  while (head < queue.length) {
    const i = queue[head++];
    if (i >= last) return true;
    const end = Math.min(last, i + nums[i]);
    for (let j = farthest + 1; j <= end; j++) queue.push(j); // 처음 보는 칸만 넣는다
    farthest = Math.max(farthest, end);
  }
  return false;                                 // 줄이 비었다. 더 퍼질 곳이 없다
}
```

칸마다 줄에 한 번만 들어가니 시간은 O(n)이고, 줄 때문에 공간도 O(n)이다. 10만 칸에서 5ms 정도였다.

줄에 들어간 칸들을 보면 언제나 0, 1, 2, ..., farthest처럼 빈틈없이 이어진 번호다. 줄이 들고 있는 정보가 사실은 farthest 숫자 하나뿐이라는 뜻이다. 그렇다면 줄을 없애고 칸 번호를 차례로 훑기만 해도 된다. 그게 다음 풀이다. 이 BFS를 층별로 나눠 세면 "몇 번 뛰어야 하나"도 나오는데, 그 이야기는 Jump Game II에서 이어진다.

## 앞에서 닿을 수 있는 가장 먼 칸을 늘려 간다

같은 생각을 앞에서부터 할 수도 있다. 이번에는 "지금까지 본 칸들에서 닿을 수 있는 가장 먼 칸" reach 하나를 들고 걷는다.

이 방법이 맞는 이유는 한 문장이다. 닿을 수 있는 칸은 언제나 0번부터 reach번까지 빈틈없이 이어진다. reach에 닿았다면 그 사이 칸에도 닿는다. reach를 만든 칸에서 더 짧게 뛰면 되기 때문이다. 그러니 i번 칸이 reach 안에 있으면 i에 올 수 있고, i에서 `i + nums[i]`까지 범위가 늘어난다. i가 reach를 넘어서는 순간, 그 칸에는 어떤 길로도 올 수 없다. 앞의 칸들이 모두 reach까지밖에 못 보냈기 때문이다.

```js
function canJump(nums) {
  let reach = 0;                                // 지금까지 닿을 수 있는 가장 먼 칸
  for (let i = 0; i < nums.length; i++) {
    if (i > reach) return false;                // 이 칸에 올 방법이 없다
    reach = Math.max(reach, i + nums[i]);       // 이 칸에서 더 멀리 가면 늘린다
    if (reach >= nums.length - 1) return true;  // 마지막 칸이 이미 범위 안이다
  }
  return true;
}
```

나) `[1, 2, 0, 1, 0, 3]`에서 reach를 찍어 봤다.

```text
i 0 nums 1 reach 1
i 1 nums 2 reach 3
i 2 nums 0 reach 3
i 3 nums 1 reach 4
i 4 nums 0 reach 4
stop at 5 reach 4
```

reach가 4에서 멈추고 5번 칸이 그 밖이라 `false`다. 그림으로 따라가면 초록 칸(닿을 수 있는 범위)이 늘다가 멈추는 게 보인다.

2번 칸의 0은 길을 막지 못했다. 1번 칸에서 이미 3번까지 범위가 넓어져 있어서 0을 건너뛰었다. 0이 문제가 되는 건 그 0을 넘어서는 범위가 앞에 하나도 없을 때뿐이다. 그래서 "0인 칸마다, 그 앞의 어떤 칸이 0을 넘어설 수 있나"를 묻는 풀이도 결국 이 reach 풀이와 같은 계산이 된다.

시간은 O(n), 공간은 O(1)이다. 마지막 줄의 조기 종료는 없어도 답이 맞지만, 앞쪽에서 큰 숫자를 만나면 나머지를 훑지 않아도 된다.

### 범위가 끊기지 않는다는 걸 차근차근 보이면

면접에서 "증명해 보라"고 하면 귀납법으로 말한다. 주장은 "i번 칸까지 훑었을 때, 0번부터 i번까지의 칸에서 출발해 닿을 수 있는 칸은 정확히 0번부터 reach번까지다"이다.

처음에는 0번 칸만 봤고, 0번에서는 1칸부터 `nums[0]`칸까지 아무 거리로나 뛸 수 있으니 0번부터 `nums[0]`번까지 닿는다. 주장이 맞다. 이제 i - 1번까지 주장이 맞다고 하고 i번 칸을 본다. i가 reach 안이면 i번에 올 수 있고, 거기서 i + 1번부터 `i + nums[i]`번까지 모두 닿는다. 원래 범위 0번부터 reach번까지와 이 범위는 i번에서 겹치거나 이어져 있으니, 합친 범위도 빈틈없이 0번부터 둘 중 큰 끝까지다. i가 reach 밖이면 앞의 어떤 칸도 i번에 보내지 못하고, i번 뒤의 칸들은 i번보다도 멀어서 애초에 닿을 수 없으니 출발점이 되지 못한다. 그래서 거기서 멈춰도 된다.

증명에서 쓴 건 딱 하나, "최대 k칸이면 1칸부터 k칸까지 다 된다"는 조건이다. 이 조건이 빠지는 변형(정확히 k칸만 뛴다, 뒤로도 뛴다)에서 그리디가 깨지는 이유가 여기 있다.

### reach와 구간 합치기

이 풀이를 구간으로 보면 또 다른 그림이 나온다. i번 칸은 구간 `[i, i + nums[i]]`를 하나씩 만든다. 0번 구간에서 시작해서 이어지는 구간을 계속 합쳐 나갈 때 합친 구간이 마지막 칸을 덮는지 묻는 문제다. 칸 번호 순으로 이미 시작점이 정렬되어 있어서 정렬 없이 한 번 훑으면 된다. 구간을 시작 순으로 합치는 일반적인 방법은 [구간 문제 패턴 글](/posts/interval-problems-pattern)에 있고, 합친 끝이 다음 시작보다 작으면 끊긴다는 판정이 여기의 `i > reach`와 같다.

## Python과 Java로 옮기기

```python
from typing import List


class Solution:
    def canJump(self, nums: List[int]) -> bool:
        reach = 0                              # 지금까지 닿을 수 있는 가장 먼 칸
        for i, x in enumerate(nums):
            if i > reach:                      # 이 칸에 올 방법이 없다
                return False
            reach = max(reach, i + x)
            if reach >= len(nums) - 1:         # 마지막 칸이 이미 손에 들어왔다
                return True
        return True
```

```text
[1, 2, 0, 1, 0, 3] False
[2, 0, 3, 0, 0, 1] True
[0] True
[0, 1] False
[1, 0] True
[3, 2, 1, 0, 4] False
```

`enumerate`로 칸 번호와 값을 함께 받는다. 메모 풀이를 Python으로 옮긴다면 기본 재귀 한도가 1000이라 10^4칸에서 `RecursionError`가 나니, Python에서는 처음부터 반복문 풀이를 쓰는 게 낫다.

```java
class Solution {
    public boolean canJump(int[] nums) {
        int reach = 0;                         // 지금까지 닿을 수 있는 가장 먼 칸
        for (int i = 0; i < nums.length; i++) {
            if (i > reach) return false;       // 이 칸에 올 방법이 없다
            reach = Math.max(reach, i + nums[i]);
            if (reach >= nums.length - 1) return true;
        }
        return true;
    }
}
```

```text
[1, 2, 0, 1, 0, 3] false
[2, 0, 3, 0, 0, 1] true
[0] true
[0, 1] false
[1, 0] true
[3, 2, 1, 0, 4] false
```

`main`에서 같은 여섯 입력을 넣은 결과다. `i + nums[i]`의 최댓값은 10^4 + 10^5 정도라 `int`로 넉넉하다. 숫자 제약이 10^9 단위로 바뀐 변형이라면 `i + nums[i]`가 `int` 범위(약 21억)를 넘을 수 있으니 `long`으로 더하거나, 더하기 전에 `nums[i] >= n - 1 - i`처럼 빼기로 비교한다. JavaScript와 Python은 이 크기에서 넘침 걱정이 없다.

## 풀이 비교

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 모든 경로 재귀 | O(2^n) | O(n) | 문제를 처음 이해할 때만 |
| 메모이제이션 | O(n²) | O(n) | 재귀로 생각이 먼저 떠오를 때. 깊이 제한에 주의 |
| 바텀업 DP | O(n²) | O(n) | 그리디의 근거를 설명하는 다리로 |
| 뒤에서 목표 당기기 | O(n) | O(1) | DP에서 그리디로 넘어가는 과정을 보여 줄 때 |
| 범위로 퍼지는 BFS | O(n) | O(n) | 그래프로 보는 시각을 보여 줄 때. 최소 점프 변형의 출발점 |
| 앞에서 reach 늘리기 | O(n) | O(1) | 기본 답. Jump Game II로 그대로 이어진다 |

면접에서는 reach 풀이를 먼저 쓰고, "왜 맞나"를 물으면 "닿을 수 있는 칸은 언제나 앞쪽으로 빈틈없이 이어진다"로 설명한다. 더 파고들면 바텀업 DP에서 가장 가까운 good 칸만 남기는 과정으로 증명한다.

## 그럴듯하지만 틀리는 걸음

### 매번 가장 멀리 뛴다

그리디라는 말을 들으면 "매번 최대한 멀리 뛰자"가 먼저 떠오른다.

```js
function canJump(nums) {
  let i = 0;
  while (i < nums.length - 1) {
    if (nums[i] === 0) return false;
    i += nums[i];                               // 항상 최대로 뛴다
  }
  return true;
}
```

`[2, 3, 0, 0, 1]`에서 `false`가 나온다. 0번에서 2칸을 뛰면 0인 2번 칸에 빠진다. 정답은 `true`다. 0번에서 1칸만 뛰어 1번(3)에 가면 4번까지 간다. 멀리 뛰는 게 아니라 "뛴 다음 칸에서 더 멀리 갈 수 있는 곳"을 골라야 한다. reach 풀이는 한 칸을 고르지 않고 범위 안의 모든 칸을 보니까 이 함정에 빠지지 않는다.

### 범위 밖 칸을 검사하지 않는다

```js
let reach = 0;
for (let i = 0; i < nums.length; i++) {
  reach = Math.max(reach, i + nums[i]);         // i > reach 검사가 없다
}
return reach >= nums.length - 1;
```

`[0, 1]`에서 `true`가 나온다. 0번에서 못 움직이는데, 갈 수 없는 1번 칸의 값까지 reach에 더해 버렸다. 올 수 없는 칸의 숫자는 쓰면 안 된다. 반복 조건을 `i <= reach && i < nums.length`로 바꿔도 같은 효과다.

### 마지막 칸 번호를 길이로 쓴다

`reach >= nums.length`로 비교하면 `[0]`에서 `false`가 나온다. 칸이 하나면 이미 도착해 있다. 마지막 칸 번호는 `nums.length - 1`이다.

### 뒤에서 당길 때 등호를 빼먹는다

```js
if (i + nums[i] > goal) goal = i;              // >= 가 아니라 >
```

`[1, 0]`에서 `false`가 나온다. 0번에서 1칸 뛰면 정확히 목표인 1번이다. 정확히 닿는 것도 닿은 것이다.

### 0을 무조건 실패로 본다

배열에 0이 있으면 `false`라고 단정하는 실수도 있다. `[2, 0, 3, 0, 0, 1]`처럼 0을 건너뛰는 범위가 앞에 있으면 괜찮고, 마지막 칸의 0은 아예 상관이 없다. `[1, 0]`은 `true`다.

### 그리디가 맞는지 손으로 확신이 안 설 때

코딩 테스트에서 탐욕을 떠올렸는데 맞는지 확신이 없으면, 느리지만 확실한 풀이와 작은 무작위 입력으로 맞춰 보는 게 가장 빠르다. 위의 "가장 멀리 뛰기"를 모든 경로 재귀와 비교해 봤다.

```js
for (let t = 0; t < 1000; t++) {
  const n = 1 + Math.floor(Math.random() * 6);              // 칸은 6개까지만
  const a = Array.from({ length: n }, () => Math.floor(Math.random() * 4));
  if (brute(a) !== greedyWrong(a)) {
    console.log("다르다", JSON.stringify(a), brute(a), greedyWrong(a));
    break;
  }
}
```

```text
다르다 [2,3,0,0] true false
```

돌릴 때마다 다른 입력이 나오지만 매번 몇 번 만에 반례가 잡힌다. 칸을 작게 잡는 게 요령이다. 반례가 짧아야 손으로 따라가며 왜 틀렸는지 볼 수 있다. reach 풀이는 같은 방식으로 2만 번을 돌려도 다른 풀이와 어긋나지 않았다.

## 조건이 바뀌면

### 최소 몇 번 뛰어야 하나

[Jump Game II](/posts/leetcode-jump-game-ii)(45번)다. 도착할 수 있다는 건 보장되고, 최소 점프 횟수를 묻는다. reach 풀이를 그대로 쓰되 "이번 점프로 닿는 범위"와 "다음 점프로 닿는 범위"를 나눠서, 범위 끝에 도달할 때마다 점프 횟수를 하나 늘린다. 범위를 층으로 보는 BFS와 같은 계산이다.

### 실제 경로를 돌려 달라면

reach 풀이는 갈 수 있는지만 알려 준다. 경로가 필요하면 reach를 늘린 칸을 기록해 두거나, 바텀업 DP에서 각 칸이 good이 된 이유(어느 j를 만났는지)를 적어 두고 0번부터 따라가면 된다. 뒤에서 목표를 당기는 풀이에서도 goal이 바뀐 칸들을 앞에서부터 이으면 바로 하나의 경로가 된다. 가) 배열에서는 0 → 2 → 5다.

### 양쪽으로 뛸 수 있다면

LeetCode 1306번 Jump Game III는 i번에서 `i + nums[i]` 또는 `i - nums[i]`로 정확히 뛰어, 값이 0인 칸에 닿을 수 있는지 묻는다. 뒤로 가는 길이 생기면 "앞쪽으로 빈틈없이 이어진다"는 성질이 깨져서 그리디가 성립하지 않는다. 칸을 정점, 점프를 간선으로 보고 방문 표시를 하며 BFS나 DFS를 한다([그래프 탐색 글](/posts/ds-graph-bfs-dfs)). O(n)이다.

### 뛸 수 있는 거리가 범위로 정해져 있다면

LeetCode 1871번 Jump Game VII은 `'0'`인 칸에만 설 수 있고, 한 번에 minJump 이상 maxJump 이하로 뛴다. 각 칸이 good인지 정하려면 "앞의 일정 범위 안에 good 칸이 있나"를 물어야 해서, 범위 안 good 개수를 누적 합이나 슬라이딩 윈도로 관리한다([슬라이딩 윈도 패턴 글](/posts/sliding-window-pattern)). 위의 바텀업 DP를 O(n)으로 줄이는 같은 모양의 고민이다.

### 구간을 최소 개수로 덮어야 한다면

LeetCode 1024번 Video Stitching과 1326번 Minimum Number of Taps to Open to Water a Garden은 겉모습이 다르지만 같은 문제다. 영상 조각이나 수도꼭지마다 덮는 구간이 있고, 0부터 끝까지를 최소 몇 개로 덮는지 묻는다. 시작점마다 가장 멀리 가는 끝을 모아 두면 "i번 칸에서 nums[i]만큼 뛴다"는 배열로 바뀌고, Jump Game II와 같은 방법으로 풀린다. 덮는지 여부만 묻는다면 이 글의 reach 풀이다.

### 숫자가 스트림으로 들어온다면

reach 풀이는 칸을 한 번씩 앞에서부터만 보니까 배열 전체를 저장할 필요가 없다. 값이 들어올 때마다 "지금 칸 번호가 reach 안인가"와 reach 갱신만 하면 된다. 뒤에서 당기는 풀이는 끝을 알아야 시작할 수 있어서 스트림에는 맞지 않는다.

## 면접에서 나올 만한 질문

### 이 문제를 그리디로 풀 수 있는 이유는 무엇인가요?

닿을 수 있는 칸이 항상 0번부터 어떤 칸까지 빈틈없이 이어지기 때문이다. 어떤 칸에서 최대 k칸까지 뛸 수 있으면 그보다 가까운 칸에도 모두 갈 수 있으니, 가장 먼 칸 하나만 알면 닿을 수 있는 칸 전체를 안다. 그래서 reach 하나를 늘려 가며 칸 번호가 reach를 넘는지만 보면 된다.

### 매번 가장 멀리 뛰는 것과 무엇이 다른가요?

매번 최대로 뛰는 건 한 칸을 고르고 나머지를 버리는 것이고, reach 풀이는 범위 안의 모든 칸을 다 보고 그중 가장 멀리 보내는 값을 남기는 것이다. `[2, 3, 0, 0, 1]`에서 최대로 뛰면 0인 칸에 빠지지만, reach 풀이는 1번 칸의 3을 보고 4번까지 범위를 넓힌다. 그리디의 기준이 "다음 칸"이 아니라 "닿는 범위"다.

### DP 풀이와 그리디 풀이는 어떻게 이어지나요?

바텀업 DP는 i번 칸에서 마지막에 갈 수 있는지를 뒤에서부터 채우고, 범위 안에 good 칸이 하나라도 있으면 good이다. 그런데 가장 가까운 good 칸에 닿지 못하면 더 먼 good 칸에도 닿지 못하니, 가장 가까운 good 칸 위치 하나만 남겨도 된다. 그게 목표를 뒤에서 당기는 O(n) 그리디다. DP 표에서 필요 없는 정보를 지운 결과라서 정당성이 따라온다.

### 메모이제이션 풀이는 왜 실무 입력에서 위험한가요?

재귀 깊이가 배열 길이만큼 깊어질 수 있기 때문이다. 모두 1인 배열이면 한 칸씩 재귀로 내려가고, Node 기본 설정에서는 8000칸에서 스택이 넘쳤다. Python은 기본 한도가 1000이라 더 빨리 막힌다. 같은 O(n²)이라도 반복문으로 바꾸면 이 위험이 없고, 그리디로 가면 O(n)이 된다.

### 마지막 칸의 숫자는 왜 쓰지 않나요?

도착만 하면 되는 문제라 마지막 칸에서 더 뛸 일이 없기 때문이다. 뒤에서 당기는 풀이가 n - 2번부터 시작하고, 앞에서 가는 풀이가 reach가 n - 1 이상이 되면 바로 끝나는 이유다. 그래서 `[1, 0]`처럼 마지막이 0이어도 답은 true다.

### 배열 길이가 1이면 답은요?

true다. 출발점이 곧 마지막 칸이다. reach 풀이에서는 첫 반복에서 reach = nums[0]이 0 이상이라 `reach >= 0` 조건으로 바로 true가 나오고, 뒤에서 당기는 풀이는 반복을 한 번도 안 돌고 goal이 0이라 true다. 마지막 칸을 길이로 착각해 `reach >= n`으로 비교하면 이 입력에서 틀린다.

### 뒤로도 뛸 수 있다면 같은 방법이 통하나요?

통하지 않는다. 뒤로 가는 길이 생기면 닿을 수 있는 칸이 앞쪽으로 빈틈없이 이어진다는 성질이 깨진다. 이때는 칸을 정점으로 보고 방문 표시를 하며 BFS나 DFS를 한다. Jump Game III가 이 경우이고 각 칸을 한 번씩만 방문해서 O(n)이다.
