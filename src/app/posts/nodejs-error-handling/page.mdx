  공장의 컨베이어 벨트를 떠올리면 쉽다. 벨트 위에서 불량품이 나오면 그 구간을 맡은 작업자가 집어서 따로 빼 두어야 하고, 아무도 맡지 않은 구간에서 불량품이 나오면 공장은 안전을 위해 벨트 전체를 세운다. Node.js에서는 에러를 잡는 자리가 바로 그 작업자다. 그런데 나중에 실행되는 일은 처음 일을 맡긴 작업자와 다른 구간에서 돌아가서, 맨 처음에 세워 둔 작업자가 불량품을 보지 못한다. 그래서 일을 나눠 맡길 때마다 그 구간에도 작업자를 세워 줘야 한다. 벨트가 멈출 때 남기는 숫자를 기록과 함께 남겨 두면, 스스로 멈춘 것인지 누가 전원을 내린 것인지 다음 날 아침에 다시 따라갈 수 있다.

새벽 세 시쯤 주문 서비스 파드가 다섯 번 재시작됐다. 쿠버네티스 이벤트에는 `Back-off restarting failed container`만 남아 있고, 앱 로그에는 마지막 정상 요청 다음 줄이 바로 다음 기동 로그였다. 에러 로그가 한 줄도 없다. 로그 수집기가 놓친 걸까 싶어 `kubectl logs --previous`를 열어 보니 거기에는 이렇게 찍혀 있었다.

undefined
^

SyntaxError: "undefined" is not valid JSON
    at JSON.parse (<anonymous>)
    at ReadFileContext.callback (/srv/app/u1.js:4:22)

이 출력은 표준 에러(stderr)로 나갔다. 앱은 구조화 로그를 표준 출력으로만 보내고 있었고, 로그 파이프라인은 JSON 줄만 받도록 걸러 두었다. 그래서 프로세스가 죽기 직전에 Node가 직접 찍은 마지막 유언이 수집기에서 버려졌다.

이 글은 Node.js가 에러를 어떻게 나누고, 그 에러가 어디서 새고, 끝내 아무도 받지 않으면 프로세스가 어떻게 끝나는지를 따라간다. Promise의 거부가 체인을 따라 내려가는 원리는 [Promise 글](/posts/js-promises)에서, Express 핸들러에서 async 에러가 새는 문제는 [Express 미들웨어 글](/posts/express-middleware)에서 다뤘다. 여기서는 그 위아래, 에러 객체 자체와 프로세스의 마지막 순간을 본다. 실행 결과는 모두 Node.js 22.22, 리눅스에서 직접 돌린 것이다.

## 에러는 생긴 곳에 따라 모양이 다르다

Node에서 만나는 에러는 크게 네 무리로 나뉜다. 겉으로는 모두 `Error`의 인스턴스지만 붙어 있는 정보가 다르고, 대응도 달라진다.

첫째는 자바스크립트 엔진이 던지는 에러다. `TypeError`, `ReferenceError`, `SyntaxError`, `RangeError` 같은 것들이다. `undefined`의 속성을 읽거나, 없는 변수를 쓰거나, 깨진 JSON을 파싱할 때 나온다. 거의 언제나 코드의 버그다.

둘째는 시스템 에러다. Node가 운영체제에 무언가를 부탁했다가 거절당한 경우다. 파일을 열었는데 없거나, 연결했는데 상대가 끊었거나. 없는 설정 파일을 읽어 보면 이렇게 나온다.

```js
import { readFile } from "node:fs/promises";

try {
  await readFile("/srv/app/config.json");
} catch (err) {
  console.log(err.message);
  console.log({ name: err.name, code: err.code, errno: err.errno, syscall: err.syscall, path: err.path });
}
```

```text
ENOENT: no such file or directory, open '/srv/app/config.json'
{
  name: 'Error',
  code: 'ENOENT',
  errno: -2,
  syscall: 'open',
  path: '/srv/app/config.json'
}
```

`name`은 그냥 `Error`다. 시스템 에러를 구분하는 단서는 `code`, `errno`, `syscall`이다. `code`는 POSIX 에러 이름(ENOENT는 "그런 파일이나 디렉터리가 없다")이고, `errno`는 그 번호에 음수를 붙인 값이다. 리눅스에서 ENOENT는 2번이라 -2가 된다. `syscall`은 실패한 시스템 콜 이름이라, 같은 ENOENT라도 `open`에서 났는지 `spawn`에서 났는지 가를 수 있다.

네트워크 쪽도 같은 모양이다. 아무도 듣지 않는 포트에 붙으면 ECONNREFUSED, 상대가 요청을 받다가 연결을 리셋하면 ECONNRESET이 나온다.

```text
{
  message: 'connect ECONNREFUSED 127.0.0.1:1',
  code: 'ECONNREFUSED',
  errno: -111,
  syscall: 'connect',
  address: '127.0.0.1',
  port: 1
}
{
  message: 'read ECONNRESET',
  code: 'ECONNRESET',
  errno: -104,
  syscall: 'read'
}
```

ECONNREFUSED는 연결이 시작조차 되지 않았다는 뜻이라 요청이 상대에게 닿지 않았다. 다시 보내도 안전하다. ECONNRESET은 `read` 도중에 끊겼다. 상대가 요청을 받아서 처리하다 끊었을 수도 있으니, 결제처럼 두 번 하면 안 되는 일은 그냥 재시도하면 안 된다. 같은 "연결 에러"라도 `syscall`과 `code`를 보면 재시도 판단이 달라진다. HTTP 클라이언트에서 이 에러들이 어떻게 올라오는지는 [Node.js HTTP 클라이언트 글](/posts/nodejs-http-clients)에서 이어 간다.

셋째는 내가 만든 에러다. 주문이 없거나, 재고가 모자라거나. 넷째는 `node:assert`가 던지는 `AssertionError`다. "여기서는 절대 이럴 리 없다"는 가정이 깨졌다는 신호다.

```js
import assert from "node:assert";

assert.strictEqual(1, 2);
```

```text
AssertionError ERR_ASSERTION true 1 2 strictEqual
Expected values to be strictly equal:

1 !== 2
```

위 줄은 `e.name`, `e.code`, `e.generatedMessage`, `e.actual`, `e.expected`, `e.operator`를 찍은 것이다. Node가 직접 던지는 에러에는 대부분 `ERR_`로 시작하는 `code`가 붙는다. 메시지 문구는 버전마다 바뀔 수 있지만 `code`는 안정적인 약속이라, 분기는 메시지가 아니라 `code`로 한다.

## 버그와 예상한 실패는 다르게 다룬다

네 무리를 다시 두 덩어리로 묶으면 다루기 쉬워진다. 하나는 예상할 수 있는 실패다. 파일이 없고, 네트워크가 끊기고, 사용자가 없는 주문 번호를 보낸다. 코드가 멀쩡해도 일어나는 일이라, 잡아서 응답을 정하면 된다. 다른 하나는 버그다. `undefined`를 읽고, 가정이 깨진다. 이건 잡아서 덮을 일이 아니라 고칠 일이다.

이 구분이 왜 중요하냐면, 버그가 난 순간 프로세스 안의 상태를 더는 믿을 수 없기 때문이다. 아래 코드는 연결이 두 개뿐인 풀을 흉내 낸다. 요청 처리 중 `release()`를 부르기 전에 에러가 터지고, 그 에러를 `uncaughtException`에서 로그만 찍고 넘긴다.

```js
let free = 2;
const waiters = [];
const acquire = () => (free > 0 ? (free--, Promise.resolve()) : new Promise((r) => waiters.push(r)));
const release = () => (waiters.length ? waiters.shift()() : free++);

process.on("uncaughtException", (err) => console.error("[ignored]", err.message));

function handle(id, bad) {
  acquire().then(() => {
    setTimeout(() => {
      if (bad) throw new Error(`bad row in request ${id}`); // release 전에 터진다
      release();
      console.log(`request ${id} done`);
    }, 10);
  });
}
for (let i = 1; i <= 5; i++) handle(i, i <= 2);
setTimeout(() => console.log(`after 1s: free=${free}, waiting=${waiters.length}`), 1000);
```

```text
[ignored] bad row in request 1
[ignored] bad row in request 2
after 1s: free=0, waiting=3
```

프로세스는 살아 있다. 헬스 체크도 통과한다. 그런데 연결 두 개는 영영 돌아오지 않았고, 뒤의 요청 세 개는 끝없이 기다린다. 진짜 DB 풀이었다면 서비스가 "살아 있지만 아무것도 못 하는" 상태로 몇 시간을 버틴다. 재시작되는 편이 차라리 나았다. 버그로 생긴 에러는 잡아서 살리는 게 아니라, 기록을 남기고 깔끔하게 죽게 한 뒤 프로세스 관리자(쿠버네티스, systemd, PM2)가 새로 띄우게 하는 쪽이 안전하다.

예상한 실패는 반대로 경계에서 잡아 응답으로 바꾼다. 이때 쓸 에러 클래스를 하나 정해 두면 분기가 깔끔해진다.

```ts
export class AppError extends Error {
  readonly code: string;
  readonly status: number;

  constructor(message: string, opts: { code: string; status?: number; cause?: unknown }) {
    super(message, { cause: opts.cause });
    this.name = new.target.name; // 상속해도 클래스 이름이 찍힌다
    this.code = opts.code;
    this.status = opts.status ?? 500;
  }
}

export class NotFoundError extends AppError {
  constructor(what: string) {
    super(`${what} not found`, { code: "NOT_FOUND", status: 404 });
  }
}
```

```text
true true NotFoundError NOT_FOUND 404
NotFoundError: order 42 not found
```

`instanceof AppError`와 `instanceof Error`가 모두 참이고, 스택 첫 줄에 클래스 이름이 찍힌다. `name`을 직접 정하지 않으면 스택에 그냥 `Error:`로 나와서 로그에서 구분하기 어렵다. 한 가지 더, 에러 객체를 `JSON.stringify`하면 거의 비어서 나온다.

```text
{"name":"NotFoundError","code":"NOT_FOUND","status":404}
{}
```

`message`와 `stack`은 열거되지 않는 속성이라 JSON에 빠진다. 평범한 `new Error("x")`는 `{}`가 된다. 로그에 `"error":{}`만 잔뜩 쌓여 있다면 이 실수다. pino 같은 로거는 `err` 키로 넘기면 직렬화기가 `message`, `stack`, `cause`를 꺼내 준다. 로그 한 줄에 무엇을 담을지는 [구조화 로그 글](/posts/structured-logging)에서 다뤘다.

## 에러가 새는 자리: 콜백, Promise, 이벤트

맨 처음 장면의 코드는 이랬다.

```js
const fs = require("node:fs");

function loadConfig() {
  fs.readFile("/srv/app/config.json", "utf8", (err, text) => {
    const cfg = JSON.parse(text); // err를 안 보고 바로 파싱
  });
}
loadConfig();
```

`loadConfig()`를 `try`로 감쌌어도 이 에러는 못 잡는다. 콜백은 `loadConfig`가 이미 끝난 뒤, 파일 읽기가 끝났을 때 이벤트 루프가 새로 부른다. 스택 트레이스를 다시 보면 맨 아래가 `FSReqCallback.readFileAfterOpen`이다. `loadConfig`도, 그걸 부른 코드도 스택에 없다. `try`는 지금 스택 위에 있는 코드에만 걸리는데, 콜백이 실행될 때는 그 `try`가 이미 스택에서 내려간 뒤다.

자리는 세 군데다.

콜백 API는 첫 인자로 에러를 넘긴다(error-first 콜백). `if (err)`로 먼저 보지 않으면 에러는 조용히 버려지고, 대신 엉뚱한 곳에서 `undefined` 관련 에러가 터진다. 이 장면이 정확히 그렇다. `err`에는 ENOENT가 들어 있었지만 아무도 보지 않았고, `text`가 `undefined`라 `JSON.parse`가 `SyntaxError`를 던졌다. 진짜 원인(파일이 없다)은 사라지고 증상(JSON이 깨졌다)만 남는다.

Promise는 거부를 아무도 받지 않으면 `unhandledRejection`이 된다. `await` 없이 부른 async 함수, `.catch`가 없는 체인, `forEach` 안의 async 콜백이 흔한 자리다.

```js
async function charge(orderId) {
  throw new Error(`payment failed: ${orderId}`);
}
charge(42); // await도 catch도 없다
setTimeout(() => console.log("still alive"), 100);
```

```text
file:///srv/app/u2.mjs:2
  throw new Error(`payment failed: ${orderId}`);
        ^

Error: payment failed: 42
    at charge (file:///srv/app/u2.mjs:2:9)
    at file:///srv/app/u2.mjs:4:1
    ...

Node.js v22.22.0
```

`still alive`는 찍히지 않았고 종료 코드는 1이었다. Node.js 15부터 `--unhandled-rejections`의 기본값이 `throw`라서, 처리되지 않은 거부를 잡히지 않은 예외처럼 다룬다. 14 이하에서는 경고만 찍고 계속 돌았다. 지금도 옛 동작으로 돌릴 수 있다.

```bash
# 거부를 경고로만 찍고 계속 돈다 (권장하지 않는다)
node --unhandled-rejections=warn u2.mjs
echo "exit=$?"
```

```text
(node:4633) UnhandledPromiseRejectionWarning: Error: payment failed: 42
    at charge (file:///srv/app/u2.mjs:2:9)
    ...
still alive
exit=0
```

옛날 코드를 Node 16 이상으로 올렸더니 갑자기 프로세스가 죽기 시작했다면 대개 이 기본값 변화 때문이다. 플래그로 되돌리기보다 새는 거부를 찾아 막는 게 맞다.

이벤트 에미터는 `error` 이벤트가 특별하다. `error`를 듣는 리스너가 하나도 없는데 `emit("error")`가 일어나면 에미터가 그 에러를 그대로 던진다.

```text
node:events:497
      throw er; // Unhandled 'error' event
      ^

Error: socket hang up
```

소켓, 스트림, 자식 프로세스, DB 클라이언트가 전부 에미터다. `const client = new pg.Client()`로 만들고 `client.on("error")`를 안 달아 두면, DB가 재시작되는 순간 유휴 연결에서 난 에러 하나로 프로세스 전체가 내려간다. 스트림을 이을 때 `.pipe()` 대신 `pipeline()`을 쓰는 이유도 이것이다. 에러가 어느 스트림에서 나든 한 자리로 모아 준다. 자세한 건 [Node.js 파일과 스트림 글](/posts/nodejs-fs-streams)에서 본다.

## process가 마지막으로 받는 두 이벤트

어디에서도 잡히지 않은 에러는 `process`의 `uncaughtException` 이벤트로 온다. Node 15 이후 기본 설정에서는 처리되지 않은 거부도 결국 이 이벤트로 넘어온다. 두 번째 인자 `origin`으로 어느 쪽에서 왔는지 알 수 있다.

```js
process.on("uncaughtException", (err, origin) => {
  console.error(`[fatal] ${origin}: ${err.message}`);
  process.exitCode = 1;
});
setTimeout(() => { throw new Error("boom in timer"); }, 10);
Promise.reject(new Error("boom in promise"));
setTimeout(() => console.log("server keeps running"), 50);
```

```text
[fatal] unhandledRejection: boom in promise
[fatal] uncaughtException: boom in timer
server keeps running
exit=1
```

리스너를 달면 Node는 기본 동작(스택 찍고 종료)을 하지 않는다. 그래서 `server keeps running`이 찍혔다. 이게 바로 앞에서 본 풀 고갈 장면으로 가는 길이다. `uncaughtException` 리스너는 "계속 돌게 해 주는 장치"가 아니라 "죽기 전에 할 말을 남기는 자리"로 써야 한다. Node 공식 문서도 이 이벤트 다음에 정상 재개하는 것은 안전하지 않다고 적어 둔다.

그 자리에서 할 일은 이 정도다.

```ts
import { logger } from "./logger";
import { server } from "./server";

process.on("uncaughtException", (err, origin) => {
  // 1. 동기로 남긴다. 비동기 로거 버퍼는 곧 사라질 수 있다
  logger.fatal({ err, origin }, "uncaught error, shutting down");

  // 2. 새 요청을 그만 받고, 처리 중인 요청은 잠깐 기다려 준다
  server.close(() => process.exit(1));

  // 3. 끝까지 안 닫히면 강제로 끝낸다
  setTimeout(() => process.exit(1), 5_000).unref();
});
```

`logger.fatal`은 pino 기준으로 동기 출력 대상(`pino.destination({ sync: true })` 또는 기본 stdout)이면 바로 쓰인다. 워커 스레드로 보내는 비동기 transport를 쓰고 있다면 플러시를 기다리는 처리가 따로 필요하다. 이 리스너 안에서 또 에러를 던지면 Node는 더 기다리지 않고 종료 코드 7로 끝난다.

```text
    at process._fatalException (node:internal/process/execution:155:25)

Node.js v22.22.0
exit=7
```

기본 동작은 그대로 두고 기록만 하고 싶다면 `uncaughtExceptionMonitor`가 있다. 이 이벤트는 기본 종료 동작을 막지 않는다. APM 에이전트나 에러 수집 SDK가 이 이벤트를 쓴다.

`unhandledRejection`에 따로 리스너를 달면 그 거부는 더는 예외로 바뀌지 않는다. 로그만 찍는 리스너를 달면 Node 14 시절처럼 "경고만 하고 계속 도는" 서비스가 된다. 달 거라면 똑같이 로그를 남기고 종료 절차를 밟거나, 그냥 던져서 `uncaughtException`으로 넘긴다.

```ts
process.on("unhandledRejection", (reason) => {
  throw reason; // uncaughtException 리스너로 넘긴다
});
```

새벽 장면의 진짜 해결은 둘이었다. 하나는 콜백의 `err`를 확인하는 코드 수정이고, 다른 하나는 표준 에러로 나간 마지막 출력도 수집하도록 로그 파이프라인을 고친 것이다. 컨테이너 런타임은 stdout과 stderr를 모두 받으니, 걸러 버리지만 않으면 `kubectl logs --previous`에서 보던 줄이 수집기에도 남는다.

## 종료 코드로 누가 끝냈는지 읽는다

프로세스는 끝날 때 숫자 하나를 남긴다. 0이면 정상, 그 외는 실패다. Node가 쓰는 값은 정해져 있다.

| 코드 | 언제 |
|---|---|
| 0 | 할 일이 다 끝나서 이벤트 루프가 비었다 |
| 1 | 잡히지 않은 예외로 끝났다 (가장 흔하다) |
| 7 | `uncaughtException` 리스너 안에서 또 예외가 났다 |
| 9 | 잘못된 명령행 인자 |
| 13 | ESM 최상위 `await`가 끝나지 않은 채 루프가 비었다 |
| 128 + N | 시그널 N으로 끝났다 (셸과 컨테이너가 이렇게 보여 준다) |

13은 처음 보면 당황스럽다. 직접 만들어 보면 이렇다.

```bash
echo 'await new Promise(()=>{});' > tla.mjs
node tla.mjs; echo "exit=$?"
```

```text
Warning: Detected unsettled top-level await at file:///srv/app/tla.mjs:1
await new Promise(()=>{});
^

exit=13
```

마지막 줄은 셸이 계산한 값이다. 프로세스가 시그널로 죽으면 종료 코드가 따로 없어서, 셸과 컨테이너 런타임은 128에 시그널 번호를 더해 보여 준다.

```bash
# 핸들러 없는 node를 SIGTERM(15)과 SIGKILL(9)로 끝낸다
node -e 'setInterval(() => {}, 1000)' & sleep 0.5; kill -TERM $!; wait $!; echo "TERM exit=$?"
node -e 'setInterval(() => {}, 1000)' & sleep 0.5; kill -KILL $!; wait $!; echo "KILL exit=$?"
```

```text
TERM exit=143
KILL exit=137
```

143은 SIGTERM에 핸들러가 없어서 기본 동작(즉시 종료)으로 끝났다는 뜻이다. 배포 때마다 파드가 143으로 끝난다면 정상 종료 코드가 없는 것이고, 처리 중이던 요청이 끊겼을 수 있다. 137은 SIGKILL이다. 누군가 강제로 죽였다는 뜻이고, 컨테이너에서는 메모리 한도를 넘어 OOM killer가 죽인 경우가 가장 흔하다. 앱 로그에 아무것도 없는데 137이면 앱이 아니라 커널을 의심한다. 시그널 자체와 PID 1 문제는 [리눅스 프로세스와 시그널 글](/posts/linux-processes-signals)에서 자세히 다뤘다.

SIGTERM에 핸들러를 달고 정리한 뒤 직접 0으로 끝내면 종료 코드는 0이 된다.

```text
closing...
handled TERM exit=0
```

## process.exit는 기다려 주지 않는다

`process.exit(code)`와 `process.exitCode = code`는 비슷해 보이지만 다르다. 앞의 것은 그 자리에서 끝내고, 뒤의 것은 "끝날 때 이 숫자를 써 달라"고 적어 두기만 한다. 감사 로그를 쓰자마자 끝내는 코드로 비교했다.

```js
import { appendFile } from "node:fs/promises";

appendFile("/srv/app/audit.log", "order 42 refunded\n").then(() => console.log("written"));
if (process.argv[2] === "exit") process.exit(1);
else process.exitCode = 1;
```

```bash
rm -f audit.log; node ex.mjs exit; ls -l audit.log   # process.exit(1)
rm -f audit.log; node ex.mjs; cat audit.log          # process.exitCode = 1
```

```text
-rw-r--r-- 1 root root 0 Oct 23 12:53 audit.log
written
order 42 refunded
```

`process.exit(1)` 쪽은 파일이 만들어지긴 했는데 크기가 0이다. 스레드 풀에서 `open`까지는 끝났지만 `write`가 돌기 전에 프로세스가 사라졌다. 세 번 돌려도 똑같이 0바이트였다. `exitCode` 쪽은 남은 일을 다 마치고 루프가 빈 뒤에 1로 끝났다. 비동기 로거, 아직 안 끝난 DB 쓰기, 보내던 지표가 모두 이렇게 잘린다.

그래서 CLI 스크립트의 실패 처리는 `process.exitCode = 1`로 적고 자연스럽게 끝나게 두는 편이 낫다. `process.exit`는 "더 기다리면 영영 안 끝날 것 같을 때" 쓰는 마지막 수단이다. 앞의 `uncaughtException` 코드에서 `setTimeout(...).unref()`로 강제 종료를 걸어 둔 것도 같은 이유다. `unref()`를 붙인 타이머는 그것 하나만 남았을 때 루프를 붙잡지 않는다.

## 스택 트레이스는 어디까지 따라가나

스택 트레이스는 에러가 만들어진 순간의 호출 스택이다. 위에서부터 "가장 안쪽 함수"이고, 아래로 갈수록 그걸 부른 쪽이다. 각 줄은 `at 함수이름 (파일:줄:칸)` 모양이다.

V8은 기본으로 열 줄까지만 남긴다.

```bash
node -e 'console.log(Error.stackTraceLimit)'
```

```text
10
```

프레임워크 안쪽이 깊으면 열 줄이 전부 라이브러리 내부라, 정작 내 코드가 잘려 나간다. 개발 환경에서 `Error.stackTraceLimit = 50`으로 늘리거나 `node --stack-trace-limit=50`으로 띄우면 더 본다. 스택을 모으는 데 비용이 들어서, 운영에서 무한정 늘리지는 않는다.

비동기 경계에서는 스택이 끊긴다. 콜백 장면에서 `loadConfig`가 스택에 없던 이유다. `await`는 예외다. V8의 비동기 스택 트레이스(zero-cost async stack traces)는 `await`로 이어진 함수를 `at async 함수이름`으로 이어 붙인다. `.then` 콜백, `setTimeout`, 이벤트 콜백은 이어 주지 않는다. 같은 일을 `await`로 쓰면 스택이 길게 남는 이유다.

`Error.cause`는 끊기지 않은 이야기를 남기는 방법이다. 아래쪽 에러를 감싸 의미를 더하되, 원래 에러를 버리지 않는다. Node 16.9부터 쓸 수 있다.

```js
async function loadConfig(path) {
  try {
    return JSON.parse(await readFile(path, "utf8"));
  } catch (err) {
    throw new Error(`config load failed: ${path}`, { cause: err });
  }
}
async function main() { await loadConfig("/srv/app/config.json"); }
main().catch((err) => { console.error(err); process.exitCode = 1; });
```

```text
Error: config load failed: /srv/app/config.json
    at loadConfig (file:///srv/app/cause.mjs:6:11)
    at async main (file:///srv/app/cause.mjs:9:25) {
  [cause]: Error: ENOENT: no such file or directory, open '/srv/app/config.json'
      at async open (node:internal/fs/promises:636:25)
      at async readFile (node:internal/fs/promises:1235:14)
      at async loadConfig (file:///srv/app/cause.mjs:4:23)
      at async main (file:///srv/app/cause.mjs:9:25) {
    errno: -2,
    code: 'ENOENT',
    syscall: 'open',
    path: '/srv/app/config.json'
  }
}
```

바깥 에러는 "무엇을 하다가" 실패했는지, `[cause]`는 "운영체제가 왜 거절했는지"를 말한다. `at async main`이 두 군데 모두 나오는 것도 보인다. 흔한 실수는 `throw new Error("config load failed: " + err.message)`처럼 메시지만 이어 붙이는 것이다. 그러면 `code`와 원래 스택이 사라져서, 위쪽에서 `err.code === "ENOENT"`로 분기할 수 없다.

## 받은 에러를 어떻게 할지 정하는 함수

정리하면 에러를 받은 쪽이 고를 길은 넷이다. 버그면 기록하고 죽는다. 다시 해 볼 만한 일시적 실패면 재시도한다. 사용자의 잘못이면 4xx로 답한다. 나머지는 5xx로 답한다. 이걸 함수로 짜 보면 `cause` 사슬까지 봐야 한다는 게 드러난다. 겉은 평범한 `Error`인데 안쪽에 ETIMEDOUT이 있을 수 있다.

아래 `triage`를 완성해 보자. 사슬 안 어디든 버그 이름(`TypeError`, `ReferenceError`, `SyntaxError`, `RangeError`, `AssertionError`)이 있으면 `"crash"`, 아니면 사슬 안 어디든 일시적 코드(`ECONNRESET`, `ETIMEDOUT`, `ECONNREFUSED`, `EAI_AGAIN`, `EPIPE`)가 있으면 `"retry"`, 아니면 바깥 에러의 `status`가 400~499면 `"client"`, 그 밖은 `"server"`다.

  const BUGS = ["TypeError", "ReferenceError", "SyntaxError", "RangeError", "AssertionError"];

## 운영에서 에러를 따라가는 순서

재시작이 반복되는데 이유를 모를 때는 이 순서로 본다.

```bash
# 1. 마지막으로 어떻게 끝났는지: 종료 코드와 이유
kubectl get pod order-api-7d9f -o jsonpath='{.status.containerStatuses[0].lastState.terminated}'
# 2. 직전 컨테이너가 남긴 stdout과 stderr
kubectl logs order-api-7d9f --previous --tail=50
# 3. systemd로 돌리는 서버라면
sudo journalctl -u order-api --since "03:00" --until "03:30"
```

첫 줄에서 `exitCode`와 `reason`을 본다. 1이면 앱 안에서 잡히지 않은 에러이고, 2번 로그의 마지막 스택이 범인이다. 137에 `OOMKilled`면 메모리를, 143이면 배포나 스케일 다운 같은 바깥의 종료 요청을 본다. 앱 로그 시스템에 마지막 스택이 없다면 stderr를 버리고 있지 않은지 확인한다.

새는 거부를 개발 중에 미리 찾고 싶다면 `--unhandled-rejections=strict`로 띄워 본다. `unhandledRejection` 리스너가 있어도 무조건 예외로 올린다. 테스트 러너에서 켜 두면 `await` 빠뜨린 호출이 테스트 실패로 드러난다. 타입스크립트 쪽에서는 typescript-eslint의 `no-floating-promises` 규칙이 같은 실수를 정적으로 잡는다.

운영 중인 프로세스에 직접 붙어서 에러가 나는 순간을 멈춰 보는 방법, CPU와 메모리를 뜨는 방법은 [Node.js 디버깅과 프로파일링 글](/posts/nodejs-debugging-profiling)에서 이어 간다.

## 다시 새벽 세 시로

로그 한 줄 없이 재시작되던 서비스는 사실 매번 마지막 말을 남기고 있었다. 표준 에러에 찍힌 스택, 종료 코드 1, 그리고 그 스택 맨 아래의 `FSReqCallback`이 "콜백 경계에서 샌 에러"라고 말해 주고 있었다. 에러를 받는 자리를 경계마다 두고, 버그는 기록하고 죽게 하고, 예상한 실패는 `code`와 `cause`를 살려 위로 올린다. 그리고 프로세스가 끝날 때 남기는 숫자를 읽는다. 이 세 가지면 다음 새벽에는 첫 줄에서 원인을 본다.

## 면접에서 나올 만한 질문

### Node.js에서 에러는 어떤 종류로 나뉘나요?

자바스크립트 엔진이 던지는 `TypeError` 같은 에러, 운영체제 요청이 실패한 시스템 에러, 직접 정의한 에러, `assert`가 던지는 `AssertionError`로 나눈다. 시스템 에러는 `name`이 그냥 `Error`라서 `code`(ENOENT, ECONNRESET), `errno`, `syscall`로 구분한다. 분기는 바뀔 수 있는 메시지 대신 `code`로 한다.

### 콜백 안에서 던진 에러는 왜 바깥 try/catch로 못 잡나요?

콜백은 바깥 함수가 이미 반환한 뒤에 이벤트 루프가 새 스택에서 부르기 때문이다. `try`는 실행 중인 스택에만 걸려 있어서, 콜백이 돌 때는 이미 없다. 그래서 콜백 API는 첫 인자로 에러를 넘기고, 받은 쪽이 `if (err)`로 직접 확인해야 한다. 요즘은 `fs/promises`처럼 Promise API를 쓰고 `await`로 이어서 `try`가 닿게 만든다.

### uncaughtException에서 로그만 찍고 계속 돌리면 왜 위험한가요?

에러가 난 지점 이후의 코드가 실행되지 않아서 상태가 반쯤 바뀐 채로 남기 때문이다. 빌린 DB 연결이나 잠금이 반납되지 않으면 프로세스는 살아 있지만 요청을 처리하지 못하고, 헬스 체크는 통과해서 재시작도 안 된다. 그래서 이 이벤트는 동기로 로그를 남기고, 새 요청을 막고, 짧게 기다린 뒤 종료하는 자리로 쓴다. 재시작은 쿠버네티스나 systemd 같은 프로세스 관리자에게 맡긴다.

### 처리되지 않은 Promise 거부는 Node에서 어떻게 되나요?

Node 15부터 기본값 `--unhandled-rejections=throw`라서 잡히지 않은 예외처럼 다뤄지고 종료 코드 1로 끝난다. 14 이하는 경고만 찍고 계속 돌았다. `unhandledRejection` 리스너를 달면 예외로 바뀌지 않으므로, 로그만 찍는 리스너는 옛 동작으로 되돌리는 셈이다. 개발 중에는 `strict` 모드나 `no-floating-promises` 린트로 새는 곳을 찾는다.

### 종료 코드 137과 143은 무엇을 뜻하나요?

시그널로 끝난 프로세스는 셸과 컨테이너가 128에 시그널 번호를 더해 보여 준다. 143은 SIGTERM(15)에 핸들러가 없어 바로 죽은 것이고, 배포 때 처리 중인 요청이 끊겼을 수 있다. 137은 SIGKILL(9)이라 누군가 강제로 죽인 것이고, 컨테이너에서는 메모리 한도 초과로 OOM killer가 죽인 경우가 흔하다. Node 자신의 잡히지 않은 예외는 1이다.

### process.exit()와 process.exitCode는 어떻게 다른가요?

`process.exit()`는 남은 비동기 작업을 기다리지 않고 바로 끝낸다. 파일 쓰기가 `open`만 되고 `write` 전에 끊겨 0바이트 파일이 남는 일이 실제로 생긴다. `exitCode`는 종료 코드만 정해 두고 이벤트 루프가 빌 때까지 기다린다. 보통은 `exitCode`를 쓰고, 정리가 끝나지 않을 때를 대비한 강제 종료에만 `exit`를 쓴다.

### async 에러를 Express 4가 왜 못 잡았나요?

Express 4 라우터는 핸들러를 동기 `try/catch`로 부르고 반환값을 보지 않는다. async 핸들러는 에러를 던지지 않고 거부된 Promise를 돌려주므로 라우터의 `catch`에 닿지 않고, 처리되지 않은 거부가 되어 Node 15 이상에서는 프로세스가 죽는다. Express 5는 반환된 Promise의 거부를 `next(err)`로 넘겨 준다. 그래도 핸들러 안의 `setTimeout`이나 이벤트 콜백에서 던진 에러는 그 Promise와 무관해서 여전히 못 잡는다.

### Error.cause는 왜 쓰나요?

아래쪽 에러를 감싸 "무엇을 하다 실패했는지"를 더하면서 원래 에러의 `code`와 스택을 그대로 남기려고 쓴다. 메시지만 이어 붙이면 위쪽에서 `code`로 분기할 수 없고 원래 스택도 잃는다. Node 16.9부터 `new Error(msg, { cause })`로 쓸 수 있고, `console.error`나 `util.inspect`는 `[cause]`까지 펼쳐 찍는다. 분류 코드도 사슬을 따라가며 판단해야 겉은 평범한데 안에 ETIMEDOUT이 있는 경우를 놓치지 않는다.
