서버 지표 대시보드에서 "최근 5분 동안의 최대 응답 시간"을 1초마다 갱신한다고 해 보자. 새 값이 들어오면 5분 전 값이 빠진다. 합이나 평균이라면 들어온 값을 더하고 나간 값을 빼면 끝이다. 최댓값은 그렇게 안 된다. 빠져나간 값이 최댓값이었다면 두 번째로 큰 값이 무엇인지 알아야 하는데, 그걸 들고 있지 않다.

이 문제가 정확히 그 상황이다. 지금까지의 창 문제([Minimum Window Substring](/posts/leetcode-minimum-window-substring)까지)는 개수를 세는 것으로 창의 상태를 표현할 수 있었다. 최댓값은 개수로 표현되지 않는다. 그래서 창 안의 "앞으로 최댓값이 될 수 있는 후보"만 순서대로 들고 다니는 단조 덱(monotonic deque)이라는 구조가 등장한다. 이 글은 창마다 다 보기, 최대 힙, 정렬된 멀티셋, 희소 테이블, 블록 나누기, 단조 덱 순서로 간다. 문제 원문은 [LeetCode 239](https://leetcode.com/problems/sliding-window-maximum/)다. 코드는 모두 Node.js 22, Python 3.13, Java로 돌렸다.

## 길이 k인 창마다 최댓값

정수 배열 `nums`와 창의 길이 `k`가 주어진다. 길이 k인 창을 맨 왼쪽부터 한 칸씩 오른쪽으로 옮기며, 창마다 그 안의 최댓값을 구해 배열로 돌려준다. 창은 `n - k + 1`개다.

풀이에 영향을 주는 제약은 이렇다.

- 길이 n은 1 이상 10만 이하, k는 1 이상 n 이하다. k가 n의 절반쯤이면 창마다 다 보는 방법이 약 25억 번 비교해야 한다.
- 값은 -1만 이상 1만 이하다. 음수가 있으니 최댓값의 초깃값을 0으로 두면 안 된다.

## 손으로 먼저 풀어 보기

예시는 `nums = [4, 2, 12, 3, 8, 1, 5]`, `k = 3`이다.

```text
창 위치   창 안         최댓값
0~2      4  2  12      12
1~3      2  12  3      12
2~4      12  3  8      12
3~5      3  8  1        8
4~6      8  1  5        8
```

답은 `[12, 12, 12, 8, 8]`이다.

표를 보면서 생각해 볼 것이 있다. 12가 2번 칸에 들어온 뒤로 4와 2는 다시는 최댓값이 되지 못한다. 12보다 작은데, 12보다 먼저 창을 떠나기 때문이다. 3도 8이 들어온 순간 쓸모가 없어진다. 반대로 8은 12보다 작지만 12보다 오래 창에 남으니, 12가 떠난 뒤 최댓값이 될 수 있다. 실제로 3~5번 창에서 그렇게 된다.

"나보다 늦게 들어왔고 나보다 큰 값이 있으면, 나는 영영 최댓값이 못 된다." 이 관찰이 마지막 풀이의 전부다.

## 창마다 처음부터 다 보기

창마다 k개를 훑어 최댓값을 찾는다.

```js
function maxBrute(nums, k) {
  const res = [];
  for (let i = 0; i + k <= nums.length; i++) {
    let m = -Infinity; // 값에 음수가 있으니 0이 아니라 -Infinity에서 시작한다
    for (let j = i; j < i + k; j++) m = Math.max(m, nums[j]);
    res.push(m);
  }
  return res;
}
```

창이 n − k + 1개이고 하나에 k번 보니 O((n − k + 1)·k) = O(nk)다. k가 작으면 오히려 가장 빠르다. 10만 개, k = 3에서 3ms였다. 그런데 k = 5만이면 비교가 약 25억 번이라 2초가 걸렸다. k가 크면 쓸 수 없다.

낭비는 이웃한 두 창이 k − 1칸을 공유하는데도 매번 처음부터 본다는 데 있다. 합이라면 한 칸 들어오고 한 칸 나가는 걸 O(1)로 처리했을 것이다. 최댓값도 그렇게 하고 싶은데, 나간 값이 최댓값이었을 때가 문제다. 다음 풀이들은 "나간 값을 빼도 다음 최댓값을 빨리 알 수 있는 구조"를 찾는다.

## 최대 힙에 넣고 낡은 꼭대기만 버린다

[힙](/posts/ds-heap)은 가장 큰 값을 O(1)에 보여 주고, 넣기와 꺼내기가 O(log n)이다. 문제는 힙이 "임의의 원소 지우기"를 잘 못한다는 것이다. 창 밖으로 나간 값을 힙 한가운데서 찾아 지우려면 O(n)이 든다.

요령은 지우기를 미루는 것이다. 힙에 `[값, 인덱스]`를 넣어 두고, 꼭대기를 볼 때만 그게 창 안인지 확인한다. 창 밖이면 그때 꺼내 버린다. 꼭대기가 아닌 낡은 값은 힙 안에 남아 있어도 답에 영향을 주지 않는다. 늦은 삭제(lazy deletion)라고 부른다.

자바스크립트에는 내장 힙이 없어서 작게 만들어 쓴다.

```js
class MaxHeap {
  constructor() { this.a = []; }
  top() { return this.a[0]; }
  push(x) { // x = [값, 인덱스]
    const a = this.a;
    a.push(x);
    let i = a.length - 1;
    while (i > 0) { // 부모보다 크면 위로 올린다
      const p = (i - 1) >> 1;
      if (a[p][0] >= a[i][0]) break;
      [a[p], a[i]] = [a[i], a[p]];
      i = p;
    }
  }
  pop() {
    const a = this.a, top = a[0], last = a.pop();
    if (a.length) {
      a[0] = last;
      let i = 0;
      for (;;) { // 자식 중 큰 쪽보다 작으면 아래로 내린다
        const l = 2 * i + 1, r = l + 1;
        let m = i;
        if (l < a.length && a[l][0] > a[m][0]) m = l;
        if (r < a.length && a[r][0] > a[m][0]) m = r;
        if (m === i) break;
        [a[m], a[i]] = [a[i], a[m]];
        i = m;
      }
    }
    return top;
  }
}

function maxHeap(nums, k) {
  const heap = new MaxHeap(), res = [];
  for (let i = 0; i < nums.length; i++) {
    heap.push([nums[i], i]);
    if (i >= k - 1) {
      // 꼭대기가 창 [i-k+1, i] 밖이면 버린다. 안이면 그게 최댓값이다
      while (heap.top()[1] <= i - k) heap.pop();
      res.push(heap.top()[0]);
    }
  }
  return res;
}
```

원소마다 한 번 넣고 많아야 한 번 꺼내니 O(n log n)이다. 힙 크기가 k를 넘어 n까지 커질 수 있다는 점이 아쉽다. 예를 들어 값이 계속 커지는 배열이면 낡은 값이 꼭대기에 오지 않아 쌓이기만 한다. 공간은 O(n)이다.

Python은 `heapq`가 최소 힙이라 부호를 뒤집어 넣는다.

```python
import heapq

def max_heap(nums, k):
    heap, res = [], []
    for i, x in enumerate(nums):
        heapq.heappush(heap, (-x, i))  # 최소 힙이라 부호를 뒤집는다
        if i >= k - 1:
            while heap[0][1] <= i - k:  # 꼭대기가 창 밖이면 버린다
                heapq.heappop(heap)
            res.append(-heap[0][0])
    return res
```

Java는 `PriorityQueue`에 내림차순 비교자를 준다. 비교자를 `(a, b) -> b[0] - a[0]`으로 쓰는 코드가 흔한데, 이 문제의 값 범위(±1만)에서는 괜찮지만 값이 `int` 범위 끝까지 가면 뺄셈이 넘쳐 순서가 뒤집힌다. `Integer.compare(b[0], a[0])`가 안전하다.

```java
static int[] withHeap(int[] nums, int k) {
    PriorityQueue<int[]> pq = new PriorityQueue<>((a, b) -> Integer.compare(b[0], a[0]));
    int[] res = new int[nums.length - k + 1];
    for (int i = 0; i < nums.length; i++) {
        pq.offer(new int[]{nums[i], i});
        if (i >= k - 1) {
            while (pq.peek()[1] <= i - k) pq.poll(); // 낡은 꼭대기를 버린다
            res[i - k + 1] = pq.peek()[0];
        }
    }
    return res;
}
```

## 정렬된 멀티셋에서 나간 값을 바로 지운다

힙 대신 원소를 정렬된 상태로 들고 있으면서 임의의 값을 O(log k)에 지울 수 있는 구조를 쓰면, 창 안의 값만 정확히 들고 다닐 수 있다. 균형 이진 탐색 트리가 그런 구조다. Java의 `TreeMap`을 "값 → 개수"로 쓰면 같은 값이 여러 개 있는 멀티셋이 된다.

```java
static int[] withTreeMap(int[] nums, int k) {
    TreeMap<Integer, Integer> count = new TreeMap<>(); // 값 -> 창 안 개수
    int[] res = new int[nums.length - k + 1];
    for (int i = 0; i < nums.length; i++) {
        count.merge(nums[i], 1, Integer::sum);
        if (i >= k) { // 창 밖으로 나간 값을 하나 지운다
            int out = nums[i - k];
            if (count.merge(out, -1, Integer::sum) == 0) count.remove(out);
        }
        if (i >= k - 1) res[i - k + 1] = count.lastKey(); // 가장 큰 키가 최댓값
    }
    return res;
}
```

넣기, 지우기, 최댓값이 모두 O(log k)라 전체 O(n log k), 공간 O(k)다. 힙과 달리 창 크기만큼만 들고 있다. 개수가 0이 된 키를 `remove`하지 않으면 `lastKey()`가 이미 나간 값을 돌려준다.

C++의 `multiset`, Python의 `sortedcontainers.SortedList`도 같은 역할이다. JavaScript와 Python 표준 라이브러리에는 이런 구조가 없어서 코딩 테스트에서는 잘 쓰지 않는다. 대신 "창의 중앙값"(LeetCode 480)처럼 최댓값이 아닌 순위 정보가 필요해지면 이 풀이 쪽이 살아남는다.

## 미리 구간 최댓값 표를 만들어 두기

배열이 바뀌지 않으니, 아무 구간의 최댓값이든 O(1)에 답하는 표를 먼저 만들 수도 있다. 희소 테이블(sparse table)은 `st[j][i]`에 "i에서 시작하는 길이 2^j 구간의 최댓값"을 적는다. 길이 k 구간은 길이 2^j(2^j ≤ k인 가장 큰 j) 구간 두 개로 덮을 수 있다. 두 구간이 겹쳐도 최댓값은 상관없다.

```js
function maxSparse(nums, k) {
  const n = nums.length;
  const lg = new Array(n + 1).fill(0); // lg[x] = floor(log2 x)
  for (let i = 2; i <= n; i++) lg[i] = lg[i >> 1] + 1;
  const st = [nums.slice()]; // st[0]: 길이 1 구간 = 원소 자신
  for (let j = 1; (1 << j) <= n; j++) {
    const prev = st[j - 1], cur = new Array(n - (1 << j) + 1);
    // 길이 2^j 구간 = 길이 2^(j-1) 구간 두 개를 이어 붙인 것
    for (let i = 0; i + (1 << j) <= n; i++) cur[i] = Math.max(prev[i], prev[i + (1 << (j - 1))]);
    st.push(cur);
  }
  const j = lg[k], res = [];
  for (let i = 0; i + k <= n; i++) {
    res.push(Math.max(st[j][i], st[j][i + k - (1 << j)])); // 앞쪽 2^j칸과 뒤쪽 2^j칸
  }
  return res;
}
```

표를 만드는 데 O(n log n) 시간과 공간이 들고, 창마다 O(1)이다. 이 문제처럼 창 길이가 하나로 정해져 있으면 과한 도구다. 하지만 "길이가 제각각인 구간 최댓값 질문이 수만 개"라면 이 표가 가장 빠르다. 값이 바뀌기도 한다면 세그먼트 트리를 쓴다.

## k칸씩 블록으로 나눠 양쪽에서 쌓기

창 길이가 k로 고정돼 있으니 표를 O(n)으로 줄일 수 있다. 배열을 앞에서부터 k칸씩 블록으로 자른다. 그러면 길이 k인 창은 많아야 두 블록에 걸친다. 앞 블록의 뒷부분과 뒤 블록의 앞부분이다.

- `left[i]`: i가 속한 블록의 시작부터 i까지의 최댓값 (블록 안 앞쪽 누적)
- `right[i]`: i부터 i가 속한 블록의 끝까지의 최댓값 (블록 안 뒤쪽 누적)

창 `[i, i + k − 1]`의 최댓값은 `max(right[i], left[i + k − 1])`이다. `right[i]`가 앞 블록의 뒷부분, `left[i + k − 1]`이 뒤 블록의 앞부분을 덮는다. 창이 한 블록에 딱 맞으면 두 값이 같은 블록 전체를 덮을 뿐 답은 같다.

```js
function maxBlocks(nums, k) {
  const n = nums.length;
  const left = new Array(n), right = new Array(n);
  for (let i = 0; i < n; i++) {
    // 블록이 시작하는 칸에서 누적을 새로 시작한다
    left[i] = i % k === 0 ? nums[i] : Math.max(left[i - 1], nums[i]);
  }
  for (let i = n - 1; i >= 0; i--) {
    // 블록이 끝나는 칸(또는 배열 끝)에서 거꾸로 누적을 새로 시작한다
    right[i] = i === n - 1 || (i + 1) % k === 0 ? nums[i] : Math.max(right[i + 1], nums[i]);
  }
  const res = [];
  for (let i = 0; i + k <= n; i++) res.push(Math.max(right[i], left[i + k - 1]));
  return res;
}
```

예시에서 블록은 `[4, 2, 12]`, `[3, 8, 1]`, `[5]`다. `left = [4, 4, 12, 3, 8, 8, 5]`, `right = [12, 12, 12, 8, 8, 1, 5]`이고, 창 1~3은 `max(right[1], left[3]) = max(12, 3) = 12`, 창 3~5는 `max(right[3], left[5]) = max(8, 8) = 8`이 나온다.

세 번 훑으니 O(n) 시간, 배열 두 개라 O(n) 공간이다. 덱 없이 배열만으로 O(n)을 내는 깔끔한 방법이라 면접에서 두 번째 풀이로 보여 주기 좋다. 한계는 배열 전체를 먼저 알아야 한다는 것이다. 값이 하나씩 흘러 들어오는 스트림에서는 `right`를 만들 수 없다.

## 앞으로 최댓값이 될 후보만 남긴다

손으로 풀며 본 관찰로 돌아간다. 새 값 x가 창에 들어오면, x보다 먼저 들어왔고 x보다 작거나 같은 값은 앞으로 영원히 최댓값이 될 수 없다. x보다 먼저 창을 떠나고, 남아 있는 동안엔 x가 더 크거나 같기 때문이다. 그런 값은 지금 버려도 된다.

그렇게 버리고 나면 남는 후보들은 들어온 순서대로 놓았을 때 값이 점점 작아진다(앞이 가장 크다). 이 성질을 지키는 덱(deque, 양쪽 끝에서 넣고 뺄 수 있는 큐)을 단조 덱이라고 한다. 덱 자체는 [스택·큐·덱 글](/posts/ds-stack-queue-deque)에서 다뤘다.

덱에는 값이 아니라 인덱스를 넣는다. 창 밖으로 나갔는지 판단하려면 위치가 필요하기 때문이다.

1. 덱 맨 앞 인덱스가 창 밖(`i - k` 이하)이면 앞에서 뺀다. 창이 한 칸씩 움직이니 많아야 하나다.
2. 덱 맨 뒤 값이 `nums[i]`보다 작거나 같은 동안 뒤에서 뺀다.
3. `i`를 뒤에 넣는다.
4. 창이 다 찼으면(`i >= k - 1`) 덱 맨 앞 값이 이 창의 최댓값이다.

```js
function maxSlidingWindow(nums, k) {
  const dq = new Array(nums.length); // 인덱스를 담는 덱. 배열과 머리/꼬리 위치로 만든다
  let head = 0, tail = 0;            // 덱의 내용은 dq[head..tail)
  const res = [];
  for (let i = 0; i < nums.length; i++) {
    // 1. 맨 앞이 창 [i-k+1, i] 밖으로 나갔으면 뺀다
    if (head < tail && dq[head] <= i - k) head++;
    // 2. 새 값보다 작거나 같은 뒤쪽 후보는 다시는 최댓값이 못 된다
    while (head < tail && nums[dq[tail - 1]] <= nums[i]) tail--;
    // 3. 새 인덱스를 뒤에 넣는다
    dq[tail++] = i;
    // 4. 맨 앞이 이 창의 최댓값
    if (i >= k - 1) res.push(nums[dq[head]]);
  }
  return res;
}
```

반복문 안에 `while`이 있지만 O(n)이다. 인덱스마다 덱에 한 번 들어오고(3번), 많아야 한 번 나간다(1번이나 2번). 그래서 덱 연산은 모두 합쳐 2n 이하다. 공간은 덱에 많아야 k개라 O(k)다(결과 배열 제외).

## 세 언어로 쓴 최종 코드

Python은 `collections.deque`가 양쪽 끝 연산을 O(1)에 한다.

```python
from collections import deque
from typing import List

class Solution:
    def maxSlidingWindow(self, nums: List[int], k: int) -> List[int]:
        dq = deque()  # 인덱스. 앞에서 뒤로 갈수록 값이 작아진다
        res = []
        for i, x in enumerate(nums):
            if dq and dq[0] <= i - k:       # 창 밖으로 나간 앞쪽 인덱스
                dq.popleft()
            while dq and nums[dq[-1]] <= x:  # 새 값보다 작거나 같은 뒤쪽은 다시는 최댓값이 못 된다
                dq.pop()
            dq.append(i)
            if i >= k - 1:
                res.append(nums[dq[0]])
        return res
```

Java는 `ArrayDeque`를 쓴다. `Stack`이나 `LinkedList`보다 빠르다.

```java
import java.util.ArrayDeque;
import java.util.Deque;

class Solution {
    public int[] maxSlidingWindow(int[] nums, int k) {
        Deque<Integer> dq = new ArrayDeque<>(); // 인덱스. 앞쪽 값이 가장 크다
        int[] res = new int[nums.length - k + 1];
        for (int i = 0; i < nums.length; i++) {
            if (!dq.isEmpty() && dq.peekFirst() <= i - k) dq.pollFirst();          // 창 밖
            while (!dq.isEmpty() && nums[dq.peekLast()] <= nums[i]) dq.pollLast(); // 쓸모없어진 뒤쪽
            dq.offerLast(i);
            if (i >= k - 1) res[i - k + 1] = nums[dq.peekFirst()];
        }
        return res;
    }
}
```

`([4,2,12,3,8,1,5], 3)`, `([1], 1)`, `([-3,-1,-2,-5], 2)`, `([7,7,7,7], 2)`를 넣어 세 언어 모두 `[12,12,12,8,8]`, `[1]`, `[-1,-1,-2]`, `[7,7,7]`이 나왔다. 여섯 풀이가 같은 답을 내는지는 길이 12 이하, 값 -5~5인 무작위 배열 3000개로 비교했다.

언어마다 조심할 곳이 다르다.

- JavaScript 배열의 `shift()`는 앞을 빼고 나머지를 한 칸씩 당기니 O(덱 길이)다. 덱이 짧으면 티가 안 나지만, 값이 계속 줄어드는 배열이면 덱에 k개가 꽉 찬다. 10만 개 감소 배열, k = 5만에서 `shift()` 버전은 6.4초, 머리 위치를 옮기는 위 코드는 2ms였다. 덱 앞을 빼는 일이 잦으면 `head` 인덱스를 쓴다.
- Java의 `Deque<Integer>`는 박싱된 `Integer`를 담는다. `dq.peekFirst() <= i - k`처럼 `int`와 비교하면 자동으로 풀려 괜찮지만, `dq.peekFirst() == dq.peekLast()`처럼 `Integer`끼리 `==`로 비교하면 -128~127 밖에서는 객체 비교가 되어 틀린다. 속도가 중요하면 `int[]`와 머리·꼬리 인덱스로 직접 만든다.
- Python의 `list.pop(0)`도 O(n)이다. 반드시 `deque.popleft()`를 쓴다.

## 여섯 풀이 비교

| 풀이 | 시간 | 공간 | 언제 고르나 |
|---|---|---|---|
| 창마다 다 보기 | O(nk) | O(1) | k가 아주 작을 때, 정답 확인용 |
| 최대 힙 + 늦은 삭제 | O(n log n) | O(n) | 덱이 떠오르지 않을 때의 첫 개선 |
| 정렬된 멀티셋 | O(n log k) | O(k) | 최댓값 말고 중앙값·k번째 값이 필요할 때 |
| 희소 테이블 | O(n log n) | O(n log n) | 길이가 제각각인 구간 질문이 많을 때 |
| 블록 나누기 | O(n) | O(n) | 덱 없이 O(n), 배열 전체를 알 때 |
| 단조 덱 | O(n) | O(k) | 면접 기본 답. 스트림에도 쓴다 |

10만 개 무작위 배열에서 k = 5만일 때 창마다 다 보기는 2초, 나머지는 모두 20ms 안쪽이었다. k = 3에서는 창마다 다 보기가 3ms로 오히려 힙(51ms)이나 희소 테이블(35ms)보다 빨랐다. 복잡도가 같아도 k가 작으면 상수가 이긴다.

## 값만 담으면 생기는 일

덱에 인덱스 대신 값을 담고, 창에서 나가는 값 `nums[i - k]`가 덱 맨 앞 값과 같으면 빼는 코드가 있다. 그럴듯하지만 같은 값이 있으면 틀린다.

```js
function valueDeque(nums, k) {
  const dq = [], res = [];
  for (let i = 0; i < nums.length; i++) {
    if (i >= k && dq[0] === nums[i - k]) dq.shift(); // 나가는 값과 같으면 뺀다?
    while (dq.length && dq[dq.length - 1] <= nums[i]) dq.pop();
    dq.push(nums[i]);
    if (i >= k - 1) res.push(dq[0]);
  }
  return res;
}
valueDeque([2, 2, 0], 2); // [2, 0]. 정답은 [2, 2]
```

값을 담고 싶다면 뒤를 뺄 때 `<`로 써서 같은 값을 모두 남겨야 한다. 그러면 나가는 값과 같은 맨 앞이 정말 그 원소이거나, 같은 값이 하나 더 남아 있어 답이 틀리지 않는다. 하지만 이런 경우의 수를 따지느니 처음부터 인덱스를 담는 게 낫다.

다른 실수들도 있다.

- 창 밖 판정을 `dq[head] < i - k`로 쓴다. 인덱스 `i - k`는 이미 창 `[i - k + 1, i]` 밖인데 남겨 두니 창이 k + 1칸이 된다. 예시에서 `[12, 12, 12, 12, 8]`이 나온다.
- 결과를 창이 다 차기 전부터 넣는다. `i >= k - 1` 검사를 빼면 결과가 n개가 된다.
- 최댓값 초깃값을 0으로 둔다. 창마다 다 보기 풀이에서 값이 모두 음수면 0이 나온다.
- 결과 배열 크기를 `n - k`로 잡는다. 창은 `n - k + 1`개다. Java에서 `ArrayIndexOutOfBoundsException`이 난다.

## 덱을 바꿔 쓰는 문제들

### 창의 최솟값이라면

부등호를 뒤집어 앞이 가장 작게 유지한다. 뒤에서 뺄 조건이 `nums[뒤] >= nums[i]`가 된다. [Best Time to Buy and Sell Stock](/posts/leetcode-best-time-to-buy-and-sell-stock)을 "최근 k일 안에서만 사고팔 수 있다"로 바꾸면 창의 최솟값이 필요한데, 바로 이 덱으로 푼다.

### 최댓값과 최솟값의 차이가 limit 이하인 가장 긴 구간 (LeetCode 1438)

창 길이가 고정이 아니라 가변이다. 최댓값 덱과 최솟값 덱을 함께 들고 다니며, 차이가 limit를 넘으면 왼쪽을 당긴다. 당길 때 각 덱의 맨 앞 인덱스가 `l`보다 작아지면 앞에서 뺀다.

```js
function longestSubarray(nums, limit) {
  const maxQ = [], minQ = [];
  let mh = 0, nh = 0; // 두 덱의 머리 위치
  let l = 0, best = 0;
  for (let r = 0; r < nums.length; r++) {
    while (maxQ.length > mh && nums[maxQ[maxQ.length - 1]] <= nums[r]) maxQ.pop();
    while (minQ.length > nh && nums[minQ[minQ.length - 1]] >= nums[r]) minQ.pop();
    maxQ.push(r);
    minQ.push(r);
    while (nums[maxQ[mh]] - nums[minQ[nh]] > limit) { // 차이가 크면 왼쪽을 당긴다
      l++;
      if (maxQ[mh] < l) mh++;
      if (minQ[nh] < l) nh++;
    }
    best = Math.max(best, r - l + 1);
  }
  return best;
}
longestSubarray([4, 2, 12, 3, 8, 1, 5], 4); // 2
```

모든 구간을 보는 코드와 무작위 배열 3000개로 비교해 같은 답이 나왔다. [Longest Substring Without Repeating Characters](/posts/leetcode-longest-substring-without-repeating)의 가변 창에 이 글의 덱을 얹은 모양이다.

### 합이 K 이상인 가장 짧은 구간, 음수 포함 (LeetCode 862)

값에 음수가 있으면 보통의 가변 창이 안 통한다. 오른쪽을 늘려도 합이 줄 수 있어 "조건이 깨지면 왼쪽을 당긴다"는 단조성이 무너지기 때문이다. 이때는 누적 합 배열 위에서 단조 증가 덱을 쓴다. 지금 누적 합에서 덱 맨 앞 누적 합을 뺀 값이 K 이상이면 기록하고 앞에서 빼고, 지금 누적 합 이상인 뒤쪽은 뒤에서 뺀다. 창 패턴이 실패하는 자리에서 덱이 대신 들어간다.

```js
function shortestSubarray(nums, k) {
  const n = nums.length, P = new Array(n + 1).fill(0);
  for (let i = 0; i < n; i++) P[i + 1] = P[i] + nums[i]; // P[i] = 앞 i개의 합
  const dq = new Array(n + 1);
  let head = 0, tail = 0, best = Infinity;
  for (let i = 0; i <= n; i++) {
    // 맨 앞에서 시작하는 구간이 K 이상이면 기록하고 버린다. 더 뒤의 i는 더 길기만 하다
    while (head < tail && P[i] - P[dq[head]] >= k) { best = Math.min(best, i - dq[head]); head++; }
    // 지금 누적 합 이상인 뒤쪽 시작점은 지금 것보다 늘 불리하다
    while (head < tail && P[dq[tail - 1]] >= P[i]) tail--;
    dq[tail++] = i;
  }
  return best === Infinity ? -1 : best;
}
shortestSubarray([4, -3, 1, 5], 6); // 2 ([1, 5])
```

모든 구간을 보는 코드와 음수를 섞은 무작위 배열 5000개로 비교해 같은 답이 나왔다.

### DP의 이전 k칸 중 최댓값 (LeetCode 1696)

`dp[i] = nums[i] + max(dp[i-k..i-1])` 같은 점화식은 그대로 쓰면 O(nk)다. `dp` 값 위에서 이 글의 덱을 돌리면 "이전 k칸의 최댓값"을 O(1)에 얻어 O(n)이 된다. 단조 덱은 창 문제뿐 아니라 DP 최적화 도구로도 자주 나온다.

### 값이 스트림으로 들어온다면

단조 덱은 원래 온라인 알고리즘이다. 값이 하나 들어올 때마다 1~3번 단계를 하고 맨 앞을 읽으면 된다. 메모리는 덱 크기 k 이하로, 창 전체를 따로 저장할 필요도 없다. 처음 장면의 "최근 5분 최대 응답 시간"이 바로 이렇게 계산된다. 시간 기준 창이라면 인덱스 대신 타임스탬프를 덱에 넣고, 맨 앞의 시각이 5분보다 오래됐으면 뺀다.

### 단조 스택과의 관계

뒤에서만 빼는 부분만 보면 단조 스택이다. 단조 스택은 "다음으로 큰 수"처럼 각 원소의 오른쪽 경계를 찾고, 단조 덱은 거기에 "창 밖으로 나간 앞쪽 빼기"를 더해 범위가 정해진 최댓값을 찾는다. 단조 스택 쪽 이야기는 [단조 스택 패턴 글](/posts/monotonic-stack-pattern)에서 이어진다.

## 정리하며

창의 최댓값은 개수로 표현되지 않아서, 나간 값이 최댓값일 때 다음 값을 알 방법이 필요하다. 힙은 낡은 꼭대기를 늦게 버려 O(n log n), 멀티셋은 정확히 지워 O(n log k), 블록 나누기는 앞뒤 누적 최댓값으로 O(n)이다. 단조 덱은 "나보다 늦게 왔고 나보다 크거나 같은 값이 있으면 나는 쓸모없다"는 관찰로 후보만 남겨, 앞이 언제나 최댓값인 덱을 만든다. 인덱스마다 한 번 들어오고 한 번 나가니 O(n)이고, 덱에는 값이 아니라 인덱스를 담는다. 슬라이딩 윈도 문제를 한꺼번에 돌아보려면 [슬라이딩 윈도 패턴 글](/posts/sliding-window-pattern)을 본다.

## 면접에서 나올 만한 질문

### 단조 덱 풀이가 O(n)인 이유는 무엇인가요?

인덱스마다 덱에 한 번 들어오고, 앞에서든 뒤에서든 많아야 한 번 나가기 때문이다. 반복문 안의 `while`이 한 번에 여러 개를 빼더라도 전체를 통틀어 빼는 횟수는 n을 넘지 못한다. 그래서 덱 연산은 합쳐 2n 이하이고, 창마다 맨 앞을 읽는 건 O(1)이다.

### 덱 뒤에서 값을 빼도 되는 근거는 무엇인가요?

새 값 x보다 먼저 들어왔고 x보다 작거나 같은 값은 x보다 먼저 창을 떠나고, 남아 있는 동안은 x가 더 크거나 같다. 그러니 그 값이 최댓값이 되는 창은 앞으로 하나도 없다. 이렇게 빼고 나면 덱은 앞에서 뒤로 값이 줄어드는 순서가 되어 맨 앞이 최댓값이다.

### 덱에 값이 아니라 인덱스를 넣는 이유는 무엇인가요?

맨 앞이 창 밖으로 나갔는지 판단하려면 위치가 필요해서다. 값만 담고 "나가는 값과 맨 앞 값이 같으면 뺀다"로 하면 같은 값이 여러 개일 때 아직 창 안에 있는 원소를 빼 버린다. `[2, 2, 0]`, k = 2에서 `[2, 0]`이 나오는 게 그 예다. 인덱스로는 `dq[0] <= i - k`로 정확히 판정한다.

### 힙으로 풀면 무엇이 아쉽나요?

힙은 임의의 원소를 빨리 지우지 못해서 창 밖 값을 바로 빼지 못한다. 꼭대기를 볼 때만 창 밖인지 확인해 버리는 늦은 삭제로 풀면 O(n log n)이고, 낡은 값이 쌓여 힙이 n까지 커질 수 있다. 덱은 O(n) 시간에 O(k) 공간이다. 대신 힙 풀이는 덱이 떠오르지 않을 때 빠르게 맞는 답을 내는 방법으로 쓸 만하다.

### 덱 없이 O(n)으로 풀 수 있나요?

배열을 k칸씩 블록으로 나누고, 블록마다 앞에서부터의 누적 최댓값과 뒤에서부터의 누적 최댓값을 만든다. 길이 k인 창은 많아야 두 블록에 걸치니 `max(right[i], left[i + k - 1])`로 O(1)에 답한다. 시간 O(n), 공간 O(n)이다. 배열 전체를 먼저 알아야 해서 스트림에는 쓸 수 없다.

### JavaScript로 덱을 만들 때 주의할 점은 무엇인가요?

배열의 `shift()`는 나머지 원소를 한 칸씩 당겨 O(덱 길이)다. 감소하는 배열처럼 덱에 k개가 꽉 차는 입력에서는 전체가 O(nk)로 무너진다. 10만 개, k = 5만에서 `shift()` 버전은 6.4초, 머리 인덱스를 옮기는 버전은 2ms였다. 배열에 머리와 꼬리 위치를 따로 두고 움직인다.

### 창의 중앙값을 구하라면 어떻게 바꾸나요?

중앙값은 최댓값처럼 "쓸모없는 후보"를 버릴 수 없어서 단조 덱이 통하지 않는다. 창 안의 값을 모두 순서 있게 들고 있어야 한다. 작은 절반은 최대 힙, 큰 절반은 최소 힙에 두고 늦은 삭제로 나간 값을 처리하거나, 정렬된 멀티셋에서 가운데를 읽는다. 어느 쪽이든 O(n log k)다.
