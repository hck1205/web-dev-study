서버 세 대 중 한 대가 몇 년 된 장비다. 평소엔 티가 안 나는데, 트래픽이 조금만 늘면 그 서버로 간 요청만 몇 초씩 걸린다. 대시보드의 요청 수는 세 대가 정확히 3분의 1씩이다. 똑같이 나눴는데 왜 한 대만 무너질까.

로드 밸런서가 "어느 서버로 보낼지" 고르는 방법을 알고리즘이라고 부른다. 라운드 로빈, least connections, IP 해시 같은 이름은 익숙하지만, 언제 무엇을 골라야 하는지는 이름만 봐서는 알기 어렵다. 이 글은 같은 요청 흐름 하나를 만들어 놓고 알고리즘만 바꿔 가며 돌려서, 서버별로 몇 개를 받았고 응답이 얼마나 늦었는지를 숫자로 비교한다.

이 주제의 다른 글: 로드 밸런서가 서버를 빼고 넣는 일(헬스 체크, 드레이닝, 세션 고정)은 [로드 밸런서 기본 글](/posts/load-balancer-basics)에, nginx `upstream`에서 각 방식을 켜는 설정과 smooth weighted round-robin의 점수 계산 과정은 [Nginx 리버스 프록시 글](/posts/nginx-reverse-proxy)에, 해시 링의 내부 구조는 [일관 해싱 글](/posts/consistent-hashing)에 있다.

## 실험 무대: 서버 셋, 요청 2만 개

모든 알고리즘을 같은 조건에서 비교하려고 Node.js로 작은 시뮬레이터를 짰다. 무대는 이렇다.

- 서버 A와 B는 일꾼(동시에 처리할 수 있는 요청)이 8개씩이다. 서버 C도 8개지만 처리 속도가 절반이다. 같은 요청이 C에서는 두 배 걸린다.
- 요청 2만 개가 초당 평균 550개씩 무작위 간격(포아송 도착)으로 들어온다.
- 요청의 90%는 10ms짜리 가벼운 조회, 10%는 200ms짜리 무거운 작업이다. 평균은 0.9 × 10 + 0.1 × 200 = 29ms다.
- 요청의 30%는 한 회사의 NAT 뒤에서 오는 같은 IP(198.51.100.1)이고, 나머지는 IP 200개에 흩어져 있다.

일꾼이 모두 바쁘면 요청은 그 서버 앞에 줄을 선다. 서버별 처리 능력을 계산해 보면 A와 B는 초당 8 ÷ 0.029 ≈ 276개, C는 그 절반인 약 138개, 합해서 약 690개다. 초당 550개면 전체로는 80% 정도만 쓰는 여유 있는 상황이다. 문제가 생긴다면 전체 용량이 아니라 나누는 방법 때문이다.

## 차례대로 돌리면 느린 서버가 무너진다

라운드 로빈은 서버 목록을 차례로 돈다. 상태를 볼 필요가 없어서 가장 싸고, 요청 수는 정확히 3분의 1씩이다. 그런데 결과의 C 칸을 보면 가장 붐빌 때 1603개가 걸려 있었고 p99는 10.8초다. 앞에서 계산한 대로 C는 초당 138개를 감당하는데 183개를 받았다. 들어오는 속도가 처리 속도보다 빠르면 줄은 끝없이 길어진다. 실험이 길었다면 더 길어졌을 것이다. 무작위(random)도 기대값으로는 3분의 1씩이라 같은 길을 간다.

이 장면이 처음 질문의 답이다. "요청 수가 같다"는 "부하가 같다"가 아니다. 라운드 로빈은 서버가 모두 같은 사양이고 요청 하나하나의 비용이 비슷할 때만 공평하다.

서버 사양이 다르다는 걸 미리 안다면 가중치를 준다. A와 B에 2, C에 1을 주면 몫이 40:40:20이 되고, C는 초당 110개만 받아 줄이 사라졌다(p99 400ms). nginx가 쓰는 smooth weighted round-robin은 같은 서버를 연달아 주지 않고 섞어서 준다. 점수를 더하고 빼는 과정은 [Nginx 리버스 프록시 글](/posts/nginx-reverse-proxy)에서 한 칸씩 따라갔으니, 여기서는 직접 짜 본다. 가중치 배열과 요청 수를 받아, 요청마다 고른 서버의 번호를 돌려주면 된다. 동점이면 앞 번호가 이긴다.

<CodePlayground
  caption="smooth weighted round-robin"
  functionName="smoothWrr"
  initialCode={`function smoothWrr(weights, n) {
  // 요청마다: 모든 서버 점수 += 자기 weight
  //          가장 큰 서버를 고르고, 그 서버 점수 -= weight 합계
  // 예: smoothWrr([3, 1, 1], 5) → [0, 1, 0, 2, 0]
  const out = [];
  return out;
}`}
  solution={`function smoothWrr(weights, n) {
  const cur = weights.map(() => 0);
  const total = weights.reduce((a, b) => a + b, 0);
  const out = [];
  for (let k = 0; k < n; k++) {
    let best = 0;
    for (let i = 0; i < weights.length; i++) {
      cur[i] += weights[i];
      if (cur[i] > cur[best]) best = i;
    }
    cur[best] -= total;
    out.push(best);
  }
  return out;
}`}
  tests={[

    { args: [[5, 1], 6], expected: [0, 0, 0, 1, 0, 0], label: "5:1은 가운데에 끼운다" },
    { args: [[4, 2, 1], 7], expected: [0, 1, 0, 2, 0, 1, 0], label: "4:2:1" },
    { args: [[1, 1, 1], 4], expected: [0, 1, 2, 0], label: "가중치가 같으면 라운드 로빈" },

가중치의 약점은 숫자를 사람이 정한다는 점이다. 2:2:1은 내가 C가 절반 속도라는 걸 알아서 맞힌 값이다. 실제로는 C가 GC 때문에 잠깐 더 느려지거나, 같은 사양의 서버라도 한 대에 무거운 배치가 같이 돌거나, 클라우드 인스턴스가 시끄러운 이웃을 만나면 비율이 어긋난다. 가중치는 이런 변화를 모른다. 실험에서도 가중치 쪽의 A·B 최대 부하(48)는 아래에서 볼 least-conn(21)보다 두 배 높았다. 몫은 맞췄지만 순간순간의 바쁨은 보지 못해서다.

가중치가 실무에서 빛나는 곳은 오히려 일부러 비율을 어긋나게 할 때다. 새 버전 서버에 weight 1, 기존 서버에 weight 19를 주면 5%만 새 버전으로 가는 카나리 배포가 된다.

## 지금 덜 바쁜 서버로

least connections는 요청이 올 때마다 지금 처리 중인 요청(연결)이 가장 적은 서버를 고른다. 서버의 바쁨을 직접 보는 방식이다. 실험에서 가중치를 주지 않았는데도 몫이 41.5 : 39.3 : 19.2로 저절로 맞춰졌다. C는 요청을 늦게 끝내니 처리 중인 수가 늘 조금 많고, 그만큼 덜 고르게 된다. 최대 부하도 세 서버 모두 20 남짓으로 고르다.

실제 nginx에서도 같은 실험을 했다. 백엔드 셋 중 9003만 응답을 세 배 늦게 주게 하고, 요청 600개를 동시 30개로 보낸 뒤 access.log에서 업스트림별 요청 수를 셌다.

```bash
# 알고리즘만 바꾼 설정으로 nginx를 띄우고, 요청 600개 뒤 업스트림별 개수
node loadq.js 600 30 '/item/{i}?ms=20'
grep -o 'up=[0-9.:]*' logs/access.log | sort | uniq -c
```

```text
== alg-rr
600 req, conc 30: 861ms total, p50 26ms, p99 111ms
    200 up=127.0.0.1:9001
    200 up=127.0.0.1:9002
    200 up=127.0.0.1:9003
== alg-least_conn
600 req, conc 30: 662ms total, p50 23ms, p99 78ms
    254 up=127.0.0.1:9001
    251 up=127.0.0.1:9002
     95 up=127.0.0.1:9003
```

라운드 로빈은 느린 9003에도 정확히 200개를 줬고, least_conn은 95개만 줬다. 전체 시간과 p99가 함께 줄었다. 한 번 돌린 결과라서 숫자는 돌릴 때마다 조금씩 다르지만, 느린 서버의 몫이 줄어드는 방향은 매번 같았다.

least connections를 쓸 때 알아 둘 함정이 셋 있다.

하나는 "연결 수"가 무엇을 세느냐다. HTTP/1.1에서는 연결 하나에 요청 하나가 걸려 있으니 연결 수가 곧 진행 중인 요청 수다. HTTP/2나 gRPC는 연결 하나로 요청 수백 개를 동시에 보낸다. 이때 연결 수로 고르면 의미가 없다. Envoy가 이름을 least connections가 아니라 `LEAST_REQUEST`로 붙인 이유다.

둘은 빨리 실패하는 서버다. DB가 끊긴 서버가 모든 요청에 1ms 만에 500을 돌려주면, 처리 중인 요청이 늘 0이니 least connections는 이 서버를 가장 한가하다고 보고 점점 더 많이 보낸다. 장애 서버가 트래픽을 빨아들이는 블랙홀이 된다. 응답 시간을 보는 방식도 같은 함정에 빠진다. 오류를 따로 세서 빼는 장치(Envoy의 outlier detection, 헬스 체크)와 꼭 함께 쓴다.

셋은 새로 들어온 서버다. 막 뜬 서버는 처리 중인 요청이 0이라 모든 로드 밸런서가 한꺼번에 이 서버를 고른다. 캐시가 비고 JIT가 덜 데워진 서버에 요청이 몰리니 처음 몇십 초가 가장 느리다. slow start로 몫을 서서히 늘린다([로드 밸런서 기본 글](/posts/load-balancer-basics)).

## 모두가 같은 서버를 고를 때

지금까지는 로드 밸런서가 한 대였다. 실제로는 여러 대가 같은 서버 풀을 나눠 쓴다. nginx worker 여러 개, Envoy 사이드카 수백 개, 클라이언트 쪽에서 직접 고르는 gRPC 클라이언트들이 그렇다. 이들은 서로가 방금 어디로 보냈는지 바로 알지 못한다. 서버의 부하 정보는 주기적으로만 갱신되거나(지표 수집 간격), 각자 자기가 보낸 것만 센다.

이 상황에서 least connections는 이상하게 동작한다. 모두가 같은 시점의 같은 숫자를 보고 "가장 한가한 서버"를 고르니, 같은 서버로 한꺼번에 몰린다. 몰린 뒤에야 숫자가 갱신되고, 그러면 또 다른 한 서버로 다 같이 옮겨 간다. 이걸 무리 짓기(herd behavior)라고 한다. 아래 그림에서 다음을 누르면 그 과정이 보인다.

## 둘만 뽑아서 비교하기

P2C(power of two choices)는 서버 전체에서 가장 한가한 하나를 찾지 않는다. 무작위로 두 대를 뽑고, 그 둘 중 덜 바쁜 쪽으로 보낸다. 그게 전부다.

P2C가 잘 동작하는 이유는 두 가지 성질의 균형에 있다. 가장 바쁜 서버는 뽑혀도 다른 하나에게 지니 절대 고르지 않는다. 그리고 가장 한가한 서버도 뽑힐 때만 고르니, 여러 로드 밸런서가 동시에 같은 서버로 몰리지 않는다. 이론으로도 차이가 크다. 서버 n대에 무작위로 n개를 던지면 가장 많이 받은 서버가 log n ÷ log log n 정도를 받는데, 둘을 뽑아 덜 찬 쪽에 넣기만 해도 log log n 정도로 떨어진다(Mitzenmacher의 "the power of two choices" 결과). 셋을 뽑으면 조금 더 좋아지지만 둘에서 얻는 개선이 압도적으로 크다.

계산도 싸다. 전체 서버를 훑지 않고 둘만 보니 서버가 수천 대여도 고르는 비용이 같다. 그래서 대규모 환경의 기본값이 됐다. Envoy의 `LEAST_REQUEST`는 기본으로 두 대를 뽑아 비교하고(`choice_count: 2`), nginx도 1.15.1부터 `random two least_conn`으로 쓸 수 있다. 같은 nginx 실험에서 결과는 least_conn과 거의 같았다.

```text
== alg-randomtwoleast_conn
600 req, conc 30: 601ms total, p50 21ms, p99 70ms
    250 up=127.0.0.1:9001
    250 up=127.0.0.1:9002
    100 up=127.0.0.1:9003
```

nginx 문서도 여러 worker나 여러 nginx가 같은 백엔드를 나눠 쓰는 환경에 `random`을 권한다. worker마다 따로 세는 연결 수는 서로 공유되지 않기 때문이다(upstream에 `zone`을 두면 worker끼리는 공유된다).

## 같은 키는 같은 서버로

지금까지는 요청이 어느 서버로 가도 결과가 같다고 봤다. 그렇지 않은 경우가 있다. 서버마다 로컬 캐시를 두는 경우, 같은 사용자의 WebSocket이 같은 방에 있어야 하는 경우, 세션을 서버 메모리에 두는 옛 앱이다. 이때는 요청의 어떤 값(클라이언트 IP, URL, 사용자 ID)을 해시해서 서버를 정한다.

시뮬레이션 결과의 ip-hash 줄을 다시 보자. 몫이 22.4 : 24.0 : 53.6이고 p99가 40초다. 요청의 30%를 차지하는 NAT IP 하나가 해시로 C에 떨어졌다. 하필 가장 느린 서버였고, 해시는 그 손님을 다른 서버로 보낼 방법이 없다. 키 하나가 전체 트래픽에서 큰 몫을 차지하면(핫 키) 해시 방식은 고르게 나눌 수 없다. 회사 NAT, 모바일 통신사의 CGNAT, 앞단 프록시 IP를 그대로 해시하면 흔히 생기는 일이다.

해시에는 다른 문제도 있다. 가장 단순한 방법은 `hash(key) % 서버 수`인데, 서버 수가 바뀌면 거의 모든 키의 자리가 바뀐다. 서버 4대일 때 자리를 정한 키 6개가, 한 대가 빠져 3대가 되면 어떻게 되는지 봤다(MD5 앞 4바이트를 해시로 썼다).

일관 해싱(consistent hashing)은 서버와 키를 같은 원(링) 위에 올려놓고, 키에서 시계 방향으로 처음 만나는 서버를 고른다. 서버 하나가 빠지면 그 서버가 맡던 구간의 키만 다음 서버로 넘어간다. 키 1만 개로 비교했다.

```bash
# 키 1만 개, 서버 4대에서 하나를 빼거나 더할 때 자리가 바뀐 키 수
node ch.js
```

```text
10000 keys
hash % N        4대 분포: s1=2468 s2=2447 s3=2479 s4=2606
ring vnode 1    4대 분포: s1=2942 s2=2643 s3=2596 s4=1819
ring vnode 160  4대 분포: s1=2525 s2=2510 s3=2521 s4=2444
s4 제거 → 자리가 바뀐 키
  hash % N      : 7630
  ring vnode 160: 2444
s5 추가 → 자리가 바뀐 키
  hash % N      : 7971
  ring vnode 160: 1800
```

서버 하나를 뺐을 때 `% N`은 7630개를 옮겼고, 링은 빠진 서버가 들고 있던 2444개만 옮겼다. 하나를 더할 때도 `% N`은 7971개, 링은 새 서버가 가져갈 몫인 1800개 정도만 움직였다. 서버 하나당 점 하나만 링에 올리면(vnode 1) 구간 길이가 들쭉날쭉해서 1819부터 2942까지 벌어진다. 서버마다 점을 여러 개(가상 노드) 올려 이걸 고르게 만든다. nginx의 `hash ... consistent`는 ketama 방식으로 weight 1당 160개의 점을 쓴다.

일관 해싱도 핫 키는 못 푼다. 한 키에 몰린 트래픽은 여전히 한 서버로 간다. 그래서 서버마다 받을 수 있는 상한(평균의 1.25배 같은)을 두고, 넘치면 링의 다음 서버로 넘기는 bounded-load 방식이 나왔다. 링의 구조와 가상 노드 수, bounded load는 [일관 해싱 글](/posts/consistent-hashing)에서 자세히 본다. L4 계층에서 여러 로드 밸런서가 같은 연결을 같은 서버로 보내야 할 때는 Google의 Maglev 해싱처럼 고르게 나누면서 서버 변경 때 움직임이 적은 표 방식을 쓴다.

실제 nginx에서 `hash $request_uri consistent`로 URL 500가지를 보냈을 때는 이렇게 나뉘었다. 해시는 부하를 보지 않으니 느린 9003도 다른 서버만큼 받았다.

```text
== alg-hashrequest_uriconsistent
600 req, conc 30: 774ms total, p50 21ms, p99 69ms
    231 up=127.0.0.1:9001
    145 up=127.0.0.1:9002
    224 up=127.0.0.1:9003
```

## 응답 시간을 보는 방법들

연결 수 대신 응답 시간을 직접 보는 방식도 있다. 서버마다 최근 응답 시간의 지수 가중 이동 평균(EWMA)을 들고, 그 값에 처리 중인 요청 수를 곱한 비용이 가장 작은 서버를 고른다. Twitter Finagle과 Linkerd의 peak EWMA가 이 계열이다. NGINX Plus의 `least_time`도 비슷한 생각이다. 느려지기 시작한 서버를 연결 수보다 빨리 알아챈다는 장점이 있다.

다만 응답 시간에는 요청의 종류가 섞인다. 무거운 리포트 API가 몰린 서버는 아프지 않아도 느려 보이고, 앞서 본 것처럼 빨리 실패하는 서버는 가장 빨라 보인다. 그래서 응답 시간 기반 방식도 오류율을 따로 보는 장치와 짝을 이룬다. 대개의 서비스에서는 P2C와 진행 중인 요청 수 조합으로 충분하고, 응답 시간 기반은 서버 성능이 자주 흔들리는 환경(공유 인프라, 원격 리전 섞임)에서 고려한다.

- 요청 비용이 들쭉날쭉하거나 서버가 가끔 느려지면 진행 중인 요청 수를 보는 방식, 로드 밸런서가 여러 대면 그중에서도 P2C를 쓴다.
- 서버에 상태(로컬 캐시, 방, 세션)가 있어 같은 키가 같은 서버로 가야 하면 일관 해싱을 쓰고, 핫 키가 있으면 bounded load를 함께 쓴다.

알고리즘보다 먼저 볼 것도 있다. L4 로드 밸런서는 연결 단위로 나누니, 연결을 오래 쓰는 gRPC나 HTTP/2 클라이언트 앞에서는 어떤 알고리즘을 골라도 처음 붙은 서버로 몰린다([OSI 글](/posts/osi-in-practice)). 쿠버네티스 Service의 기본 kube-proxy(iptables 모드)도 연결이 맺어질 때 확률로 엔드포인트를 하나 고르는 L4 방식이다. 이 경우는 알고리즘을 바꾸는 게 아니라 요청 단위로 나누는 L7 프록시나 클라이언트 쪽 분산으로 바꿔야 한다.

## 분배가 이상할 때 확인하는 순서

"한 서버만 바쁘다"는 말을 들으면 먼저 업스트림별 요청 수와 응답 시간을 나눠 본다. nginx라면 로그 형식에 `$upstream_addr`와 `$upstream_response_time`을 넣어 둬야 이게 가능하다.

```bash
# 업스트림별 요청 수
grep -o 'up=[0-9.:]*' /var/log/nginx/access.log | sort | uniq -c | sort -rn

# 업스트림별 평균 응답 시간 (로그에 'up=주소 ... rt=초'가 있을 때)
awk '{for(i=1;i<=NF;i++){if($i~/^up=/)u=$i; if($i~/^rt=/)r=substr($i,4)}; s[u]+=r; n[u]++} END{for(k in s) printf "%s %.3fs %d\n", k, s[k]/n[k], n[k]}' /var/log/nginx/access.log
```

요청 수는 고른데 한 서버만 응답이 느리면 서버 문제이고 알고리즘을 least request나 P2C로 바꾸면 그 서버가 덜 받게 된다. 요청 수 자체가 한쪽으로 쏠렸다면 고정 장치(`ip_hash`, 세션 쿠키, 해시 키)를 찾는다. 해시를 쓰고 있다면 키별 요청 수를 세서 상위 몇 개가 전체의 몇 %인지 본다. 상위 키 하나가 수십 %면 알고리즘이 아니라 키 선택을 바꿔야 한다.

```bash
# 해시 키(여기선 클라이언트 IP)별 요청 수 상위 5개
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -5
```

설정을 바꿀 때 흔한 실수도 있다. `hash` 지시자에서 `consistent`를 빼먹으면 서버 하나를 추가할 때마다 캐시가 거의 다 빈다. nginx worker가 여러 개인데 upstream에 `zone`이 없으면 least_conn의 연결 수를 worker마다 따로 세서 기대만큼 고르지 않다. 그리고 `backup` 서버는 `hash`, `ip_hash`, `random`과 함께 쓸 수 없어서 설정 검사(`nginx -t`)에서 막힌다.

## 같은 숫자, 다른 부하

라운드 로빈은 요청 수를 맞추고, least request는 바쁨을 맞추며, P2C는 여러 로드 밸런서가 동시에 고를 때도 무리 짓지 않게 하고, 해시는 같은 키를 같은 곳에 둔다. 같은 2만 개 요청에서 p99가 10.8초에서 400ms까지 갈린 건 서버를 더 넣어서가 아니라 나누는 방법을 바꿔서였다. 어느 서버가 아프면 빼는 일은 [로드 밸런서 기본 글](/posts/load-balancer-basics)에서, 해시 링을 직접 짜는 일은 [일관 해싱 글](/posts/consistent-hashing)에서 이어진다.

## 면접에서 나올 만한 질문

### 라운드 로빈의 단점은 무엇인가요?

요청 수를 똑같이 나눌 뿐 서버의 바쁨을 보지 않는다. 서버 사양이 다르거나 요청마다 처리 비용이 크게 다르면 느린 서버 앞에 줄이 쌓인다. 실험에서는 전체 사용률이 80%였는데도 절반 속도 서버의 p99가 10초를 넘었다. 가중치로 비율을 맞출 수는 있지만 사람이 정한 고정값이라 순간적인 변화를 따라가지 못한다.

### least connections는 언제 쓰고, 무엇을 조심하나요?

요청 처리 시간이 들쭉날쭉할 때 쓴다. 진행 중인 요청이 적은 서버를 고르니 느린 서버가 자연스럽게 덜 받는다. 다만 HTTP/2·gRPC처럼 연결 하나에 요청이 여럿이면 연결 수가 아니라 요청 수를 세야 하고, 빨리 실패하는 서버가 가장 한가해 보여 트래픽을 빨아들일 수 있으니 오류 감지와 함께 쓴다. 새로 들어온 서버에 몰리는 것도 slow start로 막는다.

### Power of Two Choices는 왜 잘 동작하나요?

무작위로 두 서버를 뽑아 덜 바쁜 쪽을 고르면, 가장 바쁜 서버는 절대 고르지 않으면서 여러 로드 밸런서가 같은 서버로 동시에 몰리지도 않는다. 이론적으로 최대 부하가 무작위 배정의 log n / log log n 수준에서 log log n 수준으로 떨어진다. 전체를 훑지 않아 비용이 일정하고, 부하 정보가 조금 늦어도 잘 버틴다. Envoy의 LEAST_REQUEST 기본 동작이 이 방식이다.

### 로드 밸런서가 여러 대일 때 least connections가 왜 나빠지나요?

각 로드 밸런서가 서로의 결정을 바로 알지 못하고 같은 시점의 부하 정보를 보기 때문이다. 모두가 같은 "가장 한가한 서버"를 골라 그 서버로 몰리고, 정보가 갱신되면 또 다른 서버로 함께 옮겨 가는 무리 짓기가 생긴다. 실험에서 로드 밸런서 10대에 정보 공유를 200ms로 늦추자 최대 부하가 네 배가 됐다. P2C는 고르는 후보를 무작위로 갈라 이 쏠림을 줄인다.

### IP 해시의 문제는 무엇인가요?

NAT나 프록시 뒤의 많은 사용자가 IP 하나로 보이면 그들이 모두 한 서버로 간다. 실험에서 요청의 30%를 차지하는 IP 하나가 느린 서버에 떨어져 p99가 40초가 됐다. 모바일 사용자는 IP가 바뀌면 다른 서버로 가서 세션을 잃는다. 세션이 목적이라면 공유 저장소로 빼는 게 낫고, 같은 서버가 꼭 필요하면 더 고른 키로 일관 해싱을 쓴다.

### hash % N 대신 일관 해싱을 쓰는 이유는?

서버 수가 바뀔 때 움직이는 키를 최소로 만들기 위해서다. 키 1만 개, 서버 4대에서 한 대를 빼면 % N은 7630개가 자리를 옮겼지만 링은 빠진 서버의 2444개만 옮겼다. 서버마다 캐시가 있다면 % N은 서버 하나를 바꿀 때마다 캐시가 거의 다 빈다. 링의 편차는 가상 노드로 줄이고, 핫 키는 bounded load로 다룬다.

### gRPC 서비스에서 Pod 하나만 CPU가 높습니다. 알고리즘을 바꾸면 해결되나요?

대개는 알고리즘이 아니라 나누는 층의 문제다. gRPC는 HTTP/2 연결 하나를 오래 쓰는데, 쿠버네티스 기본 Service처럼 L4에서 연결 단위로 나누면 처음 붙은 Pod로 모든 요청이 간다. 요청 단위로 나누는 L7 프록시(Envoy, 서비스 메시)나 클라이언트 쪽 로드 밸런싱으로 바꿔야 하고, 그 위에서야 P2C 같은 알고리즘이 의미가 있다.
