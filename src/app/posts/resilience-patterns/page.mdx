## 느린 서비스 하나가 전부를 멈추는 과정

## 기다림에 끝을 정한다: 타임아웃

첫 번째 방어선은 타임아웃이다. 의외로 기본값이 없는 경우가 많다. 자바의 `HttpURLConnection`은 연결과 읽기 타임아웃 기본값이 0이고, 0은 무한히 기다린다는 뜻이다. axios도 `timeout` 기본값이 0이고, 브라우저의 `fetch`에는 타임아웃 옵션 자체가 없다. 아무것도 설정하지 않으면 위 그림 같은 일이 그대로 일어난다.

타임아웃은 두 종류를 구분해서 건다. 연결 타임아웃은 TCP 연결을 맺기까지 기다리는 시간이다. 상대 서버가 살아 있으면 같은 데이터센터 안에서 몇 밀리초면 끝나니 짧게(수백 ms~1초) 잡는다. 이게 오래 걸린다면 서버가 없거나 네트워크가 끊긴 것이다. 읽기(응답) 타임아웃은 연결된 뒤 응답을 기다리는 시간이다. 상대의 처리 시간을 기준으로 정한다.

값은 감으로 정하지 않고 상대 서비스의 지연 분포를 보고 정한다. 평소 p99(가장 느린 1%의 경계)가 120ms라면 읽기 타임아웃은 그보다 조금 넉넉한 300ms쯤이 출발점이다. 평균을 기준으로 잡으면 정상 요청의 꽤 많은 몫이 잘리고, 너무 크게 잡으면 막아 주지 못한다.

여러 단계를 거치는 호출에서는 타임아웃이 서로 맞아야 한다. 브라우저가 3초를 기다리는데 게이트웨이가 상품 서비스를 5초 기다리고, 상품 서비스는 추천을 10초 기다린다면, 브라우저가 포기한 뒤에도 안쪽에서는 아무도 받지 않을 응답을 계속 만들고 있다. 안쪽으로 갈수록 타임아웃이 짧아야 한다. 더 나은 방법은 데드라인 전파다. 맨 바깥에서 "이 요청은 언제까지 끝나야 한다"는 절대 시각을 정하고, 호출마다 남은 시간을 함께 넘긴다. gRPC는 데드라인을 `grpc-timeout` 헤더로 넘기고, 받은 쪽이 같은 컨텍스트로 다음 호출을 하면 남은 시간이 그대로 이어진다. 남은 시간이 이미 0이면 받은 쪽은 일을 시작하지 않고 바로 실패를 돌려준다.

## 다시 보내기: 지수 백오프와 지터

네트워크 오류 중에는 잠깐 생겼다 사라지는 것이 많다. 연결이 끊겼거나, 배포 중인 인스턴스에 걸렸거나, 순간적으로 503을 받은 경우다. 이런 일시적 오류는 한 번 더 보내면 대개 성공한다.

다시 보낼 오류와 아닌 오류는 구분한다. 400(요청이 잘못됨), 401, 403, 404, 409 같은 4xx는 다시 보내도 결과가 같다. 다시 보낼 만한 건 연결 실패, 502·503·504, 그리고 429(너무 많이 보냄)다. 429와 503에 `Retry-After` 헤더가 붙어 있으면 그 시간을 따른다. 타임아웃은 애매하다. 요청이 서버에 닿아 처리됐는데 응답만 늦은 것일 수도 있다. 이 문제는 다음 절의 멱등성과 엮인다.

바로 다시 보내면 안 된다. 상대가 과부하로 느린 상황이라면 즉시 재시도는 부하를 두 배로 만든다. 그래서 기다리는 시간을 늘려 가며 보낸다. 지수 백오프(exponential backoff)는 기다림을 base × 2ⁿ으로 두 배씩 늘리고, 너무 길어지지 않게 상한(cap)으로 자른다. base 100ms, 상한 1초라면 100, 200, 400, 800, 1000ms가 된다.

아래에서 이 계산을 직접 짜 보자. `attempts`번째까지의 대기 시간을 배열로 돌려준다.

<CodePlayground
  caption="상한이 있는 지수 백오프"
  functionName="backoffDelays"
  initialCode={`function backoffDelays(base, cap, attempts) {
  // n번째(0부터) 대기 시간은 base * 2^n, 단 cap을 넘지 않는다
  const delays = [];
  return delays;
}`}
  solution={`function backoffDelays(base, cap, attempts) {
  const delays = [];
  for (let n = 0; n < attempts; n++) {
    delays.push(Math.min(cap, base * 2 ** n));
  }
  return delays;
}`}
  tests={[
    { args: [100, 1000, 5], expected: [100, 200, 400, 800, 1000] },
    { args: [200, 5000, 6], expected: [200, 400, 800, 1600, 3200, 5000] },
    { args: [1000, 30000, 7], expected: [1000, 2000, 4000, 8000, 16000, 30000, 30000], label: "1초 시작, 30초 상한" },
    { args: [500, 500, 3], expected: [500, 500, 500], label: "base가 곧 상한" },
    { args: [100, 10000, 0], expected: [], label: "재시도 없음" },
  ]}
/>

세 번째 테스트의 숫자는 TanStack Query가 쿼리 재시도에 쓰는 기본 대기 시간(`Math.min(1000 * 2 ** n, 30000)`)과 같다.

이 계산은 결정적이라 문제가 하나 있다. 서버가 잠깐 멈춘 순간 실패한 클라이언트 1000개가 모두 정확히 100ms 뒤에, 다시 200ms 뒤에 한꺼번에 몰려온다. 백오프가 부하를 흩어 주지 못하고 파도처럼 묶어서 보낸다. 그래서 무작위성을 섞는다. 이걸 지터(jitter)라고 한다. AWS 아키텍처 블로그의 "Exponential Backoff And Jitter" 글은 몇 가지 방식을 비교했는데, 대기 시간을 0부터 계산값 사이에서 고르게 뽑는 full jitter(`random(0, min(cap, base * 2 ** n))`)가 단순하면서도 전체 호출 수와 완료 시간이 모두 좋게 나왔다. 위 함수에서 `Math.min(...)` 결과에 `Math.random()`을 곱하면 된다.

재시도는 곱해진다는 것도 기억해야 한다. 브라우저, 게이트웨이, 상품 서비스가 각자 3번씩 시도하면, 맨 아래 추천 서비스는 요청 하나에 최대 3 × 3 × 3 = 27번 불린다. 이미 힘든 서비스에 27배의 부하가 쏟아진다. 그래서 재시도는 한 계층에서만 하는 게 원칙이고, 보통 호출 사슬의 가장 바깥이나 실패한 호출 바로 위 한 곳이다. 여기에 재시도 예산을 더한다. Google SRE 책은 요청 하나당 재시도 횟수 제한과 함께, 클라이언트 전체에서 재시도가 원래 요청의 10%를 넘지 않게 하는 예산을 권한다. 평소에는 재시도가 몇 건 안 되니 예산이 남고, 상대가 크게 망가져서 실패가 쏟아지면 예산이 바닥나 재시도가 자동으로 멈춘다. 계층마다 걸린 타임아웃은 [타임아웃](/posts/timeouts)에서, 재시도 증폭과 예산을 직접 잰 결과는 [재시도](/posts/retries)에서, 지터 방식 비교는 [지수 백오프와 지터](/posts/exponential-backoff-jitter)에서 더 깊게 다룬다.

## 두 번 보내도 한 번만 처리되게

결제 요청을 보냈는데 타임아웃이 났다. 결제가 됐을까. 요청이 서버에 닿기 전에 끊겼을 수도 있고, 결제는 됐는데 응답만 못 받았을 수도 있다. 여기서 다시 보내면 두 번 결제될 수 있다.

HTTP 메서드 중 GET, PUT, DELETE는 멱등하게 정의돼 있다. 같은 요청을 여러 번 보내도 결과 상태가 한 번 보낸 것과 같다는 뜻이다. "3번 주문의 주소를 X로 바꿔라"(PUT)는 몇 번 해도 결과가 X다. POST는 그렇지 않다. "주문을 만들어라"는 보낼 때마다 새 주문이 생긴다.

<Callout kind="warning" title="POST에 자동 재시도를 걸지 않는다">
HTTP 클라이언트나 쿼리 라이브러리의 재시도 옵션을 전역으로 켜 두면 결제·주문 생성 같은 POST까지 다시 보낼 수 있다. 자동 재시도는 GET 같은 멱등한 요청에만 걸고, POST를 재시도해야 한다면 아래의 멱등성 키를 먼저 갖춘다.
</Callout>

POST를 안전하게 재시도하려면 멱등성 키(idempotency key)를 쓴다. 클라이언트가 작업마다 고유한 키(UUID)를 만들어 `Idempotency-Key` 헤더에 싣고, 재시도할 때도 같은 키를 보낸다. 서버는 처음 보는 키면 작업을 하고 결과를 키와 함께 저장한다. 이미 본 키면 작업을 다시 하지 않고 저장해 둔 응답을 그대로 돌려준다. Stripe의 결제 API가 이 방식으로 유명하고, IETF에서도 이 헤더를 표준으로 만드는 초안이 진행 중이다.

구현할 때 빠지기 쉬운 곳이 몇 군데 있다. 키 저장과 실제 작업(주문 생성)은 같은 트랜잭션으로 묶어야 한다. 따로 하면 그 사이에 죽었을 때 다시 어긋난다. 같은 키로 요청 두 개가 동시에 들어오면, 하나가 처리 중일 때 다른 하나는 기다리게 하거나 409로 거절한다. 같은 키인데 본문이 다르면 클라이언트의 버그이니 에러로 돌려준다. 키는 영원히 보관하지 않고 기한을 둔다. Stripe는 24시간이 지난 키를 지울 수 있다고 밝히고 있다.

키를 언제 만드는지도 중요하다. 버튼을 누를 때마다 새로 만들면 사용자가 두 번 누른 것을 막지 못한다. 주문서 화면이 열릴 때 한 번 만들어 두고, 그 화면에서의 모든 재시도와 중복 클릭에 같은 키를 쓴다. 동시에 온 중복과 처리 도중 죽은 서버까지 다루는 저장소 구현은 [멱등성 키 구현](/posts/idempotency-key)에 따로 적었다.

## 회로를 끊어 두는 서킷 브레이커

타임아웃과 재시도만 있으면 추천 서비스가 완전히 망가졌을 때도 모든 요청이 300ms씩 기다린 뒤 실패한다. 실패할 게 뻔한 호출에 매번 시간과 스레드를 쓰는 셈이고, 회복하려는 추천 서비스에도 계속 요청이 들어간다.

서킷 브레이커는 집의 누전 차단기처럼 동작한다. 실패가 일정 비율을 넘으면 호출 자체를 끊고, 한동안은 상대를 부르지 않고 즉시 실패를 돌려준다. 상태는 세 가지다.

닫힘(closed)은 정상 상태다. 호출을 그대로 보내면서 최근 결과를 센다. 실패가 기준을 넘으면 열림으로 간다. 열림(open)에서는 호출을 보내지 않고 바로 실패(또는 폴백)를 돌려준다. 몇 밀리초 안에 끝나니 스레드를 잡아먹지 않는다. 정해진 시간이 지나면 반열림(half-open)으로 간다. 반열림에서는 시험 요청을 몇 개만 보내 본다. 성공하면 닫힘으로 돌아가고, 실패하면 다시 열림으로 가서 대기 시간을 처음부터 센다.

## 칸막이로 피해를 가두기

처음 장면을 다시 보자. 추천 호출이 막혀서 상품 서비스의 스레드 200개가 전부 묶였다. 추천만 막혔는데 재고 조회까지 못 한 이유는 모든 호출이 같은 풀을 썼기 때문이다.

벌크헤드(bulkhead)는 배의 격벽에서 온 이름이다. 선체를 여러 칸으로 나눠 두면 한 칸에 물이 차도 배가 가라앉지 않는다. 의존성마다 쓸 수 있는 자원의 몫을 따로 정하는 것이다. 추천 호출은 동시에 20개까지, 재고 호출은 40개까지로 묶어 두면 추천이 막혀도 묶이는 스레드는 20개다. 나머지 180개로 상품 정보와 재고를 계속 처리한다. 21번째 추천 호출은 기다리지 않고 바로 거절되고, 이건 폴백으로 넘어간다.

방식은 두 가지다. 의존성마다 별도 스레드 풀을 두면 호출하는 스레드와 실제 호출을 하는 스레드가 분리돼서, 호출이 멈춰도 호출한 쪽 스레드는 타임아웃 뒤 빠져나올 수 있다. 대신 스레드 전환 비용이 든다. 세마포어 방식은 같은 스레드에서 실행하되 동시 실행 수만 센다. 가볍지만 호출 자체가 멈추면 그 스레드도 같이 멈추니 타임아웃이 꼭 함께 있어야 한다. 비동기 I/O(WebFlux, Node.js)에서는 스레드 대신 동시 요청 수와 커넥션 풀을 의존성별로 나눈다. HTTP 클라이언트의 커넥션 풀을 서비스마다 따로 만드는 것도 같은 생각이다.

크게 보면 인스턴스나 클러스터를 나누는 것도 벌크헤드다. 무거운 관리자 배치 작업과 사용자 요청을 같은 인스턴스에서 받지 않고 배포를 나누는 식이다.

## 안 되면 덜 보여 주기

차단하거나 거절한 다음에는 사용자에게 무엇을 보여 줄지 정해야 한다. 이게 폴백(fallback)이다. 추천이 안 되면 캐시해 둔 인기 상품을, 리뷰 수 집계가 안 되면 숫자 없이 "리뷰 보기" 링크만, 개인화 배너가 안 되면 기본 배너를 보여 준다. 페이지 전체를 에러로 만드는 대신 일부 기능만 줄여서 핵심 흐름을 살린다. 이걸 우아한 기능 축소(graceful degradation)라고 한다.

폴백에도 지켜야 할 게 있다. 폴백은 원래 경로보다 단순하고 싸야 한다. 추천 서비스가 DB 때문에 느린데 폴백이 같은 DB에 다른 쿼리를 던진다면 폴백도 같이 죽는다. 미리 만들어 둔 정적 값, 로컬 캐시, 조금 오래된 데이터가 좋은 폴백이다. 그리고 모든 기능에 폴백이 있는 건 아니다. 결제 승인이 안 됐는데 "아마 됐을 것"으로 처리하면 안 된다. 이런 곳은 빠르고 분명하게 실패시키고, 사용자에게 다시 시도하라고 알리는 게 맞다.

폴백이 일어났다는 사실은 꼭 남긴다. 폴백이 너무 잘 동작하면 아무도 장애를 모른 채 며칠이 지난다. 폴백 횟수를 지표로 남기고 알림을 건다.

## 들어오는 양 자체를 줄이기

지금까지는 내가 부르는 쪽을 다뤘다. 반대로 나에게 들어오는 요청이 감당할 수 있는 양을 넘으면, 다 받아서 다 느려지는 것보다 일부를 빨리 거절하는 편이 낫다.

요청 수 제한(rate limiting)은 사용자나 API 키마다 정해진 속도를 넘는 요청을 429로 거절한다. 토큰 버킷이 흔한 구현이다. 통에 초당 일정한 속도로 토큰이 채워지고, 요청 하나가 토큰 하나를 쓰며, 통이 비면 거절한다. 통의 크기만큼은 순간적으로 몰려도 받아 준다. 공정성을 위한 장치라서, 한 사용자가 폭주해도 다른 사용자가 피해를 보지 않게 한다. 게이트웨이에서 하는 경우가 많고, 여러 대에서 정확히 세는 문제는 [게이트웨이 글](/posts/gateway)에 적었다.

부하 차단(load shedding)은 사용자와 상관없이 서버 자신의 상태를 보고 거절한다. 처리 중인 요청 수가 한계를 넘거나, 대기열에서 기다린 시간이 길어지면 새 요청을 바로 503으로 돌려준다. 대기열에서 이미 2초를 기다린 요청은 클라이언트가 포기했을 가능성이 크니, 처리하지 않고 버리는 게 자원을 아낀다. 이때 모든 요청을 똑같이 버리지 않고 우선순위를 둔다. 결제와 로그인은 살리고, 추천과 통계 수집 같은 요청부터 버린다.

거절할 때는 `Retry-After`를 붙여 클라이언트가 언제 다시 와야 하는지 알려 준다. 클라이언트의 지터 섞인 백오프와 서버의 빠른 거절이 함께 있어야 과부하에서 빠져나올 수 있다.

## 프런트엔드에서 본 장애 대응

브라우저도 호출 사슬의 맨 바깥 고리다. 같은 원칙이 그대로 적용된다.

먼저 타임아웃이다. `fetch`에는 타임아웃 옵션이 없으니 `AbortSignal`로 건다.

```ts
async function getRecommendations(itemId: string) {
  const res = await fetch(`/api/recs?item=${itemId}`, {
    signal: AbortSignal.timeout(2000),
  });
  // fetch는 4xx·5xx에서 reject하지 않는다. 상태 코드를 직접 확인한다
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}
```

시간이 지나면 `TimeoutError`라는 이름의 DOMException으로 reject되고, 사용자가 화면을 떠나 직접 취소했을 때는 `AbortError`가 난다. 둘을 구분하면 "느려서 실패"와 "필요 없어져서 취소"를 다르게 다룰 수 있다. 컴포넌트가 사라질 때의 취소와 타임아웃을 함께 걸려면 `AbortSignal.any([controller.signal, AbortSignal.timeout(2000)])`로 합친다. `AbortSignal.any`는 2023~2024년에야 주요 브라우저에 들어온 기능이라, 오래된 브라우저를 지원해야 한다면 지원 범위를 확인한다.

재시도는 멱등한 요청에만 자동으로 건다. TanStack Query는 브라우저에서 쿼리를 기본 3번 재시도하고, 뮤테이션은 기본적으로 재시도하지 않는다. 이 기본값이 앞에서 본 원칙과 맞는다. 쿼리 쪽도 `retry`에 함수를 넘겨 4xx에서는 재시도하지 않게 해 두면 404에 세 번씩 헛걸음하지 않는다. 서버나 게이트웨이도 재시도를 한다면 브라우저 쪽 재시도 횟수를 줄여서 곱셈을 피한다.

주문처럼 POST를 다시 보내야 하는 화면은 앞에서 말한 대로 화면이 열릴 때 `crypto.randomUUID()`로 멱등성 키를 만들어 두고, 버튼은 요청이 끝날 때까지 비활성화한다.

마지막은 화면 설계다. 페이지를 영역별로 나눠서, 부가 영역의 실패가 페이지 전체를 깨지 않게 한다. React라면 추천 영역만 감싸는 에러 바운더리를 두고, 실패하면 그 자리에 작은 안내와 다시 시도 버튼만 보여 준다. 서버가 위 그림처럼 `degraded` 표시를 보내면 그 영역을 숨기거나 "지금은 추천을 불러올 수 없다" 정도로 처리한다. 이미 받아 둔 데이터가 있다면 지우지 않고 그대로 보여 주며 "마지막 업데이트: 3분 전"처럼 시점을 함께 적는 것도 방법이다. 결제처럼 실패하면 안 되는 흐름이 추천 같은 부가 요청의 결과를 기다리느라 막히지 않게, 요청을 서로 독립적으로 보내는 것도 같은 생각에서 나온다.

## 실패를 예상하고 짜는 코드

느린 의존성 하나가 스레드를 붙잡으며 위로 번지는 게 연쇄 장애다. 타임아웃으로 기다림에 끝을 정하고, 일시적 오류만 지터 섞인 백오프로 한 계층에서 다시 보내고, POST는 멱등성 키를 갖춘 뒤에만 재시도한다. 실패가 계속되면 서킷 브레이커가 호출을 끊어 상대가 회복할 시간을 주고, 벌크헤드가 피해를 한 칸에 가두며, 폴백이 사용자에게 줄어든 화면이라도 보여 준다. 들어오는 쪽에서는 요청 수 제한과 부하 차단으로 감당할 수 있는 만큼만 받는다.

## 면접에서 나올 만한 질문

### 연쇄 장애는 왜 생기나요?

한 의존성이 느려지면 그걸 부르는 쪽의 스레드와 커넥션이 응답을 기다리며 묶이고, 풀이 바닥나면 관계없는 요청까지 처리하지 못한다. 그러면 그 서비스를 부르는 쪽이 다시 같은 식으로 막히면서 위로 번진다. 죽은 서비스보다 느린 서비스가 자원을 오래 붙잡아서 더 위험하다. 타임아웃, 벌크헤드, 서킷 브레이커가 이 번짐을 끊는 장치다.

### 타임아웃 값은 어떻게 정하나요?

상대 서비스의 지연 분포, 보통 p99에 여유를 더해 정한다. 연결 타임아웃은 짧게, 읽기 타임아웃은 처리 시간 기준으로 따로 둔다. 여러 단계를 거치면 안쪽으로 갈수록 짧아야 하고, 더 나은 방법은 데드라인을 전파해서 남은 시간만큼만 기다리게 하는 것이다. 기본값이 무한대인 클라이언트가 많아 꼭 직접 설정해야 한다.

### 재시도할 때 주의할 점은요?

일시적 오류(연결 실패, 502·503·504, 429)만 재시도하고 4xx는 하지 않는다. 지수 백오프에 지터를 섞어서 실패한 클라이언트들이 한꺼번에 몰려오지 않게 한다. 계층마다 재시도하면 횟수가 곱해지니 한 계층에서만 하고, 재시도 예산으로 전체 재시도 비율을 제한한다. 멱등하지 않은 요청은 멱등성 키 없이는 재시도하지 않는다.

### 지터는 왜 필요한가요?

같은 순간에 실패한 클라이언트들이 결정적인 백오프를 쓰면 모두 같은 시각에 다시 몰려와 부하가 파도처럼 반복된다. 대기 시간에 무작위성을 섞으면 재시도가 시간축에 흩어져서 서버가 회복할 여유가 생긴다. 0부터 계산된 백오프 값 사이에서 고르게 뽑는 full jitter가 흔히 쓰인다.

### 결제 요청이 타임아웃 났을 때 다시 보내도 되나요?

그냥 다시 보내면 안 된다. 서버가 이미 처리하고 응답만 못 보냈을 수 있어서 이중 결제가 될 수 있다. 클라이언트가 작업마다 멱등성 키를 만들어 같은 키로 재시도하고, 서버는 키와 결과를 작업과 같은 트랜잭션에 저장해 두었다가 같은 키가 오면 저장된 응답을 돌려준다. 키는 버튼 클릭이 아니라 주문 화면 단위로 만들어 중복 클릭도 막는다.

### 서킷 브레이커의 상태를 설명해 주세요.

닫힘에서는 호출을 보내며 최근 결과를 세고, 실패율이나 느린 호출 비율이 기준을 넘으면 열림이 된다. 열림에서는 호출하지 않고 즉시 실패나 폴백을 돌려줘서 자원을 아끼고 상대에게 회복할 시간을 준다. 대기 시간이 지나면 반열림이 되어 시험 요청을 몇 개 보내고, 성공하면 닫힘, 실패하면 다시 열림으로 간다. 최소 호출 수를 너무 작게 두거나 4xx를 실패로 세면 엉뚱하게 열리니 주의한다.

### 벌크헤드는 서킷 브레이커와 무엇이 다른가요?

서킷 브레이커는 실패가 계속되는 의존성 호출을 시간 단위로 끊는 장치이고, 벌크헤드는 의존성마다 쓸 수 있는 스레드나 동시 호출 수의 몫을 미리 나눠 두는 장치다. 브레이커가 열리기 전까지 쌓이는 느린 호출도 벌크헤드가 있으면 정해진 칸 안에서만 자원을 쓴다. 그래서 둘을 함께 쓴다.

### 프런트엔드에서는 무엇을 하나요?

fetch에 `AbortSignal.timeout`으로 타임아웃을 걸고, 자동 재시도는 GET 같은 멱등한 요청에만 건다. POST는 멱등성 키와 버튼 비활성화로 중복을 막는다. 화면은 영역별 에러 바운더리로 나눠 부가 기능이 실패해도 핵심 흐름은 보이게 하고, 이미 받은 데이터는 시점을 표시해 계속 보여 주는 식으로 기능을 줄여서 버틴다.
