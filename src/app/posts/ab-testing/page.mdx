새 결제 화면을 배포했다. 다음 주 구매 전환율이 4.8%에서 5.3%로 올랐다. 새 화면 덕분이라고 말하고 싶은데, 그 주에 마침 카드사 할인 행사가 있었다. 날씨가 추워져서 겨울 옷 주문이 늘었을 수도 있다. 숫자는 올랐지만 무엇 때문에 올랐는지는 알 수 없다.

A/B 테스트는 이 질문에 답하려고 쓰는 방법이다. 그리고 A/B 테스트를 웹에서 실제로 돌리려면 피처 플래그라는 장치가 거의 반드시 따라온다. 이 글은 두 개를 같이 다룬다. 사용자를 어떻게 나누는지, 무엇을 어떻게 세는지, 결과를 언제 믿어도 되는지, 그리고 실험을 자주 돌려도 코드가 엉망이 되지 않으려면 화면을 어떻게 만들어야 하는지까지.

## 지난주와 비교하면 안 되는 이유

지난주와 이번 주를 비교하면 그 사이에 바뀐 모든 것이 결과에 섞인다. 할인 행사, 계절, 광고 예산, 경쟁사 이벤트. 이걸 다 걸러 낼 방법이 없다.

A/B 테스트는 같은 기간에 사용자를 무작위로 두 무리로 나눠서, 한쪽(A, 대조군)에는 기존 화면을, 다른 쪽(B, 실험군)에는 새 화면을 보여 준다. 두 무리는 같은 날 같은 할인 행사를 겪는다. 무작위로 나눴으니 성향도 평균적으로 비슷하다. 그러면 두 무리 사이에 남는 차이는 화면 하나뿐이라서, 결과 차이를 화면 탓으로 돌릴 수 있다. 원인과 결과를 가려낼 수 있는 거의 유일한 방법이 이렇게 동시에, 무작위로 나누는 것이다.

말로는 간단한데 실제로 하려면 문제가 여럿 생긴다. 같은 사람이 새로고침할 때마다 다른 화면을 보면 안 되고, 화면이 깜빡이면 안 되고, 실제로 화면을 본 사람만 세야 하고, 표본이 충분해야 하고, 중간에 결과를 들여다보는 유혹을 참아야 한다. 하나씩 보자.

## 배포와 공개를 떼어 놓는 스위치

피처 플래그(feature flag)는 코드 안에 넣어 두는 스위치다. 새 코드를 배포하되, 누구에게 켤지는 배포가 아니라 설정으로 정한다.

```ts
if (flags.isOn("new-checkout", user)) {
  return <NewCheckout />;
}
return <Checkout />;
```

이렇게 하면 배포(deploy)와 공개(release)가 분리된다. 코드는 화요일에 나가 있고, 사용자에게 보여 주는 건 목요일에 설정으로 켠다. 문제가 생기면 다시 배포하지 않고 끈다. 모든 사람에게 같은 설정이 적용되는 게 아니라 "직원에게만", "10%에게만", "한국 사용자에게만"처럼 대상을 고를 수 있다. 환경 변수와 다른 부분이 여기다.

플래그는 용도에 따라 수명과 관리 방식이 다르다. Pete Hodgson이 정리한 분류가 널리 쓰인다.

릴리스 플래그는 아직 덜 만든 기능을 숨겨 두거나 조금씩 켜 나가는 데 쓴다. 다 켜지면 지워야 하는 단기 플래그다. 실험 플래그는 A/B 테스트용이다. 사용자를 일관되게 나누고 노출을 기록해야 하며, 실험이 끝나면 이긴 쪽만 남기고 지운다. 운영 플래그는 장애 때 무거운 기능을 끄는 킬 스위치(kill switch)다. 추천 영역이 API를 너무 많이 불러 서버가 버거우면 그 영역만 끈다. 이건 오래 남는다. 권한 플래그는 유료 회원이나 베타 테스터에게만 기능을 여는 데 쓰고, 사실상 제품 기능의 일부라서 가장 오래 산다.

## 같은 사람에게는 항상 같은 쪽을

무작위로 나눈다고 해서 요청이 올 때마다 `Math.random()`을 굴리면 안 된다. 새로고침할 때마다 A와 B를 오가게 되고, 그런 사람의 행동은 어느 쪽 결과로도 셀 수 없다. 배정은 고정(sticky)돼야 한다.

배정 결과를 DB에 저장해 둘 수도 있지만, 요청마다 조회해야 하고 여러 서버와 엣지에서 같은 값을 보려면 저장소를 공유해야 한다. 그래서 흔히 해시를 쓴다. 실험 이름과 사용자 id를 이어 붙인 문자열을 해시 함수에 넣고, 나온 숫자를 100으로 나눈 나머지를 버킷 번호로 쓴다. 해시는 같은 입력에 항상 같은 값을 내니 저장할 필요가 없고, 어느 서버에서 계산해도 같다. 좋은 해시라면 결과가 고르게 퍼지므로 0~99 버킷에 사람이 비슷하게 나뉜다.

## 직접 버킷을 계산해 보기

FNV-1a는 구현이 몇 줄밖에 안 되는 단순한 해시다. 시작값 `0x811c9dc5`에서 출발해 글자 하나마다 XOR하고 `0x01000193`을 곱하는 걸 반복한다. 자바스크립트에서 32비트 곱셈은 `Math.imul`로 하고, 결과를 부호 없는 정수로 바꾸려고 `>>> 0`을 붙인다. 이 함수를 채워서 테스트를 통과시켜 보자.

<CodePlayground
  caption="실험 이름과 사용자 id로 버킷(0~99) 정하기"
  functionName="getBucket"
  initialCode={`function getBucket(experimentKey, userId) {
  // 1. "실험이름:사용자id" 문자열을 만든다
  // 2. FNV-1a 32비트 해시: 시작값 0x811c9dc5
  //    글자마다 hash ^= 글자 코드, hash = Math.imul(hash, 0x01000193) >>> 0
  // 3. 100으로 나눈 나머지를 돌려준다
  return 0;
}`}
  solution={`function getBucket(experimentKey, userId) {
  const key = experimentKey + ":" + userId;
  let hash = 0x811c9dc5;
  for (let i = 0; i < key.length; i++) {
    hash ^= key.charCodeAt(i);
    hash = Math.imul(hash, 0x01000193) >>> 0;
  }
  return hash % 100;
}`}

마지막 테스트가 흔한 실수를 보여 준다. 서버는 id를 소문자로 바꿔서 해시하고 클라이언트는 그대로 해시하면, 같은 사람이 서버에서는 B(63), 화면에서는 A(47)로 나온다. 해시 재료는 한 곳에서 정규화하고, 가능하면 배정 계산도 한 곳(서버나 엣지)에서만 한다.

FNV-1a는 설명용으로 좋지만 비슷한 입력에서 결과가 고르게 섞이는 성질이 아주 강하지는 않다. 실무 실험 도구들은 MurmurHash3 같은 해시를 쓰거나, 버킷을 100개가 아니라 1,000~10,000개로 잘게 나눠서 1% 미만의 비율도 표현한다. 그리고 `charCodeAt`은 UTF-16 코드 단위를 돌려주니, 서버와 클라이언트가 다른 언어로 같은 해시를 계산한다면 바이트 인코딩까지 맞춰야 한다.

## 어디서 나누느냐에 따라 화면이 깜빡인다

배정을 어디서 계산하느냐에 따라 사용자가 보는 화면이 달라진다.

클라이언트에서 나누면 구현이 쉽다. 페이지가 뜬 다음 브라우저 SDK가 플래그 설정을 받아 오고, 배정을 계산하고, B라면 화면을 바꾼다. 문제는 그 사이에 이미 A가 한 번 그려졌다는 것이다. 사용자는 기존 버튼이 보였다가 새 버튼으로 바뀌는 깜빡임(flicker)을 본다. 이건 보기 싫은 것을 넘어서 실험을 망친다. B 사용자는 "A를 잠깐 보고 B로 바뀌는 화면"을 경험한 거라서, 측정 대상이 처음 설계한 B가 아니게 된다.

깜빡임을 숨기려고 배정이 끝날 때까지 페이지 전체를 투명하게 가려 두는 스크립트(anti-flicker snippet)를 쓰기도 한다. 깜빡임은 사라지지만 모든 사용자의 첫 화면이 그만큼 늦어진다. LCP 같은 로딩 지표가 실험 대상이 아닌 사람까지 나빠지는 셈이다.

서버나 엣지에서 나누면 이 문제가 없다. HTML을 만들기 전에 배정이 끝나니 처음부터 B 화면이 내려간다. Next.js라면 미들웨어에서 쿠키의 id로 버킷을 계산하고, 결과에 맞는 경로로 rewrite하거나 서버 컴포넌트에 변형 값을 넘기는 식이다. 대신 조심할 게 하나 생긴다. 사람마다 다른 HTML이 나가니까 CDN이 첫 번째 응답을 캐시해서 모두에게 주면 실험이 무너진다. 응답을 `Cache-Control: private`로 두거나, 변형별로 캐시 키를 나눠야 한다.

## 보여 준 사람만 센다

배정을 받았다고 해서 그 사람이 실제로 새 화면을 본 건 아니다. 결제 화면 실험이라면, 메인 페이지에서 배정만 받고 결제 화면까지 오지 않은 사람이 대부분이다. 이 사람들까지 분석에 넣으면 두 무리 모두 "결제 화면을 안 봐서 구매 안 함"인 사람으로 채워지고, 실제 차이가 희석돼서 잘 보이지 않는다.

## 무엇이 나아져야 이긴 건가

실험을 시작하기 전에 판정 기준을 먼저 적는다. 끝나고 나서 지표 수십 개를 뒤지면 우연히 좋아진 지표 하나쯤은 항상 나온다.

주 지표(primary metric)는 이 실험으로 움직이고 싶은 숫자 하나다. 결제 화면 실험이면 노출된 사람 중 구매한 비율이다. 가드레일 지표(guardrail metric)는 좋아지길 바라는 건 아니지만 나빠지면 안 되는 숫자다. 페이지 로딩 시간, 에러 비율, 환불률, 고객 문의 수 같은 것이다. 주 지표가 올랐어도 가드레일이 크게 나빠졌으면 이긴 게 아니다. 버튼을 더 눈에 띄게 바꿔서 구매가 늘었는데 실수로 누른 사람의 취소가 같이 늘었다면, 실제로는 손해일 수 있다.

## 몇 명이 필요한가

두 무리의 전환율이 4.8%와 5.0%로 나왔다. 이 0.2%p가 화면 때문인지, 우연히 그렇게 나뉜 건지 판단해야 한다. 이때 쓰는 숫자가 p값이다.

p값은 "두 화면에 실제로 차이가 없다고 가정했을 때, 이만큼 이상의 차이가 우연히 나올 확률"이다. 이 값이 미리 정한 기준(보통 0.05)보다 작으면, 우연이라고 보기에는 드문 일이라서 차이가 있다고 판단한다. 흔히 오해하는 것과 달리 p값이 0.03이라고 "B가 더 나을 확률이 97%"라는 뜻은 아니다.

기준 0.05는 차이가 없는데도 있다고 잘못 판단하는 비율(1종 오류, 거짓 양성)을 5%로 묶는다는 뜻이다. 반대 방향의 실수도 있다. 실제로 차이가 있는데 표본이 적어서 못 알아채는 것이다. 차이가 있을 때 그걸 잡아낼 확률을 검정력(power)이라고 하고, 보통 80%로 잡는다.

표본 크기는 이 두 기준과 "얼마나 작은 차이까지 잡고 싶은지"로 정해진다. 기존 전환율이 5%이고 5.5%로 오르는 차이(상대적으로 10%)를 기준 0.05, 검정력 80%로 잡으려면, 두 비율을 비교하는 공식으로 계산했을 때 한 무리에 약 31,200명이 필요하다. 어림 공식 `16 × p(1−p) / δ²`(p는 기존 전환율, δ는 잡고 싶은 차이)로 계산하면 16 × 0.05 × 0.95 / 0.005² = 30,400명으로 비슷하다. 잡고 싶은 차이를 절반으로 줄이면 필요한 사람은 네 배가 된다. 작은 개선을 확인하려면 생각보다 훨씬 많은 트래픽이 필요하다는 뜻이다. 트래픽이 적은 서비스라면 작은 문구 실험보다 효과가 클 만한 변경을 실험하는 편이 현실적이다.

## 중간에 들여다보면 거짓 승리가 늘어난다

실험을 켜 두면 매일 대시보드를 열어 보게 된다. 그러다 사흘째에 p값이 0.04로 떨어지면 "이겼다"고 멈추고 싶어진다. 이걸 엿보기(peeking)라고 하고, 가장 흔하면서 가장 결과를 망치는 실수다.

p값은 실험 동안 오르락내리락한다. 차이가 없는 실험이라도 중간 어딘가에서 잠깐 0.05 아래로 내려가는 일은 꽤 자주 생긴다. 0.05 기준은 "정해 둔 표본을 다 모은 뒤 한 번만 본다"는 전제에서 5%다. 차이가 없는 두 무리를 놓고 다섯 번 나눠서 보다가 한 번이라도 0.05 아래면 멈추는 모의실험을 돌려 보면, 거짓 양성이 5%가 아니라 14% 안팎으로 올라간다. 열 번 보면 20% 가까이 된다.

해결책은 두 가지다. 표본 크기와 종료일을 실험 전에 정하고 그때까지 판정하지 않는다. 대시보드를 보는 건 괜찮지만, 보는 목적은 버그와 가드레일 확인이다. 아니면 처음부터 여러 번 보는 걸 전제로 만든 순차 검정(sequential testing)을 쓴다. 중간에 볼 때마다 더 엄격한 기준을 적용해서 전체 거짓 양성을 5%로 유지하는 방식이고, 상용 실험 도구 다수가 이 방식을 지원한다.

## 처음에만 반짝하는 효과

새 화면은 새롭다는 이유만으로 한동안 더 눌린다. 자주 오는 사용자일수록 바뀐 걸 알아채고 한 번씩 눌러 본다. 이걸 새로움 효과(novelty effect)라고 한다. 반대로 익숙한 화면이 바뀌어서 처음 며칠은 오히려 불편해하다가 적응하면서 나아지는 경우도 있다(primacy effect).

둘 다 짧게 돌린 실험의 결과를 왜곡한다. 최소 1~2주처럼 요일 주기가 온전히 들어가게 돌리고, 날짜별 효과 크기가 시간에 따라 줄어드는지 본다. 처음 방문한 사용자와 기존 사용자를 나눠서 보는 것도 방법이다. 처음 온 사람에게는 무엇이 새로운지 알 수 없으니 새로움 효과가 없다.

## 반반으로 나눴는데 반반이 아니다

50:50으로 나눴는데 노출된 사람이 A 50,000명, B 48,500명이 나왔다. 1,500명 차이는 작아 보인다. 하지만 정말 50:50으로 나눴다면 이 정도로 벌어질 확률은 거의 없다. 카이제곱 검정으로 계산하면 기대값은 각각 49,250명이고, 통계량은 2 × 750² / 49,250 ≈ 22.8, p값은 약 0.000002다.

이걸 표본 비율 불일치, SRM(Sample Ratio Mismatch)이라고 한다. SRM이 나오면 효과를 해석하지 않는다. 두 무리가 무작위로 나뉘었다는 전제가 깨진 것이라서, 전환율 차이가 화면 때문인지 빠진 사람들 때문인지 알 수 없다. 많은 실험 도구가 p값 0.001 아래를 SRM 경고 기준으로 쓴다.

원인은 대개 배정이 아니라 기록 쪽에 있다. B 화면이 무거워서 노출 이벤트를 보내기 전에 이탈한 사람이 많거나, B로 리다이렉트하는 과정에서 일부가 떨어져 나가거나, CDN 캐시가 일부 사용자에게 A를 보내거나, 봇이 한쪽에만 몰리는 경우다. 앞에서 본 대소문자 정규화 실수도 SRM을 만든다.

## 실험이 싸지려면 화면이 설정을 받아야 한다

실험을 한 해에 몇 번 하는 게 아니라 한 주에 여러 개씩 돌리려면, 변형 하나를 만드는 비용이 낮아야 한다. 매번 `if (variant === "B")`를 컴포넌트 깊숙이 흩뿌리면 실험 하나가 끝날 때마다 그걸 다 찾아 지워야 하고, 실험이 겹치면 분기가 곱으로 늘어난다.

변형을 코드 분기가 아니라 데이터로 표현하면 이 비용이 크게 줄어든다. 컴포넌트는 설정 객체를 받아서 그리기만 하고, 플래그는 화면 최상단 한 곳에서만 읽는다.

```tsx
// 변형은 데이터다
const CHECKOUT_VARIANTS = {
  A: { cta: "구매하기", layout: "single", showTrustBadge: false },
  B: { cta: "바로 결제", layout: "split", showTrustBadge: true },
} satisfies Record<string, CheckoutConfig>;

// 플래그는 한 곳에서만 읽는다
function CheckoutPage() {
  const variant = useExperiment("new-checkout"); // "A" | "B"
  return <Checkout config={CHECKOUT_VARIANTS[variant]} />;
}
```

## 끝난 플래그는 빚이 된다

플래그는 넣기는 쉽고 지우기는 어렵다. 실험이 끝나도 "일단 100%로 켜 두고 나중에 지우자"가 반복되면, 코드에 아무도 무슨 역할인지 모르는 분기가 쌓인다. 분기가 n개면 이론상 가능한 조합은 2ⁿ개이고, 그 대부분은 아무도 테스트하지 않는다.

이게 실제로 사고가 된 유명한 사례가 2012년 Knight Capital이다. 오래전에 쓰지 않게 된 기능의 플래그를 새 기능에 다시 썼는데, 서버 여덟 대 중 한 대에 새 코드가 배포되지 않았다. 플래그가 켜지자 그 서버에서는 죽어 있던 옛 코드가 깨어나 주문을 쏟아 냈고, 45분 만에 4억 6천만 달러가 넘는 손실이 났다. 미국 SEC 보고서에 정리된 내용이다.

그래서 플래그를 만들 때 지우는 일까지 같이 만든다. 플래그마다 주인과 만료일을 적어 두고, 만료일이 지나면 알림이나 린트 경고가 나게 한다. 플래그를 추가하는 PR에서 제거 작업 티켓을 같이 만든다. 이름은 재사용하지 않는다. 운영용 킬 스위치처럼 오래 남는 플래그는 실험 플래그와 구분되게 이름이나 태그를 다르게 붙여서, 정리할 때 헷갈리지 않게 한다.

## 다시 4.8%와 5.3%로

처음의 숫자로 돌아가면, 지난주와 이번 주를 비교한 0.5%p로는 아무것도 말할 수 없다. 같은 기간에 사용자를 해시로 일관되게 나누고, 실제로 화면을 본 사람만 세고, 미리 정한 표본만큼 모은 뒤 한 번 판정해야 그 숫자가 화면의 효과라고 말할 수 있다. 그 전에 SRM으로 나누기가 제대로 됐는지 확인하고, 가드레일로 다른 곳이 망가지지 않았는지 본다. 이 과정을 자주 반복하려면 변형을 데이터로 다루는 화면 구조와 끝난 플래그를 지우는 습관이 같이 있어야 한다.

## 면접에서 나올 만한 질문

### A/B 테스트는 왜 필요한가요? 배포 전후를 비교하면 안 되나요?

전후 비교에는 그 기간에 바뀐 계절, 프로모션, 광고 같은 다른 요인이 모두 섞인다. A/B 테스트는 같은 기간에 사용자를 무작위로 나눠 두 무리가 같은 외부 요인을 겪게 하므로, 남는 차이를 변경의 효과로 볼 수 있다. 인과 관계를 확인하는 가장 확실한 방법이다.

### 피처 플래그의 종류와 각각의 수명은 어떻게 다른가요?

릴리스 플래그는 미완성 기능을 숨기거나 점진 공개할 때 쓰고 다 켜지면 지운다. 실험 플래그는 A/B 테스트용으로 일관된 배정과 노출 기록이 필요하며 실험이 끝나면 지운다. 운영 플래그는 장애 시 기능을 끄는 킬 스위치라 오래 남고, 권한 플래그는 특정 사용자에게만 기능을 여는 용도로 가장 오래 산다. 수명이 다르니 관리 규칙도 따로 둔다.

### 같은 사용자가 항상 같은 변형을 보게 하려면 어떻게 하나요?

실험 이름과 사용자 id를 이어 붙여 해시하고, 나머지 연산으로 버킷을 정해 버킷 구간에 변형을 할당한다. 해시는 같은 입력에 같은 값을 내니 저장소 없이 어느 서버에서든 같은 결과가 나온다. 실험 이름을 섞는 건 실험끼리 배정이 얽히지 않게 하려는 것이고, id 정규화가 서버와 클라이언트에서 다르면 같은 사람이 다른 버킷에 들어가니 주의한다. 점진 공개 비율을 올려도 기존 대상자가 그대로 남는다는 장점도 있다.

### 클라이언트에서 배정하면 어떤 문제가 있나요?

기존 화면이 먼저 그려진 뒤 바뀌는 깜빡임이 생기고, B 사용자가 실제로 겪는 화면이 설계한 B와 달라져 실험이 오염된다. 페이지를 가리는 스니펫은 깜빡임은 없애지만 모든 사용자의 첫 화면을 늦춘다. 서버나 엣지에서 HTML을 만들기 전에 배정하면 해결되지만, 사람마다 응답이 달라지니 CDN 캐시를 private으로 두거나 변형별로 키를 나눠야 한다.

### 노출 로깅은 왜 배정과 따로 하나요?

배정만 받고 실험 대상 화면을 보지 않은 사람까지 분석에 넣으면 두 무리 모두 효과와 무관한 사람으로 채워져 차이가 희석된다. 그래서 실험 영역이 실제로 보인 순간에 노출을 한 번 기록하고 노출된 사람만 비교한다. 플래그를 화면과 무관한 곳에서 미리 읽어 노출이 과하게 찍히거나, 한쪽 화면이 느려 노출이 덜 찍히는 실수를 조심한다.

### p값이 0.05보다 작으면 바로 실험을 끝내도 되나요?

미리 정한 표본을 다 모으기 전이라면 안 된다. 0.05 기준은 마지막에 한 번 본다는 전제에서의 거짓 양성률이라, 중간에 여러 번 보다가 처음 내려간 순간 멈추면 거짓 양성이 크게 늘어난다. 다섯 번 보면 14% 안팎까지 올라간다. 표본 크기와 종료일을 미리 정하거나, 여러 번 보는 걸 전제로 한 순차 검정을 쓴다.

### SRM이 무엇이고 발견하면 어떻게 하나요?

설계한 비율과 실제로 들어온 사람의 비율이 통계적으로 맞지 않는 상태다. 카이제곱 검정으로 확인하고, 나오면 효과를 해석하지 않고 원인부터 찾는다. 무작위 배정이라는 전제가 깨진 것이라 결과를 믿을 수 없기 때문이다. 원인은 한쪽 화면의 이탈로 노출이 덜 찍히는 경우, 리다이렉트 손실, 캐시, 봇, id 정규화 불일치 같은 기록 쪽 문제가 많다.

### 실험을 자주, 싸게 돌리려면 프런트엔드를 어떻게 설계하나요?

변형을 코드 분기가 아니라 설정 데이터로 표현하고, 플래그는 화면 최상단 한 곳에서만 읽어 아래 컴포넌트에는 설정값만 props로 넘긴다. 그러면 변형마다 테스트하기 쉽고, 실험 종료 후 정리도 설정 하나와 한 줄을 지우면 끝난다. 컴포넌트가 지원하는 범위의 변형은 플래그 시스템이 JSON 값으로 내려 줘서 배포 없이 실험할 수 있고, 이때 스키마 검증과 기본값 대체를 함께 둔다. 플래그마다 주인과 만료일을 정해 플래그 부채가 쌓이지 않게 한다.
