[Gas Station](https://leetcode.com/problems/gas-station/)은 LeetCode 134번이다. 원형으로 놓인 주유소에서 한 바퀴를 돌 수 있는 출발점을 찾는다. 모든 출발점을 해 보는 O(n²) 풀이는 금방 떠오르는데, 제약이 10^5라 통과하지 못한다. O(n)으로 가려면 "실패한 구간은 통째로 건너뛰어도 된다"는 관찰 하나가 필요하고, 이걸 설명하는 게 면접의 핵심 질문이 된다.

이 글은 다섯 가지 풀이를 본다. 모든 출발점을 해 보기, 실패한 구간 건너뛰기, 한 번 훑는 그리디, 누적 합의 최저점, 양 끝에서 좁혀 오는 투 포인터다. 셋은 같은 사실을 다른 각도에서 본 것이라, 하나를 이해하면 나머지가 왜 맞는지도 따라온다. 그리디를 증명하는 일반적인 방법은 [그리디 알고리즘 글](/posts/greedy-algorithms)에 있다. 코드는 Node.js 22, Python 3.13, Java 21에서 돌렸다.

## 원형 길 위의 주유소

주유소가 n개 원형으로 놓여 있다. i번 주유소에서는 기름을 `gas[i]`만큼 넣을 수 있고, i번에서 다음 주유소(i + 1번, 마지막은 0번)로 가는 데 `cost[i]`가 든다. 차의 기름통은 무한히 크고 처음에는 비어 있다. 시계 방향으로 한 바퀴를 돌아 출발한 주유소로 돌아올 수 있는 출발점의 번호를 돌려준다. 그런 곳이 없으면 -1이다. 답이 있으면 하나뿐이라는 보장이 있다.

풀이를 고르는 데 영향을 주는 제약은 이렇다.

- 주유소 수는 최대 10^5다. 출발점마다 한 바퀴를 시뮬레이션하면 10^10번이라 안 된다.
- `gas[i]`와 `cost[i]`는 0 이상 10^4 이하다. 합은 최대 10^9 정도라 Java `int`(약 21억)에 들어간다.
- 기름통에 상한이 없다. 이 조건이 그리디를 성립하게 한다. 상한이 생기면 이야기가 달라진다.

문제를 단순하게 만드는 첫걸음은 두 배열을 하나로 합치는 것이다. i번 주유소에 들렀다가 다음 주유소로 가면 기름이 `gas[i] - cost[i]`만큼 바뀐다. 이 값을 d[i]라 하자. 양수면 남고 음수면 모자란다. 출발점 s에서 한 바퀴를 돈다는 건, d[s]부터 원형으로 차례로 더해 가는 동안 합이 한 번도 음수가 되지 않는다는 뜻이다.

## 손으로 한 바퀴 돌아 본다

이 글에서 쓸 예시다.

```text
번호    0  1  2  3  4
gas     3  1  3  5  4
cost    2  4  5  1  2
d       1 -3 -2  4  2
```

d를 모두 더하면 1 - 3 - 2 + 4 + 2 = 2다. 한 바퀴를 돌고 기름이 2 남으니 어딘가에서는 출발할 수 있다.

0번에서 출발해 본다. 0번을 지나면 1, 1번을 지나면 1 - 3 = -2다. 1번에서 2번으로 가는 길에 바닥난다. 1번에서 출발하면 바로 -3이다. 2번에서도 바로 -2다. 3번에서 출발하면 4, 6, 7, 4, 2로 끝까지 음수가 안 된다. 답은 3이다. 4번에서 출발하면 2, 3, 0, -2로 2번을 지나다 바닥난다.

손으로 하다 보면 이상한 점이 보인다. 0번에서 출발해 1번 근처에서 실패했으면, 1번에서 다시 출발해 보는 건 헛수고였다. 0번에서 출발했을 때 1번에 도착하는 순간에는 기름이 1 있었는데, 1번에서 새로 출발하면 0에서 시작한다. 더 적은 기름으로 같은 길을 가니 같은 곳이나 더 빨리 실패할 수밖에 없다. 이 관찰을 정리하면 O(n) 풀이가 된다.

## 모든 출발점에서 한 바퀴를 돌려 본다

곧은 풀이부터 쓴다. 출발점 s마다 한 바퀴를 따라가며 기름을 더하고, 음수가 되면 그 출발점은 버린다.

```js
function canCompleteCircuit(gas, cost) {
  const n = gas.length;
  for (let s = 0; s < n; s++) {
    let tank = 0, ok = true;
    for (let k = 0; k < n; k++) {
      const i = (s + k) % n;                    // 원형이라 나머지로 돌아온다
      tank += gas[i] - cost[i];
      if (tank < 0) { ok = false; break; }      // 이 출발점은 실패
    }
    if (ok) return s;
  }
  return -1;
}
```

시간은 O(n²), 공간은 O(1)이다. 오래 걸리는 입력은 거의 모든 출발점이 한참 가다가 실패하는 경우다. 모든 칸의 d가 0이고 끝에서 두 번째만 -1, 마지막만 +1인 배열을 만들면, 0번부터 n - 3번까지는 끝 근처까지 가서 실패하고 답은 마지막 칸이다. 이 입력으로 재 봤다.

```text
10000 canBrute 9999 307.9
100000 canBrute 99999 19969.1
```

10만 칸에서 20초다. 제한 시간을 한참 넘는다. 낭비는 앞에서 본 그대로다. 실패한 출발점 바로 다음 칸에서 다시 출발해 같은 길을 또 걷는다.

## 실패한 구간은 통째로 건너뛴다

s에서 출발해 j번을 지나다 처음 바닥났다고 하자. 그러면 s와 j 사이의 어떤 칸 t에서 출발해도 j를 넘지 못한다.

이유는 이렇다. s에서 출발해 t에 도착했을 때 기름은 0 이상이다. 처음 바닥난 곳이 j였으니 t까지는 음수가 된 적이 없다. t에서 새로 출발하면 기름 0에서 시작하는데, s에서 온 차는 t에서 0 이상을 들고 있었다. 같은 길을 더 적거나 같은 기름으로 가니 j까지 가는 동안 언제나 s에서 온 차보다 기름이 적거나 같다. s에서 온 차가 j에서 음수가 됐으니 t에서 출발한 차도 j에서 음수가 된다.

그래서 실패하면 다음 출발점을 s + 1이 아니라 j + 1로 바로 옮긴다.

```js
function canCompleteCircuit(gas, cost) {
  const n = gas.length;
  let s = 0;
  while (s < n) {
    let tank = 0, k = 0;
    while (k < n) {
      const i = (s + k) % n;
      tank += gas[i] - cost[i];
      if (tank < 0) break;
      k++;
    }
    if (k === n) return s;                      // 한 바퀴를 다 돌았다
    s = s + k + 1;                              // 실패한 칸 다음으로 건너뛴다
  }
  return -1;
}
```

s는 계속 앞으로만 가고, 시뮬레이션한 칸은 모든 출발점을 합쳐도 대략 2n개를 넘지 않는다. 실패한 시도들이 각자 다른 구간을 걷고, 성공한 마지막 시도만 한 바퀴를 돈다. 시간 O(n), 공간 O(1)이다. 앞의 20초짜리 입력이 2.8ms로 줄었다. 무작위 입력 5만 개로 모든 출발점 풀이와 같은 답이 나오는지 맞춰 봤다.

이 풀이는 정확하지만 원형 나머지 계산과 이중 반복이 남아 있다. 한 걸음 더 정리할 수 있다.

## 한 번 훑으며 출발점을 다시 고른다

앞 풀이에서 s가 j + 1로 건너뛸 때, j + 1이 n을 넘으면 그냥 실패다. 그러니 실제로 원형으로 넘어가는 시도는 마지막 한 번뿐이다. 그 마지막 시도가 성공하는지는 매번 시뮬레이션하지 않아도 전체 합으로 알 수 있다. 전체 합이 0 이상이면 성공한다. 이 부분은 아래에서 증명한다.

그러면 반복이 하나로 합쳐진다. 0번부터 n - 1번까지 한 번 훑으며 두 가지를 더한다.

- `total`: 지금까지 모든 d의 합. 끝나면 한 바퀴 전체의 남는 기름이다.
- `tank`: 지금 출발점 `start`에서 출발했을 때의 기름. 음수가 되면 `start`를 다음 칸으로 옮기고 0으로 되돌린다.

```js
function canCompleteCircuit(gas, cost) {
  let total = 0, tank = 0, start = 0;
  for (let i = 0; i < gas.length; i++) {
    const d = gas[i] - cost[i];
    total += d;                                 // 한 바퀴 전체의 남는 기름
    tank += d;                                  // start에서 출발했을 때 지금 기름
    if (tank < 0) {                             // start부터 i까지는 출발점이 될 수 없다
      start = i + 1;
      tank = 0;
    }
  }
  return total >= 0 ? start : -1;
}
```

예시에서 칸마다 값을 찍었다.

```text
i 0 d 1 tank 1 start 0 total 1
i 1 d -3 tank 0 start 2 total -2 reset
i 2 d -2 tank 0 start 3 total -4 reset
i 3 d 4 tank 4 start 3 total 0
i 4 d 2 tank 6 start 3 total 2
```

`reset` 줄의 tank가 0인 건 음수가 된 뒤 0으로 되돌린 값을 찍었기 때문이다. 1번에서 tank가 -2, 2번에서 -2가 되어 출발점이 두 번 옮겨졌다. 아래 그림에서 다음을 누르면 출발점이 옮겨 가는 모습을 볼 수 있다. 칸의 숫자는 d다.

### 전체 합이 0 이상이면 왜 끝까지 돌 수 있나

마지막 `start`에서 n - 1번까지 가는 동안은 tank가 음수가 된 적이 없다. 남은 건 n - 1번을 지나 0번으로 넘어가서 `start` 앞까지 가는 구간이다.

0번부터 `start - 1`번까지는 앞의 실패한 시도들이 나눠 가진 구간들이다. 각 구간은 끝에서 tank가 음수가 되어 끊겼으니 구간마다 합이 음수다. 그래서 이 앞부분 전체의 합 A는 0보다 작거나 같고, 뒷부분(`start`부터 끝까지)의 합 B는 지금 tank다. A + B = total이 0 이상이다.

앞부분을 지나는 동안 어느 지점에서든 기름은 B + (앞부분의 앞쪽 일부의 합)이다. 이 앞쪽 일부의 합이 언제나 A 이상이라는 걸 보이면 된다. 앞쪽 일부를 잘라 내고 남는 뒤쪽은 어떤 실패 구간의 뒷부분과 그 뒤의 실패 구간들이다. 실패 구간의 앞부분은 바닥나기 전이라 합이 0 이상이니, 뒷부분의 합은 구간 전체의 합보다도 작아서 음수다. 뒤의 실패 구간들도 음수다. 남는 뒤쪽의 합이 0 이하이니 잘라 낸 앞쪽의 합은 A 이상이다. 결국 어느 지점에서든 기름은 B + A 이상, 즉 total 이상이라 음수가 되지 않는다.

예시로 숫자를 맞춰 보면 이렇다. 마지막 출발점은 3번이고, 앞부분 0~2번의 합 A는 1 - 3 - 2 = -4, 뒷부분 3~4번의 합 B는 4 + 2 = 6이다. 4번을 지나 0번으로 넘어가면 기름은 6 + 1 = 7, 1번을 지나면 7 - 3 = 4, 2번을 지나면 4 - 2 = 2다. 가장 낮은 값이 끝의 2, 즉 total이고 그보다 아래로 내려가지 않는다.

말로 풀면 길지만 그림은 단순하다. 바닥난 구간들은 모두 손해만 본 구간이고, 그 손해를 뒷부분이 미리 벌어 둔 기름이 덮는다. 전체 합이 0 이상이라는 건 덮을 만큼 벌었다는 뜻이다.

## 누적 합이 가장 낮은 곳 다음에서 출발한다

같은 사실을 그래프로 보면 더 짧게 증명된다. 0번 앞의 0에서 시작해 d를 차례로 더한 누적 합을 그린다고 하자. 예시에서는 0, 1, -2, -4, 0, 2다.

출발점 s에서 출발하면 기름은 "지금 누적 합 - s 직전의 누적 합"이다. 원형으로 넘어가면 total이 한 번 더해진다. 그러니 s 직전의 누적 합이 가장 낮은 지점이면, 그 뒤의 누적 합은 모두 그보다 높거나 같아서 기름이 음수가 되지 않는다. 넘어간 뒤에도 total이 0 이상이라 더 높아지기만 한다.

그래서 답은 "누적 합이 가장 낮은 지점 바로 다음 칸"이다. 출발 전 0도 후보에 넣는다. 아무 칸도 0보다 낮아지지 않으면 0번에서 출발하면 된다.

```js
function canCompleteCircuit(gas, cost) {
  let sum = 0, minSum = 0, minIdx = -1;        // 출발 전 누적 합 0을 최저점으로 시작
  for (let i = 0; i < gas.length; i++) {
    sum += gas[i] - cost[i];
    if (sum < minSum) { minSum = sum; minIdx = i; } // 더 낮은 지점을 찾았다
  }
  if (sum < 0) return -1;                       // 한 바퀴 전체가 모자란다
  return (minIdx + 1) % gas.length;             // 최저점 바로 다음 칸
}
```

앞의 그리디와 답이 같은 건 우연이 아니다. 그리디가 tank를 0으로 되돌리는 순간은 누적 합이 지금까지의 최저점보다 낮아지는 순간과 정확히 같다. 그리디의 `start`가 언제나 "최저점 다음 칸"을 가리키고 있었던 셈이다. 면접에서 그리디가 왜 맞냐고 물으면 이 그림으로 설명하는 게 가장 빠르다.

이 관점은 [주식 문제 글의 카데인 풀이](/posts/leetcode-best-time-to-buy-and-sell-stock#하루치-변화량을-이어-붙인다)와도 닮았다. 거기서도 "지금까지 합이 음수가 되면 버리고 다시 시작한다"는 같은 동작이 나온다. 차이는 그쪽이 가장 큰 구간 합을 찾고, 이쪽은 음수가 되지 않는 시작점을 찾는다는 것이다.

## 양 끝에서 좁혀 온다

원형이라는 걸 정면으로 쓰는 풀이도 있다. 출발점 `start`를 맨 끝(n - 1번)에, 도착 쪽 끝 `end`를 0번에 둔다. `start`에서 출발해 n - 1번을 지나 0번, 1번으로 넘어가는 구간을 생각하는 것이다. 지금 기름이 0 이상이면 `end`를 앞으로 늘려 한 칸 더 간다. 음수면 출발점을 한 칸 앞(`start - 1`)으로 당긴다. 출발점을 당기면 그 칸의 d가 맨 앞에 더해지니 기름이 바뀐다. 두 끝이 만나면 한 바퀴 구간이 완성된다.

```js
function canCompleteCircuit(gas, cost) {
  const n = gas.length;
  let start = n - 1, end = 0;                   // start에서 출발해 end 앞까지 왔다
  let tank = gas[start] - cost[start];
  while (end < start) {
    if (tank >= 0) {                            // 아직 여유가 있으니 한 칸 더 간다
      tank += gas[end] - cost[end];
      end++;
    } else {                                    // 모자라니 출발점을 한 칸 앞으로 당긴다
      start--;
      tank += gas[start] - cost[start];
    }
  }
  return tank >= 0 ? start : -1;
}
```

예시에서 움직임을 찍었다.

```text
init start 4 tank 2
extend end -> 1 tank 3
extend end -> 2 tank 0
extend end -> 3 tank -2
move start -> 3 tank 2
```

마지막에 두 끝이 3번에서 만나고 기름이 2라 답은 3이다. 매 단계에서 두 끝 중 하나가 한 칸씩 움직이니 시간 O(n), 공간 O(1)이다. 두 포인터가 양쪽에서 좁혀 오는 모양은 [투 포인터 패턴 글](/posts/two-pointers-pattern)과 같다.

이 풀이가 맞는 이유도 결국 누적 합이다. 구간을 넓히는 쪽을 고르는 규칙이 "기름이 모자라면 앞쪽에서 더 많이 벌어 온다"이고, 끝났을 때 tank는 구간 전체, 즉 total이다. 답의 성질은 같지만 코드가 조금 덜 직관적이라 면접에서 첫 답으로 쓰기는 어렵다. 다른 풀이를 아는지 물을 때 꺼내면 좋다.

## Python과 Java로 옮기기

```python
from typing import List


class Solution:
    def canCompleteCircuit(self, gas: List[int], cost: List[int]) -> int:
        total = tank = start = 0
        for i, (g, c) in enumerate(zip(gas, cost)):
            total += g - c                     # 한 바퀴 전체의 남는 기름
            tank += g - c                      # start에서 출발했을 때 지금 기름
            if tank < 0:                       # start부터 i까지는 출발점이 될 수 없다
                start = i + 1
                tank = 0
        return start if total >= 0 else -1
```

[2, 3, 4] [3, 4, 3] -1
[5] [4] 0
[3] [4] -1

`zip`으로 두 배열을 같이 훑는다. 전체 합 판정만 따로 하고 싶으면 `sum(gas) < sum(cost)`로 먼저 걸러도 된다. 배열을 한 번 더 읽을 뿐 복잡도는 같다.

누적 합 풀이를 Python으로 쓰면 `itertools.accumulate`가 누적 합을 만들어 준다.

```python
from itertools import accumulate


def can_complete_circuit_prefix(gas, cost):
    sums = list(accumulate(g - c for g, c in zip(gas, cost)))
    if sums[-1] < 0:                           # 한 바퀴 전체가 모자란다
        return -1
    low = min(sums)
    if low >= 0:                               # 출발 전 0이 가장 낮다
        return 0
    return (sums.index(low) + 1) % len(gas)   # 처음 나오는 최저점 바로 다음 칸
```

```text
3 -1 0 -1 0
```

위의 다섯 입력을 차례로 넣은 결과로, 그리디와 같다. `sums.index(low)`는 최저점이 여러 번 나오면 처음 것을 준다. 최저점이 여럿이면 그 다음 칸들이 모두 답이 될 수 있지만, 이 문제는 답이 하나라 상관없다. 배열을 하나 더 만드니 공간은 O(n)이다.

```java
class Solution {
    public int canCompleteCircuit(int[] gas, int[] cost) {
        int total = 0, tank = 0, start = 0;
        for (int i = 0; i < gas.length; i++) {
            int d = gas[i] - cost[i];
            total += d;                        // 한 바퀴 전체의 남는 기름
            tank += d;                         // start에서 출발했을 때 지금 기름
            if (tank < 0) {                    // start부터 i까지는 출발점이 될 수 없다
                start = i + 1;
                tank = 0;
            }
        }
        return total >= 0 ? start : -1;
    }
}
```

```text
[3, 1, 3, 5, 4] [2, 4, 5, 1, 2] 3
[2, 3, 4] [3, 4, 3] -1
[5] [4] 0
[3] [4] -1
[4, 5, 1, 2] [3, 2, 4, 3] 0
```

`main`에서 같은 다섯 입력을 넣었다. d의 절댓값은 최대 10^4이고 10^5개를 더하니 total은 ±10^9 안이다. `int` 최대가 약 21억이라 들어가지만 여유가 두 배 정도뿐이다. 제약이 조금만 커져도 넘치니, 값의 범위가 다른 변형이면 `long`을 쓴다.

## 틀리기 쉬운 자리

### 전체 합 검사를 빼먹는다

```js
let tank = 0, start = 0;
for (let i = 0; i < gas.length; i++) {
  tank += gas[i] - cost[i];
  if (tank < 0) { start = i + 1; tank = 0; }
}
return start;                                   // total 검사가 없다
```

`gas = [2, 3, 4]`, `cost = [3, 4, 3]`에서 2가 나온다. d가 -1, -1, 1이라 전체가 -1인데, 마지막 칸만 보면 tank가 1이라 출발점처럼 보인다. 정답은 -1이다. "start가 n이 아니면 성공" 같은 조건으로 바꿔도 같은 입력에서 2가 나온다. 앞부분의 손해를 뒷부분이 덮는지는 전체 합만 알려 준다.

### 바닥난 칸을 새 출발점으로 삼는다

`start = i + 1` 대신 `start = i`로 쓰면 `gas = [1, 1, 5]`, `cost = [3, 3, 1]`에서 1이 나온다. 정답은 2다. 바닥난 칸 i 자체도 실패 구간에 들어 있다. i에서 출발하면 d[i]가 음수라 바로 바닥난다.

### tank를 0으로 되돌리지 않는다

출발점만 옮기고 `tank = 0`을 빼먹으면 앞 구간의 빚을 그대로 들고 간다. `gas = [1, 3, 2, 4, 3]`, `cost = [5, 1, 2, 1, 3]`에서 d가 -4, 2, 0, 3, 0인데, tank가 -4에서 시작해 계속 음수라 출발점이 끝까지 밀려 3이 나온다. 정답은 1이다.

### 가장 많이 남는 주유소에서 출발한다

그럴듯한 탐욕이지만 틀린다. `gas = [4, 5, 1, 2]`, `cost = [3, 2, 4, 3]`에서 d는 1, 3, -3, -1이다. 가장 많이 남는 1번에서 출발하면 3, 0, -1로 3번을 지나다 바닥난다. 정답은 0번이다. 0번에서 출발하면 1, 4, 1, 0으로 딱 맞게 돌아온다. 중요한 건 한 칸의 이득이 아니라 출발점 앞까지의 손해가 가장 큰 지점, 즉 누적 합의 최저점이다.

### 기름이 정확히 0 남는 경우

`tank < 0`일 때만 출발점을 옮긴다. `tank <= 0`으로 쓰고 싶어지는데, 0은 바닥난 게 아니다. 다음 주유소에 딱 맞게 도착했을 뿐이다. 마찬가지로 `total >= 0`의 등호도 필요하다. 한 바퀴를 돌고 기름이 0 남는 것도 성공이다. `gas = [4, 5, 1, 2]`, `cost = [3, 2, 4, 3]`은 total이 정확히 0이라 `total > 0`으로 쓰면 -1이 나온다. 모든 값이 0인 `[0, 0, 0]`도 0번에서 출발하면 돈다.

### 답이 여러 개인 입력

이 문제는 답이 하나라고 보장하지만, 보장이 없으면 풀이마다 다른 답을 낼 수 있다. 모든 칸에서 `gas`와 `cost`가 1인 `[1, 1, 1]`은 어디서 출발해도 된다. 한 번 훑는 그리디와 최저점 풀이는 0을, 투 포인터는 2를 돌려준다. 셋 다 맞는 출발점이다. 테스트 코드를 짤 때 이런 입력을 넣으면 "정답과 다르다"고 잘못 판정할 수 있으니, 출발점이 실제로 한 바퀴를 도는지로 검사한다.

### 손으로 확신이 안 서면 작은 입력으로 맞춰 본다

증명이 길어서 코딩 테스트 중에 확신이 안 서면, 모든 출발점 시뮬레이션과 무작위 입력으로 맞춰 본다. 답이 여럿인 입력도 섞이니, 돌려준 출발점이 실제로 한 바퀴를 도는지로 검사한다.

## 조건이 바뀌면

### 가능한 출발점을 모두 구하라면

답이 하나라는 보장을 빼면, 누적 합 관점에서 조건을 그대로 적으면 된다. 출발점 i가 되려면 i 뒤의 누적 합이 모두 i 직전 값 이상이고, 한 바퀴 넘어간 뒤의 값(total + 앞쪽 누적 합)도 i 직전 값 이상이어야 한다. 뒤쪽 최솟값과 앞쪽 최솟값을 미리 구해 두면 O(n)이다.

```js
function allStarts(gas, cost) {
  const n = gas.length;
  const P = new Array(n + 1).fill(0);           // P[i]: 0번부터 i - 1번까지의 합
  for (let i = 0; i < n; i++) P[i + 1] = P[i] + gas[i] - cost[i];
  const total = P[n];
  if (total < 0) return [];
  const sufMin = new Array(n + 1).fill(Infinity); // sufMin[i]: P[i..n] 중 최솟값
  for (let i = n; i >= 0; i--) sufMin[i] = Math.min(P[i], i < n ? sufMin[i + 1] : Infinity);
  const res = [];
  let preMin = Infinity;                        // P[1..i] 중 최솟값 (한 바퀴 넘어간 구간)
  for (let i = 0; i < n; i++) {
    const okRest = sufMin[i + 1] >= P[i];               // i부터 끝까지 바닥나지 않는다
    const okWrap = preMin === Infinity || total + preMin >= P[i]; // 0번으로 넘어가서도
    if (okRest && okWrap) res.push(i);
    preMin = Math.min(preMin, P[i + 1]);
  }
  return res;
}
```

```text
[0,1,2] [0,2] [3]
```

`gas = [3, 3, 2]`, `cost = [1, 1, 2]`, 그리고 `gas = [2, 0, 2, 0]`, `cost = [1, 1, 1, 1]`, 이 글의 예시를 넣은 결과다. 무작위 입력 10만 개로 모든 출발점 시뮬레이션과 맞춰 봤다. 처음에는 "누적 합이 최저점과 같은 칸 다음"만 모았다가 틀렸다. total이 0보다 크면 최저점이 아닌 곳에서 출발해도 넘어간 뒤의 여유로 버티는 경우가 있다. `[3, 3, 2]` 예시가 그렇다.

### 기름통에 상한이 있다면

통에 최대 C만큼만 담을 수 있으면, 넘치는 기름은 버려진다. 그러면 "s에서 온 차가 t에 도착할 때 기름이 0 이상이니 t에서 새로 출발하는 것보다 낫다"는 비교는 여전히 성립하지만, 누적 합으로 계산하는 방법은 깨진다. 버려지는 양 때문에 기름이 단순한 합이 아니게 된다. 건너뛰기 풀이의 시뮬레이션은 넘친 기름을 C로 자르기만 하면 그대로 쓸 수 있고, 건너뛰기의 근거도 남아서 O(n)이다.

### 반대 방향으로도 돌 수 있다면

시계 반대 방향으로 돌 때는 i번에서 i - 1번으로 가는 비용이 필요하다. 그 비용 배열이 주어지면 배열을 뒤집어 같은 함수를 한 번 더 돌린다. 두 방향의 결과 중 원하는 쪽을 고른다.

### 기름을 넣는 횟수를 최소로 하라면

LeetCode 871번 Minimum Number of Refueling Stops는 직선 도로에서 주유소마다 기름을 넣을지 말지 고르고, 넣는 횟수를 최소로 한다. 지나온 주유소를 최대 힙에 넣어 두고 기름이 모자랄 때만 가장 많은 것을 꺼내 넣는다. 그리디의 결이 다르다. 여기서는 선택을 미뤘다가 꼭 필요할 때 가장 좋은 것을 고른다. 힙은 [힙 글](/posts/ds-heap)에 있다.

### 원형 배열에서 구간 합의 최댓값이라면

LeetCode 918번 Maximum Sum Circular Subarray는 원형 배열에서 연속 구간 합의 최댓값을 묻는다. 이 글과 같은 생각이 통한다. 원형으로 넘어가는 구간은 "전체 합에서 가운데 가장 작은 구간을 뺀 것"이라, 카데인으로 최대 구간과 최소 구간을 함께 구하면 된다. 원형을 직선으로 펴서 전체 합으로 넘어간 부분을 계산한다는 점이 Gas Station과 같다.

## 면접에서 나올 만한 질문

### 전체 기름이 전체 비용 이상이면 반드시 출발점이 있나요?

있다. 누적 합이 가장 낮은 지점 바로 다음 칸에서 출발하면, 그 뒤의 누적 합은 모두 그보다 높거나 같아서 기름이 음수가 되지 않는다. 0번으로 넘어간 뒤에도 전체 합이 0 이상이라 더 높아지기만 한다. 그래서 전체 합만으로 "답이 있는가"를 판정할 수 있다.

### 바닥나면 왜 다음 칸으로 바로 건너뛰나요?

s에서 출발해 j에서 처음 바닥났다면, 그 사이 칸 t에 도착했을 때 기름은 0 이상이었다. t에서 새로 출발하면 0에서 시작하니 같은 길을 더 적거나 같은 기름으로 가서 j에서 역시 바닥난다. 그래서 s부터 j까지는 모두 출발점 후보에서 빠지고, j + 1부터 다시 본다. 이 건너뛰기 덕분에 O(n)이다.

### 마지막 출발점에서 원형으로 넘어가는 구간은 검사하지 않아도 되나요?

전체 합이 0 이상이면 검사하지 않아도 된다. 0번부터 출발점 앞까지는 실패한 구간들이라 합이 음수인 손해 구간이고, 출발점부터 끝까지 벌어 둔 기름이 그 손해를 덮는다. 둘을 더한 값이 전체 합이라, 전체 합이 0 이상이면 넘어가는 동안에도 기름이 음수가 되지 않는다.

### 누적 합 풀이와 그리디 풀이는 어떤 관계인가요?

같은 계산이다. 그리디가 tank를 0으로 되돌리는 순간은 누적 합이 지금까지의 최저점보다 낮아지는 순간과 같다. 그래서 그리디의 start는 언제나 최저점 다음 칸을 가리킨다. 그래프로 그리면 증명이 한눈에 보여서 설명할 때는 누적 합 쪽이 편하다.

### 가장 많이 남는 주유소에서 출발하면 왜 틀리나요?

한 칸의 이득이 커도 그 뒤에 큰 손해가 이어지면 버티지 못하기 때문이다. d가 1, 3, -3, -1이면 3이 남는 1번에서 출발해 3번을 지나다 바닥나지만, 0번에서 출발하면 딱 맞게 돌아온다. 기준은 한 칸의 값이 아니라 출발점 앞까지 쌓인 손해, 즉 누적 합의 최저점이다.

### Java로 풀 때 정수 넘침은 괜찮나요?

이 문제의 제약에서는 괜찮다. 칸마다 차이가 최대 10^4이고 10^5칸이라 합이 ±10^9 안이고, `int` 최대는 약 21억이다. 하지만 여유가 두 배뿐이라 값 범위가 커지는 변형이면 `long`을 쓴다.

### 답이 여러 개일 수 있다면 어떻게 하나요?

원래 문제는 답이 하나라고 보장해서 아무 출발점이나 돌려주면 된다. 모두 구해야 하면, 출발점 i 뒤의 누적 합 최솟값과 한 바퀴 넘어간 뒤의 최솟값이 모두 i 직전 누적 합 이상인지 보면 된다. 뒤쪽과 앞쪽 최솟값을 미리 구해 두면 O(n)이다.
