## 가깝다는 건 어떻게 재나

두 점 사이의 직선 거리(유클리드 거리)를 써도 되지만, 임베딩에서는 코사인 유사도를 더 많이 쓴다. 위 그림의 두 번째 단계에서 본 화살표의 방향이 얼마나 비슷한지를 재는 값이다. 같은 방향이면 1, 직각이면 0, 정반대면 −1이 나온다.

```ts
function cosineSimilarity(a: number[], b: number[]) {
  let dot = 0, normA = 0, normB = 0;
  for (let i = 0; i < a.length; i++) {
    dot += a[i] * b[i];
    normA += a[i] * a[i];
    normB += b[i] * b[i];
  }
  return dot / (Math.sqrt(normA) * Math.sqrt(normB));
}
```

길이를 1로 맞춰 둔(정규화한) 벡터끼리는 코사인 유사도와 내적이 같아진다. 그래서 많은 시스템이 저장할 때 미리 정규화해 두고 계산이 가벼운 내적을 쓴다.

## 하나하나 다 재면 느리다

가장 확실한 방법은 질문 벡터를 저장된 모든 벡터와 하나씩 비교하는 것이다. 문서가 천 개라면 이걸로 충분하다. 문제는 규모다. 1536차원 벡터가 1억 개 있으면 질문 하나에 곱셈만 1,500억 번이 넘는다. 검색 한 번에 이걸 기다릴 수는 없다.

그래서 실제 벡터 DB는 근사 최근접 탐색(ANN, Approximate Nearest Neighbor)을 쓴다. 정답을 아주 가끔 놓치는 대신 비교 횟수를 크게 줄인다. 그중 가장 널리 쓰이는 방식이 HNSW다.

## 지름길이 있는 그래프, HNSW

HNSW는 점마다 가까운 이웃 몇 개를 선으로 이어 그래프를 만들어 둔다. 검색할 때는 아무 점에서나 출발해서, 이웃 중 질문에 더 가까운 쪽으로 계속 옮겨 간다. 더 가까워지는 이웃이 없으면 거기서 멈추고, 그 주변을 답으로 돌려준다. 낯선 동네에서 목적지 방향으로 한 블록씩 걸어가는 것과 비슷하다.

## 정확도와 속도를 맞바꾸는 손잡이

근사 탐색이라 가끔 진짜 가장 가까운 점을 놓친다. 진짜 정답 중 몇 개를 찾았는지를 재현율(recall)이라고 하고, 이 값과 속도는 서로 맞바꾼다. HNSW에서는 점마다 이웃을 몇 개까지 이을지(M), 검색할 때 후보를 몇 개나 들고 다닐지(ef) 같은 값으로 조절한다. 이웃을 많이 잇고 후보를 많이 들고 다닐수록 정확해지지만 메모리와 시간이 더 든다.

## HNSW 말고 다른 인덱스

HNSW만 있는 건 아니다. 자주 비교되는 게 IVF(Inverted File Index)다. 먼저 전체 벡터를 k-평균 같은 방법으로 수백~수천 개 묶음(클러스터)으로 나눠 두고, 검색할 때는 질문과 가까운 묶음 몇 개(`nprobe`)만 열어서 그 안을 다 비교한다. 동네를 먼저 고르고 그 동네만 뒤지는 셈이다. 묶음 경계 근처의 정답을 놓칠 수 있어서, 여는 묶음 수를 늘리면 정확해지고 느려진다.

벡터가 너무 많아 메모리에 다 올리기 어려우면 PQ(Product Quantization) 같은 압축을 함께 쓴다. 벡터를 여러 조각으로 나누고 조각마다 가장 비슷한 대표값의 번호로 바꿔 저장해서, 1536개의 실수를 수십 바이트 정도로 줄인다. 대신 거리 계산이 근사가 되어 정확도가 조금 더 떨어진다.

둘을 고를 때는 보통 이렇게 본다. HNSW는 검색이 빠르고 재현율이 높지만 그래프 때문에 메모리를 많이 쓰고 인덱스를 만드는 데 시간이 걸린다. 삭제가 잦으면 그래프에 구멍이 생겨 주기적으로 다시 만들어야 하는 경우도 있다. IVF는 메모리가 적고 빨리 만들어지지만, 데이터 분포가 바뀌면 묶음을 다시 나눠야 한다.

## 실제로는 어디에 쓰나: RAG

## 직접 붙여 볼 때

전용 벡터 DB(Pinecone, Qdrant, Milvus, Weaviate 등)도 많지만, 이미 PostgreSQL을 쓰고 있다면 pgvector 확장으로 시작하는 경우가 많다. 테이블에 벡터 컬럼을 하나 더 두고, HNSW 인덱스를 거는 정도면 된다. `<=>`는 코사인 거리 연산자다.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE docs (
  id        bigserial PRIMARY KEY,
  content   text,
  embedding vector(1536)
);

CREATE INDEX ON docs USING hnsw (embedding vector_cosine_ops);

SELECT content
FROM docs
ORDER BY embedding <=> $1   -- $1: 질문 벡터
LIMIT 3;
```

실제로 붙여 보면 인덱스보다 데이터를 어떻게 넣느냐가 결과를 더 크게 좌우한다. 긴 문서는 문단 단위 정도로 잘라서(청크) 넣어야 검색이 정확해지고, 너무 잘게 자르면 앞뒤 맥락이 사라진다. 저장할 때와 검색할 때 같은 임베딩 모델을 써야 한다는 것도 잊기 쉽다. 제품명이나 에러 코드처럼 글자가 정확히 맞아야 하는 검색은 여전히 키워드 검색이 강해서, 둘을 섞는 하이브리드 검색도 많이 쓴다.

조건을 함께 거는 검색도 생각보다 까다롭다. "작년 문서 중에서 가까운 것"처럼 메타데이터 필터를 걸 때, 가까운 벡터를 먼저 k개 찾고 나서 필터를 적용하면(post-filtering) 조건에 맞는 게 몇 개 안 남거나 아예 비어 버릴 수 있다. 필터를 먼저 걸고 그 안에서 찾으면(pre-filtering) 정확하지만 인덱스를 제대로 못 써서 느려질 수 있다. 벡터 DB마다 이 부분을 다르게 풀고 있어서, 필터가 중요한 서비스라면 고를 때 꼭 확인해야 한다.

검색 품질을 한 번 더 끌어올리는 방법으로 리랭킹이 있다. 벡터 검색으로 후보를 넉넉하게(예: 50개) 뽑고, 질문과 문서를 함께 넣어 관련도를 직접 매기는 더 무거운 모델(cross-encoder)로 다시 순위를 매겨 상위 몇 개만 쓴다. 품질은 "정답 문서가 상위 k개 안에 들어왔는가"(recall@k) 같은 지표로 재고, 청크 크기나 모델을 바꿀 때마다 같은 질문 세트로 비교한다.

## pgvector를 붙였는데 결과가 이상할 때

pgvector로 시작하면 처음 몇 주 안에 부딪히는 일이 정해져 있다. Ubuntu 24.04의 PostgreSQL 16에 `postgresql-16-pgvector` 패키지(0.6.0)를 깔고, 64차원 벡터 2만 개를 넣은 `docs` 테이블에서 직접 재현해 봤다. 100개 중 1개는 `category`가 `'faq'`이고 나머지는 `'blog'`다.

첫 번째는 인덱스를 만들었는데 검색이 여전히 느린 경우다. `EXPLAIN`부터 본다.

```sql
-- 인덱스는 코사인 거리용(vector_cosine_ops)으로 만들었다
EXPLAIN SELECT id FROM docs
ORDER BY embedding <-> (SELECT embedding FROM docs WHERE id = 42)  -- <->는 유클리드 거리
LIMIT 5;
```

```text
 Limit  (cost=1360.50..1360.51 rows=5 width=16)
   InitPlan 1 (returns $0)
     ->  Index Scan using docs_pkey on docs docs_1  (cost=0.29..8.30 rows=1 width=264)
           Index Cond: (id = 42)
   ->  Sort  (cost=1352.19..1402.19 rows=20000 width=16)
         Sort Key: ((docs.embedding <-> $0))
         ->  Seq Scan on docs  (cost=0.00..1020.00 rows=20000 width=16)
```

맨 아래 `Seq Scan`과 그 위의 `Sort`가 문제다. 2만 개를 전부 재고 정렬했다. 인덱스는 만들 때 고른 거리 연산자에만 쓰인다. 연산자를 `<=>`(코사인 거리)로 바꾸면 같은 쿼리가 이렇게 된다.

```text
 Limit  (cost=32.91..33.74 rows=5 width=16)
   InitPlan 1 (returns $0)
     ->  Index Scan using docs_pkey on docs docs_1  (cost=0.29..8.30 rows=1 width=264)
           Index Cond: (id = 42)
   ->  Index Scan using docs_embedding_idx on docs  (cost=24.60..3354.60 rows=20000 width=16)
         Order By: (embedding <=> $0)
```

`Index Scan using docs_embedding_idx`와 `Order By`가 보이면 HNSW를 탄 것이다. ORM이나 라이브러리가 기본으로 어떤 연산자를 쓰는지 확인하고, 인덱스의 연산자 클래스(`vector_l2_ops`, `vector_ip_ops`, `vector_cosine_ops`)와 맞춘다.

두 번째는 조건을 걸었더니 결과가 모자란 경우다. "FAQ 중에서 가까운 10개"를 물었는데 1개만 왔다.

```sql
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
SELECT id FROM docs WHERE category = 'faq'
ORDER BY embedding <=> (SELECT embedding FROM docs WHERE id = 42)
LIMIT 10;
```

```text
 Limit (actual rows=1 loops=1)
   ...
   ->  Index Scan using docs_embedding_idx on docs (actual rows=1 loops=1)
         Order By: (embedding <=> $0)
         Filter: (category = 'faq'::text)
         Rows Removed by Filter: 39
```

`Rows Removed by Filter: 39`가 답이다. HNSW 인덱스는 후보를 `hnsw.ef_search`(기본 40)개만 꺼내고, 필터는 그 뒤에 걸린다. 40개 중 FAQ가 1개뿐이었다. 앞에서 말한 post-filtering이 실제로는 이렇게 보인다. `SET hnsw.ef_search = 1000`(최댓값)으로 올려도 6개였다. 조건이 늘 정해져 있다면 그 조건만 담은 부분 인덱스가 확실하다.

```sql
CREATE INDEX docs_faq_embedding_idx ON docs
USING hnsw (embedding vector_cosine_ops) WHERE category = 'faq';
```

같은 쿼리가 `Index Scan using docs_faq_embedding_idx`로 바뀌고 `actual rows=10`이 나왔다. 조건 값이 많고 자주 바뀌면 부분 인덱스로는 못 버티니, pgvector 0.8.0부터 생긴 반복 탐색(`hnsw.iterative_scan`)을 쓰거나 필터를 잘 다루는 전용 벡터 DB를 검토한다.

세 번째는 재현율이 얼마나 나오는지 모르는 채로 쓰는 경우다. 같은 질문에 대해 인덱스 결과와 전부 재 본 정답을 비교하면 된다. `ORDER BY (embedding <=> q) + 0`처럼 식을 살짝 바꾸면 인덱스를 못 타서 정확한 상위 10개가 나온다. 질문 100개로 재 보니 이랬다.

```text
ef_search=10  recall@10=0.945
ef_search=40  recall@10=0.955
ef_search=100 recall@10=0.978
ef_search=200 recall@10=0.993
```

후보를 많이 들고 다닐수록 정답을 덜 놓친다. 실제 임베딩은 무작위 벡터보다 뭉쳐 있어서 숫자가 다르게 나오니, 내 데이터와 실제 질문으로 이렇게 한 번 재 보고 `ef_search`를 정한다.

인덱스를 만들 때도 신호가 하나 있다. `maintenance_work_mem`을 1MB로 줄이고 만들면 이런 알림이 뜬다.

```text
NOTICE:  hnsw graph no longer fits into maintenance_work_mem after 1079 tuples
DETAIL:  Building will take significantly more time.
HINT:  Increase maintenance_work_mem to speed up builds.
```

이 상태로 29.0초 걸린 생성이 `SET maintenance_work_mem = '256MB'` 뒤에는 7.7초였다. 대량으로 넣을 때는 데이터를 먼저 넣고 인덱스를 나중에 만들고, 그 세션에서만 이 값을 올린다. 마지막으로 임베딩 모델을 바꾸면 차원이 달라져서 `ERROR:  expected 64 dimensions, not 3` 같은 에러로 바로 드러난다. 차원이 같은 모델로 바꿨다면 에러 없이 조용히 엉뚱한 결과가 나오니, 모델을 바꿀 때는 새 컬럼에 전부 다시 임베딩하고 한 번에 넘어간다.

## 정리

벡터 DB는 뜻을 좌표로 바꿔 저장하고, 질문과 가까운 좌표를 빠르게 찾아 주는 데이터베이스다. 모두를 비교하는 대신 HNSW 같은 그래프 인덱스로 가까운 쪽을 따라가며 찾는다. 정확도는 조금 내주고 속도를 크게 얻는 방식이다. LLM에 필요한 문서를 찾아 붙여 주는 RAG가 지금 가장 흔한 쓰임새다.

## 면접에서 나올 만한 질문

### 벡터 DB는 왜 필요한가요? 키워드 검색과 무엇이 다른가요?

키워드 검색은 글자가 겹치는지를 보기 때문에 "강아지 사료"로 "반려견 먹이"를 찾지 못한다. 벡터 DB는 임베딩 모델로 텍스트를 의미 공간의 좌표로 바꿔 저장하고, 질문 벡터와 가까운 것을 찾는다. 그래서 표현이 달라도 뜻이 가까우면 찾는다. 반대로 고유명사나 코드처럼 정확히 일치해야 하는 검색은 키워드 검색이 낫기 때문에 둘을 섞어 쓰는 경우가 많다.

### 임베딩이란 무엇인가요?

텍스트(또는 이미지 등)를 고정 길이의 숫자 벡터로 바꾼 것이다. 모델이 뜻이 비슷한 입력에 비슷한 벡터를 내도록 학습되어 있어서, 벡터 사이 거리가 의미의 가까움을 나타낸다. 저장할 때와 검색할 때 반드시 같은 모델을 써야 좌표계가 맞는다.

### 코사인 유사도, 내적, 유클리드 거리는 어떻게 다른가요?

코사인 유사도는 두 벡터의 방향만 비교하고 길이는 무시한다. 내적은 방향과 길이를 함께 반영하고, 유클리드 거리는 두 점 사이의 직선 거리다. 벡터 길이를 1로 정규화하면 세 값이 같은 순서를 만들기 때문에, 보통 정규화한 뒤 계산이 가벼운 내적을 쓴다. 어떤 거리를 쓸지는 임베딩 모델이 학습된 방식을 따른다.

### 근사 최근접 탐색(ANN)은 왜 쓰고, 무엇을 포기하나요?

모든 벡터와 비교하는 정확한 탐색은 데이터 수 × 차원만큼 계산이 필요해서 수백만 건 이상에서는 느리다. ANN은 인덱스를 이용해 일부만 비교해서 훨씬 빠르게 찾는 대신, 진짜 가장 가까운 것을 가끔 놓친다. 이 정확도를 재현율(recall)로 재고, 인덱스 파라미터로 속도와 맞바꾼다.

### HNSW는 어떻게 동작하나요?

벡터마다 가까운 이웃들을 연결한 그래프를 여러 층으로 만든다. 위층은 점이 적어 멀리 건너뛰고, 아래층으로 내려오며 질문에 더 가까운 이웃으로 계속 이동하다가 더 가까워지지 않으면 멈춘다. `M`(연결할 이웃 수)과 `ef`(탐색 중 유지할 후보 수)를 키우면 정확해지지만 메모리와 시간이 늘어난다.

### HNSW와 IVF는 어떻게 다르고 언제 무엇을 고르나요?

HNSW는 그래프 탐색이라 검색이 빠르고 재현율이 높지만 메모리를 많이 쓰고 인덱스 생성이 느리다. IVF는 벡터를 클러스터로 나눠 가까운 클러스터 몇 개만 뒤지는 방식이라 메모리가 적고 빨리 만들어지지만, 같은 재현율을 내려면 더 많이 뒤져야 할 수 있다. 메모리가 넉넉하고 지연 시간이 중요하면 HNSW, 데이터가 매우 크면 IVF에 PQ 압축을 더하는 식으로 고른다.

### RAG의 검색 품질을 높이려면 무엇을 보나요?

문서를 적절한 크기로 나누는 청크 전략, 같은 임베딩 모델 사용, 키워드 검색을 섞는 하이브리드 검색, 후보를 넉넉히 뽑은 뒤 cross-encoder로 다시 순위를 매기는 리랭킹, 메타데이터 필터를 먼저 거는지 나중에 거는지를 본다. 그리고 recall@k 같은 지표로 바꾼 설정을 비교한다.
