## 가깝다는 건 어떻게 재나

두 점 사이의 직선 거리(유클리드 거리)를 써도 되지만, 임베딩에서는 코사인 유사도를 더 많이 쓴다. 위 그림의 두 번째 단계에서 본 화살표의 방향이 얼마나 비슷한지를 재는 값이다. 같은 방향이면 1, 직각이면 0, 정반대면 −1이 나온다.

```ts
function cosineSimilarity(a: number[], b: number[]) {
  let dot = 0, normA = 0, normB = 0;
  for (let i = 0; i < a.length; i++) {
    dot += a[i] * b[i];
    normA += a[i] * a[i];
    normB += b[i] * b[i];
  }
  return dot / (Math.sqrt(normA) * Math.sqrt(normB));
}
```

길이를 1로 맞춰 둔(정규화한) 벡터끼리는 코사인 유사도와 내적이 같아진다. 그래서 많은 시스템이 저장할 때 미리 정규화해 두고 계산이 가벼운 내적을 쓴다.

## 하나하나 다 재면 느리다

가장 확실한 방법은 질문 벡터를 저장된 모든 벡터와 하나씩 비교하는 것이다. 문서가 천 개라면 이걸로 충분하다. 문제는 규모다. 1536차원 벡터가 1억 개 있으면 질문 하나에 곱셈만 1,500억 번이 넘는다. 검색 한 번에 이걸 기다릴 수는 없다.

그래서 실제 벡터 DB는 근사 최근접 탐색(ANN, Approximate Nearest Neighbor)을 쓴다. 정답을 아주 가끔 놓치는 대신 비교 횟수를 크게 줄인다. 그중 가장 널리 쓰이는 방식이 HNSW다.

## 지름길이 있는 그래프, HNSW

HNSW는 점마다 가까운 이웃 몇 개를 선으로 이어 그래프를 만들어 둔다. 검색할 때는 아무 점에서나 출발해서, 이웃 중 질문에 더 가까운 쪽으로 계속 옮겨 간다. 더 가까워지는 이웃이 없으면 거기서 멈추고, 그 주변을 답으로 돌려준다. 낯선 동네에서 목적지 방향으로 한 블록씩 걸어가는 것과 비슷하다.

## 정확도와 속도를 맞바꾸는 손잡이

근사 탐색이라 가끔 진짜 가장 가까운 점을 놓친다. 진짜 정답 중 몇 개를 찾았는지를 재현율(recall)이라고 하고, 이 값과 속도는 서로 맞바꾼다. HNSW에서는 점마다 이웃을 몇 개까지 이을지(M), 검색할 때 후보를 몇 개나 들고 다닐지(ef) 같은 값으로 조절한다. 이웃을 많이 잇고 후보를 많이 들고 다닐수록 정확해지지만 메모리와 시간이 더 든다.

## 실제로는 어디에 쓰나: RAG

## 직접 붙여 볼 때

전용 벡터 DB(Pinecone, Qdrant, Milvus, Weaviate 등)도 많지만, 이미 PostgreSQL을 쓰고 있다면 pgvector 확장으로 시작하는 경우가 많다. 테이블에 벡터 컬럼을 하나 더 두고, HNSW 인덱스를 거는 정도면 된다. `<=>`는 코사인 거리 연산자다.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE docs (
  id        bigserial PRIMARY KEY,
  content   text,
  embedding vector(1536)
);

CREATE INDEX ON docs USING hnsw (embedding vector_cosine_ops);

SELECT content
FROM docs
ORDER BY embedding <=> $1   -- $1: 질문 벡터
LIMIT 3;
```

실제로 붙여 보면 인덱스보다 데이터를 어떻게 넣느냐가 결과를 더 크게 좌우한다. 긴 문서는 문단 단위 정도로 잘라서(청크) 넣어야 검색이 정확해지고, 너무 잘게 자르면 앞뒤 맥락이 사라진다. 저장할 때와 검색할 때 같은 임베딩 모델을 써야 한다는 것도 잊기 쉽다. 제품명이나 에러 코드처럼 글자가 정확히 맞아야 하는 검색은 여전히 키워드 검색이 강해서, 둘을 섞는 하이브리드 검색도 많이 쓴다.

## 정리

벡터 DB는 뜻을 좌표로 바꿔 저장하고, 질문과 가까운 좌표를 빠르게 찾아 주는 데이터베이스다. 모두를 비교하는 대신 HNSW 같은 그래프 인덱스로 가까운 쪽을 따라가며 찾는다. 정확도는 조금 내주고 속도를 크게 얻는 방식이다. LLM에 필요한 문서를 찾아 붙여 주는 RAG가 지금 가장 흔한 쓰임새다.
