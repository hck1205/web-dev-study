쇼핑몰에 할인 이벤트가 걸린 날, DB 서버의 CPU가 90%에 붙어서 내려오지 않는다. 느린 쿼리를 열어 보면 대부분 `SELECT`다. 상품 목록, 주문 내역, 마이페이지. 쓰기는 많지 않은데 읽기가 서버 한 대를 다 먹고 있다. 몇 달 뒤에는 다른 문제가 온다. `orders` 테이블이 수억 건이 되자 1년 지난 주문을 지우는 새벽 배치가 몇 시간씩 돌고, 그동안 복제본이 뒤처진다.

둘 다 "DB 한 대로는 모자라다"는 말로 들리지만 처방이 다르다. 읽기가 많으면 같은 데이터를 여러 대에 복사해 읽기를 나눈다(복제). 테이블 하나가 너무 크면 한 DB 안에서 테이블을 조각으로 나눈다(파티셔닝). 쓰기와 데이터 자체가 한 대를 넘으면 데이터를 여러 DB 서버에 나눠 담는다(샤딩). 뒤로 갈수록 강력하지만 되돌리기 어렵고 앱이 알아야 할 것이 늘어난다. 이 글은 이 순서대로 직접 돌려 보며 각 단계가 무엇을 풀고 무엇을 새로 만드는지 정리한다.

기준은 Ubuntu 24.04 LTS의 PostgreSQL 16(16.15)이다. 복제 실험은 한 장비에 프라이머리(5441 포트)와 스탠바이(5442 포트)를 따로 띄워서 했고, 아래 출력은 모두 그 환경에서 실제로 나온 것이다. 그래서 주소가 `127.0.0.1`로 찍혀 있다. 시간(ms)은 장비마다 다르니 자릿수만 보면 된다. 인덱스와 쿼리 자체를 고치는 이야기는 [인덱스 글](/posts/db-index)과 [쿼리 튜닝 글](/posts/sql-query-tuning)에 있다.

## 실험에 쓸 두 테이블

글 전체에서 회원(`users`)과 주문(`orders`) 두 테이블을 쓴다. 처음에는 몇 줄뿐이다.

```sql
-- 회원
CREATE TABLE users (
  id         bigint PRIMARY KEY,
  email      text NOT NULL UNIQUE,
  name       text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

-- 주문: 누가(user_id), 얼마를(amount), 언제(created_at)
CREATE TABLE orders (
  id         bigint PRIMARY KEY,
  user_id    bigint NOT NULL REFERENCES users(id),
  amount     integer NOT NULL,
  status     text NOT NULL,
  created_at timestamptz NOT NULL
);

INSERT INTO users VALUES
  (1, 'minji@example.com',   '민지', '2026-01-03'),
  (2, 'junho@example.com',   '준호', '2026-02-11'),
  (3, 'seoyeon@example.com', '서연', '2026-03-20');

INSERT INTO orders VALUES
  (101, 1, 32000, 'paid',    '2026-09-30 23:10+09'),
  (102, 2, 15000, 'paid',    '2026-10-01 09:00+09'),
  (103, 1,  8900, 'shipped', '2026-10-02 14:30+09');

SELECT * FROM orders ORDER BY id;
```

```text
 id  | user_id | amount | status  |       created_at
-----+---------+--------+---------+------------------------
 101 |       1 |  32000 | paid    | 2026-09-30 23:10:00+09
 102 |       2 |  15000 | paid    | 2026-10-01 09:00:00+09
 103 |       1 |   8900 | shipped | 2026-10-02 14:30:00+09
(3 rows)
```

DB의 시간대는 `ALTER DATABASE shop SET timezone = 'Asia/Seoul'`로 맞춰 두었다. 그래서 `+09`로 찍힌다.

## 나누기 전에 한 대부터 키운다

서버를 늘리기 전에 볼 것이 있다. CPU를 먹는 쿼리가 인덱스 없이 테이블 전체를 읽고 있는 경우가 생각보다 많다. 쿼리 하나에 인덱스 하나를 붙여 CPU가 절반으로 떨어지는 일이 복제본 두 대를 붙이는 것보다 싸다. `pg_stat_statements`로 총 실행 시간이 큰 쿼리부터 보고, 같은 결과를 반복해서 읽는 화면이면 [캐시](/posts/caching-strategies)를 앞에 둔다. 연결이 수백 개씩 열려 있으면 커넥션 풀(PgBouncer 같은)로 줄인다. PostgreSQL은 연결마다 프로세스를 하나씩 띄우기 때문에 연결 수 자체가 메모리와 CPU를 쓴다.

그래도 모자라면 서버를 더 큰 것으로 바꾼다(수직 확장, scale-up). 앱 코드를 하나도 고치지 않아도 된다는 게 가장 큰 장점이다. 클라우드 관리형 DB는 vCPU 수십~백여 개, 메모리 1TB가 넘는 인스턴스까지 있어서 생각보다 멀리 간다.

한계도 분명하다. 크기를 두 배로 올리면 값도 대략 두 배씩 오르는데, 성능은 그만큼 오르지 않는 구간이 온다. 잠금 경합이나 WAL 쓰기처럼 코어를 늘려도 나아지지 않는 병목이 있어서다. 서버를 바꾸는 동안 짧게라도 멈춰야 하고, 무엇보다 여전히 한 대다. 그 한 대가 죽으면 서비스 전체가 멈춘다. 그래서 수직 확장을 하더라도 복제본 하나는 장애 대비로 붙여 두는 게 보통이고, 그 복제본이 다음 단계의 출발점이 된다.

## 복제본은 WAL을 받아 다시 실행한다

PostgreSQL은 데이터 파일을 고치기 전에 "무엇을 어떻게 바꿀지"를 WAL(Write-Ahead Log, 먼저 쓰는 로그)에 먼저 적는다. 서버가 갑자기 꺼져도 WAL만 남아 있으면 다시 켤 때 그 기록을 재생해 복구한다. 스트리밍 복제는 이 WAL을 다른 서버에 실시간으로 보내서, 받은 서버가 똑같이 재생하게 하는 것이다.

쓰기를 받는 쪽이 프라이머리, WAL을 받아 재생하는 쪽이 스탠바이(복제본, 레플리카)다. 프라이머리의 walsender 프로세스가 WAL을 보내고, 스탠바이의 walreceiver가 받아 디스크에 쓰고, startup 프로세스가 그걸 재생한다. 스탠바이는 재생하는 동안에도 읽기 쿼리를 받을 수 있다(hot standby, 16에서는 기본으로 켜져 있다). 쓰기를 보내면 거절한다.

```text
INSERT INTO orders VALUES (104,3,12000,'paid',now());
ERROR:  cannot execute INSERT in a read-only transaction
```

SQL 문장을 다시 실행하는 게 아니라 "몇 번 페이지의 몇 바이트를 이렇게 바꿔라" 수준의 물리적인 변경을 재생한다. 그래서 스탠바이는 프라이머리와 바이트 단위로 같은 복사본이 되고, 메이저 버전과 아키텍처가 같아야 하며, 일부 테이블만 골라 복제할 수는 없다. 테이블을 골라 복제하거나 다른 버전으로 보내야 할 때는 논리 복제(`CREATE PUBLICATION` / `CREATE SUBSCRIPTION`)를 쓴다.

## 스탠바이를 하나 붙여 보기

프라이머리가 `10.0.0.11`, 스탠바이가 `10.0.0.12`인 Ubuntu 서버 두 대라고 하자. 둘 다 `apt install postgresql`로 16이 깔려 있다. 먼저 프라이머리에서 복제 전용 계정을 만들고 접속을 허용한다.

```bash
# [프라이머리] 복제 전용 계정 (REPLICATION 권한만, 테이블 권한은 없다)
sudo -u postgres psql -c "CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'change-me'"

# [프라이머리] 다른 서버에서 접속을 받도록 (기본값은 localhost만)
sudo sed -i "s/^#listen_addresses = 'localhost'/listen_addresses = '*'/" /etc/postgresql/16/main/postgresql.conf

# [프라이머리] 스탠바이 주소에서 오는 복제 연결만 허용
echo "host replication replicator 10.0.0.12/32 scram-sha-256" | sudo tee -a /etc/postgresql/16/main/pg_hba.conf

# [프라이머리] listen_addresses는 재시작해야 적용된다
sudo systemctl restart postgresql@16-main
```

`wal_level = replica`와 `max_wal_senders = 10`은 16의 기본값이라 따로 바꿀 필요가 없다. 방화벽이 있다면 5432 포트를 스탠바이 주소에만 열어 둔다.

스탠바이에서는 비어 있는 데이터 디렉터리에 프라이머리의 전체 복사본을 받는다. `pg_basebackup`이 그 일을 한다.

```bash
# [스탠바이] 서버를 멈추고 기존 데이터 디렉터리를 치운다 (새로 깐 서버라 비어 있어도 된다)
sudo systemctl stop postgresql@16-main
sudo -u postgres mv /var/lib/postgresql/16/main /var/lib/postgresql/16/main.old

# [스탠바이] 프라이머리 전체를 복사한다
#   -R: 스탠바이 설정(standby.signal, primary_conninfo)을 자동으로 써 준다
#   -X stream: 복사하는 동안 생긴 WAL도 같이 받는다
#   -C -S standby1: 프라이머리에 복제 슬롯 standby1을 만든다
sudo -u postgres pg_basebackup -h 10.0.0.11 -U replicator \
  -D /var/lib/postgresql/16/main -R -X stream -C -S standby1 -P

# [스탠바이] 시작하면 스탠바이로 뜬다
sudo systemctl start postgresql@16-main

# [스탠바이] 스탠바이인지 확인 (t면 복구, 즉 재생 중)
sudo -u postgres psql -c "SELECT pg_is_in_recovery()"
```

```text
 pg_is_in_recovery
-------------------
 t
(1 row)
```

프라이머리에서는 `pg_stat_replication` 뷰로 붙어 있는 스탠바이를 본다.

```bash
# [프라이머리] 붙어 있는 스탠바이 목록
sudo -u postgres psql -x -c "SELECT * FROM pg_stat_replication"
```


볼 줄은 세 군데다. `state`가 `streaming`이면 실시간으로 받고 있다. `catchup`이면 아직 따라잡는 중이다. `sent_lsn`부터 `replay_lsn`까지 네 값은 WAL의 위치(LSN, Log Sequence Number)인데, 바로 다음 절에서 본다. `sync_state`가 `async`면 비동기 복제다. 기본값이 비동기다.

복제 슬롯(`-S standby1`)은 "이 스탠바이가 아직 안 받아 간 WAL은 지우지 마라"는 표시다. 스탠바이가 잠깐 끊겨도 다시 붙어서 이어 받을 수 있게 해 준다. 대신 스탠바이가 며칠 죽어 있으면 프라이머리에 WAL이 계속 쌓인다. 16의 `max_slot_wal_keep_size` 기본값은 `-1`(제한 없음)이라 그대로 두면 프라이머리 디스크가 가득 차서 프라이머리까지 멈춘다. 디스크 여유에 맞춰 값을 정하고, `pg_replication_slots`의 `active`가 `f`인 슬롯이 있는지 감시한다.

```sql
-- 슬롯 상태. active = f 로 오래 남아 있으면 WAL이 쌓이고 있다
SELECT slot_name, active, restart_lsn, wal_status FROM pg_replication_slots;
```

```text
 slot_name | active | restart_lsn | wal_status
-----------+--------+-------------+------------
 standby1  | t      | 0/7D49D8F0  | reserved
(1 row)
```

## 방금 결제한 주문이 안 보인다

복제본을 붙이고 읽기를 그쪽으로 보내면 프라이머리의 CPU가 내려간다. 그런데 이상한 문의가 들어온다. 결제를 마치고 주문 내역으로 넘어갔더니 방금 주문이 없다고 한다. 새로고침하면 보인다.

같은 장비에서 이 틈은 보통 1ms도 안 돼서 눈으로 보기 어렵다. 그래서 스탠바이에서 `pg_wal_replay_pause()`로 재생을 잠깐 세워 놓고 재현했다.

```sql
-- [스탠바이] 재생을 잠깐 멈춘다 (실험용. 운영에서 쓰면 그만큼 뒤처진다)
SELECT pg_wal_replay_pause();

-- [프라이머리] 주문을 쓰고, 그 직후의 WAL 위치를 본다
INSERT INTO orders VALUES (104, 3, 12000, 'paid', '2026-10-17 10:00+09');
SELECT pg_current_wal_lsn();
```

```text
INSERT 0 1

--------------------

(1 row)
```

```sql
-- [스탠바이] 방금 쓴 주문을 찾는다
SELECT id, amount FROM orders WHERE id = 104;

-- [스탠바이] 어디까지 받았고 어디까지 재생했나
SELECT pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn(), pg_is_wal_replay_paused();
```

```text
 id | amount
----+--------
(0 rows)

 pg_last_wal_receive_lsn | pg_last_wal_replay_lsn | pg_is_wal_replay_paused
-------------------------+------------------------+-------------------------
 0/3434AA8               | 0/34349A8              | t
(1 row)
```

받은 위치는 `0/3434AA8`로 프라이머리와 같은데 재생한 위치는 `0/34349A8`에 멈춰 있다. WAL은 이미 스탠바이 디스크에 와 있지만 재생 전이라 쿼리에는 안 보인다. 프라이머리 쪽에서 같은 상황을 보면 이렇다.

```sql
-- [프라이머리] 스탠바이가 얼마나 뒤처졌나
SELECT application_name, state, sent_lsn, write_lsn, flush_lsn, replay_lsn,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS replay_gap_bytes,  -- 보낸 것과 재생한 것의 차이 (바이트)
       replay_lag, sync_state
FROM pg_stat_replication;
```

```text
 application_name |   state   | sent_lsn  | write_lsn | flush_lsn | replay_lsn | replay_gap_bytes |   replay_lag    | sync_state
------------------+-----------+-----------+-----------+-----------+------------+------------------+-----------------+------------
 walreceiver      | streaming | 0/3434AA8 | 0/3434AA8 | 0/3434AA8 | 0/34349A8  |              256 | 00:00:00.000817 | async
(1 row)
```

`replay_gap_bytes`가 256으로, 주문 한 건 분량의 WAL이 재생되지 않고 남아 있다. 눈여겨볼 것은 `replay_lag`다. 재생이 멈춰 있는데도 0.0008초로 찍혔다. 이 값은 최근에 재생이 끝난 WAL이 얼마나 걸렸는지를 재는 값이라, 재생이 아예 멈추거나 쓰기가 뜸하면 실제 상황보다 작게 보인다. 그래서 지연 감시는 시간과 바이트 차이를 같이 건다.

스탠바이에서 흔히 쓰는 다른 확인법에도 함정이 있다.

```sql
-- [스탠바이] 마지막으로 재생한 트랜잭션이 얼마 전 것인가
SELECT now() - pg_last_xact_replay_timestamp() AS replay_delay;
```

```text
  replay_delay
-----------------
 00:00:01.048564
(1 row)
```

이 출력을 찍을 때 스탠바이는 완전히 따라잡은 상태였다(받은 위치와 재생 위치가 같았다). 그런데도 1초로 나온 건 프라이머리에 1초 동안 쓰기가 없었기 때문이다. 쓰기가 없는 새벽에는 지연이 없어도 이 값이 몇 분씩 커진다. 이 값으로 경보를 걸면 새벽마다 거짓 경보가 울린다.

## 쓴 사람에게는 쓴 것을 보여 준다

사용자가 기대하는 건 모든 데이터가 즉시 맞는 것이 아니다. 자기가 방금 쓴 것만큼은 바로 보이는 것이다(read-your-writes). 남이 쓴 리뷰가 1초 늦게 보이는 건 아무도 모르지만, 내 주문이 사라지는 건 바로 문의가 된다. 해결책은 몇 가지가 있고 섞어서 쓴다.

가장 단순한 건 쓰기 직후 잠깐 프라이머리에서 읽는 것이다. 쓰기를 한 사용자의 세션에 "5초 동안 프라이머리"라는 표시를 남기고, 그동안 그 사용자의 읽기만 프라이머리로 보낸다. 5초는 평소 복제 지연보다 넉넉히 큰 값으로 잡는다. 지연이 그보다 커지는 순간에는 여전히 틀릴 수 있다.

결제 결과, 잔액, 재고처럼 틀리면 안 되는 화면은 아예 항상 프라이머리에서 읽는다. 복제본은 목록, 검색, 통계처럼 조금 낡아도 되는 읽기에만 쓴다. 복제본을 붙인다고 모든 읽기를 넘기는 게 아니라 읽기마다 얼마나 낡아도 되는지를 정하는 일이다.

더 정확한 방법은 LSN을 기억하는 것이다. 쓰기를 커밋한 뒤 프라이머리의 WAL 위치를 받아 세션에 넣어 두고, 복제본에서 읽기 전에 그 위치까지 재생됐는지 확인한다. 아직이면 잠깐 기다리거나 프라이머리로 보낸다. PostgreSQL 16에는 특정 LSN까지 기다리는 내장 명령이 없어서 앱이 이렇게 물어본다.

```sql
-- [프라이머리] 쓰기 커밋 직후. 이 값을 세션(쿠키, Redis 등)에 저장한다
SELECT pg_current_wal_lsn();        -- 0/3434AA8

-- [스탠바이] 읽기 전에 확인. f면 기다리거나 프라이머리에서 읽는다
SELECT pg_last_wal_replay_lsn() >= '0/3434AA8'::pg_lsn AS caught_up;
```

재생을 멈춘 상태에서는 `f`였고, `pg_wal_replay_resume()`으로 재생을 다시 켠 뒤에는 `t`가 나왔다.

```text
 caught_up
-----------
 f
(1 row)

 caught_up
-----------
 t
(1 row)
```

복제본이 여러 대일 때는 다른 문제도 있다. 새로고침할 때마다 다른 복제본에 붙으면, 덜 뒤처진 복제본에서 본 댓글이 더 뒤처진 복제본에서는 사라진다. 시간이 거꾸로 가는 것처럼 보인다. 한 사용자를 한 복제본에 고정하면(사용자 id로 고르기) 적어도 시간이 거꾸로 가지는 않는다(monotonic reads).

`synchronous_commit`만 바꿔서는 동기 복제가 되지 않는다. 기다릴 스탠바이를 `synchronous_standby_names`에 적어야 한다. 비어 있으면(기본값) `on`도 자기 디스크까지만 기다린다. 실험 환경에서 스탠바이 하나를 동기로 지정했다.

```sql
-- [프라이머리] walreceiver라는 이름의 스탠바이 1대를 동기로 기다린다
ALTER SYSTEM SET synchronous_standby_names = 'FIRST 1 (walreceiver)';
SELECT pg_reload_conf();

SELECT application_name, sync_state FROM pg_stat_replication;
```

```text
 application_name | sync_state
------------------+------------
 walreceiver      | sync
(1 row)
```

이름은 스탠바이의 `primary_conninfo`에 있는 `application_name`이고, 따로 주지 않으면 `walreceiver`다. 실무에서는 스탠바이마다 `application_name=standby1`처럼 이름을 붙인다.

이 상태에서 스탠바이를 꺼 보면 동기 복제의 대가가 바로 보인다.

```bash
# [스탠바이] 서버를 내린다
sudo systemctl stop postgresql@16-main
```

```sql
-- [프라이머리] 주문을 쓰면 응답이 오지 않는다
INSERT INTO orders VALUES (105, 2, 5000, 'paid', '2026-10-17 10:05+09');
```

`INSERT`가 돌아오지 않았다. 다른 세션에서 보면 그 연결이 `SyncRep`을 기다리고 있다.

```sql
-- [프라이머리, 다른 세션] 무엇을 기다리고 있나
SELECT pid, wait_event_type, wait_event, state, left(query, 40)
FROM pg_stat_activity WHERE wait_event = 'SyncRep';
```

```text
 pid  | wait_event_type | wait_event | state  |                   left
------+-----------------+------------+--------+------------------------------------------
 3158 | IPC             | SyncRep    | active | INSERT INTO orders VALUES (105,2,5000,'p
(1 row)
```

`statement_timeout = '3s'`을 걸어 두었는데도 끊기지 않았다. 커밋 기록은 이미 프라이머리 디스크에 내려갔고, 남은 건 스탠바이 확인을 기다리는 일이라 문장 시간 제한이 적용되지 않는다. `pg_cancel_backend(3158)`로 직접 취소하니 이렇게 나왔다.

```text

DETAIL:  The transaction has already committed locally, but might not have been replicated to the standby.
INSERT 0 1
```

경고 문구 그대로다. 프라이머리에는 이미 커밋됐다. 그래서 이 주문은 `SELECT`로 조회된다. 앱 입장에서는 실패처럼 보였던 쓰기가 사실은 들어가 있는 셈이라, 재시도하면 중복 주문이 생길 수 있다. 주문 id를 앱에서 미리 정해 두면(뒤에서 볼 ID 생성) 재시도해도 같은 id라 중복을 막을 수 있다.

`FIRST 1 (standby1)`처럼 스탠바이 한 대만 동기로 지정하면 그 서버가 죽거나 네트워크가 끊기는 순간 프라이머리의 모든 커밋이 멈춘다. 프라이머리를 지키려고 붙인 서버가 프라이머리를 세우는 것이다. 동기 복제를 쓸 거면 스탠바이를 두 대 이상 두고 `ANY 1 (standby1, standby2)`처럼 "둘 중 아무나 하나"를 기다리게 한다. 이미 멈췄다면 `ALTER SYSTEM SET synchronous_standby_names = ''`와 `SELECT pg_reload_conf()`로 비동기로 되돌리면 기다리던 커밋들이 풀린다. 또 `synchronous_commit`은 트랜잭션마다 바꿀 수 있으니, 결제처럼 중요한 쓰기만 `SET LOCAL synchronous_commit = on`으로 기다리고 나머지는 `local`로 두는 방법도 있다.

## 복제본에서 긴 쿼리가 끊긴다

복제본에서 무거운 통계 쿼리를 돌리면 이런 에러를 만날 수 있다. 스탠바이의 `max_standby_streaming_delay`를 2초로 줄이고, 스탠바이에서 오래 걸리는 트랜잭션을 여는 동안 프라이머리에서 행을 고치고 `VACUUM`을 돌려서 재현했다.

```text
ERROR:  canceling statement due to conflict with recovery
DETAIL:  User query might have needed to see row versions that must be removed.
```

프라이머리의 `VACUUM`은 아무도 안 보는 옛 행 버전을 지우고, 그 기록도 WAL로 스탠바이에 간다. 그런데 스탠바이에서 돌고 있는 쿼리는 그 옛 버전을 봐야 할 수 있다. 프라이머리는 스탠바이의 쿼리를 모른다. 스탠바이는 재생을 미루고 쿼리를 기다리다가, `max_standby_streaming_delay`(기본 30초)를 넘으면 쿼리를 취소하고 재생을 이어 간다. 쿼리를 무한정 기다리면 복제 지연이 끝없이 커지기 때문이다.

고르는 방법은 두 가지다. `hot_standby_feedback = on`을 켜면 스탠바이가 "나 아직 이 버전 본다"고 프라이머리에 알려서 프라이머리가 그 행을 지우지 않는다. 쿼리는 덜 끊기지만 프라이머리에 지우지 못한 행이 쌓여 테이블이 부푼다(bloat). 다른 방법은 분석용 복제본을 따로 두고 그쪽만 `max_standby_streaming_delay`를 크게 잡는 것이다. 그 복제본은 쿼리가 길어지면 몇 분씩 뒤처지지만 분석에는 상관없다. 화면용 복제본은 짧게 둔다.

## MySQL은 binlog로 복제한다

MySQL 8의 복제도 구조는 비슷하지만 보내는 것이 다르다. InnoDB의 내부 로그(redo log)가 아니라 바이너리 로그(binlog)라는 별도의 변경 기록을 보낸다. 8.0의 기본 형식(`binlog_format = ROW`)은 바뀐 행의 전후 값을 담는다. 레플리카는 받은 binlog를 relay log에 쓰고, SQL 스레드(8.0에서는 여러 개의 적용 스레드)가 그걸 다시 실행한다. 행 단위의 논리적인 기록이라 버전이 조금 달라도 복제가 되고, 필터로 일부 DB만 복제할 수 있다.

GTID(Global Transaction ID)를 켜면(`gtid_mode = ON`) 트랜잭션마다 `서버UUID:번호` 형태의 id가 붙는다. 장애 조치 때 새 프라이머리로 갈아탈 때 "binlog 파일 몇 번의 몇 바이트부터"를 계산할 필요 없이 "아직 안 받은 GTID부터"로 이어 받을 수 있어서 요즘은 거의 켜고 쓴다. 지연은 `SHOW REPLICA STATUS`의 `Seconds_Behind_Source`로 보는데, PostgreSQL의 타임스탬프 방식과 비슷하게 상황에 따라 실제와 다르게 보일 수 있다. 기다리는 쪽으로는 semi-synchronous 복제가 있다. 레플리카가 받았다고 답할 때까지 커밋 응답을 미루고, 시간 안에 답이 없으면 비동기로 내려간다.

## 프라이머리가 죽으면 누가 이어받나

복제본이 있다고 장애가 자동으로 넘어가지는 않는다. 누군가 스탠바이를 프라이머리로 올려야 한다(승격, promote).

```bash
# [스탠바이] 프라이머리로 승격한다
sudo -u postgres psql -c "SELECT pg_promote()"

# 이제 복구 상태가 아니다 (f)
sudo -u postgres psql -c "SELECT pg_is_in_recovery()"
```

손으로 하면 사람이 깨어나는 시간만큼 멈춘다. 그래서 보통 Patroni 같은 도구를 쓴다. Patroni는 각 DB 서버 옆에서 돌면서 etcd나 Consul 같은 합의 저장소에 "지금 프라이머리는 나"라는 잠금(리더 키)을 일정 시간마다 갱신한다. 프라이머리가 죽어 잠금이 만료되면 남은 스탠바이 중 가장 많이 받은 쪽이 잠금을 잡고 승격한다. 관리형 서비스(RDS Multi-AZ, Aurora, Cloud SQL 등)는 이 과정을 대신 해 준다.

가장 위험한 장애는 프라이머리가 두 대가 되는 것이다(split-brain). 옛 프라이머리가 죽은 게 아니라 네트워크만 끊겼다면, 스탠바이가 승격된 뒤에도 옛 프라이머리는 자기가 프라이머리인 줄 알고 쓰기를 받는다. 두 서버에 서로 다른 주문이 쌓이고, 나중에 합칠 방법이 없다. Patroni는 리더 키를 갱신하지 못한 프라이머리가 스스로 읽기 전용으로 내려가게 하고, 그래도 불안하면 watchdog으로 서버를 강제로 재부팅하게 한다. 이렇게 옛 프라이머리를 확실히 끊는 일을 펜싱(fencing)이라고 한다. 살아난 옛 프라이머리는 `pg_rewind`로 새 프라이머리와 갈라진 부분을 되감은 뒤 스탠바이로 다시 붙인다.

앱은 프라이머리가 바뀌어도 따라가야 한다. 가상 IP나 DNS, HAProxy 같은 프록시를 앞에 두는 방법이 있고, libpq 기반 드라이버라면 연결 문자열에 서버를 여러 개 적고 쓰기 가능한 쪽만 고르게 할 수도 있다.

```bash
# 두 서버 중 쓰기 가능한(프라이머리) 쪽에 붙는다
psql "postgresql://app@10.0.0.11:5432,10.0.0.12:5432/shop?target_session_attrs=read-write"
```

비동기 복제에서 장애 조치를 하면 프라이머리가 스탠바이에 보내지 못한 마지막 커밋은 사라진다. 얼마나 잃어도 되는지(RPO)와 얼마나 멈춰도 되는지(RTO)를 먼저 정하고, 그 답에 맞춰 동기 여부와 스탠바이 대수를 정한다.

## 주문 테이블을 달마다 나눈다

읽기는 복제본으로 나눴는데, `orders`가 수억 건이 되자 다른 문제가 생긴다. 1년 지난 주문을 지우는 배치는 `DELETE`로 수천만 건을 지운다. 지운 행은 바로 사라지지 않고 죽은 행으로 남아 `VACUUM`이 치울 때까지 자리를 차지한다. 그 와중에 WAL이 쏟아져서 복제본이 뒤처진다. 인덱스도 수억 건짜리 하나라 다시 만들려면 몇 시간이다.

파티셔닝은 한 DB 안에서 큰 테이블을 여러 개의 작은 테이블(파티션)로 나누는 것이다. 앱은 여전히 `orders` 하나에 쿼리를 보내고, PostgreSQL이 조건을 보고 해당하는 파티션으로 보낸다. PostgreSQL 10부터 들어간 선언적 파티셔닝(`PARTITION BY`)을 쓴다. 주문은 날짜 범위로 조회하고 날짜 기준으로 지우니 `created_at`의 범위(RANGE)로 나눈다.

처음 만들 때 대부분 한 번은 이 에러를 본다.

```sql
CREATE TABLE orders (
  id         bigint PRIMARY KEY,          -- id만으로 기본 키
  created_at timestamptz NOT NULL
) PARTITION BY RANGE (created_at);
```

```text
ERROR:  unique constraint on partitioned table must include all partitioning columns
DETAIL:  PRIMARY KEY constraint on table "orders" lacks column "created_at" which is part of the partition key.
```

PostgreSQL의 고유 인덱스는 파티션마다 따로 있다. 9월 파티션의 인덱스는 10월 파티션에 같은 id가 있는지 모른다. 그래서 기본 키와 UNIQUE에는 파티션 키가 들어가야 "같은 파티션 안에서만 확인하면 전체에서 고유하다"가 성립한다. 기본 키를 `(id, created_at)`으로 바꾼다.

```sql
-- 부모 테이블. 데이터는 직접 담지 않고 파티션으로 보낸다
CREATE TABLE orders (
  id         bigint      NOT NULL,
  user_id    bigint      NOT NULL,
  amount     integer     NOT NULL,
  status     text        NOT NULL,
  created_at timestamptz NOT NULL,
  PRIMARY KEY (id, created_at)          -- 파티션 키를 포함해야 한다
) PARTITION BY RANGE (created_at);

-- 달마다 하나씩. FROM은 포함, TO는 포함하지 않는다
CREATE TABLE orders_2026_01 PARTITION OF orders FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE orders_2026_02 PARTITION OF orders FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
-- ... 3월부터 9월까지 같은 식으로 ...
CREATE TABLE orders_2026_10 PARTITION OF orders FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

-- 어느 범위에도 안 맞는 행이 갈 곳 (없으면 INSERT가 에러가 난다)
CREATE TABLE orders_default PARTITION OF orders DEFAULT;

-- 부모에 만든 인덱스는 모든 파티션에 자동으로 생긴다
CREATE INDEX ON orders (user_id, created_at);
```

## 오래된 달은 통째로 떼어 낸다

이제 처음의 새벽 배치를 다시 본다. 나누지 않은 테이블에서 1월 주문을 지우면 이렇다.

```sql
-- 나누지 않은 테이블: 행을 하나씩 지운다
\timing on
SELECT pg_current_wal_lsn() AS before \gset
DELETE FROM orders_flat WHERE created_at < '2026-02-01';
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), :'before')) AS wal_written;

-- 지운 행은 죽은 행으로 남는다
SELECT n_live_tup, n_dead_tup FROM pg_stat_user_tables WHERE relname = 'orders_flat';
```

```text
DELETE 318858
Time: 196.882 ms
 wal_written
-------------
 38 MB
(1 row)

 n_live_tup | n_dead_tup
------------+------------
    2681142 |     318858
(1 row)
```

31만 건에 WAL이 38MB 나왔고, 31만 개의 죽은 행이 남아 `VACUUM`을 기다린다. 이 38MB는 모든 복제본으로 그대로 흘러간다. 수억 건 테이블에서 수천만 건을 지우면 WAL이 수 GB가 되고, 복제본이 그만큼 뒤처진다. 파티션은 테이블째 떼어 낸다.

```sql
-- 파티션 테이블: 1월 파티션을 부모에서 떼어 내고 지운다
\timing on
SELECT pg_current_wal_lsn() AS before \gset
ALTER TABLE orders DETACH PARTITION orders_2026_01;
DROP TABLE orders_2026_01;
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), :'before')) AS wal_written;
```

```text
DROP TABLE
Time: 32.832 ms

(1 row)
```

WAL 72kB, 죽은 행 0개다. 파일을 지우는 일이라 행 수와 상관이 없다. 지우기 전에 보관해야 한다면 `DETACH`만 하고 그 테이블을 `pg_dump`로 떠서 저렴한 저장소로 옮긴 뒤 `DROP`한다.

`DETACH`는 잠깐이지만 부모 테이블에 강한 잠금(ACCESS EXCLUSIVE)을 건다. 그 순간 `orders`를 쓰는 긴 쿼리가 있으면 그걸 기다리고, 기다리는 동안 뒤에 오는 쿼리도 줄줄이 막힌다. PostgreSQL 14부터 있는 `DETACH PARTITION ... CONCURRENTLY`는 약한 잠금으로 떼어 내지만, 이번 구성에서는 바로 거절됐다.

```text
ALTER TABLE orders DETACH PARTITION orders_2026_01 CONCURRENTLY;
ERROR:  cannot detach partitions concurrently when a default partition exists
```

default 파티션이 있으면 `CONCURRENTLY`를 쓸 수 없다. 그래서 일반 `DETACH`를 쓰되 `SET lock_timeout = '3s'`을 걸어 잠금을 오래 기다리지 않게 하고, 실패하면 잠시 뒤 다시 시도한다.

default 파티션에는 함정이 하나 더 있다. 11월 파티션을 미리 안 만들어 두었는데 11월 주문이 들어오면 default로 간다. 그 상태로 11월 파티션을 만들면 에러가 난다.

```sql
INSERT INTO orders VALUES (3000001, 7, 25000, 'paid', '2026-11-05 12:00+09');
SELECT tableoid::regclass, id, created_at FROM orders WHERE id = 3000001;

CREATE TABLE orders_2026_11 PARTITION OF orders FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
```

```text
    tableoid    |   id    |       created_at
----------------+---------+------------------------
 orders_default | 3000001 | 2026-11-05 12:00:00+09
(1 row)

ERROR:  updated partition constraint for default partition "orders_default" would be violated by some row
```

default에 이미 11월 행이 있어서다. 한 트랜잭션 안에서 그 행들을 새 테이블로 옮기고 붙인다.

```sql
BEGIN;
-- 1. 같은 모양의 빈 테이블
CREATE TABLE orders_2026_11 (LIKE orders INCLUDING DEFAULTS INCLUDING CONSTRAINTS);
-- 2. default에 잘못 들어간 11월 행을 옮긴다
INSERT INTO orders_2026_11
  SELECT * FROM orders_default
  WHERE created_at >= '2026-11-01' AND created_at < '2026-12-01';
DELETE FROM orders_default
  WHERE created_at >= '2026-11-01' AND created_at < '2026-12-01';
-- 3. 파티션으로 붙인다 (부모의 인덱스가 자동으로 만들어진다)
ALTER TABLE orders ATTACH PARTITION orders_2026_11
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
COMMIT;
```

```text
    tableoid    |   id
----------------+---------
 orders_2026_11 | 3000001
(1 row)
```

애초에 이런 일이 없게 파티션은 몇 달 앞서 미리 만들어 둔다. 손으로 하면 언젠가 잊으니 `pg_partman` 확장이나 매일 도는 작업으로 "다음 3개월 파티션 만들기, 13개월 지난 파티션 떼기"를 자동화한다. default 파티션을 아예 안 두는 선택도 있다. 그러면 범위 밖의 행은 INSERT 에러가 나서 바로 드러나고, `DETACH CONCURRENTLY`도 쓸 수 있다.

이미 운영 중인 큰 테이블을 파티션 테이블로 바꿀 때는 새 파티션 부모를 만든 뒤, 옛 테이블을 "과거 전체"를 담는 파티션 하나로 `ATTACH`하는 방법이 있다. 이때 `ATTACH`는 모든 행이 범위 안에 있는지 확인하느라 테이블 전체를 읽는데, 옛 테이블에 같은 범위의 `CHECK` 제약을 먼저 걸어 두면 그 확인을 건너뛴다.

## 목록과 해시로도 나눈다

범위 말고도 두 가지가 더 있다. 국가처럼 값이 몇 개로 정해진 열은 LIST로 나눈다.

```sql
-- 국가별 회원. 한국과 일본만 따로, 나머지는 default
CREATE TABLE users_by_region (
  id     bigint NOT NULL,
  region text   NOT NULL,
  email  text   NOT NULL,
  PRIMARY KEY (id, region)
) PARTITION BY LIST (region);

CREATE TABLE users_kr  PARTITION OF users_by_region FOR VALUES IN ('KR');
CREATE TABLE users_jp  PARTITION OF users_by_region FOR VALUES IN ('JP');
CREATE TABLE users_etc PARTITION OF users_by_region DEFAULT;
```

자연스러운 범위가 없고 그냥 고르게 나누고 싶으면 HASH로 나눈다. 값의 해시를 파티션 수로 나눈 나머지로 고른다.

```sql
-- 장바구니를 회원 id의 해시로 4개에 나눈다
CREATE TABLE carts (
  user_id    bigint NOT NULL,
  product_id bigint NOT NULL,
  qty        int    NOT NULL,
  PRIMARY KEY (user_id, product_id)
) PARTITION BY HASH (user_id);

CREATE TABLE carts_p0 PARTITION OF carts FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE carts_p1 PARTITION OF carts FOR VALUES WITH (MODULUS 4, REMAINDER 1);
CREATE TABLE carts_p2 PARTITION OF carts FOR VALUES WITH (MODULUS 4, REMAINDER 2);
CREATE TABLE carts_p3 PARTITION OF carts FOR VALUES WITH (MODULUS 4, REMAINDER 3);

-- 회원 1~8이 어디로 갔나
INSERT INTO carts SELECT u, 1001, 1 FROM generate_series(1, 8) u;
SELECT tableoid::regclass AS part, array_agg(user_id ORDER BY user_id) FROM carts GROUP BY 1 ORDER BY 1;
```

```text
   part   | array_agg
----------+-----------
 carts_p0 | {1}
 carts_p1 | {3,5,8}
 carts_p2 | {2}
 carts_p3 | {4,6,7}
(4 rows)
```

8명이라 고르지 않아 보이지만 수만 명이 되면 거의 같아진다. 해시 파티션은 `WHERE user_id = 42` 같은 같음 조건에서만 가지치기가 되고, 범위 조건으로는 안 된다. 오래된 것을 떼어 내는 용도로도 못 쓴다. 쓰기와 `VACUUM`을 잘게 나누는 게 목적일 때 쓴다.

파티셔닝에서 자주 막히는 것도 정리해 둔다. 파티션 키가 빠진 UNIQUE는 만들 수 없다. `CREATE UNIQUE INDEX ON orders (id)`도 앞의 기본 키와 같은 에러가 난다. 회원 테이블을 지역으로 나누면 이메일 중복을 전체에서 막을 수 없게 되는 식이라, 전역으로 고유해야 하는 값은 따로 작은 테이블(`email → user_id`)을 두고 거기에 UNIQUE를 건다. 파티션 수는 수천 개 단위로 늘리면 계획 시간과 메모리가 눈에 띄게 늘어난다. 날짜로 나눈다면 하루 단위보다 달 단위가 보통 적당하다. MySQL 8에도 `PARTITION BY RANGE`가 있고 "모든 고유 키에 파티션 열이 들어가야 한다"는 규칙도 같다. 다만 MySQL은 파티션된 InnoDB 테이블에 외래 키를 걸 수 없다. PostgreSQL은 12부터 파티션 테이블을 가리키는 외래 키도 된다.

## 서버 여러 대에 나눠 담는다

복제는 읽기를 나눠 줄 뿐 쓰기는 여전히 프라이머리 한 대가 다 받는다. 파티셔닝도 한 서버 안의 일이다. 쓰기가 프라이머리 한 대의 디스크와 CPU로 감당이 안 되거나, 데이터가 한 서버에 담기 버거워지면 데이터를 여러 DB 서버에 나눠 담는다. 이게 샤딩이고, 나눠 담긴 각 DB를 샤드라고 한다.

샤딩에서 가장 중요한 결정은 무엇을 기준으로 나눌지, 샤드 키다. 한번 정하면 바꾸기가 거의 이사 수준이라 처음에 신중해야 한다. 좋은 샤드 키는 두 가지를 만족한다. 데이터와 트래픽이 샤드들에 고르게 퍼지고, 자주 하는 쿼리가 샤드 하나 안에서 끝난다.

주문을 `created_at`의 범위로 나눴다고 해 보자. 1~6월은 샤드 1, 7~12월은 샤드 2. 파티셔닝에서는 좋았던 키지만 샤딩에서는 나쁘다. 새 주문은 전부 "지금"이라서 모든 쓰기가 가장 최근 샤드 한 대로 몰린다. 나머지 샤드는 놀고, 바쁜 샤드는 샤딩 전과 똑같이 바쁘다. 이런 쏠림을 핫스팟이라고 한다. 쓰기를 나누려고 샤딩했는데 쓰기가 안 나뉜다.

`user_id`로 나누면 쓰기가 회원 수만큼 퍼진다. 마이페이지의 "내 주문"처럼 회원 한 명의 데이터를 보는 쿼리는 샤드 하나에서 끝난다. 대신 "어제 들어온 전체 주문"은 모든 샤드에 물어서 합쳐야 한다. 어떤 키도 모든 쿼리를 샤드 하나로 끝내 주지는 않는다. 가장 자주, 가장 빨라야 하는 쿼리에 맞춘다.

나누는 방식은 세 가지가 있다. 범위(range)는 키의 구간마다 샤드를 정한다(회원 1~100만은 샤드 1). 범위 조회가 쉽지만 앞의 날짜처럼 쏠리기 쉽다. 해시(hash)는 키를 해시해서 샤드를 고른다. 고르게 퍼지지만 범위 조회는 모든 샤드에 가야 한다. 디렉터리(directory)는 "회원 42는 샤드 3"을 적어 둔 조회 테이블을 따로 둔다. 큰 고객 하나만 전용 샤드로 옮기는 것처럼 자유롭지만, 그 테이블이 모든 요청 경로에 끼어서 그것 자체가 캐시와 고가용성이 필요한 핵심 부품이 된다.

## 샤드를 늘려도 조금만 옮기는 해시

해시로 나눌 때 가장 쉬운 방법은 `hash(user_id) % 샤드 수`다. 문제는 샤드를 늘릴 때 온다. 회원 1만 명을 3개 샤드에 나눠 두었다가 4개로 늘리면, 나머지 연산의 결과가 바뀐 회원이 7,525명이었다(아래 플레이그라운드와 같은 해시 함수로 계산한 값). 4분의 3이 다른 서버로 이사해야 한다. 이사하는 동안 그 데이터를 어디서 읽어야 할지도 정해야 한다.

일관된 해싱(consistent hashing)은 샤드와 키를 둘 다 같은 원 위에 올린다. 원은 해시 값의 범위(0부터 2³²−1까지)를 둥글게 이어 붙인 것이다. 키는 자기 자리에서 시계 방향으로 가다가 처음 만나는 샤드로 간다. 아래 그림에서 다음을 누르면 키가 샤드를 찾아가는 과정과, 샤드를 하나 더했을 때 무엇이 움직이는지가 보인다.

샤드를 더하면 새 샤드 바로 앞 구간의 키만 옮긴다. 샤드를 빼면 그 샤드의 키만 다음 샤드로 간다. 나머지 연산처럼 전체가 흔들리지 않는다.

그림의 세 번째 단계에서 본 것처럼 샤드가 원 위에 몇 개 없으면 구간 길이가 제각각이라 한 샤드가 큰 몫을 맡는다. 실제로 샤드마다 점을 하나씩만 찍고 1만 명을 나눠 보니 8,246명, 1,507명, 247명으로 갈렸다. 그래서 샤드 하나를 원 위의 여러 자리에 찍는다. 이걸 가상 노드(vnode)라고 한다. 샤드마다 200개씩 찍으니 3,577명, 3,085명, 3,338명으로 고르게 갈렸고, db4를 더했을 때 옮긴 회원은 2,448명(약 4분의 1)이었다. 옮긴 회원은 모두 db4로 갔다. 이론상 최소치(새 샤드가 맡을 몫만큼)에 가깝다.

일관된 해싱 말고 자주 쓰는 방법이 하나 더 있다. 처음부터 논리 샤드(버킷)를 넉넉히 만들어 두는 것이다. 키는 `hash(key) % 1024`로 1024개 버킷 중 하나에 고정되고, 버킷이 어느 서버에 있는지는 작은 지도로 관리한다. 서버를 늘리면 키의 버킷은 그대로 두고 버킷 몇 개를 새 서버로 옮긴 뒤 지도만 고친다. Redis Cluster의 16384 슬롯이 이 방식이다. 버킷 수를 나중에 바꾸기는 어려우니 처음에 서버 수보다 훨씬 크게 잡는다.

## 샤드를 넘나드는 쿼리는 비싸다

샤딩하면 한 DB에서 당연하던 것들이 비싸진다. `user_id`로 나눈 주문에서 "오늘 매출 합계"를 구하려면 모든 샤드에 같은 쿼리를 보내고 결과를 앱이나 라우터에서 합친다(scatter-gather). 샤드가 10개면 10번 묻고, 가장 느린 샤드가 전체 응답 시간을 정한다. `ORDER BY created_at DESC LIMIT 20`이면 샤드마다 20개씩 받아서 다시 정렬해 20개를 고른다. `OFFSET 10000`처럼 깊은 페이지는 샤드마다 10,020개를 받아야 해서 훨씬 나빠진다.

조인은 같은 샤드 안에서만 싸다. 주문(`orders`)과 주문 상품(`order_items`)을 둘 다 `user_id`로 나누면 한 회원의 주문과 상품은 같은 샤드에 모여서 조인이 그 안에서 끝난다. 이렇게 함께 쓰는 테이블을 같은 키로 나눠 같은 곳에 두는 걸 코로케이션(colocation)이라고 한다. 주문 상품 테이블에 `user_id`가 없었다면 샤딩하면서 넣어야 한다. 상품(`products`)처럼 작고 모두가 참조하는 테이블은 나누지 않고 모든 샤드에 통째로 복사해 둔다. 그래야 어느 샤드에서든 상품과 조인할 수 있다.

샤드 키가 아닌 값으로 찾는 것도 문제다. 로그인할 때는 `user_id`가 아니라 이메일로 회원을 찾는다. 이메일만으로는 어느 샤드인지 모르니 전부 물어봐야 한다. 그래서 `email → user_id`를 담은 조회 테이블을 따로 두거나(이 테이블도 이메일로 샤딩한다), 검색 엔진 같은 별도 색인을 둔다. 이메일 중복 검사도 이 조회 테이블의 UNIQUE가 맡는다.

샤드 두 곳을 함께 바꾸는 트랜잭션이 가장 어렵다. 회원 42(샤드 1)가 회원 7(샤드 3)에게 포인트를 선물하면 두 샤드에서 동시에 성공하거나 동시에 실패해야 한다. 2단계 커밋(2PC)은 조정자가 모든 샤드에 먼저 "준비됐나"를 묻고(PostgreSQL의 `PREPARE TRANSACTION`), 모두 준비되면 커밋을 지시한다. 준비 단계에서 조정자가 죽으면 샤드들은 잠금을 쥔 채 결정을 기다린다. PostgreSQL은 `max_prepared_transactions`가 기본 0이라 켜야 쓸 수 있고, 남겨진 준비 트랜잭션을 정리하는 운영 도구까지 갖춰야 한다. 그래서 실무에서는 샤드 키를 잘 골라 이런 트랜잭션이 드물게 만들고, 남는 경우는 각 샤드의 로컬 트랜잭션을 이어 붙이고 실패하면 보상 작업을 실행하는 사가로 푼다. 사가와 아웃박스는 [마이크로서비스 글](/posts/microservices)에 자세히 있다.

## 주문 번호는 누가 만드나

한 DB에서는 `bigserial`이나 `GENERATED AS IDENTITY`가 1, 2, 3을 만들어 줬다. 샤드마다 따로 만들면 샤드 1의 주문 101과 샤드 2의 주문 101이 겹친다. 방법은 몇 가지다.

샤드마다 시작값과 간격을 달리하는 방법이 있다. 샤드 1은 1, 4, 7, 샤드 2는 2, 5, 8 식이다. MySQL의 `auto_increment_increment`와 `auto_increment_offset`이 이걸 해 준다. 단순하지만 샤드 수를 바꾸면 규칙이 깨진다.

UUID는 어디서 만들어도 겹치지 않는다. 다만 완전히 무작위인 UUIDv4를 기본 키로 쓰면 새 행이 B-tree 인덱스의 아무 곳에나 끼어들어서, 최근 행이 인덱스의 끝에 모이지 않는다. 테이블이 커지면 인덱스 페이지가 메모리에서 계속 밀려나 쓰기가 느려진다. 2024년에 표준(RFC 9562)이 된 UUIDv7은 앞 48비트에 밀리초 단위 유닉스 시간을 넣어서 시간 순서대로 정렬된다.

```text
01a1475f-7280-7c3a-9e41-5b2d8f6a10c4
└──────────┘     7: 버전
  0x01a1475f7280 = 1792198800000 ms = 2026-10-17 10:00:00 KST
```

뒤쪽은 무작위라 겹치지 않고, 앞쪽이 시간이라 새 행이 인덱스 끝에 붙는다. PostgreSQL은 18에서 `uuidv7()` 함수가 생겼고, 16에서는 앱에서 만들어 `uuid` 열에 넣는다.

128비트가 부담스러우면 Twitter가 공개한 Snowflake 방식으로 64비트 정수를 만든다. 앞에서부터 41비트는 기준 시점부터 지난 밀리초, 10비트는 기계 번호, 12비트는 그 밀리초 안의 순번이다. 기계 하나가 1ms에 4,096개, 41비트로 약 69년을 쓴다. Twitter의 기준 시점(1288834974657)으로 2026-10-17 10:00:00 KST에 기계 5번이 만든 일곱 번째(순번 7) id는 이렇다.

```text
(1792198800000 - 1288834974657) << 22 | 5 << 12 | 7
= 2111260906091466759
```

정수라 인덱스에 작게 들어가고 시간순으로 정렬된다. 대신 기계 번호를 겹치지 않게 나눠 주는 장치가 필요하고, 서버 시계가 뒤로 가면 이미 쓴 id를 다시 만들 수 있어서 시계가 되돌아가면 그동안 발급을 멈추도록 구현한다. 두 방식 모두 id에 시간이 들어 있어서, 앞에서 본 파티션 테이블에서 id만으로 어느 달 파티션인지 계산해 조건에 붙일 수 있다.

## 샤드를 다시 나누는 일

샤드 4개가 다시 모자라서 8개로 늘린다고 하자. 데이터를 옮기는 동안에도 서비스는 돌아가야 한다. 순서는 대체로 이렇다. 새 샤드를 준비하고, 옮길 데이터를 복사하기 시작한다(덤프로 한 번 복사하고 논리 복제나 CDC로 그 뒤의 변경을 따라 붙인다). 둘이 거의 같아지면 잠깐 그 범위의 쓰기를 멈추거나 이중 쓰기를 켜고, 라우팅 지도를 새 샤드로 바꾼다. 행 수와 체크섬으로 맞는지 확인한 뒤 옛 샤드의 데이터를 지운다. 하나하나가 실패할 수 있는 단계라 되돌리는 경로도 같이 준비한다.

이 일을 직접 짜는 대신 샤딩을 대신 해 주는 도구가 있다. Citus는 PostgreSQL 확장이다. 조정자 노드 하나와 작업자 노드 여럿을 두고, `SELECT create_distributed_table('orders', 'user_id')` 한 줄로 테이블을 `user_id` 기준으로 나눈다. 상품 같은 작은 테이블은 `create_reference_table`로 모든 노드에 복사한다. 앱은 조정자에 평범한 SQL을 보내고, 같은 키로 나눈 테이블끼리의 조인은 작업자 안에서 처리된다. Vitess는 MySQL용으로, VTGate라는 프록시가 쿼리를 받아 샤드로 보내고, 샤드를 나누거나 합치는 작업(Reshard)을 워크플로로 제공한다. YouTube에서 시작했다. 처음부터 나눠 저장하도록 만든 DB(Cassandra, DynamoDB, MongoDB 샤딩, CockroachDB 같은 분산 SQL)를 고르는 방법도 있다. MongoDB의 샤드 키 이야기는 [MongoDB 글](/posts/mongodb-document-model)에 있다.

## 읽기 모양을 따로 만들어 두기

샤딩하고 나면 "전체 주문을 날짜별로" 같은 쿼리가 비싸다. 이런 읽기는 원본 DB에서 해결하려 하지 않고, 읽기 전용 모델을 따로 만드는 방법이 있다. 쓰기는 회원별로 샤딩한 주문 DB가 받고, 변경이 생길 때마다 이벤트나 CDC로 그 내용을 받아 "일별 매출 테이블", "관리자 화면용 검색 색인"처럼 읽기에 맞춘 모양으로 다시 쌓는다. 쓰기 모델과 읽기 모델을 나누는 이 방식을 CQRS(Command Query Responsibility Segregation)라고 한다. 읽기 모델은 원본보다 조금 늦게 따라오니, 앞의 복제 지연과 같은 고민(쓴 사람에게는 쓴 것을 보여 주기)이 그대로 따라온다. 서비스 규모에 따라 저장소를 나누는 이야기는 [서비스 규모별 DB 설계 글](/posts/db-architecture-by-scale)에서 이어 간다.

## 언제 다음 단계로 넘어가나

숫자는 하드웨어와 쿼리 모양에 따라 크게 달라서 출발점으로만 본다.

쿼리와 인덱스를 고쳤는데도 프라이머리 CPU가 바쁜 시간대에 70%를 넘게 머물고, 그 대부분이 읽기라면 복제본을 붙인다. `pg_stat_statements`에서 SELECT가 총 실행 시간의 대부분을 차지하는지 먼저 본다. 장애 대비용 스탠바이는 규모와 상관없이 처음부터 두는 편이 낫다.

테이블 하나가 수십 GB를 넘어 서버 메모리보다 커지고, 날짜 범위로 조회하거나 오래된 데이터를 정기적으로 지워야 한다면 파티셔닝을 본다. 1년치를 남기고 지우는 `DELETE` 배치가 복제 지연을 몇 분씩 만들거나, `VACUUM`이 그 테이블 하나에서 몇 시간씩 돈다면 늦은 편이다. 지울 일이 없고 쿼리에 파티션 키가 안 들어간다면 파티셔닝은 오히려 느려질 수 있다.

샤딩은 쓰기 자체가 한계일 때 간다. 가장 큰 인스턴스로 올렸는데도 쓰기 때문에 WAL 쓰기나 디스크가 포화되거나, 데이터가 수 TB로 커져 백업 복원과 복제본 하나 새로 만드는 데 하루가 걸리는 상황이다. 읽기만 많다면 샤딩보다 복제본과 캐시가 훨씬 싸다. 샤딩은 앱 코드, 운영, 장애 대응 방식이 다 바뀌기 때문에 다른 방법이 바닥났을 때 꺼내는 마지막 카드에 가깝다.

## 나누는 순서

DB 한 대가 버거울 때는 먼저 쿼리와 인덱스를 고치고 서버를 키운다. 읽기가 문제면 WAL을 받아 재생하는 복제본으로 읽기를 나누되, 복제는 늦을 수 있으니 방금 쓴 것을 읽는 경로는 프라이머리나 LSN 확인으로 막는다. 테이블 하나가 너무 커지면 같은 DB 안에서 파티션으로 나눠 오래된 것을 통째로 떼어 내고, 쿼리에 파티션 키가 들어가게 만든다. 쓰기와 데이터가 서버 한 대를 넘을 때 비로소 샤딩으로 가는데, 샤드 키가 쿼리의 모양과 데이터 분포를 결정하고 나중에 바꾸기 어렵다는 걸 알고 고른다.

## 면접에서 나올 만한 질문

### 레플리케이션과 샤딩은 무엇이 다른가요?

복제는 같은 데이터를 여러 서버에 복사하는 것이고, 샤딩은 데이터를 나눠서 서버마다 다른 부분을 담는 것이다. 복제는 읽기를 나누고 장애에 대비하지만 쓰기는 여전히 프라이머리 한 대가 받는다. 샤딩은 쓰기와 저장 용량을 나누지만 샤드를 넘는 조인, 트랜잭션, 재분배가 어려워진다. 보통 샤드마다 복제본을 두어 둘을 같이 쓴다.

### 복제 지연 때문에 방금 쓴 데이터가 안 보이면 어떻게 하나요?

비동기 복제는 프라이머리가 커밋 응답을 먼저 주고 WAL을 나중에 보내서 생기는 문제다. 쓰기 직후 몇 초 동안 그 사용자의 읽기를 프라이머리로 보내거나, 결제처럼 중요한 화면은 항상 프라이머리에서 읽는다. 더 정확하게는 커밋 후 `pg_current_wal_lsn()`을 세션에 저장하고, 복제본의 `pg_last_wal_replay_lsn()`이 그 위치를 넘었을 때만 복제본에서 읽는다. `synchronous_commit = remote_apply`도 있지만 모든 커밋이 느려진다.

### synchronous_commit의 on과 remote_apply는 어떻게 다른가요?

동기 스탠바이가 지정돼 있을 때 on은 스탠바이가 WAL을 디스크에 flush할 때까지 기다리고, remote_apply는 재생까지 끝나 쿼리에 보일 때까지 기다린다. on이면 프라이머리가 사라져도 커밋은 남지만 스탠바이에서 바로 읽으면 안 보일 수 있다. 동기 스탠바이가 한 대뿐이면 그 서버 장애가 프라이머리 쓰기를 멈추게 하니 `ANY 1 (s1, s2)`처럼 두 대 이상을 둔다.

### 파티셔닝을 하면 쿼리가 항상 빨라지나요?

아니다. 쿼리 조건에 파티션 키가 있어야 필요한 파티션만 읽는 가지치기가 되고, 없으면 모든 파티션을 열어 보느라 오히려 느려진다. 범위 조회도 인덱스가 잘 걸린 단일 테이블과 비교하면 차이가 크지 않을 수 있다. 큰 이득은 오래된 데이터를 `DELETE` 대신 `DETACH`와 `DROP`으로 지우는 것, 파티션 단위의 VACUUM과 인덱스 관리에서 나온다.

### PostgreSQL 파티션 테이블에서 id만으로 기본 키를 만들 수 없는 이유는?

고유 인덱스가 파티션마다 따로 있어서 다른 파티션의 값을 확인할 수 없기 때문이다. 기본 키와 UNIQUE에 파티션 키가 들어가야 각 파티션 안의 고유성만으로 전체 고유성이 보장된다. 그래서 `(id, created_at)`처럼 만들고, 이메일처럼 전역으로 고유해야 하는 값은 별도의 작은 테이블에 UNIQUE를 건다.

### 샤드 키는 어떻게 고르나요?

데이터와 쓰기가 고르게 퍼지고, 가장 자주 하는 쿼리가 샤드 하나에서 끝나는 키를 고른다. 생성 시각처럼 계속 증가하는 값으로 범위 샤딩을 하면 새 쓰기가 최신 샤드 한 대에 몰리는 핫스팟이 생긴다. 회원 id처럼 카디널리티가 높고 요청이 그 단위로 묶이는 값이 흔한 선택이고, 함께 조인하는 테이블은 같은 키로 나눠 같은 샤드에 둔다.

### 일관된 해싱은 왜 쓰나요?

`hash % N` 방식은 샤드 수가 바뀌면 대부분의 키가 다른 샤드로 옮겨진다. 실제로 1만 개 키를 3개에서 4개로 늘리면 약 75%가 이동했다. 일관된 해싱은 샤드와 키를 같은 해시 링에 놓고 시계 방향으로 첫 샤드에 배정해서, 샤드를 더하거나 빼도 이웃 구간의 키만 옮긴다. 샤드마다 가상 노드를 여러 개 찍어 구간 길이를 고르게 만든다.

### 샤딩 환경에서 ID는 어떻게 만드나요?

샤드마다 자동 증가를 쓰면 겹치니 전역에서 유일한 id가 필요하다. UUIDv7은 앞부분이 밀리초 시간이라 정렬되면서도 어디서나 충돌 없이 만들 수 있고, Snowflake는 시간 41비트, 기계 번호 10비트, 순번 12비트로 64비트 정수를 만든다. 무작위 UUIDv4는 B-tree 인덱스에 흩어져 들어가 쓰기 성능이 떨어진다. Snowflake는 기계 번호 관리와 시계가 뒤로 가는 경우를 처리해야 한다.
