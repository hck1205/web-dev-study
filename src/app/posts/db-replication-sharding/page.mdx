<EasyIntro>
  할인 행사 날 데이터베이스 서버 한 대가 읽기 요청에 짓눌려 CPU가 90%에서 내려오지 않았다. 처음 할 일은 서버를 늘리는 것이 아니라 느린 쿼리를 고치고 서버를 키우는 것이고, 그래도 읽기가 넘치면 같은 데이터를 여러 대에 복사해 읽기를 나눈다.

  복사하는 방식은 원본 서버가 쓰는 변경 일지를 복사본 서버에 실시간으로 보내고, 복사본이 그 일지를 그대로 따라 하는 것이다. 이렇게 하면 복사본은 원본과 똑같아지지만, 일지가 도착하고 반영되기까지 아주 잠깐 늦는다. 그 틈에 복사본에서 읽으면 방금 결제한 주문이 안 보이는 일이 생긴다.

  그래서 방금 쓴 사람의 읽기는 잠깐 원본으로 보내거나, 일지가 어디까지 반영됐는지 확인하고 읽는다. 복사본이 받았다고 답할 때까지 기다리게 할 수도 있지만, 그 복사본 하나가 멈추면 원본의 쓰기까지 모두 멈춘다는 점을 알아야 한다. 복제는 읽기를 나눠 줄 뿐 쓰기는 나눠 주지 않는다.
</EasyIntro>

쇼핑몰에 할인 이벤트가 걸린 날, DB 서버의 CPU가 90%에 붙어서 내려오지 않는다. 느린 쿼리를 열어 보면 대부분 `SELECT`다. 상품 목록, 주문 내역, 마이페이지. 쓰기는 많지 않은데 읽기가 서버 한 대를 다 먹고 있다. 몇 달 뒤에는 다른 문제가 온다. `orders` 테이블이 수억 건이 되자 1년 지난 주문을 지우는 새벽 배치가 몇 시간씩 돌고, 그동안 복제본이 뒤처진다.

둘 다 "DB 한 대로는 모자라다"는 말로 들리지만 처방이 다르다. 읽기가 많으면 같은 데이터를 여러 대에 복사해 읽기를 나눈다(복제). 테이블 하나가 너무 크면 한 DB 안에서 테이블을 조각으로 나눈다(파티셔닝). 쓰기와 데이터 자체가 한 대를 넘으면 데이터를 여러 DB 서버에 나눠 담는다(샤딩). 뒤로 갈수록 강력하지만 되돌리기 어렵고 앱이 알아야 할 것이 늘어난다. 이 글은 그 첫 단계인 복제를 직접 돌려 보며 무엇을 풀고 무엇을 새로 만드는지 정리한다. 파티셔닝은 [파티셔닝 글](/posts/db-partitioning)에서, 샤딩은 [샤딩 글](/posts/db-sharding)에서 이어 간다.

기준은 Ubuntu 24.04 LTS의 PostgreSQL 16(16.15)이다. 복제 실험은 한 장비에 프라이머리(5441 포트)와 스탠바이(5442 포트)를 따로 띄워서 했고, 아래 출력은 모두 그 환경에서 실제로 나온 것이다. 그래서 주소가 `127.0.0.1`로 찍혀 있다. 시간(ms)은 장비마다 다르니 자릿수만 보면 된다. 인덱스와 쿼리 자체를 고치는 이야기는 [인덱스 글](/posts/db-index)과 [쿼리 튜닝 글](/posts/sql-query-tuning)에 있다.

## 실험에 쓸 두 테이블

글 전체에서 회원(`users`)과 주문(`orders`) 두 테이블을 쓴다. 처음에는 몇 줄뿐이다.

```sql
-- 회원
CREATE TABLE users (
  id         bigint PRIMARY KEY,
  email      text NOT NULL UNIQUE,
  name       text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

-- 주문: 누가(user_id), 얼마를(amount), 언제(created_at)
CREATE TABLE orders (
  id         bigint PRIMARY KEY,
  user_id    bigint NOT NULL REFERENCES users(id),
  amount     integer NOT NULL,
  status     text NOT NULL,
  created_at timestamptz NOT NULL
);

INSERT INTO users VALUES
  (1, 'minji@example.com',   '민지', '2026-01-03'),
  (2, 'junho@example.com',   '준호', '2026-02-11'),
  (3, 'seoyeon@example.com', '서연', '2026-03-20');

INSERT INTO orders VALUES
  (101, 1, 32000, 'paid',    '2026-09-30 23:10+09'),
  (102, 2, 15000, 'paid',    '2026-10-01 09:00+09'),
  (103, 1,  8900, 'shipped', '2026-10-02 14:30+09');

SELECT * FROM orders ORDER BY id;
```

```text
 id  | user_id | amount | status  |       created_at
-----+---------+--------+---------+------------------------
 101 |       1 |  32000 | paid    | 2026-09-30 23:10:00+09
 102 |       2 |  15000 | paid    | 2026-10-01 09:00:00+09
 103 |       1 |   8900 | shipped | 2026-10-02 14:30:00+09
(3 rows)
```

DB의 시간대는 `ALTER DATABASE shop SET timezone = 'Asia/Seoul'`로 맞춰 두었다. 그래서 `+09`로 찍힌다.

## 나누기 전에 한 대부터 키운다

서버를 늘리기 전에 볼 것이 있다. CPU를 먹는 쿼리가 인덱스 없이 테이블 전체를 읽고 있는 경우가 생각보다 많다. 쿼리 하나에 인덱스 하나를 붙여 CPU가 절반으로 떨어지는 일이 복제본 두 대를 붙이는 것보다 싸다. `pg_stat_statements`로 총 실행 시간이 큰 쿼리부터 보고, 같은 결과를 반복해서 읽는 화면이면 [캐시](/posts/caching-strategies)를 앞에 둔다. 연결이 수백 개씩 열려 있으면 커넥션 풀(PgBouncer 같은)로 줄인다. PostgreSQL은 연결마다 프로세스를 하나씩 띄우기 때문에 연결 수 자체가 메모리와 CPU를 쓴다.

그래도 모자라면 서버를 더 큰 것으로 바꾼다(수직 확장, scale-up). 앱 코드를 하나도 고치지 않아도 된다는 게 가장 큰 장점이다. 클라우드 관리형 DB는 vCPU 수십~백여 개, 메모리 1TB가 넘는 인스턴스까지 있어서 생각보다 멀리 간다.

한계도 분명하다. 크기를 두 배로 올리면 값도 대략 두 배씩 오르는데, 성능은 그만큼 오르지 않는 구간이 온다. 잠금 경합이나 WAL 쓰기처럼 코어를 늘려도 나아지지 않는 병목이 있어서다. 서버를 바꾸는 동안 짧게라도 멈춰야 하고, 무엇보다 여전히 한 대다. 그 한 대가 죽으면 서비스 전체가 멈춘다. 그래서 수직 확장을 하더라도 복제본 하나는 장애 대비로 붙여 두는 게 보통이고, 그 복제본이 다음 단계의 출발점이 된다.

## 복제본은 WAL을 받아 다시 실행한다

PostgreSQL은 데이터 파일을 고치기 전에 "무엇을 어떻게 바꿀지"를 WAL(Write-Ahead Log, 먼저 쓰는 로그)에 먼저 적는다. 서버가 갑자기 꺼져도 WAL만 남아 있으면 다시 켤 때 그 기록을 재생해 복구한다. 스트리밍 복제는 이 WAL을 다른 서버에 실시간으로 보내서, 받은 서버가 똑같이 재생하게 하는 것이다.

쓰기를 받는 쪽이 프라이머리, WAL을 받아 재생하는 쪽이 스탠바이(복제본, 레플리카)다. 프라이머리의 walsender 프로세스가 WAL을 보내고, 스탠바이의 walreceiver가 받아 디스크에 쓰고, startup 프로세스가 그걸 재생한다. 스탠바이는 재생하는 동안에도 읽기 쿼리를 받을 수 있다(hot standby, 16에서는 기본으로 켜져 있다). 쓰기를 보내면 거절한다.

```text
INSERT INTO orders VALUES (104,3,12000,'paid',now());
ERROR:  cannot execute INSERT in a read-only transaction
```

SQL 문장을 다시 실행하는 게 아니라 "몇 번 페이지의 몇 바이트를 이렇게 바꿔라" 수준의 물리적인 변경을 재생한다. 그래서 스탠바이는 프라이머리와 바이트 단위로 같은 복사본이 되고, 메이저 버전과 아키텍처가 같아야 하며, 일부 테이블만 골라 복제할 수는 없다. 테이블을 골라 복제하거나 다른 버전으로 보내야 할 때는 논리 복제(`CREATE PUBLICATION` / `CREATE SUBSCRIPTION`)를 쓴다.

## 스탠바이를 하나 붙여 보기

프라이머리가 `10.0.0.11`, 스탠바이가 `10.0.0.12`인 Ubuntu 서버 두 대라고 하자. 둘 다 `apt install postgresql`로 16이 깔려 있다. 먼저 프라이머리에서 복제 전용 계정을 만들고 접속을 허용한다.

```bash
# [프라이머리] 복제 전용 계정 (REPLICATION 권한만, 테이블 권한은 없다)
sudo -u postgres psql -c "CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'change-me'"

# [프라이머리] 다른 서버에서 접속을 받도록 (기본값은 localhost만)
sudo sed -i "s/^#listen_addresses = 'localhost'/listen_addresses = '*'/" /etc/postgresql/16/main/postgresql.conf

# [프라이머리] 스탠바이 주소에서 오는 복제 연결만 허용
echo "host replication replicator 10.0.0.12/32 scram-sha-256" | sudo tee -a /etc/postgresql/16/main/pg_hba.conf

# [프라이머리] listen_addresses는 재시작해야 적용된다
sudo systemctl restart postgresql@16-main
```

`wal_level = replica`와 `max_wal_senders = 10`은 16의 기본값이라 따로 바꿀 필요가 없다. 방화벽이 있다면 5432 포트를 스탠바이 주소에만 열어 둔다.

스탠바이에서는 비어 있는 데이터 디렉터리에 프라이머리의 전체 복사본을 받는다. `pg_basebackup`이 그 일을 한다.

```bash
# [스탠바이] 서버를 멈추고 기존 데이터 디렉터리를 치운다 (새로 깐 서버라 비어 있어도 된다)
sudo systemctl stop postgresql@16-main
sudo -u postgres mv /var/lib/postgresql/16/main /var/lib/postgresql/16/main.old

# [스탠바이] 프라이머리 전체를 복사한다
#   -R: 스탠바이 설정(standby.signal, primary_conninfo)을 자동으로 써 준다
#   -X stream: 복사하는 동안 생긴 WAL도 같이 받는다
#   -C -S standby1: 프라이머리에 복제 슬롯 standby1을 만든다
sudo -u postgres pg_basebackup -h 10.0.0.11 -U replicator \
  -D /var/lib/postgresql/16/main -R -X stream -C -S standby1 -P

# [스탠바이] 시작하면 스탠바이로 뜬다
sudo systemctl start postgresql@16-main

# [스탠바이] 스탠바이인지 확인 (t면 복구, 즉 재생 중)
sudo -u postgres psql -c "SELECT pg_is_in_recovery()"
```

```text
 pg_is_in_recovery
-------------------
 t
(1 row)
```

프라이머리에서는 `pg_stat_replication` 뷰로 붙어 있는 스탠바이를 본다.

```bash
# [프라이머리] 붙어 있는 스탠바이 목록
sudo -u postgres psql -x -c "SELECT * FROM pg_stat_replication"
```

볼 줄은 세 군데다. `state`가 `streaming`이면 실시간으로 받고 있다. `catchup`이면 아직 따라잡는 중이다. `sent_lsn`부터 `replay_lsn`까지 네 값은 WAL의 위치(LSN, Log Sequence Number)인데, 바로 다음 절에서 본다. `sync_state`가 `async`면 비동기 복제다. 기본값이 비동기다.

복제 슬롯(`-S standby1`)은 "이 스탠바이가 아직 안 받아 간 WAL은 지우지 마라"는 표시다. 스탠바이가 잠깐 끊겨도 다시 붙어서 이어 받을 수 있게 해 준다. 대신 스탠바이가 며칠 죽어 있으면 프라이머리에 WAL이 계속 쌓인다. 16의 `max_slot_wal_keep_size` 기본값은 `-1`(제한 없음)이라 그대로 두면 프라이머리 디스크가 가득 차서 프라이머리까지 멈춘다. 디스크 여유에 맞춰 값을 정하고, `pg_replication_slots`의 `active`가 `f`인 슬롯이 있는지 감시한다.

```sql
-- 슬롯 상태. active = f 로 오래 남아 있으면 WAL이 쌓이고 있다
SELECT slot_name, active, restart_lsn, wal_status FROM pg_replication_slots;
```

```text
 slot_name | active | restart_lsn | wal_status
-----------+--------+-------------+------------
 standby1  | t      | 0/7D49D8F0  | reserved
(1 row)
```

## 방금 결제한 주문이 안 보인다

복제본을 붙이고 읽기를 그쪽으로 보내면 프라이머리의 CPU가 내려간다. 그런데 이상한 문의가 들어온다. 결제를 마치고 주문 내역으로 넘어갔더니 방금 주문이 없다고 한다. 새로고침하면 보인다.

비동기 복제에서 프라이머리는 자기 디스크에 WAL을 쓰자마자 앱에 "커밋됐다"고 답한다. 스탠바이로 보내고 재생하는 건 그 뒤의 일이다. 아래 그림에서 다음을 누르면 그 짧은 틈에 읽기가 끼어드는 과정이 차례로 보인다.

같은 장비에서 이 틈은 보통 1ms도 안 돼서 눈으로 보기 어렵다. 그래서 스탠바이에서 `pg_wal_replay_pause()`로 재생을 잠깐 세워 놓고 재현했다.

```sql
-- [스탠바이] 재생을 잠깐 멈춘다 (실험용. 운영에서 쓰면 그만큼 뒤처진다)
SELECT pg_wal_replay_pause();

-- [프라이머리] 주문을 쓰고, 그 직후의 WAL 위치를 본다
INSERT INTO orders VALUES (104, 3, 12000, 'paid', '2026-10-17 10:00+09');
SELECT pg_current_wal_lsn();
```

```text
INSERT 0 1
 pg_current_wal_lsn
--------------------
 0/3434AA8
(1 row)
```

```sql
-- [스탠바이] 방금 쓴 주문을 찾는다
SELECT id, amount FROM orders WHERE id = 104;

-- [스탠바이] 어디까지 받았고 어디까지 재생했나
SELECT pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn(), pg_is_wal_replay_paused();
```

```text
 id | amount
----+--------
(0 rows)

 pg_last_wal_receive_lsn | pg_last_wal_replay_lsn | pg_is_wal_replay_paused
-------------------------+------------------------+-------------------------
 0/3434AA8               | 0/34349A8              | t
(1 row)
```

받은 위치는 `0/3434AA8`로 프라이머리와 같은데 재생한 위치는 `0/34349A8`에 멈춰 있다. WAL은 이미 스탠바이 디스크에 와 있지만 재생 전이라 쿼리에는 안 보인다. 프라이머리 쪽에서 같은 상황을 보면 이렇다.

```sql
-- [프라이머리] 스탠바이가 얼마나 뒤처졌나
SELECT application_name, state, sent_lsn, write_lsn, flush_lsn, replay_lsn,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS replay_gap_bytes,  -- 보낸 것과 재생한 것의 차이 (바이트)
       replay_lag, sync_state
FROM pg_stat_replication;
```

```text
 application_name |   state   | sent_lsn  | write_lsn | flush_lsn | replay_lsn | replay_gap_bytes |   replay_lag    | sync_state
------------------+-----------+-----------+-----------+-----------+------------+------------------+-----------------+------------
 walreceiver      | streaming | 0/3434AA8 | 0/3434AA8 | 0/3434AA8 | 0/34349A8  |              256 | 00:00:00.000817 | async
(1 row)
```

`replay_gap_bytes`가 256으로, 주문 한 건 분량의 WAL이 재생되지 않고 남아 있다. 눈여겨볼 것은 `replay_lag`다. 재생이 멈춰 있는데도 0.0008초로 찍혔다. 이 값은 최근에 재생이 끝난 WAL이 얼마나 걸렸는지를 재는 값이라, 재생이 아예 멈추거나 쓰기가 뜸하면 실제 상황보다 작게 보인다. 그래서 지연 감시는 시간과 바이트 차이를 같이 건다.

스탠바이에서 흔히 쓰는 다른 확인법에도 함정이 있다.

```sql
-- [스탠바이] 마지막으로 재생한 트랜잭션이 얼마 전 것인가
SELECT now() - pg_last_xact_replay_timestamp() AS replay_delay;
```

```text
  replay_delay
-----------------
 00:00:01.048564
(1 row)
```

이 출력을 찍을 때 스탠바이는 완전히 따라잡은 상태였다(받은 위치와 재생 위치가 같았다). 그런데도 1초로 나온 건 프라이머리에 1초 동안 쓰기가 없었기 때문이다. 쓰기가 없는 새벽에는 지연이 없어도 이 값이 몇 분씩 커진다. 이 값으로 경보를 걸면 새벽마다 거짓 경보가 울린다.

## 쓴 사람에게는 쓴 것을 보여 준다

사용자가 기대하는 건 모든 데이터가 즉시 맞는 것이 아니다. 자기가 방금 쓴 것만큼은 바로 보이는 것이다(read-your-writes). 남이 쓴 리뷰가 1초 늦게 보이는 건 아무도 모르지만, 내 주문이 사라지는 건 바로 문의가 된다. 해결책은 몇 가지가 있고 섞어서 쓴다.

가장 단순한 건 쓰기 직후 잠깐 프라이머리에서 읽는 것이다. 쓰기를 한 사용자의 세션에 "5초 동안 프라이머리"라는 표시를 남기고, 그동안 그 사용자의 읽기만 프라이머리로 보낸다. 5초는 평소 복제 지연보다 넉넉히 큰 값으로 잡는다. 지연이 그보다 커지는 순간에는 여전히 틀릴 수 있다.

결제 결과, 잔액, 재고처럼 틀리면 안 되는 화면은 아예 항상 프라이머리에서 읽는다. 복제본은 목록, 검색, 통계처럼 조금 낡아도 되는 읽기에만 쓴다. 복제본을 붙인다고 모든 읽기를 넘기는 게 아니라 읽기마다 얼마나 낡아도 되는지를 정하는 일이다.

더 정확한 방법은 LSN을 기억하는 것이다. 쓰기를 커밋한 뒤 프라이머리의 WAL 위치를 받아 세션에 넣어 두고, 복제본에서 읽기 전에 그 위치까지 재생됐는지 확인한다. 아직이면 잠깐 기다리거나 프라이머리로 보낸다. PostgreSQL 16에는 특정 LSN까지 기다리는 내장 명령이 없어서 앱이 이렇게 물어본다.

```sql
-- [프라이머리] 쓰기 커밋 직후. 이 값을 세션(쿠키, Redis 등)에 저장한다
SELECT pg_current_wal_lsn();        -- 0/3434AA8

-- [스탠바이] 읽기 전에 확인. f면 기다리거나 프라이머리에서 읽는다
SELECT pg_last_wal_replay_lsn() >= '0/3434AA8'::pg_lsn AS caught_up;
```

재생을 멈춘 상태에서는 `f`였고, `pg_wal_replay_resume()`으로 재생을 다시 켠 뒤에는 `t`가 나왔다.

```text
 caught_up
-----------
 f
(1 row)

 caught_up
-----------
 t
(1 row)
```

복제본이 여러 대일 때는 다른 문제도 있다. 새로고침할 때마다 다른 복제본에 붙으면, 덜 뒤처진 복제본에서 본 댓글이 더 뒤처진 복제본에서는 사라진다. 시간이 거꾸로 가는 것처럼 보인다. 한 사용자를 한 복제본에 고정하면(사용자 id로 고르기) 적어도 시간이 거꾸로 가지는 않는다(monotonic reads).

`synchronous_commit`만 바꿔서는 동기 복제가 되지 않는다. 기다릴 스탠바이를 `synchronous_standby_names`에 적어야 한다. 비어 있으면(기본값) `on`도 자기 디스크까지만 기다린다. 실험 환경에서 스탠바이 하나를 동기로 지정했다.

```sql
-- [프라이머리] walreceiver라는 이름의 스탠바이 1대를 동기로 기다린다
ALTER SYSTEM SET synchronous_standby_names = 'FIRST 1 (walreceiver)';
SELECT pg_reload_conf();

SELECT application_name, sync_state FROM pg_stat_replication;
```

```text
 application_name | sync_state
------------------+------------
 walreceiver      | sync
(1 row)
```

이름은 스탠바이의 `primary_conninfo`에 있는 `application_name`이고, 따로 주지 않으면 `walreceiver`다. 실무에서는 스탠바이마다 `application_name=standby1`처럼 이름을 붙인다.

이 상태에서 스탠바이를 꺼 보면 동기 복제의 대가가 바로 보인다.

```bash
# [스탠바이] 서버를 내린다
sudo systemctl stop postgresql@16-main
```

```sql
-- [프라이머리] 주문을 쓰면 응답이 오지 않는다
INSERT INTO orders VALUES (105, 2, 5000, 'paid', '2026-10-17 10:05+09');
```

`INSERT`가 돌아오지 않았다. 다른 세션에서 보면 그 연결이 `SyncRep`을 기다리고 있다.

```sql
-- [프라이머리, 다른 세션] 무엇을 기다리고 있나
SELECT pid, wait_event_type, wait_event, state, left(query, 40)
FROM pg_stat_activity WHERE wait_event = 'SyncRep';
```

```text
 pid  | wait_event_type | wait_event | state  |                   left
------+-----------------+------------+--------+------------------------------------------
 3158 | IPC             | SyncRep    | active | INSERT INTO orders VALUES (105,2,5000,'p
(1 row)
```

`statement_timeout = '3s'`을 걸어 두었는데도 끊기지 않았다. 커밋 기록은 이미 프라이머리 디스크에 내려갔고, 남은 건 스탠바이 확인을 기다리는 일이라 문장 시간 제한이 적용되지 않는다. `pg_cancel_backend(3158)`로 직접 취소하니 이렇게 나왔다.

```text
WARNING:  canceling wait for synchronous replication due to user request
DETAIL:  The transaction has already committed locally, but might not have been replicated to the standby.
INSERT 0 1
```

경고 문구 그대로다. 프라이머리에는 이미 커밋됐다. 그래서 이 주문은 `SELECT`로 조회된다. 앱 입장에서는 실패처럼 보였던 쓰기가 사실은 들어가 있는 셈이라, 재시도하면 중복 주문이 생길 수 있다. 주문 id를 앱에서 미리 정해 두면 재시도해도 같은 id라 중복을 막을 수 있다. 여러 서버에서 겹치지 않는 id를 만드는 방법은 [샤딩 글](/posts/db-sharding)에 있다.

<Callout kind="warning" title="동기 스탠바이를 한 대만 두면 그 한 대가 쓰기를 멈춘다">
`FIRST 1 (standby1)`처럼 스탠바이 한 대만 동기로 지정하면 그 서버가 죽거나 네트워크가 끊기는 순간 프라이머리의 모든 커밋이 멈춘다. 프라이머리를 지키려고 붙인 서버가 프라이머리를 세우는 것이다. 동기 복제를 쓸 거면 스탠바이를 두 대 이상 두고 `ANY 1 (standby1, standby2)`처럼 "둘 중 아무나 하나"를 기다리게 한다. 이미 멈췄다면 `ALTER SYSTEM SET synchronous_standby_names = ''`와 `SELECT pg_reload_conf()`로 비동기로 되돌리면 기다리던 커밋들이 풀린다. 또 `synchronous_commit`은 트랜잭션마다 바꿀 수 있으니, 결제처럼 중요한 쓰기만 `SET LOCAL synchronous_commit = on`으로 기다리고 나머지는 `local`로 두는 방법도 있다.
</Callout>

## 복제본에서 긴 쿼리가 끊긴다

복제본에서 무거운 통계 쿼리를 돌리면 이런 에러를 만날 수 있다. 스탠바이의 `max_standby_streaming_delay`를 2초로 줄이고, 스탠바이에서 오래 걸리는 트랜잭션을 여는 동안 프라이머리에서 행을 고치고 `VACUUM`을 돌려서 재현했다.

```text
ERROR:  canceling statement due to conflict with recovery
DETAIL:  User query might have needed to see row versions that must be removed.
```

프라이머리의 `VACUUM`은 아무도 안 보는 옛 행 버전을 지우고, 그 기록도 WAL로 스탠바이에 간다. 그런데 스탠바이에서 돌고 있는 쿼리는 그 옛 버전을 봐야 할 수 있다. 프라이머리는 스탠바이의 쿼리를 모른다. 스탠바이는 재생을 미루고 쿼리를 기다리다가, `max_standby_streaming_delay`(기본 30초)를 넘으면 쿼리를 취소하고 재생을 이어 간다. 쿼리를 무한정 기다리면 복제 지연이 끝없이 커지기 때문이다.

고르는 방법은 두 가지다. `hot_standby_feedback = on`을 켜면 스탠바이가 "나 아직 이 버전 본다"고 프라이머리에 알려서 프라이머리가 그 행을 지우지 않는다. 쿼리는 덜 끊기지만 프라이머리에 지우지 못한 행이 쌓여 테이블이 부푼다(bloat). 다른 방법은 분석용 복제본을 따로 두고 그쪽만 `max_standby_streaming_delay`를 크게 잡는 것이다. 그 복제본은 쿼리가 길어지면 몇 분씩 뒤처지지만 분석에는 상관없다. 화면용 복제본은 짧게 둔다.

## MySQL은 binlog로 복제한다

MySQL 8의 복제도 구조는 비슷하지만 보내는 것이 다르다. InnoDB의 내부 로그(redo log)가 아니라 바이너리 로그(binlog)라는 별도의 변경 기록을 보낸다. 8.0의 기본 형식(`binlog_format = ROW`)은 바뀐 행의 전후 값을 담는다. 레플리카는 받은 binlog를 relay log에 쓰고, SQL 스레드(8.0에서는 여러 개의 적용 스레드)가 그걸 다시 실행한다. 행 단위의 논리적인 기록이라 버전이 조금 달라도 복제가 되고, 필터로 일부 DB만 복제할 수 있다.

GTID(Global Transaction ID)를 켜면(`gtid_mode = ON`) 트랜잭션마다 `서버UUID:번호` 형태의 id가 붙는다. 장애 조치 때 새 프라이머리로 갈아탈 때 "binlog 파일 몇 번의 몇 바이트부터"를 계산할 필요 없이 "아직 안 받은 GTID부터"로 이어 받을 수 있어서 요즘은 거의 켜고 쓴다. 지연은 `SHOW REPLICA STATUS`의 `Seconds_Behind_Source`로 보는데, PostgreSQL의 타임스탬프 방식과 비슷하게 상황에 따라 실제와 다르게 보일 수 있다. 기다리는 쪽으로는 semi-synchronous 복제가 있다. 레플리카가 받았다고 답할 때까지 커밋 응답을 미루고, 시간 안에 답이 없으면 비동기로 내려간다. binlog 내용, GTID, 반동기 전환, 지연 측정은 [MySQL 복제와 온라인 DDL](/posts/mysql-replication-online-ddl)에서 서버 두 대로 직접 따라간다.

## 프라이머리가 죽으면 누가 이어받나

복제본이 있다고 장애가 자동으로 넘어가지는 않는다. 누군가 스탠바이를 프라이머리로 올려야 한다(승격, promote).

```bash
# [스탠바이] 프라이머리로 승격한다
sudo -u postgres psql -c "SELECT pg_promote()"

# 이제 복구 상태가 아니다 (f)
sudo -u postgres psql -c "SELECT pg_is_in_recovery()"
```

손으로 하면 사람이 깨어나는 시간만큼 멈춘다. 그래서 보통 Patroni 같은 도구를 쓴다. Patroni는 각 DB 서버 옆에서 돌면서 etcd나 Consul 같은 합의 저장소에 "지금 프라이머리는 나"라는 잠금(리더 키)을 일정 시간마다 갱신한다. 프라이머리가 죽어 잠금이 만료되면 남은 스탠바이 중 가장 많이 받은 쪽이 잠금을 잡고 승격한다. 관리형 서비스(RDS Multi-AZ, Aurora, Cloud SQL 등)는 이 과정을 대신 해 준다.

가장 위험한 장애는 프라이머리가 두 대가 되는 것이다(split-brain). 옛 프라이머리가 죽은 게 아니라 네트워크만 끊겼다면, 스탠바이가 승격된 뒤에도 옛 프라이머리는 자기가 프라이머리인 줄 알고 쓰기를 받는다. 두 서버에 서로 다른 주문이 쌓이고, 나중에 합칠 방법이 없다. Patroni는 리더 키를 갱신하지 못한 프라이머리가 스스로 읽기 전용으로 내려가게 하고, 그래도 불안하면 watchdog으로 서버를 강제로 재부팅하게 한다. 이렇게 옛 프라이머리를 확실히 끊는 일을 펜싱(fencing)이라고 한다. 살아난 옛 프라이머리는 `pg_rewind`로 새 프라이머리와 갈라진 부분을 되감은 뒤 스탠바이로 다시 붙인다.

앱은 프라이머리가 바뀌어도 따라가야 한다. 가상 IP나 DNS, HAProxy 같은 프록시를 앞에 두는 방법이 있고, libpq 기반 드라이버라면 연결 문자열에 서버를 여러 개 적고 쓰기 가능한 쪽만 고르게 할 수도 있다.

```bash
# 두 서버 중 쓰기 가능한(프라이머리) 쪽에 붙는다
psql "postgresql://app@10.0.0.11:5432,10.0.0.12:5432/shop?target_session_attrs=read-write"
```

비동기 복제에서 장애 조치를 하면 프라이머리가 스탠바이에 보내지 못한 마지막 커밋은 사라진다. 실제로 얼마나 멈추고 무엇을 잃는지는 [장애 조치](/posts/failover) 글에서 직접 잰다. 얼마나 잃어도 되는지(RPO)와 얼마나 멈춰도 되는지(RTO)를 먼저 정하고, 그 답에 맞춰 동기 여부와 스탠바이 대수를 정한다.

## 언제 다음 단계로 넘어가나

숫자는 하드웨어와 쿼리 모양에 따라 크게 달라서 출발점으로만 본다.

쿼리와 인덱스를 고쳤는데도 프라이머리 CPU가 바쁜 시간대에 70%를 넘게 머물고, 그 대부분이 읽기라면 복제본을 붙인다. `pg_stat_statements`에서 SELECT가 총 실행 시간의 대부분을 차지하는지 먼저 본다. 장애 대비용 스탠바이는 규모와 상관없이 처음부터 두는 편이 낫다.

테이블 하나가 수십 GB를 넘어 서버 메모리보다 커지고, 날짜 범위로 조회하거나 오래된 데이터를 정기적으로 지워야 한다면 [파티셔닝](/posts/db-partitioning)을 본다. 1년치를 남기고 지우는 `DELETE` 배치가 복제 지연을 몇 분씩 만들거나, `VACUUM`이 그 테이블 하나에서 몇 시간씩 돈다면 늦은 편이다. 지울 일이 없고 쿼리에 파티션 키가 안 들어간다면 파티셔닝은 오히려 느려질 수 있다.

[샤딩](/posts/db-sharding)은 쓰기 자체가 한계일 때 간다. 가장 큰 인스턴스로 올렸는데도 쓰기 때문에 WAL 쓰기나 디스크가 포화되거나, 데이터가 수 TB로 커져 백업 복원과 복제본 하나 새로 만드는 데 하루가 걸리는 상황이다. 읽기만 많다면 샤딩보다 복제본과 캐시가 훨씬 싸다. 샤딩은 앱 코드, 운영, 장애 대응 방식이 다 바뀌기 때문에 다른 방법이 바닥났을 때 꺼내는 마지막 카드에 가깝다.

## 복제는 읽기를 나누고, 늦을 수 있다

DB 한 대가 버거울 때는 먼저 쿼리와 인덱스를 고치고 서버를 키운다. 그래도 읽기가 문제면 WAL을 받아 재생하는 복제본으로 읽기를 나눈다. 복제본은 프라이머리와 바이트 단위로 같은 사본이지만 늦을 수 있다. 그래서 방금 쓴 것을 읽는 경로는 프라이머리로 보내거나 LSN으로 확인하고, 지연은 시간과 바이트 차이를 함께 감시한다. 동기 복제는 그 틈을 줄이는 대신 커밋마다 기다림을 얹고, 동기 스탠바이 한 대가 쓰기 전체를 세울 수 있다. 복제는 쓰기를 나눠 주지 않는다. 테이블이 너무 커지면 [파티셔닝](/posts/db-partitioning)으로, 쓰기가 한 대를 넘으면 [샤딩](/posts/db-sharding)으로 간다.

## 면접에서 나올 만한 질문

### 레플리케이션과 샤딩은 무엇이 다른가요?

복제는 같은 데이터를 여러 서버에 복사하는 것이고, 샤딩은 데이터를 나눠서 서버마다 다른 부분을 담는 것이다. 복제는 읽기를 나누고 장애에 대비하지만 쓰기는 여전히 프라이머리 한 대가 받는다. 샤딩은 쓰기와 저장 용량을 나누지만 샤드를 넘는 조인, 트랜잭션, 재분배가 어려워진다. 보통 샤드마다 복제본을 두어 둘을 같이 쓴다.

### 복제 지연 때문에 방금 쓴 데이터가 안 보이면 어떻게 하나요?

비동기 복제는 프라이머리가 커밋 응답을 먼저 주고 WAL을 나중에 보내서 생기는 문제다. 쓰기 직후 몇 초 동안 그 사용자의 읽기를 프라이머리로 보내거나, 결제처럼 중요한 화면은 항상 프라이머리에서 읽는다. 더 정확하게는 커밋 후 `pg_current_wal_lsn()`을 세션에 저장하고, 복제본의 `pg_last_wal_replay_lsn()`이 그 위치를 넘었을 때만 복제본에서 읽는다. `synchronous_commit = remote_apply`도 있지만 모든 커밋이 느려진다.

### synchronous_commit의 on과 remote_apply는 어떻게 다른가요?

동기 스탠바이가 지정돼 있을 때 on은 스탠바이가 WAL을 디스크에 flush할 때까지 기다리고, remote_apply는 재생까지 끝나 쿼리에 보일 때까지 기다린다. on이면 프라이머리가 사라져도 커밋은 남지만 스탠바이에서 바로 읽으면 안 보일 수 있다. 동기 스탠바이가 한 대뿐이면 그 서버 장애가 프라이머리 쓰기를 멈추게 하니 `ANY 1 (s1, s2)`처럼 두 대 이상을 둔다.

### 복제 슬롯을 쓸 때 주의할 점은요?

복제 슬롯은 스탠바이가 아직 받아 가지 않은 WAL을 프라이머리가 지우지 않게 붙잡아 둔다. 덕분에 스탠바이가 잠깐 끊겨도 이어 받을 수 있지만, 스탠바이가 오래 죽어 있으면 프라이머리에 WAL이 끝없이 쌓인다. 16의 `max_slot_wal_keep_size` 기본값은 제한 없음이라 그대로 두면 프라이머리 디스크가 차서 프라이머리까지 멈춘다. 디스크 여유에 맞춰 상한을 정하고 `pg_replication_slots`에서 `active = f`인 슬롯을 감시한다.

### 복제본에서 긴 쿼리가 "conflict with recovery"로 끊기는 이유는요?

프라이머리의 VACUUM이 옛 행 버전을 지운 기록이 스탠바이로 오는데, 스탠바이에서 돌던 쿼리가 그 버전을 봐야 할 수 있어서다. 스탠바이는 재생을 미루고 기다리다가 `max_standby_streaming_delay`(기본 30초)를 넘으면 쿼리를 취소한다. `hot_standby_feedback = on`을 켜면 덜 끊기지만 프라이머리 테이블이 부풀고, 분석용 복제본을 따로 두어 그쪽만 지연 한도를 크게 잡는 방법도 있다.

### 프라이머리 장애 조치에서 split-brain은 어떻게 막나요?

네트워크만 끊긴 옛 프라이머리가 계속 쓰기를 받으면 두 서버에 서로 다른 데이터가 쌓이고 합칠 방법이 없다. Patroni 같은 도구는 etcd 같은 합의 저장소의 리더 키를 갱신하지 못한 프라이머리를 스스로 읽기 전용으로 내리고, 필요하면 watchdog으로 재부팅해 확실히 끊는다(펜싱). 살아난 옛 프라이머리는 `pg_rewind`로 되감아 스탠바이로 다시 붙인다. 비동기 복제라면 보내지 못한 마지막 커밋은 잃으니 RPO와 RTO를 먼저 정한다.
