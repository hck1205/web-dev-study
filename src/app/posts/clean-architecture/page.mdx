  요청은 바깥에서 들어와 안쪽까지 갔다가 다시 나가야 하는데, 안쪽이 바깥을 부르지 않으려면 안쪽에 인터페이스를 두고 바깥이 그것을 구현한다. 원을 건너는 데이터는 그 원의 단순한 자료 구조로 바꾼다. 이렇게 하면 7일 규칙을 프레임워크 없이 테스트할 수 있지만 파일이 여섯 배 넘게 늘어나니, 규칙이 무거운 곳에만 원을 다 쓰고 단순 조회는 접는 게 맞다.

Express로 만든 주문 서비스를 다른 프레임워크로 옮기기로 했다고 해 보자. 라우터만 바꾸면 될 줄 알았는데, "결제 후 7일 안에만 취소된다"는 규칙이 `req.params`와 `res.status(409)` 사이에 끼어 있다. 취소 가능 여부를 판단하는 `if` 문이 ORM 모델의 메서드를 부르고, 그 모델은 데코레이터로 테이블과 묶여 있다. 업무 규칙만 떼어 옮기려 했는데, 잡아당기면 프레임워크와 DB가 함께 딸려 나온다.

클린 아키텍처(clean architecture)는 이 딸려 나오는 고리를 끊는 규칙이다. 로버트 C. 마틴이 2012년 블로그 글에서 그림 한 장으로 정리했고, 2017년 같은 이름의 책으로 풀어 썼다. 생각의 뿌리는 [헥사고날 아키텍처](/posts/hexagonal-architecture)와 같다. 이 글은 포트와 어댑터의 기본을 반복하지 않고, 클린 아키텍처가 더 정해 둔 부분을 본다. 원을 건너는 데이터의 모양, 프레젠터, 의존 규칙을 기계로 지키는 법, 그리고 그 비용이다. 의존 방향을 뒤집는 첫걸음은 [레이어드 아키텍처 글](/posts/layered-architecture)에 있다.

예제는 Node 22와 TypeScript(`--experimental-strip-types`)로 돌렸다. 주문 취소 하나를 원 네 개에 나눠 담았다.

## 원 네 개와 규칙 하나

그림은 동심원이다. 가장 안쪽부터 엔티티, 유스케이스, 인터페이스 어댑터, 프레임워크와 드라이버.

엔티티는 이 회사가 소프트웨어가 없어도 지키는 규칙이다. "결제된 주문만, 결제 후 7일 안에만 취소된다"가 여기에 들어간다. 유스케이스는 이 애플리케이션이 하는 일이다. "주문을 불러와 취소 규칙을 적용하고 저장한 뒤 결과를 알린다"는 절차가 여기에 있다. 인터페이스 어댑터는 바깥의 형식과 안쪽의 형식을 서로 바꾼다. 컨트롤러, 프레젠터, DB 게이트웨이가 여기다. 가장 바깥은 웹 프레임워크, DB 드라이버, UI처럼 남이 만든 도구다.

규칙은 하나다. 소스 코드의 의존은 안쪽으로만 향한다. 안쪽 원의 코드는 바깥 원에 있는 것의 이름을 한 번도 쓰지 않는다. 함수 이름, 클래스, 타입, 변수 모두 해당한다. 마틴은 이걸 의존 규칙(Dependency Rule)이라고 불렀다.

원이 꼭 네 개일 필요는 없다고 마틴 스스로 적었다. 원의 수는 바뀌어도 화살표 방향은 바뀌지 않는다. 실제 프로젝트에서는 폴더 네 개로 옮기는 경우가 많고, 이 글의 예제도 그렇다.

```text
src/
  domain/order.ts                    엔티티: cancel(order, now)
  application/cancel-order.ts        유스케이스, 입력·출력 모델, 필요한 포트
  adapters/order-controller.ts       요청 → 입력 모델
  adapters/presenters.ts             출력 모델 → 뷰 모델
  adapters/sqlite-order-gateway.ts   행 ↔ 엔티티
  frameworks/main.ts                 DB 연결, 조립, 실행
```

엔티티는 아무것도 import하지 않는다.

```ts
// src/domain/order.ts
export type OrderStatus = "PAID" | "SHIPPED" | "CANCELLED";
export type Order = { id: string; status: OrderStatus; paidAt: Date; total: number };

const CANCEL_WINDOW_MS = 7 * 24 * 60 * 60 * 1000;

export function cancel(order: Order, now: Date): Order {
  if (order.status !== "PAID") throw new DomainError(`NOT_CANCELLABLE:${order.status}`);
  if (now.getTime() - order.paidAt.getTime() > CANCEL_WINDOW_MS) throw new DomainError("WINDOW_CLOSED");
  return { ...order, status: "CANCELLED" };
}

export class DomainError extends Error {}
```

## 호출은 밖에서 안으로 갔다가 다시 밖으로

헷갈리는 지점은 실행 흐름과 의존 방향이 다르다는 사실이다. 요청은 바깥에서 들어와 안쪽까지 갔다가, 결과를 들고 다시 바깥으로 나간다. 그런데 소스 코드의 화살표는 그동안 계속 안쪽을 향해야 한다.

들어갈 때는 문제가 없다. 컨트롤러가 유스케이스를 import해서 부르면 된다. 나올 때가 문제다. 유스케이스가 DB에 저장하고 화면에 결과를 내려면 바깥을 불러야 한다. 이때 유스케이스는 바깥을 부르지 않고, 자기 원 안에 인터페이스를 선언한 뒤 그 인터페이스를 부른다. 바깥 원이 그 인터페이스를 구현해서 넘겨준다. 경계를 넘을 때마다 이렇게 의존을 뒤집는다.

```ts
// src/application/cancel-order.ts
import { cancel, DomainError, type Order } from "../domain/order.ts";

export type CancelOrderInput = { orderId: string };
export type CancelOrderOutput = { orderId: string; refundAmount: number };

export interface OrderGateway { load(id: string): Order | null; store(order: Order): void }
export interface Clock { now(): Date }
export interface CancelOrderPresenter {
  cancelled(out: CancelOrderOutput): void;
  rejected(reason: string): void;
  notFound(orderId: string): void;
}

export function cancelOrder(deps: { orders: OrderGateway; clock: Clock }) {
  return (input: CancelOrderInput, presenter: CancelOrderPresenter): void => {
    const order = deps.orders.load(input.orderId);
    if (!order) return presenter.notFound(input.orderId);
    try {
      const next = cancel(order, deps.clock.now());
      deps.orders.store(next);
      presenter.cancelled({ orderId: next.id, refundAmount: next.total });
    } catch (e) {
      if (e instanceof DomainError) return presenter.rejected(e.message);
      throw e;
    }
  };
}
```

아래 그림에서 다음을 누르면 `DELETE /orders/o1` 하나가 원을 오가는 순서가 나온다. 화살표는 호출 방향이고, 설명에는 그 호출의 소스 코드 의존이 어느 쪽인지 적었다.

## 원을 건너는 데이터는 그 원의 모양으로

원 경계를 건너는 데이터는 단순한 자료 구조여야 한다. 마틴은 DB 행이나 프레임워크의 요청 객체를 그대로 안쪽으로 넘기지 말라고 했다. 그것들은 바깥 원의 모양이라, 넘기는 순간 안쪽이 바깥 형식을 알게 된다.

그래서 유스케이스는 자기 입력 모델(`CancelOrderInput`)과 출력 모델(`CancelOrderOutput`)을 직접 정의한다. 컨트롤러는 요청을 입력 모델로 바꾸고, 게이트웨이는 행을 엔티티로 바꾼다.

```ts
// src/adapters/order-controller.ts
export function toCancelInput(req: HttpRequest): CancelOrderInput {
  return { orderId: req.params.id };
}

// src/adapters/sqlite-order-gateway.ts
load(id) {
  const r = db.prepare("SELECT id, status, paid_at, total FROM orders WHERE id = ?").get(id) as any;
  return r ? { id: r.id, status: r.status, paidAt: new Date(r.paid_at), total: r.total } : null;
},
```

게이트웨이가 `paid_at` 문자열을 `Date`로 바꾸는 한 줄이 이 원칙의 실제 모습이다. 엔티티는 컬럼 이름도, 날짜가 TEXT로 저장된다는 사실도 모른다.

출력 모델에 엔티티를 그대로 넣고 싶은 유혹이 있다. 필드가 똑같아 보일 때 특히 그렇다. 그러면 화면에 무엇을 보여 줄지가 엔티티 모양에 묶인다. 엔티티에 내부용 필드(예: 결제사 거래 번호)를 추가하는 순간 그 필드가 API 응답에 섞여 나간다. 출력 모델은 화면에 필요한 것만 담는다. 위 예제가 `refundAmount`라는 이름을 따로 둔 것도 그래서다. 지금은 `total`과 같지만, 부분 환불이 생기면 달라질 값이다.

## 프레젠터가 따로 있는 이유

헥사고날 아키텍처에서는 유스케이스가 결과 값을 return하고 들어오는 어댑터가 그걸 응답으로 바꾸는 경우가 많다. 클린 아키텍처는 결과를 출력 포트(프레젠터 인터페이스)로 내보내는 모양을 기본으로 그린다. 이렇게 하면 "200이냐 409냐", "금액에 쉼표를 찍을까" 같은 결정을 모두 프레젠터에 모을 수 있다.

```ts
// src/adapters/presenters.ts
export function jsonPresenter() {
  const vm: { value?: HttpViewModel } = {};
  const p: CancelOrderPresenter = {
    cancelled: (o) => { vm.value = { status: 200, body: { id: o.orderId, refund: o.refundAmount.toLocaleString("ko-KR") + "원" } }; },
    rejected: (r) => { vm.value = { status: 409, body: { error: r } }; },
    notFound: (id) => { vm.value = { status: 404, body: { error: `order ${id} not found` } }; },
  };
  return { p, vm };
}

export function cliPresenter(print: (line: string) => void): CancelOrderPresenter {
  return {
    cancelled: (o) => print(`취소 완료: ${o.orderId}, 환불 ${o.refundAmount}원`),
    rejected: (r) => print(`취소 불가: ${r}`),
    notFound: (id) => print(`주문 없음: ${id}`),
  };
}
```

같은 유스케이스를 두 프레젠터로 돌렸다. 시계는 `2026-10-21T12:00:00Z`로 고정했고, o1은 사흘 전, o2는 20일 전에 결제됐고, o3는 이미 배송 중이다.

```bash
node --experimental-strip-types src/frameworks/main.ts
```

```text

DELETE /orders/o1 -> {"status":409,"body":{"error":"NOT_CANCELLABLE:CANCELLED"}}
DELETE /orders/o2 -> {"status":409,"body":{"error":"WINDOW_CLOSED"}}
DELETE /orders/o3 -> {"status":409,"body":{"error":"NOT_CANCELLABLE:SHIPPED"}}
DELETE /orders/o9 -> {"status":404,"body":{"error":"order o9 not found"}}
---- 같은 유스케이스, CLI 프레젠터

```

두 번째 줄이 눈여겨볼 곳이다. 같은 주문을 두 번 취소하면 엔티티 규칙이 막고, 프레젠터가 그 거절을 409로 바꾼다. 상태 코드를 정하는 코드는 프레젠터에만 있다. 프레젠터와 뷰를 나누면 뷰는 받은 값을 그대로 찍기만 하는 얇은 껍데기가 된다. 테스트하기 어려운 부분(화면, 프레임워크)을 최대한 멍청하게 만들고, 판단은 테스트하기 쉬운 쪽으로 옮기는 방법이다. 제라드 메사로스가 테스트 패턴으로 이름 붙인 험블 오브젝트(Humble Object)이고, 마틴은 프레젠터와 뷰의 경계에 이걸 쓴다.

다만 유스케이스가 return으로 출력 모델을 돌려주고 컨트롤러가 프레젠터 함수를 부르는 방식도 의존 규칙을 어기지 않는다. 출력 포트를 꼭 콜백 인터페이스로 만들어야 하는 건 아니다. 한 유스케이스의 결과를 여러 형식으로 내야 하거나 결과가 여러 번 나오는 경우(진행률 같은 것)에 콜백 모양이 더 잘 맞는다.

## 시간도 바깥에서 들어온다

엔티티 함수 `cancel`은 현재 시각을 인자로 받는다. 안에서 `new Date()`를 부르면 시계라는 바깥 세계에 의존하게 되고, "정확히 7일째"를 테스트할 방법이 없어진다. 유스케이스는 `Clock` 포트로 시각을 받아 엔티티에 넘긴다.

경계값을 테스트로 고정해 둔다.

```ts
test("결제 후 정확히 7일째는 취소된다", () => {
  assert.deepEqual(harness("2026-10-14T12:00:00Z", "2026-10-21T12:00:00Z"), { seen: ["cancelled 24000"], status: "CANCELLED" });
});
test("7일하고 1ms가 지나면 거절된다", () => {
  assert.deepEqual(harness("2026-10-14T12:00:00Z", "2026-10-21T12:00:00.001Z"), { seen: ["rejected WINDOW_CLOSED"], status: "PAID" });
});
```

```text
✔ 결제 후 정확히 7일째는 취소된다 (3.44776ms)
✔ 7일하고 1ms가 지나면 거절된다 (0.398494ms)
```

이 테스트를 쓰다 보면 업무 질문이 하나 생긴다. "7일"이 밀리초로 168시간인가, 한국 시간 기준 달력으로 7일째 자정까지인가. 코드는 지금 앞의 뜻이다. 이 질문은 엔티티를 프레임워크에서 떼어 놓고 테스트할 수 있어야 비로소 눈에 띈다. 고칠 곳도 엔티티 한 곳이다.

## 의존 규칙을 사람 대신 검사기가 지킨다

규칙은 문서에만 있으면 금방 깨진다. 급하게 리포트 기능을 넣던 누군가가 유스케이스 폴더에 DB 드라이버를 import하는 식이다. 그래서 import 문을 읽어 원을 비교하는 검사기를 CI에 둔다. 아래는 34줄짜리 검사기 전체다.

```js
// check-deps.mjs
import fs from "node:fs";
import path from "node:path";

const RINGS = ["domain", "application", "adapters", "frameworks"]; // 안쪽 → 바깥
const PACKAGES_ALLOWED_FROM = RINGS.indexOf("adapters");         // 외부 패키지는 adapters부터

const ringOf = (file) => RINGS.findIndex((r) => file.split(path.sep).includes(r));
const files = fs.readdirSync("src", { recursive: true }).filter((f) => f.endsWith(".ts")).map((f) => path.join("src", f));

let violations = 0;
for (const file of files) {
  const from = ringOf(file);
  const lines = fs.readFileSync(file, "utf8").split("\n");
  lines.forEach((line, i) => {
    const m = line.match(/^\s*import\s.*?from\s+["']([^"']+)["']/);
    if (!m) return;
    const spec = m[1];
    if (!spec.startsWith(".")) {
      if (from < PACKAGES_ALLOWED_FROM) {
        console.log(`✖ ${file}:${i + 1} ${RINGS[from]} → package "${spec}"`);
        violations++;
      }
      return;
    }
    const to = ringOf(path.join(path.dirname(file), spec));
    if (to > from) {
      console.log(`✖ ${file}:${i + 1} ${RINGS[from]} → ${RINGS[to]} (${spec})`);
      violations++;
    }
  });
}
console.log(`${files.length} files, ${violations} violation(s)`);
process.exit(violations ? 1 : 0);
```

처음엔 깨끗하다. 그다음 유스케이스 폴더에 리포트 파일을 하나 넣고, 엔티티 파일 끝에 디버그용 import를 한 줄 붙인 뒤 다시 돌렸다.

```ts
// src/application/order-report.ts
import { DatabaseSync } from "node:sqlite";
import type { HttpViewModel } from "../adapters/presenters.ts";
import type { Order } from "../domain/order.ts";
```

## 폴더 이름이 업무를 말하게

마틴은 2011년 글에서 프로젝트의 최상위 폴더를 열었을 때 "이건 Rails 앱이다"가 아니라 "이건 주문 시스템이다"가 보여야 한다고 썼다. 이름하여 소리치는 아키텍처(Screaming Architecture)다.

```text
# 프레임워크가 소리치는 구조       # 업무가 소리치는 구조
src/                              src/
  controllers/                      ordering/
  services/                           domain/ application/ adapters/
  repositories/                     refunds/
  models/                             domain/ application/ adapters/
                                    frameworks/
```

왼쪽은 기능 하나를 고칠 때 네 폴더를 오간다. 오른쪽은 업무 단위로 먼저 자르고, 그 안에서 원을 나눈다. 주문 팀과 환불 팀이 따로 있다면 오른쪽이 훨씬 덜 부딪힌다. 업무 단위를 어떻게 자르는지는 [바운디드 컨텍스트 글](/posts/ddd-bounded-context)에서 이어 간다.

## 헥사고날, 어니언과 나란히 놓으면

비슷한 구조가 세 이름으로 불린다. 셋 다 업무 규칙을 가운데 두고 의존을 안쪽으로 모은다는 점은 같고, 무엇을 더 정해 두었는지가 다르다.

| | 헥사고날 (2005) | 어니언 (2008) | 클린 (2012) |
|---|---|---|---|
| 만든 사람 | 앨리스터 코번 | 제프리 팔레르모 | 로버트 C. 마틴 |
| 나누는 축 | 안과 밖, 포트와 어댑터 | 도메인 모델, 도메인 서비스, 애플리케이션 서비스, 바깥 | 엔티티, 유스케이스, 어댑터, 프레임워크 |
| 안쪽을 몇 겹으로 | 정하지 않는다 | 여러 겹 | 여러 겹 (넷은 예시) |
| 결과를 내보내는 법 | 정하지 않는다 | 정하지 않는다 | 출력 포트(프레젠터)를 그린다 |
| 강조하는 것 | 입구와 출구의 대칭, 테스트 | 도메인 모델이 중심 | 의존 규칙, 원을 건너는 데이터 |

현장에서 따질 것은 이름이 아니라 실제로 지켜지는 규칙이다. "코어는 바깥을 모른다", "바깥의 형식은 경계에서 바꾼다", "조립은 한 곳에서 한다". 세 이름 모두 이 셋으로 대부분 설명된다. 면접에서 차이를 물으면 클린 아키텍처가 안쪽을 엔티티와 유스케이스로 더 나누고, 경계를 건너는 데이터와 프레젠터까지 규칙으로 정했다고 답하면 된다.

## 화면 쪽에서 원을 그리면

React 앱에도 같은 원을 그릴 수 있다. 장바구니 합계, 쿠폰 적용 순서, 주문 취소 가능 여부처럼 화면과 상관없는 규칙은 순수 함수로 엔티티 원에 둔다. "취소 버튼을 누르면 확인을 받고, API를 부르고, 목록을 갱신한다" 같은 절차는 유스케이스에 해당한다. 커스텀 훅이 그 절차를 React 상태로 바꾸는 어댑터가 되고, 컴포넌트와 Next.js는 가장 바깥 원이다.

```ts
// domain/cancel-policy.ts: React도 fetch도 모른다
export function canCancel(order: { status: string; paidAt: string }, now: Date) {
  return order.status === "PAID" && now.getTime() - Date.parse(order.paidAt) <= 7 * 864e5;
}

// adapters/use-cancel-button.ts: 규칙의 결과를 화면 상태로 바꾼다
export function useCancelButton(order: OrderView) {
  const now = useNow();                                  // 시계도 훅으로 주입
  return { disabled: !canCancel(order, now), label: canCancel(order, now) ? "취소" : "취소 기간 지남" };
}
```

이렇게 나누면 취소 정책 테스트에 렌더링이 필요 없다. 다만 화면 코드에서 원을 끝까지 나누면 비용이 빨리 커진다. 컴포넌트마다 프레젠터 인터페이스를 만드는 건 대개 과하다. 규칙이 있는 곳만 순수 함수로 빼고, 나머지는 훅과 컴포넌트로 두는 정도가 맞는 경우가 많다. 순수 함수가 테스트를 어떻게 쉽게 하는지는 [순수 함수 글](/posts/js-pure-functions)에 따로 있다.

## 파일이 늘어나는 값을 따져 본다

주문 취소 하나에 파일이 여섯 개다.

같은 기능을 핸들러 함수 하나에 몰아 쓰면 DB 준비와 실행 코드까지 합쳐 18줄이다. 여섯 배 넘는 코드를 들여 얻은 것은 프레임워크 없이 도는 업무 규칙 테스트, 두 프레젠터에서 같은 판단, 경계값 질문을 드러내는 구조다. 이 거래가 남는지는 규칙의 무게에 달렸다.

남지 않는 신호는 이렇다. 유스케이스 대부분이 게이트웨이 메서드 하나를 부르고 결과를 그대로 넘긴다. 입력 모델, 엔티티, 출력 모델, 뷰 모델의 필드가 모두 똑같아서 필드 하나를 추가할 때마다 네 파일을 고친다. 이런 기능은 원을 접어도 된다. 조회 화면은 유스케이스 없이 어댑터가 읽기 전용 쿼리를 바로 부르게 두고, 규칙이 있는 쓰기 쪽에만 원을 다 쓰는 식으로 섞는 것도 흔하다. 읽기와 쓰기를 아예 다른 모델로 나누는 이야기는 [CQRS 글](/posts/cqrs)로 이어진다.

흔한 실수도 여기서 나온다. ORM 엔티티를 엔티티 원에 두면 가장 안쪽 원이 ORM 패키지를 import한다. 유스케이스가 `Request`나 `Response` 타입을 받으면 프레임워크를 바꿀 때 유스케이스를 고쳐야 한다. 모든 원이 함께 쓰는 `common/dto` 폴더를 만들면 원 사이 경계가 그 폴더 하나로 무너진다. 그리고 구조를 지키느라 생긴 빈 껍데기 파일이 많아지면, 그건 규칙이 무거운 곳과 가벼운 곳을 같은 틀로 찍어 낸 결과다.

클린 아키텍처에서 남겨야 할 것은 원의 개수가 아니라 화살표 방향이다. 업무 규칙이 프레임워크와 DB의 이름을 모르게 하고, 경계를 건널 때는 그 원의 자료 구조로 바꾸고, 그 규칙을 사람이 아니라 검사기가 지키게 한다. 처음 장면의 "7일 안에만 취소"는 그러면 `cancel(order, now)` 한 함수로 따로 옮겨진다.

## 면접에서 나올 만한 질문

### 클린 아키텍처의 의존 규칙이 무엇인가요?

소스 코드의 의존은 안쪽 원으로만 향해야 한다는 규칙이다. 엔티티와 유스케이스는 바깥의 프레임워크, DB, UI의 이름을 하나도 쓰지 않는다. 실행 흐름이 바깥으로 나가야 할 때는 안쪽에 인터페이스를 두고 바깥이 그걸 구현하게 해서 의존을 뒤집는다.

### 엔티티와 유스케이스는 무엇이 다른가요?

엔티티는 소프트웨어가 없어도 회사가 지키는 업무 규칙이고, 유스케이스는 이 애플리케이션이 그 규칙을 써서 하는 절차다. "결제 후 7일 안에만 취소"는 엔티티, "주문을 불러와 취소 규칙을 적용하고 저장한 뒤 결과를 알린다"는 유스케이스다. 그래서 엔티티는 여러 애플리케이션이 공유할 수 있고, 유스케이스는 애플리케이션마다 다르다.

### 원을 건널 때 엔티티를 그대로 넘기면 안 되나요?

안쪽으로 바깥의 형식(요청 객체, DB 행)을 넘기는 건 규칙 위반이고, 바깥으로 엔티티를 그대로 내보내는 것도 피하는 게 좋다. 엔티티를 응답에 그대로 쓰면 내부용 필드가 API에 섞여 나가고, 화면 요구가 엔티티 모양을 끌고 다닌다. 각 경계에 그 원의 단순한 자료 구조를 두고 어댑터에서 바꾼다.

### 프레젠터는 왜 따로 두나요?

상태 코드, 숫자 형식, 문구처럼 보여 주는 방식의 결정을 한곳에 모으려고 둔다. 그러면 뷰는 받은 값을 찍기만 하는 얇은 껍데기가 되고, 판단은 테스트하기 쉬운 프레젠터로 간다. 같은 유스케이스를 HTTP와 CLI에 함께 쓸 때도 프레젠터만 바꾸면 된다. 유스케이스가 출력 모델을 return하고 컨트롤러가 프레젠터를 부르는 방식도 규칙에 어긋나지 않는다.

### 헥사고날 아키텍처와 어떻게 다른가요?

방향은 같고 정해 둔 정도가 다르다. 헥사고날은 안과 밖, 포트와 어댑터만 말하고 안쪽을 어떻게 나눌지는 열어 둔다. 클린 아키텍처는 안쪽을 엔티티와 유스케이스로 나누고, 원을 건너는 데이터의 모양과 출력 포트까지 규칙으로 그린다.

### 이 규칙이 깨지지 않게 하려면 어떻게 하나요?

사람의 리뷰에 맡기지 않고 import 검사를 CI에 넣는다. 원의 순서를 설정에 적고, 안쪽 파일이 바깥 원이나 외부 패키지를 import하면 빌드를 멈춘다. ESLint 규칙이나 의존 그래프 검사 도구로 할 수 있고, `import type`도 결합이니 함께 막는 편이 낫다.

### 클린 아키텍처의 단점은 무엇인가요?

파일과 변환 코드가 많이 늘어난다. 규칙이 거의 없는 CRUD에서는 입력 모델, 엔티티, 출력 모델, 뷰 모델이 모두 같은 필드라서 필드 하나에 네 파일을 고치게 된다. 그래서 규칙이 무거운 쓰기 쪽에만 원을 다 쓰고, 단순 조회는 어댑터가 바로 읽게 하는 식으로 섞어 쓰는 경우가 많다.
