서비스가 커지면서 서버끼리 주고받는 트래픽이 늘었다. 마이크로서비스가 서로 부르고, 데이터베이스가 복제를 보내고, 분산 스토리지가 블록을 세 군데에 나눠 쓴다. 어느 날 모니터링에서 이상한 그래프가 보였다. 서버 쪽 포트는 한가한데 코어 스위치로 올라가는 업링크가 먼저 꽉 찼다. 같은 데이터 센터 안의 두 서버가 대화하는데, 그 패킷이 매번 건물 맨 꼭대기 장비까지 올라갔다 내려오고 있었다.

망은 처음 설계할 때 정한 모양에서 쉽게 벗어나지 못한다. 케이블을 다시 깔고 장비를 바꾸는 일이라 그렇다. 이 글은 선을 잇는 기본 모양(토폴로지)에서 시작해, 오랫동안 기업 망의 표준이던 3계층 구조와 그 축약형인 2계층 구조, 그리고 서버 간 트래픽이 늘면서 데이터 센터의 표준이 된 스파인-리프 구조를 비교한다. 업링크가 얼마나 모자란지 숫자로 재는 오버서브스크립션 계산, ECMP가 실제로 흐름을 나누는 모습, 장애 도메인과 주소 계획 같은 설계 원칙, 그리고 클라우드 VPC 설계로 이어지는 부분까지 본다.

라우터와 스위치의 차이, STP는 [라우터와 스위치 글](/posts/router-vs-switch)에서, 라우터끼리 길을 배우는 방법은 [동적 라우팅 프로토콜 글](/posts/routing-protocols-ospf-rip-eigrp)에서, 게이트웨이와 링크 이중화는 [게이트웨이와 링크 이중화 글](/posts/gateway-link-redundancy-fhrp-lacp)에서 다뤘다. ECMP 실측은 Ubuntu 24.04의 네트워크 네임스페이스에서 했고 출력은 그대로 옮겼다.

## 선을 어떻게 이을까

망의 모양부터 보자. 모든 장비를 선 하나에 매다는 버스, 고리로 잇는 링은 지금 랜에서는 거의 사라졌다. 남은 것은 셋이다.

스타(star)는 가운데 장비 하나에 모두를 잇는다. 사무실 스위치 하나에 PC가 다 꽂힌 모양이다. 단순하고 선이 적지만 가운데 장비가 단일 장애 지점이다. 메시(mesh)는 장비끼리 서로 직접 잇는다. 모든 쌍을 잇는 풀 메시는 장비 n대에 선이 n(n−1)/2개 필요하다. 10대면 45개, 50대면 1,225개다. 경로가 많아 튼튼하지만 금방 감당할 수 없게 된다. 그래서 실제 망은 중요한 장비끼리만 잇는 부분 메시, 그리고 스타를 여러 층으로 쌓은 트리(계층형) 구조가 대부분이다.

설계의 질문은 결국 "어디를 겹치게 잇고 어디를 한 가닥으로 둘까"다. 겹치게 이을수록 튼튼하지만 비싸고, 고리가 생기면 L2에서는 STP가 일부를 막아 버린다. 아래의 3계층과 스파인-리프는 이 질문에 대한 두 가지 답이다.

액세스(access) 계층은 PC, 서버, 프린터, AP가 실제로 꽂히는 스위치다. 포트가 많고 저렴하며, VLAN 지정, 포트 보안, PoE처럼 단말 하나하나를 다루는 일을 한다. 디스트리뷰션(distribution, 데이터 센터에서는 aggregation이라고도 한다) 계층은 액세스 스위치 여러 대를 모은다. 보통 여기가 L2와 L3의 경계다. VLAN 사이 라우팅, 게이트웨이(VRRP나 HSRP로 이중화), ACL과 QoS 같은 정책이 여기 있다. 그리고 아래쪽 대역을 요약해 코어에 올린다. 코어(core) 계층은 디스트리뷰션끼리를 잇는 고속 중심이다. 정책은 최대한 빼고 빠르게 나르는 일만 한다.

층을 나누는 이유는 변경과 장애를 층 안에 가두기 위해서다. 새 건물을 하나 붙이면 디스트리뷰션 한 쌍과 액세스 몇 대를 추가하고 코어에 잇기만 하면 된다. 액세스 쪽 VLAN을 바꿔도 코어는 모른다. 디스트리뷰션이 대역을 요약해 올리니 코어의 라우팅 테이블도 작게 유지된다.

작은 회사나 건물 하나짜리 캠퍼스에서는 디스트리뷰션과 코어를 한 쌍의 장비로 합친다. 이걸 축약 코어(collapsed core), 또는 2계층 구조라고 한다. 장비 수와 비용이 줄고, 건물이 여러 개로 늘어나기 전까지는 이걸로 충분하다. 디스트리뷰션 쌍이 셋 이상으로 늘어 서로 풀 메시로 잇기 버거워질 때가 코어를 따로 둘 신호다.

## L2와 L3의 경계를 어디에 둘까

3계층 설계에서 가장 오래 논쟁한 질문은 L3 경계의 위치다. 전통적인 방식은 액세스와 디스트리뷰션 사이를 L2로 두고 디스트리뷰션에서 라우팅한다. 같은 VLAN을 여러 액세스 스위치에 걸쳐 쓸 수 있어 편하다. 사람이 자리를 옮겨도, 서버를 옆 랙으로 옮겨도 같은 대역에 남는다. 대가는 액세스와 디스트리뷰션 사이 고리다. 액세스 스위치를 디스트리뷰션 두 대에 이중으로 이으면 STP가 한쪽 업링크를 막고, 게이트웨이는 디스트리뷰션 두 대가 VRRP나 HSRP로 나눠 갖는다. 장애가 나면 STP 수렴과 FHRP 전환을 둘 다 기다려야 한다.

다른 방식은 라우팅을 액세스까지 내리는 것(routed access)이다. 액세스 스위치가 자기 VLAN의 게이트웨이가 되고, 위로는 L3 링크 두 개를 OSPF나 BGP로 잇는다. 업링크 둘을 ECMP로 모두 쓰고, STP는 액세스 스위치 안으로 갇히고, 장애 감지와 전환은 라우팅 프로토콜과 BFD가 맡아 1초 아래로 줄일 수 있다. 대신 VLAN이 액세스 스위치 하나를 넘을 수 없다. 같은 대역을 여러 스위치에 걸쳐야 하는 요구가 있으면 쓸 수 없거나, 그 위에 오버레이를 얹어야 한다.

이 두 번째 방식을 데이터 센터 전체에 밀어붙인 것이 아래의 스파인-리프다. 리프가 곧 라우팅하는 액세스 스위치이고, 스파인은 디스트리뷰션과 코어의 역할을 합친 층이다.

## 남북에서 동서로

3계층 구조는 트래픽이 주로 위아래로 흐른다는 가정 위에 있다. 사용자의 PC에서 인터넷이나 본사 서버로 나가는 트래픽, 즉 망 바깥과 안을 오가는 흐름을 남북(north-south) 트래픽이라고 부른다. 기업 사무실 망은 지금도 대부분 이렇다.

데이터 센터는 달라졌다. 요청 하나가 들어오면 웹 서버가 인증 서비스를, 인증 서비스가 캐시와 DB를, DB가 복제본을 부른다. 같은 데이터 센터 안의 서버끼리 오가는 동서(east-west) 트래픽이 바깥으로 나가는 트래픽보다 훨씬 커졌다. 이 흐름이 3계층 구조에서 어디로 가는지 아래 그림에서 다음을 누르며 본다.

세 가지가 겹친다. 서버 위치에 따라 경로 길이가 다르다. 같은 pod면 짧고 다른 pod면 코어까지 갔다 온다. 지연이 예측하기 어렵고, 분산 시스템은 가장 느린 경로에 맞춰 느려진다.

다음으로 L2를 넓게 쓰는 구조라 STP가 이중 업링크의 절반을 막는다. 돈 주고 깐 선의 절반이 평소에 논다.

마지막으로 트래픽이 코어 쪽 몇 개 링크로 모인다. 서버를 늘릴수록 코어 장비를 더 큰 것으로 바꿔야 하는데, 장비 하나를 키우는 데는 한계가 있다.

## 스파인-리프: 어디서 어디로 가든 홉 수가 같다

스파인-리프(spine-leaf)는 이 문제를 모양으로 푼다. 스위치를 두 종류로만 나눈다. 리프(leaf)는 서버가 꽂히는 스위치다. 랙마다 하나나 두 대를 두어 ToR(Top of Rack)이라고도 부른다. 스파인(spine)은 리프끼리를 잇는 스위치다. 규칙은 두 개뿐이다. 모든 리프는 모든 스파인에 하나씩 선을 잇는다. 리프끼리, 스파인끼리는 잇지 않는다.

그러면 어느 리프에서 어느 리프로 가든 리프, 스파인, 리프로 똑같이 두 번 건넌다. 서버를 어느 랙에 두든 지연이 같다. 그리고 리프에서 다른 리프로 가는 길이 스파인 수만큼 있다. 스파인이 넷이면 길이 넷이고, 넷 모두 비용이 같다. 리프와 스파인 사이를 L3로 라우팅하면 라우팅 프로토콜이 이 네 길을 모두 ECMP로 쓴다. 아래 그림에서 다음을 누르면 흐름마다 다른 스파인을 타고, 스파인 하나가 빠지면 나머지로 옮겨 가는 모습이 보인다.

## ECMP는 흐름을 해시로 나눈다

ECMP가 정말 길을 나눠 쓰는지 리눅스에서 확인해 본다. 리프 역할 네임스페이스에 스파인 두 대로 가는 다음 홉을 가진 경로를 넣었다.

```bash
# 같은 대역에 다음 홉 둘 (ECMP 경로)
sudo ip -n leaf route add 10.20.0.0/24 nexthop via 10.1.1.1 dev sp1 nexthop via 10.1.2.1 dev sp2
ip -n leaf route show 10.20.0.0/24
```

```text
10.20.0.0/24
	nexthop via 10.1.1.1 dev sp1 weight 1
	nexthop via 10.1.2.1 dev sp2 weight 1
```

리눅스는 `net.ipv4.fib_multipath_hash_policy`로 무엇을 해시할지 정한다. 0(기본)은 출발지·목적지 IP만, 1은 포트 번호까지 본다. `ip route get`에 포트를 주면 커널이 어느 다음 홉을 고를지 알려 준다.

```bash
# 해시 정책별로 출발지 포트만 바꿔 가며 어느 스파인으로 가는지 본다
for pol in 0 1; do
  sudo ip netns exec leaf sysctl -w net.ipv4.fib_multipath_hash_policy=$pol
  for sp in 50001 50002 50003 50004 50005 50006; do
    echo -n "sport $sp -> "
    ip -n leaf route get 10.20.0.7 from 10.10.0.1 ipproto tcp sport $sp dport 443 | head -1
  done
done
```

```text
net.ipv4.fib_multipath_hash_policy = 0
sport 50001 -> 10.20.0.7 from 10.10.0.1 via 10.1.1.1 dev sp1 uid 0
sport 50002 -> 10.20.0.7 from 10.10.0.1 via 10.1.1.1 dev sp1 uid 0
sport 50003 -> 10.20.0.7 from 10.10.0.1 via 10.1.1.1 dev sp1 uid 0
sport 50004 -> 10.20.0.7 from 10.10.0.1 via 10.1.1.1 dev sp1 uid 0
sport 50005 -> 10.20.0.7 from 10.10.0.1 via 10.1.1.1 dev sp1 uid 0
sport 50006 -> 10.20.0.7 from 10.10.0.1 via 10.1.1.1 dev sp1 uid 0
net.ipv4.fib_multipath_hash_policy = 1
sport 50001 -> 10.20.0.7 from 10.10.0.1 via 10.1.2.1 dev sp2 uid 0
sport 50002 -> 10.20.0.7 from 10.10.0.1 via 10.1.1.1 dev sp1 uid 0
sport 50003 -> 10.20.0.7 from 10.10.0.1 via 10.1.1.1 dev sp1 uid 0
sport 50004 -> 10.20.0.7 from 10.10.0.1 via 10.1.2.1 dev sp2 uid 0
sport 50005 -> 10.20.0.7 from 10.10.0.1 via 10.1.2.1 dev sp2 uid 0
sport 50006 -> 10.20.0.7 from 10.10.0.1 via 10.1.1.1 dev sp1 uid 0
```

정책 0에서는 같은 두 호스트 사이 연결이 포트와 상관없이 모두 sp1로 간다. 정책 1에서는 포트에 따라 갈린다. 몇 개만 봐서는 고른지 모르니 많이 돌려서 세어 본다.

```bash
# 정책 1: 출발지 포트 1,000개를 바꿔 가며 다음 홉을 센다
sudo ip netns exec leaf sysctl -qw net.ipv4.fib_multipath_hash_policy=1
for sp in $(seq 40000 40999); do
  ip -n leaf route get 10.20.0.7 from 10.10.0.1 ipproto tcp sport $sp dport 443 | head -1 | grep -o "dev sp[12]"
done | sort | uniq -c

# 정책 0: 포트는 의미가 없으니 목적지 IP 200개를 바꿔 가며 센다
sudo ip netns exec leaf sysctl -qw net.ipv4.fib_multipath_hash_policy=0
for d in $(seq 1 200); do
  ip -n leaf route get 10.20.0.$d from 10.10.0.1 | head -1 | grep -o "dev sp[12]"
done | sort | uniq -c
```

```text
    506 dev sp1
    494 dev sp2
    101 dev sp1
     99 dev sp2
```

정책 1에서 포트 1,000개는 506 대 494로, 정책 0에서 목적지 200개는 101 대 99로 나뉘었다. 어느 쪽이든 많이 섞이면 고르게 나뉜다. 문제는 섞일 것이 적을 때다. 서버 두 대 사이의 대용량 복제처럼 IP 쌍이 하나뿐이면 정책 0은 한 길만 쓴다.

해시가 흐름 단위라 연결 하나는 한 길만 쓴다는 점은 [링크 묶기와 같다](/posts/gateway-link-redundancy-fhrp-lacp). 거대한 흐름 몇 개가 같은 스파인으로 해시되면 그 길만 넘친다. VXLAN 같은 오버레이 위에서는 바깥 헤더만 보고 해시하니, 캡슐화할 때 출발지 UDP 포트에 안쪽 흐름의 해시를 넣어 엔트로피를 살린다([SDN과 VXLAN 글](/posts/sdn-vxlan-overlay)). 장비가 여러 층일 때 층마다 같은 해시 함수를 쓰면 위층에서 이미 갈라진 흐름이 아래층에서 다시 한쪽으로 몰리는 해시 편향(polarization)도 생긴다. 장비마다 해시에 다른 씨앗 값을 넣어 피한다.

## 업링크가 얼마나 모자란가: 오버서브스크립션

리프 스위치 한 대를 보자. 서버 쪽으로 25G 포트 48개가 있으면 서버가 동시에 밀어 넣을 수 있는 최대량은 1,200G다. 위로 스파인 여섯 대에 100G씩 이으면 업링크는 600G다. 서버가 모두 동시에 최대로 다른 랙과 통신하면 절반만 지나간다. 이 비율, 아래쪽 대역폭 ÷ 위쪽 대역폭을 오버서브스크립션(oversubscription)이라고 하고 2:1로 적는다.

1:1이면 막힘 없는(non-blocking) 패브릭이다. 모든 서버가 동시에 다 써도 업링크가 버틴다. 비싸다. 실제로는 서버가 모두 동시에 최대로 쓰는 일이 드물어서, 일반 웹 서비스용 데이터 센터는 2:1에서 4:1 정도를 받아들이는 경우가 많다. 분산 스토리지, 머신러닝 학습 클러스터처럼 서버들이 동시에 서로에게 쏟아붓는 곳은 1:1에 가깝게 맞춘다. 어느 쪽이 맞는지는 자기 트래픽 패턴으로 정한다.

스파인이 하나 죽으면 비율이 바뀐다는 점도 설계에 넣어야 한다. 스파인 네 대 중 하나가 빠지면 업링크가 4분의 3이 되어 비율이 나빠진다. 스파인이 많을수록 한 대가 빠질 때 잃는 몫이 작다. 스파인 두 대면 하나가 죽을 때 절반을 잃는다. 직접 계산해 보자. 리프마다 스파인 한 대당 업링크 하나를 잇는다고 가정한다.

## 스파인-리프에서 STP가 사라지는 이유

3계층 구조의 이중 업링크는 L2였다. 같은 VLAN이 액세스와 디스트리뷰션 사이에 걸쳐 있으니 선을 겹치게 이으면 고리가 되고, STP가 한쪽을 막았다. 스파인-리프는 리프와 스파인 사이를 L3로 라우팅한다. 각 링크는 그 자체로 작은 IP 망(/31 하나)이고, L2 브로드캐스트는 리프를 넘지 않는다. 라우팅에는 고리를 끊으려고 링크를 막는 개념이 없다. 고리가 있어도 TTL과 최단 경로 계산이 처리하고, 비용이 같은 길은 모두 쓴다([라우터와 스위치 글](/posts/router-vs-switch)에서 본 L2 고리와 L3 고리의 차이 그대로다).

그래서 패브릭 안에는 STP가 막을 고리가 없다. 리프 아래 서버 포트에는 여전히 L2가 있으니, 그 아래에서 누가 스위치를 잘못 꽂는 경우를 막는 STP나 BPDU Guard는 리프에 남겨 둔다. 패브릭 전체에서 STP의 역할이 사라졌다는 뜻이다.

L2가 필요한 경우도 있다. 가상 머신을 다른 랙으로 옮겨도 IP를 유지해야 하거나, 오래된 애플리케이션이 같은 L2를 요구하면 랙을 넘는 같은 VLAN이 필요하다. 이때는 L3 패브릭 위에 VXLAN 오버레이를 얹고, 어느 MAC이 어느 리프 뒤에 있는지는 BGP EVPN으로 알린다. 물리망(언더레이)은 L3로 단순하게, 논리망(오버레이)은 필요한 곳에만 L2를 만든다. 게이트웨이도 리프마다 같은 가상 IP와 MAC으로 두는 분산 애니캐스트 게이트웨이를 쓰면, 서버의 첫 홉이 언제나 바로 위 리프라 VRRP 같은 전환이 필요 없다.

## 바깥으로 나가는 문: 경계 리프

스파인-리프에서 인터넷이나 다른 데이터 센터로 나가는 선은 스파인에 바로 꽂지 않는다. 스파인은 모든 리프를 똑같이 잇는 일만 하게 두고, 바깥 연결은 경계 리프(border leaf)라는 리프 한 쌍에 모은다. 경계 리프 위로 인터넷 회선, 전용선, 클라우드 연결이 붙고, 방화벽과 로드 밸런서 같은 공용 장비도 서비스 리프라는 별도 리프 쌍에 꽂는 경우가 많다.

이렇게 하면 바깥 연결도 패브릭 안에서는 그냥 리프 하나다. 서버에서 인터넷으로 가는 남북 트래픽도 리프, 스파인, 경계 리프로 같은 두 홉을 지나고, 스파인을 늘리거나 바꿀 때 바깥 회선을 건드리지 않는다. 경계 리프가 바깥 경로를 받아 패브릭 안에는 기본 경로나 요약 경로만 알리는 것이 보통이다. 바깥의 인터넷 경로 전체를 패브릭 안 리프마다 뿌리면 리프의 하드웨어 경로 테이블이 먼저 찬다.

## 패브릭 안의 라우팅

리프와 스파인 사이 라우팅에는 OSPF나 IS-IS 같은 IGP를 써도 되고, 큰 데이터 센터에서는 eBGP만 쓰는 방식이 널리 퍼졌다. RFC 7938이 정리한 방식은 리프마다 AS 번호를 따로 주고(스파인들은 같은 번호를 하나 공유하는 경우가 많다) 모든 링크에서 eBGP 세션을 맺는 것이다. BGP의 AS_PATH가 그대로 루프 방지 장치가 되고, 프로토콜 하나로 패브릭 내부와 바깥 연결을 다 처리할 수 있으며, 장애의 영향이 이웃 단위로 나뉘어 퍼진다. 비용이 같은 길을 모두 쓰려면 BGP multipath를 켠다.

IGP를 쓰든 BGP를 쓰든 링크 장애를 빨리 알아채는 일은 BFD에 맡긴다. 기본 타이머를 그대로 두면 [라우팅 프로토콜 글](/posts/routing-protocols-ospf-rip-eigrp)의 실습처럼 조용한 장애에 수십 초가 걸린다.

## 장애 도메인과 설계 원칙

어떤 모양을 고르든 설계 원칙은 비슷하다. 장애 도메인(하나가 고장 날 때 함께 영향을 받는 범위)을 작게 만들고, 단일 장애 지점을 두지 않고, 같은 모양을 반복한다.

장애 도메인을 작게 만든다는 건 L2 브로드캐스트 범위를 작게, 라우팅 영역을 적당히 나누고 요약하고, 한 장비나 한 랙이 망가져도 그 안에서 끝나게 하는 것이다. 3계층에서 VLAN 하나를 건물 전체에 펼쳐 두면 브로드캐스트 스톰 하나가 건물 전체를 멈춘다. 스파인-리프는 L2를 리프 아래로 가둬서 이 범위를 랙 하나로 줄였다.

이중화는 장비만이 아니라 전원, 선이 지나는 경로, 광 모듈 같은 공통 원인까지 본다. 리프 두 대를 MLAG로 묶어 서버를 이중으로 꽂아도 두 리프가 같은 전원 분배기에 꽂혀 있으면 하나의 장애다. [고가용성 글](/posts/high-availability)의 공통 원인 계산이 망에도 그대로 적용된다.

모듈화는 같은 블록을 반복하는 것이다. pod 하나, 랙 하나의 설계를 표준으로 정해 두면 늘릴 때 같은 모양을 찍어 내기만 하면 되고, 설정 자동화와 장애 분석도 쉬워진다. 반대로 장비마다 사연이 있는 망은 아무도 전체 모양을 모른다.

## 주소 계획은 요약을 위해 한다

주소는 처음에 아끼지 말고, 요약할 수 있게 블록으로 나눈다. 스파인 4대, 리프 32대 패브릭이라면 이런 식이다.

```text
10.255.0.0/24     루프백. 장비마다 /32 하나 (라우터 ID, BGP 세션 주소)
10.254.0.0/24     리프-스파인 링크. 링크마다 /31 (32 리프 × 4 스파인 = 128 링크 × 2 = 256 주소)
10.1.0.0/16       서버 대역. 리프 n에 10.1.n.0/24
10.2.0.0/16       다음 pod용으로 비워 둔다
```

링크 주소에 /31을 쓰는 것은 두 장비만 있는 링크에 망 주소와 브로드캐스트 주소가 필요 없기 때문이다(RFC 3021). /30이면 주소의 절반이 버려진다. 서버 대역을 리프 번호와 맞추면 주소만 보고 어느 랙인지 알 수 있고, pod 전체를 /16 한 줄로 요약해 바깥에 알릴 수 있다.

흔한 실수는 겹치는 대역이다. 사내 데이터 센터에서 쓴 10.0.0.0/16이 나중에 연결할 클라우드 VPC, 쿠버네티스의 Pod·Service CIDR, 인수한 회사의 망과 겹치면 서로 이을 수 없다. 겹치는 VPC 사이를 잇는 방법이 따로 필요해진다([VPC 연결 글](/posts/vpc-peering-transit-privatelink)). 처음에 회사 전체의 큰 주소 지도를 만들고 거기서 잘라 쓰는 것이 가장 싸다.

## 랙 하나에 리프를 몇 대 둘까

스파인-리프에서 서버에게 가장 가까운 단일 장애 지점은 리프다. 랙에 리프가 한 대뿐이면 그 리프를 재부팅할 때 랙 전체가 끊긴다. 선택지는 셋이다.

리프 한 대만 두고 랙 단위 장애를 받아들일 수도 있다. 서비스가 여러 랙에 복제본을 나눠 두고 랙 하나쯤 빠져도 버티게 만들어져 있다면(대형 웹 서비스가 흔히 이렇다) 가장 싸고 단순하다. 장애 도메인이 랙 하나로 명확해진다. 대신 리프 업그레이드는 랙을 비우고 해야 한다.

리프 두 대를 MLAG로 묶고 서버를 양쪽에 하나씩 꽂으면, 서버는 LACP 묶음 하나로 두 리프를 동시에 쓴다. 리프 하나가 빠져도 서버는 대역폭만 절반이 되고 끊기지 않는다. 다만 두 리프가 피어 링크로 상태를 맞추는 만큼 둘은 사실상 한 쌍으로 움직이고, 피어 링크 장애와 스플릿 브레인을 따로 대비해야 한다([게이트웨이와 링크 이중화 글](/posts/gateway-link-redundancy-fhrp-lacp)). EVPN 멀티호밍은 피어 링크 없이 같은 일을 표준 방식으로 한다.

서버 쪽에서 active-backup bonding으로 두 리프에 꽂는 방법도 있다. 리프 쪽 설정이 필요 없고, 한 선만 쓰지만 리프 장애는 견딘다. 어느 쪽이든 두 리프가 같은 전원과 같은 업그레이드 묶음에 있으면 이중화의 의미가 줄어드니, 리프 두 대는 서로 다른 전원에, 업그레이드는 한 대씩 한다.

## 규모에 따라 고르는 순서

정답은 규모와 트래픽 모양이 정한다. 사무실 한 층, 스위치 몇 대면 스타 모양에 게이트웨이 한 쌍이면 충분하다. 건물 하나에 층이 여럿이면 층마다 액세스, 건물에 디스트리뷰션 겸 코어 한 쌍을 두는 축약 코어로 간다. 건물이 셋 이상이 되어 디스트리뷰션 쌍끼리 잇는 선이 늘기 시작하면 코어를 따로 둔다. 사무실 망은 지금도 대부분 남북 트래픽이라 이 계층 구조가 맞다.

데이터 센터는 랙 몇 개짜리라도 처음부터 스파인-리프 모양으로 시작하는 편이 낫다. 스파인 두 대, 리프 몇 대로 시작해도 모양이 같으니, 커질 때 스파인과 리프를 옆으로 붙이기만 하면 된다. 나중에 3계층에서 스파인-리프로 바꾸는 건 케이블을 전부 다시 까는 일이다. 스파인을 늘릴 신호는 업링크 사용률이 꾸준히 높아지는 것과 스파인 한 대가 빠졌을 때의 비율이 견딜 수 없는 수준이 되는 것이다. 리프 수가 스파인 포트 수에 가까워지면 pod를 나누고 슈퍼 스파인을 얹을 준비를 한다.

## 클라우드 VPC로 옮기면

클라우드에서는 스파인과 리프를 직접 고르지 않는다. 물리 패브릭은 클라우드 사업자가 운영하고, 사용자에게는 VPC라는 논리망만 보인다([VPC 기본 글](/posts/vpc-basics)). 그래도 설계 원칙은 그대로 옮겨 간다.

장애 도메인은 가용 영역(AZ)이 된다. 서브넷은 AZ 하나에 속하니, 같은 역할의 서브넷을 AZ마다 하나씩 만들고 서버를 나눠 둔다. 3계층의 층 구분은 퍼블릭·프라이빗·데이터 서브넷 같은 역할 구분과 라우트 테이블로 바뀐다([서브넷과 라우트 테이블 글](/posts/vpc-subnets-route-tables)). VPC가 여러 개로 늘면 모두를 서로 잇는 풀 메시 피어링은 앞에서 본 n(n−1)/2 문제를 다시 만든다. 그래서 Transit Gateway 같은 허브에 스포크로 붙이는 스타 모양으로 돌아간다. 주소 계획은 클라우드에서 더 중요하다. VPC의 CIDR은 만든 뒤 바꾸기 어렵고, 겹치면 피어링 자체가 안 된다.

클라우드에서 더 조심할 것은 AZ 사이 트래픽이다. 같은 리전 안이라도 AZ를 넘는 트래픽은 지연이 조금 더 붙고 사업자에 따라 요금이 붙는다. 동서 트래픽이 많은 서비스라면 서로 자주 부르는 서비스를 같은 AZ에 두되, AZ 하나가 통째로 빠져도 버틸 만큼은 다른 AZ에 남기는 균형을 잡는다.

## 바꾸기 어려운 것부터 정한다

설계 문서에 들어갈 결정은 많지만, 나중에 바꾸기 어려운 순서로 먼저 정한다. 가장 어려운 것은 케이블과 모양이다. 스파인과 리프 사이 선은 한 번 깔면 몇 년을 간다. 리프의 업링크 포트 수가 스파인 최대 대수를 정하고, 스파인 포트 수가 리프 최대 대수를 정하니 장비를 고를 때 이미 패브릭의 최대 크기가 정해진다.

그 다음이 주소 계획과 L2/L3 경계다. 서버 대역을 리프에 묶을지, VLAN을 랙 너머로 펼칠지는 애플리케이션이 IP를 어떻게 쓰는지에 달려 있고, 바꾸려면 서버 주소를 다시 줘야 한다. 라우팅 프로토콜, 오버서브스크립션 비율, 해시 정책, 타이머는 상대적으로 바꾸기 쉽다. 스파인을 추가해 비율을 낮추거나 BFD를 켜는 건 운영 중에도 할 수 있다.

## 현장에서 설계를 의심하는 순간

설계 문제는 장애보다 "느려졌다"로 먼저 나타난다. 특정 서비스의 p99 지연이 오르는데 서버 CPU와 앱 로그는 멀쩡하면 망의 어느 링크가 차는지 본다. 리프 업링크와 스파인 포트의 사용률을 포트별로, 그리고 드롭 카운터를 같이 본다. 서버에서는 인터페이스별로 확인할 수 있다.

```bash
# 인터페이스별 누적 바이트, 에러, 드롭
ip -s link show eth0
# 1초 간격으로 인터페이스별 처리량 (sysstat 패키지)
sar -n DEV 1 5
```

업링크 여러 개 중 하나만 차 있으면 해시 분배 문제다. 큰 흐름 몇 개가 한 길로 몰렸거나, 해시 정책이 포트를 보지 않거나, 여러 층이 같은 해시로 편향된 것이다. 모든 업링크가 고르게 차 있으면 진짜로 대역폭이 모자란 것이고, 위에서 계산한 오버서브스크립션을 다시 본다. 평균은 낮은데 드롭이 쌓이면 마이크로버스트다. 1분 평균 그래프로는 안 보이니 초 단위 카운터나 스위치의 버퍼 통계를 본다.

서버 NIC에서 버려지는 패킷은 `ip -s link`의 dropped보다 드라이버 카운터가 더 자세히 알려 준다.

```bash
# NIC 드라이버가 세는 상세 카운터 중 드롭·누락 관련만 본다
sudo ethtool -S eth0 | grep -i -E "drop|discard|miss"
```

카운터 이름은 드라이버마다 다르다. 수신 링 버퍼가 넘쳐 버린 것(이름에 `missed`나 `no_buffer`가 들어가는 경우가 많다)이 오르면 망이 아니라 서버가 받아 내지 못한 것이고, 스위치 포트의 출력 드롭이 오르면 망 쪽 버퍼가 넘친 것이다. 어느 쪽 숫자가 오르는지가 범인을 가른다.

지연이 서버 위치에 따라 다르면 경로 길이가 다른 구조인지 본다. 3계층 망에서 같은 pod 안과 pod 사이의 지연 차이, 클라우드에서 같은 AZ와 다른 AZ의 차이다. traceroute로 홉 수를 비교하면 바로 보인다. 스파인 하나를 점검으로 내렸을 때 서비스가 느려진다면 장애 시 비율을 계산하지 않고 스파인 수를 정한 것이다.

## 위로 쌓느냐, 옆으로 늘리느냐

3계층 구조는 역할별로 층을 쌓아 변경을 층 안에 가두고, 주로 바깥을 오가는 남북 트래픽에 잘 맞는다. 서버끼리의 동서 트래픽이 커지자 코어로 모이는 병목과 STP가 막는 업링크가 문제가 됐고, 스파인-리프는 모든 리프를 모든 스파인에 이어 어디서든 홉 수를 같게 하고 L3 ECMP로 모든 링크를 쓴다. 대역폭이 모자라면 스파인을, 포트가 모자라면 리프를 옆으로 늘린다. 어느 구조든 오버서브스크립션을 평소와 장애 시로 계산하고, 장애 도메인을 작게, 주소는 요약할 수 있게 잡는 것이 설계의 뼈대다.

## 면접에서 나올 만한 질문

### 3계층 네트워크 구조의 각 계층은 무엇을 하나요?

액세스는 서버와 PC가 꽂히는 포트를 제공하고 VLAN, 포트 보안 같은 단말 단위 일을 한다. 디스트리뷰션은 액세스 스위치를 모으고 보통 L2와 L3의 경계로서 VLAN 간 라우팅, 게이트웨이, ACL 같은 정책, 대역 요약을 맡는다. 코어는 디스트리뷰션끼리를 빠르게 잇는 일만 한다. 층을 나누면 변경과 장애가 층 안에 머물고, 작은 곳은 디스트리뷰션과 코어를 합친 축약 코어로 시작한다.

### 축약 코어(2계층)와 3계층은 언제 각각 쓰나요?

건물 하나, 디스트리뷰션 한 쌍으로 충분한 규모면 디스트리뷰션과 코어를 한 쌍의 장비로 합친 축약 코어가 비용과 운영 면에서 낫다. 건물이나 구역이 늘어 디스트리뷰션 쌍이 셋 이상이 되면, 그것들을 서로 풀 메시로 잇는 선이 n(n−1)/2로 늘어 버겁다. 그때 코어를 따로 두고 디스트리뷰션을 모두 코어에만 잇는 3계층으로 간다. 데이터 센터라면 처음부터 스파인-리프 모양으로 시작하는 편이 낫다.

### 데이터 센터가 스파인-리프로 넘어간 이유는 무엇인가요?

서버끼리의 동서 트래픽이 바깥으로 나가는 남북 트래픽보다 커졌기 때문이다. 3계층에서는 다른 pod 사이 흐름이 코어로 모여 업링크가 먼저 차고, 서버 위치에 따라 경로 길이가 달라지며, L2 이중 업링크의 절반을 STP가 막는다. 스파인-리프는 모든 리프를 모든 스파인에 이어 어디서든 리프-스파인-리프 두 홉으로 같고, L3 ECMP로 모든 링크를 동시에 쓴다.

### 스파인-리프에서 STP가 필요 없어지는 이유는 무엇인가요?

리프와 스파인 사이를 L3로 라우팅하기 때문이다. 각 링크가 /31짜리 독립된 IP 망이라 L2 고리가 생기지 않고, 라우팅은 TTL과 최단 경로 계산으로 고리를 다루며 비용이 같은 길은 ECMP로 모두 쓴다. 그래서 고리를 막으려고 링크를 끄는 STP의 역할이 패브릭 안에서는 사라진다. 서버가 꽂히는 리프 아래 포트에는 잘못 꽂힌 스위치를 막기 위한 BPDU Guard 정도를 남긴다.

### 오버서브스크립션 비율은 어떻게 계산하고 얼마가 적당한가요?

리프의 서버 쪽 대역폭 합을 업링크 대역폭 합으로 나눈다. 25G 포트 48개(1,200G)에 100G 업링크 여섯 개(600G)면 2:1이다. 일반 웹 서비스는 서버들이 동시에 최대로 쓰는 일이 드물어 2:1에서 4:1 정도를 받아들이는 경우가 많고, 분산 스토리지나 ML 학습처럼 동시에 쏟아붓는 곳은 1:1에 가깝게 맞춘다. 스파인 한 대가 빠졌을 때의 비율도 함께 계산해야 한다.

### ECMP로 길이 넷인데 특정 링크만 차는 이유는 무엇인가요?

ECMP는 흐름 단위로 해시해 길을 고르기 때문에, 큰 흐름 몇 개가 같은 길로 해시되면 그 링크만 넘친다. 해시가 IP만 보면(리눅스 기본 정책 0) 같은 두 호스트 사이 연결은 모두 한 길로 간다. 여러 층의 장비가 같은 해시 함수를 쓰면 이미 갈라진 흐름이 다시 한쪽으로 몰리는 편향도 생긴다. 포트까지 해시하게 바꾸고, 장비마다 해시 씨앗을 다르게 주고, 큰 흐름은 여러 연결로 나눈다.

### 스파인-리프 패브릭 안에서 BGP를 쓰는 이유는 무엇인가요?

RFC 7938 방식처럼 리프마다 AS 번호를 주고 모든 링크에 eBGP를 맺으면, 프로토콜 하나로 패브릭 내부와 바깥 연결을 다 처리하고 AS_PATH가 루프를 막아 준다. BGP는 큰 경로 수를 견디고 정책을 세밀하게 걸 수 있으며, 장애 영향이 이웃 단위로 나뉜다. multipath를 켜서 같은 비용의 길을 모두 쓰고, 감지는 BFD에 맡긴다. 작은 패브릭이면 OSPF나 IS-IS로도 충분하다.

### 망 주소 계획에서 무엇을 신경 쓰나요?

요약할 수 있게 블록으로 나누는 것이다. 루프백, 링크(/31), 서버 대역을 큰 블록으로 따로 잡고, 서버 대역을 리프나 pod 번호와 맞추면 바깥에는 pod 단위로 한 줄만 알릴 수 있다. 가장 비싼 실수는 겹침이라, 나중에 이을 클라우드 VPC나 쿠버네티스 Pod·Service CIDR, 다른 사업장과 겹치지 않도록 회사 전체 주소 지도를 먼저 만든다.
