주문 버튼을 누르면 응답이 0.5초쯤 걸린다는 문의가 들어왔다. 요청은 게이트웨이, 주문 서비스, 재고 서비스를 거쳐 DB까지 간다. 세 팀에 물어보니 다 "우리 쪽 API 평균 응답은 빠르다"고 한다. 각자 자기 서버의 지표를 보고 있으니 틀린 말은 아니다. 그런데 사용자는 느리다. 문제는 그 0.5초가 세 서비스 중 어디에서, 몇 번에 걸쳐 쓰였는지 아무도 한 장으로 보지 못한다는 데 있다.

분산 추적(distributed tracing)은 요청 하나가 여러 서비스를 지나는 동안 각 구간의 시작과 끝을 기록해, 한 장의 폭포 그림으로 이어 붙이는 기술이다. 이 글은 Node.js 서비스 셋에 OpenTelemetry를 붙여 Jaeger로 모은 실제 trace에서 느린 구간을 찾고, 그 trace를 이어 붙이는 `traceparent` 헤더, 이어 붙이기가 끊기는 흔한 경우, 다 저장할 수 없어서 고르는 샘플링, 로그와 trace를 잇는 법까지 따라간다. 지표·로그·추적이 각각 무엇을 맡는지는 [관측 가능성 기본 글](/posts/observability-basics)에, 로그를 JSON 한 줄로 남기는 법은 [구조화 로그 글](/posts/structured-logging)에 있다. 이 글은 그중 추적만 깊게 본다.

실습 환경은 Ubuntu 24.04, Node.js 22, PostgreSQL 16이다. OpenTelemetry JS SDK는 `@opentelemetry/sdk-node` 0.223.0(SDK 2.x 계열), 수집과 화면은 Jaeger 2.10.0, 꼬리 샘플링은 OpenTelemetry Collector contrib 0.132.0을 썼다. 2026년 10월에 SDK 3.0 계열(0.300.0)이 막 나왔으니, 따라 할 때는 버전을 맞추길 권한다.

## trace는 나무, span은 가지 하나

용어부터 정리한다. span은 "어떤 일을 언제 시작해서 언제 끝냈다"는 기록 하나다. HTTP 요청을 받은 일, 다른 서비스를 부른 일, SQL 한 번을 보낸 일이 각각 span이다. span에는 이름, 시작 시각, 걸린 시간, 상태(성공·오류), 속성(URL, SQL, 상태 코드 등)이 들어 있다.

trace는 요청 하나에서 생긴 span 전체다. span마다 자기 ID(span id)와 부모 span의 ID를 갖고 있어서, 이걸 따라가면 나무 모양이 된다. 그리고 같은 trace에 속한 모든 span은 같은 trace id를 갖는다.

여기서 어려운 부분은 서비스 경계다. 주문 서비스가 재고 서비스를 부를 때, 재고 서비스는 "내가 받은 이 요청이 어느 trace의 어느 span에서 왔는지" 알아야 자기 span의 부모를 정할 수 있다. 그래서 부르는 쪽이 요청 헤더에 trace id와 자기 span id를 실어 보낸다. 이걸 문맥 전파(context propagation)라고 부른다. 아래 그림에서 다음을 누르면 요청 하나가 서비스를 건너면서 헤더가 어떻게 바뀌는지 보인다. 헤더 값은 실습에서 실제로 찍힌 것이다.

마지막 단계가 중요하다. trace 전체를 어느 한 서비스가 들고 있는 게 아니다. 각자 자기 조각을 보내고, 저장소가 trace id로 맞춘다. 그래서 한 서비스라도 헤더를 넘기지 않으면 나무가 둘로 쪼개진다. 뒤에서 이 장면을 직접 만든다.

계측 코드는 서비스 코드보다 먼저 불러오는 파일 하나다. HTTP와 pg 라이브러리를 감싸서 span을 만들고 헤더를 넣고 빼는 일을 대신 한다.

```js
// tracing.js: node -r ./tracing.js 처럼 다른 모듈보다 먼저 불러온다
const { NodeSDK } = require("@opentelemetry/sdk-node");
const { OTLPTraceExporter } = require("@opentelemetry/exporter-trace-otlp-http");
const { HttpInstrumentation } = require("@opentelemetry/instrumentation-http");
const { PgInstrumentation } = require("@opentelemetry/instrumentation-pg");
const { BatchSpanProcessor } = require("@opentelemetry/sdk-trace-base");

const sdk = new NodeSDK({
  serviceName: process.env.OTEL_SERVICE_NAME, // gateway, orders, inventory
  spanProcessors: [
    new BatchSpanProcessor(new OTLPTraceExporter({ url: "http://10.78.0.2:4318/v1/traces" })),
  ],
  instrumentations: [new HttpInstrumentation(), new PgInstrumentation()],
});
sdk.start();
process.on("SIGTERM", () => sdk.shutdown().finally(() => process.exit(0)));
```

먼저 불러와야 하는 이유는 계측이 `require("http")`와 `require("pg")`를 가로채서 감싸기 때문이다. 앱이 먼저 `pg`를 불러 버리면 감싸지 않은 원본을 쓰게 되고, span이 하나도 안 나온다. 종료할 때 `shutdown()`을 부르는 것도 같은 이유로 빠뜨리면 안 된다. 배치에 남아 있던 마지막 span들이 버려진다.

orders에는 "재고 확인" 단계를 직접 span으로 하나 열었다. 자동 계측은 라이브러리 경계(HTTP, SQL)만 보이니, 업무상 의미 있는 단계는 직접 감싼다.

```js
const { trace } = require("@opentelemetry/api");
const tracer = trace.getTracer("orders");

const stock = await tracer.startActiveSpan("check stock", async (span) => {
  span.setAttribute("order.items", items.length);
  const out = [];
  for (const sku of items) out.push(await getStock(sku)); // 하나씩 차례로 묻는다
  span.end();
  return out;
});
```

처음 한 번은 span이 Jaeger에 하나도 도착하지 않았다. 서비스 로그에는 아무 오류도 없었다. Jaeger 2.10은 OTLP 수신 포트를 기본으로 `localhost`에만 연다. 다른 네임스페이스(컨테이너라면 다른 컨테이너)에서 보낸 span은 연결이 거부됐고, SDK는 내보내기 실패를 기본으로 조용히 넘긴다.

```bash
# Jaeger가 어느 주소로 열었는지 본다
sudo ip netns exec n7-trace ss -ltn | grep -E '4317|4318'
```

```text
LISTEN 0      4096       127.0.0.1:4317       0.0.0.0:*          
LISTEN 0      4096       127.0.0.1:4318       0.0.0.0:*          
```

`JAEGER_LISTEN_HOST=0.0.0.0`을 주고 다시 띄우자 `0.0.0.0:4318`로 열렸고 span이 들어오기 시작했다. "계측을 붙였는데 화면에 아무것도 없다"면 앱 코드보다 먼저 수집기가 어느 주소에서 듣고 있는지, 앱이 어디로 보내는지를 본다. SDK의 진단 로그를 켜면(`OTEL_LOG_LEVEL=debug`) 내보내기 실패가 보인다.

읽는 순서가 있다. 먼저 맨 위 루트 span의 길이(465ms)가 사용자가 기다린 시간이다. 그다음 들여쓰기를 따라 내려가며 "자식들로 설명되지 않는 시간"을 찾는다.

- `check stock` 452ms 아래에 `GET (client)`이 세 개 있고, 시작 시각이 7ms, 191ms, 313ms다. 앞의 것이 끝나야 다음 것이 시작한다. 차례로 불렀다는 게 그림 모양으로 보인다.
- 각 GET 안에서는 `pg.query`가 거의 전부다. 151 + 113 + 138 = 402ms, 전체의 86%가 같은 SQL 세 번이다.
- 첫 GET에만 `pg.connect` 18ms가 있다. 풀에 연결이 없어서 처음 한 번 새로 맺은 비용이다. 이후로는 `pg-pool.connect`가 0.3ms다.

span의 kind도 볼 만하다. `client`는 부르는 쪽, `server`는 받는 쪽이다. orders의 `GET (client)` 시작과 inventory의 `GET (server)` 시작 사이의 틈(7ms → 14ms)이 네트워크와 상대 서버의 큐에서 기다린 시간이다. 이 틈이 크면 네트워크나 상대의 accept 큐, 이벤트 루프 지연을 의심한다. 이 실습은 한 호스트라 시계가 같지만, 서버가 다르면 시계 차이(clock skew)만큼 틈이 틀어진다. 자식이 부모보다 먼저 시작한 것처럼 보이면 대개 시계 문제다.

## 헤더가 한 번 끊기면 추적도 끊긴다

분산 추적에서 가장 흔한 고장은 문맥 전파가 끊기는 것이다. 한 구간이라도 헤더를 넘기지 않으면 그 뒤는 새 trace로 시작한다. 화면에는 짧은 trace 두 개가 따로 보이고, 둘을 잇는 방법이 없다.

직접 만들어 봤다. orders가 inventory를 부를 때 `http.get` 대신 Node 내장 `fetch`를 쓰게 바꿨다. Node의 `fetch`는 undici라는 별도 HTTP 구현 위에 있어서, `http` 모듈을 감싸는 `HttpInstrumentation`이 잡지 못한다.

```text
{"service":"orders","msg":"order created","trace_id":"52a572b7ee108077262bab35f19bc873",...}
{"service":"inventory","msg":"stock lookup","trace_id":"c20c3f64f1f58e5a12ba1442eaee6213","sku":"SKU-88"}
{"service":"gateway","msg":"checkout done","trace_id":"52a572b7ee108077262bab35f19bc873",...}
```

(`ts`, `span_id` 필드는 줄였다.) inventory의 trace id가 다르고, 받은 `traceparent`가 없어서 로그에 그 필드가 아예 없다. 오류는 하나도 나지 않았다. 고치려면 `@opentelemetry/instrumentation-undici`를 추가한다. 자동 계측 묶음(`auto-instrumentations-node`)을 쓰면 들어 있다.

계측되지 않은 HTTP 클라이언트나 RPC 라이브러리가 하나 섞인 경우. 위의 fetch가 그렇다. 새 라이브러리를 들일 때 계측이 있는지 먼저 본다.

비동기 경계. 메시지 큐, 배치 작업, 스레드 풀로 일을 넘기는 순간 메모리의 문맥이 따라가지 않는다. Kafka라면 레코드 헤더에, RabbitMQ라면 메시지 속성에 traceparent를 넣고 꺼낸다. 이벤트 흐름 전체를 이어 보는 관점은 [이벤트 기반 아키텍처 글](/posts/event-driven-architecture)에 있다.

서비스 메시. Envoy 같은 사이드카가 span을 만들어 주니 앱은 아무것도 안 해도 된다고 오해하기 쉽다. 사이드카는 들어온 요청과 나가는 요청이 같은 요청이라는 걸 모른다. 앱이 받은 헤더를 나가는 요청에 옮겨 주지 않으면 메시의 trace도 끊긴다. 메시 구조는 [서비스 메시 글](/posts/service-mesh)에서 봤다.

헤더를 지우는 프록시. 일부 API 게이트웨이나 WAF는 허용 목록에 없는 헤더를 버린다. 반대로 바깥에서 들어온 `traceparent`를 그대로 믿는 것도 문제다. 실습에서 임의의 값을 넣어 보내자 그대로 이어받았다.

```bash
# 바깥에서 trace id를 지정해 보낸다
curl -s -o /dev/null -H "traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01" \
  "http://127.0.0.1:17001/checkout?items=SKU-77"
```

```text
{"ts":"2026-10-20T19:40:22.820Z","service":"gateway","msg":"checkout done","trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","span_id":"95b91624460e5868","status":201}
```

누구나 sampled 플래그를 01로 보내 모든 요청을 저장하게 만들 수 있고, 남의 trace id에 span을 섞어 넣을 수 있다. 인터넷에 열린 첫 관문에서는 받은 trace를 이어받지 않고 새로 시작하거나(받은 값은 link로만 남긴다), 샘플링 결정을 다시 내리게 설정하는 경우가 많다.

## 다 저장할 수 없어서 고른다

span은 많다. 이 실습의 주문 하나가 span 16~17개였다. 초당 1,000건이면 초당 1만 6천 개, 하루 14억 개다. 저장소와 네트워크 비용 때문에 대부분은 버리고 일부만 남긴다. 무엇을 남길지 언제 정하느냐에 따라 두 방식으로 나뉜다.

헤드 샘플링은 trace가 시작될 때, 즉 첫 서비스에서 정한다. 정한 결과를 traceparent의 sampled 플래그에 실어 뒤로 보내고, 뒤의 서비스는 그 결정을 따른다. gateway만 `OTEL_TRACES_SAMPLER=parentbased_traceidratio`, `OTEL_TRACES_SAMPLER_ARG=0.25`로 띄우고 200번 주문을 보낸 뒤, inventory가 받은 헤더의 플래그를 셌다.

```bash
# inventory 로그에 찍힌 traceparent의 마지막 칸(flags)을 센다
grep -o '"traceparent":"[^"]*"' inventory.log | awk -F- '{print $NF}' | sort | uniq -c
```

200건 중 44건(22%)만 01이었다. 비율 샘플러는 trace id 값으로 결정을 내려서, 같은 trace id라면 어느 서비스에서 계산해도 같은 결론이 나온다. 싸고 단순하다. 대신 시작할 때는 이 요청이 느릴지, 실패할지 모른다. 0.25로 잡으면 장애 난 요청의 75%도 같이 버린다.

꼬리 샘플링은 trace가 끝난 뒤에 정한다. 서비스는 모든 span을 보내고, Collector가 trace id별로 span을 잠시 모아 두었다가 전체를 보고 남길지 정한다. 오류가 있는 trace, 느린 trace는 모두 남기고 나머지는 10%만 남기도록 설정했다.

```yaml
processors:
  tail_sampling:
    decision_wait: 5s          # 첫 span을 받은 뒤 5초 동안 trace를 모아 둔다
    num_traces: 50000          # 메모리에 들고 있을 trace 수 상한
    policies:
      - name: keep-errors
        type: status_code
        status_code: {status_codes: [ERROR]}
      - name: keep-slow
        type: latency
        latency: {threshold_ms: 200}
      - name: sample-rest
        type: probabilistic
        probabilistic: {sampling_percentage: 10}
```

주문 100건 중 5건은 재고 조회에 300ms를 더하고(느림), 5건은 inventory가 500을 돌려주게(오류) 만들었다. 서비스는 모두 always-on으로 두고 Collector를 거쳐 Jaeger에 보냈다. Jaeger에 남은 trace를 종류별로 셌다.

```text
23 {'slow': 5, 'bad': 5, 'normal': 13}
```

느린 것 5건, 오류 5건이 하나도 빠지지 않고 남았고, 정상 90건 중에서는 13건이 남았다. Collector 자신의 지표에도 정책별 결정이 보인다(라벨 일부 생략).

```text
otelcol_processor_tail_sampling_count_traces_sampled{decision="sampled",policy="keep-errors",sampled="true"} 5
otelcol_processor_tail_sampling_count_traces_sampled{decision="sampled",policy="keep-slow",sampled="true"} 5
otelcol_processor_tail_sampling_count_traces_sampled{decision="sampled",policy="sample-rest",sampled="true"} 15
otelcol_processor_tail_sampling_global_count_traces_sampled{decision="sampled",sampled="true"} 23
```

`sample-rest`가 15건을 골랐는데 최종이 23건인 건, 확률 정책이 느리거나 실패한 trace도 일부 골라서 겹쳤기 때문이다. 정책 중 하나라도 남기라고 하면 남는다.

꼬리 샘플링의 대가도 분명하다. 모든 span이 일단 Collector까지 와야 하니 서비스와 Collector 사이 네트워크 비용은 줄지 않는다. Collector는 결정을 내릴 때까지 trace를 메모리에 들고 있어야 한다. 그리고 한 trace의 span이 모두 같은 Collector 인스턴스에 모여야 판단할 수 있어서, Collector를 여러 대로 늘리면 앞에 trace id 기준으로 나눠 주는 계층(loadbalancing exporter)을 하나 더 둔다. `decision_wait`보다 오래 걸리는 trace는 결정이 난 뒤에 도착한 span이 따로 처리된다. 그래서 실무에서는 서비스에서 헤드 샘플링으로 양을 한 번 줄이고(예: 정상 트래픽의 일부), Collector의 꼬리 샘플링으로 오류와 느린 요청을 건지는 식으로 섞는다.

## 로그와 trace를 trace_id로 잇는다

추적의 실무 가치는 절반이 로그와의 연결에서 나온다. 이 실습의 서비스는 로그 한 줄마다 현재 span의 trace id를 넣었다.

```js
const { trace } = require("@opentelemetry/api");
// 한 줄 JSON 로그에 지금 span의 trace_id, span_id를 붙인다
function log(msg, extra = {}) {
  const ctx = trace.getActiveSpan()?.spanContext();
  console.log(JSON.stringify({ ts: new Date().toISOString(), service: process.env.OTEL_SERVICE_NAME,
    msg, trace_id: ctx?.traceId, span_id: ctx?.spanId, ...extra }));
}
```

이러면 Jaeger에서 느린 trace를 찾은 뒤 그 trace id로 로그 저장소를 검색해, 세 서비스의 로그를 시간순으로 한 번에 본다. 반대로 오류 로그에서 trace id를 복사해 trace를 연다. 지표의 이상한 점에서 trace로 넘어가는 연결(exemplar)도 같은 trace id로 만든다.

## 추적을 들일 때 정할 것

span에 무엇을 넣을지부터 정한다. `db.query.text`에는 실습처럼 파라미터 자리표시자(`$1`)가 들어간 SQL이 남는데, 문자열을 이어 붙여 만든 SQL이라면 고객 정보가 그대로 남는다. 헤더, 쿼리 문자열, 요청 본문을 속성으로 넣을 때도 같다. trace 저장소는 로그 저장소만큼 접근 통제가 엄격하지 않은 경우가 많다.

span 이름은 낮은 카디널리티로 짓는다. `GET /stock/SKU-31`처럼 ID가 들어간 이름을 쓰면 span 이름마다 통계가 갈라져 집계가 무의미해진다. 이름은 `GET /stock/:sku`처럼 경로 템플릿으로 두고, 실제 값은 속성(`url.path`)에 넣는다. 이 실습의 HTTP span 이름이 그냥 `GET`인 것도 프레임워크 없이 http 모듈만 써서 경로 템플릿을 몰랐기 때문이다. Express 같은 프레임워크 계측을 붙이면 라우트 이름이 붙는다.

오버헤드는 생각보다 작지만 0은 아니다. span을 만들고 속성을 붙이는 데 CPU가 들고, 배치 큐가 메모리를 쓴다. 큐(`maxQueueSize`, 기본 2048)가 넘치면 span을 버린다. 수집기가 죽어도 앱은 멀쩡해야 하니 이 설계가 맞지만, "trace가 가끔 중간이 비어 있다"면 큐 넘침을 의심한다.

마지막으로 추적은 지표를 대신하지 않는다. 샘플링된 trace로는 정확한 요청 수나 오류율을 셀 수 없다. 숫자는 지표로 세고 알림을 걸고([알림 글](/posts/alerting)), 원인은 trace로 찾는다. 네트워크 계층에서 연결 단위로 누가 누구와 통신했는지는 [흐름 로그](/posts/network-flow-logs)가, 호스트의 재전송과 큐 넘침은 [네트워크 모니터링](/posts/network-monitoring)이 본다. 추적에서 서버 span이 시작되기 전의 긴 틈이 보일 때 넘어갈 곳이 이 둘이다. 계층마다 걸린 타임아웃이 trace에서 어떻게 보이는지는 [타임아웃 글](/posts/timeouts)과 함께 보면 좋다.

## 다시 주문 버튼으로

세 팀이 모두 맞는 말을 했는데도 사용자가 느렸던 건, 각자의 평균에는 "한 주문이 같은 느린 쿼리를 차례로 세 번 부른다"는 모양이 담기지 않았기 때문이다. 분산 추적은 trace id 하나를 헤더에 실어 서비스 경계를 넘기고, 각자 보낸 span을 다시 나무로 세워서 그 모양을 보여 준다. 나무가 끊기지 않게 모든 구간에서 헤더를 넘기고, 저장할 것은 끝난 뒤에 고르고, 로그에도 같은 trace id를 찍어 두면 "어디가 느린가"라는 질문에 폭포 그림 한 장으로 답할 수 있다.

## 면접에서 나올 만한 질문

### trace와 span은 어떻게 다른가요?

span은 한 가지 일을 언제 시작해서 얼마나 걸렸는지 적은 기록 하나이고, trace는 요청 하나에서 생긴 span 전체다. 같은 trace의 span은 같은 trace id를 갖고, 각자 부모 span id를 적어서 나무를 이룬다. HTTP 요청을 받은 일, 다른 서비스를 부른 일, SQL 한 번이 각각 span이 된다.

### 서비스 A가 B를 부를 때 B는 어떻게 같은 trace에 이어 붙나요?

A가 요청 헤더에 W3C `traceparent`를 실어 보낸다. 값은 버전, trace id, A의 클라이언트 span id, 샘플링 플래그 네 칸이다. B는 이 헤더를 읽어 같은 trace id로 자기 서버 span을 만들고 부모를 A의 span id로 적는다. 보통은 HTTP·RPC 계측 라이브러리가 넣고 빼는 일을 대신한다.

### 계측을 붙였는데 trace가 중간에서 끊겨 두 개로 보입니다. 어디를 보나요?

헤더 전파가 끊긴 구간을 찾는다. 계측되지 않은 HTTP 클라이언트(Node의 fetch처럼 다른 구현을 쓰는 것), 메시지 큐 같은 비동기 경계, 헤더를 지우는 프록시, 받은 헤더를 나가는 요청에 옮기지 않는 앱(서비스 메시에서 흔하다)이 대표적이다. 끊긴 지점 뒤 서비스의 로그에 받은 traceparent가 있는지부터 확인한다.

### 헤드 샘플링과 꼬리 샘플링의 차이와 트레이드오프는?

헤드 샘플링은 trace가 시작될 때 trace id로 남길지를 정하고 그 결정을 헤더로 전파한다. 싸고 단순하지만 시작할 때는 느릴지 실패할지 몰라서 중요한 trace도 같은 비율로 버린다. 꼬리 샘플링은 Collector가 trace 전체를 잠시 모아 두고 오류·지연을 보고 고른다. 중요한 trace를 놓치지 않는 대신 모든 span을 일단 보내야 하고, 메모리와 trace id 기준 분산이 필요하다.

### 서비스 메시를 쓰면 앱에서 추적 코드를 안 넣어도 되나요?

span 생성은 사이드카가 해 주지만 헤더 전달은 앱이 해야 한다. 사이드카는 들어온 요청과 그 요청을 처리하다 나가는 요청이 같은 일이라는 걸 알 수 없어서, 앱이 받은 traceparent를 나가는 요청에 옮겨 주지 않으면 trace가 끊긴다. 그리고 메시가 보는 건 네트워크 구간뿐이라 앱 안의 DB 쿼리나 업무 단계는 보이지 않는다.

### 추적이 있는데도 지표와 로그가 따로 필요한 이유는?

추적은 보통 샘플링하기 때문에 정확한 요청 수와 오류율을 셀 수 없다. 그래서 숫자와 알림은 지표가 맡고, 추적은 "어느 구간이 느렸나"라는 원인을 맡는다. 로그는 구간 안에서 무슨 일이 있었는지를 남기고, trace id를 로그에 함께 찍으면 trace를 저장하지 않은 요청도 서비스 사이의 로그를 하나로 묶을 수 있다.

### 바깥에서 들어온 traceparent를 그대로 믿으면 어떤 문제가 있나요?

누구나 sampled 플래그를 01로 보내 저장 비용을 올리거나, 임의의 trace id로 남의 trace에 span을 섞을 수 있다. 실습에서도 임의의 trace id를 넣어 보내자 세 서비스가 그대로 이어받았다. 인터넷에 열린 첫 관문에서는 새 trace를 시작하고 받은 값은 link로만 남기거나, 샘플링 결정을 다시 내리도록 설정한다.
