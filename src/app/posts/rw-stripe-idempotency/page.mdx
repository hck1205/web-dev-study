## 연결이 끊긴 결제 요청은 세 가지 중 하나다

Stripe 블로그의 [Designing robust and predictable APIs with idempotency](https://stripe.com/blog/idempotency)(Brandur Leach, 2017년 2월)는 네트워크가 믿을 수 없다는 말로 시작한다. 서버 사이 네트워크는 휴대폰 회선보다 낫지만, 오가는 정보가 충분히 많으면 결국 이상한 방식으로 실패한다. 장애와 라우팅 문제는 통계적으로 드물어도 늘 어느 정도는 배경처럼 일어나고 있다.

두 노드 사이의 호출 하나가 실패하는 방식을 글은 셋으로 나눴다.

1. 클라이언트가 서버에 연결하는 단계에서 실패한다.
2. 서버가 일을 하는 도중에 호출이 실패해, 일이 어중간한 상태로 남는다.
3. 일은 성공했는데 서버가 결과를 알려 주기 전에 연결이 끊긴다.

첫 번째는 비교적 분명하다. 연결조차 안 됐으니 다시 보내도 된다. 문제는 두 번째와 세 번째다. 클라이언트 쪽에서는 둘을 구분할 수 없다. 메시지를 주고받는 중에 연결이 끊겼다는 사실만 안다. 글은 Stripe API와 그 API를 부르는 서버 한 대만으로도 이미 분산 시스템이라고 적었다. 컴퓨터 두 대가 네트워크로 메시지를 주고받으면 이 문제를 피할 수 없다.

글의 처방은 서버의 끝점(endpoint)을 멱등하게 만드는 것이다. 몇 번을 불러도 부수 효과가 한 번만 일어나는 성질이다. 그러면 클라이언트는 어떤 오류를 보든 성공이 확인될 때까지 다시 보내면 되고, 애매한 실패를 한 가지 방법으로 다룰 수 있다. HTTP 의미상 `PUT`과 `DELETE`는 원래 멱등이다. 글은 서브도메인을 추가하는 DNS API를 예로 들었다. 요청 안에 레코드를 만들 정보가 다 있으니 몇 번을 보내도 같은 결과가 나오고, 이미 있으면 서버가 무시하고 성공을 돌려주면 된다. 메서드별 멱등성의 일반적인 정의는 [HTTP 메서드 글](/posts/http-methods)에 있다.

## 정확히 한 번 일어나야 하는 요청

`PUT`처럼 원래 멱등인 요청은 쉽다. 블로그가 다루는 진짜 문제는 정확히 한 번만 일어나야 하는 작업이다. 고객에게 돈을 청구하는 API를 실수로 두 번 부르면 이중 청구가 된다.

여기서 멱등 키(idempotency key)가 나온다. 클라이언트가 그 작업 하나만을 가리키는 고유한 ID를 만들어 요청과 함께 보낸다. 서버는 그 ID를 자기 쪽의 요청 상태와 연결해 둔다. 실패를 보면 클라이언트는 같은 ID로 다시 보내고, 무엇을 할지는 서버가 정한다. 블로그는 앞의 세 실패에 각각 이렇게 답했다.

- 연결 실패 뒤의 재시도: 서버는 그 ID를 처음 보니 평소처럼 처리한다.
- 처리 도중 실패 뒤의 재시도: 서버가 일을 이어받아 끝낸다. 구현에 크게 달려 있는데, 앞선 작업이 ACID 데이터베이스로 깨끗이 되돌려졌다면 통째로 다시 해도 안전하고, 아니면 상태를 복구해 이어 간다.
- 응답 실패 뒤의 재시도: 일은 이미 성공했으니 서버는 그 성공 결과를 저장해 둔 그대로 돌려준다.

Stripe API는 상태를 바꾸는 끝점, 즉 `POST` 요청에 `Idempotency-Key` 헤더로 이 값을 받는다. 아래 그림은 세 번째 경우, 결제는 됐는데 응답을 잃은 상황이다.

## API 문서가 정해 둔 규칙

블로그가 원리라면 API 문서는 계약이다. 2026년 10월 기준 [Idempotent requests](https://docs.stripe.com/api/idempotent_requests) 문서와 [Advanced error handling](https://docs.stripe.com/error-low-level) 문서가 정해 둔 API v1의 규칙을 정리하면 이렇다.

API 레퍼런스에 실린 요청 예는 이렇다(키 값은 가렸다).

```bash
# 고객을 만드는 POST 요청에 멱등 키를 붙인다 (Stripe API 레퍼런스의 예)
curl https://api.stripe.com/v1/customers \
  -u "sk_test_••••:" \
  -H "Idempotency-Key: KG5LxwFBepaKHyUD" \
  -d description="My First Test Customer (created for API docs at https://docs.stripe.com/api)"
```

연결이 끊겨 응답을 못 받았다면 이 명령을 그대로, 키까지 같게 다시 실행하면 된다. 고객이 둘 생기지 않는다.

저장하는 것은 첫 요청의 상태 코드와 본문이다. 같은 키로 재시도하면 저장된 응답을 돌려주고, 500 오류도 저장된 그대로 돌아온다. 저장 시점이 중요하다. 끝점 실행이 시작된 뒤에야 저장한다. 파라미터 검증에 실패했거나, 같은 키의 다른 요청이 아직 실행 중이라 부딪쳤거나, 잘못된 API 키나 요청 수 제한처럼 실행 전에 나는 오류는 저장하지 않는다. 그런 요청은 원인을 고친 뒤 다시 보내도 된다. 반대로 실행이 시작된 뒤 나온 400은 저장되니, 같은 키로 다시 보내면 같은 400이 돌아온다.

키는 적어도 24시간 보관하고, 그 뒤에는 지울 수 있다. 지워진 뒤 같은 키를 쓰면 새 요청으로 처리된다. 그래서 문서는 결과를 모르는 요청의 재시도를 원래 요청 뒤 24시간 안으로 제한하라고 한다. 같은 키로 다른 파라미터를 보내면 멱등 계층이 원래 요청과 비교해 오류를 낸다. 실수로 키를 다른 작업에 다시 쓰는 일을 막으려는 것이다.

`GET`과 `DELETE`에는 키를 보내지 말라고 했다. 정의상 이미 멱등이라 효과가 없다. 모든 `POST`가 키를 받는다.

같은 키의 요청이 아직 실행 중일 때 409가 오면, 기다렸다가 같은 키와 같은 파라미터로 다시 보낸다. 문서는 여기서 새 키를 쓰면 두 번째 작업이 시작될 수 있다고 경고한다. 파라미터를 바꿔야 한다면 먼저 원래 작업이 성공하지 않았고 실행 중도 아니라는 것을 확인한 뒤 새 키를 쓴다.

키를 만드는 방법으로 문서는 두 가지를 든다. 하나는 UUID v4처럼 충분히 무작위인 값이다. 다른 하나는 장바구니 ID처럼 사용자에게 붙은 객체에서 키를 끌어내는 방법인데, 같은 장바구니로 두 번 제출하는 일을 막기에 간단하다. 어느 쪽이든 최근 24시간 동안 계정 안에서 작업 하나를 분명히 가리킬 만큼 고유해야 한다.

API v2는 동작이 다르다. 같은 문서에 따르면 v2에서는 성공한 작업을 반복하지 않고, 실패했거나 일부만 된 작업을 가능하면 끝까지 다시 시도해 갱신된 응답을 돌려준다. Advanced error handling 문서는 v2가 30일 창을 쓴다고 덧붙였다. 이 글의 나머지는 v1 기준이다.

## 500은 실패가 아니라 모른다는 뜻이다

문서가 가장 강조하는 부분은 5xx를 다루는 법이다. 500을 받은 요청의 결과는 "정해지지 않은 것"으로 다루라고 한다. 오류를 받았어도 작업이 부수 효과를 남겼을 수 있다. 그래서 원래 결과를 확인하기 전에는 새 키로 다시 보내지 말라고 했다. 해당 객체를 조회하고, 대시보드에서 요청을 보고, 웹훅 이벤트로 무슨 일이 있었는지 맞춰 본다.

같은 키로 다시 보내면 저장된 500이 그대로 돌아온다. 장애 복구 중 Stripe가 실패한 작업을 맞춰 보고, 그 과정에서 만들어진 객체의 웹훅을 보내려고 시도하지만, 저장된 응답은 바뀌지 않고 모든 작업이 해결된다는 보장도 없다고 문서는 적었다. 그래서 웹훅 처리기는 API 응답으로 받은 적 없는 객체도 처리할 수 있어야 하고, 객체를 만들 때 메타데이터에 내 쪽 식별자를 넣어 두면 나중에 웹훅으로 온 객체를 내 기록과 맞출 수 있다.

24시간이 지나도 결과를 모르면 옛 키로도 새 키로도 다시 보내지 말고 결과를 맞춰 보라고 한다. 그래도 알 수 없으면 Stripe 지원팀에 문의한 뒤에 작업을 반복하라고 했다. 시간 초과를 실패로 보지 말라는 일반 원칙과 우리 기록·결제사 기록을 맞추는 대사 작업은 [결제 신뢰성 글](/posts/sd-payment-reliability)에서 다뤘다. Stripe 문서가 정해 둔 규칙이 바로 그 원칙을 자기 API에 적용한 것이다.

## 언제 다시 보내나: SDK가 고르는 기준

문서는 응답 헤더 하나를 더 정의해 둔다. `Stripe-Should-Retry`가 `true`면 지수 백오프로 다시 보내고, `false`면 다시 보내지 않으며, 헤더가 없으면 상태 코드와 응답 내용으로 판단한다. Stripe SDK는 이 헤더를 자동으로 따른다.

판단을 실제로 어떻게 하는지는 SDK 소스가 가장 정확하다. 블로그는 Stripe Ruby 라이브러리가 멱등 키를 붙여 백오프와 지터를 섞어 자동으로 재시도한다며 GitHub의 구현을 보라고 했다. 지금의 [stripe-ruby `api_requestor.rb`](https://raw.githubusercontent.com/stripe/stripe-ruby/master/lib/stripe/api_requestor.rb)의 `should_retry?`를 아래 그림에서 응답 종류별로 따라가 볼 수 있다.

## 얼마나 기다렸다 다시 보내나

블로그는 재시도할 때 지수 백오프를 쓰라고 했다. 첫 실패에는 짧게 기다리고, 실패가 이어지면 실패 횟수가 n이면 2^n에 비례해 기다린다. 서버가 장애 중이면 재시도가 통하지 않을 뿐 아니라 상황을 더 나쁘게 만들 수 있기 때문이다. 여기에 무작위를 섞으라고도 했다. 서버 문제로 많은 클라이언트가 거의 같은 순간에 실패하면, 백오프를 해도 재시도 시각이 겹쳐 서버를 다시 두드린다. 블로그는 이것을 썬더링 허드 문제라고 불렀고, 클라이언트마다 대기 시간에 지터를 더해 요청을 흩으라고 했다.

stripe-ruby의 `sleep_time`이 그 구현이다. 2026년 10월 확인한 [stripe-ruby 설정 소스](https://raw.githubusercontent.com/stripe/stripe-ruby/master/lib/stripe/stripe_configuration.rb) 기준으로 기본값은 최대 재시도 2번, 첫 대기 0.5초, 최대 대기 5초다. 계산은 세 줄이다.

```ruby
# stripe-ruby api_requestor.rb의 sleep_time을 줄여 옮김
sleep_seconds = [initial_network_retry_delay * (2**(num_retries - 1)),
                 max_network_retry_delay].min   # 두 배씩, 상한에서 멈춤
sleep_seconds *= (0.5 * (1 + rand))             # 절반에서 전부 사이로 흔듦
[initial_network_retry_delay, sleep_seconds].max  # 첫 대기보다 짧지는 않게
```

`rand`는 0 이상 1 미만이라, 대기 시간은 기준값의 절반 이상 기준값 미만이 된다. 이런 방식을 [지수 백오프 글](/posts/exponential-backoff-jitter)의 분류로는 equal jitter라고 부른다. 마지막 줄 때문에 절반이 첫 대기보다 작아지면 첫 대기로 올린다. 재시도 횟수별로 대기 시간이 어느 범위에 들어가는지 직접 계산해 보자.

## SDK가 키를 대신 만들 때의 함정

같은 소스에서 눈여겨볼 줄이 하나 더 있다. 사용자가 키를 주지 않았더라도, `POST`나 `DELETE` 요청이고 최대 재시도가 0보다 크면 SDK가 `SecureRandom.uuid`로 `Idempotency-Key`를 만들어 붙인다. 소스 주석은 키를 붙여야만 `POST`와 `DELETE`의 네트워크 실패를 안전하게 다시 보낼 수 있다고 적었다.

이 자동 키는 SDK 호출 한 번 안에서만 산다. 재시도 루프가 SDK 안에서 도는 동안에는 같은 키가 쓰이지만, 내 코드가 SDK 호출을 다시 하거나 프로세스가 재시작되면 새 키가 만들어진다. 문서도 이 점을 짚었다. 앱이 여러 SDK 호출이나 프로세스 재시작을 넘어 재시도한다면, 작업 하나에 쓸 키를 직접 만들어 저장해 두고 모든 시도에 그 키를 넘기라고 한다.

실무에서 이중 청구가 나는 전형적인 경로가 여기다. 주문 처리 작업이 결제 호출 중에 타임아웃으로 죽고, 작업 큐가 그 작업을 다시 실행한다. 다시 실행된 작업은 SDK를 새로 부르니 키도 새로 생긴다. Stripe 쪽에서는 서로 다른 두 요청이다. 키를 주문 ID에서 끌어내거나, 처음 만든 키를 주문 행에 저장해 두면 이 경로가 막힌다. 키를 언제, 누가 만들지에 대한 일반 원칙은 [멱등성 키 글](/posts/idempotency-key)의 "키는 누가, 언제 만드나" 부분에 있다.

## 공개된 것과 공개되지 않은 것

여기서 기댄 자료는 Stripe가 바깥에 약속하는 동작과 SDK 코드다. Stripe 서버 안에서 멱등 키를 어디에 어떻게 저장하는지, 같은 키의 동시 요청을 어떤 잠금으로 거르는지, 처리 도중 죽은 요청을 어떻게 이어 받는지는 이 자료들에 나오지 않는다. 블로그는 "구현에 크게 달려 있다"고만 했다.

문서도 바뀐다. API v2는 v1과 재생 방식과 보관 기간이 다르고, SDK 기본값도 언어와 버전마다 다르다고 문서가 직접 밝혔다. 위의 0.5초, 5초, 2번은 2026년 10월에 확인한 stripe-ruby의 값이다. 다른 언어 SDK를 쓴다면 그 SDK의 소스나 문서에서 다시 확인해야 한다. 이 자료들이 Stripe가 고른 설명이라는 한계도 있다. 실제로 이중 청구 문의가 얼마나 들어오는지, 어떤 사고에서 이 규칙들이 생겼는지는 공개돼 있지 않다.

## 우리 API에 멱등 키를 붙인다면

Stripe의 규칙은 "남의 돈을 움직이는 공개 API"라는 조건에서 나왔다. 호출하는 쪽이 수많은 외부 개발자이고, 그들의 재시도 코드를 통제할 수 없으며, 한 번의 실수가 이중 청구로 이어진다. 우리 서비스의 내부 API라면 조건이 다르다. 호출하는 쪽이 우리 팀이고, 요청이 DB 트랜잭션 하나로 끝난다면 유일 제약이나 조건부 쓰기만으로 충분할 때가 많다. 멱등 키 저장소는 DB 한 군데로 끝나지 않는 부수 효과(바깥 결제사 호출, 메일 발송, 메시지 발행)가 있을 때 값어치가 커진다.

처음부터 Stripe만큼 갖추면 비용도 따라온다. 키마다 응답 본문을 저장하니 저장소가 필요하고, 같은 키의 동시 요청을 막는 잠금, 파라미터 비교, 보관 기간이 지난 키 청소, 실행 도중 죽은 요청의 복구까지 만들어야 한다. [멱등성 키 글](/posts/idempotency-key)에서 직접 만들어 본 것처럼 하나하나는 작지만 빠뜨리면 그 구멍으로 중복이 샌다.

지금 바로 가져올 만한 것은 세 가지다. 첫째, 결제처럼 바깥으로 나가는 호출에는 작업 하나에 키 하나를 정하고 그 키를 저장해 둔다. 재시도가 SDK 밖에서 일어나는 경로(작업 큐 재실행, 배포 중 재시작)를 막는 가장 싼 방법이다. 둘째, 타임아웃과 5xx를 "실패"로 기록하지 말고 "모름"으로 기록한다. 모르는 상태는 새 요청으로 덮지 않고 조회나 웹훅으로 맞춘다. 셋째, 우리 API가 키를 받는다면 Stripe처럼 같은 키에 다른 파라미터가 오면 오류를 내고, 재생한 응답에는 표시 헤더를 붙인다. 클라이언트 버그를 일찍 드러낸다.

비슷한 증상을 만나면 볼 곳도 정리할 수 있다. 같은 주문에 결제가 두 건 생겼다면 두 요청의 멱등 키가 같았는지부터 본다. 키가 달랐다면 재시도가 SDK 밖에서 일어난 것이다. 키가 같은데도 두 건이면 24시간 보관 기간을 넘겨 재시도했는지 본다. 429가 늘었다면 `Stripe-Rate-Limited-Reason` 헤더가 있는지 확인해 요청 수 제한과 락 타임아웃을 나누고, 락 타임아웃이면 같은 객체를 동시에 고치는 코드를 찾는다.

## 면접에서 나올 만한 질문

### 결제 API에 멱등 키가 왜 필요한가요?

응답을 못 받은 클라이언트는 결제가 됐는지 알 수 없기 때문이다. Stripe 블로그는 연결 실패, 처리 도중 실패, 처리는 성공했는데 응답만 잃은 실패를 구분하는데, 뒤의 둘은 클라이언트가 구분할 수 없다. 멱등 키가 있으면 같은 키로 다시 보내도 서버가 한 번만 처리하고, 이미 처리했으면 저장한 응답을 돌려준다. 그래서 클라이언트는 어떤 실패든 같은 방법으로 다룰 수 있다.

### Stripe는 멱등 키로 무엇을 저장하고 얼마나 보관하나요?

API v1 기준으로 그 키의 첫 요청이 끝점 실행을 시작한 뒤의 상태 코드와 본문을 저장하고, 500도 저장한다. 키는 적어도 24시간 보관하고 그 뒤에는 지울 수 있다. 검증 실패, 동시 실행 충돌, 요청 수 제한처럼 실행 전에 난 오류는 저장하지 않으니 고쳐서 다시 보내면 된다. 같은 키로 다른 파라미터를 보내면 오류가 난다.

### 500을 받으면 새 키로 다시 보내도 되나요?

안 된다. Stripe 문서는 500의 결과를 정해지지 않은 것으로 보라고 한다. 작업이 부수 효과를 남겼을 수 있으니, 새 키로 보내면 두 번째 결제가 될 수 있다. 같은 키로 보내면 저장된 500이 돌아올 뿐이니, 객체 조회, 대시보드, 웹훅으로 원래 결과를 확인한 뒤에 다음 행동을 정한다.

### 409와 429는 어떻게 다르게 다루나요?

409는 같은 키의 요청이 아직 실행 중이라는 뜻이라 기다렸다가 같은 키, 같은 파라미터로 다시 보낸다. 429는 둘로 나뉜다. `Stripe-Rate-Limited-Reason` 헤더가 붙은 요청 수 제한이면 속도를 줄여야 하고, stripe-ruby도 자동으로 다시 보내지 않는다. 헤더 없는 `lock_timeout`이면 같은 객체를 다른 요청이 잠근 것이라 백오프로 다시 보내고, 같은 객체 변경은 줄 세운다.

### Stripe SDK가 키를 자동으로 붙여 주는데 왜 직접 만들라고 하나요?

SDK가 만든 키는 SDK 호출 한 번 안의 재시도에서만 같다. 내 코드가 SDK를 다시 부르거나, 작업 큐가 작업을 다시 실행하거나, 프로세스가 재시작되면 새 키가 생긴다. Stripe 쪽에서는 다른 요청이라 이중 청구가 될 수 있다. 그래서 문서는 작업 하나에 쓸 키를 직접 만들어 저장하고 모든 시도에 넘기라고 한다.

### 재시도에 지터는 왜 넣고, stripe-ruby는 어떻게 넣나요?

서버 문제로 많은 클라이언트가 같은 순간 실패하면 백오프만으로는 재시도 시각이 겹쳐 서버를 다시 두드리기 때문이다. stripe-ruby는 0.5초에서 시작해 두 배씩 늘리고 5초에서 멈춘 기준값에, 절반에서 전부 사이의 무작위 배수를 곱한다. 다만 첫 대기보다 짧아지지 않게 올리기 때문에 첫 재시도는 늘 0.5초이고 흩어지는 건 두 번째부터다.

### 내부 서비스 사이 API에도 Stripe 같은 멱등 키 저장소를 만들어야 하나요?

부수 효과가 DB 트랜잭션 하나로 끝난다면 유일 제약이나 조건부 쓰기로 충분할 때가 많다. 바깥 결제사 호출, 메일, 메시지 발행처럼 되돌릴 수 없는 부수 효과가 섞이고, 호출하는 쪽의 재시도를 통제할 수 없을 때 키 저장소가 값어치를 한다. 규모가 작아도 결제 호출만큼은 작업마다 키를 정해 저장해 두는 습관이 가장 싸게 이중 청구를 막는다.
