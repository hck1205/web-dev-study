<EasyIntro>
  Next.js에서는 모든 요청이 페이지에 닿기 전에 한 번 지나가는 문지기 파일을 둘 수 있다. 이 파일을 proxy라고 부른다.

  문지기는 들어오는 사람을 보고 그대로 들여보내거나, 다른 문으로 보내거나, 쪽지를 붙여서 들여보낸다. 그런데 로그인 화면 앞에도 같은 문지기를 세우면, 로그인하러 온 사람에게도 로그인부터 하라며 다시 로그인 화면으로 보내서 끝없이 돌게 된다.

  route라는 파일은 화면 대신 데이터를 돌려주는 창구다. 앱이나 다른 서버가 물건 목록을 달라고 하면 이 창구가 답한다.

  문지기는 빠르게 훑어보는 역할이라 모든 검사를 맡기면 안 된다. 문지기를 피해 들어오는 길이 생길 수 있어서, 중요한 방은 방문 앞에서 한 번 더 확인해야 안전하다.
</EasyIntro>

로그인하지 않은 사용자가 `/me`에 오면 `/login`으로 보내려고 `proxy.js`를 처음 썼다. 쿠키에 `session`이 없으면 리다이렉트한다. 배포하자마자 브라우저가 "리디렉션한 횟수가 너무 많습니다"를 띄웠다. Next.js 16.4.1로 같은 코드를 띄우고 `curl`로 따라가 봤다.

```js
// proxy.js — 첫 번째 버전
import { NextResponse } from "next/server";

export function proxy(request) {
  const session = request.cookies.get("session")?.value;
  if (!session) return NextResponse.redirect(new URL("/login", request.url));
  return NextResponse.next();
}

export const config = { matcher: ["/me", "/login", "/dash/:path*", "/api/me"] };
```

```bash
# 리다이렉트를 최대 5번까지 따라가 본다
curl -s -o /dev/null -L --max-redirs 5 \
  -w '%{http_code} redirects=%{num_redirects} final=%{url_effective}\n' localhost:3922/me
```

```text

proxy GET /login
proxy GET /login
proxy GET /login
proxy GET /login
proxy GET /login
```

`/login`에 갈 때마다 proxy가 다시 돌았고, 거기서도 쿠키가 없으니 다시 `/login`으로 보냈다. matcher에 `/login`을 넣은 게 원인이다. 한 줄짜리 실수지만 이 장면에 proxy를 이해하는 데 필요한 것이 다 들어 있다. proxy가 어느 요청에서 도는지(matcher), 요청이 페이지에 닿기 전에 무엇을 거치는지(실행 순서), proxy가 무엇을 할 수 있고 무엇을 맡기면 안 되는지다. 이 글은 이것과 함께 페이지 대신 데이터를 돌려주는 Route Handler(`route.js`)를 다룬다.

## 요청이 페이지에 닿기 전에 거치는 곳

`next start`로 띄운 서버는 요청을 받으면 정해진 순서로 처리한다. 문서에 적힌 순서다.

```text
1. next.config의 headers
2. next.config의 redirects
3. Proxy (rewrite, redirect, 응답 직접 만들기)
4. next.config rewrites의 beforeFiles
5. 파일 시스템 라우트 (public/, _next/static/, app/, pages/)
6. rewrites의 afterFiles
7. 동적 라우트 (/blog/[slug])
8. rewrites의 fallback
```

이 순서는 실험에서도 보인다. `next.config.mjs`에 모든 경로에 `X-Frame-Options: DENY`를 붙이는 `headers`를 넣어 두었다. proxy가 리다이렉트한 응답에도 이 헤더가 붙어 있었다. 헤더 규칙이 proxy보다 먼저 적용되기 때문이다.

```text
HTTP/1.1 307 Temporary Redirect
X-Frame-Options: DENY
location: /login
```

## 무한 리다이렉트를 고치는 matcher

고치는 방법은 둘이다. 코드 안에서 `/login`이면 그냥 넘기거나, matcher에서 `/login`을 빼는 것이다. 보통은 matcher로 "보호할 경로"가 아니라 "제외할 경로"를 적는다. 새 페이지를 만들 때마다 matcher에 추가하는 걸 잊는 일이 없어서다.

```js
// proxy.js — 고친 버전
export function proxy(request) {
  const session = request.cookies.get("session")?.value;
  if (!session) {
    const url = new URL("/login", request.url);
    url.searchParams.set("next", request.nextUrl.pathname); // 로그인 뒤 돌아올 곳
    return NextResponse.redirect(url);
  }
  return NextResponse.next();
}

export const config = {
  matcher: ["/((?!api|_next/static|_next/image|favicon.ico|login).*)"],
};
```

```text
200 redirects=1 final=http://localhost:3922/login?next=%2Fme
```

matcher를 쓸 때 더 알아 둘 것이 있다. matcher 값은 빌드 때 정적으로 읽으므로 변수나 함수 호출 결과를 넣으면 무시된다. 배열 원소로 객체를 주면 `has`, `missing`으로 헤더·쿠키·쿼리 조건을 걸 수 있다. 예를 들어 미리 받기(prefetch) 요청을 빼고 싶으면 `missing: [{ type: "header", key: "next-router-prefetch" }]`를 준다. matcher를 아예 안 쓰면 정적 파일과 이미지까지 모든 요청에서 proxy가 돈다.

proxy 로그를 보면 페이지 요청만 지나가는 게 아니다. 링크를 미리 받는 RSC 요청, 서버 액션 호출도 지나간다. 서버 액션을 부르자 로그에 이렇게 남았다.

```text
proxy POST /shop-actions (server action)
```

서버 액션은 별도 주소가 아니라 그 액션을 쓰는 페이지 주소로 가는 POST다. 그래서 matcher에서 어떤 페이지를 빼면 그 페이지의 서버 액션도 proxy를 건너뛴다. 이게 다음 절의 주제다.

## proxy가 할 수 있는 일

proxy 함수는 `NextRequest`를 받아 무엇을 할지 돌려준다. 할 수 있는 일은 이 정도다.

```js
import { NextResponse } from "next/server";

export function proxy(request, event) {
  const { pathname } = request.nextUrl;

  // 1) 다른 주소로 보낸다. 주소창이 바뀐다
  if (pathname === "/old") return NextResponse.redirect(new URL("/new", request.url));

  // 2) 주소창은 그대로 두고 다른 라우트의 응답을 준다 (A/B 테스트, 다국어)
  if (request.cookies.get("exp")?.value === "b") {
    return NextResponse.rewrite(new URL(`/b${pathname}`, request.url));
  }

  // 3) 응답을 직접 만든다
  if (pathname === "/healthz") return Response.json({ ok: true });

  // 4) 요청 헤더를 바꿔 넘기고, 응답에 쿠키를 심는다
  const headers = new Headers(request.headers);
  headers.set("x-request-id", crypto.randomUUID());
  const res = NextResponse.next({ request: { headers } });
  res.cookies.set("seen", "1", { httpOnly: true, sameSite: "lax" });

  // 5) 응답을 보낸 뒤에도 끝까지 할 일 (로그 전송)
  event.waitUntil(fetch("https://log.example.com", { method: "POST", body: pathname }));
  return res;
}
```

redirect와 rewrite는 헷갈리기 쉽다. redirect는 브라우저에 "저기로 다시 요청해"라고 3xx를 돌려주는 것이라 주소창이 바뀌고 요청이 한 번 더 생긴다. rewrite는 서버 안에서 다른 라우트를 대신 렌더링하는 것이라 주소창은 그대로다. 상태 코드 307, 308과 303의 차이는 [HTTP 상태 코드](/posts/http-status-codes)에 있다.

요청 헤더에 값을 붙여 넘기는 방식은 편하지만 조심해야 한다. 실험 앱의 proxy는 세션 쿠키 값을 `x-user-id` 헤더로 넘기고, `/api/me` Route Handler는 그 헤더를 읽어 돌려준다. 그런데 고친 matcher는 `api`를 제외한다. 쿠키 없이 헤더를 직접 넣어 요청했다.

```bash
# proxy가 돌지 않는 경로에 헤더를 직접 넣는다
curl -s -H 'x-user-id: admin' localhost:3922/api/me
```

```text
{"userId":"admin"}
```

proxy가 돌지 않는 경로에서는 클라이언트가 보낸 헤더가 그대로 들어온다. proxy가 도는 `/me`에서는 `headers.set`이 덮어써서 같은 공격이 통하지 않았다. 덮어쓰지 않고 `headers.append`를 했거나, 값이 없을 때 지우지 않았다면 그곳도 뚫린다. proxy가 붙인 헤더를 믿는 코드는 "그 경로에 proxy가 반드시 돌고, 반드시 덮어쓴다"는 두 가지에 기대는 것이다. matcher를 한 번 고치면 첫째가 조용히 깨진다.

fetch의 캐시 옵션(`cache`, `next.revalidate`, `next.tags`)은 proxy 안에서 효과가 없다. 그리고 proxy는 요청마다 돈다. 미리 받기 요청까지 포함해서다. DB를 조회하거나 느린 API를 부르면 모든 페이지 이동이 그만큼 느려진다. 서명된 쿠키나 JWT를 로컬에서 검증하는 정도의 빠른 확인만 둔다. 문서도 proxy는 낙관적 확인(optimistic check)에만 쓰고, 세션 관리나 권한 판단의 전부를 맡기지 말라고 한다.

## middleware가 proxy로 이름을 바꾼 이유

Next 15까지 이 파일의 이름은 `middleware.ts`였다. 16에서 `proxy.ts`로 바뀌었고 함수 이름도 `middleware`에서 `proxy`로 바뀌었다. 동작은 같다. 옛 이름으로 빌드하면 경고가 나온다.

```text
⚠ The "middleware" file convention is deprecated. Please use "proxy" instead.
  To migrate automatically, run:
  npx @next/codemod@canary middleware-to-proxy .
  Learn more: https://nextjs.org/docs/messages/middleware-to-proxy
```

두 파일을 같이 두면 빌드가 멈춘다.

```text
Error: Both middleware file "./middleware.js" and proxy file "./proxy.js" are detected. Please use "./proxy.js" only. Learn more: https://nextjs.org/docs/messages/middleware-to-proxy
```

문서가 밝힌 이유는 두 가지다. "middleware"라는 이름이 Express의 미들웨어와 헷갈려서 무엇이든 넣는 곳으로 오해받았다. Express 미들웨어는 요청 처리 사슬의 한 칸이라 그 안에서 DB를 부르고 요청 객체에 사용자를 붙이는 게 자연스럽다([Express 미들웨어](/posts/express-middleware)). Next의 이 파일은 앱 앞에 놓인 네트워크 경계에 가깝고, 앱 본체와 따로 배포되어 CDN 가까이에서 돌 수도 있다. 그래서 "proxy"가 더 맞는 이름이라고 본다. 그리고 Next는 이 파일을 최후의 수단으로 쓰길 바란다. 리다이렉트는 설정 파일로, 인증은 데이터 접근 계층으로 가는 API를 계속 늘리겠다고 한다.

런타임도 바뀌었다. proxy는 Node.js 런타임에서만 돌고 바꿀 수 없다. `runtime` 설정을 export하면 에러다. 기존 `middleware.ts`를 Edge 런타임으로 쓰고 있었다면 이름만 바꾸면 안 된다. Edge가 꼭 필요하면 당분간 `middleware.ts`를 유지하라는 게 16 업그레이드 문서의 안내다. 반대로 Node 런타임이 되면서 Node API와 대부분의 npm 패키지를 쓸 수 있게 됐다. 15.5에서 Node 런타임 미들웨어가 안정화된 흐름의 연장이다.

파일은 프로젝트에 하나만 둔다. 경로별 로직이 많으면 모듈로 나눠서 `proxy.ts`에서 불러 조합한다.

## proxy만 믿으면 안 되는 이유

2025년 3월에 공개된 CVE-2025-29927이 이 문제를 크게 드러냈다. Next는 미들웨어가 자기 자신을 다시 부르며 무한히 도는 걸 막으려고 `x-middleware-subrequest`라는 내부 헤더를 썼다. 이 헤더에 미들웨어 이름이 일정 횟수 이상 들어 있으면 미들웨어를 건너뛰었다. 문제는 외부 요청이 이 헤더를 직접 보내도 똑같이 건너뛰었다는 점이다. 미들웨어에서만 로그인을 확인하던 앱은 헤더 하나로 인증이 통째로 우회됐다.

영향받은 건 주로 `next start`나 standalone 출력으로 직접 띄운 앱이고, 15.2.3, 14.2.25, 13.5.9, 12.3.5에서 고쳐졌다. 바로 올릴 수 없으면 앞단의 리버스 프록시에서 이 헤더를 지우는 게 임시 조치였다. 16.4.1에서 같은 헤더를 보내 봤다.

```bash
# 예전 우회 헤더를 넣어 보호된 경로에 요청한다
curl -sI -H 'x-middleware-subrequest: proxy:proxy:proxy:proxy:proxy' localhost:3922/me | grep -i -E '^HTTP|^location'
curl -sI -H 'x-middleware-subrequest: middleware:middleware:middleware:middleware:middleware' localhost:3922/me | grep -i -E '^HTTP|^location'
```

```text
HTTP/1.1 307 Temporary Redirect
location: /login
HTTP/1.1 307 Temporary Redirect
location: /login
```

지금 버전에서는 통하지 않는다. 그래도 이 사건이 남긴 교훈은 버전과 상관없다. 앞에서 본 matcher의 빈틈, proxy가 붙인 헤더를 믿는 코드, 경로를 옮긴 서버 액션 모두 같은 종류의 구멍이다. 문서는 matcher를 바꾸거나 서버 함수를 다른 경로로 옮기면 proxy가 덮던 범위가 조용히 사라질 수 있으니, 인증과 권한은 각 서버 함수 안에서 확인하라고 적어 두었다.

그래서 역할을 나눈다. proxy는 "로그인 안 했으면 로그인 화면으로"처럼 사용자 경험을 위한 빠른 1차 판단을 한다. 진짜 판단은 데이터를 읽고 쓰는 자리, 즉 페이지가 부르는 데이터 함수, Route Handler, 서버 액션 안에서 다시 한다. 인증과 인가가 어떻게 다른지는 [인증과 인가](/posts/authn-vs-authz)에, 서버 액션 안에서 확인을 거는 구체적인 방법은 [서버 액션과 민감 데이터](/posts/nextjs-server-actions-security)에 있다.

## Route Handler로 API 만들기

화면이 아니라 JSON이나 파일을 돌려줄 주소가 필요하면 `route.js`를 만든다. HTTP 메서드 이름으로 함수를 export한다. 웹 표준 `Request`와 `Response`를 그대로 쓰고, Next가 확장한 `NextRequest`로 `nextUrl`과 `cookies`를 편하게 읽는다.

```js
// app/api/items/route.js
const items = [{ id: 1, name: "keyboard" }];

export async function GET(request) {
  const q = request.nextUrl.searchParams.get("q") ?? "";
  return Response.json(items.filter((i) => i.name.includes(q)));
}

export async function POST(request) {
  const body = await request.json();
  if (typeof body.name !== "string") {
    return Response.json({ error: "name required" }, { status: 400 });
  }
  const item = { id: items.length + 1, name: body.name };
  items.push(item);
  return Response.json(item, { status: 201 });
}
```

```bash
curl -s 'localhost:3922/api/items?q=key'                                          # 검색
curl -s -X POST -H 'content-type: application/json' -d '{"name":"mouse"}' \
  -w ' %{http_code}\n' localhost:3922/api/items                                    # 추가
curl -s -X POST -H 'content-type: application/json' -d '{}' \
  -w ' %{http_code}\n' localhost:3922/api/items                                    # 잘못된 입력
curl -s -X PUT -o /dev/null -w 'PUT %{http_code}\n' localhost:3922/api/items       # 없는 메서드
```

```text
[{"id":1,"name":"keyboard"}]
{"id":2,"name":"mouse"} 201
{"error":"name required"} 400
PUT 405
```

export하지 않은 메서드는 Next가 알아서 405로 답한다. 지원하는 메서드는 GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS다. 실험 코드처럼 모듈 변수에 데이터를 쌓으면 인스턴스가 여러 개이거나 서버리스일 때 요청마다 다른 배열을 볼 수 있다. 상태는 DB에 둔다.

동적 세그먼트 아래의 Route Handler는 두 번째 인자로 `params`를 받는다. 페이지처럼 Promise다. TypeScript에서는 전역 타입 `RouteContext`가 경로 문자열로 `params` 타입을 만들어 준다.

```ts
// app/users/[id]/route.ts
import type { NextRequest } from "next/server";

export async function GET(_req: NextRequest, ctx: RouteContext<"/users/[id]">) {
  const { id } = await ctx.params;
  return Response.json({ id });
}
```

Route Handler는 레이아웃에 들어가지 않고 클라이언트 내비게이션에도 참여하지 않는다. 가장 낮은 단계의 라우트다. 같은 세그먼트에 `page.js`와 함께 둘 수 없다. 서버 컴포넌트 트리 밖이라 같은 `fetch`를 두 번 부르면 두 번 나간다. 요청 메모이제이션이 없다.

캐시는 기본으로 하지 않는다. GET만 캐시할 수 있고, 켜려면 세그먼트 설정을 준다. 실험에서 빌드 시각을 돌려주는 GET에 `force-static`을 걸자 빌드 표에 `○ /api/static-info`로 나왔고, 응답은 이랬다.

```text
HTTP/1.1 200 OK
x-nextjs-cache: HIT
cache-control: s-maxage=31536000
```

같은 파일에 POST를 같이 둬도 POST는 캐시되지 않는다. Cache Components를 켠 앱에서는 GET Route Handler도 페이지와 같은 규칙을 따른다. 요청 값이나 캐시 안 된 데이터를 건드리지 않으면 빌드 때 미리 만들고, `request.headers`나 `cookies()`를 읽거나 DB를 부르면 요청 때 실행한다. 캐시하려면 `"use cache"`를 붙인 도우미 함수로 빼서 부른다. 핸들러 본문에 직접 붙일 수는 없다. 캐시 층 전체는 [Next.js 캐시 네 겹](/posts/nextjs-caching-layers)에 정리했다.

응답을 한 번에 다 만들지 않고 흘려보낼 수도 있다. `ReadableStream`을 `Response`에 넣으면 된다.

```js
// app/api/stream/route.js
export async function GET() {
  const enc = new TextEncoder();
  const stream = new ReadableStream({
    async start(c) {
      for (let i = 1; i <= 3; i++) {
        c.enqueue(enc.encode(`data: tick ${i}\n\n`));
        await new Promise((r) => setTimeout(r, 1000));
      }
      c.close();
    },
  });
  return new Response(stream, {
    headers: { "Content-Type": "text/event-stream", "Cache-Control": "no-cache" },
  });
}
```

```text
19:01:21.637 data: tick 1
19:01:22.639 data: tick 2
19:01:23.643 data: tick 3
```

1초 간격으로 한 줄씩 도착했다. LLM 응답을 글자 단위로 흘려보내는 API가 이 모양이다. SSE 형식 자체는 [Server-Sent Events](/posts/server-sent-events)에 있다. 서버리스 플랫폼에서는 함수의 최대 실행 시간 안에서만 흘려보낼 수 있으니 `maxDuration` 세그먼트 설정과 플랫폼 제한을 같이 본다.

언제 Route Handler를 쓰고 언제 서버 액션을 쓰나. 내 앱의 화면에서 일어나는 변경(폼 제출, 버튼)은 서버 액션이 짧고, 응답에 새 화면을 같이 실어 준다. 외부에서 부르는 주소가 필요하면 Route Handler다. 결제사 웹훅, 모바일 앱이 부르는 API, CMS가 부르는 재검증 주소, 파일 다운로드, 공개 GET API처럼 주소와 메서드와 상태 코드가 약속이 되는 경우다.

## next.config의 규칙과 proxy 중 무엇을 쓰나

요청 내용을 보지 않고 정할 수 있는 규칙은 `next.config`에 둔다. 빌드 때 정해지고 proxy보다 먼저, 더 싸게 처리된다.

```js
// next.config.mjs
export default {
  async redirects() {
    return [{ source: "/old-blog/:slug", destination: "/blog/:slug", permanent: true }];
  },
  async headers() {
    return [{ source: "/:path*", headers: [{ key: "X-Frame-Options", value: "DENY" }] }];
  },
};
```

```text
HTTP/1.1 308 Permanent Redirect
location: /blog/hello
```

`permanent: true`는 308, `false`는 307이다. 301, 302가 아닌 이유는 POST가 GET으로 바뀌지 않게 메서드를 지키는 코드라서다. 옛 주소 정리, 보안 헤더처럼 모든 사용자에게 같은 규칙은 여기에 둔다. 보안 헤더 각각의 뜻은 [웹 보안 헤더](/posts/web-security-headers)에 있다.

쿠키, 요청 헤더, 위치처럼 요청을 봐야 정할 수 있는 것만 proxy로 간다. 로그인 여부에 따른 이동, 실험군에 따른 rewrite, 국가별 기본 언어 선택이 여기에 속한다. 그리고 페이지를 그리다가 결정되는 이동은 서버 컴포넌트나 서버 액션 안에서 `redirect()`를 부른다. 데이터를 조회해 보고 "없는 상품이면 목록으로"를 정하는 경우다.

## 다시 /login으로

무한 리다이렉트는 matcher가 로그인 페이지까지 덮어서 생겼다. proxy는 설정 파일의 headers와 redirects 다음에, 파일 시스템 라우트보다 먼저 돈다. 모든 요청, 미리 받기 요청, 서버 액션 POST까지 matcher에 맞으면 지나간다. 그래서 matcher는 제외 목록으로 쓰되 접두사로 비교한다는 걸 알고 쓰고, proxy에서는 빠른 1차 판단만 한다. proxy가 붙여 준 헤더를 믿는 대신, 데이터를 읽고 쓰는 자리에서 세션을 다시 확인한다. CVE-2025-29927은 문지기 한 명에 모든 것을 맡기면 어떻게 되는지 보여 준 사례다. 화면이 아닌 데이터를 돌려줄 주소는 Route Handler로 만들고, 캐시는 GET만, 그것도 직접 켤 때만 된다는 점을 기억한다.

## 면접에서 나올 만한 질문

### Next.js의 Proxy(미들웨어)는 언제 실행되나요?

next.config의 headers와 redirects 다음, beforeFiles rewrite와 파일 시스템 라우트보다 먼저 실행된다. matcher에 맞는 모든 요청에서 돌며 페이지 요청뿐 아니라 RSC 미리 받기 요청과 서버 액션 POST도 포함한다. matcher가 없으면 정적 파일과 이미지 요청에서도 돈다. 그래서 무거운 일을 넣으면 모든 이동이 느려진다.

### 로그인 리다이렉트가 무한히 반복됩니다. 원인과 해결은요?

리다이렉트 목적지인 `/login`도 matcher에 걸려서, 로그인 페이지 요청도 세션이 없다는 이유로 다시 `/login`으로 보내기 때문이다. matcher를 제외 목록 형태로 바꿔 `login`을 빼거나, 코드에서 목적지 경로면 통과시킨다. 제외 목록은 접두사 비교라 `/login-help`, `/apiary` 같은 경로도 함께 빠진다는 점을 확인한다.

### middleware.ts가 proxy.ts로 바뀐 이유는 무엇인가요?

Express 미들웨어와 이름이 같아 무엇이든 넣는 곳으로 오해받았고, 실제로는 앱 앞의 네트워크 경계에 가까워서 Next 16에서 proxy로 이름을 바꿨다. 동작은 같고 codemod로 옮길 수 있다. proxy는 Node.js 런타임 고정이라 Edge 런타임이 필요한 앱은 당분간 middleware를 유지한다. 두 파일을 함께 두면 빌드가 실패한다.

### 미들웨어에서만 인증을 확인하면 왜 위험한가요?

matcher 변경, 경로 이동, 프레임워크 취약점처럼 proxy를 건너뛰는 길이 생기면 보호가 통째로 사라진다. CVE-2025-29927은 내부 헤더 `x-middleware-subrequest` 하나로 미들웨어를 건너뛸 수 있었던 사례다. proxy가 붙인 요청 헤더를 믿는 코드도 proxy가 돌지 않는 경로에서는 클라이언트가 보낸 값을 그대로 받는다. 인증과 인가는 데이터 함수, Route Handler, 서버 액션 안에서 다시 확인한다.

### redirect와 rewrite는 어떻게 다른가요?

redirect는 브라우저에 3xx와 Location을 돌려줘서 주소창이 바뀌고 요청이 한 번 더 생긴다. rewrite는 서버 안에서 다른 라우트의 응답을 대신 주는 것이라 주소창이 그대로다. A/B 테스트나 다국어처럼 사용자에게 주소를 바꿔 보이고 싶지 않을 때 rewrite를 쓴다. 고정 규칙은 next.config에, 요청을 봐야 하는 것만 proxy에 둔다.

### Route Handler의 캐시 동작을 설명해 주세요.

기본으로 캐시하지 않는다. GET만 `dynamic = "force-static"` 같은 세그먼트 설정으로 캐시할 수 있고, 같은 파일의 POST 등은 캐시되지 않는다. Cache Components를 켜면 GET도 페이지와 같은 규칙이라 요청 값이나 캐시 안 된 데이터를 쓰지 않으면 미리 만들어지고, `"use cache"`를 붙인 도우미 함수로 일부를 캐시한다. React 트리 밖이라 요청 메모이제이션도 없다.

### Route Handler와 서버 액션은 어떻게 나눠 쓰나요?

내 앱 화면의 폼과 버튼에서 일어나는 변경은 서버 액션이 짧고, 응답에 바뀐 화면을 함께 실어 준다. 웹훅, 모바일 앱용 API, 재검증 주소, 파일 다운로드처럼 외부에서 주소와 메서드와 상태 코드를 약속하고 부르는 경우는 Route Handler로 만든다. 둘 다 누구나 부를 수 있는 엔드포인트라 인증과 입력 검증은 똑같이 안에서 한다.
