Express로 만든 주문 API를 FastAPI로 옮겼다. 코드는 절반으로 줄었고, 문서 페이지(`/docs`)도 저절로 생겼다. 그런데 부하 테스트를 돌리자 이상한 숫자가 나왔다. 요청 10개를 동시에 보냈더니 0.5초짜리 API가 전부 끝나는 데 5초가 걸렸다. 같은 함수에서 `async` 한 단어를 지우자 0.55초로 돌아왔다. "비동기가 더 빠르다"고 생각하고 붙인 `async`가 서버를 한 줄로 세우고 있었다.

이 글은 [Express 미들웨어 글](/posts/express-middleware)에서 만든 주문 서비스를 파이썬의 FastAPI로 다시 만들면서 무엇이 같고 무엇이 다른지를 본다. 경로 연산과 Pydantic 검증, 422 응답, `Depends`로 하는 의존성 주입, `async def`와 `def`가 실제로 어디서 도는지, uvicorn 워커가 프로세스를 늘리는 방식까지 차례로 간다. Node.js 쪽의 스레드 풀과 프로세스 이야기는 [Node.js 서버 런타임 글](/posts/nodejs-server-runtime)에 있어서, 여기서는 파이썬이 같은 문제를 어떻게 다르게 푸는지에 집중한다.

실행 결과는 코어 4개 리눅스 컨테이너의 Python 3.13에서 FastAPI 0.156.8, Pydantic 2.14.1, Starlette 1.9.0, uvicorn 0.54.0으로 직접 돌린 것이다. 긴 경로와 경고 줄은 줄였다.

## 타입 힌트가 곧 검증이다

FastAPI의 엔드포인트는 데코레이터가 붙은 평범한 함수다. 이걸 경로 연산(path operation)이라고 부른다. 눈에 띄는 건 함수 인자의 타입 힌트가 그대로 요청 검증 규칙이 된다는 것이다.

```python
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()

class CreateOrder(BaseModel):
    product_id: str = Field(min_length=1)
    qty: int = Field(gt=0, le=100)

@app.get("/orders/{order_id}")
async def get_order(order_id: int):      # 경로 변수는 int여야 한다
    return {"id": order_id}

@app.post("/orders", status_code=201)
async def create_order(body: CreateOrder):  # 본문은 CreateOrder 모양이어야 한다
    return {"id": 42, **body.model_dump()}
```

```bash
# uvicorn이 ASGI 서버다. app.py의 app 객체를 17540 포트로 띄운다
uvicorn app:app --port 17540
```

Express에서는 `express.json()` 파서, zod 스키마, `validate` 미들웨어를 따로 만들어 줄을 세웠다. FastAPI에서는 `order_id: int`와 `body: CreateOrder` 두 개의 타입 힌트가 그 일을 한다. 함수가 불리는 시점에는 이미 `order_id`가 정수이고 `body`가 검증된 객체다.

## 422는 누가 왜 보내나

검증에 실패한 요청을 몇 가지 보냈다. Express 글에서 보낸 것과 같은 실수들이다.

```text
GET /orders/abc
{"detail":[{"type":"int_parsing","loc":["path","order_id"],"msg":"Input should be a valid integer, unable to parse string as an integer","input":"abc"}]} -> 422

POST /orders  {"product_id":"","qty":"2"}
{"detail":[{"type":"string_too_short","loc":["body","product_id"],"msg":"String should have at least 1 character","input":"","ctx":{"min_length":1}}]} -> 422

POST /orders  {"product_id":"p-7","qty":"two"}
{"detail":[{"type":"int_parsing","loc":["body","qty"],"msg":"Input should be a valid integer, unable to parse string as an integer","input":"two"}]} -> 422

POST /orders  (Content-Type 없이, curl -d)
{"detail":[{"type":"model_attributes_type","loc":["body"],"msg":"Input should be a valid dictionary or object to extract fields from","input":"{\"product_id\":\"p-7\",\"qty\":2}"}]} -> 422

POST /orders  {"product_id":"p-7",
{"detail":[{"type":"json_invalid","loc":["body",20],"msg":"JSON decode error","input":{},"ctx":{"error":"Expecting property name enclosed in double quotes"}}]} -> 422
```

FastAPI는 요청 검증에 실패하면 모두 422 Unprocessable Content로 답한다. 깨진 JSON도 422다. Express에서는 같은 깨진 JSON이 본문 파서의 400이었다. 클라이언트가 두 서버를 같이 부른다면 상태 코드가 갈린다는 걸 알고 있어야 한다. 팀이 "검증 실패는 400"으로 정했다면 `RequestValidationError`에 예외 처리기를 등록해서 바꾼다.

에러 하나의 모양을 뜯어보자. 조각을 누르면 각 칸이 무엇을 뜻하는지 나온다.

## Pydantic은 기본으로 관대하다

위 출력에서 지나친 줄이 하나 있다. `{"product_id":"","qty":"2"}`를 보냈을 때 에러는 `product_id` 하나뿐이었다. 문자열 `"2"`는 통과했다. zod는 같은 값에 `expected number, received string`을 냈다. 모르는 필드도 확인해 봤다.

```text
POST /orders  {"product_id":"p-7","qty":2,"price":0,"is_admin":true}
{"id":42,"product_id":"p-7","qty":2} -> 201
```

`price`와 `is_admin`은 조용히 버려졌다. 이건 zod와 같다. 모델에 없는 필드는 기본으로 무시(`extra="ignore"`)한다. 정리하면 Pydantic v2의 기본 모드(lax)는 모르는 필드를 버리고, 손실 없이 바꿀 수 있는 값은 바꿔 준다. 엄격하게 하고 싶으면 모델 설정을 바꾼다.

```python
from pydantic import BaseModel, ConfigDict, Field

class Strict(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid")
    product_id: str = Field(min_length=1)
    qty: int = Field(gt=0, le=100)

data = {"product_id": "p-7", "qty": "2", "is_admin": True}
```

```text
lax   : product_id='p-7' qty=2
strict: int_type ('qty',) Input should be a valid integer
strict: extra_forbidden ('is_admin',) Extra inputs are not permitted
lax 2.0: product_id='p' qty=2 | 2.5 -> int_from_float
```

기본 모드도 아무거나 바꾸지는 않는다. `2.0`은 정수로 받아 주지만 `2.5`는 소수점이 사라지니 거절한다. 관대한 쪽은 폼이나 쿼리 문자열처럼 원래 모든 값이 문자열로 오는 입력에 편하다. 대신 클라이언트가 숫자를 문자열로 보내는 버그를 서버가 숨겨 준다. 외부에 공개하는 API라면 `extra="forbid"`로 오타 난 필드 이름(`quantity`를 `qtty`로)을 422로 알려 주는 편이 디버깅 시간을 줄인다.

## Depends는 함수 인자로 하는 주입이다

Express에서는 인증을 미들웨어로 라우트 앞에 세우고, 결과를 `req.user`에 붙였다. FastAPI는 같은 일을 함수 인자로 한다. "이 함수를 부르기 전에 저 함수를 먼저 불러서 그 결과를 넣어 달라"고 선언하는 게 `Depends`다. 이것이 FastAPI의 의존성 주입이다.

```python
def get_db():
    db = FakeSession("postgres")
    print("db: open")
    try:
        yield db                      # 여기서 엔드포인트가 돈다
    finally:
        print("db: close")            # 응답 뒤 정리

def current_user(authorization: Annotated[str | None, Header()] = None):
    print("auth: check")
    if authorization != "Bearer t0k3n":
        raise HTTPException(status_code=401, detail="unauthorized")
    return {"id": "u-1"}

DB = Annotated[FakeSession, Depends(get_db)]
User = Annotated[dict, Depends(current_user)]

@app.get("/orders/{order_id}")
def read_order(order_id: int, db: DB, user: User):
    print(f"handler: user={user['id']}")
    return db.get_order(order_id)
```

토큰이 있는 요청과 없는 요청을 보냈다.

```text
{"id":7,"db":"postgres"} -> 200
{"detail":"unauthorized"} -> 401
```

```text
db: open
auth: check
handler: user=u-1
db: close
db: open
auth: check
db: close
```

`yield`가 있는 의존성은 앞부분이 요청 전에, `finally` 뒷부분이 응답 뒤에 돈다. DB 세션, 트랜잭션, 파일 핸들처럼 열고 닫아야 하는 자원을 이렇게 둔다. 그리고 두 번째 요청을 보면 실수가 하나 보인다. 401로 끝날 요청인데도 DB 세션을 먼저 열었다. FastAPI는 의존성을 함수 인자 순서대로 푼다. `db`가 `user`보다 앞에 있으니 DB를 열고 나서 인증을 확인했다. 인자 순서만 바꿔서 다시 돌렸다.

```python
def read_order(order_id: int, user: User, db: DB):  # 인증을 앞으로
```

```text
--- no token
auth: check
401
--- with token
auth: check
db: open
handler: user=u-1
db: close
200
```

이제 토큰이 없으면 DB 세션을 열지 않는다. 커넥션 풀이 작은 서비스에서는 인증 실패 요청이 몰릴 때 이 차이가 풀 고갈로 나타난다. Express에서 미들웨어 등록 순서가 하던 일을 여기서는 인자 순서가 한다.

의존성의 진가는 테스트에서 나온다. 같은 앱에서 DB와 인증만 갈아 끼웠다.

```python
from fastapi.testclient import TestClient
from deps import app, get_db, current_user, FakeSession

def fake_db():
    yield FakeSession("in-memory")

app.dependency_overrides[get_db] = fake_db
app.dependency_overrides[current_user] = lambda: {"id": "test-user"}
r = TestClient(app).get("/orders/7")
print(r.status_code, r.json())
```

```text
handler: user=test-user
200 {'id': 7, 'db': 'in-memory'}
```

엔드포인트 코드는 하나도 바꾸지 않았다. Express에서는 같은 일을 하려면 모듈 모킹을 쓰거나 앱을 만드는 함수에 의존성을 인자로 넘기는 구조를 직접 짜야 한다. 인터페이스 뒤에서 구현을 바꿔 끼우는 이 생각은 [헥사고날 아키텍처 글](/posts/hexagonal-architecture)의 포트와 어댑터와 같은 뿌리다.

같은 요청 안에서 같은 의존성은 한 번만 불린다. `user`에 의존하는 `perm`과 `user`를 둘 다 받는 엔드포인트라도 `user`는 한 번만 돈다. FastAPI 0.156.8에서 확인한 실제 순서는 `token → user → perm → endpoint`였다. 아래에서 이 규칙을 직접 구현해 보자. 의존성 그래프와 엔드포인트 이름을 받아 함수가 불리는 순서를 돌려준다. 인자 순서대로 깊이 우선으로 풀고, 이미 푼 것은 다시 부르지 않는다.

## async def에 블로킹을 넣으면 한 줄로 선다

처음 장면을 그대로 재현했다. 0.5초를 기다리는 엔드포인트 셋을 만들었다. 블로킹 `time.sleep`을 `async def` 안에서, 같은 호출을 `def` 안에서, 진짜 비동기 대기 `await asyncio.sleep`을 `async def` 안에서.

```python
@app.get("/async-block")
async def async_block():
    time.sleep(0.5)            # 블로킹 호출을 async def 안에서
    return {"ok": True}

@app.get("/sync-block")
def sync_block():
    time.sleep(0.5)            # 같은 호출을 def 안에서
    return {"ok": True}

@app.get("/async-ok")
async def async_ok():
    await asyncio.sleep(0.5)   # 진짜 비동기 대기
    return {"ok": True}
```

각각 10개씩 동시에 보냈다. 블로킹 도중에 `/ping`도 하나 끼워 넣었다.

```text
/async-block  x10  total 5.02s
/sync-block   x10  total 0.56s
/async-ok     x10  total 0.52s
/ping during 4x /async-block: 1.97s
```

`async def` 안의 `time.sleep`이 10개를 한 줄로 세웠다. 0.5초 × 10 = 5초다. 아무 일도 안 하는 `/ping`도 2초 가까이 기다렸다. `async def` 함수는 이벤트 루프 스레드에서 직접 돌기 때문에, 그 안에서 `await` 없이 기다리면 루프 전체가 멈춘다. Node.js에서 `pbkdf2Sync`가 루프를 막은 것과 같은 모양이다. 반면 그냥 `def`로 쓴 함수는 FastAPI가 스레드 풀로 보내서 10개가 동시에 기다렸다.

규칙은 단순하다. 함수 안에서 `await`할 수 있는 라이브러리(httpx의 `AsyncClient`, asyncpg, `redis.asyncio`)만 쓴다면 `async def`. 블로킹 라이브러리(requests, psycopg2, 동기 SQLAlchemy 세션, boto3)를 하나라도 부른다면 `def`. 헷갈리면 `def`가 안전하다. 느릴 수는 있어도 서버 전체를 세우지는 않는다. `async def` 안에서 어쩔 수 없이 블로킹 함수를 불러야 한다면 `await run_in_threadpool(fn)`이나 `asyncio.to_thread(fn)`으로 감싼다.

장애 현장에서 이 실수는 "평소엔 멀쩡한데 부하가 오면 모든 API의 응답 시간이 같이 늘고, CPU는 놀고 있다"로 보인다. CPU가 노는 건 스레드가 계산이 아니라 기다리고 있기 때문이다. `async def`로 선언된 함수 안의 블로킹 호출을 찾는다. asyncio의 디버그 모드(`PYTHONASYNCIODEBUG=1`)는 100ms 넘게 루프를 잡은 콜백을 경고로 찍어 주니 개발 환경에서 켜 두면 일찍 잡힌다.

## def도 무한히 동시에 돌지 않는다

`def` 함수가 가는 스레드 풀은 크기가 정해져 있다. FastAPI(정확히는 그 아래의 Starlette와 AnyIO)의 기본 스레드 수는 40이다. 0.5초짜리 `def` 함수에 요청 80개를 한꺼번에 보내고, 함수 안에서 실제로 시작한 시각을 0.5초 단위로 묶었다.

```python
@app.get("/sync-stamp")
def sync_stamp():
    started = time.monotonic()  # 스레드 풀에서 실제로 시작한 시각
    time.sleep(0.5)
    return {"started": started}
```

```text
started at +0.0s: 40 requests
started at +0.5s: 40 requests
```

정확히 40개씩 두 무리다. 41번째부터는 스레드가 빌 때까지 기다렸다. Node.js의 libuv 풀이 4칸이었던 것과 같은 구조이고, 칸 수만 다르다.

## 스레드로는 계산이 빨라지지 않는다

여기까지는 기다리는 일이었다. 계산하는 일은 사정이 다르다. 순수 파이썬으로 600만 번 도는 리포트 엔드포인트를 `def`로 만들고, 한 프로세스(`--workers 1`)에 동시에 4개를 보냈다.

```python
@app.get("/report")
def report():
    t0 = time.perf_counter()
    s = 0
    for i in range(6_000_000):  # 순수 파이썬 계산 (CPU)
        s += i % 7
    return {"pid": os.getpid(), "ms": round((time.perf_counter() - t0) * 1000)}
```

```text
=== --workers 1
4 concurrent /report: total 1.56s
   {'pid': 901, 'ms': 1222}
   {'pid': 901, 'ms': 1436}
   {'pid': 901, 'ms': 1380}
   {'pid': 901, 'ms': 1366}
```

혼자 돌면 약 270ms 걸리는 계산이 넷이 동시에 돌자 각자 1.2~1.4초가 됐다. 4개의 스레드에서 돌았지만 코어 하나 분량만큼만 진행했다. CPython에는 GIL(Global Interpreter Lock)이 있어서 한 프로세스 안에서 파이썬 바이트코드를 실행하는 스레드는 한 번에 하나다. `time.sleep`이나 소켓 대기처럼 기다리는 동안에는 GIL을 놓기 때문에 앞의 실험에서는 스레드 40개가 잘 겹쳤다. 계산은 겹치지 않는다. Python 3.13부터 GIL 없이 빌드한 실험용 인터프리터(free-threaded)가 나왔지만 아직 기본 배포판은 아니고 라이브러리 지원도 고르지 않다.

계산을 여러 코어로 나누려면 프로세스를 늘린다. uvicorn의 `--workers 4`가 그 일을 한다.

```bash
uvicorn cpu:app --port 17543 --workers 4
```

```text
=== --workers 4
4 concurrent /report: total 1.03s
   {'pid': 1761, 'ms': 441}
   {'pid': 1760, 'ms': 866}
   {'pid': 1760, 'ms': 896}
   {'pid': 1762, 'ms': 360}
4 concurrent /report: total 0.94s
   {'pid': 1761, 'ms': 371}
   {'pid': 1759, 'ms': 850}
   {'pid': 1759, 'ms': 887}
   {'pid': 1759, 'ms': 835}
```

빨라지긴 했는데 고르지 않다. 두 번째 시도에서는 4개 중 3개가 pid 1759로 갔다. uvicorn 워커들은 같은 리슨 소켓을 함께 열어 두고 각자 연결을 `accept`한다. 누가 연결을 가져갈지는 커널이 정하고, 그 순간 한가한 프로세스가 먼저 집어 가기 쉽다. 그래서 순서대로 나눠 주는 Node.js `cluster`의 라운드 로빈과 달리 몰릴 수 있다. 위 클라이언트처럼 연결 몇 개를 재사용하는 경우라면 더 그렇다. 앞단에 로드 밸런서가 연결을 고르게 나눠 주는 구성이 이 편차를 줄인다.

## 기본값이 다른 곳들

Express에서 겪은 문제들이 FastAPI에서는 어떻게 되는지 확인했다. 먼저 엔드포인트에서 예외가 났을 때다.

```python
@app.get("/boom")
async def boom():
    raise RuntimeError("db connection refused")
```

```text
GET /boom     Internal Server Error -> 500
GET /orders/8 {"id":8,"pid":12136} -> 200
```

```text
ERROR:    Exception in ASGI application
Traceback (most recent call last):
  File ".../uvicorn/protocols/http/h11_impl.py", line 411, in run_asgi
  ...
RuntimeError: db connection refused
```

`async def`에서 던진 예외가 500으로 바뀌었고, 같은 pid의 프로세스가 다음 요청을 정상으로 받았다. Express 4에서 프로세스를 내렸던 장면이 여기서는 없다. 응답 본문은 스택 없이 `Internal Server Error` 한 줄이다. 트레이스는 서버 로그에만 남는다. 의도한 에러는 `HTTPException(status_code=404, detail=...)`으로 던지고, 도메인 예외를 응답으로 바꾸는 규칙은 `@app.exception_handler`로 한곳에 모은다.

다음은 본문 크기다. 20MB짜리 JSON을 보냈다.

```text
{"keys":1,"note_len":20971520} -> 200 in 0.361065s
```

그냥 받았다. Express의 `express.json()`은 기본 100kb에서 413을 냈는데, FastAPI와 uvicorn에는 JSON 본문 크기의 기본 한도가 없다. 큰 본문을 통째로 메모리에 올리고 파싱하는 동안 그 워커는 다른 일을 못 한다. 한도는 앞단의 nginx `client_max_body_size`나 직접 만든 미들웨어에서 건다. 앞단 없이 uvicorn을 바로 인터넷에 노출하지 않는 이유 중 하나다.

마지막은 종료다. 2초 걸리는 `/slow` 요청 도중에 `SIGTERM`을 보냈다.

```text
 -> new request: curl exit 7
{"ok":true} -> in-flight 200 after 2.002588s
exit code 143
```

```text
INFO:     Shutting down
INFO:     Waiting for connections to close. (CTRL+C to force quit)
INFO:     127.0.0.1:46114 - "GET /slow HTTP/1.1" 200 OK
INFO:     Waiting for application shutdown.
INFO:     Application shutdown complete.
INFO:     Finished server process [1986]
```

uvicorn은 따로 코드를 쓰지 않아도 새 연결을 막고 처리 중인 요청을 끝까지 마친 뒤, 앱의 lifespan 종료 코드(DB 풀 닫기 등)를 돌리고 끝났다. Express에서 직접 짰던 정상 종료가 기본으로 들어 있는 셈이다. 종료 코드가 0이 아니라 143으로 나온 건, 이 버전의 uvicorn이 정리를 마친 뒤 받은 시그널로 다시 종료해 셸에 "SIGTERM으로 끝났다"는 사실을 전하기 때문이다. 기다리는 시간의 상한은 `--timeout-graceful-shutdown`으로 건다. 다만 로드 밸런서에서 빠지기 전에 문을 닫는 문제는 FastAPI에서도 똑같다. 그 부분은 [Express 글의 종료 절](/posts/express-middleware#끄는-것도-요청-처리다)과 [Pod 생명주기 글](/posts/k8s-pod-lifecycle)을 그대로 따른다.

## Express와 나란히 놓고 고르기

같은 서비스를 두 번 만들어 보면 개념은 거의 일대일로 대응한다. 다른 건 "누가 해 주느냐"다.

| 하는 일 | Express | FastAPI |
|---|---|---|
| 본문 파싱 | `express.json()`을 직접 등록, 기본 100kb | 타입 힌트로 자동, 기본 한도 없음 |
| 검증 | zod 같은 라이브러리 + 미들웨어 | Pydantic 모델, 실패하면 422 |
| 인증·DB 세션 주입 | 미들웨어가 `req`에 붙인다 | `Depends`가 함수 인자로 넣는다 |
| 실행 순서 | 미들웨어 등록 순서 | 의존성 인자 순서 |
| 처리 안 된 예외 | 4: 프로세스 종료 가능, 5: 에러 처리기 | 500으로 바꾸고 프로세스 유지 |
| 블로킹 코드 | 루프를 막는다. 피하는 수밖에 없다 | `def`로 쓰면 스레드 풀(40)에서 돈다 |
| 코어 여러 개 | `cluster` 또는 복제본 | `--workers` 또는 복제본 |
| API 문서 | 따로 작성 | 모델에서 OpenAPI 자동 생성 |

FastAPI가 많은 것을 해 주는 대가도 있다. 타입 힌트와 데코레이터 뒤에서 일어나는 일이 많아서, 위의 `async def` 함정이나 의존성 순서처럼 겉으로 안 보이는 규칙을 알아야 한다. Express는 해 주는 게 적은 대신 줄에 무엇이 서 있는지 눈에 다 보인다. 팀이 이미 파이썬으로 데이터 처리나 ML 모델을 다룬다면 FastAPI가 자연스럽고, 프론트엔드와 같은 언어로 타입을 공유하고 싶다면 Node.js 쪽이 편하다. 성능은 둘 다 I/O 위주의 API에서 병목이 프레임워크보다 DB와 외부 호출에 있는 경우가 대부분이라, 언어 선택의 이유로 앞세우기 어렵다.

## 같은 서비스를 두 번 만들고 나서

FastAPI는 함수의 타입 힌트를 읽어 검증과 주입을 대신 해 준다. 검증 실패는 함수가 불리기 전에 422로 끝나고, 인증과 DB 세션은 `Depends`로 인자 순서대로 풀려서 들어온다. 함수가 어디서 도는지는 선언 한 단어로 갈린다. `async def`는 이벤트 루프에서 돌아서 그 안의 블로킹 호출이 서버 전체를 세우고, `def`는 40칸짜리 스레드 풀에서 돈다. 그리고 GIL 때문에 계산은 스레드가 아니라 프로세스를 늘려야 코어를 나눠 쓴다. 처음 장면의 5초는 `async`를 지우거나 비동기 라이브러리로 바꾸면 사라진다. Node.js 쪽의 같은 이야기는 [Node.js 서버 런타임 글](/posts/nodejs-server-runtime)과 [Express 미들웨어 글](/posts/express-middleware)에 있다.

## 면접에서 나올 만한 질문

### FastAPI는 요청 검증을 어떻게 하나요?

엔드포인트 함수의 타입 힌트를 읽어서 경로 변수, 쿼리, 헤더, 본문을 각각 검증한다. 본문은 Pydantic 모델로 선언하고, 실패하면 함수를 부르지 않고 422와 함께 `type`, `loc`, `msg`가 담긴 목록을 돌려준다. 깨진 JSON도 422로 처리한다. 400으로 바꾸고 싶다면 `RequestValidationError`에 예외 처리기를 등록한다.

### Pydantic이 "2"라는 문자열을 정수 필드에 받아 주는 이유는 무엇이고, 막으려면 어떻게 하나요?

Pydantic v2의 기본 모드가 손실 없이 바꿀 수 있는 값은 바꿔 주는 lax 모드이기 때문이다. `"2"`와 `2.0`은 받고 `2.5`는 거절한다. 모르는 필드는 기본으로 버린다. 엄격하게 하려면 `ConfigDict(strict=True, extra="forbid")`를 주거나 필드 단위로 `strict`를 건다.

### Depends는 무엇이고 테스트에 어떤 도움이 되나요?

엔드포인트가 필요로 하는 값(인증된 사용자, DB 세션, 설정)을 만드는 함수를 인자로 선언하면 FastAPI가 먼저 불러 결과를 넣어 주는 의존성 주입이다. `yield`를 쓰면 요청 전에 열고 응답 뒤에 닫는 자원 관리도 된다. 테스트에서는 `app.dependency_overrides`로 실제 DB와 인증을 가짜로 바꿔 끼울 수 있어서 엔드포인트 코드를 고치지 않고 테스트한다.

### 의존성이 여러 개면 어떤 순서로 실행되나요?

함수 인자 순서대로 깊이 우선으로 풀고, 같은 요청 안에서 같은 의존성은 한 번만 부른다. 그래서 DB 세션을 인증보다 앞에 두면 401로 끝날 요청도 세션을 먼저 연다. 비싼 자원은 인증 같은 검사 뒤에 오도록 인자 순서를 정한다.

### async def와 def 중 무엇을 써야 하나요?

함수 안에서 `await`할 수 있는 비동기 라이브러리만 쓴다면 `async def`, 블로킹 라이브러리를 하나라도 부른다면 `def`를 쓴다. `async def`는 이벤트 루프 위에서 돌기 때문에 그 안의 블로킹 호출이 서버 전체를 멈춘다. 실험에서 0.5초 `time.sleep`을 `async def`에 넣으니 동시 요청 10개가 5초 걸렸고, `def`로 바꾸니 0.56초였다. `def`는 FastAPI가 스레드 풀에서 돌려 준다.

### def 엔드포인트는 몇 개까지 동시에 도나요?

기본 40개다. FastAPI가 쓰는 AnyIO 스레드 풀의 기본 크기다. 41번째부터는 스레드가 빌 때까지 기다리므로, 느린 외부 호출을 하는 `def` 엔드포인트가 다른 `def` 엔드포인트까지 늦출 수 있다. 외부 호출에 타임아웃을 걸고, 가능하면 비동기 클라이언트로 바꾸고, 필요하면 리미터 크기를 조정한다.

### 파이썬 서버에서 CPU 작업을 여러 코어로 나누려면 어떻게 하나요?

스레드로는 안 되고 프로세스를 늘려야 한다. CPython의 GIL 때문에 한 프로세스 안에서는 파이썬 코드를 실행하는 스레드가 한 번에 하나다. uvicorn `--workers`로 프로세스를 늘리거나 컨테이너 복제본을 늘리고, 무거운 계산은 작업 큐로 요청 경로에서 빼는 것도 방법이다. Python 3.13의 free-threaded 빌드는 아직 실험 단계다.

### uvicorn 워커와 Node.js cluster는 요청 분배가 어떻게 다른가요?

Node.js `cluster`는 리눅스에서 primary가 연결을 받아 워커에게 라운드 로빈으로 넘긴다. uvicorn 워커들은 같은 리슨 소켓에서 각자 `accept`하고, 누가 가져갈지는 커널이 정한다. 그래서 순간적으로 한 워커에 연결이 몰릴 수 있고, 실험에서도 4개 중 3개가 한 프로세스로 갔다. 고른 분배가 중요하면 앞단 로드 밸런서에 맡기고, 컨테이너 환경에서는 프로세스 하나짜리 복제본을 늘린다.
