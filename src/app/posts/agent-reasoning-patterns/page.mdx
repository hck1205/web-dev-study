환불 문의를 처리하는 기능을 만들었다. 주문을 조회하고, 주문마다 환불 가능 여부를 확인하고, 고객에게 보낼 답장 초안을 쓰는 일이다. 요즘 다들 에이전트를 만든다길래 도구 세 개를 주고 모델이 알아서 하게 했다. 동작은 했다. 그런데 문의 하나에 모델을 여섯 번 불렀고, 16초가 걸렸다. 같은 일을 코드로 순서를 정해 두고 마지막 답장만 모델에게 쓰게 하니 호출 한 번, 5.6초였다. 결과는 같았다.

이 일에는 에이전트가 필요 없었다. 하지만 어떤 일에는 필요하다. 이 글은 그 경계를 긋는 법과, 에이전트가 필요할 때 고를 수 있는 구조를 같은 과제로 돌려 비교한다. 순서가 정해진 워크플로, 생각-행동-관찰을 되풀이하는 ReAct, 계획을 먼저 세우는 계획-실행, 의존성이 없는 단계를 동시에 돌리는 DAG, 스스로 비평하는 루프, 그리고 여러 에이전트로 나누는 구조다. ReAct 루프는 프레임워크 없이 Node.js 22로 직접 짰고, 모델은 대본대로 답하는 스텁으로 대신해 무엇이 오가는지만 봤다. 시간 비교는 모델 호출 2초, 도구 호출 0.3초라는 가정으로 계산한 값이다.

도구 호출 한 바퀴의 API 형식은 [LLM API 연동 글](/posts/llm-api-integration)에, 모델이 생각을 길게 쓰게 하는 프롬프트 기법(CoT, 자기 일관성, ToT)은 [생각을 시키는 프롬프트 글](/posts/prompt-reasoning-techniques)에 있다. 검색에 특화된 에이전트 루프는 [에이전틱 RAG 글](/posts/agentic-rag)에서 다룬다. 여기서는 루프의 구조 자체를 본다.

## 누가 다음 단계를 정하나

모델을 부르는 시스템은 다음 단계를 누가 정하느냐로 나뉜다. 코드가 정하면 워크플로, 모델이 정하면 에이전트다. Anthropic이 2024년 말에 정리한 분류가 실무에서 많이 쓰이는데, 워크플로 쪽에 이런 모양들이 있다.

- 프롬프트 체이닝: 한 호출의 출력을 다음 호출의 입력으로 잇는다. "개요 쓰기 → 개요 검사 → 본문 쓰기"처럼 단계가 고정된 일에 맞다.
- 라우팅: 입력을 분류해서 갈 곳을 고른다. 환불 문의는 환불 프롬프트로, 배송 문의는 배송 프롬프트로 보낸다.
- 병렬화: 서로 상관없는 일을 동시에 돌리거나(문서 다섯 개 요약), 같은 일을 여러 번 돌려 다수결을 낸다.
- 오케스트레이터-워커: 중심 모델이 일을 쪼개 워커에게 맡기고 결과를 합친다. 쪼개는 방식이 입력마다 달라서 에이전트 쪽에 가깝다.
- 평가자-최적화: 한 모델이 만들고 다른 호출이 평가해서 기준을 넘을 때까지 고친다.

에이전트는 모델에게 도구와 목표를 주고, 루프 안에서 모델이 다음 행동을 고르게 한다. 몇 단계가 걸릴지 미리 모르는 일, 중간 결과를 봐야 다음에 할 일을 알 수 있는 일에 맞다. 코드 수정(테스트를 돌려 봐야 다음 수정을 안다), 낯선 데이터 탐색, 여러 시스템을 오가며 원인 찾기가 그렇다.

처음 장면의 환불 처리는 단계가 정해져 있었다. 주문 조회, 주문마다 확인, 답장 쓰기. 중간 결과에 따라 갈래가 생기지도 않는다. 이런 일에 에이전트를 붙이면 모델이 매번 "다음에 뭘 하지"를 생각하는 값을 낸다. 판단 기준은 단순하다. 순서도를 그릴 수 있으면 워크플로로 짠다. 그릴 수 없을 때 에이전트를 쓴다.

## 생각, 행동, 관찰을 되풀이하는 루프

에이전트의 기본형은 ReAct(Reason + Act)다. 2022년 논문에서 이름이 붙었는데, 모델이 생각(thought)을 쓰고, 행동(action, 도구 호출)을 고르고, 결과(observation)를 읽은 뒤 다시 생각하는 루프다. 지금 모델 API의 도구 호출 루프가 바로 이 구조다. 프레임워크 없이 짜면 이렇게 된다.

```js
// react-loop.mjs: 프레임워크 없이 짠 ReAct 루프의 뼈대
async function runAgent({ maxSteps = 8, maxSameCall = 2 } = {}) {
  const history = [];
  const callCount = new Map();
  for (let step = 1; step <= maxSteps; step++) {
    const d = stubModel(history);                       // 모델 호출 한 번
    if (d.final) { console.log(`#${step} final: ${d.final}`); return { steps: step, history }; }
    const key = d.action + JSON.stringify(d.input);
    callCount.set(key, (callCount.get(key) ?? 0) + 1);
    if (callCount.get(key) > maxSameCall) { console.log(`#${step} stop: same call repeated`); return { steps: step, history }; }
    try {
      const result = await tools[d.action](d.input);
      history.push({ type: "observation", action: d.action, input: d.input, ok: true, result });
      console.log(`#${step} ${d.thought} -> ${d.action}(${JSON.stringify(d.input)}) = ${JSON.stringify(result)}`);
    } catch (e) {
      // 오류도 관찰이다. 모델이 읽고 고칠 수 있게 그대로 돌려준다
      history.push({ type: "observation", action: d.action, input: d.input, ok: false, error: e.message });
      console.log(`#${step} ${d.thought} -> ${d.action}(${JSON.stringify(d.input)}) ERROR ${e.message}`);
    }
  }
  console.log(`stop: maxSteps ${maxSteps} reached`);
  return { steps: maxSteps, history };
}
```

도구는 두 개다. `get_orders`는 주문 세 건(A-1은 3일 전, A-2는 12일 전, A-3은 5일 전)을 돌려주고, `check_refund`는 7일 이내면 환불 가능이라고 답한다. A-3 확인은 처음 한 번 타임아웃이 나게 해 두었다. 스텁 모델은 관찰을 보고 다음 행동 하나를 고른다. 돌린 결과다.

```text
#1 주문부터 본다 -> get_orders({"userId":"u1"}) = [{"id":"A-1","days":3},{"id":"A-2","days":12},{"id":"A-3","days":5}]
#2 A-1 확인 -> check_refund({"orderId":"A-1","days":3}) = {"orderId":"A-1","refundable":true}
#3 A-2 확인 -> check_refund({"orderId":"A-2","days":12}) = {"orderId":"A-2","refundable":false}
#4 A-3 확인 -> check_refund({"orderId":"A-3","days":5}) ERROR timeout after 3000ms
#5 타임아웃이니 한 번 더 -> check_refund({"orderId":"A-3","days":5}) = {"orderId":"A-3","refundable":true}
#6 final: A-1, A-3 환불 가능. A-2는 7일이 지나 불가.
model calls: 6 tool calls: 5
```

## 루프를 멈추는 조건

루프는 모델이 "다 했다"고 할 때 끝난다. 문제는 모델이 그 말을 안 할 때다. 같은 도구를 같은 인자로 계속 부르거나, 실패한 검색을 조금씩 바꿔 끝없이 다시 하거나, 할 일을 스스로 계속 늘린다. 그래서 멈춤 조건을 여러 겹으로 둔다.

최대 단계 수는 가장 기본이다. 위 루프를 `maxSteps: 4`로 돌리면 이렇게 끝난다.

```text
#1 주문부터 본다 -> get_orders({"userId":"u1"}) = [{"id":"A-1","days":3},{"id":"A-2","days":12},{"id":"A-3","days":5}]
#2 A-1 확인 -> check_refund({"orderId":"A-1","days":3}) = {"orderId":"A-1","refundable":true}
#3 A-2 확인 -> check_refund({"orderId":"A-2","days":12}) = {"orderId":"A-2","refundable":false}
#4 A-3 확인 -> check_refund({"orderId":"A-3","days":5}) ERROR timeout after 3000ms
stop: maxSteps 4 reached
```

멈추긴 했는데 사용자에게 줄 답이 없다. A-1과 A-2는 이미 확인했는데 그 결과가 버려졌다. 그래서 상한에 닿았을 때 그냥 끊지 말고, 모델을 한 번 더 불러 "지금까지 알아낸 것으로 답하고, 못 한 것은 못 했다고 적어라"를 시키는 마무리 단계를 둔다. 도구를 주지 않고 부르면 모델은 답을 쓸 수밖에 없다.

같은 호출 반복 감지는 루프에 빠진 걸 빨리 잡는다. 그런데 너무 빡빡하면 정상적인 재시도까지 막는다. `maxSameCall: 1`로 돌리면 이렇다.

```text
#4 A-3 확인 -> check_refund({"orderId":"A-3","days":5}) ERROR timeout after 3000ms
#5 stop: same call repeated
```

타임아웃 뒤 한 번 다시 해 보는 건 맞는 행동인데 반복으로 판정되어 멈췄다. 같은 호출을 세는 기준을 "성공한 같은 호출"로 바꾸거나, 실패 뒤 재시도는 루프 밖의 도구 실행기가 맡게 해서 모델이 같은 호출을 다시 내지 않아도 되게 한다.

이 밖에 실무에서 거는 상한은 토큰 예산(누적 입력·출력 토큰), 시간 제한(전체 벽시계 시간), 비용 상한(요청 하나에 쓸 수 있는 달러)이다. 어느 상한에 걸렸는지는 로그와 지표로 남긴다. 상한에 걸리는 비율이 오르면 도구가 느려졌거나, 프롬프트가 바뀌어 모델이 길을 잃기 시작했다는 신호다. 에이전틱 RAG에서 멈춤 조건을 숫자로 잡는 예는 [에이전틱 RAG 글](/posts/agentic-rag)에도 있다.

## 도구가 실패했을 때

위 실행의 4단계처럼 도구는 실패한다. 이때 예외를 던지고 루프를 끝내면 사용자는 아무것도 못 받는다. 오류를 관찰로 돌려주면 모델이 읽고 대응한다. 다시 해 보거나, 다른 도구를 쓰거나, 그 부분은 못 했다고 답한다. Anthropic API에서는 `tool_result`에 `is_error: true`를 붙여 돌려준다.

돌려주는 오류는 모델이 고칠 수 있게 쓴다. `Error: 400`보다 "orderId는 'A-' 뒤에 숫자가 오는 형식이어야 한다. 받은 값: '1001'"이 낫다. 이 오류 메시지와 도구 설명을 어떻게 쓰는지는 [에이전트 도구 설계 글](/posts/agent-tool-design)에서 자세히 다룬다.

일시적인 실패(타임아웃, 429)는 모델에게 보이기 전에 도구 실행기가 몇 번 재시도하는 게 싸다. 모델 호출 한 번이 도구 재시도 몇 번보다 비싸기 때문이다. 모델에게 보여 줄 오류는 판단이 필요한 실패(권한 없음, 입력 형식 틀림, 대상 없음)로 남긴다.

## 계획을 먼저 세우고 실행하기

ReAct는 한 걸음씩 정하니 유연하지만, 긴 작업에서는 앞에서 뭘 하려 했는지 잊고 옆길로 새기 쉽다. 계획-실행(Planner-Executor) 구조는 첫 호출에서 전체 계획을 세우고, 그 계획대로 실행한다.

```json
{
  "goal": "u1의 최근 주문 환불 가능 여부를 확인하고 답장 초안을 쓴다",
  "steps": [
    { "id": "s1", "tool": "get_orders", "input": { "userId": "u1" } },
    { "id": "s2", "tool": "check_refund", "forEach": "s1.orders" },
    { "id": "s3", "tool": "draft_reply", "uses": ["s2"] }
  ]
}
```

실행은 코드가 해도 되고, 작은 모델이 단계마다 해도 된다. 코드가 하면 모델 호출은 계획 한 번과 마지막 답장 한 번, 두 번이다. 계획이 있으니 진행 상황을 사용자에게 "3단계 중 2단계"로 보여 주기도 쉽고, 사람이 계획을 먼저 승인하게 만들 수도 있다.

약점은 계획이 틀렸을 때다. 계획을 세울 때는 몰랐던 사실이 실행 중에 나온다. 주문 조회 결과 중 하나가 해외 배송이라 다른 환불 규정이 적용된다면, 처음 계획에는 그 규정을 확인하는 단계가 없다. 그래서 재계획 지점을 둔다. 단계가 실패하거나 결과가 계획의 전제와 다르면(예상한 필드가 없음, 결과가 비어 있음), 지금까지의 결과를 붙여 계획을 다시 세운다. 재계획 횟수에도 상한을 건다. 계획을 고치다 끝나는 것도 루프다.

## 기다릴 필요 없는 단계는 동시에

계획을 단계 목록이 아니라 의존성 그래프(DAG, 방향이 있고 순환이 없는 그래프)로 세우면 한 단계 더 나간다. A-1, A-2, A-3 확인은 서로 기다릴 이유가 없다. 셋 다 주문 조회만 끝나면 된다. 의존성을 적어 두면 실행기가 독립된 단계를 동시에 돌린다.

이때 전체 시간은 단계 시간의 합이 아니라 가장 긴 의존 사슬(임계 경로)의 길이다. 계획 2초, 주문 조회 0.3초, 확인 세 개(A-3은 타임아웃 3초 + 재시도 0.3초), 답장 2초면 확인 단계는 가장 느린 A-3의 3.3초만 기다린다. 전체는 2 + 0.3 + 3.3 + 2 = 7.6초다. 아래에서 임계 경로를 직접 계산해 볼 수 있다. 각 작업은 의존하는 작업이 모두 끝나야 시작하고, 동시에 돌릴 수 있는 수에 제한이 없다고 둔다.

DAG 실행에서 조심할 것은 부작용이다. 읽기만 하는 단계는 동시에 돌려도 되지만, 같은 주문에 환불을 실행하는 단계 두 개가 동시에 돌면 이중 환불이 날 수 있다. 쓰기 단계는 의존성을 명시하거나 멱등하게 만든다. 동시 실행 수에도 실제로는 상한이 있다. 외부 API의 호출 한도를 넘지 않게 실행기에서 동시성을 묶는다.

ReAct에서도 비슷한 효과를 낼 수 있다. 요즘 모델 API는 한 응답에 도구 호출 여러 개를 담는 병렬 도구 호출을 지원한다. 모델이 2단계에서 `check_refund` 세 개를 한꺼번에 요청하면 모델 호출이 6번에서 4번으로 준다.

## 같은 과제로 재 본 호출 수와 시간

지금까지의 구조를 같은 환불 과제에 놓고, 모델 호출 2초, 도구 호출 0.3초, A-3 첫 시도 타임아웃 3초라는 가정으로 계산했다.

```text
구조                        모델 호출   걸린 시간
고정 워크플로                1          5.6s   (조회 → 확인 3개 동시 → 답장)
ReAct, 도구 하나씩           6          16.2s
ReAct, 병렬 도구 호출        4          11.6s
계획-실행 (실행은 코드)      2          8.2s   (확인을 하나씩)
DAG (계획 + 동시 실행)       2          7.6s
ReAct 병렬 + 자기 비평       6          15.6s  (비평 1회, 수정 1회 추가)
```

이 과제는 단계가 고정되어 있어서 고정 워크플로가 가장 빠르고 싸다. 다른 구조들은 이 과제에서는 유연함의 값만 냈다. 표가 말해 주는 건 "어느 구조가 좋다"가 아니라 "유연함에 드는 값이 얼마인가"다. 성공률은 이 표에 없다. 스텁 모델은 늘 맞게 움직이니 성공률을 잴 수 없고, 실제 모델로 구조마다 성공률을 재려면 [LLM 평가 글](/posts/llm-evals)처럼 과제 묶음을 만들어 돌린다. 단계가 매번 다른 과제(낯선 저장소의 버그 고치기)라면 고정 워크플로는 아예 풀지 못하니, 이 표의 순서도 뒤집힌다.

## 스스로 비평하게 하기

자기 비평(self-critique, reflection)은 답을 낸 뒤 모델에게 그 답을 검토하게 하고, 문제가 있으면 고치게 하는 구조다. 2023년의 Reflexion 연구는 실패한 시도에 대한 반성문을 다음 시도에 붙여 성공률을 올렸다. 위 표의 마지막 줄처럼 호출이 두 번 늘어난다.

비평이 값을 하는 건 기준이 분명할 때다. "답장에 주문 번호 세 개가 모두 있는가", "환불 불가 이유를 적었는가", "코드가 테스트를 통과하는가"처럼 확인할 항목이 있으면 비평이 실제로 오류를 잡는다. 특히 테스트, 타입 검사, 스키마 검증처럼 코드로 판정할 수 있는 기준이 있으면 모델 비평보다 그 결과를 관찰로 돌려주는 게 더 믿을 만하다.

기준 없이 "더 좋게 고쳐 봐"를 시키면 효과가 작거나 오히려 나빠진다. 같은 모델은 자기 답의 맹점을 같은 방식으로 놓치기 쉽고, 고치라는 지시를 받으면 멀쩡한 답도 바꾼다. 비평 루프에도 멈춤 조건을 둔다. 비평이 "문제없음"을 내거나, 고친 답이 이전 답과 거의 같거나, 횟수 상한에 닿으면 끝낸다.

## 생각의 나무와 CoT는 에이전트 안에서 어디에 있나

Tree-of-Thought(ToT)는 생각의 갈래 여러 개를 펼쳐 평가하고 유망한 것만 더 파는 탐색이다. 에이전트 구조로 보면 한 단계에서 행동 후보를 여러 개 만들고, 평가하고, 고른 것만 실행하는 것과 같다. 호출 수가 후보 수 × 깊이만큼 늘어나서 실무 에이전트에서 전체 루프를 ToT로 돌리는 경우는 드물다. 되돌릴 수 없는 행동을 고르기 전처럼 중요한 갈림길에서만 후보를 몇 개 비교하는 식으로 쓴다. 24 게임으로 따라간 ToT의 동작과 비용은 [생각을 시키는 프롬프트 글](/posts/prompt-reasoning-techniques)에 있다.

Chain of Thought도 비슷하다. 예전에는 ReAct의 "생각" 단계를 프롬프트로 시켜야 했다. 지금의 추론 모델은 도구 호출 사이에도 스스로 생각하는 경우가 많아서 "단계별로 생각하라"를 따로 적는 효과가 줄었다. 그래도 남는 것이 있다. 생각을 글로 받으면 로그로 남고, 사람이 어디서 판단이 틀렸는지 볼 수 있다. 추론 모델의 생각은 공급사에 따라 요약만 주거나 아예 숨기니, 디버깅에 필요한 판단 근거는 답이나 도구 인자에 이유 필드로 따로 받는 편이 확실하다.

## 에이전트를 여럿으로 나눌 때

일이 커지면 에이전트 하나의 컨텍스트가 감당하지 못한다. 문서 200개를 읽고 보고서를 쓰는 일이라면 읽은 내용이 창을 다 채운다. 이럴 때 여러 에이전트로 나눈다. 흔한 모양은 두 가지다.

오케스트레이터-워커는 중심 에이전트가 일을 쪼개 워커 여러 개에 맡기고, 워커는 각자 새 컨텍스트에서 일한 뒤 요약된 결과만 돌려준다. 중심 에이전트의 창에는 워커들이 읽은 원문이 아니라 결과만 쌓인다. Claude Code의 서브에이전트가 이 구조다.

핸드오프는 대화의 주인을 넘기는 구조다. 접수 에이전트가 문의를 받아 환불 전문 에이전트에게 넘기면, 그 뒤로는 환불 에이전트가 사용자와 대화한다. 전문 에이전트마다 도구와 프롬프트를 작게 유지할 수 있다.

## 사람이 승인할 자리

에이전트에게 맡기는 범위가 넓어질수록, 되돌릴 수 없는 행동 앞에 사람이 확인하는 자리를 둔다. 환불 실행, 메일 발송, 결제, 데이터 삭제, 운영 배포 같은 것이다. 구조별로 승인 자리가 다르다. 계획-실행은 계획을 승인받는 자리가 자연스럽다. 계획 단계에서 "환불 2건 실행, 답장 발송"을 보여 주고 승인을 받은 뒤 실행한다. ReAct는 행동 단위로 막는다. 부작용이 있는 도구를 부르려 할 때 루프를 멈추고 승인을 기다린다.

승인 요청에는 사람이 판단할 수 있는 내용을 담는다. "check_refund 호출 승인?"이 아니라 "주문 A-1(₩32,000)과 A-3(₩18,500)을 환불하고 이 내용으로 메일을 보낸다"여야 한다. 승인이 너무 잦으면 사람은 읽지 않고 누르기 시작한다. 읽기 도구는 자동으로, 쓰기 도구는 금액이나 대상 수 기준을 넘을 때만 승인받는 식으로 기준을 둔다.

## 현장에서 에이전트가 이상할 때

"에이전트가 끝나지 않는다"는 제보가 오면 단계별 추적 로그부터 본다. 단계마다 모델이 고른 행동, 인자, 관찰, 토큰 수를 남겨 두어야 한다. 같은 호출이 반복되면 도구 결과가 모델이 기대한 모양이 아니거나(빈 배열을 실패로 오해), 오류 메시지가 고칠 방법을 알려 주지 않는 경우가 많다.

"가끔 엉뚱한 도구를 부른다"는 도구 설명이 겹치거나 도구가 너무 많은 경우다. 도구 목록과 설명을 손보는 쪽이 프롬프트에 "이럴 땐 이 도구를 써라"를 계속 덧붙이는 것보다 효과가 크다.

"비용이 문의마다 들쭉날쭉하다"는 단계 수 분포를 보면 갈린다. 대부분 3~4단계인데 일부가 상한까지 간다면, 그 일부의 공통점(특정 문의 유형, 특정 도구의 오류)을 찾는다. 그런 유형이 고정된 절차로 처리할 수 있는 것이라면 그 유형만 워크플로로 빼서 라우팅한다.

## 순서도를 그릴 수 있으면 에이전트가 아니다

모델이 다음 단계를 정하게 하는 데는 값이 붙는다. 호출 수, 늘어나는 입력, 지연, 예측하기 어려운 동작이다. 순서도를 그릴 수 있는 일은 워크플로로 짜고, 중간 결과를 봐야 다음을 알 수 있는 일에만 에이전트 루프를 쓴다. 루프를 쓴다면 멈춤 조건을 여러 겹으로 두고, 상한에 닿아도 지금까지 알아낸 것으로 답하게 하고, 오류를 모델이 읽을 수 있게 돌려준다. 계획, DAG, 비평, 여러 에이전트는 그 위에 얹는 선택지이고, 각각 무엇을 사고 무엇을 내는지 같은 과제로 재 보고 고른다. 루프 안에서 기억을 다루는 법은 [에이전트 메모리 글](/posts/agent-memory)에, 호출이 곱해질 때의 모델 선택은 [모델 고르기 글](/posts/llm-model-selection)에 있다.

## 면접에서 나올 만한 질문

### 워크플로와 에이전트는 어떻게 다르고, 언제 무엇을 쓰나요?

다음 단계를 코드가 정하면 워크플로, 모델이 정하면 에이전트다. 순서도를 그릴 수 있는 일은 워크플로가 호출 수와 지연이 적고 동작을 예측하기 쉬워서 낫다. 중간 결과를 봐야 다음에 할 일을 알 수 있는 일, 단계 수를 미리 모르는 일에만 에이전트를 쓴다. 같은 환불 과제를 워크플로로 하면 모델 호출 1번인데 ReAct로 하면 6번이 됐다.

### ReAct 패턴을 설명하고 직접 구현할 때 주의할 점은요?

모델이 생각을 쓰고, 도구 호출을 고르고, 결과를 관찰한 뒤 다시 생각하는 루프다. 직접 구현하면 루프 하나에 모델 호출, 도구 실행, 관찰 추가가 들어가고, 단계마다 쌓인 기록 전체를 다시 보내니 입력 토큰이 단계 수의 제곱에 가깝게 는다. 최대 단계 수와 반복 감지 같은 멈춤 조건, 오류를 관찰로 돌려주는 처리, 상한에 닿았을 때 지금까지 결과로 답하게 하는 마무리 단계를 함께 넣는다.

### 에이전트 루프의 멈춤 조건은 어떻게 설계하나요?

모델의 완료 선언 외에 최대 단계 수, 같은 호출 반복 감지, 토큰·시간·비용 상한을 겹쳐 둔다. 반복 감지를 너무 빡빡하게 걸면 정상적인 재시도도 막으니, 일시적 실패의 재시도는 도구 실행기가 맡게 한다. 상한에 걸렸을 때 그냥 끊으면 이미 알아낸 결과가 버려지므로, 도구 없이 한 번 더 불러 부분 답과 못 한 일을 정리하게 한다. 어떤 상한에 걸렸는지 지표로 남겨 비율 변화를 본다.

### 계획-실행 구조의 장단점과 계획이 틀렸을 때의 처리는요?

계획을 먼저 세우면 긴 작업에서 옆길로 새지 않고, 실행을 코드가 맡으면 모델 호출이 크게 줄며, 계획 단계에서 사람 승인을 받기 쉽다. 대신 계획할 때 몰랐던 사실이 실행 중에 나오면 계획이 맞지 않는다. 단계가 실패하거나 결과가 계획의 전제와 다르면 지금까지의 결과를 붙여 재계획하고, 재계획 횟수에도 상한을 둔다.

### DAG로 실행하면 무엇이 빨라지고 무엇을 조심해야 하나요?

서로 의존하지 않는 단계를 동시에 돌려서 전체 시간이 단계 합이 아니라 가장 긴 의존 사슬 길이가 된다. 환불 과제에서 확인 세 개를 동시에 돌리니 가장 느린 하나만 기다렸다. 조심할 것은 부작용 있는 단계의 동시 실행으로, 같은 대상에 쓰는 단계가 겹치면 이중 처리가 나니 의존성을 명시하거나 멱등하게 만든다. 외부 API 한도에 맞춰 동시 실행 수도 제한한다.

### 자기 비평(reflection)은 언제 효과가 있나요?

확인할 기준이 분명할 때다. 필수 항목 포함 여부, 테스트 통과, 스키마 검증처럼 판정할 수 있는 기준이 있으면 비평이 실제로 오류를 잡고, 코드로 판정할 수 있으면 그 결과를 관찰로 돌려주는 게 더 믿을 만하다. 기준 없이 "더 좋게"를 시키면 같은 모델이 같은 맹점을 놓치거나 멀쩡한 답을 바꾼다. 호출이 늘어나니 비평 결과가 "문제없음"이거나 횟수 상한에 닿으면 끝낸다.

### 멀티 에이전트로 나누면 손해인 경우는요?

워커는 중심 에이전트의 맥락을 모르니 넘길 때 빠뜨린 정보로 틀리거나 다시 알아내야 하고, 워커마다 프롬프트와 도구를 따로 읽어 토큰이 곱으로 는다. 서로 엮인 판단(한 파일 동시 수정)을 쪼개면 일관성이 깨진다. 그래서 일이 독립된 조각으로 갈라지고 한 컨텍스트에 다 담기지 않을 때만 나눈다. 하나가 순서대로 해도 되면 하나가 낫다.

### 에이전트에 사람 승인 지점은 어디에 두나요?

환불, 발송, 결제, 삭제, 배포처럼 되돌릴 수 없는 행동 앞에 둔다. 계획-실행 구조면 계획을 승인받고, ReAct면 부작용 있는 도구 호출 직전에 루프를 멈춘다. 승인 요청에는 대상과 금액처럼 사람이 판단할 수 있는 내용을 담고, 승인이 너무 잦으면 읽지 않고 누르게 되니 읽기는 자동으로, 쓰기는 기준을 넘을 때만 승인받게 한다.
