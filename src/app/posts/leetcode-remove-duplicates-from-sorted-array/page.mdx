정렬된 배열에서 중복을 지우라는 문제를 받으면 `[...new Set(nums)]`가 먼저 손에 잡힌다. 한 줄이다. 그런데 이 문제는 새 배열을 돌려받지 않는다. 같은 배열의 앞쪽을 고치고, 남은 개수를 정수로 돌려줘야 한다. 이 채점 방식 하나 때문에 문제가 "읽는 포인터와 쓰는 포인터"를 연습하는 문제가 된다.

[LeetCode 26. Remove Duplicates from Sorted Array](https://leetcode.com/problems/remove-duplicates-from-sorted-array/)의 기본 코드는 [투 포인터 패턴 글](/posts/two-pointers-pattern)의 "같은 방향으로 달리는 두 포인터"에서 이미 봤다. 이 글은 거기서 한 걸음 더 간다. 여섯 가지 풀이를 느린 것부터 재 보고, "바로 앞에 읽은 값"과 비교하는 코드와 "마지막으로 쓴 값"과 비교하는 코드가 어디서 갈리는지 80번 변형으로 확인하고, 같은 값이 길게 이어질 때 이진 탐색으로 덩어리를 통째로 건너뛰는 풀이까지 본다. 실행 결과는 Node.js 22, Python 3.13, Java 21에서 돌린 값이다.

## 앞쪽 k칸만 채점한다

문제를 내 말로 줄이면 이렇다. 오름차순으로 정렬된 정수 배열 `nums`가 있다. 같은 값이 여러 번 나올 수 있다. 값마다 하나만 남기도록 `nums`의 앞쪽을 고치고, 남은 값의 개수 k를 돌려준다. 남은 값들은 원래 순서(오름차순)를 지켜야 한다. 채점은 돌려준 k와 `nums`의 앞 k칸만 본다. k번째 칸부터 뒤에 무엇이 남아 있든 상관없다.

```text
nums = [1, 1, 2, 3, 3, 3, 5]

돌려줄 값: 4
nums 앞 4칸: [1, 2, 3, 5]
nums 뒤 3칸: 무엇이든 괜찮다
```

풀이에 영향을 주는 제약은 셋이다. 길이는 최대 3 × 10^4이라 O(n²)도 아슬아슬하게 돌기는 한다. 값은 -100부터 100까지라 서로 다른 값은 최대 201개다. 그리고 가장 중요한 조건, 배열이 정렬돼 있다. 정렬돼 있으면 같은 값이 모두 붙어 있다. 중복인지 알려면 바로 옆만 보면 된다는 뜻이고, 이 문제의 모든 빠른 풀이가 이 성질에서 나온다.

## 집합에 담았다가 앞에 다시 쓰기

정렬 조건을 쓰지 않는 가장 일반적인 방법은 집합(Set)이다. JavaScript의 `Set`은 넣은 순서를 기억하니, 정렬된 배열을 넣으면 꺼낼 때도 오름차순이다.

```js
// 풀이 1: Set에 담고 앞쪽에 다시 쓰기
function removeDuplicates(nums) {
  const uniq = [...new Set(nums)];             // 처음 나온 순서대로 한 번씩
  for (let i = 0; i < uniq.length; i++) nums[i] = uniq[i]; // 원래 배열 앞에 쓴다
  return uniq.length;
}
```

시간 O(n), 공간 O(n)이다. `nums`의 앞에 다시 써야 하는 이유는 LeetCode가 넘긴 배열을 직접 채점하기 때문이다. `uniq.length`만 돌려주고 쓰기를 빼먹으면 개수는 맞는데 앞 k칸이 원래 값이라 틀린다.

이 풀이는 정렬되지 않은 배열에도 그대로 통한다. 대신 정렬돼 있다는 정보를 버렸고, 그 대가로 O(n) 공간과 해시 계산 비용을 낸다. 문제가 원하는 건 추가 공간 없이 제자리에서 고치는 것이다.

## 중복을 만날 때마다 잘라 낸다

추가 공간 없이 가장 먼저 떠오르는 건 바로 앞과 같으면 그 칸을 `splice`로 빼는 코드다.

```js
// 풀이 2: splice로 중복 칸 빼기
function removeDuplicates(nums) {
  for (let i = 1; i < nums.length; ) {
    if (nums[i] === nums[i - 1]) nums.splice(i, 1); // 빼면 뒤가 당겨지니 i는 그대로
    else i++;
  }
  return nums.length;
}
```

배열 길이 자체가 줄어서 결과도 깔끔하다. 하지만 `splice(i, 1)`은 i 뒤의 모든 칸을 한 칸씩 당기는 O(n) 연산이다. 중복이 많으면 전체가 O(n²)이다. 값마다 두 번씩 나오는 길이 3 × 10^4 배열로 재 봤다.

```text
3e4 splice  374.46ms
3e4 Set     5.69ms
```

LeetCode 제한에서 통과는 하지만 Set 풀이보다 60배 넘게 느리다. 같은 일을 하는 [Move Zeroes](/posts/leetcode-move-zeroes)에서도 `splice`가 10만 칸에 5초를 넘겼다. 반복문 안의 `splice`는 거의 항상 제곱이 숨어 있다는 신호다.

이 풀이에서 가져갈 생각은 "칸을 당기지 말고, 남길 값이 최종적으로 갈 자리를 바로 계산하자"다. 그 자리는 지금까지 남긴 값의 개수다.

## 읽는 포인터와 쓰는 포인터

포인터를 두 개 둔다. `r`(읽기)은 매번 한 칸씩 간다. `w`(쓰기)는 다음에 남길 값을 놓을 자리이고, 값을 하나 남길 때만 한 칸 간다. `w`는 지금까지 남긴 값의 개수와 같다. 끝나면 `w`가 곧 답 k다.

남길지 말지를 정하는 비교는 두 가지로 쓸 수 있다.

### 바로 앞에 읽은 값과 비교

패턴 글에서 본 형태다. 정렬된 원래 배열에서 `nums[r]`이 바로 앞 칸 `nums[r - 1]`과 다르면 새 값이다.

```js
// 풀이 3: 바로 앞에 읽은 칸과 비교
function removeDuplicates(nums) {
  let w = 0;
  for (let r = 0; r < nums.length; r++)
    if (r === 0 || nums[r] !== nums[r - 1]) nums[w++] = nums[r]; // 새 값일 때만 쓴다
  return w;
}
```

그런데 잠깐, `nums[r - 1]`은 이미 덮어썼을 수도 있는 칸 아닌가? `w`가 `r`보다 작으면 `w`번 칸을 덮어쓰는데, `r - 1`은 `w` 이상일 수 있다. 확인해 보면 이 문제에서는 안전하다. 덮어쓰는 칸은 `w - 1` 이하이고, `w - 1`번 칸에는 지금까지 남긴 마지막 값이 들어 있다. 그런데 `r - 1`번 칸이 덮어써졌다면 `w - 1 ≥ r - 1`이고 `w ≤ r`이니 `w - 1 = r - 1`, 즉 `w === r`인 경우뿐이다. 그때 `r - 1`번 칸에는 원래 값 그대로가 쓰여 있다(자기 자리에 자기를 썼으니까). 그래서 우연히 맞는다. 이 "우연"이 80번 변형에서 깨진다.

### 마지막으로 쓴 값과 비교

더 단단한 방법은 원래 배열이 아니라 결과와 비교하는 것이다. 결과의 마지막 값은 `nums[w - 1]`이다. 지금 읽은 값이 그것과 다르면 새 값이다.

```js
// 풀이 4: 마지막으로 쓴 값과 비교
function removeDuplicates(nums) {
  if (nums.length === 0) return 0;
  let w = 1;                                  // nums[0]은 무조건 남긴다
  for (let r = 1; r < nums.length; r++) {
    if (nums[r] !== nums[w - 1]) {            // 결과의 마지막 값과 다르면 새 값
      nums[w] = nums[r];
      w++;
    }
  }
  return w;                                   // 남긴 개수 = 다음에 쓸 자리
}
```

이 비교는 "덮어썼나 안 썼나"를 따질 필요가 없다. `nums[w - 1]`은 언제나 내가 쓴 결과의 끝이고, 그게 정확히 "지금 값이 중복인가"를 정하는 기준이기 때문이다. 정렬돼 있으니 지금 값과 같은 값이 결과에 있다면 반드시 결과의 맨 끝에 있다.

시간은 O(n)이다. `r`은 n − 1번 움직이고 반복마다 비교 한 번, 쓰기는 많아야 한 번이다. 공간은 포인터 두 개라 O(1)이다. 쓰기는 서로 다른 값의 수 − 1번이라, 중복이 없는 배열에서는 모든 칸을 자기 자리에 다시 쓴다. 신경 쓰인다면 `if (w !== r)`를 붙여 같은 자리 쓰기를 건너뛰면 되지만 결과는 같다.

마지막 그림에서 `nums`는 `[1, 2, 3, 5, 3, 3, 5]`다. 뒤 세 칸에 옛 값이 남았다. 처음 풀 때 이걸 지워야 할 것 같아서 `nums.length = w`를 붙이기도 하는데, JavaScript에서는 해가 없지만 문제는 요구하지 않는다. Java의 `int[]`는 길이를 줄일 수도 없다. "앞 k칸만 본다"는 계약이 바로 이 쓰레기를 허용하려고 있는 것이다.

### Python과 Java의 쓰기 포인터

```python
from typing import List

def remove_duplicates(nums: List[int]) -> int:
    if not nums:
        return 0
    w = 1                                  # nums[:w]는 중복 없는 결과
    for r in range(1, len(nums)):
        if nums[r] != nums[w - 1]:         # 마지막으로 쓴 값과 비교한다
            nums[w] = nums[r]
            w += 1
    return w
```

Python에는 한 줄짜리 유혹이 둘 있다. `sorted(set(nums))`와 `list(dict.fromkeys(nums))`다. 둘 다 `[1, 2, 3, 5]`를 만들지만 새 리스트라서, 쓰려면 `nums[:] = ...`로 원래 리스트에 다시 넣고 `len(nums)`를 돌려줘야 한다. O(n) 추가 공간이 든다. `dict.fromkeys`는 Python 3.7부터 넣은 순서가 보장되는 덕분에 정렬되지 않은 입력에서도 처음 나온 순서를 지킨다.

```java
class Solution {
    public int removeDuplicates(int[] nums) {
        if (nums.length == 0) return 0;
        int w = 1;                                 // nums[0..w)는 중복 없는 결과
        for (int r = 1; r < nums.length; r++) {
            if (nums[r] != nums[w - 1]) nums[w++] = nums[r];
        }
        return w;
    }
}
```

Java는 `nums[w++] = nums[r]`처럼 후위 증가를 대입 왼쪽에 넣어 한 줄로 쓰는 경우가 많다. 증가 전의 `w`번 칸에 쓰고 나서 `w`가 는다. `int`끼리 `!=` 비교라 박싱 문제도 없다. 세 언어 모두 같은 결과를 냈다.

```text
4 [1, 2, 3, 5]
1 [7]
1 [2]
4 [-3, -1, 0, 4]
```

`[1, 1, 2, 3, 3, 3, 5]`, `[7]`, `[2, 2, 2]`, `[-3, -3, -1, 0, 0, 4]`를 넣은 결과다.

## 같은 값 덩어리를 통째로 건너뛰기

풀이 4는 같은 값이 1만 개 이어져도 1만 번 비교한다. 서로 다른 값이 몇 개 안 되고 덩어리가 길다면, 덩어리의 끝을 [이진 탐색](/posts/binary-search)으로 찾아 한 번에 건너뛸 수 있다. 정렬돼 있으니 "지금 값보다 큰 첫 칸"을 찾는 상한(upper bound) 탐색이 된다.

```js
// 풀이 5: 덩어리 끝을 이진 탐색으로 찾기
function upper(a, lo, x) {          // a[lo..]에서 x보다 큰 첫 칸
  let hi = a.length;
  while (lo < hi) {
    const m = (lo + hi) >> 1;
    if (a[m] <= x) lo = m + 1;
    else hi = m;
  }
  return lo;
}
function removeDuplicates(nums) {
  let w = 0, r = 0;
  while (r < nums.length) {
    const v = nums[r];
    nums[w++] = v;                  // 새 값 하나를 쓰고
    r = upper(nums, r, v);          // 다음 값이 시작하는 칸으로 뛴다
  }
  return w;
}
```

`nums[w]`에 쓰는 동안 이진 탐색이 망가지지 않을까 걱정되지만, `w ≤ r`이고 탐색은 `r`부터 오른쪽만 보니 덮어쓴 칸을 읽을 일이 없다.

서로 다른 값의 수를 u라 하면 시간은 O(u log n)이다. u가 작으면 O(n)보다 훨씬 빠르다. 그런데 u가 n에 가까우면 O(n log n)이 되어 풀이 4보다 느리다. 세 가지 입력으로 재 봤다.

```text
                       풀이 4     풀이 5
3e4, 값마다 2개        0.12ms     1.38ms
1e6, 서로 다른 값 100  2.60ms     0.10ms
1e6, 모두 다른 값      1.80ms     105.67ms
```

덩어리가 길면 25배 빠르고, 덩어리가 짧으면 수십 배 느리다. 입력의 모양에 크게 기대는 풀이다.

## 한 칸, 두 칸, 네 칸씩 뛰어 보고 좁히기

풀이 5의 약점은 덩어리가 짧아도 매번 배열 끝까지를 범위로 이진 탐색한다는 점이다. 덩어리가 짧을 땐 짧게, 길 땐 길게 탐색하면 둘 다 잡을 수 있다. 지수 탐색(exponential search, 갤로핑이라고도 부른다)이다. 지금 칸에서 1, 2, 4, 8칸 뒤를 차례로 보며 값이 바뀌는 지점을 넘을 때까지 보폭을 두 배로 늘리고, 넘은 뒤에는 마지막 두 지점 사이만 이진 탐색한다.

```js
// 풀이 6: 지수 탐색으로 덩어리 끝 찾기
function runEnd(a, r) {                 // a[r]과 같은 값이 끝나는 다음 칸
  const v = a[r];
  let step = 1, lo = r, hi = r + 1;     // a[lo] === v는 확실하다
  while (hi < a.length && a[hi] === v) { lo = hi; step *= 2; hi = r + step; }
  if (hi > a.length) hi = a.length;     // 이제 답은 (lo, hi] 안에 있다
  while (lo + 1 < hi) {                 // a[lo] === v, a[hi] !== v (또는 끝)
    const m = (lo + hi) >> 1;
    if (a[m] === v) lo = m; else hi = m;
  }
  return hi;
}
function removeDuplicates(nums) {
  let w = 0, r = 0;
  while (r < nums.length) {
    nums[w++] = nums[r];                // 새 값 하나를 쓰고
    r = runEnd(nums, r);                // 같은 값 덩어리를 통째로 건너뛴다
  }
  return w;
}
```

## 비교 대상이 하나 어긋나면

### 80번에서 원래 배열의 두 칸 앞과 비교한다

LeetCode 80(Remove Duplicates from Sorted Array II)은 같은 값을 두 번까지 남긴다. 풀이 4를 넓히면 "결과의 두 칸 앞 `nums[w - 2]`와 다르면 쓴다"가 된다. 풀이 3을 넓히면 "원래 배열의 두 칸 앞 `nums[r - 2]`와 다르면 쓴다"가 된다. 둘을 같은 입력에 넣어 봤다.

```js
function atMostK(nums, k) {                       // 결과와 비교
  let w = 0;
  for (const x of nums) if (w < k || x !== nums[w - k]) nums[w++] = x;
  return w;
}
function atMost2Bug(nums) {                       // 원래 배열과 비교 (틀림)
  let w = 0;
  for (let r = 0; r < nums.length; r++)
    if (r < 2 || nums[r] !== nums[r - 2]) nums[w++] = nums[r];
  return w;
}
```

```text
[1,1,1,2,2,3]  결과와 비교 5 [1,1,2,2,3]  원래 배열과 비교 4 [1,1,2,3]
```

원래 배열과 비교한 쪽이 2를 하나 잃었다. r = 3에서 2를 2번 칸에 썼는데(`w`가 2였다), r = 4에서 비교하는 `nums[r - 2]`가 바로 그 2번 칸이다. 원래는 1이었던 칸이 이미 2로 덮어써져서, 두 번째 2를 "이미 두 개 있다"고 잘못 판단했다. 26번에서는 `r - 1`이 덮어써지는 경우가 `w === r`뿐이라 티가 안 났지만, 두 칸 앞을 보면 `w`와 `r`이 벌어진 상태에서도 덮어쓴 칸을 읽게 된다.

결과와 비교하는 쪽은 이런 걱정이 없다. `nums[w - k]`는 언제나 결과 안의 값이고, 정렬돼 있으니 결과 끝 k개가 모두 x와 같은지는 k칸 앞 하나만 보면 안다. `atMostK(nums, 1)`이 곧 이 문제의 답이고, `atMostK(nums, 2)`가 80번의 답이다. 같은 값을 k번까지 남기는 일반형이 한 줄로 끝나는 게 풀이 4를 기본으로 삼는 이유다.

### w를 1에서 시작하면서 빈 배열을 막지 않는다

```js
let w = 1;
for (let r = 1; r < nums.length; r++) ...
return w;   // 빈 배열에서도 1
```

```text
noguard empty 1
```

LeetCode 26의 제약은 길이가 1 이상이라 통과하지만, 같은 함수를 실무 코드에 옮기면 빈 배열에 "원소 1개"라고 답한다. `w = 0`에서 시작하는 풀이 3이나 `atMostK`는 이 문제가 없다.

### 쓸 자리를 인덱스로 들고 다닌다

```js
let w = 0;                                   // w = 마지막으로 쓴 칸의 인덱스
for (let r = 1; r < nums.length; r++)
  if (nums[r] !== nums[w]) nums[++w] = nums[r];
return w;                                    // w + 1이어야 한다
```

```text
returns w (index)  3
```

`w`를 "다음에 쓸 자리"가 아니라 "마지막으로 쓴 자리"로 정의하면 비교는 `nums[w]`, 쓰기는 `++w`, 반환은 `w + 1`이 된다. 셋 중 하나만 다른 정의를 따르면 한 칸씩 어긋난다. 위 코드는 4가 답인 입력에 3을 돌려줬다. 포인터가 가리키는 게 "마지막으로 채운 칸"인지 "다음에 채울 칸"인지 주석으로 박아 두면 이런 실수가 줄어든다.

### 정렬되지 않은 배열에 그대로 쓴다

```text
unsorted s4 5 [3,1,3,2,1]
unsorted set 3 [3,1,2]
```

`[3, 1, 3, 2, 1]`에 풀이 4를 넣으면 이웃끼리 모두 달라서 아무것도 지우지 않는다. 같은 값이 붙어 있다는 성질은 정렬이 줬던 것이다. 정렬되지 않았으면 Set으로 본 값을 기억하며 같은 쓰기 포인터를 쓴다. 처음 나온 순서가 유지되고 O(n) 공간이 든다. 내림차순으로 정렬된 입력은 같은 값이 여전히 붙어 있어서 풀이 4가 그대로 통한다(`[5, 3, 3, 1, 1]` → `[5, 3, 1]`).

## 남기는 규칙을 바꾸면 생기는 문제들

### 한 번만 나온 값만 남기라면

LeetCode 82(Remove Duplicates from Sorted List II)는 연결 리스트에서 중복된 값을 아예 모두 지운다. 배열로 옮기면 덩어리의 끝을 먼저 찾고, 덩어리 길이가 1일 때만 쓴다.

```js
function onlyUnique(nums) {
  let w = 0, r = 0;
  while (r < nums.length) {
    let e = r;
    while (e + 1 < nums.length && nums[e + 1] === nums[r]) e++; // 덩어리 끝
    if (e === r) nums[w++] = nums[r];                          // 길이 1일 때만 남긴다
    r = e + 1;
  }
  return w;
}
```

```text
only 2 [2,5]
```

`[1, 1, 2, 3, 3, 3, 5]`에서 한 번만 나온 2와 5만 남았다. 덩어리 단위로 생각하는 건 풀이 6과 같다.

### 배열이 아니라 연결 리스트라면

LeetCode 83(Remove Duplicates from Sorted List)이다. 노드를 옮길 필요 없이, 다음 노드가 지금과 같으면 그 노드를 건너뛰도록 `next`만 바꾼다. 같은 값이 없을 때만 앞으로 간다. [연결 리스트](/posts/ds-linked-list)에서 노드를 떼어 내는 기본 동작 그대로다.

```js
function deleteDuplicates(head) {
  let cur = head;
  while (cur && cur.next) {
    if (cur.next.val === cur.val) cur.next = cur.next.next; // 같은 다음 노드를 떼어 낸다
    else cur = cur.next;                                    // 다를 때만 전진
  }
  return head;
}
```

```text
list [1,2,3,5] []
```

같은 값을 떼어 낸 뒤에도 `cur = cur.next`로 전진하면 틀린다. `[3, 3, 3]`이 `[3, 3]`으로 남았다. 첫 3의 다음을 세 번째 3으로 바꾼 뒤, 그 세 번째 3도 같은지 다시 봐야 하는데 그 노드로 전진해 버렸기 때문이다. 배열에서 `splice` 뒤에 인덱스를 올리는 버그와 같은 모양이다.

### 숫자가 아니라 객체 목록이라면

실무에서는 id로 정렬된 레코드 목록에서 같은 id를 하나만 남기는 일이 더 흔하다. 비교를 `!==`로 그대로 하면 객체는 내용이 아니라 참조로 비교되어서, 같은 `id: 1`인 두 객체도 다르다고 나온다(`{ id: 1 } === { id: 1 }`은 `false`). 비교할 키를 꺼내는 함수만 받으면 같은 틀이 그대로 통한다.

```js
function dedupBy(items, key) {
  let w = 0;
  for (const it of items)
    if (w === 0 || key(it) !== key(items[w - 1])) items[w++] = it; // 결과 끝의 키와 비교
  items.length = w;            // 실무 코드에서는 뒤를 잘라 둔다
  return items;
}
dedupBy([{ id: 1, v: "a" }, { id: 1, v: "b" }, { id: 2, v: "c" }, { id: 3, v: "d" }, { id: 3, v: "e" }], r => r.id);
```

```text
[{"id":1,"v":"a"},{"id":2,"v":"c"},{"id":3,"v":"d"}]
```

같은 id 중 먼저 나온 레코드가 남았다. 나중 것을 남기고 싶으면 같은 키일 때 `items[w - 1] = it`로 덮어쓰면 된다. 어느 쪽을 남길지가 요구 사항에 따라 다르다는 점은 Set 풀이로는 표현하기 어렵다.

### 이웃 비교가 다시 나오는 문제

- LeetCode 80(Remove Duplicates from Sorted Array II): 위에서 본 `atMostK(nums, 2)`.
- LeetCode 27(Remove Element): 특정 값만 지운다. 비교 대상이 고정된 값이 된다.
- [Move Zeroes](/posts/leetcode-move-zeroes): 남길 조건이 "0이 아닌가"이고, 뒤를 0으로 정리해야 한다.
- [3Sum](/posts/leetcode-3sum): 정렬한 뒤 "바로 앞과 같으면 건너뛴다"로 같은 조합을 한 번만 낸다. 이 문제의 비교가 반복문 안에 들어간 모양이다.
- [Contains Duplicate](/posts/leetcode-contains-duplicate): 정렬되지 않은 배열에서 중복이 있는지만 묻는다. 정렬 후 이웃 비교, 또는 Set.

## 셸의 uniq도 이웃만 본다

이 문제의 "이웃 비교"는 터미널에서 매일 쓰는 도구에도 그대로 들어 있다. 로그에서 응답 코드 종류를 뽑아 보려고 `uniq`를 쓰면 처음엔 이상한 결과가 나온다.

```bash
# 응답 코드가 한 줄에 하나씩 든 파일
printf '200\n404\n200\n200\n500\n404\n' > codes.txt

echo "== uniq"; uniq codes.txt                  # 붙어 있는 같은 줄만 하나로 합친다
echo "== sort | uniq"; sort codes.txt | uniq     # 정렬해서 같은 값을 붙인 뒤 합친다
echo "== sort | uniq -c"; sort codes.txt | uniq -c # 덩어리마다 몇 줄이었는지 센다
```

```text
== uniq
200
404
200
500
404
== sort | uniq
200
404
500
== sort | uniq -c
      3 200
      2 404
      1 500
```

정렬하지 않은 `uniq`는 3, 4번째 줄의 `200 200`만 하나로 합쳤고, 떨어져 있는 200과 404는 그대로 남겼다. `uniq`는 바로 앞 줄과만 비교하기 때문이다. 이 문제의 풀이 4와 똑같은 동작이고, 정렬되지 않은 `[3, 1, 3, 2, 1]`에서 아무것도 못 지운 것과 같은 이유다. 그래서 늘 `sort | uniq`(또는 `sort -u`)로 쓴다. `uniq -c`는 덩어리 길이를 세는 것이라, 위의 "한 번만 나온 값만 남기라면"에서 덩어리 끝을 찾은 것과 같은 일을 한다.

거꾸로 보면 이 문제가 왜 "정렬된" 배열을 주는지 알 수 있다. 이웃 비교는 메모리를 거의 쓰지 않는다. 마지막 값 하나만 들고 있으면 된다. 수십 GB짜리 로그도 `sort`가 디스크를 써서 정렬해 주면 `uniq`는 한 줄씩 흘려 읽으며 중복을 지운다. Set으로 지우려면 서로 다른 값을 모두 메모리에 들고 있어야 한다. 서로 다른 값이 메모리에 다 들어가면 Set이 빠르고(정렬 O(n log n)이 없다), 안 들어가면 정렬 후 이웃 비교가 유일한 길이다. SQL의 `DISTINCT`나 `GROUP BY`도 데이터베이스가 상황에 따라 해시와 정렬 중 하나를 고르는데, 고르는 기준이 바로 이 메모리다.

## 정렬이 준 선물은 이웃 비교

정렬된 배열에서는 같은 값이 모두 붙어 있다. 그래서 중복인지 알려면 결과의 마지막 값 하나와만 비교하면 되고, 읽기 포인터 `r`과 쓰기 포인터 `w`로 한 번 훑기에 끝난다. `w`는 남긴 개수이자 다음에 쓸 자리라 끝나면 그대로 답이 된다. 비교 대상을 원래 배열의 앞 칸이 아니라 결과의 끝(`nums[w - 1]`)으로 잡아 두면 덮어쓴 칸을 읽을 걱정이 없고, k칸 앞과 비교하는 것만으로 "k번까지 허용"으로 넓어진다. 같은 값이 아주 길게 이어지면 지수 탐색으로 덩어리를 통째로 건너뛰는 것도 가능하다. 다음 문제인 [Boats to Save People](/posts/leetcode-boats-to-save-people)은 같은 투 포인터지만 다시 양 끝에서 좁혀 오는 모양이다.

## 면접에서 나올 만한 질문

### 추가 공간 없이 어떻게 푸나요?

읽기 포인터 `r`과 쓰기 포인터 `w`를 둔다. `nums[r]`이 결과의 마지막 값 `nums[w - 1]`과 다르면 `w` 자리에 쓰고 `w`를 민다. 정렬돼 있어서 같은 값은 모두 붙어 있으니 마지막 값 하나와의 비교로 중복을 가릴 수 있다. O(n) 시간, O(1) 공간이고 끝나면 `w`가 답이다.

### 덮어쓰다가 아직 안 읽은 값을 지우지는 않나요?

`w`는 지금까지 남긴 값의 개수라 항상 `r` 이하다. 쓰는 칸은 이미 읽은 칸뿐이라 아직 읽지 않은 값은 그대로 있다. 같은 방향 투 포인터로 제자리 수정을 할 때 늘 확인하는 성질이다.

### nums[r - 1]과 비교하는 것과 nums[w - 1]과 비교하는 것은 무엇이 다른가요?

26번에서는 둘 다 맞는다. `r - 1`번 칸이 덮어써지는 건 `w === r`일 때뿐이고 그때는 자기 값을 자기 자리에 쓴 것이라서다. 하지만 80번처럼 두 칸 앞을 보면 `nums[r - 2]`가 이미 덮어쓴 칸일 수 있어서 `[1, 1, 1, 2, 2, 3]`에서 2 하나를 잃는다. 결과 쪽 `nums[w - k]`와 비교하면 그런 경우가 없고 k번까지 허용으로 바로 넓어진다.

### 같은 값을 두 번까지 남기라면 어떻게 바꾸나요?

비교 대상을 `nums[w - 2]`로 바꾸고, 처음 두 개(`w < 2`)는 무조건 쓴다. 정렬돼 있어서 결과 끝의 두 값이 지금 값과 같은지는 두 칸 앞 하나만 보면 안다. 일반화하면 `w < k || x !== nums[w - k]`다.

### 배열이 정렬돼 있지 않다면요?

같은 값이 붙어 있지 않으니 이웃 비교가 통하지 않는다. `[3, 1, 3, 2, 1]`에 그대로 넣으면 아무것도 지우지 않는다. Set에 본 값을 기억하며 같은 쓰기 포인터로 처음 나온 값만 남기면 O(n) 시간, O(n) 공간이다. 공간을 못 쓰면 먼저 정렬하고 O(n log n)으로 푼다. 다만 그러면 원래 순서는 잃는다.

### O(n)보다 빠르게 할 수 있나요?

최악에는 안 된다. 모든 값이 다르면 결과에 n개를 다 써야 하니 O(n)이 하한이다. 하지만 같은 값이 길게 이어진다면 덩어리의 끝을 지수 탐색으로 찾아 통째로 건너뛸 수 있다. 서로 다른 값이 100개인 100만 칸에서 한 칸씩 훑기가 2.6ms, 지수 탐색이 0.08ms였다.

### 실무 코드라면 Set과 투 포인터 중 무엇을 쓰나요?

입력이 정렬돼 있다는 보장이 있고 같은 배열을 고쳐야 하면 투 포인터다. 추가 메모리가 없고 정렬 정보를 그대로 쓴다. 정렬 보장이 없거나 새 배열을 만들어도 되면 `[...new Set(arr)]`가 읽기 쉽고 틀릴 곳이 없다. 객체를 키로 비교해야 하거나 같은 키 중 어느 것을 남길지 정해야 하면 키 함수를 받는 투 포인터가 더 다루기 쉽다.

### 반환값 k 뒤의 칸은 왜 정리하지 않아도 되나요?

문제가 앞 k칸만 채점하기로 정했기 때문이다. 이 계약 덕분에 뒤쪽을 지우거나 배열을 줄이는 O(n) 작업이 필요 없다. Java의 `int[]`는 길이를 바꿀 수도 없으니, 제자리 수정 문제가 "길이"를 따로 돌려받는 방식을 쓰는 이유이기도 하다.
