검색창에 `re`를 치자 아래에 다섯 줄이 뜬다. `render`, `rest`, `redis`, `react`, `replica deno`. 한 글자를 더 쳐서 `red`가 되면 목록이 바로 바뀐다. 사람이 다음 글자를 누르기까지는 보통 0.1~0.3초 정도다. 그 안에 답이 와야 추천이 타이핑을 따라온다. 늦게 온 추천은 이미 지나간 글자에 대한 답이라 쓸모가 없다.

면접의 "검색어 자동완성을 설계하라"는 이 짧은 시간 제한에서 출발한다. 기능은 단순하다. 지금까지 친 글자(접두사)로 시작하는 검색어 중 많이 검색된 순서로 다섯 개를 돌려준다. 이 글은 빈도표 하나와 `LIKE` 하나로 시작해서 트라이라는 자료구조로 옮겨 가고, 노드마다 답을 미리 적어 두면 무엇을 얻고 무엇을 잃는지 직접 재 본다.

## 빈도표 하나와 LIKE 하나로 시작하기

가장 작은 버전은 검색어와 검색 횟수를 담은 표 하나다. 검색어는 소문자 영어로만 받는다고 범위를 좁힌다. PostgreSQL 16에 가짜 검색어 20만 개를 넣었다. 기술 단어를 1~3개 이어 붙여 만들었고, 짧은 검색어일수록 인기가 많도록 빈도를 정했다. 실제 검색 기록이 아니니 숫자의 모양만 본다.

```sql
CREATE TABLE query_freq (query text PRIMARY KEY, cnt bigint NOT NULL);  -- 검색어별 검색 횟수
-- 접두사 검색(LIKE 're%')에 쓸 수 있는 인덱스. 기본 정렬 규칙과 상관없이 바이트 순서로 비교한다
CREATE INDEX query_freq_prefix_idx ON query_freq (query text_pattern_ops);

SELECT query, cnt FROM query_freq WHERE query LIKE 're%' ORDER BY cnt DESC LIMIT 5;
```

```text
    query     |  cnt  
--------------+-------
 render       | 71428
 rest         | 29411
 redis        | 14925
 react        | 11235
 replica deno |  4901
(5 rows)
```

답은 맞다. 문제는 비용이다. 실행 계획을 봤다.

```text
 Limit  (cost=1922.89..1922.90 rows=5 width=26) (actual time=7.496..7.499 rows=5 loops=1)
   ->  Sort  (cost=1922.89..1943.09 rows=8081 width=26) (actual time=7.494..7.496 rows=5 loops=1)
         Sort Key: cnt DESC
         Sort Method: top-N heapsort  Memory: 25kB
         ->  Bitmap Heap Scan on query_freq  (cost=233.65..1788.66 rows=8081 width=26) (actual time=0.952..6.926 rows=7413 loops=1)
               Filter: (query ~~ 're%'::text)
               Heap Blocks: exact=1416
               ->  Bitmap Index Scan on query_freq_prefix_idx  (cost=0.00..231.63 rows=7921 width=0) (actual time=0.747..0.748 rows=7413 loops=1)
                     Index Cond: ((query ~>=~ 're'::text) AND (query ~<~ 'rf'::text))
 Planning Time: 0.317 ms
 Execution Time: 7.524 ms
```

`Index Cond: ((query ~>=~ 're'::text) AND (query ~<~ 'rf'::text))`가 인덱스가 하는 일이다. `re` 이상 `rf` 미만인 범위를 잘라 7,413줄을 찾았다. 그런데 그다음 `Sort Key: cnt DESC`에서 7,413줄을 모두 횟수로 정렬해야 다섯 개를 고를 수 있다. 인덱스는 "re로 시작하는 것"은 빨리 찾지만 "그중 많이 찾은 것"은 모른다. 한 글자만 친 `r`은 17,208줄을 정렬해 8.6ms가 걸렸고, `redis c`처럼 길어지면 101줄이라 0.12ms에 끝났다. 가장 먼저 치는 짧은 접두사가 가장 비싸다.

얼마나 자주 불리는지도 따져 보자. 이 글의 가정은 하루 활성 사용자 500만 명, 한 사람이 하루 8번 검색하고, 검색어 하나에 평균 15글자를 친다. 글자마다 요청을 보낸다면 500만 × 8 × 15 ÷ 86,400초 = 초당 약 6,944번이고, 피크가 세 배면 2만 번을 넘는다. 요청마다 수천 줄을 정렬하는 쿼리를 DB가 초당 2만 번 하기는 어렵다. 그래서 접두사로 바로 찾아 들어가는 자료구조가 필요하다.

## 접두사를 길로 바꾸는 트라이

트라이(trie)는 문자열을 글자 하나씩 내려가는 나무로 저장한다. 맨 위 뿌리에서 `r`로 내려가고, 거기서 `e`로, 다시 `d`로. 같은 접두사를 가진 검색어는 같은 길을 공유한다. `redis`와 `react`는 `re`까지 같은 노드를 지나고 거기서 갈라진다. 검색어가 끝나는 노드에는 검색 횟수를 적어 둔다. 이름은 꺼낸다는 뜻의 retrieval에서 왔다.

## 접두사 아래를 전부 뒤지면

가장 단순한 방법은 출발 노드 아래를 전부 돌며 끝나는 검색어를 모으고, 횟수로 정렬해 다섯 개를 자르는 것이다. Node 22로 같은 20만 개 검색어의 트라이를 만들고 재 봤다.

```js
// trie.mjs 일부: 노드는 자식 맵과 이 노드에서 끝나는 검색어의 횟수를 가진다
class Node { constructor() { this.children = new Map(); this.count = 0; this.top = null; } }

function topNaive(root, prefix) {
  const start = find(root, prefix); if (!start) return { top: [], visited: 0 };
  const found = []; let visited = 0;
  const stack = [[start, prefix]];
  while (stack.length) {                                   // 출발 노드 아래를 전부 돈다
    const [n, s] = stack.pop(); visited++;
    if (n.count) found.push([s, n.count]);
    for (const [ch, c] of n.children) stack.push([c, s + ch]);
  }
  found.sort((a, b) => b[1] - a[1] || (a[0] < b[0] ? -1 : 1));  // 횟수, 같으면 사전순
  return { top: found.slice(0, K), visited };
}
```

```text
"r" visited=88862 naive=61234.4us cached=0.2us same=true
"re" visited=38220 naive=24894.4us cached=0.1us same=true
"red" visited=6533 naive=2752.5us cached=0.0us same=true
"redis" visited=6531 naive=2588.6us cached=0.1us same=true

```

20만 개 검색어가 노드 103만 개가 됐고 메모리 234MB를 썼다. `r` 하나를 치면 노드 8만 8,862개를 돌아 61ms가 걸렸다. SQL보다 오히려 느리다. 출발 노드를 빨리 찾아도 그 아래가 넓으면 소용없다. 이 표의 `cached` 열은 다음 절의 방법이다.

## 노드마다 상위 5개를 적어 둔다

어차피 같은 접두사에는 늘 같은 답이 나온다. 그러면 답을 미리 계산해 노드에 적어 두면 된다. 모든 노드에 "이 노드 아래에서 가장 많이 찾은 다섯 개"를 저장한다. 질의는 접두사를 따라 내려간 뒤 거기 적힌 목록을 읽기만 하면 끝난다.

목록은 아래에서 위로 채운다. 잎 노드의 목록은 자기 자신뿐이다. 부모 노드는 자기 검색어(있다면)와 자식들의 목록을 모아 다시 상위 다섯 개를 고른다. 자식의 목록 바깥에 있는 검색어는 그 자식 아래에서 이미 다섯 등 밖이니 부모에서도 다섯 등 안에 들 수 없다. 그래서 자식마다 다섯 개만 보면 충분하다.

```js
// trie.mjs 일부: 노드마다 상위 5개를 계산해 둔다 (자식들의 상위 5개 + 자기 자신 → 다시 5개)
function cacheTop(n, s) {
  const cand = n.count ? [[s, n.count]] : [];
  for (const [ch, c] of n.children) cand.push(...cacheTop(c, s + ch));
  cand.sort((a, b) => b[1] - a[1] || (a[0] < b[0] ? -1 : 1));
  n.top = cand.slice(0, K);
  return n.top;
}
const topCached = (root, prefix) => find(root, prefix)?.top ?? [];
```

```text
cache top-5 at every node: 1647ms heap=+89MB
re  -> render(71428), rest(29411), redis(14925), react(11235), replica deno(4901)
redis -> redis(14925), redis kubernetes(3436), redis trie(2531), redis json(2518), redis https(1510)
```

앞 표의 `cached` 열로 돌아가 보면 `r`의 61ms가 0.2µs가 됐다. 30만 배다. 이제 질의 시간은 접두사 길이에만 달렸고, 노드 아래가 얼마나 넓은지와는 상관없다. 결과도 `same=true`로 전부 뒤진 결과와 같았다. 위 `re`의 목록이 SQL의 결과와 똑같은 것도 확인할 수 있다.

대가는 세 가지다.

- 메모리가 늘었다. 이 측정에서는 89MB가 더 들었다. 노드 103만 개가 각자 목록을 가졌기 때문이다. 이 데모에서는 같은 검색어 문자열을 여러 노드가 참조로 공유했지만, 디스크나 다른 서버에 저장하면 노드마다 문자열 사본이 생겨 더 커진다. 그래서 목록에 문자열 대신 검색어 ID를 두기도 한다.
- 만드는 시간이 든다. 목록 계산에 1.6초가 걸렸다. 검색어가 수억 개면 한 대에서 하기 어렵다.
- 고치기가 어렵다. `redis kubernetes`의 횟수가 하나 늘면 그 검색어가 지나는 모든 노드, 즉 `r`, `re`, `red`부터 끝까지 16개 노드의 목록을 다시 계산해야 할 수 있다. 검색이 초당 수천 번 들어오는데 그때마다 이렇게 고치면 읽기보다 쓰기가 더 바빠진다.

마지막 대가 때문에 실무에서는 트라이를 검색이 들어올 때마다 고치지 않는다. 검색 기록을 모아 두었다가 주기적으로 새 트라이를 통째로 만들어 바꿔 끼운다. 그 과정이 [㉚](/posts/sd-autocomplete-data-pipeline)의 주제다.

목록을 적는 깊이에도 상한을 둔다. 사람은 수십 글자를 넘게 친 뒤에도 추천을 기다리지 않는다. 접두사 길이를 예컨대 50글자까지로 자르면 그보다 깊은 노드는 목록을 갖지 않아도 되고, 엄청나게 긴 문자열로 서버를 괴롭히는 요청도 막힌다.

## 한글은 치는 동안 글자가 바뀐다

영어는 친 글자가 그대로 접두사다. 한글은 다르다. 두벌식 자판으로 `닭갈비`를 칠 때 입력창에는 `ㄷ`, `다`, `달`, `닭` 순으로 글자가 바뀐다. `달`은 `닭갈비`의 접두사가 아니다. 문자열로는 `달`과 `닭`이 전혀 다른 글자다. 다섯 검색어로 확인했다.

```js
// hangul.mjs 일부: 완성형 음절을 키보드로 친 자모 순서로 푼다 (겹받침 ㄺ → ㄹㄱ도 쪼갠다)
function toKeys(s) {
  let out = "";
  for (const ch of s) {
    const c = ch.codePointAt(0) - 0xac00;                 // 한글 음절은 가(U+AC00)부터 11,172자
    if (c >= 0 && c < 11172) out += CHO[Math.floor(c / 588)] + JUNG[Math.floor((c % 588) / 28)] + JONG[c % 28];
    else out += COMPOUND[ch] ?? ch;
  }
  return out;
}
```

세 방식을 비교했다. `plain`은 문자열 그대로 `startsWith`, `nfd`는 유니코드 정규화(NFD, 음절을 초성·중성·종성 부호로 나누기)를 한 뒤 비교, `keys`는 위 함수로 키보드 입력 순서까지 푼 뒤 비교했다.

`plain`은 `다`에서 `닭갈비`를 못 찾고, `닭가`에서도 `닭갈비`를 놓쳤다. 다음 글자 `ㄹ`이 아직 받침으로 붙지 않은 순간이다. `nfd`는 `다`와 `닭가`는 맞혔지만 `ㄷ`과 `달`에서 실패했다. 입력창의 `ㄷ`은 호환용 자모(U+3137)라 NFD가 만드는 초성 부호(U+1103)와 다른 글자이고, `닭`의 받침 `ㄺ`은 NFD에서도 부호 하나라 `ㄹ` 다음에 `ㄱ`이 온다는 정보가 없다. 키보드 순서로 끝까지 푼 `keys`만 모든 순간에 맞았다.

그래서 한글 자동완성은 트라이에 넣을 때와 찾을 때 모두 같은 방식으로 자모를 풀어 쓴다. 트라이 깊이가 세 배쯤 늘지만 사용자가 치는 모든 순간에 추천이 끊기지 않는다. 같은 원리로 초성만 친 `ㄷㄱㅂ`을 `닭갈비`로 찾는 초성 검색은 초성만 뽑은 문자열로 트라이를 하나 더 만든다. 나라와 언어마다 트라이를 따로 두는 이유도 여기에 있다. 정규화 규칙과 인기 검색어가 언어마다 다르다.

## 추천이 이상하다는 문의가 오면

자동완성 문의는 몇 가지로 모인다.

- 추천이 타이핑을 못 따라온다. 서버 응답 시간부터 본다. 트라이 질의는 마이크로초 단위라 서버 처리 시간이 길다면 노드 목록 없이 아래를 뒤지는 코드가 섞였거나, 질의 서버가 트라이를 다시 읽는 중이다. 서버는 빠른데 체감이 느리면 디바운스 대기 시간이 너무 길다.
- 지운 글자의 추천이 화면에 남는다. 늦게 온 응답이 최신 응답을 덮어쓴 것이다. 응답의 접두사와 입력창을 비교하는 코드가 있는지 본다.
- 한글을 칠 때 중간에 추천이 사라졌다 돌아온다. 접두사를 음절 단위로 비교하고 있다. 위 실험의 `달`과 `닭가` 같은 순간이다.
- 사람마다 추천이 다르게 나온다. 질의 서버 일부가 이전 버전의 트라이를 들고 있을 수 있다. 응답 헤더에 트라이 버전을 실어 보내면 바로 확인할 수 있다.

## 트라이로 상위 k개 찾기

트라이를 직접 짜 보자. `entries`는 `[검색어, 횟수]` 배열이고, 같은 검색어가 두 번 나오면 횟수를 더한다. `prefix`로 시작하는 검색어를 횟수가 많은 순으로, 횟수가 같으면 사전순으로 `k`개까지 돌려준다. 먼저 출발 노드 아래를 전부 뒤지는 버전으로 통과시키고, 여유가 있으면 노드마다 목록을 적어 두는 버전으로 바꿔 보자.

## 다음에 읽을 글

질의 쪽은 이렇게 정리된다. 빈도표와 `LIKE`는 접두사는 찾아도 그 안의 순위를 매번 다시 정렬해야 해서 짧은 접두사일수록 비싸다. 트라이는 접두사를 길로 바꿔 출발점을 접두사 길이만큼에 찾고, 노드마다 상위 목록을 적어 두면 질의가 그 목록을 읽는 일로 끝난다. 대신 메모리가 늘고 고치기가 어려워진다. 한글은 자모로 풀어 넣고, 브라우저는 디바운스와 캐시로 요청을 줄이고 늦게 온 응답을 버린다.

남은 질문은 트라이를 어떻게 만들고 바꾸느냐다. 검색 기록을 어디에 모으고, 얼마나 자주 집계하고, 수억 개 검색어의 트라이를 어디에 저장해 여러 서버로 나눌지는 [㉚ 검색어 자동완성 ②](/posts/sd-autocomplete-data-pipeline)에서 이어 간다. 접두사가 아니라 단어 중간이나 오타까지 찾아야 하는 검색은 [역색인](/posts/elasticsearch-inverted-index)의 영역이다. 트라이 자체를 짜고 지우고 Word Search II 같은 면접 문제에 쓰는 이야기는 [트라이 글](/posts/ds-trie)에 있다.

## 면접에서 나올 만한 질문

### 자동완성에 왜 트라이를 쓰나요?

트라이는 문자열을 글자 단위 경로로 저장해서, 접두사의 출발 노드를 접두사 길이만큼만 내려가 찾는다. 데이터 양과 상관없이 출발점을 찾는 비용이 일정하다. DB의 `LIKE 'r%'`는 인덱스로 범위는 찾지만 그 안의 수천 줄을 매번 횟수로 정렬해야 해서, 가장 많이 불리는 짧은 접두사가 가장 비싸다.

### 트라이에서 상위 k개를 빠르게 찾으려면 어떻게 하나요?

노드마다 그 아래에서 가장 많이 찾은 k개를 미리 계산해 적어 둔다. 질의는 접두사 노드까지 내려가 목록을 읽기만 하면 된다. 목록은 아래에서 위로, 자식들의 목록과 자기 자신을 합쳐 다시 k개를 고르는 방식으로 만든다. 측정에서 한 글자 접두사가 61ms에서 0.2µs가 됐다.

### 노드마다 목록을 두면 어떤 대가가 있나요?

메모리가 늘고, 검색어 하나의 횟수가 바뀌면 그 경로의 모든 노드 목록을 다시 계산해야 할 수 있다. 검색이 들어올 때마다 고치면 쓰기 부하가 커지므로 검색 기록을 모아 주기적으로 트라이를 새로 만들어 바꿔 끼운다. 목록에 문자열 대신 ID를 두고, 접두사 길이에 상한을 두어 메모리를 줄인다.

### 한글 자동완성은 무엇이 다른가요?

입력 중에 음절이 바뀌어서 `달`처럼 최종 검색어의 접두사가 아닌 글자가 나타난다. 음절 단위로 비교하면 그 순간 추천이 끊긴다. 트라이에 넣을 때와 찾을 때 모두 키보드 입력 순서의 자모로 풀어 비교하고, 겹받침도 쪼갠다. NFD 정규화만으로는 호환용 자모와 겹받침 때문에 부족하다.

### 글자마다 요청이 가면 서버가 버거울 텐데요?

브라우저에서 디바운스로 입력이 잠깐 멈출 때만 보내고, 같은 접두사의 응답을 `Cache-Control`로 캐시한다. 이전 요청은 취소하고, 늦게 온 응답은 접두사를 비교해 버린다. 서버는 상태 없는 질의 서버를 여러 대 두고 각자 같은 트라이를 메모리에 올려 둔다.

### 부적절한 검색어가 추천에 뜨면 어떻게 하나요?

질의 결과와 응답 사이에 차단 목록으로 거르는 단계를 두어 즉시 지운다. 트라이를 다시 만들 때까지 기다리지 않아도 된다. 거르면 개수가 모자랄 수 있으니 노드에는 보여 줄 개수보다 넉넉히 적어 두고, 트라이 데이터에서는 다음 재생성 때 실제로 지운다.

### 질의 서버 한 대가 죽으면 어떻게 되나요?

모든 질의 서버가 같은 트라이를 들고 있는 상태 없는 서버라, 로드 밸런서가 헬스 체크로 빼고 나머지가 받는다. 새로 뜬 서버는 저장소에서 최신 트라이를 읽어 메모리에 올린 뒤에야 트래픽을 받아야 한다. 트라이가 커서 한 대에 안 들어가면 접두사로 나눈 샤드마다 복제본을 둔다.
