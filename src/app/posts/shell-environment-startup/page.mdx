서버에 백업 도구를 `~/.local/bin`에 깔고 터미널에서 돌려 보니 잘 됐다. 같은 명령을 crontab에 걸었더니 다음 날 아침 메일함에 이런 줄이 와 있었다.

```text
/bin/sh: 1: mytool: not found
```

명령도 사용자도 같은데 결과가 다르다. 차이는 그 명령을 실행한 셸이 들고 있던 환경이다. 실제로 crontab에 `env`를 걸어 cron이 넘겨주는 환경을 통째로 받아 봤다.

```text
HOME=/root
LOGNAME=root
PATH=/usr/bin:/bin
LANG=C.UTF-8
SHELL=/bin/sh
PWD=/root
```

변수가 여섯 개뿐이고 PATH는 `/usr/bin:/bin` 두 칸이다. 내가 작업하던 셸에서 `env | wc -l`을 세어 보니 159개였다. `~/.local/bin`을 PATH에 넣은 건 로그인할 때 읽는 `~/.profile`이었고, cron은 그 파일을 읽지 않는다. 셸은 `/bin/bash`가 아니라 `/bin/sh`(Ubuntu에서는 dash)였다.

이 글은 이 차이를 처음부터 따라간다. 셸 변수와 환경 변수의 차이, 자식 프로세스에 무엇이 넘어가는지, 명령 이름을 파일로 찾는 순서, 셸 종류마다 읽는 시작 파일, 스크립트를 실행하는 세 가지 방법을 실험으로 확인한다. 기준은 Ubuntu 24.04와 bash 5.2이고, 22.04도 같은 파일 구성을 쓴다. 출력은 직접 돌린 결과이고, 긴 실험 폴더 경로는 `~/lab`으로 줄여 적었다. 스크립트 안의 조건문과 함수는 [bash 조건문과 함수 글](/posts/bash-control-flow-functions)에서, 실패를 숨기지 않는 스크립트 설정은 [bash 스크립트 글](/posts/bash-scripting)에서 다룬다.

## 셸 변수와 환경 변수는 사는 곳이 다르다

셸에서 `APP_ENV=prod`라고 쓰면 그 셸 안에만 있는 셸 변수가 생긴다. `export`를 붙여야 환경 변수가 되고, 그때부터 이 셸이 띄우는 프로그램에게 넘어간다.

```bash
APP_ENV=prod
echo "shell: APP_ENV=$APP_ENV"
bash -c 'echo "child: APP_ENV=[$APP_ENV]"'            # 자식 셸에서 읽는다
export APP_ENV
bash -c 'echo "child after export: APP_ENV=[$APP_ENV]"'
```

```text
shell: APP_ENV=prod
child: APP_ENV=[]
child after export: APP_ENV=[prod]
```

두 종류를 구분하는 도구도 다르다. `set`은 셸 변수와 환경 변수를 모두 보여 주고, `env`(또는 `printenv`)는 환경 변수만 보여 준다. `declare -p 이름`은 그 변수가 export됐는지(`-x`)까지 알려 준다.

```bash
FOO=1; export BAR=2
env | grep -E '^(FOO|BAR)='      # 환경 변수만
set | grep -E '^(FOO|BAR)='      # 셸이 가진 변수 전부
declare -p BAR FOO
```

```text
BAR=2
BAR=2
FOO=1
declare -x BAR="2"
declare -- FOO="1"
```

환경 변수는 셸의 기능이 아니라 운영체제의 기능이다. 프로세스마다 "이름=값" 문자열 목록이 하나씩 있고, 새 프로그램을 실행할 때(`execve`) 그 목록을 넘긴다. 파이썬의 `os.environ`, Node의 `process.env`, Go의 `os.Getenv`가 읽는 것이 모두 이 목록이다. 셸 변수는 bash 프로세스 메모리 안에만 있어서 다른 프로그램은 볼 수 없다. 설정 파일 대신 환경 변수로 설정을 주입하는 방식(12-factor의 설정 원칙)이 언어를 가리지 않고 통하는 이유가 이거다.

## 자식은 복사본을 받는다

환경은 부모에서 자식으로 복사된다. 거꾸로는 흐르지 않는다. 자식이 바꾼 값은 부모에게 돌아오지 않고, 자식이 뜬 뒤에 부모가 바꾼 값도 자식에게 닿지 않는다.

```bash
bash -c 'APP_ENV=staging; export APP_ENV; echo "child set: $APP_ENV"'
echo "parent still: $APP_ENV"

LOG_LEVEL=debug bash -c 'echo "one-shot: LOG_LEVEL=[$LOG_LEVEL]"'   # 이 명령에만 준다
echo "after one-shot: LOG_LEVEL=[$LOG_LEVEL]"
```

```text
child set: staging
parent still: prod
one-shot: LOG_LEVEL=[debug]
after one-shot: LOG_LEVEL=[]
```

`이름=값 명령`처럼 명령 앞에 붙여 쓰면 그 명령 하나의 환경에만 들어간다. 현재 셸에는 남지 않는다. `sudo`는 기본적으로 환경을 정리하고 PATH를 `secure_path`로 바꾸니, `FOO=1 sudo cmd`는 `cmd`에 FOO가 닿지 않는다. sudoers 정책이 허락하는 범위에서 `sudo FOO=1 cmd`나 `sudo --preserve-env=FOO cmd`로 넘긴다. Ubuntu 24.04의 `/etc/sudoers`에 있는 값은 이렇다.

```text
Defaults	secure_path="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/snap/bin"
```

실행 중인 프로세스가 어떤 환경을 받았는지는 `/proc/PID/environ`에서 볼 수 있다. 그런데 이 파일은 프로세스가 시작할 때 받은 목록이다. 부모가 나중에 `export`로 바꿔도 이미 뜬 프로세스의 환경은 그대로다.

```bash
export DB_HOST=10.0.0.5
sleep 30 & p=$!
tr '\0' '\n' < /proc/$p/environ | grep DB_HOST     # 항목이 NUL로 나뉘어 있다
export DB_HOST=10.0.0.9                            # 부모에서 바꾼다
tr '\0' '\n' < /proc/$p/environ | grep DB_HOST
```

```text
DB_HOST=10.0.0.5
DB_HOST=10.0.0.5
```

아래 그림에서 단계를 넘기면 값이 언제 복사되고, 어디서 바뀐 것이 어디에 보이지 않는지 따라갈 수 있다.

운영에서 "환경 변수를 바꿨는데 반영이 안 된다"는 말의 대부분이 이 그림이다. 쿠버네티스에서 ConfigMap을 env로 주입했다면 값을 바꿔도 Pod를 다시 띄워야 하는 것도 같은 이유다. 의심스러울 때는 앱의 설정 화면이 아니라 `sudo cat /proc/$(pgrep -o myapp)/environ | tr '\0' '\n'`로 프로세스가 실제로 받은 값을 본다. 이 파일에는 비밀 값도 들어 있어서 같은 사용자나 root만 읽을 수 있다. 환경 변수로 넘긴 비밀이 어디로 새는지는 [비밀 관리 글](/posts/secrets-management)에 정리했다.

빈 환경으로 시작하는 `env -i`는 cron 같은 환경을 재현할 때 쓴다.

```bash
env -i bash --norc --noprofile -c 'echo "PATH=[$PATH] HOME=[$HOME]"; env'
```

```text
PATH=[/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin] HOME=[]
PWD=~/lab
SHLVL=0
_=/usr/bin/env
```

환경이 비어 있어도 bash는 PATH 셸 변수에 컴파일할 때 정한 기본값을 넣는다. 하지만 `env` 출력에 PATH가 없다. export하지 않은 셸 변수라서 bash가 띄우는 자식에게는 넘어가지 않는다는 뜻이다. cron 장애를 재현할 때는 `env -i PATH=/usr/bin:/bin HOME=$HOME /bin/sh -c '명령'`처럼 cron이 주는 값을 그대로 준다.

```bash
env -i HOME=/root LOGNAME=root PATH=/usr/bin:/bin SHELL=/bin/sh /bin/sh -c 'mytool; echo "rc=$?"'
```

```text
/bin/sh: 1: mytool: not found
rc=127
```

## 명령 이름이 파일이 되기까지

`mytool`이라고 쳤을 때 셸이 그 이름을 무엇으로 바꾸는지는 순서가 정해져 있다. 이름에 `/`가 있으면 그 경로를 그대로 실행한다. 없으면 alias, 셸 키워드, 함수, 내장 명령을 먼저 보고, 그래도 없으면 해시 테이블(전에 찾아 둔 경로)을 본 뒤 PATH의 디렉터리를 왼쪽부터 하나씩 찾는다. 처음 찾은 것을 쓰고 멈춘다.

`type`은 이 순서대로 셸이 실제로 무엇을 실행할지 알려 준다. `which`는 외부 프로그램이라 alias, 함수, 내장 명령을 모르고 PATH만 뒤진다.

```bash
alias ll='ls -l'
type ll ls cd echo
which -a echo
```

```text
ll is aliased to `ls -l'
ls is /usr/bin/ls
cd is a shell builtin
echo is a shell builtin
/usr/bin/echo
/bin/echo
```

`which echo`는 `/usr/bin/echo`를 알려 주지만, 셸에서 `echo`를 치면 실행되는 건 내장 명령이다. 두 `echo`는 `-e` 처리 같은 세부 동작이 다르다. 명령이 어디서 오는지 확인할 때는 `type -a`를 쓴다. 스크립트에서 "이 명령이 있나"를 볼 때는 `command -v jq`가 표준이다.

같은 이름이 PATH의 여러 디렉터리에 있으면 앞쪽이 이긴다. `~/.local/bin`을 PATH 맨 앞에 넣는 Ubuntu 기본 `.profile` 덕분에 사용자가 깐 도구가 시스템 도구를 덮을 수 있다. 반대로 말하면, 누가 쓸 수 있는 디렉터리를 PATH 앞에 두면 `ls`나 `sudo`를 가짜로 바꿔치기할 수 있다는 뜻이다. root의 PATH에 `.`이나 남이 쓸 수 있는 디렉터리를 넣지 않는 이유다. PATH 끝에 빈 칸(`PATH="$PATH:"`)이 생겨도 현재 디렉터리를 뜻하게 되니 조심한다.

```bash
deploy.sh                 # 현재 디렉터리에 있지만 PATH에 없다
PATH="$PATH:"; deploy.sh  # 끝의 빈 칸이 현재 디렉터리가 됐다
```

```text
bash: line 1: deploy.sh: command not found
deployed
```

해시 테이블은 PATH를 매번 다 뒤지지 않으려고 bash가 기억해 두는 경로다. 이 기억이 낡으면 이상한 오류가 난다. `bin2`에만 `mytool`이 있던 상태에서 시작해, `bin1`을 앞에 넣고, `bin1`의 파일을 지웠다.

```bash
PATH=~/lab/bin2:$PATH; mytool; hash
PATH=~/lab/bin1:$PATH; mytool; hash   # PATH에 대입하면 해시가 비워진다
rm ~/lab/bin1/mytool
mytool                                # 기억해 둔 경로로 바로 간다
hash -r; mytool                       # 기억을 지우고 다시 찾는다
```

```text
bin2/mytool
hits	command
   1	~/lab/bin2/mytool
bin1/mytool
hits	command
   1	~/lab/bin1/mytool
bash: ~/lab/bin1/mytool: No such file or directory
bin2/mytool
```

`command not found`가 아니라 `No such file or directory`가 났다. bash가 PATH를 다시 찾지 않고 기억해 둔 경로를 실행하려다 실패한 것이다. 패키지를 지우고 다른 경로에 다시 깔았을 때, 또는 `/usr/local/bin`의 도구를 지웠을 때 흔히 본다. `hash -r`로 지우거나 새 셸을 열면 풀린다. 아래 그림은 이 순서를 cron의 PATH와 터미널의 PATH에서 각각 따라간 것이다.

## 로그인 셸과 대화형 셸이 읽는 파일

bash가 시작할 때 읽는 파일은 두 가지 질문으로 정해진다. 로그인 셸인가(ssh 접속, 콘솔 로그인, `bash -l`, `su -`)와 대화형인가(사람이 프롬프트에서 치는가)다. 어느 파일이 언제 읽히는지 알아보려고, 빈 홈 디렉터리에 읽힐 때 한 줄씩 찍는 시작 파일을 두고 여러 방식으로 띄웠다.

```bash
# ~/lab/home/.profile
echo "  read: ~/.profile"
if [ -n "$BASH_VERSION" ] && [ -f "$HOME/.bashrc" ]; then . "$HOME/.bashrc"; fi

# ~/lab/home/.bashrc  (Ubuntu 기본 .bashrc의 첫 줄과 같은 방어문)
case $- in *i*) ;; *) echo "  read: ~/.bashrc (비대화형이라 여기서 return)"; return;; esac
echo "  read: ~/.bashrc"
```

```text
[bash -l -c true]
  read: ~/.profile
  read: ~/.bashrc (비대화형이라 여기서 return)
[bash -i -c true]
  read: ~/.bashrc
[bash -c true]
[bash -l -i -c true]
  read: ~/.profile
  read: ~/.bashrc
[bash script]
```

규칙은 이렇다. 로그인 셸은 `/etc/profile`을 읽고, 홈의 `~/.bash_profile`, `~/.bash_login`, `~/.profile` 중 처음 있는 하나만 읽는다. 로그인이 아닌 대화형 셸은 `~/.bashrc`만 읽는다(Ubuntu는 `/etc/bash.bashrc`도 먼저 읽는다). 스크립트를 돌리는 비대화형 셸은 아무것도 읽지 않는다. `BASH_ENV`에 파일 경로가 있으면 그것만 읽는다.

그래서 Ubuntu의 기본 `~/.profile`은 bash일 때 `~/.bashrc`를 직접 불러 준다. 로그인 셸이 `.bashrc`를 따로 읽지 않으니 손으로 이어 붙인 것이다. 여기서 흔한 사고가 하나 난다. 어떤 설치 안내를 따라 `~/.bash_profile`을 새로 만들었다.

```text
[bash -l -c true]
  read: ~/.bash_profile
[bash -i -c true]
  read: ~/.bashrc
```

`.bash_profile`이 생기자 로그인 셸은 그것만 읽고 `.profile`을 건너뛰었다. `.profile`이 하던 일, 즉 `~/.local/bin`을 PATH에 넣고 `.bashrc`를 부르던 일이 한꺼번에 사라진다. ssh로 들어가면 alias와 프롬프트 색이 없어지고 몇몇 도구를 못 찾는다. `.bash_profile`을 만들어야 한다면 첫 줄에 `[ -f ~/.profile ] && . ~/.profile`을 넣는다.

dash처럼 bash가 아닌 셸은 로그인일 때 `~/.profile`만 읽는다. `sh -l -c true`는 `read: ~/.profile` 한 줄을 찍었다. bash 전용 문법은 `.profile`에 넣지 말고 `.bashrc`에 둔다.

## .bashrc에 넣을 것과 .profile에 넣을 것

두 파일의 역할을 나누면 대부분의 혼란이 정리된다. `~/.profile`에는 로그인할 때 한 번 정하면 되는 것, 그리고 자식에게 물려줘야 하는 것을 둔다. PATH, `EDITOR`, `LANG` 같은 환경 변수다. `~/.bashrc`에는 사람이 프롬프트를 쓸 때만 필요한 것을 둔다. alias, 함수, 프롬프트(`PS1`), 히스토리 설정, 탭 완성이다.

`.bashrc` 맨 위의 `case $- in *i*)` 방어문도 지운다면 문제가 생긴다. `$-`에 `i`가 없으면 비대화형이니 바로 돌아가라는 줄이다. 이 줄이 없으면 `scp`나 `rsync`처럼 ssh로 원격 명령을 돌리는 도구가 `.bashrc`의 `echo` 출력을 받아 프로토콜이 깨진다. bash 매뉴얼은 원격 셸 데몬이 띄운 비대화형 bash도 `.bashrc`를 읽는다고 적고 있어서, 이 방어문이 그 경우를 막아 준다.

PATH를 `.bashrc`에서 `PATH=$PATH:~/bin`처럼 늘리면, 셸 안에서 셸을 열 때마다 같은 디렉터리가 계속 붙는다. 터미널 안에서 `bash`를 몇 번 열고 나면 PATH가 길어진다. `.profile`에서 한 번만 하거나, 이미 있는지 확인하고 붙인다.

```bash
case ":$PATH:" in
  *":$HOME/.local/bin:"*) ;;                 # 이미 있으면 그냥 둔다
  *) PATH="$HOME/.local/bin:$PATH" ;;
esac
export PATH
```

`.bashrc`나 `.profile`을 고친 뒤에는 이미 열린 셸에 반영되지 않는다. 새 셸을 열거나 `source ~/.bashrc`로 현재 셸에서 다시 읽는다. ssh 세션이 여러 개 열려 있다면 각각 따로다. 시스템 전체에 주는 값은 `/etc/profile.d/*.sh`에 파일 하나로 넣는 것이 관례다. `/etc/profile`이 그 디렉터리의 파일을 모두 읽는다. `/etc/environment`는 셸 문법이 아니라 `이름=값` 줄만 받는 파일이고, 셸이 아니라 PAM이 로그인할 때 읽는다.

## alias는 사람을 위한 것이다

alias는 명령 줄의 첫 단어를 다른 글자로 바꿔 끼우는 기능이다. 대화형 셸에서만 펼쳐진다. 스크립트 안에서 alias를 정의하고 써도 동작하지 않는다.

```bash
#!/bin/bash
alias ll="ls -alF"
ll -d .
```

```text
al.sh: line 3: ll: command not found
rc=127
```

`shopt -s expand_aliases`를 켜면 스크립트에서도 펼쳐지지만, 줄을 읽는 시점에 바꿔 끼우는 방식이라 같은 줄이나 같은 함수 안에서 정의한 alias는 여전히 안 먹는다. 스크립트에서 이름을 줄여 쓰고 싶다면 함수를 쓴다. 함수는 인자를 받고(`"$@"`), 조건문을 쓸 수 있고, 어디서나 동작한다.

```bash
ll() { ls -alF "$@"; }   # alias보다 함수가 낫다
```

alias가 진짜 명령을 가리는 일도 있다. Ubuntu 기본 `.bashrc`는 `grep`에 `--color=auto`를 붙여 두고, 어떤 서버는 `rm='rm -i'`를 alias로 걸어 둔다. 터미널에서 `rm`이 매번 확인을 묻다 보니 그게 기본이라고 믿게 되고, 스크립트나 다른 서버에서는 묻지 않고 지운다. alias를 건너뛰고 원래 명령을 부를 때는 `\rm`이나 `command rm`을 쓴다. `command`는 함수도 건너뛴다.

## 스크립트를 실행하는 세 가지 방법

같은 스크립트도 `./setenv.sh`, `bash setenv.sh`, `source setenv.sh`로 부를 때 결과가 다르다. 환경 변수를 정하고 디렉터리를 옮기는 스크립트로 비교했다.

```bash
#!/bin/bash
# setenv.sh
export APP_ENV=staging
cd /tmp
echo "  in script: pid=$$ ppid=$PPID APP_ENV=$APP_ENV pwd=$PWD"
```

```text
caller: pid=11044 pwd=proj
bash: line 2: ./setenv.sh: Permission denied
rc=126
  in script: pid=11048 ppid=11044 APP_ENV=staging pwd=/tmp
after ./     : APP_ENV=[] pwd=proj
  in script: pid=11049 ppid=11044 APP_ENV=staging pwd=/tmp
after bash   : APP_ENV=[] pwd=proj
  in script: pid=11044 ppid=11039 APP_ENV=staging pwd=/tmp
after source : APP_ENV=[staging] pwd=tmp
```

첫 줄은 실행 권한 없이 `./setenv.sh`를 부른 결과다. 126은 "찾았지만 실행할 수 없다"는 뜻이다. `chmod +x`를 하고 나면 `./`와 `bash`는 모두 새 프로세스(pid 11048, 11049)에서 돈다. 스크립트 안의 `export`와 `cd`는 그 프로세스와 함께 사라지고, 부르는 쪽 셸은 그대로다. `source`(또는 `.`)는 새 프로세스를 만들지 않고 현재 셸(pid 11044)에서 파일의 줄을 그대로 실행한다. 그래서 환경과 현재 디렉터리가 바뀐 채로 남는다.

차이를 정리하면 이렇다. `./script`는 커널이 파일 첫 줄의 shebang을 보고 해석기를 고르며, 실행 권한이 필요하다. `bash script`는 해석기를 내가 정하고 파일은 읽기 권한만 있으면 된다(shebang은 주석으로 무시된다). `source script`는 현재 셸에서 돌고, 그 셸의 변수와 함수를 바꿀 수 있다. `.env` 파일을 읽거나 `venv/bin/activate`처럼 현재 셸을 바꾸는 게 목적인 파일은 `source`로 부르고, 나머지 스크립트는 새 프로세스로 돌린다. `source`로 부른 파일 안의 `exit`은 내 터미널을 닫는다.

`source`로 비밀 값이 든 `.env`를 읽을 때도 조심한다. 셸 문법으로 실행되는 것이라, 값에 `$(...)`가 들어 있으면 명령이 실행된다. 남이 쓸 수 있는 파일을 `source`하는 건 그 사람에게 내 셸을 넘기는 것과 같다.

## shebang과 실행 권한

`./script`를 실행하면 커널은 파일 첫 두 바이트가 `#!`인지 본다. 맞으면 그 뒤의 경로를 해석기로 실행하고 스크립트 경로를 인자로 넘긴다. `#!/usr/bin/env python3`처럼 `env`를 쓰면 PATH에서 해석기를 찾는다. 가상 환경이나 nvm처럼 해석기 위치가 사람마다 다를 때 쓴다. 대신 cron처럼 PATH가 짧은 곳에서는 찾지 못할 수 있고, 리눅스에서 shebang 줄은 인자를 하나로 묶어 넘기기 때문에 `#!/usr/bin/env python3 -u`처럼 옵션을 붙이면 깨진다(coreutils 8.30부터 `env -S`로 나눌 수 있다).

shebang이 없으면 누가 해석할지 정해지지 않는다. bash에서 실행하면 bash가 스스로 읽어 돌리고, 다른 셸이나 프로그램에서 실행하면 그쪽 기본 셸이 돈다. Ubuntu의 `/bin/sh`는 dash다.

```bash
# nosheb.sh: shebang 없이 bash 문법을 쓴 파일
echo "array: ${BASH_VERSION:-not bash}"
[[ 1 == 1 ]] && echo double-bracket ok
```

```text
array: 5.2.21(1)-release
double-bracket ok
array: not bash
./nosheb.sh: 2: [[: not found
```

위 두 줄은 bash에서 `./nosheb.sh`를 부른 결과, 아래 두 줄은 `sh ./nosheb.sh`로 부른 결과다. cron이 명령 줄을 `/bin/sh`로 돌리니, crontab에 `bash` 없이 스크립트를 적었는데 shebang마저 없으면 dash가 bash 문법을 만나 깨진다. 스크립트 첫 줄에는 늘 `#!/bin/bash`(또는 `#!/usr/bin/env bash`)를 쓴다.

윈도에서 저장한 스크립트는 첫 줄이 `#!/bin/bash\r`이 된다. 커널은 `bash\r`이라는 해석기를 찾는다.

```bash
./crlf.sh; echo "rc=$?"
file crlf.sh
```

```text
bash: line 1: ./crlf.sh: cannot execute: required file not found
rc=127
crlf.sh: Bourne-Again shell script, ASCII text executable, with CRLF line terminators
```

파일은 분명히 있는데 "required file not found"다. 없는 건 스크립트가 아니라 해석기 `/bin/bash\r`이다. `file`이 `CRLF line terminators`를 알려 주고, `sed -i 's/\r$//' crlf.sh`나 `dos2unix`로 고친다. 저장소에 `.gitattributes`로 `*.sh text eol=lf`를 걸어 두면 다시 생기지 않는다.

`noexec`로 마운트된 디렉터리(보안 설정으로 `/tmp`를 이렇게 두는 서버가 있다)에서는 실행 권한이 있어도 `./script`가 Permission denied로 실패한다. `bash script`는 bash가 파일을 읽기만 하니 돈다. 실행 비트와 마운트 옵션이 어떻게 겹쳐 판정되는지는 [파일 권한 글](/posts/linux-files-permissions)에 있다.

## cron과 systemd에는 내 셸이 없다

처음 장면으로 돌아가면 고치는 방법이 몇 가지 있다. 어느 쪽이든 원칙은 같다. 사람의 시작 파일에 기대지 말고, 실행되는 곳에서 필요한 환경을 직접 밝힌다.

```bash
# crontab -e
SHELL=/bin/bash
PATH=/home/me/.local/bin:/usr/local/bin:/usr/bin:/bin
MAILTO=ops@example.com
15 3 * * * /home/me/.local/bin/mytool --backup >> /var/log/mytool.log 2>&1
```

crontab 맨 위에 `PATH=`와 `SHELL=`을 적을 수 있다. 여기는 셸이 아니라 cron이 읽는 줄이라 `$PATH`나 `~` 같은 확장이 되지 않는다. 경로를 글자 그대로 적는다. 명령은 절대 경로로 쓰는 게 가장 확실하다. 스크립트 안에서 `source ~/.profile`로 사람의 환경을 끌어오는 방법도 있지만, `.profile`이 바뀔 때마다 배치가 같이 흔들린다. 언제 돌릴지, 겹치는 실행은 어떻게 막는지는 [크론 잡 글](/posts/cron-jobs)에서 다룬다.

systemd 서비스는 셸을 거치지 않고 직접 프로그램을 띄운다. `.bashrc`도 `.profile`도 읽지 않는다. 기본 PATH에는 `/usr/local/bin`, `/usr/bin` 같은 시스템 경로만 들어 있어서 nvm이나 pyenv가 깐 해석기는 보이지 않는다. 필요한 값은 유닛 파일에 적는다.

```ini
[Service]
Environment=APP_ENV=prod
EnvironmentFile=/etc/myapp/env
ExecStart=/opt/myapp/bin/server
```

`EnvironmentFile`의 줄도 셸 문법이 아니라 `이름=값`만 받는다. 서비스가 실제로 받은 환경은 `systemctl show myapp -p Environment`로, 실행 중인 프로세스는 위에서 본 `/proc/PID/environ`으로 확인한다. 유닛 파일을 쓰는 법은 [systemd 글](/posts/linux-systemd-systemctl)에 있다. 도커 컨테이너도 마찬가지로, 이미지의 `ENV`와 실행할 때 넘긴 `-e`만 들고 시작한다.

## 손에 익혀 두면 좋은 것들

여기서부터는 셸을 매일 쓰는 사람의 습관에 가깝다. 몇 가지만 적는다.

히스토리는 `history`로 보고, `Ctrl+R`로 거꾸로 검색한다. `!!`는 바로 앞 명령, `!$`는 앞 명령의 마지막 인자다. `sudo !!`는 권한 없이 친 명령을 다시 sudo로 친다. Ubuntu 기본 `.bashrc`는 `HISTCONTROL=ignoreboth`라서 공백으로 시작한 명령은 히스토리에 남지 않는다. 비밀번호가 든 명령을 꼭 쳐야 한다면 앞에 공백을 하나 둔다. 다만 셸 히스토리에서만 빠질 뿐 `ps`나 감사 로그에는 남는다. 히스토리 파일(`~/.bash_history`)은 셸이 끝날 때 쓰이기 때문에, 터미널 여러 개를 쓰면 마지막에 닫은 것이 앞의 기록을 덮는다. `shopt -s histappend`가 기본 `.bashrc`에 들어 있는 이유다.

탭 완성은 bash-completion 패키지가 명령마다 규칙을 더해 준다. `git checkout <Tab>`이 브랜치 이름을 보여 주는 것이 이 덕분이다. 기본 `.bashrc`가 `/usr/share/bash-completion/bash_completion`을 읽는데, 이게 대화형 셸에서만 도는 이유도 위와 같다. 최소 설치 이미지에는 패키지가 빠져 있어 `sudo apt install bash-completion`을 따로 해야 하기도 한다.

도움말은 명령 종류에 따라 찾는 곳이 다르다. 내장 명령은 `help cd`, `help read`로 본다. `man cd`는 없거나 엉뚱한 페이지가 나온다. 외부 명령은 `man ls`, 짧게는 `ls --help`다. 이름이 기억나지 않으면 `man -k 키워드`(apropos)로 찾는다. Ubuntu 컨테이너 이미지처럼 최소화된 시스템은 man 페이지를 지워 두었으니 `unminimize`를 돌리거나 `--help`에 기댄다. 무엇인지부터 모를 때는 `type 이름`이 첫 단계다.

## 다시 cron 앞에서

`mytool: not found`는 cron이 내 `.profile`을 읽지 않아서 생긴 일이었다. 환경 변수는 export한 것만, 실행하는 순간의 사본으로, 부모에서 자식으로만 흐른다. 시작 파일은 로그인 여부와 대화형 여부에 따라 골라 읽히고, cron과 systemd와 컨테이너는 그 어느 쪽도 아니다. 그러니 사람이 쓰는 셸의 편의는 `.bashrc`에, 물려줄 환경은 `.profile`에, 자동으로 도는 작업의 환경은 그 작업의 설정(crontab, 유닛 파일, 이미지)에 적는다. 무엇이 실행될지 헷갈리면 `type -a`, 무엇을 받았는지 헷갈리면 `/proc/PID/environ`을 본다.

## 면접에서 나올 만한 질문

### 셸 변수와 환경 변수는 어떻게 다른가요?

셸 변수는 bash 프로세스 메모리 안에만 있고, `export`한 변수만 환경 변수가 되어 그 셸이 띄우는 프로그램에 넘어간다. 환경 변수는 운영체제가 프로세스마다 들고 있는 "이름=값" 목록이라 언어와 상관없이 `process.env`나 `os.environ`으로 읽힌다. `set`은 둘 다, `env`는 환경 변수만 보여 준다.

### 자식 프로세스에서 바꾼 환경 변수가 부모에게 보이나요?

보이지 않는다. 환경은 프로그램을 실행하는 순간 부모의 사본이 자식에게 복사되고, 그 뒤로는 각자 따로다. 부모가 나중에 바꾼 값도 이미 뜬 자식에게는 닿지 않아서, 설정을 바꾸면 프로세스를 재시작해야 한다. 실제로 받은 값은 `/proc/PID/environ`으로 확인한다.

### 터미널에서는 되는 명령이 cron에서 command not found가 나는 이유는요?

cron은 로그인 셸이 아니라서 `.profile`이나 `.bashrc`를 읽지 않고, PATH를 `/usr/bin:/bin`처럼 짧게 준 채 `/bin/sh`로 명령을 돌리기 때문이다. `~/.local/bin`이나 `/usr/local/bin`의 도구를 못 찾는다. crontab 맨 위에 `PATH=`를 적거나 절대 경로를 쓰고, `env -i PATH=/usr/bin:/bin sh -c '명령'`으로 같은 환경을 재현해 확인한다.

### .bashrc와 .profile(.bash_profile)은 언제 읽히나요?

로그인 셸은 `/etc/profile`과 `~/.bash_profile`, `~/.bash_login`, `~/.profile` 중 처음 있는 하나를 읽고, 로그인이 아닌 대화형 셸은 `~/.bashrc`를 읽는다. 스크립트를 돌리는 비대화형 셸은 둘 다 읽지 않는다. 그래서 Ubuntu의 `.profile`은 `.bashrc`를 직접 불러 주고, `.bash_profile`을 새로 만들면 `.profile`이 무시되는 사고가 난다.

### ./script.sh, bash script.sh, source script.sh의 차이는요?

앞의 둘은 새 프로세스에서 돌아서 스크립트 안의 `export`와 `cd`가 부르는 셸에 남지 않는다. `./`는 실행 권한과 shebang이 필요하고, `bash script`는 해석기를 내가 정하니 읽기 권한만 있으면 된다. `source`는 현재 셸에서 줄을 그대로 실행해 환경과 디렉터리를 바꾼다. 가상 환경 활성화처럼 현재 셸을 바꾸는 파일에만 쓰고, 그 안의 `exit`은 내 셸을 닫는다.

### which와 type은 어떻게 다른가요?

`which`는 외부 프로그램이라 PATH만 뒤지고, alias와 함수와 내장 명령을 모른다. `type`은 bash 내장이라 셸이 실제로 실행할 것을 alias, 함수, 내장, hash, PATH 순서대로 알려 준다. `which echo`는 `/usr/bin/echo`를 말하지만 실제로는 내장 `echo`가 돈다. 스크립트에서 명령이 있는지 볼 때는 `command -v`를 쓴다.

### 지운 프로그램을 부르니 No such file or directory가 나는 이유는요?

bash가 전에 찾은 경로를 해시 테이블에 기억해 두고 PATH를 다시 뒤지지 않기 때문이다. 기억한 경로의 파일이 사라지면 `command not found` 대신 그 경로로 실행하다 실패한다. `hash -r`로 비우거나 새 셸을 열면 되고, PATH에 대입하면 bash가 해시를 자동으로 비운다.

### PATH에 현재 디렉터리를 넣으면 왜 위험한가요?

현재 디렉터리나 남이 쓸 수 있는 디렉터리가 PATH 앞쪽에 있으면, 그곳에 `ls`나 `sudo` 같은 이름의 파일을 두는 것만으로 내가 치는 명령을 바꿔치기할 수 있다. 특히 root의 PATH에서 위험하다. PATH 끝의 빈 칸(`PATH=$PATH:`)도 현재 디렉터리를 뜻하니, 현재 디렉터리의 스크립트는 `./script`로 명시해서 부른다.
