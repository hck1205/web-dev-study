<EasyIntro>
  서버 디스크가 통째로 사라지면 곧바로 두 질문이 나온다. 몇 분어치 데이터를 잃었나, 언제 다시 일을 받을 수 있나. 백업이 있다는 사실만으로는 둘 다 답할 수 없어서, 미리 숫자로 목표를 정해 두고 그 숫자를 지키는 준비를 한다.

  게임을 하다 갑자기 컴퓨터가 꺼진 상황과 같다. 마지막으로 저장한 뒤에 한 플레이는 사라지는데, 이 잃어도 되는 양이 RPO다. 다시 게임을 켜고 저장 파일을 불러와 이어 하기까지 걸리는 시간이 RTO다. 자주 저장할수록 잃는 양이 줄고, 다른 컴퓨터에 게임을 미리 켜 두고 저장 파일을 계속 보내 두면 다시 시작하는 시간이 준다. 미리 켜 두는 범위가 넓을수록 빨리 돌아오지만 그만큼 돈이 든다.

  그래서 모든 서비스에 같은 수준을 주지 않고, 멈췄을 때 손해가 큰 곳부터 높은 수준을 준다. 그리고 실제로 되살리는 훈련을 해 보아야, 사라진 곳에만 있던 열쇠나 비밀번호처럼 문서에 빠진 것을 사고 전에 찾을 수 있다.
</EasyIntro>

DB 서버의 디스크가 통째로 사라졌다고 하자. 다행히 매일 밤 뜬 백업이 있고, WAL도 다른 곳에 모으고 있었다. 그런데 회의실에서 바로 두 가지 질문이 나온다. "몇 분어치 주문을 잃었나?", "언제 다시 주문을 받을 수 있나?" 백업이 있다는 사실만으로는 둘 다 답할 수 없다.

이 글은 그 두 질문에 숫자로 답하는 법을 다룬다. 잃어도 되는 데이터의 양이 RPO(Recovery Point Objective), 멈춰 있어도 되는 시간이 RTO(Recovery Time Objective)다. 직접 PostgreSQL 클러스터 하나를 만들어 0.2초마다 주문을 넣다가 데이터 디렉터리를 지워 버리고, 실제로 몇 건을 잃었는지, 복원에 몇 초가 걸렸는지 잰다. 그다음 그 숫자를 줄이려면 무엇을 얼마나 사야 하는지, 즉 재해 복구(DR, Disaster Recovery) 구성의 네 단계와 비용을 본다.

이 주제의 다른 글: 백업을 몇 벌, 어디에, 얼마나 두는지는 [백업 전략](/posts/backup-strategy), 살아 있는 복제본으로 넘기는 과정은 [장애 조치](/posts/failover), 리전 두 곳 이상을 함께 쓰는 설계는 [멀티 리전](/posts/multi-region)에서 다룬다. PITR(시점 복구)의 설정 하나하나는 [PostgreSQL 운영](/posts/postgres-operations) 글에 있으니 여기서는 숫자를 재는 데 집중한다.

실습 환경은 Ubuntu 24.04, PostgreSQL 16.15다. 공용 클러스터는 건드리지 않고 `initdb`로 만든 실험용 클러스터를 따로 띄웠다.

## 디스크가 사라진 날 잃은 39건

먼저 사고를 그대로 만든다. 클러스터 하나를 띄우고 WAL 보관을 켠다. `archive_timeout = 15s`는 쓰기가 적어도 15초마다 WAL 파일을 넘겨 보관하라는 뜻이다.

```bash
# 실험용 클러스터 (포트 55181, 공용 클러스터와 무관)
sudo -u postgres /usr/lib/postgresql/16/bin/initdb -D /var/tmp/v18pg/a -U postgres --auth=trust

# 보관 설정을 덧붙인다
cat <<'C' | sudo tee -a /var/tmp/v18pg/a/postgresql.conf
port = 55181
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /var/tmp/v18pg/archive/%f && cp %p /var/tmp/v18pg/archive/%f'
archive_timeout = 15s
C

# 띄우고, 테이블을 만들고, 베이스 백업을 뜬다
sudo -u postgres /usr/lib/postgresql/16/bin/pg_ctl -D /var/tmp/v18pg/a -l /var/tmp/v18pg/a.log -w start
psql -h 127.0.0.1 -p 55181 -U postgres -c "CREATE TABLE orders (id bigserial PRIMARY KEY, amount int, created_at timestamptz DEFAULT clock_timestamp())"
sudo -u postgres pg_basebackup -h 127.0.0.1 -p 55181 -U postgres -D /var/tmp/v18pg/base -Xstream -c fast
```

이제 0.2초마다 주문을 하나씩 넣고, 클라이언트가 성공 응답을 받은 주문 번호와 시각을 파일에 남긴다. 40초 뒤 서버를 `kill -9`로 죽이고 데이터 디렉터리를 지운다. 디스크가 날아간 상황이다.

```bash
# 0.2초마다 주문 하나, 커밋된 id와 시각을 기록
for i in $(seq 1 250); do
  psql -h 127.0.0.1 -p 55181 -U postgres -XqAtc \
    "INSERT INTO orders(amount) VALUES ($i) RETURNING id, to_char(created_at,'HH24:MI:SS.MS')"
  sleep 0.2
done > writer.log &

sleep 40
echo "crash at $(date +%T.%3N)"
sudo kill -9 $(sudo head -1 /var/tmp/v18pg/a/postmaster.pid)   # 서버가 죽고
sudo rm -rf /var/tmp/v18pg/a                                    # 디스크도 사라졌다

tail -1 writer.log                                              # 클라이언트가 마지막으로 성공한 주문
ls -l --time-style=+%T.%3N /var/tmp/v18pg/archive               # 바깥에 나가 있던 WAL
```


클라이언트는 153번 주문까지 성공 응답을 받았다. 보관소에 마지막으로 도착한 WAL은 20:31:18.398의 파일이고, 사고는 그로부터 10초 뒤에 났다. 베이스 백업과 보관된 WAL로 되살려 본다.

```bash
# 백업을 새 디렉터리로 복사하고, 보관소에서 WAL을 가져오게 한다
sudo cp -a /var/tmp/v18pg/base /var/tmp/v18pg/a2
echo "archive_mode = 'off'" | sudo tee -a /var/tmp/v18pg/a2/postgresql.auto.conf
echo "restore_command = 'cp /var/tmp/v18pg/archive/%f %p'" | sudo tee -a /var/tmp/v18pg/a2/postgresql.auto.conf
sudo -u postgres touch /var/tmp/v18pg/a2/recovery.signal      # 복구 모드로 시작하라는 표시
sudo -u postgres /usr/lib/postgresql/16/bin/pg_ctl -D /var/tmp/v18pg/a2 -l /var/tmp/v18pg/a2.log -w start

psql -h 127.0.0.1 -p 55181 -U postgres -XAc "SELECT count(*), max(id), max(created_at)::time(3) FROM orders"
```

114건이 돌아왔다. 클라이언트에게 "주문 완료"라고 답한 153건 중 39건, 시간으로 20:31:18.301부터 20:31:28.418까지 약 10.1초가 사라졌다. 이 실험에서 RPO의 실측값이 10.1초다. 15초로 잡은 `archive_timeout`보다 작은 건 사고가 마침 다음 보관 5초 전에 났기 때문이다. 최악이라면 15초에 가깝게 잃는다.

## 얼마나 잃고 얼마나 멈추나

RPO와 RTO는 둘 다 사고 순간을 기준으로 잰다. RPO는 사고 순간에서 과거 쪽으로, 마지막으로 안전한 곳에 기록된 시점까지의 거리다. RTO는 사고 순간에서 미래 쪽으로, 서비스가 다시 정상으로 돌아올 때까지의 거리다. 위 실험이라면 RPO는 10.1초였고, RTO는 사고를 알아채고 복원을 시작해 쓰기를 다시 받을 때까지다.

둘 다 이름에 목표(Objective)가 붙어 있다. "결제는 1분 이상 잃으면 안 되고 30분 안에 돌아와야 한다"처럼 사업 쪽과 미리 정해 두는 약속이다. 장애가 난 뒤 실제로 잰 값은 RPA, RTA(Actual)처럼 따로 부르기도 한다. 목표가 있어야 그 목표를 지키는 구성과 비용이 정해진다.

RPO는 "데이터를 얼마나 자주, 얼마나 빨리 바깥으로 내보내나"가 정한다. RTO는 "사고를 얼마나 빨리 알아채고, 되살리는 단계가 몇 개고, 각각 얼마나 걸리나"가 정한다. 둘은 서로 다른 장치로 줄인다. 백업을 더 자주 떠도 RTO는 그대로일 수 있고, 대기 서버를 둬도 RPO는 그대로일 수 있다.

## 마지막으로 바깥에 나간 기록이 RPO를 정한다

같은 실험을 `archive_timeout = 60s`로 바꿔서 한 번 더 했다. 이번에는 30초 동안 117건을 넣고 사고를 냈다.

```bash
# 보관된 WAL만으로 복원한 결과
psql -h 127.0.0.1 -p 55181 -U postgres -XAc "SELECT count(*), max(created_at)::time(3) AS last_order FROM orders"
```

```text
count|last_order
0|
(1 row)
```

0건이다. 30초 동안 쓴 WAL이 16MB를 채우지 못했고 60초도 지나지 않아서, 그 파일은 한 번도 보관소로 나가지 못했다. 쓰기가 적은 서비스일수록 WAL 파일이 늦게 차니 `archive_timeout`이 곧 최악의 RPO다. 반대로 쓰기가 많으면 파일이 금방 찬다. pgbench로 8개 연결을 60초 돌렸을 때 WAL이 880MB 쌓였다. 초당 14.7MB, 16MB 파일 하나가 1.1초 만에 찬다. 이때는 `archive_timeout`이 거의 의미가 없다.

이 틈을 메우는 방법은 WAL을 파일이 다 찰 때까지 기다리지 않고 바이트 단위로 바로 받아 두는 것이다. 다른 서버에서 `pg_receivewal`을 띄워 두면 복제 프로토콜로 WAL을 실시간으로 받는다.

```bash
# 다른 서버(여기서는 다른 디렉터리)에서 WAL을 실시간으로 받는다
sudo -u postgres pg_receivewal -h 127.0.0.1 -p 55181 -U postgres -D /var/tmp/v18pg/stream --synchronous -n &

# 사고 뒤: 받던 중인 파일은 .partial로 남는다
ls -l --time-style=+%T /var/tmp/v18pg/stream
```

```text
-rw------- 1 postgres postgres 16777216 20:33:08 000000010000000000000003.partial
```

```bash
# .partial의 꼬리표를 떼서 보관된 WAL과 합치고 복원한다
cp archive/0* merged/ && cp stream/000000010000000000000003.partial merged/000000010000000000000003
# restore_command = 'cp /var/tmp/v18pg/merged/%f %p' 로 복원한 뒤
psql -h 127.0.0.1 -p 55181 -U postgres -XAc "SELECT count(*), max(created_at)::time(3) AS last_order FROM orders"
```

```text
count|last_order
117|20:33:08.497
(1 row)
LOG:  last completed transaction was at log time 2026-10-20 20:33:08.497672+00
```

117건이 모두 돌아왔다. 클라이언트가 마지막으로 성공 응답을 받은 주문이 20:33:08.497이었으니 이 실험에서는 하나도 잃지 않았다. 다만 `pg_receivewal`은 커밋을 기다려 주지 않는다. 프라이머리는 커밋을 끝내고 응답한 뒤 WAL을 보내니, 운이 나쁘면 마지막 몇 밀리초는 여전히 잃는다. 0을 보장하려면 커밋이 다른 곳의 기록을 기다리게 하는 동기 복제가 필요하고, 그 대가는 [장애 조치](/posts/failover)와 [멀티 리전](/posts/multi-region) 글에서 잰다.

세 경우의 최악 RPO를 직접 계산해 보자. 베이스 백업만 있으면 백업 주기가, WAL 보관이면 파일이 넘어가는 간격과 옮기는 시간이, 실시간 수신이면 그 지연이 RPO다.

// stream : lagS (실시간 수신 지연)

function worstCaseRpo(plan) {
  return 0;
}`}
  solution={`function worstCaseRpo(plan) {
  const round = (x) => Math.round(x * 10) / 10;
  if (plan.mode === "backup") return round(plan.backupEveryH * 3600);
  if (plan.mode === "stream") return round(plan.lagS);
  // archive: 파일이 다 차거나 archive_timeout이 되는 것 중 먼저 오는 쪽
  const fill = 16 / plan.walMBps;
  const switchEvery = plan.archiveTimeoutS > 0 ? Math.min(plan.archiveTimeoutS, fill) : fill;
  return round(switchEvery + plan.shipDelayS);
}`}

세 번째 경우가 흔한 실수다. `archive_timeout`을 기본값(0, 꺼짐)으로 두면 한가한 밤에는 WAL 파일 하나가 차는 데 몇 분, 어떤 서비스는 몇 시간이 걸린다. 그동안의 데이터는 서버 디스크에만 있다. 그렇다고 너무 작게(몇 초) 잡으면 거의 빈 16MB 파일이 계속 쌓여 보관소 용량을 먹는다. 보통 1분 안팎에서 정하고, 더 줄여야 하면 실시간 수신이나 복제를 쓴다.

## RTO는 복원 단계를 더한 값이다

60초 분량의 쓰기를 9.51초에 재생했다. 같은 부하가 계속된다고 치면 백업 뒤 1시간이 지난 시점의 사고는 재생만 약 9.5분, 6시간이면 57분, 24시간이면 3시간 48분이다. 베이스 백업을 하루 한 번 뜨면 최악의 경우 그날 하루치 WAL을 다 재생해야 한다는 뜻이다. 복사 속도도 같은 식으로 본다. 이 실험의 로컬 복사는 초당 약 101MB였고, 1TB라면 약 173분이다. 이 숫자들은 로컬 SSD와 페이지 캐시 위에서 잰 값이라 실제 객체 저장소에서 내려받으면 더 느리다. 그래서 자기 환경에서 한 번은 직접 재 봐야 한다.

RTO를 줄이는 방향은 단계마다 다르다. 재생을 줄이려면 베이스 백업을 더 자주 뜬다. 복사를 줄이려면 증분 백업이나 디스크 스냅숏을 쓴다. 서버 준비와 복사를 아예 없애려면 이미 데이터를 받고 있는 대기 서버를 둔다. 이게 다음 절의 DR 단계다.

## 네 단계의 DR 구성

"다른 곳에 무엇을 얼마나 미리 켜 두나"에 따라 DR 구성을 보통 네 단계로 나눈다. 아래로 갈수록 RPO와 RTO가 줄고 비용이 늘어난다. AWS의 DR 백서가 쓰는 이름이 널리 쓰여서 그대로 옮겼다.

| 단계 | 대기 쪽에 있는 것 | RPO (대략) | RTO (대략) | 비용 |
|---|---|---|---|---|
| 백업 후 복원 | 백업과 WAL만 | 백업 주기 ~ 수 분 | 수 시간 | 저장 비용만 |
| 파일럿 라이트 | DB 복제본은 켜 둠, 앱 서버는 꺼 둠 | 수 초 ~ 수 분 | 수십 분 | DB 한 벌 |
| 웜 스탠바이 | 전체가 작은 규모로 켜져 있음 | 수 초 | 수 분 | 작은 운영 환경 한 벌 |
| 액티브-액티브 | 양쪽이 모두 트래픽을 받음 | 0 ~ 수 초 | 거의 0 | 운영 환경 두 벌 이상 |

## 비용과 RTO를 함께 놓고 고르기

어느 단계를 고를지는 "한 시간 멈추면 얼마를 잃나"와 "한 단계 올리면 한 달에 얼마가 드나"를 나란히 놓고 정한다. 아래 숫자는 설명을 위한 가정이다. 주문 서비스가 시간당 3천만 원의 매출을 내고, 리전 전체 장애는 1년에 한 번쯤 난다고 하자.

```text
가정: 시간당 매출 3,000만 원, 리전 장애 연 1회

단계            예상 RTO   장애 1회 손실   연간 추가 비용(가정)
백업 후 복원     4시간       1억 2,000만 원    1,200만 원  (저장소)
파일럿 라이트    40분          2,000만 원    6,000만 원  (DB 한 벌)
웜 스탠바이      10분            500만 원  1억 5,000만 원 (작은 환경)
액티브-액티브     1분 미만         50만 원  4억 원 이상 (두 벌 + 충돌 처리)
```

이 가정이라면 파일럿 라이트까지는 남는 장사다. 웜 스탠바이로 올리면 연 9천만 원을 더 내고 1,500만 원을 아낀다. 그런데 매출 손실만 있는 게 아니다. 결제처럼 멈추면 신뢰를 잃는 서비스, 규제로 복구 시간이 정해진 서비스(금융권은 감독 규정으로 핵심 시스템의 목표 복구 시간을 두는 경우가 많다)는 계산이 달라진다. 반대로 사내 리포트 시스템은 하루 멈춰도 괜찮을 수 있다.

그래서 서비스 전체에 한 단계를 고르지 않는다. 결제와 주문은 웜 스탠바이, 상품 검색은 파일럿 라이트, 추천과 리포트는 백업 후 복원처럼 서비스마다 등급을 나눈다. 다만 의존 관계를 같이 봐야 한다. 주문 서비스를 10분 안에 살려도 로그인 서비스가 4시간 뒤에 살아나면 실제 RTO는 4시간이다. 등급표를 만들 때 각 서비스가 무엇에 기대는지 같이 적는다.

## DR 훈련: 문서대로 되살아나는지

DR 계획은 실제로 해 보기 전까지는 가설이다. 사고 당일에야 처음 복원해 보면 문서에 빠진 단계, 만료된 권한, 아무도 모르는 비밀번호를 그때 발견한다. 그래서 정해진 날에 일부러 해 본다. 흔히 게임 데이(game day)라고 부른다.

훈련의 깊이는 단계적으로 올린다.

- 문서 읽기 훈련: 당번 두세 명이 런북을 처음부터 읽으며 "이 명령을 어디서 치나", "이 비밀번호는 어디 있나"를 짚는다. 30분이면 되는데 빠진 단계가 꽤 나온다.
- 복원 훈련: 실제 백업을 별도 계정이나 리전에 복원해 띄우고, 행 수와 최근 데이터를 확인한다. 걸린 시간을 단계별로 기록해 RTO 목표와 비교한다.
- 전환 훈련: 트래픽 일부나 전부를 실제로 대기 쪽으로 돌린다. 가장 위험하지만 DNS, 인증서, 방화벽, 연결 풀처럼 복원 훈련에서는 드러나지 않는 문제가 여기서 나온다.

기록은 단계마다 남긴다. "알림 3분, 판단 7분, 서버 준비 22분, 복원 31분, 검증 6분, 전환 4분, 합계 73분"처럼 남겨야 다음에 어느 단계를 줄일지 보인다. 훈련 자체가 장애가 되지 않게, 전환 훈련은 사용자 트래픽이 적은 시간에 하고 되돌리는 절차를 먼저 써 둔다. 실패를 일부러 넣어 보는 실험 전반은 [카오스 엔지니어링](/posts/chaos-engineering)에서 다룬다.

## 훈련에서 자주 터지는 것들

실제 훈련에서 자주 나오는 실패는 기술보다 "사라진 리전 안에 있던 것"이다.

증상은 "복원을 시작하려는데 백업 파일을 못 연다"로 나온다. 백업을 암호화한 키가 사라진 리전의 키 관리 서비스에만 있었던 경우다. AWS KMS 키는 기본적으로 리전마다 따로라서, 다른 리전에서 쓰려면 멀티 리전 키를 쓰거나 대기 리전 키로 다시 암호화해 복사해야 한다. 확인은 간단하다. 대기 리전에서 백업 하나를 실제로 내려받아 풀어 본다.

"새 서버는 떴는데 앱 이미지를 못 받는다"도 흔하다. 컨테이너 레지스트리가 운영 리전에만 있었다. 레지스트리 복제를 켜 두거나 대기 리전에 이미지를 미리 밀어 둔다. 같은 종류로, 비밀 값(DB 비밀번호, API 키)이 운영 리전의 비밀 저장소에만 있는 경우도 있다.

"복제본을 승격했는데 앱이 계속 옛 주소로 붙는다"는 DNS TTL이 길거나, 앱이 DNS 결과를 프로세스 안에 오래 들고 있는 경우다. 연결 풀이 옛 연결을 붙잡고 있어도 같은 증상이 난다. 이건 [장애 조치](/posts/failover) 글에서 직접 잰다.

"객체 저장소 복제를 켰는데 대기 쪽에 옛 파일이 없다"는 S3 복제 규칙의 성질 때문이다. 복제는 규칙을 켠 뒤에 새로 올라온 객체만 옮긴다. 이미 있던 객체는 S3 Batch Replication 같은 작업을 따로 돌려야 한다.

마지막으로, 복원 절차가 사라진 리전의 무언가를 부르는 경우가 있다. 배포 파이프라인이 운영 리전의 서버에서 돌거나, 런북이 운영 리전의 위키에만 있거나, 접속용 배스천 서버가 운영 리전에 있는 식이다. 훈련 때 "운영 리전의 모든 것을 못 쓴다"고 가정하고 해 보면 바로 드러난다.

## 두 질문에 숫자로 답하기

처음 회의실의 두 질문으로 돌아가면, 몇 분어치를 잃었는지는 마지막으로 바깥에 나간 기록이 정하고, 언제 돌아오는지는 알아채기부터 전환까지 각 단계의 합이 정한다. 실험에서는 `archive_timeout` 15초가 10.1초의 손실로, 60초 분량의 쓰기가 9.51초의 재생으로 나타났다. 목표를 먼저 정하고, 그 목표에 맞는 DR 단계를 서비스마다 고르고, 훈련으로 실제 숫자를 재서 목표와 맞춰 보는 것이 재해 복구의 전부다.

이 주제의 다른 글: [백업 전략](/posts/backup-strategy), [장애 조치](/posts/failover), [멀티 리전](/posts/multi-region).

## 면접에서 나올 만한 질문

### RPO와 RTO의 차이는 무엇인가요?

RPO는 잃어도 되는 데이터의 양, RTO는 멈춰 있어도 되는 시간이다. 둘 다 사고 순간을 기준으로, RPO는 마지막으로 안전하게 기록된 시점까지 과거 쪽으로, RTO는 서비스 복귀까지 미래 쪽으로 잰다. RPO는 데이터를 얼마나 자주 바깥으로 내보내느냐로, RTO는 감지·판단·복원·전환 단계의 길이로 줄인다.

### WAL 보관을 켜 두면 RPO가 0인가요?

아니다. 아직 보관소로 나가지 못한 WAL 파일 안의 커밋은 서버 디스크와 함께 사라진다. 쓰기가 적으면 파일이 늦게 차서 `archive_timeout`이 최악의 RPO가 되고, 이 값이 꺼져 있으면 몇 분에서 몇 시간이 될 수 있다. 실험에서 `archive_timeout` 60초 설정으로 30초 동안 쓴 117건을 모두 잃었고, `pg_receivewal`로 실시간 수신을 더하자 모두 살아났다.

### RTO를 줄이려면 무엇부터 하나요?

먼저 단계별로 시간을 재서 가장 긴 단계를 찾는다. 서버 준비가 길면 IaC나 미리 켜 둔 대기 환경으로, 복사가 길면 증분 백업이나 스냅숏으로, WAL 재생이 길면 베이스 백업 주기를 줄여서 해결한다. 실험에서 60초 쓰기를 재생하는 데 9.51초가 걸렸으니, 하루 한 번 백업이면 최악으로 하루치를 재생해야 한다.

### 파일럿 라이트와 웜 스탠바이는 어떻게 다른가요?

둘 다 대기 리전에 DB 복제본을 켜 둔다는 점은 같다. 파일럿 라이트는 앱 서버를 꺼 두고 이미지만 준비해 두니 사고 때 앱 서버를 새로 띄우는 시간이 든다. 웜 스탠바이는 앱까지 작은 규모로 켜 두어서 승격하고 늘리기만 하면 되고, 그만큼 RTO가 짧고 평소 비용이 크다.

### 모든 서비스를 액티브-액티브로 하면 되지 않나요?

비용과 복잡도가 감당이 안 된다. 운영 환경을 두 벌 이상 상시 돌려야 하고, 양쪽에서 같은 데이터에 쓰기가 들어오는 충돌을 풀어야 한다. 서비스마다 멈췄을 때의 손실이 다르니 결제·주문처럼 손실이 큰 곳만 높은 등급을 주고 나머지는 낮춘다. 다만 높은 등급 서비스가 기대는 서비스도 같은 등급이어야 실제 RTO가 지켜진다.

### DR 훈련에서 자주 발견되는 문제는 무엇인가요?

사라진 리전 안에만 있던 것들이다. 백업을 연 키가 그 리전의 KMS에만 있거나, 컨테이너 이미지와 비밀 값이 그 리전에만 있거나, 런북과 배스천 서버가 그 리전에 있는 경우다. 또 DNS TTL과 앱의 DNS 캐시 때문에 전환이 늦어지는 문제도 전환 훈련에서야 드러난다. 훈련은 "운영 리전의 모든 것을 못 쓴다"는 가정으로 한다.

### 복제본이 있으면 백업은 필요 없지 않나요?

필요하다. 복제는 실수도 그대로 복제한다. WHERE 없는 `DELETE`나 랜섬웨어의 암호화는 몇 밀리초 만에 복제본에도 반영된다. 복제본은 하드웨어나 리전 장애의 RTO를 줄이고, 백업과 WAL 보관은 과거 시점으로 돌아가는 수단이라 서로 다른 사고를 막는다.
