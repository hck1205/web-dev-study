상품 검색 API를 고치다가 정확히 일치하는 상품만 찾으려고 `term` 질의를 썼다. 상품명은 "삼성전자 갤럭시 S24 자급제"로 분명히 들어 있다.

```bash
curl -s "localhost:9299/products/_search?filter_path=hits.total" \
  -H 'content-type: application/json' \
  -d '{"query":{"term":{"name":"삼성전자 갤럭시"}}}'
```

```text
{"hits":{"total":{"value":0,"relation":"eq"}}}
```

0건이다. `"S24"`로 바꿔도 0건이다. 그런데 `"s24"`로 소문자를 넣으면 1건이 나온다. 이유는 색인된 모습을 보면 바로 보인다.

```bash
# name 필드의 분석기가 이 문장을 어떻게 자르는지 본다
curl -s "localhost:9299/products/_analyze" \
  -H 'content-type: application/json' \
  -d '{"field":"name","text":"삼성전자 갤럭시 S24 자급제"}'
```

```text
tokens: 삼성전자 / 갤럭시 / s24 / 자급제
```

(응답 JSON에서 토큰만 추렸다.) `name`은 `text` 필드라 색인할 때 standard 분석기가 공백으로 자르고 소문자로 바꿨다. 역색인에는 "삼성전자 갤럭시"라는 텀이 없다. 그런데 `term`은 검색어를 분석하지 않고 그대로 텀 하나로 찾는다. "S24"도 대문자 그대로 찾으니 소문자 "s24"와 다르다. 한국어 형태소 분석기 nori를 쓰는 필드라면 사전에 따라 "삼성전자" 하나조차 "삼성"과 "전자"로 쪼개져, 한 단어짜리 `term`도 0건이 될 수 있다.

분석기와 역색인이 어떻게 만들어지는지, text와 keyword 필드의 차이, BM25 점수는 [역색인 글](/posts/elasticsearch-inverted-index)에 정리해 두었다. 이 글은 그 위에서 질문을 적는 언어, Query DSL을 다룬다. 어떤 질의가 검색어를 분석하는지, bool로 조건을 어떻게 묶는지, 어떤 질의가 비싼지, 점수와 정렬과 페이지를 어떻게 다루는지.

이 글의 출력은 이 컨테이너에서 Elasticsearch 배포판을 내려받을 수 없어서 OpenSearch 3.9로 돌린 것이다. OpenSearch는 Elasticsearch 7.10에서 갈라져 나온 포크라 여기서 쓴 질의의 문법과 동작은 같다(점수의 소수점 아래 값은 버전에 따라 조금 다를 수 있다). API가 다른 곳(PIT)은 따로 적었다. 예제 색인은 상품 여섯 개짜리 `products`다.

```text
id  name                                     brand    price    sales  created_at (UTC)      in_stock  color
1   삼성전자 갤럭시 S24 자급제               Samsung  1155000  820    2026-10-01 09:00:00   true      black
2   삼성전자 갤럭시 버즈3 프로 무선 이어폰   Samsung  299000   1430   2026-10-15 12:00:00   true      white
3   소니 WF-1000XM5 무선 이어폰 노이즈캔슬링 Sony     359000   610    2026-09-20 03:00:00   false     null
4   애플 에어팟 프로 2 무선 이어폰           Apple    359000   2100   2026-10-22 23:30:00   true      ""
5   이어폰 케이스 갤럭시 버즈 호환           Generic  9900     5300   2026-10-31 23:59:59   true      (없음)
6   무선 충전기 삼성전자 정품                Samsung  39000    300    2026-11-01 00:00:00   true      black
```

`name`은 `text`(하위 필드 `name.keyword`), `brand`와 `color`는 `keyword`, `price`와 `sales`는 `integer`, `created_at`은 `date`다.

## 검색어를 분석하는 질의, 안 하는 질의

Query DSL의 질의는 크게 두 무리다. 전문 검색(full text) 질의인 `match`, `match_phrase`, `multi_match`는 검색어를 그 필드의 분석기로 잘라 텀으로 바꾼 뒤 찾는다. 색인할 때와 같은 방식으로 자르니 대소문자나 띄어쓰기 차이가 흡수된다. 텀 수준(term-level) 질의인 `term`, `terms`, `range`, `exists`, `prefix`, `wildcard`, `ids`는 검색어를 분석하지 않고 색인된 텀과 그대로 비교한다.

규칙은 단순하다. `text` 필드에는 전문 검색 질의를, `keyword`·숫자·날짜·불리언 필드에는 텀 수준 질의를 쓴다. 처음 장면은 `text` 필드에 텀 수준 질의를 쓴 것이다. 같은 문자열로 `match`를 쓰면 이렇게 나온다.

```text
match name "삼성전자 갤럭시"  → 4건
  id 1  score 0.694
  id 2  score 0.591
  id 6  score 0.347   (삼성전자만 맞음)
  id 5  score 0.319   (갤럭시만 맞음)
```

정말 상품명 전체가 일치하는 것만 원했다면 `name.keyword`에 `term`을 쓴다. keyword 필드는 문자열 전체를 텀 하나로 저장하기 때문이다.

```text
term name.keyword "삼성전자 갤럭시 S24 자급제"  → 1건 (id 1, score 1.0)
```

## 질의는 나무 모양으로 조립한다

질의는 두 종류의 조각으로 만든다. 리프(leaf) 질의는 필드 하나에 조건 하나를 거는 조각이다. `match`, `term`, `range`가 여기에 든다. 복합(compound) 질의는 다른 질의를 감싸서 묶거나 점수를 바꾸는 조각이다. `bool`, `constant_score`, `boosting`, `function_score`, `dis_max`가 있다. 복합 질의 안에 또 복합 질의를 넣을 수 있어서 질의 하나가 나무 모양이 된다.

## bool의 네 칸

`must`와 `filter`는 둘 다 "반드시 맞아야 한다"이고 차이는 점수뿐이다. `must`는 질의 문맥(query context)에서 돌아 BM25 점수를 매기고, `filter`는 필터 문맥(filter context)에서 맞는지만 본다. 필터 문맥의 결과는 예/아니요라서 캐시할 수 있다. 이 구분과 흔한 실수(모든 조건을 must에 넣기)는 [역색인 글](/posts/elasticsearch-inverted-index)에서 다뤘으니 여기서는 실제 점수가 어떻게 나오는지만 본다.

`must_not`도 필터 문맥이다. 점수를 매기지 않는다. 그래서 `must_not` 하나만 있는 질의는 모든 결과의 점수가 0이다.

```text
bool must_not term brand Samsung  → 3건
  id 3  score 0.0
  id 4  score 0.0
  id 5  score 0.0
```

헷갈리는 건 `should`다. `should`가 "맞아야 하는 조건"인지 "맞으면 좋은 조건"인지가 같은 bool 안에 무엇이 함께 있느냐에 따라 바뀐다. 같은 `should`를 세 가지로 돌려 보면 차이가 보인다.

```text
(가) should만: brand Sony 또는 Apple
    → 2건: id 3 score 1.0, id 4 score 1.0

(나) filter in_stock=true + should: brand Sony 또는 Apple
    → 5건: id 4 score 1.0, id 1 score 0.0, id 2 score 0.0, id 5 score 0.0, id 6 score 0.0

(다) (나)에 minimum_should_match: 1 추가
    → 1건: id 4 score 1.0
```

(가)처럼 `must`도 `filter`도 없이 `should`만 있으면 그중 적어도 하나는 맞아야 한다(`minimum_should_match` 기본값 1). (나)처럼 `must`나 `filter`가 하나라도 있으면 기본값이 0으로 바뀌어 `should`는 점수만 더해 주는 조건이 된다. 재고 있는 상품이 모두 나오고, Apple만 점수 1을 받아 맨 위로 올라갔을 뿐이다. "재고 있는 Sony나 Apple"을 원했다면 (다)처럼 `minimum_should_match`를 명시해야 한다. 이 규칙을 모르면 필터를 하나 추가했을 뿐인데 결과가 갑자기 늘어나는 버그가 생긴다.

"재고 있는 Sony나 Apple"을 점수 없이 걸고 싶다면 `should`를 담은 bool을 통째로 `filter` 안에 넣는 방법도 있다. 안쪽 bool은 `should`만 있으니 하나는 맞아야 하고, 바깥 `filter` 덕분에 점수는 매기지 않는다.

```text
filter [ bool should [Sony, Apple] ]  → 2건: id 3 score 0.0, id 4 score 0.0
```

점수 없이 걸러 놓고 모두 같은 점수를 주고 싶으면 `constant_score`로 감싸도 된다. 감싼 질의는 필터 문맥에서 돌고, 결과마다 `boost` 값(기본 1)을 점수로 받는다.

## minimum_should_match는 개수를 세는 규칙이다

`minimum_should_match`는 bool의 `should` 절이나 `match`의 텀 가운데 몇 개가 맞아야 하는지 정한다. 숫자만 주면 그 개수, 음수면 "전체에서 그만큼 빼고", 퍼센트면 비율이다. 퍼센트는 계산한 값을 버림(내림)한다. 그래서 75%와 -25%는 같은 말 같지만 절 수에 따라 다르다.

```text
match name "갤럭시 무선 이어폰" (텀 3개)
  minimum_should_match 75%  → 3 x 0.75 = 2.25 → 2개   → 4건 (id 2, 5, 3, 4)
  minimum_should_match -25% → 3 x 0.25 = 0.75 → 0개를 빼서 3개 → 1건 (id 2)
  operator and               → 3개 모두                → 1건 (id 2)
```

`"3<-25% 9<-3"` 같은 조건부 형식도 있다. 절이 3개 이하면 모두 맞아야 하고, 3개를 넘으면 -25%, 9개를 넘으면 -3을 적용한다. 검색어가 짧을 때는 엄격하게, 길 때는 느슨하게 하려고 쓴다. 검색창에 단어를 많이 넣은 사용자는 그중 몇 개가 안 맞아도 결과를 보고 싶어 한다.

아래 함수로 규칙을 직접 짜 볼 수 있다. 테스트의 기댓값은 should 절 n개짜리 bool 질의를 실제로 돌려서, 결과에 나온 문서가 맞힌 절 수의 최솟값을 확인한 것이다.

  // 1. "<"가 있으면: 기본은 n개 모두. 공백으로 나눈 "기준<규칙"마다
  //    n이 기준보다 크면 그 규칙으로 다시 계산한다 (뒤의 것이 이긴다)
  // 2. 퍼센트: 양수면 floor(n * p / 100), 음수면 n - floor(n * |p| / 100)
  // 3. 정수: 양수면 그대로, 음수면 n + 값
  // 4. 0보다 작으면 0
  return n;
}`}
  solution={`function requiredClauses(n, spec) {
  spec = String(spec).trim();
  if (spec.includes("<")) {
    let result = n;
    for (const part of spec.split(/\\s+/)) {
      const [limit, rule] = part.split("<");
      if (n > Number(limit)) result = requiredClauses(n, rule);
    }
    return result;
  }
  let req;
  if (spec.endsWith("%")) {
    const p = Number(spec.slice(0, -1));
    req = p >= 0 ? Math.floor((n * p) / 100) : n - Math.floor((n * -p) / 100);
  } else {
    const v = Number(spec);
    req = v >= 0 ? v : n + v;
  }
  return Math.max(0, req);
}`}

계산이 절 수보다 큰 값이 나오면 아무 문서도 맞지 않는다. 절 1개에 `"3"`을 주면 결과가 0건이다. 반대로 0이 나와도, `must`와 `filter` 없이 `should`만 있는 bool이라면 하나는 맞아야 한다. 실험에서 절 2개에 `"-5"`를 주면 0이 계산되지만 결과는 절 하나 이상 맞은 문서만 나왔다.

## match는 OR, match_phrase는 순서와 거리

`match`는 검색어를 텀으로 자른 뒤 기본으로 OR로 묶는다. "갤럭시 무선 이어폰"이면 셋 중 하나만 있어도 나온다. 많이 맞을수록 점수가 높아서 위에 오지만, 결과 개수는 많다. `operator: "and"`를 주면 모두 맞아야 한다. 그 중간이 앞에서 본 `minimum_should_match`다.

`match_phrase`는 텀이 그 순서로 붙어 있어야 맞는다. 색인할 때 텀마다 위치(position)를 같이 저장해 두기 때문에 가능하다.

```text
match_phrase "무선 이어폰"            → 3건 (id 2, 3, 4)
match_phrase "이어폰 무선"            → 0건
match_phrase "이어폰 무선" slop 1     → 0건
match_phrase "이어폰 무선" slop 2     → 3건
match_phrase "갤럭시 이어폰" slop 2   → 0건
match_phrase "갤럭시 이어폰" slop 3   → 2건 (id 5, 2)
```

`slop`은 텀을 몇 칸까지 옮겨서 맞춰 볼지다. 아래 그림은 id 2 상품명의 텀 위치를 따라가며 "갤럭시 이어폰"에 몇 칸이 필요한지 센다.

순서가 뒤집힌 "이어폰 무선"이 slop 2부터 맞는 것도 같은 계산이다. 붙어 있는 두 텀의 순서를 바꾸려면 한 텀이 상대를 건너가야 해서 2칸이 든다. id 5("이어폰 케이스 갤럭시 버즈 호환")는 "갤럭시 이어폰"이 거꾸로 2칸 떨어져 있어 역시 3칸이 필요했다.

실무에서는 `match`로 넓게 찾고, 같은 검색어의 `match_phrase`를 `should`에 넣어 구절이 그대로 들어 있는 상품을 위로 올리는 조합을 많이 쓴다. 구절만 쓰면 너무 좁고, `match`만 쓰면 "무선 충전기"와 "무선 이어폰"이 비슷한 점수를 받는다.

## range와 날짜 계산

`range`는 `gt`, `gte`, `lt`, `lte`로 범위를 건다. 숫자는 단순하고, 날짜에서 실수가 많다.

날짜에는 날짜 수학(date math)을 쓸 수 있다. `now-7d`는 지금부터 7일 전, `now/d`는 오늘 0시로 내림, `2026-10-01||/M`은 그 날짜를 월 단위로 내림한 값이다. 그런데 반올림 방향이 연산자마다 다르다. `gte`는 그 단위의 시작으로, `lte`는 그 단위의 끝(마지막 밀리초)으로, `gt`는 그 단위의 끝 다음으로, `lt`는 그 단위의 시작 전으로 간다. 그래서 "10월 전부"를 이렇게 적어도 맞게 나온다.

```text
range created_at gte "2026-10-01||/M", lte "2026-10-01||/M"  → 4건 (id 1, 2, 4, 5)
range created_at gt  "2026-10-01||/M"                        → 1건 (id 6, 11월 1일 0시)
```

`lte`가 10월의 끝인 31일 23:59:59.999로 올라갔고, `gt`는 10월이 끝난 뒤부터다. 날짜만 적고 시각을 빼도 비슷하게 동작한다. `lte: "2026-10-31"`은 31일 하루 전체를 포함해서 id 5(31일 23:59:59)가 결과에 들어왔다. 헷갈리지 않으려면 `gte`와 `lt`로 반열린 구간(`gte 2026-10-01`, `lt 2026-11-01`)을 쓰는 습관이 가장 안전하다. 결과는 같은 4건이다.

시간대는 더 자주 틀린다. 날짜는 UTC로 저장되는데 사용자는 한국 시간으로 "10월 22일 주문"을 찾는다.

```text
range created_at gte "2026-10-22", lte "2026-10-22"                        → 1건 (id 4)
range created_at gte "2026-10-22", lte "2026-10-22", time_zone "+09:00"   → 0건
```

id 4는 UTC로 22일 23:30이지만 한국 시간으로는 23일 08:30이다. `time_zone`을 주지 않으면 UTC 기준 하루를 찾아서 한국 시간 23일 주문이 22일 주문으로 잡힌다. `time_zone`은 날짜 문자열과 날짜 수학의 반올림에 적용되고, `now` 자체에는 적용되지 않는다.

`now`가 들어간 질의는 캐시에도 영향을 준다. `now`는 요청마다 값이 달라서 필터 결과를 캐시할 수 없다. `now/m`이나 `now/h`처럼 단위로 내림해 두면 그 단위 동안 같은 값이 되어 캐시가 다시 쓰인다. 대시보드가 1분마다 같은 범위를 묻는다면 `now-1h/m`처럼 쓴다.

## exists와 ids

`exists`는 필드에 색인된 값이 있는 문서를 찾는다. 무엇을 "없다"로 보는지가 함정이다.

```text
exists color  → 4건 (id 1, 2, 4, 6)
```

`null`(id 3)과 필드 자체가 없는 문서(id 5)는 빠지고, 빈 문자열 `""`(id 4)은 값이 있는 것으로 친다. 빈 배열 `[]`도 값이 없는 것으로 본다. "색상 미입력 상품"을 찾으려고 `must_not exists`를 쓰면 빈 문자열로 저장된 상품은 빠진다. 입력 단계에서 빈 문자열을 `null`로 맞추거나, 매핑에 `null_value`를 정해 둔다.

`ids`는 `_id` 목록으로 찾는다. 없는 id는 조용히 무시한다.

```text
ids ["3", "5", "99"]  → 2건 (id 3, 5)
```

문서 하나만 꺼낼 때는 검색보다 `GET /products/_doc/3`이 낫다. 검색은 refresh가 된 뒤에만 보이지만 문서 조회는 방금 쓴 것도 바로 돌려준다.

## prefix와 wildcard가 비싼 이유

`prefix`, `wildcard`, `regexp`, `fuzzy`는 검색어 하나가 텀 하나가 아니다. "갤럭으로 시작하는 모든 텀"을 텀 사전에서 찾아 펼친 뒤, 그 텀들을 모두 OR로 찾는다. 텀 사전은 정렬되어 있어서 `prefix`는 그나마 범위를 좁힐 수 있지만, `*어폰`처럼 앞에 와일드카드가 오면 사전 전체를 훑어야 한다. 상품명 텀이 수백만 개면 질의 하나가 수백만 개 텀을 검사한다.

결과 자체는 잘 나온다.

```text
prefix   name "갤럭"         → 3건 (id 1, 2, 5)
wildcard name "*어폰"        → 4건 (id 2, 3, 4, 5)
```

그래서 클러스터 단위로 이런 질의를 막는 설정이 있다. 켜 두면 비싼 질의가 오류로 돌아온다.

```bash
# 비싼 질의를 클러스터 전체에서 막는다
curl -s -XPUT "localhost:9299/_cluster/settings" \
  -H 'content-type: application/json' \
  -d '{"transient":{"search.allow_expensive_queries":false}}'
```

```text
wildcard name "*어폰" →
  "[wildcard] queries cannot be executed when 'search.allow_expensive_queries' is set to false."

prefix name "갤럭" →
  "[prefix] queries cannot be executed when 'search.allow_expensive_queries' is set to false.
   For optimised prefix queries on text fields please enable [index_prefixes]."
```

두 번째 오류 메시지가 대안을 알려 준다. `text` 필드에 `index_prefixes`를 켜면 색인할 때 텀의 앞부분(기본 2~5자)을 따로 저장해 둔다. 그러면 `prefix` 질의가 펼치기 없이 저장해 둔 접두사 텀 하나를 찾는 것으로 바뀌고, 비싼 질의로 치지 않는다. 같은 설정을 켠 채로 `index_prefixes`(1~5자)를 준 색인에서는 `prefix "갤럭"`이 오류 없이 1건을 돌려줬다.

자동완성처럼 "입력 중인 글자로 시작하는 단어"를 찾는 일이 많다면 edge n-gram 분석기를 쓴다. 색인할 때 단어마다 앞에서부터 잘라 여러 텀을 만든다.

```text
edge_ngram(1~10) 분석: "갤럭시 버즈3" → 갤 / 갤럭 / 갤럭시 / 버 / 버즈 / 버즈3
```

검색할 때는 이 분석기가 아니라 standard 같은 일반 분석기(`search_analyzer`)를 쓴다. 그래야 사용자가 친 "버즈"가 "버", "버즈"로 또 잘리지 않고 "버즈" 텀 하나로 찾는다. 색인이 커지는 대신 질의가 일반 `match`가 되어 빠르다. Elasticsearch에는 이 구성을 미리 묶은 `search_as_you_type` 필드 타입도 있다.

`*이어폰*`처럼 가운데가 맞는 검색이 정말 필요하다면 n-gram 분석기나 Elasticsearch의 `wildcard` 필드 타입(문자열을 n-gram으로 색인해 와일드카드를 빠르게 하는 타입)을 고른다. `keyword` 필드에 앞뒤 와일드카드를 거는 것은 가장 느린 선택이다.

## 점수 손보기: boosting과 function_score

"이어폰"으로 검색하면 1등이 케이스다.

```text
match name "이어폰"
  id 5  score 0.204   이어폰 케이스 갤럭시 버즈 호환
  id 2  score 0.188
  id 3  score 0.188
  id 4  score 0.188
```

BM25는 짧은 필드에 나온 텀을 더 무겁게 본다. 케이스 상품명은 텀이 다섯 개로, 여섯 개인 다른 이어폰 상품명보다 짧아서 점수가 조금 높게 나왔다. 케이스를 아예 빼고 싶으면 `must_not`이지만, 케이스를 찾는 사람도 있으니 순위만 내리고 싶다. 그럴 때 `boosting` 질의를 쓴다.

```json
{
  "query": {
    "boosting": {
      "positive": { "match": { "name": "이어폰" } },
      "negative": { "match": { "name": "케이스" } },
      "negative_boost": 0.2
    }
  }
}
```

```text
  id 2  score 0.188
  id 3  score 0.188
  id 4  score 0.188
  id 5  score 0.041   (0.204 x 0.2)
```

`negative`에 맞는 문서는 지우지 않고 점수에 `negative_boost`를 곱한다.

판매량이나 평점, 최신성 같은 문서 값으로 점수를 바꾸려면 `function_score`를 쓴다. 감싼 질의의 점수에 함수 결과를 섞는다.

```json
{
  "query": {
    "function_score": {
      "query": { "match": { "name": "무선 이어폰" } },
      "field_value_factor": { "field": "sales", "modifier": "log1p", "factor": 1 },
      "boost_mode": "multiply"
    }
  }
}
```

```text
  id 4  score 1.252   (판매 2100)
  id 2  score 1.189   (판매 1430)
  id 3  score 1.050   (판매 610)
  id 5  score 0.758   (판매 5300)
  id 6  score 0.548   (판매 300)
```

`log1p`는 `log10(1 + 값)`이다. id 4는 원래 점수 0.377에 log10(2101) = 3.32를 곱해 1.252가 됐다. 판매량을 그대로 곱하면 판매 5,300의 케이스가 검색어와 상관없이 모든 결과의 1등이 된다. 로그로 눌러 두어야 관련도가 주인이고 판매량이 거드는 모양이 된다. `boost_mode`는 원래 점수와 함수 값을 어떻게 섞을지(`multiply`가 기본, `sum`, `replace` 등), 함수가 여러 개면 `score_mode`가 함수끼리 어떻게 합칠지를 정한다.

최신성은 감쇠 함수(`gauss`, `exp`, `linear`)로 넣는다. 기준점(`origin`, 예: `now`)에서 멀어질수록 점수가 줄어드는 모양을 `scale`과 `decay`로 정한다. "7일 지나면 점수 절반" 같은 식이다. 판매량 필드에 값이 없는 문서가 있으면 `field_value_factor`가 오류를 내니 `missing` 값을 정해 둔다.

`function_score`는 결과 전부에 함수를 계산하니 결과가 많을수록 비싸다. 상위 몇백 개에만 비싼 점수 계산을 하고 싶다면 `rescore`로 1차 결과의 앞부분만 다시 점수를 매기는 방법이 있다.

## 하이라이트

검색 결과에서 맞은 단어를 굵게 보여 주는 건 `highlight`가 한다.

```json
{
  "query": { "match": { "name": "무선 이어폰" } },
  "highlight": { "fields": { "name": {} } }
}
```

```text
id 2  name: ["삼성전자 갤럭시 버즈3 프로 <em>무선</em> <em>이어폰</em>"]
id 3  name: ["소니 WF-1000XM5 <em>무선</em> <em>이어폰</em> 노이즈캔슬링"]
```

기본 하이라이터(unified)는 질의에 쓴 텀을 찾아 `<em>` 태그로 감싸고, 긴 본문이면 맞은 부분 주변만 조각(fragment)으로 잘라 준다. 조각 길이와 개수는 `fragment_size`(기본 100자)와 `number_of_fragments`(기본 5)로 정하고, 태그는 `pre_tags`, `post_tags`로 바꾼다.

하이라이트 결과에는 원문이 그대로 들어 있다. 상품명이나 본문에 사용자가 넣은 HTML이 있으면 화면에 `<em>`과 함께 그대로 박힌다. 하이라이트 조각을 HTML로 그리기 전에 원문을 이스케이프하고 하이라이트 태그만 되살리거나, `encoder: "html"`로 원문을 이스케이프하게 한다. 그러지 않으면 검색 결과가 XSS 통로가 된다.

## 정렬하면 점수가 사라진다

`sort`를 주면 결과 순서는 정렬 값이 정하고, 점수는 계산하지 않는다.

```text
match name "이어폰", sort price asc
  id 5  score null  sort [9900]
  id 2  score null  sort [299000]

같은 질의 + track_scores: true
  id 5  score 0.204  sort [9900]
  id 2  score 0.188  sort [299000]
```

`_score`가 `null`로 나오는 게 정상이다. "가격순으로 보되 화면에 관련도도 보여 주고 싶다"면 `track_scores`를 켠다. 점수 계산 비용이 다시 든다. 관련도순 안에서 같은 점수끼리만 가격으로 정렬하려면 `sort: ["_score", { "price": "asc" }]`처럼 `_score`를 첫 정렬 기준으로 둔다.

정렬은 `keyword`, 숫자, 날짜처럼 doc_values(열 방향으로 저장한 값)가 있는 필드에서 한다. `text` 필드로 정렬하면 오류가 난다. 상품명 정렬이 필요하면 `name.keyword`를 쓴다. 같은 정렬 값이 많을 때 페이지 경계에서 순서가 흔들리지 않도록 유일한 필드(상품 id)를 마지막 정렬 기준으로 붙인다.

## 필요한 필드만 돌려받기

검색 응답은 기본으로 문서마다 `_source`(색인할 때 보낸 원본 JSON 전체)를 돌려준다. 상품 설명 같은 큰 필드가 있으면 목록 화면에 필요 없는 바이트가 네트워크로 나간다.

```text
_source ["name", "price"]
  id 2  _source: {"price": 299000, "name": "삼성전자 갤럭시 버즈3 프로 무선 이어폰"}

_source false, fields ["price", "created_at"]
  id 2  fields: {"price": [299000], "created_at": ["2026-10-15T12:00:00.000Z"]}
```

`_source`에 배열을 주면 그 필드만 남기고, `includes`와 `excludes`로 와일드카드를 쓸 수도 있다. `fields`는 매핑을 거친 값을 돌려준다. 값이 늘 배열이고, 날짜는 매핑 형식으로 정리되어 나온다. 원본 그대로가 필요하면 `_source`, 매핑대로 정리된 값(런타임 필드 포함)이 필요하면 `fields`를 쓴다.

## 총 개수는 10,000에서 멈춘다

결과 개수를 정확히 세는 것도 비용이다. 그래서 기본으로 10,000건까지만 정확히 센다. 같은 "무선 이어폰 모델 N" 문서 12,000개를 넣은 색인에서 돌리면 이렇다.

```text
기본                    → {"value":10000,"relation":"gte"}
track_total_hits: true  → {"value":12000,"relation":"eq"}
track_total_hits: false → total 없음
```

`relation`이 `gte`면 "10,000건 이상"이라는 뜻이다. 화면에 "검색 결과 10,000+건"처럼 쓰면 된다. 정확한 숫자가 꼭 필요할 때만 `true`를 준다. 결과가 많은 질의에서 `true`를 주면 모든 일치 문서를 끝까지 세느라 느려진다. 숫자를 안 보여 주는 화면이라면 `false`로 아예 세지 않는 게 가장 빠르다. 개수를 세지 않으면 상위 결과만 찾으면 되니 점수가 낮은 문서를 건너뛰는 최적화가 켜진다.

## 깊은 페이지는 다른 길로 간다

`from`과 `size`로 페이지를 넘기면 깊은 페이지에서 막힌다.

```text
from 9995, size 10 →
  "Result window is too large, from + size must be less than or equal to: [10000] but was [10005].
   ... This limit can be set by changing the [index.max_result_window] index level setting."
```

샤드마다 앞의 `from + size`개를 다 정렬해 모아야 하니 깊을수록 일이 커지기 때문이다. 한도를 올리는 설정이 메시지에 나오지만 올리는 건 답이 아니다. 앞 페이지 마지막 문서의 정렬 값을 넘기는 `search_after`와, 넘기는 동안 같은 시점의 데이터를 보게 하는 PIT(point in time)를 쓴다. 원리와 쓰는 법은 [역색인 글](/posts/elasticsearch-inverted-index)에 있다.

PIT은 여기서 두 제품의 API가 갈린다. Elasticsearch는 `POST /products/_pit?keep_alive=1m`으로 PIT을 열고, 검색 본문의 `"pit": { "id": "...", "keep_alive": "1m" }`로 넘긴다. 이때 URL에 색인 이름을 쓰지 않는다. OpenSearch는 `POST /products/_search/point_in_time?keep_alive=1m`으로 열고 응답의 `pit_id`를 쓴다. 다 쓴 PIT은 닫는다. 열어 둔 PIT은 그 시점의 세그먼트를 지우지 못하게 붙잡아서, 많이 열어 두면 디스크와 힙을 먹는다.

## 느린 질의를 찾는 순서

검색이 느려졌다는 이야기가 오면 질의 모양부터 본다. 이 글에서 본 것들이 대부분의 원인이다.

- `text` 필드에 `term`을 쓰거나 `keyword` 필드에 `match`를 써서 결과가 이상하다 → 필드 타입과 질의 종류를 맞춘다.
- 점수가 필요 없는 조건이 `must`에 있다 → `filter`로 옮긴다.
- 앞에 와일드카드가 붙은 `wildcard`, `regexp`, 긴 `fuzzy`가 있다 → `index_prefixes`, edge n-gram, `wildcard` 필드로 바꾸고 `search.allow_expensive_queries`로 막는다.
- `now`를 내림 없이 쓴다 → `now/m`처럼 내려 캐시가 쓰이게 한다.
- `track_total_hits: true`가 습관처럼 붙어 있다 → 빼거나 `false`로.
- `function_score`가 모든 결과에 비싼 계산을 한다 → `rescore`로 앞부분만.
- 깊은 `from` → `search_after`.

어디서 시간이 드는지 정확히 보려면 요청에 `"profile": true`를 붙인다. 샤드별로 질의가 어떤 Lucene 질의로 바뀌었는지, 각 단계에 몇 나노초가 들었는지 나온다. `wildcard`가 수만 개 텀으로 펼쳐진 것도 여기서 보인다. 운영에서는 색인별 검색 느린 로그(`index.search.slowlog.threshold.query.warn` 같은 설정)를 걸어 기준 시간을 넘는 질의 본문을 남긴다.

## 질문을 조립하는 언어

처음 0건은 분석하지 않는 질의를 분석된 필드에 쓴 결과였다. Query DSL을 쓸 때 매번 묻는 것은 결국 몇 가지다. 이 질의는 검색어를 분석하는가. 이 조건은 점수에 들어가야 하는가. `should`는 지금 필수인가 선택인가. 이 질의는 텀 몇 개로 펼쳐지는가. 정렬과 개수와 페이지에 정말 정확함이 필요한가. 이 질문들에 답하면서 리프를 bool에 담으면, 같은 결과를 더 빠르고 덜 놀랍게 얻는다.

## 면접에서 나올 만한 질문

### term과 match의 차이는요?

`match`는 검색어를 그 필드의 분석기로 잘라 텀으로 바꾼 뒤 찾고, `term`은 검색어를 그대로 텀 하나로 찾는다. 그래서 `text` 필드에 `term`으로 "S24"나 "삼성전자 갤럭시"를 찾으면, 색인된 텀이 소문자로 바뀌고 공백으로 잘려 있어서 0건이 된다. `text` 필드에는 전문 검색 질의를, `keyword`·숫자·날짜에는 텀 수준 질의를 쓴다. 정확히 일치가 필요하면 `.keyword` 하위 필드에 `term`을 쓴다.

### bool의 must, filter, should, must_not은 어떻게 다른가요?

`must`와 `filter`는 둘 다 맞아야 하지만 `must`만 점수를 매기고, `filter`와 `must_not`은 점수 없이 맞는지만 봐서 캐시된다. `should`는 맞으면 점수를 더한다. 점수가 필요 없는 조건은 `filter`에 둬야 순위가 흔들리지 않고 캐시도 쓴다.

### should 조건이 무시되는 것처럼 보입니다. 왜 그런가요?

bool에 `must`나 `filter`가 하나라도 있으면 `minimum_should_match` 기본값이 0이 되어 `should`는 점수만 올리는 선택 조건이 된다. `should`만 있을 때는 기본값이 1이라 하나는 맞아야 한다. 필터를 하나 추가했을 뿐인데 결과가 늘었다면 이 규칙이다. `minimum_should_match: 1`을 명시하거나 should를 담은 bool을 `filter` 안에 넣는다.

### minimum_should_match의 75%와 -25%는 같은가요?

절 4개에서는 둘 다 3개로 같지만, 절 3개에서는 75%가 2개(2.25 내림), -25%는 3개(0.75를 내려 0개를 뺌)로 다르다. 퍼센트는 계산 값을 내림하기 때문이다. 검색어 길이에 따라 다르게 하려면 `"3<-25%"` 같은 조건부 형식을 쓴다.

### prefix나 wildcard 질의는 왜 느리고, 대안은 무엇인가요?

검색어 하나가 텀 사전에서 조건에 맞는 모든 텀으로 펼쳐진 뒤 OR로 찾기 때문이다. 앞에 와일드카드가 오면 사전 전체를 훑는다. 접두사 검색은 `index_prefixes`나 edge n-gram 분석기로 색인 시점에 접두사를 만들어 두고, 가운데 일치는 n-gram이나 `wildcard` 필드 타입을 쓴다. `search.allow_expensive_queries: false`로 비싼 질의를 클러스터에서 막을 수 있다.

### range로 날짜를 걸 때 주의할 점은요?

날짜 수학의 반올림 방향이 연산자마다 다르다. `lte`는 단위의 끝으로 올라가고 `gte`는 시작으로 내려가서, 헷갈리지 않으려면 `gte`와 `lt`로 반열린 구간을 쓴다. 저장은 UTC라 한국 시간 기준 하루를 찾으려면 `time_zone: "+09:00"`을 준다. `now`는 캐시를 막으니 `now/m`처럼 내림해 둔다.

### 판매량이나 최신성을 점수에 섞으려면요?

`function_score`로 원래 BM25 점수에 함수 값을 곱하거나 더한다. 판매량은 `field_value_factor`에 `log1p` 같은 modifier를 줘서 눌러야 관련도가 낮은 인기 상품이 모든 검색의 1등이 되는 일을 막는다. 최신성은 `gauss` 같은 감쇠 함수로 넣는다. 결과 전체에 계산하니 비싸면 `rescore`로 상위 결과에만 적용한다. 특정 결과만 순위를 내리려면 `boosting`의 `negative_boost`가 간단하다.

### 검색 결과 총 개수가 10,000에서 멈춥니다. 버그인가요?

버그가 아니다. 정확한 개수를 세는 비용 때문에 기본으로 10,000건까지만 세고 `relation: "gte"`로 "그 이상"이라고 알려 준다. 정확한 수가 필요하면 `track_total_hits: true`를 주되 결과가 많으면 느려진다. 숫자를 보여 주지 않는다면 `false`로 세지 않는 게 가장 빠르다. 깊은 페이지는 `from`이 아니라 `search_after`와 PIT로 넘긴다.
