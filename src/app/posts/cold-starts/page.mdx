새벽에 알림이 하나 왔다. 결제 웹훅을 받는 Lambda 함수의 p99 지연이 2.8초로 튀었다는 내용이다. 평균은 40ms로 멀쩡하다. 로그를 열어 보니 느린 요청 줄에만 `Init Duration`이라는 칸이 하나 더 붙어 있다. 밤새 한가하던 함수에 아침 첫 요청이 들어오면서 실행 환경을 처음부터 만든 것이다. 이게 콜드 스타트(cold start)다.

이 글은 콜드 스타트 동안 실제로 무엇이 일어나는지 단계별로 나누고, 그 단계를 로컬에서 Node 프로세스로 흉내 내 직접 잰다. 그다음 프로비저닝된 동시성, SnapStart, 주기적인 핑으로 데우기를 비교하고, 핑이 왜 생각만큼 효과가 없는지를 시뮬레이션으로 보인다. 측정은 이 컨테이너에서 Node 22.22와 esbuild 0.24로 돌린 실제 값이고, CloudWatch 로그와 AWS CLI 출력은 계정 없이 실제 형식대로 쓴 예시다. AWS 쪽 숫자와 기능 범위는 2026년 10월 확인 기준이며 자주 바뀐다.

이 주제의 다른 글: 서버리스가 어디서 막히는지(시간 한도, 동시성, DB 연결)는 [서버리스의 한계](/posts/serverless-limits)에서, 서버를 늘리는 데 걸리는 시간 일반은 [오토스케일링](/posts/autoscaling)에서 다룬다.

## 요청 하나가 빈 자리에 떨어지면

서버리스 함수는 요청이 올 때 코드를 실행할 "실행 환경"을 빌려 쓴다. 실행 환경 하나는 한 번에 요청 하나만 처리한다. 앞 요청이 끝난 환경이 남아 있으면 그걸 그대로 다시 쓰고(웜 스타트), 남은 게 없으면 새로 만든다(콜드 스타트).

환경이 얼마나 오래 남는지는 AWS가 공개하지 않는다. 몇 분에서 수십 분 사이로 관찰된다는 이야기가 많지만 보장된 값이 아니고, 트래픽이 꾸준해도 환경은 몇 시간 안에 교체된다. "한 번 데우면 계속 따뜻하다"는 가정은 처음부터 틀렸다.

## 로컬에서 콜드와 웜을 재 보기

클라우드 계정 없이도 단계별 비용을 느낄 수 있다. Node 프로세스 하나를 실행 환경으로 보고, "프로세스 기동 → 핸들러 모듈 require → 첫 요청 → 이후 요청"의 시간을 따로 쟀다. 핸들러는 실제 Lambda 함수에서 흔히 하듯 바깥에서 `@aws-sdk/client-s3`(v3.700)를 불러와 클라이언트를 만든다.

```js
// handler.js — 핸들러 바깥이 init 구간이다
const { S3Client, ListBucketsCommand } = require("@aws-sdk/client-s3");
const client = new S3Client({ region: "ap-northeast-2" });

exports.handler = async (event) => {
  // 첫 호출에서만 설정을 계산해 캐시한다
  return { statusCode: 200, body: "{}" };
};
```

측정 스크립트는 `child_process.fork`로 런타임 프로세스를 띄우고, 런타임이 핸들러를 require한 뒤 HTTP로 요청을 받게 한다. 같은 실험을 7번 반복해 중앙값을 냈다.

```bash
# SDK 없이 빈 핸들러, SDK를 바깥에서 불러오는 핸들러를 각각 7번씩 띄워 잰다
node measure.js ./empty.js
node measure.js ./handler.js
```

```text

    of which require(handler): 0.4 ms
  first request handler     : 0.4 ms
  cold total (spawn→1st res): 54.9 ms
```

봐야 할 줄은 셋이다. 빈 핸들러도 프로세스를 띄우는 데 약 50ms가 든다. 이건 런타임 init에 해당하고 코드로 줄일 수 없다. SDK를 불러오는 순간 `require(handler)`가 0.4ms에서 120.8ms로 뛴다. 콜드 스타트 전체(179.6ms)의 3분의 2가 import 한 줄이다. 마지막으로 웜 요청은 둘 다 0.5ms다. 콜드와 웜의 차이가 300배가 넘는다.

`first request handler`가 5.0ms로 웜보다 열 배 느린 것도 눈여겨볼 만하다. 첫 호출에서만 하는 캐시 채우기와, 아직 최적화되지 않은 코드를 V8이 처음 실행하는 비용이 겹쳤다. 실제 함수에서는 DB 연결, TLS 핸드셰이크, 비밀 값 조회가 여기에 붙어서 첫 요청이 수백 ms 더 느려진다.

실제 Lambda에서는 이 앞에 microVM과 코드 내려받기가 붙는다. 내 노트북 숫자를 그대로 클라우드에 옮기면 안 되지만, 어느 단계가 큰지의 비율은 같은 방향으로 나온다.

## 묶음 크기와 import가 init을 정한다

import가 비싸다면 줄이는 방법은 두 갈래다. 파일을 하나로 묶어 읽는 횟수를 줄이거나, 아예 필요할 때까지 불러오지 않는 것이다. 설치된 SDK는 파일이 1,600개, 34MB였다.

```bash
# 의존성 크기와 .js 파일 수를 본다
du -sh node_modules
find node_modules -name '*.js' | wc -l
# esbuild로 하나의 파일로 묶는다 (그냥, 그리고 minify까지)
npx esbuild handler.js --bundle --platform=node --target=node22 --outfile=dist/bundle.js
npx esbuild handler.js --bundle --minify --platform=node --target=node22 --outfile=dist/bundle.min.js
ls -l dist
```

```text
34M	node_modules
1600
-rw-r--r-- 1 root root 1461268 Oct 21 00:14 bundle.js
-rw-r--r-- 1 root root  657570 Oct 21 00:14 bundle.min.js
```

묶은 결과와 지연 불러오기(SDK를 쓰는 경로에서만 require)를 같은 방법으로 쟀다.

```bash
# 묶은 파일, minify한 파일, SDK를 쓸 때만 require하는 핸들러를 각각 잰다
node measure.js ./dist/bundle.js
node measure.js ./dist/bundle.min.js
node measure.js ./lazy.js
```


묶기만 해도 import가 120.8ms에서 94.1ms로 줄었다. 파일 1,600개를 찾고 여는 비용이 사라진 몫이다. 그런데 minify는 거의 효과가 없었다. 파일 크기는 절반이 됐지만 V8이 파싱하고 실행해야 하는 코드의 양은 그대로라서다. 가장 크게 줄인 건 지연 불러오기다. SDK를 쓰지 않는 요청 경로라면 init이 빈 핸들러와 같아진다. 대신 SDK가 필요한 첫 요청이 그 비용을 떠안는다. 비용을 없앤 게 아니라 옮긴 것이다.

묶음 안에 무엇이 들었는지는 esbuild의 metafile로 본다.

```bash
# 묶음을 만들며 입력 파일별 크기를 기록하고, 패키지별로 합쳐 본다
npx esbuild handler.js --bundle --minify --platform=node --metafile=dist/meta.json --outfile=dist/m.js
node summarize-meta.js dist/meta.json
```

```text
@aws-sdk/client-s3                 250.7 KB
@aws-sdk/client-sts                40.7 KB
@aws-sdk/client-sso-oidc           29.1 KB
fast-xml-parser                    25.1 KB
@aws-sdk/client-sso                20.6 KB
@smithy/smithy-client              18.2 KB
@smithy/node-http-handler          11.7 KB
@aws-sdk/middleware-sdk-s3         11.7 KB
```

S3 클라이언트 하나를 불렀는데 STS, SSO 클라이언트가 같이 들어왔다. 자격 증명을 여러 방식으로 찾는 기본 체인 때문이다. Lambda 안에서는 환경 변수로 자격 증명이 주어지니 쓰지 않는 코드다. 이런 걸 발견하는 게 metafile을 보는 이유다.

Node 런타임 이미지에 들어 있는 SDK를 쓰면 묶음은 작아지지만, 그 SDK도 init 때 불러오기는 해야 한다. 업로드 크기와 import 시간은 다른 문제다. 컨테이너 이미지로 배포할 때도 Lambda는 이미지 블록을 필요할 때 읽어 오는 방식이라 이미지 크기와 콜드 스타트가 정비례하지는 않는다. 그래도 베이스 이미지를 작게 두면 캐시에 잘 남는다.

```text
| stats count(*) as invocations,
        count(@initDuration) as coldStarts,
        avg(@initDuration) as avgInit,
        max(@initDuration) as maxInit
  by bin(1h)
```

결과가 "시간당 호출 3만 건 중 콜드 스타트 12건"이라면 평균에는 거의 영향이 없지만 p99, p99.9에는 그대로 찍힌다. [백분위 지연](/posts/percentile-latency)으로 봐야 보이는 문제다. 반대로 "새벽 6시 정각에 콜드 스타트 200건"이라면 스케줄 작업이나 배포가 한꺼번에 환경을 새로 만들게 한 것이다. 배포하면 기존 환경은 전부 버려지니, 배포 직후 지연이 튀는 것도 콜드 스타트다.

프로비저닝된 동시성(provisioned concurrency)은 정한 수만큼 환경을 미리 만들고 init까지 끝내 둔다. 그 수 안의 요청은 콜드 스타트가 없다. 함수 버전이나 별칭에만 걸 수 있고 `$LATEST`에는 걸 수 없다. 켜 둔 수만큼 쓰지 않아도 시간당 요금이 나간다. 사실상 서버를 예약하는 것과 같다. Application Auto Scaling으로 시간대별 일정이나 사용률 목표를 걸어 수를 바꿀 수 있다.

```bash
# prod 별칭에 환경 20개를 미리 만들어 둔다
aws lambda put-provisioned-concurrency-config \
  --function-name payment-webhook --qualifier prod \
  --provisioned-concurrent-executions 20
# 준비가 끝났는지 본다
aws lambda get-provisioned-concurrency-config \
  --function-name payment-webhook --qualifier prod
```

```text
{
    "RequestedProvisionedConcurrentExecutions": 20,
    "AvailableProvisionedConcurrentExecutions": 20,
    "AllocatedProvisionedConcurrentExecutions": 20,
    "Status": "READY",
    "LastModified": "2026-10-21T00:32:11+0000"
```

(계정 없이 실제 형식대로 쓴 예시다.) `Status`가 `IN_PROGRESS`인 동안은 아직 다 준비되지 않았다. 배포 파이프라인에서 새 버전에 별칭을 옮길 때 이 값이 READY가 되기 전에 옮기면 그 사이 요청이 콜드 스타트를 맞는다.

몇 개를 잡아야 하는지는 동시성 계산으로 나온다. 동시에 처리 중인 요청 수는 초당 요청 수 × 요청 하나의 처리 시간(초)이다. 리틀의 법칙이다. 여기에 순간 변동을 받을 여유를 더한다.

## SnapStart는 init이 끝난 순간을 사진으로 찍는다

SnapStart는 다른 접근이다. 함수 버전을 발행할 때 init을 한 번 돌리고, init이 끝난 microVM의 메모리와 디스크 상태를 스냅숏으로 저장한다. 콜드 스타트 때는 init을 다시 돌리지 않고 스냅숏을 복원한다. 자바처럼 클래스 로딩과 프레임워크 기동이 몇 초씩 걸리는 런타임에서 효과가 크다. 처음엔 자바만 지원했고 2024년 11월에 Python 3.12 이상과 .NET 8 이상으로 넓어졌다. 지원 런타임과 리전은 계속 바뀌니 쓰기 전에 문서를 확인한다.

함정은 "init이 한 번만 돈다"는 데서 나온다. init에서 만든 값이 복원된 모든 환경에 똑같이 복사된다. init에서 UUID 생성기의 시드를 정해 두면 여러 환경이 같은 ID를 낼 수 있다. init에서 연 DB 연결은 복원 시점엔 이미 끊겨 있다. 그래서 고유성이 필요한 값과 네트워크 연결은 핸들러 안이나 복원 훅(자바는 CRaC의 `afterRestore`)에서 만든다. 프로비저닝된 동시성과 같이 쓸 수 없고, 512MB를 넘는 임시 저장소나 EFS와도 같이 쓸 수 없다는 제약도 있다. 자바는 추가 요금이 없지만 Python과 .NET은 스냅숏 보관과 복원에 요금이 붙는다. 오래(14일) 호출되지 않은 버전은 스냅숏이 지워지고 다음 호출 때 다시 만들어진다.

## 콜드 스타트가 정말 문제인지부터 본다

모든 함수가 콜드 스타트를 걱정할 필요는 없다. AWS는 운영 환경 호출 중 콜드 스타트가 보통 1% 미만이라고 설명한다. 큐에서 메시지를 꺼내 처리하는 비동기 함수라면 0.5초 늦어도 아무도 모른다. 문제가 되는 건 사람이 기다리는 동기 요청, 그중에서도 p99를 약속한 API다.

현장에서 순서대로 확인할 것은 이렇다.

1. Logs Insights로 콜드 스타트 비율과 `Init Duration` 분포를 본다. 비율이 낮고 init이 짧으면 손대지 않는다.
2. init이 길면 무엇이 긴지 본다. 핸들러 바깥에 타이머 로그를 찍거나 X-Ray의 Initialization 구간을 본다. 대개 SDK·프레임워크 import, 비밀 값 조회, DB 연결이다.
3. 코드로 줄인다. 번들링, 쓰지 않는 의존성 제거, 무거운 모듈 지연 불러오기, 메모리 올리기(CPU가 같이 오른다)를 먼저 해 본다.
4. 그래도 안 되면 돈으로 산다. 트래픽 패턴이 예측되면 프로비저닝된 동시성을 일정에 맞춰 걸고, 자바·Python·.NET이면 SnapStart를 검토한다.
5. 그래도 수백 ms가 남고 트래픽이 꾸준하다면 서버리스가 이 일에 맞는지 다시 묻는다. 항상 떠 있는 컨테이너가 더 싸고 빠를 수 있다.

흔한 실수도 몇 가지 적어 둔다. init에서 하던 일을 "콜드 스타트를 줄이겠다"며 전부 핸들러 안으로 옮기면 매 요청마다 SDK 클라이언트와 연결을 새로 만들어 웜 요청이 느려진다. 재사용할 것은 바깥에, 무겁지만 드물게 쓰는 것만 지연시킨다. VPC에 붙인 함수는 예전(2019년 이전)에는 ENI를 만드느라 콜드 스타트가 10초씩 걸렸지만 지금은 공유 ENI 방식으로 바뀌어 그 비용이 거의 없다. 오래된 글을 보고 VPC를 피할 이유는 없다. 그리고 init은 10초 안에 끝나야 한다. 넘기면 init을 다시 시도하는데, 이때는 함수 타임아웃이 적용된다.

다른 플랫폼도 이름만 다르고 구조는 같다. Cloud Run은 최소 인스턴스 수(min instances)와 시작할 때 CPU를 더 주는 startup CPU boost가 있고, 한 인스턴스가 여러 요청을 동시에 받을 수 있어 콜드 스타트 횟수 자체가 적다. Azure Functions는 Premium 플랜에서 미리 데워 둔 인스턴스를 둔다.

## 결국 init을 언제, 누가 치르나

콜드 스타트는 실행 환경을 새로 만드는 비용이고, 그 대부분은 런타임 기동과 핸들러 바깥 코드다. 로컬에서 잰 것처럼 import 한 줄이 전체의 3분의 2를 차지할 수 있고, 번들링과 지연 불러오기로 크게 줄일 수 있다. 줄이고도 남는 비용은 프로비저닝된 동시성으로 미리 치르거나, SnapStart로 발행할 때 한 번만 치른다. 핑은 환경 하나만 살리니 몰리는 트래픽 앞에서는 거의 쓸모가 없다. 다음으로 볼 것은 콜드 스타트 말고 서버리스가 부딪히는 벽들이다. [서버리스의 한계](/posts/serverless-limits)와 [클라우드 비용 줄이기](/posts/cloud-cost-optimization)로 이어진다.

## 면접에서 나올 만한 질문

### 콜드 스타트가 무엇이고 언제 생기나요?

실행 환경을 새로 만들어야 할 때 드는 추가 지연이다. microVM을 띄우고 코드를 붙이고 런타임과 핸들러 바깥 코드를 실행하는 시간이 첫 요청에 더해진다. 한가하던 함수의 첫 요청뿐 아니라, 동시에 들어온 요청 수가 지금 따뜻한 환경 수를 넘을 때마다 생긴다. 배포 직후에도 모든 환경이 새로 만들어진다.

### 콜드 스타트 시간 중 개발자가 줄일 수 있는 부분은 어디인가요?

런타임 init과 함수 init이다. 특히 핸들러 바깥의 import, SDK 클라이언트 생성, 설정과 비밀 값 조회가 크다. 직접 재 보면 AWS SDK import 하나가 콜드 스타트의 3분의 2를 차지하기도 했다. 번들링으로 파일 수를 줄이고, 쓰지 않는 의존성을 빼고, 드물게 쓰는 무거운 모듈은 지연 불러오기를 하고, 메모리를 올려 CPU를 더 받는 순서로 손댄다.

### 그럼 init 코드를 전부 핸들러 안으로 옮기면 되지 않나요?

안 된다. 바깥 코드는 환경당 한 번만 돌고 이후 웜 요청에서 재사용된다. 핸들러 안으로 옮기면 매 요청마다 클라이언트와 연결을 새로 만들어 웜 요청 전체가 느려진다. 재사용할 것은 바깥에 두고, 일부 경로에서만 쓰는 무거운 것만 첫 사용 때 만들어 캐시한다.

### 프로비저닝된 동시성과 SnapStart는 어떻게 다른가요?

프로비저닝된 동시성은 정한 수만큼 환경을 미리 만들어 init까지 끝내 두는 것이고, 그 수 안에서는 콜드 스타트가 없다. 대신 쓰지 않아도 계속 돈이 나간다. SnapStart는 init 결과를 스냅숏으로 저장해 콜드 스타트 때 복원하는 방식이라 콜드 스타트를 없애지 않고 짧게 만든다. 둘은 함께 쓸 수 없고, SnapStart는 지원 런타임이 정해져 있다.

### SnapStart를 쓸 때 주의할 점은요?

init이 한 번만 돌고 그 상태가 모든 환경에 복사된다는 점이다. init에서 만든 난수 시드나 고유 ID가 여러 환경에서 겹칠 수 있고, init에서 연 네트워크 연결은 복원 시점에 끊겨 있으며, 임시 자격 증명도 만료됐을 수 있다. 고유해야 하는 값과 연결은 핸들러나 복원 훅에서 새로 만든다.

### 5분마다 핑을 보내 데우는 방식은 왜 권하지 않나요?

핑 하나는 환경 하나만 살리기 때문이다. 동시에 요청 10개가 몰리면 9개는 여전히 콜드 스타트를 맞는다. 시뮬레이션으로 돌려 봐도 9건이 콜드였고, 핑과 요청이 겹치면 10건 모두 콜드였다. 플랫폼이 환경을 언제 교체할지도 알 수 없고 핑이 지표를 흐린다. 확실히 막아야 하면 프로비저닝된 동시성을 쓴다.

### 프로비저닝된 동시성은 몇 개로 잡나요?

리틀의 법칙으로 동시 실행 수를 계산한다. 초당 요청 수에 요청 하나의 처리 시간(초)을 곱하고 여유를 더한다. 초당 100건, 200ms면 20개이고 20% 여유면 24개다. 처리 시간이 길수록 필요한 수가 커지니 함수를 빠르게 만드는 것이 비용도 줄인다. 시간대별로 트래픽이 다르면 일정 기반 스케일링을 건다.

### 콜드 스타트가 문제인지 어떻게 확인하나요?

REPORT 로그의 `Init Duration`이 콜드 스타트 표시다. Logs Insights에서 `count(@initDuration)`과 전체 호출 수를 시간대별로 세어 비율과 init 분포를 본다. 평균 Duration에는 init이 들어가지 않아 평균만 보면 놓치고, p99에서 드러난다. 비동기 처리 함수라면 비율이 높아도 손대지 않을 수 있다.
