글 위에 붙은 읽기 진행 막대를 만든다고 하자. 흔한 구현은 `scroll` 이벤트를 듣다가 `scrollY / (전체 높이 - 화면 높이)`를 계산해서 막대의 `transform`을 바꾸는 것이다. 데스크톱에서는 잘 돈다. 그런데 메인 스레드가 무거운 페이지에서는 손가락을 움직이는 동안 막대가 멈춰 있다가 한꺼번에 따라온다. 스크롤 자체는 부드러운데 막대만 늦는다.

CSS에는 이 계산을 통째로 브라우저에 넘기는 방법이 있다. 애니메이션의 시계를 "흐르는 시간" 대신 "스크롤 위치"로 바꾸는 것이다. 이 글은 스크롤 기반 애니메이션(scroll-driven animations)의 `scroll()`, `view()`, `animation-range`를 크로미움 141(Playwright, 헤드리스)에서 직접 재 보면서 정리한다. 지원하지 않는 브라우저를 위한 대비와, 막대가 처음부터 꽉 차 있는 흔한 실수도 다룬다.

스크롤 패턴 아홉 가지를 한 번에 훑은 글은 [스크롤 패턴 한눈에 보기](/posts/scroll-patterns-overview), 붙는 헤더와 스냅은 [sticky와 scroll-snap](/posts/css-sticky-scroll-snap)에 있다. 화면에 들어오는 순간 한 번 실행하는 쪽은 [IntersectionObserver](/posts/scroll-triggered-intersection-observer), 이 글의 도구로 장면을 짜는 쪽은 [패럴랙스와 스크롤리텔링](/posts/parallax-scrollytelling)에서 이어 간다.

## 시계 대신 스크롤 위치를 넣는다

보통의 CSS 애니메이션은 문서 타임라인(`DocumentTimeline`)을 따라 간다. 페이지가 열린 뒤 흐른 밀리초가 시계다. `animation: grow 1s`라고 쓰면 1초 동안 0%에서 100%로 간다.

스크롤 타임라인은 이 시계를 스크롤 위치로 바꾼다. 맨 위가 0%, 끝까지 내리면 100%다. 시간 단위가 없으니 `1s` 같은 길이도 의미가 없어지고, 스크롤을 멈추면 애니메이션도 그 자리에 멈춘다. 되돌리면 되감긴다.

<ScrollDemo patterns={["scroll-progress"]} caption="스크롤한 만큼 위쪽 막대가 차오른다. 스크롤을 멈추면 막대도 멈춘다" />

읽기 진행 막대를 CSS만으로 쓰면 이렇다.

```css
.progress {
  position: fixed;
  inset: 0 0 auto 0;
  height: 4px;
  background: royalblue;
  transform-origin: 0 50%;
  /* 순서 중요: animation 단축 속성을 먼저 쓴다 */
  animation: grow linear both;
  animation-timeline: scroll(root block);
}

@keyframes grow {
  from { transform: scaleX(0); }
  to { transform: scaleX(1); }
}
```

크로미움에서 화면 높이 800px, 스크롤할 수 있는 거리가 1800px인 페이지에 이 막대를 띄우고, 스크롤 위치를 바꿔 가며 계산된 `transform`과 애니메이션의 `currentTime`을 읽었다.

```js
const { chromium } = require("playwright-core");

(async () => {
  const browser = await chromium.launch({ executablePath: "/opt/pw-browsers/chromium" });
  const page = await browser.newPage({ viewport: { width: 400, height: 800 } });
  await page.setContent(`<!doctype html><style>/* 위의 .progress와 @keyframes */</style>
    <div class="progress"></div><div style="height:2600px"></div>`);
  for (const y of [0, 450, 900, 1800]) {
    await page.evaluate((y) => scrollTo(0, y), y);
    await page.waitForTimeout(100);
    console.log(await page.evaluate(() => {
      const bar = document.querySelector(".progress");
      const a = bar.getAnimations()[0];
      return JSON.stringify({ scrollY, transform: getComputedStyle(bar).transform,
        timeline: a.timeline.constructor.name, currentTime: String(a.currentTime) });
    }));
  }
  await browser.close();
})();
```

## 타임라인, 키프레임, 구간이 만나는 자리

스크롤 기반 애니메이션은 새로운 애니메이션 종류가 아니다. 원래 있던 CSS 애니메이션에서 시계만 갈아 끼운 것이다. 키프레임, 채우기 모드(`both`), 이징은 그대로 쓴다. 바뀌는 것은 "무엇이 진행률을 정하나"뿐이다.

타임라인은 두 종류다.

- `scroll()`은 스크롤 컨테이너 하나를 처음부터 끝까지 본다. 진행 막대, 페이지 전체에 걸친 배경 변화에 쓴다.
- `view()`는 요소 하나가 스크롤 컨테이너 안에서 얼마나 보이는지를 본다. 들어오면서 나타나기, 지나가는 동안 움직이기에 쓴다.

`scroll()`의 인자는 어떤 스크롤 컨테이너를 볼지와 어느 축을 볼지다. 기본값은 `scroll(nearest block)`이다. `nearest`는 가장 가까운 조상 스크롤 컨테이너, `root`는 문서 전체, `self`는 요소 자신이다. 축은 `block`(세로쓰기 문서가 아니면 세로), `inline`, `x`, `y` 중에서 고른다.

이름을 붙인 타임라인도 있다. 가로로 넘기는 갤러리 바깥의 점 표시가 갤러리 스크롤을 따라가야 한다면, 갤러리에 `scroll-timeline: --gallery x`라고 이름을 주고 점 쪽에서 `animation-timeline: --gallery`로 가져다 쓴다. 이름은 기본적으로 그 요소의 자손만 볼 수 있어서, 형제 요소가 쓰려면 공통 조상에 `timeline-scope: --gallery`를 둔다.

```css
.gallery {
  overflow-x: auto;
  scroll-timeline: --gallery x;   /* 이 스크롤에 이름을 붙인다 */
}

.carousel {
  timeline-scope: --gallery;      /* 형제인 .dots도 이 이름을 보게 한다 */
}

.dots .active {
  animation: move-dot linear both;
  animation-timeline: --gallery;
}
```

## 요소가 지나가는 구간을 잘라 쓰는 view()

카드가 화면 아래에서 들어오는 동안 서서히 나타나게 하고 싶다. `view()`는 카드의 위쪽 가장자리가 화면 아래쪽 가장자리에 닿는 순간부터, 카드의 아래쪽 가장자리가 화면 위쪽 가장자리를 빠져나가는 순간까지를 0%~100%로 잡는다. 이 전체를 `cover` 구간이라고 부른다.

들어오는 순간만 쓰려면 `animation-range`로 잘라 낸다.

## 구간 경계를 직접 계산해 보기

구간 이름만 외우면 헷갈린다. 경계가 어떤 식으로 나오는지 직접 써 보면 오래 간다. 아래 함수는 문서 기준 요소 위치(`top`), 요소 높이, 화면 높이, 구간 이름을 받아 지금 `scrollY`에서의 진행률을 0~1로 돌려준다. 테스트 값 중 앞의 다섯 개와 마지막 두 개는 위에서 크로미움으로 잰 상황 그대로다.

  // top: 문서 맨 위에서 요소 윗변까지 거리(px)
  // height: 요소 높이, vh: 화면(스크롤 컨테이너) 높이
  // range: "cover" | "contain" | "entry" | "exit"
  // cover 시작 = 요소 윗변이 화면 아랫변에 닿을 때
  // cover 끝   = 요소 아랫변이 화면 윗변에 닿을 때

  return 0;
}`}
  solution={`function rangeProgress(scrollY, top, height, vh, range) {
  const coverStart = top - vh;
  const coverEnd = top + height;
  const containStart = Math.min(top, top + height - vh);
  const containEnd = Math.max(top, top + height - vh);
  const ranges = {
    cover: [coverStart, coverEnd],
    contain: [containStart, containEnd],
    entry: [coverStart, containStart],
    exit: [containEnd, coverEnd],
  };
  const [start, end] = ranges[range];
  const p = (scrollY - start) / (end - start);
  return Math.round(Math.min(1, Math.max(0, p)) * 1000) / 1000;
}`}

  ]}
/>

마지막 테스트가 중요하다. 요소가 화면보다 크면 `top + height - vh`가 `top`보다 커져서 `contain`의 시작과 끝이 뒤바뀐다. `Math.min`과 `Math.max`로 감싼 이유가 그것이다. 이 경우는 [패럴랙스와 스크롤리텔링](/posts/parallax-scrollytelling)의 가로 스크롤 섹션에서 그대로 쓴다.

## 자바스크립트로 같은 타임라인 만들기

CSS로 표현하기 어려운 경우, 예를 들어 키프레임을 데이터에서 만들어야 하면 Web Animations API에 타임라인 객체를 넘긴다. `ScrollTimeline`과 `ViewTimeline` 생성자가 있다.

```js
const bar = document.querySelector(".progress");

// 문서 전체 스크롤을 시계로 쓰는 애니메이션. duration을 주지 않는다
const animation = bar.animate(
  { transform: ["scaleX(0)", "scaleX(1)"] },
  { fill: "both", timeline: new ScrollTimeline({ source: document.documentElement, axis: "block" }) },
);
```

스크롤할 거리가 2000px인 페이지에서 1000px을 내린 뒤 읽은 값이다.

```text
{"maxScroll":2000,"currentTime":"50%","scaleX":0.5,"duration":"100%"}
```

길이(`duration`)를 주지 않으면 계산된 길이가 `100%`로 나온다. 여기서 한 번 헛걸음을 했다. 처음 테스트 페이지에 `<!doctype html>`을 빼먹었더니 같은 코드에서 `currentTime`이 `null`이고 막대가 움직이지 않았다.

```text
doctype 없음 {"compatMode":"BackCompat","scrollingElement":"BODY","currentTime":"null"}
```
 doctype이 없으면 문서가 쿼크 모드로 열리고, 그때는 문서를 스크롤하는 요소(`document.scrollingElement`)가 `<html>`이 아니라 `<body>`가 된다. `source`에 스크롤하지 않는 `<html>`을 넘겼으니 타임라인이 비활성(inactive) 상태가 된 것이다. 생성자에 `source`를 넘기지 않으면 기본값이 `document.scrollingElement`라서 두 모드 모두 동작한다.

## 메인 스레드가 바빠도 움직이는 이유

처음 이야기로 돌아가 보자. `scroll` 리스너로 만든 막대가 늦게 따라오는 이유는 스크롤과 리스너가 서로 다른 스레드에서 돌기 때문이다. 크로미움은 스크롤을 합성 스레드(compositor)에서 처리한다. 화면은 그쪽에서 바로 움직이고, `scroll` 이벤트는 메인 스레드로 따로 보낸다. 메인 스레드가 긴 작업에 붙잡혀 있으면 이벤트는 기다리고, 막대도 기다린다.

```js
// 1) scroll 리스너: 스크롤마다 모든 카드의 위치를 재고 opacity를 쓴다
addEventListener("scroll", () => {
  for (const c of cards) {
    const r = c.getBoundingClientRect();
    c.style.opacity = Math.min(1, Math.max(0, (innerHeight - r.top) / r.height));
  }
}, { passive: true });

// 2) IntersectionObserver: 들어오면 클래스를 붙이고 관찰을 끝낸다 (CSS transition)
// 3) CSS: animation: r linear both; animation-timeline: view(); animation-range: entry 0% entry 100%;
```

```text
scroll-listener        scrollY 12000 | 콜백 100회 80.6ms | Layout 100회 20.6ms | Style 478회 6.1ms
intersection-observer  scrollY 12000 | 콜백 94회 7.0ms | Layout 93회 35.8ms | Style 368회 39.5ms
css-view-timeline      scrollY 12000 | 콜백 0회 0.0ms | Layout 0회 0.0ms | Style 100회 16.1ms
```

리스너 쪽은 스크롤 이벤트마다 평균 0.8ms를 자바스크립트에 썼다. 이 컨테이너의 CPU 기준이고, 느린 휴대폰이면 몇 배가 된다. CSS 쪽은 자바스크립트도 레이아웃도 0이다. `Style 100회`는 스크롤 위치가 바뀔 때마다 애니메이션 값을 다시 반영한 흔적이다. 가운데 IntersectionObserver는 사정이 다르다. 관찰자 자체는 거의 공짜이고, 레이아웃과 스타일 비용은 대부분 클래스를 붙여 transition을 시작한 쪽에서 나온다. 이건 [IntersectionObserver 글](/posts/scroll-triggered-intersection-observer)에서 따로 잘라 본다.

어떤 속성이 합성 단계에서 끝나는지, 레이아웃을 깨우는 속성이 왜 비싼지는 [애니메이션 성능과 접근성](/posts/animation-performance)에 정리해 두었다. 스크롤 타임라인도 같은 규칙을 따른다. `top`이나 `height`를 스크롤에 묶으면 메인 스레드에서 매 프레임 레이아웃을 다시 한다.

## 막대가 처음부터 꽉 차 있다

스크롤 기반 애니메이션에서 가장 흔한 증상은 "아무것도 안 움직인다"와 "처음부터 끝 상태로 보인다"다. 원인은 대개 아래 셋 중 하나다. 크로미움에서 하나씩 재현했다.

첫째, 선언 순서다. `animation` 단축 속성은 `animation-timeline`도 초기값 `auto`로 되돌린다. 타임라인을 먼저 쓰고 단축 속성을 뒤에 쓰면 타임라인이 지워진다.

```css
/* 틀림: 뒤의 animation이 animation-timeline을 auto로 덮는다 */
.bar { animation-timeline: scroll(); animation: grow linear both; }

/* 맞음 */
.bar { animation: grow linear both; animation-timeline: scroll(); }
```

```text
timeline 뒤에 shorthand  {"timeline":"auto","scale":"1.000","tl":"DocumentTimeline","ps":"finished"}
shorthand 뒤에 timeline  {"timeline":"scroll()","scale":"0.250","tl":"ScrollTimeline","ps":"running"}
duration 3s 줌          {"timeline":"scroll()","scale":"0.250","tl":"ScrollTimeline","ps":"running"}
```

틀린 쪽은 평범한 문서 타임라인 애니메이션이 되는데, 길이를 안 줬으니 0초 만에 끝나서(`finished`) `both` 때문에 끝 모습, 즉 꽉 찬 막대로 고정된다. 세 번째 줄은 반대 방향 확인이다. `3s`처럼 길이를 줘도 스크롤 타임라인에서는 무시되고 스크롤 위치대로 간다.

둘째, `scroll()`과 `view()`의 기본값 `nearest`는 가장 가까운 조상 스크롤 컨테이너를 찾는데, `overflow: hidden`도 스크롤 컨테이너다. 가로 넘침을 막으려고 바깥 래퍼에 흔히 거는 `overflow-x: hidden`이 바로 그것이다. 그 래퍼는 실제로는 스크롤되지 않으니 타임라인이 비활성이 된다.

```text
overflow-x:hidden 부모 + scroll() {"scrollY":1000,"timelineTime":"null","transform":"none"}
overflow-x:hidden 부모 + scroll(root) {"scrollY":1000,"timelineTime":"49.9002%","transform":"matrix(0.499002, 0, 0, 1, 0, 0)"}
```

타임라인 시간이 `null`이면 비활성이다. 키프레임이 아예 적용되지 않아서 `transform`이 `none`, 즉 원래 크기의 막대가 그대로 보인다. `scroll(root)` 쪽이 50%가 아니라 49.9%인 것은 막대 자신이 sticky로 문서 흐름에서 4px을 차지해 스크롤 거리가 조금 늘었기 때문이다. 고치는 방법은 `scroll(root)`처럼 컨테이너를 명시하거나, 이름 붙인 타임라인을 쓰거나, 래퍼의 `overflow: hidden`을 스크롤 컨테이너를 만들지 않는 `overflow: clip`으로 바꾸는 것이다. 같은 래퍼가 `position: sticky`도 망가뜨린다는 이야기는 [sticky와 scroll-snap](/posts/css-sticky-scroll-snap)에 있다.

셋째, 이징이다. 앞에서 봤듯 `linear`를 빼면 `ease`가 걸린다. 나타나기 효과에는 오히려 자연스러울 수 있지만, 진행 막대나 스크롤 양과 맞물려야 하는 위치 이동에는 어긋나 보인다.

## 지원하지 않는 브라우저를 위한 바닥

크롬과 엣지는 115(2023년 7월)부터 `animation-timeline`, `scroll()`, `view()`, `animation-range`를 기본으로 지원한다. 이 글의 크로미움 141에서 잰 값은 다음과 같다.

```js
({
  scroll: CSS.supports("animation-timeline: scroll()"),
  view: CSS.supports("animation-timeline: view()"),
  range: CSS.supports("animation-range: entry 0% cover 50%"),
  timelineScope: CSS.supports("timeline-scope: --a"),
  ScrollTimeline: typeof ScrollTimeline,
  ViewTimeline: typeof ViewTimeline,
  trigger: CSS.supports("animation-trigger: --t play-forwards"),
})
```

```text
{"scroll":true,"view":true,"range":true,"timelineScope":true,"ScrollTimeline":"function","ViewTimeline":"function","trigger":false}
```

사파리는 26(2025년 가을)에서 스크롤 기반 애니메이션을 넣었다고 WebKit이 발표했다. 파이어폭스는 내가 확인한 자료 기준으로 Nightly에서 설정 플래그를 켜야 동작했고 정식 버전 기본값은 꺼져 있었다. 이 부분은 빨리 바뀌니 쓰기 전에 MDN 호환성 표나 caniuse로 다시 확인한다. 마지막 줄 `animation-trigger`는 "스크롤 위치에 닿으면 시간 기반 애니메이션을 한 번 재생"하는 더 새로운 제안인데, 크로미움 141에서는 아직 `false`다.

지원 범위가 고르지 않으니 원칙은 하나다. 지원하지 않는 브라우저에서도 내용이 다 보여야 한다. 처음 상태를 `opacity: 0`으로 두는 코드를 `@supports` 바깥에 쓰면, 지원하지 않는 브라우저에서는 카드가 영원히 안 보인다.

```css
/* 바닥: 아무 효과 없이 내용이 그대로 보인다 */
.card { opacity: 1; }

/* 지원하는 브라우저에서만, 움직임을 원하는 사람에게만 효과를 얹는다 */
@supports (animation-timeline: view()) {
  @media (prefers-reduced-motion: no-preference) {
    .card {
      animation: reveal linear both;
      animation-timeline: view();
      animation-range: entry 0% entry 100%;
    }
  }
}
```

`prefers-reduced-motion`으로 감싸는 이유는 [애니메이션 성능과 접근성](/posts/animation-performance)에서 다뤘다. 스크롤에 묶인 움직임은 사용자가 스크롤하는 내내 이어지기 때문에, 움직임에 민감한 사람에게는 시간 기반 애니메이션보다 더 오래 불편할 수 있다. 진행 막대처럼 화면 끝에 붙은 작은 표시는 남겨도 되지만, 화면 전체가 움직이는 효과는 끈다.

React에서 쓸 때 따로 할 일은 거의 없다. 이 방식의 장점이 바로 상태(state)를 거치지 않는다는 것이다. `onScroll`에서 `setState`로 진행률을 저장하면 스크롤 이벤트마다 컴포넌트가 다시 렌더링되고, 처음 이야기의 늦게 따라오는 막대로 돌아간다. 진행률을 화면에 숫자로 보여 줘야 하는 경우처럼 정말 자바스크립트 값이 필요할 때만 리스너를 쓰고, 그때도 [디바운스와 스로틀](/posts/debounce-throttle)에서 본 것처럼 프레임 단위로 묶는다.

## 스크롤 타임라인을 고를 때와 피할 때

스크롤 타임라인은 "스크롤 위치와 연속적으로 비례하는 움직임"에 맞다. 진행 막대, 지나가는 동안의 패럴랙스, 헤더가 줄어드는 정도, 들어오는 정도에 맞춘 흐려짐이 여기에 든다. 되돌리면 되감기는 것이 자연스러운 경우다.

반대로 "어느 지점을 지나면 한 번 일어나는 일"에는 맞지 않는다. 이미지 지연 로딩, 다음 페이지 불러오기, 분석 이벤트 보내기, 한 번 나타나면 계속 보여야 하는 카드가 그렇다. 이런 일은 상태가 바뀌는 사건이라서 [IntersectionObserver](/posts/scroll-triggered-intersection-observer)가 맡는다. 스크롤 양에 따라 숫자를 계산해서 데이터로 써야 할 때도 자바스크립트가 필요하다.

한 가지 더, 스크롤 타임라인은 스크롤을 빼앗지 않는다. 휠을 가로채서 `preventDefault()`하고 대신 애니메이션을 돌리는 스크롤 재킹(scroll-jacking)과 다르다. 사용자가 내린 만큼만 움직이고, 키보드, 스크롤바, 화면 읽기 프로그램의 이동도 그대로 둔다. 그래서 같은 효과라면 스크롤 타임라인 쪽이 접근성 면에서도 안전하다.

스크롤과 비례하는 움직임은 CSS 타임라인에 맡기고 지원하지 않는 브라우저에서는 효과 없이 내용만 보이게 둔다. 한 번 일어나는 사건은 관찰자에게 맡긴다. 다음 글 [IntersectionObserver](/posts/scroll-triggered-intersection-observer)에서 그 관찰자를 재 본다.

## 면접에서 나올 만한 질문

### 스크롤 기반 애니메이션이 뭔가요?

CSS 애니메이션의 시계를 흐르는 시간 대신 스크롤 위치로 바꾼 것이다. `animation-timeline: scroll()`이면 스크롤 컨테이너의 처음과 끝이 0%와 100%가 되고, `view()`면 요소가 화면에 걸치기 시작해서 빠져나갈 때까지가 0%~100%다. 키프레임과 이징은 그대로 쓰고, 길이 대신 `animation-range`로 어느 구간을 쓸지 정한다.

### scroll 리스너로 만든 것과 무엇이 다른가요?

리스너는 메인 스레드에서 돌기 때문에 긴 작업이 있으면 화면보다 늦게 따라온다. 스크롤 타임라인은 브라우저가 스크롤 위치에서 진행률을 직접 계산하고, 크로미움은 transform·opacity 같은 속성이면 합성 스레드에서 처리한다. 측정해 보면 카드 300개 기준으로 리스너는 이벤트마다 약 0.8ms의 자바스크립트와 매번 레이아웃을 썼고, CSS 쪽은 둘 다 0이었다.

### cover, contain, entry, exit는 어떻게 다른가요?

`cover`는 요소가 걸치기 시작해서 완전히 빠질 때까지 전체다. `contain`은 요소가 화면 안에 완전히 들어와 있는 동안이고, 요소가 화면보다 크면 화면을 꽉 덮고 있는 동안이다. `entry`는 cover 시작부터 contain 시작까지, `exit`는 contain 끝부터 cover 끝까지다. 들어오면서 나타나기는 보통 `entry 0% entry 100%`나 `entry 0% cover 40%`처럼 쓴다.

### 막대가 처음부터 꽉 차 있으면 무엇부터 보나요?

계산된 `animation-timeline`이 `auto`인지 먼저 본다. 단축 속성 `animation`을 타임라인 뒤에 쓰면 타임라인이 초기화되고, 길이 0인 시간 애니메이션이 바로 끝나서 끝 모습으로 고정된다. 타임라인은 맞는데 `currentTime`이 `null`이면 `nearest`가 `overflow: hidden` 조상 같은 스크롤되지 않는 컨테이너를 잡은 것이다. `scroll(root)`나 이름 붙인 타임라인, `overflow: clip`으로 고친다.

### 지원하지 않는 브라우저는 어떻게 하나요?

효과 없이도 내용이 다 보이는 상태를 기본으로 두고, `@supports (animation-timeline: view())` 안에서만 애니메이션을 얹는다. 처음 상태를 `opacity: 0`으로 두는 코드를 바깥에 두면 지원하지 않는 브라우저에서 내용이 사라진다. 크롬·엣지는 115부터 지원하고, 사파리와 파이어폭스는 버전마다 상황이 달라서 배포 전에 호환성 표로 확인한다.

### IntersectionObserver와는 어떻게 나눠 쓰나요?

스크롤 양과 연속적으로 비례하고 되돌리면 되감겨도 되는 움직임은 스크롤 타임라인이다. 어느 지점을 지날 때 한 번 일어나는 사건, 즉 이미지 로딩, 다음 페이지 요청, 한 번 나타나고 유지되는 효과, 분석 이벤트는 IntersectionObserver다. 앞쪽은 상태가 없고 뒤쪽은 상태를 바꾼다는 차이로 기억하면 된다.

### 움직임 줄이기 설정을 켠 사용자는요?

`@media (prefers-reduced-motion: no-preference)` 안에서만 스크롤 효과를 켠다. 스크롤에 묶인 움직임은 스크롤하는 내내 이어지므로 시간 기반 애니메이션보다 더 오래 영향을 준다. 진행 막대처럼 작고 의미 있는 표시는 남기고, 화면 전체가 움직이거나 확대되는 효과는 끈다.
