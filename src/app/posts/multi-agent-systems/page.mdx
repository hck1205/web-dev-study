<EasyIntro>
  학교에서 모둠 숙제를 한다고 해 보자. 혼자 하면 자료를 찾고, 정리하고, 발표 자료까지 만들다가 무엇을 하던 중이었는지 헷갈리기 쉽다. 그래서 모둠장이 일을 나눠 준다. 한 친구는 역사를, 한 친구는 지리를, 한 친구는 그림을 맡는다.

  나눠 맡으면 각자 자기 일만 보면 되니 덜 헷갈리고, 동시에 하니까 빨리 끝난다. 대신 모둠장이 "무엇을 어디까지 해 와"라고 분명하게 말해 주지 않으면 두 친구가 같은 내용을 찾아오거나, 서로 "그건 네가 하는 거 아니야?" 하며 일을 미루기도 한다.

  모인 자료를 하나로 합치는 일도 모둠장 몫이다. 친구마다 쓴 말투와 숫자가 다르면 맞춰야 한다. 그리고 모둠 숙제는 혼자 할 때보다 전체적으로 드는 시간이 더 많다. 모두가 자기 몫의 시간을 쓰기 때문이다.

  인공지능도 똑같이 일을 나눠 맡길 수 있다. 이 글은 언제 나누면 좋고, 언제 혼자 하는 게 나은지를 다룬다.
</EasyIntro>

사내 업무 봇에 도구를 하나씩 붙이다 보니 서른 개가 됐다. 위키 검색, 티켓 조회, 배포 기록, 결제 조회, 환불 요청, 사용자 정보, 슬랙 보내기 같은 것들이다. 어느 날부터 "어제 배포 이후 결제 실패가 늘었나?"를 물으면 봇이 `search_wiki`를 먼저 부르고, 결제 실패 건수는 `get_payment`로 한 건씩 조회하려 든다. `get_payment_stats`라는 집계 도구가 따로 있는데도 그렇다.

도구가 늘면 모델이 매번 읽는 도구 설명이 길어지고, 이름과 설명이 비슷한 도구끼리 헷갈린다. 몇 개부터 흔들리는지는 모델과 도구 설명의 품질에 따라 달라서 정해진 숫자는 없다. 다만 증상은 늘 비슷하다. 엉뚱한 도구를 고르고, 필요 없는 도구를 부르고, 긴 대화 끝에서는 처음 받은 지시를 놓친다.

여기서 흔히 떠올리는 해법이 일을 나누는 것이다. 결제는 결제 에이전트가, 배포는 배포 에이전트가 맡고, 위에서 누군가 일을 나눠 주고 합친다. 이게 멀티 에이전트다. 그런데 나눈다고 늘 좋아지지는 않는다. 이 글은 어떤 모양으로 나누는지, 각 에이전트에 무엇을 넘기고 결과를 어떻게 합치는지, 토큰 비용이 왜 커지는지, 그리고 서로 일을 떠넘기다 끝나지 않는 실패를 따라간다.

에이전트 한 개가 도는 루프 자체는 [AI 코딩 에이전트는 어떻게 일하나](/posts/ai-coding-agents)와 [에이전틱 RAG](/posts/agentic-rag)에서 이미 봤으니 여기서는 그 루프가 여러 개 엮일 때만 본다. 직접 짤지 프레임워크를 쓸지는 [에이전트 프레임워크 비교](/posts/agent-frameworks-comparison)에서 다룬다.

## 일을 나누는 세 가지 모양

멀티 에이전트라는 말은 넓다. 실제로 쓰이는 구조는 크게 셋으로 나뉜다.

첫째는 오케스트레이터-워커다. 위에 있는 에이전트(오케스트레이터, 또는 리드 에이전트)가 질문을 받아 하위 작업으로 쪼개고, 하위 작업마다 워커 에이전트를 띄운다. 워커는 자기 작업만 하고 결과를 요약해 돌려준다. 오케스트레이터가 결과를 모아 최종 답을 쓴다. 워커끼리는 서로 말하지 않는다. Anthropic이 2025년 6월에 공개한 리서치 기능 설계 글이 이 구조였고, Claude Code의 서브에이전트도 같은 모양이다([Claude Code 확장](/posts/claude-code-extensions)에서 서브에이전트가 물려받는 것을 봤다).

둘째는 핸드오프다. 대화의 주도권 자체를 다른 에이전트에게 넘긴다. 고객 문의를 받은 분류 에이전트가 "환불이네" 하고 환불 에이전트에게 대화를 넘기면, 그때부터 사용자와 말하는 건 환불 에이전트다. 오케스트레이터처럼 결과를 받아 합치는 쪽이 없고, 바통을 넘기는 계주에 가깝다. OpenAI Agents SDK는 핸드오프를 `transfer_to_refund_agent` 같은 이름의 도구로 모델에게 보여 준다. 모델 입장에서는 도구를 하나 부르는 것과 같다.

셋째는 병렬로 조사한 뒤 합치기다. 같은 질문을 여러 에이전트가 다른 각도나 다른 출처로 동시에 조사하고, 마지막에 하나가 합친다. 오케스트레이터-워커의 특수한 경우인데, 하위 작업이 서로 겹치지 않게 나뉘는 대신 같은 질문을 다르게 보는 경우가 많다. 코드 리뷰를 보안, 성능, 테스트 관점의 에이전트 셋에게 동시에 맡기고 결과를 모으는 식이다.

이 셋 말고도 에이전트들이 공용 메모장(블랙보드)에 결과를 쓰고 서로 읽어 가며 일하는 구조, 에이전트끼리 자유롭게 대화하게 두는 그룹 채팅 구조도 있다. AutoGen 같은 프레임워크가 그룹 채팅을 지원한다. 다만 다음 발언자를 누가 정하는지가 흐려서 대화가 길어지기 쉽고, 실무에서는 결국 발언 순서를 정하는 관리자 에이전트를 두게 된다. 그러면 오케스트레이터-워커와 비슷해진다.

구조를 고르는 기준은 "누가 최종 답을 책임지나"다. 답을 한 곳에서 합쳐야 하면 오케스트레이터-워커, 분야마다 끝까지 책임지는 담당자가 따로 있으면 핸드오프가 맞다. 둘을 섞기도 한다. 핸드오프로 넘겨받은 환불 에이전트가 안에서 워커를 띄워 주문 조회와 정책 확인을 동시에 시킬 수 있다.

## 나누면 좋아지는 이유는 컨텍스트가 갈라지기 때문이다

나누면 왜 나아지는지부터 분명히 해 두자. 이유는 두 가지다.

하나는 컨텍스트가 갈라진다는 점이다. 워커 A는 결제 도구 다섯 개와 결제 관련 지시만 받는다. 배포 기록 검색 결과 수천 토큰이 A의 컨텍스트에 쌓이지 않는다. 도구 선택이 흔들리던 원인 두 가지(긴 도구 목록, 긴 대화)가 동시에 줄어든다. [Claude Code 컨텍스트 창](/posts/claude-code-context-window)에서 조사를 서브에이전트에게 맡기는 이유로 본 것과 같은 효과다.

다른 하나는 병렬성이다. 워커 셋이 동시에 돌면 걸리는 시간은 가장 느린 워커 하나만큼이다. 혼자서 하위 작업 셋을 차례로 하면 세 배가 걸린다.

나머지는 대부분 비용이다. 에이전트가 늘면 모델 호출이 늘고, 일을 나누고 합치는 단계가 추가되고, 에이전트 사이에서 정보가 빠지거나 왜곡될 자리가 생긴다. 그래서 "이 일이 정말 쪼개지나"와 "쪼갠 조각이 서로 얼마나 독립적인가"가 먼저다. 결제 지표와 배포 기록과 오류 로그는 서로 몰라도 각자 조사할 수 있다. 반면 함수 하나를 고치는 일을 "인터페이스 담당", "구현 담당"으로 나누면 두 에이전트가 서로 다른 가정을 하고 맞지 않는 조각을 만든다. Cognition이 2025년에 쓴 "Don't Build Multi-Agents"라는 글이 바로 이 점을 짚었다. 행동 하나하나에 암묵적인 결정이 들어 있는데, 쪼개진 에이전트는 서로의 결정을 모른다는 것이다.

## 워커에게 넘기는 브리프

오케스트레이터가 워커를 띄울 때 넘기는 글을 여기서는 브리프라고 부르겠다. 멀티 에이전트가 잘 도는지는 대부분 이 브리프에서 갈린다.

가장 흔한 실수는 너무 짧게 쓰는 것이다. "결제 실패를 조사해"라고만 넘기면 워커는 기간도, 기준도, 돌려줄 모양도 모른다. 어떤 워커는 지난 한 달을 보고, 어떤 워커는 어제 하루를 본다. 반대 실수는 오케스트레이터의 대화 전체를 통째로 넘기는 것이다. 그러면 컨텍스트를 나눈 이유가 사라지고 비용만 늘어난다(뒤에서 숫자로 본다).

Anthropic의 리서치 시스템 글은 초기 실패로 비슷한 장면을 적었다. 간단한 질문에 워커를 50개나 띄우고, 워커끼리 같은 검색을 반복하고, 작업 설명이 모호해서 서로 다른 해석으로 일했다고 한다. 고친 방법은 브리프에 목표, 돌려줄 형식, 쓸 도구와 출처, 작업의 경계를 분명히 적는 것이었다. 실제로 쓰는 브리프는 이런 모양이 된다.

```json
{
  "task_id": "inv-42/payment",
  "objective": "2026-10-23 14:00 배포 전후 6시간의 결제 실패율을 비교한다",
  "scope": {
    "window": ["2026-10-23T08:00:00+09:00", "2026-10-23T20:00:00+09:00"],
    "not_in_scope": "배포 내용 분석, 오류 로그 원인 분석(다른 워커가 맡는다)"
  },
  "tools": ["get_payment_stats", "list_payment_errors"],
  "return_format": {
    "before_rate": "number (0~1)",
    "after_rate": "number (0~1)",
    "top_error_codes": "array of {code, count}, 최대 5개",
    "evidence": "사용한 도구 호출과 인자"
  },
  "budget": { "max_tool_calls": 8 }
}
```

`not_in_scope`가 중요하다. 다른 워커가 맡은 일을 적어 두지 않으면 성실한 워커일수록 범위를 넓혀 남의 일까지 한다. `budget`은 질문 난이도에 맞춰 준다. 같은 글에서 Anthropic은 단순한 사실 확인은 에이전트 하나에 도구 호출 3~10번, 비교 질문은 워커 2~4개에 각각 10~15번처럼 규모 기준을 프롬프트에 넣었다고 했다. 정확한 숫자보다 "질문 크기에 맞춰 사람 수를 정하라"는 규칙을 오케스트레이터에게 주는 게 핵심이다.

워커가 쓰는 도구 목록을 브리프마다 좁혀 주는 것도 같은 맥락이다. 도구 서른 개 문제를 풀려고 나눴는데 워커마다 서른 개를 다 주면 나눈 의미가 없다.

브리프를 쓰는 건 오케스트레이터 모델이니, 결국 오케스트레이터의 시스템 프롬프트에 "브리프를 어떻게 쓰라"를 적어 둬야 한다. 내가 쓰는 틀은 대략 이렇다.

```text
너는 조사 작업을 나눠 맡기는 리드다. 직접 도구로 조사하지 않는다.

1. 질문 크기를 먼저 정한다.
   - 사실 하나 확인: 워커를 띄우지 말고 바로 답한다.
   - 두세 가지 비교: 워커 2~3개, 각자 도구 호출 8번 이하.
   - 넓은 조사: 워커 최대 5개. 그 이상이 필요하면 먼저 사용자에게 범위를 묻는다.
2. 워커마다 브리프를 JSON으로 쓴다: objective, scope.not_in_scope, tools, return_format, budget.
   not_in_scope에는 다른 워커가 맡은 일을 적는다.
3. 결과를 합칠 때
   - status가 ok가 아닌 조각은 답에 "확인하지 못했다"고 적는다.
   - 워커끼리 숫자가 다르면 evidence를 비교해 이유를 쓰거나, 추가 워커 하나를 띄운다.
   - 같은 브리프로 워커를 다시 띄우지 않는다. 다시 띄울 때는 무엇을 바꿨는지 적는다.
```

숫자는 서비스마다 다르게 정하면 된다. 중요한 건 "언제 나누지 않을지"를 첫 줄에 둔 점이다. 오케스트레이터에게 워커를 띄우는 도구를 주면 모델은 그 도구를 쓰고 싶어 한다. 간단한 질문에도 워커를 띄우는 습관은 프롬프트의 첫 규칙으로 막는 게 가장 싸다. 이 규칙이 잘 먹는지는 뒤에서 볼 추적의 "질문별 워커 수"로 확인한다.

## 결과를 합치는 자리

워커 셋이 돌아왔다. 이제 합쳐야 한다. 여기서 생기는 문제는 세 가지다.

첫째, 워커가 너무 많이 돌려준다. 검색 결과 원문을 그대로 붙여 돌려주면 오케스트레이터의 컨텍스트가 다시 커진다. 그래서 브리프의 `return_format`으로 요약된 모양을 강제하고, 원문이 꼭 필요하면 파일이나 저장소에 쓰고 경로만 돌려주게 한다. 워커의 출력을 다음 워커에게 넘길 때도 마찬가지다. 오케스트레이터를 거치며 요약이 한 번 더 되면 정보가 조금씩 빠진다. 전화 게임처럼 말이 바뀐다.

둘째, 워커끼리 말이 다르다. 결제 워커는 실패율이 "2.1%에서 3.4%로" 올랐다고 하는데, 오류 로그 워커는 "실패 건수는 비슷하다"고 한다. 둘 다 맞을 수 있다. 분모(결제 시도 수)가 배포 뒤에 줄었으면 건수는 그대로여도 비율이 오른다. 오케스트레이터에게는 이런 충돌을 그냥 평균 내지 말고, 근거(`evidence`)를 비교해서 왜 다른지 밝히거나 추가 조사를 시키라고 지시해야 한다. 근거 없이 숫자만 돌려받으면 이 판단을 할 수 없다. 브리프에 `evidence`를 넣은 이유다.

셋째, 합치는 쪽이 지어낸다. 워커 하나가 실패하거나 시간 초과로 빈손으로 돌아오면, 오케스트레이터 모델은 나머지 둘로 그럴듯한 답을 만들어 버리곤 한다. 워커 결과에 `status: "ok" | "partial" | "failed"`를 두고, 실패한 조각이 있으면 최종 답에 "오류 로그는 확인하지 못했다"를 반드시 적게 한다. 이건 프롬프트로만 부탁하지 말고 코드로 검사하는 편이 낫다. 실패한 워커가 있는데 최종 답에 그 사실이 없으면 다시 쓰게 하는 식이다.

## 워커를 띄우고 기다리는 코드

말로만 보면 감이 덜 오니 오케스트레이터의 뼈대를 코드로 짜 봤다. 워커는 브리프를 받아 결과를 돌려주는 비동기 함수이고, 여기서는 모델 대신 정해진 값을 늦게 돌려주는 스텁을 넣었다. 로그 워커는 일부러 5초가 걸리게 했다.

```js
const workers = {
  payment: async () => { await sleep(120); return { before_rate: 0.021, after_rate: 0.034 }; },
  deploy: async () => { await sleep(80); return { deploys: ["api@1.42.0"] }; },
  logs: async () => { await sleep(5000); return { top: [] }; }, // 너무 오래 걸린다
};

function withTimeout(promise, ms) {
  return Promise.race([
    promise,
    new Promise((_, reject) => setTimeout(() => reject(new Error(`timeout ${ms}ms`)), ms)),
  ]);
}

async function orchestrate(briefs, { timeoutMs }) {
  // 하나가 실패해도 나머지 결과는 받는다
  const settled = await Promise.allSettled(
    briefs.map((b) => withTimeout(workers[b.worker](b), timeoutMs)),
  );
  return settled.map((s, i) => ({
    task_id: briefs[i].task_id,
    status: s.status === "fulfilled" ? "ok" : "failed",
    ...(s.status === "fulfilled" ? { data: s.value } : { error: s.reason.message }),
  }));
}

// 합친 답이 실패한 조각을 숨기지 않았는지 코드로 검사한다
function checkMerged(answer, results) {
  const missing = results.filter((r) => r.status !== "ok" && !answer.includes(r.task_id));
  return missing.length === 0 ? "ok" : `rewrite: ${missing.map((r) => r.task_id).join(", ")} 실패를 밝히지 않았다`;
}
```

시간 상한 1초로 돌리고, 합친 답 두 개를 검사에 넣은 실제 출력이다.

```text
{"task_id":"inv-42/payment","status":"ok","data":{"before_rate":0.021,"after_rate":0.034}}
{"task_id":"inv-42/deploy","status":"ok","data":{"deploys":["api@1.42.0"]}}
{"task_id":"inv-42/logs","status":"failed","error":"timeout 1000ms"}
elapsed 1000 ms
rewrite: inv-42/logs 실패를 밝히지 않았다
ok
```

볼 곳은 세 군데다. `Promise.all`이 아니라 `Promise.allSettled`를 썼다. `Promise.all`이었다면 로그 워커 하나 때문에 이미 받은 결제·배포 결과까지 버렸을 것이다. 걸린 시간은 1초로, 가장 느린 워커(상한에 걸린 로그 워커)에 맞춰졌다. 병렬 실행의 시간은 늘 가장 느린 하나가 정한다. 그리고 첫 번째 답은 로그 조사가 실패했다는 말이 없어서 다시 쓰라는 판정을 받았다.

이 뼈대에는 빠진 것이 하나 있다. `Promise.race`로 시간 초과를 냈지만 로그 워커 자체는 멈추지 않고 뒤에서 계속 돈다. 실제 워커는 모델을 부르는 중이니 그대로 두면 토큰이 계속 나간다. 브리프와 함께 `AbortSignal`을 넘겨 모델 API 요청까지 끊어야 한다. 중지 신호를 모델 API까지 전하는 방법은 [LLM API를 서비스에 붙이기](/posts/llm-api-integration)에서 다뤘다.

합치는 단계에도 모델 호출이 든다. 워커 수가 많을수록 합칠 입력이 길어진다. 그래서 다음 이야기는 비용이다.

## 토큰은 더해지는 게 아니라 곱해진다

에이전트 루프는 호출할 때마다 지금까지의 대화 전체를 다시 보낸다. 그래서 같은 에이전트가 오래 돌수록 한 번 호출의 입력이 커지고, 전체 입력 토큰은 호출 수의 제곱에 가깝게 는다. 여기에 에이전트 수가 곱해진다.

감을 잡으려고 간단한 비용 모델을 Node 22로 계산해 봤다. 숫자는 설명용 가정이다. 시스템 프롬프트, 도구 정의 하나당 150토큰, 도구 결과 한 번에 900토큰씩 대화에 쌓인다고 놓고 입력 토큰만 셌다.

- 단일 에이전트: 시스템 1,500 + 도구 30개 정의 4,500 + 질문 200으로 시작한다. 하위 작업 셋을 차례로 하며 도구를 12번 부르고 마지막에 답을 쓴다. 호출 13번.
- 오케스트레이터-워커: 오케스트레이터는 도구 2개만 쥐고 계획 1번, 합치기 1번을 부른다. 워커 셋은 각자 시스템 800 + 도구 5개 + 브리프 300으로 시작해 도구 4번, 요약 1번을 부른다.

```text
single { calls: 13, inputTokens: 150800 } tool defs per call 4500
orch-plan { calls: 1, inputTokens: 1700 }
orch-merge { calls: 1, inputTokens: 3200 }
worker-1 { calls: 5, inputTokens: 18250 }
worker-2 { calls: 5, inputTokens: 18250 }
worker-3 { calls: 5, inputTokens: 18250 }
multi { calls: 17, inputTokens: 59650 } ratio 0.40
sequential steps single 13 multi 7
multi with full history { calls: 17, inputTokens: 149650 }
```

결과가 의외일 수 있다. 이 가정에서는 멀티 에이전트가 오히려 입력 토큰이 40% 수준이다. 호출 수는 13번에서 17번으로 늘었는데도 그렇다. 단일 에이전트는 하위 작업 셋의 도구 결과가 한 대화에 계속 쌓여서 13번째 호출에는 입력이 17,000토큰이 된다. 워커는 자기 결과만 쌓이니 다섯 번째 호출도 5,450토큰이다. 아래 그림에서 단일 에이전트의 호출마다 입력이 어떻게 커지는지 볼 수 있다.

```text

```

단일 에이전트의 2.7배다. 실제 서비스 숫자도 이쪽에 가깝다. Anthropic은 같은 글에서 에이전트가 일반 채팅보다 토큰을 약 4배, 멀티 에이전트는 약 15배 쓴다고 밝혔다. 그리고 그 비용을 치를 만한 일로 "가치가 높고, 병렬로 나뉘고, 한 컨텍스트에 다 안 들어가는 조사"를 꼽았다. 같은 글에는 리드 에이전트와 워커를 둔 구성이 내부 리서치 평가에서 단일 에이전트보다 90.2% 나은 점수를 냈다는 숫자도 있다. 나아지는 이유의 상당 부분은 결국 토큰을 더 많이 쓴 데 있었다고 그들 스스로 분석했다.

## 서로 넘기다 끝나지 않는 대화

핸드오프 구조에서 자주 보는 장애가 있다. 사용자가 "환불 받고 카드 변경도 하고 싶어요"라고 썼다. 분류 에이전트는 "환불"을 보고 환불 에이전트로 넘긴다. 환불 에이전트는 "카드 변경"이 자기 일이 아니라며 결제 에이전트로 넘긴다. 결제 에이전트는 "환불"이 보이니 다시 환불 에이전트로 넘긴다. 아무도 답하지 않는데 대화는 계속 오간다.

모델 판단을 규칙으로 흉내 낸 스텁으로 돌려 보면 이렇게 된다. 각 에이전트는 자기 일이 아닌 단어가 보이면 넘긴다.

```js
const agents = {
  triage: (t) => ({ handoff: t.includes("환불") ? "refund" : "billing" }),
  refund: (t) => t.includes("카드 변경") ? { handoff: "billing" } : { answer: "환불 접수" },
  billing: (t) => t.includes("환불") ? { handoff: "refund" } : { answer: "결제 수단 변경" },
};
```

```text
{"stop":"answered","answer":"환불 접수","hops":1,"path":"triage>refund"}
{"stop":"max_hops","hops":6,"path":"triage>refund>billing>refund>billing>refund>billing"}
{"stop":"repeat","hops":3,"path":"triage>refund>billing>refund"}
```

첫 줄은 "환불해 주세요"만 쓴 정상 사례다. 둘째 줄은 같은 문의를 넘김 횟수 6번 상한으로만 막았을 때다. 상한에 걸려 멈추긴 했지만 그동안 모델 호출을 여섯 번 했다. 상한이 없었다면 토큰 예산이나 타임아웃이 끝날 때까지 돈다. 셋째 줄은 "같은 문의로 같은 방향 넘김이 두 번째 나오면 멈춘다"는 반복 감지를 넣은 경우다. 세 번 만에 멈췄다. 아래 그림에서 다음을 누르면 대화가 어떻게 핑퐁을 치는지 보인다.

막는 방법은 겹으로 둔다. 넘김 횟수 상한은 마지막 안전망이다. 그 위에 같은 쌍의 반복을 감지하고, 근본적으로는 에이전트 지시를 "내 범위의 일은 먼저 끝내고, 남은 부분만 넘긴다"로 바꾼다. 요청이 여러 담당에 걸치면 핸드오프 대신 오케스트레이터가 조각을 나눠 주는 구조가 맞는 신호이기도 하다. 그리고 어느 경로든 결국 사람 상담원에게 넘기는 출구를 하나 둔다.

오케스트레이터-워커에도 비슷한 무한 루프가 있다. 오케스트레이터가 결과에 만족하지 못해 같은 워커를 같은 브리프로 다시 띄우는 경우다. 워커가 결정적으로 같은 실패를 하면 끝이 없다. 재시도할 때는 브리프의 무엇을 바꿨는지 기록하게 하고, 바뀐 것이 없으면 재시도를 막는다.

## 같은 일을 두 번 하는 워커

병렬 조사에서 흔한 낭비는 겹침이다. "결제 실패가 왜 늘었나"를 결제 워커와 로그 워커에게 따로 줬는데 둘 다 `list_payment_errors`를 같은 기간으로 부른다. 결과도 비슷하니 합칠 때 같은 내용이 두 번 들어간다.

겹침은 대부분 브리프에서 시작한다. 경계(`not_in_scope`)가 없거나, 하위 작업을 "관점"으로만 나누고 "자료"로는 나누지 않았을 때다. 고치는 순서는 이렇다.

- 브리프에 다른 워커가 맡은 일을 적는다. 앞의 브리프 예시처럼.
- 같은 도구 호출(도구 이름과 인자)이 이미 있었는지 공용 기록을 둔다. 워커가 도구를 부르기 전에 하네스가 기록을 보고, 같은 호출이 있으면 저장된 결과를 돌려준다. 모델에게 "중복하지 마"라고 부탁하는 것보다 확실하다.
- 쓰기 도구는 겹치면 안 된다. 같은 티켓에 두 워커가 댓글을 달거나, 같은 파일을 동시에 고치면 서로의 결과를 덮는다. 쓰기는 오케스트레이터 한 곳에서만 하거나, 워커마다 다른 대상을 배정한다. 코딩 에이전트라면 워커마다 다른 작업 폴더를 준다([Claude Code 병렬 세션](/posts/claude-code-parallel-and-scheduled)에서 worktree로 나눈 것처럼).

읽기 겹침은 돈만 버리지만 쓰기 겹침은 데이터를 망가뜨린다. 우선순위는 쓰기 쪽이다.

## 무엇이 어디서 틀렸는지 따라가기

단일 에이전트도 디버깅이 어렵지만 멀티 에이전트는 한 단계 더 어렵다. 최종 답이 틀렸을 때 오케스트레이터가 잘못 나눴는지, 워커가 잘못 조사했는지, 합치다가 틀렸는지를 알아야 하기 때문이다. 같은 입력을 다시 넣어도 모델 출력이 달라서 재현도 잘 안 된다.

그래서 처음부터 추적을 남긴다. 구조는 분산 시스템의 [분산 추적](/posts/distributed-tracing)과 같다. 사용자 요청 하나가 트레이스 하나이고, 에이전트 호출과 도구 호출이 그 안의 스팬이다. 워커 스팬은 오케스트레이터 스팬의 자식으로 단다.

```text
trace inv-42                                   total 41.2s  in 61,204 tok  out 3,880 tok
└─ orchestrator.plan                            2.1s
   ├─ worker payment   brief=inv-42/payment     11.8s  tools=4  status=ok
   ├─ worker deploy    brief=inv-42/deploy       9.4s  tools=3  status=ok
   ├─ worker logs      brief=inv-42/logs        30.6s  tools=8  status=partial (budget)
   └─ orchestrator.merge                         4.7s
```

이 트리는 설명용으로 만든 모양이다. 도구마다 화면은 다르지만, 남겨야 할 것은 같다. 스팬마다 받은 브리프 원문, 쓴 도구와 인자, 돌려준 결과 원문, 입력·출력 토큰, 걸린 시간, 끝난 이유(정상, 예산 초과, 오류)다. 이게 있으면 "로그 워커가 예산에 걸려 partial로 돌아왔는데 합친 답에 그 사실이 빠졌다" 같은 원인을 바로 짚는다. 에이전트 추적을 OpenTelemetry 형식으로 남기는 규약(GenAI semantic conventions)도 정리되는 중이고, LangSmith나 Langfuse 같은 도구가 이런 화면을 만들어 준다.

원문을 남기는 데는 대가가 있다. 브리프와 도구 결과에는 사용자 이름, 주문 번호, 결제 정보가 그대로 들어간다. 추적 저장소가 운영 DB보다 느슨하게 관리되면 그쪽이 새는 구멍이 된다. 저장하기 전에 개인정보를 가리고, 보관 기간을 정하고, 접근 권한을 운영 로그와 같은 수준으로 둔다.

워커가 쓴 도구 호출이 쓰기 작업이었다면 추적에 멱등 키도 남긴다. 재시도한 워커가 같은 환불을 두 번 요청했는지 나중에 가려낼 수 있어야 한다.

추적에서 먼저 볼 숫자는 단순하다. 워커 수, 워커별 도구 호출 수, 같은 도구·인자 호출이 몇 번 겹쳤나, 끝난 이유별 분포. 워커 수가 질문마다 들쭉날쭉하면 오케스트레이터의 규모 기준이 안 먹고 있다는 뜻이다. 그리고 평가 세트로 결과를 정기적으로 채점해야 프롬프트를 고쳤을 때 나아졌는지 알 수 있다. 채점 방법은 [LLM 평가](/posts/llm-evals)에 있다.

## 에이전트 하나로 충분한 신호

멀티 에이전트는 매력적이지만 처음부터 고를 구조는 아니다. 다음 신호가 보이면 에이전트 하나로 버티는 편이 낫다.

- 하위 작업이 서로의 결과에 기대서 순서대로만 할 수 있다. 병렬의 이득이 없고 넘김 비용만 남는다.
- 하위 작업이 같은 파일이나 같은 상태를 고친다. 코딩 작업 대부분이 여기에 들어간다.
- 질문 하나에 도구를 몇 번만 부르면 끝난다. 나누고 합치는 호출이 본 작업보다 비싸다.
- 도구가 많아서 헷갈리는 게 문제의 전부다. 도구 설명을 고치거나, 질문 종류에 따라 도구 일부만 보여 주는 라우팅으로 먼저 푼다. 에이전트를 나누지 않고도 된다.
- 응답 시간이 중요하고 비용 상한이 빠듯하다. 병렬로 줄인 시간보다 계획·합치기 단계가 더하는 시간이 클 수 있다.

반대로 이런 일은 나눌 가치가 있다. 서로 독립적인 출처를 넓게 조사해야 하고, 한 컨텍스트에 다 안 들어가며, 답의 가치가 토큰 비용보다 확실히 큰 일이다. 시장 조사, 여러 저장소에 걸친 영향 분석, 여러 관점의 코드 리뷰 같은 것들이다.

순서로 정리하면, 단일 에이전트로 만들고 → 도구 설명과 컨텍스트를 다듬고 → 그래도 컨텍스트가 넘치거나 독립적인 조사가 느려질 때 워커를 하나씩 떼어 낸다. 떼어 낼 때마다 평가 점수와 토큰 비용을 같이 본다. 점수는 그대로인데 비용만 늘었다면 되돌린다.

## 면접에서 나올 만한 질문

### 멀티 에이전트 시스템은 무엇이고, 왜 쓰나요?

여러 LLM 에이전트가 일을 나눠 맡는 구조다. 위에서 나누고 합치는 오케스트레이터-워커, 대화를 넘기는 핸드오프, 같은 질문을 병렬로 조사해 합치는 방식이 있다. 쓰는 이유는 둘이다. 에이전트마다 컨텍스트와 도구 목록이 작아져서 선택이 덜 흔들리고, 독립적인 하위 작업을 동시에 돌려 시간이 준다.

### 오케스트레이터-워커와 핸드오프는 어떻게 다른가요?

오케스트레이터-워커는 워커 결과가 다시 오케스트레이터로 돌아오고 오케스트레이터가 최종 답을 책임진다. 핸드오프는 대화 주도권 자체가 넘어가서 넘겨받은 에이전트가 사용자와 계속 대화한다. 답을 한곳에서 합쳐야 하면 앞쪽, 분야별로 끝까지 맡을 담당이 있으면 뒤쪽이 맞다. 요청 하나가 여러 담당에 걸치면 핸드오프는 핑퐁에 빠지기 쉽다.

### 워커 에이전트에게는 무엇을 넘겨야 하나요?

대화 전체가 아니라 브리프를 넘긴다. 목표, 범위와 다른 워커가 맡은 일, 쓸 도구, 돌려줄 형식, 호출 예산을 적는다. 너무 짧으면 워커마다 다르게 해석하고 범위를 넓혀 남의 일을 하고, 대화 전체를 넘기면 컨텍스트를 나눈 이득이 사라진다. 돌려줄 형식에 근거를 넣어야 합칠 때 충돌을 판단할 수 있다.

### 멀티 에이전트가 단일 에이전트보다 비싼 이유는 무엇인가요?

호출마다 대화 전체를 다시 보내는 구조에 에이전트 수가 곱해지고, 나누기와 합치기 호출이 더해지기 때문이다. Anthropic은 멀티 에이전트가 일반 채팅보다 약 15배 토큰을 쓴다고 밝혔다. 다만 컨텍스트가 잘 나뉘면 한 대화에 결과가 계속 쌓이는 단일 에이전트보다 쌀 수도 있다. 결국 워커 수와 워커가 넓게 찾는 정도, 넘기는 컨텍스트 크기가 비용을 정한다.

### 에이전트끼리 핸드오프하다 무한 루프에 빠지면 어떻게 막나요?

겹으로 막는다. 넘김 횟수 상한을 두고, 같은 요청으로 같은 방향 넘김이 반복되면 멈추게 하고, 에이전트 지시를 자기 범위는 먼저 처리하고 남은 것만 넘기게 바꾼다. 모두 실패하면 사람에게 넘기는 출구를 둔다. 여러 담당에 걸치는 요청이 자주 오면 구조를 오케스트레이터-워커로 바꾸는 게 맞는 신호다.

### 워커들이 같은 일을 중복하는 문제는 어떻게 줄이나요?

브리프에 다른 워커가 맡은 범위를 적고, 하네스가 도구 이름과 인자로 공용 호출 기록을 둬서 같은 호출은 저장된 결과로 돌려준다. 모델에게 부탁하는 것보다 코드로 막는 게 확실하다. 쓰기 도구는 겹치면 데이터를 망가뜨리므로 한 곳에서만 쓰거나 워커마다 대상을 나눈다.

### 멀티 에이전트 시스템은 어떻게 디버깅하나요?

요청 하나를 트레이스로, 에이전트와 도구 호출을 부모-자식 스팬으로 남긴다. 스팬마다 브리프 원문, 도구 인자와 결과, 토큰, 시간, 끝난 이유를 기록하면 나누기, 조사, 합치기 중 어디서 틀렸는지 짚을 수 있다. 출력이 확률적이라 재현이 어려우니 평가 세트로 정기 채점해 변경 전후를 비교한다.

### 언제 멀티 에이전트를 쓰지 말아야 하나요?

하위 작업이 순서대로만 가능하거나, 같은 파일과 상태를 고치거나, 도구 몇 번이면 끝나는 일이면 쓰지 않는다. 도구가 많아 헷갈리는 게 문제라면 도구 설명 개선이나 도구 라우팅으로 먼저 푼다. 단일 에이전트로 시작해 컨텍스트가 넘치거나 독립 조사가 느려질 때만 워커를 떼어 내고, 그때마다 평가 점수와 비용을 함께 본다.
