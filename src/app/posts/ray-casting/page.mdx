배달 앱에서 주소를 입력하면 "배달 가능 지역이 아닙니다"가 뜨기도 한다. 가게마다 배달 구역은 반경 몇 km 같은 원이 아니라 지도에 손으로 그린 다각형이다. 강을 건너면 안 되고, 큰길 건너편은 빼고, 아파트 단지 하나는 넣는다. 그러면 질문은 하나로 줄어든다. 손님의 좌표 하나가 이 다각형 안에 있나?

이 질문에 답하는 가장 흔한 방법이 레이 캐스팅(ray casting)이다. 점에서 한쪽 방향으로 광선(반직선)을 쏘아 다각형의 변을 몇 번 넘는지 센다. 홀수면 안, 짝수면 밖이다. 이 글에서는 그 원리와 꼭짓점·가로 변 같은 함정, 짝홀 규칙과 감는 수(winding number)의 차이, 지오펜싱에서 GPS 오차 때문에 생기는 문제, 구역이 수천 개일 때 빨리 찾는 법을 본다. 후반부에서는 같은 아이디어가 게임에서 쓰이는 모습, 빠른 총알의 충돌 판정과 울펜슈타인 3D 방식의 레이캐스터까지 직접 돌려 본다. 계산과 측정은 Node.js 22, DB 예제는 PostgreSQL 16.15로 했다.

이 주제의 다른 글: 위치를 문자열 칸으로 묶는 [지오해시](/posts/geohash), 데이터 밀도에 맞춰 칸을 나누는 [쿼드트리](/posts/quadtree).

## 광선을 쏘아 변을 넘은 횟수를 센다

원리는 직관적이다. 다각형 밖 아주 먼 곳은 확실히 밖이다. 점에서 그쪽으로 걸어가면서 변을 하나 넘을 때마다 안과 밖이 뒤바뀐다. 끝에 도착했을 때 밖이어야 하니, 넘은 횟수가 홀수면 출발점은 안이었고 짝수면 밖이었다. 이걸 짝홀 규칙(even-odd rule)이라고 한다.

## 코드는 짧고, 조건 하나가 전부다

이 판정은 W. Randolph Franklin이 공개한 PNPOLY라는 C 함수로 널리 알려졌고, 몇 줄짜리 반복문으로 끝난다. 변마다 두 가지만 확인한다.

1. 변의 두 끝 중 정확히 하나만 점의 높이 y보다 위에 있는가? `(yi > y) !== (yj > y)`
2. 그렇다면 그 변이 높이 y에서 지나는 x 좌표를 구해서, 점보다 오른쪽이면 넘은 것으로 친다.

넘을 때마다 `inside`를 뒤집으니 횟수를 따로 셀 필요도 없다. 위의 ㄷ자 구역에서 (90, 150)을 판정하면 이렇게 진행된다. 칸은 꼭짓점 번호로 적은 변이다(꼭짓점 0은 왼쪽 위에서 시작해 시계 방향).

## 꼭짓점을 지나면 한 번인가 두 번인가

광선이 꼭짓점을 정확히 지나면 문제가 생긴다. 그 꼭짓점에는 변이 두 개 붙어 있다. 둘 다 세면 한 번 넘은 걸 두 번으로 세고, 하나로 세면 스치기만 한 걸 넘었다고 센다. 좌표가 정수로 찍힌 지도나 같은 위도에 놓인 꼭짓점이 많은 데이터에서는 드문 일이 아니다.

PNPOLY의 첫 조건 `(yi > y) !== (yj > y)`가 이 문제를 한 번에 푼다. 각 변을 "아래 끝은 포함, 위 끝은 제외"한 반열린 구간으로 보는 것과 같다. 아래 그림에서 세 가지 경우를 확인해 보자.

꼭짓점을 지나 건너가는 경우는 붙은 두 변 중 하나만 조건을 만족해 1번이 되고, 스치는 경우는 둘 다 만족하지 않거나 둘 다 만족해 0번이나 2번이 된다. 어느 쪽이든 홀짝이 맞는다. 가로 변은 두 끝의 y가 같아서 조건을 만족할 수 없으니 저절로 빠진다. 나눗셈 `(yj - yi)`가 0이 되는 경우도 이 조건 덕분에 생기지 않는다.

점이 변 위에 정확히 있으면 어떻게 될까. 이건 규칙이 정해 주지 않는다. PNPOLY는 왼쪽·아래쪽(y가 작은 쪽) 변 위의 점을 안으로, 오른쪽·위쪽 변 위의 점을 밖으로 보는 식으로 한쪽에 몰아줄 뿐이다. 4×4 정사각형으로 돌려 보면 (0, 2)와 (2, 0)은 `true`, (4, 2)와 (2, 4)는 `false`가 나온다. 그래서 이웃한 두 구역이 변을 공유하면 경계 위의 점이 정확히 한 구역에만 속한다는 장점이 있다. 하지만 "경계도 안으로 친다"는 정책이 필요하다면 점과 각 변 사이 거리가 아주 작은지(예: 1e-9)를 먼저 따로 검사해야 한다. DB마다 정책도 다르다. PostgreSQL에서 직접 확인해 봤다.

```sql
-- 4×4 정사각형 안, 변 위, 꼭짓점 위, 밖
SELECT polygon '((0,0),(4,0),(4,4),(0,4))' @> point '(2,2)' AS inside,
       polygon '((0,0),(4,0),(4,4),(0,4))' @> point '(4,2)' AS on_edge,
       polygon '((0,0),(4,0),(4,4),(0,4))' @> point '(4,4)' AS on_vertex,
       polygon '((0,0),(4,0),(4,4),(0,4))' @> point '(5,2)' AS outside;
```

```text
 inside | on_edge | on_vertex | outside
--------+---------+-----------+---------
 t      | t       | t         | f
(1 row)
```

PostgreSQL의 기본 `polygon` 자료형은 경계를 안으로 친다. PostGIS는 함수마다 다르다. `ST_Contains`는 경계 위의 점을 포함하지 않고(false), `ST_Covers`와 `ST_Intersects`는 포함한다(true). 배달 구역 경계에 정확히 놓인 주소가 어느 가게에도 안 잡히는 문제가 생기면 이 차이부터 확인한다.

  caption="짝홀 규칙으로 점이 다각형 안인지 판정하기"
  functionName="pointInPolygon"
  initialCode={`// point = [x, y], polygon = [[x, y], ...] (마지막 꼭짓점은 첫 꼭짓점과 이어진다)
// 짝홀 규칙: 오른쪽으로 쏜 광선이 변을 홀수 번 넘으면 안이다
function pointInPolygon(point, polygon) {
  const [x, y] = point;
  let inside = false;
  for (let i = 0, j = polygon.length - 1; i < polygon.length; j = i++) {

감는 수(winding number)는 다각형의 변을 따라 한 바퀴 돌 때 점을 몇 바퀴 감는지다. 광선으로도 셀 수 있다. 광선을 넘는 변이 아래에서 위로 가면 +1, 위에서 아래로 가면 −1을 더한다. 보통 다각형의 안은 ±1, 밖은 0이고, 별의 가운데는 2다. 0이 아니면 안으로 치는 규칙을 0이 아닌 규칙(nonzero rule)이라고 한다.

```js
// 감는 수: 광선을 아래→위로 넘는 변은 +1, 위→아래는 −1
function windingNumber([x, y], poly) {
  let w = 0;
  for (let i = 0; i < poly.length; i++) {
    const [x1, y1] = poly[i], [x2, y2] = poly[(i + 1) % poly.length];
    const side = (x2 - x1) * (y - y1) - (x - x1) * (y2 - y1); // 점이 변의 왼쪽이면 양수
    if (y1 <= y && y2 > y && side > 0) w++;
    else if (y1 > y && y2 <= y && side < 0) w--;
  }
  return w;
}
```

같은 별 좌표로 돌리면 가운데 (180, 135)는 2, 꼭짓점 쪽 (180, 65)는 1, 밖 (330, 135)는 0이 나왔다. 짝홀 규칙으로는 가운데만 밖이다.

어느 규칙이 맞는지는 도메인이 정한다. 그림 쪽에서는 둘 다 쓴다. SVG의 `fill-rule`과 Canvas의 `isPointInPath(x, y, fillRule)`은 둘 다 기본값이 `nonzero`이고 `evenodd`를 고를 수 있다. 앞의 PostgreSQL `polygon @> point`는 같은 별의 가운데를 `t`로 답했다. 짝홀 규칙이 아니라는 뜻이다.

```sql
-- 위 그림의 별: 가운데와 꼭짓점 쪽
SELECT polygon '((180,25),(244.7,224),(75.4,101),(284.6,101),(115.3,224))' @> point '(180,135)' AS star_center,
       polygon '((180,25),(244.7,224),(75.4,101),(284.6,101),(115.3,224))' @> point '(180,65)' AS star_tip;
```

```text
 star_center | star_tip
-------------+----------
 t           | t
(1 row)
```

지도 데이터에서는 이런 다각형이 애초에 잘못된 데이터다. OGC 표준(Simple Features)은 변이 엇갈리는 폴리곤을 유효하지 않은 것으로 보고, PostGIS의 `ST_IsValid`는 `false`를 돌려준다. 손으로 그린 배달 구역이 실수로 8자로 꼬이면 짝홀 규칙에서는 꼬인 부분이 구멍이 되고, 감는 수에서는 겹친 부분이 두 번 칠해진다. 어느 쪽이든 의도와 다르니 저장할 때 유효성을 검사해 막는 편이 낫다.

구멍(hole)이 있는 구역, 예를 들어 공원은 빼고 그 둘레만 배달하는 구역은 짝홀 규칙이 자연스럽게 처리한다. 바깥 고리와 구멍 고리의 변을 모두 한 번에 세면, 구멍 안의 점은 넘은 횟수가 짝수가 되어 밖으로 나온다. GeoJSON(RFC 7946)은 폴리곤의 첫 고리를 바깥 경계, 나머지를 구멍으로 정하고 있다.

## 지도 위의 다각형에서 조심할 것

위도·경도를 그대로 x, y로 써도 레이 캐스팅은 동작한다. 배달 구역처럼 수 km 안쪽이면 평면으로 봐도 오차가 무시할 만하다. 몇 가지 경우만 따로 챙긴다.

- 경도 ±180을 가로지르는 구역(피지, 알래스카 서쪽 끝)은 경도가 179에서 −179로 뛰어서 변이 지구를 거꾸로 한 바퀴 돈다. 구역을 둘로 자르거나 경도를 0~360으로 옮겨 계산한다.
- 변이 수백 km로 길면 "두 점 사이의 직선"이 무엇인지가 달라진다. GeoJSON은 경도·위도 평면에서의 직선으로 정하고, PostGIS `geography`는 지구 표면의 최단 경로(대권)로 본다. 같은 좌표라도 판정이 달라질 수 있다.
- 꼭짓점 좌표를 저장할 때 소수점을 잘라 정수 그리드에 맞추면 광선이 꼭짓점을 지나는 일이 늘어난다. 반열린 규칙을 지키는 구현이면 괜찮지만, 직접 짠 코드라면 위 테스트를 꼭 돌려 본다.

## 구역이 만 개면 다 검사할 수 없다

판정 한 번은 싸다. 같은 Node.js에서 꼭짓점 수별로 재 보면 이렇다.

```text
one polygon, 8 vertices: 116 ns/test
one polygon, 64 vertices: 475 ns/test
one polygon, 512 vertices: 3269 ns/test
one polygon, 4096 vertices: 28122 ns/test
```

꼭짓점 수에 거의 정비례한다. 문제는 구역이 많을 때다. "이 주소를 배달하는 가게는 어디인가"는 구역 전부에 판정을 돌리는 질문이다. 20km × 20km 안에 꼭짓점 32개짜리 구역 1만 개를 뿌리고 무작위 주소 10만 개로 재 봤다.

```bash
# 전부 검사 / 경계 사각형으로 먼저 거르기 / 1km 격자 색인 + 경계 사각형
node zones.js
```

```text
zones 10000 x 32 vertices, queries 100000
brute force   : 6816.8 µs/query, PIP tests/query 10000, hits/query 1.74
bbox prefilter: 228.6 µs/query, PIP tests/query 3.14, hits/query 1.75
grid 1km+bbox : 6.18 µs/query, PIP tests/query 3.14, hits/query 1.75, build 11 ms
```

(전부 검사는 오래 걸려서 앞의 2,000개 주소로만 쟀다. 그래서 `hits/query`가 조금 다르다.)

1. 다각형마다 경계 사각형(bounding box)을 미리 구해 두고, 주소가 그 사각형 밖이면 레이 캐스팅을 하지 않는다. 판정 횟수가 1만 번에서 3.14번으로 줄고 시간은 30분의 1이 됐다. 사각형 비교는 숫자 네 개뿐이라 싸다.
2. 그래도 사각형 1만 개를 다 훑는다. 공간을 1km 격자로 나눠 칸마다 "이 칸에 걸친 구역 목록"을 만들어 두면, 주소의 칸 하나만 보면 된다. 6.18µs, 전부 검사보다 1,000배 넘게 빠르다.

격자 대신 [쿼드트리](/posts/quadtree)나 R-tree에 구역의 경계 사각형을 넣어도 된다. PostGIS의 GiST 인덱스가 하는 일이 정확히 이 순서다. 인덱스로 경계 사각형이 겹치는 후보를 뽑고(`&&`), 후보에만 정확한 판정을 한다. `EXPLAIN`에 인덱스 조건과 `Filter`가 따로 찍히는 이유다. 꼭짓점이 수천 개인 행정구역 경계라면 `ST_Subdivide`로 작은 조각으로 쪼개 저장해 두는 방법도 쓴다. 조각마다 경계 사각형이 작아져 거르기가 잘 듣고, 판정할 변도 줄어든다.

## 게임에서는 광선이 벽을 찾는다

같은 광선 아이디어는 게임에서 더 많이 쓰인다. 다만 질문이 "몇 번 넘나"에서 "처음 부딪히는 것이 무엇이고 얼마나 먼가"로 바뀐다. 시야(적이 플레이어를 볼 수 있나), 총알 판정, 마우스로 누른 물체 고르기가 모두 이 질문이다.

계산의 바탕은 선분과 선분의 교차다. 광선을 `P + t·r`, 벽을 `Q + u·s`로 놓고 두 식이 같아지는 t, u를 구한다. 2차원 외적 `cross(a, b) = a.x·b.y − a.y·b.x`를 쓰면 이렇다.

```text
t = cross(Q − P, s) / cross(r, s)
u = cross(Q − P, r) / cross(r, s)
0 ≤ t ≤ 1 이고 0 ≤ u ≤ 1 이면 교차, 교점은 P + t·r
cross(r, s) = 0 이면 평행 (겹치거나 만나지 않음)
```

광선이 여러 벽과 만나면 t가 가장 작은 것이 처음 부딪히는 벽이다. 이 계산이 꼭 필요한 대표적인 예가 빠른 총알이다.

## 면접에서 나올 만한 질문

### 점이 다각형 안에 있는지 어떻게 판정하나요?

점에서 한 방향으로 광선을 쏘아 다각형의 변을 넘는 횟수를 센다. 홀수면 안, 짝수면 밖이다. 변마다 "두 끝 중 하나만 점의 높이보다 위에 있는가"와 "그 변이 점의 높이에서 지나는 x가 점보다 오른쪽인가"를 보고, 맞으면 결과를 뒤집는다. 변 n개에 O(n)이고 오목한 다각형과 구멍이 있는 다각형도 처리한다.

### 광선이 꼭짓점을 정확히 지나면 어떻게 처리하나요?

변을 아래 끝 포함, 위 끝 제외의 반열린 구간으로 보는 조건 `(yi > y) !== (yj > y)` 하나로 처리한다. 꼭짓점을 지나 건너가는 경우는 붙은 두 변 중 하나만 세어 1번, 스치기만 하는 경우는 0번이나 2번이 되어 홀짝이 맞는다. 광선과 겹치는 가로 변은 조건을 만족할 수 없어 저절로 빠지고, 0으로 나누는 일도 없다.

### 점이 경계 위에 있으면 안인가요, 밖인가요?

짝홀 규칙 자체는 정하지 않고, 구현이 어느 한쪽으로 몰아준다. 경계 정책이 필요하면 점과 변 사이 거리를 따로 검사한다. DB마다 다르다. PostgreSQL `polygon @> point`는 경계를 안으로 치고, PostGIS `ST_Contains`는 경계 위의 점에 false, `ST_Covers`는 true를 준다. 이웃 구역이 변을 공유한다면 경계 점이 정확히 한 구역에 들어가도록 정책을 정해야 한다.

### 짝홀 규칙과 감는 수 규칙은 언제 결과가 다른가요?

변이 서로 엇갈리는 다각형에서 다르다. 별 모양의 가운데는 광선이 변을 두 번 넘어 짝홀 규칙으로는 밖이지만, 감는 수가 2라서 0이 아닌 규칙으로는 안이다. 단순 다각형에서는 두 규칙이 같다. SVG와 Canvas는 기본이 nonzero이고, 지도 데이터에서는 엇갈리는 폴리곤 자체를 유효하지 않은 데이터로 본다.

### 지오펜스에서 들어왔다 나갔다 알림이 계속 울립니다. 어떻게 고치나요?

GPS 오차 때문에 경계 근처에서 판정이 흔들리는 것이다. 상태를 바꾸려면 경계에서 일정 거리 이상 넘어와야 하는 히스테리시스를 두고, 필요하면 같은 판정이 몇 번 연속일 때만 바꾸는 조건과 GPS 정확도 값도 함께 본다. 시뮬레이션에서 판정만 쓰면 10분에 이벤트 95번, 15m 히스테리시스로 3번이었다. 알림은 상태가 바뀔 때만 한 번 보낸다.

### 배달 구역이 수만 개일 때 주소 하나의 담당 구역을 빨리 찾으려면?

모든 구역에 레이 캐스팅을 돌리지 않고, 경계 사각형으로 먼저 거른 뒤 후보에만 정확히 판정한다. 그 경계 사각형도 격자, 쿼드트리, R-tree 같은 공간 색인에 넣어 주소 근처 후보만 꺼낸다. 실험에서 구역 1만 개에 전부 검사가 6.8ms, 격자 색인과 사각형 거르기로 6µs였다. PostGIS GiST 인덱스도 같은 순서로 동작하고, 꼭짓점이 많은 경계는 잘게 쪼개 저장한다.

### 게임에서 빠른 총알이 벽을 뚫고 지나가는 문제는 왜 생기고 어떻게 막나요?

프레임마다 위치만 검사하면, 한 프레임 이동 거리가 벽 두께보다 클 때 벽 안에 있던 순간이 없어서 충돌을 놓친다. 이전 위치에서 현재 위치까지를 선분으로 보고 벽과 교차 검사를 하면 막을 수 있다. 교차의 매개변수 t가 가장 작은 벽이 처음 맞은 벽이다. 게임 엔진의 연속 충돌 감지와 레이캐스트 총알이 이 방식이다.

### 레이캐스터에서 물고기 눈 효과는 왜 생기나요?

화면 가장자리 광선은 비스듬히 나가서 같은 벽이라도 정면 광선보다 길다. 그 길이로 벽 높이를 정하면 평평한 벽이 가장자리에서 낮아져 휘어 보인다. 광선 길이 대신 카메라 평면에 수직인 거리, 즉 길이에 cos(각도)를 곱한 값을 쓰면 평평해진다. 정면 벡터와 카메라 평면 벡터로 광선 방향을 만들면 DDA가 그 수직 거리를 바로 준다.
