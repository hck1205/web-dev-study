<EasyIntro>
  내가 만든 프로그램 앞에 웹 서버 nginx를 세워 손님 요청을 대신 받게 했더니, 손님 주소가 전부 서버 자신으로 찍히고, 보안 주소로 왔는데 일반 주소로 돌려보내고, 배포할 때마다 몇 초씩 502 오류가 떴다.

  nginx는 식당의 홀 직원처럼 손님을 맞고 주문을 주방에 넘긴다. 그런데 주방에는 손님이 누구인지, 어느 문으로 들어왔는지가 저절로 전해지지 않아서, 직원이 주문서에 그 정보를 따로 적어 줘야 한다. 주방이 여러 곳이면 직원이 순서대로 또는 덜 바쁜 곳으로 나눠 주고, 대답이 없는 주방은 잠시 빼 둔다.

  알아 두면 좋은 점은 502와 504가 주방이 아니라 홀 직원이 만든 답이라는 것이다. 502는 주방과 말이 안 통했다는 뜻이고, 504는 정해진 시간 안에 음식이 안 나왔다는 뜻이다. 그래서 원인은 프로그램 기록이 아니라 nginx의 오류 기록에서 찾는다.
</EasyIntro>

Node로 만든 API 서버를 `127.0.0.1:3000`에 띄워 두고, 앞에 nginx를 세워 `https://example.com/api/`로 들어오는 요청을 넘기기로 했다. 검색해서 나온 `proxy_pass` 한 줄을 붙였더니 동작은 하는데 이상한 게 몇 가지 보인다. 앱 로그의 클라이언트 IP가 전부 `127.0.0.1`이고, 로그인 후 리다이렉트가 `http://`로 가고, 경로 앞의 `/api`가 붙었다 빠졌다 한다. 배포할 때마다 몇 초씩 `502 Bad Gateway`도 뜬다.

nginx를 앱 앞에 세우는 이유는 분명하다. TLS를 한곳에서 처리하고, 정적 파일은 nginx가 바로 내주고, 느린 클라이언트를 nginx가 대신 상대해서 앱 프로세스가 오래 붙잡히지 않게 하고, 앱이 여러 대가 되면 요청을 나눈다. 이 개념 자체는 [프록시와 리버스 프록시 글](/posts/proxy-reverse-proxy)에서 다뤘다. 이 글은 그걸 nginx 설정으로 옮길 때 실제로 부딪히는 것들, 즉 `proxy_pass`의 슬래시 규칙, 넘겨야 할 헤더, upstream과 로드 밸런싱, 502·504가 생기는 자리, WebSocket과 버퍼링, 업로드 크기 제한을 차례로 본다.

기준은 [앞 글](/posts/nginx-basics)과 같이 Ubuntu 24.04 LTS와 Ubuntu 저장소의 nginx 1.24다. 설정 파일 배치(`sites-available`·`sites-enabled`)와 `nginx -t && systemctl reload nginx` 순서는 앞 글에서 본 그대로 쓴다.

## proxy_pass 한 줄로 넘기기

먼저 앱이 서버 안에서 응답하는지부터 본다. 프록시 문제를 볼 때 nginx와 앱을 나눠서 확인하는 습관이 가장 시간을 아낀다.

```bash
# 앱이 3000을 듣고 있는지 확인 (127.0.0.1에만 열려 있어야 밖에서 직접 못 들어온다)
sudo ss -ltnp | grep 3000

# nginx를 거치지 않고 앱에 직접 요청
curl -i http://127.0.0.1:3000/api/health
```

```text
LISTEN 0      511        127.0.0.1:3000      0.0.0.0:*    users:(("node",pid=4120,fd=21))
```

앱이 `0.0.0.0:3000`으로 떠 있으면 방화벽이 열려 있는 한 밖에서 nginx를 건너뛰고 바로 들어올 수 있다. 앞단에서 거는 인증, 속도 제한, 로그가 모두 무의미해진다. Node라면 `server.listen(3000, "127.0.0.1")`처럼 루프백에만 묶는다.

가장 짧은 프록시 설정은 이렇다.

```nginx
# /etc/nginx/sites-available/app
server {
    listen 80;
    listen [::]:80;
    server_name example.com;

    # 정적 파일은 nginx가 직접
    root /var/www/app/public;

    # /api/ 로 시작하면 앱으로
    location /api/ {
        proxy_pass http://127.0.0.1:3000;
    }
}
```

```bash
# 사이트를 켜고 문법 검사 후 적용
sudo ln -s /etc/nginx/sites-available/app /etc/nginx/sites-enabled/app
sudo nginx -t && sudo systemctl reload nginx

# nginx를 거쳐 요청
curl -i -H "Host: example.com" http://127.0.0.1/api/health
```

이것만으로 요청은 간다. 하지만 이 상태의 nginx는 앱에게 꽤 많은 정보를 숨긴다. 기본값으로 nginx는 업스트림(뒤에 있는 앱 서버를 이렇게 부른다)에 보내는 `Host` 헤더를 `proxy_pass`에 적은 주소인 `127.0.0.1:3000`으로 바꾸고, `Connection: close`를 붙여 요청마다 새 TCP 연결을 맺는다. 앱 입장에서 출발지 IP는 언제나 nginx, 즉 `127.0.0.1`이다. 글머리의 증상 중 둘이 여기서 나온다.

## 끝 슬래시 하나가 경로를 바꾼다

`proxy_pass` 뒤 주소에 경로(URI)가 붙어 있느냐에 따라 nginx가 업스트림에 보내는 경로가 달라진다. 규칙은 하나다.

- 주소에 경로가 없으면(`http://127.0.0.1:3000`) 요청 경로를 그대로 보낸다.
- 주소에 경로가 있으면(`http://127.0.0.1:3000/` 처럼 슬래시 하나라도) location이 맞춘 부분을 그 경로로 바꿔서 보낸다.

슬래시 하나도 "경로"로 친다는 게 함정이다. `/api/users?page=2` 요청으로 보면 이렇게 된다.

| location | proxy_pass | 앱이 받는 경로 |
|---|---|---|
| `/api/` | `http://127.0.0.1:3000` | `/api/users?page=2` |
| `/api/` | `http://127.0.0.1:3000/` | `/users?page=2` |
| `/api/` | `http://127.0.0.1:3000/v1/` | `/v1/users?page=2` |
| `/api` | `http://127.0.0.1:3000/` | `//users?page=2` |
| `/api/` | `http://127.0.0.1:3000/v1` | `/v1users?page=2` |

앞의 세 줄이 의도대로 쓰는 모양이고, 뒤의 두 줄이 흔한 실수다. location과 proxy_pass의 끝 슬래시를 짝 맞추지 않으면 슬래시가 겹치거나 사라진다. 앱 라우터가 `/api/users`로 정의돼 있으면 첫 줄을, `/users`로 정의돼 있으면 둘째 줄을 쓴다. 쿼리 문자열은 어느 경우든 그대로 붙는다.

예외도 알아 둔다. 정규식 location(`location ~ ^/api/`)에서는 바꿀 "맞춘 부분"이 정해지지 않으니 `proxy_pass`에 경로를 쓸 수 없다. 쓰면 `nginx -t`가 이렇게 거부한다.

```text
nginx: [emerg] "proxy_pass" cannot have URI part in location given by regular expression, or inside named location, or inside "if" statement, or inside "limit_except" block in /etc/nginx/sites-enabled/app:12
```

그럴 땐 `rewrite ^/api/(.*)$ /$1 break;`로 경로를 먼저 바꾸고 경로 없는 `proxy_pass`를 쓴다. 또 `proxy_pass http://$backend;`처럼 변수를 쓰면 nginx는 경로를 바꾸지 않고, 변수 안에 경로가 있으면 그걸 요청 경로 전체로 쓴다. 변수로 호스트를 적을 때는 이름을 요청 때마다 풀어야 하니 `resolver`도 있어야 한다.

## 앱에게 진짜 손님 정보를 넘긴다

앱이 알아야 하는 건 네 가지다. 사용자가 친 도메인, 사용자의 IP, 거쳐 온 프록시들의 IP, 사용자가 쓴 프로토콜(http인지 https인지). nginx가 바꿔 버리는 걸 헤더로 다시 실어 보낸다.

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:3000;

    # 사용자가 요청한 도메인 그대로
    proxy_set_header Host              $host;
    # nginx가 본 클라이언트 IP 하나
    proxy_set_header X-Real-IP         $remote_addr;
    # 기존 X-Forwarded-For 뒤에 클라이언트 IP를 덧붙인 목록
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    # 사용자가 쓴 프로토콜 (http 또는 https)
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

`Host`가 틀리면 앱이 만드는 절대 URL, 가상 호스트 라우팅, 쿠키 도메인이 모두 틀어진다. `$host`는 요청의 Host 헤더(없으면 server_name)이고, 포트까지 그대로 넘기려면 `$http_host`를 쓴다.

`X-Forwarded-Proto`는 TLS를 nginx에서 끝내는 구성에서 꼭 필요하다. 사용자는 https로 들어왔지만 nginx와 앱 사이는 평문 http라서, 앱은 자기가 http로 서비스한다고 믿는다. 그러면 리다이렉트 `Location`을 `http://`로 만들고, `Secure` 쿠키를 안 붙이거나 아예 세션을 거부한다. 글머리의 http 리다이렉트가 이것이다.

`$proxy_add_x_forwarded_for`는 들어온 `X-Forwarded-For` 값 끝에 `, $remote_addr`를 붙인 값이다. 들어온 헤더가 없으면 `$remote_addr`만 된다. CDN이나 로드 밸런서를 여러 겹 지나면 왼쪽부터 원래 클라이언트, 지나온 프록시 순으로 쌓인다.

```text
X-Forwarded-For: 198.51.100.7, 203.0.113.50
```

여기서 보안 문제가 생긴다. 이 헤더의 왼쪽 값은 클라이언트가 마음대로 써서 보낼 수 있다. `curl -H "X-Forwarded-For: 1.2.3.4"`로 보내면 nginx는 그 뒤에 진짜 IP를 붙일 뿐이고, 앱이 맨 왼쪽 값을 믿으면 IP 기반 차단이나 속도 제한을 쉽게 피한다. 믿어도 되는 건 내가 운영하는 프록시가 붙인 오른쪽 값뿐이다. nginx가 맨 앞단(인터넷과 바로 닿는 자리)이라면 들어온 값을 버리고 덮어쓰는 게 안전하다.

```nginx
# nginx가 가장 바깥이라면: 클라이언트가 보낸 X-Forwarded-For는 버린다
proxy_set_header X-Forwarded-For $remote_addr;
```

앱 쪽에서는 "몇 단계 프록시를 믿을지"를 정한다. Express라면 `app.set("trust proxy", "loopback")`이 루프백에서 온 프록시만 믿고 그 프록시가 붙인 값으로 `req.ip`와 `req.protocol`을 정한다. 이 설정이 없으면 `req.ip`는 `127.0.0.1`, `req.protocol`은 `http`다. 반대로 `trust proxy`를 `true`로 두면 모든 값을 믿으니 앞의 위조에 그대로 당한다. 다른 프레임워크도 이름만 다르고 같은 설정이 있다(Django의 `SECURE_PROXY_SSL_HEADER`, Spring의 `server.forward-headers-strategy`).

nginx 앞에 또 로드 밸런서가 있으면 nginx의 `$remote_addr`가 로드 밸런서 IP가 된다. 이때는 nginx의 realip 모듈로 진짜 클라이언트 IP를 복원한다.

```nginx
# http 또는 server 컨텍스트: 이 대역에서 온 X-Forwarded-For만 믿는다
set_real_ip_from 10.0.0.0/16;
real_ip_header   X-Forwarded-For;
real_ip_recursive on;   # 오른쪽부터 믿는 대역을 건너뛰고 처음 나오는 IP를 클라이언트로
```

이 헤더 묶음은 location마다 반복되니 파일로 빼 둔다. 앞 글에서 본 대로 `proxy_set_header`는 안쪽 블록에 한 줄이라도 쓰면 바깥 것을 모두 잃으니, 각 location에서 include하는 편이 실수가 적다.

```nginx
# /etc/nginx/snippets/proxy-headers.conf
proxy_http_version 1.1;
proxy_set_header Connection        "";
proxy_set_header Host              $host;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

앞의 두 줄은 아래 keepalive에서 설명한다.

## upstream으로 서버 여럿에 나누기

앱을 한 대로 시작했다가 두 대, 세 대로 늘리면 `proxy_pass`에 주소 하나를 쓰는 대신 이름 붙은 서버 묶음을 만든다. 이게 `upstream` 블록이다. http 컨텍스트에 두고, `proxy_pass http://이름;`으로 쓴다.

```nginx
# /etc/nginx/conf.d/upstream-app.conf
upstream app {
    server 10.0.0.11:3000 weight=3 max_fails=3 fail_timeout=30s;
    server 10.0.0.12:3000 max_fails=3 fail_timeout=30s;
    server 10.0.0.13:3000 max_fails=3 fail_timeout=30s;
    server 10.0.0.20:3000 backup;

    keepalive 32;
}
```

```nginx
# 사이트 설정에서
location /api/ {
    proxy_pass http://app;
    include snippets/proxy-headers.conf;
}
```

아래 그림이 이 구성이다. 점이 흐르는 방향이 요청이다. backup은 평소엔 요청을 받지 않아서 점선으로 그렸다.

### 나누는 방법 고르기

아무것도 적지 않으면 가중 라운드 로빈이다. 차례로 돌리되 weight만큼 더 준다. nginx는 같은 서버로 몰아서 보내지 않고 고르게 섞는 방식(smooth weighted round-robin)을 쓴다. 서버마다 "현재 점수"를 두고, 요청이 올 때마다 모든 서버의 점수에 각자의 weight를 더한 뒤 점수가 가장 큰 서버를 고르고, 고른 서버의 점수에서 weight 합계를 뺀다. 위 설정(A=3, B=1, C=1, 합계 5)으로 요청 다섯 개를 보내 보면 아래처럼 된다. 칸은 서버이고, 아래 칩이 각 서버의 현재 점수다.

A A A B C처럼 몰아 주지 않고 A B A C A로 섞어서, 가중치가 큰 서버도 한꺼번에 몰리는 순간이 없다. 여러 방식을 같은 요청 흐름에 돌려 서버별 몫과 p99를 비교한 결과는 [로드 밸런싱 알고리즘 글](/posts/load-balancing-algorithms)에 있다.

다른 방법은 upstream 블록 맨 위에 한 줄로 적는다.

```nginx
upstream app {
    least_conn;                          # 지금 처리 중인 연결이 가장 적은 서버로
    # ip_hash;                           # 클라이언트 IP로 서버 고정
    # hash $request_uri consistent;      # 키(여기선 URL)로 서버 고정, 일관 해싱
    server 10.0.0.11:3000;
    server 10.0.0.12:3000;
}
```

라운드 로빈은 요청 하나하나의 처리 시간이 비슷할 때 잘 맞는다. 어떤 요청은 10ms, 어떤 요청은 5초가 걸리는 API라면 라운드 로빈은 느린 요청이 쌓인 서버에도 계속 차례를 준다. 이때 `least_conn`이 낫다. 지금 열려 있는 연결 수가 적은 서버를 고르니, 바쁜 서버를 자연스럽게 피한다. weight와 함께 쓸 수 있다.

`ip_hash`는 같은 클라이언트를 같은 서버로 보낸다. 세션을 서버 메모리에 두는 옛 앱을 옮길 때 쓰는데, IPv4는 앞의 세 옥텟(`198.51.100.x`)만 해시에 쓴다. 회사 하나가 NAT 뒤에서 같은 IP로 들어오면 그 회사 전체가 한 서버에 몰리고, 모바일 사용자는 IP가 바뀌면 세션을 잃는다. 근본적으로는 세션을 Redis 같은 공유 저장소로 빼서 아무 서버나 받아도 되게 만드는 게 맞다.

`hash 키 consistent`는 임의의 키로 서버를 고정한다. `consistent`를 붙이면 일관 해싱(ketama)이라서 서버 하나를 더하거나 빼도 대부분의 키는 원래 서버에 남는다. 붙이지 않으면 서버 수가 바뀔 때 거의 모든 키의 자리가 바뀐다. 서버마다 로컬 캐시를 두는 구성(같은 URL은 같은 캐시 서버로)에서 쓴다. 참고로 `backup` 서버는 `hash`, `ip_hash`, `random`과 함께 쓸 수 없다.

### 쓰러진 서버를 알아채는 법

오픈 소스 nginx는 서버에 주기적으로 찔러 보는 능동 헬스 체크가 없다(상용 NGINX Plus의 `health_check` 기능이다). 대신 실제 요청을 보내다 실패하는 걸 세는 수동 방식이다. `fail_timeout` 30초 안에 3번 실패하면 그 서버를 30초 동안 빼고, 30초가 지나면 요청 하나를 다시 보내 본다. 성공하면 복귀한다.

무엇을 실패로 치는지는 `proxy_next_upstream`이 정한다. 기본값은 `error timeout`이다. 연결 실패와 타임아웃만 실패고, 앱이 500을 돌려준 건 정상 응답으로 본다. 500을 낸 요청도 다른 서버로 넘기려면 `http_500`, `http_502` 같은 값을 더한다.

```nginx
location /api/ {
    proxy_pass http://app;
    include snippets/proxy-headers.conf;

    # 연결 실패, 타임아웃, 502·503이면 다음 서버로 한 번 더
    proxy_next_upstream error timeout http_502 http_503;
    proxy_next_upstream_tries 2;      # 최대 시도 횟수 (처음 포함)
    proxy_next_upstream_timeout 10s;  # 재시도에 쓸 총 시간
}
```

다음 서버로 넘기는 재시도에는 조심할 점이 있다. 요청을 이미 업스트림에 보낸 뒤에 실패했다면, nginx는 POST·PATCH처럼 멱등하지 않은 메서드는 다음 서버로 다시 보내지 않는다(1.9.13부터). 첫 서버가 결제를 처리하고 응답만 못 보냈을 수 있어서다. `non_idempotent`를 더하면 POST도 재시도하는데, 앱이 멱등성 키 같은 장치로 중복을 막고 있을 때만 켠다. 재시도 횟수에 상한이 없으면 서버 전체가 느려졌을 때 요청이 서버 수만큼 불어나 장애를 키우니 `tries`와 `timeout`으로 묶어 둔다.

upstream의 모든 서버가 빠지면 nginx는 backup으로 보내고, backup도 없으면 바로 502를 낸다. error.log에 `no live upstreams while connecting to upstream`이 찍힌다. 반대로 upstream에 서버가 하나뿐이면 `max_fails`와 `fail_timeout`이 무시되고 그 서버는 절대 빠지지 않는다. 빼 봐야 보낼 곳이 없기 때문이다.

### 업스트림 연결을 재사용하기

기본 설정의 nginx는 업스트림에 HTTP/1.0으로, 요청마다 `Connection: close`를 붙여 보낸다. 요청마다 TCP 연결을 새로 맺고 끊는다는 뜻이다. 같은 서버 안이면 비용이 작지만, 다른 서버로 가거나 업스트림이 TLS라면 핸드셰이크 비용이 매번 붙고, 초당 요청이 많으면 nginx 쪽에 TIME_WAIT 소켓이 쌓여 로컬 포트가 바닥나기도 한다. 연결을 재사용하려면 세 가지가 함께 있어야 한다.

```nginx
upstream app {
    server 10.0.0.11:3000;
    server 10.0.0.12:3000;
    keepalive 32;          # worker마다 놀고 있는 연결을 최대 32개까지 남겨 둔다
}

location /api/ {
    proxy_pass http://app;
    proxy_http_version 1.1;          # keepalive는 HTTP/1.1부터
    proxy_set_header Connection "";  # 기본값 close를 지운다
}
```

`keepalive 32`는 연결 수의 상한이 아니라, 일이 끝나고 놀고 있는 연결을 버리지 않고 남겨 둘 개수다. 바쁠 땐 이보다 많은 연결이 열린다. 하나라도 빠지면 연결은 재사용되지 않는다. 앞의 `snippets/proxy-headers.conf`에 두 줄을 넣어 둔 이유다.

keepalive를 켜면 생기는 대표적인 502가 있다. Node의 HTTP 서버는 놀고 있는 연결을 기본 5초(`server.keepAliveTimeout`) 뒤에 닫는다. nginx 쪽 업스트림 keepalive 유지 시간(`keepalive_timeout`, upstream 안, 기본 60초)이 더 길면, 앱이 막 닫은 연결에 nginx가 요청을 실어 보내는 순간이 생긴다. 간헐적으로 이런 로그가 찍힌다.

```text
2026/10/16 14:03:51 [error] 2315#2315: *8812 upstream prematurely closed connection while reading response header from upstream, client: 198.51.100.7, server: example.com, request: "GET /api/orders HTTP/1.1", upstream: "http://10.0.0.11:3000/api/orders", host: "example.com"
```

규칙은 "앱의 유지 시간이 nginx보다 길어야 한다"이다. nginx 쪽을 줄이거나 앱 쪽을 늘린다.

```nginx
upstream app {
    server 10.0.0.11:3000;
    keepalive 32;
    keepalive_timeout 4s;   # Node 기본 5초보다 짧게 (1.15.3부터 쓸 수 있다)
}
```

```js
// 또는 Node 쪽을 nginx보다 길게
server.keepAliveTimeout = 65_000;
server.headersTimeout = 66_000; // keepAliveTimeout보다 크게
```

## 502와 504가 나는 자리

상태 코드 자체의 뜻은 [HTTP 상태 코드 글](/posts/http-status-codes)에서 봤다. 프록시에서는 이 코드를 만드는 게 앱이 아니라 nginx다. 앱 로그를 아무리 뒤져도 안 나오는 이유다.

- 502 Bad Gateway: 업스트림과 대화가 안 됐다. 연결을 거부당했거나, 연결이 중간에 끊겼거나, 응답이 HTTP가 아니었다.
- 504 Gateway Timeout: 업스트림이 정해진 시간 안에 응답하지 않았다.
- 499: nginx 전용 코드로 응답을 보내기 전에 클라이언트가 먼저 끊었다는 뜻이다. access.log에만 찍히고 클라이언트는 받지 않는다. 업스트림이 느려서 사용자가 새로고침을 누르면 많이 보인다.

### 타임아웃 값 정하기

```nginx
location /api/ {
    proxy_pass http://app;
    include snippets/proxy-headers.conf;

    proxy_connect_timeout 3s;   # TCP 연결을 맺기까지 (기본 60s, 75s를 넘을 수 없다)
    proxy_send_timeout    30s;  # 요청을 보내는 중 두 번의 쓰기 사이 간격 (기본 60s)
    proxy_read_timeout    30s;  # 응답을 받는 중 두 번의 읽기 사이 간격 (기본 60s)
}

# 오래 걸리는 게 정상인 경로만 따로 늘린다
location /api/reports/ {
    proxy_pass http://app;
    include snippets/proxy-headers.conf;
    proxy_read_timeout 300s;
}
```

`proxy_connect_timeout`은 짧게 둔다. 같은 데이터센터 안이라면 연결은 밀리초 단위로 맺어진다. 3초 안에 안 되면 그 서버는 문제가 있는 것이고, 빨리 포기해야 다음 서버로 넘어갈 수 있다. 기본 60초를 그대로 두면 서버 하나가 응답 없이 사라졌을 때 요청마다 60초씩 붙잡힌다.

`proxy_read_timeout`은 응답 전체 시간이 아니라 "두 번 읽는 사이의 간격"이라는 걸 기억한다. 앱이 10초마다 조금씩 데이터를 보내면 10분짜리 응답도 끊기지 않는다. 그리고 504가 났다고 무작정 늘리면 안 된다. 사용자는 그렇게 오래 기다리지 않고, 기다리는 동안 앱 프로세스와 연결이 묶인다. 오래 걸리는 작업은 요청을 받으면 바로 202로 답하고 작업은 큐에서 처리하는 식으로 앱 구조를 바꾸는 게 맞는 경우가 많다. 앞단에 CDN이나 로드 밸런서가 있으면 그쪽 타임아웃이 더 짧을 수 있으니(클라우드 로드 밸런서는 보통 60초 안팎) 체인 전체에서 바깥이 안쪽보다 길도록 맞춘다.

## WebSocket은 연결을 바꿔 달라고 요청한다

WebSocket은 HTTP 요청으로 시작해서 `Upgrade: websocket` 헤더로 "이 연결을 WebSocket으로 바꾸자"고 요청한다. 서버가 `101 Switching Protocols`로 답하면 그 TCP 연결은 양방향 통로가 된다. 동작 원리는 [실시간 통신 글](/posts/realtime-communication)에서 다뤘다.

문제는 `Upgrade`와 `Connection`이 홉 바이 홉(hop-by-hop) 헤더라는 것이다. 연결 한 구간에서만 의미가 있는 헤더라서 프록시는 이걸 다음 구간으로 넘기지 않는다. nginx가 업스트림에 그냥 보내면 앱은 업그레이드 요청을 받지 못하고, 브라우저 콘솔에 `WebSocket connection to 'wss://...' failed`가 뜬다. 그래서 직접 실어 보낸다.

```nginx
# http 컨텍스트 (conf.d/websocket-map.conf 같은 파일)
# Upgrade 헤더가 있으면 "upgrade", 없으면 "close"
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
```

```nginx
# 사이트 설정
location /ws/ {
    proxy_pass http://app;
    proxy_http_version 1.1;                       # Upgrade는 HTTP/1.1에서만 된다
    proxy_set_header Upgrade    $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_set_header Host       $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

    proxy_read_timeout 1h;   # 아무 메시지 없이 60초가 지나면 끊기는 것을 막는다
}
```

`map`을 쓰는 이유는 같은 location에 일반 HTTP 요청도 섞여 올 수 있어서다. `Connection: upgrade`를 고정으로 박아 두면 일반 요청에도 업그레이드를 요청하는 셈이 된다.

업그레이드가 끝난 뒤의 연결에도 `proxy_read_timeout`이 적용된다. 기본 60초 동안 양쪽에서 메시지가 하나도 없으면 nginx가 연결을 끊는다. 채팅 앱에서 "1분 동안 조용하면 끊긴다"는 증상이 이것이다. 타임아웃을 늘리는 것과 함께, 앱이 20~30초마다 ping 프레임을 보내게 하는 쪽이 더 튼튼하다. 중간의 다른 장비(클라우드 로드 밸런서, 회사 프록시)도 조용한 연결을 끊기 때문이다.

연결이 오래 붙어 있으니 nginx reload 때 옛 worker가 그 연결이 끝날 때까지 남는다. 앞 글에서 본 `worker_shutdown_timeout`(예: `30s`)을 main 컨텍스트에 두면 그 시간 뒤에 옛 연결을 정리한다. 클라이언트가 끊겼을 때 다시 붙는 로직이 있어야 하는 이유다. 연결 수도 계산에 넣는다. WebSocket 하나가 클라이언트 쪽 하나, 업스트림 쪽 하나로 연결 두 개를 계속 차지하니 `worker_connections`를 넉넉히 잡는다.

## 버퍼링은 켜 두고, 흘려보낼 때만 끈다

nginx는 기본적으로 업스트림의 응답을 버퍼에 받아 둔다(`proxy_buffering on`). 앱은 응답을 nginx에 빠르게 넘기고 바로 다음 요청을 처리하고, 느린 휴대폰 회선으로 그걸 천천히 보내는 일은 nginx가 맡는다. 앱 프로세스 수가 적은 구성(Node, Python의 워커 몇 개)에서 이게 큰 차이를 만든다. 느린 클라이언트 몇 명이 앱 워커를 붙잡아 다른 요청이 줄 서는 일을 막아 준다.

응답이 메모리 버퍼(`proxy_buffers`, 기본 8개 × 4k 또는 8k)보다 크면 임시 파일에 쓴다. 큰 다운로드가 많으면 이런 경고가 쌓인다.

```text
2026/10/16 15:20:44 [warn] 2315#2315: *10233 an upstream response is buffered to a temporary file /var/lib/nginx/proxy/3/00/0000000003 while reading upstream, client: 198.51.100.7, server: example.com, request: "GET /api/export.csv HTTP/1.1", upstream: "http://10.0.0.11:3000/api/export.csv", host: "example.com"
```

경고일 뿐이지만 디스크 I/O가 늘어난다. 큰 응답이 흔한 경로라면 `proxy_buffers 16 16k;`처럼 버퍼를 늘리거나, 아주 큰 파일은 앱이 `X-Accel-Redirect` 헤더로 nginx에게 파일 경로만 알려 주고 nginx가 디스크에서 직접 보내게 한다.

반대로 버퍼링이 방해가 되는 경우가 있다. Server-Sent Events나 LLM 응답 스트리밍처럼 앱이 조금씩 흘려보내는 응답이다. 버퍼링이 켜져 있으면 nginx가 버퍼가 찰 때까지 모아서 보내니, 브라우저에는 몇 초 동안 아무것도 안 오다가 한꺼번에 쏟아진다. 그 경로만 끈다.

```nginx
location /api/stream/ {
    proxy_pass http://app;
    include snippets/proxy-headers.conf;

    proxy_buffering off;      # 받는 즉시 클라이언트로
    proxy_cache off;
    proxy_read_timeout 1h;    # 이벤트 사이가 길 수 있다
    gzip off;                 # 압축 모듈도 모아서 보내려 한다
}
```

nginx 설정을 못 고치는 환경이라면 앱이 응답 헤더에 `X-Accel-Buffering: no`를 실어 보내도 그 응답만 버퍼링이 꺼진다. 버퍼링을 전역으로 끄면 위에서 말한 느린 클라이언트 보호가 사라지니 필요한 경로에만 쓴다.

## 업로드는 1MB에서 막힌다

nginx는 요청 본문 크기를 기본 1MB(`client_max_body_size 1m`)로 제한한다. 프로필 사진을 올리는데 일부 사용자만 실패한다면 이 값부터 본다. 넘으면 nginx가 앱에 보내지도 않고 413을 돌려준다.

```text
2026/10/16 15:42:10 [error] 2316#2316: *10410 client intended to send too large body: 5242880 bytes, client: 198.51.100.7, server: example.com, request: "POST /api/upload HTTP/1.1", host: "example.com"
```

브라우저는 `413 Request Entity Too Large` 제목의 nginx 기본 HTML 페이지를 받는다. 프런트엔드가 JSON을 기대하고 있으면 파싱 에러로만 보여서 원인을 놓치기 쉽다. 업로드 경로에서만 늘린다.

```nginx
location /api/upload {
    proxy_pass http://app;
    include snippets/proxy-headers.conf;

    client_max_body_size 50m;     # 이 경로에서만 50MB까지
    proxy_request_buffering off;  # 다 받은 뒤 넘기지 않고 받는 대로 앱에 흘려보낸다
    proxy_read_timeout 120s;
}
```

`proxy_request_buffering`은 기본으로 켜져 있어서 nginx가 본문 전체를 받아(크면 임시 파일에) 둔 뒤 앱에 넘긴다. 앱이 느린 업로드에 묶이지 않는 장점이 있고, 대신 큰 파일은 nginx 디스크를 한 번 거친다. 끄면 앱이 바로 받지만, 실패했을 때 nginx가 다른 서버로 재시도할 수 없다. 이미 본문 일부를 보냈기 때문이다. 전역 값을 크게 올리는 건 피한다. 아무 경로에나 큰 본문을 보내 디스크와 대역폭을 쓰게 하는 공격이 쉬워진다.

설정을 바꿨으면 실제로 확인한다.

```bash
# 문법 검사 후 적용
sudo nginx -t && sudo systemctl reload nginx

# 5MB 파일을 만들어 업로드 경로로 보낸다 (413이 아니면 통과)
head -c 5242880 /dev/urandom > /tmp/5m.bin
curl -s -o /dev/null -w "%{http_code}\n" -H "Host: example.com" \
  -F "file=@/tmp/5m.bin" http://127.0.0.1/api/upload

# 앱이 받은 헤더를 확인 (앱에 헤더를 그대로 돌려주는 디버그 경로가 있다면)
curl -s -H "Host: example.com" http://127.0.0.1/api/debug/headers
```

문제가 생기면 앞 글의 순서대로 되돌린다. 백업한 설정을 풀거나, git으로 관리 중이라면 `git checkout`으로 되돌린 뒤 `nginx -t && systemctl reload nginx`다.

## 앞에 서서 대신 받아 주는 자리

nginx 리버스 프록시는 클라이언트 대신 요청을 받아 업스트림에 넘기는 자리에 선다. 그 자리에서 경로를 바꾸고(`proxy_pass`의 슬래시), 잃어버린 손님 정보를 헤더로 되살리고(`Host`, `X-Forwarded-*`), 서버 여럿에 나누고(upstream, 실패한 서버 빼기), 연결을 재사용하고(keepalive), 느린 쪽을 대신 상대한다(버퍼링). 502와 504는 그 자리에서 nginx가 만드는 코드라서 앱 로그가 아니라 nginx error.log에서 원인을 찾는다. 다음 글에서는 이 앞단에 [HTTPS와 캐시, 속도 제한](/posts/nginx-https-performance)을 얹는다. 여러 서비스의 인증·라우팅을 한곳에 모으는 더 큰 그림은 [게이트웨이 글](/posts/gateway)에서 볼 수 있다.

## 면접에서 나올 만한 질문

### 앱 서버 앞에 nginx를 리버스 프록시로 두는 이유는 무엇인가요?

TLS 종료, 정적 파일 서빙, 로드 밸런싱, 압축·캐시·속도 제한 같은 공통 기능을 앱 밖 한곳에서 처리하려고 둔다. 버퍼링 덕분에 느린 클라이언트를 nginx가 대신 상대해서 적은 수의 앱 워커가 오래 묶이지 않는다. 앱은 루프백이나 내부망에만 열어 두고 외부 노출을 nginx로 줄이는 보안 효과도 있다.

### proxy_pass 끝에 슬래시를 붙이면 무엇이 달라지나요?

`proxy_pass`에 경로가 없으면 요청 경로를 그대로 넘기고, 슬래시 하나라도 경로가 있으면 location이 맞춘 부분을 그 경로로 바꾼다. `location /api/`에서 `http://app`이면 `/api/users`, `http://app/`이면 `/users`가 간다. location과 슬래시 짝이 안 맞으면 `//users`나 `/v1users`처럼 깨지고, 정규식 location에서는 경로를 붙일 수 없다.

### X-Forwarded-For는 왜 필요하고, 그대로 믿으면 어떤 문제가 있나요?

프록시를 거치면 앱이 보는 출발지 IP가 프록시 주소가 되니, 원래 클라이언트 IP를 헤더로 넘겨야 한다. 그런데 왼쪽 값은 클라이언트가 위조할 수 있어서 맨 왼쪽을 믿으면 IP 차단이나 속도 제한을 피할 수 있다. 앱은 신뢰하는 프록시 수만큼만 오른쪽에서 읽도록 설정하고(Express의 trust proxy), nginx가 가장 바깥이면 들어온 값을 `$remote_addr`로 덮어쓴다.

### least_conn과 ip_hash는 언제 쓰나요?

요청마다 처리 시간 차이가 크면 지금 연결이 가장 적은 서버를 고르는 `least_conn`이 라운드 로빈보다 부하를 고르게 나눈다. `ip_hash`는 같은 클라이언트를 같은 서버로 보내 서버 메모리 세션을 유지하려 할 때 쓰지만, NAT 뒤 사용자 쏠림과 IP 변경 시 세션 손실이 있어서 세션을 공유 저장소로 빼는 게 근본 해결이다. 캐시 지역성이 중요하면 `hash $request_uri consistent`로 서버 증감에도 키 대부분이 제자리에 남게 한다.

### 502와 504는 어떻게 다르고, 각각 어디부터 보나요?

502는 업스트림과 대화가 안 된 경우로 연결 거부, 중간 끊김, 잘못된 응답이 원인이고, 504는 업스트림이 `proxy_read_timeout` 안에 응답하지 않은 경우다. 둘 다 nginx가 만드는 코드라 앱 로그가 아니라 nginx error.log의 `Connection refused`, `upstream timed out`, `no live upstreams` 같은 문구로 원인을 가른다. 504라고 타임아웃만 늘리기보다 느린 작업을 비동기로 바꿀 수 있는지 먼저 본다.

### 업스트림 keepalive를 켰더니 간헐적으로 502가 납니다. 원인은요?

앱이 놀고 있는 연결을 nginx보다 먼저 닫아서, nginx가 막 닫힌 연결에 요청을 보내는 경쟁 상태다. Node는 기본 keepAliveTimeout이 5초인데 nginx 업스트림 유지 시간은 기본 60초라 이런 일이 생기고, 로그에 `upstream prematurely closed connection`이 찍힌다. 앱의 유지 시간을 nginx보다 길게 하거나 upstream의 `keepalive_timeout`을 짧게 맞춘다. keepalive 자체는 `proxy_http_version 1.1`과 `Connection ""`이 함께 있어야 동작한다.

### nginx는 실패한 요청을 다른 서버로 재시도하나요? POST도 그런가요?

`proxy_next_upstream` 기본값인 `error timeout`에 해당하면 다음 서버로 넘긴다. 하지만 요청을 이미 업스트림에 보낸 뒤라면 POST 같은 멱등하지 않은 요청은 재시도하지 않는다. 첫 서버가 처리했는데 응답만 잃었을 수 있어서다. `non_idempotent`로 켤 수는 있지만 멱등성 키 같은 중복 방지가 있을 때만 쓰고, `tries`와 `timeout`으로 재시도가 장애를 키우지 않게 묶는다.

### WebSocket을 프록시할 때 필요한 설정과 끊기는 문제는요?

`Upgrade`와 `Connection`은 홉 바이 홉 헤더라 nginx가 넘기지 않으니, `proxy_http_version 1.1`과 함께 `map $http_upgrade`로 만든 값을 직접 실어 보낸다. 업그레이드 뒤에도 `proxy_read_timeout`이 적용돼 기본 60초 동안 메시지가 없으면 끊기므로, 타임아웃을 늘리고 앱에서 주기적으로 ping을 보낸다. reload 때 오래된 연결이 옛 worker를 붙잡으니 클라이언트 재연결 로직도 필요하다.
