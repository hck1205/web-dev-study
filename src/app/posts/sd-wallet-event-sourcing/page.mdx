이 시리즈에서 이 글의 자리: 앞 글 [디지털 지갑 설계 ①](/posts/sd-wallet-transfer)에서 샤드가 갈린 두 지갑 사이의 송금을 2PC, TC/C, 사가로 묶었다. 이 글은 같은 지갑을 잔액 칸이 아니라 사건의 기록으로 다시 쌓는다. 지난 시점의 잔액을 증명하고, 코드를 바꾼 뒤에도 계산이 같은지 확인하고, 한 노드가 더 많은 송금을 받게 만드는 게 목표다. 다음 글은 [증권 거래소 설계 ①](/posts/sd-stock-exchange-order-book)이고, 거래소도 이 글의 "같은 입력이면 같은 결과" 원리를 그대로 쓴다.

감사팀에서 메일이 왔다. "3월 15일 오후 3시 기준 u0601 고객의 잔액과, 그 잔액이 맞다는 근거를 주세요." 지갑 DB에는 지금 잔액 한 칸만 있다. 거래 내역 테이블이 있긴 하지만 잔액 칸과 따로 쓰여서, 둘이 어긋난 적이 없다고 말할 근거가 없다. 지난주 수수료 계산 코드를 고쳤는데 그게 과거 잔액에 영향을 줬는지도 모른다.

지갑은 "지금 얼마"만 맞으면 되는 시스템이 아니다. 왜 그 금액인지, 그때는 얼마였는지, 계산 규칙이 바뀌어도 과거가 그대로인지 답해야 한다. 이 글에서는 잔액 대신 잔액을 바꾼 사건을 저장하는 지갑을 Node로 만들어, 35만 건의 사건을 재생하고, 스냅숏으로 줄이고, 두 버전의 코드를 같은 기록 위에서 비교해 본다.

## 잔액 칸을 덮어쓰면 남지 않는 것

앞 글의 지갑은 `UPDATE wallets SET balance = balance - 30000`으로 잔액을 덮어쓴다. 덮어쓰는 순간 이전 값은 사라진다. 대사(reconciliation)로 총액이 안 맞는다는 걸 알아챌 수는 있다. 하지만 어디서부터, 왜 틀어졌는지는 덮어쓴 칸에서 찾을 수 없다.

잔액 대신 "u0601에서 26,000원이 빠졌다", "u0448에 26,000원이 들어왔다" 같은 사실을 차례로 이어 쓰면 이야기가 달라진다. 이렇게 상태를 바꾼 사실(사건)을 원본으로 저장하고 현재 상태는 사건을 처음부터 다시 적용해서 얻는 방식을 이벤트 소싱이라고 한다. 사건을 하나씩 접어 상태를 만드는 구조, 같은 스트림에 두 요청이 동시에 쓸 때의 버전 검사, 옛 형식 사건을 읽는 업캐스팅은 [이벤트 소싱 구현 글](/posts/event-sourcing)에서 다뤘다. 이 글은 지갑에 붙였을 때 생기는 질문에 집중한다.

지갑에서 쓰는 말 네 개를 먼저 정한다.

- 명령: 바깥에서 들어온 요청이다. "u0601이 u0448에게 26,000원 보내 줘." 거절될 수 있다.
- 사건: 이미 일어난 사실이다. "u0601에서 26,000원 출금됨." 한 번 쓰면 고치지 않는다.
- 상태: 사건을 모두 적용한 결과다. 사용자별 잔액 표다.
- 상태 기계: 명령을 검사해 사건을 만들고(결정), 사건을 상태에 적용하는(적용) 코드다.

명령과 사건을 굳이 나누는 이유는 둘의 성질이 달라서다. 명령은 처리하는 순간의 잔액, 수수료 정책, 외부 조회 결과에 따라 결과가 달라진다. 같은 송금 명령도 오늘은 성공하고 내일은 잔액 부족으로 거절될 수 있다. 사건은 그 판단이 끝난 결과라서 언제 다시 적용해도 같은 결과를 낸다. 뒤에서 실제로 확인한다.

## 명령 하나가 사건 두 개가 되기까지

지갑의 상태 기계는 함수 두 개다.

```js
// 결정: 지금 상태와 명령을 보고 사건을 만든다. 실패하면 빈 배열
function decide(state, cmd) {
  if (cmd.type === "Deposit") return [{ type: "Credited", tx: cmd.tx, user: cmd.user, amount: cmd.amount }];
  if (cmd.type === "Transfer") {
    if ((state.get(cmd.from) ?? 0) < cmd.amount) return [];          // 잔액 부족: 사건 없음
    return [
      { type: "Debited", tx: cmd.tx, user: cmd.from, amount: cmd.amount },
      { type: "Credited", tx: cmd.tx, user: cmd.to, amount: cmd.amount },
    ];
  }
  return [];
}
// 적용: 사건만 보고 상태를 바꾼다. 시계, 난수, 외부 조회를 쓰지 않는다
function apply(state, e) {
  const cur = state.get(e.user) ?? 0;
  state.set(e.user, e.type === "Debited" ? cur - e.amount : cur + e.amount);
}
```

사용자 1,000명에게 10만 원씩 넣고, 씨앗을 고정한 난수로 송금 명령 20만 건을 만들어 차례로 처리했다. 사건은 한 줄에 하나씩 JSON으로 파일 끝에 이어 썼다. 다 처리한 뒤의 상태는 사용자 id 순으로 정렬해 sha256으로 요약한 값(상태 해시)으로 남겼다. 두 상태가 같은지 이 16글자만 비교하면 된다.

```text
첫 사건 3줄:
{"seq":1,"type":"Credited","tx":"d0","user":"u0000","amount":100000}

```

명령 201,000건 중 25,381건은 잔액 부족으로 거절돼 사건을 남기지 않았다. 거절도 감사 대상이라면 `TransferRejected` 같은 사건으로 남길 수 있다. 성공한 송금은 출금과 입금 두 사건이 되고, 둘은 같은 `tx`로 묶인다. `seq`는 이 기록 안에서의 순번이다. 사건의 순서가 바뀌면 결과가 달라질 수 있으니(출금 전에 다른 출금이 끼면 잔액 부족이 될 수 있다) 사건은 반드시 하나의 순서로 쌓는다. 명령도 마찬가지라 처리 전에 하나의 줄(FIFO 큐)에 세운다.

## 그 시점의 잔액을 다시 계산한다

이제 감사팀 질문에 답할 수 있다. 사건 기록을 처음부터 원하는 순번까지만 적용하면 그 순간의 상태가 나온다. u0601의 잔액을 몇 군데서 멈춰 봤다.

```js
for (const e of events) {
  apply(s, e);
  if (marks.has(e.seq)) console.log(`seq ${e.seq} 까지 재생: u0601 = ${s.get("u0601")}`);
}
```

```text
seq   1000 까지 재생: u0601 = 100000
seq   1001 까지 재생: u0601 = 74000
seq  50000 까지 재생: u0601 = 221000
seq 150000 까지 재생: u0601 = 72000
seq 350238 까지 재생: u0601 = 17000
```

"3월 15일 오후 3시"를 순번으로 바꾸려면 사건에 기록 시각을 같이 적어 두고, 그 시각 이전의 마지막 순번까지 재생한다. 근거도 같이 나온다. 그 시점까지 u0601에 붙은 사건 목록이 곧 잔액의 근거다.

처음부터 전부 재생해서 처리할 때의 해시와 같은지도 봤다. 세 번 돌렸다.

## 다시 재생했더니 잔액이 다르다

같은 기록이면 같은 결과라는 성질은 적용 함수가 사건 밖의 것을 읽는 순간 깨진다. 송금 수수료 100원을 붙이면서 수수료를 설정 파일에서 읽게 짠 경우를 만들었다. 사건 기록은 그대로 두고, 다음 달 수수료가 150원으로 바뀐 뒤에 재생했다.

```js
const config = { fee: 100 };      // 바깥 설정: 운영 중에 바뀔 수 있다
function applyBad(s, e) {         // 적용 함수가 바깥 설정을 읽는다
  const cur = s.get(e.user) ?? 0;
  s.set(e.user, e.type === "Debited" ? cur - e.amount - config.fee : cur + e.amount);
}
```

```text
바깥 설정을 읽는 apply
  처리할 때 c878c17ea6881f9b  u0601=112200
  다시 재생 159f0dd7da46c13a  u0601=111300
```

같은 사건을 재생했는데 u0601의 잔액이 900원 다르다. 출금 사건 18건에 50원씩 더 붙었다. 감사팀에 "그때 잔액"을 물으면 재생하는 날마다 다른 답이 나온다. 수수료 대신 `Date.now()`로 야간 수수료를 정하거나, 환율 API를 부르거나, `Math.random()`으로 이벤트 당첨을 정해도 똑같이 깨진다.

고치는 방법은 바뀔 수 있는 값을 결정할 때 읽고, 그 값을 사건에 적는 것이다. 적용 함수는 사건만 본다.

```js
// 결정할 때 수수료를 사건에 적는다
return [{ type: "Debited", user: c.from, amount: c.amount, fee: config.fee }, /* … */];
// 적용 함수는 사건에 적힌 수수료만 쓴다
s.set(e.user, e.type === "Debited" ? cur - e.amount - e.fee : cur + e.amount);
```

```text
수수료를 사건에 적은 apply
  처리할 때 c878c17ea6881f9b  u0601=112200
  다시 재생 c878c17ea6881f9b  u0601=112200
```

이 실험에서 하나 더 알 수 있다. 명령을 다시 처리하면 같은 사건이 나오지 않는다. 수수료 설정이 150원으로 바뀐 뒤 명령을 다시 돌리면 출금 금액이 달라지고, 잔액 부족으로 거절되는 송금도 달라진다. 그래서 잃으면 안 되는 건 사건 기록이다. 상태와 스냅숏은 사건에서 언제든 다시 만들 수 있지만, 사건은 명령에서 다시 만들 수 없다.

## 코드를 바꾼 뒤 같은 답을 내는지 확인한다

사건 기록이 있으면 새 버전의 코드를 배포하기 전에 과거 전체를 돌려 볼 수 있다. 메모리를 아끼려고 잔액을 천 원 단위 정수로 저장하도록 적용 함수를 고친 v2를 만들고, 운영 로그(수수료 100원이 사건에 들어 있다) 위에서 v1과 나란히 돌렸다. 1만 건마다 상태 해시를 비교했다.

```js
function v2(s, e) {                      // 천 원 단위로 저장하는 리팩터링
  const k = (x) => Math.floor(x / 1000);
  const cur = s.get(e.user) ?? 0;
  s.set(e.user, e.type === "Debited" ? cur - k(e.amount) - k(e.fee) : cur + k(e.amount));
}
```

## 35만 건을 매번 처음부터 읽지 않는다

처음부터 재생하면 이 데이터에서 0.5초가 걸렸다. 사건이 쌓일수록 서버를 재시작하거나 새 복제본을 띄울 때 걸리는 시간이 늘어난다. 그래서 일정 간격마다 그 순간의 상태 전체를 스냅숏으로 저장한다. 사건 하나의 스트림마다 스냅숏을 두는 방식은 [이벤트 소싱 구현 글](/posts/event-sourcing)에서 봤다. 지갑의 상태 기계는 사용자 1,000명의 잔액 전체를 한 번에 들고 있으니 스냅숏도 전체 잔액 표 하나다.

여기서 하나 더 적어 둔다. 스냅숏 직후의 사건이 파일 어디서 시작하는지(바이트 위치)다. 이게 없으면 스냅숏을 쓰고도 기록 전체를 읽으며 순번을 걸러야 한다. 실제로 처음엔 위치를 안 적어서 seq 200000 스냅숏에서 출발해도 470ms가 걸렸다.

```text
{"seq":200000,"offset":15124345,"state":{"u0000":124000,"u0001":80000,"u0002":6000,…
```

10만 건마다 스냅숏을 남겼고, 마지막 스냅숏(seq 300000)에서 시작해 그 위치부터만 읽었다.

```js
const snap = JSON.parse(fs.readFileSync("snapshot-300000.json", "utf8"));
const s = new Map(Object.entries(snap.state));
// 스냅숏이 적어 둔 위치부터만 읽는다
const buf = Buffer.alloc(size - snap.offset);
fs.readSync(fd, buf, 0, buf.length, snap.offset);
```

```text
스냅숏(seq 300000) + 뒤 50238건: 58.8ms, 해시 f7729d926916645d
스냅숏(seq 300000) + 뒤 50238건: 61.4ms, 해시 f7729d926916645d
스냅숏(seq 300000) + 뒤 50238건: 61.0ms, 해시 f7729d926916645d
```

460ms 남짓이던 것이 60ms로 줄었고 해시는 같다. 스냅숏은 원본이 아니라 다시 만들 수 있는 캐시라서, 적용 함수가 바뀌면 옛 스냅숏을 버리고 사건에서 다시 만든다. 스냅숏을 믿기 전에 가끔 처음부터 재생한 해시와 비교하는 검사를 돌리면 스냅숏 자체의 버그도 잡힌다.

## 한 노드를 빠르게, 그리고 잃지 않게

앞 글에서 초당 2만 건 송금에 DB 29대가 필요하다고 어림했다. 한 노드가 받는 양을 늘리면 그 수가 줄어든다. 사건을 이어 쓰는 구조는 여기서 유리하다. 하는 일이 파일 끝에 덧붙이기뿐이라서다. 같은 크기의 사건 5,000건을 몇 가지 방식으로 써 봤다.

```text
PostgreSQL에 한 건씩 커밋   5000건 2149.7ms  초당 2,326건
쓰기만(fsync 없음)          5000건     7.7ms  초당 647,387건
한 건마다 fsync            5000건  1132.4ms  초당 4,416건
100건마다 fsync           5000건    21.3ms  초당 234,376건
```

이 머신의 디스크와 로컬 PostgreSQL 기준이고 장비마다 크게 다르다. 그래도 방향은 분명하다. 가장 비싼 건 디스크에 확실히 내려 쓰라는 `fsync`다. 한 건마다 부르면 초당 4천 건 남짓이고, 100건을 모아 한 번에 부르면 50배 넘게 빨라진다. 여러 명령의 사건을 모아 한 번에 디스크에 내리는 이 방식을 그룹 커밋이라고 한다. 대신 모으는 동안 응답이 늦어지니 "몇 건 또는 몇 밀리초 중 먼저 오는 쪽"으로 묶는다. fsync 없이 쓰기만 하면 가장 빠르지만 전원이 나가면 OS가 아직 디스크에 내리지 않은 사건을 잃는다.

상태도 노드 안에 둔다. 잔액 표를 메모리에 두고, 디스크에는 쓰기에 강한 내장 키-값 저장소(RocksDB 같은 LSM 트리 기반)나 SQLite에 저장한다. 외부 DB로 가는 네트워크 왕복이 사라진다.

문제는 이렇게 하면 노드가 상태를 들고 있게 된다는 것이다. 그 디스크가 망가지면 사건 기록이 사라진다. 앞 절에서 본 대로 잃으면 안 되는 건 사건 기록 하나다. 그래서 사건 기록만 여러 노드에 같은 순서로 복제한다. 여러 노드가 같은 순서의 기록을 갖게 하는 합의 알고리즘으로 Raft를 많이 쓴다. 리더가 사건을 받아 팔로워들에게 보내고, 과반이 받았다고 답하면 그 사건을 확정한다. 동작은 [Raft 글](/posts/raft-consensus)에 있다.

## 잔액 조회는 다른 길로 간다

쓰기 쪽은 명령을 받아 사건을 쓰는 일만 한다. "내 잔액 보여 줘", "이번 달 내역 보여 줘" 같은 조회는 사건을 따라 읽으며 조회용 표를 채우는 별도의 읽기 전용 상태 기계가 맡는다. 바꾸는 모델과 읽는 모델을 나누는 이 구조가 [CQRS](/posts/cqrs)다.

그러면 송금 요청을 보낸 앱은 결과를 언제 아나. 명령은 줄에 섰다가 처리되니 요청에 바로 결과를 실어 보낼 수 없다. 앱이 주기적으로 물어보면(폴링) 늦고, 사용자가 많으면 조회 서버가 버티지 못한다. 그래서 앱과 지갑 사이에 응답을 대신 기다려 주는 프록시를 둔다. 읽기 쪽 상태 기계는 사건을 반영하는 즉시 그 결과를 프록시에 밀어 주고(push), 프록시가 기다리던 요청에 응답한다. 사용자 입장에서는 요청 하나에 응답 하나다.

읽기 쪽은 쓰기보다 늦다. 송금 직후 잔액을 보면 잠깐 옛 값일 수 있다. 이 지연을 다루는 방법(내가 쓴 것은 바로 보이게 하기, 버전 기다리기)은 [CQRS 글](/posts/cqrs)에 있다.

현장에서 이 구조를 운영할 때 보는 지표도 적어 둔다. 읽기 기계가 쓰기 쪽 기록을 얼마나 뒤따라오는지(마지막 적용 순번의 차이), 리더의 그룹 커밋 대기 시간, 스냅숏 이후 쌓인 사건 수다. 마지막 값이 커지면 재시작이 오래 걸린다는 뜻이다. 흔한 실수는 적용 함수 안에서 시계나 설정을 읽는 것, 사건 기록과 별도로 잔액 테이블을 직접 고치는 관리자 도구를 만드는 것, 스냅숏을 원본처럼 백업하고 사건 기록은 백업하지 않는 것이다.

## 다음은 같은 원리로 움직이는 거래소

지갑의 원본은 사건 기록이고, 잔액은 그 기록을 결정적인 함수로 적용한 결과다. 그래서 그 시점의 잔액을 다시 계산할 수 있고, 새 코드를 과거 전체에 돌려 어긋나는 사건을 찾을 수 있으며, 사건만 복제해도 복제본이 같은 잔액을 갖는다. 적용 함수가 사건 밖의 것을 읽지 않는 것, 사건 기록만큼은 잃지 않는 것 두 가지가 전부를 받친다.

[증권 거래소 설계 ①](/posts/sd-stock-exchange-order-book)에서는 매수·매도 주문을 짝짓는 호가창과 매칭 엔진을 만든다. [②](/posts/sd-stock-exchange-low-latency)에서는 이 글의 결정적 재생을 마이크로초 단위의 지연 목표와 함께 다시 만난다.

## 면접에서 나올 만한 질문

### 지갑에 이벤트 소싱을 쓰면 무엇이 좋아지나요?

잔액이 왜 그 값인지 증명할 수 있다. 잔액을 덮어쓰지 않고 잔액을 바꾼 사건을 원본으로 남기니, 처음부터 원하는 순번까지 재생하면 그 시점의 잔액과 근거가 함께 나온다. 같은 기록을 새 코드로 재생해 결과를 비교하면 코드 변경이 과거 계산을 바꿨는지도 확인할 수 있다.

### 명령과 사건은 어떻게 다른가요?

명령은 바깥에서 온 요청이라 처리하는 순간의 상태와 정책에 따라 성공하거나 거절되고, 결과도 달라질 수 있다. 사건은 판단이 끝난 사실이라 다시 적용해도 늘 같은 결과를 낸다. 송금 명령 하나는 출금과 입금 두 사건이 되거나, 잔액 부족이면 사건을 남기지 않는다.

### 상태 기계가 결정적이어야 하는 이유는요?

같은 사건을 같은 순서로 적용하면 언제 어디서든 같은 상태가 나와야 재생과 복제가 성립한다. 적용 함수가 바깥 설정을 읽게 만든 실험에서는 수수료 정책이 바뀐 뒤 재생하자 같은 사용자의 잔액이 900원 달라졌다. 바뀔 수 있는 값은 결정 단계에서 읽어 사건에 적고, 적용 함수는 사건만 본다.

### 무엇을 반드시 잃지 않아야 하나요? 명령 기록이면 충분하지 않나요?

사건 기록이다. 상태와 스냅숏은 사건에서 다시 만들 수 있지만, 명령을 다시 처리하면 그때의 잔액과 정책에 따라 다른 사건이 나온다. 그래서 사건 기록만 Raft 같은 합의로 여러 노드에 같은 순서로 복제하고, 나머지는 각 노드가 사건을 적용해 만든다.

### 사건이 수억 건 쌓이면 재시작이 오래 걸리지 않나요?

일정 간격으로 전체 상태를 스냅숏으로 저장하고, 재시작 때는 마지막 스냅숏에서 출발해 그 뒤의 사건만 적용한다. 스냅숏에는 다음 사건의 파일 위치를 함께 적어야 기록 전체를 읽지 않는다. 35만 건 실험에서 460ms 남짓이던 재생이 60ms로 줄었고 상태 해시는 같았다.

### 이벤트 소싱으로 초당 처리량을 어떻게 올리나요?

외부 DB 대신 노드의 로컬 디스크에 사건을 이어 쓰고, 상태는 메모리와 내장 저장소에 둔다. 가장 비싼 fsync는 여러 사건을 모아 한 번에 부르는 그룹 커밋으로 줄인다. 실험에서 한 건마다 fsync하면 초당 4천 건 남짓, 100건마다 하면 20만 건을 넘었다. 노드가 상태를 갖게 되니 사건 기록을 복제해 디스크 장애에 대비한다.

### 송금 결과를 사용자는 언제, 어떻게 받나요?

명령은 줄을 서서 처리되니 요청에 바로 결과를 실을 수 없다. 앱이 폴링하면 늦고 조회 서버에 부하가 몰린다. 앱과 지갑 사이에 프록시를 두고, 읽기 쪽 상태 기계가 사건을 반영하자마자 결과를 프록시에 밀어 주면 앱은 요청 하나에 응답 하나를 받는다.

### 한 Raft 그룹으로 감당이 안 되면요?

사용자를 여러 파티션으로 나누고 파티션마다 Raft 그룹을 둔다. 같은 파티션 안의 송금은 상태 기계 하나가 처리하고, 파티션을 넘는 송금은 TC/C나 사가 코디네이터가 각 파티션에 명령을 보내 묶는다. 이때도 각 단계는 사건으로 남아 재생할 수 있다.
