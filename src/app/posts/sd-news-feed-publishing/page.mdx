이 시리즈에서 이 글의 자리: [㉓ 알림 시스템 ②](/posts/sd-notification-reliability)에서 메시지를 잃지 않고 여러 사람에게 보내는 법을 봤다. 이 글부터 두 편은 뉴스 피드를 설계한다. 이 글은 쓰는 쪽, 글 하나가 팔로워들의 피드에 들어가는 길을 다룬다. 같은 장의 다음 글 [㉕ 뉴스 피드 ②: 피드 캐시와 페이지 넘기기](/posts/sd-news-feed-retrieval)가 읽는 쪽을 맡고, 그다음은 [㉖ 채팅 ①](/posts/sd-chat-connections)이다.

앱을 열면 친구가 5초 전에 올린 사진이 맨 위에 있다. 내가 팔로우하는 사람이 300명이라면 앱은 300명이 쓴 글 가운데 가장 최근 20개를 순식간에 골라낸 셈이다. 300명에게 일일이 물어본 걸까, 아니면 누가 미리 골라 둔 걸까.

면접의 "뉴스 피드 시스템을 설계하라"는 이 질문 하나로 귀결된다. 피드를 만드는 일을 글을 쓸 때 할지, 읽을 때 할지. 이 글은 표 하나로 만든 피드에서 시작해 두 방식을 같은 가짜 SNS에서 돌려 보고, 팔로워가 100만 명인 계정이 글을 쓰는 순간 무엇이 무너지는지 따라간다.

## 표 하나와 쿼리 하나로 만든 피드

기능은 두 개로 좁힌다. 글을 올리는 `POST /v1/me/feed`, 내 피드를 보는 `GET /v1/me/feed`. 피드에는 내가 팔로우한 사람의 글이 최신순으로 나온다. 추천이나 순위 매기기는 빼고 시간순만 다룬다.

가장 작은 버전은 서버 한 대와 DB 하나다. 글은 `posts`에, 누가 누구를 팔로우하는지는 `follows`에 넣는다. PostgreSQL 16에 사용자 10만 명, 글 200만 개를 넣었다.

```sql
CREATE TABLE follows (follower_id bigint NOT NULL, followee_id bigint NOT NULL,
                      PRIMARY KEY (follower_id, followee_id));
CREATE TABLE posts (id bigint PRIMARY KEY, author_id bigint NOT NULL, body text NOT NULL,
                    created_at timestamptz NOT NULL DEFAULT now());
CREATE INDEX posts_author_id_idx ON posts (author_id, id DESC);  -- 작성자별 최신 글
-- 사용자 42는 150명을, 사용자 43은 3,000명을 팔로우한다
```

피드는 쿼리 한 줄이다. 내가 팔로우한 사람들의 글을 최신순으로 20개 가져온다.

```sql
EXPLAIN ANALYZE
SELECT p.id, p.author_id FROM posts p
WHERE p.author_id IN (SELECT followee_id FROM follows WHERE follower_id = 42)
ORDER BY p.id DESC LIMIT 20;
```

- 쓰기: 1,000만 × 0.5 ÷ 86,400초 = 초당 약 58개.
- 피드 읽기: 1,000만 × 10 ÷ 86,400 = 초당 약 1,157번. 저녁 피크가 세 배면 3,500번 가까이 된다.

읽기가 쓰기의 20배다. 그런데 위 구조는 비싼 일(모으고 정렬하기)을 전부 읽기 쪽에 몰아 두었다. 같은 친구의 피드를 하루 열 번 열면 거의 같은 계산을 열 번 한다. 그러면 계산을 쓰기 쪽으로 옮기면 어떨까.

## 글을 쓸 때 미리 나눠 넣는다

한 곳에서 여러 곳으로 퍼뜨리는 일을 팬아웃(fan-out)이라고 한다. 부채(fan)를 펼치듯 하나가 여럿으로 갈라진다는 뜻이다. 뉴스 피드에서는 "글 하나를 팔로워 여러 명의 피드에 넣는 일"이다. 언제 펼치느냐에 따라 두 방식으로 나뉜다.

쓰기 시점 팬아웃(fan-out on write)은 글을 쓰는 순간 펼친다. 사용자마다 자기 피드 목록을 하나씩 갖고 있고, 누가 글을 쓰면 그 글의 ID를 팔로워 전원의 목록 맨 앞에 넣는다. 우편함에 비유하면 집집마다 우편함이 있고, 글이 나오면 우체부가 구독자 우편함에 한 부씩 넣어 두는 셈이다. 밀어 넣는다고 해서 push 모델이라고도 부른다.

## 읽을 때 모아 온다

읽기 시점 팬아웃(fan-out on read)은 반대다. 글을 쓰면 내 타임라인(내가 쓴 글 목록)에만 넣는다. 누가 피드를 열면 그 사람이 팔로우한 사람들의 타임라인을 모두 가져와 합치고, 최신 20개를 고른다. 당겨 온다고 해서 pull 모델이라고도 한다. 앞의 SQL 버전이 바로 이 방식이다.

각 타임라인은 이미 최신순이라 전부 합쳐 정렬할 필요는 없다. 목록마다 맨 앞을 가리키는 손가락을 두고, 그중 가장 최신인 글을 하나씩 뽑으면 된다. 이것을 k개 목록 병합(k-way merge)이라고 한다.

## 같은 가짜 SNS에서 둘을 돌려 보기

말로만 비교하면 감이 오지 않아서 Node 22로 가짜 SNS를 만들어 세 방식을 돌렸다. 사용자 10만 명이 각자 일반 사용자 150명을 무작위로 팔로우하고, 유명인 세 명은 팔로워가 각각 8만, 4만, 2만 명이다. 하루 동안 일반 사용자가 글 2만 개, 유명인이 15개를 쓰고, 피드 읽기가 5만 번 일어난다. 피드 목록은 최신 500개까지만 둔다.

```js
// fanout.mjs 일부: 글 하나를 처리하는 부분. mode가 push거나, hybrid인데 팔로워가 기준보다 적으면 펼친다
for (const p of posts) {
  timelines.get(p.author).unshift(p.id);              // 내 타임라인에는 항상 넣는다
  const push = mode === "push" || (mode === "hybrid" && followers[p.author].length < threshold);
  if (push) {
    for (const f of followers[p.author]) {           // 팔로워마다 피드 맨 앞에 ID 하나
      const feed = feeds.get(f) ?? []; feed.unshift(p.id);
      if (feed.length > FEED_CAP) feed.pop();         // 500개를 넘으면 가장 오래된 것을 버린다
      feeds.set(f, feed); writes++;
    }
  }
}
```

```bash
node fanout.mjs
```

push는 글 2만 개를 위해 쓰기를 371만 번 했다. pull의 186배다. 피드에 쌓인 항목도 370만 개인데, 그중 61%(`unreadStored`)는 그날 앱을 한 번도 열지 않은 사람의 피드에 들어갔다. 읽을 사람 없는 우편함을 열심히 채운 셈이다. 반대로 pull은 피드 한 번에 타임라인을 평균 151.4개(`lookupsPerRead`) 조회했다.

시간 열은 한 프로세스의 메모리 안에서 잰 값이라 실제 서비스와 차이가 크다. 실제로는 조회 하나하나가 네트워크를 건넌다. 그래서 같은 동작을 로컬 Redis 7.0에 직접 해 봤다. 피드는 Redis의 정렬된 셋(sorted set, 점수 순으로 정렬해 두는 집합)에 넣었다. 자료구조 자체는 [Redis 기본 글의 정렬된 셋](/posts/redis-basics#셋과-정렬된-셋-중복-없는-모음과-순위표)에 있다.

```js
// redis-fanout.mjs 일부: 팔로워 1,000명씩 묶어 파이프라인으로 보낸다
cmds.push(["ZADD", `feed:${f}`, postId, postId]);           // 점수와 멤버 모두 글 ID
cmds.push(["ZREMRANGEBYRANK", `feed:${f}`, 0, -(CAP + 1)]); // 최신 500개만 남긴다
```

같은 컴퓨터 안의 Redis라 네트워크 지연이 거의 없는데도 차이가 분명하다. push 읽기는 명령 하나라 0.061ms, pull 읽기는 150개를 한 번에 보내도(파이프라인) 2.46ms로 40배, 하나씩 기다리며 보내면 10.5ms다. 서버가 다른 기계에 있으면 왕복마다 수백 µs가 더 붙는다. 쓰기는 반대로 push가 무겁다. 팔로워 150명인 글은 2.6ms면 끝났지만, 팔로워 100만 명인 글 하나는 4초 넘게 걸렸다.

| | 쓰기 시점 팬아웃 (push) | 읽기 시점 팬아웃 (pull) |
|---|---|---|
| 글 하나의 쓰기 | 팔로워 수만큼 | 한 번 |
| 피드 읽기 | 내 목록 하나 | 팔로우한 사람 수만큼 조회 후 병합 |
| 저장 공간 | 팔로워마다 ID 하나씩 | 거의 없음 |
| 새 글이 보이는 시점 | 팬아웃이 끝난 뒤 | 바로 |
| 약한 곳 | 팔로워가 아주 많은 계정, 안 들어오는 사용자 | 팔로우가 많은 사용자, 읽기 피크 |

읽기가 쓰기보다 20배 많은 서비스라면 push가 유리하다. 피드를 여는 순간의 지연이 사용자가 느끼는 속도이기 때문이다. 문제는 표의 마지막 줄이다.

## 팔로워 100만 명이 글을 쓰는 순간

팔로워 수는 고르게 퍼져 있지 않다. 대부분은 수백 명이고, 아주 소수가 수십만~수천만 명을 가진다. push에서는 이 소수가 글을 쓸 때마다 팔로워 수만큼 쓰기가 한꺼번에 몰린다. 이것을 유명인 문제(celebrity problem)라고 부른다. 앞의 [샤딩 글에서 본 핫스팟](/posts/sd-sharding-intro)이 피드에서 나타난 모습이다.

위 측정에서 100만 명 팬아웃은 Redis 한 대에서 4초가 걸렸고, 피드 키 100만 개가 86MB를 차지했다. 실제 서비스에서는 이 쓰기가 여러 Redis 샤드로 흩어지니 한 대가 4초를 다 받지는 않는다. 그래도 세 가지가 문제가 된다.

- 늦게 보인다. 100만 번째 팔로워의 피드에는 몇 초에서 몇 분 뒤에 들어간다. 그사이 그 팔로워가 피드를 열면 글이 없다.
- 줄이 밀린다. 팬아웃 작업이 한 줄로 서 있다면 유명인 글 하나 뒤에 일반 사용자 글 수천 개가 기다린다. 친구가 방금 쓴 글이 유명인 때문에 늦게 뜬다.
- 낭비가 크다. 시뮬레이션에서 61%가 그날 들어오지 않은 사람의 피드로 갔다. 팔로워가 많을수록 안 들어오는 사람도 많다.

pull로 바꾸면 이 문제는 사라지지만, 그 대신 모든 사용자의 읽기가 다시 비싸진다. 그래서 둘을 섞는다.

## 대부분은 밀고, 유명인만 당긴다

혼합 팬아웃(hybrid fan-out)은 작성자에 따라 방식을 고른다. 팔로워가 기준보다 적은 일반 사용자의 글은 push로 미리 넣는다. 기준을 넘는 계정의 글은 자기 타임라인에만 두고, 피드를 읽을 때 그 계정들의 타임라인만 따로 당겨 와 내 피드 목록과 합친다.

시뮬레이션의 `hybrid` 줄이 이 방식이다. 팔로워 1만 명 이상인 세 명만 pull로 돌렸더니 쓰기가 371만에서 301만으로 19% 줄었다. 하루 글 2만 15개 가운데 15개가 쓰기의 19%를 차지하고 있었다는 뜻이다. 가장 무거운 글 하나의 처리 시간(`worstPublishMs`)도 54ms에서 11ms로 줄었다. 읽기는 내 목록 하나에 팔로우한 유명인 수만큼 조회가 더해져 평균 2.4번이 됐다. pull의 151번보다 훨씬 적다.

기준값은 정답이 없다. 팔로워 수 분포를 보고, 기준을 넘는 계정 수가 "한 사람이 평균적으로 팔로우하는 유명인 수"를 작게 유지하는 선에서 정한다. 유명인을 200명 팔로우한 사람은 읽기에서 200번을 당겨야 하니, 읽을 때 당겨 올 계정 수에 상한을 두거나 그 사람에게는 유명인 글도 미리 넣어 주는 예외를 둔다.

push 쪽의 낭비를 줄이는 방법도 하나 더 있다. 최근 며칠 안에 들어온 활성 사용자에게만 밀어 넣고, 오래 안 들어온 사람의 피드는 비워 둔다. 그 사람이 돌아오면 그때 pull로 피드를 다시 만든다. 이 재구성은 읽기 쪽 일이라 [㉕](/posts/sd-news-feed-retrieval)에서 다룬다.

경계에서 생기는 일도 있다. 어떤 계정이 하루 사이에 팔로워 1만 명을 넘으면, 그 전에 쓴 글은 이미 push로 들어가 있고 새 글부터 pull로 온다. 읽을 때 두 목록을 합치면 같은 글이 두 번 나올 수 있으니 병합할 때 글 ID로 중복을 지운다.

- 팔로우 그래프는 "누가 누구를 팔로우하나"를 담는다. 관계형 DB의 `follows` 테이블로 충분한 경우가 많고, 친구의 친구를 따라가는 질의가 많으면 [그래프 DB](/posts/db-type-graph)를 쓰기도 한다. 팬아웃은 한 단계 관계만 보니 테이블과 인덱스로도 빠르다.
- 작업은 크게 하나로 두지 않는다. 팔로워 100만 명인 글은 "팔로워 1~1,000번", "1,001~2,000번"처럼 1,000개의 작은 작업으로 쪼개 큐에 넣는다. 작업자 여러 대가 나눠 처리하고, 하나가 실패해도 그 조각만 다시 하면 된다.
- 유명인 작업은 줄을 따로 세운다. 큰 팬아웃용 큐와 일반 큐를 나누면 일반 사용자의 글이 유명인 글 뒤에서 기다리지 않는다.
- 피드 캐시에는 글 ID만 넣는다. 본문을 팔로워마다 복사하면 메모리가 수백 배로 늘고, 글을 고칠 때 모든 사본을 고쳐야 한다. ID만 넣으면 본문은 한 곳에서 고친다. 피드 하나가 메모리를 얼마나 쓰는지는 [㉕](/posts/sd-news-feed-retrieval)에서 잰다.

글 하나를 여러 받는 쪽에 복사하는 구조는 [발행·구독](/posts/pub-sub)과 닮았다. 차이는 받는 쪽이 사용자 수만큼 있다는 데 있다. 토픽을 사용자마다 만들 수는 없으니, 피드는 "구독자마다 우편함 하나"를 직접 관리한다.

## 작업자가 같은 글을 두 번 넣으면

팬아웃 작업자는 큐에서 작업을 받아 Redis에 쓰고, 끝나면 큐에 "처리했다"고 알린다. 그런데 Redis에 다 쓴 직후 작업자가 죽거나 응답이 늦어 시간 초과가 나면, 큐는 그 작업을 다른 작업자에게 다시 준다. 큐는 보통 "최소 한 번 전달"을 보장하기 때문이다. 전달 보장의 종류는 [메시지 전달 보장](/posts/message-delivery-semantics)에 정리되어 있다.

리스트와 정렬된 셋에 같은 ID를 두 번 넣어 봤다.

```bash
# 같은 글 ID를 두 번 넣는다: 리스트는 LPUSH, 정렬된 셋은 ZADD (점수와 멤버 모두 글 ID)
redis-cli -p 6420
```

```text
127.0.0.1:6420> LPUSH feed:list:7 9001
(integer) 1
127.0.0.1:6420> LPUSH feed:list:7 9001
(integer) 2
127.0.0.1:6420> LRANGE feed:list:7 0 -1
1) "9001"
2) "9001"
127.0.0.1:6420> ZADD feed:7 9001 9001
(integer) 1
127.0.0.1:6420> ZADD feed:7 9001 9001
(integer) 0
127.0.0.1:6420> ZRANGE feed:7 0 -1 REV
1) "9001"
```

리스트는 두 번째 `LPUSH`에도 길이가 2로 늘었다. 그 사용자의 피드에 같은 글이 두 줄로 보인다. 정렬된 셋은 두 번째 `ZADD`가 0을 돌려줬다. 이미 있는 멤버라 새로 추가된 것이 없다는 뜻이다. 같은 일을 여러 번 해도 결과가 같은 성질을 멱등성이라고 하는데, 정렬된 셋에 글 ID를 넣는 동작은 그 자체로 멱등이다. 일반적인 멱등 처리 방법은 [멱등성 키](/posts/idempotency-key)에 있다.

점수를 글 ID로 두는 데는 이유가 하나 더 있다. 작업 순서가 뒤섞여 9005가 9001보다 먼저 들어가도, 정렬된 셋은 점수 순으로 정렬하니 피드 순서가 맞다. 그러려면 글 ID가 시간순으로 커져야 한다. [⑰ 고유 ID 생성기](/posts/sd-unique-id-generator)의 Snowflake ID가 앞자리에 시각을 담는 이유가 여기서도 쓰인다. 다만 64비트 Snowflake ID는 Redis 점수(배정밀도 실수)가 정확히 담는 범위를 넘는다. 이 데모처럼 작은 ID에서는 괜찮지만 실제 ID에서는 함정이 생기는데, [㉕](/posts/sd-news-feed-retrieval)에서 직접 부딪혀 본다. 리스트는 메모리를 훨씬 적게 쓰는 장점이 있어서, 리스트를 쓴다면 읽을 때 중복을 지우는 단계를 둔다. 두 자료구조의 메모리 차이는 다음 글에서 숫자로 본다.

팬아웃 뒤에 일어나는 변화도 정해 둔다.

- 글을 지우면 팔로워 100만 명의 피드를 다 뒤지지 않는다. 글 DB에 지움 표시를 하고, 피드를 읽을 때 지워진 글을 걸러 낸다.
- 언팔로우하면 그 사람의 글을 내 피드에서 지우는 작업을 뒤에서 천천히 하거나, 역시 읽을 때 거른다.
- 새로 팔로우하면 그 사람의 최근 글 몇 개를 내 피드에 채워 넣는다. 그래야 팔로우 버튼을 누르고 피드를 열었을 때 바로 보인다.

## 친구 글이 몇 분 늦게 뜬다는 문의가 오면

push 구조에서 가장 흔한 문의는 "글을 올렸는데 친구 피드에 늦게 뜬다"다. 글은 이미 저장됐으니 작성자 본인의 타임라인에는 보인다. 늦는 곳은 팬아웃이다. 순서대로 본다.

1. 큐가 얼마나 밀렸나. 쌓인 작업 수와 소비자 지연(lag, 생산된 위치와 소비한 위치의 차이)을 본다. 이 값이 계속 늘면 작업자 처리량이 들어오는 양을 못 따라가는 중이다.
2. 언제부터 밀렸나. 특정 시각에 갑자기 늘었다면 그 시각에 팔로워가 많은 계정이 글을 썼는지 본다. 큐를 나눴는데도 일반 큐가 밀렸다면 기준값을 넘는 계정이 일반 큐로 들어가고 있다는 신호다.
3. 피드 캐시가 느린가. Redis 샤드별 초당 명령 수와 응답 시간을 본다. 한 샤드만 바쁘면 키 분배가 치우친 것이다.

이 장애를 미리 잡으려면 "글을 쓴 시각부터 마지막 팔로워 피드에 들어간 시각까지"를 팬아웃 지연 지표로 남겨 두고, p99(가장 느린 1%의 경계값)에 알림을 건다. 큐 길이만 보면 작업이 쪼개진 정도에 따라 숫자가 달라져 판단이 어렵다.

메모리도 같이 본다. 잘라 내기(`ZREMRANGEBYRANK`)를 빠뜨리면 피드가 끝없이 길어져 Redis 메모리가 하루하루 늘어난다. 팬아웃 코드를 고친 배포 뒤에 메모리 그래프가 꺾이지 않고 오르기만 하면 이것부터 의심한다.

## 팬아웃 쓰기량 어림하기

면접에서는 "push로 하면 초당 쓰기가 몇 번인가"를 꼭 묻는다. 하루 활성 사용자, 한 사람의 하루 평균 글 수, 평균 팔로워 수, 피크 배수를 받아 `[초당 글 수, 초당 피드 쓰기, 피크 때 초당 피드 쓰기]`를 돌려주는 함수를 짜 보자. 셋 모두 반올림한 정수로 돌려주고, 반올림은 마지막에 한 번만 한다.

<CodePlayground

  // postQps: 하루 글 수 / 86400
  // writesPerSec: postQps * 평균 팔로워 수
  // peakWritesPerSec: writesPerSec * 피크 배수
  // 셋 다 마지막에 Math.round
  return [0, 0, 0];
}`}
  solution={`function fanoutLoad(dau, postsPerUserPerDay, avgFollowers, peakFactor) {
  const postQps = (dau * postsPerUserPerDay) / 86400;
  const writes = postQps * avgFollowers;
  return [Math.round(postQps), Math.round(writes), Math.round(writes * peakFactor)];
}`}

본문의 가정이면 초당 글 58개가 피드 쓰기 1만 1,574번이 되고, 피크에는 3만 5천 번 가까이 된다. 앞의 Redis 측정에서 150명 팬아웃(쓰기 300번)이 2.6ms였으니 Redis 몇 대로 받을 수 있는 양이다. 평균 팔로워가 10배가 되면 피크 35만 번이 되는데, 이 숫자가 혼합 팬아웃의 기준값을 정할 때 출발점이 된다. 평균은 유명인 몇 명이 크게 끌어올리므로 실제로는 팔로워 분포를 보고 계산한다.

## 다음에 읽을 글

쓰는 쪽은 이렇게 정리된다. 표 하나로 만든 피드는 읽을 때마다 모으고 정렬해서 읽기가 많은 서비스에 맞지 않는다. 쓰기 시점 팬아웃은 글을 쓸 때 팔로워 피드에 ID를 미리 넣어 읽기를 명령 하나로 만들고, 그 대가로 쓰기와 저장이 팔로워 수만큼 늘어난다. 팔로워가 아주 많은 계정만 읽기 시점으로 돌리는 혼합 방식이 둘의 약점을 함께 줄인다. 팬아웃은 큐 뒤에서 작은 조각으로 나눠 돌리고, 정렬된 셋과 시간순 ID로 재시도와 순서 문제를 막는다.

남은 건 읽는 쪽이다. 피드 캐시에서 꺼낸 ID 20개를 화면에 보일 글로 바꾸는 법, 스크롤을 내릴 때 같은 글이 두 번 나오지 않게 페이지를 넘기는 법, 캐시가 비어 있는 사용자의 피드를 다시 만드는 법은 [㉕ 뉴스 피드 ②](/posts/sd-news-feed-retrieval)에서 이어 간다. 캐시를 채우고 지우는 일반 패턴은 [캐시 전략](/posts/caching-strategies)에 있다.

## 면접에서 나올 만한 질문

### 쓰기 시점 팬아웃과 읽기 시점 팬아웃은 무엇이 다른가요?

쓰기 시점은 글을 쓸 때 팔로워 피드마다 글 ID를 미리 넣고, 읽기 시점은 피드를 열 때 팔로우한 사람들의 글을 모아 합친다. 쓰기 시점은 읽기가 명령 하나라 빠르지만 쓰기와 저장이 팔로워 수만큼 늘어난다. 읽기 시점은 쓰기가 한 번이지만 피드를 열 때마다 팔로우한 사람 수만큼 조회한다. 읽기가 쓰기보다 훨씬 많은 피드 서비스는 쓰기 시점을 기본으로 둔다.

### 팔로워가 수백만 명인 계정이 글을 쓰면 어떻게 되나요?

쓰기 시점 팬아웃에서는 글 하나가 수백만 번의 쓰기가 되어 팔로워 피드에 늦게 들어가고, 같은 큐에 있는 다른 글까지 밀린다. 그래서 팔로워가 기준을 넘는 계정은 팬아웃하지 않고, 읽을 때 그 계정의 타임라인만 따로 당겨 와 병합한다. 큰 팬아웃 작업은 큐를 따로 두고 작은 조각으로 나눠 여러 작업자가 처리하게 한다.

### 혼합 방식의 기준값은 어떻게 정하나요?

팔로워 수 분포를 보고 정한다. 기준이 낮으면 pull 대상 계정이 많아져 한 사람의 피드 읽기에서 당겨 올 타임라인이 늘고, 높으면 큰 팬아웃이 다시 생긴다. 한 사람이 팔로우하는 유명인 수가 작게 유지되는 선을 고르고, 그래도 많이 팔로우한 사용자에게는 당겨 올 수에 상한을 둔다.

### 팬아웃을 글 올리기 요청 안에서 하지 않고 큐로 넘기는 이유는요?

팬아웃이 끝날 때까지 응답을 기다리면 팔로워가 많은 사람은 글 올리기에 몇 초가 걸리고, 중간에 실패하면 어디까지 넣었는지 알기 어렵다. 글만 저장하고 응답한 뒤 큐에 작업을 넣으면 응답이 빠르고, 몰려드는 글을 큐가 받아 두며, 실패한 조각만 다시 처리할 수 있다. 대신 친구 피드에 보이기까지 짧은 지연이 생긴다.

### 작업이 재시도돼서 같은 글이 두 번 들어가면 어떻게 막나요?

피드를 정렬된 셋으로 두고 멤버를 글 ID로 하면 같은 ID를 몇 번 넣어도 하나만 남는다. 점수도 시간순으로 커지는 글 ID로 두면 작업이 뒤섞여 도착해도 피드 순서가 맞다. 리스트를 쓴다면 읽을 때 ID로 중복을 지우는 단계를 둔다.

### 트래픽이 10배가 되면 어디부터 손대나요?

피드 쓰기가 팔로워 수에 비례하니 팬아웃 작업자와 피드 캐시 샤드를 먼저 늘린다. 활성 사용자에게만 밀어 넣어 쓰지 않을 쓰기를 줄이고, 혼합 기준을 낮춰 큰 팬아웃을 pull로 돌린다. 글 DB는 쓰기가 초당 수백 개 수준이라 비교적 여유가 있고, 글 캐시의 핫 키를 따로 살핀다.

### 피드 캐시를 담은 Redis가 죽으면 피드가 사라지나요?

피드 캐시는 원본이 아니다. 원본은 글 DB와 팔로우 그래프에 있으니, 캐시가 비면 그 사용자의 피드를 읽기 시점 방식으로 다시 만들어 채운다. 다만 한꺼번에 많은 사용자의 피드가 비면 재구성이 DB로 몰리므로 복제본을 둔 Redis로 장애를 줄이고, 재구성 요청을 제한한다.
